### Title
Pool `repay`/`recapitalize` compute the refund from the declared `amount`, not from measured inbound tokens, so an unfunded "overpayment" refund drains pool custody — (`contracts/pool/src/ops/repay.rs`, `contracts/pool/src/ops/recapitalize.rs`)

### Summary
The external report is a bound computed against the wrong base: `buf_to_xdp` checked `len` against `xsk_pool_get_rx_frame_size() + vi->hdr_len` even though the first buffer's capacity excludes the header bytes consumed out of the headroom — i.e., a limit derived from the nominal layout instead of the actual capacity of that first element. The analog in XOXNO Lending is the pool-side overpayment refund: `repay` and `recapitalize` derive the refund purely from the caller-declared `amount` argument (`refund = amount - applied`), then push real tokens out of pool custody with `transfer_out`, without ever measuring how much the payer actually transferred in. The refund bound is anchored on the declared input, not on the pool's measured balance delta — the same "check against the wrong quantity" class.

### Finding Description
In `contracts/pool/src/ops/repay.rs:44-57`, `accounting` resolves the repay into `burned` debt shares and `overpayment`:

```rust
let (burned, overpayment) = cache.resolve_repay(amount, position);
let net_repay = amount.checked_sub(overpayment)...;
cache.credit_cash(net_repay);
```

`apply` then executes `outcome.cache.transfer_out(payer, outcome.overpayment)` (line 32). `overpayment = amount - current_debt_ceil`, computed entirely from the declared `action.amount`. Nothing in the leg measures the pool's token balance before/after, so the refund is paid out of existing pool custody regardless of whether any inbound transfer happened.

`contracts/pool/src/ops/recapitalize.rs:52-55` has the identical shape: `applied = amount.min(backing_shortfall)`, `refund = amount - applied`, then `transfer_out(&payer, refund)` at line 34. The doc comments state "The controller transfers `amount` into the pool before this call" — an assumption enforced nowhere in the pool itself.

This is confirmed by the codebase's own regression test `test_unfunded_repay_overpayment_refund_also_pays_out_of_custody` (`contracts/pool/tests/flows.rs:3590-3610`): calling `repay` on a market with zero debt makes the entire declared amount "excess," `net_repay` is zero, the `RepayRoundsToZeroShares` assert passes on its `net_repay == 0` disjunct, and the full declared amount is paid out of real custody with the book untouched. The test comment states the same holds for `recapitalize` ("Neither refund debits `cash` or passes `require_reserves`").

The correct bound — analogous to the kernel fix — is that the refund must be capped by what this call actually brought in (`measured_balance_delta`), not by `amount - applied` alone, because the "capacity" for a refund is the measured inflow, not the declared amount.

### Impact Explanation
If `pool::repay` or `pool::recapitalize` is reachable with a self-chosen `payer`/`amount` (the test invokes `repay` directly via the pool client), an unprivileged address declares an arbitrarily large `amount` against a market with low or zero debt (or zero backing shortfall), receives virtually the whole declared sum as an "overpayment" refund transferred from the pool's real token balance, and never deposits anything. That is direct theft of supplier funds held in custody, bounded only by the pool's token balance. Severity: Critical if reachable, since it converts a bookkeeping refund into an unconditional withdrawal.

If the pool gates these legs to the controller, the same defect still matters transitively: any controller path that forwards a user-declared amount without a measured-inflow check (flash-position/repay legs, liquidation pull-then-refund) inherits an unfunded refund primitive. The codebase's measured-receipt pattern (`balance_delta_since`, `refund_controller_balance_delta` in `contracts/controller/src/payments.rs:41-52`) shows the correct idiom is already used elsewhere — the controller refunds only the measured balance increase — but the pool legs do not apply it.

### Likelihood Explanation
Reachability hinges on the pool's authorization of `repay`/`recapitalize`. I could not read `contracts/pool/src/lib.rs` to confirm whether these entrypoints enforce a controller-only caller check; the in-repo test calls `client().repay(&payer, ...)` directly with a generated payer address, which suggests no controller-only gate (or that tests mock auth — uncertain). On the controller path, `liquidate` and `repay` pull tokens from the payer before invoking the pool leg, which would fund the refund — but `docs/reference/formulas.md` notes liquidation pulls each merged *offered* amount while the pool refunds the per-leg excess, so on a full-close quote the declared-offer/refund asymmetry still routes through this unfunded-by-design code path. The primitive exists and is reachable wherever the inbound transfer assumption is not enforced by measurement.

### Recommendation
Make the refund measured, not declared:

1. In `pool::repay::apply` and `pool::recapitalize::apply`, snapshot the pool's token balance before committing and cap the refund at `min(declared_refund, measured_balance_delta)` — mirroring `refund_controller_balance_delta` in `contracts/controller/src/payments.rs:41-52`.
2. Alternatively, require the inbound transfer inside the same leg (pull `amount` from `payer` via `token.transfer` before `accounting`), so `amount` is guaranteed funded before any refund is computed.
3. Add a `require_reserves`/custody predicate asserting `post_balance >= pre_balance - applied` for both legs.

### Proof of Concept
1. Attacker calls `pool.repay(payer = attacker, PoolAction { hub_asset, amount = B })` on a market with `borrowed == 0` (or `recapitalize` on a market with zero backing shortfall).
2. `resolve_repay` returns `overpayment = B - 0 = B`; `net_repay = 0` satisfies `RepayRoundsToZeroShares`; `credit_cash(0)` leaves the book unchanged.
3. `transfer_out(attacker, B)` moves `B` tokens out of pool custody. Attacker paid nothing.
4. Repeat per market until custody is drained; suppliers' claims become unbacked (protocol insolvency / theft of user funds).

This is exactly the scenario exercised by `contracts/pool/tests/flows.rs:3590-3610`.

Caveat: the finding's severity depends on the authorization around the pool `repay`/`recapitalize` entrypoints, which I was unable to confirm from `lib.rs` within the tool budget. If they are controller-gated and the controller always pre-funds `amount`, the residual risk is the full-close liquidation path where the pulled offer and the pool-side refund are computed independently (`formulas.md:334-336`).
