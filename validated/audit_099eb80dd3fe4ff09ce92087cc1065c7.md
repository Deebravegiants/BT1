## Custody Analog Finding — Aptos `multisig_account` Timelock Override

### Title
Timelock override-threshold invariant is not re-validated after quorum changes, silently nullifying multisig timelock protection - ([File: aptos-move/framework/aptos-framework/sources/multisig_account.move])

### Summary
`multisig_account` implements an optional per-account timelock (`MultisigAccountTimeLock`) that is supposed to delay execution of approved transactions unless an `override_threshold` number of approvals is reached. `upsert_timelock_internal` enforces at set-time that `override_threshold > num_signatures_required` [1](#0-0) . However, `update_owner_schema` (invoked by `add_owners_and_update_signatures_required`, `swap_owners_and_update_signatures_required`, `update_signatures_required`) only re-clamps `override_threshold` against the **owner count**, never against the (possibly newly raised) `num_signatures_required` [2](#0-1) .

### Finding Description
The timelock's entire security value rests on the invariant `override_threshold > num_signatures_required` — i.e., bypassing the time delay must always require *strictly more* approvals than the normal quorum, so that a timelocked transaction cannot be executed the instant it reaches quorum. This invariant is enforced only in `upsert_timelock_internal` at the moment the timelock is configured [3](#0-2) .

`update_owner_schema` (the shared code path behind owner/threshold changes) recomputes `num_signatures_required` and validates only `num_owners >= num_signatures_required` [4](#0-3) , then separately clamps `override_threshold` down only if it now **exceeds the owner count** [5](#0-4) . There is no check comparing the new `num_signatures_required` against the existing `override_threshold`.

Once `num_signatures_required` is raised to a value `>= override_threshold` (e.g., both become 3-of-3), `can_execute_with_timelock`'s bypass condition — `override_threshold.is_some() && num_approvals >= *override_threshold.borrow()` [6](#0-5)  — becomes true at exactly the same moment normal quorum is satisfied. The timelock therefore silently loses all effect for every subsequent transaction on that multisig account: transactions execute immediately with plain quorum, the same as if no timelock existed, even though `MultisigAccountTimeLock` still reports a nonzero `timelock_period` to callers and off-chain monitors.

### Impact Explanation
For multisig accounts that hold live assets (APT, fungible-asset stores, resource/code-object control) and that rely on the timelock as a defense-in-depth control (e.g., to give co-owners a window to detect and reject a malicious transaction, such as a fund-drain or owner-swap payload), this bug removes that protection without any explicit signal — the timelock configuration still exists on-chain and reports a period, but functionally provides zero delay. This corrupts a documented custody/control invariant ("override_threshold must be greater than num_signatures_required") governing the multisig's execution-authority gating, which directly affects whether the intended controller retains a meaningful veto window before value-moving or control-changing multisig transactions execute.

### Likelihood Explanation
The break is triggered purely through the normal, already-approved `update_owner_schema` flow (`add_owners_and_update_signatures_required`, `swap_owners_and_update_signatures_required`, `update_signatures_required`) — no privilege escalation is needed beyond what the multisig quorum itself authorizes. This makes it plausible as an operational misconfiguration (owners raising `num_signatures_required` without realizing it silently disables the timelock) rather than a pure external attack, since changing `num_signatures_required` still requires quorum approval under the *current* schema.

### Recommendation
In `update_owner_schema`, after computing the new `num_signatures_required`, also re-validate (or auto-raise) the `MultisigAccountTimeLock.override_threshold` so the invariant `override_threshold > num_signatures_required` continues to hold — either by aborting the update if it would violate the invariant, or by proportionally increasing `override_threshold` and emitting `TimelockUpdated`, mirroring the existing owner-count clamp logic.

### Proof of Concept
1. Create a 3-owner multisig with `num_signatures_required = 1`.
2. Call `upsert_timelock(timelock_period = 3600, override_threshold = some(3))` — valid since `3 > 1`.
3. Call `update_signatures_required(new_num_signatures_required = 3)` via the normal multisig-approved flow — this passes the `num_owners >= num_signatures_required` check (3 >= 3) and the override-threshold owner-count clamp (3 <= 3), so it succeeds with no re-check against `num_signatures_required`.
4. Now `override_threshold (3) == num_signatures_required (3)`. Any future transaction reaching 3 approvals satisfies `can_execute_with_timelock`'s override branch immediately, executing without waiting for `timelock_period` to elapse — confirmable by tracing `can_execute_with_timelock` [6](#0-5)  against the unmodified `MultisigAccountTimeLock` state.

**Note on confidence:** I was unable to fully view `update_owner_schema`'s complete source in `multisig_account.move` (only the rendered `.md` doc excerpt was retrieved due to index/tool-call limits) and could not confirm whether any additional check exists elsewhere in the same function body that might re-validate `override_threshold` against `num_signatures_required`.     inline fun can_execute_with_timelock(multisig_account: address, sequence_number: u64, num_approvals: u64): bool {
        if (exists<MultisigAccountTimeLock>(multisig_account)) {
            let multisig_account_resource = &MultisigAccountTimeLock[multisig_account];
            let timelock = multisig_account_resource.timelock_period;
            let override_threshold = multisig_account_resource.override_threshold;

            // Get the pending transaction to check if the timelock has expired
            // Assume that the transaction has already been checked to exist and is valid
            let pending_transaction = get_transaction(multisig_account, sequence_number);

            // Use subtraction to avoid overflow (now_seconds() >= creation_time_secs is always true)
            let elapsed = now_seconds() - pending_transaction.creation_time_secs;

            // If the number of approvals meets the override threshold, or the timelock has expired, allow execution
            (override_threshold.is_some() && &num_approvals >= override_threshold.borrow()) || elapsed >= timelock
        } else {
            true
        }
