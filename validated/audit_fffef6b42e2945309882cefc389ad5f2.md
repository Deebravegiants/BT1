### Title
Webhook `shop` identity is not bound to the HMAC signature, enabling cross-tenant shop spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook exclusively by validating the HMAC over the raw request body, then hands the handler a `shop` value taken from an HTTP header that is never covered by that signature.

### Finding Description
`Registry.process` does: `raise ... unless Utils::HmacValidator.validate(request)` and then builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)`. [1](#0-0) 

`HmacValidator.validate` computes/compares the signature only against `verifiable_query.to_signable_string`, and for `Webhooks::Request` that method returns just `@raw_body`: [2](#0-1) 

Meanwhile `shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic tie to the signed body: [3](#0-2) [4](#0-3) 

The identity binding that should hold is: `shop header used by the handler == shop for which the signed body/HMAC pair was actually generated`. Because the header is outside the signable string, that equality is never checked — the gem only proves "this body+secret pair is authentic for *some* install of this app," not "...for *this* shop."

In a multi-tenant app the `api_secret_key`/`client_secret` is shared across every merchant install (that is the whole point of the OAuth app model), so a valid `(raw_body, hmac)` pair generated by Shopify for tenant A's webhook remains cryptographically valid for that same body content regardless of which shop header accompanies it. An attacker who legitimately installs the app on their own store (a normal, unprivileged action any internet user can do for a public app) can capture a genuine Shopify-signed webhook delivery, then replay the exact `raw_body` with the identical `hmac` header but a **different** `shop-domain` header pointing at a target merchant's domain. `HmacValidator.validate` will report success (body/HMAC match), and `Registry.process` will pass `shop: "victim-shop.myshopify.com"` to the app's handler, even though that value was never authenticated.

### Impact Explanation
This breaks the tenant-isolation guarantee the gem is supposed to provide via `Registry.process`/`Webhooks::Request`. Any app whose webhook handler uses `data.shop` to key persistence, look up sessions, or route side effects (exactly the pattern shown in this gem's own documentation, `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) can be made to attribute attacker-controlled, replayed webhook content to an arbitrary victim shop domain, i.e., cross-tenant data confusion/injection through the gem's documented webhook API. [5](#0-4) 

### Likelihood Explanation
Reachable by any unprivileged internet user who can install the target app on their own (attacker-controlled) shop and capture one legitimate webhook delivery — no access token, `api_secret_key`, or privileged account is required. The only work needed is intercepting/replaying an HTTP request with a modified header, which is standard behavior for any public HTTP endpoint exposed per the gem's documented "Process a Webhook" pattern. [6](#0-5) 

### Recommendation
Include the shop domain (and ideally topic/webhook-id) inside the HMAC-covered signable content, or otherwise cryptographically bind the header value to the signature, so `HmacValidator.validate` fails whenever the `shop-domain` header does not match the value the signature was actually computed over. At minimum, document/require verification that `request.shop` corresponds to a shop the app has an active install/session for before trusting it, and change `Webhooks::Request#to_signable_string` so it cannot be satisfied by a replayed body/hmac pair under a different shop header.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and registers a webhook, e.g. `orders/create`.
2. Shopify delivers a webhook to the app with headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC over raw_body>`, and some `raw_body`.
3. Attacker captures this raw body + HMAC value.
4. Attacker resends the identical `raw_body` and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
5. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only re-hashes `raw_body` and compares to the supplied `hmac` — this succeeds because neither depends on the shop header. [7](#0-6) 
6. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and the attacker's body content, believing it is an authentic event for the victim's store. [8](#0-7)

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
