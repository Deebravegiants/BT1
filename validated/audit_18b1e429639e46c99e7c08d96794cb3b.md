Based on my investigation, I found a valid analog vulnerability matching the reported bug class.

### Title
Webhook `shop` and `topic` identity fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing via replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
The Unlock Protocol bug was caused by an identity-binding field (`keyManager`) being left unreset in one code branch while it was properly reset in the sibling branch, letting an attacker retain authority after a state transition. The analogous flaw here is that `ShopifyAPI::Webhooks::Request` computes its HMAC over the raw body only, while the `shop` and `topic` identity fields used by `ShopifyAPI::Webhooks::Registry.process` to route and attribute the webhook are taken from HTTP headers that are completely outside the signed content.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) . `Request#shop` and `Request#topic` are read straight from headers (`x-shopify-shop-domain`, `x-shopify-topic`) that are never mixed into the signed string: [2](#0-1) .

`Registry.process` validates only the raw-body HMAC and then trusts `request.topic` and `request.shop` for dispatch and for the metadata handed to the app's handler: [3](#0-2) . `HmacValidator.validate` in turn only compares `verifiable_query.to_signable_string` against the secret — it has no way to know that `shop`/`topic` exist at all: [4](#0-3) .

Because the same app secret signs every shop's webhooks and the signature covers only the body, a party who legitimately receives one valid, signed webhook (e.g. by installing the app on their own shop, or from a shop whose webhook body they can otherwise obtain) can take that untouched `raw_body` + its valid `hmac-sha256` header and resubmit it to the app's public webhook endpoint with the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header changed. `Utils::HmacValidator.validate(request)` still succeeds because it only checks the body signature, yet `Registry.process` reports the forged `shop`/`topic` as authoritative to the handler: `request.shop`, `request.topic` in the metadata construction at [5](#0-4) . The identity equality that should hold — "shop claimed in the (attacker-controlled) header equals the shop whose data actually produced the signed body" — is not enforced anywhere in this gem.

### Impact Explanation
This breaks the tenant-binding guarantee applications rely on when handling webhooks: the gem asserts the request passed HMAC validation, implying it is an authentic, unmodified Shopify webhook for the shop/topic named in its headers, but that binding is never cryptographically established. Any host application that uses `WebhookMetadata#shop`/`#topic` (the values `Registry.process` derives directly from unauthenticated headers) to select per-tenant secrets, records, or handler branches can be made to act on data belonging to shop A while believing it belongs to shop B, or to dispatch under a different topic than actually occurred. This is a cross-tenant impact within the scope defined by the analog rules (shop authenticated vs. shop actually bound to the signed content).

### Likelihood Explanation
The prerequisite is that the attacker (an unprivileged internet user) can obtain at least one legitimately signed webhook body — trivially achievable by installing the target public app on an attacker-controlled development/test shop, since Shopify will then send genuinely HMAC-signed webhooks to the app's endpoint for that shop. No access to `client_secret`, access tokens, or privileged accounts is required; the attacker only replays their own captured request with edited headers.

### Recommendation
Include `shop` and `topic` (and any other header-derived identity fields the app is expected to trust) inside the HMAC-signed content, or otherwise cryptographically bind them (e.g., by validating them against a shop the app previously registered for that specific webhook subscription/id) before `Registry.process` treats them as authoritative in `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the target Shopify app on their own development shop `attacker.myshopify.com`.
2. Shopify sends a legitimate webhook, e.g. `orders/create`, with a valid `X-Shopify-Hmac-Sha256` header computed by Shopify over the JSON body using the app's real `client_secret`.
3. Attacker captures the raw body and the `hmac-sha256` header unchanged, then re-POSTs it to the app's webhook endpoint, only replacing the `X-Shopify-Shop-Domain` header with `victim.myshopify.com` (and/or the topic header, if targeting a differently-registered handler using the same body shape).
4. `ShopifyAPI::Webhooks::Request.new` parses the forged headers plus the untouched body: [6](#0-5) .
5. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only re-computes the HMAC over `@raw_body`, which is identical to what Shopify originally signed: [7](#0-6) .
6. The registered handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)`, where `shop` is now `victim.myshopify.com` even though the payload actually originated from and describes `attacker.myshopify.com`'s data: [5](#0-4) .

          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
