### Title
Duplicate authority-index padding in BEEFY `verifyMmrUpdateProof`/`verify_mmr_update_proof` bypasses the 2/3+1 supermajority threshold - (File: `evm/src/consensus/EcdsaBeefy.sol`, `modules/consensus/beefy/verifier/src/lib.rs`)

### Summary
Both the Solidity (`EcdsaBeefy.sol`) and Rust (`beefy/verifier`) BEEFY consensus verifiers compute the supermajority participation threshold from the raw count of submitted votes/signatures (`sigLen` / `signatures_length`), before ever checking that the `authorityIndex`/`index` values referenced by those votes are distinct. This is architecturally the same bug class as the `QVBaseStrategy.reviewRecipients` issue: a count that is meant to represent distinct approving parties is incremented/derived from a list that can contain repeats of the same party, letting the threshold gate be satisfied without real supermajority support.

### Finding Description
In `evm/src/consensus/EcdsaBeefy.sol::verifyMmrUpdateProof`:
```solidity
uint256 sigLen = relayProof.signedCommitment.votes.length;
...
if (!checkParticipationThreshold(sigLen, authoritySet.len)) revert SuperMajorityRequired();
...
for (uint256 i = 0; i < sigLen; i++) {
    Vote memory vote = relayProof.signedCommitment.votes[i];
    address authority = ECDSA.recover(commitmentHash, vote.signature);
    authorities[i] = MerkleMultiProof.Leaf({index: vote.authorityIndex, hash: keccak256(abi.encodePacked(authority))});
}
bool valid = MerkleMultiProof.VerifyProof(authoritySet.root, relayProof.proof, authorities, authoritySet.len);
``` [1](#0-0) 

The identical structure exists in the Rust light-client verifier used by pallet-ismp-beefy-consensus-proofs:
```rust
let signatures_length = mmr.signed_commitment.signatures.len();
...
if !check_participation_threshold(signatures_length as u32, authority_set.len) {
    return Err(Error::SuperMajorityRequired);
}
...
for sig in mmr.signed_commitment.signatures.iter() { ... authority_indices.push(sig.index as usize); }
let valid = merkle_proof.verify(authority_set.keyset_commitment.into(), &authority_indices, &authority_leaves, authority_set.len as usize);
``` [2](#0-1) 

At no point is `vote.authorityIndex` (Solidity) / `sig.index` (Rust) checked for uniqueness across the submitted vote/signature array — unlike every other consensus client in this codebase, which explicitly guards against exactly this class of double-counting:
- Pharos: `verify_validator_membership` rejects duplicate participant keys with `Error::DuplicateParticipant` before computing stake-threshold participation. [3](#0-2) 
- BSC/Parlia and Sync-committee: explicitly bound bitset iteration to `validators.len()`/`committee_size` to stop an attacker from padding `count_ones()` with junk bits beyond the real validator count. [4](#0-3) [5](#0-4) 
- GRANDPA: `finality_grandpa::validate_commit` result is explicitly checked for `num_duplicated_precommits() > 0`, rejecting the commit if any voter is double-counted. [6](#0-5) 

The BEEFY verifier (both the Solidity `EcdsaBeefy.sol` client and the Rust `beefy-verifier` crate, which back Hyperbridge's Polkadot/Kusama relay-chain consensus updates) has no analogous check. Because a relayer wholly controls the byte content of `ConsensusMessage`/`BeefyConsensusProof` submitted via the permissionless `update_client`/`verify()` entry points, a malicious or Byzantine relayer that has captured (or forged, via a leaked/compromised key) even a minority of valid authority signatures can pad `votes`/`signatures` with repeated `(signature, authorityIndex)` entries for the *same* authority to inflate `sigLen`/`signatures_length` past the `2/3*N + 1` bound, while the merkle multi-proof step is only asked to prove membership of indices already present in the submitted list — it never asserts those indices are pairwise distinct.

Whether `MerkleMultiProof.VerifyProof` / `rs_merkle`'s `MerkleProof::verify` outright reject a proof request containing a repeated leaf/index (which would neutralize this) could not be conclusively confirmed by static inspection alone, since neither library's internal verification routine was directly located in this pass. This is the one point of uncertainty in this finding, and is the exact detail a Devin session with full repo/tool access should verify by writing a PoC test that submits a `MmrProof`/`BeefyConsensusProof` with duplicate `(index, leaf)` entries and confirms whether `verify_mmr_update_proof`/`verifyMmrUpdateProof` accepts it below the real distinct-signer threshold.

### Impact Explanation
If the duplicate-index padding is accepted by the multiproof verification (as it is not defended against upstream of it, unlike every sibling consensus client), an attacker who controls fewer than `2/3*N+1` of the BEEFY authority set's signing keys can still get `update_client`/`verify()` to accept a forged relay-chain state commitment. Since BEEFY consensus underlies Hyperbridge's cross-chain state proofs for Polkadot/Kusama parachains, a forged commitment could let an attacker fabricate state/membership proofs for cross-chain messages (e.g. token mint/burn, ISMP request/response delivery) that were never actually finalized on the relay chain — a forged-message-delivery / unsound-state-commitment class of impact, meeting the Critical/High severity bar for consensus verification bugs.

### Likelihood Explanation
Reachability is high in principle: `update_client` is a permissionless, unsigned-relayer-submitted extrinsic/call, and `EcdsaBeefy.verify()` is invoked by the EVM `IsmpHost`/`HandlerV2` path on any submitted consensus proof — no privileged role is required to submit a proof. The likelihood of actual exploitability, however, hinges entirely on whether the merkle multiproof verification (Solidity `MerkleMultiProof.VerifyProof` / Rust `rs_merkle::MerkleProof::verify`) tolerates duplicate `(index, leaf)` pairs in its input; if it strictly requires strictly-increasing unique indices (a common but not universal implementation choice), the duplicate-padding attempt would fail at that step regardless of the missing upstream check. This library-level detail was not confirmed in this pass.

### Recommendation
Add an explicit uniqueness check on `authorityIndex`/`sig.index` before computing `sigLen`/`signatures_length` and before the threshold check, mirroring the pattern already used in `pharos-verifier::verify_validator_membership` and GRANDPA's `num_duplicated_precommits()` check:
- Solidity: collect `vote.authorityIndex` values and revert (e.g. `DuplicateAuthorityIndex()`) if any repeats, before computing `sigLen`/calling `checkParticipationThreshold`.
- Rust: build a `BTreeSet` of `sig.index` values and return `Error::DuplicateAuthorityIndex` if its length differs from `mmr.signed_commitment.signatures.len()`, before calling `check_participation_threshold`.

### Proof of Concept
1. Construct a `BeefyConsensusProof` where `signedCommitment.votes` contains `N` entries all carrying the **same** valid `signature` and the **same** `authorityIndex` for one real authority (or a small minority of real authorities each repeated), such that `votes.length >= (2/3 * authoritySet.len) + 1`.
2. Submit this proof to `EcdsaBeefy.verify()` (or the equivalent `verify_consensus`/`verify_mmr_update_proof` call in the Rust BEEFY verifier via `update_client`).
3. Observe whether `checkParticipationThreshold`/`check_participation_threshold` passes purely from the padded count, and whether `MerkleMultiProof.VerifyProof`/`MerkleProof::verify` accepts the resulting duplicated `(index, leaf)` array against the authority-set merkle root — if so, a forged relay-chain state commitment signed by fewer than the required supermajority of distinct authorities is accepted as finalized.

pub fn verify_mmr_update_proof<H: Keccak256 + EcdsaRecover + Send + Sync>(
	mut trusted_state: ConsensusState,
	mmr: MmrProof,
) -> Result<(ConsensusState, H256), Error> {
	let signatures_length = mmr.signed_commitment.signatures.len();
	let latest_height = mmr.signed_commitment.commitment.block_number;

	if trusted_state.latest_beefy_height >= latest_height {
		return Err(Error::StaleHeight {
			trusted_height: trusted_state.latest_beefy_height,
			current_height: latest_height,
		});
	}

	let commitment = mmr.signed_commitment.commitment.clone();

	// Pick the authority set the commitment claims to be signed under, then judge
	// participation against that set alone.
	let authority_set = if commitment.validator_set_id == trusted_state.current_authorities.id {
		&trusted_state.current_authorities
	} else if commitment.validator_set_id == trusted_state.next_authorities.id {
		&trusted_state.next_authorities
	} else {
		return Err(Error::UnknownAuthoritySet { id: commitment.validator_set_id });
	};

	if !check_participation_threshold(signatures_length as u32, authority_set.len) {
		return Err(Error::SuperMajorityRequired);
	}

	let mmr_root_data = commitment
		.payload
		.get_raw(&MMR_ROOT_PAYLOAD_ID)
		.ok_or(Error::MmrRootHashMissing)?;

	if mmr_root_data.len() != 32 {
		return Err(Error::InvalidMmrRootHashLength { len: mmr_root_data.len() });
	}
	let mmr_root = H256::from_slice(mmr_root_data);

	let commitment_hash = H::keccak256(&commitment.encode());
	let mut authority_leaves: Vec<[u8; 32]> = Vec::new();
	let mut authority_indices = Vec::new();

	for sig in mmr.signed_commitment.signatures.iter() {
		let uncompressed = H::secp256k1_recover(&commitment_hash.0, &sig.signature)
			.map_err(|_| Error::FailedToRecoverPublicKey)?;

		let hashed_uncompressed = H::keccak256(&uncompressed);

		let mut eth_address = [0u8; 20];
		eth_address.copy_from_slice(&hashed_uncompressed.as_ref()[12..]);

		let authority_address_hash = H::keccak256(&eth_address);

		authority_leaves.push(authority_address_hash.into());
		authority_indices.push(sig.index as usize);
	}

	let merkle_proof = MerkleProof::<MerkleHasher<H>>::new(mmr.authority_proof.clone());

	let valid = merkle_proof.verify(
		authority_set.keyset_commitment.into(),
		&authority_indices,
		&authority_leaves,
		authority_set.len as usize,
	);

	if !valid {
		Err(Error::InvalidAuthoritiesProof)?;
	}

/// Verify that all participating validators are members of the trusted validator set.
fn verify_validator_membership(
	validator_set: &ValidatorSet,
	participants: &[BlsPublicKey],
) -> Result<(), Error> {
	let deduped: alloc::collections::BTreeSet<&[u8]> =
		participants.iter().map(|k| k.as_ref()).collect();
	if deduped.len() != participants.len() {
		return Err(Error::DuplicateParticipant);
	}
	if let Some(key) = participants.iter().find(|key| !validator_set.contains(key)) {
		return Err(Error::UnknownValidator { key: key.clone() });
	}
	Ok(())
}
