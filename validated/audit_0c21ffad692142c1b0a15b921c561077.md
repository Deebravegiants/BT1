Audit Report

## Title
Unvalidated hex length in `normalizeHex` causes a negative-count panic (DoS) in the Gateway HTTP trigger handler - (File: core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go)

## Summary
`normalizeHex` computes `expectedHexLength - len(hexStr)` and passes it to `strings.Repeat` without checking for a negative result, which will panic in Go. [1](#0-0)  While `resolveWorkflowID`'s callers do run `validateWorkflowID`/`validateWorkflowOwner` (via `validateHexInput`) before `normalizeHex` is invoked, that pre-validation only bounds the *raw input length* (including any `0x` prefix) against the full constant (`workflowIDLength`=66 or `workflowOwnerLength`=42), and does not require the `0x` prefix to actually be present. [2](#0-1)  As a result, a caller can submit a `workflowID`/`workflowOwner` value of exactly the maximum length made up purely of lowercase hex digits with **no** `0x` prefix (e.g. 66 hex chars for workflowID, 42 for workflowOwner); `hex.DecodeString` succeeds since the length is even, and `len(input) <= expectedLength` holds, so `validateHexInput` passes. [3](#0-2)  But when `normalizeHex` later runs, `strings.TrimPrefix` finds no `0x` to strip (since valid hex characters cannot spell "0x" as a leading substring), leaving `hexStr` at its full length while `expectedHexLength = length - 2` is 2 less than that length, making `expectedHexLength - len(hexStr)` negative and causing `strings.Repeat` to panic. [4](#0-3) 

## Finding Description
`resolveWorkflowID` is reached from `HandleUserTriggerRequest`, which is the entry point for unauthenticated/unprivileged HTTP trigger requests to the gateway. [5](#0-4)  Before `resolveWorkflowID` runs, `validatedTriggerRequest` calls `validateTriggerParams` → `validateWorkflowFields`, which calls `validateWorkflowID`/`validateWorkflowOwner`. [6](#0-5)  These wrap `validateHexInput`, which only checks: lowercase, `len(input) <= expectedLength`, and that `hex.DecodeString(TrimPrefix(input,"0x"))` succeeds — it never requires the `0x` prefix to be present. [2](#0-1)  This creates a length-accounting mismatch: `validateHexInput` bounds the total string length (including a *potential* 2-char prefix) against the full constant, while `normalizeHex` unconditionally subtracts 2 from that constant assuming the prefix was present and stripped. If a caller omits the `0x` prefix and submits a maximal-length pure-hex string, both checks individually pass, but the combined effect drives `normalizeHex`'s subtraction negative, panicking `strings.Repeat` with `"strings: negative Repeat count"`.

I could not find a panic-recovery/middleware wrapper (e.g., `recover()`, gin `Recovery`, or an equivalent) around the gateway's HTTP request-handling path for this handler in the available code — searches within `core/services/gateway/network/` and the trigger-handling call chain did not surface such a mechanism, though this could not be fully confirmed for the underlying HTTP server framework due to search/tooling limitations in this session.

## Impact Explanation
An unhandled panic in the request-processing goroutine is a denial-of-service condition; depending on whether an upstream recovery mechanism exists, this could fail only the single offending request or crash the process/goroutine handling gateway traffic, denying service to legitimate users of that gateway instance. This maps to an in-scope DoS/availability impact against an internet-facing gateway component.

## Likelihood Explanation
Reachable by any unprivileged, unauthenticated caller of the gateway's HTTP trigger endpoint — they need only submit a `workflowID` or `workflowOwner` string of the maximum expected length consisting solely of lowercase hex characters, without the `0x` prefix. No special role or credential is required, and the trigger is fully attacker-controlled and repeatable.

## Recommendation
Fix `normalizeHex` to be prefix-agnostic and safe regardless of whether the caller included `0x`:
```go
func normalizeHex(input string, length int) (string, error) {
    hexStr := strings.TrimPrefix(input, "0x")
    expectedHexLength := length - 2
    if len(hexStr) > expectedHexLength {
        return "", fmt.Errorf("hex value %q exceeds expected length %d", input, expectedHexLength)
    }
    return "0x" + strings.Repeat("0", expectedHexLength-len(hexStr)) + hexStr, nil
}
```
Additionally, align `validateHexInput` to check the *decoded/trimmed* hex length against `expectedLength-2` consistently, and/or require the `0x` prefix to be present, so the two functions cannot disagree on expected length. Propagate any error from `normalizeHex` up through `resolveWorkflowID` via `handleUserError` instead of allowing an unchecked call into `strings.Repeat`.

## Proof of Concept
1. Send a JSON-RPC HTTP trigger request to the gateway with `method: "workflows.execute"` and `params.workflow.workflowOwner` set to a 42-character, all-lowercase hex string with no `0x` prefix (e.g., 42 repeated `"ab"` characters truncated/adjusted to exactly 42 chars) and no `workflowID`, `workflowName`/`workflowTag` set appropriately to reach the `workflowOwner` branch.
2. `validateWorkflowOwner`/`validateHexInput` accepts it: length (42) ≤ `workflowOwnerLength` (42), lowercase, and `hex.DecodeString` succeeds since 42 is even and all chars are valid hex digits.
3. `resolveWorkflowID` calls `normalizeHex(owner, 42)`; `hexStr` remains the full 42-character string (no `0x` to trim), `expectedHexLength = 40`, so `strings.Repeat("0", 40-42)` is invoked.
4. `strings.Repeat` panics with `"strings: negative Repeat count"`, unwinding the goroutine handling the request.

A Go unit test directly calling `normalizeHex("aa"+strings.Repeat("bb", 20), 42)` (42-char pure-hex, no prefix) would reproduce the panic deterministically and should be added to `http_trigger_handler_test.go` to confirm and guard against regression.

func validateHexInput(input string, expectedLength int) error {
	if input != strings.ToLower(input) {
		return errors.New("must be lowercase")
	}

	if len(input) > expectedLength {
		return fmt.Errorf("hex string too long: expected at most %d characters, got %d", expectedLength, len(input))
	}

	hexStr := strings.TrimPrefix(input, "0x")
	_, err := hex.DecodeString(hexStr)
	if err != nil {
		return errors.New("must be a valid hex string")
	}

	return nil
}

// normalizeHex normalizes a hex string by stripping 0x prefix, padding with leading zeros, and adding 0x prefix back
func normalizeHex(input string, length int) string {
	hexStr := strings.TrimPrefix(input, "0x")
	// length-2 because we'll add "0x" prefix
	expectedHexLength := length - 2
	paddedHex := strings.Repeat("0", expectedHexLength-len(hexStr)) + hexStr
	return "0x" + paddedHex
}
