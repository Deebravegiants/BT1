## Title
Unchecked ERC20 `transfer` return value in Tron `IntentGatewayV2.withdraw`/`onAccept` (SweepDust) permanently burns escrowed funds for non-reverting-failure tokens - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` deliberately does not use `SafeERC20.safeTransfer` for outbound token payouts (unlike the canonical EVM contract), instead making a raw low-level `.call` to the `transfer` selector and only checking that the call itself did not revert. It never inspects the returned boolean. Any TRC20/ERC20-like token that signals a failed transfer by returning `false` (rather than reverting) will cause the gateway to treat a failed payout as successful, decrement the internal escrow accounting anyway, and mark the order as filled — permanently losing the escrowed tokens.

### Finding Description
In `withdraw`, escrowed tokens are released with:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();

_orders[body.commitment][token] -= amount;
``` [1](#0-0) 

The same unchecked pattern is used for the fee-token payout in the same function, and for `SweepDust` handling in `onAccept`:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, req.beneficiary, amount));
if (!success) revert TransferFailed();
``` [2](#0-1) 

`success` here only reflects whether the low-level call reverted, not whether the token's `transfer` function actually returned `true`. Many real-world TRC20/ERC20 tokens (a class the report analogously flags for USDT-style tokens) return `false` on failure instead of reverting — insufficient balance in a rebasing/blacklist/pausable token, a blacklisted recipient, a paused token, etc. In all of these cases the raw `.call` succeeds (returns `success = true`), so the contract proceeds as if the transfer worked: it decrements `_orders[body.commitment][token]` and marks `_filled[body.commitment] = beneficiary` (or emits `EscrowReleased`/`EscrowRefunded`), even though the beneficiary received nothing.

This is the exact bug class from the external report (SafeERC20 imported and used elsewhere via `using SafeERC20 for IERC20;` at line 56, but the payout path here bypasses it with a raw call whose return value is never decoded), generalized to the Tron intents escrow release path instead of a margin-trading approval path. [3](#0-2) 

By contrast, the canonical EVM `IntentsBase.sol` correctly uses `safeTransfer`, which does decode and validate the return value:
```solidity
IERC20(token).safeTransfer(beneficiary, amount);
``` [4](#0-3) 

### Impact Explanation
Once `withdraw` (invoked from `onAccept` for `RedeemEscrow`/`RefundEscrow` or from `onGetResponse` for cancellation-by-GET-response) silently "succeeds" on a failed transfer, the escrow bookkeeping (`_orders[body.commitment][token]`) is permanently reduced and the order is marked filled/refunded, but the underlying tokens remain stuck in the contract with no way for the depositor or intended beneficiary to reclaim them — a permanent freezing/loss of user funds. This is triggered through the normal intent-fill/cancel message-delivery path reachable by any relayer/solver completing or cancelling an order, not a privileged action. [5](#0-4) [6](#0-5) 

### Likelihood Explanation
The likelihood depends on which ERC20/TRC20 tokens are actually permitted as escrow inputs/outputs on the Tron deployment. If any token whose `transfer` can return `false` without reverting is supported (a common pattern for TRC20 tokens on Tron, and explicitly the bug class called out in the source report for tokens like USDT), every fill/cancel involving that token that hits a transfer failure condition (blacklist, pause, insufficient contract balance) will silently corrupt escrow accounting.

### Recommendation
Replace the raw `.call(...)` + `success`-only check with `SafeERC20.safeTransfer` (already imported and used via `using SafeERC20 for IERC20;`) for all three payout sites — the token payout and fee payout in `withdraw`, and the `SweepDust` payout in `onAccept` — so both call success and the decoded boolean return value (or lack of return data per EIP-20) are validated before mutating escrow state.

### Proof of Concept
1. Deploy the Tron `IntentGatewayV2` with a token `T` whose `transfer` function returns `false` when the recipient is blacklisted/paused instead of reverting (a supported real-world TRC20/ERC20 pattern).
2. Place and fill/cancel an order with input token `T`, engineering the beneficiary to be in the token's failure state (e.g., blacklisted) so `T.transfer(beneficiary, amount)` returns `false`.
3. `withdraw` receives `success = true` from the raw `.call` (the call itself doesn't revert, only the boolean return is `false`), so it does not revert with `TransferFailed`.
4. `_orders[body.commitment][token] -= amount;` executes, the order is marked filled/refunded, and `EscrowReleased`/`EscrowRefunded` is emitted — but `beneficiary`'s token balance never increased. The escrowed `amount` of `T` is now permanently stuck in the contract with no accounting path to recover it.
