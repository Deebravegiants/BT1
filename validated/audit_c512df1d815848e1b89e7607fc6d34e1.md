### Title
Webhook `shop`/`topic` identity headers are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop`, `topic`, `api_version` and `webhook_id` values from raw HTTP headers, but the HMAC signature that `Utils::HmacValidator` verifies is computed over the request body only. The header that identifies which tenant (`shop`) the webhook belongs to is never bound to the signature, so it can be freely substituted without invalidating the HMAC check.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all read straight from headers that are not part of that signable string: [2](#0-1) 

`Utils::HmacValidator.validate` only recomputes the HMAC over `to_signable_string` (the body) and compares it to the `hmac` header value: [3](#0-2) 

`Webhooks::Registry.process` accepts the request once this body-only HMAC passes, then dispatches to the handler using the unauthenticated `request.shop` value: [4](#0-3) 

The binding that should hold is: `HMAC_secret(shop || topic || body) == received_hmac`. What is actually enforced is: `HMAC_secret(body) == received_hmac`, with `shop` and `topic` accepted from unauthenticated bytes. Because Shopify signs webhooks for every shop installed on an app using the same app-level `client_secret` (not a per-shop secret), any raw body + HMAC pair that is valid for one tenant (e.g. one the attacker legitimately controls and can trigger events on) remains cryptographically valid when replayed with a different `X-Shopify-Shop-Domain`/`shopify-shop-domain` header. The gem performs no cross-check that the shop claimed in the header is consistent with anything cryptographically bound to the payload.

### Impact Explanation
This breaks the tenant identity binding between an inbound webhook's cryptographic proof of authenticity and the tenant it is attributed to. An app built on this gem that trusts `WebhookMetadata#shop` (as documented/intended usage in `Registry.process`) to select which merchant's data/session/state to act upon can be made to process attacker-supplied (or replayed) webhook bodies under a victim shop's identity, since the HMAC only proves "signed with our client secret" and not "genuinely originated from shop X". This is a cross-tenant integrity issue: the attacker cannot forge state for a shop they don't control at the signature level, but they can cause the host application to associate/write attacker-chosen webhook content against an arbitrary victim `shop` value, since that value carries no cryptographic guarantee.

### Likelihood Explanation
Exploitation requires only: (1) the ability to trigger or capture one genuine, validly-HMAC'd webhook delivery for the target app (trivial for any merchant who has installed the app, including the attacker's own test store), and (2) the ability to POST an HTTP request to the app's public webhook endpoint with a modified `shop-domain` header, which is entirely under the requester's control and not authenticated by this gem. No access token, client secret, or privileged account is required — an unprivileged internet user who can install/interact with the target app on their own shop can obtain a valid signed payload and header-swap it.

### Recommendation
Bind the shop identity (and ideally topic) into the value that is HMAC-verified, or otherwise cryptographically tie the header claims to the signed body — for example by requiring the host application to independently confirm `request.shop` corresponds to a shop with a currently stored, valid session/access token before trusting the webhook payload, and by documenting/enforcing that `to_signable_string` alone must never be treated as proof of the `shop` header's authenticity. At minimum, update documentation to make explicit that `Webhooks::Request#shop`/`#topic` are unauthenticated header values and must not be used as an untrusted-but-load-bearing tenant key without additional verification by the integrating application.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` and triggers a real webhook event (e.g., `orders/create`). Shopify delivers a request with a genuine `x-shopify-hmac-sha256` computed over the raw body using the app's `client_secret`.
2. Attacker captures the raw body bytes and the `x-shopify-hmac-sha256` value from this delivery.
3. Attacker POSTs to the app's webhook endpoint reusing the exact same raw body and `x-shopify-hmac-sha256` header, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` computes the HMAC over `to_signable_string` (the unchanged raw body) and it matches — validation succeeds, as shown by the test fixture pattern in `test/webhooks/registry_test.rb` where `hmac` is computed solely from `"{}"` (the body) independent of the `shop-domain` header: [5](#0-4) 
5. `Registry.process` invokes the registered handler with `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body:, ...)`, causing the host application to act on attacker-controlled content attributed to a shop the attacker does not control.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
