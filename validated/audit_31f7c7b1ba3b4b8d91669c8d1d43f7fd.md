### Title
Webhook `shop`, `topic`, and `webhook_id` fields are not covered by HMAC verification, enabling cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
The gem's webhook processing verifies the HMAC signature of an inbound webhook using only the raw request body, but the `shop`, `topic`, `webhook_id`, and `api_version` values — which are taken from unauthenticated HTTP headers — are passed straight through to the app's `WebhookHandler` as trusted identity/routing data.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `VerifiableQuery` and defines `to_signable_string` to return only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors are derived purely from HTTP headers (`shopify-shop-domain`, `shopify-topic`, etc.) and are never included in the HMAC-signed content: [2](#0-1) 

`Registry.process` validates the HMAC over the body only, then immediately forwards the unauthenticated `request.shop`, `request.topic`, and `request.webhook_id` values to the registered handler as trusted `WebhookMetadata`: [3](#0-2) 

`WebhookMetadata` treats `shop` as an ordinary trusted `String` field with no further verification: [4](#0-3) 

The identity binding this breaks is: `shop_that_produced_hmac_signed_body == shop_attributed_to_the_webhook_by_the_app`. In Shopify's webhook design, the HMAC secret (`api_secret_key` / client secret) is shared across *every* shop that has installed the app — it is not per-shop. Consequently, a genuine, validly-signed `(body, hmac)` pair generated by Shopify for a webhook fired by Shop A (which the attacker legitimately controls, e.g., by installing the app on their own store and generating a webhook event) remains valid regardless of which `x-shopify-shop-domain`/`x-shopify-topic`/`x-shopify-webhook-id` header values accompany it, because those headers are never part of the signed content. An attacker who owns Shop A can capture one legitimately-signed webhook body+HMAC and replay it directly to the app's public webhook endpoint with a forged `x-shopify-shop-domain` header naming a different, victim shop (Shop B). `HmacValidator.validate` will still succeed because it only checks the body/HMAC pair, and the handler will receive `WebhookMetadata(shop: "shop-b.myshopify.com", body: <Shop A's data>, ...)`, i.e., data attributed to a tenant that never produced it.

### Impact Explanation
This breaks the tenant boundary at the point where a webhook's origin shop is determined, which is the primary key most host applications use to route webhook data (e.g., "which merchant's order/product/customer record should this update"). Because the exploit lets one unprivileged, low-cost attacker (anyone who can install the app on a shop they control, including trial/free installs) inject arbitrary attacker-chosen body content under an arbitrary victim shop's identity, this is a cross-tenant data-integrity/confusion vulnerability reachable from the public webhook endpoint with no credentials beyond having installed the app once.

### Likelihood Explanation
Likelihood is high: the webhook endpoint is, by design, a public, unauthenticated HTTP endpoint (Shopify calls it directly), the client secret is shared across all shops that install the app, and capturing one's own legitimately-signed webhook body (e.g., by triggering `orders/create` on your own dev/trial store) requires no special access. Replaying it with modified headers to the same endpoint is a trivial HTTP request.

### Recommendation
Include the identity-critical headers (`shop`, `topic`, `webhook_id`, `api_version`) in the HMAC-signed content, or otherwise cryptographically bind them to the body (e.g., verify `shop` against a per-installation secret or session record rather than trusting the header), so that a signature computed for one shop/topic/webhook cannot be replayed under a different shop's identity. At minimum, document that consumers of `WebhookMetadata#shop` must independently validate the shop against their own installation/session store rather than trusting it as authenticated.

### Proof of Concept
1. Install the target app on attacker-controlled Shop A; trigger any webhook (e.g., `orders/create`) so Shopify sends a POST to the app's webhook endpoint with headers `x-shopify-shop-domain: shop-a.myshopify.com`, `x-shopify-topic: orders/create`, `x-shopify-hmac-sha256: <valid-hmac-of-body>`, and the JSON body.
2. Capture this raw body and its `x-shopify-hmac-sha256` value (attacker has full visibility of their own webhook deliveries, e.g., via a controlled receiving server or a proxy).
3. Resend the identical body and HMAC header directly to the app's public webhook endpoint, but replace `x-shopify-shop-domain` with `shop-b.myshopify.com` (a victim shop that also has the app installed).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because the signature only covers `raw_body`: [5](#0-4) 
5. The registered handler executes with `WebhookMetadata.new(shop: "shop-b.myshopify.com", body: <Shop A's payload>, ...)`, causing the host application to process attacker-supplied content as if it originated from Shop B.
