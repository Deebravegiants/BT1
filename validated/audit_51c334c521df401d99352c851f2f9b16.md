### Title
`Oauth.begin_auth` builds the authorization redirect host from an unvalidated `shop` parameter, enabling forced OAuth completion / open redirect - (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
`ShopifyAPI::Auth::Oauth.begin_auth` derives the OAuth authorization host directly from the caller-supplied `shop:` argument with **no validation**, via `auth_base_uri(shop)` (`"https://#{shop}/admin"`). Every other credential-bearing flow in this gem (`ClientCredentials.client_credentials`, `TokenExchange.exchange_token`) explicitly runs the `shop` value through `Utils::ShopValidator.sanitize!` (or derives it from an HMAC/JWT-signed source) before using it to build a request host. `begin_auth` breaks that same binding: `validated_host == host_receiving_oauth_parameters` does not hold, because no validation step exists at all.

### Finding Description
The `sanitize!`/`sanitize_shop_domain` helpers in `lib/shopify_api/utils/shop_validator.rb` exist specifically to ensure a `shop` string is a genuine, trusted Shopify domain before it is used to construct a URL that the app will send OAuth material to. This validator is consistently applied elsewhere:

- `lib/shopify_api/auth/client_credentials.rb:25` — `validated_shop = Utils::ShopValidator.sanitize!(shop)` before building the `HttpClient` that sends `client_id`/`client_secret`.
- `lib/shopify_api/auth/token_exchange.rb` — the `shop` used to build the exchange request is taken from the `dest` claim of a session token that is verified via `JWT.decode` (`lib/shopify_api/auth/jwt_payload.rb:26-44`), i.e. cryptographically bound.
- `lib/shopify_api/auth/refresh_token.rb` also references `ShopValidator`.

By contrast, in `lib/shopify_api/auth/oauth.rb`:
```ruby
def begin_auth(shop:, redirect_path:, is_online: true, scope_override: nil)
  ...
  auth_route = auth_base_uri(shop) + "/oauth/authorize?#{query_string}"
  ...
end

def auth_base_uri(shop)
  return "https://#{shop}/admin" unless defined?(DevServer) && shop.include?(".my.shop.dev")
  ...
end
``` [1](#0-0) [2](#0-1) 

`shop` here comes straight from the caller with no sanitization anywhere in the method, and the documentation for this exact API confirms the intended integration pattern is to take `shop` from an unauthenticated request value (e.g. a login form or header):
```ruby
def login
  shop = request.headers["Shop"]
  auth_response = ShopifyAPI::Auth::Oauth.begin_auth(shop: domain, redirect_path: "/auth/callback")
  ...
end
``` [3](#0-2) 

This is the exact bug class described in the external report ("incorrect/absent binding of a value used downstream"), mapped onto this gem's authentication boundary: the binding **`host_used_for_redirect == validated_myshopify_host`** is not enforced. Instead of validating `shop` the way `ClientCredentials`/`TokenExchange` do, `Oauth.begin_auth` trusts it outright and uses it to build the URL the merchant's browser is redirected to, carrying the app's `client_id`, `scope`, and `redirect_uri`.

### Impact Explanation
This matches the High-impact category "session fixation or forced OAuth completion". An attacker who controls the `shop` value passed into `begin_auth` (a value the gem's own documentation expects to originate from unauthenticated user input) can force the merchant's browser to be redirected to an attacker-controlled host instead of Shopify, while still carrying the legitimate app's `client_id`, `scope`, and `redirect_uri` in the query string. This can be used to:
- Present a convincing phishing page (posing as the Shopify authorization screen) to harvest merchant credentials.
- Force/steer the OAuth flow so that the browser is later driven back to the app's real `redirect_path` with attacker-chosen `code`/`shop` values, since the attacker's page can read and manipulate all query parameters delivered to it and craft the subsequent callback navigation.
- Leak the app's `client_id` and internal `redirect_uri` to a third-party host, aiding further targeted attacks.

The subsequent `validate_auth_callback` step is still protected by Shopify's HMAC over the callback query and by the `state` cookie check (`lib/shopify_api/auth/oauth.rb:64,70-71`), so `client_secret` cannot be directly exfiltrated through this specific path without also defeating HMAC — but the forced-navigation / open-redirect condition itself is a complete, concrete break of the host-trust boundary at `begin_auth`, independent of any secret knowledge, and directly enables the "forced OAuth completion" impact category.

### Likelihood Explanation
High. No credentials, API keys, or privileged access are required — only the ability to influence the `shop` string passed to `begin_auth`, which per the gem's own documented integration pattern comes from unauthenticated request data (e.g., a query/header parameter on the app's login route). This is a purely unprivileged, internet-reachable trigger.

### Recommendation
Validate `shop` in `Oauth.begin_auth` (and anywhere else `auth_base_uri` is constructed) using the same `Utils::ShopValidator.sanitize!` call already used by `ClientCredentials.client_credentials` and effectively enforced for `TokenExchange` via signed JWT claims, before using it to build `auth_base_uri`. Reject or normalize any `shop` value that is not a trusted `*.myshopify.com` (or configured `myshopify_domain`) host prior to redirecting the browser.

### Proof of Concept
1. Host app implements the documented pattern:
   ```ruby
   def login
     shop = params[:shop] # attacker-controlled, e.g. via login form
     auth_response = ShopifyAPI::Auth::Oauth.begin_auth(shop: shop, redirect_path: "/auth/callback")
     redirect_to auth_response[:auth_route]
   end
   ```
2. Attacker sends the victim merchant a link: `https://legit-app.com/login?shop=attacker.example.com`.
3. `begin_auth` computes `auth_base_uri("attacker.example.com")` → `"https://attacker.example.com/admin"` (no validation performed) and returns `auth_route = "https://attacker.example.com/admin/oauth/authorize?client_id=<real_client_id>&scope=<real_scope>&redirect_uri=https://legit-app.com/auth/callback&state=<nonce>&grant_options[]=per-user"`.
4. The app 307-redirects the merchant's browser to this attacker-controlled URL, carrying the real app's `client_id`, `scope`, and `redirect_uri` — a forced navigation into attacker-controlled infrastructure that can phish for credentials or redirect the flow back into the app's real callback with attacker-influenced parameters, matching the "forced OAuth completion" impact.

        def begin_auth(shop:, redirect_path:, is_online: true, scope_override: nil)
          scope = if scope_override.nil?
            ShopifyAPI::Context.scope
          elsif scope_override.is_a?(ShopifyAPI::Auth::AuthScopes)
            scope_override
          else
            ShopifyAPI::Auth::AuthScopes.new(scope_override)
          end

          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = SecureRandom.alphanumeric(NONCE_LENGTH)

          cookie = SessionCookie.new(value: state, expires: Time.now + 60)

          query = {
            client_id: ShopifyAPI::Context.api_key,
            scope: scope.to_s,
            redirect_uri: "#{ShopifyAPI::Context.host}#{redirect_path}",
            state: state,
            "grant_options[]": is_online ? "per-user" : "",
          }

          query_string = URI.encode_www_form(query)
          auth_route = auth_base_uri(shop) + "/oauth/authorize?#{query_string}"

          { auth_route: auth_route, cookie: cookie }
        end

class ShopifyAuthController < ApplicationController
  def login
    shop = request.headers["Shop"]

    # Builds the authorization URL route to redirect the user to
    auth_response = ShopifyAPI::Auth::Oauth.begin_auth(shop: domain, redirect_path: "/auth/callback")

    # Store the authorization cookie
    cookies[auth_response[:cookie].name] = {
      expires: auth_response[:cookie].expires,
      secure: true,
      http_only: true,
      value: auth_response[:cookie].value
    }

    # Redirect the user to "auth_response[:auth_route]" to allow user to grant the app permission
    # This will lead the user to the Shopify Authorization page
    head 307
    response.set_header("Location", auth_response[:auth_route])
  end
```
