### Title
Webhook `shop` identity is trusted from an unauthenticated header while the HMAC only binds the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` exposes `shop` (and `topic`, `webhook_id`, `api_version`) straight from HTTP headers, but `Utils::HmacValidator` only verifies the raw request body against the HMAC signature. The `shop` field that host applications use to attribute a webhook to a specific merchant tenant is never bound by the cryptographic check, breaking the identity equality `shop authenticated-by-HMAC == shop acted-upon-by-handler`.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over that signable string (the body) and compares it to the `hmac` header: [2](#0-1) 

`Registry.process` gates only on this body-HMAC check, then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` — all parsed from headers that are outside the signed payload — and hands them to the application handler: [3](#0-2) 

`request.shop` is read verbatim from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no validation against `ShopValidator` and no cryptographic binding to the body/HMAC: [4](#0-3) [5](#0-4) 

The resulting `WebhookMetadata.shop` (the merchant-identity field the app's handler acts on) is populated directly from this unauthenticated header: [6](#0-5) 

**Identity binding broken:** `hmac_valid(body) == true` is treated as proof that `(shop, topic, webhook_id, api_version)` all originate from Shopify for that shop, when in fact only the raw body bytes are authenticated. The gem's own `AuthQuery` (OAuth callback) HMAC, by contrast, explicitly binds `shop` into the signable string: [7](#0-6) 
showing the library elsewhere recognizes the need to bind identity fields into the HMAC — but omits this for webhook headers.

### Impact Explanation
Because the app's shared `client_secret`/`api_secret_key` is identical across every merchant install, any unprivileged party who can obtain one legitimate `(body, hmac)` pair from a real webhook delivery to *any* shop using the app (e.g., by installing the app on their own store, or observing a webhook triggered by an ordinary customer action) can replay that same body+HMAC to the app's webhook endpoint while forging the `shop-domain` header to name a different, victim merchant. `HmacValidator.validate` will still pass (it never inspected `shop`), so `Registry.process` will invoke the app's handler with `WebhookMetadata.shop` set to the attacker-chosen victim shop. This is a cross-tenant identity-spoofing primitive: the application (relying on this gem's guarantee that a passing HMAC means "this webhook payload for this shop is authentic") will process/store/act on data as if it came from the victim tenant, corrupting or forging data across tenant boundaries (Critical: cross-tenant access).

### Likelihood Explanation
Exploitation requires only network access to the target application's public webhook endpoint plus one legitimate webhook payload+signature pair obtainable through ordinary use of the app (no leaked secrets, no privileged account, no TLS interception needed) — squarely an "unprivileged internet user" scenario. The main constraint is that the attacker needs a body they can plausibly replay for the target victim's context (e.g., topics whose body content is generic or attacker-influenced, such as `customers/data_request`, `shop/redact`, or app/customer-initiated topics), which is realistic for several mandatory webhook topics registered by this gem.

### Recommendation
Bind the identity fields into the HMAC-verified payload: include `shop`, `topic`, and `webhook_id` in `to_signable_string` (or otherwise cryptographically bind them, e.g., by having callers separately validate the shop domain against session/storage records before trusting `WebhookMetadata.shop`), and document that `Registry.process` callers must not treat a valid body-HMAC as proof of the shop identity in the headers.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` (or triggers a webhook via a generic customer/shop-agnostic topic).
2. Attacker captures the resulting legitimate webhook POST: raw body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
3. Attacker sends a new POST to the same app endpoint with identical body `B` and header `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` recomputes `HMAC-SHA256(api_secret_key, B)`, which still equals `H`, so validation passes: [8](#0-7) 
5. `Registry.process` builds `WebhookMetadata.new(shop: request.shop, ...)` with `shop == "victim-shop.myshopify.com"`, and the handler runs believing the event genuinely originated from the victim's store, despite the payload/HMAC only ever having proven authorship by *an* app-installed shop, not this one.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
