### Title
Zero-valued `tokensForLP` combined with an attacker-minted HyperSwap pre-seed permanently deadlocks `finalizeGraduation` — ([File: packages/contracts/src/Bonding.sol])

### Summary
CVE-2022-31621 is a class of bug where an error path leaves a previously-acquired lock un-released, deadlocking the resource forever. `Bonding`'s two-phase graduation has an analogous "lock": `_enterGraduating` (phase 1, fired inline by any unprivileged buy or by the permissionless `triggerGraduation`) drains the curve, freezes trading (`info.lifecycle = Lifecycle.Graduating`), and caches `(tokensForLP, ltFromPair)` in a **separate transaction** from `finalizeGraduation` (phase 2). If `finalizeGraduation` is made to revert deterministically against those frozen cached values, there is no rollback path back to `Lifecycle.Curve` — the token is permanently "locked" in `Graduating`, exactly like MariaDB's held-but-never-released mutex.

### Finding Description
`_prepareGraduationLiquidity` computes
```
tokensForLP = assetReserve == 0 ? 0 : (ltFromPair * tokenReserve) / assetReserve;
``` [1](#0-0) 

Because the dual graduation trigger can fire on the **USD-value** condition `(storedAssetReserve - virtualLtReserve) × exchangeRate ≥ $9K`, a token backed by an LT with a very high live `exchangeRate()` can cross the $9K threshold while `ltFromPair` (the real LT raised, in LT units) is tiny relative to the launch-time virtual reserve baked into `assetReserve`. Integer division then rounds `tokensForLP` down to `0`.

This cached, frozen value (`pendingGraduation[token].tokensForLP == 0`) is stored at the end of phase 1: [2](#0-1) 

In phase 2, `finalizeGraduation` is fully permissionless, so an attacker can front-run the keeper and pre-seed the HyperSwap pair via `pair.mint(attacker)` against a self-funded TOKEN/LT deposit before `finalizeGraduation` lands. With non-zero `reserveToken` already in the pool and `tokensForLP == 0`, `_seedRebalancing`'s comparison `reserveToken * ltFromPair > reserveLT * tokensForLP` degenerates (RHS is 0), routing into the rebalance branch: [3](#0-2) 

`_noFeeSwapInput` safely short-circuits on `targetD == 0` and returns `0` (no panic): [4](#0-3) 

so `_pairRebalance` returns `false`, and the code falls back to `_seedDirectMint(tokenAddress, lt, pair, tokensForLP=0, ltFromPair)`: [5](#0-4) 

`_seedDirectMint` transfers `0` TOKEN and `ltFromPair` LT to the pair and calls `pair.mint(lpLock)`. Because the pool already holds a nonzero, attacker-controlled `reserveToken` from the pre-seed while the TOKEN-side deposit is `0`, UniswapV2's mint formula `liquidity = min(amount0 * totalSupply / reserve0, amount1 * totalSupply / reserve1)` evaluates to `0` on the TOKEN side, and the pair's standard `require(liquidity > 0, 'INSUFFICIENT_LIQUIDITY_MINTED')` check reverts. Since `tokensForLP` is a **fixed, frozen** value from phase 1 and the attacker's pre-existing pool reserve does not change on its own, every subsequent call to `finalizeGraduation(tokenAddress)` reverts identically forever — the "lock" (`Lifecycle.Graduating`, curve frozen, funds parked in `Bonding`) is never released. This is confirmed by the developers' own natspec acknowledging the exact zero-liquidity failure mode as a design hazard that the 1% swap-budget reservation only guards against in the *rebalance-swap* path, not the `tokensForLP == 0` direct-mint fallback path: [6](#0-5) 

The one-shot `LPLock.recordLock` (which additionally reverts on `amount == 0`) can never even be reached in this scenario, since `_seedUniswapV2Direct`/`_seedDirectMint`'s `pair.mint` reverts first: [7](#0-6) 

### Impact Explanation
Once `_enterGraduating` fires, trading is frozen (`buy`/`sell` revert with `TokenIsGraduating`) and all curve-raised LT plus the 250M `LP_RESERVE` tokens are parked in `Bonding`, per the documented two-phase design: [8](#0-7)  and [9](#0-8) . If `finalizeGraduation` is made to permanently revert, this state is unrecoverable on-chain — there is no admin escape hatch or rollback to `Lifecycle.Curve`. This is a permanent freeze of trader/creator funds (all LT raised by the curve and the 250M reserved tokens), matching the required "permanent freezing of trader, creator or LP funds" impact bar.

### Likelihood Explanation
Reaching `tokensForLP == 0` requires the LT's live `exchangeRate()` to be large enough that a very small real LT raise crosses the $9K USD trigger — realistic for a rebasing LT whose price can move substantially between launch and graduation, and it is an unprivileged, permissionless condition (no special role needed to trigger graduation once `canGraduate` is true). The attacker only needs to front-run the permissionless `finalizeGraduation` call with a single `pair.mint(attacker)` against a HyperSwap pair holding some TOKEN reserve — well within the documented "hostile mint pre-seed" threat model the team already defends against for the *nonzero*-`tokensForLP` case, but not for the `tokensForLP == 0` corner case.

### Recommendation
- In `_prepareGraduationLiquidity`, treat `tokensForLP == 0` as an invalid/ungraduatable state (revert phase 1, or defer graduation) rather than caching it for phase 2.
- In `_seedDirectMint` / `_seedRebalancing`, explicitly detect `tokensForLP == 0` (or `ltFromPair == 0`) against a non-empty pre-existing pool and select a defensive branch (e.g., treat it like Regime 2/3 dust-absorption instead of a literal zero-amount direct mint) so `pair.mint` cannot revert on a frozen, unrecoverable input.
- Add a regression test seeding the pool with a legitimate mint pre-seed while forcing `ltFromPair`/`tokensForLP` to round to a tiny/zero value via a high `exchangeRate()`, verifying `finalizeGraduation` still succeeds.

### Proof of Concept
1. Launch a token whose reserve LT has a controllable/high `exchangeRate()` (per `test/` mocks, `lt.setExchangeRate(...)`).
2. Buy just enough on the curve that `(storedAssetReserve - virtualLtReserve) × exchangeRate ≥ $9K` while the real LT raised (`ltFromPair`) is tiny relative to `assetReserve`, so `_prepareGraduationLiquidity`'s integer division yields `tokensForLP == 0`.
3. Let phase 1 fire (`triggerGraduation` or the threshold-crossing buy) — `pendingGraduation[token].tokensForLP == 0` is now frozen.
4. Before anyone calls `finalizeGraduation`, front-run: create/get the HyperSwap pair via `IUniswapV2Factory.createPair`, `transfer` some TOKEN and LT to it, and call `pair.mint(attacker)` to seed non-zero `reserveToken`.
5. Call `bonding.finalizeGraduation(tokenAddress)` — it reverts inside `_seedDirectMint`'s `pair.mint(lpLock)` call with `INSUFFICIENT_LIQUIDITY_MINTED` because the TOKEN-side deposit is `0` against a non-zero existing reserve.
6. Every subsequent call to `finalizeGraduation(tokenAddress)` reverts identically — the token is permanently stuck in `Lifecycle.Graduating`, trading is frozen, and the curve-raised LT plus the 250M reserved tokens remain locked in `Bonding` with no recovery path.

    function recordLock(
        address token,
        address lpPair,
        uint256 amount
    ) external {
        LPLockStorage storage $ = _s();
        if (!$.isLocker[msg.sender]) revert NotAuthorized();
        if (lpPair == address(0)) revert ZeroAddress();
        if (amount == 0) revert ZeroAmount();
        // `lockedAt` is the one-shot sentinel: it is always set to a non-zero
        // timestamp on the first lock, so the guard holds for any `amount`.
        if ($.locks[token].lockedAt != 0) revert AlreadyLocked();
        if (IERC20(lpPair).balanceOf(address(this)) < amount) revert InsufficientLPBalance();
        $.locks[token] = LockInfo({lpPair: lpPair, amount: amount, lockedAt: block.timestamp});
        emit LPLocked(token, lpPair, amount);
    }

```markdown
- **Two-phase split.** Graduation is split across two transactions to fit HyperEVM's small-block (~2M gas) ceiling.
  - **Phase 1: `_enterGraduating`**, fired inline by the threshold-crossing buy (~150-200k of additional gas on top of the buy). Drains the curve, computes the LP-bound amounts, caches them in `pendingGraduation[token]`, flips `lifecycle: Curve → Graduating`, freezes trading. Emits `TokenGraduating`.
  - **Phase 2: `finalizeGraduation`**, **permissionless** big-block tx (~2.5M gas). Creates the HyperSwap pair if needed, seeds liquidity across the empty, donation, and hostile mint-pre-seed regimes, locks LP, flips `lifecycle: Graduating → Graduated`. Emits `TokenGraduated`. A Cloudflare Worker keeper handles the happy path; anyone can call to rescue a stuck token.
- **Brick resistance.** Phase 2 must never revert under any pre-seed shape. Empty/donation pairs use direct pair calls; hostile mint pre-seeds use direct `pair.swap` for rebalance plus router `addLiquidity` for the canonical quote-based deposit. Tested by `test_brick_resistance_frontRun_dust_seed` in [`test/TwoPhaseGraduation.t.sol`](test/TwoPhaseGraduation.t.sol).
```
