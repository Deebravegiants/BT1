This confirms the vulnerability path: the gem's own documentation explicitly instructs host apps to key their business logic off `data.shop` (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), while the underlying `shop` value is read straight from an unauthenticated HTTP header.

### Title
Webhook shop identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `ShopifyAPI::Webhooks::Registry.process` validates the HMAC over that body alone. The `shop` value that is handed to the app's webhook handler comes from the `X-Shopify-Shop-Domain`/`shopify-shop-domain` header, which is never covered by the HMAC. Any party that can obtain one valid `(body, hmac)` pair for a topic — trivially true for an attacker who installs the app on their own store and receives a legitimate webhook — can replay that exact body/HMAC to the app's webhook endpoint while substituting an arbitrary `shop-domain` header, and the gem will report the webhook as authentic for the attacker-chosen shop.

### Finding Description
`Request#to_signable_string` [1](#0-0)  only signs `@raw_body`; `shop` is read separately from headers with no cross-check [2](#0-1) . `Registry.process` validates the HMAC via `Utils::HmacValidator.validate(request)` — which itself only compares the HMAC of `to_signable_string` (i.e., the body) — and then immediately trusts `request.shop` to build `WebhookMetadata` dispatched to the app's handler [3](#0-2) . `Utils::HmacValidator` itself only ever authenticates `verifiable_query.to_signable_string` against the shared `api_secret_key`, with no parameter binding to the claimed shop [4](#0-3) .

The equality that should hold is: `shop_that_signed(body, hmac) == shop_dispatched_to_handler`. Because `shop` is excluded from the signable string, this equality is never enforced — any `shop` header value is accepted as long as the body+hmac pair is valid for *some* shop that installed the app (since `api_secret_key` is shared across all shops of a given app, not per-shop).

The gem's own docs confirm apps are expected to key business logic off this unauthenticated field: `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)` [5](#0-4) .

### Impact Explanation
An attacker who legitimately installs the target app on their own (unprivileged) Shopify store receives real, correctly-signed webhooks for their own shop. By replaying the identical `raw_body`/`hmac-sha256` pair to the app's public webhook endpoint with a forged `X-Shopify-Shop-Domain` header naming a victim shop, the request passes `Utils::HmacValidator.validate` and is dispatched with `WebhookMetadata#shop` set to the victim's domain. Any host application following the gem's documented pattern (using `data.shop` to select which tenant's records to update/create/delete) will act on the victim's tenant using attacker-supplied body content — a cross-tenant data manipulation / cross-tenant access vulnerability that crosses a real authentication boundary (the app's own webhook secret) without needing the app's credentials.

### Likelihood Explanation
Moderate-to-high: exploitation only requires the attacker to be an "unprivileged internet user" with respect to the victim, but a legitimate (self-service) installer of the target app for their own store — a normal, unprivileged action for any public Shopify app. Capturing one's own webhook body+HMAC and replaying it with a different `shop-domain` header requires no secret material and no access to the victim's environment.

### Recommendation
Bind the shop identity into the authenticated payload before trusting it: either include the `shop-domain` header (and other identifying headers) in the HMAC-signed material used for verification, or require the caller to independently verify that `request.shop` matches a shop known to have a currently valid webhook/app installation (e.g., cross-check against a stored, previously-registered shop/session) before dispatching to the handler. At minimum, document prominently that `data.shop` is unauthenticated header data and must not be trusted as a tenant-scoping key without additional verification.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and triggers any subscribed webhook topic (e.g. `orders/create`), capturing the raw POST body and the `X-Shopify-Hmac-Sha256` header sent by Shopify.
2. Attacker POSTs to the app's webhook endpoint reusing the exact same body and HMAC header, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` parses `shop` as `"victim.myshopify.com"` [2](#0-1) .
4. `ShopifyAPI::Webhooks::Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over the (unchanged) body and matches — validation succeeds [6](#0-5) .
5. The handler is invoked with `WebhookMetadata.new(topic:, shop: "victim.myshopify.com", body:, ...)` [7](#0-6) , and any host app that scopes work by `data.shop` performs the attacker's chosen action against the victim shop's data.
