Based on my investigation, I found a clear analog to the reported bug class in Raydium's `Initialize2` instruction. This is the strongest match: `AmmInfo.lp_amount` (the initial liquidity minted) is computed directly from the raw vault token-account balances rather than from the amounts the caller actually specified/transferred, which lets an unprivileged actor permanently corrupt/DoS a brand-new pool's accounting by front-running `Initialize2` with a direct token transfer to the not-yet-initialized vault accounts.

### Title
Anyone can donate tokens to a not-yet-initialized AMM vault to corrupt initial LP accounting - (File: program/src/processor.rs)

### Summary
`process_initialize2` derives the amm's vault addresses deterministically from the market key and program-derived seeds before the AMM account is created, and only transfers `init.init_coin_amount`/`init.init_pc_amount` from the creator into those vaults. However, the initial liquidity (`amm.lp_amount`) and the `TargetOrders` PnL baseline (`target_order.check_init`) are computed from the vaults' *actual on-chain balances* (`amm_coin_vault.amount`, `amm_pc_vault.amount`), not from `init.init_coin_amount`/`init.init_pc_amount`. Because the vault token accounts are deterministic PDAs derivable by anyone before `Initialize2` executes, and SPL token transfers do not require receiver permission, any unprivileged party can pre-fund these vault accounts, causing the pool to be initialized with a balance/LP-mint mismatch relative to what the pool creator intended.

### Finding Description
In `process_initialize2` [1](#0-0) , the creator's tokens are moved into `amm_coin_vault_info`/`amm_pc_vault_info` for exactly `init.init_coin_amount`/`init.init_pc_amount`. Immediately after, the code re-reads the vault accounts and uses their live `amount` field — not the `init_*` parameters — for all subsequent invariant setup: [2](#0-1) 

The normalized invariant values `x`/`y` used to seed `TargetOrders` (the PnL baseline) and the initial `liquidity` (LP token supply) minted for the creator are calculated from `amm_pc_vault.amount` / `amm_coin_vault.amount`: [3](#0-2) 

Since `amm_coin_vault_info` and `amm_pc_vault_info` are created via `generate_amm_associated_spl_token`, whose address is deterministically derived from the `market` account and a fixed seed (`COIN_VAULT_ASSOCIATED_SEED`/`PC_VAULT_ASSOCIATED_SEED`) [4](#0-3) , any unprivileged actor can compute these addresses ahead of time (using `get_associated_address_and_bump_seed`) and transfer arbitrary amounts of the coin/pc mint into them *before* the pool creator's `Initialize2` transaction lands. Because the account is only "assigned" to the program (not yet holding `AmmInfo`), an attacker's prior token transfer into the not-yet-owned SPL token account is a normal, permissionless SPL transfer — it does not require the account to be initialized as belonging to any particular AMM. This is directly analogous to the reported bug class: an unprivileged party manipulates a balance-derived calculation by donating tokens directly to a contract-controlled account, corrupting downstream accounting that the legitimate flow assumed would exactly equal caller-supplied amounts.

The result: `liquidity` (LP mint amount) is computed as `sqrt(x * y)` from the polluted balances rather than from `init_pc_amount`/`init_coin_amount`, so the pool creator receives an LP amount that does not correspond to the tokens they actually contributed, and `TargetOrders.calc_pnl_x/calc_pnl_y` — the baseline used by `calc_take_pnl` for all future PnL accounting in swaps, deposits, and withdrawals — is permanently seeded with the attacker-inflated totals.

### Impact Explanation
This permanently corrupts the pool's core invariant accounting at the moment of creation:
- The LP supply/vault-balance ratio becomes wrong from inception, meaning legitimate depositors' later `Deposit`/`Withdraw` calculations (which rely on `total_coin_without_take_pnl`/`total_pc_without_take_pnl` proportional to `lp_amount`) are skewed relative to the creator's intended initial price and liquidity.
- The `TargetOrders.calc_pnl_x/calc_pnl_y` baseline used in every subsequent `calc_take_pnl` call [5](#0-4)  is seeded from the polluted balance, permanently distorting the "PnL owner" fee-skim accounting for the life of the pool (unless the pool is unusable/needs a workaround, this is a persistent unbacked-LP/insolvent-accounting condition affecting all future LPs and swappers of that pool).
- This satisfies "insolvent pool accounting" / "unbacked LP minting" from the validation criteria — the minted `lp_amount` no longer corresponds 1:1 to the creator-intended deposit ratio, and it cannot be fixed after the fact since `Initialize2` can only run once (`amm.status != Uninitialized` guard prevents re-init).

### Likelihood Explanation
Likelihood is high for any attacker who front-runs pool creation: the vault addresses are fully deterministic PDAs computable from the `market` pubkey alone (public knowledge, and market accounts are typically created/known before the AMM `Initialize2` transaction is submitted). The attacker only needs to know the target mint's decimals and send an SPL `Transfer` to the pre-computed vault address before the `Initialize2` transaction executes — no privileged access, no special permissions, a single transaction.

### Recommendation
In `process_initialize2`, do not trust the raw vault `amount` field for computing `lp_amount` and the `TargetOrders` baseline. Instead:
1. Snapshot the vault balances immediately after account creation but *before* the creator's transfer, and require they equal `0`.
2. After the creator's transfer, verify `amm_coin_vault.amount == init.init_coin_amount` and `amm_pc_vault.amount == init.init_pc_amount` exactly (reject otherwise), or compute `x`/`y`/`liquidity` strictly from `init.init_coin_amount`/`init.init_pc_amount` rather than from the live vault balances.

### Proof of Concept
1. Attacker computes the coin/pc vault PDAs via `get_associated_address_and_bump_seed(program_id, market.key, COIN_VAULT_ASSOCIATED_SEED, program_id)` (and the pc equivalent) using the public `market` pubkey that will be used in the pool creator's forthcoming `Initialize2` call.
2. Before the creator's `Initialize2` transaction lands, the attacker sends an SPL `Transfer` of, e.g., 1,000,000 extra coin-mint tokens to the not-yet-created vault address (the associated-account creation in `generate_amm_associated_spl_token` will still succeed since the account is only "assigned", and SPL transfers to any valid token account succeed regardless of who initialized it — this can even be done to an address that doesn't exist yet by having the attacker create it first if allowed, or immediately after `generate_amm_associated_spl_token` runs but before the creator's own transfer in the same slot via transaction ordering).
3. When `Initialize2` executes, `amm_coin_vault.amount` reflects `init_coin_amount + attacker_donation`, inflating `y` in [6](#0-5) , which inflates `liquidity` and `target_order.calc_pnl_y`, permanently misaligning the pool's PnL/LP accounting relative to the creator's intended `init_coin_amount`/`init_pc_amount`.
