### Title
Permissionless `flash_loan` pulls `amount + fee` from an attacker-chosen `receiver`'s allowance — residual approvals to the pool are drained as fees - (File: contracts/pool/src/ops/flash.rs)

### Summary
`Pool::flash_loan(initiator, receiver, ...)` lets the caller name an arbitrary `receiver`. The pool pays `amount` to that receiver, invokes its `execute_flash_loan` callback, and then repays itself via `token.transfer_from(pool, receiver, pool, amount + fee)` (`collect_repayment`, `contracts/pool/src/ops/flash.rs:166-180`), spending the receiver's allowance to the pool. The only checks on `receiver` are `require_wasm_receiver` and `allowance(receiver, pool) >= amount + fee`. No `receiver.require_auth()` is ever performed — the pool's own invoker-contract auth suffices for `transfer_from`. Any WASM contract that left a standing/residual allowance to the pool and implements `execute_flash_loan` without reverting can be forced into an uninvited flash loan by any unprivileged address, losing `fee` per call until the allowance or pool cash is exhausted.

### Finding Description
Same bug class as the BaseVault report: a public entrypoint takes the *source* of a `transfer_from` pull as a caller-supplied parameter instead of binding it to the authenticated caller. In `apply`, `receiver` flows from the entrypoint arguments into `collect_repayment`, which uses it as the `from` leg of `asset.transfer_from(pool, receiver, pool, &terms.total_repayment)` (flash.rs:178). The pre-check at flash.rs:175 (`asset.allowance(receiver, pool) >= terms.total_repayment`) confirms this path deliberately relies on the receiver's pre-existing allowance rather than on a repayment `transfer` under the receiver's auth. Because the pool is the spender, no authorization from `receiver` is required for the pull itself; authorization only matters inside the `execute_flash_loan` callback, which a compliant receiver will not use to block repayment it never consented to.

### Impact Explanation
Theft of user funds: each forced loan burns `fee` of the victim receiver's token balance, paid to the pool as protocol revenue (`book_fee` credits cash and mints revenue, flash.rs:124-136). The attacker can repeat with the maximum cash amount every call until the victim's allowance to the pool is consumed, so total loss is bounded by the victim's residual allowance — the exact same exposure as the original finding (a user who over-approved the contract). Receiver contracts are precisely the population likely to hold standing allowances to the pool (approve-once patterns).

### Likelihood Explanation
Requires (a) a WASM receiver contract that implements `execute_flash_loan` and does not internally validate `initiator`/revert for unsolicited loans, and (b) that contract having a nonzero allowance to the pool. Both are realistic for integrations that pre-approve the pool. The attacker path is a single unprivileged `flash_loan` call per iteration. Severity Medium: loss is bounded by allowance and protocol cash per call, and attacker profit is indirect (griefing / fee siphoning rather than direct receipt of funds).

### Recommendation
Bind the pull to consent, the same fix as the original report:
- Require `receiver.require_auth()` — or have the receiver repay via `transfer` inside its callback — instead of `transfer_from` on an arbitrary allowance, or
- Have `initiator.require_auth()` and enforce `initiator == receiver` in the `flash_loan` entrypoint so a caller can only spend allowance belonging to the authenticated party.

### Proof of Concept
1. Victim receiver contract `V` implements `execute_flash_loan` and holds a standing allowance `A` to the pool from a prior operation (e.g., `approve(pool, A)` retained after a repaid loan).
2. Attacker calls `pool.flash_loan(initiator = attacker, receiver = V, amount = max_cash, data = "")`.
3. Pool pays `amount` to `V` (flash.rs:60), invokes `V.execute_flash_loan(attacker, asset, amount, fee, pool, data)` which returns normally.
4. `collect_repayment` verifies `allowance(V, pool) >= amount + fee` and calls `transfer_from(pool, V, pool, amount + fee)` — `V` loses `fee` net, allowance decreases by `amount + fee`.
5. Repeat until `A` is drained or below `amount + fee`; all fees accrue to the pool as protocol revenue.

Uncertainty noted: the exact `flash_loan` entrypoint signature and `require_wasm_receiver` internals were not read line-by-line, but `flash::apply`'s signature (`initiator`, `receiver` as free parameters) and the allowance-pull repayment are confirmed in `contracts/pool/src/ops/flash.rs:40-71,166-180`.
