### Title
PoA Bridge withdrawal status matching by `assetId` alone misreports completion status/txHash for batched same-token withdrawals - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal` resolves the on-chain status of a specific withdrawal by calling `findMatchingWithdrawal`, which matches purely on `assetId`, ignoring the withdrawal's `index` within the originating transaction. When a NEAR transaction contains more than one withdrawal of the same token (a legitimate, unprivileged batch withdrawal), the SDK can report the wrong withdrawal's status and `txHash` for a given `WithdrawalIdentifier`.

### Finding Description
`describeWithdrawal` calls `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`, which returns the first API-reported withdrawal whose `near_token_id` matches the requested `assetId`, with no consideration of `args.index`: [1](#0-0) [2](#0-1) 

The code's own comment acknowledges this: "Currently only matches by assetId. This means multiple withdrawals of the same token in a single transaction are not supported." The `index` is computed and passed through in `createWithdrawalIdentifiers`/`createWithdrawalIdentifier` for exactly this disambiguation purpose, but `findMatchingWithdrawal` never uses it: [3](#0-2) [4](#0-3) 

`watchWithdrawal` treats whatever `describeWithdrawal` returns as authoritative and resolves the promise with that `txHash` once `status === "completed"`: [5](#0-4) 

This breaks the equality "status/txHash reported == the on-chain outcome for that specific withdrawal (index)". If a user (via `signAndSendIntent` with multiple withdrawal intents, or via the SDK's batch withdrawal composition) submits two `ft_withdraw` intents of the same POA token to different destination addresses/amounts within one NEAR transaction, both `WithdrawalIdentifier`s share the same `tx.hash` and `assetId` but differ by `index`. `findMatchingWithdrawal` will return the same (first) API record for both identifiers, causing the SDK/integrator to believe withdrawal #2 is "completed" with withdrawal #1's `txHash` while #2 may still be pending, failed, or actually landed at a different destination.

### Impact Explanation
An integrator that credits/refunds a user or updates internal ledger state based on `describeWithdrawal`'s `status`/`txHash` can double-credit a withdrawal as completed (using another withdrawal's transfer hash as proof) or refund the wrong entry, before the actual withdrawal has settled — a status misreport that can lead an integrator to release funds/credits prematurely or twice, matching the High severity criteria ("a status or hash misreport making an integrator credit or refund twice").

### Likelihood Explanation
This requires only that an ordinary, unprivileged user (or an integrator building on the SDK) construct a batch/composed NEAR transaction with two or more POA-bridge withdrawals of the same underlying token in a single transaction — a normal usage pattern the SDK itself supports (multiple `withdrawalParams`, `signedIntents` composition). No malicious relayer, admin, or bridge operator behavior is required.

### Recommendation
Update `findMatchingWithdrawal` (and the POA bridge status API usage) to disambiguate by more than `assetId` — e.g., match on `assetId` + destination address + amount, or track per-index ordinal matches deterministically (as the code comment suggests, by sorting both API results and withdrawal params by amount) so each `WithdrawalIdentifier.index` maps to a unique settlement record before reporting `completed` with its associated `txHash`.

### Proof of Concept
1. Build an intent transaction containing two `ft_withdraw` intents for the same POA asset (e.g., `nep141:usdc.omft.near`) with different `destinationAddress`/`amount`, submitted as one NEAR tx via `signAndSendIntent`/composed payloads.
2. `createWithdrawalIdentifiers` assigns `index: 0` and `index: 1` to the two withdrawals sharing the same `tx.hash`, per `packages/intents-sdk/src/core/withdrawal-watcher.ts` lines 80-107.
3. When both withdrawals are queried via `watchWithdrawal` → `PoaBridge.describeWithdrawal`, `getWithdrawalStatusWithRetry` returns the same list of withdrawal records for `tx.hash`; `findMatchingWithdrawal` for both `index: 0` and `index: 1` filters solely on `assetId` and returns the identical (first-matching) record.
4. Both watchers resolve with the same `status`/`txHash`, even though the two withdrawals are actually distinct on-chain events that may complete at different times or to different recipients — demonstrating the status/txHash misattribution.

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}
