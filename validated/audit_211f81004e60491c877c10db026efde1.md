### Title
Webhook shop-domain identity spoofing via HMAC that only covers the request body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while the shop identity (`shop-domain` header) that is later trusted and forwarded to the app's webhook handler is never included in that signature.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns `@raw_body` exclusively: [1](#0-0) 
Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from HTTP headers with no cryptographic binding to the signed payload: [2](#0-1) 

`Utils::HmacValidator.validate` verifies `OpenSSL::HMAC.hexdigest(secret, verifiable_query.to_signable_string)` against the `hmac` field, i.e. it only proves the raw body bytes were signed by the app's shared `api_secret_key`; it says nothing about which shop the request claims to be from: [3](#0-2) 

`Webhooks::Registry.process` then trusts `request.shop` as the tenant identity and hands it straight to the registered handler alongside the (validated-body-but-unbound-shop) payload: [4](#0-3) 

The broken binding, as an equality that should hold but doesn't:
`shop_header_used_by_handler == shop_that_the_HMAC_actually_authenticates`

Because Shopify signs webhooks with the **app's single shared `client_secret`** (the same `api_secret_key` used for every merchant install of the app, not a per-shop secret), any merchant who has legitimately installed the app can capture a genuine webhook delivery to their own shop (raw body + valid `X-Shopify-Hmac-Sha256`) and replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary victim shop's domain in the `X-Shopify-Shop-Domain` header. `HmacValidator.validate` still returns `true` (the body and secret didn't change), and `Registry.process` passes the forged `shop` value into `WebhookMetadata`/the handler as if it were an authenticated fact.

### Impact Explanation
This lets an unprivileged, already-installed merchant (an "unprivileged internet user" relative to other tenants of the same app) inject attacker-controlled webhook data — e.g. order, customer, or product payloads that they fully control from their own shop — while making the app attribute that data to a different tenant (`shop-domain` header of their choosing). Any host application that follows this gem's documented pattern of trusting `WebhookMetadata#shop` as the tenant key (there is no gem-provided or documented alternative binding) is exposed to cross-tenant data confusion/injection. This matches the Critical category "cross-tenant access" since the identity boundary between shops enforced by webhook delivery is broken at the gem level.

### Likelihood Explanation
Requires only that the attacker be able to install the app on at least one shop (a normal, low-privilege action for any merchant) and be able to POST arbitrary HTTP requests with a crafted `X-Shopify-Shop-Domain` header to the app's public webhook endpoint — both trivially available to "any internet user" who installs the app. No access token, `client_secret`, or privileged credentials are needed; only knowledge of one legitimately-received (body, HMAC) pair, which the attacker already possesses from their own installation.

### Recommendation
Bind the shop identity into the signed material used to verify webhook authenticity, or otherwise cryptographically tie the `shop-domain` header to the specific delivery (e.g., derive/verify the shop domain against Shopify's registered webhook endpoint metadata per shop, or require the app to cross-check `request.shop` against a previously known/authorized shop before trusting `WebhookMetadata#shop`). At minimum, `Utils::VerifiableQuery`/`Webhooks::Request#to_signable_string` should document clearly, or the library should enforce, that `shop`, `topic`, and `webhook_id` are *not* authenticated by the HMAC and must not be used as a sole tenant-identity source in application logic without additional verification (e.g. against a stored per-shop record).

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker.myshopify.com` (a normal, unprivileged flow).
2. Shopify delivers a legitimate webhook to the app: raw body `B` with a valid `X-Shopify-Hmac-Sha256: H` (computed over `B` with the app's shared `client_secret`) and `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. Attacker captures `(B, H)` and replays a POST to the app's webhook endpoint with the same body `B` and header `H`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it validates only `B` against `H`
   ( [1](#0-0)  and [5](#0-4) ).
5. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and body `B`, even though `B` originated from and was authorized only for `attacker.myshopify.com`
   ( [4](#0-3) ).
