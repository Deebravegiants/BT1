### Title
Unchecked ERC20 return value in `withdraw()` and `SweepDust` handling causes fund loss and permanently stuck escrow — ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of `IntentGatewayV2` correctly uses OpenZeppelin's `SafeERC20` (`safeTransferFrom`/`safeTransfer`) for escrow deposits in `placeOrder`/`_fillCrossChain`-equivalent paths, but the escrow-release path (`withdraw()`) and the governance `SweepDust` handler instead use raw low-level `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` calls and only check that the *call itself* did not revert (`success`), never decoding/validating the ERC20 boolean return value.

### Finding Description
`withdraw()` — invoked from `onAccept()` when a `RedeemEscrow`/`RefundEscrow` message is delivered via a relayed Hyperbridge proof, and also directly from `cancelOrder()` for same-chain cancellation and from `onGetResponse()` — pays out escrowed tokens like this: [1](#0-0) 

and pays accumulated fees the same way: [2](#0-1) 

The `SweepDust` admin/governance-triggered branch of `onAccept` has the identical pattern: [3](#0-2) 

In all three cases the code only checks `success` (i.e. that the low-level call did not revert), then unconditionally decrements `_orders[body.commitment][token] -= amount` and emits `EscrowReleased`/`EscrowRefunded`/`DustSwept`, without checking the ABI-decoded boolean return value that the ERC20 standard specifies for `transfer`. Compare this with the escrow-*deposit* side of the very same contract (`_fillCrossChain`/`placeOrder`), which correctly uses `SafeERC20.safeTransferFrom`/`safeTransfer`: [4](#0-3) 

`SafeERC20` (already imported and used elsewhere in this very file) verifies both `success` and (if return data is present) that it decodes to `true`; the `withdraw`/`SweepDust` code path does neither, so it will treat a token call that returns `false` (a valid, non-reverting failure signal for ERC20-compliant tokens, and also emitted by numerous "bugged"/non-standard tokens on this Tron deployment target) as a successful transfer.

### Impact Explanation
Because `_orders[...] -= amount` and the `EscrowReleased`/`EscrowRefunded`/`DustSwept` events fire unconditionally on any non-reverting call, a token `transfer` that returns `false` (transfer failed) will still be accounted for as delivered: the beneficiary/solver receives nothing, but the escrow slot is decremented and the order is marked filled/refunded (`_filled[body.commitment] = beneficiary`). The result is a direct, permanent loss of the escrowed input tokens for the user/solver who was supposed to receive them — the tokens remain locked in the `IntentGatewayV2` contract with no accounting path left to reclaim them, since the withdrawal has already been marked complete. This is reachable by any relayer submitting a normal cross-chain settlement proof or any user calling `cancelOrder`, using nothing more than the ordinary intent lifecycle.

### Likelihood Explanation
This does not require an adversarial actor: the bug triggers whenever the underlying ERC20 token used as an input asset does not strictly follow OpenZeppelin's "revert-on-failure" convention and instead returns `false` on failed transfers (e.g., due to insufficient contract balance from prior fee/dust rounding, paused/blacklisted-recipient tokens, or otherwise non-standard tokens commonly deployed on the Tron network this contract targets). Since arbitrary ERC20 tokens are accepted as order inputs (`order.inputs[i].token`), any solver or relayer completing a normal, permissionless settlement flow can encounter this path without any special crafting.

### Recommendation
Replace the raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` + `success`-only checks in `withdraw()` (both the per-token loop and the fee payout) and in the `SweepDust` branch of `onAccept()` with `SafeERC20.safeTransfer`, consistent with how the deposit side of this same contract already uses `safeTransferFrom`/`safeTransfer`. This ensures both call success and standard-conformant boolean-return validation before mutating escrow accounting or emitting finalization events.

### Proof of Concept
1. A user places a cross-chain order with an input token `T` that is ERC20-compliant but returns `false` (rather than reverting) on a failed `transfer` — a legal implementation per EIP-20 semantics (e.g., a token that returns `false` when the recipient is blacklisted/paused, or a mock/legacy-style token common on Tron).
2. Escrow deposit succeeds via `safeTransferFrom` in the input-token collection phase: [4](#0-3) .
3. Solver fills the order on the destination chain; a `RedeemEscrow` message is relayed back and delivered through `onAccept()` → `withdraw()`.
4. At payout time, token `T.transfer(beneficiary, amount)` returns `false` (e.g., beneficiary transiently blacklisted, or contract-side condition causing a controlled failure) but the low-level `.call` does not revert: [1](#0-0) .
5. `success` is `true` (the call didn't revert), so the code proceeds to decrement `_orders[commitment][token]` and emits `EscrowReleased`, marking the order as finalized even though the beneficiary received zero tokens — the tokens are now stranded in the `IntentGatewayV2` contract with no remaining code path to withdraw them for that commitment.
