### Title
Unvalidated route payload lets a rogue venue execute arbitrary token transfers under the caller's signed auth tree, draining wallet funds - (File: contracts/controller/src/strategies/swap.rs)

### Summary
Analog of CVE-2020-15961 ("insufficient policy validation → sandbox escape"): `swap_collateral`/`multiply`-style entrypoints accept an opaque, caller-supplied `swap` route blob and forward it verbatim to the configured router. Neither the controller nor the router validates which venue contracts the route names, so a crafted route can place attacker-controlled code on the call stack beneath the victim's authorization. Any token transfer that code makes from the victim's wallet is recorded as a child of the victim's signed `swap_collateral` auth entry and executes if the victim signs the simulated tree — escaping the intended "one exact input transfer" policy.

### Finding Description
`swap_tokens` grants narrow authority only for the controller's own input token: `authorize_transfer_as_current(env, token_in, &controller, &router_addr, amount_in)` binds exactly one transfer, and post-call balance deltas bound the router's spend (`RouterOverspend`/`NoSwapOutput` checks). [1](#0-0) 

However, the `swap` payload itself is never inspected. The router resolves venues from the payload and keeps no venue/pool allowlist (documented in the threat model: "The router calls the pool and token addresses its payload names and keeps no allowlist of them, so a route can put third-party code on the call stack below the caller's authorization"). [2](#0-1) 

The harness test `rogue_hop_pool_transfer_joins_caller_auth_tree.rs` proves the escape end-to-end: a `RogueHopPool` named in the route performs `token::transfer(victim, attacker, WALLET_BALANCE)` inside `swap_collateral`; simulation records it as a child of the caller's `swap_collateral` entry, and when the victim signs that tree the transfer executes — the victim's unrelated wallet token is fully drained while the swap itself still returns fair output and passes all controller gates. [3](#0-2) [4](#0-3) 

### Impact Explanation
Theft of user funds: an unprivileged attacker deploys a venue contract that transfers arbitrary tokens from the victim's wallet, embeds it in a route, and induces the victim to sign the poisoned auth tree (the recorded tree looks like an ordinary swap to a wallet that doesn't decode children). The victim's loss is their full wallet balance of the target token — unbounded by the swap amount, the payload minimum, or the controller's final risk gate. Direct `execute_strategy` on the router carries the same exposure for every swap user. [5](#0-4) 

### Likelihood Explanation
Requires victim interaction (signing a route containing the malicious hop), mirroring CVE-2020-15961's UI:R requirement. Any party able to supply or influence the route bytes the user signs — a malicious or compromised quoting frontend, a crafted quote API response — can mount it. The protocol provides no on-chain venue validation, and the mitigation is delegated entirely to client-side route decoding (`verifyRouteBytes` style checks), which users of other clients or raw signing flows do not perform.

### Recommendation
Enforce venue/policy validation on-chain or constrain the auth surface: (1) require the controller/router to validate route venues against a governance-managed allowlist before invocation; or (2) architect the strategy call so the router executes under the controller's authorization only, never under the caller's — i.e., have the caller transfer `amount_in` to the controller up front and remove the need for caller-signed child invocations during the route. At minimum, ship and mandate the documented client-side tree verification as part of the signing path.

### Proof of Concept
`tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` in the repo demonstrates it: `UnlistedPoolRouter` invokes the route-named `hop_pool.swap`, and `RogueHopPool` executes `token::Client::transfer(&victim, &attacker, &WALLET_BALANCE)`. With the honest root-only signed tree the host rejects the call (`Unauthorized function call for address`); with the simulation-produced poisoned tree the call succeeds, `wallet(alice) == 0` and `wallet(attacker) == WALLET_BALANCE`. [6](#0-5)

#[test]
fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
}
