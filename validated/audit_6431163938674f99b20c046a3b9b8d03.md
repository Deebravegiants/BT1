### Title
Owner-pausing `HyperFungibleToken`/`WrappedHyperFungibleToken` blocks the `onPostRequestTimeout` refund path, freezing already-burned/locked user funds until unpause - (File: `sdk/packages/core/contracts/apps/HyperFungibleToken.sol`, `sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol`, and their Upgradeable counterparts)

### Summary
`HyperFungibleToken.send()` burns the sender's tokens immediately and dispatches an ISMP POST request. If that request times out without delivery, the only way for the sender to get their funds back is via `onPostRequestTimeout`, which re-mints (or, for the wrapped/lock variant, unlocks/transfers back) the burned amount. That callback is guarded by `whenNotPaused`. If the contract owner pauses the token — the documented emergency lever — while a timeout proof is being submitted, the refund call reverts and the user's funds stay stuck, mirroring the SiloAMO/MINTR pattern where an emergency pause on one component (`MINTR`) blocks the completion of an already-committed unwind (`_withdraw`) on another.

### Finding Description
`send()` burns tokens up front: [1](#0-0) 

The only recovery path for a message that never gets delivered before its `timeoutTimestamp` is the timeout callback, which is explicitly gated by `whenNotPaused`: [2](#0-1) 

The same pattern exists in the wrapped/lock-unlock variant, whose `onPostRequestTimeout` unwraps WETH or transfers the underlying ERC20 back to the refundee, and is likewise `whenNotPaused`: [3](#0-2) 

And the Upgradeable variants duplicate this exactly: [4](#0-3) [5](#0-4) 

`pause()`/`unpause()` are owner-only, and the docs describe pausing as the intended full-stop emergency mechanism, explicitly covering `onAccept()` (mint on delivery) but not calling out that it also blocks refunds of already-burned funds: [6](#0-5) [7](#0-6) 

At the ISMP host level, `EvmHost.dispatchTimeOut` calls the application's `onPostRequestTimeout` and, only on success, deletes the request commitment and refunds the relayer fee; if the callback reverts, the commitment is restored so the timeout can be resubmitted later: [8](#0-7) 

So while a paused token cannot itself be worked around by the relayer, the timeout is not permanently destroyed — it can be retried once the owner unpauses. This is the same structural pattern as the M-03 report: an emergency-pause primitive on a supporting component blocks an already-committed reversal/unwind action, leaving user/AMO funds stuck for the duration of the pause, at exactly the time (an emergency) when the pause is most likely to be engaged and least likely to be quickly lifted.

### Impact Explanation
- Users whose cross-chain transfer already burned/locked their tokens on the source chain cannot recover funds via timeout while the token is paused, even though the tokens were destroyed/locked before the pause. Funds are frozen (not lost) for the duration of the pause, which is an unbounded, admin-controlled window.
- Because `onPostRequestTimeout` reverts entirely (not gracefully swallowing the pause condition), the relayer's fee refund on the source `EvmHost` for that timeout is also blocked in the same transaction, compounding the freeze with relayer fee non-payment until retried.
- This qualifies as a temporary/likely-recoverable freezing of user funds during exactly the periods (protocol emergencies) where responsiveness matters most, analogous to the accepted-severity M-03 finding (Medium) for the SiloAMO/MINTR case.

### Likelihood Explanation
Requires the token owner to pause the contract (a legitimate, documented admin action for emergencies) while at least one in-flight `send()` has timed out and is awaiting a relayer's timeout-proof submission. This is a realistic operational scenario: the same emergency conditions that motivate an owner to pause the bridge token (e.g., a compromised peer chain or exploit) are also the conditions under which in-flight cross-chain sends are most likely to be timing out and need refunding.

### Recommendation
Do not let `whenNotPaused` block the refund/timeout path. Either:
- Remove the `whenNotPaused` modifier from `onPostRequestTimeout` in `HyperFungibleToken`, `HyperFungibleTokenUpgradeable`, `WrappedHyperFungibleToken`, and `WrappedHyperFungibleTokenUpgradeable`, since a timeout refund only returns funds that were already removed from circulation/custody and does not create new exposure the way `send()`/`onAccept()` do; or
- If pausing must also stop refunds (e.g., because the peer/source is suspected compromised and a forged timeout proof is the concern), wrap only the state-changing mint/transfer in a `try/catch` so a pause does not cause the whole callback to revert and instead defers gracefully, consistent with the bophades fix pattern (`try MINTR.burnOhm(...) {} catch {}`) — though note the ISMP host's restore-on-failure already provides retryability, so the primary risk here is only the length of the freeze, not permanent loss.

### Proof of Concept
1. User calls `HyperFungibleToken.send()` on chain A, burning `amount` tokens and dispatching a POST request with a `timeout` window (`sdk/packages/core/contracts/apps/HyperFungibleToken.sol:264-282`).
2. The destination chain fails to deliver the message before `timeoutTimestamp` (e.g., relayer outage or chain B halt) — the same category of emergency that would prompt pausing.
3. Owner of the `HyperFungibleToken` on chain A calls `pause()` (`sdk/packages/core/contracts/apps/HyperFungibleToken.sol:213-215`) in response to the incident.
4. A relayer submits the timeout proof via `HandlerV2.handlePostRequestTimeouts`, which calls `EvmHost.dispatchTimeOut`, which in turn calls `onPostRequestTimeout` on the token (`evm/src/core/EvmHost.sol:885-906`).
5. `onPostRequestTimeout` reverts due to `whenNotPaused` (`sdk/packages/core/contracts/apps/HyperFungibleToken.sol:321-326`); `dispatchTimeOut` catches the revert and restores the commitment for later retry, but the user's burned tokens are not refunded and the relayer fee is not paid, for as long as the pause remains in effect.

    function onPostRequestTimeout(PostRequestTimeout calldata incoming) external override onlyHost whenNotPaused {
        HyperFungibleToken.Message memory message = abi.decode(incoming.request.body, (HyperFungibleToken.Message));
        address refundee = _toAddr(message.from);

        if (_isWeth) {
            // Try a native-ETH push first; if the refundee cannot accept native value
            // (e.g. the caller used the ERC-20 deposit path in `send()` from a
            // non-payable contract), re-wrap the withdrawn ETH and deliver the
            // underlying WETH as an ERC-20 transfer so the timeout still settles and
            // funds are not permanently locked.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = refundee.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(refundee, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(refundee, message.amount);
        }

        emit Refunded({to: refundee, amount: message.amount});
    }

## Pausability

Both contracts inherit from OpenZeppelin's `Pausable`. The owner can pause and unpause all operations:

```solidity lineNumbers
IHyperFungibleToken(tokenAddress).pause();
IHyperFungibleToken(tokenAddress).unpause();
```

When paused, `HyperFungibleToken` blocks all ERC20 transfers (`transfer` and `transferFrom`) in addition to cross-chain `send()` and `onAccept()`. This is a full stop on all token movement — use it for emergency situations or during migrations.

    function dispatchTimeOut(
        PostRequestTimeout memory timeout,
        FeeMetadata memory meta,
        bytes32 commitment
    ) external restrict(_hostParams.handler) {
        // replay protection
        delete _requestCommitments[commitment];
        (bool success,) = _bytesToAddress(timeout.request.from)
            .call(abi.encodeWithSelector(IApp.onPostRequestTimeout.selector, timeout));

        if (!success) {
            // so that it can be retried
            _requestCommitments[commitment] = meta;
            return;
        }

        if (meta.fee != 0) {
            // refund relayer fee
            IERC20(feeToken()).safeTransfer(meta.sender, meta.fee);
        }
        emit PostRequestTimeoutHandled({commitment: commitment, dest: string(timeout.request.dest)});
    }
```
