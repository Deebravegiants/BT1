This confirms the key vulnerability: `HttpClient#initialize` builds `@base_uri` directly from `session.shop` — `"https://#{api_host || session.shop}"` — with **no domain validation** [1](#0-0) . `ShopifyAPI::Utils::ShopValidator.sanitize!` exists specifically to constrain shop values to trusted Shopify domains, but `Auth::Oauth.validate_auth_callback` never calls it on `auth_query.shop` before using it to build the `null_session` that POSTs the `client_secret` and authorization `code` [2](#0-1) .

### Title
SSRF/Client-secret exfiltration via unsanitized `shop` domain in OAuth callback token exchange - (File: lib/shopify_api/auth/oauth.rb)

### Summary
`Auth::Oauth.validate_auth_callback` builds the access-token-exchange request host from `auth_query.shop` without ever routing it through `Utils::ShopValidator.sanitize!`, even though that validator exists precisely to constrain shop values to Shopify's trusted domain suffixes (`myshopify.com`, `shopify.com`, `spin.dev`, etc.) [3](#0-2) . `HttpClient#initialize` then trusts `session.shop` verbatim to compose `@base_uri` for the outbound HTTPS request that carries the app's `client_secret` and OAuth `code` [4](#0-3) .

### Finding Description
The binding that should hold is: `shop` value used to select the token-exchange host == a value drawn from `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`. Instead, the gem only checks that `auth_query.shop` is HMAC-covered/consistent with the OAuth callback signature (`AuthQuery#to_signable_string` includes `shop`) [5](#0-4)  — it never checks that the *value itself* is a real, trusted Shopify domain versus an attacker-controlled host.

Concretely, in `validate_auth_callback`:
1. `null_session = Auth::Session.new(shop: auth_query.shop)` is created directly from the caller-supplied `shop` string, with zero sanitization [6](#0-5) .
2. `client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")` builds `@base_uri = "https://#{api_host || session.shop}"` from that unsanitized shop [7](#0-6) .
3. The client then POSTs `{ client_id, client_secret, code, expiring }` to `#{@base_uri}/admin/oauth/access_token` [8](#0-7) .

Since the calling host application is documented to construct `auth_query` from raw request parameters (`ShopifyAPI::Auth::Oauth::AuthQuery.new(request.parameters...)`) [9](#0-8) , the `shop`, `code`, `state`, `host`, `timestamp` values themselves are exactly the values Shopify signed in the redirect back to the app. The HMAC covers the string, but the gem is not enforcing that the shop domain matches `ShopValidator::TRUSTED_SHOPIFY_DOMAINS` (`myshopify.com`, `shopify.com`, `myshopify.io`, `spin.dev`, `shop.dev`) before using it as a network destination for `client_secret`. `ShopValidator.sanitize!`/`sanitize_shop_domain` is invoked elsewhere in the gem (e.g. `token_exchange.rb`, `client_credentials.rb`, `refresh_token.rb`, `clients/graphql/storefront.rb`) — confirming this is the gem's own established pattern for this exact binding — but it is conspicuously absent from `Auth::Oauth.validate_auth_callback` and `begin_auth` [10](#0-9) .

### Impact Explanation
If the host application does not itself re-validate `shop` before calling `validate_auth_callback` (which the gem's own docs example does not do [11](#0-10) ), an attacker who can influence the callback's `shop` query parameter enough to still produce a domain that is technically routable (e.g. a subdomain trick or a host the attacker controls that Shopify would still legitimately redirect to/sign for, or in a misconfigured/legacy flow where HMAC validation is weakened via `old_api_secret_key`) can cause the app's `client_secret` and one-time authorization `code` to be POSTed to a non-Shopify host of the attacker's choosing — SSRF with credential exfiltration of the app's `client_secret`. This directly matches the Critical impact category: "theft or exfiltration of ... the app's `client_secret`."

### Likelihood Explanation
Medium: exploitation depends on the host application passing through an insufficiently-validated `shop` value and on either a weakened HMAC check path or a host framework that fails to independently canonicalize `shop`. The gem's own defense-in-depth pattern (`ShopValidator.sanitize!`) is used in every other OAuth-adjacent credential-bearing flow (`token_exchange.rb`, `client_credentials.rb`, `refresh_token.rb`) but is missing specifically from `validate_auth_callback`, making this an inconsistency/gap rather than a purely theoretical issue.

### Recommendation
In `ShopifyAPI::Auth::Oauth.validate_auth_callback` (and `begin_auth`), call `Utils::ShopValidator.sanitize!(auth_query.shop)` immediately after HMAC validation and before constructing `null_session` / `auth_base_uri`, so the token-exchange request host is guaranteed to be a member of `ShopValidator::TRUSTED_SHOPIFY_DOMAINS` before the app's `client_secret` is transmitted.

### Proof of Concept
1. Host app builds `AuthQuery` directly from callback request params, per documented usage [9](#0-8) .
2. `ShopifyAPI::Auth::Oauth.validate_auth_callback(cookies:, auth_query:)` is called; HMAC check passes (`Utils::HmacValidator.validate(auth_query)`), state cookie matches.
3. `null_session = Auth::Session.new(shop: auth_query.shop)` is created with the unsanitized shop value — no call to `ShopValidator.sanitize!` occurs anywhere in the method [12](#0-11) .
4. `Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")` sets `@base_uri = "https://#{session.shop}"` [7](#0-6) .
5. `client.request(...)` POSTs `{client_id, client_secret, code, expiring}` to `https://#{auth_query.shop}/admin/oauth/access_token`, sending the app's `client_secret` to whatever host `auth_query.shop` resolves to.

        def validate_auth_callback(cookies:, auth_query:)
          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state

          null_session = Auth::Session.new(shop: auth_query.shop)
          body = {
            client_id: Context.api_key,
            client_secret: Context.api_secret_key,
            code: auth_query.code,
            expiring: Context.expiring_offline_access_tokens ? 1 : 0, # Only applicable for offline tokens
          }

          client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
          response = begin
            client.request(
              Clients::HttpRequest.new(
                http_method: :post,
                path: "access_token",
                body: body,
                body_type: "application/json",
              ),
            )
          rescue ShopifyAPI::Errors::HttpResponseError => e
            raise Errors::RequestAccessTokenError,
              "Cannot complete OAuth process. Received a #{e.code} error while requesting access token."
          end

          session_params = T.cast(response.body, T::Hash[String, T.untyped]).to_h
          session = Session.from(shop: auth_query.shop,
            access_token_response: Oauth::AccessTokenResponse.from_hash(session_params))
