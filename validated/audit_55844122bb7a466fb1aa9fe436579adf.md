### Title
Webhook `shop`/`topic` headers are trusted without HMAC coverage, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC validated by `Utils::HmacValidator.validate` in `Registry.process` binds solely to the JSON body bytes. The `shop-domain`, `topic`, `api-version`, and `webhook-id` values are read straight from unauthenticated HTTP headers (`shopify_header`) and forwarded as trusted fields in `WebhookMetadata` to the host app's handler.

### Finding Description
`lib/shopify_api/webhooks/request.rb` builds `shop`, `topic`, `api_version`, and `webhook_id` purely from HTTP headers: [1](#0-0) 
`Registry.process` verifies only the HMAC (which covers `@raw_body`), then immediately builds `WebhookMetadata` using `request.shop` and `request.topic` without any further binding check between the authenticated body and these header-derived identity fields: [2](#0-1) 
The HMAC computation itself, via `HmacValidator.validate_signature`, hashes `verifiable_query.to_signable_string`, which for webhooks is `@raw_body` only: [3](#0-2) [4](#0-3) 

This mirrors the report's bug class: a field acted upon (`shop`) is not covered by the integrity check (HMAC), breaking the intended binding `shop_header == shop_that_produced_this_HMAC-signed_body`. Because the same `api_secret_key` is shared by the app across all installed shops, any tenant that can trigger/replay a webhook delivery with a body they control (or capture a previously delivered valid `(body, hmac)` pair for topics with attacker-influenced content, e.g. `orders/create` with attacker-controlled order fields) can present it with a forged `shop-domain` header pointing at a different, victim shop. The library will accept the HMAC (it only validates body integrity) and hand the forged `shop` value to the app's handler as if it were verified.

### Impact Explanation
This is a cross-tenant integrity/authentication issue: the library's own webhook verification API silently returns "verified" for a payload whose claimed shop identity is unauthenticated, misleading any host application that (reasonably) trusts `WebhookMetadata#shop` after `Registry.process` succeeds. This can lead to cross-tenant data confusion in the app for webhook-driven business logic (e.g. an app which keys off `data.shop` to route the payload to a tenant's records), effectively achieving cross-tenant access to the app's per-shop processing without holding a valid credential for the target shop.

### Likelihood Explanation
Requires an attacker to be able to make an HTTP POST to the app's webhook endpoint with a valid HMAC over some body — achievable by any install of the app (which is an "unprivileged internet user" relative to other tenants) replaying its own genuine webhook deliveries with a swapped `shop-domain` header, since nothing in this gem ties the header to the signed content.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the signable string used for the webhook HMAC, or otherwise cryptographically bind the `shop-domain` header to the signed body before trusting it in `WebhookMetadata`, consistent with the binding used for OAuth/JWT flows elsewhere in the library.

### Proof of Concept
1. App installs on `attacker.myshopify.com` and receives a genuine webhook delivery with headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC over raw body>`.
2. Attacker resends the same raw body and HMAC to the app's webhook endpoint but replaces the header with `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only hashes `request.to_signable_string` (`@raw_body`), independent of the `shop-domain` header. [5](#0-4) 
4. The handler receives `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` with `shop` set to the forged `victim.myshopify.com`, despite no cryptographic proof that this webhook body actually pertains to that shop. [6](#0-5)
