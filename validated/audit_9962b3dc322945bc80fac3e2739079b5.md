### Title
Webhook `shop-domain` Header Is Not Covered by HMAC, Enabling Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identifier (`shop`) from an HTTP header that is never included in the HMAC signature computation. `Registry.process` validates only the HMAC over the raw body and then hands the unverified `shop` header straight to the application's webhook handler as the tenant key, breaking the intended binding of `hmac == sign(raw_body, shop)` down to `hmac == sign(raw_body)`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is completely separate from that signable string: [2](#0-1) 

`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (i.e., the raw body) and the app's `api_secret_key`, and never touches the shop header: [3](#0-2) 

`Registry.process` performs exactly that HMAC check and then, once it passes, forwards `request.shop` unchanged into `WebhookMetadata` for the handler to act on: [4](#0-3) 

The identity binding the gem is supposed to provide is effectively:
`hmac_valid ⇒ (raw_body, shop) both authenticated by Shopify`

What is actually implemented is:
`hmac_valid ⇒ raw_body authenticated by Shopify` (shop is unauthenticated, attacker-controlled metadata)

Because the `shop-domain` header is attacker-controlled input on an inbound HTTP request and is not part of the signed material, any request with a *previously-observed valid* `(raw_body, hmac)` pair can be replayed with the `shop-domain` header swapped to a different (victim) shop, and `Registry.process` will accept it and dispatch it to the handler as if it came from the victim tenant.

An unprivileged internet user can obtain a valid `(raw_body, hmac)` pair without any secret knowledge simply by being a legitimate, unprivileged merchant on their own store: they install the target app (or trigger any subscribed webhook topic, e.g. `app/uninstalled`, `shop/update`, or any topic whose payload is not shop-specific/small), capture the genuinely-Shopify-signed webhook delivered to the app's endpoint for their own store, and then re-POST that exact `raw_body`+`hmac` to the same endpoint while substituting the `shop-domain` header for a victim shop.

### Impact Explanation
Any host application that relies on the documented `ShopifyAPI::Webhooks::Registry.process` contract and uses `WebhookMetadata#shop` (the only tenant identifier this gem exposes for a webhook) to select the merchant/session context for the operation — is exposed to cross-tenant action: an attacker-controlled webhook payload (from their own shop) gets attributed to and processed under a different shop's identity. Depending on the topic, this can trigger tenant-scoped side effects (e.g., data deletion flows on `shop/redact` or `app/uninstalled` handling, cache/session invalidation, or business logic keyed by `shop`) against a shop the attacker does not control — a cross-tenant access impact.

### Likelihood Explanation
The attacker needs no credentials, no `api_secret_key`, and no access token: only the ability to be an ordinary installer of the target app on their own store (or otherwise trigger a subscribed webhook topic) to harvest one valid `(raw_body, hmac)` pair, plus the ability to send an arbitrary HTTP request to the app's public webhook endpoint with a forged `shop-domain` header. Both are available to any unprivileged internet user; the header-substitution is a header-only tamper, not a signature forgery.

### Recommendation
Include the shop domain (and ideally the webhook topic/API version) in the material that is HMAC-verified, or independently bind `shop` to the caller by re-deriving it from a value that is itself covered by the signature (e.g., by having the `to_signable_string` method incorporate the shop header, similar to how `AuthQuery#to_signable_string` binds `shop`, `code`, `host`, `state`, and `timestamp`). At minimum, document and enforce that `WebhookMetadata#shop` must not be treated as an authenticated tenant identifier unless verified against known registered shops via a corroborating source (e.g., cross-check against a stored session for that shop before trusting the header).

### Proof of Concept
1. App subscribes to a webhook topic with an attacker-controllable/observable body, e.g. `app/uninstalled`.
2. Attacker installs the target app on their own store `attacker-shop.myshopify.com`, then uninstalls it, triggering Shopify to POST a legitimately HMAC-signed webhook to the app's endpoint:
   ```
   POST /webhook
   x-shopify-topic: app/uninstalled
   x-shopify-hmac-sha256: <valid_hmac_for_body>
   x-shopify-shop-domain: attacker-shop.myshopify.com
   Body: {...}
   ```
3. Attacker captures this exact `Body` and `x-shopify-hmac-sha256` value (both are visible to them, since they control the receiving endpoint or a proxy in front of it, or simply reuse the request from their own app's logs if they run the app themselves for testing).
4. Attacker replays the identical request to the same public endpoint, changing only the shop header:
   ```
   POST /webhook
   x-shopify-topic: app/uninstalled
   x-shopify-hmac-sha256: <same_valid_hmac_for_body>
   x-shopify-shop-domain: victim-shop.myshopify.com
   Body: {...}   (byte-identical)
   ```
5. `Utils::HmacValidator.validate` recomputes the HMAC over `@raw_body` only, matches the attacker-supplied hash, and passes.
6. `Registry.process` dispatches to the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, causing the app to execute uninstall/cleanup logic for the victim's tenant triggered entirely by the attacker.
