## Title
Postponed action receipts with unmet `input_data_ids` accumulate in state indefinitely, unmetered by storage staking - (File: `runtime/runtime/src/lib.rs`)

## Summary
`Runtime::process_action_receipt` stores a `PostponedReceiptId`, `PendingDataCount`, and `PostponedReceipt` trie entry for every action receipt whose `input_data_ids` are not yet satisfied, but never charges the receiver account's `storage_usage()` for these entries and never times them out. Unlike `PromiseYield`, which has an explicit timeout queue (`PromiseYieldTimeout`/`resolve_promise_yield_timeouts`), ordinary cross-contract callback receipts postponed on missing `DataReceipt`s have no expiry mechanism, so a data producer that never returns leaves the postponed state permanently.

## Finding Description
In `process_action_receipt` (`runtime/runtime/src/lib.rs:1593-1658`), for each `data_id` in `action_receipt.input_data_ids()` not already satisfied (`has_received_data`), the runtime writes a `TrieKey::PostponedReceiptId` entry [1](#0-0) . If any are missing, it writes `TrieKey::PendingDataCount` and calls `set_postponed_receipt` to persist the full receipt under `TrieKey::PostponedReceipt` [2](#0-1) . These three trie keys (`PostponedReceiptId`, `PendingDataCount`, `PostponedReceipt`) are keyed by the receiver's `AccountId` [3](#0-2) .

There is no code path in `process_action_receipt`, `apply_action_receipt`, or anywhere else found in the codebase that increments `account.storage_usage()` (via `set_storage_usage`) to account for these postponed-receipt trie entries — contrast this with `add_gas_key`, `deploy_deterministic_account`, and `ContractData` writes, which explicitly call `account.set_storage_usage(...)` after every write [4](#0-3) [5](#0-4) . The genesis `StorageComputer` even explicitly documents that postponed receipts are excluded from per-account storage accounting: `StateRecord::PostponedReceipt(_) => None` [6](#0-5) . `check_storage_stake` (`runtime/runtime/src/verifier.rs:48` per spec docs) only validates `account.storage_usage()`, which never reflects these bytes, so `LackBalanceForState` can never be triggered by postponed-receipt growth [7](#0-6) .

By contrast, the `PromiseYield`/`PromiseResume` mechanism has an explicit, bounded lifecycle: entries go into a `PromiseYieldTimeout` FIFO queue with `expires_at`, and `resolve_promise_yield_timeouts` (`lib.rs:3009`) drains and resolves/expires them every chunk regardless of whether the counterpart ever resumes [8](#0-7) . No equivalent timeout queue exists for plain postponed `ActionReceipt`s waiting on `Data` receipts from ordinary `promise.then`/`promise.and` cross-contract calls — an attacker's contract can create a callback receipt with `input_data_ids` referencing a `Data` receipt that its own logic (or a deliberately failing/deleted producer account) never emits, and the `PostponedReceiptId`/`PendingDataCount`/`PostponedReceipt` entries then persist in state forever with no consuming event ever arriving.

## Impact Explanation
This is unbounded, unmetered validator state growth: an attacker can create arbitrary numbers of postponed-receipt trie entries on their own account (or any account they control as receiver) that are never billed against `storage_usage`/`check_storage_stake`, and never expire. Every validator/chunk producer must retain and process this account's state indefinitely, which grows disk/trie footprint and future receipt-processing overhead for the shard without the attacker ever paying storage rent for it. This matches the NEP-448-style storage-staking/metering-bypass and "unbounded resource use" bounty impact class rather than fund loss, since no tokens change hands incorrectly.

## Likelihood Explanation
Feasibility is limited by the ordinary gas/fee costs of creating cross-contract-call receipts: each postponed receipt requires the attacker to pay send/exec fees for both the "producer" promise and the "consumer" callback promise (bounded by `max_number_input_data_dependencies`/receipt size limits per transaction/receipt). So the attack is throttled by gas price/limits per block, not free, but the *storage* portion is genuinely free — the attacker does not need to hold NEAR balance proportional to the number of postponed entries they accumulate over many blocks/epochs, unlike ordinary contract storage which requires locked balance under `check_storage_stake`. Given enough transactions over time (an ordinary, unprivileged attacker with only gas to spend, no validator/node access needed), state bloat is achievable and cumulative, with no GC path found in the codebase for postponed receipts (only `ReceiptToTx`/outcome-related GC and `PromiseYieldTimeout` GC were found for other receipt kinds).

## Recommendation
Charge `account.storage_usage()` for the byte size of `PostponedReceiptId`, `PendingDataCount`, and the serialized `PostponedReceipt` when they are written in `process_action_receipt`, and release that usage when the receipt is resolved in `process_receipt` (the `Data` arm). This forces `check_storage_stake`/`LackBalanceForState` to apply, making unresolved postponed receipts subject to normal storage-rent economics. Alternatively (or additionally), introduce a bounded timeout/expiry queue for postponed action receipts analogous to `PromiseYieldTimeout`, so entries whose data never arrives are eventually purged and a refund/failure outcome is produced.

## Proof of Concept
Unit/integration test plan (in `runtime/runtime/src/tests/apply.rs` style):
1. Deploy a test contract on account `A` with a method that issues N independent cross-contract calls to itself (`promise_batch_create` + `promise_then`/`promise_and`) whose "producer" leg is designed never to emit the callback's required `Data` receipt (e.g., call a nonexistent method / an account that will be deleted, or simply never generate an output for one of `output_data_receivers`).
2. Submit and apply this receipt across several chunks; assert that `TrieKey::PostponedReceiptId`, `TrieKey::PendingDataCount`, and `TrieKey::PostponedReceipt` entries exist in state for account `A`'s receipt_id after apply, using `get`/`get_postponed_receipt`.
3. Read `account.storage_usage()` for `A` before and after the postponed receipts are created; assert it is **unchanged** despite N new trie entries — demonstrating the metering gap.
4. Repeat step 1 with N scaled up while keeping `A`'s balance fixed at the minimum required for existing storage; assert the transaction/receipt is never rejected with `LackBalanceForState` despite unbounded growth in trie entries under `A`.
5. Advance many epochs/blocks (as done in `test_promise_resume_receipt_to_tx_gc`-style GC tests) and assert the `PostponedReceiptId`/`PendingDataCount`/`PostponedReceipt` entries are *not* garbage collected, unlike `PromiseYieldTimeout`-driven `ReceiptToTx` entries which are collected in `test_promise_resume_receipt_to_tx_gc` [9](#0-8) .

Expected assertion for a fix: either `storage_usage()` grows to match the postponed-receipt bytes (enforcing `LackBalanceForState` once the attacker's balance is exhausted), or the entries are removed by a timeout mechanism after a bounded number of blocks.
