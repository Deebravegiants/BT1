### Title
Missing duplicate-input-token rejection in `IntentGatewayV2.placeOrder` (Tron) reintroduces the "over-release escrow" bug already fixed on EVM - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The CVE-2023-51384 bug class is "a constraint meant to apply to every item in a set is only actually applied to one occurrence, because duplicate/aliased entries collapse onto the same underlying record." The Tron deployment of Hyperbridge's intent gateway, `evm/tron/contracts/apps/IntentGatewayV2.sol`, exhibits the same class of defect: `placeOrder` never rejects duplicate `token` entries in `order.inputs`, whereas the parallel, audited EVM contract explicitly added this rejection as a regression fix for exactly the failure mode of "same-chain partial fills over-release repeated input escrow."

### Finding Description
In the current EVM contract, `evm/src/apps/IntentGatewayV2.sol`, escrow crediting in `placeOrder` is guarded per input index: [1](#0-0) 
This explicit "Reject duplicate input tokens" check exists specifically because, without it, two input legs referencing the same ERC-20 `token` collapse onto the single mapping slot `_orders[commitment][token]`, and the per-index fill/release logic in `IntrinsicIntents._fillSameChain` (`escrowedInputs[i] = ... _orders[commitment][token]`) then treats each duplicate index as an independent, fully-funded escrow bucket: [2](#0-1) 
The regression test on the EVM side names this failure precisely: "same-chain partial fills over-release repeated input escrow": [3](#0-2) 

The Tron variant of the same contract, `evm/tron/contracts/apps/IntentGatewayV2.sol`, has no equivalent guard. Its `placeOrder` credits escrow additively per index without ever checking for repeated `token` values in `order.inputs`: [4](#0-3) [5](#0-4) 
Because `_orders[commitment][token] += reducedInputs[i].amount` accumulates into one slot per token but `order.inputs` (and therefore any per-index fill/withdrawal loop that indexes by `i`, mirroring the EVM `IntrinsicIntents`/`ExtrinsicIntents` pattern) still carries two separate entries for the same token, a solver who fully fills such an order can have the fill/redeem path resolve the *same* accumulated escrow bucket twice — once for each duplicate index — releasing roughly double the actual escrowed amount for that token. This is structurally identical to the CVE's "constraint applied only to the first of several aliased items": the duplicate-rejection constraint that should apply to every input token is enforced on the EVM contract but is absent on the Tron contract, so on Tron the aliasing (two inputs → one storage slot) goes unguarded and lets escrow be double-counted.

### Impact Explanation
This is unbacked release of escrowed funds: a user or colluding solver placing an order with a duplicated input token on the Tron deployment can cause the gateway to pay out escrow twice for a single token bucket, directly draining the gateway's token balance beyond what was actually deposited for that order. This is a concrete theft/permanent-loss-of-funds vector reachable from a single `placeOrder` + `fillOrder` transaction pair by an unprivileged intent solver, matching the "concrete theft ... of funds" bar required for validity.

### Likelihood Explanation
`placeOrder` and `fillOrder` are fully permissionless, user/solver-facing entry points — no privileged role is required. Constructing an order with two `TokenInfo` entries sharing the same `token` address is a trivial client-side action; the EVM contract needed a dedicated revert and regression test to close exactly this path, indicating it was a real, exploitable defect once discovered, not a theoretical one. The Tron contract is deployed as a first-class production target of the same protocol (per the mirrored file layout and identical `Order`/`TokenInfo` structures), so the same order shape is reachable there.

### Recommendation
Port the EVM fix to `evm/tron/contracts/apps/IntentGatewayV2.sol`: reject any `order.inputs` array containing duplicate `token` values in `placeOrder`, before crediting `_orders[commitment][token]`, exactly mirroring the check at `evm/src/apps/IntentGatewayV2.sol:363-373`. Additionally, audit whatever fill/redeem logic Tron's `IntentGatewayV2.sol` uses (the file was not fully retrievable in this session) to confirm whether it indexes escrow release by input index the same way `IntrinsicIntents._fillSameChain`/`ExtrinsicIntents._fillCrossChain` do; if so, add the corresponding regression test (`testRevert_PlaceOrder_DuplicateInputTokens`) to the Tron test suite.

### Proof of Concept
1. Caller submits `placeOrder` on the Tron gateway with `order.inputs = [ {token: USDC, amount: 1000}, {token: USDC, amount: 1000} ]`.
2. `_orders[commitment][USDC]` accumulates to `2000` via the additive `+=` at `evm/tron/contracts/apps/IntentGatewayV2.sol:463` — no revert occurs because there is no duplicate-token check (contrast with `evm/src/apps/IntentGatewayV2.sol:367`, which would revert with `InvalidInput`).
3. A solver fully fills the order. If the fill/redeem path indexes escrow release by input-array position (as it does in the audited EVM `IntrinsicIntents._fillSameChain`, `evm/src/apps/intentsv2/IntrinsicIntents.sol:111-118`), the escrow release for index `0` and index `1` both resolve against the same `_orders[commitment][USDC]` slot, each independently computing a fully-filled release of the accumulated `2000` — i.e., `4000` total released for a `2000` deposit.

**Note on verification limits:** I was able to confirm the missing check in Tron's `placeOrder` and the presence (and documented regression history) of the analogous check and exploit in the EVM contract. I was not able to retrieve Tron's fill/redeem function bodies within this session to trace the exact double-release arithmetic there; if that logic differs materially from the EVM `IntrinsicIntents`/`ExtrinsicIntents` pattern, the precise over-release mechanics should be re-confirmed by reading `evm/tron/contracts/apps/IntentGatewayV2.sol` in full (it is a single-file contract without separate `Intrinsic`/`Extrinsic` inheritance).
