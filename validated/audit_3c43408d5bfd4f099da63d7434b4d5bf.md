## Title
Webhook `shop` header is not covered by the HMAC signature, breaking the (body, shop) binding used to attribute inbound webhooks - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC computed over it authenticates *the body content* but says nothing about which shop it belongs to. `ShopifyAPI::Webhooks::Registry.process` validates that HMAC and then unconditionally trusts the `shop-domain` header (parsed, unauthenticated bytes) to build the `WebhookMetadata` passed to the app's handler. This is the same identity-binding gap described in the M-15 report: a field that is acted on (`shop`) is not covered by the value that is cryptographically verified (the HMAC only binds `raw_body`).

### Finding Description
`Request#hmac` and `Request#to_signable_string` show the signable material is solely the raw body: [1](#0-0) 

`Request#shop` is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header without any cryptographic tie to the signed body: [2](#0-1) 

`HmacValidator.validate` only checks `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)` — i.e., body vs. secret, never shop vs. secret: [3](#0-2) 

`Registry.process` performs exactly that check and then forwards the unauthenticated `request.shop` straight into `WebhookMetadata`, which is the tenant identifier the host app's handler will act on: [4](#0-3) 

Because `Context.api_secret_key` is a single app-level secret shared across every shop that installs the app (not a per-shop secret), any merchant who installs the app can legitimately trigger a webhook for their own store, capture the resulting valid `(raw_body, hmac)` pair, and replay it to the app's public webhook endpoint with the `shop-domain` header rewritten to a victim shop. The gem's `process` will accept it: the HMAC check passes (same secret, same body), and `request.shop` is taken verbatim from the attacker-controlled header. The equality that should hold — `shop encoded in the HMAC-verified payload == shop attributed to the webhook by the gem` — is never enforced; the gem only enforces `hmac(raw_body) == received_hmac`.

### Impact Explanation
This is a cross-tenant identity-binding break: an unprivileged merchant (any user able to install the app on their own store) can make the app process attacker-controlled webhook content while impersonating an arbitrary target shop's identity within the app, since `WebhookMetadata#shop` — the only tenant signal the gem exposes to handler code — is fully attacker-controlled and not bound to the verified HMAC. This matches the "cross-tenant access" Critical impact category, since the gem itself provides no protection binding the delivered shop identity to the authenticated payload.

### Likelihood Explanation
Exploitation requires only: (1) the app being installed on an attacker-owned store (a standard, low-privilege step for any public Shopify app), (2) the ability to trigger a webhook topic the app subscribes to (e.g., by creating an order/product in the attacker's own store), and (3) direct HTTP access to the app's public webhook endpoint to replay the captured body+HMAC with a forged `X-Shopify-Shop-Domain` header. No access to the victim's credentials, access token, or `client_secret` is needed.

### Recommendation
Bind the shop identity into the verified material instead of trusting a separate, unsigned header: either include the shop domain in the HMAC signable string, or require callers of `Registry.process`/`Request` to cross-check `request.shop` against the shop encoded in `parsed_body` (e.g., `shop_id`/`myshopify_domain` fields present in most webhook payloads) or against a known/installed-shop allowlist before constructing `WebhookMetadata`, rejecting mismatches.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`, receiving a legitimately signed webhook: `raw_body = B`, header `x-shopify-hmac-sha256 = HMAC(secret, B)`, `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker POSTs the same `raw_body = B` and same `hmac` header to the app's public webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes HMAC over `B` and matches — validation succeeds [5](#0-4) .
4. The handler is invoked with `WebhookMetadata.new(..., shop: "victim.myshopify.com", body: <attacker-controlled parsed body>, ...)`, so the host app processes attacker-supplied data under the victim shop's identity.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
