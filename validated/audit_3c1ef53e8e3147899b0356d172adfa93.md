### Title
Webhook `shop` (and `topic`/`api-version`/`webhook-id`) headers are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` is documented as verifying "the request did indeed come from Shopify" before invoking the app's handler, and the handler is handed a `WebhookMetadata#shop` that the docs describe as "The shop domain of the webhook." In reality, the HMAC signature only binds the raw request body — it never binds the `shop`, `topic`, `webhook-id`, or `api-version` headers. Any party who can obtain one valid `(raw_body, hmac)` pair for their own shop (trivial: they own a store with the app installed and can trigger a real webhook) can replay that exact body/HMAC to the app's public webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header. The request still passes `HmacValidator.validate`, and the forged shop value is handed to the host application as authenticated fact.

### Finding Description
`Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

`HmacValidator.validate` computes/compares the HMAC exclusively over `to_signable_string`: [2](#0-1) 

`Registry.process` uses this single check as its entire authenticity gate, then forwards the unauthenticated `shop` header straight into the metadata passed to the app's handler: [3](#0-2) 

`Request#shop` is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cross-check against the HMAC or any other authenticated value: [4](#0-3) 

The gem's own documentation tells integrators that `process` "will verify the request did indeed come from Shopify" and that `data.shop` is "The shop domain of the webhook," encouraging exactly the trust that the implementation doesn't provide: [5](#0-4) [6](#0-5) 

This is the same class of bug as the referenced report: a value that is *acted upon* (here, `shop`, used by the host app to select which tenant's data to update, per the gem's own documented usage pattern `perform_later(topic:, shop_domain: data.shop, webhook: data.body)`) is not covered by the integrity check (`gracePeriod` not bumped alongside `creation`; here `shop` not bumped into the HMAC alongside the body). The binding that should hold is:
`hmac_verified(raw_body) == hmac_verified(raw_body, shop)` — but the implementation only guarantees the former while callers, per documentation, rely on the latter.

### Impact Explanation
Because `api_secret_key` is shared by the app across every merchant that installs it, any merchant/unprivileged internet user who has legitimately installed the app on their own store can capture a real `(raw_body, hmac)` pair (e.g., from an `orders/create` webhook they triggered themselves) and replay it to the app's webhook endpoint with a forged `shop` header naming a different, victim shop. The request passes signature validation and the handler receives `WebhookMetadata` claiming the (attacker-controlled) body originated from the victim shop. Any host application following the gem's documented pattern of keying business logic/state off `data.shop` (queueing jobs, updating per-tenant records, invalidating caches, etc.) will act on forged data attributed to another tenant — a cross-tenant data-integrity/confidentiality violation achieved with no access token, session, or `client_secret` knowledge.

### Likelihood Explanation
High: the attacker only needs their own working installation of the app (no elevated privilege, no leaked secrets) and the ability to POST to the app's public webhook route with custom headers — both routinely available to any merchant/unprivileged internet actor. The gem does nothing to bind `shop` to the signature, so the attack requires no cryptographic break, only a straightforward header substitution.

### Recommendation
Include the security-relevant headers (`shop`, `topic`, `webhook-id`, `api-version`) in the signable payload that `HmacValidator` verifies (e.g., by canonicalizing header+body into `to_signable_string`), or otherwise independently authenticate `shop` before it is handed to the handler (e.g., cross-referencing it against a session/shop record established during OAuth). At minimum, update the documentation to make explicit that `data.shop` is *not* cryptographically authenticated and must not be trusted for tenant-selection without additional verification.

### Proof of Concept
1. Attacker installs the app on their own store `attacker.myshopify.com` and triggers a real webhook (e.g. `orders/create`), capturing the raw POST body `B` and the valid `x-shopify-hmac-sha256` header `H` Shopify sent (HMAC of `B` under the shared `api_secret_key`).
2. Attacker POSTs to the app's public webhook endpoint with:
   - body: `B` (unchanged)
   - `x-shopify-hmac-sha256: H` (unchanged, still valid since it only signs `B`)
   - `x-shopify-shop-domain: victim-shop.myshopify.com` (forged)
   - `x-shopify-topic`, `x-shopify-webhook-id` optionally forged too
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `B` against `H`. [7](#0-6) 
4. The registered handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)` and, per the gem's documented integration pattern, performs tenant-scoped work (e.g. `perform_later(shop_domain: data.shop, webhook: data.body)`) against the victim tenant using attacker-supplied body content.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
