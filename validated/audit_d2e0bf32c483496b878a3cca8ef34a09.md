### Title
Secure-Element Signup Signature Does Not Bind `distributorId`/`region`/`reason`, Allowing Post-Signing Manipulation of Attribution Fields - (File: src/plans/enroll_user.rs)

### Summary
`make_signature()` computes a secure-element (attestation) signature over `ORB_ID`, the user QR code's `user_id`, and the iris/mask codes and versions [1](#0-0) . This signature is intended to attest that the orb performed this specific biometric capture for this specific user. However, when the signup request is submitted, several additional fields that materially affect signup attribution and processing — `distributorId` (the operator's QR-code-derived `user_id`), `region`, and `reason` (`SignupReason`) — are sent in the same multipart form but are never included in the signed digest [2](#0-1) .

### Finding Description
This mirrors the reported `hashAssignment()` issue: a cryptographic signature is supposed to secure an entire logical record, but only signs over a subset of the fields that are actually sent and acted upon. Here, `make_signature` is called once with only `user_qr_code` and `pipeline` in scope [3](#0-2) , and the resulting `signature` is then submitted together with unsigned `distributorId`, `region`, and `reason` fields [2](#0-1) . Because these fields are not part of the signed payload, an entity with access to the request path between signature computation and transmission (e.g. a compromised or manipulated `signup_post::request` call site, or any component able to influence the parameters passed into `request()`) can pair a legitimately-signed iris code/user-ID attestation with an arbitrary `distributorId` (operator attribution) or `reason` value, without invalidating the secure-element signature — because the signature never covered those fields in the first place.

### Impact Explanation
The `distributorId` field determines operator/referrer attribution for a signup; the `reason` field distinguishes `NORMAL`/`FAILURE`/`FRAUD` signups. Since neither is bound to the secure-element signature, a signed biometric attestation for a given `user_id` could be resubmitted or forwarded with a different operator attribution or a different signup reason while still presenting a valid orb-signed signature for the iris codes and `user_id`. This is a misattribution risk analogous to the metaHash issue: the signature is supposed to vouch for the full transaction/record, but a subset of security-relevant fields can be freely altered by whichever process constructs the outgoing request.

### Likelihood Explanation
The signature-construction path (`make_signature`) and the request-construction path (`signup_post::request`) are in different modules and are only loosely coupled through function parameters passed at the `Plan::run` call site [4](#0-3) ; there is no structural enforcement (e.g., via a signed struct or EIP-712-like typed hashing) that ties the signature to the exact set of fields transmitted. Exploitability depends on whether an attacker can influence the arguments to `signup_post::request` independently of what was hashed in `make_signature` — this requires either a compromised orb-core process/IPC boundary or a bug in how these plan fields are populated, which I could not fully verify from static reading alone.

### Recommendation
Include all backend-relevant, security-sensitive fields (`distributorId`, `region`, `reason`, and ideally `signup_id`) in the digest computed by `make_signature`, following the same remediation pattern as the referenced report (sign over the full logical structure, not a subset of fields) [1](#0-0) .

### Proof of Concept
1. `make_signature(&user_qr_code, &pipeline)` is computed and signs only `ORB_ID`, `user_qr_code.user_id`, and iris/mask code fields [1](#0-0) .
2. `signup_post::request()` is called with this signature plus independently-supplied `operator_qr_code` (→ `distributorId`), `s3_region`, and `signup_reason` (→ `reason`) [5](#0-4) .
3. Because `distributorId`/`region`/`reason` are not part of the SHA-256 digest passed to `secure_element::sign`, the same valid signature accompanies the request regardless of what values are placed in those fields, so the backend cannot cryptographically detect if these fields were altered relative to what the orb's secure element actually attested to.

**Caveat:** I could not fully verify from static analysis alone whether an actual attacker-controlled boundary exists between the point where `make_signature` is invoked and where `signup_post::request` is called with the (potentially different) `operator_qr_code`/`signup_reason` values — this would require tracing all call sites of `Plan::run` in `enroll_user.rs` across the full orchestration flow, which was not completely explorable within the available context.

fn make_signature(user_qr_code: &qr_scan::user::Data, pipeline: &Pipeline) -> Result<String> {
    let mut ctx = Context::new(&SHA256);
    ctx.update(ORB_ID.as_str().as_bytes());
    ctx.update(user_qr_code.user_id.as_bytes());
    ctx.update(pipeline.v2.ir_net_version.as_bytes());
    ctx.update(pipeline.v2.iris_version.as_bytes());
    ctx.update(pipeline.v2.eye_left.iris_code.as_bytes());
    ctx.update(pipeline.v2.eye_left.mask_code.as_bytes());
    ctx.update(pipeline.v2.eye_left.iris_code_version.as_bytes());
    ctx.update(pipeline.v2.eye_right.iris_code.as_bytes());
    ctx.update(pipeline.v2.eye_right.mask_code.as_bytes());
    ctx.update(pipeline.v2.eye_right.iris_code_version.as_bytes());
    let signed = secure_element::sign(ctx.finish())?;
    Ok(BASE64.encode(&signed))
