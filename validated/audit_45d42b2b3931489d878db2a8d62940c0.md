### Title
First-LP donation/inflation attack on pool creation dilutes or freezes subsequent depositors' funds - (File: `program/src/processor.rs`, `Initialize2`/`Deposit`/`Withdraw`)

### Summary
Raydium's `Initialize2` mints LP tokens based on `sqrt(coin*pc)` minus a `10^lp_decimals` "phantom" buffer, and `Deposit`/`Withdraw` compute mint/redeem ratios from **live SPL vault balances** divided by the internally tracked `amm.lp_amount`. Because the anti-inflation buffer is a function of `coin_mint.decimals` (not a fixed floor) and `market_info` is explicitly documented as "just a seed... can be any account" (no real market/liquidity validation), a pool creator who controls or picks a low/zero-decimal mint can seed a pool with a near-zero effective floor, then donate tokens directly to the vaults to skew the deposit/withdraw ratio for all later depositors — the same mechanics as the referenced ERC4626 gogopool `ggAVAX` first-depositor inflation bug (`convertToShares`/`syncRewards` donation attack).

### Finding Description
In `process_initialize2` (`program/src/processor.rs:908-929`), the initial LP amount is: [1](#0-0) 
```
let liquidity = sqrt(pc_amount * coin_amount);
let user_lp_amount = liquidity.checked_sub(10^lp_mint.decimals)...;
token_mint_to(..., user_lp_amount);
...
amm.lp_amount = liquidity;   // includes the un-minted "phantom" buffer
```
`lp_decimals` is taken from `coin_mint.decimals` [2](#0-1) . Unlike Uniswap V2's fixed `MINIMUM_LIQUIDITY = 1000`, this floor is decimals-dependent: if the coin mint has 0 or very few decimals, the anti-inflation buffer becomes 1 (or a few units), effectively defeating the mitigation. Additionally, `market_info` in `Initialize2` is documented as not needing to be a real market — "Just a seed for AMM account. Can be any account" [3](#0-2)  — so the pool creator fully controls which mints (and their decimals) are used, and can freely create a pool with negligible starting liquidity.

`process_deposit` computes the LP mint amount from the **actual vault balances** (`amm_coin_vault.amount`, `amm_pc_vault.amount`) divided by the internally tracked `amm.lp_amount`, not the true circulating LP supply proportion validated against donations: [4](#0-3) [5](#0-4) 
Because these vault-balance reads come from live SPL token account state, anyone can transfer tokens directly into `amm_coin_vault`/`amm_pc_vault` via a plain SPL `Transfer` (not going through `Deposit`), inflating `total_coin_without_take_pnl`/`total_pc_without_take_pnl` without minting any LP. This mirrors the gogopool bug's `WAVAX` donation + `syncRewards()` pattern that inflated `totalAssets()` relative to `totalSupply`.

Attack flow:
1. Attacker calls `Initialize2` with a self-created or existing 0-decimal (or low-decimal) coin mint and minimal `init_coin_amount`/`init_pc_amount` (e.g. 2/2), making `user_lp_amount = liquidity - 1 ≈ 1`. Attacker receives virtually all LP.
2. Attacker donates a large amount of coin/pc tokens directly to `amm.coin_vault`/`amm.pc_vault` via ordinary SPL transfers (no program instruction needed, vaults are normal token accounts).
3. Victim calls `Deposit`. `mint_lp_amount` is computed as `deduct_amount / total_*_without_take_pnl (inflated) * amm.lp_amount (mostly attacker-owned)` [6](#0-5) , so victim receives disproportionately few LP tokens for the value they contributed (in the worst case, rounds to 0 and reverts via `AmmError::InvalidInput` at [7](#0-6) , denying deposits entirely; in the exploitable case it mints a nonzero-but-too-small amount).
4. Attacker calls `Withdraw`, redeeming their (near-total) share of `amm.lp_amount` for a proportional slice of the now-inflated real vault balances — including the victim's freshly deposited funds — via the same `exchange_pool_to_token`-style ratio against live vault balances [8](#0-7) , extracting value the victim just contributed.

### Impact Explanation
This allows an unprivileged pool creator/attacker to either (a) steal a portion of a subsequent depositor's funds by minting themselves a disproportionate share of `amm.lp_amount` relative to true contributed value, or (b) permanently grief/freeze small deposits by forcing `mint_lp_amount == 0` reverts for any depositor whose contribution is smaller than the donation-inflated vault balance. Both are concrete fund-theft/freezing outcomes reachable from a single attacker-controlled `Initialize2` + SPL transfer + `Withdraw` sequence, satisfying High severity per the analogous gogopool finding (confirmed High, C4 #209).

### Likelihood Explanation
The attacker needs only to be the first LP provider of a brand-new pool (trivially achievable since `Initialize2` accepts arbitrary mint pairs and an arbitrary "market" seed account with no real orderbook/market validation) and to control or pick a low-decimal coin mint to minimize the `10^lp_decimals` buffer. No privileged signer, leaked key, or off-chain component is required — everything is done with a single submitted `Initialize2` transaction, plain SPL `Transfer` CPIs, and a `Deposit`/`Withdraw` pair, all reachable by any unprivileged actor.

### Recommendation
- Enforce an absolute (decimals-independent) minimum locked liquidity at `Initialize2` (e.g., require `liquidity >= FIXED_MINIMUM_LIQUIDITY` regardless of `coin_mint.decimals`), and/or require a meaningful minimum USD/absolute value of `init_coin_amount`/`init_pc_amount`.
- Track LP-supply-to-asset accounting using the actual `lp_mint.supply` compared against a protocol-tracked "last known good" balance rather than trusting live vault balances that can be inflated via bare SPL transfers; alternatively, reconcile/absorb unexpected vault balance surplus into existing LP holders proportionally only through an explicit, permissioned sync step rather than implicitly via `Deposit`/`Withdraw` ratios.
- Consider validating that pools are only created for genuine, pre-existing markets (restore real market/orderbook validation) to prevent trivial creation of pools over attacker-chosen, low-decimal mints purely to weaken the anti-inflation floor.

### Proof of Concept
```
1. Attacker mints a custom SPL token `X` with 0 decimals (or uses an existing 0-decimal mint) as coin_mint; pc_mint = USDC.
2. Attacker calls Initialize2(coin_mint=X, pc_mint=USDC, init_coin_amount=2, init_pc_amount=2, market=<arbitrary account>).
   -> liquidity = sqrt(2*2) = 2
   -> user_lp_amount = 2 - 10^0 = 1   (attacker receives 1 LP, amm.lp_amount = 2)
3. Attacker SPL-transfers 1,000,000 X and 1,000,000 USDC directly into amm.coin_vault / amm.pc_vault
   (no Deposit instruction call — plain token::transfer CPI to the vault addresses).
4. Victim calls Deposit(max_coin_amount=2000 X, max_pc_amount=2000 USDC, base_side=0).
   -> total_coin_without_take_pnl ≈ 1,000,002 (inflated by donation)
   -> mint_lp_amount = deduct_coin_amount * amm.lp_amount / total_coin_without_take_pnl
                     ≈ 2000 * 2 / 1,000,002 ≈ 0  -> reverts with AmmError::InvalidInput (deposit griefed)
   OR, with larger victim deposit, mint_lp_amount rounds to a tiny nonzero value versus the true value deposited.
5. Attacker calls Withdraw with their 1 LP token (near 100% of amm.lp_amount if victim's deposit failed,
   or a large majority otherwise), redeeming a share of total_coin_without_take_pnl / total_pc_without_take_pnl
   that now includes the victim's contributed/attempted funds, extracting value disproportionate to their
   original 2+2 deposit and donation cost recovery.
```
