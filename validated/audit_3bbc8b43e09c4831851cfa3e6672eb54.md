Webhook `shop`, `topic`, and `webhook_id` fields are trusted from unauthenticated headers while HMAC only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw JSON body, then dispatches to the app's handler using `shop`, `topic`, `webhook_id`, and `api_version` values pulled straight from HTTP headers that are never included in that HMAC computation. This breaks the identity binding the DKG-style analog targets: the equality "bytes verified by HMAC == bytes acted on by the handler" does not hold, because `shop`/`topic`/`webhook_id` are acted on but not covered.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all read from HTTP headers with no cryptographic linkage to the body or the HMAC: [2](#0-1) 

`HmacValidator.validate` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it to the `hmac` header - i.e., it only proves the body bytes are untampered, never the header bytes: [3](#0-2) 

`Registry.process` uses this weak guarantee to build a `WebhookMetadata` object whose `shop`/`topic`/`webhook_id` are the unauthenticated header values, and hands it directly to the app-registered handler: [4](#0-3) 

The handler contract (`WebhookHandler#handle`) receives this `WebhookMetadata` and is expected to trust `data.shop` as the tenant identity for the webhook: [5](#0-4) 

This is exactly the DKGResultVerification bug class: the report flagged that `keccak256(abi.encodePacked(groupPubKey, misbehaved))` let an attacker move bytes between two logically distinct fields without either field's boundary being authenticated. Here, the analogous broken equality is:

`shop_authenticated_by_hmac == shop_used_by_handler`

This equality is false: the HMAC authenticates zero bytes of `shop` (or `topic`/`webhook_id`), yet the handler uses `data.shop` as if it were Shopify-attested.

### Impact Explanation
Any request bearing a valid `(raw_body, hmac)` pair — which an attacker can obtain simply by capturing one real webhook delivery (e.g., to their own dev/trial store, which anyone can create for free) — can be replayed to the app's webhook endpoint with an arbitrary attacker-chosen `X-Shopify-Shop-Domain` (and `topic`/`webhook-id`) header. `HmacValidator.validate` will accept it because it never examines the header. The gem then calls the app's handler with `WebhookMetadata#shop` set to the attacker's chosen value, while `body` is the replayed content. Any host app that uses `data.shop` to key session/tenant lookups (a common and gem-encouraged pattern, since `WebhookMetadata#shop` is the field explicitly provided for that purpose) will process/store attacker-influenced data under an arbitrary tenant identity, or use it to look up or mutate another shop's stored session/access token — i.e., cross-tenant access facilitated by data this gem asserts as authenticated but is not.

### Likelihood Explanation
Exploitation requires no privileged credentials: any actor who can install/trial a Shopify app (trivial, free) can capture one legitimate webhook body+HMAC pair from their own store and replay it against the app's public webhook endpoint with modified headers. The gem performs no header-integrity check, so likelihood is high for any app that (reasonably, given the API surface) trusts `WebhookMetadata#shop`/`topic` without independent verification.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the HMAC-signed payload (or otherwise cryptographically bind them, e.g. `HMAC(secret, shop || "\0" || topic || "\0" || webhook_id || "\0" || raw_body)` with explicit length-prefixed/salted separators to avoid the same "move bytes between fields" ambiguity called out in the original report), and reject the webhook if the computed HMAC does not match. At minimum, document loudly that `WebhookMetadata#shop`/`topic` are unauthenticated and must not be trusted for tenant-identity decisions.

### Proof of Concept
1. Install the target app on an attacker-controlled trial shop `attacker.myshopify.com`; trigger any subscribed webhook topic (e.g. `orders/create`) to capture a legitimate `(raw_body, X-Shopify-Hmac-Sha256)` pair.
2. Replay this exact `raw_body` and `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, but set `X-Shopify-Shop-Domain: victim.myshopify.com` (a shop the attacker does not control) and keep/alter `X-Shopify-Topic`/`X-Shopify-Webhook-Id` as desired.
3. `Utils::HmacValidator.validate` in [6](#0-5)  succeeds because it only checks `raw_body` against the HMAC.
4. `Registry.process` in [4](#0-3)  invokes the app handler with `WebhookMetadata(shop: "victim.myshopify.com", body: <attacker's captured body>, ...)`, letting the attacker inject data attributed to a victim shop.
