Audit Report

## Title
Improper Wildcard CORS Origin Validation Allows Origin Allowlist Bypass - (File: core/services/gateway/network/httpserver.go)

## Summary
The Gateway's `isAllowedOrigin` function validates `Origin` headers against wildcard `CORSAllowedOrigins` entries (e.g. `*.example.com`) using a raw `strings.HasSuffix` check without requiring a `.` label boundary. This lets an attacker whose hostname merely ends with the allowed suffix (e.g. `evilexample.com` matching `*.example.com`) be treated as an allowed origin, resulting in the gateway echoing that attacker origin into `Access-Control-Allow-Origin`.

## Finding Description
In `isAllowedOrigin` [1](#0-0) , when an allowed entry starts with `*.`, the code strips the prefix and does `strings.HasSuffix(originHost, allowedHost)` with no check that the preceding character is a `.`. This means `originHost = "evilexample.com"` satisfies `strings.HasSuffix("evilexample.com", "example.com")` even though it is not a subdomain of `example.com`.

This function is called directly from `handleRequest` [2](#0-1) , which is the unauthenticated HTTP handler registered for the gateway's public API path and invoked for every incoming request when `CORSEnabled` is true. There is no other validation layer (auth middleware, role check, or origin normalization) that would catch this before the header is set, so the flawed suffix check is the sole gate on `Access-Control-Allow-Origin`.

## Impact Explanation
This is a concrete CORS allowlist bypass on the gateway's internet-facing HTTP entrypoint. An operator using the documented wildcard pattern for `CORSAllowedOrigins` unintentionally grants browser read-access to any origin sharing the suffix, not just genuine subdomains, which maps to the in-scope "allowlist bypass" impact category. This allows cross-origin reads of gateway JSON-RPC responses by domains never intended to be trusted.

## Likelihood Explanation
Exploitation requires only: (1) an operator using the wildcard CORS feature (a supported, documented configuration), and (2) an attacker registering a cheap domain with the matching suffix and getting a victim's browser to make a CORS request. No privileged access, credentials, or code changes are needed; the bug is always active whenever `CORSEnabled` is true and a wildcard entry exists.

## Recommendation
Modify `isAllowedOrigin` to require an explicit dot boundary before the suffix, e.g., match only when `originHost == allowedHost` or `strings.HasSuffix(originHost, "."+allowedHost)`, so `evilexample.com` no longer matches `*.example.com`.

## Proof of Concept
1. Configure `CORSEnabled = true` and `CORSAllowedOrigins = ["https://*.example.com"]`.
2. Send an HTTP request to the gateway's configured `Path` with header `Origin: https://evilexample.com`.
3. Observe `isAllowedOrigin` computes `allowedHost = "example.com"` and `strings.HasSuffix("evilexample.com", "example.com")` returns `true`.
4. Observe the response includes `Access-Control-Allow-Origin: https://evilexample.com`, confirming the bypass. This can be codified as a Go unit test directly calling `isAllowedOrigin("https://evilexample.com")` against a server configured with `CORSAllowedOrigins: []string{"https://*.example.com"}` and asserting it returns `true`.
