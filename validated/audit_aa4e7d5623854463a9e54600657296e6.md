### Title
Attacker-controlled swap-route code can drain caller wallet tokens through a poisoned authorization tree - (`contracts/controller/src/strategies/swap.rs`)

### Summary
High severity: a malicious contract embedded in a strategy route executes during `swap_collateral`, `swap_debt`, `multiply`, or `repay_debt_with_collateral` and can add arbitrary caller-authorized token transfers beneath the signed invocation tree. [1](#0-0) 

### Finding Description
Controller strategy entrypoints accept opaque `swap` bytes and forward them to the configured router; for example, `swap_collateral` authorizes the caller and delegates route execution to `withdraw_and_swap_from_supply`. [2](#0-1) 

`swap_tokens` grants only one exact controller-to-router input transfer, but it then invokes `router.execute_strategy(controller, amount_in, swap)` and afterward verifies only controller input/output deltas. [3](#0-2) 

The routed payload can name third-party pool and token contracts without an allowlist, so arbitrary route code runs below the caller’s authorization context. [4](#0-3) 

If that code calls `token.transfer(caller, attacker, amount)`, transaction simulation records the transfer as a child authorization under the caller’s strategy entry; once the caller signs that tree, the transfer executes even though the controller’s router grant itself remains narrowly scoped. [5](#0-4) [6](#0-5) 

### Impact Explanation
The attacker can steal tokens held directly in the victim’s wallet, including assets that were never supplied to or listed by the lending protocol. [7](#0-6) [8](#0-7) 

The malicious route can still provide a legitimate positive output, allowing controller output measurement and final account-risk checks to pass after the unrelated wallet transfer. [9](#0-8) [10](#0-9) 

### Likelihood Explanation
Exploitation requires persuading a position owner or delegate to submit an attacker-crafted route and sign the poisoned authorization tree, but the route is opaque bytes and the recorded child transfer need not be intelligible to a client that only validates the requested strategy and expected output. [11](#0-10) 

The same exposure applies to every strategy path that reaches `swap_tokens`, including `swap_collateral`, `swap_debt`, `multiply`, and collateral-funded debt repayment. [12](#0-11) [13](#0-12) [14](#0-13) 

### Recommendation
Restrict router payload execution to allowlisted pool and token contracts, or otherwise make route venues and token addresses protocol-validated rather than arbitrary payload addresses. [15](#0-14) 

Until contract-level route validation exists, clients must decode the complete simulated authorization tree and reject any invocation containing children other than the exact expected controller input transfer. [11](#0-10) 

### Proof of Concept
A test fixture demonstrates the complete behavior: a payload-selected `RogueHopPool` invokes `token.transfer(victim, attacker, wallet_balance)` during `execute_strategy`. [16](#0-15) [5](#0-4) 

```rust
// Victim submits attacker-crafted `route` bytes through:
swap_collateral(
    caller = victim,
    account_id = victim_account,
    current = usdc_hub_asset,
    amount = 50_000_000_000,
    new = eth_hub_asset,
    swap = route,
);

// Inside the route, the payload-selected pool executes:
token::Client::new(&env, &victim_wallet_token).transfer(
    &victim,
    &attacker,
    &victim_wallet_balance,
);
```

The test shows that the unauthorized transfer fails under an honest root-only tree, while signing the simulation-produced tree containing the extra token transfer causes the victim’s full unrelated wallet balance to move to the attacker. [17](#0-16) [6](#0-5)

That bound covers the controller's own grant only. The router calls the pool
