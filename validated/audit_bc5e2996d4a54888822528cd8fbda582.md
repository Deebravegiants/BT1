### Title
Untrusted flash receiver can convert caller authorization into unrelated token transfers - ([File: contracts/pool/src/ops/flash.rs])

### Summary
`flash_loan` lets the caller select an arbitrary Wasm receiver, and the pool invokes that receiver while the caller’s top-level authorization is still active. [1](#0-0) [2](#0-1)  A malicious callback can therefore request an unrelated token transfer from the initiator; simulation records it as a child of the caller’s signed `flash_loan` authorization, and the transfer executes if that tree is signed. [3](#0-2) [4](#0-3) 

### Finding Description
The controller authenticates `caller`, verifies only that `receiver` is a Wasm contract, and forwards the caller-selected receiver and data to the pool. [5](#0-4) [6](#0-5)  The pool pays the loan principal to that receiver and invokes `execute_flash_loan`, passing the original caller as `initiator`. [7](#0-6) [8](#0-7)  Because the callback receives no authorization boundary, nested code can call a victim token’s `transfer(initiator, attacker, amount)`, causing Soroban to record that call beneath the initiator’s top-level authorization. [9](#0-8) [10](#0-9)  After the callback, the pool verifies only its own balance and repayment allowance; it does not constrain unrelated token movements performed under the caller’s authorization. [11](#0-10) [12](#0-11) 

### Impact Explanation
An attacker can steal arbitrary tokens held by the victim, including assets that are not listed or otherwise involved in the flash-loan market. [13](#0-12)  The protocol’s balance checks still pass because the receiver can approve repayment of principal plus fee from its own contract balance while the unrelated victim-token transfer goes to the attacker. [14](#0-13) [12](#0-11) 

### Likelihood Explanation
The attacker must convince a victim to invoke `flash_loan` with the malicious receiver and sign the simulated authorization tree containing the extra token transfer. [15](#0-14) [16](#0-15)  This is a phishing-style precondition, so the issue is best rated Medium rather than Critical or High. [17](#0-16) 

### Recommendation
Restrict `flash_loan` receivers to governance-approved contracts or Wasm hashes if arbitrary callbacks are not required. [18](#0-17)  If arbitrary receivers must remain supported, clients should require the `flash_loan` authorization root to contain no sub-invocations, because a normal receiver spends only its own contract balance and does not need caller-authorized child calls. [19](#0-18) [20](#0-19) 

### Proof of Concept
1. Attacker deploys a Wasm receiver whose `execute_flash_loan` calls `victim_token.transfer(initiator, attacker, stolen_amount)` and then approves the pool for `amount + fee`. [21](#0-20) [12](#0-11) 
2. The victim calls `Controller::flash_loan(caller = victim, asset, amount, receiver = attacker_contract, data)`, with `data` selecting the token to steal and the attacker’s payout address. [22](#0-21) 
3. Simulation records the unrelated victim-token transfer beneath the victim’s `flash_loan` authorization, and the victim signs the returned tree. [23](#0-22) 
4. The pool sends `amount` to the receiver, the callback steals `victim_token`, and the receiver approves the loan repayment. [24](#0-23) 
5. The pool pulls `amount + fee`, finalizes the flash loan, and the attacker retains the unrelated stolen tokens. [14](#0-13) [12](#0-11)

**File:** docs/explanation/threat-model.md (L154-164)
```markdown
That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap
```
