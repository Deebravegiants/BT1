### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC of the *raw body*, but the `shop` value used to attribute the webhook to a tenant is read from an HTTP header that is never included in the signed material. An unprivileged user who owns any Shopify store connected to the app can capture a genuine, validly-signed webhook for their own shop and replay it with a forged `shop-domain`/`x-shopify-shop-domain` header pointing at a victim shop, and the gem will accept it as authentic and hand it to the app's handler under the victim's identity.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor is derived independently from a header that is not part of that signable string: [2](#0-1) 

`Registry.process` validates the request using only `Utils::HmacValidator.validate(request)`, i.e. only the body/HMAC pairing, and then immediately trusts `request.shop` to build the metadata passed to the app's handler: [3](#0-2) 

`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (the raw body for webhooks) and the app's shared `api_secret_key`: [4](#0-3) 

Because Shopify signs webhook payloads with the app's single `client_secret`/`api_secret_key` (not a per-shop secret), the HMAC only proves "this body was produced by Shopify for this app," not "this body came from shop X." The `shop-domain` header — the only field that binds the payload to a specific tenant — is excluded from the signed string. This breaks the intended identity binding: `shop header used for attribution == shop that produced the signed body`. The equality does not hold, since the header can be freely substituted without invalidating the HMAC.

The documented processing flow confirms the host app is expected to trust `data.shop` from `WebhookMetadata` as the tenant identifier without independent verification: [5](#0-4) [6](#0-5) 

### Impact Explanation
This is a cross-tenant identity confusion: an attacker who legitimately controls a single installed shop (an "unprivileged" tenant relative to other merchants using the same app) can trigger real webhooks on their own store (e.g. `orders/create`), capture the raw body + valid HMAC, then send a forged HTTP request to the app's webhook endpoint with the same body/HMAC but a victim shop's `shop-domain` header. `Registry.process` will accept it as valid and invoke the app's handler with `WebhookMetadata#shop` set to the victim's domain, causing the host application to process attacker-controlled data as if it originated from the victim shop. Depending on how the host app uses `data.shop` (e.g., to look up and update per-shop records, queue per-tenant jobs, or attribute financial/order data), this can lead to cross-tenant data corruption or injection of attacker-controlled content into another merchant's tenant space — meeting the "cross-tenant access" criterion for a Critical-impact finding.

### Likelihood Explanation
Likelihood is moderate to high in gems that follow the documented usage exactly (as shown in `docs/usage/webhooks.md`): the webhook endpoint is a public, unauthenticated HTTP endpoint by design (Shopify calls it without any session), and the attacker needs no privileged credentials — only the ability to install the app on a store they control (a normal, permissionless action) and to observe/replay one of their own valid webhook deliveries.

### Recommendation
Include the tenant-identifying header (`shop-domain`) in the HMAC-signed material, or otherwise cryptographically bind the shop domain to the payload before validation — for example, incorporate `shop` into `to_signable_string`, or additionally verify that a shop-specific secret/session (obtained via OAuth for that shop) matches the shop asserted in the header. At minimum, document that host applications must independently corroborate `data.shop` against a shop they have an active, verified session/webhook registration for before trusting it.

### Proof of Concept
1. Attacker installs the app on their own store `attacker.myshopify.com` and lets it register for `orders/create` webhooks (a normal, permissionless action).
2. Attacker creates an order on their own store, triggering Shopify to POST a genuine webhook with a valid `X-Shopify-Hmac-Sha256` computed over the raw JSON body using the app's `api_secret_key`, plus header `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. Attacker intercepts this request (e.g., via their own reverse proxy/logging in front of the app) and replays it to the app's public webhook endpoint, but with the header rewritten to `X-Shopify-Shop-Domain: victim.myshopify.com`, keeping the raw body and `X-Shopify-Hmac-Sha256` unchanged.
4. In `ShopifyAPI::Webhooks::Request.new`, `shop` is parsed from the (forged) header; in `Registry.process`, `Utils::HmacValidator.validate(request)` succeeds because it only checks the raw body against the HMAC — the shop header was never part of the signed content: [7](#0-6) 
5. The app's handler is invoked with `WebhookMetadata#shop == "victim.myshopify.com"` even though the payload actually originated from `attacker.myshopify.com`, demonstrating the identity-binding break.

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
