### Title
Webhook `shop` header is not covered by the Shopify HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes and verifies the webhook HMAC over the raw request body only, while the `shop` (and `topic`/`webhook-id`/`api-version`) values are taken from unauthenticated HTTP headers and are never included in the signed payload. `Registry.process` accepts any request whose body/HMAC pair is valid and forwards the header-derived `shop` value to the app's webhook handler as trusted tenant identity, breaking the binding between "HMAC-authenticated bytes" and "shop the handler believes the event is from."

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from the `x-shopify-shop-domain`/`shopify-shop-domain` header with no cryptographic binding to the body or the HMAC: [2](#0-1) 

`HmacValidator.validate` only verifies `verifiable_query.to_signable_string` (i.e., the raw body) against the HMAC secret, so the `shop` header is completely outside the scope of what is cryptographically authenticated: [3](#0-2) 

`Registry.process` validates the HMAC (over body only) and then builds `WebhookMetadata` using the unauthenticated `request.shop`, handing it to the app-provided handler as the identity of the tenant the event pertains to: [4](#0-3) 

Because the app's `client_secret` (used as the webhook HMAC key) is shared across every shop that has the app installed, any merchant who has legitimately installed the app can capture a genuine `(body, hmac)` pair from a webhook Shopify delivers to their own shop. That merchant can then replay the identical body and HMAC to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` still succeeds (it never inspected the shop header), and `Registry.process` dispatches the event to the handler labeled with the victim's shop. This is the "field acted upon but not covered by the HMAC" identity-binding break: the equality the code should enforce — `shop-in-signed-payload == shop-acted-upon` — is never checked; only `hmac(body) == signature` is checked, and `shop` is disjoint from `body`.

### Impact Explanation
Any app built on this gem that uses `WebhookMetadata#shop` to key persistence, trigger tenant-scoped side effects, or select which merchant's session/store to act on (a standard, documented usage pattern, e.g. `data.shop` in this library's own tests) is exposed to cross-tenant event injection: an unprivileged but legitimately-onboarded merchant can cause the app to process attacker-chosen webhook bodies attributed to a different merchant's shop. This matches the "cross-tenant access" Critical/High impact bucket, since it lets one tenant force the app to act as if an event occurred for another tenant it does not control, without needing the app's `client_secret`, an access token, or any credential belonging to the victim.

### Likelihood Explanation
Exploitation only requires: (1) the attacker's own legitimate installation of the target app on any shop (a normal, unprivileged action), (2) capturing one webhook body/HMAC pair Shopify already delivers to them, and (3) POSTing that body to the app's public webhook endpoint with a forged `shop-domain` header. No secret material, elevated privileges, or Shopify-side compromise is needed, making this practically reachable by any external actor who can install the target app for free (dev store).

### Recommendation
Include the shop domain (and ideally topic/webhook-id) as part of the signed material verified against the header value, or otherwise cryptographically bind the `shop` header to the payload before trusting it (e.g., verify the header-provided shop against a shop-specific value embedded in and covered by the signed body, or require the caller to separately validate the shop against a maintained list of shops that have the webhook topic registered before invoking the handler).

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`.
2. Shopify sends attacker a webhook, e.g. body `{"id":123}"` with header `x-shopify-hmac-sha256: <valid HMAC>` and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker replays the exact same body and HMAC header to the app's public webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `OpenSSL::HMAC.hexdigest(..., "{\"id\":123}")` against the header HMAC — see `lib/shopify_api/webhooks/request.rb` lines 10-38 and `lib/shopify_api/utils/hmac_validator.rb` lines 26-31.
5. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` (`lib/shopify_api/webhooks/registry.rb` lines 198-199) and processes the attacker's payload as if it came from the victim shop.
