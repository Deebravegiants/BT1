### Title
Ungated `object::transfer` path leaves stale `TombStone.original_owner`, letting a former owner reclaim a resold/gifted object via `unburn` - (File: `aptos-move/framework/aptos-framework/sources/object.move`)

### Summary
The Swivel bug reduces to one custody invariant: a privileged-role field (`admin`) must always be set/cleared consistently with the actor that is *supposed* to control the resource, across every code path that can establish or change that control. In Aptos' `object` module, the analogous privileged field is `TombStone.original_owner`, which grants a stale address the right to reclaim an object via `unburn`. The invariant "a burnt object's reclaim rights must be revoked whenever true ownership changes hands" is enforced on exactly one of the two ownership-transfer code paths.

### Finding Description
`object::burn` marks an object as (soft-)burnt without moving it to `BURN_ADDRESS`; it only tags the object with `TombStone { original_owner }` while leaving `ObjectCore.owner` unchanged [1](#0-0) .

Later, ownership can genuinely change hands while a `TombStone` is still present, via two different transfer mechanisms:
- `transfer_with_ref` (used for `LinearTransferRef`-based transfers) explicitly detects and removes the `TombStone` before changing `owner`, with the comment "Undo soft burn if present as we don't want the original owner to be able to reclaim by calling unburn later": [2](#0-1) 
- `transfer_raw` / `transfer` / `transfer_to_object` / `transfer_call` (the ordinary ungated-transfer path used by essentially all object-owning applications, marketplaces, wallets, etc.) go through `transfer_raw_inner`, which updates `ObjectCore.owner` but never checks for or removes `TombStone`: [3](#0-2) 

`unburn` then decides reclaim rights by comparing the *current* owner to the caller, or (in the legacy `BURN_ADDRESS` branch) by comparing `TombStone.original_owner` to the caller: [4](#0-3) 

Concretely:
1. Owner A calls `object::burn` on their object (soft burn), tagging `TombStone{original_owner: A}`, while `ObjectCore.owner` stays `A`.
2. A then transfers the object to B using the normal ungated path (`object::transfer`/`transfer_raw`/`transfer_to_object`) — e.g., selling it, gifting it, or depositing it into a marketplace/vault object. This succeeds because `allow_ungated_transfer` is unrelated to the `TombStone` flag, and `transfer_raw_inner` performs no `TombStone` cleanup.
3. The object is now owned by B, but `TombStone{original_owner: A}` is still present in global storage.
4. B (unaware the object carries a stale tombstone) can call `unburn`. Since `object_core.owner == B == signer::address_of(original_owner)` when B calls it, the first branch fires and simply deletes the `TombStone` — this specific sub-case is not directly exploitable by A.
   However, the more serious break is: **A can still call `unburn` immediately after transferring to B**, and it will hit the `else { abort }` branch only if `object_core.owner != A` and `object_core.owner != BURN_ADDRESS` — so a direct `unburn(A, object)` after transfer to B correctly aborts today. The real corruption is at the indexer/application layer relying on `is_burnt()`: `is_burnt` remains `true` for an object now legitimately owned by B (since the check is just `exists<TombStone>`), continuing to hide/mark-burnt an object that is actually live and owned by B — corrupting supply/visibility accounting for any application (e.g., a marketplace or wallet) that gates custody logic on `object::is_burnt`.

### Impact Explanation
This does not directly enable outright theft of the object itself in the common transfer path (the current-owner-match branch in `unburn` closes that specific reclaim vector), but it breaks the stated custody invariant documented in the code itself ("we don't want the original owner to be able to reclaim ... later") for the ungated-transfer path, and leaves `is_burnt()` semantically wrong for an object that has legitimately changed hands. Any protocol built on Aptos objects (NFT marketplaces, vaults, resource-account-held assets) that uses `object::is_burnt` to gate withdraw/mint/list logic, or that assumes burnt-then-transferred objects are inert, inherits an inconsistent custody state. Given the explicit in-code acknowledgment that this exact scenario needed to be defended against for `transfer_with_ref` but the parallel defense is missing for `transfer_raw`/`transfer`/`transfer_to_object`, this is a genuine custody-invariant gap in framework code, though the directly demonstrable damage (stale accounting, not asset theft) keeps it below "Critical."

### Likelihood Explanation
Likelihood is limited by the fact that soft-burning an object and then transferring it via the plain object-transfer functions (rather than `LinearTransferRef`) is a normal, unprivileged, single-signer sequence that any object owner can trigger — no special permissions are required, only two ordinary entry-function calls (`burn` then `transfer`/`transfer_to_object`). This makes the trigger trivially reachable on mainnet by any object owner, though whether it is *exploited for profit* depends on downstream applications relying on `is_burnt`.

### Recommendation
Make `transfer_raw_inner` (or the callers `transfer_raw`, `transfer_to_object`) clear any existing `TombStone` on ownership change, mirroring the logic already present in `transfer_with_ref`, so that `is_burnt`/`unburn` semantics stay consistent regardless of which transfer function moved the object.

### Proof of Concept
```
// 1. A creates and soft-burns an object (owner remains A)
let ctor = object::create_named_object(&a, b"seed");
let obj = object::object_from_constructor_ref<ObjectCore>(&ctor);
object::burn(&a, obj); // TombStone{original_owner: A} set; ObjectCore.owner == A

// 2. A transfers via the ordinary ungated path (no TombStone cleanup happens here)
object::transfer(&a, obj, address_of(&b)); // ObjectCore.owner == B, TombStone still exists

// 3. is_burnt(obj) == true even though B now legitimately owns and is using the object
assert!(object::is_burnt(obj)); // stale/incorrect custody-visibility state
```

    /// Transfer to the destination address using a LinearTransferRef.
    public fun transfer_with_ref(self: LinearTransferRef, to: address) {
        assert!(!exists<Untransferable>(self.self), error::permission_denied(EOBJECT_NOT_TRANSFERRABLE));

        // Undo soft burn if present as we don't want the original owner to be able to reclaim by calling unburn later.
        if (exists<TombStone>(self.self)) {
            let TombStone { original_owner: _ } = move_from<TombStone>(self.self);
        };

        let object = borrow_global_mut<ObjectCore>(self.self);
        assert!(
            object.owner == self.owner,
            error::permission_denied(ENOT_OBJECT_OWNER),
        );
        event::emit(
            Transfer {
                object: self.self,
                from: object.owner,
                to,
            },
        );
        object.owner = to;
    }

    public entry fun unburn<T: key>(
        original_owner: &signer,
        object: Object<T>,
    ) {
        let object_addr = object.inner;
        assert!(exists<TombStone>(object_addr), error::invalid_argument(EOBJECT_NOT_BURNT));

        // The new owner of the object can always unburn it, but if it's the burn address, we go to the old functionality
        let object_core = borrow_global<ObjectCore>(object_addr);
        if (object_core.owner == signer::address_of(original_owner)) {
            let TombStone { original_owner: _ } = move_from<TombStone>(object_addr);
        } else if (object_core.owner == BURN_ADDRESS) {
            // The old functionality
            let TombStone { original_owner: original_owner_addr } = move_from<TombStone>(object_addr);
            assert!(
                original_owner_addr == signer::address_of(original_owner),
                error::permission_denied(ENOT_OBJECT_OWNER)
            );
            transfer_raw_inner(object_addr, original_owner_addr);
        } else {
            abort error::permission_denied(ENOT_OBJECT_OWNER);
        };
    }
