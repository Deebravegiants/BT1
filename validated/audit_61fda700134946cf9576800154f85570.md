## Analog Found

### Title
Updating `cost_per_block` does not settle/accrue the pending block-span reward at the old rate before the new rate takes effect - ([File: modules/pallets/consensus-incentives/src/lib.rs])

### Summary
The reported bug class is: a privileged setter changes a rate/limit parameter that feeds into a derived accrual calculation (interest indices), but the setter does not first "settle" the pending accrual at the old rate before applying the new rate — so the next accrual calculation retroactively applies the new rate to a period that occurred (partly or wholly) under the old rate. `pallet-consensus-incentives`'s `update_cost_per_block` extrinsic has the same structural flaw: it mutates the reward rate in place with no checkpoint/settlement step, and the next reward computation applies the *new* rate to the *entire* un-rewarded block span, including blocks that elapsed while the old rate was in effect.

### Finding Description
`update_cost_per_block` simply overwrites `StateMachinesCostPerBlock` with the new rate and emits an event — there is no step that first computes and pays out (or freezes) the reward for the span already accrued under the previous rate: [1](#0-0) 

The reward for a given state machine is only ever computed lazily, on the next `on_executed`/`process_message` call, using whatever `block_cost` is *currently* stored — not the rate(s) that were actually in effect while those blocks elapsed: [2](#0-1) 

```rust
fn calculate_reward(...) -> Result<...> {
    ...
    let baseline = LastRewardedHeight::<T>::get(state_machine_id).unwrap_or(previous_height);
    let blocks = latest_height.saturating_sub(baseline);
    let reward = blocks_as_balance.saturating_mul(block_cost); // block_cost = CURRENT rate
    Ok(reward)
}
``` [3](#0-2) 

`blocks` is the entire span since `LastRewardedHeight` (which can be many blocks/epochs old if no relayer has delivered a consensus update in the interim), and `block_cost` is read once from storage at reward-calculation time. If governance calls `update_cost_per_block` to change the rate while a reward span is still outstanding, the *entire* outstanding span — including all the blocks that elapsed under the old rate — is paid at the new rate the moment any relayer next submits a `ConsensusMessage`. This is exactly analogous to `MiniPoolAddressProvider.setFlowLimit`: changing a rate-affecting parameter should force settlement/accrual of the pending value (here: pay out or checkpoint the reward owed for the span-to-date) at the old rate before the new rate becomes effective for future spans.

### Impact Explanation
- If governance raises `cost_per_block` (e.g., to attract more relayers going forward), any relayer can then submit a stale-but-valid consensus proof for a state machine that has been under-serviced for a long span, and collect the *entire* backlog at the new, higher rate — a direct treasury overpayment/fund drain relative to what was actually owed for the elapsed period.
- If governance lowers `cost_per_block`, relayers who already earned the higher rate for blocks elapsed before the change are retroactively underpaid, since the reward computation has no way to split the span across rate regimes.
- The transfer is real: `T::Currency::transfer` moves `TreasuryAccount` funds to the relayer based on this miscalculated amount. [4](#0-3) 

This is a genuine loss-of-funds vector (treasury overpays), reachable purely by the normal, unprivileged act of relaying a consensus message — it does not require a malicious governance actor, only a legitimate, routine rate update combined with any relayer's ordinary, permissionless delivery of a pending consensus update.

### Likelihood Explanation
`update_cost_per_block` is a normal operational lever expected to be used periodically to tune relayer incentives (per the pallet's own docs). Any state machine with an outstanding, un-rewarded block span at the time of a rate change is affected, and the mis-priced reward is realized automatically the next time *any* relayer (not necessarily colluding with governance) submits a `ConsensusMessage` for that chain — a fully permissionless, expected action.

### Recommendation
Before/at the point `update_cost_per_block` changes the rate for a `state_machine_id`, force settlement of the outstanding reward span at the *old* rate — e.g., compute and pay (or checkpoint into `LastRewardedHeight`/an explicit accrued-reward store) the reward owed for blocks between `LastRewardedHeight` and the current `latest_commitment_height` using the old `block_cost`, then apply the new rate only to blocks going forward. This mirrors the recommended fix for `setFlowLimit`: update accrual/indices before changing the parameter that feeds them.

### Proof of Concept
1. Governance sets `cost_per_block = 1` for `state_machine_id = X` via `update_cost_per_block`.
2. No relayer submits a consensus update for `X` for 10,000 blocks (span accumulates, `LastRewardedHeight` stays stale).
3. Governance raises `cost_per_block` to `1000` for `X` (a routine incentive-tuning action).
4. Any relayer submits a single valid `ConsensusMessage` for `X` bringing `latest_commitment_height` current.
5. `calculate_reward` computes `reward = 10,000 * 1000` instead of the intended `10,000 * 1` (or a blended amount), draining the treasury for the entire backlog at the new rate — see `calculate_reward` and `process_message`. [5](#0-4)

		pub fn update_cost_per_block(
			origin: OriginFor<T>,
			state_machine_id: StateMachineId,
			cost_per_block: <T as pallet_ismp::Config>::Balance,
		) -> DispatchResult {
			T::IncentivesOrigin::ensure_origin(origin)?;

			StateMachinesCostPerBlock::<T>::mutate(state_machine_id.clone(), |maybe_cost| {
				*maybe_cost = Some(cost_per_block);
			});

			Self::deposit_event(Event::<T>::StateMachineCostPerBlockUpdated {
				state_machine_id,
				cost_per_block,
			});

			Ok(())
		}

		state_machine_height: StateMachineHeight,
		state_machine_id: StateMachineId,
		relayer_account: T::AccountId,
	) -> Result<(), Error<T>> {
		if let Some(block_cost) = StateMachinesCostPerBlock::<T>::get(state_machine_id) {
			let reward = Self::calculate_reward(&state_machine_id, block_cost)?;

			if reward.is_zero() {
				return Ok(());
			}

			T::Currency::transfer(
				&T::TreasuryAccount::get().into_account_truncating(),
				&relayer_account,
				reward,
				Preservation::Expendable,
			)
			.map_err(|_| Error::<T>::RewardTransferFailed)?;

	/// Calculate the reward for a message based on the state machine id
	fn calculate_reward(
		state_machine_id: &StateMachineId,
		block_cost: <T as pallet_ismp::Config>::Balance,
	) -> Result<<T as pallet_ismp::Config>::Balance, Error<T>> {
		let host = <T::IsmpHost>::default();
		let latest_height = host
			.latest_commitment_height(state_machine_id.clone())
			.map_err(|_| Error::<T>::CouldNotGetStateMachineHeight)?;
		let previous_height =
			host.previous_commitment_height(state_machine_id.clone()).unwrap_or_default();

		// Use the rewarded watermark as the baseline and fall back to the previous height until
		// the first reward is recorded for this chain. The watermark only moves forward, so a
		// height that is rolled back and later resubmitted is not paid for a second time.
		let baseline = LastRewardedHeight::<T>::get(state_machine_id).unwrap_or(previous_height);

		let blocks = latest_height.saturating_sub(baseline);

		let blocks_as_balance: <T as pallet_ismp::Config>::Balance = blocks.saturated_into();
		let reward = blocks_as_balance.saturating_mul(block_cost);

		Ok(reward)
	}
