### Title
Unprotected native-token-to-feeToken swaps in `EvmHost.dispatch`/`fundRequest` expose callers to MEV sandwich attacks - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest` each swap a caller's native token payment for the protocol `feeToken` via `IUniswapV2Router02.swapETHForExactTokens`, using the pool's live spot price with no caller-supplied maximum-input/slippage bound beyond the raw `msg.value`, and a `deadline` set to `block.timestamp` (i.e., no real deadline protection either). Any unprivileged account that submits a native-funded dispatch or fee top-up is exposed to sandwich attacks that push the effective ETH price up to the full `msg.value` before the swap executes.

### Finding Description
`dispatch(DispatchPost)` builds a fixed WETH→feeToken path and calls `swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)`. Because this is an *exact output* swap, `post.fee` (the amount of `feeToken` obtained) is fixed, but the amount of ETH consumed to reach it is priced off the pool's instantaneous reserves at execution time, bounded only by `require(amounts[0] <= msg.value, ...)` inside the router. There is no explicit `amountInMax` distinct from `msg.value`, and no parameter lets the caller express "abort if the effective price is worse than X." [1](#0-0) 

The same pattern is repeated verbatim for GET requests and for topping up an existing request's relayer fee: [2](#0-1) [3](#0-2) 

The SDK/docs explicitly warn that the companion `quote()` view function (which calls the router's `getAmountsIn`) must never be used on-chain because "it uses Uniswap's `getAmountsIn`, making it vulnerable to sandwich attacks," and instruct integrators to only use it off-chain for estimation. [4](#0-3)  That warning acknowledges the sandwich risk on the quoting side, but the actual swap executed inside `dispatch`/`fundRequest` has the identical exposure at execution time: since callers estimate `msg.value` off-chain via `quote()` shortly before submitting, an MEV searcher observing the pending dispatch transaction can front-run it with a buy that pushes the WETH/feeToken price up, causing the exact-output swap to consume close to the full `msg.value` (or revert with `EXCESSIVE_INPUT_AMOUNT` if pushed too far), extracting the difference between the fair-market ETH cost and the manipulated cost as MEV profit, then back-run to restore the price. Because `dispatch()`/`fundRequest()` are the entry points every native-paying message dispatcher, relayer-fee top-upper, or any `HyperApp`-based application built on top of `IDispatcher` must go through, this is reachable from a single unprivileged transaction on every EVM deployment of the host contract.

Additionally, unused ETH is refunded by the router to `msg.sender` of the swap call, which is `EvmHost` itself (`address(this)` is only the `to` for token output, not the ETH refund recipient) — meaning any residual ETH from a manipulated/overpriced swap is not automatically returned to the original dispatcher, compounding the loss.

### Impact Explanation
This is a direct value-extraction/theft vector against any unprivileged user or integrating application that funds a dispatch or `fundRequest` call with native token. Because `post.fee`/`get.fee`/`amount` denominate the exact `feeToken` output, the attacker cannot reduce what the user receives, but they can force the user to pay up to the full `msg.value` in ETH for that fixed output — capturing the delta via sandwich as MEV, and the excess ETH refund (if any) does not return to the caller. Given hyperbridge dispatch is a core, constantly-used unprivileged entry point (every native-funded message, relayer-fee top-up, and downstream HyperApp/token bridge/intent flow that opts to pay in native token), this is systemically and repeatedly exploitable, matching the High severity of the original `ReferralFeePoolV0.claimRewardAsMochi` finding (no slippage control on an economically significant, frequently-triggered swap).

### Likelihood Explanation
High. Any pending `dispatch()`/`fundRequest()` transaction paying with native token is visible in the public mempool prior to inclusion, and MEV searchers are known to actively monitor and sandwich unprotected AMM swaps (as cited in the original report's reference to flashbots/MEV literature). No privileged role or special conditions are required — this triggers on ordinary, expected usage of the protocol's fee-payment mechanism.

### Recommendation
Add an explicit `amountInMax` (or equivalently a `maxFee`/slippage-bps parameter distinct from `msg.value`) to `DispatchPost`, `DispatchGet`, and `fundRequest`, and pass it to `swapETHForExactTokens` instead of relying on `msg.value` as the implicit ceiling, so the caller can bound the acceptable native-token cost based on an off-chain quote plus a tolerance. Also use a real expiring `deadline` rather than `block.timestamp`, and ensure any ETH refunded by the router is forwarded back to the original caller (`_msgSender()`), not retained by `EvmHost`.

### Proof of Concept
1. A user calls `quote()` off-chain to estimate `msg.value` needed for `post.fee` feeToken via the current WETH/feeToken pool price, then submits `dispatch{value: quotedAmount}(post)`.
2. An MEV searcher observes the pending transaction in the mempool and front-runs it with a large WETH→feeToken buy on the same Uniswap V2 pool `_hostParams.uniswapV2` used by `EvmHost`, temporarily raising the ETH price required to obtain `post.fee` tokens.
3. The victim's transaction executes `swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)`; since `amounts[0]` (ETH needed) is now higher due to the manipulated reserves, the router consumes up to the entirety of the supplied `msg.value` to still deliver exactly `post.fee` tokens, or reverts entirely if the price moved past `msg.value`, wasting the user's gas and requiring resubmission at a worse price.
4. The searcher back-runs by selling the feeToken/WETH back, extracting the difference between the fair-market cost and the manipulated cost as profit — a classic sandwich, with no on-chain guard in `EvmHost.dispatch`/`fundRequest` to prevent it. [1](#0-0)
