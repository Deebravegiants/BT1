### Title
IR-Net Selection Score Trusts Malformed Model Output Without Range/Outlier Validation - (File: `src/agents/python/ir_net.rs`)

### Summary
The Chainlink `PriceOracle` bug class in the referenced report is: an external, potentially unreliable data source's value is consumed and acted upon without validating that the value is sane/in-range, checking only for a trivial malformed case (zero) rather than bounding or cross-checking the value. The same root-cause pattern exists in orb-core's biometric quality-gating logic, where the IR-Net ML model's numeric outputs are trusted to gate signup eligibility with only a narrow, single-field sanity check.

### Finding Description
`calculate_selection_score` computes the `score` used to decide whether an eye capture is good enough to be selected for signup: [1](#0-0) 

It only guards against `sharpness.is_nan()` (plus `status != 0` / `!valid_for_identification`). None of the other numeric fields returned by the same external/untrusted inference backend (`occlusion_30`, `occlusion_90`, `pupil_to_iris_ratio`, `gaze`, `mean_brightness_raw`, etc., all declared as raw `f64` in `EstimateOutput`) are validated for `NaN`, infinite, or out-of-expected-range values before being used downstream: [2](#0-1) 

These unvalidated values flow directly into the signup quality gate in `biometric_capture::Plan::handle_ir_net`, which compares `estimate.score` against `IRIS_SCORE_MIN` and uses `frame.mean()` bounded by `IRIS_BRIGHTNESS_RANGE`, and separately into an occlusion low-pass filter compared against `THRESHOLD_OCCLUSION_30`: [3](#0-2) [4](#0-3) [5](#0-4) 

Similarly, `FaceIdentifier`'s `IsValidOutput`/`FIIsValidOutput.score` is an `Option<f64>` compared with plain `>` against the current best score with no bounds check at all, and is used to select the "self-custody" face frame used for identity binding: [6](#0-5) [7](#0-6) 

This mirrors the report's core issue exactly: a single external/inference source's numeric output is consumed via a simple comparison (`>=`, `>`, `.contains()`) with only a narrow zero/NaN-style check, no secondary source cross-validation, and no bounds/outlier filtering — so a malfunctioning model backend (e.g., Python inference crash recovery returning stale/garbage floats, deserialization of a corrupted PyAny dict, or a backend regression producing `inf`/absurdly large values in non-`sharpness` fields) is not caught before being used to gate signup-critical decisions.

### Impact Explanation
If the IR-Net or FaceIdentifier Python inference backend returns a malformed but non-NaN value in any of the unguarded fields (e.g., `occlusion_30 = -inf`, `pupil_to_iris_ratio = inf`, or an inflated `FIIsValidOutput.score`), the orb's quality/liveness gates could pass or fail incorrectly: a poor-quality, occluded, or fraudulent iris/face capture could be accepted as the best candidate for a biometric signup, or a legitimate valid capture could be silently rejected. Because these scores directly drive which frame is selected as the "self-custody candidate" and which iris capture is used for enrollment, a malfunctioning model is analogous to a malfunctioning price oracle silently corrupting downstream financial decisions — here it corrupts downstream biometric-enrollment decisions (which frame gets bound to the identity commitment).

### Likelihood Explanation
Likelihood is low-to-moderate and unprivileged-user-reachable only in the passive sense: an ordinary orb operator/user simply undergoing a normal scan is the one whose capture is gated by this logic; no privileged access or malicious peer is required to trigger the code path — it runs on every signup. However, actually producing an out-of-range value requires the underlying ML inference backend to genuinely malfunction (model bug, corrupted intermediate state, backend crash-recovery returning a stale/garbage `PyAny`), which is not something an external attacker can directly force from the QR/network boundary; it is analogous to the disputed rating given to the original Chainlink finding ("we expect these feeds to be fairly reliable... but not 100%").

### Recommendation
- Validate all numeric fields extracted from the Python inference output in `extract()` (`src/agents/python/ir_net.rs`) and in `FIIsValidOutput`/`IsValidOutput` parsing — reject or clamp `NaN`/`±inf` and enforce expected ranges (e.g., `occlusion_30`, `occlusion_90`, `gaze`, `pupil_to_iris_ratio`, `score` should be within documented bounds) rather than checking only `sharpness.is_nan()`.
- Extend `calculate_selection_score` to also fail-closed (`-1.0`/rejected) when any of `occlusion_30`, `occlusion_90`, `pupil_to_iris_ratio`, `gaze`, or `mean_brightness_raw` is `NaN`, infinite, or outside a sane range.
- Apply the same defensive bounds-check to `FIIsValidOutput.score` before using it in the `>` comparison that selects the self-custody candidate frame.

### Proof of Concept
1. Simulate/inject a Python inference response where `sharpness` is a normal finite value but `occlusion_30` (or `pupil_to_iris_ratio`, `gaze`) is `inf`/`-inf`/`NaN` (e.g., from a backend timeout/crash-recovery path returning stale float state).
2. `calculate_selection_score` (src/agents/python/ir_net.rs:305-308) does not inspect these fields, so `score` is computed and returned as a seemingly valid finite value based on `sharpness` alone.
3. `handle_ir_net` (src/plans/biometric_capture/mod.rs:236-259) accepts the frame as `valid_capture` once `estimate.score >= IRIS_SCORE_MIN`, without ever checking the malformed `occlusion_30`/`gaze` fields, even though `occlusion_30` independently feeds the UX-facing occlusion filter (`THRESHOLD_OCCLUSION_30`, src/consts.rs:349) that is supposed to reject occluded eyes.
4. Result: a capture that should have been rejected due to malformed/out-of-range occlusion or gaze data is instead selected as the sharp iris frame used for enrollment.
