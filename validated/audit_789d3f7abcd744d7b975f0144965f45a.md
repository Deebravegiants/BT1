### Title
Direct LT transfers into a curve `Pair` are permanently and unrecoverably locked, with no sweep/rescue path - ([File: packages/contracts/src/Router.sol], [File: packages/contracts/src/Bonding.sol])

### Summary
Any LT sent directly to a bonding-curve `Pair` via a plain ERC20 `transfer` (not through `Zap.buy`/`Bonding.buy`) becomes permanently stuck. The curve's accounting only recognizes LT that flows through `Router.buy`/`sell`, and at graduation only the precisely-computed `ltFromPair = reserve1 - virtualLtReserve` is drained; anything above that (i.e., the donated LT) is deliberately left behind in the pair. Once the token's lifecycle passes `Curve`, the only code path that can move LT out of the pair (`Router.graduate`, invoked solely from `Bonding._prepareGraduationLiquidity`) becomes permanently unreachable, so the leftover LT can never be withdrawn by anyone — not the depositor, not the creator, not the protocol.

### Finding Description
`Router.addInitialLiquidity` explicitly notes the launch-time asset reserve is virtual — "no real LT moved here" [1](#0-0) . This means the only real LT balance a curve `Pair` ever holds is what enters via `Router.buy` (`IERC20(asset).safeTransferFrom(...)`) or an arbitrary direct `transfer` from any wallet [2](#0-1) .

At graduation, `Router.graduate` is documented to move only the exact `amount` passed in (`stored assetReserve - virtualLtReserve`), explicitly excluding any LT donated directly to the pair via `IERC20.transfer` [3](#0-2) . The same function's own comments acknowledge this is a trust assumption, not an on-chain guarantee, and that the leftover becomes unreachable once the token's lifecycle flips past `Curve`, since `graduate` is callable only from `Bonding._prepareGraduationLiquidity`, which cannot run again after graduation [4](#0-3) . The scope docs confirm the same design: "Direct LT donations to the pair don't count toward the USD threshold and don't enter the LP — they stay in the curve pair under the trust assumption that BONDING_ROLE is only ever held by Bonding," and "donated LT remains in the curve pair, reachable only via `Pair.transferAsset` which is gated by Router's `BONDING_ROLE`" [5](#0-4) .

There is no function anywhere in `Pair`, `Router`, or `Bonding` that lets the owner, creator, or the depositor sweep this excess LT after graduation (or even while on the curve, outside the exact `ltFromPair` calculation). This is the same bug class as the referenced report: value sent into a contract in excess of what the accounting model expects (there, rebasing yield; here, directly-transferred LT) has no withdrawal path and is permanently stranded.

### Impact Explanation
Any LT accidentally or deliberately sent directly to a `Pair` address (a reachable, permissionless action — a plain ERC20 `transfer`) is permanently frozen for the life of the contract once the token graduates, since `Router.graduate`/`Bonding._prepareGraduationLiquidity` cannot be invoked again post-`Curve` lifecycle. Even pre-graduation, the stuck LT is invisible to `canGraduate`'s USD-threshold math and is excluded from LP seeding, so it never benefits any trader, creator, or the protocol — it simply sits inert in the `Pair` forever. This is permanent freezing of an unrelated wallet's/depositor's funds, matching the Medium-severity impact class of the referenced finding.

### Likelihood Explanation
Likelihood is non-trivial: any unrelated wallet can trigger this by mistakenly sending LT directly to a known `Pair` address (a common user error with ERC20 tokens, since `Pair` addresses are public and predictable via `Factory.getPair`), or a wallet could donate LT deliberately (e.g., to grief accounting or as a mistaken deposit attempt believing it functions like `Zap.buy`). No privileged role or unusual precondition is required — only a direct ERC20 `transfer`, which is one of the explicitly in-scope reachable paths.

### Recommendation
Add an owner- or role-gated sweep function on `Pair` (exposed through `Router`, restricted to `BONDING_ROLE`) that can transfer out LT held in the pair in excess of the tracked `assetReserve` (i.e., `IERC20(asset).balanceOf(pair) - reserveAsset`), similar in spirit to `FeeVault.sweepDonations()`, which already implements exactly this pattern for USDC donations to the vault [6](#0-5) . This sweep should remain callable after graduation, not be gated behind the `Curve`-only lifecycle check in `Bonding._prepareGraduationLiquidity`.

### Proof of Concept
1. `Bonding.launch(...)` creates a token and its `Pair` (LT reserve seeded virtually, no real LT transferred, per `Router.addInitialLiquidity`).
2. An unrelated wallet calls `IERC20(lt).transfer(pairAddress, X)` directly, bypassing `Zap.buy`/`Bonding.buy`.
3. The pair's live `IERC20(lt).balanceOf(pair)` now exceeds its accounted `assetReserve` by `X`, but `canGraduate` and `previewLtUntilGraduation` only ever compute against the stored reserve, so `X` is invisible to threshold math.
4. Once the token graduates, `Bonding._prepareGraduationLiquidity` calls `Router.graduate(token, ltFromPair)` where `ltFromPair = reserve1 - virtualLtReserve` — strictly excluding the donated `X` [7](#0-6) .
5. Post-graduation, `Bonding`'s lifecycle for this token is no longer `Curve`, so `_prepareGraduationLiquidity`/`Router.graduate` can never be invoked again for this token — the `X` LT sitting in the pair is permanently unrecoverable by any address.

    ///         Called by `Bonding._prepareGraduationLiquidity` during graduation
    ///         with `amount = stored assetReserve - virtualLtReserve` (i.e. the
    ///         real LT raised by the curve, excluding the virtual seed).
    /// @dev    Donation-resistant: passing an explicit `amount` instead of
    ///         draining `assetBalance()` ensures any LT that was donated
    ///         directly to the pair via `IERC20.transfer` is left behind and
    ///         excluded from LP seeding.
    ///
    ///         "Locked" here is a trust-assumption claim, not an on-chain
    ///         guarantee. `Pair.transferAsset` is gated by `onlyRouter`, and
    ///         `Router` only exposes it via this function and `sell`. Both
    ///         require `BONDING_ROLE`, which only `Bonding` holds. `Bonding`
    ///         in turn only calls `graduate` from
    ///         `_prepareGraduationLiquidity` — which is unreachable once the
    ///         token's lifecycle has flipped past `Curve`. So the leftover
    ///         is unreachable as long as (a) `BONDING_ROLE` is not granted
    ///         to any other address, and (b) future `Bonding` upgrades
    ///         preserve the lifecycle gate.
    function graduate(
        address token,
        uint256 amount
    ) external onlyRole(BONDING_ROLE) {
        address asset = assetTokenFor(token);
        address pairAddr = factory.getPair(token, asset);
        if (pairAddr == address(0)) revert PairNotFound();
        IPair(pairAddr).transferAsset(msg.sender, amount);
    }

### Dynamic LP Seeding (zero price gap)

The problem: the reserve asset (LT) has a varying USD price, so the exact number of LP tokens needed to make the DEX pool open at the last curve price is not known ahead of time. Naively seeding the LP with the full 250M reserve would create a large price gap that arbitrage bots would immediately close, transferring value out of the protocol.

Our approach: compute the exact `tokensForLP` at graduation time so the LP opens at **precisely** the last curve price. Burn whatever is left of the 250M reserve.

`_graduate()` performs, in order:

1. Read `(reserve0, reserve1)` from the Pair **before** any state mutation.
2. Burn any unsold real curve tokens from the pair (`unsoldBurned`). This also burns any tokens donated to the pair via direct ERC20 transfer.
3. Recover `virtualLtReserve = Pair.k() / Token.TOTAL_SUPPLY()` and compute `ltFromPair = reserve1 - virtualLtReserve` — the real LT raised by the curve, excluding the launch-time virtual seed AND any LT donated to the pair. Drain exactly that amount via `Router.graduate(token, ltFromPair)`. Donated LT remains in the curve pair, reachable only via `Pair.transferAsset` which is gated by `Router`'s `BONDING_ROLE`.
4. Compute `tokensForLP = (ltFromPair × reserve0) / reserve1` — the unique amount that sets the LP price `ltFromPair / tokensForLP` equal to the last curve price `reserve1 / reserve0`. Capped at `lpReserveTotal` as a defensive guard (parabola math proves `tokensForLP ≤ lpReserveTotal` by construction).
5. Burn `lpReserveTotal − tokensForLP` from `Bonding`'s held reserve (`lpBurned`).
6. `addLiquidity(tokensForLP, ltFromPair)` on HyperSwap V2 → LP tokens go to `LPLock`.
