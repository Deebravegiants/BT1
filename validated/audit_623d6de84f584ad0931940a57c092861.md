### Title
Webhook `shop-domain` header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the HMAC-signable content solely from the raw request body (`to_signable_string` returns `@raw_body`), while the `shop` (shop-domain) field used downstream to identify the tenant is read from a separate, unsigned HTTP header. `Registry.process` validates only the body/HMAC pair and then trusts the header-derived `shop` value when building `WebhookMetadata`, breaking the binding between "bytes verified" and "shop identity acted on."

### Finding Description
`Utils::HmacValidator.validate` computes and compares the HMAC over `verifiable_query.to_signable_string` [5](#0-4) . For webhooks, `to_signable_string` is defined as just the raw JSON body [3](#0-2) , and never incorporates the `shopify-shop-domain` / `x-shopify-shop-domain` header, which is read independently via `shop` [2](#0-1) .

`Registry.process` calls `Utils::HmacValidator.validate(request)` to authenticate the request, and — once that passes — immediately constructs `WebhookMetadata` using `request.shop` taken straight from the unauthenticated header, dispatching it to the app's handler [6](#0-5) .

Because the `shop` field is never part of the signed payload, any request whose body+HMAC pair is valid for the app's secret can be replayed with an arbitrary `shop-domain` header value, and it will still pass validation. An unprivileged attacker can obtain a legitimate body+HMAC pair by installing the app on their own store (a normal, unprivileged action) and capturing a real webhook Shopify sends them. They can then resend that exact body/HMAC to the app's public webhook endpoint while substituting the `shop-domain` header with a victim shop's domain. `HmacValidator.validate` still succeeds (it never looked at the header), and the handler receives `WebhookMetadata` claiming the data belongs to the victim shop [7](#0-6) .

### Impact Explanation
This breaks the equality that should hold: `shop authenticated by HMAC` == `shop the handler acts on`. Any app logic that uses `data.shop` to look up a session/store record, write shop-scoped data, or trigger shop-scoped side effects (e.g., updating inventory, disabling a feature, writing audit logs) can be tricked into operating on a different, victim tenant's data using attacker-supplied (though real, self-obtained) webhook payloads. This is a cross-tenant confusion primitive reachable by any internet user who can install the app once on their own shop, satisfying the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Likelihood is High: no secret key, session, or token is required. The attacker only needs to be an app installer (unprivileged) to obtain one valid signed webhook body/HMAC pair, then can freely relabel it with any `shop-domain` value and POST it directly to the app's public webhook endpoint.

### Recommendation
Include the shop domain (and topic/webhook-id) inside the HMAC-covered signable content, or otherwise cryptographically bind the `shop` header to the signed body (e.g., verify that the `shop` header matches a shop value embedded in the signed payload, or require the app layer to cross-check `request.shop` against a shop this app knows to be legitimately installed and currently expecting this webhook_id/topic combination) before constructing `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and configures a webhook subscription (e.g., `orders/create`).
2. Attacker triggers the webhook (e.g., creates an order), and Shopify sends a legitimately signed request to the app's webhook endpoint with body `B` and header `x-shopify-hmac-sha256: H` (valid for secret `S`) and `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker intercepts/replays this exact request but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`, keeping body `B` and HMAC `H` unchanged, and POSTs it to the app's public webhook endpoint.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `B`/`H` [8](#0-7) .
5. `WebhookMetadata.new(... shop: request.shop ...)` is built with `shop == "victim-shop.myshopify.com"` and dispatched to the app's handler, causing the app to process attacker-controlled order data as if it belongs to the victim shop.
