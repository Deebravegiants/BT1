### Title
Fee-on-Transfer/Deflationary Token Escrow Over-Crediting in Tron IntentGatewayV2 - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of `IntentGatewayV2.placeOrder` credits escrow (`_orders[commitment][token]`) based on the user-declared/nominal order amount (only reduced by the protocol fee bps), without ever measuring the token balance actually received by the contract via `balanceOf` before/after the `transferFrom`/sweep. For fee-on-transfer, deflationary, or rebasing-down tokens, this causes the gateway to record escrow obligations larger than the tokens it actually holds.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol::placeOrder`, the commitment and `reducedInputs` (escrow amounts) are computed purely from `order.inputs[i].amount` minus the protocol fee, before any token transfer occurs: [1](#0-0) 

Then, in the non-predispatch escrow path, the contract calls `safeTransferFrom` and immediately credits `_orders[commitment][token] += reducedInputs[i].amount` without checking `IERC20(token).balanceOf(address(this))` before/after the transfer: [2](#0-1) 

Similarly, in the predispatch branch, dust is computed only against `requiredAmount` (the dispatcher-side balance vs. `order.inputs[i].amount`), and the escrow amount credited is still `reducedInputs[i].amount` (the fee-bps-reduced nominal amount), not the amount that actually lands on `address(this)` after the dispatcher→gateway sweep transfer (which itself would incur a second transfer-fee deduction for FOT tokens): [3](#0-2) 

This is a direct regression relative to the main EVM `IntentGatewayV2.sol`, which was explicitly hardened against this exact bug class: it snapshots balances before/after transfers, mutates `order.inputs[i].amount` to the actual received amount, and only then computes the commitment and protocol fee, ensuring `_orders[commitment][token]` always matches real contract balance: [4](#0-3) [5](#0-4) 

The comprehensive fee-on-transfer test suite in `evm/tests/foundry/IntentGatewayV2SameChainTest.sol` (`testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived`, `testPlaceOrder_FeeOnTransferToken_WithProtocolFee`, `testPlaceAndFill_FeeOnTransferToken_RoundTrip`, `testPlaceOrder_FeeOnTransferToken_Predispatch`) confirms this is a known, deliberately-fixed bug class for the main EVM gateway — but no equivalent tests or logic exist for the Tron gateway, indicating the same fix was not ported: [6](#0-5) 

### Impact Explanation
Any unprivileged user calling `placeOrder` on the Tron `IntentGatewayV2` with a fee-on-transfer/deflationary token as an input causes the contract's internal escrow ledger (`_orders[commitment][token]`) to overstate the tokens actually custodied. Because `_orders` is a shared per-token accounting map across all orders, this shortfall is not isolated to the malicious order — it depletes the pool of actual token balance backing other legitimately-placed orders for the same token. When solvers later `fillOrder`/settle and the protocol attempts to pay out the recorded escrow amount to solvers or refund users on timeout, transfers can fail for the last claimant (denial of service / stuck funds) or, depending on withdrawal ordering, earlier claimants can drain real balance that rightfully belongs to later orders, causing shortfall/insolvency and effectively socializing the loss across all escrowed holders of that token. This is a concrete freezing-of-funds / accounting-insolvency vulnerability reachable from a single `placeOrder` transaction, matching the "concrete theft or permanent freezing of funds" bar.

### Likelihood Explanation
Likelihood is medium-high: many popular tokens implement transfer fees, rebasing, or deflationary burn-on-transfer mechanics (e.g., certain stablecoin variants, reflection tokens). No allow-list or standard-ERC20-only restriction is visible in the reviewed `placeOrder` code path to prevent listing such tokens as intent inputs, and the trigger requires only a normal user calling `placeOrder` with such a token as input — no special privileges needed.

### Recommendation
Port the balance-snapshot logic from `evm/src/apps/IntentGatewayV2.sol` (lines 260–329) to `evm/tron/contracts/apps/IntentGatewayV2.sol`: measure `balanceOf(address(this))` before and after each `transferFrom`/sweep, mutate `order.inputs[i].amount` to the actually-received amount, and compute `reducedInputs`/`commitment`/escrow credit from that real received value rather than the nominal user-specified amount, for both the direct-transfer and predispatch paths.

### Proof of Concept
1. Deploy a fee-on-transfer ERC20 (as in `FeeOnTransferToken` from `evm/tests/foundry/IntentGatewayV2SameChainTest.sol`) with e.g. a 1% transfer fee.
2. User calls Tron `IntentGatewayV2.placeOrder` with `order.inputs[0] = {token: FOT, amount: 1000e18}`, no protocol fee.
3. `transferFrom` moves 1000e18 nominally but the gateway only receives 990e18 (contract `balanceOf` = 990e18).
4. `_orders[commitment][FOT]` is credited with `reducedInputs[0].amount == 1000e18` (since `protocolFeeBps == 0`, `reducedInputs = order.inputs` unchanged) — a 10e18 mismatch between recorded escrow and actual balance.
5. If a solver fills the order and the protocol later attempts to transfer out 1000e18 to the solver/refund path, either this transfer reverts (insufficient balance) or, if other orders' FOT escrow coexists in the same contract, it succeeds by consuming balance that was escrowed for other unrelated orders, leaving those orders under-collateralized.

    /// @notice Escrow correctly reflects actual received amount for fee-on-transfer tokens.
    function testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived() public {
        // Deploy a 1% fee-on-transfer token
        FeeOnTransferToken fot = new FeeOnTransferToken(100); // 1% = 100 bps
        fot.mint(user, 10000 * 1e18);

        uint256 inputAmount = 1000 * 1e18;
        uint256 expectedReceived = inputAmount - (inputAmount * 100) / 10000; // 990

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(fot)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 900 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        vm.startPrank(user);
        fot.approve(address(intentGateway), inputAmount);
        intentGateway.placeOrder(order, bytes32(0));
        vm.stopPrank();

        // Gateway should hold only what it actually received
        assertEq(
            fot.balanceOf(address(intentGateway)), expectedReceived, "Gateway balance should match received amount"
        );

        // Reconstruct the order as placeOrder would have mutated it
        order.user = bytes32(uint256(uint160(user)));
        order.source = host.host();
        order.nonce = 0;
        order.inputs[0].amount = expectedReceived;
        bytes32 commitment = keccak256(abi.encode(order));

        // Escrow should match actual received, not the user-specified amount
        assertEq(
            intentGateway._orders(commitment, address(fot)),
            expectedReceived,
            "Escrow should equal actual received amount"
        );
    }
