### Title
Spoke supply cap can be inflated past its token-denominated limit after bad-debt write-downs lower the supply index - (File: contracts/controller/src/spoke_usage.rs)

### Summary
XOXNO Lending enforces per-spoke `supply_cap`/`borrow_cap` (token base units) by converting the cap into scaled shares with the current market index and comparing it against cumulative scaled usage in `SpokeUsageRaw`. Because a borrow-side seize socializes bad debt by *reducing* the supply index, `cap_scaled = cap × 10^(27−d) × RAY / supply_index` grows after every bad-debt event while `supplied_scaled_ray` usage is untouched. An unprivileged user can therefore push a spoke's token-denominated supply well above its configured `supply_cap`, defeating the risk-allocation bound that the cap is meant to provide.

### Finding Description
The cap check lives in `enforce_spoke_cap`, which converts the token-unit cap to shares via `calculate_scaled_cap(env, cap, decimals, index)` and asserts `usage_scaled + delta_scaled <= cap_scaled` [1](#0-0) . Usage is stored as fixed scaled shares (`supplied_scaled_ray`), while the cap is index-dependent [2](#0-1) .

Separately, when a borrow position is seized (liquidation shortfall or `clean_bad_debt`), the pool calls `interest::apply_bad_debt_to_supply_index`, which multiplies the supply index by `remaining / total_supplied_value` — i.e., writes the loss into the index [3](#0-2) [4](#0-3) . The index is floored only at `SUPPLY_INDEX_FLOOR_RAW = RAY/1000`, so repeated bad debt can drive it down by up to three orders of magnitude.

Consequence: with `supply_index` at 0.5×RAY, `cap_scaled` doubles, so a spoke whose `supply_cap` was exhausted can supply ~2× the cap in tokens; at the floor, ~1000×. This is the same bug class as H-01: a risk bound denominated in a share/index unit that bad debt itself moves in the attacker's favor.

### Impact Explanation
The spoke cap is the protocol's bound on how much exposure one spoke (risk container) may take in a hub market. Once breached, the capped spoke can hold a token-supply share far beyond its allocation; subsequent bad debt in that market is socialized across all suppliers of the hub market (`apply_bad_debt_to_supply_index` reduces every supplier's claim pro-rata), so other spokes' users absorb losses the cap was configured to prevent — protocol insolvency / theft of user funds beyond the designed maximum loss.

### Likelihood Explanation
Triggering requires only permissionless operations: supply collateral, borrow to create an underwater position (or wait for/force index drift), run `liquidate`/`clean_bad_debt` so bad debt hits the supply index, then `supply` again into the same spoke — the cap now admits more tokens. No admin action, oracle manipulation, or privileged role is needed; the write-down is a normal, permissionlessly reachable code path.

### Recommendation
Track cap usage in token terms rather than scaled shares: either store `supplied`/`borrowed` usage as unscaled asset amounts, or compare `usage_scaled × index / RAY + delta_tokens` against the raw `cap`. Alternatively, snapshot the cap check at the supply index recorded when usage was accrued so index write-downs cannot expand headroom.

### Proof of Concept
1. Spoke S lists hub asset USDC with `supply_cap = 1_000_000` (token units), borrow cap sufficient for the attacker.
2. Attacker supplies USDC up to the cap through spoke S (`supply` → `apply_entry(UsageSide::Supply, ...)` passes since `supplied_scaled_ray == cap_scaled`).
3. Attacker supplies collateral in another asset, borrows USDC, and lets the position go underwater (or engineers a shortfall via liquidation mechanics), then calls `liquidate`/`clean_bad_debt`. `seize` runs `apply_bad_debt_to_supply_index`, cutting `supply_index` to, e.g., 0.5×RAY.
4. `cap_scaled` doubles while `supplied_scaled_ray` is unchanged. Attacker calls `supply` again with up to ~1_000_000 more USDC tokens; `enforce_spoke_cap` accepts because `usage + delta <= 2 × original cap_scaled`.
5. Repeat after further bad debt: at `SUPPLY_INDEX_FLOOR_RAW` (RAY/1000), the spoke can hold ~1000× its configured cap in tokens, and the next write-down socializes the oversized loss to all suppliers.

Note: I verified the cap conversion, index write-down, and seize path in the code above; I did not trace every controller call site of `apply_entry` to confirm which index snapshot (`MarketIndexRaw`) is passed on the supply path, though `UsageSide::Supply` maps to `market_index.supply_index` [5](#0-4)  and the documented formula in `skills/xoxno-lending/math.md` confirms `cap_scaled` is computed against the current supply index.

```rust
fn enforce_spoke_cap(
    env: &Env,
    side: UsageSide,
    usage: &SpokeUsageRaw,
    delta_scaled: Ray,
    cap: i128,
    index: Ray,
    decimals: u32,
) -> Ray {
    let cap_scaled = calculate_scaled_cap(env, cap, decimals, index);
    let next_scaled = Ray::from(side.scaled(usage)).checked_add(env, delta_scaled);
    assert_with_error!(env, next_scaled <= cap_scaled, side.cap_error());
    next_scaled
}
```

```rust
pub(crate) fn apply_bad_debt_to_supply_index(cache: &mut Cache, bad_debt: Ray) {
    let total_supplied_value = cache.supplied().mul(cache.env(), cache.supply_index());

    if total_supplied_value == Ray::ZERO {
        return;
    }

    let capped = bad_debt.min(total_supplied_value);
    let remaining = total_supplied_value.checked_sub(cache.env(), capped);

    let reduction_factor = remaining.div_floor(cache.env(), total_supplied_value);
    let new_supply_index = cache
        .supply_index()
        .mul_floor(cache.env(), reduction_factor);

    cache.set_supply_index(new_supply_index.max(Ray::from(SUPPLY_INDEX_FLOOR_RAW)));
}
```
