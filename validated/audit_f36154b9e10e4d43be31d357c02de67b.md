## Analysis

I found no length bound on `RequestMessage.requests`, `ResponseMessage.requests`, or `TimeoutMessage`'s request vectors in `modules/ismp/core/src/messaging.rs`, and no batch-size cap on `messages: Vec<Message>` in `handle_unsigned`. Combined with the static weight `fn weight() -> Weight { Weight::from_parts(300_000_000, 0) }` used for **every** `handle_unsigned` call regardless of how many messages/requests it contains, this reproduces the CVE-2023-45130 bug class: a fixed cost is charged for an operation whose real I/O/PoV cost scales with attacker-controlled batch size.

### Title
Unbounded, fixed-weight `handle_unsigned` batch lets an unsigned relayer inflate PoV/execution cost with unbacked weight accounting - (File: modules/pallets/ismp/src/lib.rs)

### Summary
`pallet_ismp::Call::handle_unsigned` is a permissionless, fee-free (`ensure_none`) unsigned extrinsic that accepts an arbitrary-length `Vec<Message>`, each of which can itself carry an arbitrary-length `Vec<PostRequest>` / `Vec<GetRequest>` / timeout batch (no `MaxMessages`/`BoundedVec` cap found in `modules/ismp/core/src/messaging.rs`). The dispatchable is annotated with a single static weight, `weight() -> Weight::from_parts(300_000_000, 0)` [1](#0-0) , applied unconditionally via `#[pallet::weight(weight())]` on `handle_unsigned` [2](#0-1) . This is exactly the pattern the Frontier SUICIDE CVE describes: a single primitive dispatch whose actual work (many child-trie reads/writes for receipts/commitments, MMR membership/non-membership verification, and module callbacks) is unbounded, but the declared/charged weight is a constant that does not scale with the batch size.

### Finding Description
`Self::execute(messages)` iterates every `Message` in the batch and, per message, iterates every request/response inside it, doing for each one: a state-proof membership/non-membership check, a child-trie storage read (`request_receipt`/`response_receipt` lookups), a child-trie write (`store_request_receipt`, `store_response_receipt`, or a `delete_request_commitment`/`delete_request_receipt` pair for timeouts), and a module callback [3](#0-2) ; the response and timeout handlers do the analogous per-item child-trie insert/remove work [4](#0-3) , [5](#0-4) . All of this genuine, scaling I/O and computation is dispatched under one flat weight figure computed independently of `messages.len()` or the size of any inner `requests` vector [6](#0-5) .

Because `handle_unsigned` is unsigned (`ensure_none(origin)?`) and free of fees, the only gatekeeping is `ValidateUnsigned::validate_unsigned`, which itself calls `Self::execute(messages.clone())` to check proof validity before letting the transaction into the pool/block [7](#0-6) . Validity checking requires valid state/consensus proofs, but nothing in that path caps the number of messages or requests per message — an attacker who has (or can synthesize, e.g. via GET responses that only need a valid state proof at a height Hyperbridge has already committed) a large number of provably-valid post requests/timeouts/get-responses for a chain it controls can submit one `handle_unsigned` extrinsic containing thousands of them, all charged the same constant weight as a single-message call. The testsuite itself demonstrates unbounded batch sizes are accepted at the type level (batches of 100 GET requests each with 256 keys, or 1000 POST requests, encoded into a single `handle_unsigned` call) [8](#0-7) .

This mirrors the Frontier SUICIDE root cause precisely: (1) a single dispatched call, (2) performing an I/O-heavy operation whose real cost is proportional to attacker-controlled input size, (3) charged a fixed, size-independent weight, so the runtime's weight/PoV accounting under-prices the actual work. On Substrate-based parachains, underpriced weight for a block-included extrinsic means the actual PoV size and execution time of that block can exceed what `frame_system::CheckWeight`/block builder assumed when packing the block, which can push the parachain's block over the relay chain's PoV size limit exactly as described in the CVE, or otherwise cause block production to stall on that block.

### Impact Explanation
Underpriced, size-independent weight for an unbounded I/O operation is a High-severity availability bug in the Frontier precedent because it can force a parachain block to exceed the relay chain's PoV limit, permanently or repeatedly stalling block production/finality — "a route unable to deliver messages" for however long the malformed/oversized block keeps getting proposed or until governance intervenes. Because `handle_unsigned` is free (no fee is charged — the whole point of the unsigned design is "execute for free" per the pallet docs [9](#0-8) ), there is no economic disincentive scaling with batch size, unlike a normal signed extrinsic where weight-based fees would make an oversized batch prohibitively expensive.

### Likelihood Explanation
Medium-High. The attacker needs valid proofs for whatever chain/height is being used, but does not need any privileged role — `handle_unsigned` is explicitly permissionless ("permits anyone execute ISMP messages for free, provided they have valid proofs") [10](#0-9) . GET-response batches in particular only require a state proof against an already-finalized state commitment, and the request/timeout paths only require commitments that already exist on Hyperbridge (which an attacker can create cheaply by dispatching many small requests from a chain they control, then submitting the resulting large valid batch back through `handle_unsigned`). No admin, governance, or malicious-collator assumption is needed — the reachable actor is exactly "a relayer submitting a dispatched/relayed proof," the class the scope rules call out.

### Recommendation
Bound the size of `messages: Vec<Message>` in `handle_unsigned` (and/or the inner `requests`/`timeouts` vectors in `RequestMessage`/`ResponseMessage`/`TimeoutMessage`) with an enforced `MaxMessages`/`BoundedVec`-style cap checked in both `validate_unsigned`/`pre_dispatch` and `execute`, and make the declared `#[pallet::weight(...)]` scale with the actual batch size (number of messages × per-message/per-request weight) instead of the flat `Weight::from_parts(300_000_000, 0)`, mirroring how `insert_bounded_state_commitment` already caps per-call storage churn via `MAX_COMMITMENT_EVICTIONS_PER_INSERT` [11](#0-10) .

### Proof of Concept
1. On a connected source chain, dispatch a large number (e.g., several thousand) of small `PostRequest`s or `GetRequest`s addressed to Hyperbridge/the target parachain, so that valid commitments/state proofs exist for all of them at a height Hyperbridge already has committed.
2. Construct a single `pallet_ismp::Call::handle_unsigned { messages: vec![Message::Request(RequestMessage { requests: <huge vec>, proof, signer })] }` (the testsuite shows this construction pattern working for 1000+ requests/100 GET requests with 256 keys each) [12](#0-11) .
3. Submit as an unsigned transaction; `validate_unsigned` executes and accepts it as long as proofs verify, with no batch-size check.
4. The resulting extrinsic is weighed at the constant `300_000_000` regardless of size, while its actual child-trie I/O, MMR verification, and module-callback cost (and thus PoV size / execution time) scales with the number of requests included — reproducing the Frontier SUICIDE fixed-cost-for-variable-work pattern in a block-inclusion context.

## Transaction fees

Pallet ISMP uses unsigned transactions for executing cross-chain messages. This means all cross-chain messages received are executed for free as unsigned transactions. The upside to this is that it cannot be exploited as a spam vector, since the transaction pool will check if the submitted extrinsics are valid before they are included in the pool. This validity check ensures that the transaction can be successfully executed and contains valid proofs. Malformed messages or those with invalid proofs are filtered out by the transaction pool validation logic preventing unnecessary processing and potential network congestion.
