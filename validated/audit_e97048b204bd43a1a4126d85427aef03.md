### Title
Creator fee balance in `FeeVault` becomes permanently frozen if the creator's address is blacklisted by USDC - (File: packages/contracts/src/FeeVault.sol)

### Summary
`FeeVault.claim()` hardcodes the payout recipient to `msg.sender` with no way to redirect the already-accrued `creatorBalance` to a different address. If a token creator's address is ever blacklisted by USDC (a reserve/fee asset used by the protocol), their entire accrued but unclaimed fee balance becomes permanently frozen in the vault, with no on-chain recourse to recover it — the same bug class as the referenced `recoverERC20` blacklist issue, but here it locks real, already-earned trader/creator fee revenue rather than a rescue utility.

### Finding Description
`claim()` reads the caller's `creatorBalance[msg.sender]`, zeroes it, decrements `totalAccruedCreator`, and calls `$.usdc.safeTransfer(msg.sender, amount)`: [1](#0-0) 

There is no parameter to specify an alternate beneficiary address, unlike patterns that let a user redirect payouts to a fresh address. If USDC blacklists the creator's address, `safeTransfer` to that address will revert every time `claim()` is invoked, and the funds tied to `creatorBalance[msg.sender]` can never be extracted through this function.

Unlike `claimProtocol()`, whose recipient `feeTo` can be rotated by the owner via `setFeeTo()` to work around a blacklisted address: [2](#0-1) 

the creator-side balance has no equivalent redirect mechanism. `Bonding.transferCreator(tokenAddress, newCreator)` only changes the *creator* attribution used for **future** `accrue()` calls — it does not move any already-accrued `creatorBalance[oldCreator]` to the new creator, per the documented behavior: "`transferCreator(tokenAddress, newCreator)` (on `Bonding`) — transfers role and future fee attribution." [3](#0-2) 

Since `creatorBalance` is keyed directly by the creator's address (not by token, and not migratable), any USDC already accrued to a blacklisted creator address sits in the vault with no path to withdrawal: `claim()` will always revert for that address, and no admin or protocol function exists to reassign a stranded `creatorBalance[creator]` entry to a new address.

### Impact Explanation
This results in permanent freezing of legitimately earned creator fee funds (0.25% of every buy/sell on that creator's token) inside `FeeVault`. The funds remain locked in the contract's USDC balance indefinitely, unable to be claimed by the affected creator or redirected by governance, since `transferCreator` does not carry over historical balances and no rescue path exists for stuck `creatorBalance` entries.

### Likelihood Explanation
This requires the specific condition that the creator's wallet address gets blacklisted by USDC (Circle-controlled blacklist), which is outside the protocol's control but is a realistic real-world event (sanctions, compliance actions, compromised address flagged by Circle) for any of potentially many creator addresses across the launchpad. Given USDC is the vault's settlement asset (`FeeVaultStorage.usdc`), and creators can be any unprivileged address that launches a token via `Bonding`, this is reachable without any special privilege.

### Recommendation
Add a beneficiary parameter to `claim()` (e.g., `claim(address to)`), restricted so only the balance owner (`msg.sender`) can trigger it but funds are sent to an address of their choosing, mirroring the recommendation in the referenced report. Alternatively, extend `transferCreator` (or add a dedicated `migrateCreatorBalance`) to move any outstanding `creatorBalance[oldCreator]` to the new creator address so a blacklisted creator can reroute funds via a fresh wallet.

### Proof of Concept
1. `depositor` (an allow-listed router such as `Zap`) calls `FeeVault.accrue(token, creator, creatorAmount, protocolAmount, isBuy)` repeatedly as trades occur, growing `creatorBalance[creator]`.
2. USDC's issuer blacklists `creator`'s address (e.g., due to an unrelated compliance action).
3. `creator` calls `FeeVault.claim()`; `usdc.safeTransfer(creator, amount)` reverts because `creator` is blacklisted (USDC blocks transfers to/from blacklisted addresses).
4. `creator` calls `Bonding.transferCreator(tokenAddress, newCreatorAddress)` hoping to redirect the balance — this only updates future fee attribution in `Bonding`'s `tokenInfo`, not `FeeVault.creatorBalance[creator]`, so `creatorBalance[creator]` remains keyed to the blacklisted address and stays permanently unclaimable.
5. The USDC corresponding to `creatorBalance[creator]` is now permanently stuck in `FeeVault` with no function capable of extracting it.

```text
    function claim() external nonReentrant returns (uint256 amount) {
        FeeVaultStorage storage $ = _s();
        amount = $.creatorBalance[msg.sender];
        if (amount == 0) revert NothingToClaim();
        $.creatorBalance[msg.sender] = 0;
        $.totalAccruedCreator -= amount;
        $.usdc.safeTransfer(msg.sender, amount);
        emit CreatorFeesClaimed(msg.sender, amount);
    }
```
