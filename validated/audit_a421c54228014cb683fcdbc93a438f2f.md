### Title
Webhook shop identity spoofing via header/body signature mismatch - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes and validates the webhook HMAC solely over the raw request body, while the `shop` field consumed by webhook handlers is read from an HTTP header that is never covered by that signature. This breaks the binding "shop verified by HMAC == shop attributed to the webhook", allowing a party who can obtain one genuine, validly-signed webhook for their own shop to relabel it as originating from an arbitrary victim shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, however, is derived entirely from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, which is not part of the signed bytes: [2](#0-1) 

`Registry.process` validates the HMAC against `request` (i.e., only the body) and then, once it passes, builds `WebhookMetadata` using `request.shop` — the unauthenticated header value — and hands it to the app's handler as trusted tenant identity: [3](#0-2) 

`HmacValidator.validate`/`validate_signature` only ever compares `to_signable_string` (the raw body) against the computed digest — it has no knowledge of, and does not bind, the `shop-domain` header: [4](#0-3) 

Because the HMAC signs only the body, any request that reuses a previously-observed valid `(raw_body, hmac)` pair for a given app will pass validation regardless of the `shop-domain` header value sent alongside it. Concretely, a merchant who has legitimately installed the app on their own store (an unprivileged actor with respect to any other tenant) will, over time, receive genuine webhooks from Shopify — each with a body and a valid HMAC computed using the app's `api_secret_key`. That merchant can capture one such `(raw_body, hmac)` pair and replay it directly to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a different, victim shop's domain. `Utils::HmacValidator.validate` still returns `true` (the body/HMAC pair is unchanged and valid), so `Registry.process` proceeds and invokes the handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain and `body` equal to the attacker's own webhook payload.

This is exactly the "bytes verified versus bytes parsed" identity-binding failure: the gem verifies the *body* bytes but hands the handler a *shop* value taken from bytes that were never verified, letting an unprivileged caller who can obtain any one valid signed body forge the tenant attribution for it.

### Impact Explanation
Any host application that relies on the gem's HMAC check as proof that `data.shop` in `WebhookHandler#handle` is authentic (which is the documented contract — `Registry.process` is described as verifying "the request did indeed come from Shopify" before dispatching) will process attacker-controlled data under an arbitrary victim shop's identity. Depending on how the handler uses `data.shop` (e.g., to select the tenant's database record, session, or downstream API scope), this enables cross-tenant data injection or corruption — writing/mutating data attributed to a shop the attacker does not control, using content the attacker fully chooses (their own webhook body). This meets the Critical bar of cross-tenant access via a documented gem primitive (`Registry.process` / `WebhookMetadata.shop`).

### Likelihood Explanation
The webhook HTTP endpoint is public and internet-reachable by design. The only prerequisite is that the attacker previously received at least one legitimate webhook for their own (attacker-owned) shop — trivial for anyone who installs a public app — after which the HMAC-valid body/signature pair can be replayed indefinitely with a different `shop-domain` header, since nothing in `lib/shopify_api/webhooks/**` binds the header to the signature.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `api-version`, `webhook-id`) header values in the signable string used by `Utils::HmacValidator`, or otherwise cryptographically bind the header-derived identity fields to the HMAC before they are exposed via `WebhookMetadata`. At minimum, document loudly that `data.shop` is unauthenticated and must not be trusted for tenant selection without an independent check against a known/installed shop.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and receives a genuine webhook, capturing `raw_body` and the valid `X-Shopify-Hmac-Sha256` header sent by Shopify.
2. Attacker POSTs to the app's webhook route with the exact same `raw_body`/`hmac` pair, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` parses `shop` as `victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `raw_body` against the (still-valid) HMAC: [5](#0-4) 
5. The registered handler is invoked with `WebhookMetadata(shop: "victim.myshopify.com", body: <attacker-controlled>, ...)`, and any tenant-scoped logic in the handler now operates on `victim.myshopify.com` using attacker-supplied data.
