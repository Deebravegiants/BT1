### Title
Webhook `shop` (and `topic`) identity is taken from unauthenticated headers, not bound to the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Registry.process` claims to "verify the request did indeed come from Shopify" before invoking the app's handler, but the HMAC it checks only covers the raw request body. The `shop` (and `topic`) values that are handed to the app's handler as the trusted tenant identifier are read straight from HTTP headers that are never included in the signed material, breaking the binding `HMAC-verified bytes == tenant identity acted upon`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from HTTP headers with no cryptographic binding to that body: [2](#0-1) 

`Registry.process` validates only the body/HMAC pair, then constructs the handler payload using the unauthenticated `request.shop`/`request.topic`: [3](#0-2) 

`HmacValidator.validate` computes `HMAC(secret, to_signable_string)` and compares it to the `hmac` header — again, this only proves the *body* bytes were signed by someone holding `api_secret_key`; it says nothing about which shop or topic that signature was intended for: [4](#0-3) 

Because a single app has one `api_secret_key` shared across every installed shop, any legitimately-signed `(body, hmac)` pair — e.g., one an attacker obtains from a webhook fired by their own store, or from a topic they can freely trigger — remains valid under `HmacValidator.validate` no matter what `shop-domain`/`topic` headers accompany it. An unprivileged internet user who can send arbitrary HTTP requests to the app's public webhook endpoint can therefore replay a validly-signed body while substituting the `X-Shopify-Shop-Domain` header for a victim shop's domain (and/or the `X-Shopify-Topic` header for a different registered topic). `Registry.process` will pass HMAC validation and invoke the handler with `WebhookMetadata` claiming the payload originated from the victim shop: [5](#0-4) 

The gem's own documentation reinforces that host apps are meant to trust this verification step completely ("This will verify the request did indeed come from Shopify"), i.e. this is a documented API guarantee of the gem, not something the host app is expected to independently re-check.

### Impact Explanation
This breaks the identity binding: `shop authenticated by HMAC` ≠ `shop stored/acted upon as the tenant key`. A host app that trusts `data.shop`/`data.topic` (as the gem's own docs instruct it to) can be made to process attacker-supplied webhook content under an arbitrary victim shop's identity — e.g., triggering `app/uninstalled` handling, order/product mutation jobs, or any per-shop side effect keyed off `data.shop`, for a shop the attacker does not own. This is a cross-tenant confusion vulnerability reachable by any unprivileged internet user who can POST to the app's public webhook endpoint, without needing any credentials.

### Likelihood Explanation
Exploitation requires only: (1) a validly-signed `(body, hmac)` pair, obtainable by triggering any webhook on the attacker's own installed shop (attacker fully controls this, no privileges needed against the victim), and (2) an unauthenticated HTTP POST to the target app's public webhook route with the `shop-domain`/`topic` headers swapped. Both prerequisites are trivially satisfiable by any internet user, making this a straightforward abuse of the gem's documented "verified" webhook flow.

### Recommendation
Bind the shop (and ideally the topic) into the material that is actually verified — e.g., require callers to pass the expected shop for the endpoint/session being processed and compare it against `request.shop` before trusting it, or include shop/topic in the signable payload used for HMAC comparison, rather than relying solely on `@raw_body`. At minimum, the documentation and `Registry.process` should not represent the shop/topic as verified when only the body has been authenticated; host apps must be explicitly told to independently corroborate `data.shop` against a known/installed shop record.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com` and `victim-shop.myshopify.com`, both governed by the same app `api_secret_key`.
2. Attacker triggers a real webhook on their own shop (e.g. `orders/create`), capturing the raw POST body and the legitimate `X-Shopify-Hmac-Sha256` header Shopify sent.
3. Attacker POSTs that exact body + hmac header to the app's webhook endpoint, but sets:
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
   - `X-Shopify-Topic: orders/create` (or any registered topic)
4. `ShopifyAPI::Webhooks::Request.new` parses these headers unmodified; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `HMAC(secret, raw_body)`.
5. The registered handler is invoked with `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: <attacker's own order data>, ...)`, causing the host application to process attacker-controlled content under the victim shop's tenant identity.
