### Title
Webhook `shop` field is passed to handlers without being covered by the HMAC signature, allowing cross-tenant shop spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable payload from only the raw request body [1](#0-0) , while the `shop` value used downstream by `Registry.process` and forwarded to the app's `WebhookHandler` is read directly from an unauthenticated HTTP header [2](#0-1) . `Utils::HmacValidator.validate` only checks that the HMAC matches `to_signable_string` (the raw body) [3](#0-2) , so the `shop-domain` header is never part of the signed data.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` validates the webhook solely via `Utils::HmacValidator.validate(request)`, then immediately builds a `WebhookMetadata` object using `request.shop`, `request.topic`, and `request.parsed_body`, and dispatches it to the registered handler [4](#0-3) . The `WebhookMetadata` struct stores this `shop` value as the tenant identifier that the host application's `WebhookHandler#handle` implementation uses to determine which shop's data the webhook body applies to [5](#0-4) .

The identity binding that should hold is: `shop used to validate HMAC == shop the handler acts on`. Because `Request#to_signable_string` returns only `@raw_body` [1](#0-0)  and `Request#shop` is parsed from the `shopify-shop-domain`/`x-shopify-shop-domain` header without any cryptographic binding to that body [2](#0-1) , the two sides of that equality are never actually verified together. An attacker who controls a shop that has installed the vulnerable app (an "unprivileged" tenant relative to other merchants) receives genuine webhook deliveries with a valid HMAC over the body. Because the HMAC never covers the shop header, the attacker can capture such a delivery and replay the identical `raw_body` + `hmac-sha256` value while substituting the `shop-domain` header with a victim shop's domain. `HmacValidator.validate` will still return `true` (the body/HMAC pair is legitimately signed), and `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload came from the victim shop [6](#0-5) .

This is the same bug class as the reported issue: a value that is *acted upon* (the escrow pool address vs. the escrow portion; here, the `shop` tenant identifier vs. the signed body) is not covered by the integrity check (HMAC/escrow-pool-set check), letting an attacker cause the trusted code path to associate attacker-controlled data with a different identity than what was actually authenticated.

### Impact Explanation
If a host application's `WebhookHandler#handle` implementation trusts `data.shop` (as the gem's own documentation and struct design encourage) to select which merchant's database row/record to update, delete, or redact — for example, mandatory `shop/redact`, `customers/redact`, `customers/data_request` topics used for GDPR compliance, which every app using this gem must implement [7](#0-6)  — an attacker-shop can forge webhook deliveries that are misattributed to a victim shop. This crosses a tenant boundary: data belonging to/affecting the attacker's own shop can be injected into another shop's context (or a redact/erase action for the attacker's shop can be triggered against a different shop's data), which is a cross-tenant access impact.

### Likelihood Explanation
Exploitation requires the attacker to control a shop that has installed the target app (to receive at least one legitimately HMAC-signed webhook body) and to be able to POST directly to the app's public webhook endpoint with a modified `shop-domain` header — both of which are realistic since webhook endpoints are unauthenticated public HTTP endpoints and any merchant can install a public app. No access to the app's `client_secret` or another merchant's credentials is required, satisfying the unprivileged-attacker constraint.

### Recommendation
Bind the `shop` header (and other headers relied upon for identity/authorization decisions, e.g., `topic`, `webhook-id`) into the signed payload used for HMAC verification, e.g. include them in `to_signable_string`, or require the caller to independently confirm `request.shop` against a shop already known to be installed/subscribed to that specific webhook topic/id before trusting it in `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a webhook (e.g. `orders/create`), capturing the raw POST body and the `X-Shopify-Hmac-Sha256` header.
2. Attacker resends this exact body and HMAC header to the app's webhook endpoint, but replaces `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate(request)` returns `true` because verification only checks the raw body against the HMAC [8](#0-7) [9](#0-8) .
4. `Registry.process` builds `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker's body>, ...)` and invokes the handler [10](#0-9) , causing the host app to act on attacker-controlled data under the identity of the victim shop.
