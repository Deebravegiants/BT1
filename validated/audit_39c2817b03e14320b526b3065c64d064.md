### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by verifying the HMAC over the raw request body, while the `shop` (and `topic`/`webhook_id`) values that the application actually acts on come from HTTP headers that are never included in the signed bytes. This mirrors the report's bug class: a field that is *used* (the "owner"/tenant identity) is not the field that is *cryptographically bound* (the "locked" state). An attacker who can obtain one genuine `(raw_body, hmac)` pair signed with the app's own `client_secret` (e.g. by installing the app on their own store) can replay that exact body/HMAC pair to the app's webhook endpoint while swapping the `shop-domain` header to a victim shop, and the request will pass verification and be dispatched to the app's handler as if it originated from the victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request` exposes several attributes taken directly from HTTP headers — `shop`, `topic`, `webhook_id`, `api_version` — none of which participate in the value that is HMAC-verified: [1](#0-0) [2](#0-1) 

`to_signable_string` returns only `@raw_body`; `shop` (the `shop-domain` header) is not part of the signable string. `Registry.process` verifies the request using `Utils::HmacValidator.validate`, which computes `HMAC(secret, to_signable_string)` and compares it to the header-provided digest, then unconditionally trusts `request.shop`, `request.topic`, and other header-derived fields when building `WebhookMetadata` for the handler: [3](#0-2) [4](#0-3) 

The identity binding that should hold is: `HMAC-verified bytes == bytes the handler trusts for the tenant ("shop")`. Here that equality is broken — the HMAC only certifies the JSON body content came from someone who possesses the `client_secret` (i.e., was originally sent by Shopify for *some* shop), it does not certify *which* shop the body pertains to. `Registry.process` and the documented handler contract (`data.shop`) both treat the header `shop` as authoritative: [5](#0-4) [6](#0-5) 

Any unprivileged user who can install the target app on their own store (a normal, unprivileged action any merchant can take) will receive genuine webhooks whose body/HMAC pair is valid under the app's real `client_secret` — no leaked or privileged credential is required, only ordinary app installation. That attacker can then capture the raw body and `x-shopify-hmac-sha256` header from a real webhook (for a topic they control, e.g. `orders/create` on their own shop), and replay the exact same body+HMAC to the app's public webhook endpoint with the `x-shopify-shop-domain` header set to an arbitrary victim shop domain. `HmacValidator.validate` will still succeed because it only checks the body, and the handler will process attacker-supplied JSON content under the identity of the victim shop.

### Impact Explanation
This qualifies as cross-tenant access (Critical): it lets an unprivileged app installer inject fabricated webhook events attributed to any other shop the app services, with content the attacker fully controls (subject to Shopify's payload schema for the topic). Depending on how the host app's handler acts on `data.shop`/`data.body` (e.g. updating per-shop records, triggering `customers/redact` or `shop/redact` compliance flows, altering order/customer state keyed by `shop`), this can corrupt or exfiltrate another tenant's data purely through a header value that was never authenticated.

### Likelihood Explanation
Likelihood is high for any app that keys business logic off `data.shop` from `WebhookMetadata` (which is the gem's documented pattern) and exposes a public webhook endpoint, since obtaining one genuine signed body only requires installing the app on an attacker-controlled test shop — a capability any anonymous merchant has.

### Recommendation
Include the tenant identity in the HMAC-protected material, or otherwise cryptographically bind `shop` to the verified payload — since the raw JSON body from Shopify webhooks already contains the shop's domain/ID for most topics, the header-derived `shop` used in `WebhookMetadata` should be cross-checked against a value taken from the verified body (or the header itself should be included in `to_signable_string` before comparing HMACs). At minimum, document to consumers that `data.shop` is unauthenticated header data and must not be trusted for authorization decisions without additional validation.

### Proof of Concept
1. Install the target app on attacker-controlled store `attacker.myshopify.com`; trigger a webhook (e.g. `orders/create`) to capture a genuine `raw_body` and its `x-shopify-hmac-sha256` value, both signed with the app's real `client_secret`.
2. POST to the app's public webhook endpoint with:
   - `x-shopify-hmac-sha256`: the captured (still-valid) HMAC value
   - `x-shopify-topic`: unchanged
   - `x-shopify-shop-domain`: `victim-shop.myshopify.com`
   - body: the captured `raw_body` unchanged
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate`, which recomputes the HMAC over `raw_body` only [2](#0-1)  and finds it matches, so the check in `process` passes [7](#0-6) .
4. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and the attacker-controlled body, and executes tenant-scoped logic as though it were a legitimate event for the victim shop.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
