## Title
Precision loss / silent zero-value delivery in `convert_to_balance` truncates dust cross-chain transfers to zero, permanently losing user funds - (File: `modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
`pallet-hyper-fungible-token`'s `on_accept` handler converts an incoming ERC20-denominated amount to the local balance denomination via integer division in `convert_to_balance`. When the source-chain ERC20 amount is smaller than the scale factor `10^(erc_decimals - local_decimals)`, the division truncates the result to zero, silently crediting the beneficiary with `0` tokens while the funds were already burned/escrowed on the source chain and cannot be recovered, since the message is processed successfully (not timed out).

### Finding Description
`convert_to_balance` performs plain integer division with no dust/remainder check: [1](#0-0) 

This is invoked in the ISMP `on_accept` handler of the pallet, which is reached whenever a relayer delivers a valid cross-chain post request from a registered `HyperFungibleToken`/`WrappedHyperFungibleToken` contract: [2](#0-1) 

The `BridgeToken` EVM contract documents that its ERC20 representation uses 18 decimals while the corresponding asset on nexus is only 12 decimals, i.e. `erc_decimals - local_decimals = 6`: [3](#0-2) 

Any incoming message whose `amount` (18-decimal ERC20 units) is below `1e6` — i.e. any dust transfer under `0.000001` token — divides to `0` in `convert_to_balance`, and the pallet proceeds to transfer/mint `0` to the beneficiary without reverting, error, or refund path: [4](#0-3) 

Because the source-side EVM contract already burned/locked the sender's tokens before dispatching the request (this happens in the EVM `send`/burn path, independent of what the destination does with the amount), and the request is considered successfully delivered (not eligible for timeout-based refund), the value is permanently lost. The exact same truncation-without-guard also exists in the `on_timeout` refund path, which reuses `convert_to_balance` identically: [5](#0-4) 

This is a direct analog of the reported `mintForToken` bug: precision loss when the destination denomination is more coarse than the source denomination, and small (sub-scale-factor) amounts round down to zero, and unlike simple "dust rounding" this occurs on an unprivileged, permissionlessly reachable bridge mint/transfer path (any token holder can trigger a bridge `send` for an arbitrary small amount, and a relayer delivering that legitimate message triggers the truncation).

### Impact Explanation
Any user (or an attacker griefing other users, or an automated system moving very small residual balances) who bridges an amount smaller than the decimal scale factor between the EVM ERC20 representation and the local substrate asset denomination has their funds burned/escrowed on the source chain but receives nothing on the destination chain, with no revert and no timeout-eligible refund. This is a genuine, unrecoverable loss of user funds on the core token bridge mint/burn path — squarely within the "token bridge mint/burn" reachable-path category.

### Likelihood Explanation
The scale factor is not attacker-controlled but is a normal consequence of assets registered with differing decimals across chains (explicitly the case for the shipped `BRIDGE` token, 18 vs 12 decimals, scale factor `1e6`). Any transfer amount under the scale factor threshold — trivially achievable by any unprivileged sender, intentionally or accidentally — triggers the loss deterministically, with no special preconditions, privileged roles, or complex sequencing required.

### Recommendation
In `convert_to_balance` (and consequently in `on_accept`/`on_timeout`), reject (revert the request) or explicitly disallow conversions that produce a zero balance when the input amount is non-zero, e.g. by returning an error such as `Error::AmountTooSmallForPrecision` when `value != 0 && converted == 0`. This causes the relayer to receive a failure rather than the pallet silently minting/transferring zero, preserving the invariant that a non-zero remote amount always yields a non-zero, correctly-scaled local credit (or an explicit, auditable failure instead of silent fund loss).

### Proof of Concept
1. Register a token/asset where `erc_decimals = 18` and local `decimals = 12` (as documented for `BridgeToken`, scale factor `10^6`), configured in `Precisions` via `register_token`.
2. From the EVM side, a user calls `send`/bridges an amount of `500_000` wei (i.e., `5e5 < 1e6`) of the ERC20 token to nexus; the EVM contract burns/locks this amount from the sender.
3. A relayer delivers the resulting ISMP post request to the pallet; `on_accept` is invoked, calling:
   `convert_to_balance(U256::from(500_000), 18, 12)` → `500_000 / 10^6 = 0` (integer division).
4. `amount = 0` is used to `transfer`/`mint_into` the beneficiary, emitting `TokenReceived { amount: 0, .. }`.
5. The message is marked delivered/successful; the sender's `500_000` wei is permanently lost with the beneficiary receiving `0` tokens and no refund mechanism available (the request did not time out).

/// Converts an ERC20 U256 amount to a local balance type
///
/// Divides by 10^(erc_decimals - local_decimals) to scale down from ERC20 precision.
/// The target type must implement `FromStr`.
pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}
