### Title
Webhook `shop` identity is trusted from an unauthenticated header while the HMAC only signs the body — cross-tenant webhook confusion - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` exposes a `shop` value that comes straight from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, but the HMAC signature that `Registry.process` validates is computed only over the raw request body, never over that header. The gem therefore accepts and forwards a shop identity that is not bound by the cryptographic check meant to authenticate the request.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read from an HTTP header that is not part of that signable string: [2](#0-1) 

`HmacValidator.validate` / `validate_signature` compute the HMAC purely from `verifiable_query.to_signable_string` (the body) and compare it to the `hmac` header: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` (and `request.topic`, `request.webhook_id`, `request.api_version`, none of which are signed either) to build the `WebhookMetadata` handed to the app's handler: [4](#0-3) [5](#0-4) 

The identity binding that should hold is:
`bytes covered by HMAC == bytes used to authenticate the tenant (shop)`

In this implementation, the actual equality is:
`bytes covered by HMAC == raw_body only`
`shop trusted by the handler == shopify-shop-domain header (unsigned)`

These are not the same set of bytes, so the `shop` field can diverge from what was actually authenticated.

### Impact Explanation
Any entity that can install the app on their own store (an "unprivileged internet user" relative to any *other* merchant's tenant) receives genuine, correctly-HMAC-signed webhook deliveries from Shopify for their own shop. Because the app's shared `client_secret`/`api_secret_key` is the same for every installation of the app (it is not shop-specific), a valid `hmac` for one shop's webhook body remains a valid `hmac` for the exact same body regardless of which `shop-domain` header accompanies it — the header is never covered by the signature. An attacker who owns Shop A can capture their own legitimately-signed webhook request and replay it to the app's webhook endpoint with the `x-shopify-shop-domain` header swapped to Shop B (or any target shop). The gem's `HmacValidator.validate` still returns `true` because it only checks the (unmodified) body, and `Registry.process` passes the attacker-controlled `shop` value straight to the handler via `WebhookMetadata#shop`.

If the host application uses `WebhookMetadata#shop` to key tenant-scoped data (e.g., write order/customer data under that shop's record, or use it to look up/mutate the session/access-token associated with that shop), the attacker can inject content into another merchant's tenant context using their own genuinely-signed payload — a cross-tenant confusion primitive rooted entirely in this gem's webhook verification/parsing logic.

### Likelihood Explanation
The precondition (installing the target app on an attacker-controlled store to obtain genuinely signed webhook traffic, then replaying it with a modified header to the same public webhook endpoint) requires no privileged credentials, no access token, and no knowledge of `api_secret_key`/`client_secret` — the attacker only needs their own shop's real webhook deliveries, which any app installer naturally receives. It does depend on the host application actually branching tenant-sensitive logic on `WebhookMetadata#shop` without independently correlating body content to the claimed shop, which is a very common integration pattern (this is exactly why the gem hands `shop` to the handler in the first place).

### Recommendation
Bind the shop (and topic/webhook id) to the authenticated bytes, not to an unauthenticated header:
- Include `shop`, `topic`, and `webhook_id` in the signable string used by `HmacValidator`, or
- Cross-check the header `shop` against a shop identifier embedded in the verified JSON body (most Shopify webhook payloads carry a shop-scoped resource), and reject the webhook if they disagree, or
- At minimum, document prominently that `WebhookMetadata#shop` is not authenticated by the HMAC and must not be trusted to select tenant context without additional verification (e.g., cross-referencing against the shop that owns the registered webhook subscription id).

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`.
2. Shopify sends a legitimate webhook to the app's callback URL, with body `B` and header `x-shopify-hmac-sha256: HMAC(secret, B)`, `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker intercepts/replays this exact request to the same endpoint, changing only `x-shopify-shop-domain` to `victim.myshopify.com` (and, if desired, the `x-shopify-webhook-id`).
4. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC solely from `request.to_signable_string` (`B`) — the signature still matches because the header was never part of the signed content: [6](#0-5) 
5. Validation passes; the handler receives `WebhookMetadata.new(..., shop: "victim.myshopify.com", body: parsed body B, ...)`, i.e., attacker-controlled body content is now attributed to the victim's tenant: [7](#0-6)
