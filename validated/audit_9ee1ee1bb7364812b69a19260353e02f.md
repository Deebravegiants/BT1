### Title
Direct-transfer donation to `amm_coin_vault`/`amm_pc_vault` causes zero-LP-mint DoS on `Deposit` - (File: `program/src/processor.rs`)

### Summary
The `Deposit` instruction mints LP tokens by computing a ratio between the amount deposited and the *raw current balance* of the AMM's coin/pc vaults, then flooring the result. Because the vaults are plain SPL token accounts, any unprivileged actor can transfer tokens into them directly (outside of `Deposit`), inflating the vault balances relative to `amm.lp_amount`. This is functionally the same "MinShares"/donation attack class described in the Ethena StakedUSDe report: an attacker manipulates the exchange-rate denominator so that a legitimate depositor's `mint_lp_amount` calculation floors to `0`, and the instruction reverts, denying service to depositors until they deposit disproportionately large (and increasingly expensive) amounts.

### Finding Description
In `process_deposit`, the pool computes the current reserves directly from the live vault token accounts via `Self::unpack_token_account` and `Calculator::calc_total_without_take_pnl_no_orderbook`, then computes the LP amount to mint as a floor-rounded ratio against those reserves: [1](#0-0) [2](#0-1) [3](#0-2) 

If the computed `mint_lp_amount` is `0`, the instruction explicitly reverts with `AmmError::InvalidInput`: [4](#0-3) 

The vaults referenced (`amm_coin_vault_info`, `amm_pc_vault_info`) are ordinary SPL token accounts owned by the AMM authority PDA, created once at pool init: [5](#0-4) 

Because SPL Token transfers only require the *source* owner to sign — not the destination — any unprivileged user can call the SPL Token program directly (outside of the Raydium program) to transfer arbitrary amounts of the coin or pc mint straight into `amm_coin_vault` / `amm_pc_vault`. This is exactly analogous to the `USDe` direct-transfer-to-`StakedUSDe` donation described in the external report: the balance used for exchange-rate/shares calculation (`totalAssets()` in StakedUSDe, `total_coin_without_take_pnl`/`total_pc_without_take_pnl` here) is read as the raw token balance of the vault rather than an internally tracked "deposited" amount, so a donation inflates the denominator without minting any corresponding LP/shares. Once the ratio of vault balance to `amm.lp_amount` is pushed high enough, `InvariantPool::exchange_token_to_pool` with `RoundDirection::Floor` rounds legitimate deposit amounts down to `0`.

### Impact Explanation
A successful attack denies normal `Deposit` functionality for the pool: legitimate LPs attempting reasonable deposit sizes will have their `mint_lp_amount` computed as `0` and their transaction reverted with `AmmError::InvalidInput`, exactly mirroring the `MinSharesViolation` DoS pattern in the source report. To restore the ability to deposit, a user would need to deposit an amount large enough (proportional to the attacker's donation) to clear the floor-rounding threshold, which — as in the original report — can require a "substantial amount" of capital, effectively freezing liquidity provisioning for the pool for typical-sized depositors. This is a availability/DoS impact on LP funds flow rather than direct fund theft, consistent with Medium severity in the referenced finding.

### Likelihood Explanation
The attack is reachable by any unprivileged user in a single transaction using only a standard SPL Token transfer CPI to a publicly known, non-privileged destination (the AMM's `amm_coin_vault`/`amm_pc_vault`, whose addresses are public on-chain accounts once the pool is initialized). No signer privileges, leaked keys, or special build/runtime conditions are required — only knowledge of the target pool's vault addresses and enough tokens of the relevant mint, which is cheaper the smaller `amm.lp_amount` is (e.g., shortly after pool creation) or on low-liquidity pools generally.

### Recommendation
Do not derive the LP-mint ratio purely from the raw, externally-transferable vault token balances. Track pool reserves via internal accounting that is only updated through `Deposit`/`Withdraw`/swap instructions (or reconcile/ignore un-accounted-for balance deltas), and/or enforce a minimum non-zero `mint_lp_amount` check with a clear, documented minimum-deposit requirement so that floor-rounding-to-zero cannot silently deny deposits after a donation. Rejecting deposits that would mint `0` LP is already done, but the underlying reserve values feeding that computation should not be trivially inflatable by unprivileged direct transfers.

### Proof of Concept
1. Attacker identifies an existing Raydium pool with a relatively small `amm.lp_amount` (e.g., a newly created pool) and reads `amm.coin_vault` / `amm.pc_vault` addresses from the on-chain `AmmInfo` account.
2. Attacker issues a plain `spl_token::instruction::transfer` (or `transfer_checked`) CPI, sending a modest amount of the coin or pc mint directly to `amm_coin_vault` (no interaction with the Raydium program, no signature needed from the vault owner).
3. This inflates `amm_coin_vault.amount`/`amm_pc_vault.amount` as read by `Self::unpack_token_account` in the next `Deposit` call, at line [6](#0-5) , without any corresponding increase to `amm.lp_amount`.
4. A legitimate LP then calls `Deposit` with a normal-sized `max_coin_amount`/`max_pc_amount`. The computed `mint_lp_amount` via `InvariantPool::exchange_token_to_pool(amm.lp_amount, RoundDirection::Floor)` at [7](#0-6)  floors to `0`.
5. The instruction reverts with `AmmError::InvalidInput` at [8](#0-7) , denying the deposit until the user provides a disproportionately larger amount, reproducing the same DoS effect described in the referenced StakedUSDe `MinSharesViolation` finding.
