### Title
Webhook `shop-domain` Header Is Not Covered by HMAC Verification, Enabling Cross-Tenant Webhook Spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content solely from the raw request body, while the `shop` (tenant identifier) used by the webhook handler is read from an unauthenticated header. Because the shop identity is never part of the signed bytes, an attacker who legitimately triggers webhook events from a shop they control can capture a validly-signed body/HMAC pair and replay it with a substituted `shop-domain` header, causing the host application's webhook handler to attribute the payload to a different (victim) merchant.

### Finding Description
`Webhooks::Registry.process` validates a webhook only by checking the HMAC over the body: [1](#0-0) [1](#0-0) 

```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
```

`HmacValidator.validate` calls `to_signable_string`, which for `Webhooks::Request` returns only the raw body: [2](#0-1) 

```ruby
sig { override.returns(String) }
def to_signable_string
  @raw_body
end
```

Meanwhile `shop` is parsed directly from the unauthenticated `shopify-shop-domain` / `x-shopify-shop-domain` header: [3](#0-2) 

```ruby
sig { returns(String) }
def shop
  T.cast(shopify_header("shop-domain"), String)
end
```

Both `topic` and `webhook_id` are similarly taken from headers not covered by the signature. The identity binding that should hold is:

`bytes verified by HMAC == bytes the handler uses to identify the tenant (shop)`

but here the verified bytes are only `@raw_body`, while the tenant-identifying `shop` field is parsed independently from headers and passed straight into `WebhookMetadata` for the handler to act on — breaking that equality. This matches the report's bug class: "a field acted on but not covered by the HMAC."

### Impact Explanation
This is a cross-tenant data-integrity/confusion vulnerability. Any user with a Shopify store that installs the app (i.e., a normal, unprivileged merchant, not the app owner) receives genuinely-signed webhooks for their own store events — signed with the app's `client_secret`/`api_secret_key` by Shopify itself. Because the signature only covers the body and not the `shop-domain` header, that same attacker can resend the identical signed body to the app's webhook endpoint while swapping the `shop-domain` header to a victim shop's domain. `HmacValidator.validate` will still pass (the body bytes are unchanged), but `Registry.process` will hand the handler a `WebhookMetadata` claiming the data belongs to the victim shop. Any host application that trusts `request.shop`/`WebhookMetadata#shop` to select which merchant's records to create/update/delete (the gem's documented usage pattern) will process or store data under the wrong tenant, i.e., cross-tenant data injection/corruption.

### Likelihood Explanation
Likelihood is high for any app that relies on this gem's webhook verification as an authenticity guarantee of the full webhook context (topic + shop + body), which is the documented usage pattern in `docs/`. All an attacker needs is their own (potentially free/dev) shop with the app installed to legitimately receive a signed webhook, then a single HTTP replay with modified headers to the app's public webhook endpoint. No access to `api_secret_key`, tokens, or the target shop is required.

### Recommendation
Include the identity-critical headers (`shop-domain`, `topic`, and ideally `webhook_id`/`api_version`) in the HMAC-signable content, or otherwise cryptographically bind them to the body before verification, so that `HmacValidator.validate` fails if any of these headers are altered. At minimum, document and warn that `request.shop`/`topic` are not authenticated by the HMAC and must not be trusted for tenant selection without an independent verification step (e.g., cross-checking against a known/registered shop for that webhook subscription).

### Proof of Concept
1. Install the app on an attacker-controlled shop `attacker.myshopify.com`.
2. Trigger a webhook event (e.g., `orders/create`) on that shop; Shopify sends a POST with a valid `x-shopify-hmac-sha256` computed over the JSON body using the app's real `api_secret_key`.
3. Capture the request; keep the body and `x-shopify-hmac-sha256` unchanged, but replace `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
4. Replay the modified request to the app's webhook endpoint. `ShopifyAPI::Utils::HmacValidator.validate` (see `lib/shopify_api/utils/hmac_validator.rb:13-22`) succeeds because it only checks `@raw_body`; `Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-199`) then invokes the app's handler with `shop: "victim-shop.myshopify.com"`, causing the host app to process attacker-supplied data as if it originated from the victim shop.
