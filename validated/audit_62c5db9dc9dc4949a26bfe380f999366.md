## Title
OAuth callback (`ShopifyAPI::Auth::Oauth.validate_auth_callback`) sends the app's `client_secret` to a shop host that is never checked against `ShopValidator` - ([File: lib/shopify_api/auth/oauth.rb])

### Summary
`ShopifyAPI::Auth::ClientCredentials.client_credentials` and `ShopifyAPI::Auth::RefreshToken.refresh_access_token` both call `Utils::ShopValidator.sanitize!(shop)` before building the `Session` that is used to target the `/admin/oauth/access_token` host, but `ShopifyAPI::Auth::Oauth.validate_auth_callback` skips this check entirely and builds the session (and therefore the HTTP request host) directly from the untrusted `auth_query.shop` value.

### Finding Description
The security invariant the gem otherwise enforces elsewhere is: `session.shop == ShopValidator.sanitize!(raw_shop)`, i.e. the host that ultimately receives the app's `client_secret` must be a Shopify-trusted domain (`myshopify.com`, `shopify.com`, `myshopify.io`, `spin.dev`, `shop.dev` or the configured `myshopify_domain`) as defined in `lib/shopify_api/utils/shop_validator.rb`. `ClientCredentials.client_credentials` [1](#0-0)  and `RefreshToken.refresh_access_token` [2](#0-1)  both call `validated_shop = Utils::ShopValidator.sanitize!(shop)` and then build `Session.new(shop: validated_shop)`, which the `Clients::HttpClient` uses to derive the request host (`@base_uri = "https://#{api_host || session.shop}"`) [3](#0-2) .

`Oauth.validate_auth_callback`, however, never calls `ShopValidator` at all: [4](#0-3) 

It only verifies the HMAC over `auth_query` (covering `code`, `host`, `shop`, `state`, `timestamp` per `AuthQuery#to_signable_string` [5](#0-4) ) and then immediately does:
```
null_session = Auth::Session.new(shop: auth_query.shop)
...
client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
```
passing `client_id`/`client_secret` in the POST body to whatever host `auth_query.shop` resolves to. `Auth::Session#initialize` itself performs no validation on `shop` [6](#0-5) .

Because HMAC validity depends only on `Context.api_secret_key` (the app's own secret, known to the app but not to Shopify-external attackers in a way that would let them forge signatures without it), an attacker cannot forge an arbitrary `shop` value through the HMAC check by itself. However, the code that consumes `auth_query.shop` treats "HMAC-verified" as equivalent to "trusted host to send `client_secret` to," which is the same binding class the other two OAuth-adjacent flows explicitly guard against with `ShopValidator.sanitize!`. `begin_auth` compounds this: it builds `auth_base_uri(shop)` directly from a caller-supplied `shop` with **no HMAC and no `ShopValidator` check at all** [7](#0-6) , so a caller who plumbs an unsanitized `shop` (as the gem's own documented `getting_started`/`oauth.md` example does: `shop = request.headers["Shop"]`) into `begin_auth` will have the resulting `state` (nonce) cookie set and the browser redirected to `auth_base_uri(shop) + "/oauth/authorize?..."` — an attacker-chosen host — before any HMAC exists. If that host is attacker-controlled and mimics Shopify's OAuth authorize+redirect flow, it can still complete the redirect back to the app's `redirect_uri` with a `code`/`hmac` pair that only Shopify could produce, so `client_secret` exfiltration via this exact path still requires Shopify's cooperation and is not by itself exploitable purely from the library's code without the host application also failing to validate/sanitize the initial `shop` value (per the "reject analogs that depend on the host application ignoring this gem's documented API" rule).

### Impact Explanation
This maps to the "SSRF with the app's credentials" impact class: the `client_secret` is sent in a POST body to a host derived from `auth_query.shop`/`shop`, and that host is not validated against `ShopValidator.TRUSTED_SHOPIFY_DOMAINS` inside `validate_auth_callback`/`begin_auth`, unlike the parallel `client_credentials`/`refresh_access_token` flows in the same gem which explicitly enforce this binding.

### Likelihood Explanation
Low-to-Medium. The `validate_auth_callback` path is gated by a correct HMAC (which requires possession of `api_secret_key`, out of scope per the rules), so a pure "unprivileged internet user" cannot exploit that specific call in isolation. The `begin_auth` path has no such gate, but exploiting it to leak `client_secret` still requires the host application to pass through an unsanitized shop param and requires attacker infrastructure to complete a plausible-looking OAuth redirect loop, so it is not a fully self-contained exploit within this gem's code alone.

### Recommendation
Add `Utils::ShopValidator.sanitize!(shop)` calls in both `Oauth.begin_auth` (before constructing `auth_base_uri`) and `Oauth.validate_auth_callback` (before constructing `null_session`), mirroring the pattern already used in `ClientCredentials.client_credentials` and `RefreshToken.refresh_access_token`, so the shop-to-host binding is enforced consistently across all OAuth-related client_secret-sending code paths.

### Proof of Concept
Not independently reproducible as a self-contained exploit purely through this gem's code without either (a) knowledge of `api_secret_key` for `validate_auth_callback`, or (b) a host application that forwards an unsanitized `shop`/`Shop` header into `begin_auth`, both of which fall under the excluded categories (`requiring api_secret_key`, or "depend[ing] on the host application ignoring this gem's documented API"). No further concrete PoC can be constructed within scope.

        def begin_auth(shop:, redirect_path:, is_online: true, scope_override: nil)
          scope = if scope_override.nil?
            ShopifyAPI::Context.scope
          elsif scope_override.is_a?(ShopifyAPI::Auth::AuthScopes)
            scope_override
          else
            ShopifyAPI::Auth::AuthScopes.new(scope_override)
          end

          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = SecureRandom.alphanumeric(NONCE_LENGTH)

          cookie = SessionCookie.new(value: state, expires: Time.now + 60)

          query = {
            client_id: ShopifyAPI::Context.api_key,
            scope: scope.to_s,
            redirect_uri: "#{ShopifyAPI::Context.host}#{redirect_path}",
            state: state,
            "grant_options[]": is_online ? "per-user" : "",
          }

          query_string = URI.encode_www_form(query)
          auth_route = auth_base_uri(shop) + "/oauth/authorize?#{query_string}"

          { auth_route: auth_route, cookie: cookie }
        end

        def validate_auth_callback(cookies:, auth_query:)
          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state

          null_session = Auth::Session.new(shop: auth_query.shop)
          body = {
            client_id: Context.api_key,
            client_secret: Context.api_secret_key,
            code: auth_query.code,
            expiring: Context.expiring_offline_access_tokens ? 1 : 0, # Only applicable for offline tokens
          }

          client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
          response = begin
            client.request(
              Clients::HttpRequest.new(
                http_method: :post,
                path: "access_token",
                body: body,
                body_type: "application/json",
              ),
            )
          rescue ShopifyAPI::Errors::HttpResponseError => e
            raise Errors::RequestAccessTokenError,
              "Cannot complete OAuth process. Received a #{e.code} error while requesting access token."
          end

          session_params = T.cast(response.body, T::Hash[String, T.untyped]).to_h
          session = Session.from(shop: auth_query.shop,
            access_token_response: Oauth::AccessTokenResponse.from_hash(session_params))
