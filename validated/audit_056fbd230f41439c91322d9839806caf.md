Webhook `shop-domain` header is not covered by the HMAC, allowing cross-tenant shop spoofing on replayed webhooks - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable content from the raw body only, excluding the `shop-domain` header, yet `Webhooks::Registry.process` trusts `request.shop` unconditionally when dispatching to the registered handler.

### Finding Description
`Webhooks::Request#to_signable_string` returns just `@raw_body`: [1](#0-0) 

The `shop` accessor pulls straight from the (unauthenticated) `shopify-shop-domain`/`x-shopify-shop-domain` header, which is never mixed into the signable string: [2](#0-1) 

`Utils::HmacValidator.validate` only verifies `verifiable_query.to_signable_string` (i.e., the body) against `verifiable_query.hmac`: [3](#0-2) 

`Registry.process` checks this HMAC and then immediately passes the unauthenticated `request.shop` value into `WebhookMetadata`, which the host application's handler uses to attribute the payload to a tenant: [4](#0-3) 

The binding that should hold is: `shop-domain header == shop that produced (body, hmac)`. Because the HMAC is computed over the body only, any `(body, hmac)` pair that was legitimately produced by Shopify for one shop (the app's client secret is shared across every shop that installs the app, so any merchant who installs the app can capture such a pair by observing webhooks delivered to their own reachable endpoint/proxy) remains a valid signature no matter what `shop-domain` header value accompanies it. An unprivileged internet user who controls one shop's install of the app can therefore replay a captured `(body, hmac)` pair to the app's public webhook endpoint while substituting an arbitrary `shop-domain` header, and `Registry.process` will accept it as valid and hand it to the handler labeled as coming from the victim shop.

### Impact Explanation
This breaks the tenant boundary that host applications rely on `WebhookMetadata#shop` to enforce: a handler that persists webhook data keyed by `request.shop` (a normal, documented usage pattern) can be made to attribute attacker-supplied/attacker-controlled body content to a shop the attacker does not own, i.e., cross-tenant data injection/corruption. This matches the "cross-tenant access" critical-impact category, since it lets an attacker who only controls their own shop's app installation cause data to be attributed to another tenant.

### Likelihood Explanation
Requires the attacker to (a) install the app on their own shop (which is normal, unprivileged access any Shopify merchant can obtain) and (b) be able to capture at least one legitimate webhook `(body, hmac)` delivered to them (achievable by configuring their own webhook endpoint/receiver, since webhook delivery addresses are configured per install). No access to `api_secret_key` or any privileged credential is required. The only extra step is crafting a POST to the target app's webhook endpoint with a spoofed `shop-domain` header, which is fully within reach of an "unprivileged internet user."

### Recommendation
Bind the `shop-domain` (and ideally `topic`/`webhook-id`) header into the signable string used for HMAC verification, or otherwise cryptographically tie the shop identity to the signed payload before trusting `request.shop` for routing/tenant attribution. At minimum, document that host applications must independently verify the reporting shop belongs to a known, installed tenant before trusting `WebhookMetadata#shop`.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and configures a webhook endpoint they control to receive deliveries (or otherwise observes a legitimate webhook body+HMAC pair, e.g. via `orders/create`).
2. Attacker captures the raw body `B` and its valid `x-shopify-hmac-sha256` value `H` (computed by Shopify using the app's shared secret).
3. Attacker sends a POST to the target application's public webhook endpoint with:
   - `x-shopify-hmac-sha256: H`
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - `x-shopify-topic: <same topic>`
   - body: `B`
4. `ShopifyAPI::Webhooks::Request.new` parses the request; `Utils::HmacValidator.validate` succeeds because it only checks `B` against `H`
   ( [5](#0-4) ).
5. `Registry.process` dispatches to the handler with `shop: "victim-shop.myshopify.com"` and body `B`, even though `B` and `H` never originated from `victim-shop.myshopify.com`
   ( [6](#0-5) ).
