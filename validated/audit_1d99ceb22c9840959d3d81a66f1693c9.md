### Title
`EvmHost.dispatch`/`fundRequest` overpay excess native ETH gets permanently trapped in the host instead of being refunded to the caller - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest` all accept native ETH via `msg.value` and swap it for the exact fee-token amount required via Uniswap's `swapETHForExactTokens`, but none of them account for or refund unspent ETH back to the caller who supplied it.

### Finding Description
In all three payable dispatch entry points, when `msg.value > 0` the host calls the router directly with the full `msg.value`, requesting only `post.fee`/`get.fee`/`amount` worth of exact output tokens: [1](#0-0) [2](#0-1) [3](#0-2) 

`swapETHForExactTokens` only spends the ETH necessary to buy the exact `amountOut`, and refunds any unspent ETH to `msg.sender` of the router call. Since `EvmHost` itself calls the router (not the original transaction sender), that leftover ETH is refunded to `address(EvmHost)`, not to the app/user who paid it. The host never inspects the swap's return value (`amounts[0]`, the actual ETH spent), and it has no logic afterward to compute or forward the difference (`msg.value - amounts[0]`) back to `_msgSender()`/`post.payer`. `EvmHost` also exposes no admin/rescue function to sweep stray native ETH out of the contract, so any overpaid ETH becomes permanently stuck.

This is the same bug class as the report: a caller who sends more ETH than strictly required for the operation (a very common case, since `swapETHForExactTokens` requires callers to supply an ETH ceiling above the expected cost as slippage protection) has that excess silently consumed by the contract with no refund path, rather than reverting or returning it.

Contrast this with `IntentGatewayV2.placeOrder`/`_fillCrossChain`, which correctly capture the router's returned `amounts[0]` and refund the remainder of `msgValue` to `msg.sender`: [4](#0-3) 
This shows the codebase is aware of the overpayment-refund pattern for the same router call, but `EvmHost` — the lowest-level, most-used entry point reachable from every app dispatching a message — omits it entirely.

### Impact Explanation
Any user, app, or intent solver invoking `IDispatcher(host).dispatch{value: X}(...)` or `fundRequest{value: X}(...)` with `X` even slightly larger than the ETH actually needed to buy the exact fee-token amount (which is the normal/expected way to call these payable functions, since exact-in-advance pricing is impractical due to slippage/price movement between quote and execution) will have the excess ETH swept into `EvmHost` and permanently lost with no recovery mechanism. This is a direct, unbounded loss of user funds on every native-fee dispatch across the protocol (POST, GET, and fee-top-up paths), not an edge case.

### Likelihood Explanation
High likelihood: every integrator quoting fees off-chain and padding `msg.value` for slippage tolerance (the pattern shown in the SDK/docs, e.g. `dispatch.mdx`'s "Automatically swapped to fee token via Uniswap") will trigger this on essentially every call, since it is unlikely that `msg.value` exactly equals the ETH-for-exact-tokens cost at execution time.

### Recommendation
- In `EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest`, capture the `amounts` array returned from `swapETHForExactTokens` and compute `refund = msg.value - amounts[0]`.
- Forward `refund` back to `_msgSender()` (or the designated `payer`) via a safe ETH transfer, mirroring the pattern already used in `IntentGatewayV2._placeOrder`/`_fillCrossChain`.
- Alternatively, add a host-level rescue/sweep function restricted to admin/governance to recover any ETH accidentally trapped in the contract, as a defense-in-depth measure.

### Proof of Concept
1. Attacker/user calls `host.dispatch{value: 10 ether}(DispatchPost{... fee: 1e18 ...})` where the actual ETH cost to buy `1e18` fee tokens via Uniswap is only `0.01 ether`.
2. Inside `dispatch`, `IUniswapV2Router02.swapETHForExactTokens{value: 10 ether}(1e18, path, address(this), block.timestamp)` executes, spending only `0.01 ether` and refunding `9.99 ether` back to `address(this)` (i.e., `EvmHost`), because `EvmHost` is `msg.sender` from the router's perspective.
3. `dispatch` returns normally with a valid `commitment`; no code path returns or credits the `9.99 ether` to the caller.
4. The `9.99 ether` remains locked in `EvmHost`'s balance indefinitely — there is no `withdraw`/`rescue` function in `EvmHost.sol` to recover it. [1](#0-0)
