### Title
Deposit into a bad-debt-drained vault mints zero shares while charging full principal, permanently freezing/transferring the depositor's funds - (File: `mainnet/contracts/vault/v0-vault-usdc.clar` and equivalent per-asset vaults)

### Summary
When a vault's total assets are driven to zero by full bad-debt socialization while its share supply (`zft` total supply) remains nonzero, the vault's `deposit` function computes zero shares for any subsequent deposit yet still accepts and books the depositor's full underlying payment. Unlike `redeem`, `deposit` has no `ERR-OUTPUT-ZERO`-style guard against minting zero shares, so a normal-looking deposit silently converts to a total loss for the depositor and a windfall to existing (already-bad-debt-socialized) shareholders.

### Finding Description
`convert-to-shares-preview` intentionally returns `u0` shares whenever `total-supply != 0` and `total-assets == 0`: [1](#0-0) 

This zero-assets/nonzero-supply state is directly reachable through the protocol's own bad-debt socialization path. `socialize-debt` in the vault writes down `assets` (only by the principal-reduction portion) and forces `lindex` to `u0` whenever the socialized debt equals or exceeds the vault's `total-assets`, but it never touches `zft` total supply (share tokens are not burned during socialization): [2](#0-1) 

This is invoked from the market's liquidation flow when a position's debt is fully written off (`liquidate` -> `socialize-debt-asset` -> `vault-socialize-debt`): [3](#0-2) [4](#0-3) 

Once `total-assets-preview == 0` while `total-supply-preview > 0` (i.e., a pool where a fully utilized borrower's collateral was wiped out and all outstanding debt was socialized across depositors), `deposit` computes `inkind = 0`: [5](#0-4) 

The function only checks `(>= inkind min-out)` for slippage - if the caller (or a naive front-end defaulting `min-out` to `0`) passes `min-out = 0`, the check trivially passes. `ft-mint?` with `inkind = 0` succeeds (minting nothing), `receive-underlying` still pulls the full `amount` from the depositor, and `assets` is incremented by the full `amount`. Contrast this with `redeem`, which explicitly guards against a zero output with `(asserts! (> inkind u0) ERR-OUTPUT-ZERO)` - no analogous guard exists in `deposit`: [6](#0-5) 

The value identity broken is:
`shares_minted_to_depositor * price_per_share == assets_deposited`
but here `shares_minted_to_depositor = 0` while `assets_deposited = amount > 0`, and that `amount` is absorbed into `total-assets`, which now backs the *existing* nonzero share supply - i.e., existing (already bad-debt-socialized) shareholders' shares regain backing paid for entirely by the new depositor, who receives nothing.

### Impact Explanation
This is a direct, permanent loss of principal for the depositor (100% of their deposited amount is unrecoverable - they hold zero shares and cannot redeem anything back), and it functions as an uncompensated transfer of value to the pool's pre-existing shareholders (whose shares, worth zero moments before, become backed again). This matches the "theft/loss of user funds at rest" and "protocol insolvency masking" impact classes: the depositor's funds are effectively stolen by the pre-existing share supply with no compensating mint.

### Likelihood Explanation
Reaching `total-assets == 0` with `total-supply > 0` requires only that a single fully-utilized position accrue bad debt that consumes the entire vault's assets in one liquidation - a scenario the underlying report already establishes as realistic (illiquid/unpopular pools, rapid collateral price drops, rapid debt price spikes, or interest driving 100% utilization). No attacker action or privileged access is needed; any organic depositor who is unaware the vault is currently in this degenerate zero-total-assets state (and who does not manually set a nonzero `min-out`) will trigger the loss. The vault provides no on-chain block or warning against depositing into a zero-total-assets, nonzero-total-supply vault.

### Recommendation
In `deposit`, add an explicit guard analogous to `redeem`'s `ERR-OUTPUT-ZERO`, e.g. `(asserts! (or (is-eq (total-supply) u0) (> inkind u0)) ERR-OUTPUT-ZERO)`, so that any deposit which would mint zero shares while the vault has an existing nonzero share supply is rejected. More fundamentally, when bad-debt socialization fully wipes `total-assets` for a pool with outstanding shares, the vault should either pause deposits for that asset until manually resolved, or burn/write off the affected shares so `total-supply` returns to zero (restoring the intended 1:1 initial-deposit behavior) rather than leaving "zombie" shares with no backing.

### Proof of Concept
1. Vault `v0-vault-usdc` is initialized; `assets = 1000e6`, `total-supply (zft) = 1000e6` (1:1 after initial deposit).
2. A position borrows the full `1000e6` available liquidity (100% utilization) via `v0-4-market.clar`'s borrow flow.
3. Collateral price crashes; the position becomes undercollateralized with zero recoverable collateral. `liquidate` is called; `no-collateral-left` is true, triggering `socialize-debt-asset` -> vault `socialize-debt` with `scaled-amount` covering the entire outstanding debt: [2](#0-1) 
4. Because `debt-reduction >= old-total-assets`, `lindex` is set to `u0` and `assets` is reduced to `u0` (bounded at `u0`), while `zft` total supply remains `1000e6` (no shares burned).
5. `total-assets-preview` now evaluates to `u0`; `total-supply-preview` is still `1000e6`.
6. A new depositor calls `deposit(500e6, min-out=0, recipient)`. `convert-to-shares-preview` returns `u0` shares (since `ts != 0` and `ta == 0`): [1](#0-0) 
7. `deposit` passes all asserts (`inkind (0) >= min-out (0)`), pulls `500e6` from the depositor, mints `0` zft shares, and sets `assets = 500e6`: [7](#0-6) 
8. The depositor now holds `0` shares worth `0`, having paid `500e6`; the pre-existing `1000e6` zft shares are now collectively backed by the `500e6` in `assets`, i.e. the new depositor's funds are fully absorbed by prior shareholders.
