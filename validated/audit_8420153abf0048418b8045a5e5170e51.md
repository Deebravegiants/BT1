### Title
Webhook `shop-domain` header is trusted and dispatched to per-shop handlers without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely by checking `Utils::HmacValidator.validate(request)`, which signs only the raw request body. The `shop-domain` header — which is the value the app uses to attribute the webhook to a specific merchant/tenant — is never included in the signed data, so its authenticity is never checked.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from HTTP headers with no cryptographic binding to the signed body: [2](#0-1) 

`Registry.process` verifies only the HMAC over that signable string (the body) and then immediately trusts `request.shop` to build `WebhookMetadata` that is handed to the app's handler: [3](#0-2) 

`HmacValidator.validate` computes an HMAC-SHA256 over `verifiable_query.to_signable_string` (the body, for webhooks) using the app's `client_secret`, and only checks that value against the received `hmac`: [4](#0-3) 

The identity binding that should hold is:
`shop_header == shop_bound_by_hmac`

but the actual binding enforced is:
`hmac_valid_for(body) ⇏ shop_header_authentic`

Because the *same* `client_secret` is used by Shopify to sign webhooks for **every** shop that has this app installed, any unprivileged user who can install the app on their own store (a normal, unprivileged merchant/developer action) can obtain a genuine `(raw_body, hmac)` pair for their own webhook deliveries. They can then replay that exact body+HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) header with an arbitrary value naming a *different, victim* shop. `HmacValidator.validate` still passes because it only checks the body signature, and `Registry.process` dispatches `WebhookMetadata.new(shop: request.shop, ...)` — i.e., attacker-chosen shop identity, with attacker-controlled body content — straight to the app's handler as if it were an authentic event for the victim's tenant.

### Impact Explanation
This breaks the tenant identity binding that `Registry.process` is supposed to enforce before invoking per-shop business logic (e.g., enqueuing jobs keyed by `shop_domain`, updating per-shop state, billing, order sync, etc., as illustrated in the gem's own webhook docs example `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`). An attacker can inject attacker-controlled webhook payloads that are processed under a victim shop's identity — a cross-tenant data-injection/confusion primitive reachable purely by an unprivileged internet user who has (or creates) their own installation of the app. This matches the "cross-tenant access" Critical impact category, since the app-level tenant boundary (`shop`) is not actually bound to the cryptographically verified data.

### Likelihood Explanation
Exploitability requires: (1) the attacker has any store with the app installed (unprivileged, self-serve for most public apps) so they can trigger a legitimate webhook and capture a valid `(body, hmac)` pair; (2) the ability to send an arbitrary HTTP request to the app's public webhook endpoint with a modified `shop-domain` header, which is trivial since it's just an HTTP header under attacker control. No secrets, tokens, or privileged access are needed — only interaction with the gem's own `Registry.process`/`Request` API exactly as documented. This is a directly reachable code path in the library, not a misuse of an undocumented API.

### Recommendation
Do not trust the `shop-domain` (or `topic`/`webhook_id`) header value on its own. Either:
- Include the shop domain (and topic) in the HMAC-signed material used for verification (not solely relying on Shopify's body-only signature scheme), or
- After HMAC verification, cross-check the header-derived `shop` against a value embedded in and covered by the verified body payload (most Shopify webhook payloads include shop-identifying fields), or, at minimum, require that the resolved `shop` corresponds to a shop for which the app has an active installation/session before dispatching to the handler, and reject/flag mismatches, and
- Document clearly for consumers of `ShopifyAPI::Webhooks::Registry.process` that `request.shop` is not authenticated by the HMAC and must not be used as the sole tenant key without additional verification (e.g., correlating with a known installed-shop list).

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` (normal, unprivileged onboarding).
2. Attacker triggers any subscribed webhook event (e.g., `orders/create`) for their own shop, and captures the raw HTTP request Shopify sends to the app's webhook endpoint, including headers `x-shopify-hmac-sha256: <HMAC>`, `x-shopify-shop-domain: attacker.myshopify.com`, and the raw JSON body.
3. Attacker replays this exact request to the app's webhook endpoint, but rewrites the header to `x-shopify-shop-domain: victim.myshopify.com` (leaving `raw_body` and `x-shopify-hmac-sha256` untouched).
4. `ShopifyAPI::Webhooks::Request.new` accepts the headers/body (no relevant header validation) as shown in [5](#0-4) .
5. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `raw_body` only and matches the (still-valid, since body unchanged) received HMAC, returning `true`, per [6](#0-5) .
6. `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` using the attacker-modified `shop` header and dispatches it to the registered handler, per [7](#0-6) , causing attacker-controlled webhook content to be processed as if it belonged to `victim.myshopify.com`.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
