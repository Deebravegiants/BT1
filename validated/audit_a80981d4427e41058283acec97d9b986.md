### Title
Missing duplicate input/output token rejection in Tron `IntentGatewayV2.placeOrder` enables escrow over-release - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The canonical EVM `IntentGatewayV2.placeOrder` (`evm/src/apps/IntentGatewayV2.sol`) explicitly rejects orders containing duplicate input tokens and duplicate output tokens, with regression tests stating this fixes real over-release/premature-finalization bugs in partial fills. The Tron variant of the same contract (`evm/tron/contracts/apps/IntentGatewayV2.sol`) implements `placeOrder` without either check, reproducing exactly the class of bug described in the external report: per-element "add/merge if present" bookkeeping that is not deduplicated against the rest of the batch, corrupting downstream per-token state.

### Finding Description
In `evm/src/apps/IntentGatewayV2.sol`:
- Duplicate **output** tokens are rejected via a transient-storage guard before escrow: [1](#0-0) 
- Duplicate **input** tokens are rejected explicitly during escrow crediting: [2](#0-1) 

The accompanying tests document why these checks exist — omitting them lets a same-chain partial fill "over-release repeated input escrow" or "prematurely finalize repeated output legs": [3](#0-2) [4](#0-3) 

In `evm/tron/contracts/apps/IntentGatewayV2.sol`, `placeOrder` performs the same escrow bookkeeping but with neither guard. It accumulates per-token escrow with `+=` instead of rejecting a repeat, and has no transient-storage duplicate-output check at all: [5](#0-4) [6](#0-5) 

This is the same root-cause shape as the reported `YsDistributor.depositMultipleToken` bug: a caller-controlled batch (`deposits` there, `order.inputs`/`order.output.assets` here) is folded into per-token accounting without deduplication, so a duplicated key in the batch produces state that downstream per-leg logic (fill/redeem/refund, which iterate `order.inputs`/`order.output.assets` leg-by-leg exactly as `_claimTokenRewards` iterates `depositedTokenAddressForTde`) treats as independent legs — even though the escrow ledger only holds one merged/overwritten bucket per token. Since the order commitment is computed by hashing the full `order` struct (including the duplicated legs), an attacker (any unprivileged order placer) can craft an order with duplicate input or output token entries specifically to desynchronize the leg-count assumptions relied on by the same-chain partial-fill and refund paths that consume `order.inputs`/`order.output.assets` per index against the single `_orders[commitment][token]` bucket.

### Impact Explanation
The upstream fix and its tests classify this exact condition as leading to over-release of escrowed input tokens and premature/duplicate finalization of output legs during same-chain partial fills — i.e., a solver or the order placer can extract more value from escrow than was deposited, or cause partial-fill accounting to consider an order filled when it should not be. This is a direct fund-loss/fund-freezing vector reachable by any user submitting a single `placeOrder` transaction, with no privileged access required.

### Likelihood Explanation
High. `placeOrder` is a fully public, unprivileged entry point on the Tron `IntentGatewayV2` deployment; an attacker only needs to submit an `Order` with two `TokenInfo` entries sharing the same `token` value in either `inputs` or `output.assets`. No proof, consensus, or relayer interaction is needed to trigger the missing check — it fires at order placement, and the resulting inconsistent state is then exploited at fill/refund time exactly as the EVM-side regression tests demonstrate.

### Recommendation
Port the same guards from `evm/src/apps/IntentGatewayV2.sol` into `evm/tron/contracts/apps/IntentGatewayV2.sol`:
1. Reject duplicate `order.output.assets[i].token` entries before escrow (transient-storage or an in-memory dedup array).
2. Replace the `_orders[commitment][token] += reducedInputs[i].amount` accumulation for inputs with an explicit `if (_orders[commitment][token] != 0) revert InvalidInput();` check as done in the canonical contract, so duplicate input tokens cause the whole `placeOrder` call to revert rather than silently merging into a single escrow bucket that per-leg fill/refund logic does not expect.

### Proof of Concept
1. Call `IntentGatewayV2(tron).placeOrder` with `order.inputs = [ {token: USDC, amount: A}, {token: USDC, amount: B} ]` (or duplicate `order.output.assets` entries).
2. The Tron contract accepts the order (no revert), computing `commitment = keccak256(abi.encode(order))` over the duplicated legs and crediting `_orders[commitment][USDC] = A+B` via the unmatched `+=` path.
3. During a same-chain partial fill/refund that iterates `order.inputs`/`order.output.assets` per-index against `_orders[commitment][token]`, the duplicate legs are treated as independent — reproducing the exact over-release/premature-finalization scenario the EVM contract's `testRevert_PlaceOrder_DuplicateInputTokens` / `testRevert_PlaceOrder_DuplicateOutputTokens` regression tests were written to prevent: [7](#0-6)

    function placeOrder(Order memory order, bytes32 graffiti) public payable {
        // Validate that order has inputs
        if (order.inputs.length == 0) revert InvalidInput();

        address hostAddr = host();
        // fill out the order preludes
        order.user = bytes32(uint256(uint160(msg.sender)));
        order.source = IDispatcher(hostAddr).host();
        order.nonce = _nonce++;

        // Calculate reduced inputs (after protocol fees) for commitment and escrow
        uint256 inputsLen = order.inputs.length;
        // Use destination-specific protocol fee, fallback to source chain fee if zero
        bytes32 destinationHash = keccak256(order.destination);
        uint256 protocolFeeBps = _destinationProtocolFees[destinationHash];
        if (protocolFeeBps == 0) {
            protocolFeeBps = _params.protocolFeeBps;
        }
        TokenInfo[] memory reducedInputs;
        bytes32 commitment;

        if (protocolFeeBps > 0) {
            reducedInputs = new TokenInfo[](inputsLen);
            for (uint256 i; i < inputsLen;) {
                uint256 originalAmount = order.inputs[i].amount;
                uint256 protocolFee = (originalAmount * protocolFeeBps) / 10_000;
                uint256 reducedAmount = originalAmount - protocolFee;
                address token = address(uint160(uint256(order.inputs[i].token)));

                // Emit DustCollected for protocol fee if non-zero
                if (protocolFee > 0) emit DustCollected(token, protocolFee);

                reducedInputs[i] = TokenInfo({token: order.inputs[i].token, amount: reducedAmount});
                unchecked {
                    ++i;
                }
            }

            // Temporarily swap inputs to calculate commitment with reduced amounts
            TokenInfo[] memory originalInputs = order.inputs;
            order.inputs = reducedInputs;
            commitment = keccak256(abi.encode(order));
            order.inputs = originalInputs;
        } else {
            // No protocol fees, use order.inputs directly
            reducedInputs = order.inputs;
            commitment = keccak256(abi.encode(order));
        }
