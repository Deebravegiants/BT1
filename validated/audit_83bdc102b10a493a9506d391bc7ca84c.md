### Title
Webhook shop-domain identity spoofing due to HMAC not covering the shop header - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes and verifies the webhook HMAC over the raw request body only, while the `shop` (and `topic`, `webhook_id`, `api_version`) values are pulled from unsigned HTTP headers. `Registry.process` validates the HMAC and then hands `request.shop` straight to the app's webhook handler, so the attacker-controlled shop identity is never covered by the signature that is actually checked.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`hmac` is likewise derived only from the `shopify-hmac-sha256`/`x-shopify-hmac-sha256` header, decoded to be compared against the HMAC of that same raw body: [2](#0-1) 

`shop`, `topic`, `webhook_id`, and `api_version` are read straight from other HTTP headers (`shopify-shop-domain`/`x-shopify-shop-domain`, etc.) with no cryptographic binding to the body or to the HMAC: [3](#0-2) 

`Registry.process` validates the HMAC (which only proves the body bytes were signed with the app's secret at some point) and then immediately trusts `request.shop` to build the `WebhookMetadata` delivered to the host app's handler: [4](#0-3) 

The identity binding that should hold is: `shop value the HMAC authenticates == shop value delivered to the handler`. Because the signable string never includes the shop header, this equality does not hold — the HMAC only proves "this body was signed for *some* shop by this app's secret," not "this body belongs to shop X." Any two webhook deliveries that carry the same raw body (e.g., an empty-body `orders/create` test payload, or any webhook whose body an attacker can reproduce/observe from their own installed store) will have interchangeable, HMAC-valid `(body, hmac)` pairs across shops.

### Impact Explanation
An unprivileged internet user who legitimately installs the app on their own store receives real webhook deliveries containing a valid `(raw_body, hmac)` pair signed with the app's `client_secret`. They can replay that exact body and HMAC to the app's public webhook endpoint while substituting the `shopify-shop-domain` (or `x-shopify-shop-domain`) header with a victim shop's domain. `Utils::HmacValidator.validate` still succeeds because it only checks the body's HMAC, and `Registry.process` forwards `WebhookMetadata` claiming the event came from the victim shop. This is a cross-tenant identity-confusion vector: the host app's handler will process/act on data attributing it to a shop the request did not actually originate from — matching the "Critical - cross-tenant access" impact category, since no access token, `api_secret_key`, or privileged account is required, only participation as any ordinary merchant with the app installed.

### Likelihood Explanation
Likelihood is high for topics with predictable or attacker-reproducible bodies (e.g., mandatory compliance webhooks, or any payload the attacker can obtain from their own shop's legitimate deliveries) since the attacker fully controls headers on requests to the app's public webhook endpoint and only needs a body+hmac pair they've legitimately received once.

### Recommendation
Include the shop domain (and ideally topic/webhook id) as part of the HMAC-covered signable content, or otherwise cryptographically bind the shop identity to the signed payload, before `Registry.process` trusts `request.shop` for handler dispatch — analogous to caching/binding the authenticated identity at the time of the signed event rather than trusting a value that sits outside the verified boundary.

### Proof of Concept
1. Attacker installs the app on their own store `attacker.myshopify.com` and receives a legitimate webhook POST with body `B` and header `x-shopify-hmac-sha256: H` (valid for the app's `client_secret`).
2. Attacker crafts and sends the app's public webhook endpoint a POST with the same body `B`, the same `x-shopify-hmac-sha256: H`, but header `x-shopify-shop-domain: victim.myshopify.com`.
3. `Utils::HmacValidator.validate(request)` returns `true` because it only recomputes HMAC over `raw_body` (`B`) — see `to_signable_string` returning `@raw_body`.
4. `Registry.process` builds `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed_body(B), ...)` and calls the host app's handler, which now processes an event attributed to `victim.myshopify.com` that Shopify never actually sent for that shop.
