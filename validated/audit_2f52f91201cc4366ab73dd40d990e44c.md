### Title
Webhook shop attribution is not covered by the HMAC signature, allowing cross-tenant data injection - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` used to process a webhook from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, while `Utils::HmacValidator` only authenticates the raw request body bytes. Because the shop-domain header is not included in the signed content, a shop that is cryptographically authenticated (the body) and the shop that is trusted for tenant attribution (the header) are not bound to each other, letting a legitimate webhook payload be replayed under an attacker-chosen shop.

### Finding Description
`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` and compares it to the `hmac` value carried by the same object: [1](#0-0) 

For webhooks, `Webhooks::Request#to_signable_string` returns only the raw HTTP body (`@raw_body`), and `#hmac` is read from the `hmac-sha256` header — but `#shop` is read independently from the `shop-domain` header and is never included in the signed content: [2](#0-1) 

`Webhooks::Registry.process` validates only the body/HMAC pair, then forwards `request.shop` — an unauthenticated header value — directly to the app's handler as the tenant identifier for the event: [3](#0-2) 

The binding that should hold is: `shop cryptographically authenticated by the signature == shop used to attribute/process the event`. Here the left side is empty (no shop claim is signed at all), so the equality trivially fails — any caller who possesses one valid `(raw_body, hmac)` pair (e.g., a genuine webhook Shopify sent for their *own* shop) can resend that exact body/HMAC pair while substituting the `shop-domain` header for a victim shop. The signature still validates because it only covers the body bytes, and the handler receives `WebhookMetadata(shop: "victim-shop.myshopify.com", body: <attacker-controlled>)`.

### Impact Explanation
This is a cross-tenant confidentiality/integrity break: an attacker who is a legitimate merchant (and thus a source of validly-HMAC'd webhook traffic for their own store) can cause the app to process attacker-controlled webhook payloads as if they originated from a different, victim shop. Any host application that keys persistence, business logic, or authorization decisions off `WebhookMetadata#shop` (as the library's documented `WebhookHandler#handle(data:)` contract intends) will attribute/store attacker data under the victim tenant's identity, i.e. cross-tenant data injection.

### Likelihood Explanation
Webhook endpoints are internet-reachable by design (Shopify calls them over HTTPS), so an attacker only needs: (1) their own shop installed on the target app to receive one legitimately-signed webhook of any topic/body they control, and (2) the ability to POST to the app's public webhook route with a modified `shop-domain` header and the captured, unmodified `(raw_body, hmac)`. No access to `api_secret_key` or any victim credential is required.

### Recommendation
Bind the shop identity into the authenticated material: include `shop-domain` (and ideally `topic`, `webhook-id`) in the signable string used for HMAC computation, or otherwise cryptographically bind them to the signature, so `Utils::HmacValidator.validate` fails whenever the shop header is substituted relative to the value used when the signature was generated.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers any webhook-eligible event, capturing Shopify's real POST request: headers include `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid-hmac-for-raw_body>`, and some `raw_body`.
2. Attacker resends the identical `raw_body` and `x-shopify-hmac-sha256` value to the same app endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses `shop` from the (now spoofed) header; `Utils::HmacValidator.validate` recomputes the HMAC over the unchanged `raw_body` and it matches, so `Registry.process` calls the app's handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: <attacker's own event body>)` — see `lib/shopify_api/webhooks/registry.rb:188-200` and `lib/shopify_api/webhooks/request.rb:10-38`.

          end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
