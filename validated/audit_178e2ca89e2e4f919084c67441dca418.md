### Title
Webhook signature does not cover `shop-domain`, `topic`, `api-version`, or `webhook-id` headers, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`Webhooks::Request#to_signable_string` returns only `@raw_body`, and `HmacValidator.validate` HMACs only that string against the received `hmac-sha256` header. The `shop`, `topic`, `api_version`, and `webhook_id` accessors read directly from unauthenticated HTTP headers and are never included in the signed material, yet `Registry.process` passes them straight into `WebhookMetadata` as trusted values for the handler, with no call to `ShopValidator.sanitize!` or any session/tenant cross-check.

### Finding Description
The invariant under test is: *every value the handler acts on is inside the string handed to `HmacValidator` via `to_signable_string`*. Tracing the code shows this is false.

- `to_signable_string` returns `@raw_body` only: [1](#0-0) 
- `shop`, `topic`, `api_version`, `webhook_id` are read from HTTP headers, not from the body: [2](#0-1) 
- `HmacValidator.validate_signature` computes `HMAC(secret, to_signable_string)` and compares it only to the `hmac-sha256` header — headers play no role in the comparison at all: [3](#0-2) 
- `Registry.process` validates the HMAC, then forwards `request.shop`, `request.topic`, `request.api_version`, `request.webhook_id` and `request.parsed_body` (from the same `@raw_body`) directly into `WebhookMetadata` for the handler, with no `ShopValidator.sanitize!` call or any check that the shop is one the app actually has a session for: [4](#0-3) 

Because Shopify signs an app's webhooks with the app's single `client_secret` regardless of which shop triggered the event, an unprivileged attacker can legitimately install the app on their own development shop, receive a validly-signed webhook (`raw_body` + `hmac-sha256` header) for that shop, and then replay the exact same `raw_body`/HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`, `X-Shopify-Webhook-Id`) header with an arbitrary victim shop's domain. `HmacValidator.validate` still returns `true` because it never inspects headers, so `Registry.process` calls the handler with `data.shop` set to the attacker-chosen victim domain and a valid-looking HMAC. Any app logic that trusts `WebhookMetadata#shop` for tenant identification (as the gem's own documentation instructs — see `docs/usage/webhooks.md`) will process attacker-supplied data under the victim tenant's identity.

No existing guard prevents this: `HmacValidator.validate` only checks the body signature; `ShopValidator.sanitize!` exists in the codebase but is never invoked in `Registry.process`; there is no session/installed-shop lookup gating the header value before it reaches the handler.

### Impact Explanation
This is a cross-tenant authentication bypass: header values (`shop`, `topic`, `webhook_id`, `api_version`) that downstream handlers treat as authenticated ride along with a validly-signed body but are outside signature coverage. An attacker who legitimately installs the app on their own shop can forge the shop context of any webhook delivery to make it appear to originate from a different (victim) shop, potentially causing the app to mutate or expose the wrong tenant's data. This is repeatable against arbitrary victim shop domains for every webhook topic the app subscribes to.

### Likelihood Explanation
Preconditions are minimal and fully within the "unprivileged attacker" capability set defined by the rules: create a dev shop, install the app, register/receive one legitimately signed webhook. The attacker needs no secret — they simply replay a body+HMAC pair they legitimately received with a modified `X-Shopify-Shop-Domain` header. Feasibility depends on whether the host application actually keys logic off `WebhookMetadata#shop` for tenant isolation (this gem's own docs recommend exactly that), which is the standard integration pattern shown in `docs/usage/webhooks.md`.

### Recommendation
Bind the `shop-domain`, `topic`, `api-version`, and `webhook-id` header values into the signed material used for verification (or otherwise cryptographically tie them to the body), and additionally call `ShopValidator.sanitize!` on `request.shop` plus cross-check it against a known/installed shop or active session before handing it to the handler in `Registry.process`.

### Proof of Concept
Minitest outline (WebMock/Mocha, no live shop):
```ruby
def test_shop_header_not_covered_by_hmac
  ShopifyAPI::Context.setup(api_key: "key", api_secret_key: "secret", ...)
  body = '{"id":123}'
  hmac = Base64.encode64(OpenSSL::HMAC.digest("sha256", "secret", body))

  req_a = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: {
    "x-shopify-topic" => "orders/create",
    "x-shopify-hmac-sha256" => hmac,
    "x-shopify-shop-domain" => "attacker-shop.myshopify.com",
  })
  req_b = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: {
    "x-shopify-topic" => "orders/create",
    "x-shopify-hmac-sha256" => hmac,
    "x-shopify-shop-domain" => "victim-shop.myshopify.com",
  })

  assert ShopifyAPI::Utils::HmacValidator.validate(req_a)
  assert ShopifyAPI::Utils::HmacValidator.validate(req_b)
  refute_equal req_a.shop, req_b.shop
  # both requests pass validation with identical body/HMAC but different shop -> Registry.process
  # would dispatch to handler.handle with data.shop == "victim-shop.myshopify.com" for attacker-supplied body.
end
```
This demonstrates one signature validating two different shop contexts, proving the binding "signature covers shop/topic/webhook_id" is false.
