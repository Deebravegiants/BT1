Audit Report

## Title
Missing slippage protection in `SwapFirstAssetTrader::refund_weight` XCM fee-refund swap - (File: `cumulus/primitives/utility/src/lib.rs`)

## Summary
`SwapFirstAssetTrader::refund_weight` calls `SwapCredit::swap_exact_tokens_for_tokens` with `amount_out_min = None` when swapping unused `Target`-asset fee credit back into the user's original fee-payment asset, unlike `buy_weight` which uses the bounded `swap_tokens_for_exact_tokens` with an explicit `fee` amount. This allows the refund swap to execute at whatever pool price exists at execution time with no minimum-output protection.

## Finding Description
The code at [1](#0-0)  confirms `refund_weight` extracts a `refund` credit and swaps it via `SwapCredit::swap_exact_tokens_for_tokens(vec![Target::get(), refund_swap_asset], refund, None)`, passing `None` as `amount_out_min`. This contrasts with `buy_weight` at [2](#0-1) , which uses `swap_tokens_for_exact_tokens` bounded by an explicit target `fee`. `SwapFirstAssetTrader` is confirmed wired into production runtime `WeightTrader` configurations, including `cumulus/parachains/runtimes/assets/asset-hub-rococo/src/xcm_config.rs`, `asset-hub-westend/src/xcm_config.rs`, `cumulus/parachains/runtimes/testing/penpal/src/xcm_config.rs`, and `substrate/frame/staking-async/runtimes/parachain/src/xcm_config.rs`. The path is reachable by any unprivileged XCM sender who pays fees in a non-`Target` asset and consumes less weight than purchased.

## Impact Explanation
The impact is real but narrow: the value at risk is limited to `refund_amount`, i.e., the unused portion of a single XCM message's weight fee, not a pool/vault balance. If the `Target`/`refund_swap_asset` pool is thin or its price shifts unfavorably between the implicit rate used when the fee was bought and the moment `refund_weight` executes, the fee payer receives a reduced refund with no floor protecting them. This is a genuine, if low-value-per-instance, missing-slippage-check defect in SDK-internal code (not user-supplied parameters), distinguishing it from the general observation that `pallet_asset_conversion` extrinsics require explicit min/max — this internal call site opts out of that protection.

## Likelihood Explanation
The code path is reachable by any unprivileged party constructing an XCM message that overpays weight in a swappable non-`Target` asset — a common, ordinary scenario, not requiring governance or node privileges. However, profitable exploitation requires influencing the pool's spot price at the precise moment `refund_weight` executes within the same message's execution (effectively same-block), which in a Substrate/parachain context is meaningfully harder to achieve reliably than Ethereum mempool front-running and was not demonstrated with a working PoC.

## Recommendation
Pass an explicit, non-`None` `amount_out_min` to `swap_exact_tokens_for_tokens` in `refund_weight`, derived via `QuotePrice` (already used in `quote_weight`) with a reasonable slippage tolerance, and on an unfavorable/failed swap return the credit to `total_fee` rather than accepting an unbounded-slippage refund, mirroring the bounded-swap pattern already used in `buy_weight`.

## Proof of Concept
No working exploit transaction/test was constructed; validation is based on static code review confirming the `None` parameter and production wiring described above. A concrete PoC would extend `cumulus/primitives/utility/src/tests/swap_first.rs` to simulate a pool-price shift between fee collection and `refund_weight` invocation and measure the refunded amount against the `QuotePrice`-implied expectation.
