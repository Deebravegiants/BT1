### Title
Unchecked-length `message.from` slice/copy causes reachable panic in `pallet-hyper-fungible-token`'s `on_accept` calldata path - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
`Message.from` in the ABI-decoded HFT payload is set by the sender on the source chain and is only used for (a) refunding on timeout, where it is length-checked, and (b) as the dispatch-origin fallback when a bridged message carries unsigned calldata. In the timeout path and in the `to` (recipient) handling, the code validates the byte length (must be 20 or 32) and returns a typed `HftError` otherwise. In the `on_accept` unsigned-calldata branch, the equivalent handling of `message.from` skips that validation entirely, directly indexing/copying into fixed-size buffers.

### Finding Description
In `on_accept` (`modules/pallets/hyper-fungible-token/src/module.rs:176-186`):
```rust
let from_bytes = message.from.as_ref();
if source.is_evm() {
    T::EvmToSubstrate::convert(H160::from_slice(
        &from_bytes[from_bytes.len() - 20..],
    ))
} else {
    let mut account = [0u8; 32];
    account.copy_from_slice(from_bytes);
    account.into()
}
``` [1](#0-0) 

This is reachable only when `message.data` is non-empty and `SubstrateCalldata::decode` succeeds with `signature == None`, at which point `message.from` is used to build the substrate dispatch `origin` rather than to validate a signature.

Contrast with the sibling `to` (recipient) handling a few lines earlier in the same function, which explicitly checks length and returns `HftError::InvalidRecipientLength` for anything other than 20/32 bytes: [2](#0-1) 

And with the `on_timeout` handler, which performs the identical from-bytes-to-AccountId conversion but with the same length checks (`HftError::InvalidSenderLength`): [3](#0-2) 

The pallet's error enum even already defines `InvalidSenderLength` for exactly this situation [4](#0-3) , but it is never used to guard the `on_accept` branch.

`message.from` comes straight from the ABI-decoded `Message.from` field [5](#0-4) , a field documented only as "the original sender on the source chain (used for timeout refunds)" — nothing constrains its length to 20/32 bytes at the point of ABI encoding, and the only authentication performed before this code runs is `ContractToAsset::<T>::get(source, &from)` (the ISMP `PostRequest.from` contract address, a *different* field than `message.from`) [6](#0-5) . `message.from` itself is never validated before the vulnerable slice/copy.

Root cause, matching the CVE bug-class (an unchecked type/length assumption on attacker data leading to a runtime crash instead of a graceful error):
- `source.is_evm()` branch: if `from_bytes.len() < 20`, `from_bytes.len() - 20` underflows `usize`, panicking on overflow-checked builds, or wrapping to a huge index and panicking on out-of-bounds slicing on non-overflow-checked builds.
- non-EVM branch: `account.copy_from_slice(from_bytes)` panics whenever `from_bytes.len() != 32` (`copy_from_slice` requires exact length match).

### Impact Explanation
`on_accept` executes inside the ISMP message-dispatch/handling path invoked when a relayer delivers a proven `PostRequest` destined for the HFT module — this is a normal, permissionless flow (any token bridger/dApp on the source chain crafts the `Message`, any relayer delivers it). A crafted `message.from` of the wrong length (e.g. 0, 5, 19, or 33+ bytes) combined with non-empty, unsigned `data` containing a decodable `SubstrateCalldata` causes an unhandled Rust panic during extrinsic/message execution instead of returning the already-defined `HftError`. A panic inside pallet logic invoked from block-import/extrinsic-application is a denial-of-service on the chain executing the message (aborts the node's execution worker / can halt block production depending on how the runtime handles panics), which blocks message delivery for this and all subsequent messages routed through the same execution path — this matches the "route unable to deliver messages" acceptance criterion.

### Likelihood Explanation
High: any account able to call the `send`/transfer function on a source-chain `HyperFungibleToken.sol` deployment (or any equivalent app dispatching an ISMP `PostRequest` with an ABI-encoded `Message`) fully controls the `from` field's byte length; no additional privilege or governance action is required, and no other check constrains `message.from`'s length before it reaches the vulnerable code. The only precondition is supplying non-empty `data` that decodes as `SubstrateCalldata` with `signature: None`, which is an attacker-controlled, self-contained encoding.

### Recommendation
Add the same length validation used for `to_bytes` (lines 62-71) and in `on_timeout` (lines 224-232) to the `from_bytes` handling in the unsigned-calldata branch of `on_accept`: require exactly 20 bytes for EVM sources and exactly 32 bytes for non-EVM sources, returning `HftError::InvalidSenderLength(from_bytes.len())` on mismatch instead of slicing/copying unconditionally.

### Proof of Concept
1. On the source chain, call `HyperFungibleToken.send(SendParams)` (or the equivalent bridging entrypoint) with a `Message.from` set to an arbitrary byte string whose length is not 20 (destination is EVM) — e.g. 1 byte — and with `data` set to an ABI/SCALE-encoded `SubstrateCalldata { signature: None, runtime_call: <any decodable call> }`.
2. Have the message relayed and delivered to `pallet-hyper-fungible-token::on_accept` on the Substrate destination chain via the standard ISMP `handle`/`handle_unsigned` path.
3. Execution reaches `modules/pallets/hyper-fungible-token/src/module.rs:176-181`; `from_bytes.len() - 20` underflows (or, for the non-EVM destination case, `account.copy_from_slice(from_bytes)` panics on length mismatch), panicking mid-dispatch instead of returning `HftError::InvalidSenderLength`.
