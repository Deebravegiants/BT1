## Finding [1](#0-0) 

Below is the finding based on the pattern: **a field acted on (the `shop` domain, `topic`, and `webhook_id`) but not covered by the HMAC**.

### Title
Webhook `shop`, `topic`, and `webhook_id` headers are not covered by HMAC verification, allowing cross-tenant webhook spoofing via payload replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content solely from the raw request body, while the `shop`, `topic`, `webhook_id`, and `api_version` values used downstream for dispatching and identifying the tenant are taken from unauthenticated HTTP headers.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`, and none of the Shopify-supplied headers are folded into the signed content: [2](#0-1) 

`Registry.process` verifies the HMAC of the request via `Utils::HmacValidator.validate(request)`, which only proves the *body* bytes are unmodified/authentic — it does not bind `request.shop`, `request.topic`, or `request.webhook_id` to that signature: [3](#0-2) 

`HmacValidator.validate_signature` compares the computed signature only against `verifiable_query.to_signable_string`, i.e. the raw body for webhooks: [4](#0-3) 

The binding broken is: **shop authenticated (payload signed by Shopify with the app's secret) ≠ shop asserted to the handler** (`request.shop` from the `X-Shopify-Shop-Domain`/`shopify-shop-domain` header). Since the header is never part of the signed content, any request carrying a previously-valid `(raw_body, hmac)` pair — obtainable by an attacker who installs the app on their own store and receives a genuine webhook delivery — can be replayed directly to the app's public webhook endpoint with the `shop-domain` (and/or `topic`/`webhook-id`) header swapped to a victim shop, and the HMAC check in `Registry.process` will still pass. The handler then receives `WebhookMetadata.new(topic:, shop:, body:, ...)` populated from the attacker-controlled headers [5](#0-4) , believing the event originated from the victim tenant.

### Impact Explanation
This is a cross-tenant identity confusion: an app that keys any per-shop side effects (e.g., GDPR data-request/erasure webhooks, `app/uninstalled` cleanup, billing state, session invalidation) off `WebhookMetadata#shop` can be tricked into applying those effects to a shop the attacker does not control, using only a body/HMAC pair the attacker legitimately received for their own shop. This matches the "cross-tenant access" Critical-impact category.

### Likelihood Explanation
Any internet user can sign up for a free/dev Shopify store, install the target app, and trigger a real webhook delivery to capture one valid `(raw_body, hmac)` pair for a body they control (or a fixed low-entropy body such as `{}` used for mandatory compliance topics, as seen in tests). They then send a forged HTTP POST directly to the app's public webhook endpoint with the same body/hmac but a different `shop-domain`/`topic`/`webhook-id` header combination — no access token, `client_secret`, or credential of the victim is required.

### Recommendation
Bind the identity fields to the signed content: include `shop`, `topic`, and `webhook_id` in the value verified by HMAC (or require the host application to independently confirm the `shop-domain` header corresponds to a shop with an active, previously-established installation/session before trusting it), rather than trusting these headers purely because the raw body's HMAC validates.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`; Shopify sends a webhook to the app's public endpoint with body `{}` and header `X-Shopify-Hmac-Sha256: <valid hmac of "{}">`.
2. Attacker records this `(body="{}", hmac)` pair.
3. Attacker sends a direct POST to the same endpoint with the same body `{}` and hmac header, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` and (optionally) a different `X-Shopify-Topic`.
4. `Utils::HmacValidator.validate(request)` succeeds because it only checks the body against the hmac: [6](#0-5) 
5. `Registry.process` dispatches to the registered handler with `shop: "victim-shop.myshopify.com"`, causing the app to act as though the event came from the victim tenant: [3](#0-2)
