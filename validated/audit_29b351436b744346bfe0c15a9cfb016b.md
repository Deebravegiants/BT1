### Title
Pool `repay`/`recapitalize` refund unfunded declared amounts out of real custody - ([File: contracts/pool/src/ops/repay.rs])

### Summary
Both `ops::repay::apply` and `ops::recapitalize::apply` compute a refund from the *declared* inbound `amount`, not from any measured receipt or book entry, and pay it out of the pool's actual token balance via `Cache::transfer_out`. `transfer_out` does not debit `cash` and never passes `require_reserves`. If a caller can invoke these legs with a declared amount that was never (or only partially) prefunded — exactly the bug class of the Napier TrancheRouter issue, where a second funding path satisfies the operation while caller-supplied funds sit unaccounted — the "overpayment" refund pays real pool assets for nothing.

### Finding Description
`ops::repay::accounting` resolves the declared `action.amount` into `burned` shares plus `overpayment`; `apply` then calls `outcome.cache.transfer_out(payer, outcome.overpayment)` unconditionally [1](#0-0) . Similarly, `ops::recapitalize::accounting` sets `refund = amount - applied` and `apply` transfers it out [2](#0-1) . `Cache::transfer_out` sends tokens from `env.current_contract_address()` (the pool) to an arbitrary `recipient` without touching accounting [3](#0-2) .

The correctness of the refund rests entirely on the documented precondition "The controller transfers the repay amount into the pool before this call" [4](#0-3) . The controller does honor this via `transfer_amount_measured` [5](#0-4) , but the pool itself treats the declared `amount` as cash backing the refund. The protocol's own test demonstrates the hole: a `repay` with nothing transferred in and zero debt still pays the full declared amount out of custody — "the whole amount is refunded out of real custody with the book untouched" [6](#0-5) .

This is the structural analog of the Napier bug: a fallback/alternative funding path (declared amount vs. actual receipt) is trusted, and the residual is payable to whoever triggers the leg rather than being reconciled against a measured inflow.

### Impact Explanation
Theft of user funds / protocol insolvency: any refund leg reachable with a declared amount exceeding the real inflow pays suppliers' principal out of pool custody without debiting `cash`, so the book remains balanced while tokens leave. For `repay`, the full-close branch makes the *entire* amount refundable whenever outstanding debt is smaller than declared — including zero-debt markets.

### Likelihood Explanation
Reachability depends on whether `LiquidityPool::repay`/`recapitalize` gate the caller to the controller. In the in-scope code shown (`apply`/`accounting`), no caller check exists — the trust assumption is implicit in comments only. The pool's own test invokes `client().repay(&payer, …)` directly and drains custody [7](#0-6) . If the entrypoint is controller-gated upstream, the residual risk reduces to any path that calls `repay_prefunded_position` with a `req.amount` exceeding the pool's actual receipt (e.g., a taxed in-transfer where the measured `received` is substituted but a stale larger `amount` slips through — mitigated today since `settle_repay` and `apply_liquidation_repayments` do pass the measured value [8](#0-7) ). Even in the gated case, the invariant is enforced only by convention: any future or alternate prefunding path that passes a declared rather than measured amount silently turns into an unfunded drain.

### Recommendation
Make the refund book-aware or receipt-aware in the pool itself:
- Debit `cash` (via `debit_cash`/`require_reserves`) for the refunded amount, so an unfunded refund fails `InsufficientLiquidity` instead of paying out of custody, or
- Have the pool measure its own `asset_id` balance delta around the inbound leg and cap `overpayment`/`refund` at that delta, mirroring the controller's `transfer_amount_measured` pattern [9](#0-8) , or
- If the pool is intended to be controller-only, enforce it with an explicit caller check rather than relying on an off-code precondition.

### Proof of Concept
The repository already contains a self-contained reproduction: `test_unfunded_repay_overpayment_refund_also_pays_out_of_custody` [10](#0-9) . A generated `payer` calls `pool.repay(payer, [(market, custody_before)])` on a zero-debt market; `resolve_repay` takes the full-close branch, `net_repay = 0`, and `transfer_out` pays `custody_before` to `payer` while `cash` and `borrowed` remain unchanged. The same gap is documented for `ops::recapitalize::apply` (excess over the shortfall) in the test's preamble [11](#0-10) .

Caveat: I could not fully confirm whether `LiquidityPool::repay` performs a caller-authentication check in `contracts/pool/src/lib.rs` (entrypoint code was not retrieved). If it is gated to the controller, the finding downgrades to a fragile invariant rather than a directly reachable exploit; the unfunded-refund primitive itself is confirmed by the in-repo test.

pub(crate) fn accounting(
    env: &Env,
    hub_asset: HubAssetKey,
    amount: i128,
) -> RecapitalizationOutcome {
    require_nonneg_amount(env, amount);
    let mut cache = ops::renewed_market(env, &hub_asset);

    let applied = amount.min(guards::backing_shortfall(&cache));
    let refund = amount
        .checked_sub(applied)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow));

    cache.credit_cash(applied);
    cache.commit();

/// The refund gap is not specific to `recapitalize`. Two pool legs refund an
/// excess derived from a declared inbound amount, not from the cash book:
/// `ops::recapitalize::apply` (the excess over the shortfall) and
/// `ops::repay::apply` (the excess over the debt). Neither refund debits `cash`
/// or passes `require_reserves`.
///
/// A repay against a market with no debt makes the entire declared amount an
/// overpayment: `current_debt_ceil` is zero, so `resolve_repay` takes the
/// full-close branch and `net_repay` is zero. The `RepayRoundsToZeroShares`
/// assert in `ops::repay::accounting` passes on its `net_repay == 0` disjunct,
/// and the whole amount is refunded out of real custody with the book untouched.
#[test]
fn test_unfunded_repay_overpayment_refund_also_pays_out_of_custody() {
    let t = TestSetup::new();
    let token = token::Client::new(&t.env, &t.asset);
    let payer = Address::generate(&t.env);

    let custody_before = token.balance(&t.pool);
    let before = t.state_snapshot();
    assert_eq!(
        before.cash, custody_before,
        "fixture guard: book and custody must start in sync"
    );
    assert_eq!(before.borrowed, 0, "fixture must carry no debt");

    // Nothing transferred in, no debt to retire: the whole amount is "excess".
    let credited = t
        .client()
        .repay(&payer, &t.ract(0, custody_before))
        .get_unchecked(0)
        .actual_amount;
    assert_eq!(credited, 0, "no debt was retired, so nothing is credited");
    assert_unfunded_refund_drained_custody(&t, &payer, custody_before, &before);
}
