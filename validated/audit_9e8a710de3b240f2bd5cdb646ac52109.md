### Title
`msgValue` not decremented after ETH→feeToken swap in Tron `IntentGatewayV2::placeOrder`, causing native ETH to be silently trapped or double-spent against escrow accounting - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
In the Tron variant of `IntentGatewayV2.sol`, `placeOrder` pays `order.fees` by swapping native ETH for the fee token via `swapETHForExactTokens{value: msgValue}(...)` when `msgValue > 0`. Unlike the EVM mainline contract (`evm/src/apps/IntentGatewayV2.sol:383-386`), which does `msgValue -= amounts[0];` after the swap, the Tron variant never reduces `msgValue` after the swap call. ### Finding Description
`placeOrder` tracks `msgValue` as a running counter of the caller's unspent `msg.value`, decrementing it for every native-token input escrowed at line 456-457. When `order.fees > 0` and the user pays the fee in ETH, the fee-swap branch spends up to `msgValue` wei of ETH on the router (`swapETHForExactTokens{value: msgValue}`), but the actual amount consumed by the swap (`amounts[0]`, returned by the router) is discarded — the code doesn't capture the return value or subtract it from `msgValue`, unlike the sibling implementation in `evm/src/apps/IntentGatewayV2.sol` which explicitly does `msgValue -= amounts[0];`.

Because the Tron `placeOrder` function has no post-fee refund-of-unspent-ETH step (unlike the mainline version's `if (msgValue > 0) { _sendValue(msg.sender, msgValue); }` at line 395-397), any ETH sent for input escrow plus the (unswapped) leftover from the fee route is not reconciled — the stale `msgValue` figure is simply dropped, with no path to return or use it. This mirrors the reported `protocolFeeOwed` bug class: an accounting variable representing "funds still owed/held" is updated in one payment branch (native path in the mainline contract) but not in the sibling branch (Tron fee-swap), leading to an incorrect internal accounting state after a supported payment rail is used.

### Impact Explanation
Native ETH sent by the order-placer to cover `order.fees` is not properly accounted after the swap. Any ETH overshoot (the difference between `msgValue` sent to the router and `amounts[0]` actually consumed) is permanently stuck in the contract with no bookkeeping variable tracking it and no user-facing refund mechanism, unlike the corresponding EVM contract. This is a freezing-of-funds condition reachable by any unprivileged order-placer paying the fee in native ETH.

### Likelihood Explanation
Any user calling `placeOrder` with `order.fees > 0` and supplying native ETH as `msgValue` (which is a documented, first-class payment rail per the intent gateway fee documentation) triggers this path. Because `swapETHForExactTokens` typically consumes less than the max ETH supplied (it computes exact-in amount for exact-out tokens and can return unspent value depending on router semantics/slippage), any msgValue not exactly equal to `amounts[0]` results in silently orphaned value with no explicit tracking or refund.

### Recommendation
Capture the return value of `swapETHForExactTokens` in the Tron `placeOrder` implementation and decrement `msgValue` accordingly, matching the mainline `evm/src/apps/IntentGatewayV2.sol` implementation; then add the missing "refund unspent native tokens to `msg.sender`" step after the fee-escrow block so any leftover `msgValue` (from either input escrow or the fee swap) is returned to the caller instead of being stranded.

### Proof of Concept
1. Deploy the Tron `IntentGatewayV2` with `order.fees = X` (fee-token amount) and a configured Uniswap V2-style router.
2. Call `placeOrder` with a non-zero `order.input` amount paid in ERC20 (so `msgValue` remains equal to `msg.value` after Phase 1's input loop) and send `msg.value` = `Y` ETH, where `Y` is intentionally set higher than the amount the router will actually consume to buy `X` fee tokens.
3. Observe: `swapETHForExactTokens{value: Y}(X, path, address(this), ...)` executes, spending `amounts[0] < Y` wei; the surplus `Y - amounts[0]` remains in the contract's ETH balance.
4. `msgValue` is never decremented by `amounts[0]`, and there is no subsequent `_sendValue(msg.sender, msgValue)` refund call in the Tron contract (confirmed absent by inspection at `evm/tron/contracts/apps/IntentGatewayV2.sol:471-506` versus `evm/src/apps/IntentGatewayV2.sol:394-397`).
5. Result: the caller's surplus ETH (`Y - amounts[0]`) is permanently locked in the contract with no accounting entry or recovery path, confirming the freezing-of-funds impact.
