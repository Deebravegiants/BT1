This confirms the analog is reachable and concrete: `MainEVMCircuitMin` (used for `HINKAL_EMPORIUM_ACTION_ID` when `erc20TokenAddresses.length == 0`, per `CircomDataBuilder.formInputForCircom` at [1](#0-0) ) only constrains `outTimeStamp` and `calldataHash` against an arbitrary `messageSeed` — it enforces no relationship to any funds, balances, or nullifiers [2](#0-1) . Any address holding a valid relay/originalSender combination can trivially produce a "valid" proof for this path.

### Title
Emporium unsigned (`signerAddress == address(0)`) stateless ops with zero-length `erc20TokenAddresses` allow unauthorized draining of Emporium's native ETH balance - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`EmporiumUpgradeable.runAction` executes `EmporiumOperation`s that carry attacker-chosen `endpoint`, `callData`, and `value` fields. When `stack.signerAddress == address(0)`, `verifyWallet` skips all signature verification and returns immediately [3](#0-2) . The subsequent "Stateless Interaction" branch performs `op.endpoint.call{value: op.value}(op.callData)` directly from the Emporium contract's own balance, with `op.value` fully attacker-controlled [4](#0-3) .

### Finding Description
The only guardrail against unbounded native-ETH outflow is the post-execution balance check performed per-token over `circomData.erc20TokenAddresses`:
```
for (uint256 i = 0; i < circomData.erc20TokenAddresses.length; i++) { ... if (balanceChange < 0) revert BalanceChangeShouldBePositive(); }
``` [5](#0-4) 

`CircomDataBuilder.formInputForCircom` selects a minimal circuit (`MainEVMCircuitMin`) precisely when `externalActionId == HINKAL_EMPORIUM_ACTION_ID && erc20TokenAddresses.length == 0` [1](#0-0) . In that case the balance-preservation loop in `runAction` iterates zero times — no check is performed on the contract's native ETH (or any token) balance at all. The `MainEVMCircuitMin` template only proves knowledge of a `messageSeed` hashing to `message`, constraining nothing about funds movement, nullifiers, or the `EmporiumOperation[]` array's `op.value`/`op.endpoint` fields beyond the fact that they hash into `calldataHash` (which is itself only a passive integrity check, not a value-conservation constraint) [2](#0-1) .

Because `verifyWallet` short-circuits for `signerAddress == address(0)` with no signature check [6](#0-5) , an unprivileged caller acting as its own relay (satisfying `relayerIsValid`/`originalSender` checks in `HinkalHelper.performHinkalChecks`) can submit a `transact` call whose `CircomData.externalActionData.externalActionId == HINKAL_EMPORIUM_ACTION_ID`, `erc20TokenAddresses = []`, and `externalActionMetadata` decodes to an `EmporiumStack` with `signerAddress = address(0)` and one `EmporiumOperation` whose `endpoint` is the attacker's own address and `value` equals however much native ETH currently sits in the Emporium contract (accumulated from other users' shielded deposits, un-invoked wallet funds, or dust). The `op.endpoint.call{value: op.value}(op.callData)` then sweeps that ETH with no balance check ever executed to catch the shortfall.

This is the direct analog of the ArbitrumBridgeFacet bug: an outbound native-value transfer sized by attacker-controlled data is not checked against what was actually deposited/committed by the transaction, permitting sweep of ether resting in the protocol's shared contract (Emporium plays the role LibDiamond plays in LI.FI).

### Impact Explanation
Critical: direct theft of protocol/user funds (native ETH) held by the `Emporium` contract, executed by an unprivileged EOA with no signature, no shielded-UTXO ownership proof, and no balance-conservation check whatsoever for the drained asset.

### Likelihood Explanation
High. Reaching this path requires only: (1) a self-relayed `transact` call satisfying the ordinary relay/originalSender checks in `HinkalHelper.performHinkalChecks` (no privileged role needed), and (2) a trivial ZK proof for `MainEVMCircuitMin`, which has no economic constraints. The only precondition is that Emporium hold a non-zero ETH balance at the time of attack (plausible given deposits/refunds/dust routed through it via `HinkalWallet`/relay fee flows).

### Recommendation
- Never allow the zero-token-array (`erc20TokenAddresses.length == 0`) Emporium code path to skip native-asset balance accounting. Always include `address(0)` in the balance-diff check whenever any `EmporiumOperation` in the decoded stack carries non-zero `op.value`, regardless of `erc20TokenAddresses.length`.
- Do not let `verifyWallet` fully bypass authorization when `signerAddress == address(0)`; if unsigned/relay-only stateless ops are intended, bound `op.value` to zero (or to funds explicitly accounted for via `deltaAmountChanges`) rather than allowing arbitrary outbound value.
- Track Emporium's own ETH balance immutably (a `require(address(this).balance == balanceBefore[native] - explicitly-authorized-outflow)` style check) independent of whether `erc20TokenAddresses` includes `address(0)`.

### Proof of Concept
1. Attacker becomes their own relay (or otherwise satisfies `relayerIsValid`) and sets `circomData.originalSender = attacker`, `circomData.relay = attacker`.
2. Constructs `circomData.erc20TokenAddresses = []`, `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `externalActionData.externalAddress = EmporiumUpgradeable address`.
3. Encodes `externalActionData.externalActionMetadata` as an `EmporiumStack` with `signerAddress = address(0)`, `ops = [{ endpoint: attackerAddress, invokeWallet: false, value: address(emporium).balance, callData: "" }]`.
4. Generates a trivial `MainEVMCircuitMin` proof (only needs a `messageSeed` and matching `calldataHash`/`outTimeStamp`).
5. Calls `Hinkal.transact(...)`; `_externalTransact` invokes `Emporium.runAction`; `verifyWallet` returns immediately (no signature required); the loop performs `attackerAddress.call{value: emporium.balance}("")`, transferring all of Emporium's ETH to the attacker; the post-loop balance-check loop is empty (`erc20TokenAddresses.length == 0`) and never reverts.
