Confirmed. The Tron `IntentGatewayV2.onAccept` (`evm/tron/contracts/apps/IntentGatewayV2.sol:629-683`) has no `_relayer`/`_checkRelayer` mechanism at all — it is entirely absent from that contract — while the canonical EVM `IntentGatewayV2`/`ExtrinsicIntents.onAccept` (`evm/src/apps/intentsv2/ExtrinsicIntents.sol:75-78,330`) gates every delivery (redemptions, refunds, and all governance actions) behind `_checkRelayer(incoming.relayer)` before any body byte is read.

### Title
Tron IntentGatewayV2 `onAccept` omits the relayer-allowlist gate enforced on the canonical EVM gateway - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The mainline EVM `IntentGatewayV2` (via `ExtrinsicIntents.sol`) enforces a single-authorised-relayer allowlist on every `onAccept`/`onGetResponse` delivery before the request body is even decoded — this is a deliberate, documented authorization control (see `sdk/packages/core/docs/ai/changelog/2026-09-03-relayer-allowlist-on-the-intent-gateway.md` and `sdk/packages/core/docs/ai/flows/how-a-cross-chain-delivery-reaches-the-gateway-and-where-the.md`). The Tron port of the same contract (`evm/tron/contracts/apps/IntentGatewayV2.sol`) implements the identical `onAccept` dispatch surface (`RedeemEscrow`, `RefundEscrow`, `NewDeployment`, `UpdateParams`, `SweepDust`) but never declares `_relayer`, `_checkRelayer`, or `setRelayer` — the allowlist gate simply does not exist in this variant.

### Finding Description
On the canonical implementation, `ExtrinsicIntents._checkRelayer` (`evm/src/apps/intentsv2/ExtrinsicIntents.sol:75-78`) is called as the very first line of `onAccept` (`evm/src/apps/intentsv2/ExtrinsicIntents.sol:330`), rejecting any delivery whose `incoming.relayer` (the `msg.sender` that called `HandlerV2.handlePostRequests`/`handleGetResponses`, per `evm/src/core/HandlerV2.sol:181-210` and `EvmHost.dispatchIncoming`) is not the single authorised relayer, once one is configured. [1](#0-0) 

The Tron `IntentGatewayV2.onAccept` reuses the same `RequestKind` dispatch structure and the same `IApp.onAccept(IncomingPostRequest)` entry point, meaning it receives the same `incoming.relayer` field carrying the untrusted `msg.sender` of whoever submitted the proof to the (permissionless) handler on that chain. But it never checks that field: [2](#0-1) 

`RedeemEscrow`/`RefundEscrow` are gated only by `authenticate(incoming.request)` (source-module check), and `NewDeployment`/`UpdateParams`/`SweepDust` are gated only by the "source is Hyperbridge" check — both checks that the mainline contract also performs, but *in addition to*, not *instead of*, the relayer allowlist. Since handler submission is explicitly permissionless ("All handler methods are permissionless - anyone can call them to relay messages", `docs/content/developers/evm/api/ihandler.mdx:24`), any untrusted party who can produce/relay a valid consensus+state proof for a message that was legitimately dispatched by Hyperbridge or a paired gateway becomes the one who triggers `onAccept` on Tron — a class of caller the mainline design explicitly intends to exclude once a relayer is armed.

### Impact Explanation
This breaks the authorization model that the rest of the protocol relies on: the operator-configured relayer allowlist is the only mechanism (per the project's own flow documentation) protecting governance-critical `onAccept` actions — `NewDeployment` (registers a new trusted gateway instance per state machine, directly controlling where future `RedeemEscrow`/`RefundEscrow` funds are authenticated to/from), `UpdateParams` (protocol fee configuration), and `SweepDust` (transfers accumulated protocol-held tokens to an attacker-supplied beneficiary) — from being triggered by any relayer instead of only the governance-designated one. On the Tron deployment, an unprivileged party who races or reproduces a legitimately-sourced Hyperbridge governance message (or any handler-relayed message) can be the one whose delivery lands, defeating the "only the authorised relayer may effect this state change" guarantee that underlies the design elsewhere in the codebase (see `HostManagerTest.testForgedHandlerSwapIsRefused` and related tests validating exactly this property on the canonical contracts). This is an authorization-bypass / unauthorized-app-action class issue consistent with the reported analog: an allowlist enforced on one ingress path (mainline EVM gateway) silently missing on a structurally identical ingress path (Tron gateway) reachable from the same untrusted relayed-message surface.

### Likelihood Explanation
Handler submission is permissionless by design, so no privilege is required to become the "relayer" of a message once a valid proof exists; the only missing barrier is the allowlist check itself, which is present everywhere else in the codebase but absent here. The bug requires no admin/governance compromise — the Tron contract's own source review is sufficient to see the gate is missing.

### Recommendation
Port the `_relayer`/`_checkRelayer`/`setRelayer` mechanism from `evm/src/apps/intentsv2/ExtrinsicIntents.sol` (and its interface additions) into `evm/tron/contracts/apps/IntentGatewayV2.sol`, and call `_checkRelayer(incoming.relayer)` as the first statement of `onAccept` (and any `onGetResponse` equivalent) before the request kind or body is inspected, matching the canonical contract exactly.

### Proof of Concept
1. Deploy/observe the Tron `IntentGatewayV2` with governance intending only relayer `R` to submit deliveries (as is standard for the canonical gateway, per `sdk/packages/core/docs/ai/changelog/2026-09-03-relayer-allowlist-on-the-intent-gateway.md`).
2. A legitimate Hyperbridge-sourced `UpdateParams`/`NewDeployment`/`SweepDust` message (or a legitimately-dispatched `RedeemEscrow`/`RefundEscrow`) becomes provable once consensus/state finalizes on Hyperbridge.
3. Any third party (not `R`) submits the proof to the Tron handler; `dispatchIncoming` calls `IntentGatewayV2.onAccept` with `incoming.relayer == thirdParty`.
4. Compare to `evm/src/apps/intentsv2/ExtrinsicIntents.sol:75-78,330`, where step 3 would revert with `Unauthorized`; on Tron (`evm/tron/contracts/apps/IntentGatewayV2.sol:629-683`) no such check exists, so the action executes exactly as if `R` had submitted it — confirming the allowlist is bypassed on this ingress path while being enforced on the sibling implementation.
