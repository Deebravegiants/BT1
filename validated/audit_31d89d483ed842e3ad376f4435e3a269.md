### Title
Webhook shop/topic identity spoofing via body-only HMAC verification — cross-tenant webhook confusion (`lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC of the raw request body via `Utils::HmacValidator.validate(request)`. The `shop-domain`, `topic`, and `webhook-id` values that the handler subsequently trusts to route and attribute the event are taken directly from HTTP headers, which are **not** part of the signed bytes.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, and `webhook_id` accessors read straight from headers, none of which are covered by that signable string: [2](#0-1) 

`Registry.process` validates only the HMAC of this request object, then trusts `request.topic` to select the handler and forwards `request.shop`, `request.topic`, and `request.webhook_id` into `WebhookMetadata` for the handler to act on: [3](#0-2) 

The identity binding that should hold is: `bytes verified by HMAC == bytes the application treats as authoritative for shop/topic attribution`. Here that equality is broken — `HmacValidator.validate` only proves "the body bytes were produced by someone who can compute HMAC-SHA256(secret, raw_body)", which for a Shopify webhook is provably Shopify **for that specific shop's webhook body**. It says nothing about which shop or topic header accompanies the request. Documentation instructs consumers to trust `data.shop` and `data.topic` directly as the tenant/topic identity: [4](#0-3) 

### Impact Explanation
An unprivileged internet user who installs the target app on their own store (a normal, unprivileged install — no special credential, admin access, or `api_secret_key` needed) will receive legitimately-HMAC-signed webhook deliveries for their own shop. Because the signature covers only the body, the attacker can capture one such valid `(raw_body, hmac)` pair and replay it to the app's webhook endpoint with an arbitrary `X-Shopify-Shop-Domain` and/or `X-Shopify-Topic` header. `Registry.process` will:
1. Validate the (still-valid, since body unchanged) HMAC.
2. Route based on the attacker-chosen `topic` header to a different handler than the one the payload was actually generated for.
3. Pass the attacker-chosen `shop` value into `WebhookMetadata`, which the host application uses to decide which tenant record to update.

This crosses a tenant boundary: data intended for the attacker's own shop can be attributed to (and processed against) a different, victim shop record in the host application, satisfying the "cross-tenant access" impact category.

### Likelihood Explanation
Requires only that the attacker be able to install the target app for free/normally (a routine, unprivileged action for any Shopify merchant) and be able to send arbitrary HTTP headers to the app's public webhook endpoint — both trivially achievable. No secret material, session, or privileged account is required.

### Recommendation
Include `shop-domain`, `topic`, and `webhook-id` in the HMAC-signed material (or otherwise cryptographically bind them to the signed body), and reject the request if those bound values don't match the ones the caller relies on. At minimum, document that consuming applications must not use `data.shop`/`data.topic` from `WebhookMetadata` as an authoritative tenant identifier without separately validating that the webhook's registered subscription actually corresponds to that shop.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, receiving a real webhook for topic `orders/create` with body `B` and a valid `X-Shopify-Hmac-Sha256` header computed as `HMAC-SHA256(secret, B)`.
2. Attacker replays the exact same `B` and HMAC header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` and/or `X-Shopify-Topic: customers/redact`.
3. `ShopifyAPI::Webhooks::Registry.process` computes `Utils::HmacValidator.validate(request)`, which only checks `B` against the HMAC — validation succeeds.
4. The handler is invoked with `WebhookMetadata.new(topic: "customers/redact", shop: "victim-shop.myshopify.com", body: <attacker's orders/create body>, ...)`, causing the host application to process the attacker's data as if it belonged to `victim-shop.myshopify.com` under a different topic than actually signed.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
