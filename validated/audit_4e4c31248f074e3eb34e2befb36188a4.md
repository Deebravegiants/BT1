Audit Report

## Title
CORS wildcard-origin allowlist bypass via missing domain-boundary check in `isAllowedOrigin` - (File: core/services/gateway/network/httpserver.go)

## Summary
The Gateway HTTP server's `isAllowedOrigin` function matches wildcard CORS entries (e.g., `*.remix.com`) using a raw `strings.HasSuffix(originHost, allowedHost)` check after stripping the `*.` prefix, without verifying a `.` domain-boundary immediately precedes the match. This allows any attacker-controlled hostname that merely ends with the configured domain string (e.g., `evilremix.com`) to be treated as a valid subdomain match.

## Finding Description
In `isAllowedOrigin` [1](#0-0) , when an allowed origin has the form `*.remix.com`, the code strips `*.` leaving `allowedHost = "remix.com"`, then checks `strings.HasSuffix(originHost, allowedHost)`. This check has no requirement that the character preceding the matched suffix in `originHost` be a `.`, so `evilremix.com` incorrectly satisfies `HasSuffix("evilremix.com", "remix.com") == true`.

This flawed result is consumed directly in `handleRequest` [2](#0-1) , which reflects the attacker-supplied `Origin` header value back as `Access-Control-Allow-Origin` when `isAllowedOrigin` returns true, thereby granting cross-origin browser access to an origin the operator did not intend to trust. There is no additional authentication or role check that would prevent this — CORS validation is the sole gate here, and it is broken for the wildcard case.

## Impact Explanation
This is a genuine implementation bug in a documented, supported configuration feature (wildcard CORS origins), not an operator misconfiguration — the operator correctly specifies `*.remix.com` intending to scope trust to subdomains of `remix.com`, but the flawed suffix check silently extends that trust to any domain sharing the suffix (e.g., `evilremix.com`, `not-remix.com`). This maps to the in-scope "gateway request impersonation / allowlist bypass" impact category, since an attacker-controlled origin can be granted `Access-Control-Allow-Origin` reflection, letting a browser-based attacker read cross-origin responses from the Gateway's HTTP API as though from a trusted origin.

## Likelihood Explanation
Exploitation requires only: (1) the Gateway operator has enabled CORS with at least one wildcard entry (a normal, documented configuration option, not a misuse), and (2) an attacker registers/controls any domain sharing the configured suffix and lures a victim's browser to send a request with that `Origin` header to the Gateway. No credentials, privileged roles, or host/database access are needed — this is directly reachable by any unprivileged web client hitting the internet-facing Gateway HTTP endpoint.

## Recommendation
Enforce a domain boundary in the wildcard suffix check, e.g., verify that `originHost` equals the base domain or ends with the base domain preceded by a literal `.`:
```go
if strings.HasPrefix(allowedHost, "*.") {
    base := allowedHost[2:]
    if originHost == base || strings.HasSuffix(originHost, "."+base) {
        return true
    }
}
```

## Proof of Concept
1. Configure the Gateway with `CORSEnabled: true` and `CORSAllowedOrigins: ["https://*.remix.com"]`.
2. Send an HTTP request to the Gateway's configured path with header `Origin: https://evilremix.com`.
3. Observe `isAllowedOrigin` computes `allowedHost = "remix.com"` and `strings.HasSuffix("evilremix.com", "remix.com")` evaluates to `true`, causing `handleRequest` to respond with `Access-Control-Allow-Origin: https://evilremix.com`.
4. This can be codified as a Go unit test directly calling `isAllowedOrigin("https://evilremix.com")` against a server configured with `CORSAllowedOrigins: []string{"https://*.remix.com"}` and asserting it incorrectly returns `true`.
