### Title
Unbounded gzip decompression in `unzipIcon()` allows a zip-bomb DoS before SVG validation runs - ([File: adapters/storage-icons-browser/src/utils.js], [File: adapters/storage-icons-mobile/src/icons-storage.js])

### Summary
`unzipIcon()` in both the browser and mobile icon-storage adapters fully decompresses an attacker-influenced `token.icon` gzip/base64 blob with `zlib.gunzip` / `pako.ungzip` before any size check, `@exodus/svg-safe` `cleanup()`, or `validate()` ever executes. A custom-token registry response with a highly compressible icon payload can force the wallet process to allocate an arbitrarily large decompressed buffer, causing an out-of-memory crash/DoS prior to any content validation.

### Finding Description
`token.icon` originates from the custom tokens registry HTTP response fetched via `#fetch` in `features/assets-feature/module/assets-module.js` (`fetchToken`, `#fetchTokens`, `#fetchTokensByNames`, `#fetchUpdates`, `addRemoteTokens`), all of which eventually call `#storeIcons` → `iconsStorage.storeIcons(tokens)`.

In the browser adapter: [1](#0-0) 
`gunzip` decompresses the entire buffer into memory with no output-size limit, and only after `unzip.toString('utf8')` is produced does `cleanup()` (which calls `validate()`) run.

In the mobile adapter: [2](#0-1) 
`pako.ungzip` similarly performs a single-shot, unbounded decompression into a string before `cleanupSVG`/`validateSVG` are invoked.

`validateCustomToken` (schema validation) may bound the base64 `icon` field's *compressed* length, but there is no check anywhere in `#storeIcon`/`unzipIcon` that caps the *decompressed* output size before it is fully materialized in memory. Since a single DEFLATE stream can achieve compression ratios in the range of ~1000:1, even a schema-bounded base64 icon field can decompress into a proportionally large buffer, and nested/optimized inputs can push this further. The size/complexity check that would reject an oversized SVG (`validate()` in `libraries/svg-safe/src/validate.mjs`) only runs on the fully decompressed string, i.e. after the expensive/oversized allocation has already occurred.

### Impact Explanation
Because `#storeIcon` is invoked from the icon-storing path that runs as part of ordinary custom-token fetch/update flows (`fetchToken`, `addRemoteTokens`, background `updateTokens`), a malicious or compromised custom-tokens registry response (an accepted "remote config/API response" vector) can cause the wallet's extension background process or mobile app process to attempt a very large in-memory allocation. This can crash or hang the process, creating a denial-of-service that blocks in-flight signing/approval UI until the process restarts. This does not by itself lead to key disclosure, unauthorized signing, or auth bypass — it is a scoped availability/DoS impact on the wallet process.

### Likelihood Explanation
Exploitability requires the attacker to control (or MITM) the custom-tokens registry server response that supplies `token.icon`, which is one of the explicitly accepted vectors ("remote config or API responses") in this audit's scope. Given that vector, the exploit is straightforward and fully reproducible: craft a highly compressible payload, base64-encode it, and set it as `token.icon`. No authentication, account state, or user interaction is needed beyond the wallet performing its normal custom-token fetch/update cycle.

### Recommendation
Enforce a hard cap on decompressed size before or during decompression in both `unzipIcon` implementations (e.g., stream `gunzip`/`ungzip` with an output byte-count guard that aborts once a maximum threshold, such as a few hundred KB, is exceeded), rather than relying solely on compressed-input length limits and post-hoc regex validation in `cleanup()`/`validate()`.

### Proof of Concept
Add a fuzz/unit test to `adapters/storage-icons-browser/src/__tests__` and `adapters/storage-icons-mobile/src/__tests__`:
1. Generate gzip payloads with increasing compressed-to-decompressed ratio (e.g., gzip of `'A'.repeat(N)` for N = 10MB, 100MB, 1GB) and base64-encode them as `token.icon`.
2. Call `storeIcons([{ name: 'test', icon: payload }])` (or `unzipIcon(payload)` directly) and measure process RSS / wall time.
3. Assert that decompression is rejected (throws a "payload too large" error) once decompressed size exceeds a defined cap, and that this rejection happens before `cleanup()`/`validate()` are reached — i.e., instrument/mock `cleanup` to assert it is never called for oversized payloads.

```javascript
import { gunzip } from 'zlib'
import { cleanup } from '@exodus/svg-safe'

export const unzipIcon = async (base64) => {
  const buff = Buffer.from(base64, 'base64')
  const unzip = await new Promise((resolve, reject) => {
    gunzip(buff, (err, res) => {
      if (err) {
        reject(err)
        return
      }

      resolve(res)
    })
  })
  return cleanup(unzip.toString('utf8'))
}
```
