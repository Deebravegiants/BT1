Based on the code I reviewed, `limitSecretReferences` at [1](#0-0) , and does not inspect `pod.Spec.Volumes[].VolumeSource.Projected.Sources[].Secret` (projected volume secret sources), even though the standard core API type `VolumeProjection` supports a `Secret` field alongside `ConfigMap`, `DownwardAPI`, and `ServiceAccountToken` projections.

### Title
Projected-volume Secret sources bypass ServiceAccount mountable-secrets enforcement - (plugin/pkg/admission/serviceaccount/admission.go)

### Summary
`limitSecretReferences` enumerates only `volume.VolumeSource.Secret` when validating pod volumes against the ServiceAccount's `mountableSecrets` set, but never inspects `volume.VolumeSource.Projected.Sources[].Secret`. A pod can therefore mount an arbitrary Secret in the namespace via a projected volume even when `EnforceMountableSecretsAnnotation`/`LimitSecretReferences` is enabled, defeating the isolation invariant the admission controller is meant to provide.

### Finding Description
`Validate` calls `s.limitSecretReferences(serviceAccount, pod)` when `enforceMountableSecrets` is true [2](#0-1) . Inside `limitSecretReferences`, only the direct `SecretVolumeSource` case is checked: [3](#0-2) 
There is no corresponding walk of `volume.VolumeSource.Projected.Sources`, meaning a pod spec containing:
```yaml
volumes:
- name: sneaky
  projected:
    sources:
    - secret:
        name: victim-secret
```
will pass `limitSecretReferences` unconditionally, regardless of whether `victim-secret` is listed in the bound ServiceAccount's `.secrets[]`. An attacker with only namespace-scoped `create pods` RBAC (no special secret read/mount permission) can reference any Secret name in the namespace this way; the kubelet will then mount that Secret's contents into the pod's filesystem, exposing its data. This also structurally matches the pattern already special-cased for mirror pods, where the code explicitly walks `Projected.Sources` to block `ServiceAccountToken` projections [4](#0-3)  — showing the developers were aware projected sources needed separate handling in at least one code path, but the equivalent handling for `Secret` sources in `limitSecretReferences` was not implemented.

Note also that `limitEphemeralContainerSecretReferences` (invoked on the `ephemeralcontainers` subresource update path) only checks `Env`/`EnvFrom` of `EphemeralContainers`, consistent with ephemeral containers not being able to add volumes at that stage, so that path is not an additional independent bypass beyond the volumes gap.

### Impact Explanation
This is a workload isolation / secret-confidentiality bypass: an unprivileged user restricted by the "mountable secrets" invariant (RBAC intentionally scoped so a ServiceAccount can only mount specific Secrets) can read the contents of any Secret in the same namespace by mounting it through a projected volume, bypassing the specific protection `EnforceMountableSecretsAnnotation`/`LimitSecretReferences` is documented to provide. This corresponds to an unauthorized cross-tenant (within-namespace) secret disclosure / privilege-escalation-adjacent class of bug, since Secrets often contain credentials (e.g., other ServiceAccounts' tokens, DB passwords) that can subsequently be used for lateral movement.

### Likelihood Explanation
Preconditions: the target ServiceAccount must have `EnforceMountableSecretsAnnotation: "true"` (or the plugin globally configured with `LimitSecretReferences: true`), and the attacker needs only namespace-scoped RBAC to create Pods using that ServiceAccount. This is a common pattern for multi-tenant clusters. The exploit requires no special privilege beyond normal pod creation, and it's fully repeatable/deterministic — a straightforward pod spec change.

### Recommendation
Extend `limitSecretReferences` (and ideally factor out shared logic with the mirror-pod projected-volume walk) to also iterate `volume.VolumeSource.Projected.Sources[]` and validate any `Secret` projection's `Name` against `mountableSecrets`, in the same way `ServiceAccountToken` projections are already checked for mirror pods.

### Proof of Concept
Table test addition to `plugin/pkg/admission/serviceaccount/admission_test.go` (or equivalent):
1. Create a ServiceAccount `sa` with annotation `EnforceMountableSecretsAnnotation: "true"` and `Secrets: []` (no secrets referenced).
2. Construct a Pod with `Spec.ServiceAccountName: "sa"` and a volume:
   ```go
   Volumes: []api.Volume{{
       Name: "v",
       VolumeSource: api.VolumeSource{
           Projected: &api.ProjectedVolumeSource{
               Sources: []api.VolumeProjection{{
                   Secret: &api.SecretProjection{LocalObjectReference: api.LocalObjectReference{Name: "not-allowed-secret"}},
               }},
           },
       },
   }}
   ```
3. Call `plugin.Validate(ctx, admission.NewAttributesRecord(pod, ...Create...), o)`.
4. Expected (secure) assertion: `Validate` should return an `admission.NewForbidden` error referencing `not-allowed-secret`, matching the behavior already exhibited for direct `VolumeSource.Secret` references.
5. Actual (current) behavior: `Validate` returns `nil` (no error), demonstrating the bypass.

```go
func (s *Plugin) limitSecretReferences(serviceAccount *corev1.ServiceAccount, pod *api.Pod) error {
	// Ensure all secrets the pod references are allowed by the service account
	mountableSecrets := sets.NewString()
	for _, s := range serviceAccount.Secrets {
		mountableSecrets.Insert(s.Name)
	}
	for _, volume := range pod.Spec.Volumes {
		source := volume.VolumeSource
		if source.Secret == nil {
			continue
		}
		secretName := source.Secret.SecretName
		if !mountableSecrets.Has(secretName) {
			return fmt.Errorf("volume with secret.secretName=\"%s\" is not allowed because service account %s does not reference that secret", secretName, serviceAccount.Name)
		}
	}
```
