## Title
Webhook `shop-domain` (and `topic`/`api-version`/`webhook-id`) headers are trusted for tenant identification without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then uses the unauthenticated `shop-domain` header to attribute the payload to a specific merchant/tenant. Because the app's `api_secret_key` is shared across every shop that installs the app, any merchant who has installed the app can capture one of their own legitimately-signed webhooks and replay it with a forged `X-Shopify-Shop-Domain` header pointing at a different (victim) shop. The HMAC still validates because it only covers the body, so the host application's webhook handler is invoked believing the data came from the victim tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`: [1](#0-0) 

`hmac` reads the `hmac-sha256` header and `to_signable_string` returns only `@raw_body`. Note that `shop`, `topic`, `api_version`, and `webhook_id` are all exposed as separate header-derived accessors that are never mixed into `to_signable_string`.

`HmacValidator.validate` computes `OpenSSL::HMAC.hexdigest` over `verifiable_query.to_signable_string` (i.e., the body only) and compares it to the supplied `hmac`: [2](#0-1) 

`Registry.process` uses this HMAC check as the sole authentication gate, and then trusts `request.shop` (and `request.topic`) to build the `WebhookMetadata` passed to the host app's handler: [3](#0-2) 

The binding that should hold is: `hmac_verified_bytes == bytes_used_for_tenant_routing`. Instead the equality is broken — `hmac_verified_bytes = raw_body` while `bytes_used_for_tenant_routing = shop-domain header`, a field never included in the signed payload. Since `api_secret_key` is one shared secret per app (not per-shop), any shop that has installed the app can produce a body+HMAC pair that is valid for the app, then attach an arbitrary `shop-domain`/`topic`/`webhook-id` header set before replaying it to the app's public webhook endpoint. The signature check in `HmacValidator.validate` passes because it never inspects those headers, so `Registry.process` dispatches the (attacker-chosen) body to the handler under the identity of any shop the attacker names.

### Impact Explanation
This breaks the tenant boundary the gem is expected to enforce: a shop-scoped app relies on `WebhookMetadata#shop` to know which merchant's data/session to update. An attacker who is a genuine (if unprivileged, non-target) app installer can forge webhook deliveries "from" a victim shop they do not control, without ever needing the victim's credentials, access token, or the app's `client_secret` in plaintext. Depending on how the host app's webhook handler processes `data.shop` (e.g., updating stored order/product state, deleting resources, or triggering downstream automation for that shop), this enables cross-tenant data corruption or state injection — matching the "cross-tenant access" impact category.

### Likelihood Explanation
Any user can install a free/dev copy of an app on their own Shopify shop and thereby obtain valid `(body, hmac)` pairs signed with the app's real secret (since Shopify computes the HMAC using the app's shared secret when delivering webhooks to any of its installs). Forging the header set on the replayed HTTP request requires no cryptographic material and no access to the victim's shop. The only friction is discovering the app's public webhook endpoint, which is normally advertised/fixed.

### Recommendation
Bind the routing headers (`shop-domain`, and ideally `topic`/`api-version`/`webhook-id`) into the value verified by the HMAC, or otherwise cross-check that the `shop-domain` on the request corresponds to a shop that is legitimately associated with the specific delivery (e.g., verify against Shopify's IP allowlist, or require the host app to independently confirm the shop has an active session/install before trusting the payload). At minimum, document prominently that `request.shop` is unauthenticated and must not be used to select per-tenant state without additional verification.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and receives a real webhook, e.g. `orders/create`, with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
2. Attacker resends the same `(B, H)` pair to the app's webhook endpoint but replaces the header `X-Shopify-Shop-Domain: attacker.myshopify.com` with `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers (they are not part of the signable content): [4](#0-3) 
4. `Utils::HmacValidator.validate` succeeds because it only recomputes the HMAC over `@raw_body`, which is unchanged.
5. `Registry.process` invokes the handler with `WebhookMetadata.new(... shop: "victim.myshopify.com" ...)`, causing the host app to process attacker-controlled data as though it originated from the victim shop.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
