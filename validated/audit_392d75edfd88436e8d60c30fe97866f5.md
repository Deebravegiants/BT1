## Title
Webhook shop-domain header not covered by HMAC and not format-validated, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` extracts the `shop` value from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, but the HMAC signature validated by `ShopifyAPI::Webhooks::Registry.process` only covers the raw request body, never the shop-domain header. Any party that can obtain one valid `(body, HMAC)` pair signed with the app's `api_secret_key` (e.g. by installing the app on their own store and receiving legitimate webhooks) can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `shop-domain` header, and the request will still pass `HmacValidator.validate`.

### Finding Description
- `Request#hmac` and `Request#to_signable_string` are defined as: [1](#0-0) 
`to_signable_string` returns only `@raw_body`; none of the headers (`topic`, `shop`, `api_version`, `webhook_id`) are part of the signable string.

- `HmacValidator.validate` computes the HMAC strictly over `verifiable_query.to_signable_string` and compares it to the received signature: [2](#0-1) 

- `Registry.process` trusts `request.shop` (a raw, unauthenticated header value) as the tenant identifier and forwards it straight into the handler payload with no additional binding to the verified body: [3](#0-2) 

- Unlike `Session`/OAuth flows, which use `lib/shopify_api/utils/shop_validator.rb` to validate shop-domain format and origin, `Webhooks::Request#shop` performs no such validation and is not cross-checked against the HMAC-covered content: [4](#0-3) 

The documentation states that `Registry.process` "will verify the request did indeed come from Shopify," implying full authenticity of the delivered data, including `data.shop`: [5](#0-4) 
but this only proves the *body* originated from a request signed with the app secret — it says nothing about which shop the header claims to be from.

This breaks the identity binding: **shop authenticated (via HMAC-verified content) ≠ shop stored/acted upon (header value passed to the handler)**.

### Impact Explanation
An unprivileged attacker who legitimately installs the target app on their own (attacker-controlled) Shopify store will receive genuine webhook deliveries from Shopify — each with a body and an HMAC computed using the real `api_secret_key`. Because the HMAC never covers the `shop-domain` header, the attacker can capture one such `(raw_body, hmac)` pair and resend it to the app's webhook endpoint with the `shopify-shop-domain` header rewritten to any victim shop's domain. `HmacValidator.validate` will still succeed (it only checks the body), and `WebhookMetadata` is constructed with the attacker-controlled `shop` value, so the app's handler will process attacker-supplied body content as if it were authentic data for the victim shop. Depending on how the host app keys data by `data.shop` (the documented, expected usage pattern), this enables cross-tenant data injection/confusion — e.g. writing attacker-controlled webhook payloads into a victim shop's records, or triggering mandatory-topic handlers (`shop/redact`, `customers/redact`, `customers/data_request`) against a victim tenant. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires no credentials beyond signing up as a normal merchant/installer of the app (freely available to any internet user), and no interception of TLS traffic or access to `api_secret_key` — the attacker legitimately owns a valid signed webhook for their own store's data and merely changes an unauthenticated header on replay. The webhook endpoint is a public HTTP endpoint by design. Likelihood is High for any app that trusts `data.shop` from `WebhookMetadata` as the tenant key, which is exactly the pattern the gem's own documentation recommends.

### Recommendation
Bind the shop identity to the signed content: either include the shop domain (and other trust-critical headers) in the HMAC-signed payload verification, or require the host application to cross-validate `request.shop` against an independently-authenticated source (e.g. a known access token/session record) before trusting it, and document this requirement prominently. At minimum, apply the existing `ShopifyAPI::Utils::ShopValidator` format checks to `Webhooks::Request#shop` and clearly document that the shop-domain header is *not* HMAC-protected so host apps do not treat it as fully authenticated the way the current docs imply.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com`, completing OAuth normally (no special privilege required).
2. Shopify sends the attacker a legitimate webhook, e.g. `orders/create`, to the app's registered callback URL:
   - Headers: `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC of raw_body>`, `x-shopify-topic: orders/create`.
   - Body: arbitrary JSON the attacker fully controls (their own order data).
3. Attacker captures this exact `raw_body` and `x-shopify-hmac-sha256` value (both are visible to them as the recipient/originator of their own store's data).
4. Attacker sends a new POST request to the app's webhook endpoint with the **same raw_body and HMAC header**, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only hashes `raw_body` — validation succeeds.
6. The handler receives `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: <attacker's data>, ...)`, and the host app (following the documented pattern of keying by `data.shop`) processes/stores attacker-controlled data under the victim's tenant.
