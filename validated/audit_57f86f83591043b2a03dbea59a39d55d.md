### Title
Null-pointer-style DoS in `Zap._swapOnUniswapV2` when `graduatedPair` lookup returns `address(0)` - (File: packages/contracts/src/Zap.sol)

### Summary
The GHSA-7qcc-g2m9-8533 bug class is a NULL pointer dereference: a caller-influenced code path is used to select a resource reference, and if that reference resolves to null/zero, the code calls into it anyway and the transaction/process fails. `Zap._swapOnUniswapV2` (`packages/contracts/src/Zap.sol:542-561`) has the analogous shape: it resolves the HyperSwap pair address via `Bonding.graduatedPair(tokenIn)` with a fallback to `graduatedPair(tokenOut)`, and if the resolved value is still `address(0)` it unconditionally dereferences it with `IUniswapV2Pair(pair).token0()`, `.getAmountOut(...)`, and `.swap(...)`, with no `pair == address(0)` revert guard.

### Finding Description [1](#0-0) 

```solidity

```

`graduatedPair` is keyed only by the *launched token* address (`packages/contracts/AGENTS.md:61-120`, `Bonding.graduatedPair` getter at `packages/contracts/src/Bonding.sol:784-788`). The fallback logic (`graduatedPair(tokenIn)` then `graduatedPair(tokenOut)`) assumes exactly one of `tokenIn`/`tokenOut` is a launched token key with a non-zero recorded pair. In every currently-callable path this holds — `_buyOnUniswapV2`/`_sellOnUniswapV2` are only invoked from `_executeBuy`/`_sellInternal` after `bonding_.isGraduated(tokenAddress)` is confirmed true, and `finalizeGraduation` sets `lifecycle = Graduated` and `graduatedPair[token]` atomically in the same call (`packages/contracts/src/Bonding.sol:1000-1034`), so no gap exists there today. However, the function contains **no defensive `pair == address(0)` revert** the way `Router.graduate` does (`if (pairAddr == address(0)) revert PairNotFound();`, `packages/contracts/src/Router.sol:203-211`). Any future change to the two call sites, to `graduatedPair`'s keying, or to the two-phase lifecycle ordering that decouples the `isGraduated` check from the `graduatedPair` write would let `pair` resolve to `address(0)` here, and the subsequent `IUniswapV2Pair(address(0)).token0()` call — a call to an address with no code, whose ABI-decoded return value can't be produced — reverts with an undecodable low-level error, exactly mirroring fltk's non-raster-image null dereference: a resource reference that silently resolves to null is dereferenced without a guard.

### Impact Explanation
If triggered, every post-graduation buy/sell through `Zap` for the affected token would revert unconditionally — a permanent freeze of trading for that token via the Zap entry point (holders would be limited to swapping directly against the raw HyperSwap pair, bypassing Zap's fee/referral accounting). This matches the "permanent freezing of trader ... funds" acceptance criterion for a High-severity finding, contingent on the guarded precondition (`isGraduated` ⇒ `graduatedPair` set) being violated by any future change.

### Likelihood Explanation
Low under the current code, because the only two callers already gate on `bonding_.isGraduated(tokenAddress)` which today is written atomically with `graduatedPair` inside `finalizeGraduation`. This is a **defense-in-depth gap** rather than a presently-exploitable path by an unprivileged caller with today's code: I could not construct a concrete unprivileged-caller sequence that makes `pair == address(0)` reachable in the current `Bonding`/`Zap` wiring.

### Recommendation
Add an explicit `if (pair == address(0)) revert ZeroAddress();` (or a dedicated `PairNotFound` error) immediately after the fallback resolution in `_swapOnUniswapV2`, mirroring the guard already present in `Router.graduate`. This converts a potential undecodable low-level revert into the project's standard clean error and removes the null-dereference-shaped hazard for any future refactor of the graduation atomicity or `graduatedPair` keying.

### Proof of Concept
Not reproducible as a standalone unprivileged-caller exploit against the current code: the only reachable path to `_swapOnUniswapV2` is already gated by `isGraduated`, which is set atomically with `graduatedPair` in `finalizeGraduation`. This finding is reported as a hardening gap (missing null-address guard analogous to the null-pointer-dereference bug class) rather than a demonstrated live exploit; a PoC would require first demonstrating a way to desynchronize `isGraduated` from `graduatedPair`, which is not currently possible with the code as reviewed.
