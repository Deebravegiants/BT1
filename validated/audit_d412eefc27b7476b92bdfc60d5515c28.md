### Title
Malicious swap route venue executes arbitrary token transfers under the caller's authorization tree - (File: contracts/swap-aggregator/src/venues/mod.rs)

### Summary
The swap router keeps no allowlist of pool/venue addresses: each hop invokes whatever `pool` address the user-supplied `swap_xdr` names. A rogue "pool" contract placed in a route can therefore run arbitrary code on the call stack below the caller's `require_auth`, and any `token.transfer(caller, attacker, x)` it issues is recorded as a child of the caller's own authorization entry. If the caller signs the simulated auth tree without decoding it, the rogue contract drains arbitrary tokens from the caller's wallet — the direct analog of a malicious MacPorts mirror executing commands on the client: untrusted code supplied through a fetched artifact runs under the victim's authority.

### Finding Description
`execute_strategy(sender, total_in, swap_xdr)` decodes a `StrategyPayload` whose `assets` registry contains attacker-chosen pool addresses, and `dispatch_hop` invokes them via `env.invoke_contract(&ctx.hop.pool, ...)` with no allowlist check (`venues/mod.rs:34-40`, `venues/phoenix.rs:23-25`, `venues/sushi.rs:48-50`). The only sender-facing auth is `sender.require_auth()` covering the input `transfer`; all venue calls sit below that entry. In Soroban recording mode, a `token.transfer(victim, to, amount)` executed by the rogue pool joins the victim's authorization tree as a child invocation, and in enforcing mode it executes because the victim signed the tree. This is reachable both directly via `Router::execute_strategy` and through controller strategies (`swap_collateral`, `swap_debt`, `multiply`, `repay_debt_with_collateral`) which call the router with the user-supplied route — the threat model itself notes "the router calls the pool and token addresses its payload names and keeps no allowlist" and that "the loss is then the caller's wallet, not the routed amount" (`docs/explanation/threat-model.md:154-165`). The harness test `rogue_hop_pool_transfer_joins_caller_auth_tree.rs` demonstrates a `RogueHopPool` whose `swap` performs `token::transfer(victim, attacker, amount)` inside a controller `swap_collateral` call.

### Impact Explanation
Theft of user funds. The stolen amount is any balance of any token the victim holds — including tokens the protocol never listed — and is bounded neither by the routed `total_in`, nor by the route `min_out`, nor by the controller's final account-risk check. The swap can even pay a fair output so the leg succeeds and the victim's position remains healthy, hiding the theft inside a legitimate-looking transaction.

### Likelihood Explanation
Requires the victim to sign an authorization tree containing the extra child transfer — i.e., to submit a route built by an untrusted source (a compromised/malicious quote or route provider, exactly the MacPorts-mirror analog) and to approve the simulated auth without inspecting it. Unprivileged attacker: deploys `RogueHopPool`, embeds its address as a hop `pool` in the XDR, and supplies the route. Medium likelihood matching the source advisory's medium severity; the protocol itself does not bound or detect the extra child invocation.

### Recommendation
Enforce a venue allowlist in the router: resolve pool addresses from an owner/governance-managed registry (or a venue→pool mapping set) rather than trusting `assets` indices, so route bytes can only reach vetted pool contracts. Alternatively, restrict each hop to a fixed pool-per-pair registry and reject payload-supplied pool addresses entirely. Client-side mitigation (decoding the auth tree) should remain defense-in-depth, not the only control.

### Proof of Concept
1. Attacker deploys `RogueHopPool` storing `(victim, victim_wallet_token, attacker, amount)` and a `swap()` that calls `token::Client::transfer(victim, attacker, amount)` (see `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs:62-71`).
2. Attacker crafts `swap_xdr` with `hop.pool = RogueHopPool`, honest `token_in`/`token_out`, and a plausible `min_out` so the swap leg pays fair output.
3. Victim calls `controller.swap_collateral(account_id, token_in, amount_in, token_out, route)` (or `Router::execute_strategy` directly). Simulation records the rogue `transfer` as a child of the victim's auth entry; the victim signs the tree.
4. `RogueHopPool::swap` executes `transfer(victim → attacker)`; the venue call returns, `dispatch_hop` measures a positive output, the controller's risk gate passes, and the victim loses `amount` of an unrelated wallet token. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)
