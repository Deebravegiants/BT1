### Title
Webhook `shop-domain` header trusted by handler dispatch without HMAC coverage, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request body, then unconditionally trusts the `shop`, `topic`, `api_version`, and `webhook_id` values taken from HTTP headers and hands them to the host application's handler as authenticated `WebhookMetadata`. None of these header-derived fields are covered by the HMAC, breaking the intended binding `hmac_valid == shop_authenticated`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `api_version`, and `webhook_id` accessors read straight from HTTP headers, with no cryptographic binding to the signed body: [2](#0-1) 

`Registry.process` validates only the HMAC over the body, then immediately trusts `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` to construct the `WebhookMetadata` passed to the app's registered handler: [3](#0-2) 

`WebhookMetadata` is a typed struct whose `shop` field is exactly what handlers rely on to know which tenant the event belongs to: [4](#0-3) 

Because `HmacValidator.validate` (used here) computes the signature only from `Context.api_secret_key` and the `to_signable_string` value (the raw body), and `Context.api_secret_key` is the same app-level secret shared across *every* shop that installs the app — not a per-shop secret — a valid HMAC merely proves "this body was signed with this app's client secret." It proves nothing about which shop the body actually originated from: [5](#0-4) 

Equality that should hold: `hmac_valid(body) == authenticated(shop_header)`. In reality: `hmac_valid(body)` only proves the app-secret was known to whoever produced the body+signature pair; `shop_header` is read unauthenticated from headers that ride alongside the body but are excluded from the signable string. Any party who can install the app on their own shop (an unprivileged internet user, from the perspective of any other tenant) can trigger a real webhook delivery for their own shop, capture the `(raw_body, hmac)` pair — which is valid because it was legitimately computed by Shopify with the shared app secret — and replay that exact body+HMAC pair to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header. `Registry.process` will pass HMAC validation (the body/signature pair is untouched) and dispatch to the handler with attacker-chosen `shop`, causing the host application to act on another tenant's data using attacker-supplied `WebhookMetadata#shop`.

### Impact Explanation
This breaks the tenant boundary the webhook subsystem is supposed to enforce: an attacker with only unprivileged access (their own shop's app installation, no access token or leaked credentials required) can make the library report that a webhook event belongs to a shop domain of their choosing. Any host application logic keyed off `WebhookMetadata#shop` (e.g., looking up per-shop session/access-token to react to the event, updating per-shop state, or triggering privileged per-shop actions) is exposed to cross-tenant confusion/spoofing purely through this gem's own dispatch code, which is what the analog explicitly calls out (a "shop authenticated versus shop stored" binding break through header trust). This maps to the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is reasonably high: the only prerequisite is that the attacker can install the target app on a shop they control (a normal, unprivileged capability for public apps) and can send an arbitrary HTTP POST to the app's public webhook endpoint with attacker-controlled headers. No leaked secrets, TLS interception, or privileged access is required — the entire attack surface is the header/body split baked into `Webhooks::Request` and `Webhooks::Registry.process`.

### Recommendation
Do not treat `Registry.process`'s HMAC check as proof of shop identity. Either:
- Include the `shop-domain` (and ideally `topic`/`webhook-id`) header values in the signable string used for HMAC verification so header tampering invalidates the signature, or
- Require callers to independently verify `request.shop` against a known/installed shop record before trusting `WebhookMetadata#shop`, and document clearly that the HMAC only authenticates the app, not the originating shop.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`, which is legitimate and unprivileged.
2. Attacker triggers any subscribed webhook topic (e.g., `orders/create`) on their own shop, capturing the raw POST body and the `X-Shopify-Hmac-Sha256` header Shopify computed with the app's shared `api_secret_key`.
3. Attacker replays this exact `(raw_body, hmac)` pair to the app's webhook endpoint but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks the body against the shared secret: [6](#0-5) 
5. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` and the host application acts on the victim shop's identity based on attacker-controlled data.
