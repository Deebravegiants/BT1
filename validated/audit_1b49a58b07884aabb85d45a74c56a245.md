### Title
Webhook shop-domain identity is not bound by HMAC, enabling cross-tenant shop spoofing on replay - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then hands the caller-supplied `shop-domain` header straight through to the app's handler as the trusted tenant identity, without that header ever being covered by the signature.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
`HmacValidator.validate` computes/validates the signature purely against that signable string: [2](#0-1) 
`Registry.process` treats this body-only check as full authentication of the request, then reads `request.shop` (the raw `shop-domain`/`x-shopify-shop-domain` header, entirely attacker-supplied and never part of the signed bytes) and forwards it as the authoritative tenant identifier to the handler: [3](#0-2) [4](#0-3) 

The identity binding broken here is: `bytes_verified (raw_body signed by HMAC) != bytes_the_gem_attributes_to_a_tenant (shop header, unsigned)`. Since a single `client_secret` (`Context.api_secret_key`) is shared across *all* shops/tenants of the app, any merchant who has installed the app can capture a genuine webhook delivery to their own store (valid `body` + valid HMAC, because the secret is app-wide, not per-shop) and replay that exact `raw_body`/HMAC pair to the app's webhook endpoint while substituting an arbitrary `shop-domain` header (e.g. a victim shop). `HmacValidator.validate` still returns `true` because it only checks `raw_body` against the secret; the header is untouched by verification. `Registry.process` then dispatches to the handler with `WebhookMetadata.shop` set to the attacker-chosen victim shop, per the gem's documented contract: [5](#0-4) 

The gem's documented processing flow explicitly tells integrators that `process` "will verify the request did indeed come from Shopify" and gives no indication that `shop` still needs independent verification: [6](#0-5) 

### Impact Explanation
This breaks the tenant/shop boundary at the gem level: `Registry.process` supplies a shop identity to the app that is not cryptographically bound to the authenticated payload. Any app that keys downstream logic (data storage, redaction jobs, GDPR compliance tasks, order/product processing) off `data.shop` as returned by this library — exactly as the gem's own example handler does (`shop_domain: data.shop`) — can be made to attribute attacker-controlled webhook content to a different, victim shop. This is a cross-tenant identity-binding failure consistent with the "Critical – cross-tenant access" impact category, since the gem itself performs the HMAC check and hands back an un-bound shop value as if it were verified.

### Likelihood Explanation
Exploitation requires only that the attacker be an installed, unprivileged merchant of the target app (a normal "unprivileged internet user" relative to other tenants) capable of triggering any webhook to their own shop and replaying the captured HTTP request with a modified `shop-domain` header to the app's public webhook endpoint. No access token, `client_secret`, or privileged account is required — only observation of one's own webhook traffic, which every installed merchant can generate legitimately (e.g. via `orders/create`).

### Recommendation
`Registry.process` (or `HmacValidator`) should not treat HMAC-of-body-only as authentication of the `shop`, `topic`, or `webhook-id` headers. At minimum, the gem should document/enforce that `shop` returned from `WebhookMetadata` must be cross-checked by the app against a known/installed shop list before being trusted, or better, the library should require callers to supply the expected shop (from their own session store) to `process` and reject mismatches, rather than exposing an unauthenticated header as if it were part of the verified payload.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and receives a real webhook, e.g. `orders/create`, with headers including a valid `x-shopify-hmac-sha256` computed by Shopify over the JSON body using the app's shared `client_secret`.
2. Attacker replays the identical `raw_body` and `x-shopify-hmac-sha256` value to the same endpoint but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers (only presence, not authenticity, of headers is checked): [7](#0-6) 
4. `Utils::HmacValidator.validate(request)` succeeds because it only recomputes HMAC over `raw_body`.
5. `Registry.process` finds the handler and calls it with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com", body: <attacker's own order payload> ...)`, causing the app to process attacker-controlled data under the victim tenant's identity.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
