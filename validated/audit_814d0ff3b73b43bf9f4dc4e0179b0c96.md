No validation prevents batch withdrawals from including multiple entries with the same `assetId` but different `destinationAddress`/`amount` values, and the PoA bridge's status-matching logic keys only on `assetId`.

### Title
Batch withdrawal status/hash misreport when multiple same-asset withdrawals share an intent (PoA Bridge) - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal` resolves the on-chain completion status/txHash for a specific withdrawal entry in a batch solely by matching `assetId` against the POA API's returned withdrawal list, via `findMatchingWithdrawal`. When a batch (`WithdrawalParams[]`) contains two or more entries with the same `assetId` (e.g., same token withdrawn to two different destination addresses/amounts in one intent), every entry with that `assetId` resolves to the *same* API record — including the same `transfer_tx_hash`/status — regardless of which destination address or amount it actually corresponds to.

### Finding Description
The SDK supports batch withdrawals: [1](#0-0) . Each batch entry becomes an independent `WithdrawalIdentifier` tracked by index via `createWithdrawalCompletionPromises`/`watchWithdrawal`, which calls `bridge.describeWithdrawal` per index: [2](#0-1) [3](#0-2) .

For the PoA bridge, `describeWithdrawal` fetches the withdrawal status list once per NEAR tx hash and picks a match using `findMatchingWithdrawal`, which is explicitly documented to match by `assetId` only, not by index/destination/amount: [4](#0-3) [5](#0-4) .

The equality this breaks: the destination tx hash/status returned for withdrawal index *i* is supposed to equal the on-chain outcome of the withdrawal that was actually created for `withdrawalParams[i]` (its specific destination address/amount). Because matching keys only on `assetId`, if `withdrawalParams[0]` and `withdrawalParams[1]` share the same `assetId` but different `destinationAddress`, both indices resolve to whichever single record in the API response happens to have that `assetId` — an integrator polling per-index (as the batch API is designed to support, see `createWithdrawalCompletionPromises`/`waitForWithdrawalCompletion`) receives a `txHash` that may belong to the *other* destination's withdrawal, not its own. The identical issue exists in the internal-utils single-hash version of this matcher, which additionally lacks even a `destinationAddress` field in `WithdrawalCriteria`: [6](#0-5) .

Nothing in `estimateWithdrawalFee`, `signAndSendWithdrawalIntent`, or `processWithdrawal` rejects batches with duplicate `assetId` entries; the type only requires an array of `WithdrawalParams`: [7](#0-6) , and batch usage with distinct destinations for potentially overlapping assets is a documented, expected pattern (README batch examples show different assets, but nothing structurally prevents same-asset batches): [8](#0-7) .

### Impact Explanation
An integrator relying on per-index completion status (`createWithdrawalCompletionPromises`) for a batch withdrawal with duplicate-asset entries can be told that withdrawal B (to address Y) is "completed" with a tx hash that actually corresponds to withdrawal A (to address X) — or vice versa. This is a status/hash misreport that can cause an integrator to prematurely credit/mark-complete a withdrawal that has not actually completed on-chain for that specific destination, or to associate a real completion hash with the wrong recipient's record, matching the "status or hash misreport making an integrator credit or refund twice" High-impact category.

### Likelihood Explanation
Requires the SDK caller to construct a batch withdrawal containing two-or-more entries with the same `assetId`. This is not blocked by any validation, and the batch API is explicitly designed for exactly this multi-entry-per-intent scenario. The bridge's own code comment acknowledges the limitation exists today ("multiple withdrawals of the same token in a single transaction are not supported"), confirming the maintainers are aware this case is unhandled but have not gated it off — callers are not warned/blocked at runtime.

### Recommendation
Disambiguate `findMatchingWithdrawal` (in both `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts` and `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts`) using additional fields available in the POA API response (e.g., `data.address`/destination and `data.amount`) in addition to `assetId`, or reject/throw when a batch contains multiple withdrawals with the same `assetId` until the API/matcher can disambiguate reliably, rather than silently returning a possibly-mismatched record.

### Proof of Concept
1. Build a batch `withdrawalParams` with two entries, both `assetId: "nep141:usdt.tether-token.near"`, but `destinationAddress` A for index 0 and `destinationAddress` B for index 1.
2. Call `sdk.processWithdrawal({ withdrawalParams })` or the granular `createWithdrawalCompletionPromises`.
3. The POA bridge indexer returns a withdrawals list with one entry per token per intent tx; `findMatchingWithdrawal` matches on `nep141:${near_token_id} === assetId` only [9](#0-8) .
4. Both index 0 and index 1's `describeWithdrawal` calls resolve to the same matched record/`transfer_tx_hash`, so the promise for index 1 (destination B) can resolve with the tx hash that actually paid out to destination A (or the reverse), depending on API ordering — an unverified, incorrect status report for at least one of the two batch entries.

	public createWithdrawalCompletionPromises(
		params: CreateWithdrawalCompletionPromisesParams,
	): Array<Promise<TxInfo | TxNoInfo>> {
		const { withdrawalParams, intentTx, signal, logger } = params;

		const widsPromise = createWithdrawalIdentifiers({
			bridges: this.bridges,
			withdrawalParams,
			intentTx,
		});

		// Track the last promise per HOT bridge landing chain for sequential waiting.
		// HOT bridge processes withdrawals sequentially per chain with ~30s gaps,
		// so polling in parallel would cause later withdrawals to timeout.
		const hotChainLastPromise = new Map<Chain, Promise<TxInfo | TxNoInfo>>();

		return withdrawalParams.map(async (_, index) => {
			const wids = await widsPromise;
			const entry = wids[index];
			assert(entry != null, `Missing wid for index ${index}`);

			// Only apply sequential waiting for HOT bridge
			if (entry.bridge.route === RouteEnum.HotBridge) {
				const landingChain = entry.wid.landingChain;
				const previousPromise = hotChainLastPromise.get(landingChain);

				const sequentialPromise = (async () => {
					if (previousPromise) {
						// Wait for previous withdrawal to same chain to complete.
						// Use allSettled to continue even if previous fails.
						await Promise.allSettled([previousPromise]);
					}
					return watchWithdrawal({
						bridge: entry.bridge,
						wid: entry.wid,
						signal,
						logger,
					});
				})();

				hotChainLastPromise.set(landingChain, sequentialPromise);
				return sequentialPromise;
			}

			// Non-HOT bridges: parallel polling (existing behavior)
			return watchWithdrawal({
				bridge: entry.bridge,
				wid: entry.wid,
				signal,
				logger,
			});
		});

		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index

			response.withdrawals,
			args.withdrawalParams.assetId,

			return { status: "pending" };
		}

			return { status: "pending" };

				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};

type WithdrawalStatusResponse = Awaited<
	ReturnType<typeof poaBridge.httpClient.getWithdrawalStatus>
>;

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
