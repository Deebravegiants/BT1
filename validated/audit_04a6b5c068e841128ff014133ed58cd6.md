### Title
Silent decimal-scaling corruption in `pallet-hyper-fungible-token` due to unchecked assumption that ERC20 decimals are always ≥ local asset decimals - (File: `modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
`pallet-hyper-fungible-token`'s cross-chain amount conversion helpers assume that the registered EVM-side (`erc_decimals`) precision is always greater than or equal to the local substrate asset's (`local_decimals`) precision, mirroring the flawed assumption in the reported `ERC4626Price.sol` bug where a fixed relationship between two decimal values is assumed rather than verified at the point of use.

### Finding Description
`convert_to_balance` and `convert_to_erc20` compute the scaling exponent with `erc_decimals.saturating_sub(local_decimals)`: [1](#0-0) 

`saturating_sub` silently clamps to `0` whenever `local_decimals > erc_decimals`, instead of erroring. That `0` is then used as the power-of-ten exponent, so the conversion functions silently apply **no scaling at all** in that case rather than failing.

The pallet does define an `Error::ErcDecimalsBelowLocal` variant, documented as "Configured ERC decimals are less than the local asset's decimals; precision conversion requires erc_decimals >= local_decimals": [2](#0-1) 

However, `local_decimals` is not a value fixed at registration time — it is read live on every `send`, `on_accept`, and `on_timeout` call via `fungibles::metadata::Inspect::decimals`: [3](#0-2) [4](#0-3) 

Because `local_decimals` is a live read from the underlying `pallet-assets`/`fungibles` implementation rather than a value pinned at `register_token` time, any dynamic change to that asset's metadata after registration (e.g. via `pallet-assets::force_set_metadata`, permitted for whichever origin the runtime authorizes for asset metadata) that raises the asset's decimals above the configured `erc_decimals` in `Precisions` silently breaks the invariant the `ErcDecimalsBelowLocal` error was meant to enforce — but that error is only checked (if at all) at registration, never again on the hot path. The conversion functions themselves have no runtime check and cannot detect the violated invariant; they degrade silently via `saturating_sub` instead of reverting.

### Impact Explanation
Once the invariant `erc_decimals >= local_decimals` is violated, every `send`, `on_accept` (mint/unlock), and `on_timeout` (refund) call for that asset silently applies a scale factor of `10^0 = 1` instead of the correct down-scaling factor. This corrupts amount conversion between the local substrate balance and the ERC20-denominated `Message.amount` sent over ISMP — e.g. an amount intended to be scaled down by `10^12` is instead sent unscaled, inflating or deflating the cross-chain transferred value by orders of magnitude. Depending on direction, this results in either the destination-chain mint delivering vastly more tokens than were escrowed/burned on the source chain (unbacked mint / theft), or vastly fewer, permanently mis-crediting or freezing value for users of that registered token — reachable by any signed account calling the pallet's `send` extrinsic.

### Likelihood Explanation
This requires the local asset's decimals to actually change after `register_token`, which depends on the pallet-assets configuration in a given runtime allowing metadata mutation on an already-registered asset. This is plausible in a Substrate parachain runtime where asset metadata is admin-mutable, and there is no runtime-level guard re-validating the `Precisions` invariant when the underlying asset's decimals are altered.

### Recommendation
Do not rely on `saturating_sub`; use checked subtraction and return `Error::ErcDecimalsBelowLocal` (or an equivalent runtime error) at the point of conversion in `send`, `on_accept`, and `on_timeout` whenever `local_decimals > erc_decimals`, rather than only (if at all) validating at `register_token` time. Alternatively, support bidirectional scaling (multiply or divide depending on which side has more precision) instead of assuming one direction always holds.

### Proof of Concept
1. `register_token` registers asset `X` as non-native with `Precisions::<T>::get(X, dest) = 6` (erc_decimals = 6), while at registration `X`'s local decimals are `6` too (`erc_decimals >= local_decimals` holds).
2. Later, the runtime's asset-metadata admin updates asset `X`'s metadata decimals to `18` via the underlying `pallet-assets` (outside this pallet's control).
3. A user calls `send` with `asset_id = X`. `decimals` is now read live as `18` [5](#0-4) 
 while `erc_decimals` is still `6`. `convert_to_erc20(amount, 6, 18)` computes `10u128.pow(6u8.saturating_sub(18) as u32) = 10^0 = 1` [6](#0-5) 
 instead of the correct division, so the dispatched `Message.amount` carries the raw 18-decimal local amount unscaled, mis-representing it as a 6-decimal ERC20 amount to the destination `HyperFungibleToken`/`WrappedHyperFungibleToken` contract — inflating the credited value by `10^12`.

/// Converts an ERC20 U256 amount to a local balance type
///
/// Divides by 10^(erc_decimals - local_decimals) to scale down from ERC20 precision.
/// The target type must implement `FromStr`.
pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}

/// Converts a local u128 balance to an ERC20 U256 amount
///
/// Multiplies by 10^(erc_decimals - local_decimals) to scale up to ERC20 precision
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
