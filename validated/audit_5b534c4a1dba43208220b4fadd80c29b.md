### Title
Webhook `shop-domain` and `topic` headers are trusted by handlers without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating an HMAC over the raw request body, then dispatches to the registered handler using a `shop` value read directly, and unauthenticated, from the `X-Shopify-Shop-Domain` HTTP header. The identity binding "bytes verified == bytes the handler acts on" is broken: the HMAC covers only `@raw_body`, while `shop`, `topic`, `api_version`, and `webhook_id` are taken from headers outside the signed payload.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

The `shop`, `topic`, `api_version`, and `webhook_id` accessors read directly from HTTP headers, with no cryptographic binding to the body or the HMAC: [2](#0-1) 

`Registry.process` validates the HMAC using `Utils::HmacValidator.validate(request)` — which, per `HmacValidator#validate_signature`, recomputes the signature over `verifiable_query.to_signable_string` (i.e. the body only) and compares it to the `hmac` header — and then immediately trusts `request.shop` and `request.topic` (both unauthenticated header values) to route and label the event to the handler: [3](#0-2) [4](#0-3) 

The binding that should hold is:
`bytes_verified_by_HMAC == bytes_the_handler_acts_on_for_tenant_identity`

Here, `bytes_verified_by_HMAC = raw_body` while `bytes_the_handler_acts_on_for_tenant_identity = shop-domain header`, which are disjoint. Any unprivileged internet user who is themselves a legitimate merchant with the app installed (or who can otherwise get one genuine webhook delivered to them, e.g. via a mandatory/customer-initiated topic) can capture one valid `(raw_body, hmac)` pair signed by the app's actual `client_secret`/`api_secret_key`, and then replay that exact body+HMAC to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header value naming a *different* shop/tenant. Because `to_signable_string` never includes `shop`, the HMAC check in `HmacValidator.validate` still succeeds, and `WebhookMetadata.shop` passed to the handler will be attacker-controlled and cross-tenant.

### Impact Explanation
This qualifies as cross-tenant access (Critical) per the rules: an attacker with no special privileges and no leaked credentials can cause the app's webhook-processing logic to attribute a webhook event (and any body content, e.g. `customers/data_request`, `shop/redact`, order/customer state-change payloads) to a shop they do not own or control, purely by manipulating an unauthenticated header while replaying an HMAC-valid body they legitimately obtained for their own tenant. Any application logic keyed on `WebhookMetadata#shop` (e.g., updating per-shop state, honoring redact/data requests, session lookups keyed by shop) is fed a value with no cryptographic tie to the signed payload, enabling tenant-identity confusion.

### Likelihood Explanation
Likelihood is high: the only prerequisite is the ability to receive one genuine webhook for any shop (trivial for a developer/merchant with a free/dev store and the app installed, or for mandatory customer-privacy topics that can be self-triggered), plus the ability to send an arbitrary HTTP POST with custom headers to the app's public webhook endpoint. No knowledge of `api_secret_key` is required — the attacker reuses a signature Shopify already computed for them.

### Recommendation
Bind the `shop` (and ideally `topic`) values into the signed payload verification, e.g., include the `X-Shopify-Shop-Domain` and `X-Shopify-Topic` header values (or verify them against out-of-band expected values, such as the shop obtained from a previously stored session/HMAC-verified registration) as part of `to_signable_string`, or otherwise cryptographically bind them so that the HMAC cannot validate if these headers are altered. At minimum, document/require that consumers of `WebhookMetadata#shop` not treat it as authenticated for tenant-isolation decisions unless additionally cross-checked against a known/stored shop for that webhook subscription.

### Proof of Concept
1. As merchant on `attacker-shop.myshopify.com` with the app installed, trigger a webhook whose payload is generic/attacker-known content (e.g., `shop/redact`, `{}` body, or a body the attacker fully controls/can predict) and capture the resulting POST: raw body `B` and header `X-Shopify-Hmac-Sha256: H` (valid signature over `B` using the app's real secret).
2. Replay a new HTTP POST to the same webhook endpoint with the identical raw body `B` and identical `X-Shopify-Hmac-Sha256: H`, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and, if desired, a different `X-Shopify-Topic`/`X-Shopify-Webhook-Id`).
3. `Utils::HmacValidator.validate(request)` in `Registry.process` succeeds because it only checks `H` against `B` (`to_signable_string` returns `@raw_body` only) — the altered `shop-domain`/`topic` headers are never part of what's verified.
4. `Registry.process` invokes the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, causing the host application to act on behalf of `victim-shop` using data that was never actually authorized/signed for that shop. [3](#0-2)

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
