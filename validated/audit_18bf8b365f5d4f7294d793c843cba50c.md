### Title
BEEFY consensus supermajority threshold can be satisfied with duplicate signatures instead of unique authorities - ([File: evm/src/consensus/EcdsaBeefy.sol])

### Summary
Both the Solidity (`EcdsaBeefy.sol`) and Rust (`modules/consensus/beefy/verifier/src/lib.rs`) BEEFY verifiers compute the supermajority participation count directly from the raw length of the submitted votes/signatures array, without first deduplicating by `authorityIndex`. This mirrors the `PoolGovernance::proposeEpoch` bug class: a tally is incremented/measured without checking whether the same voter (here, the same authority index) has already been counted, letting a minority of real signers inflate the apparent participation count past the 2/3+1 threshold by repeating already-collected signatures at additional array slots.

### Finding Description
`EcdsaBeefy.verifyMmrUpdateProof` takes `sigLen = relayProof.signedCommitment.votes.length` and checks `checkParticipationThreshold(sigLen, authoritySet.len)` — i.e. `sigLen >= (2*total)/3 + 1` — before doing any per-signature uniqueness check: [1](#0-0) 

It then builds a `MerkleMultiProof.Leaf[]` array of length `sigLen`, one leaf per vote, keyed by `vote.authorityIndex`, and hands the whole (potentially duplicated) index/leaf array to `MerkleMultiProof.VerifyProof`: [2](#0-1) 

Nowhere in this function — nor in `checkParticipationThreshold` itself — is `vote.authorityIndex` checked for uniqueness across the `votes` array: [3](#0-2) 

The exact same pattern exists in the Rust verifier used by the substrate-side BEEFY light client (`ismp-beefy`): `signatures_length` is taken as the raw `.len()` of the signatures vector and fed straight into `check_participation_threshold`, with `authority_indices`/`authority_leaves` built by iterating the (unde-duplicated) signature list: [4](#0-3) [5](#0-4) [6](#0-5) 

Contrast this with the sibling consensus verifiers in the same codebase — BSC (Parlia), the sync-committee client, and the Pharos client — which all explicitly guard against this exact class of inflation. BSC and sync-committee reject any bit set beyond the real validator/committee size (to stop `count_ones()` padding), and Pharos explicitly rejects duplicate participant keys before computing stake-weighted participation: [7](#0-6) [8](#0-7) [9](#0-8) 

BEEFY's `EcdsaBeefy.sol`/`modules/consensus/beefy/verifier/src/lib.rs` is the one BEEFY-family verifier missing an equivalent uniqueness guard on the vote/signature list before it is used to satisfy the supermajority threshold.

### Impact Explanation
If a submitted `RelayChainProof`/`MmrProof` can contain the same `(signature, authorityIndex)` pair (or the same `authorityIndex` with a re-derived identical signature) more than once, `sigLen`/`signatures_length` is inflated relative to the number of *distinct* authorities that actually signed. A minority of colluding (or even a single compromised) BEEFY validator whose signatures happen to already be public (BEEFY signatures are gossiped/justification data, not secret) could construct a proof that satisfies `checkParticipationThreshold`/`check_participation_threshold` without a genuine 2/3+1 quorum. Because this threshold gate protects the entire consensus-state advance (`trustedState.currentAuthoritySet`/`nextAuthoritySet` rotation and `latestHeight` update) and the subsequent MMR/parachain-header verification that yields `IntermediateState`s consumed by ISMP state-machine updates, breaking it means a forged/under-quorum consensus update can be accepted as canonical. This directly maps to "unsound state commitment" / "forged message delivery" — any parachain header committed via this path is then trusted for state and non-membership proofs used to mint tokens, settle intents, and deliver ISMP messages across Hyperbridge.

### Likelihood Explanation
BEEFY commitments and their signatures are public relay-chain data (gossiped justifications), so an attacker does not need validator collusion to obtain valid signature bytes for a given commitment/authorityIndex — they only need to know whether the multi-proof/merkle-verification step tolerates a duplicated `(index, leaf)` pair in its input arrays. Given the absence of any explicit "unique authorityIndex" check in either implementation (unlike the other consensus modules in this same codebase), exploitability hinges only on whether the underlying merkle multi-proof verification algorithm (`MerkleMultiProof.VerifyProof` / `rs_merkle`'s multi-proof verify) rejects repeated indices — a property this on-chain code never enforces itself and should not rely on implicitly.

### Recommendation
Before computing `sigLen`/`signatures_length` for the participation-threshold check, deduplicate votes by `authorityIndex` (e.g., collect into a set/BTreeSet keyed by index, or explicitly reject the proof if any `authorityIndex` repeats), analogous to the fixes already applied in the BSC, sync-committee, and Pharos verifiers in this codebase. The count used against `checkParticipationThreshold`/`check_participation_threshold` must reflect distinct authority indices only, not the raw length of the submitted votes/signatures array.

### Proof of Concept
1. Take a real, previously-observed BEEFY `SignedCommitment` for a given block with `N` authorities and only `M < 2/3*N+1` real distinct signers (e.g., a minority partition, or simply fewer validators willing to sign at that instant).
2. Construct `relayProof.signedCommitment.votes` (Solidity) / `mmr.signed_commitment.signatures` (Rust) by repeating some of the `M` genuine `(authorityIndex, signature)` pairs additional times until `votes.length`/`signatures.len() >= (2*N)/3 + 1`.
3. Submit this padded proof to `EcdsaBeefy.verify` (or the Rust `verify_consensus`/`verify_mmr_update_proof`). `checkParticipationThreshold`/`check_participation_threshold` passes on the padded count.
4. If the merkle multi-proof verification step does not itself reject the duplicate `(authorityIndex, leaf)` entries, the call succeeds and updates `trustedState`/`ConsensusState`, advancing the BEEFY light client height and authority-set rotation, and returns `IntermediateState`s for parachain headers that were finalized under this under-quorum "consensus" — with only `M` real signers instead of the required supermajority.

pub fn verify_mmr_update_proof<H: Keccak256 + EcdsaRecover + Send + Sync>(
	mut trusted_state: ConsensusState,
	mmr: MmrProof,
) -> Result<(ConsensusState, H256), Error> {
	let signatures_length = mmr.signed_commitment.signatures.len();
	let latest_height = mmr.signed_commitment.commitment.block_number;

	if trusted_state.latest_beefy_height >= latest_height {
		return Err(Error::StaleHeight {
			trusted_height: trusted_state.latest_beefy_height,
			current_height: latest_height,
		});
	}

	let commitment = mmr.signed_commitment.commitment.clone();

	// Pick the authority set the commitment claims to be signed under, then judge
	// participation against that set alone.
	let authority_set = if commitment.validator_set_id == trusted_state.current_authorities.id {
		&trusted_state.current_authorities
	} else if commitment.validator_set_id == trusted_state.next_authorities.id {
		&trusted_state.next_authorities
	} else {
		return Err(Error::UnknownAuthoritySet { id: commitment.validator_set_id });
	};

	if !check_participation_threshold(signatures_length as u32, authority_set.len) {
		return Err(Error::SuperMajorityRequired);
	}

fn verify_validator_membership(
	validator_set: &ValidatorSet,
	participants: &[BlsPublicKey],
) -> Result<(), Error> {
	let deduped: alloc::collections::BTreeSet<&[u8]> =
		participants.iter().map(|k| k.as_ref()).collect();
	if deduped.len() != participants.len() {
		return Err(Error::DuplicateParticipant);
	}
	if let Some(key) = participants.iter().find(|key| !validator_set.contains(key)) {
		return Err(Error::UnknownValidator { key: key.clone() });
	}
	Ok(())
}
