### Title
`withdraw`/`borrow` recipient guard only blocks the pool and controller — tokens sent to any other protocol contract (e.g. the position-NFT contract) are debited and permanently stranded - (File: contracts/controller/src/positions/mod.rs)

### Summary
The bridge bug class — *recipient passes validation but can never be honored downstream, so funds are debited and silently lost* — maps onto XOXNO's `to: Option<Address>` parameter on `Controller::withdraw` and `Controller::borrow`. The protocol already recognized this class and fixed the two worst recipients under GH-17 via `require_external_recipient`, which rejects only the pool and the controller itself. Every other contract address — notably the deployed **position-NFT contract**, the token SAC itself, or any other contract with no token-release function — still passes the guard, so the position is burned/created and the SAC transfer lands on an address that can never move the tokens. The loss is permanent and triggered by a simple user mistake, exactly as in H-01.

### Finding Description
`process_withdraw` resolves `to` to a `recipient` and calls `require_external_recipient` before settling:

```rust
// contracts/controller/src/positions/supply.rs
let recipient = to.unwrap_or_else(|| caller.clone());
let mut cache = Context::new(env);
require_external_recipient(env, &mut cache, &recipient);
```

`require_external_recipient` only rejects the controller and the pool:

```rust
// contracts/controller/src/positions/mod.rs
assert_with_error!(
    env,
    *recipient != env.current_contract_address() && *recipient != pool,
    FlashLoanError::InvalidFlashloanReceiver
);
```

The GH-17 rationale in that same file documents why the check exists: "Pool self-transfers debit cash without moving tokens; controller receipts would remain unclaimed by balance-delta accounting." The identical reasoning applies to any other protocol contract: after the guard passes, `apply_withdraw_batch` burns the user's supply shares and the pool executes an unconditional SAC transfer via `Cache::transfer_out` (`contracts/pool/src/cache/cash.rs`), which moves real tokens to `recipient` with no decode or capability check. `process_borrow` (`contracts/controller/src/positions/debt.rs`) uses the same `to → require_external_recipient → pool_borrow_call` flow and is affected identically.

The position-NFT contract (deployed by `deploy_position_nft`, `contracts/controller/src/lib.rs`) exposes NFT mint/transfer/approve functions only — it has no token-transfer or sweep entrypoint — so a `withdraw(..., to = position_nft_address)` transfers underlying tokens to an address that can never release them. The same holds for withdrawing to the asset SAC contract's own address or to any other in-scope contract lacking a token-release path.

### Impact Explanation
Permanent freezing of funds. The user's supply position (or newly minted debt obligation for `borrow`) is settled on-chain, the pool's cash accounting and token balance decrease, and the tokens land on a contract address with no mechanism to send them out. There is no retry or recovery path — matching the accepted impact of the reference report (burned source-side position, unreachable destination funds).

### Likelihood Explanation
Requires a user (or integrating contract) to pass a wrong but well-formed `Address` in `to`. This is the same user-mistake profile as H-01: on Stellar, addresses are typed `Address` values, so malformed bytes cannot slip through — but an address that is *valid yet unable to custody the funds* is the direct analog, and the protocol's own GH-17 fix proves this is a recognized, in-scope failure mode. The fix was simply incomplete: it enumerated two contract addresses instead of enforcing that the recipient is an externally-owned-style address or a known-safe destination.

### Recommendation
Extend `require_external_recipient` to reject all deployed protocol contract addresses (position NFT, price aggregator, swap aggregator, governance, and each market's `asset_id` token contract), or invert the check: require the recipient to differ from every contract the deployment registers in storage. Alternatively, document that `to` must be an account address and validate accordingly where feasible.

### Proof of Concept
1. Deploy controller, pool, and position NFT; list a USDC market. Alice calls `supply` to open an account with 10,000 USDC collateral.
2. Alice calls `Controller::withdraw(caller = alice, account_id, withdrawals = [(usdc_hub_asset, 10_000e7)], to = Some(position_nft_contract_address))`.
3. `process_withdraw` authorizes Alice, resolves `recipient` to the NFT contract, and `require_external_recipient` passes because the NFT contract is neither the pool nor the controller (`positions/mod.rs:36-43`).
4. `apply_withdraw_batch` → `pool_withdraw_call` burns Alice's supply shares, debits pool cash, and `Cache::transfer_out` executes `token.transfer(pool, position_nft_contract, amount)` (`cache/cash.rs:46-53`). The transfer succeeds — the NFT contract is a valid recipient address.
5. Alice's position is zeroed and the USDC sits on the position-NFT contract, which has no entrypoint capable of moving tokens. The funds are permanently frozen; the identical sequence works through `borrow(..., to = Some(position_nft_contract))` (debt.rs:45-47), leaving Alice with debt and unrecoverable proceeds.

Uncertainty note: whether the position-NFT (or governance) contract carries an admin sweep/recovery function could not be fully verified within available iterations; if a privileged sweep exists, the impact downgrades to "user funds recoverable only by admin action" — still a valid analog, but lower severity.
