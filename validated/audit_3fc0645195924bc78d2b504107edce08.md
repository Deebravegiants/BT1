### Title
Webhook `shop-domain` header is trusted but not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then forwards the unauthenticated `x-shopify-shop-domain` header value to the app's handler as the trusted tenant identifier. Because the HMAC signature never covers the `shop` field, any request with a body/HMAC pair that is valid for shop A can be replayed with the `shop-domain` header changed to shop B, and the gem will report it to the handler as an authenticated webhook "from" shop B.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and compares it with the `hmac` field [1](#0-0) . For webhooks, `Request#to_signable_string` returns only `@raw_body` [2](#0-1) , while `Request#shop` is read directly and unauthenticated from the `x-shopify-shop-domain`/`shopify-shop-domain` header [3](#0-2) .

`Registry.process` validates only the HMAC of the request and then passes `request.shop` straight into the `WebhookMetadata` object delivered to the app's handler, without any check that the `shop` header matches an install this webhook subscription belongs to: [4](#0-3) 

The identity binding that should hold is: `hmac == HMAC(secret, raw_body ++ shop)`, i.e., the tenant identifier acted upon (`shop`, used by the app to select per-merchant state/session) should be covered by the same signature that authenticates the payload. Instead the binding actually enforced is `hmac == HMAC(secret, raw_body)` only, with `shop` supplied out-of-band and trusted implicitly. This is exactly the "field acted on but not covered by the HMAC" class of bug: the `shop` field is used by `WebhookMetadata`/handler logic to decide which merchant's data to update, yet it is not part of the signed material.

### Impact Explanation
A merchant that has installed the app (and is therefore able to trigger genuinely-signed webhooks for their own shop, e.g. by creating an order) can capture a legitimate `(raw_body, hmac)` pair signed with the app's `api_secret_key` for their own store, then resend that exact payload to the app's webhook endpoint while altering only the `x-shopify-shop-domain` header to name a victim shop. `HmacValidator.validate` will still succeed because the signature never covered `shop`, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload came from the victim shop [5](#0-4) . Any handler that uses `data.shop` to select which merchant's session/records to update (the documented usage pattern shown in `docs/usage/webhooks.md`, e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) will act on the victim tenant's behalf with attacker-supplied body content — a cross-tenant confusion/write primitive achieved purely by an unprivileged installed merchant, without ever needing the app's `api_secret_key`, an access token, or any credential belonging to the victim.

### Likelihood Explanation
Likelihood is moderate-to-high in any app that follows the gem's documented handler pattern and trusts `data.shop`: the only capability required from the attacker is being a normal (even trial) merchant able to install the app and trigger one webhook event, which is an ordinary unprivileged action. No secret material, token theft, or victim interaction is required — only capturing one's own legitimate webhook body+signature and replaying it with a modified header.

### Recommendation
Include the authenticated `shop` (and ideally `topic`/`webhook_id`) in the signed material checked against the HMAC, or otherwise cryptographically bind the `shop-domain` header to the payload before trusting it (e.g., cross-check `request.shop` against records for the specific `webhook_id`/subscription that only Shopify would know, or validate that the shop is one the app has an active session/install for and require handlers to reject unexpected shops). At minimum, document prominently that `data.shop` from `WebhookMetadata` is unauthenticated header data and must not be used as a sole tenant-selection key without additional server-side verification.

### Proof of Concept
1. App merchant "attacker-shop" installs the app and legitimately owns webhook subscriptions; they trigger an event (e.g. `orders/create`) and capture the raw POST body `B` and the `X-Shopify-Hmac-Sha256` header `H` that Shopify sent for that webhook (this is a valid `(B, H)` pair under the app's real `api_secret_key`).
2. Attacker sends a new HTTP request to the app's webhook endpoint with:
   - Body: `B` (unchanged)
   - Header `x-shopify-hmac-sha256`: `H` (unchanged)
   - Header `x-shopify-shop-domain`: `victim-shop.myshopify.com` (changed)
   - Header `x-shopify-topic`: unchanged
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (`== B`) only, matching `H` — validation passes [6](#0-5) .
4. The handler is invoked with `WebhookMetadata.new(... shop: request.shop ...)`, where `request.shop == "victim-shop.myshopify.com"` [7](#0-6) .
5. Any app logic keyed off `data.shop` (per the documented handler example in `docs/usage/webhooks.md`) now processes attacker-controlled body content as if it originated from `victim-shop`, achieving cross-tenant impact without possessing any victim credential.
