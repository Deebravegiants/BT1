This confirms the key asymmetry: for `Auth::Oauth::AuthQuery`, `shop` is included in `to_signable_string` [1](#0-0)  and is therefore bound by the HMAC. But for `Webhooks::Request`, `to_signable_string` returns only `@raw_body`, while `shop` is read from the unauthenticated `shop-domain` HTTP header [2](#0-1)  and is never part of the signed material [3](#0-2) . `Registry.process` validates only the HMAC over the body and then passes `request.shop` straight into `WebhookMetadata` given to the app's handler [4](#0-3) .

### Title
Webhook shop-domain header not covered by HMAC, allowing cross-tenant shop spoofing via webhook replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC signature over the raw request body only, while the `shop` value that is handed to the app's webhook handler is read from an unauthenticated header (`shopify-shop-domain` / `x-shopify-shop-domain`) that is not part of the signed payload. `Registry.process` validates the HMAC and then trusts `request.shop` unconditionally when constructing `WebhookMetadata` for the handler, breaking the identity binding `shop-header == shop-covered-by-HMAC`.

### Finding Description
`Utils::HmacValidator.validate` calls `verifiable_query.to_signable_string` to compute the expected signature [5](#0-4) . For webhooks, `to_signable_string` returns only `@raw_body` [3](#0-2) , so the HMAC in `shopify-hmac-sha256` only authenticates the JSON body — it says nothing about which shop the request claims to originate from. The `shop` attribute is derived purely from the `shopify-shop-domain` header, an ordinary HTTP header fully controlled by whoever sends the HTTP request to the app's webhook endpoint [2](#0-1) .

`Registry.process` only checks `Utils::HmacValidator.validate(request)` (body HMAC) before dispatching to the registered handler with `request.shop` passed through as the tenant identifier in `WebhookMetadata` [4](#0-3) . Contrast this with `Auth::Oauth::AuthQuery`, where `shop` is explicitly included inside `to_signable_string` and therefore is cryptographically bound to the HMAC [1](#0-0) . The webhook path lacks this same binding for the identically-purposed `shop` field.

The equality that should hold but does not: `shop-header-value == shop-value-covered-by-HMAC`. Before the request: the legitimate webhook has `(raw_body_A, hmac_A, shop_A)` where `hmac_A` is valid for `raw_body_A` under `client_secret`. An attacker who has observed or received one legitimate webhook delivery (e.g., to their own store, or any webhook whose body they can predict/observe) can resend `(raw_body_A, hmac_A)` unchanged but substitute `shop-domain: shop_B` (a victim tenant). `HmacValidator.validate` still passes because it only checks `raw_body_A`/`hmac_A`, and the handler receives `WebhookMetadata` with `shop: shop_B`, attributing attacker-supplied/replayed data to the victim tenant.

### Impact Explanation
This crosses a tenant boundary: the gem hands the app a `shop` value that the app is expected to trust as the authenticated tenant for this webhook event, but that value was never covered by the cryptographic proof. Apps built on this gem's documented `WebhookMetadata#shop` contract (as shown in the library's own webhook handling flow) can be made to process/store data under, or take actions against, a `shop` chosen entirely by the request sender, not the one that actually produced the signed body. This is a cross-tenant identity binding failure consistent with the High severity class in scope (scope/identity check bypass via an unbound field).

### Likelihood Explanation
No `api_secret_key`, access token, or privileged credential is required. The attacker only needs one previously-observed valid `(raw_body, hmac)` pair for any topic — e.g. delivered to a store they control, or a predictable/empty body such as the `"{}"` bodies shown in the library's own tests — then resend it to the app's public webhook endpoint with an arbitrary `shop-domain` header. This is trivially reachable by any unprivileged internet user who can reach the app's webhook URL.

### Proof of Concept
1. Attacker registers a webhook on their own shop (`attacker.myshopify.com`) or observes a webhook delivery with body `raw_body_A` and valid header `shopify-hmac-sha256: hmac_A` (valid under the app's `client_secret` for `raw_body_A`, learned via legitimate delivery to attacker's own store).
2. Attacker POSTs to the app's webhook endpoint with headers:
   - `shopify-topic: <same topic>`
   - `shopify-hmac-sha256: hmac_A` (unchanged)
   - `shopify-shop-domain: victim-shop.myshopify.com` (changed to target tenant)
   - body: `raw_body_A` (unchanged)
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because `to_signable_string` only covers `raw_body_A`, matching `hmac_A` [3](#0-2) .
4. The handler is invoked with `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body: ..., ...)` [6](#0-5) , causing the app to process attacker-controlled data attributed to the victim tenant.

### Recommendation
Include `shop` (and ideally `topic`, `webhook_id`, `api_version`) inside `to_signable_string` for `Webhooks::Request`, mirroring the pattern already used in `Auth::Oauth::AuthQuery#to_signable_string` [1](#0-0) , or otherwise cryptographically bind the shop-domain header to the HMAC before trusting `request.shop` in `Registry.process`.
