## Title
Fee-on-transfer/deflationary underlying tokens cause reserve insolvency in `WrappedHyperFungibleToken` - (File: `sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol`, also `sdk/packages/core/contracts/apps/WrappedHyperFungibleTokenUpgradeable.sol`)

### Summary
`WrappedHyperFungibleToken.send()` locks an underlying ERC20 via `safeTransferFrom` and then dispatches a cross-chain message committing to the *nominal* `params.amount`, without verifying how much was actually received by the contract. If the underlying token charges a transfer fee/burns a percentage on transfer (a "deflation" token), the contract receives less than `params.amount` but the destination-chain instance unconditionally unlocks the full nominal `message.amount` to the beneficiary via `safeTransfer`. This mismatch drains the locked-token reserve faster than it is topped up, over repeated transfers producing insolvency and inevitably causing legitimate redemptions/unlocks to fail (permanent freezing of funds) once the reserve is depleted.

### Finding Description
In `send()`:
```solidity
IERC20(_underlying).safeTransferFrom(msg.sender, address(this), params.amount);
...
bytes memory body = abi.encode(HyperFungibleToken.Message({
    from: abi.encodePacked(msg.sender),
    to: params.to,
    amount: params.amount,   // nominal amount, not actual received
    data: params.data
}));
``` [1](#0-0) [2](#0-1) 

There is no balance-before/after check to determine actual tokens received, unlike the codebase's own `IntentGatewayV2` implementation, which explicitly guards against this exact class of token:
```solidity
uint256 balBefore = IERC20(token).balanceOf(address(this));
IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
order.inputs[i].amount = IERC20(token).balanceOf(address(this)) - balBefore;
``` [3](#0-2) 

On the destination chain, `onAccept()` unlocks the full nominal `message.amount` from the reserve regardless of what was actually contributed on the source side:
```solidity
IERC20(_underlying).safeTransfer(beneficiary, message.amount);
``` [4](#0-3) 

Because the message commits to `params.amount` rather than the amount actually locked, every bridge operation with a fee-on-transfer/deflationary underlying token creates a shortfall between what the contract actually holds and what it has promised to pay out cross-chain. The identical pattern exists in `WrappedHyperFungibleTokenUpgradeable.sol`. [5](#0-4) [6](#0-5) 

### Impact Explanation
Any user can trigger this by bridging a deflationary/fee-on-transfer ERC20 configured as the wrapper's `_underlying`. Each `send()` call under-funds the reserve relative to what the destination side is authorized to unlock. Repeated over time (or amplified via large volume), the locked-token reserve backing all outstanding wrapped positions becomes insolvent — later legitimate users attempting to redeem/receive their bridged tokens via `onAccept()` will find `safeTransfer` reverting due to insufficient balance, resulting in permanent freezing of funds for those users, and effectively an unbacked liability for the difference already paid out to earlier users.

### Likelihood Explanation
This requires the governance/owner to configure a deflationary or fee-on-transfer token as the `_underlying` asset via `configure()`. Whether this is likely depends on the operator's token vetting process, but the contract provides no on-chain protection or documented restriction against such tokens, and the codebase's own `IntentGatewayV2` module demonstrates the project is aware of and normally defends against exactly this token class — indicating the omission here is a gap rather than an intentional design constraint.

### Recommendation
Mirror the pattern already used in `IntentGatewayV2`: measure the actual balance delta after `safeTransferFrom` in `send()` and use that measured amount (not `params.amount`) when building and dispatching the cross-chain `Message`. Alternatively, explicitly document that fee-on-transfer/deflationary tokens are unsupported as `_underlying` for `WrappedHyperFungibleToken`/`WrappedHyperFungibleTokenUpgradeable`, and consider adding a governance-enforced allowlist or a runtime check that rejects tokens exhibiting this behavior.

### Proof of Concept
1. Owner configures `WrappedHyperFungibleToken` with `_underlying` = a deflationary ERC20 that burns 5% on every `transfer`/`transferFrom`.
2. User A calls `send({amount: 100e18, ...})`. `safeTransferFrom` moves 100e18 nominal but the contract's balance only increases by 95e18 (5e18 burned). The dispatched message nonetheless encodes `amount: 100e18`.
3. On the destination chain, `onAccept()` executes `safeTransfer(beneficiary, 100e18)`, paying out the full nominal amount even though only 95e18 worth was actually locked on the source side.
4. Repeat with more users; each round the destination reserve is over-paid relative to what was actually locked. Eventually a legitimate redemption/unlock reverts because `IERC20(_underlying).safeTransfer` fails due to insufficient contract balance, permanently freezing that user's funds while earlier users have already extracted the surplus.
