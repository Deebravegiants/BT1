## Analysis Result

### Title
CORS wildcard-origin allowlist bypass via missing domain-boundary check in Gateway HTTP server - (File: core/services/gateway/network/httpserver.go)

### Summary
The Gateway's HTTP server implements a custom CORS origin check, `isAllowedOrigin`, that supports wildcard-style allowed origins (e.g. `https://*.ethereum.org`). The wildcard match is implemented with a raw `strings.HasSuffix` comparison that does not enforce a domain boundary (a preceding `.` or exact match), allowing any attacker-registered domain that merely ends with the configured suffix string — not just legitimate subdomains — to be treated as an allowed CORS origin.

### Finding Description
`isAllowedOrigin` splits both the incoming `Origin` header and each configured allowed origin into scheme/host/port, then for wildcard entries strips the `*.` prefix and checks `strings.HasSuffix(originHost, allowedHost)`: [1](#0-0) 

Because `HasSuffix` performs a pure string-suffix comparison, an origin host that is not a real subdomain of the allowed domain — but simply ends with the same character sequence — will still match. For example, with an operator configuring `CORSAllowedOrigins = ["https://*.chain.link"]`, `allowedHost` becomes `chain.link`. An attacker who registers (or controls) a domain such as `https://evilchain.link` produces `originHost = "evilchain.link"`, and `strings.HasSuffix("evilchain.link", "chain.link")` evaluates to `true`, even though `evilchain.link` is a completely unrelated, attacker-owned domain and not a subdomain of `chain.link`.

This is invoked directly from `handleRequest`, which is the entry point for every unprivileged HTTP request hitting the Gateway's public-facing endpoint, using the attacker-controlled `Origin` request header: [2](#0-1) 

If `isAllowedOrigin` returns `true`, the server reflects the attacker's `Origin` value back in `Access-Control-Allow-Origin`, effectively granting that attacker-controlled origin permission to make authenticated cross-origin requests against the Gateway API.

This is the same root-cause bug class as the Keycloak advisory: a wildcard/suffix-based match intended to scope trust to subdomains of a specific domain, implemented without a proper boundary check, allowing unrelated attacker-controlled origins to satisfy the check and bypass the allowlist.

### Impact Explanation
An attacker who registers a domain ending in the same character sequence as a configured wildcard allowed origin can have their origin treated as trusted by the Gateway CORS policy. Combined with any credentialed or session-bearing cross-origin calls made against Gateway endpoints, this enables an allowlist bypass that could allow unauthorized cross-origin requests/response reads from a malicious site, matching the "allowlist bypass" impact category.

### Likelihood Explanation
The wildcard matching path is only reachable when an operator configures a wildcard entry in `CORSAllowedOrigins` (e.g. `*.somecompany.com`), a documented and supported configuration option: [3](#0-2) 
Given that, exploitation only requires the attacker to control (register) any domain name ending with the same string as the configured suffix — no special network position or privileged access is required, and the check is triggered purely by the `Origin` header on a normal HTTP request.

### Recommendation
Update `isAllowedOrigin` to require a domain boundary when doing suffix matching, e.g. verify that `originHost == allowedHost` or `originHost` ends with `"."+allowedHost` (not just a raw string suffix), so `evilchain.link` is correctly rejected as not matching `*.chain.link`.

### Proof of Concept
1. Operator configures Gateway with `CORSEnabled = true` and `CORSAllowedOrigins = ["https://*.chain.link"]`.
2. Attacker registers `https://evilchain.link` (or any domain ending in `chain.link`).
3. Attacker's browser sends a request to the Gateway with header `Origin: https://evilchain.link`.
4. `isAllowedOrigin` strips `*.` to get `allowedHost = "chain.link"`, computes `originHost = "evilchain.link"`, and `strings.HasSuffix("evilchain.link", "chain.link")` returns `true`.
5. The server responds with `Access-Control-Allow-Origin: https://evilchain.link`, granting the attacker's unrelated domain cross-origin trust intended only for legitimate `*.chain.link` subdomains.

func (s *httpServer) handleRequest(w http.ResponseWriter, r *http.Request) {
	if s.config.CORSEnabled {
		origin := r.Header.Get("Origin")
		if s.isAllowedOrigin(origin) {
			w.Header().Set("Access-Control-Allow-Origin", origin)
			w.Header().Set("Access-Control-Allow-Methods", "GET, POST, OPTIONS")
			w.Header().Set("Access-Control-Allow-Headers", "Content-Type")
		}

		// handle preflight requests
		if r.Method == http.MethodOptions {
			w.WriteHeader(http.StatusNoContent)
			return
		}
	}
