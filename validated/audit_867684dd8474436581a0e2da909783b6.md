## Finding

### Title
Webhook shop identity spoofing via HMAC-unbound `shop-domain` header - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` attribute exclusively from the unauthenticated `x-shopify-shop-domain` (or `shopify-shop-domain`) HTTP header, while `Utils::HmacValidator` verifies only the raw request body against that same shared, app-wide `api_secret_key`. Because the HMAC signature is completely independent of the shop-domain header, and because the same `api_secret_key` is valid for every shop that has installed the host app, any attacker who can obtain one genuine `(body, hmac)` pair for *any* shop (including one they legitimately control) can replay it against the app's webhook endpoint with a forged `shop-domain` header pointing at a victim tenant. `Registry.process` accepts the request as authentic and forwards the attacker-controlled `shop` value straight to the app's webhook handler as trusted tenant identity.

### Finding Description
The identity binding that should hold is:
```
shop_header_used_by_handler == shop_that_the_verified_hmac_was_actually_computed_for
```
This equality is never enforced.

`HmacValidator.validate` computes the signature purely from `to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` returns only the raw body — the shop-domain header is never part of the signed material: [2](#0-1) 

`shop` is read straight from a caller-supplied HTTP header with zero cryptographic binding to the HMAC: [3](#0-2) 

`Registry.process` validates only the body HMAC and then trusts `request.shop` as the tenant identifier passed to the handler: [4](#0-3) 

Because `api_secret_key` is the app's own client secret (not a per-shop secret), the HMAC of any given body string is identical no matter which shop the webhook event actually originated from. An attacker who installs the target app on a shop they control receives real, validly-signed webhook deliveries from Shopify for their own store. For any webhook topic whose JSON body does not itself embed the shop domain (many payloads simply describe the resource, e.g., generic app/shop lifecycle or empty-body test pings), the `(body, hmac)` pair captured from the attacker's own store is equally valid for a different shop's body — the header is the only thing that differs, and it isn't checked.

### Impact Explanation
This breaks the tenant/shop identity boundary the gem is documented to preserve: `data.shop` is documented as authoritative ("The shop domain of the webhook") and downstream host applications key off it to route, persist, or dispatch data per-tenant. Successful exploitation lets a low-privileged attacker inject events attributed to a shop they do not control, producing cross-tenant data confusion/injection — the "Critical: cross-tenant access" category defined in scope.

### Likelihood Explanation
Exploitation requires only that the attacker be able to install the vulnerable app on any shop they control (a standard, unprivileged action any Shopify merchant/dev can perform) and be able to send arbitrary POST requests with custom headers to the app's public webhook endpoint — no possession of `api_secret_key`, access tokens, or TLS interception is needed. The likelihood is bounded mainly by whether a given webhook topic's body payload happens to omit shop-identifying content, which is common for several topics.

### Recommendation
Bind the header-derived `shop` value into the HMAC-signed material (e.g., include it in `to_signable_string`, or independently verify it against the shop associated with the session/registration that requested the webhook) before trusting `request.shop` in `Registry.process`. Short term, document that `request.shop` is unauthenticated and must be independently cross-checked by the host application against a known/installed shop list before use.

### Proof of Concept
1. Attacker installs the vulnerable host app on their own store `attacker.myshopify.com` and registers for a webhook topic whose payload body is generic/shop-agnostic (e.g., `{}` or a fixed schema not containing the shop domain).
2. Shopify delivers a legitimate webhook to the app's endpoint with headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid-hmac-of-body>`, and the captured `raw_body`.
3. Attacker replays the exact same `raw_body` and `x-shopify-hmac-sha256` value to the same endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` ( [5](#0-4) ) succeeds because it only checks the (unchanged) body against the (unchanged) valid HMAC.
5. `Registry.process` invokes the handler with `WebhookMetadata.new(..., shop: "victim.myshopify.com", ...)`, and the host application acts on the spoofed victim shop identity.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
