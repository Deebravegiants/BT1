### Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable content solely from the raw request body, while the `shop` (tenant identity) field returned to the handler is read directly from an unauthenticated HTTP header. Any party that possesses one valid `(raw_body, hmac)` pair signed with the app's `api_secret_key` — trivially obtainable by installing the app on their own store and capturing its own webhook deliveries — can replay that body with an arbitrary `x-shopify-shop-domain` header, causing `ShopifyAPI::Webhooks::Registry.process` to deliver data attributed to a victim shop of the host application's choosing.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns `@raw_body`: [1](#0-0) 

`shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic binding to the HMAC at all: [2](#0-1) 

`Utils::HmacValidator.validate` only checks `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)` — i.e., it verifies the body, never the shop header: [3](#0-2) 

`Registry.process` validates the HMAC and then forwards `request.shop` — the unauthenticated field — directly into `WebhookMetadata`, which is the identity the handler is documented to trust for routing/tenant lookups: [4](#0-3) [5](#0-4) 

The library's own documentation instructs host apps to key work off `data.shop` (e.g., `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), confirming that `shop` is meant to be the trusted tenant identifier delivered by this gem: [6](#0-5) 

**Binding broken (as an equality):** the gem should guarantee `shop_header == shop_that_produced(raw_body, hmac)`. In fact only `hmac == HMAC(secret, raw_body)` is checked; `shop_header` is arbitrary attacker-supplied input never covered by the signature. Since one app uses a single `api_secret_key` shared across every installed shop (this is the standard Shopify multi-tenant app model — one client secret, many shop installs), any merchant/attacker who installs the app on their own store can generate a genuinely-signed `(raw_body, hmac)` pair and then re-send it with a forged `shop-domain` header naming a different, victim shop.

### Impact Explanation
This is a cross-tenant data confusion vulnerability: a host application built per this gem's documented contract will process attacker-supplied webhook payloads under an arbitrary victim shop's identity (e.g., queue background jobs, write to the victim's tenant record, trigger data mutation/redaction flows, or overwrite state keyed by `shop`) despite the payload never actually originating from Shopify for that shop. This crosses a tenant boundary using only unprivileged access (installing the app on one's own store), satisfying the "cross-tenant access" impact bucket.

### Likelihood Explanation
Any developer/business user can install a public or custom app on their own store, trigger any subscribed webhook topic (e.g., `app/uninstalled`, `products/create`) to obtain a legitimately Shopify-HMAC-signed `(raw_body, hmac)` pair, then POST that exact body/HMAC to the app's webhook endpoint with a modified `shop-domain` (and optionally `topic`/`webhook-id`) header. No secrets, tokens, or privileged access are required — only network access to the app's public webhook URL. Likelihood is high wherever a host app trusts `data.shop` (as this gem's own docs recommend) without independently re-verifying shop identity.

### Recommendation
Include the shop domain (and topic/webhook id) in the HMAC-verified signable content, or otherwise cryptographically bind them to the payload, so `Utils::HmacValidator.validate` fails if any of these fields are altered relative to what Shopify actually sent. At minimum, document prominently that `shop`, `topic`, and `webhook_id` headers are unauthenticated and must not be trusted for tenant routing without an independent shop-registration check (e.g., cross-referencing against a shop known to have this specific webhook subscription/id registered).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (an ordinary, unprivileged store) and receives a real webhook, e.g. `orders/create`, with raw body `B` and header `x-shopify-hmac-sha256: H`, where `H = Base64(HMAC-SHA256(api_secret_key, B))`.
2. Attacker sends a forged HTTP request to the app's public webhook endpoint:
   - Headers: `x-shopify-topic: orders/create`, `x-shopify-hmac-sha256: H`, `x-shopify-shop-domain: victim-shop.myshopify.com`, `x-shopify-webhook-id: <anything>`
   - Body: `B` (unchanged, byte-for-byte)
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: ...)` is built server-side; `Utils::HmacValidator.validate` recomputes `HMAC(secret, B)` and it matches `H`, so validation succeeds [7](#0-6) .
4. `Registry.process` calls the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)` [8](#0-7) , even though this payload never came from Shopify for `victim-shop`.
5. The host application (following this gem's documented usage) acts on `data.shop`, causing data intended for/about `attacker-shop` to be attributed to and processed under `victim-shop`'s tenant context.

          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
