### Title
Webhook shop/topic/webhook_id/api_version headers are not covered by the HMAC signature, enabling cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes and validates the HMAC over the raw body only, while the `shop`, `topic`, `webhook_id`, and `api_version` fields are parsed from unauthenticated HTTP headers and passed straight through to the application's webhook handler. Because the same app `client_secret` is used to sign webhooks for every shop that installs the app, an attacker who controls one shop (or otherwise obtains a validly-signed webhook body) can replay that body to the app's webhook endpoint while forging the `shopify-shop-domain` header to name a victim shop. `Utils::HmacValidator.validate` will accept it because it only checks `to_signable_string` (the raw body) against the HMAC, and `Registry.process` will dispatch the forged shop identity to the handler as authentic.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are read directly from attacker-controlled HTTP headers and are never included in the signed string: [2](#0-1) 

`HmacValidator.validate`/`validate_signature` only verifies `verifiable_query.to_signable_string` (i.e., the raw body) against the HMAC using the app's `api_secret_key`: [3](#0-2) 

`Registry.process` gates purely on this body-only HMAC check, then forwards `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` — all unauthenticated header values — into `WebhookMetadata`, which is delivered to the app's handler as trusted, verified data: [4](#0-3) [5](#0-4) 

**The broken binding, stated as an equality:**
`bytes verified by HMAC` (`raw_body`) ≠ `bytes/fields acted upon` (`shop`, `topic`, `webhook_id`, `api_version` headers). The gem treats `WebhookMetadata.shop` as an authenticated tenant identifier, but the HMAC never covers that value.

Because the app's `client_secret` (not a per-shop secret) is what signs webhooks, any tenant that has legitimately installed the app can obtain a body + HMAC pair that is valid under the app's shared secret. That attacker-controlled tenant can then replay the exact same raw body to the app's webhook endpoint with a modified `shopify-shop-domain` (or `x-shopify-shop-domain`) header naming a different, victim shop. `HmacValidator.validate` still returns `true` (raw body/HMAC pair unchanged), and `Registry.process` will build a `WebhookMetadata` claiming the event originated from the victim shop, invoking the handler as if it were an authentic event for that victim's tenant.

### Impact Explanation
This is a cross-tenant identity-binding break within the gem's own webhook verification path: the gem asserts webhook authenticity via `HmacValidator.validate` but hands the caller-controlled `shop` field to the application as if it were verified alongside the body. Any application logic that keys off `WebhookMetadata.shop` (e.g., looking up the shop's stored session/access token, updating shop-scoped records, or triggering privileged shop-scoped API calls) can be made to act on/for the wrong tenant, using data supplied by a different (attacker-controlled) tenant. This matches the "Critical - cross-tenant access" impact category, since it lets a single tenant with legitimate app access impersonate arbitrary other shops toward the app's own webhook-processing logic.

### Likelihood Explanation
Likelihood is realistic but requires the attacker to be an existing, "unprivileged" user of the ecosystem — i.e., they must be able to install the target app on a shop they control (a normal, low-privilege action for any Shopify merchant/developer), which lets them harvest a validly-HMAC'd body for one of the mandatory or subscribed topics. From there, forging the shop header on the HTTP request to the app's public webhook endpoint requires no secret knowledge at all, since that header is completely outside the HMAC's scope.

### Recommendation
- Extend `to_signable_string` (or add a secondary check in `Registry.process`) to bind the `shop`, `topic`, and `webhook_id` header values into the value that is HMAC-verified, or otherwise cryptographically bind them to the payload.
- Alternatively/additionally, require `Registry.process` (or the calling application, documented as a hard requirement) to cross-check `request.shop` against the shop that the webhook was actually registered for (e.g., by looking up an expected shop/webhook mapping) before trusting `WebhookMetadata.shop`.
- Document explicitly that `WebhookMetadata.shop` is *not* itself authenticated by the HMAC and must not be used to route to privileged/tenant-scoped operations without additional verification.

### Proof of Concept
1. Attacker registers the target app on `attacker.myshopify.com` and subscribes to a webhook topic (e.g., `orders/create`).
2. Shopify sends a webhook to the app's endpoint with body `B` and header `shopify-hmac-sha256: HMAC(app_secret, B)`, `shopify-shop-domain: attacker.myshopify.com`.
3. Attacker captures this request, then re-sends it to the same app endpoint unmodified except for the header `shopify-shop-domain: victim.myshopify.com` (and/or `shopify-topic`).
4. `ShopifyAPI::Webhooks::Request.new` parses `shop = "victim.myshopify.com"`, but `Utils::HmacValidator.validate` still passes because it only checks `B` against the unchanged HMAC: [6](#0-5) 
5. `Registry.process` dispatches `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed(B), ...)` to the registered handler, which now processes attacker-supplied content as if it belongs to the victim shop.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
