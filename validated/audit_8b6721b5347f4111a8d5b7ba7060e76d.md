### Title
Webhook `shop` (and other) headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw body only, while the `shop`, `topic`, `api_version`, and `webhook_id` fields — all of which are read from HTTP headers and directly acted upon by `ShopifyAPI::Webhooks::Registry.process` — are excluded from the signed data. This breaks the intended binding `hmac == HMAC(secret, body)` from the binding `hmac == HMAC(secret, {body, shop})` that `Registry.process` implicitly assumes when it trusts `request.shop` after HMAC validation succeeds.

### Finding Description
`Utils::HmacValidator.validate` verifies the HMAC by comparing it against `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` returns only `@raw_body`: [2](#0-1) 

But `shop`, `topic`, `api_version`, and `webhook_id` are all read straight from HTTP headers, none of which are part of the signed payload: [3](#0-2) 

`Registry.process` validates only the body HMAC, then hands `request.shop` (an unauthenticated header value) directly into the handler as the tenant identifier, with no cross-check that the header corresponds to the shop that generated the signature: [4](#0-3) 

Since a single app's `client_secret` is used to sign webhook bodies for every shop that has the app installed, the HMAC over the body alone does not bind the request to any particular tenant. Anyone can install the app on their own shop (an unprivileged, self-service action requiring no special access), receive a legitimately signed webhook with a given body, and then replay that exact `(raw_body, hmac)` pair to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header value naming a different, victim shop. `Utils::HmacValidator.validate` will still return `true` because it only checks the body, and `Registry.process` will invoke the handler with `WebhookMetadata` claiming the spoofed shop: [4](#0-3) 

Any host application logic that uses `data.shop` to select which tenant's records to create/update/delete (e.g., mandatory `shop/redact`, `customers/redact`, `customers/data_request` topics, or app-specific business webhooks) will act on the wrong tenant using an attacker-controlled shop value that was never cryptographically bound to the signed payload.

### Impact Explanation
This is a cross-tenant integrity issue: an attacker who legitimately controls one shop can forge webhook deliveries that the app is misled into attributing to any other shop of their choosing, because the tenant identifier (`shop`) is trusted without being covered by the HMAC. This can trigger cross-tenant side effects in host application logic (e.g., data deletion/redaction against the wrong shop, or state corruption keyed by the spoofed shop domain), matching the "Critical - cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is moderate-to-high: the only prerequisite is the ability to install the target app on any shop (self-service, unprivileged) to obtain one valid `(raw_body, hmac)` pair, and the ability to send an HTTP request to the app's webhook endpoint with a forged `shopify-shop-domain` header — both of which require no access token, no `api_secret_key`, and no privileged Shopify account.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) header values in the signable string used for HMAC verification, or otherwise cryptographically bind the shop identity to the signed payload (e.g., verify the topic/shop combination against the webhook subscription that was registered), so `Registry.process` cannot be made to attribute a validly-signed body to an attacker-chosen shop.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` and registers a webhook handler, receiving a legitimate webhook delivery with body `B` and header `x-shopify-hmac-sha256: H` (valid for `B` under the app's shared `client_secret`).
2. Attacker replays the same `B`/`H` to the app's webhook endpoint but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request#hmac` decodes `H`, and `Utils::HmacValidator.validate` recomputes the HMAC over `to_signable_string` (`B` only), which matches `H`, so validation succeeds: [5](#0-4) 
4. `Registry.process` invokes the registered handler with `WebhookMetadata.new(... shop: request.shop ...)`, where `request.shop` is `"victim-shop.myshopify.com"` — a value the attacker fully controls, despite the HMAC check having "passed": [6](#0-5)
