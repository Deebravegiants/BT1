### Title
Unbounded parent-hash cycle in `AncestryChain::ancestry` allows a relayed GRANDPA consensus proof to loop forever, permanently freezing consensus updates - ([File: modules/consensus/grandpa/primitives/src/justification.rs])

### Summary
`AncestryChain::ancestry` walks a header's `parent_hash` chain looking for a `base` hash, using a `while current_hash != base { ... }` loop with no bound on iterations and no cycle detection. The `AncestryChain` map is built directly from attacker/relayer-supplied `unknown_headers` (and, transitively, `votes_ancestries`) inside a `GrandpaJustification`/`FinalityProof`, which is untrusted bytes submitted in an ISMP consensus message. A relayer can craft two or more headers whose `parent_hash` fields point at each other (a cycle) without ever including the real `base`. Since every hash in the cycle is present in the map, the loop never hits the `None` arm that would terminate it with `NotDescendent`, and it spins forever while unboundedly growing `route`. This is the same bug class as CVE-2022-35724 (Apache Avro reader looping endlessly on attacker-controlled input, CWE-835), reachable here through consensus-proof verification instead of Avro decoding.

### Finding Description
`AncestryChain::ancestry`: [1](#0-0) 

```rust
fn ancestry(
    &self,
    base: H::Hash,
    block: H::Hash,
) -> Result<Vec<H::Hash>, finality_grandpa::Error> {
    let mut route = vec![block];
    let mut current_hash = block;
    while current_hash != base {
        match self.ancestry.get(&current_hash) {
            Some(current_header) => {
                current_hash = *current_header.parent_hash();
                route.push(current_hash);
            },
            _ => return Err(finality_grandpa::Error::NotDescendent),
        };
    }
    Ok(route)
}
```

`self.ancestry` is a `BTreeMap<H::Hash, H>` built by `AncestryChain::new` straight from the caller-supplied header slice: [2](#0-1) 

That header slice comes from `FinalityProof::unknown_headers`, decoded verbatim from the untrusted `proof` bytes of an ISMP consensus message, with no validation that the declared `parent_hash` fields form an acyclic chain toward any real genesis/root — the verifier trusts whatever `parent_hash` value is embedded in each attacker-supplied header struct: [3](#0-2) 

This same `ancestry` method is also invoked once per precommit inside `GrandpaJustification::verify_with_voter_set` (and internally by the `finality_grandpa` crate's `validate_commit`, which uses the `Chain` trait implemented by `AncestryChain`): [4](#0-3) 

Reachability: `GrandpaConsensusClient::verify_consensus` decodes the raw `proof: Vec<u8>` into a `ConsensusMessage`, then calls `verify_grandpa_finality_proof` / `verify_parachain_headers_with_grandpa_finality_proof`, both of which build an `AncestryChain` from the untrusted headers and call `.ancestry(...)`: [5](#0-4) 

`verify_consensus` is the standard `ConsensusClient` entry point invoked by `pallet-ismp`'s unsigned message-handling path (`handle_unsigned` / `handle_incoming_message`), so any relayer can submit a crafted GRANDPA consensus proof containing a small cyclic set of fake headers to trigger this loop — no privileged role, signature over the header content's parent pointers, or prior valid state is required, since only the header's self-declared `parent_hash` field (attacker-controlled plaintext) is used for the walk.

### Impact Explanation
Once triggered, the executing node/runtime spins in an unbounded loop inside `ancestry`, consuming CPU indefinitely and growing `route` without bound. Because this runs inside on-chain consensus-client verification (dispatched via `pallet-ismp`'s unsigned extrinsic path), a single malicious relayed proof can hang block execution for the GRANDPA consensus client, denying consensus updates for that light client and effectively freezing the associated bridge route (no further state commitments / message delivery can be verified through it) — matching "a route unable to deliver messages" under High severity DoS impact.

### Likelihood Explanation
The attack requires only crafting a `FinalityProof` with a handful of headers whose `parent_hash` fields cycle among themselves (trivial to construct offline, no cryptographic material other than well-formed SCALE-encoded header structs is needed to reach the ancestry walk — the header's finality *signature*/*justification* checks occur separately and can be exercised or bypassed depending on which call path is hit first, but `verify_with_voter_set`'s own precommit loop and the underlying `finality_grandpa::validate_commit` both invoke the vulnerable `ancestry` function directly on attacker-supplied ancestry headers before/independently of full commit validation succeeding). Submission is permissionless via the standard unsigned consensus-message relay path, so likelihood is high for any deployment using the GRANDPA consensus client.

### Recommendation
Bound the `ancestry` walk by the number of distinct headers in the map (e.g., `self.ancestry.len() + 1` max iterations) and return an error (e.g., `NotDescendent` or a new `CyclicAncestry` error) if the walk exceeds that bound without reaching `base`. Alternatively, track visited hashes in a `BTreeSet` and reject immediately if a hash is revisited before reaching `base`.

### Proof of Concept
1. Construct two headers `H1`, `H2` such that `hash(H1) = A`, `H1.parent_hash = B`, `hash(H2) = B`, `H2.parent_hash = A` (any header fields can be chosen freely to realize this; only the hash/parent_hash relationship matters for the loop).
2. Place both headers in `FinalityProof::unknown_headers` (or `GrandpaJustification::votes_ancestries`) such that neither `A` nor `B` equals the intended `base`/`consensus_state.latest_hash`.
3. Submit this as the `proof` bytes of a GRANDPA `ConsensusMessage` through the standard unsigned ISMP message-handling path invoking `GrandpaConsensusClient::verify_consensus`.
4. `AncestryChain::ancestry(base, target)` (or the internal call from `finality_grandpa::validate_commit`/`verify_with_voter_set`) walks `target -> B -> A -> B -> A -> ...` forever, since both `A` and `B` are present in the map and neither equals `base`, causing unbounded CPU consumption and hanging that verification call.
