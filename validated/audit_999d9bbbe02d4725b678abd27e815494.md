This confirms an inconsistency: `ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, and `TokenExchange.migrate_to_expiring_token` all call `Utils::ShopValidator.sanitize!(shop)` before using the shop value to construct the URL that receives the app's `client_secret`. `Oauth.begin_auth`, however, never validates its `shop` parameter — it is passed straight into `auth_base_uri(shop)` to build the redirect target.

### Title
OAuth `begin_auth` builds the authorize redirect from an unvalidated `shop` host, breaking the binding between the validated shop and the host that receives the app's credentials - (File: lib/shopify_api/auth/oauth.rb)

### Summary
`ShopifyAPI::Auth::Oauth.begin_auth` accepts a caller-supplied `shop` string and uses it, unsanitized, to build the OAuth authorize URL that the merchant's browser is redirected to. Every other credential-issuing flow in this gem (`ClientCredentials`, `RefreshToken`, `TokenExchange.migrate_to_expiring_token`) runs the `shop` argument through `Utils::ShopValidator.sanitize!` before using it to build the URL that will receive `client_id`/`client_secret`, but `begin_auth` does not.

### Finding Description
`begin_auth` builds the redirect target directly from the raw `shop` argument: [1](#0-0) 
and the private helper constructs the host with no domain check at all: [2](#0-1) 

Compare this with the other three token-issuing flows, which all treat `shop` as untrusted input and validate it against the trusted-domain allowlist before it is used to build a request target: [3](#0-2) [4](#0-3) [5](#0-4) 

The validator itself exists specifically to prevent an attacker-controlled string from being treated as a Shopify host: [6](#0-5) [7](#0-6) 

The identity binding that should hold is: `shop (validated as a trusted *.myshopify.com/myshopify.io/spin.dev/shop.dev/shopify.com host)` == `shop (host embedded in the OAuth authorize URL that the browser is sent to, alongside client_id and redirect_uri)`. `begin_auth` breaks this equality — the host used to build the redirect is whatever string the caller (ultimately often derived from an HTTP request parameter such as `?shop=`, per Shopify app conventions and the OAuth flow documented in `docs/usage/oauth.md`) passes in, with no allowlist check.

### Impact Explanation
If a host application (as is standard practice per Shopify app tutorials) passes a `shop` query parameter straight from an incoming installation/login request into `begin_auth(shop:, ...)`, an attacker can supply an arbitrary hostname (e.g., `attacker.example`). The merchant's browser is then redirected to `https://attacker.example/admin/oauth/authorize?client_id=<real client_id>&redirect_uri=<real app callback>&state=<nonce>&scope=...`, exposing the app's `client_id` and internal `redirect_uri`/scope configuration to an attacker-controlled host and enabling a forced/attacker-steered OAuth flow (the browser session cookie containing `state` is set for the real app's domain by `begin_auth`, so the attacker's site can attempt to complete a forced-OAuth-style flow back against the real callback). While the callback (`validate_auth_callback`) still requires a valid HMAC computed with `Context.api_secret_key`, which the attacker cannot forge, this still constitutes credential/configuration leakage to an untrusted host and a broken host-validation boundary that every sibling flow in the same module explicitly guards against.

### Likelihood Explanation
Any unprivileged internet user who can reach the app's "begin OAuth" endpoint with a controlled `shop` parameter (the normal entry point for Shopify app installation flows, as documented in `docs/usage/oauth.md`) can trigger this — no credentials, tokens, or `api_secret_key` are required. The inconsistency between `begin_auth` and the other three sibling methods in the same `Auth` module strongly indicates this is a missing validation rather than an intentional design choice.

### Recommendation
Call `Utils::ShopValidator.sanitize!(shop)` (or `sanitize_shop_domain`) at the top of `begin_auth`, exactly as done in `ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, and `TokenExchange.migrate_to_expiring_token`, before passing `shop` to `auth_base_uri`.

### Proof of Concept
1. A host app implements the documented pattern: `ShopifyAPI::Auth::Oauth.begin_auth(shop: params[:shop], redirect_path: "/auth/callback")`.
2. Attacker sends the victim merchant a link to the app's install route with `?shop=attacker.example`.
3. `begin_auth` calls `auth_base_uri("attacker.example")`, producing `https://attacker.example/admin/oauth/authorize?client_id=<APP_CLIENT_ID>&scope=...&redirect_uri=https://realapp.com/auth/callback&state=<nonce>`, and the app sets the `state` cookie on the victim's browser scoped to the real app's domain.
4. The victim's browser is redirected to the attacker's host, leaking `client_id`, `redirect_uri`, and `scope` to the attacker and placing the victim into an attacker-controlled page while a valid `state` cookie is already set on the real app — a direct violation of the shop-host trust boundary that `ShopValidator` is designed to enforce elsewhere in the same module.

          scope = if scope_override.nil?

          state = SecureRandom.alphanumeric(NONCE_LENGTH)
