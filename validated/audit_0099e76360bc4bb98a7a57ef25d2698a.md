This confirms the vulnerable pattern. Both `process_swap_base_out` (`SwapBaseOut`, instruction tag 11) and `process_swap_base_out_v2` (`SwapBaseOutV2`) call `Calculator::swap_token_amount_base_out()` with `swap.amount_out` (fully attacker-controlled instruction data) **before** validating that `swap.amount_out < total_pc_without_take_pnl` / `total_coin_without_take_pnl`. That validation only happens later, at [1](#0-0) .

Inside `swap_token_amount_base_out`, the vault totals are reduced by `amount_out` via `checked_sub(amount_out).unwrap()` with no `?`/`ok_or` guard: [2](#0-1)  for `Coin2PC` and [3](#0-2)  for `PC2Coin`. If a caller supplies `amount_out >= total_pc_without_take_pnl` (or `total_coin_without_take_pnl`), the subtraction underflows, `checked_sub` returns `None`, and `.unwrap()` panics — an on-chain `Option::unwrap()` panic reachable from a single attacker-crafted transaction, directly analogous to the CVE's `history_index().unwrap()` panic on peer-controlled request handlers.

### Title
Unvalidated `swap.amount_out` causes `checked_sub().unwrap()` panic (transaction abort / DoS) in `process_swap_base_out` and `process_swap_base_out_v2` - (File: program/src/processor.rs, program/src/math.rs)

### Summary
`SwapBaseOut` and `SwapBaseOutV2` instruction handlers compute the required input amount via `Calculator::swap_token_amount_base_out` before checking that the caller-supplied `amount_out` is smaller than the pool's available liquidity. The math helper performs `total_without_take_pnl.checked_sub(amount_out).unwrap()`, which panics on underflow whenever `amount_out` is greater than or equal to the corresponding pool total.

### Finding Description
In `process_swap_base_out` the call sequence is: unpack instruction → compute `total_pc_without_take_pnl`/`total_coin_without_take_pnl` → immediately call `Calculator::swap_token_amount_base_out(swap.amount_out.into(), ...)` [4](#0-3) . Only afterwards, inside the `match swap_direction` block, does the code check `if swap.amount_out >= total_pc_without_take_pnl` (or `total_coin_without_take_pnl`) and return `AmmError::InsufficientFunds` [1](#0-0) . The identical ordering exists in `process_swap_base_out_v2` [5](#0-4) .

`Calculator::swap_token_amount_base_out` itself does `total_pc_without_take_pnl.checked_sub(amount_out).unwrap()` for `Coin2PC` and `total_coin_without_take_pnl.checked_sub(amount_out).unwrap()` for `PC2Coin` [6](#0-5) . Because `swap.amount_out` comes straight from unvalidated instruction data (`AmmInstruction::unpack`, tag `11`/`SwapBaseOutV2`) [7](#0-6) , any unprivileged caller can set `amount_out` equal to or greater than the pool's current PC/coin balance (net of `need_take_pnl`), causing the subtraction to underflow and `.unwrap()` to panic mid-transaction, before any of the later balance/slippage checks execute.

### Impact Explanation
A panicking `unwrap()` in an on-chain program instruction causes the transaction to abort (equivalent to a runtime error), but more importantly it demonstrates that the intended validation order is broken: the amount-out bound check that is supposed to gate this computation runs strictly after the unchecked subtraction. Any account (a low-liquidity pool, or a pool drained close to zero via prior legitimate swaps/withdrawals) can be targeted by supplying an oversized `amount_out`, reliably reverting the transaction via a panic rather than a clean program error. This matches the reported bug class (an assumption that a value satisfies a precondition that is not actually enforced before use, leading to an `Option::unwrap()` panic reachable by an unprivileged caller in a request/instruction handler) — no funds are stolen or minted, but it is a reachable, single-transaction DoS/panic path with attacker-chosen instruction data.

### Likelihood Explanation
High likelihood of triggering: `amount_out` is a plain `u64` fully controlled by the transaction sender, and no upstream check clamps it below the pool totals before the arithmetic in `swap_token_amount_base_out` runs. Any swapper can construct a `SwapBaseOut`/`SwapBaseOutV2` instruction with `amount_out >= total_pc_without_take_pnl` (or `total_coin_without_take_pnl`) targeting any pool, especially pools with low liquidity.

### Recommendation
Move the `swap.amount_out >= total_*_without_take_pnl` bounds check before calling `Calculator::swap_token_amount_base_out`, and additionally replace the `checked_sub(...).unwrap()` calls in `swap_token_amount_base_out` (`program/src/math.rs` lines 341 and 358) with proper `ok_or`/`?` error propagation (e.g., returning `AmmError::InsufficientFunds` or `AmmError::CalculationExRateFailure`) so the function never panics regardless of caller-supplied input ordering.

### Proof of Concept
1. Identify or create a pool where `total_pc_without_take_pnl` (for `Coin2PC`) or `total_coin_without_take_pnl` (for `PC2Coin`) is a known value `T`.
2. Submit a `SwapBaseOut` (tag `11`) or `SwapBaseOutV2` instruction with `amount_out = T` (or any value `>= T`) and a valid `max_amount_in`, using correctly-owned user source/destination token accounts.
3. Execution reaches `Calculator::swap_token_amount_base_out` at [4](#0-3)  before the `amount_out >= total_*` guard at [1](#0-0)  is ever evaluated.
4. Inside the helper, `total_pc_without_take_pnl.checked_sub(amount_out)` (or the coin equivalent) underflows and returns `None`; `.unwrap()` panics, aborting the transaction with a runtime panic instead of a controlled `ProgramError`.

    pub fn swap_token_amount_base_out(
        amount_out: U128,
        total_pc_without_take_pnl: U128,
        total_coin_without_take_pnl: U128,
        swap_direction: SwapDirection,
    ) -> U128 {
        let amount_in;
        match swap_direction {
            SwapDirection::Coin2PC => {
                // (x + delta_x) * (y + delta_y) = x * y
                // (coin + amount_in) * (pc - amount_out) = coin * pc
                // => amount_in = coin * pc / (pc - amount_out) - coin
                // => amount_in = (coin * pc - pc * coin + amount_out * coin) / (pc - amount_out)
                // => amount_in = (amount_out * coin) / (pc - amount_out)
                let denominator = total_pc_without_take_pnl.checked_sub(amount_out).unwrap();
                amount_in = total_coin_without_take_pnl
                    .checked_mul(amount_out)
                    .unwrap()
                    .checked_ceil_div(denominator)
                    .unwrap()
            }
            SwapDirection::PC2Coin => {
                // (x + delta_x) * (y + delta_y) = x * y
                // (pc + amount_in) * (coin - amount_out) = coin * pc
                // => amount_out = coin - coin * pc / (pc + amount_in)
                // => amount_out = (coin * pc + coin * amount_in - coin * pc) / (pc + amount_in)
                // => amount_out = coin * amount_in / (pc + amount_in)

                // => amount_in = coin * pc / (coin - amount_out) - pc
                // => amount_in = (coin * pc - pc * coin + pc * amount_out) / (coin - amount_out)
                // => amount_in = (pc * amount_out) / (coin - amount_out)
                let denominator = total_coin_without_take_pnl.checked_sub(amount_out).unwrap();
                amount_in = total_pc_without_take_pnl
                    .checked_mul(amount_out)
                    .unwrap()
                    .checked_ceil_div(denominator)
                    .unwrap()
            }
        }
