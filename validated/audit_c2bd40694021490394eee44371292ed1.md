Based on the investigation, the closest legitimate custody analog to the "duration not saved/limited" bug class is in the recently-added multisig timelock feature in `multisig_account.move`, specifically the missing re-validation of `override_threshold` against `num_signatures_required` whenever the signature threshold is later changed.

### Title
Multisig timelock override threshold is never re-validated after `num_signatures_required` is updated, allowing the timelock delay to be silently bypassed - (File: `aptos-move/framework/aptos-framework/sources/multisig_account.move`)

### Summary
`upsert_timelock_internal` validates, at set-time only, that `override_threshold > num_signatures_required` and `override_threshold <= owners.length()` [1](#0-0) . However, `num_signatures_required` can later be changed independently via `update_signatures_required`, `add_owners_and_update_signatures_required`, and `swap_owners_and_update_signatures_required`, all of which route through `update_owner_schema` [2](#0-1) . None of these owner/threshold-mutation entry points reference `MultisigAccountTimeLock` or re-check the invariant that `override_threshold` must stay greater than the (new) `num_signatures_required`.

### Finding Description
The `MultisigAccountTimeLock` design intends two execution paths: (1) reach `num_signatures_required` approvals and wait `timelock_period` seconds, or (2) reach the stricter `override_threshold` approvals for immediate execution [3](#0-2) . This is only safe as long as `override_threshold > num_signatures_required` holds, so path (2) is always a strictly harder condition than path (1).

If a multisig later raises `num_signatures_required` above the previously configured `override_threshold` (a normal, unprivileged self-governance action reachable through the same multisig approval + timelock flow), the invariant flips: reaching the new (higher) `num_signatures_required` now also automatically satisfies the old (lower) `override_threshold`. Since the code never revisits or invalidates the stale `override_threshold` when the signature requirement changes, every subsequent transaction that reaches the base approval threshold will also be treated as meeting the override condition and skip the mandatory `timelock_period` delay entirely — silently and permanently defeating the timelock for that multisig account.

### Impact Explanation
Multisig timelocks exist specifically to give owners/watchers a mandatory window to detect and react to (e.g., revoke approval for, or move funds out of reach of) a malicious or compromised pending transaction before it can execute. Once `override_threshold` becomes stale relative to a raised `num_signatures_required`, that safety delay silently disappears for all future transactions on the account, including transactions that move or reassign control of assets held by the resource account backing the multisig. This directly undermines a custody control guarantee (mandatory execution delay) that owners configured and rely on, without any explicit action to remove or downgrade the timelock — `remove_timelock`/`upsert_timelock` are never called, so on-chain state and views (`timelock_period`) still report the timelock as active and unchanged, masking the loss of protection.

### Likelihood Explanation
Reaching this state does not require any privileged or out-of-scope action: raising `num_signatures_required` is a normal, documented multisig self-management operation (`update_signatures_required`, `add_owners_and_update_signatures_required`, `swap_owners_and_update_signatures_required`) that any set of owners can execute through the standard proposal flow. Any multisig that (a) configures a timelock with an override threshold set close to the current signature requirement, and (b) later increases that requirement (a common security-hardening action, e.g., adding owners and raising the threshold) will silently fall into this broken state.

### Recommendation
When `num_signatures_required` changes (in `update_owner_schema` or wherever it is mutated), re-validate any existing `MultisigAccountTimeLock.override_threshold` against the new value, and either abort the update, automatically clear the timelock override, or force re-confirmation of the timelock configuration if the invariant `override_threshold > num_signatures_required` would be violated.

### Proof of Concept
1. Create a 3-owner multisig (A, B, C) with `num_signatures_required = 2`.
2. Call `upsert_timelock(multisig_signer, 3600, option::some(3))` — valid since `3 > 2` and `3 <= 3` [1](#0-0) .
3. Via the normal proposal flow, execute `update_signatures_required(multisig_signer, 3)`, raising the requirement to `3` (equal to the previously configured `override_threshold`) — this call performs no timelock re-validation [4](#0-3) .
4. Create a new transaction and collect the now-required 3 approvals. Because `override_threshold (3) <= votes (3)`, the transaction is treated as meeting the override condition and executes immediately, with no `timelock_period` wait — even though the timelock resource remains published and `timelock_period` view still reports `3600` seconds as configured protection.

**Note:** I was not able to fully read the body of `update_owner_schema` (the shared internal function backing all owner/threshold mutation entry points) before running out of investigation budget, so I cannot cite its exact line range confirming the absence of a timelock check — this should be verified directly in a full read of that function in `multisig_account.move`.
