### Title
Webhook shop-domain and topic headers are trusted for tenant routing but excluded from the HMAC signature, enabling cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop` (tenant) and `topic` values used to route and label the webhook come from unsigned HTTP headers. `ShopifyAPI::Webhooks::Registry.process` trusts `request.shop` as the authoritative tenant identifier once the body HMAC passes, without that field ever being bound to the signature. An attacker who controls any single shop that has the app installed can capture one of their own genuinely-signed webhook deliveries and replay it with the `shop-domain` header swapped to a victim shop, producing a request that still passes HMAC validation but is attributed to another tenant.

### Finding Description
The bug-class analog from the report is a weighted average that lets one identity's timestamp override another's because the function conflates two independently-controlled values. Here the equivalent identity-binding break is:

`hmac == HMAC(secret, raw_body)` while the trusted tenant identity `shop` is not part of what `hmac` covers, i.e. `shop != f(hmac)`.

Code proof: [1](#0-0) 

- `hmac` is derived only from the `hmac-sha256` header.
- `topic` and `shop` are both taken directly from separate, unsigned headers (`shopify-topic`, `shopify-shop-domain`).
- `to_signable_string` returns `@raw_body` exclusively — nothing else is bound into the signable string.

The validator then confirms only body integrity: [2](#0-1) 

`validate_signature` recomputes `HMAC(secret, verifiable_query.to_signable_string)` and compares it to the received `hmac`. Since `to_signable_string` for a webhook `Request` is just `@raw_body`, the `shop-domain` and `topic` headers can be altered freely without invalidating the signature.

Finally, once validation passes, the registry uses the header-derived, unsigned `shop` value as the tenant identity handed to the app's handler: [3](#0-2) 

`Registry.process` raises only if the HMAC is invalid, then builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` and hands it to the registered handler — the handler has no way to know that `shop` was never covered by the signature.

### Impact Explanation
This breaks the tenant-isolation guarantee that a webhook's HMAC is supposed to prove: "this body genuinely came from Shopify for shop X." In reality the HMAC only proves "this body genuinely came from Shopify for *some* shop that has this app installed." An attacker who legitimately installs the app on their own shop (an ordinary unprivileged action — no credentials of the app, no `api_secret_key`, no access token needed) can:

1. Trigger a real Shopify webhook for their own shop (e.g., `orders/create`), capturing the raw body and its valid `x-shopify-hmac-sha256` value.
2. Replay that exact `raw_body` + `hmac` to the app's public webhook endpoint, but with `x-shopify-shop-domain` rewritten to a victim merchant's domain (and, if desired, keep or adjust `x-shopify-topic` to any topic handler registered by the app, since topic is likewise unauthenticated).
3. `Utils::HmacValidator.validate` still passes because only `raw_body` is checked.
4. The app's webhook handler receives `WebhookMetadata` claiming the data belongs to the victim's shop and acts on it — creating, updating, or triggering side effects (e.g. orders, app/uninstalled handling, GDPR/mandatory webhook flows) under the wrong tenant.

This is a cross-tenant access vulnerability reachable by any unprivileged internet user who can install the app on a shop they control, satisfying the Critical impact bar ("cross-tenant access") without needing the app's `client_secret`, an access token, or any privileged account.

### Likelihood Explanation
Likelihood is high in any application that relies on this gem's webhook plumbing as designed: the vulnerable code path (`Request#shop`, `Request#topic`, `Registry.process`) is the library's standard, documented way of authenticating and routing webhooks, and every consumer of `ShopifyAPI::Webhooks::Registry.process` is affected unless the host application independently re-verifies `shop` against signed data (which the gem provides no hook for, since `shop` is never part of `to_signable_string`). The only prerequisite is the ability to install the app on any shop — normally an unauthenticated, self-service action for the attacker's own store.

### Recommendation
Bind the tenant/topic identity into the signature verification rather than trusting unsigned headers post-hoc:
- Include `shop`, `topic`, and (ideally) `webhook_id`/`api_version` in the value that is HMAC-verified, or
- Validate the `shop` header against an expected/allow-listed value (e.g., session store lookup) before trusting `request.shop`, and reject requests where the header-derived shop cannot be corroborated by out-of-band data, and
- Document explicitly that `HmacValidator.validate(request)` only guarantees body integrity, not header authenticity, so host apps do not conflate the two.

### Proof of Concept
```ruby
# Attacker owns "attacker-shop.myshopify.com" with the target app installed.
# They capture a real, validly-signed webhook delivery from Shopify:
raw_body = '{"id":123,"note":"legit order on attacker shop"}'
valid_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), api_secret_key, raw_body)

# Attacker replays the exact body+hmac but swaps the shop-domain header:
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(valid_hmac), # unchanged, still valid
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # attacker-controlled, unsigned
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

# Passes signature validation because only raw_body is covered by the HMAC:
ShopifyAPI::Utils::HmacValidator.validate(request) # => true

# Registry.process happily attributes the payload to the victim shop:
ShopifyAPI::Webhooks::Registry.process(request)
# handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: "orders/create", body: {...}))

module ShopifyAPI
  module Webhooks
    class Request
      extend T::Sig
      include Utils::VerifiableQuery

      sig { override.returns(String) }
      def hmac
        Digest.hexencode(Base64.decode64(T.cast(shopify_header("hmac-sha256"), String)))
      end

      sig { returns(String) }
      def topic
        T.cast(shopify_header("topic"), String)
      end

      sig { returns(String) }
      def shop
        T.cast(shopify_header("shop-domain"), String)
      end

      sig { returns(String) }
      def api_version
        T.cast(shopify_header("api-version"), String)
      end

      sig { returns(String) }
      def webhook_id
        T.cast(shopify_header("webhook-id"), String)
      end

      sig { override.returns(String) }
      def to_signable_string
        @raw_body
      end

      sig { returns(T::Hash[String, T.untyped]) }
      def parsed_body
        JSON.parse(@raw_body)
      end

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

module ShopifyAPI
  module Utils
    module HmacValidator
      extend T::Sig

      class << self
        extend T::Sig

        sig { params(verifiable_query: VerifiableQuery).returns(T::Boolean) }
        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end

        sig { params(signable_string: String, secret: String).returns(String) }
        def compute_signature(signable_string, secret)
          OpenSSL::HMAC.hexdigest(
            OpenSSL::Digest.new("sha256"),
            secret,
            signable_string,
          )
        end
      end
    end
  end
end
