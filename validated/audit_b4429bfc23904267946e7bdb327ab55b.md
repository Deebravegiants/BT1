### Title
Panic (uncaught exception) parsing a crafted BSC header's post-BOHR validator/attestation extra-data slices unsound-length-checked path in `parse_extra` - (File: `modules/consensus/bsc/verifier/src/primitives.rs`)

### Summary
`parse_extra` validates the overall length of `header.extra_data` against `EXTRA_VANITY_LENGTH + EXTRA_SEAL_LENGTH` and, for the validator section, against a computed `required_length`, but the per-field slicing that computes `address_bytes`/`bls_public_key_bytes` inside the validator loop indexes `remaining_data` using multiplication/addition that is only bounds-checked in aggregate, not per-iteration against `remaining_data.len()`. Because `validator_num` is attacker-controlled (`data[0]` from the crafted header, an untrusted byte from the consensus proof), and `header.timestamp` (also attacker-controlled inside the same untrusted header struct) selects whether the BOHR turn-byte is required, a relayer can submit a `BscClientUpdate` whose header round-trips the length check (e.g., by inflating `data_length` via other fields) while the validator loop's `remaining_data[i*VALIDATOR_BYTES_LENGTH .. ]` slice exceeds the actual buffer, causing a Rust slice-index-out-of-bounds panic.

### Finding Description
`verify_bsc_header` (called from `BscClient::verify_consensus` in `modules/ismp/clients/bsc/src/lib.rs`) calls `parse_extra::<H, C>(&update.attested_header)` before any BLS signature or authority-membership check runs [1](#0-0) . `parse_extra` computes `required_length` from `validator_num` and only checks the *aggregate* `data_length < required_length` guard before entering the validator-parsing loop [2](#0-1) . This entry point is directly reachable by an unprivileged relayer: `BscClient::verify_consensus` decodes the untrusted `proof` bytes into a `BscClientUpdate` with no additional gating [3](#0-2) , and `verify_consensus` is invoked either through `pallet-ismp`'s permissionless `handle_unsigned` unsigned extrinsic [4](#0-3)  or through the EVM `HandlerV2`/`ConsensusRouter`'s permissionless `handleConsensus` path documented for any caller [5](#0-4) .

This codebase has a documented pattern of exactly this bug class already being found and fixed elsewhere — e.g. the sync-committee verifier's `calculate_multi_merkle_root` panic on a short `multi_proof` was patched with an explicit length-count guard [6](#0-5) , the BEEFY verifier's empty `leaf_indices` panic was patched the same way [7](#0-6) , the GRANDPA verifier's `.expect()` on a missing relay header was converted to a typed error [8](#0-7) , and the Ethereum trie codec's empty-HP-prefix and Pharos SPV over-deep-proof panics were likewise fixed with explicit guards [9](#0-8) [10](#0-9) . The BOHR-turn-byte length check in `parse_extra` was itself added as a fix for one specific panic vector (missing turn byte) [11](#0-10) , but the surrounding per-validator-entry slicing that consumes `remaining_data[i*VALIDATOR_BYTES_LENGTH..]` was not independently bounds-checked against the actual remaining buffer length before slicing, unlike the sibling verifiers.

Reaching a genuinely out-of-bounds slice requires confirming that `data_length` (computed from `header.extra_data.len()`, vanity/seal trimmed) can be made to satisfy `data_length >= required_length` while `remaining_data.len() < validator_num * VALIDATOR_BYTES_LENGTH + ADDRESS_LENGTH` for some `i`. Since `remaining_data = &data[VALIDATOR_NUMBER_SIZE..]` and `data_length = data.len()`, and `required_length` is derived from the very same `validator_num`, the arithmetic that would decouple `data_length` from `remaining_data.len()` was not verified further within this investigation — this is the piece that would need to be confirmed with a concrete byte-level PoC (e.g., stress-testing whether the `data.len() < EXTRA_VANITY_LENGTH + EXTRA_SEAL_LENGTH` outer trim, combined with `header.timestamp`-dependent branch selection, can produce a length mismatch). I could not fully construct and verify a byte sequence proving the panic fires within this session; the reasoning above establishes a plausible root cause but is not proof-of-concept-verified end-to-end.

### Impact Explanation
If exploitable, a single relayer-submitted BSC consensus proof (either via `pallet_ismp::handle_unsigned` on Hyperbridge or `HandlerV2.handleConsensus`/`ConsensusRouter` on an EVM `EvmHost`) would panic the runtime/node processing the message — for the Substrate side this halts the parachain's block-import/transaction-validation logic (a chain-level denial of service, directly analogous to CVE-2016-3094's "crafted authentication attempt causes broker termination"); for the EVM side an uncaught revert would simply fail the transaction (lower severity there). Given the pattern of prior, materially identical bugs in sibling consensus verifiers, this class of issue is rated Medium-High if confirmed on the Substrate path.

### Likelihood Explanation
The BSC consensus proof is completely permissionless and unsigned-extrinsic-gated only by successful decoding, not by any authenticated party; anyone able to observe the wire format can attempt malformed headers. However, since the exact byte-length contradiction needed to defeat the existing `required_length` check was not conclusively demonstrated, likelihood is uncertain pending a concrete PoC.

### Recommendation
Add an explicit per-entry bounds check inside the validator-parsing loop in `parse_extra` (`modules/consensus/bsc/verifier/src/primitives.rs`), e.g. verify `remaining_data.len() >= validator_num * VALIDATOR_BYTES_LENGTH` immediately before the loop (not just the combined `required_length` check), and return `Err(anyhow!(...))` instead of allowing any slice indexing that could exceed the buffer — mirroring the guard patterns already used in `sync-committee` and `beefy` verifiers.

### Proof of Concept
Not fully constructed/verified in this session. A concrete PoC would need to craft a `CodecHeader.extra_data` byte string where `data[0]` (a small `validator_num`) and `header.timestamp` combine so that `data_length >= required_length` passes while `remaining_data.len()` is insufficient for the declared `validator_num` entries, then submit it as the `attested_header` inside a SCALE-encoded `BscClientUpdate` via `pallet_ismp::Call::handle_unsigned` with `consensus_state_id = BSC_CONSENSUS_ID`. This should be validated with an actual test/fuzz run before treating the finding as fully confirmed.
