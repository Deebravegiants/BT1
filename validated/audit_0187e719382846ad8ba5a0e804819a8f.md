### Title
Unauthenticated canceller-set reset lets any address replace the timelock canceller set - (File: contracts/governance/src/timelock/recovery.rs)

### Summary
The OpenReception bug class — "the schema validation IS the authorization decision", i.e. a handler accepts a privilege-bearing value with no policy check on who may set it — maps onto `propose_canceller_reset` in the governance contract. Unlike every other proposal path, this entrypoint performs no `require_auth` and no role check: any unprivileged address can schedule a `Recovery`-tier operation that, once its delay elapses, is executed by `execute_canceller_reset` (which itself permits `executor = None`, i.e. permissionless execution of a ready op) and replaces the entire canceller set via `access::apply_canceller_reset`. The recovery op is also marked so it cannot be cancelled through the normal `cancel` path.

### Finding Description
`propose` in `contracts/governance/src/timelock/lifecycle.rs:38` gates scheduling behind `begin_immediate(env, proposer, PROPOSER_ROLE)`, which calls `caller.require_auth()` and `access_control::ensure_role` (`timelock/mod.rs:173-177`). `propose_canceller_reset` in `recovery.rs:17-27` skips `begin_immediate` entirely — it builds the `reset_cancellers` self-operation, schedules it at the `Recovery` delay, marks it as a recovery op, and returns, with zero authentication. Because the operation is flagged via `storage::mark_recovery_op`, `cancel` reverts on it (`lifecycle.rs:141-145`). `authorize_executor` (`timelock/mod.rs:77-82`) explicitly performs no check when `executor` is `None`, so once the delay elapses anyone may call `execute_canceller_reset` (`recovery.rs:32-43`) and the attacker's chosen `new_cancellers` vec becomes the canceller set. The hash-of-arguments scheduling check is the only "authorization" — exactly the pattern in the CVE, where accepting a well-formed value substituted for checking who submitted it.

### Impact Explanation
An unprivileged attacker can permanently seize the canceller role. Any subsequent malicious or erroneous scheduled operation becomes uncancellable, since the legitimate canceller set is wiped by an op that itself cannot be cancelled. While sensitive operations still require owner/proposer privileges to schedule, the cancellation safety net — the mechanism that bounds damage from a compromised or malicious `PROPOSER_ROLE` holder — is removed by any arbitrary address, degrading governance's ability to stop a pending operation. At minimum this is a persistent, unprivileged disruption of a core governance safety function; in combination with any schedulable-but-harmful operation it converts into irreversible execution.

### Likelihood Explanation
The path is a single contract call (`propose_canceller_reset(new_cancellers, salt)`) with no authentication, no role, and no cost beyond waiting the `Recovery` delay — which is deliberately the longest tier, but the attacker only needs to schedule it once, in advance, since it is uncancellable while pending and executable by anyone afterward. Whether this is an intended "lost-key recovery" design is not documented in the file; nothing in the code signals that opening recovery to arbitrary callers was a deliberate ADR choice, unlike the explicitly documented `executor: Option` design.

### Recommendation
Gate `propose_canceller_reset` behind an appropriate check — either the governance owner (`access::owner_or_panic`) or a dedicated role via `begin_immediate`/`ensure_role`. If permissionless recovery is genuinely intended (e.g. dead-man-switch for lost canceller keys), the threat model should be documented and the impact limited — e.g. restricting `new_cancellers` to a pre-approved guardian set, or requiring the existing canceller set to be empty before an unauthenticated reset is accepted.

### Proof of Concept
1. Attacker (any address) calls `governance::propose_canceller_reset(vec![attacker_addr], salt)` — succeeds; no auth or role is checked (`recovery.rs:17-27`).
2. The op is marked via `mark_recovery_op`, so honest cancellers calling `cancel` hit `OperationNotCancellable` (`lifecycle.rs:141-145`).
3. After `TIMELOCK_RECOVERY_MIN_DELAY_LEDGERS`, anyone calls `execute_canceller_reset(None, vec![attacker_addr], salt)`; `authorize_executor` skips all checks for `None` (`timelock/mod.rs:77-82`), and `apply_canceller_reset` installs the attacker-controlled set (`recovery.rs:38-42`).
4. Legitimate cancellers can no longer cancel any operation; any future harmful scheduled op is unstoppable.

Caveat: I verified the missing-auth path structurally but could not confirm against deployment docs whether an open recovery path is an intentional documented design choice; if it is, this finding should be downgraded.
