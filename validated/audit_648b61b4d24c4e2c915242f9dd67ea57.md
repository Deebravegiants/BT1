### Title
Low-privilege authenticated users (view role) can access `pprof` heap/profile dumps that may expose private key material — ([File: core/web/router.go])

### Summary
The Chainlink node's `net/http/pprof` debug routes are mounted under the `authv2` group and only require basic session/token authentication with no minimum role check, unlike nearly every other sensitive endpoint in the router which is explicitly gated with `auth.RequiresEditRole` or `auth.RequiresAdminRole`. This lets the lowest-privilege authenticated role (`view`) pull a full heap dump of the running node process, which the project's own documentation acknowledges can expose private key material.

### Finding Description
`metricRoutes` registers the standard Go `pprof` handlers (`/debug/pprof/heap`, `/profile`, `/goroutine`, `/allocs`, etc.) and is invoked from inside the `authv2` group in `v2Routes`: [1](#0-0) [2](#0-1) [3](#0-2) 

The `authv2` group is built with `auth.Authenticate(..., auth.AuthenticateByToken, auth.AuthenticateBySession)` only — there is no `auth.RequiresEditRole` / `auth.RequiresAdminRole` wrapper on `metricRoutes(authv2)`, unlike essentially every key-management, transfer, and admin route defined immediately around it (e.g. `authv2.DELETE("/keys/eth/:keyID", auth.RequiresAdminRole(...))`).

The role hierarchy is `view < run < edit < admin`, and `RequiresRunRole`/`RequiresEditRole`/`RequiresAdminRole` explicitly reject `view`-role users: [4](#0-3) 

Since `metricRoutes` has none of these checks, a `view`-role user — the account tier meant strictly for read-only monitoring — can hit `GET /v2/debug/pprof/heap` and dump the node process's live memory. The project's own configuration documentation confirms the sensitivity of this data: [5](#0-4) 

This documents that heap dumps "may potentially expose sensitive data e.g. private key components," and notes the setting is now "Always enabled" with no way to disable it — meaning the only remaining protection is the router's access control, which here does not enforce a privileged role.

The `debugRoutes` `/v2/debug/vars` (`expvar`) endpoint has the same gap — authenticated-only, no role check: [6](#0-5) 

### Impact Explanation
This maps directly to the CVE-2018-20509 bug class: an actor with only the lowest privilege level can read an internal diagnostic interface that discloses sensitive in-memory data (address/key material), because the access-control gate was omitted for that specific debug surface while being consistently applied elsewhere in the same router. A compromised or malicious `view`-role API token (the least-trusted credential tier the node issues) can pull heap dumps that may contain private key components or other secrets resident in process memory, going beyond that user's intended read-only monitoring privileges.

### Likelihood Explanation
Any operator who provisions a `view`-role API credential for dashboards/monitoring (a common, low-friction practice) creates a credential that can also fetch `/v2/debug/pprof/heap`. Exploitation requires no special access beyond a valid `view` session/token — the same credential used for benign read-only monitoring is sufficient, so likelihood is high wherever `view` credentials exist and pprof heap dumps happen to contain sensitive key material at capture time.

### Recommendation
Wrap `metricRoutes(authv2)` (and `debugRoutes`'s `expvar` handler) with `auth.RequiresAdminRole` so only admin-role sessions/tokens can access `/v2/debug/pprof/*` and `/v2/debug/vars`, consistent with the access-control pattern used for every other sensitive endpoint in `v2Routes`.

### Proof of Concept
1. Create a `view`-role API token via the node's user management (`authv2.POST("/users")` as admin, assigning `UserRoleView`).
2. Using only that `view` token, issue `GET /v2/debug/pprof/heap?debug=1` with the `X-API-KEY`/`X-API-SECRET` headers.
3. Observe the request succeeds (only base authentication is checked in `authv2`/`metricRoutes`, no `RequiresAdminRole`/`RequiresEditRole` gate), returning a full heap profile of the node process that may contain private key components per the node's own `InsecurePPROFHeap` documentation.

// RequiresRunRole extracts the user object from the context, and asserts the user's role is at least
// 'run'
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}

// RequiresEditRole extracts the user object from the context, and asserts the user's role is at least
// 'edit'
func RequiresEditRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView || user.Role == clsessions.UserRoleRun {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
