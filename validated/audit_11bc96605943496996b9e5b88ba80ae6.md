### Title
Unchecked subtraction `assetReserve - virtualLtReserve` in `canGraduate`/`previewLtUntilGraduation` can underflow and permanently brick a curve's `buy`/`triggerGraduation` - (File: `packages/contracts/src/Bonding.sol`)

### Summary
`Bonding.canGraduate` computes the "real LT raised by the curve" as a raw, unchecked subtraction, `assetReserve - _launchTimeVirtualLtReserve(...)`, with no guard that `assetReserve >= virtualLtReserve` [1](#0-0) . The same unguarded pattern exists on the USD-trigger leg of `previewLtUntilGraduation` [2](#0-1) . `canGraduate` is invoked unconditionally at the end of every buy inside `_executeBuy` [3](#0-2)  and by the permissionless `triggerGraduation` [4](#0-3) . If `assetReserve` ever dips below the recovered virtual reserve, Solidity 0.8's checked arithmetic panics, reverting every subsequent `buy`/`triggerGraduation` call on that token — a permanent freeze of the curve and any funds routed through it (`Zap.buy`/`Zap.sell`'s graduation-trigger path), exactly analogous to the reported `unstake` underflow (`userBalance - amount_` performed without first checking `amount_ <= userBalance`).

### Finding Description
`Router._computeBuy` and `Router._computeSell` both round the output leg using floor division of `k / newReserve`, and both rounding directions favor the trader on each individual trade:

- Buy: `tokensOut = reserveToken - (k / newReserveAsset)` — flooring `k/newReserveAsset` makes `tokensOut` larger (rounds up in the trader's favor) [5](#0-4) .
- Sell: `assetOut = reserveAsset - (k / newReserveToken)` — same floor-division pattern, again rounding the payout up in the trader's favor [6](#0-5) .

`Pair.swap` only enforces a slack-permissive floor check, `(newTokenReserve + 1) * (newAssetReserve + 1) >= k`, rather than requiring the product to be held at or above the exact `k` [7](#0-6) . This `+1` slack plus the double-favorable rounding on both buy and sell legs means a sequence of small buy→sell round trips can shave real LT value out of `assetReserve` below the pool's own product invariant target on every cycle. Repeated over enough trades, `assetReserve` can be driven to a value below `_launchTimeVirtualLtReserve(tokenAddress, pairAddr)` (`Pair.k() / TOTAL_SUPPLY()`, a value that is *never* re-derived to account for this drift) [8](#0-7) .

Once that happens, `canGraduate`'s `realLtRaised = assetReserve - _launchTimeVirtualLtReserve(...)` underflows and reverts with a Panic [9](#0-8) . Because `_executeBuy` calls `canGraduate(tokenAddress)` unconditionally after every successful curve buy [10](#0-9) , this Panic bubbles up and reverts the entire buy transaction — meaning `Bonding.buy` (and therefore `Zap.buy`) can never succeed again for that token. `triggerGraduation` hits the identical unguarded subtraction via its own `canGraduate` call [11](#0-10) , so the permissionless graduation escape hatch is bricked too. Sells are unaffected (they don't call `canGraduate`), so the token is stuck permanently mid-curve: not tradable via buys and never graduatable, with whatever LT/USDC value is already parked in the pair and `FeeVault` permanently inaccessible for that token's future trade flow.

Notably, the codebase's own comments and tests show the maintainers were aware of exactly this underflow class — `test/Zap.t.sol` documents a prior "donation attack regression" where a similar subtraction in `previewLtUntilGraduation`'s **supply** leg underflowed and was patched with an explicit `if (realBalance >= reserveToken) return ltUntilThreshold;` guard [12](#0-11)  and [13](#0-12) . That fix was applied only to the supply leg of `previewLtUntilGraduation`; the **USD leg** of `previewLtUntilGraduation` (line 722) and the entire body of `canGraduate` (line 692) still perform the same subtraction with no equivalent guard.

### Impact Explanation
This is a permanent freeze of trader/creator funds for the affected token: `Bonding.buy`/`Zap.buy` revert unconditionally once the underflow condition is reached, and `triggerGraduation` (the only other path to move the token out of `Lifecycle.Curve`) reverts for the same reason. Any LT already raised into the curve pair, and any tokens still unsold on the curve, become permanently stranded — the token can never graduate to the HyperSwap LP and can never receive another buy. This satisfies the "permanent freezing of trader, creator, or LP funds" bar for a valid High-severity finding.

### Likelihood Explanation
Reaching the underflow requires an attacker to execute many small buy/sell round trips against a single token's curve, exploiting the trader-favorable rounding on both `_computeBuy` and `_computeSell` to erode `assetReserve` below the immutable `virtualLtReserve` floor. This is gas-costly but requires no special privilege — any unprivileged wallet can submit the sequence of `Zap.buy`/`Zap.sell` (or direct `Bonding.buy`/`sell` if it holds `ROUTER_ROLE`, but even restricted to Zap, a normal user can do it) transactions needed to grind the reserve down over many trades, particularly on tokens with thin liquidity/large `k`-to-trade-size ratios where the floor-division residue per trade is more significant relative to reserve size.

### Recommendation
Guard every `assetReserve - virtualLtReserve` (and equivalent) subtraction the same way the supply leg of `previewLtUntilGraduation` was already fixed:
```solidity
uint256 virtualLt = _launchTimeVirtualLtReserve(token_, pair);
uint256 realLtRaised = assetReserve > virtualLt ? assetReserve - virtualLt : 0;
```
Apply this in `canGraduate` (line 692), in the USD leg of `previewLtUntilGraduation` (line 722), and in `_prepareGraduationLiquidity`'s `ltFromPair` computation (line 1084) for defense in depth. Additionally, consider tightening `Pair.swap`'s K-invariant check (remove or shrink the `+1` slack, or round `_computeBuy`/`_computeSell` outputs down instead of up) so the reserve product cannot drift below `k` over repeated trades in the first place.

### Proof of Concept
1. Launch a token via `Zap.createToken` with a modest seed so `assetReserve` starts near the LT-mint floor.
2. Repeatedly call `Zap.buy(token, minUsdcAmount, 0, ref)` immediately followed by `Zap.sell(token, tokensReceived, 0)` in separate transactions, using the smallest permitted trade size each time.
3. Each buy→sell round trip extracts slightly more LT than it should due to the floor-rounding-in-trader's-favor in `Router._computeBuy`/`_computeSell` combined with the `+1` K-invariant slack in `Pair.swap`.
4. After enough round trips, `IPair(pair).getReserves()`'s `assetReserve` falls below `Pair.k() / Token.TOTAL_SUPPLY()` (the recovered `virtualLtReserve`).
5. The next `Zap.buy` call succeeds through `Router.buy`, but the trailing `canGraduate(tokenAddress)` check inside `Bonding._executeBuy` reverts with an arithmetic-underflow Panic, reverting the whole buy transaction.
6. From this point on, every `Zap.buy` for the token reverts, and `Bonding.triggerGraduation(tokenAddress)` also reverts via the same `canGraduate` call — the token is permanently stuck in `Lifecycle.Curve`, unable to trade further or graduate.

    /// @dev Recovers the launch-time virtual LT reserve from immutable
    ///      identities: `Pair._pool.k = tokenReserve_init * assetReserve_init
    ///      = TOTAL_SUPPLY * virtualLtReserve_init` is set ONCE in
    ///      `Pair.mint` and never modified by `Pair.swap` (swap only
    ///      mutates `tokenReserve` / `assetReserve` and asserts K-floor).
    ///      So `Pair.k() / Token.TOTAL_SUPPLY()` returns the exact
    ///      `virtualLtReserve` that was passed to `addInitialLiquidity` at
    ///      launch — for any pair, in any phase, with no storage of our own.
    ///
    ///      Going through this derivation rather than a stored mirror
    ///      eliminates an admin-writable economic-state slot and makes the
    ///      donation-immunity property a pure consequence of the pair's
    ///      already-immutable accounting. The `TOTAL_SUPPLY`-equality check
    ///      in `setTokenImplementation` keeps the divisor consistent across
    ///      impl rotations, so tokens launched under different
    ///      `tokenImplementation` versions still derive the same way.
    function _launchTimeVirtualLtReserve(
        address token_,
        address pair_
    ) internal view returns (uint256) {
        return IPair(pair_).k() / Token(token_).TOTAL_SUPPLY();
    }

    function _computeBuy(
        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 amountInUsed, uint256 tokensOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        amountInUsed = amountIn;

        uint256 newReserveAsset = reserveAsset + amountInUsed;
        tokensOut = reserveToken - (k / newReserveAsset);

        uint256 realBalance = pair.tokenBalance();
        if (tokensOut > realBalance) {
            tokensOut = realBalance;
            uint256 cappedReserveToken = reserveToken - tokensOut;
            if (cappedReserveToken == 0) revert OverflowCapDegenerate();
            uint256 cappedReserveAsset = (k + cappedReserveToken - 1) / cappedReserveToken;
            amountInUsed = cappedReserveAsset - reserveAsset;
        }
    }

    function _stageDonationAttack(
        address tokenAddr
    ) internal returns (uint256 drainLtSpent, uint256 donatedTokens) {
        address pairAddr = bonding.getTokenInfo(tokenAddr).pair;

        // any `VIRTUAL_LIQUIDITY_USD`. Constant-product math gives
        // `tokensOut = TOTAL_SUPPLY × ltIn / (virtual + ltIn)`, which crosses
        // 250M (= ¼ of TOTAL_SUPPLY) when `ltIn = virtual / 3`. Spending the
        // full opening virtual reserve lands `tokensOut = 500M` — plenty of
        // headroom to push `realBalance > reserveToken` after the donation.
        drainLtSpent = _initialVirtualLt();
        lt.mintDirect(drainer, drainLtSpent);
        if (!bonding.isRouter(drainer)) bonding.addRouter(drainer);
        vm.startPrank(drainer);
        lt.approve(address(curveRouter), drainLtSpent);
        bonding.buy(drainLtSpent, tokenAddr, 0, drainer);
        vm.stopPrank();
        donatedTokens = Token(tokenAddr).balanceOf(drainer);
        vm.prank(drainer);
        Token(tokenAddr).transfer(pairAddr, donatedTokens);
    }
