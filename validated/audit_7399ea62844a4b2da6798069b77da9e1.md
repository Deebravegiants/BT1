### Title
Reentrancy via unsafe token callback in `withdraw` (transfer-before-effects) - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron deployment of the IntentGateway (`evm/tron/contracts/apps/IntentGatewayV2.sol`) contains the exact bug class described in the report: its `withdraw` function performs the external token transfer via a raw low-level `.call` before decrementing the escrow accounting variable, violating Checks-Effects-Interactions, and the contract has no reentrancy guard anywhere (`fillOrder`, `placeOrder`, `withdraw`).

### Finding Description
`withdraw` (called from `onAccept` for `RedeemEscrow`/`RefundEscrow` requests, and from `onGetResponse` after a cross-chain cancellation) sets `_filled[body.commitment] = beneficiary;` up front, but then for each escrowed token it:
1. checks `_orders[body.commitment][token] == 0`,
2. sends the token via `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))`,
3. only afterward does `_orders[body.commitment][token] -= amount;` [1](#0-0) 

Compare this with the fixed, canonical EVM implementation in `IntentsBase._withdraw` (`evm/src/apps/intentsv2/IntentsBase.sol`), which decrements `_orders[body.commitment][token]` *before* calling `safeTransfer`/`_sendValue` — the correct CEI ordering: [2](#0-1) 

Because the Tron `withdraw` uses a raw `.call` to an arbitrary ERC20-style token address rather than `SafeERC20.safeTransfer`, and updates the `_orders` mapping only after the transfer completes, a token contract that can execute code during the transfer (e.g. a callback/hook-style token, or any token whose `transfer` implementation invokes recipient/attacker-controlled code — a broadly accepted pattern in ERC20-derivative "malicious token" analyses) can re-enter `withdraw` for the same `body.commitment`/`token` pair while `_orders[body.commitment][token]` still reflects the pre-transfer (undecremented) balance, passing the `== 0` check again and receiving a second (or repeated) transfer for escrow that has already been paid out once. The `_filled` guard does not prevent this because `withdraw` does not check `_filled` before iterating tokens, and re-entrant calls into `withdraw` reach the same escrow-token loop that has not yet had its state updated.

The `evm/src` version of `IntentGatewayV2`/`IntentsBase`/`IntrinsicIntents`/`ExtrinsicIntents` was hardened for exactly this class of bug (see `IntrinsicIntentsReentrancyTest.sol`, which documents and tests the CEI fix for `_fillSameChain`/`_fillCrossChain`, and `IntentGatewayV2.sol` even inherits `ReentrancyGuardTransient`) [3](#0-2) [4](#0-3) , but the Tron deployment at `evm/tron/contracts/apps/IntentGatewayV2.sol` is a separately maintained copy that never received this treatment: it has no `ReentrancyGuard`/`ReentrancyGuardTransient` inheritance and never adopted the fixed CEI ordering in `withdraw`.

### Impact Explanation
`withdraw` is reached from an unprivileged, permissionless flow: any relayer can deliver a `RedeemEscrow`/`RefundEscrow` cross-chain message through `onAccept` (host-gated only on `msg.sender == host`, not on caller identity beyond that), and any user can place an order with an arbitrary ERC20 `input` token address via `placeOrder`, which is itself unprivileged and open to any caller. If the user-supplied input token is a malicious/callback token, the beneficiary side of a `withdraw` transfer can re-enter and drain escrowed input tokens beyond what was legitimately owed, directly stealing solver/protocol funds held by the gateway. This is concrete theft of escrowed funds, meeting the High severity bar.

### Likelihood Explanation
Likelihood is credible but conditioned on the input/output token being attacker-controlled or a token with recipient-callback semantics; `placeOrder` places no restriction on which ERC20 contract can be used as `order.inputs[i].token`, so an attacker can freely choose a malicious token for their own order and trigger the settlement path through the normal cross-chain fill/withdraw flow.

### Recommendation
Update `withdraw` in `evm/tron/contracts/apps/IntentGatewayV2.sol` to follow the same CEI ordering already used in `evm/src/apps/intentsv2/IntentsBase.sol`: decrement `_orders[body.commitment][token]` before performing the external token transfer, replace the raw `.call` transfer pattern with `SafeERC20.safeTransfer`, and add a reentrancy guard (`ReentrancyGuard`/`ReentrancyGuardTransient`) around `withdraw`, `fillOrder`, and `placeOrder`, mirroring the fix already applied to the primary EVM `IntentGatewayV2` implementation.

### Proof of Concept
1. Attacker deploys a malicious ERC20 token `M` whose `transfer` function, when called, re-enters the caller (the IntentGateway) by invoking a callback prior to returning.
2. Attacker calls `placeOrder` on the Tron `IntentGatewayV2`, escrowing token `M` as `order.inputs[0]`, with `order.output.beneficiary` set to the attacker's own contract.
3. A relayer/solver fills the order and dispatches settlement; eventually a `RedeemEscrow` request reaches `onAccept` → `withdraw(body, isRefund=false)` on the source chain.
4. Inside `withdraw`'s loop, `token.call(transfer(beneficiary, amount))` for token `M` triggers `M`'s callback in the attacker's beneficiary contract before `_orders[body.commitment][token] -= amount;` executes.
5. The callback re-enters `withdraw` (or a path that reaches it) with the same `commitment`; `_orders[body.commitment][token]` is unchanged (still non-zero), so the check passes again and a second transfer of `amount` of token `M` is issued to the beneficiary, doubling the payout for a single escrow deposit.         address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");

                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();

                ++i;
            }
        }
