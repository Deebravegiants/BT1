### Title
Inconsistent order-of-operations in `calc_take_pnl` fee-fraction/decimal-restoration math causes pool-reserve accounting to diverge from the internal PnL invariant baseline - ([File: program/src/processor.rs])

### Summary
`Calculator::calc_take_pnl` computes the "take-profit" fraction of a pool's price-divergence gain twice, using two different orders of multiplication/division and decimal restoration. One result (`delta_x`/`delta_y`) is used to update the internal invariant baseline (`target_orders.calc_pnl_x`/`calc_pnl_y`), while a second, independently-rounded result (`pc_pnl_amount`/`coin_pnl_amount`) is what is actually credited to `need_take_pnl_pc`/`need_take_pnl_coin` and deducted from `total_pc_without_take_pnl`/`total_coin_without_take_pnl`. This is the same class of bug as the referenced Panoptic finding: `(A*N/D)` restored via decimals is not guaranteed to equal `restore_decimal(A)*N/D` due to integer truncation, so the two supposedly-equal quantities can differ.

### Finding Description
In `calc_take_pnl` [1](#0-0) , the "sys-decimal" difference `diff_x`/`diff_y` (current invariant-implied reserves minus post-price-move reserves) is scaled by the PnL fraction to produce `delta_x`/`delta_y`:

```
delta_x = diff_x * pnl_numerator / pnl_denominator   (still in sys_decimal units)
```

Separately, the same `diff_x`/`diff_y` is first restored to native token decimals and *then* scaled by the same PnL fraction to compute the amount actually removed from the pool and credited to the PnL owner [2](#0-1) :

```
diff_pc_pnl_amount = restore_decimal(diff_x, pc_decimals, sys_decimal_value)
pc_pnl_amount = diff_pc_pnl_amount * pnl_numerator / pnl_denominator
```

Mathematically, `restore_decimal(diff_x * N / D)` (the "correct" value consistent with `delta_x`) is not guaranteed to equal `restore_decimal(diff_x) * N / D` (what `pc_pnl_amount` actually computes), because each intermediate division floors independently. This is structurally identical to the root cause described in the referenced report: splitting `A*N/D` restoration into two separately-rounded multiply/divide steps instead of doing it consistently in one order.

`pc_pnl_amount`/`coin_pnl_amount` are the values that are actually:
- added to `amm.state_data.need_take_pnl_pc` / `need_take_pnl_coin` [3](#0-2) 
- subtracted from `total_pc_without_take_pnl` / `total_coin_without_take_pnl` (the LP-owned pool reserves) [4](#0-3) 

while `delta_x`/`delta_y` (the differently-rounded sibling value) is what is later subtracted from `target_orders.calc_pnl_x`/`calc_pnl_y`, the internal baseline used to compute future PnL deltas, in `process_withdrawpnl` [5](#0-4)  and in the deposit path [6](#0-5) .

Because these two quantities are computed via different rounding orders but are treated as if they represent the same underlying value, the amount actually pulled out of the pool's LP reserves (`pc_pnl_amount`/`coin_pnl_amount`) can be systematically larger (by up to a few native-decimal units per call, magnified for low-decimal or high-value tokens) than what the invariant baseline (`calc_pnl_x`/`calc_pnl_y`) is decremented by. `calc_take_pnl` is invoked on the normal, unprivileged swap path (`process_swap_base_in`/`process_swap_base_out` and their v2 variants) as well as on deposit and withdraw, so this discrepancy accumulates over ordinary trading activity driven entirely by unprivileged swappers/LPs — no privileged signer is required to trigger the divergence.

### Impact Explanation
Each call to `calc_take_pnl` can extract a rounding-biased amount from `total_pc_without_take_pnl`/`total_coin_without_take_pnl` (LP reserves) into `need_take_pnl_pc`/`need_take_pnl_coin` (eventually withdrawn via `process_withdrawpnl`) that does not precisely correspond to the amount the internal invariant tracker (`calc_pnl_x`/`calc_pnl_y`) believes was removed. Since this function runs on every swap, the small per-call bias compounds over the pool's lifetime, degrading the accounting invariant between "reserves actually available to LPs" and the internal PnL-tracking state, and shifting value away from LPs on every trade at a rate greater than the intended `pnl_numerator/pnl_denominator` fee share. For low-decimal, high-value token pairs the effect is proportionally larger per unit of drift, as in the referenced report. This does not immediately grant unbounded fund drainage in a single transaction, hence Medium severity is appropriate.

### Likelihood Explanation
`calc_take_pnl` is reached unconditionally on the standard swap paths (`process_swap_base_in`, `process_swap_base_in_v2`, `process_swap_base_out`, `process_swap_base_out_v2`) as well as deposit, all of which are callable by any unprivileged user with attacker-chosen swap amounts/direction. No special accounts, signer privileges, or non-default configuration are required — ordinary trading activity is sufficient to repeatedly trigger the divergent rounding paths, matching the "reachable from a single submitted transaction with attacker-chosen accounts and data" bar, though a large volume of trades is needed to accumulate a materially significant drift, similar to the original report's caveat.

### Recommendation
Compute `pc_pnl_amount`/`coin_pnl_amount` by restoring `delta_x`/`delta_y` directly to native decimals (i.e., `restore_decimal(delta_x, pc_decimals, sys_decimal_value)`) instead of independently restoring `diff_x`/`diff_y` and re-applying the PnL fraction. This ensures the amount actually deducted from pool reserves and credited to `need_take_pnl_*` is derived from the exact same rounded value (`delta_x`/`delta_y`) that is subtracted from the invariant baseline (`calc_pnl_x`/`calc_pnl_y`), eliminating the divergence between the two accounting paths.

### Proof of Concept
Given `sys_decimal_value = 10^6`, `pc_decimals = 9` (i.e., `restore_decimal` multiplies by `10^3`), and `pnl_numerator/pnl_denominator = 12/100`:

- Let `diff_x = 100003` (sys-decimal units).
- Panoptic-analog path A (used for `delta_x` / invariant baseline):
  `delta_x = floor(100003 * 12 / 100) = floor(12000.36) = 12000` (sys-decimal units)
  `restore_decimal(delta_x) = 12000 * 1000 = 12,000,000` (native units) — this is the value consistent with the invariant baseline decrement.
- Path B (actually executed for `pc_pnl_amount`):
  `diff_pc_pnl_amount = restore_decimal(diff_x) = 100003 * 1000 = 100,003,000`
  `pc_pnl_amount = floor(100,003,000 * 12 / 100) = floor(12,000,360) = 12,000,360`

`pc_pnl_amount (12,000,360)` exceeds the invariant-consistent value `12,000,000` by 360 native units, even though both are meant to represent "12% of the same price-divergence profit." This 360-unit surplus is what is actually deducted from LP reserves (`total_pc_without_take_pnl`) and credited to `need_take_pnl_pc`, while only 12,000 (sys-decimal units, restoring to 12,000,000 native) is reflected in the reduction of the `calc_pnl_x` baseline — reproducing the exact rounding-order mismatch described in the referenced Panoptic report, applied to `calc_take_pnl` in `program/src/processor.rs`.
