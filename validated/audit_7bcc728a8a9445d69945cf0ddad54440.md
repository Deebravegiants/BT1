### Title
Webhook Tenant Identity Not Bound to HMAC Signature — Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes and verifies its HMAC over the raw request body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values used to route and process the webhook are taken from unauthenticated HTTP headers that are never included in the signed payload. This breaks the equality *shop verified by HMAC == shop used to attribute/process the webhook*, allowing a party who can produce one validly-signed webhook body (e.g. a merchant using the app in their own store, who legitimately receives real Shopify webhooks with valid HMACs computed from the app's shared `client_secret`) to replay that same signed body while swapping the `shopify-shop-domain` (and/or `shopify-topic`) header to impersonate a different tenant.

### Finding Description
`Request#hmac` and `Request#to_signable_string` are defined as: [1](#0-0) [2](#0-1) 

Only `@raw_body` is fed into the signable string that `Utils::HmacValidator.validate` checks: [3](#0-2) 

`Registry.process` trusts `request.shop` (and `request.topic`, `request.webhook_id`) straight from headers once the HMAC on the body passes, and hands them to the app's handler as the tenant identity for the event: [4](#0-3) 

`shop` is read directly from the `shopify-shop-domain` / `x-shopify-shop-domain` header with no cryptographic binding to it: [5](#0-4) 

Because `client_secret` (`api_secret_key`) is shared across every shop that installs the app, any tenant who has installed the app can trigger a real, validly-HMAC'd webhook body for an action in their *own* store, capture that `(body, hmac)` pair, and replay it to the app's webhook endpoint with the `shopify-shop-domain` header rewritten to a victim shop's domain. The signature still validates (it only checks the body bytes) but the app attributes the event, and its side effects (e.g. order/customer record creation, GDPR/compliance handling, data sync) to the wrong tenant.

This is the same bug class as the external report: a value used downstream (`totalClaimedShares` valuation / here, `shop` tenant attribution) is not run through the binding check (`price` multiplication / here, the HMAC digest), so the check that "should" cover the acted-upon value silently passes it through unauthenticated.

### Impact Explanation
This breaks the binding `verified_signature_owner == shop_attributed_to_event`, letting one tenant of a multi-tenant app forge webhook events attributed to another tenant — a cross-tenant integrity/confidentiality violation for any host app that trusts `WebhookMetadata#shop` from this gem as an authenticated tenant identifier, which is exactly how the gem's own documentation and `webhooks/request.rb`/`registry.rb` present it (webhook is "valid" once `HmacValidator.validate` passes, and `shop` is handed to the handler as trustworthy metadata).

### Likelihood Explanation
Any shop that has legitimately installed the app already possesses the ability to generate real, validly-signed webhook deliveries for its own shop (Shopify sends these automatically on ordinary store actions such as order/customer/app-uninstall events). Replaying such a body with a modified `shopify-shop-domain` header requires only basic HTTP tooling — no access to `api_secret_key`, no privileged account beyond a normal app install, and no interception of another tenant's traffic.

### Recommendation
Include the tenant-identifying and routing fields (`shop`, `topic`, `webhook_id`, `api_version`) in the value that is HMAC-verified, or otherwise cryptographically bind them to the signed body (e.g., verify the parsed body's own shop/tenant field against the header before use, or require host apps to cross-check `request.shop` against a shop derived from an already-authenticated session/lookup) rather than trusting the header value once only the body's HMAC checks out.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`, obtaining valid webhook deliveries signed with the app's shared `api_secret_key`.
2. Attacker triggers a store event (e.g., creates an order) to receive a real webhook POST with headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid-hmac-of-body>`, and body `B`.
3. Attacker resends the identical body `B` and `x-shopify-hmac-sha256` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` passes because it only checks `@raw_body`; `Registry.process` in `lib/shopify_api/webhooks/registry.rb:188-200` dispatches the handler with `shop: "victim.myshopify.com"`, causing the app to process attacker-controlled data under the victim tenant's identity.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
