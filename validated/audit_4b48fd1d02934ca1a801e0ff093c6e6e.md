### Title
Webhook `shop` field is not covered by the HMAC signature, allowing shop-identity spoofing in processed webhooks - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw request body, then trusts the `shop` value taken from the `X-Shopify-Shop-Domain` HTTP header — a field that is never included in the signed bytes. This breaks the equality that should hold: `shop bound by HMAC == shop used to identify the tenant in WebhookMetadata`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`ShopifyAPI::Utils::HmacValidator.validate` computes the HMAC exclusively over `to_signable_string` (i.e., only the body) and compares it against the `hmac` header: [2](#0-1) 

The `shop` value, however, is read straight from the (unsigned) `x-shopify-shop-domain` header: [3](#0-2) 

`Registry.process` validates the HMAC, then immediately forwards `request.shop` — the header value that was never part of the signed bytes — into the handler as the tenant identity: [4](#0-3) 

The app's `client_secret`/`api_secret_key` used to sign webhooks is shared across every shop that installs the app; it is not per-tenant. Consequently, any unprivileged user who installs the app on their own store (an ordinary, non-privileged action) receives genuinely-signed webhooks whose body+HMAC pair is valid for the shared secret. Because the header is excluded from the signed bytes, that same valid `(raw_body, hmac)` pair can be replayed to the app's webhook endpoint with the `x-shopify-shop-domain` header rewritten to any victim shop domain, and `HmacValidator.validate` will still return `true`. The library then hands the forged `shop` on to the host application via `WebhookMetadata`, breaking the binding: `shop verified by HMAC == shop used for tenant identification`.

### Impact Explanation
This is a scope/binding-check bypass that lets an attacker who legitimately controls one tenant (their own shop) present forged, but HMAC-valid, webhook traffic as belonging to a different, victim tenant. Any host application that keys session lookups, per-shop state updates, or authorization decisions off `WebhookMetadata#shop` (exactly as the gem's own documented workflow encourages) can be made to process attacker-controlled webhook bodies under a victim shop's identity — a cross-tenant access primitive rooted entirely in this gem's failure to bind `shop` into the HMAC-verified data.

### Likelihood Explanation
High. Registering the app on one's own store to receive genuinely signed webhooks requires no privileges beyond normal app installation, which any internet user can perform (e.g., via a free development store). Rewriting one HTTP header before forwarding the exact same body/HMAC pair to the target app's public webhook callback URL is trivial and requires no knowledge of `api_secret_key`.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the data that is actually verified, e.g., include the shop header value in `to_signable_string`'s signed digest computation only if Shopify's webhook payload signing scheme supports it, or — since Shopify does not sign these headers — require the host application to independently confirm the `shop` header value against a shop that is already known/authorized for this app (e.g., cross-check against stored sessions) before trusting it in `Registry.process`, and document clearly that `request.shop` is unauthenticated and must not be used as the sole tenant key.

### Proof of Concept
1. Install the vulnerable app on attacker-owned shop `attacker.myshopify.com`; Shopify sends a legitimately signed webhook: body `B`, header `x-shopify-hmac-sha256: H`, `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker captures `(B, H)` and replays a POST to the app's webhook endpoint with headers `x-shopify-hmac-sha256: H`, `x-shopify-shop-domain: victim.myshopify.com`, and the same raw body `B`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `request.to_signable_string` (== `B`) and matches `H` — validation succeeds. [5](#0-4) 
4. The handler receives `WebhookMetadata.new(... shop: "victim.myshopify.com", body: parsed B ...)`, causing the host app to act on attacker-controlled data under the victim's shop identity. [6](#0-5)
