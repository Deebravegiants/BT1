### Title
Same-chain intent fills release less escrowed input than a solver's proportional share, potentially zero, with no minimum-receive protection - ([File: evm/src/apps/intentsv2/IntrinsicIntents.sol])

### Summary
`_fillSameChain` in `IntrinsicIntents.sol` computes the input escrow released to a solver for a partial fill using floor-division proportional math with no floor or minimum-output guard, mirroring the ShortCollateral pattern where a caller who provides real value (debt repayment / output tokens) can be paid out less than expected — down to zero — because the payout is silently clamped/truncated instead of reverting when it falls short of what the caller implicitly expected.

### Finding Description
In `_fillSameChain`, for every partial fill that does not complete the order (`amountFilled != totalRequired`), the escrowed input released to the filler is: [1](#0-0) 

```solidity
uint256 escrowedAmount;
if (amountFilled == totalRequired) {
    escrowedAmount = _orders[commitment][address(uint160(uint256(order.inputs[i].token)))];
} else {
    escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired;
}
```

Only the filler who *completes* the order (`amountFilled == totalRequired`) receives the exact remaining escrow balance (including any accumulated rounding dust). Every other filler — anyone who submits a partial fill before the order is fully satisfied — receives `(order.inputs[i].amount * fillAmount) / totalRequired`, a plain integer division that **truncates toward zero**. There is no `minInputAmount`/`minEscrowAmount` parameter in `FillOptions` (confirmed by inspecting the fill entry point and options struct) that would let the filler specify the minimum input-token amount they are willing to accept in exchange for the output tokens they transfer to the beneficiary at `evm/src/apps/intentsv2/IntrinsicIntents.sol:99-106`.

The transfer to the beneficiary (`beneficiaryTotal`, i.e., the real value the filler gives up) always happens unconditionally before the escrow-release amount is computed, and the function never reverts or checks the release amount against any filler-supplied floor — it simply pays out whatever the truncated proportional math produces, even if that is `0`. This is structurally identical to the ShortCollateral `liquidate()` bug: the caller provides genuine value expecting a "reasonable" return, but the return is computed as a proportional/remaining-balance calculation that is silently clamped without a revert-on-shortfall guard, and in extreme cases yields nothing.

Concretely: if `order.inputs[i].amount` is small relative to `order.output.assets[i].amount` (`totalRequired`), a filler that submits a `fillAmount` less than `totalRequired / order.inputs[i].amount` gets `escrowedAmount == 0` — they transfer real output tokens to the beneficiary and receive zero input tokens in return. Because `order.inputs`/`order.output.assets` ratios are set entirely by the order creator (not the filler), a maliciously or carelessly constructed order (e.g., extreme input:output ratio) can induce this zero-payout outcome for any filler who is not the one that finally completes the order.

### Impact Explanation
This is a fund-loss vector for intent fillers/solvers: a filler transfers real output-token value (`beneficiaryTotal`) to the order's beneficiary but can receive less escrowed input than their proportional share warrants, including exactly zero in the worst case, with the only recourse being to not participate at all (impossible to know in advance without independently replicating the on-chain division). Unlike an AMM slippage parameter, there is no on-chain mechanism (`minInputAmount`) for the filler to enforce a floor and have the transaction revert instead of completing on unfavorable terms. This directly parallels the referenced Polynomial finding: value is extracted from an unprivileged, permissionless actor (a filler/solver — analogous to a liquidator) due to an unconditional truncate-and-pay pattern instead of a revert-below-minimum guard.

### Likelihood Explanation
Any of the same-chain intent order's `inputs`/`output.assets` amount ratios are attacker-controlled by the order creator (the `user` placing the order), and any third party can call `fillOrder` permissionlessly. An adversarial or even accidentally lopsided order (very small `inputs[i].amount` relative to `output.assets[i].amount`) combined with any solver submitting a non-completing partial fill will trigger the truncation. Because solvers commonly submit fills sized by their own liquidity/balance rather than by pre-computing the exact truncation boundary of `(inputs[i].amount * fillAmount) / totalRequired`, an unlucky or targeted partial fill easily lands in the zero-payout region, making this a realistically reachable condition rather than a purely theoretical one.

### Recommendation
Add a `minInputAmount` (or per-asset minimum escrow-release) field to `FillOptions`, and after computing `escrowedAmount` for each output asset in `_fillSameChain`, revert (e.g., `InsufficientEscrowReturned`) if the computed amount is below the filler-specified minimum. This mirrors the report's recommended mitigation of adding a `minCollateralAmount` to `liquidate()` — giving the permissionless caller an explicit, enforceable floor instead of silently accepting a proportionally (or fully) truncated payout.

### Proof of Concept
Conceptual Foundry-style walkthrough, following the same pattern as the existing test suite in `evm/tests/foundry/IntentGatewayV2SameChainTest.sol`:

1. User places an order with `inputs[0].amount = 1` (e.g., 1 wei of a high-value token) and `output.assets[0].amount = 1e18` (e.g., 1 unit of a low-value token), i.e., an extreme input:output ratio.
2. `solver` calls `fillOrder` with `options.outputs[0].amount = 5e17` (a 50% partial fill), transferring `5e17` of the output token to the beneficiary.
3. Inside `_fillSameChain`, since `amountFilled (5e17) != totalRequired (1e18)`:
   `escrowedAmount = (1 * 5e17) / 1e18 = 0` (integer truncation).
4. `solver` receives `0` escrowed input tokens despite transferring `5e17` of real output-token value to the beneficiary — the exact "liquidator gets nothing" failure mode from the referenced report, with no `minInputAmount` check available to make the call revert instead. [2](#0-1)
