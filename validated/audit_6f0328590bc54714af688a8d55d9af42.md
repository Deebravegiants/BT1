### Title
Intents escrow release/sweep on Tron ignores TRC20 boolean return value, permanently freezing escrowed funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2.withdraw()` and the `SweepDust` branch of `onAccept()` release escrowed ERC20/TRC20 tokens using a raw low-level `.call()` with the `transfer` selector, checking only that the call did not revert (`success`), without decoding and validating the ERC20 boolean return value the way OpenZeppelin's `safeTransfer` does. This is the same bug class as the reported `Vault.transfer(...)` issue, but strictly worse: it doesn't even check the boolean return value that plain `transfer()` would have enforced via `require`.

### Finding Description
In `withdraw()`:
```solidity
} else {
    (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
    if (!success) revert TransferFailed();
}

_orders[body.commitment][token] -= amount;
``` [1](#0-0) 

and the fee redemption right after:
```solidity
(bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
if (!success) revert TransferFailed();
delete _orders[body.commitment][TRANSACTION_FEES];
``` [2](#0-1) 

and the `SweepDust` handler in `onAccept`:
```solidity
} else {
    (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, req.beneficiary, amount));
    if (!success) revert TransferFailed();
}
``` [3](#0-2) 

`success` from a low-level `.call` only reflects whether the callee reverted, not the actual return payload. Any ERC20/TRC20 implementation that returns `false` on failure instead of reverting (a well-known non-standard pattern, especially common among tokens deployed on Tron) will make `success == true` even though no tokens moved. Since the code never decodes/checks the returned `bool`, this silent-failure path is treated as a successful transfer: the escrow accounting (`_orders[commitment][token] -= amount`, or `delete _orders[commitment][TRANSACTION_FEES]`) is unconditionally decremented/deleted as if the beneficiary was paid.

By contrast, `IntentsBase.sol` (the corresponding EVM, non-Tron implementation) correctly uses `IERC20(token).safeTransfer(beneficiary, amount)` [4](#0-3) , which decodes and requires the boolean return to be true. The Tron variant of `IntentGatewayV2.sol` deliberately swapped this for a raw `.call()` without return-value verification, reintroducing exactly the unsafe-transfer risk the report describes.

### Impact Explanation
Once the escrow decrement/delete executes despite the underlying transfer silently failing, the tokens remain locked in the `IntentGatewayV2` contract but the internal accounting (`_orders[commitment][token]`) no longer reflects them as owed to anyone. The beneficiary (solver on `RedeemEscrow`, user on `RefundEscrow`, or dust-sweep recipient) never receives their funds, and there is no other code path to re-claim that specific escrow slot once it is decremented/deleted. This results in a permanent freezing/loss of funds for legitimate order fillers or refund recipients — the exact category of impact called out in scope (permanent freezing of funds in intents escrow).

### Likelihood Explanation
This is triggered by ordinary correct usage of the intents flow whenever the input/output/fee token used in an order is a TRC20/ERC20 token whose `transfer` implementation returns `false` on failure rather than reverting — a documented non-standard behavior common on Tron token deployments, which is presumably why this contract targets Tron in the first place (`evm/tron/...`). No malicious admin, governance, or privileged actor is required; a normal relayer delivering a `RedeemEscrow`/`RefundEscrow`/`SweepDust` message against such a token is sufficient to hit the bug once that token's transfer legitimately fails (e.g., paused token, blacklisted beneficiary, insufficient contract balance from a partial-fill accounting edge case).

### Recommendation
Replace the raw `.call` + `success`-only check with OpenZeppelin's `SafeERC20.safeTransfer`, which decodes the return data and reverts if the token indicates failure (or has no return data mismatch handling), consistent with the pattern already used in `IntentsBase.sol`:
```diff
- (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
- if (!success) revert TransferFailed();
+ IERC20(token).safeTransfer(beneficiary, amount);
```
Apply the same fix to the fee-token transfer in `withdraw()` and to the `SweepDust` branch in `onAccept()`.

### Proof of Concept
1. An order escrows a TRC20 token `T` whose `transfer` function returns `false` (instead of reverting) when the transfer cannot be completed (e.g., recipient blacklisted, or contract enters a paused state that gates transfers via a return-false code path).
2. A relayer delivers a `RedeemEscrow` (or `RefundEscrow`) message; `onAccept` → `withdraw(body, isRefund)` is invoked [5](#0-4) .
3. Inside `withdraw`, `token.call(...)` succeeds (no revert) but returns `abi.encode(false)`; `success` is `true`, so `TransferFailed` is never raised [6](#0-5) .
4. `_orders[body.commitment][token] -= amount;` executes, permanently zeroing out the escrow record even though the beneficiary's token balance never increased and the tokens remain stuck in the `IntentGatewayV2` contract with no remaining accounting entry to redeem them.
