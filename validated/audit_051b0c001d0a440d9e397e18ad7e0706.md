### Title
Webhook `shop`, `topic`, and `webhook_id` fields are not covered by the HMAC signature, enabling cross-tenant impersonation of webhook data - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` reads the `shop`, `topic`, `webhook_id`, and `api_version` values from unauthenticated HTTP headers, while the HMAC signature that `ShopifyAPI::Webhooks::Registry.process` validates only covers the raw request body. Any caller who possesses a valid `(raw_body, hmac-sha256)` pair — which is trivially obtainable since the app's `client_secret` is the same for every merchant that installs the app — can attach that valid body/HMAC pair to a forged `shopify-shop-domain` (and/or `shopify-topic`/`shopify-webhook-id`) header and the gem will accept it as a legitimate webhook for the attacker-chosen shop.

### Finding Description
The identity binding that should hold is:

```
shop header value used by the app  ==  shop actually covered by the HMAC signature
```

In `ShopifyAPI::Webhooks::Request`:
```ruby
def shop
  T.cast(shopify_header("shop-domain"), String)
end
...
def to_signable_string
  @raw_body
end
``` [1](#0-0) [2](#0-1) 

`to_signable_string` — the value that `Utils::HmacValidator` signs and compares against the `hmac-sha256` header — returns only `@raw_body`. It does not include `shop`, `topic`, or `webhook_id`. `Utils::HmacValidator.validate` computes `OpenSSL::HMAC.hexdigest` over `to_signable_string` using the app's `client_secret` and compares it via `OpenSSL.secure_compare` to the `hmac` header value: [3](#0-2) 

`Registry.process` then trusts the unauthenticated header-derived `shop`/`topic`/`webhook_id` fields once the body HMAC passes:
```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
``` [4](#0-3) 

Because the app's `client_secret` is shared across every shop that has installed the app, an attacker who owns/controls any shop that has the app installed can legitimately receive a real webhook delivery for their own shop, extract the valid `(raw_body, hmac-sha256)` pair, and then POST that same body/HMAC to the host application's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header value (e.g. a victim shop's domain) and/or a different `shopify-topic`/`shopify-webhook-id`. The gem's HMAC check passes (the body is unchanged and the secret is the same), and `WebhookMetadata.shop`/`topic`/`webhook_id` will reflect the attacker's forged values, which downstream `WebhookHandler` implementations use to decide which tenant's data to update.

This mirrors the report's bug class precisely: a field ("shop"/"topic"/"webhook_id") is acted upon by the application but is not covered by the cryptographic binding ("HMAC") that is supposed to authenticate the whole message.

### Impact Explanation
This allows cross-tenant confusion: data intended for/originating from one merchant can be replayed and attributed to a different merchant in the host application, since the `shop` field used to route/store webhook data is not authenticated. This satisfies the "Critical - cross-tenant access" impact category, since a merchant-side attacker (an "unprivileged internet user" relative to other tenants, requiring only their own legitimate app installation, no leaked secrets) can cause the host app to process/store webhook payloads under another tenant's identity.

### Likelihood Explanation
Likelihood is realistic: exploitation requires only (1) installing the app on an attacker-controlled shop to receive one legitimate webhook delivery with a valid `raw_body`/`hmac-sha256` pair, and (2) sending an HTTP POST to the app's public webhook receiving endpoint with a forged `shopify-shop-domain` header. No access to the `client_secret`, access tokens, or any privileged credentials is required — headers are attacker-controlled HTTP request metadata.

### Recommendation
Include the trust-sensitive headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signed payload used for HMAC verification, or otherwise independently authenticate/bind the shop identity (e.g., verify shop is registered/known and cross-check against session data) before trusting `request.shop` in `WebhookMetadata`. At minimum, document that these headers are unauthenticated and must not be trusted for tenant attribution without additional verification.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers any webhook-eligible event, capturing the delivered request's `raw_body` and `shopify-hmac-sha256` header (both valid because the app's shared `client_secret` signs them).
2. Attacker sends a POST request to the host application's webhook endpoint with:
   - Body: the captured `raw_body` (unchanged)
   - Header `shopify-hmac-sha256`: the captured, valid HMAC
   - Header `shopify-shop-domain`: `victim-shop.myshopify.com` (forged)
   - Header `shopify-topic`: same or different registered topic
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `to_signable_string` (`@raw_body`), per [2](#0-1) .
4. `handler.handle` is invoked with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", ...)`, per [5](#0-4) , causing the host application to process the attacker's data under the victim's shop identity.
