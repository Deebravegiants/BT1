### Title
Webhook `shop-domain` (and other headers) are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, so `HmacValidator.validate` proves nothing about the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers. `Registry.process` nonetheless trusts `request.shop` as the tenant identity when dispatching the webhook to the app's handler. This breaks the intended binding `HMAC-verified bytes == data used for tenant identification`, mirroring the `[M-02]` pattern where a value acted upon (pool status / here: shop identity) is not covered by the same check that authenticates the payload (enabled-flag check / here: HMAC).

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 

Only `@raw_body` is signed. `hmac`, `topic`, `shop`, `api_version`, and `webhook_id` are all read straight from HTTP headers with no cryptographic binding to the body: [2](#0-1) 

`HmacValidator.validate` only ever calls `verifiable_query.to_signable_string` (the body) against the HMAC secret: [3](#0-2) 

`Registry.process` checks the HMAC, then immediately trusts `request.shop` (and `request.topic`, `request.webhook_id`, `request.api_version`) to build the `WebhookMetadata` handed to the app's business-logic handler — the equivalent of "taking tokens from the pool" in the referenced report, i.e. acting on a field that was never actually authenticated: [4](#0-3) 

Because the header `shop` is not part of the signed content, any bearer of a validly-signed body (e.g. a merchant who has installed the app on their own store and therefore legitimately receives correctly-HMAC'd webhooks from Shopify for that store) can replay that body to the app's public webhook endpoint while substituting a different `x-shopify-shop-domain` (and/or `x-shopify-topic`/`x-shopify-webhook-id`) header. `HmacValidator.validate` will still pass because it only checks the body bytes, and the handler will process the payload as if it belongs to the victim shop — a cross-tenant identity confusion equivalent to `verified_bytes != identity_used`.

### Impact Explanation
This crosses the tenant boundary the HMAC check is meant to enforce: an app author reasonably assumes that once `HmacValidator.validate` passes, every field on the `Request` (including `shop`) originated from Shopify for that shop. In reality only the body is authenticated. A malicious or compromised merchant can therefore inject events that host applications will attribute to another merchant's shop record (e.g. triggering shop-scoped side effects such as data updates, entitlement changes, or state transitions keyed by `shop`), which is a cross-tenant access impact.

### Likelihood Explanation
Exploitation requires only: (1) installing the app on any Shopify store (unprivileged, not requiring the app's `client_secret` or an access token) to obtain a body Shopify has legitimately signed, and (2) sending a raw HTTP POST to the app's already-public webhook endpoint with a forged `shop-domain` header. No credential of the target shop or the app is needed. Likelihood is moderate-to-high wherever the host application relies solely on `Registry.process`'s HMAC check (as documented) to trust `WebhookMetadata#shop`.

### Recommendation
Include the security-relevant headers (`shop`, `topic`, `webhook_id`, `api_version`) in the signed content used for verification, or have `Registry.process`/`WebhookMetadata` cross-check `request.shop` against an app-known allowlist of installed shops before dispatch. At minimum, document prominently that `shop`/`topic`/other headers are unauthenticated and must not be used for authorization decisions without independent verification.

### Proof of Concept
```ruby
# Attacker owns "attacker-shop.myshopify.com" with the app installed,
# and captures a legitimately Shopify-signed webhook body + hmac header.
raw_body = '{"id":1,"note":"hi"}'
valid_hmac_header = "<the value Shopify sent for attacker-shop>"

# Attacker POSTs directly to the app's public webhook endpoint,
# reusing the valid body/hmac but swapping the shop-domain header.
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => valid_hmac_header,   # still valid: only signs raw_body
  "x-shopify-shop-domain" => "victim-shop.myshopify.com",
  "x-shopify-webhook-id" => "attacker-controlled-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# HmacValidator.validate(request) passes (body/hmac match),
# handler.handle receives shop: "victim-shop.myshopify.com" though
# Shopify never sent this event for that shop.
```

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
