### Title
Webhook `shop`/`topic` identity is trusted by handlers but not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely via `Utils::HmacValidator.validate(request)`, which delegates to `request.to_signable_string`: [1](#0-0) 

The signable string is defined as `@raw_body` only: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are read straight from unauthenticated HTTP headers: [2](#0-1) 

After a successful `Utils::HmacValidator.validate(request)` check, `Registry.process` builds `WebhookMetadata` and hands it to the app's handler using `request.shop` and `request.topic` as trusted identity fields, without any additional binding to the signed bytes: [3](#0-2) 

The equality that should hold is: `bytes verified by HMAC == bytes the application treats as authenticated (including shop/topic)`. In this code, `bytes verified` = `raw_body` only, while `bytes the application treats as authenticated` = `raw_body + shop-domain header + topic header`. The `shop` field — which downstream apps use to key per-tenant state (as documented for `WebhookMetadata`) — is a field acted on but never covered by the HMAC, directly matching the "field acted on but not covered by the HMAC" analog class from the reported bug pattern (function/API name implies a full integrity guarantee that the implementation doesn't actually provide).

### Impact Explanation
A user who can install the app on their own store (an ordinary, unprivileged action available to any internet user via the Shopify App/Partner ecosystem) can trigger any webhook topic they choose (e.g., `customers/update`, `orders/create`) on their own shop, producing a body whose content they substantially control and which Shopify signs with the app's shared `api_secret_key` for that raw body. Because the signature only binds the body, the attacker can then resend that exact byte-for-byte body to the app's webhook endpoint while changing only the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header to a victim shop's domain. `Utils::HmacValidator.validate` still returns `true` (it only checks the body against the HMAC), and `Registry.process` will invoke the merchant's webhook handler with `WebhookMetadata#shop` set to the victim's domain. Any app that uses `shop` to select which tenant's data store to write into (a common and expected pattern, since the gem presents `shop` as part of the already-"validated" request) will have attacker-controlled data written into, or trigger actions against, another merchant's tenant — a cross-tenant data-integrity/confusion issue.

### Likelihood Explanation
Medium: this requires the attacker to operate their own installed store on the same app (available to anyone who can install a public/development app) and to be able to reach the raw webhook body/headers to replay the request with a modified `shop-domain` header, which is a low bar for an attacker with basic HTTP tooling. It does not require the app's `client_secret`, an access token, or any privileged access — it only requires an installation the attacker themselves controls.

### Recommendation
Bind the header-derived identity fields into the value that is HMAC-verified: either include `shop`, `topic`, and `webhook_id` in the canonical string used by `HmacValidator`/`VerifiableQuery#to_signable_string` for webhooks, or independently verify that `request.shop` matches a shop domain that is expected/registered for this app before dispatching to the handler (e.g., cross-check against known installed shops) rather than trusting the header value implicitly once HMAC on the body succeeds.

### Proof of Concept
1. Install the target app on an attacker-owned dev/partner store `attacker-shop.myshopify.com`.
2. Trigger a webhook topic whose payload content the attacker can influence (e.g., update a customer record with attacker-chosen field values), causing Shopify to POST a body `B` with header `X-Shopify-Hmac-Sha256: HMAC(B, secret)` and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Capture `B` and its HMAC header.
4. Resend the identical body `B` and HMAC header to the same webhook endpoint, but replace `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com`.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb`, calling `Utils::HmacValidator.validate`) validates successfully because only `B` is checked, and the handler executes with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, processing attacker-supplied data under the victim's tenant identity.

Note: I was unable to inspect `lib/shopify_api/webhooks/webhook_handler.rb` and `docs/usage/webhooks.md` in this pass to confirm exactly how the gem documents the trust level of `WebhookMetadata#shop` to consumers; that file content was not retrieved before the tool budget was exhausted, so the documented guidance (if any) warning developers to re-validate `shop` independently could not be fully confirmed.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
