### Title
OAuth `begin_auth` builds the authorization redirect from an unsanitized `shop` parameter, enabling forced-OAuth-completion / session fixation - (File: lib/shopify_api/auth/oauth.rb)

### Summary
`ShopifyAPI::Auth::Oauth.begin_auth` takes the caller-supplied `shop` value and uses it, completely unsanitized, to build the URL the merchant's browser is redirected to in order to start the OAuth grant. Unlike the sibling OAuth flows in this gem (`TokenExchange`, `ClientCredentials`, `RefreshToken`), which all call `Utils::ShopValidator.sanitize!` before trusting a shop value, `begin_auth` never validates that `shop` is a real `*.myshopify.com`/trusted Shopify host before embedding it in the redirect target.

### Finding Description
`begin_auth` builds the authorize URL as: [1](#0-0) 

and resolves the host purely from the raw `shop` argument via `auth_base_uri`, with no domain validation: [2](#0-1) 

Compare this to the three other credential-exchange entry points in the gem, which all invoke `ShopValidator.sanitize!`/`sanitize_shop_domain` on the shop value before trusting it (confirmed by grep hits in `lib/shopify_api/auth/token_exchange.rb`, `lib/shopify_api/auth/client_credentials.rb`, and `lib/shopify_api/auth/refresh_token.rb`), and to the validator module itself, which exists specifically to reject non-Shopify hosts: [3](#0-2) 

`begin_auth` skips this check entirely. Since the `state` nonce, `redirect_uri`, and `client_id` are placed directly in the query string of the authorize URL sent to whatever host `shop` resolves to, if the host application passes through an attacker-supplied `shop` value (a very common pattern — `shop` is typically read straight from the login URL query string before any session exists), the victim's browser is redirected to an attacker-controlled origin carrying the real `client_id`, `redirect_uri`, and the freshly-generated `state` nonce, while the victim's browser also receives the `state` cookie set by this gem: [4](#0-3) 

Because the attacker's server now knows the exact `state` value bound to the victim's cookie, and `validate_auth_callback` only checks that `state == cookie` plus that the callback's HMAC is valid for *some* shop signed by this app's real `api_secret_key` — it never confirms that the shop being authorized matches what the victim actually intended: [5](#0-4) 

the attacker can complete a *real* Shopify OAuth authorization for their own store (obtaining a genuine `code`/`hmac`/`shop`/`timestamp` from Shopify) and then redirect the victim's browser to the app's real callback URL with that data plus the stolen `state` value. `validate_auth_callback` will accept it — because HMAC and state both check out — and will bind the victim's session cookie/browser to a session for the attacker's shop.

### Impact Explanation
This is a forced-OAuth-completion / session-fixation vulnerability: the victim's app session ends up associated with the attacker's shop rather than the shop the victim intended to authorize, letting the attacker fixate the victim's session identity or trick the victim into interacting with attacker-controlled shop data inside the merchant's app session. This maps to the explicitly in-scope High-severity category "session fixation or forced OAuth completion."

### Likelihood Explanation
Likelihood is Low-Medium: it requires the host application to pass an unauthenticated, attacker-influenced `shop` value into `begin_auth` (a widely-used integration pattern, since `shop`/`shopify_domain` is the canonical way apps identify the store before any session exists) and requires social-engineering the victim into visiting the crafted login link and completing two redirects. No knowledge of `api_secret_key` or any credential is required by the attacker.

### Recommendation
Call `Utils::ShopValidator.sanitize!` (or `sanitize_shop_domain`) on `shop` inside `Oauth.begin_auth` before using it to build `auth_base_uri`, exactly as is already done in `TokenExchange`, `ClientCredentials`, and `RefreshToken`. Additionally, bind the `state` value to the specific shop being authorized (e.g., include shop in the cookie value or validate that `auth_query.shop` matches the shop that initiated `begin_auth`) so a callback for an unrelated shop cannot be accepted just because the `state` nonce and HMAC independently check out.

### Proof of Concept
1. Victim visits `https://merchant-app.example.com/login?shop=attacker.example` (host app passes `shop` straight to `ShopifyAPI::Auth::Oauth.begin_auth`).
2. `begin_auth` returns `auth_route = "https://attacker.example/admin/oauth/authorize?client_id=<APP_CLIENT_ID>&scope=...&redirect_uri=<real_callback>&state=<nonce>"` and a `state` cookie is set on the victim's browser — see `lib/shopify_api/auth/oauth.rb:22-52`.
3. Victim's browser is redirected to attacker's server, which captures `client_id`, `redirect_uri`, and `state`.
4. Attacker independently completes a real Shopify OAuth grant for their own store, obtaining a genuine `code`/`hmac`/`timestamp` for `shop=attacker-real-store.myshopify.com`.
5. Attacker redirects the victim's browser (still holding the matching `state` cookie) to `<real_callback>?code=...&shop=attacker-real-store.myshopify.com&state=<nonce>&hmac=...&timestamp=...`.
6. `Oauth.validate_auth_callback` (`lib/shopify_api/auth/oauth.rb:60-98`) validates HMAC (valid, since it's a genuine Shopify-signed callback for the attacker's store) and `state == cookie` (matches, since the attacker learned it in step 3), and completes OAuth, binding the victim's browser session to the attacker's shop.

        def begin_auth(shop:, redirect_path:, is_online: true, scope_override: nil)
          scope = if scope_override.nil?
            ShopifyAPI::Context.scope
          elsif scope_override.is_a?(ShopifyAPI::Auth::AuthScopes)
            scope_override
          else
            ShopifyAPI::Auth::AuthScopes.new(scope_override)
          end

          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = SecureRandom.alphanumeric(NONCE_LENGTH)

          cookie = SessionCookie.new(value: state, expires: Time.now + 60)

          query = {
            client_id: ShopifyAPI::Context.api_key,
            scope: scope.to_s,
            redirect_uri: "#{ShopifyAPI::Context.host}#{redirect_path}",
            state: state,
            "grant_options[]": is_online ? "per-user" : "",
          }

          query_string = URI.encode_www_form(query)
          auth_route = auth_base_uri(shop) + "/oauth/authorize?#{query_string}"

          { auth_route: auth_route, cookie: cookie }
        end

        def validate_auth_callback(cookies:, auth_query:)
          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state

          null_session = Auth::Session.new(shop: auth_query.shop)
          body = {
            client_id: Context.api_key,
            client_secret: Context.api_secret_key,
            code: auth_query.code,
            expiring: Context.expiring_offline_access_tokens ? 1 : 0, # Only applicable for offline tokens
          }

          client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
          response = begin
            client.request(
              Clients::HttpRequest.new(
                http_method: :post,
                path: "access_token",
                body: body,
                body_type: "application/json",
              ),
            )
          rescue ShopifyAPI::Errors::HttpResponseError => e
            raise Errors::RequestAccessTokenError,
              "Cannot complete OAuth process. Received a #{e.code} error while requesting access token."
          end

          session_params = T.cast(response.body, T::Hash[String, T.untyped]).to_h
          session = Session.from(shop: auth_query.shop,
            access_token_response: Oauth::AccessTokenResponse.from_hash(session_params))

        sig { params(shop: String).returns(String) }
        def auth_base_uri(shop)
          return "https://#{shop}/admin" unless defined?(DevServer) && shop.include?(".my.shop.dev")

          # For first-party apps in development only, we leverage DevServer to build the admin base URI
          admin_web = T.unsafe(Object.const_get("DevServer")) # rubocop:disable Sorbet/ConstantsFromStrings
            .new("admin-web")
          admin_host = admin_web.host!(nonstandard_host_prefix: "admin")
          shop_name = shop.split(".").first

          "https://#{admin_host}/store/#{shop_name}"
        end
