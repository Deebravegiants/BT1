Audit Report

## Title
Unbounded HTTP Action Response Cache Growth via Workflow-Controlled Cache Keys - (File: `core/services/gateway/handlers/capabilities/v2/response_cache.go`)

## Summary
The `responseCache` used by the CRE gateway's HTTP-action capability handler stores every distinct cacheable outbound HTTP response in an in-process `map[string]*cachedResponse` keyed by `req.Hash()`, with no maximum entry-count or byte-size limit anywhere in `Set`, `Fetch`, or the constructor `newResponseCache`. [1](#0-0)  The only cleanup path is the TTL-based `DeleteExpired` sweep, which never bounds total map size at insertion time. [2](#0-1)  A workflow whose `http-action` step uses a request key that varies per invocation (e.g., unique query param) and sets `CacheSettings.Store = true` will insert a new permanent-until-TTL entry on every execution, forcing unbounded memory growth if the insertion rate outpaces the TTL-based sweep interval.

## Finding Description
`makeOutgoingRequest`, invoked from `HandleNodeMessage` when a DON node relays an `http-action` capability response to the gateway, calls `h.responseCache.Fetch(...)` or `h.responseCache.Set(...)` keyed by the full request hash (method, URL, headers, body, workflow owner). [3](#0-2)  Because the key is derived from workflow-controlled fields (URL/body/headers), a workflow author who varies these fields per invocation guarantees cache misses and therefore continual new insertions. Notably, the sibling cache implementation in the same codebase, `requestCache` in `core/services/gateway/handlers/common/requestcache.go`, explicitly enforces a `maxCacheSize` and rejects new entries once full: [4](#0-3)  — confirming that a size-bounding mechanism is an established pattern elsewhere in this codebase but is absent from `responseCache`.

However, reaching this code path is not available to an arbitrary anonymous internet actor. Workflow deployment/registration on the CRE workflow registry requires the deployer's signer address to be added via `UpdateAllowedSigners`/`updateAllowedSigners`, and DON/user quota must be configured via `SetDONLimit`/`SetUserDONOverride`, all of which are administrator-controlled onboarding operations. [5](#0-4) [6](#0-5)  The submitted claim's own framing already concedes this precondition ("an external, unprivileged actor who can register/deploy a workflow"), i.e., it requires being an onboarded/authorized workflow owner rather than a fully anonymous, zero-permission client — but this level of access is the normal, expected access level for a legitimate platform tenant of the CRE workflow system, not an operator/admin/host-level privilege, so it does not disqualify the finding as "operator-only."

Existing rate limiters (`perNodeRateLimiters`, `globalNodeRateLimiter`) throttle message throughput per node and globally but do not bound the number of live cache entries, so sustained legitimate-looking traffic that stays under the throughput limit can still accumulate unboundedly in the cache over time. [7](#0-6) 

## Impact Explanation
An onboarded workflow owner can cause the gateway process serving their DON shard to grow the `responseCache` map without bound by continually issuing uniquely-keyed cacheable `http-action` requests, eventually exhausting gateway memory and causing a denial of service affecting all workflows served by that gateway instance. This is a legitimate resource-exhaustion/DoS class finding, distinct from and weaker than requiring a fully anonymous unprivileged attacker, since it requires workflow-owner-level platform access (an authorization step gated by `UpdateAllowedSigners`/DON limits) rather than zero-credential public access.

## Likelihood Explanation
Moderate: exploitation requires only normal, non-administrative workflow-owner capability (deploy a workflow with `CacheSettings.Store = true` and varying request keys) once onboarded — no operator, admin, or host-level access, and no malicious DON node is required. The main constraint is throughput imposed by the per-node/global rate limiters, meaning the growth rate is bounded by legitimate workflow execution cadence, but sustained execution over time will still exceed a purely TTL-based cleanup absent any size cap, mirroring the missing safeguard that the codebase's own `requestCache` already implements elsewhere.

## Recommendation
- Add a hard maximum entry count (or byte-size budget) to `responseCache`, mirroring the `maxCacheSize` guard already used in `core/services/gateway/handlers/common/requestcache.go`, rejecting or LRU-evicting entries once the limit is reached.
- Consider per-workflow-owner cache-entry quotas to prevent a single workflow from monopolizing the shared cache.
- Monitor `http_action_cache_size` (exposed via `metrics.RecordCacheSize`) for unbounded growth trends.

## Proof of Concept
1. Onboard as an authorized workflow owner (signer added via `UpdateAllowedSigners`, DON limit configured via `SetDONLimit`/`SetUserDONOverride`).
2. Deploy a workflow with an `http-action` step setting `CacheSettings.Store = true` and a URL/body that varies on every invocation (e.g., a random query parameter).
3. Trigger repeated executions (via cron/webhook trigger) at a sustained rate below the per-node/global rate limiter thresholds but persisting over a long duration.
4. Observe via the `http_action_cache_size` metric (`metrics.RecordCacheSize` in `response_cache.go`) or gateway process RSS that cache entries and memory grow monotonically without a ceiling, only shrinking by TTL expiry of oldest entries, never by a count-based cap.

func (rc *responseCache) DeleteExpired(ctx context.Context) int {
	rc.cacheMu.Lock()
	defer rc.cacheMu.Unlock()
	now := time.Now()
	var expiredCount int
	for key, cachedResp := range rc.cache {
		if now.After(cachedResp.storedAt.Add(rc.ttl)) {
			delete(rc.cache, key)
			expiredCount++
		}
	}
	rc.lggr.Debugw("Removed expired cached HTTP responses", "count", expiredCount, "remaining", len(rc.cache))
	rc.metrics.IncrementCacheCleanUpCount(ctx, int64(expiredCount), rc.lggr)
	rc.metrics.RecordCacheSize(ctx, int64(len(rc.cache)), rc.lggr)
	return expiredCount
}

func (h *gatewayHandler) HandleNodeMessage(ctx context.Context, resp *jsonrpc.Response[json.RawMessage], nodeAddr string) error {
	if resp.ID == "" {
		return fmt.Errorf("received response with empty request ID from node %s", nodeAddr)
	}
	h.lggr.Debugw("handling incoming node message", "requestID", resp.ID, "nodeAddr", nodeAddr)
	nodeRateLimiter, ok := h.perNodeRateLimiters[nodeAddr]
	if !ok {
		return fmt.Errorf("received message from unexpected node %s", nodeAddr)
	}
	if !nodeRateLimiter.Allow(ctx) {
		h.metrics.IncrementCapabilityNodeThrottled(ctx, nodeAddr, h.lggr)
		return fmt.Errorf("rate limit exceeded for node %s", nodeAddr)
	}
	if !h.globalNodeRateLimiter.Allow(ctx) {
		h.metrics.IncrementGlobalThrottled(ctx, h.lggr)
		return errors.New("global rate limit exceeded")
	}

	h.lggr.Debugw("handling outgoing message", "requestID", requestID, "nodeAddr", nodeAddr)
	var req gateway_common.OutboundHTTPRequest

	if err != nil {
		return fmt.Errorf("failed to unmarshal HTTP request from node %s: %w", nodeAddr, err)
	}
	timeout := time.Duration(req.TimeoutMs) * time.Millisecond

		Method:           req.Method,
		URL:              req.URL,
		Headers:          req.Headers, //nolint:staticcheck // forward deprecated Headers for backward compatibility; request uses MultiHeaders when set
		MultiHeaders:     req.MultiHeaders,
		Body:             req.Body,
		MaxResponseBytes: req.MaxResponseBytes,
		Timeout:          timeout,
	}

	sendResponseTimeout := time.Duration(defaultSendResponseTimeoutMs) * time.Millisecond

	// send response to node async
	h.wg.Go(func() {
		// not cancelled when parent is cancelled to ensure the goroutine can finish
		baseCtx := context.WithoutCancel(ctx)
		httpCtx, httpCancel := context.WithTimeout(baseCtx, timeout)

		l := logger.With(h.lggr, "requestID", requestID, "method", req.Method, "timeout", req.TimeoutMs)

type requestCache[T any] struct {
	cache        map[globalID]*pendingRequest[T]
	maxCacheSize uint32
	timeout      time.Duration
	mu           sync.Mutex
}

type globalID struct {
	sender string
	id     string
}

type pendingRequest[T any] struct {
	handlers.Callback
	responseData *T
	timeoutTimer *time.Timer
	mu           sync.Mutex
}

func NewRequestCache[T any](timeout time.Duration, maxCacheSize uint32) RequestCache[T] {
	return &requestCache[T]{cache: make(map[globalID]*pendingRequest[T]), timeout: timeout, maxCacheSize: maxCacheSize}
}

func (c *requestCache[T]) NewRequest(lggr logger.Logger, request *api.Message, callback handlers.Callback, responseData *T) error {
	if request == nil {
		return errors.New("request is nil")
	}
	if responseData == nil {
		return errors.New("responseData is nil")
	}
	key := globalID{request.Body.Sender, request.Body.MessageID}
	c.mu.Lock()
	defer c.mu.Unlock()
	_, ok := c.cache[key]
	if ok {
		return errors.New("request already exists")
	}
	if len(c.cache) >= int(c.maxCacheSize) {
		return errors.New("request cache is full")
	}
