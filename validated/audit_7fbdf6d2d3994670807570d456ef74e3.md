### Title
Unlimited router approval + unaccounted residual balance lets attacker steal stranded/in-flight tokens from `ExternalActionSwap`/`LifiExternalAction` - (File: contracts/external-actions/swaps/LifiExternalAction.sol, contracts/external-actions/swaps/ExternalActionSwap.sol)

### Summary
`LifiExternalAction.callRouter` calls `approveUnlimited(inputToken, router)` and then executes fully attacker-supplied calldata (`externalActionMetadata`) against the router, without ever constraining how much of `inputToken` the router actually pulls to the caller-declared `inputAmount`. Any `inputToken` balance sitting in the action contract (from a partial-fill refund, dust left by a prior swap, or even a plain unsolicited ERC-20 transfer) can be swept by the router call and converted into an attacker-controlled output UTXO, because the only accounting performed is on `outputToken` (`swappedAmount = balanceAfter - balanceBefore`), and Hinkal's own balance-diff check in `contracts/Hinkal.sol:97-146` only verifies Hinkal's own balance against `amountChanges`/`utxoAmount`, not that the action's execution was scoped to the caller's declared input.

### Finding Description
The claimed invariant is: *tokens leaving the action in a transaction == the `-deltaAmountChanges` Hinkal sent it that transaction.* This is broken.

- `contracts/Hinkal.sol:247-256` (`_externalTransact`) sends the action exactly `-deltaAmountChanges[0]` of `inputToken` before calling `runAction`.
- `contracts/external-actions/swaps/ExternalActionSwap.sol:63-68` calls `callRouter(inputToken, inputAmount, outputToken, externalActionMetadata)`.
- `contracts/external-actions/swaps/LifiExternalAction.sol:16-36`: for ERC-20 input, it calls `approveUnlimited(inputToken, router)` (approving `type(uint256).max`, see `contracts/TransfererBase.sol:32-43`) and then does `router.call(externalActionMetadata)`. Critically, **`inputAmount` is never used in the ERC-20 branch** — the amount the router actually pulls from the action's balance is determined solely by the attacker-controlled `externalActionMetadata`, not by `inputAmount`.
- `swappedAmount` is measured only as `getERC20OrETHBalance(outputToken) after - before` (`LifiExternalAction.sol:22-35`); there is no equivalent check that the router consumed only `inputAmount` of `inputToken`, and no UTXO/refund path exists in `ExternalActionSwap.swap` for any leftover `inputToken` balance in the action (unlike `EmporiumUpgradeable.runAction`, which explicitly computes `balancesBefore`/`balancesAfter` per token and emits a residual UTXO via `handleOut`, `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol:85-160`).

Exploit flow:
1. Any unprivileged party causes `inputToken` balance to accumulate in the `LifiExternalAction` contract beyond what the current caller supplied — e.g., a router partial fill that refunds unspent input back to `msg.sender` (the action contract), or simply an ERC-20 `transfer()` sent directly to the action's address (no protocol interaction needed).
2. Attacker calls `Hinkal.transact` with a legitimate (even minimal) own deposit/`deltaAmounts[0]` for `inputToken`, but crafts `externalActionMetadata` so the router (which already holds `type(uint256).max` approval from a prior `approveUnlimited` call, or gets it freshly in this call) pulls the *entire* current `inputToken` balance of the action contract — stranded residual plus the attacker's own tiny contribution.
3. The router swaps this inflated amount to `outputToken`; `swappedAmount` reflects the full inflated amount.
4. `ExternalActionSwap.swap` forwards `amountToSendToHinkal` (inflated) to Hinkal and returns a single `utxoSet[0]` entry attributing the entire inflated amount to the attacker's own `stealthAddressStructure` (`ExternalActionSwap.sol:93-101`).
5. Hinkal's balance-diff invariant (`Hinkal.sol:134-146`) trivially holds because `utxoAmount` is derived directly from the actual on-chain transfer amount (`amountToSendToHinkal`), and the attacker's own proof/public inputs (`amountChanges`, out-commitment amount) are self-consistently generated to match whatever the swap actually produced — the circuit (`MainEVMCircuit.circom:168`, `inTotal + amountChanges[i] === outTotal`) only enforces internal consistency of the attacker's own claimed amounts, not that the swap output is proportional to the attacker's declared input.

None of the existing guards (`performHinkalChecks`, `dimensionsCheck`, `checkOnchainCreation`, `rootHashExists`, the slippage/balance-diff requires, `onlyAllowedRecipient`, `nonReentrant`) constrain the router call to only consume the declared `inputAmount`; they only validate Hinkal's own balance bookkeeping, which stays consistent even when the action contract's balance is drained beyond what Hinkal sent it.

### Impact Explanation
Direct theft of tokens stranded/in-flight in the `LifiExternalAction`/`ExternalActionSwap` contract — funds belonging to the protocol, prior users (partial-fill refunds), or anyone who mistakenly/incidentally sends tokens to the contract — by converting them into an attacker-chosen shielded UTXO. This is repeatable per accumulated residual and matches **Critical: direct theft of shielded or in-flight user funds**, since the stolen value is pulled through the normal `Hinkal.transact` path and minted as a legitimate-looking UTXO under attacker control.

### Likelihood Explanation
- Requires the action contract to hold some `inputToken` balance beyond the caller's own contribution. This is a realistic and recurring precondition given LI.FI/router partial fills, dust, or simply an unsolicited `transfer()` to the contract (trivially triggerable by the attacker themselves, with zero privilege).
- No special role or timing is required beyond crafting `externalActionMetadata`, which the attacker fully controls per the rules.
- Cost is low: one `transfer()` to seed residual, then one `Hinkal.transact` call with custom router calldata and a self-generated proof for their own tiny UTXO.
- Repeatable every time residual accumulates.

### Recommendation
Scope the router's pull strictly to `inputAmount`: replace `approveUnlimited` with `approveERC20Token(inputToken, router, inputAmount)` (exact allowance, reset after the call), and additionally verify via balance-before/after on `inputToken` that the router consumed at most `inputAmount` from the action's balance, reverting otherwise. Any true leftover input balance should be handled explicitly (refunded via its own accounted UTXO, mirroring `EmporiumUpgradeable.handleOut`), not left as unattributed contract balance protected only by an unlimited approval.

### Proof of Concept

1. Deploy `Hinkal`, `HinkalHelper`, a mock LI.FI router, and `LifiExternalAction`.
2. Seed residual: from an unrelated EOA, `IERC20(inputToken).transfer(address(lifiExternalAction), residualAmount)` directly (no Hinkal call).
3.
