### Title
Out-of-bounds slice panic on attacker-controlled `message.from` length in HFT `on_accept` calldata path - (File: modules/pallets/hyper-fungible-token/src/module.rs)

### Summary
`Pallet::on_accept` decodes an ABI `Message` from an ISMP `PostRequest.body` originating from a registered token contract on the source chain, then, only when `message.data` carries a `SubstrateCalldata` with no `signature`, derives the dispatch origin from `message.from` [1](#0-0) . Unlike the parallel recipient-length handling for `to_bytes` a few lines above (which validates 32/20-byte lengths and returns `HftError::InvalidRecipientLength` otherwise) [2](#0-1) , and unlike the `on_timeout` handler which validates `from_bytes.len()` before copying [3](#0-2) , the no-signature branch in `on_accept` performs unchecked slicing/copying on `from_bytes` derived directly from the ABI-decoded `message.from`.

### Finding Description
`message` is fully attacker-controlled: it is ABI-decoded from `body`, the request payload of a `PostRequest` delivered by any relayer via the pallet-ismp dispatch path, gated only by a registered `(source, from)` -> asset mapping check, not by the contents of `message.from`/`message.to`/`message.data` [4](#0-3) . When `message.data` is non-empty and decodes to a `SubstrateCalldata` with `signature: None`, execution reaches:

```rust
let from_bytes = message.from.as_ref();
if source.is_evm() {
    T::EvmToSubstrate::convert(H160::from_slice(
        &from_bytes[from_bytes.len() - 20..],
    ))
} else {
    let mut account = [0u8; 32];
    account.copy_from_slice(from_bytes);
    account.into()
}
``` [5](#0-4) 

- If `source.is_evm()` and `from_bytes.len() < 20`, `from_bytes.len() - 20` underflows (`usize` subtraction), producing a huge index and panicking the range operation before any slice bounds error is even evaluated cleanly — an unchecked-length parse of attacker data analogous to `read_samples`/hcom.c indexing off a crafted length field.
- If `source` is not EVM and `from_bytes.len() != 32`, `account.copy_from_slice(from_bytes)` panics (length mismatch) — the exact `copy_from_slice`-without-length-check pattern that this repository elsewhere treats as a hardening target (see `ByteVector::decode`'s explicit length check and the `as_utf8_string` regression test that both call out fixing this same panic class) [6](#0-5) [7](#0-6) .

Since `alloy_sol_types::SolValue::abi_decode` for a `bytes from` field places no constraint on its length (it is a dynamic ABI bytes field), an attacker fully controls `message.from`'s length and can set it to any value other than 20 (EVM) or 32 (non-EVM), e.g. length 0, to trigger the panic deterministically.

### Impact Explanation
`on_accept` runs inside pallet-ismp's message dispatch when a relayer submits a `PostRequest` for the hyper-fungible-token application (reached via `handle_unsigned`/dispatch and module routing, matching the in-scope "unauthorized app action" / "route unable to deliver messages" classes). A panic inside `on_accept` aborts the extrinsic; because this executes inside `handle_unsigned` for a batch of messages, a single malicious cross-chain token-transfer PostRequest with attacker-chosen `data`/`from` length can deterministically abort processing of the message (and, depending on batching, sibling messages in the same call), a denial-of-service on the message-delivery/token-mint path — directly analogous to the CVE's "crafted file causes crash" bug class, but reachable by any relayer delivering a message from a registered source contract rather than requiring privileged access.

### Likelihood Explanation
Likelihood is High for a registered token-bridge integration: any account able to relay a `PostRequest` whose `source`/`from` matches an entry in `ContractToAsset` can construct the ABI-encoded `Message` with `data` containing a `SubstrateCalldata{ signature: None, runtime_call }` and an arbitrary-length `from` field (distinct from the `PostRequest.from` module id used for the authentication lookup — `message.from` is a separate ABI field inside `body` and is not otherwise validated). No cryptographic proof forgery or privileged role is required; only a legitimate, permissionless message dispatch through the already-registered bridge contract.

### Recommendation
Validate `from_bytes.len()` in the no-signature branch of `on_accept` before slicing or copying, mirroring the existing pattern used for `to_bytes` in the same function and for `from_bytes` in `on_timeout`: return a typed error (e.g. `HftError::InvalidSenderLength`) for any length other than 20 (when `source.is_evm()`) or 32 (otherwise), instead of performing raw `usize` arithmetic and `copy_from_slice` on unchecked attacker-supplied byte lengths.

### Proof of Concept
1. Register a source contract/asset mapping via `ContractToAsset` for `source` = an EVM state machine and `from` = attacker's contract address (standard token-bridge configuration).
2. Craft a `PostRequest` with `body` = ABI-encoding of `Message { from: b"" /* 0 bytes */, to: <valid 20 or 32 bytes>, amount: <any>, data: SubstrateCalldata{ signature: None, runtime_call: <any decodable call> }.encode() }`.
3. Deliver this `PostRequest` through the normal ISMP relay path (`handle_unsigned`) so it reaches `Pallet::on_accept`.
4. Execution reaches `&from_bytes[from_bytes.len() - 20..]` with `from_bytes.len() == 0`, causing `0usize - 20` to underflow and the subsequent slice indexing to panic, aborting the extrinsic.
