## Title
Webhook shop/topic identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by re-computing the HMAC over the raw request body and comparing it to the `x-shopify-hmac-sha256`/`shopify-hmac-sha256` header. The `shop`, `topic`, `webhook_id`, and `api_version` values — all of which come from separate, unauthenticated HTTP headers — are never included in the signed content, yet they are handed to the app's handler as if they were verified, authoritative tenant/routing identifiers.

### Finding Description
`Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

while `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers that are not part of the signed payload: [2](#0-1) 

`HmacValidator.validate_signature` only ever verifies `verifiable_query.to_signable_string` (i.e., the raw body) against the secret: [3](#0-2) 

`Registry.process` performs exactly this body-only HMAC check, then immediately trusts `request.shop` and `request.topic` (both unauthenticated headers) to route the payload to the handler and stamp the tenant identity on `WebhookMetadata`: [4](#0-3) 

The identity binding broken here is: `hmac_signed_bytes == request.raw_body`, but `tenant_identity_used_by_handler == request.shop` (a header outside the signed bytes). Any party who can obtain **one** legitimately signed `(raw_body, hmac)` pair for a given topic — trivially possible by installing the app on their own store, a dev store, or a store they control — can replay that exact `(raw_body, hmac)` pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header (and/or `x-shopify-topic` header) with any value they choose. Because the HMAC never covers those headers, the forged request passes signature validation and the handler processes it under the attacker-chosen shop/topic, achieving cross-tenant impersonation without ever needing the app's `client_secret`.

### Impact Explanation
This directly matches the "Critical – cross-tenant access" impact category: an unprivileged internet user, in possession of a single valid webhook signature for their own store (or any topic/body combination whose byte content is predictable, e.g. the empty-body `{}` payload used for topics like `app/uninstalled`), can make the host application process attacker-controlled data under a victim shop's identity — potentially triggering uninstall/downgrade logic, deleting stored data, or corrupting per-shop state keyed by `WebhookMetadata#shop`.

### Likelihood Explanation
Likelihood is high for the "same/predictable body across shops" case: several Shopify webhook topics have identical or attacker-predictable bodies regardless of shop (e.g., `app/uninstalled` sends `{}`), so no reconnaissance beyond registering/receiving one webhook on the attacker's own shop is required before forging the header and replaying it against the target app's public webhook endpoint. For topics whose body includes shop-specific content, the likelihood is lower but non-zero since some attacker-controlled resource content is reflected verbatim in body-only webhooks.

### Recommendation
Bind the header-derived identity fields (`shop`, `topic`, `webhook_id`, `api_version`) into the signed material, or at minimum re-validate them out-of-band (e.g., confirm the `shop` header corresponds to a shop with an active, stored installation/session before invoking the handler) rather than trusting them purely because the body-only HMAC matched. If Shopify's real webhook signature genuinely only covers the body, the gem's documentation/consumers must be made aware that `WebhookMetadata#shop`/`#topic` are **not** cryptographically authenticated and must not be used as sole tenant-routing keys.

### Proof of Concept
1. Install the app on an attacker-controlled/dev shop `attacker.myshopify.com` and register for a topic whose body is constant, e.g. `app/uninstalled` (body `{}`).
2. Capture the legitimate webhook delivery: raw body `{}` and its valid `x-shopify-hmac-sha256` header (computed by Shopify with the app's real secret over `{}`).
3. Replay this exact `(body, hmac)` pair to the app's public webhook endpoint, but set `x-shopify-shop-domain: victim.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks the body/hmac pair — this succeeds since it's an unmodified legitimate pair.
5. `handler.handle(data: WebhookMetadata.new(... shop: request.shop ...))` is invoked with `shop == "victim.myshopify.com"`, even though `victim.myshopify.com` never sent this webhook, demonstrating cross-tenant spoofing. [5](#0-4)
