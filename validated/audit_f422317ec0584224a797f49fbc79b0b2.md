## Analysis

The reachable analog here is **Uniswap V4 spot-price consumption in the intent-solver's FX pricing/funding logic**, which mirrors the GLP/GMX bug class exactly: a downstream financial decision (fill pricing and reorg-confirmation sizing) is derived from a manipulatable AMM spot price, guarded only by a static, config-time deviation band rather than a TWAP or manipulation-resistant oracle.

### Title
Uniswap V4 spot price used for order pricing and confirmation-depth sizing is flash-manipulable and only bounded by a static reference band - (File: `sdk/packages/simplex/src/funding/uniswapV4/UniswapV4FundingPlanner.ts`, `sdk/packages/simplex/src/strategies/fx.ts`)

### Summary
`UniswapV4FundingPlanner.getExoticTokenPrice` / `computeDirectPoolPriceUsd` read the pool's instantaneous mid price (`sdkPool.token0Price`/`token1Price`, derived from `sqrtPriceX96`) with no TWAP smoothing or manipulation resistance, exactly the class of price GMX's AMM component provided in the referenced GLP report. `FXFiller.checkPriceGuard` / `referenceRate` / `resolveLegRates` in `fx.ts` consume this venue price for both (a) sizing an intent order's fill amount and (b) determining the USD notional used for reorg-confirmation depth, and the only defense is comparing the live pool quote against a **static** `referencePrice`/`maxDeviationBps` configured once in TOML — which is optional and, per the docs, can be entirely omitted ("omit both to leave the chain unguarded"). [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`computeDirectPoolPriceUsd` derives `priceUsd` directly from the live Uniswap V4 pool's `token0Price`/`token1Price`, i.e. the pool's current spot ratio computed from `sqrtPriceX96`: [4](#0-3) 

This value flows into `FXFiller.referenceRate` (used to size the pair's USD notional for reorg-confirmation depth) and `resolveLegRates` (used to price the actual fill for curveless, venue-priced pairs): [5](#0-4) [6](#0-5) 

The only defense is `checkPriceGuard`, which compares the live quote against a **static** `referencePrice` set once at config time and never refreshed on-chain, tolerating deviations up to `maxDeviationBps`: [2](#0-1) 

Per the docs, the guard is optional entirely, and even when configured its band is fixed/static rather than tracking a manipulation-resistant reference (e.g. TWAP or Chainlink): [7](#0-6) 

This is precisely the bug class described in the external report: a component that is supposed to represent a fair price is instead taken directly from an easily flash-loan/flash-swap-manipulable AMM spot price, and the only sanity check is a static bound that an attacker who knows the reference and band can manipulate the pool to just barely satisfy while still being materially wrong. An unprivileged party (an intent submitter/order originator) can:
1. Flash-swap the configured Uniswap V4 pool to move `sqrtPriceX96` to the edge of (or briefly through, if unguarded) the static band.
2. In the same block, submit/trigger an order that the FXFiller will price against `computeDirectPoolPriceUsd`'s manipulated read.
3. Cause the solver to (a) fill the order at a manipulated rate, transferring value from the solver's own inventory to the attacker, and/or (b) undersize the USD notional used for reorg-confirmation depth, weakening the reorg protection for a fill that is actually large in real value — reproducing the "confirmation depth shrinks because the guard's manipulated price understates true value" risk explicitly called out in the referenceRate comment itself. [8](#0-7) 

### Impact Explanation
A successful manipulation causes direct fund loss to the solver's liquidity (analogous to the GMX report's "attacker profits off a manipulated collateral price") and/or degrades reorg/finality protection sized off a manipulated USD notional, which can enable a fill to be confirmed with insufficient confirmation depth relative to its true economic size — a concrete route to theft or unsound settlement of value, matching the High severity of the source report.

### Likelihood Explanation
Likelihood is Medium-High: Uniswap V4 pools are permissionlessly swappable, flash-swappable in a single transaction, and the guard is either absent by default or bounded by a static, publicly known `maxDeviationBps`/`referencePrice`, letting an attacker compute exactly how far they can push the spot price while remaining "valid." No privileged role is required — only capital to move the pool within one block, which is unprivileged/reachable exactly as required by the analog rules (an intent solver's own pricing path, triggered by an unprivileged order).

### Recommendation
Replace or supplement the direct `sqrtPriceX96`-derived spot price with a TWAP (e.g., Uniswap V4 truncated oracle observations) or an external manipulation-resistant price feed (Chainlink, as already used elsewhere in `SimplexPaymaster.sol`) before using it for fill pricing or confirmation-depth sizing; make the deviation guard mandatory rather than optional, and consider dynamically refreshing `referencePrice` from a trusted source rather than a static config value.

### Proof of Concept
1. Attacker identifies a `[[vault.uniswapV4.positions]]` pair with no `referencePrice`/`maxDeviationBps` configured (explicitly allowed per docs) or with a wide/static band.
2. Attacker flash-swaps the pool to shift `sqrtPriceX96`, changing `sdkPool.token0Price`/`token1Price` read by `computeDirectPoolPriceUsd`.
3. In the same transaction/block, attacker submits an order that routes through `FXFiller.resolveLegRates` → `venueUsdPrice` → `getExoticTokenPrice`, which returns the manipulated price.
4. `checkPriceGuard` passes (either no guard configured, or manipulated price kept within `maxDeviationBps` of a stale static reference).
5. The solver fills the order at the manipulated rate and/or sizes confirmation depth off the manipulated USD notional, resulting in solver fund loss or under-confirmed settlement.

	/**
	 * Validates a live venue quote against the static reference price for the chain.
	 * Returns true (pass) when no guard is configured, or no reference exists for the
	 * chain. Returns false when the quote (token1 per USD) deviates from the reference
	 * by more than `maxDeviationBps`, in which case the order must not be filled.
	 */
	private checkPriceGuard(orderId: string | undefined, chain: string, venueToken1PerUsd: Decimal): boolean {
		const guard = this.priceGuard?.get(chain)
		if (!guard || guard.reference.lte(0)) return true

		const deviationBps = venueToken1PerUsd.minus(guard.reference).abs().div(guard.reference).mul(10000)
		if (deviationBps.gt(guard.maxDeviationBps)) {
			this.logger.warn(
				{
					orderId,
					chain,
					venuePrice: venueToken1PerUsd.toString(),
					referencePrice: guard.reference.toString(),
					deviationBps: deviationBps.toFixed(2),
					maxDeviationBps: guard.maxDeviationBps,
				},
				"Rejecting order: Uniswap venue quote outside price-guard band",
			)
			return false
		}
		return true
	}

	/**
	 * Minimum-size reference rate (token1 per token0) for a leg's pair: the
	 * bid curve at 0 (the side token1-input legs trade at), falling back to the
	 * ask curve, then the live venue quote for venue-priced pairs.
	 */
	private async referenceRate(
		leg: ResolvedLeg,
		venueUsdPrice: (chain: string, token1Address: string) => Promise<Decimal | null>,
	): Promise<Decimal | null> {
		const policy = leg.pair.bidPricePolicy ?? leg.pair.askPricePolicy
		if (policy) {
			const rate = policy.getPrice(new Decimal(0))
			return rate.gt(0) ? rate : null
		}
		// Venue-priced pair: token0 is USD-stable (constructor invariant), so the
		// venue's USD-per-token1 quote inverts straight into token1-per-token0.
		const venueUsd = await venueUsdPrice(leg.token1Chain, leg.token1Address)
		if (!venueUsd) return null
		const venueRate = new Decimal(1).div(venueUsd)
		// Same guard as trade pricing: this rate sizes the order's USD notional
		// for confirmation depth, and a manipulated pool understating the value
		// would shrink the reorg protection — the exact attack the guard exists
		// to stop. Refusing to size skips the order, consistent with pricing.
		if (!this.checkPriceGuard(undefined, leg.token1Chain, venueRate)) return null
		return venueRate
	}

## Uniswap price guards

Pool-based pricing trusts the live pool, which leaves the solver exposed to a manipulated, stale, or thin pool returning a bad quote. To bound that risk, give a position a **`referencePrice`** and **`maxDeviationBps`**. Whenever the pool quote on that chain drifts more than `maxDeviationBps` above or below the reference, the solver refuses to fill — the order is rejected before any bid is submitted.

`referencePrice` is expressed in **exotic tokens per USD**, the same units as the bid/ask curves. The two fields must be set together; omit both to leave the chain unguarded.

```toml lineNumbers
[vault.uniswapV4]
# referencePrice is the expected cNGN per USD;
# reject if the quote is more than 2% off.
# The two go together — one without the other is rejected.
[[vault.uniswapV4.positions]]
chain           = "EVM-8453"
tokenId         = "2087350"
referencePrice  = "1575"
maxDeviationBps = 200
```
