### Title
Incorrect Authorization via permissive `instance()` fallback lets forged escrow-release/refund requests from unregistered source chains — (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2.instance()` (Tron/legacy variant) falls back to `address(this)` whenever no gateway has been registered for a given `stateMachineId` via `NewDeployment`. `authenticate()` (called from `onAccept` for `RedeemEscrow`/`RefundEscrow`) uses this same function to check that the incoming request's `from` address matches the "known instance" for `request.source`. For any state machine that Hyperbridge has a live consensus client for but for which governance has never issued a `NewDeployment`, the check silently accepts `from == address(this)` as valid, i.e. it treats "unregistered" as "trust myself."

### Finding Description
`onAccept` for `RedeemEscrow`/`RefundEscrow` only requires `authenticate(request)` to pass — it does not additionally require the source chain to match Hyperbridge itself (unlike `NewDeployment`/`UpdateParams`/`SweepDust`, which explicitly check `request.source == hyperbridge()`) [2](#0-1) . Authorization for these fund-moving actions rests entirely on `authenticate`, which in turn rests on `instance()`'s default-to-self fallback.

Because `IntentGatewayV2` is deployed at the same address across EVM chains via deterministic (CREATE2-style) deployment, `address(this)` is a fixed, well-known value. If Hyperbridge has integrated a state machine (real consensus client + valid state proofs obtainable) for which the DAO/governance has not yet called `NewDeployment` to register the peer gateway instance — e.g., a newly supported or low-priority chain — then any PostRequest with `source` = that state machine id and `from` = `abi.encodePacked(address(intentGateway))` will pass `authenticate()`, even though no legitimate gateway module actually exists or sent that request from that chain. This is functionally identical to the ES CVE's class of bug: an authorization check whose default/fallback path grants broader access ("documents"/actions) than the caller's actual role/registration should permit.

### Impact Explanation
An attacker who can get Hyperbridge to accept a POST request claiming `source` = an unregistered-but-supported chain (which only requires driving state on that chain and having Hyperbridge relay/verify it — no privileged access needed) can forge `RedeemEscrow`/`RefundEscrow` messages to withdraw arbitrary escrowed order funds (`_orders[commitment][token]`) on the honest gateway, as long as a matching commitment/token balance exists. This is a direct theft-of-funds vector for the intents escrow, satisfying the "concrete theft ... of funds" bar.

### Likelihood Explanation
Requires: (1) Hyperbridge to have a genuine, working consensus client for some EVM chain, and (2) governance to not yet have (or never) registered a `NewDeployment` for the intent gateway on that chain. This is plausible during chain onboarding windows, for low-traffic/legacy EVM state machines, or any chain where the gateway was deliberately never deployed but the chain remains a valid ISMP destination. The attacker only needs to dispatch a request from that chain with the crafted `from` field — no privileged relayer or admin role is needed, matching the "single relayed proof" reachability requirement.

### Recommendation
Change `instance()`'s zero-address fallback to revert (as already done in the hardened `_instance()` in `evm/src/apps/intentsv2/IntentsBase.sol`), and/or require `authenticate()`'s callers to also verify `request.source` is a chain intentionally trusted (explicit allowlist), consistent with how `NewDeployment`/`UpdateParams`/`SweepDust` require `request.source == hyperbridge()`. Align `evm/tron/contracts/apps/IntentGatewayV2.sol` with the already-patched logic in `evm/src/apps/intentsv2/IntentsBase.sol` / `ExtrinsicIntents.sol`.

### Proof of Concept
1. Hyperbridge has a consensus client for `StateMachine::Evm(X)`, but `_instances[keccak256(StateMachine::Evm(X))]` is unset (zero) on the target `IntentGatewayV2` deployed on chain `Y`.
2. Attacker drives (or waits for) Hyperbridge to record a state commitment for chain `X`, then dispatches/relays a `PostRequest` with:
   - `source = StateMachine::Evm(X)`
   - `from = abi.encodePacked(address(intentGatewayOnY))` (the known, deterministic address)
   - `to = abi.encodePacked(address(intentGatewayOnY))`
   - `body = [RedeemEscrow] ++ abi.encode(WithdrawalRequest{commitment: <victim's known commitment>, tokens: <victim's escrowed tokens>, beneficiary: attacker})`
3. Handler delivers via `dispatchIncoming` → `IntentGatewayV2.onAccept` → `authenticate(request)`:
   - `instance(request.source)` → `_instances[...]` is zero → falls back to `address(this)` = `address(intentGatewayOnY)`.
   - `module = address(bytes20(request.from))` = `address(intentGatewayOnY)`.
   - Check passes (`instance(source) == module`), bypassing the intended peer-registration authorization.
4. `withdraw(body, isRefund=false)` executes, transferring escrowed tokens to `attacker`.

**Uncertainty:** I could not fully confirm whether `evm/tron/contracts/apps/IntentGatewayV2.sol` is actively deployed/reachable in production alongside the hardened `evm/src/apps/intentsv2/` variant, or whether it is a legacy/Tron-specific fork retained for a different chain family. This affects the actual current-production reachability of the bug; if this Tron variant is deployed and live, the vulnerability is directly exploitable as described. Given index-size limits, I recommend a Devin session to check deployment records / addresses for this specific contract file across chains to confirm live exposure.
