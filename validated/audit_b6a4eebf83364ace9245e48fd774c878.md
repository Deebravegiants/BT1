### Title
Native token overpayment on `placeOrder` fee-swap is permanently stuck in the Tron IntentGatewayV2 contract - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
In the Tron variant of `IntentGatewayV2.placeOrder`, when a user pays `order.fees` with native tokens, the contract swaps `msgValue` for the fee token via `swapETHForExactTokens{value: msgValue}(...)` but never captures the returned `amounts[0]` (actual ETH spent) nor refunds the leftover ETH to the caller. Since the Uniswap router refunds unspent ETH to the caller of the swap — which is the `IntentGatewayV2` contract itself, not the end user — any amount sent above what the swap actually consumes becomes permanently trapped in the contract with no code path returning it to the user.

### Finding Description
In `placeOrder`, the fee-payment branch is:
```solidity
if (order.fees > 0) {
    // escrow fees
    address feeToken = IDispatcher(hostAddr).feeToken();
    if (msgValue > 0) {
        address uniswapV2 = IDispatcher(hostAddr).uniswapV2Router();
        address WETH = IUniswapV2Router02(uniswapV2).WETH();
        address[] memory path = new address[](2);
        path[0] = WETH;
        path[1] = IDispatcher(hostAddr).feeToken();
        IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msgValue}(
            order.fees, path, address(this), block.timestamp
        );
    } else {
        IERC20(feeToken).safeTransferFrom(msg.sender, address(this), order.fees);
    }

    _orders[commitment][TRANSACTION_FEES] = order.fees;
}

emit OrderPlaced({ ... });
``` [1](#0-0) 

The call `swapETHForExactTokens{value: msgValue}(order.fees, path, address(this), block.timestamp)` requests an *exact output* amount of fee token; the router only consumes as much ETH as required and refunds the rest to `msg.sender` of the swap call, which is the `IntentGatewayV2` contract itself (`address(this)` calling the router). The return value `amounts[0]` (actual ETH spent) is discarded entirely, and `msgValue` is never decremented by it — unlike the equivalent EVM implementation, which explicitly does:
```solidity
uint256[] memory amounts = IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msgValue}(
    order.fees, path, address(this), block.timestamp
);
msgValue -= amounts[0];
...
if (msgValue > 0) {
    _sendValue(msg.sender, msgValue);
}
``` [2](#0-1) 

The Tron file contains no such capture of `amounts[0]`, no decrement of `msgValue`, and — confirmed by inspecting the whole contract — no `_sendValue` helper, no `receive()`/`fallback()`, and no other refund path for leftover `msgValue` after `placeOrder` completes. Any native tokens sent in excess of the exact fee-swap cost (or in excess of input amounts, since inputs are handled the same way without refund) remain locked in the contract's balance indefinitely, with only governance-only `SweepDust` withdrawal (via `onAccept`) able to move them out — meaning ordinary users have no way to recover their own overpayment.

### Impact Explanation
This is a direct, permanent loss of user funds. Any front-end or integrator that (reasonably, mirroring the sibling EVM implementation's documented refund behavior) sends `msg.value` greater than the exact amount required for the fee-token swap — e.g., to buffer against price movement during the Uniswap-router exact-output swap — will have the difference permanently trapped in the `IntentGatewayV2` contract on Tron, unrecoverable by the user. This matches the "permanent freezing of funds" impact criterion, and is strictly worse than the referenced Trader Joe finding (which merely reverted the transaction) because here the transaction succeeds and funds are silently lost.

### Likelihood Explanation
Likelihood is high: `placeOrder` is a primary, unprivileged, single-transaction entry point for any user creating an intent order with a native-token fee payment. Since `order.fees` computed off-chain and the exact price impact of the Uniswap swap are not perfectly predictable at call time, any reasonable client will pad `msg.value` above the estimated fee cost (exactly as the analogous, corrected EVM `IntentGatewayV2.sol` implementation anticipates via its refund logic), making triggering this bug part of normal usage rather than an edge case.

### Recommendation
Mirror the fix already present in `evm/src/apps/IntentGatewayV2.sol`: capture the `amounts` array returned by `swapETHForExactTokens`, subtract `amounts[0]` from `msgValue`, and refund any leftover `msgValue` to `msg.sender` (via a `_sendValue`/native transfer) before `placeOrder` completes. The same fix should be verified for the input-token native leg of `placeOrder` in this file, since it likewise never refunds any leftover `msgValue`.

### Proof of Concept
1. User calls `IntentGatewayV2.placeOrder{value: X}(order, graffiti)` on Tron with `order.fees = F` (paid in native token) where `F` requires only `Y < X` wei of ETH via the Uniswap V2 exact-output swap.
2. `swapETHForExactTokens{value: X}(F, path, address(this), deadline)` executes, spending `Y` wei and refunding `X - Y` wei back to `address(this)` (the `IntentGatewayV2` contract), per Uniswap V2 router semantics.
3. `placeOrder` never reads the swap's returned `amounts[0]`, never decrements `msgValue`, and never sends any residual value back to `msg.sender`; the function simply emits `OrderPlaced` and returns.
4. The `X - Y` wei surplus is now permanently held in `IntentGatewayV2`'s balance, with no user-callable function to reclaim it — only the governance-restricted `SweepDust` `onAccept` path (see `RequestKind.SweepDust` handling) can move it, and only to a beneficiary chosen by governance, not the original user.
