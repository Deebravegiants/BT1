### Title
User-controlled swap route bytes are executed as arbitrary contract calls beneath the caller's authorization tree, letting a malicious route steal the signer's unrelated wallet funds - ([File: contracts/controller/src/strategies/swap.rs](contracts/controller/src/strategies/swap.rs))

### Summary
The PraisonAI report is a classic untrusted-input-to-execution-sink bug: attacker-influenced strings reach `subprocess.run(shell=True)` and run as arbitrary commands. The XOXNO Lending analog is the strategy-swap path: caller-supplied `swap: Bytes` is forwarded opaquely to the configured router as a `StrategyPayload`, whose instruction stream names the pool and token contracts to invoke. Neither the controller nor (per the threat model) the router keeps a venue/token allowlist, so a crafted route puts attacker-controlled third-party code on the call stack *inside* the victim's signed authorization tree. That code can call `token.transfer(victim, attacker, ...)` on any token the victim holds, and it executes because the victim signs the composed `swap_collateral`/`multiply`/`swap_debt`/`repay_debt_with_collateral` authorization root — the Soroban equivalent of `shell=True` executing metacharacter-injected input.

### Finding Description
`swap_tokens` authorizes exactly one input transfer (`authorize_transfer_as_current`) and then calls `router.execute_strategy(&controller, &amount_in, swap)` with the raw, never-decoded `swap` bytes (`contracts/controller/src/strategies/swap.rs:34-38`). The `swap` argument is a `Bytes`/`StrategySwap` supplied verbatim by the transaction submitter through `swap_collateral`, `swap_debt`, `multiply`, and `repay_debt_with_collateral` (`contracts/controller/src/lib.rs:283-303`). The router walks the payload's address registry and calls whatever pool/token contracts it names; the threat model explicitly confirms "the router calls the pool and token addresses its payload names and keeps no allowlist of them, so a route can put third-party code on the call stack below the caller's authorization" (`docs/explanation/threat-model.md:154-159`). A rogue hop contract invoked during route execution inherits the caller's authorization context and can append a `transfer(victim → attacker)` on an unrelated token as a child of the signed `swap_collateral` invocation. The harness test `simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry` demonstrates end-to-end theft of Alice's entire unrelated wallet token balance (`tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs:194-227`). The controller's measured-output and risk checks only bound the *routed* amount; they do not constrain side effects executed under the caller's auth (`docs/explanation/threat-model.md:157-161`).

### Impact Explanation
Theft of user funds. A victim who signs a composed strategy transaction carrying a poisoned route loses arbitrary balances of any token in their wallet — unbounded by the swap input, the payload `min_out`, or the post-swap LTV/health-factor gates. The committed test shows Alice's full `WALLET_BALANCE` of an unrelated token moved to the attacker while the swap itself still completes "fairly" (`FAIR_OUT_ETH` is credited).

### Likelihood Explanation
Requires victim interaction (signing a transaction built from a malicious route), matching the advisory's `UI:R`. Exploitation paths mirror the report's input paths: a compromised or malicious quote source, a phishing front-end, or a poisoned agent-generated route can embed a rogue hop without changing the quoted input/output, since the controller forwards `routeXdr` opaquely and honest simulation still records the theft as a child of the caller's own auth entry (`tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs:199-225`). Mitigation is currently pushed entirely onto clients decoding the auth tree, which wallets and most integrations do not do.

### Recommendation
Enforce the allowlist on-chain rather than relying on client-side auth-tree inspection:

1. Decode the `StrategyPayload` in the controller (or require the router to expose a `validate_route` view) and reject routes whose pool/token addresses are not registered venues or listed market assets.
2. Alternatively, have the router maintain an on-chain venue allowlist (governance-managed) and refuse any hop targeting an unlisted contract.
3. As defense in depth, document and enforce that strategy entrypoints must be signed with a strict auth tree (exactly one child transfer for the input leg), and surface recorded simulation auth trees in the SDK before signing.

### Proof of Concept
A committed harness test already proves the exploit. In `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`:

1. Alice supplies USDC and holds `WALLET_BALANCE` of an unrelated token.
2. An attacker crafts a `RoutedSwap` payload whose `hop_pool` is a `RogueHopPool` contract storing `(alice, wallet_token, attacker, amount)` (`route_through_pool_stealing`, lines 111-125).
3. Alice submits `swap_collateral(alice, account_id, USDC, amount, ETH, route)`. During route execution the rogue hop calls `wallet_token.transfer(alice, attacker, WALLET_BALANCE)`, which the host accepts as a child of Alice's signed `swap_collateral` invocation.
4. The test asserts the recorded auth tree contains the stolen transfer under Alice's root, `wallet(alice) == 0`, and `wallet(attacker) == WALLET_BALANCE` (lines 206-225).

Equivalent injection is reachable through `multiply`, `swap_debt`, and `repay_debt_with_collateral`, which all funnel the same caller-supplied `swap` bytes into `swap_tokens`.
