## Title
Silent Truncation on `U128::as_u64()` Cast Without Bounds Check in `swap_base_out` Enables Pool Drain - (File: `program/src/processor.rs`, `program/src/math.rs`)

### Summary
`process_swap_base_out` (and its duplicate `process_swap_base_out_v2` / similar variants) computes the required input amount as a `U128` value and then casts it down to `u64` with the unchecked `.as_u64()` method from the `uint` crate's `construct_uint!`-generated `U128` type. Exactly like the reported `int256 → int224` cast in the Api3 reader proxies, this is a narrowing conversion performed with no explicit range check: if the computed `U128` value exceeds `u64::MAX`, `.as_u64()` silently discards the high-order bits in a release build instead of reverting, producing an arbitrarily wrong (and possibly tiny) result.

### Finding Description
In `Processor::process_swap_base_out`, the amount a user must pay is derived like this: [1](#0-0) 

`Calculator::swap_token_amount_base_out` computes `amount_in = coin * amount_out / (pc - amount_out)` entirely in `U128` arithmetic: [2](#0-1) 

The only guard against a near-zero denominator is a check performed *after* this computation and *after* the truncating `.as_u64()` cast has already occurred: [3](#0-2) 

This check only rejects `amount_out >= total_pc_without_take_pnl`; it still allows `amount_out = total_pc_without_take_pnl - 1`, which makes the denominator `1`. With a pool holding a large `coin` balance (up to `u64::MAX`), `coin * amount_out / 1` can vastly exceed `u64::MAX` while still fitting comfortably in `U128`. The subsequent `.as_u64()` call at the end of the fee-adjustment chain: [4](#0-3) 

silently truncates this oversized `U128` to its low 64 bits instead of erroring, exactly mirroring the reported bug class ("Solidity does not revert on narrowing conversions... discard high-order bits without warning"). The identical pattern also affects the duplicate swap-out handler at the same file: [5](#0-4) 

### Impact Explanation
The truncated `swap_in_after_add_fee` value is subsequently used both for the slippage/insufficient-funds checks and for the actual SPL token transfer amount pulled from the attacker's own token account: [6](#0-5) 

Because truncation can yield an arbitrarily small `u64` (a modulo of the true, correct, huge input amount), an attacker can craft a single `SwapBaseOut` transaction requesting `amount_out` just below the pool's total (`total_pc_without_take_pnl - 1`) against a pool with a sufficiently large `coin` reserve, causing the real required input to overflow `u64`. After truncation, the attacker pays a tiny, wrapped-around `swap_in_after_add_fee` amount of `coin` while still receiving nearly the entire `pc` reserve of the pool. This is a direct, unauthorized drain of LP/pool funds and results in insolvent pool accounting — a Critical/High impact.

### Likelihood Explanation
This is reachable by any unprivileged user in a single transaction to the public `swap_base_out` (and `swap_base_out_v2`) instruction with attacker-chosen `amount_out`/`max_amount_in` parameters and no special permissions, account-binding bypass, or off-chain component required — only a pool with a sufficiently large `coin` reserve relative to `pc` (or vice versa for the `PC2Coin` direction) is needed to push the intermediate `U128` result past `u64::MAX`.

### Recommendation
Replace the unchecked `.as_u64()` calls in `Calculator::swap_token_amount_base_out` usage (and any other `U128`/`U256` → `u64` narrowing conversion in the swap path) with a checked conversion, e.g. `Calculator::to_u64()` (already defined and used elsewhere via `try_into()` which returns `AmmError::ConversionFailure` on overflow): [7](#0-6) 

so that any value exceeding `u64::MAX` causes the instruction to fail instead of silently wrapping.

### Proof of Concept
1. Create/observe a pool where `amm_coin_vault.amount` (coin reserve) is very large (near `u64::MAX`) and `total_pc_without_take_pnl` is a moderate value `P`.
2. Submit `SwapBaseOut` (or `SwapBaseOutV2`) with `swap_direction = Coin2PC`, `amount_out = P - 1` (passes the `amount_out < total_pc_without_take_pnl` check at `program/src/processor.rs:2214`), and `max_amount_in = u64::MAX`.
3. Inside `Calculator::swap_token_amount_base_out`, `denominator = pc - amount_out = 1`, so `amount_in = coin * amount_out`, a `U128` value far exceeding `u64::MAX`.
4. After the fee scale-up, `.as_u64()` at `program/src/processor.rs:2191` truncates this to a small wrapped `u64`.
5. The `user_source.amount < swap_in_after_add_fee` and slippage checks pass trivially since the truncated value is small; the attacker's token transfer of `swap_in_after_add_fee` (small) is executed while the pool sends out `amount_out ≈ P` tokens, draining the pool's `pc` reserve for far less than the correct price.

```rust
    pub fn swap_token_amount_base_out(
        amount_out: U128,
        total_pc_without_take_pnl: U128,
        total_coin_without_take_pnl: U128,
        swap_direction: SwapDirection,
    ) -> U128 {
        let amount_in;
        match swap_direction {
            SwapDirection::Coin2PC => {
                // (x + delta_x) * (y + delta_y) = x * y
                // (coin + amount_in) * (pc - amount_out) = coin * pc
                // => amount_in = coin * pc / (pc - amount_out) - coin
                // => amount_in = (coin * pc - pc * coin + amount_out * coin) / (pc - amount_out)
                // => amount_in = (amount_out * coin) / (pc - amount_out)
                let denominator = total_pc_without_take_pnl.checked_sub(amount_out).unwrap();
                amount_in = total_coin_without_take_pnl
                    .checked_mul(amount_out)
                    .unwrap()
                    .checked_ceil_div(denominator)
                    .unwrap()
            }
            SwapDirection::PC2Coin => {
                // (x + delta_x) * (y + delta_y) = x * y
                // (pc + amount_in) * (coin - amount_out) = coin * pc
                // => amount_out = coin - coin * pc / (pc + amount_in)
                // => amount_out = (coin * pc + coin * amount_in - coin * pc) / (pc + amount_in)
                // => amount_out = coin * amount_in / (pc + amount_in)

                // => amount_in = coin * pc / (coin - amount_out) - pc
                // => amount_in = (coin * pc - pc * coin + pc * amount_out) / (coin - amount_out)
                // => amount_in = (pc * amount_out) / (coin - amount_out)
                let denominator = total_coin_without_take_pnl.checked_sub(amount_out).unwrap();
                amount_in = total_pc_without_take_pnl
                    .checked_mul(amount_out)
                    .unwrap()
                    .checked_ceil_div(denominator)
                    .unwrap()
            }
        }
        return amount_in;
    }
```
