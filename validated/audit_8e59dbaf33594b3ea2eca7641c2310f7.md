### Title
Direct LT donations to a bonding-curve Pair become permanently unrecoverable after graduation — ([File: packages/contracts/src/Pair.sol])

### Summary
CVE-2019-19058 is a class of bug where a resource is allocated/acquired but a code path exists in which it is never released again, causing an unbounded, permanent accumulation of unusable/leaked resource. The alt.fun analog is state-level rather than memory-level: any LT an unprivileged address transfers directly into a launched token's `Pair` after `Router.graduate` has already been called for that token (i.e., after `Bonding._enterGraduating` → `_prepareGraduationLiquidity` has drained the pair once) can never be extracted again, because `Pair.transferAsset` is `onlyRouter`-gated and `Router`/`Bonding` never call it a second time for that pair.

### Finding Description
`Pair.transferAsset` is the only function capable of moving the `assetToken` (LT) balance out of a `Pair`, and it is restricted to `onlyRouter`: [1](#0-0) 

The protocol's own documentation confirms that this drain is invoked by `Bonding` exactly once, at graduation, and that LT donated to the pair afterward is intentionally left behind under the assumption that `Router`'s `BONDING_ROLE` access will never be exercised on that pair again: [2](#0-1) 

`_prepareGraduationLiquidity` computes `ltFromPair = assetReserve - virtualLtReserve` from the pair's *stored* reserves and drains exactly that amount via `Router.graduate`, explicitly excluding any LT that was donated by direct ERC20 transfer (which increases the pair's real balance but not its stored `assetReserve`): [3](#0-2) 

This is a deliberate, documented design choice for the *pre-graduation* window (donated LT "stays in the curve pair," reachable only via `Router`'s `BONDING_ROLE`). The problem is that once the token has fully graduated (`Lifecycle.Graduated`), `Bonding` never calls `Router.graduate` for that token again — `finalizeGraduation` only reads the cached `PendingGraduation` struct and interacts with the HyperSwap pair/`LPLock`, not the original curve `Pair`: [4](#0-3) 

Because `Pair.transferAsset` is `onlyRouter` and there is no `sweep`/`skim`/`rescue` entry point exposed on `Pair` itself, and `Bonding` has no code path that re-invokes `Router.graduate` on an already-`Graduated` token, any LT sent to the curve `Pair` — whether before phase-1 drains it, or any time after graduation completes — that is not captured by the one-shot `ltFromPair` computation is permanently locked in the `Pair` contract with no recovery mechanism.

### Impact Explanation
Any unrelated wallet, trader, or the token creator can send LT directly to a launched token's `Pair` address (a plain ERC20 `transfer`, fully in-scope per the rules) at any point — including after the token has already graduated. That LT is unbacked by any claim (no LP, no curve accounting, no `FeeVault` entry) and is unrecoverable by any function in the current contract surface, constituting a permanent freezing of trader/creator/protocol funds. This matches the "unbounded leaked resource with no release path" bug class of CVE-2019-19058, mapped onto a Solidity permanent-freeze primitive instead of kernel memory.

### Likelihood Explanation
High reachability: this requires only a single unprivileged ERC20 `transfer(pairAddress, amount)` call, no special timing, no race condition, and works against every graduated (or even non-graduated, pre-drain) `Pair`. The likelihood of *accidental* triggering is also non-trivial — any bot, aggregator, or user who mistakes the `Pair` address for the LT's `Bonding`/`Zap` deposit target, or who donates LT for auxiliary reasons (e.g., misdirected airdrops), permanently loses those funds.

### Recommendation
Add a permissionless `Pair.skimAsset(address to)` (mirroring UniswapV2's `skim`) that transfers only the excess LT balance over `assetReserve` to a caller-specified recipient, or add a `Bonding`-gated rescue function that can be called post-graduation to sweep any residual LT balance in a `Pair` (analogous to `_sweepLTToOwner` already used in `finalizeGraduation`) to the protocol owner or `FeeVault`, so that no donated/stray LT is permanently stranded regardless of the token's lifecycle stage.

### Proof of Concept
1. Creator launches `Token` via `Zap.createToken`; `Bonding.launch` deploys `Pair` for `TOKEN/LT`.
2. Trader/attacker calls `LT.transfer(pairAddress, X)` — a direct ERC20 transfer, no interaction with `Router`/`Bonding` required.
3. The token trades normally and eventually graduates: `Bonding._enterGraduating` → `_prepareGraduationLiquidity` computes `ltFromPair` from **stored** `assetReserve`, which does not include the donated `X`; `Router.graduate` drains only `ltFromPair`.
4. `Bonding.finalizeGraduation` runs, sets `Lifecycle.Graduated`, and never touches the curve `Pair` again.
5. `X` (and any further donations sent to the now-`Graduated` `Pair`) remains in `Pair`'s LT balance forever — `Pair.transferAsset` is `onlyRouter`, and no code path calls it again for this pair; `Pair` exposes no `skim`/`sweep` function of its own.
6. Result: LT is permanently frozen with no recovery path, confirmed by reading `Pair.sol`'s complete function surface (`mint`, `swap`, `transferAsset`, `transferToken`, view getters only) and `Bonding.sol`'s single-call-per-token invocation of `Router.graduate`.

- **Virtual token reserve.** At launch, `Pair.reserve0 = totalSupply (1B)` while only `curveSupply = 75%` (750M) of real tokens are transferred to the pair. The other 250M (`LP_RESERVE`) sit in `Bonding` for graduation. This extends the curve beyond the sellable supply, which is what makes dynamic LP seeding work cleanly.
- **Dual trigger.** Phase 1 fires on whichever hits first: `(storedAssetReserve - virtualLtReserve) × exchangeRate ≥ $9K` (USD, for LT pumps) or `IPair.tokenBalance() == 0` (supply, for flat/bear markets). The USD trigger reads STORED reserves so direct LT donations to the pair don't count toward the threshold; the launch-time `virtualLtReserve` is recovered on-the-fly as `Pair.k() / Token.TOTAL_SUPPLY()` (K is set once at mint and never modified by `Pair.swap`). The supply trigger reads live `tokenBalance()`, which is donation-resistant in the opposite direction: token donations only INCREASE the balance and can never satisfy `== 0`, and any donated tokens are unconditionally burned by `_prepareGraduationLiquidity`.
- **Zero-gap LP seeding.** `_prepareGraduationLiquidity` computes `ltFromPair = storedAssetReserve - virtualLtReserve` (the real LT raised by the curve, donation-immune; `virtualLtReserve` is derived from `Pair.k() / Token.TOTAL_SUPPLY()`) and `tokensForLP = ltFromPair × storedTokenReserve / storedAssetReserve` at end-of-phase-1, caching the result. Phase 2 uses the cached value verbatim, so the curve→LP price match is invariant under the tx split. Donated LT stays in the curve pair under the trust assumption that `BONDING_ROLE` is only ever held by `Bonding` and `Bonding` won't call `Router.graduate` again post-graduation.
- **Parabola invariant.** With `V_t_init = totalSupply` and `curveSupply = 75%`, the function `tokensForLP(sold) = sold·(S−sold)/S` peaks at `S/4 = LP_RESERVE`. The cap in `_prepareGraduationLiquidity` is defensive — it can never bind in normal operation.

    function finalizeGraduation(
        address tokenAddress
    ) external nonReentrant {
        BondingStorage storage $ = _s();
        TokenInfo storage info = $.tokenInfo[tokenAddress];
        if (info.lifecycle != Lifecycle.Graduating) revert NotGraduating();

        address lt = info.ltAddress;
        PendingGraduation memory p = $.pendingGraduation[tokenAddress];

        // Anything in this contract beyond `p.ltFromPair` belongs to a
        // concurrent graduation on the same LT (Phase 1 transferred it
        // via `Router.graduate`) or to stray dust. Either way it is
        // off-limits to this graduation's deposit and sweep — see
        // `_routerDepositAndDispose` and `_sweepLTToOwner`.
        // Saturating subtract: a balance below `p.ltFromPair` shouldn't
        // be reachable in normal operation, but we keep finalize from
        // bricking on a Panic if any future code path or non-canonical
        // LT briefly violates the invariant.
        uint256 ltBalance = IERC20(lt).balanceOf(address(this));
        uint256 protectedLT = ltBalance > p.ltFromPair ? ltBalance - p.ltFromPair : 0;

        address lpPair = _ensureUniswapV2Pair(tokenAddress, lt);
        uint256 liquidity = _seedUniswapV2Direct(tokenAddress, lt, lpPair, p.tokensForLP, p.ltFromPair, protectedLT);

        _sweepLTToOwner(lt, protectedLT);

        info.lifecycle = Lifecycle.Graduated;
        $.graduatedPair[tokenAddress] = lpPair;
        delete $.pendingGraduation[tokenAddress];

        LPLock($.lpLock).recordLock(tokenAddress, lpPair, liquidity);

        emit TokenGraduated(tokenAddress, lpPair, liquidity, p.tokensForLP, p.lpBurned, p.unsoldBurned);
    }
