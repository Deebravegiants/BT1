### Title
PoA Bridge status/hash misreport for batched same-asset withdrawals - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal` resolves the on-chain destination hash/status for a specific withdrawal by matching only on `assetId`, ignoring the `index` (and destination address/amount) that uniquely identifies which withdrawal in a batch is being queried. When a caller batches two or more withdrawals of the same token (e.g., two USDT withdrawals to different destination addresses/amounts in one NEAR transaction), the SDK can report one withdrawal's completion status/txHash for a different withdrawal.

### Finding Description
`findMatchingWithdrawal` selects the first entry in the (explicitly documented as "unsorted") API response whose `nep141:{near_token_id}` equals the requested `assetId`: [1](#0-0) 

`describeWithdrawal` uses this match directly to build the `WithdrawalStatus`, which is surfaced by `watchWithdrawal`/`createWithdrawalCompletionPromises` per-index to the caller as the authoritative destination transaction hash for that specific withdrawal: [2](#0-1) 

The `WithdrawalIdentifier.index` is set per withdrawal in a batch by `createWithdrawalIdentifier`, so the SDK's public contract implies each index maps to a distinct, correctly-attributed on-chain result: [3](#0-2) 

However, when two withdrawals in the same batch use the same `assetId` (same token) but different destination addresses/amounts, `findMatchingWithdrawal` cannot distinguish between them — it returns whichever matching entry appears first in the (unsorted) list, for every index that shares that assetId. This is explicitly acknowledged in code comments as an unhandled case, not something the caller is warned about or blocked from doing: [4](#0-3) 

I was unable to find, in `sdk.ts`, any guard rejecting or de-duplicating batched withdrawals that share the same `assetId` before dispatching them to `PoaBridge` (my last grep for such a guard in `sdk.ts` returned no matches before I ran out of iterations to confirm further), so this path appears reachable through the SDK's normal public batch withdrawal API (`signAndSendWithdrawalIntent`/`waitForWithdrawalCompletion`/`createWithdrawalCompletionPromises` with an array of `withdrawalParams`).

### Impact Explanation
This breaks the equality "status/txHash reported for withdrawal at index N == the actual on-chain outcome for withdrawal N." An integrator polling per-index completion promises (as the SDK's own batch API and README encourage, e.g. `promises[0]`/`promises[1]` handled independently) could receive the wrong destination transaction hash for a given withdrawal — e.g., crediting/marking withdrawal #0 as complete using the destination hash that actually belongs to withdrawal #1. This matches the allowed High-impact class: "a status or hash misreport making an integrator credit or refund twice," since an integrator relying on this per-index result to reconcile ledgers could double-credit one destination and never correctly attribute the other.

### Likelihood Explanation
No malicious actor is required — this triggers under ordinary use whenever a legitimate integrator batches two or more withdrawals of the same underlying token via the PoA route (a supported, documented SDK feature — batch processing is advertised in the README). The bug is latent and silent (no error thrown), so an integrator would not know their withdrawal tracking is misattributed until funds/statuses appear inconsistent.

### Recommendation
In `findMatchingWithdrawal` (both in `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts` and `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts`), disambiguate withdrawals sharing the same `assetId` by additionally matching on `amount` and `destinationAddress` (or, if the POA API exposes ordering/index guarantees, by index), and throw/return `pending`/an explicit unsupported error rather than silently returning an ambiguous match when multiple same-asset withdrawals are present in a batch. Alternatively, have `PoaBridge.supports`/`createWithdrawalIntents` reject batches containing duplicate `assetId`s until the API/matching logic supports disambiguation.

### Proof of Concept
1. Call `sdk.signAndSendWithdrawalIntent` (or `processWithdrawal`) with `withdrawalParams` array containing two PoA-route withdrawals of `nep141:usdt.tether-token.near`: withdrawal A `amount=100, destinationAddress=addrA`, withdrawal B `amount=50, destinationAddress=addrB`.
2. Call `sdk.createWithdrawalCompletionPromises` with the same array and the resulting `intentTx`.
3. Internally, `watchWithdrawal` calls `PoaBridge.describeWithdrawal` for index 0 and index 1, both with the same `assetId`.
4. `findMatchingWithdrawal` (packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts:418-427) returns the same/first matching withdrawal entry for both calls when the POA API response order does not correspond to submission order (explicitly stated as "unsorted" in the code comment at line 318), causing `promises[0]` to potentially resolve with the destination tx hash that actually belongs to withdrawal B, and vice versa.

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

	withdrawals: types.WithdrawalStatusResponseOk["result"]["withdrawals"],
	criteria: WithdrawalCriteria,

	| types.WithdrawalStatusResponseOk["result"]["withdrawals"][number]
	| undefined {
	return withdrawals.find(
		(w) => `nep141:${w.data.near_token_id}` === criteria.assetId,
