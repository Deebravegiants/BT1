### Title
Reachable panic (integer underflow) in `Processor::calc_take_pnl` from an attacker-skewed vault ratio, permanently freezing Deposit/Withdraw/WithdrawPnl — (File: `program/src/processor.rs`)

### Summary
`Processor::calc_take_pnl` computes `x2`/`y2` — the pool reserves "after PnL is taken" — from the *current* vault balances and the *stale* `TargetOrders.calc_pnl_x/calc_pnl_y` checkpoint, then subtracts them from the current values with bare `.unwrap()` instead of using `ok_or`/`checked_sub` with error propagation like the sibling function `calc_total_without_take_pnl_no_orderbook` does. An unprivileged actor can skew the vault token ratio with an ordinary SPL token transfer directly into `amm_coin_vault`/`amm_pc_vault` (no AMM instruction required), which can make the computed `x2`/`y2` exceed the current `x1`/`y1`, causing the subtraction to underflow and panic.

### Finding Description
`calc_take_pnl` guards against decreasing invariant with a k-check: [1](#0-0) 
but that check only requires `current_k = x1*y1 >= last_k = calc_pnl_x*calc_pnl_y`; it does not constrain the *ratio* `x1/y1`. `x2` is then derived assuming the last-k invariant holds at the *current* price ratio: [2](#0-1) 
and immediately subtracted from the current reserves without a checked/guarded path: [3](#0-2) 

Because `x2 = sqrt(last_x * last_y * current_x / current_y)`, if an attacker sends an outsized amount of one token directly into `amm_pc_vault` or `amm_coin_vault` (a plain, permissionless SPL `Transfer` — no AMM program instruction or signer authority beyond the sender's own token account is required), the ratio `current_x/current_y` can be pushed far away from the ratio baked into `calc_pnl_x/calc_pnl_y`, while still trivially satisfying `current_k >= last_k` (adding tokens only increases `x1*y1`). This can make `x2 > x1` (or `y2 > y1`), so `x1.checked_sub(x2).unwrap()` (or the `y` counterpart) hits `None` and panics.

This is the same bug class as the reported `gix-packetline` issue: an unguarded subtraction (`d.len() - 1` there, `checked_sub(...).unwrap()` here) that can underflow on attacker-influenced input, causing a process/transaction abort. Here the "attacker-influenced input" is the vault token balances, which are readable and directly manipulable by any permissionless token transfer to the vault's associated token account — the vault accounts are ordinary SPL token accounts owned by the AMM's PDA authority and accept incoming transfers from anyone.

`calc_take_pnl` is invoked from every state-mutating LP-facing path except swap:
- Deposit: [4](#0-3) 
- Withdraw: [5](#0-4) 
- WithdrawPnl: [6](#0-5) 

### Impact Explanation
Because the underlying condition (a skewed vault-balance ratio versus the stored `calc_pnl_x/calc_pnl_y` checkpoint) is state that persists on-chain in the vault's token balance and is not correctable by any AMM instruction (there is no instruction that lets anyone "return" tokens sent directly to the vault, and depositors/withdrawers cannot rebalance the ratio back precisely), once the panic condition is triggered it reproduces on every subsequent call to Deposit, Withdraw, and WithdrawPnl for that pool. This effectively freezes LP deposits, LP withdrawals, and PnL withdrawal for the affected pool — a permanent freezing of user/LP funds, consistent with the required impact bar (this is not a transient reverted-transaction inconvenience; the pool becomes permanently unable to process these instructions until the ratio drifts back, which is not attacker/anyone-controllable once tokens have been sent to the vault).

### Likelihood Explanation
The trigger requires no privileged signer, no malicious validator, and no off-chain component: any unprivileged actor can submit a single SPL `Transfer`/`TransferChecked` instruction moving tokens into `amm_coin_vault` or `amm_pc_vault` (both are public token accounts, addresses are derivable/known from `AmmInfo`). The magnitude required depends on the pool's existing reserves and `calc_pnl_x/calc_pnl_y` checkpoint, but for any pool with meaningfully asymmetric current PnL accrual, a comparatively modest one-sided transfer can push the ratio far enough to make `x2 > x1` or `y2 > y1`.

### Recommendation
Replace the unchecked `.unwrap()` calls in `calc_take_pnl` (lines 213–214, and cascading `checked_sub(...).unwrap()` calls at lines 1359-1360, 1369-1370, 1531-1532, 1819-1828, 1829-1838) with `checked_sub(...).ok_or(AmmError::CalcPnlError)?` (mirroring the pattern already used in `Calculator::calc_total_without_take_pnl_no_orderbook`), so that a ratio that would produce a negative PnL delta is rejected with a program error instead of panicking, and ideally re-derive `x2`/`y2` using a formula that is provably bounded by `x1`/`y1` under the existing k-check.

### Proof of Concept
1. Create a pool via `Initialize2` and perform normal `Deposit`/`Withdraw`/`WithdrawPnl` activity so `TargetOrders.calc_pnl_x`/`calc_pnl_y` reflect a non-trivial checkpoint (as in the existing test `test_calc_take_pnl` / `test_calc_pnl_precision` at [7](#0-6) ).
2. As an unprivileged actor, submit an SPL token transfer sending a large amount of only one of the two tokens (e.g., the `pc` token) directly into `amm_pc_vault`, without going through any AMM instruction.
3. Call `Withdraw` (or `Deposit`/`WithdrawPnl`). `calc_total_without_take_pnl_no_orderbook` reads the now-skewed vault balance into `total_pc_without_take_pnl`, which is normalized into `x1` at [8](#0-7)  and passed into `calc_take_pnl`; the k-check at lines 190–193 passes trivially (k only increased), but `x2` computed at lines 199–208 from the skewed ratio exceeds `x1`, so `x1.checked_sub(x2).unwrap()` at line 213 panics, aborting the transaction — and every future Deposit/Withdraw/WithdrawPnl on the pool panics identically as long as the vault ratio remains skewed.
