### Title
Webhook `shop` domain is trusted for tenant routing but is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` exposes a `shop` accessor read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, but the HMAC signature computed by `Utils::HmacValidator.validate` only covers the raw request body. `Registry.process` validates the HMAC and then forwards the unauthenticated `shop` header value directly to the host app's handler as the tenant identity key.

### Finding Description
`Utils::HmacValidator.validate` computes and compares the signature using `verifiable_query.to_signable_string`, and for webhook requests that is defined as: [1](#0-0) 

which returns only `@raw_body`. The `shop` field, however, is read independently from headers and never enters the signable string: [2](#0-1) 

`Registry.process` validates the HMAC of the body, then builds `WebhookMetadata` using `request.shop` — the header value that was never bound to the signature — and hands it to the app's registered handler as the tenant/shop identity: [3](#0-2) 

The identity binding that should hold is:
`HMAC-authenticated bytes (raw body) == bytes used to select the tenant (shop header)`

but in this implementation:
`HMAC-authenticated bytes (raw body) ≠ shop header used for tenant routing`

Because a single app-level `api_secret_key` is shared across every shop that installs the app, any merchant that has legitimately installed the app receives real webhooks with a valid HMAC computed over their own body. That same merchant can capture a `(body, hmac)` pair from a webhook Shopify sent to their own shop and replay it to the app's webhook endpoint while substituting the `shopify-shop-domain` header for a different (victim) shop. `Utils::HmacValidator.validate` will still report success, because the signature never depended on the shop header, and `Registry.process` will dispatch the (attacker-controlled) body to the handler tagged with the victim's `shop` value.

### Impact Explanation
This breaks the shop/tenant identity boundary that multi-tenant Shopify apps rely on: a handler that uses `WebhookMetadata#shop` to decide which merchant's session/access token/data store to write to can be made to attribute attacker-supplied webhook data to a victim shop, or vice versa — a cross-tenant data injection/confusion primitive that stems entirely from this gem's `Request`/`HmacValidator`/`Registry` design (the `shop` accessor and the `to_signable_string` scope), not from host-application misuse. Per the impact classification given, this constitutes cross-tenant access, which is Critical.

### Likelihood Explanation
Exploitation requires only that the attacker be a legitimate but malicious merchant of the same app (an "unprivileged internet user" relative to any other tenant) — they need no knowledge of `api_secret_key`, no access token, and no privileged account beyond their own store's install, which is the normal barrier to entry for any multi-tenant Shopify app. Capturing a valid `(body, hmac)` pair from their own webhook traffic and replaying it with a modified shop header is trivial once observed.

### Recommendation
Bind the shop identity to the signed payload instead of trusting an unauthenticated header for routing:
- Include the `shop-domain` (and ideally `webhook-id`/`topic`) in the HMAC signable string in `ShopifyAPI::Webhooks::Request#to_signable_string`, matching what is actually authenticated, or
- Have `Registry.process`/`WebhookHandler` cross-check the header-derived `shop` against a shop value independently verified for the session/topic before dispatching, and document clearly that `WebhookMetadata#shop` is not covered by the HMAC so host apps do not treat it as an authenticated tenant key without extra verification.

### Proof of Concept
1. App has two merchant tenants: `attacker-shop.myshopify.com` (installed by the attacker) and `victim-shop.myshopify.com`.
2. Shopify sends a legitimate webhook to the app for `attacker-shop.myshopify.com`:
   - Headers: `shopify-shop-domain: attacker-shop.myshopify.com`, `shopify-hmac-sha256: <valid HMAC of raw_body>`
   - Body: `{"id": 123, ...attacker-controlled resource...}` (attacker can influence some webhook bodies, e.g. by creating orders/products in their own shop before the webhook fires).
3. Attacker replays the exact same `raw_body` and `hmac` header to the app's webhook endpoint but changes only `shopify-shop-domain` to `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` — this succeeds because validation only hashes `raw_body` [4](#0-3) , and then dispatches `WebhookMetadata.new(topic:, shop: request.shop, body: request.parsed_body, ...)` with `shop == "victim-shop.myshopify.com"` even though the body content originated from the attacker's own shop.
5. Any host handler that uses `data.shop` to select the victim's session/access token/database record will now operate on attacker-supplied data under the victim's identity.
