### Title
Token exchange accepts non-Admin (e.g. checkout/customer) session tokens because `iss` is never validated - ([File: lib/shopify_api/auth/token_exchange.rb])

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` validates a session token only by checking its signature and its `aud` claim (via `JwtPayload`), then uses the token's `dest` claim as the shop to exchange for a full merchant access token. It never verifies that the token's `iss` claim identifies it as an **Admin** session token, even though `JwtPayload` already has the logic to make that distinction (`admin_session_token?`) but never applies it in the token-exchange path.

### Finding Description
`ShopifyAPI::Auth::JwtPayload#initialize` only enforces one identity binding on the incoming session token: [1](#0-0) 

```
raise ShopifyAPI::Errors::InvalidJwtTokenError,
  "Session token had invalid API key" unless @aud == Context.api_key
```

That check only proves the token was minted for *this app* — it says nothing about which surface/audience issued it. Shopify issues structurally similar, correctly-signed session tokens for different trust contexts, distinguished by `iss` — e.g. `".../admin"` for the embedded Admin app, vs `".../checkouts"` for checkout UI extensions (visible in the gem's own tests): [2](#0-1) 

The class does compute this distinction internally: [3](#0-2) 

```
def admin_session_token?
  @iss.end_with?("/admin")
end
```

…but `admin_session_token?` is `private` and is used **only** to gate `shopify_user_id`. It is never consulted by `TokenExchange.exchange_token`, which blindly trusts `jwt_payload.shop` (derived from `dest`) for *any* token that merely has the right `aud`: [4](#0-3) 

The identity-binding equality that should hold is:
`token.iss (audience/context that issued it) == "Admin session for shop"`
but the code only checks:
`token.aud == Context.api_key`

A checkout UI extension token — handed to buyer-facing, less-trusted JS running in the storefront — is signed with the same app secret and has the same `aud`, so it satisfies every check `TokenExchange.exchange_token` performs, letting it be exchanged as if it were the merchant's own Admin session, in contrast to `migrate_to_expiring_token`, which at least sanitizes the `shop` value through `Utils::ShopValidator.sanitize!` before use — a control absent from `exchange_token`.

### Impact Explanation
If an app forwards a session token it received from any context to `TokenExchange.exchange_token` without itself re-checking `iss`/context (which the gem gives it no first-class way to do, since the check is private), a buyer/customer-scoped checkout token can be laundered into a full merchant offline (or online) access token for the shop — a scope/authentication-boundary bypass that hands admin-level API credentials to a lower-privilege actor. This matches the "scope or expiry check that answers permissively" / "JWT claim trusted without being bound" class of issue.

### Likelihood Explanation
Exploitation requires an app to accept a session token from a non-Admin surface (e.g. a checkout UI extension) and pass it into `exchange_token`, which is a realistic integration mistake given the gem exposes no public helper to distinguish token types and the private `admin_session_token?` method is invisible to consumers.

### Recommendation
Expose/enforce a public "admin session token" check in `JwtPayload` and require `TokenExchange.exchange_token` to raise `InvalidJwtTokenError` unless `jwt_payload` is confirmed to be an Admin-issued session token (`iss` ends with `/admin`), mirroring the shop sanitization already done in `migrate_to_expiring_token`.

### Proof of Concept
1. Attacker/customer obtains a valid checkout UI extension session token for `shop.myshopify.com` (issued by Shopify to the storefront JS, `iss: "https://shop.myshopify.io/checkouts"`, `aud: <app's client_id>`).
2. That token (or a value the app naively forwards) is passed to:
```ruby
ShopifyAPI::Auth::TokenExchange.exchange_token(
  session_token: checkout_extension_token,
  requested_token_type: ShopifyAPI::Auth::TokenExchange::RequestedTokenType::OFFLINE_ACCESS_TOKEN,
)
```
3. `JwtPayload.new` accepts it (signature + `aud` match), `dest_shop` is extracted, and the gem performs a full token-exchange request to `/admin/oauth/access_token` for that shop — with no library-level check that the presented token was actually an Admin session token as documented in `docs/usage/oauth.md`.
