### Title
Unrestricted arbitrary external call in `EmporiumUpgradeable.runAction` lets any prover drain protocol-held ERC20 balances via `approve` - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`EmporiumUpgradeable.runAction` executes a list of attacker-supplied `EmporiumOperation`s (`endpoint`, `callData`, `value`) taken straight from `circomData.externalActionData.externalActionMetadata`. When `stack.signerAddress == address(0)`, `verifyWallet` skips **all** signature verification and the operations are dispatched directly with `op.endpoint.call{value: op.value}(op.callData)`, i.e. executed in the Emporium contract's own context/own balance, with no restriction other than blocking two specific selectors. [1](#0-0) [2](#0-1) 

### Finding Description
`runAction` is only gated by `onlyAllowedRecipient`, which just checks `msg.sender` is the whitelisted `Hinkal` contract — any unprivileged EOA that submits a normal (self-authored) `transact()` proof for its own shielded balance can reach this code path. [3](#0-2) 

Inside `runAction`, when `stack.signerAddress == address(0)` (the "no wallet" stateless case), `verifyWallet` only checks/consumes `usedMessages[circomData.emporiumMessage]` and returns immediately — it never validates an EIP-712 signature over the `ops` array: [4](#0-3) 

Because `stack.signerAddress == address(0)`, the loop always falls into "CASE 2: Stateless Interaction", which performs `op.endpoint.call{value: op.value}(op.callData)` directly as the Emporium contract, with the only filter being a block on the `callHinkalWallet`/`doSendToRelay` selectors: [5](#0-4) 

`op.endpoint` and `op.callData` are fully attacker-chosen. Nothing prevents `op.endpoint` from being an arbitrary ERC20 token and `op.callData` from encoding `approve(attacker, type(uint256).max)`. This is the same class of bug as the `RollerPeriphery.approve()` issue: an unrestricted `approve` call executed by a contract that can legitimately hold ERC20 balances that don't belong to the caller.

The code explicitly acknowledges that the Emporium contract can hold residual token balances across calls — the comment on the balance-check loop states this is expected ("the only case when balanceChange can be < 0, when there were some funds on emporium before the call"): [6](#0-5) 

Additionally, the stateless path is also used to pay relay fees directly out of Emporium's own balance via `sendToRelay` when `signerAddress == address(0)`: [7](#0-6) 

Any of: relay-fee remainders, dust from prior sweeps/rounding, ETH held via the `receive()` function, or tokens transiently sitting in Emporium mid multi-op flow, thus become approvable by an unrelated attacker. This approval by itself does not move balance in the same transaction (so the post-call balance-delta check in `runAction`/`handleOut` is not triggered), but the attacker can, in a second unrelated transaction, call `transferFrom(emporium, attacker, amount)` directly on the token to drain the approved balance — an asset movement never authorised by the actual owner of those funds (another user, the relay, or the protocol).

### Impact Explanation
This breaks the equality that only value the caller legitimately deposited into Emporium in the same transaction should ever leave the contract. It allows theft of protocol/relay-fee balances or any other ERC20 balance transiently held by the Emporium contract, by an attacker who never contributed those funds and never obtained an authorizing signature from any signer. This matches the "theft or permanent freezing of protocol/relay fees" / "unauthorised asset movement" High-impact category.

### Likelihood Explanation
Likelihood depends on the Emporium contract actually holding a non-zero residual ERC20/ETH balance at the time of the attack (e.g., dust, relay fee overpayment, or funds from a multi-op flow not yet fully swept). Given the code comments explicitly anticipate this scenario ("there were some funds on emporium before the call"), such states are expected to occur in normal operation, making the attack practically exploitable whenever any balance is present, requiring only a normal, self-funded `transact()` call — no privileged role, signer key, or admin action needed.

### Recommendation
Require signature verification (or an equivalent authorization/allowlist for `op.endpoint`) even when `stack.signerAddress == address(0)`, or restrict "stateless" `op.endpoint` calls to a fixed, protocol-controlled allowlist of routers/tokens (similar to how `LifiExternalAction` only ever approves a fixed immutable `router` address) rather than allowing arbitrary attacker-chosen `endpoint`/`callData` combinations to execute directly from the Emporium contract's own balance.

### Proof of Concept
1. Attacker (any user) waits for/observes a non-zero ERC20 balance sitting on the `EmporiumUpgradeable` contract (e.g., relay-fee dust from a previous transaction, or a race with another in-flight multi-op EmporiumStack).
2. Attacker builds a normal, self-consistent Hinkal `transact()` proof for their own shielded UTXOs, targeting the Emporium external action, with `circomData.externalActionData.externalActionMetadata` encoding an `EmporiumStack` where:
   - `signerAddress = address(0)`
   - `ops = [{ endpoint: <victim ERC20 token>, invokeWallet: false, value: 0, callData: abi.encodeWithSelector(IERC20.approve.selector, attackerAddress, type(uint256).max) }]`
3. `Hinkal.transact()` verifies the attacker's own valid proof and calls `_externalTransact` → `EmporiumUpgradeable.runAction`.
4. `verifyWallet` returns early (no signature check) because `signerAddress == address(0)`; the loop executes CASE 2, calling `token.approve(attacker, max)` from the Emporium contract.
5. Balance-delta check passes trivially since `approve` doesn't change token balance.
6. In a separate, ordinary transaction, attacker calls `token.transferFrom(emporiumAddress, attacker, residualBalance)` directly, draining funds that were never theirs.
