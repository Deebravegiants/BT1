### Title
Permanent freezing of a token creator's accrued USDC fees when their address is blacklisted by USDC - (File: `packages/contracts/src/FeeVault.sol`)

### Summary
`FeeVault.claim()` pays out a creator's entire pooled `creatorBalance[msg.sender]` in a single `safeTransfer` call. Because the vault's reserve asset is USDC — a blacklistable token by design (Circle can freeze any address) — a creator whose address is later added to the USDC blacklist can never withdraw their accrued balance again. The funds remain permanently locked in the vault's `creatorBalance` mapping with no admin override, redirect, or rescue path, mirroring the root cause of the reported OrderBook issue (a forced, unconditional transfer to a fixed address that a blacklistable token can indefinitely block).

### Finding Description
`FeeVault.claim()`:
```solidity
function claim() external nonReentrant returns (uint256 amount) {
    FeeVaultStorage storage $ = _s();
    amount = $.creatorBalance[msg.sender];
    if (amount == 0) revert NothingToClaim();
    $.creatorBalance[msg.sender] = 0;
    $.totalAccruedCreator -= amount;
    $.usdc.safeTransfer(msg.sender, amount);
    emit CreatorFeesClaimed(msg.sender, amount);
}
``` [1](#0-0) 

The transfer target is hard-coded to `msg.sender` (the creator) and there is no fallback path, alternate recipient, or admin-controlled rescue for a `creatorBalance` entry that can no longer be paid out. `Zap._collectFee` funds the vault and calls `FeeVault.accrue`, crediting `creatorBalance[creator]` on every buy/sell for that creator's token(s): [2](#0-1) 

`Bonding.transferCreator` lets the current creator hand off the role (and thus future fee attribution) to any address of their choosing, with no validation that the address can actually receive USDC: [3](#0-2) 

Once a creator's address is added to USDC's blacklist (by Circle, independent of the protocol), `IERC20(usdc).transfer/safeTransfer` to that address reverts unconditionally — the exact "blocked" failure mode from the external report. `claim()` will then always revert for that creator, and the `creatorBalance[creator]` entry sits untouched in storage indefinitely: `accrue()`'s O(1) underfund check (`usdc.balanceOf(vault) >= totalAccruedCreator + protocolBalance`) still passes because the USDC physically remains in the vault, so the protocol keeps operating normally for everyone else — but that specific creator's funds are frozen forever with no code path to recover them. [4](#0-3) 

Unlike the OrderBook bug, this does not brick a *shared* resource used by other parties (each creator's balance and claim are independent), so it does not block other creators' or the protocol's claims. It is, however, the same root cause pattern acknowledged as in-scope by the rules: a forced/unconditional transfer to a party that a blacklistable reserve-asset token (USDC) can permanently block, with no alternate delivery mechanism — resulting in permanent freezing of creator funds.

### Impact Explanation
Any creator balance accrued via `FeeVault.accrue` becomes permanently unclaimable once the associated creator address is blacklisted by USDC (Circle can do this at will for AML/sanctions/compliance reasons, unrelated to the creator's on-chain behavior). There is no owner-callable function to redirect or force-claim a stuck `creatorBalance` to a different address — `setFeeTo` only affects the `protocolBalance`/`feeTo`, not per-creator balances. This is a permanent freezing of creator funds, which is explicitly a valid impact category (theft/permanent freezing of creator funds).

### Likelihood Explanation
The trigger event — USDC blacklisting a specific address — is outside the protocol's control and not something an unprivileged attacker can force onto an arbitrary victim on demand. However, it is a realistic operational risk given the protocol's fee asset is USDC by design (`docs/contracts-scope.md`: "All fees are charged by Zap in USDC"), and every token creator is exposed to it simply by launching a token and accruing fees — no privileged action or special conditions are required to become vulnerable; the only requirement is holding creator status on a token that has accrued nonzero fees. `Bonding.transferCreator` additionally allows any creator, without validation, to route future fee attribution to an address that may already be (or later become) blacklisted, compounding the exposure. [3](#0-2) 

### Recommendation
Add a rescue/redirect path for stuck creator balances, mirroring the spirit of the OrderBook fix (avoid unconditional forced transfers to a potentially-frozen address):
- Allow a creator (or, if the creator is provably unreachable, the owner) to redirect an existing `creatorBalance[creator]` to a new address via a `reassignCreatorBalance`-style function, analogous to `transferCreator` but acting directly on the accrued USDC balance rather than only future attribution.
- Alternatively, support a `claimTo(address recipient)` variant so a creator whose own address becomes blacklisted can still direct payout to a different address they control, without needing `Bonding.transferCreator` to be called first (which does not affect already-accrued `creatorBalance`).
- Consider validating that a `newCreator` passed to `Bonding.transferCreator` is not a known-blacklisted USDC address before accepting the transfer, where feasible.

### Proof of Concept
1. `creator` launches a token via `Zap.createToken`, and `Bonding.tokenInfo(token).creator == creator`.
2. Multiple trades occur through `Zap.buy` / `Zap.sell`; each calls `_collectFee` → `FeeVault.accrue(token, creator, creatorShare, protocolShare, isBuy)`, growing `creatorBalance[creator]` [2](#0-1) .
3. USDC's issuer (Circle) adds `creator` to its blacklist (exactly as modeled in the repo's own `MockUSDC`/`StdCheats` blacklist test fixtures) [5](#0-4) .
4. `creator` calls `FeeVault.claim()`. `$.usdc.safeTransfer(msg.sender, amount)` reverts because `msg.sender` is blacklisted [1](#0-0) .
5. `creatorBalance[creator]` remains nonzero forever; there is no other function in `FeeVault.sol` that can move or pay out this specific balance to any other address. The USDC backing it stays locked in the vault indefinitely — permanent freezing of creator funds.

    function accrue(
        address token,
        address creator,
        uint256 creatorAmount,
        uint256 protocolAmount,
        bool isBuy
    ) external onlyDepositor {
        FeeVaultStorage storage $ = _s();
        if (creatorAmount > 0) {
            if (creator == address(0)) revert ZeroAddress();
            $.creatorBalance[creator] += creatorAmount;
            $.totalAccruedCreator += creatorAmount;
            $.lifetimeCreatorEarned[creator] += creatorAmount;
        }
        if (protocolAmount > 0) {
            $.protocolBalance += protocolAmount;
            $.lifetimeProtocolEarned += protocolAmount;
        }
        if ($.usdc.balanceOf(address(this)) < $.totalAccruedCreator + $.protocolBalance) {
            revert UnderfundedAccrual();
        }
        emit FeeAccrued(token, creator, creatorAmount, protocolAmount, isBuy);
    }
