### Title
Webhook shop-domain/topic headers are not covered by HMAC, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, and `ShopifyAPI::Utils::HmacValidator.validate` computes/checks the HMAC only over that body. The `shop`, `topic`, and `webhook_id` fields — all read directly from unauthenticated HTTP headers — are never part of the signed material, yet they are trusted as the tenant/topic identity passed to the host application's webhook handler.

### Finding Description
`Request#hmac` reads the `X-Shopify-Hmac-Sha256` header and `Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, and `#webhook_id` are all pulled straight from HTTP headers with no cryptographic binding: [2](#0-1) 

`HmacValidator.validate` verifies `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)`, i.e. it only authenticates the body bytes, not any header field: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` and `request.topic` (both header-derived) to route the payload to the application's handler: [4](#0-3) 

This breaks the binding: `shop authenticated (bytes covered by HMAC) == shop used as tenant key (WebhookMetadata.shop)`. Since Shopify's HMAC only covers the request body, any party capable of relaying a legitimate captured webhook body (e.g., a shared/misconfigured relay, a compromised intermediary, or — depending on deployment — anyone able to POST to the app's public webhook endpoint with a previously observed valid `(body, hmac)` pair) can present it with an arbitrary `X-Shopify-Shop-Domain` header. The gem will accept it as valid and dispatch it to the application's handler as if it originated from a different shop, because `sanitize_shop_domain`/`ShopValidator` is never invoked on the webhook `shop` value either.

### Impact Explanation
An attacker who can obtain one valid `(body, hmac)` pair (e.g., by triggering a webhook on their own store, or intercepting one in a non-TLS-protected hop) can relabel it with a victim shop's domain in the `X-Shopify-Shop-Domain` header. `Registry.process` will pass HMAC validation (since the body is unchanged) and hand the payload to the application's handler tagged as belonging to the victim shop via `WebhookMetadata#shop`. Depending on how the host app uses this shop value (e.g., to key data deletion, redact operations, or state updates for `customers/redact`, `shop/redact`, GDPR mandatory topics), this is a cross-tenant data integrity/confidentiality issue — the classic "field acted on but not covered by the HMAC" bug class.

### Likelihood Explanation
This requires the attacker to have obtained at least one legitimately-signed webhook body/HMAC pair. This is realistic in shared multi-tenant deployments where all shops share the same `client_secret` (as is standard for public Shopify apps) — a merchant/attacker who installs the app on their own store legitimately receives correctly-signed webhooks and can then replay the exact body with a forged `shop-domain` header against the same public endpoint to impersonate another tenant.

### Recommendation
Bind the `shop` (and ideally `topic`) header values into the HMAC-signed material, or require the host application to separately validate `request.shop` against `ShopValidator.sanitize!` and cross-check it against the shop associated with the resolved session/registration before trusting it as a tenant key. At minimum, document that `request.shop` is unauthenticated and must not be used as a sole tenant identifier.

### Proof of Concept
1. App installs on `attacker-shop.myshopify.com` and legitimately receives a `customers/redact` webhook with body `B` and valid header `X-Shopify-Hmac-Sha256: H = HMAC(client_secret, B)`.
2. Attacker replays a POST to the app's webhook endpoint with the same body `B`, same `H`, but `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `HmacValidator.validate` in [5](#0-4)  succeeds because it only checks the body.
4. `Registry.process` in [6](#0-5)  dispatches `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", ...)` to the app's handler, which acts on the victim tenant using attacker-supplied data.
