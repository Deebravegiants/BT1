Audit Report

## Title
Username Enumeration via Distinct Login Error Messages in `SessionsController.Create` - (File: `core/web/sessions_controller.go`)

## Summary
The `/sessions` login endpoint forwards raw, distinguishable error strings from `CreateSession` directly to unauthenticated clients, allowing an attacker to determine whether a given email corresponds to an existing Chainlink node account by comparing the "user not found" error against the "Invalid password" / "invalid email" error text.

## Finding Description
`SessionsController.Create` passes any error returned by `AuthenticationProvider().CreateSession` straight into `jsonAPIError(c, http.StatusUnauthorized, err)` [1](#0-0) . Since these errors are plain `error` values (not `*models.JSONAPIErrors`), `jsonAPIError` serializes `err.Error()` verbatim into the response JSON via `models.NewJSONAPIErrorsWith(err.Error())` [2](#0-1) .

In the local-auth provider, `CreateSession` calls `FindUser`, and if the lookup fails (email doesn't exist), the underlying SQL error is returned unmodified; if the email exists but the password check fails, the constant string `"Invalid password"` is returned instead — two textually distinguishable outcomes [3](#0-2) . The LDAP and OIDC providers exhibit the identical pattern with `"invalid email"` vs. `"invalid password"` strings in their `localLoginFallback` functions.

The `/sessions` endpoint requires no authentication — it sits behind only a rate limiter (`unauth.POST("/sessions", sc.Create)`), so any unauthenticated client can send arbitrary login attempts and observe the returned error text [4](#0-3) . No existing sanitization layer normalizes these error strings before they reach the client.

## Impact Explanation
This maps to CWE-204 (Observable Response Discrepancy) enabling account/username enumeration. An unauthenticated attacker can systematically determine which emails are registered as node operator accounts on a target Chainlink node, which facilitates targeted credential stuffing/password guessing against confirmed valid accounts — a legitimate precursor to node API authentication bypass, which is an in-scope impact category (node API authentication).

## Likelihood Explanation
High reachability and low attacker cost: the `/sessions` endpoint is unauthenticated by design (it's the login endpoint) and only rate-limited, not blocked, so an attacker can repeatedly probe it with different email addresses and directly read the differing error text in the HTTP response body without any special privileges, credentials, or host access.

## Recommendation
Normalize all `CreateSession` failure paths (in `core/sessions/localauth/orm.go`, `core/sessions/ldapauth/ldap.go`, and `core/sessions/oidcauth/oidc.go`) to return one generic error (e.g., "invalid email or password") for both the not-found and wrong-password cases, and/or have `SessionsController.Create` map any `CreateSession` error to a fixed generic message before calling `jsonAPIError`, rather than leaking `err.Error()` from the provider. Keep the detailed, distinguishing reason only in the existing audit log calls (`audit.AuthLoginFailedEmail` / `audit.AuthLoginFailedPassword`).

## Proof of Concept
1. `POST /sessions` with `{"email":"nonexistent@example.com","password":"anything"}` against a running node — response body contains the raw SQL/user-not-found error text propagated from `FindUser`.
2. `POST /sessions` with `{"email":"<known-existing-email>","password":"wrongpassword"}` — response body contains `"Invalid password"`.
3. Diff the two JSON response bodies: distinct text confirms account existence for `<known-existing-email>` without needing any valid credential, host, or admin access. This can be automated as a Go integration test against `SessionsController.Create` using `httptest`, seeding one known user and one non-existent email, and asserting the two returned error strings differ.

func jsonAPIError(c *gin.Context, statusCode int, err error) {
	_ = c.Error(err).SetType(gin.ErrorTypePublic)
	var jsonErr *models.JSONAPIErrors
	if errors.As(err, &jsonErr) {
		c.JSON(statusCode, jsonErr)
		return
	}
	c.JSON(statusCode, models.NewJSONAPIErrorsWith(err.Error()))
}
```

func (o *orm) CreateSession(ctx context.Context, sr sessions.SessionRequest) (string, error) {
	user, err := o.FindUser(ctx, sr.Email)
	if err != nil {
		return "", err
	}
	lggr := o.lggr.With("user", user.Email)
	lggr.Debugw("Found user")

	// Do email and password check first to prevent extra database look up
	// for MFA tokens leaking if an account has MFA tokens or not.
	if !constantTimeEmailCompare(strings.ToLower(sr.Email), strings.ToLower(user.Email)) {
		o.auditLogger.Audit(audit.AuthLoginFailedEmail, map[string]any{"email": sr.Email})
		return "", pkgerrors.New("Invalid email")
	}

	if !utils.CheckPasswordHash(sr.Password, string(user.HashedPassword)) {
		o.auditLogger.Audit(audit.AuthLoginFailedPassword, map[string]any{"email": sr.Email})
		return "", pkgerrors.New("Invalid password")
	}
```

func sessionRoutes(app chainlink.Application, r *gin.RouterGroup) {
	config := app.GetConfig()
	rl := config.WebServer().RateLimit()
	unauth := r.Group("/", rateLimiter(
		rl.UnauthenticatedPeriod(),
		rl.Unauthenticated(),
	))
	sc := NewSessionsController(app)
	unauth.POST("/sessions", sc.Create)
	auth := r.Group("/", auth.Authenticate(app.AuthenticationProvider(), auth.AuthenticateBySession))
	auth.DELETE("/sessions", sc.Destroy)
}
