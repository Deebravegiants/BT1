### Title
Webhook shop identity is not bound to the HMAC-authenticated payload, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies a webhook's `HMAC` over the raw request body only, then trusts the `shop` field—read from an unauthenticated header—to identify which merchant/tenant the webhook belongs to. Because the app's webhook signing secret (`api_secret_key`) is shared across every shop that installs the app, any shop that legitimately receives webhooks can capture a valid `(raw_body, hmac)` pair and replay it to the app's webhook endpoint while forging the `shop-domain` header to impersonate a different, victim shop.

### Finding Description
`Registry.process` validates the webhook exclusively via `Utils::HmacValidator.validate(request)`, and that validator checks the HMAC against `request.to_signable_string`, which is defined as just the raw body: [1](#0-0) 

The `shop` accessor used to identify the tenant is read straight from the `x-shopify-shop-domain` / `shopify-shop-domain` header and is never included in the signed payload: [2](#0-1) 

`Registry.process` only asserts the HMAC is valid, then immediately hands `request.shop` to the app's handler as the trusted tenant identifier: [3](#0-2) 

The `HmacValidator` itself only ever compares `computed_signature` (over the signable string, i.e. the body) against the received signature—`shop` never enters this computation: [4](#0-3) 

This breaks the required identity binding: `shop_authenticated_by_hmac == shop_used_by_handler`. In truth, `shop_authenticated_by_hmac = ∅` (the HMAC authenticates only "some webhook body signed with this app's client secret"), while `shop_used_by_handler = header_value` (fully attacker-controlled once they can supply *any* valid `(body, hmac)` pair). Because `api_secret_key` is one shared secret for the whole app across all installing shops (not shop-specific), an unprivileged internet user who installs the app on their own shop receives real webhooks from Shopify signed with this same secret. They can then replay that exact `raw_body` + `hmac` to the app's webhook endpoint while substituting the `shop-domain` header for a victim shop's domain. `HmacValidator.validate` still succeeds (it never looks at the header), so `Registry.process` calls the handler with `shop: <victim-shop>`, causing the host application to attribute attacker-controlled webhook data (order state, `app/uninstalled`, GDPR data-request payloads, etc.) to a tenant the attacker does not own.

### Impact Explanation
This is a cross-tenant data/identity confusion: an attacker can make the app process forged events "as" another merchant's shop while presenting an HMAC that only proves the body originated from Shopify's delivery for *some* shop of the same app, not the claimed one. Depending on how the host app uses `WebhookMetadata#shop` (e.g., to look up sessions, revoke access tokens on `app/uninstalled`, or write per-tenant data), this can lead to cross-tenant access or corruption of another merchant's data—matching the "Critical: cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires only that the attacker be able to install the target app on a shop they control (a normal, unprivileged flow for any public/listed app) and capture one webhook delivery, then replay it with a modified header to the app's public webhook endpoint. No access token, `client_secret`, or privileged account is needed—only observation of a webhook payload+HMAC that Shopify itself delivered to the attacker's own shop.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the value that is cryptographically verified, not just the raw body. Concretely, `Utils::VerifiableQuery#to_signable_string` for webhook `Request` should incorporate the `shop-domain` header (and other identifying headers) into the signed string used in `HmacValidator.validate`, or `Registry.process` should independently confirm the `shop` header against an out-of-band source of truth (e.g., cross-check against the session/store the app has on record for the topic) before trusting it. At minimum, document and enforce that `request.shop` must not be trusted for tenant routing unless it is included in the HMAC-verified payload.

### Proof of Concept
1. Attacker creates/controls `attacker-shop.myshopify.com` and installs the target Shopify app (a normal, unprivileged action).
2. Shopify delivers a legitimate webhook to the app's endpoint for `attacker-shop.myshopify.com`, e.g. body `{"id":123, ...}` with headers:
   - `x-shopify-shop-domain: attacker-shop.myshopify.com`
   - `x-shopify-hmac-sha256: <valid HMAC over the body, computed with the app's shared client secret>`
3. Attacker intercepts/logs this raw body and HMAC (they see their own webhook traffic, e.g. via a proxy in front of their own receiving endpoint, or from app debug logs of their own installation).
4. Attacker resends the identical body and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `Registry.process` calls `Utils::HmacValidator.validate(request)`—which only checks body+HMAC—and it passes. [3](#0-2) 
6. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and the attacker-controlled body, causing the host app to act as though this event came from the victim's store.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end
