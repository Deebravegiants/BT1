### Title
Webhook `shop-domain` Header Not Bound to HMAC Signature Enables Cross-Tenant Webhook Spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while the `shop` (from the `x-shopify-shop-domain`/`shopify-shop-domain` header) and `topic`/`webhook_id`/`api_version` fields are read directly from unauthenticated headers and never included in the HMAC-covered string. [1](#0-0)  `Registry.process` validates the HMAC over that same body-only string and then forwards `request.shop` straight into `WebhookMetadata`, which the host app's handler uses to identify the tenant. [2](#0-1) 

### Finding Description
The binding that should hold is: `hmac_signature == HMAC(secret, bytes_that_include_shop)`. In this gem it instead holds: `hmac_signature == HMAC(secret, raw_body_only)`, i.e., `shop` is verified against nothing. `HmacValidator.validate` calls `verifiable_query.to_signable_string`, which for `Webhooks::Request` is just `@raw_body`. [3](#0-2) [4](#0-3)  The `shop`, `topic`, `webhook_id`, and `api_version` values are all read verbatim from HTTP headers supplied by whoever calls the app's webhook endpoint, with no cryptographic tie to the signed payload. [5](#0-4) 

`Registry.process` only checks HMAC validity, then immediately trusts `request.shop` (and `request.topic`, `request.webhook_id`, `request.api_version`) to build `WebhookMetadata` passed to the app's handler: [6](#0-5) 

Because a legitimate merchant/attacker who installs the app on their own shop will receive genuinely HMAC-signed webhooks (valid signature computed only over the body), they can capture one such request and replay it to the app's webhook endpoint while swapping the `x-shopify-shop-domain` header to a victim shop's domain (and/or the topic/webhook-id headers). The signature check still passes because it never covered those header values, and the host application — following this gem's own `Registry.process`/`WebhookMetadata` contract — will process the forged webhook as if it originated from the victim shop.

### Impact Explanation
This breaks the shop-identity binding relied on by any host application dispatching business logic (e.g., updating orders, fulfilling records, deactivating shop data on `shop/redact`) keyed off `WebhookMetadata#shop`. An attacker with a legitimate, low-privilege installation on their own store can forge webhook events attributed to an arbitrary other merchant, i.e., cross-tenant data/event injection using only their own valid app installation — no access token, secret, or elevated privilege required beyond running the app on their own shop and replaying an HTTP request with modified headers.

### Likelihood Explanation
Likelihood is high for any app that installs `Registry.process`/`WebhookMetadata#shop` as documented and trusts the resulting `shop` value to select which tenant's session/data to touch, since:
- No secret material is needed by the attacker; they only need one real signed webhook payload from their own shop.
- The header-vs-body split is baked into the library's own `Request` class, so every consumer of this gem inherits the gap unless the host separately validates `shop` against another authenticated source (which the gem does not require or provide).

### Recommendation
Bind the tenant-identifying and dispatch fields into the signed payload used for verification. At minimum, include `shop`, `topic`, `webhook_id`, and `api_version` in `to_signable_string` (or otherwise cryptographically bind them, e.g., verify them against a fixed session-linked shop parameter after HMAC validation, and reject if the header no longer matches an expected/registered shop for the caller). Shopify's dispatch-time HMAC covers only the body, so the safer, gem-level fix is to require callers to supply and independently verify `shop` (e.g., against a known session store) before trusting `WebhookMetadata#shop`, and to document explicitly that header fields are unauthenticated.

### Proof of Concept
1. App developer installs their app on `attacker-shop.myshopify.com` and registers a webhook handler for, e.g., `customers/data_request`.
2. Shopify sends a legitimately signed webhook to the app's endpoint:
   ```
   x-shopify-topic: customers/data_request
   x-shopify-hmac-sha256: <valid HMAC over raw_body>
   x-shopify-shop-domain: attacker-shop.myshopify.com
   x-shopify-webhook-id: <id>
   Body: {...}
   ```
3. Attacker captures this raw request, then replays it to the same endpoint but changes only the header:
   ```
   x-shopify-shop-domain: victim-shop.myshopify.com
   ```
   leaving `raw_body` and `x-shopify-hmac-sha256` untouched.
4. `ShopifyAPI::Utils::HmacValidator.validate` recomputes HMAC over `raw_body` only (`Request#to_signable_string`) — it matches, since the body is unchanged. [3](#0-2) 
5. `Registry.process` raises no error and calls the app's handler with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)`. [6](#0-5) 
6. The host application processes the forged event as belonging to `victim-shop.myshopify.com`, despite the actual signed content originating from the attacker's own shop.
