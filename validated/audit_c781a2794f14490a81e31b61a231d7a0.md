### Title
Webhook `shop`/`topic` identity is not covered by the HMAC, allowing cross-tenant/topic spoofing of processed webhooks - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by verifying an HMAC over the raw request body, then trusts the `shop` and `topic` values taken from unauthenticated HTTP headers to route and label the payload for the host application. Because the HMAC never binds those header values, a party who has obtained one valid `(body, hmac)` pair for the app (e.g., from a webhook delivered to their own installed shop) can replay that exact body with a different `shop-domain`/`topic` header and the HMAC check still passes.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and compares it with `verifiable_query.hmac`: [1](#0-0) 

For webhook requests, `hmac` is read from the `hmac-sha256` header and `to_signable_string` returns only `@raw_body` — it does not include `topic`, `shop`, `api_version`, or `webhook_id`: [2](#0-1) 

`shop`, `topic`, `api_version`, and `webhook_id` are all pulled directly from HTTP headers with no cryptographic tie to the HMAC-verified body: [3](#0-2) 

`Registry.process` validates the HMAC (over the body only) and then immediately hands the *header-derived* `shop`/`topic`/`webhook_id`/`api_version` to the app's registered handler as authenticated metadata: [4](#0-3) 

This is the exact bug-class analog described in the report: the field that binds the request to a tenant/identity (`shop`, and here also `topic`) is *acted upon* by the library but *not covered by the HMAC* that is supposed to authenticate the request — i.e. `shop_used_by_handler != shop_covered_by_hmac`. Any entity that legitimately receives one webhook delivery from Shopify for the shared app (e.g., an attacker who installs the same app on their own store, which is normal and unprivileged) obtains a valid `(raw_body, hmac)` pair signed with the app's `api_secret_key`. They can then replay that identical body to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` and `x-shopify-topic` headers to arbitrary values, and `HmacValidator.validate` will still return `true`, because the signature never depended on those headers.

### Impact Explanation
This breaks the tenant/topic identity binding relied upon by any host application built on this gem. `Registry.process` calls the handler with a forged `shop` value and/or forged `topic`, which the host app will treat as verified because it passed HMAC validation: [5](#0-4) 

A host application that persists or acts on `data.shop` as the tenant key (the documented and expected usage pattern for `WebhookMetadata`) can have data attributed to, or actions taken against, the wrong tenant — this is a cross-tenant integrity/identity-binding failure. It can also be used to make a payload that was legitimately signed for one topic (e.g. `orders/create`) be processed under a different, more sensitive topic (e.g. a mandatory GDPR topic like `customers/data_request` or `shop/redact`) if the handler logic branches only on the trusted-looking `topic` field. No `api_secret_key`, access token, or privileged account is required to mount this — any unprivileged party who is or becomes an installed shop for the same app can harvest a valid `(body, hmac)` pair themselves and replay it with altered headers.

### Likelihood Explanation
Likelihood is limited to callers of `ShopifyAPI::Webhooks::Registry.process` who use `WebhookMetadata#shop`/`#topic` as authenticated identity (this is the documented usage — see `test/webhooks/registry_test.rb`, which asserts `data.shop`/`data.topic` are simply passed through from request headers). The prerequisite — obtaining one valid body+HMAC pair — is trivially met by installing the app on any test shop (an ordinary, unprivileged action), since the same app secret signs webhooks for every shop.

### Recommendation
Bind `shop`, `topic`, `api_version`, and `webhook_id` into the signed material, or otherwise cryptographically tie them to the verified body (e.g., include them in `to_signable_string`, or require the host app to independently confirm `shop`/`topic` against out-of-band trusted state such as the topic/shop the app actually registered/expects for that specific webhook subscription) before treating them as authenticated in `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (normal, unprivileged onboarding).
2. Shopify delivers a legitimate webhook to the attacker's endpoint, e.g. body `{"id":1}` with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: orders/create`, `x-shopify-hmac-sha256: <valid HMAC of body>`.
3. Attacker captures this exact `(body, hmac)` pair.
4. Attacker resends the identical raw body and HMAC to the app's public webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` and/or `x-shopify-topic: customers/data_request`.
5. `HmacValidator.validate` recomputes the HMAC over the (unchanged) raw body and it matches — validation succeeds (`lib/shopify_api/utils/hmac_validator.rb:26-31`, `lib/shopify_api/webhooks/request.rb:35-38`).
6. `Registry.process` invokes the registered handler with `WebhookMetadata.new(topic: "customers/data_request", shop: "victim-shop.myshopify.com", body: {...}, ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), even though none of that metadata was actually vouched for by Shopify for the victim shop or that topic.
