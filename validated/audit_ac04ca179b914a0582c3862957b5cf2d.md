### Title
Webhook HMAC validation does not bind the `shop` header, allowing cross-tenant shop spoofing on webhook delivery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by verifying the HMAC of the raw request body against the app's shared `api_secret_key`. The `shop` (tenant identity) that is handed to the app's webhook handler is read from the `x-shopify-shop-domain` / `shopify-shop-domain` header, which is never included in the signed material. This breaks the binding `shop authenticated == shop acted upon`: any two (body, HMAC) pairs the attacker can legitimately obtain from Shopify for their own store can be replayed against the same public webhook endpoint with the `shop` header swapped to a different (victim) merchant, and the handler will process the attacker's body content as if it belonged to the victim tenant.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`, and `#shop` is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header: [1](#0-0) [2](#0-1) 

`Utils::HmacValidator.validate` (and `validate_signature`) computes/compares the HMAC only over `verifiable_query.to_signable_string`, i.e. only the raw body — the `shop` value is never part of the signed message: [3](#0-2) 

`Registry.process` treats a passing HMAC check as sufficient authentication and then forwards the unauthenticated `request.shop` value straight to the handler as the tenant identity: [4](#0-3) 

Because the `api_secret_key` is a single value shared by the app for **all** shops that installed it (not per-shop), any merchant that installs the app (an "unprivileged internet user" with respect to any other merchant's tenant) can:
1. Trigger a real Shopify event on their own store whose body content they control (e.g. a product/order field), causing Shopify to deliver a genuine `(raw_body, hmac)` pair signed with the app's `api_secret_key`.
2. Replay that exact `raw_body` and `hmac` to the app's public webhook endpoint, but substitute the `shopify-shop-domain` header with a different, victim merchant's shop domain.
3. `HmacValidator.validate` still returns `true` because it only checks the (unmodified) body/HMAC pair — it has no knowledge of, or dependency on, the shop header.
4. `Registry.process` calls the handler with `WebhookMetadata.new(shop: <victim-shop>, body: <attacker-controlled>, ...)`, so the handler executes tenant-scoped logic (e.g. looking up the victim's stored session/access token and applying attacker-controlled data) under the wrong tenant's identity.

### Impact Explanation
This is a cross-tenant identity confusion: the equality that should hold — `shop authenticated via HMAC == shop the handler acts on` — does not hold, because `shop` is outside the signed payload. Any app built on this gem's webhook handling that uses `WebhookMetadata#shop` to select per-tenant state (session/access-token lookup, per-shop database rows, etc.) can be made to attribute attacker-controlled body content to an arbitrary victim shop, enabling cross-tenant data corruption/access using only a legitimately-obtained signature from the attacker's own, unprivileged installation.

### Likelihood Explanation
Webhook endpoints are public HTTP(S) endpoints by design, reachable by any internet client. Obtaining one valid `(raw_body, hmac)` pair only requires installing the target app on any shop (the normal, permission-less merchant workflow) and generating an event with attacker-influenced body fields — no access to `api_secret_key`, access tokens, or victim credentials is needed. Swapping the `shop` header on replay is trivial since the request is a plain HTTP request the attacker fully controls, and the library performs no cross-check between the header and the signed content.

### Recommendation
Include the shop-identifying header (or the shop itself) in the HMAC-signed payload (e.g., incorporate `shop`/`webhook_id`/`topic` into the signable string, or use a per-shop derived key), or otherwise cryptographically bind the `shop` value the handler receives to the same signed message that the body-HMAC covers. At minimum, document this as a requirement for host applications and reject requests where the header-derived shop cannot be independently corroborated (e.g., verifying the shop exists in the app's known-installed-shops list before trusting header-derived tenant identity).

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com`.
2. Attacker performs an action that causes Shopify to send a webhook (e.g. `products/update`) with a body they control (e.g., a product title set to arbitrary JSON-safe content). Shopify computes and sends a legitimate `x-shopify-hmac-sha256` for this exact body using the app's `api_secret_key`.
3. Attacker captures the raw body + HMAC value from this delivery (or a proxy/log they control).
4. Attacker sends a new POST request directly to the app's public webhook endpoint with:
   - Same raw body and same `x-shopify-hmac-sha256` value.
   - `x-shopify-shop-domain: victim-shop.myshopify.com` (any known/target merchant using the same app).
5. `ShopifyAPI::Utils::HmacValidator.validate` returns `true` (body/HMAC match), and `ShopifyAPI::Webhooks::Registry.process` invokes the app's handler with `shop: "victim-shop.myshopify.com"` and the attacker-controlled body, despite this request never having originated from, or being validated against, `victim-shop.myshopify.com`.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
