### Title
Webhook `shop-domain` (and `topic`/`webhook-id`) header is trusted for tenant identity but is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, then hands the *unauthenticated* `shop-domain` header straight to the app's handler as the tenant identifier. This mirrors the RewardDistributor pattern: a privileged action (dispatching data "on behalf of shop X") is gated by a check (`Utils::HmacValidator.validate`) that does not actually cover the field the rest of the code relies on (`request.shop`).

### Finding Description
`Webhooks::Request#to_signable_string` returns only the raw JSON body: [1](#0-0) 

The `shop`, `topic`, `api_version`, and `webhook_id` accessors are read directly from HTTP headers, which are never part of the signed material: [2](#0-1) [3](#0-2) 

`Registry.process` validates only the HMAC (i.e., only the body) and then immediately trusts `request.shop` as the tenant identity passed to the handler: [4](#0-3) 

`HmacValidator.validate` computes the HMAC using `Context.api_secret_key`/`Context.old_api_secret_key`, which is the **app-wide** client secret, identical for every shop that has installed the app - it is not a per-shop secret: [5](#0-4) 

Equality being broken: the code treats `hmac_valid(body) == authenticated_as(shop_header)`, but the actual invariant only proves `hmac_valid(body) == signed_by_app_secret(body)`. Nothing binds `shop-domain` to the body or to the specific installation that produced the signature.

### Impact Explanation
Because the HMAC secret is shared across every shop that installs the same app, any unprivileged merchant who installs the app on their own store receives genuinely-signed webhook deliveries for their own shop (same body/HMAC scheme as everyone else). By capturing one such delivery and re-POSTing it to the app's webhook endpoint with the `x-shopify-shop-domain` (or `shopify-shop-domain`) header changed to a victim shop's domain, the attacker produces a request that still passes `Utils::HmacValidator.validate` (since only the body, which the attacker legitimately possesses a valid signature for, is checked) while `WebhookMetadata#shop` reports the victim's domain to the handler. Any host application that uses `data.shop` from the handler to look up per-tenant state, write data, or trigger side effects (the intended and documented usage pattern) can be made to attribute attacker-controlled/replayed webhook content to a different tenant - a cross-tenant data-integrity/confidentiality break driven entirely by this gem's own signature-verification/data-exposure boundary in `Registry.process` and `Webhooks::Request`.

### Likelihood Explanation
Exploitation requires only the ability to install the target app on a shop the attacker controls (a normal, unprivileged step for any public/multi-tenant Shopify app) and the ability to send an HTTP POST to the app's public webhook endpoint with attacker-chosen headers - no access to `api_secret_key`, access tokens, or TLS interception is needed. The gem itself performs no cross-check between the header-derived `shop` and the HMAC-signed body, so the weakness is exercised purely through this library's public `Registry.process`/`Webhooks::Request` API as documented.

### Recommendation
Bind the tenant identity to the signed material instead of trusting an unauthenticated header:
- Include the `shop-domain` (and ideally `topic`/`webhook-id`) in the signable string used for HMAC verification, or
- Require callers of `Registry.process` to supply the expected shop (e.g., from the URL route or a pre-verified session) and assert it matches `request.shop` before dispatching to the handler, or
- Document/enforce that host applications must independently confirm `webhook_id` uniqueness and shop legitimacy (e.g., against a known-installed-shops list) before trusting `data.shop`, and add this check directly in `Registry.process` rather than leaving it solely to downstream handlers.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`.
2. Attacker triggers an event (e.g., creates an order) causing Shopify to send a legitimately HMAC-signed webhook to the app's endpoint:
   ```
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid HMAC over raw body>
   x-shopify-shop-domain: attacker-shop.myshopify.com
   x-shopify-webhook-id: ...
   Body: {"id": 1, ...attacker-controlled order payload...}
   ```
3. Attacker replays this exact request to the same endpoint, only changing the header:
   ```
   x-shopify-shop-domain: victim-shop.myshopify.com
   ```
4. `Utils::HmacValidator.validate` still returns `true` (body/HMAC pair unchanged, and the secret is shared across all shops of the app): [6](#0-5) 
5. `Registry.process` dispatches to the handler with `WebhookMetadata.new(... shop: request.shop ...)`, where `request.shop` now equals `"victim-shop.myshopify.com"`: [7](#0-6) 
6. The host application's handler processes attacker-controlled data under the victim shop's tenant identity.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
