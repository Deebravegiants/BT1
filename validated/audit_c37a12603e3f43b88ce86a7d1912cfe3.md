### Title
Stale user QR-code/session authorization reused for final signup enrollment without re-validation - (File: `src/plans/mod.rs`)

### Summary
`Orb::do_signup` validates the user's QR-code/session exactly once, early in the flow, via `verify_user_qr_code` → `backend::user_status::request` [1](#0-0) . The resulting `UserData` (identity commitment, self-custody public key, backend encryption keys, `orb_relay_app_id`) is then carried unchanged through biometric capture, the biometric pipeline, and fraud detection — all of which can take a significant amount of wall-clock time — before being used to build and submit the Personal Custody Package and the final signup request via `enroll_user::Plan::run` [2](#0-1) . Unlike the operator QR-code, which has an explicit `operator_qr_expiration_time` staleness check enforced in `scan_remaining_qr_codes` [3](#0-2) , there is no equivalent freshness/eligibility re-check for the user QR-code/session before the enrollment request is finally sent.

### Finding Description
The bug-class analog to M-23 is: an eligibility/authorization decision is made once ("is this position still an ADL candidate" / "is this user-session still valid") and then acted upon later without re-verifying that the condition still holds at execution time. In `orb-core`, `verify_user_qr_code` performs the authoritative backend check of user session validity and fetches session-bound cryptographic material (`backend_iris_public_key`, `self_custody_user_public_key`, `id_commitment`, etc.) once, immediately after the user QR-code scan [4](#0-3) . This `UserData` is then threaded through `do_signup` and used at the very end of the flow, well after biometric capture (which itself has multi-second timeouts and retries) and the biometric pipeline/fraud-detection stages, to build the PCP and finally call `enroll_user::Plan::run`, which posts to `/api/v2/signups/{signup_id}` [5](#0-4) . No second call to `backend::user_status::request` or any other freshness check occurs between the initial QR validation and the final signup submission.

### Impact Explanation
If the user's session becomes invalid between QR-scan-time and enrollment-time (e.g., the app-side session expires, the user cancels/restarts on another device or orb, or backend-side session state changes), the orb will still complete the signup using now-stale keys/identity-commitment data, potentially resulting in a signup being attributed to session data that the backend no longer considers authoritative. This mirrors the ADL-candidate staleness problem: the decision ("this session/position is currently eligible") is correct only at decision time, but the action is taken using data captured at that earlier point, not re-validated at execution time.

### Likelihood Explanation
The window between user QR-code validation and enrollment is non-trivial: it spans face detection, an explicit 3-second sleep, biometric capture, biometric pipeline processing, and fraud detection [6](#0-5) , all of which involve device/network variability and can extend meaningfully in practice, giving ample opportunity for the user/session state to change on the backend side. The existence of an explicit expiration mechanism for the *operator* QR-code, but not for the *user* QR-code/session, indicates the asymmetry is a genuine gap rather than an intentional design choice.

### Recommendation
Add a freshness/expiry check analogous to `operator_qr_expiration_time` for the validated user session: either re-invoke `backend::user_status::request` shortly before submitting `signup_post::request`/`enroll_user::Plan::run`, or reject the signup with a signup-fail reason if elapsed time since `verify_user_qr_code` exceeds a bounded threshold, so that stale session data is never used to submit a finalized signup.

### Proof of Concept
1. Start a signup; the orb scans and validates the user QR-code via `verify_user_qr_code`, capturing `UserData` (keys, `id_commitment`, `orb_relay_app_id`).
2. Before the flow reaches `enroll_user::Plan::run`, the backend-side session referenced by that QR-code becomes invalid (e.g., expires or is superseded) — there is no code path in `do_signup` (`src/plans/mod.rs:491-663`) that re-checks this.
3. The orb proceeds through biometric capture/pipeline/fraud-detection using the stale `UserData` and submits the final signup via `enroll_user::Plan::run`, which will succeed or fail purely based on backend-side idempotent/duplicate checks rather than an explicit re-validation of user-session eligibility at the orb layer.
