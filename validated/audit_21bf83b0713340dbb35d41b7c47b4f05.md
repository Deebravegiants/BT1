### Title
Crowdloan verifier signature replay across dissolved-and-recreated funds due to signature payload lacking fund instance binding - (File: polkadot/runtime/common/src/crowdloan/mod.rs)

### Summary
The verifier signature checked in `Pallet::do_contribute` only binds `(index, &who, old_balance, value)` where `index` is the `ParaId` and `old_balance` is the contributor's current running total in the *current* fund's child trie. Because a crowdloan for a given `ParaId` can be dissolved and re-created, and the new fund's child-trie contribution total for any account always starts at `0`, a signature previously issued for a contributor's first contribution (`old_balance == 0`) to an earlier fund incarnation for the same `ParaId` remains valid and replayable against a newly created fund for the same `ParaId` that reuses the same verifier key.

### Finding Description
`do_contribute` computes the signed payload as: [1](#0-0) 

Note that the payload is `(index, &who, old_balance, value)` — it does not include `fund.fund_index`, a nonce, or any per-fund-lifecycle identifier. `old_balance` is read from the child trie keyed by `fund.fund_index` via `contribution_get`: [2](#0-1) 

`fund_index` is a monotonically increasing counter guarded by `checked_add`, so it does not literally "wrap around" (the `create` extrinsic would instead return `Error::<T>::Overflow`): [3](#0-2) 

However, wraparound is not required for the replay: every time a fund for the same `ParaId` is created, `create` allocates a fresh `fund_index` and thus a fresh, empty child trie (`Self::id_from_index(fund_index)` differs per fund): [4](#0-3) 

So for the *new* fund, any contributor's `old_balance` starts back at `0`, identical to the state when they made their very first contribution to the *old* fund. If the fund manager reuses the same `verifier` key when recreating the crowdloan for the same `ParaId` (a common, legitimate pattern for a KYC provider tied to a project), an attacker who obtained a valid `MultiSignature` for `(index, who, 0, value)` from the verifier for their first contribution to the old fund can resubmit `contribute(index, value, Some(sig))` against the new fund and pass the check in lines 784-790, because `old_balance` again equals `0` and `index`/`value` are unchanged.

The `create` extrinsic and `dissolve` extrinsic are both reachable by ordinary signed accounts (`ensure_signed`), gated only by being the para manager / meeting dissolve conditions, not by root/governance: [5](#0-4) [6](#0-5) 

No additional check exists anywhere in `do_contribute` that ties the signature to a specific fund incarnation (e.g., `fund_index`, `fund.deposit`-derived nonce, or block-height binding), so once the state coincidentally (or intentionally, by contributing the same amount as before) matches, the "one-time" verifier authorization is not one-time across the crowdloan's lifecycle — it is one-time only per `(index, old_balance, value)` tuple, which is reused whenever the fund is torn down and rebuilt.

### Impact Explanation
A contributor can bypass the KYC verifier gate for a freshly created crowdloan of the same `ParaId` by replaying an old, previously-authorized signature, provided the new fund's verifier key is unchanged and the contribution amount matches an old `old_balance`/`value` pair (trivially satisfiable for a contributor's very first contribution, which is always `old_balance = 0`). This lets an unauthorized/unapproved actor (from the verifier's perspective, this replay was never separately approved for the new fund) contribute to the new crowdloan without fresh sign-off, undermining the verifier's intended per-fund KYC control. Funds are still fully backed (the contributor still transfers real balance), so this is a KYC/authorization-bypass issue rather than a fund-draining exploit.

### Likelihood Explanation
Requires: (1) a `ParaId` crowdloan is dissolved and a new crowdloan created for the same `ParaId`, (2) the new fund reuses the same `verifier` `MultiSigner`, and (3) the attacker retains an old valid signature for `old_balance = 0` (their first contribution amount to the old fund) or any state where `old_balance` coincidentally matches between the two funds. Condition (1) is a normal operational flow (failed auctions are commonly retried), and reusing the same verifier key across a project's re-attempts is a natural and likely administrative choice, making this feasible without any privileged/root action beyond normal parachain-manager operations.

### Recommendation
Bind the signed payload to the specific fund instance, e.g., include `fund.fund_index` (or another per-creation nonce) in the payload signed/verified in `do_contribute`, so a signature is scoped to exactly one fund lifecycle and cannot be replayed after `dissolve`/`create` recreates a fund for the same `ParaId`.

### Proof of Concept
Rust unit test in `polkadot/runtime/common/src/crowdloan/mod.rs` test module:
1. Create fund #1 for `ParaId(1)` with `verifier = V`.
2. Have `V` sign payload `(ParaId(1), who, 0, value)` → `sig`.
3. Call `contribute(ParaId(1), value, Some(sig))` from `who` — assert success, `old_balance` becomes `value`.
4. Refund/kill contributions and `dissolve(ParaId(1))` (satisfy `raised == 0` and permission conditions).
5. Recreate fund #2 for the same `ParaId(1)` reusing verifier `V`.
6. Replay `contribute(ParaId(1), value, Some(sig))` from `who` using the same old `sig` — assert it currently **succeeds** (demonstrating the bug), whereas the expected/fixed behavior should return `Error::<T>::InvalidSignature` because the signature was scoped to fund #1's lifecycle, not fund #2's.

			origin: OriginFor<T>,
			#[pallet::compact] index: ParaId,
			#[pallet::compact] cap: BalanceOf<T>,
			#[pallet::compact] first_period: LeasePeriodOf<T>,
			#[pallet::compact] last_period: LeasePeriodOf<T>,
			#[pallet::compact] end: BlockNumberFor<T>,
			verifier: Option<MultiSigner>,
		) -> DispatchResult {
			let depositor = ensure_signed(origin)?;
			let now = frame_system::Pallet::<T>::block_number();

			ensure!(first_period <= last_period, Error::<T>::LastPeriodBeforeFirstPeriod);
			let last_period_limit = first_period
				.checked_add(&((SlotRange::LEASE_PERIODS_PER_SLOT as u32) - 1).into())
				.ok_or(Error::<T>::FirstPeriodTooFarInFuture)?;
			ensure!(last_period <= last_period_limit, Error::<T>::LastPeriodTooFarInFuture);
			ensure!(end > now, Error::<T>::CannotEndInPast);

			// Here we check the lease period on the ending block is at most the first block of the
			// period after `first_period`. If it would be larger, there is no way we could win an
			// active auction, thus it would make no sense to have a crowdloan this long.
			let (lease_period_at_end, is_first_block) =
				T::Auctioneer::lease_period_index(end).ok_or(Error::<T>::NoLeasePeriod)?;
			let adjusted_lease_period_at_end = if is_first_block {
				lease_period_at_end.saturating_sub(One::one())
			} else {
				lease_period_at_end
			};
			ensure!(adjusted_lease_period_at_end <= first_period, Error::<T>::EndTooFarInFuture);

			// Can't start a crowdloan for a lease period that already passed.
			if let Some((current_lease_period, _)) = T::Auctioneer::lease_period_index(now) {
				ensure!(first_period >= current_lease_period, Error::<T>::FirstPeriodInPast);
			}

			// There should not be an existing fund.
			ensure!(!Funds::<T>::contains_key(index), Error::<T>::FundNotEnded);

			let manager = T::Registrar::manager_of(index).ok_or(Error::<T>::InvalidParaId)?;
			ensure!(depositor == manager, Error::<T>::InvalidOrigin);
			ensure!(T::Registrar::is_registered(index), Error::<T>::InvalidParaId);

		pub fn dissolve(origin: OriginFor<T>, #[pallet::compact] index: ParaId) -> DispatchResult {
			let who = ensure_signed(origin)?;

			let fund = Funds::<T>::get(index).ok_or(Error::<T>::InvalidParaId)?;
			let pot = Self::fund_account_id(fund.fund_index);
			let now = frame_system::Pallet::<T>::block_number();

			// Only allow dissolution when the raised funds goes to zero,
			// and the caller is the fund creator or we are past the end date.
			let permitted = who == fund.depositor || now >= fund.end;
			let can_dissolve = permitted && fund.raised.is_zero();
			ensure!(can_dissolve, Error::<T>::NotReadyToDissolve);

			// Assuming state is not corrupted, the child trie should already be cleaned up
			// and all funds in the crowdloan account have been returned. If not, governance
			// can take care of that.
			debug_assert!(Self::contribution_iterator(fund.fund_index).count().is_zero());

			// Crowdloan over, burn all funds.
			let _imba = CurrencyOf::<T>::make_free_balance_be(&pot, Zero::zero());
			let _ = frame_system::Pallet::<T>::dec_providers(&pot).defensive();

			CurrencyOf::<T>::unreserve(&fund.depositor, fund.deposit);
			Funds::<T>::remove(index);
			Self::deposit_event(Event::<T>::Dissolved { para_id: index });
			Ok(())
		}
