### Title
Webhook `shop-domain` and `topic` identity fields are trusted from unauthenticated headers while the HMAC only covers the raw body - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop`, `topic`, `api_version`, and `webhook_id` directly from HTTP headers, and `ShopifyAPI::Webhooks::Registry.process` only verifies the HMAC over the raw body before dispatching those unauthenticated header values to the app's handler as trusted tenant identity.

### Finding Description
The identity binding that should hold is: `hmac == HMAC(secret, bytes_verified)` implies `shop == shop_the_bytes_belong_to`. In this gem, `to_signable_string` for a webhook request returns only `@raw_body`: [1](#0-0) 

while `shop`, `topic`, `api_version`, and `webhook_id` are all read straight from HTTP headers with no cryptographic binding to that body: [2](#0-1) 

`Registry.process` validates only that the HMAC matches the body, then immediately forwards the header-derived `shop` to the caller's handler as trusted metadata: [3](#0-2) 

`HmacValidator.validate` calls `verifiable_query.to_signable_string`, so for a `Webhooks::Request` the comparison is solely `hmac == HMAC(secret, raw_body)`; the `shop` and `topic` headers never enter the signed material: [4](#0-3) 

Because `shop-domain` is not covered by the signature, any request with a *validly signed body* (i.e., a body that was genuinely HMAC-signed by Shopify for the attacker's own installed shop) can be replayed with an attacker-modified `x-shopify-shop-domain`/`shopify-shop-domain` header. The signature still validates (it only checks the body bytes), but `WebhookMetadata.shop` — which the documented handler pattern uses to route/attribute the webhook to a specific tenant (`data.shop`, e.g., `perform_later(topic: data.topic, shop_domain: data.shop, ...)`) — now names a different shop than the one that produced and was authorized to sign that body.

### Impact Explanation
This breaks the equality "the shop bytes were signed for" == "the shop the app treats them as belonging to." Downstream, apps built per this gem's own documented integration pattern key their per-tenant session lookup, job processing, and data writes off `data.shop` from `WebhookMetadata`, trusting it as authenticated. An attacker who legitimately installs the app on their own shop (an unprivileged step available to any internet user through the Shopify App Store/dev store) can capture a webhook Shopify signs for their own tenant, then replay that exact (unmodified) body with a forged `shop-domain` header claiming to be a different, victim shop. Since the HMAC only proves the body's authenticity and says nothing about which shop it is attributed to, the app processes attacker-controlled data under a victim tenant's identity — a cross-tenant data confusion/injection primitive reachable without any credentials beyond running the app as a normal merchant.

### Likelihood Explanation
Likelihood is moderate: it requires the attacker to be (or control) a merchant with the app installed (an unprivileged, self-service action for any Shopify developer/merchant), and requires the target app's webhook handler to key tenant-sensitive logic off `data.shop` — which is exactly the pattern this gem's own documentation recommends (`docs/usage/webhooks.md`, lines 24-29). No secret key, access token, or privileged account is needed; only the ability to install the app on an attacker-owned shop and intercept/replay one legitimately signed webhook request.

### Recommendation
Bind the shop (and ideally topic) identity into the verified material instead of trusting it from headers alone. Concretely: include `shop-domain` (and `topic`) in the value passed to the HMAC comparison (e.g., signable string composed of headers + body, or a secondary application-level check that cross-validates the header `shop` against a shop known to be associated with the specific `webhook_id`/subscription that was registered), and reject a webhook whose header-derived shop cannot be independently correlated to the resource that produced the signed body.

### Proof of Concept
1. Install the target Shopify app on attacker-owned dev shop `attacker.myshopify.com`.
2. Trigger a webhook Shopify legitimately signs for `attacker.myshopify.com` (e.g., `orders/create`), capturing `raw_body` and the valid `x-shopify-hmac-sha256` header.
3. Replay the request to the app's webhook endpoint unchanged except the header:
   `x-shopify-shop-domain: victim.myshopify.com`
4. `ShopifyAPI::Utils::HmacValidator.validate` in `Registry.process` (`lib/shopify_api/webhooks/registry.rb:190`) validates successfully because it only recomputes HMAC over `raw_body` (`lib/shopify_api/webhooks/request.rb:35-38`), which is unmodified.
5. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` (`lib/shopify_api/webhooks/request.rb:21-23`) and processes attacker-supplied body content as if it originated from the victim tenant.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
