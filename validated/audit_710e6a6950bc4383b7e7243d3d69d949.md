Based on my research, the strongest analog to the report's bug class ("a per-key limit defaults to zero/unrestricted until explicitly configured, so a not-yet-configured key slips through with no protection") is the per-workflow HTTP-trigger rate limiter in the Gateway, which is seeded from the **global default** and only later picks up a stricter org/owner-specific override on a fixed poll interval. ### Title
Per-workflow HTTP trigger rate limit is seeded with the unrestricted global default and only converges to a stricter org/owner override after a polling delay - (File: core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go)

### Summary
The Gateway's HTTP trigger rate limiter for a given `workflowID`/owner/org is created lazily on first use and initially seeded with the global default rate/burst settings. A stricter, tenant-specific override (e.g. `org.<org>.PerWorkflow.HTTPTrigger.RateLimit`) is only applied after the scoped rate limiter's next settings poll, which happens on a fixed interval (`pollPeriod = 5s` in `chainlink-common`'s `pkg/settings/limits`). This mirrors the reported bug class: a resource whose restrictive limit is per-key/per-tenant, defaults to a permissive value until the specific configuration is actually loaded, and an unprivileged actor who is first to use that key benefits from the permissive default for a bounded window.

### Finding Description
`checkRateLimit` in `httpTriggerHandler` resolves the workflow's `orgID` via `resolveOrgID`, then calls `h.userRateLimiter.AllowErr(ctx)` with `contexts.CRE{Owner, Org, Workflow}` attached to the context. [3](#0-2) 

`userRateLimiter` is a scoped `limits.RateLimiter` built via `lf.MakeRateLimiter(cresettings.Default.PerWorkflow.HTTPTrigger.RateLimit)` in `NewGatewayHandler`. [4](#0-3) 

The test explicitly documents the mechanism: "The first check for each workflow creates its per-workflow-tenant limiter, seeded with the global default (burst 3) until the settings-backed value is first polled," and the settings hierarchy (workflow → owner → org → global) resolves an org-only override for `PerWorkflow.HTTPTrigger.RateLimit` only after `chainlink-common`'s scoped `RateLimiter` refreshes on its fixed poll interval (documented as `pkg/settings/limits.pollPeriod = 5s`). [5](#0-4) 

This is directly analogous to the reported Kairos bug: a per-key (there: per-currency; here: per-workflow/owner/org) protective limit is not present at the moment the key is first used, so the first request(s) against a brand-new or newly-restricted key bypass the intended restriction and fall back to a much more permissive default.

### Impact Explanation
An unprivileged caller who is first to trigger a workflow belonging to an organization that has (or will have) a restrictive `PerWorkflow.HTTPTrigger.RateLimit` override can burst requests at the unrestricted global default rate for up to one polling interval before the override takes effect. Since this is a DDoS/anti-abuse control (directly analogous to the "minimum interest as a DDoS measure" in the source report), the practical impact is a temporary rate-limit/quota bypass rather than fund loss or authentication bypass, bounding the severity.

### Likelihood Explanation
This triggers on ordinary operation, not a race requiring adversarial timing beyond "be early": any first-time (or newly onboarded) workflow owner/org automatically gets the global default until the next scheduled settings poll. It requires no privileged access — any external HTTP trigger caller with valid workflow auth can hit this window by sending requests as soon as (or immediately after) a workflow/org is registered, or by being the first request to spin up the per-tenant limiter.

### Recommendation
Eagerly resolve and apply the settings-backed (org/owner/workflow) rate-limit configuration when constructing/first-seeding a per-tenant limiter (synchronous initial fetch) instead of seeding with the global default and lazily converging on the next poll tick. Alternatively, shrink the poll interval or block the first request for a tenant until the tenant-specific settings value has been resolved at least once.

### Proof of Concept
The existing unit test demonstrates the window directly: `TestHttpTriggerHandler_CheckRateLimit_PerOrgOverride` sets a global default of "every 30s, burst 3" and an org-restricted override of "every1h:0" (deny everything). It shows the first two `checkRateLimit` calls (one per org) both succeed using the seeded global default, and only after `time.Sleep(6 * time.Second)` — past the settings poll period — does the restricted org's override actually start denying requests. [6](#0-5)

// at the org scope via settings (not hardcoded) is actually enforced end-to-end: the
// handler resolves org through its OrgResolver and attaches it to the context, and the
// settings hierarchy (workflow -> owner -> org -> global, see chainlink-common's

func TestHttpTriggerHandler_CheckRateLimit_PerOrgOverride(t *testing.T) {
	t.Parallel()

	const (
		restrictedOrg   = "org-restricted"
		restrictedOwner = "0x1111111111111111111111111111111111aaaa"
		restrictedWfID  = "0x1111"
		normalOrg       = "org-normal"
		normalOwner     = "0x2222222222222222222222222222222222bbbb"
		normalWfID      = "0x2222"
	)

	// Only org-restricted gets an override (burst 0: deny everything); org-normal (and
	// everything else) falls through to the global default (every 30s, burst 3).
	getter, err := settings.NewJSONGetter([]byte(`{
		"org": {
			"org-restricted": {
				"PerWorkflow": {
					"HTTPTrigger": {
						"RateLimit": "every1h:0"
					}
				}
			}
		}
	}`))
	require.NoError(t, err)

	rateLimiter, err := limits.Factory{Settings: getter}.MakeRateLimiter(cresettings.Default.PerWorkflow.HTTPTrigger.RateLimit)
	require.NoError(t, err)

	orgResolver := &stubOrgResolver{orgByOwner: map[string]string{
		restrictedOwner: restrictedOrg,
		normalOwner:     normalOrg,
	}}

	metadataHandler := createTestMetadataHandler(t)
	metadataHandler.workflowIDToRef[restrictedWfID] = workflowReference{workflowOwner: restrictedOwner, workflowName: "wf-restricted", workflowTag: "v1"}
	metadataHandler.workflowIDToRef[normalWfID] = workflowReference{workflowOwner: normalOwner, workflowName: "wf-normal", workflowTag: "v1"}

	testMetrics := createTestMetrics(t, &config.DONConfig{Members: []config.NodeConfig{{Address: "node1"}}})
	handler := NewHTTPTriggerHandler(logger.Test(t), WithDefaults(ServiceConfig{}), nil, nil, metadataHandler, rateLimiter, testMetrics, orgResolver)

	// The first check for each workflow creates its per-workflow-tenant limiter, seeded
	// with the global default (burst 3) until the settings-backed value is first polled.
	require.NoError(t, handler.checkRateLimit(t.Context(), restrictedWfID, "req-1", hc.NewCallback()))
	require.NoError(t, handler.checkRateLimit(t.Context(), normalWfID, "req-2", hc.NewCallback()))

	// chainlink-common's scoped RateLimiter refreshes settings-sourced values on a fixed
	// poll interval (pkg/settings/limits.pollPeriod = 5s); wait past it so the org
	// override is picked up. Deliberately not checking again in the meantime: that would
	// burn through the default burst and could deny the next check for the wrong reason.
	time.Sleep(6 * time.Second)

	// org-restricted's override (burst 0) is now active: denied.
	callback := hc.NewCallback()
	err = handler.checkRateLimit(t.Context(), restrictedWfID, "req-3", callback)
	require.Error(t, err)
	payload, waitErr := callback.Wait(t.Context())
	require.NoError(t, waitErr)
	requireUserErrorSent(t, payload, jsonrpc.ErrLimitExceeded)

	// org-normal has no override and still has burst left over from the global default: allowed.
	require.NoError(t, handler.checkRateLimit(t.Context(), normalWfID, "req-4", hc.NewCallback()))
}

func (h *httpTriggerHandler) checkRateLimit(ctx context.Context, workflowID, requestID string, callback handlers.Callback) error {
	workflowRef, found := h.workflowMetadataHandler.GetWorkflowReference(workflowID)
	if !found {
		h.handleUserError(ctx, requestID, jsonrpc.ErrInvalidRequest, "workflow reference not found", callback)
		return errors.New("workflow reference not found")
	}

	orgID := h.resolveOrgID(ctx, workflowRef.workflowOwner)
	ctx = contexts.WithCRE(ctx, contexts.CRE{Owner: workflowRef.workflowOwner, Org: orgID, Workflow: workflowID})
	if err := h.userRateLimiter.AllowErr(ctx); err != nil {
		lggr := logger.With(h.lggr, platform.KeyWorkflowID, workflowID, platform.KeyWorkflowOwner, workflowRef.workflowOwner, "requestID", requestID, "err", err)
		if errLimited, ok := errors.AsType[limits.ErrorRateLimited](err); ok {
			switch errLimited.Scope {
			case settings.ScopeWorkflow:
				lggr.Errorf("failed to start execution: per workflow rate limit exceeded")
				h.metrics.IncrementWorkflowThrottled(ctx, h.lggr)
			default:
				lggr.Errorf("failed to start execution: unexpected rate limit for scope %s", errLimited.Scope)
			}
			h.handleUserError(ctx, requestID, jsonrpc.ErrLimitExceeded, "rate limit exceeded", callback)
			return err
		}
		return fmt.Errorf("failed to check rate limit: %w", err)
	}
	return nil
}
