### Title
Fee-on-transfer / deflationary ERC20 inputs cause insolvent escrow and permanently stuck refunds in Tron `IntentGatewayV2.placeOrder` - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron variant of `IntentGatewayV2.placeOrder` credits the escrow ledger `_orders[commitment][token]` with the user-specified (pre-transfer) input amount instead of the amount actually received by the contract after `safeTransferFrom`. The mainline EVM `IntentGatewayV2.sol` explicitly guards against this by measuring `balanceOf` before/after every ERC20 transfer and rewriting `order.inputs[i].amount` to the delta, but that fix was not carried over to the Tron contract.

### Finding Description
In the non-predispatch branch of `placeOrder`, the Tron contract does: [1](#0-0) 
It calls `IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` and then credits `_orders[commitment][token] += reducedInputs[i].amount`, where `reducedInputs[i].amount` is derived purely from the pre-transfer `order.inputs[i].amount` minus the protocol fee — it is never reconciled with the token balance the contract actually received.

The predispatch branch has the same defect: it credits `_orders[commitment][token] += reducedInputs[i].amount` using the pre-fee nominal amount even though the dispatcher-to-gateway sweep only guarantees `balance >= requiredAmount`, and any excess is emitted as dust rather than corrected for shortfall: [2](#0-1) 

Compare this to the mainline EVM `IntentGatewayV2.sol`, which recomputes the actual received amount for every transfer before crediting escrow: [3](#0-2) 
and validates this exact class of token in its test suite (`FeeOnTransferToken`): [4](#0-3) 

Because the Tron contract skips this reconciliation, if any input token charges a transfer fee (or is otherwise deflationary on transfer), the `_orders` ledger will record more tokens than the contract physically holds. `withdraw()` (called on fill/cancel/refund) unconditionally transfers `body.tokens[i].amount` (the full, un-discounted `reducedInputs` amount recorded at `placeOrder` time) to the beneficiary or solver: [5](#0-4) 
Once the ledger is insolvent, the physical token balance is insufficient to satisfy the recorded escrow amount for that token across all outstanding commitments, so `withdraw()`'s low-level `token.call(...transfer...)` will either revert (if the token reverts on insufficient balance) or, if a subsequent order's legitimate escrow tries to redeem, it will fail because the earlier over-credited entry already drained real balance that belonged to it.

### Impact Explanation
This is a direct, permanent value-destruction bug reachable by any unprivileged user submitting a `placeOrder` transaction with a fee-on-transfer/deflationary ERC20 as an input. It results in:
- Unbacked escrow credits (the internal ledger overstates real token holdings — a "phantom mint" of escrow claims).
- Insolvency of the intent gateway with respect to that token, which can cause `withdraw()` (used by `fillOrder`'s destination-chain redemption, `cancelOrder` refunds, and cross-chain `RedeemEscrow`/`RefundEscrow` messages) to revert or drain balance belonging to other, legitimate orders — freezing funds for solvers and users. This matches the "Medium/High" bar for permanent freezing/loss of funds via unsound internal accounting caused by non-standard token behavior, which is exactly the bug class the external report warns about ("Sets... internal accounting... invariant that actual balance must always be larger or equal to the internally tracked balance is broken... insolvent").

### Likelihood Explanation
Likelihood depends on whether fee-on-transfer/deflationary tokens are permitted as valid `order.inputs` on the Tron deployment. Given that the mainline EVM contract was explicitly hardened and tested against this exact scenario (`FeeOnTransferToken` tests), it indicates the protocol does not categorically disallow such tokens, and the omission in the Tron fork is very likely an unintentional regression/fork drift rather than an intentional restriction. Any user (malicious or not) placing an order with such a token — or even an honest user unaware their chosen token has a transfer fee — triggers the issue with a single transaction, with no special privileges required.

### Recommendation
Port the balance-reconciliation logic from `evm/src/apps/IntentGatewayV2.sol` (lines 260–329) into `evm/tron/contracts/apps/IntentGatewayV2.sol`: measure `balanceOf(address(this))` (or the dispatcher's balance for predispatch) before and after each `safeTransferFrom`/sweep, and base `reducedInputs`/`_orders` escrow credits on the actually-received amount rather than the nominal `order.inputs[i].amount`.

### Proof of Concept
1. Deploy a fee-on-transfer ERC20 (e.g. the `FeeOnTransferToken` mock used in the mainline test suite, taking 1% fee on transfer) and mint balance to `user`.
2. `user` approves the Tron `IntentGatewayV2` for `inputAmount = 1000e18` and calls `placeOrder` with this token as the sole input, no predispatch.
3. `safeTransferFrom` moves `1000e18` nominal but the contract's real balance only increases by `990e18` (1% fee burned/retained by the token).
4. `_orders[commitment][token]` is credited with `reducedInputs[i].amount` computed from `1000e18` (minus protocol fee, if any) — i.e., ~`1000e18` or `997e18`, not `990e18`.
5. When the order is filled/cancelled and `withdraw()` is invoked, it attempts to `transfer` the full escrowed amount (~`1000e18`) out of a contract that only holds `990e18` of that token, causing either an outright revert (denial of service on withdrawal) or, once multiple orders exist, silently consuming balance escrowed for other unrelated orders, making the gateway insolvent for that token.

    /// @notice Escrow correctly reflects actual received amount for fee-on-transfer tokens.
    function testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived() public {
        // Deploy a 1% fee-on-transfer token
        FeeOnTransferToken fot = new FeeOnTransferToken(100); // 1% = 100 bps
        fot.mint(user, 10000 * 1e18);

        uint256 inputAmount = 1000 * 1e18;
        uint256 expectedReceived = inputAmount - (inputAmount * 100) / 10000; // 990

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(fot)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 900 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        vm.startPrank(user);
        fot.approve(address(intentGateway), inputAmount);
        intentGateway.placeOrder(order, bytes32(0));
        vm.stopPrank();

        // Gateway should hold only what it actually received
        assertEq(
            fot.balanceOf(address(intentGateway)), expectedReceived, "Gateway balance should match received amount"
        );

        // Reconstruct the order as placeOrder would have mutated it
        order.user = bytes32(uint256(uint160(user)));
        order.source = host.host();
        order.nonce = 0;
        order.inputs[0].amount = expectedReceived;
        bytes32 commitment = keccak256(abi.encode(order));

        // Escrow should match actual received, not the user-specified amount
        assertEq(
            intentGateway._orders(commitment, address(fot)),
            expectedReceived,
            "Escrow should equal actual received amount"
        );
    }
