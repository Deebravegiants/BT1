### Title
Forced fee-refund transfer to a blacklistable `feeToken()` sender permanently blocks GET/POST request timeout processing - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatchTimeOut` (both the `GetRequestTimeout` and `PostRequestTimeout` overloads) unconditionally pushes the accumulated relayer fee back to the original request's `meta.sender` using a direct `IERC20(feeToken()).safeTransfer(...)` call inside the same atomic state transition that finalizes the timeout. If `feeToken()` is a blacklist-capable stablecoin (e.g. USDC, which Hyperbridge explicitly documents/tests as the fee token) and `meta.sender` becomes blacklisted, this transfer reverts every single time any relayer tries to submit the timeout proof for that commitment, permanently preventing that request from ever being timed out.

### Finding Description
`dispatch(DispatchGet)`/`dispatch(DispatchPost)` record the fee payer as `_msgSender()` at dispatch time: [1](#0-0) 

This value (`meta.sender`) is immutable for the lifetime of the commitment — it is not the relayer, it's whoever originally dispatched the request (e.g. a user calling `IntentsBase._cancelFromSource`, which dispatches a `DispatchGet` and pays its fee from the caller).

When a relayer later submits a timeout proof, `HandlerV2` calls into `EvmHost.dispatchTimeOut`, which — after successfully invoking the destination module's callback — force-pushes the refund directly to that stored `meta.sender`: [2](#0-1) [3](#0-2) 

This is the exact bug class from the external report: reward/fee tokens are forcibly transferred to an externally-controlled address as part of a critical state-changing operation, with no fallback "claim" pattern. If `meta.sender` is blacklisted by the fee token (USDC-style blacklist), `safeTransfer` reverts, which reverts the *entire* `dispatchTimeOut` call — including the already-executed `onGetTimeout`/`onPostRequestTimeout` module callback side effects (e.g. IntentsBase-style refund/cancellation logic), and the deletion of `_requestCommitments[commitment]`.

Crucially, unlike the relayer-reward path in `dispatchIncoming(GetResponse ...)` (where a *different*, non-blacklisted relayer could retry and succeed), the refund destination here is fixed and independent of which relayer submits the proof: [4](#0-3) 

So no relayer — ever — can successfully process the timeout for that specific commitment once `meta.sender` is blacklisted. The request is stuck forever in its pending state.

### Impact Explanation
Any application built on top of ISMP that relies on GET/POST timeout delivery to complete a critical flow (e.g. `IntentsBase`/`ExtrinsicIntents` order cancellation via `_cancelFromSource`'s `DispatchGet`, which depends on either a response or a timeout to progress) can have that flow permanently frozen if the original fee-payer becomes blacklisted by the fee token issuer in the interim. This is a permanent freezing-of-funds condition (escrowed order inputs, or any state gated behind the timeout, become irretrievable) and also constitutes "a route unable to deliver messages" — the specific request commitment can never be finalized by any relayer, matching the accepted impact categories.

### Likelihood Explanation
Low, matching the referenced report — USDC/blacklist-capable tokens are not always configured as `feeToken()`, and being blacklisted is not routine. However, since Hyperbridge documentation and tests explicitly use USDC as the reference fee/escrow token, and any user (not just a privileged actor) can dispatch fee-paying GET/POST requests as `_msgSender()`, this is reachable from an ordinary user transaction with no special privileges — satisfying the "single submitted transaction" reachability requirement.

### Recommendation
Do not force-push the fee refund to `meta.sender` inside the atomic timeout-processing path. Instead, credit an internal claimable balance (`mapping(address => mapping(address => uint256)) pendingFeeBalances`) when the transfer would be made, and expose a separate `claimFee()`/`withdrawFee()` function that the sender can call once they are no longer blacklisted (or that lets them redirect the claim to a different address). This decouples timeout finalization (and destination module callback execution) from the fee token's transfer semantics, preventing a single blacklisted address from permanently blocking a specific request's timeout resolution.

### Proof of Concept
1. User `A` calls a Hyperbridge application (e.g. `IntentsBase._cancelFromSource`) which internally calls `EvmHost.dispatch(DispatchGet)`, paying the relayer fee in `feeToken()` (USDC). `_requestCommitments[commitment] = FeeMetadata({sender: A, fee: F})` is recorded.
2. Before a relayer submits the timeout proof, the USDC issuer blacklists address `A` (e.g. due to unrelated compliance action).
3. The destination chain never responds in time (or the response condition isn't met), so the request becomes eligible for timeout.
4. A relayer submits a valid timeout proof; `HandlerV2` calls `EvmHost.dispatchTimeOut(timeout, meta, commitment)`.
5. `onGetTimeout`/`onPostRequestTimeout` on the source module executes successfully, but the subsequent `IERC20(feeToken()).safeTransfer(meta.sender, meta.fee)` reverts because `meta.sender == A` is blacklisted.
6. The entire transaction reverts; `_requestCommitments[commitment]` remains set. Any relayer retrying the same timeout proof hits the identical revert indefinitely — the request, and any funds/state gated behind its resolution, are permanently stuck.

```text
    function dispatchTimeOut(
        GetRequestTimeout memory timeout,
        FeeMetadata memory meta,
        bytes32 commitment
    ) external restrict(_hostParams.handler) {
        // replay protection
        delete _requestCommitments[commitment];
        (bool success,) = _bytesToAddress(timeout.request.from)
            .call(abi.encodeWithSelector(IApp.onGetTimeout.selector, timeout));

        if (!success) {
            // so that it can be retried
            _requestCommitments[commitment] = meta;
            return;
        }

        if (meta.fee != 0) {
            // refund relayer fee
            IERC20(feeToken()).safeTransfer(meta.sender, meta.fee);
        }
        emit GetRequestTimeoutHandled({commitment: commitment, dest: string(timeout.request.dest)});
    }
```
