### Title
Missing Shop-Domain Validation in `Oauth.begin_auth` Enables Forced OAuth Completion to an Attacker-Controlled Host - (File: lib/shopify_api/auth/oauth.rb)

### Summary
`ShopifyAPI::Auth::Oauth.begin_auth` builds the authorization redirect URL directly from the caller-supplied `shop:` string, with no validation that it is a genuine `*.myshopify.com` (or Shopify Plus/dev) domain. This is inconsistent with the rest of the gem: `ShopifyAPI::Auth::ClientCredentials` explicitly rejects non-Shopify domains before contacting them [1](#0-0) , but the interactive OAuth authorization-code flow — the most commonly used and most sensitive flow — has no equivalent guard.

### Finding Description
`begin_auth` accepts an arbitrary `shop` string and feeds it straight into `auth_base_uri(shop)`, which returns `"https://#{shop}/admin"` for any value that isn't a recognized dev-server domain: [2](#0-1) [3](#0-2) 

The resulting `auth_route` embeds the app's `client_id`, `scope`, `redirect_uri`, and freshly generated CSRF `state` nonce, and is returned to the caller to redirect the browser to:
```ruby
query = {
  client_id: ShopifyAPI::Context.api_key,
  scope: scope.to_s,
  redirect_uri: "#{ShopifyAPI::Context.host}#{redirect_path}",
  state: state,
  "grant_options[]": is_online ? "per-user" : "",
}
auth_route = auth_base_uri(shop) + "/oauth/authorize?#{query_string}"
```
Nothing in this method verifies `shop` is a `*.myshopify.com` domain (or otherwise Shopify-operated), unlike `ClientCredentials.client_credentials`, which the gem's own test suite shows raises `Errors::InvalidShopError` for `"attacker.example"` before making any request [1](#0-0) .

Because the documented integration pattern is to source `shop` directly from the inbound request (`ShopifyAPI::Auth::Oauth.begin_auth(shop: shop, ...)` where `shop` typically comes from a query parameter at installation time), an unvalidated `shop` value flows unchanged into the generated redirect target. The gem provides no built-in check that would stop this, and no documented requirement in `docs/usage/oauth.md` to validate the domain before calling `begin_auth`.

This breaks the intended identity binding: **the host that receives the OAuth authorization request (and that will subsequently be treated as the merchant's shop) is trusted to equal `shop`, without verifying `shop` is actually a Shopify-controlled host.**

### Impact Explanation
An attacker can supply `shop=evil-attacker-domain.com` to the app's install entrypoint. The library will compute `auth_route = "https://evil-attacker-domain.com/admin/oauth/authorize?client_id=...&scope=...&redirect_uri=https://app.example.com/redirect&state=...&grant_options%5B%5D=..."` and hand it back to the caller to redirect the victim's browser to. This allows:
- Forced OAuth completion / phishing: the attacker's server can present a fake "Install app" page mimicking Shopify, capture the merchant's interaction, and redirect back to the app's real `redirect_uri` with an attacker-supplied `code`, causing the victim (or the attacker acting as the victim) to complete OAuth under conditions the attacker controls.
- Leakage of the app's `client_id` and `redirect_uri` to a third-party host (not itself sensitive but supports downstream abuse), and disclosure of the CSRF `state` nonce to an attacker-controlled origin, which can undermine the CSRF protection that state is meant to provide in `validate_auth_callback`, since the state is exposed to a page fully controlled by the attacker.

This matches the "High: session fixation or forced OAuth completion" impact tier.

### Likelihood Explanation
Likelihood is high wherever a host application passes an unsanitized `shop` parameter (e.g., from `request.params[:shop]`) straight into `begin_auth`, which is exactly the pattern shown in this gem's own documentation snippets and is common in minimal/custom Rails or Sinatra integrations. The `ClientCredentials` code path proves the maintainers are aware validation is needed for this exact bug class, but the fix was not applied to the interactive OAuth authorization code flow in `Oauth.begin_auth`.

### Recommendation
Validate `shop` in `Oauth.begin_auth` (and anywhere else a shop-derived value is used to build a host, e.g. `auth_base_uri`) against the Shopify domain format (e.g. `\A[a-zA-Z0-9][a-zA-Z0-9-]*\.myshopify\.com\z`, plus any explicitly supported dev-server suffixes) before constructing `auth_route`, raising `Errors::InvalidShopError` on mismatch — mirroring the existing check in `ShopifyAPI::Auth::ClientCredentials`.

### Proof of Concept
```ruby
ShopifyAPI::Context.setup(api_key: "app_key", api_secret_key: "secret", ...)

result = ShopifyAPI::Auth::Oauth.begin_auth(
  shop: "evil-attacker-domain.com", # attacker-supplied, unvalidated
  redirect_path: "/auth/callback",
)

result[:auth_route]
# => "https://evil-attacker-domain.com/admin/oauth/authorize?client_id=app_key&scope=...&redirect_uri=https://app.example.com/auth/callback&state=<nonce>&grant_options%5B%5D="
```
The app redirects the victim's browser to a host fully controlled by the attacker, carrying the app's `client_id`, `redirect_uri`, and CSRF `state` — none of which `begin_auth` validated as belonging to Shopify.

        def begin_auth(shop:, redirect_path:, is_online: true, scope_override: nil)
          scope = if scope_override.nil?
            ShopifyAPI::Context.scope
          elsif scope_override.is_a?(ShopifyAPI::Auth::AuthScopes)
            scope_override
          else
            ShopifyAPI::Auth::AuthScopes.new(scope_override)
          end

          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = SecureRandom.alphanumeric(NONCE_LENGTH)

          cookie = SessionCookie.new(value: state, expires: Time.now + 60)

          query = {
            client_id: ShopifyAPI::Context.api_key,
            scope: scope.to_s,
            redirect_uri: "#{ShopifyAPI::Context.host}#{redirect_path}",
            state: state,
            "grant_options[]": is_online ? "per-user" : "",
          }

          query_string = URI.encode_www_form(query)
          auth_route = auth_base_uri(shop) + "/oauth/authorize?#{query_string}"

          { auth_route: auth_route, cookie: cookie }
        end
