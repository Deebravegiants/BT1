### Title
Webhook Shop-Domain Header Is Not Covered by the HMAC, Enabling Cross-Tenant Webhook Spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authorizes a webhook purely by validating an HMAC computed over the raw request body, then dispatches the handler using a `shop` value read from an HTTP header that is never part of the signed content. Any party that can obtain one authentic (body, HMAC) pair for a given topic — e.g., by installing the app on their own shop and triggering the webhook — can replay that exact body/HMAC to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for an arbitrary victim shop. The HMAC check still passes because it never inspected the header, and the handler receives `WebhookMetadata` claiming to be for the victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

`shop` (and `topic`, `webhook_id`, `api_version`) are pulled straight from HTTP headers, completely outside the HMAC-covered content: [2](#0-1) 

`HmacValidator.validate` verifies the HMAC only against `to_signable_string` (the body), never the headers: [3](#0-2) 

`Registry.process` gates on that body-only HMAC check and then unconditionally trusts `request.shop` for dispatch/attribution to the handler: [4](#0-3) 

The identity binding that should hold is:
`shop_bound_inside_hmac_signed_payload == shop_used_by_handler`

What actually holds is:
`shop_header_from_unauthenticated_HTTP_request == shop_used_by_handler`

Because the app's `api_secret_key` is shared across every shop that installs the app, an attacker who legitimately installs the app on a shop they control (or otherwise obtains one valid webhook delivery) receives a correctly HMAC-signed `(raw_body, hmac)` pair from Shopify for that topic. Since the header carrying the shop identity is unsigned, the attacker can POST that same body/HMAC pair to the app's public, fixed webhook route with a forged `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header naming any victim shop. `Utils::HmacValidator.validate` still succeeds (it never looked at the header), and `Registry.process` calls the registered handler with `WebhookMetadata.new(... shop: request.shop ...)` set to the attacker-chosen victim domain.

### Impact Explanation
This breaks the tenant boundary the whole webhook mechanism exists to enforce: an app author's handler code (which trusts `data.shop` as an authenticated tenant identifier once HMAC validation has passed) can be made to run tenant-scoped side effects for a shop the attacker does not control — e.g. a `shop/redact`, `app/uninstalled`, or custom business-logic webhook handler that deletes, disables, or mutates the target shop's stored records — purely by supplying a body/HMAC pair the attacker legitimately obtained for their own store. This is a cross-tenant access primitive achieved without ever possessing the victim's access token, session, or credentials.

### Likelihood Explanation
Exploitability only requires: (1) the ability to install the app (or otherwise capture one legitimate webhook delivery) on any shop, which is trivial for public apps and even easy for many private/custom apps during development, and (2) the ability to POST to the app's already-public webhook endpoint URL with custom headers, which is inherent to how HTTP webhook endpoints work. No secret material, no privileged Shopify account, and no interaction with a real victim session is required.

### Recommendation
Bind the tenant/shop identity into the value that is actually HMAC-verified before it is trusted for dispatch:
- Extend `VerifiableQuery#to_signable_string` for webhook `Request` to include the `shop`, `topic`, and `webhook_id` headers (canonicalized) in the signed content, or
- Cross-check `request.shop` against a shop identifier embedded in the JSON body (many Shopify webhook payloads include `shop_id`/tenant-scoped fields) or against a registry of shops the app is actually installed for, rejecting mismatches, before invoking the handler.

### Proof of Concept
1. Install the target app on an attacker-owned shop `attacker.myshopify.com`; trigger a webhook of the topic the app has a handler for (e.g. `app/uninstalled`). Capture the raw POST body `B` and the `X-Shopify-Hmac-Sha256` header value `H` that Shopify legitimately computed and sent.
2. Send a new HTTP POST directly to the app's public webhook route (same body `B`, same `X-Shopify-Hmac-Sha256: H`), but replace the shop header with the victim: `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. In `ShopifyAPI::Webhooks::Request.new`, `hmac` is decoded from the (unchanged) `H` header and `to_signable_string` still returns body `B` — identical to step 1 — so `Utils::HmacValidator.validate` succeeds:
```ruby
# lib/shopify_api/utils/hmac_validator.rb
result = validate_signature(verifiable_query, Context.api_secret_key) # passes, body B unchanged
```
4. `Registry.process(request)` proceeds and calls the registered handler with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed_body_of(B), ...)`, i.e. the handler executes attacker-supplied topic/body logic attributed to the victim shop it never touched.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
