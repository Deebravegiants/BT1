### Title
Unverified swap route can invoke attacker contracts that steal unrelated caller tokens - (File: contracts/controller/src/strategies/swap.rs)

### Summary
User-facing strategy entrypoints accept an opaque `StrategySwap` byte payload and forward it to the configured router without binding it to a trusted route manifest, an expected pool set, or an integrity commitment. [1](#0-0) [2](#0-1)   
The router decodes caller-supplied `assets` and `ops`, resolves each hop’s pool and token addresses from those registries, and dispatches the hop to the encoded venue without an on-chain venue or pool allowlist. [3](#0-2) [4](#0-3) [5](#0-4)   
A tampered route can therefore insert an attacker-controlled contract as a pool; if the victim signs the resulting authorization tree, that contract can make token transfers from the victim beyond the routed input while still returning enough output for the strategy to succeed. [6](#0-5) [7](#0-6) 

### Finding Description
`swap_collateral`, `multiply`, `swap_debt`, and `repay_debt_with_collateral` all expose an opaque `swap: Bytes` argument that is passed to the strategy layer. [8](#0-7) [9](#0-8) [10](#0-9)   
For example, `process_swap_collateral` authorizes the caller, withdraws the selected collateral, and passes the caller-supplied route directly to `withdraw_and_swap_from_supply`. [11](#0-10)   
`swap_tokens` grants the router only an exact `amount_in` transfer of the declared `token_in`, but it does not inspect the route’s internal pool addresses or otherwise bind the payload to a signed expected route. [12](#0-11)   

Inside the router, `StrategyPayload.assets` is an arbitrary address registry and each packed instruction supplies a pool index and token indices. [13](#0-12) [14](#0-13)   
Structural validation range-checks these indices and rejects malformed programs, but it does not authenticate the pool address or compare the route against an expected manifest. [15](#0-14)   
Execution then constructs `SwapHop` from the supplied registry entries and calls the selected venue adapter, which invokes the specified pool address. [4](#0-3) [5](#0-4)   

The controller’s post-swap checks are balance-based: they reject router overspending of its granted input and require a positive increase in the expected `token_out` balance. [16](#0-15) [17](#0-16)   
Those checks do not prevent a malicious pool invoked below the caller-authorized strategy from adding an unrelated authorized token transfer to the signed invocation tree. [18](#0-17) [19](#0-18)   
Consequently, route integrity relies entirely on the wallet or client detecting and rejecting an unexpected authorization child before signing, while the contracts execute any structurally valid route the user provides. [20](#0-19) [14](#0-13) 

### Impact Explanation
This is theft of user funds because the malicious pool can transfer unrelated tokens held by the victim while the controller observes a valid collateral swap. [21](#0-20) [17](#0-16)   
The attacker can fund the malicious pool with the expected output asset, allow the input transfer to complete, return enough output to satisfy the router’s minimum-output and controller delta checks, and simultaneously execute the extra caller-token transfer included in the signed authorization tree. [22](#0-21) [7](#0-6)   
The protocol-level loss is not limited to `amount_in`; it includes whatever additional token transfers the victim authorizes as children of the malicious route invocation. [2](#0-1) [23](#0-22) 

### Likelihood Explanation
Exploitation requires a tampered route and victim signature, which is analogous to the report’s user-interaction requirement. [24](#0-23) [20](#0-19)   
A malicious quote, compromised frontend, or phishing flow can replace an expected route with one containing an attacker-controlled pool because neither the controller nor router checks a trusted route commitment or allowlist before execution. [15](#0-14) [4](#0-3)   
The attack can preserve all on-chain success conditions by returning a positive expected output and leaving the account solvent, making it practical whenever the victim fails to inspect the expanded authorization tree. [25](#0-24) [17](#0-16) 

### Recommendation
Bind each strategy route to an expected route commitment supplied by a trusted signer or verify a signed quote containing the route payload, expected input, expected output, deadline, and account context. [26](#0-25) [27](#0-26)   
At minimum, add a controller- or router-level allowlist of supported venue pool contracts, reject unknown pool addresses before dispatch, and require the decoded route’s `token_in` and `token_out` to equal the caller’s declared assets. [28](#0-27) [29](#0-28)   
Clients should also simulate the transaction, render the complete authorization tree, and refuse any token transfer outside the single expected input pull. [19](#0-18) 

### Proof of Concept
1. The victim intends to call `swap_collateral(caller=V, account_id=A, current=XLM, amount=N, new=USDC, swap=R)` and receives a tampered payload `R'` from a malicious interface. [30](#0-29)   
2. `R'` contains an `assets` registry where one hop’s `idx_a` resolves to attacker-controlled contract `M`, while the program still terminates with the expected `USDC` output. [13](#0-12) [31](#0-30)   
3. The controller authorizes the victim, withdraws `N` XLM, grants the router an exact controller-held input transfer, and invokes `execute_strategy`. [11](#0-10) [32](#0-31)   
4. The router decodes the structurally valid program, pulls the input, and dispatches the malicious hop to `M`. [33](#0-32) [5](#0-4)   
5. `M` implements the expected pool ABI, returns enough USDC to the router, and additionally invokes an unrelated token `transfer(V → attacker)` that appears as a child of the victim-authorized invocation. [7](#0-6) [23](#0-22)   
6. If the victim signs the simulated tree, the router pays the USDC output to the controller, the controller’s output-delta and final risk checks pass, and the unrelated token transfer remains committed despite being unrelated to the intended swap. [22](#0-21) [25](#0-24)

    pub(crate) fn decode(env: &Env, ops: &Bytes, assets_len: u32, amounts_len: u32) -> Self {
        if assets_len == 0 || assets_len > MAX_ASSETS || amounts_len > MAX_AMOUNTS {
            panic_with_error!(env, Error::InvalidRouteXdr);
        }

        let len = ops.len();
        if len < HEADER_LEN || len as usize > MAX_PROGRAM_BYTES {
            panic_with_error!(env, Error::InvalidRouteXdr);
        }

        let mut buf = [0u8; MAX_PROGRAM_BYTES];
        ops.copy_into_slice(&mut buf[..len as usize]);

        if buf[head::VERSION] != VERSION {
            panic_with_error!(env, Error::InvalidRouteXdr);
        }

        let op_count = buf[head::OP_COUNT] as u32;
        let weight_count = buf[head::WEIGHT_COUNT] as u32;
        if op_count == 0 || op_count > MAX_OPS || weight_count > MAX_WEIGHTS {
            panic_with_error!(env, Error::EmptyBatch);
        }
        let weights_at = HEADER_LEN + OP_LEN * op_count;
        if len != weights_at + WEIGHT_LEN * weight_count {
            panic_with_error!(env, Error::InvalidRouteXdr);
        }

        let token_in = buf[head::TOKEN_IN] as u32;
        let token_out = buf[head::TOKEN_OUT] as u32;
        let min_out = buf[head::MIN_OUT] as u32;
        if token_in >= assets_len || token_out >= assets_len || min_out >= amounts_len {
            panic_with_error!(env, Error::InvalidRouteXdr);
        }
        if token_in == token_out {
            panic_with_error!(env, Error::SameToken);
        }

        let referral = &buf[head::REFERRAL..head::REFERRAL + 4];
        let referral_id =
            u32::from_be_bytes([referral[0], referral[1], referral[2], referral[3]]) as u64;

        let program = Self {
            buf,
            op_count,
            weights_at,
            token_in,
            token_out,
            min_out,
            referral_id,
        };
        program.validate(env, assets_len, amounts_len, weight_count);
        program

    fn validate(&self, env: &Env, assets_len: u32, amounts_len: u32, weight_count: u32) {
        for i in 0..self.op_count {
            let record = self.raw(i);
            let Some(opcode) = Opcode::from_u8(record[field::OPCODE]) else {
                panic_with_error!(env, Error::InvalidRouteXdr);
            };
            let mode = Mode::from_u8(record[field::MODE]);
            let (idx_a, idx_b, idx_c) = (
                record[field::POOL] as u32,
                record[field::TOKEN_IN] as u32,
                record[field::TOKEN_OUT] as u32,
            );

            // `Prev` is a purely structural link: the predecessor must exist,
            // must have a single output, and that output must be this
            // instruction's input.
            if mode == Mode::Prev {
                if i == 0 {
                    panic_with_error!(env, Error::BrokenTokenChain);
                }
                let previous = self.raw(i - 1);
                let produced = match Opcode::from_u8(previous[field::OPCODE]) {
                    // A swap produces its `token_out`, a mint its share token.
                    Some(Opcode::Swap(_)) => previous[field::TOKEN_OUT],
                    Some(Opcode::Mint) => previous[field::TOKEN_IN],
                    // A burn releases every constituent at once.
                    _ => panic_with_error!(env, Error::BrokenTokenChain),
                };
                if idx_b != produced as u32 {
                    panic_with_error!(env, Error::BrokenTokenChain);
                }
            }
            match mode {
                Mode::Fixed(idx) if idx as u32 >= amounts_len => {
                    panic_with_error!(env, Error::InvalidRouteXdr)
                }
                Mode::Ppm(idx) if idx as u32 >= weight_count => {
                    panic_with_error!(env, Error::InvalidRouteXdr)
                }
                _ => {}
            }

            if idx_a >= assets_len || idx_b >= assets_len {
                panic_with_error!(env, Error::InvalidRouteXdr);
            }
            match opcode {
                Opcode::Swap(_) => {
                    if idx_c >= assets_len {
                        panic_with_error!(env, Error::InvalidRouteXdr);
                    }
                    if idx_b == idx_c {
                        panic_with_error!(env, Error::SameToken);
                    }
                }
                // Liquidity legs spend the full vault balance, so only `Mode::All` is valid.
                Opcode::Burn | Opcode::Mint => {
                    if mode != Mode::All {
                        panic_with_error!(env, Error::InvalidRouteXdr);
                    }
                    if idx_c >= amounts_len {
                        panic_with_error!(env, Error::InvalidRouteXdr);
                    }
                }
            }
        }

    /// Decodes `swap_xdr` as a `StrategyPayload` and runs it for `sender`.
