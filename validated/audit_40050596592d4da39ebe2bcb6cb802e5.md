### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then trusts the `shop-domain` (and `topic`, `webhook-id`, `api-version`) HTTP headers—none of which are covered by that signature—to identify the tenant the payload belongs to before dispatching it to the host application's handler.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all read straight from unauthenticated headers with no cryptographic binding to the body or to each other: [2](#0-1) 

`Registry.process` verifies the request using `Utils::HmacValidator.validate(request)`, which internally calls `request.to_signable_string` (the raw body only) and compares it against the `hmac` header: [3](#0-2) [4](#0-3) 

After this check passes, the header-derived, **unsigned** `shop` value is placed directly into `WebhookMetadata` and handed to the host application's `WebhookHandler#handle`: [5](#0-4) [6](#0-5) 

The binding that should hold is:
`HMAC-verified bytes == bytes the application uses to identify the tenant (shop)`

Instead, only the JSON body is bound by the HMAC; the `shop-domain` header used for tenant attribution is bytes verified (body) ≠ bytes trusted for identity (headers). Any actor who can obtain one valid `(body, hmac)` pair for a topic they control—for example, a merchant installing the app on their own development/free shop and triggering a webhook for that shop—can replay the same body/hmac pair while substituting an arbitrary `x-shopify-shop-domain` (and `x-shopify-topic`/`x-shopify-webhook-id`) header value naming a different, victim shop. Since `HmacValidator.validate` never inspects the headers, the forged request passes signature validation, and the host application's handler receives `WebhookMetadata` claiming the payload originated from the victim shop.

### Impact Explanation
Host applications built on this gem commonly use `WebhookMetadata#shop` to select the tenant record, session, or database scope to apply the webhook payload to (per the documented `Webhooks` usage pattern). Because `shop` is not bound to the HMAC, an attacker with a valid webhook signature for content they control can cause the library to report an attacker-chosen shop, letting them inject or overwrite data under another merchant's tenant context inside the host application. This constitutes cross-tenant access/data confusion, matching the Critical "cross-tenant access" impact category — the identity binding between the cryptographically verified data (body) and the tenant identity used downstream (shop header) is broken.

### Likelihood Explanation
Exploitation requires the attacker to be able to produce (or capture) one valid `(raw_body, hmac)` pair signed with the app's own `api_secret_key` for a topic of their choosing — achievable by any developer/merchant who installs the app on their own store and triggers a webhook, since Shopify signs webhooks per-app, not per-shop. No access to `api_secret_key`, tokens, or victim credentials is required; only the ability to send an HTTP request to the app's webhook endpoint with attacker-controlled headers and a previously-observed valid body+HMAC combination (or a body they control if the app doesn't tie payload content to a specific shop's data). This is realistically reachable by any unprivileged internet user who can install the target app once.

### Recommendation
Include the tenant-identifying headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signable string, or otherwise cryptographically bind them to the payload before dispatch, so that `HmacValidator.validate` fails if any of these header values are altered post-signing. Short of that, the library should clearly document that `WebhookMetadata#shop`/`#topic`/`#webhook_id` are NOT authenticated and must not be trusted for tenant attribution by host applications without an independent verification (e.g., cross-checking against a known/allow-listed shop for the endpoint).

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and triggers a webhook (e.g., `orders/create`) for a controlled order, causing Shopify to POST a legitimately-signed request:
   - Body: `{"id": 1, ...}`
   - Header `x-shopify-hmac-sha256`: valid HMAC-SHA256 of the body using the app's `api_secret_key`
   - Header `x-shopify-shop-domain`: `attacker.myshopify.com`
2. Attacker captures this `(body, hmac)` pair and replays it directly to the app's webhook endpoint, but rewrites the header:
   - `x-shopify-shop-domain: victim.myshopify.com`
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC of `@raw_body` — unchanged — so validation succeeds: [7](#0-6) 
4. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: ..., ...)`, and the host application processes the payload as belonging to `victim.myshopify.com`, even though it never received a webhook signed for that shop: [5](#0-4)
