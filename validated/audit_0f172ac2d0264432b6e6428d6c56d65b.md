### Title
Raw `.call()` in `IntentGatewayV2.withdraw()` returns success for non-existent tokens, permanently freezing escrowed funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2.withdraw()` uses raw low-level `.call()` to transfer escrowed ERC20 tokens to a beneficiary instead of OpenZeppelin's `SafeERC20.safeTransfer`, even though `SafeERC20` is imported and used elsewhere in the same contract (e.g. `safeTransferFrom` in `placeOrder`). This reintroduces exactly the bug class described in the referenced report: Solidity's low-level `call` returns `success == true` if the target account has no code, so a non-existent (or since-destructed) token contract will make the escrow-release path believe the transfer succeeded.

### Finding Description
`withdraw()` is invoked from `onAccept` (for `RedeemEscrow`/`RefundEscrow` requests) and from `onGetResponse`, both of which are triggered by relayed cross-chain messages/proofs — paths reachable by any relayer delivering a valid ISMP message once an order has been filled or times out: [1](#0-0) 

For each escrowed token, the contract does:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
```
and then unconditionally decrements the escrow accounting:
```solidity
_orders[body.commitment][token] -= amount;
```
Because `.call()` returns `success = true` for any account with no code, if `token` has no bytecode at withdrawal time (e.g., the token self-destructs — full-code-removal `SELFDESTRUCT` is still valid on many chains including Tron — or the token was never actually deployed on this state machine), the "transfer" silently no-ops, `success` is `true`, `_orders[...]` is decremented, and `EscrowReleased`/`EscrowRefunded` is emitted as if funds were paid out — but the beneficiary receives nothing. The same pattern repeats for the transaction-fee payout at: [2](#0-1) 

This is a direct analog of the report's `_callERC20Token`/`AxelarGatewayProxy` pattern: a low-level call whose truthy return value is used to gate control flow without verifying the callee has code, unlike the project's own `CallDispatcher.dispatch()`, which explicitly performs an `extcodesize` check before calling: [3](#0-2) 

The non-Tron `IntentGatewayV2.sol` mainline codepath (`evm/src/apps/IntentGatewayV2.sol`) uses `IERC20(token).safeTransferFrom(...)` in `placeOrder`, and `SafeERC20` internally guards against the empty-code case; the Tron variant's `withdraw()` deliberately bypasses this via a raw `.call`, so the protection is missing specifically on the redemption path.

### Impact Explanation
Once `_orders[body.commitment][token]` is decremented to zero (or reduced) without an actual transfer occurring, there is no other code path to re-release those tokens: `_filled[body.commitment]` is already set, and repeat delivery of the same commitment is guarded against (`UnknownOrder`/`Filled` checks). The escrowed tokens held by the gateway become permanently stuck/unbacked by any redeemable claim — a direct, unrecoverable freezing/loss of user or solver funds. This is reachable purely by relayer message delivery for any order whose input token becomes a non-existent account before settlement completes (a token contract self-destructing during the pendency window between escrow and delivery of the fill/refund proof, which can be arbitrarily long while waiting on relayers).

### Likelihood Explanation
Requires a token used in an order to have no code at redemption time. This is a low-probability but plausible event for any token permissioned to self-destruct, is upgradeable via a proxy that can be bricked, or is deployed via CREATE2 with a deployment that can later be "undeployed" (e.g., ERC-1167 minimal proxies pointing to destructible implementations, or tokens deployed by a factory that can be removed). Given Hyperbridge's intent gateway is designed to support arbitrary user-specified ERC20 addresses across many chains (including Tron, which has different account/contract semantics), and the escrow window can be long, this is a realistic medium-likelihood scenario matching the judged severity in the original report (protocol availability/fund-safety impact from an unchecked low-level call).

### Recommendation
Replace the raw `token.call(...)` transfers in `withdraw()` (and the fee-token payout) with `SafeERC20.safeTransfer`, which is already imported and used elsewhere in the contract, or explicitly check `token.code.length != 0` before performing the low-level call, mirroring the `extcodesize` guard already implemented in `CallDispatcher.dispatch()`.

### Proof of Concept
1. User places an order via `placeOrder` with an ERC20 token that has code at that time (passes `safeTransferFrom`), escrowing `amount` tokens: [4](#0-3) .
2. Before the fill/refund settlement proof is relayed and delivered (which can be delayed indefinitely), the token contract self-destructs (removing its code), whether via an admin key compromise, protocol design (destructible proxy/factory pattern), or a bug in the token itself.
3. A relayer delivers the `RedeemEscrow`/`RefundEscrow` message, invoking `onAccept` → `withdraw(body, ...)`.
4. `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` targets an address with no code and returns `success = true` per EVM/TVM semantics.
5. `_orders[body.commitment][token] -= amount` succeeds, `EscrowReleased`/`EscrowRefunded` is emitted, but `beneficiary` never receives any tokens — the escrowed amount is permanently lost with no remaining redemption path.

        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;

                ++i;
            }
        }

            Call memory call = calls[i];
