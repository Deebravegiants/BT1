## Analysis

The `EvmHost` contract accumulates relayer fees for in-flight requests directly as an ERC20 balance of the configured `feeToken`, and pays them out later by re-reading the *current* `feeToken()` at settlement time rather than the token that was actually escrowed at dispatch time. This is the exact bug class from the ERC20Rewards report: an amount is denominated/escrowed in one token, then paid out in whatever token is configured at a later point, with no reconciliation for decimals or value. ### Title
Fee-token migration can strand relayer fees for in-flight requests, causing wrong-value payout in the new token - (File: evm/src/core/EvmHost.sol)

### Summary
`dispatch()` escrows a POST/GET relayer fee as an ERC20 balance in the host's currently configured `feeToken`, keyed only by commitment amount (`_requestCommitments[commitment].fee`), with no record of *which token* backed that amount. `dispatchIncoming`/`dispatchTimeOut` later pay that recorded `fee` value out using `feeToken()` read at *settlement* time. `updateHostParamsInternal` tries to prevent unsafe token migrations by requiring the host's raw balance of the old `feeToken` to be `0` before allowing a change, but `withdraw()` (also governance-only, meant for sweeping "bridge revenue") can drain that same pooled balance without distinguishing reserved/pending relayer fees from actual protocol revenue. A routine, non-malicious sequence — sweep revenue, then migrate the fee token — can zero out the balance check while requests are still in flight, after which every pending fee is paid out in the new token at face value, exactly reproducing the `ERC20Rewards` finding.

### Finding Description
1. When a request is dispatched, its relayer fee is pulled into the host as `feeToken()` at that time and recorded purely as a `uint256` amount: `_requestCommitments[commitment] = FeeMetadata({sender: post.payer, fee: post.fee});` [5](#0-4) . No token identifier is stored alongside the amount.
2. On delivery (e.g. `dispatchIncoming` for a `GetResponse`), the reward is paid using whatever `feeToken()` currently resolves to: `IERC20(feeToken()).safeTransfer(relayer, fee);` [6](#0-5) . The same pattern (current `feeToken()`, stored `fee` amount) is used for POST/GET timeout refunds [7](#0-6) .
3. `updateHostParamsInternal` (reachable via cross-chain governance `HostManager.onAccept` → `IHostManager.updateHostParams`, and via the admin path on `TestnetHost`) enforces a single guard against migrating `feeToken`: the *current* balance of the old token must be zero. [8](#0-7) 
4. That guard is not robust: `withdraw()`, callable by the same `hostManager`, transfers an arbitrary `params.amount` of an arbitrary `params.token` (including the fee token) to a beneficiary with no bookkeeping tying it to "excess over reserved fees": [9](#0-8) . The contract has no separate accounting for "amounts reserved against `_requestCommitments`/`_responseCommitments`" versus "sweepable protocol revenue" — it is one pooled ERC20 balance.
5. Consequently, governance sweeping revenue via `withdraw()` down to (or near) zero, immediately followed by an `updateHostParams()` call to migrate `feeToken` (e.g. DAI → USDC, or to a token with a different price), satisfies the `CannotChangeFeeToken` check even though many `_requestCommitments`/`_responseCommitments` entries with nonzero `fee` are still outstanding for requests dispatched under the old token. When those requests are later delivered or time out, the relayer/payer is paid the *old* numeric `fee` value in the *new* token — identical in effect to the `ERC20Rewards` bug where holders of an old reward period get paid their old numeric amount in a token with different decimals/value.

### Impact Explanation
Relayers who already did the work of delivering messages (or payers awaiting timeout refunds) receive amounts that are wrong by orders of magnitude whenever the new fee token's decimals or unit value differ from the old one (e.g., an 18-decimal DAI fee amount transferred in 6-decimal USDC pays 10^12× too much, draining the host's new fee-token balance and starving/overpaying arbitrary counterparties; the reverse direction underpays relayers by the same factor, causing systematic fund loss for the relayer network). Because the same pooled balance backs live in-flight commitments across the whole bridge, this can result in outright loss of relayer fee funds or protocol insolvency in the new fee token, i.e. concrete theft/freezing of funds in the fee/reward-accounting path explicitly in scope.

### Likelihood Explanation
This does not require a malicious operator — it only requires the documented, intended governance operations ("sweep revenue" then "migrate fee token to a fixed/better token", explicitly anticipated by the contract's own comments, e.g. "It's important that before changing this parameter, that all funds have been drained from the previous feeToken" [10](#0-9) ) to be performed in the ordinary sequence a team would use, without realizing `withdraw()`'s notion of "drained" silently includes funds reserved for pending relayer deliveries. Given that `CannotChangeFeeToken` was added specifically to prevent this class of bug but checks raw balance instead of "balance minus outstanding commitments," the protection is incomplete and the unsafe path is one governance withdrawal + one params update away, both of which are the *sanctioned* way to change the fee token.

### Recommendation
Track total outstanding reserved fees (sum of nonzero `FeeMetadata.fee` across live `_requestCommitments`/`_responseCommitments`) separately from sweepable revenue, and have both `withdraw()` and `updateHostParamsInternal`'s balance check account for that reserved total (i.e., only allow `withdraw` to remove the "excess" above reserved fees, and only allow a fee-token change once reserved-fee-adjusted balance is zero). Alternatively, store the fee token address alongside each `FeeMetadata` entry at dispatch time and settle/refund using that stored token rather than `feeToken()` at settlement time, so a mid-flight token migration cannot mismatch value/decimals for already-escrowed fees.

### Proof of Concept
1. Governance deploys with `feeToken = DAI` (18 decimals).
2. Multiple users dispatch POST/GET requests with `fee = 100e18` (100 DAI) each; each fee is pulled into the host and recorded in `_requestCommitments[...]` [5](#0-4) . Host DAI balance grows to, say, `1000e18`, of which say `900e18` are truly "spare" protocol revenue and `100e18` back one still-undelivered request.
3. Governance calls `withdraw({token: DAI, amount: 1000e18, beneficiary: treasury})` via `HostManager.onAccept` [9](#0-8) , intending only to sweep the 900 DAI of revenue but, since there is no separate accounting, is able to withdraw the full balance including the 100 DAI still owed to the pending request's relayer.
4. Host DAI balance is now `0`. Governance calls `updateHostParams` with `feeToken = USDC` (6 decimals); `CannotChangeFeeToken` does not revert because `balanceOf(DAI) == 0` [8](#0-7) .
5. A relayer later delivers the pending response; `dispatchIncoming` reads `fee = 100e18` from `_requestCommitments` and calls `IERC20(feeToken()).safeTransfer(relayer, 100e18)` where `feeToken() == USDC` [6](#0-5) , attempting to pay out `100e18` (100 quintillion) units of a 6-decimal token — either reverting (griefing the relayer's payout / DoS on delivery) or, if the host happens to hold that much USDC from unrelated inflows, paying a catastrophically wrong amount.

    function dispatchIncoming(GetResponse memory response, address relayer) external restrict(_hostParams.handler) {
        // replay protection
        bytes32 commitment = response.request.hash();
        _responseReceipts[commitment] = ResponseReceipt({
            relayer: relayer,
            responseCommitment: response.hash()
        });

        (bool success,) = _bytesToAddress(response.request.from)
            .call(abi.encodeWithSelector(IApp.onGetResponse.selector, IncomingGetResponse(response, relayer)));

        if (!success) {
            // so that it can be retried
            delete _responseReceipts[commitment];
            return;
        }

        // reward the relayer fee
        uint256 fee = _requestCommitments[commitment].fee;
        if (fee != 0) {
            IERC20(feeToken()).safeTransfer(relayer, fee);
        }
        emit GetRequestHandled({commitment: commitment, relayer: relayer});
    }
