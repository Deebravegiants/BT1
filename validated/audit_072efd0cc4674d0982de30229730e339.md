## Title
Withdrawal status/hash misreported when batching multiple withdrawals of the same token via POA Bridge - (File: `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`)

### Summary
`PoaBridge.describeWithdrawal()` matches a POA Bridge withdrawal status response to a specific `withdrawalParams` entry using **only the asset ID**, not the amount, destination address, or withdrawal index. When a batch withdrawal (`processWithdrawal` with an array of `withdrawalParams`) contains two or more entries with the same `assetId` (e.g. two separate withdrawals of the same token to different destination addresses/amounts), the lookup can bind the wrong on-chain result to the wrong logical withdrawal.

### Finding Description
`describeWithdrawal()` calls `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`, which does: [1](#0-0) 

This function only checks `nep141:${w.data.near_token_id} === assetId` — it ignores `destinationAddress`, `amount`, and the withdrawal `index`. The function's own comment explicitly acknowledges: "multiple withdrawals of the same token in a single transaction are not supported." [2](#0-1) 

`describeWithdrawal()` uses this match to report `completed`/`failed`/`pending` status and the destination-chain `txHash` back to the caller: [3](#0-2) 

This status is what `watchWithdrawal()` (used by `waitForWithdrawalCompletion` / `createWithdrawalCompletionPromises`) relies on to resolve or reject each withdrawal promise per index: [4](#0-3) 

If a caller submits two withdrawals of the same `assetId` in one batch (e.g., two BTC withdrawals to two different addresses), and the underlying POA API returns multiple withdrawal records for that hash, `findMatchingWithdrawal` returns the **first** record matching the asset id for *both* logical withdrawals, regardless of which index/destination it actually belongs to. If one of the two withdrawals fails while the other succeeds, both polling calls (for index 0 and index 1) can independently resolve against the single matched record — causing the SDK to report `completed` with a `txHash` for a withdrawal that did not actually complete (or to report the same `txHash` for both), while the other one's real outcome is never surfaced correctly.

### Impact Explanation
This breaks the equality "status/txHash reported by the SDK == actual on-chain outcome for that specific withdrawal." An integrator that trusts `waitForWithdrawalCompletion`/`createWithdrawalCompletionPromises` results to mark a specific withdrawal as settled (e.g., to release funds, mark an invoice paid, or avoid re-processing) could credit or consider settled a withdrawal that never actually landed on-chain, or double-count a single successful transfer as satisfying two distinct withdrawal obligations. This matches the High impact category: "a status or hash misreport making an integrator credit or refund twice."

### Likelihood Explanation
Requires the caller to legitimately batch ≥2 withdrawals of the same `assetId` in a single `processWithdrawal`/intent transaction (a supported, non-malicious usage pattern — `WithdrawalParams[]` and batch APIs exist precisely for this). No malicious actor action is needed; it's triggered by ordinary use of the documented batch-withdrawal feature combined with same-asset entries, which the code does not validate against or reject.

### Recommendation
- Reject/validate at `processWithdrawal`/`signAndSendWithdrawalIntent` time when multiple `withdrawalParams` in a batch share the same `assetId` for the POA Bridge route, until the underlying API supports disambiguation.
- Alternatively, disambiguate matches using `amount` and `destinationAddress` (and ordering) in addition to `assetId`, and only fall back to index-based matching once uniqueness is confirmed, throwing a clear error if the match is ambiguous instead of silently returning a possibly-incorrect record.

### Proof of Concept
1. Call `sdk.processWithdrawal` with `withdrawalParams` as an array containing two entries with the same `assetId` (e.g., `nep141:btc.omft.near`) but different `destinationAddress`/`amount`, routed through PoA Bridge.
2. Suppose the first withdrawal actually fails/refunds on the bridge while the second completes.
3. `getWithdrawalStatusWithRetry` returns both records; `findMatchingWithdrawal` for index 0's `describeWithdrawal` call matches on `assetId` alone and returns whichever record appears first (potentially the completed one meant for index 1).
4. `waitForWithdrawalCompletion`/`createWithdrawalCompletionPromises` resolves index 0's promise as `completed` with a `txHash`, even though that specific withdrawal never landed — see the matching code at [3](#0-2)  and [1](#0-0) .

```typescript
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}
```

```typescript
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
```
