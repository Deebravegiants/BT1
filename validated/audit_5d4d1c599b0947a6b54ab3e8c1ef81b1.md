### Title
Missing `feeEstimation.amount` guard in `createWithdrawalIntents` allows negative `actualAmount` when called with a caller-supplied `feeEstimation` - (packages/intents-sdk/src/sdk.ts)

### Summary
`IntentsSDK.createWithdrawalIntents` computes `actualAmount = withdrawalParams.amount - feeEstimation.amount` for `feeInclusive: true` withdrawals with no `FeeExceedsAmountError`/`assert` guard at that call site, unlike `_estimateWithdrawalFee` which does check `amount <= fee.amount` before subtracting. Because `feeEstimation` is a plain caller-supplied object (not derived internally), a caller who calls `createWithdrawalIntents` (or `signAndSendWithdrawalIntent`/`processWithdrawal` with an explicit `feeEstimation`) can pass `amount < feeEstimation.amount` and get a negative `actualAmount` baked into the withdrawal intent.

### Finding Description
The claimed broken equality is: **debited amount == authorised withdrawal amount + fee, exactly once, and non-negative**.

In `packages/intents-sdk/src/sdk.ts`:
```
342: const actualAmount = args.withdrawalParams.feeInclusive
343:   ? args.withdrawalParams.amount - args.feeEstimation.amount
344:   : args.withdrawalParams.amount;
``` [1](#0-0) 
there is no check that `amount > feeEstimation.amount` before subtracting, whereas `_estimateWithdrawalFee` performs exactly this check right before computing the same expression:
```
421: if (args.withdrawalParams.feeInclusive) {
422:   if (args.withdrawalParams.amount <= fee.amount) {
423:     throw new FeeExceedsAmountError(fee, args.withdrawalParams.amount);
424:   }
425: }
``` [2](#0-1) 

`createWithdrawalIntents` is a public method reachable directly, or indirectly via `signAndSendWithdrawalIntent` (line 706) and `processWithdrawal` (which accepts `args.feeEstimation` directly from the caller instead of calling `estimateWithdrawalFee`, see lines 801-812). Since `FeeEstimation` is just a data object with `amount`/`quote`/`underlyingFees` fields, nothing prevents an integrator/caller from constructing an arbitrary `feeEstimation.amount` (e.g., forwarding a stale or attacker-influenced quote) and pairing it with a small `withdrawalParams.amount`.

After `actualAmount` goes negative, it is passed into `bridge.validateWithdrawal({ amount: actualAmount, ... })` and then into `bridge.createWithdrawalIntents({ withdrawalParams: { ...args.withdrawalParams, amount: actualAmount }, ... })`. Whether this negative amount is caught depends entirely on the specific bridge's `validateWithdrawal`:
- `OmniBridge.validateWithdrawal` has multiple amount-related checks (`verifyTransferAmount`, `MinWithdrawalAmountError` comparisons against `MIN_AMOUNT_SOL_OMNI_WITHDRAWAL`, UTXO min-amount checks) that would very likely reject a negative amount as being below the minimum. [3](#0-2) 
- `DirectBridge.validateWithdrawal`, however, performs **no amount check at all** — it only validates the destination address, checks the token address doesn't match the destination, and checks NEAR account existence: [4](#0-3)  A negative `actualAmount` passes through unchecked into `createWithdrawIntentPrimitive({ amount: args.withdrawalParams.amount, ... })` at [5](#0-4) , which (per the question's premise) serialises the bigint via `.toString()`, producing a value like `"-500"` in the `ft_withdraw` intent's `amount` field.

Existing guards (`validateAddress`, `compareAddresses`, account-existence checks in `DirectBridge`) do not check the amount's sign, so the divergence is not caught for the `NearWithdrawal` (`DirectBridge`) route. The `_estimateWithdrawalFee` guard only protects the "estimate-then-withdraw" happy path; it does not protect direct calls to `createWithdrawalIntents` with a caller-controlled `feeEstimation`.

### Impact Explanation
If the resulting intent is signed, submitted, and accepted by the intents contract, a negative `ft_withdraw.amount` string breaks the intended debit accounting (`amount + fee` computed and applied exactly once, non-negative) for the caller's own withdrawal request. If the contract rejects malformed amounts, this is a self-inflicted denial-of-service on the caller's own request (low impact — attacker only harms themselves, no cross-user fund movement). If the contract mishandles negative amounts unexpectedly, this could corrupt the signed intent's economic terms. This affects only the calling user's own funds/signature slot (no cross-user fund misdirection identified), which limits the severity compared to the "Critical" bar of moving funds an unrelated party did not authorise.

### Likelihood Explanation
Preconditions: the caller must invoke `createWithdrawalIntents` (or `signAndSendWithdrawalIntent`/`processWithdrawal`) supplying its own `feeEstimation` object (bypassing the SDK's `estimateWithdrawalFee`) with `feeEstimation.amount > withdrawalParams.amount`, and select a route (e.g., NEAR/`DirectBridge`) whose `validateWithdrawal` does not check the amount sign. This requires the caller/integrator to deliberately construct an inconsistent `feeEstimation`, which is unusual but technically permitted by the public API surface (no type-level or runtime restriction ties `feeEstimation` to a prior `estimateWithdrawalFee` call).

### Recommendation
Add the same `FeeExceedsAmountError` check used in `_estimateWithdrawalFee` to `createWithdrawalIntents` before computing `actualAmount`, e.g.:
```ts
if (args.withdrawalParams.feeInclusive && args.withdrawalParams.amount <= args.feeEstimation.amount) {
  throw new FeeExceedsAmountError(args.feeEstimation, args.withdrawalParams.amount);
}
```
Additionally, add an explicit non-negative amount assertion in `DirectBridge.validateWithdrawal` (and any other bridge lacking an amount check) as defense-in-depth.

### Proof of Concept
```ts
// packages/intents-sdk/src/sdk.createWithdrawalIntents.negativeAmount.test.ts
it("produces a negative ft_withdraw amount when feeEstimation.amount > withdrawalParams.amount", async () => {
  const sdk = new IntentsSDK({ referral: "test" });
  const intents = await sdk.createWithdrawalIntents({
    withdrawalParams: {
      assetId: "nep141:usdc.near", // routed via DirectBridge (NearWithdrawal)
      amount: 10n,
      feeInclusive: true,
      destinationAddress: "alice.near",
    },
    feeEstimation: { amount: 1000n, quote: null, underlyingFees: {} },
  });

  const ftWithdraw = intents.find((i) => i.intent === "ft_withdraw");
  // Assert both sides of the broken equality:
  // expected: debited amount == withdrawalParams.amount - feeEstimation.amount >= 0
  expect(ftWithdraw?.amount).toBe("-990"); // currently reproduces a negative string
  // desired: should instead throw FeeExceedsAmountError before reaching here
});
```
This test mocks only HTTP dependencies used by `DirectBridge` (NEAR RPC provider stubs) and directly demonstrates that `createWithdrawalIntents` emits a negative `ft_withdraw.amount` string with no thrown error.
