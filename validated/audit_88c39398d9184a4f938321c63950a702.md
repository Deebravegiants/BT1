### Title
Webhook `shop-domain`/`topic` headers are not covered by the HMAC signature, allowing cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC over the raw request body, then unconditionally trusts the `shop-domain`, `topic`, `webhook_id`, and `api_version` HTTP headers — none of which are covered by that HMAC — to decide which handler runs and which shop/tenant the payload is attributed to.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Registry.process` validates the HMAC via `Utils::HmacValidator.validate(request)`, which computes the signature over `to_signable_string` (i.e. the raw body only) and compares it to the `hmac-sha256` header: [2](#0-1) 

After that single check, `process` looks up the handler by `request.topic` and constructs `WebhookMetadata` using `request.shop` and `request.topic`, both of which come directly from HTTP headers that were never part of the signed material: [3](#0-2) 

`request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` are all read straight from headers with no cryptographic binding to the HMAC: [4](#0-3) 

The broken identity binding, stated as an equality that fails to hold:
`shop/topic asserted by the (unauthenticated) HTTP headers == shop/topic that the HMAC-signed body actually originated for`.

Because an app's `client_secret` (`Context.api_secret_key`) is shared across every shop that installs the app — it is not shop-specific — any unprivileged internet user can install the target app on their own store (no privileged credentials required) and thereby receive a webhook whose body is legitimately HMAC-signed by Shopify using that shared secret. Since the signature covers only the raw body, the attacker can replay that exact `(raw_body, hmac)` pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` and/or `x-shopify-topic` headers to claim the payload belongs to a different shop or a different (registered) topic. `Utils::HmacValidator.validate` still returns `true` because the body bytes it verifies are unchanged, and `Registry.process` will happily route the forged `shop`/`topic` values into the handler's `WebhookMetadata`.

### Impact Explanation
This crosses a tenant boundary: the host application's webhook handler receives a `WebhookMetadata#shop` value that has no cryptographic relationship to the actual signed content, letting an attacker who controls only their own shop's installation impersonate another tenant (or invoke a different topic's handler with attacker-supplied data) in the app's webhook processing pipeline. Any app logic that keys tenant-scoped state (session lookups, per-shop data writes, mandatory GDPR handlers like `customers/redact`/`shop/redact`) off `WebhookMetadata#shop` or `#topic` is exposed to cross-tenant data corruption/confusion driven entirely by attacker-controlled, unauthenticated headers. This matches the "cross-tenant access" Critical impact category, since the trust boundary that should separate one merchant's webhook traffic from another's is not enforced by this gem.

### Likelihood Explanation
Exploitation only requires an attacker to (1) install the target app on a shop they control (no special credential is needed, this is normal, unprivileged Shopify app installation) to obtain one genuine `(raw_body, hmac)` pair, and (2) send a crafted HTTP request to the app's public webhook endpoint with the captured body/HMAC but forged `shop-domain`/`topic` headers. No access token, `client_secret`, or leaked credential is required from the victim shop. This is a low-effort, reliably reproducible attack path entirely within this gem's own webhook-verification code.

### Recommendation
Bind the `shop-domain`, `topic`, `webhook_id`, and `api_version` header values into the signed material verified by `HmacValidator` (e.g., include them alongside the body when computing/verifying the signature, or otherwise cryptographically tie them to the request), so that any header used to route or attribute a webhook cannot be altered without invalidating the HMAC.

### Proof of Concept
1. Register a webhook handler and app with the gem; deploy the endpoint that calls `ShopifyAPI::Webhooks::Registry.process(request)`.
2. As an attacker, install the app on `attacker-shop.myshopify.com` and capture a real Shopify webhook delivery for, e.g., topic `orders/create`, noting its raw body `B` and its valid `x-shopify-hmac-sha256` value `H` (computed by Shopify using the app's shared `client_secret`).
3. Send a forged HTTP POST to the app's webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H` (unchanged), but headers `x-shopify-shop-domain: victim-shop.myshopify.com` and/or `x-shopify-topic: customers/redact`.
4. `Utils::HmacValidator.validate(request)` returns `true` because `to_signable_string` (the body) is unchanged: [1](#0-0) .
5. `Registry.process` invokes the handler registered for the forged topic and passes `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: "customers/redact", body: JSON.parse(B), ...)`, causing the host application to process attacker-controlled body content as though it were an authentic, HMAC-verified webhook for the victim shop and/or topic: [3](#0-2) .
