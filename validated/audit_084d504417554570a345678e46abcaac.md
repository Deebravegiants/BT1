### Title
Webhook shop/topic attribution bypass via HMAC that only covers the request body, not headers - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes and validates the webhook HMAC over the raw body alone, while the `shop`, `topic`, `webhook_id`, and `api_version` values used for routing and tenant attribution are taken from unsigned HTTP headers.

### Finding Description
The identity binding broken here is: **shop/topic authenticated (bytes covered by HMAC) ≠ shop/topic acted upon (bytes trusted by the app)**.

`to_signable_string` returns only the raw body: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all pulled from headers, not the signed body: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC using `to_signable_string`, i.e., the body only: [3](#0-2) 

`Registry.process` accepts the request once the body's HMAC checks out, then uses the *unsigned* `request.topic` to select the handler and passes the *unsigned* `request.shop` straight into `WebhookMetadata`, which apps use to identify which merchant the event belongs to: [4](#0-3) 

`WebhookMetadata.shop` and `.topic` are documented as authoritative fields consumed by host-app handlers: [5](#0-4) 

Because the HMAC only proves the *body* was signed by someone holding `api_secret_key` (i.e., genuinely came from Shopify for *some* topic/shop), it proves nothing about which shop or topic that body was actually delivered for. A body+HMAC pair legitimately generated for one shop/topic can be replayed with different `x-shopify-shop-domain`/`x-shopify-topic` header values and will still pass `HmacValidator.validate`, since those headers are never part of the signed content.

### Impact Explanation
This breaks the shop-authenticated-vs-shop-acted-upon binding. In a multi-tenant Shopify app, an unprivileged user who legitimately installs the app on their own store (and can thus lawfully receive a body+HMAC pair for their own shop/topic) can replay that same body+HMAC with a forged `shop-domain` header pointing at a victim shop, or a forged `topic` header selecting a more privileged webhook handler. `Registry.process` will accept it as valid (HMAC passes) and dispatch `WebhookMetadata` carrying the attacker-chosen `shop`/`topic` to the handler, which typically persists/acts on data keyed by that `shop`. This is a cross-tenant data-integrity/attribution bypass consistent with the "field acted on but not covered by the HMAC" analog class.

### Likelihood Explanation
Requires the attacker to possess (or be able to trigger, e.g. by installing the app on their own store and generating an event) at least one legitimate body+HMAC pair, and network-level ability to POST to the app's public webhook endpoint with modified headers — both readily achievable by any unprivileged app user/merchant, without needing `api_secret_key` or any credential theft.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the signed payload used for HMAC verification (or otherwise cryptographically bind them to the body), so that `HmacValidator.validate` fails if any of these header-derived attribution fields are altered relative to what Shopify actually signed for that delivery.

### Proof of Concept
1. App legitimately receives webhook A: `raw_body="{...}"`, headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: orders/create`, `x-shopify-hmac-sha256: <valid HMAC of raw_body>`.
2. Attacker resends the identical `raw_body` and `x-shopify-hmac-sha256` to the same endpoint, but with `x-shopify-shop-domain: victim-shop.myshopify.com` and/or `x-shopify-topic: shop/redact`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC solely over `raw_body` — it matches, so validation passes.
4. The handler registered for the (attacker-controlled) topic is invoked with `WebhookMetadata.shop == "victim-shop.myshopify.com"`, even though Shopify never signed anything attributing this body to that shop.
