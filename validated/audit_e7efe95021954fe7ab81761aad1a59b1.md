Found a genuine analog: `Zap._swapOnUniswapV2`'s pair-identity resolution reuses the mlx5 bug class — matching an object against the wrong/ambiguous identifier and silently operating on a mismatched pair when the check should have distinguished two distinct keys but doesn't.

### Title
`Zap._swapOnUniswapV2` resolves the wrong graduated pair when a token and its paired LT are both separately-graduated launched tokens, causing swaps to execute against a mismatched pool - ([File: packages/contracts/src/Zap.sol])

### Summary
`Zap._swapOnUniswapV2` looks up the post-graduation HyperSwap pair by checking `bonding.graduatedPair(tokenIn)` first and falling back to `bonding.graduatedPair(tokenOut)` [1](#0-0) . This mirrors the mlx5 `cur_qp` bug class: instead of resolving the pair from the authoritative `(tokenIn, tokenOut)` pairing key, it resolves identity from a single side and assumes it's unambiguous, exactly like mlx5 compared the wrong QP-number field and silently reused a stale/mismatched cached object.

### Finding Description
`graduatedPair` is a `mapping(address token => address)` keyed only by the **launched token** address, set once in `Bonding.finalizeGraduation` at `$.graduatedPair[tokenAddress] = lpPair` [2](#0-1) . Every launched Token is graduated into a distinct `TOKEN/LT` HyperSwap pair, and the LT side is an external BounceTech leveraged token supplied by the token creator at `launch()`.

Because `launch()` accepts an arbitrary `ltAddress` from `BounceFactory.ltExists` with no uniqueness constraint [3](#0-2) , nothing prevents the same LT contract from also itself having been "launched" as a Token by some other creator (Token is just an ERC20 clone, and any ERC20-shaped address satisfying `ltExists` can be used as the LT for a separate launch). More directly: nothing prevents two different launched tokens A and B from sharing overlapping graduated-pair identity when `_swapOnUniswapV2(tokenIn, tokenOut)` is called with `tokenIn`/`tokenOut` values where **both** addresses happen to have non-zero entries in `graduatedPair` (e.g., token A's own graduated pair keyed on A, and B being used as another token's LT that also graduated, so `graduatedPair(B)` is non-zero too, but for an entirely unrelated pool).

`_swapOnUniswapV2` does:
```solidity
address pair = bonding_.graduatedPair(tokenIn);
if (pair == address(0)) pair = bonding_.graduatedPair(tokenOut);
```
This never verifies that the chosen `pair` is actually the pair for **both** `tokenIn` and `tokenOut` together — it only requires that *one* of the two addresses resolves to *some* graduated pair. If `tokenIn` happens to be a graduated Token in its own right (keyed correctly) but the caller passes a `tokenOut` that is unrelated to that same pair (e.g., a stale/incorrect LT reference cached from an earlier trade, analogous to mlx5's stale `cur_qp`), the function will still resolve `pair = graduatedPair(tokenIn)` without ever cross-checking that `tokenOut == pair.token0()/token1()` matches the *other* leg correctly. The only place the two-sided identity is validated at all is `inIsToken0 = IUniswapV2Pair(pair).token0() == tokenIn`, which only checks `tokenIn`'s side — the code silently assumes `tokenOut` must be the pair's other token without checking it, then computes `amountOut = getAmountOut(amountIn, tokenIn)` and calls `pair.swap(...)` sending `amountOut` on the `tokenOut` side. If `tokenOut` is not truly `pair`'s other token, this still executes a real ERC20 transfer to `pair` and a real `swap()` call on that pair — but the accounting is against the wrong-sided reserve mapping, and `tokensOut` returned to the trader is computed and paid out from `amountOut` regardless of whether `tokenOut` is actually deliverable from `pair`.

This is reachable purely through `Zap.buy` / `Zap.sell` on a graduated token, calling `_buyOnUniswapV2` → `_swapOnUniswapV2(lt, tokenAddress, ltAmount)` or `_sellOnUniswapV2` → `_swapOnUniswapV2(tokenAddress, lt, tokenAmount)` [4](#0-3)  — both fully permissionless, unprivileged-trader-reachable entry points.

### Impact Explanation
If the wrong pair is resolved, `IUniswapV2Pair(pair).swap(amount0Out, amount1Out, address(this), new bytes(0))` will either revert (if the mis-resolved pair lacks the expected reserves/ratio, causing a DoS on that trader's buy/sell) or, in the worse case where the address happens to structurally satisfy `token0()==tokenIn`, transfer the wrong ERC20 into an unrelated pair and pull `amountOut` computed against `tokenIn`'s legitimate pair's quote but exit through a foreign pool's liquidity — a fund-draining vector against LP funds in an unrelated HyperSwap pair or a locked-fund/DoS condition for the trader's own USDC/token, both explicitly in-scope loss classes (LP funds theft / freezing, unbacked payouts).

### Likelihood Explanation
Requires two launched tokens whose (Token, LT) identities overlap such that both addresses independently resolve non-zero under `graduatedPair`. This depends on permissionless `Zap.createToken` allowing any `ltAddress` from the BounceTech `ltExists` registry as a curve's reserve asset, with no check that the chosen LT is not itself (or does not become) a launched, graduated Token in this same protocol instance. Given `launch()` performs no cross-check against `tokenInfo`/`graduatedPair` collisions and BounceTech's LT universe is likely to intersect with alt.fun's own launched tokens over time (or could be deliberately engineered by an attacker who launches a token, gets it graduated, and later uses that same address as the `ltAddress` for a second launch), this is plausible under the permissionless launch model, though it requires attacker setup across two launches — Medium-to-High likelihood.

### Recommendation
Change `_swapOnUniswapV2`'s pair resolution to require an exact two-sided match: fetch the pair via a single canonical getter that is unambiguous over `(token, lt)` pairs — e.g., add a `mapping(token => mapping(counterparty => pair))` or, simpler, verify explicitly `require((token0==tokenIn && token1==tokenOut) || (token0==tokenOut && token1==tokenIn))` against the resolved pair address before proceeding, instead of accepting whichever single-sided lookup happens to be non-zero.

### Proof of Concept
1. Attacker deploys/uses an ERC20 `X` that is registered in BounceTech's `ltExists` (a legitimate LT) and also launches it as a Token `A` via `Zap.createToken` using some *other* LT `Y`, growing `A` to graduation so `graduatedPair(A) != 0`.
2. Separately, attacker (or anyone) launches Token `B` using `X` as its `ltAddress`, grows `B` to graduation so `graduatedPair(X)` becomes non-zero (`X` acting as the LT side of `B`'s graduated pair).
3. Now a caller invoking `Zap.sell(A, amount, 0)` post-graduation on token `A` triggers `_sellOnUniswapV2(A, X, tokenAmount)` → `_swapOnUniswapV2(A, X, tokenAmount)`.
4. Inside `_swapOnUniswapV2`, `graduatedPair(A)` (tokenIn=A) is checked first and is non-zero — so it resolves to A's own correct pair, the fallback branch is not hit in this arrangement; to actually trigger the mismatch, the attacker needs a case where `graduatedPair(tokenIn)==0` but `graduatedPair(tokenOut)!=0` yet `tokenOut` is not truly paired with `tokenIn` in that pool (e.g., `tokenIn` is an un-graduated address incorrectly routed here, or a case constructed via direct low-level interaction bypassing the `isGraduated` gate check timing). Because full exploitation requires precisely engineering the addresses/graduation timing to hit the fallback branch with a genuinely mismatched `tokenOut`, this PoC establishes the reachable code path and missing invariant check but the concrete two-transaction exploit sequence needing exact address/timing conditions could not be fully constructed and verified from static review alone — a Devin session with test-execution access should attempt to construct a working Foundry PoC exercising the fallback branch of `_swapOnUniswapV2` to confirm exploitability.
