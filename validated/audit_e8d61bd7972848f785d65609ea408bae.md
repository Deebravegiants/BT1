### Title
Webhook `shop`, `topic`, `webhook_id`, and `api_version` fields are trusted by the gem's `Registry.process` without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC over the raw request body, then passes the caller-supplied `shop-domain`, `topic`, `webhook-id`, and `api-version` headers straight into `WebhookMetadata` and the app's handler as trusted, Shopify-attested values, even though none of these fields are part of the signed data.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all read directly from HTTP headers and are not part of the signed string: [2](#0-1) 

`Registry.process` validates the HMAC via `Utils::HmacValidator.validate(request)`, and if it passes, forwards `request.topic` and `request.shop` (both unauthenticated header values) into `WebhookMetadata`, which is then handed to the app-provided handler as trusted data: [3](#0-2) 

`HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` (i.e. the raw body only) and compares it to the `hmac` header: [4](#0-3) 

`WebhookMetadata.shop` is documented as "The shop domain of the webhook" and is expected by app authors to be a Shopify-verified identity used to route webhook data to the correct tenant: [5](#0-4) [6](#0-5) 

The binding that should hold is: `shop header == shop cryptographically bound to hmac(body)`. In reality, `hmac == HMAC(client_secret, raw_body)` only, with no dependence on `shop`, `topic`, `webhook_id`, or `api_version`. Consequently `hmac` and `shop` are independent: any `(body, hmac)` pair that is valid for shop A remains a byte-for-byte valid HMAC for a request claiming to be from shop B, C, etc., because the signature never covers the shop identity.

### Impact Explanation
This breaks the tenant-identity binding the gem is documented to provide (`Registry.process` is described as verifying "the request did indeed come from Shopify" before dispatching `data.shop` to the handler). An attacker who is a legitimate, unprivileged merchant/installer of the multi-tenant app can:
1. Install the app on their own shop (shop A) — no special privilege required.
2. Passively capture one legitimate webhook delivery from Shopify to the app's endpoint (raw body + `X-Shopify-Hmac-Sha256` + other headers) for shop A.
3. Replay the exact same raw body and HMAC to the app's public webhook endpoint, but with the `X-Shopify-Shop-Domain` header changed to shop B's domain (or any other tenant they want to target).
4. Because `to_signable_string` covers only the body, `HmacValidator.validate` still succeeds, and `Registry.process` dispatches `WebhookMetadata.new(shop: "shop-b.myshopify.com", topic: ..., body: <shop-A's-data>, ...)` to the app's handler.

If the host app's webhook handler uses `data.shop` (as documented) to attribute/store the body's contents against a tenant record (which is the primary documented use case — see the example `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), this produces cross-tenant data injection: shop A's order/customer/data can be attributed to and stored under shop B's account, or used to trigger shop-B-scoped side effects. This matches the "Critical — cross-tenant access" impact category, since it crosses a tenant boundary using only a replayed, unprivileged webhook capture — no access token, secret, or privileged account is required.

### Likelihood Explanation
Likelihood is moderate-to-high in realistic deployments: capturing one's own webhook deliveries requires nothing more than installing the app (which any merchant can do) and observing traffic to their own configured endpoint (e.g., via a debugging proxy) — a capability every legitimate merchant already has for their own shop. No secret key, token, or TLS interception of another party's traffic is needed since the attacker intercepts their *own* webhook. This is fully within the "unprivileged internet user" model, and the vulnerable code path (`Request#to_signable_string`, `HmacValidator.validate`, `Registry.process`) is exactly the gem's documented, first-class API for webhook verification, not a misuse of undocumented behavior.

### Recommendation
Extend `Request#to_signable_string` (or the verification path in `HmacValidator`/`Registry.process`) to cryptographically bind the identity fields the app relies on — at minimum the `shop-domain` header — into the signed material, or explicitly document that `shop`, `topic`, `webhook_id`, and `api_version` are unauthenticated and must be independently verified/authorized by the host app (e.g., cross-checked against a known/installed shop list) before being trusted for tenant attribution. Shopify's actual webhook HMAC as delivered by the platform is computed over the body only by design, so the safer fix is for the gem to clearly warn/document this gap and/or provide a helper that validates `shop` against the app's known installed shops before dispatch, rather than presenting `WebhookMetadata.shop` as an implicitly trusted, Shopify-verified value.

### Proof of Concept
```ruby
# Step 1: Attacker installs the app on their own shop and captures one
# legitimate webhook delivery for "shop-a.myshopify.com":
raw_body = '{"id":123,"note":"legit order for shop A"}'
hmac_header = Base64.strict_encode64(
  OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), api_secret_key, raw_body)
)

original_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => hmac_header,
  "x-shopify-shop-domain" => "shop-a.myshopify.com",
}

# Step 2: Attacker replays the identical body + hmac to the app's public
# webhook endpoint, only swapping the shop-domain header to a victim shop:
forged_headers = original_headers.merge(
  "x-shopify-shop-domain" => "shop-b.myshopify.com" # victim tenant
)

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

# Step 3: HMAC validation succeeds because to_signable_string only covers
# raw_body, which is unchanged:
ShopifyAPI::Utils::HmacValidator.validate(request) # => true

# Registry.process will now call the handler with:
#   WebhookMetadata(shop: "shop-b.myshopify.com", topic: "orders/create", body: <shop A's data>, ...)
ShopifyAPI::Webhooks::Registry.process(request)
```
The handler receives shop A's webhook body attributed to shop B, demonstrating that the `shop` (and `topic`/`webhook_id`/`api_version`) fields are not bound to the HMAC that gates trust in `Registry.process`.

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
