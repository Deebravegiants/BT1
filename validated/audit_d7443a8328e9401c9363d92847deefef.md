### Title
Webhook `shop-domain`, `topic`, `api-version`, and `webhook-id` headers are not covered by the HMAC signature, allowing tenant-identity spoofing on an otherwise validly-signed webhook body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` implements the `Utils::VerifiableQuery` interface used by `HmacValidator.validate` to authenticate incoming webhooks. Its `to_signable_string` only returns the raw request body, while `shop`, `topic`, `api_version`, and `webhook_id` are all pulled from HTTP headers that are never included in the signed material. `Registry.process` trusts `request.shop` (and the other header-derived values) as authentic tenant/context data as soon as `HmacValidator.validate` succeeds, breaking the intended binding between "HMAC verified" and "shop attributed."

### Finding Description
`HmacValidator.validate` computes `OpenSSL::HMAC.hexdigest` over `verifiable_query.to_signable_string` using `Context.api_secret_key`, and compares it against the `hmac` value with `OpenSSL.secure_compare`: [1](#0-0) 

For OAuth callbacks, `Auth::Oauth::AuthQuery#to_signable_string` correctly folds `shop` into the signed string, so `shop` is bound to the signature: [2](#0-1) 

For webhooks, however, `Webhooks::Request#to_signable_string` returns only the raw body — none of the identity/context fields are included: [3](#0-2) 

`shop`, `topic`, `api_version`, and `webhook_id` are all read directly from attacker/network-controlled HTTP headers via `shopify_header`, with no cryptographic binding to the HMAC: [4](#0-3) [5](#0-4) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop`/`request.topic`/etc. to build the `WebhookMetadata` passed to the app's handler, treating the request as fully authenticated for that shop: [6](#0-5) 

The identity binding broken here is: `HMAC-verified == body-authentic-for-any-shop`, not `HMAC-verified == body-authentic-for-the-specific-shop-in-the-shop-domain-header`. Any party who can capture (or otherwise obtain) one validly-signed webhook body/HMAC pair for their own shop (e.g., their own store, on which they can trigger webhook-firing actions such as creating an order) can replay that exact body+HMAC to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header value. Because the signature only covers the body, the signature still validates, and the handler receives `WebhookMetadata` attributing the (attacker-controlled) body to a shop of the attacker's choosing.

### Impact Explanation
This is a cross-tenant identity-spoofing vector: an unprivileged actor with access to one legitimately-signed webhook (from their own shop installation) can forge webhook deliveries that the host application will process as though they originated from a different, arbitrary shop domain. Depending on how the host app's webhook handler uses `data.shop` (e.g., to look up/update per-tenant records, to trigger de-provisioning via `shop/redact`, or to inject data attributed to a victim merchant), this crosses the tenant boundary and can lead to cross-tenant data corruption or unauthorized actions taken against another merchant's account — satisfying the "cross-tenant access" criterion.

### Likelihood Explanation
Exploitability requires the attacker to possess at least one valid signed webhook body/HMAC pair, which any user of an app who installs it on their own store can obtain by triggering ordinary Shopify events. No `api_secret_key`, access token, or other privileged credential is required. The header manipulation (setting `x-shopify-shop-domain` to an arbitrary value while replaying an intercepted body+hmac) is trivial for anyone who can send HTTP requests to the app's public webhook endpoint.

### Recommendation
Include `shop`, `topic`, `api_version`, and `webhook_id` in the signable string used for webhook HMAC validation (or otherwise cryptographically bind them, e.g., by only trusting `shop`/`topic` values that the app itself registered per-webhook-id via the Shopify API, not headers on the inbound request). At minimum, `to_signable_string` in `lib/shopify_api/webhooks/request.rb` should incorporate these header values so that tampering with them invalidates the HMAC.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and triggers a webhook (e.g. `orders/create`), capturing the raw body and the valid `x-shopify-hmac-sha256` value Shopify sends.
2. Attacker replays this exact `raw_body` and `hmac` header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `HmacValidator.validate` calls `to_signable_string`, which returns only `@raw_body` — identical to the originally signed body — so the HMAC check passes: [7](#0-6) 
4. `Registry.process` proceeds to call the registered handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)`, where `shop` is `"victim-shop.myshopify.com"` even though the HMAC was never computed over that value: [8](#0-7) 
5. The host application's handler processes the (attacker-controlled) order-creation payload as if it belongs to `victim-shop.myshopify.com`.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
