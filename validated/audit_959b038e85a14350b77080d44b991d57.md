### Title
Webhook shop-domain header is trusted for identity but is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#shop` reads the `x-shopify-shop-domain` / `shopify-shop-domain` HTTP header, but `to_signable_string` (used by `Utils::HmacValidator` to verify the webhook) only signs the raw request body. The `shop` value handed to the application's webhook handler is therefore never bound by the HMAC that `Registry.process` verifies.

### Finding Description
`Webhooks::Registry.process` validates a webhook solely via: [1](#0-0) 

`Utils::HmacValidator.validate` computes the signature over `request.to_signable_string`, which for `Webhooks::Request` is only the raw body: [2](#0-1) 

The `shop` accessor, however, is read straight from an HTTP header that carries no cryptographic binding to the HMAC at all: [3](#0-2) 

`Registry.process` passes this unauthenticated `request.shop` value directly into the `WebhookMetadata` object delivered to the app's `WebhookHandler`: [4](#0-3) 

The identity binding this breaks is: `HMAC-verified bytes == bytes used to determine tenant (shop)`. In reality: `HMAC-verified bytes = raw body only`, while `shop used for tenant identification = unauthenticated header value`. An attacker who can produce any valid HMAC for a given body (e.g., by replaying a legitimately-received webhook body/HMAC pair from their own shop, or in cases where the HMAC secret is shared and app logic doesn't re-derive shop from the verified payload) can swap the `x-shopify-shop-domain` header to any other tenant's shop domain while keeping the same body+HMAC, since the header is completely outside what is verified.

Since app code (e.g., via the `shopify_app` gem or any consumer of this gem) commonly keys per-tenant session/data lookups by `WebhookMetadata#shop`, this allows cross-tenant data to be attributed to, or trigger side effects against, an arbitrary shop record without owning that shop's HMAC secret involvement in the shop field itself.

### Impact Explanation
This matches the "Critical - cross-tenant access" category: an unprivileged caller who can reuse or replay a validly-signed webhook body can direct the resulting handler processing to any `shop` value of their choosing, since the shop identity is never part of the signed material.

### Likelihood Explanation
Moderate: exploitation requires the attacker to have a valid `(raw_body, hmac)` pair for the shared `api_secret_key`/app (e.g., from a webhook the attacker's own shop receives, since apps typically use one client secret across all installs), and to be able to deliver a forged HTTP request with a different `shop-domain` header to the app's webhook endpoint. No possession of another tenant's access token or secret is required — only control over the header value.

### Recommendation
Bind the `shop` value into the material that is actually verified, e.g., include the `x-shopify-shop-domain` header (along with topic/api-version/webhook-id) as part of the HMAC-signed content check, or independently validate that the header's shop domain matches a shop domain already associated with the session/store being acted upon before dispatching to the handler. At minimum, document/require that consuming apps not trust `WebhookMetadata#shop` without cross-checking it against another authenticated source (e.g., a `shop` query param bound to install-time authentication).

### Proof of Concept
1. Attacker's own app installation receives a legitimate webhook: body `B`, header `x-shopify-shop-domain: attacker-shop.myshopify.com`, and a valid `x-shopify-hmac-sha256` computed by Shopify over `B` using the app's shared `api_secret_key`.
2. Attacker replays the exact same `B` and HMAC to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(secret, B)` — this still passes because `B` and the HMAC are unchanged. [5](#0-4) 
4. `request.shop` now returns `"victim-shop.myshopify.com"` and is passed into `WebhookMetadata`, which the app's handler will treat as an authenticated statement that this event belongs to `victim-shop`. [4](#0-3)
