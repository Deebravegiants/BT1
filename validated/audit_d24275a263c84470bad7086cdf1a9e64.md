### Title
Webhook `shop` (and `topic`/`webhook-id`) identity fields are not covered by the HMAC, allowing shop-domain spoofing via replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, then hands off a `shop` value taken from an unauthenticated HTTP header to the app's handler as if it were verified.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`, and `HmacValidator.validate` computes/verifies the HMAC against that raw body alone: `OpenSSL::HMAC.hexdigest(..., verifiable_query.to_signable_string, secret)`. [1](#0-0) [2](#0-1) 

The `shop`, `topic`, `api_version`, and `webhook_id` values, by contrast, are read directly from HTTP headers (`shopify-shop-domain`, `shopify-topic`, etc.) that are entirely attacker-controlled when the attacker sends the HTTP request, and none of them are included in the HMAC-signed bytes: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts these header-derived fields, passing `request.shop` straight into the dispatched `WebhookMetadata` given to the app's handler: [4](#0-3) 

The identity binding that should hold is: `shop authenticated by HMAC == shop acted upon by the handler`. Here, only `raw_body == raw_body` is checked; `shop` is parsed from bytes that are never part of the signature input, so the equality is never enforced. This is the same bug class as the referenced report (a value acted upon after an authorization/weighting step, but not itself covered by the binding check that gates that step) applied to this gem's webhook identity binding: a field (`shop`) that downstream code treats as authenticated is verified against nothing.

### Impact Explanation
Because the app's `client_secret` (`api_secret_key`) is shared across every shop that installs the app, any attacker who can obtain one valid `(raw_body, hmac)` pair — e.g. by installing the app on their own store and capturing a real webhook delivery, which is ordinary, unprivileged use of the app — can replay that exact body and HMAC to the app's public webhook endpoint while substituting an arbitrary `shopify-shop-domain` header. `Utils::HmacValidator.validate` will still pass (the body bytes are unchanged), yet `Registry.process` will deliver the payload to the handler labeled as belonging to a different, victim shop. If the handler uses `WebhookMetadata#shop` to key data writes, cache entries, tokens, or state transitions, this is a genuine cross-tenant boundary crossing without needing the victim's token, `api_secret_key`, or any privileged access — only participation as any normal merchant of the same app.

### Likelihood Explanation
Likelihood is moderate: it requires the attacker to be a legitimate (if low-privilege) merchant/installer of the target app so they can capture one genuine `(body, hmac)` pair from their own store's webhook traffic, then re-POST it to the app's public webhook URL with a forged `shop-domain` header. No secret material, TLS interception, or social engineering is needed — this is achievable purely with unauthenticated HTTP requests to the app's own exposed webhook endpoint.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) to the same authenticated context as the body, rather than trusting a header that sits outside the signed bytes:
- Include the shop domain (and topic) in the signable string used by `HmacValidator`, or
- Cross-check `request.shop` against an out-of-band trusted source (e.g. an active/known session or offline token store) before dispatching to handlers, and
- Document in `Webhooks::Request`/`Registry` that `shop`, `topic`, and `webhook_id` are unauthenticated metadata and must not be treated as verified merely because the body HMAC passed.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com`; capture one real webhook delivery, e.g. `orders/create`, recording the raw JSON body and the `x-shopify-hmac-sha256` header value sent by Shopify.
2. Send a forged HTTP POST to the app's public webhook endpoint with the same raw body and the same HMAC header, but with `x-shopify-shop-domain: victim.myshopify.com`.
3. `Webhooks::Request.new` parses headers, and `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only hashes `@raw_body` (unchanged): [5](#0-4) 
4. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` even though the payload never touched Shopify's servers for that shop, demonstrating the unauthenticated identity field is trusted downstream.
