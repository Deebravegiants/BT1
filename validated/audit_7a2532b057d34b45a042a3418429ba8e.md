### Title
`recapitalize` refunds un-deposited tokens — the pool pays out a measured refund without verifying any receipt, draining real custody while the cash book still reports it - (File: contracts/pool/src/ops/recapitalize.rs)

### Summary
The NTFS bug class is "a bookkeeping structure says empty/untracked while real state exists, and the kernel proceeds on the book instead of reality." In XOXNO Lending the same shape exists in `recapitalize`: the pool treats the caller's declared `offered` amount as having been received, credits only `shortfall` to the `cash` book, and **refunds the remainder from real token custody** — without ever measuring that tokens actually arrived. An unfunded call therefore extracts genuine pool assets while `state.cash` is left unchanged and overstating custody.

### Finding Description
`recapitalize(hub_asset, payer, offered)` is meant to let anyone top up an under-backed market: the caller is expected to transfer `offered` tokens to the pool first, the pool books `min(offered, shortfall)` via `credit_cash`, and refunds `offered - shortfall` back to `payer` via `transfer_out`.

The refund path in `Cache::transfer_out` (`contracts/pool/src/cache/cash.rs:46-53`) performs a raw SAC transfer of `amount` from the contract balance with no balance-delta check that `offered` was ever received, and `credit_cash`/`debit_cash` (`cash.rs:24-41`) adjust only the book. The protocol's own test `test_unfunded_recapitalize_leaves_the_cash_book_overstating_custody` (`contracts/pool/tests/flows.rs:3407-3483`) demonstrates that calling `recapitalize` with the payer holding/transferring nothing still refunds the full declared amount: `token.balance(payer)` ends at `declared`, `token.balance(pool)` goes to `0`, while `after.cash` equals `before.cash` — "the pool's entire custody has left the contract" and "the book still claims more than the supplier's deposit."

The comparison test `test_recapitalize_caps_to_shortfall_and_refunds_every_excess_unit` (`flows.rs:687-730`) shows the honest path refunds only `offered - shortfall`; in a solvent market `shortfall == 0`, so the entire declared `offered` is refunded. Nothing gates the refund on actual receipt — the bitmap is "empty" (no tokens arrived) but the operation proceeds anyway.

### Impact Explanation
Theft of user funds, unprivileged, single call. Any address can call `recapitalize(hub_asset, attacker, pool_token_balance)` on a fully-backed market (shortfall = 0) and receive the pool's entire custody as a "refund" for a deposit it never made — confirmed by the in-repo test where `token.balance(&t.pool) == 0` after the call and `token.balance(payer) == declared`. The `cash` book is untouched, so `require_reserves` (`cash.rs:15-21`) still admits withdrawals against phantom reserves; supplier exits then pass the liquidity guard and fail inside the SAC transfer (`flows.rs:3443-3476`), compounding theft into permanent freezing of remaining claims.

### Likelihood Explanation
High. `recapitalize` is a permissionless entrypoint (in the allowed list). The attacker needs only the market's `HubAssetKey`, a generated address, and knowledge of the pool's token balance — all on-chain readable. A solvent market is the common state; no corruption, racing, or privileged precondition is required. The only constraint is that the declared amount cannot exceed actual custody, which is the exact amount to steal.

### Recommendation
Make `recapitalize` a measured-receipt settlement: snapshot `token.balance(contract)` at entry, require the final balance to have increased by at least the booked amount (`min(offered, shortfall)`) before issuing the refund, or pull the `offered` tokens with `token.transfer_from`/`transfer` under `payer.require_auth()` inside the call itself instead of trusting a pre-transfer. Alternatively, reject when `shortfall == 0` and compute the refund strictly as `received - booked` where `received` is the observed balance delta, not the declared `offered`. A post-call assertion `cash <= balance` would mirror the "reject if bitmap empty but blocks exist" fix.

### Proof of Concept
Adapted from `contracts/pool/tests/flows.rs:3407-3483`:

```rust
// contracts/pool/tests/flows.rs — solvent market, zero funding
let t = TestSetup::new();
let token_admin = token::StellarAssetClient::new(&t.env, &t.asset);
let token = token::Client::new(&t.env, &t.asset);
let thief = Address::generate(&t.env);          // unprivileged, zero balance

// Legitimate supplier funds the pool.
let deposit = 10_000_000_000i128;
token_admin.mint(&t.pool, &deposit);
let supplied = t.client().supply(&t.sup(0, deposit))
    .get_unchecked(0).position.scaled_amount;

// No transfer from `thief` to the pool happens at all.
let custody = token.balance(&t.pool);
t.client().recapitalize(&hub(&t.asset), &thief, &custody);

assert_eq!(token.balance(&t.pool), 0);            // custody stolen
assert_eq!(token.balance(&thief), custody);       // "refund" paid for nothing
assert!(t.state_snapshot().cash >= deposit);      // book still claims funds exist

// Supplier's withdraw passes require_reserves (book says solvent),
// then aborts inside the SAC transfer — funds permanently frozen.
assert!(t.client()
    .try_withdraw(&Address::generate(&t.env), &false, &t.wdr(supplied, i128::MAX, 0))
    .is_err());
```
