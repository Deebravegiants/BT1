### Title
Webhook `shop` (and `topic`, `webhook_id`, `api_version`) headers are trusted for tenant attribution despite not being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely by HMAC-verifying the raw request body, then unconditionally trusts the `shop`, `topic`, `webhook_id`, and `api_version` values taken from unauthenticated HTTP headers to build the `WebhookMetadata` passed to the app's handler. Because the app's `api_secret_key` is shared across every shop that has installed the app, any merchant who receives one genuine, HMAC-valid webhook for their own store can replay that exact body to the app's webhook endpoint while forging the `x-shopify-shop-domain` header to name a different (victim) shop. The HMAC check passes because it never covers the header, so the handler is invoked believing the data belongs to the victim tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all read directly from HTTP headers, entirely outside the signed material: [2](#0-1) 

`Registry.process` validates only the HMAC over the body, then immediately trusts `request.shop`, `request.topic`, etc. to construct the metadata handed to the app's handler, with no cross-check binding these fields to the signed payload: [3](#0-2) 

The `HmacValidator.validate` call verifies `computed_signature` (HMAC over body, keyed by the app-wide `api_secret_key`) against the `hmac` header, but this is identical for every shop that installed the app — the secret is not per-tenant: [4](#0-3) 

This is a direct analog of the reported bug class: a field (`shop`) that is acted on (used as the tenant identity for the handler) is not covered by the integrity check (HMAC over body only) that is supposed to authenticate the message. Just as the Solidity bug let state (`totalSupply`) diverge from the check that gated it, here the header-derived `shop` diverges from the body that was actually authenticated, breaking the binding `authenticated_body_owner == data.shop`.

The docs also state that `Registry.process` "will verify the request did indeed come from Shopify," which overstates what the HMAC check actually proves — it proves the body was signed with the app's secret, not that the header-asserted shop is the true origin: [5](#0-4) 

### Impact Explanation
An attacker who is a legitimate merchant of the target app (unprivileged relative to other tenants) can capture one authentic webhook for their own shop (valid HMAC, since the secret is app-wide, not shop-specific) and replay its body with a forged `x-shopify-shop-domain` header pointing at another shop. The app's handler will process this as authentic data for the victim shop (e.g., trigger side effects keyed on `data.shop`, write records against the victim's tenant, or misattribute customer/order data), crossing the tenant boundary. This matches the "cross-tenant access" Critical-impact category since attribution/authorization decisions in the host app depend on `data.shop`, which is unauthenticated.

### Likelihood Explanation
Requires the attacker to run any shop that has installed the target app (a normal, unprivileged capability of anyone who can install a Shopify app) and to receive at least one genuine webhook for their own store — both trivially achievable. No access token, `client_secret`, or other privileged credential is required, only observation of one legitimate webhook payload/HMAC pair generated for their own tenant.

### Recommendation
Bind the `shop` (and other header-derived identifiers used downstream) into the signed material, or independently verify that the shop asserted in the header actually corresponds to a shop that owns/registered the webhook (e.g., by cross-referencing the webhook subscription/shop association server-side) before dispatching to the handler. At minimum, document explicitly that `data.shop`/`data.topic`/`data.webhook_id` are NOT covered by the HMAC and must not be trusted for authorization decisions without additional verification by the host application.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com` and `victim-shop.myshopify.com`, both signed with the same `api_secret_key`.
2. Attacker triggers an event on their own shop and receives a webhook POST with body `B` and header `x-shopify-hmac-sha256: HMAC(secret, B)`.
3. Attacker replays the identical body `B` and HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses the forged header successfully; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes HMAC over `@raw_body` and succeeds because the body/HMAC pair is legitimately signed.
5. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, i.e., data that was never actually generated by or for the victim shop is processed under the victim's tenant identity. [6](#0-5)

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
