### Title
Unauthenticated Origin Spoofing via Unsigned Cross-Chain Calldata in `pallet-hyper-fungible-token` - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
`pallet-hyper-fungible-token`'s `on_accept` handler decodes an attacker-supplied `data` field from a cross-chain `Message` into a `SubstrateCalldata { signature: Option<Vec<u8>>, runtime_call: Vec<u8> }`, then dispatches the embedded `runtime_call` as a `Signed` origin. When no signature is supplied, the dispatch origin is derived directly from the message's `from` bytes rather than from any cryptographic proof of authorization, permitting an attacker to dispatch arbitrary (filter-permitted) runtime calls under any account they choose to name in `from`. [1](#0-0) 

### Finding Description
`on_accept` decodes the untrusted cross-chain message body, mints/transfers tokens to `message.to`, and then — if `message.data` is non-empty — decodes it as `SubstrateCalldata` and executes an embedded runtime call: [2](#0-1) 

If `substrate_data.signature` is `Some(..)`, the code verifies an Ed25519/Sr25519/ECDSA signature that binds the call to the `beneficiary` (`message.to`) account: [3](#0-2) 

But when `signature` is `None`, the origin is computed straight from `message.from` with **no signature check at all**: [4](#0-3) 

The decoded `runtime_call` is then dispatched as `RawOrigin::Signed(origin)`: [5](#0-4) 

The only gate on the dispatched call is `BaseCallFilter`, which restricts *which* dispatchables can run, not *whose* origin is used: [6](#0-5) 

Critically, `message.to` (used to pick the token recipient/`beneficiary`) and `message.from` (used to pick the dispatch origin in the unsigned branch) are two independent fields inside the same attacker-influenced message body. Nothing in this handler ties `from` back to the actual originating account on the source chain — it is just bytes copied out of the ABI-decoded `Message`: [7](#0-6) 

This is structurally the same bug class as the Horovod advisory: untrusted, attacker-influenced data is deserialized into an object (`SubstrateCalldata`/`RuntimeCall`) that is then used to drive privileged execution, with the "no signature" code path skipping the one authentication step (there, `cloudpickle.loads`; here, `dispatch` with an unauthenticated `Signed` origin) that should have gated it.

### Impact Explanation
If `message.from` is not cryptographically bound to the real caller on the source chain (i.e., a source-chain contract or extrinsic lets the message originator freely choose the `from` bytes rather than hard-coding them to `msg.sender`/the signer), any account able to trigger a `send()` on the source chain can:
- Set `to` = attacker's own account (to receive the minted/transferred tokens), and
- Set `from` = any victim AccountId, with an empty `signature`,

causing the destination pallet to dispatch an arbitrary `BaseCallFilter`-permitted `RuntimeCall` as `RawOrigin::Signed(victim)` — full account impersonation for governance-unfiltered calls (transfers, staking, proxy calls, etc.), without ever needing the victim's key. This is a critical unauthorized-action / potential-fund-theft primitive reachable by an ordinary token bridger.

### Likelihood Explanation
Reachability requires only a standard, unprivileged cross-chain token transfer with non-empty `data` and no `signature` — the exact "convenience" path the code appears to provide for a sender dispatching calls as themselves. The severity is entirely contingent on whether the EVM/Substrate-side sending logic **hardcodes** `from` to the actual transaction sender or lets the caller supply it as free-form bytes in `SendParams`/the message body. I was not able to fully verify, within the available tool budget, whether the `send()`/`_buildDispatchPost` implementations (`sdk/packages/core/contracts/apps/HyperFungibleToken.sol` and siblings) fix `from = abi.encode(msg.sender)` or allow it to be attacker-chosen. If it is hardcoded to `msg.sender`, this specific spoofing path is not exploitable and the finding reduces to defense-in-depth concern only. **This dependency is the key uncertainty in this analog and should be confirmed against the exact `send()`/`SendParams` encoding before treating this as a confirmed critical finding.**

### Recommendation
- Never derive a dispatch origin from an unauthenticated field. Require the same signature-based binding used in the `Some(signature)` branch for *all* calldata dispatch, or bind the unsigned-origin path to a field that is provably non-forgeable (e.g., the ISMP-verified `source`/authenticated contract address only, never freeform message bytes).
- If `message.from` is meant only for refund routing, do not reuse it as a privileged dispatch origin. Use `beneficiary` (`message.to`, i.e., the same account whose signature was already verified) for both token delivery and unsigned-origin fallback, or drop the unsigned fallback entirely and always require a signature to dispatch a call.
- Add an explicit test asserting that a cross-chain message with `to = attacker`, `from = victim`, and no signature cannot cause a `RuntimeCall` to execute as `victim`.

### Proof of Concept
1. Attacker (or attacker-controlled contract) triggers a token transfer to the destination chain running `pallet-hyper-fungible-token`, setting the ABI-encoded `Message`:
   - `to` = attacker's own beneficiary bytes
   - `amount` = any small amount
   - `data` = SCALE-encoded `SubstrateCalldata { signature: None, runtime_call: <encoded RuntimeCall, e.g. a Balances::transfer draining victim's account or a Proxy::add_proxy call> }`
   - `from` = victim's 20/32-byte account identifier
2. On delivery, `on_accept` mints/transfers the token amount to the attacker's `beneficiary` (`message.to`) as usual.
3. Because `substrate_data.signature` is `None`, the origin branch at lines 176-187 computes `origin` from `message.from` (the victim) with no proof of authorization.
4. `runtime_call.dispatch(RawOrigin::Signed(victim))` executes at line 198-200, running the attacker-chosen call as the victim, subject only to `BaseCallFilter` — not to any signature or ownership check. [8](#0-7) 

*Caveat:* Step 1's forgeability of `from` depends on the exact source-chain `send()` implementation, which I could not fully verify in this pass; this must be confirmed against `sdk/packages/core/contracts/apps/HyperFungibleToken*.sol` before treating the exploit as fully proven end-to-end.

		&self,
		PostRequest { body, from, source, .. }: PostRequest,
	) -> Result<Weight, anyhow::Error> {
		// Authenticate: look up which local asset this contract address maps to
		let local_asset_id = ContractToAsset::<T>::get(source, &from)
			.ok_or(HftError::UnknownSourceContract(source))?;

		// Decode the Message
		let message = Message::abi_decode(&body).map_err(HftError::DecodeError)?;

		// Convert recipient bytes to substrate AccountId
		// If 32 bytes: use directly. If 20 bytes: left-pad with zeros.
		let mut beneficiary_bytes = [0u8; 32];
		let to_bytes = message.to.as_ref();
		if to_bytes.len() == 32 {
			beneficiary_bytes.copy_from_slice(to_bytes);
		} else if to_bytes.len() == 20 {
			beneficiary_bytes[12..].copy_from_slice(to_bytes);
		} else {
			Err(HftError::InvalidRecipientLength(to_bytes.len()))?;
		}
		let beneficiary: T::AccountId = beneficiary_bytes.into();
