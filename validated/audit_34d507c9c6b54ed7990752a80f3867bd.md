### Title
Webhook Shop-Domain Header Not Covered by HMAC Allows Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` signs only the raw request body with HMAC, while the `shop` identity that `ShopifyAPI::Webhooks::Registry.process` hands to the host application's `WebhookHandler` is read from an unauthenticated header. This breaks the intended binding `hmac(secret, signed_content) == hmac(secret, {shop, body})`, letting an attacker who legitimately receives one valid webhook (e.g., for their own installed shop) replay it against the app's webhook endpoint with a forged `shop`/`x-shopify-shop-domain` header, causing the app to process attacker-controlled data under a different tenant's identity.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header, which is never part of the signable content: [2](#0-1) 

`Registry.process` validates the HMAC (which only covers the body) and then unconditionally trusts `request.shop` to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

`WebhookMetadata.shop` is the tenant-identifying field the host application is expected to use to route/act on the webhook (look up the merchant's session, apply GDPR redaction, update the correct store's data, etc.): [4](#0-3) 

Because the webhook signing secret (`Context.api_secret_key`) is scoped to the **app**, not to an individual **shop**, any store that has the app installed can receive a genuine, correctly-HMAC-signed webhook for its own shop. That signature/body pair remains valid for *any* `shop` header value, since the header is outside the signed content. The attacker can therefore replay the captured body+HMAC to the app's own webhook endpoint while substituting a victim shop's domain in the `shop-domain` header, and `Registry.process` will pass it through as `WebhookMetadata#shop == victim-shop`, crossing the tenant boundary the HMAC check is supposed to enforce.

This mirrors the reported bug class: a field (`shop`, used to bind the request to a tenant) is acted upon by the receiving handler but is not covered by the HMAC that is meant to authenticate the request.

### Impact Explanation
This is a cross-tenant confusion vulnerability: an attacker with a legitimate, unprivileged relationship to the app (i.e., they installed the app on their own store and therefore receive real signed webhooks) can make the app process attacker-supplied webhook bodies under another merchant's shop identity, without possessing that merchant's credentials or the app's `client_secret`. Depending on how the host app implements its `WebhookHandler#handle`, this can lead to cross-tenant data corruption, unauthorized state changes, or processing of a victim's GDPR/data-redaction workflow with attacker-controlled content — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Exploitation requires only that the attacker be able to install the target app on a shop they control (a normal capability for any Shopify merchant/dev store) and have network access to the app's public webhook endpoint — both are unprivileged-internet-user conditions. No access token, refresh token, or `client_secret` is needed since the attacker reuses a genuinely signed body they already legitimately received.

### Recommendation
Bind the tenant identity into what is authenticated: either include the `shop-domain` header (and other identity-relevant headers such as `topic`/`webhook-id`) in the HMAC-signed content (`to_signable_string`), or independently verify that `request.shop` corresponds to a shop the app has an active session/installation record for before dispatching to the handler, rather than trusting the header value outright once the body-only HMAC passes.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`.
2. Shopify delivers a legitimate webhook to the app's endpoint with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC of raw body>`, and some JSON body.
3. Attacker captures the raw body and the valid HMAC value (both are visible to them since it's their own store's webhook, or they operate a proxy in front of their own dev store's endpoint).
4. Attacker crafts a new POST to the app's webhook endpoint with the same raw body and the same `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks the body against the secret: [5](#0-4) 
6. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker-controlled>, ...)` and processes it as if Shopify genuinely sent this data for `victim-shop`.
