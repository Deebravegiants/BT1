### Title
Crafted swap routes can attach unauthorized wallet-drain transfers to a caller’s authorization tree - ([File: contracts/swap-aggregator/src/execute/mod.rs])

### Summary
`execute_strategy` accepts route-supplied pool addresses, calls them during venue dispatch, and performs those calls while the sender’s authorization is active. A malicious route can therefore cause arbitrary third-party code to request `token.transfer(sender, attacker, amount)`, which simulation records as an extra child authorization under the victim’s `swap_collateral` or `execute_strategy` call. If the victim signs the simulated authorization tree, the malicious pool can drain an unrelated wallet token even though the controller’s intended authorization was only the routed input amount.

### Finding Description
The router authenticates `sender`, decodes caller-controlled route bytes, and loads pool, input-token, and output-token addresses from the route’s asset registry. [1](#0-0)  For each swap instruction, `execute_op` constructs `hop.pool` directly from that registry and dispatches it to a venue adapter. [2](#0-1)  The dispatcher validates token balance deltas but does not bind `hop.pool` to an allowlist or otherwise prevent arbitrary contract code from executing inside the sender’s authorization context. [3](#0-2) 

The controller exposes this behavior through strategy paths such as `swap_collateral`, which authenticates the caller, verifies account owner-or-delegate authority, withdraws the selected collateral, and passes the caller-controlled `swap` payload into the router. [4](#0-3)  Although the controller grants the router only one exact input-token transfer, that bound does not prevent route code from requesting additional transfers under the caller’s own authorization entry. [5](#0-4) 

The included authorization test demonstrates the bypass: a route-selected pool invokes `token.transfer(alice, attacker, WALLET_BALANCE)`, simulation records that transfer as a child of Alice’s `swap_collateral` authorization, and signing that poisoned tree moves her entire unrelated wallet balance. [6](#0-5) [7](#0-6) 

### Impact Explanation
This enables theft of user funds beyond the supplied collateral or routed input amount. The victim can sign what appears to be a normal strategy authorization while a hidden child authorization transfers any token balance accessible through `token.transfer`. The regression test proves a route-specific attacker receives all `77_770_000_000` units of an unrelated token while the swap still returns a fair output and completes. [8](#0-7) 

### Likelihood Explanation
An unprivileged attacker can deploy the malicious pool, embed its address in the route’s asset registry, and induce a user to execute the crafted route through `execute_strategy` or a controller strategy. The exploit does not require privileged access, leaked keys, compromised oracle prices, or control of the router configuration. Its practical requirement is that the victim signs the authorization tree generated by simulation, including the malicious child invocation. [9](#0-8) 

### Recommendation
Do not allow arbitrary route-selected contracts to execute under the sender’s authorization context. Enforce a governance-approved venue/pool allowlist before dispatch, or restructure settlement so venue code cannot invoke operations requiring the sender’s auth. At minimum, the signing client must decode and reject any authorization tree containing calls other than the expected exact input-token transfer; this client-side mitigation should be treated as complementary rather than sufficient because a forged or confusing route can still produce a valid-looking malicious authorization request.

That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's

final risk gate bounds it. An honest swap strategy gives the caller no child
