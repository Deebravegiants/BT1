### Title
Webhook shop identity spoofing due to `shop` not being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes and validates its HMAC over the raw request body only, while the `shop` (tenant identity) is read directly from an HTTP header that is never included in the signed material. This breaks the binding `hmac_verified(bytes) == identity_claimed(shop)`, allowing a valid HMAC produced for one shop's webhook body to be replayed against the same endpoint with a forged `shop-domain` header claiming a different tenant.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#hmac` extracts the signature purely from the `hmac-sha256` header: [2](#0-1) 

`Request#shop`, which host applications use as the tenant identity to route/process the webhook, is read straight from the `shop-domain` header with no cryptographic binding to the body or the HMAC: [3](#0-2) 

`HmacValidator.validate` computes `HMAC(secret, to_signable_string)` and compares it to the received signature — it never mixes in `shop`, `topic`, or any header: [4](#0-3) 

Because the app's `api_secret_key` is shared across every shop that installs the app, any two webhook deliveries with the same body produce the same valid HMAC regardless of which shop they were originally destined for. A merchant who has legitimately installed the app (using only their own store's admin access, no stolen credentials) can register a webhook subscription pointing at infrastructure they control, capture a `(raw_body, hmac)` pair delivered for their own store, and then replay that exact body/HMAC pair to the app's real webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. `HmacValidator.validate` will report success because it never inspected the header, and the host application — trusting `Request#shop` for tenant attribution — will process/store the data as if it belonged to the victim shop.

Binding that should hold but does not:
`verified_bytes(raw_body) == claimed_tenant(shop header)`
Before request: HMAC is computed over `raw_body_A` for shop A.
After attacker's replay: HMAC still validates against `raw_body_A`, but `shop` header now claims shop B — the two are unbound.

### Impact Explanation
This is a cross-tenant data confusion primitive: a webhook payload can be attributed to an arbitrary shop domain without holding any credential belonging to that shop, purely because the identity field lies outside the authenticated envelope. Depending on how the host application uses `Request#shop` (e.g., to select which merchant's local data to update, uninstall behavior, GDPR/compliance triggers, order/customer records), this enables cross-tenant access or data corruption attributed to a shop the attacker does not control.

### Likelihood Explanation
The only prerequisite is that the attacker already has a legitimate installation of the target app on their own store (a standard, low-privilege capability, not a stolen secret or victim credential), plus the ability to point a webhook subscription at infrastructure they control to capture one valid `(body, hmac)` pair. From there, the replay against the app's public webhook endpoint with a forged header is trivial and repeatable for any payload shape the attacker can trigger on their own store.

### Recommendation
Bind the shop identity into the verified material instead of trusting an unauthenticated header:
- Include `shop`/`shop-domain` (and ideally `topic`, `webhook-id`) in `to_signable_string`, matching Shopify's actual webhook verification contract, or
- Require host applications to independently reconcile `Request#shop` against a shop`s registered/expected identity (e.g. an already-authenticated session) rather than trusting the header value implicitly, and document this clearly since `Request#shop` is currently presented as a verified accessor once `hmac` validates.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` using their own account (no special privileges needed).
2. Attacker temporarily registers a webhook subscription pointing to a server they control, and triggers an event (e.g., creates an order) to receive a legitimate webhook delivery, capturing the raw body `B` and its header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC_SHA256(api_secret_key, B)`.
3. Attacker sends a POST request to the real app's webhook endpoint with:
   - Body: `B` (unchanged)
   - Header `X-Shopify-Hmac-Sha256: H` (unchanged)
   - Header `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (forged)
4. The host app calls `ShopifyAPI::Utils::HmacValidator.validate(request)`, which passes because it only checks `HMAC(secret, B) == H`, per [5](#0-4) .
5. The host app then reads `request.shop` (returns `"victim-shop.myshopify.com"`) per [3](#0-2)  and processes the attacker-controlled payload `B` as belonging to the victim shop.

          received_signature = verifiable_query.hmac
