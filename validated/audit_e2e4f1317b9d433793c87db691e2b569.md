### Title
Webhook `shop` and `topic` identity fields are not covered by the webhook HMAC, allowing tenant-spoofed webhook processing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw request body, while `shop`, `topic`, `api_version`, and `webhook_id` are read directly from HTTP headers that are never part of the HMAC computation. `Registry.process` validates the HMAC and then unconditionally trusts `request.shop` as the tenant identity handed to the app's webhook handler. This is the same "field acted on but not covered by the HMAC" binding break described in the external report, applied to this gem's webhook authentication path instead of `PRBMath`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are pulled straight from headers, none of which participate in the signable string: [2](#0-1) 

`Registry.process` validates the request via `Utils::HmacValidator.validate(request)`, which recomputes the HMAC solely over `to_signable_string` (i.e., the body) and compares it to the `hmac-sha256` header: [3](#0-2) [4](#0-3) 

After that check passes, `request.shop` (an unauthenticated header value) is forwarded as the tenant identity in `WebhookMetadata`, which the host app's handler uses to attribute the webhook body to a specific merchant: [5](#0-4) 

The broken identity binding is: `shop header used by handler == shop covered by HMAC`. The HMAC only binds the body bytes; it does not bind the `shopify-shop-domain` header to that body. Any party who can present a body+HMAC pair that is valid for shop A (e.g., a malicious app-installing merchant receiving genuine webhooks for their own store) can replay that same body/HMAC pair to the app's webhook endpoint while substituting a different `shopify-shop-domain` header value. `Utils::HmacValidator.validate` still returns `true` because it never inspects the header, and `Registry.process` dispatches the handler with the attacker-chosen `shop`.

### Impact Explanation
This crosses a tenant boundary: the webhook handler processes data (order/customer/shop payloads) under an attacker-controlled shop identity while the HMAC gives the host application false assurance that the entire request — including its tenant attribution — was verified by Shopify. Any per-shop authorization, session lookup, or data-isolation logic in the host app keyed off `WebhookMetadata#shop` can be bypassed or confused, resulting in cross-tenant data being written to, or read against, the wrong merchant's session/access token.

### Likelihood Explanation
Exploitation requires the attacker to possess at least one genuine, HMAC-signed webhook body (trivially available to any merchant with a store on the same app, since Shopify sends real webhooks to real merchants) and the ability to send an HTTP request with a modified `shopify-shop-domain` header to the app's public webhook endpoint. No `client_secret`, access token, or privileged access is required — only an unprivileged Shopify merchant/developer account and network access to the app's webhook receiver, both attacker-controlled and outside Shopify's own infrastructure once the header is stripped and replaced.

### Recommendation
Include the `shop`, `topic`, and `webhook_id` headers in the value that is HMAC-verified (or otherwise cryptographically bind them, e.g., derive/confirm the shop domain from a separately authenticated channel such as a stored per-shop secret or session lookup) rather than trusting header values that fall outside the signed payload. At minimum, document that `HmacValidator.validate` only authenticates the raw body and that consuming code must not treat `Request#shop`/`#topic` as verified without additional binding.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store (`shop-a.myshopify.com`) and receives a legitimate webhook: body `B`, header `X-Shopify-Hmac-Sha256: H`, header `X-Shopify-Shop-Domain: shop-a.myshopify.com`.
2. Attacker replays an HTTP POST to the app's webhook endpoint with the identical body `B` and identical `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate(request)` recomputes HMAC over `to_signable_string` (`= B`) and it matches `H`, so validation succeeds.
4. `Registry.process` builds `WebhookMetadata.new(shop: request.shop, ...)` with `shop == "victim-shop.myshopify.com"` and invokes the handler, causing the app to process attacker-supplied data as if it originated from the victim's shop.
