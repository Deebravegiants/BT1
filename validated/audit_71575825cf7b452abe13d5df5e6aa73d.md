### Title
Stale cached `user_centric_signup`/`UserData` from initial QR validation drives final enrollment decision after long biometric processing - (File: src/plans/mod.rs)

### Summary
`MasterPlan::do_signup` validates the user's QR code once via `verify_user_qr_code` (backend call), caching the returned `UserData` — including the security-relevant `user_centric_signup` flag and the self-custody/backend encryption keys — inside `qr_codes.user_data`. This snapshot is never re-validated against the backend for the remainder of the (potentially lengthy) signup: biometric capture, the ML pipeline, and fraud detection all run afterward, and only then is the cached `user_centric_signup` value read to decide the enrollment path.

### Finding Description
The check-once pattern mirrors the Governance `vote()` bug: a value (`userVotes`/`user_centric_signup`) is captured from an authoritative source at one point in time and is later compared against/used for a decision, while nothing forces re-validation of that value even though a large amount of time and mutable state elapses between the check and its use.

Concretely:
1. `verify_user_qr_code` performs a single backend HTTP request and returns `UserData` (containing `user_centric_signup`, `self_custody_user_public_key`, `orb_relay_app_id`, `id_commitment`, and encrypted key material) [4](#0-3) .
2. This `UserData` is stored in `QrCodes::Both`/`ResolvedQrCodes` and is only refreshed if the *operator* QR expires (`operator_qr_expiration_time`, default 23 hours) — there is no independent expiration or re-check tied to the *user* data itself [5](#0-4) .
3. `do_signup` proceeds through `is_orb_os_version_allowed`, a 3-second sleep, full biometric capture, the AI biometric pipeline, and fraud detection — all of which can take a substantial amount of wall-clock time — before finally reading `qr_codes.user_data.user_centric_signup` [6](#0-5) .
4. If `user_centric_signup` is `true` (and `ignore_user_centric_signups` is not set), the orb treats the signup as complete based purely on local pipeline results (`signup_reason == SignupReason::Normal`) and *never calls the backend's authoritative `enroll_user`/`signup_post` + `signup_poll` verification loop* that would otherwise catch backend-side rejections (duplicates, revoked eligibility, updated policy) [2](#0-1) .

Because the `user_centric_signup` decision and the cryptographic material used to build the Personal Custody Package are all pinned to the state fetched at the very start of the flow, any backend-side change to that user's eligibility/keys/policy occurring during the capture-and-pipeline window is silently ignored for the "user-centric" path — the orb still finalizes the signup as if the originally-fetched snapshot were current, exactly the same "checked once, stale value used for the final consequential decision" flaw as in the vote report.

### Impact Explanation
For `user_centric_signup` users, the accept/reject decision at the end of a signup is made purely from the stale, single-fetch flag and local pipeline output, bypassing the backend re-verification (`enroll_user`) that exists for the non-user-centric path. This can lead to a signup being locally marked "successful" (`signup_reason::Normal` + stale `user_centric_signup == true`) even though the user's authorization, key material, or policy on the backend has since changed — a misattributed/unauthorized signup outcome that the backend never gets the opportunity to reject, unlike the standard `enroll_user` flow which polls the backend for the definitive verdict.

### Likelihood Explanation
The window between the initial QR/user-data fetch and the final `user_centric_signup` check spans the entire biometric-capture and ML-pipeline phase of a signup, which is not instantaneous. Any app/backend-side change to that specific `user_id`'s record (revocation, key rotation, policy change) that lands within this window is reachable without any special privilege — it only requires normal backend-driven state changes during a normal signup's processing time, matching the "unprivileged user" scope of this analog.

### Recommendation
Re-validate `user_data` (in particular `user_centric_signup`, and the encryption/self-custody keys used to build the Personal Custody Package) against the backend immediately before the final enrollment decision in `do_signup`, rather than relying solely on the value captured at initial QR-code validation. Alternatively, always route the `user_centric_signup` path through the same backend-confirmed verification (`enroll_user`/`signup_poll`) rather than trusting the locally cached flag for the final success/failure verdict.

### Proof of Concept
1. Start a self-serve signup; `verify_user_qr_code` returns `UserData { user_centric_signup: true, .. }`, which is cached in `qr_codes`.
2. During the subsequent biometric capture and pipeline phases (multiple seconds to tens of seconds), have the backend update this `user_id`'s record (e.g., flip `user_centric_signup` to `false`, revoke eligibility, or rotate `self_custody_user_public_key`).
3. `do_signup` reaches line 639 and reads the *original* cached `user_centric_signup == true`, so it sets `success = signup_reason == SignupReason::Normal` without calling `enroll_user`/backend re-verification, finalizing the signup as successful based on data that the backend no longer considers current [2](#0-1) .

    /// Checks if `qr_code` is a valid user QR-code through the backend.
    async fn verify_user_qr_code(
        &self,
        orb: &mut Orb,
        user_qr_code: &qr_scan::user::Data,
        operator_data: &OperatorData,
        qr_capture_start: Option<Instant>,
    ) -> Result<Option<backend::user_status::UserData>> {
        let Config {
            user_qr_validation_use_full_operator_qr,
            user_qr_validation_use_only_operator_location,
            ..
        } = *orb.config.lock().await;
        match backend::user_status::request(
            user_qr_code,
            operator_data,
            user_qr_validation_use_full_operator_qr,
            user_qr_validation_use_only_operator_location,
        )
        .await
        {
            Ok(Some(user_data)) => {
                orb.ui.qr_scan_success(QrScanSchema::User);
                dd_incr!("main.count.signup.during.general.user_qr_code_validate");
                tracing::info!("User QR-code validated: {user_qr_code:?}");
                if let Some(qr_capture_start) = qr_capture_start {
                    dd_timing!("main.time.signup.user_qr_code_capture", qr_capture_start);
                }
                return Ok(Some(user_data));
            }
            Ok(None) => {
                orb.ui.qr_scan_fail(QrScanSchema::User);
                dd_incr!("main.count.signup.result.failure.user_qr_code", "type:invalid_qr");
            }
            Err(_) => {
                orb.ui.qr_scan_fail(QrScanSchema::User);
                dd_incr!(
                    "main.count.signup.result.failure.user_qr_code",
                    "type:validation_network_error"
                );
            }
        }
        Ok(None)
    }
