### Title
Excess native ETH sent to `EvmHost.dispatch`/`fundRequest` is refunded to the host contract instead of the user, permanently freezing user funds - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.dispatch(DispatchPost)` and `EvmHost.fundRequest` accept native ETH via `msg.value` and swap it for an exact amount of fee tokens via Uniswap V2's `swapETHForExactTokens`. Any ETH sent beyond what's needed to cover `post.fee` (or `amount` in `fundRequest`) is refunded by the Uniswap router to the caller of the swap — which is `EvmHost` itself, not the original end user who sent the transaction. This mirrors the reported bug class: a value/amount parameter (`_volume`/`post.fee`) that does not necessarily correspond to the value actually paid/received by the funder (`msg.value`), causing user overpayment to be misdirected.

### Finding Description
In `dispatch`, when `msg.value > 0`, the full `msg.value` is forwarded to `swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)`: [1](#0-0) 

The router only needs enough ETH to acquire `post.fee` fee tokens; Uniswap V2's `swapETHForExactTokens` refunds any leftover ETH to `msg.sender` of that call. Since `EvmHost` itself calls the router (not the original transaction sender / app), the refund lands in `EvmHost`'s own native balance rather than being returned to the user or the calling app that sent the excess `msg.value`. There is no logic afterward in `dispatch` (or in `fundRequest`, which has the identical pattern) that captures this router refund and forwards it back to `_msgSender()` or `post.payer`. [2](#0-1) 

This is directly analogous to the reported `BountyCore.receiveFunds` issue: a caller-supplied amount (`_volume`/`post.fee`) drives an internal accounting/swap step that does not strictly reconcile with the actual value transferred (`msg.value`), and the mismatch (overpayment) is not returned to the funder.

Any unprivileged app built on top of `IDispatcher` (e.g. `HyperFungibleToken.send`, `WrappedHyperFungibleToken.send`, `HyperbridgeLzEndpoint.send`) that forwards `msg.value` to `EvmHost.dispatch` without precisely computing the exact swap input amount is exposed to this loss whenever the actual on-chain swap price differs even slightly from the price used to estimate `nativeFee`/`msg.value` off-chain (which is normal, since AMM prices move between quote-time and execution-time).

### Impact Explanation
Any user or app who overestimates the native ETH needed for a dispatch fee (which is expected/likely given AMM price slippage between off-chain quoting and on-chain execution) permanently loses the excess ETH into the `EvmHost` contract, with no visible refund path back to them. This is a concrete freezing/loss of user funds reachable directly from a single dispatch transaction — matching the required "concrete theft or permanent freezing of funds" bar.

### Likelihood Explanation
High likelihood: `msg.value`-based fee payment is a first-class supported path (documented explicitly in `IDispatcher.dispatch`/`fundRequest` NatSpec), and it is normal for the ETH price fetched off-chain (or via `quote()`) to differ slightly from the exact swap price at execution, meaning near every native-fee dispatch either reverts (if underfunded) or leaves dust/excess trapped in the contract (if overfunded). Over many transactions this compounds into a non-trivial value leak from users into `EvmHost`.

### Recommendation
After calling `swapETHForExactTokens`, capture the actual amount of ETH used (`amounts[0]` returned by the router) and refund the difference (`msg.value - amounts[0]`) back to `_msgSender()` (or the designated `payer`), mirroring the same fix pattern recommended in the source report: reconcile the declared amount against the value actually consumed, and return any surplus to the funder instead of silently retaining it.

### Proof of Concept
1. Off-chain, a user calls `quote()` and estimates `nativeFee = X` ETH needed to cover `post.fee` fee tokens.
2. User calls `HyperFungibleToken.send{value: X}(...)`, which forwards to `IDispatcher(_host).dispatch{value: X}(request)`. [3](#0-2) 
3. Inside `EvmHost.dispatch`, the pool price has moved slightly since the quote, so `swapETHForExactTokens` only consumes `X - δ` ETH to acquire `post.fee` tokens, and refunds `δ` ETH to `msg.sender` of the swap call — `EvmHost`. [4](#0-3) 
4. `δ` accumulates as native ETH balance inside `EvmHost` with no code path returning it to the user; it is permanently lost to that user and not credited anywhere on their behalf.
