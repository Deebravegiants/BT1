### Title
Webhook shop identity not bound to HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes/validates HMAC over the raw request body only, while the `shop` (tenant identifier) is taken from an unsigned HTTP header and passed downstream to the app's webhook handler without any binding to the HMAC-verified content.

### Finding Description
`Utils::HmacValidator.validate` verifies a webhook by recomputing an HMAC over `verifiable_query.to_signable_string` and comparing it (via `OpenSSL.secure_compare`) to the `hmac` value on the request object [1](#0-0) . For `Webhooks::Request`, `to_signable_string` returns only `@raw_body`, and `hmac` is read from the `hmac-sha256` header [2](#0-1) [3](#0-2) . The `shop` attribute, however, is read straight from the `shop-domain` header and is never included in the signable string, so it is completely outside the scope of the HMAC check [4](#0-3) .

`Registry.process` validates the HMAC and then immediately dispatches to the topic handler using `request.shop` as the tenant identity for the event, with no cross-check that the signed body actually corresponds to that shop: [5](#0-4) .

This breaks the identity binding: `hmac_valid(raw_body) == true` is treated as equivalent to `shop_header == owner_of(raw_body)`, but the gem never establishes that equality — the HMAC only proves *body integrity/authenticity*, not *which shop the body belongs to*. Anyone able to reach the app's webhook endpoint with a body+HMAC pair that validates (e.g., a genuine webhook previously delivered to the app for shop A, which the recipient of that webhook can replay) can substitute an arbitrary `shop-domain` header value and have the app process the event as if it originated from shop B, because `Registry.process` never checks `request.shop` against anything derived from the signed content.

### Impact Explanation
This is a cross-tenant identity-binding failure: an app built on this gem can be made to attribute a validly-HMAC'd webhook payload to a different merchant's shop than the one it was actually issued for, since `shop` is not covered by the signature. Depending on how the host app persists/keys data from `WebhookMetadata#shop` (e.g., using it to look up sessions, write records, or trigger actions scoped to that shop), this allows cross-tenant data injection/corruption without any credential belonging to the impersonated shop.

### Likelihood Explanation
Exploitation requires the attacker to already possess at least one valid `(raw_body, hmac)` pair — for example, a legitimate webhook delivered to their own connected shop — and the ability to POST directly to the app's public webhook endpoint with a modified `shop-domain` header (webhook endpoints are plain HTTP endpoints and are not restricted to only accept traffic actually originating from Shopify's infrastructure at the gem level). No `api_secret_key`, access token, or privileged account is required beyond being any merchant/user who can trigger a webhook for their own store.

### Recommendation
Include the shop (and other identity-relevant headers such as topic/webhook-id) as part of the signable content used for HMAC verification, or otherwise cryptographically bind the `shop-domain` header to the verified body before it is trusted by `Registry.process`/`WebhookMetadata`. At minimum, document and encourage host apps to cross-validate `request.shop` against an independently known/authorized shop for that webhook subscription rather than trusting the header value implicitly.

### Proof of Concept
1. App receives (or the attacker's own shop legitimately receives) a webhook: raw body `B`, header `x-shopify-hmac-sha256: H` (valid for `B`), and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker resends the identical `B`/`H` pair to the app's webhook endpoint but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` succeeds because it only checks `B` against `H` [3](#0-2) .
4. `Registry.process` dispatches to the handler with `shop: "victim-shop.myshopify.com"` [6](#0-5) , causing the host application to process/attribute the event to the wrong tenant.
