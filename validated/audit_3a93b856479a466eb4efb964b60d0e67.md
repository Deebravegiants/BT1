### Title
Webhook HMAC signs only the raw body, not shop/topic headers, allowing cross-tenant header splicing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `HmacValidator.validate_signature` computes/compares the HMAC solely over that string [2](#0-1) . `Registry.process` then trusts `request.shop` and `request.topic` — both read straight from unauthenticated headers — to dispatch the handler and populate `WebhookMetadata` [3](#0-2) . Because the signature never binds to `shop-domain`/`topic`, a valid `(raw_body, hmac)` pair obtained by an attacker for their own shop/topic can be resubmitted with forged `shop-domain`/`topic` headers and will still pass validation.

### Finding Description
Intended binding: `computed_signature(raw_body) == received_hmac` should imply `(raw_body, shop, topic)` as an atomic, Shopify-attested triple. Actual binding: `computed_signature(raw_body) == received_hmac` only proves the body bytes were HMAC'd by someone holding `api_secret_key` — it says nothing about `shop-domain` or `topic`, which are parsed via `shopify_header` from headers the attacker fully controls in their own outbound HTTP POST [4](#0-3) [5](#0-4) .

Exploit flow: attacker installs the app on their own dev shop, receives a genuine Shopify-signed webhook (any topic, e.g. `app/uninstalled`) with body `B` and valid `hmac-sha256` header `H`. They then send their own POST directly to the app's webhook receiving route with `shopify-shop-domain: victim.myshopify.com`, `shopify-topic: customers/data_request`, body `B`, and header `H` unchanged. `HmacValidator.validate` recomputes HMAC over `B` with `Context.api_secret_key` and compares to `H` — this matches regardless of the headers, so `Registry.process` proceeds to `handler.handle(data: WebhookMetadata.new(topic: "customers/data_request", shop: "victim.myshopify.com", body: parsed_body, ...))` [6](#0-5) .

No existing guard closes this gap: there is no `ShopValidator.sanitize!` or any header/body cross-check invoked in `Registry.process` or `Request` before the handler runs [3](#0-2) . `VerifiableQuery` only requires `hmac` and `to_signable_string`, and `Request` implements `to_signable_string` as the raw body alone [7](#0-6) .

### Impact Explanation
Any handler registered for a mandatory or optional topic can be invoked with an attacker-chosen `shop` value and a body the attacker doesn't need to control the semantic content of (only needs to possess *some* validly-signed body/hmac pair). Host apps that trust `WebhookMetadata#shop` (as documented/intended) for tenant-scoped actions — e.g., GDPR `customers/data_request`, `customers/redact`, `shop/redact`, or `app/uninstalled` cleanup — can be tricked into performing that action against an arbitrary victim shop the attacker never installed to or authenticated against. This is a cross-tenant trust violation matching the Critical category (cross-tenant access via forged webhook metadata).

### Likelihood Explanation
The attacker only needs: (1) their own dev shop with the app installed, to legitimately receive at least one signed webhook (trivial, no secrets needed), and (2) the ability to POST directly to the app's public webhook endpoint with custom headers (any internet client can do this). No `api_secret_key` or access token is required. This is fully repeatable against any victim shop domain the attacker chooses to type into the `shop-domain` header, for any topic the app has a registered handler for. The only constraint is that the attacker's forged request must carry the same raw body bytes as the webhook they legitimately received, so the `body` field seen by the handler is not attacker-chosen content, but the `shop` and `topic` fields are fully attacker-chosen.

### Recommendation
Bind the shop/topic/webhook-id metadata into what is verified before dispatch, e.g.:
- Require host apps (or the gem itself, via `Registry.process`) to verify `request.shop` against a known/installed-shop store (session/offline-token lookup) before invoking the handler, rejecting requests for shops the app has no active installation for.
- Where mandatory-webhook payloads include `shop_id`/`shop_domain` fields, cross-check `parsed_body["shop_domain"]` against `request.shop` and reject on mismatch.
- Consider extending `to_signable_string` or adding a secondary integrity check that incorporates `shop-domain` and `topic` headers, if compatible with Shopify's actual signing contract (Shopify's real signature only covers the body, so this may require an app-level shop-existence check rather than a gem-level signature change).

### Proof of Concept
```ruby
# test/webhooks/registry_test.rb (new test)
def test_process_trusts_unauthenticated_shop_and_topic_headers
  raw_body = "{}"
  secret = ShopifyAPI::Context.api_secret_key
  valid_hmac = Base64.encode64(
    OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), secret, raw_body)
  )

  handler_invocations = []
  fake_handler = Class.new do
    define_method(:handle) { |data:| handler_invocations << data }
  end.new

  ShopifyAPI::Webhooks::Registry.add_registration(
    topic: "customers/data_request",
    delivery_method: :http,
    path: "/webhooks",
    handler: fake_handler,
  )

  # Attacker crafts headers claiming a shop/topic unrelated to the body's
  # original webhook context, using the same raw_body + valid hmac pair
  # they legitimately received for their own shop under a different topic.
  headers = {
    "shopify-topic" => "customers/data_request",
    "shopify-hmac-sha256" => valid_hmac,
    "shopify-shop-domain" => "victim-shop.myshopify.com",
  }

  request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)

  ShopifyAPI::Webhooks::Registry.process(request)

  assert_equal(1, handler_invocations.size)
  assert_equal("victim-shop.myshopify.com", handler_invocations.first.shop)
  # Assert: HMAC only authenticated raw_body ("{}"), yet shop/topic were
  # accepted unauthenticated and dispatched to a handler for a different
  # tenant than the one that ever authenticated with the app.
end
```
This demonstrates that `HmacValidator.validate` returns `true` and `Registry.process` invokes the handler purely based on body/hmac matching, with `shop` and `topic` accepted from unauthenticated headers.
