### Title
Webhook `shop` (and other identity headers) are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by verifying the HMAC of the raw request body, but the `shop` (and `topic`/`webhook_id`/`api_version`) values used to route and attribute the webhook to a tenant come from unauthenticated HTTP headers that are excluded from the signed payload. Any party capable of obtaining one valid `(raw_body, hmac)` pair for the app (e.g., a merchant who has installed the app and thus legitimately receives signed webhooks) can replay that exact body/HMAC to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header, and the gem will accept it as an authentic webhook for the spoofed shop.

### Finding Description
`ShopifyAPI::Webhooks::Request` extracts the shop from a header, not from the signed content: [1](#0-0) 

The value the HMAC is actually computed over is only the raw body: [2](#0-1) 

`HmacValidator.validate` verifies exactly that signable string against the secret — it never incorporates `shop`, `topic`, or `webhook_id`: [3](#0-2) 

`Registry.process` trusts `request.shop` for tenant attribution as soon as the (body-only) HMAC check passes, and forwards it straight into the handler's data object: [4](#0-3) 

The equality the code implicitly assumes — `hmac_verified_bytes == identity_bound_bytes` — does not hold: `hmac_verified_bytes` is `raw_body` only, while `identity_bound_bytes` (the `shop` used by the consuming handler to select which tenant's data to act on) comes from an unsigned header. Because the app's `api_secret_key` is shared across every shop that installs the app, a *valid* `(raw_body, hmac)` pair legitimately delivered to one shop's endpoint remains cryptographically valid when replayed with a different `shop-domain` header value — the signature check has no way to detect the substitution.

### Impact Explanation
This breaks the binding between "request whose authenticity was cryptographically verified" and "shop the host application will treat the payload as belonging to," which is precisely the cross-tenant boundary the rules call out. A host application built on this gem that dispatches webhook handling based on `WebhookMetadata#shop` (the documented and expected usage, see `docs/usage/webhooks.md`) can be made to apply another merchant's webhook body under a spoofed shop identity — e.g., an `orders/create` or `app/uninstalled` payload legitimately received for Shop A can be replayed against Shop B's tenant context, corrupting or spoofing Shop B's data/state. This is a cross-tenant access issue.

### Likelihood Explanation
Exploitation requires the attacker to possess at least one legitimately-signed webhook `(body, hmac)` pair for the app — which any merchant who installs the app obtains automatically and legitimately via normal webhook delivery — and the ability to POST to the app's public webhook endpoint with custom headers, which is trivial for any internet-reachable endpoint. No access to the app's `client_secret` or any other privileged credential is required, only the ability to receive one authentic webhook delivery, so likelihood is realistic for any multi-tenant app using this gem's webhook processing as documented.

### Recommendation
Bind the tenant-identifying fields into the authenticated payload before trusting them: either include `shop`, `topic`, and `webhook_id` header values in the signable string used by `HmacValidator`, or have `Registry.process` cross-check `request.shop` against an independently-verified source (e.g., the session/shop the caller expects) before dispatching to the handler. At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated header data and must not be used alone for tenant-scoped lookups.

### Proof of Concept
1. App is installed on `shop-a.myshopify.com`; Shopify delivers a legitimate webhook: raw body `{"id":1}` with header `x-shopify-hmac-sha256: <valid HMAC of body>` and `x-shopify-shop-domain: shop-a.myshopify.com`.
2. Attacker (which could be the merchant of `shop-a`, or anyone who captured this delivery) replays the exact same body and HMAC header to the app's webhook endpoint but sets `x-shopify-shop-domain: shop-b.myshopify.com`.
3. `HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb:13-31` recomputes the HMAC over the unchanged raw body and it matches, so `Registry.process` in `lib/shopify_api/webhooks/registry.rb:189-199` proceeds and calls the handler with `WebhookMetadata.new(... shop: "shop-b.myshopify.com" ...)`, even though the payload never had anything to do with `shop-b`.
