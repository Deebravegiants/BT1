### Title
Webhook shop identity not covered by HMAC, allowing cross-tenant shop spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while `#shop` is read from an unauthenticated HTTP header. `Registry.process` validates the HMAC over the body only, then forwards the header-derived `shop` value to application handlers as the authenticated tenant identity, breaking the binding `hmac_verified_bytes == identity_attributed_bytes`.

### Finding Description
`Utils::VerifiableQuery#to_signable_string` is the only thing the HMAC actually signs. For webhooks, this is implemented as: [1](#0-0) 

which returns `@raw_body` exclusively. The `shop` accessor, however, is pulled straight from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, which is never included in the signed content: [2](#0-1) 

`Registry.process` validates only the body-bound HMAC and then trusts `request.shop` as the tenant identity forwarded to the caller's handler: [3](#0-2) 

`Utils::HmacValidator.validate` confirms this — it calls `verifiable_query.to_signable_string` (the body) and compares against `verifiable_query.hmac`, never touching `shop`: [4](#0-3) 

The identity binding that should hold is: `shop_covered_by_hmac == shop_delivered_to_handler`. In this implementation, the left side is empty (the header is outside the signed bytes) while the right side is exactly the header value, so the equality never actually gets enforced. Any request whose body+HMAC pair is valid for *some* shop can be replayed with an arbitrary `shop-domain` header and will still pass `HmacValidator.validate`, because the header plays no role in the signature check.

This is directly analogous to the reported Noir `mod.nr` bug: there, the signed sequence bound less than the intended semantic unit (the header-field name wasn't validated as part of what was cryptographically proven), letting an attacker reattribute bytes across a field boundary. Here, the semantic unit that should be authenticated (which merchant a webhook belongs to) is not part of what the HMAC actually binds, letting an attacker reattribute a validly-signed payload to a different `shop`.

### Impact Explanation
An attacker who legitimately receives (or can otherwise obtain) one valid `(raw_body, hmac)` pair signed with the app's shared secret — e.g., a webhook delivered to their own shop's installation, or any endpoint under their control that logs/exposes the payload — can resend that exact body and HMAC to the app's webhook endpoint while substituting the `shopify-shop-domain` header for a victim shop. `HmacValidator.validate` still returns true because it never examined `shop`. The handler then receives `WebhookMetadata` populated with the attacker-chosen `shop` value, causing cross-tenant data injection/processing: the host application will act on webhook data (e.g. `orders/create`, `app/uninstalled`, GDPR topics) as if it originated from a different merchant, without needing the app's `client_secret` or any merchant credentials.

### Likelihood Explanation
Exploitation only requires knowledge of one valid `(body, hmac)` pair for any topic the app subscribes to and network access to the app's webhook endpoint — no `api_secret_key`, access token, or privileged account is required, satisfying the "unprivileged internet user" bar. The gem provides no mechanism (and no documented requirement on host apps) to bind `shop` to the signed payload, so any consumer relying solely on `Registry.process`/`HmacValidator.validate` for authenticity is affected by design.

### Recommendation
Include the shop-identifying header (and ideally topic/webhook-id) in the signable content used for HMAC verification, or require the caller to explicitly re-validate that `request.shop` matches an expected/installed shop before trusting `WebhookMetadata#shop`. At minimum, `HmacValidator.validate` should be extended (or a new check added) so that `to_signable_string` for webhooks binds the shop domain, matching Shopify's actual signing semantics for the fields the library exposes as "verified."

### Proof of Concept
```ruby
# 1. Attacker legitimately receives (or captures) a real webhook for their own shop:
#    headers: { "x-shopify-shop-domain" => "attacker-shop.myshopify.com",
#               "x-shopify-hmac-sha256" => "<valid-hmac-for-body>",
#               "x-shopify-topic" => "orders/create" }
#    body: '{"id":1,...}'

# 2. Attacker replays the identical body+hmac to the victim app's webhook endpoint,
#    only changing the shop header:
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => captured_hmac,       # unchanged, still valid for `body`
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # attacker-controlled
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: captured_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# HmacValidator.validate(request) => true, because it only checks captured_body/hmac.
# handler.handle receives WebhookMetadata(shop: "victim-shop.myshopify.com", ...)
# -> host app processes attacker's data as if it belongs to victim-shop.
```

          received_signature = verifiable_query.hmac
