This confirms the documentation explicitly states `ShopifyAPI::Webhooks::Registry.process` "will verify the request did indeed come from Shopify" — implying the whole request (including `shop`, `topic`, `webhook_id`) is authenticated. But the implementation only binds the raw body to the HMAC.This confirms the design: `Registry.process` calls `Utils::HmacValidator.validate(request)` at [1](#0-0) , which only validates `request.to_signable_string` (the raw body) against the HMAC header, per `HmacValidator.validate_signature` at [2](#0-1) . ### Title
Webhook HMAC only signs the request body, letting the `shop` and `topic` headers be forged for cross-tenant webhook injection - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, and `Utils::HmacValidator.validate` checks the `X-Shopify-Hmac-Sha256` header solely against that body. The `shop-domain`, `topic`, `webhook-id`, and `api-version` values that are handed to the host application's `WebhookHandler#handle` come from separate, unsigned headers. Because the identity fields the app relies on (`WebhookMetadata#shop`, `#topic`) are not part of the HMAC-covered bytes, any party who can obtain one validly-signed webhook body/HMAC pair (e.g., the owner of any shop that installs the app, who legitimately receives real Shopify webhooks) can replay that exact body+HMAC to the app's webhook endpoint while substituting arbitrary `shop`/`topic`/`webhook_id` header values. `HmacValidator.validate` will still return `true`, and `Registry.process` will dispatch the forged metadata to the handler as if it came from a different, victim shop.

### Finding Description
The verification flow is:
- `Registry.process` raises unless `Utils::HmacValidator.validate(request)` passes [6](#0-5) .
- `HmacValidator.validate_signature` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to `verifiable_query.hmac` [2](#0-1) .
- For `Webhooks::Request`, `to_signable_string` returns `@raw_body` only [5](#0-4) , while `shop`, `topic`, and `webhook_id` are parsed straight from HTTP headers with no cryptographic binding to the HMAC [4](#0-3) .
- `Registry.process` builds `WebhookMetadata` directly from these unauthenticated header values and hands it to the app's handler [3](#0-2) .

This is the same bug class as the referenced report: an identity-defining field (there, the vesting position's tick; here, the webhook's `shop`/`topic`) is acted upon by downstream logic without being covered by the value that was actually verified (there, the wrong tick parameter; here, the HMAC covers only the body, not the headers). The equality that is broken is: `shop authenticated by HmacValidator` (= the raw-body signer, i.e., any Shopify shop using the same app secret) is treated as equal to `shop stored/acted upon by the handler` (= whatever the `x-shopify-shop-domain` header claims), when in fact these are two different, independently-controllable pieces of data.

The library's own documentation reinforces the false expectation: it states that `Registry.process` "will verify the request did indeed come from Shopify" [7](#0-6) , and instructs handler authors to trust `data.shop` as "The shop domain of the webhook" without any further validation guidance [8](#0-7) .

### Impact Explanation
Any merchant who installs the app on their own store is a legitimate, unprivileged recipient of correctly-HMAC-signed webhooks for that store (Shopify signs the body with the app's shared secret for every installed shop). That merchant can capture one such body+HMAC pair and resend it to the app's public webhook endpoint with a forged `shopify-shop-domain` header pointing at a different (victim) tenant, and a forged `shopify-topic`/`shopify-webhook-id`. `Utils::HmacValidator.validate` accepts it because it never looks at those headers, and `WebhookMetadata` faithfully carries the attacker-chosen `shop`/`topic` into the app's business logic. Depending on what the host app does with `data.shop` (e.g., look up a tenant record, update order/inventory state, trigger side effects "on behalf of" that shop), this enables cross-tenant data injection/corruption — an attacker acting as themselves can inject events attributed to another shop's tenant boundary. This matches the "cross-tenant access" impact category.

### Likelihood Explanation
Any user capable of installing the target app on their own Shopify store (a completely unprivileged, self-service action) can obtain a validly-signed webhook. Replaying it with modified headers to the app's own publicly reachable webhook URL requires no secret material beyond what Shopify itself already sent them, and no interception of anyone else's traffic.

### Recommendation
Include the identity-defining headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signed material verified against the HMAC — or, at minimum, require the host application to independently verify that `WebhookMetadata#shop` corresponds to a shop that is actually recorded as having installed the app before trusting it, and document this requirement prominently. The library itself should not present `Registry.process` as having "verified the request did indeed come from Shopify" for fields it never actually authenticates.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and lets it register a webhook (e.g., `orders/create`).
2. Shopify sends a real webhook to the app's endpoint with body `B` and a valid `x-shopify-hmac-sha256` computed over `B` using the app's secret.
3. Attacker captures `B` and the HMAC value, then sends their own POST request to the same webhook endpoint URL, keeping body `B` and the same HMAC header, but overriding:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - `x-shopify-topic: orders/create` (or a different registered topic)
   - `x-shopify-webhook-id: <arbitrary>`
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` builds a `Request` whose `hmac` still matches `to_signable_string` (`= B`), because `to_signable_string` never looked at the headers [5](#0-4) .
5. `ShopifyAPI::Webhooks::Registry.process(request)` passes HMAC validation and calls the registered handler with `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)` [9](#0-8) .
6. The host application processes an event as if it genuinely originated from `victim-shop.myshopify.com`, even though `victim-shop` never sent it and the attacker has no relationship to that tenant.
