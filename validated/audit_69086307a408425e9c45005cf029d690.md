### Title
Unauthenticated pipeline-run resumption endpoint accepts and injects arbitrary result data with no whitelist/authorization checks - (File: core/web/pipeline_runs_controller.go)

### Summary
The `PATCH /v2/resume/:runID` route is mounted on an explicitly unauthenticated router group (`unauthedv2`) and dispatches directly to `PipelineRunsController.Resume`, which decodes an attacker-supplied JSON body into a `pipeline.ResumeRequest`, converts it into a `pipeline.Result`, and feeds it straight into `Application.ResumeJobV2` → `pipeline.runner.ResumeRun` → `orm.UpdateTaskRunResult`, which unconditionally overwrites the output/error of the pipeline task and, if the run was suspended, restarts the run. There is no token/role check, no per-job or per-initiator whitelist, and no validation that the caller is entitled to resume that particular run — the only "gate" is guessing/knowing the `runID` UUID.

### Finding Description
`core/web/router.go` registers this route outside of any authentication middleware: [1](#0-0) 


All other job-run creation/mutation endpoints in the same file (e.g. `POST /v2/jobs/:ID/runs`) are gated behind `auth.Authenticate(...)` combined with role checks such as `auth.RequiresRunRole`: [2](#0-1)

`ResumeJobV2` forwards directly to the pipeline runner's `ResumeRun`, which writes the caller-supplied value/error into the task run and restarts the run if it was suspended: [4](#0-3) [5](#0-4) 

The only implicit "authorization" is possession of the `runID` (a task UUID). This mirrors the External Report's root-cause pattern: a state-mutating operation reachable by any unprivileged caller with no whitelist/authorization gate, where the intended access-control layer (here, the node's session/token auth middleware `auth.Authenticate`) is entirely bypassed by design for this one route, unlike its sibling job-run endpoints which are properly wrapped.

### Impact Explanation
Any external, unauthenticated party who obtains or guesses a valid `runID` (task UUID) for a suspended pipeline task (e.g. a webhook/bridge/VRF/external-adapter async task) can:
- Inject arbitrary `value`/`error` results into that pipeline task run, directly controlling downstream data-dependent logic (e.g., price feeds, VRF fulfillment paths, bridge callbacks) that consumes this result.
- Force resumption/execution of a suspended run with attacker-chosen data, potentially corrupting node state, task run outputs used for on-chain submission, or triggering unintended side effects in downstream pipeline tasks.
- Because this is a data-injection primitive into node-internal job execution reachable without any credential, it directly matches the report's "unauthorized state mutation with no whitelist/authorization check" bug class.

The practical severity depends on how hard `runID` values are to obtain (they are UUIDs, which somewhat mitigates blind brute force), but there is no rate limiting, whitelist, ownership check, or authentication defense-in-depth if a UUID leaks (e.g., via logs, error messages, or a compromised bridge/adapter response).

### Likelihood Explanation
Likelihood is `Low-Medium`: exploitation requires knowledge of a valid, currently-suspended task run UUID. However, unlike the on-chain bug report (which required tricking Alice into creating a pool), this endpoint is globally reachable over HTTP with zero authentication by design — a single leaked/observed `runID` (e.g., from an external adapter's async callback configuration, logs, or a misconfigured integration) is sufficient, and no additional privilege, session, or role is ever required.

### Recommendation
- Short term: Add a scoping/whitelist mechanism for the `/v2/resume/:runID` endpoint — e.g., bind each suspended task's resume capability to a per-request signed/HMAC token or restrict acceptable resume sources via an explicit external-initiator/bridge allowlist, rather than relying solely on UUID secrecy.
- Add basic authentication (e.g., a shared secret configured per bridge/external adapter, similar to `ExternalInitiator` access-key/secret auth already used elsewhere in this codebase) before allowing `ResumeJobV2` to execute.
- Long term: Audit all routes registered under `unauthedv2` in `core/web/router.go` and any other webhook-style callback endpoints for consistent, explicit authorization guarantees, following the pattern already used for `AuthenticateExternalInitiator`/`RequiresRunRole` elsewhere in the router.

### Proof of Concept
1. Obtain (via log leakage, external-adapter misconfiguration, or observation) the UUID of a currently `suspended` pipeline task run's `runID`.
2. Send an unauthenticated request:
```
PATCH /v2/resume/<runID>
Content-Type: application/json

{"value": "<attacker-controlled-data>"}
```
3. The request succeeds with HTTP 200 and no credentials — `ResumeJobV2` → `ResumeRun` → `UpdateTaskRunResult` immediately writes the attacker's value into the task run and, if the run was suspended, restarts it (`core/services/pipeline/runner.go:732-755`), all without any authentication middleware (`core/web/router.go:243`).

*Note: I was unable to fully verify runtime guarantees around `runID` unguessability/entropy or whether any external documentation formally sanctions this as an intentional "capability token" design (the audit event name `audit.UnauthedRunResumed` suggests this was a deliberate design decision); this should be validated against the intended threat model for external-adapter callbacks before treating this purely as a bug versus an accepted design trade-off.*

```go
// Resume finishes a task and resumes the pipeline run.
// Example:
// "PATCH <application>/jobs/:ID/runs/:runID"
func (prc *PipelineRunsController) Resume(c *gin.Context) {
	taskID, err := uuid.Parse(c.Param("runID"))
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	rr := pipeline.ResumeRequest{}
	decoder := json.NewDecoder(c.Request.Body)
	err = errors.Wrap(decoder.Decode(&rr), "failed to unmarshal JSON body")
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}
	result, err := rr.ToResult()
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	if err := prc.App.ResumeJobV2(c.Request.Context(), taskID, result); err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	prc.App.GetAuditLogger().Audit(audit.UnauthedRunResumed, map[string]any{"runID": c.Param("runID")})
	c.Status(http.StatusOK)
}
```

```go
func (r *runner) ResumeRun(ctx context.Context, taskID uuid.UUID, value any, err error) error {
	run, start, err := r.orm.UpdateTaskRunResult(ctx, taskID, Result{
		Value: value,
		Error: err,
	})
	if err != nil {
		return fmt.Errorf("failed to update task run result: %w", err)
	}

	// TODO: Should probably replace this with a listener to update events
	// which allows to pass in a transactionalised database to this function
	if start {
		// start the runner again
		go func() {
			ctx, cancel := r.chStop.NewCtx()
			defer cancel()
			if _, err := r.Run(ctx, &run, false, nil); err != nil {
				r.lggr.Errorw("Resume run failure", "err", err)
			}
			r.lggr.Debug("Resume run success")
		}()
	}
	return nil
}
```
