The gem's own documentation explicitly promises that `ShopifyAPI::Webhooks::Registry.process` "will verify the request did indeed come from Shopify" [1](#0-0) , and the documented `WebhookHandler.handle` contract treats `data.shop` as the authenticated "shop domain of the webhook" [2](#0-1) . ### Title
Webhook `shop` (and `topic`/`webhook_id`) identity is trusted without being covered by the HMAC, enabling cross-tenant webhook spoofing via replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so `Utils::HmacValidator` authenticates nothing but the byte content of the body. The `shop` domain, `topic`, and `webhook_id` — all read from HTTP headers — are never part of the signed material, yet `Registry.process` treats a valid body HMAC as proof that these header-derived fields are equally trustworthy and passes them straight to the app's handler as the shop identity.

### Finding Description
`Request#hmac` decodes the `x-shopify-hmac-sha256` header [3](#0-2) , while `Request#shop` reads the `x-shopify-shop-domain` header verbatim, with no cross-check against the signed payload [4](#0-3) . `to_signable_string` — the value that actually gets HMAC'd — is defined as `@raw_body` alone [5](#0-4) . `Utils::HmacValidator.validate` computes the HMAC purely over `to_signable_string` and compares it to the header-supplied `hmac` [6](#0-5) . `Registry.process` then asserts only `Utils::HmacValidator.validate(request)` before constructing `WebhookMetadata` with `shop: request.shop`, `topic: request.topic`, and `webhook_id: request.webhook_id` and forwarding it to the app's handler [7](#0-6) .

This breaks the intended binding `HMAC(body) valid ⟺ (body, shop, topic) came from Shopify for that shop`. In reality the binding only holds for `HMAC(body) valid ⟺ body came from Shopify`; `shop`, `topic`, and `webhook_id` are unauthenticated bystanders. Any party that has previously received one legitimate Shopify webhook body+HMAC pair (e.g., because they installed the app on their own store and captured a webhook their own server received) can replay that exact body and HMAC to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop's domain. `HmacValidator.validate` still succeeds because the body is untouched, and the handler is invoked believing the event originated from the victim shop.

### Impact Explanation
Apps built on this gem are documented to key their webhook processing off `data.shop` as "the shop domain of the webhook" [2](#0-1) , typically to route data, update per-shop records, invalidate caches, or drive billing/plan logic keyed by shop. Since `shop` is not bound to the HMAC, an attacker with one valid (body, HMAC) pair (obtainable from a webhook sent to their own installed instance of the app) can impersonate any other shop domain against the app's webhook handler, causing cross-tenant data confusion in the receiving application — the gem itself has failed to bind the identity it promises to verify ("verify the request did indeed come from Shopify" per the docs, which a reasonable reader would take to include the claimed shop).

### Likelihood Explanation
Exploitation only requires the ability to install the app on an attacker-controlled shop (or otherwise obtain one legitimate body/HMAC pair) and the ability to POST directly to the app's public webhook endpoint with attacker-chosen headers — both are available to an unprivileged internet user with no access to `api_secret_key` or any access token. No signature forgery is required since the HMAC is body-only.

### Recommendation
Include the identity-bearing headers (`shop`, `topic`, and ideally `webhook_id`/`api_version`) in the signed material verified against Shopify's signature, or independently authenticate the shop domain (e.g., by cross-referencing it against a resolvable/active session or the topic's registration) before constructing `WebhookMetadata` and invoking the handler in `Registry.process`.

### Proof of Concept
1. Install the app on `attacker.myshopify.com`; trigger a webhook (e.g. `orders/create`) so Shopify sends `raw_body` B with header `x-shopify-hmac-sha256: H` and `x-shopify-shop-domain: attacker.myshopify.com` to the app's webhook endpoint.
2. Attacker captures `(B, H)` (trivial, since it's their own server/logs).
3. Attacker POSTs to the same app webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H` unchanged, but `x-shopify-shop-domain: victim.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)` [8](#0-7)  which passes because it only hashes `B`.
5. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", topic: ..., body: JSON.parse(B), ...)` [9](#0-8) , and the app processes attacker-supplied data under the victim shop's identity.
