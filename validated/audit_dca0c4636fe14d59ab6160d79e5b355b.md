## Title
Webhook shop-tenant attribution bypass via unauthenticated `shop-domain` header — cross-tenant webhook spoofing (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` value used to attribute an incoming webhook to a specific merchant from the unauthenticated `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, while the HMAC signature that `Registry.process` verifies covers only the raw request body. Because the app's webhook signing secret (`Context.api_secret_key`) is shared across every shop that installs the app, any merchant who has installed the app can capture a genuinely-signed webhook delivered to their own store and replay it to the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop, producing a payload that passes signature validation but is attributed to the wrong tenant.

### Finding Description
The identity binding that should hold is:
`shop value trusted by the handler == shop value cryptographically bound by the HMAC signature`

In this gem that equality does not hold. `Request#to_signable_string` returns only the raw body: [1](#0-0) 

while `Request#shop` is read straight from an HTTP header with no cryptographic binding: [2](#0-1) 

`Registry.process` validates only that body-derived HMAC, then forwards the unauthenticated `request.shop` value directly to the app's handler: [3](#0-2) 

`HmacValidator.validate` computes and compares the signature purely from `verifiable_query.to_signable_string` (the body, for webhooks) and `Context.api_secret_key`: [4](#0-3) 

`Context.api_secret_key` is a single, app-wide secret set once at boot — it is not per-shop: [5](#0-4) 

This means any shop that installs the app can generate a body+HMAC pair that is valid for **every** other shop using the same app, because the signature never incorporates the `shop` field at all — only the JSON body. The `shop-domain` header, which is the only signal the gem exposes to the caller for tenant attribution, travels completely outside the authenticated envelope.

### Impact Explanation
This breaks the tenant boundary of the app. An attacker who is a legitimate but unprivileged installer of the app (i.e., a normal merchant, not an admin of the platform) can:
1. Install the app on their own store and receive a normal, validly-signed webhook (e.g. `orders/create`, `app/uninstalled`, `customers/data_request`).
2. Replay the identical body + `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, but substitute the `X-Shopify-Shop-Domain` header with a victim shop's domain.
3. `HmacValidator.validate` still succeeds (it never looked at the shop header), and `Registry.process` calls the handler with `shop: <victim shop>` — the app's business logic will act as though the event legitimately originated at the victim's store.

Depending on what the host app's `WebhookHandler` does with `data.shop` (e.g., look up per-shop records, trigger data exports/redaction, disable installations, credit/debit shop-scoped resources), this results in cross-tenant data corruption/disclosure or forged lifecycle events for a shop the attacker does not control — satisfying the "cross-tenant access" impact class.

### Likelihood Explanation
Any developer registering an HTTP webhook handler through `ShopifyAPI::Webhooks::Registry` is exposed, because the gem's own `Request#shop` accessor — the documented/only way to learn which shop a webhook is for — is unauthenticated by construction. The attacker only needs to be able to install the target app once on a shop they control (a normal, unprivileged flow) and be able to send an arbitrary HTTP request to the app's public webhook endpoint. No access token, `client_secret`, or privileged credential is required, and no interaction with the victim shop is needed.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the signable material so the tenant identity cannot be forged independently of the payload, e.g. include the `shopify-shop-domain` header value in `to_signable_string`, or have `Registry.process` cross-check `request.shop` against an out-of-band trusted shop record (e.g., the shop stored for the resolved `webhook_id`/subscription) before dispatching to the handler. At minimum, document prominently that `WebhookMetadata#shop` is not authenticated and must not be used as a sole tenant key by consuming applications.

### Proof of Concept
```ruby
# Attacker installs the app on "attacker.myshopify.com" and receives a real webhook:
# POST /webhooks
# X-Shopify-Topic: customers/data_request
# X-Shopify-Hmac-Sha256: <valid HMAC of raw_body using shared Context.api_secret_key>
# X-Shopify-Shop-Domain: attacker.myshopify.com
# Body: {"customer": {...}}

# Attacker replays the SAME body + SAME hmac header, only swapping the shop header:
raw_body = original_captured_body
headers = {
  "x-shopify-topic" => "customers/data_request",
  "x-shopify-hmac-sha256" => original_captured_hmac_header, # unchanged, still valid
  "x-shopify-shop-domain" => "victim-shop.myshopify.com",   # forged
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate succeeds (only raw_body is signed)
# => handler.handle is invoked with data.shop == "victim-shop.myshopify.com"
```
