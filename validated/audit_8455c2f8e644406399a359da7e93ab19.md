### Title
Tendermint consensus client's "disable state machine" check only verifies key presence, not the support flag, reintroducing the M-10 class bug - (File: `modules/ismp/clients/tendermint/src/lib.rs`)

### Summary
The Tendermint ISMP consensus client pallet exposes `set_supported_state_machine(state_machine, supported: bool)`, allowing the admin to enable *or disable* a state machine by writing `true`/`false` into `SupportedStateMachines`. However, `TendermintClient::state_machine()` — the function relied on by request/response/consensus validation to decide whether a state machine may still be processed — only checks `contains_key(id)`, never the stored boolean value. Setting `supported = false` therefore does not disable anything: the map entry still exists, so the check still passes.

### Finding Description
`SupportedStateMachines` is defined as a `bool`-valued map specifically to support toggling support on/off: [1](#0-0) 

`set_supported_state_machine` lets the admin insert `false` to disable a chain without removing it (distinct from `remove_supported_state_machine`, which fully deletes the entry): [2](#0-1) 

But the consumer of this map, `TendermintClient::state_machine`, only checks whether the key exists, not whether its value is `true`: [3](#0-2) 

This is structurally identical to the referenced M-10 mitigation-bypass report: a boolean "enabled/disabled" flag was added, but the invariant check consulted only presence/count in a collection rather than the flag itself, so entries that were supposed to be disabled continue to be treated as active. Here, `state_machine()` is invoked from `validate_state_machine` in the shared ISMP request/response/consensus-update handling path (`modules/ismp/core/src/handlers.rs`), which is reachable by any relayer submitting a `RequestMessage`, `ResponseMessage`, or `ConsensusMessage` referencing that state machine ID.

### Impact Explanation
An admin disabling a Tendermint-tracked chain (e.g., in response to a compromise, chain halt, or governance decision to sever trust) via `set_supported_state_machine(id, false)` gets no actual protection: relayers can continue submitting consensus updates and requests/responses for that "disabled" state machine, and they will still be verified and accepted by `state_machine()`. This is an unauthorized app action — the protocol's own disable control silently fails to enforce the operator's intent, allowing continued acceptance of messages/state commitments from a state machine that governance explicitly intended to cut off. Given ISMP request/response processing can mint/transfer funds and update commitments cross-chain, an attacker exploiting a chain that was disabled specifically because it was no longer trustworthy could get forged messages accepted after the fact.

### Likelihood Explanation
The only precondition is that an admin has called `set_supported_state_machine(id, false)` instead of `remove_supported_state_machine(id)` — both are documented, supported admin operations, and the pallet explicitly provides `supported: bool` as a toggle, so relying on the softer "disable" path is a normal/expected operational flow, not a misuse. Once that state exists, any unprivileged relayer can trigger the bypass by simply submitting proofs referencing that state machine id, which is the same permissionless path used for normal relaying.

### Recommendation
Change `TendermintClient::state_machine()` to check the actual stored value, not just key existence:
```rust
if crate::pallet::SupportedStateMachines::<T>::get(id) == Some(true) {
    ...
} else {
    Err(...)
}
```
Audit sibling pallets (`ismp-arbitrum`, `ismp-optimism`) which use the same `StorageMap<_, _, StateMachine, bool, OptionQuery>` pattern to confirm whether they have (or will introduce) a similar toggle-to-false capability, and apply the same fix consistently — checking `get(id) == Some(true)` rather than `contains_key(id)` everywhere a boolean "enabled" flag exists alongside a set-membership style check.

### Proof of Concept
1. Admin (via `AdminOrigin`) calls `set_supported_state_machine(StateMachine::Evm(X), true)` to onboard chain X.
2. Later, admin calls `set_supported_state_machine(StateMachine::Evm(X), false)` intending to disable chain X (e.g., after detecting a fork/compromise), instead of `remove_supported_state_machine`.
3. `SupportedStateMachines::<T>::get(StateMachine::Evm(X))` now returns `Some(false)`, but `contains_key(StateMachine::Evm(X))` still returns `true`.
4. Any relayer submits a `RequestMessage`/`ResponseMessage`/`ConsensusMessage` referencing chain X; `validate_state_machine` → `TendermintClient::state_machine(StateMachine::Evm(X))` evaluates `contains_key(id)` → `true`, and processing proceeds exactly as if the chain were still enabled. pub fn validate_state_machine<H>(
	host: &H,
	proof_height: StateMachineHeight,
) -> Result<Box<dyn StateMachineClient>, Error>
where
	H: IsmpHost,
{
	// Ensure consensus client is not frozen
	let consensus_client_id = host.consensus_client_id(proof_height.id.consensus_state_id).ok_or(
		Error::ConsensusStateIdNotRecognized {
			consensus_state_id: proof_height.id.consensus_state_id,
		},
	)?;
	let consensus_client = host.consensus_client(consensus_client_id)?;
	// Ensure client is not frozen
	host.is_consensus_client_frozen(proof_height.id.consensus_state_id)?;

	// Ensure delay period has elapsed
	if !verify_delay_passed(host, &proof_height)? {
		return Err(Error::ChallengePeriodNotElapsed {
			state_machine_id: proof_height.id,
			current_time: host.timestamp(),
			update_time: host.state_machine_update_time(proof_height)?,
		});
	}

	consensus_client.state_machine(proof_height.id.state_id)
}
