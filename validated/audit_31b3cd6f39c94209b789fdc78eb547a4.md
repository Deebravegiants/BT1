### Title
Webhook tenant identity (`shop`, `topic`, `webhook_id`) is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC over the raw request body only, while the `shop`, `topic`, `webhook_id`, and `api_version` fields that `ShopifyAPI::Webhooks::Registry.process` uses to route and attribute the webhook to a tenant are taken from unauthenticated HTTP headers. An attacker who can obtain one genuinely-signed webhook (e.g., by installing the app on their own shop and triggering an event) can replay that exact body+HMAC to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a victim shop, causing the handler to process the attacker's payload under the victim's tenant identity.

### Finding Description
`Utils::HmacValidator.validate` verifies a `VerifiableQuery` by comparing the computed HMAC against `to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` returns only `@raw_body`: [2](#0-1) 

But `shop`, `topic`, `webhook_id`, and `api_version` are all derived from HTTP headers, which are entirely outside the HMAC-signed content: [3](#0-2) 

`Registry.process` validates only the body's HMAC, then uses the unauthenticated `request.shop` (and `request.topic`, `request.webhook_id`) directly to construct the `WebhookMetadata` that is handed to the app's registered handler: [4](#0-3) 

The identity binding that should hold is: `shop_bound_by_hmac == shop_used_for_tenant_attribution`. In this implementation, `shop_bound_by_hmac` doesn't exist at all — the HMAC only binds `raw_body`, while `shop_used_for_tenant_attribution` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, a value never included in the signed bytes. This is exactly the "field acted on but not covered by the HMAC" identity-binding break.

### Impact Explanation
Because the `shop` header is unauthenticated relative to the HMAC, an attacker who can produce or capture one legitimate `(raw_body, hmac)` pair — trivially available to any merchant/attacker who installs the app on their own store and triggers a real webhook event for it — can resend that same body and HMAC to the app's webhook endpoint with the `shop-domain` header rewritten to a different, victim shop. `Registry.process` will accept the HMAC (it is valid for the body) and dispatch the handler with `shop: <victim shop>`, even though the payload content actually belongs to the attacker's own shop. Any host application that uses `WebhookMetadata#shop` to select the tenant context (data store, session, GDPR compliance action, etc.) will act on the victim's identity with attacker-controlled webhook body data — a cross-tenant access/confusion condition. This is particularly severe for the mandatory GDPR webhooks (`shop/redact`, `customers/redact`, `customers/data_request`) which are exactly the kind of tenant-scoped compliance actions this gem special-cases in `Registry`.

### Likelihood Explanation
Exploitation requires no access token, client secret, or privileged credential — only network access to the app's public webhook endpoint and the ability to obtain one valid signed webhook (which any unprivileged merchant installing the app on their own store can generate for themselves). Because HTTP headers are fully attacker-controlled on any raw request to a public endpoint, and the gem performs no cross-check between the signed body and the header-derived `shop`/`topic`/`webhook_id`, the replay is straightforward to construct.

### Recommendation
Include `shop`, `topic`, and `webhook_id` (or at minimum `shop`) in the HMAC-signed material, or independently verify that the `shop-domain` header value is consistent with a `shop`/tenant identifier embedded in and protected by the signed body before using it for tenant routing. At minimum, document that `WebhookMetadata#shop` is not cryptographically bound to the payload's HMAC and must not be trusted for tenant attribution without additional verification (e.g., cross-checking against the resource IDs in the JSON body via a separate trusted lookup).

### Proof of Concept
1. Attacker installs the app on their own shop `attacker.myshopify.com` and triggers any subscribed webhook topic (e.g., `orders/create`), causing Shopify to send a genuine POST with headers `X-Shopify-Hmac-Sha256: <valid hmac>`, `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Topic: orders/create`, and some JSON body `B`.
2. Attacker captures this exact `raw_body = B` and `hmac` value.
3. Attacker sends a new POST to the app's public webhook endpoint with the identical `raw_body` and `X-Shopify-Hmac-Sha256` header, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only validates `raw_body` against the secret — see [5](#0-4) .
5. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and `body` from the attacker's own webhook payload, causing the host app to act on `victim.myshopify.com`'s tenant context using attacker-supplied data.
