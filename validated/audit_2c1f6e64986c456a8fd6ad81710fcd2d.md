Confirmed: the `Webhooks::Request#hmac` validation in `lib/shopify_api/webhooks/registry.rb` and `lib/shopify_api/webhooks/request.rb` signs only the raw body, while `shop` (and `topic`/`webhook_id`) are read from unauthenticated HTTP headers and passed straight into the handler as the tenant identifier.

### Title
Webhook `shop` domain is read from an HMAC-unauthenticated header, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop` from the `x-shopify-shop-domain` / `shopify-shop-domain` HTTP header, but the HMAC signature validated by `ShopifyAPI::Utils::HmacValidator.validate` only covers the raw request body (`to_signable_string` returns `@raw_body`). The header carrying the tenant identity is never part of the signed material, so the binding "HMAC-authenticated payload == tenant the payload is attributed to" is broken. [1](#0-0) [2](#0-1) 

### Finding Description
`Webhooks::Registry.process` validates the request purely via `Utils::HmacValidator.validate(request)`, which computes the signature over `request.to_signable_string` (the raw body only) and compares it against the `hmac` header value using `OpenSSL.secure_compare`. [3](#0-2) 

After that single check passes, `request.shop` — sourced from the `shopify-shop-domain`/`x-shopify-shop-domain` header, a value completely outside the HMAC's signed input — is forwarded unchanged into `WebhookMetadata.new(... shop: request.shop ...)` and handed to the host application's webhook handler as the authoritative tenant identifier. [4](#0-3) [5](#0-4) 

The identity binding that should hold is:
`hmac_valid(body) == shop_that_body_belongs_to`

But the actual binding enforced by the code is only:
`hmac_valid(body) == true`

with `shop` supplied from an entirely separate, unsigned channel. Any party who can obtain one genuine, HMAC-signed webhook body for topic X (e.g., because they run their own installed instance of the app on their own store, so Shopify legitimately delivers them signed webhooks) can replay that same body to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop's domain. `HmacValidator.validate` will still succeed, because it never inspected the header, and the handler will process the payload as if it belongs to the victim tenant.

### Impact Explanation
This breaks the tenant/shop identity binding that host applications rely on when using this gem's webhook layer: `WebhookMetadata#shop` is documented and used by consuming apps to scope database writes, cache invalidation, uninstall/redact handling, etc., to a specific merchant. Because the header is not covered by the signature, an attacker who legitimately controls one shop (their own dev/test store with the app installed, generating real signed webhooks) can forge webhook deliveries that are misattributed to a different, victim shop — i.e., cross-tenant access/confusion inside the app that trusts this gem's HMAC verification as the sole authenticity+identity check.

### Likelihood Explanation
Exploitation only requires: (1) attacker has the app installed on any shop they control (trivial — anyone can install a public app, or run a dev store), (2) attacker can reach the app's public webhook endpoint (it's a public HTTP endpoint by design), and (3) capture/replay a body they legitimately received with its valid HMAC while swapping the header. No access to `api_secret_key`, tokens, or the target's credentials is required, and no interaction with a specific victim is needed beyond knowing/guessing their myshopify domain (which is generally discoverable/public).

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) values into the material that is HMAC-verified, or otherwise cryptographically tie the header-derived shop to the signed body (e.g., include the header values in `to_signable_string`, or require host apps to additionally verify `shop` against a known/expected value per registered handler before trusting `WebhookMetadata#shop`). At minimum, document prominently that `shop` is unauthenticated and must not be trusted as a tenant identifier without additional application-level verification.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a real webhook (e.g. `orders/create`), capturing the raw body `B` and the valid `x-shopify-hmac-sha256` header `H` that Shopify computed over `B` using the shared `client_secret`.
2. Attacker POSTs the same body `B` and header `H` to the app's webhook endpoint, but replaces `x-shopify-shop-domain: attacker-shop.myshopify.com` with `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {..., "x-shopify-shop-domain" => "victim-shop.myshopify.com", "x-shopify-hmac-sha256" => H})` is constructed; `Utils::HmacValidator.validate(request)` recomputes the HMAC over `B` only and it matches `H`, returning `true`. [6](#0-5) 
4. `Registry.process` proceeds and calls the registered handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the host application to process attacker-controlled data under the victim shop's identity. [7](#0-6)

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
