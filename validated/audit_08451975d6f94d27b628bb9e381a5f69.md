### Title
Webhook shop-domain header not covered by HMAC allows cross-tenant shop spoofing - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw request body, but the `shop` value it hands to the application's webhook handler is read from an HTTP header that is not included in the signed material. This breaks the intended binding `shop authenticated by HMAC == shop attributed to the webhook payload`, letting an attacker who can obtain one genuine, validly-signed webhook (e.g., by installing the public app on their own shop) replay that same body/HMAC pair while substituting an arbitrary victim `shop-domain` header value.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is never included in the signable string: [2](#0-1) [3](#0-2) 

`Registry.process` validates the HMAC (over the body only) and then forwards `request.shop` unchanged into `WebhookMetadata`, which becomes the tenant identifier the host app's handler acts on: [4](#0-3) 

The `HmacValidator.validate` call computes/compares the signature purely against `verifiable_query.to_signable_string`, i.e., the raw body, using the app's `api_secret_key`: [5](#0-4) 

The gem's own documentation instructs host apps to key their business logic directly off `data.shop`: [6](#0-5) 

Because the HMAC signature is computed over the body alone and the same `api_secret_key` is shared across every shop that installs the app, any entity that can install the app on a shop it controls receives genuine `(body, hmac)` pairs signed by Shopify for that installation. That attacker can then submit a request to the app's webhook endpoint with the captured, still-valid `(body, hmac)` pair but an attacker-chosen `x-shopify-shop-domain` header naming a victim shop. `HmacValidator.validate` still succeeds (it never looks at the shop header), so `Registry.process` treats the payload as authentic and dispatches it to the handler tagged with the victim's shop domain — an equality the gem should enforce (`shop bound by HMAC == shop delivered to handler`) but does not.

### Impact Explanation
This is a cross-tenant identity-binding break: an unprivileged attacker (any developer who can install the public app on a shop) can make the host application's webhook processing pipeline believe fabricated/attacker-controlled webhook data belongs to an arbitrary victim merchant. Depending on how the host app uses `WebhookMetadata#shop` (e.g., looking up/updating merchant records, triggering per-shop side effects, feeding an uninstall/GDPR flow, or writing into merchant-scoped storage keyed by `data.shop`), this enables cross-tenant data corruption or injection under another merchant's identity, satisfying the "cross-tenant access" criterion.

### Likelihood Explanation
Exploitability requires only: (1) publishing/installing the vulnerable app on an attacker-controlled shop (ordinary, unprivileged action for any public Shopify app), (2) capturing one legitimate webhook delivery for a chosen topic, and (3) replaying it to the app's public webhook endpoint with a forged `shop-domain` header. No access to the app's `client_secret`, access tokens, or any privileged credential is required — the attacker only needs their own shop's legitimately-delivered webhook, which is inherent to how the gem signs webhooks (HMAC over body only, shared secret across tenants).

### Recommendation
Bind the shop identity to the signed payload rather than trusting an unauthenticated header: verify that `request.shop` matches a value derivable from the signed body (most webhook payloads Shopify sends already include shop-scoped identifiers), or, at minimum, document and enforce that host applications must independently corroborate `data.shop` against a shop known to have an active registration for that specific `webhook_id`/topic before trusting it as a tenant key. Alternatively, extend `to_signable_string` to include the shop-domain header content so `HmacValidator` binds the two together.

### Proof of Concept
1. Attacker installs the target public app on `attacker-shop.myshopify.com`, obtaining a real installation with the app's shared `api_secret_key` used for HMAC signing.
2. Attacker triggers a webhook event (e.g., `orders/create`) on their own shop and captures the raw POST body `B` and the `x-shopify-hmac-sha256` header `H` that Shopify sent — both valid and correctly signed for `B`.
3. Attacker sends a new POST to the app's webhook endpoint reusing body `B` and header `H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and any topic/webhook-id headers of choice).
4. `ShopifyAPI::Webhooks::Request.new` accepts the request (all required headers present); `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `B` only and matches `H` — validation passes.
5. `Registry.process` invokes the registered handler with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)`, causing the host application to process attacker-supplied data as though it originated from the victim shop.
