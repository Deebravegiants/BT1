### Title
Unpatched fee-on-transfer accounting in Tron IntentGatewayV2.placeOrder causes escrow over-crediting and stuck withdrawals - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron variant of `IntentGatewayV2.placeOrder` (`evm/tron/contracts/apps/IntentGatewayV2.sol`) credits the per-order escrow ledger `_orders[commitment][token]` using the **nominal** `order.inputs[i].amount` (minus protocol fee) rather than the token amount *actually received* by the contract. The main EVM contract (`evm/src/apps/IntentGatewayV2.sol`) was explicitly patched to measure actual received balances for exactly this reason (fee-on-transfer tokens), as shown by its "Phase 1: Transfer tokens and record actual received amounts" logic and the dedicated `FEE-ON-TRANSFER TOKEN TESTS` in `evm/tests/foundry/IntentGatewayV2SameChainTest.sol`. The Tron copy of the same contract was not given this fix.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol::placeOrder`:

- `reducedInputs` is computed purely from `order.inputs[i].amount` (the amount the user *claims* to send) minus the protocol fee — it never reflects what the contract actually receives: [1](#0-0) 

- In the direct-transfer branch (no predispatch), the contract calls `safeTransferFrom` and then unconditionally credits escrow with the nominal `reducedInputs[i].amount`, without checking the actual balance delta: [2](#0-1) 

- In the predispatch branch, dust is measured against the call-dispatcher's actual balance (`balance - requiredAmount`), but the escrow credit again uses the nominal `reducedInputs[i].amount`, and moreover the accounting happens *before* the final `transferCalls` dispatch that actually moves tokens from the dispatcher to the gateway — so any transfer-fee loss on that final hop is not measured at all: [3](#0-2) 

For a fee-on-transfer ERC20, `safeTransferFrom(msg.sender, address(this), amount)` delivers less than `amount` to the gateway, but `_orders[commitment][token]` is incremented as if the full (fee-reduced-by-protocol-fee-only) `amount` arrived. Because `_orders[...] += ...` aggregates escrow liabilities per token across many orders/commitments, the contract's cumulative recorded liability for that token exceeds its actual on-chain balance of that token.

This is the exact bug class from the referenced report: `depositAsset`/escrow bookkeeping is not adjusted for tokens that charge a fee on transfer, so the stored value is greater than what was actually transferred in.

### Impact Explanation
Since escrow amounts recorded for a given ERC20 are aggregated system-wide (not tracked per-actual-balance), once any fee-on-transfer token is used as an order input, the gateway's liabilities for that token become permanently under-collateralized by the accumulated fee amount. When users/solvers later redeem escrow (via the cross-chain `RedeemEscrow` withdrawal path) or the order is filled/cancelled and the contract attempts to pay out the recorded escrow amount, the actual token balance held by the contract can be insufficient. This causes:
- Reverting withdrawals once the shortfall is reached, freezing funds for whichever legitimate order/solver attempts withdrawal after the pool is depleted (a race condition where earlier claimants drain the real balance and later legitimate claimants are permanently unable to withdraw their entitled tokens).
- A systemic under-backing of the token pool that grows with every fee-on-transfer deposit, i.e. permanent freezing/loss of user funds without any malicious actor needed — triggered purely by normal use of a standard fee-on-transfer token, reachable by any unprivileged user calling `placeOrder`.

This matches the required impact bar: permanent freezing of funds for at least one legitimate party.

### Likelihood Explanation
Reachable by a single unprivileged transaction: any user can call `placeOrder` with a fee-on-transfer ERC20 as an input token — no special privileges, governance, or malicious admin needed. The main (non-Tron) `IntentGatewayV2.sol` was already patched for this precise issue with extensive dedicated tests, confirming this is a known, real, and previously-fixed bug class for this codebase — the Tron variant simply reintroduces it because the fix was not ported.

### Recommendation
Port the actual-received-balance measurement pattern from `evm/src/apps/IntentGatewayV2.sol` into `evm/tron/contracts/apps/IntentGatewayV2.sol`: measure `balanceOf(address(this))` before and after each `safeTransferFrom`/dispatcher sweep, mutate `order.inputs[i].amount` to the actually-received delta before computing `reducedInputs`/the commitment hash, and only credit `_orders[commitment][token]` with that actually-received (post-protocol-fee) amount. For the predispatch branch, also account for the fee-on-transfer loss incurred on the final `transferCalls` hop from the dispatcher to the gateway before crediting escrow.

### Proof of Concept
1. Deploy a standard fee-on-transfer ERC20 (e.g., 1% fee) and register it as an accepted input token on the Tron `IntentGatewayV2`.
2. User A calls `placeOrder` with `inputs = [{token: FOT, amount: 1000e18}]`. `safeTransferFrom` delivers only ~990e18 to the gateway, but `_orders[commitment][FOT]` is credited with `reducedInputs[0].amount` derived from `1000e18` (minus protocol fee), e.g. ~999.7e18 — already ~9.7e18 more than the contract actually holds for this order alone.
3. Repeat with User B, C, ... using the same token; each order compounds the shortfall in the gateway's real FOT balance vs. its recorded aggregate escrow liability.
4. When orders are filled/cancelled or `RedeemEscrow` requests are processed for FOT, the last withdrawer(s) attempting to claim their recorded escrow amount find the contract's actual FOT balance insufficient, causing their withdrawal to revert — their funds are permanently stuck while the token remains supported (analogous to `evm/tests/foundry/IntentGatewayV2SameChainTest.sol::testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived`, which demonstrates the exact mismatch that the main-chain contract had to fix).
