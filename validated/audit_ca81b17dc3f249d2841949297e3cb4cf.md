### Title
Webhook shop-domain header is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies a webhook's authenticity by validating the HMAC over the raw request body only, then trusts the unauthenticated `shopify-shop-domain` HTTP header as the tenant identifier passed to the host app's handler. Because the header sits outside the HMAC's signable content, the binding "HMAC-verified request == request from claimed shop" does not hold, and the shop identity can be substituted independently of the signed payload.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` reads directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header without any cryptographic binding to the body or HMAC: [2](#0-1) 

`Registry.process` validates only the HMAC (which covers the body) and then forwards `request.shop`, taken from the unauthenticated header, straight into `WebhookMetadata` for the host app's handler to consume as the tenant identity: [3](#0-2) 

The documentation explicitly tells integrators that `Registry.process` "will verify the request did indeed come from Shopify" and that `data.shop` is "The shop domain of the webhook": [4](#0-3) [5](#0-4) 

This is the identity-binding break called out by the analog: a field acted on (`shop`, used as the tenant key by every handler built against this documented API) is not covered by the HMAC that this gem itself computes and treats as its authenticity check. `HmacValidator.validate` only proves `HMAC(raw_body) == received_hmac`; it proves nothing about which shop the payload belongs to, yet the gem's own `process` method is documented as if it fully authenticates the shop-attributed request.

### Impact Explanation
Any entity that owns a legitimate, currently-installed instance of the app (i.e., an ordinary merchant/tenant — an "unprivileged" party relative to other tenants) receives real webhooks from Shopify with a valid `raw_body` + `hmac-sha256` pair signed with the app's `client_secret`. Because the `shop-domain` header is unsigned, that same body/HMAC pair can be replayed to the app's public webhook endpoint with the `shopify-shop-domain` header changed to a different (victim) shop. `Registry.process` still reports the HMAC as valid (it only checks the body) and the host app, following this gem's documented contract, attributes the event to the attacker-chosen shop. This is a cross-tenant identity confusion: data intended for/about shop A gets processed under shop B's identity in any handler that keys work off `data.shop` (job scheduling, per-shop metafield writes, GDPR redact processing, etc., as shown in the gem's own doc example `perform_later(topic: data.topic, shop_domain: data.shop, ...)`).

### Likelihood Explanation
Exploitation requires only an HTTP request forgeable by anyone with network access to the app's public webhook endpoint plus one previously-observed legitimate webhook (trivially obtainable by installing the app once, or intercepting one's own shop's webhook traffic). No `api_secret_key`, access token, or privileged account is needed — the HMAC itself is reused unmodified, only the untrusted header is changed.

### Recommendation
Bind the shop identity into the authenticated signable content, or otherwise verify it out-of-band: either include `shop-domain` (and ideally `webhook-id`/`api-version`) in `to_signable_string` alongside the body so the HMAC covers them, or require the host app to independently confirm the claimed shop has an active session/installation before trusting `data.shop`, and update the docs to stop asserting that `process` fully verifies "the request did indeed come from Shopify" when in fact only the body is verified.

### Proof of Concept
1. App receives a genuine webhook for `shop-a.myshopify.com`: `POST /callback/orders/create` with header `shopify-shop-domain: shop-a.myshopify.com`, `shopify-hmac-sha256: <valid HMAC of body>`, and some `raw_body`.
2. Attacker (owner/operator of `shop-a`, or anyone who intercepted this request) resends the identical `raw_body` and identical `shopify-hmac-sha256` value to the same endpoint, but sets `shopify-shop-domain: shop-victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(raw_body)` and finds it matches the supplied HMAC — validation passes [6](#0-5) .
4. The handler is invoked with `WebhookMetadata.new(... shop: request.shop ...)` where `request.shop` is `"shop-victim.myshopify.com"` [7](#0-6) , even though the payload actually originated from `shop-a`'s data — no `api_secret_key` or credential of `shop-victim` was ever needed.
