## Finding

### Title
Webhook Shop-Domain Spoofing via HMAC Verification Scope Mismatch - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary

`ShopifyAPI::Webhooks::Registry.process` treats a webhook as fully authenticated ("verified... did indeed come from Shopify") once `Utils::HmacValidator.validate` succeeds, and then hands the request's `shop` header straight to the app's handler as trusted tenant identity. However, the HMAC signature only ever covers the raw request body — never the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers. Any party who can obtain one validly-signed webhook body/HMAC pair for the app (e.g. a merchant who legitimately installed the app on their own store) can replay that exact body+HMAC to the app's webhook endpoint while substituting a different shop's domain in the header, and the gem will report the payload as authenticated data belonging to the victim shop.

### Finding Description

`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

The `shop` accessor is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of that signable string: [2](#0-1) 

`Registry.process` validates the HMAC against `to_signable_string` (body only) and then, on success, immediately trusts `request.shop` when constructing the metadata passed to the app's handler: [3](#0-2) 

`HmacValidator.validate`/`validate_signature` compute the HMAC purely from `verifiable_query.to_signable_string`, i.e. the body, using the app's shared `api_secret_key`: [4](#0-3) 

The equality this design is supposed to enforce is: **shop claimed in header == shop that Shopify actually generated this signed payload for**. In reality the gem only proves: **body bytes == body bytes signed by *some* installation of this app** (since `api_secret_key` is shared across every shop that has installed the app, not shop-specific). The `shop` field is therefore acted upon (passed to the handler as authoritative tenant identity) without being covered by the HMAC that "verifies" the request.

The documentation reinforces the false impression of full verification: "construct a `ShopifyAPI::Webhooks::Request`... call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify" and describes `shop` as "The shop domain of the webhook" without any caveat that it is unauthenticated: [5](#0-4) [6](#0-5) 

A host app following this documented pattern exactly (as shown in the gem's own examples) will treat `data.shop` as a verified tenant identifier, e.g. to key into its session/token store or attribute the payload to a specific merchant record — exactly the scenario the docs recommend (`perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`).

### Impact Explanation

Since `api_secret_key` is one shared secret per app (not per shop), any merchant who has installed the app can capture one of their own legitimately-signed webhook deliveries (raw body + `X-Shopify-Hmac-Sha256`). They can then replay that exact body/HMAC pair to the app's webhook endpoint while overwriting the `X-Shopify-Shop-Domain` header to name a different, victim shop. `HmacValidator.validate` will still pass (it never looked at the header), and `Registry.process` will dispatch to the handler with `WebhookMetadata#shop` claiming the victim shop. Depending on how the host app (following the gem's documented pattern) uses `data.shop` — e.g. to write orders/customers, to trigger GDPR `customers/redact`-style deletions, or to key per-tenant business logic — this allows cross-tenant data injection/corruption or unauthorized destructive actions attributed to a shop that never sent the data. This is a cross-tenant boundary break, matching the Critical impact category (cross-tenant access) via a low-privilege actor (any merchant who installed the app).

### Likelihood Explanation

Exploitation requires only that the attacker be a legitimate but unprivileged installer of the target app (able to receive their own webhooks) and be able to POST to the app's public webhook endpoint with a captured body/HMAC and forged shop header — no access token, `api_secret_key`, or victim credentials needed. The gem's own documented integration pattern directly propagates the unauthenticated `shop` field as trusted, so any app built per the docs is exposed without additional gem-level mitigation.

### Recommendation

Include the shop domain (and ideally topic/webhook-id) in the HMAC-signable content, or independently verify `request.shop` against the set of shops that have valid, corresponding webhook registrations/sessions for this app before dispatching to handlers. At minimum, update `Registry.process`/documentation to explicitly warn that `shop` is not covered by the HMAC and must be corroborated against known installed shops before being trusted.

### Proof of Concept

1. App has two installs: attacker's shop `attacker.myshopify.com` and victim shop `victim.myshopify.com`, both under the same app (`api_secret_key` shared).
2. Attacker triggers a webhook to their own shop (e.g. `orders/create`) and captures the raw POST: body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
3. Attacker replays the request to the app's webhook endpoint, keeping body `B` and header `H` unchanged, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses headers, `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `request.to_signable_string` (`= B`) and matches `H` — validation succeeds. [7](#0-6) 
5. Handler receives `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: <attacker's body>, ...)` and processes/persists it as authenticated data for the victim shop.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
