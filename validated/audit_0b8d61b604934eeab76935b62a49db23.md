## Title
Repeated `changeLockTimer`/`restartAutoLockTimer` calls allow indefinite retention of cached passphrase, preventing auto-lock and enabling continued secret disclosure - (File: `features/application/src/modules/passphrase-cache.ts`)

### Summary
The Shelter bug's root cause is a privileged actor being able to repeatedly reset a timer-based expiry check (`activate`), which blocks the user-protective action (`withdraw`) while keeping the door open for the privileged action (`deactivate`) to drain funds. The closest reachable analog in this codebase is the `PassphraseCache` auto-lock mechanism in `features/application/src/modules/passphrase-cache.ts`, exposed through `Application.changeLockTimer` / `Application.restartAutoLockTimer` in `features/application/src/modules/application.ts` and the public headless API in `features/application/src/api/index.ts`.

### Finding Description
`PassphraseCache.changeTtl` and `PassphraseCache.scheduleClear` both reset the inactivity/expiry checkpoint used to decide when the cached passphrase should be cleared: [1](#0-0) 

- `changeTtl(ttl)` sets a new TTL on `#autoLockTimerAtom` and, if a passphrase is currently cached, reschedules the clear alarm via `#scheduleClear()`.
- `scheduleClear()` writes a fresh `INACTIVE_AT_KEY = Date.now()` and reschedules the clear alarm again.

The `get()` method's expiry check relies entirely on this rolling checkpoint: [2](#0-1) 

Because both `changeTtl` and `scheduleClear` can be invoked repeatedly and unconditionally reset the `inactiveAt` checkpoint (there is no maximum absolute-age cap once `inactiveAt` is set — only the `maxTtl` cap applies to the `addedAt` branch, which stops being consulted once `inactiveAt` exists), any caller with access to `Application.changeLockTimer({ ttl })` or `Application.restartAutoLockTimer()` can keep the cached passphrase alive indefinitely, structurally identical to how Shelter's `activate()` resets `activated[_token]` to keep the grace-period condition perpetually satisfied for the privileged party.

These methods are wired straight through to the public application/wallet API surface with no additional authorization check inside the module itself: [3](#0-2) [4](#0-3) 

and are re-exported (marked deprecated but still functional) through the headless SDK's `wallet` namespace: [5](#0-4) 

### Impact Explanation
If any less-trusted surface (e.g., a compromised or malicious UI layer, an extension content script, or any RPC-connected process that can reach the `application`/`wallet` API namespace) can invoke `changeLockTimer` or `restartAutoLockTimer` on a cadence shorter than the configured TTL, it can prevent the wallet's auto-lock/passphrase-clear from ever firing. Since the cached passphrase feeds `#autoUnlock` in `Application`, this keeps the wallet perpetually unlocked and the passphrase perpetually retrievable from cache — a direct secret-disclosure / persistent-unlock condition, analogous to the "prevent user withdraw while attacker drains" pattern in the original report (here: "prevent the user's session from ever timing out while the attacker-reachable surface keeps read access to unlock secrets").

### Likelihood Explanation
Exploitability depends on whether an untrusted or lower-privilege component (versus only the fully-trusted extension background/UI) has a reachable path to call `application.changeLockTimer` / `application.restartAutoLockTimer`. From the indexed code, these are exposed as ordinary methods on the `applicationApi`/`wallet` API surfaces without any explicit origin or capability check inside `passphrase-cache.ts` or `application.ts` — the gating (if any) would have to come from whichever RPC transport layer restricts which processes can reach this API object. I could not fully verify within the indexed files which specific channel(s) (background RPC, content-script RPC, or webpage-facing provider) are wired to expose this particular namespace to less-trusted contexts, so likelihood should be treated as **Medium** pending that verification — this is a plausible, code-supported degradation of the intended lock/TTL security boundary but not a fully proven cross-privilege call path from the indexed sources alone.

### Recommendation
- Bind the effective session lifetime to an immutable "first activation" timestamp (analogous to not letting `activate` reset the grace period) rather than only tracking a rolling `inactiveAt` checkpoint, so repeated `changeTtl`/`scheduleClear` calls cannot indefinitely postpone expiry.
- Enforce a hard maximum absolute cache lifetime (already partially present via `#maxTtl` for the `addedAt` branch) that also applies once `inactiveAt` is set.
- Restrict which internal processes/contexts are permitted to call `changeLockTimer` / `restartAutoLockTimer`, ensuring only the fully-trusted UI/background context (not any RPC-connected content script or web-facing provider) can extend the lock timer.

### Proof of Concept
1. Wallet is unlocked with a passphrase; `PassphraseCache.set(passphrase)` caches it with `addedAt` and a `ttl` from `#autoLockTimerAtom` [6](#0-5) .
2. Shortly before the TTL/inactivity window would expire, a component with access to the `application`/`wallet` API calls `application.restartAutoLockTimer()` (→ `PassphraseCache.scheduleClear()`), which rewrites `INACTIVE_AT_KEY` to `Date.now()` [7](#0-6) .
3. Repeating step 2 on an interval shorter than `ttl` keeps `get()`'s `inactiveAt + ttl > Date.now()` check perpetually true [8](#0-7) , so the cached passphrase never expires and `#autoUnlock` keeps succeeding indefinitely [9](#0-8) .

  async changeTtl(ttl: number) {
    const newTtl = Math.min(this.#maxTtl, ttl)

    await this.#autoLockTimerAtom.set(newTtl)

    const passphrase = await this.#storage.get(PASSPHRASE_KEY)

    if (passphrase) {
      await this.#storage.set(TTL_KEY, newTtl)

      void this.#scheduleClear()
    }
  }

  async scheduleClear() {
    const passphrase = await this.#storage.get(PASSPHRASE_KEY)

    if (passphrase) {
      await this.#storage.set(INACTIVE_AT_KEY, Date.now())

      void this.#scheduleClear()
    }
  }
