### Title
Session ID trusted directly from an unauthenticated cookie enables cross-tenant session hijacking via guessable IDs - ([File: lib/shopify_api/utils/session_utils.rb])

### Summary
For non-embedded (and embedded-without-JWT) flows, `ShopifyAPI::Utils::SessionUtils.current_session_id` returns the *raw, unauthenticated* cookie value as the session id with no cryptographic verification. Because the gem also sets that cookie's value to the fully deterministic session id (`offline_#{shop}` or `#{shop}_#{user_id}`), an attacker who knows (or guesses) a target shop's domain can forge the cookie in a direct HTTP request and have this gem return that shop's session id, which host applications then use to look up the stored `Session`/access token — bypassing any real proof of identity for that shop.

### Finding Description
The identity binding this gem should enforce is:
`{shop that legitimately completed OAuth and owns the cookie}` == `{shop whose session id/token gets returned by current_session_id}`

Two pieces of code combine to break this:

1. The non-embedded OAuth flow sets the session cookie's value equal to the deterministic session id, not a random opaque token: [1](#0-0) 

2. `SessionUtils` computes offline/online session ids deterministically from the shop (and user id) alone: [2](#0-1) [3](#0-2) 

3. `current_session_id`/`cookie_session_id` then simply echoes back whatever value is present in the `Cookie` header — with zero verification that this value was ever issued by the server for the current requester, or that it is bound to any authenticated fact about the request: [4](#0-3) [5](#0-4) 

Unlike the JWT/session-token path, which is cryptographically signed and verified (`Auth::JwtPayload`), the cookie path has no HMAC, no signature, and no server-side nonce check at read time (the only nonce check the gem performs, `state == auth_query.state` in `Oauth.validate_auth_callback`, happens once during the OAuth callback and is irrelevant to subsequent `current_session_id` calls): [6](#0-5) 

Because the value that ends up in the cookie is fully predictable from public information (the shop's `myshopify.com` domain, or `shop_user-id` for online sessions), any unprivileged internet user can synthesize the identical bytes and present them as their own cookie in a raw HTTP request to the host app — this gem will happily return that string as "the current session id" as documented: [7](#0-6) 

### Impact Explanation
Per the documented usage pattern, an application uses the value returned by `current_session_id` as the lookup key into its session store to retrieve the stored `Session` object (containing the shop's access token) for making authenticated Admin API calls. Since the id is deterministic and unauthenticated at read time, an attacker who knows a target shop's domain can obtain that shop's session id without ever completing OAuth for that shop, and use it to have the host application load and act with the victim shop's stored access token — i.e., cross-tenant access facilitated entirely by this gem's session-id derivation logic.

### Likelihood Explanation
Likelihood is high for non-embedded apps that follow this gem's documented cookie flow literally: shop domains are commonly public/guessable (`{shop-name}.myshopify.com`), and no additional secret material is required to construct the forged cookie value — only knowledge of the target's shop name (and, for online sessions, its numeric Shopify user id, which is often also discoverable). The attack requires no access token, no `api_secret_key`, and no privileged account — only the ability to send an HTTP request with a custom `Cookie` header.

### Recommendation
Do not use the raw, predictable session id as the literal cookie value. Instead:
- Store a server-generated random opaque token (e.g. `SecureRandom`) in the cookie and map it server-side to the session id, or
- Sign/HMAC the cookie value (similar to `Utils::HmacValidator`) so `cookie_session_id` can verify authenticity before returning it, or
- At minimum, document prominently that `SessionCookie` values must be treated as bearer secrets requiring `Secure`, `HttpOnly`, and `SameSite=Strict` cookie attributes, and that the returned id must never be trusted without an accompanying authenticated proof of the current shop.

### Proof of Concept
1. Attacker observes/knows victim shop's domain, e.g. `victim-shop.myshopify.com` (public knowledge, e.g. via the storefront).
2. Attacker computes the deterministic offline session id the same way this gem does: `"offline_victim-shop.myshopify.com"` (see `Session.from` / `SessionUtils.offline_session_id`).
3. Attacker sends a request to the host application's authenticated endpoint with header:
   `Cookie: shopify_per_user_session=offline_victim-shop.myshopify.com`
4. The host app calls `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)`, which returns `"offline_victim-shop.myshopify.com"` verbatim from `cookie_session_id` with no verification.
5. The host app looks up this id in its session store (per this gem's documented pattern) and retrieves the victim shop's stored `Session`/access token, then makes Admin API calls on the attacker's behalf using the victim's credentials — cross-tenant access achieved without any authentication as the victim shop.

#### Cookie
Cookie based authentication is not supported for embedded apps due to browsers dropping support for third party cookies due to security concerns. Non-embedded apps are able to use cookies for session storage/retrieval.

For *non-embedded* apps, you can pass the cookies into:
 - `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, true)` for online (user) sessions or
 - `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)` for offline (store) sessions.
