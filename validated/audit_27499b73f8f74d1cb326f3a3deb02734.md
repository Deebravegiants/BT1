## Title
Unsigned-length underflow causes out-of-bounds slice panic when decoding HFT cross-chain calldata sender — (`modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
`HftModule::on_accept` slices the ABI-decoded `message.from` field with `from_bytes[from_bytes.len() - 20..]` without first validating that `from_bytes` is at least 20 bytes long. Because `.len()` returns an unsigned `usize`, an attacker-supplied `from` field shorter than 20 bytes makes `len() - 20` underflow, which either panics directly (debug/overflow-checked builds) or wraps to a huge index that panics on the subsequent slice bound check. This is the same bug class as CVE-2026-80741 (`drm_log_draw_kmsg_record`'s unchecked `s[len - 1]` on an unsigned length), just for a `len() - N` pattern instead of `len() - 1`.

### Finding Description
`Message::abi_decode(&body)` in `on_accept` produces a fully attacker-controlled `message` (the `body` comes from a relayed `PostRequest`, source contract only needs to be a registered `ContractToAsset` mapping — no other authentication of field contents): [1](#0-0) 

The `to` field is defensively length-checked before use: [2](#0-1) 

But `message.from`, when calldata is present without a signature, is *not* length-checked before the subtraction-based slice: [3](#0-2) 

`from_bytes.len() - 20` is computed on a `usize`. If the attacker encodes `message.from` as a `bytes` value with length 0–19 (which the ABI decoder happily accepts — there's no length assertion anywhere on `message.from` in this code path), the subtraction underflows to a value near `usize::MAX`, and `&from_bytes[huge_index..]` panics with an index-out-of-bounds/slice-range error. This exactly mirrors the reported kernel bug class: an unsigned length arithmetic that assumes a minimum size, subtracted without a guard, triggering an out-of-bounds access when the actual length is smaller than assumed.

Note the sibling code path in `on_timeout` (lines ~224-230) *does* correctly length-check `from_bytes` (32 or 20) before use, showing the `on_accept` "no signature" branch is the outlier missing this guard.

### Impact Explanation
`on_accept` is invoked by the ISMP router when delivering a relayed `PostRequest` targeting the HFT module — reachable by any relayer/user who can get a `PostRequest` dispatched to this app (an unprivileged message dispatcher/relayer path). A crafted message with a short `data.from` triggers a Rust panic during message execution. Panics originating inside runtime dispatch/apply-extrinsic execution in a Substrate/Polkadot-SDK based chain surface as unrecoverable execution traps, which can abort block execution or otherwise permanently disrupt processing of that message route — this is a "route unable to deliver messages" condition (denial of service against the HFT bridging pallet), satisfying the required impact bar.

### Likelihood Explanation
High. Triggering this only requires: (1) a source EVM contract already registered in `ContractToAsset` (a normal, expected bridging configuration, not an admin/attacker-privileged action), and (2) crafting a `PostRequest` whose ABI-encoded `Message.data` decodes to `SubstrateCalldata` with `signature = None` and a `from` field of length < 20 bytes and `source.is_evm() == true`. All of these fields are attacker-controlled ABI-encoded bytes with no validation prior to the vulnerable slice, making exploitation trivial for anyone able to relay a message to this pallet.

### Recommendation
Validate `from_bytes.len()` before slicing, mirroring the check already used for `message.to` and in the `on_timeout` handler — reject (return `HftError::InvalidRecipientLength`/an analogous error) when `from_bytes.len() != 20` on the EVM branch, and use `saturating_sub`/an explicit length check instead of raw subtraction anywhere length-derived indices are computed from untrusted ABI-decoded byte fields.

### Proof of Concept
1. Register a source EVM contract in `ContractToAsset` (standard onboarding, not a privileged bypass).
2. Craft a `PostRequest.body` that ABI-encodes an HFT `Message` where:
   - `to` is a valid 20 or 32-byte recipient (passes the existing check),
   - `data` ABI/SCALE-encodes a `SubstrateCalldata` with `signature = None` and any valid `runtime_call`,
   - `from` is set to fewer than 20 bytes (e.g., empty `bytes` or a single byte) — the ABI encoder places no minimum-length constraint on `bytes from`.
3. Relay this `PostRequest` to the HFT module’s `on_accept` handler (`source.is_evm() == true`).
4. Execution reaches `&from_bytes[from_bytes.len() - 20..]` with `from_bytes.len() < 20`; `len() - 20` underflows, causing a slice-index panic and aborting handling of the message. [3](#0-2)
