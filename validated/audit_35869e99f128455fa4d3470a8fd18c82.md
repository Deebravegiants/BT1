### Title
Webhook shop-domain is trusted for tenant attribution without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authorizes an incoming webhook solely by validating the HMAC over the **raw request body**, then unconditionally trusts the `shop-domain` header — which is **not** part of the signed material — to attribute the event to a tenant. This breaks the intended binding: `hmac == HMAC(secret, body)` says nothing about which shop the event belongs to, yet the header value is passed straight to the app's handler as the tenant identifier.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop` is read from an unsigned header: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature exclusively from `to_signable_string`: [3](#0-2) 

`Registry.process` treats a passing HMAC check as sufficient authorization, then forwards the unauthenticated `shop-domain` header directly to the app-supplied handler as the event's tenant identity: [4](#0-3) 

The equality the gem implicitly assumes is:

`shop_that_HMAC_authenticates == shop_used_for_tenant_attribution`

but in reality:

`shop_that_HMAC_authenticates` = "whoever produced this exact `raw_body` knew `api_secret_key`"
`shop_used_for_tenant_attribution` = `request.shop` (an arbitrary, attacker-choosable header)

Because the two are never checked against each other, anyone who can obtain one legitimately-signed `(raw_body, hmac)` pair for the shared app secret (e.g. from a genuine delivery to their own installed shop, captured via their own logging/proxy/ngrok tunnel, or any debug echo of a webhook) can replay that exact body+HMAC to the app's public webhook endpoint while substituting the `shopify-shop-domain` (or `x-shopify-shop-domain`) header for a **different, victim shop**. `HmacValidator.validate` still succeeds because it never looks at the header, and `Registry.process` calls the handler with `WebhookMetadata.new(..., shop: request.shop, ...)` attributing the (attacker-controlled) body content to the victim tenant.

### Impact Explanation
This crosses a tenant boundary: an app's webhook handler (which typically looks up/creates/updates per-shop records keyed by `shop`) can be made to process attacker-supplied event data under another merchant's shop identity — e.g. injecting spoofed `orders/create`, `app/uninstalled`, or other lifecycle events for a victim shop the attacker never installed the app on. Depending on what the host app's handler does with `WebhookMetadata#shop` and `#body`, this can result in cross-tenant data corruption, false uninstall/GDPR-erase triggers, or planting attacker-controlled content into a victim's records — matching the "cross-tenant access" class of Critical impact.

### Likelihood Explanation
Exploitation requires possession of one valid `(raw_body, hmac)` pair signed with the app's shared `client_secret` — the attacker does not need the secret itself, only a captured or leaked legitimate delivery (their own shop's webhook traffic, a debug/test-notification echo, request-bin/tunnel logging during development, etc.). Since a single Shopify app shares one `client_secret` across every installing merchant, any merchant who can observe one authentic webhook delivery for their own shop can forge tenant attribution for every other shop on the shared endpoint. This is a realistic scenario for self-hosted/open-source deployments and apps using tunneling tools during onboarding, though it does require the attacker to have captured a genuine delivery first, so likelihood is moderate rather than trivial.

### Recommendation
Bind the `shop` (and ideally `topic`, `webhook_id`) values into the material that is authenticated, or otherwise cryptographically tie the header-derived shop to the verified body — for example, require the handler/registry to cross-check `request.shop` against an expected/allow-listed shop for the session, or include the shop domain in the HMAC computation contract that Shopify already guarantees is consistent per delivery (validate that the shop the app expects for this webhook registration matches the header, not just that "some" HMAC over the body is valid). At minimum, document that `WebhookMetadata#shop` is unauthenticated and must not be trusted as an identity boundary by consuming apps without additional verification.

### Proof of Concept
1. Attacker installs the target app on Shop A (a shop they control) and lets Shopify deliver a genuine webhook, e.g. `orders/create`, to the app's shared endpoint. Attacker captures the exact `raw_body` and `X-Shopify-Hmac-Sha256` value for this delivery (via their own reverse proxy/tunnel/logging in front of their self-hosted instance, or a debug echo).
2. Attacker replays the identical HTTP request to the same webhook endpoint, keeping `raw_body` and `x-shopify-hmac-sha256` unchanged, but replaces `x-shopify-shop-domain` with `shop-b.myshopify.com` (a victim shop that never sent this event).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `HMAC(secret, raw_body)` — the header was never part of the signed contents.
4. The registered handler receives `WebhookMetadata.new(topic: ..., shop: "shop-b.myshopify.com", body: <attacker's Shop A order data>, ...)`, and any handler logic keyed on `shop` now operates on Shop B's tenant using attacker-supplied content.
