### Title
Webhook `shop` identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`, `topic`, `api_version`, `webhook_id`) entirely from unauthenticated HTTP headers, while the HMAC signature that `Utils::HmacValidator` verifies covers only the raw request body. Any actor who can obtain one genuinely-signed webhook body (e.g. by triggering a webhook for their own, legitimately installed shop) can replay that exact body against the host app's webhook endpoint with a forged `shop-domain` header pointing at a different, victim shop. The signature still validates because the shop identity was never part of the signed material, so the host application's handler executes trusting an attacker-controlled `shop` value.

### Finding Description
`Utils::HmacValidator.validate` computes the signature strictly from `verifiable_query.to_signable_string` and compares it against the received HMAC: [1](#0-0) 

For webhooks, `to_signable_string` is defined to be only the raw body: [2](#0-1) 

Meanwhile, `shop`, `topic`, `api_version`, and `webhook_id` are all read directly from HTTP headers, none of which participate in the signature computation: [3](#0-2) 

`Registry.process` only checks `Utils::HmacValidator.validate(request)` and then forwards `request.shop` (and the other header-derived fields) straight to the app's handler as authoritative tenant metadata: [4](#0-3) 

Because the `api_secret_key` used to sign webhooks is the same for every shop that has installed a given app, a merchant is able to generate a validly-signed webhook payload for their own shop, then resend that identical body with an altered `shopify-shop-domain` (or `x-shopify-shop-domain`) header naming a different shop. The HMAC comparison in `validate_signature` still succeeds because the header content is never part of `signable_string`: [5](#0-4) 

The broken identity binding is: `shop asserted in header` should equal `shop that produced the HMAC-signed body`, but the gem only proves `body == HMAC(body)`, never `shop == HMAC-bound-shop`.

### Impact Explanation
Any application built on this gem that uses `WebhookMetadata#shop` (as passed by `Registry.process`) to select which merchant's records to read, update, or create will act on attacker-chosen shop identity. This is a cross-tenant vulnerability: a shop installing the app can forge webhook traffic that the host app attributes to a completely different, unrelated shop, corrupting or exfiltrating another tenant's application-side data. This matches the Critical "cross-tenant access" impact criterion.

### Likelihood Explanation
The attacker only needs to be a normal, unprivileged app user (any merchant who has installed the app, or anyone who can otherwise obtain a legitimately-signed webhook body for one shop, e.g. via their own store's public events) and control of an HTTP client to POST to the app's public webhook endpoint. No access token, no `api_secret_key`, and no special privilege on the victim shop is required, only the ability to modify a header on a replayed request.

### Recommendation
Include the shop domain (and ideally topic/webhook id) inside the HMAC-signed material, or otherwise cryptographically bind the header-supplied `shop` to the authenticated Shopify webhook delivery (e.g., derive/validate `shop` from a mechanism tied to the signature, or require the host app to cross-check `shop` against an independently verified installation record before trusting it). At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must be corroborated against known installed shops before being used for tenant selection.

### Proof of Concept
1. App installs on `attacker-shop.myshopify.com`; attacker triggers any subscribed webhook topic (e.g. `orders/create`) for their own shop, capturing the raw POST body and its `x-shopify-hmac-sha256` header from Shopify.
2. Attacker resends the exact same body and HMAC header to the app's webhook endpoint, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the signature over `to_signable_string` (the raw body only) and matches it against the (unmodified) valid HMAC header — validation passes. [6](#0-5) 
4. The app's handler receives `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: <attacker's data>, ...)` and processes it as if it originated from the victim shop.
