### Title
Hardcoded `block.timestamp` Deadline in `placeOrder()`'s Fee Swap Offers No MEV/Delay Protection - (File: `evm/src/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2.placeOrder()` is a public, unprivileged, payable entry point that lets any user create an intent order and, when paying solver fees in native token, swaps that native value into the protocol fee token via Uniswap V2's `swapETHForExactTokens`. The deadline parameter passed to the router is hardcoded to `block.timestamp`, which is evaluated at execution time and therefore never actually bounds anything — exactly the flaw the external report describes for `EnigmaZapper._depositToEnigma()`.

The `deadline` argument to `IUniswapV2Router02.swapETHForExactTokens` is `block.timestamp`, computed inside the same transaction that executes the swap. A deadline is meant to bound how long a *pending* transaction can sit before its intended execution context (price, in this case) is considered stale. Because this value is derived from the timestamp of the block that ultimately includes the transaction — not from the timestamp at which the user signed/submitted it — the check can never fail: whenever the transaction is mined, `deadline == block.timestamp` trivially holds. A validator/block-builder (or MEV searcher colluding with one) can therefore hold the transaction in the mempool or a private order-flow channel indefinitely, manipulate the WETH/feeToken pool price around it (sandwich style), and only then include it — the deadline offers zero protection against this delay, unlike a genuine user-supplied deadline that would expire.

There is no `deadline` field on the `Order` struct or any parameter on `placeOrder()` that lets the caller bound execution time for this swap; `order.deadline` exists but is used only for order-fill expiry `evm/tests/foundry/IntentGatewayV2Test.sol:297`, not passed into the fee swap.

### Impact Explanation
`swapETHForExactTokens` requests an *exact output* amount of fee tokens (`order.fees`) and returns `amounts[0]` as the ETH actually spent, refunding the remainder (`msgValue -= amounts[0]`, then refunded via `_sendValue`). If the pool price is manipulated between submission and inclusion, `amounts[0]` (ETH consumed) rises, directly reducing the ETH refunded to the unprivileged order placer — a concrete fund loss for the caller, proportional to how long/how much the price is moved during the delay. This is a direct value-extraction vector reachable by any user who places an order with `order.fees > 0` and pays in native token, matching the Medium-severity bug class in the source report (hardcoded/self-referential deadline offering no protection).

### Likelihood Explanation
Every `placeOrder()` call with non-zero `order.fees` paid in native token triggers this code path, so the surface is broad and requires no special conditions. Exploitation requires a validator/builder or colluding searcher able to delay inclusion and manipulate the WETH/feeToken pool — a realistic MEV scenario, consistent with the risk rating (Medium) assigned to the analogous finding in the external report.

### Recommendation
Add a user-supplied deadline parameter (e.g., to the `Order` struct or as a separate `placeOrder` argument) and pass it through to `swapETHForExactTokens` instead of `block.timestamp`, reverting if the deadline has already passed by the time execution begins. This mirrors the report's recommendation of making `deadline` a caller-provided, validated field rather than a self-satisfying constant.

### Proof of Concept
1. User calls `placeOrder()` with `order.fees > 0`, paying fee amount in native ETH (`msg.value` covers `order.inputs` and leaves `msgValue` for the fee swap).
2. A validator/builder observing the pending transaction delays its inclusion and, via a sandwich or other price-moving trade, shifts the WETH/feeToken pool price unfavorably.
3. The transaction is finally included; `swapETHForExactTokens{value: msgValue}(order.fees, path, address(this), block.timestamp)` executes with the manipulated price — the `deadline` check trivially passes because it equals the current block's timestamp.
4. `amounts[0]` (ETH spent) is higher than it would have been at fair/expected price; `msgValue -= amounts[0]` leaves less ETH to refund to the user in `_sendValue(msg.sender, msgValue)`, so the order placer receives back less ETH than expected for the same fee-token amount, realizing a loss.
