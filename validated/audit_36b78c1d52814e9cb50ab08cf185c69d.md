### Title
Webhook `shop` field is trusted for tenant identity but is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates only the HTTP body against the `X-Shopify-Hmac-Sha256` header, but the `shop` value handed to app handlers is read directly from the unauthenticated `X-Shopify-Shop-Domain` header, which is not part of the signed bytes. Because the app's `api_secret_key` is shared across every shop that installs the app (it is the app's OAuth client secret, not a per-shop secret), any merchant who has installed the app can legitimately receive a validly HMAC-signed webhook for their own store, then replay that exact `(raw_body, hmac)` pair to the app's webhook endpoint while substituting the `shop` header for a victim shop domain. The signature still validates (it only covers the body), so the handler is invoked with `WebhookMetadata.shop` equal to the attacker-chosen victim shop.

### Finding Description
`Request#to_signable_string` returns only the raw body: [1](#0-0) 

while `shop` is read straight from a header that is never part of the signed payload: [2](#0-1) 

`Registry.process` validates the request purely with `HmacValidator.validate(request)` and then forwards `request.shop` unmodified to the app's handler as trusted tenant identity: [3](#0-2) 

`HmacValidator.validate_signature` only ever hashes `verifiable_query.to_signable_string`, which for a webhook `Request` is the body alone — the shop header is completely excluded from the equality the HMAC is supposed to enforce: [4](#0-3) 

The identity binding the gem should be enforcing is `shop_bound_by_hmac == shop_used_by_handler`, but the actual binding is `body_bound_by_hmac == body`, with `shop` supplied out-of-band and unauthenticated. The gem's own documentation reinforces the false sense of security by stating that `Registry.process` "will verify the request did indeed come from Shopify," without qualifying that only the body — not the shop attribution — is verified: [5](#0-4) 

Since the same `api_secret_key` signs webhooks for every shop that installs the app, a merchant who is an unprivileged tenant relative to other merchants can capture a webhook payload legitimately delivered to their own store (a valid `(raw_body, hmac)` pair) and resend it to the app's public webhook endpoint with the `X-Shopify-Shop-Domain` header changed to a victim's `myshopify.com` domain. `HmacValidator.validate` still returns `true` because it only recomputes the HMAC over `raw_body`, and `Registry.process` passes the forged `shop` straight into `WebhookMetadata` for the handler to act on.

### Impact Explanation
Any app built on this gem that scopes data storage, billing, entitlement, or other tenant-sensitive logic by `WebhookMetadata#shop` (as the documented handler pattern encourages — see the example handler storing `shop_domain: data.shop`) can have attacker-controlled shop attribution injected under a passing signature check. This is a cross-tenant identity-binding bypass: data or events genuinely originating from the attacker's own shop can be attributed to an arbitrary victim shop known only by its `myshopify.com` domain (a publicly guessable/enumerable value), letting an unprivileged merchant pollute or manipulate another merchant's webhook-driven state.

### Likelihood Explanation
Any merchant that installs the app already receives real webhooks with valid signatures for their own shop, so obtaining a valid `(body, hmac)` pair requires no privilege beyond normal app installation. Replaying it against the app's public webhook route with a modified `Shop-Domain` header requires only basic HTTP tooling, no secret material, and no interaction with Shopify's own systems in the loop other than an existing install.

### Recommendation
`Request#to_signable_string` (or a validation step in `Registry.process`) should bind the `shop` header into the material that establishes trust — e.g., cross-check `request.shop` against the shop of the session/store the webhook registration was made for, or otherwise reject processing unless the shop is one this app has verified via the OAuth flow, instead of trusting the header at face value once `HmacValidator.validate` passes.

### Proof of Concept
1. App merchant A installs the target app; Shopify delivers a legitimate webhook to the app's endpoint with body `B`, header `X-Shopify-Shop-Domain: shop-a.myshopify.com`, and `X-Shopify-Hmac-Sha256: H` (computed over `B` with the shared `api_secret_key`).
2. Merchant A (attacker) intercepts/logs this request from their own server logs.
3. Merchant A resends the same request to the app's webhook endpoint, keeping body `B` and header `X-Shopify-Hmac-Sha256: H` identical, but changing `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over the (unchanged) body `B` and matches `H`, returning `true`.
5. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the app to act on attacker-controlled data as if it belonged to `victim-shop`.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

        end
