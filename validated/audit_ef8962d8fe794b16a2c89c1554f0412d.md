### Title
Webhook `shop` and `topic` identity fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then unconditionally trusts the `shop`, `topic`, `webhook_id`, and `api_version` values taken from unauthenticated HTTP headers when dispatching to the app's handler. Because the identity fields used to route/attribute the webhook are not part of the signed payload, any party who can obtain one validly-signed webhook body (e.g. a merchant who has installed the app and receives their own legitimate webhooks) can replay that exact body with a forged `x-shopify-shop-domain` header to make the app process it as if it came from a different shop, while the signature still validates.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`, whose `to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors are read directly from HTTP headers with no cryptographic binding to the body or to each other: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC solely over `verifiable_query.to_signable_string`, i.e. the raw body: [3](#0-2) 

`Registry.process` treats a passing HMAC check as authentication for the entire request, then forwards the unauthenticated `request.shop` and `request.topic` fields into `WebhookMetadata`, which is the identity the host application's handler uses to attribute/act on the event: [4](#0-3) 

This is precisely the report's bug class: a field (`shop`) that is *acted on* (used to identify the tenant in `WebhookMetadata`) but *not covered by the HMAC* used to authenticate the request. The equality the code implicitly assumes — `hmac_verified(raw_body) ⇒ shop_header_authentic` — does not hold, because `raw_body` and `shop_header` are independent inputs and only the former is signed.

### Impact Explanation
Because Shopify apps typically share a single `client_secret`/`api_secret_key` across all installed shops (multi-tenant apps), any merchant who installs the app can receive a legitimately-signed webhook for their own shop and then resubmit the identical raw body to the app's webhook endpoint with the `x-shopify-shop-domain` (and optionally `x-shopify-topic`) header changed to a victim shop's domain. `Utils::HmacValidator.validate` will still return `true` (the body/HMAC pair is unchanged and valid), and `Registry.process` will dispatch to the handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain. If the host application uses `WebhookMetadata#shop` to look up sessions, update data, or otherwise scope actions per tenant (the documented and expected usage pattern), this allows cross-tenant data manipulation/injection — an attacker acting as shop A can make the app believe an event originated from shop B.

### Likelihood Explanation
Exploitation only requires the attacker to install the target app on their own shop (a standard, unprivileged action for any merchant/app-store user) to obtain one valid `(raw_body, hmac)` pair, then send a crafted HTTP POST to the app's public webhook endpoint with a modified shop header — no access token, `client_secret`, or privileged account is needed.

### Recommendation
Bind the tenant-identifying headers into the signed material, e.g. include `shop`, `topic`, and `webhook_id` in `to_signable_string` (or independently verify that the `shop` header matches a shop for which the app has an active, previously-established session/registration) before constructing `WebhookMetadata` in `Registry.process`.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`, triggering a real webhook (e.g. `orders/create`) with a valid `x-shopify-hmac-sha256` for the raw body.
2. Attacker captures the raw POST body and its valid HMAC header.
3. Attacker resends the exact same body/HMAC to the app's public webhook route, replacing `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` returns `true` because it only checks the (unchanged) body against the (unchanged) HMAC.
5. `Registry.process` in `lib/shopify_api/webhooks/registry.rb` builds `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` and invokes the app's handler, which now processes attacker-controlled order data as if it belongs to the victim shop.
