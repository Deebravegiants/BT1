### Title
Balance equation excludes pre/post-transact hook calls, allowing unauthorised value movement from Hinkal - (File: `contracts/Hinkal.sol`)

### Summary
`Hinkal.transact()` enforces a "balance equation" invariant that ties any observed change in the contract's ERC20/ETH balance to the declared off-chain/on-chain UTXO deltas, analogous to the Ajna `LUP >= HTP` invariant that must hold after every deposit-affecting operation. However, the snapshot window used for this check (`oldBalances` / `newBalances`) does not encompass the `preHookContract` and `postHookContract` calls, which are executed strictly before and after that window, respectively.

### Finding Description
In `transact()`:
```solidity
if (circomData.hookData.preHookContract != address(0)) {
    IPreTransactHook transactHook = IPreTransactHook(circomData.hookData.preHookContract);
    transactHook.preTransact(circomData);
}

uint256[] memory oldBalances = getBalancesForArray(circomData.erc20TokenAddresses);
...
uint256[] memory newBalances = getBalancesForArray(circomData.erc20TokenAddresses);
...
// balance equation checks using oldBalances/newBalances
...
if (circomData.hookData.postHookContract != address(0)) {
    ITransactHook transactHook = ITransactHook(circomData.hookData.postHookContract);
    transactHook.afterTransact(circomData);
}
``` [1](#0-0) 

`circomData.hookData.preHookContract` and `postHookContract` are attacker-controlled fields inside `CircomData`, supplied directly by the transaction sender/prover and are not restricted to a registered/whitelisted set (unlike `externalActionMap`, which is checked in `_externalTransact`) [2](#0-1) . Their values are only bound into the proof via `calldataHash`/`getHashedCalldata2` [3](#0-2) , meaning the *addresses* are attested, but nothing constrains what code they execute or what side effects they can have on Hinkal's held balances.

Because `preTransact` runs before `oldBalances` is captured, and `afterTransact` runs after `newBalances` is captured and the balance-equation `require` has already passed, any balance change induced through these hook calls (e.g., the hook causing Hinkal to call `approve`/`transferFrom`, or itself being a malicious token contract that Hinkal already holds an allowance for from a prior transaction) is invisible to the invariant check that is supposed to bind all balance changes to the declared UTXO deltas. This mirrors the reported bug class: a value-moving action (hook execution) that is not counted in the equality the protocol relies on (`balanceDif == amountChanges + utxoAmount`).

### Impact Explanation
If a hook can trigger the movement of Hinkal-held ERC20/ETH balances outside the checked window, funds unrelated to (or in excess of) the declared circuit-verified UTXO changes could leave the contract without being detected by the balance equation, i.e., theft of protocol-held (shielded) funds — matching "temporary/permanent freezing of user funds" or "theft" impact tiers of scope.

### Likelihood Explanation
Exploitation requires the attacker to have caused Hinkal to previously grant token allowances/approvals to a contract they control (there is no explicit mechanism in the reviewed contracts preventing this), or requires reentrancy/callback abuse inside `preTransact`/`afterTransact`. `nonReentrant` on `transact()` limits reentrant calls back into `Hinkal.transact()` itself, which reduces — but does not eliminate — the practical exploitation surface, since the hook could still interact with other approved spenders or tokens. This uncertainty (whether any code path grants prior approvals to a user-supplied hook address) could not be fully verified from the indexed contracts alone.

### Recommendation
Move the `oldBalances` snapshot to before the `preHookContract` call and the balance-equation `require` (or an equivalent check) to after the `postHookContract` call, so that any balance change induced by hook execution is captured by the same equality check that governs all other value movement in `transact()`.

### Proof of Concept
Conceptual sequence (concrete exploitation depends on finding/creating a standing token allowance from Hinkal to an attacker-controlled hook, which could not be confirmed from the reviewed files):
1. Attacker deploys a contract implementing `IPreTransactHook`/`ITransactHook`.
2. Attacker submits `transact()` with `circomData.hookData.preHookContract` (or `postHookContract`) set to this contract, along with a valid proof for a self-consistent (net-zero) UTXO operation.
3. Inside `preTransact` (before `oldBalances` snapshot) or `afterTransact` (after the balance check passes), the hook contract triggers an ERC20 `transferFrom(Hinkal, attacker, amount)` using any allowance Hinkal has previously granted, or otherwise manipulates Hinkal's balance.
4. The balance-equation check in `transact()` never observes this balance change, so the transaction succeeds despite the undeclared movement of funds. [4](#0-3)
