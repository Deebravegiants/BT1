### Title
Unwrapped fee-token transfers in `EvmHost.dispatchIncoming(GetResponse)` and `dispatchTimeOut` let a single "weird" (blacklist/pausable) fee-token recipient permanently DoS an entire batched relayer delivery - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost` collects and pays out its ISMP relayer fees/refunds in an admin-configured `feeToken()`, which is typically a stablecoin and could be an upgradeable, blacklist-capable token (e.g. USDT-style). Several of the host's payout paths — the relayer reward on `dispatchIncoming(GetResponse)` and the payer refund on `dispatchTimeOut` for both GET and POST timeouts — call `IERC20(feeToken()).safeTransfer(...)` directly, with no try/catch or low-level `.call` success check. These functions are invoked in a loop from `HandlerV2` batch-processing entrypoints (`handleGetResponses`, `handlePostRequestTimeouts`, `handleGetRequestTimeouts`), so a single blacklisted/reverting recipient inside a batch reverts the whole transaction and blocks delivery of every other unrelated message batched alongside it.

### Finding Description
`EvmHost.dispatchIncoming(GetResponse memory response, address relayer)` (`evm/src/core/EvmHost.sol` lines 824-847) calls the module's `onGetResponse` via a low-level `.call` with an explicit success check — exactly like `dispatchIncoming(PostRequest)` — but then, after success, unconditionally executes: [1](#0-0) 
```
uint256 fee = _requestCommitments[commitment].fee;
if (fee != 0) {
    IERC20(feeToken()).safeTransfer(relayer, fee);
}
```
This `safeTransfer` is not shielded. If `feeToken()` reverts for the `relayer` address (blacklist, pause, upgraded logic — the exact "weird ERC20" class from the referenced report), this whole `dispatchIncoming` call reverts.

The same unguarded pattern exists in `dispatchTimeOut` for both request kinds: [2](#0-1) [3](#0-2) 
Both refund the original `payer`/`sender` (a value fully controlled by whoever dispatched the original request, e.g. `DispatchPost.payer`/`DispatchGet.payer`) via `IERC20(feeToken()).safeTransfer(meta.sender, meta.fee)`.

Crucially, `EvmHost.dispatchIncoming(PostRequest)` explicitly avoids this DoS pattern for the module callback: [4](#0-3) 
```
(bool success,) = address(destination)
    .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));
if (!success) {
    delete _requestReceipts[commitment];
    return;   // "instead of reverting the entire batch, early return here."
}
```
The comment "instead of reverting the entire batch, early return here" shows the design intent is that one bad message must not block the batch — but this protection is missing for the fee/refund transfers.

All three vulnerable functions are driven from `HandlerV2` batch entrypoints that call them inside a `for` loop over the entire submitted message set: [5](#0-4) [6](#0-5) [7](#0-6) 
Because these are `external` calls (`host.dispatchTimeOut(...)`, `host.dispatchIncoming(...)`) with no try/catch at the `HandlerV2` layer either, a revert anywhere in the loop propagates and aborts the entire batch transaction, including all the other unrelated, otherwise-deliverable GET responses / POST timeouts / GET timeouts bundled in the same call for gas efficiency.

### Impact Explanation
This is a route-availability/DoS issue, not merely an isolated stuck-claim for one user (which would be Low, per the rules). Relayers commonly batch many pending GET responses or timeouts together in a single MMR-proof transaction to amortize gas. If any single one of those batched items has a `payer`/`relayer` address that reverts on `feeToken` transfer (blacklisted, sanctioned, or the token temporarily paused), the entire batch reverts, and none of the other legitimate messages in that batch get delivered until the relayer identifies and manually excludes the poisoned item. This can be triggered repeatedly and indefinitely (the poisoned commitment is never consumed, since it reverts before any state change), causing a persistent, targeted denial of message delivery for whichever relayer batching strategy happens to include the tainted commitment — i.e., "a route unable to deliver messages," matching the accepted impact bar.

### Likelihood Explanation
Reachability only requires:
1. `feeToken()` (admin-configured, and documented as "usually a stablecoin") being an upgradeable/blacklist-capable ERC20 such as USDT.
2. Any user dispatching a POST/GET request with `payer` set to an address that later becomes blacklisted (self-inflicted or externally sanctioned) — this is fully attacker-controlled via `DispatchPost.payer` / `DispatchGet.payer` at dispatch time, requiring no privilege beyond a normal dispatch call, or simply a relayer address becoming non-compliant.
3. That request eventually timing out or receiving a response, and a relayer batching its delivery with other pending messages (the default operational pattern for gas efficiency).

No governance or privileged role is needed on the attacker's side; only an unprivileged message dispatcher choosing a "bad" payer and waiting for the natural batching behavior of relayers.

### Recommendation
Wrap the fee reward/refund transfers in `dispatchIncoming(GetResponse)` and both `dispatchTimeOut` overloads with a low-level `.call` and success check (mirroring the pattern already used for `onAccept`/`onGetResponse` callbacks), so a failing transfer degrades gracefully (e.g., leaves the fee claimable/retryable) instead of reverting the whole batch. Alternatively, isolate each per-leaf fee transfer in `HandlerV2`'s loops with try/catch so a single poisoned commitment cannot block sibling messages in the same proof batch.

### Proof of Concept
1. Assume `feeToken()` is configured to a blacklist-capable token (USDT-style) or one that can later be paused/upgraded to revert transfers to certain addresses.
2. Attacker (or any user) dispatches a `DispatchGet` (or `DispatchPost`) with `fee > 0` and `payer` set to an address `X` that they know/expect will be blacklisted by the fee token's controller (or which they get blacklisted themselves after dispatch).
3. Request times out (or a GET response is produced) without being delivered before `X` becomes non-transferable.
4. A relayer bundles the timeout/response for this commitment together with N other unrelated pending messages into one `handleGetResponses` / `handlePostRequestTimeouts` / `handleGetRequestTimeouts` call, per `evm/src/core/HandlerV2.sol` lines 217-247 / 254-286 / 293-321.
5. Inside the loop, `host.dispatchTimeOut(...)` or `host.dispatchIncoming(response, relayer)` reaches the `IERC20(feeToken()).safeTransfer(X, fee)` call in `evm/src/core/EvmHost.sol` lines 841-846 / 872-876 / 901-905, which reverts because `X` is blacklisted.
6. The revert propagates all the way up through `HandlerV2`, reverting the entire batch transaction — none of the other N legitimate messages in the batch get delivered, and the relayer must retry after manually excluding the poisoned commitment, repeating step 4 indefinitely if it keeps re-batching it.
