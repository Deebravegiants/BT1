### Title
Missing enforcement of user-signed slippage floor lets a sandwich attack drain LI.FI swap output - (File: `contracts/external-actions/swaps/ExternalActionSwap.sol`)

### Summary
`ExternalActionSwap.swap()` is the only place a shielded-swap output amount is validated before being credited to the user's new UTXO. It checks only that a slippage value was *provided*, never that the actual swap result *satisfies* it, so a sandwiching attacker can push the AMM/router price against the user and the contract will still accept and shield whatever (much smaller) amount comes back.

### Finding Description
`swap()` reads `circomData.slippageValues[1]` and requires only: [1](#0-0) 
i.e. `slippageValues[1] != 0`. It never compares the value that is actually returned by the router, `swappedAmount`, against `slippageValues[1]` anywhere in the function: [2](#0-1) 
`swappedAmount` is produced by `LifiExternalAction.callRouter`, which just diffs the recipient's balance before/after an arbitrary external call built off-chain (`externalActionMetadata`) to the LI.FI router: [3](#0-2) 
The `amountToSendToHinkal = swappedAmount - totalFee` value becomes the amount of the freshly minted shielded UTXO that is committed on-chain: [4](#0-3) 

`slippageValues` is indeed folded into `calldataHash`/`signedMessageHash` (so the prover/signer's intended floor is authenticated as part of the circuit's public input vector) via `CircomDataBuilder.getHashedCalldata1` and `getSignedMessageHash`: [5](#0-4) [6](#0-5) 

However, the fact that the value is authenticated does not mean it is *enforced*: the circuit only certifies "the user signed off on this specific `slippageValues[1]` number", while the on-chain swap logic never actually checks the post-swap balance against it. The equality that should hold — "amount credited to user's shielded UTXO ≥ user-signed minimum output" — is never checked. This mirrors the Sushi/Badger/DIGG bug class: an AMM-facing operation (LP burn → convert in the Sushi case; router swap here) executes without any effective floor/bridge validation, letting a sandwiching MEV bot manipulate the intermediate price so the value that ultimately lands is far below what the honest actor intended, and this manipulated value is then accepted into the protocol's internal accounting/balance state (here: minted directly into a new shielded UTXO) as if it were correct.

Any unprivileged EOA (an MEV searcher) that observes a pending Hinkal swap transaction (`LifiExternalAction`/router call) in the mempool can front-run it with a large trade in the same pool, let the victim's swap execute at a degraded price with `swappedAmount` far below what the user actually intended (but still nonzero, so the `!= 0` check passes), and back-run to restore the price and capture the difference — with no reliance on any Hinkal-specific privileged role.

### Impact Explanation
This is direct theft of in-flight user funds during a shielded operation: the victim's real economic loss is captured by the sandwiching bot, while Hinkal mints a shielded UTXO for the diminished amount as if the transaction succeeded normally — matching the "Critical: direct theft of shielded or in-flight user funds" category. The nonzero-slippage check gives a false sense of protection (a `slippageValues[1]` field exists and is even authenticated via the circuit's calldata hash), but it does not stop the attack because it is never compared to the executed output.

### Likelihood Explanation
High: any pending swap transaction through `LifiExternalAction`/`ExternalActionSwap` is visible in the mempool (or via the relay flow) and is a completely standard, well-known MEV sandwich pattern against DEX/aggregator routers; no elevated privileges, admin keys, or protocol-specific bugs are needed — just standard front-running/back-running tooling.

### Recommendation
In `ExternalActionSwap.swap()`, replace the "value is set" check with an actual floor enforcement: `require(swappedAmount >= uint256(circomData.slippageValues[1]), "swap output below slippage floor");` performed after `callRouter` returns and before crediting `amountToSendToHinkal` to the new UTXO/committing it to Hinkal.

### Proof of Concept
1. Attacker monitors mempool for a pending Hinkal shielded swap that calls `ExternalActionSwap.swap()` → `LifiExternalAction.callRouter()` against a LI.FI-routed liquidity pool.
2. Attacker front-runs with a large swap in the same pool to move the price against the victim's trade direction.
3. Victim's swap executes; `swappedAmount` (diff of `outputToken` balance before/after the router call) is far lower than a fair-market amount, but is still nonzero, so `require(circomData.slippageValues[1] != 0, ...)` at [1](#0-0)  passes without ever comparing against the actual `swappedAmount`.
4. Attacker back-runs to restore the pool price, pocketing the spread; Hinkal mints a new shielded UTXO for the victim using the degraded `amountToSendToHinkal` at [7](#0-6) , permanently locking in the victim's loss inside the shielded pool.

    function callRouter(
        address inputToken,
        uint256 inputAmount,
        address outputToken,
        bytes calldata externalActionMetadata
    ) internal override returns (uint256 swappedAmount) {
        uint256 balanceBefore = getERC20OrETHBalance(outputToken);

        if (inputToken == address(0)) {
            (bool success, ) = router.call{value: inputAmount}(
                externalActionMetadata
            );
            require(success, "LI.FI swap failed: native coin");
        } else {
            approveUnlimited(inputToken, router);
            (bool success, ) = router.call(externalActionMetadata);
            require(success, "LI.FI swap failed: erc-20 token");
        }

        swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore;
    }
