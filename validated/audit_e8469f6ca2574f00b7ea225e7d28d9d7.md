Confirmed root cause: `on_timeout` in `modules/pallets/hyper-fungible-token/src/module.rs` looks up `ContractToAsset::<T>::get(dest, &to)` to determine which local asset to refund, exactly the same lookup `update_token`'s `remove_chains` path deletes.

### Title
`update_token`'s `remove_chains` can strand escrowed/burned funds and break in-flight message delivery for `pallet-hyper-fungible-token` - (File: `modules/pallets/hyper-fungible-token/src/lib.rs`)

### Summary
`update_token` allows removing a chain's configuration (`TokenContracts`, `ContractToAsset`, `Precisions`) for a registered asset with no check for outstanding cross-chain transfers still in flight to/from that chain, mirroring the reported `clearTokenConfig` bug class: configuration can be cleared while the token is still "in use" by pending operations.

### Finding Description
`update_token` is defined at [1](#0-0)  and unconditionally removes the `ContractToAsset` reverse mapping and `TokenContracts`/`Precisions` entries for any `chain` listed in `update.remove_chains`, with no check that pending `send` requests to that chain (already dispatched, awaiting delivery or timeout via `pallet-ismp`) still reference the removed contract/precision data.

That reverse mapping and precision data are required later by both the receive path and the timeout/refund path:
- `on_accept` authenticates and decodes an inbound message by looking up `ContractToAsset::<T>::get(source, &from)` and `Precisions::<T>::get(local_asset_id, source)` [2](#0-1) .
- `on_timeout` — the refund path that returns escrowed/burned funds to the original sender when a dispatched `send` request times out — performs the identical lookup: `ContractToAsset::<T>::get(dest, &to)` and `Precisions::<T>::get(local_asset_id, dest)` [3](#0-2) .

If a user's `send` extrinsic (which escrows or burns the local asset, see [4](#0-3) ) is dispatched, and before the message is delivered or times out `update_token` removes that destination chain's configuration, then:
- Any inbound `on_accept`/`on_timeout` callback for that in-flight request will fail with `UnknownSourceContract` / `UnknownContractOnTimeout` since the reverse-lookup storage has been deleted.
- On timeout, `on_timeout` returning an `Err` means the ISMP relayer's timeout-message delivery reverts, so the escrowed/burned funds can never be refunded through the normal path — the route becomes permanently unable to deliver/process the message, matching the "route unable to deliver messages" and "permanent freezing of funds" impact categories.

This precisely matches the reported bug class: configuration can be cleared without verifying no active/pending operations reference it, and there is no grace period recommended in the original report.

### Impact Explanation
Funds already escrowed/burned by a `send` call for a since-removed chain configuration can become permanently unrecoverable — the `on_timeout` refund path depends on the exact `ContractToAsset`/`Precisions` entries that `update_token`'s `remove_chains` deletes. Since a normal user has no way to re-add the deleted mapping (only `T::CreateOrigin` can), this results in a stuck/frozen ISMP request whose timeout callback will always fail, and users lose access to their transferred funds.

### Likelihood Explanation
This does not require a malicious actor — any legitimate configuration update (e.g., decommissioning or repointing a chain) that overlaps with in-flight transfers (which can remain outstanding for the full request timeout window) triggers the issue. The `send` extrinsic is reachable by any signed user (token bridger), and the race window between dispatch and the update is entirely plausible in production operational flows.

### Recommendation
Before removing a chain from `TokenContracts`/`ContractToAsset`/`Precisions` in `update_token`, verify there are no outstanding dispatched (non-timed-out, non-delivered) requests targeting that `(asset_id, chain)` pair, or retain the old `ContractToAsset`/`Precisions` entries until all pending requests to that chain have resolved (delivered or timed out), e.g. by keeping historical mappings keyed by commitment/nonce rather than overwriting the live per-chain state immediately.

### Proof of Concept
1. Register a token with chain `Evm(X)` via `register_token`.
2. User calls `send` with destination `Evm(X)`; the pallet escrows/burns the asset and dispatches a `DispatchPost` via `pallet-ismp` (per [5](#0-4) ), leaving the request pending.
3. Before the request is delivered/times out, an admin/governance call to `update_token` includes `Evm(X)` in `remove_chains`, removing `TokenContracts`, `ContractToAsset`, and `Precisions` for that pair (as tested in [6](#0-5) , which only asserts storage removal, not in-flight-safety).
4. When the request eventually times out and `pallet-ismp` invokes `on_timeout`, the lookup `ContractToAsset::<T>::get(dest, &to)` returns `None`, causing `Err(HftError::UnknownContractOnTimeout)` [7](#0-6) , so the refund never executes and the escrowed/burned funds remain stuck.
