This confirms that only bids from EIP-7702-delegated `SolverAccount`s are counted (`isVerifiedSolverBid`, delegation check against `SOLVER_ACCOUNT_ADDRESSES`) — restricting the analog to a permissioned solver role, but the balance measurement itself remains gameable by *any* verified solver via transient token acquisition (self-transfer/flash-loan), which is the actual root cause parallel to the report's `balanceOf`-based pricing risk.

### Title
Phantom order price snapshots are derived from a live, unbonded `balanceOf` read that a solver can transiently inflate to set the published rate - ([File: sdk/packages/sdk/src/protocols/intents/phantom-aggregation.ts])

### Summary
`aggregatePhantomBids` prices a phantom order's legs by a **liquidity-weighted median**, where a bid's weight is a live ERC-20 `balanceOf` read of the solver's wallet on the destination chain, taken at snapshot time. Because `weightedMedian` is a selection rather than a blend, any single solver whose *measured* weight exceeds 50% of the leg's total weight sets the published price to its own quote verbatim.

### Finding Description
`getBalance(destUrl, chain, outputToken, solver)` performs a live `balanceOf`-style query against the destination chain at the moment `PhantomBidWindowExhausted` fires and the indexer runs `aggregatePhantomBids`. [1](#0-0) 
This balance directly becomes the bid's `weight` fed into `weightedMedian`: [2](#0-1) 
`weightedMedian` is documented and tested as a **selection**: whichever quote's cumulative weight crosses half the total weight is returned verbatim, so a solver controlling >50% of the leg's weight publishes its own exact price. [3](#0-2) [4](#0-3) 

Only bids from wallets EIP-7702-delegated to a chain's configured `SolverAccount` are counted (`isVerifiedSolverBid`), so this is not fully permissionless — but nothing constrains the balance a *verified* solver's own wallet can transiently hold at the moment the aggregation RPC call executes. Because the balance read is a plain state read (not a locked stake, deposit, or time-weighted average), a solver can move (self-transfer, or borrow via a flash loan within the same block window/tx before the RPC snapshot, since the read has no block-height binding to the bid itself) a large quantity of the leg's output token into its wallet immediately before/around the aggregation window, inflate its weight past the >50% threshold, and dictate `medianPrice` — the analog to `balanceOf`-derived AMM pricing in the source report, where a balance read used as a pricing input can be manipulated by transient token movement.

This median directly becomes `PhantomOrderPriceSnapshotV2.medianPrice/lowestPrice/highestPrice`: [5](#0-4) 
which then feeds `updateLiquidityPools`'s pool `sellRate`/`buyRate` via `weightedRate`: [6](#0-5) 
and those pool rates are consumed as an authoritative USD price source elsewhere in the protocol, e.g. `getFxPriceFromPools` in `intentGatewayV3.service.ts`, used to price non-stable tokens for fee/USD accounting: [7](#0-6) 

### Impact Explanation
A verified solver that can, even briefly, hold an outsized balance of a leg's output token (e.g. via a flash loan, an internal transfer between its own addresses, or coordination with a counterparty) can force the weighted-median to select its own quoted price, publishing an arbitrary rate as `PhantomOrderPriceSnapshotV2.medianPrice`. Since this snapshot rolls into `LiquidityPool.sellRate`/`buyRate` (a depth-weighted mean across chains, still directly moved by the manipulated sample) and those pool rates are read as ground truth for FX pricing (`getFxPriceFromPools`), a manipulated snapshot can misprice cross-chain fills, fee accounting, or downstream consumers relying on `LiquidityPool` rates — a "forged" price feed rather than "forged message delivery", but functionally the same class of unbacked/mispriced-state risk called out in the source report (price derived from a manipulable balance read rather than a bonded or time-weighted state).

### Likelihood Explanation
Requires being (or briefly controlling/colluding with) a delegated `SolverAccount` operator — a permissioned but not necessarily trust-verified-per-transaction role — plus the ability to hold a large output-token balance on the destination chain for the short window the aggregation RPC call executes in. A solver could use a flash loan (self-repaying within the block/tx it's briefly held) or simply transfer tokens from another owned wallet just before the snapshot is taken and back afterward, at low cost relative to influencing a published cross-chain rate. The main constraint is timing the balance to be present during the async aggregation read rather than an on-chain atomic guarantee, which is feasible but not trivially certain to land in the exact query window.

### Recommendation
Do not weight the median purely by a live, unbonded `balanceOf` snapshot. Consider requiring the weighting balance to be attested/locked (e.g. a bonded stake or an on-chain deposit recorded at bid-submission time rather than read live at aggregation time), or sample the balance multiple times across the bid window (time-weighted) rather than once, so a transient balance spike cannot single-handedly cross the 50% weight threshold. Alternatively, cap any single solver's contribution to a leg's total weight so no solver can unilaterally dictate the published median regardless of momentary balance size.

### Proof of Concept
1. Solver S is (or becomes) delegated to the chain's `SolverAccount` and is thus eligible to have its bids counted (`isVerifiedSolverBid`).
2. S submits a phantom bid quoting an arbitrary favorable price for a leg.
3. Immediately before/at the block the indexer's `handlePhantomOrderPrices.handler.ts` invokes `aggregatePhantomBids` (triggered by `PhantomBidWindowExhausted`), S moves (via flash loan or internal transfer) a large balance of the leg's output token into its bidding wallet on the destination chain.
4. `getBalance` reads this inflated balance as S's `weight`; if it exceeds 50% of the leg's total weight, `weightedMedian` returns S's price verbatim as `medianPrice`.
5. S moves the tokens back out immediately after.
6. The manipulated `medianPrice` is persisted to `PhantomOrderPriceSnapshotV2` and propagates into `LiquidityPool.sellRate`/`buyRate` via `updateLiquidityPools`, corrupting the FX price feed consumed by `getFxPriceFromPools` and any other pool-rate consumer. [8](#0-7)

//
// Callers must not hand this an entry set whose weights are all zero: with nothing to weight by it
// can only pick a quote by position, and for an even-sized set that position is the upper of the
// two middles — so "the median" becomes "whoever quoted higher", settable by a solver holding no
// inventory at all. aggregatePhantomBids drops such legs instead of pricing them. The fallback
// below stays only so an unguarded caller gets a number rather than a crash; treat reaching it as
// a caller bug.
export function weightedMedian(entries: { price: bigint; weight: bigint }[]): bigint {
	const sorted = [...entries].sort((a, b) => (a.price < b.price ? -1 : a.price > b.price ? 1 : 0))
	const totalWeight = sorted.reduce((acc, e) => (e.weight > 0n ? acc + e.weight : acc), 0n)

	if (totalWeight === 0n) {
		return sorted[Math.floor(sorted.length / 2)].price
	}

	let cumulative = 0n
	for (const entry of sorted) {
		if (entry.weight <= 0n) continue
		cumulative += entry.weight
		if (cumulative * 2n >= totalWeight) return entry.price
	}
	return sorted[sorted.length - 1].price
}
