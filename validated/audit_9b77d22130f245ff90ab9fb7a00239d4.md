### Title
Predictable, unsigned session cookie value (`offline_#{shop}` / `#{shop}_#{user_id}`) accepted as an authenticated session identifier — (File: `lib/shopify_api/utils/session_utils.rb`)

### Summary
For non-embedded apps, `SessionUtils.cookie_session_id` returns `cookies['shopify_app_session']` verbatim and treats it as the authenticated session identifier used to look up a merchant's stored `Session` (and thus its `access_token`). The value stored in that cookie by `Oauth.validate_auth_callback` is not a random secret — it is exactly `session.id`, i.e. `"offline_#{shop}"` or `"#{shop}_#{user_id}"` — a deterministic string derivable from public information, set in a plain (unsigned, unencrypted) cookie as documented in `docs/usage/oauth.md`.

### Finding Description
The broken binding is: **the app treats `cookies['shopify_app_session'] == session.id` as proof of "this browser/request was previously authenticated by Shopify OAuth for this shop/user,"** but no cryptographic mechanism enforces that equality can only be produced by a legitimate OAuth completion.

Trace:
1. During `begin_auth`, the cookie holds a random 15-character alphanumeric CSRF `state` value (`test/auth/oauth_test.rb:320-321`), which is fine — unpredictable.
2. On successful callback, `Oauth.validate_auth_callback` (`lib/shopify_api/auth/oauth.rb:100-110`) **replaces** that random cookie with a brand-new `SessionCookie` whose `value` is `session.id`:
   - offline: `"offline_#{shop}"` [1](#0-0) 
   - online: `"#{shop}_#{user_id}"` [2](#0-1) 
   Confirmed by the test expectations: [3](#0-2) 
3. The documented pattern for persisting this cookie in the host app uses a plain, unsigned cookie assignment (`cookies[name] = { value: ..., secure: true, http_only: true }`), never `cookies.signed`/`cookies.encrypted`.
4. On every later request, the host app calls `SessionUtils.current_session_id(nil, cookies, online)`, which for non-embedded apps unconditionally calls `cookie_session_id(cookies)` [4](#0-3) , which returns the raw cookie value with **no HMAC, no signature check, no comparison against any authenticated source** [5](#0-4) .
5. The host app then uses this returned string as the lookup key into its session store to retrieve the `Session` (containing `access_token`) and serves the request using that access token — this is exactly the documented usage in `docs/getting_started.md:47-52`.

Because the cookie's value is just `offline_#{shop}` or `#{shop}_#{user_id}`, and shop domains are public (`*.myshopify.com` names are guessable/enumerable) and `user_id` values are typically small sequential Shopify admin user IDs, an attacker never needs to observe or steal any real cookie. They can simply send `Cookie: shopify_app_session=offline_targetshop.myshopify.com` (or `targetshop.myshopify.com_1`) directly in an HTTP request to the app, with no `Authorization` header, no prior interaction with the target shop, and no secret material.

No existing guard stops this: `HmacValidator.validate` only checks OAuth callback query params, `ShopValidator.sanitize!` only validates shop domain formatting, the `state == auth_query.state` check only fires during the one-time OAuth callback, and `Context.embedded?` merely routes non-embedded apps into this exact cookie-trusting branch.

### Impact Explanation
An attacker who merely knows (or brute-forces) a victim shop's domain — and, for online sessions, a small numeric user id — can cause a non-embedded app to load that victim's stored `Session`/`access_token` and act on it for the attacker's request. This is cross-tenant session hijacking leading to theft/misuse of the merchant's Admin API access token, matching the Critical "theft of a merchant access token" / "cross-tenant access" category. It is fully repeatable against any shop using the app, requires no prior authentication, and scales trivially (iterate over shop names / small user-id integers).

### Likelihood Explanation
Preconditions: the app must be configured `is_embedded: false` (a legitimate, common configuration for non-embedded Shopify apps) and must follow the gem's documented persistence pattern (plain cookie holding `session.id`) and the documented session-lookup pattern (`SessionUtils.current_session_id`/`cookie_session_id` as the storage key). Attacker cost is negligible — one crafted HTTP request with a guessed/known shop domain. No secrets, tokens, or victim interaction required. This is highly feasible and repeatable.

### Recommendation
Do not let a value derivable purely from public shop/user identifiers double as the authenticated session cookie. Either:
- Keep the cookie value as an unpredictable random opaque token (as used for the OAuth `state`) mapped server-side to the real session id, rather than replacing it with the deterministic `session.id`; or
- Sign/HMAC the cookie value with `api_secret_key` at issuance and verify the signature in `cookie_session_id` before trusting it, rejecting any cookie whose signature doesn't validate.

### Proof of Concept
```ruby
# test/utils/session_utils_test.rb (new test)
def test_cookie_session_id_accepts_forged_predictable_value_without_prior_auth
  ShopifyAPI::Context.stubs(:embedded?).returns(false)

  forged_shop = "victim-shop.myshopify.com"
  forged_session_id = "offline_#{forged_shop}"   # fully derivable, never issued to this "browser"

  cookies = { ShopifyAPI::Auth::Oauth::SessionCookie::SESSION_COOKIE_NAME => forged_session_id }

  # No Authorization header, no prior OAuth completion for this request/browser,
  # yet current_session_id happily returns the victim's exact session id.
  result = ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)

  assert_equal(forged_session_id, result)
  # binding under test: cookies['shopify_app_session'] (attacker-supplied, unauthenticated)
  #                     == session.id (the real, previously-authenticated identifier)
  # This equality holds even though the attacker never went through OAuth.
end
```
This demonstrates the broken binding at the gem-API level: `cookie_session_id`/`current_session_id` return the exact same value an authenticated victim's session would use, driven entirely by attacker-supplied, unauthenticated cookie input.
