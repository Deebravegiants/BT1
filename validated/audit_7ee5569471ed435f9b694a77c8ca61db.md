### Title
Webhook `shop-domain` and `topic` headers are not covered by the HMAC signature, enabling cross-tenant webhook replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [1](#0-0) , so `Utils::HmacValidator.validate` in `Registry.process` only proves that the *body bytes* were signed with the app's `client_secret` — it says nothing about which shop the webhook actually belongs to. The `shop` and `topic` values used downstream come straight from unauthenticated HTTP headers (`shopify-shop-domain`, `shopify-topic`) [2](#0-1) .

### Finding Description
`Registry.process` validates the request purely via `Utils::HmacValidator.validate(request)`, then immediately trusts `request.shop` and `request.topic` to build `WebhookMetadata` and dispatch it to the handler: [3](#0-2) 

The HMAC is computed only over `@raw_body` [4](#0-3) , using the app-wide `Context.api_secret_key`/`old_api_secret_key` shared across every shop that installed the app [5](#0-4) . Because the same secret signs the same body identically regardless of which shop it came from, the equality the code implicitly relies on is:

`HMAC-valid(body) == body originated from request.shop`

but the actual guarantee provided is only:

`HMAC-valid(body) == body was signed with this app's client_secret (by any of its installed shops)`

A merchant who has installed the app (an "unprivileged" tenant with no access to other tenants' data) can capture one legitimately-delivered webhook (body + `X-Shopify-Hmac-Sha256` header) sent to their own endpoint, then replay that exact body/HMAC pair to the app's webhook endpoint while substituting a different `shopify-shop-domain` (and optionally `shopify-topic`) header value belonging to another shop. `HmacValidator.validate` still succeeds because it never inspects `shop`, `topic`, or any header — only the raw body — so `Registry.process` will hand the handler a `WebhookMetadata` claiming the body came from the victim shop [6](#0-5) .

### Impact Explanation
If the host application uses `WebhookMetadata#shop` as the tenant key to decide which merchant's records to update/delete/query (a normal and documented usage pattern for this field), an attacker-controlled shop can inject arbitrary (but validly-HMAC'd) webhook bodies attributed to a victim shop, resulting in cross-tenant data corruption or disclosure — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Requires only that the attacker run their own store with the target app installed (a normal, unprivileged relationship many "app store" style integrations allow), capture one webhook delivery, and replay it with a modified header. No access to the app's `client_secret`, TLS interception, or privileged account is needed, and the request-forgery is entirely within the surface this gem exposes (`Webhooks::Request`/`Webhooks::Registry`), not dependent on the host app misusing an undocumented API — `shop` is the documented field host apps are told to key on [7](#0-6) .

### Recommendation
Include the `shop-domain` (and ideally `topic`, `api-version`, `webhook-id`) header values in the signable string used for HMAC verification, or otherwise cryptographically bind the shop identity to the signed payload, so that `HmacValidator.validate` fails if any of these headers are altered relative to what was actually signed by Shopify for that specific shop/topic delivery.

### Proof of Concept
1. App receives a legitimate webhook for `attacker-shop.myshopify.com` with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC(secret, B)`).
2. Attacker (owner of `attacker-shop.myshopify.com`) replays a POST to the app's webhook endpoint with the same body `B` and header `H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...shop-domain: "victim-shop.myshopify.com", hmac-sha256: H...})` is constructed; `request.shop` now returns `"victim-shop.myshopify.com"`.
4. `Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(secret, B) == H` — this passes since `B`/`H` are a genuine pair. [8](#0-7) 
5. The registered handler is invoked with `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body: parsed_body, ...)`, causing the host app to process attacker-controlled data as if it belonged to the victim shop. [7](#0-6)
