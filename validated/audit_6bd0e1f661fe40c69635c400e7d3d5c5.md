### Title
Webhook shop/topic identity not bound by HMAC, allowing cross-tenant webhook forgery via header substitution - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable signable string from the raw body only, while the `shop`, `topic`, and `webhook_id` values used by `Registry.process` to identify which tenant the webhook belongs to are read from unauthenticated HTTP headers. The library validates the HMAC but hands the caller-supplied `shop`/`topic` header values to the handler as trusted metadata, without those values ever being covered by the signature it just verified. This is the same bug class as the reported finding: a check ("HMAC valid") that appears to authenticate the whole request but actually leaves a security-relevant field ("shop") outside the covered/protected surface, so the field can be substituted freely while the check still passes.

### Finding Description
`Request#to_signable_string` returns only the raw body: [1](#0-0) 

`Request#shop`, `#topic`, and `#webhook_id` are all read straight from HTTP headers with no binding to the signed content: [2](#0-1) 

`Registry.process` validates the HMAC over the (headers-excluded) signable string, then immediately trusts `request.shop`/`request.topic` to build `WebhookMetadata` and dispatch to the app's handler: [3](#0-2) 

Because the signature covers only `@raw_body`, the equality the library implicitly claims to enforce — "the `shop` (and `topic`) delivered to the handler == the `shop` (and `topic`) that the holder of `api_secret_key` actually signed for" — does not hold. Any HTTP header (`shop-domain`, `topic`, `webhook-id`, and any duplicated `x-shopify-*` vs `shopify-*` variant) can be modified without invalidating `Utils::HmacValidator.validate`, since that validator only recomputes the HMAC over the body: [4](#0-3) 

This mirrors the report's root cause pattern: an authorization/identity check is present and passes, but the field that actually determines the "who/what this applies to" decision (here, `shop`) is not covered by the mechanism being relied upon (here, HMAC), so it can be swapped out while the check keeps succeeding.

### Impact Explanation
`request.shop` is the tenant identifier consumed by the host application through `WebhookMetadata#shop`, which is the standard way `shopify_api`-based apps determine which merchant a webhook update pertains to (e.g. to look up that shop's session/store record and apply the webhook payload). Since `shop` is not part of the signed bytes, an unprivileged internet user who is able to submit HTTP requests to the app's public webhook endpoint — and who possesses at least one legitimate `raw_body` + valid HMAC pair (for instance, captured from a webhook delivered for their own installed shop, which is attacker-controlled/attacker-observable data) — can resubmit that exact body/HMAC with the `shop-domain` (and/or `topic`) header changed to a different, victim shop domain. `Utils::HmacValidator.validate` still returns `true` because it never inspected the header, and `Registry.process` dispatches the handler with the attacker-chosen `shop`, causing the host application to process (and potentially persist) attacker-supplied webhook content under another tenant's identity — a cross-tenant integrity/access issue.

### Likelihood Explanation
The webhook endpoint is by design a public, unauthenticated HTTP endpoint (that is the entire reason HMAC validation exists). Obtaining one legitimate `(raw_body, hmac)` pair only requires operating any single shop that has the app installed and receives webhooks for a topic whose body an attacker can influence or simply replay verbatim to a different shop context; no access to `api_secret_key`, access tokens, or privileged accounts is needed. The only gem-level obstacle is that the library never asked the caller to prove that `shop`/`topic` were what was actually signed, so likelihood of exploitation depends only on network reachability of the app's webhook route, which is always internet-reachable.

### Recommendation
Bind the values used for tenant/topic identification into the signed payload verification, or otherwise cryptographically tie `shop`/`topic`/`webhook_id` headers to the HMAC before trusting them:
- Include the `shop`, `topic`, and `webhook_id` header values in `Request#to_signable_string` (or perform a secondary integrity check binding them to the verified body), analogous to how `Auth::Oauth::AuthQuery#to_signable_string` explicitly enumerates every field it authenticates (`code`, `host`, `shop`, `state`, `timestamp`).
- At minimum, document and/or enforce that host applications must not treat `request.shop` as authenticated unless it is corroborated against a known/pre-registered `myshopify_domain` for the session the webhook is presumed to target.

### Proof of Concept
1. App is a multi-tenant Shopify app, embedding `shopify_api` and registering a webhook handler via `ShopifyAPI::Webhooks::Registry`.
2. Attacker installs the app on shop A (`attacker-shop.myshopify.com`) and triggers a webhook whose body they can predict/replay (e.g., an `orders/create` webhook they generate themselves), capturing the exact `raw_body` and the `x-shopify-hmac-sha256` header Shopify sent.
3. Attacker POSTs to the app's public webhook route with the same `raw_body` and same `hmac-sha256` header, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and, if relevant, a `topic` value chosen to hit a sensitive handler).
4. `Utils::HmacValidator.validate` recomputes the HMAC over `raw_body` only [5](#0-4)  — it matches, so `Registry.process` proceeds and calls the handler with `shop: "victim-shop.myshopify.com"` [6](#0-5) , even though nothing about that shop value was ever verified.
