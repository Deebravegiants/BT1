### Title
Single authorised-relayer gate on `onAccept`/`onGetResponse` permanently freezes escrowed order funds if that relayer withholds delivery - (File: `evm/src/apps/intentsv2/ExtrinsicIntents.sol`)

### Summary
`ExtrinsicIntents.onAccept` and `ExtrinsicIntents.onGetResponse` both call `_checkRelayer(incoming.relayer)` before processing `RedeemEscrow`/`RefundEscrow` withdrawals or cancellation `GET` responses [1](#0-0) [2](#0-1) . Once an authorised relayer address is set, any delivery from a different party — including the affected user self-relaying their own refund proof — is rejected [3](#0-2) . Because the underlying `DispatchGet`/`DispatchPost` messages that carry these withdrawals are created with `timeout: 0` (no expiry) [4](#0-3) [5](#0-4) , there is no fallback timeout-refund path either. If the single authorised relayer is unavailable or withholds delivery of these specific messages, the escrowed user funds can never be released by anyone else, permanently freezing them — the direct analog of the zkSync M-09 report where a malicious operator that only processes one class of transactions traps user ETH with no escape hatch.

### Finding Description
Hyperbridge's general design goal, documented for ordinary applications, is that message delivery is permissionless: "Self-relaying allows you to deliver POST requests to the destination chain yourself, instead of relying on the Hyperbridge relayer network" [6](#0-5) , and `HandlerV2.handlePostRequests`/`handleGetResponses` are permissionless entry points reachable by anyone with a valid proof [7](#0-6) .

`IntentGatewayV2`/`ExtrinsicIntents`, however, layers an application-level gate on top of this permissionless delivery: `_checkRelayer` rejects any `onAccept`/`onGetResponse` call whose reported relayer does not match the single `_relayer` address once one has been set [3](#0-2) . This gate is applied unconditionally to the withdrawal paths that release a user's escrowed order funds:
- `onAccept` for `RedeemEscrow`/`RefundEscrow` messages (destination-chain fill or destination-initiated cancellation, releasing escrow on the source chain) [8](#0-7) .
- `onGetResponse` for the `GET` response that `_cancelFromSource` relies on to refund the escrow once the destination `_filled` slot is proven empty [2](#0-1) .

Both the `DispatchGet` created in `_cancelFromSource` and the `DispatchPost` created by `_post` (used for both `RedeemEscrow` and `RefundEscrow`) are dispatched with `timeout: 0`, i.e. they never expire and there is no automatic ISMP timeout-refund path to fall back on [4](#0-3) [5](#0-4) .

Per the documented behavior of `EvmHost.dispatchIncoming`, a rejected `onAccept`/`onGetResponse` call (e.g. from `_checkRelayer` reverting) leaves no receipt and is "retryable" [9](#0-8)  — but only by the one authorised relayer, since the message content and proof are unaffected by who submits it; the `_checkRelayer` check depends solely on `msg.sender`/`relayer` identity, not on message content. Consequently, a user has no alternative route to submit the same valid proof themselves and unlock their funds if the authorised relayer refuses or becomes unavailable, exactly mirroring the zkSync report's scenario where an operator that only services one transaction class strands a user's funds because the alternate access path is unavailable to them.

### Impact Explanation
Escrowed order funds (input tokens locked by `placeOrder`) become permanently unrecoverable whenever the single authorised relayer withholds or refuses to deliver a `RefundEscrow`, `RedeemEscrow`, or cancellation `GET` response for a specific order/commitment. Since delivery is gated purely by sender identity rather than by message validity, and since these particular messages carry `timeout: 0` (no expiry-based recovery), there is no permissionless self-relay escape hatch and no timeout refund — this is a permanent freezing of user funds, not merely delayed settlement.

### Likelihood Explanation
Exploitability depends on the authorised relayer (set via `setRelayer`, reachable only through a governance `Execute` action [10](#0-9) ) becoming unavailable, censoring, or acting maliciously toward specific orders. This mirrors the zkSync finding's "malicious operator" precondition, which was judged Medium severity there because the underlying protocol design should still guarantee user fund recovery independent of any single privileged relaying party — a guarantee this application-level gate removes for `IntentGatewayV2` even though the base Hyperbridge messaging layer supports permissionless self-relay.

### Recommendation
Do not apply `_checkRelayer` to withdrawal-releasing paths (`RedeemEscrow`, `RefundEscrow`, and the cancellation `GET` response), or provide an alternate recovery mechanism (e.g., a non-zero timeout with a corresponding `onGetTimeout`/`onPostRequestTimeout` refund handler, or allowing the order's own user/beneficiary to self-relay their own withdrawal irrespective of the configured relayer) so that escrow release cannot be indefinitely blocked by a single relayer's non-cooperation.

### Proof of Concept
1. Governance sets `_relayer` to address `R` via `setRelayer` (through the `Execute` host action) [10](#0-9) .
2. A user places a cross-chain order via `placeOrder`, locking input tokens in escrow.
3. The order is not filled before its deadline; the user calls `_cancelFromSource`, dispatching a `DispatchGet` (timeout 0) to prove the order was never filled on the destination [11](#0-10) .
4. Once Hyperbridge produces the valid `GET` response/proof, relayer `R` refuses (or is offline) to call `HandlerV2.handleGetResponses`. Any other party (including the user) who instead submits the same valid proof will have `EvmHost.dispatchIncoming` call `onGetResponse`, which immediately reverts via `_checkRelayer` because `relayer != R` [12](#0-11) .
5. Because the `GET` request has `timeout: 0`, there is no timeout path to fall back on, and the escrow remains locked indefinitely regardless of proof validity — the user's funds are permanently frozen.

     * @dev Once a relayer is set, rejects deliveries from anyone else before the body is read. The

    function _checkRelayer(address relayer) internal view {
        address authorised = _relayer;
        if (authorised != address(0) && relayer != authorised) revert Unauthorized();

    function _cancelFromSource(Order calldata order, CancelOptions calldata options, bytes32 commitment) internal {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

        if (options.height <= order.deadline) revert NotExpired();

        uint256 inputsLen = order.inputs.length;
        for (uint256 i; i < inputsLen;) {
            if (_orders[commitment][address(uint160(uint256(order.inputs[i].token)))] == 0) revert UnknownOrder();

            unchecked {
                ++i;
            }
        }

        bytes memory context =
            abi.encode(WithdrawalRequest({commitment: commitment, tokens: order.inputs, beneficiary: order.user}));

        bytes[] memory keys = new bytes[](1);
        keys[0] = bytes.concat(abi.encodePacked(_instance(order.destination)), _calculateCommitmentSlotHash(commitment));
        DispatchGet memory request = DispatchGet({
            dest: order.destination,
            keys: keys,
            timeout: 0,
            height: options.height,
            fee: options.relayerFee,
            context: context,
            payer: msg.sender
        });

## Self Relayed Requests

Self-relaying allows you to deliver POST requests to the destination chain yourself, instead of relying on the Hyperbridge relayer network. This is useful when you want full control over delivery timing, need to save on relayer fees, or want to guarantee delivery for critical requests.

The `@hyperbridge/sdk` provides tools to track POST requests and automatically generates the calldata needed to execute [`handlePostRequests()`](/developers/evm/api/ihandler#handlepostrequests) on the destination chain's [`IHandler`](/developers/evm/api/ihandler) contract.

To learn how to self-relay requests:

1. **[Get Started with the SDK](/developers/sdk/getting-started)** - Install and set up the Hyperbridge SDK
2. **[Track POST Requests](/developers/sdk/tracking/post-requests)** - Monitor request status and extract delivery calldata
3. **[IsmpClient API](/developers/sdk/api/ismp-client)** - Use the [`postRequestStatusStream()`](/developers/sdk/api/ismp-client#postrequeststatusstream) method to get calldata when `HYPERBRIDGE_FINALIZED` status is reached

The SDK automatically generates the [`PostRequestMessage`](/developers/evm/api/ihandler#postrequestmessage) proof and calldata you need to call the [`IHandler.handlePostRequests()`](/developers/evm/api/ihandler#handlepostrequests) function on the destination chain. You can make your users self-relay requests or run a server which can relay requests on behalf of users.
