### Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb](https://github.com/AYontt/shopify-api-ruby--009/blob/main/lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop` value from the unauthenticated `x-shopify-shop-domain` / `shopify-shop-domain` HTTP header, but the HMAC signature verified by `ShopifyAPI::Utils::HmacValidator` only covers the raw request body. This breaks the intended binding `HMAC(secret, raw_body) == received_hmac` ⟹ `shop == authenticated_shop`; in reality the signature says nothing about which shop the payload belongs to.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, and `#shop` is read straight from a header: [1](#0-0) [2](#0-1) 

`Registry.process` validates the HMAC and then forwards `request.shop` verbatim to the app's handler without any cross-check against the signed content: [3](#0-2) 

`Utils::HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (the body), so the header set (`shop-domain`, `topic`, `api-version`, `webhook-id`) is entirely outside the authenticated boundary: [4](#0-3) [5](#0-4) 

Because Shopify webhook HMACs are computed with the app-level `client_secret`/`api_secret_key` (shared across every shop that has installed the app — not per-shop), any tenant that has installed the app can obtain a genuinely-signed `(body, hmac)` pair for their own shop. Nothing prevents that tenant from resending the identical body+HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop's domain. `HmacValidator.validate` still returns `true` (it never looks at the header), so `Registry.process` calls the handler with `WebhookMetadata#shop` set to the attacker-chosen victim shop, alongside the attacker-controlled body.

### Impact Explanation
Any app built on this gem that trusts `WebhookMetadata#shop` (e.g., to look up the merchant's session/access token, or to write/mutate data scoped to that shop) can be tricked into processing an attacker-controlled payload under a different merchant's identity — a cross-tenant action performed with the credentials/context of another shop. This matches the Critical "cross-tenant access" impact category, since the gem's own webhook-processing API is the exact place host apps are told to trust `shop` from `WebhookMetadata` as an authenticated fact.

### Likelihood Explanation
Any unprivileged internet user who can install the target app on their own shop (a normal, unprivileged flow for public apps) can capture a legitimate, correctly-signed webhook for their shop and replay it to the app's public webhook endpoint with a forged shop-domain header. No secret, token, or elevated privilege is required beyond having any working installation of the app — an "unprivileged internet user" analog is directly satisfied.

### Recommendation
Bind the shop identity into the authenticated data before trusting it:
- Include the `shop-domain` header (and ideally `topic`/`webhook-id`) in the HMAC-signable string, verifying header-vs-body consistency, or
- At minimum, require the caller (host app) to independently confirm that `WebhookMetadata#shop` corresponds to a shop session/installation the app expects for the specific `webhook_id`/subscription, rather than accepting the header at face value.
- Document explicitly in `docs/usage/webhooks.md` that `request.shop`/`WebhookMetadata#shop` is unauthenticated and must not be trusted for authorization decisions without additional verification.

### Proof of Concept
1. Install the target app on shop A (attacker-controlled) using the normal OAuth flow.
2. Trigger a webhook delivery (e.g., `orders/create`) from shop A; capture the raw POST body and the `x-shopify-hmac-sha256` header Shopify sends — this HMAC is valid because it is computed with the app's shared `api_secret_key`.
3. Replay the exact same body and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but set `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate`, which only checks the body against the secret and returns `true` [6](#0-5) 
, then invokes the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, causing the host app to act as though the (attacker-controlled) payload came from the victim shop.
