### Title
Webhook `shop` and `topic` Identity Not Covered by HMAC, Enabling Cross-Tenant Webhook Replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw HTTP body, so the HMAC verification performed by `Utils::HmacValidator.validate` proves nothing about the `shop-domain`, `topic`, or `webhook-id` headers. `Webhooks::Registry.process` nonetheless treats `request.shop` and `request.topic` as authenticated once the HMAC check passes and dispatches the handler with those unauthenticated values, breaking the binding "HMAC-verified bytes == identity used for tenant/topic routing."

### Finding Description
`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, that signable string is only the raw body — none of the Shopify-supplied headers are part of the signed content: [2](#0-1) 

`shop`, `topic`, and `webhook_id` are all parsed straight from headers with no cryptographic binding to the HMAC: [3](#0-2) 

`Webhooks::Registry.process` validates only the HMAC (i.e., only the body) and then unconditionally trusts `request.topic` for handler dispatch and `request.shop` for tenant identification when constructing `WebhookMetadata` passed to the app's handler: [4](#0-3) 

The equality that should hold is:
`shop/topic used for dispatch == shop/topic bound into the HMAC-signed bytes`

But in this implementation:
`shop/topic used for dispatch == shop/topic taken from unauthenticated headers`, while `HMAC-signed bytes == raw_body only`.

Because the signature is independent of the headers, any request whose body+hmac pair is valid for shop A (e.g., obtained from a legitimately-delivered webhook to the attacker's own store, or via a request smuggling / header-injection point in front of the app) remains HMAC-valid when the `shop-domain` and/or `topic` headers are swapped to arbitrary values, since `validate_signature` in `HmacValidator` re-derives the signature from the identical `raw_body` regardless of headers.

### Impact Explanation
This directly breaks the tenant/topic identity binding: an attacker who can present a valid `(raw_body, hmac)` pair (trivially available from a webhook their own installed shop legitimately receives) can relabel the `shop-domain` header to any other shop and have `Registry.process` accept it as authenticated, then invoke the registered handler with `WebhookMetadata#shop` set to the victim shop and/or a different `topic` (including mandatory compliance topics such as `customers/redact` or `shop/redact`). Any host application that — following this gem's own `WebhookMetadata` output — uses `data.shop`/`data.topic` to select which tenant's records to mutate or delete is exposed to cross-tenant data corruption/deletion driven entirely by this gem accepting the request as validly authenticated.

### Likelihood Explanation
Exploitation requires only a single genuine webhook delivery (body + valid hmac) that the attacker can obtain for a shop they control (trivial — install their own copy of the target app, or subscribe to any low-sensitivity topic), then replay that exact body with modified `shop-domain`/`topic` headers to the app's public webhook endpoint. No access token, `client_secret`, or privileged credential is required, satisfying the unprivileged-internet-user constraint.

### Recommendation
Bind the identity fields into the signable content, or otherwise fail closed:
- Include `shop`, `topic`, and `webhook_id` in `Webhooks::Request#to_signable_string` (mirroring how `AuthQuery#to_signable_string` binds `shop`/`host` into its signed string), or
- Require the host application layer to independently verify that the `shop` reported in the webhook corresponds to a shop with an active, matching installation/session before trusting `WebhookMetadata#shop` for any tenant-scoped action, and document this requirement explicitly in `Registry.process`.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and subscribes to any webhook topic (e.g., `orders/create`), receiving a legitimately signed webhook: raw body `B` and header `x-shopify-hmac-sha256: H` (valid HMAC of `B` under the app's `client_secret`).
2. Attacker replays this exact request to the app's webhook endpoint, but sets:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - `x-shopify-topic: customers/redact` (or another mandatory/sensitive topic understood by the app's handler for that body shape)
   - keeps body `B` and `x-shopify-hmac-sha256: H` unchanged.
3. `Utils::HmacValidator.validate(request)` recomputes the HMAC over `raw_body` (`B`) only and it matches `H`, so `Registry.process` proceeds: [5](#0-4) 
4. The registered handler is invoked with `WebhookMetadata.new(topic: "customers/redact", shop: "victim-shop.myshopify.com", body: parsed_body, ...)`, causing the host application to perform shop-victim-scoped business logic (e.g., data deletion) triggered entirely by an attacker-controlled, unauthenticated header value.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
