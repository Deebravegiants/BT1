Audit Report

## Title
Unauthenticated Cross-User Response Hijacking via MessageID Collision in Gateway WebAPI Handler - (File: core/services/gateway/handlers/capabilities/handler.go)

## Summary
The Gateway's user-facing HTTP endpoint accepts JSON-RPC requests whose `id` field becomes the internal `MessageID` used to route asynchronous node responses back to the originating HTTP caller. This `MessageID` is fully attacker-controlled and is not bound to the caller's identity, nor is uniqueness enforced when storing the pending callback, allowing an unprivileged client to overwrite a victim's in-flight callback and receive the victim's response instead.

## Finding Description
`ProcessRequest` in `core/services/gateway/gateway.go` (L221-234) decodes the raw JSON-RPC request; `DecodeJSONRequest` in `core/services/gateway/api/jsonrpccodec.go` (L26-35) assigns `msg.Body.MessageID = request.ID` directly from client-supplied JSON. `msg.Validate()` (`core/services/gateway/api/message.go` L54-88) only checks signature format/validity and extracts a signer address — it performs no check binding `MessageID` to a caller identity or verifying uniqueness.

`HandleLegacyUserMessage` (`core/services/gateway/handlers/capabilities/handler.go` L341-421) stores the callback keyed solely by this client-chosen `MessageID` at L411-412: `h.savedCallbacks[msg.Body.MessageID] = &savedCallback{...}` — with no existence check and no binding to the caller's session or signer. The code comment at L384, `// TODO: apply allowlist and rate-limiting here`, explicitly documents the missing authorization control on this exact path.

When a DON node later responds with `MethodWebAPITrigger`, `handleWebAPITriggerMessage` (L148-162) looks up `savedCallbacks[msg.Body.MessageID]` and forwards the result to whatever callback is currently registered under that key, with no verification the response belongs to the original requester.

By contrast, the sibling `OutgoingConnectorHandler.responses.new()` (`core/capabilities/webapi/outgoing_connector_handler.go` L449-462) explicitly rejects a duplicate ID (`already have response for id`) before creating a channel — `WebAPIHandler.savedCallbacks` has no equivalent duplicate-detection.

## Impact Explanation
An unauthenticated/unprivileged client reaching the gateway's user HTTP port (`/user`, confirmed by `GetUserPort()` wiring in `gateway.go` and integration test usage) can send a request with a `MessageID` matching a victim's in-flight request, overwriting the victim's registered callback in `savedCallbacks`. The subsequent DON response intended for the victim is delivered to the attacker's connection instead — cross-user response corruption/information disclosure, and simultaneous denial of service to the victim whose original request never gets its response. This maps to the in-scope Chainlink impact category of "gateway request impersonation / cross-user response corruption."

## Likelihood Explanation
The endpoint is user-facing and requires only a self-generated ECDSA keypair to produce a valid `Signature` passing `Validate()` — no privileged role, credential, or node/operator access is needed. Exploitability depends on the attacker matching/guessing an in-flight victim's `MessageID` within its live window (bounded by `defaultCallbackMaxAgeSec` = 120s), which is feasible when IDs are predictable, low-entropy, sequential, or when an attacker floods guesses during high request volume.

## Recommendation
Bind pending callbacks to a unique, gateway-generated correlation key (or at minimum the tuple of `(Sender, MessageID)`) instead of trusting the client-supplied `MessageID` alone. Reject requests attempting to reuse an already-pending `MessageID`, mirroring the duplicate check in `responses.new()`. Implement the allowlist/rate-limiting noted as a TODO in `HandleLegacyUserMessage` before it reaches production traffic.

## Proof of Concept
1. Victim sends a legitimate `web_api_trigger` request to `POST /user` with `id: "X"` and a valid self-signed `Message`.
2. Before the DON node responds, attacker sends their own request to `POST /user` with the same `id: "X"` and their own validly self-signed payload.
3. `HandleLegacyUserMessage` overwrites `savedCallbacks["X"]` with the attacker's callback (`handler.go` L411-412).
4. The DON node's response for message `"X"` arrives at `handleWebAPITriggerMessage`, which looks up `savedCallbacks["X"]` (now the attacker's callback) and delivers the victim's intended response to the attacker's HTTP connection (`handler.go` L148-162).

A Go unit/integration test can construct two `HandleLegacyUserMessage` calls with identical `MessageID` and distinct callbacks, then simulate a `HandleNodeMessage` (`MethodWebAPITrigger`) response for that ID, asserting the second (attacker) callback receives the response while the first (victim) callback never fires — proving the hijack. func (m *Message) Validate() error {

	}

		return errors.New("invalid hex-encoded signature length")

	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {

	}

		return errors.New("invalid DON ID length")
