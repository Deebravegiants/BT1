## Title
Webhook shop-domain spoofing due to HMAC covering only the request body, not the `shop` identity claim - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then trusts the `x-shopify-shop-domain` header — which is *not* covered by that HMAC — as the tenant identity passed to the app's handler. Any party who can obtain one genuinely-signed webhook payload (e.g. by installing the app on their own store) can replay that exact body/HMAC pair while substituting an arbitrary `shop-domain` header, causing the receiving app to process attacker-controlled webhook data attributed to a victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, by contrast, is parsed straight from the `x-shopify-shop-domain`/`shopify-shop-domain` header with no cryptographic binding to the signed content: [2](#0-1) 

`HmacValidator.validate` computes the HMAC exclusively over `to_signable_string` (the body): [3](#0-2) 

`Registry.process` accepts the request once that body-only HMAC check passes, and then forwards the unauthenticated `request.shop` value straight into the tenant-identifying `WebhookMetadata` passed to the app's handler: [4](#0-3) 

The identity binding that should hold is: `hmac == HMAC(secret, body ‖ shop)`, i.e. the authenticated shop should equal the shop the signature was computed over. Instead the code enforces only `hmac == HMAC(secret, body)` while treating `shop` as trusted, so `shop_signed == shop_trusted` is never checked — exactly the "field acted on but not covered by the HMAC" class of bug from the analog report (the strategy contract trusting a check that didn't cover all attacker-influenced state).

Because the HMAC secret (`api_secret_key`) is the same for every shop that has installed a given app, any unprivileged actor can install the target app on their own store, capture one legitimately Shopify-signed webhook delivery (valid body + valid HMAC for that body), and replay it against the app's webhook endpoint with the `x-shopify-shop-domain` header rewritten to any victim shop's domain. `Utils::HmacValidator.validate` still returns `true` (body/HMAC pair untouched), and `Registry.process` will invoke the app's handler believing the payload originated from the victim shop.

### Impact Explanation
This breaks the shop/tenant identity boundary the gem is supposed to enforce for webhook processing: an attacker can make the app act on attacker-chosen webhook content (topic-dependent — e.g. `app/uninstalled`, `shop/update`, `customers/data_request`, or any topic the app subscribes to) while it is misattributed to a shop the attacker does not own. Depending on how the host app uses `WebhookMetadata#shop` (most apps use it to look up/mutate per-shop state, revoke access, or trigger data operations), this is a cross-tenant access vector — satisfying the "Critical – cross-tenant access" bar.

### Likelihood Explanation
Any user able to install the app on a store they control (a very low bar — often a free dev/partner store) can obtain a genuinely-signed webhook body/HMAC pair from Shopify itself, then trivially forge HTTP headers when POSTing to the app's public webhook endpoint. No access to `api_secret_key`, tokens, or the victim's credentials is required.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) as part of the HMAC-signed material, or otherwise cryptographically bind the header-derived `shop` to the verified request before it is handed to `WebhookMetadata`. At minimum, `Registry.process` should cross-check that the shop asserted in the header matches an independently-authenticated identity (e.g. the shop returned by Shopify's separate verification channel) rather than trusting an unauthenticated header value as the tenant key.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` and triggers a subscribed webhook topic (e.g. updates a product to fire `products/update`).
2. Shopify delivers a legitimately HMAC-signed webhook to the app's endpoint: body `B`, header `x-shopify-hmac-sha256: H = HMAC(secret, B)`, `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker captures `(B, H)` and replays a new HTTP request to the same endpoint with identical body `B` and header `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `Utils::HmacValidator.validate` recomputes `HMAC(secret, B)`, which still equals `H` — validation passes (`lib/shopify_api/utils/hmac_validator.rb:26-31`).
5. `Registry.process` proceeds to call the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed(B), ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), causing the app to act on attacker-controlled data under the victim shop's identity.
