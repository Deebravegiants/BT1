### Title
Flash-loan-style inflation of a solver's on-chain token balance can dominate `weightedMedian` and force a manipulated price into published phantom-order pool rates - (File: sdk/packages/sdk/src/protocols/intents/phantom-aggregation.ts)

### Summary
`aggregatePhantomBids` weights every phantom-order bid by the bidding solver's *live* on-chain balance of the leg's output token, read via RPC at aggregation time, and then feeds those weights into `weightedMedian`, which is a **selection** (returns one bidder's exact quoted price verbatim) rather than a blend. This is structurally the same flaw as `ZivoeYDL::distributeYield`'s reliance on `totalSupply()`: a party who can transiently inflate the balance the mechanism reads gets outsized influence over an on-chain-consumed output — here, the published price/rate rather than a yield split.

### Finding Description
In `runAggregation` (`sdk/packages/sdk/src/protocols/intents/phantom-aggregation.ts:1479-1503`), each solver's weight for a leg is computed as: [1](#0-0) 
i.e. `getBalance(destUrl, chain, outputToken, solver)` — a live `balanceOf`-style read — plus any owned Uniswap V4 position value. These weights are pushed into `quotesByLeg`, and the final per-leg price is `weightedMedian(backedQuotes)`: [2](#0-1) 

`weightedMedian` itself is documented as a **selection, not a blend** — the entry whose cumulative weight first reaches half the total weight is returned exactly: [3](#0-2) 

This mirrors the Zivoe pattern precisely: a solver who can borrow/hold a large balance of the output token on the destination chain, right before or during the window the indexer reads it (triggered by the `PhantomBidWindowExhausted` event and processed by `handlePhantomOrderPrices`), can push its own weight over 50% of the leg's total weight and force `weightedMedian` to select **its own quoted price verbatim** as `medianPrice`, which also overwrites `lowestPrice`/`highestPrice`: [4](#0-3) 

That manipulated median is then persisted into `PhantomOrderPriceSnapshotV2` and folded into the pool's aggregate `sellRate`/`buyRate` via `updateLiquidityPools`: [5](#0-4) 

Those published `sellRate`/`buyRate` are consumed by `LiquidityEngine.getBuyAndSellRates`, which is the SDK's own quote source (`indexedRates.ts`) offered to end users/integrators as the reference pool rate: [6](#0-5) 

Note that this differs from `distributeYield`'s intra-transaction flash loan in one respect: the balance read here happens off-chain/asynchronously (an indexer RPC call some time after the triggering event), so a true same-transaction flash loan cannot land its inflated balance into the read. However, the underlying flaw class is identical: the mechanism trusts an instantaneously-read, freely-adjustable token balance as a governance/pricing weight with no time-lock, no minimum holding period, and no historical/checkpointed balance, exactly the defect Sherlock rated Medium in the Zivoe report. A solver can still borrow real capital (not necessarily atomic) and hold it across the deterministic bid-window-close event long enough for the RPC read to land, then return it — the same "temporarily inflate weight, capture the result, unwind" pattern the judges validated in the original report even after conceding a true one-block flash loan doesn't apply.

### Impact Explanation
A solver dominating the weighted median can force the published `medianPrice`/pool `sellRate`/`buyRate` to an arbitrary value of its choosing (bounded only by what other bidders quoted at all), since the selection mechanism returns one bidder's raw quote unmodified once its weight crosses 50%. Because these rates are exposed through `LiquidityEngine.getBuyAndSellRates` as a reference/indexed quote for phantom-order/intents pricing, a manipulated rate can mislead counterparties (users or other fillers) relying on the published rate, and — depending on how aggressively downstream consumers trust indexed rates without independent verification — could result in economic loss for a party that fills or prices against a manipulated rate. This is a pricing/oracle-integrity issue with cross-protocol reach (affects intents/liquidity-pool consumers of the SDK), which is why the analogous Zivoe issue was rated Medium rather than High/Critical: no direct fund custody is broken, but a decision (price) that other value-transferring flows depend on can be steered by an unprivileged party at will.

### Likelihood Explanation
Likelihood is constrained by two factors: (1) the balance read is an asynchronous, off-chain RPC call rather than an atomic in-transaction read, so a strict single-transaction flash loan cannot exploit it — the attacker needs to hold real capital across the window between the `PhantomBidWindowExhausted` event and the indexer's processing of it; (2) `weightedMedian`'s selection only flips fully to the attacker's price once their weight exceeds 50% of the leg's total weight, so the attack is cheaper on thinly-bid legs and more expensive against deep, multi-bidder legs. Given phantom orders are a probe/reference mechanism (not user capital directly) and the event timing is somewhat predictable on-chain, a well-capitalized solver participating in the delegated-solver set could feasibly execute this without needing a true flash loan.

### Recommendation
- Weight bids by a time-checkpointed or historical balance (e.g., average balance over the bid window, or balance at a block prior to the window's start) rather than a live "latest" read, removing the ability to inflate weight transiently right before aggregation.
- Alternatively, replace the pure liquidity-weighted "selection" median with a blended/trimmed statistic (e.g., a capped-weight median where no single solver's weight can exceed some fraction of total weight) so no single actor's balance alone can set the published price verbatim.
- Add a minimum bidder/weight-diversity requirement before publishing a leg's price, and/or a maximum deviation guard against a prior trusted reference price (similar to the `checkPriceGuard` already used elsewhere in the simplex FX strategy) before accepting a new median.

### Proof of Concept
Conceptual PoC (matches the unit-test pattern already in the repo, e.g. `sdk/packages/sdk/src/tests/phantomAggregation.test.ts:190-198`, "weights quotes by balance — the high-liquidity solver pulls the median to its price"):
1. Solver S is a delegated solver account for chain C (passes `isVerifiedSolverBid`).
2. Shortly before/around the `PhantomBidWindowExhausted` event for a phantom order, S borrows/acquires a very large balance of the leg's output token on chain C (e.g., via a lending protocol) and submits a bid quoting an output amount favorable to itself.
3. Other legitimate solvers bid with normal, much smaller balances.
4. When the indexer's `handlePhantomOrderPrices` → `aggregatePhantomBids` reads on-chain balances (`getBalance`) shortly after the event, S's inflated balance dominates total weight for that leg.
5. `weightedMedian` selects S's own quoted price verbatim as `medianPrice` (also `lowestPrice`/`highestPrice`), which `updateLiquidityPools` folds into the pool's `sellRate`/`buyRate`.
6. S returns/repays the borrowed tokens once the read has landed.
7. The pool's published rate now reflects S's chosen price rather than a genuine liquidity-weighted market consensus, and any consumer of `LiquidityEngine.getBuyAndSellRates` sees the manipulated rate until enough fresh, honestly-weighted samples age it out (`MAX_SAMPLE_AGE_BLOCKS`).

```typescript
// Liquidity-weighted median of solver quotes. Each quote's influence is proportional to `weight` —
// the solver's total balance for the output token across native + vault venues — so a solver that
// can actually deliver size moves the price more than one quoting on thin liquidity. Returns the
// lower weighted median: the smallest price whose cumulative weight reaches half of the total.
// Zero-weight quotes contribute nothing.
//
// Callers must not hand this an entry set whose weights are all zero: with nothing to weight by it
// can only pick a quote by position, and for an even-sized set that position is the upper of the
// two middles — so "the median" becomes "whoever quoted higher", settable by a solver holding no
// inventory at all. aggregatePhantomBids drops such legs instead of pricing them. The fallback
// below stays only so an unguarded caller gets a number rather than a crash; treat reaching it as
// a caller bug.
export function weightedMedian(entries: { price: bigint; weight: bigint }[]): bigint {
	const sorted = [...entries].sort((a, b) => (a.price < b.price ? -1 : a.price > b.price ? 1 : 0))
	const totalWeight = sorted.reduce((acc, e) => (e.weight > 0n ? acc + e.weight : acc), 0n)

	if (totalWeight === 0n) {
		return sorted[Math.floor(sorted.length / 2)].price
	}

	let cumulative = 0n
	for (const entry of sorted) {
		if (entry.weight <= 0n) continue
		cumulative += entry.weight
		if (cumulative * 2n >= totalWeight) return entry.price
	}
	return sorted[sorted.length - 1].price
```

```markdown
2. Per leg, a solver's quote is weighted by **its balance of that leg's OUTPUT token on the destination chain** — the inventory that actually backs the leg. Zero-weight quotes are dropped entirely, not down-weighted: they never reach the median, `bidCount`, or the bidder list. A leg where no bidder holds the output token is absent from the result, exactly as if nobody quoted it.

3. The leg's price is `weightedMedian` of the backed quotes — a **selection**, not a blend. It returns one bidder's exact integer, so a solver holding over half the leg's weight sets the published price verbatim, and the result can never be a value nobody quoted. `lowestPrice` and `highestPrice` are deliberately overwritten with the median so consumers cannot read an outlier bid as a tradeable bound.
```
