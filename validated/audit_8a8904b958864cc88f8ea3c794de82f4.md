### Title
Incorrect Type Conversion / Truncating Cast Risk in HyperSwap V2 Reserve Slot Not Accounted For When Combining Launch-Time LT Bound With Attacker Pre-Seed - (File: packages/contracts/src/Bonding.sol)

### Summary
`Bonding._deployAndSeed` bounds only the curve's own maximum LT contribution to the eventual HyperSwap V2 pair (`virtualLtReserve <= type(uint112).max / 4`, so `ltFromPair` tops out at `3 * virtualLtReserve`), reasoning that this keeps the pair's `uint112` reserve slot from overflowing at `finalizeGraduation`. That bound is computed in isolation from the actual mint/rebalance path in `_seedRebalancing` / `_pairRebalance` / `_seedDirectMint`, which explicitly supports a "Regime 3" where an attacker has already self-funded (`pair.mint`) the HyperSwap V2 TOKEN/LT pair with an independent LT reserve before graduation. Nothing sums the attacker's pre-existing `reserveLT` against `ltFromPair` (plus any rebalance-swap inflow) to re-check the combined total against `type(uint112).max` before depositing. A standard UniswapV2-style pair silently truncates `balance` to `uint112` in `_update`, so if the combined amount exceeds `2**112 - 1`, the pair's stored reserve wraps to a small, incorrect value that no longer matches its true token balance.

### Finding Description
`Bonding.sol`'s launch-time guard: [1](#0-0) 
only bounds the curve-native `virtualLtReserve`/`ltFromPair` contribution. The comment explicitly frames this as sufficient "so graduation can never exceed that slot" — but this reasoning omits the pre-seed path that the same contract deliberately supports: [2](#0-1) 
`_seedRebalancing` reads the pre-existing V2 reserves (`r0`, `r1`, cast up from `uint112` to `uint256` for math) and then rebalances/deposits `tokensForLP`/`ltFromPair` on top of them via `_pairRebalance` and `router.addLiquidity`. Because the attacker fully controls the size of their own pre-seed (an unprivileged wallet can call `pair.mint` on the HyperSwap V2 pair for the not-yet-graduated TOKEN/LT pair — explicitly an allowed reachable action per this analysis' scope), the attacker can size `reserveLT_preseed` so that `reserveLT_preseed + ltFromPair + rebalance-swap inflow` exceeds `2**112 - 1`. Since `ltFromPair` can legitimately be as large as `3 * virtualLtReserve` (up to `~0.75 * type(uint112).max`), the attacker only needs to contribute roughly the remaining `~0.25 * type(uint112).max` of LT itself to push the combined total over the `uint112` ceiling. No code in `_seedRebalancing`/`_pairRebalance`/`_seedDirectMint` checks the post-deposit total against `type(uint112).max` before calling `pair.mint`/`addLiquidity`.

### Impact Explanation
When the combined balance transferred into the HyperSwap V2 pair exceeds `uint112`'s range, the pair's internal reserve bookkeeping (standard UniswapV2 `_update`, which does `uint112(balance)`) truncates/wraps the stored reserve to a value far smaller than the pair's true token balance. Once `LPLock.recordLock` locks the freshly minted LP (a one-shot call that `finalizeGraduation` cannot skip or retry), the pool is permanently live with reserves that no longer reflect real balances. Any subsequent swap computed off the wrapped, undersized reserve lets the first trader (the attacker, pre-positioned) extract far more TOKEN/LT than the constant-product formula should allow, draining real value out of the pool for a fraction of its true worth — a permanent, irreversible loss of LP funds seeded at graduation, and an LP price that is not the curve-close price.

### Likelihood Explanation
Reaching the corrupted state requires the attacker to pre-seed the not-yet-graduated HyperSwap V2 pair with an LT balance on the order of `type(uint112).max / 4` (~1.3 × 10^33 raw units, i.e. billions of LT tokens at 18 decimals) — a capital requirement that is extreme for typical launches but not categorically impossible, especially for tokens whose LT has a very low per-unit exchange rate (the very condition the existing `ExchangeRateTooLow` check is calibrated against, but only for the curve's own contribution). The precondition is entirely reachable by a single unprivileged wallet using only permissionless calls (`pair.mint` on the pre-created V2 pair, then waiting for the target token to graduate), matching the report's "unrelated wallet"-reachable class. Likelihood is best characterized as low-to-moderate given the capital bar, but the code path itself contains no mitigating check at all.

### Recommendation
Before any deposit in `_seedRebalancing`/`_pairRebalance`/`_seedDirectMint`, read the pair's live reserves and explicitly verify that `reserveToken + tokensForLP <= type(uint112).max` and `reserveLT + ltFromPair + (any rebalance-swap delta) <= type(uint112).max`, reverting (or routing to a safe abort/rescue path) if either would overflow. Alternatively, cap the total amount ever deposited into the V2 pair (curve contribution plus any pre-existing reserve) rather than only bounding the curve's own `virtualLtReserve` at launch time in isolation.

### Proof of Concept
1. Attacker observes a token nearing graduation (or launches a token themselves with a low-`exchangeRate` LT that passes `ExchangeRateTooLow`, maximizing headroom for `virtualLtReserve` near `type(uint112).max/4`).
2. Attacker calls `IUniswapV2Factory.createPair(token, lt)` (or lets `_ensureUniswapV2Pair` create it) and then `pair.mint(attacker)` after transferring a large LT balance sized at roughly `type(uint112).max - 3*virtualLtReserve` directly to the pair — an ordinary permissionless V2 deposit, establishing Regime 3 in `_seedRebalancing`.
3. The target token's curve later crosses the graduation threshold (via normal `Zap.buy`/`triggerGraduation`), and `finalizeGraduation` is called (by anyone/keeper).
4. `_seedUniswapV2Direct` → `_seedRebalancing` computes the deposit against the attacker's inflated `reserveLT` without checking the combined total against `type(uint112).max`; `_pairRebalance`'s swap and the subsequent `router.addLiquidity`/`pair.mint` push the pair's true LT balance above `2**112 - 1`.
5. The pair's `_update` (standard V2 semantics) stores `uint112(balance)`, wrapping the recorded reserve to a small value while the pair's actual LT balance remains enormous.
6. Attacker immediately swaps against the corrupted (small) recorded reserve, extracting TOKEN/LT at a heavily mispriced rate, draining value that `LPLock` has already permanently locked via the one-shot `recordLock` call: [3](#0-2)
