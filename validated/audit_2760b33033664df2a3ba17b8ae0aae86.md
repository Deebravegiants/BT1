### Title
Webhook shop identity spoofing — HMAC signs only the body, not the `shop-domain` header (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) for a webhook exclusively from the `X-Shopify-Shop-Domain` HTTP header, but the HMAC signature that `Registry.process` validates only covers the raw request body. The `shop` field that the host application's handler acts on is not bound by the cryptographic check that is supposed to authenticate the request's origin.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Registry.process` validates the webhook solely against that signable string via `Utils::HmacValidator.validate(request)`, then passes `request.shop` — read straight from the `x-shopify-shop-domain`/`shopify-shop-domain` header — into the handler as authoritative tenant identity: [2](#0-1) 

`Request#shop` is a pure header read with no cryptographic or contextual binding to the HMAC: [3](#0-2) 

`HmacValidator.validate` computes `HMAC(secret, to_signable_string)` and compares it against the `hmac` header using `OpenSSL.secure_compare`: [4](#0-3) 

The equality the code is supposed to enforce is:
`shop_the_HMAC_authenticates == shop_the_handler_acts_on`

In reality the code enforces only:
`HMAC(secret, raw_body) == received_hmac`  (a body-integrity check)

and separately trusts:
`shop_the_handler_acts_on = header["x-shopify-shop-domain"]` (unauthenticated)

Because many webhook topics carry an empty or content-independent body (e.g. `app/uninstalled`, `shop/redact`, and other GDPR/lifecycle topics commonly send `{}` or a small fixed-shape payload), the same `(raw_body, hmac)` pair that Shopify legitimately delivers to *shop A* remains cryptographically valid when replayed with the `shop-domain` header changed to *shop B*. Any merchant/attacker who installs the app on their own store (a completely unprivileged action) legitimately receives real webhooks — real body, real valid HMAC computed with the app's true `api_secret_key` — for their own shop. They can then replay that exact body+HMAC pair to the app's public webhook endpoint while substituting an arbitrary victim shop domain in the header, and `HmacValidator.validate` will still return `true`, because the header is never part of the signed content.

This breaks the identity binding the webhook mechanism is meant to guarantee: the HMAC only proves "this body was signed by Shopify with our secret," not "this body was signed by Shopify **for this specific shop**." A handler that trusts `request.shop` (e.g., to deactivate a shop's session, mark it uninstalled, purge/redact its data, or update per-shop billing/subscription state) can be triggered against an arbitrary victim shop by an attacker who never needed the `api_secret_key` — they only needed to observe/replay their own legitimate low-information-content webhook.

### Impact Explanation
This is a cross-tenant action: an unprivileged internet user (any merchant who can install the app on a free/dev store) can cause the host application to execute shop-lifecycle logic (uninstall handling, data redaction, session/token invalidation, etc.) attributed to a shop they do not control, purely by controlling the unauthenticated header while reusing a validly-signed, low-entropy body. This matches the Critical "cross-tenant access" impact category — no access token, `client_secret`, or privileged account is required, only the ability to install the app on one's own store and issue a raw HTTP POST to the webhook endpoint.

### Likelihood Explanation
Likelihood is bounded by whether a given webhook topic's body is shop-independent (fixed/empty payload) — which is common for several lifecycle/compliance topics — and by whether the host application's webhook handler uses `WebhookMetadata#shop` to perform a security- or tenant-sensitive action (the gem provides this field specifically so handlers can do exactly that). Any app relying on `data.shop` from the handler callback for per-tenant authorization is exposed.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) as part of the signable content, or otherwise cryptographically bind the declared `shop` header to the validated payload before it is handed to application handlers — e.g., by including `shop-domain` in `to_signable_string`, similar to how Shopify's regular webhook verification is documented to operate on the full raw body but should be paired with out-of-band shop verification (looking up the shop by installation record rather than trusting the header value alone). At minimum, `Registry.process` should cross-check `request.shop` against a shop known to have an active installation/session before dispatching to handlers, rather than passing the raw header value through unchecked.

### Proof of Concept
1. Install the target app on an attacker-controlled development store `attacker-shop.myshopify.com`.
2. Trigger a webhook topic with a fixed/empty body shape (e.g. `app/uninstalled`), capturing the legitimately delivered `raw_body` and `X-Shopify-Hmac-Sha256` header — both valid and signed with the real `api_secret_key`.
3. Replay this exact `raw_body` + `hmac` header to the app's public webhook endpoint, but change `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` against `request.to_signable_string` (the body only) — validation succeeds.
5. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", ...)` and performs shop-lifecycle logic against the victim shop it never legitimately owns: [2](#0-1)
