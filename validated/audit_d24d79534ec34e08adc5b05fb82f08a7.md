### Title
Unrestricted swap routes can turn a signed strategy call into unauthorized wallet-token transfers - (File: contracts/controller/src/strategies/swap.rs)

### Summary
XOXNO strategy entrypoints accept caller-supplied route bytes and execute the configured router while the account owner’s `require_auth` authorization is active. Because route pool addresses are not restricted to trusted venues, a malicious route can invoke an attacker contract that requests a token transfer from the victim. Soroban records that transfer as a child of the victim’s signed strategy authorization; if the victim signs the simulated tree, the attacker receives funds unrelated to the swap.

### Finding Description
`swap_collateral` accepts an arbitrary `swap: Bytes` argument after authenticating `caller` and verifying that it owns or delegates `account_id` [1](#0-0) [2](#0-1) . The shared swap helper invokes `router.execute_strategy(controller, amount_in, swap)` after granting the controller only the exact input-token transfer authorization [3](#0-2) .

The router decodes the caller-provided payload and dispatches each swap hop to the pool address embedded in that payload [4](#0-3) [5](#0-4) . There is no production-code check that `hop.pool` belongs to a governance-approved venue contract [6](#0-5) .

A malicious pool can therefore call `token.transfer(victim, attacker, amount)`. Since the victim’s authorization for the controller strategy remains on the call stack, simulation records the unrelated transfer as a child of the victim’s `swap_collateral` authorization [7](#0-6) . In enforcing mode, the transfer executes when the signed tree contains that child [8](#0-7) .

The same route argument reaches the vulnerable helper through `multiply`, `swap_debt`, `swap_collateral`, and `repay_debt_with_collateral`; `swap_collateral` is the simplest path because it operates directly on the victim’s existing collateral.

### Impact Explanation
A malicious route can steal any token for which the victim signs the poisoned authorization child, including a token that XOXNO never listed. The harness demonstrates theft of the victim’s entire unrelated wallet-token balance while the strategy still returns fair collateral output and passes settlement checks [9](#0-8) .

This is theft of user funds rather than bad swap execution: the measured input and output can both be correct, the account can remain solvent, and the malicious transfer still succeeds as an additional authorization-tree child.

### Likelihood Explanation
Exploitation requires social engineering or a compromised route provider to make the victim submit a malicious route and sign the resulting authorization tree. No protocol privilege, leaked key, oracle manipulation, or controller-admin action is required.

The requirement for the victim to sign the extra authorization child reduces likelihood, but ordinary clients commonly obtain opaque route XDR and simulated authorization trees from off-chain services. The controller’s exact input-transfer authorization bounds only the controller’s own grant; it does not bound unrelated `victim.require_auth` children introduced by route-selected code [10](#0-9) . This is a Medium-severity, user-interaction-dependent theft path.

### Recommendation
Restrict route pool addresses to a governance-maintained registry of known venue contracts and reject routes containing any other address. Apply the restriction to every venue operation that can invoke pool-supplied code, including swap, mint, and burn operations.

Until venue addresses are constrained, clients must decode the complete route payload and reject any simulated authorization tree containing children beyond the expected strategy invocation and controller’s exact token pull. Preferably, expose a route-integrity commitment and have wallets display every requested token transfer before signing.

### Proof of Concept
1. The victim owns a debt-free account with supplied USDC and also holds an unrelated wallet token that the protocol does not list.
2. The attacker deploys a malicious “pool” contract whose swap function executes:
   `wallet_token.transfer(victim, attacker, victim_balance)`.
3. The attacker creates route bytes for `swap_collateral` naming that malicious contract as a hop pool while arranging a fair output so all measured swap checks pass.
4. The victim is induced to call:
   `swap_collateral(caller=victim, account_id=victim_account, current=USDC_market, amount=swap_amount, new=ETH_market, swap=malicious_route)`.
5. The controller authenticates the victim and calls the configured router; the router invokes the malicious pool from the route [3](#0-2) [5](#0-4) .
6. Simulation records `wallet_token.transfer(victim → attacker, victim_balance)` as a child of the victim’s `swap_collateral` authorization [11](#0-10) .
7. If the victim signs that simulated tree, enforcement accepts the child transfer: the victim’s wallet-token balance becomes zero, the attacker receives the full balance, and the strategy deposits the expected ETH output [8](#0-7) .

fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
