This is the exact identity-binding break the task targets.### Title
Shop-Domain Header Not Covered by Webhook HMAC Enables Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values are read directly from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` validates only that HMAC-over-body and then forwards the header-derived `shop` value to the host application's handler as the trusted tenant identifier, breaking the intended binding `shop_verified == shop_delivered_to_handler`.

### Finding Description
`Utils::HmacValidator.validate` recomputes the signature from `verifiable_query.to_signable_string` and compares it to `verifiable_query.hmac`: [1](#0-0) 

For webhooks, `to_signable_string` returns only the raw request body, and `hmac` is read from the `hmac-sha256` header, while `shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from headers with no involvement in the signed string: [2](#0-1) 

`Registry.process` performs the HMAC check with `Utils::HmacValidator.validate(request)` (which only proves the body was signed by someone possessing `api_secret_key`), and — without any further verification of the `shop` header — hands `request.shop` straight to the host app's handler as the webhook's tenant identity: [3](#0-2) 

The documented API explicitly states that `Registry.process` "will verify the request did indeed come from Shopify" and that the resulting `data.shop` is "The shop domain of the webhook," implying to gem consumers that this field is authenticated: [4](#0-3) [5](#0-4) 

**Identity binding broken (as an equality):**
`hmac_valid_for(body)` ⇒ (incorrectly implies) `shop_header == originating_shop`

In reality, `hmac_valid_for(body)` only proves the body bytes were signed with `api_secret_key`; it says nothing about which shop that body came from, because the shop identity travels in an unsigned header.

**Attack path:** An attacker who operates their own (legitimate) installed instance of the merchant's app on their own store can trigger webhook deliveries to the app's registered endpoint and capture a valid `(raw_body, x-shopify-hmac-sha256)` pair signed with the app's real `api_secret_key` (this requires no privileged access — it is exactly what Shopify itself sends to any store owner who installs the app). The attacker then replays that exact body+HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` still passes (it only checks the body), and `Registry.process` forwards the spoofed `shop` value to the handler, causing the host application to process/attribute the event as belonging to the victim tenant.

### Impact Explanation
This crosses the Critical "cross-tenant access" bar: an unprivileged attacker (a legitimate installer of the app on their own store) can cause the host application to believe a webhook payload originated from a different, unrelated merchant's shop. Depending on how the host app uses `data.shop` (e.g., to look up the session/access token for that shop, update per-shop billing/state, or trigger per-shop side effects), this enables cross-tenant data confusion or state corruption without needing the victim's credentials.

### Likelihood Explanation
Likelihood is High for any app relying on the documented `data.shop` contract, because:
- Obtaining a valid `(body, hmac)` pair requires no privileged access beyond installing the app on one's own store (a normal, allowed action).
- The gem itself performs no cross-check between the signed body and the header-derived `shop`, `topic`, or `webhook_id`.
- The vulnerable code path (`Registry.process` → `HmacValidator.validate` → handler dispatch with `request.shop`) is the exact, documented, intended usage pattern shown in `docs/usage/webhooks.md`, so no misuse or ignoring of the API is required to trigger it.

### Recommendation
Include the shop domain (and ideally topic/webhook id/api version) inside the signed material, or otherwise cryptographically bind the header-derived identity fields to the signed body before the HMAC check is considered to authenticate them. At minimum, update `Utils::HmacValidator.validate`/`Webhooks::Request#to_signable_string` so the signature check covers the `shop-domain` header value (concatenated with the body, in a canonical, unambiguous encoding), and update the docs to clarify what exactly the HMAC check guarantees if this cannot be changed for backward-compatibility reasons.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (legitimate, unprivileged action) and triggers a webhook event (e.g. `orders/create`).
2. Attacker captures the raw POST body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)` — this signature is valid and app-secret-authentic.
3. Attacker sends a new HTTP request to the app's webhook endpoint with:
   - Body: `B` (unchanged)
   - Headers: `x-shopify-hmac-sha256: H` (unchanged), `x-shopify-topic: orders/create` (unchanged), `x-shopify-shop-domain: victim-shop.myshopify.com` (changed)
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: spoofed_headers)` is constructed; `hmac` returns the decoded `H`, `to_signable_string` returns `B`.
5. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC-SHA256(api_secret_key, B)` and finds it equal to `H` — validation **passes**.
6. The handler is invoked with `WebhookMetadata` where `shop == "victim-shop.myshopify.com"`, even though the event actually originated from `attacker-shop.myshopify.com`. [6](#0-5) [7](#0-6)

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
