This confirms the design: `Registry.process` is documented to "verify the request did indeed come from Shopify" via a single HMAC check, and the returned `data.shop` (from an unauthenticated header) is handed directly to the app's handler as the trusted tenant identifier — this is exactly the "bytes verified versus bytes parsed" / "shop authenticated versus shop stored as identifier" analog called out in the rules.

### Title
Webhook HMAC only covers the request body, not the `shop-domain`/`topic` headers, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop` and `topic` are read directly from unauthenticated HTTP headers (`x-shopify-shop-domain`, `x-shopify-topic`) with no cryptographic binding to those values [2](#0-1) . `Utils::HmacValidator.validate` only checks the signature against `to_signable_string`, i.e. the body bytes [3](#0-2) . `Registry.process` then trusts `request.shop` and `request.topic` verbatim once the body HMAC passes, forwarding them to the app's handler as the tenant identifier [4](#0-3) .

### Finding Description
The binding that should hold is: `shop authenticated-by-HMAC == shop delivered-to-handler`. In this gem those are two different things — the HMAC authenticates only the raw body bytes, and `shop` (and `topic`) are parsed from headers that carry no signature coverage at all. Any request whose body+HMAC pair is valid for the app's shared secret will pass `HmacValidator.validate`, regardless of what `x-shopify-shop-domain` or `x-shopify-topic` header values accompany it.

Because Shopify apps typically register one shared webhook callback URL for all installed shops (the `path` given to `add_registration` is per-topic, not per-shop) [5](#0-4) , a merchant who installs the app on their own store legitimately receives real, validly-signed webhook deliveries (body + HMAC) addressed to that shared endpoint. That merchant — an unprivileged internet user with respect to any other tenant — can capture one such legitimate `(raw_body, hmac)` pair and replay it to the same endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` still succeeds because it never inspected the header, and `Registry.process` calls the handler with `WebhookMetadata.new(shop: request.shop, ...)` pointing at the victim shop [6](#0-5) . The `topic` header can be forged the same way to route the replayed body to a different (unintended) handler.

### Impact Explanation
Downstream host applications are documented to key their tenant-specific logic directly off `data.shop` from the handler callback (e.g., looking up the shop's session, enqueuing shop-scoped jobs) [7](#0-6) . Since the gem asserts (via its documented `process` contract) that this value has been verified to "come from Shopify" [8](#0-7)  when in fact only the body bytes were verified, a forged `shop` value crosses the tenant boundary — the host app processes attacker-supplied data as if it belonged to a shop the attacker does not control. This matches the "cross-tenant access" High/Critical impact category.

### Likelihood Explanation
Exploitation requires only: (1) installing the target app on any Shopify store (an unprivileged, self-service action available to any internet user for public apps), (2) triggering a webhook event on that store to obtain one legitimately-signed `(body, hmac)` pair, and (3) resending that exact byte-for-byte body with the real HMAC to the app's shared webhook endpoint while swapping the `shop-domain`/`topic` headers. No knowledge of `api_secret_key` or any victim credential is needed, since the HMAC being replayed was never generated over those headers in the first place.

### Recommendation
Bind `shop` (and ideally `topic`) into the value that is HMAC-verified, or independently cross-check the header-derived `shop` against the shop the app expects to be receiving webhooks for at that specific registered path/session before invoking the handler, rather than treating the raw-body-only HMAC check as authenticating the header-derived identifiers.

### Proof of Concept
1. Install the target app on `attacker-shop.myshopify.com`; trigger `orders/create` to receive a legitimate webhook: body `B`, header `x-shopify-hmac-sha256: H` (valid for `B` under the app's shared secret), `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Resend to the same app webhook endpoint: body `B` (unchanged), `x-shopify-hmac-sha256: H` (unchanged), `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Utils::HmacValidator.validate(request)` returns `true` because it only checks `H` against `B` [9](#0-8) .
4. `ShopifyAPI::Webhooks::Registry.process` invokes the registered handler with `data.shop == "victim-shop.myshopify.com"` [10](#0-9) , even though the payload actually originated from the attacker's own shop.
