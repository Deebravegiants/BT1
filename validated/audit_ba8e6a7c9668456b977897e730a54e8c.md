### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/registry.rb`, `lib/shopify_api/webhooks/request.rb`)

### Summary
This is the same "double binding" flaw described in the external report: an attribute that is *used* by the code (the collateral token address, in the Solidity report) is not the same attribute that was *checked* (the position's stored collateral token). In this gem, `ShopifyAPI::Webhooks::Registry.process` uses the `shop` value taken from an HTTP header to attribute an incoming webhook to a tenant, but the cryptographic HMAC that authenticates the request only covers the raw body, never the `shop` header. The two "identities" — the header value used downstream and the bytes actually verified — are not bound together.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

The `shop` accessor is derived independently from the `shopify-shop-domain` / `x-shopify-shop-domain` header, and is never included in the signed payload: [2](#0-1) 

`Registry.process` validates only that the HMAC over the raw body is correct, then immediately trusts `request.shop` (and `request.topic`, `request.webhook_id`, `request.api_version`) to build the `WebhookMetadata` that is handed to the app's handler: [3](#0-2) 

`HmacValidator.validate` computes and compares the HMAC solely against `verifiable_query.to_signable_string`, i.e. the raw body — it has no knowledge of, and does not defend, the `shop` header: [4](#0-3) 

The identity binding that should hold is:
`HMAC-verified bytes == bytes that determine the tenant attribution ("shop")`

but the gem instead enforces:
`HMAC-verified bytes == raw body only`, while `shop attribution == unauthenticated header value`

Because the shared app secret (`api_secret_key`) is the same for every shop that installs the app, any two shops receive HMACs computed with the identical secret. A merchant who operates their own installation of the app (an ordinary, unprivileged app user — not a privileged Shopify employee) legitimately receives (or can trigger and observe, e.g. via their own webhook endpoint or network logs) a `(raw_body, hmac)` pair that Shopify signed with the app's secret for their own shop's event. Nothing in this gem prevents that same `(raw_body, hmac)` pair from being replayed to the app's webhook endpoint with the `x-shopify-shop-domain` header rewritten to a victim shop's domain: `HmacValidator.validate` will still pass, because it never inspects the header, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the event came from the victim shop.

### Impact Explanation
This breaks the tenant boundary the webhook signature is supposed to enforce. Any host application that uses `request.shop` from `WebhookMetadata` to select which merchant record/session/data to update (the documented and expected usage pattern) can be made to apply an attacker-controlled, attacker-signed event to another tenant's data — a cross-tenant access/write primitive achieved purely through this gem's own webhook verification API, without needing the victim's access token, `api_secret_key`, or any privileged access. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
The attacker only needs: (1) to be an ordinary merchant with the target app installed on their own shop, and (2) the ability to trigger or capture a webhook delivery to their own endpoint (both entirely within normal, unprivileged use of any app built on this gem's webhook feature). No secret material, TLS interception, or social engineering is required — only that the vulnerable binding (`HMAC` over body only, `shop` unauthenticated) is exactly what `Registry.process`/`HmacValidator` implement.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) header value in the signed content that `HmacValidator` verifies, or otherwise cryptographically bind the declared `shop` to the HMAC-covered bytes before it is exposed via `WebhookMetadata`. At minimum, document and/or enforce that `request.shop` must never be trusted as tenant-identifying data unless it is itself covered by the HMAC.

### Proof of Concept
1. App installs on `attacker-shop.myshopify.com` and `victim-shop.myshopify.com`, both signed with the same `api_secret_key`.
2. Attacker triggers an event on their own shop (e.g. `orders/create`) and captures the resulting webhook delivery: raw body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
3. Attacker (or anyone who can reach the app's webhook endpoint) resends an HTTP request to the app's webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H` unchanged, but `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` accepts the headers (no header/shop binding check): [5](#0-4) 
5. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only re-computes the HMAC over `B` (the raw body) and compares to `H` — a match, since `H` was legitimately generated for `B`: [6](#0-5) 
6. The registered handler for that topic is invoked with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: <attacker's data>, ...)`, i.e. the host application processes attacker-controlled data under the victim's tenant identity.

      def initialize(raw_body:, headers:)

        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
