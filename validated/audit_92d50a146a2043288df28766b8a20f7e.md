### Title
Torn (non-atomic) read of destination `StateCommitment` fields in `query_state_machine_commitment` causes spurious veto of valid state commitments - ([File: tesseract/messaging/evm/src/provider.rs])

### Summary
The Bitcoin analog fixes a "corrupt rest response" caused by combining a block height and block hash from two separate, un-synchronized reads of the chain tip (`rest_getutxos`). The Hyperbridge analog is `EvmClient::query_state_machine_commitment` in `tesseract/messaging/evm/src/provider.rs:116-156`, which builds a single logical `StateCommitment` (`timestamp`, `overlay_root`, `state_root`) out of three independent `eth_getStorageAt` RPC calls, each anchored with `BlockId::latest()` rather than a pinned block number. Because `BlockId::latest()` is resolved server-side on every individual RPC round-trip, the three fields can be read from three different underlying blocks if the destination chain progresses between the awaits — a torn/inconsistent combined read, structurally identical to the Bitcoin `rest_getutxos` bug where height and hash were pulled from unrelated, non-atomic reads.

### Finding Description
`query_state_machine_commitment` computes storage keys for `timestamp`, `overlay_root`, and `state_root` for a given `StateMachineHeight`, then issues three sequential, separately-awaited `get_storage_at(...).block_id(block)` calls: [1](#0-0) 

`block` is a local variable holding `BlockId::latest()`, but this "latest" tag is not a pinned block number — it is a symbolic marker sent to the RPC node with each request and resolved independently by the node at request time: [2](#0-1) 

If a new block lands on the destination chain between any of these three awaited RPC calls, the resulting `StateCommitment` mixes fields from different blocks (e.g., `timestamp` from block N, `overlay_root` from block N, `state_root` from block N+1), producing a value that never actually existed as a single on-chain commitment — exactly the "corrupt response" pattern the Bitcoin patch fixes for `rest_getutxos` (there, height/hash pulled from two non-atomic calls to `chainman.ActiveChain()`).

This torn value is consumed directly by the byzantine-detection path used by the relayer to decide whether to veto a state commitment: [3](#0-2) 

`recorded` (the torn commitment) is compared field-by-field against `first` (the unanimous quorum header from independent byzantine providers). Any inconsistency between the torn `state_root`/`timestamp` and the quorum-observed header triggers `counterparty.veto_state_commitment(height)`, which is wired through to the on-chain `deleteStateMachineCommitmentInternal`, permanently removing the state commitment for that height: [4](#0-3) 

Once vetoed, any post/get request whose proof depends on that height's overlay root can no longer be delivered (`handlePostRequests` requires `stateMachineCommitment(...).overlayRoot != 0`): [5](#0-4) 

### Impact Explanation
A torn read causes the relayer's automated byzantine check to spuriously flag a perfectly valid, honestly-produced state commitment as fraudulent and veto it via `deleteStateMachineCommitmentInternal`, which unconditionally deletes the stored commitment (state root, overlay root, timestamp) for that height. This freezes in-flight messages whose delivery proofs are anchored to that height — `handlePostRequests`/get-response verification will revert with `StateCommitmentNotFound` once the overlay root is wiped, and no replacement commitment for the exact same height can ever be produced again (the height has already been finalized/passed by the destination chain). This is a form of permanent freezing of message delivery (and any escrowed funds/intents gated on that delivery) triggered purely by ordinary block production timing, without any attacker action — reachable automatically any time the destination chain produces a block between the three RPC calls.

### Likelihood Explanation
Likelihood is timing-dependent but not exotic: `query_state_machine_commitment` is invoked automatically by the relayer's `check_for_byzantine_attack` flow on every `StateMachineUpdated` event it observes, with no special privilege required to trigger the underlying state update (any relayer submitting a legitimate consensus/state update causes this check to run). Three sequential unpinned "latest" RPC calls racing against the destination chain's normal block production (often sub-second to a few seconds on L2s/EVM chains) makes torn reads a realistic, recurring occurrence rather than a purely theoretical one, especially under load or on fast-block chains.

### Recommendation
Pin all three storage reads to the exact same, explicit block number rather than the symbolic `BlockId::latest()`:
1. Resolve the block number once via `self.client.get_block_number().await?` (or accept an explicit `at` parameter like `query_storage` already does), then use `BlockId::number(pinned)` for all three `get_storage_at` calls.
2. Alternatively, batch the three storage reads into a single multicall/`eth_getProof` request so they are guaranteed to be evaluated against one block.
3. Apply the same pinning discipline to any other provider method that combines multiple sequential RPC reads into one logical on-chain struct under `BlockId::latest()`.

### Proof of Concept
1. Destination EVM chain is producing blocks at normal cadence (e.g., every 2s).
2. Relayer observes a `StateMachineUpdated` event and invokes `check_for_byzantine_attack`, which calls `counterparty.query_state_machine_commitment(height)`.
3. Inside `query_state_machine_commitment` (`tesseract/messaging/evm/src/provider.rs:132-150`):
   - Call 1 (`timestamp_key`) executes against block N (current "latest" at call time).
   - A new block N+1 lands on the destination chain during the `.await`.
   - Call 2 (`overlay_key`) and/or Call 3 (`state_root_key`) execute against block N+1, whose overlay/state root differs from block N's (e.g., because storage was updated again by a subsequent handler call).
4. The returned `StateCommitment` now combines `timestamp`/root fields that never co-existed in a single block.
5. Back in `byzantine.rs:174-193`, this torn `recorded` commitment is compared to `first` (quorum-verified header for the *intended* height); the mismatch triggers `counterparty.veto_state_commitment(height)`.
6. `veto_state_commitment` reaches `EvmHost.deleteStateMachineCommitmentInternal` (`evm/src/core/EvmHost.sol:704-732`), which deletes the legitimate commitment and its overlay root, permanently blocking delivery of any post/get requests proven against that height.

    /**
     * @dev Delete the state commitment at given state height.
     */
    function deleteStateMachineCommitmentInternal(StateMachineHeight memory height, address fisherman) internal {
        StateCommitment memory stateCommitment = _stateCommitments[height.stateMachineId][height.height];
        delete _stateCommitments[height.stateMachineId][height.height];
        delete _stateCommitmentsUpdateTime[height.stateMachineId][height.height];
        // technically any state commitment can be vetoed, safety check that it's the latest before resetting it.
        if (_latestStateMachineHeight[height.stateMachineId] == height.height) {
            _latestStateMachineHeight[height.stateMachineId] = 1;
        }

        // track the fisherman responsible for rewards on hyperbridge through state proofs
        _vetoes[height.stateMachineId][height.height] = fisherman;

        emit StateCommitmentVetoed({
            stateMachineId: this.stateMachineId(_hostParams.hyperbridge, height.stateMachineId),
            stateCommitment: stateCommitment,
            height: height.height,
            fisherman: fisherman
        });
    }
