### Title
Same-asset batch withdrawals resolve to a single POA withdrawal record, causing status/tx-hash misreport across distinct withdrawals - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts, packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts)

### Summary
`describeWithdrawal()`/`waitForWithdrawalCompletion()` identify which POA-bridge withdrawal record in an API response corresponds to a specific withdrawal *only by `assetId`*, ignoring the `index` that is supposed to disambiguate multiple withdrawals created in the same NEAR transaction. When a single transaction contains two or more withdrawals of the same token, every one of them resolves to the same (first) matching record, so distinct withdrawal legs are reported with the same status and the same destination `tx_hash`.

### Finding Description
`createWithdrawalIdentifier()` builds a `WithdrawalIdentifier` that carries an `index` meant to distinguish multiple withdrawals batched in one NEAR tx [1](#0-0) . However `describeWithdrawal()` never uses `args.index`; it calls `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`, which does `withdrawals.find(w => nep141:${w.data.near_token_id} === assetId)` [2](#0-1) [3](#0-2) . `Array.prototype.find` always returns the *first* element satisfying the predicate, so if the API response contains two withdrawal records for the same `near_token_id` (i.e., two withdrawals of the same asset were batched into one NEAR transaction), both `describeWithdrawal` calls — one for index 0, one for index 1 — return the identical record, identical `status`, and identical `transfer_tx_hash`.

The same defect exists in the parallel implementation used for the lower-level completion-waiting flow, `waitForWithdrawalCompletion()`'s `findMatchingWithdrawal()`, which matches purely on `assetId` criteria with no index/ordering discrimination [4](#0-3) .

The code comments explicitly acknowledge the limitation ("multiple withdrawals of the same token in a single transaction are not supported") but the callers do not enforce or guard against that scenario — nothing prevents a caller from constructing a batch with two same-asset withdrawals, and the SDK will silently report a completed status/hash for both.

This breaks the equality that "status/tx-hash reported for withdrawal N equals the on-chain outcome for withdrawal N": one physical destination-chain transfer gets falsely projected onto every same-asset withdrawal leg in the batch.

### Impact Explanation
An integrator relying on `describeWithdrawal`/`waitForWithdrawalCompletion` per withdrawal index to decide when to mark an order fulfilled, release custody, or credit an off-chain ledger would see two (or more) independent withdrawal requests marked `"completed"` with the *same* destination tx hash, even though only one on-chain transfer actually occurred. This matches the "status or hash misreport making an integrator credit or refund twice" impact class: the second (and any subsequent) same-asset withdrawal in the batch is falsely reported as delivered, potentially causing the integrator to release/credit funds for a withdrawal that was never actually paid out on the destination chain.

### Likelihood Explanation
This is triggerable by any unprivileged caller who batches two withdrawals of the same token/asset into a single NEAR transaction, which is a normal validated user action (nothing in `createWithdrawalIntents`/`validateWithdrawal` rejects duplicate-asset batches). No malicious relayer, bridge operator, or admin action is required — an ordinary user or an integrator's own batching logic can produce this state.

### Recommendation
Use `index` (or ordering by amount as the code comment suggests) to disambiguate multiple same-asset withdrawal records instead of matching by `assetId` alone; alternatively, explicitly detect and reject/flag batches containing multiple withdrawals of the same asset until the POA API supports per-withdrawal disambiguation, so that status is never reported for the wrong withdrawal leg.

### Proof of Concept
1. Construct and sign a NEAR transaction containing two `ft_withdraw`/POA-bridge withdrawal intents for the same `assetId` (e.g., `nep141:usdc.omft.near`) but different `destinationAddress`/amounts, indices 0 and 1.
2. The POA bridge processes and completes withdrawal index 1 first (destination tx hash `H`), while withdrawal index 0 is still pending/not yet broadcast.
3. Call `PoaBridge.describeWithdrawal({ index: 0, assetId, tx })` and `describeWithdrawal({ index: 1, assetId, tx })`.
4. Both calls invoke `findMatchingWithdrawal(response.withdrawals, assetId)`, which returns the same (first) record with `status: "COMPLETED"` and `transfer_tx_hash: H` for both indices — falsely reporting withdrawal index 0 as completed with hash `H`, even though it has not been settled on-chain.

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

/**
 * Finds a withdrawal matching the given criteria.
 *
 * NOTE: Currently only matches by assetId (near_token_id). This means multiple
 * withdrawals of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: types.WithdrawalStatusResponseOk["result"]["withdrawals"],
	criteria: WithdrawalCriteria,
):
	| types.WithdrawalStatusResponseOk["result"]["withdrawals"][number]
	| undefined {
	return withdrawals.find(
		(w) => `nep141:${w.data.near_token_id}` === criteria.assetId,
	);
}
