### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) identity fields are not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw request body only, while the `shop` attribute the gem hands to app handlers as the tenant identifier is read from an HTTP header that is never included in that signed content. Because Shopify signs webhooks with the app's single `client_secret` — shared across every shop that installs the app — any shop that has installed the app can capture one of its own genuinely-signed webhook deliveries and replay it to the app's webhook endpoint with the `shop-domain` (and `topic`/`webhook-id`/`api-version`) header(s) altered, while the HMAC still validates because those headers are outside the signed data.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

but `shop`, `topic`, `webhook_id`, and `api_version` are all pulled from HTTP headers that are completely separate from that signed string: [2](#0-1) 

`Registry.process` validates the HMAC using `Utils::HmacValidator.validate(request)`, which internally calls `verifiable_query.to_signable_string` (i.e. the raw body) and compares it against the received signature — it never touches the headers: [3](#0-2) 

After that check passes, `Registry.process` builds `WebhookMetadata` directly from `request.shop` (the unauthenticated header) and hands it to the app's handler as the trusted tenant identifier: [4](#0-3) [5](#0-4) 

The identity binding that should hold is: `shop attributed to the webhook == shop whose bytes were actually HMAC-signed by Shopify`. Because the signature only covers `@raw_body`, this equality is never enforced — the header-derived `shop` is fully attacker-controllable independent of the signature. The gem's own documentation confirms this field is meant to be trusted as the tenant boundary for downstream processing: [6](#0-5) 

Since Shopify signs webhooks for all merchants of an app with the same `client_secret` (there is no per-shop signing key visible to this gem — `HmacValidator` always uses `Context.api_secret_key`/`Context.old_api_secret_key` globally), a webhook body+HMAC pair legitimately generated for attacker's own shop is cryptographically valid input for `Registry.process` regardless of which `shop-domain` header accompanies it.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for HTTP webhook processing: an unprivileged actor who has merely installed the app on their own shop (no special privileges, no stolen credentials) can trigger legitimate Shopify webhook deliveries to themselves, capture the raw body and HMAC, and resend the identical body/HMAC to the app's public webhook endpoint with a forged `shopify-shop-domain` header pointing at a victim shop. The app, trusting the gem's `WebhookMetadata#shop`, will process/act on that request as if it came from the victim tenant — e.g., writing attacker-controlled data into the victim's records, triggering redact/data-request flows for the wrong shop, or otherwise causing cross-tenant state corruption. This matches the Critical "cross-tenant access" impact category, since the attribution of an authenticated payload to a specific merchant is defeated entirely.

### Likelihood Explanation
Likelihood is high for any app relying on this gem's webhook processing as documented: the exploit requires only (1) installing the target app on an attacker-owned shop (a normal, unprivileged action any merchant can take) and (2) the ability to send an arbitrary HTTP request with custom headers to the app's public webhook endpoint, which by design must be internet-reachable to receive Shopify's webhook POSTs. No access to `client_secret`, tokens, or the target shop is required.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signed content, or otherwise cryptographically bind them to the signature (e.g., compute the HMAC over a canonical string containing both headers and body, mirroring the approach already used for `Auth::Oauth::AuthQuery#to_signable_string`, which signs `code`, `host`, `shop`, `state`, and `timestamp` together). At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must not be trusted without cross-checking it against out-of-band data (e.g., the shop embedded in the JSON body when available, or a per-shop registered webhook address).

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`.
2. Attacker triggers an event (e.g., updates an order) causing Shopify to POST a legitimately signed webhook to the app's registered endpoint, with headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC over raw body>`, and a JSON body.
3. Attacker intercepts this request (e.g., via a proxy they control, or by using a webhook debugging endpoint they own) and resends the exact same `raw_body` and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but with `x-shopify-shop-domain` changed to `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `OpenSSL::HMAC.hexdigest(sha256, Context.api_secret_key, raw_body)` against the header HMAC — this still matches because `raw_body` is unchanged.
5. `Registry.process` builds `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` and invokes the app's handler, which processes the attacker-controlled body as if it belonged to the victim shop.
