### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request body, then hands the caller-supplied `shop` header value — which is never part of the signed material — to the registered handler as the tenant identity. Any actor who can obtain one valid `(body, hmac)` pair for a webhook (e.g., an attacker who is themselves a merchant of the app and legitimately receives webhooks) can replay that exact body/HMAC to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain`/`shopify-shop-domain` header. The signature still validates because the header is outside the signed scope, so the handler processes the payload under a victim shop identity of the attacker's choosing.

### Finding Description
`HmacValidator.validate` computes and compares the HMAC purely against `verifiable_query.to_signable_string`: [1](#0-0) 

For webhook requests, `to_signable_string` returns only the raw HTTP body, not any headers: [2](#0-1) 

`shop` (the tenant identity) is read directly from an HTTP header that is completely excluded from the HMAC computation: [3](#0-2) 

`Registry.process` only checks the body HMAC via `Utils::HmacValidator.validate(request)`, and then forwards `request.shop` — the unauthenticated header value — straight into the `WebhookMetadata` passed to the handler: [4](#0-3) 

Because the api secret key (and hence the HMAC) is the same for every shop that installs a given app, any merchant that legitimately receives a webhook for their own shop obtains a valid `(raw_body, hmac)` pair. They can replay that identical body and HMAC to the endpoint while forging the shop-domain header to name a different, victim shop. The HMAC check passes (it never covered the shop field), and the host application — following this gem's documented contract that `WebhookMetadata#shop` is a trustworthy, HMAC-verified tenant identifier — will process/attribute the webhook data as belonging to the victim shop.

This breaks the equality the gem is expected to guarantee: `shop authenticated by HMAC == shop delivered to the handler`. Here the HMAC only authenticates `body`, while `shop` is taken from unauthenticated bytes.

### Impact Explanation
This is a cross-tenant identity confusion: an unprivileged attacker (any merchant who installed the app) can make the host application believe a webhook payload originates from an arbitrary victim shop. Depending on how the host app uses `WebhookMetadata#shop` (e.g., to select a tenant's DB record, session, or access token), this can lead to injecting attacker-controlled data into another merchant's tenant context — a cross-tenant access primitive, which the rules classify as Critical impact.

### Likelihood Explanation
Likelihood is high: the attacker only needs to be a legitimate merchant of the target app (unprivileged, no special access), capture one webhook body/HMAC pair sent to their own endpoint, and replay it with a modified shop header. No knowledge of `api_secret_key` or any access token is required, and the "gate" (`HmacValidator.validate`) is fully satisfied.

### Recommendation
Bind the tenant identity into the HMAC-verified material for webhooks — e.g., require host applications (or add gem-level support) to verify `request.shop` against a shop already known/authorized for the given webhook `topic`/subscription instead of trusting the raw header, or extend `to_signable_string` to incorporate the shop domain in a way that is cross-checked with Shopify's registered value for that HMAC. At minimum, document prominently that `request.shop` is NOT covered by the HMAC and must not be used as a trusted tenant key without independent verification.

### Proof of Concept
1. App merchant "attacker.myshopify.com" installs the app and receives a legitimate webhook: `POST /webhooks` with body `B` and header `x-shopify-hmac-sha256: H`, `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker replays: `POST /webhooks` with the same body `B`, same header `x-shopify-hmac-sha256: H`, but `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only — matches `H` — validation passes.
4. `Registry.process` invokes the registered handler with `WebhookMetadata.new(... shop: "victim.myshopify.com" ...)`, even though the payload actually originated from the attacker's own shop.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
