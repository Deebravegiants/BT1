### Title
Reentrancy in `IntentGatewayV2.withdraw()` allows repeated escrow drainage before accounting update - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
`withdraw()` in `evm/tron/contracts/apps/IntentGatewayV2.sol` violates checks-effects-interactions: it performs the external token/native transfer to `beneficiary` *before* decrementing `_orders[body.commitment][token]`. This is the same class of bug the mainline EVM contracts (`evm/src/apps/intentsv2/IntentsBase.sol`, `_withdraw`) and the dedicated reentrancy regression suite (`evm/tests/foundry/IntrinsicIntentsReentrancyTest.sol`) were explicitly hardened against — a resource ("escrowed funds") being referenced/used again after it should have been considered consumed, i.e. a stale-accounting-after-use bug analogous to a use-after-free (the escrow "object" is used by a second withdrawal before the first withdrawal's bookkeeping "frees" it).

### Finding Description
`withdraw()`:
```solidity
function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
    address beneficiary = address(uint160(uint256(body.beneficiary)));
    _filled[body.commitment] = beneficiary;

    uint256 len = body.tokens.length;
    for (uint256 i; i < len;) {
        address token = address(uint160(uint256(body.tokens[i].token)));
        uint256 amount = body.tokens[i].amount;
        if (_orders[body.commitment][token] == 0) revert UnknownOrder();

        if (token == address(0)) {
            (bool sent,) = beneficiary.call{value: amount}("");
            if (!sent) revert InsufficientNativeToken();
        } else {
            (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
            if (!success) revert TransferFailed();
        }

        _orders[body.commitment][token] -= amount;
        ...
``` [1](#0-0) 

The check `_orders[body.commitment][token] == 0` guards only against the token being fully spent — it does not check `>= amount`, and critically the decrement `_orders[body.commitment][token] -= amount` happens *after* the external interaction (native `.call{value:}` or `IERC20.transfer`). If `beneficiary` is a contract (native-token case) or the token itself is malicious/ERC-777-like/has callback hooks, the external call can re-enter before `_orders[...]` is decremented, allowing `withdraw()` to be invoked again for the same `body.commitment` while `_orders[commitment][token]` still reflects the pre-withdrawal balance.

This is the exact bug class the maintainers already fixed in the primary EVM contracts: `IntentsBase._withdraw` in `evm/src/apps/intentsv2/IntentsBase.sol` decrements `_orders[body.commitment][token]` *before* the external transfer [2](#0-1) , and `IntrinsicIntents`/`ExtrinsicIntents` were hardened to set `_filled[commitment]` before any external call precisely to block reentrant re-fills, as documented extensively in `evm/tests/foundry/IntrinsicIntentsReentrancyTest.sol` [3](#0-2) . The Tron port's `withdraw()` reintroduces the interaction-before-effects ordering that the mainline test suite was built specifically to prevent, and unlike `IntentsBase._withdraw`, it has no `_filled != 0` reentrancy guard blocking a second call to `withdraw()` on the same commitment mid-flight — `_filled[body.commitment] = beneficiary` is set unconditionally but never checked before proceeding to transfer.

`withdraw()` is reached from `onAccept()` (restricted `onlyHost`, driven by relayed `RedeemEscrow`/`RefundEscrow` messages) and `onGetResponse()` (cross-chain cancel-from-source flow) [4](#0-3) . Because the host records delivery receipts and the message layer generally prevents the identical `onAccept` call from being re-dispatched inside its own execution, the most direct exploitation vector is a native-token payout to a malicious `beneficiary` contract whose `receive()`/fallback re-enters a different externally reachable path that also flows into `withdraw()` for the same `commitment` (e.g., a second delivery/settlement path) before the first call's loop reaches the decrement for that token. Given multiple tokens can be escrowed per order (`body.tokens` array), and the loop transfers each token fully before decrementing, a reentrant call landing between the transfer and the decrement of an earlier index can re-claim balances for tokens whose decrements haven't executed yet within the same `withdraw()` invocation, and — if any externally-reachable path can be triggered to call `withdraw()` again for the same commitment (e.g. via a second, still-unauthenticated corner of the message flow) — funds can be paid out more than once against the same escrow entry.

### Impact Explanation
This maps to concrete theft of escrowed bridge funds: an attacker (as `beneficiary`/order recipient or a controlled contract acting as beneficiary) can drain more tokens from the intent-gateway's escrow than were legitimately owed, directly costing users' or solvers' locked funds. This satisfies the "concrete theft ... of funds" bar in the validation criteria, reachable from a permissionless message settlement path (relayed RedeemEscrow/RefundEscrow or GET-response cancellation) rather than any admin/governance action.

### Likelihood Explanation
Medium-High: exploitation requires the beneficiary of a withdrawal to be a contract that can execute code on receipt of native token transfer (straightforward to arrange, since orders can specify arbitrary beneficiary addresses) and a re-entrant path back into `withdraw()` for the same commitment before its per-token decrement executes. The mainline EVM codebase's extensive reentrancy test suite (`IntrinsicIntentsReentrancyTest.sol`) shows this exact bug class was previously present and actively exploited/fixed elsewhere in the codebase, indicating it is a realistic, previously-identified risk pattern that was not carried over correctly into the Tron variant.

### Recommendation
Apply the same CEI fix used in `IntentsBase._withdraw`: decrement `_orders[body.commitment][token]` (and clear `TRANSACTION_FEES`) *before* performing the external native/ERC20 transfer in `evm/tron/contracts/apps/IntentGatewayV2.sol::withdraw()`. Additionally, consider adding an explicit reentrancy guard (e.g., checking that `withdraw()` cannot be invoked twice for the same commitment while still mid-execution, or using `nonReentrant`), consistent with the pattern of setting `_filled` first and treating it as an authoritative guard, as done in the fixed `IntrinsicIntents`/`ExtrinsicIntents` fill paths.

### Proof of Concept
Not independently executable within this review (no code execution tooling available); the vulnerable ordering is directly visible in the source at [1](#0-0) , and the exploit shape mirrors the already-documented and tested attack in `evm/tests/foundry/IntrinsicIntentsReentrancyTest.sol` (`testReentrancy_FeeTheft`, `testReentrancy_EscrowTheft_MultiOutput`), which demonstrates the identical "transfer native token to attacker-controlled beneficiary before finalizing escrow accounting" pattern against the (already-fixed) mainline EVM contracts. A concrete PoC for the Tron contract would deploy a malicious `beneficiary` contract with a `receive()` hook that re-enters a second withdrawal-triggering path for the same `commitment` before `_orders[...]` is decremented, then verify the total tokens paid out exceed the original escrowed amount.

**Note on confidence:** I was not able to fully trace which externally-reachable second path (if any, beyond `onAccept`/`onGetResponse`) could be triggered mid-reentrancy to call `withdraw()` a second time for the *same* commitment within the Tron contract in the time available — this is the key gap needed to fully prove exploitability versus a merely unsafe pattern. I recommend a Devin session with the ability to compile/run the Foundry test suite against `evm/tron/contracts/apps/IntentGatewayV2.sol` to confirm reentrant double-payout end-to-end before treating this as fully confirmed.
