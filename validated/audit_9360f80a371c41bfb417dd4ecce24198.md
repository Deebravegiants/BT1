### Title
Webhook shop identity not bound to HMAC signature enables cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, but the `shop` identity that the application uses to route/attribute the webhook is taken from an unsigned HTTP header. This breaks the intended binding "shop verified == shop acted on," analogous to the reported flaw where a value that gates trust doesn't actually correspond to the value the code later relies on.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` values are all read from separate, unauthenticated HTTP headers: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over `to_signable_string` (i.e., the body) and compares it against the `hmac` value, also taken from a header: [3](#0-2) 

`Registry.process` treats a passing HMAC check as proof the whole request — including `request.shop` — is authentic, then forwards `request.shop` directly to the application's webhook handler as the tenant identifier: [4](#0-3) 

Because `shop` is never covered by the HMAC, the equality the library implicitly claims — `hmac_valid(body) == shop_header_is_authentic` — does not hold. Anyone who has legitimately received one real webhook (e.g., any merchant with the app installed) has a valid `(raw_body, hmac)` pair signed with the shared `api_secret_key`. That same pair can be replayed to the app's public webhook endpoint with the `X-Shopify-Shop-Domain` header changed to a different, victim shop. `HmacValidator.validate` will still pass because it never inspects the shop header, and `Registry.process` will hand the handler `WebhookMetadata` carrying the attacker-chosen `shop` value alongside the replayed body.

### Impact Explanation
Applications commonly use `data.shop` (per the gem's own documented handler interface) to select which tenant's session/access token/database record to update: [5](#0-4) 

If the application trusts `data.shop` for tenant routing — which is exactly the intended and documented usage — an attacker (any store owner who installs the app, an "unprivileged" actor with respect to other tenants) can cause data belonging to their own shop's webhook to be attributed to, or overwrite state for, a different shop. This is a cross-tenant integrity issue: the library provides no mechanism to bind the verified body to the shop identity, and does not itself provide the safeguard (webhook shop being a member of the app's set of known/installed shops) that Shopify recommends implementing.

### Likelihood Explanation
Requires only that the attacker (1) install the target app on a shop they control, so they can trigger a real webhook and capture a valid `(body, hmac)` pair, and (2) send a forged HTTP POST to the app's public webhook endpoint with the shop header swapped. No access to `api_secret_key`, access tokens, or any privileged credential is needed — the shared secret is used to validate, not to forge, the payload, since the attacker reuses a signature Shopify itself produced for their own installation.

### Recommendation
- Bind the shop identity into the trust decision: either (a) require the caller to supply the expected/looked-up shop (from the app's own installed-shop store) and assert `request.shop == expected_shop` before invoking the handler, or (b) document and enforce that `WebhookMetadata#shop` must be cross-checked by the host application against its own shop/session store before being trusted for any tenant-scoped action.
- Consider incorporating the `shop` and `topic` headers into the value verified against the HMAC where feasible, or provide a library-level helper that performs the shop-membership check as part of `Registry.process`.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`, causing the app to register webhooks and to receive a real webhook POST with a valid `X-Shopify-Hmac-Sha256` header computed over the raw body using the app's shared secret.
2. Attacker captures the exact `raw_body` and `X-Shopify-Hmac-Sha256` value from that legitimate delivery.
3. Attacker sends a new POST to the same public webhook endpoint, keeping `raw_body` and `X-Shopify-Hmac-Sha256` identical, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only re-derives the HMAC from `raw_body` and succeeds, per: [6](#0-5) 
5. The handler is invoked with `WebhookMetadata.shop == "victim-shop.myshopify.com"` even though the body/content actually originated from the attacker's own shop, per: [7](#0-6) 

**Note on uncertainty:** This is a design characteristic shared with Shopify's real webhook HMAC scheme (HMAC over body only is the officially documented mechanism), so it may be considered "as designed" rather than a library defect; whether it counts as an in-scope vulnerability versus expected behavior that the host application must additionally guard against (by validating shop membership) is a judgment call I cannot fully resolve from the code alone.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
