### Title
Webhook `shop-domain` header is trusted for tenant identification but is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` exposes a `shop` accessor that is read directly from the unauthenticated `X-Shopify-Shop-Domain` HTTP header, but the HMAC signature verified by `Utils::HmacValidator.validate` only covers the raw request body. `Registry.process` passes this unauthenticated `shop` value straight into `WebhookMetadata`, which app-provided `WebhookHandler` implementations use to identify the tenant (shop) that the webhook belongs to.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) . The `shop`, `topic`, `api_version`, and `webhook_id` values are all pulled directly from HTTP headers without being part of the signed payload: [2](#0-1) .

`Registry.process` validates the request purely via `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `to_signable_string` (i.e. only the body) and compares it to the `hmac-sha256` header: [3](#0-2)  and [4](#0-3) . After that single check passes, `request.shop` (from the unsigned header) is copied verbatim into `WebhookMetadata`, which is the object handed to the app's `handle` callback: [5](#0-4) [6](#0-5) .

This breaks the identity binding: `shop authenticated (HMAC-covered) == shop used by the handler for tenant identification`. Since `shop-domain` is not part of `to_signable_string`, the equality does not hold — any bytes verified by the HMAC say nothing about which shop the request is attributed to; the `shop` field is trusted purely because it's parsed from a header, not because it's cryptographically bound to the signature.

### Impact Explanation
An unprivileged internet user who can install the app on their own (attacker-controlled) Shopify store receives legitimate webhooks from Shopify for that store — each with a valid `hmac-sha256` signature over the body and their own `shop-domain` header. Because the signature never covers the `shop-domain` header, the attacker can replay that exact `(raw_body, hmac)` pair to the app's webhook endpoint while substituting the `shop-domain` header with a victim shop's domain (any other shop that has this same app installed). `HmacValidator.validate` will still pass (it only checks the body), and `Registry.process` will invoke the handler with `WebhookMetadata#shop` set to the victim's domain. If the host application uses `data.shop` to determine which tenant's data to update, delete, or key by (a documented, intended use of this field per `WebhookMetadata`), the attacker can inject cross-tenant events under a shop identity they don't control — meeting the "cross-tenant access" impact bar.

### Likelihood Explanation
Likelihood is high for any app that relies on `WebhookMetadata#shop` for tenant scoping (the field exists specifically for this purpose): the attacker only needs their own store's install (freely available, unprivileged) to obtain a valid `(body, hmac)` pair, and can then send arbitrary HTTP requests with a forged `shop-domain` header to the app's public webhook endpoint — no access token, secret, or privileged account required.

### Recommendation
Include `shop`, `topic`, `api_version`, and `webhook_id` in the signable string used for HMAC verification (or otherwise cryptographically bind them, e.g. re-derive/verify the shop from a separately authenticated source such as the stored subscription's shop, not solely from the header), so that the values consumed downstream by `WebhookHandler` implementations are covered by the same signature that authenticates the request body.

### Proof of Concept
1. Install the target app to attacker-owned shop `attacker.myshopify.com`; trigger a webhook (e.g. `orders/create`) and capture the raw POST body and the `X-Shopify-Hmac-Sha256` header value sent by Shopify.
2. Replay the exact same POST body and `X-Shopify-Hmac-Sha256` header to the app's webhook endpoint, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `Utils::HmacValidator.validate` in `Registry.process` recomputes the HMAC over `to_signable_string` (the body only) and it matches, since the body/HMAC pair is unchanged; `Registry.process` calls `handler.handle(data: WebhookMetadata.new(..., shop: "victim.myshopify.com", ...))`, causing the app to process attacker-supplied content as though it originated from `victim.myshopify.com`.         def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

          received_signature = verifiable_query.hmac
