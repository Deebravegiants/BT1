### Title
Deterministic commitment/nullifier collision via replayed `stealthAddressStructure`+amount+timestamp+token in `DepositOnChainUtxosExternalAction` permanently freezes a duplicate leaf's funds - ([File: contracts/HinkalBase.sol], [File: contracts/external-actions/DepositOnChainUtxosExternalAction.sol], [File: circuits/NullifierCalculator.circom])

### Summary
The on-chain leaf commitment is `hash4(amount, erc20Address, stealthAddressStructure.stealthAddress, timeStamp)` with no per-deposit randomness, and the nullifier is `Poseidon(commitment, Poseidon(nullifyingPrivateKey, commitment))` — a pure function of `(amount, token, stealthAddress, timeStamp, key)`. `DepositOnChainUtxosExternalAction` lets any unprivileged depositor fully control `amount`, `erc20Address`, `stealthAddressStructure` and `timeStamp` (all public fields, observable from any prior transaction), so an attacker can mint a second leaf with an identical commitment to an existing victim leaf. Because neither `insertCommitments`/`insertMany` nor `insertNullifiers` deduplicate by commitment, both leaves coexist in the tree, but spending either one produces the same nullifier and permanently locks the other.

### Finding Description
Equality that should hold: *for two distinct funding events into the tree, the resulting leaves should be independently spendable* (one nullifier ⇔ one leaf). This is broken because:

1. Leaf commitments are computed with no blinding/nonce beyond the four public fields: [1](#0-0) 

2. `DepositOnChainUtxosExternalAction.runAction` lets the caller fully control `amount`, `erc20Address`, `stealthAddressStructure` and `timeStamp` (via `circomData.timeStamp + utxoIndex`), gated only by `onlyAllowedRecipient`, which checks `msg.sender` (the Hinkal core contract) against an allow-list — never any relationship to the depositor or the stealth-address owner: [2](#0-1) [3](#0-2) 

3. `insertCommitments`/`insertMany` insert leaves with no uniqueness check against existing leaves in the tree: [4](#0-3) [5](#0-4) 

4. The nullifier itself, computed in-circuit, depends only on `commitment` and a `signature` that is itself `Poseidon(nullifyingPrivateKey, commitment)` — i.e., fully determined by `(commitment, nullifyingPrivateKey)` with no leaf-position or per-note randomness input: [6](#0-5) [7](#0-6) 

5. `insertNullifiers` marks a nullifier as globally spent and reverts on reuse — since the nullifier is identical for both leaves, the second attempt to spend either leaf always fails: [8](#0-7) 

**Exploit flow:** Attacker observes a past genuine deposit transaction (`prooflessDeposit`, with `timeStamp = block.timestamp` of that historical block, or another `DepositOnChainUtxosExternalAction` call) and copies its public `(amount, erc20Address, stealthAddressStructure, timeStamp)` tuple exactly. Attacker calls `transact` with `externalActionData.externalActionId` pointing at `DepositOnChainUtxosExternalAction`, `circomData.originalSender = attacker`, and `externalActionMetadata` encoding the same `amount`; `circomData.timeStamp` set to match the victim's original leaf's timestamp exactly (offset 0 for the first UTXO in the batch). `onlyAllowedRecipient` only checks that the caller is the registered Hinkal core contract — it never checks any relationship between `msg.sender`/`circomData.originalSender` and the `stealthAddressStructure`'s owner. The attacker's tokens are pulled via `transferERC20TokenFrom` and a new leaf with a commitment identical to the victim's genuine leaf is inserted at a different tree index. When the true recipient (holder of the private key behind that `stealthAddressStructure`) later spends either of the two identical leaves, the nullifier is marked used; any subsequent attempt to spend the other leaf reverts forever with "Nullifier cannot be reused," because the nullifier is a function of `(commitment, key)`, not of the specific leaf/tree index.

None of the existing guards catch this: `onlyAllowedRecipient` only allow-lists the calling contract, `dimensionsCheck`/`checkOnchainCreation` validate array shapes and zero-out fields for on-chain creation but never check commitment uniqueness, and the circuit's `ForceEqualIfEnabled`/`OverflowPreventer`/Merkle-inclusion checks only validate that a claimed input leaf exists somewhere in the tree — they do not (and structurally cannot, since Merkle trees permit duplicate leaf values) distinguish which of two identical leaves is being referenced.

### Impact Explanation
Whichever of the two identical-commitment leaves is spent second becomes permanently unspendable — its funded value is frozen in the Hinkal contract forever, since the nullifier check will always fail. This is a value-freezing bug reachable by any unprivileged depositor who can observe on-chain data and fund a matching duplicate deposit; it directly demonstrates that the protocol's uniqueness/anti-replay invariant for UTXOs is not actually leaf-position-bound but purely value-bound, which is a systemic flaw in the "one nullifier = one leaf" assumption underpinning the whole shielded-balance accounting. This matches the Critical category of "permanent freezing of user funds" — the frozen leaf's value (whether funded by the attacker or the victim/relayer) can never be recovered by anyone once collided.

### Likelihood Explanation
Preconditions are minimal and fully attacker-controlled: the attacker needs (a) the public 4-tuple of an existing/target leaf (trivially obtainable from calldata of any past deposit transaction), (b) enough of their own tokens to fund the duplicate amount, and (c) a single call through `DepositOnChainUtxosExternalAction` (registered as an allowed external action, which it is per the repo's intended feature set). No proof of stealth-address ownership, no relayer, and no privileged role is required. The attack is repeatable against any observed deposit and costs only the token amount being donated (which becomes permanently stuck once the collision resolves against the attacker) or, more critically, degrades the victim's own genuine UTXO's future spendability once triggered.

### Recommendation
Bind the leaf commitment (and therefore the nullifier) to something unique per insertion — e.g., include the tree insertion index / a monotonically-increasing on-chain nonce, or a caller-committed random blinding factor that is itself constrained in-circuit, in the `hash4` commitment formula in `createOnchainCommitment`. Additionally, `DepositOnChainUtxosExternalAction` should not allow an arbitrary, non-privileged depositor to fully dictate `stealthAddressStructure` together with a `timeStamp`/`amount` combination that can be made to collide with another leaf; consider deriving `timeStamp` from `block.timestamp` (as `_createProoflessDepositCommitments` does) rather than trusting caller-supplied `circomData.timeStamp`, or reject on-chain-created commitments whose commitment value already exists in the tree.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, and `DepositOnChainUtxosExternalAction`; register the action id and allow-list Hinkal as recipient.
2. Victim (or a relayer on victim's behalf) calls `transact` targeting `DepositOnChainUtxosExternalAction` with `circomData.timeStamp = T`, `stealthAddressStructure = S` (victim's real stealth address), `amount = A`, `token = TOKEN`. Record the resulting leaf/commitment `C1 = hash4(A, TOKEN, S.stealthAddress, T)`.
3. Attacker (separate EOA, no special role) calls `transact` targeting the same external action with identical `circomData.timeStamp = T`, `stealthAddressStructure = S`, `amount = A`, `token = TOKEN`, funding it from their own balance. Assert `C2 == C1` and both leaves are present in the tree at different indices (assert via `NewCommitment` events / distinct `insertedIndexes`).
4. Generate a valid proof for the victim spending leaf at index 1 (the genuine leaf), using victim's real `nullifyingPrivateKey`; call `transact` to spend it. Assert `nullifiers[N] == true` afterward, where `N` is the computed nullifier.
5. Generate a valid proof for the victim spending leaf at index 2 (the attacker-donated duplicate) with an inclusion proof against the same/updated root, using the same `nullifyingPrivateKey`. Assert the circuit computes the identical nullifier `N`.
6. Submit this second `transact` call and assert it reverts with `"Nullifier cannot be reused"`, proving the second leaf's value (funded independently by the attacker) is permanently frozen — i.e., assert `nullifiers[N]` was already `true` before this call and the funds backing leaf-2 can never be withdrawn.

    function insertNullifiers(
        uint256[][] calldata inputNullifiers,
        bool[] calldata onChainCreation
    ) internal {
        for (uint256 i = 0; i < inputNullifiers.length; i++) {
            for (uint256 j = 0; j < inputNullifiers[i].length; j++) {
                if (onChainCreation[i] == true) break;
                if (inputNullifiers[i][j] != 0) {
                    require(
                        !nullifiers[inputNullifiers[i][j]],
                        "Nullifier cannot be reused"
                    );
                    nullifiers[inputNullifiers[i][j]] = true;
                    emit Nullified(inputNullifiers[i][j]);
                }
            }
        }
    }

    function insertMany(
        uint256[] memory leaves
    ) internal returns (uint256[] memory insertedIndexes) {
        m_index += leaves.length;
        uint256 newIndex = m_index;
        uint256 currentNodeIndex = newIndex - leaves.length;

        require(m_index <= uint256(2) ** LEVELS, "Tree is full.");

        insertedIndexes = new uint256[](leaves.length);
        for (uint256 i = 0; i < insertedIndexes.length; i++) {
            insertedIndexes[i] = currentNodeIndex + i;
        }

        uint256[][] memory sortedLeaves = sortInPairs(leaves, currentNodeIndex);

        uint256 fullCount = newIndex - MINIMUM_INDEX; // number of inserted leaves
        uint256 twoPower = logarithm2(fullCount); // number of tree levels to be updated, (e.g. if 9 => 4 levels should be updated)

        for (uint256 i = 0; i < sortedLeaves.length; i++) {
            if (sortedLeaves[i].length == 1)
                insertOne(currentNodeIndex++, twoPower, sortedLeaves[i][0]);
            else {
                insertTwo(
                    sortedLeaves[i][0],
                    sortedLeaves[i][1],
                    currentNodeIndex,
                    twoPower
                );
                currentNodeIndex += 2;
            }
        }

        roots[newIndex - 1] = tree[twoPower]; // adding root to roots mapping
    }

template NullifierCalculator() {
  signal input commitment;
  signal input signature;
  signal output out;

  component calcOriginalNullifier = Poseidon(2);
  calcOriginalNullifier.inputs[0] <== commitment;
  calcOriginalNullifier.inputs[1] <== signature;
