### Title
Unvalidated `routeConfig.auroraEngineContractId` allows redirecting NEP-141 withdrawal to an arbitrary NEAR account - (File: packages/intents-sdk/src/bridges/aurora-engine-bridge/aurora-engine-bridge.ts)

### Summary
`AuroraEngineBridge.createWithdrawalIntents` builds the `ft_withdraw` intent's `receiver_id` directly from the caller-supplied `routeConfig.auroraEngineContractId`, while `validateWithdrawal` only checks `destinationAddress` against Ethereum address format and never verifies that `auroraEngineContractId` is a legitimate, known Aurora Engine contract for that chain. This breaks route truth: the bridge contract embedded in the signed intent is not verified to be the actual custodian of the asset for the validated destination chain.

### Finding Description
The broken equality: `receiver_id` in the signed `ft_withdraw` intent (i.e., the NEAR account that will custody the NEP-141 tokens) should equal the real, canonical Aurora Engine contract that is the actual bridge/custodian for `Chains.Ethereum` (or whichever virtual chain is being withdrawn to). Instead:

- `createWithdrawalIntents` (`packages/intents-sdk/src/bridges/aurora-engine-bridge/aurora-engine-bridge.ts:105-118`) passes `args.withdrawalParams.routeConfig.auroraEngineContractId` straight into `createWithdrawIntentPrimitive`.
- `createWithdrawIntentPrimitive` (`packages/intents-sdk/src/bridges/aurora-engine-bridge/aurora-engine-bridge-utils.ts:26-29`) sets `receiver_id: params.auroraEngineContractId` (the ft_transfer_call target) with no whitelist check — this is the NEAR account that will actually receive and hold the tokens via `ft_transfer_call`.
- `validateWithdrawal` (`packages/intents-sdk/src/bridges/aurora-engine-bridge/aurora-engine-bridge.ts:128-142`) validates only `destinationAddress` format against `Chains.Ethereum` via `validateAddress`, and does not validate or cross-check `auroraEngineContractId` at all.
- `routeConfig` is constructed via `createVirtualChainRoute(auroraEngineContractId, proxyTokenContractId)` (`packages/intents-sdk/src/lib/route-config-factory.ts:32-41`), which accepts `auroraEngineContractId` as a free-form string parameter with zero validation — it is not restricted to a known/canonical set of Aurora Engine contracts.

Because `routeConfig` is attacker/caller-controlled input (per the threat model — an ordinary user or an integrator forwarding caller-supplied `routeConfig`), a caller can pass any syntactically valid NEAR account ID (e.g., `attacker-controlled.near`) as `auroraEngineContractId`. This ID becomes the `receiver_id` of the signed `ft_withdraw` intent, meaning the NEP-141 tokens are transferred via `ft_transfer_call` to that NEAR account. There is no existing guard (`supports()` only checks `assetId` standard is `nep141` and route type; `validateWithdrawal` only checks Ethereum address format; there's no cross-check that `auroraEngineContractId` is on an allow-list of real Aurora Engine deployments) that prevents this divergence.

### Impact Explanation
The signed `ft_withdraw` intent's `receiver_id` — the NEAR account that actually receives and custodies the tokens — can be set to an arbitrary caller-supplied NEAR account instead of the genuine Aurora Engine bridge contract. Once the intent is signed and executed, tokens are irrecoverably transferred (via `ft_transfer_call`) to that account. This is Critical: it moves funds to a wrong/arbitrary contract with no recovery path, matching "funds delivered to a wrong address/chain/contract with no recovery."

### Likelihood Explanation
The only precondition is that the caller (or an integrator forwarding caller-controlled `routeConfig`) can supply an arbitrary `auroraEngineContractId` string when calling `createWithdrawalIntents`/`createVirtualChainRoute`. No special privilege, contract admin access, or relayer/RPC compromise is required — this is directly reachable via the public SDK surface (`createVirtualChainRoute`, `RouteConfig.auroraEngineContractId`, `Bridge.createWithdrawalIntents`). It is repeatable for every withdrawal call.

### Recommendation
Cross-check `routeConfig.auroraEngineContractId` (and `proxyTokenContractId`) against a hardcoded/known-good allow-list of legitimate Aurora Engine contract IDs per environment/chain inside `validateWithdrawal` (and/or `supports()`), rejecting any withdrawal whose `auroraEngineContractId` is not in that list, analogous to how other bridges validate their destination/contract identifiers rather than trusting caller-supplied route configuration values.
