## Title
Webhook shop/topic/api-version headers are not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` exposes `shop`, `topic`, `api_version`, and `webhook_id` as trusted request metadata, but the HMAC signature that `ShopifyAPI::Webhooks::Registry.process` validates only covers the raw request body — never these headers. An attacker who can obtain any single valid `(body, hmac)` pair for the shared app secret (e.g. from a webhook delivered to their own installed/dev store) can replay that exact body/HMAC to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header. The signature check still passes because it never inspects the header, so the handler receives an attacker-chosen `shop` value as if it were authenticated.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, `#api_version`, and `#webhook_id` are all read directly from HTTP headers with no cryptographic binding to the signed payload: [2](#0-1) 

`HmacValidator.validate` computes the HMAC purely from `verifiable_query.to_signable_string` (the body) and compares it against `verifiable_query.hmac` (also header-derived): [3](#0-2) 

`Registry.process` trusts the HMAC check as the sole authentication gate, then immediately hands the header-derived, unauthenticated `request.shop` (along with `request.topic`, `request.api_version`, `request.webhook_id`) to the registered handler as `WebhookMetadata`: [4](#0-3) 

The identity binding that should hold is: `shop asserted by the HMAC-protected request == shop used by the handler to scope tenant data`. Because the signature only binds the JSON body bytes and not the `shop-domain` header, this equality is broken — the body can be authentic for shop A while the `shop` value delivered to the handler is forged as shop B. This is the same bug class as the reported "trader signature not covering the acting identity" issue: a value (`shop`) that drives sensitive downstream logic is not included in the value that is cryptographically verified.

### Impact Explanation
Most Shopify apps use the `shop` field from `WebhookMetadata` to look up the app's stored access token/session for that shop, or to write/update tenant-scoped records (orders, customers, billing state, uninstall handling, GDPR data requests, etc.). Since the api secret (`Context.api_secret_key`) is shared across all shops that install the app, any attacker who operates (or briefly installs the app on) one shop can legitimately receive a real webhook with a valid HMAC for arbitrary attacker-chosen body content (e.g., by triggering `orders/create` on their own store), then replay that exact body+HMAC to the app's public webhook endpoint with a spoofed `X-Shopify-Shop-Domain` header naming a victim shop. This is a cross-tenant integrity/confidentiality issue: the host application processes attacker-controlled webhook data under another merchant's identity, potentially corrupting the victim's tenant data or bypassing per-shop authorization checks that key off `shop`.

### Likelihood Explanation
Exploitation only requires the attacker to control (or install the app on) a single Shopify store to obtain one valid `(body, hmac)` pair — no access to `api_secret_key`, tokens, or TLS interception is required. Any app that exposes a public webhook receiver endpoint (as documented for this gem) is reachable this way, and the vulnerable code path (`Registry.process` / `HmacValidator.validate` / `Request#shop`) is core to the gem's documented webhook-processing flow.

### Recommendation
Include the identity-relevant headers (`shop-domain`, `topic`, and ideally `webhook-id`/`api-version`) in the HMAC-signed material that `Request#to_signable_string` returns, or otherwise cryptographically bind them (e.g., reject the request unless the header values are supplied within a signed envelope). At minimum, document loudly that `request.shop`/`request.topic` are unauthenticated and must not be used for tenant scoping without an independent verification step (e.g., cross-checking against a shop that the app already has an active session for, in addition to the raw HMAC check).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook (e.g., `orders/create`) with a crafted order body `B`.
2. Shopify delivers the webhook to the app with a valid `X-Shopify-Hmac-Sha256` header computed over `B` using the app's shared `api_secret_key`, along with `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker captures body `B` and the HMAC header value.
4. Attacker sends a new POST request directly to the app's public webhook endpoint with the same body `B`, same `X-Shopify-Hmac-Sha256` header, but `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `B` — validation succeeds.
6. The registered handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: B, ...)`, so the host application processes attacker-controlled data as if it originated from `victim-shop.myshopify.com`. [4](#0-3) [5](#0-4)
