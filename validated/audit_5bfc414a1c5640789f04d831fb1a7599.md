### Title
Accrual-time RAY multiplication overflow can permanently freeze a large lending market - ([File: `common/src/rates/index.rs`])

### Summary
Pool accrual computes market-wide scaled values by multiplying total scaled shares by the live index, but the multiplication can overflow `i128` before either index cap can engage. [1](#0-0) [2](#0-1)  Because every pool mutation loads an interest-synced market, the resulting `MathOverflow` traps subsequent repayments, withdrawals, borrows, liquidations, and explicit index updates for that market. [3](#0-2) 

### Finding Description
`update_borrow_index` first computes `old_index.mul(interest_factor)` and only afterward applies `MAX_BORROW_INDEX_RAY`, so the cap does not protect multiplication paths that use total scaled debt or supply values before the index cap is reached. [1](#0-0) 

Likewise, `update_supply_index` computes `supplied.mul(old_index)`, and `calculate_supplier_rewards` computes `borrowed.mul(old_borrow_index)` and `borrowed.mul(new_borrow_index)`. [2](#0-1) [4](#0-3)  The direct scaling helper also performs `scaled.mul(index)` with checked fixed-point arithmetic rather than saturating at the `i128` boundary. [5](#0-4) 

`interest::global_sync` performs this accrual before returning a mutable market cache. [6](#0-5)  Both `synced_market` and `renewed_market` call `global_sync`, placing the arithmetic on ordinary pool mutation paths. [3](#0-2)  The controller-facing `update_indexes` entrypoint is also permissionless apart from caller authorization. [7](#0-6) 

An unprivileged path can therefore push a very large, high-decimal market toward the finite RAY-value domain by supplying and borrowing through normal `supply` and `borrow` calls, then allow or induce sustained high utilization until the index growth causes the next accrual to overflow. [8](#0-7)  The repository’s own regression test demonstrates that an 18-decimal market with one billion whole tokens and 98% utilization reaches this cliff while `borrow_index` remains below `MAX_BORROW_INDEX_RAY`. [9](#0-8) 

### Impact Explanation
This is a permanent market-level denial of service and freezing of user funds. Once the scaled market value and index product exceeds the supported `i128` domain, every later operation that accrues first fails before reaching logic that could repay debt, withdraw collateral, liquidate positions, or repair the book. [3](#0-2)  The test explicitly demonstrates that both a one-unit withdrawal and a repayment revert with `MATH_OVERFLOW` after the accrual cliff. [10](#0-9) 

The affected market’s supplied cash remains in the pool, borrower debt cannot be safely reduced through normal operations, and liquidators cannot process exposure in that market. [3](#0-2) 

### Likelihood Explanation
The attack is not reachable from an ordinary small account because it requires a very large book relative to `i128`’s RAY-domain capacity, sustained high utilization, and enough elapsed interest for the index multiplier to cross the overflow boundary. [11](#0-10)  The demonstrated setup uses one billion whole tokens at 18 decimals, supplies that amount to the market, and borrows 98% of it. [8](#0-7) 

Nevertheless, the state is created through ordinary unprivileged supply and borrow actions rather than privileged mutation, and the repository test shows the overflow occurs before the explicit borrow-index maximum can protect the market. [12](#0-11)  After that point, the failure is deterministic because every ordinary pool mutation invokes `global_sync` before performing its operation. [3](#0-2) 

### Recommendation
- Before accrual, compare `scaled` and `index` against a multiplication headroom bound, such as `i128::MAX / RAY`, and fail safely or cap the state before executing `mul`.
- Apply domain checks inside `scaled_to_original`, `update_supply_index`, and `calculate_supplier_rewards`, rather than relying solely on `MAX_BORROW_INDEX_RAY` and `MAX_SUPPLY_INDEX_RAY` after index multiplication. [13](#0-12) 
- Enforce a market-level maximum scaled value that accounts for the configured token decimals, supply cap, borrow cap, reserve factor, and worst-case index growth.
- Add an emergency accrual path that can mark the market accrued or bound the overflowing calculation without minting additional claims, so repayment and controlled wind-down remain possible.
- Extend the existing cliff test to assert which concrete expression overflows and verify the remediation admits at least `repay`, `withdraw`, and liquidation-oriented settlement after the boundary is reached.

```rust
pub fn update_borrow_index(env: &Env, old_index: Ray, interest_factor: Ray) -> Ray {
    let new_index = old_index.mul(env, interest_factor);
    if new_index.raw() > MAX_BORROW_INDEX_RAY {
        return Ray::from(MAX_BORROW_INDEX_RAY);
    }
    new_index
}

/// Grows `old_index` by distributing `rewards_increase` over the total value
/// currently supplied (`supplied * old_index`). The division rounds down.
///
/// Returns `old_index` unchanged if `supplied` or `rewards_increase` is zero,
/// or if the total supplied value is zero. Clamps the result between
/// `old_index` (itself capped at `MAX_SUPPLY_INDEX_RAY`) and
/// `MAX_SUPPLY_INDEX_RAY`, so the returned index never decreases and never
/// exceeds the cap.
pub fn update_supply_index(env: &Env, supplied: Ray, old_index: Ray, rewards_increase: Ray) -> Ray {
    if supplied == Ray::ZERO || rewards_increase == Ray::ZERO {
        return old_index;
    }

    let total_supplied_value = supplied.mul(env, old_index);

    if total_supplied_value == Ray::ZERO {
        return old_index;
    }

    let new_value = total_supplied_value.checked_add(env, rewards_increase);
    let grown = fp_core::mul_div_floor_saturating(env, new_value.raw(), RAY, supplied.raw());

    let bounded_old = old_index.raw().min(MAX_SUPPLY_INDEX_RAY);
    Ray::from(grown.min(MAX_SUPPLY_INDEX_RAY).max(bounded_old))
```

```rust
pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}
```

```rust
/// The cliff. A billion whole tokens is `1e36` raw ray; the value ceiling is
/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
```
