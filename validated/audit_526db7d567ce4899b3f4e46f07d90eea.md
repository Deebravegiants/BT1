### Title
Webhook Shop Identity Spoofing via HMAC Not Covering the `shop-domain` Header - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw webhook body, so the HMAC signature validated by `ShopifyAPI::Utils::HmacValidator.validate` only authenticates the JSON payload. `shop`, `topic`, `webhook_id`, and `api_version` are parsed straight from HTTP headers and are never covered by that signature, yet `ShopifyAPI::Webhooks::Registry.process` trusts `request.shop` as the tenant identifier when constructing the `WebhookMetadata` passed to the app's handler.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 

while `shop`, `topic`, `webhook_id`, and `api_version` are pulled independently from headers that are not part of the signed string: [2](#0-1) 

`HmacValidator.validate` verifies the HMAC purely against `verifiable_query.to_signable_string`, i.e. the raw body: [3](#0-2) 

`Registry.process` checks the HMAC once, then immediately trusts `request.shop` (an unauthenticated header) as the tenant identity forwarded to the app's own webhook handler: [4](#0-3) 

The identity binding that should hold is:
`HMAC(secret, raw_body) == received_hmac` **and** `shop == tenant the HMAC was issued for`.

In this implementation only the first half is enforced; `shop` is never part of the signed material, so the equality `verified_bytes == bytes the shop claim is drawn from` does not hold. Because the app's `api_secret_key` is shared across every shop that installs the app, any merchant who has installed the app can capture one of their own legitimately-signed webhook deliveries (valid `raw_body` + valid HMAC over that body), then replay the identical body/HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a victim shop. `HmacValidator.validate` still succeeds because it never inspects the shop header, and `Registry.process` forwards `shop: request.shop` (the attacker-chosen victim domain) to the handler, which will typically use it to look up the target shop's session/access token or mutate per-tenant state.

### Impact Explanation
This breaks the tenant boundary the HMAC is supposed to enforce and enables an attacker who controls one shop's installation to forge webhook events (e.g. `app/uninstalled`, `shop/redact`, `customers/data_request`, or any handler-registered topic) that appear to originate from a different shop of the attacker's choosing. Any handler logic keyed off `WebhookMetadata#shop` — such as deleting/redacting a victim shop's stored data, disabling a victim shop's integration, or triggering shop-scoped side effects — can be invoked against a shop the attacker does not control, i.e. cross-tenant access without any credential belonging to the victim.

### Likelihood Explanation
The only prerequisite is being a legitimate (non-privileged) installer of the target app, which is the same trust level Shopify grants any merchant that installs a public app. No access token, client secret, or victim credential is required — only capturing one of the attacker's own valid webhook deliveries (body + HMAC) and replaying it with a modified shop header, which is straightforward request tampering.

### Recommendation
Include the shop domain (and ideally topic/webhook id) inside the HMAC-signed material, or independently bind/verify the `shop` header against a value that is cryptographically tied to the signature (e.g. incorporate it into `to_signable_string`, or require registry consumers to cross-check `request.shop` against a per-shop secret/session before trusting it). At minimum, document that `request.shop` is unauthenticated and must not be used to select tenant-scoped credentials or perform destructive per-shop actions without additional verification.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and receives a legitimate webhook, e.g. `{}` body for topic `app/uninstalled`, with header `X-Shopify-Hmac-SHA256: <valid HMAC of "{}">` (valid because `to_signable_string` only hashes the body).
2. Attacker resends the exact same raw body `{}` and the exact same `X-Shopify-Hmac-SHA256` value to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`; validation passes because the shop header was never part of the signed string (`lib/shopify_api/webhooks/request.rb:35-38`, `lib/shopify_api/utils/hmac_validator.rb:12-31`).
4. `Registry.process` invokes the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), causing the handler to act on the victim shop's tenant data as though Shopify itself sent the event for that shop.

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
