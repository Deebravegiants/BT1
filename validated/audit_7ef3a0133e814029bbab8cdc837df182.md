Confirms no size-limit anywhere on `body`/`onAccept` calldata across `EvmHost.dispatch`, `HandlerV2.handlePostRequests`, or `Message.hash`.

### Title
Unbounded POST request body length allows griefing/permanent-freeze DOS of relayed messages - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)` accepts an arbitrary-length `body` from any unprivileged caller with no size validation, unlike other apps in the same codebase (e.g. `BandwidthManager.purchase`, which explicitly bounds `app.length` to `MAX_APP_LENGTH`). This unbounded body is committed on the source chain and must later be reconstructed, hashed, and forwarded in full by a relayer calling `HandlerV2.handlePostRequests` / `IHost.dispatchIncoming` on the destination chain.

### Finding Description
`EvmHost.dispatch` builds a `PostRequest` directly from `post.body` with no length check, computes its commitment, and emits it: [1](#0-0) 

The commitment is `keccak256(abi.encode(req))` via `Message.hash`, which itself calls `abi.encode(req)` on the whole struct including `body`: [2](#0-1) 

Unlike `BandwidthManager.purchase`, which explicitly rejects an oversized `app` field before dispatch (`InvalidPurchase` if `app.length > MAX_APP_LENGTH`): [3](#0-2) 

there is no equivalent bound enforced in `EvmHost.dispatch`, `IDispatcher.dispatch(DispatchPost)`, or anywhere in the `PostRequest`/`DispatchPost` structs: [4](#0-3) 

Any application contract (or an EOA calling through a trivial pass-through app) can therefore dispatch a POST request whose `body` is arbitrarily large (bounded only by calldata/tx-size limits of the source chain, e.g. many hundreds of KB). This request must be delivered end-to-end: a relayer submits it (with proof) to `HandlerV2.handlePostRequests` on the destination chain, which decodes the full `PostRequest` (including the oversized `body`), verifies membership, and forwards the whole request to the destination `IApp.onAccept`. The gas cost of copying/decoding this payload and forwarding it in an external call scales with body size, and calldata + memory expansion costs can push the total transaction gas above the destination chain's block gas limit, especially on lower-throughput or lower-gas-limit EVM chains that Hyperbridge explicitly supports.

### Impact Explanation
If a dispatched request's body is large enough that no valid transaction on the destination chain can execute `handlePostRequests` for it within the block gas limit, the message becomes permanently undeliverable — this falls squarely within the accepted impact class "a route unable to deliver messages." Because `PostRequest`/`DispatchPost` carries an escrowed relayer `fee`, a stuck, undeliverable request also permanently locks the payer's relayer fee (recoverable only via timeout, which itself requires a non-membership proof handled through the same handler, subject to similar calldata/gas constraints for the timeout path) and denies the source-side application any which `onPostRequestTimeout` recovery. This is a protocol-level, unprivileged-triggerable griefing vector reachable directly from `EvmHost.dispatch`, matching the reachable "EvmHost and HandlerV2 dispatch and delivery" path called out as in-scope.

### Likelihood Explanation
Likelihood is Medium: an attacker (or even an unwitting integrator) pays only for calldata/storage costs of dispatching a large body on the source chain — no fee-token cost is proportional to body size (the fee model was made flat / relayer-fee only, per the SDK comment "the per-byte fee model was removed from EvmHost"), so there's essentially no economic disincentive: [5](#0-4) 
This makes the attack cheap to mount against any low-gas-limit destination chain configured in the protocol, while requiring only a normal `dispatch` call — no special privileges.

### Recommendation
Enforce a maximum `body` length in `EvmHost.dispatch(DispatchPost)` (and the analogous pallet-ismp `dispatch_request` path for POST) sized so that a `handlePostRequests`/`handleTimeout` call carrying the request plus consensus/membership proof is guaranteed to fit comfortably under the smallest supported destination chain's block gas limit. Mirror the pattern already used in `BandwidthManager.purchase` (`MAX_APP_LENGTH` check) by adding a `MaxRequestBodySize`-style `HostParams` field, validated at dispatch time, and reject with a clear error (e.g. `BodyTooLarge`) rather than allowing unbounded bodies to be committed.

### Proof of Concept
1. Deploy a trivial `IApp` wrapper (similar to `TestDispatcher` in `evm/tests/foundry/TestDispatcher.sol`) that calls `IDispatcher(host).dispatch(post)`.
2. Call `dispatch` with `post.body` set to several hundred KB of arbitrary bytes and `post.dest` set to a low gas-limit EVM chain configured in Hyperbridge. [6](#0-5) 
3. Observe the request commitment is recorded with no rejection: [7](#0-6) 
4. Attempt to relay the request via `HandlerV2.handlePostRequests` on the destination chain and observe that gas required (calldata + proof + full body decode/forward) exceeds the destination's block gas limit, making delivery permanently impossible and locking any escrowed relayer fee.
