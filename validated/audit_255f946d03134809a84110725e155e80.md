### Title
Infinite loop in GRANDPA `AncestryChain::ancestry` via attacker-crafted cyclic parent-hash headers - (File: `modules/consensus/grandpa/primitives/src/justification.rs`)

### Summary
`AncestryChain::ancestry` walks backward from a target block hash to a base hash by repeatedly looking up `parent_hash` pointers in a `BTreeMap<Hash, Header>` built directly from relayer/attacker-supplied `unknown_headers`. Because `parent_hash` is just a struct field chosen freely by whoever crafts the header bytes (independent of the header's actual computed hash), an attacker can submit two (or more) headers whose `parent_hash` fields point at each other, forming a cycle that never reaches `base`. The `while current_hash != base` loop then never terminates, hanging the node executing it.

### Finding Description
`AncestryChain::ancestry` (`modules/consensus/grandpa/primitives/src/justification.rs`, lines 176-198) is:

```rust
fn ancestry(&self, base: H::Hash, block: H::Hash) -> Result<Vec<H::Hash>, finality_grandpa::Error> {
    let mut route = vec![block];
    let mut current_hash = block;
    while current_hash != base {
        match self.ancestry.get(&current_hash) {
            Some(current_header) => {
                current_hash = *current_header.parent_hash();
                route.push(current_hash);
            },
            _ => return Err(finality_grandpa::Error::NotDescendent),
        };
    }
    Ok(route)
}
``` [1](#0-0) 

`self.ancestry` is a `BTreeMap` keyed by `H::hash()` and populated straight from the untrusted `unknown_headers` field of the submitted `FinalityProof` (`AncestryChain::new`, lines 161-167): [2](#0-1) 

A header's `parent_hash` field is arbitrary attacker-controlled data — nothing ties it to the header's *own* keccak/blake2 hash. An attacker can therefore submit two headers A and B where `A.parent_hash == hash(B)` and `B.parent_hash == hash(A)`. Once the loop begins walking from a `target` whose ancestry passes through A or B, and `base` is not itself A or B, the lookup alternates `A -> B -> A -> B -> …` forever, since both keys always resolve in the map and the base is never reached.

This function is called directly from `verify_grandpa_finality_proof` on attacker/relayer-controlled `unknown_headers` before any authority-signature verification of the ancestry route itself:
```rust
let headers = AncestryChain::<H>::new(&finality_proof.unknown_headers);
...
let finalized = headers.ancestry(from, target.hash()).map_err(|_| Error::InvalidAncestry)?;
``` [3](#0-2) 

`verify_grandpa_finality_proof` is reachable from `pallet_ismp::Call::handle_unsigned`, which is an **unsigned, permissionless** extrinsic — anyone can submit a `Message::Consensus` carrying a GRANDPA `FinalityProof` for free: [4](#0-3) 

Critically, `handle_unsigned` messages are also executed inside `ValidateUnsigned::validate_unsigned` at the transaction-pool level, i.e. `Self::execute(messages.clone())` runs for every incoming unsigned transaction before it even enters a block: [5](#0-4) 

That means a malicious, crafted-but-plausible GRANDPA `FinalityProof` — attached to a `Message::Consensus` for a GRANDPA (or GRANDPA-secured parachain) `consensus_state_id` — hangs the runtime execution of any node that attempts to validate the transaction in its pool (and any collator that includes it in a block), because Substrate does not preemptively interrupt native/WASM execution loops based on declared weight; weight/fees are only charged after execution completes.

### Impact Explanation
This is a route-availability / liveness attack, not a fund-theft bug, but it is Medium-severity and directly analogous to CVE-2018-10912 (an authenticated actor triggering an unbounded loop that DoSes the server). Here, an *unauthenticated* relayer/attacker can DoS every node connected to the transaction-pool gossip network (and any collator attempting `handle_unsigned` in a block) simply by broadcasting one specially-crafted, unsigned GRANDPA consensus message. Because the extrinsic is free (`handle_unsigned` is fee-less/unsigned) and requires no valid signatures on the ancestry cycle itself (only `target.hash()` needs to equal `finality_proof.block`, and the cycle only needs to intersect the ancestry walk before the loop's justification-signature check is even reached), this can repeatedly stall block production / relayer message delivery for the affected state machine, i.e. a "route unable to deliver messages" condition.

### Likelihood Explanation
Likelihood is meaningful but bounded by two open questions I could not fully verify given tool-call limits:
1. Whether `unknown_headers` size is capped elsewhere (e.g. by extrinsic length limits) — a cap wouldn't prevent the cycle, only bound how many entries a malicious relayer can gossip per message, but a 2-header cycle is enough regardless of caps.
2. Whether the specific target/base combination used in production genuinely allows the vulnerable code path to be reached before an earlier check rejects the malformed proof (e.g. `target.hash() != finality_proof.block` or justification decode failures) — I traced the call order in `verify_grandpa_finality_proof` and `headers.ancestry(from, target.hash())` is invoked (line 88) before `justification.verify(...)` (line 91-93), so the infinite loop triggers prior to any cryptographic authority check, making it directly reachable without valid GRANDPA signatures.

Given this pallet route requires no signature verification to trigger the loop and the target dispatch (`handle_unsigned`) is explicitly designed to be free/unauthenticated, likelihood is significant if any production consensus client instance uses the GRANDPA client (`ismp-grandpa`) with a Coprocessor/relay setup that accepts `Message::Consensus` from arbitrary senders.

### Recommendation
- Bound `AncestryChain::ancestry`'s walk by a maximum number of iterations equal to `self.ancestry.len()` (the map cannot legitimately need to visit more entries than it has, since each header should only be visited once on a genuine chain). Track visited hashes in a `BTreeSet` and return `Err(NotDescendent)` if a hash is revisited.
- Alternatively/additionally, validate that `unknown_headers` form a strictly monotonically-decreasing-by-block-number chain when constructing `AncestryChain`, rejecting any header whose `parent_hash` maps to a block number that is not strictly less than the header's own number (cycles necessarily violate strict ordering).
- Apply the same fix to any other manual "walk-by-hash" traversal in the codebase that consumes untrusted headers (e.g. similar patterns in `modules/consensus/bsc` ancestry walks, though those appear to walk against RPC-fetched trusted headers rather than fully attacker-supplied ones and were not confirmed vulnerable).

### Proof of Concept
1. Construct two headers, `A` and `B`, with attacker-chosen field values:
   - `A.number = 100`, `A.parent_hash = hash(B)`
   - `B.number = 99`, `B.parent_hash = hash(A)`
   (Header hashing is computed over the encoded struct — nothing requires `parent_hash` to relate to the real preceding block.)
2. Set `finality_proof.unknown_headers = vec![A, B, ...target_header_chain_up_to_some_real_target]` such that the ancestry walk from `target.hash()` passes through `hash(A)` at some point (e.g., make the "real" target's parent equal `hash(A)`).
3. Set `base = consensus_state.latest_hash`, a value that is neither `hash(A)` nor `hash(B)`.
4. Submit `pallet_ismp::Call::handle_unsigned { messages: vec![Message::Consensus(consensus_message_wrapping_this_finality_proof)] }` as an unsigned transaction to any node's transaction pool for a state machine backed by the `ismp-grandpa` consensus client.
5. `validate_unsigned` → `Self::execute` → the GRANDPA consensus client's proof verification → `verify_grandpa_finality_proof` → `headers.ancestry(from, target.hash())` enters the `A -> B -> A -> B -> …` cycle and never returns, hanging the node's transaction-pool validation thread (and any collator that later tries to include it in a block).

Note: I was unable to fully trace `modules/ismp/clients/grandpa/src/consensus.rs`'s top-level `verify_consensus`/`IsmpHost::verify_state_proof` message decoding (the file read was interrupted by tool-call exhaustion), so I could not 100% confirm there is no additional pre-filter between `Message::Consensus` decoding and the call into `verify_grandpa_finality_proof` that would reject a mismatched/circular header set earlier. Based on the code reviewed, no such filter exists in `verify_grandpa_finality_proof` itself, and the ancestry walk executes before the cryptographic signature check.
