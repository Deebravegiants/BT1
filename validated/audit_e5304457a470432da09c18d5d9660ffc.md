### Title
EvmHost native-token fee payment relies on manipulable spot Uniswap V2 price with no slippage bound - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.dispatch()`, `dispatch(DispatchGet)` and `fundRequest()` accept native-token (ETH) payment for message dispatch and internally swap it for `feeToken` through the configured `IUniswapV2Router02` using `swapETHForExactTokens`, exactly the class of bug the external report flags: pricing a critical operation off an instantaneous, on-chain AMM price (the Uniswap V2 pool's current reserves) rather than a manipulation-resistant reference like a TWAP.

### Finding Description
Any unprivileged caller can dispatch a POST/GET request or fund an existing request by sending native token with the call: [1](#0-0) 

```solidity
function dispatch(DispatchPost memory post) external payable notFrozen returns (bytes32 commitment) {
    if (msg.value > 0) {
        address[] memory path = new address[](2);
        address uniswapV2 = _hostParams.uniswapV2;
        path[0] = IUniswapV2Router02(uniswapV2).WETH();
        path[1] = feeToken();
        IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
            post.fee, path, address(this), block.timestamp
        );
    }
    ...
```

The identical pattern is repeated in `dispatch(DispatchGet)` [2](#0-1)  and `fundRequest()` [3](#0-2) .

`swapETHForExactTokens` derives the required input amount from the pool's live reserves (Uniswap V2's equivalent of `slot0` in the audited report — an instantaneous, single-block spot price with no TWAP or oracle check). The `deadline` parameter is hardcoded to `block.timestamp`, so it provides no protection against price movement within the same transaction/block — only against staleness across blocks. There is no `amountInMax`/slippage parameter exposed anywhere in this call chain, and no comparison against a TWAP or any external price reference before accepting `msg.value` as payment.

Because the pool's spot price can be manipulated within the same block (e.g., via a large swap immediately preceding the `dispatch()`/`fundRequest()` call, or profitably by a searcher who can also include the manipulating trade and this call in the same block), an attacker can shift the ETH/feeToken price so that:
- Less ETH than expected is required to obtain `post.fee` worth of `feeToken`, leaving unused ETH refunded by the router to `address(this)` (the `EvmHost` contract, since `EvmHost` — not the original caller — is `msg.sender` of the router call). `EvmHost` has no native-ETH withdrawal/sweep path in the reviewed code, so any ETH refunded to it this way is effectively stuck/lost to the protocol, unless a governance/host-manager path exists elsewhere to recover it (not confirmed in the excerpts reviewed).
- Conversely, the price can be manipulated so more ETH than a user expects is needed for the same `post.fee`, causing legitimate dispatches to revert (denial of service on native-fee-paying dispatch) or, if a caller sends excess `msg.value` to be safe, that excess is likewise swallowed by the same refund-to-`EvmHost` issue.

This is directly reachable by any address calling `dispatch()`/`fundRequest()` on `EvmHost` with `msg.value > 0` — no privileged role is required — which satisfies the "unprivileged message dispatcher" reachability bar.

### Impact Explanation
The manipulable spot price used for fee-token acquisition can cause native ETH sent by unprivileged users to be silently over-consumed by the swap and the excess retained by the `EvmHost` contract with no recovery mechanism visible in this file, constituting a permanent loss of user funds for the difference between the manipulated price and the fair price. It can also grief legitimate dispatches into reverting when the manipulated price makes the required ETH exceed `msg.value`. Both outcomes map to the "concrete theft or permanent freezing of funds" bar, scaled by how much value moves through the local Uniswap V2 pool used for `feeToken`/WETH.

### Likelihood Explanation
Likelihood depends on the depth/liquidity of the specific chain's local Uniswap V2 `feeToken`/WETH pool. On chains where this pool is thin (common for a niche `feeToken`), a single actor can manipulate reserves within one transaction bundle at comparatively low cost, then trigger (or wait for) a victim's `dispatch()`/`fundRequest()` call in the same block. This is a standard, well-understood MEV/sandwich pattern against AMM spot pricing, directly analogous to the reported `slot0` issue.

### Recommendation
Do not rely on the pool's instantaneous reserves/spot price for the ETH→feeToken conversion used to satisfy protocol fee requirements. Either:
- Require callers to pre-compute and pass a slippage-bounded `amountInMax`/minimum output enforced via `swapExactETHForTokens` bounds or a caller-supplied `amountOutMin`, and refund unused ETH directly to `msg.sender` of `dispatch`/`fundRequest` (not to `address(this)`), or
- Price the swap against a manipulation-resistant reference (e.g. Uniswap V2 TWAP oracle, or a Chainlink price feed) and revert if the live spot price deviates from that reference by more than a configured tolerance, or
- Remove native-token payment entirely in favor of `feeToken`-only payment, pushing any swap logic off-chain/into the SDK (as already partially the pattern for other fee-quoting paths in the SDK).

### Proof of Concept
1. Attacker identifies a chain where `EvmHost`'s configured Uniswap V2 `feeToken`/WETH pool has shallow liquidity.
2. Attacker (or a bundle builder) submits, in a single block/bundle:
   a. A large swap that shifts the pool's WETH/`feeToken` reserve ratio so that fewer WETH units are needed to buy `post.fee` amount of `feeToken`.
   b. A call to `EvmHost.dispatch(post)` (or `fundRequest`) with `msg.value` sized for the pre-manipulation price.
3. `swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)` executes against the manipulated reserves, consuming less ETH than `msg.value` and refunding the difference to `address(this)` (the `EvmHost` contract), not to the caller.
4. Attacker reverses the manipulating swap (step a) in the same block to restore the pool, keeping the arbitrage profit from steps a+swap, while the excess ETH refunded to `EvmHost` remains stranded with no observed withdrawal path in this contract — a permanent loss for the original caller/protocol.
