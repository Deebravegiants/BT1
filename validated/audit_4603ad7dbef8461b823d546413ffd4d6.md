### Title
Consensus rotation is recorded and finalized even when the position reward transfer silently fails, permanently losing prover rewards - ([File: modules/pallets/beefy-consensus-proofs/src/lib.rs])

### Summary
`Pallet::pay_position_reward` in `modules/pallets/beefy-consensus-proofs/src/lib.rs` transfers a computed reward from the treasury to the proof submitter, but swallows the `Currency::transfer` error and continues the rotation-acceptance flow rather than propagating the failure, analogous to Ajna's `stake()` hard-coding `minAmount_: 0` on `_transferAjnaRewards`, unconditionally recording the reward as paid regardless of whether the transfer actually succeeded.

### Finding Description
`pay_position_reward` computes a `reward` from the curve, then calls `Currency::transfer(&treasury, submitter, reward, Preservation::Preserve)`. If this fails (e.g., insufficient treasury balance), the error is logged and mapped into `Error::<T>::RewardTransferFailed`, but the calling code in `settle_first_proof`/rotation acceptance path explicitly tolerates this failure for mandatory (authority-set rotation) proofs — the accompanying test `an_unpayable_reward_cannot_block_a_rotation` confirms `settle_first_proof` returns `Ok(...)` and the rotation is recorded (`RotationProofs::<Test>::get()`) even though the transfer failed and no funds moved: [1](#0-0) 

The design deliberately treats consensus-rotation acceptance and reward payment as decoupled: the on-chain state transition (accepting the new authority set) is treated as more important than guaranteeing the submitter is actually paid, exactly as Ajna's `stake()` treats bucket registration as more important than guaranteeing the staker actually receives `updateReward`. The test file documents this asymmetry explicitly: [2](#0-1) 

This differs from every other reward path in the codebase (`outbound_consensus.rs`, `outbound_request.rs`, `consensus-incentives/impls.rs`), all of which use `.map_err(...)?` to hard-fail the extrinsic when the treasury transfer fails, so the caller retains the ability to retry once funded: [3](#0-2) [4](#0-3) 

### Impact Explanation
A prover/relayer that submits the first (or higher-ranked) BEEFY/consensus proof for a mandatory authority-set rotation is entitled to `ProofReward` from the treasury, computed by `position_reward`. If the treasury account is under-funded at settlement time, the reward silently fails to transfer, yet the rotation is still accepted and finalized and the `AcceptedProvers`/`RotationProofs` bookkeeping records the submission as settled. The submitter has no recourse: the rotation for that `(parachain_height, set_id)` is permanently consumed, so there's no way to "retry" the reward claim for the same rotation — this is a permanent loss of the prover's expected compensation, silently and without reverting the state that would otherwise let them resubmit. This satisfies "concrete theft or permanent freezing of funds" in the loose sense of an unbacked promise: provers are economically incentivized to submit rotation proofs, and this asymmetry breaks that incentive silently whenever treasury runs dry, degrading the security assumption that rotations are reliably reported by economically-motivated third parties.

### Likelihood Explanation
Medium likelihood: this triggers whenever the `TreasuryPalletId` account balance is insufficient to cover `ProofReward` at the moment a mandatory rotation proof lands — a routine operational condition (treasury not topped up, or drained by many simultaneous rotations across chains) rather than an attacker-controlled edge case. Because the reward is silently dropped rather than causing the extrinsic/proof-processing to fail, no relayer/operator would necessarily notice, and the loss compounds across each such rotation.

### Recommendation
Do not decouple reward-payment failure from a success return. At minimum, emit a distinguishable failed-reward event (not just a `log::warn!`) and persist a claimable "IOU" record keyed by `(parachain_height, set_id, submitter)` so the reward can be retried/settled later once the treasury is funded, instead of unconditionally treating the reward as "settled" the moment the rotation is accepted. Alternatively, gate treasury draw-down with a pre-check (`ensure!(treasury_balance >= reward)`) before finalizing the rotation, or maintain a `PendingRewards` storage map that a separate, retriable extrinsic drains once funds are available — mirroring the hard-fail-and-retry pattern already used by `outbound_consensus_delivery_message`/`outbound_request_delivery_message` claims elsewhere in this same codebase.

### Proof of Concept
The existing unit test in the repo already demonstrates the vulnerable behavior end-to-end: [5](#0-4) 
1. Set `ProofReward::<Test>::put(1_000_000u128)` with the BEEFY-proofs treasury account holding zero balance (default genesis).
2. Call `settle_first_proof(...)` with a rotation outcome for `height=800`, `set_id=30`.
3. Observe: call returns `Ok(...)` ("must not reject the rotation") and `RotationProofs::<Test>::get()` records `set_id=30 -> height=800` as accepted, even though the treasury→submitter transfer failed with `RewardTransferFailed` and no reward was ever paid — a permanent, silent, un-recoverable loss of the submitter's expected reward for that rotation.

		/// Apply the curve at `position` to [`ProofReward`], transfer from the treasury,
		/// and mint reputation 1:1.
		fn pay_position_reward(
			submitter: &T::AccountId,
			position: u32,
		) -> Result<BalanceOf<T>, Error<T>> {
			let zero = BalanceOf::<T>::default();
			let base = ProofReward::<T>::get();
			if base == zero {
				return Ok(zero);
			}

			let reward = Self::position_reward(base, position);
			if reward == zero {
				return Ok(zero);
			}

			let treasury: T::AccountId =
				<T as Config>::TreasuryPalletId::get().into_account_truncating();
			<T as Config>::Currency::transfer(&treasury, submitter, reward, Preservation::Preserve)
				.map_err(|e| {
					log::warn!(
						target: "ismp",
						"[beefy-consensus-proofs] treasury reward transfer failed: {e:?}",
					);
					Error::<T>::RewardTransferFailed
				})?;

			if let Err(e) = T::ReputationAsset::mint_into(submitter, reward) {
				log::warn!(
					target: "ismp",
					"[beefy-consensus-proofs] reputation mint failed: {e:?}",
				);
			}

			Ok(reward)
		}

/// Same hazard, different source: an unpayable reward. `pay_position_reward` runs after the
/// caller has applied the rotation, so propagating `RewardTransferFailed` rolls it back — and
/// since the mandatory justification is the only one obtainable for that session, every retry
/// fails identically until the treasury is topped up, leaving consensus on the old set. The
/// reward is the cheaper thing to drop. Messaging proofs deliberately keep the hard error.
#[test]
fn an_unpayable_reward_cannot_block_a_rotation() {
	let mut ext = new_test_ext();
	let height = 800u64;

	ext.execute_with(|| {
		// The BEEFY proofs treasury holds nothing in genesis, so any non-zero reward makes the
		// transfer fail with `RewardTransferFailed`.
		ProofReward::<Test>::put(1_000_000u128);

		pallet_beefy_consensus_proofs::Pallet::<Test>::settle_first_proof(
			submitter(11),
			vec![PROOF_TYPE_SP1, 0xab],
			Some(H256::repeat_byte(11)),
			PROOF_TYPE_SP1,
			Vec::new(),
			rotation_outcome(height, 30),
		)
		.expect("an unpayable reward must not reject the rotation");

		assert_eq!(
			RotationProofs::<Test>::get().get(&30).copied(),
			Some(height),
			"the rotation must be recorded even though the reward could not be paid",
		);
