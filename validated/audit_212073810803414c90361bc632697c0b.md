## Title
Webhook `shop` field is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` verifies the webhook HMAC over the raw body only, while the `shop` (tenant) identifier is read from an unauthenticated header and passed straight through to the application's webhook handler. Anyone who can obtain one valid `(raw_body, hmac)` pair for the app (e.g. by installing the app on their own shop, which is unprivileged) can replay that exact body/HMAC pair while substituting the `x-shopify-shop-domain` header for a victim shop, producing a webhook that the library reports as HMAC-valid and routes to the handler under the victim's tenant identity.

### Finding Description
`Request#to_signable_string` only returns the raw body bytes: [1](#0-0) 

`HmacValidator.validate`/`validate_signature` compute and compare the HMAC solely against `to_signable_string` (the body): [2](#0-1) 

but the `shop` value used by the library for routing/tenant context comes from a separate, unauthenticated header that is not part of the signable string at all: [3](#0-2) 

`Registry.process` validates only the HMAC and then forwards `request.shop` unchecked into the handler's metadata: [4](#0-3) 

The equality the code implicitly assumes is:
`shop header value == shop that produced/authorized this HMAC-signed body`

But the HMAC only proves `hmac == HMAC(secret, raw_body)`; it says nothing about which shop the header claims. Since all shops installed on a given app share the same `api_secret_key`, an unprivileged user who installs the app on their own shop will receive genuine webhooks (valid body + valid HMAC) for that shop. They can then replay the identical `(raw_body, hmac)` pair to the app's webhook endpoint with the `x-shopify-shop-domain` header changed to a victim shop's domain. `HmacValidator.validate` still succeeds (it never looks at the shop header), and `Registry.process` will invoke the handler with `WebhookMetadata#shop` set to the victim's domain while the body content is fully attacker-controlled (from their own shop's webhook).

### Impact Explanation
This breaks the shop/tenant identity binding relied on by the host application: handlers that key off `WebhookMetadata#shop` (e.g., to update per-shop records, revoke access, or process GDPR-style topics such as `customers/redact`/`shop/redact`) can be invoked with attacker-chosen body content attributed to a shop the attacker doesn't control, which is a cross-tenant confusion — the gem provides no HMAC-covered binding between shop and body, and no check that the claimed shop matches the shop implied by the payload.

### Likelihood Explanation
Likelihood is high for an unprivileged attacker: installing an app on one's own shop is normal and unprivileged; the app's shared `api_secret_key` guarantees the HMAC will validate identically regardless of the `shop-domain` header, since that header is excluded from the signable string by design (`to_signable_string` returns only `@raw_body`). No secrets or victim credentials are required.

### Recommendation
Include the shop domain (and topic/webhook-id) as part of the data verified against the HMAC, or explicitly document/require that consuming applications verify `request.shop` against their own list of installed/authorized shops before trusting it, independent of `HmacValidator.validate`. At minimum, `Registry.process` should not treat HMAC-only validation as sufficient authentication of the `shop` field.

### Proof of Concept
```ruby
# Attacker installs the app on their own shop "attacker.myshopify.com"
# and captures a legitimate webhook delivery for it:
raw_body = '{"id": 1, "note": "attacker-controlled content"}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)

# Attacker replays it to the app's webhook endpoint, spoofing the shop header:
headers = {
  "x-shopify-topic" => "customers/redact",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac),
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # not attacker's own shop
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate succeeds (only checks raw_body),
#    handler is invoked with WebhookMetadata#shop == "victim-shop.myshopify.com"
#    and body == attacker-controlled JSON.
``` [5](#0-4)
