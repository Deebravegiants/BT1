## Title
Malicious/reverting ERC-20 in a multi-token order permanently blocks escrow release, refund, and cross-chain cancellation - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`IntentsBase._withdraw` iterates over all tokens attached to an order (`body.tokens`) and calls `IERC20.safeTransfer` on each one in a single loop, with no isolation between tokens. If any single input/output token used in a multi-asset order is a malicious or non-standard ERC-20 that reverts on `transfer`/`transferFrom` (e.g., a token with a blocklist, pausable transfers, or a deliberately reverting `balanceOf`-gated transfer), the entire `_withdraw` call reverts, which blocks release of every other (legitimate) token escrowed for that same order commitment. This mirrors the reported OpenQ bug class where an unbounded iteration over caller-supplied/attacker-choosable tokens causes a single bad token to block settlement for the whole batch.

### Finding Description
`_withdraw` is the shared internal function used by both cross-chain settlement paths: [1](#0-0) 

It is called from three entry points:
- `onAccept` for `RedeemEscrow` (solver payout after fill) and `RefundEscrow` (refund after destination-side cancel) - triggered by relayer-delivered Hyperbridge messages: [2](#0-1) 
- `onGetResponse`, which refunds escrow after a source-chain cancellation is confirmed via a GET response proof: [3](#0-2) 

The order's `inputs` array (the set of tokens the user escrowed to create the order) is fully attacker/user-controlled at order-creation time via `IntentGatewayV2.placeOrder`/`IntentGatewayV2Tron` — any token address can be listed as an input, with `safeTransferFrom` used to pull it into escrow: [4](#0-3) 

There is no token allow-list or per-token isolation check preventing a user from including a malicious ERC-20 among an order's `inputs` alongside legitimate tokens (e.g. USDC + a reverting token). Once escrowed, `_withdraw` is the only path that releases that escrow — for both `RedeemEscrow` (paying the solver) and `RefundEscrow`/GET-response refund (returning funds to the user). Because the loop has no try/catch or per-token failure isolation, a revert on any single token's `safeTransfer` call reverts the whole withdrawal, meaning:
- The solver can never be paid for that order (even for the non-malicious tokens filled).
- The user can never be refunded on cancellation/timeout (even for the non-malicious tokens escrowed).

This effectively permanently freezes all tokens escrowed under that commitment, since `_orders[commitment][token]` accounting is only ever decremented inside the same atomic loop that reverts.

### Impact Explanation
This directly causes permanent freezing of funds: once an order with a mix of a good token and a reverting/malicious token is created and either filled or cancelled, both the `RedeemEscrow` and `RefundEscrow`/`onGetResponse` code paths revert unconditionally on the bad token, and there is no alternate withdrawal path in `IntentsBase`/`ExtrinsicIntents` to release the good token in isolation. Both the solver's payout and the user's refund for the entire order (not just the bad token) become permanently unrecoverable through the intended protocol flow. This satisfies "permanent freezing of funds" and blocks message delivery outcomes (RedeemEscrow/RefundEscrow can never be successfully processed for that commitment).

### Likelihood Explanation
Likelihood is high: token selection for `order.inputs` is entirely at the discretion of whoever places the order (a normal, unprivileged user creating an intent), and the input-token loop in `placeOrder`/escrow funding performs no allow-listing or safety check on token behavior. An attacker (or even an unwitting user who wraps a fee-on-transfer / pausable / blocklisting token together with a normal token in one order) can trivially construct an order where the malicious token's `transfer` reverts only at withdrawal time (e.g., after being added to a blocklist, or after the token owner pauses it), permanently bricking that order's escrow. No special privileges, timing races, or governance compromise are required — a single crafted `placeOrder` transaction is sufficient to reach the vulnerable code.

### Recommendation
Isolate per-token transfer failures in `_withdraw` so a single bad token cannot block the rest of the batch: wrap each `IERC20(token).safeTransfer(...)` call in a low-level call with try/catch (or use `Address.functionCall` with try/catch semantics), and on failure, either (a) skip that token and leave its escrow balance intact for a separate, per-token retry/claim mechanism, or (b) credit the beneficiary with an internal claimable balance instead of pushing the transfer, allowing a later `pull`-style withdrawal per token. At minimum, do not let one token's revert prevent finalization (`_filled[commitment]`) and release of all other tokens in the same order.

### Proof of Concept
1. Attacker deploys `EvilToken`, an ERC-20 whose `transfer` function reverts once a flag is set (e.g., after the attacker calls `EvilToken.arm()`), but otherwise behaves normally so it passes `safeTransferFrom` during order creation.
2. Attacker calls `placeOrder` on the source-chain `IntentGatewayV2`/`IntentGatewayV2Tron` with `order.inputs = [ {token: USDC, amount: X}, {token: EvilToken, amount: Y} ]`, escrowing both tokens under one commitment (`_orders[commitment][USDC] += X; _orders[commitment][EvilToken] += Y;`).
3. A solver fills the order on the destination chain via `_fillCrossChain`, which dispatches a `RedeemEscrow` `WithdrawalRequest{tokens: order.inputs}` back to the source chain.
4. Before the relayer delivers the message, attacker calls `EvilToken.arm()` to make future `transfer` calls revert.
5. When `onAccept` on the source gateway processes the `RedeemEscrow` request, `_withdraw` iterates `body.tokens`: the `USDC` transfer to the solver succeeds, but the `EvilToken` transfer reverts, causing the entire `onAccept` call — and thus the whole `_withdraw` — to revert.
6. The Hyperbridge message delivery fails/reverts every time it is retried (the token stays armed), so the solver never receives the escrowed `USDC` either, and `_filled`/escrow state for the commitment never finalizes. The same failure mode applies to `RefundEscrow` via `_cancelFromDest`/`onGetResponse`, permanently freezing the user's `USDC` refund as well. [1](#0-0) [2](#0-1)

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
