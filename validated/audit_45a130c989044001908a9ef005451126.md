### Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while the `shop` (and `topic`, `webhook_id`, `api_version`) values are read directly from unauthenticated HTTP headers. `HmacValidator.validate` only verifies that the raw body was signed with the app's shared `api_secret_key` — it never binds that signature to the `shop-domain` header that `Registry.process` later trusts as the tenant identifier.

### Finding Description
`Request#hmac` and `Request#to_signable_string` are defined as: [1](#0-0) 

Note that `to_signable_string` returns `@raw_body` only — `shop`, `topic`, `webhook_id`, and `api_version` are parsed straight from headers and are not part of the signed content: [2](#0-1) 

`Registry.process` validates the HMAC over the whole `request` object, then immediately trusts `request.shop` (from the unauthenticated header) as the tenant identifier passed to the app's handler: [3](#0-2) 

`HmacValidator.validate` computes the signature from `verifiable_query.to_signable_string` (the raw body) and compares it against the received `hmac`, using the app-wide `api_secret_key` (the same secret is used for every shop the app serves): [4](#0-3) 

This breaks the identity binding: `shop header used for tenant routing == shop that produced the signed body`. The signature only proves *"this body was signed by our app secret"*, not *"this body came from shop X"*. Because the same `api_secret_key` signs webhooks for every shop connected to the app, a body that was legitimately signed for shop A remains HMAC-valid even if delivered with a `shopify-shop-domain` (or `x-shopify-shop-domain`) header claiming to be shop B.

### Impact Explanation
Any actor who can capture one authentic, HMAC-valid webhook delivery for a shop they control (e.g., a merchant who installed the app receiving their own real Shopify webhooks) can replay that exact body to the app's webhook endpoint while substituting the `shop-domain` header for a victim shop. `HmacValidator.validate` still returns `true` because only the body is checked, so `Registry.process` invokes the app's handler with `WebhookMetadata#shop` set to the victim shop while the payload content is fully attacker-controlled. Any host application that uses `request.shop` (or `WebhookMetadata#shop`) to select/update per-tenant data — the intended and documented use of this field — will write or act on attacker-controlled data under another merchant's identity, i.e., cross-tenant data injection/confusion.

### Likelihood Explanation
Exploitation requires no privileged credentials, no `api_secret_key`, and no access token: the attacker only needs to be a legitimate (even trial/unpaid) user of the same multi-tenant app, since app webhook secrets are shared across all installs, and only a single captured webhook body plus a forged header is needed to replay it against a different shop identifier.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the signed content, or verify the header-derived shop against an authenticated source (e.g., the shop associated with the currently active session/install) before trusting it in `Registry.process`. At minimum, `to_signable_string` should incorporate the shop/topic headers so `HmacValidator` fails when they're altered.

### Proof of Concept
1. App merchant A's browser/server receives a legitimate webhook from Shopify: headers `x-shopify-shop-domain: shop-a.myshopify.com`, `x-shopify-hmac-sha256: <valid-hmac-of-body>`, body `{"id":123,...}`.
2. Attacker (merchant A) resends the identical raw body and HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: shop-victim.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `@raw_body`; validation succeeds because the body/HMAC pair is untouched. [5](#0-4) 
4. The handler receives `WebhookMetadata.new(... shop: "shop-victim.myshopify.com", body: <attacker-controlled>, ...)` and, if the host app trusts this field for tenant routing (its documented purpose), stores/acts on the data as belonging to `shop-victim`.
