Confirmed vulnerability: `ShopifyAPI::Auth::TokenExchange.exchange_token` (`lib/shopify_api/auth/token_exchange.rb:29-89`) takes `dest_shop` straight from the JWT's `dest` claim and, unlike every sibling credential-issuing method in the same file/module (`migrate_to_expiring_token`, `ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, all of which call `Utils::ShopValidator.sanitize!`), never passes it through `ShopValidator`. The unsanitized `dest_shop` becomes the `HttpClient`'s target host, and the request body carrying `client_id`/`client_secret` is POSTed to that host.

### Title
Missing shop-domain validation in `TokenExchange.exchange_token` allows the app's `client_secret` to be sent to an attacker-controlled host - (File: lib/shopify_api/auth/token_exchange.rb)

### Summary
`TokenExchange.exchange_token` derives the OAuth token-exchange destination host directly from the session token's `dest` claim without validating it against `ShopifyAPI::Utils::ShopValidator`, unlike every other credential-sending flow in this gem. `JwtPayload` only checks `aud == Context.api_key`; it never verifies `dest`/`iss` resolve to a trusted Shopify domain (`myshopify.com`, `myshopify.io`, `spin.dev`, etc.). The unvalidated `dest_shop` is used to build the `HttpClient`'s base URI, and the client posts `client_id`+`client_secret` (the app's own OAuth credentials) to `https://#{dest_shop}/admin/oauth/access_token`.

### Finding Description
The identity binding that should hold is: `host receiving client_secret == a Shopify-trusted domain verified by ShopValidator`. This equality is broken in `exchange_token`:

- `jwt_payload.shop` returns `@dest.gsub("https://", "")` (`lib/shopify_api/auth/jwt_payload.rb:47-51`) with no allow-list check.
- `JwtPayload#initialize` only validates `@aud == Context.api_key` (`lib/shopify_api/auth/jwt_payload.rb:43-44`); it does not validate that `dest`'s domain is one of `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`.
- `exchange_token` uses this unvalidated value directly: `dest_shop = jwt_payload.shop` → `shop_session = Session.new(shop: dest_shop)` (`lib/shopify_api/auth/token_exchange.rb:40-51`).
- `Clients::HttpClient#initialize` sets `@base_uri = "https://#{api_host || session.shop}"` (`lib/shopify_api/clients/http_client.rb:18`), so `session.shop` directly becomes the request host.
- The POST body containing `client_id` and `Context.api_secret_key` is then sent to that host (`lib/shopify_api/auth/token_exchange.rb:52-59, 65-74`).

By contrast, `TokenExchange.migrate_to_expiring_token`, `ClientCredentials.client_credentials`, and `RefreshToken.refresh_access_token` all call `Utils::ShopValidator.sanitize!(shop)` before constructing the session/host used to send `client_secret` — demonstrating the intended invariant that any host receiving `client_secret` must first pass `ShopValidator`. `exchange_token` breaks that invariant for the `dest`-derived shop.

Since JWT session tokens are signed with HS256 using the shared `api_secret_key`, the signature does prove the token was minted by Shopify's backend for this app — but the code contains no additional confirmation that the `dest` value inside that token was constrained to a Shopify-owned domain before it is used as a network destination for secret material. This is exactly the "host validated versus host that receives the client_secret" identity-binding class called out in the rules: the code trusts JWT `aud`/signature validity as a proxy for "this dest is a safe host to send my client_secret to," which is a different check than actually confirming the host is Shopify-owned.

### Impact Explanation
If reached with a `dest` value outside the trusted Shopify domain set, this results in the app's `client_id` and `client_secret` being transmitted to a host of the token issuer's choosing — SSRF carrying the app's OAuth credentials, matching the "High - SSRF with the app's credentials" impact category.

### Likelihood Explanation
Reaching this path requires a session token accepted by `JwtPayload` (correct `aud`, valid HS256 signature, unexpired). Because the impact and root cause hinge on what values Shopify's backend can legitimately place in `dest` (e.g., non-canonical partner/custom-domain issuance paths, or future/atypical token issuers), and this gem's own code offers no defense-in-depth check here (unlike its sibling functions), the likelihood is best characterized as depending on operational/issuance conditions this gem does not control — but the missing safeguard itself is a concrete, verifiable code defect since the same library elsewhere treats this validation as mandatory for exactly this operation.

### Recommendation
In `exchange_token` (`lib/shopify_api/auth/token_exchange.rb`), validate `dest_shop` with `Utils::ShopValidator.sanitize!` (as already done in `migrate_to_expiring_token`, `client_credentials`, and `refresh_access_token`) before constructing `shop_session`/`HttpClient`, so the value used to route `client_secret` is guaranteed to be a trusted Shopify domain, and raise `Errors::InvalidShopError` otherwise.

### Proof of Concept
1. Obtain/receive a Shopify-issued session token (`session_token`) whose `dest` claim is not a `*.myshopify.com`/trusted domain (e.g., due to a non-standard issuance path); the token still passes `JwtPayload` validation because only `aud` is checked.
2. Call:
```ruby
ShopifyAPI::Auth::TokenExchange.exchange_token(
  session_token: session_token,
  requested_token_type: ShopifyAPI::Auth::TokenExchange::RequestedTokenType::OFFLINE_ACCESS_TOKEN,
)
```
3. Trace execution: `dest_shop = jwt_payload.shop` (unvalidated) → `Session.new(shop: dest_shop)` → `HttpClient.new(session: shop_session, base_path: "/admin/oauth")` sets `@base_uri = "https://#{dest_shop}"` → `client.request(...)` POSTs `{client_id, client_secret, ...}` to `https://#{dest_shop}/admin/oauth/access_token`, i.e., to whatever host the `dest` claim names, unlike the parallel `migrate_to_expiring_token` path which would have rejected an untrusted `dest_shop` via `ShopValidator.sanitize!`.
