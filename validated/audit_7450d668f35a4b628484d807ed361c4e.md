### Title
Token Exchange sends the app's `client_secret` to an unvalidated shop host taken from the JWT `dest` claim - ([File: lib/shopify_api/auth/token_exchange.rb])

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` builds the HTTP request host that receives the app's `client_secret` directly from the session token's `dest` claim, without ever checking that this host is a trusted Shopify domain. This breaks the intended binding: "the shop this app is authorized to talk to" should equal "the shop host the `client_secret` is sent to," but the code only validates the token's `aud` claim (that the token was minted for this app), never the `dest` claim (which host actually gets contacted).

### Finding Description
In `exchange_token`, the shop used to build the outgoing request is taken unvalidated from the JWT: [1](#0-0) 

`JwtPayload#shop` simply strips `https://` from the raw `dest` claim with no domain allow-listing: [2](#0-1) 

The only identity check performed on the token is that `aud == Context.api_key`, i.e. the token was issued for this app — the `dest` value itself is never checked against a trusted domain list: [3](#0-2) 

That unvalidated `dest_shop` value is then used to construct the `Session` whose `shop` attribute becomes the actual HTTP request host: [4](#0-3) 

`Clients::HttpClient#initialize` builds the base URI straight from `session.shop` with no host validation of its own: [5](#0-4) 

This is exactly the pattern the two neighboring/sibling flows explicitly guard against: `ClientCredentials.client_credentials` and `TokenExchange.migrate_to_expiring_token` both call `Utils::ShopValidator.sanitize!(shop)` — which restricts the host to `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`) — before using the shop to build the request host: [6](#0-5) [7](#0-6) [8](#0-7) 

`exchange_token` is the only one of the three OAuth-credential-sending flows that omits this `ShopValidator.sanitize!` call, so the identity binding "host validated (via `aud`)" ≠ "host that receives `client_secret` (via `dest`, unchecked)" is broken specifically here.

### Impact Explanation
If a session token with an attacker-controlled or malformed `dest` value is ever presented to `exchange_token` (e.g. a JWT correctly signed for this app but carrying a non-`myshopify.com`-style `dest`, such as from a non-admin token source like checkout/customer-account extensions, or a malicious/compromised token issuer flow), the library will POST the app's `client_id` and `client_secret` to that arbitrary host — an SSRF carrying the app's OAuth `client_secret` to a host the developer never intended to trust. This matches the "High - SSRF with the app's credentials" impact category.

### Likelihood Explanation
Exploitation requires a validly-signed session token for the app (attacker cannot forge the HMAC without knowing `api_secret_key`), so a fully external attacker without any valid token cannot trigger it directly. However, the gem accepts session tokens from any context (the test suite shows both admin and checkout/customer-account tokens sharing the same `JwtPayload` decoding path with different `iss`/`dest` shapes), and unlike the two sibling credential-sending methods, this path performs zero allow-listing of the destination host before sending `client_secret`. This is a missing defense-in-depth check that the codebase itself demonstrates is the established pattern (`ShopValidator.sanitize!`) for every other flow that sends the `client_secret` based on caller/token-supplied shop data.

### Recommendation
Validate `dest_shop` with `Utils::ShopValidator.sanitize!(dest_shop)` in `TokenExchange.exchange_token` before constructing `shop_session`, exactly as already done in `client_credentials` and `migrate_to_expiring_token`, so the `client_secret` can never be sent to a host outside `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`.

### Proof of Concept
1. Obtain (or have Shopify issue) a session token whose `dest` claim is `attacker-controlled-host.example.com` but which is otherwise validly signed for the app's `api_secret_key`/`api_key` (e.g., via any code path in the host application that forwards an untrusted or non-admin session token into `exchange_token`).
2. Call `ShopifyAPI::Auth::TokenExchange.exchange_token(session_token: token, requested_token_type: ...)`.
3. `dest_shop` is set to `attacker-controlled-host.example.com` without validation (`lib/shopify_api/auth/token_exchange.rb:41`).
4. `Clients::HttpClient.new(session: shop_session, base_path: "/admin/oauth")` builds `@base_uri = "https://attacker-controlled-host.example.com"` (`lib/shopify_api/clients/http_client.rb:18`).
5. The client POSTs `{ client_id, client_secret, subject_token, ... }` to `https://attacker-controlled-host.example.com/admin/oauth/access_token`, exfiltrating the app's `client_secret` to the attacker's host.
