### Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, but the `shop` field the gem exposes to the app's handler (and calls "the shop domain of the webhook" in the documentation) is read from an unsigned HTTP header, not from the signed payload. This breaks the identity binding: `shop authenticated == shop delivered to handler`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop` (as well as `topic`, `api_version`, `webhook_id`) is derived purely from HTTP headers that are never part of the signed string: [2](#0-1) 

`Registry.process` validates the HMAC against the body only, then immediately trusts `request.shop` and hands it to the app's handler as an authenticated fact: [3](#0-2) 

`Utils::HmacValidator.validate` recomputes the signature purely from `verifiable_query.to_signable_string`, which for a webhook is the raw body — the `shop-domain` header plays no role in the cryptographic check: [4](#0-3) 

The `WebhookMetadata` struct passed to the handler carries `shop` as a bare `String`, with no indication to downstream app code that this value is unauthenticated, and the gem's own docs describe it as simply "the shop domain of the webhook": [5](#0-4) [6](#0-5) 

Because the HMAC is computed only over `raw_body`, any request with a raw body/HMAC pair that is (or was) valid for shop A's webhook traffic remains HMAC-valid no matter what value is placed in the `shop-domain` (or `X-Shopify-Shop-Domain`) header. An unprivileged internet user who operates their own Shopify development shop and receives one legitimate webhook (e.g., `orders/create`) for that shop has a real `raw_body` + valid `hmac` pair signed with the app's secret. They can replay that exact `raw_body`/`hmac` to the app's public webhook endpoint while substituting an arbitrary `shop-domain` header (e.g., a victim's shop domain). `Utils::HmacValidator.validate` will accept it because the header is outside the signed bytes, and `Registry.process` will invoke the handler with `WebhookMetadata#shop` set to the attacker-chosen victim shop.

### Impact Explanation
This crosses the "shop authenticated versus shop delivered to app logic" boundary described in the analog rules — the equality `shop verified by HMAC == shop acted upon` does not hold, because `shop` is never covered by the signature at all. Any host application that keys off `data.shop` from `WebhookMetadata` (to select a merchant's session/access token, to write to a shop-scoped record, to decide which store's data to update/delete) can be tricked into performing that action against a shop chosen entirely by the attacker, while the HMAC check gives false assurance that the request is authentic per-shop. This is a cross-tenant impact: an attacker who onboards the app on their own store (a routine, unprivileged action) can produce a self-signed genuine webhook and use it to impersonate deliveries for other merchants of the same app.

### Likelihood Explanation
Likelihood is bounded by the fact that the attacker must possess at least one genuine `raw_body`/`hmac` pair produced by Shopify for the target app. This is trivially obtainable by installing the target app on the attacker's own (or a trial) shop and letting Shopify send any real webhook — no privileged access or leaked secret is required, since the attacker only needs to capture their own legitimate traffic to their own endpoint, not the secret itself. The `shop-domain` header can then be freely substituted, because it is outside the HMAC. This makes exploitation modest-effort but does not require the app's `client_secret` or any merchant credential.

### Recommendation
Bind the shop identity to the signed payload rather than trusting an unsigned header:
- Prefer deriving/validating `shop` for webhook processing from a value that Shopify includes inside the signed body (Shopify webhook payloads generally include shop-identifying fields in JSON, or the app can independently look up/confirm the shop against its own session store using the `webhook_id`/topic and an authenticated session rather than the raw header) so that spoofing the header alone cannot change the effective shop.
- At minimum, document explicitly in `WebhookMetadata`/`docs/usage/webhooks.md` that `shop` is derived from an unauthenticated header and must be independently corroborated (e.g., cross-checked against a known/registered shop for that webhook subscription) before being used for any tenant-scoped action.
- Consider incorporating the `shop-domain`, `topic`, `api-version`, and `webhook-id` headers into the HMAC-signed string used for verification if feasible, so header tampering invalidates the signature.

### Proof of Concept
1. Attacker installs the vulnerable app on their own shop `attacker.myshopify.com` and receives a real webhook delivery from Shopify (e.g., `orders/create`), capturing the exact `raw_body` and the `X-Shopify-Hmac-Sha256` value Shopify computed with the app's real secret.
2. Attacker sends the same `raw_body` and `X-Shopify-Hmac-Sha256` to the app's public webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `to_signable_string` (the raw body only) — validation succeeds because the body/HMAC pair is genuinely correct, independent of the shop header: [7](#0-6) 
4. The handler is invoked with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, even though the request was never signed for that shop, letting the attacker inject spoofed events attributed to an arbitrary tenant.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac

          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
