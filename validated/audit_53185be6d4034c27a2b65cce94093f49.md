### Title
Webhook shop/topic identity spoofing via HMAC that only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from HTTP headers that are never included in the signed payload. `Registry.process` validates the HMAC against the body only, then trusts the unsigned `shop` and `topic` header values to dispatch the handler and populate `WebhookMetadata`. This breaks the intended binding `HMAC-authenticated bytes == the identity (shop, topic) the app acts on`.

### Finding Description
`Webhooks::Request#to_signable_string` is defined as: [1](#0-0) 
while `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from HTTP headers with no cryptographic tie to the body: [2](#0-1) 

`Registry.process` validates only the body-derived HMAC via `Utils::HmacValidator.validate(request)`, and then uses the unauthenticated `request.shop` and `request.topic` to select a handler and build the metadata handed to app code: [3](#0-2) 

`Utils::HmacValidator.validate` computes the signature purely from `to_signable_string` (the raw body) and compares it to the `hmac` header: [4](#0-3) 

Because the HMAC only binds the raw body, any payload that was legitimately signed by Shopify for *some* webhook (e.g., a webhook the attacker's own store received, since a merchant fully controls webhook delivery to their own installed app instance and thus possesses valid `(body, hmac)` pairs) can be replayed to the app's webhook endpoint with a different `x-shopify-shop-domain` header and/or a different `x-shopify-topic` header. `HmacValidator.validate` will still pass because it never inspects those headers, yet `Registry.process` passes the attacker-chosen `shop` and `topic` on to the handler as if they were authenticated. The equality the gem should enforce -- "shop/topic asserted to the handler" == "shop/topic that Shopify actually signed" -- does not hold.

### Impact Explanation
This lets an attacker who possesses one valid `(raw_body, hmac)` pair (trivially obtainable by installing the app on their own store and capturing a real webhook delivery) present that payload as if it originated from a different tenant (`shop`) or under a different `topic`. Depending on how the host app's `WebhookHandler` implementations key data by `shop` (which is the normal, documented pattern shown in `docs/usage/webhooks.md` and enforced nowhere else in the gem), this enables cross-tenant data injection: writing or triggering actions against another merchant's records using a signature that was never generated for that merchant. It also allows topic confusion, e.g., replaying a signed body under a mandatory-compliance topic (`customers/redact`, `shop/redact`) it was never issued for. This matches the "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires only that the attacker be a legitimate but unprivileged installer of the target app on their own shop (no special privileges, no leaked secrets, no TLS interception) — a scenario squarely within "unprivileged internet user." Capturing a valid webhook body+HMAC from their own store's install and re-POSTing it with forged `x-shopify-shop-domain`/`x-shopify-topic` headers to the app's public webhook endpoint is straightforward, since the gem itself performs no binding check between the signed bytes and those header-derived identity fields.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signable string used for HMAC verification (or otherwise cryptographically bind them to the signed payload), so `Utils::HmacValidator.validate` fails if any of these header values are altered relative to what Shopify actually signed.

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com`; receive a genuine webhook delivery for topic `orders/create` with body `B`, and valid header `x-shopify-hmac-sha256: H` (computed by Shopify over `B` with the app's real secret).
2. Replay the exact same `B`/`H` to the app's webhook endpoint, but set `x-shopify-shop-domain: victim.myshopify.com` and, optionally, `x-shopify-topic: customers/data_request`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the signature from `request.to_signable_string` (`= B`) and the app secret — matches `H`, validation passes: [5](#0-4) 
4. The handler is invoked with `WebhookMetadata` claiming `shop: "victim.myshopify.com"` and the forged `topic`, even though Shopify never signed anything for that shop/topic combination.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
