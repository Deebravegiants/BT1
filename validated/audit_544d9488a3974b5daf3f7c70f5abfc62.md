### Title
Webhook shop/topic attribution not covered by HMAC signature enables cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw request body only, while `shop`, `topic`, `api_version`, and `webhook_id` are read directly from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` validates only the body HMAC and then dispatches the handler using the unauthenticated `shop` and `topic` header values. This breaks the identity binding: `shop attributed to the webhook payload != shop actually covered by the HMAC`, allowing an attacker who possesses any one validly-signed `(body, hmac)` pair for the app's `client_secret` to relabel that payload as coming from an arbitrary other shop.

### Finding Description
The signable content used for HMAC verification is defined as: [1](#0-0) 

Only `@raw_body` is signed. All of the tenant-identifying fields, `shop`, `topic`, `api_version`, and `webhook_id`, come straight from HTTP headers and are excluded from the signable string: [2](#0-1) 

`ShopifyAPI::Webhooks::Registry.process` verifies HMAC using this incomplete signable string, then trusts `request.shop` and `request.topic` (the unauthenticated header values) to dispatch to the topic handler and construct `WebhookMetadata`: [3](#0-2) 

`Utils::HmacValidator.validate` only checks that `computed_signature(to_signable_string) == received hmac`, so it never ties the signature to the `shop`/`topic` headers: [4](#0-3) 

Because a single app's `api_secret_key` is shared across all shops that install the app, any merchant (an unprivileged party with respect to other tenants of the same app) can legitimately trigger a real webhook delivery to the app for their own shop, capturing a valid `(raw_body, hmac-sha256)` pair signed with the app's secret. That pair can then be replayed to the app's webhook endpoint with the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header rewritten to name a different, victim shop. `HmacValidator.validate` still succeeds because it only checks the body against the hmac, and `Registry.process` will hand the (attacker-controlled) body to the handler while claiming it belongs to the victim shop.

### Impact Explanation
This is a cross-tenant identity confusion at the boundary between the cryptographically-verified data (body) and the trusted-but-unverified tenant attribution (`shop` header). Depending on how the hosting application's webhook handlers use `WebhookMetadata#shop` (e.g., to look up/update per-shop records, react to `app/uninstalled` by purging shop data, or to update order/product state keyed by `shop`), this can lead to actions or data being applied against the wrong tenant, i.e., cross-tenant access/manipulation, using only the attacker's own legitimately-signed webhook traffic. This matches the Critical severity bucket for cross-tenant access.

### Likelihood Explanation
The `client_secret`/`api_secret_key` is identical for every shop that has installed a given app, so any existing merchant of that app (which requires no special privilege beyond installing a public app, i.e., "unprivileged internet user" relative to other tenants) can obtain a validly-signed body/hmac pair by simply generating events in their own store. Replaying that request with a modified `shop-domain` header requires only direct HTTP access to the app's public webhook endpoint. No access token, client_secret, or victim credentials are needed.

### Recommendation
- **Short term:** Include the tenant-identifying headers (`shop`, `topic`, and ideally `webhook_id`) in the value that is HMAC-verified, or otherwise cryptographically bind them to the body before dispatch, so that a re-attributed replay fails validation. At minimum, cross-check `request.shop` against a shop already known/authorized for this app installation before invoking handlers.
- **Long term:** Document explicitly that `Utils::HmacValidator.validate` only authenticates the raw body, and that any header value used for tenant routing must be independently authenticated by the calling application (e.g., only accept webhooks for a `shop` that is a) still installed and b) matches the target the webhook was registered against).

### Proof of Concept
1. App merchant A installs a public app; A's own store can legitimately trigger a real webhook (e.g., `products/update`) to the app's endpoint. Capture the raw JSON body and the `X-Shopify-Hmac-Sha256` header value — both are signed with the app's shared `api_secret_key`.
2. Replay the exact same `(raw_body, hmac)` to the app's webhook endpoint, but replace the `X-Shopify-Shop-Domain` header with `victim-shop.myshopify.com` (and, if desired, change `X-Shopify-Topic` to a more impactful topic such as `app/uninstalled`).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks the body/hmac pair (`lib/shopify_api/utils/hmac_validator.rb:12-31`) — validation succeeds.
4. The registered handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), where `shop` is `victim-shop.myshopify.com` even though the payload actually originated from attacker A's own store.
