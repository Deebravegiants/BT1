## Analysis

The `IntentGatewayV2.sol` contract on Tron declares `using SafeERC20 for IERC20;` and uses `safeTransferFrom` for pulling tokens in `placeOrder`, but for outgoing payouts it drops to raw low-level `.call(abi.encodeWithSelector(...))` and only checks the boolean `success` of the call itself — never decoding/validating the returned data. [1](#0-0) [2](#0-1) 

This is exactly the bug class from the external report: mixing safe ERC20 wrappers with raw `abi.encodeWithSelector` calls, checking only call `success` and ignoring the ABI-encoded boolean return value that a non-compliant/failing ERC20 `transfer` may set to `false`.

### Title
Unchecked raw `IERC20.transfer` low-level calls in `IntentGatewayV2.withdraw`/`onAccept` can permanently freeze escrowed funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`withdraw()` and the `SweepDust` branch of `onAccept()` pay out escrowed tokens using a raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` and only check `success` from the low-level call, without decoding/validating the returned `bool`. [3](#0-2) [4](#0-3) 

### Finding Description
`withdraw()` is invoked from `onAccept()` on `RequestKind.RedeemEscrow`/`RequestKind.RefundEscrow`, and from `onGetResponse()` after a cancellation storage-proof response — both reachable via normal cross-chain ISMP message delivery relayed by any unprivileged relayer, no admin privilege required. [5](#0-4) [6](#0-5) 

Inside `withdraw()`, for each escrowed ERC20 token the contract does:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
_orders[body.commitment][token] -= amount;
```
A low-level `.call` only reverts (`success == false`) if the target reverts or the call fails for gas/EVM reasons. Any ERC20 (or Tron TRC20) implementation that returns `false` instead of reverting on transfer failure (a well-known category of "non-standard" tokens, e.g. legacy tokens) will make `success == true` while no tokens are actually moved. The code proceeds to decrement `_orders[commitment][token]` and mark `_filled[commitment] = beneficiary`, permanently recording the order as settled even though the beneficiary never received the funds — the escrowed balance is irretrievably lost because a later withdraw attempt hits `UnknownOrder` (since `_orders` was already zeroed) and `cancelOrder` will find `_filled[commitment] != address(0)` and revert with `Filled()`.

The same unchecked pattern also appears in the `SweepDust` handler and in the transaction-fee payout at the end of `withdraw()`. [7](#0-6) 

### Impact Explanation
For any ERC20/TRC20 token used as an order input that does not strictly follow the `transfer` "revert-on-failure" convention, a single successful cross-chain message delivery (RedeemEscrow/RefundEscrow) permanently zeroes the internal escrow accounting and marks the order as filled, while the beneficiary never actually receives the tokens. This results in permanent freezing/loss of the escrowed user funds with no recovery path, since both the `withdraw` retry path (`UnknownOrder`) and the `cancelOrder` path (`Filled`) are blocked afterward.

### Likelihood Explanation
This does not require a malicious actor — it only requires an ERC20 token that returns `false` on transfer failure (a known real-world token behavior class) being used as an order's input/fee token, combined with any condition causing the transfer to fail (e.g., temporary blacklist, pause, insufficient contract balance due to accounting drift, or a non-standard Tron TRC20 with return-value quirks). Given the contract explicitly imports and partly uses `SafeERC20` yet inconsistently falls back to raw calls for payouts, the risk of this exact scenario is realistic on a contract intended to be token-agnostic across many destination chains.

### Recommendation
Use `SafeERC20.safeTransfer` (already imported and used elsewhere in the file via `using SafeERC20 for IERC20;`) consistently for all outgoing ERC20 transfers in `withdraw()` and the `SweepDust` branch of `onAccept()`, instead of raw `token.call(abi.encodeWithSelector(...))` checks that ignore the decoded boolean return value.

### Proof of Concept
1. A solver/relayer causes an order to be placed with an ERC20 input token whose `transfer` implementation returns `false` (rather than reverting) when the transfer cannot be completed (e.g., insufficient balance in edge conditions, blacklist, or non-standard token behavior).
2. A legitimate `RedeemEscrow`/`RefundEscrow` ISMP message is delivered and processed by `onAccept` → `withdraw`.
3. `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` succeeds at the call level (`success == true`) but the token's internal logic returns `false` and does not move funds.
4. `withdraw()` does not check the returned boolean, so it proceeds to zero `_orders[commitment][token]` and mark `_filled[commitment] = beneficiary`.
5. The beneficiary never receives the tokens; any retry reverts with `UnknownOrder`, and `cancelOrder` reverts with `Filled()` — the escrowed tokens are permanently stuck in the contract with no beneficiary or refund path.
