### Title
Webhook `shop` header is not covered by the HMAC digest, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw JSON body, never the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers. `Registry.process` uses `Utils::HmacValidator.validate(request)` as its sole authenticity gate before forwarding `request.shop` to the app's handler as the trusted tenant identifier. Because the `shop` field is not bound into the signed bytes, any entity capable of obtaining one legitimately-signed `(body, hmac)` pair for their own shop can splice a different `shop-domain` header onto the same body/hmac pair and have it pass validation as if it were sent by the victim shop.

### Finding Description
`api_secret_key` is the app's single client secret and is shared across every shop that installs the app; Shopify signs every webhook body with this same secret regardless of which shop it originates from. The gem's `HmacValidator.validate` only checks that `hmac == HMAC-SHA256(raw_body, api_secret_key)` [5](#0-4) ; it never incorporates `shop`, `topic`, or `webhook_id` into the signed material, because `Request#to_signable_string` deliberately returns only `@raw_body` [1](#0-0) .

The identity binding broken is:
`shop asserted to the handler (request.shop, taken from an unauthenticated header)` ≠ `shop that actually produced the signed bytes (unbound by the HMAC)`.

Any party who has legitimately installed the app on their own shop can capture one authentic webhook delivery (raw body + valid `x-shopify-hmac-sha256`), then replay that exact `(body, hmac)` pair to the app's public webhook endpoint while substituting `x-shopify-shop-domain` for a victim shop. `HmacValidator.validate` still returns `true` because it only re-hashes the body, and `Registry.process` forwards this forged shop into `WebhookMetadata#shop` without any further check [3](#0-2) , so the app's handler acts on attacker-controlled data believing it came from the victim tenant — a cross-tenant identity confusion entirely internal to this gem's own verification API.

### Impact Explanation
This is a cross-tenant boundary break: an attacker with access to only their own shop's webhook traffic can make the host application believe a webhook (and its `shop` claim) originated from a different, victim shop. Any app logic keyed on `data.shop` (e.g., looking up which merchant's records to update, dispatching background jobs "for shop X") can be tricked into acting on the wrong tenant, satisfying the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Exploitation only requires installing the app on an attacker-controlled shop (a normal, unprivileged action any merchant/developer can perform) and capturing one legitimate webhook delivery to their own endpoint/log, then replaying it with a substituted `shop-domain` header to the app's public webhook route. No access to `api_secret_key` or any credential belonging to the victim is needed.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the value that is HMAC-verified, or independently corroborate `request.shop` against a value that is cryptographically tied to the request (e.g., verify the shop against the webhook subscription that Shopify created, or require the app to look up/validate the shop via an authenticated API call) rather than trusting an unauthenticated header field once only the body's HMAC has been checked.

### Proof of Concept
1. Install the target app on attacker-owned shop `attacker.myshopify.com`; trigger any webhook and capture the raw POST body and its `x-shopify-hmac-sha256` header — both are validly signed with the app's shared `api_secret_key`.
2. Construct a new request to the app's webhook endpoint reusing the exact same raw body and `x-shopify-hmac-sha256` value, but set `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` is built from these headers; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only hashes `raw_body` [2](#0-1) .
4. The registered handler is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)` [6](#0-5) , and the app processes attacker-supplied data under the victim's tenant identity.

          received_signature = verifiable_query.hmac
