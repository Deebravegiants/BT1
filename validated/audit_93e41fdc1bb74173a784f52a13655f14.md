### Title
Missing correlation between `/v2/resume/:runID` callback and the specific outstanding bridge request allows acceptance of unsolicited async task results - (File: core/web/pipeline_runs_controller.go)

### Summary
The `PipelineRunsController.Resume` handler, which backs the unauthenticated `PATCH /v2/resume/:runID` (aliased `/v2/pipeline_runs/:runID`) callback used by async bridge/external adapters to deliver results, resumes a suspended pipeline run based solely on the `runID` (task UUID) path parameter, with no verification that the caller is the specific adapter the node actually sent the pending request to, and no secret/nonce bound to that specific outstanding request beyond the UUID itself. [1](#0-0) 

### Finding Description
This mirrors the SAML bug class: a response-consuming endpoint accepts an incoming message correlated only by an identifier that was handed out at request time (`RelayState`/`InResponseTo` in SAML; task UUID here), without validating that the response actually originates from — or is bound to — the specific outstanding request/recipient the node solicited.

When a job pipeline contains an `async=true` bridge task, `BridgeTask.finalizeAndMarshalBridgeRequestData` embeds a `responseURL` of the form `<BridgeResponseURL>/v2/resume/<taskUUID>` in the outgoing request body sent to the external adapter: [2](#0-1) 

The adapter is expected to `PATCH` back to that URL later with the result. The audit log name for this action, `UnauthedRunResumed`, itself documents that the endpoint is intentionally unauthenticated: [3](#0-2) 

`Resume` parses only the `runID` (a `uuid.UUID`) from the URL, decodes the JSON body into a `pipeline.ResumeRequest`, and immediately calls `App.ResumeJobV2(ctx, taskID, result)` — there is no check of a shared secret, an `InResponseTo`-style correlation to the originating request context, sender identity, or IP allowlisting: [4](#0-3) 

`ResumeJobV2`/`Runner.ResumeRun` then unconditionally applies the attacker-supplied `value`/`error` to the task run identified purely by that UUID and restarts the pipeline: [5](#0-4) 

Because the only "credential" binding a response to its request is the task UUID embedded in the outbound `responseURL`, and that UUID is not treated as a high-entropy bearer secret protected end-to-end (it can leak via adapter logs, proxies, SSRF-reachable adapters, or a compromised/malicious external adapter that was legitimately contacted for an unrelated run), anyone who obtains or guesses a pending run's UUID can post a forged result and force the run to resume with attacker-controlled data — the exact class of "accept a response the service never requested from the expected party" that CVE-2026-53425 describes for Samly's missing `InResponseTo` check.

### Impact Explanation
An attacker who learns (or otherwise obtains) a pending task UUID can inject arbitrary `value`/`error` into a suspended pipeline run via an unauthenticated HTTP call, causing the job to resume with attacker-controlled data. Depending on the job's downstream tasks (e.g., feeding into a `median`/`ETHTx` task), this can corrupt on-chain reported values or trigger unintended transactions, which qualifies as cross-user/cross-request response confusion and potential unauthorized job run manipulation.

### Likelihood Explanation
Exploitation requires knowledge of a live task UUID (v4 UUIDs are high-entropy, so blind guessing is impractical), but the UUID is not treated as a strict secret: it is embedded in plaintext in outbound bridge request bodies to third-party external adapters, may be logged, cached, or exposed via adapter-side systems, and the endpoint enforces no additional authentication, rate limiting tied to the run, or IdP/adapter identity check. Given a real leak vector (compromised or malicious external adapter, logging systems, SSRF, network capture), likelihood is realistic though not trivial — comparable to the "attacker obtains a validly-signed assertion for their own account" precondition in the original SAML report.

### Recommendation
Bind the `/v2/resume/:runID` callback to the specific outstanding request instead of relying on the UUID alone: generate and store a per-task, single-use, high-entropy resume token (independent from the task UUID used for lookup) that must be supplied and validated on the `Resume` call; alternatively/additionally, restrict `BridgeResponseURL` callbacks to expected adapter origins and enforce that a task can only be resumed once (defense already exists at the state-machine level, but should be paired with a real credential check) and add authentication (shared bridge secret or mTLS) to the resume endpoint.

### Proof of Concept
1. Configure a job with an `async=true` bridge task; the node sends a request to the external adapter containing `responseURL: https://node/v2/resume/<taskUUID>`.
2. An attacker who obtains `<taskUUID>` (e.g., via a compromised adapter log, MITM on the adapter call, or SSRF) sends:
   `PATCH /v2/resume/<taskUUID>` with body `{"error": null, "data": {"result": "<attacker-controlled value>"}}`.
3. `PipelineRunsController.Resume` [4](#0-3)  accepts the request without verifying the sender is the original adapter, calls `ResumeJobV2`→`Runner.ResumeRun` [5](#0-4) , and the pipeline resumes using the forged value as if the legitimate adapter had replied.

// Resume finishes a task and resumes the pipeline run.
// Example:
// "PATCH <application>/jobs/:ID/runs/:runID"
func (prc *PipelineRunsController) Resume(c *gin.Context) {
	taskID, err := uuid.Parse(c.Param("runID"))
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	rr := pipeline.ResumeRequest{}
	decoder := json.NewDecoder(c.Request.Body)
	err = errors.Wrap(decoder.Decode(&rr), "failed to unmarshal JSON body")
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}
	result, err := rr.ToResult()
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	if err := prc.App.ResumeJobV2(c.Request.Context(), taskID, result); err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	prc.App.GetAuditLogger().Audit(audit.UnauthedRunResumed, map[string]any{"runID": c.Param("runID")})
	c.Status(http.StatusOK)
}

func (r *runner) ResumeRun(ctx context.Context, taskID uuid.UUID, value any, err error) error {
	run, start, err := r.orm.UpdateTaskRunResult(ctx, taskID, Result{
		Value: value,
		Error: err,
	})
	if err != nil {
		return fmt.Errorf("failed to update task run result: %w", err)
	}

	// TODO: Should probably replace this with a listener to update events
	// which allows to pass in a transactionalised database to this function
	if start {
		// start the runner again
		go func() {
			ctx, cancel := r.chStop.NewCtx()
			defer cancel()
			if _, err := r.Run(ctx, &run, false, nil); err != nil {
				r.lggr.Errorw("Resume run failure", "err", err)
			}
			r.lggr.Debug("Resume run success")
		}()
	}
	return nil
}
