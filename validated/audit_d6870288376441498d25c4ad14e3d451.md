### Title
`SessionUtils.cookie_session_id` returns an unsigned, attacker-chosen cookie value as the storage lookup key, enabling deterministic offline-session-id guessing - (File: `lib/shopify_api/utils/session_utils.rb`)

### Summary
`cookie_session_id` returns `cookies['shopify_app_session']` verbatim with no HMAC/signature verification. Because non-embedded offline sessions are persisted under the fully deterministic id `"offline_#{shop}"` (set in `Auth::Session.from` and mirrored into the cookie by `Oauth.validate_auth_callback`), any attacker who knows a victim's `.myshopify.com` domain can set that exact string as their own `shopify_app_session` cookie value and have the gem hand back that id as "the" session key.

### Finding Description
The binding under test is: `cookie_session_id(cookies) == cookies['shopify_app_session']`, unconditionally, with no relation to who set that cookie or whether the caller is authenticated as that shop. [1](#0-0) 

Trace:
- `current_session_id` is the entrypoint; for non-embedded apps (or embedded apps without a JWT) it requires only that *some* cookie named `shopify_app_session` be present, then forwards it unmodified via `cookie_session_id`. [2](#0-1) 
- The cookie value is originally produced by `Oauth.validate_auth_callback`: for non-embedded apps the `SessionCookie` value is set to `session.id`. [3](#0-2) 
- For offline sessions, `Session.from` computes `id = "offline_#{shop}"` — fully deterministic from the public shop domain, not a random secret. [4](#0-3) 
- `SessionUtils.offline_session_id` (used on the JWT path) computes the identical deterministic string `"offline_#{shop}"`, confirming this id format is treated as the canonical storage key across the whole gem. [5](#0-4) 

Exploit flow: an attacker (their own dev shop, no credentials on victim) sends a request to any host-app route that resolves the current session via `SessionUtils.current_session_id`, with header `Cookie: shopify_app_session=offline_victim-shop.myshopify.com`. `cookie_session_id` returns that exact string unchanged. If the host app (as documented) then does `session_storage.load_session(session_id)`, it retrieves the *victim's* persisted `Session` object — including `access_token` and `refresh_token` — and treats the request as authenticated for the victim shop, all without ever validating an HMAC, signature, or ownership of that cookie value.

Why existing guards don't stop this:
- `HmacValidator.validate` only guards the OAuth *callback* query string, not routine app requests that use the session cookie.
- `state` comparison in `validate_auth_callback` only protects the OAuth handshake itself, not subsequent session lookups via the cookie.
- `covers?` / `expired?` on `Session` are evaluated only *after* the (attacker-chosen) session object has already been loaded from storage — they check scope/expiry of whatever session was fetched, they do not verify that the *caller* is entitled to that particular session id.
- `JwtPayload`'s `aud`/`iss` checks apply only to the embedded JWT path, not the cookie fallback path.
- Nothing in `cookie_session_id` or `current_session_id` ties the incoming cookie to the browser session that actually completed OAuth for that shop (no HttpOnly/Secure/SameSite enforcement is in this gem's control, and even with those, the *value* itself is guessable/known rather than a random secret for the offline case).

### Impact Explanation
If exploitable end-to-end, this exposes a merchant's persisted offline `access_token`/`refresh_token` to any third party who knows the shop's `.myshopify.com` domain (public information, often visible in storefront URLs). This is a cross-tenant identity confusion: the "identity" loaded is determined solely by an unauthenticated cookie value, not by any verified credential. Repeatable against any victim shop whose domain is known and who has installed an app using this session-cookie fallback. This matches "theft of a merchant's refresh token, granting durable access after rotation" if the host app's `SessionStorage#load_session` returns the object for an arbitrary supplied id without additional binding.

### Likelihood Explanation
This requires (a) a non-embedded app, or an embedded app falling back to the cookie path, (b) the host app using `SessionUtils.current_session_id` followed directly by a session-storage lookup on the returned id per the documented pattern, and (c) the attacker knowing the victim's shop domain. The `id` format `"offline_#{shop}"` is a fixed, documented/internal convention rather than a secret nonce, so no brute-forcing is needed — only knowledge of the shop domain. Attacker cost is a single crafted HTTP request with a forged `Cookie` header; no secrets, no signature computation, no timing attack required.

I was not able to fully verify, within this repo alone, whether host-app session-storage implementations perform any additional authorization check before returning a session for a given id (that logic lives outside `lib/shopify_api/**`, largely in example/host apps, not in this gem). The gem's own `cookie_session_id`/`current_session_id` code contains no such check, which is the crux of the flaw described.

### Recommendation
Do not use a deterministic, guessable string (`"offline_#{shop}"`) as a bearer-style lookup key for the session cookie. Either (a) generate a random, unguessable session id/cookie value (e.g., `SecureRandom.uuid`) decoupled from the shop domain, or (b) sign/HMAC the cookie value with `Context.api_secret_key` and verify that signature in `cookie_session_id` before returning it, so a forged cookie cannot be used to select an identity.

### Proof of Concept
```ruby
# test/utils/session_utils_test.rb (new test)
def test_cookie_session_id_returns_guessable_offline_id_unverified
  shop = "victim-shop.myshopify.com"
  forged_cookie_value = "offline_#{shop}" # attacker knows only the public shop domain
  cookies = { ShopifyAPI::Auth::Oauth::SessionCookie::SESSION_COOKIE_NAME => forged_cookie_value }

  returned_id = ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)

  # BROKEN BINDING: the gem returns the victim's real storage key
  # with no signature/ownership check tying it to this attacker's request.
  assert_equal(forged_cookie_value, returned_id)
  assert_equal("offline_#{shop}", ShopifyAPI::Utils::SessionUtils.offline_session_id(shop))
  # Demonstrates returned_id == the exact key under which the victim's
  # Session (containing access_token/refresh_token) would be stored.
end
```
This confirms `cookie_session_id`/`current_session_id` perform no signature check and return an attacker-suppliable, deterministically-guessable identifier as the trusted session key.
