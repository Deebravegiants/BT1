### Title
Missing Chainlink `minAnswer`/`maxAnswer` circuit-breaker check lets `SimplexPaymaster` mis-price gas fees during an oracle price crash - (File: evm/src/utils/SimplexPaymaster.sol)

### Summary
`SimplexPaymaster._getOraclePrice` only validates that the Chainlink `answer` is positive and not stale, but never checks it against the aggregator's `minAnswer`/`maxAnswer` circuit-breaker bounds. If the underlying asset's real price falls (or spikes) outside that range, Chainlink's aggregator keeps reporting the clamped `minAnswer`/`maxAnswer` instead of the true price, and any unprivileged UserOperation sender routed through this paymaster gets priced off that stale/incorrect value.

### Finding Description
`_getOraclePrice` fetches `latestRoundData()` and only guards against non-positive or stale answers: [1](#0-0) 

This value feeds directly into `_tokenPrice`, which is used to compute how much ERC-20 token a UserOperation sender must pay for gas (`_fetchDetails` -> `_tokenPrice`) and into `swapAndDeposit`'s minimum-output calculation: [2](#0-1) [3](#0-2) 

`nativeUsd`/`tokenUsd` feeding `swapAndDeposit`'s expected-output math: [4](#0-3) 

Neither `_getOraclePrice` nor its callers compare `answer` to the feed's configured `minAnswer`/`maxAnswer`. As Chainlink documents, if an asset (native gas token or a registered ERC-20 fee token) undergoes a severe price collapse (or spike) that exceeds the aggregator's configured range, `latestRoundData()` keeps returning the clamped bound rather than the real price, while still passing the `answer > 0` and staleness checks in `_getOraclePrice`.

### Impact Explanation
`_tokenPrice` computes `tokenPrice = nativeUsd * 10^tokenDecimals * (1+markup) / tokenUsd`, i.e. the amount of the ERC-20 fee token an unprivileged UserOperation sender (a "bandwidth purchaser" of gas) pays per unit of gas.
- If the registered ERC-20 fee token's real price collapses below its feed's `minAnswer`, `tokenUsd` stays inflated at `minAnswer`, so `tokenPrice` is computed too low — any UserOp sender can pay for gas using an effectively worthless token at the stale higher valuation, draining the paymaster's native-asset-backed EntryPoint deposit/treasury for a fraction of its real cost.
- Conversely, if the native asset's price collapses, `nativeUsd` stays inflated, overcharging every UserOp sender in the affected fee token.
- `swapAndDeposit` derives its slippage-protected `amountOutMin` from the same unclamped oracle values, so a stuck price can also make treasury-triggered fee recycling execute against a stale valuation.

This is a permissionless, fully reachable path: any account can submit an ERC-4337 UserOperation that specifies a registered token in `paymasterData`, triggering `_fetchDetails`/`_tokenPrice`/`_getOraclePrice` with no privileged action required.

### Likelihood Explanation
This requires a genuine, extreme market event (a supported native asset or fee token crashing/spiking past the Chainlink feed's configured band, as happened with LUNA on Venus/BSC). It is not attacker-controlled by itself, but once such an event occurs, exploitation by any ordinary UserOp sender is trivial and immediate — no special privileges, timing races, or governance access are needed to profit from or be harmed by the stuck price.

### Recommendation
In `_getOraclePrice`, fetch and cache each feed's `minAnswer`/`maxAnswer` (via the aggregator's `aggregator()`/`AggregatorInterface` or a configured bound) and revert (as `InvalidOraclePrice`) when `answer <= minAnswer || answer >= maxAnswer`, matching the pattern:
```solidity
require(answer > minAnswer && answer < maxAnswer, "invalid price");
```
so a circuit-breaker-clamped price causes the paymaster to reject pricing (falling back to `TokenNotActive`-style safety) instead of silently mispricing gas.

### Proof of Concept
1. Governance registers token `T` with Chainlink feed `F` whose aggregator has `minAnswer = $0.90` (scaled).
2. `T`'s real market price crashes to `$0.10` due to a depegging/exploit event; Chainlink's aggregator, per its circuit breaker, keeps `latestRoundData()` returning `answer = minAnswer = $0.90`.
3. `_getOraclePrice(tokenOracle, ...)` passes both the `answer <= 0` and staleness checks and returns `$0.90`-equivalent, even though `T` is worth `$0.10`.
4. Any user submits a UserOperation with `paymasterData` selecting token `T`; `_fetchDetails` -> `_tokenPrice` computes `tokenPrice` based on the inflated `$0.90` value.
5. The user pays gas costs priced as if `T` were worth `$0.90`, while only transferring tokens actually worth `$0.10`, draining the paymaster's EntryPoint deposit relative to the token collected — repeatable for every UserOperation until governance detects the issue and calls `DeactivateToken`.

```text
    /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
```
