### Title
Unchecked ERC20 `transfer` return value breaks escrow accounting on Tron `IntentGatewayV2.withdraw` - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron variant of `IntentGatewayV2` releases escrowed order tokens and protocol fees using a raw low-level `.call()` to `IERC20.transfer`, checking only that the call did not revert while discarding the ABI-encoded boolean return data. Non-standard ERC20 tokens that return `false` on failure instead of reverting will cause the withdraw path to silently "succeed" while no tokens are actually delivered, permanently desynchronizing the escrow ledger from actual token balances.

### Finding Description
`IntentGatewayV2.withdraw()` is the internal function invoked from `onAccept()` for `RequestKind.RedeemEscrow` / `RequestKind.RefundEscrow` and from `onGetResponse()` after a cross-chain cancellation check [1](#0-0) . For each escrowed token it performs:

```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
``` [2](#0-1) 

and identically for the protocol fee redemption:
```solidity
(bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
if (!success) revert TransferFailed();
``` [3](#0-2) 

The `success` boolean returned by Solidity's low-level `.call()` only indicates that the callee did not revert — it says nothing about the ABI-decoded `bool` that `transfer` is supposed to return. Any ERC20 token that returns `false` on a failed transfer (rather than reverting) — a well-known non-standard-but-common pattern (e.g., early ZRX, BNB, and many others) — will make this call return `success = true` even though the beneficiary received nothing. The code discards the returned bytes (`token.call(...)` result destructured as `(bool success,)`), so it never validates the actual transfer outcome.

Critically, this contract already imports OpenZeppelin's `SafeERC20` and uses `safeTransferFrom`/pattern correctly elsewhere in the same file (e.g. lines 405, 459), and its sibling non-Tron implementation (`evm/src/apps/intentsv2/IntentsBase.sol`) uses `IERC20(token).safeTransfer(beneficiary, amount)` for the equivalent operation [4](#0-3) , confirming the raw-call pattern in the Tron `withdraw()`/`onAccept` SweepDust path is a regression rather than an intentional design choice.

Immediately after the unchecked transfer, the code unconditionally decrements the internal escrow accounting: `_orders[body.commitment][token] -= amount;` [5](#0-4) , and `_filled[body.commitment] = beneficiary` is set before any transfer occurs, at the top of `withdraw()` [6](#0-5) . This means the order is marked filled/settled and the escrow balance is spent in storage regardless of whether the beneficiary (the cross-chain filler/solver, or the user being refunded) actually received the tokens. The same unchecked pattern also appears in the `SweepDust` handler inside `onAccept` [7](#0-6) .

### Impact Explanation
This is a High severity token-bridge/intents synchronization bug reachable by any relayer delivering a legitimate, authenticated `RedeemEscrow`/`RefundEscrow`/`SweepDust` cross-chain message for an order that used a "silent-failure" ERC20 as its input/fee token. Since `_filled` and `_orders` are updated as if the transfer succeeded, the escrowed tokens become permanently stuck in the `IntentGatewayV2` contract (the accounting says they are released, so no other code path can re-attempt or reclaim them), and the intended beneficiary (solver or user) never receives their funds — a permanent freezing/loss of user or solver funds without requiring any malicious relayer, admin, or governance action.

### Likelihood Explanation
Likelihood is Medium-High: it requires only that the order's input token or the host's configured fee token be an ERC20 implementation that returns `false` instead of reverting on failed transfers (e.g., insufficient balance in the gateway due to prior dust/rounding, paused token, blacklist, or other conditional failure that the token author chose to signal via return value). No privileged role is needed — a normal cross-chain order fill/refund flow triggers the vulnerable code path automatically once such a token is in use, and Tron's ecosystem widely includes TRC20 tokens that follow this non-reverting failure convention.

### Recommendation
Replace the raw `.call()` + `success`-only checks in `withdraw()` (lines 705-708 and 719-722) and in the `SweepDust` branch of `onAccept()` (lines 673-676) with `SafeERC20.safeTransfer`, which the contract already imports and uses elsewhere (`using SafeERC20 for IERC20;`). This correctly reverts on both call failure and on tokens that return `false` without reverting, keeping escrow accounting synchronized with actual token movement.

### Proof of Concept
1. Deploy a mock ERC20 (`SilentFailToken`) whose `transfer` returns `false` when the contract's balance is insufficient, instead of reverting.
2. Have a user place an order via `placeOrder` using `SilentFailToken` as an input, escrowing `amount` tokens into `IntentGatewayV2`.
3. Before settlement, drain part of the gateway's `SilentFailToken` balance through an unrelated legitimate path (e.g. a prior `SweepDust`/fee redemption that also uses the same unchecked pattern), so the gateway's actual token balance is less than the escrowed `amount` recorded in `_orders`.
4. Deliver a valid `RedeemEscrow` `onAccept` message for the order commitment; `token.call(transfer(...))` returns `success = true` (the callee's function executes without reverting) but internally returns `false`, so `beneficiary` receives zero tokens.
5. Observe: `_filled[commitment]` is set, `_orders[commitment][token]` is decremented to zero, and `EscrowReleased` is emitted — yet `SilentFailToken.balanceOf(beneficiary)` is unchanged, demonstrating the permanent loss of escrowed funds with no revert or error signal.
