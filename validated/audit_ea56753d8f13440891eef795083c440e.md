## Analysis Result

**Bug-class mapping:** GitLab's CVE-2022-2499 is an IDOR where a lookup path fell back to returning data for an object the caller wasn't authorized to reference. The structural analog here is `IntentGatewayV2.instance()` in the Tron intent-gateway contract: when no peer gateway is registered for a given source chain, the lookup silently falls back to `address(this)` instead of reverting — meaning "unregistered source" is treated as "authorized as myself." This default is then consumed directly by the authentication gate used before releasing escrowed funds.

### Title
Cross-chain message authentication treats an unregistered source-chain instance as `address(this)`, allowing forged `RedeemEscrow`/`RefundEscrow` messages from any unregistered chain to drain escrow - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
`IntentGatewayV2.instance()` on the Tron variant of the Intent Gateway returns `address(this)` when no peer gateway is registered for a `stateMachineId`, instead of reverting. `authenticate()` — the sole gatekeeper for `RedeemEscrow`/`RefundEscrow` delivery in `onAccept` — uses this same lookup to decide whether an incoming `PostRequest.from` is a legitimate peer gateway. Because the fallback resolves to the local contract's own address rather than "no valid instance," any source chain that has never been registered via `NewDeployment` is implicitly treated as authorized to represent this gateway.

### Finding Description
`instance()`:
```solidity
function instance(bytes calldata stateMachineId) public view returns (address) {
    address gateway = _instances[keccak256(stateMachineId)];
    return gateway == address(0) ? address(this) : gateway;
}
``` [1](#0-0) 

`authenticate()` uses this fallback-including lookup directly to gate escrow releases:
```solidity
function authenticate(PostRequest calldata request) internal view {
    if (request.from.length != 20) revert InvalidInput();
    address module = address(bytes20(request.from));
    if (instance(request.source) != module) revert Unauthorized();
}
``` [2](#0-1) 

`onAccept` calls `authenticate` for exactly the request kinds that move escrowed funds:
```solidity
if (kind == RequestKind.RedeemEscrow || kind == RequestKind.RefundEscrow) {
    authenticate(incoming.request);
    WithdrawalRequest memory body = abi.decode(incoming.request.body[1:], (WithdrawalRequest));
    return withdraw(body, kind == RequestKind.RefundEscrow);
}
``` [3](#0-2) 

`withdraw()` then releases whatever `commitment`/`tokens`/`beneficiary` the message body specifies, without any binding to the actual solver who filled the order on the destination chain — it trusts the `PostRequest` as pre-authenticated: [4](#0-3) 

For comparison, the non-Tron `IntentsBase._instance` correctly **reverts** (`UnknownInstance`) instead of defaulting to `address(this)`: [5](#0-4) 
and `ExtrinsicIntents._authenticate` relies on that reverting `_instance`: [6](#0-5) 

The Tron contract's divergence from this pattern is the root cause: it substitutes a safe "object not found → deny" check with an unsafe "object not found → treat as self" default, which is exactly the IDOR bug class from the external report (a missing per-object authorization check that allows referencing/asserting an object identity that was never actually granted).

### Impact Explanation
Any state machine (chain) that Hyperbridge can generically route ISMP messages for, but for which this specific `IntentGatewayV2` deployment has never called `NewDeployment` to register a peer instance, is implicitly authorized as if it *were* this contract's own address. An attacker who can dispatch a genuine ISMP `PostRequest` from such an unregistered source chain — with `from` equal to `address(this)` (the gateway's own address on the current chain, achievable via `CREATE2`/deterministic deployment on a chain the attacker fully controls) — passes `authenticate()` and can submit an arbitrary `WithdrawalRequest` (`RedeemEscrow` or `RefundEscrow`) naming any `commitment` and any `beneficiary`. This drains real escrowed user funds (`_orders[commitment][token]`) held by the gateway to an attacker-chosen address — concrete theft of funds, satisfying the "unauthorized app action" / "forged message delivery" impact bar.

### Likelihood Explanation
Requires: (1) Hyperbridge/ISMP supporting message delivery from a source state machine not yet registered as a peer instance on this specific gateway deployment (plausible for newly connected or long-tail EVM-compatible chains before governance runs `NewDeployment`), and (2) the attacker being able to deploy a contract at the exact address of the legitimate gateway on that unregistered chain (a well-understood technique via `CREATE`/`CREATE2` address prediction when the attacker controls the deploying chain). Both preconditions are realistic in a multi-chain rollout where new chains are onboarded to Hyperbridge before every existing app has registered its peer deployments — a known operational gap, not a theoretical corner case.

### Recommendation
Change `instance()` to revert (e.g. `UnknownInstance`) when `_instances[keccak256(stateMachineId)] == address(0)`, matching the safe behavior already implemented in `IntentsBase._instance`. Do not let any authorization-relevant lookup silently default to `address(this)`; require explicit registration for every state machine before it can be treated as a trusted peer.

### Proof of Concept
1. Governance has registered peer gateways for chains A and B only; chain C is a newly-connected but not-yet-registered EVM state machine.
2. Attacker deploys a contract at the same address as this `IntentGatewayV2` deployment on chain C (deterministic `CREATE2`/nonce-matching deployment, fully controlled since it is the attacker's own chain-side contract).
3. From that contract, attacker dispatches a `PostRequest` to this gateway's chain with `source = C`, `to = address(this gateway)`, `body = RedeemEscrow || abi.encode(WithdrawalRequest{commitment: <victim order commitment>, tokens: <victim's escrowed tokens>, beneficiary: attacker})`.
4. `onAccept` → `authenticate()` computes `instance(C)`; since C has no registered instance, it returns `address(this)`, which equals the attacker-controlled `from` address → check passes.
5. `withdraw()` releases the victim's escrowed tokens to the attacker's beneficiary address, without the corresponding order ever having been genuinely filled or refunded.
