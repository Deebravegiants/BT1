## Title
Webhook `shop`, `topic`, and `webhook-id` fields are trusted without HMAC coverage, enabling cross-tenant webhook forgery - (`lib/shopify_api/webhooks/request.rb`)

## Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC of the raw request body, then unconditionally trusts identity-bearing HTTP headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) that are never included in the signed payload.

## Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`ShopifyAPI::Utils::HmacValidator.validate` computes the HMAC exclusively over that `to_signable_string` value and compares it against the `hmac-sha256` header: [2](#0-1) 

Meanwhile, `shop`, `topic`, `webhook_id`, and `api_version` are read directly from unauthenticated HTTP headers with no cryptographic binding to the signed body: [3](#0-2) 

`Registry.process` validates only the body HMAC and then forwards the header-derived `shop` value straight into the handler's trusted metadata: [4](#0-3) 

This breaks the intended identity binding `hmac(body) == hmac(body, secret) ⟹ shop == request.shop`. In reality, only `hmac(body) == hmac(body, secret)` is proven; `shop` (and `topic`/`webhook_id`) are asserted, not verified. Any party capable of producing a body+HMAC pair with the app's own `client_secret` — for example the operator of one shop that has this app installed, since that shop legitimately receives real webhooks with a valid HMAC computed from the shared `api_secret_key` — can replay that exact body and HMAC while substituting an arbitrary `X-Shopify-Shop-Domain` header. `HmacValidator.validate` will still return `true` because it only checks the body, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the request originated from a different, victim shop.

## Impact Explanation
In a multi-tenant app, the webhook handler typically uses `WebhookMetadata#shop` to select which tenant's session/data store to act on (e.g., to record `app/uninstalled`, update customer data for `customers/redact`, or apply order data). Since `shop` is unauthenticated relative to the signature, an attacker with legitimate access to their own store's webhook stream (an unprivileged actor with respect to any other tenant) can forge a body/HMAC pair valid for the app's shared secret and impersonate any other shop domain, leading to cross-tenant data corruption/injection. This matches the "Critical - cross-tenant access" impact category.

## Likelihood Explanation
Exploitation requires the attacker to have working access to real webhook deliveries for at least one shop where the target app is installed (which any merchant installing a public app can obtain), then to be able to relay a crafted HTTP request with modified headers to the app's own webhook endpoint. No access token, `client_secret`, or privileged account is required, and the HMAC secret itself never needs to be known by the attacker because a real, validly-signed body/HMAC pair from their own store's webhook traffic is directly reusable.

## Recommendation
Include `shop`, `topic`, and `webhook_id` in the signable string used for HMAC computation (or otherwise cryptographically bind them to the verified payload) so that `Utils::HmacValidator.validate` fails whenever any of these header-derived identity fields are altered relative to what Shopify actually signed for that shop.

## Proof of Concept
1. App merchant A installs the app on `shop-a.myshopify.com` and legitimately receives a webhook: body `B`, header `X-Shopify-Hmac-Sha256: HMAC(B, secret)`, header `X-Shopify-Shop-Domain: shop-a.myshopify.com`.
2. Merchant A (or anyone with access to that webhook delivery, e.g., via a proxy/logging tool) captures `B` and its valid HMAC.
3. Attacker replays the exact same `B` and HMAC to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` in `lib/shopify_api/utils/hmac_validator.rb` returns `true` because it only checks `B` against the HMAC.
5. `Registry.process` in `lib/shopify_api/webhooks/registry.rb` invokes the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, causing the host application to act on `victim-shop`'s tenant context using attacker-supplied body content.
