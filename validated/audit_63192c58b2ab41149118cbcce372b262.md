Audit Report

## Title
JWT replay-check-then-record race in `WorkflowMetadataHandler.Authorize` allows request duplication - (File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go)

## Summary
`WorkflowMetadataHandler.Authorize` checks JWT single-use status via `h.jwtCache.isReplay(claims.ID)` and only records usage via `h.jwtCache.recordUsage(claims.ID)` after unrelated work (authorized-key map lookup, signer validation) completes. [1](#0-0)  Because the check and the record are two separate lock acquisitions on `jwtReplayCache` rather than one atomic critical section, two concurrent requests bearing the same signed JWT can both pass the replay check before either marks the `jti` as used, letting a single-use JWT authorize two workflow executions.

## Finding Description
`isReplay` acquires an `RLock`, reads, and releases; `recordUsage` separately acquires a `Lock`, writes, and releases, with no shared critical section spanning both: [2](#0-1)  Inside `Authorize`, between the `isReplay` check (line 87) and the `recordUsage` call (line 105), the code performs a map lookup for `h.authorizedKeys[workflowID]` and a signer-authorization check, both of which involve additional map access and error branches — real elapsed time during which a second goroutine can slip through. [3](#0-2) 

This handler is reached directly from `HandleUserTriggerRequest`, the externally-facing HTTP Trigger entry point, via `authorizeRequest`: [4](#0-3)  `HandleUserTriggerRequest` itself performs no per-JTI locking or serialization before calling `authorizeRequest` — it is a straight-line sequence of `validatedTriggerRequest` → `resolveWorkflowID` → `authorizeRequest` → `checkRateLimit`, with no mutex guarding the whole flow: [5](#0-4)  Nothing in the gateway's request-handling path (per-connection or per-request goroutines) serializes two calls to `Authorize` carrying the same JWT, so both can execute concurrently and both `isReplay` calls can return `false`.

By contrast, the vault capability's `RequestReplayGuard.CheckAndRecord` correctly performs the check and the write under a single mutex acquisition, which is the safe pattern: [6](#0-5)  This confirms the split-lock design in `jwtReplayCache` is a genuine structural deviation from the safe pattern used elsewhere in the same codebase, not an intentional design choice.

## Impact Explanation
A single signed HTTP-trigger JWT — meant to authorize exactly one workflow execution per the code's own error message ("JWT token has already been used") — can be used to trigger duplicate workflow executions by racing two requests. Each successful `Authorize` call proceeds to `checkRateLimit` and onward to fan the request out to DON nodes, consuming per-workflow rate-limit budget/compute and potentially causing duplicate side effects in downstream capabilities. This maps to the "unauthorized job run" / gateway request impersonation-adjacent impact category, since it breaks the single-use guarantee of an authorization token.

## Likelihood Explanation
Exploitation requires only an unprivileged external client capable of sending two HTTP requests carrying the identical previously-issued signed JWT nearly simultaneously — trivial to script with two parallel HTTP clients, no special network position, no privileged role, and no node cooperation required.

## Recommendation
Collapse `isReplay` and `recordUsage` into a single atomic `checkAndRecordJTI(jti string) error` method that performs the existence check and the insert while holding a single `cache.mu.Lock()`, mirroring `RequestReplayGuard.CheckAndRecord`. Call this immediately after JWT signature verification succeeds in `Authorize`, before the authorized-key lookup and signer validation, so no other code path can execute between the check and the record.

## Proof of Concept
1. Issue a valid signed HTTP Trigger JWT with `jti = "X"` for a registered workflow.
2. Launch two goroutines/HTTP clients that call `HandleUserTriggerRequest` (or directly `WorkflowMetadataHandler.Authorize`) concurrently with `Auth = jwt(jti=X)`.
3. Add a small sleep/synchronization point between `isReplay` and `recordUsage` in a unit test (or rely on natural goroutine scheduling) to force both goroutines to pass `isReplay("X") == false` before either calls `recordUsage("X")`.
4. Assert both calls to `Authorize` return `nil` error, demonstrating the same JWT authorized two separate executions — a Go unit test directly exercising `jwtReplayCache`/`WorkflowMetadataHandler.Authorize` with two concurrent goroutines and a `sync.WaitGroup` plus a manually inserted delay (or race-detector-triggered interleaving) would reproduce this deterministically.

func (g *RequestReplayGuard) CheckAndRecord(digest string, expiresAtUnix int64) error {
	g.mu.Lock()
	defer g.mu.Unlock()

	g.clearExpiredLocked()

	if _, exists := g.seen[digest]; exists {
		return ErrRequestAlreadySeen
	}

	g.seen[digest] = expiresAtUnix
	return nil
}
