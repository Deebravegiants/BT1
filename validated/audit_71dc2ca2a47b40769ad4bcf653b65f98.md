### Title
Webhook `shop-domain` header is trusted for tenant routing while only the raw body is HMAC-covered, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body [1](#0-0) , and `HmacValidator.validate` verifies the HMAC solely against that signable string [2](#0-1) . The `shop` value that `Registry.process` hands to the app's webhook handler, however, is read straight from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header [3](#0-2)  and is never checked against anything the HMAC covers [4](#0-3) .

### Finding Description
The equality that should hold is: `shop delivered to the handler == shop the merchant that produced this signed body belongs to`. In this gem, the `shop` header is completely outside the signed material — the signature only binds `raw_body`. Since `api_secret_key` is a single per-app secret shared across every installed shop (not a per-shop secret), any shop that has legitimately installed the app can capture one of its own genuinely-Shopify-signed webhook deliveries (valid `hmac-sha256` header for a given `raw_body`) and simply replay it to the app's webhook endpoint with the `shop-domain` header rewritten to a different (victim) shop's domain. `HmacValidator.validate` still passes, because it never inspects `shop`, and `Registry.process` forwards the attacker-chosen `shop` value straight into `WebhookMetadata` for the handler [4](#0-3) . The handler and any downstream logic keyed by `data.shop` (session lookup, per-tenant state updates, `app/uninstalled` handling, etc., per the documented handler contract) [5](#0-4)  then act as if the event came from the victim tenant.

### Impact Explanation
This breaks the tenant boundary that host applications are documented to rely on (`data.shop` identifies "The shop domain of the webhook") [6](#0-5) . A malicious but otherwise unprivileged merchant who has installed the app can forge webhook events attributed to any other shop the app serves — e.g. falsely signalling `app/uninstalled` for a victim shop, injecting spoofed `orders/create`/`customers/create` payloads that get persisted or processed under the victim's tenant record. This is a cross-tenant data-integrity/authentication issue, matching the Critical "cross-tenant access" impact bucket, because it lets one tenant impersonate another purely by capturing and replaying their own valid webhook and editing an unauthenticated header — no `client_secret`, access token, or privileged access is required.

### Likelihood Explanation
Likelihood is high for any app operator that keys webhook side effects off `data.shop` (the field the docs explicitly expose for that purpose) without independently re-verifying shop ownership. The only prerequisite is that the attacker be a legitimate installed merchant of the target app (an ordinary, unprivileged tenant) capable of receiving at least one webhook for their own store and replaying it with a modified header to the app's public webhook endpoint — no secret material, brute forcing, or privileged access is needed.

### Recommendation
Bind `shop` (and ideally `topic`) into the signed material verified by `HmacValidator`, or otherwise cryptographically associate the header-derived `shop` with the request before it is trusted. Concretely, `Webhooks::Request#to_signable_string` should incorporate the `shop-domain` header (consistent with how `AuthQuery#to_signable_string` includes `shop` in its signable string) [7](#0-6) , or `Registry.process` should cross-check the header-derived shop against a shop value obtained from a trusted, per-request registered webhook subscription rather than accepting it unconditionally.

### Proof of Concept
1. Shop A installs the app and receives a legitimately-signed webhook: body `{}"`, header `x-shopify-hmac-sha256: <valid HMAC of "{}">`, `x-shopify-shop-domain: shop-a.myshopify.com`.
2. Shop A's operator captures this request and resends it to the app's webhook endpoint, changing only the header to `x-shopify-shop-domain: shop-b.myshopify.com` (leaving body and HMAC untouched).
3. `Webhooks::Request.new` parses this into `shop = "shop-b.myshopify.com"`, `hmac = <same valid HMAC>` [8](#0-7) .
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC only over `raw_body` ("{}") and finds it valid, since the body is unmodified [9](#0-8) .
5. The registered handler is invoked with `WebhookMetadata.new(topic:, shop: "shop-b.myshopify.com", body:, ...)`, causing the app to process/store this forged event as if Shop B sent it [10](#0-9) .

```ruby
      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
```

```ruby
        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
```
