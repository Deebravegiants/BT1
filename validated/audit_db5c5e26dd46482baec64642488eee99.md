### Title
Missing scrypt cost-parameter validation in `decryptBlobKey` allows attacker-controlled n/r/p to make offline passphrase brute-force trivial - ([File: libraries/secure-container/src/metadata.js])

### Summary
`metadata.decode()` parses `scrypt.n`, `scrypt.r`, and `scrypt.p` directly from raw, attacker-controlled bytes as `UInt32BE` with no bounds checking, and `decryptBlobKey`/`boxDecrypt` forward those values straight into `stretchPassphrase`/`scrypt()` with no minimum-cost enforcement. An attacker who controls the metadata bytes (e.g. an imported/synced backup file) can set `n=0`/`r=0`/`p=1` (or similarly weak values) so that when a legitimate app later tries to decrypt with this metadata, the KDF cost is effectively free, making offline brute force of the passphrase protecting `blobKey` computationally trivial.

### Finding Description
The metadata struct declares `n`, `r`, `p` as plain `UInt32BE` fields with no validation: [1](#0-0) 

`decode()` only warns about buffer length, never validates the scrypt parameters: [2](#0-1) 

`decryptBlobKey` passes `metadata.scrypt` (attacker-supplied) directly to `boxDecrypt`: [3](#0-2) 

In `crypto.js`, `boxDecrypt` merges the caller-supplied `scryptParams` over defaults — meaning any attacker-supplied `n`/`r`/`p` in the decoded metadata overrides the safe defaults (`n:16384, r:8, p:1`) — and then calls `stretchPassphrase` → `scrypt()` unconditionally with whatever values are present, with no minimum-cost check anywhere in this path: [4](#0-3) [5](#0-4) 

The top-level `decrypt()` in `index.js` calls this chain directly on decoded, attacker-controlled metadata bytes without any allow-listing or sanity checks on `n`/`r`/`p`: [6](#0-5) 

No code in `metadata.js` or `crypto.js` enforces a minimum `n`/`r`/`p`, and there is no policy guard between `decode()` and `boxDecrypt`/`stretchPassphrase`. This confirms the described call sequence (`metadata.decode` → `decryptBlobKey` → `boxDecrypt` → `stretchPassphrase(passphrase, {n:0,r:0,p:0})`) is reachable purely from attacker-controlled bytes.

### Impact Explanation
If a wallet (or dependent library such as `seco-rw`/`seco-keyval`) ever decrypts a secure-container file/blob whose metadata originated from an untrusted source (imported backup, synced storage payload, or any file the attacker can influence before it's decrypted with the user's passphrase), the attacker-set near-zero-cost scrypt parameters drastically reduce the work factor protecting the passphrase-derived key. This does not directly leak `blobKey`/seed without the correct passphrase, but it converts what should be an expensive, brute-force-resistant KDF into a cheap one for any subsequent passphrase-guessing attempts against that specific container/blob, undermining the "secrets stay secret via cost-bound KDF" invariant. Practically, this degrades a defense-in-depth mechanism (KDF hardening) for offline passphrase attacks, which is a real but secondary risk relative to a full key-disclosure bug — the actual secret disclosure still requires guessing the passphrase, just far more cheaply.

### Likelihood Explanation
Feasible whenever attacker-influenced metadata bytes are decoded and processed by this library without additional application-level validation of `n`/`r`/`p` ranges. The library itself provides no allow-listing, so any consumer that trusts the file/metadata author (e.g. a synced or imported container) inherits this weakness. Exploitability depends on whether an integrating application (not shown in this library) adds its own guard rails; within `secure-container` itself, no such guard exists.

### Recommendation
Add minimum/maximum bounds validation for `scrypt.n`, `scrypt.r`, `scrypt.p` in `metadata.decode()` (or in `boxDecrypt`/`stretchPassphrase`) and reject/throw on values below a safe cost floor (e.g. `n >= 16384, r >= 8, p >= 1`) before calling `scrypt()`. This closes the gap between decode and KDF invocation regardless of which application consumes the library.

### Proof of Concept
```js
import { metadata } from 'secure-container'

test('decryptBlobKey should reject weak scrypt cost parameters', async (t) => {
  const md = metadata.create({ salt: Buffer.alloc(32), n: 0, r: 0, p: 1 })
  md.blobKey = { iv: Buffer.alloc(12), authTag: Buffer.alloc(16), key: Buffer.alloc(32) }

  await t.rejects(
    () => metadata.decryptBlobKey(md, 'any-passphrase'),
    /scrypt cost parameters below minimum|invalid n\/r\/p/,
    'decryptBlobKey should refuse to run scrypt with n=0/r=0'
  )
})
```
Currently this test would fail because no such validation exists in `metadata.js`/`crypto.js`, confirming the near-zero-cost KDF path is reachable as described.

  const metadata = conMetadata.decode(fileObj.metadata)
  const blobKey = await conMetadata.decryptBlobKey(metadata, passphrase)
  const header = conHeader.decode(fileObj.header)
  const data = await conBlob.decrypt(fileObj.blob, metadata, blobKey)

}
