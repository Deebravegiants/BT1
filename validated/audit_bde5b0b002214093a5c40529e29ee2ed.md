### Title
Multisig transaction execution can bypass on-chain approved payload verification, allowing an already-authorized executor to substitute an unapproved payload — (File: `aptos-move/framework/aptos-framework/sources/multisig_account.move`)

### Summary
`multisig_account.move` supports storing the full transaction payload on-chain (`create_transaction`, storing it in `MultisigTransaction.payload`) so owners can review exactly what they are voting on. However, the code that runs at execution time, `validate_multisig_transaction`, only checks the *actually submitted* payload against the *stored, voted-on* payload when the feature flag `AbortIfMultisigPayloadMismatch` is enabled. If that flag is off (its default/gateable state in this codebase), the executing owner's runtime `executable` payload is never compared to `transaction.payload`, so the vote/approval binding to a specific action is not enforced.

### Finding Description
`create_transaction` stores the full proposed entry-function payload on-chain: [1](#0-0) 

Owners vote using `approve_transaction`/`reject_transaction`, which are keyed only by `sequence_number` — not by a hash of the specific payload: [2](#0-1) 

At execution time, the VM prologue (`run_multisig_prologue`) derives `provided_payload` from whatever `executable` is actually bundled in the transaction being processed — this is fully controlled by whichever owner submits the execution transaction, independent of what was originally proposed: [3](#0-2) 

`validate_multisig_transaction` then performs the quorum/timelock checks, and only **conditionally** verifies that the submitted payload matches the on-chain-stored payload:
```
if (features::abort_if_multisig_payload_mismatch_enabled()
    && transaction.payload.is_some()
    && !payload.is_empty()
) {
    let stored_payload = transaction.payload.borrow();
    assert!(payload == *stored_payload, error::invalid_argument(EPAYLOAD_DOES_NOT_MATCH));
}
``` [4](#0-3) 

This mirrors the external report's bug class exactly: the "commitment" (here, the stored `MultisigTransaction.payload` that owners approved) is not bound to what is actually executed unless an optional flag is set. The feature is called `AbortIfMultisigPayloadMismatch`, is numbered 70, and — unlike several later flags in the same enum that are explicitly annotated "Enabled on mainnet, cannot be disabled" — carries no such annotation: [5](#0-4) 

The comment on the flag itself confirms this is a governance-gated fix for exactly this gap: "Once enabled, the multisig transaction execution will explicitly abort if the provided payload does not match the payload stored on-chain": [6](#0-5) 

### Impact Explanation
Multisig accounts commonly custody APT, fungible assets, and object ownership authority (e.g., DAO treasuries, code-object upgrade authority, resource-account admin rights). If `AbortIfMultisigPayloadMismatch` is not enabled for a given chain/network, any single owner who has accumulated enough approvals for a given `sequence_number` (which are recorded only against the sequence number, not against a specific payload hash) can submit a transaction bundle whose actual `executable` entry function differs entirely from what was proposed and approved (`transaction.payload`). Since `validate_multisig_transaction` performs no comparison in that case, the substituted payload executes with the multisig account's authority — e.g., transferring out all custodied APT/FA balances, reassigning object ownership, or rotating auth keys — despite other owners having approved a completely different, benign action. This breaks the core custody invariant that "execution authority requires the specific action to have been approved," turning quorum-based custody into effectively single-owner-authorized arbitrary execution.

### Likelihood Explanation
The likelihood is entirely dependent on the on-chain state of the `AbortIfMultisigPayloadMismatch` feature flag for the target network/deployment. I was not able to conclusively confirm from the indexed code whether this flag is currently enabled by default on Aptos mainnet — the flag lacks the "Enabled on mainnet, cannot be disabled" annotation seen on adjacent flags, but genesis/mainnet feature-set initialization data was not found in the indexed files, so I cannot rule out that it has since been turned on via governance. If it is disabled (which the code's default `is_enabled()` semantics assume in the absence of explicit activation), this is directly exploitable by any single owner with sufficient historical approvals and requires no additional privilege beyond being a legitimate owner — it is not reliant on a malicious admin/governance assumption, since the vulnerable code path is the base/pre-fix behavior of the protocol.

### Recommendation
Make the payload-match assertion unconditional (remove the `features::abort_if_multisig_payload_mismatch_enabled()` gate) so that whenever `transaction.payload` is stored on-chain, the executed payload must always match it exactly, regardless of feature-flag state. Alternatively/additionally, bind approvals to a hash of the specific proposed payload (rather than only `sequence_number`) so that votes cannot be reinterpreted as approval for a different payload once the assertion is bypassed by flag state.

### Proof of Concept
1. On a network where `AbortIfMultisigPayloadMismatch` is disabled, an owner calls `create_transaction(owner, multisig_account, payload_A)` where `payload_A` is a benign entry function (e.g., a small, harmless transfer), storing it fully on-chain.
2. Other owners review `payload_A` on-chain and call `approve_transaction(owner_i, multisig_account, sequence_number)` until quorum is reached, per [2](#0-1) .
3. Any owner (including the original proposer) then submits the actual execution transaction with a *different* `TransactionExecutableRef::EntryFunction` payload_B (e.g., "transfer all APT out of the multisig account to attacker address"). This is what becomes `provided_payload` in `run_multisig_prologue`, per [3](#0-2) .
4. `validate_multisig_transaction` checks quorum via `sequence_number` (which is satisfied because votes were counted for that sequence number regardless of payload content), and since `abort_if_multisig_payload_mismatch_enabled()` is false, the `payload_A == payload_B` comparison in [7](#0-6)  is skipped entirely.
5. `payload_B` executes with the multisig account's signer authority, draining custodied assets, despite only `payload_A` having been approved by quorum.
