### Title
Webhook shop-domain identity not bound by HMAC, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) from the unauthenticated `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, while the HMAC signature validated by `Utils::HmacValidator` only covers the raw request body. This breaks the equality `shop authenticated == shop bound by HMAC`, letting an unprivileged internet user replay a legitimate webhook body/HMAC pair while attaching an arbitrary victim shop domain header, exactly analogous to the report's "field acted on but not covered by the signature/authorization check" bug class.

### Finding Description
`Request#hmac` and `Request#to_signable_string` only operate on `@raw_body`: [1](#0-0) 

The `shop` accessor is pulled straight from the header, independent of the signed content: [2](#0-1) 

`HmacValidator.validate` verifies `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)` — i.e., against the raw body only: [3](#0-2) 

`Registry.process` accepts the request once the body-only HMAC check passes, then trusts `request.shop` (the unauthenticated header) as the tenant identity forwarded to the app's handler: [4](#0-3) 

Because the HMAC signs only the JSON body bytes and never binds them to the `shop-domain` header, any request with a body+HMAC pair that is valid for the shared `api_secret_key` (e.g., captured from a legitimate webhook delivered to the attacker's own shop) remains valid if the `x-shopify-shop-domain` header is swapped to a different shop. The library documents that `data.shop` is the trusted "shop domain of the webhook" that app authors are expected to use for tenant-scoped processing: [5](#0-4) [6](#0-5) 

### Impact Explanation
This breaks the binding "shop asserted in `WebhookMetadata.shop` == shop whose body/HMAC was actually verified," resulting in cross-tenant webhook forgery: an attacker who owns/operates any shop that has this app installed (an ordinary merchant, i.e., unprivileged relative to other tenants) can capture one of their own legitimate webhook deliveries and replay the identical body+HMAC to the app's public webhook endpoint with a forged `shop-domain` header naming a victim shop. `Registry.process` will accept it as authentic and dispatch it to the app's handler as if it originated from the victim tenant, since only the body is cryptographically checked while the identity header is not. Any host application logic that keys database updates, order/inventory sync, or other tenant-scoped side effects off `data.shop` can be corrupted or manipulated for another merchant's account — this is a cross-tenant access impact.

### Likelihood Explanation
High for any consumer of the documented API: an attacker needs only to install the app on a shop they control (or otherwise trigger any legitimate webhook to themselves), capture the raw body and its accompanying `x-shopify-hmac-sha256` value, then POST that exact pair to the app's public webhook endpoint with an altered `x-shopify-shop-domain` header. No access token, `api_secret_key`, or privileged access is required — only ordinary use of the app as any tenant.

### Recommendation
Bind the shop identity to the verified payload instead of trusting an unauthenticated header: derive/cross-check `shop` against a value embedded in the signed body (e.g., confirm the webhook's shop against the shop associated with the session/subscription that the body content is about), or require the consuming application to validate `data.shop` against an independently known set of installed shops before using it for tenant-scoped writes, and document this requirement prominently since the header itself carries no cryptographic guarantee.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` (a normal, unprivileged merchant action) and receives a real webhook delivery, e.g., body `{"id":1,...}` with header `x-shopify-hmac-sha256: <H>` valid for `api_secret_key`.
2. Attacker crafts a new HTTP POST to the app's public webhook route with the identical raw body and identical `x-shopify-hmac-sha256: <H>` header, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses this into `shop = "victim-shop.myshopify.com"`, `hmac = <H>`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only compares `<H>` against the HMAC of the (unchanged) raw body — see [7](#0-6) .
5. The registered handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker's own data>, ...)`, causing the app to process attacker-controlled data under the victim tenant's identity.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
