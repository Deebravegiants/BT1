### Title
Webhook `shop` identity field is not covered by HMAC verification, enabling cross-tenant webhook replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies only that the raw request body matches an HMAC computed with the app's `api_secret_key`, but the `shop` field that is handed to the app's webhook handler as the tenant identifier is read from an HTTP header that is never included in the signed content. An attacker who possesses one validly-signed webhook body (which any merchant using the app can obtain simply by receiving a webhook for their own store) can replay that exact body to the app's webhook endpoint while substituting a different `shop-domain` header, and the HMAC check still passes.

### Finding Description
`HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string`, and for webhooks, `Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, however, is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header, which is completely outside the HMAC-signed material: [2](#0-1) 

`Registry.process` only checks the HMAC and dispatches to the topic handler; it performs no independent check that the `shop` header corresponds to a shop that actually owns/produced this signed body: [3](#0-2) 

The gem then hands `request.shop` straight into `WebhookMetadata`, which is documented as the trusted tenant identifier that host apps use to route/persist webhook data: [4](#0-3) 

The equality that should hold is: **the shop that produced the signed bytes == the shop the gem reports to the handler**. Because `shop` is parsed from an unauthenticated header while the HMAC only binds `raw_body`, that equality is not enforced by the gem — the field acted on (`shop`) is not covered by the signature that supposedly "verifies the request did indeed come from Shopify," as the gem's own docs claim: [5](#0-4) 

### Impact Explanation
Because the same `api_secret_key` is shared by an app across all shops that install it, any merchant of the app can legitimately receive one HMAC-valid webhook body for their own store. That exact `(raw_body, hmac)` pair remains valid under `HmacValidator.validate` regardless of which `shop-domain` header accompanies it. Replaying it with a victim's shop domain causes the app's handler to process/attribute that event as coming from the victim tenant — a cross-tenant confusion that can corrupt per-shop data, trigger unintended actions keyed off `data.shop` (e.g., queuing jobs, updating records, invalidating state) for a shop the attacker does not control. This matches the report's underlying bug class: state is mutated for a tenant based on a field the authentication mechanism never actually bound.

### Likelihood Explanation
The only prerequisite is a normal merchant install of the app (no `api_secret_key`, access token, or other privileged credential is required) plus the ability to send a normal HTTP request with a forged header, which is trivial for anyone who already has one legitimately-delivered webhook payload+HMAC pair. No host-application misuse is required beyond following the gem's own documented pattern.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook-id`) into the value that is HMAC-verified, or have `Registry.process`/`WebhookMetadata` require the caller to supply the expected shop (from the app's own session/tenant lookup) and assert it matches `request.shop` before dispatching to the handler, so that the tenant identifier is authenticated rather than merely parsed.

### Proof of Concept
1. As a merchant who has installed the app, capture one legitimate webhook HTTP request delivered to your own endpoint, e.g. headers `x-shopify-hmac-sha256: <valid>`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: orders/create`, body `{"...":"..."}`.
2. Replay the identical body and `x-shopify-hmac-sha256` value to the same endpoint, but change `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Utils::HmacValidator.validate` (lib/shopify_api/utils/hmac_validator.rb) succeeds because it only checks `raw_body` against the secret; `Registry.process` (lib/shopify_api/webhooks/registry.rb:188-200) proceeds and calls the handler with `WebhookMetadata` whose `shop` is `"victim-shop.myshopify.com"`, even though `victim-shop` never sent this webhook.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
