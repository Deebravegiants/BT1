### Title
EvmHost fails to properly reset the "latest height" pointer after a state-commitment veto, reopening the monotonicity gate for stale consensus updates - (File: `evm/src/core/EvmHost.sol`)

### Summary
This is the closest reachable analog to CVE-2018-16882's root cause: an object is torn down (the KVM `pi_desc_page` is unmapped) but the descriptor/pointer that referenced it is not properly reset, so later code trusts a stale value. In `EvmHost.sol`, when a fisherman vetoes a state commitment that happens to be the chain's latest height, the code deletes the commitment but resets the "latest height" tracking variable to a hardcoded, meaningless constant (`1`) instead of restoring it to the actual previous valid height, as the Substrate/pallet-ismp equivalent correctly does.

### Finding Description
`deleteStateMachineCommitmentInternal` in `evm/src/core/EvmHost.sol` handles vetoing a state commitment: [1](#0-0) 

```solidity
function deleteStateMachineCommitmentInternal(StateMachineHeight memory height, address fisherman) internal {
    StateCommitment memory stateCommitment = _stateCommitments[height.stateMachineId][height.height];
    delete _stateCommitments[height.stateMachineId][height.height];
    delete _stateCommitmentsUpdateTime[height.stateMachineId][height.height];
    // technically any state commitment can be vetoed, safety check that it's the latest before resetting it.
    if (_latestStateMachineHeight[height.stateMachineId] == height.height) {
        _latestStateMachineHeight[height.stateMachineId] = 1;
    }
    ...
}
```

When the vetoed height is the current `_latestStateMachineHeight`, this "unmaps" the commitment (correct) but resets the pointer that gates future updates to the literal integer `1` rather than the actual prior legitimate height. This mirrors the CVE's pattern exactly: the resource (commitment) is freed, but the reference used later for a security check (`latestHeight`) is left pointing at a bogus/stale value instead of being properly invalidated or restored.

Compare this to the Substrate implementation of the same operation, which correctly restores the prior height from `PreviousStateMachineHeight`: [2](#0-1) 

The stale `latestHeight = 1` value is then consumed, without further validation, in `HandlerV2.handleConsensus`, which is reachable by any relayer submitting a consensus proof: [3](#0-2) 

```solidity
for (uint256 i = 0; i < intermediatesLen; i++) {
    IntermediateState memory intermediate = intermediates[i];
    uint256 latestHeight = host.latestStateMachineHeight(intermediate.stateMachineId);
    if (latestHeight != 0 && intermediate.height > latestHeight) {
        StateMachineHeight memory stateMachineHeight =
            StateMachineHeight({stateMachineId: intermediate.stateMachineId, height: intermediate.height});
        host.storeStateMachineCommitment(stateMachineHeight, intermediate.commitment);
    }
}
```

Because `latestHeight` is `1` (an artificial floor with no relationship to the chain's real progress) instead of the true prior height, this monotonicity check `intermediate.height > latestHeight` is trivially satisfied by almost any height a relayer's consensus proof supplies going forward — including heights that are stale relative to the actual latest legitimately-accepted state (i.e., heights between the true prior height and the vetoed height, or heights the network had already progressed past before the veto). This defeats the intended anti-replay/monotonicity guarantee that `latestStateMachineHeight` is meant to enforce for the reachable message-delivery path (`handlePostRequests`, `handleGetResponses`, timeout handlers), all of which trust `host.stateMachineCommitment(height)` as their root of truth.

The veto path itself is a normal, permissionless-adjacent protocol mechanism (a collator/fisherman calling `pallet-fishermen::veto_state_commitment`, relayed cross-chain to the EVM host's handler), not a malicious-admin action — it is the network's intended fraud-response mechanism, and this bug corrupts protocol invariants as an unavoidable side effect of using it correctly, exactly as CVE-2018-16882 corrupted the hypervisor's own error-handling path.

### Impact Explanation
The `_latestStateMachineHeight` value gates whether a new consensus-verified `IntermediateState` gets persisted as the source of truth for state-membership/non-membership proofs used by request/response/timeout dispatch. Collapsing it to `1` after any veto of the current latest height removes the monotonicity protection for all subsequent consensus updates on that state machine until a new, sufficiently high honest height re-establishes it. In principle this allows previously-superseded (stale) or otherwise-rejectable state commitments — carried in a later, still-consensus-valid proof (a legitimate but old signed BEEFY/SP1/GRANDPA/BSC commitment, or an older parachain height a relayer chooses to resubmit) — to be accepted and stored as the trusted root for that height, which downstream `HandlerV2` functions use to verify inclusion/non-inclusion of requests, responses and timeouts. This can result in stale or previously-discarded state being used to authorize message delivery or timeout finalization, undermining the integrity of cross-chain state verification that token/mint/burn and message-dispatch flows depend on.

### Likelihood Explanation
Any veto of the *current latest* height on an EVM-hosted state machine triggers this path — vetoes are a routine, expected part of fisherman operation, not an edge case, and happen automatically whenever fisherman infrastructure detects a disagreement, per `tesseract/messaging/evm/src/byzantine.rs`. Once triggered, exploitation only requires an ordinary relayer to submit any subsequent, consensus-valid but low/stale height in a normal consensus message — a permissionless action requiring no privileged role.

### Recommendation
On veto of the latest height, restore `_latestStateMachineHeight[height.stateMachineId]` to the actual previous valid height (mirroring `PreviousStateMachineHeight`/`store_latest_commitment_height` semantics on the Substrate side) rather than hardcoding it to `1`. This requires tracking a "previous latest height" per state machine in `EvmHost.sol` (analogous to `PreviousStateMachineHeight` in `modules/pallets/ismp/src/host.rs`), and using that value in `deleteStateMachineCommitmentInternal`.

### Proof of Concept
1. Consensus proofs advance `stateMachineId = X` to height `H` (`_latestStateMachineHeight[X] = H`), legitimately.
2. A fisherman later vetoes height `H` (e.g., due to a genuinely fraudulent commitment) via `deleteStateMachineCommitment`, which is relayed to `EvmHost` as the configured handler; per lines 718–721 of `EvmHost.sol`, `_latestStateMachineHeight[X]` becomes `1`.
3. Any relayer subsequently submits a consensus proof (via `HandlerV2.handleConsensus`) whose `IntermediateState` reports some height `h` where `1 < h < H` (a height that is stale relative to what the chain had already progressed past before the veto, or an old commitment the network should no longer trust as "latest").
4. `latestHeight != 0 && intermediate.height > latestHeight` evaluates to `true` (since `latestHeight == 1`), so `host.storeStateMachineCommitment` persists this stale/old commitment as accepted state, and `_latestStateMachineHeight[X]` is updated to `h`, silently reintroducing state that monotonicity was supposed to keep superseded — with no relationship enforced to the actual pre-veto progress of the chain.

	fn delete_state_commitment(&self, height: StateMachineHeight) -> Result<(), Error> {
		// The height's entry in the state commitment queue is deliberately left
		// behind; locating it would mean scanning the queue, which is the per-insert
		// cost the queue exists to avoid. Usually its eviction is a no-op, but when
		// the vetoed height is the latest the reset below re-opens it for honest
		// resubmission, and the resubmitted height gets a *second* queue entry. The
		// stale entry then evicts the live commitment when it reaches the head —
		// one insertion before the live entry would have, since the resubmission
		// lands directly behind its stale twin. So a veto costs that height one
		// insertion of retention and permanently burns one queue slot. Both are
		// negligible against the configured caps; making it exact would need a
		// height -> index map on the insert path.
		BoundedStateCommitments::<T>::remove(height.id, height.height);
		BoundedStateMachineUpdateTime::<T>::remove(height.id, height.height);

		// technically any state commitment can be vetoed,
		// safety check that it's the latest before resetting it.
		if let Some(latest) = LatestStateMachineHeight::<T>::get(height.id) {
			if latest == height.height {
				// Reset back to the initial height to allow for honest updates
				let prev_height =
					PreviousStateMachineHeight::<T>::get(height.id).ok_or_else(|| {
						Error::Custom("Previous state machine height should exist".to_string())
					})?;
				LatestStateMachineHeight::<T>::insert(height.id, prev_height);
			}
		}
		Ok(())
	}
