Audit Report

## Title
Stale `ItemAttributesApprovalsOf` delegate approvals survive item ownership transfer in pallet-nfts - (File: `substrate/frame/nfts/src/features/transfer.rs`)

## Summary
`do_transfer` in `substrate/frame/nfts/src/features/transfer.rs` updates item ownership and clears the transfer-approvals field (`details.approvals.clear()`), but never removes the separate `ItemAttributesApprovalsOf` storage map entry for the item. As a result, an account previously delegated by the old owner via `approve_item_attributes` remains authorized to write attributes in the `Account(delegate)` namespace after the item has been transferred to a new owner who never approved them.

## Finding Description
`do_transfer` at [1](#0-0)  updates `Account` ownership, clears `details.approvals` (the item transfer-approval set), and removes `ItemPriceOf`/`PendingSwapOf`, but does not call `ItemAttributesApprovalsOf::<T, I>::remove(&collection, &item)`.

`ItemAttributesApprovalsOf` is populated when an owner approves a delegate via `do_approve_item_attributes`, which only checks that `check_origin == details.owner` at the time of approval [2](#0-1) . Authorization to write an attribute in the `Account(account_id)` namespace is checked purely via `is_valid_namespace`, which for that variant checks `account_id == origin && approvals.contains(&origin)` — no cross-check against the item's *current* owner [3](#0-2) .

By contrast, `do_burn` explicitly removes `ItemAttributesApprovalsOf::<T, I>::remove(&collection, &item)` when an item is destroyed [4](#0-3) , showing the pallet authors are aware this map must be cleaned up on item lifecycle changes — this cleanup is simply absent from `do_transfer`. Revocation is only possible via `do_cancel_item_attributes_approval`, which requires `check_origin == details.owner` (i.e., only the current, possibly unaware, owner can revoke) [5](#0-4) .

## Impact Explanation
After a transfer/sale, any account the previous owner approved via `approve_item_attributes` retains the ability to call `set_attribute` and mutate metadata under the `Account(delegate)` namespace for that item without the new owner's knowledge or consent. This is a state-integrity/griefing issue (metadata manipulation) rather than a funds-loss issue, since the delegate pays their own deposit in `do_set_attribute`. This matches the reasoning in the report.

## Likelihood Explanation
Fully reachable by unprivileged users via standard extrinsics: `approve_item_attributes` → `transfer` (or `buy_item`, which reuses `do_transfer`) → the stale delegate calls `set_attribute`. No privileged origin or special conditions are required.

## Recommendation
In `do_transfer` (and any other function mutating `details.owner`, e.g. `do_claim_swap`), add `ItemAttributesApprovalsOf::<T, I>::remove(&collection, &item)`, mirroring the cleanup already performed in `do_burn`, and unreserve/refund deposits held under now-stale `Account(delegate)` attributes analogous to `do_cancel_item_attributes_approval`.

## Proof of Concept
1. Owner A mints item `(collection, item)`.
2. Owner A calls `approve_item_attributes(collection, item, delegate=X)` → `do_approve_item_attributes` inserts `X` into `ItemAttributesApprovalsOf(collection, item)`.
3. Owner A transfers item to Owner B via `transfer` → `do_transfer`; `details.approvals.clear()` runs but `ItemAttributesApprovalsOf(collection, item)` still contains `X`.
4. `X` calls `set_attribute(collection, Some(item), AttributeNamespace::Account(X), key, value)`. `is_valid_namespace` succeeds because `approvals.contains(&X)` is still true, despite B now owning the item and never approving `X`.
5. Owner B has no way to detect this except manually querying `ItemAttributesApprovalsOf`, and only B (not A) can call `cancel_item_attributes_approval` to remove it.

	pub(crate) fn do_approve_item_attributes(
		check_origin: T::AccountId,
		collection: T::CollectionId,
		item: T::ItemId,
		delegate: T::AccountId,
	) -> DispatchResult {
		ensure!(
			Self::is_pallet_feature_enabled(PalletFeature::Attributes),
			Error::<T, I>::MethodDisabled
		);

		let details = Item::<T, I>::get(&collection, &item).ok_or(Error::<T, I>::UnknownItem)?;
		ensure!(check_origin == details.owner, Error::<T, I>::NoPermission);

		ItemAttributesApprovalsOf::<T, I>::try_mutate(collection, item, |approvals| {
			approvals
				.try_insert(delegate.clone())
				.map_err(|_| Error::<T, I>::ReachedApprovalLimit)?;

			Self::deposit_event(Event::ItemAttributesApprovalAdded { collection, item, delegate });
			Ok(())
		})
	}
