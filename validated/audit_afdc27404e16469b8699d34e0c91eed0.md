## Title
Fungible-asset name/symbol seed collision allows front-running and permanent name-squatting DoS of `bonding_curve_launchpad` FA/liquidity-pair objects - (File: `aptos-move/move-examples/bonding_curve_launchpad/sources/bonding_curve_launchpad.move`)

### Summary
`bonding_curve_launchpad` and its companion module `liquidity_pairs` derive the deterministic object address for every fungible asset (FA) and its liquidity pair by concatenating the user-supplied `name` and `symbol` strings with a single `"-"` byte separator and no length prefix, then hashing that with a fixed creator address via `object::create_object_address`: [1](#0-0) [2](#0-1) 

This is precisely the "format ambiguity" class of bug from the external report: `abi.encodePacked`-style concatenation of variable-length, attacker-controlled fields without length delimiters lets two different logical inputs produce identical serialized bytes, hence identical hashes/addresses. Here, `name="AAA"`, `symbol="BBB-CCC"` and `name="AAA-BBB"`, `symbol="CCC"` serialize to the exact same byte string `"AAA-BBB-CCC"`, hence the exact same object address for the shared `fa_generator`/`pairs` signer.

### Finding Description
`object::create_object_address` itself is safe when the seed is a single self-describing value (`sha3_256(source | seed | 0xFE)`), since the domain-separation byte prevents cross-scheme collisions. The vulnerability is introduced one layer up, in how `bonding_curve_launchpad`/`liquidity_pairs` build the `seed` from two independent, fully user-controlled `String` inputs (`name`, `symbol`) with no length-prefixing and no restriction on the separator character (`"-"`) appearing inside either field: [3](#0-2) 

Both `get_fa_obj_address` (used to compute FA addresses) and `get_pair_obj_address`/`register_liquidity_pair` (used for liquidity-pair addresses) apply the same unguarded concatenation against a single, fixed, shared creator address (`fa_generator_address` / `pairs.signer_extender`, both anchored under `@bonding_curve_launchpad`), unlike `object.move`'s `create_named_object`, which at least binds the seed to the calling signer's own address. Since *any* unprivileged caller of `create_fa_pair`/`swap` supplies both `name` and `symbol` (see the entry function signature), an attacker can freely craft `(name, symbol)` pairs that collide with the byte-serialization of any other `(name, symbol)` pair: [4](#0-3) 

`create_fa` and `register_liquidity_pair` both guard against re-creation with `assert!(!does_fa_exist, ...)` / `assert!(!does_already_exist, ...)`, so a colliding creation cannot silently overwrite an already-created object. However, this still breaks the custody invariant that "each (name, symbol) pair maps to a unique, unambiguous asset/liquidity-pair identity": an attacker who front-runs a target FA launch by submitting the colliding `(name', symbol')` pair first will (a) permanently occupy the deterministic address the legitimate `(name, symbol)` combination would have resolved to, causing every subsequent legitimate `create_fa_pair(name, symbol, ...)` call to revert with `EFA_EXISTS_ALREADY`/`ELIQUIDITY_PAIR_EXISTS_ALREADY`, and (b) — more critically — causes any off-chain caller/UI that resolves an FA or liquidity pair purely from `(name, symbol)` strings via `get_fa_obj_address`/`get_metadata`/`get_pair_obj_address` to be redirected to the attacker's colliding object instead of the intended one, since `object::address_to_object` performs no additional binding check beyond the collided address. Because `swap()` resolves both the FA metadata object and its `FAController`/`TransferRef` purely from `get_fa_obj_address(name, symbol)`, any integrator that lets a user pick `name`/`symbol` to swap into can be tricked into interacting with an attacker-controlled FA/liquidity pair sharing the same on-chain address as an intended target string pair, redirecting APT/FA custody to the attacker's pool.

### Impact Explanation
This breaks the custody invariant that fungible-asset metadata, primary stores, and liquidity-pair ownership/control must be uniquely and unambiguously identified by their declared name/symbol. The exploitable outcomes are:
- Permanent denial of a specific `(name, symbol)` FA/liquidity-pair slot (irreversible squatting/front-running), since `create_named_object` never allows re-creation at an already-used address.
- Value/flow redirection: any code path (including `swap`) that derives the FA/pair address purely from attacker-suppliable strings can resolve to a different, attacker-controlled object than the caller intended, misdirecting APT or FA transfers to the attacker's liquidity pair/store.

This is example/demo code (`aptos-move/move-examples/`), not part of the core Aptos Move framework, so it is not itself a mainnet-critical vulnerability in the framework, but it demonstrates a genuine, exploitable custody-pattern bug in the `object::create_object_address`-based seed-construction pattern that any real project copying this idiom (concatenating multiple attacker-controlled strings without length-prefixing before deriving an object seed) would inherit as a high-severity custody/theft vector.

### Likelihood Explanation
High for any deployment of this exact module: both `name` and `symbol` are plain, unrestricted `String` entry-function parameters supplied by any unprivileged caller of `create_fa_pair`, with no length or character restrictions enforced before they are concatenated into the seed. Crafting a colliding pair requires no cryptographic work — it's a simple string-boundary shift around the fixed `"-"` separator.

### Recommendation
Do not concatenate two variable-length, independently-controlled strings directly as an object seed. Instead:
- BCS-serialize `name` and `symbol` as separate length-prefixed fields (e.g., `bcs::to_bytes(&(name, symbol))`) before hashing, so the encoding is injective, or
- Prefix each field with its own length (e.g., `vector::length` as a fixed-width integer) before appending, or
- Reject `name`/`symbol` values containing the separator character, and additionally disallow zero-length components.

### Proof of Concept
```move
// Attacker calls create_fa_pair with a colliding pair before the legitimate creator does:
create_fa_pair(attacker, 0, string::utf8(b"AAA"), string::utf8(b"BBB-CCC"), ...);
// vs. the legitimate intended call:
create_fa_pair(victim, 0, string::utf8(b"AAA-BBB"), string::utf8(b"CCC"), ...);

// Both produce the identical seed bytes "AAA-BBB-CCC", hence:
get_fa_obj_address(string::utf8(b"AAA"), string::utf8(b"BBB-CCC"))
    == get_fa_obj_address(string::utf8(b"AAA-BBB"), string::utf8(b"CCC"))

// Result: the victim's create_fa_pair(...) call reverts with EFA_EXISTS_ALREADY,
// and any caller resolving the FA/pair via get_fa_obj_address("AAA-BBB","CCC")
// is instead directed to the attacker's already-created FA/liquidity-pair object.
```

**Note on scope/confidence:** I was unable to find a comparable collision in the core `aptos-framework` (`object.move`, `account.move`, `multisig_account.move`, `resource_account.move`) — those all bind seeds correctly with fixed-length address prefixes and domain-separation bytes (`0xFE`/`0xFC`/`0xFD` scheme constants), or hash pre-serialized fixed-size fields, so no analogous collision exists there. The `token.move`/`collection.move` token-naming seed (`collection_bytes | "::" | name_bytes`) has the same structural pattern but I could not verify within this session whether downstream code trusts `(collection, name)`-derived addresses for custody-relevant fund routing the way `bonding_curve_launchpad::swap` does; that would need further investigation in a follow-up session if you want it fully ruled in or out.
