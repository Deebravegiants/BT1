### Title
Silent, fee-paying "delivery" of GET responses to no-code addresses bypasses `onGetResponse` execution - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.dispatchIncoming(GetResponse memory response, address relayer)` unconditionally treats a low-level `.call()` to `response.request.from` as a successful delivery, without first checking that the destination has code, unlike its sibling `dispatchIncoming(PostRequest memory request, address relayer)`, which explicitly checks `extcodesize` and early-returns (without writing a receipt) when the destination is codeless.

### Finding Description
In `EvmHost.dispatchIncoming(PostRequest memory request, address relayer)`, the destination is checked for code before any state is written: [1](#0-0) 

In `EvmHost.dispatchIncoming(GetResponse memory response, address relayer)`, no such check exists — the response receipt is written first, then a low-level `call()` is made to `_bytesToAddress(response.request.from)` for `IApp.onGetResponse`, and `success` alone gates whether the receipt is deleted: [2](#0-1) 

In Solidity, a low-level `.call()` targeting an address with no deployed code (an EOA, or a contract that has since self-destructed) always returns `success = true`, because there is no code to execute and thus nothing that can revert. This mirrors the ZeroMQ analog cited in the report: the "handshake" (proof verification and dispatch plumbing) completes successfully and the message is marked delivered, but it is never actually received/processed by any application logic.

Because `dispatchIncoming(GetResponse)` has no `extcodesize` guard analogous to the POST-request path, any `response.request.from` that resolves to a codeless address will:
1. Have its response receipt (`_responseReceipts[commitment]`) permanently written, blocking any future re-delivery attempt via the `DuplicateMessage` check in `HandlerV2.handleGetResponses`: [3](#0-2) 
2. Emit `GetRequestHandled` as if genuinely delivered.
3. Pay out the escrowed relayer fee from `_requestCommitments[commitment].fee`, even though `onGetResponse` never executed.

### Impact Explanation
This is a "route unable to deliver messages" / unauthorized-fee-payout class issue: any GET request whose originating `from` address ends up codeless at response time (e.g., an EOA directly calling the dispatcher, or a contract that self-destructs before the response returns) causes the cross-chain response to be silently and irrecoverably dropped while still being recorded as "handled" and paying the relayer. Because the duplicate-delivery check in `HandlerV2` relies on the receipt being non-empty, there is no retry path — the querying application never receives its data, and the fee is spent regardless.

### Likelihood Explanation
Reachable by an unprivileged actor: dispatching a GET request and having the relayer later submit the (validly-proven) response are both permissionless flows described in `docs/content/developers/evm/api/ihandler.mdx` [4](#0-3) . I was not able to fully confirm from the indexed code whether `EvmHost`'s dispatch function for `DispatchGet` restricts `from` to being a contract, or simply sets it to `msg.sender`/`_msgSender()` unconditionally — grep matches indicate a `from: _msgSender()`-style assignment exists in `EvmHost.sol`, but I could not retrieve and read the exact `dispatch(DispatchGet)` function body to confirm whether EOAs are permitted to originate GET requests. This should be verified directly in `evm/src/core/EvmHost.sol`'s dispatch functions before treating this as confirmed-exploitable versus an accepted design tradeoff (i.e., EOAs intentionally don't need a callback and are expected to read results off-chain).

### Recommendation
Add the same `extcodesize`/no-code guard used in `dispatchIncoming(PostRequest)` to `dispatchIncoming(GetResponse)` before the low-level call, so that a codeless `from` address does not spuriously mark the response as delivered or trigger relayer fee payout, consistent with the POST-request path's behavior.

### Proof of Concept
Not independently reproduced against a live/forked test in this session; the mechanism described (Solidity `call()` to an address with no code returning `success = true` unconditionally) is a well-known EVM property, and the asymmetric code paths are directly visible in the cited `EvmHost.sol` lines. Confirming exploitability requires verifying whether `EvmHost`'s `dispatch(DispatchGet)` permits an EOA (or later-self-destructed contract) as `from`, which a Devin session with full repo/test access should validate with a Foundry test dispatching a GET request from an EOA and delivering its response through `HandlerV2.handleGetResponses`.

        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});

    /**
     * @dev Dispatch an incoming GET response to source module
     * @param response - get response
     */
    function dispatchIncoming(GetResponse memory response, address relayer) external restrict(_hostParams.handler) {
        // replay protection
        bytes32 commitment = response.request.hash();
        _responseReceipts[commitment] = ResponseReceipt({
            relayer: relayer,
            responseCommitment: response.hash()
        });

        (bool success,) = _bytesToAddress(response.request.from)
            .call(abi.encodeWithSelector(IApp.onGetResponse.selector, IncomingGetResponse(response, relayer)));

        if (!success) {
            // so that it can be retried
            delete _responseReceipts[commitment];
            return;
        }

        // reward the relayer fee
        uint256 fee = _requestCommitments[commitment].fee;
        if (fee != 0) {
            IERC20(feeToken()).safeTransfer(relayer, fee);
        }
        emit GetRequestHandled({commitment: commitment, relayer: relayer});
    }

### handleGetResponses()

Processes and delivers GET responses with state data to source applications.

```solidity lineNumbers
function handleGetResponses(
    IHost host,
    GetResponseMessage calldata message
) external
```

| Parameter | Type | Description |
|-----------|------|-------------|
| `host` | `IHost` | The IHost contract |
| `message` | `GetResponseMessage` | Struct containing proof and responses |

**Access:** Permissionless (can be called by anyone)

**Process:**
1. Verifies state proof against stored commitment
2. For each response:
   - Validates destination matches this chain
   - Checks response hasn't timed out
   - Verifies response is for a known request
   - Validates storage proofs for each key
   - RLP-decodes storage values
   - Dispatches to source application

**Important:**
- Storage values are RLP-encoded from the state trie
- Values are provided in same order as requested keys
- Empty storage slots return empty bytes

**Reverts:**
- `InvalidMessageDestination()` - Response not for this chain
- `MessageTimedOut()` - Response exceeded timeout
- `UnknownMessage()` - Request not found
- `InvalidProof()` - State proof verification failed
