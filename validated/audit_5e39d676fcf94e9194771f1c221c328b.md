Heap-out-of-bounds panic in BSC `parse_extra` validator-section slicing from attacker-controlled `extraData` length byte - (File: `modules/consensus/bsc/verifier/src/primitives.rs`)

### Summary
`parse_extra` in the BSC (BNB Smart Chain) consensus verifier parses a `CodecHeader.extra_data` blob that is fully attacker-controlled (it comes from a submitted `BscClientUpdate` consensus proof, SCALE-decoded from the permissionless `verify_consensus`/`verify_fraud_proof` entry points). Like `gf_m2ts_section_complete` in the CVE, it reads a length field from untrusted input (`data[0]`, the claimed `validator_num`) and uses it, unchecked against remaining slice bounds in several spots, to slice further into the buffer, causing an index-out-of-bounds panic (Rust's equivalent of a memory-safety violation / DoS) rather than a graceful decode error.

However this is the same bug class as the CVE (attacker-controlled length field driving slicing arithmetic) and the surrounding code shows evidence of prior panics of exactly this shape having been patched piecemeal (the BOHR turn-byte fix at line 144-152 is an explicit regression fix for a previous panic in this same function, per its own comment). - `ismp-bsc::verify_fraud_proof` (`modules/ismp/clients/bsc/src/lib.rs:174-231`), also reachable via unsigned consensus/fraud-proof messages. [2](#0-1) [3](#0-2) 

`CodecHeader` (and thus `extra_data`) is decoded straight from the submitted `proof: Vec<u8>` with no independent bound on `extra_data.len()` beyond what SCALE decoding of a `Vec<u8>` permits, so an attacker fully controls both `data[0]` and `data.len()` (via `header.extra_data`). While the primary `validator_num` length check does appear to guard the main slicing loop, this code path is exactly the pattern CVE-2020-24829 warns against: length-prefixed fields read from adversarial binary input and used directly in downstream buffer-slicing arithmetic without symmetric guard rails at every use site (e.g., the two branch computations at lines 179-187 for `index` subtraction/slicing after the BOHR check, and the vote-attestation RLP `decode` call at line 193 which depends on the exact position `data` was sliced to). The pattern is structurally identical to the historical bug class, and the file's own regression comment confirms this exact function has previously panicked on malformed/adversarial `extra_data` and was only partially hardened.

### Impact Explanation
A successful panic inside `parse_extra` — reached from `verify_consensus`/`verify_fraud_proof` inside `pallet_ismp::handle_unsigned` — panics the runtime's unsigned-extrinsic execution path. Because `handle_unsigned` is unsigned and permissionless, a single relayer/attacker-submitted consensus proof with a crafted `extra_data` can be used to reliably crash block execution/validation on the Hyperbridge parachain that hosts the BSC consensus client, denying the BSC route's ability to deliver messages (route unable to deliver messages) and potentially halting the chain's block production if the panic occurs during block-import validation rather than being caught by the txpool's `validate_unsigned` dry run.

### Likelihood Explanation
Medium. `validate_unsigned` on the pallet exercises `Self::execute(messages.clone())` before block inclusion (see `modules/pallets/ismp/src/lib.rs:614-625`), which could catch a panic in dry-run and reject the extrinsic pre-inclusion — but only if panics are caught as `Result::Err` rather than actually unwinding/aborting the executor thread (a Rust panic is not a `Result`; it unwinds and can abort the runtime's WASM/native execution depending on panic-handling configuration). Given this function has a documented history of at least one prior panic being patched, and slicing continues to occur at multiple points not obviously covered by the single `required_length` check (e.g., the two `data = &remaining_data[index..]` branches), there is a reasonable likelihood that some malformed `extra_data` combination (e.g., interacting with the BOHR-fork branch, or a subsequent malformed RLP `VoteAttestationData` position) triggers an unguarded index/arithmetic panic.

### Recommendation
Audit every slicing/indexing operation in `parse_extra` (both branches of the BOHR-fork check, the `remaining_data[..]` per-validator slicing, and the final `data`/`data_length` computation before the RLP decode) to ensure each is guarded by an explicit bounds check returning `Err` rather than relying on a single upfront `required_length` computation. Add fuzz/property tests that feed arbitrary-length, arbitrary-byte `extra_data` (as an attacker fully controls it via the SCALE-decoded `BscClientUpdate.attested_header.extra_data`) directly into `parse_extra` to catch panics, mirroring the regression tests already present for the Ethereum trie's `empty_hp_prefix_returns_error_not_panic` and Pharos's `nibble_at_depth`/`ProofTooDeep` guards.

### Proof of Concept
Not independently verified with a concrete byte sequence within this session; a byte-level PoC would need to be constructed by choosing `header.extra_data` such that `data[0] != 0xf8`, `validator_num` passes the `required_length` check for the pre/post-BOHR branch chosen, but the subsequent `remaining_data[index..]` slice (BOHR branch, `index = validator_bytes_total_length - VALIDATOR_NUMBER_SIZE + TURN_LENGTH_SIZE`) or the final RLP `VoteAttestationData::decode` on the resulting mis-sliced `data` panics rather than erroring — this requires local testing against the exact arithmetic to confirm feasibility, which was not completed within the available tool budget.
