### Title
Webhook `shop-domain` is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while the `shop` (and `topic`, `webhook_id`) values that are handed to the application's `WebhookHandler#handle` are read straight from unauthenticated HTTP headers. `Utils::HmacValidator.validate` therefore only proves that the *body bytes* were signed with the app's shared secret — it proves nothing about which shop the event is attributed to. This breaks the identity binding `shop (verified) == shop (acted upon)` that the OAuth code path correctly enforces (`AuthQuery#to_signable_string` explicitly includes `shop` in the signed payload), but the webhook path does not.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely via: [1](#0-0) 

The HMAC check calls `Utils::HmacValidator.validate(request)`, which computes the signature over `request.to_signable_string`: [2](#0-1) 

`Webhooks::Request#to_signable_string` returns only `@raw_body`, never the `shop`, `topic`, or `webhook_id` headers: [3](#0-2) 

Yet `request.shop` (read from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` header) is passed directly into the `WebhookMetadata` struct that the host application's handler acts on: [4](#0-3) [5](#0-4) 

This is inconsistent with how the gem's own OAuth code binds the shop to the HMAC-signed payload: `Auth::Oauth::AuthQuery#to_signable_string` explicitly incorporates `shop` into the signed string, so tampering with the `shop` param invalidates the signature: [6](#0-5) 

No equivalent binding exists for webhooks. The identity equality that should hold — `shop authenticated by HMAC == shop acted upon by the handler` — does not hold; the header-derived `shop` is fully attacker-controlled and independent of the signed content.

### Impact Explanation
Since the webhook secret (`api_secret_key`) is a single, app-wide secret shared across every shop that installs the app (not per-tenant), any unprivileged user who installs the app on their own store receives legitimately HMAC-signed webhook deliveries for their own shop. That attacker can capture a `(raw_body, hmac)` pair from their own store's webhook and replay it to the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop that also has the app installed. `Utils::HmacValidator.validate` will still return `true` because the signature only covers `raw_body`, and the host application's handler will process the event believing it came from the victim shop (`WebhookMetadata#shop`). Depending on how the host app uses `data.shop` (e.g., to key local database writes, trigger data resyncs, or generate/adjust records tied to `shop`), this enables cross-tenant data confusion/corruption — one merchant forging events attributed to another merchant's store. This matches the "Critical – cross-tenant access" impact class.

### Likelihood Explanation
Likelihood is realistic for any embedded/multi-tenant app built on this gem: the attacker only needs to be a legitimate installer of the app on their own shop (no special privilege, no leaked secret) to obtain one valid `(body, hmac)` pair, then can replay it against the shared endpoint with a forged `shop-domain` header, `topic`, or `webhook_id` for a different shop. No credential theft or interception is required — only observation of headers/body from webhooks delivered to the attacker's own store.

### Recommendation
Bind the shop (and ideally topic/webhook_id) into the signature verification, or otherwise cryptographically attest the header values, e.g.:
- Include `shop`, `topic`, and `webhook_id` in `Webhooks::Request#to_signable_string` (mirroring `AuthQuery`'s approach) if Shopify's HMAC scheme supports header-inclusive signing, or
- Cross-check the `shop-domain` header against an independently verified source (e.g., the topic/subscription registered per-shop, or a lookup keyed by webhook_id from Shopify's API) before invoking the handler, and
- Document clearly that `WebhookMetadata#shop` is derived from an HMAC-unprotected header, so host applications must not use it as an authoritative tenant identifier without additional verification.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and receives a legitimate webhook delivery:
   - Headers: `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid-hmac-of-body>`, `x-shopify-topic: orders/create`
   - Body: `{"id": 1, ...}`
2. Attacker replays the exact same body and HMAC header to the app's webhook endpoint, but changes:
   - `x-shopify-shop-domain: victim.myshopify.com`
3. `Registry.process` calls `HmacValidator.validate(request)`, which only checks `OpenSSL.secure_compare(compute_signature(raw_body, secret), hmac)` — unaffected by the header change — so validation succeeds: [2](#0-1) 
4. The handler is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)`, and the host application processes/attributes the (attacker-controlled) event data as belonging to `victim.myshopify.com`.
