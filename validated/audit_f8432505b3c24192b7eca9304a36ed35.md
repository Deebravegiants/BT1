### Title
Fee-on-Transfer/Deflationary ERC20 accounting mismatch in `placeOrder` credits escrow with stated amount instead of actual amount received - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron deployment of `IntentGatewayV2.placeOrder` does not verify the actual token amount received when escrowing ERC20 inputs in the non-predispatch path. It uses `safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` and then credits `_orders[commitment][token] += reducedInputs[i].amount` based on the user-stated `order.inputs[i].amount` (minus protocol fee), never checking the contract's actual token balance delta. For fee-on-transfer / deflationary ERC20 tokens, the amount actually received by the contract will be less than `order.inputs[i].amount`, so the escrow ledger `_orders` is over-credited relative to the physical token balance held by the contract.

### Finding Description
In `placeOrder`, the "no predispatch" branch performs: [1](#0-0) 
which transfers `order.inputs[i].amount` via `safeTransferFrom` but immediately credits `reducedInputs[i].amount` (derived from the same unadjusted `order.inputs[i].amount`) to `_orders[commitment][token]`, without measuring `IERC20(token).balanceOf(address(this))` before/after the transfer.

This is a genuine regression/inconsistency relative to the fixed main EVM implementation, `evm/src/apps/IntentGatewayV2.sol`, which explicitly measures the balance delta for the non-predispatch path: [2](#0-1) 
and mutates `order.inputs[i].amount` to the actually-received value before computing `reducedInputs`/`commitment` and crediting `_orders`. The Tron variant skips this actual-balance measurement entirely in the non-predispatch path, so any fee-on-transfer token input directly produces phantom escrow credit that the contract does not physically hold.

The predispatch branch of the same Tron contract does perform a `balance < requiredAmount` check when sweeping from the call dispatcher back to the gateway, but this only guards against insufficient balance for that specific order; it still stores `reducedInputs[i].amount` (i.e., the user-stated amount minus protocol fee) into escrow rather than the truly swept/received amount, and any transfer-fee shortfall in the direct (non-predispatch) `safeTransferFrom` path is not checked or reconciled at all.

### Impact Explanation
Because `_orders[commitment][token]` is a pooled, per-token accounting ledger shared across multiple orders' commitments, and `withdraw()` blindly transfers `amount` out of the contract's token balance during `RedeemEscrow`/`RefundEscrow` handling: [3](#0-2) 
an order placed with a fee-on-transfer token creates escrow credit that exceeds what the contract actually holds for that token. This corrupts the shared token accounting: subsequent legitimate withdrawals for other orders using the same token can fail (`TransferFailed`, funds frozen/stuck) once the deficit is exposed, or — depending on withdrawal ordering — an attacker can use the inflated credit entry to redeem more tokens than they deposited, draining tokens that back other users' escrowed orders. This is a fund-freezing/fund-loss condition reachable directly from a normal user's `placeOrder` call, matching the "permanent freezing of funds" / "concrete theft" criteria.

### Likelihood Explanation
Any user (or attacker) can trigger this simply by placing an order with a fee-on-transfer ERC20 as an input token — no privileged role required, and no cross-chain proof/relayer cooperation needed to create the initial mismatch (only the source-chain `placeOrder` transaction). The Solidity Tron deployment explicitly imports `SafeERC20`/`IERC20` and mirrors the main gateway's interface, so it is intended to support the same set of ERC20 tokens, including any fee-on-transfer tokens users choose to use, yet lacks the balance-diff safeguard present in the sibling `evm/src/apps/IntentGatewayV2.sol` implementation (as also validated by the fee-on-transfer test suite `evm/tests/foundry/IntentGatewayV2SameChainTest.sol` written against the main contract, but with no analogous protection/tests in the Tron contract).

### Recommendation
Mirror the fix already present in `evm/src/apps/IntentGatewayV2.sol`: in the non-predispatch branch of `evm/tron/contracts/apps/IntentGatewayV2.sol`, record `balBefore = IERC20(token).balanceOf(address(this))` before `safeTransferFrom`, then set `order.inputs[i].amount = IERC20(token).balanceOf(address(this)) - balBefore` after the transfer, and compute `reducedInputs`/`commitment`/`_orders` credits from this actual-received amount rather than the caller-supplied `order.inputs[i].amount`. Apply the same reconciliation to the predispatch-path escrow crediting so `_orders[commitment][token]` always reflects the token balance actually held by the contract for that order.

### Proof of Concept
1. Deploy a 1% fee-on-transfer ERC20 token and mint balance to `user`.
2. `user` approves `IntentGatewayV2` (Tron) for `inputAmount = 1000e18` and calls `placeOrder` with `order.inputs = [{token: fot, amount: 1000e18}]` and no `predispatch`.
3. `safeTransferFrom(user, address(this), 1000e18)` executes; due to the 1% fee, the gateway's actual balance only increases by `990e18`.
4. `reducedInputs[i].amount` is computed from the unadjusted `1000e18` (minus any protocol fee), and `_orders[commitment][fot] += reducedInputs[i].amount` credits close to `1000e18` (or `1000e18` if `protocolFeeBps == 0`) even though the gateway only holds `990e18` of `fot`.
5. When a solver fills the order and a `RedeemEscrow`/`RefundEscrow` request triggers `withdraw()`, the contract attempts `token.call(transfer(beneficiary, amount))` for the phantom `1000e18` credited amount, either reverting (freezing the order and consuming any other orders' commingled balance of `fot`) or, if the pooled contract balance of `fot` from other orders covers the shortfall, silently draining other orders' escrowed `fot` balance to cover this over-credit — corrupting the shared accounting for all users of that token on the Tron gateway.
