### Title
Session token `iss` claim is decoded but never validated, allowing non-admin (checkout/customer-context) session tokens to be used for OAuth Token Exchange and session identification - (File: `lib/shopify_api/auth/jwt_payload.rb`, `lib/shopify_api/auth/token_exchange.rb`, `lib/shopify_api/utils/session_utils.rb`)

### Summary
`ShopifyAPI::Auth::JwtPayload` decodes and exposes the `iss` (issuer) claim of a Shopify session token but only validates the `aud` claim against `Context.api_key`. Both `TokenExchange.exchange_token` and `Utils::SessionUtils.session_id_from_shopify_id_token` accept any correctly-signed token and act on the `dest`/`sub` claims without checking that `iss` indicates an admin session token. Since Shopify signs session tokens for multiple surfaces (Admin embedded apps `.../admin`, Checkout UI Extensions `.../checkouts`, etc.) with the same shared `client_secret`, a token issued for a lower-privilege surface (available to anonymous storefront/checkout visitors) is structurally indistinguishable to this gem from an admin session token, and will be accepted equally.

### Finding Description
`JwtPayload#initialize` decodes the JWT and only enforces one binding: [1](#0-0) 

The `iss`, `dest`, `sub`, and `sid` claims are stored as plain attributes with no verification that `iss` corresponds to an admin context. The helper `admin_session_token?` exists in the class but is only used internally to gate `shopify_user_id`, not to gate whether the token itself is trustworthy for privileged operations: [2](#0-1) 

The test suite even documents that a non-admin, checkout-context payload (`iss: ".../checkouts"`) decodes successfully through the exact same code path as an admin payload: [3](#0-2) [4](#0-3) 

`TokenExchange.exchange_token` then takes any such token, extracts `dest` as the shop, and forwards it to Shopify's `/admin/oauth/access_token` token-exchange endpoint together with the app's own `client_id`/`client_secret`, requesting a fully privileged online or offline **merchant** access token: [5](#0-4) 

Similarly, `Utils::SessionUtils.session_id_from_shopify_id_token` derives a session id purely from `dest`/`sub` with no `iss` check, so a checkout-context token can be used to synthesize a valid-looking admin session id: [6](#0-5) 

The broken identity binding is: **"caller who holds a Shopify-signed session token" == "authorized Shopify Admin/embedded-app actor for that shop"**, when in fact Shopify issues the same HS256-signed token format (secret = app's `client_secret`) to multiple non-admin surfaces (e.g. Checkout UI Extensions, which are reachable by anonymous storefront customers). The library never checks the `iss` claim to confirm the token was actually minted for the Admin embedded-app surface before treating it as authorization to mint an access token or to derive an authenticated session id.

### Impact Explanation
An anonymous storefront visitor who can obtain a checkout-context (or any other non-admin surface) session token signed with the app's shared secret can feed that token into `TokenExchange.exchange_token`, and because only `aud` (the app's own client id, which is public) is checked, the gem will happily forward it to Shopify's token-exchange endpoint using the app's `client_id`/`client_secret` and receive back a genuine merchant-scoped access token for `dest_shop`. This is theft/escalation of a merchant access token driven by an actor who was never an authenticated Admin user — a Critical-impact issue per the defined categories (theft of a merchant access token via authentication/authorization bypass).

### Likelihood Explanation
Any host application built on this gem that follows the documented Token Exchange flow (`docs/usage/oauth.md`, `session_token` provided via App Bridge or extension context) is affected as soon as it accepts session tokens from any Shopify-signed surface without itself independently re-checking `iss`. Because the gem exposes no built-in enforcement or documented requirement to check `iss`, and the helper that could do so (`admin_session_token?`) is private and unused for this purpose, the omission is systemic rather than a corner case.

### Recommendation
In `JwtPayload#initialize`, enforce that `iss` ends with `/admin` (or otherwise matches the expected admin-surface issuer pattern) before allowing the payload to be used for privileged flows, or add an explicit, mandatory check in `TokenExchange.exchange_token` and `SessionUtils.session_id_from_shopify_id_token` that rejects tokens whose `iss` does not indicate an Admin session token, raising `Errors::InvalidJwtTokenError` otherwise.

### Proof of Concept
1. An anonymous customer loads a checkout page for a shop where the target app has an active Checkout UI Extension; Shopify hands the extension a session token signed with the app's `client_secret`, with `iss: "https://{shop}/checkouts"`.
2. The customer captures this token client-side and POSTs it as `session_token` to the app's token-exchange endpoint (which calls `ShopifyAPI::Auth::TokenExchange.exchange_token`).
3. `JwtPayload.new(session_token)` succeeds because `aud == Context.api_key` (public value) and signature verifies (shared secret, valid for any Shopify-issued surface token) — `iss` is never checked, per [1](#0-0) .
4. `exchange_token` extracts `dest_shop` and calls Shopify's `/admin/oauth/access_token` with the app's real `client_id`/`client_secret`, per [7](#0-6) , returning a merchant-scoped `ShopifyAPI::Auth::Session` with a genuine access token to the anonymous caller.
