### Title
Permanent market freeze from RAY-value overflow during interest accrual - (File: common/src/rates/scaling.rs)

### Summary
A sufficiently large supplied or borrowed market can overflow `i128` when accrual converts scaled shares back to original RAY value, permanently freezing that market. [1](#0-0) [2](#0-1) 

### Finding Description
`Controller::update_indexes(caller, assets)` is permissionless after caller authorization and forwards the selected `HubAssetKey` list to the pool. [3](#0-2) [4](#0-3) 

Every pool operation first loads the market and executes `interest::global_sync`. [5](#0-4)  `global_sync` calls `accrue_step`, which computes `borrowed * borrow_index` and `supplied * supply_index` before the new index is calculated. [6](#0-5) [7](#0-6) 

`scaled_to_original` delegates to `Ray::mul`, whose checked multiply-divide panics with `MathOverflow` if the resulting RAY value does not fit in `i128`. [1](#0-0) [8](#0-7) [9](#0-8) 

The borrow-index cap is applied only after `old_index.mul(interest_factor)` and does not bound the separate `scaled_amount * index` value used for utilization and rewards. [10](#0-9) [11](#0-10) 

### Impact Explanation
Once the scaled book and index product exceed `i128::MAX`, the panic occurs before the mutated accrual result or timestamp can be committed. [12](#0-11) [13](#0-12) 

Because supply, borrow, withdraw, repay, liquidation settlement, net settlement, revenue claims, and maintenance all enter the same synced-market path, the affected market remains permanently unable to repay debt, release collateral, liquidate borrowers, or pay suppliers. [5](#0-4) [14](#0-13) [15](#0-14) 

### Likelihood Explanation
The attacker does not need privileged calls during the trigger: after a large market reaches the vulnerable scaled-value/index domain through ordinary supply and borrow usage, any unprivileged caller can invoke `update_indexes(caller, vec![hub_asset])` or any normal market operation to hit the same panic. [3](#0-2) [4](#0-3) 

Likelihood is constrained by the need for a very large pool-wide book and sustained high-utilization accrual, but the included regression demonstrates a reachable market configuration where the index cap does not intervene before the value overflow. [15](#0-14) [16](#0-15) 

### Recommendation
Bound accrual on representable scaled values rather than only on the index: before calling `scaled_to_original`, check `scaled <= i128::MAX * RAY / index`, or use saturating/widened accounting for utilization and reward calculation. [1](#0-0) [10](#0-9) 

The safer remediation is to make `accrue_step` cap or safely handle the index before calculating `borrowed_original`, `supplied_original`, `old_total_debt`, or `new_total_debt`, so an overlarge book cannot trap all future entry and exit paths. [17](#0-16) [11](#0-10) 

### Proof of Concept
The repository regression demonstrates this exact sequence: create an 18-decimal market, supply one billion whole tokens, borrow at high utilization, advance accrual until `scaled_to_original` overflows, then observe that even repay and withdraw revert with `MathOverflow`. [15](#0-14) 

```rust
// Setup state:
// BIG18 supply shares = 1_000_000_000 * 10^27
// BIG18 debt shares   = 98% of that supply
// BIG18 uses a steep high-utilization rate curve.

controller.update_indexes(
    attacker,
    vec![HubAssetKey {
        hub_id,
        asset: big18,
    }],
);
// Reverts with GenericError::MathOverflow inside
// accrue_step -> scaled_to_original -> Ray::mul.

controller.repay(
    payer,
    borrower_account_id,
    vec![(hub_asset, 1)],
);
// Reverts again because synced_market accrues before repayment.

controller.withdraw(
    supplier,
    supplier_account_id,
    vec![(hub_asset, 1)],
);
// Reverts for the same reason; the market is permanently frozen.
```

    supply_index: Ray,

    let supplied_original = scaled_to_original(env, supplied, supply_index);

    let interest_factor = compound_interest(env, borrow_rate, delta_ms);

    let new_borrow_index = update_borrow_index(env, borrow_index, interest_factor);

    // this step.

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}

pub fn mul_div_half_up(env: &Env, x: i128, y: i128, d: i128) -> i128 {

        .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow))
}

/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);

            break e;
        }

## Numeric and resource limits

Finite RAY value capacity can be exhausted before the index ceiling. Synchronizing
an overlarge book can then fail before an otherwise risk-reducing operation.
Caps must account for plausible index growth as well as token balances.
Accrual cadence changes utilization and subsequent rates; bounded chunks do not
make cadence neutral or prove exact conservation after integer rounding.
See [numeric limits](../reference/formulas.md#numeric-limits).
