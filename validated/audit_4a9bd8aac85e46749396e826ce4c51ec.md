### Title
Webhook shop-domain identity spoofing via HMAC that only covers the raw body, not headers - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC verified by `ShopifyAPI::Utils::HmacValidator.validate` in `ShopifyAPI::Webhooks::Registry.process` authenticates the request body alone. The `shop` value (read from the `shopify-shop-domain`/`x-shopify-shop-domain` header) is never part of the signed material, yet it is passed straight through to the app's webhook handler as the authoritative tenant identifier.

### Finding Description
`Webhooks::Request` exposes `topic`, `shop`, `api_version`, and `webhook_id` purely from HTTP headers: [1](#0-0) 

`Registry.process` calls `Utils::HmacValidator.validate(request)` and, if it passes, hands `request.shop` (plus the parsed body) to the registered handler as trusted `WebhookMetadata`: [2](#0-1) 

`HmacValidator.validate` computes the HMAC only over `verifiable_query.to_signable_string`: [3](#0-2) 

For `Webhooks::Request`, `to_signable_string` is just the raw body — no header, including `shop`, is included in the signable string: [4](#0-3) 

This breaks the identity binding `HMAC-authenticated bytes == tenant-identifying bytes acted on`. The library's own documentation tells integrators that `Registry.process` "will verify the request did indeed come from Shopify" and then hand the handler a trusted `shop` field to key their per-tenant logic on (the docs' own example does `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`): [5](#0-4) [6](#0-5) 

### Impact Explanation
An unprivileged internet user who is a legitimate merchant of the target app (i.e., controls their own shop and thus receives real, correctly-signed webhooks for that shop) can capture one of their own genuine `raw_body` + `hmac` header pairs. Because the HMAC only signs `raw_body`, the attacker can resend that exact same body/HMAC combination to the app's webhook endpoint while substituting the `shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` still returns `true` (the body/HMAC pair is valid), and `Registry.process` will invoke the handler with `data.shop` set to the victim's domain. Any host application that follows the gem's documented pattern of keying webhook-driven writes/side effects by `data.shop` will process the attacker's payload as if it originated from the victim tenant — a cross-tenant data injection/corruption primitive using only the attacker's own valid Shopify-issued webhook traffic.

### Likelihood Explanation
Any real merchant of the app can trivially capture their own valid webhook deliveries (e.g., by triggering an event like `orders/create` in their own store) and replay them with a modified `shop-domain` header using a simple HTTP client. No secrets, tokens or privileged access are required beyond being a normal installed-app tenant, which satisfies the "unprivileged internet user" bar.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the HMAC-signed material, or otherwise cryptographically bind the `shop` header to the request signature before exposing it via `WebhookMetadata`. At minimum, cross-check `request.shop` against a shop known to have an active subscription/session for that topic before trusting it in the handler, and update the documentation to clarify that `data.shop` is not itself HMAC-authenticated.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and registers/receives a webhook for `orders/create`, capturing the raw POST body `B` and the valid header `x-shopify-hmac-sha256: H` (computed by Shopify over `B` with the app's `client_secret`).
2. Attacker POSTs to the app's webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H` unchanged, but `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` and matches `H` — validation succeeds (`lib/shopify_api/utils/hmac_validator.rb` lines 12-31, `lib/shopify_api/webhooks/request.rb` lines 35-38).
4. The handler is invoked with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: parsed(B), ...)` (`lib/shopify_api/webhooks/registry.rb` lines 198-199), even though the payload actually originated from, and was signed for, the attacker's own shop.

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
