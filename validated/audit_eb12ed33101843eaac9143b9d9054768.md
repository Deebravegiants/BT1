### Title
Unauthenticated `CallDispatcher.dispatch()` allows anyone to steal any token/ETH balance left on the shared dispatcher singleton - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher` is a single, shared, singleton contract used by every app in the protocol (`IntentGatewayV2`/`IntentsBase`, `HyperFungibleToken`, `WrappedHyperFungibleToken`) to execute arbitrary user-supplied calldata (predispatch/postdispatch swaps, calldata-execution on mint/unlock). Its `dispatch(bytes)` entrypoint is `external` with **no caller restriction whatsoever** — exactly the same design flaw as the reported `FeeWrapper.rubicall`. Any account holding a residual balance on the dispatcher (from an incompletely-swept predispatch/postdispatch call) can have those funds stolen by an attacker who simply calls `dispatch()` directly with a `Call[]` that sends the balance to themselves.

### Finding Description
`CallDispatcher.dispatch` has no access control: [1](#0-0) 

It is deployed once and referenced from `IntentGatewayV2`/`IntentsBase` as `_params.dispatcher`, and from `HyperFungibleToken`/`WrappedHyperFungibleToken` as `_dispatcher`, i.e. it is a shared, persistent, addressable contract just like `FeeWrapper` in the original report.

In `IntentGatewayV2.placeOrder`, predispatch assets are transferred to the dispatcher, arbitrary user-supplied calldata (`order.predispatch.call`) is executed on it, and then the resulting balance is swept back to the gateway strictly for the tokens declared in `order.inputs`: [2](#0-1) 

Symmetrically, `IntentsBase._execute` runs arbitrary output calldata (`order.output.call`) via the same dispatcher and only sweeps back the tokens listed in `order.output.assets`: [3](#0-2) 

`HyperFungibleToken`/`WrappedHyperFungibleToken` also route arbitrary user-supplied calldata through the same `dispatch()` call after minting/unlocking tokens directly to (or through) the dispatcher: [4](#0-3) 

Because the dispatcher only sweeps tokens explicitly enumerated by the caller (`order.inputs`, `order.output.assets`), any token balance produced or left on the dispatcher that is *not* one of those enumerated tokens — e.g. reward tokens from a DEX, dust from a partially-filled swap, an intermediate asset in a multi-hop route, or tokens accidentally sent to the well-known dispatcher address — remains sitting on a contract that anyone can call `dispatch()` on directly. Since `dispatch()` performs raw `.call{value: call.value}(call.data)` with no ownership check on `msg.sender` and no restriction on `to`/`data`, an attacker can drain any such balance with a single unprivileged call, exactly mirroring the `FeeWrapper.rubicall` exploit path where "there is no way to distinguish between users" and anyone can make the wrapper "call any function of any contract with any arguments."

### Impact Explanation
Any token or native-ETH balance that transiently or unexpectedly rests on the shared `CallDispatcher` — because it falls outside the declared `inputs`/`output.assets` set that the calling app sweeps — is directly and immediately stealable by any unprivileged address. Given that arbitrary, user-controlled calldata (predispatch/postdispatch/calldata-execution) is routed through this single contract for every app in the protocol, this significantly broadens the blast radius: a bug or edge case in *any* app's sweep accounting (fee-on-transfer surprises, multi-hop swap slippage/dust, unaccounted reward tokens from a DEX call, or a stray direct transfer to the dispatcher) turns into unconditional theft of user/protocol funds by a completely unrelated third party, with no way to attribute or restrict the caller.

### Likelihood Explanation
`dispatch()` is a permanently deployed, public, unauthenticated function with a predictable/known address (referenced by every app as `_params.dispatcher`/`_dispatcher`), so exploitation requires no special access — just watching the dispatcher's token/ETH balance and calling `dispatch()` before any (nonexistent) mechanism could recover it. The likelihood of *some* balance persisting there is non-trivial given the multiple execution paths (predispatch swaps, postdispatch DeFi routing, HFT calldata execution) that only sweep tokens the caller explicitly lists.

### Recommendation
Restrict `CallDispatcher.dispatch()` to only be callable by the whitelisted set of protocol contracts (`onlyAuthorizedCaller` style access control), or make the dispatcher a per-call/ephemeral proxy (e.g., deployed via `CREATE2`/cloned and self-destructed per invocation) so no address can ever accumulate a persistent, publicly-drainable balance. Additionally, add a reentrancy guard and ensure every app that routes calldata through the dispatcher sweeps *all* token balances left behind (not just the tokens explicitly declared in `inputs`/`output.assets`) before returning control.

### Proof of Concept
1. A user places an order via `IntentGatewayV2.placeOrder` with `predispatch.call` performing a multi-hop swap (e.g., ETH → TokenA → TokenB) where `order.inputs` only declares `TokenB`. Due to slippage/partial routing, some `TokenA` remains on the `CallDispatcher` after the swap; the sweep loop in `placeOrder` (`evm/src/apps/IntentGatewayV2.sol:260-289`) only builds transfer calls for tokens in `order.inputs`, so the leftover `TokenA` balance stays on the dispatcher.
2. An attacker (unrelated to the order) observes the `TokenA` balance sitting on the well-known `CallDispatcher` address and calls `CallDispatcher.dispatch(abi.encode([Call({to: TokenA, value: 0, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, balance)})]))` directly.
3. Because `dispatch()` performs no caller check (`evm/src/utils/CallDispatcher.sol:44-61`), the call succeeds and transfers the stranded `TokenA` to the attacker, with no way for the legitimate user/protocol to prevent or reverse it.

     *  @dev reverts if the target is not a contract or if any of the calls reverts.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
