### Title

Unvalidated swap routes let attacker-controlled contracts drain caller wallet tokens - ([File: contracts/controller/src/strategies/swap.rs])

### Summary

`swap_collateral` and the other route-bearing strategies accept opaque user-controlled `swap: Bytes` and forward it to the configured router, whose routes may invoke payload-selected pool contracts below the caller’s authorization. [1](#0-0) [2](#0-1) [3](#0-2) 

The controller protects its own input transfer and measured output, but those checks do not prevent a route-selected contract from requesting an unrelated `token.transfer(caller, attacker, amount)` that Soroban simulation attaches to the caller’s authorization tree. [4](#0-3) [5](#0-4) 

### Finding Description

`swap_collateral(caller, account_id, current, amount, new, swap)` authenticates `caller`, requires ownership or delegation, and passes the supplied `swap` into the withdraw-and-swap strategy path. [6](#0-5) [7](#0-6) [8](#0-7) 

`swap_tokens` snapshots only `token_in` and `token_out`, authorizes one exact controller-to-router input transfer, and invokes `execute_strategy(controller, amount_in, swap)`. [9](#0-8) [10](#0-9) 

Because the router executes route-selected pool code and does not confine that code to pool behavior, a malicious pool can call `token.transfer(victim, attacker, amount)` during the hop. [11](#0-10) [12](#0-11) 

Simulation records that transfer as a child of the victim’s `swap_collateral` authorization; if the victim signs the simulated tree, enforcement accepts the transfer and the unrelated wallet tokens move to the attacker while the swap itself can still return a fair output. [13](#0-12) [14](#0-13) 

### Impact Explanation

A crafted route can steal any token balance the caller holds, including assets completely unrelated to the lending position and unbounded by `amount`, `min_out`, measured router output, or the account’s final health checks. [15](#0-14) [16](#0-15) 

The demonstrated result is theft of user funds: the victim’s unrelated token balance decreases to zero, the attacker receives the full amount, and the lending account receives the expected swapped collateral. [17](#0-16) 

### Likelihood Explanation

Any unprivileged attacker can deploy a pool contract and craft a route that names it, but exploitation requires convincing an account owner or delegate to sign the poisoned authorization tree produced by simulation. [18](#0-17) [19](#0-18) 

The protocol’s own threat model confirms that an honest controller strategy should produce no child authorization, while a malicious route can add one and execute it if signed. [11](#0-10) 

### Recommendation

Do not permit route payloads to select arbitrary executable pool contracts inside a caller-authenticated lending transaction. Enforce a governance-controlled allowlist of concrete venue or pool addresses at the router boundary, or replace opaque external venue dispatch with fixed adapters that cannot invoke attacker-supplied contracts. Clients should additionally reject a controller-strategy authorization tree containing any child invocation, since the expected controller swap grants are made with controller self-authorization rather than caller child auth. [2](#0-1) [20](#0-19) 

### Proof of Concept

1. Deploy a malicious hop contract whose `swap()` executes `token.transfer(victim, wallet_token, attacker, amount)`.
2. Construct `swap_collateral(alice, account_id, USDC, amount, ETH, malicious_route)` where the route names that contract.
3. Simulate the transaction; the wallet-token transfer appears as a child beneath Alice’s `swap_collateral` authorization.
4. Have Alice sign that simulated tree.
5. Execution transfers Alice’s unrelated wallet tokens to the attacker while returning fair `ETH` output to her lending position. [21](#0-20) [22](#0-21) 

The repository’s regression test demonstrates both the unauthorized rejection under an honest root-only tree and successful theft when the simulated poisoned child is signed. [23](#0-22)
