### Title
Webhook shop identity spoofing via unsigned `x-shopify-shop-domain` header - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`)

### Summary
`HmacValidator.validate_signature` verifies `OpenSSL.secure_compare(computed_signature, received_signature)` where `computed_signature` is computed over `verifiable_query.to_signable_string`. For `ShopifyAPI::Webhooks::Request`, `to_signable_string` returns only `@raw_body` [1](#0-0) , while the tenant identity `request.shop` is read straight from the `x-shopify-shop-domain`/`shopify-shop-domain` header, which is never part of the signed content [2](#0-1) . Because the HMAC secret is the app's single `api_secret_key`/`old_api_secret_key` shared across every shop that installed the app [3](#0-2) , an attacker who legitimately received one authentic, validly-signed webhook for their own shop can replay the same `raw_body`+HMAC while swapping the shop-domain header to any victim shop, and the signature check still passes.

### Finding Description
The intended binding is: `shop identity used by the handler == shop identity covered by the verified signature`. Tracing the code shows this equality does not hold for webhooks.

- `Registry.process` calls `Utils::HmacValidator.validate(request)` [4](#0-3) .
- `HmacValidator.validate_signature` computes the HMAC over `verifiable_query.to_signable_string` and compares it to `verifiable_query.hmac` [5](#0-4) .
- For `Webhooks::Request`, `hmac` comes from the `hmac-sha256` header and `to_signable_string` is just `@raw_body` [6](#0-5) . Neither `topic`, `shop-domain`, `webhook-id`, nor `api-version` headers participate in the signature — only the request body does.
- After `validate` returns `true`, `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` and hands it to the app's handler [7](#0-6) . `request.shop` is read directly and unconditionally from the attacker-controllable header [2](#0-1) .

Attacker flow: the attacker installs the app on their own store (an unprivileged, self-serviceable action), registers their own HTTP webhook endpoint, and receives a genuine, validly-signed webhook whose `raw_body` and `hmac` header they fully control the capture of. They then send a POST directly to the app's public webhook route with the identical `raw_body`/`hmac-sha256` header (unchanged, so the signature check still succeeds) but with `x-shopify-shop-domain` rewritten to an arbitrary victim shop domain. `HmacValidator.validate` returns `true` because it only checked that the *body* was HMAC'd with the app's shared secret — it never checked that the *shop* asserted in the request matches the shop that produced that body. The app's handler then processes attacker-supplied `body`/`topic` data as if it belonged to the victim shop, i.e., it acts on an identity (`request.shop`) that was never covered by the verified artifact (`raw_body`).

None of the existing guards prevent this: `ShopValidator.sanitize!` and the OAuth `state` comparison apply only to the OAuth callback path (`AuthQuery#to_signable_string` *does* include `shop`, so OAuth callbacks are correctly bound) [8](#0-7) ; `JwtPayload`'s `aud`/session-token checks and `HttpRequest#verify` are unrelated to webhook processing; `Context.setup?`/`private?`/`embedded?` are configuration flags, not per-request identity checks. There is no code anywhere in `Registry.process` or `Request` that ties `shop` to the signed `raw_body`.

### Impact Explanation
The webhook handler is invoked believing the event genuinely originates from the shop named in `data.shop`, per the documented handler contract [9](#0-8) . Host applications (as shown in the gem's own documented usage pattern) key their per-merchant data/session/access-token lookups by this shop domain. An attacker can therefore inject an arbitrary, Shopify-signature-valid webhook body while asserting any victim shop's identity, causing the app to process attacker-chosen data under a victim tenant's context — a cross-tenant confusion that can lead the app to use the victim merchant's stored `X-Shopify-Access-Token` in response to attacker-controlled event data. This is repeatable against any shop domain (the attacker doesn't need to know anything about the victim beyond its `.myshopify.com` domain, which is often public/guessable) and can be repeated for every webhook topic the app has registered.

### Likelihood Explanation
Preconditions are minimal: the attacker only needs a free Shopify development store, must install the target app on it (self-service, standard OAuth flow available to any unprivileged user), and register their own HTTP webhook endpoint for a topic the app supports — all normal, permitted actions. No secrets, no privileged access, and no cooperation from Shopify or the app developer are required. The cost is a single legitimate webhook delivery capture plus one crafted HTTP replay with a modified header, making this trivially repeatable at will.

### Recommendation
Bind the asserted shop identity to the signed content before trusting it. At minimum, `Webhooks::Request#to_signable_string` should not be the sole signature input — the app should independently verify that `request.shop` corresponds to a shop with an active installation known to the app (e.g., look up a stored session/access token for that shop and reject if none exists), and/or Shopify's webhook signature should be validated as covering the full set of `x-shopify-*` headers, not just the body. Until then, document explicitly that `request.shop` is unauthenticated and must never be trusted as a tenant key without an independent installation/session check.

### Proof of Concept
```ruby
# test/webhooks/shop_spoof_test.rb
require_relative "../test_helper"

module ShopifyAPITest
  module Webhooks
    class ShopSpoofTest < Test::Unit::TestCase
      def test_hmac_valid_across_spoofed_shop_domain
        raw_body = "{}"
        valid_hmac = OpenSSL::HMAC.digest(
          OpenSSL::Digest.new("sha256"),
          ShopifyAPI::Context.api_secret_key,
          raw_body,
        )

        # Attacker's own legitimately-received webhook artefact
        attacker_headers = {
          "x-shopify-topic" => "orders/create",
          "x-shopify-hmac-sha256" => Base64.encode64(valid_hmac),
          "x-shopify-shop-domain" => "attacker-shop.myshopify.com",
        }
        attacker_request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: attacker_headers)
        assert(ShopifyAPI::Utils::HmacValidator.validate(attacker_request))

        # Replayed with victim's shop domain, same body/hmac
        spoofed_headers = attacker_headers.merge("x-shopify-shop-domain" => "victim-shop.myshopify.com")
        spoofed_request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: spoofed_headers)

        # Signature still verifies (bound to body only, not shop)
        assert(ShopifyAPI::Utils::HmacValidator.validate(spoofed_request))
        # But the identity used downstream has changed
        assert_equal("victim-shop.myshopify.com", spoofed_request.shop)
      end
    end
  end
end
```
This demonstrates that the verified object (`raw_body`) and the object used for tenant identity (`request.shop`) diverge while the signature check's verdict stays `true` for both, breaking the SINGLE IDENTITY invariant.
