### Title
Arbitrary route contracts can append unauthorized wallet token transfers to a user-signed authorization tree - (File: contracts/swap-aggregator/src/execute/mod.rs)

### Summary
A malicious swap route can name an attacker-controlled pool address. While executing under the victim’s `sender.require_auth()` context, that contract can call `token.transfer(victim, attacker, amount)` for any token held by the victim. Soroban records this nested transfer as a child of the victim’s authorization entry, so a wallet that presents or signs the simulated tree without rejecting unexpected children authorizes theft of funds unrelated to the swap.

### Finding Description
`execute_strategy` authenticates `sender`, then decodes a caller-supplied route whose `assets` entries supply each hop’s `pool`, `token_in`, and `token_out` addresses. The instruction loop dispatches those arbitrary pool addresses through `venues::dispatch_hop`. Although the router measures only its own input and output balances, the called pool executes arbitrary contract code while the victim’s root authorization is active. That code can invoke `token.transfer` with the victim as `from`; the token’s `from.require_auth()` is satisfied only if the victim signs the resulting child invocation. The existing security test demonstrates this exact behavior: simulation places `wallet_token.transfer(alice, attacker, WALLET_BALANCE)` below `controller::swap_collateral`, and enforced authorization succeeds when that child is included in the signed tree.

### Impact Explanation
A victim can lose arbitrary wallet tokens, including assets not supplied to the protocol and not referenced by the route. The loss is not bounded by `total_in`, the route’s minimum output, controller collateral checks, or the router’s measured output because the malicious transfer targets the victim’s external wallet balance. A similar tree can be produced through controller strategy entrypoints such as `swap_collateral`, or through a direct `execute_strategy` call. This is theft of user funds and is appropriately High severity: the attacker must get the victim to submit/sign a poisoned route authorization, but can then steal assets outside the declared swap input.

### Likelihood Explanation
The route format intentionally accepts arbitrary asset addresses, and hop dispatch does not validate `hop.pool` against an allowlist or restrict what the invoked contract may do. The attack requires user authorization, but the malicious transfer is nested inside a plausible simulated authorization tree and may be difficult for ordinary wallet UX to distinguish from the legitimate input pull. The repository’s test explicitly proves both simulation recording and successful execution once the poisoned child invocation is signed.

### Recommendation
Do not invoke user-supplied pool addresses under the swap sender’s authorization context. Constrain route hops to governance-approved venue/pool contracts, or restructure route execution so external venue code cannot request token transfers from the original user. At minimum, require router dispatch to call only adapter-authenticated contracts whose expected ABI and authorization behavior are pinned, and make wallets/clients reject any authorization tree containing children other than the single expected `token_in.transfer(sender, router, total_in)`.

### Proof of Concept
The existing test deploys `RogueHopPool`, stores `(victim, wallet_token, attacker, amount)`, and calls `token::Client::transfer(&victim, &attacker, &amount)` from its `swap` method. A route through that pool causes simulation to record the wallet transfer as a child of Alice’s `swap_collateral` authorization and drains `WALLET_BALANCE`; enforcing mode then confirms that signing the poisoned child authorizes the theft. See `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs:62-70`, `:195-226`, and `:258-268`.
