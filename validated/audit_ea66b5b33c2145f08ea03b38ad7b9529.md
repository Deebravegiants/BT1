### Title
Webhook tenant-identifying fields (`shop`, `topic`, `webhook_id`, `api_version`) are excluded from HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content solely from the raw HTTP body, while `shop`, `topic`, `webhook_id`, and `api_version` are read unauthenticated straight from request headers. `ShopifyAPI::Webhooks::Registry.process` validates only the body's HMAC and then unconditionally trusts `request.shop` (and the other header fields) to build the `WebhookMetadata` passed to the app's handler. This is the exact bug class in the report: fields that are acted upon by downstream logic (tenant attribution) but are not included in the signed data, so they can be altered without invalidating the signature.

### Finding Description
`VerifiableQuery#to_signable_string` for `Webhooks::Request` returns only `@raw_body` [2](#0-1) . The `shop`, `topic`, `api_version`, and `webhook_id` accessors read directly from HTTP headers with no cryptographic binding to the body or to each other [3](#0-2) . `HmacValidator.validate` only checks `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)` [4](#0-3) , i.e. it proves the *body bytes* were HMAC'd with the app's shared secret, but proves nothing about which shop, topic, or webhook id the caller claims those bytes belong to. `Registry.process` then raises only if the HMAC fails, and otherwise builds `WebhookMetadata` directly from the unauthenticated `request.shop`/`request.topic`/`request.webhook_id`/`request.api_version` and hands it to the app's handler [5](#0-4) . The documented handler contract explicitly tells app authors to trust `data.shop` as "The shop domain of the webhook" [1](#0-0)  and the documented Rails example passes the constructed `Request` straight to `process` with no additional shop verification [6](#0-5) .

The identity binding broken here, expressed as an equality that should hold but doesn't:
`shop-domain header value == shop bound inside the HMAC-signed payload` — currently the left side is attacker-controlled header text and the right side does not exist at all, since only the raw body is signed.

By contrast, the OAuth callback path in this same gem does this correctly: `Auth::Oauth::AuthQuery#to_signable_string` includes `shop`, `host`, `code`, `state`, and `timestamp` inside the signed query string [7](#0-6) , so the shop cannot be swapped post-signature. The webhook path has no equivalent protection for the shop/topic/webhook_id fields.

### Impact Explanation
This qualifies as cross-tenant access: since a single app-wide `client_secret` is used to HMAC all webhooks for all merchants that install the app, any HMAC-valid `(body, hmac)` pair the attacker can obtain — e.g., a webhook payload for their own shop where they have installed the app, or any leaked/publicly-observable webhook body+HMAC pair — remains HMAC-valid no matter what `X-Shopify-Shop-Domain`, `X-Shopify-Topic`, or `X-Shopify-Webhook-Id` header value is sent alongside it. An attacker submitting a request directly to the app's webhook endpoint can therefore make the app process attacker-supplied data while attributing it to an arbitrary victim shop (or an arbitrary topic/webhook-id), since `Registry.process` never checks that the signed body was actually the one Shopify generated for that specific shop/topic/id combination.

### Likelihood Explanation
Any external, unprivileged party who can install the target app on any shop (including a free/trial shop they control) can capture a legitimately HMAC-signed webhook body for a chosen topic, then replay that exact body with a forged `shop`, `topic`, or `webhook_id` header directly to the victim app's public webhook endpoint. No access token, `client_secret`, or privileged account is required — only a normal app install and control over the HTTP request sent to the app's own listener.

### Recommendation
Bind the tenant-identifying headers into the signed material, or otherwise cryptographically bind them to the verified payload, before trusting them:
- Include `shop`, `topic`, `webhook_id`, and `api_version` in the data covered by the HMAC (e.g., verify a canonicalized string of headers + body), or
- Require the host application to independently correlate `request.shop` against a shop it has an active session/install record for before dispatching to a handler, and document this as a mandatory step rather than leaving `WebhookMetadata.shop` implicitly trusted.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook (e.g., `orders/create`), capturing the raw body `B` and the valid `X-Shopify-Hmac-Sha256` header `H` that Shopify sent for that event [8](#0-7) .
2. Attacker sends a POST to the victim app's registered webhook route with the exact same body `B` and hmac header `H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and optionally a different `X-Shopify-Topic`/`X-Shopify-Webhook-Id`).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `raw_body` only and succeeds because `B`/`H` are still a valid pair [9](#0-8)  and [10](#0-9) .
4. `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` is built from the forged headers and passed to the app's handler as if Shopify itself had reported this event for `victim-shop.myshopify.com` [11](#0-10) , achieving cross-tenant data/event injection despite a "valid" signature check.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
