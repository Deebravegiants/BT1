### Title
Vault gateway/DON handlers log the full incoming JSON-RPC request — including the bearer JWT/auth token — at Debug level before authorization or redaction - ([File: core/services/gateway/handlers/vault/handler.go], [File: core/capabilities/vault/gw_handler.go])

### Summary
The Nextcloud CVE describes sensitive key material leaking into logs via unredacted exception/error logging. In the Chainlink Vault capability, the internet-facing gateway and DON-side handlers for the Vault secrets API log the *entire* raw inbound `jsonrpc.Request` object — which carries the caller-supplied `Auth` field (the Auth0 JWT bearer token used for authorization) and request `Params` — at Debug level, unconditionally and before the request has been authorized or sanitized.

### Finding Description
In `core/services/gateway/handlers/vault/handler.go`, `HandleJSONRPCUserMessage` logs the complete request object prior to authorization: [1](#0-0) 
This happens before `h.requestProcessor.ProcessRequest` validates/authorizes the caller, so it fires for any inbound request reaching the gateway, authorized or not.

Similarly, `core/capabilities/vault/gw_handler.go`'s `HandleGatewayMessage` (the node-side handler that consumes gateway-forwarded messages) logs the whole request the same way: [2](#0-1) 
and also logs the whole outgoing `response` at **Info** level (not Debug) unconditionally after every request: [3](#0-2) 

The `jsonrpc.Request[json.RawMessage]` struct carries an `Auth` field populated from the caller's `Authorization: Bearer <token>` header (seen being set/stripped throughout the vault test helpers, e.g. `jsonRequest.Auth`, `outboundRequestWithoutAuth`) — this JWT is the credential used by `JWTBasedAuth`/`Authorizer.AuthorizeRequest` to establish caller identity and vault ownership: [4](#0-3) . Logging the full struct via `%v`/structured field serialization means this bearer token ends up verbatim in Debug/Info logs.

Notably, the codebase already shows awareness of a *related* leak vector and partially remediated it: a test explicitly asserts that the "invalid params" error path does **not** log raw params at Info level, but the comment confirms the pre-existing whole-request Debug log is a known, still-present gap: [5](#0-4) 
That test only guards the error/rejection response path — it does not cover (and does not disprove) the initial `Debugw("handling vault request", ..., "request", req)` call at line 403, which still serializes the full request, `Auth` field included, for every incoming message.

### Impact Explanation
Any operator or process with read access to Vault DON node or gateway Debug/Info-level logs (log aggregation systems, log files, support bundles) can recover live JWT bearer tokens for Vault secret operations. Because the JWT's `authorization_details.request_digest` and workflow-owner claims are what the `Authorizer` uses to bind a request to an owner, an exposed token is directly usable to impersonate/replay a caller's Vault secrets requests (create/update/delete/list), consistent with a credential/secret-disclosure class bug analogous to the Nextcloud CVE's key-material logging.

### Likelihood Explanation
Debug-level logging is common to enable for troubleshooting in production DON/gateway deployments, and this log line fires on every single inbound vault request — not just on rare error paths — making exposure likely wherever verbose logging is turned on. The trigger is a completely unprivileged client request to the gateway; no attacker action beyond a normal API call is needed to cause the token to be written to logs.

### Recommendation
Redact or omit the `Auth`/JWT field (and any other bearer credential) before logging the request object in `core/services/gateway/handlers/vault/handler.go:403` and `core/capabilities/vault/gw_handler.go:182`. Apply the same pattern already used for the "invalid params" fix (logging selected safe fields like `method`/`requestID` instead of the full struct), and avoid logging the full `response` object at Info level in `gw_handler.go:231`.

### Proof of Concept
1. Deploy a Vault-enabled gateway/DON node with logger level set to `debug` (a supported, non-default but common operational configuration).
2. As an unprivileged client, send any valid JSON-RPC vault request (e.g. `vault_secretsList`) to the gateway HTTP endpoint with `Authorization: Bearer <jwt>`.
3. Observe the node/gateway log output for the "handling vault request" / "received message from gateway" log lines — the JWT token supplied in `req.Auth` appears verbatim in the log entry.
4. An operator or anyone with log access can extract this token and use it to construct new authorized Vault requests before it expires.

Note: I was not able to view the exact `jsonrpc.Request` struct definition (its `Auth` field type/tag) in this index pass to confirm precisely how it serializes in the logger's structured output; this could not be fully verified due to index coverage limits, and a Devin session with full repo access would be needed to confirm the exact serialized form of the `Auth` field in log output.

func (p *GatewayVaultRequestProcessor) authorizeAndStamp(
	ctx context.Context,
	req *jsonrpc.Request[json.RawMessage],
	stamp func(prefixedRequestID string) error,
) (*AuthorizedGatewayVaultRequest, error) {
	incomingOwner := ""
	if idx := strings.Index(req.ID, vaulttypes.RequestIDSeparator); idx != -1 {
		incomingOwner = req.ID[:idx]
	}

	p.lggr.Debugw("authorizing gateway vault request", "method", req.Method, "requestID", req.ID)
	authResult, err := p.authorizer.AuthorizeRequest(ctx, *req)
	if err != nil {
		authErr := fmt.Errorf("request not authorized: %w", err)
		p.lggr.Errorw("gateway vault request authorization failed", "method", req.Method, "requestID", req.ID, "hasAuth", req.Auth != "", "incomingOwner", incomingOwner, "error", authErr)
		return nil, authErr
	}

func TestVaultHandler_InvalidParamsDoesNotLogRawParams(t *testing.T) {
	t.Parallel()

	// Observed at Info level so the pre-existing whole-request Debug log is excluded.
	lggr, logs := logger.TestObserved(t, zapcore.InfoLevel)
	h, callback, don, _ := setupHandlerWithLogger(t, lggr, limits.Factory{Settings: cresettings.DefaultGetter})
	// Don't expect SendToNode to be called for invalid params
	don.AssertNotCalled(t, "SendToNode")

	const marker = "SENSITIVE_MARKER_123"
	invalidParams := json.RawMessage(`{"request_id":"req-1","injected":"` + marker + `"}`)
	req := jsonrpc.Request[json.RawMessage]{
		ID:     "invalid-params-logs",
		Method: vaulttypes.MethodSecretsCreate,
		Params: &invalidParams,
	}

	// The invalid-params response is sent synchronously, so no goroutine is needed.
	err := h.HandleJSONRPCUserMessage(t.Context(), req, callback)
	require.NoError(t, err)

	resp, err := callback.Wait(t.Context())
	require.NoError(t, err)
	var secretsResponse jsonrpc.Response[vaultcommon.CreateSecretsResponse]
	require.NoError(t, json.Unmarshal(resp.RawResponse, &secretsResponse))
	assert.Equal(t, req.ID, secretsResponse.ID, "Request ID should match")
	assert.Equal(t, api.ToJSONRPCErrorCode(api.InvalidParamsError), secretsResponse.Error.Code, "Error code should match")

	invalidParamsLogs := logs.FilterMessage("invalid params")
	entries := invalidParamsLogs.All()
	require.Len(t, entries, 1, "expected exactly one 'invalid params' log entry")
	assert.Equal(t, zapcore.ErrorLevel, entries[0].Level)
	assert.Equal(t, req.ID, entries[0].ContextMap()["requestID"])
	assert.NotContains(t, entries[0].ContextMap(), "params", "raw params must not be logged")

	for _, e := range logs.All() {
		assert.NotContains(t, e.Message, marker)
		for k, v := range e.ContextMap() {
			if s, ok := v.(string); ok {
				assert.NotContains(t, s, marker, "log field %q must not contain raw request params", k)
			}
		}
	}
}
