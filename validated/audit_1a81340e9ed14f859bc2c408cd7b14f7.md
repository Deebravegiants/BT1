### Title
Webhook `shop` header used for tenant identification is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its signable payload from the raw request body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values are read directly from HTTP headers that are never included in the HMAC computation. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC over the body, then hands the unauthenticated `shop` header straight to the app's webhook handler as the tenant identifier, breaking the intended binding `HMAC-verified(body) == data attributed to shop`.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0)  while `shop`, `topic`, `webhook_id`, and `api_version` are all parsed straight from headers with no cryptographic protection: [2](#0-1) 

`Utils::HmacValidator.validate` only verifies `verifiable_query.hmac` against `verifiable_query.to_signable_string` (i.e., the body) using `Context.api_secret_key`: [3](#0-2) 

`Webhooks::Registry.process` performs this body-only HMAC check and then immediately forwards the **header-derived** `request.shop` to the app's handler as the tenant key, with no additional validation that `shop` was authenticated: [4](#0-3) 

The documented handler contract explicitly tells app authors to trust `data.shop` as "The shop domain of the webhook" for routing/persistence, reinforcing that this field is expected to be trustworthy: [5](#0-4) 

Because the shop identity is carried in a header rather than in the HMAC-covered body, the equality that should hold — *the shop whose secret produced this HMAC* == *the shop the app processes this data for* — is not enforced by the gem. An unprivileged internet user who operates their own shop can receive a legitimately Shopify-signed webhook (valid body + valid HMAC, since Shopify signs with the shared `api_secret_key` for that installed app) and then replay that exact `(body, hmac)` pair to the app's webhook endpoint while substituting the `shop-domain` header (and, if desired, `webhook_id`/`topic`, though topic must match a registered handler) for a victim shop the same app is installed on. `HmacValidator.validate` still passes because only the body is checked, and `Registry.process` calls the handler with `shop: request.shop` set to the attacker-chosen victim domain: [6](#0-5) 

### Impact Explanation
This crosses the tenant boundary the report's bug class describes ("a shop authenticated versus the shop stored as a session key"): the shop value trusted by the handler for data attribution/storage is not the shop that actually authenticated (signed) the payload. Depending on how the host app uses `data.shop` (commonly to look up the shop record and persist/act on `data.body` for that shop), this enables cross-tenant data injection/confusion — an attacker can cause their own webhook payload to be attributed to and processed under a different merchant's shop record in a multi-tenant app.

### Likelihood Explanation
Requires the attacker to control (or have) their own shop installed on the same app to legitimately receive a Shopify-signed webhook body+HMAC, then replay it with a modified `shop-domain` header to the same app's public webhook endpoint. No secrets, tokens, or privileged access to the victim's account are needed — only the ability to trigger a webhook for their own store and knowledge of the target's shop domain (often discoverable). This is directly reachable through the gem's own documented `Registry.process` flow with no additional binding required by the app.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `webhook_id`, `api_version`) headers in the HMAC-signable string, or otherwise independently verify that the authenticated shop matches the one for which the handler is invoked, before passing `request.shop` to `WebhookMetadata`. At minimum, document/require host apps to independently verify shop ownership (e.g., cross-check against known installed shops) rather than trusting the header value.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and triggers a webhook (e.g. `orders/create`), receiving a request from Shopify with body `B` and header `x-shopify-hmac-sha256: H` (a valid HMAC of `B` using the shared `api_secret_key`), plus `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker replays the exact same request to the app's webhook endpoint, changing only the `x-shopify-shop-domain` header to `victim.myshopify.com` (topic/body/HMAC unchanged).
3. `Webhooks::Request.new` parses headers, `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `@raw_body` (`B`) — unchanged — and matches `H`, so validation succeeds: [7](#0-6) 
4. `handler.handle` is invoked with `WebhookMetadata.new(... shop: request.shop ...)` where `request.shop` now returns `"victim.myshopify.com"`, even though the payload/HMAC never came from Shopify on behalf of that shop: [8](#0-7)

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
