### Title
Unbounded `protocolFeeBps` / `destinationFeeBps` governance parameter can permanently brick order placement - ([File: evm/src/apps/IntentGatewayV2.sol])

### Summary
`IntentGatewayV2` stores `protocolFeeBps` and per-destination `destinationFeeBps` as plain `uint256` governance parameters, updatable via a cross-chain `UpdateParams` request, with no on-chain enforcement that the value stays below the 10,000 bps (100%) denominator used in the fee-reduction arithmetic. This mirrors the reported bug class — a reward/fee percentage that is expected to be capped/static but is never actually constrained in the contract that consumes it.

### Finding Description
`placeOrder` computes the escrowed amount by subtracting a fee derived from `protocolFeeBps` (or a destination-specific override) directly from the user's input amount: [1](#0-0) 

The `Params`/`DestinationFee` structs document the intended semantics ("10000 = 100%, 5000 = 50%, etc.") purely as a comment, with no corresponding `require`/bound check anywhere in the setter path: [2](#0-1) 

Governance updates these values cross-chain through the `UpdateParams` request body, decoded from an `Option<U256>` in the coprocessor pallet with no bound validation visible in the type definition: [3](#0-2) 

Only the off-chain SDK enforces `protocolFeeBps < BPS_DENOMINATOR` when *reading* the value for quoting purposes — this is a client-side guard, not an on-chain invariant: [4](#0-3) 

If `protocolFeeBps` (or a `destinationFeeBps` override) is ever configured at or above 10,000 — through a governance mistake, a bad `UpdateParams` payload, or any bug in the coprocessor pallet that produces the update — the on-chain computation:
```solidity
uint256 protocolFee = (originalAmount * protocolFeeBps) / 10_000;
uint256 reducedAmount = originalAmount - protocolFee; // underflow revert in Solidity 0.8
```
underflows and reverts unconditionally (Solidity ^0.8.24 checked arithmetic), for every single order that includes that input token/destination.

### Impact Explanation
Because `placeOrder` is the sole entry point for creating intents on `IntentGatewayV2`, an unbounded fee parameter set at/above 100% permanently disables order placement on that gateway (or for that specific destination), for every user and every token, until governance issues another `UpdateParams` correction — which itself is dependent on the honest operation of the cross-chain coprocessor. This satisfies the "route unable to deliver messages" bar: users can no longer dispatch intents through the affected `IntentGatewayV2` instance, a protocol-wide denial of service with no direct on-chain remedy for already-placed but not-yet-filled state, and no theft, but a full freeze of the order-placement functionality of the affected route.

### Likelihood Explanation
This requires a governance/coprocessor-issued `UpdateParams` value ≥ 10,000 bps, which should not happen under correct configuration, but there is no contract-level safety net if it does — a single malformed governance message, integration bug, or unit mismatch (e.g., mistakenly setting basis points as if they were "percent x100" or similar) reaching the pallet or the `UpdateParams` payload directly weaponizes this. Given the value flows from a privileged but remote/cross-chain-triggered path (`onAccept` handling `UpdateParams`), and no defensive `require(protocolFeeBps <= 10_000)` exists in the Solidity setter, the likelihood is non-trivial for a protocol that relies on this exact invariant elsewhere (the SDK explicitly checks it, indicating the contract itself is expected to enforce it too, but doesn't).

### Recommendation
Add an explicit on-chain bound check (`require(newParams.protocolFeeBps <= 10_000)` and equivalently for each `destinationFeeBps`) in the `UpdateParams` handler / `initialize` function of `IntentGatewayV2`, mirroring the check already present in the SDK's `readProtocolFeeBps`, so a misconfigured governance update reverts at the point of update rather than bricking `placeOrder` for all future users.

### Proof of Concept
1. Governance (or a buggy coprocessor pallet message) dispatches an `UpdateParams` request setting `params.protocolFeeBps = 10_000` (or higher), or a `DestinationFee.destinationFeeBps = 10_000` for a specific chain.
2. `onAccept` applies the update with no bound check, as reflected in the unconstrained `Option<U256>` field in `ParamsUpdate` [5](#0-4) .
3. Any user calling `placeOrder` with an input routed to that destination now hits `uint256 reducedAmount = originalAmount - protocolFee;` where `protocolFee == originalAmount` (or exceeds it), reverting due to Solidity 0.8 checked subtraction underflow in [6](#0-5) .
4. All subsequent order placements against that gateway/destination revert, halting the intents flow until another governance correction lands.
