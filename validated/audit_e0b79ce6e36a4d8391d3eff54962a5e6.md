### Title
`Auth::Oauth.begin_auth`/`validate_auth_callback` accept an unvalidated `shop` and send `client_secret` to it — SSRF/forced-OAuth-completion via unbound `shop` identity - (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
`ShopifyAPI::Auth::Oauth.begin_auth` and `ShopifyAPI::Auth::Oauth.validate_auth_callback` use the caller-supplied `shop` string directly to build the authorize redirect URL and, on callback, to build the base URI to which the app's `client_id`/`client_secret` are POSTed for the access-token exchange — without ever calling `ShopifyAPI::Utils::ShopValidator.sanitize!` to confirm `shop` is a genuine `*.myshopify.com`/trusted Shopify domain. This mirrors the `LockedBalance` bug class: an identity value (`shop`) is trusted/acted upon by a security‑sensitive routine without the routine itself enforcing the invariant (well‑formed Shopify domain) that its safety depends on — exactly the kind of "library should be self‑contained, not rely on external checks" gap flagged in the report.

### Finding Description
- `begin_auth(shop:, redirect_path:, ...)` builds the redirect target directly from `shop` via `auth_base_uri(shop)`, with no domain validation: [1](#0-0) [2](#0-1) 
- `validate_auth_callback` validates the HMAC over the query (`code, host, shop, state, timestamp`) via `Utils::HmacValidator.validate(auth_query)`, but then uses `auth_query.shop` unchecked to construct `null_session` and the `Clients::HttpClient` base path used to POST the app's `client_id`/`client_secret` for the token exchange: [3](#0-2) 
- By contrast, the newer `TokenExchange.migrate_to_expiring_token` explicitly calls `Utils::ShopValidator.sanitize!(shop)` before using `shop` to build the session/HTTP client that receives `client_secret`, establishing that this gem itself considers unvalidated `shop` unsafe for that exact purpose: [4](#0-3) 
- `ShopValidator.sanitize!`/`sanitize_shop_domain` exist precisely to enforce that `shop` resolves to a `TRUSTED_SHOPIFY_DOMAINS` suffix (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`) before it is trusted anywhere sensitive: [5](#0-4) [6](#0-5) 

The identity binding this breaks is: `shop` used to select the OAuth authorize host / access-token exchange host == `shop` proven by the gem to be a genuine Shopify domain. In `oauth.rb` this equality is never enforced; the gem instead relies entirely on the calling application to pre-validate `shop` before calling `begin_auth`/passing it in `AuthQuery` — exactly the "self-contained library" failure pattern in the analog report. The docs even show the canonical caller pattern taking `shop` straight from an unauthenticated header (`request.headers["Shop"]`) with no sanitization step shown: [7](#0-6) 

Consequences of an attacker supplying `shop` = an attacker-controlled host (not a real Shopify shop domain):
1. `begin_auth`: the victim's browser is redirected to `https://<attacker-host>/admin/oauth/authorize?client_id=...&scope=...&redirect_uri=<app>&state=<nonce>` — the attacker's server, not Shopify, receives and controls the "authorization" step, enabling a forced/completed fake-OAuth flow against the victim's browser session (the `state` cookie is set on the app's own domain regardless of `shop`).
2. `validate_auth_callback`: because the HMAC only proves the query was signed with `api_secret_key`/`old_api_secret_key`, and the calling app is responsible for populating `AuthQuery` fields (per docs, straight from `request.parameters`), the `shop`/`host` values that end up HMAC-covered still originate from parameters the app read off the request; if the app follows the documented pattern verbatim without adding its own domain check, `Auth::Oauth.validate_auth_callback` will happily build an `HttpClient` whose base path is `"https://#{auth_query.shop}/admin"` and POST the body containing `client_secret` and the OAuth `code` to that host in the `access_token` request: [8](#0-7) 

### Impact Explanation
If `shop` is attacker-influenced and not constrained to `*.myshopify.com`/trusted domains before being handed to `validate_auth_callback`, the gem will perform an outbound HTTPS POST containing the app's `client_secret` to a host the attacker chose — SSRF with the app's credentials (client_secret exfiltration to an attacker-controlled endpoint), which maps to the report's "Critical: theft/exfiltration of the app's `client_secret`" and "High: SSRF with the app's credentials" categories. Even absent the HMAC forging (which does require the real secret to fully complete a fraudulent callback), `begin_auth`'s unchecked redirect on its own enables forced OAuth completion / session-fixation-style redirection of a victim to an attacker-controlled "Shopify" authorize page, which is explicitly listed as a High-impact analog category.

### Likelihood Explanation
Exploitability depends on the host application passing an unsanitized, request-derived `shop` value into `begin_auth`/`AuthQuery` — which is exactly the pattern the gem's own `docs/usage/oauth.md` shows (`shop = request.headers["Shop"]`), and which is common practice for embedded/non-embedded login controllers. The gem provides `ShopValidator.sanitize!` for this exact purpose and applies it in `token_exchange.rb`/`client_credentials.rb`/`refresh_token.rb`, but conspicuously omits it in `oauth.rb`'s `begin_auth`/`validate_auth_callback`, the two most commonly used and most sensitive entry points (initial redirect and the code-for-token exchange that carries `client_secret`). This inconsistency within the same gem is a strong signal that the omission is a real gap rather than an intentional design choice.

### Recommendation
Call `ShopifyAPI::Utils::ShopValidator.sanitize!(shop)` (or `sanitize_shop_domain`) at the top of `Auth::Oauth.begin_auth` before constructing `auth_base_uri`, and validate `auth_query.shop` in `Auth::Oauth.validate_auth_callback` before constructing `null_session`/`Clients::HttpClient`, so the library enforces the shop-domain invariant itself rather than depending on every calling application to do so — matching the fix already applied in `token_exchange.rb`.

### Proof of Concept
1. A vulnerable host app implements login exactly as shown in `docs/usage/oauth.md`: `shop = request.headers["Shop"]`, then `ShopifyAPI::Auth::Oauth.begin_auth(shop: shop, redirect_path: "/auth/callback")` with no domain check.
2. Attacker sends the victim a link to the app's login route with `Shop: attacker.evil.com` (or an equivalent query param the app maps to `shop`).
3. `begin_auth` computes `auth_route = "https://attacker.evil.com/admin/oauth/authorize?client_id=<real client_id>&scope=<real scope>&redirect_uri=https://victimapp.com/auth/callback&state=<nonce>&grant_options[]="` and the app 307-redirects the victim's browser there.
4. The victim's browser lands on the attacker's server instead of Shopify; the attacker's server can now stage a fake authorization UI, or redirect the victim onward to complete OAuth against the attacker's own real Shopify store while reusing the victim's `state` cookie context, achieving a forced-OAuth-completion / cross-tenant confusion scenario — all made possible because `Auth::Oauth.begin_auth` never validates that `shop` resolves to a real, trusted Shopify domain, as confirmed by the absence of any `ShopValidator` call in `lib/shopify_api/auth/oauth.rb`.

        def begin_auth(shop:, redirect_path:, is_online: true, scope_override: nil)
          scope = if scope_override.nil?
            ShopifyAPI::Context.scope
          elsif scope_override.is_a?(ShopifyAPI::Auth::AuthScopes)
            scope_override
          else
            ShopifyAPI::Auth::AuthScopes.new(scope_override)
          end

          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = SecureRandom.alphanumeric(NONCE_LENGTH)

          cookie = SessionCookie.new(value: state, expires: Time.now + 60)

          query = {
            client_id: ShopifyAPI::Context.api_key,
            scope: scope.to_s,
            redirect_uri: "#{ShopifyAPI::Context.host}#{redirect_path}",
            state: state,
            "grant_options[]": is_online ? "per-user" : "",
          }

          query_string = URI.encode_www_form(query)
          auth_route = auth_base_uri(shop) + "/oauth/authorize?#{query_string}"

          { auth_route: auth_route, cookie: cookie }
        end

        def validate_auth_callback(cookies:, auth_query:)
          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state

          null_session = Auth::Session.new(shop: auth_query.shop)
          body = {
            client_id: Context.api_key,
            client_secret: Context.api_secret_key,
            code: auth_query.code,
            expiring: Context.expiring_offline_access_tokens ? 1 : 0, # Only applicable for offline tokens
          }

          client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
          response = begin
            client.request(
              Clients::HttpRequest.new(
                http_method: :post,
                path: "access_token",
                body: body,
                body_type: "application/json",
              ),
            )
          rescue ShopifyAPI::Errors::HttpResponseError => e
            raise Errors::RequestAccessTokenError,
              "Cannot complete OAuth process. Received a #{e.code} error while requesting access token."
          end

        def auth_base_uri(shop)
          return "https://#{shop}/admin" unless defined?(DevServer) && shop.include?(".my.shop.dev")

          # For first-party apps in development only, we leverage DevServer to build the admin base URI
          admin_web = T.unsafe(Object.const_get("DevServer")) # rubocop:disable Sorbet/ConstantsFromStrings
            .new("admin-web")
          admin_host = admin_web.host!(nonstandard_host_prefix: "admin")
          shop_name = shop.split(".").first

          "https://#{admin_host}/store/#{shop_name}"
        end

class ShopifyAuthController < ApplicationController
  def login
    shop = request.headers["Shop"]

    # Builds the authorization URL route to redirect the user to
    auth_response = ShopifyAPI::Auth::Oauth.begin_auth(shop: domain, redirect_path: "/auth/callback")

    # Store the authorization cookie
    cookies[auth_response[:cookie].name] = {
      expires: auth_response[:cookie].expires,
      secure: true,
      http_only: true,
      value: auth_response[:cookie].value
    }

    # Redirect the user to "auth_response[:auth_route]" to allow user to grant the app permission
    # This will lead the user to the Shopify Authorization page
    head 307
    response.set_header("Location", auth_response[:auth_route])
  end
end
