### Title
Webhook `shop-domain` header is trusted without being covered by the HMAC signature, allowing tenant confusion in `ShopifyAPI::Webhooks::Request` - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then trusts the unauthenticated `X-Shopify-Shop-Domain` header as the tenant identifier passed to the app's handler. Because the app's `api_secret_key` is shared across every shop that installs the app, any merchant who can trigger a legitimately-signed webhook for their own store can replay the same body/HMAC pair while substituting an arbitrary `shop-domain` header, causing the app to process the payload as if it belonged to a victim shop.

### Finding Description
`Utils::HmacValidator.validate` computes and compares the HMAC only over `to_signable_string`, which for a webhook request is defined as the raw body alone: [1](#0-0) 

The `shop` accessor is read directly from the `shopify-shop-domain` / `x-shopify-shop-domain` header and is never included in the signed bytes: [2](#0-1) 

`Registry.process` validates the HMAC, then immediately forwards `request.shop` — the unauthenticated header value — to the registered handler as the tenant identifier: [3](#0-2) 

The `HmacValidator` itself only checks `verifiable_query.hmac` against `verifiable_query.to_signable_string`; it has no knowledge of, or binding to, any header outside that signable string: [4](#0-3) 

**Equality that is broken:** the gem implicitly assumes
`HMAC_valid(secret, raw_body) == true` implies `shop_header == tenant_that_generated(raw_body)`.
In reality, `HMAC_valid(secret, raw_body)` only proves the *body* was produced using the app's shared `api_secret_key` — it says nothing about which shop the header claims to be. Since `api_secret_key` is the same for all shops that install the app, an unprivileged merchant (an "attacker" who is legitimately installed with their own shop, e.g. `attacker.myshopify.com`) can:
1. Trigger any webhook topic on their own store to receive a validly-HMAC'd `(raw_body, hmac)` pair from Shopify.
2. Replay that exact `(raw_body, hmac)` to the app's webhook endpoint, but override the `X-Shopify-Shop-Domain` header to `victim.myshopify.com`.
3. `HmacValidator.validate` still succeeds, because the signature only covers `raw_body`, which is unchanged.
4. `Registry.process` calls the handler with `WebhookMetadata.new(... shop: "victim.myshopify.com" ...)`, so the handler's business logic (typically keyed on `shop` to look up sessions, update per-tenant records, credit orders, etc., as documented for `shopify_app`'s webhook processing) operates on attacker-controlled body content while believing it belongs to the victim tenant.

### Impact Explanation
This breaks the tenant/shop identity boundary the app relies on when dispatching webhook payloads: the gem authenticates the byte stream but hands out an unauthenticated tenant label alongside it. Any downstream application code that trusts `WebhookMetadata#shop` (the documented, intended usage) can be made to write, update, or act on data under a victim shop's identity using attacker-supplied body content — i.e. cross-tenant access/data corruption, achievable by any unprivileged app-installer without needing the app's `client_secret`, an access token, or any elevated privilege.

### Likelihood Explanation
Any merchant who installs the app can generate valid webhook deliveries for their own store on demand (create an order, update a product, etc.), giving them an arbitrary number of validly-signed `(body, hmac)` pairs. Forging the `shop-domain` header on the replayed HTTP request requires no cryptographic material — it is a plain, unauthenticated header. The only prerequisite is that the target app's webhook endpoint is reachable from the internet, which is inherent to how Shopify webhooks are received.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook-id`) values into the authenticated material, or otherwise cryptographically tie the header claims to the payload:
- Have `Webhooks::Request#to_signable_string` include the shop domain (and topic) alongside the raw body when computing/verifying the signature, or
- Require callers/handlers to independently verify that `shop` matches an expected/known session shop before trusting body contents for that shop, and document this requirement prominently since the header is not authenticated by `HmacValidator`.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` (a normal, unprivileged installation).
2. Attacker triggers a webhook (e.g., `orders/create`) on their own store; Shopify posts to the app's webhook endpoint with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
3. Attacker intercepts/replays this same request to the endpoint but changes `X-Shopify-Shop-Domain` from `attacker.myshopify.com` to `victim.myshopify.com`, keeping `B` and `H` identical.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC-SHA256(api_secret_key, B)` and finds it equals `H` — validation passes (`lib/shopify_api/webhooks/registry.rb:190`, `lib/shopify_api/utils/hmac_validator.rb:13-22`).
5. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and attacker-controlled body `B`, processing it as though it were a genuine event from the victim's store (`lib/shopify_api/webhooks/registry.rb:198-199`).

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
