### Title
`cancelOrder()` permanently locks native ETH sent for same-chain order cancellations - ([File: evm/src/apps/IntentGatewayV2.sol])

### Summary
`IntentGatewayV2.cancelOrder()` is marked `payable` and forwards `msg.value` to the cross-chain cancellation paths, but the same-chain cancellation path (`_cancelSameChain`) never consumes, checks, or refunds `msg.value`. Any native token sent by a caller cancelling a same-chain order is silently absorbed into the contract's balance with no mechanism for the sender to reclaim it.

### Finding Description
`cancelOrder()` is declared `payable` because two of its three routing branches genuinely need `msg.value`: `_cancelFromSource` optionally uses it to pay Hyperbridge's native dispatch fee for the GET request, and `_cancelFromDest` forwards it entirely as `msg.value` to `_post(...)` for the `RefundEscrow` message dispatch fee. [1](#0-0) 

However, when `isSameChain` is true, `cancelOrder` calls `_cancelSameChain(order, commitment)` — a function that only computes remaining escrow balances and calls `_withdraw`, with no reference to `msg.value` anywhere in its body: [2](#0-1) 

Because the same-chain branch neither reverts on non-zero `msg.value` nor forwards/refunds it, any ETH attached to a same-chain `cancelOrder()` call is added to the contract's ETH balance via the implicit `receive()` and left there. `IntentGatewayV2` does define a `receive()` for accepting escrow deposits and swept balances, so the ETH transfer itself succeeds silently: [3](#0-2) 

Unlike `_fillSameChain`/`_fillCrossChain`/`placeOrder`, which explicitly track `msgValue` and refund any unspent remainder to `msg.sender` at the end of execution, there is no analogous refund logic in `_cancelSameChain` or in `cancelOrder`'s same-chain dispatch: [4](#0-3) [5](#0-4) 

The only path by which native ETH can leave the gateway to an arbitrary recipient outside of order fulfillment is `SweepDust`, which is gated to be dispatched only by Hyperbridge itself, not by the depositor: [6](#0-5) 

so the caller who mistakenly (or due to wallet/UI defaults inherited from `fillOrder`/`placeOrder` usage patterns, which do require `msg.value`) attaches ETH to a same-chain `cancelOrder()` has no way to recover it.

### Impact Explanation
This is a permanent freezing of user funds: any native ETH attached to a same-chain `cancelOrder()` transaction becomes irretrievably stuck in the `IntentGatewayV2` contract. Given that `fillOrder()` and `placeOrder()` on the same interface legitimately require `msg.value` for native-token legs, users/integrators calling `cancelOrder()` (e.g., from the same UI/SDK flow, or scripts that reuse a `{value: ...}` pattern) are realistically exposed to this mistake. There is no recovery mechanism reachable by the depositor.

### Likelihood Explanation
Likelihood is moderate: it requires user/integrator error (attaching `msg.value` to a call that doesn't need it), similar to the original Putty finding. However, because `cancelOrder` shares the same payable ABI signature pattern as `fillOrder`/`placeOrder` in the same contract, and SDKs/relayers driving cancellations may compute a `value` field generically across all three entry points, accidental submission of non-zero `msg.value` on a same-chain cancel is plausible in practice.

### Recommendation
Add an explicit guard in the same-chain cancellation path, e.g. in `cancelOrder()` before calling `_cancelSameChain`:
```solidity
if (isSameChain) {
    if (currentChain != orderSource) revert WrongChain();
    if (msg.value != 0) revert UnexpectedNativeToken();
    _cancelSameChain(order, commitment);
}
```
Alternatively, refund any `msg.value` to `msg.sender` at the end of `_cancelSameChain`, consistent with the refund pattern already used in `_fillSameChain`, `_fillCrossChain`, and `placeOrder`.

### Proof of Concept
1. User places a same-chain order via `placeOrder()` (ERC20 inputs, no native leg).
2. Order goes unfilled past `order.deadline`.
3. User (or a relayer script generically passing `value: someAmount`) calls:
   ```solidity
   intentGateway.cancelOrder{value: 1 ether}(order, options);
   ```
4. Because `orderSource == orderDest` (`isSameChain == true`), execution routes to `_cancelSameChain(order, commitment)`, which only manipulates `_orders[commitment][token]` escrow bookkeeping and calls `_withdraw` — never touching `msg.value`.
5. The 1 ETH is accepted by the contract's `receive()` and added to `address(intentGateway).balance`, with no code path returning it to the caller and no user-accessible sweep function to recover it. It is permanently locked, exactly analogous to the `fillOrder()`/`exercise()` locked-Ether pattern from the referenced report.

```text
    function _cancelSameChain(Order calldata order, bytes32 commitment) internal {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

        uint256 inputsLen = order.inputs.length;
        TokenInfo[] memory remainingTokens = new TokenInfo[](inputsLen);
        bool hasEscrow = false;
        for (uint256 i; i < inputsLen;) {
            address token = address(uint160(uint256(order.inputs[i].token)));
            uint256 escrowed = _orders[commitment][token];
            if (escrowed > 0) hasEscrow = true;
            remainingTokens[i] = TokenInfo({token: order.inputs[i].token, amount: escrowed});
            unchecked {
                ++i;
            }
        }
        if (!hasEscrow) revert UnknownOrder();

        WithdrawalRequest memory body =
            WithdrawalRequest({commitment: commitment, tokens: remainingTokens, beneficiary: order.user});

        _withdraw(body, true, true);
    }
```
