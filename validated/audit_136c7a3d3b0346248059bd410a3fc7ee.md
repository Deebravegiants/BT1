### Title
Nullifier Recording Skipped When `onChainCreation[i]` Is True, Enabling Double-Spend of Shielded Notes - (File: `contracts/HinkalBase.sol`)

### Summary
`HinkalBase.insertNullifiers` unconditionally aborts recording of an entire token-index row of `inputNullifiers` whenever the corresponding `onChainCreation[i]` flag is `true`, instead of only skipping when that row's nullifiers are actually empty/placeholder. This mirrors the reported class of bug (a boundary/flag-driven skip of an essential validation, analogous to trusting "pre-checkpoint" data without enforcing the invariant that should always hold): here, the flag that is meant to describe "is this token's *output* created on-chain" is also (mis-)used to gate whether *input* nullifiers get persisted, breaking the nullifier-uniqueness invariant.

### Finding Description
In `Hinkal.transact`, nullifiers are recorded via: [1](#0-0) 

which calls: [2](#0-1) 

The loop iterates over token index `i` (matching `circomData.erc20TokenAddresses` ordering, per `formBasicInput` in `CircomDataBuilder.sol`) and, for each `i`, breaks out of the *entire inner loop* the moment `onChainCreation[i] == true` — before ever checking whether `inputNullifiers[i][j]` is nonzero. This means that for any token index flagged `onChainCreation[i] = true`, none of that row's nullifiers are checked against the `nullifiers` mapping nor marked as spent, regardless of whether they encode real, nonzero nullifiers for genuinely-spent shielded notes.

The `onChainCreation` flag's documented/expected purpose is purely about the *output* side of the balance equation — it tells the balance check in `Hinkal.sol` to treat the off-chain `amountChanges[i]` contribution as zero and instead expect the value to appear as an on-chain UTXO commitment: [3](#0-2) 

Nothing in `Hinkal.sol`, `HinkalBase.sol`, or `CircomDataBuilder.sol` prevents a prover from simultaneously setting `onChainCreation[i] = true` for a token index while also supplying a nonzero, valid `inputNullifiers[i][j]` that spends a real note. The public-input vector construction in `formBasicInput` includes `inputNullifiers` unconditionally (independent of `onChainCreation`): [4](#0-3) 

so the ZK proof itself will validate a real spend of a note under `rootHashHinkal`, producing a legitimate nullifier as a public signal — but the on-chain contract never persists it because of the `onChainCreation[i]` short-circuit in `insertNullifiers`. This breaks the intended equality "every nullifier accepted by a valid proof is permanently marked spent," the direct analog of the "untrusted epoch" report's failure to enforce that finality-relevant signatures always come from a properly validated set.

### Impact Explanation
This is a Critical finding: a spent shielded note's nullifier is never recorded when its token index has `onChainCreation[i] = true`, so the exact same proof/`circomData` (or a newly generated proof using the same note secret) can be resubmitted to `transact()` — as long as `circomData.rootHashHinkal` is still an accepted historical root via `rootHashExists`: [5](#0-4) 

— to spend the same shielded value repeatedly. This is a direct double-spend / unbacked-value-creation vulnerability against the shielded pool's balance invariant, matching the "nullifier reusable" category explicitly called out as in-scope Critical impact.

### Likelihood Explanation
The precondition is only that the prover controls `onChainCreation` and `inputNullifiers` as ordinary calldata fields of an unprivileged `transact()` call — no admin, relayer, or oracle role is required. The only requirement is that the circuit accept a valid proof with `onChainCreation[i] = true` for a token index that also carries a genuine, nonzero input nullifier; nothing in the reviewed Solidity layer rejects this combination. I was not able to fully trace `MainEVMCircuit.circom`'s constraints (out of iterations) to confirm whether the circuit itself forbids pairing a nonzero `inputNullifiers[i][j]` with `onChainCreation[i]=true` for the same index — this is the main residual uncertainty. If the circuit does not couple these two signals, the exploit is straightforwardly reachable by a normal user.

### Recommendation
In `insertNullifiers`, do not gate nullifier persistence on `onChainCreation[i]`. Nullifier consumption/checking should always execute for every nonzero entry in `inputNullifiers[i][j]`, independent of whether the corresponding output for that token is created on-chain or off-chain. If `onChainCreation` is only ever supposed to correlate with empty nullifier rows, that invariant should be enforced explicitly on-chain (e.g., `require(inputNullifiers[i][j] == 0)` when `onChainCreation[i]` is true) rather than implicitly assumed via loop short-circuiting.

### Proof of Concept
1. Attacker owns a real shielded UTXO with nullifier `N` for token `T`, included in the Merkle tree with a valid historical root `R`.
2. Attacker (or a colluding "puppet" flow analogous to Alice in the report) crafts a valid ZK proof spending that UTXO, producing public signals including `inputNullifiers = [[N]]`, `rootHashHinkal = R`, and sets `circomData.onChainCreation = [true]` for token `T`'s index alongside an external action that produces an on-chain UTXO of equivalent value (satisfying the balance equation in `Hinkal.sol` lines 137-146).
3. Calls `Hinkal.transact(...)`. Proof verifies; balance equation holds; `insertNullifiers` is invoked but immediately `break`s on `onChainCreation[0] == true` without ever checking/marking `N`: [6](#0-5) 
4. Attacker resubmits the identical (or a freshly generated) proof for the same note/nullifier `N` in a second `transact()` call. Because `nullifiers[N]` was never set to `true`, the call succeeds again, extracting the value of the same shielded note a second time — a double-spend.

```text
    function insertNullifiers(
        uint256[][] calldata inputNullifiers,
        bool[] calldata onChainCreation
    ) internal {
        for (uint256 i = 0; i < inputNullifiers.length; i++) {
            for (uint256 j = 0; j < inputNullifiers[i].length; j++) {
                if (onChainCreation[i] == true) break;
                if (inputNullifiers[i][j] != 0) {
                    require(
                        !nullifiers[inputNullifiers[i][j]],
                        "Nullifier cannot be reused"
                    );
                    nullifiers[inputNullifiers[i][j]] = true;
                    emit Nullified(inputNullifiers[i][j]);
                }
            }
        }
    }
```
