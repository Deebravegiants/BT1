### Title
Webhook `shop` identity not covered by HMAC allows cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#shop` is derived from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, but the HMAC signature validated by `ShopifyAPI::Utils::HmacValidator.validate` in `ShopifyAPI::Webhooks::Registry.process` only covers `@raw_body` (`to_signable_string`), not this header. `Registry.process` passes the unauthenticated `request.shop` straight into `WebhookMetadata`, which host applications use to identify the tenant the webhook belongs to.

### Finding Description
The equality that should hold is: `shop asserted to the handler == shop cryptographically bound to the signed payload`. Instead:

- `Request#hmac` reads `shopify-hmac-sha256` header and `Request#shop` reads `shopify-shop-domain` header, both attacker-controllable inputs to any code path that constructs a `Request` from raw HTTP input. [4](#0-3) 
- `Request#to_signable_string` returns only `@raw_body`, excluding all headers (including `shop-domain`) from what is verified by HMAC. [5](#0-4) 
- `HmacValidator.validate` computes the signature strictly over `verifiable_query.to_signable_string`, so it never validates the `shop` header. [6](#0-5) 
- `Registry.process` gates only on this body-only HMAC check, then forwards `request.shop` unchanged into `WebhookMetadata`, which is the struct host applications use to route/attribute webhook data per-tenant. [2](#0-1) [3](#0-2) 

Because `api_secret_key` is required to forge a valid HMAC of the raw body, an unrelated internet user without any app credentials cannot exploit this. However, an unprivileged merchant who has legitimately installed the app on their own store can obtain a genuinely-signed webhook payload for their store (any topic whose JSON body doesn't itself embed/bind the shop, e.g. `app/uninstalled`, `shop/update`, GDPR topics with minimal PII, or any custom topic), then replay that exact raw body and valid HMAC to the app's public webhook endpoint while substituting an arbitrary victim `x-shopify-shop-domain` value. `Registry.process` still validates because the HMAC only covers the untouched raw body; the forged `shop` header passes straight through into `WebhookMetadata.shop`, so the host application's handler processes the attacker's payload as if it originated from the victim tenant.

### Impact Explanation
This breaks the cross-tenant boundary the gem is expected to enforce for host applications consuming `WebhookMetadata`: the `shop` field, which apps use to key per-tenant data/side effects (e.g., mark an install as uninstalled, update per-shop settings, trigger customer/shop redaction flows), can be attributed to any shop domain chosen by the attacker rather than the shop that actually owns the signed payload. This satisfies the Critical criterion of cross-tenant access, since the gem provides no mechanism (nor guidance) binding the identity field consumed by `WebhookMetadata` to the cryptographic proof of authenticity.

### Likelihood Explanation
Any merchant with the app installed on their own store can trivially capture a legitimately-delivered webhook (raw body + HMAC header) for a low-sensitivity topic and replay it with a forged shop-domain header to the same public webhook endpoint. No access to `api_secret_key`, tokens, or victim infrastructure is required — only the gem's documented `Registry.process` verification path, which never re-validates the shop identity against the signature.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the value that is HMAC-verified, or otherwise cryptographically bind `Request#shop` to the signed payload before it is exposed via `WebhookMetadata`. At minimum, the gem should document that `WebhookMetadata#shop` is not authenticated by the HMAC and host applications must independently verify the shop against a known/registered tenant before trusting it.

### Proof of Concept
```ruby
# 1. Attacker legitimately installs the app on their own store "attacker.myshopify.com"
#    and captures a real webhook delivery, e.g. for topic "app/uninstalled":
raw_body = '{}'  # topic bodies that don't embed the shop domain
valid_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), api_secret_key, raw_body)

# 2. Attacker replays the exact same raw_body/hmac to the app's public webhook
#    endpoint, but swaps the shop-domain header to the victim's shop:
headers = {
  "x-shopify-topic" => "app/uninstalled",
  "x-shopify-hmac-sha256" => Base64.encode64(valid_hmac),
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged, not covered by HMAC
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# HmacValidator.validate(request) succeeds (it only checks raw_body),
# and the handler receives WebhookMetadata(shop: "victim-shop.myshopify.com", ...)
# even though the payload never originated from that shop.
