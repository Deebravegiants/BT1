### Title
Accrual-time Ray value overflow freezes a whale market permanently — borrow-index cap never engages - (File: common/src/rates/scaling.rs)

### Summary
The iperf advisory is a malformed-input assertion failure that kills the process. The on-chain analog in XOXNO Lending is a reachable arithmetic assertion during interest accrual: `scaled_to_original` (`Ray::mul` of scaled debt by `borrow_index`) panics with `MathOverflow` when `borrowed × borrow_index` exceeds `i128::MAX`. Because `global_sync` runs before every market mutation and `borrow_index` is monotone non-decreasing, once the product crosses the ceiling the market is permanently bricked — supply, withdraw, borrow, repay, liquidate, `clean_bad_debt`, `recapitalize`, and `claim_revenue` all revert on the same panic. The `MAX_BORROW_INDEX_RAY` cap exists precisely to bound index growth but is checked too late: the value product overflows before the index cap can engage.

### Finding Description
Every market mutation in the pool loads the `Cache` and calls `interest::global_sync`, which chunks elapsed time and calls `accrue_chunk` → `accrue_step` [1](#0-0) . The accrual rescales `borrowed` and `supplied` (stored as raw `i128` RAY shares) by their indexes via `scaled_to_original`, which is `scaled.mul(env, index)` — a checked multiply that panics on overflow [2](#0-1) . The scaled book can legitimately reach ~`1e36` (a billion whole 18-decimal tokens); `i128::MAX` is only ~170× that, so once `borrow_index` grows past ~170× — which the steep segment of the XLM rate curve reaches within a few years at ~98% utilization — the multiply overflows inside accrual, before the borrow-index cap is ever consulted.

The freeze is permanent rather than a transient revert: `borrow_index` "only ever grows" [3](#0-2) , so no sequence of calls can return the product below `i128::MAX`, and every remediation path (`repay`, `clean_bad_debt`, `recapitalize`) accrues first and hits the identical panic. The harness test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` pins exactly this: `update_indexes` fails with `MATH_OVERFLOW` while `borrow_index < MAX_BORROW_INDEX_RAY`, and subsequent `withdraw`/`repay` fail identically [4](#0-3) .

### Impact Explanation
Permanent freezing of all funds in the affected market: every supplier's deposit and every borrower's collateral exit is blocked, liquidations cannot run, bad debt cannot be cleaned or recapitalized, and accrued revenue cannot be claimed — all because a single checked multiply panics inside the mandatory accrual prelude. An unprivileged attacker creates the entire precondition with ordinary `supply` and `borrow` calls (whale-sized supply plus ~98% utilization borrowing against their own collateral), after which time itself triggers the cliff via the permissionless `update_indexes`.

### Likelihood Explanation
Medium: it requires a high-decimals market with caps large enough for a ~`i128::MAX/170` scaled book and sustained near-max utilization, i.e., real capital rather than a free trigger, and the index needs time on the steep rate segment to reach ~170×. But nothing privileged is involved, utilization is driven by permissionless borrow demand, and once the state is crossed there is no recovery path — the index cap designed to bound growth is unreachable because the value product saturates first.

### Recommendation
Cap `borrow_index` growth by value headroom, not just by `MAX_BORROW_INDEX_RAY`: inside `accrue_chunk`/`accrue_step`, clamp the step so `borrowed × borrow_index` and `supplied × supply_index` stay below `i128::MAX` (e.g., halt index growth at `min(cap, i128::MAX / borrowed)`), matching the documented intent that the index cap protects accrual. Alternatively, store books in a wider internal type or scale per-market so the value ceiling cannot precede the index cap on any listable decimal/cap combination. Add a regression test asserting the cap engages before the overflow on the steepest configured curve.

### Proof of Concept
Existing test demonstrates the freeze end-to-end: `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:320-361` — `supply_raw(BOB, BIG18, 1e9·1e18)`, borrow 98% of it, advance time in yearly `update_indexes` steps until `MATH_OVERFLOW`, then confirm `borrow_index < MAX_BORROW_INDEX_RAY` and that `withdraw`/`repay` revert with the same error [5](#0-4) . Root cause chain: `global_sync` → `accrue_chunk` → `accrue_step` [1](#0-0)  → `scaled_to_original` checked multiply [2](#0-1) .

Caveat I could not fully verify within the search budget: the exact location where `MAX_BORROW_INDEX_RAY` is enforced relative to the overflowing multiply (in `common::rates::accrue_step`); the test confirms empirically that the cap does not engage first, but the precise line ordering in `accrue_step` was not read.

```rust
pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}

/// Applies one compound step of `delta_ms` to indexes and protocol revenue.
///
/// The arithmetic lives in [`accrue_step`], shared with the read-only
/// `simulate_update_indexes` so the view and the mutator cannot drift.
fn accrue_chunk(env: &Env, cache: &mut Cache, delta_ms: u64) {
    let step = accrue_step(
        env,
        cache.params(),
        cache.borrowed(),
        cache.supplied(),
        cache.borrow_index(),
        cache.supply_index(),
        delta_ms,
    );

    cache.set_borrow_index(step.borrow_index);
    cache.set_supply_index(step.supply_index);
    cache.accrue_revenue(step.revenue_shares);
}
```

```rust
/// The cliff. A billion whole tokens is `1e36` raw ray; the value ceiling is
/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
```
