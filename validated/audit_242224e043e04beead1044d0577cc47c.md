### Title
Verbose backend error messages leaked to unauthenticated clients during external-initiator and session authentication - ([File: core/web/auth/auth.go])

### Summary
`AuthenticateExternalInitiator` and `AuthenticateByToken`/`AuthenticateBySession` (via `Authenticate`) propagate raw internal/datastore error strings back to an unauthenticated caller when the auth backend lookup fails for a reason other than "not found", and these raw errors are serialized directly into the HTTP response body.

### Finding Description
`AuthenticateExternalInitiator` in `core/web/auth/auth.go` calls `store.FindExternalInitiator(ctx, eia)`. If the returned error is `sql.ErrNoRows` it is mapped to the generic `auth.ErrorAuthFailed`, but for any other error it is instead wrapped and returned verbatim: `return errors.Wrap(err, "finding external initiator")` [1](#0-0) . The same pattern exists in `AuthenticateByToken`, which returns the raw `err` from `authr.FindUserByAPIToken` unless it matches `sql.ErrNoRows` or `ErrUserSessionExpired` [2](#0-1) , and in `AuthenticateBySession`, which returns the raw error from `authr.AuthorizedUserWithSession` unconditionally [3](#0-2) .

These unwrapped errors then reach `Authenticate`, which on any non-`ErrorAuthFailed` error calls `jsonAPIError(c, http.StatusUnauthorized, err)` [4](#0-3) . `jsonAPIError` serializes `err.Error()` directly into the JSON response sent to the client: `c.JSON(statusCode, models.NewJSONAPIErrorsWith(err.Error()))` [5](#0-4) .

Because the underlying authentication providers issue raw SQL/database calls (e.g. `o.ds.GetContext(ctx, &user, sql, apiToken)` in `FindUserByAPIToken` [6](#0-5) , and `l.ds.GetContext(ctx, exi, ...)` in `FindExternalInitiator` [7](#0-6) ), any database-layer failure that is not exactly `sql.ErrNoRows` (e.g. connection failures, timeouts, driver-level errors, malformed query errors) is surfaced verbatim, unauthenticated, to the requester's HTTP response. This mirrors the CVE-2016-9839 pattern of an OGR data-connection error being too verbose and leaking backend details on connection failure — here, a DB/connection-layer error is returned as-is to an unauthenticated actor attempting API-token, external-initiator, or session authentication.

### Impact Explanation
An unauthenticated network client probing the `/v2/...` API with garbage or crafted `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret`, `X-API-KEY`/`X-API-SECRET` headers, or a malformed session cookie can trigger backend datastore errors (e.g. by sending malformed/oversized tokens that cause query or driver errors) and receive the raw error text back in the 401 response body. This can leak internal implementation details such as database driver messages, which aids further attacks (information disclosure, fingerprinting internal infrastructure), consistent with the "High" severity information-disclosure class of the reference CVE. It does not by itself grant authentication bypass or fund movement, so impact is limited to information disclosure.

### Likelihood Explanation
Likelihood is moderate: triggering a genuine backend/database error (rather than a simple "no rows" miss) from unauthenticated input requires a fault condition in the datastore layer (e.g. a transient connection issue, timeout, or query-level fault caused by unusual header input), which is not trivially reproducible on demand by a remote attacker under normal healthy operation, but is realistic during database load, network partitions, or crafted malformed input that causes driver-level errors.

### Recommendation
Do not return raw underlying errors from `AuthenticateExternalInitiator`, `AuthenticateByToken`, and `AuthenticateBySession` to the HTTP layer. Map any non-`ErrorAuthFailed`/`sql.ErrNoRows` error to a generic authentication failure response (or a generic 500 with no message body), while logging the detailed error server-side only, mirroring the fix pattern used for MapServer's OGR driver (generic external-facing error, detailed internal log).

### Proof of Concept
1. Send a request to any external-initiator-protected endpoint with `X-Chainlink-EA-AccessKey` and `X-Chainlink-EA-Secret` headers while the datastore returns a non-`sql.ErrNoRows` error (e.g. simulate a DB connectivity fault or malformed token causing a driver error).
2. Observe that `AuthenticateExternalInitiator` returns `errors.Wrap(err, "finding external initiator")` [8](#0-7)  instead of the generic `auth.ErrorAuthFailed`.
3. `Authenticate` forwards this error to `jsonAPIError`, which serializes `err.Error()` into the JSON body of the 401 response [5](#0-4) , exposing the underlying datastore error text to the unauthenticated caller.

```go
func jsonAPIError(c *gin.Context, statusCode int, err error) {
	_ = c.Error(err).SetType(gin.ErrorTypePublic)
	var jsonErr *models.JSONAPIErrors
	if errors.As(err, &jsonErr) {
		c.JSON(statusCode, jsonErr)
		return
	}
	c.JSON(statusCode, models.NewJSONAPIErrorsWith(err.Error()))
}
```
