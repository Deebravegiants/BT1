### Title
Webhook `shop` identity is not bound by the HMAC signature, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` verifies webhook authenticity by HMAC-signing only the raw request body, while the tenant-identifying `shop` value (taken from the `X-Shopify-Shop-Domain` header) is never included in the signed content. Any party who can obtain one validly-signed webhook delivery for their own store can replay the same body+signature against the app's webhook endpoint while substituting an arbitrary victim shop domain in the header, and the library will accept it as authentic and hand it to the app's handler under the victim's identity.

### Finding Description
`Request#to_signable_string` returns only the raw body: [1](#0-0) 

`Request#shop` is read directly from an unauthenticated header, independent of the signed payload: [2](#0-1) 

`Registry.process` validates the HMAC over exactly that signable string (the body) and, once it passes, dispatches the handler with `request.shop` as the trusted tenant identifier, without any cross-check that the signature is bound to that shop value: [3](#0-2) 

`HmacValidator.validate` simply recomputes the HMAC of `verifiable_query.to_signable_string` (the body) using the app's single, shop-independent `api_secret_key` and compares it to the received signature: [4](#0-3) 

Because the same `api_secret_key` is used to validate webhooks for *every* shop that has installed the app, a signature computed for a webhook delivered to the attacker's own shop is equally valid when replayed with a different `shop-domain` header value — the signature carries no binding to which shop it was issued for. The identity-binding equality that should hold is `shop_used_by_handler == shop_covered_by_signature`; here the right-hand side doesn't exist at all, since `shop` is entirely outside the signed bytes.

The library's own documentation confirms that `data.shop` is meant to be trusted as the tenant identifier by host applications, and that `Registry.process` "will verify the request did indeed come from Shopify": [5](#0-4) [6](#0-5) 

This is a documented, intended usage pattern of the gem's own API, not host-application misuse: the doc explicitly shows `data.shop` being forwarded as the tenant/shop scope (`shop_domain: data.shop`) for downstream processing.

### Impact Explanation
This is a cross-tenant access vulnerability. An unprivileged attacker who has installed the target app on their own (attacker-controlled) shop can obtain a legitimately-signed webhook (body + `X-Shopify-Hmac-Sha256`) by triggering any subscribed event (e.g. `orders/create`) in their own store. They can then submit that exact body/signature to the app's public webhook endpoint while forging the `X-Shopify-Shop-Domain` header to name a victim shop. `ShopifyAPI::Webhooks::Registry.process` will accept it as authentic (the HMAC check only covers the body) and invoke the app's handler with `WebhookMetadata#shop` set to the victim's domain, causing the host application to process/store attacker-supplied data under the victim tenant's scope — exactly the "cross-tenant access" category called out as Critical impact.

### Likelihood Explanation
High. No special privileges beyond a normal app install on any shop (including the attacker's own store, which they fully control) are required, and no access token, `api_secret_key`, or victim credential is needed. The attacker only needs to capture one legitimate webhook delivery from their own installation and can replay it indefinitely with different shop headers, since the HMAC is shop-independent and body content for many topics does not vary the signature outcome the app cares about (e.g. record IDs may collide/be attacker-chosen in their own store).

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook-id`) values into the signed content that `HmacValidator` verifies, or otherwise cryptographically tie the header-derived `shop` to the verified signature (e.g., verify that the signature was computed specifically for the shop being processed, mirroring how `AuthQuery#to_signable_string` includes `shop` in its signed parameters). At minimum, document prominently that `request.shop` is unauthenticated and must not be trusted as a tenant boundary without additional verification (e.g., cross-referencing against the shop associated with a known webhook subscription/session).

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com`.
2. Attacker triggers a subscribed webhook event (e.g., creates an order) in their own store, and captures the raw POST body and `X-Shopify-Hmac-Sha256` header sent by Shopify to the app's webhook endpoint.
3. Attacker resends this exact `raw_body` + `X-Shopify-Hmac-Sha256` to the same app endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `raw_body` only and matches — validation succeeds.
5. The registered handler is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", body: <attacker's own order data>, ...)`, and the host app (per documented usage) processes/stores this payload as belonging to the victim shop.

          received_signature = verifiable_query.hmac

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
