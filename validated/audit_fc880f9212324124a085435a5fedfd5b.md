Based on the analogous bug class (missing EIP‑2 style low‑S / malleability rejection on ECDSA recovery used for authorization-critical counting), I found a concrete match in the Substrate‑side BEEFY consensus verifier.

### Title
BEEFY vote signatures are not checked for low‑S canonical form, allowing a single authority's vote to be counted twice toward the supermajority threshold - (File: modules/consensus/beefy/verifier/src/lib.rs)

### Summary
The BEEFY light‑client consensus verifier recovers the signer of every submitted vote signature with `H::secp256k1_recover`, which is backed by `sp_io::crypto::secp256k1_ecdsa_recover` [1](#0-0) [2](#0-1) . Unlike Homestead‑era Ethereum transaction validation (the analog from the report), this recovery path performs no restriction on `s` to the lower half of the curve order — any `s` in `[1, n-1]` is accepted, so for every valid vote signature `(r, s, v)` an attacker can compute a second, equally valid signature `(r, n-s, 1-v)` for the exact same authority and commitment **without knowing the private key**.

### Finding Description
`verify_mmr_update_proof` counts `signatures_length = mmr.signed_commitment.signatures.len()` and checks it against the supermajority threshold before recovering any signer: [3](#0-2) . It then loops over every submitted signature, recovers the address with the malleability‑unaware `secp256k1_recover`, and pushes an `(authority_index, authority_leaf)` pair into the arrays used for the merkle multi‑proof check — with no deduplication on `authority_index` or on the recovered address: [4](#0-3) . Because the signature is never validated for canonical (low‑S) form, an attacker who observes even a single genuine BEEFY vote (these are gossiped before finality) can synthesize its malleable twin for the same `authority_index` and submit it as an extra, distinct-looking "signature" in the proof. This inflates `signatures_length`/the participation count used by `check_participation_threshold` without requiring any additional honest validator's private key.

### Impact Explanation
If the merkle multi-proof verification does not itself reject duplicate `authority_index` entries, this lets a minority of colluding/leaked signers reach the 2/3+1 supermajority threshold by having each of their signatures counted twice, causing the consensus client to accept a forged or premature MMR/authority-set update — i.e., an unsound state commitment for the whole light client, which is the trust root Hyperbridge relies on for cross-chain proof verification (`modules/ismp/clients/beefy`, `modules/pallets/beefy-consensus-proofs`). This is a High severity issue matching the reachable-path categories (consensus verification, BEEFY) explicitly in scope.

### Likelihood Explanation
Exploitation only requires observing one legitimate BEEFY vote signature (public, gossiped data) per authority the attacker wants to "double count," and computing `n - s` is a purely arithmetic, keyless operation. No cryptographic secret or privileged access is needed, only that the merkle multi-proof step accepts a duplicated `authority_index`/leaf pair, which the reviewed code does nothing to prevent.

### Recommendation
Reject BEEFY vote signatures whose `s` value exceeds `secp256k1n/2` (mirroring EIP‑2/Homestead) inside `EcdsaRecover::secp256k1_recover` or immediately after recovery in `verify_mmr_update_proof`, and additionally enforce that `authority_index` values in a single proof are unique before counting them toward `signatures_length` / the supermajority threshold.

### Proof of Concept
1. Observe a valid BEEFY vote `(r, s, v)` from authority `i` over `commitment_hash`.
2. Compute the malleated signature `(r, n-s, 1-v)` — still recovers to the same authority `i`.
3. Submit a `MmrProof` containing both `(r,s,v)` and `(r,n-s,1-v)` tagged with the same `authority_index = i`, alongside genuinely-collected signatures from fewer than 2/3+1 authorities.
4. If the merkle multi-proof accepts the duplicate index/leaf, `signatures_length` reported to `check_participation_threshold` exceeds the true number of participating authorities, and the forged commitment is accepted as a new trusted state via `verify_mmr_update_proof`. [4](#0-3) 

**Caveat:** I could not directly confirm within the available context whether the underlying `MerkleProof`/multi-proof verification (`rs_merkle`) rejects duplicate leaf indices — this is the remaining condition needed for the double-counting to succeed in practice, and should be verified against that library's behavior before treating this as fully confirmed. Separately, the EVM-side `EcdsaBeefy.sol` uses OpenZeppelin's `ECDSA.recover` [5](#0-4) , which (in OZ ≥4.7.3) already rejects high-S signatures, so this specific analog does not apply to the Solidity light client — only to the Substrate/Rust `beefy-verifier` path.
