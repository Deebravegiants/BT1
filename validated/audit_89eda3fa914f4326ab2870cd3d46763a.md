### Title
Chainlink price feeds in `SimplexPaymaster` are not checked against the aggregator's `minAnswer`/`maxAnswer` circuit-breaker bounds - (File: `evm/src/utils/SimplexPaymaster.sol`)

### Summary
`SimplexPaymaster._getOraclePrice` only rejects a non-positive or stale Chainlink answer, but never checks that the returned answer is strictly inside the aggregator's `minAnswer`/`maxAnswer` bounds. This is the exact bug class from the external report: during a circuit-breaker event (extreme price crash/spike), Chainlink continues to return the clamped bound value instead of reverting or signalling the true market price, and downstream consumers that don't check for this keep operating on stale/incorrect pricing.

### Finding Description
`_getOraclePrice` fetches `latestRoundData()` and validates only positivity and staleness: [1](#0-0) 

There is no comparison of `answer` against the feed's configured `minAnswer`/`maxAnswer` (obtainable from the underlying `AggregatorV3` proxy's `aggregator()` and `minAnswer()/maxAnswer()`), so when the underlying asset's real price moves beyond the feed's configured band, the price stays "fresh" (recent `updatedAt`) and positive, yet is clamped to the bound and no longer reflects the market price. This price feeds directly into `_tokenPrice`, which computes the ERC-20/native exchange rate used to charge UserOperation senders for gas: [2](#0-1) 

`_tokenPrice` is invoked from `_fetchDetails` (called by the ERC-4337 `EntryPoint` during every UserOperation's paymaster validation) and from `swapAndDeposit` (which uses the same clamped price to size `amountOutMin` for a Uniswap swap of accrued token fees into native): [3](#0-2) [4](#0-3) 

Any account submitting a UserOperation through this paymaster (an unprivileged "bandwidth purchaser" paying for gas in an ERC-20 token) is a direct, permissionless trigger path for `_getOraclePrice`/`_tokenPrice`. No governance or privileged action is required to reach the vulnerable code — every gas-paying UserOp recomputes the price from the live Chainlink feed.

### Impact Explanation
If either the native/USD feed (`nativeOracle`) or a registered token/USD feed hits its aggregator bound during a market dislocation (e.g. a de-peg or crash), `_getOraclePrice` will keep returning the clamped `minAnswer`/`maxAnswer` value as if it were current and valid, because it passes both the `answer > 0` and staleness checks. Consequences:
- Users can be systematically overcharged or undercharged in the ERC-20 token relative to actual gas cost, transferring value between UserOp senders and the paymaster's treasury.
- `swapAndDeposit`'s `amountOutMin` is derived from the same clamped price, so the treasury-gated swap can execute at a manipulated/incorrect rate, mis-valuing the swap and depleting the paymaster's native reserve used to fund the EntryPoint deposit that backs future gas sponsorship.
This is a concrete-fund-impact path (mispriced token transfers and swap execution against a false price), directly reachable by ordinary UserOp senders without any admin/governance involvement.

### Likelihood Explanation
The trigger condition is an external market event (extreme price movement causing a Chainlink feed to hit its circuit-breaker bound) rather than an on-chain exploit primitive, so likelihood is tied to market conditions for the specific token/native asset pairs configured via `RegisterToken`/`UpdateParams`. It is a known, recurring failure mode for Chainlink feeds (e.g., LUNA collapse) and requires no special privilege or contract interaction complexity to exploit once the condition occurs — any UserOp sender using the affected token automatically transacts at the incorrect clamped price.

### Recommendation
In `_getOraclePrice`, after reading `latestRoundData()`, fetch the underlying aggregator's `minAnswer`/`maxAnswer` (via the feed's `aggregator()` accessor plus `minAnswer()`/`maxAnswer()` on the underlying `AccessControlledOffchainAggregator`) and revert if `answer <= minAnswer || answer >= maxAnswer`, mirroring the recommendation in the source report. Alternatively, allow governance to configure explicit sane bounds per token/native oracle via `RegisterToken`/`UpdateParams` and enforce them in `_getOraclePrice`.

### Proof of Concept
1. Governance registers a token whose Chainlink token/USD feed has `minAnswer = X`.
2. The real market price of the token collapses below `X` (e.g., a de-peg event).
3. The Chainlink aggregator continues returning `answer = X` with a fresh `updatedAt` (per Chainlink's circuit-breaker behavior).
4. `_getOraclePrice` (evm/src/utils/SimplexPaymaster.sol:662-676) accepts this answer since it is `> 0` and not stale.
5. `_tokenPrice`/`_fetchDetails` compute gas cost in the token using the stale `X` instead of the real, much lower price, overcharging every UserOp sender that pays gas in that token until governance intervenes via `DeactivateToken`/`RegisterToken`.

    /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
