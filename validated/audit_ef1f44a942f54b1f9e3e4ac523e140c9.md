Based on the exploration, the strongest candidate identity-binding break in the in-scope library code is in the webhook request handling path.

### Title
Webhook shop identity is trusted from an unauthenticated header not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` exposes a `shop` accessor that is read directly from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, but the HMAC validation performed by `ShopifyAPI::Utils::HmacValidator` only covers the raw request body, never the shop-domain header. [1](#0-0) [2](#0-1) 

### Finding Description
`Registry.process` verifies only that the HMAC is valid over the raw body, then immediately builds `WebhookMetadata` using `request.shop`, which is taken verbatim from the (attacker-controllable) `shop-domain` header — not from any value bound by the signature. [3](#0-2) 

The identity binding that should hold is: `shop asserted to the handler == shop cryptographically bound by the HMAC`. In this implementation, the HMAC only proves `bytes_verified(raw_body) == bytes_signed(raw_body)`; it says nothing about which shop the body belongs to. Because all shops installed on a given app share the same `client_secret`/`api_secret_key`, an unprivileged holder of one legitimate installation (their own dev/test store) can capture a genuinely-signed webhook (valid HMAC over a body they control) and replay it against the app's webhook endpoint while swapping the `x-shopify-shop-domain` header to name a victim shop. The HMAC still validates (it never covered the header), and the handler receives `data.shop` = victim shop with attacker-controlled `data.body`.

### Impact Explanation
This breaks the tenant boundary the HMAC is supposed to enforce for webhook delivery: a webhook is meant to be non-forgeable proof that "shop X experienced event Y." Here, only "some shop experienced event Y" is proven; "shop X" is unauthenticated. Any host application that uses `data.shop` to look up per-tenant secrets, sync state, or perform actions scoped to that shop (the intended and documented use, per `docs/usage/webhooks.md`) can be made to act on a victim shop's identity using attacker-supplied body content, i.e., cross-tenant confusion driven entirely through this gem's own `Request`/`Registry` code paths, with no credentials belonging to the victim required.

### Likelihood Explanation
Requires only that the attacker be a legitimate, unprivileged merchant/installer of the app (or otherwise able to trigger one authentic webhook delivery to themselves) and be able to send an HTTP POST to the app's public webhook endpoint — both trivially available to any unprivileged internet user who installs a public app on their own store.

### Recommendation
Bind the shop identity into the material that is verified, or independently authenticate it: either include the shop domain in the HMAC-signed payload construction used by `HmacValidator`/`VerifiableQuery`, or require host applications to cross-check `request.shop` against a shop that is already known/installed (e.g., matching a stored session/shop record) before trusting it — and document/enforce this in `Registry.process` rather than leaving it to unverified header trust.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`, receiving genuine webhooks signed with the app's shared `client_secret`.
2. Attacker captures one such webhook: body `B`, header `x-shopify-hmac-sha256: HMAC(secret, B)`, header `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker resends the same request to the app's webhook endpoint, changing only `x-shopify-shop-domain` to `victim.myshopify.com`.
4. `Utils::HmacValidator.validate` succeeds (it only checks `B` against the HMAC) [4](#0-3) ; `Registry.process` calls the handler with `data.shop == "victim.myshopify.com"` and attacker-chosen `data.body` [3](#0-2) .

**Caveat / uncertainty:** This mirrors Shopify's actual documented webhook signing scheme (HMAC over body only; shop domain intentionally not covered), so it may be considered inherent platform behavior rather than a defect unique to this gem — I could not confirm whether Shopify's own security model expects apps to separately validate `shop-domain` against a known-installed-shops list as a mandatory step. I was also unable to fully inspect `lib/shopify_api/auth/session.rb` and `lib/shopify_api/utils/session_utils.rb` in this pass (tool errors prevented reading them) to rule out a stronger, more clearly in-gem-scope analog such as a session-id or JWT-derived binding issue.
