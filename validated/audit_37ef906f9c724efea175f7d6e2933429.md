### Title
Direct token transfers to the liquidity pool permanently freeze unbooked assets - (File: contracts/pool/src/lib.rs)

### Summary
Severity: Medium

An unprivileged user can transfer a listed token directly to the pool contract. The transfer increases the token balance but does not increase any market's tracked `cash`, create supply shares, or create revenue. The pool exposes no sweep or rescue entrypoint, so the donated amount remains permanently locked.

### Finding Description
The pool treats `cash` as accounting state separate from its actual token balance: `credit_cash`, `debit_cash`, and `transfer_out` mutate independent books and custody legs [1](#0-0) . A direct `token.transfer(user, pool, amount)` bypasses all controller paths that measure receipts and credit either shares or cash.

The money-flow test confirms this state: after transferring `7 * UNIT` directly to the pool, physical custody equals both markets' cash plus the unassigned donation [2](#0-1) .

The apparent recovery path does not help. `Controller::recapitalize` first pulls a new payment from the payer and passes only the measured new receipt to the pool [3](#0-2) . The pool applies only `min(amount, backing_shortfall)` and refunds the remainder; it does not inspect or consume a previously donated balance [4](#0-3) . Thus a payer receives back only the newly transferred excess, while the earlier donation remains unbooked.

Every outbound pool operation is owner-only and tied to a specific accounting claim: withdrawals consume supply shares, borrows consume cash, revenue claims consume revenue shares, and refunds consume only the amount declared for that operation [5](#0-4) . The `LiquidityPoolInterface` has no rescue, sweep, or arbitrary withdrawal function [6](#0-5) .

### Impact Explanation
Any token amount sent directly to the pool instead of through `Controller::supply`, `repay`, or `recapitalize` is permanently frozen. Because the donation is not represented by supply shares, debt, revenue, or cash, neither the sender nor protocol governance can recover it through the public call flow.

### Likelihood Explanation
The attack/deposit path is a plain token transfer and requires no privilege. The primary likelihood driver is user or integration error—sending funds to the custody pool rather than invoking the controller. Once made, the freeze is deterministic.

### Recommendation
Add a bounded rescue path for unbooked surplus. For each token, the pool should calculate:

```text
rescueable = token.balance(pool) - sum(tracked cash for every market using this token)
```

and expose an owner-only `sweep_excess(asset, recipient)` callable through a corresponding governance-controlled controller entrypoint. The sweep must aggregate cash across all hub markets sharing the same physical token and must never withdraw booked reserves.

### Proof of Concept
1. Query the pool address with `Controller::get_pool_address`.
2. As an unprivileged user, execute:

```rust
token::Client::new(&env, &listed_asset).transfer(&user, &pool, &amount);
```

3. Observe that `token.balance(pool)` increases by `amount`, while `Pool::get_reserves(hub_asset)` does not.
4. Call `Controller::recapitalize(user, hub_asset, amount)` on a fully backed market. The controller pulls another `amount`; the pool returns that new amount because `backing_shortfall == 0`. The original donation remains locked.
5. No public or owner ABI can transfer the residual surplus: `withdraw`, `borrow`, `claim_revenue`, `repay`, and `recapitalize` all operate only on accounted claims or newly measured input.

    /// Increases accounting cash by `amount`. Rejects negative amounts and overflow.
    pub(crate) fn credit_cash(&mut self, amount: i128) {
        require_nonneg_amount(&self.env, amount);
        self.cash = self
            .cash
            .checked_add(amount)
            .unwrap_or_else(|| panic_with_error!(&self.env, GenericError::MathOverflow));
    }

    /// Decreases accounting cash by `amount`. Rejects negative amounts or
    /// insufficient reserves.
    pub(crate) fn debit_cash(&mut self, amount: i128) {
        require_nonneg_amount(&self.env, amount);
        self.require_reserves(amount);
        self.cash = self
            .cash
            .checked_sub(amount)
            .unwrap_or_else(|| panic_with_error!(&self.env, GenericError::MathOverflow));
    }

    /// Transfers `amount` of the market asset from the pool to `recipient`.

pub(crate) fn accounting(
    env: &Env,
    hub_asset: HubAssetKey,
    amount: i128,
) -> RecapitalizationOutcome {
    require_nonneg_amount(env, amount);
    let mut cache = ops::renewed_market(env, &hub_asset);

    let applied = amount.min(guards::backing_shortfall(&cache));
    let refund = amount
        .checked_sub(applied)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow));

    cache.credit_cash(applied);
    cache.commit();
