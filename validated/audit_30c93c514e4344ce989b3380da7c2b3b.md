### Title
Removing a state machine from `HostParams.stateMachines` does not revoke it — stale trust in a de-whitelisted state machine persists indefinitely - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.updateHostParamsInternal` treats `_hostParams.stateMachines` as an append-only whitelist: when governance pushes a new `HostParams` list, the code only *initializes* entries that are new, but never resets or clears `_latestStateMachineHeight` for state machines that are dropped from the list. Because `_latestStateMachineHeight[id] != 0` is the sole "is this chain supported" signal used elsewhere in the protocol, and neither `HandlerV2.handlePostRequests`/`handleGetResponses` nor `dispatchIncoming` re-check current whitelist membership at delivery time, a state machine that governance has removed from the trusted set keeps being fully functional: new consensus-verified commitments for it keep getting stored, and previously stored commitments for it are never purged, so requests/responses proven against them keep being delivered by any relayer.

### Finding Description
`updateHostParamsInternal` only adds missing entries to `_latestStateMachineHeight`, never removes stale ones for state machines that were dropped from `params.stateMachines`: [1](#0-0) 

The getter's own documentation states the intended semantics — `0` means unsupported: [2](#0-1) 

But `HandlerV2.handleConsensus` uses exactly this stale, never-reset value as the gate for whether to keep accepting and persisting new state commitments for a state machine: [3](#0-2) 

Even setting that aside, `handlePostRequests` and `handleGetResponses` never consult `_hostParams.stateMachines` (or `latestStateMachineHeight`) at all when accepting a proof — they only check that a stored `stateMachineCommitment(height).overlayRoot` is non-zero and that the merkle proof verifies against it: [4](#0-3) 

So the whitelist check that exists only at the moment new state machines are *added* (`updateHostParamsInternal`'s init loop) is never re-enforced, either when new consensus updates arrive for a state machine already known to `_latestStateMachineHeight`, or when relayers deliver requests/responses proven against previously stored commitments. This is the same failure pattern as the Rancher advisory: an authorization change (auth-provider disabled / users removed from the authorized list ≈ a state machine removed from `HostParams.stateMachines`) is recorded, but the previously granted trust (session tokens ≈ `_latestStateMachineHeight`/`_stateCommitments` for that chain) is never revoked, so access continues indefinitely.

### Impact Explanation
If governance removes a state machine from the whitelist — for example because its consensus is compromised, deprecated, or was mistakenly added — the host does not actually stop trusting it. A relayer (unprivileged, permissionless by design in this system) can still:
1. Submit consensus proofs whose intermediate states target the "removed" state machine id, and `handleConsensus` will still store new `StateCommitment`s for it because `latestStateMachineHeight != 0` was never cleared.
2. Submit `handlePostRequests`/`handleGetResponses` proofs against any commitment (old or newly injected) for that id, since delivery never checks current whitelist membership at all.

This allows forged/unsound message delivery from a state machine the protocol operators believed they had cut off, directly enabling theft of funds via forged cross-chain messages (e.g., token mint/intent fill messages) that should no longer be trusted.

### Likelihood Explanation
This requires no special privilege beyond being a relayer, which is explicitly permissionless in this design (`handle_unsigned`/`handlePostRequests` accept any caller with a valid proof). The only precondition is that governance has, at some point, removed a state machine from `HostParams.stateMachines` (a normal, expected governance operation, e.g., in response to a compromise) while the underlying consensus client can still be made to (or already did) produce commitments for that id.

### Recommendation
When applying `HostParams` updates, diff the new `stateMachines` list against the old one and explicitly clear/zero `_latestStateMachineHeight` (and ideally purge or mark inert any stored `_stateCommitments`) for entries that are no longer present. Additionally, `handlePostRequests`/`handleGetResponses`/`handleConsensus` should check current whitelist membership (`_hostParams.stateMachines` or equivalently a live `latestStateMachineHeight != 0` check performed against the current whitelist, not stale state) before trusting any commitment for a given state machine id.

### Proof of Concept
1. Governance calls `updateHostParams` with `stateMachines = [A, B]`; both get `_latestStateMachineHeight` initialized to `1`.
2. A relayer submits consensus/state proofs, causing `_latestStateMachineHeight[A]` to advance and commitments to be stored for `A`.
3. Governance discovers `A`'s consensus is compromised and calls `updateHostParams` again with `stateMachines = [B]` only, intending to revoke trust in `A`. `updateHostParamsInternal`'s loop (lines 638-644) does nothing for `A` since it iterates only over the new list.
4. `_latestStateMachineHeight[A]` remains non-zero and previously stored `_stateCommitments[A][...]` remain intact.
5. Any relayer can still call `HandlerV2.handlePostRequests`/`handleGetResponses` with proofs against `A`'s stored commitments, and the host delivers them — despite `A` no longer being part of `HostParams.stateMachines`. A relayer can also submit a new consensus proof containing an intermediate state for `A`, which `handleConsensus` will happily store because `latestHeight != 0`.

    function handlePostRequests(IHost host, PostRequestMessage calldata request) external notFrozen(host) {
        uint256 timestamp = block.timestamp;
        uint256 delay = timestamp - host.stateMachineCommitmentUpdateTime(request.proof.height);
        uint256 challengePeriod = host.challengePeriod();
        if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();

        uint256 requestsLen = request.requests.length;
        MerkleMountainRange.Leaf[] memory leaves = new MerkleMountainRange.Leaf[](requestsLen);

        for (uint256 i = 0; i < requestsLen; ++i) {
            PostRequestLeaf memory leaf = request.requests[i];
            // check destination
            if (!leaf.request.dest.equals(host.host())) revert InvalidMessageDestination();
            // check time-out
            if (timestamp >= leaf.request.timeout()) revert MessageTimedOut();
            leaves[i] = MerkleMountainRange.Leaf(leaf.index, leaf.request.hash());
        }

        bytes32 root = host.stateMachineCommitment(request.proof.height).overlayRoot;
        if (root == bytes32(0)) revert StateCommitmentNotFound();
        bool valid = MerkleMountainRange.VerifyProof(root, request.proof.multiproof, leaves, request.proof.leafCount);
        if (!valid) revert InvalidProof();

        for (uint256 i = 0; i < requestsLen; ++i) {
            PostRequestLeaf memory leaf = request.requests[i];
            // duplicate request?
            if (host.requestReceipts(leaf.request.hash()) != address(0)) revert DuplicateMessage();
            host.dispatchIncoming(leaf.request, _msgSender());
        }
    }
