### Title
Webhook shop-domain header is trusted for tenant identification but is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` attribute solely from the `X-Shopify-Shop-Domain` HTTP header, but `HmacValidator` only verifies the raw request body against the app's `client_secret`-derived HMAC. The `shop-domain` header is never included in the signed material, so it can be freely altered by anyone who can reach the webhook endpoint with a body/HMAC pair that validates.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

and `Request#shop` is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header, independent of the signed payload: [2](#0-1) 

`HmacValidator.validate` computes the signature purely from `to_signable_string` (i.e., the raw body) and the app's secret: [3](#0-2) 

`Registry.process` accepts any request whose HMAC (over the body) validates, then forwards `request.shop` straight to the handler as the tenant identity, with no separate check that the header matches the shop that actually produced/signed the body: [4](#0-3) 

This breaks the intended binding: **`shop` header used to attribute the webhook == shop whose data was actually HMAC-signed by Shopify**. Since the app's HMAC secret (`client_secret`) is the same for every shop that installs the app, a request with a given raw body and its correct signature remains valid for that body regardless of which `shop-domain` header accompanies it. An attacker who controls or can replay a raw body/HMAC pair (e.g., their own store's legitimately-received webhook, or any topic where they can influence/observe the body content) can swap the `X-Shopify-Shop-Domain` header to any victim shop domain string and have `Registry.process` treat the payload as belonging to that victim tenant, since nothing in this gem cross-checks the header against the signed content or against any known/expected shop list.

### Impact Explanation
This is a cross-tenant identity-binding failure: the gem exposes `request.shop` as an unauthenticated field to the host application's webhook handler while implying (via `HmacValidator.validate` passing) that the entire request, including its shop attribution, is authentic. Any app that uses `WebhookMetadata#shop`/`request.shop` to select which merchant's session/data record to act on (a common and reasonable pattern, since that's the field this gem exposes for that exact purpose) can be made to write, delete, or process data under the wrong tenant, or to trigger tenant-specific side effects (e.g. app-installed/uninstalled handling, order processing) attributed to a shop that never actually sent that webhook. This matches the "cross-tenant access" Critical impact category, since it is a caller-forgeable field acted upon downstream but excluded from the HMAC.

### Likelihood Explanation
Reaching the webhook endpoint requires no privileged credentials — it is an unauthenticated internet-facing endpoint by design (Shopify calls it over plain HTTP with only the HMAC as proof of authenticity). Producing a valid `(raw_body, hmac)` pair does not require the `client_secret`: an attacker can capture a legitimate webhook delivery to their own shop (which they fully control, since they can install the app on a store they own) and simply replay it with a modified `shop-domain` header. No secret material is needed to perform the header substitution itself.

### Recommendation
Include the shop domain (and preferably `webhook-id`/`api-version`) in the value that is HMAC-verified, or otherwise cryptographically bind the header to the signed body (e.g., verify the header against a shop known to be associated with the specific installation/session before trusting it). At minimum, document explicitly that `request.shop` is unauthenticated and must be cross-validated by the host application against a known, previously-established shop/session record before being used for any tenant-scoped action.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and receives a legitimate webhook, e.g. body `{"id":1}` with header `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>` and `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Attacker resends the exact same body and HMAC header to the app's webhook endpoint, but changes `X-Shopify-Shop-Domain` to `victim.myshopify.com`.
3. `HmacValidator.validate` recomputes the HMAC over `@raw_body` only (unchanged), so it matches and the request is accepted: [5](#0-4) 
4. `Registry.process` invokes the handler with `shop: request.shop`, which now returns `"victim.myshopify.com"`: [6](#0-5) 
5. The host application's handler processes the (attacker-supplied) body as if it were authentic data for `victim.myshopify.com`, achieving cross-tenant data injection/confusion.
