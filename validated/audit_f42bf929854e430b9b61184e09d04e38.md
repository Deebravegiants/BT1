### Title
`usdk::transfer_from` uses the owner's account sequence number as an approval nonce, which is never consumed by the transfer, allowing unbounded replay of a single signed approval to drain the owner's balance - ([File: aptos-move/move-examples/fungible_asset/stablecoin/sources/usdk.move])

### Summary
`usdk::transfer_from` [1](#0-0)  is the Aptos analog of Solidity's `transferFrom`/`safeTransferFrom` allowance pattern flagged in the external report: a `spender` presents a signature from `from` authorizing a transfer, and the module moves funds out of `from`'s primary store on `from`'s behalf. The `Approval` message's replay-protection field (`nonce`) is bound to `account::get_sequence_number(from)` [2](#0-1) , but that sequence number is only incremented when `from` submits its own on-chain transaction — never as a side effect of `transfer_from` being called by `spender`. This mirrors the root cause in the external report: authority to move a victim's tokens is asserted once (an "approval"), but the enforcement path allows that authority to be exercised more times than the victim intended.

### Finding Description
In `transfer_from`, the `nonce` used to prevent replay of the approval message is `account::get_sequence_number(from)`: [3](#0-2) 

`account::get_sequence_number` reads `from`'s on-chain sequence number, which is a property of `from`'s *own* transactions (incremented by `transaction_validation::check_for_replay_protection_regular_txn` only when `from` is the signer of a validated transaction) [4](#0-3) . Calling `usdk::transfer_from` is a transaction signed by `spender`, not by `from`, so it never touches `from`'s sequence number. Consequently, a single `Approval` signature that `from` produces off-chain (e.g., "let spender move X to Y") remains valid and re-usable in `transfer_from` for as many times as `spender` chooses to submit it, as long as `from` does not happen to submit any transaction of their own (which would only accidentally bump the nonce, not because of any consumption logic in the stablecoin contract itself).

This breaks the custody invariant that an owner's authorization to move funds should be scoped to a single use (or to an amount actually approved once) — the same underlying issue as `safeTransferFrom` being called against a "residual/looser than intended" authorization in the Sherlock report, except here the authorization can be replayed an unbounded number of times rather than merely reused up to a stale allowance.

### Impact Explanation
Any spender who ever obtains one valid `Approval` signature from a victim (e.g., for a single legitimate payment) can call `transfer_from` repeatedly with the exact same `proof`, draining `from`'s USDK balance in `amount`-sized increments each time, until the store is exhausted or `from` submits any transaction (bumping the sequence number and invalidating the nonce). Because ordinary users may go long periods without submitting transactions themselves, this is a practical, high-impact fund-theft vector: it moves value out of the victim's custody without additional authorization, directly matching the Custody Impact Gate's "theft ... of ... fungible assets" and "supply or custody accounting corruption that moves value to the wrong holder" criteria.

### Likelihood Explanation
Likelihood is high once an attacker/spender is ever given a legitimately signed `Approval` for a nonzero amount: the exploit requires no privileged access — merely resubmitting the previously-obtained `proof` bytes via `transfer_from` again. No additional signature, key compromise, or governance access is needed. The only mitigating factor is that any transaction sent by `from` in the interim invalidates the nonce, but this is incidental, not a designed protection in `usdk.move`.

### Recommendation
- Do not derive replay protection from the account's global transaction sequence number, which the stablecoin contract does not control. Instead, maintain a dedicated on-chain "used approval" or a per-`(from, spender)` monotonically-increasing nonce/allowance counter inside `usdk`'s own resources (e.g., a `Table<address, u64>` mapping `from` to its own approval-nonce), and increment it every time `transfer_from` successfully consumes an approval.
- Alternatively/bind the approval to a one-time, single-use hash (mark it consumed in a `Table<vector<u8>, bool>`) so the exact same `proof` cannot be replayed regardless of `from`'s activity.
- Consider also binding an expiration timestamp to the `Approval` struct to bound the exposure window.

### Proof of Concept
1. `owner` (victim) signs one `Approval { owner: owner_addr, to: attacker_addr, nonce: account::get_sequence_number(owner_addr), chain_id, spender: attacker_addr, amount: N }` intending to authorize a single transfer of `N` USDK to `attacker`.
2. `owner` never submits any of their own transactions afterward.
3. `attacker` calls `usdk::transfer_from(attacker, proof, owner_addr, scheme, pubkey, attacker_addr, N)` — this succeeds and moves `N` tokens.
4. `attacker` calls `usdk::transfer_from` again with the identical `proof`/parameters. Because `account::get_sequence_number(owner_addr)` is unchanged (the previous call did not increment it), `expected_message` is bytewise identical to the first call, `account::verify_signed_message` succeeds again, and another `N` tokens are moved.
5. Repeat until `owner`'s balance is exhausted or `owner` finally submits a transaction of their own (incidentally bumping the sequence number and breaking replay only at that point).

Note: this finding is limited to the move-examples `stablecoin`/`usdk` sample contract in this repo; I could not verify whether an equivalent pattern is deployed as a real mainnet module outside of the examples directory, and did not have time in this session to check whether other in-repo consumers of this pattern exist (e.g. other `move-examples` contracts using `account::verify_signed_message` with `get_sequence_number` as a nonce). If `usdk.move` is purely illustrative and not deployed as a live custody-holding contract, the mainnet-relevance would need separate confirmation.

    fun check_for_replay_protection_regular_txn(
        sender_address: address,
        gas_payer_address: address,
        txn_sequence_number: u64,
    ) {
        if (
            sender_address == gas_payer_address
                || account::exists_at(sender_address)
                || !features::sponsored_automatic_account_creation_enabled()
                || txn_sequence_number > 0
        ) {
            assert!(account::exists_at(sender_address), error::invalid_argument(PROLOGUE_EACCOUNT_DOES_NOT_EXIST));
            let account_sequence_number = account::get_sequence_number(sender_address);
            assert!(
                txn_sequence_number < (1u64 << 63),
                error::out_of_range(PROLOGUE_ESEQUENCE_NUMBER_TOO_BIG)
            );

            assert!(
                txn_sequence_number >= account_sequence_number,
                error::invalid_argument(PROLOGUE_ESEQUENCE_NUMBER_TOO_OLD)
            );

            assert!(
                txn_sequence_number == account_sequence_number,
                error::invalid_argument(PROLOGUE_ESEQUENCE_NUMBER_TOO_NEW)
            );
        } else {
            // In this case, the transaction is sponsored and the account does not exist, so ensure
            // the default values match.
            assert!(
                txn_sequence_number == 0,
                error::invalid_argument(PROLOGUE_ESEQUENCE_NUMBER_TOO_NEW)
            );
        };
    }
