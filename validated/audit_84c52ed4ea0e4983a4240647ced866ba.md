### Title
Missing re-initialization guard in `LockupContract::new` allows takeover of an already-deployed lockup contract - (File: `lockup/src/lib.rs`)

### Summary
`LockupContract::new` (the `#[init]` constructor) validates `owner_account_id`, `staking_pool_whitelist_account_id`, `transfer_poll_account_id`, and `foundation_account_id`, but never checks `assert!(!env::state_exists(), "Already initialized")` before overwriting contract state [1](#0-0) . This is analogous to the external report's root cause (missing checks in an `init` function letting the contract be reinitialized and ownership be seized), except here the concrete missing check is the state-exists / already-initialized guard rather than a zero-address check (NEAR account model has no zero address for AccountId).

### Finding Description
Every other production contract in this repo that defines an `#[init]` constructor explicitly guards against being called a second time:
- `voting/src/lib.rs:36` — `assert!(!env::state_exists(), "The contract is already initialized")`
- `whitelist/src/lib.rs:34` — `assert!(!env::state_exists(), "Already initialized")`
- `staking-pool/src/lib.rs:179` — `assert!(!env::state_exists(), "Already initialized")`
- `multisig/src/lib.rs:104` — `assert!(!env::state_exists(), "Already initialized")`
- `multisig2/src/lib.rs:117` — uses `#[derive(..., PanicOnDefault)]`, which produces the equivalent guard automatically.

`lockup/src/lib.rs`'s `LockupContract::new` (lines 181-243) has no such assertion [2](#0-1) . Because near-sdk's `#[init]` macro (in the versions used here, `near-sdk = "3.1.0"` for lockup, matching `2.0.0` for the others that still needed the explicit check) does not automatically prevent re-invocation of an already-initialized contract's `#[init]` method, the guard must be added manually — as it was everywhere else except in the lockup contract.

Since a keyless NEAR contract account can be called by any predecessor account via a `FunctionCall` action regardless of whether the caller holds a key on the target account, any unprivileged account can send a transaction invoking `new` on an already-deployed, already-funded lockup contract account, supplying attacker-controlled `owner_account_id`, `staking_pool_whitelist_account_id`, `vesting_schedule`, `foundation_account_id`, etc. Because `Self { owner_account_id, ... }` unconditionally overwrites the previous struct/state [3](#0-2) , this reassigns `owner_account_id` (and thus all owner-only privileges over the account's balance, including transfer and staking control) to the attacker, discarding the legitimate lockup/vesting schedule and locked balance in favor of attacker-chosen parameters.

### Impact Explanation
This maps to the Critical impact category: "Unauthorized transfer, withdrawal, spending, or release of locked, vested, pooled ... NEAR through public-call ... accounting failure reachable by an unprivileged user," and also "Permanent freezing, unrecoverable lock, or irrevocable loss of user or protocol funds in lockup release ... flows." An attacker who reinitializes the contract as `owner_account_id` gains the owner's ability to call the owner-only methods in `lockup/src/owner.rs` (e.g., transferring available balance, selecting a staking pool, staking/unstaking, withdrawing rewards), effectively taking over the entire NEAR balance held by the lockup account.

### Likelihood Explanation
High. The entry path requires no privilege whatsoever — any account can submit a `FunctionCall` transaction to the target lockup account's `new` method, since NEAR does not require the caller to hold access keys on the receiver to invoke its public contract methods. The only friction is that the attacker must know/guess the deployed lockup contract's account ID, which is derivable/public (lockup contract addresses are deterministically derived from `owner_account_id` by `lockup-factory`) [4](#0-3) .

### Recommendation
Add `assert!(!env::state_exists(), "Already initialized");` as the first statement of `LockupContract::new` in `lockup/src/lib.rs`, mirroring the guard already present in `staking-pool/src/lib.rs:179`, `multisig/src/lib.rs:104`, `whitelist/src/lib.rs:34`, and `voting/src/lib.rs:36`.

### Proof of Concept
1. Lockup contract `lockup1` is deployed and initialized by `lockup-factory` with `owner_account_id: "owner1"` and a funded balance.
2. An unprivileged attacker account `mallory` submits a transaction calling `lockup1.new({owner_account_id: "mallory", lockup_duration: 0, transfers_information: {TransfersEnabled:{transfers_timestamp: 0}}, vesting_schedule: None, release_duration: None, staking_pool_whitelist_account_id: "whitelist", foundation_account_id: None})`.
3. Because there is no `state_exists` check, `new` executes successfully and overwrites `owner_account_id` to `"mallory"`.
4. `mallory` now calls owner-only methods (e.g. `transfer`) on `lockup1` and drains/controls the account's NEAR balance, which previously belonged to `owner1`.

            "The staking pool whitelist account ID is invalid"
        );
        if let TransfersInformation::TransfersDisabled {
            transfer_poll_account_id,

            assert!(

                "The transfer poll account ID is invalid"
            );
        }
        let lockup_information = LockupInformation {
            lockup_amount: env::account_balance(),
            termination_withdrawn_tokens: 0,
            lockup_duration: lockup_duration.0,

            lockup_timestamp: lockup_timestamp.map(|d| d.0),
            transfers_information,
        };
        let vesting_information = match vesting_schedule {
