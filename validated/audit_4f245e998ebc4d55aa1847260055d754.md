### Title
Sybil bypass of `TokenFaucet`'s per-address daily mint cap via unlimited attacker-deployed contracts - (File: `evm/src/utils/TokenFaucet.sol`)

### Summary
`TokenFaucet.drip()` restricts each caller to minting once per day using a `mapping(address => uint256)` keyed on `msg.sender`. Exactly like the `MeritDutchAuction.CAP_PER_ADDRESS` bug, this per-address bookkeeping is trivially defeated because `msg.sender` is attacker-controlled: an attacker can deploy an arbitrary number of throwaway contracts, each calling `drip()` once, to mint an unbounded amount of the fee token in a single transaction (via a factory/multicall contract) instead of the intended 1000 tokens/day/address.

### Finding Description
`TokenFaucet.drip(address token)` in `evm/src/utils/TokenFaucet.sol` reads and writes `consumers[msg.sender]` to enforce a 1-per-day mint limit, then calls `HyperFungibleTokenImpl(token).mint(msg.sender, 1000 * 1e18)`: [1](#0-0) 

Because the cap is keyed purely by `msg.sender` and there is no `tx.origin` check, no per-block/global limit, and no cooldown tied to a real-world identity, a single attacker can deploy N helper contracts (or a factory that `CREATE`s N contracts in a loop) that each call `drip(token)` exactly once. Every helper contract is a distinct `msg.sender`, so `consumers[helper] == 0` for all of them and each one passes the `delay < 1 days` check and receives `1000 * 1e18` freshly minted tokens — all within a single transaction, exactly the pattern used in the referenced `MeritDutchAuction` PoC (deploy sub-contracts, mint to each, then sweep to one address).

The mint itself is real and backed by `MINTER_ROLE` on the underlying `HyperFungibleTokenImpl`: [2](#0-1) 

so this is not a griefing-only bug — it produces genuinely unbacked new supply of the token the faucet is authorized to mint, at whatever multiple of 1000 tokens the attacker chooses to deploy contracts for.

### Impact Explanation
`TokenFaucet` is documented as dripping "Hyper USD (USD.h)" — the fee token required to dispatch ISMP POST/GET requests through Hyperbridge (see `docs/content/developers/evm/messaging/testnet-faucet.mdx`) — and the faucet contract holds `MINTER_ROLE` on that token to perform the mint. Bypassing the per-address cap lets a single actor mint an unbounded quantity of this fee token via a single orchestrating transaction, i.e., an unbacked-mint of a protocol fee token, which is exactly the "unbacked mint" impact category this scan is validating against.

However, this faucet is explicitly documented and wired only for testnet fee-token distribution (`docs/content/developers/evm/messaging/testnet-faucet.mdx`, `evm/script/DeployIsmp.s.sol`, `evm/tests/foundry/BaseTest.sol`), not deployed against a mainnet fee token with real economic value. I could not find any evidence in the indexed codebase that `TokenFaucet` is deployed in a production/mainnet configuration or that it mints a token with real monetary backing.

### Likelihood Explanation
Exploitation is trivial and fully permissionless: it requires only deploying contracts and calling a public function, with no signature checks, allowlists, or `tx.origin` gating anywhere in the call path. Any address, contract or EOA, can trigger it at will.

### Recommendation
- Gate `drip()` on `tx.origin == msg.sender` (accepting that this blocks legitimate contract wallets), or
- Track consumption per a Sybil-resistant identity (e.g., off-chain KYC/captcha-gated allowlist) rather than per raw address, or
- Enforce a global/per-block mint ceiling on the faucet independent of the per-address cooldown, or
- If this contract is genuinely testnet-only, explicitly restrict `mint` authorization / deployment so it can never be pointed at a fee token with real value, and treat this as low-severity given testnet scope.

### Proof of Concept
```solidity
// Deploy any number of one-shot helper contracts, each calling drip() once.
contract DripHelper {
    constructor(address faucet, address token) {
        TokenFaucet(faucet).drip(token);
        // token.transfer(attacker, token.balanceOf(address(this))) to sweep
    }
}

contract DripSybilAttack {
    constructor(address faucet, address token, uint256 n) {
        for (uint256 i = 0; i < n; i++) {
            new DripHelper(faucet, token); // each helper is a fresh msg.sender
        }
        // sweep minted balances to the attacker's EOA
    }
}
```
Each `DripHelper` is a distinct address with `consumers[helper] == 0`, so `delay >= 1 days` trivially holds and every helper mints `1000 * 1e18` tokens, bypassing the intended once-per-day-per-address limit entirely within one attacker transaction.

*Note on confidence*: I was not able to fully confirm from the indexed codebase whether `TokenFaucet` is ever deployed against a token with real (non-testnet) value, which materially affects the severity classification here — this is the main open uncertainty in this finding.

```text
contract TokenFaucet {
    mapping(address => uint256) private consumers;

    // @dev Will only drip tokens, once per day
    function drip(address token) public {
        uint256 lastDrip = consumers[msg.sender];
        uint256 delay = block.timestamp - lastDrip;

        if (delay < 1 days) {
            revert("Can only request tokens once daily");
        }

        consumers[msg.sender] = block.timestamp;
        HyperFungibleTokenImpl(token).mint(msg.sender, 1000 * 1e18);
    }
```
