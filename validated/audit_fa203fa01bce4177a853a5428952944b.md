## Finding

### Title
Unchecked ERC-20 return value in Tron `IntentGatewayV2.withdraw()` allows silent transfer failure that permanently freezes escrowed funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` uses low-level `.call()` with the raw `IERC20.transfer.selector` and only checks that the call did not revert (`success`), never decoding and validating the returned boolean. Non-reverting-but-`false`-returning ERC20 tokens (a well-known category on token bridges, including many Tron/TRC-20 style tokens) can cause escrow accounting to be permanently decremented while the actual token transfer silently fails, freezing the underlying balance in the contract forever.

### Finding Description
`withdraw()` releases escrowed input tokens after a cross-chain `RedeemEscrow`/`RefundEscrow` message is delivered via `onAccept`/`onGetResponse`: [1](#0-0) 

For every non-native token, it performs:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
```
then unconditionally decrements `_orders[body.commitment][token] -= amount;` right after — this only reverts if the external call itself reverts; it never inspects the ABI-decoded boolean return value. The same unchecked pattern appears for fee payout in the same function, for the `SweepDust` handler, and for the post-dispatch sweep in `placeOrder`: [2](#0-1) [3](#0-2) 

Elsewhere in the very same file, `safeTransferFrom` (`SafeERC20`) is correctly used for inbound transfers, e.g. escrowing order inputs and fees: [4](#0-3) [5](#0-4) 

showing the outbound-transfer paths were deliberately (or mistakenly) not brought up to the same standard, unlike the equivalent EVM contracts (`IntentsBase.sol`, `IntentGatewayV2.sol` on EVM) which consistently `safeTransfer`/`safeTransferFrom`: [6](#0-5) 

This is the exact bug class in the external report: relying on a boolean transfer return without checking it, instead of reverting on failed transfer via `safeTransfer`.

### Impact Explanation
`order.inputs[i].token` is an arbitrary address chosen by the order creator when calling `placeOrder`. If that token contract's `transfer` returns `false` on failure without reverting (a legitimate ERC20 pattern, and common on Tron), then when a solver fills the order and the cross-chain `RedeemEscrow`/`RefundEscrow` message is delivered:
1. `withdraw()` calls `token.call(...)`, which succeeds at the EVM/TVM call level (`success == true`) even though the token itself refused to move balance (e.g., due to insufficient balance, pause, blacklist, or simply returning `false` by design).
2. The code does not detect this and proceeds to decrement `_orders[commitment][token]` and mark the order `_filled`/emit `EscrowReleased`.
3. The tokens actually stay locked in the `IntentGatewayV2` contract's balance, with no accounting path left to recover them — escrow state says the funds were already paid out.

This results in permanent freezing of the escrowed token balance (funds theft from the intended beneficiary and stranding of contract funds), satisfying the impact bar for a Medium-severity finding.

### Likelihood Explanation
Reachable by any unprivileged flow: order creation via `placeOrder` allows arbitrary `token` addresses, and settlement via `onAccept`/`onGetResponse` is driven by ordinary relayed ISMP messages following a normal fill — no privileged role is required to trigger the vulnerable code path, only a token contract that returns `false` instead of reverting on failed transfer.

### Recommendation
Replace all `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `evm/tron/contracts/apps/IntentGatewayV2.sol` (`withdraw`, `SweepDust` handling, and the `placeOrder` predispatch sweep) with `SafeERC20.safeTransfer`/`safeTransferFrom`, consistent with the rest of the file and with the EVM `IntentsBase.sol` implementation, so that a `false` return value causes a revert rather than silently succeeding.

### Proof of Concept
1. Order creator deploys a custom ERC20 token whose `transfer` returns `false` (without reverting) once the contract's balance is fully depleted or under attacker-controlled conditions, and uses it as `order.inputs[0].token` in `placeOrder` on the Tron IntentGatewayV2.
2. A solver fills the order cross-chain via `fillOrder`; a `RedeemEscrow` request is dispatched back to the Tron chain.
3. A relayer delivers the message; `onAccept` calls `withdraw()`, which attempts `token.call(transfer(beneficiary, amount))`.
4. The malicious token returns `false` but does not revert; `success == true`, so the code proceeds, decrements `_orders[commitment][token]`, and emits `EscrowReleased`.
5. The beneficiary never receives the tokens, and the balance remains stuck in the `IntentGatewayV2` contract with no remaining accounting path to release it — permanent loss/freezing of funds. [7](#0-6)
