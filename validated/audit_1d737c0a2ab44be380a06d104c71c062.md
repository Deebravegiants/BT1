### Title
Cross-Tenant Webhook Spoofing via Unauthenticated `shop-domain` Header - ([File: lib/shopify_api/webhooks/request.rb], [File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by HMAC-verifying the raw request body, then dispatches the handler using the `shop` value taken from the `X-Shopify-Shop-Domain` header — a field that is never included in the signed payload. Any party capable of obtaining one genuinely-signed webhook delivery (e.g. by installing the app on a free/trial store they control) can replay that exact body while substituting the `shop-domain` (and `topic`/`webhook-id`) header to point at an arbitrary victim shop, and the library will accept it as authentic and hand it to the host app's handler attributed to that victim shop.

### Finding Description
The identity-binding equality that should hold is: `shop that is HMAC-authenticated == shop the handler is told the event belongs to`. In this gem that equality is broken.

- `HmacValidator.validate` only verifies `verifiable_query.to_signable_string`, and for webhooks `to_signable_string` returns just the raw JSON body: [1](#0-0) 

- The `shop`, `topic`, `webhook_id`, and `api_version` values are all pulled straight from HTTP headers with no cryptographic binding to the signature at all: [2](#0-1) 

- `Registry.process` validates only the HMAC over the body, then immediately trusts `request.shop` (the unauthenticated header) to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

Because the HMAC secret (`Context.api_secret_key`) is shared across every shop that has the app installed, and the header claiming *which* shop the event is for is unsigned, anyone who can obtain one legitimately-signed webhook body (trivially done by installing the app on their own store, or triggering any topic they subscribe to) can re-send that identical body to the same endpoint with a forged `X-Shopify-Shop-Domain` header naming a different, victim shop. `HmacValidator.validate` still succeeds because it never inspects the header, and `Registry.process` will invoke the handler believing the event originates from the victim tenant.

### Impact Explanation
This is a cross-tenant access vector: an attacker with no credentials belonging to the victim shop can inject events (with a body of their choosing) that the host application will process as belonging to the victim's tenant. Any handler logic keyed on `shop` (order updates, uninstall flows, billing/plan-change handling, GDPR-topic processing, etc.) can be triggered against a shop the attacker does not control, without needing that shop's access token, `client_secret`, or any privileged credential — matching the "cross-tenant access" Critical-impact category.

### Likelihood Explanation
Likelihood is high: no special access is required beyond the ability to install the app once (many apps allow free/dev-store installs) or capture one webhook delivery for a topic the attacker can trigger. Replaying an HTTP POST with a modified header is trivial, and the gem performs no additional check tying the signed body to the claimed shop.

### Recommendation
Bind the shop identity into what is verified:
1. Reject or independently verify the `X-Shopify-Shop-Domain` header against a value the app already has associated with the specific `access_token`/session used to register that webhook subscription (e.g., cross-check against a known/allow-listed list of shops that installed the app), rather than trusting the header blindly.
2. Where possible, include the shop domain in application-level validation after HMAC success (e.g., look up whether `request.shop` matches an existing installed-shop record before invoking the handler), so a replayed body cannot be reattributed to an arbitrary shop.
3. Document to consumers of `ShopifyAPI::Webhooks::Registry` that `shop`, `topic`, `webhook_id`, and `api_version` are unauthenticated and must be revalidated against known installed shops before being used for any state-changing or tenant-scoped operation.

### Proof of Concept
1. Attacker installs the target app on their own (attacker-controlled) shop `attacker.myshopify.com`, subscribing to a webhook topic (e.g. `orders/paid`).
2. Shopify delivers a legitimately HMAC-signed webhook to the app's endpoint:
   - Body: `{"id": 123, ...}`
   - Headers: `X-Shopify-Hmac-Sha256: <valid for body>`, `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Topic: orders/paid`
3. Attacker captures this raw request and re-sends it to the same public endpoint, keeping the body and `X-Shopify-Hmac-Sha256` header identical, but changing `X-Shopify-Shop-Domain` to `victim.myshopify.com`.
4. `HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` re-computes the signature over the unchanged body and it matches — validation passes.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) invokes the app's handler with `shop: "victim.myshopify.com"`, causing the host application to process attacker-supplied data as though it originated from the victim tenant.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
