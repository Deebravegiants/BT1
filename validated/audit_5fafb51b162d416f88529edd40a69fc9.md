## Title
CORS wildcard origin allowlist bypass via missing subdomain boundary check - (File: core/services/gateway/network/httpserver.go)

## Summary
The Gateway's `isAllowedOrigin` function in `httpserver.go` implements wildcard CORS matching (`*.domain.com`) using a plain `strings.HasSuffix` check on the origin host, without verifying that a `.` boundary actually precedes the matched suffix. This allows an attacker-controlled domain that merely ends with the same character sequence as the allowed suffix (e.g., `evilethereum.org` against `*.ethereum.org`) to be treated as an allowed origin.

## Finding Description
In `isAllowedOrigin`, after stripping the `*.` prefix from a configured wildcard entry, the code performs:
```go
allowedHost = allowedHost[2:]
if strings.HasSuffix(originHost, allowedHost) {
    return true
}
``` [1](#0-0) 

This check only confirms `originHost` ends with the literal `allowedHost` string, not that it is an actual subdomain (i.e., there is no verification that the character preceding the suffix is a `.`). A host like `notethereum.org` or `evilethereum.org` satisfies `strings.HasSuffix(originHost, "ethereum.org")` while not being a genuine subdomain of `ethereum.org`.

The result feeds directly into the CORS response headers in `handleRequest`: [2](#0-1) 

The existing test suite validates only the intended positive wildcard matches and negative cases involving scheme/port/full-non-suffix mismatches; it does not test a suffix-collision case such as `evilethereum.org`, so the boundary bypass is unguarded by regression tests. This is a genuine code-level logic bug reachable by any unprivileged client that can send an HTTP request with a crafted `Origin` header to the gateway's user-facing endpoint — no operator misconfiguration beyond the documented, supported act of configuring a wildcard CORS entry is required.

## Impact Explanation
When an operator configures a wildcard CORS allowlist entry (a supported configuration option, as shown in `sample_config_tls.toml` and covered by the wildcard test in `httpserver_test.go`), an attacker who registers or controls a domain ending in the same suffix (without an actual subdomain relationship) can have the gateway reflect `Access-Control-Allow-Origin` for their origin. This grants cross-origin browser access to the gateway's JSON-RPC user endpoint that was intended to be restricted to legitimate subdomains, enabling cross-origin request/response exposure — mapping to the "allowlist bypass" / "gateway request impersonation" impact category.

## Likelihood Explanation
Exploitation only requires: (1) an operator using the documented wildcard CORS feature (not a misconfiguration but intended use), and (2) trivial, low-cost domain registration of a suffix-colliding name by an unprivileged external attacker. No credentials, elevated roles, or host access are needed — a normal browser request with a forged `Origin` header suffices.

## Recommendation
Enforce a proper subdomain boundary in the wildcard check, e.g.:
```go
if originHost == allowedHost || strings.HasSuffix(originHost, "."+allowedHost) {
    return true
}
```
Add regression tests covering suffix-collision hosts (e.g., `notethereum.org` / `evilethereum.org` against `*.ethereum.org`).

## Proof of Concept
1. Start the gateway's `httpServer` with `CORSEnabled = true` and `CORSAllowedOrigins = []string{"https://*.ethereum.org"}` (as done via `startNewServer` in `httpserver_test.go`).
2. Send a POST request to the configured path with header `Origin: https://evilethereum.org`.
3. Observe `resp.Header.Get("Access-Control-Allow-Origin")` returns `https://evilethereum.org`, confirming the bypass, since `strings.HasSuffix("evilethereum.org", "ethereum.org")` evaluates true in `isAllowedOrigin` at [1](#0-0) .
