### Title
Permanent market freeze: accrual value overflow panics before the borrow-index cap engages, bricking withdraw/repay/liquidate - (File: common/src/rates/index.rs)

### Summary
Every mutating pool entrypoint runs `global_sync` first, which recomputes `borrowed * borrow_index` inside `calculate_supplier_rewards`. The index is capped at `MAX_BORROW_INDEX_RAY` (1e36 raw), but the *product* `scaled_shares × index` overflows `i128` well before that cap is reached. Once `borrowed.mul(env, new_borrow_index)` (or even `borrowed.mul(env, old_borrow_index)`) exceeds `i128::MAX`, accrual panics with `MathOverflow` (33) on every subsequent call — permanently, because the stored index never decreases and no verb can skip accrual. The repository's own adversarial test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` demonstrates this end-to-end: after the cliff, `update_indexes`, `withdraw`, and `repay` all revert with `MATH_OVERFLOW`, and the index cap is confirmed not to have engaged.

### Finding Description
- `update_borrow_index` clamps the index at `MAX_BORROW_INDEX_RAY`, but `calculate_supplier_rewards` computes `borrowed.mul(env, old_borrow_index)` and `borrowed.mul(env, new_borrow_index)` with checked arithmetic; a market whose scaled debt times index exceeds `i128::MAX` panics inside `accrue_step`.
- `interest::global_sync` runs at the top of every market mutation (`supply`, `borrow`, `withdraw`, `repay`, `net_settle`, `seize_positions`, `flash_loan`, `create_strategy`, `claim_revenue`, `recapitalize`), so the panic propagates to all of them — this is not a fail-closed check, it is an arithmetic overflow on the mandatory path.
- The cap `MAX_BORROW_INDEX_RAY` only bounds the index; it does not bound `scaled × index`. On a steep interest-rate curve (the XLM preset in tests), a large market at sustained ~98% utilization grows the index fast enough that the value ceiling is hit while `borrow_index < MAX_BORROW_INDEX_RAY`.
- Once the state is reached, even setting future rates to zero cannot rescue the market: `calculate_supplier_rewards` multiplies by `old_borrow_index` too, so accrual still panics. No in-scope verb avoids `global_sync`.

### Impact Explanation
Permanent freezing of all funds in the affected `(hub_id, asset)` market: suppliers cannot withdraw, borrowers cannot repay, liquidators cannot liquidate (controller liquidation calls pool `seize_positions`/`repay`, which accrue first), and protocol revenue cannot be claimed. The market is bricked absent a contract upgrade. This satisfies the "permanent freezing of funds" impact class.

### Likelihood Explanation
An unprivileged attacker can drive a market to the cliff using only `supply` and `borrow`: supply a very large amount of a high-decimal, low-unit-value asset and borrow to sustained maximum utilization on a steep rate curve. The attacker's own borrow position even accrues value during the wait. The cost is large capital and sustained high utilization; it requires no privilege, leaked key, or bad parameter — only the admin-configured rate curve, which verification already accepts. Likelihood is gated by capital requirements and multi-year accrual on realistic parameters, consistent with Medium severity.

### Recommendation
- Make `calculate_supplier_rewards` (and any `scaled.mul(index)` inside `accrue_step`) saturating rather than checked: compute total debt via `mul_div`-style saturating helpers so accrual degrades gracefully instead of panicking.
- Alternatively, clamp `borrowed * new_borrow_index` growth by capping the index *dynamically* at `i128::MAX / borrowed` before multiplying, and/or cap scaled-debt issuance at borrow time so `scaled × MAX_BORROW_INDEX_RAY` can never overflow.
- Add a governance/keeper-facing guard test asserting `borrowed.mul(borrow_index)` stays below `i128::MAX` after every accrual step.

### Proof of Concept
```rust
// From tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321
// A whale supplies principal = 1e9 * 10^18 units of an 18-decimal asset,
// borrows 98% of it on the steep XLM curve, then advances time yearly.
let principal = BILLION * 10i128.pow(18);
t.supply_raw(BOB, "BIG18", principal);
t.borrow_raw(ALICE, "BIG18", principal / 100 * 98);
loop {
    t.advance_time(YEAR_SECS);
    if let Err(e) = t.try_update_indexes_for(&["BIG18"]) { break e; } // -> MATH_OVERFLOW
}
// Confirmed by the test: borrow_index < MAX_BORROW_INDEX_RAY (cap never engaged),
// yet withdraw and repay now both panic:
assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
```
