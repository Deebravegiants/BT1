### Title
Webhook HMAC Only Covers the Raw Body, Not the `shop-domain`/`topic`/`webhook-id` Headers, Allowing Cross‑Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while `shop`, `topic`, and `webhook_id` are read straight from unauthenticated headers and forwarded, unchecked, into the handler that `Registry.process` invokes. The equality the gem should enforce — "the shop that authorizes the HMAC == the shop attributed to the event" — is never checked, so an attacker who is a legitimate (but "unprivileged" relative to other tenants) install of the same app can capture one of their own genuinely-signed webhooks and replay it with a forged `x-shopify-shop-domain` header, causing the app to process it as belonging to a different merchant.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 

Only `@raw_body` is signed. The `shop`, `topic`, and `webhook_id` accessors are pulled directly from attacker-controllable HTTP headers with no cryptographic binding to the signature: [2](#0-1) 

`Utils::HmacValidator.validate` (used by `Registry.process`) validates the signature purely against `to_signable_string`, i.e. the body: [3](#0-2) 

`Registry.process` then trusts `request.shop`/`request.topic`/`request.webhook_id` unconditionally and passes them into the handler's `WebhookMetadata`: [4](#0-3) 

Because the HMAC secret (`api_secret_key`, the app's client secret) is the same for every shop that has the app installed, any merchant with the app installed can receive a genuinely-signed webhook for their own store (valid `raw_body` + `hmac`), and simply resend that exact `(raw_body, hmac)` pair to the app's public webhook endpoint while substituting `x-shopify-shop-domain` (and optionally `x-shopify-topic`/`x-shopify-webhook-id`) with another tenant's shop domain. `HmacValidator.validate` still succeeds because it never inspects the header values — only the body. The identity binding broken is:

`shop authenticated by the HMAC (none, since shop isn't signed) != shop attributed to the processed event (attacker-supplied header)`

### Impact Explanation
This is a cross-tenant integrity issue: the receiving app will process attacker-controlled webhook content (order data, customer data, app-uninstall notices, etc., depending on registered topics) while believing it originates from a different merchant's shop, because the gem hands `request.shop` straight to the handler as if it were authenticated. Any application logic keyed off `shop` (e.g., looking up a session/access token for that shop, updating per-shop state, billing, GDPR data-request flows) can be poisoned by another tenant. This matches the "Critical – cross-tenant access" impact category, rooted entirely in this gem's `Webhooks::Request`/`Registry` implementation rather than host-application misuse.

### Likelihood Explanation
Any entity that can install the app on at least one shop (a normal, unprivileged action for a public/multi-tenant Shopify app) can capture one legitimate signed webhook delivered to their own store — this requires no special access, no leaked secret, and no privileged account. The webhook endpoint is a public HTTP(S) URL. Replaying the exact `(body, hmac)` pair with a substituted `shop-domain` header is a trivial HTTP replay, requiring no cryptography to be broken since the header was never part of what's signed.

### Recommendation
Include the identifying headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signed material, or otherwise cryptographically bind the shop attribution to the verified body (e.g., verify that the resolved shop has webhooks registered with a topic/id combination that matches server-side state before dispatch). At minimum, `to_signable_string` in `lib/shopify_api/webhooks/request.rb` should not sign the body alone when downstream code (`Registry.process` in `lib/shopify_api/webhooks/registry.rb`) treats header-derived `shop`/`topic`/`webhook_id` as trusted identity data.

### Proof of Concept
1. App `X` is installed on `attacker-shop.myshopify.com` and on victim `victim-shop.myshopify.com`, both webhooks signed with the same app `api_secret_key`.
2. Shopify sends a legitimate `orders/create` webhook to `attacker-shop`:
   ```
   POST /webhooks
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid-hmac-for-body>
   x-shopify-shop-domain: attacker-shop.myshopify.com
   x-shopify-webhook-id: abcd-1234
   Body: {"id": 1, "malicious_field": "..."}
   ```
   The attacker captures `Body` and `x-shopify-hmac-sha256` (both fully attacker-visible since it's their own webhook).
3. Attacker resends the same request to the app's webhook endpoint, only changing the shop header:
   ```
   POST /webhooks
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <same-valid-hmac>
   x-shopify-shop-domain: victim-shop.myshopify.com
   x-shopify-webhook-id: abcd-1234
   Body: {"id": 1, "malicious_field": "..."}   (unchanged)
   ```
4. `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:26-31`) succeeds because it only checks `@raw_body`, which is unchanged.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) dispatches the handler with `shop: "victim-shop.myshopify.com"`, causing the app to process attacker-controlled order data as belonging to the victim tenant.
