## Analysis

I investigated the Hyperbridge/Simplex codebase for an analog to the Vee.Finance incident (price-oracle/price-source manipulation enabling attacker to extract far more value than legitimately owed). The closest reachable analog is in the Simplex intent solver's FX filler, where a previously-existing loss-bound clamp against manipulated venue prices has been explicitly disabled.

### Title
Disabled overfill clamp lets a manipulated Uniswap V4 venue price force the solver to overpay on intent fills - (File: `sdk/packages/simplex/src/strategies/fx.ts`)

### Summary
The FXFiller intent-filling strategy computes the output it delivers to a cross-chain intent using either a static bid/ask curve or, for "venue-priced" pairs, the live Uniswap V4 pool price as an oracle. A per-leg overfill ceiling `(1 + maxOverfillBps) × userRequested` was designed to bound loss from "a bug / stale cache / manipulated venue price," but this clamp has been deliberately disabled — it now only logs a warning while the filler transfers the full, unclamped computed amount.

### Finding Description
In `resolveLegRates`/`computeLegPolicyOutput` a venue-priced pair (`token0` is a USD stable, no static curve) derives its rate from the live Uniswap V4 pool mid-price via `getVenueUsdPrice` / `UniswapV4FundingPlanner.getExoticTokenPrice`, guarded only by an optional `checkPriceGuard` that compares against a static `referencePrice`/`maxDeviationBps` (both fields are optional and can be left unset, "leaving the chain unguarded"). [1](#0-0) 

Once `rawPolicyMaxOutput` is computed from this (potentially manipulated) rate, the code compares it against `overfillCeiling = output.amount * (10000n + maxOverfillBps) / 10000n`, but explicitly does **not** clamp to it — it only emits a warning and fills `rawPolicyMaxOutput` unchanged: [2](#0-1) 

The comment in the code itself states the removed protection targeted exactly this bug class: *"this removes the per-leg loss bound that previously protected against a bug / stale cache / manipulated venue price."* [3](#0-2) 

`checkPriceGuard`'s deviation check is also known to be insufficient even when configured — it only validates a static-reference deviation, not the actual execution cost the venue-priced fill will pay when the solver swaps through its own pool to source inventory: [4](#0-3) 

### Impact Explanation
An unprivileged actor can submit (or wait for) a cross-chain intent order on a Uniswap-V4-funded pair and, around the time the solver resolves/fills it, manipulate the destination-chain pool price (e.g. via flash-loan swap) within the guard's tolerance (or on an unguarded chain where `referencePrice`/`maxDeviationBps` are unset). Because the overfill clamp is disabled, `computeLegPolicyOutput` will return an inflated `policyMaxOutput` derived from the skewed pool price, and the filler will transfer that inflated amount to fill the order — a direct, uncapped loss of solver funds analogous to the Vee.Finance exploit where a manipulated/compromised price input let the attacker extract far more collateral value than legitimately owed.

### Likelihood Explanation
Reachable from a single external actor manipulating a public AMM pool immediately before/around a solver's fill transaction; no privileged access, governance, or off-chain compromise is required. The guard rails that would have prevented this (`maxOverfillBps` clamp) exist in code but are intentionally bypassed, and the secondary guard (`checkPriceGuard`) is both optional per-pair and does not account for execution/fee-tier cost, so the exposure is not merely theoretical.

### Recommendation
Re-enable enforcement of `overfillCeiling` as a hard cap (reject or clamp the fill) rather than warn-only, and make `referencePrice`/`maxDeviationBps` mandatory for any venue-priced pair, additionally incorporating the pool's actual fee tier / execution slippage into `checkPriceGuard` rather than comparing only the quoted mid-price.

### Proof of Concept
1. Configure (or find) a `[vault.uniswapV4]` venue-priced pair without `referencePrice`/`maxDeviationBps`, or within tolerance of one that is configured.
2. Submit a cross-chain intent order for that pair sized to approach `maxOrderSize`.
3. Immediately before the solver's fill lands, flash-loan-manipulate the destination Uniswap V4 pool to shift `sqrtPriceX96` so `getExoticTokenPrice` returns a favorable (attacker-benefiting) quote.
4. The solver's `computeLegPolicyOutput` computes an inflated `rawPolicyMaxOutput`; per `sdk/packages/simplex/src/strategies/fx.ts:684-701` the overfill ceiling check only logs a warning and does not reduce `policyMaxOutput`, so the filler transfers the inflated amount, realizing a loss for the solver equal to the manipulated price delta.
