## Title
RBAC authorization bypass for pod exec/attach/portforward via WebSocket protocol verb mismatch (feature-gated, off by default) - (File: `pkg/registry/core/pod/rest/subresources.go`)

## Summary
Kubernetes maps the pod `exec`/`attach`/`portforward` subresource connect requests to different RBAC verbs depending on the wire protocol used to establish the connection: SPDY uses an HTTP `POST`, which the authorization layer maps to the `create` verb, while WebSocket upgrade uses an HTTP `GET`, which maps to the `get` verb. This is the same class of bug as the GitLab report: two different transport/protocol paths to the same logical operation are subject to *different* authorization enforcement, and the weaker path can be used to bypass the intended access-control rule. The kubernetes maintainers are aware of this (tracked as https://issues.k8s.io/133515) and added a corrective check, but it is hidden behind a feature gate, `AuthorizePodWebsocketUpgradeCreatePermission`, which appears newly introduced (referenced only in the 1.35 changelog) and is therefore very likely still Alpha/disabled by default.

## Finding Description
`AttachREST.Connect` and `ExecREST.Connect` in `pkg/registry/core/pod/rest/subresources.go` only call the corrective `ensureAuthorizedForVerb(ctx, r.Authorizer, "create")` check when the feature gate `features.AuthorizePodWebsocketUpgradeCreatePermission` is enabled: [1](#0-0) [2](#0-1) 

The helper itself, and the comment documenting the underlying protocol/verb mismatch, live in `pkg/registry/core/pod/rest/authorize.go`: [3](#0-2) 

The comment explicitly states the root cause: "SPDY uses POST that at the authz layer is translated to 'create'. Websockets uses GET that is translated to 'get'." This means that without the gate enabled, a subject who is granted only the `get` verb on `pods/exec` (or `pods/attach`, and potentially `pods/portforward`) — but explicitly *not* `create` — can still open an exec/attach session by using the WebSocket upgrade protocol (`GET`), because the RBAC authorizer only ever sees a `get` request and never checks for `create`.

The intended, more restrictive policy (requiring `create` for pod exec/attach, which is the long-standing kubectl/RBAC convention) is silently not enforced for WebSocket-based clients unless the operator has manually turned on this specific alpha feature gate. This is confirmed by the integration test `TestPodSubresourceAuth`, which demonstrates that a user with only `get` permission on `pods/exec` is expected to be forbidden via the WebSocket (`GET`) path — but this expectation only holds when the gate’s corrective check is active: [4](#0-3) 

## Impact Explanation
This is a genuine RBAC authorization-bypass analog to the GitLab report: two request paths (SPDY vs. WebSocket) to the identical privileged operation (opening an interactive shell inside a pod/container) are authorized against different verbs. An operator who deliberately restricts a role/service-account to `get` (read-only) on `pods/exec` — believing this prevents interactive command execution — can be bypassed by any client using the WebSocket upgrade protocol (which is the default protocol negotiated by modern `kubectl` per KEP-4006), granting the caller full interactive command execution capability inside containers. This is equivalent in severity to a privilege-escalation / authorization bypass, since it can grant execute access on workloads to principals who were only granted read access.

## Likelihood Explanation
The bypass is reachable by any ordinary authenticated user issuing a normal Kubernetes API request (no special network position, no malicious node/kubelet needed) — merely choosing the WebSocket subprotocol instead of SPDY when calling the `exec`/`attach` subresource. Because `kubectl` now defaults to WebSocket for these subresources (per KEP-4006), this is not an esoteric path; it's the default client behavior. The bypass is only closed if the cluster administrator has explicitly enabled the new `AuthorizePodWebsocketUpgradeCreatePermission` feature gate, which — being newly introduced and referenced only in the 1.35 changelog — is very likely disabled by default in this codebase (Alpha stage), meaning most clusters running this version remain vulnerable out of the box.

## Recommendation
- Promote `AuthorizePodWebsocketUpgradeCreatePermission` to enabled-by-default (Beta with default `true`) as soon as feasible, rather than leaving the RBAC-consistency fix opt-in.
- Alternatively, remove the feature gate entirely and always enforce `ensureAuthorizedForVerb(ctx, r.Authorizer, "create")` unconditionally in `AttachREST.Connect`, `ExecREST.Connect`, and any equivalent `PortForwardREST.Connect` path, since the underlying protocol-to-verb mapping discrepancy is a genuine authorization inconsistency, not an optional hardening.
- Document explicitly in release notes / upgrade guides that clusters relying on `get`-only RBAC restrictions for `pods/exec`/`pods/attach` are not actually protected against WebSocket-based access until the gate is enabled.

## Proof of Concept
1. Create a ClusterRole/RoleBinding granting a subject `get` (but not `create`) on the `pods/exec` subresource, e.g.:
```yaml
rules:
- apiGroups: [""]
  resources: ["pods/exec"]
  verbs: ["get"]
```
2. As that subject, issue a WebSocket exec request (the default for modern `kubectl exec`, or directly via a WebSocket client) to `GET /api/v1/namespaces/<ns>/pods/<pod>/exec?...`.
3. With `AuthorizePodWebsocketUpgradeCreatePermission` disabled (default), `ExecREST.Connect` skips the `ensureAuthorizedForVerb(ctx, r.Authorizer, "create")` check entirely (per `pkg/registry/core/pod/rest/subresources.go:191-197`), and the request proceeds to authorize only against `get`, which the subject already has — granting an interactive shell despite lacking `create` permission.
4. The same request made via SPDY (`POST`) with only `get` granted would correctly be denied, since the authorizer sees the `create` verb directly (as demonstrated by `TestPodSubresourceAuth`), confirming the protocol-dependent authorization inconsistency.

```go
// Pod subresources differs on the REST verbs depending on the protocol used
// SPDY uses POST that at the authz layer is translated to "create".
// Websockets uses GET that is translated to "get".
// Since the defaulting to websocket for kubectl in KEP-4006 this caused an
// unexpected side effect and in order to keep existing policies backwards
// compatible we always check that the "create" verb is allowed.
// Ref: https://issues.k8s.io/133515
func ensureAuthorizedForVerb(ctx context.Context, a authorizer.UnconditionalAuthorizer, verb string) error {
	requestInfo, ok := genericapirequest.RequestInfoFrom(ctx)
	if !ok {
		return apierrors.NewInternalError(errors.New("no request info in context"))
	}
	if requestInfo.Verb == verb {
		// already authorized
		return nil
	}
```
