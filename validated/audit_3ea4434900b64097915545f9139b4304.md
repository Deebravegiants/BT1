### Title
Webhook shop/topic/id headers are not covered by HMAC verification, enabling cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature only over the raw request body, while the shop domain, topic and webhook id are read directly from unauthenticated HTTP headers and then handed to the app's webhook handler as trusted tenant-identifying data. Any unprivileged actor who can obtain one valid `(body, hmac)` pair for the app (e.g. by installing the app on their own shop and triggering a webhook) can replay that exact body/HMAC while forging the `shop-domain` header to point at a victim shop, and the gem will report the request as valid.

### Finding Description
`Request#to_signable_string` returns only the raw body: [1](#0-0) 

`shop`, `topic`, `webhook_id` and `api_version` are parsed straight from headers with no cryptographic binding to the signature: [2](#0-1) 

`Utils::HmacValidator.validate` only checks `verifiable_query.hmac` against `to_signable_string`, i.e. the body: [3](#0-2) 

`Webhooks::Registry.process` accepts the request once that body-only HMAC check passes, then forwards `request.shop` (header-derived, unauthenticated) to the app's handler as the tenant identifier, alongside the (authenticated) body: [4](#0-3) 

The identity binding that should hold is: `shop used to authenticate the payload == shop the app associates the payload with`. Because the header is outside the signed string, this equality does not hold — the gem authenticates the *bytes* of the body, but the *shop* value that callers use to select the tenant/store the data is never verified against that signature.

Since a single app's `api_secret_key` (used to compute the webhook HMAC) is shared across every shop that installs the app, a value that is valid for shop A's payload is equally "valid" (per this check) when replayed with a different shop header.

### Impact Explanation
An attacker who installs the target app on their own shop (a completely unprivileged action — anyone can install a public/dev Shopify app) can capture a legitimate `(raw_body, x-shopify-hmac-sha256)` pair from a webhook delivered to their own install, then POST the identical body+HMAC to the app's webhook endpoint with the `x-shopify-shop-domain` header changed to a victim shop's domain. `HmacValidator.validate` still returns true (body unchanged), `Registry.process` still dispatches, and the handler receives `WebhookMetadata` with `shop` set to the victim's domain. Any host application that uses this gem's documented `shop` field to route webhook data to per-tenant records will have attacker-controlled body content associated with — and potentially written into — a victim tenant's data, i.e. cross-tenant data injection/corruption via the app's own trusted webhook path. This satisfies the Critical "cross-tenant access" impact category.

### Likelihood Explanation
The prerequisite (installing the app on an attacker-controlled shop to obtain one valid body/HMAC sample) requires no privileges beyond normal, unauthenticated use of the Shopify platform, and no secret material from the target app. The replay itself only requires sending an HTTP POST with a forged header to the app's public webhook endpoint, which by design must be internet-reachable. Likelihood is High for any consuming app that trusts `WebhookMetadata#shop` (the exact field this library hands the app) as the tenant key, which is the documented intended usage.

### Recommendation
Include the shop domain (and ideally topic/webhook id) inside the signed payload verification, or independently verify that the `shop-domain` header corresponds to a shop the app has an active, previously-established install/session for before trusting it as a tenant key. At minimum, document prominently that `shop` on `WebhookMetadata` is not covered by the HMAC and must not be trusted for tenant routing without additional verification (e.g., cross-checking against a known/installed shop list).

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (unprivileged, self-service).
2. Attacker triggers any webhook-eligible event on their own shop and captures the resulting POST: raw body `B` and header `x-shopify-hmac-sha256: H` (valid, since it's their own legitimate delivery).
3. Attacker sends a new POST to the app's webhook endpoint with the same body `B` and header `H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses this into an object whose `hmac` and `to_signable_string` (body `B`) are unchanged, so:
   ```ruby
   ShopifyAPI::Utils::HmacValidator.validate(request) # => true
   ```
   as shown by `validate_signature` in [5](#0-4) .
5. `ShopifyAPI::Webhooks::Registry.process(request)` proceeds and calls the app's handler with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: <attacker's body>, ...)`, per [6](#0-5) , causing the host app to process/store attacker-controlled data under the victim tenant's identity.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
