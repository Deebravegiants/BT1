### Title
Webhook `shop` identity is taken from an unauthenticated HTTP header excluded from the HMAC signature, breaking the shop-binding guarantee - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identifier (`shop`) from the `X-Shopify-Shop-Domain` HTTP header, while the HMAC signature that `ShopifyAPI::Webhooks::Registry.process` verifies only covers the raw request body. The `shop` field is never bound to the signature that authenticates the webhook, so `bytes verified` (the body) and `bytes acted on` (the header-derived shop) diverge.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string`. For webhooks, `Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor used downstream is read directly from the `shopify-shop-domain` header, which plays no part in that signable string: [2](#0-1) 

`Registry.process` validates the HMAC (over the body only) and then hands the header-derived `shop` straight to the app's webhook handler as the tenant context: [3](#0-2) 

Because the signature check (`Utils::HmacValidator.validate(request)`, keyed on `Context.api_secret_key`) authenticates only the body bytes, an attacker who is themselves a legitimate merchant/tenant of the app (an "unprivileged internet user" relative to *other* tenants) receives genuinely-signed webhook payloads for their own shop. Nothing in this gem prevents such a user from replaying that exact body to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a different shop domain — the HMAC over the unchanged body still validates successfully, and `request.shop` (and thus `WebhookMetadata#shop` passed to the handler) now reports the attacker-chosen shop instead of the shop the signed body actually belongs to. This is the same class of bug as the reported issue: an identity-relevant field (`shop`) is acted upon by application logic without being covered by the integrity check (HMAC) that establishes trust, exactly analogous to `_takeToken`'s balance-diff accounting being decoupled from the actual reentrant transfer count.

### Impact Explanation
If a host application uses `WebhookMetadata#shop` from this gem to select which tenant's data to update/delete/associate with the webhook payload (a normal, documented usage pattern — see `docs/usage/webhooks.md` handler examples), an attacker can cause the webhook body to be attributed to an arbitrary victim shop domain while the signature check still passes. This is a cross-tenant identity-binding break: the shop the app trusts (`data.shop`) is not the shop the cryptographic signature actually vouches for (the body only). This satisfies the "Critical – cross-tenant access" criterion, since it lets one tenant's webhook events be falsely attributed to another tenant purely by manipulating an unsigned header.

### Likelihood Explanation
Requires only network-level control over one's own legitimately-received webhook request (any merchant/tenant who installs the app can capture their own signed webhook and replay it with a modified header) — no `api_secret_key`, access token, or privileged access is needed. It depends on the host app trusting `WebhookMetadata#shop` without independent cross-validation against the body content (e.g. many webhook payloads also include shop-identifying fields inside the JSON body, but the gem does not compare `request.shop` against any such in-body field, nor does it document a requirement for callers to do so).

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`/`api_version`) header values in the HMAC-covered signable string, or otherwise cryptographically bind them to the request (e.g. by mixing them into the digest input) so header tampering invalidates the HMAC. At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must not be used as the sole tenant-identity source without further validation against signed body content.

### Proof of Concept
1. Legitimate tenant `shop-a.myshopify.com` installs the app; Shopify sends a webhook to the app's endpoint with body `B` and headers including `X-Shopify-Hmac-Sha256: H` (computed over `B` using the app's `client_secret`) and `X-Shopify-Shop-Domain: shop-a.myshopify.com`.
2. The tenant (or anyone who can intercept/replay this legitimate request, e.g. via a proxy they control) resends the identical body `B` and identical `X-Shopify-Hmac-Sha256: H` header to the app's webhook endpoint, but replaces `X-Shopify-Shop-Domain` with `shop-victim.myshopify.com`.
3. `Utils::HmacValidator.validate(request)` recomputes the HMAC over `request.to_signable_string` (`= @raw_body = B`), which still equals `H`, so validation passes: [4](#0-3) [1](#0-0) 
4. `Registry.process` invokes the handler with `WebhookMetadata.new(topic: ..., shop: request.shop, body: ..., ...)`, where `request.shop` now returns `"shop-victim.myshopify.com"`: [3](#0-2) 
5. Any application logic keyed on `data.shop` (per the documented handler pattern) now processes shop A's webhook data under shop victim's tenant context, despite the signature only proving the body's authenticity, not the shop attribution.
