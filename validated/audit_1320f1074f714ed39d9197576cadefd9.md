### Title
Webhook shop-domain (tenant) identity is not covered by the HMAC signature, allowing cross-tenant webhook impersonation - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the identity fields `shop`, `topic`, `webhook_id`, and `api_version` entirely from unauthenticated HTTP headers, while the HMAC signature validated by `Utils::HmacValidator` only covers the raw request body. Consequently, the tenant-identifying `shop` value handed to application webhook handlers is never cryptographically bound to the signature that is supposed to authenticate the request.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` (and `topic`, `webhook_id`, `api_version`) are read straight from HTTP headers with no relation to the signed body: [2](#0-1) 

`Registry.process` validates the HMAC of the body only, then immediately trusts `request.shop` and `request.topic` to build the `WebhookMetadata` dispatched to the app's handler: [3](#0-2) 

`HmacValidator.validate` computes/compares the signature purely against `verifiable_query.to_signable_string`, i.e. the raw body — the `shop-domain` header plays no part in the equality check: [4](#0-3) 

This breaks the intended identity binding:
`shop_authenticated_by_hmac (∅, body only)` ≠ `shop_used_as_tenant_key (request.shop, from unsigned header)`.

Because the webhook endpoint is a public HTTP route reachable by any internet user, and because the HMAC key (`Context.api_secret_key`) is shared across all shops installed on the app, any user who can obtain one genuine `(raw_body, hmac)` pair — for example by installing the app on their own store and receiving one real webhook — can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header value. `Utils::HmacValidator.validate` will still report the signature as valid because it never inspects the header, and `Registry.process` will dispatch the (attacker-controlled) body to the handler tagged with `shop:` set to whatever domain the attacker supplied — including another merchant's real shop domain.

### Impact Explanation
If the host application uses the `shop` value from `WebhookMetadata` to key data or trigger tenant-scoped business logic (the intended and documented use of this field, since it's the only tenant identifier the gem exposes on `Request`), an attacker can inject forged/replayed event data attributed to an arbitrary victim shop, without ever possessing that shop's session or access token. This is a cross-tenant data/attribution bypass class issue: the shop key trusted by the application layer is not the shop key actually authenticated by the cryptographic proof.

### Likelihood Explanation
Exploitability requires only: (1) the ability to send arbitrary HTTP requests to the app's public webhook endpoint, and (2) possession of one legitimately-signed `(body, hmac)` pair, which any user can obtain by simply installing the app on a shop they control (a normal, unprivileged action) and observing one real webhook delivery. No access token, `client_secret`, or privileged account is required — only the shared `api_secret_key` is used server-side to compute a signature that never binds to the shop header, exactly matching the "field acted on but not covered by the HMAC" identity-binding gap.

### Recommendation
Bind the shop (and ideally topic) to the signed content rather than trusting them from headers alone. Options include:
- Have `Registry.process` cross-check that `request.shop` corresponds to a shop that both has an active session/installation *and* that the specific webhook was actually registered/expected for that shop (e.g., correlate via `webhook_id` looked up against Shopify, or require the host app to verify shop provenance before dispatch).
- At minimum, document prominently (and enforce via an API) that `request.shop` is not covered by the HMAC and must not be used as a sole tenant-authorization key without additional verification (e.g., confirming the shop has a valid, independently-stored offline session before acting on webhook data).
- Consider incorporating the shop domain into the value hashed/compared during validation if a future webhook delivery format from Shopify supports it, or add a secondary check in `HmacValidator`/`Registry` that ties the header shop to a known/expected value for the specific webhook subscription id.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and lets Shopify deliver one real webhook, capturing the raw request body `B` and the valid header `x-shopify-hmac-sha256: H` (computed by Shopify using the app's `api_secret_key` over `B`).
2. Attacker sends a new POST request directly to the app's webhook endpoint with:
   - Body: `B` (unchanged)
   - Header `x-shopify-hmac-sha256: H` (unchanged, still valid since it only signs `B`)
   - Header `x-shopify-shop-domain: victim-shop.myshopify.com` (forged)
   - Header `x-shopify-topic`: unchanged or forged to a topic the attacker wants processed
3. `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:26-31`) recomputes the HMAC over `B` only, matches `H`, and returns `true`.
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-199`) proceeds to call the app's handler with `shop: "victim-shop.myshopify.com"` and the attacker-controlled body `B`, even though this webhook never originated from Shopify for that shop.
