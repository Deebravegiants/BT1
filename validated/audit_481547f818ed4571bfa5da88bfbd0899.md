## Title
Webhook shop-domain header is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` is documented to "verify the request did indeed come from Shopify" before invoking the app's handler with a `WebhookMetadata` struct that includes a `shop` field described as "The shop domain of the webhook". In reality, the HMAC signature only covers the raw request body, not the `shop-domain` header, so the `shop` value handed to the app's handler is unauthenticated and attacker-controllable while the request is still reported as "verified".

### Finding Description
The identity binding that should hold is:
`hmac_valid(request) == true` should imply `request.shop` is the shop that Shopify actually sent the webhook for.

`Utils::HmacValidator.validate` computes the signature only from `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` returns only the raw HTTP body: [2](#0-1) 

The `shop`, `topic`, and `webhook_id` values are all read straight from HTTP headers and are not part of the signed payload: [3](#0-2) 

`Registry.process` validates only the HMAC and then trusts `request.shop` for dispatch to the handler: [4](#0-3) 

So an attacker who has ever received (or can capture) one legitimately-signed raw body + HMAC pair for a given topic (e.g., by installing the target app on their own store and triggering an event, since the body/HMAC pair for a fixed topic body is otherwise independent of which shop it names) can replay that exact `raw_body` + `shopify-hmac-sha256` header to the app's public webhook endpoint while substituting an arbitrary `shopify-shop-domain` header. `HmacValidator.validate` still succeeds, because it never inspects the shop header, and `Registry.process` calls the handler with `WebhookMetadata.new(shop: request.shop, ...)` where `shop` is the attacker-forged value.

This breaks the exact equality the gem's own documentation implies:
`Registry.process` "verifies the request did indeed come from Shopify" == "the `shop` field in the resulting `WebhookMetadata` is authentic," which is false — only the body's authenticity is proven, not the shop attribution.

### Impact Explanation
This is a cross-tenant identity confusion: the shop domain reaching the app's handler is not bound to the cryptographic proof the gem provides, allowing an unprivileged attacker (who only needs the ability to install/operate the target app on any shop and to POST to the app's public webhook route) to make the host app believe body content originated from a different (victim) shop. Host applications that key persistence, authorization, or side effects (e.g., `perform_later(shop_domain: data.shop, ...)`, exactly as shown in the gem's own webhook usage docs) off `data.shop` without independent verification will attribute attacker data to another tenant — a cross-tenant access primitive stemming directly from this gem's verification contract.

### Likelihood Explanation
Exploitation requires only: (1) the ability to send arbitrary HTTP requests to the app's public webhook endpoint (no credentials needed), and (2) possession of one legitimately-signed `(raw_body, hmac)` pair for the topic being targeted, which an attacker can obtain by simply installing the app on their own Shopify store (a free, unprivileged action) and triggering the relevant event themselves. No access token, `client_secret`, or other privileged credential is required, and the HMAC check as implemented always passes for a replayed body regardless of the shop header, since the header is never part of the signable string.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook-id`) header values into the signed/verifiable payload, or independently verify that the shop asserted in the header matches a shop for which the webhook topic was actually registered (e.g., cross-check against stored per-shop webhook registrations) before constructing `WebhookMetadata`. At minimum, update `VerifiableQuery#to_signable_string` for webhook requests to incorporate the header fields it does not currently cover, so `HmacValidator.validate` fails for header-mismatched replays.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook (e.g. `orders/create`), capturing Shopify's request: `raw_body = B`, header `shopify-hmac-sha256 = H` (valid HMAC of `B` with the app's `client_secret`), and `shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker POSTs to the same app's webhook endpoint with the same body `B` and same `shopify-hmac-sha256: H`, but sets `shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...shop-domain: "victim-shop.myshopify.com", hmac: H...})` is constructed; `to_signable_string` returns `B` only: [5](#0-4) 
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` and matches `H`, returning `true`: [6](#0-5) 
5. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ...)`, i.e., verified-looking data falsely attributed to the victim shop, matching the documented but unenforced contract at `docs/usage/webhooks.md` lines 12-14, 125.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
