### Title
Removing a state machine from `HostParams.stateMachines` does not clear its `_latestStateMachineHeight` entry, allowing continued consensus acceptance - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.updateHostParamsInternal()` replaces the whitelist of supported state machines (`_hostParams.stateMachines`) but only ever *adds* new entries to the `_latestStateMachineHeight` mapping; it never resets/deletes the entry for a state machine that governance removes from the new list. This is the same bug class as the reported `AggregateStablePrice.remove_price_pair()` issue: a per-item side-mapping is left stale after the parent list entry is "removed," and other logic keys off that stale mapping as its source of truth for whether the item is still active.

### Finding Description
`HostParams.stateMachines` is the whitelist of state machine IDs whose consensus-verified state is accepted by this host [1](#0-0) . When governance calls `updateHostParams` → `updateHostParamsInternal`, the function overwrites `_hostParams.stateMachines = params.stateMachines` and then only *initializes* `_latestStateMachineHeight` for IDs present in the new list — it never zeroes out the mapping entry for an ID that was in the old list but is absent from the new one: [2](#0-1) 

Elsewhere in the codebase, `latestStateMachineHeight(id) == 0` is the documented/used signal that "the state machine is unsupported" [3](#0-2) . `HandlerV2.handleConsensus` relies exactly on this non-zero check to decide whether to accept and persist a new state machine commitment coming from a relayed consensus proof: [4](#0-3) 

Because the removed state machine's `_latestStateMachineHeight[id]` entry is never cleared, it remains non-zero after removal, so `handleConsensus` keeps treating that state machine as supported and keeps storing new `StateCommitment`s for it whenever the underlying consensus client's `verify()` returns intermediate states for that ID.

### Impact Explanation
Governance's `remove`-by-omission (dropping an ID from `params.stateMachines`) is a security control meant to de-whitelist a state machine — e.g., after it is deemed compromised, forked, or otherwise untrustworthy. Because the stale `_latestStateMachineHeight` entry survives, any relayer can still call `handleConsensus` to push new state commitments for the "removed" state machine, and `handlePostRequests`/`handleGetResponses`/timeout handlers will subsequently accept proofs rooted in those newly stored commitments (`host.stateMachineCommitment(...)`, `stateMachineCommitmentUpdateTime(...)`) with no additional gating on `_hostParams.stateMachines` membership [5](#0-4) . This effectively defeats the de-whitelisting action: messages/state from a supposedly removed chain can continue to be delivered and trusted, which can be leveraged for forged message delivery or unsound state acceptance from a chain governance intended to cut off.

### Likelihood Explanation
Any relayer can trigger the vulnerable path simply by submitting a valid consensus proof via `handleConsensus` (a permissionless, unprivileged entrypoint) for a state machine that was previously whitelisted and later removed via `updateHostParams`. No additional privilege is required beyond normal relaying activity, and the only precondition is that governance has, at some point, called `updateHostParams` with a `stateMachines` list that omits a previously-supported ID — a realistic and expected governance action (e.g., during a security incident).

### Recommendation
In `updateHostParamsInternal`, compute the set difference between the old `_hostParams.stateMachines` and the new `params.stateMachines`, and explicitly reset `_latestStateMachineHeight[id]` (and any other per-state-machine metadata, e.g. cached commitments) to `0` for every ID that is no longer present, mirroring the existing "initialize new entries" loop [6](#0-5) .

### Proof of Concept
1. Deploy `EvmHost` with `HostParams.stateMachines = [A, B]`; both get `_latestStateMachineHeight[A] = 1` and `_latestStateMachineHeight[B] = 1`.
2. Governance calls `updateHostParams` with `stateMachines = [A]` only (removing `B`) via the `hostManager` path [7](#0-6) .
3. `_hostParams.stateMachines` now excludes `B`, but `_latestStateMachineHeight[B]` remains `1` (unchanged, since the loop at lines 638-644 only touches IDs in the new list).
4. A relayer submits a consensus proof to `HandlerV2.handleConsensus` containing an `IntermediateState` for `B` with `height > 1`. Since `host.latestStateMachineHeight(B) != 0`, the check at line 159 passes and `storeStateMachineCommitment` is called, persisting a new commitment for the "removed" chain `B`.
5. The relayer then submits `handlePostRequests`/`handleGetResponses` proofs rooted at this new commitment for `B`; they are accepted because `stateMachineCommitment` for `B`'s new height exists and no `_hostParams.stateMachines` membership check exists in `HandlerV2`, demonstrating that the de-whitelisting had no effect.
