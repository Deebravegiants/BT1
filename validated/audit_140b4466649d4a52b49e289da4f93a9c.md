### Title
Webhook shop/topic identity not bound to HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook's authenticity solely by checking the HMAC over the raw request body, but the `shop`, `topic`, `webhook_id`, and `api_version` values used to route and attribute the webhook are read directly from unauthenticated HTTP headers and are never covered by that HMAC. This breaks the intended binding: "shop the HMAC authenticates" == "shop the handler acts on".

### Finding Description
`Registry.process` performs exactly one authenticity check:
```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
``` [1](#0-0) 

`HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string`, and `Webhooks::Request#to_signable_string` returns only `@raw_body`:
```ruby
sig { override.returns(String) }
def to_signable_string
  @raw_body
end
``` [2](#0-1) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from HTTP headers, with no cryptographic tie to the body or its HMAC:
```ruby
def shop
  T.cast(shopify_header("shop-domain"), String)
end
``` [3](#0-2) [4](#0-3) 

The equality the gem implicitly promises is: `shop authenticated by HMAC == shop the handler receives`. In reality, the HMAC only authenticates `raw_body` bytes; `shop`/`topic`/`webhook_id` are attacker-controllable headers on any raw HTTP request reaching the app's webhook endpoint. As long as the attacker can present a `raw_body` + HMAC pair that is valid for *some* shop (e.g., their own shop, on which they are a legitimately installed low-privilege merchant receiving genuine webhooks), they can pair that same signed body with a different `x-shopify-shop-domain` (and/or `x-shopify-topic`) header value, and `HmacValidator.validate` will still pass, since it only checks the body bytes against the shared `api_secret_key`.

The gem's own documentation confirms host apps are expected to trust `data.shop` post-verification without any additional binding:
```
- `shop`, `String` - The shop domain of the webhook
``` [5](#0-4) 
```ruby
def handle(data:)
  puts "Received webhook! topic: #{data.topic} shop: #{data.shop} ..."
  perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
end
``` [6](#0-5) 

This is the exact analog of the reported bug class: a field (`shop`) that is acted on (used as the tenant key passed to the handler / downstream persistence) is not covered by the integrity check (HMAC), so the value verified (body bytes) and the value trusted (header-derived shop) diverge.

### Impact Explanation
Any merchant who has installed the app on their own shop (an unprivileged, low-trust actor relative to other tenants) can capture one legitimately-signed webhook body/HMAC pair sent to their own shop, then replay it to the app's public webhook endpoint with the `x-shopify-shop-domain` header changed to a victim shop's domain (and/or the `x-shopify-topic` header changed, e.g. to `shop/redact` or `customers/redact`). Since `Registry.process` never checks that the signed body corresponds to the claimed shop or topic, the handler executes attacker-chosen data under an arbitrary victim shop identity. Depending on the host app's handler logic, this enables cross-tenant data injection/corruption (e.g., writing fabricated order/customer data attributed to a shop the attacker doesn't own) or triggering compliance/data-deletion workflows (`shop/redact`, `customers/redact`) against a victim's data — a cross-tenant impact.

### Likelihood Explanation
Likelihood is moderate-to-high for apps that install this gem's webhook processing as documented: the attacker only needs their own (real, low-privilege) installation to obtain valid signed payloads, and standard HTTP tooling to replay the request with modified headers to the app's public webhook endpoint. No access to `api_secret_key`, tokens, or any other tenant's credentials is required.

### Recommendation
- Include `shop`, `topic`, and `webhook_id` in the value that is HMAC-verified (or otherwise cryptographically bind them to the signed body), rather than trusting header values independently of the signature.
- At minimum, cross-check the header-provided `shop` against a shop the caller is known to be authorized for (e.g., an active session or a shop already registered for that specific webhook subscription) before invoking the handler.
- Document this trust boundary explicitly so host apps know `data.shop` is not itself authenticated by the HMAC check.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` (a normal, unprivileged app installation) and receives a genuine webhook for `orders/create`, capturing:
   - raw body `B`
   - header `x-shopify-hmac-sha256: H` (valid HMAC of `B` under `api_secret_key`)
2. Attacker sends a POST to the app's webhook endpoint with the same body `B` and header `x-shopify-hmac-sha256: H`, but sets:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - (optionally) `x-shopify-topic: customers/redact`
3. `Utils::HmacValidator.validate` succeeds because it only checks `B` against `H`:
```ruby
def validate_signature(verifiable_query, secret)
  received_signature = verifiable_query.hmac
  computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
  OpenSSL.secure_compare(computed_signature, T.must(received_signature))
end
``` [7](#0-6) 
4. `Registry.process` builds `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and dispatches it to the host app's handler, which acts on `victim-shop.myshopify.com` using attacker-supplied body content — a cross-tenant action the attacker was never authorized to perform.
