## Title
Webhook shop-domain and topic identity not bound to the HMAC signature, allowing cross-tenant webhook replay - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop`, `topic`, and `webhook_id` are read straight from HTTP headers that are never included in the HMAC-signed bytes. `Registry.process` validates the HMAC and then dispatches the handler using these unsigned header values, so the identity of "which shop this webhook is for" is not actually bound to the cryptographic proof that Shopify sent it.

### Finding Description
`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string`, and for webhooks that string is just `@raw_body`: [1](#0-0) 

The `shop`, `topic`, and `webhook_id` accessors are pulled from headers that sit entirely outside the signed payload: [2](#0-1) 

`Registry.process` trusts these header-derived values once the HMAC over the body passes: [3](#0-2) 

`HmacValidator.validate_signature` only proves the body bytes were HMAC'd with the app's secret; it says nothing about which shop-domain/topic header accompanied those bytes: [4](#0-3) 

This breaks the intended identity binding: `HMAC(body) == HMAC(body)` is verified, but the equality that actually matters for tenant isolation — `shop_header == shop_that_produced_this_signed_body` — is never checked. An unprivileged actor who can install the target app on their own store (or otherwise obtain any one validly-signed webhook payload/HMAC pair for an in-scope topic with an identical or attacker-controlled JSON body) can resend that exact `raw_body` + `x-shopify-hmac-sha256` to the app's public webhook endpoint while substituting `x-shopify-shop-domain` (and/or `x-shopify-topic`) for a different, victim shop. The signature still validates because the signature never covered those headers, and the host app's handler receives `WebhookMetadata` claiming the payload came from the victim shop.

### Impact Explanation
This is a cross-tenant boundary break: the gem allows webhook data whose cryptographic authenticity was established for shop A to be attributed to shop B purely by manipulating an unsigned header. Depending on the webhook topic the host app registers (e.g. `app/uninstalled`, `shop/update`, `customers/redact`, `orders/*`), this can be used to trigger shop-scoped side effects (data deletion, resyncs, uninstall handling, billing state changes) against a shop the attacker does not control, without ever needing the app's `api_secret_key`, an access token, or any credential belonging to the victim.

### Likelihood Explanation
Exploitation only requires the ability to obtain one legitimately-signed webhook (trivial for anyone who can install the app on their own development/test store, which is normal, unprivileged access) and knowledge of the app's public webhook endpoint URL, which is not secret. No interception of victim traffic or secret material is needed, making this practically reachable by any external actor who can install the app.

### Recommendation
Include the shop domain, topic, and webhook id in the bytes that are HMAC-verified (or otherwise cryptographically bind them, e.g. by deriving them only from a signed source), so that `Registry.process` cannot dispatch header-controlled identity fields that fall outside the signature's coverage. At minimum, `to_signable_string` should incorporate `shopify_header("shop-domain")` and `shopify_header("topic")` alongside the raw body, and `HmacValidator` callers should reject requests where these headers were altered post-signing.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com` and trigger any subscribed webhook topic (e.g. `app/uninstalled`) so Shopify sends a legitimately HMAC-signed request:
   - headers: `x-shopify-topic: app/uninstalled`, `x-shopify-hmac-sha256: <valid>`, `x-shopify-shop-domain: attacker.myshopify.com`, body `B`.
2. Capture `B` and the valid `x-shopify-hmac-sha256` value (computed over `B` with the app's real secret by Shopify — attacker never needs the secret itself).
3. Replay a POST to the victim app's public webhook endpoint with the same body `B` and same `x-shopify-hmac-sha256`, but set `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate` in `Registry.process` succeeds because it only checks `B` against the HMAC (`lib/shopify_api/webhooks/request.rb:35-38`, `lib/shopify_api/utils/hmac_validator.rb:26-31`), and the handler is invoked with `WebhookMetadata` claiming `shop: "victim.myshopify.com"` (`lib/shopify_api/webhooks/registry.rb:198-199`), triggering shop-scoped app logic for a shop the attacker does not own.
