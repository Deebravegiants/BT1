Based on my research, I found an important finding: the shared `CallDispatcher` contract at `evm/src/utils/CallDispatcher.sol` has an unrestricted, permissionless `dispatch` function with no access control and no caller/source verification whatsoever.## Finding: Shared, permissionless `CallDispatcher` executes arbitrary calls with no caller or source verification

### Title
Permissionless `CallDispatcher.dispatch` allows theft of tokens/ETH left in the shared dispatcher between transactions - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
The report's core lesson — a contract that executes cross-chain-triggered actions must verify *who* is instructing it before moving value — is violated by `CallDispatcher`, the shared execution utility used by `HyperFungibleToken`, `WrappedHyperFungibleToken`, `IntentGatewayV2`/`ExtrinsicIntents`, and their upgradeable variants. Unlike every `onAccept` handler in this codebase (which the search confirms consistently checks `request.source`/`request.from` against a registered peer, e.g. `HyperFungibleToken.onAccept` at [1](#0-0) ), `CallDispatcher.dispatch` itself has **no access control and no verification of the caller at all**: [2](#0-1) 

### Finding Description
`CallDispatcher` is deployed once per chain and shared across all apps that need to execute attacker/solver-supplied `Call[]` payloads (HFT bridging calldata, IntentGatewayV2 predispatch/postdispatch calldata). Any address — not just the HFT/IntentGateway contracts that are supposed to be its only legitimate callers — can call `dispatch(bytes)` directly, because the function has no modifier, no `msg.sender` allowlist, and no linkage back to a verified ISMP source or an authenticated order.

The apps that call it rely on a temporal assumption: they transfer tokens/ETH into the `CallDispatcher` immediately before calling `dispatch`, and sweep whatever is left immediately after (see `IntentsBase._execute` sweeping "dust" back after `ICallDispatcher(dispatcher).dispatch(...)`, [3](#0-2) , and the HFT calldata flow that mints tokens "to" the dispatcher then calls `dispatch`, [4](#0-3) ). Because `CallDispatcher` is a single shared, stateless, permissionless executor, any balance it is holding at any block — whether from an in-flight HFT mint, an IntentGatewayV2 predispatch swap, or unswept dust left by a previous fill — is exposed to anyone who can front-run/back-run with their own `dispatch()` call before the legitimate sweep executes. Since `Call.to` requires only that the target has code (`NotContract` check), and `dispatch` forwards arbitrary `data`/`value` to any contract, an attacker can drain any ERC-20/ETH balance sitting in the dispatcher, or misuse any stale `approve()` that a prior legitimate `Call[]` left set on the dispatcher (documented as a known risk: *"Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution."* — [5](#0-4) ). This is structurally the same root cause as the report: a contract that acts on arbitrary instructions with no verification of who issued them, combined with residual balances/allowances left behind by a caller that assumed only it could reach the execution surface.

### Impact Explanation
Any value transiently held by `CallDispatcher` — minted HFT tokens en route to a swap, unwrapped native ETH from `WrappedHyperFungibleToken`'s WETH mode, predispatch/postdispatch swap proceeds in `IntentGatewayV2`, or leftover allowances from a prior `Call[]` — is reachable by an unprivileged third party who simply calls `dispatch()` in the same block window, since the mainnet deployment is one single `CallDispatcher` address shared by all of IntentGatewayV2, HyperFungibleToken and WrappedHyperFungibleToken across every chain (see deployed addresses, [6](#0-5) ). This can result in theft of bridged funds or solver/order collateral that transiently passes through the dispatcher.

### Likelihood Explanation
Medium: it requires either (a) a mempool race to intercept a legitimate `Call[]` execution window (front-running the sweep with the attacker's own `dispatch()` call targeting the same token), or (b) exploiting a leftover unlimited/unswept approval from a misconfigured integrator (explicitly acknowledged as a risk in the docs). Because `CallDispatcher` is a single, permanently-deployed, permissionless shared resource across all apps and all chains, the attack surface is persistent rather than one-off.

### Recommendation
Restrict `CallDispatcher.dispatch` to a caller allowlist (e.g., an `onlyAuthorizedCaller` modifier checking `msg.sender` against the set of HFT/WrappedHFT/IntentGatewayV2 instances that are permitted to use it), or deploy per-app dispatcher instances instead of one shared singleton, so that an unprivileged party cannot invoke arbitrary calls against balances/allowances the dispatcher happens to be holding. At minimum, enforce that all token approvals granted to the dispatcher are single-use/exact-amount and revoked after every `dispatch()` call, and consider using `nonReentrant`/single-transaction guarantees (e.g., requiring `dispatch` to be called only via a delegatecall-free trusted forwarder) to close the front-running window described above.

### Proof of Concept
1. A relayer delivers an HFT cross-chain transfer whose `Message.to` is the shared `CallDispatcher` address and whose `Message.data` encodes a `Call[]` that approves a Uniswap router for the full minted amount, then swaps.
2. `HyperFungibleToken.onAccept` mints tokens to the `CallDispatcher` and calls `ICallDispatcher(_dispatcher).dispatch(message.data)` ( [4](#0-3) ).
3. Because `CallDispatcher.dispatch` ( [2](#0-1) ) is callable by anyone, an attacker who observes the mint in the mempool/same block submits their own `dispatch()` call that spends the dispatcher's now-non-zero token balance (or exploits the unswept approval left after execution) before or interleaved with the intended swap, redirecting the tokens to themselves.

This finding could not be fully validated against a live/mainnet deployment or exact block-level ordering guarantees (e.g., whether the L2/L1 in question guarantees atomic single-block execution that would prevent the front-running window); this is noted as an open uncertainty requiring dynamic/mempool-level testing to confirm exploitability in production, beyond what static code review here can establish.

        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;

            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
