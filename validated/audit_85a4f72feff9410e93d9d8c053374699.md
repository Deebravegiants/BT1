Based on my investigation, I found a custody-relevant analog in `aptos_framework::multisig_account`'s timelock override mechanism, which mirrors the reported bug class: an admin-invoked parameter update silently mutates a security threshold without accounting for its effect on already-pending, partially-approved state.

### Title
Timelock bypass threshold is silently weakened as a side effect of unrelated owner-removal transactions, allowing premature execution of pending multisig transactions - (File: `aptos-move/framework/aptos-framework/sources/multisig_account.move`)

### Summary
`multisig_account.move` implements an optional `MultisigAccountTimeLock` with an `override_threshold`: transactions normally must wait `timelock_period` before execution, but if approvals reach `override_threshold`, they can execute immediately, bypassing the delay. This threshold is meant to require a supermajority of owners to consciously waive the waiting period. However, `update_owner_schema` — the shared internal function backing `remove_owners`, `swap_owners`, `remove_owner`, etc. — automatically clamps `override_threshold` down whenever the owner count shrinks below it, with no check on whether any pending transaction already has approvals equal to (or exceeding) the newly lowered threshold.

### Finding Description
In `update_owner_schema` [1](#0-0) , after owners are added/removed and the new owner count is validated, the code checks the optional timelock:

```
if (exists<MultisigAccountTimeLock>(multisig_address)) {
    let timelock = &mut MultisigAccountTimeLock[multisig_address];
    if (timelock.override_threshold.is_some() && timelock.override_threshold.borrow() > &num_owners) {
        timelock.override_threshold = option::some(num_owners);
        emit(TimelockUpdated { ... });
    };
    assert!(
        timelock.override_threshold.is_none() || timelock.override_threshold.borrow() > &multisig_account_ref_mut.num_signatures_required,
        error::invalid_state(EINVALID_TIMELOCK_OVERRIDE_THRESHOLD)
    );
};
```

This logic only preserves the invariant `override_threshold > num_signatures_required` — it never checks whether the *new, lower* `override_threshold` now matches or falls below the approval count of any existing pending transaction that had already collected partial approvals under the *old, higher* threshold. Because owner-removal transactions (`remove_owners`, `swap_owners`, etc.) only require the standard `num_signatures_required` approval count to execute — a much lower bar than `override_threshold` by design — the act of removing owners for an unrelated, legitimate reason can incidentally collapse the override threshold onto the approval count of a separate, currently timelocked, pending transaction. That other pending transaction then immediately becomes eligible for override-execution, skipping the deliberate waiting period the timelock was designed to enforce, purely as an unreviewed side effect.

This is the direct analog of the reported bug: `update_collateral_info`/`update_owner_schema` both permit an owner-driven config change that alters a bound (`max_slot` / `override_threshold`) without checking whether already-existing state (bids in the trimmed slots / pending transactions sitting at the old threshold) is invalidated or newly exposed by the change.

### Impact Explanation
If exploited (or triggered unintentionally), a transaction that owners intended to be delayed by the timelock (e.g., an auth-key rotation, a large fund transfer, or another sensitive multisig-controlled action) can be executed immediately once an unrelated owner-removal transaction happens to lower `override_threshold` to meet its already-collected approval count. Since multisig accounts commonly custody APT, fungible assets, or control resource/code-object ownership, this allows bypassing a deliberately configured custody safety delay, potentially enabling a malicious or compromised subset of owners to rush through a harmful transaction before other owners have a chance to react (the entire purpose of a timelock).

### Likelihood Explanation
This requires the timelock feature to be enabled and a multisig account with concurrent pending transactions (one owner-management transaction and one other sensitive transaction), which is a realistic operational pattern for teams managing owner rotation and asset movements. The clamping is unconditional and automatic on every owner-count-reducing action, so no special malicious intent is required to trigger it — the weakening is baked into the standard `update_owner_schema` path.

### Recommendation
Before clamping `override_threshold` downward, verify that no pending transaction's current approval count is at or above the new candidate `override_threshold` (or otherwise force re-validation / re-timelock of already-approved-but-not-yet-executed transactions when the threshold changes), similar to how the original report recommends checking existing bids before shrinking `max_slot`.

### Proof of Concept
1. Multisig account has 5 owners, `num_signatures_required = 2`, `override_threshold = 5` (requires all owners to bypass timelock).
2. Owner A creates transaction #1 (a sensitive fund transfer) and it collects 3 approvals — meets `num_signatures_required` but not `override_threshold`; it is subject to `timelock_period`.
3. Separately, owners create and approve transaction #2, `remove_owners`, dropping the owner count to 3 (only needs the 2-of-5 threshold, unrelated to timelock policy).
4. Transaction #2 executes via `update_owner_schema`, which sees `override_threshold (5) > num_owners (3)` and clamps `override_threshold` to 3.
5. Transaction #1 already has 3 approvals, which now equals the new `override_threshold`. It can be executed immediately as an override, bypassing the timelock delay that owners were relying on.

**Note on verification limits:** I could not, within the available tool budget, read the transaction-execution function (e.g., `execute_transaction`) that consumes `override_threshold` to confirm the exact comparison logic (`>=` vs `>`) used at execution time, nor confirm whether this `MultisigAccountTimeLock`/`override_threshold` feature is gated behind a feature flag that might mitigate real-world exposure. This should be verified against `aptos-move/framework/aptos-framework/sources/multisig_account.move` (the execution/approval-counting functions) before treating this as fully confirmed.
