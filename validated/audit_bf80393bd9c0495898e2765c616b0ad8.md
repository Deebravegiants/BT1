### Title
Unauthenticated raw port strings reach `deserialize` before any RPC method routing, causing unhandled parse exceptions and attacker-forgeable "asset" type-confusion objects - ([File: libraries/browser-extension-rpc/src/index.js], [libraries/json-rpc/index.js], [libraries/domain-serialization/src/assets-serialization.js])

### Summary
`PortTransport` forwards every raw string received on a `chrome.runtime.Port` straight into `transport.emit('data', data)`, which is consumed both by `RPC._processResponse` (`this.parse(data)` = `deserialize(data)`) and by the optional `onData` hook (`deserialize(data)`) with no prior authentication, envelope validation, or method routing. Because `domain-serialization`'s `deserialize` dispatches purely on an attacker-visible `{"t": <type>, "v": <payload>}` tag, an attacker who can post strings on the port can (a) trigger unhandled exceptions in the JSON-RPC error path, and (b) directly invoke the `asset` deserializer with arbitrary `name`/`baseAssetName`/`feeAssetName` values without ever going through a legitimate `serialize()` call.

### Finding Description
`createRpc` wires the transport directly to `deserialize` for both the RPC channel and the optional side-channel: [1](#0-0) 

`PortTransport` is a thin relay: any string posted to `port.onMessage` is delivered unmodified to listeners, including `RPC`'s internal `_processResponse`: [2](#0-1) 

In `@exodus/sdk-rpc`, `deserialize` is passed straight through as the low-level `parse` function of `@exodus/json-rpc`: [3](#0-2) 

`@exodus/json-rpc`'s `_processResponse` calls `this.parse(data)` (i.e. attacker-controlled `deserialize`) before determining whether the payload is even a request or response: [4](#0-3) 

Two concrete issues follow from this:

1. **Unhandled exception on malformed (non-JSON) strings.** `domain-serialization`'s `deserialize` re-throws on `JSON.parse` failure: [5](#0-4) 
`_processResponse`'s `catch` block then does `JSON.parse(data).id` again on the same malformed string to look up a request id, which itself throws a second, uncaught `SyntaxError` that escapes the `catch` block entirely (line 112 of `libraries/json-rpc/index.js`). This is a robustness gap — the id-recovery path assumes `data` is at least valid JSON, which is not guaranteed for arbitrary attacker strings.

2. **Tag-driven dispatch with no serialize-side authentication.** `deserialize`/`serialize` route strictly by an embedded `t` tag (demonstrated by the `'{"t":"test","v":"test:hello"}'` shape in tests), and `deserializeAsset` for the UI process is wired to accept any `assetPayload` shape: [6](#0-5) 
`deserializeAssets`/`deserializePassOne`/`deserializePassTwo` build the resulting object from attacker-supplied `name`, `baseAssetName`, and `feeAssetName` fields and use them to look up entries in a locally-constructed `allAssets` map that layers the fake object over the real stored assets by name: [7](#0-6) 
An attacker who can post an arbitrary string of the form `{"t":"asset","v":{"name":"bitcoin","baseAssetName":"bitcoin","feeAssetName":"bitcoin",...}}` on the port causes this code to run and produce an object impersonating a real asset name entirely from attacker bytes, with no signature/HMAC binding the payload to a legitimate `serializeAsset` call.

However, sensitive operations (signing, address derivation, fee estimation) are exposed via `PROXIED_FUNCTION` markers and executed by calling back into the background process using the **asset name string**, resolved against the background's own trusted asset registry (`getAsset`/`assetsApi(assets[assetName], ...)` pattern), not the attacker's local fake object's contents. I could not find, within this repo, code that persists this attacker-forged object into a trusted store or uses its fields (rather than a background-verified name) for signing/key operations, so I cannot confirm escalation to unauthorized signing or secret disclosure from this code alone.

### Impact Explanation
Concretely demonstrable impact is (a) an unhandled parse exception reachable from any unprivileged party that can write arbitrary strings to the extension port (e.g. a compromised content-script relay), and (b) the ability to fabricate an "asset" object with attacker-chosen `name`/`baseAssetName`/`feeAssetName` fields that gets returned from `deserialize`/`onData` into UI-side code with no cryptographic binding to a real `serializeAsset` call — a genuine type-confusion primitive per the STORAGE_INTEGRITY/SECRET_ISOLATION invariant tested. This matches the "type confusion in wallet RPC leading to asset/account impersonation" scope named in the question. I could not verify, from the indexed code, that this forged object is subsequently trusted for signing or secret-bearing operations (those remain background-authoritative by asset-name lookup), so the confirmed impact should be treated as UI-local state corruption / minor denial-of-service rather than confirmed key/secret compromise.

### Likelihood Explanation
Precondition (attacker can post arbitrary strings on the connected port) is explicitly assumed valid per the prompt. Given that, the exploit requires no further privilege: `chrome.runtime.Port.onMessage` delivers the string directly to `PortTransport`'s listener with no origin check, no envelope schema check, and no HMAC/signature check before `deserialize` runs. The double-`JSON.parse` bug triggers on any single malformed string. The asset-impersonation object requires only well-formed JSON with a `t: "asset"` tag, which is trivial to construct.

### Recommendation
- In `libraries/json-rpc/index.js`, guard the id-recovery path in `_processResponse`'s `catch` block with its own `try/catch` so a second parse failure cannot escape unhandled.
- In `libraries/domain-serialization/src/index.js` / `assets-serialization.js`, do not dispatch to `deserializeAsset` purely by an untrusted `t` tag from raw wire data; validate that incoming asset payloads reference only asset names known to the receiving process's trusted asset registry before merging/overlaying, and reject/ignore unknown or self-referential `baseAssetName`/`feeAssetName` values that would let attacker-controlled entries shadow real ones in `allAssets`.
- Ensure any RPC/domain-serialization consumer that eventually performs signing or address/key derivation always resolves assets by cross-checking against the background's own trusted asset registry, never trusting fields embedded in a client-supplied deserialized asset object.

### Proof of Concept
Unit test outline for `libraries/json-rpc`:
```js
test('malformed non-JSON data does not throw uncaught from _processResponse', (t) => {
  const [client] = createPair()
  t.doesNotThrow(() => {
    client._transport.emit('data', 'not-json-at-all')
  })
})
```
Expected today: throws uncaught `SyntaxError` from the nested `JSON.parse(data).id` call — demonstrating the gap.

Fuzz/invariant test outline for `libraries/domain-serialization`:
```js
test('deserialize cannot forge a trusted asset via tag-only payload', () => {
  const ui = createUIDomainSerialization({ getStoredAssets: () => ({ bitcoin: realBitcoinAsset }), proxyFunction })
  const forged = '{"t":"asset","v":{"name":"bitcoin","baseAssetName":"bitcoin","feeAssetName":"bitcoin","units":{}}}'
  const result = ui.deserialize(forged)
  // Expected: should throw or be rejected because this payload never passed through serializeAsset
  // Actual: returns an object with result.name === 'bitcoin' built entirely from attacker-controlled fields
  expect(() => ui.deserialize(forged)).toThrow()
})
```
