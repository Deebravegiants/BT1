### Title
Unvalidated swap routes can graft a wallet-draining transfer onto the caller’s authorization - ([File: contracts/controller/src/strategies/swap.rs](contracts/controller/src/strategies/swap.rs))

### Summary
`swap_collateral`, and other controller strategies using `swap_tokens`, accept caller-controlled route bytes and forward them to the configured router without venue allowlisting or validation. [1](#0-0)  A crafted route can invoke an attacker-controlled hop that requests the strategy caller’s authorization for an unrelated token transfer. [2](#0-1) [3](#0-2)  The resulting Soroban authorization tree records that transfer as a child of the caller’s strategy invocation, so signing the simulated tree authorizes the theft. [4](#0-3) 

### Finding Description
`process_swap_collateral` authenticates `caller` and requires owner-or-delegate authority over `account_id`, but treats `swap` as opaque attacker-controlled input. [5](#0-4)  It then passes that input through `withdraw_and_swap_from_supply`. [6](#0-5) 

`swap_tokens` checks only that the swap bytes are non-empty, grants the configured router one controller-held input transfer, invokes `execute_strategy(controller, amount_in, swap)`, and subsequently checks input spend plus positive output. [7](#0-6)  Those measurements do not constrain which contracts the route invokes or which additional authorization requests those contracts make. [8](#0-7) 

The regression test demonstrates a router hop that performs the expected fair output while its attacker-selected pool calls `transfer(victim, attacker, amount)` on an unrelated token held by the victim. [9](#0-8) [10](#0-9)  An honest authorization tree rejects the hidden transfer, but a tree returned by simulation includes and authorizes it. [11](#0-10) [12](#0-11) 

### Impact Explanation
An unprivileged attacker can steal arbitrary token balances from a user who signs a crafted strategy transaction, even when that token is unrelated to the lending position. [13](#0-12)  The controller’s positive-output and solvency checks can still pass because the malicious leg performs the expected collateral swap in addition to the unrelated wallet transfer. [14](#0-13) 

### Likelihood Explanation
Exploitation requires the account owner or delegate to sign a transaction containing the crafted `swap` route and its poisoned authorization tree. [15](#0-14)  This matches the user-interaction prerequisite in the external bug class: the attacker supplies a malicious route through a quote, interface, or other route-delivery path, but cannot independently act on the victim’s account. [16](#0-15) 

### Recommendation
Do not permit opaque routes to invoke arbitrary venue contracts while operating under a user-authorized controller call. Enforce an allowlist of audited venue/pool contract addresses or otherwise bind each route to contracts that cannot request unrelated caller authorization. Client-side validation is also necessary but is not a sufficient protocol boundary because it cannot constrain a malicious or compromised route source.

### Proof of Concept
1. Attacker supplies a `swap` payload for `Controller.swap_collateral(caller, account_id, current, amount, new, swap)` where one route hop resolves to attacker-controlled code.
2. The victim must own or delegate `account_id`, so the victim signs the strategy call. [17](#0-16) 
3. The controller forwards `swap` to the router after authorizing only its own input-token transfer. [1](#0-0) 
4. The malicious hop calls `token.transfer(victim, attacker, victim_balance)` for an unrelated wallet token. [10](#0-9) 
5. Simulation adds that transfer as a child authorization under `swap_collateral`. [18](#0-17) 
6. If the victim signs that simulated tree, the unrelated token balance moves to the attacker while the expected strategy output is still deposited. [19](#0-18)
