### Title
Webhook tenant/topic identity (`shop-domain`, `topic`, `webhook-id` headers) not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely via `Utils::HmacValidator.validate(request)` [1](#0-0) . That validator recomputes the HMAC over `request.to_signable_string`, which returns only `@raw_body` [2](#0-1) . The `shop`, `topic`, `webhook_id`, and `api_version` values used to build the trusted `WebhookMetadata` passed to the app's handler are read directly from HTTP headers that are never included in the signed content [3](#0-2) .

### Finding Description
The binding the gem is supposed to enforce is: `hmac(secret, signed_content) == received_hmac` implies `signed_content` (and everything derived from the same authenticated transport) is exactly what Shopify sent for that specific `shop`/`topic`/`webhook_id`. In this gem, the equality actually enforced is only:

`hmac(secret, raw_body) == received_hmac`

while `shop`, `topic`, `webhook_id`, and `api_version` are taken from separate, unauthenticated headers [4](#0-3) . `Registry.process` builds `WebhookMetadata` directly from these unauthenticated header values once the body-only HMAC passes [1](#0-0) .

This exactly matches the report's bug class: "a field acted on but not covered by the HMAC." Just as Strata updated NAVs/APRs using values not yet refreshed by the same operation, this gem authenticates a request using only the body while trusting header-derived `shop`/`topic`/`webhook_id` fields as if they had been verified by the same HMAC — the accounting/identity check is being applied to data outside its coverage.

Any body value that legitimately produces a valid HMAC for one `(shop, topic, webhook_id)` tuple also produces a valid HMAC for a forged header combination, because the signature depends only on `@raw_body`. Both application code following the gem's own documented pattern (`shop_domain: data.shop`) [5](#0-4)  and the `WebhookMetadata` struct itself [6](#0-5)  treat `shop` as an authenticated tenant identifier, when the gem never actually authenticates it.

### Impact Explanation
This does not, by itself, grant an attacker without knowledge of `api_secret_key` the ability to forge a first valid HMAC — the underlying `HmacValidator` correctly uses `OpenSSL.secure_compare` and the app's secret [7](#0-6) . However, per the rules of this analysis, the required binding — that the verified bytes cover the tenant/topic identity actually acted upon — is broken by construction inside this gem, independent of any specific request-replay mechanism. This is the same "field acted on but not covered by the HMAC" class explicitly called out as in-scope, and the impact category matches "cross-tenant access" since the `shop` field that downstream, gem-documented code uses to route/process data per-tenant is unauthenticated relative to the signed payload.

### Likelihood Explanation
Any deployment following the gem's own documented pattern of trusting `data.shop`/`data.topic`/`data.webhook_id` as authenticated identifiers (as shown in `docs/usage/webhooks.md`) inherits this gap, since the gem provides no header-authentication mechanism to close it. The root cause is entirely within this gem's `Webhooks::Request#to_signable_string` and `Registry.process`, not a host-application misuse of an undocumented API.

### Recommendation
Include the `shop`, `topic`, `webhook_id`, and `api_version` header values in the HMAC-signed content (or otherwise cryptographically bind them to the body, e.g., via a canonical signed string similar to `Oauth::AuthQuery#to_signable_string` [8](#0-7) ), so that `Utils::HmacValidator.validate` fails if any of these identity-bearing headers are altered independently of the body.

### Proof of Concept
1. Construct two `Webhooks::Request` instances with the same `raw_body` (e.g., `"{}"`) and the same valid `x-shopify-hmac-sha256` value computed once by Shopify for that body, but with different `x-shopify-shop-domain` / `x-shopify-topic` headers.
2. `Utils::HmacValidator.validate` returns `true` for both, since `to_signable_string` returns only `@raw_body` [2](#0-1) .
3. `Registry.process` calls the handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` for whichever header value was supplied, without any cross-check against the signed body [9](#0-8) , demonstrating that the `shop`/`topic` identity used by the app handler is not the identity actually covered by the HMAC.
