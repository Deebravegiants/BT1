## Finding

### Title
Webhook shop/topic attribution is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its verifiable HMAC signature over the raw request body only, while the `shop`, `topic`, `api_version`, and `webhook_id` values used by `ShopifyAPI::Webhooks::Registry.process` to attribute and route the event are read directly from HTTP headers that are excluded from the signed content. Anyone who can obtain one genuine, validly-signed webhook body (e.g., a merchant with the app installed on their own store) can resend that exact body to the app's public webhook endpoint with an arbitrary `X-Shopify-Shop-Domain` header, and the signature will still validate — even though the resulting event is now falsely attributed to a different shop.

### Finding Description
The identity binding that should hold is: `hmac == HMAC(secret, bytes_the_app_will_act_on)`. In `Request`, `to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `shop`, `topic`, `webhook_id`, and `api_version` — the fields the app actually acts on — are pulled straight from headers that are never part of the signed bytes: [2](#0-1) 

`HmacValidator.validate` only verifies `verifiable_query.hmac` against `verifiable_query.to_signable_string` (i.e., the body), and returns a boolean with no binding to headers: [3](#0-2) 

`Registry.process` trusts this boolean result and then dispatches using the unauthenticated `request.shop` and `request.topic` values directly to the handler: [4](#0-3) 

Since all shops installed under the same app share one `api_secret_key`, a merchant with the app on their own store legitimately receives a webhook with a valid `hmac` computed over a body they can capture in full. Because the shop attribution is not part of the signed bytes, that same signature+body pair remains valid if replayed to the app's public webhook endpoint with the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header changed to point at a different shop. The equality the app relies on — "the shop whose secret validated this HMAC" equals "the shop this data will be attributed to" — is broken: the HMAC only proves knowledge of the shared app secret and the body's integrity; it proves nothing about which shop the header claims to be.

### Impact Explanation
This breaks the tenant boundary the webhook signature is meant to enforce. Any host application that keys per-shop data storage/updates off `WebhookMetadata#shop` (which is the documented and expected pattern — see `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))`) can be made to apply another shop's genuine webhook payload under an attacker-chosen shop identity. Depending on the topic, this enables cross-tenant data injection/corruption (e.g., an `orders/create` or `app/uninstalled` payload attributed to a victim shop), which falls under "cross-tenant access."

### Likelihood Explanation
Likelihood is significant for any Shopify Partner-style app where multiple merchants install the same app (sharing one `api_secret_key`). Obtaining a single real webhook (body + valid signature) requires nothing more than operating one's own store with the app installed — no privileged access, leaked secret, or credential theft is needed. Crafting the forged request (same body, same HMAC header, different shop-domain header) is trivial once captured.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the value that is HMAC-verified, or independently authenticate the shop domain against the app's own session store before trusting `request.shop`/`request.topic` for dispatch — e.g., require the host application to confirm the shop exists in its installed-shops table (matching Shopify's own webhook-handling guidance) rather than relying solely on `HmacValidator.validate` to vouch for header-derived identity fields.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com`.
2. Capture a legitimately delivered webhook: raw body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC_SHA256(api_secret_key, B)`.
3. POST the exact same body `B` and header `H` to the app's public webhook endpoint, but replace `X-Shopify-Shop-Domain` with `victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses this into a request whose `hmac` matches `H`; `HmacValidator.validate` returns `true` because it only checks `B` against `H`. [5](#0-4) 
5. `Registry.process` invokes the app's handler with `shop: "victim.myshopify.com"` and the attacker's original body content, even though the data never originated from `victim.myshopify.com`. [4](#0-3)
