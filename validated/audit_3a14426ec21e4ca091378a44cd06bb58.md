### Title
Webhook `shop` (and other header) fields are trusted but not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook as authenticated once `Utils::HmacValidator.validate(request)` succeeds, but that validation only covers the raw request body. The `shop`, `topic`, `api_version`, and `webhook_id` values — all read straight from HTTP headers — are never part of the HMAC-signed material, yet they are handed to the host application as trusted, tenant-identifying data.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

and `HmacValidator.validate_signature` computes/compares the HMAC solely over that signable string: [2](#0-1) 

`Registry.process` gates on this HMAC check and then constructs `WebhookMetadata` directly from the unauthenticated header accessors (`request.topic`, `request.shop`, `request.webhook_id`, `request.api_version`): [3](#0-2) 

`request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` are all pulled from `shopify_header(...)`, i.e. plain HTTP headers with no cryptographic binding to the signed body: [4](#0-3) [5](#0-4) 

The identity binding the host application relies on is effectively:
`shop_used_by_handler == shop_header_value`, when it should be `shop_used_by_handler == shop_cryptographically_bound_to(raw_body, api_secret_key)`. Because the HMAC secret (`api_secret_key`) is shared across every shop that installs the app, any request whose body+HMAC pair was legitimately produced by Shopify for one shop can be replayed with the `X-Shopify-Shop-Domain` (and `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header swapped to a different shop, and `Registry.process` will still accept it as valid and dispatch it to the handler tagged with the attacker-chosen shop.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook processing: `Registry.process` is the sole authentication gate host apps use before trusting webhook payloads, and it allows the `shop` field — the tenant key — to be forged independently of the signed content. A host application that persists or acts on webhook data keyed by `WebhookMetadata#shop` can be made to associate one shop's real webhook data with another shop record, which is a cross-tenant integrity issue.

### Likelihood Explanation
Exploitation only requires the ability to send arbitrary HTTP requests to the app's public webhook endpoint plus one legitimately-signed body+HMAC pair (obtainable by installing the app on any shop and capturing a real webhook delivery, or by triggering any Shopify webhook to one's own store). No access to `api_secret_key` or any privileged credential is required, and the header can be freely modified by any client since it isn't covered by the signature check.

### Recommendation
Bind the header-derived identity fields cryptographically. Options: include the relevant headers (shop domain, topic) in the value that is HMAC-verified (Shopify's docs support verifying against the full raw request including headers only via the body's HMAC, so the safer fix is architectural), or require host applications/`Registry.process` to cross-check `request.shop` against the shop the app's webhook subscription was registered for, or reject/flag any mismatch between the header-derived shop and any shop identifier embeddable in the JSON body when available. At minimum, document clearly that `request.shop`/`request.topic` are not authenticated by the HMAC check and must not be used as a sole tenant-identity source by host applications.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; trigger any webhook (e.g. `orders/create`) so Shopify sends a legitimately HMAC-signed POST to the app's public webhook endpoint.
2. Capture the raw body and `X-Shopify-Hmac-Sha256` value from that request.
3. Replay the identical body and HMAC header to the same endpoint, but set `X-Shopify-Shop-Domain: victim.myshopify.com` (and optionally change `X-Shopify-Topic`).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` (`lib/shopify_api/webhooks/registry.rb:190`), which only checks the raw body against the shared `api_secret_key` — the forged header passes unchanged.
5. `handler.handle` is invoked with `WebhookMetadata#shop == "victim.myshopify.com"` (`lib/shopify_api/webhooks/registry.rb:198-199`), even though that data actually originated from `attacker.myshopify.com`, demonstrating the shop-tenant confusion.
