### Title
Webhook `shop`/`topic`/`webhook_id` headers are trusted for tenant identification but are not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by verifying an HMAC over the raw request body, yet the shop-identifying header (`shop`) that the host application is told to trust and act on is never included in that signature.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) . `ShopifyAPI::Utils::HmacValidator.validate` computes and compares the HMAC exclusively over `verifiable_query.to_signable_string`: [2](#0-1) . `Registry.process` gates handler execution on that same HMAC check and then builds `WebhookMetadata` directly from unauthenticated headers (`request.shop`, `request.topic`, `request.webhook_id`, `request.api_version`): [3](#0-2) . Those header accessors simply read `shopify-shop-domain`/`shopify-topic`/etc. with no cryptographic binding to the signed body: [4](#0-3) .

The equality that should hold but does not: `shop used by the handler to key tenant data == shop authenticated by the HMAC`. In reality the HMAC only proves `raw_body` is unmodified/genuinely signed by the app's secret; it proves nothing about which shop, topic, or webhook the body belongs to.

The gem's own documentation instructs developers to treat `data.shop` as trustworthy for routing tenant-scoped work (`perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), reinforcing that the "shop" header is meant to be relied upon: [5](#0-4) . The same documentation claims `process` "will verify the request did indeed come from Shopify," which is only true for the body content, not for the shop/topic attribution: [6](#0-5) .

### Impact Explanation
Because any app is installed on multiple/arbitrary shops (including a shop the attacker legitimately controls), an attacker can install the target app on their own store to receive a genuinely-signed webhook (valid body + HMAC), then replay that exact body/HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) header with an arbitrary value of their choosing, including another merchant's shop domain. The HMAC check still passes (it only re-validates the untouched body), and `Registry.process` will dispatch to the handler with `data.shop` set to the attacker-chosen domain. Any host application that follows the documented pattern of using `data.shop` to select which tenant's database row/webhook job to update will process attacker-controlled body content under a victim shop's identity — a cross-tenant data-integrity/confusion vulnerability.

### Likelihood Explanation
Requires only: (1) the ability to install the target app on a shop the attacker controls (any unprivileged internet user with a Shopify dev/test store can do this), and (2) the ability to POST a modified HTTP request to the app's public webhook endpoint. No access token, `client_secret`, or privileged account is needed.

### Recommendation
Include the shop domain, topic, and webhook id in the signable payload (e.g., canonicalize `shop|topic|webhook_id|raw_body` and HMAC that string), or otherwise cryptographically bind these header values to the verified body before constructing `WebhookMetadata`. At minimum, `Registry.process` should independently confirm that `request.shop` corresponds to a shop with an active session/installation before dispatching, rather than trusting the header outright.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com`, triggering a legitimate webhook, e.g. `orders/create`, with body `B` and header `x-shopify-hmac-sha256: H = HMAC(secret, B)`.
2. Attacker captures the raw POST request (body `B`, header `H`) sent to the app's webhook endpoint.
3. Attacker resends the identical body `B` and header `H` to the same endpoint, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com` (and optionally `x-shopify-topic`/`x-shopify-webhook-id`).
4. `HmacValidator.validate` in `Registry.process` recomputes the HMAC over `B` only — [7](#0-6)  — which matches `H`, so validation succeeds.
5. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the host app to process attacker-controlled data as belonging to `victim-shop.myshopify.com`.
