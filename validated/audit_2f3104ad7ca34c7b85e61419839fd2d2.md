This confirms the core mechanism. The `ShopifyAPI::Webhooks::Request#shop` (used as the tenant identifier passed to app handlers via `WebhookMetadata.shop`) is read from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, while the HMAC signature only covers the raw request body (`to_signable_string` returns `@raw_body`).

### Title
Webhook tenant identity (`shop-domain` header) is not bound by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, then trusts the unsigned `shop-domain` header as the tenant identity delivered to the app's handler. Because the HMAC never covers the shop header, any party capable of producing a request with a valid body+HMAC pair for the shared app secret can freely relabel that payload as belonging to any other shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read directly from an HTTP header that is not part of the signed material: [2](#0-1) 

`Registry.process` validates the HMAC (over the body only) and then immediately trusts `request.shop` as the tenant identity forwarded to the app-supplied handler: [3](#0-2) 

`HmacValidator.validate` computes the signature purely from `to_signable_string` (the body), never incorporating the shop header: [4](#0-3) 

Since the same `api_secret_key` is shared across every shop that has installed the app, an HMAC value that is valid for one shop's webhook body is *also* valid for that identical body claimed under a different `shop-domain` header — the signature check cannot distinguish tenants. The documented handler contract explicitly treats `data.shop` as the authoritative tenant identifier used to route/attribute the webhook body to app-side per-merchant storage: [5](#0-4) 

The binding that is broken, stated as an equality that should hold but does not:
`shop authenticated by HMAC` ≠ `shop used as the session/tenant key passed to the handler`.
Before the request: the attacker (a legitimate merchant who installed the app on their own shop, hence able to receive genuinely-signed webhooks addressed to themselves) has one valid `(raw_body, hmac)` pair for their own shop. After the request: the attacker resends that same `(raw_body, hmac)` pair to the app's webhook endpoint but substitutes the `shop-domain` header with a victim shop's domain. `HmacValidator.validate` still returns `true` because it only checks `raw_body` against the shared secret; `Registry.process` then calls the handler with `WebhookMetadata.shop` set to the victim's domain while the `body` is fully attacker-chosen content from the attacker's own legitimately-signed webhook.

### Impact Explanation
This breaks the app-level assumption that webhook data are correctly attributed to the tenant (shop) they came from. Any app built on this gem that uses `data.shop` from the webhook handler as a lookup/write key into per-shop state (as the documented example does: `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) can have attacker-controlled body content written into another merchant's tenant context — a cross-tenant data-integrity/confusion issue, without needing the app's `client_secret`, an access token, or any privileged account; only participation as an ordinary installed merchant (or interception/replay of one's own legitimate webhook) is required.

### Likelihood Explanation
Any merchant who installs the app (an ordinary, unprivileged action) automatically receives genuinely HMAC-signed webhooks for their own shop and can capture the `(raw_body, hmac)` pair from any webhook topic. Replaying it against the shared webhook endpoint with a forged `shop-domain` header requires no cryptographic material beyond what a normal installer already possesses, making this a directly reachable network exploit through the gem's own `Registry.process`/`Request` contract, not a misuse of the host app's documented API.

### Recommendation
Bind the tenant identity into the signed material, or otherwise cryptographically bind `shop-domain` to the payload before trusting it: e.g., include the `shop-domain` (and `webhook-id`/`topic`) header values in `to_signable_string`, or independently verify that the `shop-domain` header corresponds to a shop for which this specific webhook subscription (`webhook_id`) was registered before invoking the handler.

### Proof of Concept
1. Merchant A installs the app; the app registers a webhook (e.g. `orders/create`) and receives a legitimate request with headers `x-shopify-shop-domain: shop-a.myshopify.com`, `x-shopify-hmac-sha256: <valid-hmac-of-body>`, and some `raw_body`.
2. Merchant A captures this exact `raw_body` and `x-shopify-hmac-sha256` value.
3. Merchant A sends a new HTTP request to the app's webhook endpoint with the identical `raw_body` and `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: shop-b.myshopify.com` (a victim shop).
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:190`) validates the HMAC successfully (it only checks the body) and calls `handler.handle(data: WebhookMetadata.new(shop: "shop-b.myshopify.com", body: <attacker-chosen body>, ...))`, causing the app to process attacker-controlled data as if it originated from Merchant B's shop.
