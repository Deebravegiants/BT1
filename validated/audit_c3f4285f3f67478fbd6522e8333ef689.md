Audit Report

## Title
Unsafe `int64`→`uint` cast in WebAPI Gateway staleness check allows message replay bypass - (File: core/services/gateway/handlers/capabilities/handler.go)

## Summary
`HandleLegacyUserMessage` casts a client-controlled, signed `int64` `Timestamp` field to `uint` before comparing it against the current time to detect stale/replayed messages. A negative timestamp wraps around to a very large unsigned value on the cast, causing the staleness check to always evaluate as "fresh," permanently bypassing anti-replay protection for this message type.

## Finding Description
`webapicap.TriggerRequestPayload.Timestamp` is defined as `int64` and populated straight from attacker-supplied JSON via `json.Unmarshal`/custom `UnmarshalJSON`, with no sign or range validation. In `HandleLegacyUserMessage`, the only pre-cast check is `payload.Timestamp == 0`; negative values pass through untouched. The comparison `uint(time.Now().Unix())-h.config.MaxAllowedMessageAgeSec > uint(payload.Timestamp)` casts the signed value to `uint`, and the `//nolint:gosec // G115` comment shows the unsafe conversion was consciously silenced instead of fixed. A negative `Timestamp` (e.g., `-1`) wraps to a value near `2^64-1`, which is always greater than the left-hand side, so the "stale message" branch never triggers. Immediately afterward, with only a TODO noting missing allowlist/rate-limiting, the request is forwarded to all DON members via `don.SendToNode`.

## Impact Explanation
An unprivileged client reaching the Gateway's public/user-facing endpoint can forge a `web_api_trigger` request with a negative `timestamp`, defeating the freshness/anti-replay gate designed to reject old or replayed signed messages. Combined with the absent allowlist/rate-limiting at this stage, this permits unauthorized repeated triggering of workflow execution on DON nodes — an in-scope "unauthorized job run" / gateway request impersonation-adjacent impact.

## Likelihood Explanation
Exploitation requires only sending a JSON payload with a negative `timestamp` field, no special credentials or roles are needed beyond reaching the Gateway's user message endpoint, making this trivially and repeatably exploitable.

## Recommendation
Validate `payload.Timestamp > 0` (in addition to the existing `== 0` check) before use, and perform the staleness comparison with signed `int64` arithmetic instead of casting to `uint`:
```go
now := time.Now().Unix()
if payload.Timestamp <= 0 || now-payload.Timestamp > int64(h.config.MaxAllowedMessageAgeSec) {
    // reject
}
```
Remove the `//nolint:gosec` suppression once fixed.

## Proof of Concept
1. Craft a `web_api_trigger` JSON-RPC message to the Gateway's user endpoint with `payload.timestamp = -1`.
2. Observe `HandleLegacyUserMessage` at `core/services/gateway/handlers/capabilities/handler.go:372` computes `uint(-1) = 18446744073709551615`, which is always `> uint(time.Now().Unix()) - MaxAllowedMessageAgeSec`, so the "stale message" branch is skipped.
3. Observe the request proceeds past the staleness check to `don.SendToNode` calls at lines 416-419, forwarding the (potentially replayed/old) request to all DON nodes regardless of true age.
4. A Go unit test asserting `HandleLegacyUserMessage` returns a stale-message error for `Timestamp: -1` would currently fail, confirming the bypass.
