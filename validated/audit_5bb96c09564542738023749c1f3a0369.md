### Title
Front-running of vesting-claim `dest` account blocks legitimate victim's later claim via `VestedBalanceExists` - (File: polkadot/runtime/common/src/claims/mod.rs)

### Summary
`Pallet::process_claim` only checks `T::VestingSchedule::vesting_balance(&dest).is_some()` to decide whether a vesting-schedule claim can be applied to `dest`, but `dest` is an arbitrary, caller-chosen `AccountId` that is never bound to the calling Ethereum signer's identity beyond the ECDSA signature over that specific `dest` value. Any holder of any valid Ethereum-claim key (even a dust claim with a vesting schedule attached) can sign a message for an arbitrary `dest = X` and call `claim`/`claim_attest` first, installing a vesting lock on `X` via `T::VestingSchedule::add_vesting_schedule`, which permanently blocks any subsequent, unrelated vesting claim from a different Ethereum signer intending to use the same `dest`.

### Finding Description
`process_claim` at [1](#0-0)  performs:

```
let vesting = Vesting::<T>::get(&signer);
if let Some(_) = vesting {
    if T::VestingSchedule::vesting_balance(&dest).is_some() {
        return Err(Error::<T>::VestedBalanceExists.into());
    }
    ...
}
...
if let Some(vs) = vesting {
    T::VestingSchedule::add_vesting_schedule(&dest, vs.0, vs.1, vs.2)
        .map_err(|_| Error::<T>::VestedBalanceExists)?;
}
```

`dest` is supplied directly by the caller in `claim`/`claim_attest` [2](#0-1) [3](#0-2) , and the only binding to `dest` is that the Ethereum signature must be produced over the ASCII-hex encoding of that specific `dest` value [4](#0-3) . Since the attacker controls their own Ethereum private key, they can freely sign an arbitrary `dest` of their choosing — including a `dest` they know or suspect the victim intends to use for their own (unrelated) claim.

The `vesting_balance(&dest).is_some()` guard is a check on the *account*, not on any relationship between the claim being processed and prior claims to that account. It only prevents the same `dest` from having two vesting schedules installed — it does not, and structurally cannot, verify that the party installing the first vesting schedule has any legitimate claim to control that `dest`. Because `claim`/`claim_attest` are unsigned extrinsics (`ensure_none(origin)`) validated only via ECDSA recovery [5](#0-4) , there is no proxy/multisig/origin check that ties `dest` usage to a specific claimant; any account holding any valid claims-map entry with an associated vesting schedule can race to install a lock on any `dest`.

Exploit flow:
1. Attacker holds (or purchases/receives) a valid, possibly tiny, Ethereum claim entry in `Claims`/`Vesting` storage, mapped to attacker's own Ethereum key.
2. Attacker signs `dest = X` (the account the victim plans to later use) with their own Ethereum key and submits `claim(dest = X, sig)`.
3. `process_claim` finds `Vesting::<T>::get(&attacker_signer)` is `Some`, checks `vesting_balance(&X).is_some()` → `false` (fresh account) → proceeds, deposits attacker's balance to `X`, and calls `add_vesting_schedule(&X, ...)`, which succeeds and installs a vesting lock on `X`.
4. Victim later submits `claim(dest = X, victim_sig)` for their own, larger, unrelated vesting claim. `process_claim` now finds `vesting_balance(&X).is_some()` → `true` (attacker's lock) → returns `Error::VestedBalanceExists`, permanently rejecting the victim's legitimate claim to `X`.

The victim's claim itself (`Claims::<T>` entry keyed by their Ethereum address) is untouched and not consumed, so it is not stolen outright — but the victim cannot use `dest = X` for it. The victim's only path to release funds is to attempt the claim to a different destination account.

### Impact Explanation
This is a denial-of-service/griefing against a specific `dest` account choice, not fund theft or permanent fund loss: the victim's underlying claim (keyed by their Ethereum address in `Claims`/`Vesting` storage) is not deleted or reassigned by the attacker's action, and the victim can still successfully claim to a *different* destination account since `process_claim` and the check are scoped per-`dest`. Therefore the "permanent denial-of-claim / fund freeze" framing in the prompt is only accurate if the victim is somehow forced to use exactly that one `dest` (e.g. an off-chain/exchange deposit account they cannot change) — a real but narrower scenario than an unconditional freeze of the victim's Ethereum-address claim itself.

### Likelihood Explanation
Feasibility is high in principle: any attacker with a valid vesting-claim entry (even for a negligible amount) and knowledge of the victim's intended `dest` can race an unsigned `claim`/`claim_attest` transaction ahead of the victim's transaction, since these calls are unsigned and require no special privilege, proxy approval, nonce ordering relative to the victim, or on-chain state about the victim. The only precondition is that the attacker must actually control an Ethereum key with a vesting-flagged claim already registered in `Claims`/`Vesting` (via genesis config or `mint_claim` by root) — the attacker cannot fabricate such an entry themselves, but per the prompt's stated precondition this is assumed to hold ("attacker holds any valid Ethereum claim ... mapped to their own Ethereum key"). Given that, front-running is deterministic and repeatable against any predictable `dest`.

### Recommendation
- Do not let `process_claim` treat "any pre-existing vesting lock on `dest`" as an unconditional error caused by an unrelated party; consider tracking which Ethereum claim installed the vesting schedule on a given `dest`, or restrict `dest` for vesting-schedule claims to require the destination account be newly created / not already touched by an unrelated claim.
- Alternatively/additionally, document (and, if desired, enforce at the wallet/UX layer) that `dest` accounts used for vesting claims should be unique per claim and not shared/predictable, since the current on-chain design intentionally allows any Ethereum key holder to choose an arbitrary `dest`.
- A stronger structural fix would be to key the "already has vesting schedule" check against the specific claim/signer rather than solely against the destination account state, or to require `dest` to not have received funds from a different, previously-processed claim before allowing a second vesting claim to succeed with a clear, distinguishable error path (rather than reusing `VestedBalanceExists` for both "self already vested" and "different claimant's vesting occupies this account").

### Proof of Concept
Rust unit test in `polkadot/runtime/common/src/claims/tests.rs` (using existing test scaffolding, e.g. `alice()`, `bob()` keys and a new attacker key/index, following the pattern of existing tests in that file [6](#0-5) ):

1. In `new_test_ext`/genesis config, register:
   - Attacker's Ethereum address with a small `Claims` amount and a `Vesting` schedule.
   - Alice's Ethereum address (existing test fixture) with a larger `Claims` amount and a `Vesting` schedule.
2. Call `Claims::claim(RuntimeOrigin::none(), 42, attacker_sig_over_dest_42)` — assert `Ok(())`, and assert `Vesting::vesting_balance(&42).is_some()` is now `true`.
3. Call `Claims::claim(RuntimeOrigin::none(), 42, alice_sig_over_dest_42)` — assert it returns `Err(Error::<Test>::VestedBalanceExists)`.
4. Assert Alice's original `Claims`/`Vesting` entries (keyed by her Ethereum address) are unchanged/still present, confirming she can still claim to a different `dest` (e.g. `Claims::claim(RuntimeOrigin::none(), 43, alice_sig_over_dest_43)` succeeds), demonstrating the scoped-to-`dest` DoS rather than total fund loss.

	fn process_claim(signer: EthereumAddress, dest: T::AccountId) -> sp_runtime::DispatchResult {
		let balance_due = Claims::<T>::get(&signer).ok_or(Error::<T>::SignerHasNoClaim)?;

		let new_total =
			Total::<T>::get().checked_sub(&balance_due).ok_or(Error::<T>::PotUnderflow)?;

		let vesting = Vesting::<T>::get(&signer);
		if let Some(_) = vesting {
			if T::VestingSchedule::vesting_balance(&dest).is_some() {
				return Err(Error::<T>::VestedBalanceExists.into());
			}

			// A vesting schedule installs a balance lock, which requires the account to stay alive,
			// otherwise it is dusted and the lock placed on a non-existent account. The `dest` may
			// already hold funds, so a small claim that tops an existing account over the ED is
			// valid.
			let free_after = CurrencyOf::<T>::free_balance(&dest).saturating_add(balance_due);
			ensure!(
				free_after >= CurrencyOf::<T>::minimum_balance(),
				Error::<T>::ClaimBelowExistentialDeposit,
			);
		}

		// We first need to deposit the balance to ensure that the account exists.
		let _ = CurrencyOf::<T>::deposit_creating(&dest, balance_due);

		// Check if this claim should have a vesting schedule.
		if let Some(vs) = vesting {
			// This can only fail if the account already has a vesting schedule or its balance is
			// below the existential deposit, both of which are checked above.
			T::VestingSchedule::add_vesting_schedule(&dest, vs.0, vs.1, vs.2)
				.map_err(|_| Error::<T>::VestedBalanceExists)?;
		}
