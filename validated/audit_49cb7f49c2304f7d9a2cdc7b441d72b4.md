### Title
Deposit/mint functions in the zTokenized vaults allow minting shares to the vault's own contract address, permanently freezing the depositor's principal - (File: `mainnet/contracts/vault/v0-vault-stx.clar` and sibling vaults `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`)

### Summary
The vault contracts implement a self-transfer guard in `transfer` but omit the equivalent check in `deposit` (and `redeem`'s `recipient` argument), letting a caller mint `zft` shares to the vault's own contract principal with no way to ever redeem them.

### Finding Description
`transfer` explicitly rejects sending shares to the vault itself: [1](#0-0) 

`deposit`, however, takes a user-supplied `recipient` principal and mints `zft` directly to it with no validation that `recipient` is not `current-contract` (or any other address the caller cannot subsequently act as `contract-caller` for): [2](#0-1) 

`redeem` derives the burning account from `contract-caller`, and it burns/repays based on the caller's own balance — a contract can never make itself `contract-caller` in a transaction it did not initiate, so any `zft` balance sitting on the vault's own principal is permanently unredeemable: [3](#0-2) 

This is the exact bug class from the report (missing zero/invalid-address validation on an address parameter used for minting/transfer), analogous here as a missing self-address check on the `recipient` parameter of `deposit`.

### Impact Explanation
If `recipient` is set (by mistake or by a buggy integrating contract) to the vault contract's own address, `receive-underlying` still pulls in the depositor's real underlying assets and `assets` is incremented correctly, but the corresponding `zft` shares are minted to an address that can never call `redeem` to claim them. The depositor's principal is irrecoverably locked — the code base has no sweep/rescue function for stray token balances (verified: no `sweep`, `recover-tokens`, or `rescue` functions exist in the vault contracts). This is a permanent freezing of user funds, matching the required Critical/High impact bar.

### Likelihood Explanation
Any external caller invoking `deposit` (directly, or indirectly through `market.clar`'s `borrow`/`repay`/`vault-redeem` wiring, or through a third-party integration that forwards a wrong `recipient`) can trigger this by simply passing the vault's own contract principal as `recipient`. No special privilege is required, and the existing self-check in `transfer` shows the vault authors were already aware of this exact hazard for one function but did not apply the same guard consistently to `deposit`.

### Recommendation
Add the same self-address guard used in `transfer` to `deposit` (and to `redeem`'s `recipient`, and `system-borrow`'s `receiver`):
```
(asserts! (not (is-eq current-contract recipient)) ERR-TOKENIZED-VAULT-PRECONDITIONS)
```
Apply this consistently across all vault contracts (`v0-vault-stx`, `v0-vault-sbtc`, `v0-vault-ststx`, `v0-vault-ststxbtc`, `v0-vault-usdc`, `v0-vault-usdh`).

### Proof of Concept
1. User calls `(contract-call? .v0-vault-stx deposit u1000000 u0 .v0-vault-stx)` — passing the vault's own contract principal as `recipient`.
2. `receive-underlying` transfers 1,000,000 STX-equivalent underlying from the user into the vault; `assets` is incremented; `ft-mint? zft inkind .v0-vault-stx` mints shares to the vault contract itself.
3. No principal can ever call `redeem` as `contract-caller` equal to `.v0-vault-stx` (a contract cannot originate a transaction as itself), so the minted shares — and the underlying value they represent — are permanently stranded, and the depositor cannot recover the deposited funds.
