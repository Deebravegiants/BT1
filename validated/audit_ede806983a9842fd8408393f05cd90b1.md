### Title
`Webhooks::Registry.process` accepts forged `topic`/`shop`/`webhook-id`/`api-version` headers on any legitimately-signed body, treating unsigned metadata as authenticated - ([File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates the request solely via `Utils::HmacValidator.validate(request)`, which HMACs `request.to_signable_string`. For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` [1](#0-0) . The `topic`, `shop`, `webhook_id`, and `api_version` values that `process` reads from headers and hands to the handler are never part of the signed string [2](#0-1) , so any attacker who possesses one valid `(body, hmac)` pair can replay it with arbitrary `topic`/`shop`/`webhook-id`/`api-version` headers and have `process` dispatch it as if it were an authentic webhook for the forged topic/shop.

### Finding Description
The broken binding: the code implicitly assumes
`HmacValidator.validate(request) == true` implies `(request.topic, request.shop, request.webhook_id, request.api_version)` are authentic values sent by Shopify for this exact webhook event.
In reality, `HmacValidator.validate` only proves
`HMAC(secret, request.to_signable_string) == request.hmac`, and `to_signable_string == @raw_body` [3](#0-2) . None of `topic`, `shop`, `webhook_id`, `api_version` (all read from headers via `shopify_header`) are included in that signable string [2](#0-1) [4](#0-3) .

`Registry.process` uses `request.topic` to look up the handler in `@registry` and forwards `request.topic`, `request.shop`, `request.api_version`, `request.webhook_id` straight into `WebhookMetadata`, which is what the handler receives and trusts [5](#0-4) . The gem's own documentation tells developers that `process` "will verify the request did indeed come from Shopify," encouraging handlers to trust `data.shop`/`data.topic` [6](#0-5) .

Exploit flow: an unprivileged attacker creates their own development shop, installs the app, and registers a webhook endpoint they control on their own server (permitted per the rules). Shopify sends them a genuine, validly signed webhook `(raw_body B, X-Shopify-Hmac-Sha256 = HMAC(secret, B))` for some topic on their own shop. The attacker now has a `(B, HMAC)` pair that is valid for *any* topic/shop combination, because the signature never covered those fields. They then send a direct HTTP POST to the target app's public webhook route with body `B`, the same valid `hmac-sha256` header, but attacker-chosen `x-shopify-topic` (any topic registered in the app, e.g. `shop/redact` or `app/uninstalled`) and `x-shopify-shop-domain` (the victim merchant's domain). `HmacValidator.validate` passes because it only checks `B` against the secret [7](#0-6) , and `process` dispatches to the handler for the forged topic with `WebhookMetadata.shop` set to the victim's domain [8](#0-7) .

Existing guards do not stop this: `HmacValidator.validate` only checks the HMAC over the body [9](#0-8) ; there is no comparison of `request.shop` against any known/registered shop, and no binding of `webhook_id`/`topic` to the signed payload. The GraphQL-interpolation concern raised in the question (`topic.gsub(%r{/|\.}, "_").upcase` in `get_webhook_id`/`unregister`) is a separate, unrelated code path invoked by the developer with a static topic string, not by `process`, so it does not apply to this entry point [10](#0-9) .

### Impact Explanation
Any handler that branches on `data.topic` or uses `data.shop` to select which merchant's data to act on (e.g. GDPR redaction on `shop/redact`, deprovisioning on `app/uninstalled`, updating cached order/product state keyed by `data.shop`) can be triggered for an arbitrary victim shop domain string using only a webhook the attacker legitimately received for their own shop. This is a cross-tenant authentication bypass: a forged/replayed request is accepted by `process` as an authentic webhook for a shop and topic the signature never attested to. It is repeatable per attacker-controlled webhook sample and works against any shop domain string the attacker chooses to put in the header, matching the Critical "authentication bypass" category.

### Likelihood Explanation
Preconditions: the app must register at least one HTTP webhook handler that trusts `data.shop` and/or dispatches purely on `data.topic` (the documented and intended usage pattern) [11](#0-10) . Attacker cost is low: install the app on a shop they control, capture one real webhook delivery, then replay it directly to the app's public webhook endpoint with modified headers — no secret, session, or credential is required. This is fully repeatable and does not depend on timing or race conditions.

### Recommendation
Bind the metadata to the signature, or independently authenticate it: either (a) have Shopify's signed payload include topic/shop (not controllable by this gem, since Shopify computes the HMAC), so instead the gem should treat `request.shop` and `request.topic` as untrusted metadata and require host apps to cross-check `request.shop` against a known/installed shop list before trusting `WebhookMetadata`, or (b) explicitly document in `process`/`docs/usage/webhooks.md` that only the body is authenticated, and that `data.shop`/`data.topic`/`data.webhook_id` are not covered by the HMAC and must be revalidated by the app (e.g., against its own shop/session store) before being used for any privileged action. At minimum, correct the doc claim in `docs/usage/webhooks.md` line ~125 that `process` "verif[ies] the request did indeed come from Shopify" without qualifying that only the raw body is verified.

        # under a different topic/shop than the one Shopify actually signed for.
        forged_headers = {
          "x-shopify-topic" => @victim_topic,          # attacker-chosen, unsigned
          "x-shopify-hmac-sha256" => @valid_hmac,       # valid only for @raw_body
          "x-shopify-shop-domain" => @victim_shop,      # attacker-chosen, unsigned
        }

        forged_request = ShopifyAPI::Webhooks::Request.new(raw_body: @raw_body, headers: forged_headers)

        # HMAC validation passes (body is genuinely signed)...
        assert(ShopifyAPI::Utils::HmacValidator.validate(forged_request))

        # ...and process() dispatches to the victim-topic handler with the
        # forged shop, even though the attacker never received a webhook
        # for @victim_topic / @victim_shop.
        ShopifyAPI::Webhooks::Registry.process(forged_request)

## Create a Webhook Handler

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
