### Title
Webhook HMAC only covers the request body, not the `shop-domain`/`topic` headers, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies a webhook's authenticity solely via an HMAC computed over the raw request body [1](#0-0) . The `shop-domain`, `topic`, and `webhook-id` values that the handler subsequently trusts as the identity of the sending shop are taken from unauthenticated HTTP headers that are never included in the HMAC computation [2](#0-1) . The equality the gem implicitly claims to enforce — "the shop that produced this authenticated body" == "the shop reported in `request.shop`" — is never actually checked.

### Finding Description
`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string`, and for `Webhooks::Request` that method returns only `@raw_body`: [3](#0-2) 

The `shop`, `topic`, `api_version`, and `webhook_id` accessors are all pulled straight from HTTP headers with no cryptographic binding to the signed body: [4](#0-3) 

`Registry.process` validates the HMAC and then constructs `WebhookMetadata` directly from these unauthenticated header values, handing them to the app's handler as trusted facts: [5](#0-4) 

Because the HMAC secret (`Context.api_secret_key` / `client_secret`) is per-app, not per-shop, any store that installs the app receives real webhooks signed with the same secret used for every other store on that app. An attacker who has installed the app on their own store therefore possesses a batch of (raw_body, valid-HMAC) pairs signed with the app's shared secret. Since the `shop-domain` header is outside the signed material, the attacker can resend that exact raw body and HMAC to the app's webhook endpoint while substituting the `shopify-shop-domain` header for a victim shop. `HmacValidator.validate` still passes (it never looks at headers), and `Registry.process` calls the handler with `shop: <victim-shop>` — the attacker's data is delivered under the victim's identity.

The gem's own documentation states that `Registry.process` "will verify the request did indeed come from Shopify," encouraging host apps to trust `data.shop` unconditionally, as shown in the documented example handler that keys work off `data.shop` without additional checks: [6](#0-5) 

### Impact Explanation
This breaks the tenant-isolation equality "HMAC-authenticated payload" == "attributed shop", letting one merchant's install inject webhook events (order data, customer data, product changes, etc.) that the host app processes as if they originated from a different merchant's store — a cross-tenant data-integrity/confidentiality violation, which the rules classify as Critical impact.

### Likelihood Explanation
Requires only that the attacker be able to install the target app on any store (a normal, unprivileged action for public apps) to obtain valid signed webhook bodies, plus the ability to send an HTTP POST with attacker-chosen headers to the app's known webhook callback URL. No access token, `client_secret`, or privileged account is needed — the HMAC secret is shared across all installs of the app, and the header spoofing requires nothing beyond basic HTTP tooling.

### Recommendation
Bind the shop identity into the signed material actually verified, e.g. include `shop-domain` (and ideally `topic`/`webhook-id`) in the string that `Webhooks::Request#to_signable_string` returns, or independently verify that the shop reported in the header is one your app has an active, matching webhook registration/session for before dispatching to the handler. At minimum, document explicitly that host apps must not trust `data.shop`/`data.topic` without separately correlating them against known installed shops.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and triggers any subscribed event (e.g. `orders/create`) to receive a legitimate webhook POST with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(client_secret, B)`.
2. Attacker replays this exact request to the app's webhook endpoint but changes only the header `x-shopify-shop-domain` to `victim-shop.myshopify.com` (and optionally `x-shopify-topic`).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `request.to_signable_string` (`= B`, unchanged) and compares to `H` — validation succeeds because the shop header was never part of the signed data: [7](#0-6) 
4. `Registry.process` invokes the registered handler with `WebhookMetadata.new(topic: request.topic, shop: "victim-shop.myshopify.com", body: ..., ...)`, causing the host app to record/act on attacker-controlled data attributed to the victim shop.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
