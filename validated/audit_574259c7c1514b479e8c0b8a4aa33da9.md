### Title
Signup declared successful and reported to app/backend before Tier 1/2 personal-custody-package uploads complete or are silently dropped - (File: src/plans/mod.rs)

### Summary
In `MainVault`/`XChainController` (Derby), `rebalance()` could be invoked based on a "funds received" acknowledgement (`pushFeedbackToVault()` → `receiveFunds()`) that arrives out of order/asynchronously relative to the actual fund transfer (`xTransfer()`), allowing state to advance before the underlying data actually arrived. The analogous pattern in `orb-core` is in the signup completion flow in `src/plans/mod.rs`: the biometric enrollment result (success/failure) is finalized and reported to the backend, dbus, and the operator's App (`SignupEnded` relay message) while the Tier 1/Tier 2 Personal Custody Package (PCP) uploads — which contain sensitive iris/face biometric data — are merely enqueued to an independent, asynchronous background agent (`data_uploader::Agent`) without waiting for their actual completion.

### Finding Description
`Plan::do_signup()` builds the PCP packages and uploads Tier 0 synchronously via `upload_pcp_tier_0()`, which blocks and retries until success/failure is known [1](#0-0) . However, for `pcp_version >= 3`, Tier 1 and Tier 2 packages are merely pushed onto the `data_uploader` agent's input port and the code immediately continues — there is no wait for these uploads to succeed or fail [2](#0-1) .

Immediately afterward, `enroll_user`/`report_signup_reason` determine `result.success`, and `after_signup()` uploads the debug report and, in self-serve mode, sends a `SignupEnded` message to the App declaring success/failure and DBus emits `signup_finished` [3](#0-2) . None of this waits on the Tier 1/Tier 2 upload completion.

The only synchronization point is `data_uploader::wait_queues()`, which only blocks if the upload queues are already past a *blocking threshold* (backpressure), not to confirm actual delivery of a specific PCP tier1/tier2 payload [4](#0-3) [5](#0-4) .

Inside `data_uploader::Agent::run()`, tier queues can silently drop the oldest queued PCP once a per-tier *dropping threshold* is reached, with only a fire-and-forget upload retry loop that gives up permanently on any client-error HTTP status [6](#0-5) [7](#0-6) . In other words, the signup's success/completion state — analogous to the vault's `rebalance()` being permitted before `xTransfer()` funds truly land — is asserted and propagated to the backend/app/dbus before the corresponding asynchronous "transfer" (tier1/tier2 biometric data upload) is confirmed to have arrived, and that transfer can fail or be dropped entirely without ever correcting the already-reported success state.

### Impact Explanation
This is analogous to the referenced bug class ("state advances based on an out-of-order/unconfirmed cross-channel signal") but the concrete unprivileged-user impact here is data-integrity/availability related to biometric retention rather than fund loss: the Orb can report a signup as `Success` to the backend enrollment record, to the operator App (`SignupEnded{success:true}`), and via DBus (`signup_finished(true)`), while the Tier 1/Tier 2 self-custody biometric packages (containing iris-code and face embeddings needed for eventual user self-custody/export) never actually reach the backend — either due to network failure exhausting retries with a client error, or due to the queue's drop-oldest backpressure policy silently discarding a pending upload under load. The signup is already recorded as complete/successful and the user has moved on, so this loss is undetectable and unrecoverable to the user at signup time.

### Likelihood Explanation
Likelihood is moderate: the tier1/tier2 send only fails silently in specific conditions — sustained client-error responses (e.g., presigned URL expiry, malformed request) or heavy load triggering the configured dropping threshold in `data_uploader.rs`. This does not require a malicious actor; it is a legitimate unprivileged-user code path (every self-serve/pcp_v3 signup), triggered purely by network/timing conditions, matching the requirement to keep only unprivileged-user analogs in biometric upload/retention.

### Recommendation
Before finalizing signup success/reporting `SignupEnded`/`signup_finished`, await explicit per-package completion acknowledgements for Tier 1/Tier 2 uploads (not just queue backpressure via `wait_queues()`), and reconcile/retry indefinitely (or mark the signup provisionally incomplete) if tier1/tier2 uploads ultimately fail or are dropped, rather than allowing the "dropping threshold" to silently discard biometric data after success has already been reported.

### Proof of Concept
1. Configure `pcp_tier1_dropping_threshold`/`pcp_tier2_dropping_threshold` low relative to signup throughput, or simulate a backend that returns a 4xx status for the presigned-URL/multipart upload of tier1/tier2 PCPs.
2. Run a self-serve signup with `pcp_v3` enabled; `build_pcp()` succeeds and `data_uploader::Input::Pcp` messages for tier1/tier2 are sent (`src/plans/mod.rs:613-636`).
3. `data_uploader::Agent::upload_pcp()` hits a client-error and `break`s out of the retry loop without surfacing failure to the signup plan (`src/agents/data_uploader.rs:195-213`), or the queue drops the oldest pending PCP entirely once `dropping_thresholds[i]` is hit (`src/agents/data_uploader.rs:143-145`).
4. Meanwhile `do_signup()`/`after_signup()` proceed unaffected, reporting `success:true` via `SignupEnded` and `signup_finished` (`src/plans/mod.rs:1463-1497`), even though the tier1/tier2 biometric package never reached the backend.

Note: I was unable to fully trace the numeric default values of `pcp_tier1_dropping_threshold`/`pcp_tier2_dropping_threshold` in `src/config.rs` within the available tool budget, so the exact conditions under which drop-oldest triggers in production configuration remain unverified.
