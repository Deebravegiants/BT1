### Title
Unprivileged lamport top-ups to a stake account can force artificial delegation increases during epoch-reward distribution - (File: `runtime/src/inflation_rewards/mod.rs`)

### Summary
`redeem_stake_rewards` in `runtime/src/inflation_rewards/mod.rs` calls `delegation_may_need_adjustment`, which decides whether a stake account's tracked `delegation.stake` should be bumped up during partitioned epoch-reward distribution based on the account's raw lamport balance (`current_lamports`) rather than solely on values that flowed through the stake program's controlled delegate/deposit path. [1](#0-0)  Because Solana allows anyone to credit lamports to any account via an ordinary System Program transfer (the analog of a forced `selfdestruct` ETH transfer — no cooperation or signature from the recipient is required), an attacker or even the stake account owner can inflate the account's balance between epochs and cause the protocol to treat those lamports as legitimate delegated stake at distribution time, exactly mirroring the GenesisGroup pattern of trusting `address(this).balance` as a proxy for tracked accounting state.

### Finding Description
`delegation_may_need_adjustment` computes a `new_delegation` as `min(new_delegation_with_rewards, lamports_with_rewards.saturating_sub(minimum_lamports))` and returns whether this differs from `current_delegation`. [2](#0-1)  This is called from `redeem_stake_rewards` with `current_lamports.saturating_add(staker_rewards)` as `lamports_with_rewards`, and if the computed value differs from the currently tracked delegation, `stake.delegation.stake` is overwritten with `new_delegation_with_rewards`: [1](#0-0) 

The `current_lamports` parameter here is the actual lamport balance of the stake account at distribution time — not a value gated by the stake program's `Delegate`/`DeactivateDelegation`/deposit instructions. The test suite makes this explicit: it stores a stake account, then before distribution "transfers in more lamports" directly via `checked_add_lamports`/`store_account`, and shows that `distribute_epoch_rewards_in_partition` subsequently raises `post_stake_state.delegation().unwrap().stake` beyond what legitimate stake+reward accounting alone would produce. [3](#0-2) 

The docstring on `delegation_may_need_adjustment` itself acknowledges the underlying assumption: "The actual adjustment happens at distribution, to account for any lamports credited to the account during partitioned epoch rewards, before the distribution has occurred." [4](#0-3)  This assumes any lamports appearing on the account between epoch boundary and distribution time came from the protocol's own crediting process (e.g. partitioned epoch rewards not yet fully applied), but nothing in the checked code path restricts the source of those lamports — any unprivileged System Program `transfer` instruction targeting the stake account's pubkey achieves the same effect, exactly as a `selfdestruct` forcibly inflates a Solidity contract's `address(this).balance` outside of its intended deposit function (`purchase` in the Fei report).

### Impact Explanation
If an attacker (or the stake account owner, who has an even stronger incentive) transfers extra lamports into their own stake account after the reward-calculation snapshot for an epoch but before `distribute_epoch_rewards_in_partition` runs for that account's partition, `delegation_may_need_adjustment` will treat the inflated balance as evidence that more stake should have been delegated and will silently raise `stake.delegation.stake` to reflect it. This is not merely rewards bookkeeping error: `Delegation.stake` directly drives the account's effective/activating stake used for consensus/leader-schedule stake weighting and for future reward point calculations, meaning lamports moved via a plain, unprivileged transfer bypass the stake program's `DelegateStake` instruction (with its minimum-delegation and activation-epoch rules) to materially and durably increase a validator's or delegator's on-chain stake weight — a form of undeclared/underpriced value creation analogous to the GenesisGroup exploit where forced ETH balance bypassed the `purchase` checks and minting logic.

### Likelihood Explanation
Triggering this path requires no special privilege: any keypair can send a normal `system_instruction::transfer` to a target stake account pubkey at any time, since Solana permits crediting lamports to accounts without their owner's cooperation. The only constraint is timing — the transfer must land after the epoch-boundary stake snapshot used for reward calculation but before the specific partition containing the account is processed during `distribute_epoch_rewards_in_partition`, a window that is deterministic and observable on-chain (partition assignment/timing is public), making the attack practically executable by a patient or well-informed actor, particularly one targeting their own stake account.

### Recommendation
Do not derive `stake.delegation.stake` adjustments from the stake account's live lamport balance sampled after the epoch boundary. Instead, base `delegation_may_need_adjustment`'s inputs strictly on lamports that are provably attributable to the protocol's own reward-crediting flow (e.g., an internally tracked "pending rent/rewards adjustment" value recorded at the epoch boundary, separate from `AccountSharedData::lamports()`), so that externally-initiated transfers occurring during the distribution window cannot influence tracked delegation amounts.

### Proof of Concept
The existing regression test demonstrates the mechanism end-to-end: a stake account is created with a known `pre_lamports`/delegation; `checked_add_lamports(1_000_000_000)` (a stand-in for an unprivileged external transfer) is applied directly to the stored account before calling `bank.distribute_epoch_rewards_in_partition`; the post-distribution `stake.delegation.stake` is asserted to equal `pre_stake_state.delegation().unwrap().stake + reward_lamports`, confirming the adjustment logic incorporates the externally added balance into the tracked delegation. pub(crate) fn delegation_may_need_adjustment(
    current_delegation: u64,
    new_delegation_with_rewards: u64,
    lamports_with_rewards: u64,
    minimum_lamports: u64,
    status: StakeActivationStatus,
) -> bool {
    if status.effective == 0 && status.activating == 0 {
        return false;
    }

    let new_delegation = std::cmp::min(
        new_delegation_with_rewards,
        lamports_with_rewards.saturating_sub(minimum_lamports),
    );

    new_delegation != current_delegation
}
