### Title
Webhook shop/topic/webhook_id identity fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC over the body only and then dispatches the handler using the unverified `shop` header value, breaking the binding: `HMAC(body, secret) verified == body-only, while (shop, topic, webhook_id) acted upon by the handler == unverified header values`.

### Finding Description
In `lib/shopify_api/webhooks/request.rb`:
- `shop`, `topic`, `webhook_id`, `api_version` are all parsed straight from HTTP headers with no cryptographic binding: [1](#0-0) 
- `to_signable_string` returns only `@raw_body`, excluding every one of those header fields from what is HMAC-verified: [2](#0-1) 

In `lib/shopify_api/webhooks/registry.rb`, `process` validates the HMAC (over body only) and then constructs `WebhookMetadata` directly from the unverified header-derived fields, most importantly `shop: request.shop`, which is passed to the app's handler: [3](#0-2) 

Critically, the HMAC secret used for webhook validation is the app's single `api_secret_key`/`client_secret`, shared across every merchant/shop that has installed the app — it is not shop-specific: [4](#0-3) 

This mirrors the report's bug class exactly: a field that is acted upon (here, `shop`, used to attribute/route webhook processing to a specific tenant) is not covered by the cryptographic check (the HMAC only covers the body). Any unprivileged user who can install the app on a shop they control (e.g. a free development store) receives genuinely-signed webhooks from Shopify for their own shop. Because the signature never binds the `shop-domain`/`topic`/`webhook-id` headers, that attacker can replay the same body + HMAC digest to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header with an arbitrary victim shop domain. `Utils::HmacValidator.validate` will still return `true` (it only recomputes HMAC over `@raw_body`), so `Registry.process` will accept the forged request and dispatch it to the handler as if it came from the victim shop.

### Impact Explanation
Any app handler logic keyed by `shop` (installation/uninstallation bookkeeping, data sync per shop, cache/session invalidation, billing/plan changes, GDPR/data-erasure triggers, etc.) can be triggered under an attacker-chosen victim shop identity. Since dispatch is per-shop and this is the core tenant boundary the host application relies on the gem to authenticate, this breaks tenant isolation — a cross-tenant confusion where actions attributable to shop B (victim) are actually driven by an untrusted party who only controls shop A (attacker), because the identity field the app trusts (`shop`) was never covered by the HMAC that is supposed to authenticate the request as a whole.

### Likelihood Explanation
Requires only: (1) the ability to install a public/unlisted app onto any shop the attacker controls (freely available via a Shopify partner/dev store — no privileged access needed), and (2) the ability to send an arbitrary HTTP POST with attacker-chosen headers to the app's public webhook endpoint (trivial). No access token, `client_secret`, or privileged account is required. This is a structural gap in the signing scheme's coverage rather than a rare misconfiguration, making it consistently reachable by any unprivileged user who installs the app once.

### Recommendation
Bind the identity headers into what is cryptographically verified before they're trusted:
- Either include `shop`, `topic`, and `webhook_id` in the HMAC-covered signable content, or
- Require the caller (host application) to independently confirm that `request.shop` corresponds to a shop with an active, previously-established session/installation for this app before invoking the handler, treating the header-derived `shop` as untrusted input until then, and document this requirement prominently since the gem's `Registry.process` currently gives no such warning.

### Proof of Concept
1. Install the target Shopify app on an attacker-controlled development store `attacker-shop.myshopify.com`.
2. Trigger any registered webhook topic (e.g. `orders/create`) so Shopify delivers a legitimately HMAC-signed webhook request to the app's endpoint, with body `B` and header `X-Shopify-Hmac-Sha256: H = HMAC-SHA256(secret, B)`.
3. Capture this request. Replay it to the same app endpoint, keeping body `B` and header `X-Shopify-Hmac-Sha256: H` unchanged, but replace `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate(request)` in `Registry.process` recomputes `HMAC(secret, B)`, which still equals `H`, so validation passes: [5](#0-4) 
5. The handler executes with `WebhookMetadata.shop == "victim-shop.myshopify.com"`, even though the request body and shop's actual data have nothing to do with that shop.
