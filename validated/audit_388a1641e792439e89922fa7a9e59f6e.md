### Title
Webhook shop-domain header not bound to HMAC allows cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content solely from the raw request body [2](#0-1) , while the `shop` (and `topic`, `webhook_id`, `api_version`) values are read directly from unauthenticated HTTP headers [3](#0-2) . `Registry.process` validates only the HMAC over the body via `Utils::HmacValidator.validate(request)` and then forwards `request.shop` straight into `WebhookMetadata` without any binding to the verified signature [4](#0-3) .

### Finding Description
The identity binding that should hold is: `shop header value == shop that produced the HMAC-signed body`. In reality, `HmacValidator.validate` only proves that `computed_signature(body, api_secret_key) == received_signature`; it never touches `shop`, `topic`, `webhook_id`, or `api_version` (`Utils::HmacValidator#validate_signature` at [5](#0-4) , and `VerifiableQuery#to_signable_string` returning only `@raw_body` at [2](#0-1) ).

Because the `api_secret_key` is a single, app-wide secret shared across every shop that installs the app (not a per-shop secret), an attacker who installs the same app on their own shop receives genuine, correctly-HMAC-signed webhook deliveries for their own shop. They can then replay that exact `raw_body` + `hmac-sha256` header to the app's public webhook endpoint while substituting an arbitrary victim's `shop-domain` header. `HmacValidator.validate` still succeeds because it only checks the body against the secret, so `Registry.process` proceeds and calls the registered handler with `WebhookMetadata.shop` set to the attacker-chosen value [6](#0-5) .

The gem's own documentation instructs consumers to trust `data.shop` as the tenant identifier for downstream processing (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) [1](#0-0) , and `Registry.process` provides no mechanism or warning that `shop` is unauthenticated. This is the direct analog of the report class: "a field acted on but not covered by the HMAC."

### Impact Explanation
Any handler built per the documented pattern applies webhook body data (orders, products, GDPR data, etc.) keyed by `data.shop`. An attacker exploiting the header/HMAC binding gap can make an application record or act on their own controlled webhook body under an arbitrary victim shop's identity, i.e. cross-tenant data confusion/injection — matching the Critical "cross-tenant access" impact class.

### Likelihood Explanation
Requires the attacker to install the target app on a shop they control (any developer/merchant can do this for public or even custom apps they have access to install) and to replay one legitimately received webhook body with a modified `shop-domain` header. No secret material needs to be known; the attacker only reuses an HMAC that Shopify itself issued for their own installation. This is straightforward for any determined attacker with an app installation.

### Recommendation
Do not treat `shop`, `topic`, `webhook_id`, or `api_version` header values as trusted metadata independent of the HMAC. Either include these fields in the signable content that is HMAC-verified, or require host applications to cross-check `request.shop` against the shop associated with the specific `webhook_id`/subscription (e.g., by looking up the expected shop from local state keyed by `webhook_id`) before acting on `WebhookMetadata`. At minimum, document prominently that `shop` is not authenticated by `HmacValidator.validate` and must not be used as the sole tenant-scoping key.

### Proof of Concept
1. Install the target app on attacker-owned shop `attacker.myshopify.com`; trigger a webhook (e.g., `orders/create`) and capture the raw POST: `raw_body` and header `x-shopify-hmac-sha256`.
2. Resend the identical `raw_body` and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but set `x-shopify-shop-domain: victim.myshopify.com`.
3. `Utils::HmacValidator.validate` succeeds (body/HMAC pair is genuinely valid for the shared `api_secret_key`) [7](#0-6) .
4. `Registry.process` calls the handler with `WebhookMetadata.shop == "victim.myshopify.com"` even though the body actually originated from the attacker's own shop [6](#0-5) , causing the host app to process attacker-supplied webhook content under the victim tenant's identity.
