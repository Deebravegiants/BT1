Confirmed root cause with sufficient evidence to write the finding.### Title
Webhook `shop-domain` header is trusted as the tenant identity but is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop` (tenant identifier) delivered to the app's webhook handler is read from an HTTP header that is completely outside the scope of that signature. This breaks the identity binding `authenticated_bytes == acted_on_identity`: the bytes that are cryptographically verified (`@raw_body`) are not the bytes that determine which shop the webhook payload is attributed to (`shopify-shop-domain` / `x-shopify-shop-domain` header).

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

The `shop` accessor used by the rest of the library is derived purely from a header, never checked against the signature: [2](#0-1) 

`ShopifyAPI::Utils::HmacValidator.validate` verifies `verifiable_query.to_signable_string` (the body) against `verifiable_query.hmac`, and never touches `shop`, `topic`, `api_version`, or `webhook_id`: [3](#0-2) 

`ShopifyAPI::Webhooks::Registry.process` performs exactly this check and then forwards `request.shop` (the unauthenticated header value) straight into `WebhookMetadata`, which is handed to the app's handler as the authoritative shop/tenant for that payload: [4](#0-3) [5](#0-4) 

The identity binding that should hold is:
`hmac_verified(bytes) == bytes_that_determine(shop, topic, api_version, webhook_id)`

but instead the gem verifies only `bytes == raw_body`, while `shop`/`topic`/`api_version`/`webhook_id` come from a disjoint, unauthenticated channel (headers). Since the signature only covers the body, a `(body, hmac)` pair that was validly produced for shop A's webhook remains a **valid** signature under a **different** `shop-domain` header value, because the header plays no role in `compute_signature`.

### Impact Explanation
An unprivileged actor can install the target app on a shop they control (a normal, unprivileged action — installing a free/dev app requires no special credential) and thereby legitimately receive Shopify-signed webhook deliveries `(raw_body, hmac)` for their own shop. Because `shop-domain` is not part of the signed content, that same `(raw_body, hmac)` pair can be replayed to the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop's domain. `Utils::HmacValidator.validate` still returns `true` (the body/hmac pair is unchanged), and `Registry.process` will hand the attacker's body to the handler tagged as belonging to the victim shop. If the host app scopes storage, redaction, or business logic (order/customer records, GDPR redact webhooks, billing state, etc.) by `data.shop` as the library's documented contract instructs (`docs/usage/webhooks.md`), the attacker can inject or overwrite data under another tenant's identity — a cross-tenant integrity/confidentiality violation rooted in this gem's `Request`/`HmacValidator` design, not in host misuse of an undocumented API.

### Likelihood Explanation
Requires only: (1) the ability to install the app on any shop (unprivileged, no leaked secrets needed) to obtain one valid `(body, hmac)` pair, and (2) the ability to POST to the app's public webhook endpoint with attacker-chosen headers — both are available to any unprivileged internet user. No access token, `client_secret`, or privileged account is required.

### Recommendation
Include the tenant-identifying and semantically load-bearing headers (`shop-domain`, `topic`, `api_version`, `webhook_id`) in the HMAC-signed material, or independently re-derive/verify the shop against a trusted, out-of-band source (e.g., cross-check against the session/shop the delivery was registered against) before trusting `request.shop` in `WebhookMetadata`. At minimum, `to_signable_string` should bind the header values it later exposes via accessors, so that no header can be swapped post-signature without invalidating the HMAC.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (unprivileged, no secrets needed).
2. Shopify delivers a legitimate webhook to the app's endpoint with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid-hmac-of-body>`, and some `raw_body`.
3. Attacker captures this `(raw_body, hmac)` pair (e.g., by pointing the endpoint at a URL they control, or via any request logging they have visibility into for their own shop's deliveries).
4. Attacker crafts a new HTTP POST to the same app webhook endpoint with the identical `raw_body` and `x-shopify-hmac-sha256` header, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `Utils::HmacValidator.validate(request)` in `lib/shopify_api/utils/hmac_validator.rb` (lines 12-31) succeeds because it only checks `raw_body` against `hmac`.
6. `Registry.process` (lines 188-200 of `lib/shopify_api/webhooks/registry.rb`) invokes the app handler with `WebhookMetadata.shop == "victim-shop.myshopify.com"`, causing the app to process attacker-controlled body content as if it were authentic data from the victim shop.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
