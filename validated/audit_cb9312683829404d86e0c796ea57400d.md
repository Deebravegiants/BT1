## Title
Hardcoded Uniswap V3/V4 fee tier in the `uniswapV2Router` wrapper used for `EvmHost` fee-token swaps — ([File: evm/src/utils/uniswapv2/UniV3UniswapV2Wrapper.sol])

### Summary
`EvmHost` and `IntentGatewayV2` swap native tokens for the ISMP `feeToken` by calling `IUniswapV2Router02(uniswapV2).swapETHForExactTokens(...)` on whatever router address is configured in `HostParams.uniswapV2` [1](#0-0) . On chains where a native Uniswap V2 pool for the fee token doesn't exist, this role is filled by `UniV3UniswapV2Wrapper` (or `UniV4UniswapV2Wrapper`), an adapter that exposes the V2 interface but internally swaps through Uniswap V3/V4 using a single, hardcoded fee tier configured once at deployment, applied to every swap regardless of which pool is actually optimal or exists for the WETH↔feeToken pair.

### Finding Description
`UniV3UniswapV2Wrapper` stores a single `maxFee` (`uint24`) in its `Params` struct at `init()` time and reuses that exact fee tier for every subsequent swap and quote, on every token pair it is asked to route [2](#0-1) . This value is baked into `swapETHForExactTokens`, `swapExactTokensForETH`, `getAmountsIn`, and `getAmountsOut`: [3](#0-2) [4](#0-3) [5](#0-4) 

The V4 sibling has the same design: a fixed `defaultFee`/`defaultTickSpacing` baked into every `PoolKey` it constructs [6](#0-5) , confirmed by the deployment/test config hardcoding `defaultFee: 3000` [7](#0-6) .

This wrapper is deployed specifically to be plugged in as `HostParams.uniswapV2` / `IDispatcher.uniswapV2Router()` [8](#0-7) . `EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()` all route native-token fee payments through this configured router with `swapETHForExactTokens` [1](#0-0) [9](#0-8) . `IntentGatewayV2.placeOrder()` does the same for the solver fee when the user pays in native token [10](#0-9) . `HyperApp.quote()`/`dispatchWithFeeToken()` and the SDK's `quoteNative` all rely on `getAmountsIn` from this same fixed-fee-tier router for cost estimation [11](#0-10) [12](#0-11) .

Because the fee tier is fixed at wrapper deployment and cannot be chosen per-call, any unprivileged caller of `dispatch`, `fundRequest`, or `placeOrder` with native-token payment is forced through that single pool. If the configured tier's pool for WETH/feeToken has no liquidity (or none was ever created) on that chain, every native-fee dispatch/order call permanently reverts. If the pool exists but is not the deepest one, users are quoted/charged worse-than-market exchange rates for a mandatory, non-optional swap embedded in core message dispatch.

### Impact Explanation
- **Denial of message dispatch**: If the hardcoded fee tier's pool doesn't exist for a given WETH/feeToken pair on a deployed chain, `EvmHost.dispatch()`/`fundRequest()` and `IntentGatewayV2.placeOrder()` for native-token payers revert unconditionally — this is a permanent route-level failure to deliver messages/fund requests, satisfying the "route unable to deliver messages" impact criterion.
- **Economic loss for users**: Even where the hardcoded-tier pool exists but has poor liquidity relative to other tiers, every ETH-denominated dispatch fee, request funding, and order fee is forced through it, so users systematically overpay native tokens for the exact fee-token amount required — a mandatory swap embedded in the core dispatch path with no way for the caller to select a better route.

### Likelihood Explanation
This is triggered on every native-token-funded `dispatch`, `fundRequest`, or `placeOrder` call whenever a deployment configures `HostParams.uniswapV2` to one of these wrapper contracts (the documented and intended pattern for chains lacking a native Uniswap V2 deployment, per `DeployUniV3Wrapper.s.sol`/`DeployUniV4Wrapper.s.sol`). No privileged action or special conditions are required — any ordinary user submitting a message dispatch or intent order with native token payment exercises this code path.

### Recommendation
Do not hardcode a single fee tier in the wrapper's `Params`. Instead, either (a) probe multiple standard tiers (as the SDK's off-chain `Swap` utility already does via `COMMON_FEE_TIERS` [13](#0-12) ) and select the best available on-chain, or (b) allow the fee tier to be passed/overridden per call, with a fallback discovery mechanism, so dispatch/fund/order flows aren't permanently bricked or forced into a suboptimal, potentially illiquid pool.

### Proof of Concept
1. Deploy `UniV3UniswapV2Wrapper` with `maxFee = 3000` for a chain whose only WETH/feeToken Uniswap V3 pool with real liquidity is the 500 (0.05%) tier [8](#0-7) .
2. Configure this wrapper as `HostParams.uniswapV2` in `EvmHost`.
3. Any user calls `EvmHost.dispatch{value: x}(DispatchPost{...})` with `msg.value > 0`; `EvmHost` calls `IUniswapV2Router02(wrapper).swapETHForExactTokens{value: x}(post.fee, [WETH, feeToken], address(this), block.timestamp)` [1](#0-0) .
4. Inside the wrapper, `swapETHForExactTokens` builds `ExactOutputSingleParams{ tokenIn: weth, tokenOut: feeToken, fee: _params.maxFee (3000), ... }` [14](#0-13) . Since the 3000 tier pool has no/insufficient liquidity, the Uniswap V3 router call reverts, and the entire `dispatch()` transaction reverts — permanently blocking native-fee dispatch on that chain until redeployment with a different fee tier.
