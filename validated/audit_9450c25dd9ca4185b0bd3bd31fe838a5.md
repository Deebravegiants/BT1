### Title
Hardcoded `STSTX-RATIO-DECIMALS` scaling constant can desynchronize from the external StackingDAO ratio contract, corrupting collateral valuation for stSTX/zstSTX - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`market.clar` prices stSTX (and its ztoken zstSTX) by multiplying the Pyth STX/USD price by a ratio fetched from an external, third-party contract and dividing by a hardcoded constant `STSTX-RATIO-DECIMALS`. This mirrors the reported Berachain/Infrared pattern of a protocol hardcoding a scale/threshold constant (`INITIAL_DEPOSIT` = 32 ether) that is assumed to match an external, still-evolving system's actual enforced value (`BeaconDeposit.MIN_DEPOSIT_AMOUNT_IN_GWEI`), and which can silently drift out of sync as the external system changes.

### Finding Description
`call-ststx-ratio` calls out to a third-party StackingDAO contract to obtain the STX-per-stSTX ratio: [1](#0-0) 

That ratio is consumed by `resolve-ststx`, which divides by a hardcoded constant `STSTX-RATIO-DECIMALS` (defined as `u1000000`) to normalize the ratio into the price calculation: [2](#0-1) 

The same hardcoded decimals constant is duplicated in the `protocol-data`/`v0-1-data.clar` utility contract for reserve/APR display: [3](#0-2) [4](#0-3) 

This resolved price feeds directly into `resolve-callcode`/`resolve-ztoken`, which is the value used for collateral notional valuation, LTV checks, borrow capacity, and liquidation health checks throughout the market (as seen in the local-testing mirror at `local-testing/contracts/market/market.clar:371-380`, `991-1080`). If the external StackingDAO ratio contract ever changes the scale/precision of the value returned by `get-ststx-ratio-v3` (e.g., re-denominates from 1e6 to 1e8, or changes rounding/precision semantics as part of its own upgrades), the fixed divisor `STSTX-RATIO-DECIMALS` in Zest would no longer match the actual precision of the returned value, producing a price that is off by orders of magnitude while still passing the oracle's own sanity checks (`oracle-price-legal` only checks `> u0`, and `oracle-timestamp-fresh` only checks staleness, not scale). This is a bug in Zest's own price-resolution code, since it hardcodes a scaling assumption about a third-party contract's internals without any on-chain validation of that assumption — exactly the underlying bug class described in the report (hardcoded constant assumed to be in sync with an external, evolving implementation, InfraredBERAConstants vs BeaconDeposit).

### Impact Explanation
If `STSTX-RATIO-DECIMALS` desynchronizes from the actual precision returned by the external ratio contract:
- An inflated ratio value combined with a stale hardcoded divisor would inflate the computed stSTX/zstSTX collateral price, letting users borrow against collateral that is not actually worth that much — this is a direct path to protocol insolvency / theft of other depositors' funds (identity broken: `notional-collateral-value-used-for-LTV != real-collateral-value`).
- A deflated computed price would understate collateral value, causing legitimate positions to be wrongfully flagged unhealthy and liquidated, or borrowing/withdraws to revert — temporary freezing of funds.

Both outcomes match in-scope impact categories (protocol insolvency / theft, or temporary freezing of funds), because the value identity `collateral USD value (via oracle) == real backing value` breaks the moment the hardcoded decimals constant no longer matches the actual precision emitted by the external contract.

### Likelihood Explanation
Low-to-medium. This requires the external, third-party StackingDAO ratio contract to change its return precision/semantics, which is outside Zest's control and not something an attacker can trigger unilaterally within this codebase. This mirrors the report's own "Likelihood: Low" rating for the analogous Infrared/Berachain issue, since it depends on an out-of-band change to an external, still-evolving protocol rather than a bug an attacker can directly exploit through a call sequence in Zest alone.

### Recommendation
1. Do not hardcode `STSTX-RATIO-DECIMALS` as an immutable constant tied to the external contract's current implementation; expose it as a DAO-governable parameter, or query the decimals/precision from the external contract itself if such a getter exists, and validate it before use.
2. Add a sanity bound/circuit-breaker on the resolved stSTX ratio (e.g., reject or pause if the ratio deviates too far from a previously observed value in one update), similar to existing confidence/staleness checks (`max-confidence-ratio`, `oracle-timestamp-fresh`), so a scale mismatch cannot silently corrupt collateral valuation.
3. Track upstream changes to the StackingDAO ratio contract (and any other external dependency such as the DIA oracle or Pyth storage contract addresses hardcoded in `v0-1-data.clar`) and re-validate `STSTX-RATIO-DECIMALS` and related constants before/after any upstream upgrade.

### Proof of Concept
Not directly exploitable on-chain by an unprivileged attacker today — the vulnerability is latent and only manifests if/when the external `SP4SZE494VC2YC5JYG7AYFQ44F5Q4PYV7DVMDPBG.block-info-nakamoto-ststx-ratio-v2` contract changes the precision or semantics of `get-ststx-ratio-v3`. Conceptual trigger sequence:
1. External StackingDAO contract upgrades/changes the returned ratio's scale (analogous to Berachain's `BeaconDeposit.MIN_DEPOSIT_AMOUNT_IN_GWEI` change referenced in the report).
2. `call-ststx-ratio()` in `mainnet/contracts/market/v0-4-market.clar:1014-1016` returns a value in the new scale.
3. `resolve-ststx` still divides by the stale `STSTX-RATIO-DECIMALS = u1000000`, producing a stSTX price that is wrong by orders of magnitude.
4. This corrupted price flows into `resolve-callcode` → `get-notional-evaluation` → LTV/health checks used by `collateral-add`, `borrow`, and liquidation, letting a user either borrow against inflated stSTX collateral value or triggering wrongful liquidations/freezes against deflated value.
