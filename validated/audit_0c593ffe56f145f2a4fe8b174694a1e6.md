### Title
Webhook `shop`, `topic`, and `webhook_id` fields are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw HTTP body, so the HMAC that `Utils::HmacValidator` verifies covers exclusively the JSON payload bytes. The `shop-domain`, `topic`, `webhook-id`, and `api-version` values are read straight from HTTP headers and are never included in the signed data, yet `Registry.process` trusts them unconditionally to build the tenant-identifying `WebhookMetadata` passed to the app's handler.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
which returns only `@raw_body`. `HmacValidator.validate` computes the signature over exactly this string and compares it to the `hmac` header: [2](#0-1) 
Meanwhile, `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are pulled directly from headers with no cryptographic binding to the body: [3](#0-2) 
`Registry.process` validates only the HMAC and then forwards these unauthenticated header values straight to the app's webhook handler as the tenant/topic identity: [4](#0-3) 

This breaks the intended identity binding `shop authenticated by HMAC == shop attributed to the event`. Because the signature is computed only over the body bytes, any request carrying a body+HMAC pair that was legitimately produced for one shop's webhook delivery remains **valid** even if the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header is swapped for a different shop. The gem provides no mechanism, and performs no check, to ensure the header-derived `shop` matches the tenant whose secret actually produced the HMAC.

### Impact Explanation
An unprivileged user who can trigger any webhook delivery for their own shop (e.g., by installing the app on a shop they control and performing an action that fires a webhook such as `orders/create`) can capture the raw body and its valid `hmac-sha256` value. They can then replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `shop-domain` header with a victim shop that also has the app installed. `HmacValidator.validate` will still succeed (body unchanged, same shared `api_secret_key`), and `Registry.process` will hand the handler a `WebhookMetadata` claiming the event came from the victim's shop. If the host application uses `WebhookMetadata#shop` to select which tenant's data to update/delete (a very common pattern for webhook consumers), this results in cross-tenant data corruption or disclosure — a Critical-class cross-tenant access issue.

### Likelihood Explanation
Exploitation requires only the ability to install/uninstall the app or otherwise cause one webhook delivery for an attacker-controlled shop (which any merchant that installs the app can do) and to send an arbitrary HTTP request with a modified header to the app's public webhook endpoint — no access to `api_secret_key`, tokens, or the victim's account is needed. The requirement to observe one raw body/HMAC pair for a shop the attacker controls is a normal, low-effort step, making this reasonably likely wherever a host app trusts the gem's `shop` field as sufficient tenant identification.

### Recommendation
Include the identity-critical headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signable content used for HMAC verification, or otherwise cryptographically bind them to the payload before dispatch, rather than allowing `to_signable_string` to cover only `@raw_body`. Additionally, document/require host applications to independently correlate `WebhookMetadata#shop` against their own installed-shop/session record before trusting it as an authenticated tenant identifier.

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com` and triggers `orders/create`, capturing:
   - raw JSON body `B`
   - `X-Shopify-Hmac-Sha256: H` (valid HMAC of `B` under the app's shared secret)
2. Attacker sends a forged webhook POST to the app's webhook endpoint with:
   - Body: `B` (unchanged)
   - `X-Shopify-Hmac-Sha256: H` (unchanged, still valid since only body is signed)
   - `X-Shopify-Shop-Domain: victim.myshopify.com` (swapped)
   - `X-Shopify-Topic`, `X-Shopify-Webhook-Id` optionally swapped as well
3. `Utils::HmacValidator.validate` returns `true` because only `B` and `H` are checked: [5](#0-4) 
4. `Registry.process` dispatches to the handler with `shop: "victim.myshopify.com"`, `body: parsed(B)` — an event that never happened for `victim` is now processed as if it did: [6](#0-5)
