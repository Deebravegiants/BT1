This confirms the analog: the webhook HMAC in `HmacValidator.validate` is computed only over `to_signable_string`, which for `ShopifyAPI::Webhooks::Request` returns just `@raw_body` [1](#0-0) , while `shop`, `topic`, `api_version`, and `webhook_id` are all read from unauthenticated HTTP headers via `shopify_header` [2](#0-1) . `Registry.process` validates the HMAC against the request, then unconditionally trusts `request.shop` (and `request.topic`) to build `WebhookMetadata` passed to the host app's handler [3](#0-2) . Since a Shopify app's `client_secret` (and thus the HMAC signing key, see `HmacValidator.compute_signature`) is shared across every shop that has the app installed [4](#0-3) , any merchant who installs the app can obtain a genuinely-signed `(body, hmac)` pair from their own store's real webhook delivery, then replay that exact body/HMAC to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header for a different, victim shop — the header is never covered by the signature, so the forged shop attribution passes `HmacValidator.validate` unchanged.

### Title
Webhook shop attribution is not bound by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw body, so the HMAC verification performed by `Utils::HmacValidator.validate` authenticates the body content but not the `shop-domain`, `topic`, `api-version`, or `webhook-id` headers. `Webhooks::Registry.process` nonetheless treats `request.shop` as an authenticated tenant identifier after HMAC validation succeeds.

### Finding Description
The equality the gem is supposed to guarantee is: `shop authenticated by HMAC == shop used as tenant key by the handler`. In reality:
- `HmacValidator.validate_signature` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the `hmac` field [5](#0-4) .
- For webhooks, `to_signable_string` is defined as `@raw_body` only [1](#0-0) , meaning none of the HTTP headers — including `shop-domain` — are part of the signed material.
- `Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cross-check against the body or signature [6](#0-5) .
- `Registry.process` only checks `Utils::HmacValidator.validate(request)` (body-only check) before forwarding `request.shop` to the host app's handler as the trusted tenant identity [3](#0-2) .

Because the HMAC key is the app's single `client_secret` (or `old_api_secret_key`) shared by all shops that installed the app, not a per-shop secret [7](#0-6) , any merchant that has installed the app can capture a legitimately-signed `(raw_body, hmac)` pair delivered to their own endpoint and resend it with a forged `shop-domain` header pointing at a different, victim shop. The forged request still passes `HmacValidator.validate` because the header is outside the signed scope, so `Registry.process` hands the handler a `WebhookMetadata` claiming the victim shop for attacker-controlled body content.

### Impact Explanation
This breaks the shop-authentication binding the gem is expected to provide for webhook processing: host applications rely on `request.shop`/`WebhookMetadata#shop` (post-HMAC-validation) as an authenticated tenant key to route or persist data (e.g., mandatory `customers/redact`, `shop/redact`, order/product update handlers keyed by shop). An attacker who is any installed merchant of the app can cause the handler to process attacker-supplied body content attributed to a different shop, corrupting or exfiltrating another tenant's data — a cross-tenant access issue.

### Likelihood Explanation
Exploitability only requires the attacker to be an ordinary merchant who has installed the app (an "unprivileged" actor relative to other tenants) and to capture one real webhook delivery from Shopify to obtain a valid `(body, hmac)` pair, then replay it with a modified `shop-domain` header — no possession of `client_secret` or access tokens is required.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the material verified against the HMAC, e.g., either request that Shopify's HMAC cover headers, or independently verify `request.shop` against session/shop records established via OAuth for that specific merchant before trusting it, rather than accepting the header verbatim once the body-only HMAC passes.

### Proof of Concept
1. App merchant A installs the app; Shopify delivers a webhook to the app's endpoint with headers `X-Shopify-Shop-Domain: shop-a.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid hmac over raw_body>`, and some `raw_body`.
2. Merchant A captures this raw body and HMAC value (e.g., via a proxy they control, since it's their own webhook traffic).
3. Merchant A resends the exact same `raw_body` and `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: shop-b.myshopify.com` (a victim shop that also has the app installed).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `@raw_body`; the signature still matches because headers are not signed [8](#0-7) .
5. The handler receives `WebhookMetadata.new(topic: request.topic, shop: "shop-b.myshopify.com", body: request.parsed_body, ...)` [9](#0-8) , causing shop-b's data to be processed/mutated using attacker-controlled content from shop-a's webhook.
