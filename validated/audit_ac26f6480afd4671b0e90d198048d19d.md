## Title
Webhook `shop` (and `topic`/`webhook_id`) headers are not covered by HMAC verification, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while `ShopifyAPI::Webhooks::Registry.process` trusts the unauthenticated `shop`, `topic`, and `webhook_id` headers to route and label the payload delivered to the app's handler. Because these identity fields are not part of the signed bytes, an attacker who has received one legitimately-signed webhook (e.g. by installing the app on their own store) can replay the same body+HMAC to the app's webhook endpoint while substituting the `shop-domain` header for a victim shop, and the gem will accept it as authentic.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

but `shop`, `topic`, `api_version`, and `webhook_id` are all read straight from unauthenticated headers: [2](#0-1) 

`Registry.process` validates only the HMAC over the body via `Utils::HmacValidator.validate(request)`, then immediately builds `WebhookMetadata` from `request.shop`, `request.topic`, and `request.webhook_id` and hands it to the app-registered handler: [3](#0-2) 

`HmacValidator.validate` and `validate_signature` only ever hash `verifiable_query.to_signable_string`, i.e. the body bytes for webhooks: [4](#0-3) 

The binding that is broken: `shop_header == shop_bound_by_hmac`. In reality `shop_header` is attacker-controlled while `shop_bound_by_hmac` doesn't exist — the HMAC only proves the body bytes match, not which shop the event belongs to. Since the `api_secret_key` used to sign webhooks is shared across every merchant that has installed the app, any merchant/attacker who installs the app on their own store legitimately receives valid `(body, hmac)` pairs from Shopify. That attacker can replay the identical body/HMAC to the app's webhook endpoint while forging the `X-Shopify-Shop-Domain` (and topic/webhook-id) header to name a victim shop. `HmacValidator.validate` still returns `true` because it only checks the body, and `Registry.process` dispatches the forged event to the handler labeled with the victim's shop domain.

### Impact Explanation
This is a cross-tenant data-integrity/authentication issue: the app's webhook handler receives events it believes are scoped to `victim-shop.myshopify.com` (used to look up sessions, update per-tenant records, trigger uninstall/GDPR flows, etc.) but whose content and timing are fully attacker-controlled. Depending on the handler logic this enables injecting fabricated orders/customers/app-uninstalled events attributed to a shop the attacker does not control — a cross-tenant access primitive that meets the "Critical - cross-tenant access" bar.

### Likelihood Explanation
Requires only that the attacker can install the app (or otherwise obtain one valid signed webhook body) and can send arbitrary HTTP requests to the app's public webhook endpoint with spoofed headers — no leaked secret, TLS interception, or privileged account needed. This is a realistic capability for any unprivileged internet user who can install a public Shopify app.

### Recommendation
Bind the identity fields into the signed material, or otherwise independently authenticate the shop before trusting it: e.g. verify the reported `shop` header against a shop known to have installed the app (an active session), or include `shop`/`topic`/`webhook_id` in the value being HMAC-verified rather than trusting the raw headers unconditionally in `Registry.process`.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`. Shopify delivers a legitimate webhook: body `B`, header `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC(api_secret_key, B)`), `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker crafts a raw HTTP POST to the app's webhook endpoint with the exact same body `B` and `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body as usual; `Utils::HmacValidator.validate` calls `validate_signature`, which hashes only `@raw_body` (`to_signable_string`) — matches `H`, so validation succeeds. [5](#0-4) 
4. `Registry.process` raises no error and calls `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))` with `shop == "victim-shop.myshopify.com"`. [6](#0-5) 
5. The app's handler processes attacker-chosen webhook content as if it legitimately originated from `victim-shop.myshopify.com`.

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
