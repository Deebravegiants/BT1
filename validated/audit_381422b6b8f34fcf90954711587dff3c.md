### Title
Webhook `shop` (and `topic`/`webhook-id`) identity headers are trusted without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body alone, while the shop-identifying `shop-domain` header (along with `topic` and `webhook-id`) is read out-of-band and forwarded, unverified, to the app's webhook handler. Because a single app-level `api_secret_key` is shared across every shop that installs the app, any shop operator (an unprivileged actor who merely installs the public app) can capture one of their own legitimately HMAC-signed webhook deliveries and replay it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to point at a victim shop. The library validates the HMAC successfully (body/HMAC pair is untouched and was genuinely signed by Shopify) and hands the handler a `WebhookMetadata` object whose `shop` field is the attacker-chosen value, causing the merchant-scoped data to be attributed to the wrong tenant.

### Finding Description
The binding that should hold is:
`bytes verified by HMAC == bytes the application treats as authenticated (topic + shop + body)`

But in this gem, only the body is verified: [1](#0-0) 

The `shop`, `topic`, `api_version`, and `webhook_id` are pulled straight from headers with no cryptographic binding to the signed payload: [2](#0-1) 

`HmacValidator.validate` only checks `verifiable_query.hmac` against `verifiable_query.to_signable_string`, i.e. the raw body: [3](#0-2) 

`Registry.process` gates on that HMAC check alone and then forwards the unauthenticated `request.shop` (and `topic`, `webhook_id`) straight into the metadata object passed to the app's handler: [4](#0-3) 

Since `api_secret_key` is one shared secret for the whole app (not per-shop), an attacker who has installed the same public app on any shop they control can obtain a validly-signed `(body, hmac)` pair from their own store's webhook traffic, then re-send that exact pair to the app's webhook endpoint while substituting the `shop-domain` header for a victim shop domain. `Utils::HmacValidator.validate` still returns `true` (the body and HMAC are untouched and genuinely valid), so `Registry.process` proceeds and calls the handler with `WebhookMetadata#shop` set to the victim's domain while the `body` is attacker-controlled content from the attacker's own store. This is precisely the report's bug class: a value that is *acted on* (here, tenant attribution/routing of webhook data) is not *covered* by the integrity check that is supposed to authenticate it (the HMAC only covers the body).

### Impact Explanation
This crosses a tenant boundary: a party with no privileged access to the victim shop (only their own, independently-installed instance of the same public app) can cause the app, via this gem's documented webhook-processing API, to process attacker-supplied payloads under the victim shop's identity. Depending on how the host app's handler uses `WebhookMetadata#shop` (e.g., to look up and update shop-scoped records), this enables cross-tenant data injection/corruption without ever touching the victim's credentials — matching the "cross-tenant access" High/Critical impact category.

### Likelihood Explanation
Likelihood is high for any app operator: becoming "one of many shops that installed the app" requires no privilege beyond normal, public app installation (unprivileged internet user), and replaying an HTTP request with one header changed is trivial once a legitimate `(body, hmac)` pair has been observed from the attacker's own store.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the signed material that `HmacValidator` verifies, or otherwise cryptographically tie the `shop-domain` header to the specific installation before trusting it (e.g., verify the shop is one for which the app holds an active session/access token, and reject/flag webhooks whose header-derived shop cannot be corroborated). At minimum, document that `WebhookMetadata#shop` is unauthenticated header data and must not be used as the sole tenant key without additional verification against a known/active session for that shop.

### Proof of Concept
1. Install the target public app on attacker-owned shop `attacker.myshopify.com`; trigger any webhook (e.g., `orders/create`) and capture the raw POST: body `B` and header `X-Shopify-Hmac-Sha256: H` (valid because it's computed with the app's shared `client_secret`/`api_secret_key`).
2. Replay the exact same request to the same app webhook endpoint, changing only `X-Shopify-Shop-Domain` to `victim.myshopify.com` (also present on the same app).
3. `ShopifyAPI::Webhooks::Request.new` parses headers; `Utils::HmacValidator.validate` recomputes HMAC over `B` only [5](#0-4)  and succeeds since `B`/`H` are unmodified.
4. `Registry.process` invokes the handler with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed(B), ...)` [6](#0-5) , causing the attacker's payload to be processed as if it belonged to the victim shop.
