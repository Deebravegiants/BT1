### Title
Relayer-fee withdrawal transfer lacks balance validation, risking permanent freezing of relayer rewards - (File: `modules/pallets/ismp/src/dispatcher.rs`)

### Summary
The `HyperbridgeWithdrawalModule::on_accept` handler that pays out relayer fees on the destination chain performs a direct `T::Currency::transfer` from `RELAYER_FEE_ACCOUNT` to the relayer's account without first validating that the account holds sufficient balance to cover the requested `amount`. This mirrors the reported bug class: a token transfer is attempted without any pre-check that the paying account can fulfill it, so it is entirely dependent on the underlying `transfer` call reverting cleanly if funds are short.

### Finding Description
When a relayer withdraws accumulated fees, `pallet-ismp-relayer`'s `withdraw` function dispatches an ISMP `POST` with `Message::WithdrawRelayerFees` to the destination chain's built-in `HYPERBRIDGE_MODULE_ID` handler [1](#0-0) . On the destination/coprocessor side, `HyperbridgeWithdrawalModule::on_accept` decodes the message and unconditionally calls:

```rust
T::Currency::transfer(
    &RELAYER_FEE_ACCOUNT.into_account_truncating(),
    &account,
    amount,
    Preservation::Expendable,
)
``` [2](#0-1) 

There is no explicit check that `RELAYER_FEE_ACCOUNT`'s free balance is ≥ `amount` (or ≥ `amount + ExistentialDeposit` under `Preservation::Expendable`) before attempting the transfer. The account is only credited incrementally as other requests are dispatched with a fee [3](#0-2) , so its balance is not guaranteed to track 1:1 with what `pallet-ismp-relayer`'s off-chain-accumulated `Fees` map believes is owed (accumulation happens via a separate proof-verification path on Hyperbridge, decoupled from the actual balance movements on the destination chain). Any accounting drift (rounding, multiple relayers claiming against the same pool of collected fees, partial fee refunds on timeout, etc.) can leave `RELAYER_FEE_ACCOUNT` under-funded relative to a legitimately owed `amount`.

This is directly analogous to `_redeemRewards` in the referenced Sherlock report, which transfers reward funds to a beneficiary without verifying the contract has sufficient balance to cover the transfer, resulting in guaranteed transaction failure when the balance is insufficient.

### Impact Explanation
Because this handler is invoked from `on_accept`, which is called from ISMP's message-execution path when a relayer submits a valid delivery proof, a transfer failure here causes the entire request-handling transaction to revert. The `WithdrawRelayerFees` `POST` request in `pallet-ismp-relayer::withdrawal.rs` is dispatched with `timeout: 0` (i.e., never times out) [4](#0-3) , meaning if the transfer keeps failing on every re-delivery attempt, the relayer's fee balance (already zeroed out in `Fees::<T>::insert(..., U256::zero())` on the source chain at withdrawal-initiation time [5](#0-4) ) becomes permanently unrecoverable — the source-side accounting has already been cleared, but the destination-side payout can never succeed. This is a concrete freezing-of-funds condition for the relayer and a route that is permanently unable to deliver the intended payout message.

### Likelihood Explanation
This requires `RELAYER_FEE_ACCOUNT`'s actual balance to fall short of the cumulative `amount` values relayers are entitled to withdraw. Since fee accumulation (`Fees` map growth on Hyperbridge) and the destination account's real balance are governed by separate mechanisms (state-proof verification of source-chain fee payments vs. actual `T::Currency` transfers on the destination), any drift between the two — e.g., from rounding in `convert_to_balance`-style conversions, concurrent withdrawals racing against `Preservation::Expendable`'s existential-deposit floor, or partial fee collection edge cases — can trigger this. It does not require privileged access; it can be triggered by ordinary relayer fee-withdrawal activity once the two ledgers diverge even slightly.

### Recommendation
Before calling `T::Currency::transfer` in `HyperbridgeWithdrawalModule::on_accept`, explicitly check `T::Currency::reducible_balance(&RELAYER_FEE_ACCOUNT.into_account_truncating(), Preservation::Expendable, Fortitude::Polite) >= amount` and handle the insufficient-balance case gracefully (e.g., emit an event and either retry-safe queue the withdrawal or credit a shortfall ledger) rather than allowing the whole request-processing transaction to fail with no recovery path, given the request never times out and the source-side balance has already been zeroed.

### Proof of Concept
1. Relayer accumulates fees; `pallet-ismp-relayer::Fees` map records an owed `amount` for the relayer on some destination chain.
2. Relayer calls `withdraw`, which zeroes `Fees` on the source/coprocessor chain and dispatches a `POST` request with `Message::WithdrawRelayerFees{ account, amount }`, `timeout: 0`, to `HYPERBRIDGE_MODULE_ID` on the destination chain [6](#0-5) .
3. Suppose `RELAYER_FEE_ACCOUNT`'s balance on that destination chain is, at the time of delivery, less than `amount` (e.g., due to prior withdrawals already having drawn it down, or accounting drift between accumulation and real balance).
4. When the relayer submits the delivery proof, `on_accept` attempts `T::Currency::transfer(&RELAYER_FEE_ACCOUNT, &account, amount, Preservation::Expendable)`, which fails with an underflow/insufficient-balance error [2](#0-1) .
5. The message delivery transaction reverts. Since the request has no timeout, it can be resubmitted indefinitely but will keep failing under the same balance shortfall, while the relayer's claim has already been extinguished on the source chain — resulting in a permanently stuck, undeliverable fee-withdrawal message and lost relayer funds.
