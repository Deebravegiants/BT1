### Title
`EvmHost` collects native-token dust via `receive()` but exposes no way to withdraw it - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost` defines a bare `receive() external payable {}` explicitly documented as the sink for "dust native tokens" returned by the `UniswapV2Router02` integration used during fee-token swaps, but the contract's only fund-recovery entry point, `withdraw`/`WithdrawParams` (reached through `HostManager.onAccept`'s `Withdraw` action), operates on the ERC20 fee-token revenue accounting, not on the host's raw native balance. [1](#0-0) 

### Finding Description
The comment above the `receive()` function states its purpose is to "collect all dust native tokens" left over from `UniswapV2Router02` interactions. This implies native ETH/BNB dust is expected to accumulate in the host contract as a normal side effect of protocol operation (e.g. fee-token swap paths that route through the configured `uniswapV2Router`), not from accidental user error. However, the governance withdrawal path exposed through `HostManager.onAccept` only forwards a `WithdrawParams` struct to `IHostManager(_params.host).withdraw(withdrawParams)`, which is the mechanism for paying out fee-token revenue collected by the host/relayers — there is no code path shown that lets governance, relayer, or any account sweep the host's raw native-token (`address(this).balance`) holdings back out. [2](#0-1) 

This mirrors the reported bug class exactly: a `receive()` function is intentionally present to accept value generated by normal contract operation, but no corresponding sweep/withdraw exists for that specific balance, so any native token routed into the host through this path becomes permanently stuck. This differs from `IntentGatewayV2`, which explicitly implements a `SweepDust` request kind capable of returning both ERC20 and native dust to a beneficiary — the counterpart mechanism appears to be absent for `EvmHost`. [3](#0-2) 

### Impact Explanation
Because dust ETH accumulation is described as an expected consequence of ordinary host operation (UniswapV2Router02 dust from routine fee-token swap flows dispatched by unprivileged users), the balance held unrecoverable in `EvmHost` grows over time with normal protocol usage and can never be retrieved by governance, freezing real value inside the contract permanently.

### Likelihood Explanation
High likelihood of occurrence given the comment explicitly documents this as routine behavior tied to `UniswapV2Router02` swap dust rather than a rare edge case; every dispatch/operation that triggers this router path contributes further un-recoverable native balance.

### Recommendation
Add a governance-gated sweep function (or extend `WithdrawParams`/`HostManager`'s `Withdraw` action) that allows the admin/governance to transfer the host contract's native token balance to a designated beneficiary, mirroring the `SweepDust` pattern already implemented in `IntentGatewayV2`.

### Proof of Concept
Not independently reproducible from the indexed snippets alone since the full `withdraw`/`WithdrawParams` implementation and the exact code paths that route native value into `EvmHost` via the `UniswapV2Router02` integration were not fully retrievable within the available search budget — this could not be conclusively confirmed beyond the `receive()` comment and the `HostManager.onAccept` dispatch shown above. A Devin session with full repository access should verify the complete `EvmHost.withdraw`/`WithdrawParams` definitions and the fee-swap call sites that generate the described dust before treating this as fully confirmed.
