Webhook `shop` identity is not covered by HMAC verification, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
The bug class in the report is an early-exit/identity-binding failure: a value that is *trusted and acted upon* is not actually part of what was *cryptographically verified*. The direct analog in this gem is `ShopifyAPI::Webhooks::Request`: the HMAC signature only covers the raw request body, but the `shop` (tenant) identity used by webhook handlers is read from an unauthenticated header and is never bound to that signature.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely via `Utils::HmacValidator.validate(request)` [1](#0-0) . That validator computes the HMAC over `request.to_signable_string` and compares it to the provided HMAC using `Context.api_secret_key` [2](#0-1) .

Crucially, `Request#to_signable_string` returns only `@raw_body` [3](#0-2) , while `Request#shop` is read directly from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header with no cryptographic binding to that header at all [4](#0-3) .

After HMAC validation succeeds, `process` passes this unauthenticated `request.shop` value straight into the handler as the tenant identity for the delivered data: [5](#0-4) 

This is exactly the pattern flagged in the external report: the equality the code implicitly relies on is `shop_used_by_handler == shop_verified_by_hmac`, but in reality `shop_used_by_handler` is an arbitrary attacker-controlled header while `shop_verified_by_hmac` doesn't exist — the signature never covers the shop at all. Any (body, HMAC) pair valid for the shared `api_secret_key` — which an attacker can obtain by installing the app on their own shop and capturing one legitimate webhook delivery to their own endpoint — can be replayed to the same endpoint with the `shop-domain` header rewritten to name a victim shop. `HmacValidator.validate` will still pass because it never inspects the header, and the handler will process/store the payload under the victim's tenant identity.

### Impact Explanation
This breaks the tenant boundary that host applications rely on this gem to enforce: the gem's own webhook-processing primitive (`Registry.process`) hands developers a `WebhookMetadata.shop` value that they reasonably assume was authenticated (since it comes from the very requests the gem just told them "passed HMAC validation"). An attacker who can obtain any single valid signed webhook body (trivially achievable by installing a public app on a shop they control) can forge deliveries attributed to any other shop, causing cross-tenant data corruption/injection in any app that trusts `WebhookMetadata.shop` after `Registry.process` succeeds — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Webhook endpoints are public HTTP endpoints by design (no TLS interception, no leaked credentials, and no access token required). Obtaining one legitimate (body, HMAC) pair only requires installing the target's public app on an attacker-owned shop — an unprivileged action available to any internet user — after which the shop header can be freely substituted since it is outside the signed data.

### Recommendation
- **Short term:** Include the shop domain (and ideally topic/webhook-id) inside the HMAC-signed payload comparison, or otherwise cryptographically bind the `shop` header to the verified request before it is exposed via `WebhookMetadata`, e.g., verify that the shop header matches session/shop state known independently of the raw header.
- **Long term:** Add negative tests asserting that a valid HMAC for shop A's payload cannot be replayed with a different `shop-domain` header and still validate/route to a handler as shop B.

### Proof of Concept
1. Attacker installs the target public app on `attacker.myshopify.com`, triggering a legitimate webhook delivery with body `B` and a correctly computed `hmac = HMAC-SHA256(api_secret_key, B)` (attacker doesn't need the secret — Shopify computes and sends it).
2. Attacker captures this `(B, hmac)` pair from their own endpoint logs (no TLS interception needed since it's their own delivery).
3. Attacker crafts a new POST to the app's webhook endpoint with the *same* body `B` and `hmac`, but sets the header `shopify-shop-domain: victim-shop.myshopify.com`.
4. `Request.new` parses this into a `Request` object where `shop == "victim-shop.myshopify.com"` [4](#0-3) .
5. `Registry.process` calls `HmacValidator.validate(request)`, which only checks `raw_body` against `hmac` — this still passes [1](#0-0) , [6](#0-5) .
6. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, processing attacker-controlled data under the victim's tenant identity [7](#0-6) .
