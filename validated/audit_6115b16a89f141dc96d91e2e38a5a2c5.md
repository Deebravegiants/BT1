### Title
Divide-by-zero panic in `calc_take_pnl` permanently freezes LP deposit/withdraw when a malicious pool creator drives the PC-side invariant coordinate to zero via decimal rounding - (`program/src/processor.rs`)

### Summary
`Calculator::normalize_decimal_v2` performs an unchecked integer division that can floor a nonzero token amount down to `0` when the mint's native decimals are large relative to `sys_decimal_value` and the deposited amount is small. `TargetOrders::check_init` (called from `process_initialize2`) stores this normalized, possibly-zero value into `calc_pnl_x`/`calc_pnl_y`. Later, every `Deposit`/`Withdraw` call feeds the *current* normalized PC amount as `x1` into `Processor::calc_take_pnl`, which performs `x2.checked_mul(y1).unwrap().checked_div(x1).unwrap()` — an unchecked `.unwrap()` on `checked_div`. If `x1 == 0` this panics, aborting the transaction and permanently bricking the instruction for that pool.

### Finding Description
`Calculator::normalize_decimal_v2` computes `val * sys_decimal_value / 10^native_decimal`: [1](#0-0) 

At pool creation (`process_initialize2`), the raw PC vault amount only has to be non-zero (`amm_pc_vault.amount == 0` → error), but there is no minimum-size check relative to decimals: [2](#0-1) 

The normalized `x`/`y` are then computed and stored via `target_order.check_init(...)` as `calc_pnl_x`/`calc_pnl_y`: [3](#0-2) 

If the pool creator chooses a PC mint with a large decimal count (e.g. 9) and a tiny `init_pc_amount` (e.g. `1`), `normalize_decimal_v2(1, 9, sys_decimal_value≈10^6)` floors to `0`. `calc_pnl_x` is thus stored as `0`.

Every subsequent `Deposit` and `Withdraw` recomputes the same normalized value from the live vault balance and passes it into `calc_take_pnl` as `x1`: [4](#0-3) [5](#0-4) 

Inside `calc_take_pnl`, the branch guard `pool_pc_amount * pool_coin_amount >= calc_pc_amount * calc_coin_amount` is satisfied trivially whenever `calc_pc_amount == restore_decimal(0,...) == 0` (any nonzero pool product is `>= 0`), so execution always enters the pnl-taking branch: [6](#0-5) 

`calc_x_power` returns `0` when `last_x == 0` (since it multiplies by `last_x`): [7](#0-6) 

so `x2 = integer_sqrt(0) = 0`. The very next line then divides by `x1`, which is also `0` in this state, with no zero-check: [8](#0-7) 

`U256::checked_div` returns `None` for a zero divisor, and `.unwrap()` panics, aborting the transaction. Since `calc_take_pnl` is invoked unconditionally on every `Deposit` and on `Withdraw` whenever `amm.status != WithdrawOnly`, once this state is reached the pool's deposit/withdraw path is permanently broken.

### Impact Explanation
Any account is free to call `Initialize2` (permissionless pool creation) supplying an SPL mint with decimals it fully controls and an arbitrarily small `init_pc_amount`/`init_coin_amount` that still satisfies the "non-zero" check but rounds to zero after `normalize_decimal_v2`. This permanently sets `calc_pnl_x` (or `calc_pnl_y`, symmetrically for the coin side) to `0`, and every future `Deposit`/`Withdraw` instruction on that pool will panic in `calc_take_pnl`, making the pool's liquidity un-depositable and un-withdrawable. Any LP tokens or vault balances subsequently locked in the pool become permanently frozen (swaps, which don't call `calc_take_pnl`, may still function, but LP principal can never be added to or withdrawn), matching the "permanent freezing of user or LP funds" impact bar.

### Likelihood Explanation
High. `Initialize2` is a fully permissionless, single-transaction instruction; the attacker only needs to mint an SPL token with sufficiently high decimals (fully attacker-controlled, e.g. mint their own token with 9 decimals) and supply a minimal `init_pc_amount`/`init_coin_amount`. No privileged signer, validator collusion, or off-chain component is required — this mirrors the "legitimate state transition producing a zero divisor" root cause of CVE-2022-49670 (RDMA DIM), where a normally-nonzero ratio field could become exactly zero through ordinary operation and crash the reachable code path.

### Recommendation
- Replace the unchecked `.unwrap()` on `checked_div(x1)` (and the symmetric coin-side division) in `Processor::calc_take_pnl` with a proper error return (e.g. `AmmError::CalcPnlError`) when the divisor is zero.
- Additionally, enforce a minimum normalized (`sys_decimal_value`-scaled) amount in `process_initialize2` (i.e., reject pools whose `normalize_decimal_v2(init_pc_amount, pc_decimals, sys_decimal_value)` or coin-side equivalent evaluates to `0`), rather than only checking the raw vault balance for non-zero.

### Proof of Concept
1. Attacker creates a new SPL mint `M` with `decimals = 9` and mints themselves `1` base unit of it.
2. Attacker calls `Initialize2` for a new Raydium pool using `M` as the PC mint, with `init_pc_amount = 1` and any acceptable `init_coin_amount` (e.g. using a normal coin mint with 6 decimals and enough amount that its normalized value is nonzero). This passes the `amm_pc_vault.amount == 0` check (amount is `1`, nonzero) but `Calculator::normalize_decimal_v2(1, 9, amm.sys_decimal_value)` floors to `0`, so `target_order.calc_pnl_x` is stored as `0`.
3. Any account (attacker or unwitting LP) calls `Deposit` on this pool. `process_deposit` recomputes `x1 = normalize_decimal_v2(total_pc_without_take_pnl, ...) = 0` (still floors to zero for small PC balances) and calls `Self::calc_take_pnl(..., x1.as_u128().into(), y1.as_u128().into())`.
4. Inside `calc_take_pnl`, the guard condition passes trivially since `calc_pc_amount == 0`; `x2 = 0`; the subsequent `checked_div(x1)` with `x1 == 0` returns `None`; `.unwrap()` panics, aborting the transaction.
5. Every future `Deposit`/`Withdraw` call against this pool reproduces the same panic, permanently freezing any coin/PC funds sent into the pool's vaults through those instructions.
