### Title
Webhook `shop` identity is not covered by HMAC verification, allowing shop-domain spoofing in `Webhooks::Registry.process` - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then hands the caller-supplied `x-shopify-shop-domain` header straight through to the app's handler as the authenticated tenant identity. The HMAC never covers that header, so the “shop” binding the app trusts is not the same value that was cryptographically verified.

### Finding Description
`Webhooks::Registry.process` does:
```ruby
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
...
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))
``` [1](#0-0) 

`Utils::HmacValidator.validate` computes the signature only from `verifiable_query.to_signable_string`, and for a webhook `Request`, `to_signable_string` returns `@raw_body` — the request body only: [2](#0-1) 

Meanwhile, `Request#shop` is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, which is completely outside the HMAC computation: [3](#0-2) 

`HmacValidator` itself just compares the computed HMAC of the body against the header-supplied `hmac` value; it never binds `shop` into the signature: [4](#0-3) 

Equality that should hold but doesn't: *the shop value cryptographically bound by the HMAC* must equal *the shop value trusted/acted on by the handler (`WebhookMetadata#shop`)*. Since the HMAC only signs the raw body, an attacker who possesses one valid `(raw_body, hmac)` pair issued by Shopify for their own shop (any developer/merchant with the app installed can trigger a real webhook and capture it) can replay that same body+hmac to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header (e.g., a victim's shop domain). `HmacValidator.validate` still returns `true` because it only checks the body, and `Registry.process` dispatches to the handler with `shop: "victim-shop.myshopify.com"` — an identity the attacker fully controls and that Shopify never attested to.

This directly matches the required bug class: “a field acted on but not covered by the HMAC” — here, `shop` is acted on (passed to the app's business logic as the authenticated tenant) but is not part of the signed payload.

### Impact Explanation
If a host application uses `WebhookMetadata#shop` to select which merchant's session/access token/data to touch (the intended and documented use of this field), an attacker can forge webhook deliveries that claim to originate from any Shopify shop while carrying event data of their choosing (constrained to whatever body they can get validly signed for their own store), achieving cross-tenant impersonation of webhook events. This falls under the “cross-tenant access” Critical impact category, since the identity binding the gem is supposed to guarantee (`shop` is authentic because HMAC validated the request) is broken.

### Likelihood Explanation
Exploitation requires only: (1) the attacker to have — or create — a Shopify development store/app installation capable of receiving at least one real webhook (trivial, e.g., install any free/dev app and trigger `orders/create` or similar on their own store), and (2) the ability to POST directly to the victim app's public webhook endpoint with custom headers, which is inherent to how webhook endpoints work (no additional secrets or network position needed). No access token, `client_secret`, or privileged account is required. This is a fully unprivileged-internet-user analog.

### Recommendation
Bind the shop (and ideally topic/webhook-id/api-version) into the material verified by the HMAC, or otherwise cross-check the header-derived `shop` against a value independently established by the app (e.g., looked up via the resource in the payload, or by requiring hosts to pin one shop per registered webhook URL). At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must not be used as a trust boundary for session/token lookup without additional verification.

### Proof of Concept
1. Attacker installs the app on their own store `attacker-shop.myshopify.com` and triggers a webhook event (e.g., updates a product) so Shopify sends a legitimately HMAC-signed webhook to the app's endpoint. Attacker captures the raw body and the `x-shopify-hmac-sha256` value from that real delivery (they control the receiving infrastructure or can proxy/log it).
2. Attacker crafts a new HTTP POST to the same app webhook endpoint, reusing the captured `raw_body` and `x-shopify-hmac-sha256`, but sets:
   ```
   x-shopify-shop-domain: victim-shop.myshopify.com
   x-shopify-topic: <same topic>
   ```
3. `Webhooks::Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (= `raw_body`) and matches the attacker-supplied HMAC — validation passes: [5](#0-4) 
4. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, i.e., the app processes a spoofed event as if it came from the victim shop, despite Shopify never having sent any webhook for that shop with this content.
