### Title
Webhook `shop` field is trusted for tenant identity but not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` (and `topic`, `webhook_id`, `api_version`) values from HTTP headers, while the HMAC signature verified by `Utils::HmacValidator` covers only the raw request body. `Registry.process` validates the HMAC and then hands `request.shop` straight to the app's handler as the authoritative tenant identifier, without that value ever being bound to the signature that was actually verified.

### Finding Description
`Request#to_signable_string` returns only the raw body: [1](#0-0) 

But `shop`, `topic`, `webhook_id`, and `api_version` are all read from headers that are not part of that signable string: [2](#0-1) 

`Registry.process` validates the HMAC using `Utils::HmacValidator.validate(request)`, which calls `request.to_signable_string` (i.e. only the body) against `request.hmac`, and — once that passes — immediately trusts `request.shop` (and the other unsigned headers) to construct the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

`Utils::HmacValidator.validate` itself only checks the body-derived `to_signable_string` against the secret: [4](#0-3) 

The identity binding that is broken: the `shop` value the handler acts on (`request.shop`, taken from the `X-Shopify-Shop-Domain`/`shopify-shop-domain` header) is not equal to, nor cryptographically bound to, the bytes actually covered by the HMAC (`@raw_body` only). Since the HMAC secret (`Context.api_secret_key`) is the same app-wide secret used for every shop that installs a given public app, any holder of a valid `(body, hmac)` pair for one tenant (e.g., their own shop, where they can trigger legitimate webhooks by taking normal actions like creating an order) can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header value. The signature will still validate because the shop header is never part of `to_signable_string`, and the forged `shop` field flows unchecked into `WebhookMetadata.shop`, which host applications use to select tenant-specific session/storage state.

### Impact Explanation
This enables cross-tenant confusion at the webhook-processing boundary: a party controlling any shop where the app is installed can produce webhook payloads that are accepted as valid (HMAC passes) but attributed to a different shop of their choosing, because the shop header is un-signed. Depending on how the host app uses `WebhookMetadata#shop` (e.g., looking up per-shop sessions or writing per-shop records), this can lead to cross-tenant data writes/reads — matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires only the ability to install the app on one's own shop (or otherwise cause a legitimate webhook to fire) and the ability to send a crafted HTTP request with a substituted shop-domain header to the app's public webhook endpoint — both are attacker-controlled unprivileged actions. It requires no leaked secrets, tokens, or TLS interception, since the attacker can generate their own valid `(body, hmac)` pair for their own shop and reuse it with a different header.

### Recommendation
Include the shop domain (and other trust-relevant headers such as topic/webhook id) in the HMAC-signed material, or otherwise cryptographically bind the `shop` value to the verified payload, e.g., by mandating that the raw body/signature only ever be trusted for the shop under whose registered webhook subscription the request was expected, and rejecting any mismatch server-side (such as cross-checking against a known/expected shop per subscription) rather than trusting the header unconditionally.

### Proof of Concept
1. Attacker installs the target public app on their own shop `attacker.myshopify.com` and triggers a webhook (e.g., `orders/create`) to obtain a legitimate `(raw_body, X-Shopify-Hmac-Sha256)` pair signed with the app's shared `api_secret_key`.
2. Attacker replays this exact `raw_body` and `hmac-sha256` value to the app's webhook endpoint, but sets `shopify-shop-domain: victim.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `request.to_signable_string` (`@raw_body`) against the HMAC — this passes because body and hmac are unmodified.
4. `WebhookMetadata.new(... shop: request.shop ...)` is built using the attacker-forged `victim.myshopify.com` value and passed to the host app's handler, which now processes attacker-controlled data as if it originated from `victim.myshopify.com`.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
