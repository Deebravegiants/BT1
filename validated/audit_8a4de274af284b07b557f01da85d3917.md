### Title
Webhook shop/topic/webhook-id identity is not bound to the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request body, then trusts the `shop`, `topic`, and `webhook_id` values taken from separate, unsigned HTTP headers to dispatch the payload to the host app's handler. Because the signed bytes and the identity fields used afterward are not the same data, an attacker who can obtain any single valid `(body, hmac)` pair for the app (e.g., from their own, unprivileged store) can replay it with a forged `x-shopify-shop-domain` header and have it accepted as authentic for a different tenant.

### Finding Description
`Utils::HmacValidator.validate` computes and compares the HMAC only against `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` returns only the raw HTTP body — it does not include the shop domain, topic, or webhook id: [2](#0-1) 

`Registry.process` validates that HMAC, then immediately reads `request.shop`, `request.topic`, and `request.webhook_id` — values pulled from headers that were never part of the signed content — and forwards them to the app-defined handler as trusted tenant/topic metadata: [3](#0-2) 

This is the exact "field acted on but not covered by the HMAC" pattern: the binding that should hold is `hmac_signed(shop, topic, webhook_id, body) == received(shop, topic, webhook_id, body)`, but the gem only enforces `hmac_signed(body) == received(body)`. `shop`, `topic`, and `webhook_id` are free variables an attacker can set independently of the signature.

Critically, the signing secret (`Context.api_secret_key`) is the app's single `client_secret`, shared across *all* shops that install the app — it is not shop-specific. That means a valid `(body, hmac)` pair generated from a webhook the attacker legitimately receives on their **own**, unprivileged development/test store is cryptographically valid for **any** shop using the same app, since the shop identity is never part of the signed material.

### Impact Explanation
An unprivileged attacker who operates any store that has the target app installed (trivial — free Shopify dev/test stores) can:
1. Trigger a webhook on their own store to receive a legitimate `(raw_body, x-shopify-hmac-sha256)` pair signed with the shared `api_secret_key`.
2. Replay that exact body and HMAC to the app's public webhook endpoint, but substitute the `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) header with an arbitrary victim shop domain.
3. `Registry.process` validates the (still-correct) HMAC over the body and dispatches the handler believing the event originated from the victim shop.

Any host application logic that uses the `shop` field from `WebhookMetadata` to look up stored access tokens, apply mutations, or make authorization decisions on behalf of "the shop" will act under a forged tenant identity — this is a cross-tenant confusion/spoofing primitive reachable without any credentials belonging to the victim shop.

### Likelihood Explanation
High for anyone building on this gem's webhook feature as documented: obtaining a legitimate body+HMAC pair requires only an attacker-owned store with the target app installed (no privileged access, no leaked secrets), and replaying an HTTP request with modified headers is trivial. The only limiting factor is that the attacker needs body content that is meaningful for the topic they want to spoof, which is achievable for many generic/templated webhook topics.

### Recommendation
Include the tenant-identifying headers (`shop-domain`, `topic`, and ideally `webhook-id`/timestamp) in the HMAC-signed material — or otherwise cryptographically bind them — rather than relying on the body alone. At minimum, `to_signable_string` in `lib/shopify_api/webhooks/request.rb` should incorporate the shop domain and topic so `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` fails when these headers are altered independently of the signed body.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store, `attacker-shop.myshopify.com`.
2. Attacker triggers (or waits for) a webhook, e.g. `orders/create`, and captures the raw POST body `B` and header `x-shopify-hmac-sha256: H`, where `H = Base64(HMAC-SHA256(api_secret_key, B))`.
3. Attacker crafts a new HTTP request to the app's webhook endpoint with:
   - Body: `B` (unchanged)
   - Header `x-shopify-hmac-sha256: H` (unchanged, still valid)
   - Header `x-shopify-shop-domain: victim-shop.myshopify.com` (forged)
   - Header `x-shopify-topic: orders/create`
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `HMAC(B)`.
5. The registered handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, and any app logic keyed on `shop` operates as if the event genuinely came from the victim tenant.
