## Title
Webhook shop/topic identity not bound to HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`, `lib/shopify_api/utils/hmac_validator.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, but then trusts the `shop`/`topic` values taken from unsigned HTTP headers to identify the tenant and dispatch business logic. Because the app's `client_secret` (used as the HMAC key) is shared across every shop that installs the app, any shop owner who has installed the app can generate a body/HMAC pair that is valid for *their own* shop and then replay it with a forged `x-shopify-shop-domain` (and/or `x-shopify-topic`) header pointing at a victim shop. The signature check still passes because the header is not part of the signed material, letting the attacker's webhook be processed as if it originated from the victim tenant.

### Finding Description
`Utils::HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` and the app's secret: [1](#0-0) 

For webhook requests, `to_signable_string` returns only the raw body: [2](#0-1) 

while `shop`, `topic`, and `webhook_id` are read directly from attacker-controllable headers with no cryptographic binding to the HMAC: [3](#0-2) 

`Registry.process` checks only the HMAC of the body, then immediately dispatches the handler using the unauthenticated `request.shop` and `request.topic` as the tenant/event identity: [4](#0-3) 

This breaks the intended identity binding `hmac_verified_bytes == identity_used_for_dispatch`. In this gem, the equality that should hold is:

`HMAC(client_secret, signed_material) valid ⇒ signed_material fully determines the tenant (shop) the payload is attributed to`

But the actual behavior is:

`HMAC(client_secret, raw_body) valid` (says nothing about `shop`) `⇒ shop is taken from an unsigned header`

Because `client_secret` is per-app, not per-shop, any merchant who installs the app can legitimately obtain a `(raw_body, hmac)` pair signed with the *same* secret used for every other installation of that app. That attacker can then submit that same body/HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header for a different, victim shop domain (and/or forging the `topic` header), and the library will report this to the handler as an authentic webhook for the victim shop.

### Impact Explanation
This is a cross-tenant integrity/access issue (Critical per the given impact categories: "cross-tenant access"). A malicious merchant with a legitimate but low-privilege installation of the app can:
- Cause the host app to process forged data (e.g., `orders/create`, `app/uninstalled`, `customers/redact`, `shop/update`) attributed to another, victim shop.
- Trigger tenant-scoped side effects (e.g., app-uninstalled cleanup, GDPR redaction, order/inventory sync) against a shop the attacker does not control, since the only thing verified is that *some* installation of the same app produced the body — not which shop it belongs to.

### Likelihood Explanation
Exploitability requires the attacker to have their own (even free/trial) installation of the target app to obtain valid `(body, hmac)` pairs, and knowledge of the victim shop's `myshopify.com` domain (public information). No access token, `client_secret`, or privileged account is required — this matches the "unprivileged internet user" threat model, since the attacker merely replays their own legitimately-received webhook while altering an unsigned header.

### Recommendation
Bind the shop (and ideally topic) into the material that is authenticated, or otherwise validate that the `shop` header used for dispatch corresponds to an installation whose access token/session the app has on record and matches the shop the webhook was registered for, rather than trusting the header value directly once the body-only HMAC passes. At minimum, document/enforce that `request.shop` must be independently corroborated (e.g., against a known/allow-listed set of installed shops) before being used as a dispatch key, since the current `to_signable_string` in `lib/shopify_api/webhooks/request.rb` does not include the shop domain.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com`, using the app's real `client_secret` (shared across all installs of that app).
2. Attacker triggers a webhook (e.g. `orders/create`) on their own store, capturing the raw body `B` and the valid `x-shopify-hmac-sha256` header `H = HMAC-SHA256(client_secret, B)`.
3. Attacker POSTs `B` with header `H` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com` and `x-shopify-topic: app/uninstalled` (or leaves the original topic if desired).
4. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` succeeds because it only checks `B` against `H`.
5. `Registry.process` in `lib/shopify_api/webhooks/registry.rb` (line 198) invokes the app's handler with `shop: "victim.myshopify.com"`, causing the host application to process attacker-controlled data as authoritative content for the victim tenant.
