### Title
Webhook shop attribution is not covered by HMAC verification, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [1](#0-0)  while the tenant-identifying `shop` value is read from the unauthenticated `shop-domain` header [2](#0-1) . `Utils::HmacValidator.validate` only checks the HMAC over `to_signable_string`, i.e. the body, and never over the shop header [3](#0-2) . `Registry.process` treats a passing HMAC check as proof the request "did indeed come from Shopify" (per the gem's own documentation) and then forwards `request.shop` verbatim as the tenant identity to the app's handler [4](#0-3) .

### Finding Description
The equality the gem is supposed to enforce is: `shop attributed to the webhook == shop cryptographically bound by the HMAC`. That equality does not hold.

- `Webhooks::Request` reads `hmac` from the `hmac-sha256` header and `shop` from the `shop-domain` header, both attacker-controlled request headers [5](#0-4) .
- The signable string used for verification is `@raw_body` only [1](#0-0) .
- `HmacValidator.validate_signature` recomputes `HMAC-SHA256(api_secret_key, to_signable_string)` and compares it to the header HMAC [6](#0-5) . The shop domain never enters this computation.
- `Registry.process` raises only if the HMAC check fails; otherwise it builds `WebhookMetadata` using `request.shop` as the authoritative tenant identity and dispatches it to the app's handler [4](#0-3) .
- The gem's own documentation instructs integrators to treat `data.shop` as trustworthy tenant identity and to key downstream work off it (e.g. `shop_domain: data.shop`), and explicitly states that `Registry.process` "will verify the request did indeed come from Shopify."

Because `api_secret_key` (the app's `client_secret`) is a single value shared across every installed shop [7](#0-6) , any party who can obtain one valid `(raw_body, hmac)` pair for the app — trivially achievable by installing the target app on their own store and subscribing to any webhook topic — can replay that exact body/HMAC pair to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop. The HMAC check still passes (it only validates the body), and `Registry.process` will happily attribute the payload to the victim shop.

### Impact Explanation
This breaks the tenant boundary the HMAC is supposed to enforce: an unprivileged holder of any single valid webhook for the app can inject arbitrary shop-attributed webhook data for any other shop into the host application, without needing that victim's credentials. Depending on how the host app uses `data.shop` (e.g., for `shop/redact`, `customers/redact`, `customers/data_request`, order/product update processing, billing, etc. — all mandatory or common topics the gem itself registers [8](#0-7) ), this enables cross-tenant data injection/impersonation, matching the Critical "cross-tenant access" category.

### Likelihood Explanation
Any internet user can trigger this without any privileged credential: they only need one legitimate webhook capture from their own (attacker-controlled) store on the same app, which is freely obtainable since app installation and webhook subscription require no special privilege. The replay requires only re-sending an HTTP POST with a modified header.

### Recommendation
Bind the shop domain (and other attributes the app relies on for tenant identity) into the HMAC-signed payload, or otherwise cryptographically verify that the `shop-domain` header matches the shop that legitimately owns the signed body (e.g., by requiring the body's own `myshopify_domain`/similar field, verified against the sender, or by including the header in the signable string when Shopify's docs support it). At minimum, document clearly that `request.shop` is not verified by `Registry.process` and must not be trusted for tenant attribution without additional verification.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and registers for a webhook topic the app handles (e.g. `orders/create`).
2. Shopify sends the attacker a real webhook: `raw_body = B`, header `x-shopify-hmac-sha256 = HMAC(secret, B)`, `x-shopify-shop-domain = attacker.myshopify.com`.
3. Attacker replays the identical `raw_body = B` and `x-shopify-hmac-sha256` value to the app's public webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `Utils::HmacValidator.validate` recomputes the HMAC over `B` only, which matches, so `Registry.process` proceeds and calls the app's handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: B, ...)`, causing the host app to process attacker-controlled data as if it originated from the victim shop.
