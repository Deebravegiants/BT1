## Title
Unvalidated cross-chain `from` field length causes a runtime panic in `HyperFungibleToken::on_accept` - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

## Summary
The `hyper-fungible-token` pallet's `on_accept` handler decodes an attacker-controlled ABI `Message` from an incoming ISMP `PostRequest` body and, for non-EVM source chains without an accompanying calldata signature, copies the arbitrary-length `message.from` bytes directly into a fixed 32-byte buffer with `copy_from_slice` — without first checking the length, unlike every other place in this file that performs the same conversion.

## Finding Description
`on_accept` is the `IsmpModule` entry point invoked by `pallet-ismp`'s message handler (`handle_incoming_message`) whenever any relayer delivers a proven cross-chain `PostRequest` targeting this pallet — i.e. it is reachable from a single relayed message with no privilege required. [1](#0-0) 

The `Message` is `abi_decode`d from the raw request `body`, so every field, including `message.from` (a dynamic `bytes` value), is fully attacker-controlled and can be any length.

Later, when the message carries optional calldata (`message.data`) with no `signature` field, the code derives the dispatch `origin` from `message.from`: [2](#0-1) 

For the EVM-source branch it correctly truncates to the last 20 bytes regardless of input length (`&from_bytes[from_bytes.len()-20..]`), but for the non-EVM branch it does:
```rust
let mut account = [0u8; 32];
account.copy_from_slice(from_bytes);
```
`copy_from_slice` panics unless `from_bytes.len() == 32` exactly. There is no length check here at all.

Contrast this with the *same conversion* performed correctly elsewhere in the very same file, in `on_timeout`: [3](#0-2) 

and in `on_accept`'s own beneficiary (`to`) handling just above: [4](#0-3) 

Both of these correctly branch on `len() == 32`/`len() == 20` and return a typed `HftError` otherwise. The `from_bytes` conversion inside the calldata-execution branch of `on_accept` is the one place this pattern was not applied, so any `message.from` value whose length is not exactly 32 bytes (e.g. 0, 1, 20, 33 bytes) triggers an unrecoverable Rust panic instead of a graceful `Result::Err`.

This directly parallels the CVE-2018-25018 bug class: a fixed-size buffer write (`memcpy`/`copy_from_slice`) driven by an attacker-supplied length field that is never validated against the destination buffer size.

## Impact Explanation
- The mint/transfer to the beneficiary (derived from the separately-validated `to` field) has already executed by the time this code runs, so the panic occurs mid-dispatch inside a runtime call.
- A panic inside on-chain WASM runtime execution is not a normal `DispatchError` — it is not caught by pallet-ismp's `?`-based error propagation, and aborts execution of the surrounding call. Because every validating node deterministically hits the same panic when processing the same relayed message/block, this can halt block execution/import for the message rather than simply failing one extrinsic gracefully.
- Even in the more benign interpretation (extrinsic-level abort with state rollback), the specific cross-chain request becomes permanently un-processable: the relayer cannot deliver it successfully, no error variant is recorded, and repeated delivery attempts keep panicking — a message that can never be delivered, matching the "route unable to deliver messages" impact category.
- This is reachable by any unprivileged actor able to get a `PostRequest` routed to this module (e.g., dispatching a small malformed HFT transfer with calldata and no signature from a non-EVM source chain), with no special permissions needed.

## Likelihood Explanation
High. Triggering this requires only:
1. A registered source contract for a chain that `!source.is_evm()` (any configured Substrate-family source, per `ContractToAsset`).
2. A non-empty `message.data` that decodes as valid `SubstrateCalldata` with `signature: None`.
3. A `message.from` value whose length is not exactly 32 bytes.

All of these are attacker-controlled ABI fields in the request body; no cryptographic proof forgery or privileged role is needed — only a normal, provable cross-chain dispatch through the standard relaying path.

## Recommendation
Apply the same length validation used elsewhere in this file before constructing the fixed 32-byte account buffer, mirroring `on_timeout`'s pattern:
```rust
let mut account = [0u8; 32];
if from_bytes.len() == 32 {
    account.copy_from_slice(from_bytes);
} else if from_bytes.len() == 20 {
    account[12..].copy_from_slice(from_bytes);
} else {
    Err(HftError::InvalidSenderLength(from_bytes.len()))?
}
account.into()
```
More broadly, audit the codebase for any other `copy_from_slice`/fixed-array writes fed by ABI-decoded or otherwise externally-controlled `bytes`/`Vec<u8>` fields to ensure a length check always precedes the copy.

## Proof of Concept
1. Register a `ContractToAsset` mapping for a non-EVM `source` state machine and a contract address, with valid `Precisions` configured.
2. Craft a `PostRequest` whose ABI-encoded `body` decodes to an HFT `Message` where:
   - `to` is a valid 20 or 32-byte recipient (so minting succeeds),
   - `amount` is any valid value,
   - `data` decodes as `SubstrateCalldata { signature: None, runtime_call: <any bytes> }`,
   - `from` is set to a byte string of length other than 32 (e.g., 4 bytes).
3. Relay this request through the standard ISMP delivery path so `handle_incoming_message` invokes `HyperFungibleToken::on_accept`.
4. Execution reaches `account.copy_from_slice(from_bytes)` with `from_bytes.len() == 4`, causing an unhandled `panic!` inside on-chain execution instead of a typed `HftError`, as demonstrated by the length checks already present in `on_timeout` at [5](#0-4)  that are absent from the `on_accept` calldata-origin branch.
