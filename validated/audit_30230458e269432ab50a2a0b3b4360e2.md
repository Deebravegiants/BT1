### Title
Webhook `shop-domain` Header Is Not Covered by HMAC Verification, Enabling Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating the HMAC over the raw request body only, then hands the caller-supplied `shop-domain` header to the handler as the trusted tenant identifier. Because the HMAC signature never covers the `shop` field, an attacker who can produce (or replay) any body/HMAC pair that passes validation can freely choose which shop the handler believes the webhook belongs to, breaking the binding `hmac-authenticated bytes == shop attributed to the event`.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read from an unauthenticated header (`shopify-shop-domain` / `x-shopify-shop-domain`) and is never mixed into the signable string: [2](#0-1) 

`Registry.process` validates only the HMAC of the body, then constructs `WebhookMetadata` using `request.shop` directly, passing it straight to the app's handler as the authenticated tenant identity: [3](#0-2) 

The HMAC secret (`Context.api_secret_key`) is the app's single `client_secret`, shared across every shop that has installed the app — it is not shop-specific. Consequently, any HMAC that validates for one shop's webhook body validates identically regardless of which `shop-domain` header accompanies it, because that header is outside the signed content. This exactly matches the "shop authenticated vs. shop stored/acted upon" binding-break pattern: the value verified by the HMAC (`raw_body`) is disjoint from the value acted upon (`request.shop`, later exposed as `WebhookMetadata#shop` to the handler).

### Impact Explanation
Any party that can obtain one HMAC-valid webhook body (e.g., because they run their own store with the app installed and receive genuine webhooks) can replay that exact body to the app's webhook endpoint while substituting an arbitrary `shop-domain` header for a victim shop. Because `Utils::HmacValidator.validate` only checks the body signature, the request passes verification, and the handler is invoked believing the event/data belongs to the victim shop. Depending on how the host application's webhook handlers act on `WebhookMetadata#shop` (e.g., updating shop-scoped records, revoking sessions on `app/uninstalled`, adjusting billing/subscription state), this allows cross-tenant data corruption or unauthorized actions attributed to a shop the attacker does not control — a cross-tenant boundary violation.

### Likelihood Explanation
Exploitation requires the attacker to obtain at least one HMAC-valid body for the app (trivially achievable by installing the app on their own store and capturing a real webhook, or using a webhook topic that yields attacker-controlled body content such as `{}`), and then send a raw HTTP request to the app's public webhook endpoint with a forged `shop-domain` header. No access to `api_secret_key`, tokens, or privileged accounts is needed beyond ordinary app installation, which is the normal unprivileged-merchant flow. Likelihood is moderate: it depends on the host app's handler logic trusting `shop` for tenant-scoped actions, which is the intended and documented usage of `WebhookMetadata#shop` in this gem's webhook API.

### Recommendation
Bind the tenant identity into the authenticated material before trusting it: e.g., require host applications to independently verify that `request.shop` corresponds to a shop with a matching, previously-stored session/installation before acting on webhook data, or extend `to_signable_string`/documentation to explicitly warn that `shop-domain` is unauthenticated and must be cross-checked against known installed shops prior to use.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook with a fixed/predictable body (e.g., a topic whose payload is `{}` or otherwise attacker-influenced), capturing the valid `x-shopify-hmac-sha256` value computed over that body with the app's shared `client_secret`.
2. Attacker sends a POST request to the app's public webhook endpoint with:
   - the same raw body,
   - the captured valid HMAC header,
   - `x-shopify-shop-domain: victim-shop.myshopify.com` (arbitrary victim domain).
3. `Registry.process` validates the HMAC via `Utils::HmacValidator.validate(request)` — this passes because only `raw_body` is checked: [4](#0-3) 
4. The handler is invoked with `WebhookMetadata.new(... shop: request.shop ...)` where `shop` is `"victim-shop.myshopify.com"`, an unauthenticated value: [5](#0-4) 
5. Any host-app logic that trusts this `shop` for tenant-scoped side effects now acts on behalf of `victim-shop.myshopify.com` based on attacker-controlled/replayed content.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
