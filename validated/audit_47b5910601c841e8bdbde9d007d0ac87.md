### Title
Webhook `shop-domain` header is trusted by `ShopifyAPI::Webhooks::Registry.process` without being covered by the HMAC signature, allowing cross-tenant shop spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook by checking the HMAC over the raw body only, then hands the handler a `shop` value taken from an unauthenticated HTTP header. The equality the gem implicitly claims to the host app — "the shop this webhook is `for` == the shop whose HMAC secret validated it" — is never actually enforced, because the `shop` field is not part of the signed payload.

### Finding Description
`Registry.process` calls `Utils::HmacValidator.validate(request)` before dispatching to the handler: [1](#0-0) 

The HMAC validator computes the signature strictly from `to_signable_string`: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` returns only the raw request body — none of the headers, including `shop`, are included in the signed string: [3](#0-2) 

Yet immediately after HMAC validation succeeds, `Registry.process` reads `request.shop` (sourced from the `x-shopify-shop-domain`/`shopify-shop-domain` header) and passes it straight into `WebhookMetadata`, which is delivered to the app's handler as the authoritative tenant identifier: [4](#0-3) [5](#0-4) 

The documented contract explicitly tells integrators to trust `data.shop` as "The shop domain of the webhook" and to use it to key work per-tenant (e.g. `perform_later(shop_domain: data.shop, ...)`): [6](#0-5) 

So the binding the gem is supposed to guarantee is:
`hmac_valid(body, secret) == true` implies `request.shop == the tenant that legitimately produced (body, hmac)`.

That equality does not hold: `shop` is not an input to the HMAC computation at all. Any HTTP request with a *body+HMAC pair that is valid for the app's single shared `api_secret_key`* (e.g. captured from any legitimately delivered webhook, or from a webhook belonging to the attacker's own installed shop for a multi-tenant app) will pass `HmacValidator.validate` regardless of what `x-shopify-shop-domain` header value is sent alongside it. `Registry.process` then reports whatever `shop` value the attacker chose in `WebhookMetadata`, letting the host application record/act on webhook data under a shop identity that was never cryptographically bound to that payload.

This matches the report's bug class exactly: *"a field acted on but not covered by the HMAC."* Here `shop` is the load-bearing field, and `to_signable_string` deliberately excludes it (compare with `Auth::Oauth::AuthQuery#to_signable_string`, which correctly includes `shop` in its signed string): [7](#0-6) 

### Impact Explanation
For a multi-tenant app (the standard Shopify app model, one shared `api_secret_key` across all installed shops), an attacker who controls one installed shop can capture any valid `(raw_body, hmac)` pair delivered to their own webhook endpoint, then replay the same bytes to the app's public webhook callback route while substituting a victim shop's domain in the `shop-domain` header. `Registry.process` will accept the HMAC as valid (it only checks the body against the shared secret) and hand the handler `WebhookMetadata` claiming the payload belongs to the victim shop. Any host app that follows the gem's documented pattern of keying persistence/business logic off `data.shop` (as shown in the gem's own docs) will process attacker-supplied data as if it originated from the victim's shop — a cross-tenant data-integrity/confusion issue driven directly by a false guarantee this gem's `process` API implies it provides.

### Likelihood Explanation
Requires only an internet-reachable webhook HTTP endpoint (which every app using this gem's webhook feature must expose) and access to a single valid `(body, hmac)` pair for that app's secret. For any app with multiple installs sharing one `api_secret_key`, this is trivially obtainable by installing the app on an attacker-controlled shop and capturing its own legitimate webhook deliveries — no access to `api_secret_key`, access tokens, or privileged accounts is needed.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) header values in the HMAC-signed material, or otherwise cryptographically bind them to the body before exposing `request.shop` to `WebhookMetadata`. At minimum, `Webhooks::Request#to_signable_string` should incorporate the shop-domain header the same way `Auth::Oauth::AuthQuery#to_signable_string` incorporates `shop`, so that `HmacValidator.validate` fails whenever the claimed shop does not match the shop the payload was actually signed for.

### Proof of Concept
1. App `App` is installed on `victim-shop.myshopify.com` and `attacker-shop.myshopify.com`, sharing one `Context.api_secret_key`.
2. Attacker installs the app on `attacker-shop.myshopify.com` and receives a legitimate webhook POST with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(secret, B)` — valid per `HmacValidator.validate`/`Webhooks::Request#to_signable_string` (`lib/shopify_api/webhooks/request.rb:36-38`).
3. Attacker replays the exact same request to the app's public webhook callback route, keeping `B` and `H`, but sets header `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:189-199`) calls `HmacValidator.validate`, which succeeds because it only checks `B` against `H` (`lib/shopify_api/utils/hmac_validator.rb:26-31`), and never checks the shop header.
5. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: B, ...)` and, following the gem's documented usage pattern, processes/stores `B` under `victim-shop.myshopify.com`'s tenant record — a cross-tenant data confusion the app developer had no way to detect using this gem's API as documented.
