### Title
Withdraw's slippage protection (`min_coin_amount`/`min_pc_amount`) can be silently skipped, exposing LPs to sandwich attacks - (File: `program/src/processor.rs`, `program/src/instruction.rs`)

### Summary
`process_withdraw` only enforces the LP's minimum-output slippage guard when **both** `min_coin_amount` and `min_pc_amount` are `Some`. When either is `None` (which happens whenever a caller submits the shorter, backward-compatible `Withdraw` instruction payload, or explicitly encodes both fields absent), the check is skipped entirely and the withdrawal proceeds unconditionally at whatever `coin_amount`/`pc_amount` the pool computes at execution time.

### Finding Description
The `WithdrawInstruction` struct declares the minimum amounts as optional: [1](#0-0) 

Unpacking preserves this optionality — if the instruction data is exactly 8 bytes (just `amount`), both mins default to `None`: [2](#0-1) 

In `process_withdraw`, the redemption ratio (`coin_amount`, `pc_amount`) is computed from the pool's *current* vault balances via `Calculator::calc_total_without_take_pnl_no_orderbook` and `InvariantPool::exchange_pool_to_token`, i.e., whatever the live pool state is at execution time: [3](#0-2) 

Then the slippage guard is applied only if **both** optional values are present: [4](#0-3) 

If either `min_coin_amount` or `min_pc_amount` is `None` (which is the default/legacy path since the CLI builder `withdraw()` also accepts `Option<u64>` for both and only serializes them when both are `Some`), the `if` condition is `false`, the check block is skipped, and the LP burn/transfer proceeds regardless of how unfavorable `coin_amount`/`pc_amount` are: [5](#0-4) [6](#0-5) 

This mirrors the referenced DODO GSP report: the function purports to protect withdrawers via minimum-amount parameters, but the validation can be trivially bypassed (there, by passing `0`; here, by omitting the fields, which any client compiled against the shorter instruction encoding, or an attacker crafting the instruction data directly, can do), leaving the withdrawer with no slippage protection whatsoever.

### Impact Explanation
An LP submitting a `Withdraw` transaction without both minimum fields set (either because they use the legacy 8-byte instruction encoding, or because an integrator/attacker constructs the instruction data that way) has no protection against price manipulation between submission and execution. An attacker who observes the pending withdraw in the mempool can sandwich it: swap to shift the coin/pc vault ratio unfavorably before the withdraw executes, let the victim redeem LP tokens for far less value than expected, then reverse the swap to capture the difference. This is a direct, unprivileged theft of LP redemption value, reachable purely through the public `Withdraw` instruction with attacker-chosen swap transactions surrounding it.

### Likelihood Explanation
The bypass requires no special privilege — it only requires that the `Withdraw` instruction be built without both `min_coin_amount`/`min_pc_amount` populated, which is a legitimate, program-supported instruction shape (the shorter encoding is explicitly handled by `unpack`, and the `withdraw()` helper takes `Option<u64>` for both params, defaulting to `None`). Any user, wallet integration, or older SDK build that omits these optional parameters is exposed, and an attacker only needs standard sandwich-bot infrastructure (front-run/back-run swaps) to exploit it — a well-established attack pattern on AMMs. Likelihood is High.

### Recommendation
Remove the optionality of the slippage checks in `process_withdraw`: require `min_coin_amount`/`min_pc_amount` (or reject withdrawals when either is `None`) so the `ExceededSlippage` check in `program/src/processor.rs:1780-1786` always executes, rather than being conditioned on `is_some()` for both fields. At minimum, enforce the check whenever either one is `Some`, and consider deprecating/removing support for the no-slippage-check legacy instruction encoding entirely.

### Proof of Concept
1. Attacker observes a pending `Withdraw` transaction from Alice in the mempool that was built with the legacy/short instruction encoding (only `amount` supplied, no min amounts) — this is valid input per `AmmInstruction::unpack` (tag `4`, `program/src/instruction.rs:372-386`).
2. Attacker front-runs with a large `SwapBaseIn`/`SwapBaseOut` that shifts `amm_coin_vault`/`amm_pc_vault` balances unfavorably relative to Alice's LP share.
3. Alice's `Withdraw` executes: `process_withdraw` computes `coin_amount`/`pc_amount` from the now-skewed vault balances (`program/src/processor.rs:1719-1761`), and since `withdraw.min_coin_amount`/`min_pc_amount` are `None`, the guard at `program/src/processor.rs:1780-1786` is skipped — the withdrawal proceeds and burns Alice's LP for a reduced payout.
4. Attacker back-runs with the reverse swap, restoring the pool ratio and pocketing the difference extracted from Alice's redemption.
