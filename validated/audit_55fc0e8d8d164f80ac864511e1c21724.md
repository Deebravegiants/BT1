### Title
Opaque swap routes can hide an unauthorized wallet-token transfer in the caller’s authorization tree - (File: contracts/controller/src/strategies/swap.rs)

### Summary
Controller strategies accept `swap` as opaque `Bytes` and forward it to the configured swap aggregator without decoding or constraining the contracts named by the route. [1](#0-0) [2](#0-1)  Because strategy entrypoints authorize the caller once at the root, a malicious route can make route-selected code request an additional transfer of an unrelated token from that caller; if the submitted authorization tree contains that child, the wallet-token transfer executes alongside an otherwise successful strategy. [3](#0-2) 

### Finding Description
`StrategySwap` is defined only as raw `Bytes`, so the controller cannot determine which route components or contract addresses the router will invoke. [1](#0-0)  `swap_collateral`, `swap_debt`, `multiply`, and `repay_debt_with_collateral` expose this route argument directly to an authorized caller. [4](#0-3) [5](#0-4)  `swap_tokens` passes the opaque bytes to `execute_strategy`; it snapshots only the controller’s input and output token balances and grants the router one exact input-token transfer from the controller. [6](#0-5)  Its later checks bound controller overspending and require a positive controller output, but they do not inspect unrelated subinvocations that route-selected code performs under the original caller’s authorization tree. [7](#0-6) 

The strongest reachable path is `swap_collateral(caller, account_id, current, amount, new, swap)`, where `swap` encodes a route through an attacker-deployed contract. [8](#0-7)  During router execution, that contract can invoke `unrelated_token.transfer(caller, attacker, amount)`; the call is attached beneath the caller’s `swap_collateral` authorization rather than beneath the controller’s exact input-transfer authorization. [3](#0-2) [9](#0-8)  A fair-looking output then satisfies the controller’s measured-output check, while the signed child authorization moves unrelated wallet assets that were never supplied to the protocol. [10](#0-9) 

### Impact Explanation
This is theft of user funds beyond the declared swap input because the route can drain any token held by the caller for which a child transfer is included in the signed authorization tree. [3](#0-2)  The protocol’s balance-delta checks protect controller balances but do not measure or restrict the caller’s unrelated wallet balances. [11](#0-10)  The maximum loss is therefore the caller’s balance of every unrelated token whose malicious child transfer is signed, not merely `amount` or the supplied collateral. [12](#0-11) 

### Likelihood Explanation
An unprivileged attacker can deploy the malicious route component and distribute the encoded route, while the victim remains able to submit it through an ordinary `swap_collateral` call. [12](#0-11)  The strategy can still return a positive measured output and pass the final position checks, so the malicious child invocation does not need to make the visible swap economically abnormal. [13](#0-12)  Exploitation requires the victim to authorize the poisoned invocation tree, making the attack dependent on route construction or signing UX rather than being fully permissionless against an arbitrary account. [3](#0-2) 

### Recommendation
Do not treat `StrategySwap` as trustworthy opaque input. Require routes to resolve only against immutable or explicitly allowlisted venue contracts, reject payload-selected arbitrary contract addresses, and make the configured router fail any attempted subinvocation outside the expected venue call graph. Until route destinations are constrained, clients should decode every route and reject any `swap_collateral`, `swap_debt`, `multiply`, or `repay_debt_with_collateral` authorization tree containing children other than the expected transfer and venue calls.

### Proof of Concept
1. The victim owns a debt-free account with supplied USDC and also holds an unrelated wallet token that is not part of the lending operation. [14](#0-13) 
2. The attacker deploys a route component whose execution calls `unrelated_token.transfer(victim, attacker, victim_balance)`. [15](#0-14) 
3. The attacker constructs `swap` so the configured router invokes that component while still returning enough `new` tokens to satisfy the controller’s positive-output check. [13](#0-12) 
4. The victim submits `swap_collateral(victim, account_id, usdc_hub_asset, amount, eth_hub_asset, malicious_swap)`. [12](#0-11) 
5. The controller executes `victim.require_auth()`, withdraws the supplied collateral into controller custody, and forwards the opaque route to the configured router. [3](#0-2) [16](#0-15) 
6. During that router call, the attacker component requests the unrelated wallet-token transfer as a child of the victim’s authorization. [15](#0-14) 
7. If the transaction’s signed authorization tree includes that child, the unrelated wallet token moves to the attacker while the measured swap output remains positive and the controller’s input/output assertions pass. [7](#0-6) [13](#0-12)

/// Passes matching assets through only with an empty route; otherwise swaps.
pub(crate) fn swap_tokens_or_passthrough(
    env: &Env,
    refund_to: &Address,
    token_in: &Address,
    amount_in: i128,
    token_out: &Address,
    swap: &StrategySwap,
) -> i128 {
    if token_in == token_out {
        assert_with_error!(env, swap.is_empty(), GenericError::InvalidPayments);
        amount_in
    } else {
        swap_tokens(env, refund_to, token_in, amount_in, token_out, swap)
    }
}

/// Returns the output balance increase; rejects zero or negative receipts.
fn verify_router_output(env: &Env, token_out: &Address, balance_before: i128) -> i128 {

        env,
        token_out,
        &env.current_contract_address(),
        balance_before,
    );
    assert_with_error!(env, received > 0, StrategyError::NoSwapOutput);
    received
