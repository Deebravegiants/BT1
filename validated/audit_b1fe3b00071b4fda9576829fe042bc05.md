### Title
Webhook Shop Identity Spoofing via Unauthenticated Header - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by HMAC-validating the raw request body, but the `shop` (and `topic`/`webhook_id`/`api_version`) value handed to the app's handler is read from an HTTP header that is never included in the HMAC computation. This breaks the intended identity binding `shop_verified_by_hmac == shop_used_by_handler`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all read directly from unauthenticated HTTP headers via `shopify_header`, entirely outside of what is signed: [2](#0-1) 

`Utils::HmacValidator.validate` only ever verifies `verifiable_query.to_signable_string` (i.e., the raw body) against the computed signature — it never covers the `shop-domain` header: [3](#0-2) 

`Registry.process` validates the HMAC and then blindly forwards `request.shop` (an unauthenticated value) into `WebhookMetadata`, which is passed to the app's handler as the authoritative tenant identifier: [4](#0-3) 

The `WebhookMetadata` struct and documented handler usage confirm apps are expected to trust `data.shop` as the source-of-truth shop domain for routing/processing (e.g., looking up a shop's session or enqueuing per-tenant work): [5](#0-4) [6](#0-5) 

Because the HMAC secret is shared across all shops that install a given app, a merchant who has installed the app can legitimately trigger a webhook for their own store, capture the resulting valid `(raw_body, hmac)` pair, and then replay that exact request to the app's webhook endpoint while swapping only the `x-shopify-shop-domain` (or `shopify-shop-domain`) header to name a different, victim shop. `HmacValidator.validate` will still pass because it only checks the body's signature, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the webhook belongs to the victim shop.

### Impact Explanation
This is a cross-tenant identity binding break: the shop identity that passed HMAC authentication (the attacker's own shop, since only the attacker's shop actually produced a validly signed body) is not the shop identity the application acts on (the victim's shop, taken from the forged header). Any app relying on this gem's documented pattern (`data.shop` as tenant key, as shown in the gem's own webhook documentation) is exposed to cross-tenant confusion — e.g., enqueuing processing/state changes attributed to a victim shop, or fetching/overwriting the victim shop's session/data based on the spoofed shop domain.

### Likelihood Explanation
Any merchant who installs the app (a normal, unprivileged flow — no leaked secrets or special access required) can generate at least one validly signed webhook body for their own store, then freely forge the `shop-domain` header when forwarding it to the app's public webhook endpoint. No knowledge of `api_secret_key` is needed since the attacker only replays a body Shopify already signed for them.

### Recommendation
**Short term:** Bind the shop domain (and other identifying headers) into the signed material used for HMAC validation, or otherwise cryptographically tie the `shop-domain` header to the signed body before trusting it in `WebhookMetadata`. At minimum, document that consuming apps must independently verify `data.shop` is one of their known/installed shop domains before acting on it.

**Long term:** Have `ShopifyAPI::Webhooks::Request`/`Registry` verify header-derived fields against a signed representation (e.g., include shop domain, topic, and webhook id in the signable string) rather than trusting unauthenticated headers for any downstream authorization/routing decision.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook event (e.g., `orders/create`) for their own shop, capturing the raw POST body and the `x-shopify-hmac-sha256` header Shopify sent — this is a validly signed `(raw_body, hmac)` pair.
2. Attacker sends a new HTTP request to the app's webhook endpoint with the identical `raw_body` and `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged shop header successfully (no error, since headers are just read, not verified) — see `lib/shopify_api/webhooks/request.rb` lines 21-23.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `request.to_signable_string` (the raw body) against the HMAC — it passes since the body/HMAC pair is legitimate — see `lib/shopify_api/webhooks/registry.rb` line 190 and `lib/shopify_api/utils/hmac_validator.rb` lines 12-22.
5. The app's registered handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` and processes/attributes the webhook data as if it came from the victim shop.

          received_signature = verifiable_query.hmac
