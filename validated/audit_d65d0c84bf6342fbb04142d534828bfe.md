### Title
Webhook HMAC Signature Does Not Cover the `shop-domain`, `topic`, or `webhook-id` Headers, Allowing Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, while `shop`, `topic`, and `webhook_id` are read directly from unauthenticated HTTP headers and passed downstream unchanged. `HmacValidator.validate` verifies the HMAC only over the raw body, so the identity fields that `Registry.process` uses to attribute the event to a tenant are never bound to the cryptographic signature.

### Finding Description
The relevant binding that should hold is:

`shop used to authorize/attribute the webhook == shop bytes actually covered by the verified HMAC`

`ShopifyAPI::Webhooks::Request` exposes `shop`, `topic`, and `webhook_id` purely from HTTP headers: [1](#0-0) 

But the value that is actually HMAC-signed is only the raw body: [2](#0-1) 

`HmacValidator.validate` computes the signature exclusively over `to_signable_string` (i.e., the body) and compares it against the `hmac-sha256` header: [3](#0-2) 

`Registry.process` then trusts `request.shop` (and `request.topic`) to route and construct `WebhookMetadata` passed to the host app's handler, without any additional check that the shop header was part of what was signed: [4](#0-3) 

Because the signature only proves “this body was HMAC’d with the app’s secret,” and says nothing about which shop or topic it belongs to, any two legitimate webhook deliveries (from any shop, including the attacker’s own shop if they install the same public app) yield a valid `(raw_body, hmac)` pair that can be replayed with **different** `shopify-shop-domain` / `shopify-topic` / `shopify-webhook-id` header values. The gem will still report `Utils::HmacValidator.validate(request)` as `true`, since these headers are outside the signed content, and will hand the handler a `WebhookMetadata` object whose `shop` field is attacker-controlled while carrying a body meant for a different topic/shop.

This exactly mirrors the report's bug class: "a field acted on but not covered by the HMAC" — here `shop` (and `topic`/`webhook_id`) are consumed to make trust decisions in `Registry.process`/handler dispatch but are never part of the verified signable string.

### Impact Explanation
This breaks the shop-identity/tenant boundary that the webhook signature is supposed to guarantee. An attacker who controls one shop that installs the same public app can capture a legitimate `(raw_body, hmac)` pair from their own webhook deliveries, then resend it to the app's webhook endpoint with a forged `shopify-shop-domain` header naming a victim shop. The signature check passes, and the host application's handler processes attacker-supplied body content attributed to the victim's shop — a cross-tenant data/attribution confusion classified as Critical (cross-tenant access) under the rules, since the tenant binding enforced by this gem's HMAC validation is not actually enforced for the shop field it hands to the handler.

### Likelihood Explanation
Any developer/attacker who can install the same public app on their own store (a normal, unprivileged action) automatically receives legitimately signed webhook deliveries to inspect. No secret key, leaked credential, or privileged access is required — only observation of one's own webhook traffic and the ability to POST a crafted request with substituted headers to the app's public webhook endpoint. This makes exploitation straightforward for any internet user with a Shopify Partner/store account.

### Recommendation
Include the identity-critical headers (`shop`, `topic`, `webhook_id`, `api_version`) as part of the signed/verified material, or otherwise cryptographically bind them to the body before trusting them in `Registry.process`. At minimum, `to_signable_string` in `lib/shopify_api/webhooks/request.rb` should incorporate these header values (matching Shopify's actual webhook HMAC scheme if it covers them) so that tampering with `shop`, `topic`, or `webhook_id` invalidates the HMAC check.

### Proof of Concept
1. Attacker installs the target public app on `attacker-shop.myshopify.com` and receives a legitimate webhook delivery, e.g.:
   ```
   headers: {
     "x-shopify-topic" => "orders/create",
     "x-shopify-hmac-sha256" => "<valid-hmac-for-body>",
     "x-shopify-shop-domain" => "attacker-shop.myshopify.com",
     "x-shopify-webhook-id" => "id-1"
   }
   body: '{"id":123, ...}'
   ```
2. Attacker resends the exact same `body` and `hmac` header to the app's webhook endpoint, but replaces:
   ```
   "x-shopify-shop-domain" => "victim-shop.myshopify.com"
   ```
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` parses `shop` as `"victim-shop.myshopify.com"`; `Utils::HmacValidator.validate(request)` still returns `true` because it only verifies `raw_body` against the (unchanged) hmac.
4. `Registry.process` dispatches to the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, causing the host app to process attacker-controlled webhook content as if it originated from and pertains to the victim shop.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
