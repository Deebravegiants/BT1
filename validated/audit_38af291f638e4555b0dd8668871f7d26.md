## Analog Found

### Title
Arithmetic Underflow in `BandwidthManager.purchase()` Decimal Scaling for Fee Tokens With >18 Decimals - (File: `evm/src/apps/BandwidthManager.sol`)

### Summary
`BandwidthManager.purchase()` computes a scaling factor as `10 ** (18 - dec)` where `dec` is the fee token's `decimals()`. If the configured fee token has more than 18 decimals, `18 - dec` underflows and the entire purchase path reverts, permanently bricking the contract's only user-facing entrypoint — the same root-cause pattern as the CamelotRelayer/UniV3Relayer `multiplier = 18 - decimals()` bug.

### Finding Description
In `purchase()`, the tier price (stored in 18-decimal units) is converted to the fee token's native decimal precision: [1](#0-0) 

```solidity
uint256 total18d = price18d * months;
address feeToken = IDispatcher(_host).feeToken();
uint8 dec = IERC20Metadata(feeToken).decimals();
uint256 scale = 10 ** (18 - dec);
```

This is unchecked-subtraction-style logic identical to the reported `multiplier = 18 - IERC20Metadata(_quoteToken).decimals()` pattern: it silently assumes `dec <= 18`. If `IDispatcher(_host).feeToken()` ever returns a token with more than 18 decimals (e.g. `YAMv2`-style tokens with 24 decimals), `18 - dec` underflows a `uint8`/`uint256` computation and Solidity 0.8's checked arithmetic causes every call to `purchase()` to revert unconditionally.

The project's own documentation acknowledges this exact limitation as an accepted assumption rather than an enforced invariant: [2](#0-1) 

The fee token is set by `IDispatcher(_host).feeToken()` on the host contract — a value the `BandwidthManager` does not control and cannot validate at deployment or call time, unlike `CamelotRelayer`/`UniV3Relayer` where the check would at least happen once, at construction. Here, the failure mode surfaces at every single call to `purchase()` — the sole revenue-generating entrypoint of the contract — for as long as the host's fee token has >18 decimals, whether that arises from a host-side fee-token change/misconfiguration or an unaudited target chain being onboarded with a >18-decimal fee token.

Contrast with the already-correct analog `_normalizeAmount` in `VWAPOracle.sol`, which explicitly branches on `decimals > 18` vs `< 18` and is proven correct by `testHighDecimalsNormalization` against a 24-decimal mock token: [3](#0-2) [4](#0-3) 

`BandwidthManager.sol` lacks this defensive handling entirely.

### Impact Explanation
If the fee token configured on the host ever has more than 18 decimals, `BandwidthManager.purchase()` reverts for every caller, permanently and unconditionally freezing the bandwidth-purchase route — no user can top up bandwidth for any app on any chain via this manager instance until a redeploy/reconfiguration. This matches the allowed impact class "a route unable to deliver messages": the ISMP dispatch to `pallet-bandwidth` can never be reached because the transaction reverts before `IDispatcher(_host).dispatch(...)` is invoked.

### Likelihood Explanation
Reachable by any unprivileged bandwidth purchaser calling the public `purchase()` function — no special privileges required. Triggering condition depends on the host's `feeToken()` decimals, which is outside `BandwidthManager`'s control; while current supported fee tokens are documented as ≤18 decimals, this is an unenforced assumption, not a code-level guarantee, making the contract fragile to any future fee-token configuration with higher precision.

### Recommendation
Mirror the `VWAPOracle._normalizeAmount` pattern: branch on whether `dec` is greater than, less than, or equal to 18, using multiplication in one direction and division in the other, instead of computing `10 ** (18 - dec)` unconditionally. Alternatively, validate and cap/reject fee tokens with more than 18 decimals when the host's fee token is read, and add a defensive check/test for this case in `BandwidthManager`.

### Proof of Concept
1. Deploy `BandwidthManager` and configure a host whose `feeToken()` returns a token with 24 decimals (e.g., mint a mock `ERC20Token` with `decimals_ = 24` per `evm/tests/foundry/mocks/ERC20Token.sol`).
2. Configure a tier via `SetTiers`/`onAccept` so `tierPrice[tier] != 0`.
3. Call `purchase(app, tier, months, chain)` as any unprivileged user.
4. `dec = 24` → `scale = 10 ** (18 - 24)` underflows → the call reverts, and this occurs on every subsequent call for as long as the host uses this fee token, per [1](#0-0) .

Two implications:

1. **Fee tokens with `decimals > 18` would underflow `(18 - dec)`.** This is not a concern in practice — the supported fee tokens are all `≤ 18` decimals.
2. **Tier prices must be representable at the local fee-token's decimals after multiplication by `months`.** A tier priced at `10**12` (a hypothetical sub-penny SKU) and a 6-decimal fee token would revert with `PriceNotRepresentable()` because the 18-decimal value doesn't divide cleanly. Set tier prices to multiples of `10**12` to keep them clean on 6-decimal fee tokens.

```text
    function _normalizeAmount(uint256 amount, uint8 _decimals) private pure returns (uint256 normalized) {
        if (_decimals == 18) {
            return amount;
        } else if (_decimals < 18) {
            return amount * (10 ** (18 - _decimals));
        } else {
            return amount / (10 ** (_decimals - 18));
        }
    }
```
