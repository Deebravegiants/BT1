### Title
Webhook shop-domain identity not covered by HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while the `shop` (tenant identity) is read from an unauthenticated header. `Registry.process` validates the HMAC and then trusts `request.shop` to build the `WebhookMetadata` handed to the app's handler, without that value ever being part of the signed material. This breaks the equality that should hold between "the shop the signature proves the payload came from" and "the shop the handler is told the payload came from."

### Finding Description
`Utils::HmacValidator.validate` verifies a `VerifiableQuery` by comparing the computed HMAC against `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `Request#to_signable_string` returns only the raw request body — it never includes the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers: [2](#0-1) 

`Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all pulled straight from HTTP headers with no cryptographic binding to the signed body: [3](#0-2) 

`Registry.process` validates only the body's HMAC, then immediately forwards `request.shop` (and the other unverified headers) to the app's `WebhookHandler` as tenant identity: [4](#0-3) 

The resulting `WebhookMetadata.shop` field is a plain, unauthenticated `String` consumed by the handler to determine which tenant/session the payload belongs to: [5](#0-4) 

**Root cause / broken identity binding**: the gem's contract is effectively `signed(body) == valid` implies `shop-domain header == origin shop`, but those are two independent, unrelated properties. Any request whose body/HMAC pair was legitimately produced by Shopify for *some* shop (e.g., an attacker's own free/dev store) will pass `HmacValidator.validate` regardless of which `x-shopify-shop-domain` (or `shopify-shop-domain`) header value accompanies it, because that header is never part of `to_signable_string`.

### Impact Explanation
This is a cross-tenant identity confusion: an attacker who legitimately receives one valid `(body, hmac)` pair from Shopify (trivially obtainable by installing the target app, or any app using this library, on their own store and triggering a webhook) can replay that exact body+HMAC to the same endpoint while substituting the `shop-domain` header for a victim shop. `Registry.process` will accept the HMAC (it never inspected the shop header) and hand the handler a `WebhookMetadata` claiming the payload is for the victim tenant. Any application logic that uses `data.shop` to select which merchant's session/data to update (a very common and recommended pattern per the docs) can be tricked into applying attacker-controlled webhook data to a different tenant's records — a cross-tenant data integrity/access issue.

### Likelihood Explanation
The prerequisite is only "possession of one validly-signed webhook payload from Shopify," which is available to any unprivileged internet user via a free Shopify development store and this library's own webhook flow — no access token, client secret, or privileged account is required. The header rewrite (swapping `x-shopify-shop-domain`) is a trivial HTTP-level modification once such a payload is captured or replayed.

### Recommendation
Include the tenant-identifying header (`shop-domain`) — and ideally `topic`/`webhook-id`/`api-version` — in the signed material, or otherwise cryptographically bind them (e.g., derive/verify shop identity from a source Shopify itself signs end-to-end, or require the app to independently verify that the shop in the header matches a shop that is expected to be sending this specific webhook, such as by checking it against a known/installed-shops list before trusting `data.shop`). At minimum, document prominently that `request.shop`/`WebhookMetadata.shop` is *not* cryptographically authenticated by `HmacValidator.validate`, since the current API surface strongly implies verified webhooks are fully trustworthy end-to-end.

### Proof of Concept
1. Attacker installs the target app (or any app using `shopify-api-ruby`) on their own shop `attacker-shop.myshopify.com` and triggers a webhook, e.g. `orders/create`, capturing the raw request:
   - Headers: `x-shopify-topic: orders/create`, `x-shopify-hmac-sha256: <valid-hmac-for-body>`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, body `B`.
2. Attacker replays the exact same body `B` and `x-shopify-hmac-sha256` value to the same webhook endpoint, but changes the header to `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes HMAC over `@raw_body` (identical to step 1) and succeeds: [6](#0-5) 
4. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: B, ...)`, causing the host application to process attacker-controlled data as if it originated from the victim tenant.
