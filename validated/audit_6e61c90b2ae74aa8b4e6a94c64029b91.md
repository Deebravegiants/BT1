### Title
Unvalidated swap routes can invoke attacker-controlled pools that steal unrelated wallet tokens - (File: contracts/controller/src/strategies/swap.rs)

### Summary
A crafted `swap_collateral` route can place an attacker-controlled contract in the pool address slot. Although the controller narrowly authorizes only the expected input transfer to the configured router, the router invokes the route-selected pool as a nested call; that pool can request a completely unrelated token transfer from the victim, which simulation records beneath the victim’s `swap_collateral` authorization tree. [1](#0-0) [2](#0-1) 

### Finding Description
`swap_collateral(caller, account_id, current, amount, new, swap)` requires authorization from the account owner or an active delegate, but `swap` remains caller-controlled opaque route bytes. [3](#0-2) [4](#0-3) 

The controller passes those bytes to the configured router after authorizing only `token_in.transfer(controller, router, amount_in)`. [1](#0-0) 

The router decodes an address registry and constructs each hop’s `pool`, `token_in`, and `token_out` from attacker-supplied indices. [5](#0-4) [6](#0-5) 

Program validation checks only index bounds, structural links, split weights, and same-token swaps; it does not bind a pool address to a deployed venue registry or other allowlist. [7](#0-6) 

For an Aquarius-shaped hop, the router authorizes the pool to pull the routed input and then invokes the route-selected `pool.swap`. [8](#0-7) 

Because that pool executes below the victim’s authorized top-level invocation, a token transfer it initiates from the victim is recorded as another child of the victim’s authorization tree; if the victim signs the simulated tree, the transfer executes. [9](#0-8) 

### Impact Explanation
A malicious route can steal unrelated tokens held by the victim while still making the lending operation appear successful. The attacker-controlled pool can transfer any victim-held token whose corresponding authorization is included in the signed tree, independently of the collateral amount being routed. [10](#0-9) 

The attack is not limited to failed or economically unfavorable swaps: the pool can retain the routed input, return a valid listed output token from attacker inventory, satisfy the router’s positive-output and minimum-output checks, and leave the victim’s account in its expected post-swap state. [11](#0-10) [12](#0-11) 

This is theft of user funds. For a debt-free account performing `swap_collateral`, even the numerical post-operation risk gates provide no protection because they return immediately when the account remains debt-free. [13](#0-12) [14](#0-13) 

### Likelihood Explanation
The attack requires the victim to execute a malicious route and sign the authorization tree containing the extra token transfer. This is practical when a malicious interface, quote provider, or phishing flow presents the transaction as a normal collateral swap and the wallet does not prominently distinguish unrelated child transfers. [9](#0-8) 

No privileged role, compromised protocol key, oracle manipulation, or flawed market parameter is required: the attacker only needs to deploy an ABI-compatible pool contract and encode its address in the route supplied to the victim. [6](#0-5) [8](#0-7) 

### Recommendation
Bind route-selected pool addresses to a governance-managed allowlist or registry for each supported adapter and token pair, rather than accepting arbitrary pool addresses from the payload. [7](#0-6) 

Until route venues are restricted on-chain, clients must decode the route and reject any authorization tree containing calls beyond the expected single input transfer; this client-side check mitigates signing exposure but does not make arbitrary pools safe for contracts or wallets that auto-accept simulated auth. [9](#0-8) 

### Proof of Concept
1. Alice owns a debt-free account with supplied USDC collateral and holds an unrelated attacker-targeted token, `VICTIM_TOKEN`, in her wallet. [4](#0-3) 
2. The attacker deploys a contract exposing an Aquarius-compatible `swap(user, in_idx, out_idx, amount_in, min_out) -> u128` entrypoint and preconfigures it with Alice’s address, `VICTIM_TOKEN`, the attacker’s address, and the amount to steal. [8](#0-7) 
3. The attacker funds that pool with enough ETH to satisfy a plausible minimum output and gives Alice a `StrategyPayload` whose `assets` include USDC, ETH, and the malicious pool address, with one Aquarius swap instruction selecting those indices. [5](#0-4) [6](#0-5) 
4. Alice calls `swap_collateral(alice, account_id, usdc_key, amount, eth_key, malicious_route)`; the controller verifies her authority, withdraws the measured collateral to itself, authorizes the exact input transfer to the router, and invokes `execute_strategy`. [15](#0-14) [1](#0-0) 
5. The router pulls the input from the controller and dispatches the hop to the malicious pool. [16](#0-15) [17](#0-16) 
6. Inside its `swap` implementation, the malicious pool invokes `VICTIM_TOKEN.transfer(alice, attacker, victim_balance)`; simulation records that transfer as a child authorization under Alice’s `swap_collateral` invocation. [2](#0-1) 
7. The pool then transfers the expected ETH output to the router, allowing the min-out check, router payout, controller output check, collateral deposit, and finalization to succeed. [11](#0-10) [13](#0-12) 
8. If Alice signs the simulated authorization tree, her collateral swap completes while the unrelated `VICTIM_TOKEN` balance moves to the attacker. [18](#0-17)
