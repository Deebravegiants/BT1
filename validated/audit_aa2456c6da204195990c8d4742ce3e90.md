### Title
Webhook `shop` identity is not covered by HMAC verification, allowing shop-attribution spoofing on replayed webhooks - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and defines `to_signable_string` to return only the raw request body: [1](#0-0) [2](#0-1) 

The `shop` value that `Registry.process` attributes the event to is read straight from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, which is never included in `to_signable_string`. `HmacValidator.validate` only checks that the HMAC matches `verifiable_query.to_signable_string` (the body) against the received `hmac`: [3](#0-2) 

`Registry.process` performs exactly this check and then forwards `request.shop` — an unauthenticated field — into `WebhookMetadata`, which is handed to the app's handler as the trusted merchant identity for the event: [4](#0-3) [5](#0-4) 

This breaks the identity binding: `shop` claimed by the request ≠ `shop` that produced the HMAC-signed bytes. Contrast this with `Auth::Oauth::AuthQuery`, where `shop` *is* explicitly part of the signed content: [6](#0-5) 

Because only the body is signed, any unprivileged internet user who can obtain one genuine `(raw_body, hmac)` pair — for example by installing the app on a shop they control and letting Shopify send a real webhook — can replay that exact body+HMAC to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header. `HmacValidator.validate` still succeeds because it never inspects the shop header, and `Registry.process` will invoke the handler with `WebhookMetadata#shop` set to the attacker-chosen value instead of the shop that actually authored the payload.

### Impact Explanation
Apps built on this gem commonly use `WebhookMetadata#shop` to decide which merchant's stored offline session/access token to load and act on (this is the documented purpose of the `shop` field in `WebhookMetadata`). An attacker who forges the shop attribution can cause the host application to process attacker-controlled webhook body content under a victim merchant's identity/session, i.e. cross-tenant data confusion — data belonging to shop A is injected and processed as if it came from shop B, while any resulting API calls execute with shop B's access token. This matches the "cross-tenant access" tier of Critical impact, since the security boundary the HMAC is meant to enforce (this webhook genuinely originates from the named shop) is not actually enforced for the `shop` field.

### Likelihood Explanation
Exploitation requires the attacker to obtain at least one valid `(body, hmac)` pair, which is trivial for any developer who can install the target app on their own store (a normal, low-privilege action) and trigger a webhook event with a body they control (e.g., an order/product update with attacker-chosen field values). No possession of `api_secret_key`, access tokens, or any elevated Shopify permissions is required — only the ability to replay an HTTP request with a modified header, which any unprivileged internet user capable of reaching the app's public webhook endpoint can do.

### Recommendation
Bind the `shop` (and ideally `topic`/`api_version`) header values into the HMAC-signed content, or otherwise cryptographically bind the shop domain to the signature before `Registry.process` trusts it. At minimum, `Webhooks::Request#to_signable_string` should not be the sole basis for verifying the payload while a separate, unauthenticated header (`shop`) is passed on as trusted identity; downstream handlers relying on `WebhookMetadata#shop` should be documented as receiving an unauthenticated value, or the gem should validate that the shop belongs to a shop with an active/expected installation before dispatching.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com`; trigger a real webhook event (e.g. `orders/create`) with body content the attacker controls to whatever extent the resource allows.
2. Capture the genuine `raw_body` and its `x-shopify-hmac-sha256` value sent by Shopify to the app's webhook endpoint — this HMAC is valid for `secret = api_secret_key` because it is computed only over `raw_body`, as implemented in `Webhooks::Request#to_signable_string` (`lib/shopify_api/webhooks/request.rb:35-38`).
3. Replay an HTTP POST to the same webhook endpoint with the identical `raw_body`/`x-shopify-hmac-sha256`, but set `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate(request)` (`lib/shopify_api/utils/hmac_validator.rb:12-22`) returns `true` because it only checks the body against the HMAC.
5. `ShopifyAPI::Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-199`) invokes the registered handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: <attacker-controlled body>, ...)`, causing the app to process attacker-supplied data attributed to the victim shop.
