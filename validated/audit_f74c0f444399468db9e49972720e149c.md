No caching involved here—`getFeeQuote` calls `solverRelay.getQuote` fresh each time, per-call, with no shared cache keyed loosely across batch elements. Each `FeeEstimation`'s `quote` is scoped to that individual `_estimateWithdrawalFee` call's closure and pushed into the `feeEstimations` array by the caller only after `Promise.all` resolves successfully for **all** elements [1](#0-0) . If any single element throws (e.g. `validateWithdrawal` failure), `Promise.all` rejects entirely, and the caller never receives a `FeeEstimation[]` — so there's no path where quote hashes from a failed batch member leak into `signAndSendWithdrawalIntent`'s `relayParamsFn`, since that function only iterates over the `feeEstimations` array that was actually returned to and passed by the caller [2](#0-1) .

Examining every named cache (`getCachedSupportedTokens`, `getCachedStorageDepositValue` in omni-bridge/direct-bridge, `getCachedDestinationTokenAddress`, `getCachedIntentsStorageBalance`), they are all keyed on token/contract/chain identifiers — not on per-withdrawal parameters like destination address, amount, or feeInclusive:

- `getCachedSupportedTokens` keys on sorted chain list [3](#0-2) 
- `getCachedStorageDepositValue` (omni) keys on `contractId` alone [4](#0-3) 
- `getCachedStorageDepositValue` (direct-bridge) keys on `contractId+accountId` [5](#0-4) 
- `getCachedDestinationTokenAddress` keys on `chainKind:contractId` [6](#0-5) 
- `getCachedIntentsStorageBalance` uses one fixed global key [7](#0-6) 

All of these represent genuinely token-level or chain-level facts (minimum withdrawal amount, min storage balance, bridged token address, intents contract's own storage balance) that are identical regardless of which batch element requested them, at a given instant. A concurrent sibling populating the cache for `nep141:zec.omft.near` doesn't inject different or attacker-influenced data into another element's computation — it just supplies the *same correct value* that a standalone call would fetch itself. There is no per-account, per-destination, or per-amount keying that an attacker could collide, and the actual per-element outputs (`fee.amount`, `underlyingFees`, `fee.quote`) are computed independently inside each `_estimateWithdrawalFee`/bridge `estimateWithdrawalFee` call, not derived from another element's `FeeEstimation`.

The claimed equality — `FeeEstimation[i]` equals what a standalone estimate for `withdrawalParams[i]` would return at that instant — holds because:
1. Fee/quote values are computed per-call, not read from any batch-shared mutable state that differs by element identity.
2. Shared caches only store token/chain-level facts that are correct irrespective of caller identity.
3. A rejection anywhere in the `Promise.all` batch aborts the whole batch — no partial `FeeEstimation[]` with orphaned quote hashes is ever returned to feed into `signAndSendWithdrawalIntent`.

At most, a genuine TOCTOU race exists on-chain (e.g., NEAR storage balance changing between the RPC read and use), but that is a blockchain-state timing issue outside this repo's control, not a cache-poisoning bug reachable by shaping batch composition or ordering.
