## Title
Webhook `shop` identity field is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes and validates the webhook HMAC over the raw body only, while the `shop` (tenant identity) is read from a separate, unauthenticated HTTP header. `ShopifyAPI::Webhooks::Registry.process` passes this unauthenticated `shop` value straight to the app's webhook handler as the merchant identity, so the value an app relies on to select which tenant/session/access-token the event belongs to is never bound by the signature that is supposed to authenticate the request.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header, independent of the signed payload: [2](#0-1) 

`HmacValidator.validate` verifies `verifiable_query.hmac` against `verifiable_query.to_signable_string` (i.e., the raw body) using `Context.api_secret_key`: [3](#0-2) 

`Registry.process` only checks that the HMAC over the body is valid, then forwards `request.shop` — the unauthenticated header — to the app's handler as the tenant identity for the event: [4](#0-3) 

The identity binding that should hold is: `shop asserted to the handler == shop covered by the HMAC signature`. Because `to_signable_string` excludes the `shop-domain` header entirely, this equality never actually holds — the HMAC only proves "Shopify (or holder of the secret) produced this exact body," not "this body belongs to shop X." Any request with a body/HMAC pair that is valid for one shop (e.g., replayed, or obtained from any tenant of the app, since Shopify sends the same webhook secret across all shops installed on the app) can have its `shop-domain` header swapped to a different shop's domain and will still pass `Utils::HmacValidator.validate`, since that header is never part of the signed content.

### Impact Explanation
Apps built on this gem are expected to use `WebhookMetadata#shop` (built directly from `request.shop`) to resolve the correct shop/session and act on data (e.g., mark data deleted, update shop-scoped records, fetch a session/access token for that shop) once the HMAC passes. Because `shop` is never covered by the HMAC, an attacker who can obtain one valid signed webhook body (e.g., a webhook delivered to their own shop installation of the same app, since all shops share the same app-level `client_secret`/webhook signing key) can relabel it for a different shop domain and have the app process it as if it originated from that other tenant — a cross-tenant data confusion/spoofing condition reachable purely from the network side, without the attacker ever holding the target's or the app's credentials.

### Likelihood Explanation
Any developer who installs the target app on their own store legitimately receives correctly signed webhooks for their own shop. Swapping the `shop-domain` header before forwarding to the app's webhook endpoint is trivial and requires no secret material beyond what an ordinary installer of the app already has access to (their own webhook payload/HMAC pair). This is a self-contained defect in the gem's `Request`/`Registry` design and does not depend on the host app ignoring documented behavior — the gem itself never binds `shop` to the signature it verifies.

### Recommendation
Include the shop domain (and topic) as part of the signed material verified against the HMAC, or independently re-derive/verify the shop against a trusted, tenant-scoped context (e.g., cross-check `request.shop` against the session/shop the app expects for this webhook subscription) before trusting it in `WebhookMetadata`. At minimum, document and enforce that `WebhookMetadata#shop` must not be trusted without corroboration from the app's own installation registry, since `Request#to_signable_string` only covers `@raw_body`.

### Proof of Concept
1. Install the app on Shop A; capture a legitimately delivered webhook: headers include `x-shopify-hmac-sha256: H`, `x-shopify-shop-domain: shop-a.myshopify.com`, and raw body `B`.
2. Replay the same body `B` and same HMAC `H` to the app's webhook endpoint, but set `x-shopify-shop-domain: shop-b.myshopify.com`.
3. `Utils::HmacValidator.validate` in [3](#0-2)  succeeds because it only checks `B` against `H`.
4. `Registry.process` in [4](#0-3)  invokes the handler with `shop: "shop-b.myshopify.com"`, even though the event body actually originated from Shop A — demonstrating the broken `shop`-to-`HMAC` binding.
