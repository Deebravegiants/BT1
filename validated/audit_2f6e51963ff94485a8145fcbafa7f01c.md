## Custody Invariant Reduction

The Sound Protocol bug reduces to one invariant: **once minting has begun and users have committed based on a stated maximum supply, the issuer must not be able to unilaterally raise that supply ceiling.** Any function that lets a privileged party increase a capped-supply/max-mintable value after mint activity has started breaks this invariant and enables a rug via dilution.

## Candidate Paths Considered

1. `dispatchable_fungible_asset::register_dispatch_functions` — requires a `ConstructorRef`, which has only `drop` (no `store`) and can't be persisted past the creation transaction, so a malicious hook can't be attached later. **Rejected** — structurally safe.
2. `multisig_account::upsert_timelock` / `add_owners` — these are self-governed (require multisig-account signer via the k-of-n proposal flow itself), not unprivileged escalation. **Rejected** — expected owner-controlled behavior, not root-cause bypass.
3. `object::TransferRef` enable/disable ungated transfer — symmetric, creator-controlled, no supply/quantity implication. **Rejected**.
4. `aptos_token_objects::collection::set_max_supply` — allows the collection creator (via a persistable `MutatorRef`) to **increase** `max_supply` (for both `FixedSupply` and `ConcurrentSupply` variants) at any time, with the only guard being `max_supply >= current_supply`. **Kept** — this is a direct structural analog to the `editionMaxMintableUpper` bug.

## Title
Collection `max_supply` can be silently inflated by the creator after minting begins - (File: aptos-move/framework/aptos-token-objects/sources/collection.move)

## Summary
`collection::set_max_supply` lets the holder of a `MutatorRef` (the collection creator) raise a "fixed"/capped collection's `max_supply` at any point after tokens have already been minted, with no restriction tying the new value to the value promised at collection creation. This mirrors the Sound Protocol M-03 pattern where `editionMaxMintableUpper` could be manipulated post-mint to rug users who believed supply was capped.

## Finding Description
`create_fixed_collection` establishes a `ConcurrentSupply`/`FixedSupply` resource with a `max_supply` intended to represent a hard, user-visible cap on the collection ("a guaranteed, limited supply on-chain digital asset"). [1](#0-0) 

However, `set_max_supply` only enforces that the new `max_supply` is not below the *current* minted count — it does not prevent raising `max_supply` above the value originally advertised, and does so unconditionally regardless of how much minting has already occurred: [2](#0-1) 

The only gate is `mutator_ref`, generated once at creation time via `generate_mutator_ref`, but (unlike `ConstructorRef`) `MutatorRef` is a persistable capability the creator can call repeatedly, at any future point in the collection's lifetime: [3](#0-2) 

This is structurally identical to the audited bug: a privileged party can silently raise a supply ceiling that buyers relied on being fixed, at any time — including after most of the collection has already sold out, right before minting the "final" token.

## Impact Explanation
A collection marketed as fixed-supply (e.g., "10,000 max") can have its `max_supply` doubled, tripled, or set arbitrarily high by the creator after buyers have already minted/purchased tokens under the belief that supply was capped. Because Aptos NFT collection value (and secondary market pricing) is directly tied to `max_supply`/scarcity, this is a direct custody/value-integrity break: it corrupts the supply accounting invariant that purchasers rely on, diluting/devaluing the tokens already held by users and enabling the creator to mint and sell additional tokens far beyond the originally promised ceiling — a rug-pull via inflation, matching the exact impact class in the reference report (Critical/High: supply accounting corruption moving value away from existing holders).

## Likelihood Explanation
Likelihood is high: `set_max_supply` is a `public fun` reachable by anyone holding the collection's `MutatorRef` (the creator, by design), requires no special conditions besides `max_supply >= current_supply` (trivially satisfiable at any point before full sell-out), and is documented/available for exactly this purpose in the shipped framework — no additional bypass or edge-case is needed to trigger it.

## Recommendation
Mirror the Sound Protocol fix: disallow *increasing* `max_supply` once any tokens have been minted (`current_supply > 0` / `total_minted > 0`), or restrict `set_max_supply` to only ever decrease the cap (down to at least the current supply), removing the ability to raise it after mint has started. If increasing supply is a desired product feature, gate it explicitly (e.g., require it to be set at creation only, or require it to only be lowered post-mint), and document/emit clear on-chain signaling so indexers/marketplaces can flag any post-mint increase as a red flag.

## Proof of Concept
```move
// Creator publishes a "fixed" 100-supply collection.
let ctor = collection::create_fixed_collection(
    creator, description, /*max_supply=*/100, name, royalty, uri
);
let mutator_ref = collection::generate_mutator_ref(&ctor);

// Users mint tokens believing supply is capped at 100 (e.g., 95 minted).
// ... token::mint calls happen via a separate minting flow using `collection` ...

// Creator, holding the persisted mutator_ref, raises the cap post-mint:
collection::set_max_supply(&mutator_ref, 1_000_000);
// current_supply (95) <= new max_supply, so this succeeds — no restriction
// tied to "minting has begun," unlike the intended invariant.

// Creator can now mint far beyond the originally advertised 100-token cap,
// diluting existing holders' tokens.
```
This is directly demonstrable using the framework's own tests, which confirm `set_max_supply` succeeds for any `max_supply >= current_supply` with no post-mint-begin restriction: [4](#0-3) 

**Note on verification limits:** I was unable to fully confirm the exact ability set (`drop`/`store`) declared on the `MutatorRef` struct definition within the tool's indexed context (the struct definition itself wasn't returned by the final search), though its usage pattern across the file (stored in test helpers and invoked repeatedly across separate calls/tests) strongly indicates it is a persistable capability rather than a one-time-use ref. A Devin session with full file access would be needed to confirm the exact struct declaration and any additional call-site guards that might exist in downstream `token_objects` example minting modules layering restrictions on top of the raw `collection::set_max_supply` API.

    public fun set_max_supply(mutator_ref: &MutatorRef, max_supply: u64) acquires ConcurrentSupply, FixedSupply {
        let collection = object::address_to_object<Collection>(mutator_ref.self);
        let collection_address = collection.object_address();
        let old_max_supply;

        if (exists<ConcurrentSupply>(collection_address)) {
            let supply = &mut ConcurrentSupply[collection_address];
            let current_supply = supply.current_supply.read();
            assert!(
                max_supply >= current_supply,
                error::out_of_range(EINVALID_MAX_SUPPLY),
            );
            old_max_supply = supply.current_supply.max_value();
            supply.current_supply = aggregator_v2::create_aggregator(max_supply);
            supply.current_supply.add(current_supply);
        } else if (exists<FixedSupply>(collection_address)) {
            let supply = &mut FixedSupply[collection_address];
            assert!(
                max_supply >= supply.current_supply,
                error::out_of_range(EINVALID_MAX_SUPPLY),
            );
            old_max_supply = supply.max_supply;
            supply.max_supply = max_supply;
        } else {
            abort error::invalid_argument(ENO_MAX_SUPPLY_IN_COLLECTION)
        };

        event::emit(SetMaxSupply { collection, old_max_supply, new_max_supply: max_supply });
    }
