### Title
Webhook `shop-domain` header is trusted for tenant attribution but is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` authenticates incoming webhooks solely by verifying the HMAC over the raw request body, while the `shop` (tenant identity) is read from an HTTP header that is never included in the signed material. This breaks the intended binding `authenticated_bytes == acted_upon_identity`, allowing an attacker who possesses one validly-signed webhook body (e.g., from their own Shopify store) to relabel it with an arbitrary `shop-domain` header and have the host application process it as if it came from a different merchant.

### Finding Description
`ShopifyAPI::Webhooks::Registry#process` authenticates a webhook by calling `Utils::HmacValidator.validate(request)`: [1](#0-0) 

The validator computes/verifies the signature only over `request.to_signable_string`, which is defined as the raw HTTP body: [2](#0-1) 

The `shop` accessor, however, is read straight from the `shop-domain` header, which is not part of `to_signable_string` and thus is not covered by the HMAC at all: [3](#0-2) 

`Registry#process` then passes this unauthenticated `request.shop` value directly into `WebhookMetadata`, which is handed to the app's webhook handler as the tenant identity for the event: [1](#0-0) 

The `Utils::HmacValidator.validate` implementation confirms the scope of what is actually checked — the shared-secret HMAC is computed and compared only against `verifiable_query.to_signable_string`: [4](#0-3) 

The identity binding that should hold is: `shop attributed to the event == shop whose secret produced the verified HMAC`. Because `shop` is carried out-of-band in a header untouched by the signature, this equality is not enforced by the gem. Any body that carries a valid signature (which an attacker can obtain trivially for their own, legitimately-installed shop by triggering any webhook topic) can be replayed with a forged `shop-domain` header value, and `HmacValidator.validate` will still return `true` because it never looks at the header.

### Impact Explanation
This is a cross-tenant identity-confusion vector: the webhook subsystem authenticates *content* but not *sender identity*, and the gem hands the (unauthenticated) sender identity to the app as if it were verified. A host application that trusts `WebhookMetadata#shop` (which is exactly what the gem's own API surface encourages, since the shop field is exposed right next to the "verified" HMAC check) can be made to apply another merchant's data/action to the wrong tenant (e.g., an `app/uninstalled` or `customers/data_request` handler acting against the attacker-chosen shop domain using data belonging to the attacker's own store), which constitutes cross-tenant access mediated entirely by fields this library exposes and implicitly vouches for via its own "Invalid webhook HMAC" guard.

### Likelihood Explanation
Any unprivileged internet user who can install the target app on their own Shopify development store (a normal, no-privilege action) can obtain a body + HMAC pair that will pass `HmacValidator.validate`. Replaying that exact body with a different `X-Shopify-Shop-Domain`/`X-Shopify-Topic`-consistent header requires only a normal HTTP POST to the app's public webhook endpoint — no secrets, tokens, or elevated access are needed. The only external dependency is that the host app dispatches the webhook request through this gem's `Registry#process` and trusts the resulting `shop` field, which is the intended and documented usage pattern of the class.

### Recommendation
Include the `shop-domain` (and ideally `topic`/`webhook-id`) header values in the signed material verified by `HmacValidator`, or otherwise cryptographically bind the shop identity to the HMAC-verified payload before it is forwarded to handlers. Short of that, document prominently that `request.shop` is not authenticated by the HMAC check and that callers must independently verify it corresponds to a shop that actually has this app installed and matches an existing session/access token before trusting it.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and triggers any webhook topic (e.g., `orders/create`), capturing the raw POST body and the `X-Shopify-Hmac-Sha256` header Shopify sends — this HMAC is valid because it was produced with the app's real secret over that exact body.
2. Attacker resends the identical body and HMAC header to the app's webhook endpoint, but changes `X-Shopify-Shop-Domain` to `victim.myshopify.com`.
3. `Registry#process` calls `Utils::HmacValidator.validate(request)`; because `to_signable_string` only returns `@raw_body`, the comparison in `validate_signature` succeeds: [5](#0-4) 
4. Processing proceeds, and `handler.handle` receives `WebhookMetadata.new(... shop: "victim.myshopify.com" ...)`, i.e., the attacker's own webhook data is now attributed to the victim shop inside the app: [6](#0-5)
