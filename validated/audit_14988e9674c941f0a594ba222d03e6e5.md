### Title
Shared `Emporium` contract lets any caller steal principal/yield deposited into external positions by another shielded user via unauthenticated "stateless" ops - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`EmporiumUpgradeable` is a single shared contract instance that every Hinkal user routes external calls through when `externalActionData.externalActionId` targets Emporium. When an `EmporiumOperation` is executed with `invokeWallet == false` (or `stack.signerAddress == address(0)`), the call is made directly from the Emporium contract's own address (`op.endpoint.call{value: op.value}(op.callData)`), rather than from a user-specific wallet. Any resulting external position (e.g. vault shares, staked balance, lending deposit) is therefore custodied under the Emporium contract's shared identity, not under any individual user. `runAction` then hands 100% of the positive balance delta it observes to whichever caller happened to invoke it (`handleOut` → `transferERC20TokenOrETH(..., msg.sender, ...)`), exactly like the AutoRoller `combine()`/`eject()` bug where the entire collected/combined balance was sent to whoever called last, regardless of true ownership share.

### Finding Description
In `runAction`, when `stack.signerAddress == address(0)`, `verifyWallet` only marks `circomData.emporiumMessage` as used and returns — it performs **no signature check and no binding of the op to any particular depositor**: [1](#0-0) 

For the stateless branch, the call executes with `msg.sender == Emporium` against the arbitrary `op.endpoint`: [2](#0-1) 

Because the external protocol only ever sees `Emporium`'s address as depositor/owner, any position created there (vault shares, staking receipts, accrued yield) is fungible and shared across all Hinkal users who go through this path — there is no on-chain record tying a specific slice of that position to the depositor's UTXO/nullifier.

When the position is later unwound, `runAction` computes the delta purely from `balancesBefore`/`balancesAfter` of the tracked `erc20TokenAddresses` and gives the *entire* amount to `msg.sender` of the current call: [3](#0-2) [4](#0-3) 

This mirrors the reported bug: `divider.combine` pooled all YTs' yield onto the `AutoRoller` contract, and `eject()` transferred the *entire* contract's target balance to whichever user called it. Here, the pooled/shared custody point is the `Emporium` contract's own address for any stateless op, and `handleOut` transfers the entire observed delta to whoever calls `runAction`, with zero check that the caller is the one who originally deposited the underlying position. In contrast, the "stateful" path uses a per-user `HinkalWallet` (`onlyEmporium` gated, deployed/owned per signer) which does properly isolate custody: [5](#0-4) 
— but this isolation is entirely bypassed by the stateless branch (`signerAddress == address(0)` or `invokeWallet == false`), which is a fully supported, unauthenticated code path.

### Impact Explanation
Any unprivileged EOA can submit a `transact()` call targeting the Emporium external action with a crafted stateless `EmporiumOperation` that withdraws/redeems from an external protocol position previously opened (deposited into) by a different Hinkal user through the same shared Emporium identity. Because the withdrawal's proceeds are credited wholesale to `msg.sender` via `handleOut`, the attacker can redirect another user's principal and/or accrued yield into a UTXO under their own control. This is direct theft of shielded/in-flight user funds — a Critical impact per the rubric (theft of shielded funds via an action a wallet owner never authorized for that specific caller).

### Likelihood Explanation
No proof-of-ownership, signature, or nullifier binds a stateless Emporium op to the depositor who created the underlying external position. Any user who has previously routed a deposit through the stateless path (signerAddress = 0) exposes that position to being drained by any other Hinkal caller who knows (or can guess/observe on-chain) the vault/protocol address and constructs the matching withdraw calldata. This requires no special privilege, admin key, or relayer collusion — just knowledge of a public, already-executed on-chain deposit transaction (fully observable on-chain), making exploitation straightforward once such deposits occur.

### Recommendation
Ensure every stateless `EmporiumOperation` is cryptographically bound to the depositor who owns the resulting external position (e.g., require `stack.signerAddress != address(0)` with wallet-scoped custody for any op that can create or unwind a position holding value, or require Emporium to route all value-bearing external interactions exclusively through the per-user `HinkalWallet`). Alternatively, disallow the stateless (`signerAddress == address(0)`) branch from performing any call whose target can leave residual value/positions attributable to the caller-of-record rather than the original depositor, and enforce that `handleOut`'s balance delta can only be attributed to whoever's deposit created it (e.g. via position accounting keyed to the depositor's commitment/nullifier).

### Proof of Concept
1. User A calls `Hinkal.transact()` with `externalActionData.externalActionId` = Emporium, an `EmporiumStack` with `signerAddress = address(0)`, and one stateless `EmporiumOperation` that calls `vault.deposit(amount, receiver=Emporium)` on some ERC4626-like vault (`op.invokeWallet = false`, so it runs via `op.endpoint.call(...)` from `EmporiumUpgradeable`'s own address, per `runAction`'s "CASE 2" branch — lines 102-113). The vault share token is not included in `circomData.erc20TokenAddresses`, so no UTXO is created for it; the deposited value sits invisibly as vault shares owned by the shared `Emporium` contract.
2. Time passes and yield accrues to the vault position (or the attacker acts immediately for the principal).
3. Attacker (any unprivileged EOA) calls `Hinkal.transact()` with the same externalActionId, a fresh `EmporiumStack` (`signerAddress = address(0)`), and a stateless op calling `vault.redeem(shares, receiver=Emporium, owner=Emporium)`. Since `msg.sender` for the vault call is `Emporium` itself, the redeem succeeds (`Emporium` is both owner and caller).
4. `runAction` observes `balancesAfter - balancesBefore` for the underlying asset (now included in `circomData.erc20TokenAddresses`) as fully positive, and `handleOut` (lines 162-184) transfers that entire amount to the attacker's `msg.sender` and mints them a UTXO for it — stealing User A's deposited principal and any yield.

contract HinkalWallet is Transferer, IHinkalWallet {
    address public immutable emporium;

    event EthReceivedOnWallet(address indexed sender, uint256 amount);

    error NotAllowedToCallWallet();

    constructor(address _emporium) {
        emporium = _emporium;
    }

    modifier onlyEmporium() {
        if (msg.sender != emporium) {
            revert NotAllowedToCallWallet();
        }
        _;
    }

    function callHinkalWallet(
        address endpoint,
        bytes calldata data,
        uint value
    ) external onlyEmporium returns (bool success, bytes memory err) {
        (success, err) = endpoint.call{value: value}(data);
    }
