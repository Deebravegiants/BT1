## Finding

### Title
Front-running `Initialize2` to squat the deterministic pool PDA derived from `market_info`, permanently denying the legitimate pool creator that address - (File: `program/src/processor.rs`)

### Summary
`process_initialize2` derives every core pool account (`amm_info`, `amm_lp_mint`, `amm_coin_vault`, `amm_pc_vault`, `amm_target_orders`) as PDAs seeded off the `market_info` account key supplied by the caller, with no requirement that `market_info` correspond to a real, unowned, or program-validated market. [1](#0-0) [2](#0-1)  Because these accounts' addresses are 100% deterministic from a value that is visible in the mempool before the transaction lands, an unprivileged attacker can observe a pending `Initialize2` transaction and front-run it, submitting their own `Initialize2` with the same `market_info` key first (using arbitrary/dust mints and minimal `init_coin_amount`/`init_pc_amount`), just as in the reported `cancel` bug where an unchecked, front-runnable identifier let an attacker pre-empt a legitimate action tied to that identifier.

### Finding Description
The instruction's account-derivation helpers (`generate_amm_associated_account`, `generate_amm_associated_spl_mint`, `generate_amm_associated_spl_token`) use `market_info.key` as a PDA seed to create the pool, lp-mint, and vault accounts. The comments in the code explicitly acknowledge this is unchecked: `market_info` is documented as "Just a seed for AMM account. Can be any account." [3](#0-2)  There is no on-chain verification that `market_info` refers to a legitimate/expected OpenBook market, nor is there any binding between the `market_info` key and the transaction submitter beyond the `user_wallet_info.is_signer` check [4](#0-3) . The only guard against re-initialization is the `AlreadyInUse` check performed on the pool account after it has already been created by the PDA derivation [5](#0-4) , which is exactly analogous to the reported governance bug: the check happens too late to prevent the front-runner from claiming the identifier (there `proposalId`, here the `market_info`-derived PDA family) before the legitimate actor's transaction executes.

### Impact Explanation
Since the pool's core accounts are permanently and deterministically bound to `market_info.key`, once an attacker front-runs `Initialize2` for a given `market_info`, that PDA family (pool, lp mint, coin/pc vaults, target orders) is permanently occupied by the attacker's pool — with attacker-chosen mints/amounts and full control over the initial LP mint (they receive the initial LP position at `process_initialize2`'s liquidity-minting step [6](#0-5) ). The legitimate creator can never initialize the pool for that specific `market_info` again (permanent denial of service on that market identity), and any integrator or user who derives the "canonical" pool address from that market key will unknowingly interact with an attacker-controlled, potentially malicious/undercapitalized pool instead of the intended one.

### Likelihood Explanation
Any unprivileged actor monitoring the mempool for `Initialize2` transactions can extract the plaintext `market_info` account key from the transaction's account list and resubmit their own `Initialize2` instruction with a higher priority fee, requiring only the (small, refundable-to-attacker) pool-creation fee and dust token amounts to satisfy the non-zero vault checks [7](#0-6) .

### Recommendation
Bind pool creation to a value that cannot be pre-empted independent of the legitimate creator's intent — e.g., require `market_info` to be validated as an actual, program-recognized market account (owned by the expected market program and not attacker-supplied), or otherwise remove the ability for the PDA-deriving seed to be an arbitrary attacker-chosen account, so that pool identity cannot be squatted via mempool front-running.

### Proof of Concept
1. Alice builds an `Initialize2` transaction using `market_info = M` and broadcasts it.
2. Bob observes `M` in Alice's pending transaction in the mempool.
3. Bob submits his own `Initialize2` with the same `market_info = M`, arbitrary/cheap mints, and minimal `init_coin_amount`/`init_pc_amount`, with a higher fee so it lands first.
4. Bob's transaction succeeds: the PDAs for `amm_info`, `amm_lp_mint`, `amm_coin_vault`, `amm_pc_vault`, and `amm_target_orders` derived from `M` are all created and initialized under Bob's control, and Bob receives the initial LP mint.
5. Alice's transaction now fails with `AmmError::AlreadyInUse` when loading `amm_info` [5](#0-4) , permanently preventing her from ever creating the intended pool for market `M`.
