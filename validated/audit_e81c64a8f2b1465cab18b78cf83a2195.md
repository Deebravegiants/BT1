## Analysis

The Augur bug is a *partial-reset* pattern: `disavowCrowdsourcers` resets one piece of dispute state (the reporting chain) while leaving a related piece of state (`preemptiveDisputeCrowdsourcer`) stale, so a later legitimate action misdirects funds to the wrong, no-longer-current outcome.

The same partial-reset pattern exists in `pallet-ismp`'s state-commitment veto path, and the developers have even documented and tested it themselves — but the impact assessment in their own comments understates what the test actually proves.### Title
Vetoing a chain's latest state commitment leaves a stale queue twin that prematurely deletes the honestly resubmitted commitment for that same height, causing message verification/delivery failure - (File: `modules/pallets/ismp/src/host.rs`)

### Summary
`delete_state_commitment` in `pallet-ismp` resets `LatestStateMachineHeight` back to the previous height when the vetoed height was the chain's latest, but — exactly like Augur's `disavowCrowdsourcers` failing to reset `preemptiveDisputeCrowdsourcer` — it does not clean up the corresponding entry in the per-chain FIFO `StateCommitmentQueue`. This stale queue entry later interacts with a subsequent legitimate, correct state update to delete the *live*, currently-latest state commitment for that height, one eviction cycle earlier than the configured retention cap intends.

### Finding Description
`veto_state_commitment` in `modules/pallets/fishermen/src/lib.rs` is a permissionless, single-extrinsic action any active collator can call: it fetches a `StateCommitment` and calls `ismp_host.delete_state_commitment(height)`. [1](#0-0) 

`delete_state_commitment` removes the `BoundedStateCommitments`/`BoundedStateMachineUpdateTime` entries for the vetoed height and, if that height was the chain's `LatestStateMachineHeight`, resets the latest pointer back to `PreviousStateMachineHeight` "to allow for honest updates" — but it deliberately leaves the height's old index in `StateCommitmentQueue` behind, as the inline comment states. [2](#0-1) 

When consensus subsequently re-verifies that same height honestly (the normal `update_client` path, reachable from any relayed consensus proof), `insert_bounded_state_commitment` appends a *second* queue entry for the same height, because the first (stale) entry was never removed: [3](#0-2) 

The pallet's own test proves the consequence: after `veto` + honest resubmission of height 11, the next legitimate insertion (height 12) evicts the *stale* queue index, but that eviction calls `BoundedStateCommitments::remove(id, 11)` — deleting the live, current `StateCommitment` for height 11, even though `LatestStateMachineHeight` for that chain is still 11 and `state_machine_commitment(11)` is expected to be provable: [4](#0-3) 

The pallet's own comments characterize this as merely a "negligible" loss of one retention slot, but the test's actual assertion (`state_machine_commitment(id, 11).is_err()`) shows this is not simply a retention accounting nit: it deletes a state commitment that the chain considers its authoritative `latest` verified state, one insertion cycle before the configured per-chain retention cap (`StateMachineCommitmentCap`) says it should be evicted. [5](#0-4) 

### Impact Explanation
Once the height-11 commitment is deleted while `LatestStateMachineHeight` still points at it, any relayed request/response/GET-response proof anchored at that height (via `pallet-ismp`'s `handle_unsigned` / membership-proof verification against `BoundedStateCommitments`) can no longer be verified, even though it is within the operator-configured retention window and the chain considers it the current provable height. This can deny delivery of legitimate, already-in-flight cross-chain messages (a "route unable to deliver messages") for the affected state machine until the next consensus update lands — a real liveness/DoS impact on message delivery reachable from a single relayed consensus update following a single veto extrinsic, not merely a cosmetic accounting quirk as the inline developer comments suggest.

### Likelihood Explanation
Triggering requires only: (1) a state commitment for a chain's *latest* height being vetoed (an intended, permissionless single-collator action against any commitment, most commonly the currently disputed/fraudulent latest height), and (2) the height being honestly resubmitted afterward, and (3) one further consensus update arriving — all normal, expected operational sequences that the codebase's own regression test deliberately exercises and documents as reproducible, not a contrived edge case.

### Recommendation
When `delete_state_commitment` resets `LatestStateMachineHeight` to `PreviousStateMachineHeight`, also remove or invalidate the corresponding stale entry in `StateCommitmentQueue` for that height (or track a height→queue-index map, as the code comment suggests) so a later honest resubmission cannot collide with a leftover stale queue slot and delete the live commitment prematurely. At minimum, `insert_bounded_state_commitment`'s eviction path should verify the height being evicted is actually the oldest live entry to avoid deleting the just-reinserted commitment for the same height.

### Proof of Concept
The existing test `vetoed_latest_height_that_is_resubmitted_evicts_one_insertion_early` is itself a complete, deterministic PoC: [6](#0-5) 
1. Set cap to 2 for a state machine; store heights 10 and 11 (latest = 11).
2. Call `delete_state_commitment` on height 11 (simulating `veto_state_commitment`) → latest resets to 10, but the queue entry for 11 remains.
3. Re-store height 11 honestly → queue now has two entries pointing at height 11 (indices 1 and 2).
4. Store height 12 → eviction removes the stale index 1, which deletes `BoundedStateCommitments` for height 11 — confirmed by `state_machine_commitment(11).is_err()` — even though 11 is still expected to be a currently provable height under the configured cap of 2.

	fn delete_state_commitment(&self, height: StateMachineHeight) -> Result<(), Error> {
		// The height's entry in the state commitment queue is deliberately left
		// behind; locating it would mean scanning the queue, which is the per-insert
		// cost the queue exists to avoid. Usually its eviction is a no-op, but when
		// the vetoed height is the latest the reset below re-opens it for honest
		// resubmission, and the resubmitted height gets a *second* queue entry. The
		// stale entry then evicts the live commitment when it reaches the head —
		// one insertion before the live entry would have, since the resubmission
		// lands directly behind its stale twin. So a veto costs that height one
		// insertion of retention and permanently burns one queue slot. Both are
		// negligible against the configured caps; making it exact would need a
		// height -> index map on the insert path.
		BoundedStateCommitments::<T>::remove(height.id, height.height);
		BoundedStateMachineUpdateTime::<T>::remove(height.id, height.height);

		// technically any state commitment can be vetoed,
		// safety check that it's the latest before resetting it.
		if let Some(latest) = LatestStateMachineHeight::<T>::get(height.id) {
			if latest == height.height {
				// Reset back to the initial height to allow for honest updates

					PreviousStateMachineHeight::<T>::get(height.id).ok_or_else(|| {
						Error::Custom("Previous state machine height should exist".to_string())
					})?;
				LatestStateMachineHeight::<T>::insert(height.id, prev_height);
			}
		}

#[test]
fn vetoed_latest_height_that_is_resubmitted_evicts_one_insertion_early() {
	let mut ext = new_test_ext();
	ext.execute_with(|| {
		let host = Ismp::default();
		let id = queue_test_state_machine();
		let store = |height: u64| {
			host.store_state_machine_commitment(
				StateMachineHeight { id, height },
				queue_test_commitment(),
			)
			.unwrap();
			host.store_latest_commitment_height(StateMachineHeight { id, height }).unwrap();
		};

		pallet_ismp::Pallet::<Test>::update_commitment_caps(
			RuntimeOrigin::root(),
			BTreeMap::from([(id, 2)]),
		)
		.unwrap();

		store(10);
		store(11);

		// Vetoing the latest height rolls the latest pointer back to 10, so the
		// consensus handler would accept 11 again: it is not below the latest and
		// its commitment is now absent.
		host.delete_state_commitment(StateMachineHeight { id, height: 11 }).unwrap();
		assert_eq!(host.latest_commitment_height(id).unwrap(), 10);

		store(11);
		assert!(host.state_machine_commitment(StateMachineHeight { id, height: 11 }).is_ok());
		// Two queue entries now point at height 11: the stale one and the live one.
		assert_eq!(StateCommitmentQueue::<Test>::get(id, 1), Some(11));
		assert_eq!(StateCommitmentQueue::<Test>::get(id, 2), Some(11));

		// Evicting the stale entry at index 1 deletes the live commitment for 11,
		// one insertion before the entry at index 2 would have.
		store(12);
		assert!(host.state_machine_commitment(StateMachineHeight { id, height: 11 }).is_err());
		assert!(host.state_machine_commitment(StateMachineHeight { id, height: 12 }).is_ok());
		// The queue still counts index 2 as live, so the burnt slot leaves this
		// chain retaining one fewer commitment than its cap of 2.
		assert_eq!(
			CommitmentQueueStates::<Test>::get(id),
			CommitmentQueueState { head: 2, tail: 4 }
		);
		assert_eq!(StateCommitmentQueue::<Test>::get(id, 2), Some(11));
	})
}
