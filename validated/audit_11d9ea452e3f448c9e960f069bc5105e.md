## Finding

### Title
Unauthenticated pipeline run resume endpoint allows anyone with a run's UUID to hijack/complete another user's job run - ([File: core/web/pipeline_runs_controller.go])

### Summary
The `PATCH /v2/jobs/:ID/runs/:runID` endpoint, handled by `PipelineRunsController.Resume`, resumes a suspended pipeline task run and supplies its final result using only the `runID` (task UUID) taken from the URL path — with no check that the caller is the party who is supposed to complete that particular run. This mirrors the report's bug class: a resource is uniquely identified by a "key" that is not itself a secret bound to the legitimate actor, so anyone who obtains or guesses that key can take over/manipulate someone else's in-flight resource.

### Finding Description
`Resume` parses `taskID` from the `runID` path param, decodes an arbitrary JSON body into a `pipeline.ResumeRequest`, and calls `prc.App.ResumeJobV2(ctx, taskID, result)` directly — it performs no authorization check against the caller at all: [1](#0-0) 

This is in stark contrast to the sibling `Create` handler on the same controller, which explicitly checks `auth.GetAuthenticatedUser` / `auth.GetAuthenticatedExternalInitiator` before allowing a run to be triggered: [2](#0-1) 

The audit event fired at the end of `Resume` is literally named `UnauthedRunResumed`: [3](#0-2) 

confirming this route is intentionally exposed without the normal session/API-token/external-initiator authentication, so that async bridge adapters can call back into the node to resume a suspended task. The only "credential" protecting a given run from being resumed/finalized by an arbitrary party is the unguessability of the `runID` UUID itself — exactly analogous to the Sherlock report, where the only thing protecting a borrowing position from takeover is knowledge of a computable key (`address`, `saleToken`, `holdToken`). If a `runID` is disclosed (e.g., through logs, a compromised adapter, a shared network, or trial of low-entropy/duplicated UUIDs), any unprivileged actor can:
- Submit a fabricated `result`/`error` to force a pipeline run to complete with attacker-chosen data (`pipeline.ResumeRequest`/`rr.ToResult()`), effectively taking over control of someone else's in-flight job run without any authentication.

### Impact Explanation
An unprivileged, unauthenticated client that knows or obtains a run's UUID can forcibly resume/finalize a pipeline run belonging to another job/user with attacker-controlled data, corrupting downstream on-chain reporting (e.g., ETHTx, VRF, OCR-triggered task pipelines depend on `ResumeRun` results feeding subsequent tasks). This is a request-impersonation / missing-authorization vulnerability directly reachable from the internet-facing HTTP API by an unprivileged party who merely possesses the identifier — matching the "any position can be taken over immediately" bug class from the report (ownership tied only to a guessable/leakable identifier, not a real, hard-to-forge secret bound to the resource creator).

### Likelihood Explanation
Likelihood depends on whether `runID` values can be observed or guessed by an attacker (e.g., leaked in logs, exposed to bridge adapters that are less trusted than the node operator, or via other endpoints that expose run IDs like `Index`/`Show`). Since UUIDs are otherwise high entropy, likelihood is lower than the original Solidity report (where the key is deterministic and easily computable from a known address), but the underlying architectural weakness — a mutating/state-changing endpoint gated by "knowledge of an ID" rather than real authentication of the party who should be allowed to resume that specific run — is the same root cause.

### Recommendation
Bind resume authorization to the actual entity permitted to callback for that run (e.g., a per-run, single-use resume token/secret generated at suspend time and required in addition to the `runID`, or authenticate the caller as the specific bridge/adapter tied to that task), instead of relying solely on the difficulty of guessing a UUID.

### Proof of Concept
1. Suspend a pipeline run via an async task (e.g., a bridge task) so it is left `PENDING`, generating a `taskID` (UUID).
2. Obtain that `taskID` through any leak vector (logs, network observation, guessing).
3. As an arbitrary unauthenticated client, send `PATCH /v2/jobs/<jobID>/runs/<taskID>` with a crafted JSON body matching `pipeline.ResumeRequest`.
4. The server calls `ResumeJobV2` and finalizes the run with attacker-supplied data, without ever validating that the caller is the legitimate resumer — confirmed by the absence of any `auth.GetAuthenticated...` check in `Resume` (contrast with `Create`) and by the `UnauthedRunResumed` audit tag.

```go
// Resume finishes a task and resumes the pipeline run.
// Example:
// "PATCH <application>/jobs/:ID/runs/:runID"
func (prc *PipelineRunsController) Resume(c *gin.Context) {
	taskID, err := uuid.Parse(c.Param("runID"))
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	rr := pipeline.ResumeRequest{}
	decoder := json.NewDecoder(c.Request.Body)
	err = errors.Wrap(decoder.Decode(&rr), "failed to unmarshal JSON body")
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}
	result, err := rr.ToResult()
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	if err := prc.App.ResumeJobV2(c.Request.Context(), taskID, result); err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	prc.App.GetAuditLogger().Audit(audit.UnauthedRunResumed, map[string]any{"runID": c.Param("runID")})
	c.Status(http.StatusOK)
}
```
