This confirms the finding: `docs/usage/webhooks.md` line 125 explicitly documents `Registry.process` as "verify the request did indeed come from Shopify" — the gem's own documentation frames the HMAC check as authenticating the entire webhook (including its shop attribution), and line 14 of the same doc documents `data.shop` as the trusted shop domain to be used directly (e.g., `perform_later(topic: data.topic, shop_domain: data.shop, ...)`). This is not the host app misusing an undocumented API — the gem itself computes `shop` from an HMAC-unprotected header and hands it to the handler as if it were verified.

### Title
Webhook shop-domain spoofing via HMAC that only covers the request body - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, so `Utils::HmacValidator.validate` proves nothing about the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers. `Registry.process` nonetheless takes `request.shop` straight from that unauthenticated header and hands it to the app's handler as trusted tenant identity, letting any party who can obtain one valid `(body, hmac)` pair replay it with a forged shop domain.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
only the raw body. Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers that are never fed into the signable string: [2](#0-1) 

`HmacValidator.validate` computes the HMAC over `to_signable_string` (the body only) and compares it against the `hmac` field: [3](#0-2) 

`Registry.process` treats a passing HMAC check as proof the *entire request*, including `request.shop`, came from Shopify for the claimed shop, and forwards it unmodified to the app's handler: [4](#0-3) [5](#0-4) 

This is exactly the identity-binding break described in the report's bug class: a field that is *acted on* (the `shop` used to attribute the webhook payload to a tenant) is not covered by the cryptographic check (the HMAC only binds the body bytes). The equality that should hold is:
`shop authenticated by HMAC == shop the handler attributes the payload to`
but the gem only guarantees `body authenticated by HMAC == body the handler receives`; `shop` (and `topic`/`webhook_id`/`api_version`) float free.

Since the app's `client_secret` (used as the HMAC key) is shared across every shop installed on a multi-tenant app, any merchant who has legitimately installed the app can obtain a valid `(raw_body, hmac)` pair from a webhook Shopify sends them (e.g. by subscribing to a topic with a body they control, such as `app/uninstalled` or any webhook whose body content doesn't matter to them). They can then send that exact `(raw_body, hmac)` pair directly to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. `HmacValidator.validate` will still succeed (it never looks at the shop header), and `Registry.process` will hand the handler a `WebhookMetadata` claiming the (attacker-chosen) body came from the victim shop.

### Impact Explanation
The gem's documentation instructs apps to treat `data.shop` as an authenticated tenant identifier once `Registry.process` succeeds, and to use it directly for tenant-scoped actions: [6](#0-5) 
Because that value is not actually bound by the HMAC, an attacker can make the host application believe arbitrary attacker-controlled webhook content originated from a shop they do not control — a cross-tenant data-injection primitive delivered through the gem's own verification API, satisfying the "cross-tenant access" impact criterion.

### Likelihood Explanation
Any of the app's own unprivileged merchants (an "unprivileged internet user" from the perspective of any other tenant) can obtain a valid `(body, hmac)` pair simply by having the app installed and receiving one real webhook, then replay it with a modified shop header directly against the app's public webhook endpoint — no access token, `client_secret`, or privileged account is required.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `webhook_id`, `api_version`) header values in the signable string used for HMAC validation, or otherwise cryptographically bind them to the body before `Registry.process` trusts `request.shop`, so a valid HMAC for one shop's webhook cannot be replayed under a different shop's identity.

### Proof of Concept
1. App is installed by attacker's own store `attacker.myshopify.com` and by victim `victim.myshopify.com`; both share the same `client_secret` used as the HMAC key (`Context.api_secret_key`).
2. Attacker configures a webhook subscription on their own store for a topic whose body content is fully attacker-influenced or otherwise fixed/predictable, and captures the resulting `raw_body` and `X-Shopify-Hmac-Sha256` value that Shopify sends to the app's endpoint.
3. Attacker sends a direct HTTP POST to the app's public webhook endpoint with that exact `raw_body` and `X-Shopify-Hmac-Sha256`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (the unchanged body) and matches — validation passes.
5. `Registry.process` builds `WebhookMetadata.new(shop: request.shop, ...)` with `shop == "victim.myshopify.com"`, and the app's handler processes the attacker-crafted body as if it were an authentic webhook from the victim shop.
