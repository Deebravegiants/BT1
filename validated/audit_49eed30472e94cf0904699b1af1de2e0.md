### Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by verifying an HMAC over the raw request body, but the `shop` (tenant) identifier that the handler is told to act on is read from an unauthenticated HTTP header. Any user who can obtain one genuine `(body, hmac)` pair from Shopify (e.g., by installing the app on their own store) can replay that exact pair to the app's webhook endpoint while swapping the `X-Shopify-Shop-Domain`/`shopify-shop-domain` header to a victim shop, and the library will report the payload as authentic and belonging to the victim tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over `to_signable_string` and compares it to the `hmac` extracted from the payload: [2](#0-1) 

`request.shop` and `request.topic`, however, are parsed straight from HTTP headers and are never included in the signed string: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` (and `request.topic`) to build the `WebhookMetadata` that is handed to the app's handler as the tenant/topic context: [4](#0-3) [5](#0-4) 

The equality the library implicitly claims to enforce is:
`shop_that_HMAC_authenticates == shop_the_handler_acts_on`

But the actual bound identity is only:
`HMAC(secret, raw_body) == received_hmac`

`shop` (and `topic`) are outside this binding. Since Shopify's HMAC scheme signs only the body and never binds it to the sender's shop domain, any actor who can obtain a legitimately-signed body (trivially, by having Shopify send a real webhook to their own store's endpoint) holds a `(body, hmac)` pair that remains valid for any `shop` header value they choose to attach on replay. `Registry.process` performs no comparison between `request.shop` and any known/installed session or store, so it will happily dispatch the replayed payload to the handler tagged with an attacker-chosen shop, i.e., a different tenant's identity.

### Impact Explanation
This crosses a tenant boundary that the gem is trusted to preserve: the app author receives `WebhookMetadata#shop` as an authenticated tenant identifier (it is the only shop-scoping information the gem hands the app for a webhook), but that field carries no HMAC protection. An app that uses this value to select tenant data, refresh tokens, or perform administrative actions per-shop (which is the intended use, since it's the field exposed to handlers precisely for that purpose) can be tricked into operating on/injecting data for a shop other than the one that actually sent the payload — a cross-tenant access condition.

### Likelihood Explanation
Exploitation requires no privileged credentials: any user can install the target app on a store they control (or otherwise obtain any single genuine webhook delivery, since Shopify signs bodies with a fixed per-app secret independent of the shop), capture one valid `(raw_body, hmac)` pair, and POST it to the app's public webhook endpoint with a forged `shop`/`topic` header. `Registry.process` performs no additional binding check, so the replay is accepted as authentic for the spoofed shop.

### Recommendation
Include `shop` (and ideally `topic`) in the HMAC-signable string, or otherwise cryptographically bind the shop-domain header to the body before trusting it (e.g., look up an active installation/session for the claimed shop and reject webhooks whose `shop` cannot be independently corroborated), consistent with the general principle that any field acted upon must be covered by the same authentication check used to accept the request.

### Proof of Concept
1. Attacker installs the vulnerable app on `attacker-shop.myshopify.com`, triggering Shopify to deliver a real webhook (e.g. `orders/create`) to the app's registered webhook URL with a valid `X-Shopify-Hmac-Sha256` header computed over the JSON body using the app's `client_secret`.
2. Attacker captures the exact `raw_body` and `hmac` value from that request (they legitimately received it as their own store's traffic, or via any endpoint under their control).
3. Attacker replays the identical `raw_body` and `hmac` to the app's webhook endpoint again, but this time sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` recomputes the HMAC over `raw_body` only, matches the replayed `hmac`, and returns `true`.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) builds `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` and invokes the app's handler, which now processes attacker-controlled order/webhook data under the victim shop's tenant context.
