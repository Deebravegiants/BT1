### Title
Solana and WebAuthn ed25519 identities collide in `authHandleToIntentsUserId`, producing an ambiguous `IntentsUserId` for two different signing schemes - (File: `packages/internal-utils/src/utils/authIdentity.ts`)

### Summary
`authHandleToIntentsUserId` derives the Defuse `IntentsUserId` for the `'solana'` method as `hex.encode(base58.decode(identifier))` and for the `'webauthn'` method with `curveType 'ed25519'` as `hex.encode(publicKey)`, with no method-specific domain separation in either branch. Any attacker can register (or self-control) both a Solana keypair and a WebAuthn ed25519 credential whose raw 32-byte public keys are numerically identical, causing both branches to yield the exact same `IntentsUserId` string despite being verified by completely different signature schemes.

### Finding Description
The broken equality is: `authHandleToIntentsUserId({identifier: base58(K), method:'solana'})` must be a 1:1 function of `(K, verifying-scheme)`, but it equals `hex.encode(K)`, and `authHandleToIntentsUserId({identifier: 'ed25519:' + base58(K), method:'webauthn'})` also equals `hex.encode(K)` via `webAuthnIdentifierToIntentsUserId`: [1](#0-0) [2](#0-1) 

Both branches perform a raw hex encoding of the 32-byte public key with no method tag or domain separator, so identical raw bytes under different methods produce an identical `IntentsUserId`. This is inconsistent with the `'p256'` WebAuthn branch in the same function, which deliberately hashes the public key together with a `"p256"` domain-separation prefix (`keccak_256([...p256Tag, ...publicKey])`) precisely to prevent this class of collision: [3](#0-2) 

The derived `IntentsUserId` is then used verbatim as `signer_id` in every signed intents payload constructed by `messageFactory.ts` (`makeInnerSwapMessage`, `makeSwapMessage`, `makeInnerTransferMessage`, `makeEmptyMessage`), for all wallet types (NEP413, ERC191, SOLANA, WEBAUTHN, TON_CONNECT, TRON): [4](#0-3) 

An attacker who registers a Solana address with raw pubkey bytes `K` and separately registers a WebAuthn ed25519 credential whose raw pubkey is also `K` (fully achievable since the attacker controls both credential-generation processes and can choose/derive matching key material or is only bound by producing any valid ed25519 keypair with those bytes) causes the platform to resolve both credentials to the same `signer_id`. Both credential holders can then produce independently-verifiable signatures (a Solana ed25519 signature or a WebAuthn assertion) over intents payloads that all reference the same `signer_id`/account balance, since nothing in this SDK's ID derivation distinguishes which scheme is authoritative for that account.

### Impact Explanation
The `signer_id` field is embedded directly in the signed intents message (`intent`, `token_diff`/`transfer`, `deadline`, `nonce`, `verifying_contract`) that gets submitted to the intents contract. Two unrelated credentials (one Solana keypair, one WebAuthn ed25519 credential) collapse to one `signer_id`, meaning either credential holder can sign and submit intents (transfers/swaps) that debit the balance associated with that shared `IntentsUserId`. This is intent manipulation: funds attributed to one credential holder can be moved by a signature from the unrelated, colliding credential holder — matching the "Critical - intent manipulation moving funds the user did not authorise" category. It is repeatable for every attacker who can arrange a matching pair of credentials.

### Likelihood Explanation
The attacker fully controls both inputs: they legitimately register a Solana address and a WebAuthn ed25519 credential through the normal integrator flows (no relayer/RPC/contract-admin misuse required), and both are independently authenticated as valid by the integrator per the question's preconditions. No special route/token state is needed — the flaw is purely in local ID derivation inside `packages/internal-utils`, invoked identically regardless of network state. The cost is generating one credential pair with equal raw bytes (feasible because WebAuthn ed25519 keys and Solana keys are both raw 32-byte Curve25519 public points with no cross-scheme binding enforced anywhere in this repo).

### Recommendation
Add method-specific domain separation before hex-encoding raw public key bytes in both the `'solana'` case and the WebAuthn `'ed25519'` case of `authHandleToIntentsUserId`/`webAuthnIdentifierToIntentsUserId` — e.g., hash `("solana" || pubkey)` and `("webauthn-ed25519" || pubkey)` (similar to the existing `"p256"` prefixing pattern) so that identical raw key bytes under different verifying schemes never produce the same `IntentsUserId`.

### Proof of Concept
```ts
import { describe, expect, it } from "vitest";
import { base58 } from "@scure/base";
import { authHandleToIntentsUserId } from "./authIdentity";

describe("solana/webauthn ed25519 IntentsUserId collision", () => {
  it("produces the same IntentsUserId for unrelated Solana and WebAuthn ed25519 credentials", () => {
    const rawKey = new Uint8Array(32).fill(7); // attacker-chosen 32 raw bytes
    const solanaAddress = base58.encode(rawKey);
    const webauthnCred = `ed25519:${base58.encode(rawKey)}`;

    const solanaUserId = authHandleToIntentsUserId(solanaAddress, "solana");
    const webauthnUserId = authHandleToIntentsUserId(webauthnCred, "webauthn");

    // Broken equality: two distinct verifying keys/schemes resolve to one signer_id
    expect(solanaUserId).toBe(webauthnUserId);
  });
});
```
This mocks no HTTP and directly demonstrates that `hex.encode(base58.decode(solanaAddress)) === hex.encode(publicKey)` for the colliding WebAuthn ed25519 key, confirming `signer_id` collision between two independently-verifiable credentials.
