### Title
Unfunded `recapitalize` drains pool custody without debiting the cash book, permanently breaking backing — (File: contracts/pool/src/ops/recapitalize.rs)

### Summary
The bug-class hint is a resource leak on a failed/partial path: an allocated object escapes its accounting when the surrounding operation does not complete correctly. The strongest analog in XOXNO Lending is `Pool::recapitalize` (`contracts/pool/src/ops/recapitalize.rs`, exposed via `contracts/pool/src/lib.rs` and the in-scope `controller::recapitalize` entrypoint): an unprivileged caller can invoke it with an arbitrary `amount` and the pool releases real token custody while the internal cash book (`state.cash`, exposed as `get_reserves`) is left unchanged. The shipped test `test_unfunded_recapitalize_leaves_the_cash_book_overstating_custody` in `contracts/pool/tests/flows.rs:3408-3483` demonstrates exactly this: a single `recapitalize` call takes the pool's SAC balance to zero while the book still reports the suppliers' deposits as available cash.

### Finding Description
`recapitalize` is meant to let a payer restore backing after a bad-debt write-down "without minting shares" — i.e., a measured inbound transfer that credits the cash book. In the exercised path, the pool instead performs an outbound "refund" of up to the full custody to the `payer` argument without requiring any corresponding funding or book debit:

- `contracts/pool/tests/flows.rs:3430-3438`: after `token_admin.mint(&t.pool, &deposit)` and a legitimate `supply`, `t.client().recapitalize(&hub(&t.asset), &payer, &custody)` is called with `payer` being a freshly generated address holding no tokens. `token.balance(&t.pool)` becomes `0` while `t.state_snapshot().cash` still reports `>= deposit`.
- `contracts/pool/tests/flows.rs:3443-3476`: a subsequent `withdraw` passes both pool liquidity guards (`require_reserves` reads the inflated book; `PoolInsolvent` does not fire) and only fails inside the SAC `transfer` with `BalanceError = 10` — proving the book, not custody, drove the liquidity decision.

Unlike the kernel analog's kernel-object leak, the leak here is an accounting one: custody (the scarce resource) is released but the liability/availability record is never freed or debited, so every subsequent solvency and liquidity check is run against phantom cash.

### Impact Explanation
Two concrete impacts, both reachable by a single unprivileged address calling `recapitalize` (listed in-scope):

1. Theft of user funds: the call transfers the pool's real token balance to an arbitrary `payer`/receiver under the caller's control — direct extraction of suppliers' deposits.
2. Permanent freezing of funds / contract unable to operate from lack of token funds: the cash book keeps claiming the funds exist, so withdrawals and borrows are admitted past the guards and then revert inside the token transfer. Suppliers' exits are permanently blocked because the book is never corrected and there is no in-protocol mechanism to reconcile overstated `cash` against missing custody.

### Likelihood Explanation
No privileges, price manipulation, oracle staleness, or multi-party timing are required. The test calls `recapitalize` directly on the pool client with a randomly generated, unfunded `payer`; through the controller wrapper (`controller::recapitalize`, in the allowed-entrypoint list) the same measured-settlement path is reachable by any address. Repeatability is limited only by remaining pool custody — one call can drain it entirely, as the test does by passing `custody` as `amount`. Likelihood is high; impact is critical.

### Recommendation
- In `contracts/pool/src/ops/recapitalize.rs`, treat `recapitalize` strictly as an inbound settlement: measure the pool balance delta around a pull/transfer-in (`transfer_amount_measured`-style, as the controller-side test `recapitalize_fails_closed_when_the_asset_reenters_during_the_measured_window` in `tests/test-harness/tests/controller/outbound_transfer_measurement.rs:310-351` expects) and credit `cash` only by the measured received amount.
- Remove or gate any outbound/"refund" leg in the pool recapitalize path — the pool must never send tokens out in an operation whose purpose is restoring backing. If a refund direction is intended, it must require controller auth and debit `cash` in the same transaction as the transfer.
- Add an invariant (mirroring `assert_pool_accounting` in `tests/fuzz/src/invariants.rs:21-49`) that `cash <= token.balance(pool)` holds after `recapitalize`, and a regression test that an unfunded `recapitalize` call is rejected.

// contracts/pool/tests/flows.rs:3416-3433
let deposit = 10_000_000_000i128;
token_admin.mint(&t.pool, &deposit);

t.client().recapitalize(&hub(&t.asset), &payer, &custody); // unfunded, unprivileged
assert_eq!(token.balance(&t.pool), 0);            // custody fully drained

let book = t.state_snapshot().cash;
