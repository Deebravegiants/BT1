### Title
Omni Bridge withdrawal status is matched by array index without verifying recipient/amount, allowing misattributed destination tx hashes in batch withdrawals - (File: `packages/intents-sdk/src/bridges/omni-bridge/omni-bridge.ts`)

### Summary
`OmniBridge.describeWithdrawal()` trusts the Omni Bridge indexer's array ordering to correlate a destination-chain transaction with a specific withdrawal, instead of verifying that the returned transfer's recipient/amount/token actually match the caller-supplied `withdrawalParams`. This breaks the equality "the destination hash reported for withdrawal `i` corresponds to the recipient/amount that withdrawal `i` actually requested."

### Finding Description
In `packages/intents-sdk/src/bridges/omni-bridge/omni-bridge.ts`: [1](#0-0) 

```ts
async describeWithdrawal(
    args: WithdrawalIdentifier & { logger?: ILogger },
): Promise<WithdrawalStatus> {
    const transfer = (
        await this.omniBridgeAPI.getTransfer({
            transactionHash: args.tx.hash,
        })
    )[args.index];

    if (transfer == null || transfer.recipient == null) {
        return { status: "pending" };
    }
    ...
    return { status: "completed", txHash };
}
```

The function retrieves the list of transfers associated with a NEAR transaction hash and simply indexes into it with `[args.index]`. `args.index` is a purely positional value assigned when the batch of withdrawal intents was built client-side (see `WithdrawalIdentifier.index` set in `createWithdrawalIdentifier`). Nowhere in `describeWithdrawal` is `transfer.recipient` compared against `args.withdrawalParams.destinationAddress`, nor is any transferred amount/token compared against `args.withdrawalParams.amount` / `assetId`, before the resulting `txHash` is reported as "completed" for that withdrawal.

This is in explicit contrast to the sibling `PoaBridge.describeWithdrawal()` implementation, which the codebase authors deliberately built to avoid index-based matching: [2](#0-1) 

```ts
async describeWithdrawal(
    args: WithdrawalIdentifier & { logger?: ILogger },
): Promise<WithdrawalStatus> {
    const response = await this.getWithdrawalStatusWithRetry(args);

    // Response list is unsorted, so we match by assetId instead of index
    const withdrawal = findMatchingWithdrawal(
        response.withdrawals,
        args.withdrawalParams.assetId,
    );
    ...
```

The PoA bridge's own code comment ("Response list is unsorted, so we match by assetId instead of index") documents that trusting array-index correlation with an external indexer is unsafe. The Omni Bridge implementation does not apply the same safeguard: it neither matches by asset/recipient nor asserts the transfer's recipient equals the requested destination address.

`describeWithdrawal` results feed directly into `sdk.waitForWithdrawalCompletion()` / `sdk.processWithdrawal()`, which report the returned `txHash` to the integrator as the on-chain completion evidence for a specific withdrawal: [3](#0-2) 

### Impact Explanation
For batch withdrawals through the Omni Bridge route (multiple `withdrawalParams` submitted in one NEAR intent, a documented supported feature — see README "Batch Withdrawals"), if the Omni Bridge indexer ever returns transfers in an order that does not exactly match the SDK's intent submission order (e.g., due to indexer-side reordering, retries, or partial indexing), `describeWithdrawal` will report the wrong destination `txHash`/status for a given withdrawal slot without any check. An integrator relying on `waitForWithdrawalCompletion`/`processWithdrawal` output to mark a specific withdrawal (specific recipient/amount) as completed could credit or reconcile the wrong destination transaction against the wrong withdrawal request — i.e., "a status or hash misreport making an integrator credit or refund twice," which matches the High severity bucket in scope.

### Likelihood Explanation
The likelihood depends entirely on whether the external Omni Bridge indexer API guarantees stable, submission-order array output for a given NEAR transaction hash. That guarantee is an external/API trust assumption which is explicitly out of scope to assume adversarial per the rules ("trust assumptions about external RPCs, the relayer, bridge APIs"). However, the root cause identified is a code-level equality gap: the SDK itself performs zero defensive verification (recipient/amount) before trusting index correlation, unlike its sibling PoA implementation which explicitly guards against exactly this class of mismatch. This is a genuine missing equality check in-scope code, independent of whether the external API is currently well-behaved.

### Recommendation
In `OmniBridge.describeWithdrawal()`, after fetching the transfer list, verify that the transfer at the returned index (or a transfer matched by other criteria) has a `recipient` that decodes to the same chain and address as `args.withdrawalParams.destinationAddress`, and that the transferred `amount`/token matches the expected withdrawal amount/asset, mirroring the pattern already used in `PoaBridge.describeWithdrawal()`. If no transfer matches those fields, return `{ status: "pending" }` rather than trusting positional indexing.

### Proof of Concept
1. Submit a batch withdrawal with two Omni Bridge withdrawals in one NEAR intent transaction: withdrawal A → recipient X, amount 100; withdrawal B → recipient Y, amount 200.
2. Assume (or simulate via a mocked `omniBridgeAPI.getTransfer`) that the indexer returns the transfers for that NEAR tx hash in reverse order, i.e. `[transferForY, transferForX]`.
3. Call `sdk.waitForWithdrawalCompletion({ withdrawalParams: [A, B], intentTx })`.
4. `describeWithdrawal` for index 0 (withdrawal A, expected recipient X) returns the finalized `txHash` belonging to the transfer to recipient Y, because it only does `transfers[0]` without checking `transfer.recipient === destinationAddress`.
5. The integrator now believes withdrawal A (to X) completed with a tx hash that actually paid Y — misreport of the on-chain outcome for withdrawal A.

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const transfer = (
			await this.omniBridgeAPI.getTransfer({
				transactionHash: args.tx.hash,
			})
		)[args.index];

		if (transfer == null || transfer.recipient == null) {
			return { status: "pending" };
		}

		const destinationChain = getChain(transfer.recipient as OmniAddress);
		let txHash = null;
		if (
			isEvmChain(destinationChain) ||
			destinationChain === ChainKind.Sol ||
			destinationChain === ChainKind.Fogo ||
			destinationChain === ChainKind.Strk ||
			destinationChain === ChainKind.Aptos
		) {
			txHash = transfer.finalised?.transaction_hash;
		} else if (isUtxoChain(destinationChain)) {
			// pending_sign_id is not the finalised tx hash. In rare cases, the hash may
			// change if the BTC transfer fails to be submitted. We return fast hash for FE and
			// wait for final one (transfer.finalised?.transaction_hash) for BE.
			txHash =
				typeof window !== "undefined"
					? transfer.utxo_meta?.pending_sign_id
					: transfer.finalised?.transaction_hash;
		} else {
			return { status: "completed", txHash: null };
		}

		if (!txHash) {
			return { status: "pending" };
		}

		return { status: "completed", txHash };
	}
