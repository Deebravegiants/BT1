### Title
Yield-ID reuse allows a delayed `promise_yield_resume_with_yield_id` transaction to resolve a stale, unrelated promise ("auction restart" analog) - ([File: runtime/near-vm-runner/src/logic/logic.rs])

### Summary
`promise_yield_create_with_id` / `promise_yield_resume_with_yield_id` implement a request/response pattern keyed by a caller-chosen 32-byte `yield_id` rather than the runtime-generated `data_id`. The `yield_id → data_id` mapping is looked up **at execution time from current trie state**, with no way for the caller to pin the specific pending-promise instance it originally observed. This mirrors the Venus `placeBid()` bug class: an entity that reacts to an ID-keyed piece of state, and later submits a transaction referencing only that ID, can have the ID "restarted" (resumed and recreated) underneath it, so the transaction ends up interacting with a completely different logical instance than the one that was inspected.

### Finding Description
`create_promise_yield_receipt_with_id` (`runtime/runtime/src/ext.rs:371-400`) checks for a duplicate `yield_id` and, once absent, allocates a fresh `data_id` and writes `YieldIdToDataId`/`DataIdToYieldId` bidirectional mappings via `set_yield_id_mapping` [1](#0-0) [2](#0-1) .

When a `PromiseResume` for that `data_id` is applied, the runtime removes the yield receipt, removes the `PromiseYieldStatus`, and explicitly **deletes the `yield_id ↔ data_id` mapping**, freeing the `yield_id` for reuse: [3](#0-2) 

This "freed after resume" behavior is intentional and test-covered: after a yield created with a given `yield_id` is resumed, a subsequent `promise_yield_create_with_id` call with the *same* `yield_id` succeeds and creates a brand-new, unrelated promise: [4](#0-3) 

The resume path, `promise_yield_resume_with_yield_id`, only carries the `yield_id` and payload — it has no field pinning the specific `data_id`/instance the caller intended to resolve: [5](#0-4) 

Internally this resolves via `get_data_id_for_yield_id`, which reads whatever `data_id` is currently mapped to that `yield_id` in the trie at the moment of execution — not the mapping that existed when the caller decided to submit the resume: [6](#0-5) 

Exactly like `placeBid(comptroller, bidBps)` referencing an `Auction` only by `comptroller` (with no `auctionStartBlock` pinning), a resume call referencing only `yield_id` has no way to assert "the pending promise I'm resolving is still the one I observed." If the owning contract account resumes/times-out the original yield and creates a new `promise_yield_create_with_id` reusing the same `yield_id` before a previously-submitted resume transaction lands (e.g. because it sat in the mempool, was delayed by congestion, or a relayer race), the delayed resume's payload is delivered to the *new*, semantically different promise instead of failing or targeting the original one.

### Impact Explanation
A delayed/racing resume transaction can inject a payload intended for one pending yielded computation into a completely different one that happens to reuse the same `yield_id`. Because `promise_yield_create_with_id`/`resume_with_yield_id` are designed for exactly the kind of external-callback/oracle-style workflows where an off-chain relayer observes a pending request and later submits its answer, this allows unintended state transitions in the receiving contract (e.g. a price/oracle answer meant for request N being fed into a differently-parameterized request N', a wrong branch of contract logic executing, or funds/inventory being unlocked based on stale/mismatched data) — an unauthorized state change caused entirely by the protocol's ID-reuse + execution-time-only resolution, with no built-in defense (unlike, e.g., the explicit `expected_hash` guard added in `ReceiptPreparationPipeline` for the analogous account-recreation race, see `runtime/runtime/src/pipelining.rs:94-99`, which shows the codebase is otherwise aware of and defends against this class of race).

### Likelihood Explanation
This requires: (1) a contract intentionally using `promise_yield_create_with_id`/`promise_yield_resume_with_yield_id` with externally-driven resumers (the documented use case), and (2) a resume transaction being delayed (mempool queuing, congestion, chunk scheduling) long enough for the same account to resume the original yield and recreate a new one with the same `yield_id`. This is plausible under normal network congestion or with an account programmed to reuse fixed/sequential `yield_id`s, and does not require any privileged or malicious-node capability — only ordinary unprivileged transaction submission and timing, matching the original report's likelihood profile (Medium).

### Recommendation
Have `promise_yield_resume_with_yield_id` (and/or the host function contract) allow pinning to the specific `data_id`/generation the resumer observed — e.g., return and let callers optionally supply an expected `data_id` (or a monotonically increasing generation counter per `yield_id`) that `submit_promise_resume_data_with_yield_id` must match against the currently stored mapping before delivering the payload, rejecting (returning `0`) on mismatch instead of silently resolving whichever promise currently occupies that `yield_id`.

### Proof of Concept
1. Contract account `C` calls `promise_yield_create_with_id(yield_id = X, method = "handle_price", …)`, creating pending yield `Y1` (`data_id = D1`), mapped `X → D1`.
2. A relayer observes `Y1`/`X` and prepares a transaction calling `promise_yield_resume_with_yield_id(yield_id = X, payload = P1)` intended to fulfill `Y1`. This transaction is delayed in the mempool.
3. Before it lands, `C`'s own logic (or a subsequent user call) resumes or times out `Y1` — the runtime removes `Y1` and the `X → D1` mapping (`runtime/runtime/src/lib.rs:1511-1537`).
4. `C` then calls `promise_yield_create_with_id(yield_id = X, method = "handle_shipment", …)` again, since `X` is now free (as demonstrated by `create_with_id_reuses_yield_id_after_resume`), creating a new, semantically unrelated yield `Y2` (`data_id = D2`), mapped `X → D2`.
5. The relayer's delayed transaction from step 2 finally executes. `submit_promise_resume_data_with_yield_id` resolves `X → D2` (current mapping) and delivers `P1` into `Y2`'s callback (`handle_shipment`) instead of failing or reaching `Y1`, causing the contract to execute unintended logic with a mismatched payload.

    fn create_promise_yield_receipt_with_id(
        &mut self,
        receiver_id: AccountId,
        user_yield_id: YieldId,
    ) -> Result<Option<(ReceiptIndex, CryptoHash)>, VMLogicError> {
        // Check for duplicate yield_id in trie. TrieUpdate also reflects writes from earlier
        // calls within the same function call, so this also catches in-transaction duplicates.
        if has_yield_id_mapping(self.trie_update, &receiver_id, user_yield_id)
            .map_err(wrap_storage_error)?
        {
            return Ok(None);
        }

        let input_data_id = self.generate_data_id();

        // Store bidirectional yield_id <-> data_id mappings
        set_yield_id_mapping(&mut self.trie_update, &receiver_id, user_yield_id, input_data_id);

        let receipt_index =
            self.receipt_manager.create_promise_yield_receipt(input_data_id, receiver_id.clone());

        set_promise_yield_status(
            &mut self.trie_update,
            &receiver_id,
            input_data_id,
            PromiseYieldStatus::Yielded,
        );

        Ok(Some((receipt_index, input_data_id)))
    }

pub fn set_yield_id_mapping(

fn create_with_id_reuses_yield_id_after_resume() {
    let node = setup_test_contract(near_test_contracts::rs_contract());
    let alice_id: AccountId = "alice.near".parse().unwrap();
    let contract_id: AccountId = "test_contract.alice.near".parse().unwrap();

    let yield_payload = vec![6u8; 16];
    let yield_id = [11u8; 32];

    // TX1: create the yield, storing the yield_id <-> data_id mappings.
    let create_args = serde_json::to_vec(&serde_json::json!([yield_create_with_id_op(
        &yield_id,
        &yield_payload,
        0
    )]))
    .unwrap();
    let res = node
        .user()
        .function_call(
            alice_id.clone(),
            contract_id.clone(),
            "call_promise",
            create_args.clone(),
            MAX_GAS,
            Balance::ZERO,
        )
        .unwrap();
    assert_eq!(res.status, FinalExecutionStatus::SuccessValue(vec![]), "{res:?} unexpected result");

    // TX2: resume it. Applying the PromiseResume receipt removes the mappings.
    let resume_args = serde_json::to_vec(&serde_json::json!([yield_resume_with_yield_id_op(
        &yield_id,
        &yield_payload,
        1
    )]))
    .unwrap();
    let res = node
        .user()
        .function_call(
            alice_id.clone(),
            contract_id.clone(),
            "call_promise",
            resume_args,
            MAX_GAS,
            Balance::ZERO,
        )
        .unwrap();
    assert_eq!(res.status, FinalExecutionStatus::SuccessValue(vec![]), "{res:?} unexpected result");

    // TX3: the yield_id is free again, so the create returns promise index 0
    // instead of the u64::MAX sentinel.
    let res = node

        .unwrap();
    assert_eq!(res.status, FinalExecutionStatus::SuccessValue(vec![]), "{res:?} unexpected result");
}

    /// Like [`promise_yield_resume`], but accepts the user-provided `yield_id` (from
    /// [`promise_yield_create_with_id`]) instead of the runtime-generated `data_id`. The runtime looks
    /// up the corresponding `data_id` internally.
    ///
    /// Returns `1` if the yield was found and resume was submitted, `0` otherwise.
    pub fn promise_yield_resume_with_yield_id(
        &mut self,
        yield_id_len: u64,
        yield_id_ptr: u64,
        payload_len: u64,
        payload_ptr: u64,
    ) -> Result<u32, VMLogicError> {
        self.result_state.gas_counter.pay_base(base)?;
        if self.context.is_view() {
            return Err(HostError::ProhibitedInView {
                method_name: "promise_yield_resume_with_yield_id".to_string(),
            }
            .into());
        }
        self.result_state.gas_counter.pay_base(yield_resume_base)?;
        self.result_state.gas_counter.pay_per(yield_resume_byte, payload_len)?;
        let yield_id = get_memory_or_register!(self, yield_id_ptr, yield_id_len)?;
        let payload = get_memory_or_register!(self, payload_ptr, payload_len)?;
        let payload_len = payload.len() as u64;
        if payload_len > self.config.limit_config.max_yield_payload_size {
            return Err(HostError::YieldPayloadLength {
                length: payload_len,
                limit: self.config.limit_config.max_yield_payload_size,
            }
            .into());
        }

        let yield_id: [_; YieldId::LENGTH] =
            (&*yield_id).try_into().map_err(|_| HostError::YieldIdMalformed)?;
        let yield_id = YieldId::from_bytes(yield_id);
        let payload = payload.into_owned();
        self.ext.submit_promise_resume_data_with_yield_id(yield_id, payload).map(u32::from)
    }
