## Title
Duplicate `NewRaise` entry via `poke` + `contribute` causes double `place_bid` execution per block - (File: polkadot/runtime/common/src/crowdloan/mod.rs)

## Summary
`Crowdloan::poke` (call_index 7) appends a `para_id` to `NewRaise` guarded only by a `contains()` check on `NewRaise` itself, but never updates `fund.last_contribution`. Since `do_contribute`'s own duplicate-suppression logic relies exclusively on `fund.last_contribution` (not on inspecting `NewRaise`), a subsequent `contribute`/`contribute_all` call on the same fund within the same block will not detect that the entry was already added by `poke`, and will append the same `para_id` a second time, causing `on_initialize` to invoke `T::Auctioneer::place_bid` twice for the same fund/para in a single block.

## Finding Description
`poke` only checks `NewRaise::<T>::get().contains(&index)` before appending, and does not touch `fund.last_contribution`: [1](#0-0) 

`do_contribute`, in contrast, decides whether to append to `NewRaise` purely based on the `fund.last_contribution` field's relationship to `now`/`EndingsCount`, with no reference to `NewRaise` contents: [2](#0-1) 

Because `poke` never sets `last_contribution`, if `poke` is called first in a block, `fund.last_contribution` still holds its pre-poke value. A following `contribute` call in the same block falls into the `_ =>` branch (whether in the ending period or not) and calls `NewRaise::<T>::append(index)` again, producing a duplicate `para_id` entry in the `NewRaise` vector.

`on_initialize` takes the whole `NewRaise` vector without deduplication and iterates it via `filter_map`, invoking `place_bid` once per entry — so a duplicated entry results in `place_bid` being called twice for the identical fund/para/amount within one block: [3](#0-2) 

This confirms the claim's root cause: two independent, unsynchronized duplicate-checks (`NewRaise::contains` in `poke` vs. `last_contribution` state machine in `do_contribute`) that do not share a single source of truth, allowing a caller to defeat both checks by interleaving the two extrinsics in one block.

## Impact Explanation
The duplicate invocation of `place_bid` and duplicated `HandleBidResult` event emission increases the weight/PoV consumed by `on_initialize`, which runs as a `Mandatory` hook and is not throttled by ordinary block weight limits. Since `NewRaise` is drained every block during the ending period (re-opening the `poke` duplicate check each block), an attacker can repeat the `poke` + `contribute` sequence every block across the auction ending period, for multiple funds, compounding wasted weight in the auction-ending hot path. This is a real (if narrow) invariant violation — funds should place at most one bid per block — with a legitimate, if modest, weight/DoS-adjacent impact on `on_initialize` processing during auction endings.

## Likelihood Explanation
Both `poke` and `contribute`/`contribute_all` are permissionless, signed-origin extrinsics reachable by any account. The only precondition is an active auction in its ending period and a fund with `raised > 0`, which any user can trivially satisfy via a prior contribution (even their own). The exploit sequence is fully attacker-controlled, requires no privileged access, and is repeatable every block throughout the ending period.

## Recommendation
Unify the duplicate-detection logic so both `poke` and `do_contribute` rely on the same signal. For example, have `poke` also set `fund.last_contribution` to the equivalent `LastContribution::Ending(now)` / `LastContribution::PreEnding(endings_count)` value it would set had `do_contribute` performed the append, so a following `contribute` call correctly perceives the fund as already queued. Alternatively, change `do_contribute` to check `NewRaise::<T>::get().contains(&index)` directly rather than relying solely on `last_contribution` bookkeeping.

## Proof of Concept
1. Set up an active auction and advance it into its ending period using the mock `TestAuctioneer`.
2. `create` a fund and have some account `contribute` to it pre-ending so `fund.raised > 0`; advance to a fresh block within the ending period.
3. In that block, call `Crowdloan::poke(signed(attacker), index)` followed by `Crowdloan::contribute(signed(attacker), index, MinContribution)`.
4. Inspect `NewRaise::<Test>::get()` and observe it contains `index` twice instead of once.
5. Advance to the next block to trigger `on_initialize`, and observe the mock `Auctioneer`'s bid-tracking vector records two identical `place_bid` calls for the same fund/para at that height, instead of one.
