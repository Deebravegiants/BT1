### Title
Orb-Relay client leaks last relayed signup state to unverified message source - (File: `orb-relay-client/src/client.rs`)

### Summary
In `PollerAgent::main_loop`, incoming relay messages are supposed to be checked against `self.config.dst_id` before being trusted, exactly like the reference bug where an operation was performed against the wrong actor because the caller's identity was implicitly trusted without verifying it matched the intended counterparty. However, the `RequestState` message type is special-cased and handled *before* that source check runs, so it is processed regardless of who sent it.

### Finding Description
The `main_loop` response-handling arm is:
```rust
if self_serve::app::v1::RequestState::matches(&payload).is_some() {
    sender_tx.send(self.last_message.clone()).await...
} else if src.id != self.config.dst_id {
    tracing::error!("Skipping received message from unexpected source: ...");
} else {
    self.handle_message(...).await?;
}
``` [1](#0-0) 

The `src.id != self.config.dst_id` check exists specifically to ensure only the paired counterparty (the app for an orb-mode client, or the orb for an app-mode client) can interact with this session. For every other message type this check is enforced first, but the `RequestState::matches` branch short-circuits and replies with `self.last_message` — the most recently sent `RelayConnectRequest` (e.g. `AnnounceOrbId`, `SignupEnded`, `CaptureStarted`, etc.) — without ever inspecting `src.id`. This is structurally the same root cause as the reported bug: an operation that is supposed to be scoped to a specific, verified counterparty instead executes based on an implicit assumption about the caller's identity that the code never actually checks for this particular code path, exactly as `_unwrap` implicitly assumed `msg.sender` held the tokens instead of validating/using the correct principal.

`self.last_message` is populated in the outgoing-message arm:
```rust
self.pending_messages.insert(self.seq, (relay_message.clone().into(), maybe_ack_tx));
self.last_message = relay_message.clone().into();
``` [2](#0-1) 
and can contain signup/session-relevant payloads such as `AnnounceOrbId` or `SignupEnded` sent during `orb_relay_announce_orb_id` and `do_signup` flows. [3](#0-2) 

### Impact Explanation
Because the `RequestState` branch never verifies `src.id`, any relay entity able to route a `RequestState`-shaped payload into this session's stream (i.e., outside of the intended app/orb pairing enforced client-side) can trigger disclosure of the last state message associated with that signup session. This constitutes unauthorized disclosure of signup/session-scoped state to an unverified sender, directly matching the "cross-signup state bleed" and "unauthorized ... disclosure" categories called out for this analysis. The severity depends on what the relay backend independently enforces about session membership; if the backend does not otherwise guarantee that only the two paired entities can inject messages tagged with a given `src`, this client-side gap becomes directly exploitable.

### Likelihood Explanation
This code path is reached passively by any inbound relay message during the ordinary self-serve signup flow, `orb_relay_announce_orb_id`/`proceed_with_biometric_capture` — no privileged access or special conditions are required beyond being able to place a matching payload on the session's relay stream. The bypass is unconditional (a plain type check, not a corner case), so it triggers deterministically whenever a `RequestState` payload arrives, regardless of its `src`. [4](#0-3) 

### Recommendation
Move the `src.id != self.config.dst_id` check ahead of the `RequestState` match so all inbound payload types — including `RequestState` — are validated against the expected counterparty before any response or state disclosure occurs:
```rust
if src.id != self.config.dst_id {
    tracing::error!("Skipping received message from unexpected source: {:?}", src.id);
} else if self_serve::app::v1::RequestState::matches(&payload).is_some() {
    sender_tx.send(self.last_message.clone()).await...
} else {
    self.handle_message(...).await?;
}
```

### Proof of Concept
1. Establish a session as the intended `dst_id` counterpart is not required; any entity able to inject a `RelayPayload` into the response stream with `payload` matching `self_serve::app::v1::RequestState` and an arbitrary/unexpected `src` triggers the branch at [5](#0-4)  before the `src.id != self.config.dst_id` guard at line 441 is ever evaluated.
2. The client immediately replies over `sender_tx` with `self.last_message`, disclosing the last transmitted signup-session payload (e.g., `AnnounceOrbId`/`SignupEnded`) to the unverified sender.
