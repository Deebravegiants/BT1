### Title
Auto-lock timeout bypass via `restartAutoLockTimer()` — unbounded passphrase cache lifetime — ([File: features/application/src/modules/passphrase-cache.ts])

### Summary
`PassphraseCache.get()` implements two mutually-exclusive expiry checks for the cached wallet passphrase — an absolute `addedAt + maxTtl` bound, and an activity-based `inactiveAt + ttl` bound — but once `inactiveAt` is set (via `restartAutoLockTimer()`), the absolute `maxTtl` cap is never consulted again, exactly mirroring the DelayBuffer report's inconsistent-decrease pattern where the order/frequency of state-updating calls silently defeats the intended security bound.

### Finding Description
`PassphraseCache.set()` records `addedAt = Date.now()` and a `ttl` when the passphrase is cached [1](#0-0) . `PassphraseCache.get()` decides whether the cached passphrase is still valid:

```
if (inactiveAt) {
  if (inactiveAt + ttl > Date.now()) return passphrase
} else if (addedAt + this.#maxTtl > Date.now()) {
  return passphrase
}
``` [2](#0-1) 

`inactiveAt` is set by `scheduleClear()`, which is invoked from the public `restartAutoLockTimer()` API method exposed on `exodus.application.restartAutoLockTimer()` [3](#0-2) [4](#0-3) [5](#0-4) .

`config.maxTtl` (default 60 minutes) is meant to be the absolute ceiling for how long a passphrase can remain cached, as documented ("Changes the auto lock timer TTL...the wallet will be considered locked after the timer expires") [6](#0-5) . However, once any single call to `restartAutoLockTimer()` occurs, `get()` permanently switches to the `inactiveAt`-branch and the `addedAt + maxTtl` absolute cap is never evaluated again for the lifetime of that cached passphrase. Repeated calls to `restartAutoLockTimer()` (each resetting `inactiveAt` to `Date.now()`) before the per-call `ttl` window elapses will keep resetting the "activity" window indefinitely, so the passphrase — and therefore the ability to auto-unlock the wallet (`#autoUnlock` re-derives keys from the cached passphrase) — never actually expires [7](#0-6) . This is structurally identical to the Arbitrum bug: a security-relevant timer/threshold is supposed to be bounded, but the bound is only checked along one code path, and repeatedly exercising the other path (analogous to "including the newest message first") silently neutralizes the guarantee.

### Impact Explanation
`maxTtl` is the last line of defense limiting how long the wallet's decryption secret sits in (session) storage/cache after unlock, per the design comment in `application.ts`'s API docs ("the wallet will be considered locked after the timer expires"). Any code path (background scripts, other plugins, or a compromised/malicious dApp integration surface that has access to `exodus.application.restartAutoLockTimer()`) that calls this method periodically defeats the absolute cap entirely, keeping the passphrase cached and the wallet auto-unlockable far beyond the configured `maxTtl`. Since `#autoUnlock` derives the primary seed and adds it to the live keychain whenever the cached passphrase is fetched, this extends the window during which the mnemonic/seed material is reachable from cache, increasing exposure to secret disclosure if the device/session storage is otherwise compromised (e.g. malware, forensic extraction, or another extension with storage access) during what should have been a locked/expired session.

### Likelihood Explanation
`restartAutoLockTimer` is exposed as a standard part of the deprecated wallet API and the `application` API surface, callable by any caller with access to the SDK's RPC methods (UI process, or any code able to invoke exposed RPC methods over the port) [8](#0-7) . No user interaction bypassing normal activity-detection is required — a script only needs to call this one method on an interval shorter than the configured `ttl` to keep `inactiveAt` refreshed forever, which is a low-effort, reliably reproducible condition (comparable in effort to the "sequential ordering of forceInclusion calls" in the original report).

### Recommendation
Always enforce the absolute cap regardless of activity state: compute effective expiry as `Math.min(inactiveAt ? inactiveAt + ttl : Infinity, addedAt + maxTtl)`, and clear/reject the cached passphrase once `Date.now()` exceeds this combined bound, i.e., check `addedAt + maxTtl` unconditionally in addition to the activity-based check rather than in an `else` branch.

### Proof of Concept
Conceptual reproduction using existing test patterns (`features/application/src/modules/passphrase-cache.ts` semantics):
1. `application.unlock({ passphrase })` → `passphraseCache.set(passphrase)` stores `addedAt = T0`, `ttl = T` (e.g. 5 min), with `config.maxTtl = 60 min`.
2. Every `T - ε` minutes, an attacker-reachable caller invokes `exodus.application.restartAutoLockTimer()` → `scheduleClear()` sets `inactiveAt = now`.
3. `passphraseCache.get()` is now permanently evaluated via `inactiveAt + ttl > Date.now()`; `addedAt + maxTtl` is never checked again.
4. Repeating step 2 indefinitely (e.g., for 24+ hours, far exceeding the 60-minute `maxTtl`) keeps `get()` returning the cached passphrase, and `#autoUnlock()` continues to successfully unlock the wallet — demonstrating the `maxTtl` absolute-session bound is bypassed.
