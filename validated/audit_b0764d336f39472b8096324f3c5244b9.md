## Title
Webhook HMAC only covers the request body, not the `shop`/`topic`/`webhook-id` headers, allowing cross-tenant webhook forgery via replay - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC of the raw request body, while the shop identity, topic, API version and webhook id are all taken from unauthenticated HTTP headers that are never included in the signed material. An attacker who controls a legitimate (attacker-owned) shop installation of the app can capture a validly-signed webhook and replay it with a forged `X-Shopify-Shop-Domain` header pointing at a victim shop, and the library will accept it as authentic.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body: [1](#0-0) 

`shop`, `topic`, `api_version` and `webhook_id` are all read straight from HTTP headers and are not part of the signed string: [2](#0-1) 

`HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` (i.e. only the body) and compares it to the `hmac` header: [3](#0-2) 

`Registry.process` relies exclusively on this HMAC check before dispatching the (header-derived, unauthenticated) `shop` value to the app's handler: [4](#0-3) 

The broken identity binding is:
`hmac_signed_bytes == { shop, topic, webhook_id, api_version }` is expected, but in reality `hmac_signed_bytes == raw_body only`, while `handler-trusted shop == header value` — a field (`shop`, and the other headers) that is acted upon by the handler is not covered by the HMAC that is supposed to authenticate the whole request.

Since the app's `client_secret`/webhook signing key is shared across all shops that install the app (it is not shop-specific), any unprivileged internet user who installs the app on their own free development/trial shop can obtain a genuinely-signed webhook (valid HMAC) whose body they can influence to a good degree (e.g. by creating orders/products/customers with attacker-chosen field values in their own shop, which get delivered in the webhook body). They can then replay that exact `raw_body` + `hmac` pair to the app's webhook endpoint while swapping the `X-Shopify-Shop-Domain` (and, if desired, `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) headers to any victim shop's domain. `HmacValidator.validate` still succeeds because it never inspects those headers, and `Registry.process` forwards `shop: request.shop` (the forged victim shop) together with the attacker's body to the registered handler via `WebhookMetadata`.

### Impact Explanation
This is a cross-tenant identity-confusion primitive: it lets an attacker inject webhook events that the host application will process as if they originated from a specific victim merchant, while the actual event data is attacker-controlled. Any app logic that uses `WebhookMetadata#shop` to select the tenant record to update/create (a common and expected usage pattern, since that's precisely why the library exposes `shop` on the metadata object) can be tricked into writing attacker-supplied data into a victim merchant's records, or into acting on the victim's behalf with attacker-chosen parameters — a cross-tenant access/data-integrity violation crossing the trust boundary the HMAC is meant to enforce.

### Likelihood Explanation
Exploitation only requires the ability to install the target app on any shop (dev/trial store) — no privileged credentials, access tokens, or `client_secret` are needed — plus the ability to send an HTTP POST to the app's public webhook endpoint with modified headers, which is exactly the capability this gem hands to the host application without warning that headers are unauthenticated. The `Request` class's own header-parsing code demonstrates how easily a caller passes raw, attacker-suppliable header dictionaries straight through.

### Recommendation
Include the security-relevant identity fields (`shop domain`, `topic`, `webhook_id`, `api_version`) in the HMAC-signed material, or otherwise cryptographically bind them to the body's signature, so that a valid HMAC can only be produced for the exact `(body, shop, topic, webhook_id)` tuple that Shopify actually sent. At minimum, document prominently that `WebhookMetadata#shop`/`topic`/`webhook_id` are not authenticated by `HmacValidator.validate` and must not be trusted for tenant selection without additional verification (e.g., cross-checking against a known/expected shop for the delivery).

### Proof of Concept
1. Attacker installs the target Shopify app on their own shop `attacker.myshopify.com`.
2. Attacker triggers an event (e.g., creates an order) whose webhook body content they control to the extent the resource allows.
3. Shopify delivers a webhook to the app's endpoint with headers `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid hmac of raw_body>`, and the crafted `raw_body`.
4. Attacker captures this request and replays it to the same endpoint, changing only `X-Shopify-Shop-Domain` to `victim.myshopify.com` (and optionally the topic/webhook-id headers), keeping `raw_body` and the `X-Shopify-Hmac-Sha256` value identical.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only hashes `raw_body`: [1](#0-0) 
6. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: attacker_body, ...)` and, if it uses `shop` to select the tenant to act on, processes attacker-controlled data under the victim's identity.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
