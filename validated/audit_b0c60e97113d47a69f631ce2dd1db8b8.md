### Title
`HmacValidator.validate` succeeds while `Webhooks::Request#shop` is unauthenticated, enabling cross-tenant webhook spoofing - (`lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0)  , so the HMAC that `HmacValidator.validate` checks never covers the `x-shopify-shop-domain`/`shopify-shop-domain` header that `Request#shop` reads [2](#0-1) . Because Shopify's webhook HMAC is computed with a single app-level `client_secret` shared across every shop that installs the app (not a per-shop secret), an attacker who installs the app on their own development shop can receive a genuinely-signed webhook and replay its exact `raw_body`/`hmac` pair to the host app's public webhook endpoint with the `shop-domain` header rewritten to a victim shop.

### Finding Description
The intended binding a host app relies on is: `Utils::HmacValidator.validate(request) == true` implies `request.shop` is the shop that actually produced/authorized `request.parsed_body`. Tracing the code shows this does not hold:

- `HmacValidator.validate_signature` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it against `verifiable_query.hmac` [3](#0-2) .
- `Request#to_signable_string` returns `@raw_body` only [1](#0-0) , and `Request#hmac`/`Request#shop` are both read from independent, unsigned headers via `shopify_header` [4](#0-3) .
- `Registry.process` validates HMAC and then trusts `request.shop` directly to build `WebhookMetadata` passed to the host app's handler, with no cross-check that the shop matches the body or any known install [5](#0-4) .
- `Utils::ShopValidator.sanitize!` (which validates a shop is a trusted `*.myshopify.com`-style domain) is never invoked anywhere in this webhook path, so nothing rejects a well-formed but arbitrary shop-domain value either.

Because a single `client_secret` signs webhooks for every shop that installs the app, an attacker can install the app on their own shop (permitted per the threat model), trigger an event (e.g. `orders/create`) with attacker-controlled JSON fields, receive the genuinely Shopify-signed `raw_body` + `hmac` at their own endpoint, then POST that identical body/HMAC pair to the victim-facing webhook URL while substituting `x-shopify-shop-domain: victim-shop.myshopify.com`. `HmacValidator.validate` recomputes HMAC over `raw_body` only, which still matches, and `Registry.process` then dispatches the handler with `shop: "victim-shop.myshopify.com"` even though the payload actually originated from the attacker's own shop.

### Impact Explanation
A successful replay lets an attacker inject an authenticated-looking webhook payload attributable to any target shop domain, without ever compromising `client_secret`, an access token, or the victim's credentials. Depending on how the host app's `WebhookHandler.handle` uses `data.shop` (e.g., writing to per-tenant DB records, triggering emails/notifications, updating cached shop state, or driving business logic keyed by shop), this is a cross-tenant data-integrity/isolation break: attacker-chosen data (drawn from fields they control in their own store, such as order notes, customer name, product titles) gets attributed to and processed as belonging to an arbitrary victim tenant. This is repeatable for any topic the host app has registered and for any victim shop domain string, since nothing in the gem validates that `request.shop` corresponds to the shop that actually produced the signed body.

### Likelihood Explanation
Preconditions are modest and fully within the described unprivileged-attacker capabilities: create a free development store, install the target app on it, and let Shopify deliver a genuinely signed webhook to an endpoint the attacker controls. The attacker then needs only to know (or guess) the host app's public webhook URL and any victim `*.myshopify.com` domain (shop domains are not secret). No live shop, credential theft, or TLS interception is required — this is a pure request-crafting/replay attack against the gem's verification logic.

### Recommendation
Include the shop domain (and ideally topic/webhook-id/api-version) in the signable material, or otherwise bind `request.shop` to Shopify's own authoritative record before trusting it — e.g., have `Registry.process` cross-check `request.shop` against a shop that is known to have `hmac`-eligible active install/session state, and run `ShopValidator.sanitize!` on the header before using it, rather than trusting the raw header value once HMAC (over body only) succeeds.

### Proof of Concept
```ruby
# test/webhooks/cross_tenant_replay_test.rb
require_relative "../test_helper"

class CrossTenantWebhookReplayTest < Minitest::Test
  def setup
    ShopifyAPI::Context.setup(
      api_key: "key", api_secret_key: "shared_app_secret", host_name: "host",
      scope: "scope", is_private: false, api_version: "2024-01",
      is_embedded: true,
    )
  end

  def test_hmac_valid_but_shop_header_is_forged
    raw_body = '{"id":1,"note":"attacker-controlled data"}'
    valid_hmac = Base64.encode64(
      OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), "shared_app_secret", raw_body)
    ).strip

    # Attacker's own shop legitimately received this signed webhook,
    # but rewrites shop-domain before forwarding to victim-facing endpoint.
    forged_headers = {
      "shopify-topic" => "orders/create",
      "shopify-hmac-sha256" => valid_hmac,
      "shopify-shop-domain" => "victim-shop.myshopify.com",
    }

    request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

    assert(ShopifyAPI::Utils::HmacValidator.validate(request)) # binding LHS: true
    assert_equal("victim-shop.myshopify.com", request.shop)    # binding RHS: trusted as victim, but never signed
  end
end
```
This demonstrates `Utils::HmacValidator.validate(request) == true` while `request.shop` (`"victim-shop.myshopify.com"`) was never part of `to_signable_string` and does not correspond to the shop whose action actually produced `raw_body`.
