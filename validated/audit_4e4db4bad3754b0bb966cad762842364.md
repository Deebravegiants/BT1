### Title
Webhook shop-domain header is not covered by the HMAC, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` is documented to "verify the request did indeed come from Shopify" before invoking the app's handler with a `WebhookMetadata` struct whose `shop` field is presented as a trustworthy tenant identifier. However, the HMAC signature computed by `Utils::HmacValidator` only covers the raw request body (`Request#to_signable_string` returns `@raw_body`), never the `shop-domain` header. Because Shopify signs all webhooks for an app installation with the same `client_secret` regardless of which shop triggered the event, any party who legitimately receives a webhook for their own shop can replay the identical body/HMAC pair while substituting the `x-shopify-shop-domain` (or `shopify-shop-domain`) header to name a different, victim shop. The signature still validates, and `Registry.process` forwards the attacker-chosen `shop` value to the app's handler as if it were authenticated.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
only the body is included. `Request#shop` is read straight from an unauthenticated header: [2](#0-1) 
`Registry.process` validates the HMAC and then trusts `request.shop` when constructing the metadata passed to the app-supplied handler: [3](#0-2) 
`WebhookMetadata` carries `shop` as a plain `String` field with no further verification: [4](#0-3) 

The identity binding broken here is: `shop header used by the handler != shop bytes covered by the HMAC`. The equality the gem should be enforcing — "the shop the handler is told about" == "the shop cryptographically bound to the signed payload" — does not hold, because the shop is never part of the signable string. Since all installations of a given app share the same `client_secret`/HMAC key, this is not merely a "different tenant's secret" problem; a single captured legitimate webhook (which any merchant naturally receives at their own endpoint) is fully replayable under an arbitrary victim shop's identity.

### Impact Explanation
This produces cross-tenant access: an app that keys per-shop records, credentials, or business logic off `data.shop` from `WebhookMetadata` (as the gem's own documentation instructs consumers to do, e.g. `perform_later(topic: data.topic, shop_domain: data.shop, ...)`) can be tricked into writing, deleting, or acting on data attributed to a shop that never sent the event. This matches the "Critical - cross-tenant access" impact category, since the binding between the authenticated bytes and the tenant identifier is absent at the point the gem hands control to the host app.

### Likelihood Explanation
Likelihood is high for any app that has more than one installed shop (nearly universal for any Shopify Partner app). No secret key, access token, or privileged access is required — only a genuine webhook delivery to the attacker's own endpoint (obtained simply by installing the app on their own store) and the ability to POST a modified header value to the app's public webhook URL, which is by definition internet-reachable.

### Recommendation
Include the shop domain (and, ideally, topic and webhook id) in the HMAC-signed material, or otherwise cryptographically bind the header-supplied `shop` value before it is surfaced to the handler. At minimum, `Utils::VerifiableQuery`/`HmacValidator` should be extended so that `Webhooks::Request#to_signable_string` incorporates the `shop-domain` header (and other headers used for trust decisions), not just the raw body, so that `Registry.process` cannot be tricked into reporting a shop that differs from the one whose secret and payload were actually used to compute the signature.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and receives a legitimate webhook at their endpoint with body `B`, header `x-shopify-hmac-sha256: H` (computed by Shopify from `B` and the app's shared `client_secret`), and `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker resends the exact same request to the app's webhook endpoint, changing only `x-shopify-shop-domain` to `victim.myshopify.com`, keeping body `B` and header `H` unchanged.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {..., "x-shopify-shop-domain" => "victim.myshopify.com", "x-shopify-hmac-sha256" => H})` is constructed.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `B` only — this matches `H`, so validation passes: [5](#0-4) 
5. The registered handler is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)`, and the host application processes the event as if it genuinely originated from `victim.myshopify.com`.
