### Title
Global `challengePeriod`/`challenge_period` is read live at message-processing time instead of being snapshotted per state commitment, letting a shortened parameter retroactively bypass the fraud-proof observation window for already-pending commitments - (File: evm/src/core/HandlerV2.sol)

### Summary
Hyperbridge's challenge-period mechanism is the direct analog of the reported `_gracePeriod` bug: a single mutable governance parameter is consulted at execution time to decide whether a time-bound security window has "elapsed," instead of being captured as an immutable property of the specific object (here, a `StateCommitment`) whose safety it is meant to protect.

### Finding Description
On the EVM side, `challengePeriod` lives in the single mutable `HostParams` struct [1](#0-0) , updatable at any time via `updateHostParams`/`updateHostParamsInternal` [2](#0-1) . Every message handler re-reads this live value and compares it against a per-height `delay` derived from `stateMachineCommitmentUpdateTime`, which was fixed at the time the commitment was stored: [3](#0-2) [4](#0-3) 

The same pattern exists on the Substrate/pallet-ismp side: `challenge_period` is a mutable per-`StateMachineId` value settable via `store_challenge_period`/`update_consensus_state`, and `verify_delay_passed` reads it live against the fixed `state_machine_update_time` of the commitment being checked: [5](#0-4) .

The protocol's own documentation describes the intended invariant: relayers must wait for "the configured `challenge_period`" and fishermen get that same window to submit a fraud/veto proof before a `StateCommitment` is considered safely canonical: [6](#0-5) . Because the check re-reads the *current* `challengePeriod` rather than the value that was in effect (or promised) when the commitment was stored, any reduction of this global parameter after a `StateCommitment` has already been stored immediately and retroactively shortens the observation window for every commitment already pending challenge — exactly like the reported `_gracePeriod` bug, where a global config change silently changes the executability of already-created objects instead of only affecting future ones.

### Impact Explanation
If `challengePeriod` is lowered (for any operational reason) while a `StateCommitment` produced under a longer promised window is still pending, an unprivileged relayer can immediately call `handlePostRequests`, `handleGetResponses`, `handlePostRequestTimeouts`, or `handleGetRequestTimeouts` (or the equivalent pallet-ismp `handle`/`handle_unsigned` path) using that commitment once the new, shorter delay is satisfied — before fishermen have had the full window they were promised to submit a `freeze_client` fraud proof. This undermines the "unsound state commitment" security guarantee documented for the protocol and can result in forged/unauthorized message delivery (dispatch of `PostRequest`/`GetResponse`/timeouts) based on a state commitment that has not actually survived its intended fraud-proof review period, i.e., an unsound-state-commitment class issue with the potential for unauthorized app action or forged message delivery.

### Likelihood Explanation
Triggering this requires only two ordinary events: (1) a legitimate `updateHostParams`/`update_consensus_state` call lowering `challengePeriod`/`challenge_period` (a normal, expected governance operation, not itself malicious), and (2) an unprivileged relayer submitting a routine `handlePostRequests`/`handleGetResponses`/timeout message for a `StateCommitment` that was stored before the reduction. No forged proofs or special privileges are needed for the second step, making the exploit trivially reachable by any relayer once the parameter is lowered while commitments are in flight.

### Recommendation
Snapshot the challenge period alongside each `StateCommitment` at the moment it is stored (e.g., store `challengePeriod` together with `stateMachineCommitmentUpdateTime` on the EVM side, and alongside `state_machine_update_time`/`IntermediateState` on the Substrate side), and use that snapshotted value — never the live/global one — when checking `ChallengePeriodNotElapsed` in `HandlerV2.sol` and `verify_delay_passed` in `modules/ismp/core/src/handlers.rs`. This mirrors the report's recommendation to persist `_gracePeriod` as a parameter of the action itself rather than reading a mutable global at execution time.

### Proof of Concept
1. Consensus client for state machine `S` finalizes `StateCommitment` at height `H` at time `T0`; `challengePeriod` is currently `P1` (e.g., 24h).
2. Governance calls `updateHostParams` (EVM) or `update_consensus_state` (Substrate) to reduce `challengePeriod` to `P2` (e.g., 1h) for legitimate/operational reasons unrelated to commitment `H`.
3. At `T0 + P2` (still well within the originally-promised `P1` window during which fishermen were expected to be able to submit a fraud proof), any relayer calls `handlePostRequests`/`handleGetResponses`/`handlePostRequestTimeouts` referencing height `H`.
4. `delay = block.timestamp - stateMachineCommitmentUpdateTime(H) = P2`, and `challengePeriod() == P2`, so `challengePeriod > delay` is false and the `ChallengePeriodNotElapsed` check in [7](#0-6)  passes, allowing the message to be dispatched even though only `P2 < P1` time has passed since `H` was finalized — bypassing the security window that was in effect when `H` was created.

    function handlePostRequests(IHost host, PostRequestMessage calldata request) external notFrozen(host) {
        uint256 timestamp = block.timestamp;
        uint256 delay = timestamp - host.stateMachineCommitmentUpdateTime(request.proof.height);
        uint256 challengePeriod = host.challengePeriod();
        if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();

        uint256 requestsLen = request.requests.length;
        MerkleMountainRange.Leaf[] memory leaves = new MerkleMountainRange.Leaf[](requestsLen);

        for (uint256 i = 0; i < requestsLen; ++i) {
            PostRequestLeaf memory leaf = request.requests[i];
            // check destination
            if (!leaf.request.dest.equals(host.host())) revert InvalidMessageDestination();
            // check time-out
            if (timestamp >= leaf.request.timeout()) revert MessageTimedOut();
            leaves[i] = MerkleMountainRange.Leaf(leaf.index, leaf.request.hash());
        }

        bytes32 root = host.stateMachineCommitment(request.proof.height).overlayRoot;
        if (root == bytes32(0)) revert StateCommitmentNotFound();
        bool valid = MerkleMountainRange.VerifyProof(root, request.proof.multiproof, leaves, request.proof.leafCount);
        if (!valid) revert InvalidProof();

        for (uint256 i = 0; i < requestsLen; ++i) {
            PostRequestLeaf memory leaf = request.requests[i];
            // duplicate request?
            if (host.requestReceipts(leaf.request.hash()) != address(0)) revert DuplicateMessage();
            host.dispatchIncoming(leaf.request, _msgSender());
        }
    }

/// for the state machine has elasped.
pub fn verify_delay_passed<H>(host: &H, proof_height: &StateMachineHeight) -> Result<bool, Error>
where
	H: IsmpHost,
{
	let update_time = host.state_machine_update_time(*proof_height)?;
	let delay_period = host
		.challenge_period(proof_height.id)
		.ok_or(Error::ChallengePeriodNotConfigured { state_machine: proof_height.id })?;
	let current_timestamp = host.timestamp();
	Ok(delay_period.as_secs() == 0 || current_timestamp.saturating_sub(update_time) > delay_period)
}

A `StateMachineUpdated` event is emitted to notify network participants (both relayers and fishermen) of some newly available `StateCommitment`s for a given state machine. Relayers will wait for the configured `challenge_period` before attempting to transmit new requests & responses. While fishermen will check if these pending `StateCommitment`s describe valid states on the counterparty network. If the `challenge_period` elapses without any fraud proofs being presented, we can safely conclude that the provided `StateCommitment`s are indeed canonical.
