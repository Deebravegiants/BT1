### Title
Permanent freeze of escrowed order funds if the input/output token reverts transfers to the fixed token address recorded at `placeOrder` time - (File: evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
`IntentGatewayV2`/`IntentsBase` escrows a user's order inputs (and a solver's fill outputs) keyed by the exact token contract address supplied in `Order.inputs[i].token` / `WithdrawalRequest.tokens[i].token`. Every subsequent release path (`RedeemEscrow`, `RefundEscrow`) transfers out using that same fixed address via `IERC20(token).safeTransfer(beneficiary, amount)`. If that specific token address ever stops accepting `transfer`/`transferFrom` calls for the escrow contract (the double-entrypoint-token bug class cited in the report, e.g. a TUSD-style migration that blocks the legacy proxy address, or any token that later pauses/blacklists the escrow contract at that specific address), the escrowed balance recorded under `_orders[commitment][token]` can never be moved out, because there is no mechanism to substitute a different address or bypass the transfer for that token.

### Finding Description
`placeOrder` credits escrow strictly by token address: [1](#0-0) 

The corresponding release path, used by both `RedeemEscrow` (pay the solver) and `RefundEscrow` (refund the user) request kinds, decrements the same address-keyed slot and unconditionally calls `safeTransfer` on that exact token contract: [2](#0-1) 

There is no allowlist of "acceptable" tokens, no fallback/rescue path, and no way to redirect the transfer to a successor contract for the same underlying asset. The accounting (`_orders[commitment][token]`) and the payout mechanism are both permanently bound to the address captured when the order was placed. If, after an order is placed but before it is filled/refunded (which, per the protocol's cross-chain design, can be an arbitrary amount of time — orders can sit in escrow while cross-chain fill/refund proofs are produced), the token contract at that fixed address becomes non-transferable to the gateway/beneficiary (the exact failure mode the external report describes for double-entrypoint tokens), the `safeTransfer` call at line 468 reverts on every future attempt to call `RedeemEscrow`/`RefundEscrow` for that commitment+token, because `_withdraw` performs the escrow-debit and the token transfer atomically in the same call with no way to skip only the failing leg.

Since `IntentGatewayV2.placeOrder` is explicitly designed to accept "ANY" ERC20 token supplied by an arbitrary, unprivileged user (fee-on-transfer tokens are already handled defensively, showing the intent to support broad token compatibility), this places the same trust assumption on arbitrary tokens that the original Footium report flagged.

### Impact Explanation
Any user's escrowed input tokens, or a solver's escrowed output/fill tokens, for a given commitment become permanently unrecoverable if the underlying token contract at the recorded address stops accepting transfers from the gateway. Because `_orders[commitment][token]` is the only accounting record and `_withdraw` is the only release path, this is a full, indefinite loss of the escrowed funds for that token — not a temporary DoS. This is a direct loss-of-funds condition reachable by a single unprivileged `placeOrder` transaction combined with an external token-contract state change outside the protocol's control.

### Likelihood Explanation
Likelihood is low-to-moderate in absolute terms (it requires a token whose access model changes after escrow, mirroring the real-world TUSD/double-entrypoint precedent), but the surface is broad: `IntentGatewayV2` accepts arbitrary ERC20 addresses from any caller with no allowlist, so the condition is entirely dependent on third-party token behavior rather than any privileged or malicious actor within Hyperbridge. Given the intents system is meant to support arbitrary tokens across many chains over the life of open orders, the exposure window (time between `placeOrder` and finalization) is nontrivial.

### Recommendation
- Add a rescue/administrative path (gated by appropriate governance) that allows re-pointing a stuck escrow entry to a successor token address or performing an emergency withdrawal bypass when the primary transfer path is provably broken, similar to how the protocol already special-cases fee-on-transfer tokens.
- Consider decoupling escrow debit from the token transfer so a failed transfer for one token in a multi-token release does not brick the entire commitment's finalize path, and expose a per-token retry/rescue call.
- Document and/or enforce a token allowlist for `IntentGatewayV2` orders, consistent with the recommendation in the original report, to avoid unbounded exposure to arbitrary/mutable ERC20 implementations.

### Proof of Concept
1. User calls `placeOrder` with `inputs[0] = { token: TOKEN, amount: X }`; `IntentGatewayV2.placeOrder` escrows `X` (minus fees) into `_orders[commitment][TOKEN]` (`evm/src/apps/IntentGatewayV2.sol:364-368`).
2. Before the order is filled/refunded, `TOKEN`'s issuer migrates to a new contract and blocks/reverts all `transfer`/`transferFrom` calls at the old `TOKEN` address for the gateway contract (the double-entrypoint scenario), while off-chain proofs/merkle-style commitments referencing the old address remain otherwise valid.
3. A relayer submits a `RedeemEscrow` or `RefundEscrow` request that reaches `IntentsBase._withdraw` with `body.tokens[i].token == TOKEN` (`evm/src/apps/intentsv2/IntentsBase.sol:451-470`).
4. `IERC20(TOKEN).safeTransfer(beneficiary, amount)` at line 468 reverts every time it is called, because the token no longer honors transfers from this contract at that address.
5. `_orders[commitment][TOKEN]` remains permanently non-zero and unreachable — the escrowed funds are stuck with no available code path to release them.

        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
