### Title
Emporium `runAction`/`handleOut` lets any unprivileged prover mint a shielded UTXO backed by tokens stolen from any third party's stale/existing ERC20 approval to the Emporium contract - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
When `EmporiumStack.signerAddress == address(0)`, `verifyWallet` skips all signature verification on `stack.ops` entirely, so the attacker's own proof can encode an arbitrary `EmporiumOperation{endpoint: victimToken, callData: transferFrom(victim, emporium, amount)}` executed as a raw low-level call with `msg.sender == Emporium`. Any account (EOA, `HinkalWallet`, or contract) that has ever granted `Emporium` an ERC20 allowance—whether from a legitimate prior op or a stale/leftover unlimited approval—can be drained by any unrelated attacker in a single `transact` call, and the pulled tokens are converted directly into the attacker's own new on-chain shielded UTXO via `handleOut`.

### Finding Description
The broken equality: **AUTHORITY** - the `from` address of every `transferFrom` executed inside `stack.ops` must be authorized by the account that produced the current proof (`msg.sender` of `transact`). In practice `from` can be any address that has an outstanding allowance to the singleton `Emporium` contract, with zero relation to the current prover.

Code path:
1. `EmporiumUpgradeable.runAction` decodes `stack` from attacker-supplied `circomData.externalActionData.externalActionMetadata` [1](#0-0) .
2. `verifyWallet` marks the message used and, when `stack.signerAddress == address(0)`, returns immediately with **no signature check on `stack.ops`**, leaving `op.endpoint`/`op.callData` completely attacker-controlled [2](#0-1) .
3. In CASE 2 (`op.invokeWallet==false` or `signerAddress==address(0)`), the only guard is a selector blacklist for `callHinkalWallet`/`doSendToRelay`; any other call, including `victimToken.transferFrom(victimApprover, emporium, amount)`, is executed directly as `op.endpoint.call{value: op.value}(op.callData)` with `msg.sender == Emporium` [3](#0-2) . If `victimApprover` (any account, including a `HinkalWallet` that previously ran `approve(emporium, type(uint256).max)` for a legitimate swap/deposit flow, or any external account) has ever approved `Emporium`, the `transferFrom` succeeds and pulls `amount` into `Emporium`.
4. `balanceChange = balancesAfter[i] - balancesBefore[i]` captures this stolen inflow for that token index [4](#0-3) .
5. `handleOut` unconditionally forwards `balanceChange` to `msg.sender` (Hinkal.sol) and mints a `UTXO(amount=balanceChange, ..., circomData.stealthAddressStructure)` addressed to the attacker's own stealth key [5](#0-4) .
6. Because the attacker sets `onChainCreation[i] = true` for that token index, `checkOnchainCreation` only requires `amountChanges[i] == 0` and no input nullifiers [6](#0-5) , and `Hinkal.sol`'s balance equation `balanceDif == (onChainCreation[i] ? 0 : amountChanges[i]) + utxoAmount` is satisfied trivially because `balanceDif` (Hinkal's own balance delta) equals exactly the stolen `utxoAmount` handed back by Emporium [7](#0-6) . The on-chain commitment is created directly from `utxoSet[j]` outside of any circuit constraint (`inTotal + amountChanges === outTotal` never applies to this token, since it's not part of the circuit's in/out set) [8](#0-7) .

None of `performHinkalChecks`, `verifyProof`, `rootHashExists`, or the balance/slippage requires constrain `op.endpoint`/`op.callData` content or the `from` argument of any call the attacker embeds in `stack.ops`—these guards only validate the attacker's own UTXO inputs/outputs and overall balance deltas, not the identity of whichever third party's tokens get pulled into Emporium.

### Impact Explanation
Direct theft of a third party's ERC20 tokens (any account with an outstanding, non-revoked allowance to the shared `Emporium` contract, e.g. a `HinkalWallet` that ran an earlier legitimate operation with `invokeWallet=true`, or any other approver) converted into the attacker's own shielded balance with zero backing from the attacker. This is minting shielded value without real deposit and matches the Critical category (direct theft of user funds / minting shielded value without backing).

### Likelihood Explanation
Preconditions: at least one address must hold a non-zero ERC20 allowance with `Emporium` as spender. This is a natural byproduct of the existing "stateful interaction" design (`invokeWallet=true` calls that approve Emporium once for repeated future pulls), so stale/persistent approvals are expected to exist in normal operation, not a contrived edge case. Attacker cost is a single `transact` call plus gas; the exploit is fully repeatable against every account/token pair with an outstanding allowance, until the approval is revoked.

### Recommendation
Do not allow `stack.ops` with `signerAddress == address(0)` to execute arbitrary `endpoint.call(callData)` unconstrained. Either always require a valid EIP-712 signature binding `stack.ops` to a specific `signerAddress`/prover-controlled account, or restrict CASE 2 calls to a strict allow-list of endpoints/selectors that cannot move funds `from` an address other than `Emporium` itself (e.g. disallow `transferFrom` where `from != Emporium`/`from != stack.signerAddress`). Additionally, consider scoping/limiting `HinkalWallet` approvals to bounded amounts or single-use, and require every `EmporiumOperation` to be signed regardless of `signerAddress`.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `EmporiumUpgradeable`, a `HinkalWallet` for a `victimApprover`, and a mock ERC20.
2. Simulate a prior legitimate op: have `victimApprover`'s `HinkalWallet` (via `callHinkalWallet`) call `token.approve(emporium, type(uint256).max)`, then let that approval persist (no revoke).
3. Fund `victimApprover` (or its wallet) with `X` tokens.
4. As an unrelated `attacker`, craft `circomData` for `transact` with `externalActionData.externalActionId` pointing to Emporium, `erc20TokenAddresses = [token]`, `onChainCreation = [true]`, `amountChanges = [0]`, `inputNullifiers = [[]]`, and `externalActionMetadata` encoding `EmporiumStack{signerAddress: address(0), ops: [EmporiumOperation{endpoint: token, invokeWallet: false, value: 0, callData: abi.encodeCall(token.transferFrom, (victimApprover, emporium, X))}]}`.
5. Generate a valid Groth16 proof for the attacker's own (empty) inputs/outputs matching the circuit's `inTotal + amountChanges === outTotal` for the unrelated in/out set, satisfying `verifyProof`.
6. Call `Hinkal.transact(...)` from `attacker`.
7. Assert: `token.balanceOf(victimApprover) == 0` (drained), and a new on-chain UTXO of amount `X` for `token` is inserted into the tree encrypted to the attacker's `stealthAddressStructure`, i.e. `balanceDif == 0 + X` passes in `Hinkal.sol` and `handleOut` transferred `X` to `msg.sender==Hinkal` while `victimApprover` never signed or authorized this `transact` call.
