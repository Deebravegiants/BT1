### Title
Webhook `shop` and `topic` fields are trusted without HMAC coverage, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats an incoming webhook as fully verified once `Utils::HmacValidator.validate(request)` passes, but the HMAC signature only covers the raw request body — never the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers. Any entity capable of producing one valid `(body, HMAC)` pair — trivially available to any developer/attacker who installs the app on their own store and receives a genuine webhook — can replay that exact body+HMAC pair while substituting an arbitrary `shop-domain` and `topic` header. `Registry.process` will accept it as authentic and dispatch it to the app's handler as if it originated from the victim shop, breaking the identity binding between "HMAC-verified bytes" and "the shop that the app believes sent the event."

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors are read straight from unauthenticated HTTP headers with no cryptographic binding to the signed content: [2](#0-1) 

`Registry.process` validates only the HMAC-over-body and then unconditionally forwards `request.shop` and `request.topic` to the app's handler, documented by this library as data the app can trust: [3](#0-2) 

The gem's own documentation states that `Registry.process` "will verify the request did indeed come from Shopify" before invoking the handler with `data.shop`/`data.topic`, reinforcing the (false) guarantee that these fields are authenticated: [4](#0-3) 

Equality that should hold: `shop header value == shop that produced the HMAC-signed body`. In reality, the HMAC only proves `body == HMAC⁻¹(secret, signature)`; it says nothing about which shop or topic accompanied that body. Because HMAC-SHA256 of an attacker-controlled or replayable body (e.g., the attacker's own store's real webhook, or any body an attacker can get validly signed, including bodies with no shop-specific secret content) is independent of the headers, an attacker who owns/installs the app on their own shop can capture a real `(raw_body, x-shopify-hmac-sha256)` pair from their own genuine webhook delivery and resend it to the app's webhook endpoint with `x-shopify-shop-domain` and `x-shopify-topic` set to any value they choose (e.g., a victim shop's domain and `app/uninstalled` or `shop/redact`).

### Impact Explanation
This crosses the shop-identity boundary that multi-tenant apps rely on to route webhook side effects to the correct tenant's data (e.g., updating billing state, disabling access, deleting data via GDPR redact topics, or triggering `app/uninstalled` cleanup) — a cross-tenant access/confusion vector reachable by an unprivileged internet user who merely needs to install the app once on any shop to obtain a validly-signed payload. This matches the "Critical - cross-tenant access" impact category, since it lets one tenant's traffic (or an attacker's own tenant) forge events attributed to a different tenant.

### Likelihood Explanation
Any developer/attacker can install the target app for free on a throwaway development store, immediately receive a genuine webhook (with a real HMAC over some body), and then replay that exact body/HMAC pair against the app's public webhook endpoint while changing only the `shop-domain`/`topic` headers — no secret key, access token, or privileged account is required. The webhook endpoint is by design internet-reachable and unauthenticated aside from the HMAC check.

### Recommendation
Bind `shop` and `topic` into the signed content that `HmacValidator` verifies (e.g., include them, like Shopify's `AuthQuery#to_signable_string` already does for OAuth), or otherwise require applications to cross-check `request.shop` against a known, previously-registered/installed shop's session before trusting the payload. At minimum, the gem's documentation and `Registry.process` should not claim the full request "did indeed come from Shopify" when only the body bytes are actually authenticated.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`, completing OAuth normally (no special access needed).
2. Shopify sends a legitimate webhook to the app, e.g. `POST /callback/orders/create` with body `{"id":1}` and header `x-shopify-hmac-sha256: <valid HMAC over {"id":1}>` and `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker captures this exact `raw_body` and `x-shopify-hmac-sha256` value.
4. Attacker replays the identical body/HMAC to the same endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com` and/or `x-shopify-topic: app/uninstalled`.
5. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Utils::HmacValidator.validate` succeeds because it only checks `raw_body` against the (still-correct) HMAC: [5](#0-4) 
6. `Registry.process` calls the registered handler with `WebhookMetadata` populated from the forged `shop` and `topic` values, `Registry.rb` lines 198-199, causing the app to act on `victim.myshopify.com`'s behalf based on attacker-controlled input.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
