### Title
Iris-code signature omits `signup_id`, enabling replay of a signature across different signup attempts - (File: `src/plans/enroll_user.rs`)

### Summary
The M-14 report describes a class of bug where a cryptographic commitment (a merkle leaf) omits a domain-separating value (chain ID), so a valid, previously-observed authorization can be replayed in a different context to misattribute or redirect an action. The closest reachable analog in orb-core is `make_signature()` in `src/plans/enroll_user.rs`, which produces the secure-element signature attached to a signup submission. That signature commits to the orb ID, the scanned user ID, and the iris/mask codes, but never commits to the `signup_id` that uniquely identifies the specific signup attempt/session that the signature is meant to authorize.

### Finding Description
`make_signature` hashes only a fixed set of fields before asking the secure element to sign the digest: [1](#0-0) 

Notably absent from the hashed material is `signup_id`, even though the signature is submitted together with `signup_id` to the backend's per-signup endpoint: [2](#0-1) [3](#0-2) 

The request is posted to `/api/v2/signups/{signup_id}`, i.e., `signup_id` is the value that scopes/binds this specific signup transaction on the backend, but it is not part of the signed payload. This is structurally the same root cause as the reported issue: the authorization artifact (merkle leaf / iris-code signature) does not incorporate the identifier that is supposed to scope it to one specific transaction/context (chain ID / `signup_id`), so the signed blob is portable across contexts that share the other fields (same `ORB_ID`, same `user_qr_code.user_id`, same iris/mask codes) but differ in the scoping identifier.

### Impact Explanation
If a `signup_id` (or the corresponding signature+codes payload) is ever observed or reused outside of its original single-attempt context, the missing binding means the backend cannot cryptographically distinguish "this signature was produced for signup session A" from "this signature was replayed for signup session B" for the same user/orb — because nothing in the signed digest encodes which signup transaction it belongs to. This maps to the "cross-signup state bleed" impact category: a signature computed for one signup attempt could be paired with a different `signup_id` value and still validate the same iris data, potentially letting a signup record be created/attributed under a `signup_id` that does not correspond to the actual capture/session that produced it. The retry loop in `Plan::run` already illustrates that the same signature is reused verbatim across `RETRIES_COUNT` POSTs to the same `signup_id`, confirming the signature is not itself scoped to a single request/nonce: [4](#0-3) 

### Likelihood Explanation
Exploitation likelihood is low-to-moderate and requires more than a purely network-observing attacker: requests are sent over TLS with orb-token basic auth [3](#0-2) , so this is not trivially exploitable by an unprivileged outside observer in the way the original cross-chain replay was (permissionless resubmission on a public chain). The realistic risk here is architectural/defense-in-depth: because orb-core is the only place a `signup_id`-bound signature could be created, and it does not bind one, any future or existing backend logic that trusts the signature as attesting to "this specific signup transaction" is relying on an assumption the signature does not actually enforce. This is a genuine root-cause weakness in the signing scheme rather than a demonstrated end-to-end unauthenticated exploit, since full validation logic lives server-side and is out of scope/not visible in this repo.

### Recommendation
Include `signup_id` (and ideally a freshness/nonce value and intended purpose string, analogous to EIP-712 domain separation) inside the data hashed by `make_signature` before it is passed to `secure_element::sign`, e.g.:
```rust
ctx.update(signup_id.as_bytes());
```
so the secure-element signature cryptographically commits to the specific signup transaction it is meant to authorize, preventing any reuse of a valid signature/iris-code payload under a different `signup_id`.

### Proof of Concept
1. Observe that `make_signature` in `src/plans/enroll_user.rs:290-304` hashes `ORB_ID`, `user_qr_code.user_id`, and iris/mask code fields only.
2. Observe that `signup_post::request` in `src/backend/signup_post.rs:98-143` sends this signature together with an independently-chosen `signup_id` in the URL path and multipart form, with no cryptographic link between the two.
3. Because the `signup_id` is not part of the signed digest, the same `(signature, codes)` pair is valid input for any request that reuses those same iris/mask/user fields, regardless of which `signup_id` accompanies it — demonstrating the signature does not scope the authorization to one specific signup transaction, which is the same root cause identified in the referenced report (missing domain-separating identifier in the signed/hashed payload).

Note: full backend-side verification logic is not present in this repository, so it cannot be confirmed here whether the backend independently enforces `signup_id`-to-signature binding through other means; this is a limitation of what is visible from orb-core alone.

fn make_signature(user_qr_code: &qr_scan::user::Data, pipeline: &Pipeline) -> Result<String> {
    let mut ctx = Context::new(&SHA256);
    ctx.update(ORB_ID.as_str().as_bytes());
    ctx.update(user_qr_code.user_id.as_bytes());
    ctx.update(pipeline.v2.ir_net_version.as_bytes());
    ctx.update(pipeline.v2.iris_version.as_bytes());
    ctx.update(pipeline.v2.eye_left.iris_code.as_bytes());
    ctx.update(pipeline.v2.eye_left.mask_code.as_bytes());
    ctx.update(pipeline.v2.eye_left.iris_code_version.as_bytes());
    ctx.update(pipeline.v2.eye_right.iris_code.as_bytes());
    ctx.update(pipeline.v2.eye_right.mask_code.as_bytes());
    ctx.update(pipeline.v2.eye_right.iris_code_version.as_bytes());
    let signed = secure_element::sign(ctx.finish())?;
    Ok(BASE64.encode(&signed))
}
