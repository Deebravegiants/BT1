### Title
XRPL X-address's embedded destination tag is silently overridden/ignored when a separate `destinationMemo` is supplied - ([File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge-utils.ts])

### Summary
`validateXrpAddress()` accepts both classic addresses and X-addresses (`xrp_isValidClassicAddress(address) || xrp_isValidXAddress(address)`), but `createWithdrawMemo()` treats the `destinationAddress` as an opaque string and never decodes an X-address into its classic account + embedded tag. If a caller supplies a valid X-address (which self-encodes a destination tag) together with a separate, different `destinationMemo`, the resulting `WITHDRAW_TO` memo embeds the raw X-address string plus the caller-supplied tag, with no reconciliation of the two tag values.

### Finding Description
The claimed equality is: *(classic account, tag) encoded in the X-address the user believes they are sending to* **==** *(address, tag) that ends up in the `ft_withdraw` intent's `memo` field*.

Trace:
- `PoaBridge.validateWithdrawal()` calls `validateAddress(args.destinationAddress, assetInfo.blockchain)`, which for `Chains.XRPL` calls `validateXrpAddress()`: [1](#0-0) . This accepts X-addresses without ever decoding them.
- `validateWithdrawal()` only additionally checks `requireDestinationTag` (rejecting if `!args.destinationMemo`) and `depositAuthEnabled` — it never checks whether an X-address's embedded tag conflicts with a supplied `destinationMemo`: [2](#0-1) .
- `createWithdrawIntentPrimitive()` passes `destinationAddress` and `destinationMemo` straight into `createWithdrawMemo()`: [3](#0-2) .
- `createWithdrawMemo()` does no XRPL-specific address normalization (only strips a BCH prefix) and unconditionally appends the raw `xrpMemo`/`destinationMemo` as a third colon-separated field, regardless of whether the address itself already encodes a tag: [4](#0-3) .

Root cause: the SDK's XRPL validation accepts a tag-carrying address representation (X-address) but the memo-construction logic assumes `destinationAddress` never carries a tag, and the caller-supplied `destinationMemo` is treated as the sole source of truth for the tag. There is no code path anywhere in this file (or in `poa-bridge.ts`) that decodes an X-address to recover its embedded tag or that cross-checks it against `destinationMemo`.

Result: for input `destinationAddress = <X-address encoding tag=12345>`, `destinationMemo = "99999"`, the produced memo is `"WITHDRAW_TO:<X-address-string>:99999"` — a string that mixes an address representation which already claims tag `12345` with an explicit, different tag `99999`. Whichever value the downstream bridge/relayer ultimately honors, the SDK output is internally self-contradictory and does not represent the (account, tag) pair the user actually intended when constructing the X-address.

Existing guards do not prevent this:
- `validateXrpAddress` only checks address *format* validity, not consistency with `destinationMemo` [1](#0-0) .
- `compareAddresses` is only used to check the destination isn't the token's own origin address, not for tag consistency [5](#0-4) .
- `requireDestinationTag` check only guards against a *missing* tag when the destination account requires one, not a conflicting/duplicated tag [6](#0-5) .

### Impact Explanation
The signed NEAR intent's `memo` field (`WITHDRAW_TO:<address>:<tag>`) is the only channel by which the POA bridge backend learns the destination tag for an XRPL payout. Producing a memo that bundles a raw (undecoded) X-address together with an unrelated tag value creates an ambiguous/inconsistent destination specification generated and signed by this SDK, for a bridge where a wrong/duplicated destination tag routinely causes unrecoverable loss of funds on custodial/exchange deposit accounts. This matches "funds delivered to a wrong address/chain/contract with no recovery" (Critical) if it results in the wrong tag being paid, since XRPL destination tags cannot be corrected post-transaction. It affects any withdrawing user who (knowingly or via an integrator UI) passes both an X-address and a separately entered memo/tag, and is repeatable per withdrawal call — no privilege beyond calling the SDK is required.

### Likelihood Explanation
Preconditions: caller must control both `destinationAddress` and `destinationMemo` parameters when calling the POA bridge withdrawal path for XRPL assets — both are user-supplied strings per the `WithdrawalParams` shape and are not restricted to matching formats. An X-address is a legitimate, common way to represent an XRPL account+tag pair (e.g., produced by some wallets/exchanges), so it is plausible that a user or an integrator's form (which may separately solicit a "memo/tag" field) supplies both, especially if the UI doesn't special-case X-addresses. No RPC/relayer control is required to trigger the SDK-side production of the inconsistent memo. Actual on-chain fund-loss impact still depends on how the downstream (out-of-repo) bridge backend interprets the resulting memo string, which is not verifiable from this repository.

### Recommendation
In `createWithdrawMemo()` (or earlier, in `validateWithdrawal`), detect X-address inputs explicitly: decode them (e.g., via `ripple-address-codec`'s `xAddressToClassicAddress`) into `{classicAddress, tag}`, and:
- If `destinationMemo` is also supplied and its value differs from the decoded tag, reject the withdrawal with a clear validation error instead of silently combining both.
- Otherwise, always normalize the address to the classic account form in the memo, and use the single reconciled tag value (from the X-address or the memo, never both blindly concatenated).

### Proof of Concept
```ts
// packages/intents-sdk/src/bridges/poa-bridge/poa-bridge-utils.spec.ts
import { describe, it, expect } from "vitest";
import { classicAddressToXAddress } from "ripple-address-codec";
import { createWithdrawIntentPrimitive } from "./poa-bridge-utils";

describe("XRPL X-address tag consistency", () => {
  it("silently drops the X-address's embedded tag in favor of destinationMemo", () => {
    const classicAddress = "rEXAMPLE_VALID_CLASSIC_ACCOUNT"; // valid XRPL classic address
    const embeddedTag = 12345;
    const xAddress = classicAddressToXAddress(classicAddress, embeddedTag, false);

    const conflictingMemo = "99999";

    const intent = createWithdrawIntentPrimitive({
      assetId: "nep141:xrp.omft.near",
      destinationAddress: xAddress,
      destinationMemo: conflictingMemo,
      amount: 1000n,
    });

    // BROKEN EQUALITY: memo tag (from destinationMemo) != tag embedded in the X-address
    expect(intent.memo).toBe(`WITHDRAW_TO:${xAddress}:${conflictingMemo}`);
    expect(intent.memo).not.toContain(String(embeddedTag)); // embedded tag 12345 is lost
  });
});
```
This demonstrates that `createWithdrawIntentPrimitive` produces a memo containing both the un-decoded X-address (which itself claims tag `12345`) and the separately supplied, conflicting tag `99999`, with no validation error and no reconciliation between the two.

function createWithdrawMemo({
	receiverAddress,
	xrpMemo,
}: {
	receiverAddress: string;
	xrpMemo: string | undefined;
}) {
	// Strip "bitcoincash:" prefix from BCH CashAddr addresses
	const normalizedAddress = receiverAddress
		.toLowerCase()
		.startsWith("bitcoincash:")
		? receiverAddress.slice("bitcoincash:".length)
		: receiverAddress;

	const memo = ["WITHDRAW_TO", normalizedAddress];

	if (xrpMemo != null && xrpMemo !== "") {
		memo.push(xrpMemo);
	}

	return memo.join(":");
}
