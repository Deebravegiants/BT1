### Title
Unchecked ERC-20 `transfer` return-value bypasses non-standard token failures in Tron IntentGatewayV2 escrow withdrawal — ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of `IntentGatewayV2` uses low-level `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` for outbound token payouts and decrements internal escrow accounting based only on whether the external call did not revert (`success == true`), without decoding and validating the ABI-encoded boolean return value that ERC-20 mandates. This is the classic "unchecked return value of ERC-20 functions" bug class, and here it directly guards fund-releasing accounting (`_orders[commitment][token] -= amount`), unlike the canonical EVM implementation which consistently uses OpenZeppelin `SafeERC20`.

### Finding Description
`withdraw()` in `evm/tron/contracts/apps/IntentGatewayV2.sol` releases escrowed tokens to a beneficiary: [1](#0-0) 

```solidity
if (token == address(0)) {
    (bool sent,) = beneficiary.call{value: amount}("");
    if (!sent) revert InsufficientNativeToken();
} else {
    (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
    if (!success) revert TransferFailed();
}

_orders[body.commitment][token] -= amount;
```
and similarly for transaction fees:
```solidity
(bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
if (!success) revert TransferFailed();
```

`success` here only reflects whether the low-level call reverted — it does **not** decode `returndata` to confirm the token actually returned `true`. Per EIP-20, a compliant token may legitimately return `false` on failure instead of reverting. If the token used as an order input (attacker/user-controlled at `placeOrder` time via `order.inputs[i].token`) implements this behavior — either intentionally (a malicious ERC-20 crafted by the order creator/solver) or because it is one of the many known non-standard tokens that return `false` instead of reverting — `withdraw()` will treat the payout as successful, decrement the escrow bookkeeping, and emit `EscrowReleased`/`EscrowRefunded` even though no tokens were actually transferred to the beneficiary.

The same unchecked pattern recurs in the `SweepDust` handler and in the `predispatch`/fill flow of `placeOrder`/`fillOrder`: [2](#0-1) 

By contrast, the reference (non-Tron) `IntentGatewayV2` and `IntentsBase` implementations consistently use `SafeERC20.safeTransfer`/`safeTransferFrom`, which do validate return data: [3](#0-2) 

This shows the Tron port diverges from the hardened pattern used elsewhere in the same codebase, reintroducing exactly the return-value-validation gap the referenced Sherlock finding describes.

### Impact Explanation
Because escrow accounting is mutated (`_orders[...] -= amount`) and the order is marked `_filled`/finalized purely based on an unchecked `success` boolean, an order funded with a token that returns `false` on failed transfer (without reverting) allows:
- The gateway to mark an order as filled/refunded and wipe escrow state while the beneficiary never receives funds — a permanent loss of the escrowed value from the beneficiary's perspective, and a state inconsistency that can be leveraged to re-trigger withdrawal paths or desynchronize commitments across chains (since same-chain and cross-chain flows both rely on this bookkeeping being an accurate record of custody).
- This qualifies as concrete freezing/loss of user funds under a reachable path: any unprivileged party can create an order (`placeOrder`) using an arbitrary ERC-20 token address, then trigger `withdraw()` via `cancelOrder`/`RedeemEscrow`/`RefundEscrow`, all reachable without any privileged role.

### Likelihood Explanation
`placeOrder` accepts an arbitrary `order.inputs[i].token` address supplied by the caller, so triggering the vulnerable code path only requires deploying (or already possessing) an ERC-20 that returns `false` instead of reverting on failure — a well-documented and common non-standard token pattern. No privileged access is required; this is directly reachable by any ordinary user/solver interacting with the Tron `IntentGatewayV2` contract's `placeOrder`, `cancelOrder`, and `onAccept`(`RedeemEscrow`/`RefundEscrow`/`SweepDust`) paths.

### Recommendation
Replace all raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` / `.call(abi.encodeWithSelector(IERC20.transferFrom.selector, ...))` patterns in `evm/tron/contracts/apps/IntentGatewayV2.sol` with OpenZeppelin's `SafeERC20.safeTransfer`/`safeTransferFrom` (already imported and used elsewhere in the same file for `safeTransferFrom` calls, e.g. in `placeOrder`), matching the pattern already used consistently in `evm/src/apps/intentsv2/IntentsBase.sol`. This ensures both call-revert and non-reverting-`false`-return failure modes are treated as failures before mutating escrow state.

### Proof of Concept
1. Deploy a malicious/non-standard ERC-20 whose `transfer(address,uint256)` returns `false` (instead of reverting) when, e.g., the caller's balance is insufficient (contract's own balance drained by a prior operation, or intentionally coded to fail after a threshold).
2. Call `placeOrder` on the Tron `IntentGatewayV2` with this token as an input asset; escrow is recorded (`_orders[commitment][token] += amount`).
3. Trigger a scenario in which the gateway's balance of the malicious token is insufficient at withdrawal time (e.g., via `SweepDust`/multiple concurrent withdrawals draining the balance, or the token's `transfer` deliberately returns `false` for the beneficiary address).
4. Call `cancelOrder`/dispatch `RedeemEscrow` to invoke `withdraw()`. The low-level `token.call(...)` returns `success = true` (call doesn't revert) but with encoded `false` in `returndata`, which is never checked.
5. `_orders[commitment][token] -= amount` executes and `EscrowReleased`/`EscrowRefunded` is emitted, while the beneficiary's on-chain token balance remains unchanged — the escrowed funds are permanently unaccounted for and unrecoverable through the normal flow.
