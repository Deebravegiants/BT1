## Title
Permissionless `CallDispatcher.dispatch()` lets any attacker plant a self-approval backdoor that drains tokens transiently held by the shared dispatcher — ([File: evm/src/utils/CallDispatcher.sol])

### Summary
`CallDispatcher.dispatch()` is a fully public function with no access control that executes any caller-supplied `Call[]` from the dispatcher's own context. Because `IntentGatewayV2` and `HyperFungibleToken`/`WrappedHyperFungibleToken` all route through the *same* shared `CallDispatcher` instance to temporarily hold user funds during predispatch/postdispatch swaps and calldata-triggered mints, an unprivileged attacker can call `dispatch()` directly with an `approve(attacker, type(uint256).max)` call for any ERC20 token. This plants a permanent backdoor allowance on the shared dispatcher. Whenever that token later transiently lands in the dispatcher as part of any other, unrelated user's legitimate order or bridged calldata execution, the attacker can call `transferFrom` on the token directly to steal it — completely bypassing `IntentGatewayV2` and `HyperFungibleToken`'s own checks. This mirrors the reported `Loihi.safeApprove` backdoor (an owner-only function that could move any tokens the contract held to any address), except here the capability requires **no privilege at all** — it is reachable by any address.

### Finding Description
`CallDispatcher.dispatch` has no caller restriction: [1](#0-0) 

It executes arbitrary `Call{to, value, data}` entries via `to.call{value: call.value}(call.data)`, so any `data` payload — including `IERC20.approve(spender, amount)` — runs with `msg.sender == CallDispatcher`. There is no restriction on who may invoke `dispatch`, nor any check on what calldata is forwarded.

This same `CallDispatcher` instance is the shared utility both `IntentGatewayV2` and the `HyperFungibleToken`/`WrappedHyperFungibleToken` apps rely on to transiently hold funds:
- `IntentGatewayV2.placeOrder` transfers a user's predispatch input tokens to the dispatcher, then calls `dispatch(order.predispatch.call)`, before sweeping the resulting balance back to the gateway: [2](#0-1) 

- `IntentsBase._execute` sends output calldata execution through the same dispatcher on fill (postdispatch), sweeping any residual balances back afterward: [3](#0-2) 

- `HyperFungibleToken`/`WrappedHyperFungibleToken` mint or unlock bridged tokens directly to the `CallDispatcher` address so its calldata can spend them:

The docs even acknowledge the dispatcher "holds tokens temporarily during execution," implicitly relying on well-behaved callers rather than an access-controlled interface: [4](#0-3) 

Because `dispatch()` is callable by anyone, an attacker does not need to go through `IntentGatewayV2` or `HyperFungibleToken` at all. A single direct call — `CallDispatcher.dispatch(abi.encode([Call({to: TOKEN, value: 0, data: approve(ATTACKER, type(uint256).max)})]))` — permanently sets `allowance[CallDispatcher][ATTACKER] = max` for `TOKEN` on the shared dispatcher. This is functionally identical to the reported `Loihi.safeApprove(token, spender, value)` backdoor, except it requires zero privilege.

### Impact Explanation
Once the malicious allowance is planted, the attacker can drain any amount of `TOKEN` that ever transiently sits on the `CallDispatcher` in the future — from any other user's `IntentGatewayV2` order (predispatch/postdispatch), any bridged `HyperFungibleToken`/`WrappedHyperFungibleToken` calldata-execution mint, or any accidental direct transfer to that address. Because the dispatcher is a single, protocol-wide shared contract, this is a concrete theft-of-funds primitive reachable from a single unprivileged transaction, satisfying "concrete theft of funds" under a High/Critical severity.

### Likelihood Explanation
The attack requires only one unprivileged call to a public function with no gating, and costs the attacker nothing but gas. Any high-value token routed through `CallDispatcher` by intent solvers, order placers, or HFT bridging users is at risk the moment it lands transiently on the dispatcher, which happens routinely as part of normal, intended protocol operation (predispatch swaps, postdispatch calldata, calldata-triggered mints).

### Recommendation
Remove `dispatch`'s implicit trust model: either (a) restrict `CallDispatcher.dispatch` to be callable only by the authorized apps (`IntentGatewayV2`, `HyperFungibleToken` instances) via an allow-list/`onlyAuthorized` modifier, or (b) make dispatcher instances ephemeral/per-call (e.g., deploy a minimal-proxy per invocation via `CREATE2`/`CREATE` and self-destruct or discard after use) so no state (including allowances) persists across calls from different callers, or (c) explicitly deny `approve`-selector calldata (and any other state-persisting selector) from being forwarded by `dispatch`. At minimum, ensure the dispatcher never retains allowances or balances outside the scope of the single legitimate transaction that funded it.

### Proof of Concept
1. Attacker calls `CallDispatcher.dispatch(abi.encode([Call({to: USDC, value: 0, data: abi.encodeWithSelector(IERC20.approve.selector, attacker, type(uint256).max)})]))` directly — no prior order, no privilege, no funds required.
2. This sets `USDC.allowance(CallDispatcher, attacker) = type(uint256).max`.
3. Later, a legitimate user places an `IntentGatewayV2` order with `predispatch.assets` including USDC (see `evm/src/apps/IntentGatewayV2.sol:235-256`, which does `IERC20(token).safeTransferFrom(msg.sender, dispatcher, amount)`), or a `HyperFungibleToken` bridge transfer mints USDC-equivalent tokens directly `to` the `CallDispatcher` address for calldata execution.
4. Before (or in a race with) the protocol's own sweep-back logic completes, the attacker calls `USDC.transferFrom(CallDispatcher, attacker, amount)` directly on the ERC20 contract, draining the victim's funds using the pre-planted allowance — entirely independent of `IntentGatewayV2`'s or `HyperFungibleToken`'s own accounting.

        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }

### Security

The `CallDispatcher` executes calls in its own context (not via `delegatecall`), so the HFT contract's storage is never at risk. If any call in the array reverts, the entire `onAccept` handler reverts — including the token mint/unlock. The request can then be retried by any relayer until the timeout expires. If no successful execution occurs before the timeout, the request times out and the sender is eligible for a refund on the source chain. Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution.

Existing `CallDispatcher` deployments are listed on the [contract addresses](/developers/evm/contract-addresses/mainnet) page.
