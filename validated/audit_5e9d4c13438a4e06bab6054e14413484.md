### Title
`Webhooks::Request#shop`/`#topic`/`#webhook_id` are excluded from the HMAC signature, allowing shop-spoofed replay of a validly-signed body - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`Webhooks::Registry.process` validates only `request.hmac` against `request.to_signable_string`, and `to_signable_string` returns just `@raw_body`. The `shop`, `topic`, `webhook_id`, and `api_version` values passed into the handler via `WebhookMetadata` come from HTTP headers that are never covered by the signature, so an attacker holding one genuinely-signed body (from their own shop's webhook) can replay it directly to the app's webhook endpoint with an arbitrary `x-shopify-shop-domain` header and still pass `HmacValidator.validate`.

### Finding Description
The claimed binding is: `HmacValidator.validate(request) == true` should imply `request.shop` (and other headers used by the handler) are authenticated together with `request.parsed_body`. This does not hold.

- `to_signable_string` returns only `@raw_body`: [1](#0-0) 
- `shop`, `topic`, `webhook_id`, `api_version` are all read straight from attacker-controlled headers, with no signature coverage: [2](#0-1) 
- `HmacValidator.validate_signature` computes the HMAC only over `verifiable_query.to_signable_string`, i.e. the raw body: [3](#0-2) 
- `Registry.process` first checks the HMAC, then immediately trusts `request.topic`, `request.shop`, `request.parsed_body`, `request.api_version`, `request.webhook_id` to build the `WebhookMetadata` handed to the app's handler: [4](#0-3) 
- The documented handler contract explicitly treats `data.shop` as the authenticated shop identity for the webhook: [5](#0-4) 

Exploit flow: an attacker who has installed the app on their own development shop receives a genuinely Shopify-signed webhook (raw body + `x-shopify-hmac-sha256`) for their own shop. They can influence the body content substantially (e.g. via product titles, order notes, customer fields on their own store) since HMAC coverage is body-only and computed with the app's single shared `api_secret_key` (not shop-specific). The attacker then POSTs this exact `(raw_body, hmac)` pair directly to the app's public webhook endpoint (bypassing Shopify's servers entirely — nothing in this gem restricts webhook delivery source), but sets `x-shopify-shop-domain` to an arbitrary/victim value. `HmacValidator.validate` still succeeds because it only checks the body against the shared secret; `Registry.process` then calls the handler with `WebhookMetadata#shop` set to the attacker's chosen domain. The app, following the documented contract, will process/attribute this data as though it were an authenticated webhook for that shop.

Existing guards do not stop this: `HmacValidator.validate` only checks body+secret [6](#0-5) ; there is no `ShopValidator.sanitize!` call, no nonce/timestamp/delivery-id binding check, and `webhook_id` (intended per docs for de-duplication, not authentication) is likewise unsigned [7](#0-6) .

The `decode64`/base64url angle in the question is a red herring: `Base64.decode64` is lenient and simply produces a different (garbage) byte string for `-`/`_` input, which would fail `OpenSSL.secure_compare` against the correctly computed HMAC — it does not itself cause a bypass. The actual, demonstrable gap is the missing signature coverage of the `shop`/`topic`/`webhook_id`/`api_version` headers.

### Impact Explanation
Any header value (`shop`, `topic`, `webhook_id`, `api_version`) used by the documented handler contract can be forged independently of the signed body content, because the signature only binds the body. This enables cross-tenant confusion: content genuinely signed for one shop's webhook can be replayed and falsely attributed by the app to a different shop, since `api_secret_key` is shared across all installs of the app rather than being shop-specific. This matches the "cross-tenant access" / authentication-bypass class, since the app is led to trust an unauthenticated header value (`shop`) as if it were authenticated. The blast radius depends on what the host app does with `data.shop` (e.g., attributing orders, mandatory-compliance topics like `customers/redact`, or billing/entitlement logic to the wrong merchant).

### Likelihood Explanation
Preconditions: attacker needs a real (self-controlled) shop with the app installed and at least one HTTP webhook registered, so they can obtain one genuinely signed `(raw_body, hmac)` pair — a low-cost, self-serve step per the rules' attacker model. The attacker must also know/guess the app's public webhook endpoint path (typically documented/predictable, e.g. `/webhooks`), and the app must use `data.shop`/`data.topic` for anything security- or tenant-sensitive without independently re-verifying shop association (e.g. via session/shop lookup) — this depends on host-app implementation, which is not controlled by this gem. Given the documented pattern in `docs/usage/webhooks.md` encourages trusting `data.shop` directly, this is a realistic, repeatable exploitation path with no live shop needed, only a single genuinely-signed body captured once and replayable indefinitely.

### Recommendation
Include the security-relevant headers (`shop`, `topic`, `webhook_id`, `api_version`) in the signable string, or otherwise cryptographically bind them to the body before comparing the HMAC — e.g. by canonicalizing `topic + "\n" + shop + "\n" + raw_body` in `to_signable_string`, or by requiring the host app to independently verify `shop` against a known/expected value (e.g. the shop tied to the session used to register the webhook) rather than trusting the header as-is. At minimum, document clearly that `shop`/`topic`/`webhook_id` are NOT covered by the HMAC and must not be trusted for tenant attribution without further verification.

### Proof of Concept
```ruby
# test/webhooks/registry_shop_spoof_test.rb
require "test_helper"

class RegistrySpoofTest < Test::Unit::TestCase
  def setup
    ShopifyAPI::Context.setup(api_key: "key", api_secret_key: "secret", ...)
    @received_shops = []
    handler = Module.new do
      extend ShopifyAPI::Webhooks::WebhookHandler
      define_singleton_method(:handle) { |data:| @received_shops = (@received_shops ||= []) << data.shop }
    end
    ShopifyAPI::Webhooks::Registry.add_registration(
      topic: "orders/create", delivery_method: :http, path: "cb", handler: handler,
    )
  end

  def test_same_signature_accepted_for_two_different_shops
    raw_body = '{"id":1,"note":"attacker-controlled"}'
    hmac = Base64.strict_encode64(
      OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), "secret", raw_body),
    )

    req_a = ShopifyAPI::Webhooks::Request.new(
      raw_body: raw_body,
      headers: {
        "x-shopify-topic" => "orders/create",
        "x-shopify-hmac-sha256" => hmac,
        "x-shopify-shop-domain" => "victim-shop.myshopify.com",
        "x-shopify-webhook-id" => "1",
        "x-shopify-api-version" => "2024-01",
      },
    )
    req_b = ShopifyAPI::Webhooks::Request.new(
      raw_body: raw_body,
      headers: {
        "x-shopify-topic" => "orders/create",
        "x-shopify-hmac-sha256" => hmac,
        "x-shopify-shop-domain" => "attacker-shop.myshopify.com",
        "x-shopify-webhook-id" => "2",
        "x-shopify-api-version" => "2024-01",
      },
    )

    ShopifyAPI::Webhooks::Registry.process(req_a)
    ShopifyAPI::Webhooks::Registry.process(req_b)

    # Same signature/body accepted twice while resolving to two different shops:
    assert_equal ["victim-shop.myshopify.com", "attacker-shop.myshopify.com"], @received_shops
  end
end
```
This demonstrates that `HmacValidator.validate` treats `req_a` and `req_b` as equally authentic despite differing `shop` — confirming the signature does not bind `shop` to the body, i.e. `HmacValidator.validate(request) == true` does not imply `request.shop` is authenticated.
