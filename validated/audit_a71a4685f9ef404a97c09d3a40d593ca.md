## Title
Webhook shop attribution is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies webhook authenticity using `Utils::HmacValidator.validate`, which computes the HMAC only over `to_signable_string`, i.e. the raw request body. The `shop` value used to attribute the webhook to a tenant is read directly from the `x-shopify-shop-domain`/`shopify-shop-domain` header and is never included in the signed payload, so the binding `hmac_verified_bytes == bytes_used_for_shop_attribution` does not hold.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is a separate accessor that simply reads the `shop-domain` header, entirely outside the signed data: [2](#0-1) 

`Registry.process` validates the HMAC over the body only, then immediately trusts `request.shop` to build the `WebhookMetadata` handed to the app's handler: [3](#0-2) 

`HmacValidator.validate`/`validate_signature` confirm this: the comparison is strictly between the computed signature of `verifiable_query.to_signable_string` (the body) and the received HMAC — the shop header never enters the equality check: [4](#0-3) 

By contrast, the OAuth callback's `AuthQuery` (the other `VerifiableQuery` implementer in this gem) does bind `shop` into the signed string: [5](#0-4) 

showing the gem's own pattern for correctly binding tenant identity into an HMAC-verified value — a pattern the webhook path does not follow.

Because Shopify signs a webhook body with the app's shared `api_secret_key` regardless of which installed shop it originates from, any shop that has this app installed can receive a legitimate, validly-signed webhook body+HMAC pair for its own tenant, then replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header value. `HmacValidator.validate` will still succeed (it never looks at the header), and `Registry.process` will hand the host application's handler a `WebhookMetadata` object whose `shop` field is attacker-controlled and disconnected from the actually-authenticated bytes.

### Impact Explanation
This breaks the identity binding `authenticated_shop == shop_used_for_tenant_dispatch`. Any host application that uses this gem's webhook processing and trusts `WebhookMetadata#shop` (or `request.shop`) to select which tenant's data to update — a documented and expected usage pattern — can be made to apply another shop's data under the identity of an arbitrary target shop, i.e. cross-tenant access/confusion originating from an unprivileged party (a shop merely capable of installing the app and receiving its own genuine webhooks).

### Likelihood Explanation
Exploitation requires only that the attacker installs the app on their own shop (an unprivileged, self-serve action) and is able to receive one legitimate webhook delivery — which happens automatically for any registered topic. No access token, `client_secret`, or privileged account is required; the attacker only replays already-received, validly-signed traffic with a modified header.

### Recommendation
Include the `shop-domain` header value in the signable string used by `Webhooks::Request#to_signable_string` (or otherwise cryptographically bind it, e.g. by requiring host apps to cross-check `request.shop` against the shop associated with the resolved session/access token) so that the HMAC verifies both body integrity and shop attribution together, mirroring the approach already used in `Auth::Oauth::AuthQuery#to_signable_string`.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; trigger any registered webhook topic (e.g. `orders/create`) so Shopify delivers a body `B` with a valid `x-shopify-hmac-sha256` computed over `B` using the app's `api_secret_key`.
2. Capture the raw POST: headers include `x-shopify-hmac-sha256: <valid>`, `x-shopify-shop-domain: attacker.myshopify.com`, body `B`.
3. Replay the identical request to the app's webhook endpoint, changing only `x-shopify-shop-domain` to `victim.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate` recomputes the HMAC over `B` only [6](#0-5)  — it succeeds because `B` is unmodified.
5. `Registry.process` proceeds and calls the app's handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed(B), ...)` [7](#0-6) , causing the host app to act on attacker-supplied data under the victim shop's identity.
