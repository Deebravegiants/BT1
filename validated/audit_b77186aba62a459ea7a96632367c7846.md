### Title
Unvalidated `bytes32`→`address` truncation of cross-chain `beneficiary`/`token` fields silently redirects escrowed funds - (File: evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
`IntentsBase._withdraw` and `_execute`/`_sweepDust` derive `address` values by doing `address(uint160(uint256(x)))` on `bytes32` fields (`body.beneficiary`, `body.tokens[i].token`, `order.output.assets[i].token`) that arrive either from a relayed cross-chain ISMP message body (`WithdrawalRequest`) or from a solver/order-encoded `TokenInfo`. This is the same bug class as the ENS `hexToAddress` finding: the upper 96 bits of the 256-bit value are discarded without ever checking they are zero, so any non-canonical encoding of the field (extra garbage in the high bits) is silently accepted and converted into an arbitrary, unintended address instead of being rejected.

### Finding Description
`_withdraw` is the function that actually pays out escrowed input/output tokens on both the fill and refund/cancel paths: [1](#0-0) 

It converts `body.beneficiary` (a `bytes32`) and each `body.tokens[i].token` (also `bytes32`) straight into an `address` with a raw truncating cast, with no check that the top 96 bits are zero: [2](#0-1) 

The same pattern recurs in `_execute` (sweeping dispatcher dust for `order.output.assets[i].token`) and `_sweepDust` (governance dust sweep for `info.token`): [3](#0-2) [4](#0-3) 

`WithdrawalRequest.beneficiary` is decoded from the body of a `RedeemEscrow`/`RefundEscrow` ISMP request delivered through `onAccept` (relayed cross-chain message), and `TokenInfo.token`/`PaymentInfo.beneficiary` fields originate from the `Order` struct that any unprivileged user assembles and submits via `placeOrder`, and that a solver echoes back via `fillOrder`'s `FillOptions.outputs`. Both paths are reachable from a single, unprivileged transaction/dispatched request — exactly the class of entry point in scope (message dispatch/delivery and token-bridge/intents escrow paths).

Because the destination-chain contract never verifies `bytes32(uint256(uint160(x))) == x` before consuming these fields, an attacker (or a source-chain bug/relayer replaying a subtly corrupted body) can supply a `beneficiary` or `token` value whose high 96 bits are non-zero. `_withdraw` will still compute a valid-looking 20-byte `address`, mark the order `_filled[commitment] = beneficiary` with that truncated address, and transfer the escrowed ERC-20/native tokens to it — an address that has no relationship to the value actually committed to in the order hash. Since the commitment hash `keccak256(abi.encode(order))` is computed over the full un-truncated `bytes32` fields, but the payout resolves the truncated address, a discrepancy between "the address the order committed to" and "the address that actually receives funds" becomes possible whenever the upper bits are non-zero — this is a state where committed funds can be routed to an address other than what any off-chain observer (indexer, solver, or the user) believes was authorized, satisfying "unsound state commitment" / permanent misdirection of escrowed funds.

### Impact Explanation
Escrowed input tokens (for fills) or output tokens on the destination side (or refunds) can be paid to a truncated/attacker-influenced address rather than the intended `beneficiary`, and ERC-20 `token` addresses derived the same way could point at an unintended contract. Because `_filled[commitment]` is also set from this truncated value and gates re-fill/re-refund logic, once funds have moved to the wrong address the order is finalized and irrecoverable — a permanent loss of escrowed funds. This matches the "concrete theft or permanent freezing of funds" acceptance bar.

### Likelihood Explanation
Likelihood is moderate: exploiting it requires getting a `bytes32` field with non-zero high bits into a `WithdrawalRequest`/`TokenInfo`/`PaymentInfo` field that reaches `_withdraw`/`_execute`/`_sweepDust`. The SDK-side helper functions that construct these values (`bytes20ToBytes32`, `normalizeAddressForEvmBytes32`) do enforce 20/32-byte lengths off-chain, but the on-chain contract itself performs no equivalent check, so it depends entirely on well-behaved off-chain encoders and honest solvers never sending a malformed 32-byte value. Any deviation — a bug in an alternate SDK/relayer implementation, a malicious solver crafting `FillOptions.outputs`, or hand-crafted calldata bypassing the SDK — is accepted silently rather than rejected, consistent with the ENS report's judged severity (data-integrity issue that "relies on some user/encoder error, is easy to check/fix, and presents material risk").

### Recommendation
In `IntentsBase._withdraw`, `_execute`, and `_sweepDust` (and anywhere else in `evm/src/apps/intentsv2/*.sol` and `evm/src/apps/IntentGatewayV2.sol` performing `address(uint160(uint256(x)))`), add an explicit check that the high 96 bits of the `bytes32` are zero before truncating, e.g.:
```solidity
if (uint256(x) >> 160 != 0) revert InvalidAddress();
```
and revert (or reject the request) instead of silently accepting a truncated/mismatched address, mirroring the recommended fix from the ENS report (validate upper 96 bits before casting `bytes32` → `address`).

### Proof of Concept
1. A user or relayed request supplies a `WithdrawalRequest` (or `Order.output.beneficiary` / `TokenInfo.token`) whose `bytes32` value is `0xFFFFFFFF000000000000000000000000000000AAAAAAAAAAAAAAAAAAAAAAAA` (non-zero upper 96 bits, valid-looking low 160 bits).
2. This request reaches `IntentsBase._withdraw` via the `RedeemEscrow`/`RefundEscrow` request-handling path in `IntentGatewayV2.onAccept`.
3. `address(uint160(uint256(body.beneficiary)))` in `evm/src/apps/intentsv2/IntentsBase.sol:452` truncates the value to `0xAAAAAAAAAAAAAAAAAAAAAAAA...` without any revert, and `_orders`/escrowed tokens are transferred to this truncated address.
4. Because the full 32-byte value (with the non-zero high bits) is what was hashed into the order commitment on the source chain, the address that actually received the funds does not match what any correctly-encoding, honest party expected — with no on-chain check to prevent it.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
