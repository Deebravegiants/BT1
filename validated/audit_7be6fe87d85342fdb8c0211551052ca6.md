Audit Report

## Title
CORS Origin Allowlist Bypass via Unanchored Suffix Matching in Gateway HTTP Server - (File: `core/services/gateway/network/httpserver.go`)

## Summary
The gateway's `isAllowedOrigin` function validates wildcard CORS allowlist entries (e.g. `*.ethereum.org`) using unanchored `strings.HasSuffix` matching instead of a dot-boundary subdomain check, allowing any domain that textually ends with the allowed suffix (e.g. `myethereum.org`) to be incorrectly treated as a trusted subdomain of `ethereum.org`.

## Finding Description
In `isAllowedOrigin` [1](#0-0) , after stripping the `*.` prefix from a configured allowed origin, the code checks `strings.HasSuffix(originHost, allowedHost)` with no verification that the matched suffix is preceded by a `.` label separator. This means `originHost = "myethereum.org"` matches `allowedHost = "ethereum.org"` even though `myethereum.org` is an independent, separately registrable domain rather than a true subdomain. This result feeds directly into `handleRequest` [2](#0-1) , which sets `Access-Control-Allow-Origin` to the caller-supplied `Origin` header whenever `isAllowedOrigin` returns true — there is no additional origin validation layer downstream. The existing regression tests [3](#0-2)  only cover dot-separated label mismatches (`ethereum.remix.org`) and scheme/port mismatches, never the no-boundary concatenation case, confirming the gap is untested and unfixed.

## Impact Explanation
This is a concrete CORS allowlist bypass: an attacker who registers or controls a domain ending in a trusted wildcard suffix string can have their page's cross-origin requests to the gateway accepted with a reflected `Access-Control-Allow-Origin`, breaking the intended origin-boundary trust model gating browser-based access to the gateway's request-handling API. This falls into the "allowlist or subscription bypass" impact category for the Chainlink bounty scope.

## Likelihood Explanation
Exploitability requires only that an operator configure a wildcard `CORSAllowedOrigins` entry (a normal, documented configuration option) and that an attacker register a domain ending with that suffix — both realistic conditions since arbitrary second-level domains ending in a given string are commonly registrable. No special privilege, credential, or victim interaction is required beyond a standard browser request with a crafted `Origin` header.

## Recommendation
Require a dot boundary before the matched suffix, e.g. check `originHost == baseDomain || strings.HasSuffix(originHost, "."+baseDomain)` instead of the raw `strings.HasSuffix(originHost, allowedHost)` comparison in `isAllowedOrigin`.

## Proof of Concept
1. Start the gateway HTTP server with `CORSAllowedOrigins = ["https://*.ethereum.org"]` and `CORSEnabled = true`.
2. Send a request with header `Origin: https://myethereum.org`.
3. Observe `isAllowedOrigin` strips to `allowedHost = "ethereum.org"` and `strings.HasSuffix("myethereum.org", "ethereum.org")` returns `true`.
4. Observe the response includes `Access-Control-Allow-Origin: https://myethereum.org`, confirming the bypass — this can be added as a Go unit test analogous to `TestHTTPServer_HandleRequest_CORSEnabled_FromNotAllowedOriginWildcards` but asserting the header IS set for `https://myethereum.org` (currently it incorrectly would be).
