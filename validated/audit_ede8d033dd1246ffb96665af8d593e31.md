### Title
Excess native token sent to `EvmHost.dispatch`/`fundRequest` is permanently stranded in the host contract - (File: `evm/src/core/EvmHost.sol`)

### Summary
This is the same bug class as the OpenQ report: a function accepts both a native-value payment and records/uses only part of it, silently losing the excess for the caller. In `EvmHost`, `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest` swap `msg.value` for an exact amount of fee tokens via `swapETHForExactTokens{value: msg.value}(...)`, but never forward or refund any leftover ETH back to `_msgSender()`.

### Finding Description
In each of these functions, whenever `msg.value > 0`, the code does: [1](#0-0) 
i.e. it calls `swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)` and moves straight on to build/emit the request — with no code afterward that checks for or refunds unspent ETH.

The router used underneath (either the genuine Uniswap V2 router, or the project's own `UniV3UniswapV2Wrapper`/`UniV4UniswapV2Wrapper`/`GnosisUniswapV2Wrapper`) refunds unspent ETH to `msg.sender` of the swap call. Since `EvmHost` itself calls the router, the refund goes to `EvmHost`'s own balance: [2](#0-1) 

`EvmHost` has no logic to forward that refunded value back to the original caller, and no `withdraw`/sweep function was found for stray native balance in `EvmHost.sol`. The same pattern repeats in `dispatch(DispatchGet)` and `fundRequest`: [3](#0-2) [4](#0-3) 

Any caller (including `WrappedHyperFungibleToken.send`/`WrappedHyperFungibleTokenUpgradeable.send`, which forward the full remaining `msg.value` as the native fee) that supplies more native value than the exact fee-token cost, or whose swap quote turns out to require less ETH than initially estimated (price movement between quoting and executing), permanently loses that excess: it is not tracked in any accounting struct (`FeeMetadata`), not returned to the sender, and not recoverable via any documented admin/withdraw path.

### Impact Explanation
Any unprivileged user calling `dispatch`, `fundRequest`, or any HyperApp/adapter that forwards `msg.value` through these entry points (e.g. `WrappedHyperFungibleToken.send`) with even slight overpayment of native token loses the difference permanently to the `EvmHost` contract balance, unrecoverable by them. This is a direct, concrete loss of user funds reachable from a single transaction with no privileged role required — a Medium severity finding, matching the exact bug class described in the report (partial payment silently lost when both a native amount and a token-denominated cost are involved).

### Likelihood Explanation
Likelihood is high: any minor mismatch between the amount of ETH a caller sends and the exact amount the router consumes (due to slippage between quoting and execution, or a caller intentionally/accidentally over-sending) triggers the loss on every affected call. No malicious actor is required — this occurs in normal usage whenever `msg.value` isn't the exact amount consumed by the swap.

### Recommendation
After each `swapETHForExactTokens` call in `EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest`, check the actual ETH consumed (returned by `amounts[0]`) versus `msg.value`, and refund any unspent ETH to `_msgSender()` (or `post.payer`), mirroring the refund pattern already implemented in `IntentGatewayV2.placeOrder` and `ExtrinsicIntents._fillCrossChain`: [5](#0-4) 

### Proof of Concept
1. Caller invokes `EvmHost.dispatch(post)` with `msg.value = X` where `X` is intentionally or accidentally larger than the exact ETH cost to acquire `post.fee` fee tokens via the configured Uniswap V2-compatible router.
2. `swapETHForExactTokens{value: X}(post.fee, path, address(this), block.timestamp)` executes; the router/wrapper spends `spent < X` ETH and refunds `X - spent` ETH to `msg.sender` of the swap call, i.e., `EvmHost` itself. [1](#0-0) 
3. Execution continues directly to constructing the `PostRequest`/`FeeMetadata` and emitting the event; the refunded `X - spent` ETH is never sent back to the original caller nor tracked anywhere. [6](#0-5) 
4. The excess ETH remains permanently in `EvmHost`'s balance with no recovery mechanism for the caller.
