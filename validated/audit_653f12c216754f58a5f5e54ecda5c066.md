### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant shop-identity spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string solely from the raw request body, while the `shop` (and `topic`, `webhook_id`) values used to attribute the webhook to a tenant are taken from unsigned HTTP headers. `Utils::HmacValidator.validate` only checks that the body matches the HMAC; it never binds the `shop-domain` header to that signature. This breaks the identity binding `hmac(shop, body) == received_hmac` down to `hmac(body) == received_hmac`, letting a caller reuse a genuinely-signed body while substituting an arbitrary `shop` header.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read straight from an unauthenticated header, independent of the signed content: [2](#0-1) 

`HmacValidator.validate` computes the signature purely over `verifiable_query.to_signable_string` (the body) and compares it to the received HMAC — it never incorporates `shop`, `topic`, or `webhook_id`: [3](#0-2) 

`Registry.process` trusts this unverified `shop` value and forwards it directly into the handler's `WebhookMetadata`, which is the app-facing, "authenticated" webhook payload: [4](#0-3) 

By contrast, the OAuth callback path correctly binds `shop` into the HMAC-signed string (`AuthQuery#to_signable_string` includes `shop`): [5](#0-4) 

This asymmetry shows the webhook path is the outlier: the exact field (`shop`) that `Registry.process` relies on to identify the tenant is excluded from the cryptographic check that is supposed to authenticate the whole request.

### Impact Explanation
An attacker who legitimately receives webhooks for their own shop (installed instance of the same app) possesses a genuine `(raw_body, hmac)` pair signed by the app's `client_secret`. Because the HMAC never covers the `shopify-shop-domain` header, the attacker can replay that same body/HMAC pair to the app's webhook endpoint while substituting the `shopify-shop-domain` header for a victim shop. `HmacValidator.validate` still returns `true` (body unchanged), and `Registry.process` passes the attacker-chosen shop value straight to the app's handler via `WebhookMetadata#shop`. If the host app uses `data.shop` (as this gem's own webhook API and documentation direct it to) to look up/mutate per-shop state (e.g., process an `orders/create`, `app/uninstalled`, or GDPR-type webhook "as" another shop), this results in cross-tenant data confusion/manipulation — one merchant's traffic being attributed to another merchant's tenant.

### Likelihood Explanation
Exploitation requires only that the attacker control one legitimate app installation (a normal, unprivileged capability for any merchant who installs a public/embedded app) and knowledge of the gem's documented `Webhooks::Request`/`Registry.process` interface — no access to the `client_secret`, no privileged account, and no interception of TLS is required. The header manipulation is trivial (a raw HTTP request replay with one header changed).

### Recommendation
Include the `shop` (and `topic`/`webhook_id`, if they are meant to be trusted) in the HMAC-signable string for webhook requests, mirroring how `AuthQuery` includes `shop` in its signable string, so that any header value consumed downstream is cryptographically bound to the same signature that authenticates the payload. Alternatively, document explicitly that only the raw body is authenticated and that host applications must not trust `shop`, `topic`, or `webhook_id` headers from `Webhooks::Request`/`WebhookMetadata` for tenant attribution — however, since the gem's own `Registry.process`/`WebhookMetadata` API surfaces these fields as the trusted result of "webhook HMAC validation," binding them cryptographically is the correct fix.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and receives a legitimate webhook, e.g. `orders/create`, with body `B` and header `shopify-hmac-sha256: H`, where `H = HMAC-SHA256(client_secret, B)`.
2. Attacker resends the same raw body `B` and the same `shopify-hmac-sha256: H` header to the app's webhook endpoint, but sets `shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...shop-domain: "victim.myshopify.com", hmac-sha256: H...})` is constructed; `to_signable_string` returns `B` unchanged.
4. `Utils::HmacValidator.validate(request)` recomputes `HMAC-SHA256(client_secret, B)` — matches `H` — returns `true`.
5. `Registry.process(request)` invokes the app's handler with `WebhookMetadata.new(shop: "victim.myshopify.com", topic: ..., body: parsed(B), ...)`, causing the app to process attacker-supplied data under the victim shop's identity.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
