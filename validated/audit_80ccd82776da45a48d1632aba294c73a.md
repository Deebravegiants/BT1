### Title
Missing `state_exists` Reinitialization Guard Allows Unauthorized Owner Takeover of Lockup Contract - (File: lockup/src/lib.rs)

### Summary
`LockupContract::new` in `lockup/src/lib.rs` is a public `#[init]` method that lacks the `assert!(!env::state_exists(), ...)` guard present in every other production contract in this repository (`staking-pool`, `staking-pool-factory`, `whitelist`, `multisig`, `lockup-factory`, `voting`). This omission allows any unprivileged account to call `new` again on an already-deployed and funded lockup account, fully overwriting `owner_account_id`, `vesting_information`, `staking_pool_whitelist_account_id`, and `foundation_account_id`, effectively seizing ownership of the locked NEAR held by the account.

### Finding Description
Every sibling `#[init]` constructor in this repo defends against re-initialization by checking `env::state_exists()` before writing state: [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) 

`LockupContract::new`, however, performs no such check before constructing and returning `Self`: [6](#0-5) 

Because this near-sdk version (`near-sdk = "3.1.0"`, per `lockup/Cargo.toml`) does not itself enforce a single-call invariant for `#[init]` methods — as evidenced by every other contract in the same repository having to add the check manually — `new` on the lockup contract remains callable indefinitely as a normal public method after deployment. Any account (an unprivileged, non-owner, non-foundation caller) can send a `FunctionCall` action invoking `new` on the deployed lockup account with attacker-chosen arguments: their own `owner_account_id`, `foundation_account_id: None` (removing the NEAR Foundation's ability to terminate vesting), and `vesting_schedule: None`/`transfers_information` set to `TransfersEnabled` immediately.

Once this succeeds, `self.owner_account_id` is now the attacker's account, and `assert_owner()` — used by every fund-moving owner method (`transfer`, `unstake_all`, `withdraw_from_staking_pool`, `add_full_access_key`, etc.) — will pass for the attacker: [7](#0-6) [8](#0-7) 

This mirrors the class of vulnerability in the external report: state that must only be set once, at initialization, and thereafter trusted for access control, can be re-set by an untrusted caller because the "constructor" is not properly locked after first use.

### Impact Explanation
This falls squarely under "Critical – Unauthorized transfer, withdrawal, spending, or release of locked … NEAR through public-call … reachable by an unprivileged user." An attacker who successfully reinitializes an existing lockup account becomes its owner and, once transfers are enabled (which the attacker can also set via the same call, or via `TransfersDisabled` pointing to an attacker-controlled poll account), can call `transfer` to drain the account's NEAR balance, or `add_full_access_key` to gain a full-access key to the account, fully expropriating all locked/vested NEAR held by that lockup contract.

### Likelihood Explanation
Likelihood depends on whether `#[init]` in `near-sdk 3.1.0` independently rejects calls when contract state already exists, regardless of the function body. I could not verify the near-sdk-rs 3.1.0 macro-expansion behavior directly (it lives outside `scope_files`, in the external `near-sdk` crate) to confirm whether the framework itself blocks re-invocation of `#[init]` methods once state exists. The fact that every other contract in this repository has to manually add `assert!(!env::state_exists(), ...)` strongly suggests the framework does **not** provide this protection automatically, and that its absence in `lockup/src/lib.rs` is a real, exploitable gap rather than redundant defense-in-depth. Given this repo's own precedent, this should be treated as a genuine finding requiring confirmation against the exact near-sdk 3.1.0 `#[init]` codegen before final triage.

### Recommendation
Add the same guard used everywhere else in the codebase to `LockupContract::new`:
```rust
assert!(!env::state_exists(), "The contract is already initialized");
```
at the top of the function in `lockup/src/lib.rs`, before any state is asserted or constructed.

### Proof of Concept
1. Lockup contract `alice.lockup.near` is deployed and initialized via `LockupContract::new(owner_account_id: "alice.near", ...)`, funded with locked NEAR.
2. Attacker `mallory.near` (unprivileged, not owner, not foundation) sends a `FunctionCall` to `alice.lockup.near` invoking `new` again with:
   - `owner_account_id: "mallory.near"`
   - `transfers_information: TransfersEnabled { transfers_timestamp: <now> }`
   - `vesting_schedule: None`, `foundation_account_id: None`
3. Because `new` has no `state_exists` guard, the call succeeds and overwrites contract state, including `owner_account_id = "mallory.near"`.
4. `mallory.near` calls `transfer(amount, "mallory.near")` or `add_full_access_key(mallory_pubkey)`; `assert_owner()` passes since `predecessor_account_id() == self.owner_account_id`, allowing the attacker to withdraw or seize full control of the account's NEAR. [6](#0-5)

    #[init]
    pub fn new(
        owner_account_id: AccountId,
        lockup_duration: WrappedDuration,
        lockup_timestamp: Option<WrappedTimestamp>,
        transfers_information: TransfersInformation,
        vesting_schedule: Option<VestingScheduleOrHash>,
        release_duration: Option<WrappedDuration>,
        staking_pool_whitelist_account_id: AccountId,
        foundation_account_id: Option<AccountId>,
    ) -> Self {
        assert!(
            env::is_valid_account_id(owner_account_id.as_bytes()),
            "The account ID of the owner is invalid"
        );
        assert!(
            env::is_valid_account_id(staking_pool_whitelist_account_id.as_bytes()),
            "The staking pool whitelist account ID is invalid"
        );
        if let TransfersInformation::TransfersDisabled {
            transfer_poll_account_id,
        } = &transfers_information
        {
            assert!(
                env::is_valid_account_id(transfer_poll_account_id.as_bytes()),
                "The transfer poll account ID is invalid"
            );
        }
        let lockup_information = LockupInformation {
            lockup_amount: env::account_balance(),
            termination_withdrawn_tokens: 0,
            lockup_duration: lockup_duration.0,
            release_duration: release_duration.map(|d| d.0),
            lockup_timestamp: lockup_timestamp.map(|d| d.0),
            transfers_information,
        };
        let vesting_information = match vesting_schedule {
            None => {
                assert!(
                    foundation_account_id.is_none(),
                    "Foundation account can't be added without vesting schedule"
                );
                VestingInformation::None
            }
            Some(VestingScheduleOrHash::VestingHash(hash)) => VestingInformation::VestingHash(hash),
            Some(VestingScheduleOrHash::VestingSchedule(vs)) => {
                VestingInformation::VestingSchedule(vs)
            }
        };
        assert!(
            vesting_information == VestingInformation::None ||
                env::is_valid_account_id(foundation_account_id.as_ref().unwrap().as_bytes()),
            "Foundation account should be added for vesting schedule"
        );

        Self {
            owner_account_id,
            lockup_information,
            vesting_information,
            staking_information: None,
            staking_pool_whitelist_account_id,
            foundation_account_id,
        }
    }
