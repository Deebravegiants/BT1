Confirmed: `ShopifyAPI::Webhooks::Request#to_signable_string` at `lib/shopify_api/webhooks/request.rb:36-38` returns only `@raw_body`, while `shop`, `topic`, `api_version`, and `webhook_id` are all read from HTTP headers that are never part of the HMAC-signed string. `Registry.process` at `lib/shopify_api/webhooks/registry.rb:189-199` validates only the HMAC and then forwards `request.shop` straight into `WebhookMetadata` for the handler, with no separate binding between the authenticated body and the shop-domain claim.

### Title
Webhook tenant identity (`shop`, `topic`) is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Utils::HmacValidator.validate` authenticates a webhook solely by recomputing the HMAC over `Request#to_signable_string`, which is hard-coded to the raw body only. The `shop`, `topic`, `api_version`, and `webhook_id` headers that `Registry.process` trusts and passes to the app's handler are excluded from that signature, so the binding `hmac_verifies(body) == hmac_verifies(shop, topic, body)` does not hold.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and defines: [1](#0-0) 
returning only `@raw_body`. `shop`, `topic`, `api_version`, and `webhook_id` are read directly from attacker-controlled HTTP headers: [2](#0-1) 

`HmacValidator.validate` only checks that the supplied `hmac` header matches HMAC(secret, `to_signable_string`): [3](#0-2) 

`Registry.process` performs exactly this check and then dispatches the handler using the unauthenticated `shop`/`topic` headers as the tenant identity: [4](#0-3) 

Because HMAC is computed over the body only, any request with a body+HMAC pair that is valid for the app's secret (which the attacker can legitimately obtain by installing the app on their own store and capturing a real webhook delivery) remains "valid" even after swapping the `x-shopify-shop-domain` and/or `x-shopify-topic` headers to arbitrary values, since none of those fields are part of the signed content. This breaks the identity binding the gem is supposed to enforce: "the shop whose HMAC was verified" vs. "the shop the handler acts on" are two different, uncoupled values.

### Impact Explanation
This is a cross-tenant identity confusion: an app that keys downstream side effects (e.g., "which merchant record to update", "which merchant's data to fulfill") off `WebhookMetadata#shop`/`#topic` as delivered by this gem's `Registry.process` can be made to act on behalf of a shop the attacker does not control, using a signature that only ever proved authenticity of the body content, not of the tenant metadata. This matches the Critical-tier "cross-tenant access" impact category, since it defeats the very tenant-binding guarantee the HMAC check exists to provide.

### Likelihood Explanation
Exploitability requires only unprivileged internet access plus a legitimate installation of the target app on an attacker-owned store (a normal, unprivileged action for any developer app listed on Shopify or any app with open installs) to obtain one valid (body, hmac) pair, and the ability to POST directly to the app's webhook endpoint with forged headers — no `api_secret_key`, access token, or victim credential is needed. No Shopify-side control resists this because Shopify's outbound HMAC only ever covered the body in the first place; the gem's `to_signable_string` decision to sign only the body is the root cause of the missing binding.

### Recommendation
Include the shop-domain (and ideally topic and API version) headers in the HMAC-signable string for webhook requests, or otherwise cryptographically bind those header values to the webhook body/signature before trusting them in `WebhookMetadata`. At minimum, document/require that host applications independently verify `data.shop` against a shop record and treat it as untrusted metadata, and consider making `Registry.process` re-derive a canonical shop identity rather than propagate raw header content.

### Proof of Concept
1. Install the target Shopify app (any unprivileged action) on an attacker-owned store `attacker.myshopify.com`.
2. Trigger a real webhook (e.g. `orders/create`) and capture the legitimate `raw_body`, `x-shopify-hmac-sha256`, and other headers from the delivered request — the HMAC is valid because it is computed only over `raw_body`.
3. Replay this exact `raw_body` + `hmac` header pair to the app's webhook endpoint, but set `x-shopify-shop-domain: victim-shop.myshopify.com` (and optionally change `x-shopify-topic`).
4. `Utils::HmacValidator.validate` succeeds because `to_signable_string` never included the shop/topic headers. [5](#0-4) 
5. `Registry.process` dispatches to the handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", topic: ..., body: attacker's body)`, causing the app to act as if the victim shop sent this data.
