### Title
BitcoinCash `compareAddresses` uses raw string equality, allowing bypass of token-address self-send guard - (File: packages/intents-sdk/src/lib/compareAddresses.ts)

### Summary
`compareAddresses` for `Chains.BitcoinCash` compares addresses with plain `a === b`, while `validateAddress`/`validateBchAddress` accepts multiple equivalent textual encodings of the same BCH address (with/without `bitcoincash:` prefix, mixed case). An attacker can submit a `destinationAddress` that is a differently-encoded form of the bridged token's own `origin_chain_address`, bypassing the `DestinationAddressMatchesTokenAddressError` guard in `PoaBridge.validateWithdrawal` and causing funds to be withdrawn to the token contract address itself.

### Finding Description
The invariant that should hold is: for any destination `d` accepted by `validateAddress(d, BitcoinCash)` and any token address `t`, if `d` and `t` denote the same account, then `compareAddresses(t, d, BitcoinCash)` must be `true`. This invariant is broken because `validateBchCashAddr` (called from `validateAddress`) normalizes input by lowercasing it and adding the `bitcoincash:` prefix when absent before checksum verification, but `compareAddresses`'s `Chains.BitcoinCash` branch does no such normalization — it simply falls into the `a === b` case shared with Bitcoin, Dogecoin, Litecoin, etc., chains that don't have alternate encodings.

Exploit flow: the attacker calls `IntentsSDK.processWithdrawal`/`createWithdrawalIntents` for a BCH-routed PoA-bridge asset (e.g., `nep141:bch.omft.near`), supplying `destinationAddress` equal to the token's `origin_chain_address` but re-cased and/or with the `bitcoincash:` prefix added or removed relative to how it's stored in the PoA bridge's supported-tokens list. `validateAddress` accepts it as a valid BCH address. `compareAddresses(tokenInfo.origin_chain_address, args.destinationAddress, Chains.BitcoinCash)` returns `false` because the literal strings differ, so `DestinationAddressMatchesTokenAddressError` is never thrown. The withdrawal proceeds, and `createWithdrawIntentPrimitive` embeds the attacker-controlled destination string into the `WITHDRAW_TO:` memo passed to the bridge, resulting in tokens being withdrawn to the token's own contract address, which is presumably not designed to receive/forward such transfers, causing permanent loss.

### Impact Explanation
This causes funds delivered to a wrong (unrecoverable) destination — the bridged token's own contract address — matching the "Critical: funds delivered to a wrong address/chain/contract with no recovery" category. Any unprivileged NEAR Intents user withdrawing a BCH-routed asset through the PoA bridge can trigger this on every call, with the loss scoped to the withdrawn amount.

### Likelihood Explanation
Preconditions: the target asset must route through `PoaBridge` for `Chains.BitcoinCash`, and the token's `origin_chain_address` must be knowable (it's returned from the public `getSupportedTokens` API used for validation). The attacker needs only to re-encode a known, valid BCH address (e.g., toggle case or the `bitcoincash:` prefix) — no special privileges or timing required, and it's repeatable on any BCH PoA-bridge withdrawal.

### Recommendation
Add a CashAddr-aware normalization branch for `Chains.BitcoinCash` in `compareAddresses`, analogous to `validateBchCashAddr`'s normalization (lowercase, strip/normalize the `bitcoincash:` prefix, decode-and-compare the underlying payload bytes) instead of relying on raw string equality, so that all forms accepted by `validateAddress` are correctly recognized as equal.

function validateBchCashAddr(address: string): boolean {
	// Normalize the address
	let normalized = address.toLowerCase();

	// Add prefix if missing
	if (!normalized.includes(":")) {

import { base64urlnopad } from "@scure/base";

import { TON_ADDRESS_TAG_BOUNCEABLE_MAINNET, crc16ccitt } from "./ton-address";

function buildTonFriendlyAddress(
	workchainId: number,
	addressHex: string,
): string {
	const data = new Uint8Array(36);
	data[0] = TON_ADDRESS_TAG_BOUNCEABLE_MAINNET;
	data[1] = workchainId & 0xff;
	for (let i = 0; i < 32; i++) {
		data[2 + i] = Number.parseInt(addressHex.slice(i * 2, i * 2 + 2), 16);
	}
	const [hi, lo] = crc16ccitt(data.subarray(0, 34));
	data[34] = hi;
	data[35] = lo;
	return base64urlnopad.encode(data);
}
