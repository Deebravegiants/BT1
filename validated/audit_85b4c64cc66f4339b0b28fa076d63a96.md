### Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature exclusively over the raw request body, while the `shop` (tenant) identity is read from an HTTP header that is never part of the signed content. `ShopifyAPI::Webhooks::Registry.process` accepts any request whose body/HMAC pair validates and then trusts the header-derived `shop` value for tenant attribution, breaking the equality `shop authenticated by HMAC == shop used to route/attribute webhook data`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, however, is taken from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, which is not included anywhere in `to_signable_string`: [2](#0-1) 

`Registry.process` validates the HMAC over the body only, then immediately forwards the *unverified* header-derived `shop` to the app's handler as the authoritative tenant identity: [3](#0-2) 

Because webhook HMACs are computed with the app's `client_secret`, which is identical for every shop that has installed the app, an attacker who installs the app on a shop they control receives legitimately-HMAC-signed webhook deliveries. They can replay that same body/HMAC pair to the app's webhook endpoint while substituting the `shopify-shop-domain` header with a victim shop's domain. `Utils::HmacValidator.validate(request)` only checks the body against the HMAC, so it still passes, and the app's `WebhookHandler#handle` receives a `WebhookMetadata` claiming to be from the victim shop while carrying attacker-chosen body content, breaking the tenant binding.

### Impact Explanation
This is a cross-tenant identity confusion: any app built on this gem that uses `WebhookMetadata#shop` to key persistence, authorization, or cache lookups (the documented and intended usage of `Registry.process`/`WebhookHandler#handle`) can be made to process or store attacker-supplied data under an arbitrary victim shop's identity, satisfying the "Critical - cross-tenant access" category.

### Likelihood Explanation
Requires only that the attacker be able to install (or already have installed) the app on any shop they control — an unprivileged action available to any Shopify merchant — and the ability to send arbitrary HTTP requests to the app's public webhook endpoint with a modified header. No access token, `client_secret`, or privileged account of the victim is required.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `webhook-id`) header values in the signed content verified by `HmacValidator`, or otherwise cryptographically bind the shop identity to the payload before it is trusted by `Registry.process`/`WebhookHandler`.

### Proof of Concept
1. Attacker installs the app on their own store `attacker.myshopify.com`, receiving a legitimate webhook POST with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC(client_secret, B)`).
2. Attacker resends the same body `B` and same header `H` to the app's webhook endpoint, but replaces `X-Shopify-Shop-Domain: attacker.myshopify.com` with `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `Utils::HmacValidator.validate(request)` in `Registry.process` (`lib/shopify_api/webhooks/registry.rb` line 190) succeeds because it only checks `HMAC(client_secret, B) == H`.
4. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(... shop: request.shop ...))` with `shop == "victim.myshopify.com"`, even though the payload actually originated from the attacker's own shop.
