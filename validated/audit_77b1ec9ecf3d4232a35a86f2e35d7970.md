### Title
Unchecked ERC20 `transfer` return value in `IntentGatewayV2.placeOrder` predispatch sweep leads to escrow accounting that is not backed by actual token balance - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
In the Tron variant of `IntentGatewayV2.placeOrder`, the predispatch sweep (moving swapped tokens from the `CallDispatcher` back to the gateway) is executed as a raw, un-checked `IERC20.transfer` call routed through `CallDispatcher.dispatch`. `CallDispatcher` only checks that the low-level `.call` did not revert; it never decodes/validates the ERC20 boolean return value. `_orders[commitment][token]` is credited with `reducedInputs[i].amount` unconditionally, before this sweep call even runs, and there is no post-sweep balance verification (unlike the equivalent EVM mainline contract). If the escrowed input token returns `false` on failure instead of reverting, the gateway's internal escrow accounting becomes decoupled from its real token balance.

### Finding Description
`placeOrder` in `evm/tron/contracts/apps/IntentGatewayV2.sol` builds a sweep call using the raw selector instead of `SafeERC20.safeTransfer`: [1](#0-0) 

This call is dispatched through `CallDispatcher.dispatch`, which only checks the low-level call's `success` boolean and never inspects the ABI-encoded return data of the ERC20 call: [2](#0-1) 

For tokens that signal failure by returning `false` rather than reverting (e.g., legacy tokens such as `ZRX`), the `to.call{...}(data)` succeeds at the EVM level even though no tokens moved, so `CallDispatcher` does not revert.

Crucially, `_orders[commitment][token] += reducedInputs[i].amount;` is executed inside the same loop that builds the sweep call, *before* the sweep even executes, and there is no subsequent check that the gateway's actual token balance increased by the expected amount: [3](#0-2) 

This is in contrast to the parallel/mainline EVM contract, `evm/src/apps/IntentGatewayV2.sol`, which snapshots balances before the sweep and re-measures the actual amount received afterward, using the *measured* delta (not the requested amount) to update `order.inputs[i].amount` before it is used for escrow/commitment purposes: [4](#0-3) 

The tron contract lacks this balance-delta safety check entirely, so a silently-failing `transfer` call leaves `_orders[commitment][token]` crediting tokens the gateway never actually received.

### Impact Explanation
Escrow accounting (`_orders[commitment][token]`) can be inflated beyond the gateway's real token balance for that token. When settlement/withdrawal is later triggered (via `RedeemEscrow`/`RefundEscrow` in `onAccept` calling `_withdraw`), the contract attempts `IERC20(token).safeTransfer(beneficiary, amount)` against a balance the gateway never actually holds: [5](#0-4) 

Because the same token balance is shared across all orders escrowed in that token, this can cause a legitimate, unrelated depositor's later withdrawal to permanently revert (their escrow ledger entry is now unbacked by real tokens held by the contract), effectively freezing their funds, or allow whichever withdrawal races first to drain the deficient pool at the expense of others.

### Likelihood Explanation
This requires the order's `predispatch.assets` to include a token that returns `false` on failed transfer instead of reverting, and the predispatch call to leave a real (or manipulated) shortfall. Since `placeOrder` is a completely unprivileged, user-submitted transaction and predispatch behavior/tokens are user-supplied within `order.predispatch`, this is directly reachable by any user placing an order with a legacy-style ERC20 as an input asset.

### Recommendation
Use `SafeERC20.safeTransfer`/`safeTransferFrom` (as already done elsewhere in this codebase, e.g. `IntentsBase._withdraw`, `HyperFungibleToken`, `EvmHost`) for the sweep call instead of raw `abi.encodeWithSelector(IERC20.transfer.selector, ...)`, and/or add the same pre/post balance snapshot-and-measure pattern used in `evm/src/apps/IntentGatewayV2.sol` so that `_orders[commitment][token]` is only credited with the amount actually received by the gateway.

### Proof of Concept
1. Deploy `IntentGatewayV2` (tron variant) with a predispatch-capable order where one `order.inputs[i].token` is a token contract whose `transfer` returns `false` on failure (no revert) — e.g., under some condition the token's transfer silently fails once the `CallDispatcher`'s balance is insufficient or blacklisted.
2. Call `placeOrder` with `predispatch.call` and `predispatch.assets` set so that after the predispatch call, `CallDispatcher`'s balance of the token is (through token-specific behavior) not fully transferable back (transfer silently returns `false`).
3. `CallDispatcher.dispatch` sees `success == true` for the low-level call (since the token doesn't revert) and does not revert the batch.
4. `_orders[commitment][token]` has already been incremented by `reducedInputs[i].amount`, even though the gateway's real balance of `token` did not increase by that amount.
5. When `onAccept` later calls `_withdraw` for this commitment, `IERC20(token).safeTransfer(beneficiary, amount)` reverts (insufficient balance) or succeeds by draining balance escrowed for a different order, demonstrating the escrow ledger is decoupled from actual custody.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
