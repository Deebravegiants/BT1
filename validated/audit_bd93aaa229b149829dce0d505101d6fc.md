## Finding

Confirmed: `TokenExchange.exchange_token` in `lib/shopify_api/auth/token_exchange.rb` derives `dest_shop` from the unvalidated JWT `dest` claim and uses it directly as the request host, unlike its sibling methods.

### Title
SSRF / host binding bypass in `TokenExchange.exchange_token` via unsanitized JWT `dest` claim used as request host - (File: lib/shopify_api/auth/token_exchange.rb)

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` takes the `shop` value directly from the session token's `dest` claim (`jwt_payload.shop`, i.e. `JwtPayload#dest` with `"https://"` stripped) and uses it, unsanitized, as the hostname for the outbound `POST /admin/oauth/access_token` request that carries the app's `client_id`/`client_secret`. Every other method in the same file (`migrate_to_expiring_token`) and in sibling auth modules (`ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`) explicitly calls `Utils::ShopValidator.sanitize!(shop)` before building the session/host used for the credentialed request. `exchange_token` breaks this pattern.

### Finding Description
The binding that should hold is: **shop host used to route the client_secret-bearing HTTP request == a value validated against `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`**.

In `lib/shopify_api/auth/token_exchange.rb:40-41`:
```ruby
jwt_payload = ShopifyAPI::Auth::JwtPayload.new(session_token)
dest_shop = jwt_payload.shop
```
`JwtPayload#shop` (`lib/shopify_api/auth/jwt_payload.rb:47-51`) is simply `@dest.gsub("https://", "")` — no domain allow-list check, no call to `ShopValidator`. `JwtPayload#initialize` only checks `aud == Context.api_key` [1](#0-0) , and it does not validate that `iss`/`dest` belongs to a Shopify-owned domain.

This `dest_shop` is then used unsanitized to build the target host of the token-exchange request:
```ruby
shop_session = ShopifyAPI::Auth::Session.new(shop: dest_shop)
...
client = Clients::HttpClient.new(session: shop_session, base_path: "/admin/oauth")
``` [2](#0-1) 

`Clients::HttpClient#initialize` builds the request base URI directly from `session.shop`: `@base_uri = "https://#{api_host || session.shop}"` [3](#0-2) . The subsequent `client.request(...)` POSTs a body containing `client_id` and `client_secret` (the app's confidential OAuth credentials) to that host [4](#0-3) .

Compare with the sibling method in the same file, `migrate_to_expiring_token`, which validates the shop before use:
```ruby
validated_shop = Utils::ShopValidator.sanitize!(shop)
shop_session = ShopifyAPI::Auth::Session.new(shop: validated_shop)
``` [5](#0-4) 

And `ClientCredentials.client_credentials` / `RefreshToken.refresh_access_token`, which do the same: [6](#0-5) [7](#0-6) 

`ShopValidator.sanitize!` exists precisely to constrain `shop` values to `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`, plus configured `myshopify_domain`) [8](#0-7) , and raises `Errors::InvalidShopError` otherwise [9](#0-8) . `exchange_token` is the one code path in the OAuth/token-exchange family that omits this check before using the shop value as an outbound request host, exactly mirroring the "host validated versus the host that receives the ... `client_secret`" analog called out in the rules.

Whether this claim is reachable by an unprivileged internet user depends on how the host application obtains `session_token`. Per this gem's documented flow (`docs/getting_started.md`, `docs/usage/oauth.md`), the session token is meant to come from Shopify's App Bridge (`Authorization` header/`id_token`), signed with the shared `api_secret_key`. Under that intended usage, `dest` is Shopify-controlled and this is not exploitable by an outsider without the secret — this mirrors the general pattern in this codebase (HMAC/JWT-signed fields are otherwise trustworthy). However, because `JwtPayload` does not itself constrain `dest` to a Shopify domain (it is trusted purely because of the HS256 signature, not because of an allow-list), and because `exchange_token` skips the allow-list check that every sibling method performs, the code is structurally inconsistent and one defense-in-depth layer weaker than the rest of the module. If the host application's `session_token` acquisition path is ever looser than the documented App Bridge flow (e.g., accepting a session token forwarded from a different, less-trusted source, or a future JWT algorithm/key-handling change), this omission removes the last line of defense against directing app-secret-bearing requests to an attacker-chosen host.

### Impact Explanation
If reachable, impact is High: SSRF carrying the app's `client_id`/`client_secret` to an attacker-chosen host, which is explicit in-scope impact per the rules. This is the same class of risk `ShopValidator.sanitize!` is designed to prevent, and the inconsistency (present everywhere else, absent here) is the exact "interface/consistency" defect pattern flagged by the external report, translated into this Ruby gem's authentication code.

### Likelihood Explanation
Low-to-moderate on its own, because under the gem's documented usage the JWT is HS256-signed with the shared `api_secret_key`, which an unprivileged attacker does not possess, so they cannot mint an arbitrary `dest`. This finding is reported as a defense-in-depth / consistency gap rather than a demonstrated end-to-end bypass reachable purely from the internet without any credential — I was not able to find a path in this gem's own code that lets an unprivileged, uncredentialed caller supply an arbitrary `session_token` whose `dest` is not already constrained by the shared secret. That is an acknowledged limitation of this analysis given ask-only, static review.

### Recommendation
Apply the same `Utils::ShopValidator.sanitize!` check to `dest_shop` in `TokenExchange.exchange_token` before constructing `shop_session`/`Clients::HttpClient`, matching `migrate_to_expiring_token`, `ClientCredentials.client_credentials`, and `RefreshToken.refresh_access_token`. Additionally, consider having `JwtPayload#shop`/`#dest` itself validate against `ShopValidator::TRUSTED_SHOPIFY_DOMAINS` so all consumers of the JWT payload get this protection automatically rather than relying on each call site to remember to sanitize.

### Proof of Concept
Not independently demonstrable as a full exploit within this gem alone: constructing a `session_token` with an attacker-chosen `dest` requires either (a) knowledge of `api_secret_key`/`old_api_secret_key` (out of scope per the rules) to sign a valid HS256 JWT with `aud == Context.api_key`, or (b) a host application that forwards an unauthenticated/attacker-supplied token into `exchange_token`. Given (a) is excluded by scope and (b) depends on host-application behavior (also excluded per the rules), I cannot construct a concrete unprivileged-attacker PoC confined to this gem's own code. This is reported as a structural/consistency defect (the interface-inconsistency analog requested) rather than a proven bypass.
