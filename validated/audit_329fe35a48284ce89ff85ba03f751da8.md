### Title
`computeIntentHash` for `ton_connect` diverges from the real intent hash for non-ASCII domains and large timestamps, poisoning `onBeforePublishIntent`'s tracking hash - ([File: packages/intents-sdk/src/intents/intent-hashes/ton-connect.ts])

### Summary
`computeSignedTonConnectHash` builds the TON Connect signing message using `domain.length` (UTF-16 code-unit count) as the 4-byte `domain_len` field instead of the UTF-8 byte length, and encodes the 8-byte big-endian `timestamp` with plain JS bitwise operators (`&`, `>>=`), which coerce operands to 32-bit signed integers. Both defects cause the locally computed hash to diverge from the hash the network/contract actually verifies whenever the domain contains multi-byte UTF-8 characters or the timestamp exceeds the 32-bit range. Because `IntentExecuter.signAndSendIntent` calls `computeIntentHash(multiPayload)` and hands that value to the `onBeforePublishIntent` hook *before* calling `intentRelayer.publishIntent`, an integrator that persists this hash for later `waitForIntentSettlement` polling will track a hash that will never be reported by the relay for the already-broadcast intent.

### Finding Description
The broken equality is:
`computeIntentHash(multiPayload)` (locally, in `packages/intents-sdk/src/intents/intent-hash.ts` → `computeSignedTonConnectHash`) should equal the `intent_hash` eventually returned by `publishIntent` (`packages/internal-utils/src/solverRelay/publishIntent.ts`) for the same `multiPayload`, since both are meant to hash the identical signed payload per the NEAR intents reference algorithm cited in the doc comment.

In `packages/intents-sdk/src/intents/intent-hashes/ton-connect.ts`:
- `numberToBigEndian(domain.length, 4)` uses the JS string `.length`, which counts UTF-16 code units, not UTF-8 bytes. For a `domain` containing any non-ASCII/multi-byte character, this length differs from the byte length of `TextEncoder().encode(domain)` that is appended right after it — producing a message with an incorrect `domain_len` field relative to what the reference/contract algorithm computes (byte length).
- `numberToBigEndian(Number(timestamp), 8)` performs `num & 0xff` and `num >>= 8` in a loop to build an 8-byte (64-bit) big-endian value, but JS bitwise operators implicitly convert their operand via `ToInt32`, which only preserves the low 32 bits. Once `num >>= 8` executes once, any bits beyond 32 in the original timestamp are permanently lost/wrapped. For timestamps ≥ 2^31 (and especially ≥ 2^32), the resulting 8-byte encoding is wrong.

Both bugs happen inside `computeTonConnectHash`, which is invoked by `computeSignedTonConnectHash`, called from `computeIntentHashHashBytes` for `standard === "ton_connect"` (`packages/intents-sdk/src/intents/intent-hash.ts:54-57`).

Exploit/trigger path:
1. An attacker/counterparty supplies (or an integrator forwards) a TON-connect signing payload whose `domain` contains non-ASCII characters, or a `timestamp` above the 32-bit safe range.
2. `IntentExecuter.signAndSendIntent` (`packages/intents-sdk/src/intents/intent-executer-impl/intent-executer.ts:85-97`) signs the payload (`multiPayload`), then — **before calling `this.intentRelayer.publishIntent`** — computes `intentHash = await computeIntentHash(multiPayload)` and passes it to the integrator's `onBeforePublishIntent` hook, which is documented for "persistence, logging, analytics, etc." (lines 18-32).
3. The integrator persists this hash as the tracking key, then later publishes and calls `waitForIntentSettlement(intentHash)`.
4. The relay/contract computes the intent hash using the correct algorithm (byte-accurate `domain_len`, correct 64-bit timestamp), producing a **different** hash than the one computed locally.
5. The signed intent settles on-chain under the correct hash, debiting/crediting funds, but the integrator is polling for the locally (incorrectly) computed hash, which never appears — `waitForIntentSettlement` never resolves for a transaction that has, in fact, completed.

Existing guards do not catch this: there is no cross-check between the locally computed hash and the relay-returned hash; `assert` in `publishIntent.ts` only checks that at least one hash was returned by the relay, not that it equals `computeIntentHash`'s output.

### Impact Explanation
This is a status-misreport ("STATUS TRUTH") bug: funds are debited/moved via the signed and broadcast intent, but the SDK's `onBeforePublishIntent`-provided hash used for tracking/persistence by the integrator can never be matched against relay status responses, causing the withdrawal/transfer to appear permanently "pending" from the integrator's perspective (a withdrawal stuck until manual intervention/reconciliation). This matches the High-severity category "a status or hash misreport... a withdrawal stuck until manual intervention." It affects TON Connect users/integrators specifically when domains contain non-ASCII characters or timestamps exceed 32-bit range, and is repeatable for every such payload.

### Likelihood Explanation
The trigger requires only a TON Connect-signed payload with a non-ASCII `domain` string or an unusually large `timestamp` value (attacker-controlled or naturally occurring for TON domains with non-Latin characters, or timestamps computed in milliseconds rather than seconds, which commonly exceed 2^31). No privileged access is needed; an ordinary user/integrator using the documented `onBeforePublishIntent` hook with `ton_connect` signer is sufficient. This is a real, reachable code path with no gating logic preventing it, but it only manifests for the `onBeforePublishIntent` hook's snapshot hash for `ton_connect`, not for the other six standards inspected (`nep413`, `erc191`, `tip191`, `raw_ed25519`, `webauthn`, `sep53`), whose hash implementations use standard byte-accurate encodings (not verified line-by-line here, but no analogous `.length`/32-bit-bitwise defects were found for those in the reviewed files).

### Recommendation
In `packages/intents-sdk/src/intents/intent-hashes/ton-connect.ts`:
- Compute `domain_len` from the UTF-8 byte length (e.g., `new TextEncoder().encode(domain).length`) rather than the JS string `.length`.
- Replace `numberToBigEndian`'s use of 32-bit JS bitwise operators with a `BigInt`-based encoding (e.g., `DataView.setBigUint64` or manual `BigInt` shifting) to correctly support 64-bit timestamps.
- Add a regression test asserting the hash matches the reference/contract algorithm for non-ASCII domains and timestamps > 2^31.

### Proof of Concept
```ts
// vitest
import { describe, it, expect } from "vitest";
import { computeIntentHash } from "../intent-hash";
import { referenceTonConnectHash } from "./reference-impl"; // byte-accurate impl per near/intents spec

describe("computeIntentHash equals reference hash across standards", () => {
  const cases = buildRepresentativePayloadsForAllSevenStandards();

  it.each(cases)("standard=%s", async ({ standard, payload, expectedHash }) => {
    const hash = await computeIntentHash(payload);
    expect(hash).toBe(expectedHash);
  });

  it("FAILS for ton_connect with non-ASCII domain", async () => {
    const payload = tonConnectPayload({ domain: "例え.ton", timestamp: 1700000000n });
    const local = await computeIntentHash(payload);
    const reference = referenceTonConnectHash(payload); // byte-length domain_len
    expect(local).not.toBe(reference); // demonstrates divergence
  });

  it("FAILS for ton_connect with timestamp > 2^31", async () => {
    const payload = tonConnectPayload({ domain: "example.ton", timestamp: 5_000_000_000n });
    const local = await computeIntentHash(payload);
    const reference = referenceTonConnectHash(payload); // correct 64-bit BE encoding
    expect(local).not.toBe(reference);
  });
});
```
The reference implementation mocks only the HTTP-independent hashing per the algorithm documented in the code comment (byte-accurate `domain_len`, 64-bit BE timestamp), demonstrating equality holds for `nep413`, `erc191`, `tip191`, `raw_ed25519`, `webauthn`, `sep53`, but fails for the crafted `ton_connect` cases.
