Confirmed: for OAuth's `AuthQuery`, `shop` is explicitly included in `to_signable_string` (`lib/shopify_api/auth/oauth/auth_query.rb:34-43`), so the OAuth path binds shop identity to the HMAC. In contrast, the webhook path does not.

### Title
Webhook shop-domain identity not covered by HMAC signature allows cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from unauthenticated HTTP headers. `Registry.process` validates the HMAC over the body only, then trusts the header-derived `shop` value to build `WebhookMetadata` passed to the app's handler. Since the HMAC secret (`client_secret`) is shared across all shops of the same app, any holder of one valid `(body, hmac)` pair from any of the app's shops can replay it with a different `shopify-shop-domain` header and have it validated as if it came from that other shop.

### Finding Description
`HmacValidator.validate` computes the signature only over `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` is defined to return only `@raw_body`: [2](#0-1) 

But `shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from HTTP headers with no cryptographic binding to the signed body: [3](#0-2) 

`Registry.process` validates only the HMAC (over the body) and then forwards the header-derived `shop` (and other header fields) straight into `WebhookMetadata`, which the host application's handler uses to attribute the event to a tenant: [4](#0-3) [5](#0-4) 

By contrast, the OAuth callback path (`AuthQuery`) explicitly includes `shop` inside the signed string, so shop identity is bound to the signature there: [6](#0-5) 

This is the exact bug class described in the analog report: a field (`mapMemberSynth_lastTime`'s target member in the original; here, the tenant-identifying `shop` field) is acted upon by security-sensitive logic but is not covered by the authentication mechanism (there, no access control on `depositForMember`; here, no HMAC coverage of `shop`). The broken identity equality is:

`shop that produced/owns the signed raw_body` **≠** `shop-domain header trusted by Registry.process to route/attribute the webhook`

Because the app's `client_secret` (and therefore the webhook signing key) is identical for every shop that has installed the same app, a valid `(raw_body, hmac)` pair captured from any one tenant (e.g., the attacker's own store, where the attacker is a legitimate merchant/app installer and thus has full read access to their own webhook deliveries) remains cryptographically valid under `HmacValidator.validate` even when replayed with a forged `shopify-shop-domain` (or `x-shopify-shop-domain`) header pointing at a different tenant of the same app.

### Impact Explanation
This crosses a tenant boundary without needing the app's `client_secret`, an access token, or any privileged credential — only a legitimately-received webhook delivery for the attacker's own shop (something any merchant/app installer can obtain trivially). The attacker can cause the host application to process order/customer/inventory/etc. webhook data while believing it originates from `shopA.myshopify.com` when it actually pertains to (or is falsely attributed to) `shopB.myshopify.com`, or conversely make legitimate data for their own shop appear to originate from a victim shop. Depending on how the host app keys its per-tenant session/store lookup off `WebhookMetadata#shop`, this can lead to cross-tenant data corruption, incorrect authorization decisions, or data leakage between merchants of the same app — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Any merchant who installs the app receives real webhook deliveries and thus obtains valid `(body, hmac)` pairs signed with the app's shared `client_secret`. Replaying such a request against the app's public webhook endpoint with a modified `shop-domain` header requires no special access — it is a straightforward HTTP replay/header-tamper attack reachable by any unprivileged internet user who is (or has been) a merchant using the target app.

### Recommendation
Include the shop identity (and ideally topic/webhook_id) inside the HMAC-signed material, or alternatively verify that the `shop` header value matches an expected/known tenant record (e.g., a shop this app currently has an active, verified installation/session for) before trusting it, rather than deriving tenant identity solely from an unauthenticated header. At minimum, `Webhooks::Request#to_signable_string` should incorporate the `shop-domain` header so that the HMAC binds body-to-shop, preventing cross-tenant replay.

### Proof of Concept
1. Attacker installs the target Shopify app on their own shop `attacker-shop.myshopify.com` and receives a legitimate webhook, e.g. `orders/create`, with body `B` and header `x-shopify-hmac-sha256: H` (valid for secret `S`, the app's shared `client_secret`).
2. Attacker resends this exact request to the app's public webhook endpoint, keeping body `B` and header `x-shopify-hmac-sha256: H` unchanged, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `request.to_signable_string` (`== B`) using the same shared secret `S` — validation succeeds because `shop` is not part of the signed data: [7](#0-6) 
4. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and body `B`, causing the host application to process/attribute attacker-controlled or mismatched data under the victim tenant's identity.
