### Title
`Webhooks::Registry.process` dispatches on and trusts `topic`/`shop` headers that are never covered by the webhook HMAC - ([File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates only that the raw request body was HMAC-signed with the app's secret, then uses `request.topic` and `request.shop` — both read from unsigned HTTP headers — to select the handler and to build the `WebhookMetadata` passed to it. An attacker who can obtain any one validly-signed webhook body (trivially available by installing the app on their own development shop and receiving a genuine webhook) can replay that exact body directly to the app's public webhook endpoint with forged `X-Shopify-Topic` / `X-Shopify-Shop-Domain` headers, and the signature check still passes.

### Finding Description
The broken binding: the code implicitly assumes `HMAC_valid(raw_body) == authentic(topic, shop, webhook_id, api_version)`, but in fact `VerifiableQuery#to_signable_string` for `Webhooks::Request` returns only `@raw_body`: [1](#0-0) 

while `topic`, `shop`, `api_version`, and `webhook_id` are pulled straight from attacker-controlled, unsigned headers with no cryptographic binding to the signed body: [2](#0-1) 

`Registry.process` validates the HMAC over that body-only signable string via `HmacValidator.validate`, then immediately uses the unsigned `request.topic` to select the handler from `@registry` and passes the unsigned `request.shop` into `WebhookMetadata`, which the handler treats as authenticated identity of the sending shop/topic: [3](#0-2) 

`HmacValidator.validate` and `validate_signature` only ever hash `verifiable_query.to_signable_string` (i.e., the raw body for webhooks) against `Context.api_secret_key`; they never see or check `topic`/`shop`/`webhook_id`/`api_version`: [4](#0-3) 

Because the same `api_secret_key` is shared across every shop and every topic for a given app, and the webhook endpoint is a plain public HTTP route that directly forwards to `Registry.process`, an attacker can:
1. Install the app on their own development shop (allowed per rules) and trigger any webhook delivery, capturing the raw body and its valid `X-Shopify-Hmac-Sha256` value.
2. POST that exact raw body straight to the app's public webhook endpoint, replacing `X-Shopify-Topic` with a different registered topic (e.g. a mandatory `shop/redact`/`customers/data_request` handler, or any other sensitive handler) and/or replacing `X-Shopify-Shop-Domain` with an arbitrary (including victim) shop domain.
3. `HmacValidator.validate` still returns `true` because it only checks the raw body, so `process` dispatches the forged topic's handler with the wrong-schema body, and/or attributes the payload to a shop the data never came from.

None of the existing guards catch this: `HmacValidator.validate` checks only body/secret; there is no `ShopValidator.sanitize!`-style check on `request.shop`; there is no per-topic or per-shop signing; Sorbet typing only enforces that `topic`/`shop` are `String`, not that they match anything the signature covers.

### Impact Explanation
This breaks the security guarantee that a passing HMAC check means "this exact (topic, shop, body) triple came from Shopify for this app." Concretely:
- **Topic confusion**: an attacker-controlled, validly-signed body for one topic can trigger the handler registered for an entirely different topic, including sensitive/mandatory handlers (`shop/redact`, `customers/redact`, `customers/data_request`), with a body whose shape/semantics the handler never expects.
- **Shop/tenant confusion**: `WebhookMetadata#shop` is forgeable, so any handler logic that trusts `data.shop` to identify which merchant's session/access token to load or which tenant's records to mutate can be tricked into acting under a victim shop's identity using attacker-supplied body content — a cross-tenant data-integrity issue.

This matches the Critical class "a forged...request is accepted as authentic" in the sense that the (topic, shop) attribution of an otherwise-signed request is unauthenticated and attacker-controlled, and is repeatable against arbitrary registered topics/shops per request.

### Likelihood Explanation
Preconditions are modest and within the unprivileged attacker's stated capabilities: they need only (a) install the target app on their own shop or otherwise obtain one genuinely signed webhook body/HMAC pair, and (b) know the app's public webhook URL (typically documented/discoverable, and shared across all topics for `Registrations::Http`). No secret key, session, or victim credential is needed. The attack is a simple direct HTTP POST with modified headers and a reused body, fully repeatable against any topic the app has registered and any shop-domain value the app trusts from the header.

### Recommendation
Bind the security-relevant routing fields into the signed content, or otherwise validate them out-of-band before dispatch:
- Include `topic`, `shop-domain`, and (if used) `webhook-id`/`api-version` in the signable string used for HMAC validation (this requires deviating from/extending Shopify's raw-body-only HMAC spec, e.g., by additionally verifying the shop domain against the session/shop known for the given topic subscription, or maintaining a per-shop-and-topic expected mapping validated after HMAC success).
- At minimum, in `Registry.process`, cross-check `request.shop` against an authenticated source of truth (e.g., the shop associated with the currently active session/webhook subscription) before invoking the handler, rather than trusting the header value outright.
- Document clearly to app developers that `topic` and `shop` on `WebhookMetadata` are unauthenticated and must not be used as sole tenant/topic identifiers without additional verification.

### Proof of Concept
```ruby
# test/webhooks/registry_topic_spoof_test.rb
def test_dispatch_follows_unsigned_topic_header_not_signature
  ShopifyAPI::Webhooks::Registry.clear

  called_with_topic = nil
  handler_a = TestHelpers::FakeWebhookHandler.new(->(data) { called_with_topic = data.topic })
  handler_b = TestHelpers::FakeWebhookHandler.new(->(data) { called_with_topic = data.topic })

  ShopifyAPI::Webhooks::Registry.add_registration(
    topic: "orders/create", path: "p", delivery_method: :http, handler: handler_a,
  )
  ShopifyAPI::Webhooks::Registry.add_registration(
    topic: "shop/redact", path: "p", delivery_method: :http, handler: handler_b,
  )

  raw_body = '{"attacker":"controlled"}'
  hmac = Base64.encode64(
    OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body),
  )

  # Attacker captured this signed body for "orders/create" from their own shop,
  # then replays it claiming a different, sensitive topic.
  forged_headers = {
    "x-shopify-topic" => "shop/redact",
    "x-shopify-hmac-sha256" => hmac,
    "x-shopify-shop-domain" => "victim-shop.myshopify.com",
  }

  request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

  # Assertion: HMAC still validates (signature covers body only)
  assert(ShopifyAPI::Utils::HmacValidator.validate(request))

  # Assertion: dispatch follows the unsigned header, invoking the "shop/redact" handler
  # with a body that was never actually signed/intended for that topic or shop.
  ShopifyAPI::Webhooks::Registry.process(request)
  assert_equal("shop/redact", called_with_topic)
end
```
This demonstrates that `HmacValidator.validate` (bound only to `to_signable_string` == raw body) and `Registry.process`'s handler/shop selection are decoupled, confirming the signature-coverage invariant is violated.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
