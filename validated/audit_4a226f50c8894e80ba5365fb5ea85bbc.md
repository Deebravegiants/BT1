Audit Report

## Title
Missing `return` after failed email-claim extraction lets an OIDC login succeed and create a session with an empty/invalid user identity - (File: `core/sessions/oidcauth/oidc.go`)

## Summary
In `handleTokenExchange`, when the type assertion `claims["email"].(string)` fails, the handler logs an error and writes a `500` response via `c.String(...)` but does not `return`, unlike every other error branch in the function. Execution falls through, computes the RBAC `role` from group claims, inserts a row into `oidc_sessions` with `user_email = ''`, sets the session cookie, and returns `ExchangeTokenResponse{Success: true}` with HTTP 200.

## Finding Description
All sibling failure branches in `handleTokenExchange` (bad JSON, state mismatch, token exchange failure, missing `id_token`, ID token verification failure, claims parsing failure, `ExtractIDClaimValues` failure, role mapping failure) call `return` right after writing the error response. The email extraction branch is the sole exception: [1](#0-0) 
Because `c.String` does not abort Gin's handler execution, the code proceeds to derive `role` from `idClaims` (independent of the email extraction outcome), insert the session row keyed by the empty `email`, set the session cookie, and respond with success: [2](#0-1) 
Downstream, `AuthorizedUserWithSession` trusts whatever `user_email`/`user_role` was persisted in `oidc_sessions` without any secondary validation against a `users` table record: [3](#0-2) 
This matches the described "anyone-can-pay" pattern: a gating check (successful email extraction) fails, but the code that should be conditioned on that check (session persistence and cookie issuance) executes unconditionally anyway.

## Impact Explanation
An unprivileged client that completes the OAuth2 authorization-code exchange and whose ID token satisfies one of the configured group-claim mappings (`AdminClaim`/`EditClaim`/`RunClaim`/`ReadClaim`) but lacks a usable `email` claim still receives a valid, cookie-backed session with a role attached, and the client-visible response falsely reports `Success: true`. Since `AuthorizedUserWithSession` performs no secondary check tying the session back to a legitimate user record, this session is fully usable against authenticated node API/GraphQL endpoints — a concrete node authentication/role-bypass impact in the internet-facing OIDC callback endpoint, in scope per Chainlink's node API authentication bypass category.

## Likelihood Explanation
Triggering this requires only completing a normal OIDC authorization-code exchange against the configured identity provider with an ID token that satisfies a configured group-claim mapping while omitting or malforming the `email` claim. No privileged/operator/host access, malicious node/peer, or network-layer manipulation is required — this is reachable by any client able to complete the standard sign-in flow, which is explicitly within the session/token handling attack surface in scope.

## Recommendation
Add `return` immediately after `c.String(http.StatusInternalServerError, "Failed to get email from claims")` in `handleTokenExchange`, mirroring every other error branch in the function. Additionally validate that `email` is non-empty before executing the `INSERT INTO oidc_sessions` statement, and add a regression test asserting that a token exchange whose ID token lacks a valid `email` claim never yields `Success: true` nor a persisted `oidc_sessions` row.

## Proof of Concept
1. Configure/control an OIDC identity provider so the issued ID token contains group claims matching a configured `AdminClaim`/`EditClaim`/`RunClaim`/`ReadClaim` value but omits (or wrongly types) the `email` claim.
2. Complete the standard `/sessions/oidc` sign-in redirect flow and POST the resulting `code`/`state` to the token-exchange endpoint served by `handleTokenExchange`.
3. Observe the response contains the `500` body text "Failed to get email from claims" is never actually surfaced as the final response — instead the handler continues and returns HTTP 200 with `ExchangeTokenResponse{Success: true}`, and a row is inserted into `oidc_sessions` with `user_email = ''` and the derived role.
4. Use the returned session cookie against an authenticated endpoint (e.g., a GraphQL mutation gated by role checks) and confirm the request succeeds via `AuthorizedUserWithSession`, which trusts the `oidc_sessions` row without cross-referencing a legitimate `users` record.

// AuthorizedUserWithSession will return the API user associated with the Session ID if it
// exists and hasn't expired
func (oi *oidcAuthenticator) AuthorizedUserWithSession(ctx context.Context, sessionID string) (clsessions.User, error) {
	if len(sessionID) == 0 {
		return clsessions.User{}, errors.New("session ID cannot be empty")
	}
	var foundUser clsessions.User
	err := sqlutil.TransactDataSource(ctx, oi.ds, nil, func(tx sqlutil.DataSource) error {
		// Query the oidc_sessions table for given session ID, user role and email are saved after the id claims is provided and validated
		var foundSession struct {
			UserEmail string
			UserRole  clsessions.UserRole
			Valid     bool
		}
		if err := tx.GetContext(ctx, &foundSession,
			"SELECT user_email, user_role, created_at + $2 >= now() as valid FROM oidc_sessions WHERE id = $1",
			sessionID, oi.config.SessionTimeout().Duration(),
		); err != nil {
			if errors.Is(err, sql.ErrNoRows) {
				return clsessions.ErrUserSessionExpired
			}
			return err
		}
		if !foundSession.Valid {
			// Sessions expired, purge
			return clsessions.ErrUserSessionExpired
		}
		foundUser = clsessions.User{
			Email: foundSession.UserEmail,
			Role:  foundSession.UserRole,
		}
		return nil
	})
	if err != nil {
		if errors.Is(err, clsessions.ErrUserSessionExpired) {
			if _, execErr := oi.ds.ExecContext(ctx, "DELETE FROM oidc_sessions WHERE id = $1", sessionID); execErr != nil {
				oi.lggr.Errorf("error purging stale OIDC session: %v", execErr)
			}
		}
		return clsessions.User{}, err
	}
	return foundUser, nil
}
