Audit Report

## Title
JWT replay-protection check-then-act race in `WorkflowMetadataHandler.Authorize` allows single JWT to authorize multiple concurrent workflow executions - (File: `core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go`)

## Summary
`WorkflowMetadataHandler.Authorize` implements JWT single-use ("replay") protection by first checking `isReplay(claims.ID)` under an `RLock`, then performing several unrelated steps (workflow lookup, signer/key comparison), and only afterward calling `recordUsage(claims.ID)` under a separate `Lock`. Because the check and the write are not atomic and are separated by intervening logic, two concurrent requests carrying the same signed JWT can both pass the replay check before either records usage, defeating the intended single-use guarantee.

## Finding Description
`Authorize` is reached from an unprivileged external caller's `workflows.execute` HTTP trigger via `HandleUserTriggerRequest` → `authorizeRequest`: [1](#0-0) 

Inside `Authorize`, the read (`isReplay`) happens immediately after JWT verification, but the write (`recordUsage`) only occurs after the `authorizedKeys` map lookup and signer-comparison steps complete: [2](#0-1) 

`isReplay` and `recordUsage` use independent locks (`RLock`/`RUnlock` vs. separate `Lock`/`Unlock`) rather than a single atomic check-and-set operation: [3](#0-2) 

This is a genuine check-then-act (TOCTOU) race: two goroutines processing concurrent requests carrying the same JWT `jti` can both execute `isReplay` and observe "not yet used" before either executes `recordUsage`. No existing lock spans both operations, and no other code path (e.g., `setupCallback`'s `requestID`-uniqueness check in `http_trigger_handler.go`) prevents this, since `setupCallback` dedupes on the caller-supplied `requestID`, which is independent of the JWT's `jti` — a caller can supply distinct `requestID`s while reusing the same JWT.

## Impact Explanation
This defeats the single-use guarantee of the JWT-signed HTTP trigger authorization mechanism, allowing a caller in possession of one valid JWT to have it accepted by `Authorize` more than once under concurrency, resulting in duplicate/unauthorized workflow executions from a single authorization token. This falls under the in-scope "unauthorized job run" / "gateway request impersonation of the anti-replay control" impact category, since it lets a request bypass an intended one-time-use security control on the gateway's trigger endpoint.

## Likelihood Explanation
The exploit requires only that the caller possess one valid, previously-unused JWT and send it in two or more concurrent `workflows.execute` requests to the gateway — no elevated privileges are needed beyond what is already required to call the endpoint normally. The race window (map lookup for `authorizedKeys`, key comparison) is small but real and consists of genuine in-memory work executed between the check and the write, so the race is plausible, especially under realistic concurrent/duplicate client behavior.

## Recommendation
Make the JTI check-and-record atomic by combining `isReplay` and `recordUsage` into a single `checkAndRecord(jti) bool` method that holds one `Lock` across both the existence check and the insertion, and invoke this combined operation immediately after JWT verification, before any other authorization logic (workflow/key lookups) executes.

## Proof of Concept
1. Generate one valid, signed JWT (`jti` fixed) authorized for a given `workflowID`.
2. Issue two concurrent `workflows.execute` HTTP trigger requests to the gateway with distinct `requestID`s but the same JWT in `req.Auth`.
3. In `Authorize`, both goroutines call `h.jwtCache.isReplay(claims.ID)` before either calls `h.jwtCache.recordUsage(claims.ID)`, since the two operations use independent locks with intervening unrelated work (`authorizedKeys` lookup, signer comparison).
4. Both requests pass the "JWT already used" check and get authorized, each triggering a separate workflow execution from the single JWT — demonstrated via a Go unit test that calls `Authorize` concurrently from two goroutines with the same `jti` and asserts both return `nil` error.

```go
func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
}
```

```go
func (cache *jwtReplayCache) isReplay(jti string) bool {
	cache.mu.RLock()
	defer cache.mu.RUnlock()

	_, exists := cache.cache[jti]
	return exists
}

func (cache *jwtReplayCache) recordUsage(jti string) {
	cache.mu.Lock()
	defer cache.mu.Unlock()

	cache.cache[jti] = time.Now()
}
```
