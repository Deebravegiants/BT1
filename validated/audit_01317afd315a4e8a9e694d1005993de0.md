## Title
USDC/USDT blocklist can permanently freeze escrowed intent funds during `RedeemEscrow`/`RefundEscrow` settlement - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentsBase._withdraw()` pushes escrowed ERC-20 tokens directly to a beneficiary address using `safeTransfer` while processing a Hyperbridge-delivered `RedeemEscrow` or `RefundEscrow` message. If the beneficiary (the solver who filled the order, or the original order's user on refund) is on a token's admin-controlled blocklist (e.g. USDC, USDT), the transfer reverts, the entire `onAccept` call reverts, and `EvmHost.dispatchIncoming` treats this as a retriable failure — but every retry hits the exact same reverting transfer, permanently freezing the escrowed input tokens for that order commitment.

### Finding Description
When a cross-chain intent order is filled or cancelled, `ExtrinsicIntents.onAccept()` decodes the incoming Hyperbridge post request and dispatches to `_withdraw()`: [1](#0-0) 

`_withdraw()` unconditionally pushes tokens to the `beneficiary` address decoded from the message body, with no fallback or pull-based recovery path: [2](#0-1) 

This call happens inside `EvmHost.dispatchIncoming(PostRequest, address relayer)`, which is the sole entry point Hyperbridge uses to deliver verified post requests to modules. Failures there are treated as "retriable" by clearing the request receipt so a relayer can resubmit: [3](#0-2) 

The flaw is that this retry mechanism assumes failures are transient (e.g. gas, temporary reentrancy guards). A blocklist-enforced ERC-20 transfer failure is deterministic: the same beneficiary will be blocked on every subsequent delivery attempt, from any relayer, forever. Since `beneficiary` is fixed at order-placement time (the user for `RefundEscrow`) or at fill time (the solver for `RedeemEscrow`), and cannot be changed after the fact, once that address is blocklisted by the token issuer the escrowed tokens can never be released — the commitment is permanently undeliverable.

The same push-pattern also exists in `IntrinsicIntents.sol` (same-chain fills, calling the identical `_withdraw`) and in the Tron port's analogous `withdraw()`: [4](#0-3) 

### Impact Explanation
Intent orders routinely escrow stablecoins such as USDC. A blocklisted beneficiary (solver payout address or the original depositor, e.g. due to unrelated compliance action by Circle/Tether after the order is placed) permanently blocks settlement of that specific order: the escrowed input tokens are stuck in the `IntentGateway` contract with no recovery path, since `_withdraw` is the only route to release `_orders[commitment][token]` balances. This is a permanent freezing-of-funds condition reachable by ordinary cross-chain intent participants (placing an order, filling an order) without any privileged role, satisfying the "permanent freezing of funds" impact bar.

### Likelihood Explanation
Likelihood is moderate: it requires the beneficiary address to become blocklisted by the underlying token's centralized issuer at some point between order creation/fill and settlement delivery. This is realistic for popular stablecoins (USDC/USDT) with active compliance blocklists, and does not require any malicious action from within Hyperbridge — an already-sanctioned or later-sanctioned address is sufficient. It can also be deliberately triggered by a user placing an order with a beneficiary they know is likely to be listed, or by a griefer front-running a solver's own address (if user-controlled fill beneficiary is attacker-influenced in any flow).

### Recommendation
Replace the push-based `safeTransfer` to `beneficiary` in `_withdraw()` with a pull-based (claimable balance) pattern: on `onAccept`, credit an internal `claimable[beneficiary][token]` mapping instead of transferring immediately, and expose a separate `claim()` function the beneficiary calls to pull funds. This decouples message delivery/finality from the token transfer's success, so a blocklisted beneficiary cannot block delivery of the underlying Hyperbridge message or the order's finalization state, and any recovery (address change, appeal, etc.) can happen independently without requiring changes to the settled order state.

### Proof of Concept
1. User places a cross-chain order via `IntentGatewayV2.placeOrder` escrowing USDC as input, specifying their own address as `order.user` (refund beneficiary).
2. Order is not filled before expiry; user calls the cancellation flow, which eventually causes the destination chain to dispatch a `RefundEscrow` request back to the source chain gateway (`ExtrinsicIntents._cancelFromDestination`/`onGetResponse` paths).
3. Before the `RefundEscrow` message is delivered on the source chain, the user's address is added to USDC's `isBlacklisted` mapping (simulate by overriding `transfer`/`transferFrom` to return false for that address, as in the original report's PoC).
4. A relayer submits the proof to `EvmHost`, which calls `dispatchIncoming` → `IntentGatewayV2.onAccept` → `_withdraw`. The `IERC20(token).safeTransfer(beneficiary, amount)` call reverts.
5. `EvmHost.dispatchIncoming` catches the revert and deletes `_requestReceipts[commitment]`, allowing retry — but every subsequent retry (by any relayer) hits the same revert since the user's blocklist status doesn't change.
6. The escrowed USDC for that commitment is now permanently stuck in the `IntentGateway` contract with no way to release it.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }
