### Title
Webhook `shop` (and other metadata) trusted from unauthenticated HTTP headers while only the raw body is HMAC-verified, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook's authenticity by checking the HMAC signature, but the signature only covers the raw request body. The `shop` (and `topic`, `webhook_id`, `api_version`) values that identify *which tenant* the webhook belongs to are read from HTTP headers that are never included in the signed payload. This breaks the identity binding `shop (cryptographically bound to the signed data) == shop (used to attribute the webhook to a tenant)`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` value used to identify the tenant is pulled straight from the `shopify-shop-domain` HTTP header, which is completely outside of the HMAC-covered data: [2](#0-1) 

`Registry.process` validates the HMAC using `HmacValidator.validate(request)`, which only checks that `compute_signature(request.to_signable_string, secret)` (i.e. HMAC of the raw body) matches the `hmac-sha256` header. It never checks the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers against anything signed: [3](#0-2) [4](#0-3) 

After the (body-only) HMAC check passes, the unauthenticated `request.shop` header value is handed to the host application's handler as the trusted tenant identifier in `WebhookMetadata`: [5](#0-4) 

Because the shop attribution is not cryptographically bound to the payload, any party who can obtain one legitimately-signed webhook body+HMAC pair (e.g., an ordinary merchant who installs the app on their own store and receives real webhooks for their own shop) can replay that exact body/HMAC pair to the app's public webhook endpoint while substituting the `shopify-shop-domain` (and `webhook-id`/`topic`) header for a different (victim) shop. The gem will report the HMAC as valid (it only checks the body) and will hand the host application a `WebhookMetadata` claiming the payload belongs to the victim shop.

### Impact Explanation
This is a cross-tenant identity-binding break: the equality `attributed_shop == hmac_signed_shop` does not hold, since `hmac_signed_shop` is never a formal field of the signature at all — the signature covers only the body. A host application that stores/updates shop-scoped records keyed by `WebhookMetadata#shop` (as documented and demonstrated in the test suite) can have data intended for the attacker's own shop misattributed to, or overwrite state belonging to, a different (victim) shop, since the gem gives the application no cryptographic guarantee that the body actually originated from the shop named in the header. This qualifies as cross-tenant access/confusion, meeting the "Critical: cross-tenant access" impact bar, since it requires no possession of the app's `client_secret`, no access token, and no privileged account — just normal app installation and the ability to send HTTP requests to the app's own public webhook endpoint.

### Likelihood Explanation
Likelihood is high for any app built on this gem: any ordinary merchant/attacker can install the app on their own (unprivileged) test/dev shop, receive one legitimately-signed webhook, and immediately have a valid `(raw_body, hmac)` pair they can replay with an arbitrary `shopify-shop-domain` header. No secrets, credentials, or social engineering are needed — only normal, unprivileged use of Shopify's app-install and webhook-delivery flow that this gem's `Registry.process` accepts as-is.

### Recommendation
Bind the tenant-identifying fields into the signed material, or otherwise cryptographically verify that the `shop-domain` (and `topic`/`webhook-id`) headers are consistent with the signed body — e.g., by validating the sending shop against a known registration for that specific webhook/topic before trusting `request.shop`, or by having `to_signable_string` incorporate the headers that determine tenant attribution so that any header tampering invalidates the HMAC.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker-shop.myshopify.com` and subscribes to a webhook topic (e.g., `orders/updated`).
2. Shopify sends a legitimately-signed webhook to the app's endpoint:
   - Headers: `shopify-topic: orders/updated`, `shopify-shop-domain: attacker-shop.myshopify.com`, `shopify-hmac-sha256: <valid HMAC over raw body>`
   - Body: `{"id": 123, ...}`
3. Attacker captures this exact `(raw_body, hmac)` pair and replays it directly to the app's public webhook endpoint, changing only:
   - `shopify-shop-domain: victim-shop.myshopify.com`
4. `ShopifyAPI::Webhooks::Request.new` parses headers/body as usual; `HmacValidator.validate` recomputes the HMAC over the (unchanged) body and it matches — validation passes, per `lib/shopify_api/utils/hmac_validator.rb` lines 12-31.
5. `Registry.process` calls the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, per `lib/shopify_api/webhooks/registry.rb` lines 198-199, even though the payload never actually originated from or was signed on behalf of `victim-shop.myshopify.com`.
