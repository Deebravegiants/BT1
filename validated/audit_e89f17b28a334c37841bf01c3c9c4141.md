## Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable payload from the raw request body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values used to route and process the webhook are taken from unauthenticated HTTP headers that are never included in the signed data. `ShopifyAPI::Webhooks::Registry.process` validates only that the body's HMAC matches, then trusts the header-derived `shop` value when dispatching to the app's handler — breaking the binding between "bytes verified by HMAC" and "identity fields acted upon."

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are read directly from HTTP headers, independent of the signed body: [2](#0-1) 

`Registry.process` validates the HMAC over the body via `Utils::HmacValidator.validate`, and — once that check passes — trusts `request.shop`, `request.topic`, and `request.webhook_id` when constructing `WebhookMetadata` and dispatching to the app's handler: [3](#0-2) 

`Utils::HmacValidator.validate_signature` computes the signature strictly over `verifiable_query.to_signable_string`, i.e., the raw body, using `api_secret_key`: [4](#0-3) 

The equality that should hold is:
`bytes cryptographically verified (raw body) == bytes the identity/tenant decision is made from (shop header)`

Here that equality does not hold: the `shop` (and `topic`/`webhook-id`) header is completely outside the HMAC's scope. Since most Shopify webhook payload bodies (e.g., `orders/create`, `products/update`) do not themselves embed the originating shop's domain, the `x-shopify-shop-domain` header is the sole signal used to attribute a webhook to a tenant, and it can be freely modified by anyone who can produce one valid `(body, hmac)` pair signed with the app's `api_secret_key` for their own shop.

Any merchant installing the app is a legitimate, unprivileged holder of at least one valid `(body, hmac)` pair (Shopify will deliver real webhooks to their own store events, all signed with the same shared `api_secret_key` configured for the app). Because the header carrying the tenant identity is unauthenticated, that attacker-controlled merchant can replay the same valid `raw_body`/`hmac` pair while substituting an arbitrary `x-shopify-shop-domain` value (e.g., a victim shop they don't own), and `Registry.process` will accept it as fully authentic and hand it to the app's webhook handler tagged with the spoofed shop.

### Impact Explanation
This crosses a tenant boundary: an app's webhook handler that keys off `WebhookMetadata#shop` (as intended and documented, see `data.shop` usage in tests) can be made to apply, store, or act on webhook data under an attacker-chosen shop identity instead of the true origin shop, without possessing that shop's credentials. This matches the "Critical - cross-tenant access" impact bucket, since it lets one merchant's legitimately-signed traffic be attributed to another merchant's tenant record purely by header manipulation.

### Likelihood Explanation
Any installed merchant of the app already receives real webhooks signed with the shared `api_secret_key`, giving them at least one valid `(raw_body, hmac)` sample without needing to know the secret itself. Constructing a POST to the app's public webhook endpoint with a modified `shop-domain` header while keeping the same body/hmac requires no privileged access — the webhook endpoint is a normal public HTTP endpoint by design (Shopify must be able to reach it from the internet), so likelihood is high whenever an app's handler distinguishes behavior/storage by `shop`.

### Recommendation
Bind the tenant/topic identity to the HMAC-covered material: either require Shopify's per-message signing scheme to cover the identifying headers, or — more robustly — cross-check the header-derived `shop` against another already-authenticated source of truth (e.g., a shop that has a valid registered session/webhook registration id in the app's own store) before trusting it, rather than trusting `x-shopify-shop-domain` outright once only the body-HMAC passes.

### Proof of Concept
1. App receives a legitimate webhook for `shop-a.myshopify.com` with body `{}` and header `x-shopify-hmac-sha256` computed from that body and the app's `api_secret_key` (as in `test_process_with_new_format_headers`, `lib/shopify_api/webhooks/registry.rb` test setup).
2. Attacker (owner of `shop-a`) captures this `(raw_body, hmac)` pair.
3. Attacker POSTs to the app's public webhook endpoint reusing the same `raw_body` and `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` succeeds because it only checks `raw_body` against `hmac` — it never inspects `shop`: [5](#0-4) 
5. `Registry.process` calls the app's handler with `WebhookMetadata.new(... shop: request.shop ...)`, where `request.shop` is `"victim-shop.myshopify.com"`, despite the payload never having been produced or authorized by `victim-shop`: [6](#0-5)
