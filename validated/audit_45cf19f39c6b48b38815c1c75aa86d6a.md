## Title
Webhook shop attribution is not covered by the HMAC signature, allowing cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its signable material from the raw body only, while the `shop` value that is later used to route and attribute a webhook to a tenant is taken from an HTTP header that is never included in the HMAC computation. Anyone who can obtain one valid `(raw_body, hmac)` pair for the app (e.g. by capturing a genuine webhook delivered to their own installed shop) can resubmit the same body/HMAC pair to the app's webhook endpoint with the `x-shopify-shop-domain` header changed to a different tenant's shop domain, and `Registry.process` will accept it as authentic and pass it to the handler as if it originated from that other shop.

### Finding Description
`Webhooks::Request#to_signable_string` only returns `@raw_body`: [1](#0-0) 

The `shop` accessor, however, is read straight from an unauthenticated header and is never part of what gets signed: [2](#0-1) 

`Registry.process` validates the request purely via `Utils::HmacValidator.validate(request)`, which internally calls `verifiable_query.to_signable_string` (i.e., the raw body only) and then immediately trusts `request.shop` to build the `WebhookMetadata` passed to the handler: [3](#0-2) 

`HmacValidator.validate` does exactly what the name implies — it recomputes an HMAC over `verifiable_query.to_signable_string` (the raw body) and compares it to the `hmac` header: [4](#0-3) 

So the equality the code relies on is:

```
HMAC(secret, raw_body) == received_hmac  →  therefore shop = header["x-shopify-shop-domain"] is trusted
```

but the binding that should hold is:

```
HMAC(secret, raw_body ⧺ shop) == received_hmac
```

Because `shop` is excluded from the signed material, the two are not equivalent — the signature authenticates the body only, not the (body, shop) pair. Any party capable of obtaining one valid signed payload for the shared app secret (e.g. a malicious merchant who has installed the app and can observe/replay the genuine webhooks Shopify sends to their own store) can splice a different `x-shopify-shop-domain` header onto the same body+hmac and have the library treat it as an authentic webhook for the victim shop, since the HMAC check never inspects the shop header.

### Impact Explanation
This breaks the tenant-identity binding between the cryptographic signature and the shop the message is attributed to. A malicious/compromised tenant of a multi-shop app can forge webhook deliveries that the handler will process as belonging to a *different* shop (`WebhookMetadata#shop` is populated straight from the unauthenticated header). Depending on what the host application's webhook handler does with `shop` (e.g. look up/update per-shop state, trigger internal actions, write records keyed by shop domain), this enables cross-tenant data injection/corruption — one shop's traffic being attributed to and acted upon under another shop's identity. This matches the "cross-tenant access" critical-impact category.

### Likelihood Explanation
Exploitation only requires the attacker to be an existing, unprivileged tenant of the app (any merchant who installs it) capable of receiving/observing one webhook delivery for their own shop — no access to the app's `client_secret`/`api_secret_key` is needed, since the HMAC value from a legitimate delivery is reused verbatim. The webhook receiving endpoint is a normal internet-reachable HTTP(S) endpoint, so replay with a substituted header is trivial. The gem provides no mechanism (and the tests confirm none is exercised) to bind `shop` to the signature.

### Recommendation
Include the shop domain (and ideally topic/webhook id) as part of the signed/verified material — or otherwise cryptographically bind the header-derived `shop` value to the payload — before trusting `request.shop` in `Registry.process`/`WebhookMetadata`. At minimum, `to_signable_string` should incorporate the `shop-domain` header value so that `HmacValidator.validate` fails when the shop is altered independently of the body.

### Proof of Concept
1. App installs on `shop-a.myshopify.com`; Shopify sends a legitimate webhook to the app's endpoint with body `B` and header `x-shopify-hmac-sha256: HMAC(secret, B)`.
2. The merchant who controls `shop-a` (or anyone who can observe that request, e.g. via their own server logs/proxy) captures `(B, HMAC)`.
3. That party sends a new HTTP request to the same webhook endpoint with the identical body `B` and `x-shopify-hmac-sha256` header, but sets `x-shopify-shop-domain: shop-b.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` is built; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only hashes `B` — the check passes.
5. `handler.handle(data: WebhookMetadata.new(..., shop: "shop-b.myshopify.com", body: parsed_body, ...))` is invoked, so the host application processes attacker-controlled data as though it were an authentic webhook from `shop-b`, despite `shop-b` never having sent or authorized it.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
