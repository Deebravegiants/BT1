### Title
Overflow in accrued RAY market values can permanently freeze a pool market - (File: `common/src/rates/simulate.rs`)

### Summary
A sufficiently large borrowed or supplied RAY position can make `scaled_to_original` exceed the `i128` result domain during routine index accrual, causing `MathOverflow` before the transaction reaches repayment, withdrawal, or liquidation logic. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`Controller::supply` and `Controller::borrow` allow an authorized unprivileged caller to create accounts and build very large supply and debt positions, subject to the configured market and spoke caps. [4](#0-3) [5](#0-4) 

After accrual time elapses, the same caller can invoke `Controller::update_indexes(caller, assets)`, which forwards the requested `HubAssetKey` to the pool's owner-gated `update_indexes`. [6](#0-5) [7](#0-6) 

The pool loads the market and calls `interest::global_sync`; every normal mutation uses the same synchronization path before applying its mutation. [8](#0-7) [9](#0-8) 

`accrue_step` first reconstructs the full borrowed and supplied values with `borrowed * borrow_index / RAY` and `supplied * supply_index / RAY`. [2](#0-1) 

Although `mul_div_half_up` widens the intermediate product to `I256`, it still rejects an exact quotient that does not fit `i128`. [10](#0-9) 

The borrow-index ceiling bounds only the index and does not cap the derived market value, so a large share balance can cross the value ceiling before the configured index ceiling is reached. [11](#0-10) [12](#0-11) 

### Impact Explanation
Once the market crosses this boundary, every subsequent accrual transaction reverts before `cache.mark_accrued()` or the requested mutation can run. [13](#0-12) 

Repayment loads an interest-synced market through `ops::load_leg`, and withdrawal does the same, so neither debt repayment nor collateral withdrawal can execute after the overflow. [14](#0-13) [15](#0-14) 

The regression test demonstrates that `update_indexes` returns `MATH_OVERFLOW`, the borrow-index cap has not been reached, and subsequent repay and withdraw calls also revert with `MATH_OVERFLOW`. [16](#0-15) 

This permanently freezes suppliers' remaining pool funds and blocks normal liquidation or debt resolution for the affected market unless an out-of-scope contract upgrade changes the arithmetic. [8](#0-7) [17](#0-16) 

### Likelihood Explanation
The trigger requires a very large token balance, permissive caps, an 18-decimal or similarly scaled asset, sustained high utilization, and enough compounding for the scaled debt or supply value to approach `i128::MAX`. [18](#0-17) 

No privileged action is required once such a listed market admits the required balances: the attacker can control both the supplying account and the collateralized borrowing account and then call the permissionless index-update entrypoint. [4](#0-3) [6](#0-5) 

The existing test uses one billion whole 18-decimal tokens supplied to the target market and a 98% borrow, showing that the condition is reachable within the admitted arithmetic domain rather than relying on malformed state. [19](#0-18) 

### Recommendation
Make accrual value-domain aware before computing `borrowed * borrow_index / RAY` or `supplied * supply_index / RAY`, rather than allowing the derived totals to cross the `i128` boundary. [2](#0-1) 

A robust fix should calculate the next index with widened arithmetic and clamp it to a dynamic bound derived from `i128::MAX / scaled_shares`, or otherwise prevent index growth that would make either market total unrepresentable. [11](#0-10) 

Admission checks should also reject additional supply or debt when the resulting scaled balance could exceed the current value domain, because lowering a dynamic cap after shares are admitted cannot rescue a market whose value is already unrepresentable. [20](#0-19) 

Add regression coverage that `update_indexes`, `repay`, `withdraw`, and liquidation still succeed at the largest admitted market sizes instead of reverting in `global_sync`. [8](#0-7) [17](#0-16) 

### Proof of Concept
The in-repository test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` reproduces the issue by supplying `1_000_000_000 * 10^18` base units and borrowing `98%` of that amount against large collateral. [18](#0-17) 

Conceptually, an attacker can submit the following unprivileged calls:

```rust
let debt_key = HubAssetKey { hub_id, asset: debt_asset };
let collateral_key = HubAssetKey { hub_id, asset: collateral_asset };

let supplier_id = controller.supply(
    attacker,
    0,
    spoke_id,
    vec![(debt_key.clone(), 1_000_000_000 * 10i128.pow(18))],
);

let borrower_id = controller.supply(
    attacker,
    0,
    spoke_id,
    vec![(collateral_key, 3_000_000_000 * 10i128.pow(7))],
);

controller.borrow(
    attacker,
    borrower_id,
    vec![(debt_key.clone(), 980_000_000 * 10i128.pow(18))],
    Some(attacker),
);

// After sufficient compounding:
controller.update_indexes(attacker, vec![debt_key]); // reverts with MathOverflow
```

The reproduced transaction path then fails on `update_indexes`, `withdraw`, and `repay` with `MATH_OVERFLOW`. [16](#0-15)

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
