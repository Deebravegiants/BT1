### Title
Unprivileged spot-price manipulation of Uniswap V4 pool state lets an attacker trick the Simplex intent solver into filling cross-chain orders at a manipulated price - (File: sdk/packages/simplex/src/funding/uniswapV4/UniswapV4FundingPlanner.ts)

### Summary
`UniswapV4FundingPlanner.getExoticTokenPrice` / `computeDirectPoolPriceUsd` prices a curveless trading pair directly from the Uniswap V4 pool's current `sqrtPriceX96` (read via `StateView.getSlot0`, the V4 analog of `UniV3Pool.slot0`), exactly the manipulable "most recent data point" pattern flagged in H-10 for `IchiVault#getTotalAmounts`/`IchiLpOracle`. There is no TWAP or execution-cost-aware pricing anywhere on this path.

### Finding Description
When a trading pair has no configured bid/ask curves, `resolveLegRates` in `sdk/packages/simplex/src/strategies/fx.ts` prices it entirely from the pool: [1](#0-0) 

which calls `UniswapV4FundingPlanner.getExoticTokenPrice`, which selects the position with the largest liquidity and derives the price straight from the pool's live tick/`sqrtPriceX96` via `computeDirectPoolPriceUsd`: [2](#0-1) [3](#0-2) 

The underlying pool state is fetched with `StateView.getSlot0`/`getLiquidity` — a direct, instantaneous read with no time-weighting: [4](#0-3) 

This is functionally identical to the H-10 root cause: `IchiVault._amountsForLiquidity` reading `IUniswapV3Pool(pool).slot0()` directly rather than a TWAP, so the valuation used downstream (there, LP token pricing; here, the exotic-token USD price used to size and rate a fill) is trivially manipulable within a single block by anyone who can move the pool's spot price (e.g., a large swap/flash-loan-funded swap against a thin pool). The project's own documentation acknowledges the pool is trusted as-is: "Pool-based pricing trusts the live pool, which leaves the solver exposed to a manipulated, stale, or thin pool returning a bad quote," and the only defense, `checkPriceGuard`, is a static-reference deviation check, not a TWAP or execution-cost check — and it is optional (`referencePrice`/`maxDeviationBps` must both be set or "the chain is left unguarded").

### Impact Explanation
An attacker fully controls when to submit a cross-chain intent order against a curveless, pool-priced pair. By sandwiching the order (or timing it after moving the pool's spot price with a swap, and reverting/unwinding that swap afterward, or simply relying on natural pool thinness), the attacker can force the solver to derive `venueUsd` from an artificially skewed instantaneous price. The solver then quotes/fills using `computeLegPolicyOutput`, which linearly extends this manipulated mid-price across the full order size with no size/impact term: [5](#0-4) 

This causes the solver to hand over more of the exotic/stable token than the fair market price justifies, resulting in real, unrecoverable economic loss to the solver's escrowed/vault liquidity for every such fill — a concrete theft of funds analogous to the loss described in H-10, reachable purely by an unprivileged intent placer submitting an order plus a permissionless pool swap.

### Likelihood Explanation
Medium-High when a pair is configured for pool-based (curveless) pricing and either (a) `referencePrice`/`maxDeviationBps` is not configured for that chain ("unguarded" per the docs), or (b) the guard's static deviation band is wide enough / stale enough to admit a profitable manipulation window while the linear mid-price extension still misprices size. Any V4 pool with moderate-to-thin liquidity relative to the configured `maxOrderSize` is a viable target, and no special privileges are required — only capital to move the pool's tick temporarily.

### Recommendation
- Replace the direct `getSlot0` spot-price read in `computeDirectPoolPriceUsd`/`UniswapV4LiquidityState.refresh` with a TWAP derived from the pool's oracle/observation data (or an external, harder-to-manipulate price feed) before using it for cross-asset settlement pricing.
- Make `referencePrice`/`maxDeviationBps` mandatory (not optional) for any pool-priced pair, and additionally bound deviation using recent-block TWAP rather than only a static configured reference.
- Add a size/impact-aware pricing term (e.g., simulate the swap through the pool, or apply slippage to the sourced-liquidity fee tier) instead of extending the raw mid-price linearly across the whole leg notional, closing the exact gap the venue-pricing docs already flag ("A venue-priced pair that has to swap through its own pool to source inventory pays a fee tier it never quoted against").

### Proof of Concept
1. Solver operator configures a curveless pair (e.g., `USDC/EXOTIC`) priced from a `[vault.uniswapV4]` V4 position, without setting `referencePrice`/`maxDeviationBps` (an explicitly supported, "unguarded" configuration per `docs/content/developers/evm/simplex/pricing.mdx`).
2. Attacker executes a large swap against the same V4 pool (which need not be deep, since the solver "picks the position with the largest pool liquidity" among configured pools, not necessarily a deep global pool) to shift `sqrtPriceX96` favorably for the attacker.
3. In the same block/near-block window, attacker submits (or has ready) an intent order on this pair sized near `maxOrderSize`.
4. `resolveLegRates` → `getExoticTokenPrice` → `computeDirectPoolPriceUsd` reads the manipulated `getSlot0` value; `computeLegPolicyOutput` linearly extends this manipulated mid across the whole notional with no TWAP/impact correction.
5. The solver fills the order at the manipulated rate, transferring an inflated amount of the exotic/stable token to the attacker, realizing a loss for the solver's liquidity that a TWAP-based or impact-aware price would have prevented.

	async getExoticTokenPrice(chain: string, exoticToken: string): Promise<Decimal | null> {
		const state = this.stateByChain.get(chain)
		if (!state || !state.isHydrated()) return null

		try {
			await state.refresh()
		} catch (err) {
			this.logger.error({ err, chain }, "Failed to refresh state for price query")
			return null
		}

		const tokenLower = exoticToken.toLowerCase()
		let bestPrice: Decimal | null = null
		let bestLiquidity = 0n

		for (const pos of state.allPositions()) {
			if (pos.currency0.toLowerCase() !== tokenLower && pos.currency1.toLowerCase() !== tokenLower) continue
			const sdkPool = state.getSdkPool(pos.tokenId)
			if (!sdkPool) continue

			const result = this.computeDirectPoolPriceUsd(pos, sdkPool, chain)
			if (result && result.exoticToken.toLowerCase() === tokenLower) {
				const poolLiquidity = state.getPoolLiquidity(pos.tokenId)
				if (poolLiquidity > bestLiquidity) {
					bestPrice = result.priceUsd
					bestLiquidity = poolLiquidity
				}
			}
		}

		if (bestPrice) {
			this.logger.debug({ chain, token: tokenLower, priceUsd: bestPrice.toString() }, "Exotic token price computed")
		}
		return bestPrice
	}

	/**
	 * Computes the USD price of the non-stable token in a pool.
	 * Returns null if neither currency is USDC/USDT on this chain.
	 */
	private computeDirectPoolPriceUsd(
		pos: HydratedV4Position,
		sdkPool: V4Pool,
		chain: string,
	): { exoticToken: string; priceUsd: Decimal } | null {
		const usdc = this.configService.getUsdcAsset(chain).toLowerCase()
		const usdt = this.configService.getUsdtAsset(chain).toLowerCase()
		const c0 = pos.currency0.toLowerCase()
		const c1 = pos.currency1.toLowerCase()

		if (c0 === usdc || c0 === usdt) {
			// currency0 is stable → exotic is currency1
			// token1Price = "token0 per token1" = USD per exotic
			return {
				exoticToken: c1,
				priceUsd: new Decimal(sdkPool.token1Price.toFixed(18)),
			}
		}

		if (c1 === usdc || c1 === usdt) {
			// currency1 is stable → exotic is currency0
			// token0Price = "token1 per token0" = USD per exotic
			return {
				exoticToken: c0,
				priceUsd: new Decimal(sdkPool.token0Price.toFixed(18)),
			}
		}

		return null
	}
