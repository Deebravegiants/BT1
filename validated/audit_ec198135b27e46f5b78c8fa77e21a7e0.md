### Title
Unchecked ERC20 return-value bypass causes silent loss of escrowed funds on withdraw/dust-sweep - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of `IntentGatewayV2` releases escrowed tokens using a raw low-level `.call` to `IERC20.transfer`, but only checks that the *external call itself* did not revert (`success`). It never inspects the ABI-decoded boolean return value of `transfer()`. For any ERC20 that signals failure by returning `false` instead of reverting (e.g. ZRX-style tokens), the check passes even though no tokens were moved, while the escrow accounting is unconditionally decremented as if the transfer succeeded — permanently losing the beneficiary's funds.

### Finding Description
`withdraw()` in `evm/tron/contracts/apps/IntentGatewayV2.sol` is the internal settlement function invoked from `onAccept` (for `RedeemEscrow`/`RefundEscrow` cross-chain messages), `onGetResponse` (source-chain cancellation), and `cancelOrder`'s same-chain branch. It releases each escrowed input token to the beneficiary:

```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
...
_orders[body.commitment][token] -= amount;
``` [1](#0-0) 

`success` here reflects only whether the call reverted, not the boolean return value ERC20's `transfer()` encodes in the return data. A non-reverting-on-failure token (returns `false`) will make `success == true`, so the `revert TransferFailed()` guard never triggers, yet `beneficiary` receives nothing. The code proceeds to decrement `_orders[...]`, delete the fee escrow, and emit `EscrowReleased`/`EscrowRefunded` as if settlement succeeded: [2](#0-1) 

The same unchecked pattern recurs in the `SweepDust` handler inside `onAccept`: [3](#0-2) 

Notably, this file already imports and declares `using SafeERC20 for IERC20;`, and the sibling non-Tron contracts (`IntentsBase.sol`, `HyperFungibleToken.sol`) correctly use `safeTransfer`, which reverts on a `false` return. The Tron contract's manual `.call` pattern regressed this safety check, reproducing exactly the bug class from the referenced Teller report: an ERC20 that "fails silently" causes the caller/beneficiary to lose the tokens they were owed while the contract's internal ledger (and events) report success. [4](#0-3) 

### Impact Explanation
Any solver settling a cross-chain fill, any user receiving a refund via `RefundEscrow`/source-chain cancellation, or any beneficiary of the fee-token payout can permanently lose their entire escrowed amount if the configured input/fee token is one that returns `false` on failed transfer rather than reverting (a well-known real-world ERC20 pattern). Because `_orders[...]` is decremented and `EscrowReleased`/`EscrowRefunded` is emitted regardless of actual token movement, the loss is silent, unrecoverable through the normal contract flow, and indistinguishable on-chain from a legitimate settlement — this is a direct, permanent loss of user/solver funds.

### Likelihood Explanation
This does not require any privileged actor or governance action — it only requires that the IntentGateway configure or accept an ERC20 token that returns `false` on failure (a token property outside the gateway's control, entirely plausible for arbitrary token listings on an Intent Gateway used across many assets). Any relayer delivering a normal `RedeemEscrow`/`RefundEscrow` message, or any user calling `cancelOrder` same-chain, triggers the vulnerable path — no adversarial timing or front-running is even needed, unlike the original report; the bug fires deterministically whenever such a token is involved.

### Recommendation
Replace all raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `evm/tron/contracts/apps/IntentGatewayV2.sol` (in `withdraw()` and the `SweepDust` branch of `onAccept`) with OpenZeppelin's `SafeERC20.safeTransfer`, which is already imported and used via `using SafeERC20 for IERC20;` elsewhere in the codebase (e.g., `IntentsBase.sol`, `HyperFungibleToken.sol`). `safeTransfer` correctly decodes and validates the ERC20 return value and reverts on `false`, closing the silent-failure window before any escrow state is mutated.

### Proof of Concept
1. Deploy `IntentGatewayV2` (Tron variant) with an ERC20 `EvilToken` whose `transfer()` returns `false` when, e.g., the recipient is blacklisted or a condition is unmet, without reverting.
2. A user places a cross-chain order escrowing `EvilToken` as input (or `RefundEscrow` fee token).
3. A solver fills the order on the destination chain; the settlement message reaches the source chain and `onAccept` calls `withdraw(body, false)`.
4. Inside `withdraw`, `EvilToken.transfer(beneficiary, amount)` returns `false`; `token.call(...)` reports `success = true` since the call did not revert.
5. `_orders[body.commitment][token] -= amount;` executes, `EscrowReleased` is emitted, but `beneficiary`'s `EvilToken` balance never increased — the tokens remain stuck/unaccounted-for in the gateway with no code path to recover them for that beneficiary.

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
    }
