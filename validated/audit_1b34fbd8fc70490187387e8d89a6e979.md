### Title
Panic (validator halt) if a staked vote account's balance drops below the VAT amount between filtering and burning - (File: `runtime/src/bank.rs`)

### Summary
`Bank::maybe_burn_vat_from_staked_accounts` unconditionally subtracts a fixed "Validator Admission Ticket" (VAT) amount from every staked vote account's lamports using an `.expect()` instead of a graceful/checked fallback, relying entirely on an upstream filtering step (`clone_and_filter_for_vat`) to have guaranteed sufficient balance. This mirrors the Heart.sol bug class: a privileged/periodic "reward/fee sweep" operation that assumes funds are available without re-validating at the point of debit, except here the failure mode is a hard panic in bank-commit code rather than a benign self-DoS.

### Finding Description
In `runtime/src/bank.rs`, `maybe_burn_vat_from_staked_accounts` iterates every vote account returned by `epoch_stakes.stakes().vote_accounts()` and does: [1](#0-0) 
```
for (vote_pubkey, _stake) in vote_accounts.delegated_stakes() {
    let mut account = self.get_account(vote_pubkey).unwrap();
    total_vat += vat_to_burn_per_epoch;
    account.set_lamports(
        account
            .lamports()
            .checked_sub(vat_to_burn_per_epoch)
            .expect(
                "Vote accounts should have already been filtered to contain enough \
                 balance for the VAT",
            ),
    );
    accounts_to_store.push((*vote_pubkey, account));
}
```

This is structurally identical to the reported bug class: an operation (`_issueReward` in Heart.sol) that blindly transfers/subtracts a fixed amount without checking the current, authoritative balance at execution time, instead trusting a prior calculation (the `reward` variable / here, the `clone_and_filter_for_vat` filtering pass) to remain valid. The vote account's lamports are *not* re-read or re-validated at burn time beyond the same `get_account` call whose value is immediately trusted; the actual "insufficient funds" enforcement is `.checked_sub(...).expect(...)`, i.e. a panic path instead of an error/skip path.

If `clone_and_filter_for_vat`'s snapshot of vote-account balances becomes stale by the time `maybe_burn_vat_from_staked_accounts` runs — for example if a vote account's authorized withdrawer withdraws lamports via the vote program's `withdraw` instruction (an unprivileged, user-reachable path shown at `programs/vote/src/vote_state/mod.rs:1062-1129`) in a transaction processed after the filter snapshot was taken but before this bank-commit-time VAT burn executes — the `checked_sub` will return `None` and the `.expect()` will panic the bank/validator process. Because this runs as part of bank freezing/epoch-boundary processing (not as an isolated transaction), a panic here does not fail a single transaction; it aborts the entire validator process, causing a cross-node/consensus-halt scenario if it happens deterministically across the cluster (since all validators compute the same bank state).

### Impact Explanation
Unlike the original Heart.sol finding — where the worst case is a benign self-DoS requiring manual re-funding — a panic in bank-commit code inside `maybe_burn_vat_from_staked_accounts` crashes the validator process outright. Because this logic runs deterministically as part of epoch-boundary bank state computation (Alpenglow VAT collection), if the balance/filter invariant is violated on one validator it would likely be violated on all validators processing the same epoch boundary, resulting in a cluster-wide halt rather than an isolated node failure. This is a severe availability/liveness impact far beyond the referenced report's "self-DoS until refunded" — it is closer to a full network halt.

### Likelihood Explanation
This can only be triggered if `clone_and_filter_for_vat`'s "sufficient balance" guarantee can become stale before `maybe_burn_vat_from_staked_accounts` executes — e.g., a withdrawal transaction against a filtered vote account lands in the same slot/epoch-boundary window after the filter snapshot but before the burn is applied. I was not able to fully verify, within the remaining investigation budget, the exact ordering guarantees between `clone_and_filter_for_vat` (in `runtime/src/stakes.rs`) and the point where `epoch_stakes` used here is captured/frozen relative to transaction processing in the same slot — this is the key uncertainty. If the filtering snapshot is taken from `current_epoch_stakes()`/vote-account state that is fixed prior to the epoch boundary slot's transaction processing (i.e., a strictly earlier snapshot that cannot be mutated by transactions in the burn slot), then the invariant likely holds and this would not be exploitable. Confirming this requires reading `clone_and_filter_for_vat` in `runtime/src/stakes.rs` and its call site relative to `maybe_burn_vat_from_staked_accounts`, which I could not complete before the iteration limit.

### Recommendation
Regardless of whether the current invariant is airtight, replace the `.expect()` panic with a saturating/checked-and-skip pattern (e.g. `saturating_sub` and cap the burn to what is available, similar to the `min(reward, available_balance)` remediation recommended in the referenced finding), so that any staleness or future refactor of `clone_and_filter_for_vat` cannot turn into a validator-crashing panic. Additionally, add an explicit debug assertion or recheck of the invariant with a graceful `continue`/logged-skip fallback instead of relying solely on documentation comments to preserve the safety property across future code changes.

### Proof of Concept
Not independently reproduced. A conceptual PoC would require: (1) identifying a vote account admitted by `clone_and_filter_for_vat` with a balance only marginally above `vat_to_burn_per_epoch`, (2) submitting a valid vote-withdraw transaction (`programs/vote/src/vote_state/mod.rs::withdraw`) from that account's authorized withdrawer that reduces its balance below `vat_to_burn_per_epoch` before `maybe_burn_vat_from_staked_accounts` runs in the same epoch-boundary bank, and (3) confirming that `checked_sub` returns `None`, triggering the `.expect()` panic. I could not verify the timing/ordering guarantees between the filter step and the burn step to confirm this is actually reachable, so this should be treated as a plausible-but-unverified analog pending further code review of `clone_and_filter_for_vat` in `runtime/src/stakes.rs`.
