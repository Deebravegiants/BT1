### Title
Same-Asset Batch Withdrawals Report Identical Status/TxHash Due to AssetId-Only Matching - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts, packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts)

### Summary
`findMatchingWithdrawal()` in the POA bridge withdrawal-status lookup matches an on-chain withdrawal API response entry to a specific withdrawal request using only the token `assetId`, not the withdrawal's index or amount. When a single NEAR intent transaction contains two or more withdrawals of the same token (a legitimate batch-withdrawal use case supported by `createWithdrawalCompletionPromises`/`waitForWithdrawalCompletion`), every one of those withdrawals resolves to the *same* matched entry — the first one returned by `.find()`. This breaks the equality "the status/txHash reported for withdrawal index N corresponds to withdrawal N's actual on-chain outcome."

This is structurally the same bug class as the reported `_searchApproxIndex()` issue: a shared response list (`response.withdrawals`, analogous to `updatedTimestamps`/`indexes`) is queried under the implicit assumption that only one relevant entry (bucket) exists, when in fact multiple entries for the same key can legitimately coexist. The lookup returns whichever entry happens to be first, not necessarily the one belonging to the withdrawal being queried.

### Impact Explanation
If a batch intent includes two withdrawals of the same token (e.g., two USDC withdrawals to different destination addresses within one signed intent — supported per the `CreateWithdrawalCompletionPromisesParams`/multi-withdrawal design), both `describeWithdrawal` calls return identical status and `txHash`. An integrating service using `promises[0]`/`promises[1]` or `createWithdrawalCompletionPromises` (per `docs/design/rfc-batch-withdrawal-granular-control.md`, Index correspondence section) would credit/mark both withdrawals as completed using the same destination tx hash, even though only one of the two actual on-chain transfers may have completed, and the second withdrawal's real destination/tx hash is never surfaced. This is a status misreport that can cause an integrator to double-credit or falsely close out a still-pending withdrawal — matching the "High" impact category (status misreport making an integrator credit twice).

### Likelihood Explanation
Reachability depends on whether the SDK actually allows constructing a batch intent with two withdrawals of the identical `assetId` in the withdrawal params array. I was not able to confirm, within the remaining tool budget, whether `sdk.ts` or the intent-building code path enforces any uniqueness constraint on `assetId` across `withdrawalParams` in a batch — grepping `sdk.ts` for duplicate/uniqueness checks found nothing, but I did not have iterations left to trace the full batch-construction path (`sdk.signAndSendWithdrawalIntent.test.ts`, `sdk.createWithdrawalCompletionPromises.test.ts`, `core/withdrawal-watcher.ts`) to confirm no dedup/validation exists elsewhere. The bug's authors themselves flag this as a known, currently-accepted limitation rather than an unknown defect, which suggests it may be considered acceptable risk given current POA API constraints — but the code comment states the limitation is inherited from the POA API's own inability to distinguish same-token withdrawals, not from an SDK-side safeguard preventing the scenario.

### Recommendation
Match withdrawals using index-preserving correlation (e.g., stable sort of both the API response and the local `withdrawalParams` by amount, as the existing code comment already suggests) instead of `assetId` alone, or reject/flag batches containing duplicate `assetId` entries at intent-construction time until POA API support for disambiguation is added, so `describeWithdrawal`/`waitForWithdrawalCompletion` never silently returns the same entry for two distinct withdrawal indices.

### Proof of Concept
1. Construct a NEAR intent with two POA-bridge withdrawals of the same token (`assetId = "nep141:usdc.omft.near"`) but different destination addresses/amounts, submitted as `withdrawalParams[0]` and `withdrawalParams[1]` in one transaction.
2. Call `sdk.createWithdrawalCompletionPromises({ withdrawalParams, intentTx })` or invoke `describeWithdrawal` for both indices.
3. Both calls internally invoke `findMatchingWithdrawal(response.withdrawals, "nep141:usdc.omft.near")`, which returns `withdrawals.find(...)` — the same first matching array element for both index 0 and index 1.
4. Both `promises[0]` and `promises[1]` (or both `describeWithdrawal` results) resolve with the identical `status`/`txHash`, even though only one underlying on-chain transfer may exist/complete — an integrator following the RFC's recovery pattern (`handledIndexes`) would mark both withdrawals as settled using the same tx hash.

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}

function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
