## Title
Log injection via unsanitized user email in LDAP login logging - (File: core/sessions/ldapauth/ldap.go)

## Summary
`ldapAuthenticator.CreateSession` logs the raw, unauthenticated, attacker-controlled `sr.Email` via a printf-style `Infof` call (line 435) without stripping `\n`/`\r`, and the earlier `escapedEmail` value (line 418) is only LDAP-filter-escaped (not newline-stripped). The sibling `oidcAuthenticator.CreateSession` explicitly sanitizes `\n`/`\r` from `sr.Email` before an equivalent log call, showing the project is aware of and mitigates this exact bug class elsewhere but missed it in the LDAP path.

## Finding Description
`SessionsController.Create` (`core/web/sessions_controller.go` L29-60) is an unauthenticated `POST /sessions` endpoint that binds client JSON directly into `clsessions.SessionRequest` and forwards it to `AuthenticationProvider().CreateSession`. When LDAP auth is configured, this reaches:

```go
// core/sessions/ldapauth/ldap.go:406-435
escapedEmail := ldap.EscapeFilter(strings.ToLower(sr.Email))
...
l.lggr.Infof("Successful user login, but error querying for user groups: user: %s, error %v", escapedEmail, err)
...
l.lggr.Infof("Successful LDAP login request for user %s - %s", sr.Email, foundUser.Role)
```

`ldap.EscapeFilter` only escapes RFC 4515 filter metacharacters (`*`, `(`, `)`, `\`, NUL) — it does not strip `\r`/`\n`. Line 435 uses the fully raw `sr.Email` with no escaping at all. By contrast, `core/sessions/oidcauth/oidc.go` L418-420 explicitly does:
```go
sanitizedEmail := strings.ReplaceAll(sr.Email, "\n", "")
sanitizedEmail = strings.ReplaceAll(sanitizedEmail, "\r", "")
oi.lggr.Infof("Successful local admin login request for user %s - %s", sanitizedEmail, foundUser.Role)
```
confirming the codebase treats this as a fix-worthy pattern that was simply not applied consistently to LDAP.

I additionally verified the logger's rendering pipeline. The core logger always JSON-encodes messages (`core/logger/logger.go` `newDefaultLoggingCore`, using `zapcore.NewJSONEncoder`), and when `JSONConsole=false` (the documented default), output is routed to a `pretty://console` sink (`core/logger/prettyconsole.go`). `PrettyConsole.Write` parses the JSON bytes with `gjson` (which unescapes `\n` back to a literal newline) and renders the message through `sanitized.String()`:
```go
// core/logger/prettyconsole.go:139-155
case '\n', '\r', '\t':
    // allowed
```
This function explicitly passes `\n`/`\r` through unescaped when producing the human-readable console log line. This confirms that on the default, human-readable console log format, an embedded newline in `sr.Email` does produce additional forged-looking lines in the actual rendered log stream, not just an escaped substring inside one JSON line.

## Impact Explanation
An unauthenticated attacker submitting a crafted `email` value containing `\n`/`\r` plus forged text can inject fabricated lines into the node's default pretty-console log output (CWE-117 log injection / log forgery). This can mislead operators or log-based monitoring/SIEM tooling with fake "successful login" or fake error/audit lines. This does not grant privilege escalation, data exfiltration, or unauthorized fund movement — it is a log integrity/observability issue only, consistent with the Low/Medium classification used for the referenced Jenkins CVE analog. Note that the underlying `.jsonl` file (when `JSONConsole=true`, or as the always-JSON-encoded on-disk record) keeps the injected content JSON-escaped within a single `msg` field value, so the file-based structured log is not broken into forged separate JSON records — only the pretty/human console rendering is affected.

## Likelihood Explanation
High likelihood of triggering: `/sessions` is intentionally unauthenticated (login endpoint), the `email` field is fully attacker-controlled JSON input, and no validation rejects control characters before reaching the LDAP logging calls. Reproducible on any node configured with `AuthenticationMethod = 'ldap'`.

## Recommendation
Sanitize `sr.Email` (strip `\r`/`\n`, as already done in `core/sessions/oidcauth/oidc.go`) before use in `l.lggr.Infof` calls in `core/sessions/ldapauth/ldap.go` (both the line 418 `escapedEmail`-based message and the line 435 raw `sr.Email` message). Prefer structured logging fields (`Infow`) over interpolating user input into printf-style messages, and consider hardening the shared `sanitized.String()` pretty-console formatter to also escape `\n`/`\r` (or clearly document the tradeoff if intentional for multi-line messages).

## Proof of Concept
1. Configure a node with `[WebServer] AuthenticationMethod = 'ldap'` and `Log.JSONConsole = false` (default).
2. `POST /sessions` with body:
```json
{
  "email": "attacker@example.com\nINFO Successful LDAP login request for user admin@example.com - admin",
  "password": "irrelevant"
}
```
3. Observe the node's console log output (pretty-console sink) contains an extra forged line resembling a successful admin login, injected via the crafted `email` field.
