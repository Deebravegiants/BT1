### Title
Webhook shop identity spoofing via unauthenticated `shop-domain` header - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC computed over the raw request **body**. The `shop` value that the handler receives and acts on is read from the `x-shopify-shop-domain` / `shopify-shop-domain` HTTP header, which is never included in the HMAC-signed material. An attacker who can obtain one genuine (body, HMAC) pair — for example by installing the app on their own store, since apps typically share a single `api_secret_key` across every merchant install — can replay that exact body/HMAC to the app's public webhook endpoint while substituting an arbitrary value in the `shop-domain` header. The signature check still passes because the HMAC never covered that field, so the payload is processed as if it originated from a different (victim) shop.

For webhooks, the "signable" material used for that HMAC is only the raw body: [2](#0-1) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all pulled straight from HTTP headers that sit outside the signed payload: [3](#0-2) 

`Registry.process` only checks the HMAC, then dispatches the handler using the header-derived, unauthenticated `shop`: [4](#0-3) 

This is structurally the same class of bug as the reported `verifyHash256Merkle` issue: the code verifies one set of bytes (the raw body) but then acts on a different, unverified field (`shop-domain` header) as if it had been authenticated together with the verified bytes. The equality that should hold — "the shop whose secret validated the HMAC" == "the shop the handler believes sent the payload" — is broken because the header is never bound into the signature computation.

### Impact Explanation
Because the same `api_secret_key` is normally shared by an app across all its merchant installations, any single legitimate installer (an ordinary, unprivileged merchant who installs the app on their own store) can capture one valid `(raw_body, hmac)` pair from Shopify's real webhook delivery to their own endpoint, then replay it directly to the app's public webhook endpoint with the `shop-domain` header changed to a victim shop's domain. `HmacValidator.validate` still returns `true` (body/HMAC pair is genuinely valid), and `Registry.process` invokes the registered handler with `shop: <victim-domain>` and attacker-chosen body content (e.g., fabricated `orders/create`, `app/uninstalled`, or GDPR webhook payloads). This is a cross-tenant confusion/injection primitive: application logic keyed off `WebhookMetadata#shop` (e.g., look up the victim's session/store record and apply the attacker-supplied body) can be corrupted or manipulated for a tenant the attacker does not control, without ever needing the app's `client_secret` or a stolen access token.

### Likelihood Explanation
Exploitation requires the attacker to be able to install the target app on at least one store they control (a normal, unprivileged action for any Shopify merchant/developer), capture one legitimate webhook body+HMAC, and send an unauthenticated HTTP POST to the app's public webhook URL with a modified `shop-domain` header — no secret material, TLS interception, or privileged access is needed.

### Recommendation
Bind the `shop` (and ideally `topic`/`api_version`) into the value that is HMAC-verified, or otherwise cryptographically tie the header-derived shop to the verified body (e.g., require the shop domain to appear inside the signed payload, or validate it against a shop-specific secret/session rather than trusting the header outright). At minimum, document and enforce that host applications must independently confirm the `shop` header corresponds to a shop that has actually installed the app before trusting webhook `shop` metadata.

### Proof of Concept
1. Install the target app on attacker-owned store `attacker.myshopify.com`; capture a real webhook delivery `{raw_body, x-shopify-hmac-sha256}` for e.g. `orders/create`.
2. POST that identical `raw_body` and `x-shopify-hmac-sha256` value to the app's public webhook endpoint, but set `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Utils::HmacValidator.validate` succeeds (body/HMAC match), and `ShopifyAPI::Webhooks::Registry.process` invokes the handler with `shop: "victim.myshopify.com"` and the attacker's chosen `orders/create` body, even though the payload never came from `victim.myshopify.com`.
