### Title
Webhook `shop-domain`, `topic`, and `webhook-id` headers are trusted without HMAC coverage, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then hands the handler a `WebhookMetadata` object built from **unauthenticated** header values (`shop`, `topic`, `webhook_id`, `api_version`). The identity binding the app actually needs — "this body belongs to this shop/topic" — is never enforced by the gem.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all pulled directly from HTTP headers with no cryptographic binding to the signed body: [2](#0-1) 

`Registry.process` validates only the HMAC (which covers the body) and then constructs `WebhookMetadata` using the unauthenticated `request.shop`/`request.topic`/`request.webhook_id` fields, passing them straight to the app's handler: [3](#0-2) 

`WebhookMetadata.shop` is a plain `String` field with no additional validation performed by the gem: [4](#0-3) 

The equality that should hold is: `HMAC(secret, raw_body)` should authenticate `(shop, topic, body)` as a unit. Instead it only authenticates `body`; `shop`, `topic`, and `webhook_id` are asserted, not verified. This is precisely the "field acted on but not covered by the HMAC" identity-binding gap. Because `HmacValidator.validate` only recomputes over `to_signable_string` (`= raw_body`), any request with a body/HMAC pair that was legitimately produced by Shopify for one shop will pass validation even if the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header is swapped to point at an entirely different shop.

### Impact Explanation
An attacker who operates their own store using the merchant app (an ordinary, unprivileged action any internet user can take by installing a public app on a free/dev store) can trigger webhook deliveries whose body content they influence (e.g., `products/update`, `customers/update`, `orders/create` fields for their own store). Since the HMAC only covers the body, the attacker can replay that legitimately-signed `(body, hmac)` pair to the app's public webhook endpoint while substituting the `shop-domain` header for a victim shop. `Registry.process` will pass HMAC validation and hand the handler a `WebhookMetadata` claiming the data belongs to the victim shop. Any host application that uses `data.shop` to key storage, look up the victim's session/access token, or update victim records (the exact pattern shown in the gem's own documentation, `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) will process attacker-controlled data as if it originated from the victim, producing cross-tenant data corruption/injection. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires only: (1) the ability to become an app user on some store (widely available, no special privilege), (2) intercepting/replaying one's own legitimately delivered webhook HTTP request with a modified `shop-domain` header, and (3) the app's webhook endpoint being reachable over the internet (a documented requirement for HTTP webhook delivery). No access to the app's `api_secret_key`, access tokens, or victim credentials is required. The gem's documentation actively encourages using `data.shop` to drive tenant-specific logic, so the vulnerable usage pattern is the expected one.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the value that is HMAC-verified, or perform a secondary authenticated lookup: after validating the body HMAC, cross-check that `request.shop` corresponds to a shop for which the app currently holds an active, previously-established session/installation record before trusting it. At minimum, the gem should document/enforce that `WebhookMetadata.shop` must not be treated as authenticated on its own, or should provide a combined verification method that binds header-derived shop/topic values into the signature check (e.g., validate against a stored expected value per delivery, or require the caller to supply an already-authenticated shop context).

### Proof of Concept
1. Attacker installs the target app on their own test store `attacker-shop.myshopify.com`.
2. Attacker performs an action that triggers a webhook whose body they control content of (e.g., updates a product to include arbitrary JSON in an editable field), causing Shopify to POST to the app's webhook endpoint with a valid `X-Shopify-Hmac-Sha256` computed over that body using the real `api_secret_key`.
3. Attacker intercepts this request (e.g., via a local proxy sniffing their own traffic, or by using a webhook capture/replay tool) and resends it to the app's public webhook endpoint, changing only the `X-Shopify-Shop-Domain` header to `victim-shop.myshopify.com`, leaving body and HMAC header untouched.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `HMAC(secret, raw_body)` — unaffected by the header change: [5](#0-4) 
5. `Registry.process` builds `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker-controlled JSON>, ...)` and invokes the app's handler, which (per the gem's own documented usage pattern) updates victim-shop records with attacker-supplied data.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,

        end
