### Title
Webhook `shop-domain` header is not covered by HMAC verification, enabling cross-tenant webhook replay - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signable string from the raw body only, while the `shop` (and `topic`, `webhook_id`, `api_version`) values are read directly from unauthenticated HTTP headers. `Registry.process` validates the HMAC and then hands the header-derived `shop` straight to the app's webhook handler. This breaks the intended binding `shop-domain-header == shop-that-produced-this-body`, mirroring the reentrancy report's root cause: a value that participates in a security-relevant decision (`_pods[from]`/`updateBalances` target) is trusted without being covered by the integrity check that is supposed to bind the whole operation together.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of the signable string and therefore not covered by the HMAC: [2](#0-1) [3](#0-2) 

`HmacValidator.validate` only verifies `verifiable_query.to_signable_string` (i.e., the raw body) against `verifiable_query.hmac`; it never checks anything about `shop`: [4](#0-3) 

`Registry.process` validates the HMAC and then forwards the *header-derived* `shop` to the handler as trusted tenant metadata: [5](#0-4) 

Because the HMAC only proves "this body was signed with the app's secret for *some* webhook," and not "this body belongs to this shop," an attacker who is a merchant/dev-store owner of their own shop (an unprivileged actor with respect to any other tenant) can capture one of their own legitimately-signed webhook deliveries (raw body + valid HMAC), then replay that exact body/HMAC pair to the app's public webhook endpoint while substituting an arbitrary `shop-domain` header. The HMAC still validates (it only checks the body), but the handler receives `WebhookMetadata` claiming the payload belongs to a different shop.

This is the same class of bug as the reported reentrancy issue: the code assumes an unchecked value (`_pods[from]`/`_pods[to]` in the report; `shop` header here) stays consistent with the value that was actually authenticated (the delegation-transfer set; the raw body here), and acts on the unchecked value as if it had been verified.

### Impact Explanation
If the host application uses `WebhookMetadata#shop` (as most integrations do, per this gem's own docs/tests) to select which tenant's records to update from `WebhookMetadata#body`, an attacker can inject attacker-controlled webhook content that is falsely attributed to a victim shop, producing cross-tenant data confusion/corruption without needing the victim's credentials, access token, or `client_secret` — only the ability to receive one legitimate webhook for their own shop and the app's public webhook URL. This matches the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Any developer/merchant can install the app on a shop they control and legitimately receive at least one webhook, satisfying the prerequisite of obtaining a valid `(raw_body, hmac)` pair. The webhook endpoint is by design internet-reachable and unauthenticated apart from the HMAC. No secret material is required from the attacker.

### Recommendation
Include the `shop-domain` (and ideally `topic`/`webhook-id`) header values in the HMAC-signable string, or otherwise cryptographically bind the shop identity to the signed payload, so `Utils::HmacValidator.validate` fails if the shop header is altered relative to what was actually signed by Shopify for that delivery.

### Proof of Concept
1. Install the target app on attacker-owned shop `attacker.myshopify.com`; capture a legitimate webhook POST, e.g. `orders/create`, noting the raw body `B` and header `x-shopify-hmac-sha256: H` (valid because `HMAC(secret, B) == H`).
2. Replay a new POST to the app's webhook endpoint with the same body `B` and header `x-shopify-hmac-sha256: H`, but set `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged `shop` header; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only re-derives `HMAC(secret, B)` and compares to `H` — validation succeeds.
4. The registered handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed(B), ...)`, causing the host app to process attacker-controlled data under the victim's tenant identity.
