### Title
Missing compute cost charge for gas key nonce insertion in `add_gas_key` while `delete_gas_key` explicitly charges removal compute - (File: runtime/runtime/src/access_keys.rs)

### Finding Description
`delete_gas_key` explicitly computes and adds a compute cost for the trie removals it performs on gas key nonces: [1](#0-0) 
via `storage_removes_compute`, which is added to `result.compute_usage`.

In contrast, `add_gas_key` performs an analogous loop that writes `num_nonces` trie entries (`set_gas_key_nonce`) but never computes or adds any compute cost for these insertions: [2](#0-1) 

The only accounting performed on the insert side is a `storage_usage` increase via `gas_key_storage_cost`, which affects ongoing storage rent, not the per-chunk `compute_usage` metric. `compute_usage` in nearcore is a distinct resource-limiting mechanism (separate from gas) intended to bound the actual wall-clock/trie-operation cost of processing a chunk, independent of how gas is priced for the action. Because there is no `storage_insert_compute`-equivalent call in `add_gas_key`, the trie-insertion work for gas-key nonces is entirely unaccounted for in `compute_usage`, while the removal path for the same structure is fully accounted for. This is a genuine and verifiable asymmetry in the code as written.

### Impact Explanation
This falls under "gas/storage metering bypass" — specifically, an underpriced-compute (not underpriced-gas) issue. Since `compute_usage` is meant to bound real per-chunk execution cost distinctly from the gas fee schedule (to prevent slow-but-cheap-in-gas operations from stalling chunk production), a systematic gap on the insert side for gas key nonces means the actual resource cost of `AddKeyAction` with a `GasKeyFullAccess` permission and large `num_nonces` is not reflected in `compute_usage`, unlike the symmetric delete operation.

### Likelihood Explanation
This requires only an ordinary account holder submitting `AddKeyAction`s with `GasKeyFullAccess(num_nonces)` — no special privilege is needed to reach `action_add_key` → `add_gas_key`. I was not able to verify in the available context whether `num_nonces` is bounded by a separate validation check (e.g. in the transaction verifier) that would limit the achievable asymmetry, since I ran out of tool iterations before confirming this. This is a material gap in my analysis and should be checked before treating the severity as high.

### Recommendation
Add a `storage_insert_compute`-equivalent charge in `add_gas_key` for the `num_nonces` nonce-insertion loop, mirroring the `storage_removes_compute` charge already applied in `delete_gas_key`, and add it to `result.compute_usage` via `safe_add_compute`, so insert and remove compute costs for gas key nonces are symmetric.

### Proof of Concept
Add a unit test analogous to `test_delete_gas_key` (which already asserts `result.compute_usage == expected_nonce_remove_compute(...)`) for `action_add_key`/`add_gas_key`: construct an `AddKeyAction` with `AccessKey::gas_key_full_access(num_nonces)` for a large `num_nonces` (e.g. 1024), call `action_add_key`, and assert `result.compute_usage` is non-zero and comparable in magnitude to the delete-side compute cost for the same `num_nonces` (currently it will assert `result.compute_usage == 0`, exposing the asymmetry since `action_add_key`'s `ActionResult` is never populated with any compute cost in `add_gas_key`).
