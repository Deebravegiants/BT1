### Title
Webhook `shop` domain is not covered by the HMAC signature, allowing cross-tenant identity spoofing in `Webhooks::Registry.process` - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives its `hmac` signable content solely from the raw request body, while the `shop` value (and `topic`, `api_version`, `webhook_id`) are read directly from unauthenticated HTTP headers. `Webhooks::Registry.process` validates only that the HMAC matches the body, then passes the header-derived `shop` straight into `WebhookMetadata` for the app's handler to act on. This breaks the identity binding `hmac-verified(body) == shop-acted-on(header)`: a valid HMAC only proves the body's integrity, not that the accompanying `x-shopify-shop-domain` header is genuine for that body.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read from the `x-shopify-shop-domain`/`shopify-shop-domain` header, entirely outside the signed content: [2](#0-1) 

`Registry.process` validates only the HMAC-over-body via `Utils::HmacValidator.validate(request)` and then forwards `request.shop` unchanged into the handler's `WebhookMetadata`: [3](#0-2) 

`HmacValidator.validate` computes the signature purely over `verifiable_query.to_signable_string`, i.e., the raw body in this case: [4](#0-3) 

Because the shop-domain header is not part of the signed material, any request carrying a body+HMAC pair that is valid for the app's `api_secret_key` (e.g., a body genuinely produced for one shop that installed the app) can be replayed with an arbitrary `x-shopify-shop-domain` header value substituted in. The HMAC check still passes (it only re-verifies the body), yet `WebhookMetadata#shop` — which host applications use as the tenant identity to select the correct session/access token/data scope — reflects the attacker-supplied header instead of the shop the payload actually originated from. This is the same class of defect as the report: a field (`shop`) that a handler acts on as an identity/tenant key is not covered by the cryptographic binding (HMAC) that is meant to authenticate the whole request.

The documentation explicitly frames `process` as verifying "the request did indeed come from Shopify," implying the entire `WebhookMetadata`, including `shop`, is trustworthy: [5](#0-4) 

### Impact Explanation
Any unprivileged party who can obtain one valid (body, HMAC) pair for the target app — trivially achievable by installing the app on their own store and capturing a real webhook delivery to their own endpoint, or via any other channel where a legitimate webhook body/HMAC leaks — can replay that exact body with a forged `x-shopify-shop-domain` header pointing at a victim shop. Applications built on this gem that key per-tenant logic (e.g., which merchant's data a webhook body updates, cache invalidation, order/customer record association, or fetching the correct stored access token) off `WebhookMetadata#shop` will process the attacker's payload as if it belonged to the victim's shop. This is a cross-tenant confusion / cross-tenant data-processing bypass, since the shop identity used to route/authorize the payload is not actually bound to the verified bytes.

### Likelihood Explanation
Medium-High. It requires obtaining one valid webhook body+HMAC for the target application (not the target victim shop) — reachable by any actor who installs the app themselves, since app installation is typically open. The webhook receiving endpoint is by design internet-facing and unauthenticated aside from the HMAC, so replaying with a different `x-shopify-shop-domain` header requires no special access, credentials, or social engineering.

### Recommendation
Bind the shop-domain header to the same trust boundary as the body, or make it explicit that `shop` is untrusted metadata that callers must not use for tenant authorization decisions without additional verification (e.g., cross-checking against a known/registered shop for that specific webhook subscription, or including the shop domain in the signable content if Shopify's webhook signing scheme is updated to support it). At minimum, update documentation to clarify that `Registry.process` verifies body integrity only, and that `WebhookMetadata#shop` must not be treated as authenticated for authorization purposes without separately confirming the shop is one for which this app holds an active session.

### Proof of Concept
```ruby
# Attacker installs the app on their own store "attacker-shop.myshopify.com"
# and receives a real webhook delivery with a valid HMAC for the app's secret:
raw_body = '{"id":123,"note":"legit payload for attacker shop"}'
valid_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), api_secret_key, raw_body)

# Attacker now replays the same body/HMAC pair but swaps the shop-domain header
# to point at a victim shop that also uses the app:
forged_headers = {
  "x-shopify-topic" => "orders/updated",
  "x-shopify-hmac-sha256" => Base64.encode64(valid_hmac),
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # attacker-controlled, unverified
  "x-shopify-webhook-id" => "any-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HMAC validation passes (it only checks raw_body against the secret),
#    and the handler receives WebhookMetadata with shop: "victim-shop.myshopify.com",
#    even though the body/HMAC pair was never generated for that shop.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
