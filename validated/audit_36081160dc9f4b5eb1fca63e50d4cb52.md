### Title
Header-precedence collision in `shopify_header` lets an attacker forge `topic`/`shop-domain` on an otherwise validly-HMAC'd webhook body, causing cross-handler/cross-tenant dispatch - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`Webhooks::Request#initialize` normalizes headers by stripping a leading `http_` and dashing underscores, then `shopify_header` resolves a value by trying `"shopify-#{name}"` before `"x-shopify-#{name}"`. Because HMAC validation (`HmacValidator.validate`) only signs `@raw_body` and never covers headers, an attacker who legitimately captured one signed webhook body/HMAC pair (e.g., from their own dev shop) can replay it to the app's public webhook endpoint while injecting extra headers that normalize into the higher-priority `shopify-topic` / `shopify-shop-domain` slots, overriding the genuine `x-shopify-topic` / `x-shopify-shop-domain` values without invalidating the HMAC check.

### Finding Description
The broken binding: the code assumes `shopify_header("shop-domain") == the shop that authenticated/signed this webhook delivery`. In reality `shopify_header` only reflects **header name precedence**, not authenticity:

```ruby
def shopify_header(name)
  @headers["shopify-#{name}"] || @headers["x-shopify-#{name}"]
end
``` [2](#0-1) 

and header normalization collapses attacker-supplied header names into the same key namespace used for trusted Shopify headers:

```ruby
headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }
``` [3](#0-2) 

`HmacValidator.validate` computes the HMAC purely from `to_signable_string` (i.e. `@raw_body`) and compares it to `hmac` (`shopify_header("hmac-sha256")`); it never incorporates `topic` or `shop-domain` into the signable string: [4](#0-3)  and [5](#0-4) . `Registry.process` then trusts `request.topic` for handler lookup and `request.shop` for `WebhookMetadata.shop`, both derived from the unauthenticated header map: [1](#0-0) .

Exploit flow: the attacker registers a webhook endpoint on their own dev shop, receives a legitimate, validly-signed webhook (body B, HMAC H for `X-Shopify-Topic: orders/create`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`). They then POST body B directly to the victim app's public webhook URL with the original `X-Shopify-Hmac-Sha256: H` header (still valid since HMAC only covers the body) plus two extra attacker-chosen headers, e.g. `shopify-topic: shop/redact` and `shopify-shop-domain: victim-shop.myshopify.com`. After normalization, these collide with the priority-preferred `shopify-*` keys, so `shopify_header` returns the attacker's forged topic/shop instead of the genuine `x-shopify-*` values, while HMAC verification still succeeds because it only checked `@raw_body`. `Registry.process` dispatches `handler.handle` with `WebhookMetadata.shop == "victim-shop.myshopify.com"` even though the body actually belongs to the attacker's own shop, and/or routes to a different topic's handler (e.g. a mandatory redact handler) than the one that was actually signed.

No existing guard closes this gap: `HmacValidator.validate` (body-only), `ShopValidator.sanitize!` (used elsewhere for OAuth, not webhooks), and Sorbet's `T.cast`/struct typing only enforce that the value is a `String`, not that it is authentic.

### Impact Explanation
The host app uses `WebhookMetadata.shop` to decide which merchant's records to update/delete (e.g., process `customers/redact` or `shop/redact` for a shop the attacker never controls, or write into another tenant's data model), and uses `WebhookMetadata.topic` to pick the handler. This is a cross-tenant data integrity/confidentiality issue driven entirely by an unauthenticated header value being treated as authenticated identity, matching the "cross-tenant access" Critical category. Each replay of one captured signed body can be repeated against arbitrary target shop names chosen by the attacker (bounded only by whatever validation the *host app's handler* itself performs on `shop`, which this gem does not enforce).

### Likelihood Explanation
Low attacker cost: create a free dev shop, install the app, capture one legitimately signed webhook. No `api_secret_key` or access token required — HMAC validity is preserved because the signature never covered headers to begin with. The attacker needs the target app's public webhook endpoint URL, which is typically fixed/discoverable per app. Repeatable indefinitely with the same captured body/HMAC pair as long as the body content itself doesn't need to vary for the attack to matter (topic/shop confusion works with any valid body).

### Recommendation
Do not let header name precedence or `http_`-stripping create synonym keys that can shadow genuine `x-shopify-*` headers. At minimum: (1) only accept the canonical `x-shopify-*` header names for webhook metadata, or explicitly reject requests where both `shopify-<name>` and `x-shopify-<name>` are present and disagree; (2) more importantly, include `topic` and `shop-domain` in the HMAC-signable string (or otherwise cryptographically bind them) so header spoofing cannot alter the trusted identity while keeping the same valid signature.
