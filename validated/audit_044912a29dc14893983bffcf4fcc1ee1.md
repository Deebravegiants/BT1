### Title
Blacklisted beneficiary permanently freezes escrowed intent funds in `IntentsBase._withdraw` - (File: evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
`IntentGatewayV2`'s escrow-release path (`_withdraw`) performs a raw `IERC20.safeTransfer`/low-level `.call` to a beneficiary address taken from cross-chain message data (the solver on `RedeemEscrow`, or the original order user on `RefundEscrow`/`onGetResponse` cancellation). If the debt/input asset is a blacklist-capable token (e.g. USDC) and that beneficiary is blacklisted, the transfer reverts. Because the host's delivery layer swallows this revert and simply marks the message as retryable rather than completing it differently, the message can never be delivered successfully again — permanently freezing the escrowed input tokens for that specific order commitment.

### Finding Description
`_withdraw` releases escrowed input tokens directly to a beneficiary decoded from the incoming ISMP message body, with no try/catch around the transfer: [1](#0-0) 

This is reached from two unprivileged-relayer-delivered paths:
- `onAccept` for `RedeemEscrow` (solver payout after a cross-chain fill) and `RefundEscrow` (refund after destination-side cancellation): [2](#0-1) 

- `onGetResponse` for source-side cancellation refunds: [3](#0-2) 

The Tron/EVM sibling contract has the identical unguarded transfer pattern: [4](#0-3) 

When the underlying `IApp.onAccept`/`onGetResponse` call reverts, `EvmHost.dispatchIncoming` does **not** propagate the revert to fail the whole relayer batch — it deletes the just-written receipt and returns, leaving the message "retryable": [5](#0-4) 

This "retry forever" design is meant for transient failures (e.g., temporary out-of-gas or reentrancy guards). It does not help when the failure cause is permanent, such as a beneficiary address being blacklisted by the token contract: every future relayer resubmission of the exact same message will keep calling `safeTransfer` to the same blacklisted address and keep reverting.

Because `_filled[commitment]` is only set atomically together with the token transfer inside the same `_withdraw` call (and reverts together with it), the order is never actually finalized on the paying chain. Meanwhile, the *other* side of the order lifecycle has already been irreversibly finalized:
- For `RedeemEscrow`: the solver already delivered output tokens and `_filled[commitment]` was set on the destination chain at fill time, so `cancelOrder`'s source-side GET-based path will find a non-empty `_filled` slot on the destination and revert with `Filled()` — the user cannot reclaim the escrow either.
- For `RefundEscrow` (cancel-from-destination): `_filled[commitment]` is already set to the user on the destination chain to lock out further fills, so there is no alternate route back to try a different beneficiary on the source chain.

In both cases, once the beneficiary is durably blacklisted, the escrowed input tokens sit unreleasable in the `IntentGatewayV2` contract on the source chain indefinitely.

### Impact Explanation
This results in permanent freezing of user/solver funds held in escrow by `IntentGatewayV2`, with no on-chain recovery path (no admin sweep of a specific order's escrow, and the alternate cancellation routes are blocked by the already-finalized `_filled` state on the other chain). This satisfies the "permanent freezing of funds" impact bar and is a direct analog of the original BendDAO finding, reachable by any user/solver simply becoming blacklisted by a common blacklist-capable stablecoin (USDC, USDT, etc.) used as an intent input/output asset — an unprivileged, realistic condition requiring no malicious actor beyond the token issuer's own compliance action.

### Likelihood Explanation
Intent Gateway explicitly supports arbitrary ERC-20 tokens as inputs/outputs (documentation and fee-on-transfer-token tests confirm this design intent), and USDC/USDT-style blacklisting is a well-known, real-world occurrence. Any long-lived cross-chain order whose solver or user later becomes blacklisted on the relevant token will hit this path with certainty once the corresponding settlement/refund message is relayed.

### Recommendation
Wrap the beneficiary transfer(s) in `_withdraw` (and the Tron `withdraw`) in a try/catch (or use a pull-payment/escrow-to-recipient-vault fallback) so that a reverting transfer does not block finalization of the order's on-chain state. On transfer failure, credit the amount to an internal, beneficiary-claimable balance (or a designated fallback recipient) instead of reverting the whole `_withdraw`, and still emit `EscrowReleased`/`EscrowRefunded` and mark `_filled` so the order is not stuck in limbo.

### Proof of Concept
1. User places a cross-chain order with `inputs` denominated in USDC on the source chain; `IntentGatewayV2.placeOrder` escrows the USDC.
2. Solver fills the order on the destination chain (`_fillCrossChain`), which sets `_filled[commitment] = solver` there and dispatches a `RedeemEscrow` POST request back to the source chain.
3. Before the message is relayed, USDC's issuer blacklists the solver's address (e.g., due to unrelated compliance action).
4. A relayer submits `HandlerV2.handlePostRequests` → `EvmHost.dispatchIncoming` → `ExtrinsicIntents.onAccept` → `IntentsBase._withdraw`, which calls `IERC20(usdc).safeTransfer(solver, amount)`; this reverts because the solver is blacklisted.
5. `EvmHost.dispatchIncoming` catches the failed call, deletes the request receipt, and returns without reverting the batch — the message is "retryable" but will fail identically on every future relayer resubmission since the solver's blacklist status persists.
6. The user cannot reclaim the escrow via `cancelOrder` because the destination chain already shows `_filled[commitment] = solver` (non-empty), so the GET-based cancellation reverts with `Filled()`.
7. The escrowed USDC is now permanently stuck in `IntentGatewayV2` on the source chain.

        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

                (bool sent,) = beneficiary.call{value: amount}("");

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }
