### Title
Webhook HMAC Verification Does Not Bind the `shop` Identity to the Signed Payload, Enabling Cross-Tenant Webhook Spoofing - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, and `ShopifyAPI::Webhooks::Registry.process` uses that same HMAC check to authorize the entire request, then trusts the unauthenticated `x-shopify-shop-domain` header as the tenant identity handed to the app's handler. Because the `shop` field that determines tenant scoping is never included in the HMAC-signed material, any unprivileged merchant who has installed the app can replay a legitimate webhook body (signed with the app's single, shared `client_secret`) while substituting an arbitrary victim shop domain in the header, and the signature will still validate.

### Finding Description
`Request#to_signable_string` binds the HMAC exclusively to `@raw_body`: [1](#0-0) 

`shop`, `topic`, and `webhook_id` are all pulled straight from HTTP headers that are never part of the signed string: [2](#0-1) 

`Registry.process` validates only this body-bound HMAC, then immediately trusts `request.shop` (the header) as the tenant identity forwarded to the app's handler: [3](#0-2) 

The equality that should hold is:
`shop authenticated by HMAC == shop used as the tenant key in WebhookMetadata`

but the actual state is:
`shop authenticated by HMAC == "" (no shop is authenticated at all)` while `shop used as tenant key == unauthenticated x-shopify-shop-domain header value`.

Because `Context.api_secret_key` is a single, app-wide secret shared across every merchant who installs the app (not a per-shop secret), any unprivileged merchant can install the app, receive a fully legitimate webhook for their own store (correct body + valid HMAC), and then replay that exact `raw_body`/HMAC pair to the app's webhook endpoint with the `x-shopify-shop-domain` header rewritten to a victim shop's domain. `HmacValidator.validate` will pass because the body is unchanged, and `Registry.process` will invoke the handler with `WebhookMetadata.shop` set to the victim's domain: [4](#0-3) 

The gem's own documented usage pattern encourages handlers to key persistence/business logic directly off `data.shop`, which is exactly the value that is spoofable: [5](#0-4) 

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook delivery: an unprivileged, independently-installing merchant can inject fabricated webhook events (`orders/create`, `customers/data_request`, etc.) attributed to a different, victim shop's tenant scope in the host application's data store, without ever needing the victim's credentials. Depending on how the host app consumes `data.shop` (which the gem's own docs recommend using directly for storage/processing), this can lead to cross-tenant data corruption, spoofed mandatory compliance webhooks (`customers/redact`, `shop/redact`), or triggering of shop-scoped business logic for a shop the attacker does not control. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high: the only prerequisite is that the attacker installs the same public app on their own Shopify store (an action any unprivileged internet user can take for any app that supports open installs), then captures one legitimate webhook delivery and replays it with a modified header. No access to the app's `client_secret`, TLS interception, or any privileged account is required — only observation of traffic the attacker's own store legitimately receives.

### Recommendation
Include the shop identity (and ideally topic/webhook-id) inside the HMAC-signed material, or otherwise cryptographically bind the header-derived `shop` value to the verified payload before it is handed to `WebhookMetadata`. At minimum, `Registry.process` should require that the caller supply/validate the expected shop (e.g., from the route or install record) and reject processing if it doesn't match `request.shop`, rather than trusting the header verbatim as the sole tenant identifier reaching the handler.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` and lets the app register `orders/create` webhooks.
2. Shopify sends a legitimate webhook to the app's endpoint:
   - Headers: `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC of raw_body>`
   - Body: `{"id":1,...}`
3. Attacker captures `raw_body` and `x-shopify-hmac-sha256` verbatim.
4. Attacker replays the identical `raw_body`/HMAC to the same endpoint but sets `x-shopify-shop-domain: victim.myshopify.com`.
5. `HmacValidator.validate(request)` returns `true` (HMAC only covers `raw_body`, unchanged), so `Registry.process` invokes the app's handler with `WebhookMetadata.shop == "victim.myshopify.com"`, causing the host app to process/store attacker-controlled data under the victim shop's tenant scope.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,

        end
