### Title
Precision-mismatched pnl guard lets `calc_take_pnl` underflow-panic and permanently freeze pool operations - (File: `program/src/processor.rs`)

### Summary
`Processor::calc_take_pnl` gates its sqrt-based pnl calculation with an invariant check performed in *denormalized, floor-rounded* units, but then performs the actual pnl math in *normalized* units without that rounding loss. This precision mismatch lets a state that should be rejected by the guard slip through, causing an unguarded `checked_sub(...).unwrap()` to underflow and panic. Because `calc_take_pnl` is invoked from `process_deposit`, withdraw, and both swap paths, and the panicking transaction never commits, the on-chain state that produced the panic persists — permanently freezing all future deposits, withdrawals and swaps on that pool.

### Finding Description
`calc_take_pnl` first checks whether it's safe to "take" pnl using **denormalized** (native decimal) amounts: [1](#0-0) 

`calc_pc_amount`/`calc_coin_amount` are produced by `Calculator::restore_decimal`, which performs a **floor** division when converting the normalized `target.calc_pnl_x`/`calc_pnl_y` back to native units: [2](#0-1) 

`pool_pc_amount`/`pool_coin_amount`, on the other hand, are the exact native vault balances (`total_pc_without_take_pnl`, `total_coin_without_take_pnl}`) with no rounding. Because the RHS of the guard is rounded **down**, the guard `pool_pc*pool_coin >= calc_pc*calc_coin` is strictly easier to satisfy than the true, unrounded relationship between the normalized quantities that the subsequent math actually depends on.

Once the guard passes, the code switches to **normalized** units (`x1`, `y1`, `target.calc_pnl_x`, `target.calc_pnl_y` — all in `sys_decimal_value` scale) to compute `x2` via `calc_x_power`/`integer_sqrt`: [3](#0-2) [4](#0-3) 

and then immediately subtracts with an unchecked-guard `unwrap`: [5](#0-4) 

The correctness of `x1.checked_sub(x2)` (and `y1.checked_sub(y2)`) actually requires `target.calc_pnl_x * target.calc_pnl_y <= x1 * y1` in **normalized, exact** terms — not the floor-rounded, denormalized comparison performed by the guard. Because `restore_decimal` truncates, there exist pool states where the true normalized invariant has already fallen below `target.calc_pnl_x * target.calc_pnl_y` (making `x2 > x1` mathematically), yet the denormalized/rounded guard still reports `pool_pc*pool_coin >= calc_pc*calc_coin` as true. In that case, `x1.checked_sub(x2).unwrap()` underflows and panics.

`calc_take_pnl` is called from `process_deposit`, `process_withdraw`, `process_swap_base_in`, and `process_swap_base_out` (all reachable by any unprivileged swapper/LP/pool creator) with the same `total_pc_without_take_pnl`/`total_coin_without_take_pnl`/`target_orders` state each time: [6](#0-5) [7](#0-6) [8](#0-7) 

Since a panicking Solana transaction reverts all state changes, once the pool's on-chain state (vault balances + `target_orders.calc_pnl_x`/`calc_pnl_y`) reaches the triggering condition, every subsequent deposit/withdraw/swap transaction that reaches `calc_take_pnl` with that same state will deterministically panic again — there is no way for a user transaction to change the state without first passing through the same panicking call.

### Impact Explanation
This permanently denies all pool participants (LPs and swappers) access to `Deposit`, `Withdraw`, and both swap instructions on the affected pool, because every one of them invokes the panic-prone `calc_take_pnl` with the frozen, unmovable pool state. This matches "permanent freezing of user or LP funds" — user tokens held in the AMM vaults and LP positions become permanently inaccessible through the AMM program's own instructions.

### Likelihood Explanation
Reaching the triggering rounding condition does not require a privileged signer; it only requires ordinary swap/deposit/withdraw activity to drive the pool's normalized invariant down to a boundary value where the denormalized floor-rounding in the guard masks the true state. Given `sys_decimal_value` normalization commonly compresses higher-precision token decimals (e.g., 9-decimal SPL tokens vs. a 6-decimal `sys_decimal_value`), floor-rounding loss of several units per call is routine, making the boundary condition realistically reachable through normal, repeated trading activity rather than a contrived one-off input.

### Recommendation
Perform the pnl-safety guard comparison in the same units and precision as the subsequent computation (i.e., compare `target.calc_pnl_x.checked_mul(target.calc_pnl_y)` directly against `x1.checked_mul(y1)` in normalized U256 space, without the lossy `restore_decimal` round-trip), or replace the unchecked `checked_sub(...).unwrap()` calls in `calc_take_pnl` with `checked_sub(...).ok_or(AmmError::CalcPnlError)` so a guard miss surfaces as a recoverable error instead of an unrecoverable panic.

### Proof of Concept
1. Create a pool and perform a sequence of swaps/deposits/withdraws that gradually change `total_pc_without_take_pnl` / `total_coin_without_take_pnl` relative to the stored `target_orders.calc_pnl_x`/`calc_pnl_y`, such that the true normalized product `calc_pnl_x * calc_pnl_y` exceeds `x1 * y1`, while the denormalized/floor-rounded guard at `program/src/processor.rs:190-192` still evaluates true (achievable because `restore_decimal` at `program/src/math.rs:96-104` floors `calc_pnl_x`/`calc_pnl_y` down before the comparison).
2. Submit any subsequent `Deposit`, `Withdraw`, `SwapBaseIn`, or `SwapBaseOut` instruction on this pool.
3. Execution reaches `Processor::calc_take_pnl`, computes `x2 > x1` via `calc_x_power`/`integer_sqrt` (`program/src/math.rs:50-60`, `program/src/processor.rs:199-209`), and panics at `x1.checked_sub(x2).unwrap()` (`program/src/processor.rs:213`).
4. Because the panicking transaction reverts, the pool's state (and thus the triggering condition) is unchanged, so every future call to any of the four instruction types against this pool panics identically, permanently freezing the pool.

    pub fn calc_x_power(last_x: U256, last_y: U256, current_x: U256, current_y: U256) -> U256 {
        // must be use u256, because u128 may be overflow
        let x_power = last_x
            .checked_mul(last_y)
            .unwrap()
            .checked_mul(current_x)
            .unwrap()
            .checked_div(current_y)
            .unwrap();
        x_power
    }

    pub fn restore_decimal(val: U128, native_decimal: u64, sys_decimal_value: u64) -> U128 {
        // e.g., amm.sys_decimal_value is 10**6, native_decimal is 10**9, price is 1.23, this function will convert (1.23*10**6) -> (1.23*10**9)
