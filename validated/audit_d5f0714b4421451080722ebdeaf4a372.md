### Title
Reentrancy in `withdraw()` violates checks-effects-interactions, allowing escrow double-spend across multiple tokens - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron deployment of `IntentGatewayV2` implements an internal `withdraw()` function that sends native ETH/tokens to a caller-influenced `beneficiary` address via raw `.call` **before** decrementing the corresponding `_orders[commitment][token]` escrow balance, and does so per-token inside a loop with no reentrancy guard anywhere in the contract.

### Finding Description
`withdraw()` is reached from three places: `onAccept` (RedeemEscrow/RefundEscrow, `onlyHost`), `onGetResponse` (`onlyHost`), and directly from `cancelOrder()`'s same-chain branch (fully permissionless, caller-controlled `order.user`/beneficiary). In all cases the beneficiary address ultimately resolves to a value that can be an attacker-deployed contract (the order's `user`/`beneficiary` field, or a solver address from a cross-chain message).

Inside `withdraw`, `_filled[body.commitment]` is set at the very top (good), but the token-release loop is not CEI-compliant: [1](#0-0) 

For each token in `body.tokens`, the function performs an external call (`beneficiary.call{value: amount}("")` for native tokens, or a raw `token.call(...transfer...)` for ERC20) and only afterwards executes `_orders[body.commitment][token] -= amount;`. The same pattern repeats for the transaction-fee payout: [2](#0-1) 

Because the external call happens strictly before the corresponding storage write for **that same token slot**, a malicious `beneficiary` contract can re-enter during the callback. All the top-level public entry points that could re-invoke `withdraw` (`cancelOrder`, and the host-gated `onAccept`/`onGetResponse`) are guarded only by the `_filled[commitment]` check, which is set once, globally, at the very start of `withdraw` — not per-token. This means:
- A single `withdraw()` call that releases **multiple token slots** for one commitment (e.g., native ETH + an ERC20 input) is vulnerable: the ETH transfer to the malicious beneficiary fires its `receive()`/fallback mid-loop, before `_orders[commitment][ETH]` is decremented, but crucially also before later iterations decrement `_orders[commitment][ERC20]`.
- Because the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` does not check the boolean return value (only whether the call itself succeeded/didn't revert), a non-standard or fee-on-transfer-like token can silently fail the transfer while the code still proceeds to decrement `_orders`, or conversely a malicious "token" contract at that address could execute arbitrary reentrant logic during the `.call`.
- Unlike the EVM (`evm/src/apps/intentsv2/IntentsBase.sol`) implementation of `_withdraw`, which decrements the escrow (`_orders[body.commitment][token] = escrowed - amount;`) **before** calling `_sendValue`/`safeTransfer`, the Tron contract inverts this order, reintroducing exactly the CEI violation that the sibling EVM contracts and their dedicated `IntrinsicIntentsReentrancyTest.sol` suite were built to eliminate.
- No `nonReentrant`/`ReentrancyGuardTransient` modifier is present anywhere in `evm/tron/contracts/apps/IntentGatewayV2.sol`, in contrast to `IntentGatewayV2.sol` (main EVM) which inherits `ReentrancyGuardTransient` and guards `fillOrder` with `nonReentrant`.

This is a direct analog of the reported Diamond-pattern issue: an unprivileged, externally reachable entry point (`cancelOrder`, and indirectly the ISMP-delivered `RedeemEscrow`/`RefundEscrow` messages handled by `onAccept`) performs state-changing external calls without a reentrancy guard, and the guard that does exist (`_filled`) does not protect the intra-loop, per-token escrow bookkeeping.

### Impact Explanation
If the destination/beneficiary of a withdrawal is (or delegates to) an attacker-controlled contract, a reentrant call during the native-token `.call` inside the loop can be used to manipulate escrow state for other tokens tied to the same commitment before it is finalized, or to exploit the unchecked ERC20 return value to make the contract believe a transfer succeeded when it did not — leading to loss of escrowed user/protocol funds (theft or permanent freezing of the remaining escrow, since `_orders` bookkeeping becomes inconsistent with actual token balances once reentered). This affects real user/solver escrow funds, satisfying the "concrete theft or permanent freezing of funds" bar.

### Likelihood Explanation
Medium: the attacker fully controls the order's `beneficiary`/`user` for the same-chain `cancelOrder` path (any attacker can place and cancel their own order with a malicious beneficiary contract), and the cross-chain `RedeemEscrow`/`RefundEscrow` beneficiary is set by the destination-chain solver/user, which is also attacker-influenceable in the intents flow. The `_filled` early-set does block the most obvious "re-enter the whole withdraw path" attack, but it does not protect the per-token loop or the unvalidated ERC20 `.call` return value, leaving a narrower but still exploitable window, particularly for orders with multiple escrowed input tokens (one native + one ERC20, or a malicious/non-standard token contract).

### Recommendation
Rewrite `withdraw()` in `evm/tron/contracts/apps/IntentGatewayV2.sol` to follow strict checks-effects-interactions per token: decrement `_orders[body.commitment][token]` (and delete the fee slot) *before* making any external call, mirroring `IntentsBase._withdraw` in `evm/src/apps/intentsv2/IntentsBase.sol`. Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` calls with `SafeERC20.safeTransfer`, which already validates the return value. Additionally, add a `nonReentrant` (or transient reentrancy guard) to all externally reachable state-changing entry points (`placeOrder`, `cancelOrder`) as a defense-in-depth measure, consistent with the fix already applied to the main EVM `IntentGatewayV2`/`IntrinsicIntents`/`ExtrinsicIntents` contracts.

### Proof of Concept
1. Attacker calls `placeOrder` with `order.output.beneficiary`/`order.user` set to a malicious contract `M`, escrowing both a native-ETH input and an ERC20 input for the same commitment (same-chain order).
2. Attacker calls `cancelOrder(order, options)`. Since `isSameChain` is true and `order.user == msg.sender` (M's controller), the check passes and `withdraw(body, true)` is invoked directly with `beneficiary = M`.
3. Inside `withdraw`, `_filled[commitment]` is set, then the loop iterates `body.tokens`: on the native-ETH entry, `beneficiary.call{value: amount}("")` transfers ETH to `M`, triggering `M`'s `receive()`.
4. `M`'s `receive()` cannot re-enter `cancelOrder`/`onAccept` for the same commitment (blocked by `_filled`), but it can call arbitrary other contracts/functions during this callback — including manipulating a malicious ERC20 token contract placed as the second `body.tokens[1].token` so that its `transfer` callback (`.call`) executes attacker logic before `_orders[commitment][token] -= amount` runs for that slot, or returns a false success without reverting, causing the escrow accounting to diverge from actual balances (loss/freezing of the ERC20 escrow amount that was never really transferred but is treated as spent).

Note: I was unable to find a `fillOrder`/`_fillSameChain`/`_fillCrossChain` equivalent in `evm/tron/contracts/apps/IntentGatewayV2.sol` — this Tron variant only exposes `placeOrder`, `cancelOrder`, `onAccept`, and `onGetResponse`. This is unusual compared to the main EVM `IntentGatewayV2`, and I could not fully confirm from the index whether solver-side filling for Tron happens through a separate, un-indexed contract; this should be verified directly in the repository before treating the PoC path above as complete, since the destination-side fill flow (where a solver-supplied beneficiary is most attacker-controllable) may live elsewhere.

        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }
