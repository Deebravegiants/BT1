### Title
Webhook shop-domain spoofing allows cross-tenant webhook forgery via HMAC/identity mismatch - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while the `shop` value used to attribute the webhook to a tenant is read from a separate, unsigned header. Since the HMAC never covers the shop header, and the app's `api_secret_key` is shared across all shops installed on the app (it is not shop-specific), any party that receives one legitimate, validly-signed webhook (e.g. by installing the app on their own store) can replay the same body/HMAC pair while substituting the `shop-domain` header for any victim shop domain, and `Registry.process` will accept it as authentic.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is parsed straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, independently of the HMAC: [2](#0-1) 

`HmacValidator.validate_signature` verifies `computed_signature` (over `to_signable_string`, i.e. the body) against the received HMAC, never touching `shop`: [3](#0-2) 

`Registry.process` gates on that HMAC check alone, then forwards `request.shop` verbatim as the `shop` field of `WebhookMetadata` passed to the app's handler: [4](#0-3) 

The identity binding that should hold is: `bytes verified by HMAC == bytes that determine the tenant this webhook is attributed to`. Here that equality is broken — the verified bytes are `raw_body` only, while the tenant-determining bytes are the unauthenticated `shop-domain` header. Because `api_secret_key` is one secret per app (shared across every shop that installs the app, not per-tenant), an unprivileged party who legitimately installs the app on a store they control receives real webhooks with valid HMACs computed over bodies they can freely choose to interpret (e.g., an `orders/create` or `app/uninstalled` payload). They can then resend that exact `raw_body` + HMAC pair to the app's webhook endpoint with the `x-shopify-shop-domain` header changed to any victim shop domain. `Utils::HmacValidator.validate` still returns `true` (the body/HMAC pair is valid), and `Registry.process` calls the handler with `shop: <victim-domain>` and the attacker-controlled body, letting the attacker inject cross-tenant events attributed to a shop they don't control.

### Impact Explanation
This is a cross-tenant integrity/identity violation: an attacker can forge webhook events that the app will process as if they originated from a victim shop, without ever needing the app's `client_secret`. Depending on how the host application acts on `data.shop`/`data.body` (e.g., updating shop-specific records, triggering `app/uninstalled` cleanup, altering order state), this can cause cross-tenant data corruption or trigger actions on a shop the attacker does not own. This matches the "cross-tenant access" Critical impact category, since the attacker crosses the shop/tenant boundary using only a valid webhook they received for their own store.

### Likelihood Explanation
Likelihood is high for any app that installs the app on a shop the attacker controls (a normal, unprivileged capability — anyone can install a public/embedded Shopify app on their own development or trial store) and that exposes a webhook endpoint built per the documented pattern: [5](#0-4) 
No secret material, TLS interception, or social engineering is required — only capturing one legitimate webhook body+HMAC from a shop the attacker controls, then replaying it with a different shop header value.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the signed material, or otherwise cryptographically bind the header value to the verified request, before trusting `request.shop` in `Registry.process`. At minimum, document prominently that `data.shop` from `WebhookMetadata` is not covered by HMAC verification and must be cross-checked by the host application against a known/installed shop record before being trusted for any tenant-scoped action.

### Proof of Concept
1. Install the target app on `attacker-shop.myshopify.com` (a normal, unprivileged action).
2. Trigger any subscribed webhook (e.g. `orders/create`) and capture the raw POST body plus the `x-shopify-hmac-sha256` header sent by Shopify — this is a validly-signed message for the attacker's own shop.
3. Replay the exact same body and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but set `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` returns `true` because it only checks the body against the HMAC.
5. `Registry.process` invokes the app's handler with `WebhookMetadata#shop == "victim-shop.myshopify.com"` and the attacker-chosen body — the app now processes attacker-controlled data as if it came from the victim shop.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
