### Title
Webhook Shop/Topic/Metadata Spoofing via HMAC Covering Only the Raw Body — Cross-Tenant Webhook Forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#hmac` is validated only against the raw request body, while the `shop`, `topic`, `webhook_id`, and `api_version` values that `ShopifyAPI::Webhooks::Registry.process` hands to the host application's handler are read directly from unauthenticated HTTP headers. Because a single `api_secret_key` is shared across every shop that installs the app, any merchant (an unprivileged actor with respect to other tenants) can generate their own valid `(body, hmac)` pair on their own store and replay it to the app's webhook endpoint with a forged `shop-domain` header, causing the app to process attacker-chosen webhook content under a victim shop's identity.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

and `hmac` is derived purely from the `hmac-sha256` header: [2](#0-1) 

`shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from headers with no cryptographic binding to the body or to the HMAC: [3](#0-2) 

`HmacValidator.validate` checks only `verifiable_query.hmac` against `verifiable_query.to_signable_string` (i.e. the body), never the shop/topic headers: [4](#0-3) 

`Registry.process` validates that body-only HMAC and then immediately trusts the header-derived `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` when building `WebhookMetadata` for the handler: [5](#0-4) 

The identity binding that should hold is:
`hmac_valid(raw_body) == true` should imply `shop header == shop that produced raw_body`.

In reality, because the same app-wide `api_secret_key` signs *every* shop's webhooks, `hmac_valid(raw_body)` only proves "some shop belonging to this app produced this exact body" — it says nothing about *which* shop. An attacker who legitimately installs the app on their own shop can trigger webhooks with attacker-controlled body content (e.g. by editing an order, customer, or product on their own store, or via `shop/redact`/`customers/data_request` GDPR topics), capture the resulting valid `(raw_body, hmac)` pair, and replay it to the app's public webhook endpoint with the `x-shopify-shop-domain` (and `x-shopify-topic`/`x-shopify-webhook-id`) headers rewritten to name a victim shop. `Utils::HmacValidator.validate` still passes because it only re-computes the HMAC over the untouched body, and `Registry.process` forwards the forged `shop` value straight into the handler's `WebhookMetadata`.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce: `data.shop` in `WebhookMetadata` (documented as "The shop domain of the webhook") is not actually authenticated. Any host application that uses `data.shop` to select which tenant's database/session to act on — the pattern explicitly shown in the gem's own docs (`perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) — can be made to write, delete, or process attacker-controlled data under a victim shop's identity, e.g. spoofing a `shop/redact` or `customers/redact` GDPR compliance event, or injecting fabricated order/customer data attributed to a shop the attacker doesn't own. This is a cross-tenant access primitive reachable by any unprivileged merchant who can install the target app, without requiring `api_secret_key`, an access token, or any other credential belonging to the victim.

### Likelihood Explanation
Likelihood is high for any app author following the documented webhook handler pattern: any user can install a public Shopify app on a free/dev store, trigger a webhook with content they control, capture the outbound `(body, hmac)` pair (visible to them as the receiving app operator would log it, or observable via their own endpoint/proxy), and replay it against the shared webhook endpoint with a substituted `shop-domain` header. No additional secrets are required beyond normal app installation, which is an unprivileged action.

### Recommendation
- Include the shop domain (and ideally topic/webhook id) in the value that is HMAC-verified, or otherwise cryptographically bind the header-derived `shop` to the signed payload, instead of trusting header values that fall outside the HMAC's coverage.
- At minimum, document prominently that `data.shop` from `WebhookMetadata` is not authenticated by the HMAC check and that host applications must independently verify the shop is a known, currently-installed tenant before trusting webhook content for that shop (e.g., cross-check against a `shop` value obtained from a previously-established, trusted session store), and add a reference implementation of this check in `docs/usage/webhooks.md`.

### Proof of Concept
```ruby
# 1. Attacker installs the target app on their own shop "attacker-shop.myshopify.com"
#    and edits e.g. an order, causing Shopify to POST a legitimate webhook:
raw_body = '{"id":123,"note":"hello"}'
valid_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), APP_SHARED_SECRET, raw_body)
# attacker captures (raw_body, valid_hmac) — both derived only from data they control.

# 2. Attacker replays the exact same body+hmac to the app's public webhook endpoint,
#    but rewrites the shop header to a victim shop that also installed the app:
headers = {
  "x-shopify-topic"       => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(valid_hmac),
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged, not covered by HMAC
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)

# 3. Registry.process validates HMAC over raw_body only -> passes -> handler receives
#    WebhookMetadata(shop: "victim-shop.myshopify.com", body: attacker-controlled body)
ShopifyAPI::Webhooks::Registry.process(request)
# Host app's handler now believes attacker-controlled data originated from victim-shop.
