### Title
Excess native ETH sent to `EvmHost.dispatch()` / `fundRequest()` is refunded to the Host contract instead of the caller, permanently trapping funds - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` all accept `msg.value` and swap it for the protocol `feeToken` via `IUniswapV2Router02.swapETHForExactTokens`. None of these functions refunds any leftover native token to the original caller after the swap, matching the "excess ETH is not refunded" bug class from the external report (applied there to Nabla's price-feed update paths).

### Finding Description
In `dispatch(DispatchPost)`, when `msg.value > 0`, the full amount is forwarded to the Uniswap router to buy exactly `post.fee` worth of the fee token: [1](#0-0) 

The same pattern repeats in `dispatch(DispatchGet)`: [2](#0-1) 

and in `fundRequest`: [3](#0-2) 

Standard `UniswapV2Router02.swapETHForExactTokens` refunds any unspent ETH to `msg.sender` of the swap call. In all three functions, `EvmHost` itself is the caller of the router (it forwards `{value: msg.value}` from its own balance), so **the unspent ETH refund lands back in `EvmHost`'s balance, not the original user's wallet**. None of these three functions contains any subsequent logic that measures leftover ETH and forwards it to `_msgSender()`/`post.payer`. The excess ETH is therefore permanently trapped in the `EvmHost` contract.

This is not merely a theoretical concern — the SDK's LayerZero adapter comment explicitly (and incorrectly) assumes the caller gets the refund automatically: [4](#0-3) 

and applies a 2x buffer on `nativeFee` quotes specifically anticipating a refund that never reaches the original sender: [5](#0-4) 

Any of `IDispatcher.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, or `fundRequest`, all externally reachable `payable` entry points used by every app built on Hyperbridge (intents, token bridges, LZ adapter, arbitrary `HyperApp` contracts), can trigger this loss whenever a caller sends `msg.value` greater than the amount the Uniswap swap actually consumes — which is expected/likely given the documented use of quote buffers and inherent Uniswap slippage variance.

### Impact Explanation
Impact is High: any user or integrating application dispatching a POST/GET request or funding a request with native token payment permanently loses the unspent portion of `msg.value`. Because this is baked into the core dispatcher used across the entire EVM stack (all `HyperApp` contracts, `IntentGatewayV2`/`ExtrinsicIntents`, `HyperFungibleToken`, the LayerZero adapter), the affected surface is broad and the funds are unrecoverable — there is no sweep/withdraw path visible for these accidentally-received native balances distinct from protocol fee-token revenue withdrawal.

### Likelihood Explanation
Likelihood is Medium-High in practice: the documented usage pattern instructs callers to "Estimate Fees Off-Chain" and warns that `quote()` is subject to Uniswap slippage, and the LZ adapter deliberately applies a 2x buffer "to absorb ... markup," meaning overpayment of native value is the expected common case rather than an edge case, yet the refund mechanics do not return the excess to the actual payer.

### Recommendation
In `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest`, after calling `swapETHForExactTokens`, capture the returned `amounts[0]` (actual ETH consumed) and refund `msg.value - amounts[0]` to `_msgSender()` (or `post.payer`) via a low-level call, mirroring the refund pattern already implemented correctly in `IntentGatewayV2.sol` (`_sendValue(msg.sender, msgValue)`) and `UniV4UniswapV2Wrapper.sol`. Alternatively, add an admin-only sweep function for stray native balances as a fallback safety net.

### Proof of Concept
1. A user calls `IDispatcher(evmHost).dispatch{value: 1 ether}(post)` where `post.fee` only requires 0.1 ETH worth of feeToken via the configured Uniswap pool.
2. `EvmHost.dispatch` forwards the full `1 ether` to `swapETHForExactTokens{value: 1 ether}(post.fee, path, address(this), block.timestamp)`.
3. The Uniswap router consumes ~0.1 ETH and refunds the remaining ~0.9 ETH — but the refund destination is `msg.sender` as seen by the router, which is `EvmHost`, not the original user.
4. `dispatch` returns normally with `commitment` computed; no code path forwards the ~0.9 ETH back to the user.
5. The ~0.9 ETH remains permanently in `EvmHost`'s balance with no way for the user to reclaim it.

    function dispatch(DispatchPost memory post) external payable notFrozen returns (bytes32 commitment) {
        if (msg.value > 0) {
            address[] memory path = new address[](2);
            address uniswapV2 = _hostParams.uniswapV2;
            path[0] = IUniswapV2Router02(uniswapV2).WETH();
            path[1] = feeToken();
            IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
                post.fee, path, address(this), block.timestamp
            );
        } else if (post.fee > 0) {
            IERC20(feeToken()).safeTransferFrom(_msgSender(), address(this), post.fee);
        }
