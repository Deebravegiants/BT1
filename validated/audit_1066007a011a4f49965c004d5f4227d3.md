### Title
POA Bridge withdrawal status matching by `assetId` only causes duplicate/wrong completion reports in batch withdrawals - (File: `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`)

### Summary
When a caller submits a batch withdrawal (`sdk.processWithdrawal({ withdrawalParams: [...] })`) that contains two or more withdrawals of the *same* token (same `assetId`) to different destinations/amounts in a single NEAR intent transaction, `PoaBridge.describeWithdrawal` (and the equivalent helper in `internal-utils`) cannot distinguish between them. Both lookups resolve to the same underlying record from the POA Bridge status API, so the SDK can report the wrong (or duplicate) `status`/`txHash` for a given withdrawal index.

### Finding Description
`PoaBridge.describeWithdrawal` fetches all withdrawals tied to the NEAR tx hash and matches the *one relevant to this call* using `findMatchingWithdrawal`, which filters purely by `assetId`, ignoring `index`: [1](#0-0) [2](#0-1) 

The same pattern exists in the lower-level helper used elsewhere in `internal-utils`: [3](#0-2) [4](#0-3) 

The SDK explicitly supports batching multiple withdrawals into one intent/tx via `createWithdrawalIdentifiers`, which assigns a separate, per-bridge `index` to each withdrawal call and later polls status per index through `watchWithdrawal`/`createWithdrawalCompletionPromises`: [5](#0-4) [6](#0-5) 

Nothing in `createWithdrawalIdentifiers`, `PoaBridge.supports`, or `PoaBridge.createWithdrawalIntents` prevents two entries in `withdrawalParams` from sharing the same `assetId` while differing in `destinationAddress`/`amount` — this is exactly the documented batch-withdrawal usage pattern (README shows multiple withdrawals in one call), and nothing restricts the assets to be distinct.

Once such a tx settles on NEAR, `getWithdrawalStatusWithRetry` returns *all* withdrawal records for that tx hash from the POA indexer. `findMatchingWithdrawal` then does `withdrawals.find(w => nep141:${w.data.near_token_id} === assetId)`, which — for two withdrawals of the same token — always returns the **first** matching record in the API's array, regardless of which `index` (i.e., which of the two withdrawals) is actually being queried. The code comment even acknowledges this: [7](#0-6) 

This breaks the equality that `describeWithdrawal(wid_i)` must report the on-chain outcome specifically of withdrawal `i`. Instead, `describeWithdrawal(wid_0)` and `describeWithdrawal(wid_1)` for two same-asset withdrawals converge on the identical record, so:
- Both promises can resolve `completed` with the exact same `txHash`, even though only one of the two underlying transfers actually completed (or they completed to different destination chains/addresses with different amounts).
- An integrator relying on `sdk.waitForWithdrawalCompletion`/`createWithdrawalCompletionPromises` per-index results (as the SDK's own docs/RFC recommend, e.g. `if (index === 0) quoteEntity.destinationTx = tx.hash;` `if (index === 1) quoteEntity.refundTx = tx.hash;`) will record the same transaction hash for two logically distinct withdrawals, and may consider both "delivered" and credit/reconcile twice, while the second withdrawal's actual status is silently unobserved.

### Impact Explanation
This is a status/hash misreport that can cause an integrator to credit or reconcile a withdrawal twice, or attribute a destination tx hash to the wrong withdrawal (wrong amount/destination). Per the stated High-impact category ("a status or hash misreport making an integrator credit or refund twice"), this qualifies as High severity. It does not require any malicious actor — it triggers under the SDK's own documented, unprivileged, legitimate batch-withdrawal usage (two withdrawals of the same token in one call).

### Likelihood Explanation
Likelihood is real but conditional: it requires a batch withdrawal where at least two entries share the same `assetId` (POA-bridge-routed token) within a single intent transaction. The SDK's public README documents and encourages batch withdrawals, and does not disallow duplicate assets within a batch, nor does `PoaBridge.supports`/`createWithdrawalIntents` reject it. Any integrator batching multiple withdrawals of the same token (e.g., splitting a large withdrawal into two destinations for compliance/limits reasons) would trigger this.

### Recommendation
`findMatchingWithdrawal` (in both `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts` and `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts`) should disambiguate between multiple withdrawals of the same asset in a batch — e.g., by matching on `(assetId, destinationAddress, amount)` tuples, or, if the POA API exposes an ordering/sequence guarantee, by sorting both the API's returned withdrawals and the local `withdrawalParams` by amount (as the existing code comment already suggests) instead of relying on `assetId` alone. Until fixed, the SDK should either explicitly reject batches containing duplicate `assetId`s routed through the POA bridge, or surface a loud warning/error so integrators do not silently double-credit.

### Proof of Concept
1. Call `sdk.processWithdrawal({ withdrawalParams: [ { assetId: "nep141:usdt.tether-token.near", amount: 100n, destinationAddress: "0xAAA...", feeInclusive: false }, { assetId: "nep141:usdt.tether-token.near", amount: 200n, destinationAddress: "0xBBB...", feeInclusive: false } ] })`.
2. Both withdrawals route through `PoaBridge` (`RouteEnum.PoaBridge`) and get `index: 0` and `index: 1` respectively via `createWithdrawalIdentifiers`.
3. After NEAR intent settlement, the POA bridge indexer returns two withdrawal records for the same `withdrawal_hash` (tx hash), both with `near_token_id = "usdt.tether-token.near"`.
4. `PoaBridge.describeWithdrawal` is invoked for `wid_0` and `wid_1`; `findMatchingWithdrawal(response.withdrawals, "nep141:usdt.tether-token.near")` returns the same first-matching record for both calls (the code performs no filtering by amount/destination/index).
5. Both `createWithdrawalCompletionPromises` entries resolve using this same matched record's `transfer_tx_hash`/status, so an integrator persisting `destinationTx` per index (per the SDK's own documented pattern) stores the same tx hash for both the `0xAAA...` and `0xBBB...` withdrawals — one of which may not have actually completed, causing a duplicate "completed" credit.

		args: WithdrawalIdentifier & { logger?: ILogger },

		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(

			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}

	public createWithdrawalCompletionPromises(
		params: CreateWithdrawalCompletionPromisesParams,
	): Array<Promise<TxInfo | TxNoInfo>> {
		const { withdrawalParams, intentTx, signal, logger } = params;

		const widsPromise = createWithdrawalIdentifiers({
			bridges: this.bridges,
			withdrawalParams,
			intentTx,
		});

		// Track the last promise per HOT bridge landing chain for sequential waiting.
		// HOT bridge processes withdrawals sequentially per chain with ~30s gaps,
		// so polling in parallel would cause later withdrawals to timeout.
		const hotChainLastPromise = new Map<Chain, Promise<TxInfo | TxNoInfo>>();

		return withdrawalParams.map(async (_, index) => {
			const wids = await widsPromise;
			const entry = wids[index];
			assert(entry != null, `Missing wid for index ${index}`);

			// Only apply sequential waiting for HOT bridge
			if (entry.bridge.route === RouteEnum.HotBridge) {
				const landingChain = entry.wid.landingChain;
				const previousPromise = hotChainLastPromise.get(landingChain);

				const sequentialPromise = (async () => {
					if (previousPromise) {
						// Wait for previous withdrawal to same chain to complete.
						// Use allSettled to continue even if previous fails.
						await Promise.allSettled([previousPromise]);
					}
					return watchWithdrawal({
						bridge: entry.bridge,
						wid: entry.wid,
						signal,
						logger,
					});
				})();

				hotChainLastPromise.set(landingChain, sequentialPromise);
				return sequentialPromise;
			}

			// Non-HOT bridges: parallel polling (existing behavior)
			return watchWithdrawal({
				bridge: entry.bridge,
				wid: entry.wid,
				signal,
				logger,
			});
		});
