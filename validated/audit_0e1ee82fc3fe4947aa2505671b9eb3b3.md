### Title
Unconstrained router calldata + persistent unlimited allowance let an attacker sweep stranded/in-flight token balances out of `ExternalActionSwap` beyond the input amount Hinkal sent it - (File: `contracts/external-actions/swaps/ExternalActionSwap.sol`)

### Summary
When `circomData.relay == address(0)`, the flat fee withheld from the swap input (`inputAmount -= circomData.feeStructure.flatFee`) is never forwarded anywhere and is left sitting as the action contract's own token balance, because `sendToRelay` silently no-ops on `relay == address(0)`. Because `LifiExternalAction.callRouter` grants the LI.FI router a persistent, un-reset `type(uint256).max` allowance over the action contract's *entire* balance of `inputToken`, and the router calldata (`externalActionMetadata`) is fully attacker-controlled and never checked to actually consume only `inputAmount`, a subsequent attacker transaction can encode a router call that pulls more than the `inputAmount` Hinkal sent for that transaction - including the stranded residual - and have it credited to the attacker's own output UTXO.

### Finding Description
The broken equality is: **tokens leaving the action contract in a transaction must equal `-deltaAmountChanges` that Hinkal sent it for that transaction.** `ExternalActionSwap.swap` only measures the *output* side of this via a before/after balance diff of `outputToken`: [1](#0-0) 

It never measures or bounds the *input* side consumed from the contract's own balance of `inputToken`. `inputAmount` is only used to compute the intended amount: [2](#0-1) 

but `callRouter` just forwards `externalActionMetadata` verbatim to `router.call(...)` after granting unlimited allowance: [3](#0-2) 

The unlimited-allowance helper only re-approves when the current allowance is below half of `type(uint256).max`, so once granted it persists across transactions and is never scoped to the current `inputAmount`: [4](#0-3) 

Root cause of the "stranded residual": when `inputToken == feeStructure.feeToken`, the flat fee is subtracted from `inputAmount` before the swap, so that portion of the token Hinkal transferred into the action is never swapped: [5](#0-4) 

and `sendToRelay` is a no-op when `relay == address(0)`: [6](#0-5) 

so that flat-fee amount of `inputToken` simply remains as the action contract's own ERC20 balance after the transaction completes - it is neither swapped, sent to a relay, nor returned to Hinkal.

**Exploit flow:**
1. Attacker (or anyone) performs a LI.FI swap transaction through `Hinkal.transact` with `circomData.relay == address(0)` and `feeStructure.feeToken == erc20TokenAddresses[0]` (the input token), causing the flat fee to be stranded as a residual balance of that token inside the `LifiExternalAction`/`ExternalActionSwap` contract. This also leaves (or refreshes) a `type(uint256).max` router allowance on that token from the contract.
2. In a later transaction, the attacker submits their own valid Hinkal proof with a small legitimate `inputAmount` for the same `inputToken`, but crafts `externalActionMetadata` (fully attacker-controlled LI.FI calldata) that instructs the router to pull an amount greater than the `inputAmount` Hinkal transferred for this call - up to the full current balance of `inputToken` held by the action contract (their deposit + the stranded residual from step 1), since the router already holds unlimited allowance and nothing in `swap`/`callRouter` checks that only `inputAmount` was consumed.
3. `swappedAmount` is computed purely as `outputToken` balance-before/after diff, so it reflects the full swapped amount (deposit + stolen residual).
4. The resulting `utxoSet[0].amount` (`amountToSendToHinkal`) is transferred back to Hinkal and becomes the attacker's own shielded output UTXO, i.e. value that was never part of `-deltaAmountChanges` Hinkal sent the action for the attacker's transaction is captured as the attacker's own funds.

Existing guards do not prevent this: `performHinkalChecks`, `verifyProof`, nullifier/root checks, and the circuit's `inTotal + amountChanges === outTotal` constraint all operate on the *declared* `amountChanges`/`deltaAmountChanges` values from the attacker's own valid proof - none of them constrain what the LI.FI router calldata semantically does with the action contract's on-chain token balance, and the Solidity code itself has no input-side balance check analogous to the output-side `balanceBefore`/`getERC20OrETHBalance` diff.

### Impact Explanation
The attacker can extract value that the protocol/relay was owed (stranded flat fee) or any other stray/dust token balance sitting in the `ExternalActionSwap`/`LifiExternalAction` contract, routing it into their own shielded UTXO. At minimum this is theft of protocol/relay fee residue (High: "theft ... of protocol/relay fees"). Because the primitive is a general "pull more `inputToken` than `inputAmount` from the action's balance via unconstrained router calldata + persistent unlimited allowance," it is not strictly limited to fee residue - any balance the action contract happens to hold in that token when the malicious transaction lands (including funds momentarily in flight from another user's not-yet-completed transaction within the same block) could be swept the same way, which would escalate to Critical ("direct theft of shielded or in-flight user funds"). This is repeatable every time a residual/stray balance exists and the attacker can time a transaction against it.

### Likelihood Explanation
Preconditions: (a) at least one prior transaction with `circomData.relay == address(0)` and `feeStructure.feeToken` equal to the swap's input token (a normal, attacker-inducible/observable state, since the attacker can trigger their own prior swap to create the residual), and (b) the LI.FI router's calldata format allows specifying a pull amount independent of what the action-contract-side bookkeeping expects (a property of the real LI.FI router, but the exploit path through this repo's code is the missing input-side accounting/allowance scoping). Attacker cost is just gas plus the cost of running two of their own valid Hinkal transactions; no privileged role is needed at any step.

### Recommendation
- In `ExternalActionSwap.swap`, sweep or account for the leftover flat-fee token balance explicitly (e.g., always call `sendToRelay`/transfer it back into the Hinkal-tracked output regardless of `relay == address(0)`, or add it to `amountToSendToHinkal`/a UTXO instead of leaving it as bare contract balance).
- Scope router approvals to the exact `inputAmount` per call instead of an unlimited, persistent allowance (`approveToken` with reset-to-zero after use, not `approveUnlimited`), so a single call cannot draw down balances left over from unrelated transactions.
- Add an input-side balance check in `callRouter`/`swap` (balance-before vs balance-after of `inputToken`) asserting that exactly `inputAmount` (not more) left the contract, mirroring the existing output-side check.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `LifiExternalAction` (with a mock LI.FI router that supports `transferFrom`-style pulls using an existing allowance for an attacker-specified amount), and required verifiers/helpers with locally generated proofs.
2. Tx1: Attacker calls `Hinkal.transact` with a valid proof, `erc20TokenAddresses = [inputToken, outputToken]`, `relay = address(0)`, `feeStructure.feeToken = inputToken`, `feeStructure.flatFee = F > 0`. Assert after the tx: `inputToken.balanceOf(actionContract) == F` (the stranded residual) and router allowance for `inputToken` is `type(uint256).max`.
3. Tx2: Attacker calls `Hinkal.transact` again with a new valid proof declaring `deltaAmountChanges[0] = -D` (small legitimate deposit `D`), but crafts mock-router calldata in `externalActionMetadata` that pulls `D + F` from the action contract (using the pre-existing unlimited allowance) rather than `D`.
4. Assert: `swappedAmount`/`utxoSet[0].amount` corresponds to swapping `D + F`, not `D`, i.e. `amountToSendToHinkal > uint256(-deltaAmountChanges[0])` scaled by the swap rate - violating "tokens leaving the action == -deltaAmountChanges Hinkal sent it that tx." Assert `inputToken.balanceOf(actionContract)` drops to 0 (the residual `F` is gone), captured entirely in the attacker's resulting shielded output.
