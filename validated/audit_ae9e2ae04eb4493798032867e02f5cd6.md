### Title
Webhook shop identity spoofing via `shop-domain` header not covered by HMAC verification - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` only verifies the HMAC over the webhook's raw body, while the `shop` value handed to the app's webhook handler is parsed from an unauthenticated HTTP header. This breaks the identity binding: `HMAC-verified bytes == raw_body` but `shop identity used by handler == header bytes, never covered by the HMAC`. This is the same class of bug as the reported issue, where a value used for a security-relevant decision (`discountTimestampByPercent`) was decoupled from the value actually authenticated/initialized — here, the *tenant identity* used by the handler is decoupled from what the HMAC actually authenticates.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate`/`validate_signature` compute and compare the HMAC solely against `verifiable_query.to_signable_string`, i.e. only the raw body bytes: [2](#0-1) 

Meanwhile, `Request#shop` is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, which is never part of the signed payload: [3](#0-2) 

`Registry.process` validates the HMAC, then immediately builds `WebhookMetadata` using `request.shop` (the unauthenticated header) and hands it to the app's handler: [4](#0-3) 

Because Shopify's webhook HMAC secret (`api_secret_key`) is the **app's** shared secret — identical across every shop that has installed the app, not shop-specific — any shop that has installed the app can obtain genuinely-signed webhook bodies for its own store. An attacker who controls one installed shop (an "unprivileged" tenant relative to other merchants) can capture one of their own legitimately-signed webhook requests (valid `hmac-sha256` header for a given raw body) and replay it to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header value. Since that header is not covered by the HMAC, `Utils::HmacValidator.validate` still returns `true`, and the handler is invoked believing the webhook body belongs to the victim shop named in the forged header — even though the body content is really the attacker's own shop's data (or an attacker-influenced payload, for mandatory topics like `shop/redact` whose body an app might trust for destructive actions).

This exactly maps to the report's bug class: a check ("is this HMAC valid?") answers based on bytes (`raw_body`) that do not cover the field actually consumed downstream (`shop`), so the binding `verified_bytes == acted_on_field` is violated — identical in shape to `discountTimestampByPercent` being decoupled from the currently relevant discount tier in `PriceReturn.calculatePriceReturns`.

### Impact Explanation
This enables cross-tenant confusion: the webhook handler (and any app logic keyed on `data.shop`, e.g. looking up a stored session/token for that shop, deleting shop data on `shop/redact`, or updating shop-scoped records) can be tricked into acting on/for the wrong shop identity while still passing the gem's own authenticity check. Depending on how the host app uses `data.shop` (e.g. `shopify_app`'s reference pattern of looking up a shop record by that value and performing state changes), this can lead to cross-tenant data corruption or spoofed mandatory-compliance webhooks (`customers/redact`, `shop/redact`) being accepted as authentic for a shop the attacker does not own — satisfying the "cross-tenant access" Critical impact category. The vulnerability is in the gem's own `Webhooks::Request`/`Registry.process` API, not merely host misuse, since the gem itself asserts "This will verify the request did indeed come from Shopify" based solely on the body HMAC while simultaneously exposing/using the unverified `shop` field as the tenant identity.

### Likelihood Explanation
Requires no privileged credentials, no `api_secret_key` knowledge, and no TLS interception — only that the attacker controls one shop that has installed the target app (a normal, unprivileged merchant/user of the app), which is a realistic and low-barrier precondition for any public Shopify app. Capturing a self-owned webhook's raw body + HMAC and replaying it with a modified header is trivial (standard HTTP tooling).

### Recommendation
Bind the shop identity to the authenticated payload instead of trusting the header in isolation:
- Include the `shop-domain` (and ideally `topic`, `webhook-id`) header values in the HMAC-signable string (`to_signable_string`) so that `shop` is authenticated together with the body, or
- Independently verify that `request.shop` corresponds to a shop with an active, known installation before invoking the handler, or
- Document explicitly and enforce in the gem that `data.shop` must not be trusted as authenticated unless it is cryptographically bound to the payload, and give host apps a helper to validate shop/topic against the signed body.

### Proof of Concept
1. App developer installs their own test shop `attacker.myshopify.com` and registers a webhook (e.g. `shop/redact` or `orders/create`).
2. Shopify sends a webhook to the app with headers `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid HMAC of raw_body computed with the app's shared api_secret_key>`, and some `raw_body`.
3. Attacker captures this raw request, then re-sends it to the app's webhook endpoint unmodified except for `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses `shop` from the header as `"victim.myshopify.com"`; `to_signable_string` is unaffected (still `raw_body`).
5. `Utils::HmacValidator.validate` recomputes HMAC over `raw_body` with the app's `api_secret_key` — identical to step 2 — and returns `true`.
6. `Registry.process` invokes the handler with `WebhookMetadata.new(... shop: "victim.myshopify.com", body: <attacker's own shop's parsed body> ...)`, causing the app to act on/for `victim.myshopify.com` using attacker-controlled content, despite the HMAC check having "passed." [4](#0-3) [5](#0-4)
