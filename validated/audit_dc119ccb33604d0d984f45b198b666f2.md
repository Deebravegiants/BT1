### Title
Webhook shop-domain and topic identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while `shop`, `topic`, and `webhook_id` are read from unauthenticated HTTP headers. `Webhooks::Registry.process` accepts the request as long as the body's HMAC is valid, then hands the caller-supplied `shop` straight to the handler as the tenant identity, without that value ever being covered by the signature.

### Finding Description
`Utils::HmacValidator.validate` verifies a `VerifiableQuery` by recomputing an HMAC over `verifiable_query.to_signable_string` and comparing it to `verifiable_query.hmac`: [1](#0-0) 

For `Webhooks::Request`, `to_signable_string` returns only `@raw_body`: [2](#0-1) 

But `shop`, `topic`, and `webhook_id` are pulled directly from HTTP headers, which are not part of the signed content at all: [3](#0-2) 

`Webhooks::Registry.process` validates the HMAC and then, on success, forwards the header-derived, unauthenticated `request.shop` and `request.topic` directly to the registered handler as the trusted tenant/topic identity: [4](#0-3) 

This breaks the intended identity binding: `shop-domain header verified == shop-domain header used`. In this gem, only the body bytes are verified by the HMAC, but the `shop` (and `topic`/`webhook_id`) header value that the handler treats as ground truth for tenant scoping is never bound to that signature. Any request whose body+HMAC pair is valid (e.g., a genuine webhook delivery previously observed by an attacker who controls or monitors their own shop's endpoint) can be replayed with the `shop-domain` header rewritten to name a different, victim shop, and `Registry.process` will still accept it as authentic and dispatch it to the handler labeled with the attacker-chosen shop.

### Impact Explanation
Handlers registered via `Webhooks::Registry` (see `WebhookHandler`/`Registration`) receive `WebhookMetadata` built from `request.shop`, `request.topic`, and `request.parsed_body`, and typically use `shop` as the tenant key to look up sessions, write shop-scoped records, or trigger shop-scoped side effects. Because the HMAC never authenticates `shop`, an attacker can cause the app to process attacker-controlled webhook content under an arbitrary victim shop's identity, i.e., cross-tenant data injection/manipulation purely through this gem's webhook-processing path.

### Likelihood Explanation
Exploitation requires the attacker to obtain at least one valid `(raw_body, hmac-sha256 header)` pair — most straightforwardly by installing the app on a shop they control and observing/capturing a legitimate webhook Shopify sends them — and then replaying it against the shared webhook endpoint with a modified `shop-domain` (and optionally `topic`/`webhook-id`) header. No possession of the app's `client_secret` is required, only a body/HMAC pair that was legitimately generated for the attacker's own tenant, which they can obtain themselves. This is directly reachable through the gem's own `Webhooks::Request`/`Registry.process` code path, not through host-application misuse.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the signed content that `HmacValidator` verifies, or otherwise cryptographically bind those header values to the signature (e.g., require the host app to independently confirm the `shop-domain` against a known/expected registered shop before trusting `WebhookMetadata#shop`). At minimum, document clearly and enforce in the gem that `request.shop`/`topic` are unauthenticated and must not be trusted as tenant identity without an additional binding check.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker-shop.myshopify.com` and lets Shopify deliver a legitimate webhook to the app's callback URL, capturing the raw body `B` and the `X-Shopify-Hmac-Sha256` header value `H` (valid because `HmacValidator` only signs `B`).
2. Attacker POSTs to the same webhook endpoint with:
   - body `B` (unchanged)
   - header `X-Shopify-Hmac-Sha256: H` (unchanged)
   - header `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (rewritten)
3. `Webhooks::Request.new` accepts the headers/body, and `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `B` against `H`. [5](#0-4) 
4. The handler executes with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, even though that value was never part of the signed payload, letting the attacker inject content under the victim's tenant identity.
