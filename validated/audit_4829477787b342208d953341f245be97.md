### Title
Unfunded `recapitalize` overstates the cash book, so withdrawals pass the pool's liquidity guard and then revert inside the SAC transfer — freezing user funds - (File: contracts/pool/src/ops/recapitalize.rs)

### Summary
The pool's `withdraw` leg gates exits on the tracked `cash` bookkeeping value (`require_reserves`), not on the pool's real token balance. `recapitalize` credits `min(amount, backing_shortfall)` to cash and refunds the remainder to `payer` purely from the `amount` argument, on the assumption that the controller has already transferred `amount` into the pool. If a recapitalization is applied without the pool actually receiving `amount` tokens, the cash book overstates custody: subsequent withdrawals clear `InsufficientLiquidity`, then revert inside `token::transfer` for lack of balance, leaving suppliers unable to exit.

### Finding Description
- `Cache::require_reserves` compares the requested payout against the `cash` field only; no `token.balance()` check exists on the withdraw path. [1](#0-0) 
- `gate_and_debit` runs `require_reserves`, the utilization and backing guards, then `debit_cash`, and `apply` then calls `transfer_out`, which performs the real SAC `token.transfer` from the pool to `receiver`. [2](#0-1) [3](#0-2) 
- `recapitalize::accounting` computes `applied = amount.min(backing_shortfall)`, credits `applied` to cash, and sets `refund = amount - applied`; `apply` transfers `refund` to `payer`. The docstring states "The controller transfers `amount` into the pool before this call" — the pool never measures the inbound transfer. [4](#0-3) 
- The repository's own test demonstrates the end state: after an unfunded recapitalization drains custody while `cash` still claims solvency, a supplier's `withdraw` passes `require_reserves` and `PoolInsolvent` and then fails with the SAC's `BalanceError (10)` inside the token transfer, rolling the exit back. [5](#0-4) 

This is the direct analog of the external report: a balance-independent guard validates the exit, and the failure only surfaces at the token-transfer leg, reverting the whole withdrawal.

### Impact Explanation
Temporary freezing of funds. Suppliers holding real supply positions cannot withdraw: every exit attempt reverts in the SAC transfer after all pool guards pass. Their shares are not burned (Soroban rolls back atomically), but the assets are unwithdrawable until real custody is restored — matching the external report's "funds stuck, not lost" impact. It also blocks liquidation `seize` legs in `SeizeMode::Transfer` and `claim_revenue` payouts for the affected market.

### Likelihood Explanation
Reachability depends on the controller's `recapitalize` entrypoint (listed as an unprivileged-reachable path). The pool unconditionally trusts that the caller pre-funded `amount` and pays the `refund` leg from real custody regardless. If the controller's `recapitalize` does not pull the full `amount` of tokens from the payer into the pool before the pool call — or pulls less than `amount` — any unprivileged caller can create the book/custody divergence cheaply (in the extreme, receive an unfunded refund outright). I was unable to confirm the exact funding behavior of `contracts/controller/src/markets.rs::recapitalize` within this session; the pool-side defect (unverified inbound, refund paid from custody, withdraws gated on the inflated book) is fully proven by the code and the dedicated test.

### Recommendation
Reconcile custody against the book on the recapitalization path, and/or make outbound legs self-consistent:
- In `pool::recapitalize`, measure the actual inbound amount via `token.balance` deltas (as `flash_loan` already does with strict balance reconciliation) rather than trusting `amount`; set `applied`/`refund` from the measured receipt.
- Alternatively, have `transfer_out`/`require_reserves` use `min(cash, token.balance(pool))`, or cap the refund to the measured inbound excess, so the cash book can never authorize payouts exceeding real custody.

### Proof of Concept
1. Attacker calls controller `recapitalize(hub_asset, amount)` with `amount` larger than the market's `backing_shortfall`, while the pool receives less than `amount` in real tokens (unfunded or underfunded inbound leg).
2. Pool credits `applied = min(amount, shortfall)` to `cash` and refunds `amount - applied` to the attacker from custody (`recapitalize.rs:52-58`, `cash.rs:46-53`).
3. The pool's real `token.balance` is now below the `cash` book — the state the test `test_unfunded_recapitalize_leaves_the_cash_book_overstating_custody` reproduces.
4. Any supplier calling controller `withdraw` → `pool::withdraw` passes `require_reserves` (book still shows the funds) and then reverts with SAC `BalanceError` inside `token.transfer` — withdrawals are frozen until someone restores real custody.

/// reads the book, not the balance, so it admits exits that then fail inside
/// the SAC transfer. The market reports itself solvent and cannot pay.
#[test]
fn test_unfunded_recapitalize_leaves_the_cash_book_overstating_custody() {
    let t = TestSetup::new();
    let token = token::Client::new(&t.env, &t.asset);
    let token_admin = token::StellarAssetClient::new(&t.env, &t.asset);
    let payer = Address::generate(&t.env);
    let receiver = Address::generate(&t.env);

    // A legitimate supplier, with custody moved in as the controller would.
    let deposit = 10_000_000_000i128;
    token_admin.mint(&t.pool, &deposit);
    let supplied = t
        .client()
        .supply(&t.sup(0, deposit))
        .get_unchecked(0)
        .position
        .scaled_amount;
    assert_eq!(
        t.state_snapshot().cash,
        token.balance(&t.pool),
        "fixture guard: book and custody must still agree after the deposit"
    );

    // Drain every token via an unfunded refund.
    let custody = token.balance(&t.pool);
    t.client().recapitalize(&hub(&t.asset), &payer, &custody);
    assert_eq!(token.balance(&t.pool), 0, "custody is gone");

    let book = t.state_snapshot().cash;
    assert!(
        book >= deposit,
        "the book still claims more than the supplier's deposit: {book}"
    );

    // The supplier's exit clears the pool's own liquidity guard -- the book
    // says the cash is there -- and then fails in the token transfer.
    let outcome = t
        .client()
        .try_withdraw(&receiver, &false, &t.wdr(supplied, i128::MAX, 0));
    assert!(
        outcome.is_err(),
        "the withdraw cannot be paid, so it must fail"
    );
    // The failure must come from custody, not from a pool guard. The SAC
    // reports insufficient balance as its own contract error `BalanceError = 10`.
    // The asserts check that exact code and that neither pool liquidity guard
    // fired: `require_reserves` read the book and let the exit through.
    const SAC_BALANCE_ERROR: u32 = 10;
    match outcome {
        Err(Ok(err)) => {
            assert_ne!(
                err,
                Error::from_contract_error(CollateralError::InsufficientLiquidity as u32),
                "the pool's own liquidity guard must NOT be what stopped this -- \
                 it reads the cash book, which still shows the funds"
            );
            assert_ne!(
                err,
                Error::from_contract_error(CollateralError::PoolInsolvent as u32),
                "the pool's solvency guard must NOT be what stopped this either"
            );
            assert_eq!(
                err,
                Error::from_contract_error(SAC_BALANCE_ERROR),
                "the exit must fail inside the SAC transfer for want of custody"
            );
        }
        Err(Err(host_abort)) => panic!("expected a SAC contract error, got {host_abort:?}"),
        Ok(_) => unreachable!("asserted is_err above"),
    }
    assert_eq!(token.balance(&receiver), 0, "the supplier received nothing");
    assert_eq!(
        t.state_snapshot().cash,
        book,
        "the failed exit rolled back, so the book still overstates custody"
    );
}
