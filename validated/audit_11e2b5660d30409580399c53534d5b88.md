Audit Report

## Title
Full remaining fee credit is forfeited (not just `corrected_fee`) and misreported as `corrected_fee_with_tip` when a transaction's own dispatch kills the payer's account - ([File: substrate/frame/transaction-payment/src/payment.rs])

## Summary
In `FungibleAdapter::correct_and_deposit_fee`, when `frame_system::Pallet::<T>::account_exists(who)` returns `false` after dispatch, the code intentionally forwards the entire `remaining_credit` (the full pre-dispatch `fee_with_tip` minus tip credit) to `OU::on_unbalanceds` instead of splitting off only `corrected_fee` and attempting a refund of the excess. This is a deliberate "skip refund if account was killed by the tx" design choice, confirmed directly in the code, and it causes the payer to be charged more than `corrected_fee` when their own transaction removes all providers from their account.

## Finding Description
The withdrawal of `fee_with_tip` happens upfront in `withdraw_fee` using `Preservation::Preserve`, which only guards against the withdrawal itself killing the account — it does not prevent the account from being killed later by the call's own dispatch logic [1](#0-0) . In `correct_and_deposit_fee`, the branch taken depends on `frame_system::Pallet::<T>::account_exists(who)`: if true, `remaining_credit` is split into `corrected_fee` and a refundable excess that is resolved back to `who`; if false, the entire `remaining_credit` is used as `fee_credit` with no split attempted, per the explicit comment `// skip refund if account was killed by the tx` [2](#0-1) . This whole `fee_credit` (potentially equal to the full `fee_with_tip`) is then forwarded to `OU::on_unbalanceds`, and the function unconditionally returns `Ok(())` [3](#0-2) , so callers cannot detect that more than `corrected_fee_with_tip` was actually collected.

The exploit path is plausible: a user submits a call (e.g., "transfer all remaining balance", or any call that removes all providers as a side effect of its own logic) together with a `DispatchInfo` weight that overestimates actual execution weight, causing `corrected_fee < fee_with_tip`. Because the account is killed by the call itself (not by the fee withdrawal, which already preserved the account), `account_exists` is false at post-dispatch time, triggering the no-split branch and causing the full `fee_with_tip` to be forwarded rather than `corrected_fee`.

## Impact Explanation
This is a genuine, self-inflicted accounting deviation from the stated invariant that fee correction should not confiscate more than `corrected_fee`. The excess amount (`fee_with_tip - corrected_fee`) is unconditionally donated to `OU::on_unbalanceds` rather than refunded or accounted for, and the on-chain `TransactionFeePaid` event (constructed by the runtime from `corrected_fee_with_tip` before calling `correct_and_deposit_fee`) does not reflect the larger amount actually taken, creating an observable discrepancy between reported and actual fee collection. It is not theft from other accounts and does not create insolvency; the affected party is the same user whose action caused the account to be killed, and the impact is bounded by the delta between declared/refundable weight and actual weight for that single transaction.

## Likelihood Explanation
This is reachable by any unprivileged signed user without special privileges, races, or governance action — they only need to submit a self-draining/self-emptying call with an overestimated weight. It is deterministic given the described conditions and does not rely on victim mistakes beyond the account owner choosing to drain their own account within the same transaction that pays fees. The behavior is also explicitly acknowledged as intentional in the code comment, indicating a known trade-off (favoring implementation simplicity over exact refund correctness in this specific killed-account edge case) rather than an accidental bug, and the existing PoC pattern used for the analogous asset-conversion-tx-payment pallet (`asset_account_killed_post_withdraw_emits_full_fee_event`) confirms this is an established/tested code path rather than a hidden defect.

## Recommendation
When `account_exists(who)` is `false` post-dispatch, still attempt to split `remaining_credit` at `corrected_fee` and try `F::resolve(who, refund_credit)` (which will naturally fail gracefully back into `fee_credit` if the account cannot be resurrected below the existential deposit, mirroring the existing `Err(not_refunded)` handling in the `account_exists` branch), so that any calls where a refund could still succeed (or where only a small excess exists) are not needlessly forfeited. Alternatively/additionally, emit a distinguishing event when the killed-account branch is taken and the forwarded amount exceeds `corrected_fee`, so the mismatch between `TransactionFeePaid`'s `actual_fee` and the amount truly collected is observable on-chain rather than silently absorbed.

## Proof of Concept
As outlined in the report: configure a mock runtime using `FungibleAdapter` with a call that transfers away the account's entire balance (removing all providers) combined with a `DispatchInfo` weight larger than the actual post-dispatch weight so `corrected_fee < fee_with_tip`; run `withdraw_fee`, execute the call, then `correct_and_deposit_fee`; assert `account_exists(who)` is `false`, that the amount forwarded to the mock `OnUnbalanced` handler equals `fee_with_tip` (not `corrected_fee`), and that `TransactionFeePaid`'s `actual_fee` (`corrected_fee_with_tip`) is strictly less than the amount actually deducted from the user. This mirrors the existing `asset_account_killed_post_withdraw_emits_full_fee_event` test present in `substrate/frame/transaction-payment/asset-conversion-tx-payment/src/tests.rs` for the analogous asset-conversion adapter, confirming the same pattern applies to `FungibleAdapter` in `substrate/frame/transaction-payment/src/payment.rs`.
