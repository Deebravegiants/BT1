### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing tenant impersonation in `ShopifyAPI::Webhooks::Request` - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then passes the `shop` value taken from an unauthenticated HTTP header straight to the handler as the tenant identity. The HMAC never covers the shop domain, so the "authenticated" bytes (body) and the "acted-upon" identity (shop header) are not bound together.

### Finding Description
`Utils::HmacValidator.validate` computes `HMAC(api_secret_key, verifiable_query.to_signable_string)` and compares it to the `hmac` header value: [1](#0-0) 

For webhooks, `Request#to_signable_string` returns only `@raw_body`: [2](#0-1) 

But `Request#shop` is read from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, which participates in no cryptographic check at all: [3](#0-2) 

`Registry.process` validates the HMAC (over body only) and then forwards `request.shop` — the unauthenticated header — directly as the tenant identity to the app's handler: [4](#0-3) 

The handler receives a `WebhookMetadata` struct whose `shop` field is exactly this unauthenticated value and is expected to be trusted as "which merchant this event is about": [5](#0-4) 

This is precisely the identity-binding class described in the analog report: the field the code *acts on* (the `shop` used to route/attribute the webhook to a specific tenant) is *not covered* by the HMAC that is supposed to authenticate the message. The equality the code assumes is:

`shop used for tenant attribution == shop the signature was computed for`

but what is actually checked is only:

`HMAC(secret, body) == received_hmac`

with `shop` entirely outside that computation. Because the same app-level `api_secret_key` signs webhooks for *every* shop that installs the app, any body+hmac pair that is valid for one shop (e.g., captured from a webhook legitimately delivered to a merchant's own endpoint, or from a shop the attacker controls) remains a valid signature no matter what `shop-domain` header value accompanies it. An attacker who installs the target app on their own shop can capture a legitimately-signed webhook (body + hmac) from their own tenant and resend it to the host application's webhook endpoint with the `shop-domain` header rewritten to a victim shop, and `Registry.process` will accept it as authentic and hand it to the handler as if it were an event for the victim tenant.

### Impact Explanation
This breaks the cross-tenant boundary the gem's webhook verification is supposed to enforce: an unprivileged attacker who is merely a legitimate installer of the app for their own shop can forge webhook deliveries that are attributed to a *different* merchant's shop, without ever needing the app's `client_secret`/`api_secret_key`. Depending on how the host app's handler uses `WebhookMetadata#shop` (e.g. `app/uninstalled`, `shop/redact`, `customers/data_request`, billing or subscription events), this enables cross-tenant data manipulation, forced "uninstall"/redaction actions against a victim shop, or injection of attacker-controlled body content attributed to a victim tenant — a cross-tenant access impact.

### Likelihood Explanation
Any app that uses `ShopifyAPI::Webhooks::Registry.process`/`Request` as documented is affected, and the only precondition is that the attacker be able to install the app on a shop they control (a normal, unprivileged capability for any Shopify merchant) and be able to POST to the app's public webhook endpoint (which by design is a public, unauthenticated endpoint). No leaked secrets, TLS interception, or privileged access is required — only the gem's own verification logic is used.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the HMAC-signed material, or otherwise authenticate the shop header against the signature before trusting it. Concretely, `Request#to_signable_string` should incorporate the shop domain header (or the verification should independently confirm that the signing key corresponds to the shop claimed in the header) rather than relying on body-only HMAC while trusting an unauthenticated header for tenant attribution in `Registry.process`.

### Proof of Concept
1. Attacker installs the vulnerable app on `attacker-shop.myshopify.com`, a shop they control.
2. Shopify sends a legitimately HMAC-signed webhook (e.g. `app/uninstalled`) to the app's public webhook endpoint for `attacker-shop.myshopify.com`; attacker captures `raw_body` and the `x-shopify-hmac-sha256` header.
3. Attacker resends the same `raw_body` and `hmac` value to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` recomputes `HMAC(api_secret_key, raw_body)`, which still matches, because the shop header was never part of the signed string (`lib/shopify_api/webhooks/request.rb#to_signable_string`).
5. `Registry.process` calls the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: "app/uninstalled", ...)`, causing the host app to perform the `app/uninstalled` action against the victim's tenant data.
