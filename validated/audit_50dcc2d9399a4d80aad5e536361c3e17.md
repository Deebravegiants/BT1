## Summary

The BakerFi bug reduces to one custody invariant: **every path that credits value to a recipient must pass through the same recipient-authorization check**; if one privileged/asset-creation path skips the check that the normal transfer path enforces, a non-whitelisted address can end up holding assets.

Aptos' Fungible Asset (FA) standard implements exactly this kind of pluggable recipient-authorization mechanism via **dispatchable deposit hooks**, and the framework itself documents "Transfer allowlist: token can only be transferred to addresses in the allow list" as an intended use case for this hook [1](#0-0) . The finding below shows that this custody control is not uniformly enforced across all deposit entry points in `aptos_framework::fungible_asset`.

## Candidate paths considered

1. `object::transfer_raw` / `verify_ungated_and_descendant` ownership-chain walk — checked, ownership and `allow_ungated_transfer` gating look internally consistent [2](#0-1) .
2. `multisig_account` execution/quorum flow — checked, `assert_is_owner` and quorum/timelock checks are applied consistently across all mutating entry points [3](#0-2) .
3. `object_code_deployment::upgrade`/`freeze_code_object` — checked, both consistently assert `object::is_owner` before acting [4](#0-3) .
4. **`fungible_asset::mint_to` / `deposit_with_ref` bypassing the dispatchable deposit hook that implements custody/whitelist logic** — kept as the strongest candidate, detailed below.

## Title
Inconsistent enforcement of dispatchable deposit hooks lets `MintRef`/`TransferRef` deposits bypass whitelist/compliance custody logic - (File: aptos-move/framework/aptos-framework/sources/fungible_asset.move)

## Summary
`aptos_framework::fungible_asset` lets a Fungible Asset issuer register a custom deposit hook (via `dispatchable_fungible_asset::register_dispatch_functions`) to implement recipient-side custody controls such as an allowlist/whitelist, exactly like the whitelist BakerFi enforces on `VaultBase` deposits. However, `fungible_asset::mint_to` and `fungible_asset::deposit_with_ref` deposit directly via `unchecked_deposit`, **never invoking the registered deposit hook**, while the "normal" path (`fungible_asset::deposit` / `dispatchable_fungible_asset::deposit`) does invoke it. This mirrors the BakerFi finding precisely: recipients are validated on one deposit path but not on another.

## Finding Description
- The framework documents the deposit hook's purpose explicitly as an allowlist mechanism: "Transfer allowlist: token can only be transferred to addresses in the allow list" [5](#0-4) .
- The "safe" deposit path is `fungible_asset::deposit`, which calls `deposit_sanity_check(store, true)` with `abort_on_dispatch = true`; if a custom deposit function is registered it **aborts**, forcing callers to use `dispatchable_fungible_asset::deposit`, which actually invokes the custom hook [6](#0-5) [7](#0-6) .
- `fungible_asset::mint_to`, however, calls `deposit_sanity_check(store, false)` (`abort_on_dispatch = false`) and then goes straight to `unchecked_deposit`, **skipping the hook call entirely** regardless of whether a deposit hook is registered [8](#0-7) .
- `deposit_sanity_check` only ever verifies the *native* `FungibleStore.frozen` boolean; it has no knowledge of any custody state the token's custom hook may keep separately (e.g., a `SmartTable` allowlist) [9](#0-8) .
- `fungible_asset::deposit_with_ref` (used with a `TransferRef`) is even more permissive: it bypasses both the frozen check and the hook [10](#0-9) .

So, for any FA whose issuer implements recipient authorization purely inside the custom deposit hook (as the framework's own documentation suggests doing for an "allowlist"), calling `MintRef::mint_to(store, amount)` or `TransferRef::deposit_with_ref` deposits new/existing supply into `store` **without ever running the allowlist check**, exactly as `VaultBase`'s missing receiver check let non-whitelisted addresses receive shares while other paths enforced the whitelist.

Note on scope of confidence: the on-chain `usdk.move` stablecoin example in this repo happens to implement its denylist via the *native* `frozen` flag (which `mint_to`'s sanity check still honors) and additionally re-checks the denylist manually inside its own `mint` entry function before calling `deposit_with_ref` [11](#0-10) , so that particular example is not itself exploitable. The vulnerability is in the framework's inconsistent enforcement contract, not in that example's usage of it — any FA issuer who (reasonably, per the framework's own "Transfer allowlist" documentation) implements the allowlist purely in the deposit hook, without separately re-checking it before every `mint_to`/`deposit_with_ref` call, is exposed.

## Impact Explanation
If a live FA's compliance/whitelist logic lives only in its dispatchable deposit hook, any code path in that FA's own module that calls `fungible_asset::mint_to` or `deposit_with_ref` directly (a very natural pattern, since these are the "privileged" ref-based primitives issuers are expected to use for minting/administrative transfers) will silently mint/deposit tokens to disallowed or unintended recipients, corrupting the custody/holder-identity invariant the issuer relies on. This is a supply/custody accounting corruption that moves value to the wrong holder, matching the required impact class.

## Likelihood Explanation
Medium. The bug requires an FA issuer to place custody-relevant logic (allowlist, KYC, rate limits) exclusively in the deposit hook without also gating `mint_to`/`deposit_with_ref` call sites — a design choice the framework's own comments actively encourage ("Transfer allowlist" as the headline dispatch use case), making this a plausible, repeatable footgun across issuers building compliant stablecoins/tokens on Aptos, rather than a one-off misuse.

## Recommendation
Make `fungible_asset::mint_to` and `deposit_with_ref` consistent with `deposit`'s hook-enforcement contract: either always invoke the registered deposit hook when one exists (mirroring `dispatchable_fungible_asset::deposit`), or clearly force these ref-based entry points to abort when a deposit hook is registered (as `abort_on_dispatch = true` already does for `deposit`), so issuers cannot unknowingly create a second, hook-bypassing deposit path. At minimum, framework documentation for `mint_to`/`deposit_with_ref` should explicitly warn that dispatchable deposit hooks (including allowlist logic) are bypassed.

## Proof of Concept
1. Issuer creates FA `X` with `create_primary_store_enabled_fungible_asset`, generates `MintRef`, and registers a deposit hook via `dispatchable_fungible_asset::register_dispatch_functions` that checks an off-store `SmartTable<address, bool>` allowlist before calling `fungible_asset::deposit_with_ref` internally (per the framework's documented "Transfer allowlist" pattern) [1](#0-0) .
2. A normal user transfer via `primary_fungible_store::transfer` → `dispatchable_fungible_asset::transfer` correctly invokes the deposit hook and rejects non-allowlisted recipients [12](#0-11) .
3. Issuer's own `mint(admin, to, amount)` entry function calls `fungible_asset::mint(&mint_ref, amount)` then `fungible_asset::mint_to(&mint_ref, to_store, amount)` directly instead of routing through the dispatch hook.
4. `mint_to` calls `deposit_sanity_check(store, false)` — passes because `to_store.frozen == false` — then `unchecked_deposit` credits `to_store` directly; the allowlist `SmartTable` check inside the custom deposit hook is never executed [8](#0-7) .
5. Result: a non-allowlisted `to` address receives minted tokens, which it can freely hold/transfer among other non-allowlisted addresses, defeating the custody control — the same outcome as the BakerFi `VaultBase` finding.

        }
    }

    /// This checks that the destination address is eventually owned by the owner and that each
    /// object between the two allows for ungated transfers. Note, this is limited to a depth of 8
    /// objects may have cyclic dependencies.
    fun verify_ungated_and_descendant(owner: address, destination: address) {
        let current_address = destination;
        assert!(
            exists<ObjectCore>(current_address),
            error::not_found(EOBJECT_DOES_NOT_EXIST),
        );

        let object = borrow_global<ObjectCore>(current_address);
        assert!(
            object.allow_ungated_transfer,
            error::permission_denied(ENO_UNGATED_TRANSFERS),
        );

        let current_address = object.owner;
        let count = 0;
        while (owner != current_address) {
            count += 1;
            assert!(count < MAXIMUM_OBJECT_NESTING, error::out_of_range(EMAXIMUM_NESTING));
            // At this point, the first object exists and so the more likely case is that the
            // object's owner is not an object. So we return a more sensible error.
            assert!(
                exists<ObjectCore>(current_address),
                error::permission_denied(ENOT_OBJECT_OWNER),
            );
            let object = borrow_global<ObjectCore>(current_address);
            assert!(
                object.allow_ungated_transfer,
                error::permission_denied(ENO_UNGATED_TRANSFERS),
            );
            current_address = object.owner;
        };
    }
