The docs confirm that `begin_auth`'s `shop` input, exactly like `client_credentials`'s, is documented as "A Shopify domain name in the form `{exampleshop}.myshopify.com`" (`docs/usage/oauth.md` lines 151 and 291), and the example wiring for `begin_auth` takes the shop straight from an attacker-controlled request header (`shop = request.headers["Shop"]`). This confirms `begin_auth` has no validation guard equivalent to `client_credentials`'s `Utils::ShopValidator.sanitize!` call.

### Title
`begin_auth` builds the OAuth authorize URL from an unsanitized `shop` while `client_credentials` requires `Utils::ShopValidator.sanitize!` - ([File: lib/shopify_api/auth/oauth.rb])

### Summary
`Oauth.begin_auth` passes the caller-supplied `shop` directly into `auth_base_uri(shop)` to build `https://#{shop}/admin/oauth/authorize?...`, with no domain validation, whereas `ClientCredentials.client_credentials` and `RefreshToken`/`TokenExchange` all call `Utils::ShopValidator.sanitize!(shop)` first and raise `Errors::InvalidShopError` on non-Shopify domains. This breaks the intended invariant that every OAuth-family entrypoint accepts the same class of `shop` strings.

### Finding Description
The claimed binding is: `shop` accepted by `Oauth.begin_auth` == `shop` accepted by `ClientCredentials.client_credentials` == `shop` accepted by `RefreshToken`/`TokenExchange` (all gated by `Utils::ShopValidator.sanitize!`, which restricts hosts to `TRUSTED_SHOPIFY_DOMAINS` — `shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev` — [1](#0-0) ).

Tracing `begin_auth`: it takes `shop` as a raw `String`, builds a `state`/cookie, and computes `auth_route = auth_base_uri(shop) + "/oauth/authorize?..."`, where `auth_base_uri` does `"https://#{shop}/admin"` unless a dev-only `.my.shop.dev` branch applies [2](#0-1) [3](#0-2) . No call to `Utils::ShopValidator.sanitize!` appears anywhere in `begin_auth` or `auth_base_uri`.

By contrast, `client_credentials` calls `validated_shop = Utils::ShopValidator.sanitize!(shop)` before constructing the session or making any request, raising `Errors::InvalidShopError` for any `shop` whose host is not one of the trusted Shopify domains [4](#0-3) . The same guard is used by `refresh_token.rb` and `token_exchange.rb` (confirmed via grep matches on `Utils::ShopValidator`), showing `client_credentials` is not an outlier — `begin_auth` is.

The attacker-facing path: the gem's own documentation shows apps wiring `begin_auth` directly from a request-controlled value, e.g. `shop = request.headers["Shop"]` then `ShopifyAPI::Auth::Oauth.begin_auth(shop: domain, redirect_path: "/auth/callback")` [5](#0-4) . An unprivileged attacker who controls this header/param (e.g., via a query param `shop=evil.attacker.example.com` in a login-initiation request that a host app naively forwards) causes `begin_auth` to return `auth_route: "https://evil.attacker.example.com/admin/oauth/authorize?client_id=<real client_id>&scope=...&redirect_uri=<real host>/auth/callback&state=<real state>"`. The app then 307-redirects the victim's browser to that attacker-controlled host, leaking the app's `client_id`, requested `scope`, and the legitimate `redirect_uri` in the URL to a non-Shopify server, and can be used to phish/social-engineer the merchant since the URL structure looks like a legitimate OAuth kickoff. This is a classic unvalidated-redirect / SSRF-style trust boundary break enabled purely by the omission of `ShopValidator.sanitize!` in `begin_auth`.

Existing guards do not stop this: `Context.setup?` and `Context.private?` checks only validate app configuration, not the `shop` value [6](#0-5) ; `HmacValidator.validate` and the `state` comparison only apply in `validate_auth_callback`, which runs after redirection and does not gate `begin_auth`; Sorbet's `sig` only enforces `shop: String`, not domain shape.

### Impact Explanation
The client's `client_id`, requested OAuth `scope`, and real `redirect_uri` are sent, embedded in a redirect, to a host of the attacker's choosing — this is High-severity per the rubric's "SSRF driving an authenticated request to an unintended host" / forced-redirect category, since the browser (acting on behalf of the merchant/victim) is redirected off-platform carrying app configuration values. This is repeatable against any shop/user that triggers the login flow with an attacker-supplied `shop` value, and the blast radius spans every merchant whose login endpoint forwards an unvalidated `shop` parameter to `begin_auth`, since the gem does not stop it.

### Likelihood Explanation
Exploitability depends on the host application passing a user/request-controlled `shop` value into `begin_auth` without its own validation — which is exactly the pattern shown in this gem's own `docs/usage/oauth.md` example (`shop = request.headers["Shop"]`). No credentials, secrets, or privileged access are needed; the attacker only needs to control the `shop` value sent to the login-initiation endpoint (a header or query param), which matches the stated unprivileged-attacker capability set. Given the gem provides `ShopValidator.sanitize!` and uses it in three of the four OAuth-family entrypoints but omits it from `begin_auth`, the likelihood of real-world apps being unprotected is high — they'd reasonably assume the gem enforces this consistently, as it does elsewhere.

### Recommendation
In `lib/shopify_api/auth/oauth.rb`, validate `shop` in `begin_auth` via `Utils::ShopValidator.sanitize!(shop)` (mirroring `client_credentials`) before using it to build `auth_base_uri`, raising `Errors::InvalidShopError` for untrusted domains, consistent with the rest of the OAuth-family entrypoints.

```ruby
class OauthShopValidationDivergenceTest < Minitest::Test
  INVALID_SHOPS = [
    "evil.attacker.example.com",
    "myshopify.com.evil.com",
    "not-a-shop",
  ]

  def setup
    ShopifyAPI::Context.setup(
      api_key: "key", api_secret_key: "secret",
      scope: ["read_products"], host_name: "app.example.com",
      is_embedded: false, is_private: false, api_version: "unstable",
    )
  end

  def test_client_credentials_rejects_invalid_shop_but_begin_auth_accepts_it
    INVALID_SHOPS.each do |bad_shop|
      assert_raises(ShopifyAPI::Errors::InvalidShopError) do
        ShopifyAPI::Auth::ClientCredentials.client_credentials(shop: bad_shop)
      end

      result = ShopifyAPI::Auth::Oauth.begin_auth(shop: bad_shop, redirect_path: "/cb")
      assert result[:auth_route].start_with?("https://#{bad_shop}/admin/oauth/authorize"),
        "begin_auth built an authorize URL against untrusted host #{bad_shop}, " \
        "while client_credentials correctly rejected the same shop value"
    end
  end
end
```
This demonstrates the divergence: `client_credentials(shop: bad_shop)` raises `Errors::InvalidShopError` for each invalid shop, while `begin_auth(shop: bad_shop, ...)` succeeds and returns an `auth_route` pointing at the attacker-controlled host, proving the two entrypoints do not enforce the same `shop` trust boundary.

```ruby
        def begin_auth(shop:, redirect_path:, is_online: true, scope_override: nil)
          scope = if scope_override.nil?
            ShopifyAPI::Context.scope
          elsif scope_override.is_a?(ShopifyAPI::Auth::AuthScopes)
            scope_override
          else
            ShopifyAPI::Auth::AuthScopes.new(scope_override)
          end

          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = SecureRandom.alphanumeric(NONCE_LENGTH)

          cookie = SessionCookie.new(value: state, expires: Time.now + 60)

          query = {
            client_id: ShopifyAPI::Context.api_key,
            scope: scope.to_s,
            redirect_uri: "#{ShopifyAPI::Context.host}#{redirect_path}",
            state: state,
            "grant_options[]": is_online ? "per-user" : "",
          }

          query_string = URI.encode_www_form(query)
          auth_route = auth_base_uri(shop) + "/oauth/authorize?#{query_string}"

          { auth_route: auth_route, cookie: cookie }
        end
```

```markdown
class ShopifyAuthController < ApplicationController
  def login
    shop = request.headers["Shop"]

    # Builds the authorization URL route to redirect the user to
    auth_response = ShopifyAPI::Auth::Oauth.begin_auth(shop: domain, redirect_path: "/auth/callback")

    # Store the authorization cookie
    cookies[auth_response[:cookie].name] = {
      expires: auth_response[:cookie].expires,
      secure: true,
      http_only: true,
      value: auth_response[:cookie].value
    }

    # Redirect the user to "auth_response[:auth_route]" to allow user to grant the app permission
    # This will lead the user to the Shopify Authorization page
    head 307
    response.set_header("Location", auth_response[:auth_route])
  end
```
