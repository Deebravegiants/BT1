### Title
Webhook `shop` (tenant identifier) is read from an unauthenticated header and is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#shop` is populated from the `X-Shopify-Shop-Domain` HTTP header, but `Request#to_signable_string` (the data that `HmacValidator` signs/verifies) is only the raw request body. `Registry.process` validates the HMAC and then trusts `request.shop` to build the `WebhookMetadata` passed to the app's handler, without ever checking that the `shop` header is bound to the HMAC-signed payload.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes `HMAC(client_secret, verifiable_query.to_signable_string)` and compares it to `verifiable_query.hmac` [1](#0-0) . For webhooks, `to_signable_string` returns only `@raw_body` [2](#0-1) , while `shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight out of HTTP headers via `shopify_header` with no cryptographic binding to the signed body [3](#0-2) .

`Registry.process` only checks `Utils::HmacValidator.validate(request)` (i.e., that the body's HMAC matches) and then immediately builds `WebhookMetadata` using `request.shop`, `request.topic`, etc., handing it to the app-registered handler: [4](#0-3) .

This breaks the intended identity binding: `shop` (the field acted upon / used for tenant attribution) is not covered by the HMAC that authenticates the request as genuinely originating from Shopify for that specific shop. The equality that should hold is `hmac_signed_bytes == bytes_containing(shop)`, but here `hmac_signed_bytes == raw_body` while `shop` is sourced independently from a header.

Because an attacker who owns/operates any legitimate Shopify store can freely control the content that ends up in body fields for their own shop's webhooks (product titles, order notes, customer fields, etc.), and Shopify will compute and send a fully valid HMAC over that body to the attacker's own registered endpoint, the attacker possesses a `(raw_body, valid_hmac)` pair they fully control. They can then replay that exact body + HMAC to the shared webhook endpoint of a multi-tenant app while substituting the `X-Shopify-Shop-Domain` header for a victim shop. `HmacValidator.validate` will still pass because it only checks the body, and `Registry.process` will invoke the handler with `shop: <victim-shop>` alongside attacker-controlled body content — a tenant/shop confusion.

### Impact Explanation
This is a cross-tenant boundary violation: an app's webhook handler is told the event belongs to shop B (victim) while the payload content is attacker-controlled data from shop A. Depending on how the host application uses `data.shop` (e.g., looking up the victim's session/access token to process the "webhook" and take shop-scoped actions, or writing attacker-controlled data into the victim shop's records), this can lead to cross-tenant data corruption or actions being taken against a shop that never sent that webhook. This matches the rules' Critical bucket ("cross-tenant access").

### Likelihood Explanation
Requires only that the attacker control any legitimate Shopify store to obtain valid `(body, hmac)` pairs from Shopify's own webhook delivery — no possession of the app's `client_secret`, access token, or other privileged credential is required. The webhook endpoint is typically a single shared, unauthenticated-by-tenant route (`docs/usage/webhooks.md` example shows one controller action processing all shops' webhooks), making the header swap trivial for anyone who can reach that HTTP endpoint.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the HMAC-verified material, or otherwise cryptographically/structurally tie the shop identity to the signed payload — e.g., include the shop domain in the signable string, or require the webhook path itself to embed and independently validate the destination shop rather than trusting the `X-Shopify-Shop-Domain` header on its own.

### Proof of Concept
1. Attacker registers webhooks (e.g., `orders/create`) on the app for their own shop `attacker.myshopify.com`, pointing at the app's public webhook callback URL.
2. Attacker triggers an event on their own store causing Shopify to POST a webhook: raw body `B` and header `X-Shopify-Hmac-Sha256: H` where `H = HMAC(client_secret, B)`.
3. Attacker intercepts/logs this delivery (they control the destination endpoint, so this is simply their own server logs) and replays a POST to the same webhook endpoint, using the identical raw body `B` and `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `HmacValidator.validate` at [5](#0-4)  succeeds because it only checks `B` against `H`.
5. `Registry.process` builds `WebhookMetadata` with `shop: "victim.myshopify.com"` and the attacker-controlled body `B`, and invokes the app's handler as if this were a genuine event for the victim shop [6](#0-5) .

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
