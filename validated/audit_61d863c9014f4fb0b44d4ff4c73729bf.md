### Title
Webhook HMAC does not bind the `shop-domain` or `topic` headers, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body [1](#0-0) , while `shop` and `topic` are read straight from unauthenticated HTTP headers [2](#0-1) . `Registry.process` validates the HMAC over that signable string and then unconditionally trusts `request.shop`/`request.topic`/`request.webhook_id` to build the `WebhookMetadata` handed to the app's handler [3](#0-2) . The identity binding the HMAC is supposed to enforce — "this body was produced by Shopify **for this shop and this topic**" — only actually covers the body bytes, not the shop/topic bytes.

### Finding Description
The equality that should hold is:
`HMAC-verified(bytes) == bytes_that_determine_tenant_identity(shop, topic)`

In this gem that equality does not hold. `HmacValidator.validate` recomputes the HMAC using `verifiable_query.to_signable_string`, which for a webhook `Request` is literally `@raw_body` [4](#0-3) [1](#0-0) . The `shop-domain` and `topic` headers are parsed independently from the (unauthenticated, attacker-controllable) HTTP headers [2](#0-1) [5](#0-4) , and are never fed into the signature computation.

`Registry.process` only checks `Utils::HmacValidator.validate(request)` before dispatching to the topic handler using `request.shop` as the tenant identifier for the callback: [6](#0-5)  — note the shop/topic fields flow straight into `WebhookMetadata` without any cryptographic tie to the HMAC that was just verified.

Because the `api_secret_key` used to sign webhooks is a single per-app secret shared across every shop that has installed the app (it is not shop-specific), any merchant who has installed the app (an "unprivileged" party relative to other tenants of the same app) receives genuinely-signed webhook deliveries for their own store. Nothing stops that merchant from capturing one such `(raw_body, hmac)` pair and replaying it to the app's webhook endpoint with a forged `x-shopify-shop-domain` (and/or `x-shopify-topic`) header pointing at a victim shop. `HmacValidator.validate` will still pass because it only checks the body bytes, and the app's registered handler will process the payload believing it originates from the victim tenant.

### Impact Explanation
This breaks the tenant isolation the HMAC is meant to guarantee: an attacker-controlled shop can make the app process, store, or act on data while impersonating a different shop, i.e. cross-tenant access/confusion driven entirely by the requester's own currently-valid webhook credentials plus header manipulation, no leaked secrets required. Depending on what a consuming app's webhook handler does with `WebhookMetadata#shop` (e.g., writing order/product state, updating billing status, revoking access, gating multi-tenant records), this can lead to cross-tenant data corruption or privilege confusion — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Exploitation requires only that the attacker be a legitimate installer of the target app (to receive genuinely-signed webhook traffic for their own shop) — no theft of the app's `api_secret_key`, no TLS interception, no social engineering. Capturing your own webhook deliveries and replaying them with a modified header is trivial with any HTTP proxy. The likelihood is high for any app that keys authorization or per-tenant side effects off `WebhookMetadata#shop`/`#topic` as delivered by this library, since the library provides no protection and no documented warning about this gap.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, and ideally `webhook-id`) in the signable string used for HMAC verification, or otherwise cryptographically bind them to the body before dispatch — matching Shopify's admin/webhook design intent that the whole delivery (not just the payload) is authenticated per shop. At minimum, `Registry.process` should refuse to trust `request.shop`/`request.topic` for authorization decisions unless they are covered by the verified signature.

### Proof of Concept
1. Install the target app on an attacker-controlled test shop `attacker.myshopify.com`; Shopify sends a legitimately HMAC-signed webhook, e.g. `orders/create` with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC(api_secret_key, B)`.
2. Attacker replays this exact request to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com` (and optionally a different `x-shopify-topic`).
3. `Utils::HmacValidator.validate` recomputes `HMAC(api_secret_key, B)` from `to_signable_string` (`= B`), which matches `H` — validation succeeds [7](#0-6) .
4. `Registry.process` looks up the handler for the (forged) topic and invokes it with `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` — `shop` is `victim.myshopify.com`, even though Shopify never sent this webhook for that shop [3](#0-2) .
5. Any app logic keyed on `data.shop` now runs against the victim tenant using attacker-chosen content.
