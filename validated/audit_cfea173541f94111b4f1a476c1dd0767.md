Audit Report

## Title
Bridge `OutgoingToken` is stored unencrypted and permanently disclosed via API/GraphQL to any authenticated user, including read-only `view`-role users - (File: core/bridges/bridge_type.go)

## Summary
`NewBridgeType` stores the bridge's `IncomingToken` only as a salted hash (`IncomingTokenHash`), but persists `OutgoingToken` in plaintext in the `bridge_types.outgoing_token` column and re-serves it in plaintext on every `Index`/`Show` call and via GraphQL `Bridge.outgoingToken`. Critically, these read routes carry no minimum-role restriction beyond plain authentication, so even a `UserRoleView` account can repeatedly retrieve the plaintext token for every bridge.

## Finding Description
`NewBridgeType` generates `incomingToken` and `outgoingToken`, hashes only the incoming one, and stores `outgoingToken` unhashed on the persisted `BridgeType` struct: [1](#0-0) . This is persisted directly in the `outgoing_token` column: [2](#0-1) . `BridgeResource` unconditionally serializes `OutgoingToken` with no redaction or one-time-only semantics (unlike `IncomingToken`, whose comment marks it creation-only): [3](#0-2) . The `Index` and `Show` controller actions call `presenters.NewBridgeResource` on every request: [4](#0-3) , and the GraphQL schema exposes the same field: [5](#0-4) .

Verified role-gating gap: in `v2Routes`, the bridge routes are registered as `authv2.GET("/bridge_types", paginatedRequest(bt.Index))` and `authv2.GET("/bridge_types/:BridgeName", bt.Show)` with no `auth.RequiresEditRole`/`auth.RequiresAdminRole` wrapper, while `Create`, `Update`, `Destroy` are wrapped with `auth.RequiresEditRole` [6](#0-5) . The `authv2` group itself only requires `auth.Authenticate(..., auth.AuthenticateByToken, auth.AuthenticateBySession)` [7](#0-6) , meaning any authenticated user of any role — including `UserRoleView`, the lowest role — can hit `Index`/`Show` and receive the plaintext `OutgoingToken`. The role hierarchy is defined in `core/sessions/user.go` (`UserRoleAdmin`, `UserRoleEdit`, `UserRoleRun`, `UserRoleView`), and `RequiresRunRole`/`RequiresEditRole`/`RequiresAdminRole` in `core/web/auth/auth.go` show that finer-grained gating exists elsewhere in the router but was not applied to bridge read routes [8](#0-7) .

## Impact Explanation
Any authenticated node account, even a read-only `view` role intended only to observe node state, can enumerate all configured bridges and obtain the plaintext `OutgoingToken` for each one, indefinitely, through `GET /v2/bridge_types`, `GET /v2/bridge_types/:BridgeName`, or the GraphQL `bridge`/`bridges` queries. This is a genuine privilege-boundary violation: `view` role is documented/intended as read-only/observability, not as a credential-management role, yet it can extract secrets used to authenticate outbound bridge adapter callbacks. This maps to an in-scope "key/secret exfiltration" / node API role-bypass impact class, since a `view`-role principal obtains a credential that should require at least `edit` (the role required to create/rotate bridges).

## Likelihood Explanation
Likelihood is high given verified facts: no additional role check exists on the bridge read endpoints, so exploitation only requires a valid session/API token of any role — no admin/edit privilege escalation, no host or DB access, no malicious peer needed. Repeatable at will by anyone with `view`-level node credentials.

## Recommendation
- Add `auth.RequiresEditRole` (matching the write endpoints) to `authv2.GET("/bridge_types", ...)` and `authv2.GET("/bridge_types/:BridgeName", ...)` so `view`/`run` roles cannot read bridge secrets, and apply equivalent role gating to the GraphQL bridge resolver/loader.
- Longer term, avoid round-tripping the plaintext `OutgoingToken`: expose it only once at creation (as with `IncomingToken`), or redact it from subsequent reads.

## Proof of Concept
1. As an admin, create a node user with `UserRoleView` (`POST /v2/users` role=view).
2. Authenticate as that view-role user and call `GET /v2/bridge_types/:BridgeName` (or the GraphQL `bridge(id:)` query) for a bridge created by another user.
3. Observe the response includes the plaintext `outgoingToken` field, sourced directly from the unhashed `bridge_types.outgoing_token` column, despite `view` role having no bridge-management permission — confirmed by the absence of `auth.RequiresEditRole`/`auth.RequiresAdminRole` on these two routes in `core/web/router.go` lines 269–271, contrasted with the wrapped `Create`/`Update`/`Destroy` routes on lines 270–273.
