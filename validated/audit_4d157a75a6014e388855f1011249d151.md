### Title
Webhook `shop` Field Not Covered by HMAC Verification Enables Cross-Tenant Shop Impersonation - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` exposes a `shop` attribute (the tenant identifier used downstream by app handlers) that is read directly from the `X-Shopify-Shop-Domain`/`shopify-shop-domain` HTTP header, but the HMAC signature computed by `HmacValidator` only covers the raw request body. This breaks the binding: `hmac_authenticated_bytes == raw_body` while `shop_identity_used_by_handler == unauthenticated_header_value`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, however, is derived purely from the `shop-domain` header, which is never included in that signable string: [2](#0-1) 

`Registry.process` validates the HMAC of the request and then forwards `request.shop` — the unauthenticated header value — as the tenant identity to the app's handler: [3](#0-2) 

`HmacValidator.validate` computes the signature using the app's single, shop-independent `Context.api_secret_key` (the same secret is shared by every shop that installs the app): [4](#0-3) 

Because the secret is shared across all shops the app is installed on, and the header carrying the tenant identity is not part of the signed material, any shop that has legitimately installed the app can obtain a `(body, hmac)` pair that is valid under the shared secret, then re-submit that exact body/HMAC pair to the app's webhook endpoint with a forged `X-Shopify-Shop-Domain` header pointing to a different (victim) shop. `Utils::HmacValidator.validate` will still return `true` because it never inspects the header, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload belongs to the victim shop.

Equality broken: `hmac_verifies(raw_body) == true` is treated as proof that `(raw_body, shop_header)` together are authentic, when in fact only `raw_body` is authenticated and `shop_header` is attacker-controlled.

### Impact Explanation
This is a cross-tenant identity binding failure: an app that keys per-shop state (access tokens, cached data, business logic) off `WebhookMetadata#shop` as provided by this gem can be made to process/attribute another merchant's webhook data (or an attacker's crafted body) under a victim shop's identity, without needing the victim's credentials. This matches the Critical category "cross-tenant access."

### Likelihood Explanation
Any actor who can install the app on their own shop (a normal, unprivileged action available to any Shopify merchant/developer) can trigger real webhooks for their own shop, capture a valid `(body, hmac)` pair signed with the app's shared secret, and replay it with a modified shop header to any exposed webhook endpoint using this library's `Registry.process`/`Request` classes. No access token, `api_secret_key` value, or victim credential is required — only a header value is substituted, and the HMAC check does not detect the tampering because it is scoped to `raw_body` alone.

### Recommendation
Bind the shop identity to the authenticated material, e.g., include the `shop-domain` header (and/or `topic`, `webhook-id`) in `to_signable_string` so the HMAC covers exactly the bytes/headers acted upon, or independently verify that the `shop-domain` header corresponds to a shop with an active, known installation/session before trusting it as a tenant key in `WebhookMetadata`.

### Proof of Concept
1. Install the target app on an attacker-owned shop `attacker.myshopify.com`; trigger an event (e.g., `orders/create`) so Shopify sends a webhook to the app's endpoint with headers `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid hmac over raw body, computed with the app's shared api_secret_key>`.
2. Capture the raw body and the valid HMAC header value.
3. Re-send the same raw body and HMAC to the app's webhook endpoint, but replace the header with `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb`) succeeds because it only checks the (unchanged) body against the (unchanged) HMAC using the shared secret.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:189-200`) invokes the app's handler with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)`, causing the app to process attacker-supplied data as if it belonged to the victim shop.
