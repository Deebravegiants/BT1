### Title
Fire-and-forget upload of tier1/tier2 personal custody packages allows secure-element-signed hash attestations to be persisted while the attested biometric data is silently and permanently lost - (File: src/plans/mod.rs, src/plans/personal_custody_package.rs, src/agents/data_uploader.rs)

### Summary
The reported bug class is: an accounting/state update (`collateralReturnedCount`) is committed unconditionally even when the underlying value transfer (`_sendValue`) can fail, so the on-chain bookkeeping diverges from reality and the client's funds get silently misappropriated. The same "commit-then-maybe-fail" pattern exists in orb-core's personal custody package (PCP) upload flow: a secure-element-signed hash commitment covering the tier1/tier2 biometric payload is built and uploaded as part of tier0 (which is retried and confirmed), but the tier1/tier2 payload itself is uploaded fire-and-forget through the `data_uploader` agent, with no success confirmation propagated back to the signup flow and no additional retry once a client error is hit.

### Finding Description
In `personal_custody_package::Package::build`, the hashes for the tier1/tier2 encrypted blobs are computed and then cryptographically signed via the secure element before those blobs are ever confirmed as uploaded: [1](#0-0) 

That `hashes.sign` / `hashes.json` (containing the SHA256 digests of `tier1_encrypted` and `tier2_encrypted`) is bundled into `tier0`, and `tier0` upload is the only tier that is retried and gated on success before the signup continues: [2](#0-1) [3](#0-2) 

For `pcp_version >= 3`, once tier0 succeeds, tier1 and tier2 (which actually contain the raw iris/normalized-iris/face tars per `Package::build`) are simply pushed into the `data_uploader` agent's queue and the send is only checked for whether it entered the channel, not whether the upload itself succeeded: [4](#0-3) 

Inside the `data_uploader` agent, `upload_pcp` retries on network errors but silently gives up (`break`) on any client error, with no error propagated to the signup plan and no further attempt to retry or notify the user: [5](#0-4) 

The net effect: the secure-element-signed attestation of the tier1/tier2 hashes (already durably persisted to the backend as part of tier0) can outlive the actual tier1/tier2 payload it attests to, exactly mirroring the reported pattern where `s_validatorData.collateralReturnedCount` is updated regardless of whether `_sendValue` actually succeeded.

### Impact Explanation
This creates a state divergence between what the backend/attestation records claim happened (a complete, cryptographically-signed PCP with tier1/tier2 hash commitments) and what actually exists (only tier0 uploaded; tier1/tier2 data permanently missing). Because the failure is invisible to the signup flow — the loop in `do_signup` proceeds to `enroll_user`/success reporting without ever knowing tier1/tier2 upload failed — a signup can be recorded as fully successful and attested while the user's actual biometric custody images are irrecoverably lost. This is a genuine attestation/state-commitment integrity issue: a secure-element-signed claim is finalized before the operation it certifies is confirmed, the same causal chain as the original bug (state updated before the value-transfer's success is verified).

### Likelihood Explanation
This is reachable by any unprivileged signup participant under ordinary conditions — no malicious operator or attacker is required. Any transient client-side error during tier1/tier2 upload (e.g., an expired presigned URL or backend 4xx from `upload_personal_custody_package::request`) is enough to trigger `is_client_error()` and break out of the retry loop for good, while `do_signup` has already unconditionally advanced past the `.send()` calls with no error check on payload success.

### Recommendation
Do not finalize (sign/commit) the tier1/tier2 hash attestation in tier0 until the corresponding tier1/tier2 upload has been confirmed successful, or alternatively make the `data_uploader::Input::Pcp` send path return a completion signal back to `do_signup` so the plan can react to tier1/tier2 upload failure (retry, mark signup as failed/incomplete, or drop the previously-signed attestation). At minimum, propagate the tier1/tier2 upload result and gate final `signup_successful()`/enrollment status reporting on it, mirroring the existing `upload_pcp_tier_0` success-gating pattern already used for tier0.

### Proof of Concept
1. Complete a signup with `pcp_version >= 3` so tier0/tier1/tier2 packages are built (`src/plans/personal_custody_package.rs` `Package::build`), and the secure-element-signed `hashes.sign`/`hashes.json` committing to `tier1_encrypted`/`tier2_encrypted` digests is placed into tier0.
2. Let tier0 upload succeed via `upload_pcp_tier_0` (`src/plans/mod.rs:1778-1839`), so `do_signup` proceeds.
3. Force the tier1/tier2 upload request (`backend::upload_personal_custody_package::request`) to return a 4xx client error (e.g., expired/invalid presigned URL) on the first attempt.
4. Observe in `Agent::upload_pcp` (`src/agents/data_uploader.rs:176-217`) that the loop `break`s immediately after incrementing the `main.count.signup.result.failure.upload_custody_images` metric, with no signal sent back to `do_signup`.
5. Observe that `do_signup`/`enroll_user` still proceed to report the signup as successful, while the tier1/tier2 payload attested to by the already-uploaded, secure-element-signed `hashes.sign` in tier0 never reaches the backend and is permanently lost.

```rust
    async fn upload_pcp_tier_0(
        &self,
        orb: &mut Orb,
        signup_id: &SignupId,
        user_id: &str,
        data: Vec<u8>,
        checksum: Digest,
        tier: Option<u8>,
    ) -> Result<bool> {
        const RETRIES_COUNT: usize = 6;
        tracing::info!("Start uploading personal custody package");
        let t = Instant::now();
        for i in 0..RETRIES_COUNT {
            let response = backend::upload_personal_custody_package::request(
                signup_id,
                user_id,
                checksum.as_ref(),
                &data,
                tier,
                &orb.config,
            )
            .await;
            match response {
                Ok(()) => {
                    dd_timing!("main.time.signup.upload_custody_images", t);
                    tracing::info!(
                        "Personal custody package uploading completed in: {}ms",
                        t.elapsed().as_millis()
                    );
                    return Ok(true);
                }
                Err(err) => {
                    tracing::error!("UPLOAD PERSONAL CUSTODY PACKAGE ERROR: {err:?}");
                    dd_incr!(
                        "main.count.http.upload_custody_images.error.network_error",
                        "error_type:normal"
                    );
                    if let Some(reqwest_err) = err.downcast_ref::<reqwest::Error>() {
                        if let Some(status) = reqwest_err.status() {
                            if status.is_client_error() {
                                dd_incr!(
                                    "main.count.signup.result.failure.upload_custody_images",
                                    "type:network_error",
                                    "subtype:signup_request"
                                );
                                break;
                            }
                        }
                    }
                    if i == RETRIES_COUNT - 1 {
                        dd_incr!(
                            "main.count.signup.result.failure.upload_custody_images",
                            "type:network_error",
                            "subtype:signup_request"
                        );
                    }
                }
            }
        }
        notify_failed_signup(orb, Some(SignupFailReason::UploadCustodyImages));
        Ok(false)
    }
```
