### Title
Pausable/blacklistable fee token permanently blocks GET-response and timeout delivery - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.dispatchIncoming(GetResponse, ...)`, `dispatchTimeOut(GetRequestTimeout, ...)`, and `dispatchTimeOut(PostRequestTimeout, ...)` each perform an unconditional `IERC20(feeToken()).safeTransfer(...)` to the relayer/original sender *after* the destination module's callback has already succeeded and after replay-protection state has been written. If the configured `feeToken` supports pausing or address-blacklisting (e.g. USDC-style tokens, which are explicitly the intended fee token per the docs referencing "typically a stablecoin"), a paused/blacklisted recipient causes the `safeTransfer` to revert, which reverts the *entire* transaction — undoing the callback execution and the receipt bookkeeping — making that specific message permanently non-deliverable.

### Finding Description
In `dispatchIncoming(GetResponse memory response, address relayer)`: [1](#0-0) 
the function writes `_responseReceipts[commitment]`, calls `IApp.onGetResponse` on the destination module, and only after that succeeds does it perform `IERC20(feeToken()).safeTransfer(relayer, fee)`. There is no try/catch around this transfer — unlike the callback call, which is wrapped in a low-level `.call` with a `success` check that allows retry via `delete`. If the transfer reverts (e.g., because `relayer` is blacklisted/paused on the fee token, or the fee token itself is globally paused), the whole external call from `HandlerV2` reverts, rolling back the state that made the message "delivered." Because the underlying source-chain state proof the relayer used to build this delivery does not change, retrying the same message on the destination will hit the same `safeTransfer` failure indefinitely — the message can never be delivered.

The identical pattern exists in the timeout paths: [2](#0-1) [3](#0-2) 
Here `meta.sender` (the original request's fee payer) is the transfer recipient. If that fee-payer address is later blacklisted on the fee token (a scenario entirely outside the protocol's control), or if the fee token is globally paused, every future timeout claim referencing that fee/sender combination becomes stuck: the callback to the app succeeds, but the mandatory refund transfer reverts and unwinds the whole transaction, so the timeout (and the fee-escrowed capital) can never be settled.

This exactly mirrors the reported bug class: an escrow/settlement flow (`liquidateLoan()` in the original report) becomes permanently blocked because a token used inside it can pause/blacklist transfers. Here it's Hyperbridge's core message-delivery path (`dispatchIncoming`/`dispatchTimeOut`) rather than a lending liquidation, but the root cause — an unconditionally required ERC20 transfer inside a state-transition function with no fallback for a paused/blacklisted token — is the same.

### Impact Explanation
A GET response or a request/GET timeout whose associated relayer or fee-payer address becomes blacklisted (or whose fee token is globally paused) can never be delivered/settled on that destination host. This is a permanent freezing-of-funds condition: the escrowed relayer fee is stuck in the host contract forever (no path exists to skip or retry the transfer independently of the callback), and more importantly the underlying cross-chain message (GET response data, or the timeout notification to the app) is permanently undeliverable through this host, since every retry replays the identical failing transfer. This matches the "route unable to deliver messages" / "permanent freezing of funds" acceptance criteria.

### Likelihood Explanation
Likelihood depends on the fee token's admin exercising pause/blacklist power against a specific relayer or fee-payer address, which requires the fee token issuer (e.g., a centralized stablecoin issuer) to blacklist that particular address — a plausible real-world event given `feeToken` is documented as "typically a stablecoin" (e.g., USDC, which has an on-chain blacklist). It does not require any malicious Hyperbridge actor; it is triggered purely by third-party token-issuer action, making it a legitimate protocol-level design gap rather than a malicious-admin scenario.

### Recommendation
Wrap the relayer/fee-payer reward and refund transfers in `dispatchIncoming(GetResponse,...)`, `dispatchTimeOut(GetRequestTimeout,...)`, and `dispatchTimeOut(PostRequestTimeout,...)` in a try/catch (or low-level call with success check), similar to how the `IApp` callback failure is already handled. On transfer failure, credit the fee to an internal per-account claimable balance instead of reverting the whole delivery, so the message delivery and receipt bookkeeping can still finalize, and the affected party (or a designated recovery path) can later withdraw once unblacklisted, or so governance can redirect stuck fees.

### Proof of Concept
1. Configure `EvmHost` with a fee token that supports address blacklisting/pausing (e.g., a USDC-like token).
2. A user dispatches a GET request with a non-zero fee; `_requestCommitments[commitment].fee` is set on the source/host tracking side per `EvmHost.dispatchTimeOut`/`dispatchIncoming` bookkeeping shown at: [4](#0-3) 
3. Before the relayer submits the GET response proof, the fee token issuer blacklists the relayer's address (or globally pauses transfers).
4. Relayer submits the response via `HandlerV2`, which calls `EvmHost.dispatchIncoming(GetResponse, relayer)`. The `IApp.onGetResponse` callback succeeds, but `IERC20(feeToken()).safeTransfer(relayer, fee)` reverts due to the blacklist/pause.
5. The entire transaction reverts, un-writing `_responseReceipts[commitment]`. Every future attempt to deliver the same response replays the same failing transfer — the message is permanently stuck, and the escrowed fee can never be released.

```text
    function dispatchIncoming(GetResponse memory response, address relayer) external restrict(_hostParams.handler) {
        // replay protection
        bytes32 commitment = response.request.hash();
        _responseReceipts[commitment] = ResponseReceipt({
            relayer: relayer,
            responseCommitment: response.hash()
        });

        (bool success,) = _bytesToAddress(response.request.from)
            .call(abi.encodeWithSelector(IApp.onGetResponse.selector, IncomingGetResponse(response, relayer)));

        if (!success) {
            // so that it can be retried
            delete _responseReceipts[commitment];
            return;
        }

        // reward the relayer fee
        uint256 fee = _requestCommitments[commitment].fee;
        if (fee != 0) {
            IERC20(feeToken()).safeTransfer(relayer, fee);
        }
        emit GetRequestHandled({commitment: commitment, relayer: relayer});
    }
```

```text
    function dispatchTimeOut(
        GetRequestTimeout memory timeout,
        FeeMetadata memory meta,
        bytes32 commitment
    ) external restrict(_hostParams.handler) {
        // replay protection
        delete _requestCommitments[commitment];
        (bool success,) = _bytesToAddress(timeout.request.from)
            .call(abi.encodeWithSelector(IApp.onGetTimeout.selector, timeout));

        if (!success) {
            // so that it can be retried

            // refund relayer fee
            IERC20(feeToken()).safeTransfer(meta.sender, meta.fee);
        }
        emit GetRequestTimeoutHandled({commitment: commitment, dest: string(timeout.request.dest)});
    }
```
