### Title
Webhook `shop-domain` (and `topic`/`webhook-id`/`api-version`) header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop` value from the unauthenticated `x-shopify-shop-domain` / `shopify-shop-domain` HTTP header, but the HMAC signature that `Registry.process` validates only covers the raw request body, never the headers. Because the shared `api_secret_key` used to sign webhooks is the same for every shop that has the app installed, any merchant with the app installed can take one of their own genuinely-signed webhook deliveries and resend it to the app's webhook endpoint with the `shop-domain` header changed to a victim shop, and it will still pass HMAC validation.

### Finding Description
`Request#to_signable_string` only returns the raw body: [1](#0-0) 

`Request#shop` (and `topic`, `webhook_id`, `api_version`) are read straight from HTTP headers with no cryptographic binding: [2](#0-1) 

`HmacValidator.validate_signature` computes the signature purely from `verifiable_query.to_signable_string`, i.e. the body, using the app-wide `Context.api_secret_key`: [3](#0-2) 

`Registry.process` gates only on this body-HMAC check, then immediately forwards the header-derived `shop` to the app's handler as trusted tenant context: [4](#0-3) 

Because the equality the code implicitly relies on is:

`hmac_valid(raw_body, api_secret_key) == true  ⇒  shop_header is authentic`

but the HMAC never incorporates `shop_header`, the two sides diverge: any bytes can be attached to the header independent of the signed body. A single app's `api_secret_key` is shared across every shop that installs it, so a merchant who has legitimately installed the app receives real webhook deliveries with valid HMACs computed over their own payload. That attacker-controlled shop can replay the exact same body/HMAC pair while substituting an arbitrary `x-shopify-shop-domain` value (e.g., a victim shop that also has the app installed). `Utils::HmacValidator.validate` still returns `true` because it never inspects the shop header, and `Registry.process` builds `WebhookMetadata` with the forged `shop` value, handing the app's own handler logic data attributed to a different tenant.

### Impact Explanation
This breaks the tenant/shop identity binding that host applications rely on when processing webhooks (looking up sessions, shop-scoped records, billing, or fulfillment data by `shop`). An attacker with any app installation can cause the host application to process attacker-supplied body content under an arbitrary victim shop's identity, i.e. cross-tenant data confusion/injection through the gem's own webhook verification primitive. This matches the "cross-tenant access" Critical impact category, since the compromise happens entirely within the gem's `Webhooks::Registry`/`Request`/`HmacValidator` trust boundary, not because the host app misused documented behavior.

### Likelihood Explanation
Exploitation requires only that the attacker has (or once had) a legitimate installation of the same app (so they receive genuinely-signed webhook bodies), and the ability to POST arbitrary headers to the app's public webhook endpoint - both of which are ordinary unprivileged-internet-user capabilities relative to the target app. No access to `api_secret_key`, access tokens, or the victim's credentials is needed.

### Recommendation
Include the shop domain (and ideally topic/webhook id) as part of the signed material verified against Shopify, or independently verify that the `shop-domain` header matches the shop actually associated with the raw body via a side channel Shopify guarantees to be authentic (Shopify does not sign headers, so the safer fix is for `HmacValidator`/`Request` to not treat `shop_domain` as trusted at all unless corroborated by a call back to Shopify, or by only accepting the header value in combination with an app-level record of installed shops plus rate/replay protections). At minimum, document prominently that `request.shop` is unauthenticated and must not be used as the sole tenant key without further verification.

### Proof of Concept
1. Install the target app on Shop A (attacker-controlled) and capture a real webhook delivery: body `B`, headers including `x-shopify-hmac-sha256: H` (valid for `B` under the app's shared `api_secret_key`) and `x-shopify-shop-domain: shop-a.myshopify.com`.
2. Replay the exact same request to the app's webhook endpoint, but replace `x-shopify-shop-domain` with `shop-b.myshopify.com` (a victim shop that also has the app installed), keeping body `B` and `x-shopify-hmac-sha256: H` unchanged.
3. `ShopifyAPI::Webhooks::Request.new` accepts the forged header, and `Utils::HmacValidator.validate` returns `true` because it only checks `H` against `B`: [5](#0-4) 
4. The app's registered handler receives `WebhookMetadata` with `shop: "shop-b.myshopify.com"` and body `B`, even though `B` truly originated from Shop A - demonstrating the cross-tenant identity confusion.
