### Title
Unchecked ERC20 return value in `withdraw`/`onAccept` SweepDust of Tron IntentGatewayV2 can silently fail token payouts - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron deployment of `IntentGatewayV2` releases escrowed input tokens, transaction fees, and swept dust using a raw low-level `.call()` to the ERC20 `transfer` selector, checking only that the call did not revert (`success`) but never decoding/validating the returned boolean. Tokens that return `false` on failure instead of reverting (non-compliant ERC20s, several of which exist on Tron/TRC20 ecosystems) will pass this check even though no tokens were actually moved, while escrow accounting is unconditionally decremented as if the transfer succeeded.

The same unchecked pattern is used for protocol/transaction fee payout: [2](#0-1) 

and for the `SweepDust` admin/relayer-triggered path in `onAccept`: [3](#0-2) 

In each case, `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` only reverts the transaction if the call itself failed (e.g., target has no code, or the token function reverts). If the target token implements `transfer` to return `false` on insufficient balance/blocklist/etc. (as several legacy/non-standard ERC20s do, mirroring the `transferFrom`-return-value bug in the referenced report), `success` is still `true` because the low-level call succeeded — the returned `false` is discarded. The code then proceeds to decrement `_orders[body.commitment][token] -= amount` (in `withdraw`) or emit `DustSwept`/mark `_filled` as completed, permanently recording the escrow as paid out even though the beneficiary received nothing.

This directly parallels the referenced bug class: an ERC20 transfer's boolean return value is not checked, allowing a "successful" transaction to actually fail to move funds, while internal state treats it as delivered.

Note: elsewhere in this same file and in the primary (non-Tron) `IntentGatewayV2.sol`/`IntentsBase.sol`, deposits use OpenZeppelin's `safeTransferFrom` (e.g. `IERC20(token).safeTransferFrom(msg.sender, dispatcher, amount)` [4](#0-3) ), showing the project is otherwise aware of and uses `SafeERC20` for the deposit direction — but the payout/withdraw direction in the Tron contract regressed to unchecked raw calls.

### Impact Explanation
A user (order creator awaiting a refund) or a solver/filler awaiting escrow redemption can lose the entirety of their expected payout if the escrowed token is a non-standard ERC20 that returns `false` instead of reverting on failed transfers (e.g., due to insufficient gateway balance/dust, or a blocklisted/paused beneficiary address, or any other conditional-false-return implementation). The gateway's internal accounting (`_orders[...][token]`) is decremented as though the payout succeeded, so the funds become permanently unrecoverable — this is unbacked loss/freezing of user/solver funds within the intents escrow accounting, delivered through a normal relayed Hyperbridge message (`RedeemEscrow`/`RefundEscrow`) or a `SweepDust` message.

### Likelihood Explanation
This requires the affected token to implement the "return false instead of revert" pattern. This is a known class of non-standard ERC20 tokens; the codebase's own test suite already demonstrates active awareness of non-standard token behavior (fee-on-transfer tokens are explicitly handled), showing the team anticipates real integrations with non-vanilla ERC20/TRC20 tokens on Tron. Given any listed token with this behavior, the trigger requires only a normal relayed cross-chain redeem/refund/sweep message — no privileged or malicious actor needed — making likelihood moderate to high for tokens matching this pattern.

### Recommendation
Replace the raw `.call` + `success`-only checks in `withdraw()` (lines 702–723) and the `SweepDust` handler (lines 670–681) with OpenZeppelin's `SafeERC20.safeTransfer`, consistent with the `safeTransferFrom` already used for deposits in this same contract. This ensures both call-success and the ERC20 boolean return value are validated, reverting the whole transaction (and Hyperbridge redelivery/timeout mechanics) if a transfer genuinely fails, instead of silently marking escrow as released.

### Proof of Concept
1. Configure/whitelist a TRC20/ERC20 token whose `transfer` function returns `false` (rather than reverting) when, e.g., the recipient is blocklisted or the internal transfer condition fails.
2. A user places an order and deposits this token into `IntentGatewayV2` escrow via `placeOrder` (which correctly uses `safeTransferFrom`).
3. The order is later cancelled/refunded, or filled and redeemed, triggering a Hyperbridge `RefundEscrow`/`RedeemEscrow` POST request that is delivered to `onAccept` → `withdraw`.
4. If the beneficiary address triggers the token's `false`-return condition (e.g., temporarily blocklisted, or the contract has an internal check causing `false`), `token.call(...)` still returns `success = true` at the outer low-level-call level.
5. `withdraw()` proceeds to execute `_orders[body.commitment][token] -= amount` and emits `EscrowReleased`/`EscrowRefunded`, permanently closing out the escrow record even though the beneficiary's token balance never increased — resulting in irrecoverable loss of the escrowed funds.
