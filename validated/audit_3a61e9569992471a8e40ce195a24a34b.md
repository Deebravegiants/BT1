### Title
Webhook `shop`/`topic`/`webhook_id` headers are unauthenticated, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while the `shop`, `topic`, `webhook_id`, and `api_version` fields are read from unauthenticated HTTP headers and forwarded to the app's webhook handler as trusted `WebhookMetadata`. `Utils::HmacValidator` verifies the HMAC only against the body bytes, never against these header fields, so the tenant-identifying `shop` value is "acted on" by the registry/handler but is not covered by the HMAC that establishes authenticity.

### Finding Description
`Webhooks::Request` extracts `shop`, `topic`, `webhook_id`, and `api_version` purely from HTTP headers: [1](#0-0) 

But the value that is actually HMAC-verified is only the raw request body: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature exclusively from `verifiable_query.to_signable_string` (i.e., the body) and compares it with the `hmac-sha256` header via `secure_compare`: [3](#0-2) 

`Registry.process` then trusts `request.shop`, `request.topic`, and `request.webhook_id` unconditionally once the body HMAC passes, and hands them straight to the app's handler: [4](#0-3) 

Because the app's `api_secret_key` is shared across every shop that installs the app, any merchant who has legitimately installed the app receives real Shopify webhooks for their own shop — genuine `(raw_body, hmac-sha256)` pairs signed with that same shared secret. That merchant/attacker can resend the exact same body and HMAC value to the app's public webhook endpoint while forging the `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header to claim a different, victim shop. `HmacValidator.validate` still succeeds because it never inspects the headers, and `Registry.process` builds `WebhookMetadata` with the attacker-chosen `shop` value, which is exactly the "field acted on but not covered by the HMAC" identity-binding break described in the prompt rules (`request.shop` ≠ the shop cryptographically bound by the HMAC, which is actually nothing — no shop is bound at all).

### Impact Explanation
This breaks the identity binding `shop_authenticated_by_hmac == shop_acted_on_by_handler`. The documented usage pattern (`docs/usage/webhooks.md`) explicitly has apps key persistence and processing off `data.shop`: [5](#0-4) 

An attacker with a legitimate low-privilege installation of the app (any shop can install most public apps) can replay a validly-signed body under a spoofed `shop-domain` header, causing the host app to write/update/act on webhook data under an arbitrary victim shop's tenant record — a cross-tenant confusion/injection. This can also be used to trigger the mandatory compliance webhooks (`customers/redact`, `shop/redact`, `customers/data_request`) against a shop the attacker has no relationship with, since `Registry` treats `MANDATORY_TOPICS` the same way and dispatches on `request.topic`/`request.shop` without any additional binding. This meets the Critical "cross-tenant access" bar.

### Likelihood Explanation
Likelihood is Medium: the attacker needs their own legitimate app installation (trivial for public apps) to obtain one valid `(body, hmac)` pair signed with the app's shared secret, and needs to know/guess the victim's `myshopify.com` domain (often public/guessable). No access to the `api_secret_key`, access tokens, or the victim's credentials is required — only replaying a byte-for-byte payload with a modified header, which is straightforward for any unprivileged internet user capable of installing the app once.

### Recommendation
Include the tenant-identifying fields (`shop`, `topic`, `webhook_id` at minimum) in the value that is HMAC-verified, or independently verify that the `shop` header corresponds to a shop session/installation the app actually expects for that specific webhook delivery (e.g., cross-check against a known list of currently-installed shops before trusting `data.shop`), rather than relying solely on a body-only HMAC to implicitly authenticate header-derived routing data.

### Proof of Concept
1. Attacker installs the target app for `attacker-shop.myshopify.com` and registers for a webhook topic (e.g., `customers/redact` or any topic the app subscribes to).
2. Shopify sends a legitimate webhook to the app for `attacker-shop.myshopify.com`:
   - Headers: `X-Shopify-Topic: customers/redact`, `X-Shopify-Hmac-Sha256: <valid_hmac>`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`
   - Body: `<raw_body>` (attacker fully controls this content, e.g. crafted redact payload).
3. Attacker captures `<raw_body>` and `<valid_hmac>` (computed by Shopify over the body using the shared app secret).
4. Attacker resends the identical request to the app's webhook endpoint, changing only the `X-Shopify-Shop-Domain` header to `victim-shop.myshopify.com` (leaving body/HMAC untouched).
5. `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:13`) succeeds because it only re-hashes `raw_body`.
6. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) invokes the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker-controlled body>, ...)`, causing the host app to act on victim-shop's tenant data using attacker-supplied content.
