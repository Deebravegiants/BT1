### Title
Untrusted swap routes can inject unauthorized wallet transfers into the caller’s authorization tree - ([File: contracts/controller/src/strategies/swap.rs])

### Summary
Controller strategy entrypoints accept caller-supplied swap payloads and invoke the configured router without restricting the pools or contracts reachable through that payload. Because Soroban authorization is represented as a tree rooted at the caller’s controller invocation, a malicious downstream pool can request an unrelated `token.transfer` from the caller; once simulation records that transfer and the caller signs the resulting tree, the token contract accepts it. The controller’s balance-delta checks validate only the swap input and output, leaving unrelated caller assets unprotected.

### Finding Description
`swap_collateral`, `swap_debt`, `multiply`, and `repay_debt_with_collateral` all funnel attacker-controlled route bytes into `swap_tokens`. [1](#0-0) [2](#0-1)  `swap_tokens` authorizes only the expected input-token transfer to the router, then passes the caller-provided payload to `execute_strategy`. [3](#0-2) 

The router payload selects pool addresses from an unrestricted address registry, and a swap hop dispatches to the selected pool through the selected venue adapter. [4](#0-3) [5](#0-4)  A malicious contract implementing the expected venue interface can therefore execute arbitrary code during the swap, including a token transfer requiring the caller’s authorization. The controller checks only that its own input balance did not grow, that spending did not exceed `amount_in`, and that positive output was received; it does not account for unrelated caller-token transfers made beneath the route. [6](#0-5) 

Soroban records that malicious transfer as a sub-invocation under the caller’s root authorization for `swap_collateral`; if the caller signs the recorded tree, the unrelated wallet token is transferred to the attacker while the swap otherwise completes successfully. [7](#0-6)  Enforcing mode rejects the same transfer when the caller signs only the honest root, but accepts it when the signed tree includes the malicious child. [8](#0-7) 

### Impact Explanation
An attacker who supplies a crafted route to a user can steal arbitrary spendable tokens from that user’s wallet, including assets never supplied to or listed by the lending protocol. [9](#0-8)  The demonstrated loss is the caller’s entire balance of an unrelated token, while the protocol-side swap deposits the expected collateral and satisfies the controller’s accounting checks. [10](#0-9) 

This is theft of user funds rather than a pool insolvency. It affects any strategy entrypoint that accepts a route and invokes the configured aggregator, including `multiply`, `swap_debt`, `swap_collateral`, and `repay_debt_with_collateral`. [11](#0-10) 

### Likelihood Explanation
The exploit requires user interaction: the victim must submit or sign a controller operation containing the malicious route and must sign the authorization tree containing the malicious child transfer. This is plausible when routes are generated by an external interface or copied from another party, because the route is opaque XDR and the dangerous behavior is visible primarily as an extra authorization sub-invocation. [12](#0-11) 

The test demonstrates the exact phishing sequence: simulation records the malicious transfer under the caller’s `swap_collateral` authorization, and enforcement succeeds after the caller signs that tree. [7](#0-6) [13](#0-12) 

### Recommendation
Constrain swap routes to governance-approved venue contracts or pool addresses rather than permitting arbitrary pool addresses in caller-supplied payloads. At minimum, maintain a per-venue pool allowlist and reject routes containing unlisted pools before invoking the router.

Additionally, clients and transaction-signing interfaces should decode the complete simulated authorization tree and reject any child invocation outside the expected bounded set—for these swaps, the expected router interaction and token-input transfer, with no unrelated token transfers from the caller. Contract-level balance checks cannot compensate for an authorization-tree signature the user has already granted to downstream code. [14](#0-13) 

### Proof of Concept
A malicious route contains a pool contract whose venue-compatible `swap` implementation calls `token::Client::transfer(victim, attacker, victim_balance)`. The router invokes that pool while executing the caller-provided route. During simulation, the unauthorized wallet transfer is recorded under the caller’s root `swap_collateral` invocation. When the signed transaction includes that recorded child, the token contract accepts the transfer and the attacker receives the victim’s full unrelated-token balance. [15](#0-14) [7](#0-6) 

```rust

}
```

The harness asserts that simulation places this transfer beneath the caller’s `swap_collateral` authorization and that the signed poisoned tree drains `WALLET_BALANCE` from Alice to the attacker. [16](#0-15) [13](#0-12)

```rust
fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };

    assert_eq!(s.wallet(&s.alice), 0);
```
