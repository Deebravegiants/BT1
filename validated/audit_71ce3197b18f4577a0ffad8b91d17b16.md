### Title
Webhook shop-domain header is not covered by the HMAC, allowing cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook as authentic and dispatches it to the app's handler once `Utils::HmacValidator.validate(request)` succeeds. However, the HMAC signable string is defined as only the raw body, not any header, so the `shop` value that the handler receives and trusts as the tenant identity is never covered by the signature.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [4](#0-3) , and `#shop` is read directly from the unauthenticated `x-shopify-shop-domain`/`shopify-shop-domain` header [5](#0-4) . `Registry.process` validates the HMAC via `Utils::HmacValidator.validate(request)` [6](#0-5) , and `HmacValidator.validate_signature` recomputes the HMAC only over `verifiable_query.to_signable_string` (the body) and compares it to the received signature [7](#0-6) . Once that check passes, `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` and hands it to the app's handler [8](#0-7) , i.e. it asserts the equality `{shop trusted by handler} = {x-shopify-shop-domain header}`, when the actual authenticated equality the HMAC proves is only `{HMAC(secret, body)} = {received hmac}` — nothing ties the header to the signed bytes.

Because Shopify signs webhooks with the single `client_secret`/`api_secret_key` shared across every shop that has the app installed (not a per-shop key), any merchant that installs the app can legitimately receive a validly-signed `(body, hmac)` pair for their own store. That merchant (the "unprivileged internet user" here, i.e. any attacker who installs the app on a store they control) can then replay that exact body and HMAC to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header pointing at a victim shop. `HmacValidator.validate` still returns `true` because the body/HMAC pair is untouched, and the handler executes believing the event originated from the victim shop.

### Impact Explanation
Any app that uses `data.shop` from a processed webhook to look up a session/access token, gate business logic per tenant, or otherwise act "on behalf of" that shop (exactly as the gem's own documented example does) can be made to perform actions against, or attribute attacker-supplied data to, a shop the attacker does not control. This is a cross-tenant identity confusion rooted entirely in this gem's `Request`/`Registry` design, matching the Critical "cross-tenant access" category, since the boundary crossed is between the attacker's own tenant and an arbitrary victim tenant, using only a webhook subscription the attacker legitimately obtained for their own store.

### Likelihood Explanation
Likelihood is high for any unprivileged internet user who can install the target app on a store they control (a normal, unprivileged action for any Shopify merchant/developer): they can capture one legitimate webhook delivery to their own endpoint, then replay the identical body+HMAC to the app's public webhook endpoint with a forged shop-domain header. No access token, `api_secret_key`, or privileged account is required — only a standard app install and control of the raw HTTP request to the app's own public webhook URL.

### Recommendation
Do not treat `request.shop` as authenticated identity by HMAC verification alone. Either (a) include the shop-domain header in the signable string/verification (not possible without changing Shopify's protocol, so instead) (b) require callers to cross-check `request.shop` against the shop associated with the specific `webhook_id`/subscription that was registered (e.g., verify `request.shop` matches the shop under which that `topic`/`webhook_id` was actually registered before invoking the handler), and document clearly that `data.shop` is not itself proven authentic by the body HMAC alone.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`, a normal, unprivileged action.
2. Shopify sends a legitimate webhook (e.g. `orders/create`) to the app's registered endpoint, with body `B` and header `x-shopify-hmac-sha256: HMAC(secret, B)` — this HMAC uses the app's single shared `client_secret`, valid for any shop.
3. Attacker captures `B` and its valid HMAC.
4. Attacker POSTs `B` with the same valid HMAC to the app's webhook endpoint again, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `B` against the HMAC [9](#0-8) .
6. The handler is invoked with `WebhookMetadata` carrying `shop: "victim-shop.myshopify.com"` and the attacker's chosen body, despite the event never having originated from the victim shop.
