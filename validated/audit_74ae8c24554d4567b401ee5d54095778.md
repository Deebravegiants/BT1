### Title
HOT Bridge reports withdrawal as "completed" from unverified API hash without checking `verified_withdraw` flag - (File: packages/intents-sdk/src/bridges/hot-bridge/hot-bridge.ts)

### Summary
`HotBridge.fetchWithdrawalHashFromApi` parses the HOT API response with a schema that includes a `verified_withdraw` boolean field, but the field is never read or asserted before the withdrawal hash is trusted and returned as `status: "completed"`.

### Finding Description
The schema explicitly models the field: `verified_withdraw: v.boolean()` in `HotApiWithdrawalSchema` [1](#0-0) . In `fetchWithdrawalHashFromApi`, after parsing succeeds, the code only checks `withdrawal?.hash` and whether it is valid hex — it never inspects `withdrawal.verified_withdraw`: [2](#0-1) 
This hash is then used directly to report `status: "completed"` to the caller in `describeWithdrawal`, both in the EVM/Stellar/TON branch fallback and the non-EVM branch fallback: [3](#0-2) [4](#0-3) 

The equality that should hold is: *status reported == actual on-chain outcome*. Here, the "completed" status is derived from a `hash` value present in the HOT off-chain API payload, while a sibling field (`verified_withdraw`) that presumably indicates whether that hash has actually been confirmed/verified is silently discarded. The test suite confirms the API can return a hash together with `verified_withdraw: true` without the code path differentiating on it: [5](#0-4) .

### Impact Explanation
If the HOT API can return a `hash` for a withdrawal whose `verified_withdraw` is `false` (unverified/unconfirmed destination transaction), `describeWithdrawal` would still report `status: "completed"` with that hash to the integrator. An integrator that treats "completed" as final proof of delivery could act on an unconfirmed/unverified transaction hash — e.g., crediting a user or reconciling accounting — before the destination chain transaction is actually confirmed, or in the worst case if the hash later turns out invalid/reorged, producing a status/hash misreport. This maps to the "status reported that is not the on-chain outcome" class of equality violation named in scope, with potential impact of "a status or hash misreport making an integrator credit or refund twice."

### Likelihood Explanation
This path is only reachable in fallback scenarios — when the primary source (bridge indexer for EVM/Stellar/TON, or the on-chain contract view for other chains) fails or returns null/pending, and the code fully depends on the HOT off-chain API as source of truth for the final status. This is a real, always-available code path (not requiring an admin/attacker to misbehave), triggered simply by transient bridge-indexer/contract unavailability, which is common. Whether the live HOT API ever actually returns `hash` with `verified_withdraw: false` cannot be confirmed from this repo alone — that behavior lives in the external HOT API server, which is out of scope for direct proof, but the client-side code neither defends against it nor requires it, i.e. the field is dead code from a trust perspective.

### Recommendation
In `fetchWithdrawalHashFromApi`, before treating a `withdrawal.hash` as authoritative, require `withdrawal.verified_withdraw === true`; otherwise treat the withdrawal as still pending, matching the same "trust but verify" pattern used elsewhere in this file (e.g., hex validation of `status` before formatting).

### Proof of Concept
1. Bridge indexer call fails or returns null (simulated in tests via `mockBridgeIndexerFailure()` / non-EVM contract branch returning `null`/pending).
2. `hotSdk.api.requestApi` returns a JSON body with `withdrawals: [{ hash: "0xDEADBEEF", nonce: "1", near_trx: "txhash", verified_withdraw: false, chain_id: 56 }]`.
3. `fetchWithdrawalHashFromApi` parses this successfully, extracts `withdrawal.hash`, strips `0x`, validates hex, and returns the hash — ignoring `verified_withdraw: false`.
4. `describeWithdrawal` returns `{ status: "completed", txHash: "DEADBEEF" }` even though the withdrawal was not verified, as shown by the equivalent passing test case with `verified_withdraw: true` at [5](#0-4)  — no test exercises the `verified_withdraw: false` case, confirming the flag is unchecked in the implementation at [2](#0-1) .
