## Title
Escrow accounting is decoupled from actual tokens received in Tron `IntentGatewayV2.placeOrder`, allowing fee-on-transfer tokens to permanently under-collateralize escrow - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2.placeOrder` computes the escrow amount from the user-declared `order.inputs[i].amount` (minus protocol fee) rather than from the tokens actually received by the contract. For any ERC-20 with a transfer fee (or any other transfer-amount-reducing behavior), the contract will escrow (and later promise to pay out via `RedeemEscrow`/fill flows) more tokens than it actually holds, causing insolvency and permanently trapped/undeliverable funds for solvers or refund recipients — the same root cause reported for `DonationVotingMerkleDistributionVaultStrategy._afterAllocate`, where the recorded claim amount is not reconciled against actual balance received.

### Finding Description
In `evm/src/apps/IntentGatewayV2.sol::placeOrder`, the mainline EVM implementation was hardened against fee-on-transfer tokens: it snapshots the contract's token balance before `safeTransferFrom`, then computes `order.inputs[i].amount = IERC20(token).balanceOf(address(this)) - balBefore` to record only what was actually received: [1](#0-0) 

However, the Tron fork of this contract, `evm/tron/contracts/apps/IntentGatewayV2.sol`, does not have this reconciliation. It computes `reducedInputs` (escrow amount after protocol fee) directly from the caller-supplied `order.inputs[i].amount`: [2](#0-1) 

Then, in the non-predispatch escrow path, it performs `safeTransferFrom` for the nominal `order.inputs[i].amount` and immediately credits the escrow mapping with `reducedInputs[i].amount` — a value derived from the nominal amount, not the balance actually received: [3](#0-2) 

The same disconnect exists in the predispatch path, where `_orders[commitment][token] += reducedInputs[i].amount` is also computed from the nominal `order.inputs[i].amount`, even though the dust/balance check (`balance - requiredAmount`) only verifies a lower bound, not equality with what will be swept into the gateway: [4](#0-3) 

If `token` charges a transfer fee (fee-on-transfer / deflationary token), the gateway's actual balance increase is strictly less than `order.inputs[i].amount`, yet the `_orders` escrow mapping is incremented by the full (fee-adjusted-only-for-protocol-fee) amount. This is functionally identical to the reported bug class: an accounting value derived from an intended transfer amount, rather than the measured balance delta, is persisted as a claimable/escrowed liability.

### Impact Explanation
Because `_orders[commitment][token]` now overstates the gateway's actual token holdings, later withdrawal paths (solver fills reading escrow, or `RedeemEscrow`/refund handling via `IntentsBase._release`-style logic) will attempt to pay out more tokens than the contract holds for that commitment. This produces:
- Reverting/stuck withdrawals for the legitimate recipient(s) of that specific order (their funds are effectively frozen since the contract cannot pay the recorded amount), and
- Potential shared-pool insolvency: because escrow is tracked per `(commitment, token)` but tokens of the same type are fungible in the contract's balance, an under-funded order can silently drain the token balance backing *other* users' escrowed orders when they attempt to withdraw first, causing funds belonging to unrelated orders to become unrecoverable.

This is a permanent freezing-of-funds condition triggerable by any user simply placing an order with a fee-on-transfer token — a token class the gateway does not explicitly exclude.

### Likelihood Explanation
Likelihood is realistic: `placeOrder` is a fully permissionless, unprivileged entry point reachable by any user submitting a single transaction with an arbitrary ERC-20 `token` address; no allowlist of tokens is enforced in this function. Fee-on-transfer/deflationary tokens are common on Tron/TRC20 (and EVM chains generally), and the mainline `evm/src/apps/IntentGatewayV2.sol` contract's own author explicitly patched this exact issue there (see the balance-diff pattern and the dedicated Foundry test suite `IntentGatewayV2SameChainTest.sol` fee-on-transfer tests), confirming the bug class is recognized as a real, in-scope threat — but the fix was not carried over to the Tron implementation.

### Recommendation
Apply the same balance-based accounting fix used in `evm/src/apps/IntentGatewayV2.sol` to `evm/tron/contracts/apps/IntentGatewayV2.sol`: for each ERC-20 input, snapshot `balanceOf(address(this))` before `safeTransferFrom`, then set the amount used for `reducedInputs`/`_orders` accounting (and the commitment hash) to the actual post-transfer balance delta rather than the caller-declared `order.inputs[i].amount`. Apply the equivalent balance-diff check to the predispatch sweep path as well, so `_orders[commitment][token]` is always backed 1:1 by tokens the contract actually holds.

### Proof of Concept
1. Deploy a TRC20 token with a 1% transfer fee (as in `FeeOnTransferToken` used in `evm/tests/foundry/IntentGatewayV2SameChainTest.sol`).
2. User calls `placeOrder` on the Tron `IntentGatewayV2` with `order.inputs[0] = {token: FOT, amount: 1000e18}` and `protocolFeeBps = 0`.
3. `safeTransferFrom(msg.sender, address(this), 1000e18)` transfers 1000e18 nominally, but the gateway's balance only increases by 990e18 (1% fee).
4. `_orders[commitment][FOT] += reducedInputs[0].amount` credits the escrow with `1000e18` (since `reducedInputs = order.inputs` when `protocolFeeBps == 0`), even though the gateway only holds `990e18` of that token.
5. When a solver/beneficiary later attempts to redeem/fill using the full escrowed `1000e18`, the transfer will fail or drain the balance backing other orders, permanently freezing the shortfall (10e18) and potentially other users' escrowed balances of the same token.
