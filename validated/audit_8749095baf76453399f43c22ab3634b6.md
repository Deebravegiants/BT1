Based on tracing the actual code, this scenario does not hold up as a valid vulnerability.

**Key facts that invalidate the premise:**

1. **Bank hash / lt_hash is computed independently of `clean_accounts` timing.** The authoritative per-slot `accounts_lt_hash` is computed incrementally at transaction-commit/freeze time via `enqueue_on_chain_accounts_lt_hash_updates`, which mixes out the previous account state and mixes in the current one [1](#0-0) . This computation never re-reads the accounts index state as later modified by `clean_accounts`; it is derived purely from the write cache / committed transaction results at the moment of freezing the bank. `clean_accounts` is a background garbage-collection pass that runs after the bank hash for a slot is already fixed, so any timing difference in when a stale zero-lamport index entry gets purged cannot retroactively change an already-computed slot hash.

2. **Zero-lamport accounts are treated identically to absent accounts in every hash computation path.** `lt_hash_account` returns the identity hash (`ZERO_LAMPORT_ACCOUNT_LT_HASH`) for any account with zero lamports [2](#0-1) . The startup/verification path `calculate_accounts_lt_hash_at_startup_from_index` explicitly skips zero-lamport index entries via `(!account_info.is_zero_lamport()).then(...)` [3](#0-2) , so whether or not the physical index entry has been purged by `clean_accounts` makes no difference to the resulting hash — a lingering zero-lamport entry contributes nothing, same as a fully purged one.

3. **The described race does not actually cause incorrect flag/state divergence.** `construct_candidate_clean_keys` drains `dirty_stores` via `retain` and only removes entries it processes in that call [4](#0-3) ; any store not yet inserted by a concurrent flush simply remains for the next `clean_accounts` invocation — no data is lost. The `might_contain_zero_lamport_entry` flag is accumulated via bitwise-OR across all contributing dirty stores for a pubkey (`|= is_zero_lamport`) [5](#0-4) , and entries reaching candidates via `uncleaned_pubkeys` are conservatively always marked `true` [6](#0-5) . Even in a worst-case scenario where the flag is wrongly `false` and the disk-only `scan_filter_for_shrinking` misses the zero-lamport entry, the candidate is simply skipped that round (empty `slot_list`, dropped from `candidates.retain`) rather than incorrectly purged — it is not a "one node purges, the other retains" scenario; it is at most a delayed reclaim.

4. **Not attacker-reachable.** The claimed race depends on the internal scheduling of `flush_accounts_cache` and `clean_accounts` background threads on a given validator, which is driven by validator implementation/timing, not by transaction content, ALTs, nonces, or compute-budget instructions an unprivileged user controls. An attacker broadcasting transactions cannot control when a validator's background threads interleave.

        // process accounts in reverse because we must only count the latest version of each account
        for index in (0..accounts.len()).rev() {
            let address = accounts.pubkey(index);
            if !seen_accounts.insert(*address) {
                // we've already enqueued a newer update for the same account; skip this one
                continue;
            }

                .rc
                .accounts
                .load_with_fixed_root_do_not_populate_read_cache(&self.ancestors, address)
                .map(|(account, _slot)| account);

                (account.lamports() != 0).then(|| account.take_account())
            });

                    thread_pool,
                    AccountsLtHashUpdate {
                        address: *address,
                        prev_account,
                        curr_account,
                    },
                );
            }
