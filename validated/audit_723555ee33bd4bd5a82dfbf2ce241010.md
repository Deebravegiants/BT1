### Title
Webhook Shop Domain Not Covered by HMAC Signature Enables Cross-Tenant Webhook Forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` verifies webhook authenticity using an HMAC that is computed only over the raw request body, while the `shop` identifier used to attribute the webhook to a specific merchant/tenant is read from an HTTP header that is never included in the signed data. An unprivileged user who can trigger a webhook for their own shop (obtaining a legitimately-signed `(body, hmac)` pair) can replay that exact body/HMAC pair while substituting the `shopify-shop-domain` header for an arbitrary victim shop. `Utils::HmacValidator.validate` will still accept the signature, and the forged webhook will be dispatched to the app's handler attributed to the victim tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all parsed straight from headers, none of which are part of the signed content: [2](#0-1) 

`Utils::HmacValidator.validate` computes and compares the signature strictly against `verifiable_query.to_signable_string`, i.e. the raw body only: [3](#0-2) 

`Webhooks::Registry.process` trusts `request.shop` (an unsigned header) as the tenant identity once the (body-only) HMAC check passes, and hands it directly to the application's webhook handler: [4](#0-3) 

This is the same identity-binding gap described in the external report: the signed material (here, the request body) does not bind to the entity the signature is meant to authorize (here, the specific shop/tenant). Just as a BLS signature over `(nonce, bundle, chainId)` without the wallet address can be replayed against a different wallet once the same public key is attached to it, an HMAC over the body alone can be replayed against a different `shop` header once an attacker captures one valid `(body, hmac)` pair for their own tenant.

### Impact Explanation
Any unprivileged actor who can generate one legitimate webhook delivery for a shop they control (e.g., installing the app and triggering `app/uninstalled`, whose body is the fixed literal `{}`) obtains a `(raw_body, hmac)` pair that will validate successfully regardless of which `shop` is claimed. By POSTing that same body/HMAC combination to the app's webhook endpoint with the `x-shopify-shop-domain` (or `shopify-shop-domain`) header rewritten to a victim shop, the forged request passes `HmacValidator.validate` and is processed by the app's handler as authentic data for the victim shop — a cross-tenant authentication/data-integrity bypass. Depending on the handler (e.g., `app/uninstalled`, `shop/redact`, or any handler that mutates per-shop state based on `WebhookMetadata#shop`), this can cause deletion of the victim's stored session/data, unauthorized state changes attributed to the victim tenant, or other cross-tenant side effects — satisfying the Critical "cross-tenant access" bar.

### Likelihood Explanation
Exploitation only requires: (1) the ability to install the app or otherwise trigger a webhook for one's own shop to capture a valid `(body, hmac)` pair — trivially available to any merchant/unprivileged user; and (2) the ability to send an arbitrary HTTP POST to the app's public webhook endpoint with attacker-chosen headers, which is the normal shape of that endpoint. No secrets, tokens, or privileged access are required, making this readily reachable by an unprivileged internet user.

### Recommendation
Include the tenant-identifying and message-defining metadata (at minimum `shop`, `topic`, and ideally `webhook_id`) as part of the signed/verified material, or independently bind the header-derived `shop`/`topic` to the verified payload before dispatch (e.g., require the handler-invocation path to re-validate that the `shop` header matches a value embedded in the signed body, if Shopify's webhook payload includes it, or track/reject replays via `webhook_id`/`jti`-style uniqueness). At minimum, document and enforce that `Registry.process` must not trust the `shop` header as tenant identity unless it is cryptographically bound to the verified signature.

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com`; uninstall the app to receive a legitimate `app/uninstalled` webhook delivery with headers:
   - `x-shopify-topic: app/uninstalled`
   - `x-shopify-hmac-sha256: <valid HMAC of body "{}">`
   - `x-shopify-shop-domain: attacker.myshopify.com`
   - body: `"{}"`
2. Replay the exact same body (`"{}"`) and the exact same `x-shopify-hmac-sha256` value to the app's webhook endpoint, but change `x-shopify-shop-domain` to `victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: "{}", headers: forged_headers)` is constructed; `Utils::HmacValidator.validate(request)` computes the HMAC over `"{}"` only (`to_signable_string`), which matches the captured signature, so validation succeeds.
4. `ShopifyAPI::Webhooks::Registry.process(request)` invokes the `app/uninstalled` handler with `WebhookMetadata.new(topic: "app/uninstalled", shop: "victim.myshopify.com", ...)`, causing the app to treat the victim shop as uninstalled/redacted despite no such webhook having been sent by Shopify for that shop.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
