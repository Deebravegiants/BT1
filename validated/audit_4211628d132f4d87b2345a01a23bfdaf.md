### Title
`isHostname()` IPv4 regex is broken (double-escaped), causing `isSubdomain`/`assertMatchingDomain` to treat IP-literal cookie domains as valid hostnames - (File: `modules/networking-common/src/cookie/validators.ts`)

### Summary
`isHostname()` is supposed to reject IP-literal domains so that `isSubdomain()` never performs suffix-based domain matching against an IP address, per RFC 6265 §5.1.3. The `v4` regex used for this check is malformed (`\\d`/`\\.` instead of `\d`/`\.`), so it never matches real dotted-decimal strings, making `isHostname()` return `true` for virtually all inputs, including real IPv4 addresses — not just the edge cases (`999.999.999.999`, IPv6) mentioned in the question.

### Finding Description
In [1](#0-0) , the `v4` pattern is written with double backslashes:
```
const v4 = /^(?:25[0-5]|2[0-4]\\d|1\\d\\d|[1-9]\\d|\\d)(?:\\.(?:25[0-5]|2[0-4]\\d|1\\d\\d|[1-9]\\d|\\d)){3}$/
```
Inside a JS/TS `RegExp` literal, `\\d` is parsed as an escaped backslash character followed by the literal `d` (i.e., it matches the two-character sequence `\d` in the input), not a digit-class shorthand. Because no real IPv4 string like `192.168.1.1` contains literal backslash characters, `v4.test(value)` is `false` for essentially any real input, so `isHostname(value) = !v4.test(value)` returns `true` even for genuine IP-literal strings — the "is not an IP address" guard is completely non-functional.

This feeds `isSubdomain()`, [2](#0-1) , whose suffix-matching logic is intended to be gated by `isHostname(value)` per the RFC comment ("The string is a host name (i.e., not an IP address)"). Since that guard always passes, `isSubdomain()` performs plain string-suffix matching even when `value` is an IP literal, e.g. `isSubdomain('192.168.1.1', '1.1')` returns `true` when it should not (an IP address has no sub-domain relationship to a numeric suffix). This is consumed by `assertMatchingDomain(domain, originDomain)`, [3](#0-2) , which is the function whose entire purpose is to reject third-party/cross-origin cookie `Domain` attributes.

**Reachability caveat:** I was able to confirm `assertMatchingDomain` is exported from the package's public API (`modules/networking-common/src/cookie/index.ts`) and directly unit-tested in [4](#0-3) , but I could not find a production call site wiring `deserialize()` (used by `CookieJar.set()` in [5](#0-4) ) into `assertMatchingDomain`. The mobile `CookieJar.set()` for string cookies delegates directly to the native `store.setFromResponse(url, cookie)` without calling `assertMatchingDomain`, and for object cookies calls only `validate()`, which checks name/value characters, not domain matching. Due to index size limits I could not exhaustively rule out a caller in `networking-browser` or `networking-node` packages that may not have been indexed.

### Impact Explanation
If (and only if) some consumer wires `assertMatchingDomain` into real cookie acceptance from `Set-Cookie` responses, this bug lets an IP-literal `Domain` string bypass the "not an IP address" restriction of RFC 6265 domain matching, potentially allowing a cookie meant for one IP-addressed origin to be accepted for an unrelated string that happens to share a numeric suffix — corrupting origin-scoped cookie boundaries. Given the current evidence, I could not confirm this validator is actually invoked in the reachable production cookie-set path, which limits confidence in end-to-end wallet compromise via this exact route.

### Likelihood Explanation
The regex defect itself is unconditionally true (100% reproducible via a plain unit test) and requires no special preconditions to trigger at the function level. However, exploitation requires that `assertMatchingDomain` actually gate origin acceptance of `Set-Cookie` data reachable from attacker-controlled dapp/origin traffic — a link I could not verify in the indexed code.

### Recommendation
Fix the regex to use single backslashes (`\d`, `\.`) so it correctly matches IPv4 dotted-decimal strings, and extend `isHostname` to also reject IPv6 literals (addressing the existing `// TODO: also make sure this ain't a v6 ip address` comment), e.g. via `net.isIP()` equivalent logic. Additionally, verify/confirm whether `assertMatchingDomain` is (or should be) invoked from every cookie-jar `set()` implementation (mobile, browser, node) so the intended origin-isolation guarantee is actually enforced end-to-end.

### Proof of Concept
Add to `modules/networking-common/src/cookie/validators.spec.ts`:
```ts
it('should not treat a real IPv4 address as a hostname', () => {
  // isHostname is not exported; test indirectly via isSubdomain-driven assertMatchingDomain
  expect(() => assertMatchingDomain('1.1', '192.168.1.1')).toThrow() // should reject IP suffix match
})
```
Fuzz plan: generate a corpus of valid IPv4 addresses (`0.0.0.0`–`255.255.255.255`), malformed numeric strings (`999.999.999.999`), and IPv6 literals; for each, assert that `isSubdomain(ipLiteral, anySuffix)` never returns `true` against an unrelated real hostname/suffix. Current code fails this invariant for all valid IPv4 inputs because `v4.test()` never returns `true`.

function assertMatchingDomain(domain: string | undefined, originDomain: string) {
  if (domain === undefined) return

  // Domain matching: https://datatracker.ietf.org/doc/html/rfc6265#section-5.1.3
  if (domain === originDomain) return

  if (isSubdomain(domain, originDomain)) {
    throw new Error(
      `Cannot set a cookie for a subdomain. Tried to set ${domain} with origin ${originDomain}`
    )
  }

  if (isSubdomain(originDomain, domain)) {
    return
  }

  throw new Error(
    `Cannot set a cookie for a third party origin. Tried to set ${domain} with origin ${originDomain}`
  )
}
```

function isSubdomain(value: string, domain: string): boolean {
  /*
   *  - The domain string is a suffix of the string.
   *  - The last character of the string that is not included in the
   *     domain string is a %x2E (".") character.
   *  - The string is a host name (i.e., not an IP address).
   */

  return value.endsWith(domain) && value.replace(domain, '').endsWith('.') && isHostname(value)
}
```
