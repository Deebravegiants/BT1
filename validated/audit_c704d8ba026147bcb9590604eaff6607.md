## Title
Duplicate input tokens in a Tron `IntentGatewayV2.placeOrder` accumulate into a single escrow bucket, letting a solver over-release escrow relative to a single leg's fill — (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

## Summary
The mainline EVM `IntentGatewayV2.sol` explicitly rejects orders with duplicate input tokens before crediting escrow, with an accompanying regression test noting this was fixed because "same-chain partial fills over-release repeated input escrow." [1](#0-0) [2](#0-1)  The Tron variant of the same contract, however, still uses `_orders[commitment][token] += reducedInputs[i].amount` with no duplicate-token check, so a user (or a user colluding with a solver) can place an order whose `order.inputs` array repeats the same token across multiple legs, causing their amounts to be merged into one escrow slot rather than kept per-leg. [3](#0-2) 

## Finding Description
This mirrors the analog bug class: state from one "position"/leg (a prior collateral/leg contribution) is silently folded into the accounting for a subsequent leg, inflating what is available to be drawn down by a single triggering action — exactly the Rubicon pattern where unspent borrow capacity from a prior position was folded into a new position's borrow, breaking the intended per-position risk isolation.

In the Tron `placeOrder`, escrow is credited per input leg with an *accumulating* assignment instead of a keyed, once-only assignment: [4](#0-3) [5](#0-4) 

There is no equivalent of the mainline contract's duplicate-token guard, which on EVM reverts with `InvalidInput` before any escrow is credited: [1](#0-0) 

The regression test on the mainline contract documents precisely the failure mode this class of bug produces — the escrow buckets for two legs sharing a token "previously merged into one escrow bucket," enabling a fill of one (smaller) leg to release escrow sized for the combined (larger) total: [6](#0-5) 

Because the same-chain fill path (`IntrinsicIntents._fillSameChain`, shared logic across chains) computes proportional escrow release from `order.inputs[i].amount` and looks up `_orders[commitment][token]` by output-index-independent token key, a merged escrow bucket for a repeated input token means a solver filling one leg (whose `totalRequired` for that leg is smaller than the sum of both merged input legs) can trigger release of an escrow amount computed against the *combined* balance, rather than the amount actually deposited for that specific leg. [7](#0-6) 

## Impact Explanation
This is a concrete over-release-of-escrowed-funds vulnerability: a maliciously constructed order can cause the gateway to pay out more escrow to a solver (or via a partial/full fill sequence) than the intended per-leg amount, resulting in permanent loss of user/gateway-held funds on the Tron deployment of `IntentGatewayV2`. This directly satisfies "concrete theft or permanent freezing of funds" via unauthorized escrow release, reached from a single `placeOrder` + `fillOrder` transaction pair by an unprivileged user/solver — no admin, governance, or privileged role is required.

## Likelihood Explanation
High. `placeOrder` takes an arbitrary `Order.inputs` array with no validation preventing duplicate tokens on Tron, and any ordinary user calling `placeOrder` followed by a solver calling `fillOrder` (which can be the same actor colluding, or simply a normal user constructing a crafted order) can trigger the merged-escrow condition. The mainline EVM contract's own regression test and fix commentary confirm this exact merge behavior is a known, previously-exploited defect pattern in this codebase — it was fixed on the primary EVM contract but the fix was not ported to the Tron variant.

## Recommendation
Port the duplicate-input-token rejection from `evm/src/apps/IntentGatewayV2.sol` (`placeOrder`'s pre-check reverting `InvalidInput` on any repeated `order.output.assets[i].token` / equivalently `order.inputs[i].token`) into `evm/tron/contracts/apps/IntentGatewayV2.sol`, and replace the accumulating `_orders[commitment][token] += ...` assignments with the same single-assignment-with-duplicate-check pattern (`if (_orders[commitment][token] != 0) revert InvalidInput(); _orders[commitment][token] = reducedInputs[i].amount;`) used on the mainline contract.

## Proof of Concept
1. On the Tron deployment, a user calls `placeOrder` with `order.inputs = [ {token: USDC, amount: 1200}, {token: USDC, amount: 1000} ]` and two output legs.
2. Escrow crediting loop runs `_orders[commitment][USDC] += 1200` then `+= 1000`, leaving `_orders[commitment][USDC] == 2200` merged into a single bucket, unlike the mainline contract which would revert this order outright. [5](#0-4) 
3. A solver fills only the smaller output leg (whose `totalRequired` in escrow terms was intended to correspond to the 1000-amount input leg). Because escrow release logic reads/derives amounts from the merged per-token bucket rather than a per-leg bucket, the solver can receive escrow computed against the combined 2200 balance for completing only the smaller leg, over-releasing funds relative to what that leg actually escrowed.
4. This exact "over-release" failure mode is the one the mainline EVM regression test (`testRevert_PlaceOrder_DuplicateInputTokens`) was written to prevent, confirming this class of bug's real-world reachability in this codebase. [6](#0-5) 

*Note: due to index size limits, I could not view the Tron contract's `fillOrder`/`_fillSameChain`-equivalent fill logic in full (it wasn't found by name search in this pass), so the exact release computation on Tron is inferred from the mainline `IntrinsicIntents._fillSameChain` shared design and the placeOrder escrow-crediting code confirmed present on Tron. A Devin session with full repository access should verify the Tron fill-path arithmetic against the merged bucket to confirm the exact over-release magnitude before filing.*
