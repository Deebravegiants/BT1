## Analog Found

### Title
Overly Permissive `MAX_ORACLE_AGE` Ceiling Allows Stale Chainlink Prices to Mis-price Gas Sponsorship in `SimplexPaymaster` - (File: `evm/src/utils/SimplexPaymaster.sol`)

### Summary
`SimplexPaymaster` is a permissionless ERC-4337 paymaster that lets any user pay gas in a whitelisted ERC-20 token, converting cost via two Chainlink feeds (native/USD and token/USD). The staleness bound on these feeds, `maxOracleAge`, is governance-configurable up to a hard ceiling of 7 days — an order of magnitude beyond what is safe for a volatile native-asset price feed used to price real-time gas sponsorship, mirroring the reported `Vault.vy` issue where a 24-hour `ORACLE_FRESHNESS_THRESHOLD` was flagged as unsafe for rapidly moving markets.

### Finding Description
`_getOraclePrice` only rejects a Chainlink round if it is *older* than `maxOracleAge`; it performs no other sanity check on divergence between the oracle price and the live market price: [1](#0-0) 

`maxOracleAge` is bounded only by the constant `MAX_ORACLE_AGE`, which is set to 7 days: [2](#0-1) 

and governance's `updateParams` handler only checks the value is nonzero and `<= MAX_ORACLE_AGE`, with no additional constraint tied to the actual volatility of the configured native/token pair: [3](#0-2) 

`_tokenPrice` derives the token-per-wei-of-gas rate directly from both oracle reads without any deviation/circuit-breaker check: [4](#0-3) 

This price feeds `_fetchDetails`, which is invoked during `validatePaymasterUserOp` for every UserOperation that uses this paymaster — i.e., reachable by any unprivileged "bandwidth purchaser" submitting a UserOperation: [5](#0-4) 

The project's own internal design-decision notes acknowledge this exact class of risk was identified and explicitly deferred rather than fixed — "bounding `validationData`'s `validUntil` by oracle freshness so bundlers drop soon-to-be-stale ops... Sound in principle... but... out of scope for this pass": [6](#0-5) 

### Impact Explanation
If the native-asset price rises sharply (e.g., a rally following a stale feed's last update) within the 7-day permitted staleness window, `nativeUsd` remains understated, making `tokenPrice` (token base units charged per wei of native gas) artificially low. Any unprivileged UserOp sender can then repeatedly pay for EntryPoint-sponsored gas at a stale, underpriced exchange rate, systematically draining the paymaster's native EntryPoint deposit/stake relative to the ERC-20 revenue collected — a real transfer of value from the paymaster/treasury to callers, and, at scale, an insolvency/freezing condition for the paymaster (unable to cover legitimate future sponsorship or unstake obligations). This is directly analogous to the reported "stale oracle" impact of "mispriced transactions or incorrect contract state," except here it is concretely monetizable because the mispriced quantity is the amount of native gas subsidized per UserOp.

### Likelihood Explanation
Any address can construct and submit a UserOperation using this paymaster's mode 0x00/0x02 paths — no privileged role required. The 7-day ceiling combined with the lack of any deviation check between rounds means an attacker only needs a native asset with a sufficiently large Chainlink heartbeat and a favorable price move within that window (a routine occurrence for less-liquid or infrequently-updated feeds), making exploitation a matter of monitoring feed staleness rather than any exotic precondition.

### Recommendation
Cap `MAX_ORACLE_AGE` much lower and scale it to the true heartbeat of the configured feeds (as the code comment for `maxOracleAge` itself already notes heartbeats vary from ~27s to 24h), and additionally implement the deferred safeguard of bounding `validUntil`/`validAfter` by oracle freshness so bundlers reject a UserOp before a price goes stale mid-flight, rather than solely gating with a static after-the-fact age check.

### Proof of Concept
1. Governance (or default) sets `maxOracleAge` near `MAX_ORACLE_AGE` (7 days) for a native/USD feed with a multi-day heartbeat.
2. Native asset price rises materially after the feed's last update but before `maxOracleAge` elapses (feed is still "fresh" per the check).
3. Attacker submits UserOperations through `SimplexPaymaster`, paying in the registered ERC-20 token; `_fetchDetails` → `_tokenPrice` → `_getOraclePrice` returns the stale, understated `nativeUsd`, so `tokenPrice` undercharges relative to the real market rate.
4. Attacker repeats across many UserOps, extracting subsidized native gas from the paymaster's EntryPoint deposit at the stale exchange rate until the feed updates, resulting in a net loss to the paymaster/treasury.

        PackedUserOperation calldata userOp,
        bytes32 /* userOpHash */
    )
        internal
        view
        override
        returns (uint256 validationData, IERC20 token, uint256 tokenPrice)
    {
        bytes calldata data = userOp.paymasterData();
        if (data.length < 21) revert InvalidPaymasterData(data.length);

        uint8 mode = uint8(data[0]);
        if (mode != 0x00 && mode != 0x02) revert InvalidMode(mode);

        address tokenAddr = address(bytes20(data[1:21]));

        TokenConfig memory cfg = tokenConfigs[tokenAddr];
        if (address(cfg.tokenOracle) == address(0)) revert TokenNotRegistered(tokenAddr);
        if (!cfg.active) revert TokenNotActive(tokenAddr);

        tokenPrice = _tokenPrice(cfg);
        token = IERC20(tokenAddr);
        validationData = 0; // no time-range restriction

        if (mode == 0x02) {
            (,,, uint256 deadline,,,) = _parsePermit2Data(data);
            // Surfacing the permit deadline as validUntil lets bundlers drop
            // expiring ops instead of discovering it through a Permit2 revert.
            uint48 validUntil = deadline > type(uint48).max ? 0 : uint48(deadline);
            validationData = ERC4337Utils.packValidationData(true, 0, validUntil);
        }
    }

    /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }

# 2026-08-19 — Not adopted: soft-failing the prefund, and oracle-derived validity bounds (#1071)

Rejected: returning `prefunded = false` instead of reverting in the mode-2 `_prefund`. Upstream advises it to protect bundler reputation, but reading EntryPoint v0.8 shows both outcomes are `revert FailedOp` — AA33 for a paymaster revert, AA34 for a sig-failure — so both revert `handleOps` identically. The change would trade the `Permit2Failed(token, reason)` diagnostic, which carries Permit2's own revert data, for no bundle-level benefit.

Also deferred at the maintainer's direction: bounding `validationData`'s `validUntil` by oracle freshness so bundlers drop soon-to-be-stale ops instead of building bundles that revert. Sound in principle and would have made stale-oracle failures expire cleanly, but it touches every pricing path and was out of scope for this pass.
