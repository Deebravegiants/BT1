### Title
Escrow release (`onAccept` → `_withdraw`) permanently stuck when any single escrowed order token becomes non-transferable (paused/blacklisted) - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentsBase._withdraw()` releases every token escrowed for an order commitment in one loop using `SafeERC20.safeTransfer`, which reverts the entire function if any single token transfer fails. This function is invoked from the permissionless Hyperbridge delivery path (`onAccept`/`onGetResponse`), and a failed `onAccept` call is deliberately made retriable forever by `EvmHost`. If any one of an order's escrowed tokens is a pausable/blacklistable asset (e.g. a USDC-style token that later pauses transfers or blacklists the beneficiary/solver), the whole multi-token escrow release for that order — including unrelated, perfectly healthy tokens and the accumulated relayer/protocol fees — becomes permanently un-deliverable for as long as that one token remains blocked.

### Finding Description
`_withdraw` iterates over `body.tokens` and calls `IERC20(token).safeTransfer(beneficiary, amount)` for each escrowed token in the order, finalizing (marking filled, paying fees, emitting events) only if the whole loop succeeds: [1](#0-0) 

This is called from `ExtrinsicIntents.onAccept` for both `RedeemEscrow` and `RefundEscrow` request kinds, and from `onGetResponse` for the cancel-from-source path: [2](#0-1) [3](#0-2) 

`onAccept` is dispatched by `EvmHost.dispatchIncoming`, which is permissionless to trigger (any relayer submits the proof), and on revert simply deletes the request receipt so the same message "can be retried" — it never marks the request as permanently failed or provides a fallback path: [4](#0-3) 

Because `safeTransfer` reverts the entire loop on the first failing token, an order that escrows multiple input tokens (a common flow — `order.inputs` is an array, and `_orders[commitment][token]` accounting supports arbitrary tokens per commitment) can never be settled if even one of those tokens becomes non-transferable to the beneficiary. This mirrors the reported Balancer-pause pattern: an external asset-level restriction (pause/blacklist on one token) makes an unprivileged, otherwise-correct settlement call revert indefinitely, and Hyperbridge's own retry design (delete-and-retry) guarantees the message is resubmitted forever without ever succeeding, rather than degrading gracefully per-token.

### Impact Explanation
All escrowed tokens for the affected order — not just the blocked token — are frozen, plus the escrowed relayer/protocol fee (`TRANSACTION_FEES`) which is only paid out when `finalize` succeeds. This is a real freezing-of-funds condition reachable by a single relayed settlement message, triggered by ordinary external token behavior (issuer pause, blacklist, upgradeable-token bug, or a fee-on-transfer/rebasing token whose balance later can't cover the recorded escrow amount), not by any Hyperbridge admin action.

### Likelihood Explanation
Likelihood is moderate-to-high in practice: IntentGateway orders can escrow tokens like USDC/USDT that carry issuer-controlled pause/blacklist functionality, and orders are user-supplied, so a solver or malicious order-placer can also deliberately include a token they know is likely to become blocked (or is already blacklisted for the intended beneficiary) to grief settlement of the entire multi-token order.

### Recommendation
Make `_withdraw` resilient to a single token's transfer failure: either (a) process each token transfer independently with try/catch and only defer/retain the failed leg for later retry while still releasing the others and paying fees, similar to the isolation pattern already used in `HyperbridgeLzEndpoint.onAccept` (see the `try/catch` + retained payload/retry design there), or (b) allow partial finalization so a stuck token doesn't block release of the rest of the escrow and the fee payment. [5](#0-4) 

### Proof of Concept
1. User places a cross-chain order escrowing two input tokens: a normal ERC20 and a USDC-style token with issuer pause/blacklist capability, via `placeOrder`.
2. Solver fills the order on the destination chain; `RedeemEscrow` is dispatched back to source chain.
3. Before the relayer delivers the proof, the pausable token's issuer pauses transfers (or blacklists the solver/beneficiary address) for a compliance/incident reason unrelated to Hyperbridge.
4. Relayer submits the settlement message; `EvmHost.dispatchIncoming` calls `IntentGatewayV2.onAccept` → `_withdraw`.
5. The loop successfully transfers the first (healthy) token, then reverts on `safeTransfer` for the paused/blacklisted token.
6. `dispatchIncoming` catches the revert, deletes the request receipt "so it can be retried" — but every future retry hits the same revert until the token is unpaused/unblacklisted, indefinitely freezing both the healthy token's escrow (transfer is rolled back with the revert) and the accumulated fee payout for that order.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
