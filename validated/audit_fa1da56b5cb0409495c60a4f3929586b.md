### Title
Webhook HMAC Verification Does Not Cover Shop/Topic Headers, Allowing Cross-Tenant Webhook Spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while `shop`, `topic`, `webhook_id`, and `api_version` are read from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` trusts these header-derived values to route the payload to a handler tagged with a specific `shop`, breaking the binding between "HMAC-verified bytes" and "shop the payload is attributed to."

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
while `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from request headers with no HMAC coverage: [2](#0-1) 

`Utils::HmacValidator.validate` only checks the signature against `to_signable_string` (the raw body) and the app's shared `api_secret_key`: [3](#0-2) 

`Registry.process` then trusts the header-derived `request.shop` and `request.topic` to attribute the (HMAC-verified) body to a tenant and dispatch it: [4](#0-3) 

The broken identity binding is:
`HMAC-verified(raw_body)` ≠ `shop used to process/attribute the payload (request.shop from header, unsigned)`

Because Shopify apps share a single `api_secret_key` across every shop that installs them, any merchant who installs the app can obtain a genuinely-signed webhook body for an event they trigger in their own store (the HMAC only signs the JSON body). Since the `shopify-shop-domain` (and `shopify-topic`/`shopify-webhook-id`) headers are not part of the signed content, an attacker controlling the webhook delivery to the host app's endpoint (e.g., replaying/relaying a request with modified headers) can substitute an arbitrary victim shop's domain in the `shop` header while keeping the valid HMAC over their own attacker-controlled body. `Registry.process` will pass HMAC validation and dispatch `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` attributing attacker-controlled data to the victim shop.

### Impact Explanation
This breaks tenant isolation: an app built on this library that keys its persistence, business logic, or side effects (e.g., updating inventory, creating orders, sending notifications) off `WebhookMetadata#shop` can be made to apply attacker-supplied data under an arbitrary victim shop's identity, i.e., cross-tenant data injection/corruption using only knowledge that is available to any shop that installs the app (no `api_secret_key`, access token, or privileged account required).

### Likelihood Explanation
Requires the attacker to (a) install the app on any shop, (b) capture a validly-HMAC-signed webhook body from an event they trigger, and (c) be able to influence the request(headers) delivered to the app's webhook endpoint (e.g. via a proxy/replay ability, or if the host framework exposes the endpoint to arbitrary posted requests with attacker-controlled headers rather than solely Shopify's direct delivery). Likelihood depends heavily on the host application's deployment; this gem itself provides no protection against header spoofing because `shop`/`topic` are never covered by the signature it verifies.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the HMAC-signable string (or otherwise cryptographically bind them to the verified payload), or clearly document that consumers of `ShopifyAPI::Webhooks::Request` must independently authenticate the source/headers (e.g., verify shop is a known, installed shop and reject requests not delivered directly from Shopify's servers) before trusting `request.shop`/`request.topic` for tenant routing.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker.myshopify.com`, obtaining the app's shared `api_secret_key` usage on any legitimately triggered webhook (e.g., `orders/create`) with attacker-controlled order data.
2. Attacker captures the raw body and the valid `shopify-hmac-sha256` header from that legitimate webhook delivery.
3. Attacker (or a component that can influence header delivery to the endpoint) resends the same raw body/HMAC to the app's webhook endpoint but with `shopify-shop-domain: victim.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` at [5](#0-4)  returns `true` because only the raw body is checked.
5. `Registry.process` dispatches the handler with `shop: "victim.myshopify.com"` and attacker-controlled `body`, causing the host app to process/store attacker data under the victim's tenant.
