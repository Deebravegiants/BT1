### Title
Cross-Account Address Disclosure via `getConnectedAccounts` in Connected Origins - (File: `features/connected-origins/module/connections.js`)

### Summary
The external report describes a bug class where a scoped/tracked value (`amountInShelter`) is not preserved when a state is reset (`exitShelter`), causing value meant for a specific scope (donations) to bleed into an unrelated party (the raw contract balance) because the reset logic only checks a coarse boolean flag (`activated`) rather than reconciling the exact scoped amount. The analogous pattern in this codebase is `ConnectedOrigins.getConnectedAccounts()`, which gates exposure of wallet-account data behind a single coarse `trusted` boolean per origin rather than the specific set of accounts the origin was actually granted, causing addresses of unrelated wallet accounts to bleed to the origin.

### Finding Description
When a website connects to Exodus, `connectedOrigins.add()` stores a single `trusted` flag along with `connectedAssetName`/`assetNames` for that origin [1](#0-0) . Later, `getConnectedAccounts({ origin })` is the only gate used to decide whether to return wallet-account data to that origin, and it checks nothing but the coarse `isTrusted` boolean: [2](#0-1) 

Once `isTrusted` passes, the function iterates over **every key** of `#connectedAccountsAtom`, which is populated from **all enabled wallet accounts** in the wallet (see `#getAccounts`, which maps over `Object.values(await this.#enabledWalletAccountsAtom.get())`) [3](#0-2) , and returns the address of each account for the assets the origin declared interest in. There is no per-account authorization check against a specific list of accounts the user consented to share with that origin — `value.accounts`/`value.walletAccount` fields exist on the stored origin record but are never consulted inside `getConnectedAccounts` [4](#0-3) .

This mirrors the Shelter bug's root cause: a binary/coarse state transition (`activated`/`trusted`) is used as the sole authorization gate, while a supposedly scoped resource (`amountInShelter` / per-account authorization) is not actually enforced when the resource is handed back out, so data/value belonging to accounts or parties outside the intended scope is disclosed/returned.

### Impact Explanation
Per documented single-account provider semantics (e.g. `eth_accounts` returns only the single active account address, and Solana's provider only exposes one `publicKey`) [5](#0-4) [6](#0-5) , a dApp is only meant to see the currently active/connected account. However, `getConnectedAccounts` unconditionally returns **addresses for every enabled wallet account** in the user's wallet to any origin that was merely marked `trusted` for one connection [7](#0-6) . This links/deanonymizes all of a user's separate wallet accounts to a single website, enabling cross-account address correlation, tracking/fingerprinting, and increases phishing/targeting surface for accounts the user never intended to expose to that origin — a concrete cross-account privilege bleed across the origin trust boundary.

### Likelihood Explanation
Any website the user has connected to and marked trusted (a normal, common user action) can call the API surface backed by `connectedOrigins.getConnectedAccounts` (exposed via `connectedOriginsApiDefinition`) [8](#0-7)  without any additional per-account consent check, so exploitation requires no privileged access — only a standard, single-account dApp connection already granted by the user.

### Recommendation
Scope `getConnectedAccounts` to only the wallet account(s) explicitly authorized for that origin (e.g., using the already-stored `walletAccount`/`accounts` fields on the origin record) instead of returning every entry from `#connectedAccountsAtom`. Reconcile authorization per-account the same way the mitigation for the Shelter bug recommends reconciling per-scope amounts (`amountInShelter`) rather than relying on a single coarse boolean flag.

### Proof of Concept
1. User connects Wallet Account A to `attacker-site.com`, setting `trusted: true` with `connectedAssetName: 'solana'`.
2. User separately has Wallet Account B (unrelated, never shared with `attacker-site.com`).
3. `attacker-site.com` calls `exodus.connectedOrigins.getConnectedAccounts({ origin: 'attacker-site.com' })`.
4. Per `getConnectedAccounts`'s implementation, since `isTrusted` returns true, it iterates `Object.keys(accounts)` — this includes Wallet Account B — and returns Account B's Solana address to `attacker-site.com`, even though the user never consented to share Account B with that origin [9](#0-8) , exactly as demonstrated in the existing test showing multiple accounts returned for a single trusted origin [7](#0-6) .

  getConnectedAccounts = async ({ origin }) => {
    const isTrusted = await this.isTrusted({ origin })
    if (!isTrusted) return []

    const value = await this.#getOrigin({ origin })
    const assetNames = [value.connectedAssetName, ...(value.assetNames ?? [])].filter(
      (name, index, ary) => Boolean(name) && ary.indexOf(name) === index
    )

    const activeWalletAccount = await this.#activeWalletAccountAtom.get()
    const accounts = await this.#connectedAccountsAtom.get()

    const connectedAccounts = []
    for (const name of Object.keys(accounts)) {
      if (name === activeWalletAccount) continue
      connectedAccounts.push({ name, addresses: pick(accounts[name].addresses, assetNames) })
    }

    connectedAccounts.unshift({
      name: activeWalletAccount,
      addresses: pick(accounts[activeWalletAccount].addresses, assetNames),
    })

    return connectedAccounts
  }
