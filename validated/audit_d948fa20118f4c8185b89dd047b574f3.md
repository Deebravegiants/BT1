### Title
Backend signup confirmation (duplicate/fraud detection) is bypassed for user-centric signups, allowing a misattributed "successful" signup - (File: `src/plans/mod.rs`)

### Summary
`MasterPlan::do_signup()` has two code paths that both end up marking a signup as `Success` and triggering the same downstream side effects (UI success animation, `dbus::Signup::signup_finished(true)`, `SignupEnded { success: true }` relay message, `debug_report.signup_successful()`). Only one of these paths actually calls the backend to confirm the signup is valid, non-duplicate and non-fraudulent. The other path infers success purely from local state and skips that confirmation entirely, exactly mirroring the `moveQuoteToken()`/`removeQuoteToken()` asymmetry where one function applies a critical consistency check and the sibling function that reaches the same end-state does not.

### Finding Description
In `do_signup()`, after biometric capture/pipeline/local fraud-check computation, the code branches on `user_centric_signup`: [1](#0-0) 

- Else branch (`enroll_user`): calls `enroll_user::Plan::run()`, which POSTs the signup to the backend (`signup_post::request`) and then polls `signup_poll::request()` until the backend authoritatively reports `Status::Completed` with `success: true`. The code explicitly documents that backend-side failures here include duplicate signups, legacy/inflight matches, and backend-detected fraud: [2](#0-1) 

- If branch (`user_centric_signup && !ignore_user_centric_signups`): `enroll_user()` (and therefore `signup_post`/`signup_poll`) is never called. `success` is derived solely from `signup_reason`, which is computed locally: [3](#0-2) 

`signup_reason` is `Normal` whenever the local pipeline succeeded and the on-device `detect_fraud()` step (also called `fraud_detected`) returns `false`. In this build, `detect_fraud()` is fully stubbed out and unconditionally returns `false`: [4](#0-3) 

So for the `user_centric_signup` branch, "success" reduces to "pipeline produced output," with no backend confirmation of uniqueness/fraud/duplicate status at all. This mirrors the audited bug: `removeQuoteToken()` (the `enroll_user` path) performs the check that reconciles global accounting state (backend confirmation of a valid, unique, non-fraudulent signup), while `moveQuoteToken()` (the `user_centric_signup` bypass path) reaches the same terminal state (`SignupStatus::Success`, `debug_report.signup_successful()`) without performing that check — an accounting/authorization inconsistency between two paths that are supposed to represent the same real-world event ("this Orb identity was legitimately and uniquely enrolled").

The resulting `success`/`signup_status` feeds directly into user-visible and system-visible signup-completion signals: [5](#0-4) [6](#0-5) 

### Impact Explanation
Under this branch, a signup can be locally recorded and reported (to the UI, via DBus signal, and via the Orb Relay `SignupEnded` message) as `Success`/verified without the Orb ever receiving backend confirmation that the biometric signup was accepted, unique, and free of fraud/duplicate flags. This is a misattributed-signup class of impact: local state ("this person successfully and uniquely signed up") diverges from the authoritative backend record, the same class of impact as the referenced accounting-desync bug (bucket state marked healthy locally while the true backend-equivalent state — bankruptcy/duplicate — was never recorded).

### Likelihood Explanation
The branch is taken whenever the backend-supplied `user_centric_signup` flag on the user QR/app data is `true` and the Orb's `ignore_user_centric_signups` config is `false` (the default, per `src/config.rs` `Default` impl: `ignore_user_centric_signups: false`). This is a normal, reachable production code path (not test-only, not requiring a malicious operator/node), gated only by backend-controlled configuration/data that determines the signup mode.

### Recommendation
Ensure the same authoritative backend confirmation (duplicate/fraud/uniqueness check equivalent to `enroll_user`'s `signup_post`/`signup_poll` round trip) is performed, or an equivalent explicit confirmation signal from the app-centric flow is required, before setting `enroll_user::Status::Success` / `SignupStatus::Success` and firing success side effects in the `user_centric_signup` branch of `do_signup()` (`src/plans/mod.rs`, lines 639-656).
