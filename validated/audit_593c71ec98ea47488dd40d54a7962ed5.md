## Finding: Missing per-asset ownership check on `pallet-hyper-fungible-token::update_token` allows a lower-privileged caller to hijack another user's registered token mapping

### Title
Improper access control in `pallet-hyper-fungible-token::update_token` allows any `CreateOrigin`-authorized account to remap another account's registered token contract, enabling unbacked mint / theft of escrowed funds - (File: `modules/pallets/hyper-fungible-token/src/lib.rs`)

### Summary
`pallet-hyper-fungible-token` is Hyperbridge's replacement for the deprecated `pallet-token-gateway`, explicitly designed so that "each token is its own bridge application, with no governance overhead, no shared custody pool, and no token-governor" [1](#0-0) . Both `register_token` and `update_token` are gated only by a single, non-resource-scoped `T::CreateOrigin::ensure_origin(origin)?` check [2](#0-1) [3](#0-2) . Neither call verifies that the caller is the account that originally registered the `asset_id` being modified — there is no "owner" or "registrant" field stored anywhere in the pallet's storage items (`TokenContracts`, `ContractToAsset`, `NativeAssets`, `Precisions`) [4](#0-3) .

This mirrors the aimeos CVE-2024-39323 bug class exactly: a role intended to have narrow/self-scoped privileges (an "editor" that can manage its own token) can instead mutate a resource belonging to a different, unrelated party (an "admin"'s or another user's token), because the access-control check tests only role membership, not resource ownership.

### Finding Description
`update_token` accepts a `TokenUpdate` containing an arbitrary `asset_id` and rewrites the `TokenContracts` and `ContractToAsset` maps for that asset on any EVM chain the caller specifies [5](#0-4) :

```rust
pub fn update_token(origin: OriginFor<T>, update: TokenUpdate<AssetId<T>>) -> DispatchResult {
    T::CreateOrigin::ensure_origin(origin)?;
    ...
    for (chain, config) in update.add_chains {
        ...
        TokenContracts::<T>::insert(chain, update.asset_id.clone(), token_contract.clone());
        ContractToAsset::<T>::insert(chain, token_contract, update.asset_id.clone());
        Precisions::<T>::insert(update.asset_id.clone(), chain, config.decimals);
    }
```

`ContractToAsset` is documented as the reverse lookup "used in `on_accept` to find which local asset an incoming message corresponds to" [6](#0-5) . Because `update_token` performs no check that `msg.sender` (the extrinsic origin) is the party that originally called `register_token` for that specific `asset_id`, any second account that also satisfies `T::CreateOrigin` can:
1. Call `update_token` targeting a victim's already-registered `asset_id` (e.g. a bridged USDC asset).
2. Overwrite `TokenContracts[chain][asset_id]` and `ContractToAsset[chain][attacker_contract]` to point at an attacker-controlled EVM contract address.
3. Have the attacker's own contract on that EVM chain send a message that the pallet's `on_accept` will resolve — via the now-poisoned `ContractToAsset` mapping — to the victim's legitimate `asset_id`.

Because `register_token`'s `native` flag determines custody model (native assets are locked/unlocked from a shared pallet escrow account, non-native assets are minted/burned) [7](#0-6) , an attacker who hijacks the reverse mapping for a `native: true` asset can forge an "incoming" message that the pallet will treat as authentic and release custodied funds to an attacker-chosen beneficiary, or for a `native: false` asset can trigger unbacked minting. The pallet's own test suite demonstrates that `register_token`/`update_token` succeed under an arbitrary signed account (`ALICE`) with no ownership binding recorded [8](#0-7) , and the pallet's own documented purpose ("no governance overhead") strongly implies `CreateOrigin` is meant to be broadly available (e.g. `EnsureSigned<AccountId>`, as literally used for the predecessor pallet's example config) [9](#0-8) , rather than restricted to a single trusted governance origin.

**Uncertainty:** I could not confirm the exact `CreateOrigin` binding used in the production `gargantua`/`nexus` runtimes (`parachain/runtimes/gargantua/src/ismp.rs`, `parachain/runtimes/nexus/src/ismp.rs`) within the available tool budget — I only confirmed the config type exists there via `grep`, not its concrete value. If `CreateOrigin` is bound to a single fixed root/governance account, this becomes a governance self-inflicted bug and is out of scope per the rules (malicious-governance excluded). If it is bound to `EnsureSigned` (any account) or any origin satisfied by more than one distinct principal — consistent with the pallet's "no governance overhead, each token is its own bridge application" design goal — this is a directly reachable, unprivileged-actor vulnerability.

### Impact Explanation
If `CreateOrigin` permits more than one principal (which the pallet's design intent and its own permissive unit test strongly suggest), any such account can overwrite another party's token-to-contract mapping and subsequently forge cross-chain deliveries that the pallet accepts as legitimate for that `asset_id`, leading to unbacked minting or theft of custodied (locked) native-asset funds — a High severity impact matching "concrete theft ... unbacked mint" in the validation criteria.

### Likelihood Explanation
The action requires only a single signed extrinsic (`update_token`) from any account authorized by `CreateOrigin`, with no proof, no multi-party approval, and no ownership check tying the caller to the `asset_id` in the request. If `CreateOrigin` is permissively configured (as the deprecated-pallet docs example and the design philosophy suggest), likelihood is high and trivially exploitable by any signed account.

### Recommendation
Store the registering account (or an explicit owner/admin) alongside each `asset_id` in `NativeAssets`/a new `AssetOwners` map when `register_token` runs, and require `update_token` to verify `ensure!(caller == AssetOwners::<T>::get(asset_id), Error::<T>::NotAssetOwner)` in addition to (or instead of) the blanket `CreateOrigin` check, before permitting any mutation of `TokenContracts`/`ContractToAsset`/`Precisions` for that asset.

### Proof of Concept
1. Account A calls `register_token` (satisfying `CreateOrigin`) to register `asset_id = X`, mapping `TokenContracts[Evm(1)][X] = legit_contract` and `ContractToAsset[Evm(1)][legit_contract] = X`, with `native = true` (so real funds get locked in the pallet's escrow account on `send`).
2. Account B, an unrelated account that also satisfies `CreateOrigin`, calls `update_token` with `asset_id = X`, `add_chains = {Evm(1): {token_contract: attacker_contract, decimals: ...}}`. This succeeds because `update_token` never checks that B registered `X`.
3. Storage now has `TokenContracts[Evm(1)][X] = attacker_contract` and `ContractToAsset[Evm(1)][attacker_contract] = X`.
4. Account B's `attacker_contract` on Evm chain 1 sends a cross-chain message to the pallet. `on_accept` resolves the incoming contract address via the poisoned `ContractToAsset` map to `asset_id = X`, and releases X's custodied (locked) funds to a beneficiary of B's choosing — an unbacked release/mint of A's escrowed asset.

		pub fn update_token(
			origin: OriginFor<T>,
			update: TokenUpdate<AssetId<T>>,
		) -> DispatchResult {
			T::CreateOrigin::ensure_origin(origin)?;

			let local_decimals = if update.asset_id == T::NativeAssetId::get() {
				T::Decimals::get()
			} else {
				<T::Assets as fungibles::metadata::Inspect<T::AccountId>>::decimals(
					update.asset_id.clone(),
				)
			};

			for (chain, config) in update.add_chains {
				// This pallet bridges substrate <-> EVM only; reject non-EVM peers.
				if !matches!(chain, StateMachine::Evm(_)) {
					return Err(Error::<T>::NonEvmPeerChain.into());
				}
				ensure!(
					config.decimals >= local_decimals,
					Error::<T>::ErcDecimalsBelowLocal
				);
				// Remove old reverse mapping if it exists
				if let Some(old_contract) = TokenContracts::<T>::get(chain, update.asset_id.clone())
				{
					ContractToAsset::<T>::remove(chain, old_contract);
				}

				let token_contract = config.token_contract.0.to_vec();
				TokenContracts::<T>::insert(
					chain,
					update.asset_id.clone(),
					token_contract.clone(),
				);
				ContractToAsset::<T>::insert(chain, token_contract, update.asset_id.clone());
				Precisions::<T>::insert(update.asset_id.clone(), chain, config.decimals);
			}

#[test]
fn should_register_and_update_token() {
	use pallet_hyper_fungible_token::types::{ChainConfig, TokenRegistration, TokenUpdate};
	use std::collections::BTreeMap;

	new_test_ext().execute_with(|| {
		let asset_id: H256 = sp_io::hashing::keccak_256(b"NEW_TOKEN").into();
		let contract = vec![0xEEu8; 20];

		let mut chains = BTreeMap::new();
		chains.insert(
			StateMachine::Evm(42),
			ChainConfig { token_contract: H160::from_slice(&contract), decimals: 6 },
		);

		let reg = TokenRegistration { local_id: asset_id, native: false, chains };

		HyperFungibleToken::register_token(RuntimeOrigin::signed(ALICE), reg).unwrap();

		// Verify storage
		assert_eq!(
			pallet_hyper_fungible_token::TokenContracts::<Test>::get(
				StateMachine::Evm(42),
				asset_id
			)
			.unwrap(),
			contract
		);
		assert_eq!(
			pallet_hyper_fungible_token::ContractToAsset::<Test>::get(
				StateMachine::Evm(42),
				&contract
			)
			.unwrap(),
			asset_id
		);
		assert_eq!(
			pallet_hyper_fungible_token::Precisions::<Test>::get(asset_id, StateMachine::Evm(42))
				.unwrap(),
			6
		);
		assert!(!pallet_hyper_fungible_token::NativeAssets::<Test>::get(asset_id));

		// Update: remove chain
		let update = TokenUpdate {
			asset_id,
			add_chains: BTreeMap::new(),
			remove_chains: vec![StateMachine::Evm(42)],
		};

		HyperFungibleToken::update_token(RuntimeOrigin::signed(ALICE), update).unwrap();

		assert!(pallet_hyper_fungible_token::TokenContracts::<Test>::get(
			StateMachine::Evm(42),
			asset_id
		)
		.is_none());
		assert!(pallet_hyper_fungible_token::ContractToAsset::<Test>::get(
			StateMachine::Evm(42),
			&contract
		)
		.is_none());
	});
}
