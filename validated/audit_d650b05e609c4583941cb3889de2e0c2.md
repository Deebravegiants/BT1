### Title
Unbounded return-data copy in native-token transfers can grief escrow release/refund and permanently freeze funds - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`IntentsBase._sendValue` and the tron `IntentGatewayV2.withdraw`/`onAccept` dust-sweep paths perform native ETH transfers with a plain `.call{value: amount}("")` and only check the boolean `success` flag, discarding the returned bytes. Even though the return data is never used, the EVM still copies it into memory as part of the low-level call, so a malicious beneficiary contract can force the caller to pay for and process an arbitrarily large `returndata` blob, causing an out-of-gas revert. Since the beneficiary address is attacker-controllable order/withdrawal data, this can be weaponized to DoS escrow release/refund flows.

### Finding Description
`IntentsBase._sendValue` is the shared native-token transfer primitive used throughout the intents subsystem: [1](#0-0) 

It is invoked from `_withdraw` (escrow release/refund) and `_sweepDust`, both of which use attacker-influenced `beneficiary` addresses taken from order/withdrawal data: [2](#0-1) [3](#0-2) 

The equivalent pattern exists in the tron `IntentGatewayV2.withdraw` (redeem/refund path reachable from `onAccept`/`onGetResponse` after a relayed cross-chain message) and its `SweepDust` handler: [4](#0-3) 

And in `IntrinsicIntents.fillOrder`, where a solver-supplied fill pushes value directly to an order-supplied `beneficiary`: [5](#0-4) 

In all of these, `beneficiary`/`to` is an address supplied by the order creator or embedded in a relayed cross-chain payload — not a trusted, hardcoded address. A malicious actor can set the beneficiary to a contract whose `receive()`/fallback returns a very large blob of data. Because the calls use `.call{value: ...}("")` (a high-level Solidity call that always copies returndata into memory) rather than an assembly-level call that discards it, the EVM must allocate memory and copy the entire returned blob before the `success` boolean can even be checked, at gas cost proportional to the size of the data. This can exhaust the gas forwarded to the transaction, forcing an out-of-gas revert of the whole call.

### Impact Explanation
For `_withdraw` (called during `onAccept`/`onGetResponse` for `RedeemEscrow`/`RefundEscrow` in the intents flow), a griefing beneficiary can force the entire escrow-release/refund transaction to revert. Because `_withdraw` iterates over multiple tokens per commitment and finalizes/marks the order as filled only if the loop completes, a single malicious beneficiary/token entry can block release of all escrowed assets for that commitment, permanently freezing solver and user funds tied to that order and preventing legitimate relayed messages from being applied (a route unable to deliver messages). The same applies to `_sweepDust` for governance dust sweeps, and to the tron `IntentGatewayV2.withdraw`/`SweepDust` handler.

### Likelihood Explanation
Any order creator, solver, or party able to set a `beneficiary`/withdrawal-recipient address in intents/order data controls this address without special privilege — this satisfies the "unprivileged... intent solver" reachability requirement. Deploying a contract with a gas/return-data bomb fallback is trivial and cheap, and the attack can be triggered on the resolving/relaying transaction of a legitimately placed order.

### Recommendation
Replace `.call{value: amount}("")` calls used purely for native-value transfer (in `IntentsBase._sendValue`, `IntentsBase._sweepDust`, tron `IntentGatewayV2.withdraw`/`onAccept` dust sweep, and `IntrinsicIntents.fillOrder`) with an assembly-level call that ignores/discards returndata, e.g.:
```solidity
assembly {
    success := call(gas(), to, amount, 0, 0, 0, 0)
}
```
This avoids copying arbitrary-sized return data into memory, eliminating the gas-griefing vector while preserving the success check.

### Proof of Concept
1. Attacker deploys `EvilBeneficiary` with a `receive()`/fallback that returns e.g. 1,000,000+ bytes of arbitrary data (or simply consumes memory via `mstore` loops) before returning.
2. Attacker places (or fills) an order specifying `EvilBeneficiary` as the `beneficiary` in `Order`/`WithdrawalRequest`.
3. When escrow release is triggered — e.g. via `onAccept` invoking `IntentsBase._withdraw` (or the tron `IntentGatewayV2.withdraw`) — the call `beneficiary.call{value: amount}("")` in `_sendValue` executes against `EvilBeneficiary`, which returns the oversized blob.
4. The EVM copies the full return data into memory before the `success` flag is even evaluated, consuming gas proportional to the blob size; with a sufficiently large return payload the transaction runs out of gas and reverts.
5. Because the escrow-release loop in `_withdraw` must complete fully before `_filled` is finalized, this reverts the entire release, leaving escrowed tokens for that commitment permanently locked and unable to be released or refunded through the normal path.
