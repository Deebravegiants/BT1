### Title
Cross-tenant webhook spoofing via unauthenticated `shop` field not covered by HMAC - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating only the raw request body against the `X-Shopify-Hmac-Sha256` header, then hands the caller a `shop` value that is taken from an entirely separate, unsigned HTTP header. The identity binding "HMAC-authenticated sender == shop attributed to the event" does not hold, because the `shop` field is never part of the signed content.

### Finding Description
`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and compares it with the `hmac` field using `OpenSSL.secure_compare`: [1](#0-0) 

For webhook requests, `to_signable_string` returns only the raw HTTP body: [2](#0-1) 

Meanwhile `shop` is read directly from the `shopify-shop-domain` / `x-shopify-shop-domain` header, which is not included anywhere in the signed payload: [3](#0-2) 

`Registry.process` validates only the HMAC over the body, and then forwards `request.shop` (the unauthenticated header value) straight to the app's handler as the authoritative shop identity for that event: [4](#0-3) 

The equality that should hold is:
`shop_bound_by_hmac(request) == shop_delivered_to_handler(request)`

but in reality:
`shop_bound_by_hmac(request) = undefined` (the signature never touches `shop`)
`shop_delivered_to_handler(request) = request.shop` (attacker-controlled header)

So the two sides are never actually equal in the cryptographic sense — the HMAC only proves "this body was signed by someone holding `api_secret_key`", not "this event pertains to shop X".

The gem's own documentation instructs developers to trust the `shop` field of `WebhookMetadata` as "The shop domain of the webhook" without any caveat about it being unauthenticated: [5](#0-4) 

### Impact Explanation
An attacker who is a legitimate (if malicious) merchant/installer of the app receives real webhook deliveries from Shopify for their own store, complete with a valid HMAC computed by Shopify using the app's real `api_secret_key`. Because the header carrying `shop` is outside the signed content, the attacker can capture one such genuine `(raw_body, hmac)` pair and replay it to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `Registry.process` will still accept the request (the HMAC only checks the untouched body) and will pass the forged `shop` value to the application's webhook handler as if the event genuinely belonged to the victim shop. Any app that uses `WebhookMetadata#shop` to select the tenant context (e.g., to look up the shop's stored session/access token, write to the wrong tenant's records, or trigger tenant-specific side effects) is exposed to cross-tenant data corruption or disclosure — this matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitability requires the attacker to control at least one legitimate, currently-installed shop for the target app (a normal, unprivileged self-service install is sufficient — no leaked secrets or victim credentials needed) and to be able to produce or predict a webhook whose JSON body is shop-agnostic or attacker-influenced (e.g., a topic like `app/uninstalled`, or any webhook whose payload the attacker fully controls through normal store actions, such as creating a product/order with attacker-chosen content). This is a realistic, low-effort scenario for topics with static or attacker-controllable bodies, though for topics whose body contains shop-specific identifiers, exploitation is limited to what the forged shop attribution actually needs (many apps use the header `shop` for routing/lookup, not deep field validation against body content).

### Recommendation
Do not treat `request.shop` as an authenticated value. `Registry.process` (or `Webhooks::Request`) should require the caller to supply the expected/looked-up shop for the endpoint independently (e.g., via URL routing per-shop, or via a lookup by webhook_id/topic against stored sessions) rather than trusting the header value directly, or the library should document explicitly and prominently that `shop`/`WebhookMetadata#shop` is unauthenticated and must be cross-checked by the host application against its own tenant records before being used for any access decision.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com`.
2. Trigger a webhook whose body content is static/attacker-influenced (e.g., `app/uninstalled`, or a `products/create` webhook where you control the JSON payload) and capture the real request Shopify sends, including the valid `x-shopify-hmac-sha256` header and raw body.
3. Replay the exact same raw body and HMAC header to the app's webhook endpoint, but replace `x-shopify-shop-domain` with `victim.myshopify.com`.
4. `Utils::HmacValidator.validate` still succeeds because the signature only covers the raw body (unchanged), and `Registry.process` forwards `shop: "victim.myshopify.com"` to the app's handler: [4](#0-3) 
5. If the handler uses `data.shop` to select which tenant's session/data to act on, the attacker has caused the app to act on behalf of `victim.myshopify.com` using content the attacker fully controlled.

          received_signature = verifiable_query.hmac

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
