### Title
Missing duplicate-token rejection in Tron `IntentGatewayV2.placeOrder` reintroduces the fixed "duplicate escrow bucket" bug, enabling over-release/freezing of intent escrow funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The canonical EVM `IntentGatewayV2.sol` explicitly rejects orders whose `inputs` or `output.assets` arrays contain the same token more than once, because the escrow/partial-fill bookkeeping is keyed only by `(commitment, token)` and cannot represent two distinct legs sharing one token. The Tron fork of the same contract (`evm/tron/contracts/apps/IntentGatewayV2.sol`) is missing both of these checks in its `placeOrder`, so it accepts orders with duplicated input/output tokens — the exact "duplicated entry allowed, corrupting removable/accountable state" bug class described in the external report (there, a duplicated plugin address broke withdraw accounting; here, a duplicated token entry breaks escrow accounting for the same reason: the code assumes uniqueness but never enforces it).

### Finding Description
In the patched, canonical implementation, `placeOrder` performs two duplicate checks before escrowing:
- Duplicate **output** tokens are rejected via transient-storage tracking: [1](#0-0) 
- Duplicate **input** tokens are rejected while crediting escrow: [2](#0-1) 

The accompanying regression tests confirm these were fixes for real accounting bugs where duplicate legs shared one `_partialFills`/escrow bucket, causing "same-chain partial fills over-release repeated input escrow" and "same-chain partial fills prematurely finalize repeated output legs": [3](#0-2) [4](#0-3) 

The Tron fork's `placeOrder`, however, has no equivalent guard. It computes `reducedInputs`/`commitment` and escrows tokens without ever checking for repeated `order.inputs[i].token` or repeated `order.output.assets[i].token` values: [5](#0-4) [6](#0-5) 

Because escrow is credited with `_orders[commitment][token] += reducedInputs[i].amount` (an unconditional accumulation, not a set-once check), two input legs specifying the same token silently merge into a single bucket even though the order still records two independent legs with two independent amounts/semantics. The same absence of a check applies to `order.output.assets`. The `withdraw`/fill accounting later iterates per declared leg and mutates the single merged bucket per token: [7](#0-6) 

This is structurally identical to the reported Vault plugin issue: a collection that is supposed to hold unique entries (plugins in Vault; tokens per order in IntentGateway) has no uniqueness enforcement, so downstream code that assumes one bucket per entry (removePlugin's balance withdrawal; per-leg partial-fill accounting) is fed multiple logical legs sharing one physical bucket, and can either double-count or zero out incorrectly.

### Impact Explanation
An order placer (fully unprivileged, single `placeOrder` transaction) can construct an order with duplicated input or output tokens on the Tron deployment. Depending on which side is duplicated:
- Duplicate **input** tokens merge into one escrow bucket while the order still advertises two separate legs to solvers/relayers; a solver satisfying (or partially filling) one leg can drain/release the merged bucket meant to also cover the other leg, or the withdrawal/cancel path can under- or over-subtract against the single bucket, leading to permanent loss of a portion of user's escrowed funds or a solver receiving/reclaiming more than entitled.
- Duplicate **output** tokens targeting the same partial-fill bucket allow a fill against one leg to be seen as satisfying both legs (or vice versa), letting a solver finalize/collect the order having only delivered part of the promised output — theft from the counterpart or permanent freezing of the user's principal since the order can never be correctly completed or cancelled.

This directly maps to "concrete theft or permanent freezing of funds" in the intents escrow, reachable via a single unprivileged `placeOrder` call — no admin/governance/relayer collusion required.

### Likelihood Explanation
High for any Tron deployment of this contract: `placeOrder` is a fully public, unauthenticated entry point, and the missing checks are a straightforward diff omission relative to the already-known-and-fixed EVM version (the fix's own regression tests describe exactly this failure mode). Any user can trivially construct an `Order` with two `TokenInfo` entries sharing a token address to trigger the divergence from the intended one-bucket-per-token invariant.

### Recommendation
Port the duplicate-token guards from `evm/src/apps/IntentGatewayV2.sol` into `evm/tron/contracts/apps/IntentGatewayV2.sol`:
1. Before crediting escrow, reject if `_orders[commitment][token] != 0` when writing an input bucket (mirror lines 361-373 of the canonical contract) instead of unconditionally using `+=`.
2. Add the same transient-storage (or a `bool` mapping, since Tron's EVM compatibility for `TLOAD/TSTORE` may differ — verify Tron opcode support before reusing the transient-storage pattern, and fall back to a `mapping(bytes32 => bool)` cleared at the end of the call if `tload/tstore` isn't guaranteed) duplicate check for `order.output.assets` before the order is accepted.
3. Add regression tests mirroring `testRevert_PlaceOrder_DuplicateInputTokens` / `testRevert_PlaceOrder_DuplicateOutputTokens` to the Tron test-suite so future forks of this contract cannot silently drop the fix again.

### Proof of Concept
1. Deploy `evm/tron/contracts/apps/IntentGatewayV2.sol` (as done for Tron) and approve USDC to the gateway.
2. Call `placeOrder` with `order.inputs = [ {token: USDC, amount: 1200e6}, {token: USDC, amount: 1000e6} ]` and two output legs (e.g. DAI 500e18 and 1000e18), as in the analogous EVM regression test: [8](#0-7) 
   On the canonical EVM contract this call reverts with `InvalidInput`. On the Tron contract (lacking the check) the call succeeds, and `_orders[commitment][USDC]` is silently merged to `2200e6` while the order object still records two independent 1200e6/1000e6 legs.
3. A solver can then fill/cancel/withdraw against this single merged bucket in a way inconsistent with the two declared legs (e.g., satisfying one leg drains the whole merged escrow, or the withdrawal-subtraction logic in the Tron `withdraw` function is invoked twice against a bucket that was only credited once), producing either an over-release to the solver or a stuck/unrecoverable balance for the user — the same class of outcome documented by the canonical repo's own regression-test comments ("over-release repeated input escrow", "prematurely finalize repeated output legs").

    function placeOrder(Order memory order, bytes32 graffiti) public payable {
        // Validate that order has inputs
        if (order.inputs.length == 0) revert InvalidInput();

        address hostAddr = host();
        // fill out the order preludes
        order.user = bytes32(uint256(uint160(msg.sender)));
        order.source = IDispatcher(hostAddr).host();
        order.nonce = _nonce++;

        // Calculate reduced inputs (after protocol fees) for commitment and escrow
        uint256 inputsLen = order.inputs.length;
        // Use destination-specific protocol fee, fallback to source chain fee if zero
        bytes32 destinationHash = keccak256(order.destination);
        uint256 protocolFeeBps = _destinationProtocolFees[destinationHash];
        if (protocolFeeBps == 0) {
            protocolFeeBps = _params.protocolFeeBps;
        }
        TokenInfo[] memory reducedInputs;
        bytes32 commitment;

        if (protocolFeeBps > 0) {
            reducedInputs = new TokenInfo[](inputsLen);
            for (uint256 i; i < inputsLen;) {
                uint256 originalAmount = order.inputs[i].amount;
                uint256 protocolFee = (originalAmount * protocolFeeBps) / 10_000;
                uint256 reducedAmount = originalAmount - protocolFee;
                address token = address(uint160(uint256(order.inputs[i].token)));

                // Emit DustCollected for protocol fee if non-zero
                if (protocolFee > 0) emit DustCollected(token, protocolFee);

                reducedInputs[i] = TokenInfo({token: order.inputs[i].token, amount: reducedAmount});
                unchecked {
                    ++i;
                }
            }

            // Temporarily swap inputs to calculate commitment with reduced amounts
            TokenInfo[] memory originalInputs = order.inputs;
            order.inputs = reducedInputs;
            commitment = keccak256(abi.encode(order));
            order.inputs = originalInputs;
        } else {
            // No protocol fees, use order.inputs directly
            reducedInputs = order.inputs;
            commitment = keccak256(abi.encode(order));
        }

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }
