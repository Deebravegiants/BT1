The docs at `docs/usage/webhooks.md:125` state that `Registry.process` "will verify the request did indeed come from Shopify" — implying the gem itself vouches for the authenticity of the entire webhook, including the shop identity — yet the `shop` field is never covered by the HMAC signature.

### Title
Webhook `shop` field is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` extracts `topic`, `shop`, `webhook_id`, and `api_version` directly from unauthenticated HTTP headers [1](#0-0) , while the HMAC signature is computed only over the raw request body via `to_signable_string` [2](#0-1) . `Registry.process` validates only that HMAC-over-body [3](#0-2) , then constructs `WebhookMetadata` trusting the unauthenticated `shop` header and passes it to the host app's handler [4](#0-3) .

### Finding Description
The identity binding broken is: `hmac_signed_bytes == raw_body` but `shop_used_by_handler == header["shop-domain"]`, i.e. the shop identity acted upon by the app is never part of what the HMAC authenticates. `Utils::HmacValidator.validate` only checks `verifiable_query.to_signable_string` (the raw body) against the app's `Context.api_secret_key` [5](#0-4) . Since the same `client_secret` is shared across every shop that installs the app, any shop with a legitimate installation can capture a validly-signed webhook body+HMAC pair from its own tenant, then replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header value. `Request#shop` reads this header verbatim with no cross-check against the signature [6](#0-5) , and `Registry.process` forwards it into `WebhookMetadata.shop` unmodified [7](#0-6) . The gem's own documentation asserts that `Registry.process` "will verify the request did indeed come from Shopify" [8](#0-7) , which overstates what is actually validated — only body authenticity is confirmed, not shop attribution.

### Impact Explanation
A malicious merchant/attacker who has installed the app on their own shop can forge webhook deliveries that the host application will attribute to a victim shop of their choosing, because the multi-tenant app relies on `data.shop` from `WebhookMetadata` to select which tenant's session/records to act on. This is a cross-tenant confusion vulnerability: the attacker supplies both the body content (up to what the signature permits — same secret across tenants) and the arbitrary target shop, allowing forged data to be attributed to and processed against another merchant's tenant.

### Likelihood Explanation
Exploitation requires the attacker to control at least one legitimate installation of the target app (any merchant can install typical public apps) to obtain a validly HMAC-signed body/signature pair, then replay it with a modified `shop-domain` header to the app's public webhook endpoint — no secrets, tokens, or privileged access are required beyond that.

### Recommendation
Bind the shop identity to the authenticated data: either include the `shop-domain` (and ideally `topic`, `webhook_id`) in the HMAC-signed payload used by `to_signable_string`, or have `Registry.process`/the host app cross-verify the header-derived `shop` against a shop already known/authorized for that specific registered webhook (e.g., verify against Shopify's per-request webhook signing metadata or an independently stored shop-to-webhook mapping) before invoking the handler.

### Proof of Concept
1. App developer registers a webhook handler that trusts `data.shop` from `WebhookMetadata` to load/act on a specific tenant's records (the documented usage pattern in `docs/usage/webhooks.md`).
2. Attacker installs the app on `attacker-shop.myshopify.com` and receives a real webhook: body `B`, header `x-shopify-hmac-sha256: H` (valid HMAC of `B` under the app's shared `client_secret`), header `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker replays the exact same body `B` and HMAC `H` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` recomputes HMAC over `B` only and it matches `H`, so `Registry.process` proceeds [9](#0-8) .
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and processes attacker-controlled body content as if it originated from the victim's store.
