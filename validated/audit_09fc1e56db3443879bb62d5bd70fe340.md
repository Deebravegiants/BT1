### Title
Webhook shop/topic identity spoofing via HMAC that only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb], [File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` claims to "verify the request did indeed come from Shopify" before invoking the registered handler, but the HMAC check only authenticates the raw request body bytes. The `shop`, `topic`, `webhook_id`, and `api_version` fields — which are read straight from unauthenticated HTTP headers and then handed to the application's webhook handler as trusted identity data — are never part of the signed material.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id` and `api_version` accessors are all derived from HTTP headers that are not included in that signable string: [2](#0-1) 

`Registry.process` validates the request with `Utils::HmacValidator.validate(request)`, which internally calls `verifiable_query.to_signable_string` (i.e. the body only) and compares it against the received `hmac`: [3](#0-2) [4](#0-3) 

Once that body-only check passes, the header-derived, unauthenticated `shop`/`topic`/`webhook_id` values are packaged into `WebhookMetadata` and passed directly to the app's handler: [3](#0-2) 

The gem's own documentation tells integrators that `Registry.process` "will verify the request did indeed come from Shopify," creating the false impression that the whole request (including `shop`) is authenticated: [5](#0-4)  and it documents `data.shop`/`data.topic` as trustworthy fields to key application logic on: [6](#0-5) 

This breaks the identity binding: `shop header used to route/authorize webhook handling` ≠ `shop actually covered by the HMAC signature`. Any attacker who can obtain one legitimate `(raw_body, hmac)` pair — trivially available since anyone can install the app on their own store and receive a real, correctly signed webhook for it — can replay that exact body+signature to the app's webhook endpoint while substituting the `shopify-shop-domain` (and `shopify-topic`, `shopify-webhook-id`) headers with values naming a different, victim shop. `Utils::HmacValidator.validate` still returns `true` because only the body bytes are checked, and the handler receives `shop: "victim-shop.myshopify.com"` with attacker-controlled body content and topic.

### Impact Explanation
This is a cross-tenant identity-binding break reachable by any unprivileged internet user with no knowledge of the app's `client_secret`/`api_secret_key`: they only need one legitimate signed payload from their own tenant to forge webhook events attributed to an arbitrary other shop. Depending on how the host application uses `data.shop`/`data.topic` (e.g., updating merchant-specific order/inventory records, honoring `customers/redact`/`shop/redact` GDPR deletion requests, or gating logic per-shop), this allows an attacker to inject or trigger actions against another merchant's tenant data — a cross-tenant access impact.

### Likelihood Explanation
Likelihood is high for any app exposing the documented webhook endpoint: the attacker needs no privileged credentials, no access to `api_secret_key`, and no interception of others' traffic — only a single genuine webhook delivery to their own store (trivially obtainable by installing/using the app themselves) and the ability to send an HTTP request with custom headers to the app's own public webhook route.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signed/verified material, or otherwise cryptographically bind them to the verified body (e.g., verify `shop` against the session/shop that the app expects for that webhook subscription rather than trusting the header verbatim). At minimum, update `docs/usage/webhooks.md` to stop stating that `process` "verifies the request did indeed come from Shopify" for these header fields, and document that `data.shop`/`data.topic` are unauthenticated and must be independently checked (e.g., against a known list of shops for which the webhook was registered) by the host application before being trusted.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and receives one legitimate webhook delivery, e.g. for `orders/create`, with body `B` and header `shopify-hmac-sha256: H` (a valid HMAC-SHA256 of `B` using the app's secret — computed by Shopify, not the attacker).
2. Attacker resends the request to the same app webhook endpoint using the exact same raw body `B` and `shopify-hmac-sha256: H`, but sets `shopify-shop-domain: victim-shop.myshopify.com` (and optionally a different `shopify-topic`, e.g. `customers/redact`).
3. `ShopifyAPI::Webhooks::Request.new` accepts the headers (`lib/shopify_api/webhooks/request.rb:45-63`), and `Registry.process` calls `Utils::HmacValidator.validate(request)`, which computes the HMAC over `@raw_body` only and successfully matches `H` (`lib/shopify_api/webhooks/registry.rb:189-190`, `lib/shopify_api/utils/hmac_validator.rb:26-31`).
4. The app's registered handler is invoked with `WebhookMetadata.new(topic: "customers/redact", shop: "victim-shop.myshopify.com", body: parsed(B), ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), causing the host application to act on data/tenant `victim-shop.myshopify.com` despite the payload never actually originating from or being signed with respect to that shop.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
