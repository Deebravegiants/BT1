## Analysis

The reported bug pattern is a mismatch between the field that is *checked* (used to gate a privileged action) and the field that is *actually verified* by a cryptographic mechanism. Searching the in-scope library code (`lib/shopify_api/**`, excluding generated REST resources) for the strongest analog surfaces the webhook-processing path.

`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`, and its `to_signable_string` binds only the raw HTTP body to the HMAC: [1](#0-0) 

But the `shop` accessor — the value the gem hands to the app's webhook handler as the tenant identifier — is read straight from the unauthenticated `x-shopify-shop-domain` HTTP header, which is never part of the signed string: [2](#0-1) 

`Registry.process` validates only the HMAC of the body, then forwards `request.shop` (and `request.topic`, `request.webhook_id`, `request.api_version` — all header-derived, all unsigned) straight to the handler with no cross-check against the signed content: [3](#0-2) 

The `HmacValidator` only ever validates `to_signable_string` (i.e., body bytes) against the secret — it never touches `shop`: [4](#0-3) 

Since Shopify apps share **one** `client_secret` across every merchant that installs them, any merchant who installs the app receives their own genuinely-HMAC-signed webhook deliveries. Because the identity-binding equality `shop_used_by_handler == shop_covered_by_hmac` does not hold (the right-hand side doesn't exist — HMAC covers only the body), an installing merchant can capture one of their own valid `(raw_body, hmac)` pairs and replay it to the app's public webhook endpoint with the `x-shopify-shop-domain` header swapped to a victim shop. `Registry.process` will pass the validation (body+secret still match) and hand the handler a `WebhookMetadata` claiming to be from the victim shop — the only documented way this gem exposes shop identity to webhook handlers.

### Title
Webhook shop-domain spoofing via unsigned header — cross-tenant webhook impersonation - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` binds the HMAC signature to the raw body only, while `#shop` (the tenant identity forwarded to the app's handler via `Registry.process`) is read from the unauthenticated `x-shopify-shop-domain` header. Because Shopify's HMAC is computed with a single `client_secret` shared across all merchants installing the same app, any installing merchant can capture a validly-signed webhook body/HMAC pair from their own shop and replay it with a forged `x-shopify-shop-domain` header, causing the app to process the payload as if it came from a different (victim) shop.

### Finding Description
`Utils::HmacValidator.validate` verifies only `verifiable_query.to_signable_string` against the request's `hmac`. For webhooks, `to_signable_string` returns `@raw_body` exclusively: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all derived from HTTP headers that are outside the signed byte range: [5](#0-4) 

`Registry.process` gates on the HMAC check and then trusts these unsigned header-derived fields wholesale when building the `WebhookMetadata` delivered to the app's handler: [3](#0-2) 

This is exactly the reported bug class: the check that gates the sensitive action (HMAC validity) covers a different scope than the field that the action actually relies on (`shop` used for tenant attribution). Because Shopify apps use one `client_secret` for every installing merchant, a genuinely-signed body from Merchant A's own webhook delivery remains validly signed no matter what shop-domain header accompanies it when replayed to the app's webhook endpoint.

### Impact Explanation
This breaks the tenant boundary the gem's own documented webhook API is supposed to preserve: `WebhookMetadata#shop` is the only identity signal the gem gives host apps in the handler, and it is unauthenticated. A malicious merchant (an "unprivileged" user relative to other tenants of the same app) can cause an app to process attacker-controlled webhook content while it's attributed to another merchant's shop — i.e., cross-tenant access/data confusion, matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Any developer that installs the target app on their own store legitimately receives valid `(body, hmac)` pairs signed with the app's shared `client_secret`. Capturing and replaying such a pair with a modified `x-shopify-shop-domain` header requires no special access — just a normal HTTP client and one's own legitimate app installation, making this readily reachable without any credential theft.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the signed payload verification, e.g., require host apps (or the gem itself) to cross-check `request.shop` against a shop that is actually registered/installed for this app before dispatching to a handler, rather than trusting the header purely because the body HMAC passed. At minimum, document prominently that `WebhookMetadata#shop` is not cryptographically bound to the HMAC and must be independently validated against known installed shops before being used for tenant attribution.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`, triggers a webhook (e.g., `orders/create`) and captures the raw POST: body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(client_secret, B)`.
2. Attacker crafts a POST to the app's public webhook endpoint using the same body `B` and header `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC-SHA256(client_secret, B) == H` — this still passes because `B` and `H` are genuinely correlated. [6](#0-5) 
4. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and attacker-chosen `body`, and the host app (using this gem's documented API) processes it as though it were a legitimate webhook from the victim's store.

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
