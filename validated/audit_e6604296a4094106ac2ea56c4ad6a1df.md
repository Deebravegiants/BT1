### Title
Cross-tenant webhook injection via unauthenticated `shop`/`topic` headers — `resistantFei`-style identity mismatch — (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
The external report's bug class is: a value that is trusted for a security-relevant decision (collateral accounting) is computed/verified inconsistently from the value that is actually cryptographically bound. The analogous break in this gem is in the webhook pipeline: `ShopifyAPI::Utils::HmacValidator.validate` only authenticates the **raw body** of an incoming webhook request, while the `shop` (tenant identity) and `topic` used to dispatch and attribute the event are read straight from unauthenticated HTTP headers. The equality that should hold — `shop_verified_by_hmac == shop_used_for_tenant_attribution` — never holds, because the left side is undefined.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are parsed directly from HTTP headers with no cryptographic binding to the signed body: [2](#0-1) 

`Registry.process` validates only the HMAC over the body, then immediately trusts `request.shop`/`request.topic` to route to a handler and to build the metadata object passed to app logic: [3](#0-2) 

`HmacValidator.validate` itself is sound (uses `OpenSSL.secure_compare`) — the problem is not the HMAC computation, it's that the fields the app is expected to trust for tenant identity (`shop`) and dispatch (`topic`) sit entirely outside what the HMAC covers: [4](#0-3) 

Because the webhook endpoint is a public internet-facing route (by design, so Shopify's servers can reach it), and because the only secret material required to produce a valid `(body, hmac)` pair is the app's `api_secret_key`, **any legitimate installer of the app on their own shop** can capture one authentic `(body, hmac)` pair from a webhook Shopify sends to their own store, then replay that exact pair directly to the app's endpoint with a forged `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header. `HmacValidator.validate` will still pass (body unchanged), and `Registry.process` will dispatch the attacker-authored payload as though it belongs to any other victim shop.

### Impact Explanation
This is a cross-tenant identity-binding break: an unprivileged internet user (an app installer on their own store) can make the host application process, and attribute to an arbitrary other shop, event data of the attacker's own choosing (subject to being drawn from a real webhook body they legitimately received) without ever possessing the victim's credentials or the app's `client_secret`. Any host application logic that trusts `WebhookMetadata#shop` for per-tenant state changes (e.g., marking orders paid, updating fulfillment, billing, or app-specific per-shop state) can be manipulated cross-tenant. This matches the "Critical – cross-tenant access" impact category.

### Likelihood Explanation
No leaked/privileged credentials, TLS interception, or `api_secret_key` knowledge is required. The attacker only needs to be a normal user capable of installing (or already having installed) the target public app on a store they control and observing one webhook delivery — a routine, unprivileged action. The forged headers (`X-Shopify-Shop-Domain`, `X-Shopify-Topic`) are trivial to set when POSTing directly to the app's public endpoint, bypassing Shopify's servers entirely.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the HMAC-signed material, or require `Registry.process`/host applications to independently corroborate `request.shop` against the session/tenant that is expected to be receiving that specific webhook (e.g., cross-check against a known/installed-shops list) before trusting it for any tenant-scoped action. At minimum, this trust boundary should be explicitly documented in `docs/usage/webhooks.md` so host applications don't rely on `request.shop` as an authenticated value.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and triggers a webhook (e.g., `orders/create`), capturing the exact raw request body and the `X-Shopify-Hmac-Sha256` header Shopify sent.
2. Attacker POSTs directly to the app's public webhook endpoint (not through Shopify) reusing the identical body and `X-Shopify-Hmac-Sha256` value, but sets:
   - `X-Shopify-Shop-Domain: victim.myshopify.com`
   - `X-Shopify-Topic: orders/create` (unchanged, or another registered topic)
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because the body is unmodified: [5](#0-4) 
4. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", ...)` and processes attacker-controlled data as belonging to the victim's tenant.
