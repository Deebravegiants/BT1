### Title
Webhook shop attribution is not covered by the HMAC signature, allowing cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC over the raw request body only, while the `shop` (and `topic`/`webhook_id`) values used by `ShopifyAPI::Webhooks::Registry.process` to dispatch and attribute the event are taken from unauthenticated HTTP headers. This breaks the identity binding `hmac-verified-bytes == data acted upon`, since the signature never covers the value that identifies which tenant the event belongs to.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, and `webhook_id` are read straight from HTTP headers with no cryptographic binding to the body or to each other: [2](#0-1) 

`Utils::HmacValidator.validate` only checks that `hmac` matches `compute_signature(verifiable_query.to_signable_string, secret)`, i.e. it only authenticates the body bytes, not the headers: [3](#0-2) 

`Registry.process` calls `Utils::HmacValidator.validate(request)` and, on success, dispatches to the handler using `request.shop` (the unauthenticated header) as the tenant identifier: [4](#0-3) 

Because the shop-domain header is not part of the signed material, any bearer of one valid `(body, hmac)` pair — which any app-installing shop legitimately receives for its own webhook deliveries — can replay that exact body+hmac against the app's webhook endpoint while substituting an arbitrary `shop-domain` header. `HmacValidator.validate` will still return `true` (the body is unmodified and the signature matches), and `Registry.process` will hand the handler a `WebhookMetadata` claiming the event came from the victim shop specified in the attacker-controlled header, even though the body/content actually originated from the attacker's own store.

This satisfies the identity-binding-break pattern called out in the rules: "a field acted on (`shop`) but not covered by the HMAC (only `body` is covered)."

### Impact Explanation
This allows an unprivileged internet user who has installed the app on their own (attacker-controlled) shop to forge webhook events that the receiving application will process as if they originated from an arbitrary victim shop domain. Any host application that trusts `WebhookMetadata#shop` for tenant-scoped actions (e.g., looking up a stored access token/session for that shop, writing/deleting tenant data, or triggering `shop/redact`/`customers/redact` handling for a shop other than the one that actually sent the data) would perform actions attributed to, or scoped by, the wrong tenant. This is a cross-tenant data/action confusion, meeting the "cross-tenant access" bar in the Impact criteria, though the ultimate blast radius depends on how the host app's `WebhookHandler` implementations use `data.shop`.

### Likelihood Explanation
Medium-High. Exploitation only requires:
1. The attacker installs the target app on a shop they control (a normal, low-privilege action any internet user/merchant can perform for apps in the app store or via public install flow).
2. The attacker captures one legitimate webhook delivery (body + `x-shopify-hmac-sha256` header) sent to their own endpoint for their own shop.
3. The attacker POSTs that identical body and HMAC header back to the app's webhook endpoint, replacing only the `shop-domain` header with the victim's domain.

No knowledge of `api_secret_key` or any victim credentials is required — the HMAC was legitimately produced by Shopify for the attacker's own shop and is merely replayed with a different, unauthenticated header.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the value that is HMAC-verified, or otherwise cryptographically tie the header values to the signed body — e.g., by validating the signature against a canonical string that includes body plus the identifying headers, or by requiring the host application to cross-check `request.shop` against the recipient/session context it expected for that specific webhook subscription, rejecting mismatches. Document clearly that `HmacValidator.validate` for webhooks only authenticates payload bytes and that consuming applications must not treat header-derived fields such as `shop` as authenticated without additional binding.

### Proof of Concept
1. Install the app on shop `attacker-shop.myshopify.com`; trigger a webhook (e.g. `orders/create`) to the app's configured webhook endpoint.
2. Capture the resulting POST: raw body `B` and header `x-shopify-hmac-sha256: H` (valid because Shopify signed `B` with the app's real secret).
3. Send a new POST to the same endpoint with body `B` (unchanged), header `x-shopify-hmac-sha256: H` (unchanged), but `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `B` against `H`: [5](#0-4) 
5. The handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)`, where `request.shop` is `"victim-shop.myshopify.com"` — an unauthenticated, attacker-chosen value: [6](#0-5)

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
