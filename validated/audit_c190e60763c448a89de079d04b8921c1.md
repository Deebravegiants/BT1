## Analysis

The equality to test: **assets Emporium's `ops` can move in a call == assets accounted for in `balancesBefore`/`balancesAfter`**.

Tracing the path:

1. `formInputForCircom` routes to `formInputEmporiumMin` whenever `externalActionId == HINKAL_EMPORIUM_ACTION_ID && erc20TokenAddresses.length == 0`, producing a public-input vector of only `emporiumMessage`, `timeStamp`, `calldataHash` — no `rootHashHinkal`, no nullifiers, no `amountChanges` are constrained by the circuit. [1](#0-0) 

2. `dimensionsCheck` forces `erc20TokenAddresses.length == dimensions.tokenNumber` and `inputNullifiers.length == dimensions.tokenNumber`, so with `tokenNumber == 0` no nullifiers need to be spent at all — the attacker proves nothing about owning any UTXO. [2](#0-1) 

3. `rootHashExists` only checks that `circomData.rootHashHinkal` is *some* historical root (public information), not that the caller owns a leaf under it, so it is trivially satisfiable. [3](#0-2) 

4. In `EmporiumUpgradeable.runAction`, `balancesBefore`/`balancesAfter` are computed **only over `circomData.erc20TokenAddresses`** — an empty array in the min path — while the `ops` loop executes attacker-supplied calls (`op.endpoint.call{value: op.value}(op.callData)`) from Emporium's own identity, completely unconstrained by that (empty) accounting set. `verifyWallet` only checks an ECDSA signature when `stack.signerAddress != address(0)`; the attacker can either set it to `address(0)` to skip signature checks entirely, or set it to their own address and self-sign (trivial for an unprivileged attacker). [4](#0-3) [5](#0-4) 

So the two sides of the equality diverge: the `ops` list can call `approve()` on any arbitrary ERC20, granting the attacker unlimited allowance drawn against Emporium's own address, while the balance-diffing loop iterates zero elements and can never detect or revert this.

One caveat: the question also frames this as "routed through HinkalWrapper's fee settlement first." Tracing `HinkalWrapper`, it only forwards to `IHinkal(hinkal).prooflessDeposit(...)`; it never calls `Hinkal.transact()` and has no path into `EmporiumUpgradeable.runAction`. [6](#0-5) 
That part of the premise is not supported by the code — the Emporium min-path bug is reachable directly via `Hinkal.transact`, independent of `HinkalWrapper`.

### Title
Unaccounted arbitrary-call execution in Emporium's Min-proof path lets an attacker grant themselves unlimited token allowance from Emporium's identity - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
When `externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `erc20TokenAddresses.length == 0`, `formInputForCircom` selects `formInputEmporiumMin`, whose circuit only constrains `emporiumMessage`, `timeStamp`, and `calldataHash` — no nullifiers, no root ownership, no token/amount data. `EmporiumUpgradeable.runAction` still unconditionally executes every attacker-supplied `EmporiumOperation` via `op.endpoint.call{value: op.value}(op.callData)`, while its before/after balance-accounting loop iterates the (empty) `erc20TokenAddresses` array, so it enforces nothing over that arbitrary call.

### Finding Description
The broken equality is: *assets Emporium's `ops` loop can move in a tx == assets accounted for in `balancesBefore`/`balancesAfter`*. With `erc20TokenAddresses.length == 0`, the RHS is the empty set while the LHS is unbounded — `stack.ops` (decoded from attacker-controlled `externalActionMetadata`) can target any `op.endpoint` with any `op.callData`, e.g. `IERC20(anyToken).approve(attacker, type(uint256).max)`, executed with `msg.sender == address(EmporiumUpgradeable)`. `verifyWallet` requires no valid third-party signature since the attacker fully controls `stack.signerAddress` (set to `address(0)` to skip the check, or to their own EOA to self-sign trivially). None of `performHinkalChecks`, `dimensionsCheck`, `checkOnchainCreation`, `verifyProof`, or `rootHashExists` constrain the contents of `ops` beyond the calldata hash matching, and the calldata hash itself is attacker-chosen along with everything it hashes. The result: an unprivileged attacker with no deposited funds and no real UTXO can force Emporium to `approve()` (or otherwise call) arbitrary contracts on its own behalf, with zero balance verification.

### Impact Explanation
The attacker gains unlimited ERC20 allowance (or arbitrary call execution) from Emporium's own address over any token/asset Emporium holds — this matches the "executing calls or moving assets a wallet owner or prover never authorised" High-severity category. Repeatable per distinct `emporiumMessage` (each message can only be used once via `usedMessages`, but new messages are free to mint). Whether this escalates to Critical direct theft of user funds depends on Emporium persistently holding real balances (e.g., ETH sent to its payable `receive()`, or ERC20 dust left over from prior operations that weren't in a given transaction's `erc20TokenAddresses`); the structural bypass of all balance accounting is unconditionally present regardless.

### Likelihood Explanation
No privileged role, no deposit, and no genuine UTXO ownership is required — only a self-chosen `emporiumMessage`/`messageSeed`, a Min-circuit proof (its only real work is a Poseidon hash the attacker fully controls), and any historically valid `rootHashHinkal`. Cost is a single transaction; feasibility is high because every check gating this path (`dimensionsCheck`, `rootHashExists`, `verifyWallet` with `signerAddress == 0`) is satisfiable unilaterally by the attacker.

### Recommendation
Reject `EmporiumUpgradeable.runAction` calls (or the entire Min-proof Emporium path) whenever `stack.ops` targets tokens/endpoints not represented in `circomData.erc20TokenAddresses`, or require `erc20TokenAddresses.length > 0` (and thus real balance accounting) for any op that can move value; alternatively, restrict the Min path to actions that provably cannot invoke arbitrary `endpoint.call` (e.g., only `cancelEmporiumMessage`-style state changes), and always require `stack.signerAddress != address(0)` with a verified signature before executing any `op`.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `EmporiumUpgradeable` (as registered external action), a mock ERC20, and mint/transfer some balance of that ERC20 directly to the Emporium proxy address (simulating dust/residual balance).
2. As an unprivileged attacker EOA with zero deposits, build `CircomData` with `externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `erc20TokenAddresses = []`, `amountChanges = []`, `inputNullifiers = []`, `outCommitments = []`, `dimensions.tokenNumber = 0`, an `EmporiumStack{ signerAddress: address(0), ops: [EmporiumOperation(endpoint: mockERC20, invokeWallet: false, value: 0, callData: abi.encodeCall(IERC20.approve, (attacker, type(uint256).max)))] }`, and a locally generated valid Min-circuit proof over `emporiumMessage/timeStamp/calldataHash`.
3. Call `Hinkal.transact(a,b,c,dimensions,circomData)` from the attacker.
4. Assert `IERC20(mockERC20).allowance(address(emporium), attacker) == type(uint256).max` afterward, then call `transferFrom(emporium, attacker, mockERC20.balanceOf(emporium))` and assert attacker's balance increased by Emporium's full prior balance — with `balancesBefore == balancesAfter == []` throughout `runAction`, proving the accounting loop never saw or blocked the drain.

    function runAction(
        CircomData calldata circomData,
        int256[] calldata deltaAmountChanges
    ) external override onlyAllowedRecipient returns (UTXO[] memory) {
        EmporiumStack memory stack = abi.decode(
            circomData.externalActionData.externalActionMetadata,
            (EmporiumStack)
        );

        uint256[] memory balancesBefore = getBalancesForArray(
            circomData.erc20TokenAddresses
        );

        verifyWallet(stack, circomData);

        for (uint256 i = 0; i < stack.ops.length; i++) {
            EmporiumOperation memory op = stack.ops[i];

            bool success;
            bytes memory err;

            // CASE 1: Stateful Interaction
            if (op.invokeWallet && stack.signerAddress != address(0)) {
                (success, err) = IHinkalWallet(stack.signerAddress)
                    .callHinkalWallet(op.endpoint, op.callData, op.value);
            }
            // CASE 2: Stateless Interaction
            else {
                bytes4 selector = bytes4(op.callData);
                if (
                    selector == IHinkalWallet.callHinkalWallet.selector ||
                    selector == IHinkalWallet.doSendToRelay.selector
                ) {
                    revert UnauthorizedWalletCall();
                }

                (success, err) = op.endpoint.call{value: op.value}(op.callData);
            }

            if (!success) {
                revert CallFailed(err);
            }
        }

        payRelayFees(circomData, stack.signerAddress, deltaAmountChanges);

        uint256[] memory balancesAfter = getBalancesForArray(
            circomData.erc20TokenAddresses
        );

        UTXO[] memory utxoSet = new UTXO[](
            circomData.erc20TokenAddresses.length
        );

        uint256 utxoSetLength;

        for (uint256 i = 0; i < circomData.erc20TokenAddresses.length; i++) {
            int256 balanceChange = int256(balancesAfter[i]) -
                int256(balancesBefore[i]);

            if (deltaAmountChanges[i] < 0) {
                balanceChange -= deltaAmountChanges[i];
                // this equation reads: total change of emporium balance = what was moved to emporium (-deltaAmountChange) + how emporium balance changed through tx (balanceChange)
            }

            // the only case when balanceChange can be < 0, when there were some funds on emporium before the call
            if (balanceChange < 0) {
                revert BalanceChangeShouldBePositive();
            }

            UTXO memory utxoOut = handleOut(balanceChange, circomData, i);

            if (utxoOut.amount > 0) {
                utxoSet[utxoSetLength++] = utxoOut;
            }
        }
