### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant shop spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, but the `shop` identity that the host application's handler acts upon is read from the `shopify-shop-domain` HTTP header, which is never included in the signed material. This breaks the equality that should hold: `shop authenticated by HMAC == shop the handler is told the event belongs to`. An attacker who controls any shop that has installed the app (an unprivileged relationship — just an installer, not the app's secret holder) can capture one of their own genuine, validly-signed webhook deliveries and replay it to the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop, causing the host application to process/store data under the wrong tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`ShopifyAPI::Utils::HmacValidator.validate` computes/compares the HMAC over exactly that signable string (`compute_signature(verifiable_query.to_signable_string, secret)`): [2](#0-1) 

`Registry.process` gates the whole request on that HMAC check, and then unconditionally trusts `request.shop` (parsed straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header) to build the `WebhookMetadata` handed to the app's handler: [3](#0-2) 

`Request#shop` simply reads the header with no cross-check against anything in the signed body: [4](#0-3) 

The binding that should hold is:
`shop value cryptographically bound by HMAC (signed material) == shop value the handler is told owns this event (request.shop)`

Before the attack: for a genuine delivery, both sides naturally match because Shopify itself set the header to the shop that triggered the event and signed the body with the app's shared `client_secret`.

After the attacker's request sequence: the attacker (an installer of the app on their own store `attacker-shop.myshopify.com`) receives a real webhook delivery from Shopify — valid raw body, valid HMAC (computed by Shopify using the app's single, shop-agnostic `client_secret`), and header `shopify-shop-domain: attacker-shop.myshopify.com`. The attacker resends this exact `raw_body` (and thus a still-valid `hmac-sha256` header) to the app's webhook endpoint, but substitutes `shopify-shop-domain: victim-shop.myshopify.com`. `HmacValidator.validate` still returns `true` because the check only covers `raw_body`, which the attacker left untouched. `Registry.process` therefore accepts the request and calls the handler with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, even though the event content actually originated from the attacker's own shop.

Because Shopify apps share one `client_secret` across all installing shops, any single installer can forge this shop attribution for arbitrary victim shops of the same app without ever needing the app's secret, an access token, or any privileged credential — satisfying the "unprivileged internet user" constraint.

### Impact Explanation
This is a cross-tenant identity-binding bypass in a multi-tenant Shopify app: the webhook processing pipeline (`Registry.process` → `WebhookMetadata`) that host applications rely on for shop attribution can be tricked into believing an event belongs to a shop it did not originate from. Per the documented usage pattern (`docs/usage/webhooks.md`, `data.shop` is the field apps use to route/persist per-tenant data), a host app following the gem's documented handler pattern will store or act on data keyed to the wrong shop — e.g., writing attacker-supplied order/customer payloads into another merchant's tenant record, or triggering shop-specific business logic (uninstall/redact handling, billing, etc.) against a shop the attacker doesn't control. This matches "cross-tenant access" (Critical) under the given impact taxonomy, since the trust boundary between tenants of the same app is broken using only the capabilities of an ordinary app installer.

### Likelihood Explanation
Likelihood is high given the low bar to exploit: any user can install the target app on their own development/test store, capture one genuine webhook POST (raw body + `hmac-sha256` + headers) via a simple HTTP proxy, and replay it to the same public webhook endpoint with only the `shop-domain` header changed. No secrets, tokens, or elevated privileges are required — only knowledge of the app's public webhook URL, which is normally discoverable/registered by the app itself.

### Recommendation
Bind the shop (and other routing metadata the handler trusts, e.g. `topic`, `api_version`, `webhook_id`) to the authenticated payload instead of trusting unauthenticated headers in isolation:
- Cross-validate `request.shop` against the shop embedded in the webhook body payload (Shopify webhook JSON bodies typically contain shop-identifying resource data, or the app can maintain a shop→webhook-subscription mapping and confirm `request.shop` matches a known, previously registered shop for that specific `webhook_id`/topic before dispatching).
- At minimum, document and/or enforce that `Registry.process` verify the `shop-domain` header consistency against the app's own list of shops that have live sessions/webhook registrations, rejecting shops with no active installation state.
- Consider requiring/validating the `webhook_id` uniqueness per shop as an idempotency+attribution check (already recommended for duplicate suppression) to also catch cross-shop replay.

### Proof of Concept
```ruby
# Attacker owns "attacker-shop.myshopify.com" and has installed the target app,
# so Shopify legitimately sends them a webhook for, e.g., "orders/create":
raw_body = '{"id":1,"note":"hello"}'
secret   = ShopifyAPI::Context.api_secret_key  # shared app secret; attacker does NOT need to know this value directly —
                                                # Shopify computes and sends the resulting HMAC for the attacker's own shop.

hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), secret, raw_body)

genuine_headers = {
  "x-shopify-topic"       => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac),
  "x-shopify-shop-domain" => "attacker-shop.myshopify.com",
}

# Attacker captures this genuine delivery, then replays raw_body + hmac unchanged,
# but swaps the shop-domain header to a victim shop they do not own/control:
forged_headers = genuine_headers.merge(
  "x-shopify-shop-domain" => "victim-shop.myshopify.com",
)

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

# HMAC check passes because it only validates raw_body, which was untouched:
ShopifyAPI::Webhooks::Registry.process(request)
# => host app's handler receives WebhookMetadata(shop: "victim-shop.myshopify.com", ...)
#    even though the event never originated from victim-shop.
```
