### Title
Webhook tenant/topic attribution (`shop-domain`, `topic`, `webhook-id` headers) is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body [4](#0-3) . The `shop`, `topic`, `webhook_id`, and `api_version` values that are handed to the app's handler and used to attribute the payload to a specific merchant/tenant are read from HTTP headers [2](#0-1)  that are never included in the signed content (`to_signable_string` returns only `@raw_body`) [1](#0-0) .

### Finding Description
The identity binding that should hold is: `shop header used to attribute the webhook == shop covered by the HMAC signature`. That binding is broken here.

`HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string`, which for `Webhooks::Request` is just the raw body bytes [5](#0-4) [1](#0-0) . Meanwhile `Registry.process` builds the `WebhookMetadata` passed to the app's handler using `request.topic`, `request.shop`, and `request.webhook_id`, all of which are pulled from headers that carry no cryptographic binding to the signed body [3](#0-2) .

Since every shop installing a given app shares the same `client_secret` (`Context.api_secret_key`) for webhook HMAC signing, a merchant who installs the app on their own store legitimately receives a validly-signed `(body, hmac)` pair for their own shop. Because the header values are not part of the signed content, that same attacker can resend the identical body+hmac to the app's public webhook endpoint while substituting the `shop-domain` header with a victim shop's domain and/or an arbitrary `topic`/`webhook-id`. `HmacValidator.validate` will still return `true` because it only checks the body against the shared secret; the app's webhook handler will then process data under the identity of the victim shop.

### Impact Explanation
This breaks the tenant boundary the HMAC is supposed to enforce (`Critical - cross-tenant access`). Any app that uses `WebhookMetadata#shop` to select which merchant's records to create/update/delete (a standard pattern, e.g. `orders/create`, `app/uninstalled`, `customers/data_request`) can be made to apply attacker-supplied (and attacker-controlled, since the attacker controls the content of their own store's webhook body) data against a different, victim tenant's records, since the receiving app has no way to distinguish this from a genuine webhook for that victim shop.

### Likelihood Explanation
Exploitation requires only: (1) the attacker installs the target app on any shop they control (a normal, low-privilege action, not requiring any of this gem's secrets or a compromised account), (2) capturing a real webhook body+HMAC sent to their own configured endpoint, and (3) replaying it to the target app's public webhook endpoint with modified headers. No access to `api_secret_key`, tokens, or the app's infrastructure is needed — this is an unprivileged-internet-user attack once the attacker onboards as any merchant.

### Recommendation
Include the tenant/topic-identifying fields (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signable content that `HmacValidator` verifies, e.g. by having `Webhooks::Request#to_signable_string` combine the raw body with a canonical representation of these headers, so that any attacker-controlled tampering with headers invalidates the signature.

### Proof of Concept
1. Attacker creates a normal developer store or trial merchant account, installs the target app, and registers a webhook (e.g. `orders/create`).
2. Attacker triggers a real event (e.g. creates an order) so Shopify sends a legitimately-signed webhook to the attacker's own listener, containing `x-shopify-hmac-sha256: <valid-hmac>` and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker resends the exact same raw body and `hmac-sha256` header to the target app's public webhook endpoint, but replaces `x-shopify-shop-domain` with `victim-shop.myshopify.com` (and/or changes `x-shopify-topic`).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only validates the (unchanged) body against `Context.api_secret_key` [4](#0-3) .
5. The app's registered handler receives `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: attacker_controlled_body, ...)` [6](#0-5)  and processes attacker-controlled data under the victim's tenant identity.
