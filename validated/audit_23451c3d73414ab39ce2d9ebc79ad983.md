### Title
Webhook `shop`, `topic`, and `webhook_id` headers are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so `ShopifyAPI::Utils::HmacValidator.validate` only proves that the *body bytes* were signed by Shopify with the app's `client_secret`. The `shop`, `topic`, and `webhook_id` values, which are read straight from HTTP headers, are never part of the signed payload, yet `ShopifyAPI::Webhooks::Registry.process` trusts them unconditionally to route the webhook and attribute it to a tenant.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 

while `shop`, `topic`, and `webhook_id` are pulled from headers that are completely separate from the signed body: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately uses the unauthenticated `request.shop` (and `request.topic`, `request.webhook_id`) to build the metadata handed to the application's webhook handler: [3](#0-2) 

`HmacValidator.validate` computes the HMAC purely over `to_signable_string`, i.e. the body, and compares it with `OpenSSL.secure_compare`: [4](#0-3) 

The binding the gem is supposed to enforce is:
`bytes verified (raw_body signed by HMAC)` == `bytes acted on (shop-domain, topic, webhook-id headers used for tenant routing)`

That equality does not hold: only the body is verified, but the shop/topic/webhook-id headers are acted on as if they were verified too.

### Impact Explanation
Because Shopify signs the same `hmac-sha256` value for a given body regardless of which shop or topic header accompanies it (the signature is computed over the body alone on Shopify's side too, following the documented webhook verification scheme), a webhook payload legitimately received by an attacker for a shop they control (e.g., their own development store) carries a hmac that remains valid if the attacker retransmits the identical body to the app's webhook endpoint while swapping the `X-Shopify-Shop-Domain`, `X-Shopify-Topic`, or `X-Shopify-Webhook-Id` header. `Utils::HmacValidator.validate(request)` will still pass because it only ever re-derives the signature from `@raw_body`. The application then processes this forged request as if it genuinely originated from the spoofed shop/topic, letting an attacker (an unprivileged party who is merely a merchant on their own store, holding no access to the app's `client_secret`) inject attacker-controlled body content that the host app attributes to a different tenant (`WebhookMetadata#shop`) — a cross-tenant data-integrity/confusion issue.

### Likelihood Explanation
Any user who can install the app on a shop they control (a normal, unprivileged flow) can capture a legitimate `(body, hmac)` pair from their own webhook deliveries and does not need the `client_secret` or any privileged credential to replay it with altered headers, since the gem never binds those headers to the signature. The only requirement is that the app process the same webhook topic to attacker-supplied bodies with different shop headers.

### Recommendation
Include the header values that the code depends on (`shop`, `topic`, `webhook_id`, `api_version`) in the value that is HMAC-verified, or at minimum verify that the shop present in the headers matches an out-of-band expectation (e.g. the shop the webhook was registered for) before dispatching to a handler. Alternatively, follow Shopify's guidance of also validating that the `shop-domain` corresponds to a shop with an active session/installation before trusting `WebhookMetadata#shop` for tenant-scoped operations.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers any webhook topic the app subscribes to, capturing the raw request body `B` and its `X-Shopify-Hmac-Sha256` header value `H` (valid because it's computed over `B` with the app's real secret by Shopify).
2. Attacker sends a new POST to the app's webhook endpoint with body `B` unchanged, header `X-Shopify-Hmac-Sha256: H` unchanged, but `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: ...)` is constructed; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `B` against `H`: [5](#0-4) 
4. The handler receives `WebhookMetadata.new(... shop: "victim-shop.myshopify.com", body: parsed(B) ...)` and processes attacker-controlled data as if it belonged to `victim-shop.myshopify.com`.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
