### Title
Webhook `shop-domain` header is trusted for tenant identification without being covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature only over the raw request body, while the `shop-domain` header used to identify which merchant/tenant a webhook belongs to is read directly from an unauthenticated header and passed on to handler code untouched.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `Utils::HmacValidator.validate` computes `OpenSSL::HMAC.hexdigest` over exactly that signable string and compares it against the `hmac` value taken from the `shopify-hmac-sha256`/`x-shopify-hmac-sha256` header [2](#0-1) . The `shop` accessor, however, is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic binding to the signed body [3](#0-2) .

`Registry.process` validates only the HMAC of the body, then passes `request.shop` straight into `WebhookMetadata` for the handler to act on [4](#0-3) . This means the equality that the app actually relies on — "the shop this data affects" == "the shop that the client_secret-holder (Shopify) says it is for" — is never checked. Only "the body bytes I verify" == "the body bytes with a valid signature" is checked; the shop header is out-of-band and unauthenticated.

### Impact Explanation
An attacker who is a merchant of their own store (thus an "unprivileged" API/webhook counterpart with no special access to any other tenant, the app's `client_secret`, or access tokens) legitimately receives valid `(raw_body, hmac)` pairs from Shopify for webhooks addressed to their own shop. Because the `shop-domain` header is not part of the signed content, the attacker can replay that exact `(raw_body, hmac)` pair to the app's webhook endpoint while substituting `shop-domain` with a victim shop's domain. The HMAC check still succeeds (it only verifies body integrity/authenticity, not the shop binding), and the app's webhook handler will process the payload believing it originated from — and applies to — the victim shop. Depending on what the handler does with `WebhookMetadata#shop` (e.g., look up session, update per-shop data, trigger app/shop uninstall logic, feed shop into downstream trust decisions), this is a cross-tenant data confusion/cross-tenant action vulnerability requiring no possession of the victim's or app's credentials.

### Likelihood Explanation
Reaching this requires only that: (1) the attacker operates their own shop that has the app installed (readily available to anyone since installing a public/dev app is unprivileged), (2) they receive at least one legitimate webhook for a topic the app cares about, and (3) they can send an HTTP POST to the app's public webhook endpoint with modified headers — trivial with any HTTP client. No secret material or elevated privilege is needed, only the ability to capture their own valid webhook payloads and hmac and replay them with a different `shop-domain` header. The bar to exploit is low, though usefulness is bounded by what payload/topic content the attacker can control while still being routed to a victim-relevant handler action.

### Recommendation
Do not treat `shop-domain` (or `topic`, `webhook-id`, `api-version`) as trusted merely because the HMAC on the body validates. Either (a) include the shop domain (and topic) inside the HMAC-covered signable string so any tampering invalidates the signature, or (b) cross-check the header-provided shop domain against the shop associated with the specific `webhook_id`/subscription (fetched via a trusted, session-authenticated lookup) before acting on the payload, so tenant identity is bound to something authenticated rather than an arbitrary header value.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook event (e.g., `orders/create`) that they control.
2. Attacker's server receives headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid-hmac>` and raw body `B`.
3. Attacker resends the exact same raw body `B` and `x-shopify-hmac-sha256: <valid-hmac>` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate(request)` returns `true` because it only recomputes HMAC over `@raw_body` [1](#0-0) [5](#0-4) .
5. `Registry.process` invokes the registered handler with `WebhookMetadata.new(... shop: request.shop ...)` set to `victim-shop.myshopify.com` [4](#0-3) , causing the app to act on/associate attacker-controlled data with the victim tenant.
