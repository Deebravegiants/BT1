### Title
Webhook HMAC only covers request body, not the `shop-domain`/`topic` headers, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw JSON body [2](#0-1) . The HMAC's signable content is defined as just `@raw_body` [3](#0-2) , while `shop`, `topic`, `webhook_id` and `api_version` are all read directly from unauthenticated HTTP headers [4](#0-3) . The `shop` value is then passed straight into `WebhookMetadata` and handed to the app's handler as the authoritative tenant identifier, per the gem's own documented usage [5](#0-4) [6](#0-5) .

### Finding Description
The identity binding that should hold is: `shop header used by the handler == shop that the HMAC-authenticated body actually originated from`. Because the HMAC signature is computed over `to_signable_string`, which returns only `@raw_body` [3](#0-2) , the `shopify-shop-domain` (and `shopify-topic`, `shopify-webhook-id`, `shopify-api-version`) headers are never part of what is verified in `HmacValidator.validate` [7](#0-6) .

Any actor who possesses one genuine, unmodified `(body, hmac)` pair for any shop that uses the same app (which is easy to obtain — e.g., by installing the app themselves, or simply replaying a captured webhook delivery) can resend that exact body/HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with an arbitrary victim shop domain. `Registry.process` will still call `Utils::HmacValidator.validate` successfully (it only checks the body against the shared `api_secret_key`), and will then dispatch to the handler with `shop: request.shop` set to the attacker-chosen value [8](#0-7) . Because the documentation instructs handlers to key downstream processing (e.g., job enqueueing, per-tenant data writes) off `data.shop` [1](#0-0) , this results in webhook data being attributed to, and potentially acted upon for, the wrong tenant — a cross-tenant data-confusion condition. The `topic` and `webhook_id` headers used for deduplication and routing are equally unauthenticated.

### Impact Explanation
This breaks the tenant isolation boundary the gem is meant to enforce for webhook processing: an app relying on `data.shop` as returned by this gem (exactly as its own docs recommend) can be made to process, store, or act on webhook data under an incorrect shop identity, i.e., cross-tenant data confusion, satisfying the "Critical - cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires only network access to the public webhook endpoint and one legitimately-received `(body, hmac)` pair — obtainable by installing the app on any shop (a normal, unprivileged action available to any Shopify merchant) and capturing the resulting webhook call, or otherwise intercepting a delivery. No access to `api_secret_key`, tokens, or credentials of the victim shop is needed, since the same `api_secret_key` is used by Shopify to sign webhooks for every shop of a given app, and the signature never binds to a specific shop.

### Recommendation
Include the `shop-domain` (and ideally `topic`/`webhook_id`) header values in the signable content that is HMAC-verified, or otherwise cryptographically bind the header-derived shop identity to the verified body before it is handed to `WebhookMetadata`/the handler, so a valid signature for one shop's body cannot be replayed under another shop's identity.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and triggers a webhook (e.g., `orders/create`), capturing the raw body `B` and the valid `x-shopify-hmac-sha256` header `H` that Shopify sent for it.
2. Attacker POSTs to the app's registered webhook endpoint with:
   - `x-shopify-hmac-sha256: H`
   - `x-shopify-topic: orders/create`
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - body: `B`
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `B` only and it matches `H`, so validation succeeds [9](#0-8) .
4. The handler is invoked with `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: parsed(B), ...)` [5](#0-4) , causing the app to process the attacker's own order data as if it belonged to `victim-shop.myshopify.com`.
