## Title
Webhook HMAC does not bind the `shop-domain` header, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body and excludes the `shopify-shop-domain` (and `topic`/`webhook-id`) headers from the HMAC signature computation. `Registry.process` trusts `request.shop` to build the `WebhookMetadata` handed to the app's handler, without that field ever being covered by the signature check that gates processing. This breaks the identity binding `hmac_verified(body) == shop_trusted(body)`.

### Finding Description
`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` and compares it to the `hmac` field [1](#0-0) . For webhooks, `Request#to_signable_string` returns `@raw_body` exclusively [2](#0-1) , while `Request#shop`, `#topic`, and `#webhook_id` are pulled straight from unauthenticated HTTP headers [3](#0-2) .

`Registry.process` gates handler dispatch on `Utils::HmacValidator.validate(request)` (i.e., only the body's integrity/authenticity), then unconditionally forwards `request.shop`, `request.topic`, and `request.webhook_id` — none of which are covered by that same HMAC — into `WebhookMetadata` passed to the app-level handler [4](#0-3) .

Because the shared `api_secret_key` is the same across all shops installed on a given app, any party who can obtain one valid `(raw_body, hmac)` pair (e.g., by installing the app on their own store and triggering a webhook event on data they control) can replay that exact body+hmac to the app's public webhook endpoint while substituting the `shopify-shop-domain` header for a victim shop's domain. The HMAC check still passes (it only verifies the body), but `WebhookMetadata.shop` now falsely claims to be the victim tenant.

### Impact Explanation
This is a cross-tenant identity-binding break: the field the host application relies on to attribute a webhook event to a specific merchant (`shop`) is unauthenticated relative to the signature that gates trust. An attacker-controlled body (generated from resources in their own shop) can be replayed and attributed to an arbitrary victim shop domain, corrupting per-tenant records, triggering merchant-scoped side effects, or polluting audit/data pipelines keyed by shop — a cross-tenant access impact.

### Likelihood Explanation
Exploitation requires only: (1) being able to install the app on an attacker-controlled/trial shop to legitimately obtain one valid `(body, hmac)` pair (no special access to `api_secret_key`, access tokens, or the victim's credentials needed), and (2) POSTing that body with a substituted `shop-domain` header to the app's public webhook endpoint. Both steps are reachable by an unprivileged internet user/merchant who can self-install the app once, satisfying the "unprivileged" and "unauthenticated boundary crossed" requirements.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signable string (or otherwise cryptographically bind them, mirroring how OAuth's `AuthQuery` includes `shop`/`state`/`code` in its signable string) so the HMAC verification covers the identity fields the handler consumes, not just the payload bytes.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker.myshopify.com` and triggers a webhook (e.g., `orders/create`) with attacker-chosen order content. Shopify sends a request with headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid hmac of raw_body>`, and the raw JSON body.
2. Attacker captures `(raw_body, hmac)`.
3. Attacker replays the identical `raw_body` and `hmac` to the app's webhook endpoint but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` returns `true` because it only checks `raw_body` against `hmac` [5](#0-4) ; `Registry.process` then dispatches `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` to the handler with `shop == "victim.myshopify.com"` [6](#0-5) , despite the payload actually originating from the attacker's shop.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
