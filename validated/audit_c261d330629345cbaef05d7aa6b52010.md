### Title
Stale `_latestStateMachineHeight` entries let de-whitelisted state machines keep accepting new state commitments - ([File: evm/src/core/EvmHost.sol])

### Summary
`updateHostParamsInternal` in `EvmHost.sol` replaces `_hostParams.stateMachines` with the new whitelist and *initializes* `_latestStateMachineHeight` for any newly-added state machine, but it never clears `_latestStateMachineHeight` for state machines that governance removes from the list. [1](#0-0)  This mirrors the reported `addNewAsset` bug class: an authoritative "membership" array is replaced/rewritten, but the corresponding boolean/height mapping that other functions rely on to decide validity is left stale and still reads as "supported."

### Finding Description
`updateHostParamsInternal` is the sole update path for the host's state-machine whitelist, invoked either via cross-chain governance (`hostManager`) or, on testnets, directly by admin. [2](#0-1)  When new params are applied:

```solidity
_hostParams.stateMachines = params.stateMachines;
...
for (uint256 i = 0; i < stateMachinesLen; ++i) {
    if (_latestStateMachineHeight[params.stateMachines[i]] == 0) {
        _latestStateMachineHeight[params.stateMachines[i]] = 1;
    }
}
``` [3](#0-2) 

This loop only ever *adds* initialization entries for state machines present in the **new** list — exactly like the reported bug's `s.IndexToken[_address[i]] = true` loop that only sets `true` for the new assets. There is no complementary step that iterates the **previous** `_hostParams.stateMachines` and deletes/zeroes `_latestStateMachineHeight` for IDs that are no longer present in the new whitelist. Once a state machine ID has been initialized, its `_latestStateMachineHeight` entry stays non-zero forever, even after that ID is removed from `_hostParams.stateMachines`.

The only place this cleanup exists at all is in `TestnetHost.updateHostParams`, and even there it is admin-only and testnet-specific — it deletes `_latestStateMachineHeight` for state machines in the *new* `params.stateMachines` list (a reset-on-reinit convenience), not for state machines being *removed* from the whitelist: [4](#0-3) 

`storeStateMachineCommitment`, which is called by the permissionless message-handling path (`restrict(_hostParams.handler)`, i.e. gated only to the `HandlerV2` contract that any relayer can invoke by submitting a valid consensus proof), stores new `StateCommitment`s keyed by `StateMachineHeight` without re-checking whether the target state machine ID is still present in the current `_hostParams.stateMachines` whitelist array. [5](#0-4)  Because `_latestStateMachineHeight` for a de-whitelisted ID is never zeroed out, code paths that gate on "has this state machine ever been initialized" (`_latestStateMachineHeight[id] != 0`) continue to treat it as an active, trusted state machine.

### Impact Explanation
Governance uses `updateHostParams` to shrink `stateMachines` specifically to revoke trust in a state machine — e.g., because its consensus client is deprecated, compromised, or its chain is being deauthorized. Because the height/whitelist bookkeeping is not cleared, a relayer can continue to submit new state commitments and associated request/response proofs for the supposedly de-whitelisted chain, since the height-tracking storage still reports it as previously-initialized/valid. This defeats the intended effect of a governance whitelist removal: a route that should be permanently shut down remains able to deliver messages, undermining the "unsound state commitment / route unable to be disabled" guarantee that the whitelist is meant to enforce.

### Likelihood Explanation
This requires no attacker privilege beyond the normal permissionless relayer role: any relayer can submit a consensus/state-commitment message through `HandlerV2` for the stale, previously-whitelisted-but-now-removed state machine ID, and `EvmHost` will still track/accept it because of the residual non-zero `_latestStateMachineHeight`. The precondition (governance having removed a state machine at some point) is a normal, expected operational action, making the stale-state exposure highly likely to occur in practice whenever the whitelist shrinks.

### Recommendation
In `updateHostParamsInternal`, before overwriting `_hostParams.stateMachines`, diff the old and new state-machine lists and explicitly `delete _latestStateMachineHeight[oldId]` (and any other per-state-machine trust bookkeeping, e.g., consensus state metadata) for every ID present in the old list but absent from the new one — analogous to the report's recommendation to set `s.indexToken[address] = false` for removed assets. Additionally, gate `storeStateMachineCommitment`/consensus proof acceptance on membership in the current `_hostParams.stateMachines` whitelist rather than solely on `_latestStateMachineHeight != 0`.

### Proof of Concept
1. Cross-chain governance calls `updateHostParams` with `stateMachines = [A, B]`; `_latestStateMachineHeight[A]` and `[B]` become `1`.
2. Later, governance calls `updateHostParams` with `stateMachines = [B]` only, intending to de-whitelist `A`. `_hostParams.stateMachines` becomes `[B]`, but `_latestStateMachineHeight[A]` remains `1` (never cleared). [3](#0-2) 
3. A relayer submits a consensus/state-commitment message for state machine `A` via `HandlerV2`, which calls `storeStateMachineCommitment` (restricted only to the handler, not to whitelist membership). [5](#0-4) 
4. The commitment for `A` is stored and `_latestStateMachineHeight[A]` is updated as if `A` were still an actively-trusted state machine, even though governance removed it — proofs/requests from `A` continue to be deliverable.

        }

        if (caller == _hostParams.admin) {
            uint256 whitelistLength = params.stateMachines.length;
            for (uint256 i = 0; i < whitelistLength; ++i) {
                delete _latestStateMachineHeight[params.stateMachines[i]];
