### Title
Phantom bid price is weighted by a solver's spot on-chain balance, letting temporary self-funding manipulate the published pool rate - (File: sdk/packages/sdk/src/protocols/intents/phantom-aggregation.ts)

### Summary
`aggregatePhantomBids` prices a phantom order leg by taking a **liquidity-weighted median** of solver quotes, where each quote's weight is the solver's *live* on-chain balance of the leg's output token, read at aggregation time. A solver can temporarily inflate that balance (deposit right before its bid is aggregated, withdraw right after) to buy itself majority weight and force the published price to its own quote — exactly the "deposit → get favorable pricing → withdraw" pattern in the OracleMaker report, but here it manipulates a persisted market rate consumed by real orders rather than a single maker's own exposure.

### Finding Description
The weight computation reads a spot balance with no time-lock, no historical averaging, and no minimum holding period: [1](#0-0) 

That weight feeds `weightedMedian`, whose own documentation acknowledges the exposure: a bidder holding over half the total weight sets the published price *verbatim*: [2](#0-1) 

The design doc for this path confirms the intended (but exploitable) property in plain language: "a solver holding over half the leg's weight sets the published price verbatim, and inventory in the wrong token buys no influence on that leg." [3](#0-2) 

The resulting `medianPrice` is written into `PhantomOrderPriceSnapshotV2` unmodified (`lowestPrice = highestPrice = medianPrice`): [4](#0-3) 

and is renormalized straight into the pool's persisted `sellRate`/`buyRate` by `updateLiquidityPools`: [5](#0-4) 

Those pool rates are exactly what the SDK now defaults to for pricing real user intents — `quoteIntent`'s `indexed_rates` strategy consumes `LiquidityPool.buyRate`/`sellRate` directly, with no fallback and no sanity check against another source: [6](#0-5) 

So the causal chain from a single unprivileged action to real economic impact is: solver deposits output token → bids on a phantom order (or is already the majority holder of a token the pallet uses for its next phantom probe) → its weight dominates `weightedMedian` → the manipulated price is written verbatim into `PhantomOrderPriceSnapshotV2` → folded into `LiquidityPool.sellRate/buyRate` → consumed unmodified by every subsequent `quoteIntent` call using `indexed_rates`, mispricing real user orders that get filled/settled through the escrow (`IntentGatewayV3`/`ExtrinsicIntents`) path. Unlike OracleMaker's own single-maker exposure, this pushes a bad price to *all* counterparties transacting against the indexed rate until the next snapshot corrects it.

### Impact Explanation
A solver that briefly inflates its balance of a leg's output token can unilaterally set that leg's published price, and through the pool-rate merge, bias the `LiquidityPool` rate that real intents are quoted and settled against. This is a persistent (until the next window) protocol-level mispricing usable to extract value from counterparties on real fills — a fund-impacting manipulation of a market rate, analogous in class to the acknowledged OracleMaker medium-severity finding, but here it corrupts a shared oracle-like rate consumed by every intent rather than one maker's own risk position.

### Likelihood Explanation
Reachable by any unprivileged solver participating in phantom bidding (no special privilege required — placing a bid and holding/moving ERC-20/vault balance is the ordinary solver flow). The balance read has no minimum holding duration, no time-lock, and (per the code comments) is explicitly a spot read; a solver only needs liquidity for the window during which its bid is aggregated, which can be sourced short-term (e.g., a flash loan or a brief self-transfer) since ordinary ERC-20/ERC-4626 balances are read directly.

### Recommendation
Do not let a spot, instantaneous balance dominate a persisted market rate. Options: (1) require the weight to be sourced from a time-locked or historically-averaged balance (mirrors the "implement a time lock when deposit/withdraw into makers" mitigation the OracleMaker team proposed), (2) cap any single bidder's contribution to `weightedMedian`'s total weight (e.g., no bidder may exceed X% of total weight for a leg), and (3) cross-check the resulting `medianPrice` / `LiquidityPool` rate against an independent reference (Uniswap venue price, `referencePrice`/`maxDeviationBps`-style guard) before it is allowed to move `sellRate`/`buyRate`, so `quoteIntent`'s `indexed_rates` strategy cannot be steered by a single-block balance change.

### Proof of Concept
1. Solver S holds negligible balance of `tokenOut` on the destination chain, but knows a `PhantomOrderV2` bid window for `tokenOut` is about to close (`PhantomBidWindowExhausted` is imminent).
2. S transfers/borrows a large amount of `tokenOut` into its EVM account and submits a phantom bid quoting a favorable-to-itself price for the leg.
3. `aggregatePhantomBids` runs, reads S's balance (now large) via `getBalance`, computes S's weight as dominant, and `weightedMedian` returns S's exact quoted price verbatim (per `phantom-aggregation.ts:702-723` and the confirming unit test `weights quotes by balance — the high-liquidity solver pulls the median to its price`, see `sdk/packages/sdk/src/tests/phantomAggregation.test.ts:190-198`).
4. S moves the borrowed/temporary `tokenOut` back out immediately after the snapshot.
5. The manipulated `medianPrice` is folded into `LiquidityPool.sellRate`/`buyRate` (`updateLiquidityPools`), and every subsequent call to `quoteIntent` using the default `indexed_rates` strategy prices real user orders off this manipulated rate until the next snapshot window.

```typescript
//
// Callers must not hand this an entry set whose weights are all zero: with nothing to weight by it
// can only pick a quote by position, and for an even-sized set that position is the upper of the
// two middles — so "the median" becomes "whoever quoted higher", settable by a solver holding no
// inventory at all. aggregatePhantomBids drops such legs instead of pricing them. The fallback
// below stays only so an unguarded caller gets a number rather than a crash; treat reaching it as
// a caller bug.
export function weightedMedian(entries: { price: bigint; weight: bigint }[]): bigint {
	const sorted = [...entries].sort((a, b) => (a.price < b.price ? -1 : a.price > b.price ? 1 : 0))
	const totalWeight = sorted.reduce((acc, e) => (e.weight > 0n ? acc + e.weight : acc), 0n)

	if (totalWeight === 0n) {
		return sorted[Math.floor(sorted.length / 2)].price
	}

	let cumulative = 0n
	for (const entry of sorted) {
		if (entry.weight <= 0n) continue
		cumulative += entry.weight
		if (cumulative * 2n >= totalWeight) return entry.price
	}
	return sorted[sorted.length - 1].price
```
