### Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` trusts `request.shop` as the tenant identifier when dispatching a webhook to the host app's handler, but the HMAC signature that `Utils::HmacValidator` verifies only covers the raw request body, not the `shop` (or `topic`/`webhook-id`) header. Because every shop installed on the same app shares the same `client_secret`, a merchant who legitimately receives genuine webhooks for their own store can capture a validly-signed body+HMAC pair and replay it to the app's webhook endpoint with a forged `X-Shopify-Shop-Domain` header claiming to be a different, victim shop. The signature still validates, and the host handler receives data it believes originates from the victim's tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes/compares the signature strictly against that signable string: [2](#0-1) 

`Registry.process` then uses `request.shop`, which is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header — a value that was never part of the signed bytes — to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) [4](#0-3) 

The identity binding that should hold is:
`hmac(secret, bytes_verified) == hmac(secret, bytes_that_determine_the_tenant)`

Here, `bytes_verified = raw_body`, but `bytes_that_determine_the_tenant = shop header`, which are disjoint. Since all shops of a given app share one `client_secret`, any attacker who is themselves a legitimate installer of the app (an "unprivileged internet user" with no elevated access to other tenants) can:
1. Install the app on their own store and receive a genuine webhook (`raw_body`, valid `hmac`) for a topic of their choosing.
2. Replay that exact `raw_body`/`hmac` pair to the same webhook endpoint, substituting `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `HmacValidator.validate` passes (it never inspects the shop header), and `Registry.process` invokes the host's handler with `data.shop == "victim-shop.myshopify.com"` while `data.body` is attacker-controlled content.

The library ships no signal to the host application that `shop` is unauthenticated, and the documented handler contract (`docs/usage/webhooks.md`) explicitly encourages using `data.shop` to key work (e.g., `perform_later(topic: data.topic, shop_domain: data.shop, ...)`), reinforcing reliance on this unauthenticated field: [5](#0-4) 

### Impact Explanation
This allows cross-tenant data injection/confusion: an attacker who is a legitimate (but malicious) merchant of the same multi-tenant app can forge webhook events that the host app attributes to a different shop it also serves — e.g. injecting fabricated `orders/create`/`app/uninstalled`/other topic payloads "on behalf of" a victim tenant, or triggering victim-side side effects (revoking data, corrupting synced state, causing duplicate/incorrect processing) without ever compromising the victim's credentials. This matches the "cross-tenant access" Critical impact category, since the tenant boundary (`shop`) is not cryptographically bound to the authenticated content.

### Likelihood Explanation
Any user who can install the app on at least one shop (a routine, low-privilege action for any Shopify merchant/dev-store owner) can obtain one legitimately signed body+HMAC pair, then simply swap an HTTP header when POSTing to the app's public webhook endpoint. No secret material, TLS interception, or social engineering is required — only knowledge of the HMAC-validation logic in `Utils::HmacValidator`/`Webhooks::Request`, which is open source in this gem.

### Recommendation
Bind the shop (and topic/webhook-id) into the value that is HMAC-verified, or otherwise cryptographically tie the header-derived tenant identity to the signed body — for example by including the `shop`, `topic`, and `webhook-id` headers as part of `to_signable_string` (matching Shopify's documented webhook validation, which recommends validating the full request), or by having `Registry.process` cross-check `request.shop` against an independently retrieved/verified value (e.g. re-querying the webhook subscription's registered shop by `webhook_id` via the Admin API) before dispatching to handlers.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and registers for topic `orders/create`.
2. Shopify delivers a webhook: `raw_body = '{"id":1,...}'`, header `x-shopify-hmac-sha256 = HMAC(secret, raw_body)`, header `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker POSTs the identical `raw_body` and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `Utils::HmacValidator.validate` recomputes HMAC over `raw_body` only and it matches — validation succeeds.
5. `Registry.process` invokes the host's `WebhookHandler#handle` with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, letting the attacker inject content that the host application will process/store as belonging to the victim tenant.
