#### Title
`IntentGatewayV2.withdraw` on Tron reverts on zero-amount `TransferFailed`/native-send checks, permanently freezing escrow for orders with a zero-amount input token - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` iterates over `body.tokens` in the internal `withdraw` function and unconditionally issues a token/native transfer for every entry, without skipping zero-amount entries. `order.inputs` (which becomes `body.tokens` in the `WithdrawalRequest`) is attacker/user-controlled at `placeOrder` time and is only guarded against `amount == 0` at order-placement for the *predispatch*/regular transfer-in path, not for every downstream use of the same array. If any listed input token is a "strict" ERC-20 that reverts on zero-value transfers (the exact bug class described in the `WDIA` report), or more generally if `amount` for one of the escrowed tokens legitimately becomes `0` for some entry while other entries are non-zero (e.g. due to fee-token accounting or a specific input composition), the `token.call(...transfer(beneficiary, 0)...)` will return `success=false` for such a token and the whole `withdraw` reverts with `TransferFailed`, or a native zero-value send could similarly be rejected by unusual recipient logic.

### Finding Description
`withdraw` is reached from two unprivileged/relayer-triggered entry points:
- `onAccept` for `RequestKind.RedeemEscrow` / `RequestKind.RefundEscrow`, driven by a relayed cross-chain POST message. [1](#0-0) 
- `onGetResponse`, driven by a relayed GET response used for the refund/redeem flow. [2](#0-1) 

The `withdraw` function itself does not check `amount == 0` before calling `transfer`: [3](#0-2) 

Compare this to the sibling function `_withdraw` in `IntentsBase.sol` (used by the non-Tron `IntentGatewayV2`/`IntrinsicIntents` code path), which explicitly skips zero-amount entries with `if (amount == 0) continue;` before transferring: [4](#0-3) 

This shows the codebase is aware zero-amount transfers must be skipped, but the fix was not applied to the Tron `withdraw` implementation. `body.tokens` is built directly from `order.inputs` at cancel/refund/redeem time: [5](#0-4) 

If any one of the tokens configured as an order input is a "zero-transfer-reverting" token (same class of behavior as the reported `WDIA`), or the amount for one of the escrowed line items is zero for any other legitimate reason (partial reductions, protocol-fee rounding making the reduced amount zero, dust accounting, etc.), the low-level `.call` to `transfer(beneficiary, 0)` returns `success = false` for that token, causing `revert TransferFailed()` and reverting the *entire* `withdraw` call — including the fee-token payout logic that runs afterward. Because `withdraw` is the only code path that clears `_orders[commitment][token]` escrow accounting and pays out `beneficiary`, a permanent revert here permanently freezes all escrowed funds for that commitment: the relayed message that triggered `onAccept`/`onGetResponse` cannot be resubmitted with a different outcome (the underlying commitment/proof is fixed), so the user's principal and reward tokens for that order are locked forever.

### Impact Explanation
This is a direct permanent freezing-of-funds bug reachable by any ordinary user through the normal intent lifecycle (place → cancel/timeout → redeem/refund), with no privileged action required. Because the same `withdraw` function also handles fee-token payout after the token loop, a single problematic zero-amount entry in `body.tokens` blocks distribution of the entire escrow (input tokens + protocol fee token) for that order, matching the "permanent freezing of funds" impact bar for Critical/High severity classes covered by this scan.

### Likelihood Explanation
Likelihood is Medium: it requires either (a) an input token used in an order that reverts on zero-value ERC-20 transfers (a known real-world token behavior class, exactly the pattern documented in the external `WDIA` report), or (b) an order construction/fee-reduction path that drives one of the escrowed input amounts down to exactly zero while keeping the commitment intact. Both are plausible given the protocol allows arbitrary ERC-20 tokens to be configured as order inputs and does not filter for "strict" zero-transfer-reverting tokens anywhere in the Tron withdrawal path.

### Recommendation
Add a zero-amount guard identical to the one already used in `IntentsBase._withdraw` before performing each token transfer in `evm/tron/contracts/apps/IntentGatewayV2.sol`'s `withdraw` function:
```solidity
uint256 amount = body.tokens[i].amount;
if (amount == 0) { unchecked { ++i; } continue; }
```
Apply the same skip to the native-token branch and re-verify the fee-token transfer at the end of `withdraw` uses `fees > 0` (it already does), ensuring consistency between the two `IntentGatewayV2` implementations (Tron vs. EVM/`IntentsBase`).

### Proof of Concept
1. A user places an order (via `placeOrder`) whose `order.inputs` includes a token `T` that reverts on `transfer(_, 0)` (or whose downstream reduced/fee-adjusted amount can become `0`).
2. The order is later cancelled/expired/refunded, generating a `WithdrawalRequest` where `body.tokens` includes an entry `{token: T, amount: 0}` alongside other non-zero entries.
3. A relayer delivers the corresponding POST/GET response, invoking `onAccept`/`onGetResponse` → `withdraw(body, ...)`.
4. In the loop over `body.tokens`, the call `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, 0))` for token `T` returns `success = false` (or reverts), causing `withdraw` to revert with `TransferFailed()`.
5. Because the commitment/proof and message are already fixed by the relayed request, the transaction can never succeed with the same inputs — the escrowed funds for that commitment (including any other token amounts and fees for the same order) are permanently locked, with no code path able to bypass the zero-amount transfer.     function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }
