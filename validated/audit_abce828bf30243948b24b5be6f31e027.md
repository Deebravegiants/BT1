### Title
Webhook `shop` (and `topic`/`api_version`/`webhook_id`) header is trusted for tenant routing without being covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, so the HMAC verified by `Utils::HmacValidator.validate` binds nothing but the body bytes. The `shop-domain` header, which `Registry.process` passes straight into `WebhookMetadata` and thus into the app's webhook handler as the authoritative tenant identifier, is never part of the signed material.

### Finding Description
`Registry.process` enforces `raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)` (`lib/shopify_api/webhooks/registry.rb:190`), then builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`) and dispatches it to the handler.

`Utils::HmacValidator.validate_signature` computes the HMAC over `verifiable_query.to_signable_string` (`lib/shopify_api/utils/hmac_validator.rb:27-31`). For `Webhooks::Request`, `to_signable_string` returns `@raw_body` only (`lib/shopify_api/webhooks/request.rb:36-38`). Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all read from HTTP headers via `shopify_header` (`lib/shopify_api/webhooks/request.rb:15-33`, `67-70`) and are not included in `to_signable_string`.

This is exactly the identity-binding gap described in the analog bug class: a field that is acted on (`shop`, used by the handler/host app to select which tenant's data to update) is not covered by the value that is cryptographically verified (the HMAC, which only covers `@raw_body`). The equality that should hold — "the shop this signature was produced for" == "the shop the handler treats this payload as belonging to" — is not enforced anywhere in this code path.

Because the HMAC secret (`Context.api_secret_key`) is shared across all shops/tenants of a single app installation, any party who can obtain one validly-signed `(raw_body, hmac)` pair for that app (e.g., a merchant who installed the app and can observe/replay webhook deliveries sent to their own endpoint, or any actor who can replay a captured delivery) can resend that exact body and HMAC to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header value. The signature still validates because the header is not part of the signed bytes, and the handler receives `shop` pointing at a different tenant than the one the payload actually originated from.

### Impact Explanation
If a host application uses `WebhookMetadata#shop` (as delivered by this gem) to key its own per-tenant data (a common and encouraged pattern — see `docs/usage/webhooks.md` handler examples), a replayed payload with a forged `shop-domain` header lets an attacker write or process data under a shop they do not own. This is a cross-tenant identity confusion enabled directly by this gem's incomplete HMAC binding, matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Medium: the attacker needs at least one legitimately-signed `(body, hmac)` pair for the target app (obtainable by installing the app on their own shop and capturing/replaying their own webhook deliveries, since the app's webhook endpoint is a public internet-facing URL by design), and needs the target app's handler logic to trust `data.shop` for tenant scoping without additional cross-checks against the body's own content. No access to `api_secret_key`, tokens, or privileged accounts is required — only observation of one's own legitimately delivered webhook.

### Recommendation
Include `shop`, `topic`, `api_version`, and `webhook_id` in the HMAC-signed material (or otherwise cryptographically bind the header-derived tenant identifier to the verified payload), so that `Utils::HmacValidator.validate` fails if any of these header values are altered relative to what Shopify actually signed for. At minimum, document prominently that `WebhookMetadata#shop`/`#topic` are unauthenticated header values and must never be used alone as a tenant key without corroborating the shop identity from the authenticated body content or from an independently stored per-shop webhook secret/session lookup.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook (e.g. `orders/create`) so Shopify delivers a POST to the app's public webhook endpoint with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC over raw body>`, and some JSON `raw_body`.
2. Attacker captures this exact `raw_body` and `x-shopify-hmac-sha256` value (they own this shop, so they can capture their own deliveries, e.g. via a debugging proxy on their own infrastructure).
3. Attacker replays the identical request to the app's webhook endpoint, but changes only `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
4. `Webhooks::Request.new` accepts the request (all required headers present), and `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (`= @raw_body`, unchanged) and finds it matches — validation succeeds (`lib/shopify_api/webhooks/registry.rb:190`, `lib/shopify_api/webhooks/request.rb:36-38`).
5. `Registry.process` builds `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` and invokes the app's handler, which now processes attacker-controlled body content under the victim shop's tenant identity. [1](#0-0) [2](#0-1) [3](#0-2)
