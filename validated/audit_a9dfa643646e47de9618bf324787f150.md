### Title
`Router.buy`/`Router.sell` credit `Pair`'s stored reserves with the nominal transfer amount instead of the LT/Token balance actually received, permanently desyncing curve accounting from real holdings - (`packages/contracts/src/Router.sol`, `packages/contracts/src/Pair.sol`)

### Summary
`Router.buy` and `Router.sell` move the reserve asset (the external BounceTech LT) and the launched `Token` with a plain `safeTransferFrom`, then unconditionally credit `Pair`'s stored `tokenReserve`/`assetReserve` with the *requested* amount via `Pair.swap`, never checking the pair's real post-transfer balance. This is the same root cause as the reported `DonationVotingMerkleDistributionVaultStrategy::_afterAllocate` bug: internal accounting trusts a nominal transfer amount instead of measuring the actual balance delta.

### Finding Description
`Router.buy` pulls the LT into the pair and immediately marks the full nominal amount as received: [1](#0-0) 

```
IERC20(asset).safeTransferFrom(to, pairAddr, amountInUsed);
IPair(pairAddr).transferToken(to, tokensOut);
IPair(pairAddr).swap(0, tokensOut, amountInUsed, 0);
```

`Router.sell` does the symmetric thing on the `Token` leg: [2](#0-1) 

Both paths feed straight into `Pair.swap`, which updates the stored pool state purely from the arguments it's given, with no balance verification at all: [3](#0-2) 

```
function swap(uint256 tokenIn, uint256 tokenOut, uint256 assetIn, uint256 assetOut) external onlyRouter returns (bool) {
    uint256 newTokenReserve = (_pool.tokenReserve + tokenIn) - tokenOut;
    uint256 newAssetReserve = (_pool.assetReserve + assetIn) - assetOut;
    if ((newTokenReserve + 1) * (newAssetReserve + 1) < _pool.k) revert KInvariantViolated();
    _pool.tokenReserve = newTokenReserve;
    _pool.assetReserve = newAssetReserve;
    ...
}
```

There is no analog of `FeeVault.accrue`'s underfund check (`balanceOf(this) < totalAccrued...` → revert) here. `FeeVault` explicitly guards against exactly this class of bug by cross-checking its own USDC balance after a depositor's transfer: [4](#0-3) 

`Pair`/`Router` has no equivalent guard: `assetReserve`/`tokenReserve` are pure bookkeeping numbers that are never reconciled against `IERC20(assetToken).balanceOf(pairAddr)` or `IERC20(launchedToken).balanceOf(pairAddr)`. `Pair.assetBalance()`/`tokenBalance()` exist as live balance readers but are only consulted by graduation's donation-detection logic, never by `swap()` itself.

This stored, unreconciled `assetReserve` is later trusted as ground truth for draining real funds at graduation: [5](#0-4) 

```
function graduate(address token, uint256 amount) external onlyRole(BONDING_ROLE) {
    ...
    IPair(pairAddr).transferAsset(msg.sender, amount);
}
```

`amount` here is `ltFromPair = storedAssetReserve - virtualLtReserve`, computed straight from the (potentially inflated) stored reserve: [6](#0-5) 

`Pair.transferAsset` is a real `safeTransfer` that will revert if the pair doesn't actually hold that much LT: [7](#0-6) 

If any single leg of the transfer chain into the pair (the LT `safeTransferFrom` in `Router.buy`, or a hostile/quirky future integration) ever delivers less than the requested `amountInUsed`/`amountIn` to `pairAddr`, `_pool.assetReserve` (or `tokenReserve`) becomes permanently larger than what the pair physically holds — the `+1`/`+1` K-slack in `Pair.swap` only guards against dust rounding on the *stored* numbers, it does nothing to catch a real balance shortfall since it never reads `balanceOf`.

### Impact Explanation
Once `assetReserve` overstates the pair's real LT balance:
- Phase-1 graduation (`_enterGraduating`, fired inline inside a normal `Zap.buy` at the threshold-crossing trade) flips the token's lifecycle to `Graduating` and freezes trading, caching `ltFromPair` computed from the inflated stored reserve.
- Phase-2 `finalizeGraduation`'s call into `Router.graduate` (`Pair.transferAsset`) then attempts to move more LT out of the pair than it actually holds and reverts. Because `finalizeGraduation` is the only path out of the `Graduating` state and there is no rescue/rollback, the token is permanently bricked in `Graduating` — every trader's curve-raised LT for that token, plus the creator's/holders' tokens, are frozen forever (the exact "permanent freezing of trader/creator/LP funds" impact class).
- Short of a full brick, any surviving sell path (`Router.sell` → `_computeSell` → `Pair.transferAsset`) can likewise attempt to pay out `assetOut` computed against inflated stored reserves, again either reverting (DoS for sellers) or, if slack elsewhere in the pair's balance absorbs it, quietly draining the pair below what later legitimate claimants need — an insolvency identical in shape to the original report's "recipients can't claim because balance < claims".

### Likelihood Explanation
The desync is triggered purely by a shortfall between the amount `Router.buy`/`Router.sell` requests via `safeTransferFrom` and what `pairAddr` actually receives — a single unprivileged trader routes into this every time they call `Zap.buy`/`Zap.sell`, since those are the only entry points that invoke `Bonding.buy`/`Bonding.sell` → `Router.buy`/`Router.sell`. No privileged action is required; the bug is latent in every trade and only needs one shortfall event (whatever its origin) to permanently corrupt a given pair's reserve.

### Recommendation
In `Router.buy`/`Router.sell`/`Router.addInitialLiquidity`, measure the pair's actual `assetToken`/`launchedToken` balance immediately before and after each `safeTransferFrom`, and pass the *measured delta* — not the requested nominal amount — into `Pair.swap`/`Pair.mint`. Alternatively, have `Pair.swap` itself assert `IERC20(assetToken).balanceOf(address(this)) >= newAssetReserve` (and the token-side equivalent) before committing the new stored reserves, mirroring the balance-based underfund check `FeeVault.accrue` already performs for USDC.

### Proof of Concept
1. A trader calls `Zap.buy(tokenAddress, usdcAmount, 0, referrer)`; `_executeBuy` mints LT to Zap and calls `_buyOnCurve`, which calls `Bonding.buy` → `Router.buy(amountIn, token, to=Zap)`.
2. `Router.buy` executes `IERC20(asset).safeTransferFrom(Zap, pairAddr, amountInUsed)`. Assume (for any reason — a future LT implementation quirk, a misconfigured/retired LT redeploy, or any ERC20 in this slot that ever delivers less than requested) `pairAddr` receives `amountInUsed - Δ` instead of `amountInUsed`.
3. `Router.buy` still calls `IPair(pairAddr).swap(0, tokensOut, amountInUsed, 0)`, so `_pool.assetReserve += amountInUsed` even though the pair's real LT balance only grew by `amountInUsed - Δ`. `_pool.assetReserve` is now permanently `Δ` higher than `IERC20(assetToken).balanceOf(pairAddr)`.
4. When this token graduates (`_enterGraduating`/`finalizeGraduation`), `_prepareGraduationLiquidity` computes `ltFromPair = storedAssetReserve - virtualLtReserve` off the inflated `assetReserve`, and `Router.graduate` calls `Pair.transferAsset(msg.sender, ltFromPair)`, which reverts because the pair doesn't hold that much LT — `finalizeGraduation` can never succeed for this token, permanently freezing all LT raised on its curve and the tokens held by its buyers.

**Note on verification limits:** I was unable to fully trace `Bonding.buy`'s exact parameter forwarding to `Router.buy` (specifically whether `to` resolves to `Zap` or the trader EOA) within the available context — this affects only the caller identity in step 2, not the reserve-crediting root cause in `Router.sol`/`Pair.sol`, which is confirmed directly from the cited code.

    ///         in turn only calls `graduate` from
    ///         `_prepareGraduationLiquidity` — which is unreachable once the
    ///         token's lifecycle has flipped past `Curve`. So the leftover

        uint256 amount
