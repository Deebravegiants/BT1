### Title
Webhook `shop` (and `topic`/`api_version`/`webhook_id`) headers are not covered by the HMAC, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while the `shop`, `topic`, `api_version`, and `webhook_id` values used by `Registry.process` to identify the tenant and dispatch the webhook are taken from unauthenticated HTTP headers that are never included in the signable string used for HMAC verification.

### Finding Description
`Webhooks::Request` implements `Utils::VerifiableQuery` and defines: [1](#0-0) [1](#0-0) 

```ruby
sig { override.returns(String) }
def to_signable_string
  @raw_body
end
```

`shop`, `topic`, `api_version`, and `webhook_id` are all read straight off attacker-controllable HTTP headers with no cryptographic binding to the body: [2](#0-1) 

`Registry.process` validates only the body-based HMAC via `Utils::HmacValidator.validate`, then immediately trusts `request.shop`, `request.topic`, and other headers to build `WebhookMetadata` and dispatch to the registered handler: [3](#0-2) 

`HmacValidator.validate` / `validate_signature` only ever signs `verifiable_query.to_signable_string`, i.e., the raw body — never the headers: [4](#0-3) 

Because Shopify webhook HMACs are computed with the app's single shared `client_secret` (`Context.api_secret_key`) — identical for every shop that has installed the app, not a per-shop secret — the resulting `hmac-sha256` value is valid for that body *regardless of which shop it originated from*. The equality this code assumes but does not enforce is:

`request.shop` (used to route the payload to the tenant) == `shop that produced/authorized this HMAC-signed body`

but that binding does not actually exist, because `shop` is outside the HMAC's coverage.

### Impact Explanation
Any unprivileged user who can install the target app on their own shop (a normal onboarding flow for a public/embedded app) receives correctly HMAC-signed webhook bodies from Shopify for their own shop. Because the HMAC is computed with the app's shared secret and only over the body, the attacker can replay that body (unmodified) against the same app's webhook endpoint while forging the `X-Shopify-Shop-Domain` (and `Topic`/`Api-Version`/`Webhook-Id`) headers to name a different, victim shop. `HmacValidator.validate` will still succeed (it only checks the body signature), and `Registry.process` will hand the handler a `WebhookMetadata` claiming the data came from the victim shop. Any handler logic that trusts `data.shop` for tenant identification (e.g., looking up/mutating per-shop records, GDPR data requests, `shop/redact`) can be tricked into acting on/attributing data across tenants — a cross-tenant access/spoofing condition.

### Likelihood Explanation
Requires only that the attacker be able to install the app on a shop they control (or otherwise obtain one legitimately-signed webhook body+HMAC pair from Shopify) and be able to send arbitrary HTTP requests to the app's public webhook endpoint with custom headers — both are unprivileged, internet-reachable actions with no secrets needed.

### Recommendation
Bind the identity fields to the HMAC coverage instead of trusting bare headers: include `shop`, `topic`, `api_version`, and `webhook_id` in the string that is HMAC-verified (e.g., concatenate them with the body before computing/verifying the signature, mirroring how Shopify's own webhook signing should be validated end-to-end), or independently verify that the shop domain in the header matches a shop that is expected/registered for this specific webhook subscription before dispatching to the handler.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook event (e.g., `orders/create`) delivered to the app's public webhook endpoint. They capture the raw body `B` and the valid header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
2. Attacker resends body `B` with header `H` unchanged to the same endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` recomputes `HMAC-SHA256(api_secret_key, B)` (see `lib/shopify_api/utils/hmac_validator.rb:27-31`) — this still equals `H` since the shop header is not part of the signed string, so validation succeeds.
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:189-200`) builds `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and dispatches to the registered handler, which now processes attacker-supplied data under the victim's tenant identity.
