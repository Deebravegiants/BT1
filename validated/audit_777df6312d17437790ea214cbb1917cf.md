**No vulnerability found for this question.**

Explanation for context: The `create_signer::create_signer(fee_payer_address)` call in `fee_payer_script_prologue` (and its `_extended`/`unified_prologue_fee_payer_v2`/`versioned_prologue` counterparts) is only used to build a throwaway signer to pass into `prologue_common` for the balance check; it is not treated as proof of authentication by itself. Immediately after `prologue_common` runs, the code asserts `fee_payer_public_key_hash == account::get_authentication_key(fee_payer_address)` [1](#0-0)  and the same pattern for `_extended`/`versioned_prologue` variants [2](#0-1) .

The `fee_payer_public_key_hash` argument that is compared here is not attacker-suppliable Move-level data — it corresponds to the public key whose signature the Rust VM/adapter already verified against the raw transaction's fee-payer signature slot before the prologue ever executes. If that signature check fails, the transaction is discarded before Move code runs at all, so `epilogue_gas_payer_extended`/`unified_epilogue_v2` (which perform the `transaction_fee::burn_fee(gas_payer, burn_amount)` call at line 613/827) are never reached with an unauthenticated `gas_payer`.

Because the `gas_payer` address used in the epilogue is the same address whose authentication key was cross-checked against the actually-verified signature in the prologue, there is no way for an unprivileged caller to substitute a different, unauthenticated address as `gas_payer` and have their fungible store burned instead. The authority check (auth-key vs. verified public key) already closes this path, matching the "Reject if authority checks... already close the path" criterion in the review standard.
