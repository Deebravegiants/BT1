Audit Report

## Title
CORS wildcard-origin suffix check allows hostname-confusion bypass in Gateway HTTP server - (File: core/services/gateway/network/httpserver.go)

## Summary
`isAllowedOrigin` in the Gateway's public HTTP server validates wildcard CORS entries (e.g. `*.example.com`) using a raw `strings.HasSuffix(originHost, allowedHost)` check with no domain-label boundary enforcement. This allows an attacker-controlled hostname such as `evilexample.com` to be treated as a subdomain of `example.com`, causing the server to reflect the attacker's `Origin` into `Access-Control-Allow-Origin` and expose gateway JSON-RPC responses to cross-origin browser reads.

## Finding Description
In `isAllowedOrigin` [1](#0-0) , after matching scheme and port, wildcard entries strip the `*.` prefix and compare using `strings.HasSuffix(originHost, allowedHost)`. This is a plain substring-suffix comparison rather than a domain-boundary comparison: it does not require that the character preceding the matched suffix in `originHost` be a `.`. Consequently, for an allowed entry `https://*.example.com`, an origin host `evilexample.com` (no dot before "example.com") satisfies `strings.HasSuffix("evilexample.com", "example.com") == true` and is incorrectly classified as trusted.

When `isAllowedOrigin` returns true, `handleRequest` reflects the raw `Origin` header value directly into the `Access-Control-Allow-Origin` response header [2](#0-1) , and the subsequent response body from `s.handler.ProcessRequest` [3](#0-2)  becomes readable by JavaScript running on the attacker's confusable-domain page via a cross-origin `fetch`/`XHR`. No other validation step exists between `isAllowedOrigin`'s decision and the header being set — the suffix check is the sole gate, and it is insufficient.

## Impact Explanation
If an operator enables CORS with a wildcard allowed origin (a pattern the code itself is written to support, as shown by the `*.remix.com` example in its own comment), an attacker can register any domain ending in the configured suffix without a dot separator (e.g. `evilexample.com` for `*.example.com`) and have pages hosted there treated as an authorized origin. A victim visiting the attacker's page while authenticated/interacting with the gateway would have their browser issue cross-origin requests that the attacker's script can then read the responses of, resulting in disclosure of gateway JSON-RPC response content — a cross-origin/cross-user response confusion consistent with CWE-200/information disclosure.

## Likelihood Explanation
This is exploitable by any unprivileged remote actor with no credentials needed against the Gateway endpoint itself; the only precondition is that the deployment has CORS enabled with at least one wildcard entry in `CORSAllowedOrigins`, which is a supported, intentionally-coded configuration path rather than an unsupported misconfiguration. Given that precondition, the bypass is trivially and repeatably triggerable by simply registering a confusable domain and sending/hosting a request with the crafted `Origin` header.

## Recommendation
Require a domain-label boundary when matching wildcard suffixes, e.g.:
```go
if strings.HasPrefix(allowedHost, "*.") {
    base := allowedHost[1:] // ".example.com"
    if originHost == base[1:] || strings.HasSuffix(originHost, base) {
        return true
    }
}
```
This ensures `originHost` must either equal the base domain exactly or be preceded by a literal `.` before the suffix, preventing `evilexample.com` from matching `*.example.com`.

## Proof of Concept
1. Configure the Gateway with `CORSEnabled = true` and `CORSAllowedOrigins = ["https://*.example.com"]`.
2. Send an HTTP request to the gateway endpoint with header `Origin: https://evilexample.com`.
3. `splitURL` parses `originHost = "evilexample.com"`; wildcard branch computes `allowedHost = "example.com"`, and `strings.HasSuffix("evilexample.com", "example.com")` evaluates to `true`, so `isAllowedOrigin` returns `true`.
4. The server responds with `Access-Control-Allow-Origin: https://evilexample.com`, verifiable via a simple Go unit test calling `isAllowedOrigin("https://evilexample.com")` with the above config and asserting it returns `true`, or an HTTP integration test asserting the response header value.
