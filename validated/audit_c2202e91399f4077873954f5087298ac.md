### Title
`PoaBridge::describeWithdrawal` matches withdrawal status by `assetId` only, misreporting completion status/txHash for batched withdrawals of the same token - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal` and the underlying `waitForWithdrawalCompletion` utility resolve the withdrawal status for a specific withdrawal by matching only on `assetId`, ignoring destination address and amount. This is the same equality-breaking bug class as the report's `tokenURI` example: a lookup returns "data" for a request that does not uniquely identify it, so the caller can be handed a status/txHash that belongs to a different withdrawal.

### Finding Description
`findMatchingWithdrawal` in `PoaBridge` finds the first withdrawal entry whose `near_token_id` matches the requested `assetId`, without checking the destination address or amount: [1](#0-0) 

The equivalent helper in `internal-utils` has the same behavior and an explicit comment acknowledging the gap: [2](#0-1) 

`describeWithdrawal` uses this match to report `completed`/`failed`/`pending` status and the destination `txHash` for the withdrawal being watched: [3](#0-2) 

This is reachable through the public SDK batching API: `IntentsSDK.createWithdrawalCompletionPromises`/`waitForWithdrawalCompletion` accept an array of `WithdrawalParams` and create one `WithdrawalIdentifier` per entry, each carrying only `assetId`/`amount`/`destinationAddress` in `withdrawalParams`, but the POA lookup discards amount/destination and matches on `assetId` alone: [4](#0-3) [5](#0-4) 

If a single NEAR transaction contains two POA withdrawals of the same token (same `near_token_id`) to two different destinations/amounts — which the batching API allows callers to construct — `Array.prototype.find` always returns the *first* match in the (unsorted, per the code's own comment) API response for both watcher instances. The equality that should hold — "the status/txHash returned for withdrawal N corresponds to the on-chain outcome of withdrawal N" — is broken: both callers polling for their own withdrawal can be told about the same entry, and one of the two withdrawals is reported using the wrong `transfer_tx_hash`/status.

### Impact Explanation
This falls in the accepted "status reported that is not the on-chain outcome" category. An integrator using `createWithdrawalCompletionPromises`/`waitForWithdrawalCompletion` for a batch containing duplicate-asset withdrawals could be told withdrawal B is `completed` with a `txHash` that actually belongs to withdrawal A (or vice versa), which can lead to crediting/reconciling based on the wrong transaction, or reporting `pending`/`failed` for a withdrawal that has actually completed (or the reverse). This matches "a status or hash misreport making an integrator credit or refund twice" from the High severity bucket.

### Likelihood Explanation
Likelihood is limited: it requires a caller to submit two withdrawals of the exact same NEP-141 asset in the same NEAR transaction via the batch withdrawal API, which is an uncommon but explicitly-supported usage pattern (the code comment even documents the limitation as a known, accepted gap, and the API doesn't attempt to disambiguate). It is not attacker-controlled in the sense of an external adversary forging data — it's a self-inflicted correctness bug for legitimate batch use, and the POA API itself doesn't currently support disambiguating same-asset withdrawals, so this is partly bounded by an external dependency's limitation (which is flagged out-of-scope for pure API trust issues, but the client-side `find`-first-match logic is the SDK's own defect).

### Recommendation
Extend `WithdrawalCriteria`/the assetId-only match to also disambiguate by destination address and amount (or index within same-asset entries) before consuming the first match, so each concurrent watcher for a batch withdrawal resolves to the withdrawal that was actually requested, e.g.:
```diff
function findMatchingWithdrawal(
  withdrawals: WithdrawalStatusResponse["withdrawals"],
- assetId: string,
+ criteria: { assetId: string; destinationAddress: string; amount: bigint; alreadyMatchedKeys: Set<string> },
) {
- return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
+ return withdrawals.find((w) =>
+   `nep141:${w.data.near_token_id}` === criteria.assetId &&
+   w.data.address === criteria.destinationAddress &&
+   BigInt(w.data.amount) === criteria.amount &&
+   !criteria.alreadyMatchedKeys.has(matchKey(w)),
+ );
```
At minimum, until POA API support lands, reject/guard the batch API from accepting two withdrawals with identical `assetId` in one call, or serialize/tag matched entries so the same withdrawal record cannot be attributed to more than one caller.

### Proof of Concept
1. Construct a batch withdrawal via `sdk.createWithdrawalIntents`/`createWithdrawalCompletionPromises` with two `WithdrawalParams` entries both using `assetId = "nep141:usdc.token.near"` but different `destinationAddress`/`amount`, routed through `PoaBridge`.
2. Submit the resulting intent in one NEAR transaction, producing two POA withdrawal records with the same `near_token_id` but different `address`/`amount` in the withdrawal-status API response (as the code's own test fixture demonstrates two withdrawals sharing a token id) — see the test data shape in [6](#0-5)  (there for `chain`-differentiated assets, but nothing in `findMatchingWithdrawal` prevents two same-`assetId` entries).
3. Call `describeWithdrawal`/`waitForWithdrawalCompletion` concurrently for both `WithdrawalIdentifier`s; both resolve via `findMatchingWithdrawal`, which returns the same first array element (`Array.prototype.find`) to both callers regardless of which one actually corresponds to their `destinationAddress`/`amount`.
4. Observe that at least one of the two completion promises resolves with the `transfer_tx_hash`/status belonging to the *other* withdrawal, violating the "reported status matches on-chain outcome for the requested withdrawal" invariant.

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

						wid: entry.wid,
						signal,
						logger,
					});
				})();

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}
