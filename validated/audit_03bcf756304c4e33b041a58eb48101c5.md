## Analog Found

### Title
Unauthenticated/unscoped pipeline task-run resumption via `/v2/resume` allows cross-job result injection - (File: `core/web/pipeline_runs_controller.go`)

### Summary
`PipelineRunsController.Resume` accepts an attacker-supplied `taskID` (a UUID from the URL) and forwards it directly to `ResumeJobV2` → `runner.ResumeRun` → `orm.UpdateTaskRunResult`, without ever verifying that the caller is authorized for the *specific* job/run associated with that task ID. Any principal holding only the minimal "run" role (which includes External Initiators, auto-granted `UserRoleRun` on every authenticated request) can call this endpoint with an arbitrary or guessed task UUID and inject a result/error value into a suspended pipeline run belonging to a completely different job/tenant.

### Finding Description
The Sherlock report's root cause is that `reclaimContract()` trusts a caller-supplied `Order` struct/hash as proof that a contract exists and belongs to the caller, when in fact no existence or ownership check is performed — the zero-value defaults (`bulls[contractId] = address(0)`) pass every guard, letting an attacker manipulate funds tied to an entity they never created.

The chainlink analog is structurally identical: identity/ownership of the referenced entity is never checked, only its *state*. [1](#0-0) 

`Resume` parses `taskID` from the URL, decodes a JSON body into a `ResumeRequest`, and calls `prc.App.ResumeJobV2(ctx, taskID, result)` with **no check that the authenticated principal (user or, notably, an External Initiator with `run` role) owns, created, or is otherwise associated with the job that produced this `taskID`.**

This flows into: [2](#0-1) 

which calls `orm.UpdateTaskRunResult`: [3](#0-2) 

The only guard is a SQL predicate `WHERE pipeline_task_runs.id = $1 AND pipeline_runs.state in ('running','suspended')`. This is a check that the *entity exists in the right state* — exactly like the `reclaimContract()` bug's checks on `order.expiry`/`settledContracts`/`reclaimedContracts` — but there is no check that this particular pipeline run "belongs" to the caller's job/tenant/webhook context.

Compare this to `/v2/jobs/:ID/runs` (`Create`), which explicitly restricts External Initiators from triggering runs by numeric job ID and gates on `isUser && !isEI`: [4](#0-3) 

No equivalent restriction or job-scoping exists in `Resume`. Additionally, the audit log event name itself — `audit.UnauthedRunResumed` — signals that this action is treated internally as effectively unauthenticated/unscoped: [5](#0-4) 

An External Initiator is only meant to be able to trigger runs for the webhook job(s) it was registered against, and is granted the generic `run` role at authentication time: [6](#0-5) 

But `Resume` operates on a global `pipeline_task_runs.id` UUID namespace with no per-job/per-initiator scoping — so an EI (or any run-role token) can resume/complete a task run belonging to any other job in the system, not just the webhook job it is bound to.

### Impact Explanation
Successful exploitation lets a low-privilege caller (an External Initiator credential, which is explicitly meant to be scoped to a single webhook job) inject an arbitrary `value`/`error` into the suspended task run of an unrelated job — for example a pending bridge callback (`type=bridge async=true`), an ETH transaction confirmation callback, or any other async/suspended step. This is a cross-job/cross-tenant response confusion: the attacker controls output data that downstream tasks (median, jsonparse, ETH transactions, on-chain writes) will subsequently consume, potentially corrupting price feeds, VRF fulfillment paths, or automation results for jobs the caller has no legitimate access to. Because `pipeline_task_runs.id` values are UUIDv4, blind guessing is impractical, but an attacker who can observe or infer active task UUIDs (e.g., through logs, timing, or a compromised low-trust integration) can hijack that run's completion.

### Likelihood Explanation
Requires only "run"-role level authentication, the weakest privileged, unprivileged-facing role in the auth model, and no relationship between the caller's registered job/EI and the target task run's job is validated. The security-relevant barrier is solely the unguessability of the UUID and knowledge of pending task IDs, not any authorization logic in the code — a design gap identical in class to the "no existence/ownership check" root cause in the reported `reclaimContract()` finding.

### Recommendation
Before calling `App.ResumeJobV2`, verify that the resolved `pipeline_task_runs.pipeline_run_id` → `pipeline_runs.pipeline_spec_id` → job is one the authenticated principal is authorized to act on:
- For External Initiator callers, ensure the job's registered external initiator matches the authenticated EI (mirroring the `isUser && !isEI` job-ID restriction already applied in `Create`).
- Alternatively, restrict `/v2/resume` to require full user-role authentication (`edit`/`run` tied to a logged-in user) rather than accepting generic EI "run" role tokens, since EIs are meant only to trigger new runs, not resume arbitrary pending runs.

### Proof of Concept
1. Register an External Initiator (`POST /v2/external_initiators`) bound only to Webhook Job A; obtain its `AccessKey`/`Secret`.
2. A different, unrelated Job B (e.g., a bridge-based OCR/FluxMonitor job) has an in-flight async task suspended, awaiting an external bridge callback — its `pipeline_task_runs.id` is `T`.
3. Using Job A's EI credentials, send `PATCH /v2/jobs/<jobB-id>/runs/T` with `{"data":{"result": "<attacker-controlled value>"}}` and headers `X-Chainlink-EA-AccessKey` / `X-Chainlink-EA-Secret`.
4. `AuthenticateExternalInitiator` succeeds (grants `UserRoleRun`) irrespective of Job A/B mismatch; `Resume` accepts `T` with no ownership check and calls `ResumeJobV2`, injecting the attacker's value into Job B's suspended run, which then resumes execution with poisoned data.

// Resume finishes a task and resumes the pipeline run.
// Example:
// "PATCH <application>/jobs/:ID/runs/:runID"
func (prc *PipelineRunsController) Resume(c *gin.Context) {
	taskID, err := uuid.Parse(c.Param("runID"))
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	rr := pipeline.ResumeRequest{}
	decoder := json.NewDecoder(c.Request.Body)
	err = errors.Wrap(decoder.Decode(&rr), "failed to unmarshal JSON body")
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}
	result, err := rr.ToResult()
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	if err := prc.App.ResumeJobV2(c.Request.Context(), taskID, result); err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	prc.App.GetAuditLogger().Audit(audit.UnauthedRunResumed, map[string]any{"runID": c.Param("runID")})
	c.Status(http.StatusOK)
}

				r.lggr.Errorw("Resume run failure", "err", err)
			}
			r.lggr.Debug("Resume run success")

	}
	return nil
}

func (o *orm) UpdateTaskRunResult(ctx context.Context, taskID uuid.UUID, result Result) (run Run, start bool, err error) {
	if result.OutputDB().Valid && result.ErrorDB().Valid {
		panic("run result must specify either output or error, not both")
	}
	err = o.transact(ctx, func(tx *orm) error {
		sql := `
		SELECT pipeline_runs.*, pipeline_specs.dot_dag_source "pipeline_spec.dot_dag_source", job_pipeline_specs.job_id "job_id"
		FROM pipeline_runs
		JOIN pipeline_task_runs ON (pipeline_task_runs.pipeline_run_id = pipeline_runs.id)
		JOIN pipeline_specs ON (pipeline_specs.id = pipeline_runs.pipeline_spec_id)
		JOIN job_pipeline_specs ON (job_pipeline_specs.pipeline_spec_id = pipeline_specs.id)
		WHERE pipeline_task_runs.id = $1 AND pipeline_runs.state in ('running', 'suspended')
		FOR UPDATE`
		if err = tx.ds.GetContext(ctx, &run, sql, taskID); err != nil {
			return fmt.Errorf("failed to find pipeline run for task ID %s: %w", taskID.String(), err)
		}

		// Update the task with result
		sql = `UPDATE pipeline_task_runs SET output = $2, error = $3, finished_at = $4 WHERE id = $1`
		if _, err = tx.ds.ExecContext(ctx, sql, taskID, result.OutputDB(), result.ErrorDB(), time.Now()); err != nil {
			return fmt.Errorf("failed to update pipeline task run: %w", err)
		}

		if run.State == RunStatusSuspended {
			start = true
			run.State = RunStatusRunning

			sql = `UPDATE pipeline_runs SET state = $2 WHERE id = $1`
			if _, err = tx.ds.ExecContext(ctx, sql, run.ID, run.State); err != nil {
				return fmt.Errorf("failed to update pipeline run state: %w", err)
			}
		}

		return loadAssociations(ctx, tx.ds, []*Run{&run})
	})

	return run, start, err
}
