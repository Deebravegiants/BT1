### Title
Webhook shop-domain identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`), `topic`, and `webhook_id` entirely from unauthenticated HTTP headers, while `Utils::HmacValidator` only verifies the raw request body against the shared secret. The header carrying the identity binding used by the handler (`shop`) is never part of the signed material, so a valid HMAC for one payload can be replayed with an arbitrary `shop` header value and still pass verification.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes and compares the HMAC strictly over that signable string: [2](#0-1) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are read straight from HTTP headers with no cryptographic binding to the body or to each other: [3](#0-2) 

`Registry.process` validates only the HMAC (i.e., only the body) and then dispatches the handler using the unauthenticated `request.shop`, `request.topic`, and `request.webhook_id`: [4](#0-3) 

The identity-binding equality that should hold is:
`bytes_covered_by_HMAC == bytes_the_handler_trusts_for_tenant_identity`

Here that equality is broken: the HMAC covers only the JSON body bytes, while the handler trusts the `shop`/`topic`/`webhook_id` headers, which are outside the signed scope. This is precisely the "field acted on but not covered by the HMAC" pattern flagged as an in-scope analog: the shop domain is the tenant-identity field consumed by the host application (`data.shop` in `WebhookMetadata`, as documented in `docs/usage/webhooks.md`), yet it carries no signature.

### Impact Explanation
An unprivileged internet user who can install the target app on their own (attacker-controlled) development/trial shop can receive a fully valid webhook for that shop — i.e., a legitimate `(raw_body, hmac)` pair signed by Shopify with the app's real `api_secret_key`. Because the HMAC never covers the `shop`, `topic`, or `webhook_id` headers, the attacker can replay that exact `raw_body`/`hmac` pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` (any other real merchant's `*.myshopify.com` domain) and/or `x-shopify-topic`/`x-shopify-webhook-id` values. `HmacValidator.validate` still succeeds (it only checks the body bytes), and `Registry.process` calls the handler with `WebhookMetadata.new(topic: <attacker-chosen>, shop: <attacker-chosen>, body: <attacker's own real data>, webhook_id: <attacker-chosen>, ...)`.

Any host application that uses `data.shop` to select which tenant's records to update (the officially documented usage pattern, e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) will process attacker-supplied data under a victim shop's identity — enabling cross-tenant data injection, spoofed business events (e.g., fake `orders/create`/`app/uninstalled` for a shop that never sent them), and duplicate/webhook_id confusion that can defeat idempotency guards keyed on `webhook_id`. This satisfies the "cross-tenant access" Critical impact bucket without requiring any leaked credential — the attacker only needs their own valid app installation, which is available to any unprivileged internet user.

### Likelihood Explanation
Likelihood is high for any host application built directly on this gem's documented webhook API without adding out-of-band shop verification (e.g., checking `data.shop` against a known/registered shop list before trusting the payload). Producing a valid `(raw_body, hmac)` pair requires no privileged access — merely installing the app on any shop (including a free/dev store) is sufficient, since Shopify itself signs the webhook with the real `api_secret_key` for that legitimate delivery. The header rewrite step (changing `shop-domain`/`topic`/`webhook-id`) is a trivial HTTP replay with modified headers.

### Recommendation
Bind the tenant-identity headers into the signed material, or otherwise cryptographically/authoritatively verify them before dispatch:
- Include `shop`, `topic`, and `webhook_id` in `to_signable_string` if Shopify's signing scheme is changed to support it, or
- Require the host application (and/or the gem itself) to verify that the `shop` header corresponds to a shop with an active, previously stored session/installation for this app before invoking the handler, and reject `shop`/`topic` values that were not part of what was actually registered for that specific installation.
- At minimum, update `ShopifyAPI::Webhooks::Registry.process` and the documentation to explicitly warn that `data.shop`/`data.topic`/`data.webhook_id` are NOT covered by the HMAC and must not be trusted for tenant-selection without an additional authoritative check (e.g., cross-referencing against the app's session store).

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` and enables a webhook topic (e.g. `orders/create`).
2. Shopify sends a legitimate webhook POST to the app's callback URL with headers:
   - `x-shopify-hmac-sha256: <valid HMAC of raw_body, computed with the real api_secret_key>`
   - `x-shopify-shop-domain: attacker-shop.myshopify.com`
   - `x-shopify-topic: orders/create`
   - `x-shopify-webhook-id: <id>`
   and some JSON `raw_body`.
3. Attacker captures this exact `raw_body` and `x-shopify-hmac-sha256` value.
4. Attacker replays the identical `raw_body` and `x-shopify-hmac-sha256` to the same app endpoint, but changes only:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
5. Server-side: `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds a request object; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `raw_body` only — it matches, since `raw_body` was unmodified: [5](#0-4) 
6. `Registry.process` proceeds to call the registered handler with `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: <attacker's data>, ...)`: [4](#0-3) 
7. The host application (following the gem's documented pattern) processes/stores this data under `victim-shop.myshopify.com`'s tenant context, even though `victim-shop.myshopify.com` never sent this webhook and may not even have this topic enabled.

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
