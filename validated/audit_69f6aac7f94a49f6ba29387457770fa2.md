### Title
Webhook shop identity spoofing via `X-Shopify-Shop-Domain` header not covered by HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating an HMAC over the raw request body, then hands the caller a `shop` value that is read from an unauthenticated HTTP header. Because the header is not part of the signed content, any holder of one genuine, HMAC-valid webhook body (obtainable by any unprivileged merchant who installs the app on their own store) can replay that body with a forged `shop-domain` header and produce a request that the gem reports as successfully verified and attributed to an arbitrary victim shop.

### Finding Description
`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and compares it against the `hmac` field of the same object: [1](#0-0) 

For webhooks, `Webhooks::Request#to_signable_string` returns only the raw request body: [2](#0-1) 

while `Webhooks::Request#shop` is taken straight from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, which is never mixed into `to_signable_string`: [3](#0-2) 

`Registry.process` validates the HMAC and then forwards `request.shop` (the unauthenticated header value) straight into `WebhookMetadata`, which is passed to the app's handler as the trusted tenant identifier: [4](#0-3) 

The gem's own documentation tells integrators that `process` "will verify the request did indeed come from Shopify" before invoking the handler, and its own example uses `data.shop` as the shop identity to persist/act on: [5](#0-4) [6](#0-5) 

The identity binding that should hold is:
`shop reported to the handler == shop that produced the HMAC-signed bytes`

In reality the equality only holds for the raw body; `shop` is never part of what is verified. All shops that install the same app share the same webhook signing secret (`Context.api_secret_key`), because the HMAC key is the app's client secret, not a per-shop secret. Consequently:

- Before attack: victim shop's genuine webhook → `hmac` valid for `raw_body` → `request.shop == victim`.
- After attack: attacker's own legitimate webhook (`raw_body`, valid `hmac`, both computed with the same app secret since HMAC key is app-wide) is replayed with `shop-domain` header rewritten to the victim → `hmac` still valid for the (unchanged) `raw_body` → `request.shop == victim` even though the body content came from the attacker's own store.

### Impact Explanation
This breaks the tenant identity boundary the gem is supposed to enforce for webhooks: an unprivileged internet user who has done nothing more than install the app on their own shop (a completely standard, low-privilege interaction available to any merchant) can produce a `Registry.process`-accepted request that Report as originating from any other shop that uses the same app, while fully controlling the body content within that webhook topic's schema (since the body is drawn from data in the attacker's own store, which they can freely edit before triggering the real webhook, e.g. product/customer/order fields). Because the gem exposes this forged `shop` as verified/trusted in `WebhookMetadata`, and its own documented usage pattern is to key persistence/processing off `data.shop`, downstream applications that follow the gem's documented API will apply attacker-controlled data to a different tenant's records — a cross-tenant confusion/injection primitive, not a host-application misuse of an undocumented API.

### Likelihood Explanation
Exploitation only requires: (1) app installation on an attacker-controlled shop (an ordinary unprivileged action), (2) capturing one legitimate webhook request/HMAC pair the attacker's own shop receives from the app's own webhook subscription, and (3) replaying the identical raw body with a modified `shop-domain` header value to the app's webhook endpoint. No access to `api_secret_key`, access tokens, or any victim credential is required.

### Recommendation
Bind the shop identity into what is actually authenticated:
- Include the shop domain (and ideally topic/webhook id) inside the HMAC-signed material for webhooks, or
- After HMAC validation, cross-check `request.shop` against an independent, previously-established record (e.g., confirm this shop actually has an active webhook registration/session with this app) before trusting it, and document that `shop` is not itself covered by the signature so integrators know they must re-verify it.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` and it registers, e.g., the `orders/create` webhook topic.
2. Attacker creates an order on their own store, causing Shopify to POST a webhook to the app with headers including `X-Shopify-Hmac-Sha256: <hmac>` and `X-Shopify-Shop-Domain: attacker.myshopify.com`, where `hmac = HMAC-SHA256(api_secret_key, raw_body)`.
3. Attacker captures `raw_body` and `hmac` from that request.
4. Attacker replays the exact `raw_body` and `hmac` to the app's webhook endpoint, changing only the `X-Shopify-Shop-Domain` header to `victim.myshopify.com`.
5. `Webhooks::Request#to_signable_string` still returns the identical `raw_body`, so `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb` lines 12-22) succeeds.
6. `Registry.process` (`lib/shopify_api/webhooks/registry.rb` lines 188-200) invokes the app handler with `WebhookMetadata.shop == "victim.myshopify.com"` and `body` containing attacker-authored order data, exactly as if Shopify itself had sent this event for the victim shop.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
