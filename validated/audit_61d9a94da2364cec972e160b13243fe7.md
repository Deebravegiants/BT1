### Title
Flash-position leftover refunds are paid to the caller, not to the receiver contract that supplied them - (File: contracts/controller/src/strategies/flash_position.rs)

### Summary
The report's bug class is a *return-path receiver mismatch*: funds coming back through the protocol are sent to an address assumed to be the rightful owner, when in fact they originated from a different party. The same shape exists in `flash_position`. During `process_flash_position`, the controller forwards minted debt to a caller-selected `receiver` contract and invokes `execute_flash_position` on it. Any listed `refund_assets` the receiver pushes to the controller during that callback are measured by balance delta and refunded to `caller` — the account owner who initiated the call — not to `receiver`, the address that actually sent the tokens. [1](#0-0) [2](#0-1) 

### Finding Description
`process_flash_position` takes a `caller` and a `receiver` contract address. It mints fee-free debt via `borrow_into_controller` into the controller, forwards the measured amount to `receiver`, snapshots the controller's balances of each `refund_assets` token, then invokes `execute_flash_position(initiator=caller, account_id, asset, amount, 0, amount_received, controller, data)` on `receiver` inside the flash guard. [3](#0-2) [4](#0-3) 

After the callback, `refund_listed_assets(env, caller, refund_assets, &refund_before)` refunds every positive controller balance delta on the listed assets to `caller` via `refund_controller_balance_delta`, which transfers `excess` from the controller to `refund_to`. [5](#0-4) [6](#0-5) 

The code implicitly assumes the tokens arriving at the controller during the callback belong to `caller`. But they are transferred by `receiver`, a distinct contract address. `receiver` need only be a wasm contract distinct from the controller and pool (`require_wasm_receiver` plus the two inequality checks); nothing ties it to `caller` or to the account. [7](#0-6) 

An attacker can therefore initiate `flash_position` on their own account with `receiver` set to a shared/third-party adapter contract whose `execute_flash_position` implementation transfers assets to the controller as part of its normal flow — for example a generic receiver that returns leftover intermediate tokens to the invoking controller expecting them to be returned to itself. The attacker lists those tokens in `refund_assets` (any listed active asset in the hub that is not a collateral asset is accepted [8](#0-7) ), and the receiver's returned tokens are transferred to the attacker instead of remaining with or returning to `receiver`.

### Impact Explanation
Theft of funds. Tokens held by the receiver contract — which may custody or route funds belonging to other users — are redirected to an arbitrary initiator. The attacker only needs an account, a listed debt asset with `is_flashloanable`, a positive collateral receipt to satisfy `CollateralMinimumNotMet`/`FlashPositionClosed`, and a victim receiver contract that emits the tokens during its callback. The loss is borne by the receiver contract (and transitively its users), not by the pool or controller.

### Likelihood Explanation
Medium. Exploitation requires a deployed receiver contract whose `execute_flash_position` handler pushes non-collateral assets to the controller while treating those assets as its own change. Shared adapter/router-style receivers that return unused swap output or change to the invoking controller fit this pattern — precisely the wallet/multisig identity-mismatch scenario in the source report, where the sender's identity (`receiver`) differs from the credited party (`caller`). The attacker controls every argument: `receiver`, `data`, `collaterals`, and `refund_assets`, and `refund_assets` validation only requires listed, unique, non-collateral assets.

### Recommendation
Add an explicit refund destination rather than assuming `caller` is the owner of returned funds. Either pass `receiver` (or a separate `refund_to: Address` argument) to `refund_listed_assets` so leftover tokens go back to the contract that sent them, or include a receiver-declared refund address in the `execute_flash_position` callback result/`data`. At minimum, document and enforce that `refund_assets` deltas belong to the caller's own position flow rather than sweeping third-party receiver balances.

### Proof of Concept
1. Victim deploys a receiver contract `V` implementing `execute_flash_position` that, as part of its strategy, swaps and transfers leftover intermediate token `X` to the controller (a standard "return change to caller" pattern).
2. Attacker calls `controller.flash_position` with `account_id = 0`, a flashloanable `debt` hub asset, `receiver = V`, crafted `data`, a `collaterals` entry whose minimum `V` satisfies, and `refund_assets = [X]`.
3. `mint_and_forward` forwards the debt to `V`; `refund_before` snapshots the controller's `X` balance; `invoke_receiver` runs `V.execute_flash_position`, during which `V` transfers `X` to the controller and returns enough collateral token to satisfy the minimum.
4. `collect_collateral_deposits` deposits the collateral to the attacker's new account; `refund_listed_assets` then transfers the full `X` delta to `caller` (the attacker) via `refund_controller_balance_delta`.
5. `V`'s `X` is stolen; the attacker keeps both the leveraged position and the refunded tokens. [9](#0-8)

fn validate_refund_assets(
    env: &Env,
    cache: &mut Context,
    spoke_id: u32,
    hub_id: u32,
    collaterals: &Vec<(HubAssetKey, i128)>,
    refund_assets: &Vec<Address>,
) {
    let limits = storage::get_position_limits(env);
    assert_with_error!(
        env,
        refund_assets.len() <= limits.max_supply_positions,
        GenericError::InvalidPayments
    );

    let mut seen: Map<Address, bool> = Map::new(env);
    for asset in refund_assets.iter() {
        assert_with_error!(
            env,
            !seen.contains_key(asset.clone()),
            GenericError::InvalidPayments
        );
        seen.set(asset.clone(), true);
        // Refund transfers run after the guard; restrict tokens to listed assets.
        cache.require_listed_active_config(
            spoke_id,
            &HubAssetKey {
                hub_id,
                asset: asset.clone(),
            },
        );
        for (collateral, _) in collaterals.iter() {
            assert_with_error!(
                env,
                asset != collateral.asset,
                GenericError::InvalidPayments
            );
        }
    }
}

fn refund_listed_assets(
    env: &Env,
    caller: &Address,
    refund_assets: &Vec<Address>,
    before: &Map<Address, i128>,
) {
    for asset in refund_assets.iter() {
        let baseline = before
            .get(asset.clone())
            .unwrap_or_else(|| panic_with_error!(env, GenericError::InternalError));
        refund_controller_balance_delta(env, &asset, baseline, caller);
    }
}

pub(crate) fn refund_controller_balance_delta(
    env: &Env,
    asset: &Address,
    balance_before: i128,
    refund_to: &Address,
) {
    let controller = env.current_contract_address();
    let excess = balance_delta_since(env, asset, &controller, balance_before);
    if excess > 0 {
        token::Client::new(env, asset).transfer(&controller, refund_to, &excess);
