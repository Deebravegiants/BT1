### Title
Webhook shop identity spoofing via HMAC coverage gap enables cross-tenant webhook processing - ([File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, while the `shop` (and `topic`/`api_version`/`webhook_id`) values used to route and label the payload are read directly from unauthenticated HTTP headers that are never included in the signed content. This breaks the intended binding `hmac_signed_bytes == bytes_the_handler_trusts_for_tenant_identity`, allowing a payload's shop attribution to be forged independently of a valid HMAC.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is parsed from the `shopify-shop-domain`/`x-shopify-shop-domain` header, completely outside of what is HMAC-signed: [2](#0-1) 

`Registry.process` validates only `Utils::HmacValidator.validate(request)`, which computes the HMAC over `to_signable_string` (the raw body) and compares it to the `hmac` header — it performs no check binding the `shop` header to that signature — before handing the (header-derived) shop straight to the app's webhook handler: [3](#0-2) 

`Utils::HmacValidator.validate` confirms this: it only compares `verifiable_query.to_signable_string` against the secret-derived signature, never touching headers: [4](#0-3) 

The `shop` value is then placed, unauthenticated, into the `WebhookMetadata` struct that host applications use as the trusted tenant identifier for the event: [5](#0-4) [6](#0-5) 

Because a single app-level `api_secret_key` is shared across every shop that installs the app (it is not per-tenant), any webhook body legitimately signed for tenant A's shop remains HMAC-valid when replayed to the app's webhook endpoint with the `shop-domain` header changed to point at tenant B. The gem's own `process` API has no mechanism to detect this: the equality it should enforce — `shop claimed in WebhookMetadata == shop cryptographically bound by the HMAC` — is never checked, since the HMAC covers zero bytes of the shop field.

### Impact Explanation
This is a cross-tenant identity confusion: an attacker who legitimately operates their own installed shop (tenant A) can capture a genuinely-signed webhook delivered to their own endpoint (no TLS interception or secret needed — it is delivered to them) and resend it to the app's public webhook endpoint with the `shop-domain` header rewritten to a victim shop (tenant B). The HMAC validation in `Registry.process` still succeeds because the signature never covered the shop header, so the host application's handler executes business logic (e.g., data sync, order/customer processing, GDPR redaction flows) believing the event originates from tenant B, when the body content actually belongs to tenant A. This matches the "cross-tenant access" critical-impact category: data intended for/about one tenant can be attributed to and processed against a different tenant purely by header manipulation, without possessing `api_secret_key`, any access token, or privileged access.

### Likelihood Explanation
Medium-to-High: exploitation requires only (1) installing the app on any shop to receive a legitimately HMAC-signed webhook addressed to that shop, and (2) replaying the identical body/HMAC pair to the app's public webhook endpoint with a modified `shop-domain` header — both trivially achievable by any unprivileged internet user who can install the target app on a free/dev shop. No secret material, token, or elevated privilege is required; the only barrier is whether the host application performs its own independent shop-authorization check on top of the gem's `WebhookMetadata.shop`, which the gem's documented API does not require nor provide.

### Recommendation
Bind `shop` (and ideally `topic`, `api_version`, `webhook_id`) into the value verified by `HmacValidator`, or otherwise cryptographically authenticate the header set — not just the body — before constructing `WebhookMetadata`. At minimum, `Webhooks::Request#to_signable_string` should incorporate the shop-domain header (e.g., HMAC over `shop + raw_body`, or validate that the signed body's shop matches an out-of-band verified value), and `Registry.process` should reject requests where header-derived tenant identity cannot be shown to correspond to the same signed payload that was issued by Shopify for that specific shop.

### Proof of Concept
1. App installs successfully on `attacker-shop.myshopify.com`; app's `api_secret_key` is the same for all installed shops.
2. Shopify delivers a legitimate webhook to the app's endpoint for `attacker-shop.myshopify.com`:
   - Headers: `x-shopify-topic: orders/create`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC over raw_body>`
   - Body: `raw_body` (arbitrary JSON the attacker fully controls, since they own this shop and can trigger the event, e.g., by creating an order with attacker-chosen field values).
3. Attacker captures this valid `(raw_body, hmac)` pair from their own endpoint (no interception needed — it was sent to them).
4. Attacker sends a new POST to the app's webhook endpoint with the same `raw_body` and `hmac` header, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `Webhooks::Registry.process` (lib/shopify_api/webhooks/registry.rb:189-200) calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `raw_body` against the shared secret — the shop header was never part of the signed content.
6. `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: request.parsed_body, ...)` is passed to the app's `handler.handle`, which processes attacker-controlled data as if it were an authentic event from `victim-shop.myshopify.com`.
