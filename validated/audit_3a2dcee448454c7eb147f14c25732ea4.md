### Title
Webhook `shop-domain` and `topic` headers are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable payload from the raw body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values that the registry uses to route and attribute the webhook are taken from unauthenticated HTTP headers. Any actor who can obtain one valid `(body, hmac)` pair for the app's secret (e.g., by installing the app on their own store and triggering a webhook they control the content of) can replay that exact body/HMAC pair to the app's webhook endpoint while swapping the `shop-domain` and/or `topic` headers, and the signature check still passes.

### Finding Description
`Request#to_signable_string` returns only the raw request body: [1](#0-0) 

`Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are read straight from headers that are not part of the signed payload: [2](#0-1) 

`HmacValidator.validate` only verifies `verifiable_query.to_signable_string` (i.e., the raw body) against the HMAC, never the headers: [3](#0-2) 

`Registry.process` trusts the unauthenticated header-derived `request.shop` and `request.topic` to route the webhook to a handler and to populate `WebhookMetadata`, which host applications use to attribute the payload to a specific merchant/tenant: [4](#0-3) 

The identity binding that should hold is: `shop header == shop the HMAC-signed body actually originated from`. Because the HMAC only covers `@raw_body`, this equality is not enforced — the `shop-domain` header (and `topic`/`webhook_id`/`api_version`) can be swapped freely by anyone able to produce a valid body/HMAC pair, without invalidating the signature.

### Impact Explanation
Any unprivileged actor who installs the app on their own store can generate arbitrary JSON bodies of their choosing (e.g., product/order payloads with attacker-controlled content) and obtain a valid Shopify-computed HMAC for that body, since Shopify signs the webhook body with the app's shared secret for every subscribed shop. That attacker can then POST the same body + HMAC directly to the app's public webhook endpoint while substituting the `shopify-shop-domain` header with a victim shop's domain (or any other tenant they wish to target) and/or a different `shopify-topic`. `Registry.process` will accept the signature as valid (since only the body is checked) and hand the attacker-chosen data to the handler tagged with the victim's shop, causing the host application to write or act on attacker-controlled data under the victim tenant's identity — a cross-tenant data injection.

### Likelihood Explanation
Likelihood is non-trivial: it only requires the attacker to have (or create) a store that installs the target app and can trigger at least one webhook whose body content they control (many topics carry attacker-influenced content, e.g., a product or order created in their own store). No access to `api_secret_key`, no TLS interception, and no privileged account is required — only normal use of the app as an installing merchant plus direct HTTP access to the app's public webhook endpoint.

### Recommendation
Bind the `shop-domain`, `topic`, `webhook-id`, and `api-version` headers into the signed payload verification (e.g., include them in the HMAC computation, or independently validate that the `shop` claim matches a shop the caller is authorized to represent), so that the identity used for routing/attribution cannot be altered without invalidating the signature.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a webhook for a topic whose body they control (e.g., `products/create`), capturing the raw JSON body `B` and the `x-shopify-hmac-sha256` header `H` that Shopify computed with the app's shared secret.
2. Attacker sends a POST to the app's webhook endpoint with:
   - body: `B` (unchanged)
   - header `x-shopify-hmac-sha256: H` (unchanged)
   - header `x-shopify-shop-domain: victim-shop.myshopify.com` (forged)
   - header `x-shopify-topic:` unchanged or altered to any registered topic
3. `Utils::HmacValidator.validate` recomputes the HMAC over `B` only, which matches `H`, so validation succeeds (`lib/shopify_api/utils/hmac_validator.rb:26-31`).
4. `Registry.process` dispatches to the handler with `shop: "victim-shop.myshopify.com"` and the attacker-controlled body (`lib/shopify_api/webhooks/registry.rb:188-200`), even though the payload never originated from that shop.
