This confirms the vulnerability. Comparing the two `VerifiableQuery` implementations shows the design intent: for OAuth, `AuthQuery#to_signable_string` explicitly folds `shop` (and `code`, `host`, `state`, `timestamp`) into the signed string, binding the shop identity to the HMAC. For webhooks, `Webhooks::Request#to_signable_string` returns only `@raw_body`, while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from HTTP headers via `shopify_header` and never enter the signed material.

### Title
Webhook `shop`/`topic`/`webhook_id` identity fields are trusted from unsigned headers while only the raw body is HMAC-verified - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating only the raw request body against the HMAC signature, but then hands off caller-controlled, unsigned header values (`shop`, `topic`, `webhook_id`, `api_version`) as trusted identity/routing data to the host application's handler.

### Finding Description
`Webhooks::Registry.process` validates a webhook with `Utils::HmacValidator.validate(request)` [1](#0-0) , and `HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` [2](#0-1) . For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` [3](#0-2) . Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from HTTP headers via the private `shopify_header` helper, completely outside the signed material [4](#0-3) . After validation succeeds, `process` looks up the handler by `request.topic` and forwards `request.shop` unchanged into `WebhookMetadata`, which is delivered to the host application's handler as the authoritative tenant/topic identity [5](#0-4) .

This differs from how the gem treats the equivalent OAuth binding: `Auth::Oauth::AuthQuery#to_signable_string` explicitly includes `shop` (along with `code`, `host`, `state`, `timestamp`) in the string that gets HMAC-verified, so the shop identity is cryptographically bound to the signature there [6](#0-5) . No such binding exists for webhooks: the equality that should hold — "the shop the HMAC was computed for" == "the shop the handler acts on" — is never enforced, because the HMAC computation never includes the shop at all.

Concretely: HMAC bytes verified = `HMAC(secret, raw_body)`. Identity bytes acted on = `headers["x-shopify-shop-domain"]`, `headers["x-shopify-topic"]`, `headers["x-shopify-webhook-id"]`. These are disjoint, so any request with a validly-signed body (i.e., a body previously signed by Shopify for the app, such as a webhook the attacker's own store received) remains valid after the header values are swapped to a different shop/topic, since `OpenSSL.secure_compare` only re-checks the body-derived signature [2](#0-1) .

### Impact Explanation
An attacker who is a merchant/integrator on their own shop (i.e., legitimately receives webhooks from Shopify for their own store, which is achievable without any special privilege beyond installing/using the app) can capture one valid `(raw_body, hmac)` pair and resubmit it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`, `X-Shopify-Webhook-Id`) header rewritten to a victim shop. `Registry.process` will treat the HMAC as valid (since it only checks the body) and will pass the forged `shop` value straight to the host application's handler as trustworthy tenant context, and it may also dispatch it to a different handler by rewriting `topic`. If the host application relies on `WebhookMetadata#shop` to identify which tenant a webhook update belongs to (a documented and expected usage pattern of this gem), this results in cross-tenant data confusion/access — e.g., updating, deleting or acting on victim-shop state using attacker-supplied body content, or triggering mandatory GDPR-style handlers (`shop/redact`, `customers/redact`, `customers/data_request`) for the wrong shop.

### Likelihood Explanation
Moderate-to-high: no possession of `api_secret_key` or the victim's credentials is required — the attacker only needs one legitimate signed webhook body from their own shop (trivial to obtain by installing the app themselves) and the ability to send arbitrary HTTP headers to the app's public webhook endpoint. No cryptographic break is needed since the shop/topic identity was never covered by the signature to begin with.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signed material used for verification, or otherwise cryptographically bind them to the HMAC-covered body (e.g., require the host app to independently verify that `request.shop` corresponds to a shop with an active, previously-established session/installation before trusting it), so that the identity fields consumed by `Registry.process`/`WebhookMetadata` cannot be forged independently of the HMAC.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and triggers a webhook (e.g. `orders/create`), capturing the raw POST body `B` and the valid `X-Shopify-Hmac-Sha256` header `H = HMAC-SHA256(secret, B)`.
2. Attacker resends `B` with headers: `X-Shopify-Hmac-Sha256: H` (unchanged), `X-Shopify-Shop-Domain: victim.myshopify.com`, `X-Shopify-Topic: orders/create`, `X-Shopify-Webhook-Id: <any>`.
3. `Webhooks::Request.new(raw_body: B, headers: forged_headers)` parses these headers into `shop`/`topic`/`webhook_id` [4](#0-3) .
4. `Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` and compares it to `H` — this still matches because `to_signable_string` never included the shop/topic [3](#0-2) .
5. Validation passes; `handler.handle(data: WebhookMetadata.new(topic: "orders/create", shop: "victim.myshopify.com", body: JSON.parse(B), ...))` is invoked with `shop` = victim, `body` = attacker's own order data [7](#0-6) , causing the host application to act on victim-shop's tenant context with attacker-supplied content.
