### Title
Webhook `shop` (and `topic`/`webhook_id`) header values are not covered by the HMAC signature, allowing tenant-confusion via replayed/relabeled webhook payloads - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so `Utils::HmacValidator.validate` authenticates the JSON body bytes but never authenticates the `shop`, `topic`, or `webhook_id` values that are read from the `x-shopify-*`/`shopify-*` headers. `Registry.process` still hands these unauthenticated header values straight to the app's registered handler as trusted metadata.

### Finding Description
`Request#to_signable_string` is defined as:
```ruby
sig { override.returns(String) }
def to_signable_string
  @raw_body
end
``` [4](#0-3) 

`HmacValidator.validate` computes `OpenSSL::HMAC.hexdigest(sha256, secret, verifiable_query.to_signable_string)` and compares it to the `hmac` extracted from headers [5](#0-4) . Because `to_signable_string` is just the raw body, the signature proves only that Shopify produced this exact body — it says nothing about which shop, topic, or webhook id the request claims to be. Those fields come from `shopify_header("shop-domain")`, `shopify_header("topic")`, and `shopify_header("webhook-id")` [6](#0-5) , which are simply read out of the HTTP headers with no cryptographic binding to the body/signature.

`Registry.process` then verifies only the HMAC, and directly forwards `request.shop`, `request.topic`, and `request.webhook_id` into `WebhookMetadata`, without any independent check that the shop matches an app-known/installed shop:
```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
``` [2](#0-1) 

This breaks the identity binding **`shop` authenticated by the HMAC == `shop` delivered to the handler**: the HMAC only authenticates the body bytes, not the header-derived `shop` (or `topic`/`webhook_id`) that the handler treats as the tenant identity for that body.

Any unprivileged internet user who can obtain one legitimately-signed `(body, hmac)` pair for the configured topic (e.g. by installing/uninstalling the target app on their own free development store, or via Shopify's "Send test notification" feature in the Partner Dashboard, both of which are freely available to any developer and require no special privilege) can replay that exact body+hmac to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` header (and/or `x-shopify-topic`, `x-shopify-webhook-id`) with a different value. `HmacValidator.validate` still returns `true` because it only re-hashes `@raw_body`, and `Registry.process` will happily dispatch the handler with the attacker-chosen `shop` value alongside the legitimately-signed body content.

### Impact Explanation
Since apps built on this gem are documented to use `data.shop` as the tenant identifier when processing webhook events (looking up per-shop sessions/access tokens, writing shop-scoped records, gating mandatory GDPR webhooks like `shop/redact`/`customers/redact`/`customers/data_request`), an attacker can inject signed-looking webhook payloads under an arbitrary victim shop domain. This enables cross-tenant data confusion — e.g., forging a `shop/redact` or `app/uninstalled` event, or any subscribed topic's body content, and attributing it to a victim shop the attacker does not control — which matches the Critical "cross-tenant access" impact category, since the gem is the component responsible for verifying webhook authenticity end-to-end and it fails to bind the identity field it hands to the app.

### Likelihood Explanation
Exploitation only requires the ability to (a) obtain one valid `(body, hmac)` pair for the app (trivially available to any developer via a free trial/dev-store install or Partner Dashboard test webhook) and (b) send an HTTP POST to the app's public webhook endpoint with a modified `shop-domain` header — no access token, `client_secret`, or privileged account is needed.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the HMAC-covered signable content, or independently verify `request.shop` against the set of shops for which the app has an active/expected installation before dispatching to handlers. At minimum, document loudly (and enforce in code) that `WebhookMetadata#shop` must not be trusted as an authenticated identity unless cross-checked against known installed shops, since Shopify's HMAC only covers the raw body.

### Proof of Concept
1. Attacker installs (or trial-installs) the target app on their own store `attacker.myshopify.com`, or uses "Send test notification" in the Partner Dashboard for a subscribed topic (e.g. `orders/create`) to capture a legitimately Shopify-signed request:
   - `raw_body = '{"id":123,...}'`
   - `x-shopify-hmac-sha256: <valid HMAC over raw_body>`
   - `x-shopify-shop-domain: attacker.myshopify.com`
2. Attacker resends the exact same `raw_body` and `x-shopify-hmac-sha256` to the victim app's public webhook endpoint, but changes:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
3. `Utils::HmacValidator.validate(request)` returns `true` because it only hashes `raw_body`, which is unchanged.
4. `Registry.process` invokes the registered handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: <attacker-controlled JSON>, ...)`, and any host application that trusts `data.shop` for tenant scoping now processes attacker-supplied data as if it originated from `victim-shop.myshopify.com`.
