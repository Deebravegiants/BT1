Audit Report

## Title
Integer underflow/wraparound in gateway staleness check allows bypass of message freshness validation - (File: core/services/gateway/handlers/capabilities/handler.go)

## Summary
`HandleLegacyUserMessage` performs its staleness check using unsigned arithmetic: `uint(time.Now().Unix())-h.config.MaxAllowedMessageAgeSec > uint(payload.Timestamp)`, where `payload.Timestamp` is an attacker-controlled `int64` field. Only `payload.Timestamp == 0` is rejected beforehand, so a negative timestamp wraps around when cast to `uint`, becoming a huge value that always satisfies the comparison and defeats the intended freshness/anti-replay check.

## Finding Description
`payload.Timestamp` is a signed `int64` field [1](#0-0)  fully controlled by the request body. The handler only rejects `payload.Timestamp == 0` before the staleness check [2](#0-1) , then performs the freshness check with unsigned casts: `uint(time.Now().Unix())-h.config.MaxAllowedMessageAgeSec > uint(payload.Timestamp)` [3](#0-2) . A negative `int64` cast to `uint` wraps to a value near `math.MaxUint64`, making this comparison always false, so the "stale message" branch is skipped regardless of actual freshness.

I reviewed the existing validation on this path. `gateway.ProcessRequest` calls `msg.Validate()` for legacy requests before dispatching to `HandleLegacyUserMessage` [4](#0-3) . `Message.Validate()` checks structural constraints (ID/method/DonID lengths, signature length) and calls `ExtractSigner()`, which recovers the signer address from the ECDSA signature [5](#0-4) . Critically, this only verifies the signature is well-formed and can be used to derive *some* address — it does not check that address against any allowlist, so any unprivileged caller can generate their own keypair, sign the payload themselves, and produce a "validly signed" but fully attacker-controlled message. The handler code itself documents this gap with `// TODO: apply allowlist and rate-limiting here` [6](#0-5) . Thus no meaningful authentication/authorization barrier prevents an arbitrary caller from reaching and exploiting the staleness-check bug.

After the (bypassable) check, the message is forwarded unmodified to every DON member [7](#0-6) .

## Impact Explanation
This is a genuine logic bug: an unprivileged/unauthenticated (in the allowlist sense) caller who can sign their own message can supply `Timestamp: -1` and bypass the freshness/anti-replay gate entirely, causing the gateway to forward the message to all DON nodes regardless of the timestamp's validity. This matches the "gateway request impersonation / allowlist bypass" category of in-scope impact, since the freshness check is a documented security control on the message ("needs to be within certain freshness to be processed" [8](#0-7) ) and it is fully defeated by unsigned-arithmetic wraparound.

## Likelihood Explanation
High: the code path is reachable by any client that can reach the gateway's HTTP user port and produce a signed legacy `web_api_trigger` message (self-signed, since there is no allowlist gate on the legacy path prior to this check). Setting `Timestamp` to any negative number reliably bypasses the check on every invocation — no race conditions or unusual timing required.

## Recommendation
Explicitly reject negative `payload.Timestamp` values (in addition to the `== 0` check), and perform the staleness comparison using signed 64-bit arithmetic (`int64`) instead of casting to `uint`, to eliminate wraparound for out-of-range or negative attacker-supplied values.

## Proof of Concept
1. Construct a legacy `api.Message` with `Body.Method = "web_api_trigger"`, a valid `DonID`, and a `TriggerRequestPayload` payload with `Timestamp: -1`.
2. Sign the message with any ECDSA keypair (`Message.Sign`), which is sufficient to pass `Message.Validate()` since there is no allowlist check gating the legacy path.
3. Submit via the gateway's JSON-RPC HTTP endpoint (`gateway.ProcessRequest`); `msg.Validate()` succeeds, and dispatch proceeds to `HandleLegacyUserMessage`.
4. In `HandleLegacyUserMessage`, `payload.Timestamp == 0` is false (it's `-1`), so execution reaches the staleness check; `uint(-1)` wraps to `math.MaxUint64`, making `uint(now)-maxAge > uint(-1)` false, so the "stale message" branch is skipped.
5. The message is forwarded to all DON members via `don.SendToNode` despite the clearly invalid/out-of-range timestamp, demonstrating the bypass of the freshness control.

A Go unit test on `handler_test.go` calling `HandleLegacyUserMessage` with a crafted payload containing `Timestamp: -1` and asserting that no "stale message" error is returned (and that `SendToNode` is invoked) would concretely prove this.

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageID) == 0 || len(m.Body.MessageID) > MessageIDMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageID, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonID) == 0 || len(m.Body.DonID) > MessageDonIDMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonID, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil
}
