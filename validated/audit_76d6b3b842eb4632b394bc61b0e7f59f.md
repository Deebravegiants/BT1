### Title
Webhook `shop` and `topic` identity fields are not covered by the HMAC signature, enabling cross-tenant webhook confusion - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by verifying that `Utils::HmacValidator.validate(request)` succeeds, and that validation only covers the raw HTTP body. The `shop` domain and `topic` values that the handler uses to identify *which tenant* and *which event* the payload belongs to are read straight from HTTP headers and are never part of the signed bytes. This breaks the identity binding: `hmac_verified(body) == true` is treated as if it implies `shop_header == originating_shop`, but the two are independent.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`: [1](#0-0) 

`to_signable_string` returns only `@raw_body`, while `shop`, `topic`, `webhook_id`, and `api_version` are all pulled from `shopify_header(...)`, i.e. plain HTTP headers, entirely outside the signed string.

`Utils::HmacValidator.validate` computes the HMAC only over `verifiable_query.to_signable_string` and compares it to the `hmac` field: [2](#0-1) 

`Registry.process` gates entirely on that single check, then immediately trusts `request.topic` and `request.shop` to route and hand off to the tenant/topic-specific handler: [3](#0-2) 

and those unauthenticated values become the identity fields the host application relies on when it acts on the payload: [4](#0-3) 

The binding that should hold is `hmac_valid(body) ⇒ (shop_header, topic_header)` were also authenticated as originating from Shopify for *this* body. In fact the equality that actually holds is only `hmac_valid(body)`; `shop` and `topic` are unauthenticated metadata that can be swapped freely while keeping the same valid signature, since the signature is a pure function of `raw_body` and the app's single, app-wide `api_secret_key` (shared across every installed shop of the app).

### Impact Explanation
Because `api_secret_key` is one shared secret for the whole app (not per-shop), any request whose body was legitimately signed once (e.g. a webhook the attacker's own store received, or one an attacker can otherwise obtain with a valid signature for some body) remains validly signed no matter what `x-shopify-shop-domain` or `x-shopify-topic` header value is attached to it, because those headers are never hashed. An attacker able to submit HTTP requests to the app's public webhook endpoint can therefore take one genuinely-signed `(raw_body, hmac)` pair and resubmit it with an arbitrary `shop` header and/or `topic` header. `Registry.process` will pass HMAC validation and dispatch the (attacker-chosen) payload to the handler tagged with an attacker-chosen `shop`/`topic`, i.e. cross-tenant confusion: the host application's per-shop business logic (e.g. updating order/inventory/customer state keyed by `data.shop`) executes as though the payload came from a different merchant, without ever needing that merchant's credentials. This matches the Critical "cross-tenant access" impact bucket, since the tenant identity the app relies on is forgeable while the message still reports as cryptographically verified.

### Likelihood Explanation
Exploitation requires only network access to the app's public webhook URL plus possession of at least one validly-signed `(body, hmac)` pair, which is trivial to obtain by installing the (typically publicly listed) app on an attacker-controlled test store and capturing its own genuine webhook. No access token, refresh token, or `client_secret` needs to be stolen — the attacker only replays already-observed ciphertext-equivalent bytes with modified headers. This is a moderate/likely-exploitable class of bug wherever the host app trusts `WebhookMetadata#shop`/`#topic` as authenticated, which the documentation explicitly encourages developers to do.

### Recommendation
Include `shop`, `topic`, and any other field used for authorization/routing decisions inside the HMAC-signed payload (i.e., make `to_signable_string` a canonical concatenation of body + shop + topic + webhook_id, or independently verify the `shop` domain against a known/allow-listed set of installed shops before dispatch). At minimum, `Registry.process` should not treat a successful `HmacValidator.validate(request)` as proof that the header-derived `shop`/`topic` are authentic; it should cross-check the shop domain against session storage for that specific webhook id/format, or Shopify's documented approach of validating the domain format and that it corresponds to a shop the app has state for, before invoking the handler.

### Proof of Concept
```ruby
# 1. Attacker installs the target app on their own store "attacker.myshopify.com"
#    and receives a legitimate webhook, e.g. `orders/create`, capturing:
raw_body = '{"id":1,"note":"legit payload from attacker store"}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), app_secret, raw_body)
# (app_secret is the single shared api_secret_key; attacker never needs to know it,
#  they simply reuse the (raw_body, hmac) pair Shopify already sent them)

# 2. Attacker POSTs the exact same raw_body + hmac to the app's public
#    webhook endpoint, but swaps the shop/topic headers to target a victim shop:
forged_headers = {
  "x-shopify-topic"       => "customers/data_request", # or any registered topic
  "x-shopify-hmac-sha256" => Base64.encode64(hmac),     # unchanged, still valid
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged
  "x-shopify-webhook-id"  => "attacker-controlled-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

# 3. Registry.process only checks the HMAC over raw_body, which still matches,
#    then dispatches the attacker's payload as if it came from victim-shop:
ShopifyAPI::Webhooks::Registry.process(request)
# => handler.handle(data: WebhookMetadata.new(topic: "customers/data_request",
#                                              shop: "victim-shop.myshopify.com",
#                                              body: JSON.parse(raw_body), ...))
```
`Utils::HmacValidator.validate(request)` returns `true` in step 3 because it only recomputes the HMAC over `raw_body`, which is untouched; `shop` and `topic` are forged and never checked. [5](#0-4) [6](#0-5)
