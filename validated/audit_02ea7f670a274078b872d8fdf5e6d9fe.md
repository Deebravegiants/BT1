### Title
Webhook `shop` (and `topic`/`webhook-id`/`api-version`) headers are trusted for routing/processing without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw request body [1](#0-0) , while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from HTTP headers that are never part of the signed data [2](#0-1) . `Registry.process` validates only the HMAC over the body and then hands `request.shop` straight to the handler as an authoritative tenant identifier [3](#0-2) . This is the exact bug class described in the report: a field ("shop") that is *acted on* (used to attribute/route webhook data to a tenant) is not covered by the authenticating signature ("HMAC").

### Finding Description
`Utils::HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it against the `hmac` value [4](#0-3) . For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` [1](#0-0) ; the `hmac` itself is decoded from the `hmac-sha256` header [5](#0-4) . Crucially, the `shop-domain` header is read directly and returned unauthenticated by `#shop` [6](#0-5) .

`Registry.process` performs no additional binding: it validates the HMAC (which only covers the body), looks up a handler by `request.topic`, and constructs `WebhookMetadata` using the *unauthenticated* `request.shop` value, which is then delivered to the app's handler as the source-of-truth tenant identity [3](#0-2) .

The identity binding that should hold is: `shop bound by HMAC == shop trusted by handler`. In this gem it is instead `shop bound by HMAC == "" (nothing)` while `shop trusted by handler == header value`, i.e. the binding is broken.

Because the app's `client_secret` (and thus the HMAC secret) is shared across every shop that installs the app, any merchant who has installed the app can obtain a genuinely Shopify-signed `(raw_body, hmac)` pair for their own shop (by, e.g., triggering a webhook on their own store — orders, products, etc. — whose body content they substantially control via their own store data). That attacker-controlled but validly-signed body/HMAC pair can then be replayed to the app's webhook endpoint with the `shop-domain` (and `topic`/`webhook-id`) headers swapped to a victim shop. `HmacValidator.validate` will still return `true` because it never inspects those headers, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload belongs to the victim shop.

### Impact Explanation
This breaks the tenant isolation the gem is supposed to provide to consuming apps: a webhook payload that is only genuinely valid for shop A can be replayed with a forged `shop-domain` header to make the app believe it originated from shop B. Since apps commonly use `WebhookMetadata#shop` to select which merchant's session/data store to update, this enables cross-tenant data injection/corruption (e.g., poisoning shop B's order/inventory records with attacker-supplied content from shop A) without ever needing shop B's credentials. This matches the Critical impact category "cross-tenant access."

### Likelihood Explanation
Exploitation requires only that the attacker be a legitimate (unprivileged relative to other tenants) installer of the target app — a normal, internet-reachable condition for any multi-tenant Shopify app — plus the ability to send an HTTP request to the app's public webhook endpoint with attacker-chosen headers, which `ShopifyAPI::Webhooks::Request.new` accepts as long as the three required headers are present [7](#0-6) . No access token, `api_secret_key`, or privileged account for the *victim* is needed; the attacker leverages a signature that Shopify legitimately produced for the attacker's own shop.

### Recommendation
Bind the tenant-identifying fields into the signed material (or otherwise verify them) instead of trusting raw headers:
- Include `shop`, `topic`, and `webhook_id`/`api_version` in `to_signable_string` for `Webhooks::Request`, matching Shopify's documented webhook verification guidance of also validating headers server-side, or
- Have `Registry.process` cross-check `request.shop` against the shop associated with the currently loaded session/handler context before dispatching, and reject if there is no independent confirmation that the signed body actually originated from that shop.
- At minimum, document prominently that `WebhookMetadata#shop` is not covered by the HMAC and must not be trusted as an unauthenticated tenant identifier without additional verification by the host application.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store (`attacker-shop.myshopify.com`), which shares the app's single `client_secret` with all other installs.
2. Attacker triggers a legitimate webhook delivery from Shopify for `attacker-shop.myshopify.com` (e.g., updates a product) and captures the raw POST body plus the genuine `X-Shopify-Hmac-Sha256` header — this HMAC is valid per `HmacValidator.validate_signature` because it is computed only over `@raw_body` [8](#0-7) .
3. Attacker replays this exact body and HMAC header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` accepts the request (required headers present) [9](#0-8) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because only the body is checked [10](#0-9) .
5. The handler receives `WebhookMetadata.new(... shop: "victim-shop.myshopify.com", body: <attacker-controlled body> ...)` [11](#0-10)  and the host app processes attacker-controlled data under the victim's tenant identity.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
