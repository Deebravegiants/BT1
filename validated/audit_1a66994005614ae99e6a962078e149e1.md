### Title
Stale `FeeMetadata.fee` amounts are denominated in the old `feeToken` but refunded/rewarded in the new `feeToken` after `updateHostParams` — cross-token value squatting on the escrowed fee pool - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost` lets governance change the protocol's `feeToken` via `updateHostParams`/`updateHostParamsInternal`. The only safety check is that the *host's balance* of the old fee token must be zero at the moment of the swap. However, relayer fees for in-flight (not yet delivered or timed-out) requests are recorded as raw `uint256` amounts in `FeeMetadata.fee`, denominated implicitly in whatever token was `feeToken()` at dispatch time. When those requests are later settled — via delivery reward (`dispatchIncoming`) or timeout refund (`dispatchTimeOut`) — the contract pays out `meta.fee` units of `feeToken()` **read at settlement time**, not the token that was actually collected. If the fee token changes between dispatch and settlement, the stale numeric amount is redeemed in a different, potentially far more valuable, ERC20 — mirroring the "rewards squatting" bug class: value locked against one token gets paid out in a different token whose relative value may have moved, letting whoever controls settlement timing (the request's payer for timeouts, or any relayer for deliveries) extract an economic windfall from the shared fee-token pool funded by other users.

### Finding Description
`HostParams.feeToken` is mutable governance state [1](#0-0) . `updateHostParamsInternal` only guards the swap by requiring the *current on-chain balance* of the old fee token to be zero — it does not account for fees that are already collected into that balance but still owed against pending (undelivered / not-yet-timed-out) requests: [2](#0-1) 

That balance can be trivially driven to zero by the same governance channel via `withdraw()`, which sweeps any ERC20 balance to a beneficiary with no linkage to which requests are still pending: [3](#0-2) 

Meanwhile, `dispatch()` collects `post.fee` in the *current* `feeToken()` and stores only the raw numeric amount, with no record of which token it was denominated in: [4](#0-3) 

Settlement paths re-read `feeToken()` fresh at execution time and pay `meta.fee` units of whatever that resolves to: [5](#0-4) 

and the successful-delivery reward path (`dispatchIncoming` for GET responses, and the analogous POST path) does the same: [6](#0-5) 

Because `meta.fee` is a bare integer with no token tag, once `feeToken()` changes, every request still in flight at that moment becomes a claim for `meta.fee` units of the *new* token — regardless of what token backed it originally. This is economically identical to the referenced Yield finding: a value denominated against token A silently converts into a claim on token B once the "reward token" is swapped, and unprivileged actors who control the timing of settlement (submitting a timeout proof, or racing to deliver/relay a pending request) can choose to settle before or after the swap depending on which token is more valuable to them.

### Impact Explanation
Any user/relayer who has a pending dispatched request at the time governance rotates `feeToken` can capture the appreciation of the new token by delaying settlement (timeout submission is permissionless and can be submitted by anyone once the timeout window elapses) until after the swap, redeeming their old, cheaper `fee` amount for the same integer amount of the new, more valuable token — funded out of the pool of new-feeToken deposits made by *other* users for *their* unrelated requests. Symmetrically, if the new token is less valuable, rational actors rush to settle before the swap. In both directions this drains value from the shared fee-token balance that is meant to back other users' pending fees/rewards, i.e., concrete theft/misallocation of escrowed funds via a token-mismatch that is fully reachable by an ordinary relayer or request payer, not just governance.

### Likelihood Explanation
Fee-token migrations (e.g., DAI → USDC, or onboarding a new stablecoin) are a normal, anticipated operational action documented in the codebase's own `HostParams` comments ("we allow it to be configurable to prevent future regrets"). Any such migration, even performed correctly by governance, leaves a window where in-flight requests' `FeeMetadata.fee` is stale; permissionless relayers and payers who monitor mempool/timing (exactly as described in the referenced report) can exploit this without any additional privilege. The `CannotChangeFeeToken` check gives false confidence since it only checks current balance, not outstanding commitments.

### Recommendation
Track the fee token per commitment (extend `FeeMetadata` with the token address used at dispatch time) rather than relying on the live `feeToken()` getter at settlement. Alternatively, require `updateHostParamsInternal` to assert that there are zero outstanding `_requestCommitments` entries (or provide/enforce a drain/grace window that settles all pending requests in the old token) before allowing the fee token to change, so no stale numeric fee amount can ever be redeemed against a different ERC20.

### Proof of Concept
1. User A dispatches a `PostRequest` with `fee = 100` while `feeToken() == USDC`; `100 USDC` is pulled into the host and `_requestCommitments[commitment] = {sender: A, fee: 100}`.
2. Before delivery/timeout, governance calls `withdraw()` sweeping the host's USDC balance to zero, then calls `updateHostParams` to switch `feeToken` to `WETH` (passes `CannotChangeFeeToken` since USDC balance is now 0).
3. Other users now dispatch new requests paying fees in WETH, building up a WETH balance in the host.
4. User A's original request times out. Anyone submits the timeout proof; `dispatchTimeOut` reads `feeToken()` (now WETH) and calls `IERC20(WETH).safeTransfer(A, 100)` — paying out 100 units of WETH (worth far more than the 100 USDC originally paid) sourced from the WETH pool deposited by unrelated later users.

        FeeMetadata memory meta,
        bytes32 commitment
    ) external restrict(_hostParams.handler) {
        // replay protection
        delete _requestCommitments[commitment];
        (bool success,) = _bytesToAddress(timeout.request.from)
            .call(abi.encodeWithSelector(IApp.onPostRequestTimeout.selector, timeout));
