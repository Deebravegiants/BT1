### Title
Side-effect tokens minted/accrued during order calldata execution are not swept, permanently stranding value in the `CallDispatcher` - (File: evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
The reported AURA bug is a case where a contract call (`getReward()`) has an additional side effect — Aura's `Booster.rewardClaimed()` mints the `AURA` governance token to the caller — that the controller's hardcoded `tokensIn` enumeration never lists, so the resulting balance is silently dropped from accounting. The same bug class exists in Hyperbridge's Intent Gateway V2: `IntentsBase._execute()` and `IntentGatewayV2.placeOrder()`'s predispatch flow both route arbitrary solver/user-supplied calldata through a shared `CallDispatcher`, then sweep back **only the tokens explicitly enumerated in `order.output.assets` / `order.inputs`**. Any token that accrues on the dispatcher as a side effect of the executed calldata (reward tokens, airdrops, LP-unwind byproducts, etc. — exactly analogous to `AURA` being minted as a side effect of `getReward()`) is never swept and is permanently stranded.

### Finding Description
`_execute()` in `evm/src/apps/intentsv2/IntentsBase.sol` dispatches the order's output calldata through the `CallDispatcher`, then sweeps back balances strictly indexed by `order.output.assets`: [1](#0-0) 

The sweep loop iterates `outputsLen` (the declared/expected output assets) and calls `IERC20(token).balanceOf(dispatcher)` only for those specific `token` addresses. If the arbitrary calldata dispatched at line 502 (e.g., depositing into / withdrawing from a DeFi protocol, similar to Convex/Aura's `getReward()`) causes the dispatcher to receive an *additional* token not listed in `order.output.assets` — such as a reward or governance token minted as a side effect, mirroring exactly how `Booster.rewardClaimed()` mints `AURA` as an unlisted side effect of `getReward()` — that token is never included in `sweepCalls` and is left sitting on the `CallDispatcher` contract indefinitely.

The same unaccounted-token pattern exists in the predispatch phase of `placeOrder()`: [2](#0-1) 

Here again, only tokens listed in `order.inputs` are swept back from the dispatcher after the predispatch call executes; any other token minted/transferred to the dispatcher as an incidental effect of that call is not tracked or recovered.

Since `_params.dispatcher` is a single shared `CallDispatcher` instance used across all orders (not a fresh, disposable contract per order), any leftover tokens from one order's calldata execution persist in dispatcher storage between transactions, compounding the loss over time and creating a shared pool of stranded value with no path to recovery — there is no generic sweep/rescue function for arbitrary ERC20s held by the dispatcher.

### Impact Explanation
Any token balance accrued on the `CallDispatcher` that isn't part of the declared `order.inputs`/`order.output.assets` set is permanently unrecoverable by the protocol, the user, or the solver — a direct parallel to the AURA report's "this token is not accounted for ... balance is missing," except here the consequence is outright loss of funds rather than a mispriced liquidation check. Because the dispatcher is shared infrastructure reused by every order that carries `predispatch.call` or `output.call`, this is not a one-off self-inflicted mistake by a single order author; it's a systemic sink whenever composable DeFi calldata (swaps, deposits, reward claims) has any token side effect beyond the declared asset list.

### Likelihood Explanation
Reachable by any unprivileged user or solver who constructs an `Order` with non-empty `predispatch.call` or `output.call` that routes through a protocol with reward/incentive side effects (staking, yield vaults, Convex/Aura-style reward claiming, liquidity unwinding that yields extra LP/reward tokens) — precisely the interaction pattern the docs advertise ("solvers can route through DEXes, lending protocols, or other DeFi primitives as part of filling an order"). No governance or admin action is required; a normal composable fill or predispatch execution triggers it.

### Recommendation
Track dispatcher token balances more generically rather than only sweeping tokens in the pre-declared asset list: e.g., require the calldata payload (or a companion parameter) to declare every token that may be touched during execution and sweep all of them, or restrict `CallDispatcher` interactions to a per-call ephemeral contract so no state (and no stray token balance) persists between orders, or add a permissioned/timelocked rescue function that can sweep arbitrary ERC20 balances stuck on the dispatcher back to affected users based on off-chain reconciliation.

### Proof of Concept
1. User places an order with `predispatch.call` (or a solver fills an order with `output.call`) that calls into a protocol whose call has a token side effect beyond the declared asset (e.g., `deposit()`/`withdraw()`/`getReward()`-style function that also mints/transfers a secondary reward token to the caller, as Aura's `Booster.rewardClaimed()` mints `AURA`).
2. `ICallDispatcher(dispatcher).dispatch(...)` executes this calldata; the dispatcher now holds both the expected token(s) and the unexpected side-effect token.
3. `_execute()` (or the predispatch sweep in `placeOrder()`) only builds `sweepCalls`/`transferCalls` for tokens present in `order.output.assets` / `order.inputs`; the side-effect token's balance on the dispatcher is never read or swept. [3](#0-2) 
4. The side-effect token remains on the shared `CallDispatcher` after the transaction completes, with no function in the contract able to recover it — funds are permanently frozen, growing with every subsequent order that triggers the same side effect.

    function _execute(Order calldata order, uint256 outputsLen) internal {
        if (order.output.call.length == 0) return;

        address dispatcher = _params.dispatcher;
        ICallDispatcher(dispatcher).dispatch(order.output.call);

        Call[] memory sweepCalls = new Call[](outputsLen);
        uint256 sweepCount = 0;

        for (uint256 i; i < outputsLen;) {
            address token = address(uint160(uint256(order.output.assets[i].token)));

            if (token == address(0)) {
                uint256 balance = dispatcher.balance;
                if (balance > 0) {
                    sweepCalls[sweepCount] = Call({to: address(this), value: balance, data: ""});
                    sweepCount++;
                    emit DustCollected(token, balance);
                }
            } else {
                uint256 balance = IERC20(token).balanceOf(dispatcher);
                if (balance > 0) {
                    sweepCalls[sweepCount] = Call({
                        to: token,
                        value: 0,
                        data: abi.encodeWithSelector(IERC20.transfer.selector, address(this), balance)
                    });
                    sweepCount++;
                    emit DustCollected(token, balance);
                }
            }

            unchecked {
                ++i;
            }
        }
