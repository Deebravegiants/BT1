Based on the documented API, the gem explicitly exposes `data.shop` (the shop domain) to the app's webhook handler as a trusted field derived directly from the `Registry.process` flow, while `ShopifyAPI::Utils::HmacValidator.validate(request)` only authenticates the raw request body bytes, not the shop/topic/webhook-id headers.

### Title
Webhook shop identity spoofing via unauthenticated `shop-domain` header - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , so `HmacValidator.validate` authenticates only the body bytes, never the `shop-domain`, `topic`, or `webhook-id` headers that are parsed separately from the request [2](#0-1) . `Registry.process` trusts `request.shop` as the tenant identifier and hands it straight to the app's handler as `WebhookMetadata.shop` after only checking the body HMAC [3](#0-2) , and the documented contract tells integrators `shop` is "The shop domain of the webhook" to be used directly (e.g. `perform_later(shop_domain: data.shop, ...)`) [4](#0-3) .

### Finding Description
The identity-binding equality that should hold is: `bytes verified by HMAC == bytes that determine tenant (shop)`. Here it does not — `hmac == HMAC(raw_body)` only, while `shop = header["shop-domain"]` is read independently and never folded into the signable string [5](#0-4) . Because a single app-wide `api_secret_key` is shared to verify webhooks for *every* installed shop, any merchant who installs the app can trigger a real webhook for their own store, capture the valid `(raw_body, hmac)` pair, and replay it to the app's webhook endpoint with the `shop-domain` (and `topic`/`webhook-id`) headers rewritten to reference a different, victim shop. `HmacValidator.validate` will still return `true` because it only recomputes the HMAC over the unchanged body [6](#0-5) , and `Registry.process` will dispatch to the handler believing the event legitimately originated from the victim shop [3](#0-2) .

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook events: an attacker (any merchant capable of installing the app themselves) can make the app believe an event came from a shop they don't control, injecting attacker-chosen `body` content tagged with a victim's shop domain into whatever downstream processing the host app performs (job enqueueing, data writes, order/customer record updates, GDPR redact triggers, etc., since `shop/redact`, `customers/redact`, `customers/data_request` are also affected topics [7](#0-6) ). This is a cross-tenant identity confusion at the boundary this library is responsible for verifying.

### Likelihood Explanation
Requires only an app-wide-shared, non-secret piece of information: any legitimate installer of the target app can obtain a valid `(body, hmac)` pair from their own shop's normal webhook traffic and replay it with a forged `shop-domain` header directly to the app's public webhook endpoint — no possession of `api_secret_key`, access tokens, or TLS interception is needed.

### Recommendation
Include `shop`, `topic`, and `webhook_id` (in addition to the body) in the signable string used for HMAC verification, or independently bind/verify the `shop-domain` header against a value cryptographically tied to the signed payload before trusting it in `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and receives a legitimate webhook: headers include `X-Shopify-Hmac-Sha256: <valid_hmac>`, `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Topic: orders/create`, body `{"id":1,...}`.
2. Attacker replays this exact request to the app's webhook callback path, but changes only `X-Shopify-Shop-Domain` to `victim.myshopify.com` (body and hmac untouched).
3. `ShopifyAPI::Webhooks::Request.new` parses the new shop header [8](#0-7) ; `HmacValidator.validate` succeeds since it only checks the unchanged body against the shared `api_secret_key` [9](#0-8) .
4. `Registry.process` invokes the app's handler with `shop: "victim.myshopify.com"` and the attacker's chosen body, which the host app processes as if `victim.myshopify.com` sent that event [10](#0-9) .
