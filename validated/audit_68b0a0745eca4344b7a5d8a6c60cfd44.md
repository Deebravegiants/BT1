### Title
Vault deposit/redeem/borrow/repay flows only check for `err` on underlying `transfer` calls, silently accepting `(ok false)` as success - ([File: mainnet/contracts/vault/v0-vault-sbtc.clar])

### Summary
Every vault (`v0-vault-sbtc.clar`, `v0-vault-stx.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`) wraps the underlying SIP-010 `transfer` call in `try!` inside `receive-underlying`/`send-underlying`, but never inspects the boolean payload of the `(response bool uint)` that `transfer` returns. `try!` only short-circuits on `(err ...)`; if the underlying token contract returns `(ok false)` (a non-reverting failure, the SIP-010 analog of ERC20 tokens like EURS/BAT that return `false` instead of reverting), the vault treats the transfer as fully successful and continues to mint/burn shares and update its internal `assets` accounting as if real tokens moved.

### Finding Description
`receive-underlying` and `send-underlying` are defined identically across all vaults, e.g. in `v0-vault-sbtc.clar`: [1](#0-0) 

`try!` unwraps `(ok x)` to `x` and discards it, only propagating on `(err e)`. It does not assert that the unwrapped boolean `x` is `true`. `deposit` uses this helper before minting vault shares: [2](#0-1) 

If `UNDERLYING`'s `transfer` returns `(ok false)` instead of erring on a failed transfer (e.g. due to a non-standard/buggy SIP-010 implementation, a proxy, or a token upgrade), `receive-underlying` still returns `(ok true)`, `assets` is incremented by the full nominal `amount`, and `ft-mint?` mints the corresponding `inkind` shares to `recipient` — even though no underlying value actually entered the vault. This breaks the identity `assets_var == actual_underlying_custodied`, diluting/backing shares with nothing (insolvency vector), analogous to the original ERC20 `transferFrom` unchecked-return-value bug where a mint fee token silently failed without reverting.

Symmetrically, `redeem` burns shares before calling `send-underlying`: [3](#0-2) 

If `send-underlying`'s inner `transfer` returns `(ok false)`, the user's shares are already burned via `ft-burn?` and `assets` is decremented, but the redeemer receives nothing — a silent loss of principal for that user. The same pattern recurs in `system-borrow`/`system-repay` (lines 863-940) and in the other vault files (`v0-vault-stx.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`), all sharing the identical `receive-underlying`/`send-underlying` helper structure.

### Impact Explanation
If the hardcoded `UNDERLYING` SIP-010 token contract (or any future underlying swapped in) ever returns `(ok false)` on a failed transfer rather than an `err`, deposits can mint vault shares backed by no real assets (protocol insolvency / value minted from nothing), and redemptions/borrows can burn shares or reduce the debt ledger without the user actually receiving funds (theft of principal for that user). This directly breaks the share-minting-vs-backing identity that governs vault solvency.

### Likelihood Explanation
Likelihood depends entirely on whether any of the specific underlying token contracts (`sbtc-token`, `wstx`, `usdc`, `usdh-token-v1`, `ststx`, `ststxbtc`) can return `(ok false)` under any code path (bug, upgrade, or non-standard implementation) rather than reverting/erring. Zest does not control these external token implementations, so this is a latent risk rather than a currently demonstrated live exploit against a known-good token, but the vault code itself has no defense-in-depth check regardless of token behavior.

### Recommendation
In `receive-underlying` and `send-underlying` (and any other place a token's `transfer`/similar response is unwrapped via `try!`), explicitly assert the unwrapped boolean is `true` before proceeding, e.g.:
```clarity
(define-private (receive-underlying (amount uint) (account principal))
  (let ((ok? (try! (contract-call? UNDERLYING transfer amount account current-contract none))))
    (asserts! ok? ERR-TRANSFER-FAILED)
    (ok true)))
```
Apply the same fix to `send-underlying` and to every vault file exhibiting this pattern.

### Proof of Concept
1. Assume (hypothetically, or via a mock in a controlled test) `UNDERLYING` transfer returns `(ok false)` on a failed transfer instead of `(err ...)`.
2. Call `deposit` with `amount > 0`; `receive-underlying` returns `(ok true)` despite no tokens moving.
3. `ft-mint?` mints `inkind` shares to `recipient`, and `assets` is incremented by `amount` — shares now exist with no corresponding underlying backing, as shown in `v0-vault-sbtc.clar` lines 761-793.
4. Alternatively, call `redeem`; shares are burned via `ft-burn?` before `send-underlying` is invoked, and if the transfer returns `(ok false)`, the redeemer receives no assets despite having burned shares, as shown in lines 795-829.
