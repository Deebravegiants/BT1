### Title
`callRouter` in `LifiExternalAction`/`ExternalActionSwap` lets an attacker mint UTXOs backed by more value than `-deltaAmounts[0]` authorized, by pulling stranded token balance through an unconstrained router call - (File: contracts/external-actions/swaps/ExternalActionSwap.sol, contracts/external-actions/swaps/LifiExternalAction.sol)

### Summary
`ExternalActionSwap.swap` computes `inputAmount` from `-deltaAmounts[0]` (minus fee) purely to pass as a parameter to `callRouter`, but `LifiExternalAction.callRouter` never actually restricts how much `inputToken` the router pulls: it grants `approveUnlimited(inputToken, router)` and then executes attacker-controlled `externalActionMetadata` verbatim, measuring `swappedAmount` only as `outputToken` balance delta. Since the action contract's balance of `inputToken` is never zeroed/checked before or after the call, any pre-existing (stranded) balance of `inputToken` sitting in the action contract can be swept into the swap and monetized into a new UTXO that Hinkal accepts as legitimate.

### Finding Description
The claimed equality is: `tokens leaving the action (approved + pulled by router) == -deltaAmountChanges[0]` that Hinkal transferred to the action for this transaction. Tracing the code shows this equality is never enforced:

- In `Hinkal._externalTransact` (`contracts/Hinkal.sol:244-256`), Hinkal transfers exactly `-deltaAmountChanges[0]` of `inputToken` to the external action address, then calls `runAction`.
- In `ExternalActionSwap.swap` (`contracts/external-actions/swaps/ExternalActionSwap.sol:44-49, 63-68`), `inputAmount = uint256(-deltaAmounts[0])` (optionally minus `flatFee`) is computed and passed into `callRouter`, but `inputAmount` is only actually used for the native-ETH branch (`router.call{value: inputAmount}`); for ERC20 it is **not passed to the router at all**.
- In `LifiExternalAction.callRouter` (`contracts/external-actions/swaps/LifiExternalAction.sol:16-36`), for ERC20 input the code does `approveUnlimited(inputToken, router)` then `router.call(externalActionMetadata)`. The router pulls whatever amount is encoded inside the attacker-supplied `externalActionMetadata` via `transferFrom`, bounded only by the action contract's actual `inputToken` balance (now unlimited allowance). `swappedAmount` is derived purely from `outputToken` balance delta, with no cross-check against `inputAmount`.
- Back in `Hinkal.transact` (`contracts/Hinkal.sol:78-146`), the post-call balance-diff checks (`balanceDif == amountChanges[i] + utxoAmount`) are self-referential to Hinkal's own balance and the UTXO amounts *returned by the action*, not to what the action/router actually did with `inputToken`. For the input token index, Hinkal's balance already dropped by exactly `-deltaAmountChanges[0]` before `runAction` was even invoked, so the check trivially passes no matter how much extra `inputToken` the action/router consumed from its own stranded balance. For the output token index, the check simply matches `balanceDif` against the UTXO amount the action reports — which is `amountToSendToHinkal`, itself derived from the inflated `swappedAmount`. So whatever value the router coughs up (real swap value + stranded/leftover funds) becomes the amount of a freshly minted shielded UTXO for the attacker, fully accepted by the circuit-independent Solidity checks.

Root cause: nothing in `ExternalActionSwap`/`LifiExternalAction` verifies that the router consumed exactly `inputAmount` of `inputToken`, and nothing verifies that the action contract's `inputToken` balance returns to (or below) its pre-call baseline. Because `externalActionMetadata` is entirely attacker-crafted (per the threat model) and `approveUnlimited` grants infinite allowance, the router can be instructed to pull any balance sitting in the action contract, not just the amount Hinkal sent for this transaction.

Attacker flow:
1. Transaction A (can be the attacker's own transaction): craft `externalActionMetadata` such that the router under-consumes `inputToken` (e.g., only swaps 90% of the amount Hinkal transferred), leaving residual `inputToken` stranded in `LifiExternalAction`. Nothing in `swap()` checks that the action's `inputToken` balance returns to zero/baseline after the call, so this residue persists indefinitely.
2. Transaction B: attacker sets `deltaAmounts[0]` to a small value (so a small, real amount is burned from their own shielded balance and transferred to the action), but crafts `externalActionMetadata` for transaction B's router call to pull the full current `inputToken` balance of the action (the small new transfer + all previously stranded residue), swapping the entire amount.
3. `swappedAmount` (and thus `amountToSendToHinkal` and the new UTXO's `amount`) reflects the inflated swap of stranded + new funds, while the attacker's proof only needed to authorize (`amountChanges`/`deltaAmounts`) the small piece they actually contributed.
4. The new UTXO commitment (backed by the excess value) is inserted into Hinkal's Merkle tree via `insertCommitments`, effectively minting shielded value not backed by any burned/withdrawn ledger entry beyond the small authorized amount.

### Impact Explanation
This lets an attacker mint a shielded UTXO whose value exceeds what their own proof's `amountChanges`/`deltaAmounts` actually authorized, by sweeping stranded `inputToken` balance (which may originate from other users' partially-consumed swaps) through the router. This is theft of principal/value beyond authorization and effectively "minting shielded value without backing," matching the Critical category. It is repeatable any time residual balance accumulates in the action contract, and the attacker can even manufacture the precondition themselves across two of their own transactions.

### Likelihood Explanation
Preconditions: (a) some non-zero `inputToken` balance must be sitting in `LifiExternalAction` beyond what the current transaction authorizes — achievable either passively (dust from router slippage/under-fill on any prior swap) or actively (attacker deliberately under-swaps in a first transaction using self-crafted `externalActionMetadata`), and (b) attacker must be able to craft `externalActionMetadata` for the router call, which the threat model explicitly grants. No privileged role is required. Cost is just gas for two transactions; the gain scales with however much residual balance can be accumulated/exploited, and is repeatable indefinitely as long as new residue is produced.

### Recommendation
Enforce that the router consumes exactly (and no more than) `inputAmount` of `inputToken`: track the action's `inputToken` balance before/after the router call and require the decrease to equal `inputAmount` (or require any leftover to be swept back to Hinkal/relay rather than silently retained), and/or use a finite `approve(router, inputAmount)` instead of `approveUnlimited`, resetting allowance to zero after the call. Additionally, have `Hinkal.transact`'s balance-diff check trace the actual amount consumed by the action from the tokens it received, not just the action's self-reported UTXO output.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `LifiExternalAction` (with a mock router), and a mock ERC20 `inputToken`/`outputToken`.
2. Transaction A: perform a legitimate-looking swap via `Hinkal.transact` where the mock router's `externalActionMetadata` is crafted to only `transferFrom` 90% of the `inputAmount` approved, leaving 10% of `inputToken` balance stranded in `LifiExternalAction`. Assert `inputToken.balanceOf(LifiExternalAction) > 0` after the tx.
3. Transaction B: attacker generates a valid proof with a small `deltaAmounts[0]` (e.g., corresponding to 1 unit of `inputToken`), but crafts `externalActionMetadata` for the mock router to `transferFrom` the entire current `inputToken` balance of `LifiExternalAction` (small new transfer + stranded residue from step 2), and have the mock router return a proportional `outputToken` amount.
4. Assert: `swappedAmount` (the router-pulled/converted amount) `!= uint256(-deltaAmounts[0])`, and assert the new UTXO commitment inserted into the Merkle tree carries `amount` greater than what `deltaAmounts[0]`/`amountChanges[0]` authorized, i.e., `utxoSet[0].amount > f(deltaAmounts[0])` where `f` is the expected 1:1 (or oracle-fair) conversion for the authorized amount only.
5. Confirm the transaction does not revert on any of Hinkal's balance/slippage checks, demonstrating the discrepancy is undetected by existing guards. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)

```text
    function callRouter(
        address inputToken,
        uint256 inputAmount,
        address outputToken,
        bytes calldata externalActionMetadata
    ) internal override returns (uint256 swappedAmount) {
        uint256 balanceBefore = getERC20OrETHBalance(outputToken);

        if (inputToken == address(0)) {
            (bool success, ) = router.call{value: inputAmount}(
                externalActionMetadata
            );
            require(success, "LI.FI swap failed: native coin");
        } else {
            approveUnlimited(inputToken, router);
            (bool success, ) = router.call(externalActionMetadata);
            require(success, "LI.FI swap failed: erc-20 token");
        }

        swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore;
    }
```
