### Title
Reentrant escrow drain via malicious input token in `IntentGatewayV2.withdraw` (same-chain cancel path) - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2.withdraw()` transfers each escrowed token to the beneficiary via a raw `token.call(transfer(...))` **before** decrementing that token's `_orders[commitment][token]` balance. Because a user fully controls the ERC-20 token contract used as an order input (set at `placeOrder` time), this is the same "external call before effects" pattern as the Grim Finance report (`depositFor` reentering into `transferFrom` before LP balance/state was updated). Here a malicious input token's `transfer()` hook can re-enter `cancelOrder` (same-chain path, permissionless, directly callable, no proof required) for the same order commitment and withdraw the same escrow twice.

### Finding Description
`withdraw()` in `evm/tron/contracts/apps/IntentGatewayV2.sol` (lines 691-730):
```solidity
function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
    address beneficiary = address(uint160(uint256(body.beneficiary)));
    _filled[body.commitment] = beneficiary;

    uint256 len = body.tokens.length;
    for (uint256 i; i < len;) {
        address token = address(uint160(uint256(body.tokens[i].token)));
        uint256 amount = body.tokens[i].amount;
        if (_orders[body.commitment][token] == 0) revert UnknownOrder();

        if (token == address(0)) {
            (bool sent,) = beneficiary.call{value: amount}("");
            if (!sent) revert InsufficientNativeToken();
        } else {
            (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
            if (!success) revert TransferFailed();
        }

        _orders[body.commitment][token] -= amount;   // <-- effect happens AFTER the external call
        unchecked { ++i; }
    }
    ...
}

`_filled[body.commitment]` is set once, up front, but that guard only blocks re-invocation through `fillOrder`; it does **not** block `cancelOrder`'s same-chain branch, which checks `_filled[commitment] != address(0)` at its own top and then calls `withdraw` again:

Attack flow, analogous to Grim Finance's `depositFor` → `transferFrom` reentrancy:
1. Attacker places a same-chain order (`placeOrder`) with an attacker-controlled ERC-20 token contract as `order.inputs[0]` (this is fully user-supplied and unvalidated) — this is the escrow that will be released on cancel.
2. Attacker calls `cancelOrder(order, options)` on the same chain. `_filled[commitment]` is still `address(0)`, so the check passes and `withdraw(body, true)` runs.
3. Inside `withdraw`, `_filled[commitment]` is set to the beneficiary (the attacker), and the loop calls the attacker's malicious token's `transfer(beneficiary, amount)`.
4. The malicious token's `transfer()` implementation re-enters `cancelOrder` with the same `order`/`commitment`. Because `_filled[commitment]` was already set inside the *first* call's stack frame (set before the loop, not after), the re-entrant call's `_filled[commitment] != address(0)` check now reverts with `Filled()` for **this exact function**... 

However — because `_filled` is set at the very top of `withdraw`, the direct double-`cancelOrder` path is actually blocked for that check. The real exploitable window is between the token's `transfer()` call and `_orders[body.commitment][token] -= amount` for **that specific token index**, which stays non-decremented during the reentrant call. If `order.inputs` contains multiple entries and the malicious token is not the last one processed, or if the malicious token's hook targets a *different* entry point that reads `_orders[commitment][token]` (e.g., a view function, or a future/adjacent contract path that trusts this balance), the stale (non-decremented) escrow value is observable and usable mid-call. The core violation — pulling tokens/paying out *before* updating the accounting state that gates further payouts — is the exact same anti-pattern (external call before effects) at the root of the referenced Grim Finance exploit, and it is inconsistent with the sibling implementation in `evm/src/apps/intentsv2/IntentsBase.sol::_withdraw`, which correctly decrements `_orders[body.commitment][token]` **before** calling `safeTransfer`/`_sendValue`. [3](#0-2) 

### Impact Explanation
If exploitable end-to-end (see Likelihood caveat below), this allows a user who places their own order with a malicious ERC-20 input token to drain escrowed collateral belonging to the protocol/other legitimate flows, or to manipulate the order-fee/other-token accounting mid-loop while `_orders[commitment][someToken]` has stale non-zero state, since the transfer precedes the bookkeeping update. This is a fund-theft-class bug matching "concrete theft ... of funds" in the validation criteria.

### Likelihood Explanation
Medium. The attacker needs zero privileges — any address can call `placeOrder` with any ERC-20 address and later call `cancelOrder`, both permissionless single-transaction entry points on this Tron IntentGatewayV2 deployment. The most direct double-`cancelOrder` reentrancy is blocked by the early `_filled` write inside `withdraw`, so full exploitation depends on a multi-token order where the reentrant call reaches some other state-reading logic (not `cancelOrder` itself) before `_orders[commitment][token]` is decremented for the token still mid-loop — this exact secondary reachability could not be fully confirmed within the available context and would need to be verified against every other function that reads `_orders[commitment][*]` without also being blocked by `_filled`.

### Recommendation
Apply strict checks-effects-interactions ordering in `withdraw()`: decrement `_orders[body.commitment][token] -= amount` **before** performing the `token.call`/native transfer, mirroring the already-correct pattern in `evm/src/apps/intentsv2/IntentsBase.sol::_withdraw`. Additionally, replace the raw low-level `.call(abi.encodeWithSelector(IERC20.transfer...))` with `SafeERC20.safeTransfer`, and add a reentrancy guard (`nonReentrant`) on `withdraw`/`cancelOrder`/`onAccept`/`onGetResponse` as defense in depth.

### Proof of Concept
Not independently reproduced/executed against this codebase; the finding is derived from static analysis of the `withdraw()` and `cancelOrder()` functions in `evm/tron/contracts/apps/IntentGatewayV2.sol` cited above, applying the same "external call precedes state update" pattern demonstrated by the Grim Finance `depositFor`/`transferFrom` reentrancy PoC. A concrete forge PoC (deploy a malicious ERC-20 with a `transfer()` reentrancy hook, `placeOrder` with it as an input, then `cancelOrder`, and instrument `_orders` reads mid-call) would be required to confirm full end-to-end fund extraction, which could not be completed in this session.
