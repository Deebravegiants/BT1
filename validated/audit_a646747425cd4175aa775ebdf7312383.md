## Title
Panic-inducing unchecked slice arithmetic on attacker-controlled `message.from` bytes in `hyper-fungible-token` calldata origin resolution - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

## Summary
`Pallet::<T>::on_accept` in the `hyper-fungible-token` pallet decodes an ABI-encoded `Message` from an incoming ISMP `PostRequest.body`, and when the message carries optional calldata without a signature, derives a dispatch origin from `message.from` with no length validation before slicing: [1](#0-0) 

```rust
let from_bytes = message.from.as_ref();
if source.is_evm() {
    T::EvmToSubstrate::convert(H160::from_slice(
        &from_bytes[from_bytes.len() - 20..],
    ))
} else {
    let mut account = [0u8; 32];
    account.copy_from_slice(from_bytes);
    account.into()
}
```

## Finding Description
`message.from` is a `bytes` field decoded from the Solidity-ABI-encoded `Message` struct (see `HyperFungibleToken.sol`'s `Message` type, whose `from`/`to`/`data` are dynamic `bytes`) via `Message::abi_decode(&body)` at [2](#0-1) . Because ABI `bytes` fields impose no length constraint, an attacker controlling the source-chain `HyperFungibleToken` contract (or any registered `ContractToAsset` source, which only needs a valid mapping from `source`+`from`, not from the exact bytes inside the body) can set `message.from` to an arbitrary-length byte string, e.g. shorter than 20 bytes when `source.is_evm()` or any length other than exactly 32 when the source is non-EVM.

- If `source.is_evm()` and `from_bytes.len() < 20`, the expression `from_bytes.len() - 20` underflows on `usize`, which panics in debug builds and, in release builds (Substrate runtimes typically build with `overflow-checks = true` for safety, and even without it, wraps to a huge value), causes a slice-index-out-of-bounds panic when used to index `from_bytes`.
- If `source` is not EVM and `from_bytes.len() != 32`, `account.copy_from_slice(from_bytes)` panics immediately (length mismatch is a hard `panic!` in the standard library, not a `Result`).

Both panics occur inside `IsmpModule::on_accept`, which is invoked from the core ISMP request handler (`modules/ismp/core/src/handlers/request.rs`) as part of normal, permissionless message delivery by any relayer submitting a valid membership proof for a request whose body was crafted by the (attacker-controlled) source contract. This mirrors the CVE-2017-9353 class of bug: a dissector/parser trusts a field's length implicitly and indexes/copies without validating it first, leading to a crash on malformed/attacker-crafted input.

Note this is guarded from being *fully* unprivileged in the strict sense that `ContractToAsset::<T>::get(source, &from)` at line 55 must resolve — i.e., the *outer* `PostRequest.from` (the ISMP-level sender, validated by the host/consensus proof) must be a registered HFT contract on `source`. However, `message.from` inside the ABI-encoded body is a completely separate, attacker-controlled field that the honest sending contract normally sets to `msg.sender`, but a malicious/compromised registered source contract (or any source chain whose HFT deployment is compromised or misconfigured) can set to any byte string of any length, including empty or 19/21/33+ bytes.

## Impact Explanation
A crafted `message.from` of the wrong length causes a Rust panic inside pallet-ismp's `execute`/`handle_incoming_message` path during `on_accept`. Depending on how Substrate's transaction dispatch wraps panics, this can:
- Abort the encompassing runtime call, wasting relayer fees but more importantly,
- If unwind-safety around `on_accept` (called from an `IsmpModule`, executed inside block execution) is insufficient, cause a full node/runtime panic, since substrate WASM execution panicking generally traps the whole block execution, which can halt block production (a route unable to deliver messages / effectively a denial-of-service on that parachain), satisfying the "route unable to deliver messages" acceptance criterion.

This is only reachable when the optional-calldata path is used (`message.data` non-empty, no signature attached), and requires a source contract already registered in `ContractToAsset`. Given that requirement, the severity is best characterized as High rather than Critical: exploitation requires a compromised or malicious source-chain deployment, but any relayer can then deliver the malformed message permissionlessly to trigger the crash on the destination parachain.

## Likelihood Explanation
Likelihood is Medium-High conditioned on a malicious/compromised source-side HFT contract: no privileged action on the destination chain is required, any relayer can deliver the proof once a legitimate request exists, and the crafted `from` field costs nothing extra to include in the source-chain call. It is not exploitable by a fully external, ownerless attacker who has no way to make a state machine dispatch a `PostRequest` via a registered contract — but once a chain operator or governance registers any source contract, that party (or anyone who can compromise it) can reliably trigger the panic.

## Recommendation
Validate `from_bytes.len()` before use, mirroring the existing pattern already applied to `message.to` at [3](#0-2)  and to `on_timeout`'s `from_bytes` handling at [4](#0-3) : reject (return `Err(HftError::InvalidSenderLength(from_bytes.len()))` or similar) any length other than the expected 20 (EVM) or 32 (non-EVM) bytes instead of slicing/copying unconditionally.

## Proof of Concept
1. Register a malicious/compromised `HyperFungibleToken`-style contract as the authorized source for some `StateMachine` in `ContractToAsset`.
2. From that contract, dispatch a `PostRequest` whose ABI-encoded body decodes to a `Message` with:
   - `to`: a valid 20 or 32 byte recipient (so minting succeeds),
   - `data`: non-empty `SubstrateCalldata` with `signature = None` and any `runtime_call`,
   - `from`: a byte string of length 0 (or any length ≠ 20 when `source.is_evm()`).
3. Any relayer submits the corresponding ISMP `RequestMessage` with a valid membership proof through `pallet_ismp`'s `handle`.
4. During delivery, `Pallet::<T>::on_accept` executes `&from_bytes[from_bytes.len() - 20..]` which underflows/panics (or `copy_from_slice` panics for the non-EVM branch), crashing execution of that extrinsic/block instead of returning a graceful `Err`.
