### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant shop spoofing via webhook replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw HTTP body. The `shop` (tenant identity) is taken from the `X-Shopify-Shop-Domain`/`Shopify-Shop-Domain` header, which is not included in the HMAC-covered bytes. `Registry.process` trusts `request.shop` for tenant attribution once the body-only HMAC passes, so the shop identity used by the handler is unauthenticated with respect to the signature.

### Finding Description
`HmacValidator.validate` computes `OpenSSL::HMAC.hexdigest(sha256, secret, verifiable_query.to_signable_string)` and compares it to the `hmac` header value [4](#0-3) . For webhook requests, `to_signable_string` is defined as just `@raw_body` [1](#0-0) , so the signature binds only the request body — never the `shop`, `topic`, `webhook_id`, or `api_version` headers.

`Registry.process` validates the HMAC and then immediately builds `WebhookMetadata` using `request.shop`, which comes straight from the (unsigned) `shop-domain` header [3](#0-2) . Because a single app installation uses one `api_secret_key` shared across every shop that installs it, and every shop's legitimate webhooks are HMAC-signed with that same secret, a valid `(raw_body, hmac)` pair captured from a webhook addressed to one shop remains cryptographically valid when replayed with a different `shop-domain` header value. The equality that should hold — "the shop bound by the signature" == "the shop the handler attributes the payload to" — is broken: the signature binds the body bytes only, while the handler trusts the header-derived shop for tenant attribution.

### Impact Explanation
An attacker who controls (or creates, e.g. via a free Shopify Partners development store) their own shop that installs the vulnerable app can capture a legitimate webhook `(raw_body, hmac)` pair sent by Shopify to the app's registered webhook endpoint. They can then replay that exact body/HMAC to the same endpoint while substituting the `shop-domain` header with a victim shop's domain. `Utils::HmacValidator.validate` still returns `true` (body unchanged), and `Registry.process` dispatches the handler with `shop: request.shop` set to the attacker-chosen victim domain [3](#0-2) . This lets an unauthenticated, unprivileged actor inject attacker-controlled webhook data under a victim shop's identity — a cross-tenant identity confusion that can corrupt per-shop data, trigger mandatory-compliance handlers (e.g. `shop/redact`), or otherwise cause the host application to act on forged data believing it originated from the victim tenant.

### Likelihood Explanation
Exploitation only requires the attacker to operate one shop that installs the target app (freely obtainable) and to send one crafted HTTP request to the app's public webhook endpoint with a modified header; no access to `api_secret_key`, tokens, or the victim shop is required. Likelihood is high given the low barrier to entry.

### Recommendation
Bind the shop (and ideally topic/webhook-id) into the signed content, or otherwise verify that `request.shop` matches the shop context the webhook was registered/expected for, rather than trusting the header value once only the body signature is verified. At minimum, cross-check the `shop-domain` header against a known/expected shop for the delivery before dispatching to the handler.

### Proof of Concept
1. App installs on `attacker-shop.myshopify.com`; app registers webhook URL `https://app.example.com/webhooks`.
2. Shopify sends a legitimate webhook to that URL:
   - Headers: `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`
   - Body: `{"id": 1, ...}`
3. Attacker captures `raw_body` and `hmac` (their own traffic — no interception of victim traffic needed).
4. Attacker sends a new POST to `https://app.example.com/webhooks` with the same `raw_body` and `hmac`, but `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
5. `Utils::HmacValidator.validate` in `lib/shopify_api/webhooks/registry.rb` line 190 passes because it only checks `raw_body` against `hmac`.
6. `Registry.process` calls the handler with `shop: "victim-shop.myshopify.com"` [5](#0-4) , causing the host application to process attacker data as if it belongs to the victim shop.
