### Title
Theft of tokens/ETH accidentally left in the shared `CallDispatcher` via `IntentGatewayV2.placeOrder`'s predispatch balance-sweep - (File: `evm/src/apps/IntentGatewayV2.sol`)

### Summary
`placeOrder`'s predispatch-escrow path sweeps the **entire current balance** of `_params.dispatcher` (the shared, persistent `CallDispatcher` contract) for each input token/ETH, instead of only the amount actually produced by the caller's own predispatch call. Any tokens sitting in the `CallDispatcher` from another source — an accidental transfer, or residue left over from a previous predispatch execution — get pulled in and credited toward the current caller's order, exactly mirroring the reported bug where `_stethToWsteth` returned `balanceOf(address(this))` instead of the value actually produced by the operation.

### Finding Description
`_params.dispatcher` is a single, shared `CallDispatcher` instance used by every `placeOrder` call across all users [1](#0-0) [2](#0-1) . It has a bare `receive() external payable {}` and executes arbitrary `Call[]` batches for whoever calls `dispatch` — it holds no owner-scoped accounting of "whose" balance is inside it.

In `placeOrder`, when an order carries predispatch calldata, the gateway:
1. Transfers `order.predispatch.assets` from `msg.sender` to `dispatcher`.
2. Runs `dispatcher.dispatch(order.predispatch.call)`.
3. For each `order.inputs[i]`, reads `balance = IERC20(token).balanceOf(dispatcher)` (or `dispatcher`'s native balance) — the dispatcher's **entire** current balance of that token — and builds a sweep `Call` that transfers the *whole* `balance` back to the gateway, not just the amount the predispatch call was supposed to produce: [3](#0-2) 

4. It then measures `received` as the gateway's balance delta and credits `order.inputs[i].amount = received` (capped at the originally requested amount; any excess is only emitted as `DustCollected`, not returned to whoever actually owned it): [4](#0-3) 

Because the sweep is keyed on `balanceOf(dispatcher)` rather than on the amount actually attributable to the caller's own predispatch call, any token or ETH that ends up sitting in the shared `CallDispatcher` — via a stray/accidental transfer, or leftover dust from a prior predispatch execution (e.g. slippage on a swap, a partially consumed multi-step call) — is folded into the very next `placeOrder` predispatch sweep and credited to that caller's order escrow. This is structurally identical to the reported `_stethToWsteth` bug: returning/using the contract's raw balance instead of the value actually produced by the intended operation.

The Tron fork of the contract contains the identical pattern [5](#0-4) .

### Impact Explanation
An attacker can construct an order whose predispatch call produces little or no real output, but whose `order.inputs[i].amount` (the amount they claim to escrow) is satisfied for free out of whatever balance happens to already sit in the `CallDispatcher` for that token — funds that belong to someone else (an earlier accidental transfer, or dust from another user's predispatch execution). The attacker's order is then placed and can be filled by solvers cross-chain/same-chain, meaning the attacker extracts real value (the solver's output tokens) while contributing none, or less, of their own input tokens. This is concrete theft of funds routed through the intent-escrow accounting, reachable from a single `placeOrder` transaction by any unprivileged order placer.

### Likelihood Explanation
`CallDispatcher` is permissionless to send tokens/ETH to (`receive()` is unrestricted, and it is a well-known, fixed address referenced by every order's `predispatch.call`), and slippage/rounding dust from real solver/user predispatch calls (documented in the protocol's own docs as something to sweep and account for via `DustCollected`) will regularly leave small residual balances there between transactions. Any user who notices a nonzero balance on the dispatcher for a token they want as an input can immediately place an order that captures it. This requires no special privileges — only observing the dispatcher's public balance and submitting a normal `placeOrder` call — making the likelihood high whenever any stray balance exists.

### Recommendation
Do not size the sweep or the credited `order.inputs[i].amount` off `IERC20(token).balanceOf(dispatcher)`/`address(dispatcher).balance`. Instead, snapshot the dispatcher's balance for each relevant token **before** transferring predispatch assets and running the predispatch call, then sweep/credit only the *delta* produced by this specific predispatch execution (`balanceAfter - balanceBefore`), leaving any pre-existing balance untouched in the dispatcher rather than folding it into the current caller's order. Any genuinely stray balance should be recoverable only through a privileged rescue/sweep path that returns it to its rightful owner or the protocol treasury, not implicitly credited to whichever caller happens to place the next order.

### Proof of Concept
1. Some ERC20 token `T` ends up in `CallDispatcher` with balance `B` (e.g., accidental direct transfer by a victim, or leftover dust from a previous user's predispatch swap that produced slightly more `T` than that order required and was never fully swept before the next block).
2. Attacker calls `placeOrder` with:
   - `order.predispatch.assets` = a trivial/cheap asset (or one whose predispatch call yields ~0 of `T`).
   - `order.predispatch.call` = any call that touches `dispatcher` (satisfying the `predispatch.call.length > 0` branch) but need not actually produce `T`.
   - `order.inputs[0] = { token: T, amount: B }` (or any amount ≤ `B`).
3. In the sweep loop, `balance = IERC20(T).balanceOf(dispatcher)` reads `B` (the pre-existing balance, not something the attacker produced), and the transfer call sweeps all of `B` to the gateway [6](#0-5) .
4. `received = B`, and since `received <= order.inputs[0].amount`, `order.inputs[0].amount = received = B` is credited to the attacker's escrowed order [7](#0-6) , funded entirely by the victim's stray tokens rather than the attacker's own funds.
5. The attacker's order proceeds to be filled by a solver, letting the attacker realize the swapped/cross-chain value while having contributed none of the actual input token.
