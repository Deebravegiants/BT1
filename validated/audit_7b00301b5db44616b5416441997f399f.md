### Title
`MessageSigner` ignores the `enabled` flag on wallet accounts, allowing signing with disabled accounts - ([File: features/message-signer/src/module/message-signer.ts])

### Summary
`MessageSigner.signMessage()` resolves a `walletAccount` from `walletAccountsAtom` (the full/unfiltered account map) and only branches signer selection based on `isSoftware` / `isHardware`, never checking the account's `enabled` flag. This mirrors the reported bug class: an entity ("strategy" in the report, "wallet account" here) that a user/owner has explicitly deactivated is still functionally usable downstream because the consuming code validates only a *type/kind* discriminator and ignores the *active/enabled* state.

### Finding Description
`WalletAccount` carries an `enabled` boolean that defaults to `true` and is set to `false` when the user disables an account [1](#0-0) , with the constructor default `enabled = true` [2](#0-1) . Disabling a (non-hardware) account via `WalletAccounts.disableMany()` keeps the account object in the underlying map but flips `enabled` to `false` through `updateWalletAccount` [3](#0-2) [4](#0-3) .

The rest of the SDK treats `enabled` as the authoritative gate: `createEnabledWalletAccountsAtom` filters strictly on `account.enabled` [5](#0-4) , and consumers such as the `enabled` redux selector [6](#0-5)  and the NFTs monitor [7](#0-6)  rely on this atom to exclude disabled accounts from normal wallet operations.

`MessageSigner`, however, is wired directly to the raw `walletAccountsAtom`, not the enabled-filtered atom: `dependencies: ['seedBasedMessageSigner', 'hardwareMessageSigner?', 'walletAccountsAtom']` [8](#0-7) . Its `#normalizeWalletAccount` looks the string name up in that unfiltered map and only asserts the account exists — not that it is enabled [9](#0-8) . `#getMessageSigner` then dispatches purely on `isSoftware` / `isHardware` (the "kind" discriminator), with no reference to `enabled` (the "active" discriminator) at all [10](#0-9) . Both the seed-based signer and hardware signer proceed to derive the key and produce a signature without any `enabled` check [11](#0-10) [12](#0-11) .

This is the direct structural analog of the report: `removeStrategy()` zeroes `active` but downstream `PrimeStrategy` only checks `kind`, so a "removed" strategy is still callable; here, disabling a wallet account zeroes `enabled` but `MessageSigner` only checks `isSoftware`/`isHardware` (kind), so a "disabled" account is still signable.

### Impact Explanation
A disabled software wallet account retains its `seedId`/`index`, so `SeedBasedMessageSigner.signMessage()` will still derive the correct key and produce a valid signature for that account via the keychain, `keychain.signBuffer({ seedId, keyId, ... })` [13](#0-12) . Any caller with access to the `messageSignerApi.messageSigner.signMessage` surface — e.g. a connected dApp/site or SDK integration that only knows the account name string — can obtain signatures attributable to an account the user believed was deactivated/hidden. Message signing (`eth_sign`/`personal_sign`-style flows) is frequently used for authentication, permit/off-chain approvals, and login proofs, so an unauthorized signature over a "disabled" identity is a concrete unauthorized-signing / account-isolation violation, matching the "unauthorized signing" impact category.

### Likelihood Explanation
No privileged access is required beyond whatever normally invokes `messageSigner.signMessage` (a connected dApp, integration, or any caller with the wallet-account name string). Disabling an account is a common, user-initiated action (e.g., hiding an account without removing seed material), so the precondition (an existing disabled account) is easy to reach, and the missing check is a simple, always-reachable code path with no exception handling to catch it.

### Recommendation
In `MessageSigner.#normalizeWalletAccount` (or in `#getMessageSigner`), fetch the account from the enabled-filtered source (or explicitly check `walletAccount.enabled`) and throw if the account is disabled, mirroring the `enabled-wallet-accounts` atom's filter logic used elsewhere in the SDK. At minimum, add an assertion such as `assert(instance.enabled, 'wallet account is disabled')` before returning the resolved account for signing.

### Proof of Concept
1. Create a software wallet account (e.g. `exodus_1`) and disable it: `walletAccounts.disable('exodus_1')`, which sets `enabled: false` while keeping `seedId`/`index` intact [14](#0-13) .
2. Call `messageSignerApi.messageSigner.signMessage({ baseAssetName, message, walletAccount: 'exodus_1' })`.
3. `#normalizeWalletAccount` finds the (still-present, disabled) instance and only asserts it exists [9](#0-8) .
4. `#getMessageSigner` selects `seedBasedMessageSigner` because `isSoftware` is true, irrespective of `enabled` [10](#0-9) .
5. `SeedBasedMessageSigner.signMessage()` derives the key and returns a valid signature for the disabled account [11](#0-10) .
