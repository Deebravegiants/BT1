## Analysis

The reported bug class — a contract accepting `msg.value` payment for a fee, but failing to return unspent excess to the caller, resulting in permanent fund loss — has a direct, reachable analog in `EvmHost.sol`'s native-token fee payment path.

### Title
Excess native token sent to `EvmHost.dispatch`/`fundRequest` is trapped in the contract instead of being refunded to the caller - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` accept native token (`msg.value`) as payment for the protocol fee, swapping it to `feeToken()` via Uniswap V2's `swapETHForExactTokens`. Uniswap's router refunds any unused ETH to its immediate caller — which is `EvmHost` itself, not the original `msg.sender` who dispatched the request. `EvmHost` never forwards this refunded excess back to the user, and there is no sweep/withdraw function for stray native ETH in the contract, so any overpayment is permanently locked in the `EvmHost` contract balance.

### Finding Description

the same unrefunded-excess pattern also appears in `dispatch(DispatchGet memory get)`: [2](#0-1)

In each case, `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(fee, path, address(this), block.timestamp)` is called. Per the UniswapV2 router's implementation, if `msg.value` exceeds the ETH required to acquire `fee` units of `feeToken`, the router refunds the surplus ETH to its caller (`msg.sender` of the swap call), which is `EvmHost` — not the end user who called `dispatch`/`fundRequest` on `EvmHost`. `EvmHost` contains no logic afterward to forward that refunded surplus to `_msgSender()`, and the file ends at `evm/src/core/EvmHost.sol` line 1078 with no `receive()`/withdraw function that would let anyone recover stray native ETH held by the contract [4](#0-3) .

This is exactly the flaw described in the external report: a fee-paying entry point that requires "at least" a certain payment but silently keeps any excess instead of returning it to the payer.

Notably, the codebase already recognizes this exact bug class and fixes it elsewhere: `IntentGatewayV2.placeOrder` performs its own Uniswap swap and explicitly tracks `msgValue -= amounts[0]` then refunds any leftover to the caller [5](#0-4) , and `ExtrinsicIntents._fill*` explicitly refunds unspent native tokens to the solver [6](#0-5) . `EvmHost.dispatch`/`fundRequest`, which is the lower-level primitive that these and other apps (e.g. `HyperbridgeLzEndpoint.send`, which forwards raw `msg.value` directly into `IDispatcher(_host).dispatch{value: msg.value}(request)` [7](#0-6) ) call into, lacks this same refund logic.

### Impact Explanation
Any user or integrating contract (e.g. `HyperbridgeLzEndpoint`, or any `HyperApp`-based contract following the documented "Native Token Payment" pattern of forwarding `msg.value` directly to `IDispatcher(host).dispatch{value: msg.value}(post)` [8](#0-7) ) who overestimates the required native fee — which is expected given Uniswap slippage/price movement between off-chain quoting and on-chain execution, and given the documentation's own warning that native fee estimates are only "approximate (subject to slippage)" [9](#0-8)  — will have their excess ETH permanently and irrecoverably locked in `EvmHost`. This is a direct, permanent loss of user funds with no recovery path, reachable from a single `dispatch`/`fundRequest` transaction.

### Likelihood Explanation
High likelihood: `dispatch`/`fundRequest` are core, frequently used entry points for any cross-chain message dispatch paying in native token, and the documentation explicitly instructs developers to forward `msg.value` directly without any client-side exact-amount guarantee, relying on the Host to "swap and refund" — the swap happens, but the refund never reaches the user. Any minor overestimation of gas/fee by a caller (a common, non-malicious scenario) triggers the loss.

### Recommendation
After the `swapETHForExactTokens` call in `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest`, capture the returned `amounts[0]` (actual ETH spent) and refund `msg.value - amounts[0]` back to `_msgSender()`, mirroring the pattern already used in `IntentGatewayV2` and `ExtrinsicIntents`.

### Proof of Concept
1. User calls `IDispatcher(host).dispatch{value: X}(post)` where `X` is intentionally or accidentally larger than the ETH actually required to purchase `post.fee` units of `feeToken` via Uniswap (e.g. due to slippage buffer or stale off-chain quote).
2. Inside `EvmHost.dispatch`, `swapETHForExactTokens{value: X}(post.fee, path, address(this), block.timestamp)` is invoked; the Uniswap router spends only the ETH needed and refunds the remainder to its caller, `EvmHost`.
3. `EvmHost`'s ETH balance increases by the refunded amount; no code path returns this to the user.
4. Repeat for any user of `dispatch`/`fundRequest`; excess ETH accumulates in `EvmHost` with no withdrawal mechanism, permanently locking user funds.

### Native Token Payment

For native token payments, dispatch directly and let the Host handle the Uniswap swap:

```solidity lineNumbers title="MyApp.sol"
contract MyApp is HyperApp {
    function sendMessageWithNative(
        bytes memory message,
        bytes memory dest,
        uint64 timeout,
        address to,
        uint256 relayerFee
    ) public payable returns (bytes32) {
        DispatchPost memory post = DispatchPost({
            body: message,
            dest: dest,
            timeout: timeout,
            to: abi.encode(to),
            fee: relayerFee,
            payer: msg.sender
        });
        
        // User must send enough native tokens to cover fees
        // The Host will swap native -> feeToken via Uniswap
        return IDispatcher(host()).dispatch{value: msg.value}(post);
    }
}
```

```text
### Payment Method Comparison

| Feature | Native Token | FeeToken (Recommended) |
|---------|-------------|------------------------|
| **Gas Cost** | Higher (includes swap) | Lower (no swap) |
| **Slippage** | Yes (Uniswap swap) | No |
| **Fee Calculation** | Approximate (subject to slippage) | Exact |
| **Token Approval** | Not required | Required  |
| **User Convenience** | High (users have native tokens) | Low (users need feeToken) |
| **Best For** | One-off transactions, user-facing apps | Frequent dispatches, cost optimization |
```
