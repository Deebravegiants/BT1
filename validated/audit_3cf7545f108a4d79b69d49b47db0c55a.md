### Title
`handleOut` sends CASE 1 wallet-authorized proceeds to `msg.sender` instead of `stack.signerAddress` - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
`EmporiumUpgradeable.handleOut` transfers `balanceChange` unconditionally to `msg.sender`, while `verifyWallet` only checks that the EIP-712 signature recovers to `stack.signerAddress` — it never checks `msg.sender == stack.signerAddress`. This lets anyone front-run a victim's already-signed `EmporiumStack` bytes, submit them as their own `transact` call, let the CASE 1 `invokeWallet` operation correctly execute against the victim's `HinkalWallet`, and then walk away with the resulting token proceeds and the newly minted UTXO's stealth address.

### Finding Description
The broken equality is: **the recipient of `balanceChange` in `handleOut`** should equal **the address whose EIP-712 signature authorized the `invokeWallet` operation (`stack.signerAddress`)**, but instead equals **`msg.sender`, the caller of the enclosing `transact`/`runAction` call**.

Code path:
- `verifyWallet` (`EmporiumUpgradeable.sol:302-349`) verifies only `recoveredAddress == stack.signerAddress` for the EIP-712 hash over `emporiumMessage`, `ops`, `maxFee`, `deadline`. Nothing in this function, nor anywhere else in `runAction`, ties `msg.sender` to `stack.signerAddress`.
- In `runAction` (`EmporiumUpgradeable.sol:76-160`), CASE 1 (`op.invokeWallet && stack.signerAddress != address(0)`) calls `IHinkalWallet(stack.signerAddress).callHinkalWallet(...)` — this correctly executes against the victim's wallet using the victim's authorization.
- After the ops run, `handleOut` (`EmporiumUpgradeable.sol:162-184`) computes `balanceChange` and does:
```solidity
transferERC20TokenOrETH(circomData.erc20TokenAddresses[i], msg.sender, uint256(balanceChange));
outUtxo = UTXO(uint256(balanceChange), circomData.erc20TokenAddresses[i], circomData.stealthAddressStructure, circomData.timeStamp);
```
Real tokens go to `msg.sender`, and the shielded UTXO record uses `circomData.stealthAddressStructure`, which is an arbitrary field supplied by the caller of `transact` (constrained only by the caller's own proof for their own UTXOs), not derived from or bound to `stack.signerAddress`.

Since `EmporiumStack` (`v`, `r`, `s`, `signerAddress`, `ops`, `maxFee`, `deadline`) is just `bytes` embedded in `circomData.externalActionData.externalActionMetadata`, whoever holds the signed bytes (visible once broadcast/relayed) can wrap them in their own `transact` call with their own `circomData` (their own `stealthAddressStructure`, `erc20TokenAddresses`, and proof) and become `msg.sender`. `performHinkalChecks`, `onlyAllowedRecipient`, `verifyProof`, nullifier/root checks all validate the caller's own proof/circuit correctness for their own UTXO deltas — none of them constrain that the CASE 1 wallet proceeds must flow back to `stack.signerAddress`.

### Impact Explanation
This is direct theft of shielded/authorized funds: a victim who signs an `EmporiumSignature` intending to reclaim reward/withdrawal proceeds through their own subsequent shielded deposit can have those proceeds physically transferred to an attacker's address and shielded under the attacker's own stealth address, with the victim receiving nothing. This matches the Critical impact category ("direct theft of shielded or in-flight user funds ... executing calls or moving assets a wallet owner or prover never authorised" for the fund-destination aspect) since the wallet owner authorized the *operation* but never authorized *who receives the proceeds*. The attack is repeatable against any victim who broadcasts a signed `EmporiumStack` for a CASE 1 operation before it is mined.

### Likelihood Explanation
Preconditions are realistic: a victim must sign a valid `EmporiumSignature` for a CASE 1 (`invokeWallet`) operation and have the signed bytes become visible before inclusion (mempool, relay, or any off-chain channel where the signed stack transits before the victim's own `transact` call lands). The attacker only needs to be an ordinary EOA capable of calling `Hinkal.transact` with their own valid proof/`circomData` — no privileged role is required. Attacker cost is only gas plus generating their own valid proof; the payoff is the full value of the victim's authorized withdrawal, making this highly attractive and repeatable per signed stack observed.

### Recommendation
Bind the recipient of `handleOut`'s transfer (and the resulting UTXO's ownership) to `stack.signerAddress` (or a value the signer explicitly committed to receiving) rather than `msg.sender`, and/or include `msg.sender` (or an explicit designated relayer commitment) inside the EIP-712 signed payload so the signer can restrict who is allowed to execute the stack and where proceeds go.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalWallet` for `victim`, `EmporiumUpgradeable`, a reward-token mock endpoint.
2. `victim` signs an `EmporiumSignature` (`v,r,s` over `emporiumMessage`, one CASE 1 `invokeWallet` op calling the reward endpoint, `maxFee`, `deadline`) with `stack.signerAddress = victim`'s `HinkalWallet`.
3. `attacker` (different EOA, never the victim) builds their own `circomData` (their own `stealthAddressStructure`, `erc20TokenAddresses` set to the reward token, valid proof for their own dummy in/out UTXOs) embedding the victim's signed `stack` bytes as `externalActionMetadata`, and calls `Hinkal.transact` as `msg.sender = attacker`.
4. Assert: reward token balance of `attacker` increases by the reward amount (via `transferERC20TokenOrETH(..., msg.sender, balanceChange)`), and the emitted/minted `outUtxo.stealthAddressStructure` equals `attacker`'s stealth address — i.e., `outUtxo` recipient ≠ `stack.signerAddress`/victim, and `victim`'s `HinkalWallet` balance decreased with `victim` receiving none of the proceeds.
5. Compare against expected equality `handleOut recipient == stack.signerAddress`: assert it does NOT hold, confirming the break.
