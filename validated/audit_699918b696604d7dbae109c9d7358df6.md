## Title
Webhook HMAC only covers the raw body, not the `shop`/`topic`/`webhook_id` headers — enables cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook request as authentic Shopify traffic solely because `Utils::HmacValidator.validate` succeeds, but the HMAC signature is computed only over the raw request body. The `shop-domain`, `topic`, `webhook-id` and `api-version` header values are read unauthenticated and handed straight to the app's handler as trusted tenant-identifying metadata, breaking the binding `verified_bytes == identity_acted_on`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all sourced directly from HTTP headers with no cryptographic binding to that body: [2](#0-1) 

`HmacValidator.validate`/`validate_signature` compute and compare the HMAC exclusively against `verifiable_query.to_signable_string`, i.e. the body: [3](#0-2) 

`Registry.process` gates all further action on that single HMAC check, then constructs `WebhookMetadata` from the unauthenticated header values and forwards it to the app's handler as if it were verified: [4](#0-3) 

The gem's own documentation instructs apps to use `data.shop` as the tenant key when enqueuing work (`perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) and states that `process` "will verify the request did indeed come from Shopify," implying the whole payload — including `shop` — is authenticated: [5](#0-4) [6](#0-5) 

**Binding that is broken:** the gem implicitly claims `hmac_verified(bytes) ⇒ shop_header == originating_shop`, but in reality `hmac_verified(bytes)` only proves `bytes == raw_body`; `shop_header` is parsed, never verified.

Because the HMAC secret (`api_secret_key`) is per-app, not per-shop, any merchant who installs the same public app on their own store legitimately receives real webhook deliveries (correct body + correct HMAC) from Shopify. That merchant — an "unprivileged" party with respect to any other tenant of the same app — can capture one such `(raw_body, hmac)` pair and replay it to the app's webhook endpoint while substituting the `shopify-shop-domain` (and/or `shopify-topic`, `shopify-webhook-id`) header with an arbitrary victim shop's domain. `HmacValidator.validate` still passes (body/HMAC unchanged), and `Registry.process` calls the handler with `WebhookMetadata` claiming the payload belongs to the victim shop.

### Impact Explanation
This is a cross-tenant identity spoofing vector: an attacker who is a legitimate (but unprivileged w.r.t. other tenants) user of the app can make the host application believe arbitrary webhook data originates from a shop they do not own/control. Depending on how the host app trusts `data.shop` (session/record lookup, job enqueuing keyed by shop, data writes), this can lead to cross-tenant data corruption, spoofed business events being attributed to another merchant, or triggering shop-scoped side effects (e.g., billing, fulfillment, notification jobs) against a victim tenant. This matches the "Critical - cross-tenant access" impact category, since the gem's own API surface (`WebhookMetadata#shop`) is the mechanism host apps are told to rely on for tenant identification, and that value is unauthenticated by design of the current signature scope.

### Likelihood Explanation
Reasonably likely wherever the app is public/multi-tenant: any user can install the app on a shop they control to harvest a valid `(body, hmac)` pair without needing `api_secret_key`, an access token, or any privileged access — only the ability to receive their own app's webhooks and replay an HTTP POST with modified headers to the app's public webhook endpoint.

### Recommendation
Bind the trust decision to all fields the application acts on, not just the body:
- Include `shop-domain`, `topic`, and `webhook-id` in the signable string used for HMAC computation/verification (this requires coordinating with how Shopify signs webhooks — if Shopify's HMAC truly only covers the body, the gem must not present `shop`/`topic`/`webhook_id` as verified/trusted fields), or
- At minimum, update documentation so it does not describe `process` as verifying that "the request did indeed come from Shopify" for the header-derived fields, and require host apps to independently correlate the delivered `shop` against a known/expected shop (e.g. cross-check against `webhook_id` uniqueness plus a shop the app has an active session for) before acting on it.

### Proof of Concept
1. Attacker installs the target public app on their own store `attacker-shop.myshopify.com` and lets it receive a normal webhook, e.g. `orders/create`.
2. Attacker's server captures the raw POST: headers `x-shopify-hmac-sha256: <H>`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: orders/create`, and body `B`.
3. Attacker sends a new POST to the app's public webhook endpoint with the same body `B` and same `x-shopify-hmac-sha256: <H>`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` builds successfully (only checks header presence, not shop legitimacy) — see `lib/shopify_api/webhooks/request.rb` lines 45-63.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only hashes `B` — see `lib/shopify_api/webhooks/registry.rb` line 190 and `lib/shopify_api/utils/hmac_validator.rb` lines 26-31.
6. The registered handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: "orders/create", body: parsed(B), ...)`, and the host app (per the gem's documented pattern) performs shop-scoped work keyed on the forged `victim-shop.myshopify.com` value.

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
```

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
