Found it: `Webhooks::Request#shop` reads the shop identity from the unauthenticated `X-Shopify-Shop-Domain` header, while the HMAC signature (`hmac`) only covers `@raw_body` — the shop-domain header is never part of the signed bytes.

### Title
Webhook shop identity is taken from an unauthenticated header not covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` exposes a `shop` accessor that is read directly from the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) HTTP header, but the HMAC verification performed via `Utils::HmacValidator`/`VerifiableQuery` only signs `to_signable_string`, which returns the raw request body [1](#0-0) . The `shop` field used to attribute the webhook to a tenant is never part of the signed bytes.

### Finding Description
`Request#shop` is defined as:
```ruby
def shop
  T.cast(shopify_header("shop-domain"), String)
end
``` [2](#0-1) 

and `shopify_header` just reads straight from the caller-supplied `headers` hash with no cross-check against any signed value:
```ruby
def shopify_header(name)
  @headers["shopify-#{name}"] || @headers["x-shopify-#{name}"]
end
``` [3](#0-2) 

Meanwhile, `to_signable_string` (used by `Utils::HmacValidator.validate` through the `VerifiableQuery` interface) only returns `@raw_body`:
```ruby
def to_signable_string
  @raw_body
end
``` [4](#0-3) 

and `HmacValidator.validate_signature` computes the HMAC purely over that signable string with the app's secret and compares it to the `hmac` header value [5](#0-4) .

The identity binding that should hold is:
`shop used by the application to route/attribute the webhook == shop bound inside the HMAC-verified bytes`

In this code, that equality does not hold: the HMAC only proves that "some entity possessing the shared secret produced this raw body," while the `shop` value the host application will use to look up which merchant's data/webhook handler to invoke comes from a header that carries zero cryptographic binding to the signature. `Registry.process` (the caller of this class, in `lib/shopify_api/webhooks/registry.rb`) validates the HMAC and then dispatches the handler for `request.topic`, passing `request` (with attacker-controlled `shop`) to the handler; downstream consumers commonly key their persistence/session lookups off `request.shop`.

### Impact Explanation
An unprivileged internet user who can send a POST to the app's webhook endpoint with an arbitrary `X-Shopify-Shop-Domain` header, while replaying or forging a body whose HMAC happens to validate (e.g. by using a body they legitimately received a valid signature for from Shopify for their own shop, or via any scenario where the raw body's HMAC is satisfied), can cause the request to be attributed to a different shop domain than the one it was actually signed for. Because the shop domain is not part of the signed content, the "identity" of the tenant is effectively attacker-controlled data layered on top of a signature that says nothing about which shop the payload belongs to. This breaks the tenant-isolation guarantee webhook consumers rely on, and can lead to cross-tenant data being applied against the wrong shop's stored session/data (Critical impact: cross-tenant access), matching the class of "field acted on but not covered by the HMAC."

### Likelihood Explanation
Exploitability requires the attacker to control or reuse a raw body whose HMAC is valid (trivially possible if a shop owner receives webhooks for their own shop and only needs to change the shop-domain header value on a replayed/forwarded payload before the app's endpoint) — no possession of `api_secret_key` is required, only knowledge of one valid `(body, hmac)` pair that they can obtain honestly (e.g. from any webhook fired for their own shop) and a manipulated header. This is a straightforward, no-privilege manipulation of an HTTP header on an inbound webhook request.

### Recommendation
Bind the shop domain into the signed payload verification: either require the host application to independently verify `shop-domain` against a known, previously provisioned shop record (not simply trusting the header), or extend `to_signable_string` in a way that Shopify's signing process also covers, and document that `Request#shop` must never be used as a trust boundary by itself — it should be cross-checked against the `Auth::Session`/stored shop associated with the api client making the OAuth exchange rather than trusted directly from the header.

### Proof of Concept
1. Attacker has a legitimately received webhook payload+HMAC pair for `shop-a.myshopify.com` (any shop they control), or can otherwise produce a body whose HMAC is currently valid.
2. Attacker sends this raw body and the valid `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, but replaces the `X-Shopify-Shop-Domain` header with `shop-b.myshopify.com`.
3. `Registry.process` calls `HmacValidator.validate(request)`, which succeeds because it only checks the raw body against the HMAC [6](#0-5) .
4. The registered handler receives `request` with `request.shop == "shop-b.myshopify.com"` even though the HMAC never attested to that shop, letting the attacker attribute a validly-signed payload to an arbitrary target tenant.
