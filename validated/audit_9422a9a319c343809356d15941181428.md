## Title
`Oauth.begin_auth` fails to validate the `shop` domain before sending it the app's OAuth `client_id`/redirect URI, unlike every other credential-sending flow in the gem - ([File: lib/shopify_api/auth/oauth.rb])

### Summary
Every code path in this gem that sends the app's `client_secret` to a shop-controlled host (`ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, and the `dest` claim consumption in `TokenExchange.exchange_token`/`JwtPayload`) first passes the `shop` value through `Utils::ShopValidator.sanitize!`, which restricts the host to `TRUSTED_SHOPIFY_DOMAINS`. `Oauth.begin_auth`, however, builds the authorization redirect URL directly from the caller-supplied `shop` string with no call to `ShopValidator` at all.

### Finding Description
`ClientCredentials.client_credentials` and `RefreshToken.refresh_access_token` both call `Utils::ShopValidator.sanitize!(shop)` before constructing a `Session` and issuing a request that contains `client_id`/`client_secret` in the body: [1](#0-0) [2](#0-1) 

`ShopValidator.sanitize!` enforces that the resulting host belongs to `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`), raising `Errors::InvalidShopError` otherwise: [3](#0-2) [4](#0-3) 

By contrast, `Oauth.begin_auth` takes the `shop:` argument as-is and interpolates it directly into `auth_base_uri(shop)`, with no sanitization step: [5](#0-4) [6](#0-5) 

The bug-class analogy to the reported ChainLink issue is: a field (`shop`) is *acted upon* (used to build the trust boundary — the host that will receive the app's `client_id`, `scope`, and `redirect_uri`) but is not *covered* by the same binding/validation (`ShopValidator`) that every sibling function in the same module applies to the same conceptual field. The equality that should hold — `shop_used_to_build_request_host == shop_validated_against_TRUSTED_SHOPIFY_DOMAINS` — is broken specifically in `begin_auth`.

Note: this differs from the OAuth *callback* path (`validate_auth_callback`), where `auth_query.shop` is bound by Shopify's HMAC signature over `code/host/shop/state/timestamp` computed with `api_secret_key`, so an anonymous attacker cannot forge that value without knowing the secret. `begin_auth`'s `shop` parameter has no such binding at all — it is the *first* value the flow ever sees, coming straight from application input.

### Impact Explanation
If a host application passes user-controllable input into `begin_auth(shop:, ...)` (which the gem's own documented example does — `shop = request.headers["Shop"]` then directly passed to `begin_auth`, with no sanitization shown or mentioned anywhere in `docs/usage/oauth.md`), an unprivileged internet user can supply an arbitrary `shop` value (e.g. `attacker.example`). The resulting `auth_route` becomes `https://attacker.example/admin/oauth/authorize?client_id=...&scope=...&redirect_uri=...&state=...`, redirecting the victim's browser to an attacker-controlled host and disclosing the app's `client_id`, the configured `scope`, and the app's `redirect_uri` (its callback path/host) to that attacker-controlled endpoint together with the CSRF nonce (`state`). This does not itself leak `client_secret` (the secret is only sent from `validate_auth_callback`, which is HMAC-bound), so the impact is bounded to information disclosure / forced-redirect rather than direct credential theft, but it is inconsistent with the trust boundary the gem otherwise enforces uniformly in `ClientCredentials`, `RefreshToken`, and `TokenExchange`.

### Likelihood Explanation
Exploitability depends entirely on whether the host application passes unsanitized user input as `shop` to `begin_auth` — which is exactly the pattern shown in the gem's own README/doc example (`shop = request.headers["Shop"]`). Given the gem enforces `ShopValidator.sanitize!` in three of its four shop-consuming OAuth flows, the omission in `begin_auth` looks unintentional and is the weakest link in an otherwise consistently-enforced boundary.

### Recommendation
Call `Utils::ShopValidator.sanitize!(shop)` (or `sanitize_shop_domain`) at the top of `Oauth.begin_auth`, before `auth_base_uri(shop)` is constructed, mirroring the validation already performed in `ClientCredentials.client_credentials` and `RefreshToken.refresh_access_token`.

### Proof of Concept
1. Host app exposes a login route that reads `shop` from an unauthenticated request parameter/header and calls:
   ```ruby
   ShopifyAPI::Auth::Oauth.begin_auth(shop: params[:shop], redirect_path: "/auth/callback")
   ```
2. Attacker sends the victim a link that hits this route with `shop=attacker.example`.
3. `begin_auth` builds `auth_route = "https://attacker.example/admin/oauth/authorize?client_id=<APP_CLIENT_ID>&scope=<SCOPES>&redirect_uri=https://<APP_HOST>/auth/callback&state=<NONCE>"` — see `auth_base_uri`: [6](#0-5) 
4. The victim's browser is redirected (307) to `attacker.example`, leaking `client_id`, `scope`, `redirect_uri`, and `state` to the attacker's server, with no `ShopValidator` check anywhere in this call path to prevent it.

```ruby
        def begin_auth(shop:, redirect_path:, is_online: true, scope_override: nil)
          scope = if scope_override.nil?
            ShopifyAPI::Context.scope
          elsif scope_override.is_a?(ShopifyAPI::Auth::AuthScopes)
            scope_override
          else
            ShopifyAPI::Auth::AuthScopes.new(scope_override)
          end

          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = SecureRandom.alphanumeric(NONCE_LENGTH)

          cookie = SessionCookie.new(value: state, expires: Time.now + 60)

          query = {
            client_id: ShopifyAPI::Context.api_key,
            scope: scope.to_s,
            redirect_uri: "#{ShopifyAPI::Context.host}#{redirect_path}",
            state: state,
            "grant_options[]": is_online ? "per-user" : "",
          }

          query_string = URI.encode_www_form(query)
          auth_route = auth_base_uri(shop) + "/oauth/authorize?#{query_string}"

          { auth_route: auth_route, cookie: cookie }
        end
```

```ruby
        def auth_base_uri(shop)
          return "https://#{shop}/admin" unless defined?(DevServer) && shop.include?(".my.shop.dev")

          # For first-party apps in development only, we leverage DevServer to build the admin base URI
          admin_web = T.unsafe(Object.const_get("DevServer")) # rubocop:disable Sorbet/ConstantsFromStrings
            .new("admin-web")
          admin_host = admin_web.host!(nonstandard_host_prefix: "admin")
          shop_name = shop.split(".").first

          "https://#{admin_host}/store/#{shop_name}"
        end
```
