### Title
Webhook `shop` identity is trusted from an unauthenticated header while the HMAC only signs the request body, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body alone, while the `shop` (tenant identity) is read from an HTTP header that is never included in that signable content. `Registry.process` validates the HMAC and then unconditionally trusts `request.shop` to build the `WebhookMetadata` passed to the app's handler. This breaks the intended binding `HMAC-verified bytes == identity used by the handler`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is parsed straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header, completely outside of what is signed: [2](#0-1) [3](#0-2) 

`Utils::HmacValidator.validate` only ever checks `verifiable_query.to_signable_string` against `verifiable_query.hmac`, so it validates knowledge of the body/secret but says nothing about the `shop` field: [4](#0-3) 

`Registry.process` raises only if the HMAC fails, then immediately forwards the unauthenticated `request.shop` value to the app's handler as the tenant identity: [5](#0-4) 

The equality the code implicitly assumes is:
`shop used by handler (request.shop, unauthenticated header) == shop the HMAC-signed body actually belongs to`

That equality does not hold: the HMAC secret (`api_secret_key`) is per-application, shared across every shop that installs the app, not per-shop. Any shop that installs the app can capture a legitimately-signed `(raw_body, hmac)` pair from its own genuine webhook deliveries (e.g. by placing a test order in its own store to trigger `orders/create`), then replay that exact body+HMAC to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header value naming a victim shop. `HmacValidator.validate` still succeeds because the signature check never touched the shop header, and `Registry.process` hands the handler a `WebhookMetadata` claiming the victim's `shop` with attacker-controlled `body`.

### Impact Explanation
This is a cross-tenant boundary break: an attacker who legitimately installs the app on their own store (unprivileged with respect to any other merchant) can make the host application process attacker-chosen webhook payloads under a different merchant's `shop` identity. Depending on how the host app's `WebhookHandler` uses `data.shop` (commonly used as the tenant/session lookup key to load a store's access token or update its records), this can lead to writing forged data into another tenant's records, triggering tenant-scoped side effects (e.g., `customers/redact`, `orders/create` handling, cache/DB updates) attributed to the wrong shop — a cross-tenant access impact.

### Likelihood Explanation
Requires only an app installation on any single shop (something any user of the target Shopify app can do for their own store) and the ability to send an arbitrary HTTP POST to the app's public webhook endpoint with a modified `x-shopify-shop-domain` header while replaying a previously captured valid raw body + HMAC pair generated by Shopify for that attacker's own store. No access token, `client_secret`, or privileged account is required.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`/`api_version`) claim into the HMAC-signable content, or have `Registry.process`/handlers independently verify that the `shop` header corresponds to a shop with an active, previously-established session/installation before trusting it, rather than relying solely on body-only HMAC validation to authorize the claimed tenant identity.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`.
2. Attacker triggers a real webhook (e.g. `orders/create`) from Shopify to the app; captures the raw POST body and the valid `x-shopify-hmac-sha256` header Shopify computed with the app's shared `api_secret_key`.
3. Attacker replays that exact `(body, hmac)` to the same app webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` and `x-shopify-topic`/`x-shopify-webhook-id` as desired.
4. `ShopifyAPI::Webhooks::Request.new` parses `shop` as `victim-shop.myshopify.com`.
5. `Utils::HmacValidator.validate` succeeds because it only checks the raw body against the shared secret — see `lib/shopify_api/utils/hmac_validator.rb:12-31` and `lib/shopify_api/webhooks/request.rb:35-38`.
6. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: attacker_controlled_body, ...))`, causing the host app to act on attacker data under the victim tenant's identity — `lib/shopify_api/webhooks/registry.rb:188-200`.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
