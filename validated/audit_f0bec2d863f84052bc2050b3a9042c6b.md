### Title
Webhook shop identity is never covered by the HMAC signature, enabling cross-tenant webhook spoofing/replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop`, `topic`, `webhook_id`, and `api_version` values used for tenant/event dispatch purely from unauthenticated HTTP headers, while the HMAC signature that `Utils::HmacValidator` checks only covers the raw request body. Because the app's `api_secret_key` is shared across every shop that has installed the app, a valid HMAC over a body only proves the body was signed by the app's secret at some point — it proves nothing about which shop it came from. An attacker who can replay or forward a previously captured, validly-signed webhook body can substitute an arbitrary `shop-domain` header and have the registry dispatch it as if it belonged to a different merchant.

### Finding Description
`Request#to_signable_string` returns only the raw body: [1](#0-0) 

Meanwhile `shop`, `topic`, and `webhook_id` are parsed straight out of headers with no cryptographic binding to that body: [2](#0-1) 

`Utils::HmacValidator.validate` only verifies `verifiable_query.to_signable_string` (i.e., the body) against the computed HMAC — it never incorporates `shop`, `topic`, or `webhook_id` into the signed data: [3](#0-2) 

`Registry.process` validates only that HMAC, then unconditionally trusts `request.shop`, `request.topic`, and `request.webhook_id` to build the `WebhookMetadata` handed to the app's handler: [4](#0-3) 

`WebhookMetadata.shop` is the field host applications are expected to use to attribute the event to a tenant/merchant: [5](#0-4) 

The broken identity binding is: **"shop the HMAC was validated for" (any shop, since the secret is shared app-wide) ≠ "shop asserted by the unauthenticated `shop-domain`/`x-shopify-shop-domain` header that the caller controls."** Since `HmacValidator.validate` never binds the signature to the shop, topic, or webhook id, any request with a previously-observed valid `(body, hmac)` pair can be replayed with an arbitrary `shop-domain`, `topic`, or `webhook-id` header and will still pass validation.

### Impact Explanation
This is a cross-tenant confusion vector: an app that keys per-shop state (e.g., updates order/inventory/customer state keyed by `data.shop`) on the `WebhookMetadata#shop` value supplied by this gem can be made to apply shop-A's webhook body to shop-B's tenant record, since the library asserts the HMAC as proof of authenticity for the whole `WebhookMetadata` struct while only the body was actually verified. This matches the "cross-tenant access" Critical impact category, since it lets a party in possession of one legitimately-signed webhook delivery reattribute its data to a different merchant/tenant recognized by the host app.

### Likelihood Explanation
Exploitation requires the attacker to obtain at least one valid `(raw_body, hmac)` pair delivered for the app (e.g., from a webhook they can observe/intercept, a forwarding proxy, or their own shop's install using the same app secret), then resend it to the app's webhook endpoint with a forged `shop-domain`/`topic`/`webhook-id` header. No knowledge of `api_secret_key` is required because the existing valid signature is reused verbatim — only headers are altered, and `HmacValidator` never inspects them.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signed/verified material (or otherwise cryptographically bind them to the payload, e.g., via a nonce/timestamp+shop-scoped check as Shopify's platform already ties delivery to a specific shop subscription) before trusting these fields in `WebhookMetadata`. At minimum, document clearly that `WebhookMetadata#shop`/`topic`/`webhook_id` are unauthenticated and must be independently cross-checked by host applications (e.g., against the shop's known webhook subscription id) before being used as a tenant key.

### Proof of Concept
1. Attacker captures one legitimately delivered webhook HTTP request for `shop-a.myshopify.com` (raw body `B`, header `x-shopify-hmac-sha256: H`), where `H = HMAC-SHA256(api_secret_key, B)`.
2. Attacker sends a new POST to the app's webhook endpoint with the same body `B` and the same `H`, but sets `x-shopify-shop-domain: shop-b.myshopify.com` (and/or a different `x-shopify-topic`/`x-shopify-webhook-id`).
3. `Webhooks::Request.new` parses the forged headers with no validation against the body: [6](#0-5) 
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC-SHA256(api_secret_key, B)` and compares it to `H` — it matches, because the shop header is not part of the signed string: [7](#0-6) 
5. The handler receives `WebhookMetadata` with `shop: "shop-b.myshopify.com"` and the body originally meant for `shop-a`, causing the host application to process shop-A's data under shop-B's tenant context.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

        def validate(verifiable_query)

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
