### Title
Webhook `shop-domain` header is trusted for tenant identification but is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body [1](#0-0) , and `HmacValidator.validate` verifies the HMAC exclusively against that signable string [2](#0-1) . However, `Registry.process` extracts the tenant-identifying `shop` value from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header — a field that is completely outside the HMAC-signed payload — and passes it straight to the app's handler as the authoritative tenant identifier: [3](#0-2) . The `shop` accessor itself simply reads the unauthenticated header [4](#0-3) .

This is the same bug class as the external report: a value used to make a security-relevant decision (`data.shop`, analogous to `globalIC`'s stale collateral figures used for `lpCut`) is derived from data that is not bound/committed by the authentication mechanism actually checked (`hmac` over body only, analogous to `syncGlobalCollateral` not being called before `handleProfit`). The equality that should hold — "shop authenticated == shop used for tenant routing" — is broken: the shop value that passes the cryptographic check (the body) is not the shop value the host application acts on (the header).

The gem's own documentation instructs consumers to treat `data.shop` as trustworthy for tenant routing/dispatch: `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)` [5](#0-4) , with no guidance to cross-check it against a known/installed-shop list.

### Impact Explanation
An attacker who legitimately controls one shop where the app is installed can capture a genuine Shopify webhook delivery (valid raw body + valid HMAC for that body, since Shopify only signs the body) and replay it to the app's webhook endpoint with the `x-shopify-shop-domain` header altered to name a different (victim) shop that also has the app installed. `Registry.process` will pass HMAC validation (body/HMAC unchanged and genuinely valid) and will hand the handler a `WebhookMetadata` whose `shop` is the attacker-forged victim domain [6](#0-5) . If the host app uses this `shop` value to look up the tenant's session/access token or to route/write data (as the documented example does), this results in cross-tenant data confusion/injection — the attacker's payload is processed and stored under a victim shop's identity. This matches the report's Critical/High criteria for cross-tenant access.

### Likelihood Explanation
This requires no privileged credentials — only an attacker-controlled Shopify store that has installed the target app (a common pattern for public apps), plus knowledge/observation of the shop domain of a co-tenant on the same webhook endpoint. Because this mirrors Shopify's real-world webhook signing behavior (HMAC over body only) and the gem does nothing beyond that, any host app that follows the documented pattern literally is exposed. Likelihood is elevated because the gem's own usage docs actively encourage the vulnerable pattern.

### Recommendation
Either (a) have `Registry.process`/`WebhookHandler` require the caller to supply the expected/authorized shop (e.g., matched against a stored install/session record) before dispatching, or (b) clearly document and enforce that `data.shop` must never be used as an authorization/tenant boundary without independently verifying it against the app's own list of installed shops, and provide a built-in helper to perform that check so host apps are not left inferring tenant identity from an unauthenticated header.

### Proof of Concept
1. App installs on `attacker-shop.myshopify.com` and `victim-shop.myshopify.com`.
2. Shopify sends a legitimate webhook to the app for `attacker-shop.myshopify.com`: body `B`, header `x-shopify-shop-domain: attacker-shop.myshopify.com`, header `x-shopify-hmac-sha256: HMAC(secret, B)`.
3. Attacker replays the same request to the app's webhook endpoint, only changing `x-shopify-shop-domain` to `victim-shop.myshopify.com`; `HMAC(secret, B)` remains valid because HMAC is computed over `B` only (see `to_signable_string` at `lib/shopify_api/webhooks/request.rb:35-38`).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes, then invokes the handler with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", ...)` [3](#0-2) .
5. The host app (following the documented pattern) processes/stores attacker-controlled body content under `victim-shop.myshopify.com`.
