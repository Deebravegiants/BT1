### Title
Asymmetric decimal-scaling in `convert_to_erc20`/`convert_to_balance` allows unbacked minting across the HFT bridge - (File: `modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
`pallet-hyper-fungible-token`'s decimal-conversion helpers only ever handle the case where the EVM-side (`erc_decimals`) precision is *greater than* the local pallet precision (`local_decimals`). When the reverse holds — a locally registered asset has more decimal places than the ERC20/ERC6160 asset it is paired with on the remote EVM chain — both helper functions silently fall back to a no-op scale factor of `10^0 = 1` instead of correctly scaling in the opposite direction.

### Finding Description
The scaling helpers are: [1](#0-0) 

Both `convert_to_balance` and `convert_to_erc20` compute the exponent as `erc_decimals.saturating_sub(local_decimals)`. `saturating_sub` on unsigned integers clamps to `0` whenever `local_decimals > erc_decimals`, so the exponent becomes `0` and the multiplier/divisor becomes `1` — i.e., **no scaling is applied at all**, even though scaling in the *other direction* (dividing on the outbound path, multiplying on the inbound path) would be required for correctness.

Concretely, on the outbound `send` path (`module.rs`, which calls `convert_to_erc20(value, erc_decimals, local_decimals)` before dispatching an ISMP POST to the remote HFT/WrappedHFT contract), if a registered asset's `local_decimals` (e.g. 18) exceeds the `Precisions` entry recorded for the destination chain's `erc_decimals` (e.g. 6), the function should divide the locally burned/escrowed amount by `10^12` before encoding it into the cross-chain `Message.amount` field. Instead it multiplies by `10^0 = 1`, so the raw, unscaled local-precision value is placed directly into the message body.

On the destination EVM contract (`HyperFungibleToken.onAccept` / `WrappedHyperFungibleToken.onAccept`), the amount in the message is minted/transferred verbatim with no further decimal adjustment: [2](#0-1) 

Because the EVM contract trusts the amount encoded by the source pallet (source authenticity is verified, but the *magnitude* is not independently checked against what was actually escrowed), a mismatched `Precisions` registration where `local_decimals > erc_decimals` causes every outbound transfer to mint an amount inflated by `10^(local_decimals - erc_decimals)` on the destination chain relative to what was actually locked/burned on the source chain — precisely the same "cast tokens the pool doesn't back" pattern as the WLEO incident, where a wrapping mechanism let an attacker mint a wrapped asset without corresponding backing in the origin pool.

`Precisions` is set via `update_asset_precision`, which is only `CreateOrigin`-gated for updates, and initial values come from asset registration — there is no on-chain invariant enforcing `erc_decimals >= local_decimals`, so a governance/config mistake (or a chain whose asset naturally has higher local precision than the paired EVM token, e.g. an 18-decimal local asset paired with a 6-decimal USDC-style ERC20) silently produces this state without any explicit validation error. Once such a misconfiguration exists, any signed account calling `send` triggers unbacked minting on the destination chain.

### Impact Explanation
Unbacked minting on the destination chain directly inflates the token's supply beyond what is escrowed on the source chain (native) or beyond the represented burn (non-native), letting an attacker or ordinary user extract real value equal to the inflation factor times the amount transferred, and letting the destination-side token de-peg / drain any pool it is later swapped or redeemed against — the exact mechanism and impact class of the WLEO incident (unbacked wrapped-token minting drained from a DEX pool). This is a Medium-to-High severity token-bridge mint/burn accounting bug reachable from a single `send` extrinsic.

### Likelihood Explanation
The bug only manifests when `Precisions` for a given `(asset, chain)` pair is configured with `local_decimals > erc_decimals`, which requires the `CreateOrigin`/asset registration to have set such values (e.g. importing a lower-decimal ERC20 like USDC(6) as the remote representation of an 18-decimal local asset, a realistic configuration for standard tokens). Given no code-level guard prevents this configuration, and it is a plausible/likely real-world pairing, likelihood is medium — it depends on configuration but is not a contrived edge case.

### Recommendation
Fix `convert_to_balance` and `convert_to_erc20` to handle both directions of decimal mismatch: compute a signed difference (or explicit `if erc_decimals >= local_decimals { multiply } else { divide }` branch) instead of relying on `saturating_sub`, which silently discards the case where local precision exceeds remote precision. Add an explicit test asserting correct behavior for both `erc_decimals > local_decimals` and `erc_decimals < local_decimals`, and consider adding a runtime invariant/warning when registering a `Precisions` entry that could produce lossy or asymmetric scaling.

### Proof of Concept
1. Register a local asset with `local_decimals = 18` (via `register_token`), and set `Precisions` for a target EVM chain's contract to `erc_decimals = 6` (via `update_asset_precision`), such that `erc_decimals < local_decimals`.
2. A user calls `send` locking/burning `1` unit of the local asset (`1 * 10^18` raw local balance).
3. `convert_to_erc20(1e18, 6, 18)` computes `erc_decimals.saturating_sub(local_decimals) = 0`, so it returns `1e18 * 10^0 = 1e18` instead of the correct `1e18 / 10^12 = 1e6`.
4. The dispatched `Message.amount` field therefore encodes `1e18` instead of `1e6`.
5. On the destination chain, `HyperFungibleToken.onAccept` calls `_mint(beneficiary, 1e18)` verbatim — minting `1,000,000,000,000` times more tokens (in the 6-decimal ERC20's raw unit terms) than were actually escrowed for `1` unit of the source asset, an unbacked mint exploitable exactly like the WLEO incident. pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}

/// Converts a local u128 balance to an ERC20 U256 amount
///
/// Multiplies by 10^(erc_decimals - local_decimals) to scale up to ERC20 precision
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
