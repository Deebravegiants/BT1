## Confirmed: `TokenExchange.exchange_token` skips `ShopValidator` sanitization applied everywhere else the gem builds an OAuth token-endpoint URL

### Title
Missing shop-domain sanitization in `TokenExchange.exchange_token` lets the `dest` claim of a session token pick the host that receives `client_id`/`client_secret` - (File: `lib/shopify_api/auth/token_exchange.rb`)

### Summary
Every other flow in this gem that builds a `/admin/oauth/access_token` request first canonicalizes the caller-supplied shop value with `Utils::ShopValidator.sanitize!`, which restricts the resulting host to `ShopValidator::TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`) before it is used to build the request host in `Clients::HttpClient`. `TokenExchange.exchange_token` is the one exception: it takes the shop value straight from the JWT `dest` claim (`jwt_payload.shop`) and uses it, unsanitized, as `Auth::Session#shop`, which `Clients::HttpClient#initialize` turns directly into `@base_uri = "https://#{session.shop}"` - the host that then receives `client_id` and `client_secret` in the POST body.

### Finding Description
`ShopifyAPI::Auth::JwtPayload` only checks the HMAC signature and `aud == Context.api_key`; it never validates that `dest`/`iss` are constrained to a Shopify-trusted domain form: [1](#0-0) 

`TokenExchange.exchange_token` derives `dest_shop` from that unrestricted claim and passes it straight into `Auth::Session.new(shop: dest_shop)` with **no call to `Utils::ShopValidator.sanitize!`**: [2](#0-1) 

Compare this to every sibling OAuth-token flow in the same file and module, which all sanitize the shop before using it as a session/host: [3](#0-2) [4](#0-3) [5](#0-4) 

`ShopValidator.sanitize!` is the only place in the gem that constrains a shop string to `TRUSTED_SHOPIFY_DOMAINS`: [6](#0-5) 

Finally, `session.shop` becomes the literal request host, and the request body (built in `exchange_token`) carries `client_id`/`client_secret`: [7](#0-6) 

**Binding that should hold:** `host that receives client_secret == a domain in ShopValidator::TRUSTED_SHOPIFY_DOMAINS`. Because `exchange_token` never calls `sanitize!`, this equality is enforced everywhere except this one code path.

### Impact Explanation
If a `dest` claim is ever attacker-influenced or malformed in a way that is not itself a valid `myshopify.com`/`shopify.com`/`spin.dev` domain (e.g. contains a path, port, or trailing characters that `Addressable::URI` would reject/normalize differently than the naive `gsub("https://", "")`), the resulting `session.shop` string is interpolated directly into `https://#{session.shop}` with no further validation, then used as the POST host with `client_id` and `client_secret` in the body — an SSRF-with-credentials pattern (High severity per the rubric: "SSRF with the app's credentials"). This is exactly the class of bug the external report illustrates: a value computed/derived from trusted-looking input is used downstream without re-validating the exact invariant (the report's `pricePerShare`-scaled amount vs. the exact-amount `userData`; here, an un-sanitized `dest`-derived host vs. the sanitized-host invariant enforced everywhere else).

### Likelihood Explanation
Exploitability hinges on whether a value can reach `JwtPayload#shop` that (a) still verifies against `Context.api_secret_key`/`old_api_secret_key` and passes `aud == Context.api_key`, and (b) is not itself a well-formed trusted domain. Since the JWT is HS256-signed with the app's own secret, this is not directly forgeable by an unprivileged internet user without knowledge of that secret. I was not able to fully determine, within the indexed files, whether Shopify's real-world token issuance can ever produce a `dest` value that is syntactically valid as a claim but fails `ShopValidator`'s stricter parsing (e.g., unusual unified-admin or spin/dev shapes that `ShopValidator` special-cases in `unified_admin?` / `myshopify_domain_from_unified_admin` but that `JwtPayload#shop`'s plain `gsub` does not normalize the same way). This is a code-path inconsistency I can prove from the source, but the concrete exploit trigger (a signed-but-untrusted `dest` value) is not something I can construct or confirm purely from the indexed library code.

### Recommendation
In `TokenExchange.exchange_token`, sanitize `dest_shop` the same way `migrate_to_expiring_token`, `client_credentials`, and `refresh_access_token` do:
```ruby
dest_shop = Utils::ShopValidator.sanitize!(jwt_payload.shop)
```
This restores the `host-that-receives-client_secret == trusted-domain` invariant uniformly across all token-endpoint call sites.

### Proof of Concept
Not independently reproducible from the indexed library code alone: the JWT is HS256-signed with the app's own `api_secret_key`, so I could not construct a token whose `dest` value both (a) passes `JwtPayload` verification and (b) resolves to a host outside `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`, using only the files available in this index. This finding is reported as a code-path inconsistency (missing `sanitize!` call) proven by direct comparison against the three sibling flows that do call it, not as a fully demonstrated end-to-end exploit.

      TRUSTED_SHOPIFY_DOMAINS = T.let(
        [
          "shopify.com",
          "myshopify.io",
          "myshopify.com",
          "spin.dev",
          "shop.dev",
        ].freeze,
        T::Array[String],
      )

      class << self
        extend T::Sig

        sig do
          params(
            shop_domain: String,
            myshopify_domain: T.nilable(String),
          ).returns(T.nilable(String))
        end
        def sanitize_shop_domain(shop_domain, myshopify_domain: nil)
          uri = uri_from_shop_domain(shop_domain, myshopify_domain)
          return nil if uri.nil? || uri.host.nil? || uri.host.empty?

          trusted_domains(myshopify_domain).each do |trusted_domain|
            host = T.cast(uri.host, String)
            uri_domain = uri.domain
            next if uri_domain.nil?

            no_shop_name_in_subdomain = host == trusted_domain
            from_trusted_domain = trusted_domain == uri_domain

            if unified_admin?(uri) && from_trusted_domain
              return myshopify_domain_from_unified_admin(uri)
            end
            return nil if no_shop_name_in_subdomain || host.empty?
            return host if from_trusted_domain
          end
          nil
        end

        sig do
          params(
            shop: String,
            myshopify_domain: T.nilable(String),
          ).returns(String)
        end
        def sanitize!(shop, myshopify_domain: nil)
          host = sanitize_shop_domain(shop, myshopify_domain: myshopify_domain)
          if host.nil? || host.empty?
            raise Errors::InvalidShopError,
              "shop must be a trusted Shopify domain (see ShopValidator::TRUSTED_SHOPIFY_DOMAINS), got: #{shop.inspect}"
          end

          host
        end
