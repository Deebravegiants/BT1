### Title
Webhook `shop`/`topic`/`webhook-id` identity fields are not covered by the HMAC, allowing cross-tenant replay of a legitimately-signed webhook body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` extracts `shop`, `topic`, `webhook_id`, and `api_version` from HTTP headers, but the HMAC signature validated by `HmacValidator` only covers the raw request body (`to_signable_string` returns `@raw_body`). The `shop` value is then trusted downstream as the tenant identifier passed to the app's webhook handler without ever being bound to the signature.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` validates a webhook purely on `Utils::HmacValidator.validate(request)`: [1](#0-0) 

`HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string`: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` is only the raw body — the `shop`, `topic`, `webhook_id`, and `api_version` headers are never included in what's signed: [3](#0-2) 

Yet `Registry.process` passes `request.shop` (an unauthenticated header value) straight into the data handed to the app's handler, which apps use as the tenant key to look up sessions, access tokens, or write data: [4](#0-3) 

The broken identity binding is: **HMAC-verified body ≠ shop claimed in headers**. An attacker who legitimately receives one valid webhook for their own shop (with a correctly computed HMAC over that body) can replay the identical body/HMAC pair to the app's webhook endpoint while substituting the `shopify-shop-domain` header with a victim shop's domain. Because `shop` is not part of the signed payload, `HmacValidator.validate` still returns `true`, and the registry will invoke the handler with `WebhookMetadata` claiming the victim's shop, even though the attacker fully controls the (previously-signed) body content.

### Impact Explanation
This breaks the tenant boundary the HMAC is supposed to establish: the only cryptographic guarantee provided is "this body was signed by Shopify/the app secret," not "this body originated for this shop." Any app that trusts `WebhookMetadata#shop` to select which merchant's session/access token to act on, or to attribute/write data, can be induced to process attacker-supplied content under another merchant's identity — a cross-tenant data injection matching the report's "identity binding broken" bug class (HMAC covers bytes, but the field acted upon — `shop` — is not part of those bytes).

### Likelihood Explanation
Exploitation requires the attacker to have received at least one legitimately signed webhook (e.g., from their own store installed against the same app, which is trivial to obtain for any developer/merchant using the app) and requires the receiving app to key business logic off `data.shop` from `WebhookMetadata` — a very common pattern encouraged by this SDK's own handler API. No access token, `client_secret`, or privileged access is needed; only observation of one's own webhook traffic and replay to the app's public webhook endpoint with a modified `shop` header.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) to the HMAC-verified payload rather than trusting the raw header value. Concretely, `to_signable_string` in `lib/shopify_api/webhooks/request.rb` should incorporate the header-derived shop/topic into the signed string (mirroring how Shopify itself computes and forwards these values), or the registry should independently corroborate `request.shop` against session state established during OAuth for that merchant before dispatching to handlers.

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com`; capture a legitimate webhook delivery, e.g. body `{"id":1}` with header `x-shopify-shop-domain: attacker.myshopify.com` and a valid `x-shopify-hmac-sha256` computed by Shopify using the app's `api_secret_key`.
2. Replay the exact same raw body and HMAC header to the app's public webhook endpoint, but change `x-shopify-shop-domain` to `victim.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)` [5](#0-4) , which only checks the body's HMAC and returns `true` regardless of the `shop` header, since `to_signable_string` never includes it [6](#0-5) .
4. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and attacker-controlled `body`, processing it as if it were an authentic event from the victim's store.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
