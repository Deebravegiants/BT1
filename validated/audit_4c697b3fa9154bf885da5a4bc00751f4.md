### Title
Webhook `shop-domain` identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC-SHA256 signature computed over the raw request body, then blindly trusts the unsigned `shop-domain` header to attribute the event to a specific merchant before dispatching it to the app's handler. This mirrors the report's bug class exactly: a field that is *acted on* (the shop identity used to key merchant data) is not *covered by the HMAC* that is supposed to authenticate the request.

### Finding Description
`Request#to_signable_string` returns only the raw HTTP body: [1](#0-0) 

`Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, with no cryptographic binding to the signature: [2](#0-1) 

`HmacValidator.validate` computes the expected signature over `verifiable_query.to_signable_string` (i.e., the body only) and compares it with `OpenSSL.secure_compare`: [3](#0-2) 

`Registry.process` validates the HMAC and then constructs `WebhookMetadata` using the header-derived, unsigned `request.shop`, handing it to the app's handler as trusted merchant identity: [4](#0-3) 

**Identity binding broken as an equality:**
`shop` trusted by the handler (`request.shop`, from header) ≠ `shop` actually authenticated by the HMAC (covers `@raw_body` only, no headers).

**Attack sequence (unprivileged internet user):**
1. Attacker owns/creates a shop (e.g., a free development store) and registers the victim's exact webhook endpoint URL to receive a webhook for any topic whose body content the attacker can influence (e.g., `products/update`, `orders/create` on their own store).
2. Shopify sends the attacker a legitimately HMAC-signed webhook: `X-Shopify-Hmac-Sha256: <valid signature over body>`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, plus the raw body.
3. Attacker captures this raw body and signature, then replays them directly to the same app endpoint but substitutes `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `HmacValidator.validate` recomputes the signature over the (unchanged) body and it matches, since headers are never part of the signed payload.
5. `Registry.process` proceeds to call the app's handler with `shop: "victim-shop.myshopify.com"`, causing the host application to process/store attacker-controlled data under the victim tenant's identity.

### Impact Explanation
This breaks tenant isolation: an unprivileged actor can force a target app to attribute arbitrary (self-controlled) webhook payloads to a different, victim shop, without possessing any of the victim's credentials. Depending on how the host application's webhook handlers use `WebhookMetadata#shop` (e.g., to look up the shop's session/access token and act on its behalf, update its local records, or trigger downstream side effects), this can lead to cross-tenant data corruption or unauthorized actions performed in the context of another merchant — matching the "Critical: cross-tenant access" impact category.

### Likelihood Explanation
Medium: it requires the attacker to control a real (even free/dev) Shopify store to legitimately obtain HMAC-signed webhook bodies for topics whose body content they can shape, and to craft a raw HTTP request with a substituted header — both are within reach of an unprivileged internet user with no special credentials, access tokens, or `client_secret` knowledge.

### Recommendation
Do not treat the `shop-domain` header as authenticated data solely because the body's HMAC validated. At minimum:
- Require host applications to cross-check `request.shop` against an independently known, registered/installed shop (e.g., matching an existing session) before acting on webhook data — and document this requirement prominently in `Registry.process`.
- Consider extending `to_signable_string` (or adding a secondary check in `Registry.process`) so the shop domain participates in the integrity check, rather than being trusted purely from an unauthenticated header.

### Proof of Concept
1. Register a webhook subscription for a topic (e.g. `products/update`) pointing to the target app's public webhook endpoint, using a shop the attacker controls.
2. Trigger the event in the attacker's own shop; capture the resulting POST request's raw body and `X-Shopify-Hmac-Sha256` header exactly as sent by Shopify.
3. Resend that exact body and HMAC header to the same endpoint, replacing `X-Shopify-Shop-Domain` with the victim shop's domain.
4. Observe that `ShopifyAPI::Webhooks::Registry.process` accepts the request (`HmacValidator.validate` passes because only body is checked) and invokes the registered handler with `WebhookMetadata#shop == "<victim-shop>"`, even though the payload never originated from the victim shop.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
