### Title
Global `challengePeriod` update retroactively weakens the fisherman veto window for already-stored state commitments - ([File: evm/src/core/EvmHost.sol], [File: evm/src/core/HandlerV2.sol])

### Summary
`EvmHost.updateHostParamsInternal` overwrites a single global `_hostParams.challengePeriod` value used to gate *every* pending state commitment, regardless of when each commitment was stored. This mirrors the reported `ERC20Vesting.setTgeDate` bug class: a single mutable "as of now" parameter is applied uniformly to previously created records instead of being snapshotted per-record at creation time.

### Finding Description
`updateHostParamsInternal` writes the new `challengePeriod` straight into `_hostParams.challengePeriod` with no accounting for state commitments that are already stored and awaiting their originally-promised challenge window: [1](#0-0) 

`storeStateMachineCommitment` (called by the trusted handler when a consensus proof is verified) records only `_stateCommitmentsUpdateTime[...] = block.timestamp` — it does not snapshot the challenge period that was in effect at that moment: [2](#0-1) 

Every downstream delay check (`handlePostRequests`, `handleGetResponses`, `handlePostRequestTimeouts`) then reads the *current* global `challengePeriod()` and compares it against that stored timestamp: [3](#0-2) [4](#0-3) [5](#0-4) 

The exact same pattern exists on the substrate side: `verify_delay_passed` reads the *current* configured `challenge_period(proof_height.id)` against the stored `state_machine_update_time`: [6](#0-5) 

Fishermen decide whether to veto a state commitment based on the challenge period that was configured *when the commitment landed* — that window is their entire opportunity to detect and veto a fraudulent/byzantine state commitment before it becomes actionable. If governance legitimately shortens `challengePeriod` (e.g. to speed up future finality) while older commitments are still inside their *original*, longer window, those older commitments instantly become eligible for message delivery under the *new*, shorter window. This is a case of a global "as of now" parameter being applied retroactively to previously created records, exactly the bug class described in the report, and it is triggered by ordinary unprivileged relayer activity: any relayer holding a pending state commitment can immediately submit `handlePostRequests`/`handleGetResponses`/`handlePostRequestTimeouts` the moment the shortened delay is satisfied, cutting off however much of the fisherman veto window remains for that commitment.

### Impact Explanation
Fishermen who were relying on the original challenge period to detect and veto a fraudulent or byzantine `StateCommitment` before it is used may lose their remaining veto window entirely once governance shortens `challengePeriod`. Any relayer can then immediately deliver requests/responses/timeouts sourced from that state commitment via `HandlerV2`, which dispatches them onward through `host.dispatchIncoming(...)`, allowing unverified/unsound state to be actioned against `IsmpModule`s before the community had the chance it was promised to catch and veto it. This can result in forged message delivery and downstream fund loss or unauthorized app actions in any module relying on ISMP request/response delivery.

### Likelihood Explanation
Requires a legitimate (non-malicious) governance update to `challengePeriod` — which the protocol documentation and tests show is a normal, expected operation (see `HostManagerTest.sol` reducing/increasing `challengePeriod` via ordinary governance) — combined with at least one state commitment already stored and pending at the time of the update. Given that any relayer, not just the one that stored the commitment, can then submit the affected messages, the exploit path requires no privileged access once the parameter change lands.

### Recommendation
Snapshot the challenge period in effect at the time each `StateCommitment` is stored (e.g., in `_stateCommitmentsUpdateTime`/a parallel mapping, analogous to caching `tgeStartDate` per vesting schedule instead of relying on a single global value), and use that snapshotted value — not the live `challengePeriod()` — when checking `handlePostRequests`, `handleGetResponses`, and `handlePostRequestTimeouts` delay conditions. Apply the equivalent fix to `verify_delay_passed` on the substrate side.

### Proof of Concept
1. Consensus proof is verified and a `StateCommitment` for height H is stored via `storeStateMachineCommitment`, recording `_stateCommitmentsUpdateTime[id][H] = T0`; `challengePeriod` at this point is `P_old` (e.g. 24h).
2. Governance legitimately calls `updateHostParams` with `challengePeriod = P_new` (e.g. 1h) for unrelated reasons (faster future finality). This immediately overwrites the single global `_hostParams.challengePeriod`. [7](#0-6) 
3. At `T0 + P_new` (well before `T0 + P_old`), any relayer submits `handlePostRequests` for a `PostRequestLeaf` proven against height H. The check `challengePeriod > delay` now uses `P_new`, so it passes even though fishermen never received their originally promised `P_old` veto window. [8](#0-7) 
4. The requests are dispatched to their destination `IsmpModule`s before the original veto deadline `T0 + P_old`, defeating the fisherman security assumption for that specific commitment.

pub fn verify_delay_passed<H>(host: &H, proof_height: &StateMachineHeight) -> Result<bool, Error>
where
	H: IsmpHost,
{
	let update_time = host.state_machine_update_time(*proof_height)?;
	let delay_period = host
		.challenge_period(proof_height.id)
		.ok_or(Error::ChallengePeriodNotConfigured { state_machine: proof_height.id })?;
	let current_timestamp = host.timestamp();
	Ok(delay_period.as_secs() == 0 || current_timestamp.saturating_sub(update_time) > delay_period)
}
