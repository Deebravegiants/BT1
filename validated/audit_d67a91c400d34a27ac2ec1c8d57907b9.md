### Title
Webhook shop-domain identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` trusts the `shop-domain` header of an incoming webhook request as the tenant identifier, but that header is never covered by the HMAC signature that is verified. Only the raw JSON body is signed, so an attacker who possesses one genuine `(raw_body, hmac)` pair signed by the app's shared `client_secret` can replay it with an arbitrary `shop-domain` value and have it accepted as authentic, causing the receiving application to process the webhook as belonging to a different, victim shop.

### Finding Description
The webhook signature is validated by `Utils::HmacValidator.validate`, which calls `validate_signature`, which computes the HMAC over `verifiable_query.to_signable_string` and compares it with `OpenSSL.secure_compare`: [1](#0-0) 

For webhook requests, `to_signable_string` returns only `@raw_body` — the request body — while `shop` is read from the `shop-domain` header, entirely independent of the signed bytes: [2](#0-1) [3](#0-2) 

`Registry.process` verifies the HMAC and, once it passes, hands `request.shop` straight to the handler as the authoritative tenant identifier, with no cross-check against the signed body: [4](#0-3) 

The identity binding that should hold is:
`shop-domain header used for tenant routing == shop domain covered by the verified HMAC bytes`

This binding does not hold: the HMAC only authenticates the body, not the shop the request claims to be from. Because Shopify apps use a single `client_secret` shared across all merchants who install the app, any merchant who installs the app receives genuine webhook deliveries signed with that same secret for their own shop. Such a merchant can capture one legitimate `(raw_body, X-Shopify-Hmac-Sha256)` pair and resend it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to a victim shop's domain. `HmacValidator.validate` still succeeds (the body/HMAC pair is genuinely valid), and `Registry.process` calls the handler with `data.shop` equal to the attacker-chosen victim domain, as shown in the documented handler pattern that keys downstream processing directly off `data.shop`: [5](#0-4) 

### Impact Explanation
Any host application that uses `WebhookMetadata#shop` to select which tenant's records to create/update/delete (the documented and expected usage pattern) can be made to apply attacker-controlled webhook payloads under a different merchant's tenant identity, i.e., cross-tenant data injection/corruption without possessing that tenant's access token or any privileged credential — only requiring the ability to install the app on one's own store to obtain a valid signed payload. This satisfies the "cross-tenant access" High-impact category.

### Likelihood Explanation
Exploitation requires only becoming an installer of the target app (a normal, unprivileged action for any Shopify merchant) and the ability to send an HTTP request to the app's public webhook endpoint with a modified header — no secret key, access token, or other privileged material is needed. This is a realistic, low-effort attack path.

### Recommendation
Include the shop domain (and other identity-relevant headers such as topic) inside the HMAC-signed material, or independently verify that `request.shop` matches a shop domain embedded in/derivable from the verified body, before using it for tenant routing. At minimum, document that `WebhookMetadata#shop` is unauthenticated and must not be trusted for tenant-scoping without additional verification, or have `to_signable_string` incorporate the header value so `Utils::HmacValidator.validate` binds shop to signature.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`, thereby learning a genuine webhook delivery: raw body `B` and header `X-Shopify-Hmac-Sha256: H` (both signed with the app's single `client_secret`).
2. Attacker sends a POST to the app's webhook endpoint with the same raw body `B`, the same `X-Shopify-Hmac-Sha256: H`, but `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body successfully (`lib/shopify_api/webhooks/request.rb:45-63`).
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`; since `to_signable_string` returns only `B`, the previously valid `H` still matches, and validation passes (`lib/shopify_api/webhooks/registry.rb:190`, `lib/shopify_api/utils/hmac_validator.rb:26-31`).
5. The handler is invoked with `data.shop == "victim.myshopify.com"` even though the payload actually originated from, and was signed for, `attacker.myshopify.com`'s delivery (`lib/shopify_api/webhooks/registry.rb:198-199`).
