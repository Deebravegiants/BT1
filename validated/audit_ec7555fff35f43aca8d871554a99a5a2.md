Based on my research, I found a concrete, unguarded subtraction analog to the rusty-kaspa `estimate_block_count()` overflow bug. It's reachable from an unprivileged buy transaction and, unlike sibling calculations in the same file, lacks the saturating-subtraction guard the developers explicitly applied elsewhere.

### Title
Unguarded reserve subtraction in graduation-trigger math can revert-brick the bonding curve - ([File: packages/contracts/src/Bonding.sol])

### Summary
`Bonding.canGraduate`, `Bonding.previewLtUntilGraduation`, and `Bonding._prepareGraduationLiquidity` all compute `assetReserve - _launchTimeVirtualLtReserve(token_, pair)` with a plain Solidity `-`, which reverts (`Panic(0x11)`) on underflow rather than saturating. This is the same bug class as the referenced rusty-kaspa fix, where `estimate_block_count()` panicked on `virtual_score - retention_period_root_score` and was patched to `saturating_sub()`.

### Finding Description
`canGraduate` reads the pair's live reserves and subtracts the launch-time virtual LT reserve to get `realLtRaised`: [1](#0-0) 

The identical unguarded pattern is repeated in `previewLtUntilGraduation`: [2](#0-1) 

and in `_prepareGraduationLiquidity`, which runs inline at the end of every threshold-crossing buy via `_enterGraduating`: [3](#0-2) 

`_launchTimeVirtualLtReserve` recovers the launch-time virtual reserve as `Pair.k() / Token.TOTAL_SUPPLY()`: [4](#0-3) 

Notably, the codebase's own authors treat "balance below the expected floor" as a class of bug worth defending against with `saturating_sub`-style guards elsewhere in the same file — e.g. in `finalizeGraduation`'s `protectedLT` computation: [5](#0-4) 

and in `_ltSwapInventory`, whose comment explicitly states the intent: *"Saturating subtract matches `_routerDepositAndDispose` so a future violation of the `balanceOf >= protectedLT` invariant can't brick `finalizeGraduation`."* [6](#0-5) 

The three graduation-trigger call sites (`canGraduate`, `previewLtUntilGraduation`, `_prepareGraduationLiquidity`) received no equivalent defensive treatment, even though `canGraduate` is invoked at the end of **every single buy** (via `_executeBuy`), making it one of the hottest paths in the contract.

### Impact Explanation
If `assetReserve` (the pair's stored LT reserve) is ever observed below the recovered `virtualLtReserve`, every subsequent call into `canGraduate`/`previewLtUntilGraduation` reverts with a Panic instead of returning a sane value. Because `canGraduate` is checked inline at the end of `_executeBuy`, a revert there bricks **all buys** on that curve, not just graduation — freezing trader funds mid-transaction and preventing the token from ever reaching graduation (permanent freeze of trader/creator funds, matching the "concrete... permanent freezing" bar in the validation rules). `_prepareGraduationLiquidity`'s copy of the same subtraction sits inside `_enterGraduating`, so the same underflow would also brick phase-1 graduation entry.

### Likelihood Explanation
Design invariants (the K-identity: `k = totalSupply * virtualLtReserve_init`, never mutated by swaps) are argued in comments to guarantee `assetReserve >= virtualLtReserve` always holds. However, this guarantee is asserted only by natural-language reasoning about AMM rounding direction across `Router._computeBuy`/`_computeSell`, not by an explicit on-chain invariant check at these three read sites, and the authors themselves did not trust the analogous invariant elsewhere in the same file (`ltBalance >= p.ltFromPair`) enough to skip a saturating guard there. Any future change to `Router._computeSell`/`_computeBuy` rounding direction, an alternate router path, or an LT/pair implementation edge case that nudges `assetReserve` even 1 wei below `virtualLtReserve` turns a latent invariant violation into an unconditional buy-path DoS across the entire curve — exactly the failure mode the upstream Kaspa fix was hardening against.

### Recommendation
Replace the plain `-` in `canGraduate` (Bonding.sol:692), `previewLtUntilGraduation` (Bonding.sol:722), and `_prepareGraduationLiquidity` (Bonding.sol:1084) with the same saturating pattern already used in `_ltSwapInventory`/`finalizeGraduation` (`assetReserve > virtualLtReserve ? assetReserve - virtualLtReserve : 0`), so a violation of the K-identity invariant degrades gracefully (treats `realLtRaised`/`ltFromPair` as `0`) instead of permanently reverting every buy on the curve.

### Proof of Concept
A precise underflow trigger could not be constructed from static reading alone — it depends on whether `Router._computeBuy`/`_computeSell`'s rounding can, over many buy/sell cycles or through an alternate entry path, push the pair's stored `assetReserve` below the exact `Pair.k()/TOTAL_SUPPLY()` value. This would require running the fuzz/invariant suite (`test/GraduationInvariants.t.sol`, `test/Bonding.t.sol`) with additional adversarial buy/sell sequences (including near the `uint112` overflow-cap boundary and repeated capped-buy/sell round trips) to confirm whether the invariant can be broken in practice, or a Devin session with the full repo/test harness to fuzz it directly.
