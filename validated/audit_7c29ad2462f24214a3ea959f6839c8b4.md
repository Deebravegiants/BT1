### Title
Webhook shop/topic headers are trusted without being covered by the HMAC, enabling cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC-verifiable signable string from the raw body only, while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from unauthenticated HTTP headers and passed straight to the webhook handler. Because these fields are never part of the signed digest, any party who possesses one valid `(body, hmac)` pair for the app's single shared `api_secret_key` can replay it with arbitrary `shop`/`topic` header values and have it accepted as an authentic webhook for a different shop and/or event type.

### Finding Description
The `VerifiableQuery` interface requires `hmac` and `to_signable_string`, and `Utils::HmacValidator.validate` verifies the received `hmac` against `HMAC-SHA256(secret, to_signable_string)`: [1](#0-0) 

For webhooks, `to_signable_string` returns only the raw request body — none of the Shopify-provided headers are included in the signed material: [2](#0-1) 

Yet `shop`, `topic`, `webhook_id`, and `api_version` are all derived from headers that are completely outside the HMAC's scope: [3](#0-2) 

`Webhooks::Registry.process` validates only the HMAC, then immediately trusts `request.topic` and `request.shop` to dispatch to a handler and build `WebhookMetadata`: [4](#0-3) 

The broken identity binding, stated as an equality that the code assumes but never enforces:

```
HMAC-verified(raw_body)  ==  (shop, topic, webhook_id, api_version) attributed to that body
```

In reality, only `raw_body` is authenticated; `(shop, topic, webhook_id, api_version)` are asserted by an unauthenticated header and merely copied into `WebhookMetadata`. Because `api_secret_key` is a single value shared across all shops that install the app (not a per-shop secret), any shop that installs the app receives genuinely-signed webhooks whose `(body, hmac)` pair is valid under that same shared secret regardless of which shop or topic it was originally sent for. An attacker who controls one installed shop can therefore capture a legitimately Shopify-signed `(body, hmac)` and resubmit it to the app's public webhook endpoint with the `x-shopify-shop-domain` header set to a victim shop and/or the `x-shopify-topic` header changed to a sensitive topic (e.g. `app/uninstalled`, `shop/redact`, `customers/data_request`), and the app's own webhook-processing logic will accept and act on it as if it genuinely originated from the victim shop and topic.

### Impact Explanation
This crosses the tenant boundary: an attacker who legitimately controls only their own shop's install of the app can cause the app to process attacker-chosen data as if it belongs to a different, victim shop, and/or trigger handlers for a topic that was never actually sent for that body (e.g., faking `app/uninstalled` to force session/data deletion for a victim shop, or `customers/data_request`/`shop/redact` GDPR webhooks against the wrong tenant). This matches the "cross-tenant access" Critical impact category, since the app cannot distinguish which shop or topic a signed payload was actually issued for.

### Likelihood Explanation
Any user able to install the app on a shop they control (an "unprivileged internet user" relative to other merchants of the same app) can obtain at least one valid `(body, hmac)` pair from Shopify's real webhook delivery, then POST it to the app's public webhook endpoint with modified `shop`/`topic` headers. No access to `api_secret_key`, access tokens, or victim credentials is required — only the ability to install the app once, which is the normal, unprivileged flow for any Shopify merchant/dev store.

### Recommendation
Bind the identity fields into the signed material rather than trusting headers unconditionally: include `shop`, `topic`, and `webhook_id` in the digest that `Utils::HmacValidator` verifies (e.g., have `to_signable_string` concatenate a type/topic/shop prefix with the body, mirroring the raw HMAC bytes Shopify actually signs for the given headers), or otherwise cross-check the header-derived `shop`/`topic` against values independently confirmed with Shopify (e.g., via the webhook ID lookup) before dispatching to handlers.

### Proof of Concept
1. Attacker installs the app for `attacker-shop.myshopify.com`. Shopify sends a real webhook, e.g. topic `orders/create`, with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
2. Attacker resends `B` unchanged to the app's webhook endpoint, but sets:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - `x-shopify-topic: app/uninstalled` (or any registered topic)
   - `x-shopify-hmac-sha256: H` (unchanged)
3. `ShopifyAPI::Webhooks::Request.new` parses these headers unchanged; `Utils::HmacValidator.validate` recomputes HMAC over `B` only and it matches `H`, so validation passes: [5](#0-4) 
4. `Registry.process` dispatches the app's `app/uninstalled` (or other) handler with `shop: "victim-shop.myshopify.com"`, even though Shopify never sent this webhook for that shop or topic: [4](#0-3)
