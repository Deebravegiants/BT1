### Title
Unchecked ERC20 boolean return value on escrow withdrawal/refund/dust-sweep in Tron IntentGatewayV2 permanently freezes user funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` uses low-level `.call()` with `IERC20.transfer.selector` to pay out escrowed tokens on order fill/refund/cancel and to sweep dust, but only checks that the *external call* did not revert — it never decodes/validates the ABI-encoded `bool` return value that ERC20 mandates. Tokens that follow the legacy "no-revert-on-failure" pattern (e.g. ZRX-style tokens, or any token that returns `false` instead of reverting on a failed transfer) will make `success == true` even though no tokens were actually moved, while the contract still deducts the escrow balance and marks the order as filled/refunded.

### Finding Description
`withdraw()` releases escrowed input tokens and transaction fees to a beneficiary via: [1](#0-0) 

```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
```

`success` here only reflects whether the low-level call reverted, not whether the token's internal transfer logic returned `true`. A "no-revert-on-failure" ERC20 (the exact class flagged in the referenced Sherlock finding — ZRX-style tokens that return a `bool` instead of reverting) can return `false` on a failed transfer while the call itself succeeds, so `success` stays `true` and the guard never fires.

The same unchecked pattern also exists in the `SweepDust` handler: [2](#0-1) 

Both `withdraw()` (reachable via `onAccept` for `RedeemEscrow`/`RefundEscrow`, and via `cancelOrder` for same-chain cancellation) and the dust-sweep handler are triggered by permissionless/relayed message delivery paths — `onAccept` is called by the host after any relayer delivers a `RedeemEscrow`/`RefundEscrow`/`SweepDust` POST request, and `cancelOrder`/`onGetResponse` can be triggered by any user/relayer completing the GET-response flow: [3](#0-2) [4](#0-3) 

Before reaching `withdraw`, the escrow debit `_orders[body.commitment][token] -= amount;` unconditionally executes right after the unchecked transfer call: [5](#0-4) 

So even when the underlying token transfer silently fails, the escrow accounting proceeds exactly as if the beneficiary was paid.

This differs from the main EVM `IntentsBase.sol`/`IntentGatewayV2.sol`, which consistently use OpenZeppelin's `SafeERC20.safeTransfer`/`safeTransferFrom` (which decode and check the boolean return, reverting on `false`): [6](#0-5) 
The Tron contract deliberately avoids `SafeERC20` for these outbound legs and reimplements a raw `.call` check that omits the return-data validation — reproducing the exact root cause described in the external report (unchecked ERC20 return value for non-reverting tokens).

### Impact Explanation
For any principal/input token deployed on Tron that follows the legacy no-revert ERC20 pattern, a completed `RedeemEscrow`, `RefundEscrow`, same-chain `cancelOrder`, or `SweepDust` delivery will mark the order/escrow as settled and irreversibly zero out (`-= amount`) the internal accounting, while the beneficiary never receives the tokens. Because `_filled[body.commitment]` is also set, the order can never be retried or refunded again. This results in permanent freezing/loss of the escrowed user funds — a concrete, unrecoverable loss of funds impact, matching the "Unchecked return value" high-severity class from the referenced report (adapted here to the payout leg rather than the deposit leg, since deposits already use `safeTransferFrom`).

### Likelihood Explanation
Exploitation/triggering requires only that the principal token used in an order on Tron is a token that returns `false` rather than reverting on transfer failure (a documented and known ERC20 implementation pattern, not an exotic edge case) combined with a transfer condition that would legitimately fail (e.g. a blacklist/pause on the token, or any transient condition causing `balanceOf` mismatch). Given Tron/TRC20 tokens commonly implement bespoke transfer logic and the protocol's README class of "supported tokens" mirrors the same broad set discussed in the cited report, this is readily reachable via the ordinary `RedeemEscrow`/`RefundEscrow`/`cancelOrder`/`SweepDust` flows without any privileged role.

### Recommendation
Replace the raw `.call(...)` + `success`-only check with OpenZeppelin's `SafeERC20.safeTransfer` (as already used elsewhere in the codebase, e.g. `IntentsBase._withdraw`), or explicitly decode the returned bytes and require `(returnData.length == 0 || abi.decode(returnData, (bool)))` in addition to `success`, for all three sites: `withdraw()`'s token loop, `withdraw()`'s fee-token transfer, and the `SweepDust` handler in `onAccept`.

### Proof of Concept
1. Deploy a TRC20 token whose `transfer` function returns `false` on failure instead of reverting (mirroring the ZRX pattern from the referenced report).
2. Use this token as an order input on the Tron `IntentGatewayV2`; place and fill an order so tokens are escrowed under `_orders[commitment][token]`.
3. Arrange for the token to return `false` on the payout transfer (e.g., blacklist the beneficiary, or otherwise make the internal transfer condition fail without reverting).
4. Trigger `RedeemEscrow` delivery (via `onAccept`) or same-chain `cancelOrder`, which calls `withdraw()`.
5. Observe: `token.call(...)` returns `success = true` (call didn't revert) even though the token's internal `false` return means no balance moved; the guard `if (!success) revert TransferFailed();` does not fire.
6. `_orders[body.commitment][token] -= amount` executes, `_filled[body.commitment] = beneficiary` is set, and `EscrowReleased`/`EscrowRefunded` is emitted — the order is permanently marked complete while the beneficiary's balance never increased, permanently freezing the escrowed funds.
