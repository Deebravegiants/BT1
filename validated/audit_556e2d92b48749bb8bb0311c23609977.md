### Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant webhook impersonation - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC signature over the raw request body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values are read from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` validates only that the body's HMAC is correct, then trusts `request.shop` as the tenant identity when dispatching to the app's handler. Because a single app shares one `api_secret_key` across every shop that installs it, any shop that has installed the app can produce a validly-signed webhook body and then have that exact request replayed with a different `shop-domain` header, causing the receiving app to process the payload as if it came from a different (victim) tenant.

### Finding Description
The HMAC is computed like this: [1](#0-0) 

`to_signable_string` returns only `@raw_body`; none of the identifying headers are included. Yet those headers are exposed as trusted attributes: [2](#0-1) 

Validation only checks the body's HMAC: [3](#0-2) 

And `Registry.process` uses that same unauthenticated `shop` value to build the data handed to the app's business logic, with no additional binding check between the signed body and the header-derived shop: [4](#0-3) 

The identity binding that should hold is: `shop-domain header == shop that produced/authorized the signed body`. Because the HMAC secret (`api_secret_key`) is shared across *all* shops that install a given app, and the header is excluded from the signed data, that equality is not enforced by the library. Any shop `A` that has legitimately installed the app can obtain (via its own real webhook traffic) a `(body, hmac)` pair that is valid for the app's secret. That exact `(body, hmac)` pair, replayed with the `X-Shopify-Shop-Domain` header rewritten to shop `B` (another tenant of the same app), still passes `HmacValidator.validate`, since only the body is verified.

### Impact Explanation
This breaks the tenant boundary the app relies on to route webhook data (orders, customers, app-uninstall notices, etc.) to the correct merchant's records. An app that keys its downstream state (databases, feature flags, credential revocation, GDPR/compliance actions) off `WebhookMetadata#shop` can be made to attribute one tenant's data/events to a different tenant purely by an attacker controlling a header value, achieving cross-tenant data confusion/injection without needing the target shop's own token or secret.

### Likelihood Explanation
The attacker needs only to be a legitimate install of the same app (a normal, unprivileged capability for any Shopify developer/merchant who installs a public app) and the ability to intercept/replay their own outbound webhook HTTP request while editing one header — no access to the app's `client_secret`, no interception of another tenant's traffic, and no privileged account is required.

### Recommendation
Bind the identifying headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) into the signed material verified by `HmacValidator`, or otherwise cross-check that the `shop-domain` header is consistent with shop-specific state (e.g., verify the webhook against the recipient's known active session/shop rather than trusting the header verbatim) before dispatching to `handler.handle`.

### Proof of Concept
1. App has shops `A` and `B` both installed with the same app (`api_secret_key` shared).
2. Shop `A` triggers a real event; Shopify sends a webhook to the app with a valid `X-Shopify-Hmac-Sha256` computed over the JSON body and headers `X-Shopify-Shop-Domain: A`, `X-Shopify-Topic: orders/create`.
3. Attacker (who controls shop `A`, e.g. via a proxy in front of their own store/webhook endpoint) captures this request and resends it to the app's webhook endpoint, changing only `X-Shopify-Shop-Domain` to `B`.
4. `ShopifyAPI::Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:13-22`) recomputes the HMAC over the unchanged body and it matches, so `Registry.process` (`lib/shopify_api/webhooks/registry.rb:189-200`) dispatches `WebhookMetadata` with `shop: "B"` and shop `A`'s body to the app's handler, which now processes shop `A`'s data as belonging to shop `B`.
