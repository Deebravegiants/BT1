### Title
Malicious/blacklisting order input tokens permanently freeze escrow and brick solver settlement in `IntentGatewayV2` - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentGatewayV2` lets any user create an order with an arbitrary list of ERC20 `inputs` — there is no allow-list check on the tokens a user escrows. When a solver fills a cross-chain order, the escrowed inputs are released to the solver in a single atomic loop over *all* input tokens in `_withdraw()`. If one of the user-chosen input tokens is a malicious/blacklisting ERC20 that reverts when transferred to the solver's address, the whole withdrawal reverts — permanently, since the message and its token list are fixed at order-fill time and cannot be edited or split by the relayer. This freezes not just the malicious token but every other (legitimate) token escrowed in the same order, while the solver has already paid out the order's output tokens on the destination chain.

### Finding Description
`placeOrder`/`_reduceInputs` on `IntentGatewayV2` escrow `order.inputs` with no restriction on which ERC20s may be used [1](#0-0) . There is no `isTokenAllowed`-style check anywhere in the intents contracts (confirmed absent from the codebase).

When a solver fills a cross-chain order, `_fillCrossChain` dispatches a `RedeemEscrow` message carrying the **entire, unmodified `order.inputs` list**, with the solver (`msg.sender`) as beneficiary: [2](#0-1) 

The output tokens are paid to the order's beneficiary by the solver *before* this message is dispatched (`safeTransferFrom(msg.sender, beneficiary, ...)`), so the solver's cost is already sunk at this point [3](#0-2) .

On the source chain, `onAccept` authenticates the `RedeemEscrow` message and calls `_withdraw`: [4](#0-3) 

`_withdraw` iterates over `body.tokens` (i.e. `order.inputs`) and calls `IERC20(token).safeTransfer(beneficiary, amount)` for each one in sequence, with no isolation between tokens: [5](#0-4) 

If a user deliberately includes a token whose implementation reverts on transfers to a given address (a blacklist/honeypot pattern, exactly as described in the source report), the `safeTransfer` call for that single token reverts, unwinding the entire transaction — including the state write that would have marked `_filled[commitment] = beneficiary` and decremented `_orders[commitment][token]` for the *other, legitimate* tokens in the same order. Because the message body (the token list and beneficiary/solver address) is fixed once dispatched, every future delivery attempt of the same `RedeemEscrow` commitment hits the identical revert — there is no retry path that omits the poisoned token.

The tron variant of the contract has the identical structure and is equally affected (`withdraw`, using a raw `.call` + `TransferFailed()` revert instead of `SafeERC20`) [6](#0-5) .

The same unrestricted `order.inputs` list is also used for `RefundEscrow` on cancellation (`_cancelFromDest`, `_cancelFromSource`/`onGetResponse`), so the identical class of DoS also blocks a user's own refund path if any input token becomes non-transferable after escrow (e.g. later blacklisted) [7](#0-6) [8](#0-7) .

### Impact Explanation
This is a direct analog of the "Non-Liquidatable Accounts" bug class: an attacker-chosen token that reverts on transfer-out is combined with legitimate assets in a single list, then a settlement function iterates and unconditionally transfers each one, so a single poisoned token permanently DoSes the entire batch. Here the batch is an intent order's escrowed inputs:
- Funds are permanently frozen: escrowed input tokens (both the malicious one and any co-escrowed legitimate tokens) can never be withdrawn by anyone, since `_withdraw` will deterministically revert on every future call for that commitment.
- A solver who already delivered output tokens on the destination chain to fill the order is defrauded — they paid real value but the escrow release to them on the source chain is permanently blocked, i.e. concrete theft from the solver plus locked user funds.
- This qualifies as "permanent freezing of funds" and "unable to deliver settlement," both explicitly in-scope severe impacts.

### Likelihood Explanation
Any unprivileged user can create an order via `placeOrder` with a self-crafted/deployed ERC20 as one of `order.inputs` that blocks transfers to a targeted or arbitrary solver address (a well-known rugpull/honeypot pattern). No special privileges, governance, or malicious infrastructure roles are required — it is reachable purely by a single order-placement transaction plus a normal solver fill, matching the "single submitted transaction" bar for validity.

### Recommendation
- Validate that every `order.inputs[i].token` is on a protocol-maintained allow-list (or at minimum, do a pre-flight `transfer`/`transferFrom` probe) at `placeOrder` time, rejecting tokens with unusual transfer semantics.
- In `_withdraw`, isolate per-token transfer failures (e.g., via low-level `call` with `try/catch`-style handling, tracking a token as "unclaimed" and letting the beneficiary later sweep the other tokens individually) instead of reverting the whole batch when one token transfer fails.
- Alternatively, do not let the transfer of one input token block the release of unrelated input tokens or the finalization state (`_filled`, escrow bookkeeping) — decouple bookkeeping/finalization from per-token push transfers, and let recipients pull remaining tokens individually.

### Proof of Concept
1. Attacker deploys `EvilToken`, an ERC20 whose `transfer`/`transferFrom` reverts whenever `msg.sender == address(intentGateway)` and the recipient is any solver address (or a specific targeted solver).
2. Attacker calls `placeOrder` with `order.inputs = [ {token: EvilToken, amount: X}, {token: USDC, amount: Y} ]`, escrowing both tokens into `IntentGatewayV2`, and an attractive `order.output` to entice a solver.
3. A solver calls `fillOrder` on the destination chain, transferring the required output tokens to the beneficiary (`_fillCrossChain`, `evm/src/apps/intentsv2/ExtrinsicIntents.sol:164-219`), and the contract dispatches a `RedeemEscrow` message with `tokens = order.inputs` and `beneficiary = solver`.
4. Once relayed, `onAccept` → `_withdraw` (`evm/src/apps/intentsv2/IntentsBase.sol:451-470`) attempts `EvilToken.safeTransfer(solver, X)` first (or in whatever order the array iterates), which reverts, reverting the whole transaction.
5. Every subsequent relay attempt of the same commitment reverts identically. The escrowed `USDC` and `EvilToken` remain locked in the contract forever, and the solver, having already paid the order's output tokens, receives nothing back.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
