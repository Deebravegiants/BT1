This confirms the vulnerability: `Request#hmac` and `to_signable_string` bind the HMAC signature only to `@raw_body` [1](#0-0) , while `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from unauthenticated HTTP headers via `shopify_header` [2](#0-1) , and `Registry.process` only checks `Utils::HmacValidator.validate(request)` before dispatching to the handler with `request.shop` [3](#0-2) .

### Title
Webhook tenant identity (`shop-domain` header) is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, but the shop-domain, topic, and webhook-id used to route and process the webhook are taken from unauthenticated HTTP headers. Any party who can obtain one genuine, validly-signed webhook delivery (e.g., by installing the app on their own shop) can replay that exact body/HMAC pair while substituting a victim shop's domain in the `X-Shopify-Shop-Domain` header, and `ShopifyAPI::Webhooks::Registry.process` will accept it as authentic for the victim shop.

### Finding Description
`Utils::HmacValidator.validate` verifies a `VerifiableQuery` by recomputing an HMAC over `to_signable_string` and comparing it to the caller-supplied `hmac`, using the app's shared `api_secret_key` [4](#0-3) . For webhooks, `Request#to_signable_string` returns only `@raw_body`, and `Request#hmac` decodes the `hmac-sha256` header [5](#0-4) . Crucially, `shop`, `topic`, `api_version`, and `webhook_id` are pulled straight from headers with no cryptographic binding to the HMAC at all [2](#0-1) .

`Registry.process` performs exactly one check — `Utils::HmacValidator.validate(request)` — and then immediately builds `WebhookMetadata` using `request.topic`, `request.shop`, and `request.parsed_body` to invoke the app's registered handler [3](#0-2) . Because the equality actually being enforced is `HMAC(raw_body, api_secret_key) == received_hmac`, not `HMAC(raw_body + shop, api_secret_key) == received_hmac`, the `shop` value consumed by the handler is disjoint from what the signature attests to. This directly mirrors the reported bug class: an action (imprisoning an operator / dispatching a webhook handler for a specific tenant) is gated on a check (`state != 3` / valid HMAC) that does not actually correspond to the precondition that should hold (`state == 2` / HMAC covers the shop identity used).

Since `api_secret_key` is a single shared secret across every shop that installs the app, any user who installs the app on their own store receives a genuinely-signed webhook (correct body + correct HMAC + their own shop domain header) directly from Shopify. That user can capture this raw HTTP request and resend it to the app's public webhook endpoint, altering only the `X-Shopify-Shop-Domain` (or `X-Shopify-Hmac-Sha256`-adjacent, unsigned) header to name a different, victim shop. `HmacValidator.validate` still succeeds because it only checks the body against the shared secret; `Registry.process` then invokes the handler with `WebhookMetadata#shop` set to the victim's domain and attacker-chosen body content.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to guarantee for webhook delivery: cross-tenant data confusion/injection. Depending on how the host application's webhook handlers use `data.shop` (e.g., `app/uninstalled` triggering session/token deletion, `customers/data_request`, `shop/redact`, or business data writes keyed by shop), an attacker-controlled body can be forced to apply to a victim merchant's tenant, satisfying the "cross-tenant access" criteria for a High/Critical-impact finding.

### Likelihood Explanation
Any user can freely install a Shopify app on a development or trial store, receive a legitimately HMAC-signed webhook from Shopify, and replay it against the app's public webhook endpoint with only the shop header changed — no privileged credentials, access tokens, or `api_secret_key` knowledge are needed. The only mitigating factor is that the attacker must know or guess the victim's `.myshopify.com` shop domain, which is often discoverable.

### Recommendation
Bind the shop identity into what is verified: either include the `shopify-shop-domain` header value in `to_signable_string` (matching it against a session/shop record the app expects to have installed and rejecting shops the app doesn't recognize as currently installed), or independently verify that the `shop` header corresponds to a shop with a currently valid, stored offline session/access token before invoking the handler. At minimum, document and encourage host apps to cross-check `request.shop` against their own installed-shop registry rather than trusting the header as authenticated by the HMAC.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`, triggering Shopify to send a real webhook, e.g. `orders/create`, to the app's webhook endpoint with headers `X-Shopify-Topic: orders/create`, `X-Shopify-Hmac-Sha256: <valid>`, `X-Shopify-Shop-Domain: attacker.myshopify.com`, and a JSON body they control (e.g. by placing a test order with an attacker-chosen note/customer email field).
2. Attacker captures this HTTP request unmodified except for one header: replaces `X-Shopify-Shop-Domain` with `victim.myshopify.com`.
3. Attacker resends the modified request to the app's webhook endpoint.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` [6](#0-5) ; validation succeeds because the HMAC only covers `@raw_body`, which is unchanged.
5. The handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` where `shop == "victim.myshopify.com"` [7](#0-6) , causing the app to process attacker-controlled data as belonging to `victim.myshopify.com`.
