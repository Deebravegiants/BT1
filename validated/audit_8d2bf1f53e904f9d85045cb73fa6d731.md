### Title
Duplicate liquidation repayment legs are aggregated for seizure but only the first leg is pulled - (File: contracts/controller/src/positions/liquidation/apply.rs)

### Summary
A liquidator can submit multiple positive repayment legs for the same `HubAssetKey`. The liquidation planner aggregates duplicate legs and may mark the plan as a full close, but execution later retrieves only the first matching offered leg and pulls that smaller amount. Because seizure sizing still uses the aggregated/capped repayment value, the liquidator can receive collateral as though they repaid the full debt while actually paying only part of it.

### Finding Description
`calculate_repayment_amounts` first calls `aggregate_positive_payments`, which sums duplicate `HubAssetKey` entries into one repayment plan entry and caps the aggregate at the account's debt. [1](#0-0) [2](#0-1) 

On the full-close path, `apply_liquidation_repayments` receives the original unmerged offers and is documented to pull the merged offered amount, but `offered_amount` returns only the first vector entry whose key matches. [3](#0-2) [4](#0-3) [5](#0-4) 

The resulting pool repayment action uses only the measured amount received from that first leg, while the planned `RepayEntry.amount` remains the aggregate capped repayment. [6](#0-5)  Collateral seizure is nevertheless calculated from `repayment.repay_usd`, which was derived from the merged plan rather than the actual amount pulled. [7](#0-6) 

### Impact Explanation
Any unprivileged liquidator can repay less than the planned amount while the victim loses collateral sized for the larger planned repayment. For example, against a debt of `100`, offers of `[60, 60]` for the same debt market aggregate to `120`, are capped to a `100` repayment plan, and then execute a pull of only `60`. The victim can therefore lose approximately the collateral backing a `100` repayment while retaining roughly `40` of debt.

This is theft of user collateral because the excess seized collateral is transferred or credited according to the liquidation mode while the missing repayment remains outstanding. [8](#0-7) 

### Likelihood Explanation
The vulnerable path is reachable through the permissionless `liquidate(liquidator, account_id, debt_payments, seize_mode)` entrypoint whenever an account has health factor below one. [9](#0-8)  Duplicate positive payment legs are expressly supported by ordinary payment aggregation rather than rejected. [10](#0-9)  The attacker only needs to split a sufficient offered repayment into at least two entries for the same debt market so that the first entry is smaller than the aggregate.

### Recommendation
Use the already-aggregated payment list when constructing full-close pulls, or make `offered_amount` aggregate every matching offer with checked addition. A stronger fix is to pass the normalized `RepayEntry.amount` directly and avoid re-querying the raw offer vector; the plan and execution should share one canonical payment representation. Add a regression test where two duplicate legs cover a full debt and assert that either the summed amount is pulled or seizure is based only on measured receipts.

### Proof of Concept
Assume a liquidatable account owes `100` units of debt market `D` and has enough collateral for a full close.

1. Call `liquidate` with `debt_payments = [(D, 60), (D, 60)]`.
2. Planning aggregates the legs into `(D, 120)`, caps the amount at `100`, records a refund of `20`, and produces a repayment plan of `100`. [11](#0-10) 
3. Full-close execution calls `offered_amount`; `Vec::iter().find` returns only `(D, 60)`, so `transfer_amount_measured` pulls `60`. [4](#0-3) [5](#0-4) 
4. The pool action repays `60`, but `NormalizedRepaymentPlan.repay_usd` remains the USD value of `100`. [6](#0-5) 
5. `calculate_seized_collateral` computes `total_seizure_usd = repay_usd * (1 + bonus)` from the `100` plan and seizes collateral sized for that amount, even though only `60` was paid. [7](#0-6) 

Expected result: the victim loses collateral corresponding to the full `100` repayment while approximately `40` units of debt remain unpaid, giving the liquidator the unpaid principal plus applicable liquidation bonus as excess collateral.

/// Executes transfer-mode seizure: burns shares, debits pool cash, and pays
/// underlying to the liquidator after withholding the protocol fee.
pub(crate) fn apply_liquidation_seizures(
    env: &Env,
    liquidator: &Address,
    account: &mut Account,
    seized: &Vec<SeizeEntry>,
    cache: &mut Context,
) {
    let mut entries: Vec<PoolWithdrawEntry> = Vec::new(env);
    for entry in seized.iter() {
        enforce_spoke_asset_flags(
            env,
            cache,
            account.spoke_id,
            &entry.hub_asset,
            FreezePolicy::SeizureLeg,
        );

        let position: AccountPosition =
            (&expect_invariant(env, account.supply_positions.get(entry.hub_asset.clone()))).into();
        entries.push_back(PoolWithdrawEntry {
            action: make_pool_action(&position, entry.amount, entry.hub_asset),
            protocol_fee: entry.protocol_fee,
        });
    }
    apply_withdraw_batch(
        env,
        account,
        liquidator,
        WithdrawKind::Liquidation,
        events::PositionAction::LiqSeize,
        &entries,
        cache,
