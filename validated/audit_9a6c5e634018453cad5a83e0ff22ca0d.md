### Title
Assuming `tickets[beforeCount]` aligns with the caller's new intent breaks ticket/intentHash reporting when the relay's "already processed" response returns a differently-shaped `intent_hashes` array - (File: packages/intents-sdk/src/intents/intent-executer-impl/intent-executer.ts)

### Summary
`signAndSendIntent` composes `[...before, newPayload, ...after]` and unconditionally indexes the relayer's returned `tickets` array at `beforeCount = signedIntents?.before?.length ?? 0` to pick "the" ticket for the caller's freshly signed intent. This positional assumption is not validated against the actual returned array, and the relay layer itself has a documented code path (`reason === "already processed"`) where the returned `intent_hashes` can legitimately have a different shape than the submitted `signed_datas`, breaking the invariant that index `beforeCount` in `tickets` corresponds to the new payload.

### Finding Description
Equality claimed to hold but not actually enforced: `tickets[beforeCount] == intentHash(newPayload_signed_by_caller)`.

Code path:
- `composeMultiPayloads` builds `composedPayloads = [...before, newPayload, ...after]` [1](#0-0) .
- `signAndSendIntent` calls `this.intentRelayer.publishIntents(...)` and then blindly does `const newIntentTicket = tickets[beforeCount]` with no check that `tickets.length === composedPayloads.length` or that the entry actually corresponds to `newPayload` [2](#0-1) .
- The relayer implementation (`IntentRelayerPublic.publishIntents`) passes through whatever `intent_hashes` the solver-relay JSON-RPC response contains [3](#0-2) .
- Crucially, `parsePublishIntentsResponse` in the shared HTTP client explicitly treats a `"already processed"` failure reason as success and forwards `response.intent_hashes` unchanged: `if (response.reason === "already processed") { return Ok(response.intent_hashes); }` [4](#0-3) . There is no code anywhere that cross-checks the length or ordering of `response.intent_hashes` against `signed_datas` (i.e., `composedPayloads`) in this "already processed" branch, unlike the normal `"OK"` branch, which is also unchecked but at least reflects a batch the relay itself constructed the response for atomically.

Exploit flow: a counterparty supplies a `signedIntents.before` (or `.after`) array to an integrator/SDK caller for atomic composition (this is a documented, intended feature reachable via `sdk.signAndSendIntent({ signedIntents })`). If one of those pre-signed payloads has already been submitted/settled before (e.g., replayed intentionally by the counterparty, or simply resubmitted because of a retry on the caller's side), the relay can respond with `status: "FAILED", reason: "already processed"` for the whole batch, together with an `intent_hashes` array that does not have the same 1:1 index correspondence to `composedPayloads` (the relay may report fewer hashes, hashes for only the already-processed subset, or the hashes in a different arrangement, since the response schema does not document guaranteed alignment for this failure reason). The SDK will still compute `tickets[beforeCount]` and return it to the caller as `intentHash` for the caller's own withdrawal via `sdk.ts`'s `signAndSendIntent` -> `{ intentHash: ticket }` [5](#0-4) .

Existing guards do not catch this: there is no `assert(tickets.length === composedPayloads.length)`, no correlation of `tickets[i]` to `computeIntentHash(composedPayloads[i])`, and the "already processed" branch is explicitly carved out to succeed without validating the returned hash list shape.

### Impact Explanation
The caller (an ordinary integrator/user calling `signAndSendIntent` with `signedIntents.before/after` supplied by a counterparty) can receive a `ticket`/`intentHash` that does not correspond to their own newly signed intent, but instead to one of the counterparty's pre-signed payloads. The caller/integrator then polls/settles (`waitForSettlement`) against the wrong hash, so the actual settlement status of their own withdrawal is never correctly tracked — a status/hash misreport. This matches the High severity category ("a status or hash misreport making an integrator credit or refund twice") since the integrator could believe the wrong intent settled/failed and act on stale or incorrect state for the real withdrawal, with no way to recover the correct ticket for the actual signed payload after the fact (the SDK discards the true index-to-hash mapping).

### Likelihood Explanation
This requires: (1) the caller to use the `signedIntents` composition feature with `before`/`after` payloads supplied externally (a supported, documented flow), and (2) the relay to return the `"already processed"` failure reason with a hash array whose shape/order does not match `composedPayloads`. Reaching (2) does not require compromising the relay — it is a normal, defined response for already-processed multi-payload submissions, and a counterparty can trigger it simply by having previously (or concurrently) submitted one of the pre-signed intents they hand to the caller. No special privileges are needed by the attacker/counterparty beyond crafting their own pre-signed payload and submitting/resubmitting it. This is repeatable per composed submission.

### Recommendation
Do not rely on positional indexing into the relayer's returned ticket array without validation. Either (a) have `publishIntents`/`parsePublishIntentsResponse` guarantee and assert a length/order match between `signed_datas` and `intent_hashes` (including in the `"already processed"` branch, or fail loudly if it can't be established), or (b) in `intent-executer.ts`, independently compute `computeIntentHash(multiPayload)` for the new payload locally (as already done for `onBeforePublishIntent`) and return that computed hash directly as the ticket for the caller's new intent rather than trusting `tickets[beforeCount]`.

### Proof of Concept
```ts
// intent-executer.test.ts
it("returns wrong ticket when relay's already-processed response array is shorter/misaligned", async () => {
  const { intentSigner, intentRelayer } = setupMocks();
  const salt = Uint8Array.from([1, 2, 3, 4]);

  const prependIntent = await intentSigner.signIntent(
    defaultIntentPayloadFactory(salt, { verifying_contract: "" }),
  );

  // Relay reports "already processed" and returns an intent_hashes array
  // that does NOT align 1:1 with composedPayloads (only 1 entry for 2 submitted payloads)
  vi.mocked(intentRelayer.publishIntents).mockResolvedValue([
    "hash-of-prepend-intent-already-processed",
  ]);

  const exec = new IntentExecuter({
    envConfig: configsByEnvironment.production,
    intentRelayer,
    intentSigner,
  });

  const result = await exec.signAndSendIntent({
    intents: [
      { intent: "transfer", receiver_id: "alice.near", tokens: { "wrap.near": "1000" } },
    ],
    signedIntents: { before: [prependIntent] },
    salt,
  });

  // beforeCount = 1, so newIntentTicket = tickets[1] === undefined,
  // demonstrating the caller's ticket does not equal the actual hash of their own new payload.
  const actualNewIntentHash = await computeIntentHash(
    await intentSigner.signIntent(
      defaultIntentPayloadFactory(salt, {
        verifying_contract: configsByEnvironment.production.contractID,
        intents: [{ intent: "transfer", receiver_id: "alice.near", tokens: { "wrap.near": "1000" } }],
      }),
    ),
  );

  expect(result.ticket).not.toBe(actualNewIntentHash);
  expect(result.ticket).toBeUndefined(); // or equal to the counterparty's pre-signed hash in other misalignment shapes
});
```
This demonstrates that `result.ticket` (returned to the caller as `intentHash`) does not equal the actual identifier of the caller's own newly-signed intent, confirming the STATUS TRUTH equality is broken.

function composeMultiPayloads(
	newPayload: MultiPayload,
	signedIntents?: SignedIntentsComposition,
): MultiPayload[] {
	if (!signedIntents) {
		return [newPayload];
	}

	const result: MultiPayload[] = [];

	// Add "before" intents first
	if (signedIntents.before && signedIntents.before.length > 0) {
		result.push(...signedIntents.before);
	}

	// Add the new payload
	result.push(newPayload);

	// Add "after" intents last
	if (signedIntents.after && signedIntents.after.length > 0) {
		result.push(...signedIntents.after);
	}

	return result;
}

	public async signAndSendIntent(
		args: SignAndSendArgs,
	): Promise<IntentPublishResult> {
		const intentSigner = args.signer ?? this.intentSigner;
		assert(intentSigner != null, "Intent signer is not provided");

		const intentExecuter = new IntentExecuter({
			envConfig: this.envConfig,
			logger: args.logger,
			intentSigner,
			intentRelayer: this.intentRelayer,
			intentPayloadFactory: args.payload,
			onBeforePublishIntent: args.onBeforePublishIntent,
		});

		const { ticket } = await this.withSaltRetry(args, async (salt) =>
			intentExecuter.signAndSendIntent({
				intents: args.intents,
				salt,
				relayParams: args.relayParams,
				signedIntents: args.signedIntents,
			}),
		);

		return { intentHash: ticket };
	}
