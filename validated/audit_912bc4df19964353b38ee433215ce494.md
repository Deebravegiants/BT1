### Title
Unauthenticated cross-chain calldata dispatch — `on_accept` derives the RuntimeCall origin from unverified message bytes when no signature is supplied - (File: modules/pallets/hyper-fungible-token/src/module.rs)

### Summary
`pallet-hyper-fungible-token`'s `IsmpModule::on_accept` lets an incoming cross-chain transfer carry an optional `SubstrateCalldata` payload that is dispatched as a full, arbitrary `RuntimeCall` on the destination chain [1](#0-0) . When the payload includes a real signature, the origin is cryptographically bound to the beneficiary via Ed25519/Sr25519/ECDSA verification over `(nonce, runtime_call)` [2](#0-1) . But when `substrate_data.signature` is `None`, the origin used to dispatch the call is derived purely from the `message.from` bytes embedded in the ABI-decoded message body, with zero cryptographic verification: [3](#0-2) 

### Finding Description
The `Message` struct dispatched over ISMP is `{from, to, amount, data}`, and `data` optionally contains SCALE-encoded `SubstrateCalldata{ signature: Option<Vec<u8>>, runtime_call: Vec<u8> }` [4](#0-3) . `on_accept` only authenticates the *outer* `PostRequest.from` field (the sending EVM contract address) against the `ContractToAsset` registry [5](#0-4) . The *inner* `message.from` field — a raw byte string chosen by whatever logic assembled the ABI body on the source chain — is never independently verified by the pallet itself before being used to compute a dispatch origin:

The only defense applied to the dispatched call is `BaseCallFilter` (blocking globally-filtered dispatchables) — there is no requirement that the account whose privileges are being exercised ever authorized this specific call [6](#0-5) . On the Rust (Substrate→EVM) sending side, `message.from` is correctly bound to `ensure_signed(origin)` [7](#0-6) , so cross-chain security for that direction rests entirely on the destination EVM contract also binding its own `message.from` field to an on-chain-authenticated `msg.sender` (or equivalent) when constructing its outbound `Message`. Because `ContractToAsset` only checks that the *source contract address* is a registered token contract — not that the *specific message content* was constructed correctly — any code path in a registered token contract (custom wrapped-token variants, forwarding/relayer helpers, upgraded implementations, or an as-yet-undiscovered bug) that lets `message.from` diverge from the actual authenticated caller allows an attacker to impersonate any substrate account and dispatch an arbitrary `RuntimeCall` (subject only to `BaseCallFilter`) as that account, with no signature check at all. This mirrors the CVE-2023-1183 pattern: a "script"/privileged action's target/identity is taken from attacker-influenceable content rather than being independently, cryptographically re-verified at the point of use.

### Impact Explanation
If `message.from` can be made to disagree with a truly authenticated caller (e.g. via a forwarding/misconfigured/buggy registered token contract, or any future contract variant that copies `msg.sender`-adjacent data incorrectly), an attacker can dispatch arbitrary `RuntimeCall`s as any substrate `AccountId`/EVM-address-derived account on the destination chain — enabling theft of funds (e.g. `Balances::transfer` from a victim account), governance/asset-registry manipulation, or any other action the impersonated account is authorized to perform. This is a cross-chain unauthorized app action / potential theft-of-funds primitive reachable from a single relayed PostRequest.

### Likelihood Explanation
Exploitability depends on whether any registered source-chain contract can be induced to encode an unauthenticated `message.from`. The core Rust-side logic itself performs **no cryptographic check** in the unsigned branch — it is a pure trust boundary shifted entirely onto the correctness of every current and future registered EVM token contract's encoding logic. Given `register_token`/`update_token` allow governance-controlled additions of new source contracts over time [8](#0-7) , the attack surface for this trust assumption grows with every new integration, and a single mistake anywhere in that surface directly yields unauthenticated arbitrary-call dispatch.

### Recommendation
Do not treat `message.from` as authenticated by default. Either (a) require the signature to always be present for calldata execution (removing the unsigned branch entirely), or (b) additionally bind the unsigned path's authorization to something independently verifiable at the ISMP layer (e.g., requiring `message.from == PostRequest.from`'s verified sender field maintained by the ISMP request commitment itself, not application-body bytes), so that impersonation is not possible even if a registered source contract mis-encodes the body.

### Proof of Concept
1. Register (via governance `register_token`) or otherwise cause the pallet to trust a source EVM contract address `C` for state machine `S`.
2. From `C`, emit a `PostRequest` to the pallet whose ABI-encoded `Message.data` decodes to `SubstrateCalldata{ signature: None, runtime_call: <encoded Balances::transfer_allow_death{dest: attacker, value: victim_balance}> }` and `Message.from` set to the 20-byte EVM address that `T::EvmToSubstrate::convert` maps to the victim's substrate account (not the actual transaction's authenticated sender).
3. Relay the request through `pallet-ismp`'s `handle_unsigned` with a valid state/consensus proof for `PostRequest` origin `C`.
4. `on_accept` computes `origin = T::EvmToSubstrate::convert(victim_evm_address)` and dispatches the `RuntimeCall` as `RawOrigin::Signed(victim)` without any signature ever having been produced by the victim, at `modules/pallets/hyper-fungible-token/src/module.rs:176-200`, draining the victim's balance to the attacker.

		/// Registers a new token with per-chain contract configuration
		#[pallet::call_index(1)]
		#[pallet::weight(T::WeightInfo::register_token(registration.chains.len() as u32))]
		pub fn register_token(
			origin: OriginFor<T>,
			registration: TokenRegistration<AssetId<T>>,
		) -> DispatchResult {
			T::CreateOrigin::ensure_origin(origin)?;

			let local_decimals = if registration.local_id == T::NativeAssetId::get() {
				T::Decimals::get()
			} else {
				<T::Assets as fungibles::metadata::Inspect<T::AccountId>>::decimals(
					registration.local_id.clone(),
				)
			};

			NativeAssets::<T>::insert(registration.local_id.clone(), registration.native);

			let chains: Vec<StateMachine> = registration.chains.keys().cloned().collect();
			for (chain, config) in registration.chains {
				// This pallet bridges substrate <-> EVM only; reject non-EVM peers.
				if !matches!(chain, StateMachine::Evm(_)) {
					return Err(Error::<T>::NonEvmPeerChain.into());
				}
				ensure!(
					config.decimals >= local_decimals,
					Error::<T>::ErcDecimalsBelowLocal
				);
				let token_contract = config.token_contract.0.to_vec();
				TokenContracts::<T>::insert(
					chain,
					registration.local_id.clone(),
					token_contract.clone(),
				);
				ContractToAsset::<T>::insert(
					chain,
					token_contract,
					registration.local_id.clone(),
				);
				Precisions::<T>::insert(registration.local_id.clone(), chain, config.decimals);
			}

			Self::deposit_event(Event::<T>::TokenRegistered {
				asset_id: registration.local_id,
				native: registration.native,
				chains,
			});
			Ok(())
		}
