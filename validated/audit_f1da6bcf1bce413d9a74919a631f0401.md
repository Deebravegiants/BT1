### Title
Unauthenticated Livestream TCP Server Allows Unbounded Memory Allocation from Attacker-Controlled Length Prefix - ([File: src/agents/livestream/upstream.rs])

### Summary
The livestream agent's `Upstream` implementation binds an unauthenticated TCP listener on `0.0.0.0:9201` and reads a 4-byte length prefix directly from the network connection, then allocates a buffer of that exact attacker-controlled size with no upper bound check, mirroring the root cause of the reported SEDA bug class: an operation that consumes attacker-controlled length/resource values without any metering or bounds validation before performing unbounded work/allocation.

### Finding Description
`EventReader::poll_stream` reads 4 bytes from the socket into `self.len`, then immediately does: [1](#0-0) 
allocating `vec![0; u32::from_be_bytes(self.len) as usize]` — up to ~4 GiB — with no sanity/maximum-size check before allocation. The listener itself is bound without any authentication: [2](#0-1) 
Any client that can reach TCP port 9201 on the Orb (no credentials, no protocol handshake, no signup/session state required) can send a 4-byte length header claiming a multi-gigabyte payload and force the process to attempt a large allocation immediately, exactly as in the reported bug where `result_data_length` could be set to an arbitrary size with no gas/cost check before the write occurred. This is analogous to the missing `apply_gas_cost` call in `call_result_write`: the root cause in both cases is consuming an attacker-supplied size field to drive execution/memory work without any metering, rate limit, or maximum bound enforced beforehand.

### Impact Explanation
Repeated connections each supplying a large declared length (even without ever sending the actual payload bytes) can drive the Orb's `livestream` agent process to allocate large buffers repeatedly, exhausting memory on the embedded Jetson device and causing the process (and potentially the broader `orb-core` runtime it is part of via `agentwire`) to crash or become unresponsive. Because the Orb is the field device performing signups, forcing repeated crashes/restarts of this agent or memory pressure across the system can degrade or halt the biometric signup pipeline — directly analogous to the "chain delays/halts" impact described in the source report, translated to "signup service unavailability on the device."

### Likelihood Explanation
This requires only unauthenticated network reachability to TCP port 9201 on the Orb — no privileged keys, no physical/hardware access, and no valid signup session. The `livestream` module is compiled in as an `agents` submodule and reachable whenever the `livestream` feature is active; I was unable to fully confirm within available context whether this feature is enabled in the standard production build path (the `Cargo.toml` feature-gating details for `livestream` were not fully retrievable through the index), so the likelihood is contingent on that feature being active in deployed units. This uncertainty should be verified directly in the repository/build configuration rather than assumed.

### Recommendation
Enforce a maximum accepted payload length (e.g., a small constant matching the largest legitimate livestream event message) before allocating `self.buf`, and reject/close connections that declare an oversized length instead of allocating immediately. Consider adding authentication/allow-listing for the livestream TCP listener so it cannot be reached by arbitrary unauthenticated network clients.

### Proof of Concept
1. Confirm the `livestream` feature is compiled into the target Orb build (`src/agents/mod.rs` gates the module behind `#[cfg(feature = "livestream")]`) — [3](#0-2) .
2. From any machine with network access to the Orb's IP, open a raw TCP connection to port 9201.
3. Send 4 bytes representing `u32::MAX` (`0xFF 0xFF 0xFF 0xFF`) as the big-endian length prefix, per the read logic in `poll_stream` — [4](#0-3) .
4. Observe the process attempt to allocate a ~4 GiB buffer (`vec![0; u32::from_be_bytes(self.len) as usize]`) with no bound check, then repeat rapidly from multiple connections to exhaust device memory.
