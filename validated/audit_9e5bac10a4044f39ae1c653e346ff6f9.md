## Title
`ShopifyAPI::Webhooks::Registry.process` trusts the `shop` header without HMAC coverage, allowing cross-tenant webhook spoofing via replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, and `ShopifyAPI::Webhooks::Registry.process` uses the `shop` value taken from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header — a value that is never included in the HMAC-signed content. This breaks the identity binding `HMAC-verified bytes == identity used by handler`, letting an attacker who obtains one valid `(raw_body, hmac)` pair replay it with an arbitrary `shop` header value and have it accepted as authentic for a different tenant.

### Finding Description
The webhook verification flow is:

1. `Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the provided HMAC via `OpenSSL.secure_compare`. [1](#0-0) [2](#0-1) 

2. For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` — the shop domain, topic, webhook id, and api version headers are excluded from the signed content entirely. [3](#0-2) 

3. Despite this, `shop` (parsed straight from the unauthenticated header) is passed directly to the handler as the tenant identity: [4](#0-3) 

The equality this is supposed to enforce is: `shop value trusted by handler == shop value that was cryptographically bound to this specific request`. In reality it is: `shop value trusted by handler == arbitrary attacker-supplied header`, since the HMAC only proves "this raw body was produced by someone possessing `api_secret_key`" — it says nothing about which shop that body was destined for.

### Impact Explanation
This is a cross-tenant identity-binding break analogous to the reported bug class ("a field acted on but not covered by the HMAC"). Any host application following the gem's own documented usage pattern (`docs/usage/webhooks.md`, `handle(data:)` using `data.shop` to key persistence/side effects) is directly exposed: an attacker who can obtain any single valid `(body, hmac)` pair signed with the app's secret — for example by installing the app on a shop they control and capturing a legitimate webhook delivery — can replay that exact body/HMAC to the app's webhook endpoint while substituting the `shop` header for a victim shop already using the app. `HmacValidator.validate` will still succeed (it never looked at the header), and `Registry.process` will hand the handler `shop: <victim-shop>` with attacker-chosen body content, causing the app to attribute/act on that payload as if it originated from the victim tenant. Depending on what the handler does with `data.shop` (e.g., look up per-shop credentials, trigger per-shop side effects, or write into per-shop data stores keyed by `data.shop`), this enables cross-tenant data corruption or unauthorized actions scoped to another merchant's account — meeting the "cross-tenant access" criterion for Critical impact.

### Likelihood Explanation
Moderate-to-high. The precondition (a valid `(raw_body, hmac)` pair) is trivially obtainable by any developer/attacker capable of installing the target app on a shop they control (a normal, unprivileged action for any Shopify merchant/developer) and capturing one webhook delivery for a topic whose body content doesn't need shop-specific data (e.g., `app/uninstalled`, or any webhook whose body an attacker can otherwise engineer/normalize to match a victim's expected shape). No access token, `client_secret`, or privileged access to the target host app is required — only network access to the app's public webhook endpoint and a legitimately obtained payload/HMAC pair from any install of the app.

### Recommendation
Bind the shop identity (and other header fields relied upon by handlers) into the HMAC-signed content, or independently verify that the `shop` header corresponds to a shop with an active, known installation/session before dispatching to the handler. At minimum, `to_signable_string` for `Webhooks::Request` should not allow the `shop`, `topic`, and `webhook_id` values used by `WebhookMetadata` to be trusted purely from unauthenticated headers when the HMAC covers only the body; document clearly (or enforce in-gem) that host applications must not treat `data.shop` as authenticated unless it is cross-checked against known installed shops.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and receives a legitimate webhook delivery for topic `app/uninstalled` (or any topic with attacker-independent body content), capturing `raw_body` and header `x-shopify-hmac-sha256`.
2. Attacker sends a POST to the app's webhook endpoint with the same `raw_body` and `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` parses `shop` from the spoofed header. [5](#0-4) 
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes HMAC over `raw_body` — this passes because the body/HMAC pair is legitimately signed. [6](#0-5) 
5. `handler.handle(data: WebhookMetadata.new(..., shop: request.shop, ...))` is invoked with `shop = "victim-shop.myshopify.com"`, causing the host application's handler to process attacker-controlled data under the victim's tenant identity. [7](#0-6)
