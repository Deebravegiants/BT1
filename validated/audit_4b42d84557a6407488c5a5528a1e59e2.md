### Title
Cross-tenant webhook spoofing via unauthenticated `shop-domain` header not covered by HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by HMAC-verifying the raw request body, then trusts the `shop` value taken from an unsigned HTTP header to attribute the webhook to a tenant. Because the shop identity is not part of the signed payload, a party who has captured any single valid `(raw_body, hmac)` pair signed with the app's shared `api_secret_key` can replay that same body while substituting an arbitrary `shop-domain` header, and the signature check still passes — causing the webhook to be processed as if it belonged to a different, victim tenant.

### Finding Description
`Registry.process` validates a webhook exclusively via `Utils::HmacValidator.validate(request)`, then constructs the tenant-scoped payload using `request.shop`: [1](#0-0) 

`Request#hmac` and `Request#to_signable_string` show that the HMAC signature only ever covers the raw body, never the headers: [2](#0-1) 

`Request#shop` simply reads the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` header: [3](#0-2) 

`HmacValidator.validate` in turn only ever compares the received HMAC against a signature computed from `verifiable_query.to_signable_string`, i.e. the body — the `shop` field never enters the equality it verifies: [4](#0-3) 

The equality that is actually checked is:
`HMAC(api_secret_key, raw_body) == received_hmac`

but the equality the application (via `WebhookMetadata.shop`) implicitly relies on for tenant routing is:
`request.shop == "the shop that produced this signed body"`

These two are not bound together. Contrast this with `ShopifyAPI::Auth::Oauth::AuthQuery`, where `shop` is explicitly folded into `to_signable_string` and therefore is cryptographically bound to the signature: [5](#0-4) 

No equivalent binding exists for webhook requests. Since a single app typically shares one `api_secret_key` across every shop that installs it (multi-tenant SaaS pattern), any entity capable of observing one legitimate webhook body+HMAC pair sent to the app's shared webhook endpoint (e.g., a merchant/staff member of Shop A who controls that shop and can trigger webhooks and observe the endpoint traffic, or anyone who intercepts one delivery) can replay the identical body with a forged `x-shopify-shop-domain` header naming Shop B. `Utils::HmacValidator.validate` will accept it because it never inspects the shop header, and `Registry.process` will hand `WebhookMetadata.new(shop: "shop-b...", body: <shop-a's body>, ...)` to the app's handler.

### Impact Explanation
This breaks the tenant isolation guarantee the gem is expected to provide when it exposes `WebhookMetadata#shop` as the authenticated tenant identifier for a verified webhook. An application using this field (as documented/intended) to route or store data per-shop can be made to attribute one tenant's data to another tenant, corrupting or leaking data across tenant boundaries — a cross-tenant access impact.

### Likelihood Explanation
Exploitation requires only one observed valid `(body, hmac)` pair for the app's secret, which is realistic in a multi-tenant SaaS app: any shop that installs the app is itself a source of legitimate webhook deliveries the attacker (as that shop's owner/staff) can capture. No access to `api_secret_key`, access tokens, or the target shop's own credentials is needed to perform the replay against the shared webhook endpoint.

### Recommendation
Bind the shop identity into the value that is authenticated: either include the shop domain (and topic) as part of the HMAC-signed payload verification, or after verifying the HMAC, cross-check `request.shop` against the set of shop domains actually installed/known to the app (e.g., against stored sessions) before trusting it for tenant routing, rejecting requests where the shop is not a known, currently-installed tenant.

### Proof of Concept
1. App `App1` (single `api_secret_key`) is installed on `shop-a.myshopify.com` and `shop-b.myshopify.com`, both delivering webhooks to the same endpoint that calls `ShopifyAPI::Webhooks::Registry.process`.
2. Attacker owns/administers `shop-a.myshopify.com`, triggers an `orders/create` webhook, and captures the exact `raw_body` and `X-Shopify-Hmac-Sha256` header Shopify sent.
3. Attacker replays that same `raw_body` and `X-Shopify-Hmac-Sha256` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: shop-b.myshopify.com`.
4. `Utils::HmacValidator.validate` recomputes `HMAC(api_secret_key, raw_body)` and it matches the replayed header — validation succeeds.
5. `Registry.process` builds `WebhookMetadata.new(shop: "shop-b.myshopify.com", body: <shop-a's order data>, ...)` and invokes the app's handler, which processes Shop A's order data as if it belonged to Shop B.
