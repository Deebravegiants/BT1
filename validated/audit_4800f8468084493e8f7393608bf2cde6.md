### Title
Truncated User-ID Accepted by QR-Code Regex Enables Misattributed Signup/Operator Identity - (File: src/plans/qr_scan/user.rs)

### Summary
The `QR_CODE_V2` regex used to parse user (and operator) QR codes on the Orb makes the last two UUID groups (`-XXXX-XXXXXXXXXXXX`, 80 bits) optional, allowing a `user_id` as short as the first 16 hex characters (64 bits) to be accepted as a fully valid identifier. This mirrors the M-8 Sherlock finding, where an identifier meant to span the full value space (`uint256` token ID) was instead constrained to a narrower type (`uint128`), causing legitimate/expected identifiers outside the narrower range to be silently mismatched. Here the narrowing happens on the identity-string side: a value meant to uniquely identify a user/operator across the full 128-bit UUID space is accepted in a truncated 64-bit form, and the truncated string is used verbatim as the canonical `user_id` in signup attribution, signature computation, and the info.json audit record.

### Finding Description
`QR_CODE_V2` in `src/plans/qr_scan/user.rs` defines the `user_id` capture group with the trailing two UUID segments wrapped in an optional non-capturing group: [1](#0-0) 

This means a code such as `userid:3bcf883d-ce22-4a03:1` parses successfully and yields `user_id = "3bcf883d-ce22-4a03"` — an 18-character, 64-bit-entropy string — with no length/format normalization back to the full 128-bit UUID, as confirmed by the `test_v2_shortened` unit test: [2](#0-1) 

`Data::from_v2` stores this truncated value directly into `Data.user_id` with no validation that it corresponds to a genuine, fully-specified UUID: [3](#0-2) 

The same `Data` struct/schema is reused for both user and operator QR codes (`src/plans/qr_scan/operator.rs` delegates to `user::Data::try_parse`), so a truncated ID can be substituted for either the person being enrolled or the operator running the enrollment: [4](#0-3) 

This truncated `user_id` then becomes the authoritative identity value in multiple security-relevant paths:
- It is sent verbatim as `userId`/`distributorId` in the signup POST request that creates/attributes the backend signup record: [5](#0-4) 
- It is mixed into the iris-code signature computed and signed by the secure element, binding biometric data to this identifier: [6](#0-5) 
- It is salted-hashed into the personal-custody-package `info.json`, which is the audit trail linking `operator_id`/user identity to a signup: [7](#0-6) 

Because the regex intentionally narrows a value that should span the full UUID space (analogous to `uint256`→`uint128` in the referenced report) down to a shorter prefix, two distinct full UUIDs sharing the same 64-bit prefix — or a maliciously/accidentally truncated QR code — are treated as fully valid and indistinguishable identifiers throughout signup attribution, signature binding, and audit hashing, with no re-validation against the canonical 128-bit ID format used elsewhere (`orb_qr_link::decode_qr`, `wld-data-id`'s `Uuid`-backed `SignupId`).

### Impact Explanation
An identity string that is supposed to uniquely and fully identify a user or operator (128-bit UUID) can be silently accepted in a much narrower, 64-bit form. This weakens the guarantee that `distributorId`/`userId` sent to the backend, the value bound into the cryptographically-signed iris-code signature, and the value hashed into the custody-package audit record all correspond to one unambiguous identity. This can lead to misattributed signups or operator identity confusion — the exact impact class called out as acceptable (misattributed signup / identity binding failure), directly analogous to the `reduceERC721Fee` bug where an operation silently targeted/represented the wrong entity due to insufficient identifier width.

### Likelihood Explanation
Any unprivileged party presenting a QR code to the Orb (as a "user" or "operator" QR code) can trigger this path — no special privileges are needed, since `try_parse` is invoked on arbitrary scanned QR text in `src/plans/qr_scan/mod.rs`. The shortened form is explicitly exercised and accepted by existing tests, confirming it is a live, reachable code path rather than dead code.

### Recommendation
Remove the optional trailing UUID groups from `QR_CODE_V2` (and the corresponding acquisition-extension regex) so that `user_id` must always match the full 128-bit UUID format, or explicitly reject/normalize shortened IDs before they are used for signup attribution, signature computation, or audit hashing.

### Proof of Concept
1. Present a QR code encoding `userid:3bcf883d-ce22-4a03:1` (missing the last two UUID groups) to the Orb as either the operator or user QR code. [2](#0-1) 
2. `Schema::try_parse` matches via `QR_CODE_V2` and returns `Data { user_id: "3bcf883d-ce22-4a03", .. }` without error. [8](#0-7) 
3. This truncated value is forwarded as `userId`/`distributorId` to the signup backend, mixed into the SHA-256 iris-code signature, and salted-hashed into `info.json`, all treating it as if it were a fully-specified, unique 128-bit identifier. [5](#0-4) [6](#0-5)

    let mut ctx = Context::new(&SHA256);
    ctx.update(ORB_ID.as_str().as_bytes());
    ctx.update(user_qr_code.user_id.as_bytes());
    ctx.update(pipeline.v2.ir_net_version.as_bytes());
    ctx.update(pipeline.v2.iris_version.as_bytes());
    ctx.update(pipeline.v2.eye_left.iris_code.as_bytes());
    ctx.update(pipeline.v2.eye_left.mask_code.as_bytes());
    ctx.update(pipeline.v2.eye_left.iris_code_version.as_bytes());
    ctx.update(pipeline.v2.eye_right.iris_code.as_bytes());

    ctx.update(pipeline.v2.eye_right.iris_code_version.as_bytes());
