### Title
Webhook HMAC only signs the request body, so the `shop-domain` and `topic` headers are unauthenticated and can be forged in an otherwise-valid webhook replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so `Utils::HmacValidator.validate` computes/verifies the HMAC over the JSON body alone. The `shop-domain` and `topic` HTTP headers, which are read via `request.shop` / `request.topic` and passed straight into the handler as the trusted tenant identifier, are never included in the signed material. An attacker who can obtain one legitimately-signed webhook (e.g. from their own shop that has the target app installed) can replay the exact same body+HMAC while substituting an arbitrary `x-shopify-shop-domain` header, and `Registry.process` will accept it as valid and dispatch it under the forged shop.

### Finding Description
`Webhooks::Request` binds the HMAC only to the raw body: [1](#0-0) [2](#0-1) 

`Utils::HmacValidator.validate` verifies exactly (and only) `to_signable_string`, i.e. the raw body: [3](#0-2) 

`Registry.process` checks that HMAC and then trusts `request.shop`/`request.topic` (both unsigned headers) to route and label the payload for the consuming handler: [4](#0-3) 

The identity binding that is broken is: **HMAC(raw_body) verified == "shop the payload is attributed to"**. The gem treats these as equivalent, but only the body is authenticated; the shop/topic headers are attacker-controllable metadata carried alongside the signed body, not covered by the signature (the exact "field acted on but not covered by the HMAC" pattern).

### Impact Explanation
An unprivileged internet user who has legitimate access to any single shop with the target app installed (a normal, unprivileged merchant account, not a privileged/internal credential) will receive real Shopify webhooks for that shop, each with a valid `x-shopify-hmac-sha256` computed by Shopify using the app's `client_secret`. Because the signature covers only the body, that attacker can capture one such request and resend it to the app's webhook endpoint with the `x-shopify-shop-domain` header changed to a victim shop's domain (and/or `x-shopify-topic` changed). `HmacValidator.validate` still succeeds (body unchanged), and `Registry.process` forwards `WebhookMetadata.new(shop: request.shop, ...)` — the forged victim shop — to the app's handler. Depending on how the host app implements the handler (which trusts this gem's `shop`/`topic` accessors as authenticated), this enables cross-tenant data injection/corruption (e.g. writing order/customer data, or firing `shop/redact`-style logic) attributed to a shop the attacker does not control. This satisfies the Critical "cross-tenant access" impact bar.

### Likelihood Explanation
Moderate-to-high: it requires the attacker to have webhook traffic from at least one shop using the app (trivially obtainable by installing the app on their own shop) and the ability to POST directly to the app's public webhook endpoint with custom headers — both are within reach of an unprivileged internet user with no special credentials, tokens, or `api_secret_key` access.

### Recommendation
Include the identifying headers (`shop-domain`, `topic`, and ideally `webhook-id`) in the HMAC-signed material returned by `to_signable_string`, or otherwise cryptographically bind them to the body (e.g. verify against Shopify's documented webhook signature scheme that ties the shop to the payload), so that a replayed body cannot be re-attributed to a different shop or topic by simply changing headers.

### Proof of Concept
1. Attacker installs the vulnerable app on their own shop `attacker.myshopify.com` and captures a legitimate webhook request Shopify sends, including body `B` and header `x-shopify-hmac-sha256: H` (valid for `B` under the app's secret).
2. Attacker replays the request to the app's public webhook endpoint, keeping body `B` and header `H` unchanged, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` builds successfully; `Utils::HmacValidator.validate(request)` returns `true` because it only checks `HMAC(B) == H`.
4. `ShopifyAPI::Webhooks::Registry.process(request)` dispatches the handler with `shop: "victim.myshopify.com"`, causing the host app to process attacker-controlled data under the victim's tenant identity.

        def validate(verifiable_query)

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
