### Title
Webhook shop-domain header is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from only the raw request body (`to_signable_string` returns `@raw_body`), while the `shop`, `topic`, `webhook_id`, and `api_version` values are read straight from unauthenticated HTTP headers. `Registry.process` validates the body's HMAC and then unconditionally trusts `request.shop` to attribute the event to a tenant.

### Finding Description
The library's webhook authenticity check is: `Utils::HmacValidator.validate(request)` → `validate_signature` → `compute_signature(verifiable_query.to_signable_string, secret)` compared against the `hmac-sha256` header. For `Webhooks::Request`, `to_signable_string` is defined as just `@raw_body`, and `hmac` is derived from the `hmac-sha256` header. Crucially, `shop` is derived from the separate `shopify-shop-domain`/`x-shopify-shop-domain` header, which is never included in the signed bytes.

The identity binding that should hold is: *shop the HMAC authenticates == shop the handler acts on*. Because the header is outside the HMAC's scope, that equality is not enforced — any request with a body+HMAC pair that is valid for **any** shop (e.g., one the attacker legitimately controls, since Shopify signs webhooks per-app with the single shared `client_secret`, not per-shop) will pass `HmacValidator.validate` regardless of what `shop-domain` header accompanies it. An attacker who owns/controls their own installed instance of the app can capture one of their own legitimately-signed webhook deliveries (body + valid `hmac-sha256`) and resend it to the app's webhook endpoint with the `shopify-shop-domain` header rewritten to a victim shop. The signature check still succeeds because it only re-verifies the untouched body, and `Registry.process` hands `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: ..., ...)` to the host application's handler with the forged victim shop.

This mirrors the report's root cause: a value used by downstream logic (borrower's LToken shares / here, the "shop" the event applies to) is treated as authoritative even though the actual authenticated commitment (rebase-adjusted balance / here, the HMAC signature) does not cover it.

### Impact Explanation
Any host application that uses `WebhookMetadata#shop` (or `request.shop`) from `ShopifyAPI::Webhooks::Registry.process` to look up per-shop state, tokens, or perform tenant-scoped side effects (which is the gem's documented usage pattern) can be made to apply an attacker-controlled webhook payload against a shop the attacker does not own. This is a cross-tenant integrity violation: the attacker forces the host app to process fabricated business events (e.g., `orders/create`, `app/uninstalled`, `shop/redact`) as if they originated from the victim's shop, without ever possessing the victim's credentials.

### Likelihood Explanation
The attacker only needs to be a real, unprivileged merchant/developer who has installed the app once (a normal, credential-free interaction from the app's perspective) to obtain one validly-signed webhook body+HMAC pair from their own shop, since the HMAC is computed with the app-wide `client_secret` and does not vary per shop. Header values are trivially attacker-controlled in any raw HTTP request to the app's public webhook endpoint. No secrets, tokens, or privileged access are required.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the signable content that the HMAC protects, or independently bind the request's `shop` header to the signed payload before use — e.g., verify the signature over `"#{shop}\n#{raw_body}"` and reject if the header is inconsistent with an independently trusted value. At minimum, document that `Registry.process` must be paired with a check confirming the resolved shop matches a shop for which the app holds an active installation/session before dispatching handlers.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and lets Shopify deliver one webhook (any topic the app subscribes to), capturing the raw POST body and the `X-Shopify-Hmac-Sha256` header value — both valid under the app's shared `client_secret`.
2. Attacker replays the exact same body and HMAC header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the headers/body; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because `to_signable_string` returns only `@raw_body`, unchanged from step 1.
4. The registered handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: ..., ...)`, causing the host app to process attacker-supplied data as an authentic event from the victim shop.
