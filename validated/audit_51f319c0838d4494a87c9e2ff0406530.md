## Analog Found

### Title
Unauthenticated `CallDispatcher.dispatch()` lets anyone pre-install unlimited ERC20 approvals or directly drain any token/ETH balance the shared dispatcher ever holds - ([File: evm/src/utils/CallDispatcher.sol])

### Summary
`CallDispatcher` is a shared, stateless-by-convention utility contract used by `IntentGatewayV2` (predispatch/postdispatch swap execution) and by `HyperFungibleToken`/`WrappedHyperFungibleToken` (post-mint/unlock calldata execution) to run arbitrary `Call[]` batches on behalf of in-flight bridge/intents operations. Its `dispatch(bytes memory encoded)` function is `external` with **no access control whatsoever** — no `onlyOwner`, no caller allowlist, nothing restricting it to the apps that are supposed to use it. [1](#0-0) 

Because every call executed by `dispatch()` runs with `msg.sender == CallDispatcher`, any unprivileged address can directly command the dispatcher to `approve()` itself for unlimited allowance on any ERC20, or even directly `transfer()`/forward ETH out of whatever balance the dispatcher currently or later holds — completely bypassing `IntentGatewayV2` or the token-bridge contracts.

### Finding Description
The root cause mirrors the reported `FootiumEscrow` bug class: a shared, reusable custody contract exposes an unrestricted approval/action surface, and that state (an ERC20 allowance, or an unswept balance) outlives the specific transaction/user that is "supposed" to control it, becoming exploitable once unrelated, unsuspecting funds later pass through the same contract.

- `CallDispatcher.dispatch` has no caller restriction: [2](#0-1) 
- The dispatcher is shared infrastructure referenced by multiple apps via `_params.dispatcher` / `_dispatcher`, and is used both by `IntentGatewayV2` predispatch/postdispatch flows and by `HyperFungibleTokenUpgradeable`/`WrappedHyperFungibleTokenUpgradeable` calldata execution: [3](#0-2) [4](#0-3) 
- Unlike `IntentGatewayV2`, which explicitly sweeps the *entire* current dispatcher balance back to itself within the same atomic transaction (closing any leftover-balance window for that flow), the `HyperFungibleToken`/`WrappedHyperFungibleToken` calldata-execution path performs **no automatic sweep**: tokens are minted/unlocked to the dispatcher, `dispatch(message.data)` runs the caller-supplied calldata, and whatever the calldata doesn't itself forward out is left sitting on the dispatcher indefinitely: [5](#0-4) [6](#0-5) 
- Because `dispatch()` is public and unauthenticated, an attacker does not need to wait for a race: they can call `CallDispatcher.dispatch()` at any time, independent of any order or bridge transfer, to (a) install a standing `approve(attacker, type(uint256).max)` for any ERC20 on the dispatcher, or (b) directly issue a `transfer`/ETH-forwarding call moving out whatever balance is currently on the dispatcher. This is functionally identical to the `FootiumEscrow.setApprovalForERC721` bug: an unprivileged party can grant themselves standing operator rights over a shared custody contract, and that grant is exploitable whenever value that isn't theirs later lands in the same contract — exactly as the escrow approval was exploitable once the club (and its escrowed players) was later transferred to an unsuspecting buyer.

### Impact Explanation
Any dust, leftover balance, or partially-forwarded tokens/ETH left on `CallDispatcher` by any user's `HyperFungibleToken.send()`/`onAccept()` calldata execution (or by a mistaken direct transfer to the well-known dispatcher address) can be permanently stolen by an attacker who has pre-armed a standing approval or who directly issues a drain call through the unauthenticated `dispatch()` entrypoint. This is concrete, permanent theft of user/bridge funds reachable from a single unprivileged call — no special role, governance, or victim action required beyond routine use of the bridge's own documented calldata-execution feature.

### Likelihood Explanation
Likelihood is high: `dispatch()` requires zero privilege and the attack requires only two ordinary transactions (install approval/drain call; wait for or trigger a balance to appear). The documented `HyperFungibleToken` calldata-execution examples explicitly route funds through the dispatcher without any protocol-enforced sweep-back, making residual balances a realistic and recurring occurrence rather than a hypothetical edge case.

### Recommendation
Restrict `CallDispatcher.dispatch()` to a caller allowlist (e.g., only the configured `IntentGatewayV2` and `HyperFungibleToken`/`WrappedHyperFungibleToken` instances that are meant to drive it), and/or make the dispatcher deploy a fresh, single-use instance per call (or per order/message) instead of a long-lived shared singleton, so no state (approvals or balances) can outlive or leak across unrelated operations. Additionally, enforce a mandatory full-balance sweep-back to a trusted recipient at the end of every `dispatch()` invocation for the token-bridge calldata-execution path, matching the pattern already used in `IntentGatewayV2`.

### Proof of Concept
1. Attacker calls `CallDispatcher.dispatch(abi.encode([Call({to: USDC, value: 0, data: abi.encodeWithSelector(IERC20.approve.selector, attacker, type(uint256).max)})]))` directly — no relation to any order, no privilege required, since `dispatch` has no access control.
2. Some time later, a legitimate user bridges USDC via `HyperFungibleToken.send()` with `data` set to route through the `CallDispatcher` per the documented pattern (e.g., swap-then-forward). Any leftover USDC not fully forwarded by the calldata author's own swap logic remains on the `CallDispatcher`.
3. Attacker calls `USDC.transferFrom(callDispatcherAddress, attacker, leftoverBalance)`, using the standing approval installed in step 1, draining the residual balance that belongs to the bridging user/protocol. [7](#0-6)

```text
    /**
     *  @dev reverts if the target is not a contract or if any of the calls reverts.
     */
    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
```
