### Title
Global `savedCallbacks` map keyed only by client-supplied `MessageID` allows one user to overwrite/hijack another user's pending gateway callback - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
The legacy WebAPI gateway `handler` stores pending user callbacks in a single, unscoped map `savedCallbacks map[string]*savedCallback` keyed purely by the caller-supplied `MessageID` [1](#0-0) . Unlike newer handlers in the same package tree, `HandleLegacyUserMessage` writes into this map with no uniqueness/ownership check, so a colliding `MessageID` from a different (unprivileged) caller silently overwrites the previous entry, redirecting or destroying another user's response callback — the same shared-index root cause as the Timeswap `_ownedTokensIndex` bug where an index/key shared across unrelated owners lets one owner's write corrupt another owner's structure.

### Finding Description
`savedCallback` entries are added by `HandleLegacyUserMessage`: [2](#0-1) 
This line unconditionally sets `h.savedCallbacks[msg.Body.MessageID]`, with no check for an existing in-flight entry under that key, and no binding of the key to the caller's identity (address/signature). `MessageID` is attacker-controlled: `api.Message.Validate()` only bounds its length and forbids a trailing null byte [3](#0-2) , it never enforces per-sender uniqueness or namespacing.

The key is later used, unqualified, to look up and delete the callback when a node responds: [4](#0-3) 
`h.savedCallbacks[msg.Body.MessageID]` is exactly analogous to the shared `_ownedTokensIndex[tokenId]` in the reported Solidity bug: a single index/map entry that is expected to correspond to one particular caller/session but is actually shared globally across all callers, keyed only by an externally-supplied identifier. If a second unrelated request reuses the same `MessageID` (e.g. sent immediately after another user's request but before the response arrives), it silently replaces the stored `savedCallback` for the first request. When the node eventually answers for that `MessageID`, `handleWebAPITriggerMessage` will deliver the response to whichever caller is currently registered under the key — not necessarily the original requester — and the original requester's callback is dropped (`found` becomes stale, its channel/HTTP response is never resolved, or it silently receives another user's response instead).

This is notably different from the newer, hardened handlers in the same gateway subsystem, which explicitly detect and reject a duplicate/in-flight request ID rather than overwriting silently:
- v2 HTTP trigger handler rejects reused IDs with `"in-flight request"` / `ErrConflict` [5](#0-4) 
- Vault handler rejects duplicates with `"request was already authorized previously"` [6](#0-5) 
- Confidential relay handler rejects with `"request ID already exists"` [7](#0-6) 

The legacy `capabilities` handler (`MethodWebAPITrigger`/`MethodWebAPITarget`/`MethodComputeAction`/`MethodWorkflowSyncer`) has no equivalent protection.

### Impact Explanation
Because `savedCallbacks` is process-wide and keyed only on an attacker-chosen string, an unprivileged client hitting the internet-facing gateway can:
- cause another legitimate user's in-flight request to never receive its response (their `savedCallback` entry is overwritten and deleted from the map before the real answer arrives), a denial-of-service on a per-request basis; or
- under race conditions, cause the DON node's response intended for user A to be delivered to user B's callback (cross-user response confusion), since whichever `savedCallback` currently occupies the map slot at response time receives the payload via `savedCb.SendResponse(...)` [8](#0-7) .

This does not disclose secrets directly (unlike the Vault handler, which is scoped by owner-prefixed request IDs), but it does allow request/response impersonation and reliability disruption for the WebAPI/computeaction/workflow-syncer gateway paths, reachable from any unprivileged client able to submit legacy gateway messages.

### Likelihood Explanation
Exploitation requires only submitting two legacy gateway messages that happen to share the same `MessageID` while the first is still in flight (within `CallbackMaxAgeSec`, default 120s) [9](#0-8) . Since `MessageID` is entirely user-chosen and there is no per-sender scoping or uniqueness check enforced anywhere in this handler, an attacker can trivially pick a `MessageID` equal to one they can predict, guess, or observe (e.g., via timing or a sequential/deterministic ID scheme used by a target application), making likelihood moderate to high for targeted disruption, and near-certain for accidental collisions/self-inflicted bugs in poorly-randomized client IDs.

### Recommendation
Scope the callback map keys by sender identity in addition to `MessageID` (e.g. `sender+"/"+MessageID`), and/or reject a `HandleLegacyUserMessage` call whose `MessageID` already has a live, non-expired entry in `savedCallbacks` — mirroring the duplicate-request-ID rejection already implemented in the v2 HTTP trigger handler, vault handler, and confidential relay handler. At minimum, `HandleLegacyUserMessage` should check `if _, exists := h.savedCallbacks[msg.Body.MessageID]; exists { return conflict error }` before storing, instead of unconditionally overwriting.

### Proof of Concept
1. Attacker sends a legacy gateway message with method `web_api_trigger`/`web_api_target`/etc. and `MessageID = "X"`, signed with their own key, registering `callback_attacker` in `savedCallbacks["X"]`.
2. Before the DON responds, a victim (or another concurrent legitimate flow) independently sends a message that also results in `MessageID = "X"` (e.g., same deterministic ID scheme, or attacker predicts/races the victim's ID). This call overwrites `savedCallbacks["X"]` with `callback_victim`, silently discarding the attacker's registered callback reference (or vice-versa if attacker resends after the victim, discarding the victim's).
3. When the DON node's response for `MessageID = "X"` arrives, `handleWebAPITriggerMessage` looks up `savedCallbacks["X"]`, finds whichever callback is currently stored, deletes the entry, and delivers the response to that callback only [10](#0-9) . The other party's request is silently orphaned/never completed, demonstrating both the DoS and cross-user confusion outcomes described above.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageID]
	delete(h.savedCallbacks, msg.Body.MessageID)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JSONRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}
