### Title
Webhook shop attribution is trusted from an unauthenticated header while only the request body is HMAC-verified - (File: `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies a webhook by checking `Utils::HmacValidator.validate(request)`, which authenticates only the request's *body bytes*. The `shop` value that the gem hands to the host application's webhook handler (used to attribute the event/data to a tenant) is read from the `X-Shopify-Shop-Domain` header, a field that is **not** included in the HMAC signature computation. This breaks the identity binding `shop authenticated by HMAC == shop acted upon`, mirroring the report's bug class of finalizing/acting on state using a value that was never covered by the cryptographic check meant to authenticate the whole action.

### Finding Description
`Registry.process` does:
```ruby
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
...
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
  body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
``` [1](#0-0) 

`Utils::HmacValidator.validate` computes/compares the HMAC purely from `verifiable_query.to_signable_string` against `verifiable_query.hmac`:
```ruby
def validate_signature(verifiable_query, secret)
  received_signature = verifiable_query.hmac
  computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
  OpenSSL.secure_compare(computed_signature, T.must(received_signature))
end
``` [2](#0-1) 

For webhooks, Shopify's `X-Shopify-Hmac-SHA256` is computed over the raw JSON body only — never over the `X-Shopify-Shop-Domain`, `X-Shopify-Topic`, or `X-Shopify-Webhook-Id` headers. This is confirmed by the test suite, where an identical raw body (`"{}"`) is HMAC-signed and the `shopify-shop-domain` header is supplied and consumed separately as `data.shop`:
```ruby
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, "{}")
new_format_headers = {
  "shopify-topic" => @topic,
  "shopify-hmac-sha256" => Base64.encode64(hmac),
  "shopify-shop-domain" => @shop,
  ...
}
webhook_request = ShopifyAPI::Webhooks::Request.new(raw_body: "{}", headers: new_format_headers)
ShopifyAPI::Webhooks::Registry.process(webhook_request)
``` [3](#0-2) 

and the handler receives `data.shop` equal to the header value, unrelated to the signature: [4](#0-3) 

Because the HMAC only covers the body, any payload/HMAC pair that is valid for shop A's webhook (an unprivileged merchant can legitimately trigger and capture such a payload for their own store, e.g. an `orders/create` or `customers/redact` webhook fired to their own app endpoint) remains a byte-for-byte valid HMAC when replayed with the `X-Shopify-Shop-Domain` header swapped to shop B. `Registry.process` will still call `Utils::HmacValidator.validate` successfully (body unchanged) and will pass `shop: request.shop` (now shop B) to the host application's handler, misattributing shop-A-originated data/events to shop B's tenant context.

### Impact Explanation
This crosses the tenant boundary the gem is supposed to enforce via HMAC verification: the identity check (HMAC) validates the payload, but the tenant-identifying field consumed by the caller (`shop`) is not part of what was verified. Host applications that key session/data lookups off `WebhookMetadata#shop` (which is the gem's documented API for identifying which shop a webhook belongs to) can be made to process or store attacker-supplied body content under a different, victim shop's identity, or to run mandatory compliance webhooks (`shop/redact`, `customers/redact`, `customers/data_request`) against the wrong tenant. This matches "cross-tenant access" under the Critical impact bucket, since the gem-provided authentication primitive (`HmacValidator.validate`) is the sole tenant-authenticity guarantee exposed to callers, and it does not cover the shop-identifying header.

### Likelihood Explanation
Medium-to-high: replaying a webhook body with a substituted shop-domain header requires only network access and one legitimately-obtained (body, HMAC) pair, which any merchant/app-installer can capture for their own store without any special privilege — no `api_secret_key` or access token is needed by the attacker.

### Recommendation
- Have `Utils::HmacValidator`/`Webhooks::Request` bind the `shop` (and ideally `topic`, `webhook_id`) header values into the value that is authenticated, or independently verify that the shop asserted in the header matches an expected/allow-listed shop for that HMAC-verified body before exposing it via `WebhookMetadata#shop`.
- At minimum, document clearly that `request.shop` is unauthenticated so host applications know they must independently correlate it with a known, registered shop before trusting it for tenant-scoped operations.

### Proof of Concept
1. Attacker installs the app on their own store `attacker.myshopify.com` and captures a legitimate webhook delivery: raw body `B` and header `X-Shopify-Hmac-SHA256: H`, where `H = HMAC-SHA256(secret, B)`.
2. Attacker (or any network intermediary/replay tool) sends a request to the app's webhook endpoint with the same body `B` and header `X-Shopify-Hmac-SHA256: H`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `B` only and matches `H` — validation succeeds. [5](#0-4) 
4. The handler is invoked with `shop: "victim.myshopify.com"` alongside attacker-controlled body `B`, exactly as shown by the header-driven `data.shop` assertion in the test suite. [6](#0-5)
