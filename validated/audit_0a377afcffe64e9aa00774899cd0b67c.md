### Title
`EmporiumUpgradeable.runAction` skips all balance conservation when `erc20TokenAddresses.length == 0` (min-circuit path), allowing arbitrary drains of Emporium-resident funds - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
When a transaction is submitted with an empty `erc20TokenAddresses` array (the "min circuit" path selected in `CircomDataBuilder.formInputForCircom`/`formInputEmporiumMin`), both the top-level balance-conservation loop in `Hinkal.sol` and the `balancesBefore`/`balancesAfter` reconciliation loop in `EmporiumUpgradeable.runAction` are length-0 loops that never execute. This means the `ops` array executed inside `runAction` can move any token/ETH balance held by the Emporium contract with zero accounting, breaking the `VALUE_CONSERVATION` equality entirely for this path.

### Finding Description
The equality that should hold is: for every token touched by the transaction, `balanceChange == -deltaAmountChange (deposits) + utxoAmount (withdrawals accounted as UTXOs)`, enforced token-by-token in `EmporiumUpgradeable.sol:132-151` and mirrored in `Hinkal.sol:97-147`. Both loops iterate over `circomData.erc20TokenAddresses`.

`CircomDataBuilder.formInputForCircom` (contracts/CircomDataBuilder.sol:139-148) routes to `formInputEmporiumMin` whenever `externalActionId == HINKAL_EMPORIUM_ACTION_ID && erc20TokenAddresses.length == 0`, and `formInputEmporiumMin` (lines 150-161) produces a circuit public-input vector containing only `emporiumMessage`, `timeStamp`, `calldataHash` — no token addresses, no `amountChanges`, no nullifiers, no root/commitment binding. `dimensionsCheck` in `HinkalHelper.sol:64-171` only requires all these arrays to have length equal to attacker-chosen `dimensions.tokenNumber`, which the attacker can set to 0 to legally select this path.

With `erc20TokenAddresses = []`:
- In `Hinkal.sol:97` the `for (uint64 i; i < circomData.erc20TokenAddresses.length; i++)` loop that computes `balanceDif` and enforces it against `amountChanges`/`utxoAmount` never runs.
- In `EmporiumUpgradeable.runAction` (contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol:85-160), `balancesBefore`/`balancesAfter` are computed over the same empty array, and the reconciliation loop at lines 132-151 also never runs.
- `deltaAmountChanges` (derived from the empty `amountChanges`) is also empty, so `payRelayFees` does nothing meaningful either.

Meanwhile, `stack.ops` is decoded from `circomData.externalActionData.externalActionMetadata` (line 80-83) and executed unconditionally in the loop at lines 91-118. If `stack.signerAddress == address(0)`, `verifyWallet` (lines 302-316) returns immediately after marking the message used — **no EIP712 signature is checked at all** for this "stateless" mode, and case 2 in the ops loop (lines 103-113) performs a raw `op.endpoint.call{value: op.value}(op.callData)` directly from the Emporium contract with attacker-fully-controlled `endpoint`, `value`, and `callData` (only blocked from calling `callHinkalWallet`/`doSendToRelay` selectors).

Consequently, an attacker who submits `erc20TokenAddresses = []`, `amountChanges = []`, all other dimension-zero arrays, `signerAddress = address(0)`, and `ops = [{endpoint: victimToken, callData: transfer(attacker, amount), value: 0}]` can have Emporium call `victimToken.transfer(attacker, amount)` directly — draining any balance the Emporium contract holds in that token — with zero entries checked in `balancesBefore`/`balancesAfter` for that token (since it's not in `erc20TokenAddresses`) and zero UTXOs recorded. The proof only needs to satisfy the minimal 3-input circuit (`emporiumMessage`, `timeStamp`, `calldataHash`), none of which constrain what `ops` actually do to real balances.

None of the existing guards prevent this: `performHinkalChecks`'s `dimensionsCheck` only enforces internal array-length consistency (attacker sets tokenNumber=0 legitimately), `checkOnchainCreation` is vacuous on empty arrays, `rootHashExists` checks an unrelated root that isn't tied to any spent nullifier when `inputNullifiers` is empty, and `insertNullifiers`/`insertCommitments` operate on empty arrays (no-ops). The `calldataHash` check in `performHinkalChecks` only binds the proof to the attacker's own chosen `circomData` — it does not constrain the *content* of `ops` to be balance-neutral.

### Impact Explanation
Any funds transiently or persistently resident on the Emporium contract — dust left from other users' operations, funds an attacker flash-moves in via a legitimate op in the same call, or ETH sent via `receive()` — can be extracted by an unprivileged attacker with no on-chain balance accounting catching the movement. This is direct theft of funds resident on Emporium disguised as a no-op transaction, matching the Critical severity bar (direct theft of user/protocol funds via a verification bypass).

### Likelihood Explanation
Preconditions: the attacker needs (a) the ability to construct a valid Foundry-generated proof for the minimal 3-input circuit (`emporiumMessage`/`timeStamp`/`calldataHash` only — no nullifier/root binding to real ownership), and (b) some balance to exist on the Emporium contract in the target token (either genuine dust from prior transactions, or self-funded via a same-transaction op). Both are attacker-controllable/attacker-satisfiable without any privileged role, and the attack is fully repeatable per available dust/flash-in amount. This is the intended design gap of the "min circuit" fast path, not a rare edge case, making it highly feasible whenever any balance sits on Emporium.

### Recommendation
Do not allow the `erc20TokenAddresses.length == 0` / min-circuit path to execute arbitrary `ops` without balance accounting. Either: (1) forbid `stack.ops` from targeting arbitrary `endpoint`/`callData` when `erc20TokenAddresses.length == 0` (restrict min-circuit ops to a strict allow-list of stateless, non-value-transferring wallet-management calls), or (2) always compute `balancesBefore`/`balancesAfter` over the full set of tokens touched by `ops` (not just `circomData.erc20TokenAddresses`) and revert on any nonzero net balance change that isn't accounted for, or (3) require `dimensions.tokenNumber > 0` (i.e., disallow the empty-array min path) whenever `externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `ops.length > 0`.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, `EmporiumUpgradeable` (proxy), a mock ERC20 `VictimToken`, and fund the Emporium proxy address directly with `VictimToken` (simulating dust/other-user residue), plus register the min-circuit verifier (`VerifierEVMMin0v4`).
2. Craft `EmporiumStack{ signerAddress: address(0), ops: [ { endpoint: address(VictimToken), invokeWallet: false, value: 0, callData: abi.encodeCall(IERC20.transfer, (attacker, victimBalance)) } ] }`, ABI-encode as `externalActionMetadata`.
3. Build `CircomData` with `erc20TokenAddresses = []`, `amountChanges = []`, `onChainCreation = []`, `slippageValues = []`, `inputNullifiers = [[]]`/empty, `outCommitments = []`, `dimensions.tokenNumber = 0`, `externalActionId = HINKAL_EMPORIUM_ACTION_ID`, and a valid `calldataHash` computed via `CircomDataBuilder.getHashedCalldata`.
4. Generate a real proof for the min circuit (3 public inputs: `emporiumMessage`, `timeStamp`, `calldataHash`) using the project's snarkjs/circom setup for `MainEVMCircuitMin.circom`.
5. Call `Hinkal.transact(a,b,c,dimensions,circomData)` from the attacker EOA.
6. Assert: `VictimToken.balanceOf(Emporium)` drops from `victimBalance` to 0 and `VictimToken.balanceOf(attacker)` increases by `victimBalance`; assert the returned `utxoSet` from `runAction` is empty (length 0) and no `require` in `Hinkal.sol:111-146` or `EmporiumUpgradeable.sol:142-146` ever executed for this token — confirming the equality `balanceDif == amountChanges[i] + utxoAmount` was never evaluated for the drained token, proving the conservation check was bypassed while real value left the contract.
