### Title
Unbounded-depth `RuntimeCall::decode` in `pallet-hyper-fungible-token::on_accept` allows an unprivileged token bridger to stack-overflow the destination chain - ([File: modules/pallets/hyper-fungible-token/src/module.rs])

### Summary
`pallet_hyper_fungible_token::Pallet::on_accept` decodes an attacker-supplied `SubstrateCalldata.runtime_call` blob with the plain, depth-unbounded `Decode::decode` [1](#0-0) . The very same class of bug (SCALE decoding a nested/recursive `RuntimeCall` without a recursion-depth limit) was already identified and fixed elsewhere in this codebase in `pallet-call-decompressor`, which explicitly switched to `decode_all_with_depth_limit(MAX_EXTRINSIC_DECODE_DEPTH_LIMIT, ...)` and carries a regression test (`decompress_stack_exhaustion_poc`) proving that an unbounded decode of a deeply-nested `RuntimeCall` (1000x nested `Sudo::sudo`) previously caused stack exhaustion [2](#0-1) [3](#0-2) . The hyper-fungible-token pallet's cross-chain calldata path was never given the same fix.

### Finding Description
`HyperFungibleToken.send()` on the EVM side lets *any* caller attach arbitrary `params.data` to a token-transfer message; this is packed into the ISMP POST body's `Message.data` field and dispatched cross-chain with no restriction on its contents [4](#0-3) .

On the Substrate destination, `pallet_hyper_fungible_token`'s `on_accept` handler processes this untrusted `message.data` as follows:

```rust
let substrate_data = SubstrateCalldata::decode(&mut &message.data[..])...;
...
let runtime_call = T::RuntimeCall::decode(&mut &*substrate_data.runtime_call)
    .map_err(HftError::RuntimeCallDecodeError)?;
``` [5](#0-4) [1](#0-0) 

`RuntimeCall` is a recursive enum in the shipped runtimes (it composes calls like `Sudo::sudo(Box<RuntimeCall>)` and `Utility::batch(Vec<RuntimeCall>)`), and this pallet is wired into the `gargantua` and `nexus` parachain runtimes' ISMP router [6](#0-5) . Plain `codec::Decode::decode` recurses once per nesting level with no bound, so an attacker can encode a `runtime_call` payload containing thousands of nested `Sudo::sudo`/`Utility::batch` wrappers. Decoding this on the collator/validator that executes the `on_accept` callback will recurse until the native call stack is exhausted, aborting/crashing the node process that is executing the block — exactly the fix that `pallet-call-decompressor` had to add for its own `RuntimeCall::decode` path (`MAX_EXTRINSIC_DECODE_DEPTH_LIMIT = 4`, enforced via `decode_all_with_depth_limit`) [7](#0-6) [8](#0-7) .

Because `on_accept` runs deterministically inside block execution (it is invoked by the ISMP router when a relayer submits the proof for the POST request), *every* node re-executing that block hits the same stack overflow, i.e. this is not a client-only crash but a full node/collator crash — a stronger analog of the Mattermost LaTeX client-crash CVE, and capable of halting the parachain's message-delivery route entirely until the offending block/extrinsic is filtered out via a runtime upgrade.

### Impact Explanation
A stack overflow during block execution aborts the node process (panic/abort, not a catchable `Result`). If triggered by an included POST request, all collators/validators executing that block crash simultaneously, producing a chain-wide halt/DoS of the destination parachain — this blocks all subsequent ISMP message delivery on that chain (a route unable to deliver messages), which is High severity per the scope rules.

### Likelihood Explanation
Reachable by a single unprivileged transaction: any account can call `HyperFungibleToken.send()` on the EVM source chain (or an equivalent Substrate-side sender) with a crafted `data` payload, requiring only enough gas/fee to submit the transfer and its relay. No special privileges, governance, or validator collusion is needed — the "victim" state is entered as soon as a relayer (which can be anyone, including the attacker) submits the proof and the block executes `on_accept`.

### Recommendation
Replace the unbounded `T::RuntimeCall::decode(&mut &*substrate_data.runtime_call)` in `modules/pallets/hyper-fungible-token/src/module.rs` with a depth-limited decode, mirroring the fix already applied in `pallet-call-decompressor`: use `codec::DecodeLimit::decode_all_with_depth_limit` (or `decode_with_depth_limit`) with a small, explicit bound (e.g. the same `MAX_EXTRINSIC_DECODE_DEPTH_LIMIT` constant, or a pallet-specific constant sized to the legitimate calls this bridge needs to support), and add a regression test analogous to `decompress_stack_exhaustion_poc` that submits a deeply nested `RuntimeCall` through `on_accept` and asserts a clean decode error instead of a crash. The same review should be applied to `SubstrateCalldata::decode` and `MultiSignature::decode` call sites in this function to confirm none of the nested types are unboundedly recursive either.

### Proof of Concept
1. Attacker calls `HyperFungibleToken.send()` (EVM) with `params.data` = SCALE-encoded `SubstrateCalldata { signature: None, runtime_call: encoded_nested_call }`, where `encoded_nested_call` is `RuntimeCall::Sudo(Sudo::sudo(Box::new(RuntimeCall::Sudo(Sudo::sudo(...deeply nested...)))))` encoded ~thousands of levels deep (analogous to the `decompress_stack_exhaustion_poc` construction in `modules/pallets/testsuite/src/tests/pallet_call_decompressor.rs:314-352`, but targeting `pallet-hyper-fungible-token`'s `on_accept` instead of `pallet-call-decompressor`'s `decompress_call`).
2. A relayer (can be the attacker) submits the ISMP POST request + proof to the destination Substrate chain.
3. During block execution, `pallet_hyper_fungible_token::Pallet::on_accept` reaches `T::RuntimeCall::decode(&mut &*substrate_data.runtime_call)` at `module.rs:189`, which recurses once per `Sudo::sudo` nesting level with no depth limit, exhausting the stack and aborting the node process executing that block.

*Note:* I was unable to execute this PoC in a live runtime from this environment (no code execution available), so the concrete nesting depth needed to overflow the stack, and the exact runtime configuration of `Sudo`/`Utility` in `gargantua`/`nexus`, should be confirmed by a Devin session with repo access before filing/fixing. The core root-cause claim (missing depth limit on `RuntimeCall::decode` in this specific `on_accept` path, contrasted with the depth-limited decode already used in `pallet-call-decompressor`) is directly supported by the cited source.

#[test]
fn decompress_stack_exhaustion_poc() {
	let mut ext = new_test_ext();
	ext.execute_with(|| {
		use crate::runtime::RuntimeCall;
		use codec::Encode;

		let inner_call = RuntimeCall::System(frame_system::Call::remark { remark: Vec::new() });

		let mut nested_calls =
			RuntimeCall::Sudo(pallet_sudo::Call::sudo { call: Box::new(inner_call) });

		for _ in 1..1000 {
			nested_calls =
				RuntimeCall::Sudo(pallet_sudo::Call::sudo { call: Box::new(nested_calls) });
		}

		let encoded = nested_calls.encode();
		let mut buffer = vec![0u8; 1000000];
		let compressed = zstd_safe::compress(&mut buffer[..], encoded.as_slice(), 3).unwrap();
		let final_compressed_call = buffer[..compressed].to_vec();

		let res = pallet_call_decompressor::Pallet::<Test>::decompress_call(
			RuntimeOrigin::none(),
			final_compressed_call.to_vec(),
			encoded.len() as u32,
		)
		.err()
		.unwrap();

		assert_eq!(
			res,
			DispatchError::Module(ModuleError {
				index: 10,
				error: [3, 0, 0, 0],
				message: Some("ErrorDecodingCall")
			})
		);
	});
}
