## Title
Webhook Shop Attribution Not Covered by HMAC Verification Enables Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the raw body against the `X-Shopify-Hmac-SHA256` header, but the `shop` attribute that host applications rely on to route/attribute the webhook data to a specific merchant is taken from the unauthenticated `X-Shopify-Shop-Domain` header, which is never part of the signed payload.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

and `shop` is read straight from a header with no cryptographic binding to that body: [2](#0-1) 

`Registry.process` validates only this signable string via `Utils::HmacValidator.validate(request)` and then forwards `request.shop` unchanged to the app's handler: [3](#0-2) 

`HmacValidator.validate` computes the signature strictly over `to_signable_string`, i.e. the raw body — the `shop` header plays no role in the signature at all: [4](#0-3) 

This breaks the identity binding the report's bug class calls out: the equality that must hold is `authenticated(shop-that-produced-this-body) == shop-attributed-to-the-handler`. Here, the HMAC only proves "this body was signed with the app's secret for *some* webhook", not "this body belongs to shop X". Any entity capable of obtaining one genuinely-signed webhook (raw_body + hmac pair) — for example, any merchant who installs the app and receives their own legitimate webhooks, which is not a privileged action and requires no `api_secret_key`, access token, or leaked credential — can resubmit that exact raw_body/hmac pair to the app's public webhook endpoint while substituting a different value in `X-Shopify-Shop-Domain`. `HmacValidator.validate` still succeeds (it never looked at the shop header), and `Registry.process` calls the handler with `WebhookMetadata.new(... shop: request.shop ...)` set to the attacker-chosen victim shop: [5](#0-4) 

The documented usage pattern confirms host apps are expected to trust `data.shop` directly for per-tenant routing/enqueueing without any additional validation: [6](#0-5) 

### Impact Explanation
This is a cross-tenant integrity/authentication issue: a low-privileged actor (any merchant that installs a multi-tenant app) can forge the shop attribution of a validly-signed webhook payload and cause the app to process/store data (order data, customer PII, redact requests, etc.) as if it belonged to a different, victim shop. Since host apps are explicitly documented to trust `data.shop` for job dispatch and persistence keys, this can lead to cross-tenant data corruption or data leakage between merchants — satisfying the "cross-tenant access" criterion.

### Likelihood Explanation
Any app that accepts webhooks for more than one shop (the normal multi-tenant SaaS model this gem targets) is affected. The only prerequisite is obtaining a single genuine `(raw_body, hmac)` pair from a webhook the attacker legitimately receives for their own shop (trivial — they simply install the app), then replaying it to the app's public webhook endpoint with a modified `X-Shopify-Shop-Domain` header. No secret material, access token, or privileged access is required.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the value verified against the HMAC, or independently authenticate the shop domain (e.g., cross-check it against a known/installed shop record before dispatching to the handler) rather than trusting the header verbatim. At minimum, `Registry.process` should reject webhooks whose `shop` header does not correspond to a shop that has an active, registered webhook subscription/session, rather than passing through any attacker-supplied domain string.

### Proof of Concept
1. App merchant "attacker.myshopify.com" installs the target app and triggers a webhook (e.g., `orders/create`). Shopify posts a request to the app's webhook endpoint with:
   - `X-Shopify-Shop-Domain: attacker.myshopify.com`
   - `X-Shopify-Hmac-SHA256: <valid HMAC of raw_body>`
   - `raw_body: <order JSON>`
2. Attacker captures this raw body and its valid HMAC (visible to them as the shop owner receiving the webhook, or via any endpoint logging they control).
3. Attacker replays the exact same `raw_body` and `X-Shopify-Hmac-SHA256` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses this into `shop = "victim.myshopify.com"`, `to_signable_string = raw_body`.
5. `Utils::HmacValidator.validate(request)` recomputes HMAC over `raw_body` only and it matches — validation passes.
6. `Registry.process` invokes the app's handler with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: <attacker's order data>, ...)`, causing the host app to process/store attacker-controlled data under the victim shop's identity.

```ruby
        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
```

```ruby
          received_signature = verifiable_query.hmac
```

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
```
