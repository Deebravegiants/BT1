### Title
Unprivileged borrower can freeze own liquidation and bad-debt cleanup by holding a dust Aquarius LP collateral leg and draining the pool below `min_pool_value_wad` - (File: contracts/price-aggregator/src/providers/aquarius.rs)

### Summary
Any account whose supply book contains a collateral leg priced by an `AquariusLp`/`AquariusStableLp` oracle becomes unliquidatable and un-cleanable whenever that LP pool's computed value drops below its configured `min_pool_value_wad`, because the price-aggregator fails closed with `InsufficientAquariusLiquidity`. An unprivileged borrower can force this state at will: supply a dust amount of an Aquarius LP share as collateral (supply does not require a fresh/valid price), then withdraw their own liquidity from the underlying Aquarius pool to push pool value under the floor. Every risk-dependent path on the account — `liquidate`, `clean_bad_debt`, and the borrower's own `withdraw` — reverts until governance or market conditions restore pool value.

### Finding Description
`providers::aquarius::read` computes the LP share's fair price, derives `pool_value_wad = price_wad * total_shares / share_unit`, and hard-errors when it is below `lp.min_pool_value_wad` (contracts/price-aggregator/src/providers/aquarius.rs:118-122).

The controller resolves prices strictly for valuation: `fetch_prices` panics if any requested asset lacks a usable feed (contracts/controller/src/external/price_aggregator.rs:17-29). Liquidation planning and bad-debt cleanup iterate the account's entire supply book, so one unpriceable collateral leg aborts the whole call regardless of how small that leg is.

This is proven by the repo's own test `audit_supply_setup_blocks_liquidation_via_stale_dust_leg` (tests/test-harness/tests/controller/audit_supply_stale_shield.rs): a 0.001-unit WBTC dust supply leg with a bad price makes `try_liquidate` return `PRICE_FEED_STALE`, `try_clean_bad_debt` return `PRICE_FEED_STALE`, and even a tiny `try_withdraw` fail, while a twin account without the poisoned leg liquidates normally. The same fail-closed shape applies to the `InsufficientAquariusLiquidity` path, which is exercised in `test_lp_read_rejects_liquidity_below_floor` (contracts/price-aggregator/tests/oracle/registry.rs:743-764) and `test_a_stable_pool_one_wei_under_its_liquidity_floor_is_refused` (registry.rs:1153-1166).

Concrete attack path, all reachable by one unprivileged address:
1. Supply ordinary collateral, `borrow` to near max LTV.
2. `supply` a dust amount of a listed Aquarius LP share (e.g. the mainnet-listed `USDYUSDC_LP`/`AQUAUSDC_LP` hub-3 markets in configs/mainnet/markets.json, which carry `min_pool_value_wad` floors of ~$1M / ~$200k).
3. Withdraw the attacker's own liquidity from that Aquarius pool (or arrange to be the marginal LP whose withdrawal crosses the floor). Pool value drops below `min_pool_value_wad`; the aggregator now returns `InsufficientAquariusLiquidity` for the LP asset.
4. All `liquidate` calls on the account revert (every collateral leg is priced strictly; liquidation has no collateral-subset argument). `clean_bad_debt` reverts for the same reason.
5. Meanwhile interest accrues; when the position is deeply insolvent the governed force-socialize path is also blocked by the same unpriceable leg per the threat model.
6. To recover access, the attacker (or anyone) re-adds liquidity above the floor — making this a toggleable shield.

### Impact Explanation
Temporary freezing of funds plus a direct path to protocol insolvency: an underwater account cannot be liquidated or bad-debt-cleaned for as long as the pool stays under the floor. The attacker converts their own LP withdrawal into a liquidation shield, lets debt accrue unpaid interest, and any cleanup that eventually runs socializes larger losses onto suppliers via supply-index write-down. The leg also blocks the account's own exits, but that harms only the attacker. The same mechanism works without any action by the attacker whenever natural LP exits push a thin pool under the floor, shielding every borrower holding that collateral leg.

### Likelihood Explanation
- Requires only: a listed Aquarius LP market usable as collateral, a dust supply position, and enough LP share in the pool to move value across `min_pool_value_wad` — or simply waiting for organic withdrawals near the floor.
- No privileged role, no oracle dishonesty within bands, no parameter misconfiguration: the floor, the strict all-legs pricing, and the fail-closed error are all production behavior. Monitoring alerts (`LendingLpPoolValueNearFloor` in services/lending-exporter/ops/alerts.yml) acknowledge that under-floor pool value makes accounts unliquidatable.
- Cost is bounded by the dust collateral plus temporarily locked LP liquidity; the shield is reusable per account.

### Recommendation
- Do not let a single unpriceable collateral leg abort account-wide risk paths: treat a leg that fails price resolution as zero-valued collateral for HF/liquidation purposes, or exclude it from the strict fetch and skip its seizure leg, so other legs remain liquidatable.
- Alternatively, decouple `clean_bad_debt` from collateral pricing (eligibility is already defined on unweighted collateral `C` vs. ceil risk debt — allow a mode that prices debt legs only, or treats unpriceable supply as zero, which is conservative for cleanup).
- For Aquarius LP listings, prefer `min_pool_value_wad` set far below the point where a single LP's exit crosses it, or add a soft-status fallback so `prices()` returns the last valid observation rather than reverting account-wide.

### Proof of Concept
Existing coverage that demonstrates each link:

- `tests/test-harness/tests/controller/audit_supply_stale_shield.rs` — dust collateral leg with a broken price blocks `liquidate`, `clean_bad_debt`, and `withdraw` while the twin account liquidates fine; identical fail-closed behavior for `InsufficientAquariusLiquidity`.
- `contracts/price-aggregator/tests/oracle/registry.rs:743-764` — reserves below the floor make `resolve_status` invalid.
- `contracts/price-aggregator/src/providers/aquarius.rs:118-122` — the hard `InsufficientAquariusLiquidity` error on `pool_value_wad < min_pool_value_wad`.

End-to-end sequence: `supply(dust LP)` → Aquarius `withdraw` of own liquidity → `liquidate(attacker_id, ...)` reverts `InsufficientAquariusLiquidity`/`OracleNotConfigured` until liquidity is restored; `clean_bad_debt(attacker_id)` reverts the same way while debt and interest accumulate.

Note: this failure mode is acknowledged in the project's threat model (DoS.1, docs/explanation/threat-model.md:364) and an ops alert, so it is a documented residual risk rather than a novel finding; it still satisfies the requested analog shape (unprivileged reachability, availability/insolvency impact) and is reported per the prompt's acceptance criteria.
