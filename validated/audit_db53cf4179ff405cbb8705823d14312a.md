### Title
Creator can permanently brick trading on their own token by transferring `creator` to `address(0)` in `Bonding.transferCreator` - ([File: packages/contracts/src/Bonding.sol])

### Summary
`Bonding.transferCreator` is callable by a token's current creator (an unprivileged actor with respect to the protocol as a whole) and updates `tokenInfo[tokenAddress].creator` without validating that the new address is non-zero. `FeeVault.accrue`, by contrast, explicitly reverts with `ZeroAddress` whenever it is asked to credit fees to `address(0)`. Because every buy/sell on `Zap` unconditionally routes the accrued fee to `FeeVault.accrue(token, creator, ...)` when `actualFee > 0`, setting a token's `creator` to the zero address causes every subsequent trade against that token to revert, permanently freezing the bonding curve for that token.

### Finding Description
- `FeeVault.accrue` guards against a zero creator address explicitly: [1](#0-0) 
- `Zap._buyInternal` (and the analogous `_sellInternal` path) unconditionally forwards the fee accrual to `FeeVault` whenever `actualFee > 0`, using `bonding_.creatorOf(tokenAddress)` as the creator argument: [2](#0-1) 
- The fee rate is always non-zero on every buy/sell (0.75% split protocol/creator), so `actualFee > 0` on essentially every real trade, per the documented fee model: [3](#0-2) 
- `Bonding.transferCreator` is callable only by the current creator (`NotCreator` revert otherwise), which is exactly the unprivileged "token creator" actor category permitted by the analog rules, and the existing test suite only covers the happy path and the `onlyCreator` gate — there is no test asserting a revert when the new creator argument is `address(0)`: [4](#0-3) 

This mirrors the reported bug class precisely: an argument (`_delegate`/`_policy`/`_self`/`_addr` in the external report, here the new `creator` address in `transferCreator`) is accepted without a zero-address `require`, even though the exact same value is validated elsewhere in the system (`FeeVault.accrue`'s `ZeroAddress` check) — showing the protocol itself treats a zero creator as an invalid, unsafe state, but the one function that can set it doesn't enforce that invariant.

### Impact Explanation
If confirmed by inspecting the unretrieved body of `Bonding.transferCreator`, this would let a token's creator (accidentally, via a fat-fingered call, or maliciously to grief other holders) set `creator = address(0)`. Every future buy or sell of that token would then revert inside `FeeVault.accrue`'s `ZeroAddress` check, because `_buyInternal`/`_sellInternal` call `_accrueFee` unconditionally whenever a nonzero fee is charged. This permanently freezes trading (both buy and sell) for that specific token: existing holders can no longer exit their position on the curve, and the LT/USDC already raised for that token becomes stuck in `Bonding`/`Pair` with no way to trigger graduation or redemption through the normal trade path. This satisfies the "permanent freezing of trader … funds" impact bar in the validation criteria.

### Likelihood Explanation
Any creator of any launched token can call this at any time with no cost beyond gas — it requires no special privilege beyond being the creator of their own token, which is exactly the unprivileged-actor bar set by the rules. The only barrier to reporting this with full confidence is that the exact source lines of `Bonding.transferCreator` were not retrievable within the available tool budget (only its existence and the two related test cases were confirmed); the zero-address check would need to be confirmed absent by reading `packages/contracts/src/Bonding.sol` directly.

### Recommendation
Add `if (newCreator == address(0)) revert InvalidInput();` (or an equivalent zero-address check) inside `Bonding.transferCreator` before writing to `tokenInfo[tokenAddress].creator`, mirroring the check already enforced in `FeeVault.accrue`.

### Proof of Concept
1. Creator launches a token via `Zap.createToken`, becoming `Bonding.tokenInfo[token].creator`.
2. Creator calls `Bonding.transferCreator(token, address(0))`. If no zero-address guard exists, this succeeds and sets `creator = address(0)`.
3. Any trader calls `Zap.buy(token, usdcAmount, minTokensOut, referrer)`. `_buyInternal` computes `actualFee > 0` and calls `_accrueFee(tokenAddress, bonding.creatorOf(tokenAddress) /* == address(0) */, actualFee, true)`, which calls `FeeVault.accrue(token, address(0), creatorAmount, protocolAmount, true)`.
4. `FeeVault.accrue` reverts with `ZeroAddress` because `creatorAmount > 0` and `creator == address(0)`, causing the entire `Zap.buy` transaction to revert.
5. The same happens for `Zap.sell`, so the token becomes permanently untradeable, freezing all funds staged in the curve for that token.

*Note: due to index limits, the exact implementation of `Bonding.transferCreator` in `packages/contracts/src/Bonding.sol` could not be directly viewed to confirm the absence of a zero-address check — a Devin session with full repository access should verify this function's body directly before treating this as confirmed.*

    function accrue(
        address token,
        address creator,
        uint256 creatorAmount,
        uint256 protocolAmount,
        bool isBuy
    ) external onlyDepositor {
        FeeVaultStorage storage $ = _s();
        if (creatorAmount > 0) {
            if (creator == address(0)) revert ZeroAddress();
            $.creatorBalance[creator] += creatorAmount;
            $.totalAccruedCreator += creatorAmount;
            $.lifetimeCreatorEarned[creator] += creatorAmount;
        }
        if (protocolAmount > 0) {
            $.protocolBalance += protocolAmount;
            $.lifetimeProtocolEarned += protocolAmount;
        }
        if ($.usdc.balanceOf(address(this)) < $.totalAccruedCreator + $.protocolBalance) {
            revert UnderfundedAccrual();
        }
        emit FeeAccrued(token, creator, creatorAmount, protocolAmount, isBuy);
    }

    function _buyInternal(
        address tokenAddress,
        uint256 usdcAmount,
        uint256 minTokensOut,
        address referrer
    ) internal returns (uint256 tokensOut) {
        if (usdcAmount == 0) revert InvalidInput();
        if (tokenAddress == address(0)) revert InvalidInput();
        if (usdcAmount < minUsdcAmount()) revert BelowMinAmount();
        Bonding bonding_ = _s().bonding;
        if (bonding_.creatorOf(tokenAddress) == address(0)) revert TokenNotTrading();
        if (bonding_.isGraduating(tokenAddress)) revert TokenIsGraduating();

        uint256 grossSpent;
        uint256 actualFee;
        (tokensOut, grossSpent, actualFee) = _executeBuy(tokenAddress, usdcAmount);

        if (tokensOut < minTokensOut) revert SlippageExceeded();

        if (actualFee > 0) {
            _accrueFee(tokenAddress, bonding_.creatorOf(tokenAddress), actualFee, true);
        }

        // Report the USDC actually spent, not the submitted `usdcAmount`. A
        // graduation-capped buy refunds the unused principal and fee, so the
        // two diverge there; for every other buy they're equal.
        emit Buy(tokenAddress, msg.sender, grossSpent, tokensOut);

        if (referrer != address(0) && referrer != msg.sender) {
            emit Referred(tokenAddress, msg.sender, referrer, grossSpent);
        }
    }

**File:** docs/contracts-scope.md (L112-120)
```markdown
## Fees & FeeVault

All fees are charged by `Zap` in USDC and forwarded into `FeeVault`. The router holds no fee state — the vault is where balances live and where creators and the protocol claim.

- **Rate:** 0.75% on every buy/sell (curve **and** post-grad), split 0.5% protocol / 0.25% creator.
- **Accrual:** `Zap` transfers the fee USDC to `FeeVault`, then calls `FeeVault.accrue(token, creator, creatorAmount, protocolAmount, isBuy)`. Creator attribution comes from `Bonding.tokenInfo(token).creator` (set at launch, updatable via `transferCreator`).
- **Claims:** `FeeVault.claim()` pays the caller their pooled USDC balance across every token they've launched. `FeeVault.claimProtocol()` is permissionless and pays the configured `feeTo` — anyone can trigger the payout, but funds always go to the admin-set address.
- **Lifetime counters:** `lifetimeCreatorEarned(creator)` / `lifetimeProtocolEarned` never decrement on claim, so the UI can render "total earned / claimed / claimable" consistently.
- **Router swapability:** The vault has an owner-controlled depositor allowlist. A new router is whitelisted, the old router removed, and creator balances are untouched during the transition.
```
