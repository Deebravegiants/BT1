### Title
Unregistered-instance authentication fallback in `IntentGatewayV2.authenticate` lets any connected state machine impersonate the gateway itself, draining escrow - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of `IntentGatewayV2` resolves peer-gateway addresses with a fallback that treats "unregistered" the same as "registered as myself." Any relayer delivering a message from a state machine that is connected to the host (has a valid consensus client) but has *not* been explicitly registered as a `NewDeployment` peer can forge `request.from = address(this)` and pass `authenticate`, reaching `RedeemEscrow`/`RefundEscrow` and draining escrowed order funds. This mirrors the Grafana CVE's root cause: an authorization check that fails to scope its "is this the right actor for this org/chain" comparison to the specific caller's actual sphere, defaulting instead to a too-permissive answer.

### Finding Description
`_instances` maps `keccak256(stateMachineId) => gateway address`, used to authenticate that an incoming ISMP request really originated from a known IntentGateway peer on the claimed source chain: [1](#0-0) 

```solidity
function instance(bytes calldata stateMachineId) public view returns (address) {
    address gateway = _instances[keccak256(stateMachineId)];
    return gateway == address(0) ? address(this) : gateway;
}

function authenticate(PostRequest calldata request) internal view {
    if (request.from.length != 20) revert InvalidInput();
    address module = address(bytes20(request.from));
    // IntentGateway only accepts incoming assets from itself or known instances
    if (instance(request.source) != module) revert Unauthorized();
}
```

When a state machine's gateway has never been registered via a `NewDeployment` governance message (`_instances[keccak256(stateMachineId)] == address(0)`), `instance()` silently returns `address(this)` instead of reverting. `authenticate` then treats *any* message whose `request.from` bytes equal this contract's own address as legitimate, regardless of which (registered-with-the-host, but not-registered-as-a-peer) state machine it actually came from.

This differs from the hardened, current EVM/Core version of the same contract, which reverts with `UnknownInstance` when no peer is registered: [2](#0-1) 

The relayer/consensus gate that a message must pass to reach `onAccept` only proves that the *state machine* (chain) is connected to Hyperbridge/this host — it says nothing about whether a specific contract on that state machine is a legitimate IntentGateway peer. Any account on any state machine that the host consensus-verifies (which can include chains this particular gateway deployment was never meant to interoperate with, or a state machine registered generically on the host but for which this gateway simply hasn't had `NewDeployment` called yet) can dispatch a `PostRequest` with `from = <this gateway's own address, left-padded to 20 bytes coincidentally? No — attacker fully controls `from` bytes on their own source chain>`. Since `from` is attacker-controlled data on the source chain (it's just the sender address they choose to encode, not cryptographically bound to this contract), the attacker sets `request.from = bytes20(address(this))` and the check passes.

### Impact Explanation
Once `authenticate` passes, `onAccept` proceeds to decode `RequestKind.RedeemEscrow` or `RefundEscrow` and calls `withdraw()`, releasing escrowed input tokens for a commitment. An attacker who also controls the `commitment` (or can guess/replay one from a legitimate order not yet finalized) can direct escrowed user funds to an address of their choosing on this chain, from a message dispatched cheaply on any consensus-connected but non-peer state machine. This is concrete theft of escrowed funds, matching the report's "concrete theft ... of funds" bar and the CWE-863/610 class of the referenced advisory (an authorization check whose scope boundary is wrong, letting a caller act as if it were authorized in a different domain/organization/chain).

### Likelihood Explanation
Reachable by a single relayed message from an unprivileged relayer/attacker: dispatch a `PostRequest` on any state machine that has a live consensus client on the destination host but for which `NewDeployment` was never called for this gateway (a very plausible operational state — new chains are typically consensus-enabled before every app registers every peer, or a state machine can simply never be registered as a peer at all while still being a valid ISMP destination on the host). No governance or admin compromise is required; only ordinary relaying of a forged `from` field.

### Recommendation
Change `instance()` (and `authenticate`) in `evm/tron/contracts/apps/IntentGatewayV2.sol` to revert (e.g., `UnknownInstance`) when no peer has been explicitly registered for the state machine, exactly as done in `evm/src/apps/intentsv2/IntentsBase.sol::_instance`. Do not conflate "no configured peer" with "peer is myself." Audit all other Tron-specific or otherwise-diverged copies of `IntentGatewayV2`/`IntentsBase` for the same fallback pattern before deployment.

### Proof of Concept
1. Host `H` (the destination EVM chain) has a valid consensus client for state machine `S`, but the gateway on `H` has never received a `NewDeployment` message registering a peer for `S` (`_instances[keccak256(S)] == 0`).
2. Attacker, controlling any account on `S` (or simply constructing a raw ISMP `PostRequest` that a relayer will submit with a valid consensus/state proof for `S`), dispatches a request with:
   - `source = S`
   - `to = <gateway address on H>`
   - `from = abi.encodePacked(<gateway address on H>)` (20 bytes, attacker-chosen)
   - `body = bytes1(RequestKind.RedeemEscrow) ++ abi.encode(WithdrawalRequest{commitment: <target commitment>, tokens: [...], beneficiary: attacker})`
3. A relayer delivers this via the handler; the host verifies the (legitimate) consensus proof for `S` and calls `onAccept`.
4. `authenticate(request)` computes `instance(S)`; since no peer is registered, it returns `address(this)`, which equals `module` (decoded from the attacker-controlled `from`), so the check passes.
5. `withdraw()` releases the escrowed tokens for `commitment` to `attacker`.
