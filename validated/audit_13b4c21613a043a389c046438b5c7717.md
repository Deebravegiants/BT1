### Title
Webhook shop identity spoofing via unauthenticated `shop-domain` header not covered by HMAC - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, but the `shop` value that is forwarded to the application's handler is read from an HTTP header that is never included in the signed payload. Any user who can obtain one valid `(body, hmac)` pair for the app (e.g., by installing the app on their own store) can replay that exact body/HMAC pair while substituting an arbitrary `shop-domain` header, causing the app to process attacker-controlled webhook content under a victim shop's identity.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes and compares the HMAC solely against `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` returns only the raw request body: [2](#0-1) 

Meanwhile `shop` (and `topic`, `webhook_id`, `api_version`) are parsed straight from HTTP headers, which are never fed into the HMAC computation: [3](#0-2) 

`Registry.process` validates only the HMAC (over the body) and then immediately forwards the unauthenticated `request.shop` value to the app's handler as the tenant identifier: [4](#0-3) 

This breaks the intended identity binding: `HMAC-verified bytes (body) == identity used for tenant attribution (shop header)`. Because `api_secret_key` is shared across every shop that has installed the app, any store owner can generate a fully valid `(body, hmac)` pair for their own store, then resend it with the `x-shopify-shop-domain` (or `shopify-shop-domain`) header changed to any other installed shop's domain. `Registry.process` will accept it, since the HMAC check only covers the body, and will call the app's handler with `data.shop` set to the victim's domain: [5](#0-4) 

The library's own documentation presents `data.shop` as a trustworthy, verified field of a processed webhook without warning that it is not bound to the HMAC, reinforcing that host apps relying on the documented API are exposed: [6](#0-5) 

### Impact Explanation
This enables cross-tenant confusion: an attacker who owns a legitimate installation of the app can forge webhook deliveries that the receiving app will attribute to any other shop that has the app installed, because `shop` is never part of the authenticated payload. Any app logic keyed off `data.shop` (looking up a stored session/access token for that shop, updating per-shop records, enqueuing per-shop jobs) can be triggered with attacker-chosen body content under a victim tenant's identity, which is a cross-tenant access primitive.

### Likelihood Explanation
Exploitation requires only that the attacker be able to install the app on their own store (i.e., be any ordinary merchant/unprivileged user of the app), capture one legitimate webhook body+HMAC pair addressed to themselves, and resend it with a modified shop-domain header — no access to `api_secret_key`, access tokens, or any privileged component is needed.

### Recommendation
Include the `shop` (and ideally `topic`, `api_version`, `webhook_id`) values in the signed material, or independently verify that the `shop` header corresponds to a shop the app has actually installed/holds a session for before dispatching to handlers. At minimum, `Webhooks::Request#to_signable_string` should incorporate the shop-domain header, matching the identity-binding pattern used for OAuth's `AuthQuery#to_signable_string`, which does bind `shop` into the signed string: [7](#0-6) 

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`, causing the app to register webhooks for events on that store.
2. Attacker triggers or waits for a real webhook delivery, capturing the exact raw body `B` and its valid `x-shopify-hmac-sha256` header `H` (computed by Shopify using the app's shared `api_secret_key`).
3. Attacker replays a POST to the app's webhook endpoint with the same raw body `B`, the same (still-valid) HMAC header `H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(B)`; this succeeds because `B` and `H` are unmodified.
5. `Registry.process` invokes the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the host app to process attacker-controlled content attributed to `victim-shop.myshopify.com`.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
