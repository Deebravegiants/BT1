### Title
Unbounded router pull via `approveUnlimited` lets an attacker sweep residual/stranded token balance from `ExternalActionSwap` into their own output UTXO - (File: contracts/external-actions/swaps/ExternalActionSwap.sol / LifiExternalAction.sol)

### Summary
`ExternalActionSwap.swap` computes `inputAmount = uint256(-deltaAmounts[0])` (the amount Hinkal actually funded this tx) but never enforces that the router only consumes that amount. `LifiExternalAction.callRouter` grants the router an unlimited allowance (`approveUnlimited`) over the action contract's entire `inputToken` balance and then executes fully attacker-supplied `externalActionMetadata` calldata against it, so the router can pull (via `transferFrom`) any amount up to the contract's total balance of `inputToken`, not just the amount Hinkal funded this transaction. Because `swappedAmount` is measured only as `balanceAfter - balanceBefore` of `outputToken` around that call, any pre-existing/residual `inputToken` balance sitting in the shared `ExternalActionSwap` contract gets swapped along with it and lands entirely in the attacker's own output UTXO.

### Finding Description
The invariant that should hold is:
`tokens actually consumed by the router from the action's inputToken balance in a tx == -deltaAmountChanges[0] Hinkal sent that action for that same tx`.

Tracing the code:
- `Hinkal._externalTransact` (contracts/Hinkal.sol:244-256) computes `deltaAmountChanges[i]` and, for negative entries, transfers exactly `-deltaAmountChanges[i]` of `erc20TokenAddresses[i]` to the external action contract, then calls `runAction`.
- `ExternalActionSwap.swap` (contracts/external-actions/swaps/ExternalActionSwap.sol:44-68) computes `inputAmount = uint256(-deltaAmounts[0])` (minus flat fee if applicable) and passes it into `callRouter`, but this value is purely informational.
- `LifiExternalAction.callRouter` (contracts/external-actions/swaps/LifiExternalAction.sol:16-36) never uses the `inputAmount` parameter to bound the swap. It calls `approveUnlimited(inputToken, router)` — an infinite, persistent approval — and then blindly executes `router.call(externalActionMetadata)`, where `externalActionMetadata` is fully attacker-controlled calldata (an "attacker controls" field explicitly called out in the question). The LI.FI router will pull whatever amount that calldata specifies via `transferFrom`, up to the contract's actual `inputToken` balance and the (unlimited) allowance — completely decoupled from the `inputAmount`/`-deltaAmounts[0]` Hinkal funded this transaction.
- `swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore` (LifiExternalAction.sol:35) captures the *entire* output received during the call, including any output derived from residual/stranded `inputToken` balance the contract already held (e.g., dust left over from a prior swap due to rounding or a fee-on-transfer token, or any token simply transferred to this public contract address by anyone).
- Back in `Hinkal.transact` (contracts/Hinkal.sol:97-146), the check `balanceDif == amountChanges[i] + utxoAmount` is satisfied *by construction*: `utxoSet[0].amount` is set to whatever `amountToSendToHinkal` the swap actually produced, and that same figure is summed into `utxoAmount`. There is no independent, circuit-constrained upper bound on the output amount — only `circomData.slippageValues[1]`, which is a floor (`>=`), never a ceiling.

Root cause: the action contract's token custody is not scoped per-transaction. `approveUnlimited` plus arbitrary router calldata lets any unprivileged caller direct the router to consume the contract's *entire* balance of `inputToken`, not just the portion Hinkal transferred in for that call, and that extra value is credited to the attacker's own stealth-address UTXO with no cap.

### Impact Explanation
Any residual `inputToken` balance sitting in the shared `ExternalActionSwap`/`LifiExternalAction` contract (dust from rounding, fee-on-transfer remnants of a previous legitimate swap, or tokens sent to the contract's public address by any third party) can be swept by an unprivileged attacker into their own shielded output UTXO on their next swap call for that token, in excess of the `-deltaAmountChanges` Hinkal actually sent them that transaction. This is direct theft of in-flight/protocol-held funds and is repeatable every time residual balance accumulates in the contract, matching the Critical category "direct theft of shielded or in-flight user funds."

### Likelihood Explanation
Preconditions: the `ExternalActionSwap`/`LifiExternalAction` contract must hold a non-zero residual balance of the target `inputToken` (achievable via normal rounding dust from LI.FI swaps, fee-on-transfer tokens, or a trivial direct `transfer` to the contract's address by the attacker themselves as "seed"). The attacker needs no special role — only the ability to submit their own `transact` call with self-chosen `externalActionMetadata` (the LI.FI router calldata), which the question confirms is attacker-controlled. Cost is a single transaction; the technique is repeatable indefinitely as residual balance reappears.

### Recommendation
Constrain the router's token pull to exactly the funded input amount: use bounded `approve(router, inputAmount)` (reset to zero after the call) instead of `approveUnlimited`, and/or verify inside `callRouter` that the token balance consumed from the contract equals `inputAmount` (measure `balanceBefore`/`balanceAfter` of `inputToken` as well as `outputToken`, and require the pulled amount does not exceed what Hinkal funded this tx). Additionally, sweep/disallow any accumulation of unaccounted balances in the action contract, and add an explicit ceiling check (not just a slippage floor) tying `swappedAmount` to the funded input.

### Proof of Concept
Foundry plan:
1. Deploy `Hinkal`, `LifiExternalAction`, a mock ERC20 `TKN`, and a mock LI.FI router that performs `transferFrom(action, router, amountSpecifiedInCalldata)` then sends back an equivalent `outputToken` amount.
2. Seed residual: have any account directly `transfer` `R` amount of `TKN` (inputToken) to the deployed `LifiExternalAction` contract address (simulating rounding dust/stray transfer).
3. Attacker performs a normal shielded deposit of `TKN` for a small legitimate swap amount `A`, generating a valid proof with `deltaAmounts[0] = -A`.
4. Craft `externalActionMetadata` for the mock router to `transferFrom(action, router, A + R)` instead of `A` (allowed because `approveUnlimited` grants the router unlimited allowance over the whole `A+R` balance).
5. Call `Hinkal.transact` with this proof/circomData.
6. Assert: `swappedAmount` (and resulting `utxoSet[0].amount` / attacker's decrypted UTXO) reflects `A + R`, not `A`; assert `Hinkal.transact`'s balance-diff check for `TKN`/output token still passes; assert the `LifiExternalAction` contract's `TKN` balance decreased by `A + R` while Hinkal only funded `A` that transaction (i.e., `-deltaAmountChanges[0] == A` but tokens leaving the action `== A + R`), proving the invariant `tokens leaving the action == -deltaAmountChanges Hinkal sent that tx` is broken.     function callRouter(
        address inputToken,
        uint256 inputAmount,
        address outputToken,
        bytes calldata externalActionMetadata
    ) internal override returns (uint256 swappedAmount) {
        uint256 balanceBefore = getERC20OrETHBalance(outputToken);

        if (inputToken == address(0)) {
            (bool success, ) = router.call{value: inputAmount}(
                externalActionMetadata
            );
            require(success, "LI.FI swap failed: native coin");
        } else {
            approveUnlimited(inputToken, router);
            (bool success, ) = router.call(externalActionMetadata);
            require(success, "LI.FI swap failed: erc-20 token");
        }

        swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore;
    }
