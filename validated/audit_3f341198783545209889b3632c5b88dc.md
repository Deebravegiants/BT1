### Title
IntentGatewayV2 (Tron) `withdraw()` transfers escrow tokens before decrementing accounting, enabling reentrancy-based fund drain - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2.withdraw()` sends escrowed native ETH/ERC-20 to the beneficiary via a raw low-level `.call()`/`token.call()` *before* decrementing the internal `_orders[commitment][token]` escrow accounting mapping. This is the exact CEI violation described in the external report (Beedle `Lender.setPool`): an external transfer is made while the contract's own bookkeeping is still stale, giving a malicious beneficiary a reentrancy window to interact with other escrow-reading functions before the balance is reduced.

### Finding Description
`withdraw()` is invoked from `onAccept` (`RedeemEscrow`/`RefundEscrow`) and `onGetResponse`, both gated `onlyHost`, so it is ultimately triggered by intent solvers/users completing fills or cancellations of their own orders — an unprivileged, attacker-controllable path (a user can name any contract as `order.user`/beneficiary): [1](#0-0) 

```solidity
function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
    address beneficiary = address(uint160(uint256(body.beneficiary)));
    _filled[body.commitment] = beneficiary;

    uint256 len = body.tokens.length;
    for (uint256 i; i < len;) {
        address token = address(uint160(uint256(body.tokens[i].token)));
        uint256 amount = body.tokens[i].amount;
        if (_orders[body.commitment][token] == 0) revert UnknownOrder();

        if (token == address(0)) {
            (bool sent,) = beneficiary.call{value: amount}("");     // <-- external call FIRST
            if (!sent) revert InsufficientNativeToken();
        } else {
            (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
            if (!success) revert TransferFailed();
        }

        _orders[body.commitment][token] -= amount;                   // <-- state updated AFTER
        ...
```

Note the check is `== 0` (existence only), not a comparison against `amount`, and the decrement happens only *after* the external call returns. During the native-ETH `.call{value: amount}("")`, the beneficiary contract gets a fully attacker-controlled execution context before `_orders[body.commitment][token]` is reduced. Other public entry points on the same contract read this same mapping while it is still stale — e.g. the destination-chain cancellation branch of `cancelOrder`, which checks order existence via `_orders[commitment][...]` and dispatches a fresh `RefundEscrow` message without first checking `_filled[commitment]`: [2](#0-1) 

Contrast this with the corresponding, correctly-ordered logic in the primary EVM implementation, `IntentsBase._withdraw`, which decrements escrow *before* making the external transfer (proper CEI): [3](#0-2) 

The Tron contract is a divergent, unpatched copy that reintroduces the exact anti-pattern the main codebase's `IntrinsicIntentsReentrancyTest.sol` was written to eliminate (that suite documents the CEI fix applied to `_fillSameChain`/`_fillCrossChain`, but the Tron `withdraw()` was not brought in line): [4](#0-3) 

No `nonReentrant` guard exists anywhere in the Tron contract file to compensate for the ordering bug.

### Impact Explanation
A user/solver who is the beneficiary of an escrow release (fill redemption or cancellation refund) can deploy a malicious contract as the beneficiary/`order.user`. When native-ETH escrow is released, the malicious contract's fallback executes mid-transfer while `_orders[body.commitment][token]` still reflects the pre-payout balance. This stale read is reachable from other unprivileged, attacker-invocable functions operating on the same commitment (e.g. `cancelOrder`), allowing duplicate escrow-release dispatches to be initiated against funds that have already been paid out but not yet accounted for. This is a Critical/High severity fund-safety bug: it can lead to unauthorized duplicate withdrawal messages and theft/drain of escrowed lender/user funds in the IntentGatewayV2 escrow, the same impact class as the referenced report (contract drain via reentrant transfer-before-state-update).

### Likelihood Explanation
Likelihood is High for any deployment of this Tron contract: the attack requires only that the attacker be a normal, unprivileged order participant (place an order, act as solver, or be named beneficiary) with a contract address able to receive native-token payouts — no elevated privilege, governance, or validator/relayer compromise is needed. The vulnerable code path (`withdraw`) is on the standard order-completion/cancellation flow that every intent settlement passes through.

### Recommendation
Apply the Checks-Effects-Interactions pattern in `withdraw()`: decrement `_orders[body.commitment][token]` (and clear/zero the transaction fee entry) *before* performing the native-ETH `.call` or ERC-20 `transfer`, mirroring the pattern already used in `evm/src/apps/intentsv2/IntentsBase.sol`. Additionally, add a `nonReentrant` guard to `onAccept`/`onGetResponse`/`withdraw`, and add a `_filled[commitment] != address(0)` check to the destination-chain branch of `cancelOrder` to prevent duplicate refund/redeem dispatches for an already-settled commitment.

### Proof of Concept
1. Attacker places (or fills) an order on the Tron `IntentGatewayV2` deployment, setting `order.user`/beneficiary to a malicious contract `Evil` that implements a payable `receive()`.
2. The settlement flow (e.g. destination fill) causes a `RedeemEscrow`/`RefundEscrow` message to be delivered on the source chain via `onAccept` → `withdraw(body, ...)`.
3. Inside `withdraw`, for the native-token entry, `beneficiary.call{value: amount}("")` transfers ETH to `Evil` before `_orders[body.commitment][address(0)]` is decremented.
4. `Evil.receive()` re-enters the gateway (e.g. calls `cancelOrder` for the same order/commitment), which re-reads `_orders[commitment][token]` — still non-zero/stale — passing existence checks and dispatching an additional `RefundEscrow` request for funds already paid out, or otherwise manipulating shared escrow state before `withdraw`'s decrement executes.
5. When the duplicate message is eventually processed, the same vulnerable `withdraw` transfers the same escrowed amount again, resulting in a double payout / drain relative to the actual outstanding escrow.
