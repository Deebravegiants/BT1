### Title
Webhook HMAC signature does not bind the `shop-domain` header, allowing shop-identity spoofing on genuine webhook deliveries - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/utils/hmac_validator.rb)

### Summary
`ShopifyAPI::Webhooks::Request` treats `shop-domain` (and `topic`, `webhook-id`, `api-version`) as trusted, unauthenticated header data, while the HMAC signature only ever covers the raw request body. `Registry.process` then hands this unauthenticated `shop` value straight to the app's webhook handler as the identity of the tenant the event belongs to.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate`/`validate_signature` computes the HMAC purely over `verifiable_query.to_signable_string` (i.e., the body) and compares it to the `hmac` header: [2](#0-1) 

Meanwhile `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are read directly from HTTP headers with no cryptographic binding to the body or the HMAC: [3](#0-2) 

`Registry.process` validates only the HMAC and then forwards the header-derived `shop` (and `topic`) unchanged to the handler as the authoritative tenant identity: [4](#0-3) 

Because the signable string is `raw_body` alone, `(raw_body, hmac)` is a valid pair for *any* combination of header values. Any actor who can trigger a legitimate webhook for their own shop (e.g., by placing an order or updating a product in a store they control) obtains a genuinely-signed `(raw_body, hmac)` pair. That pair remains valid if resent to the app's public webhook endpoint with the `shop-domain` header rewritten to a different (victim) shop, since the header is never part of the signed content — no TLS interception or secret-key knowledge is required, only the ability to compose an HTTP POST with the exact bytes and HMAC value previously observed.

This breaks the identity binding: `authenticated(raw_body) == shop-domain-header`. The library authenticates only the *bytes*, but the identity field the host app relies on (`WebhookMetadata#shop`) is parsed from bytes that were never verified.

### Impact Explanation
An attacker-controlled shop can forge a webhook delivery for a victim shop by resending a signature-valid payload with an altered `shop-domain` header. Applications that use `WebhookMetadata#shop` to select or update tenant data (a common and expected use, since it is the field this gem explicitly exposes for that purpose) can be made to apply attacker-supplied data under another merchant's identity — a cross-tenant data-integrity/confusion issue. This matches the Critical "cross-tenant access" impact category, since the tenant boundary (`shop`) is exactly the field that fails to be bound to the authenticated bytes.

### Likelihood Explanation
Any unprivileged party with their own Shopify development/trial store can trigger events and capture legitimate `(raw_body, hmac)` pairs at will, then replay them with a rewritten header value directly against a target app's public webhook URL. No secrets, TLS interception, or privileged access are required — only the gem's own documented header/body split, which is under the gem's control (`lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`).

### Recommendation
Bind the shop (and ideally topic/webhook-id) to the authenticated payload rather than trusting it as a bare header. Concretely:
- Include `shop-domain` (and other identity-bearing headers actually consumed by `WebhookMetadata`) in the signable string used for `HmacValidator`, or
- Require host applications to cross-check `request.shop` against the shop associated with a securely looked-up webhook subscription/session before acting on the event, and document this requirement explicitly, or
- At minimum, have `Registry.process` reject/flag requests where the header-derived shop cannot be corroborated against a known, previously-registered subscription for that specific webhook id.

### Proof of Concept
1. Attacker owns `attacker-shop.myshopify.com` and has the app installed there.
2. Attacker triggers an event (e.g., `orders/create`) in their own shop; Shopify sends a webhook POST to the app's endpoint with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC of raw_body>`, and body `raw_body`.
3. Attacker captures this exact `raw_body` and `hmac` value (they are the recipient of their own webhook, so no interception is needed).
4. Attacker crafts a new POST to the same app endpoint with the identical `raw_body` and `hmac` header, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `raw_body` against `hmac` — validation succeeds.
6. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: ..., body: parsed_body, ...)` and processes attacker-controlled event data under the victim shop's identity. [5](#0-4)
