### Title
Non-embedded session lookup trusts an unsigned, deterministic session cookie value as an authenticated identity, enabling cross-tenant access-token theft - (File: `lib/shopify_api/utils/session_utils.rb`)

### Summary
For non-embedded (cookie-based) apps, `ShopifyAPI::Utils::SessionUtils.current_session_id` and `cookie_session_id` return the raw value of the `shopify_app_session` cookie as the trusted session identifier with no cryptographic verification. Because `ShopifyAPI::Auth::Session` IDs are deterministic (`"offline_#{shop}"` for offline sessions, `"#{shop}_#{user_id}"` for online sessions) and the `SessionCookie` object carries only a plain `value` with no signature or HMAC binding it to the OAuth flow that created it, any unauthenticated request can supply a forged `Cookie: shopify_app_session=offline_<victim-shop>.myshopify.com` header and have the host app resolve it to the victim shop's stored session/access token.

### Finding Description
`SessionUtils.current_session_id` (`lib/shopify_api/utils/session_utils.rb:19-37`) branches on `Context.embedded?`. For the non-embedded path (and as a fallback for embedded apps without a JWT) it does: [1](#0-0) 

It simply calls `cookie_session_id(cookies)`: [2](#0-1) 

This returns `cookies[SESSION_COOKIE_NAME]` verbatim — bytes taken directly from the incoming HTTP `Cookie` header, with no HMAC/signature check comparable to `Utils::HmacValidator` (used for OAuth callbacks and webhooks) or `JwtPayload` (used for embedded session tokens, which verifies `aud`/`exp`/signature, see `lib/shopify_api/auth/jwt_payload.rb:23-45`).

The value that ends up in that cookie is the `Session#id`, produced deterministically: [3](#0-2) 

and set into the cookie by `Oauth.validate_auth_callback` as plain text: [4](#0-3) 

`Oauth::SessionCookie` itself is a bare struct with no integrity protection: [5](#0-4) 

Every other identity-bearing value in this gem is bound with an HMAC or JWT signature (`AuthQuery` via `HmacValidator.validate`, `Webhooks::Request` via `HmacValidator.validate`, embedded session tokens via `JwtPayload`). The cookie-derived session id is the one exception: the equality the host application relies on is `session_id_from_cookie == session_id_that_HmacValidator/JwtPayload_would_have_produced_for_a_real_OAuth_session`, but the gem never checks that equality — it trusts whatever bytes arrive in the `Cookie` header. Since the id format is public and deterministic (`offline_#{shop}`), an attacker who knows (or guesses) a target's `*.myshopify.com` domain — which is not secret — can construct the exact session id string without ever completing OAuth.

### Impact Explanation
If a host application follows the gem's own documented pattern in `docs/usage/oauth.md` (plain, non-encrypted cookie assignment) and later calls `SessionUtils.current_session_id(nil, cookies, false)` to look up the shop's stored offline session/access token for making Admin API calls, an attacker can:
1. Send a request with `Cookie: shopify_app_session=offline_<victim-shop>.myshopify.com`.
2. Have the gem return that exact string as the "current session id".
3. Cause the host's session storage lookup (by this id) to return the victim shop's `Session`, including its `access_token`.

This is a cross-tenant access/authentication-bypass class issue: the identity binding "shop that completed OAuth" is not equal to "shop whose access token gets served", yet the gem treats them as equal because the session id is unauthenticated, attacker-controllable, and deterministic.

### Likelihood Explanation
Exploitation requires no credentials, no XSS, and no TLS interception — only knowledge of a target shop's `myshopify.com` domain (routinely public/discoverable) and the ability to send an arbitrary `Cookie` header, which any HTTP client can do since `HttpOnly`/`Secure` flags only restrict JavaScript access, not what bytes a client chooses to send in its own request. The offline session id format `offline_#{shop}` requires no brute forcing at all.

### Recommendation
Do not use the raw, predictable session id as the sole identity credential in the cookie. Instead:
- Store a cryptographically random, unguessable session cookie value (e.g., signed/HMAC'd, or an opaque random token distinct from the session id) and map it server-side to the real session id, or
- Sign/HMAC the cookie value (similar to `Utils::HmacValidator`) so `SessionUtils.cookie_session_id` can verify authenticity before returning it, rejecting any cookie whose signature does not match.

### Proof of Concept
1. Attacker learns (via app listing, webhook logs, or brute-force of common store-name patterns) that a victim store's domain is `victim-shop.myshopify.com`, and knows the app previously completed offline OAuth with that shop (a very common state for any installed app).
2. Attacker sends an authenticated-looking request to the host app with header:
   `Cookie: shopify_app_session=offline_victim-shop.myshopify.com`
3. Host app calls:
   ```ruby
   session_id = ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)
   # => "offline_victim-shop.myshopify.com"
   session = MyApp::SessionRepository.load_session(session_id)
   ```
4. `SessionUtils.cookie_session_id` returns the attacker-supplied string unchanged (`lib/shopify_api/utils/session_utils.rb:68-71`), with no verification, and the host app's storage lookup returns the victim's `Session` object containing its real `access_token`, which the attacker's request flow then uses to act on the victim shop via the Admin API.
