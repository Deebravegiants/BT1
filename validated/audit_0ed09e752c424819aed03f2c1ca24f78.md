### Title
Signed `EmporiumStack` authorization is not bound to `stealthAddressStructure`, allowing front-run redirection of `handleOut`-minted UTXOs to an attacker - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
The wallet owner's ECDSA signature over an `EmporiumStack` only commits to `emporiumMessage`, `ops`, `maxFee`, and `deadline`; it never commits to the `stealthAddressStructure` that will receive the resulting `UTXO`. Neither `calldataHash` (via `getHashedCalldata`) nor the `usedMessages` replay guard (keyed only on `emporiumMessage`) ties the authorized fund-moving operations to a specific destination, so anyone who observes a valid signed stack before it lands on-chain can submit it first with their own `stealthAddressStructure` and a freshly generated proof, stealing the resulting balance increase.

### Finding Description
The broken equality: `(recipient of minted UTXO in handleOut)` should equal `(recipient the wallet owner authorized)`, but on-chain nothing enforces this.

- `EmporiumUpgradeable.verifyWallet` (contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol:302-349) recovers the ECDSA signer over `keccak256(abi.encode(EMPORIUM_SIGNATURE_TYPEHASH, circomData.emporiumMessage, _hashEmporiumOps(stack.ops), stack.maxFee, stack.deadline))`. `_hashEmporiumOps` (lines 284-300) hashes only `endpoint/invokeWallet/value/callData` per op — never `stealthAddressStructure`. [1](#0-0) 
- `runAction` executes `stack.ops` via `IHinkalWallet(stack.signerAddress).callHinkalWallet(...)`, moving real value out of the victim's wallet, then `handleOut` mints the `UTXO` to `circomData.stealthAddressStructure` — a field fully controlled by whoever calls `Hinkal.transact`, not by the signer. [2](#0-1) 
- `usedMessages` in `EmporiumStorage` is a `mapping(uint256 => bool)` keyed purely on `emporiumMessage`, with no relation to `stealthAddressStructure` or the caller. [3](#0-2) 
- `HinkalHelper.performHinkalChecks` verifies `CircomDataBuilder.getHashedCalldata(circomData) == circomData.calldataHash`, but `getHashedCalldata1`/`getHashedCalldata2` never include `circomData.stealthAddressStructure`, `erc20TokenAddresses`, or `amountChanges`. [4](#0-3) 
- `CircomDataBuilder.getSignedMessageHash` does include `stealthAddressStructure.H1x/H1y/H0x/H0y` in `hash2`, but this is only a public input consumed by the ZK circuit to prove *knowledge* of a consistent tuple — it does not restrict *which* `stealthAddressStructure` the attacker chooses, since the attacker can freely generate a fresh valid proof for any self-chosen `stealthAddressStructure`. [5](#0-4) 
- Any unprivileged EOA can call `Hinkal.transact` directly (bypassing the relay whitelist) by setting `circomData.relay = address(0)` and `circomData.originalSender = msg.sender`, satisfying `performHinkalChecks`'s sender check. [6](#0-5) 

**Exploit flow:** The victim signs an `EmporiumStack` (v,r,s over ops/emporiumMessage/maxFee/deadline) intending to submit it themselves with their own `stealthAddressStructure`. Before that transaction lands, the attacker observes the signed stack + `emporiumMessage` (e.g., from a mempool, a relay queue, or any transport where the signed payload is visible prior to inclusion) and submits their own `Hinkal.transact` call with identical `externalActionData.externalActionMetadata` (same stack bytes) and identical `emporiumMessage` (required, since it's part of the signed hash and part of `usedMessages`), but their own `stealthAddressStructure` and a freshly generated valid Groth16 proof matching that choice, plus (if desired) their own `erc20TokenAddresses`/`amountChanges`/`deltaAmountChanges` for the surrounding shielded-balance bookkeeping. `verifyWallet` succeeds since none of the swapped fields affect the recovered signer or the `usedMessages` key; `stack.ops` execute against the victim's `HinkalWallet`, and `handleOut` mints the resulting UTXO to the attacker's `stealthAddressStructure`. `usedMessages[emporiumMessage]` is now consumed, so the victim's own later submission of the same signed stack reverts with `UsedMessage()`, but the funds have already left the wallet to the attacker.

Existing guards do not stop this: `performHinkalChecks`, `dimensionsCheck`, `checkOnchainCreation`, `verifyProof`, `rootHashExists`, and the slippage/balance requires in `Hinkal.transact` all validate internal consistency of the *attacker's own* circomData/proof pair — none of them validate that the destination matches what the *signer* intended, because the signer's authorization never encoded a destination in the first place.

### Impact Explanation
Critical — an unprivileged attacker can redirect the entire token balance increase resulting from a wallet owner's authorized `EmporiumStack` operations (e.g., unwrapping collateral, closing a position, swapping) into their own shielded UTXO, i.e., "executing calls or moving assets a wallet owner...never authorised" in terms of destination, resulting in direct theft of the value produced by that call sequence. This is repeatable against any victim who has a pending signed `EmporiumStack` not yet consumed on-chain, each time the attacker can observe it before submission.

### Likelihood Explanation
Preconditions: the attacker must obtain a validly signed, not-yet-used `EmporiumStack` + `emporiumMessage` before it is included on-chain (e.g., visible in a public mempool, exposed via a relay/broadcast channel, or otherwise observable pre-confirmation), and must be able to generate a valid Groth16 proof for their own chosen `stealthAddressStructure`/token fields — both entirely within the capabilities of an unprivileged attacker per the threat model (they can generate proofs for their own UTXOs and craft any `CircomData`/`Dimensions` field). Cost is a single transaction plus proof generation; the attack is trivially repeatable against any exposed signed stack.

### Recommendation
Bind the destination to the signature: include `circomData.stealthAddressStructure` (and ideally `msg.sender`/`circomData.originalSender`) inside the EIP-712 struct hashed and signed in `verifyWallet` (i.e., add it to `EMPORIUM_SIGNATURE_TYPEHASH`/the hashed message), so that the wallet owner explicitly authorizes both the operations and the recipient of any resulting UTXO. Additionally, include `stealthAddressStructure` in `getHashedCalldata`/`calldataHash` so the on-chain calldata-integrity check also covers it.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `EmporiumUpgradeable`, `HinkalWallet` (victim-owned), a mock DeFi endpoint that unwraps collateral into ERC20 balance on `callHinkalWallet`.
2. Victim EOA signs an `EmporiumStack` (`ops` = unwrap collateral call via wallet, `emporiumMessage = M`, `maxFee`, `deadline`) intended to be submitted with victim's own `stealthAddressStructure_V` and a proof `P_V`.
3. Before that transaction is submitted, attacker constructs `circomData_A` reusing the identical `externalActionData.externalActionMetadata` (same encoded stack bytes) and `emporiumMessage = M`, but sets `circomData_A.stealthAddressStructure = stealthAddressStructure_A` (attacker's), and locally generates a fresh valid Groth16 proof `(a,b,c)` for `circomData_A`/`dimensions_A` using snarkjs.
4. Attacker calls `Hinkal.transact(a,b,c,dimensions_A,circomData_A)` directly (`relay = address(0)`, `originalSender = attacker`).
5. Assert: transaction succeeds, `handleOut`'s returned `UTXO.stealthAddressStructure == stealthAddressStructure_A` (not `stealthAddressStructure_V`), victim's `HinkalWallet` balance decreased by the unwrapped amount, and `usedMessages[M] == true`.
6. Assert the equality is broken: attempt victim's original intended transaction with `stealthAddressStructure_V` and `emporiumMessage = M` reverts with `UsedMessage()`, proving the victim's authorized action's proceeds went to the attacker instead of the signer's intended recipient.

    function verifyWallet(
        EmporiumStack memory stack,
        CircomData calldata circomData
    ) internal {
        EmporiumStorageVars storage $ = _getEmporiumStorage();

        if ($.usedMessages[circomData.emporiumMessage]) {
            revert UsedMessage();
        }

        $.usedMessages[circomData.emporiumMessage] = true;

        if (stack.signerAddress == address(0)) {
            return;
        }

        bytes32 hashedMessage = _hashTypedDataV4(
            keccak256(
                abi.encode(
                    EMPORIUM_SIGNATURE_TYPEHASH,
                    circomData.emporiumMessage,
                    _hashEmporiumOps(stack.ops),
                    stack.maxFee,
                    stack.deadline
                )
            )
        );

            hashedMessage,
            stack.v,
            stack.r,
            stack.s
        );
        bool verified = err == ECDSA.RecoverError.NoError &&
            recoveredAddress == stack.signerAddress;
        if (!verified) {
            revert InvalidSignature();
