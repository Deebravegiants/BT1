Confirmed: the `VerifiableQuery` interface only requires `hmac` and `to_signable_string`, and `Webhooks::Request#to_signable_string` returns solely `@raw_body` [1](#0-0) , while `topic`, `shop`, `api_version`, and `webhook_id` are all read straight from unauthenticated HTTP headers [2](#0-1) . `Registry.process` validates only the body's HMAC and then dispatches to the handler using `request.shop` and `request.topic` taken from those headers [3](#0-2) . This is a direct analog of the Xen bug class: a field (`shop`, the tenant-identity binding) is acted upon (dispatched to the merchant-specific handler) without being covered by the integrity check (HMAC over body only).

### Title
Webhook `shop-domain` and `topic` headers are not covered by the HMAC, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC of the raw request body, then trusts the `shop` and `topic` values taken from HTTP headers to decide which handler runs and which tenant the payload is attributed to. Because those headers are not part of the signed material, any two (body, HMAC) pairs a merchant can legitimately generate (e.g., from their own shop's genuine webhooks) can be replayed with a different `shop-domain` header to make the host application process the data as if it belonged to another shop.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes and compares the HMAC over `verifiable_query.to_signable_string` [4](#0-3) . For webhooks, `to_signable_string` returns only `@raw_body`, the JSON body [1](#0-0) . The `shop`, `topic`, `api_version`, and `webhook_id` accessors are read directly from the (attacker-controllable at the HTTP layer) headers `x-shopify-shop-domain`, `x-shopify-topic`, etc. [2](#0-1) , and none of them are mixed into the signed string.

`Registry.process` then does:
```ruby
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
handler = @registry[request.topic]&.handler
...
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))
``` [3](#0-2) 

The binding the gem should be enforcing is: `hmac == HMAC(secret, body ‖ shop ‖ topic)` such that the authenticated `shop` equals the `shop` acted upon. Instead the code enforces only `hmac == HMAC(secret, body)`, and the value of `shop` used for tenant attribution is taken from an unauthenticated header. Before the attacker's request, the equality `authenticated_shop == acted_on_shop` holds only because Shopify's own infrastructure sets both consistently; after an attacker-crafted request (replaying a valid `(body, hmac)` pair captured from their own store's webhook with a substituted `shop-domain` header), `authenticated_shop` (implicitly "whatever body was signed for") no longer equals `acted_on_shop` (the header value used by the handler), yet the check still passes because the header isn't covered by the HMAC.

### Impact Explanation
Any embedded/multi-tenant app built on this gem that uses `WebhookMetadata#shop` to decide which merchant's records to update, credit, or invalidate (a first-class documented use per `docs/usage/webhooks.md`) can be tricked into attributing a webhook body to the wrong shop. An unprivileged attacker who controls one legitimately-installed shop can generate arbitrarily many valid `(body, hmac)` pairs (Shopify will happily emit real webhooks to their own store) and then send crafted HTTP requests directly to the app's webhook endpoint with the `shop-domain`/`topic` headers changed, since HMAC validation only checks the body. This crosses the tenant boundary — data or actions intended for shop A get attributed to shop B — which matches the "cross-tenant access" critical-impact category.

### Likelihood Explanation
Any internet-reachable webhook endpoint accepts this request; the attacker needs no `api_secret_key`, no access token, and no privileged account — only the ability to install the app on a shop they control (as any developer/merchant can) and to send an arbitrary HTTP POST to the app's public webhook callback URL, which is not restricted to Shopify's IP ranges by anything in this gem.

### Recommendation
Include `shop`, `topic`, `api_version`, and `webhook_id` in the signable string used for HMAC verification (or otherwise cryptographically bind them to the body), so that any header tampering invalidates the HMAC. At minimum, `Webhooks::Request#to_signable_string` should incorporate the header values that `Registry.process` subsequently trusts for tenant/topic dispatch.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers/receives a genuine webhook, capturing the raw body `B` and its valid `x-shopify-hmac-sha256` header `H` (a valid HMAC over `B` with the app's secret, computed by Shopify — no secret leakage needed since Shopify itself signs it).
2. Attacker sends a POST directly to the app's webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H` (valid), but `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Utils::HmacValidator.validate` succeeds because it only checks `B` against `H` [4](#0-3) .
4. `Registry.process` invokes the registered handler with `WebhookMetadata.shop == "victim-shop.myshopify.com"` even though the body actually originated from `attacker-shop.myshopify.com` [5](#0-4) , causing the host application to act on `victim-shop`'s tenant context using attacker-supplied data.
