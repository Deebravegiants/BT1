Audit Report

## Title
Cross-user response hijacking via unvalidated, client-controlled MessageID collision in gateway webapi capabilities handler - (File: core/services/gateway/handlers/capabilities/handler.go)

## Summary
The gateway's legacy webapi-trigger request path keys pending user callbacks in a shared in-memory map (`savedCallbacks`) using the `MessageID` field taken verbatim from the untrusted, client-supplied JSON-RPC request ID. The map write is an unconditional overwrite with no uniqueness or ownership check, so a second request using the same ID as an in-flight request from a different caller silently replaces the first caller's registered callback, causing the DON node's eventual response to be delivered to whichever caller currently occupies that map slot.

## Finding Description
`gateway.ProcessRequest` decodes the JSON-RPC request `ID` straight from the raw, unauthenticated request body via `jsonrpc2.DecodeRequest` and `g.codec.DecodeJSONRequest`, only bounding it to 200 characters, never checking for collision with other in-flight requests: [2](#0-1) . That ID becomes `msg.Body.MessageID` unconditionally in `JSONRPCCodec.DecodeJSONRequest`: [3](#0-2) .

`handler.HandleLegacyUserMessage` stores the caller's `Callback` in the shared `savedCallbacks` map keyed solely by this attacker-controlled `MessageID`, overwriting any existing entry unconditionally: [4](#0-3) . When the corresponding DON node later replies with the same `MessageID`, `handleWebAPITriggerMessage` looks up, deletes, and delivers the response to whichever callback currently occupies that map slot, with no verification that it matches the original requester: [5](#0-4) .

Critically, the HTTP entry point only extracts an optional bearer token for downstream JWT-based authorization elsewhere, but this token/caller identity is not incorporated into the `savedCallbacks` key at all — the key is purely the client-supplied string: [1](#0-0) . There is no per-caller/connection namespacing anywhere in this path, so any two unrelated HTTP callers hitting the same gateway DON/service with the same `id` value collide in the same global map. The `defaultCallbackMaxAgeSec` of 120 seconds provides a wide window during which a colliding ID from a concurrent request can overwrite an in-flight legitimate callback: [6](#0-5) . The existing test suite only validates that invalid/error-path messages don't leave stale entries; it does not cover concurrent same-ID collisions from distinct legitimate callers: [7](#0-6) .

## Impact Explanation
This maps to the "gateway request impersonation / cross-user response corruption" impact class. An unprivileged network caller who submits a request with the same JSON-RPC `id` as another in-flight request served by the same gateway/DON/service can hijack the legitimate response: the attacker's callback receives the DON's response payload intended for the original caller, while the original caller's request silently times out (their callback entry was evicted). Since this is a client-facing HTTP endpoint with no authentication requirement to reach `ProcessRequest` (the JWT is optional and unrelated to callback keying), this is triggerable purely with normal, unprivileged requests.

## Likelihood Explanation
Exploitability requires the attacker's request to share the exact same `id` value as a legitimate concurrently pending request from another user, and to be routed to the same handler instance (same gateway DON/service). If clients choose unpredictable, high-entropy IDs (e.g., random UUIDs), collision is infeasible for an attacker without insider knowledge of another user's chosen ID. Nothing in the gateway enforces ID unpredictability, uniqueness, or per-caller namespacing, which is a genuine design gap, but for the exploit to matter in practice, the attacker needs visibility into or control over the colliding ID (e.g., if a legitimate client library reuses fixed, sequential, or otherwise-guessable IDs). This is plausible but not universally guaranteed depending on deployment/client behavior, giving this moderate rather than trivial likelihood.

## Recommendation
Namespace `savedCallbacks` keys by both caller identity (e.g., derived from the authenticated JWT/connection or a server-generated correlation token) and the client-supplied `MessageID`, rather than relying solely on client input. Alternatively, generate the internal correlation key server-side (e.g., a UUID minted by the gateway per request) independent of the client-chosen JSON-RPC `id`, and only use the client ID for constructing the outward-facing JSON-RPC response envelope. Reject or queue (rather than silently overwrite) on detected collision with an in-flight ID as a defense-in-depth measure.

## Proof of Concept
1. Caller A sends a `web_api_trigger` legacy request to the gateway HTTP endpoint with JSON-RPC `id = "X"` and a valid `don_id`; this reaches `HandleLegacyUserMessage`, which registers `savedCallbacks["X"] = callbackA`.
2. Before the DON node responds, Caller B sends another legacy request to the same gateway/DON with `id = "X"`; `HandleLegacyUserMessage` unconditionally overwrites `savedCallbacks["X"] = callbackB`.
3. A DON node responds with `MessageID = "X"`; `handleWebAPITriggerMessage` looks up `savedCallbacks["X"]`, finds `callbackB`, deletes the entry, and delivers the node's response to Caller B. Caller A's HTTP request then blocks until `callback.Wait(ctx)` times out in `gateway.ProcessRequest`, receiving a `RequestTimeoutError` instead of the intended response.
4. This can be codified as a Go unit test in `core/services/gateway/handlers/capabilities/handler_test.go` that calls `handler.HandleLegacyUserMessage` twice with the same `MessageID` but different `Callback` instances, then invokes `handler.HandleNodeMessage` with a `web_api_trigger` response bearing that `MessageID`, and asserts that only the second callback receives the response while the first callback's `Wait` times out/never resolves.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageID]
