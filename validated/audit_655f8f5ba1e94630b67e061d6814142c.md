### Title
Sync-Committee (Ethereum) Consensus Client Has No Fraud-Proof/Equivocation Penalization Mechanism, Leaving Byzantine Validator Sets Unchallengeable - ([File: modules/ismp/clients/sync-committee/src/beacon_client.rs])

### Summary
The original report criticizes `OperationalStaking.sol` for lacking any mechanism to penalize dishonest Network Operators beyond an all-or-nothing `freezeValidator` call, with no slashing logic tying misbehavior to an economic cost. The analogous defect in Hyperbridge is in the `ConsensusClient` implementation for the Ethereum sync-committee light client: `verify_fraud_proof` is a stub that unconditionally errors out, meaning there is no working mechanism to detect, freeze, or penalize a validator set that equivocates.

### Finding Description
The generic `ConsensusClient` trait requires every consensus client to implement `verify_fraud_proof`, which is invoked by `freeze_client` when a relayer/fisherman submits two conflicting consensus proofs for the same height, in order to freeze the client and stop it from accepting further (potentially forged) state commitments: [1](#0-0) [2](#0-1) 

Other consensus clients (Tendermint/Polygon, which reuse the same Tendermint verifier) fully implement this by comparing canonical header hashes for equivocation and calling `verify_header_update` on both conflicting proofs: [3](#0-2) [4](#0-3) 

The sync-committee client, which verifies Ethereum's Casper FFG/sync-committee consensus for EVM destinations, does not implement this logic at all — it simply returns an error, regardless of the proofs supplied: [5](#0-4) 

This means the only mechanism the protocol documents for penalizing/containing a Byzantine Ethereum sync committee (an equivocation/51%/eclipse attack) — the `freeze_client` fraud-proof path — can never succeed for this client type, no matter how valid or well-formed the fraud proof is. As the project's own documentation states, safety for a PoS-verifying bridge depends entirely on the ability to freeze/slash on evidence of equivocation: [6](#0-5) [7](#0-6) 

### Impact Explanation
If a supermajority of the Ethereum sync committee (or an attacker who otherwise obtains signing power, e.g. via a long-range or eclipse attack window) produces two conflicting finalized headers, an honest relayer/fisherman attempting to submit a `FraudProofMessage` against the Hyperbridge beacon client will always have `verify_fraud_proof` fail with `FraudProofUnimplemented`, so `freeze_client` never completes and the consensus client is never frozen. `update_client` will continue to accept whichever forged consensus updates satisfy `verify_sync_committee_attestation`, letting attackers get state commitments for a forged Ethereum state accepted on Hyperbridge indefinitely. Any application relying on these state/storage proofs (token bridge mint/burn, message dispatch, intents settlement) can then be fed forged proofs, enabling unbacked minting or theft of escrowed/bridged funds through forged message delivery — this is exactly the "unsound state commitment / forged message delivery" impact class this analysis is instructed to accept.

### Likelihood Explanation
Submitting a fraud proof is permissionless — any relayer or fisherman monitoring the Ethereum P2P network can call this path once they observe equivocating attestations, so the *trigger* condition (detecting a Byzantine event) is realistic and matches the documented threat model (51%/eclipse/long-range attacks on PoS consensus). The defect is not conditional on any exploit sophistication: `verify_fraud_proof` fails deterministically for every input on this client, so the safety net completely and unconditionally fails to engage whenever it's needed for Ethereum-sourced state.

### Recommendation
Implement `verify_fraud_proof` for the sync-committee/beacon client using the beacon chain's equivocation rules (compare `SignedBeaconBlockHeader`s for the same slot/proposer per the `ProposerSlashing`/`AttesterSlashing` primitives already present in the codebase) and call `verify_sync_committee_attestation` (or equivalent) on both conflicting updates against the trusted state, mirroring the Tendermint/Polygon implementation, so `freeze_client` can actually engage for Ethereum-derived consensus. Track the underlying issue against `sync_committee_verifier::error::Error::FraudProofUnimplemented`.

### Proof of Concept
1. An Ethereum sync committee produces two conflicting finalized headers/attestations for the same slot (Byzantine equivocation) that both individually pass `verify_sync_committee_attestation`.
2. A relayer submits both as consensus updates via `update_client`; because verification is independent per-update, either or both can be accepted and used to derive `StateCommitment`s (subject to challenge period timing).
3. A fisherman detects the conflict and submits a `Message::FraudProof(FraudProofMessage { proof_1, proof_2, consensus_state_id, .. })` to `freeze_client`: [2](#0-1) 
4. `consensus_client.verify_fraud_proof(..)` resolves to the sync-committee client's implementation, which unconditionally returns `Err(SyncCommitteeError::FraudProofUnimplemented)`: [5](#0-4) 
5. `freeze_client` propagates the error and returns before calling `host.freeze_consensus_client(...)`, so the consensus client is never frozen and continues accepting/serving state commitments derived from the compromised validator set, regardless of how many honest fishermen submit valid fraud proofs.

```rust
/// Freeze a consensus client by providing a valid fraud proof.
pub fn freeze_client<H>(host: &H, msg: FraudProofMessage) -> Result<MessageResult, anyhow::Error>
where
	H: IsmpHost,
{
	let consensus_client_id = host
		.consensus_client_id(msg.consensus_state_id)
		.ok_or_else(|| Error::Custom("Unknown Consensus State Id".to_string()))?;

	host.is_consensus_client_frozen(msg.consensus_state_id)?;

	let consensus_client = host.consensus_client(consensus_client_id)?;
	let trusted_state = host.consensus_state(msg.consensus_state_id)?;

	consensus_client.verify_fraud_proof(host, trusted_state, msg.proof_1, msg.proof_2)?;

	host.freeze_consensus_client(msg.consensus_state_id)?;

	host.store_consensus_update_time(msg.consensus_state_id, host.timestamp())?;

	Ok(MessageResult::FrozenClient(msg.consensus_state_id))
}
```

```rust
	fn verify_fraud_proof(
		&self,
		host: &dyn IsmpHost,
		trusted_consensus_state: Vec<u8>,
		proof_1: Vec<u8>,
		proof_2: Vec<u8>,
	) -> Result<(), Error> {
		let update_1: TendermintConsensusUpdate =
			Decode::decode(&mut &proof_1[..]).map_err(|e| Error::Custom(e.to_string()))?;
		let update_2: TendermintConsensusUpdate =
			Decode::decode(&mut &proof_2[..]).map_err(|e| Error::Custom(e.to_string()))?;

		let consensus_state: ConsensusState = Decode::decode(&mut &trusted_consensus_state[..])
			.map_err(|e| Error::Custom(e.to_string()))?;

		let consensus_proof_1 = update_1
			.tendermint_proof
			.to_consensus_proof()
			.map_err(|e| Error::Custom(e.to_string()))?;

		let consensus_proof_2 = update_2
			.tendermint_proof
			.to_consensus_proof()
			.map_err(|e| Error::Custom(e.to_string()))?;

		let height_1 = consensus_proof_1.signed_header.header.height;
		let height_2 = consensus_proof_2.signed_header.header.height;
		if height_1 != height_2 {
			return Err(Error::Custom("Fraud proofs must be for the same block height".to_string()));
		}

		// A genuine fraud proof must demonstrate equivocation: two *distinct* blocks
		// signed by the validator set at the same height. Comparing the raw proof
		// bytes is insufficient — SCALE's `Decode` silently ignores trailing bytes
		// and other non-canonical encodings, so an attacker could submit the *same*
		// header twice with one copy malleated (e.g. an appended trailing byte or
		// reordered commit signatures), pass this byte-inequality check, and freeze
		// a live consensus client permissionlessly. Compare the canonical Tendermint
		// header hashes instead — they uniquely identify the block being committed.
		if consensus_proof_1.signed_header.header.hash() ==
			consensus_proof_2.signed_header.header.hash()
		{
			return Err(Error::Custom("Fraud proofs commit to the same block header".to_string()));
		}

		let trusted_state: TrustedState =
			TrustedState::try_from(consensus_state.clone().tendermint_state)
				.map_err(ismp::error::Error::Custom)?;

		let time = host.timestamp().as_secs();

		verify_header_update(trusted_state.clone(), consensus_proof_1, time)
			.map_err(|e| Error::Custom(e.to_string()))?;
		verify_header_update(trusted_state, consensus_proof_2, time)
			.map_err(|e| Error::Custom(e.to_string()))?;

		Ok(())
	}
```

```rust
			.to_consensus_proof()
			.map_err(|e| PolygonError::ConvertTendermintProof(e.to_string()))?;

		let consensus_proof_2 = update_2
			.tendermint_proof
			.to_consensus_proof()
			.map_err(|e| PolygonError::ConvertTendermintProof(e.to_string()))?;

		let height_1 = consensus_proof_1.signed_header.header.height;
		let height_2 = consensus_proof_2.signed_header.header.height;
		if height_1 != height_2 {
			return Err(PolygonError::FraudProofsDifferentHeight.into());
		}

		// A genuine fraud proof must demonstrate equivocation: two *distinct* blocks
		// signed by the validator set at the same height. Comparing the raw proof
		// bytes is insufficient — SCALE's `Decode` silently ignores trailing bytes
		// and other non-canonical encodings, so an attacker could submit the *same*
		// header twice with one copy malleated (e.g. an appended trailing byte or
		// reordered commit signatures), pass this byte-inequality check, and freeze
		// a live consensus client permissionlessly. Compare the canonical Tendermint
		// header hashes instead — they uniquely identify the block being committed.
		let header_hash_1 = consensus_proof_1.signed_header.header.hash();
		let header_hash_2 = consensus_proof_2.signed_header.header.hash();
		if header_hash_1 == header_hash_2 {
			return Err(PolygonError::FraudProofsIdentical.into());
		}

		let trusted_state: TrustedState =
			TrustedState::try_from(consensus_state.clone().tendermint_state)

		let time = host.timestamp().as_secs();

		verify_header_update(trusted_state.clone(), consensus_proof_1, time)
			.map_err(|e| PolygonError::VerifyHeaderUpdate(e.to_string()))?;
		verify_header_update(trusted_state, consensus_proof_2, time)
			.map_err(|e| PolygonError::VerifyHeaderUpdate(e.to_string()))?;

		Ok(())
	}
```

```text
This vulnerability can be mitigated by having consensus clients that actively participate in the p2p swarm and can ask as many nodes of the latest finalized header in the chain. Proof of stake consensus protocols mitigates this further with it’s use of an equivocation (aka slashing) protocol.

This protocol prevents validators from signing two headers at the same height by allowing anyone to report this misbehaviour on-chain causing the stake of the validator in question to be slashed. So, for off-chain consensus clients, this eclipse attack can be mitigated so long as the client is connected to at least one honest node.

On-chain consensus clients however do not participate in the p2p network and cannot gossip headers they receive and instead rely on relayers who do not need to be trusted to provide cryptographic proofs alongside the submitted headers. The whole point of on-chain consensus clients is anyone can be a relayer, but unfortunately in this scenario that also includes a potentially byzantine authority set of a counterparty chain.

Now that the consensus client has been eclipsed, the byzantine authority set can send state proofs of cross-chain messages associated with the forged chain allowing them to bridge tokens that simply don’t exist to the counterparty blockchain and swap them for other assets, bridging them back and destroying the peg of these assets on the counterparty.
```
