### Title
Attacker-controlled QR `parameters` octal string can crash signup via `assert_eq!` panic in `SweepConfiguration::parse_configuration_value` - ([File: src/plans/biometric_capture/focus_sweep.rs])

### Summary
When the `internal-data-acquisition` feature is enabled, a user QR code can set `SignupMode::FocusSweepExtension` with an arbitrary `parameters` string matching `[a-z0-9:]+`. This string is parsed with `u8::from_str_radix(parameter, 8)`, and any value that decodes to an octal-parseable number greater than 7 (e.g. `"10"` → decimal 8) flows unmodified into `SweepConfiguration::new` → `parse_configuration_value`, where an `assert_eq!` on the binary string length panics.

### Finding Description
The QR regex `QR_CODE_SIGNUP_EXTENSION` in [1](#0-0)  captures a free-form `parameters` group (`[a-z0-9:]+`) with no numeric-range validation. `Data::from_signup_extension` stores this raw string in `SignupExtensionConfig.parameters` [2](#0-1) , and `SignupMode::parse` allows selecting `FocusSweepExtension` (mode byte `2`) purely from attacker input [3](#0-2) .

In `focus_sweep::Plan::from`, the parameter string is converted via `u8::from_str_radix(parameter, 8).ok()`, falling back to `1` only if parsing fails [4](#0-3) . Critically, `u8::from_str_radix` with radix 8 successfully parses digit strings like `"10"` into the *decimal* value `8` (since it interprets the digits as base-8, not as validating that the number is ≤ 7); the parse succeeds for any decimal value up to `377` in octal notation (i.e., configuration_value up to 255 as u8), so the `unwrap_or(1)` fallback is never triggered for values 8–255.

That value is passed to `SweepConfiguration::new` → `parse_configuration_value`, which formats it as binary padded to at least 3 digits and asserts the resulting string is exactly 3 characters long: [5](#0-4) 
For any `configuration_value > 7`, `format!("{configuration_value:0>3b}")` produces more than 3 characters (e.g. `8` → `"1000"`), so the assertion fails and the process panics.

No validation exists anywhere in the QR regex, `SignupMode::parse`, or `focus_sweep::Plan::from` to reject or clamp values greater than 7 before they reach the assertion.

### Impact Explanation
An unprivileged attacker who presents a specially crafted user QR code (e.g. `userid:<id>:<policy>::2:10::`) can trigger a Rust `assert_eq!` panic inside the signup state machine (`biometric_capture::Plan::from` → `focus_sweep::Plan::from` → `SweepConfiguration::new`). This is an unrecoverable panic reachable purely from QR content, violating the fail-closed invariant that malformed/attacker input must not crash the signup pipeline. Depending on panic-handling/process-supervision behavior, this aborts the current signup and can wedge or restart the orb's signup process, denying service to the current and potentially subsequent signup attempts (denial of service / signup-state wedge).

### Likelihood Explanation
Exploitation requires the `internal-data-acquisition` Cargo feature to be compiled in and requires the orb to accept extension-mode user QR codes, both of which are explicit stated preconditions of this question. Given those preconditions, the exploit requires no privileges, no operator access, and no hardware tampering — only presenting a QR code with attacker-chosen text matching a permissive regex. This is fully deterministic and repeatable: any `parameters` string containing a digit sequence decoding to octal ≥ 10 (decimal ≥ 8) triggers the panic every time.

### Recommendation
Replace the `assert_eq!` with proper validation that returns a `Result`/falls back safely for out-of-range values (`configuration_value > 7`), e.g. reject/clamp in `parse_configuration_value` and propagate an error up through `SweepConfiguration::new` and `focus_sweep::Plan::from` instead of parsing directly into a panic path. Additionally, validate the octal parameter range immediately when parsing the QR code (`SignupMode::parse`/`from_signup_extension`) so malformed configuration never reaches the biometric capture plan.

### Proof of Concept
Unit test to add in `src/plans/biometric_capture/focus_sweep.rs`:
```rust
#[test]
fn parse_configuration_value_out_of_range_does_not_panic() {
    for v in 8u8..=255 {
        let result = std::panic::catch_unwind(|| {
            SweepConfiguration::parse_configuration_value(v)
        });
        assert!(result.is_ok(), "value {v} caused a panic instead of returning an error");
    }
}
```
Integration-level PoC: construct the QR string `"userid:12345678-1234-1234-1234-123456789012:1::2:10::"`, feed through `Data::from_signup_extension`, then `biometric_capture::Plan::from(...)`/`focus_sweep::Plan::from`, and assert that no panic escapes `Plan::from` (e.g. wrap the call in `std::panic::catch_unwind` and assert `Ok`). Currently this reproduces a panic with message `"Focus Sweep configuration value needs to be octal (<=3 bit)!"`.
