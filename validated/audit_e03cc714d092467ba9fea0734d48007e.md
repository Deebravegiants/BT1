### Title
Webhook `shop-domain` (and `topic`/`webhook-id`) header spoofing — HMAC covers only the raw body, not the identity headers - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC of the raw JSON body, then unconditionally trusts the `shop-domain`, `topic`, and `webhook-id` HTTP headers — none of which are covered by that signature — when building the `WebhookMetadata` handed to the app's handler.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
and `HmacValidator.validate_signature` computes the digest strictly over that signable string: [2](#0-1) 

`Registry.process` then does: [3](#0-2) 
using `request.shop`, `request.topic`, and `request.webhook_id`, all of which come directly from HTTP headers rather than from the signed payload: [4](#0-3) 

Contrast this with the OAuth callback flow, where `shop` *is* included in the signed content: [5](#0-4) 

The binding this breaks: `hmac_verified(body) == true` is treated as equivalent to `hmac_verified(shop, topic, webhook_id, body) == true`. In reality only the body is authenticated; the shop/topic/webhook-id headers are unauthenticated attacker-controlled input that flows straight into `WebhookMetadata.shop` and the handler dispatch key.

### Impact Explanation
Any actor able to install the target app on a shop they control (a normal, unprivileged Shopify merchant/developer account — not a privileged internal role) legitimately receives correctly HMAC-signed webhook deliveries for their own shop. Because the signature never covers the `shop-domain` header, that exact signed request can be replayed to the app's webhook endpoint with the `shop-domain` header rewritten to an arbitrary victim shop domain (and/or the `topic`/`webhook-id` headers altered) without invalidating the HMAC check in `HmacValidator.validate`. The application's webhook handler will then execute believing the event body originates from the victim shop, enabling cross-tenant data injection/confusion in any handler logic keyed off `WebhookMetadata#shop` (e.g., writing attacker-controlled order/customer data under the victim shop's identity, or triggering mandatory-topic handlers such as `customers/data_request`/`shop/redact` against the wrong tenant).

### Likelihood Explanation
Moderate-high: the only prerequisite is the ability to install the app on any shop (self-service, no privileged access, no leaked secrets, no TLS interception) and the ability to send an arbitrary HTTP request to the app's public webhook endpoint — both squarely within the "unprivileged internet user" threat model. No knowledge of `api_secret_key` is required because the attacker reuses a genuinely-issued signature rather than forging one.

### Recommendation
Bind the identity fields into the signed content that `Registry.process` trusts: either require the app to independently verify `request.shop` against a known/installed session before dispatching, or extend the verification so that `shop`, `topic`, and `webhook_id` are cryptographically bound to the delivery (e.g., cross-check them against Shopify's registration records / an allow-list of installed shops) rather than trusting the raw headers once the body-only HMAC passes.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; trigger an event so Shopify sends a genuinely signed webhook: headers include `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid sig over raw body>`.
2. Capture the raw body and HMAC header from that delivery.
3. Replay the identical body/HMAC to the app's webhook endpoint, but set `x-shopify-shop-domain: victim.myshopify.com`.
4. `HmacValidator.validate` succeeds (only the body is checked), and `Registry.process` invokes the handler with `WebhookMetadata#shop == "victim.myshopify.com"`, causing the app to process attacker-controlled data as if it belonged to the victim shop.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
