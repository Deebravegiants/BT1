## Analysis

The Nayms report describes a class of bug where a deterministic, non-random object ID can be **front-run** by an unprivileged party, permanently blocking the legitimate object from ever being created at that ID. The core-contracts repo has a direct structural analog in `lockup-factory/src/lib.rs`.

`LockupFactory::create()` derives the lockup contract's account ID **purely and deterministically** from the `owner_account_id` argument, with no per-call randomness, salt, or nonce, and with **no on-chain uniqueness reservation** (unlike `staking-pool-factory`, which at least maintains an `UnorderedSet` and rejects duplicate IDs before dispatching the account-creation promise): [1](#0-0) 

```rust
let byte_slice = env::sha256(owner_account_id.as_ref().as_bytes());
let lockup_account_id =
    format!("{}.{}", hex::encode(&byte_slice[..20]), env::current_account_id());
```

`create()` is a public, `#[payable]` method callable by **any unprivileged account** — there is no `assert_called_by_foundation`-style check as seen in `whitelist/src/lib.rs`: [2](#0-1) 

Because the resulting `lockup_account_id` depends only on the publicly-known `owner_account_id` (e.g., an employee's account name, which is typically known in advance), any unprivileged actor can pre-compute the exact future lockup address for a targeted beneficiary and call `create()` first, occupying that address with attacker-chosen parameters (`lockup_duration`, `vesting_schedule`, `release_duration`) while still setting `owner_account_id` to the real target (this field is not restricted to the caller). This satisfies the "account-binding failure in ... pool-creation ... flows that breaks single-execution or rightful redemption guarantees" category, since the deterministic binding between `owner_account_id` and the lockup address can be squatted by a third party before the legitimate funder (e.g., NEAR Foundation or employer) executes the real grant.

Two consequences follow:
1. **Permanent DoS**: The legitimate funder's later `create()` call for the same `owner_account_id` will fail at `create_account` (NEAR rejects creating an already-existing account), triggering `on_lockup_create`'s failure branch and refunding the deposit — the intended owner can never obtain a lockup contract at the canonical factory-derived address again: [3](#0-2) 
2. **Term-tampering / bypass risk**: Since the attacker fully controls `lockup_duration`, `vesting_schedule`, and `release_duration` when squatting the address (only `owner_account_id` needs to match the real target), if the legitimate funder is unaware the address is occupied and instead sends its funding NEAR directly to the (now pre-existing, attacker-initialized) `lockup_account_id`, the funds are governed by attacker-chosen terms (e.g., no vesting schedule / foundation termination rights, or an unintended short lockup duration) rather than the intended terms, allowing the rightful owner to receive/transfer funds without the intended vesting or termination constraints.

This differs from ordinary NEAR "account name squatting" because the ID is *not* chosen by the funder — it is a fixed, deterministic function of the *beneficiary's* account, so there is no alternative name the funder could pick to route around a squatted address, unlike `staking-pool-factory` where the caller picks an arbitrary `staking_pool_id` prefix and can simply choose another name if theirs is taken. This matches the report's escalation point that a deterministic ID with no on-chain collision protection can be permanently and unavoidably front-run.

### Title
Deterministic Lockup Account ID Derivation Allows Front-Running/Squatting of a Beneficiary's Lockup Address - (File: `lockup-factory/src/lib.rs`)

### Summary
`LockupFactory::create()` computes the lockup contract's account ID deterministically as `sha256(owner_account_id)[..20].<factory_account_id>`, with no reservation/uniqueness check on-chain and no restriction on who may call `create()`. Because the ID depends solely on the publicly-known `owner_account_id`, any unprivileged actor can pre-emptively call `create()` for a targeted beneficiary, permanently occupying the canonical lockup address before the legitimate funder does so, using attacker-chosen lockup/vesting parameters.

### Finding Description
`create()` is public and payable, with no caller restriction beyond a minimum attached deposit: [4](#0-3) . The lockup account ID is derived only from `owner_account_id`, which is attacker-suppliable and need not match the caller: [5](#0-4) . There is no analog to `staking-pool-factory`'s `staking_pool_account_ids: UnorderedSet<AccountId>` reservation check; the only protection against collision is NEAR's native `create_account` failure, which is handled by refunding the *later* caller: [3](#0-2) . Since the derivation uses no caller-specific salt/nonce, the mapping `owner_account_id -> lockup_account_id` is globally fixed and known in advance to anyone.

### Impact Explanation
An unprivileged attacker can permanently prevent a specific employee/beneficiary from ever obtaining a lockup contract via this factory at the canonical, expected address, and/or pre-seed that address with lockup/vesting terms of their choosing (e.g., omitting the vesting schedule / foundation termination clause) while keeping the correct `owner_account_id`. This is an account-binding failure in a pool/lockup-creation flow that breaks the "rightful redemption guarantee" that a `create()` call for a given owner deploys a lockup contract with the funder's intended terms.

### Likelihood Explanation
High for the DoS/squatting variant: it requires only a normal function call with the minimum attached deposit (3.5 NEAR) and knowledge of the target's account ID, which is typically known ahead of time (e.g., published employee/vendor account names). No privileged role or race-condition sophistication beyond simple front-running (submitting the transaction first) is required.

### Recommendation
Bind the lockup account ID derivation to a value that only the legitimate funder can supply/control — e.g., incorporate the funder's `predecessor_account_id`, an explicit nonce, or require the deploying/funding account to co-sign via a two-step commit-reveal, and/or add an on-chain reservation (`UnorderedSet`) analogous to `staking-pool-factory`'s `staking_pool_account_ids` so a duplicate/squatted target can be detected and rejected before deposit is consumed, with clear tx-level failure (and refund) rather than allowing an unrelated party to permanently occupy the deterministic address on behalf of a chosen `owner_account_id`.

### Proof of Concept
1. Attacker observes that `Employer` intends to grant a vesting lockup to `alice.near` via `LockupFactory::create({owner_account_id: "alice.near", ...})`.
2. Attacker computes `lockup_account_id = hex(sha256("alice.near"))[..20] + "." + factory_account_id` (same formula as in `lockup-factory/src/lib.rs:119-121`).
3. Attacker, with no special privilege, calls `create()` on the factory with `owner_account_id: "alice.near"`, attaching the minimum deposit and specifying `vesting_schedule: None`, before `Employer`'s transaction lands.
4. The attacker's transaction succeeds, deploying a lockup contract at the canonical address with `alice.near` as owner but no vesting schedule/foundation termination rights and a small locked balance.
5. `Employer`'s later `create()` call for `alice.near` fails at `create_account` (`on_lockup_create` refund branch is invoked) — `Employer` can never deploy the intended, correctly-configured lockup for `alice.near` at this factory-derived address.

    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }
