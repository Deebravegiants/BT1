### Title
Webhook `X-Shopify-Topic` (and shop domain) headers are not covered by HMAC validation, allowing topic/shop relabeling of a validly-signed webhook body - (File: lib/shopify_api/webhooks/registry.rb)

### Summary
`HmacValidator.validate` only signs and verifies `Request#to_signable_string`, which returns `@raw_body` [1](#0-0) , while `Registry.process` dispatches to a handler chosen by `request.topic` and passes `request.shop` into `WebhookMetadata`, both of which come straight from unauthenticated headers [2](#0-1) . This means the binding `topic_signed_by_hmac == topic_dispatched_by_registry` never actually holds because the topic (and shop) are never part of the signed material.

### Finding Description
The claimed binding, stated explicitly: `HMAC-SHA256(secret, raw_body) == received_hmac` is meant to imply that the entire webhook delivery (topic, shop, body) is authentic. In reality the only equality actually checked is `computed_signature(raw_body) == received_signature` [3](#0-2) ; `topic` and `shop` are read from `@headers` via `shopify_header` with no cryptographic binding to the body or to each other [4](#0-3) [5](#0-4) .

`Registry.process` first calls `HmacValidator.validate(request)`, then looks up `@registry[request.topic]&.handler`, and finally invokes `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))` [2](#0-1) . Because HMAC validation only covers `@raw_body`, an attacker who obtains any genuinely-signed `(raw_body, hmac)` pair for the app's shared `api_secret_key` — for example by installing the app on their own development shop and receiving a real webhook for a low-privilege topic like `orders/create` — can resend that same body/HMAC pair to the victim host app's webhook endpoint with `X-Shopify-Topic` changed to `customers/data_request` and `X-Shopify-Shop-Domain` changed to an arbitrary victim shop. `HmacValidator.validate` still returns `true` because the body is unmodified, and `Registry` dispatches to the `customers/data_request` handler with an attacker-chosen `shop` value in `WebhookMetadata`.

This is consistent with the actual Shopify webhook signing scheme (only the raw body is signed) — it's not something this gem invents, but this gem's `Registry.process`/`Request`/`WebhookMetadata` design does nothing to compensate: it trusts `topic` and `shop` headers as authenticated once HMAC passes, and hands them unchecked to arbitrary host-app handler code. No other guard in this codebase (`ShopValidator`, `JwtPayload`, `Context.setup?`) applies to the webhook path — those are OAuth/session-token concerns, not webhook concerns.

### Impact Explanation
Any topic/shop pair can be forged as long as the attacker can obtain one genuinely-signed body for that shared app secret (trivial: install the app on their own dev shop and trigger any webhook). This lets an attacker cause a host app's mandatory-topic handler (e.g. GDPR `customers/data_request`/`customers/redact`/`shop/redact`, which perform data export or deletion) to fire for an arbitrary attacker-chosen shop, and repeatedly, against arbitrary victims, since the shared `api_secret_key` is not shop-specific. This matches "cross-tenant access" / authentication-bypass-of-topic-authorization impact, though it depends entirely on host-app handler logic trusting `WebhookMetadata#topic`/`#shop` without independent verification (e.g. against a stored subscription/session record).

### Likelihood Explanation
Requires: (1) attacker can install/create their own development shop and register the app to receive any webhook (a normal, unprivileged action), (2) the host app registers a handler for a sensitive topic whose behavior depends on `WebhookMetadata#shop`/`#topic` alone, and (3) the host app does not independently confirm that the reported shop actually has that topic subscribed/is a known installed shop. This is a low-cost, repeatable attack requiring no secrets, matching the threat model's unprivileged attacker.

### Recommendation
This mirrors Shopify's actual signing contract, so a full fix within this gem is limited: the gem should document (and can optionally provide a helper) that `WebhookMetadata#shop` and `#topic` are unauthenticated header values and must be cross-checked by host apps against known installed sessions/subscriptions before performing privileged actions. Where feasible, `Registry.process` could accept an expected-topic/shop allowlist or verify the delivered topic against the app's own subscription records before dispatch, rather than trusting headers unconditionally.

### Proof of Concept
```ruby
# test/webhooks/registry_test.rb (new test)
def test_process_allows_topic_relabeling_of_valid_body
  recorded = []
  handler = TestHelpers::FakeWebhookHandler.new(->(data) { recorded << [data.topic, data.shop] })

  ShopifyAPI::Webhooks::Registry.add_registration(
    topic: "orders/create", path: "path", delivery_method: :http, handler: TestHelpers::FakeWebhookHandler.new(->(_) {}),
  )
  ShopifyAPI::Webhooks::Registry.add_registration(
    topic: "customers/data_request", path: "path", delivery_method: :http, handler: handler,
  )

  raw_body = "{}"
  hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)

  # Attacker's own genuinely-signed low-privilege webhook, relabeled
  forged_headers = {
    "x-shopify-topic" => "customers/data_request",
    "x-shopify-hmac-sha256" => Base64.encode64(hmac),
    "x-shopify-shop-domain" => "victim-shop.myshopify.com",
  }

  ShopifyAPI::Webhooks::Registry.process(
    ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers),
  )

  assert_equal([["customers/data_request", "victim-shop.myshopify.com"]], recorded)
end
```
This demonstrates `HmacValidator.validate` returns `true` for a body signed for one topic/shop, while `Registry.process` dispatches it to a different, sensitive handler with an attacker-chosen shop — proving `topic_signed_by_hmac != topic_dispatched_by_registry`.
