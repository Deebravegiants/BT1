### Title
`validateStarknetAddress` accepts the zero address `0x0`, allowing OmniBridge Starknet withdrawals to permanently burn funds - (File: `packages/intents-sdk/src/lib/validateAddress.ts`)

### Summary
`validateStarknetAddress` only checks hex format (`/^0x[a-fA-F0-9]{1,64}$/`) with no zero-address exclusion, unlike `validateEthAddress` which explicitly blocks `0x000...000` and the burn address `0x000...dead`. An unprivileged caller can set `destinationAddress='0x0'` on an Omni-routed, Starknet-destined withdrawal; `OmniBridge.validateWithdrawal` accepts it, and the `ft_withdraw` intent's `recipient` is encoded as the zero Starknet `OmniAddress`, causing an irrecoverable loss of funds.

### Finding Description
The claimed broken equality is: **intended recipient (a Starknet account the user controls) == encoded `recipient` in the signed `ft_withdraw` intent**. For Starknet destinations this equality can diverge to the zero felt252 address with no owner.

- `validateStarknetAddress` in `packages/intents-sdk/src/lib/validateAddress.ts` (lines 502-504) is `/^0x[a-fA-F0-9]{1,64}$/`, which matches `0x0` (a single hex digit is within `{1,64}`).
- `OmniBridge.validateWithdrawal` (`packages/intents-sdk/src/bridges/omni-bridge/omni-bridge.ts` lines 358-365) calls `validateAddress(args.destinationAddress, assetInfo.blockchain)` and only throws `InvalidDestinationAddressForWithdrawalError` when it returns `false`; for `'0x0'` + `Chains.Starknet` it returns `true`, so validation passes.
- The only other destination check, `compareAddresses` (lines 384-396 of `omni-bridge.ts`), only compares the destination against the bridged token's own contract address (`DestinationAddressMatchesTokenAddressError`) — it does not check against the zero address.
- `createWithdrawalIntents` (lines 283-330) then calls `deriveOmniWithdrawIntentParams` (`packages/intents-sdk/src/bridges/omni-bridge/omni-withdraw-params.ts` lines 52-155), which computes `recipient = omniAddress(params.omniChainKind, destinationAddress)` (line 126) using the unmodified attacker-controlled `destinationAddress`. This `recipient` is placed directly into the `ft_withdraw` intent's `msg.recipient` field by `createWithdrawIntentsPrimitive` (`omni-bridge-utils.ts` lines 29-73).
- Unlike EVM chains, where `validateEthAddress` (lines 105-113 of `validateAddress.ts`) explicitly rejects `0x0000000000000000000000000000000000000000` and the burn address `0x000000000000000000000000000000000000dead`, Starknet has no equivalent zero-address rejection anywhere in `validateAddress.ts`, `compareAddresses.ts`, or `omni-bridge.ts`.

No other guard (`supports()` ordering, `FeeExceedsAmountError`, `getUnderlyingFee`, `assert` sanity checks, or the intents contract's own signature/nonce verification) checks the semantic validity of the destination address against known burn/zero values for Starknet — they only validate fee amounts, asset support, and format.

### Impact Explanation
An attacker (an ordinary user of their own funds, or a value forwarded by an integrator) can cause a legitimately signed `ft_withdraw` intent to carry `recipient = omniAddress(ChainKind.Strk, "0x0")`. Once broadcast and executed by the Omni Bridge/relayer, the withdrawn tokens are sent to the Starknet zero address, which is not a controllable account — funds are permanently lost with no recovery path. This matches the Critical category: "funds delivered to a wrong address/chain/contract with no recovery." It is repeatable for any amount and any Starknet-routed Omni asset.

### Likelihood Explanation
Preconditions: an Omni-routed withdrawal targeting Starknet (`ChainKind.Strk`/`Chains.Starknet`) via `OmniBridge`. No special privilege is needed — a normal SDK caller (or an integrator blindly forwarding a `destinationAddress` string) simply needs to pass `'0x0'` (or any short zero-padded hex like `'0x00'`) as the destination for a Starknet withdrawal. This requires no interaction with a malicious relayer/RPC and no admin access — it's a pure client-side input that passes the SDK's own validation.

### Recommendation
In `validateStarknetAddress` (`packages/intents-sdk/src/lib/validateAddress.ts`), reject the all-zero felt (i.e., where the hex digits, ignoring leading zeros, reduce to `0` — matching the normalization already done in `compareAddresses.ts`'s `normalizeHexAddress`), mirroring the explicit zero/burn-address rejection already implemented for `validateEthAddress`.

// Aptos/Movement/Sui/Starknet addresses are hex field elements: case is not
// significant, and both zero-padded (0x000...01) and short (0x1) forms refer
// to the same address.
function compareHexAddress(a: string, b: string): boolean {
	const normalizedA = normalizeHexAddress(a);
	const normalizedB = normalizeHexAddress(b);
	if (normalizedA === null || normalizedB === null) return false;
	return normalizedA === normalizedB;
}

function normalizeHexAddress(address: string): string | null {
	const withoutPrefix = address.toLowerCase().startsWith("0x")
		? address.slice(2)
		: address;
	if (withoutPrefix.length === 0 || !/^[0-9a-fA-F]+$/.test(withoutPrefix)) {
		return null;
	}
	const withoutLeadingZeros = withoutPrefix.replace(/^0+/, "");
	return withoutLeadingZeros.toLowerCase() || "0";
}
