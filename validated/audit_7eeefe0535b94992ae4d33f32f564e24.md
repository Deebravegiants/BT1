### Title
Webhook shop identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook by validating an HMAC computed only over the raw request body, then unconditionally trusts the `x-shopify-shop-domain` header — which is *not* part of the signed material — as the tenant identity handed to the app's webhook handler. Any actor who can obtain one valid `(body, hmac)` pair signed with the app's secret (e.g. by simply installing the app on their own store and receiving a real webhook) can replay that exact body/HMAC while substituting an arbitrary `shop` header, causing the handler to process attacker-supplied webhook content under a victim shop's identity.

### Finding Description
`Utils::HmacValidator.validate` computes and compares the signature purely from `verifiable_query.to_signable_string`. For webhooks, `Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` value used downstream comes from a completely separate, unauthenticated HTTP header: [2](#0-1) 

`Registry.process` validates the HMAC (which only covers the body) and then immediately constructs the tenant-identifying `WebhookMetadata` using `request.shop`, handing it to the app's registered handler with no further binding check: [3](#0-2) 

This is structurally identical to the M05 bug class: a field that is *acted on* (the shop identity used to route/attribute the webhook) is not the field that is *cryptographically verified* (only the body is verified). The binding that should hold is:
`shop asserted to the handler == shop that the HMAC-secret holder (Shopify) actually generated this payload for`
but the code only proves `body == body Shopify actually sent for *some* shop`, and lets the caller freely choose which shop that body is attributed to.

### Impact Explanation
An attacker who is a legitimate (even free/trial) merchant of the app can install it on their own store and receive one genuine webhook delivery, which is HMAC-valid because the HMAC only signs the JSON body. The attacker can then replay that exact `raw_body` + `hmac` pair to the app's webhook endpoint while setting `x-shopify-shop-domain` (or `shopify-shop-domain`) to a victim shop's domain. `Utils::HmacValidator.validate` still returns `true` (body unchanged), and `Registry.process` dispatches the handler with `WebhookMetadata#shop` set to the victim's domain. Any host application logic that uses `data.shop` to look up/update per-tenant records (a very common and expected usage pattern, as shown in the gem's own webhook documentation) will attribute the attacker's forged event data to the victim tenant — a cross-tenant integrity/confidentiality violation with no access token, `client_secret`, or privileged account required.

### Likelihood Explanation
High. The only prerequisite is being able to install the app on any store (the normal, lowest-privilege interaction with a multi-tenant Shopify app) to capture one legitimate `(body, hmac)` pair, and the ability to send an arbitrary HTTP request with custom headers to the app's public webhook endpoint — both trivially available to an unprivileged internet actor.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the signed material verified against the HMAC, or otherwise cryptographically bind the `shop` value to the payload before it is handed to the handler — do not treat `x-shopify-shop-domain` as trusted merely because the body's HMAC validated.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a webhook (e.g., `orders/create`), capturing the real request: `raw_body = B`, headers include `x-shopify-hmac-sha256: H` (valid for `B` and the app's secret) and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker resends the identical `raw_body: B` and `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`, to the app's webhook controller endpoint.
3. `Utils::HmacValidator.validate` [4](#0-3)  succeeds because it only checks `B` against `H`.
4. `Registry.process` [3](#0-2)  invokes the app's handler with `shop: "victim-shop.myshopify.com"`, causing the app to process attacker-controlled order/webhook data as if it belonged to the victim shop.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
