### Title
Webhook `shop-domain` (and `topic`/`webhook-id`) headers are trusted without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary

### Finding Description
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable payload from the raw request body only: [1](#0-0) 

but exposes `shop`, `topic`, and `webhook_id` as plain accessors read directly from unauthenticated HTTP headers: [2](#0-1) 

`ShopifyAPI::Webhooks::Registry.process` validates the request using only `Utils::HmacValidator.validate(request)` (which, per `to_signable_string`, checks the HMAC of `@raw_body` alone), then unconditionally forwards `request.shop` into the handler: [3](#0-2) 

The identity binding this breaks is:

`shop that produced a valid HMAC over the body` ≠ `shop value the handler trusts and acts on (request.shop)`

Shopify's `client_secret`/`api_secret_key` is a single app-wide secret shared across every shop that installs the app — it is not per-shop. Consequently, any unprivileged internet user who installs the app on their own store (a legitimate, unprivileged action) receives genuinely-signed webhooks (body + HMAC) computed with that same shared secret. That attacker can then replay the exact `(raw_body, hmac)` pair to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and, if desired, `webhook-id`/`topic`) header with a victim shop's domain. `HmacValidator.validate` only re-verifies the untouched `raw_body` against the signature, which still checks out, so `Registry.process` accepts the request and hands `WebhookMetadata.new(..., shop: request.shop, ...)` — now carrying the forged victim shop — to the app's handler.

Many mandatory/no-payload topics (e.g. `app/uninstalled`, `shop/redact`) have minimal or static bodies, making a captured signed payload trivially reusable across "shop-domain" values without needing to know or crack the secret.

### Impact Explanation
This allows a cross-tenant identity confusion: the app-supplied webhook handler executes shop-scoped logic (data deletion/redaction, session invalidation, uninstall cleanup, etc.) attributing the action to an arbitrary victim shop chosen by the attacker, even though the victim shop never sent that event. Depending on what the integrating app does with `data.shop` (per the documented `WebhookMetadata` contract), this can trigger destructive or state-changing operations against a different tenant than the one that actually triggered the webhook — a cross-tenant access/impact matching the required "Critical - cross-tenant access" bar, since the tenant boundary (`shop`) is not cryptographically bound to the authenticated bytes.

### Likelihood Explanation
Likelihood is high for a determined but unprivileged attacker: installing the target app on one's own test/free store is normal, unprivileged behavior; capturing one's own webhook body+HMAC is trivial (it's delivered directly to the attacker's own endpoint); and replaying it with a modified `shop-domain` header requires no cryptographic secret, only network access to the target's public webhook endpoint.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the signed material, or independently bind `request.shop` to a value verified via a signed channel (e.g., cross-check against the shop associated with a specific, previously-registered webhook subscription/session, or require the `shop-domain` header to be part of what's HMAC-verified) before trusting it in `Registry.process`. At minimum, document/enforce that consumers must reconcile `data.shop` against their own session/tenant record before acting, and consider deriving `shop` from a signed claim (e.g., a JWT) rather than an unauthenticated header, matching the mitigation pattern in the referenced report of not trusting inputs that fall outside the cryptographically-checked scope.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a normal, unprivileged action) and receives a legitimate webhook, e.g. `POST /webhooks` with headers `X-Shopify-Topic: app/uninstalled`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid_hmac>`, and body `{}` (or any minimal, topic-generic body).
2. Attacker resends the identical `raw_body` and `X-Shopify-Hmac-Sha256` value to the same app's webhook endpoint, but replaces `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` parses the forged headers; `Utils::HmacValidator.validate(request)` succeeds because it only checks `raw_body` against the (still-matching) HMAC.
4. `ShopifyAPI::Webhooks::Registry.process` calls the registered handler with `WebhookMetadata.new(topic: "app/uninstalled", shop: "victim-shop.myshopify.com", body: {}, ...)`, causing the app to perform `app/uninstalled` cleanup (e.g., deleting stored sessions/tokens) for `victim-shop.myshopify.com` even though that shop never sent this webhook.
