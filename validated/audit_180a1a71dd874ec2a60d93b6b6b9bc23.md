## Title
Relayer fees below `MinimumWithdrawalAmount` can become permanently stuck with no way to recover them - (File: `modules/pallets/relayer/src/withdrawal.rs`)

### Summary
`Pallet::withdraw` in `pallet-ismp-relayer` hard-reverts with `Error::NotEnoughBalance` whenever a relayer's accrued, unclaimed fee balance for a given destination `StateMachine` is below `MinimumWithdrawalAmount` (default `MinWithdrawal` = 10 * 10^18). There is no alternate code path that lets a relayer pull out a sub-threshold balance, mirroring the Rio `scrapeExcessFullWithdrawalETHFromEigenPod` pattern where funds below a fixed minimum can never be swept out.

### Finding Description
`withdraw()` reads the relayer's accumulated fee balance for `(dest_chain, address)` from the `Fees` double map and gates the entire withdrawal on a minimum: [1](#0-0) 

```
let available_amount = Fees::<T>::get(withdrawal_data.dest_chain, address.clone());
if available_amount < Self::min_withdrawal_amount(withdrawal_data.dest_chain).unwrap_or(MinWithdrawal::get()) {
    Err(Error::<T>::NotEnoughBalance)?
}
```

The default floor is defined as a hard-coded 10-token equivalent: [2](#0-1) 

and can be overridden per-`StateMachine` only by privileged `RelayerOrigin` governance via `set_minimum_withdrawal`: [3](#0-2) 

Crucially, when `withdraw()` does succeed, it zeroes the *entire* `Fees` entry unconditionally rather than only debiting the withdrawn amount — so there is no partial-withdraw mechanic either: [4](#0-3) 

Fees only ever grow via `accumulate()`/`accumulate_fee_and_deposit_event()`, which adds to whatever future proofs of delivery are submitted for that specific `(state_machine, address)` pair: [5](#0-4) 

If a relayer's accrued balance for a given destination never crosses the configured minimum — e.g. it stops delivering messages to that low-traffic destination, retires, rotates its delivery address, or the destination integration is deprecated — that balance sits permanently in on-chain storage with no permissionless way to extract it. This is functionally identical to the Rio issue: a fixed minimum-withdrawal gate with no alternate recovery path for the dust left below it.

### Impact Explanation
Any relayer fee balance strictly below `MinimumWithdrawalAmount` for a given destination chain is permanently unreachable by that relayer unless it accumulates additional deliveries on that exact `(dest_chain, address)` pair to cross the threshold. Since `withdraw()` also zeroes the whole entry rather than debiting only the requested amount, there is no way to withdraw "most" of a balance while leaving a small remainder claimable later at will — the entire balance must simultaneously exceed the threshold. This is a genuine freezing-of-funds condition scoped to the relayer reward accounting path explicitly in-scope for this review (fees credited via `pallet-ismp` `IsmpDispatcher`/`FeeMetadata`, tracked per relayer, paid out through this pallet).

### Likelihood Explanation
This triggers under ordinary, permissionless usage — no attacker action is required. Any relayer whose delivery volume to a specific destination is low, or who stops delivering to that destination before crossing the floor (a common operational scenario, e.g. seasonal/low-traffic routes, address rotation, or relayer retirement), is left with fees they can never claim. Governance can raise or lower `MinimumWithdrawalAmount` per chain, but cannot force a below-threshold withdrawal for an individual relayer, and there is no privileged sweep/force-withdraw entry point in this module.

### Recommendation
Remove the hard floor on the withdraw path (or add a governance/permissionless "force withdraw regardless of minimum" call), and/or change `withdraw()` to debit only the amount being withdrawn (`available_amount -= requested`) instead of zeroing the whole `Fees` entry, so relayers are never permanently unable to reach a residual balance.

### Proof of Concept
1. Relayer `R` delivers a handful of low-fee ISMP messages destined for chain `D`, accumulating `Fees::<T>::get(D, R) = 8 * 10^18` (below the default `MinWithdrawal` of `10 * 10^18`).
2. `R` stops delivering further messages to `D` (e.g. that route goes quiet, or `R` shuts down its relayer infra for `D`).
3. `R` calls `withdraw_fees` with `dest_chain = D`; `withdraw()` computes `available_amount = 8e18 < MinWithdrawal (10e18)` and returns `Error::<T>::NotEnoughBalance` at `modules/pallets/relayer/src/withdrawal.rs:118-123`.
4. There is no other call in the pallet that lets `R` claim this balance regardless of the threshold, and `set_minimum_withdrawal` is gated behind `T::RelayerOrigin` (governance), not callable by `R`. The `8 * 10^18` fee balance is permanently stuck in the `Fees` storage map for `R`.

	pub struct MinWithdrawal;

			U256::from(10u128 * 1_000_000_000_000_000_000)
		}
	}
