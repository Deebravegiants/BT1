## Title
Withdraw can permanently revert with an unrecoverable arithmetic panic when `target_orders.calc_pnl_x`/`calc_pnl_y` drift out of sync with real vault reserves due to decimal-rounding, freezing LP redemptions - (`program/src/processor.rs`)

### Summary
The ggAVAX report shows that an ERC4626-style vault can enter a state where a bookkeeping variable (`totalReleasedAssets`) is momentarily inconsistent with the "true" redeemable balance, causing a raw arithmetic subtraction to revert and blocking user redemptions until an external condition (cycle end) resolves the drift. Raydium's AMM has a structurally analogous pattern in `process_withdraw`: pool-internal PnL bookkeeping (`target_orders.calc_pnl_x` / `calc_pnl_y`) is maintained separately from the actual vault token balances and is updated with **unchecked `.unwrap()` subtractions** rather than any tolerant/fallback path.

### Finding Description
`process_withdraw` computes the amount to send out based on `total_pc_without_take_pnl`/`total_coin_without_take_pnl` (derived from actual vault balances minus `need_take_pnl_*`), then re-derives the new "virtual" PnL baseline for `target_orders` using decimal-normalized values and a raw `.unwrap()` subtraction: [1](#0-0) 

Both `x1`/`y1` (via `Calculator::normalize_decimal_v2`) and `pc_amount`/`coin_amount` (converted back via `normalize_decimal_v2` again) pass through repeated integer-division (floor) conversions: [2](#0-1) 

`delta_x`/`delta_y` returned from `calc_take_pnl` are themselves derived from an integer-square-root approximation of the constant-product invariant and further floor-divided PnL-fee ratios: [3](#0-2) 

Because every one of these conversions independently floors/truncates, the sum `normalize_decimal_v2(pc_amount) + delta_x` can, for certain reserve ratios/decimals/amounts, exceed `x1` by a small margin after repeated withdraw/deposit cycles that keep nudging `target_orders.calc_pnl_x`/`calc_pnl_y` away from the true reserve-derived value. When that happens, the `.checked_sub(...).unwrap()` calls at lines 1819-1838 panic, aborting the whole transaction — which also rolls back the token burn and transfers performed earlier in the same instruction (lines up to ~1812) since Solana transactions are atomic. The same unwrap-heavy update pattern is repeated in `process_withdrawpnl`: [4](#0-3) 

There is no fallback (e.g., clamping to the max redeemable amount, as the C4 finding's recommended mitigation suggests) — the code simply panics/reverts, exactly mirroring the `stdError.arithmeticError` behavior described in the ggAVAX report.

### Impact Explanation
If `target_orders.calc_pnl_x`/`calc_pnl_y` drift (due to compounding floor-rounding across `normalize_decimal_v2`/`restore_decimal` conversions and the integer-sqrt-based `calc_take_pnl`) to a point where the subtraction underflows, **every** subsequent `Withdraw` (and `WithdrawPnl`) call on that pool will panic and revert. This is a pool-wide denial of LP withdrawals: liquidity providers cannot redeem their share of the pool, i.e., a freezing of LP funds, until/unless some other external state change (e.g., further swaps altering `total_pc_without_take_pnl`/`total_coin_without_take_pnl` enough to flip the comparison back) incidentally repairs the imbalance — there is no guaranteed recovery path, unlike the ggAVAX case where `rewardsCycleEnd` deterministically resolves the issue.

### Likelihood Explanation
This requires accumulated rounding drift across many deposit/withdraw operations and/or unusual token-decimal/reserve-ratio combinations — the same "hedge case, rare in typical operation" characterization the ggAVAX sponsor and judge gave to the original finding. It is reachable purely through the permissionless `Deposit`/`Withdraw` instructions available to any LP, with no privileged action required, but the probability of hitting the exact underflow boundary in normal operation is low, matching the Medium severity assigned to the analogous C4 finding.

### Recommendation
Replace the raw `.unwrap()` subtractions on `target_orders.calc_pnl_x`/`calc_pnl_y` in `process_withdraw` and `process_withdrawpnl` with saturating or checked arithmetic that clamps to zero (or otherwise gracefully caps the withdrawable/PnL amount) instead of panicking, so a rounding-driven underflow cannot brick withdrawals for the pool's LPs.

### Proof of Concept
Conceptually: repeatedly call `Deposit`/`Withdraw` on a freshly configured pool with decimals/reserve ratios chosen so that `Calculator::normalize_decimal_v2` and `Calculator::restore_decimal` round in opposite directions across cycles (e.g., pc_decimals ≠ coin_decimals with a `sys_decimal_value` that doesn't evenly divide token amounts), progressively drifting `target_orders.calc_pnl_x`/`calc_pnl_y` slightly ahead of the real vault-derived `x1`/`y1`. On a subsequent `Withdraw`, `x1.checked_sub(normalize_decimal_v2(pc_amount,...)).unwrap().checked_sub(U128::from(delta_x)).unwrap()` underflows and panics, reverting the transaction (and the LP token burn/transfer within it), exactly as the ggAVAX PoC demonstrated for `redeemAVAX()`.

    pub fn normalize_decimal(val: u64, native_decimal: u64, sys_decimal_value: u64) -> u64 {
        // e.g., amm.sys_decimal_value is 10**6, native_decimal is 10**9, price is 1.23, this function will convert (1.23*10**9) -> (1.23*10**6)
        //let ret:u64 = val.checked_mul(amm.sys_decimal_value).unwrap().checked_div((10 as u64).pow(native_decimal.into())).unwrap();
        let ret_mut = (U128::from(val))
            .checked_mul(sys_decimal_value.into())
            .unwrap();
        let ret = Self::to_u64(
            ret_mut
                .checked_div(U128::from(10).checked_pow(native_decimal.into()).unwrap())
                .unwrap()
                .as_u128(),
        )
        .unwrap();
        ret
    }

    pub fn restore_decimal(val: U128, native_decimal: u64, sys_decimal_value: u64) -> U128 {
        // e.g., amm.sys_decimal_value is 10**6, native_decimal is 10**9, price is 1.23, this function will convert (1.23*10**6) -> (1.23*10**9)
        // let ret:u64 = val.checked_mul((10 as u64).pow(native_decimal.into())).unwrap().checked_div(amm.sys_decimal_value).unwrap();
        let ret_mut = val
            .checked_mul(U128::from(10).checked_pow(native_decimal.into()).unwrap())
            .unwrap();
        let ret = ret_mut.checked_div(sys_decimal_value.into()).unwrap();
        ret
    }
