### Title
Stellar destination address regex-only validation allows CRC16/version-byte-invalid StrKey to reach a signed withdrawal intent - (File: `packages/intents-sdk/src/lib/validateAddress.ts`)

### Summary
`validateStellarAddress` (line 440-442) only checks the shape `/^G[A-Z0-9]{55}$/` and never decodes/verifies the StrKey CRC16 checksum or version byte, unlike the codebase's own proper StrKey decoder `stellarAddressToBytes` (in `packages/internal-utils/src/utils/stellarAddressToBytes.ts`), which does perform full checksum validation and throws `"invalid checksum"` on malformed input. Because `validateAddress(address, Chains.Stellar)` is the gate used before building/signing a withdrawal intent, a 56-character string that is regex-shaped but cryptographically invalid can pass validation and be carried forward as the `receiver` in a signed withdrawal.

### Finding Description
The broken equality is: **address accepted by `validateAddress` == address that is a cryptographically valid, network-acceptable StrKey**. This equality is false for Stellar in the current code.

- `validateAddress(address, Chains.Stellar)` dispatches to `validateStellarAddress`, defined as:
```
function validateStellarAddress(address: string) {
	return /^G[A-Z0-9]{55}$/.test(address);
}
``` [1](#0-0) 

- This is purely a shape check. It performs no base32 decode, no CRC16 checksum verification, and no version-byte check — all of which the repository already implements correctly elsewhere in `stellarAddressToBytes`, which throws `"invalid checksum"` for a 56-char `G...` string with a wrong CRC16 tail, exactly as demonstrated by the existing test:
```
it("should throw error for invalid checksum", () => {
    expect(() => {
        stellarAddressToBytes(
            "GAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA",
        );
    }).toThrow("invalid checksum");
});
``` [2](#0-1) 

This confirms two divergent validators exist in the codebase for the same address type: one strict (checksum-aware, used for encoding/decoding) and one weak (regex-only, used for the pre-signing gate). An attacker/integrator-forwarded `destinationAddress` such as a 56-char `G`-prefixed string with a deliberately corrupted CRC16 tail satisfies the regex and is treated as "valid" by `validateAddress`.

Per the question's call sequence, this address flows through `HotBridge.validateWithdrawal` → passes `validateAddress` → is used to check `stellar.isTrustlineExists` and ultimately becomes the `receiver` in the `mt_withdraw` intent that gets signed via `buildGaslessWithdrawIntent`. I was not able to directly confirm the exact line-level code of `hot-bridge.ts`'s `validateWithdrawal` function in this session (tool access ended before retrieving that file's full contents), so I cannot state with certainty whether `hot-bridge.ts` performs any *additional* checksum validation (e.g., re-decoding via `stellarAddressToBytes`) before signing that would catch this class of malformed address downstream of `validateAddress`. That is a gap in my verification.

### Impact Explanation
If no downstream checksum re-validation exists in the HOT bridge's Stellar path (which is plausible given `validateAddress` is the documented format gate and the module comment states "A valid format does not guarantee a bridge will accept the address" — implying bridges are expected to rely on this check), a user or integrator-forwarded destination string that is regex-shaped but checksum-invalid could result in a signed `mt_withdraw` intent that debits the user's balance and targets an address the Stellar network would reject or misinterpret, with no automatic recovery — matching the Critical category ("funds delivered to a wrong address/chain/contract with no recovery").

### Likelihood Explanation
Preconditions: HOT-bridged Stellar asset (`assetInfo.blockchain === Chains.Stellar`), and a `destinationAddress` argument controlled by an ordinary caller of `createWithdrawalIntents`. The attacker cost is trivial — constructing a 56-character base32 string with a wrong 2-byte CRC16 tail requires no privileges. The regex-only check is confirmed as written; whether it is actually the last line of defense before signing in `hot-bridge.ts` is unconfirmed due to incomplete file inspection.

### Recommendation
Replace `validateStellarAddress`'s regex-only check with a full StrKey decode using the existing `stellarAddressToBytes` (or equivalent) function, verifying the version byte and CRC16 checksum, and returning `false` (not throwing) on any decode failure — mirroring the pattern already used for Bitcoin, Tron, Litecoin, and Dash addresses in the same file (`validateBtcBase58Address`, `validateTronBase58Address`, etc., which all verify checksums via `sha256`/CRC before accepting).

### Proof of Concept
```ts
import { describe, it, expect } from "vitest";
import { validateAddress } from "../validateAddress";
import { Chains } from "../caip2";
import { stellarAddressToBytes } from "@defuse-protocol/internal-utils";

describe("Stellar address validation gap", () => {
  it("accepts a regex-shaped but checksum-invalid StrKey address", () => {
    const badAddress = "GAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA"; // wrong CRC16

    // Left side of the equality: shape-only validator
    const regexAccepts = validateAddress(badAddress, Chains.Stellar);
    expect(regexAccepts).toBe(true);

    // Right side of the equality: cryptographic StrKey validity
    expect(() => stellarAddressToBytes(badAddress)).toThrow("invalid checksum");

    // Equality broken: regexAccepts === true but address is not a valid StrKey
  });
});
```
