### Title
Webhook `shop` (and `topic`/`api-version`/`webhook-id`) Header Not Covered by HMAC Allows Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
The HMAC used to authenticate incoming webhooks only signs the raw request body; it does not cover the `shopify-shop-domain` header (or `topic`, `api-version`, `webhook-id`). Since the same `api_secret_key` is used to sign every webhook sent to every shop that installs the app, an attacker who controls a shop that has installed the target app can capture a legitimately-signed `body + HMAC` pair from a webhook Shopify sends to their own store, then replay that exact body/HMAC to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` (or `shopify-shop-domain`) header value. `Registry.process` accepts this as valid and hands the attacker-chosen shop identity straight to the host application's webhook handler.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor is read straight from an unauthenticated header, entirely outside the signed material: [2](#0-1) 

`Registry.process` validates only `Utils::HmacValidator.validate(request)`, i.e., only the body's HMAC, and then forwards `request.shop` (and `request.topic`, `request.api_version`, `request.webhook_id`) unchanged into the handler payload: [3](#0-2) 

`HmacValidator.validate_signature` computes the HMAC purely over `verifiable_query.to_signable_string` (the raw body) and compares it with `OpenSSL.secure_compare`: [4](#0-3) 

Because `api_secret_key` is shared across every shop that installs a given app, and only the body bytes are bound to the signature, the binding the library needs to guarantee — `HMAC(body, secret) valid ⇒ shop header == shop the webhook was actually generated for` — does not hold. Before the attacker's request: a legitimate webhook for the attacker's own shop `A` arrives with `(body_A, hmac_A, shop_header=A)`, `hmac_A` verifies. After the attacker's replay: the request `(body_A, hmac_A, shop_header=Victim)` still verifies, because `hmac_A` never depended on the shop header, and `Registry.process` raises no error and dispatches `WebhookMetadata` claiming `shop: "Victim"` to the app's handler. This is the exact bug class from the report: a value used by downstream logic to make a tenant-scoped decision (`totalBorrow`/utilization there, `shop` here) is not included in the value that gates whether the operation is trusted (the interest-skip check there, the HMAC check here).

### Impact Explanation
Host applications built on this gem are documented to key their per-tenant logic off `WebhookMetadata#shop` (session lookup, data mutation, deletion on `app/uninstalled`, etc.), since that is the only shop identity the gem exposes for a webhook. An attacker who onboards their own store to the target app can forge webhooks that Registry.process will accept as authentic for any other merchant's `shop` domain, letting them trigger the app's webhook handler logic under an arbitrary victim tenant identity — a cross-tenant access vulnerability with no dependency on any credential belonging to the victim.

### Likelihood Explanation
Any unprivileged internet user can install the target Shopify app on their own free/dev store, which is enough to receive genuine webhooks signed with the app's shared `api_secret_key`. Capturing one `(body, hmac)` pair from a webhook sent to their own store and replaying it with a modified `shop-domain` header requires no special access, no leaked secrets, and no privileged account — only normal use of a public HTTP endpoint the host app exposes to receive webhooks.

### Recommendation
Bind the shop identity (and topic/webhook id) into the value that is HMAC-verified, or otherwise cross-check `request.shop` against a shop the host app expects/has a stored session for before trusting it. At minimum, `to_signable_string` should incorporate the shop domain (and other header fields used downstream) so that a valid HMAC can only be produced by Shopify for the exact `(shop, body)` pair originally signed, closing the binding gap between "HMAC verified" and "shop trusted."

### Proof of Concept
1. Attacker creates/owns Dev Shop `attacker.myshopify.com` and installs the target app; Shopify sends a legitimate webhook, e.g. `orders/create`, to the app's endpoint with headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: H`, and body `B`.
2. Attacker records `(B, H)`.
3. Attacker sends a new HTTP request to the same app webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H` (unchanged), but `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)` which succeeds (only `B` and `H` are checked), then dispatches `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` to the host app's handler, which now executes tenant-scoped logic believing the event originated from `victim-shop.myshopify.com`.
