### Title
Webhook Shop-Domain Header Is Not Bound to the HMAC Signature, Enabling Cross-Tenant Webhook Spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature only over the raw request body, while the `shop` value used to attribute the webhook to a merchant tenant is read from an unauthenticated HTTP header. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then trusts that unauthenticated `shop` value to build `WebhookMetadata`, breaking the intended binding `shop-that-was-cryptographically-verified == shop-the-app-acts-on`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) . The `shop` accessor, however, is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic protection: [2](#0-1) .

`Registry.process` validates the HMAC using `Utils::HmacValidator.validate(request)`, which calls `verifiable_query.to_signable_string` (i.e., the body only) and compares it against the HMAC computed with the app's `api_secret_key`: [3](#0-2) . Once that check passes, `process` immediately constructs `WebhookMetadata` using `request.shop` — the unauthenticated header value — without any further verification that this shop actually matches the tenant that produced the signed body: [4](#0-3) .

This is the same bug class as the Redstone oracle report: a value that is *acted upon* (the `shop` used to attribute/route the webhook to a tenant) is not covered by the verification mechanism (the HMAC), so the two can be decoupled. Concretely: the equality that should hold is `hmac_verified_shop == request.shop`, but the gem only guarantees `hmac_verified_body == raw_body`; `shop` is never part of the signed content.

By contrast, `ShopifyAPI::Auth::Oauth::AuthQuery#to_signable_string` deliberately includes `shop` in the HMAC-covered parameter set [5](#0-4) , confirming that the library authors do consider `shop` a security-relevant field that should normally be bound by the HMAC — but this binding was omitted for the webhook `Request` class.

### Impact Explanation
An attacker who can deliver (or replay) any single request with a valid `(raw_body, hmac)` pair for the target app — trivially obtainable by installing the app on a shop the attacker controls and capturing one genuine webhook delivery, since Shopify computes the HMAC over the body using the app's shared `api_secret_key` and sends it in the `x-shopify-hmac-sha256` header — can resend that exact `(raw_body, hmac)` pair to the app's public webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header value. `HmacValidator.validate` will still pass (it never looks at the shop header), and `Registry.process` will hand the handler a `WebhookMetadata` claiming the event belongs to any shop the attacker names. Any host application that uses `data.shop` from `WebhookMetadata` to look up/update per-tenant records (the documented and expected usage pattern for `ShopifyAPI::Webhooks::WebhookHandler#handle`) will attribute attacker-controlled webhook data to a victim tenant — i.e., cross-tenant access/data corruption without needing the victim's or the app's credentials.

### Likelihood Explanation
The webhook endpoint is necessarily internet-facing (Shopify must be able to POST to it), so no privileged network position is required. The only prerequisite is one genuine webhook delivery under the attacker's own control (e.g., installing the free/dev-store version of the target app and triggering any webhook topic), which is available to any unprivileged internet user. No `api_secret_key`, access token, or TLS interception is needed — the attacker uses a legitimately-issued HMAC/body pair and only forges the unauthenticated header.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) values into the signed content, or otherwise independently verify that the header-derived `shop` matches a shop that is actually expected to be sending this specific signed payload (e.g., by having `Registry.process` require the caller to supply/verify the expected shop, or by including these headers as part of the HMAC computation as Shopify's other adapters do for `AuthQuery`). At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must not be trusted for tenant attribution without additional verification.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (a shop they control) and triggers any webhook topic the app subscribes to (e.g. `app/uninstalled`).
2. Attacker captures the resulting HTTP POST that Shopify sends to the app's public webhook endpoint, noting the raw body `B` and the valid `x-shopify-hmac-sha256` header `H` (computed by Shopify over `B` using the app's `api_secret_key`).
3. Attacker resends a POST to the same public webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H` (unchanged, still valid), but with `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` accepts the request (all required headers present), `HmacValidator.validate` succeeds because it only checks `B` against `H` (`lib/shopify_api/utils/hmac_validator.rb:26-31`, `lib/shopify_api/webhooks/request.rb:35-38`).
5. `Registry.process` builds `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` (`lib/shopify_api/webhooks/registry.rb:188-199`) and invokes the app's handler, which processes/persists data as belonging to `victim-shop.myshopify.com` even though the actual signed payload originated from the attacker's own shop.
