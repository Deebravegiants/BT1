## Title
Replayable off-chain approval in `transfer_from` due to stale nonce sourced from account sequence number that `transfer_from` never advances - (File: aptos-move/move-examples/fungible_asset/stablecoin/sources/usdk.move)

### Summary
`usdk::transfer_from` implements an ERC20-`permit`-style delegated transfer: an owner signs an off-chain `Approval{owner, to, nonce, chain_id, spender, amount}` message, and any `spender` can submit it on-chain to move funds out of `owner`'s primary fungible store. The `nonce` field is populated with `account::get_sequence_number(from)` [1](#0-0) , which is exactly the anti-replay pattern the original bug report recommended ("nonce uint mapping for senders"). However, this module never increments or otherwise consumes `from`'s account sequence number as part of `transfer_from` — that counter is only advanced by the Aptos VM prologue/epilogue when `from` itself is the *sender* of a transaction [2](#0-1) . Since `transfer_from` is invoked with `spender` as the transaction sender (not `from`), `from`'s sequence number stays constant across arbitrarily many `transfer_from` calls, so the "nonce" embedded in the signed `Approval` never changes and a single signature can be replayed indefinitely.

### Finding Description
The custody invariant that the external report reduces to is: *a signed authorization to move value must be single-use; the same `(request, message, signature)` tuple must not be redeemable more than once.* The report's fix was to bind consumption of a nonce mapping to the redemption path.

In `usdk.move`, `transfer_from` builds the expected challenge as:
```
let expected_message = Approval {
    owner: from,
    to: to,
    nonce: account::get_sequence_number(from),
    chain_id: chain_id::get(),
    spender: signer::address_of(spender),
    amount,
};
account::verify_signed_message(from, from_account_scheme, from_public_key, proof, expected_message);
``` [3](#0-2) 

`account::get_sequence_number` simply reads the `sequence_number` field of the `Account` resource at `from` [2](#0-1) ; that field is only mutated by the VM's own transaction-processing epilogue when `from` is the transaction's sender/signer. Because `transfer_from` is called by `spender`'s transaction, and never mutates `from`'s `Account` resource, the value read as `nonce` is identical on every call unless `from` independently submits an unrelated transaction of its own. `verify_signed_message` only checks that `proof` is a valid signature over `expected_message` under `from_public_key`/`from_account_scheme` (matching `from`'s registered auth key) — it does not perform any additional single-use bookkeeping (no consumed-nonce table, no burn of the challenge).

Consequently, once an owner signs one `Approval` for a given `(to, spender, amount)`, that exact `proof` bytes remain valid for `transfer_from` forever (until `from`'s real sequence number happens to change for an unrelated reason), and `spender` can call `transfer_from` with the identical `proof` repeatedly, each time draining `amount` more from `from`'s primary fungible store into `to`, until the store's balance is exhausted or `is_frozen`/pause halts it. This is the direct Aptos-native analog of the CommunityRound `reserve()` replay: the "nonce" field exists syntactically but is never advanced by the redemption code path, so it fails to prevent replay in practice.

### Impact Explanation
This is a custody-grade impact: unauthorized, repeated withdrawal of fungible-asset balance from an unprivileged victim's (`from`'s) primary store, moving supply to an attacker-chosen `to` without further authorization from the owner. A single off-chain-signed approval — e.g. one intended to authorize a one-time payment of X tokens — can be resubmitted by the `spender` an unbounded number of times, draining far more than the owner intended (up to their full balance), which is theft of custodied fungible-asset value with no privileged/admin assumption required (the attacker is simply the `spender` named in the original valid approval, an ordinary counterparty).

### Likelihood Explanation
High likelihood if this pattern is deployed as-is: the vulnerable code path (`transfer_from`) is a public, non-entry function intended to be called by any spender holding a validly-signed approval; there is no additional gating. Any legitimate use of the approve/transfer_from flow (e.g., a marketplace or subscription spender given a signed approval once) is directly exploitable by simply resubmitting the same call. Note: this file lives under `aptos-move/move-examples/...`, i.e., it is example/reference code rather than a `aptos_framework`-published production module; the same anti-pattern would carry identical impact if copied into a real deployed stablecoin/spender integration built from this example, which is a stated purpose of the `move-examples` stablecoin template.

### Recommendation
- Maintain an explicit, monotonically-incrementing per-owner nonce (or a consumed-approval hash set) stored in module state (e.g., a `Table<address, u64>` or `Table<vector<u8>, bool>` keyed by the approval hash), incremented/marked at the top of `transfer_from` *before* executing the transfer, rather than reusing `account::get_sequence_number(from)`.
- Alternatively, bind the approval to a single-use, module-managed nonce that is explicitly consumed (moved out of storage or incremented) as part of `transfer_from`, and reject any `proof` whose `nonce` does not match the currently stored value.
- Add an expiration/deadline field to `Approval` to bound the window of validity as defense in depth.

### Proof of Concept
1. `owner` signs `Approval { owner: from, to: attacker_relay, nonce: N, chain_id: C, spender: attacker, amount: A }` (with `N = account::get_sequence_number(from)` at signing time) and hands the `proof` bytes to `attacker` to authorize a single transfer of `A` tokens.
2. `attacker` submits `usdk::transfer_from(attacker_signer, proof, from, scheme, from_pk, attacker_relay, A)`. `account::get_sequence_number(from)` still equals `N` (unchanged, since `from` did not submit a transaction), so `verify_signed_message` succeeds and `A` tokens move from `from` to `attacker_relay`.
3. `attacker` repeats step 2 with the identical `proof` bytes any number of times. Each call re-derives the same `expected_message` (since `from`'s sequence number is still `N`) and again passes verification, transferring another `A` tokens each time — with no additional signature from `owner` — until `from`'s balance is exhausted.
