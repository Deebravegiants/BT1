### Title
Non-existent/EOA `to` address in incoming message delivery is silently treated as successful, permanently marking undeliverable messages as delivered - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.dispatchIncoming` delivers an incoming request by writing a receipt for the request commitment and then issuing a low-level call to the destination module's `onAccept`. Per EVM semantics, a low-level `call` to an address with no code returns `success = true`, identical to the bug class described in the referenced report (staticcall/call returning `true` for non-existent accounts). Because the host's only failure-handling path is "if the call fails, delete the receipt and return without reverting," a request addressed to an EOA or any address without deployed code is treated as a **successful** delivery: the receipt is written and stays written, even though no application logic ever executed.

### Finding Description
The delivery flow is:
1. A relayer submits `HandlerV2.handlePostRequests`/`handleGetResponses` with a proof.
2. After proof verification, the handler calls `host.dispatchIncoming(request, _msgSender())`.
3. `EvmHost.dispatchIncoming` writes the receipt for the request's commitment, then low-level calls `IApp(to).onAccept(IncomingPostRequest(request, relayer))`. Only if that call *fails* does the host delete the receipt and continue without reverting. [1](#0-0) 

Since a `call` to a non-existent contract or EOA address always returns `success = true` by EVM design, `to` (which is decoded directly from the untrusted, relayer-submitted request body/route and is not validated for code existence before the call) never triggers the failure branch. The commitment receipt is therefore permanently marked as delivered regardless of whether the destination app actually exists or ran any logic.

This is the same root-cause class as the referenced report: a low-level call's `true` result is used as proof that a "real" recipient processed the payload, without a preceding `extcodesize`/`code.length` check. Notably, the codebase does apply this defensive pattern elsewhere — e.g. `CallDispatcher.dispatch` explicitly checks `extcodesize(to) == 0` and reverts with `NotContract` before making the call [2](#0-1) , and `EvmHost.updateHostParamsInternal` checks `.code.length == 0` for `hostManager`, `handler`, and `consensusClient` before accepting them [3](#0-2)  — but the same guard is absent on the per-message `to` target in the incoming-request delivery path.

### Impact Explanation
A request routed to a `to` address that has no code (a miskeyed address, a not-yet-deployed proxy, a CREATE2 address computed for a contract that was never deployed, or simply an EOA) is recorded as delivered on the destination `EvmHost` even though the intended application (e.g. a token-bridge mint, an intent fill callback, or any `IIsmpModule` business logic) never ran. Because receipts gate re-delivery, this is a **one-shot, unrecoverable failure**: the message can never be redelivered once its receipt exists, so any value or state transition contingent on that message (minted tokens, released escrow, filled intent) is permanently lost or never occurs — a route that is unable to deliver messages and a form of forged/false delivery confirmation.

### Likelihood Explanation
Reachable from a single relayed request: any relayer can submit a valid, proven message whose destination module address happens to have no code (this can occur accidentally through misconfiguration on the source-chain dispatcher, use of a not-yet-deployed counterpart address, or a bridged app that is deployed later than expected), or it can be deliberately targeted by a malicious actor crafting a source-chain dispatch to a code-less address to grief a legitimate cross-chain flow. No privileged role is required to trigger the condition — only a normally-permissioned relay of a message whose `to` field lacks code.

### Recommendation
In `EvmHost.dispatchIncoming` (and the equivalent get-response delivery path), check `to.code.length == 0` (or `extcodesize`) before writing the receipt and issuing the low-level call to `onAccept`/`onGetResponse`, mirroring the existing pattern used in `CallDispatcher.dispatch` and `EvmHost.updateHostParamsInternal`. If the destination has no code, treat the delivery the same as any other failure (delete/never-write the receipt, allow retry) rather than recording success.

### Proof of Concept
1. On the source chain, dispatch (or induce dispatch of) a cross-chain request whose `to` field encodes an address with no deployed bytecode on the destination EVM chain (an EOA, or a precomputed contract address for a contract not yet deployed).
2. A relayer submits the proof through `HandlerV2.handlePostRequests` on the destination `EvmHost`.
3. `dispatchIncoming` writes the commitment receipt and low-level calls `to.onAccept(...)`; since `to` has no code, the call returns `success = true` with empty returndata, and the receipt remains recorded as a successful delivery.
4. The intended application logic (e.g., minting bridged tokens or firing an intent-fill callback) never runs, and because a receipt now exists for that commitment, no relayer can ever redeliver the same message to a corrected/deployed destination — the associated value transfer is permanently stuck.
