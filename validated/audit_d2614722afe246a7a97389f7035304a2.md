## Front-Running / Sandwich Attack Due to Missing Slippage Protection in `bonding_curve_launchpad::swap`

### Title
Unprotected AMM swaps allow front-running/sandwich attacks that redirect swap value to attackers - (File: aptos-move/move-examples/bonding_curve_launchpad/sources/bonding_curve_launchpad.move, aptos-move/move-examples/bonding_curve_launchpad/sources/liquidity_pairs.move)

### Summary
The `bonding_curve_launchpad` example module implements an on-chain AMM (constant-product) swap between APT and a launched fungible asset. The public entry point `swap` and its underlying implementations `swap_fa_to_apt`/`swap_apt_to_fa` accept only an `amount_in` and compute the output amount from current on-chain reserves with no caller-supplied minimum-output (slippage) parameter. This is the exact bug class described in the external report: a price-determining transaction can be observed in the mempool and front-run to move the price against the victim before their trade executes, extracting value that should have gone to the swapper.

### Finding Description
The entry function `swap` takes `amount_in` but no minimum acceptable output: [1](#0-0) 

Both swap directions call `get_amount_out`, which derives the output purely from the pair's current, attacker-observable and attacker-influenceable reserves: [2](#0-1) 

`swap_fa_to_apt` and `swap_apt_to_fa` then execute the transfer unconditionally based on that computed amount, without any check that the amount received meets a caller-specified floor: [3](#0-2) [4](#0-3) 

Because the `LiquidityPair`'s reserves (`fa_reserves`, `apt_reserves`) are mutable, on-chain, and read at execution time, any observer of the mempool (or of the transaction being resubmitted with higher gas/priority) can:
1. See a pending `swap` transaction with `amount_in`.
2. Submit their own swap in the same direction ahead of it to shift `fa_reserves`/`apt_reserves` unfavorably for the victim.
3. Let the victim's swap execute at the worse price, extracting the difference.
4. Optionally submit a reverse trade immediately after to complete a sandwich and lock in the profit.

This directly moves value that should accrue to the swapper to the attacker instead — corrupting the expected custody outcome of the swap (the swapper receives less FA/APT than the fair-price quote implied when they submitted the transaction), which mirrors the "Purchase of nomins/havvens is vulnerable to front-running" report: an oracle/attacker changing price-determining state ahead of a pending purchase to disadvantage the user.

### Impact Explanation
Every swap through `bonding_curve_launchpad::swap` (both FA→APT and APT→FA, including the initial creator swap during `create_fa_pair`) is exposed. An attacker (a validator, MEV searcher, or anyone able to front-run) can systematically extract value from swappers on every trade, with no cap on the amount that can be siphoned per trade beyond the AMM's price-impact curve. Since this is a live custody flow moving both APT and fungible-asset value between user primary stores and the pool's `FungibleStore`, this satisfies the "moves value to the wrong holder" custody-corruption criterion. Given the AMM handles APT (native token) directly via `aptos_account::transfer`, the impact can be significant depending on trade sizes and reserve depth.

### Likelihood Explanation
Likelihood is high: front-running/sandwiching AMMs with no slippage protection is a well-known, low-cost, and easily automatable attack requiring no special privilege — any address able to observe the mempool and submit a transaction with equal or higher priority can execute it. No governance, admin, or oracle trust assumption is required (unlike the original report's oracle-owner scenario), making this a purely permissionless/unprivileged exploit path.

### Recommendation
Add a caller-supplied minimum-output (or maximum-input) parameter to `swap`, `swap_fa_to_apt`, and `swap_apt_to_fa`, and assert that the computed `apt_gained`/`fa_gained` (or `apt_given`/`fa_given`) meets or is bounded by that value before executing the transfer, aborting otherwise. This mirrors the standard AMM slippage-protection pattern and directly addresses the front-running root cause identified in the external report by giving users a way to bound acceptable execution price.

### Proof of Concept
1. Attacker monitors the mempool for a pending `bonding_curve_launchpad::swap(account, name, symbol, false, amount_in)` (APT→FA) transaction from a victim.
2. Attacker submits their own `swap(attacker, name, symbol, false, large_amount_in)` with higher gas priority, which is processed first by `swap_apt_to_fa`, increasing `apt_reserves` and decreasing `fa_reserves` (see `liquidity_pairs.move` lines 277-325), shifting the price against the victim.
3. Victim's original transaction executes via the same `get_amount_out` (`liquidity_pairs.move` lines 91-112) against the now-worse reserves, receiving materially less FA than expected when they signed the transaction, with no on-chain check to prevent or detect this (no minimum-output parameter exists anywhere in the call path).
4. Attacker submits a follow-up `swap(attacker, name, symbol, true, ...)` (FA→APT) to realize the extracted value, completing the sandwich.

        };

    public fun get_amount_out(
        fa_reserves: u128,
        apt_reserves: u128,
        swap_to_apt: bool,
        amount_in: u64
    ): (u64, u64, u128, u128) {
        if (swap_to_apt) {
            let divisor = fa_reserves + (amount_in as u128);
            let apt_gained = (math128::mul_div(apt_reserves, (amount_in as u128), divisor) as u64);
            let fa_updated_reserves = fa_reserves + (amount_in as u128);
            let apt_updated_reserves = apt_reserves - (apt_gained as u128);
            assert!(apt_gained > 0, ELIQUIDITY_PAIR_SWAP_AMOUNTOUT_INSIGNIFICANT);
            (amount_in, apt_gained, fa_updated_reserves, apt_updated_reserves)
        } else {
            let divisor = apt_reserves + (amount_in as u128);
            let fa_gained = (math128::mul_div(fa_reserves, (amount_in as u128), divisor) as u64);
            let fa_updated_reserves = fa_reserves - (fa_gained as u128);
            let apt_updated_reserves = apt_reserves + (amount_in as u128);
            assert!(fa_gained > 0, ELIQUIDITY_PAIR_SWAP_AMOUNTOUT_INSIGNIFICANT);
            (fa_gained, amount_in, fa_updated_reserves, apt_updated_reserves)
        }
    }

    /// Facilitate swapping between a given FA to APT.
    public(friend) fun swap_fa_to_apt(
        name: String,
        symbol: String,
        transfer_ref: &TransferRef,
        swapper_account: &signer,
        fa_object_metadata: Object<Metadata>,
        amount_in: u64
    ) acquires Pairs, LiquidityPair {
        // Verify the liquidity pair exists and is enabled for trading.
        assert_liquidity_pair_exists(name, symbol);
        let liquidity_pair = borrow_global_mut<LiquidityPair>(get_pair_obj_address(name, symbol));
        assert!(liquidity_pair.is_enabled, ELIQUIDITY_PAIR_DISABLED);
        // Determine the amount received of APT, when given swapper-supplied amount_in of FA.
        let (fa_given, apt_gained, fa_updated_reserves, apt_updated_reserves) = get_amount_out(
            liquidity_pair.fa_reserves,
            liquidity_pair.apt_reserves,
            true,
            amount_in
        );
        // Verify the swapper holds the FA.
        let swapper_address = signer::address_of(swapper_account);
        let does_primary_store_exist_for_swapper = primary_fungible_store::primary_store_exists(
            swapper_address,
            fa_object_metadata
        );
        assert!(does_primary_store_exist_for_swapper, EFA_PRIMARY_STORE_DOES_NOT_EXIST);
        // Perform the swap.
        // Swapper sends FA to the liquidity pair object. The liquidity pair object sends APT to the swapper, in return.
        let liquidity_pair_signer = object::generate_signer_for_extending(&liquidity_pair.extend_ref);
        let from_swapper_store = primary_fungible_store::ensure_primary_store_exists(
            swapper_address,
            fungible_asset::transfer_ref_metadata(transfer_ref)
        );
        fungible_asset::transfer_with_ref(transfer_ref, from_swapper_store, liquidity_pair.fa_store, fa_given);
        aptos_account::transfer(&liquidity_pair_signer, swapper_address, apt_gained);
        // Record state changes to the liquidity pair's reserves, and emit changes as events.
        let former_fa_reserves = liquidity_pair.fa_reserves;
        let former_apt_reserves = liquidity_pair.apt_reserves;
        liquidity_pair.fa_reserves = fa_updated_reserves;
        liquidity_pair.apt_reserves = apt_updated_reserves;
        event::emit(
            LiquidityPairReservesUpdated {
                former_fa_reserves,
                former_apt_reserves,
                new_fa_reserves: fa_updated_reserves,
                new_apt_reserves: apt_updated_reserves
            }
        );
        event::emit(
            LiquidityPairSwap {
                is_fa_else_apt: false,
                gained: (apt_gained as u128),
                swapper_address
            }
        );
    }

    /// Facilitate swapping between APT to a given FA.
    public(friend) fun swap_apt_to_fa(
        name: String,
        symbol: String,
        transfer_ref: &TransferRef,
        swapper_account: &signer,
        fa_object_metadata: Object<Metadata>,
        amount_in: u64
    ) acquires Pairs, LiquidityPair {
        // Verify the liquidity pair exists and is enabled for trading.
        assert_liquidity_pair_exists(name, symbol);
        let liquidity_pair = borrow_global_mut<LiquidityPair>(get_pair_obj_address(name, symbol));
        assert!(liquidity_pair.is_enabled, ELIQUIDITY_PAIR_DISABLED);
        // Determine the amount received of FA, when given swapper-supplied amount_in of APT.
        let (fa_gained, apt_given, fa_updated_reserves, apt_updated_reserves) = get_amount_out(
            liquidity_pair.fa_reserves,
            liquidity_pair.apt_reserves,
            false,
            amount_in
        );
        // Perform the swap.
        // Swapper sends APT to the liquidity pair object. The liquidity pair object sends FA to the swapper, in return.
        // Requires the liquidity pair object's address, which is retrieved using the stored extend_ref.
        let swapper_address = signer::address_of(swapper_account);
        let liquidity_pair_address = object::address_from_extend_ref(&liquidity_pair.extend_ref);
        let to_swapper_store = primary_fungible_store::ensure_primary_store_exists(
            swapper_address,
            fungible_asset::transfer_ref_metadata(transfer_ref)
        );
        aptos_account::transfer(swapper_account, liquidity_pair_address, apt_given);
        fungible_asset::transfer_with_ref(transfer_ref, liquidity_pair.fa_store, to_swapper_store, fa_gained);
        // Record state changes to the liquidity pair's reserves, and emit changes as events.
        let former_fa_reserves = liquidity_pair.fa_reserves;
        let former_apt_reserves = liquidity_pair.apt_reserves;
        liquidity_pair.fa_reserves = fa_updated_reserves;
        liquidity_pair.apt_reserves = apt_updated_reserves;
        event::emit(
            LiquidityPairReservesUpdated {
                former_fa_reserves,
                former_apt_reserves,
                new_fa_reserves: fa_updated_reserves,
                new_apt_reserves: apt_updated_reserves
            }
        );
        event::emit(
            LiquidityPairSwap {
                is_fa_else_apt: true,
                gained: (fa_gained as u128),
                swapper_address
            }
        );
        // Check for graduation requirements. The APT reserves must be above the pre-defined
        // threshold to allow for graduation.
        if (liquidity_pair.is_enabled && apt_updated_reserves > APT_LIQUIDITY_THRESHOLD) {
            graduate(liquidity_pair, fa_object_metadata, transfer_ref, apt_updated_reserves, fa_updated_reserves);
        }
    }
