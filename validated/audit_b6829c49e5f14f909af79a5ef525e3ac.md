## Analog Found

### Title
Truncating ERC20→local decimal conversion in `on_accept` silently destroys sub-lot-size value on inbound HyperFungibleToken transfers - (File: `modules/pallets/hyper-fungible-token/src/impls.rs`, `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
The reported bug is a granularity mismatch: `liquidateFrom` checks that an amount is a multiple of `lotSize`, but downstream trading paths (`matchOrders`, AMM) actually require multiples of the coarser `tradingLotSize`, so a liquidated amount can leave a user with an un-tradable, stuck remainder. The same class of bug — an amount whose real-world granularity is not respected by a lossy scale conversion applied elsewhere in the pipeline — exists in the `pallet-hyper-fungible-token` bridge, where inbound ERC20 amounts are converted to the local asset's decimal precision by truncating integer division, and the truncated remainder is neither credited nor refunded.

### Finding Description
`convert_to_balance` scales an ERC20 `U256` amount down to local balance precision via integer division: [1](#0-0) 

This is invoked in `on_accept` when a `Send` message arrives from a peer EVM contract: [2](#0-1) 

The outbound path (`send` on the substrate side) is lossless because it only ever *multiplies up* from local units to ERC20 units via `convert_to_erc20`: [3](#0-2) 

However, the peer EVM contract (`HyperFungibleToken`/`WrappedHyperFungibleToken`) is a separate, permissionlessly-callable contract whose users can burn/escrow and dispatch **any raw ERC20 amount**, not necessarily one that is an exact multiple of `10^(erc_decimals - local_decimals)` (the implicit "lot size" imposed by the local chain's asset precision, e.g. 6 or 12 decimals vs. 18-decimal ERC20). Just as `liquidateFrom` only checks divisibility by `lotSize` while `matchOrders`/AMM enforce the coarser `tradingLotSize`, this pallet has no on-chain check that the inbound `message.amount` is a whole multiple of the local decimal step. When it isn't, `convert_to_balance`'s division floors the result, and the sub-unit remainder (the "lot dust") is simply dropped: it is never minted/transferred to the beneficiary in `on_accept`, and it is not accounted for in `TokenReceived`'s emitted `amount`.

`on_timeout` has the identical unchecked conversion for refunds: [4](#0-3) 

### Impact Explanation
Because the escrow/burn on the source EVM chain locks the *full* raw ERC20 amount (verified by the `HyperFungibleToken.sol` contract, not shown in this pallet), while the destination pallet only mints/releases the floor-divided amount, any remainder below one local-asset unit's ERC20-equivalent is permanently lost — burned or escrowed on one side of the bridge with no corresponding credit on the other, and no path to reclaim it. This is a direct, unbacked-mint/permanent-value-loss condition reachable by any unprivileged sender who dispatches a message with a non-lot-aligned amount (e.g., due to fee deductions, off-by-one calculations, or intentionally crafted dust amounts across many messages to accumulate loss).

### Likelihood Explanation
Any user or automated contract dispatching a `HyperFungibleToken` transfer whose ERC20 amount is not perfectly divisible by `10^(erc_decimals - local_decimals)` triggers this silently — no explicit adversarial setup is required, only a mismatch between the token's 18-decimal ERC20 representation and the local asset's typically-lower decimal precision (a very common real-world configuration, e.g., 18-decimal ERC20 vs 6/10/12-decimal local assets). The pallet's own documentation acknowledges arbitrary decimal disparities are expected (`ErcDecimalsBelowLocal` guard only prevents `erc_decimals < local_decimals`, not the truncation itself), making this readily triggerable in production configurations.

### Recommendation
Either (a) require the pallet to remint/refund the truncated remainder back to the sender/beneficiary rather than silently discarding it (analogous to "restrict amounts to multiples of the coarser granularity" or "provide a method to reclaim leftover dust" suggested in the original report), or (b) reject inbound messages via `on_accept`/`on_timeout` whose ERC20 amount is not an exact multiple of `10^(erc_decimals - local_decimals)`, forcing correctness at message-construction time on the EVM side rather than silently truncating value on delivery.

### Proof of Concept
1. Register a token pair where `erc_decimals = 18` and local asset `decimals = 6` (a realistic, permitted configuration since `register_token` only enforces `config.decimals >= local_decimals` from the substrate side, and remote EVM-originated sends are not similarly bounded).
2. From the paired `HyperFungibleToken` EVM contract, dispatch a `Send` message with `amount = 1_000_000_000_000` wei plus `1` extra wei (i.e., not a multiple of `10^12`), burning/escrowing the full amount on the EVM side.
3. On `on_accept`, `convert_to_balance` computes `value / 10^12`, flooring away the extra `1` wei permanently — `TokenReceived` mints/releases only the floored amount to the beneficiary.
4. The 1-wei-equivalent value is now burned/escrowed on the source chain but never credited anywhere on the destination chain, and no mechanism exists in this pallet to recover it — repeated across many such transfers, this is a systematic value-destruction vector reachable by any unprivileged sender. 	value: U256,
	erc_decimals: u8,

/// Converts a local u128 balance to an ERC20 U256 amount
///
/// Multiplies by 10^(erc_decimals - local_decimals) to scale up to ERC20 precision
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
