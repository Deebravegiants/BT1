## Title
Webhook `shop-domain` Header Is Not Covered by HMAC Verification, Enabling Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` binds its HMAC signature only to the raw request body, while the `shop` (and `topic`, `webhook_id`, `api_version`) values are read from unauthenticated HTTP headers. `Registry.process` validates the HMAC over the body only and then forwards the *unverified* `shop` header value to the host application's handler as though it were an authenticated tenant identifier. An attacker who can obtain one validly-signed webhook payload (e.g. from their own store where they installed the app, since the webhook signing secret is the app's single `client_secret`, not a per-shop key) can replay that same body/HMAC pair with a forged `shop-domain` header naming a victim shop, and the gem will report it to the handler as authentic data for that victim tenant.

### Finding Description
The identity binding this gem is supposed to guarantee is:
`hmac_valid(request) == true` implies `request.shop == the shop that actually produced this exact payload`.

In `lib/shopify_api/webhooks/request.rb`:
```ruby
def shop
  T.cast(shopify_header("shop-domain"), String)
end
...
def to_signable_string
  @raw_body
end
```
`to_signable_string` — the only material fed into `HmacValidator.validate` — is just `@raw_body` [1](#0-0) . The `shop`, `topic`, `api_version`, and `webhook_id` fields all come straight from attacker-controlled HTTP headers with no cryptographic tie to the signature [2](#0-1) .

`Registry.process` validates the HMAC and then hands the unverified `shop` straight to the host app's handler as trusted metadata:
```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
``` [3](#0-2) 

`HmacValidator.validate` computes and compares the HMAC purely against `to_signable_string` (the body) with the app's `api_secret_key`: [4](#0-3) . Because the signing secret is the app's single `client_secret`, it is identical for every shop that has installed the app — Shopify does not derive a per-shop webhook secret. Consequently, any body+HMAC pair produced for `shop-A.myshopify.com` remains a valid signature no matter what `shop-domain` header is attached, because that header is never part of the signed content.

**Before attack:** `handler.handle` is only ever invoked with `data.shop` equal to the shop that Shopify actually sent the webhook for.
**After attack:** an app-installing attacker captures one legitimate `(raw_body, hmac)` pair delivered to their own webhook endpoint, then re-POSTs the identical body and HMAC to the same endpoint with `shopify-shop-domain: victim-shop.myshopify.com`. `Utils::HmacValidator.validate` still returns `true` (body/HMAC pair is genuinely valid for the app's secret), and `WebhookMetadata.shop` is now `victim-shop.myshopify.com` even though the victim never sent or authorized this event.

Any host application that uses `data.shop` from `WebhookMetadata` to look up/act on a specific merchant's session, records, or credentials (the documented and expected usage pattern per `docs/usage/webhooks.md`) will now perform that action attributed to the wrong tenant, purely because this gem asserts the header value is trustworthy once `HmacValidator.validate` passes.

### Impact Explanation
This breaks the shop-identity binding this gem is documented to provide via `ShopifyAPI::Webhooks::Registry.process`/`Request`, allowing a caller with a legitimate app installation on their own shop to inject events attributed to an arbitrary other tenant (cross-tenant access), matching the Critical/High "cross-tenant access" impact category. Any consuming application logic keyed off `WebhookMetadata#shop` (order processing, data sync, session/credential lookups) can be tricked into acting on/for a shop that did not send the event.

### Likelihood Explanation
Likelihood is high for any attacker who can install the target app on a shop they control (a normal, unprivileged action for public apps) — no leaked secrets, no TLS interception, and no privileged account are required. They legitimately receive one signed webhook from their own store, then simply replay the identical raw body and `hmac-sha256` header while substituting the `shop-domain` header. The gem performs no additional integrity check tying the header to the signed payload.

### Recommendation
Include `shop` (and ideally `topic`, `api_version`, `webhook_id`) inside the HMAC-signed material verified by `HmacValidator`, or otherwise cryptographically bind the `shop-domain` header to the signature check in `Webhooks::Request#to_signable_string` / `HmacValidator.validate`, so a valid signature can only be produced for the exact shop that sent it.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and receives a legitimate webhook call, capturing:
   - `raw_body` (e.g. `{"id":123}`)
   - `x-shopify-hmac-sha256: <valid-hmac-for-raw_body>`
   - `x-shopify-shop-domain: attacker-shop.myshopify.com`
2. Attacker re-sends the identical `raw_body` and `x-shopify-hmac-sha256` header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds the request; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `raw_body` only — this matches, so validation passes [5](#0-4) .
4. The registered handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, even though `victim-shop` never sent this webhook [6](#0-5) .

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac

          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
