### Title
Webhook shop identity spoofing via HMAC that only covers the request body, not the `shop-domain` header - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request **body**. The `shop` value that the handler receives and acts on is taken from the `X-Shopify-Shop-Domain` / `shopify-shop-domain` HTTP **header**, which is completely outside the HMAC-signed data. This breaks the identity binding `shop_header == shop_that_produced_the_signed_bytes`, allowing a webhook that was legitimately signed for one shop to be replayed with a different shop's identity.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all pulled from headers, none of which participate in the signable string: [2](#0-1) 

`Registry.process` validates only that HMAC: [3](#0-2) 

and then dispatches to the app handler using `request.shop` — the unauthenticated header value — bound together with the HMAC‑authenticated body: [4](#0-3) 

The HMAC validator itself only compares `verifiable_query.hmac` against a signature computed over `to_signable_string` (the raw body for webhooks): [5](#0-4) 

**Equality that should hold but doesn't:** `shop_that_cryptographically_produced_this_signed_body == shop_delivered_to_the_handler`. Because the header is never included in the signed material, these two values can diverge.

**Exploitable gap:** Any merchant who installs the app on their own store is an "unprivileged internet user" with respect to every *other* tenant of the app. Such a merchant can trigger a real webhook delivery for their own shop (e.g. by editing an order note, product title, or any other field that flows into the webhook JSON payload) and thereby obtain a **validly HMAC-signed** `(raw_body, hmac)` pair — genuinely computed by Shopify using the app's shared `api_secret_key`. The attacker can then POST that exact `raw_body` + `hmac` header to the app's public webhook endpoint again, but with `X-Shopify-Shop-Domain` changed to name an arbitrary victim shop domain. `Utils::HmacValidator.validate` still succeeds (it only checks the body bytes), and `Registry.process` invokes the handler with `shop: <victim-shop>` and attacker-controlled `body`.

### Impact Explanation
This is a cross-tenant identity-binding break: an attacker-controlled body can be attributed to a shop the attacker does not own and never received consent from. Depending on how the host application's webhook handlers use `WebhookMetadata#shop` (e.g., updating a shop's local records, processing `app/uninstalled`, fulfilling GDPR `customers/data_request` / `shop/redact` mandatory webhooks, or triggering emails/business logic keyed by shop), this enables cross-tenant data corruption, forged compliance events, or state confusion for a victim merchant — without requiring the attacker to possess the victim's access token, the app's `client_secret`, or any privileged access. This falls under the "cross-tenant access" Critical impact bucket defined by the rules.

### Likelihood Explanation
Any user capable of installing/using the app on a store they control (a normal, low-privilege internet user in the context of a public app) can obtain genuinely-signed webhook payloads for arbitrary chosen content (by controlling the fields that populate a webhook body) and then replay them with a forged shop header against the app's public webhook endpoint. No secrets or elevated access are required, only knowledge of the app's public webhook URL, which is typically documented/discoverable.

### Recommendation
Bind the shop identity into the signed material actually verified, or otherwise independently authenticate the shop-domain header against known/authorized installations before trusting it:
- Require the webhook signature validation to also authenticate `shop`/`topic`/`webhook_id` (e.g., include them in the HMAC input, mirroring what Shopify does for OAuth's `AuthQuery#to_signable_string`), or
- Have `Registry.process` cross-check `request.shop` against the shop associated with the session/webhook registration that the app expects, rejecting deliveries for shops that were never registered by this app instance, and/or
- Track and reject `webhook_id` values that are replays for a different `shop` than originally delivered.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and registers the `orders/create` webhook (or any topic the app subscribes to).
2. Attacker creates an order (or otherwise triggers the webhook) with a crafted payload of their choosing, and captures the genuine delivery: headers `X-Shopify-Hmac-Sha256: <real-hmac>`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Topic: orders/create`, and raw body `B`.
   - This HMAC is valid because `Utils::HmacValidator.compute_signature` signs `B` with the real `api_secret_key` shared between Shopify and the app: [6](#0-5) 
3. Attacker replays the exact same `B` and `X-Shopify-Hmac-Sha256` value to the app's public webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses the forged headers, `Registry.process` calls `Utils::HmacValidator.validate(request)` which succeeds (body/HMAC pair is valid), and the handler is invoked with `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body: <attacker-crafted>, ...)` — as shown at [4](#0-3) .
5. The app's business logic processes attacker-controlled webhook content as if it originated from `victim-shop.myshopify.com`.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
