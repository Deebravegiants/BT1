### Title
Uniswap V4 pool spot price used for intent order pricing is flash-loan manipulable and the price guard does not bound execution cost - ([File: sdk/packages/simplex/src/strategies/fx.ts])

### Summary
Simplex's `FXFiller` prices curveless (venue-priced) intent-gateway pairs directly from the current Uniswap V4 pool spot price (`sqrtPriceX96`), the same "use current reserves as valuation" pattern that caused the Notional LP-token issue. The only safeguard, `checkPriceGuard`, bounds deviation against a static reference price but — by the codebase's own documentation — does not account for the execution cost (fee tier, size/price impact) of actually sourcing the token from that pool, letting an attacker manipulate the pool within the allowed band and extract value from every order the solver fills at that price.

### Finding Description
`resolveLegRates` prices curveless pairs from a live venue quote instead of a static curve: [1](#0-0) 

The venue quote comes from `UniswapV4FundingPlanner.getExoticTokenPrice`, which selects the position with the largest pool liquidity and derives price from the pool's `sqrtPriceX96`/current tick — the pool's live spot price: [2](#0-1) 

The only defense against manipulation is `checkPriceGuard`, which rejects a quote only if it deviates from a static, operator-set `referencePrice` by more than `maxDeviationBps`: [3](#0-2) 

The project's own verified flow notes state this guard is insufficient against the actual attack surface: it "checks deviation from a static reference, not execution cost," and `computeDirectPoolPriceUsd` "returns the raw pool mid derived from `sqrtPriceX96`... and there is no size or impact term," while "a venue-priced pair that has to swap through its own pool to source inventory pays a fee tier it never quoted against": [4](#0-3) 

This is structurally identical to the Notional finding: a value used for a consequential financial decision (here, the exchange rate the solver pays out on an intent order) is derived from current pool reserves rather than a manipulation-resistant TWAP, and the deviation-band mitigation only bounds *how far* the price can be pushed, not *whether* the pushed price is still profitable to exploit once the true cost of unwinding the position (fee tier + slippage) is considered.

### Impact Explanation
An attacker can flash-swap a Uniswap V4 pool that backs a solver's `[vault.uniswapV4]` position to move the pool's spot price by up to the configured `maxDeviationBps` (e.g. 2%, per the documented default config) in a direction favorable to themselves, then immediately submit or trigger an intent order that the solver prices and fills from `resolveLegRates`/`getVenueUsdPrice` at that manipulated rate. Because the guard is purely a static-reference deviation check with no execution-cost or size-impact term, the manipulation can be sized to stay inside the guard band while still being profitable once the true LP-withdrawal cost (fee tier not applied, and price impact linearly extended by `computeLegPolicyOutput`) is accounted for. This lets an attacker repeatedly extract value from the solver's vault/LP inventory — a concrete, repeatable theft of solver funds funding real order fills, not merely a griefing revert.

### Likelihood Explanation
This is directly reachable by any unprivileged actor who can submit/trigger an IntentGateway order and simultaneously interact with the public Uniswap V4 pool the solver reads from (a standard flash-loan/flash-swap primitive), requiring no privileged role, governance action, or solver misconfiguration beyond the documented (and apparently commonly used, per `docs/content/developers/evm/simplex/pricing.mdx`) pool-based pricing mode. The codebase's own audit-derived documentation explicitly flags the gap as unresolved, indicating high confidence this is a live, known-but-unmitigated exposure rather than a theoretical one.

### Recommendation
- Do not derive `getExoticTokenPrice` purely from the instantaneous `sqrtPriceX96`; incorporate a manipulation-resistant time-weighted average price (TWAP) from the Uniswap V4 pool (or an external oracle) as the primary reference, using the spot price only as a sanity check.
- Extend `checkPriceGuard` (or add a companion check) to bound the *effective* execution cost — including the pool's actual fee tier and a size/impact term for the notional being filled — rather than only the raw mid-price deviation from a static reference.
- Consider rate-limiting or requiring multi-block confirmation for venue-priced fills above a notional threshold, so a single-transaction flash manipulation cannot be monetized within one atomic bundle.

### Proof of Concept
1. Attacker identifies a Simplex solver configured with `[vault.uniswapV4]` pool-based pricing for pair `USDC/EXOTIC`, with `referencePrice`/`maxDeviationBps` set (e.g. 1575 ± 200 bps per the documented example).
2. Attacker flash-swaps the underlying Uniswap V4 pool to move the pool mid price to the edge of the allowed band (e.g. +1.9%), staying under `maxDeviationBps` so `checkPriceGuard` still passes (`sdk/packages/simplex/src/strategies/fx.ts:428-448`).
3. Attacker (or an accomplice) immediately places/relays an IntentGateway order sized so that `resolveLegRates` prices it from `getVenueUsdPrice` at the manipulated pool mid (`sdk/packages/simplex/src/strategies/fx.ts:1453-1465`), which the guard test in `fx.price-guard.test.ts` confirms accepts quotes within the band regardless of whether the pool can actually support that price at size (`sdk/packages/simplex/src/tests/strategies/fx.price-guard.test.ts:72-79`).
4. The solver's `FundingVenue.planWithdrawalForToken` withdraws from the manipulated-position pool and fills the order at the inflated/deflated rate, paying the attacker (or the order counterpart) more value than the true, execution-cost-adjusted price would allow — realizing the attacker's profit while reverting the pool to its original state after unwinding the flash swap.

	/**
	 * Validates a live venue quote against the static reference price for the chain.
	 * Returns true (pass) when no guard is configured, or no reference exists for the
	 * chain. Returns false when the quote (token1 per USD) deviates from the reference
	 * by more than `maxDeviationBps`, in which case the order must not be filled.
	 */
	private checkPriceGuard(orderId: string | undefined, chain: string, venueToken1PerUsd: Decimal): boolean {
		const guard = this.priceGuard?.get(chain)
		if (!guard || guard.reference.lte(0)) return true

		const deviationBps = venueToken1PerUsd.minus(guard.reference).abs().div(guard.reference).mul(10000)
		if (deviationBps.gt(guard.maxDeviationBps)) {
			this.logger.warn(
				{
					orderId,
					chain,
					venuePrice: venueToken1PerUsd.toString(),
					referencePrice: guard.reference.toString(),
					deviationBps: deviationBps.toFixed(2),
					maxDeviationBps: guard.maxDeviationBps,
				},
				"Rejecting order: Uniswap venue quote outside price-guard band",
			)
			return false
		}
		return true
	}

	async getExoticTokenPrice(chain: string, exoticToken: string): Promise<Decimal | null> {
		const state = this.stateByChain.get(chain)
		if (!state || !state.isHydrated()) return null

		try {
			await state.refresh()
		} catch (err) {
			this.logger.error({ err, chain }, "Failed to refresh state for price query")
			return null
		}

		const tokenLower = exoticToken.toLowerCase()
		let bestPrice: Decimal | null = null
		let bestLiquidity = 0n

		for (const pos of state.allPositions()) {
			if (pos.currency0.toLowerCase() !== tokenLower && pos.currency1.toLowerCase() !== tokenLower) continue
			const sdkPool = state.getSdkPool(pos.tokenId)
			if (!sdkPool) continue

			const result = this.computeDirectPoolPriceUsd(pos, sdkPool, chain)
			if (result && result.exoticToken.toLowerCase() === tokenLower) {
				const poolLiquidity = state.getPoolLiquidity(pos.tokenId)
				if (poolLiquidity > bestLiquidity) {
					bestPrice = result.priceUsd
					bestLiquidity = poolLiquidity
				}
			}
		}

		if (bestPrice) {
			this.logger.debug({ chain, token: tokenLower, priceUsd: bestPrice.toString() }, "Exotic token price computed")
		}
		return bestPrice
	}
