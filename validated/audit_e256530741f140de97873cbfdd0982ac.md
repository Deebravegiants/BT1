Confirmed. The webhook HMAC signature only covers the raw request body (`to_signable_string` returns `@raw_body`) while the `shop` (and `topic`) values used by `Registry.process` to identify the tenant and dispatch to the app's webhook handler come from HTTP headers that are **not included in the signed content**.

### Title
Webhook shop-domain identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC over the raw request body only, while the `shop` domain (and `topic`) that the gem hands to the app's webhook handler are read from HTTP headers that are excluded from that signature. Since the HMAC never binds the header-derived `shop` to the signed payload, any party able to produce one validly-signed webhook payload/HMAC pair (any Shopify webhook it has received for a store it controls) can resubmit that exact body+HMAC to the app's webhook endpoint with a different `x-shopify-shop-domain` header, and the gem will accept it as a webhook for the impersonated shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) . `HmacValidator.validate` verifies the received HMAC purely against that signable string, computed with `Context.api_secret_key`: [2](#0-1) .

Meanwhile, `Request#shop` and `Request#topic` are pulled directly from the `x-shopify-shop-domain`/`x-shopify-topic` headers, which are never part of `to_signable_string` and therefore are not covered by the signature at all: [3](#0-2) .

`Registry.process` validates the HMAC and then immediately trusts `request.topic` and `request.shop` to select and invoke the app's registered handler, constructing `WebhookMetadata` with the header-derived `shop`: [4](#0-3) .

This breaks the identity binding `shop authenticated by HMAC == shop delivered to the app handler`. The HMAC only proves "the body was signed with `api_secret_key`" — it says nothing about which shop the header claims the body came from. Anyone who receives one genuine, signed webhook (e.g. for their own store, since installing the app and triggering a webhook-eligible event requires no elevated privilege beyond being a merchant/tenant of the app) can replay the identical `raw_body` + `hmac-sha256` header while substituting a different `shop-domain` header value, and `Registry.process` will dispatch it to the handler as if it originated from the victim shop.

### Impact Explanation
This allows cross-tenant impersonation: an app handler that uses `WebhookMetadata#shop` to look up per-shop state, trigger actions, or update stored data (a common integration pattern) can be tricked into acting on behalf of, or against, a shop the attacker does not control, using only a webhook payload the attacker legitimately received for their own tenant. This matches the "cross-tenant access" Critical impact category since the shop identity boundary enforced by the HMAC is bypassed.

### Likelihood Explanation
Any installed merchant (a low-privilege existing tenant, not requiring `api_secret_key` or any Shopify-internal secret) can trigger a webhook for their own shop, capture the exact `raw_body` and `x-shopify-hmac-sha256` value delivered to the app's endpoint, and replay it with an altered `x-shopify-shop-domain` header. No cryptographic material needs to be forged because the header is simply excluded from what is signed.

### Recommendation
Include the shop domain (and topic) in the HMAC-covered signable content, or otherwise independently verify that the `shop-domain` header corresponds to a shop session/registration the app expects before dispatching to a handler, rather than trusting the header value once body-only HMAC validation succeeds.

### Proof of Concept
1. Install the app on shop `attacker.myshopify.com` and trigger any subscribed webhook topic; capture the resulting request body `B` and the `x-shopify-hmac-sha256: H` header sent by Shopify (H is a valid HMAC of `B` under the app's `api_secret_key`).
2. Send a new HTTP request to the app's webhook endpoint with the same body `B`, the same `x-shopify-hmac-sha256: H` header, the same `x-shopify-topic`, but `x-shopify-shop-domain: victim.myshopify.com`.
3. `HmacValidator.validate` succeeds because it only re-computes the HMAC over `B` (`Request#to_signable_string` returns `@raw_body`), independent of the shop-domain header.
4. `Registry.process` proceeds to call the registered handler with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed_body, ...)`, causing the app to process the payload as if it came from `victim.myshopify.com`.
