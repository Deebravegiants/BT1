### Title
Quadratic-time GRANDPA justification verification lets an attacker-crafted proof stall consensus updates - (File: `modules/consensus/grandpa/primitives/src/justification.rs`)

### Summary
`GrandpaJustification::verify_with_voter_set` verifies a submitted GRANDPA finality proof by iterating over every precommit in the justification and, for each one whose target differs from the base block, walking the attacker-supplied `votes_ancestries` chain from that target back to the base via `AncestryChain::ancestry`. Neither the number of precommits nor the length of the ancestry chain is bounded independently of each other, so the total work is `O(precommits × ancestry_length)` for a single submitted consensus proof — the same non-linear-scaling bug class as the reported x509 name-constraint issue (input size scales the verifier's work non-linearly).

### Finding Description
`verify_with_voter_set` in [1](#0-0)  builds an `AncestryChain` from `self.votes_ancestries` (fully attacker-controlled header set decoded from the submitted proof), then for every precommit in `self.commit.precommits` (also attacker-controlled, one signature per voting authority) calls: [2](#0-1) 

`AncestryChain::ancestry` walks parent-hash pointers one at a time from the precommit's target back to the shared base block: [3](#0-2) 

Each call is `O(H)` where `H` is the number of headers between the target and the base in `votes_ancestries` (up to the full length of the supplied ancestry vector). Because the loop runs once per precommit, and each precommit can independently target any different point along a long ancestry chain, the aggregate cost is `O(P × H)` for `P` precommits and `H` ancestry length — both counts come directly from a single relayed proof (`FinalityProof`/`GrandpaJustification`), decoded and processed in `verify_grandpa_finality_proof` ( [4](#0-3) ), which is invoked from the on-chain `verify_consensus` entrypoint in `modules/ismp/clients/grandpa/src/consensus.rs`. Unlike Pharos's SPV verifier, which explicitly caps proof depth (`MAX_PROOF_DEPTH`) and sibling counts to bound combined-walk cost ( [5](#0-4) ), there is no equivalent joint bound here on `precommits.len() * votes_ancestries.len()`.

An attacker (any relayer submitting a consensus update) can maximize `P` by including many precommit signatures (up to the full GRANDPA authority set size, easily in the hundreds to thousands for large relay chains) and maximize `H` by supplying a long ancestry chain, forcing the verifier to perform far more hashing/lookup work than the proof's byte size would suggest, mirroring the CVE's "processing time scales non-linearly with respect to input size."

### Impact Explanation
The consensus client's `verify_consensus` is the sole gate for admitting new GRANDPA finality state into hyperbridge; it runs synchronously as part of message/extrinsic execution before any state commitment is accepted. A crafted justification that drives `verify_with_voter_set` into worst-case `O(P × H)` behavior can consume disproportionate CPU/weight relative to its declared weight/size, degrading or blocking the consensus-update path for that client (and therefore blocking delivery of any ISMP messages that depend on state commitments proven against it) until the resource exhaustion is mitigated — a route unable to deliver messages due to verifier cost blowup from a single submitted proof.

### Likelihood Explanation
Likelihood is constrained by extrinsic size/weight limits on the underlying substrate chain, which bound how many precommits and ancestry headers can be packed into a single call, and by GRANDPA's existing signature-verification cost (`ed25519_verify` per precommit) which already scales with `P`. However, the additional `O(P × H)` ancestry-walk cost is *multiplicative* on top of that baseline and is not capped by any explicit joint limit in this code path, unlike other proof types in the repo (Pharos SPV) that were specifically hardened against this exact class of unbounded-combination cost.

### Recommendation
Bound the combined ancestry-walk cost explicitly, analogous to the Pharos `MAX_PROOF_DEPTH` mitigation: cap `votes_ancestries.len()` and/or the total number of ancestry-lookup steps performed across all precommits in a single justification, and reject justifications that exceed the bound before performing any ancestry walk. Alternatively, deduplicate precommit targets before walking ancestry (multiple precommits sharing a target only need one walk) and memoize partial routes so repeated overlapping walks are not recomputed.

### Proof of Concept
Not independently reproduced (no execution environment available); the vulnerability is inferred directly from the nested-loop structure in `verify_with_voter_set` and `AncestryChain::ancestry` cited above: a justification with `N` authority precommits, each targeting a distinct block near the far end of an `M`-header `votes_ancestries` list (all sharing the same distant base), forces `N` separate `O(M)` walks, i.e. `O(N·M)` total steps, from a single decoded proof submitted via `verify_consensus`.

		voters: &VoterSet<AuthorityId>,

					result.num_equivocations() > 0
				{
					Err(anyhow!("Invalid commit, found one of `duplicate precommits`, `invalid voters`, or `equivocations` {result:?}"))?
				}
			},
			err => {
				let result = err.map_err(|_| {
					anyhow!("[verify_with_voter_set] Invalid ancestry while validating commit!")
				})?;
				Err(anyhow!("invalid commit in grandpa justification: {result:?}"))?
			},
		}

		// should serve as the root block for populating ancestry (i.e.
		// collect all headers from all precommit blocks to the base)

			.commit
			.precommits
			.iter()
			.map(|signed| &signed.precommit)
			.min_by_key(|precommit| precommit.target_number)
			.map(|precommit| precommit.target_hash.clone())

impl<H: HeaderT> finality_grandpa::Chain<H::Hash, H::Number> for AncestryChain<H>
where
	H::Number: finality_grandpa::BlockNumberOps,
{
	fn ancestry(
		&self,
		base: H::Hash,
		block: H::Hash,
	) -> Result<Vec<H::Hash>, finality_grandpa::Error> {
		let mut route = vec![block];
		let mut current_hash = block;
		while current_hash != base {
			match self.ancestry.get(&current_hash) {
				Some(current_header) => {
					current_hash = *current_header.parent_hash();
					route.push(current_hash);
				},
				_ => return Err(finality_grandpa::Error::NotDescendent),
			};
		}
		Ok(route)
	}

pub fn verify_grandpa_finality_proof<H>(
	mut consensus_state: ConsensusState,
	finality_proof: FinalityProof<H>,
) -> Result<(ConsensusState, H, Vec<H256>, AncestryChain<H>), Error>
where
	H: Header<Hash = H256, Number = u32>,
	H::Number: finality_grandpa::BlockNumberOps + Into<u32>,
{
	// First validate unknown headers.
	let headers = AncestryChain::<H>::new(&finality_proof.unknown_headers);

	let target = finality_proof
		.unknown_headers
		.iter()
		.max_by_key(|h| *h.number())
		.ok_or(Error::UnknownHeadersEmpty)?;

	// this is illegal
	if target.hash() != finality_proof.block {
		Err(Error::LatestBlockMismatch)?;
	}

	let justification =
		GrandpaJustification::<H>::decode_all(&mut &finality_proof.justification[..])
			.map_err(|e| Error::DecodeJustification(alloc::format!("{e:?}")))?;

	if justification.commit.target_hash != finality_proof.block {
		Err(Error::JustificationTargetMismatch)?;
	}

	let from = consensus_state.latest_hash;

	let base = finality_proof
		.unknown_headers
		.iter()
		.min_by_key(|h| *h.number())
		.ok_or(Error::UnknownHeadersEmpty)?;

	if base.number() < &consensus_state.latest_height {
		headers
			.ancestry(base.hash(), consensus_state.latest_hash)
			.map_err(|_| Error::InvalidAncestry)?;
	}

	let finalized = headers.ancestry(from, target.hash()).map_err(|_| Error::InvalidAncestry)?;

	// 2. verify justification.
	justification
		.verify(consensus_state.current_set_id, &consensus_state.current_authorities)
		.map_err(|e| Error::JustificationVerify(e.to_string()))?;
