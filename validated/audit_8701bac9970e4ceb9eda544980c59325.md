### Title
EvmHost native-fee dispatch functions do not refund excess ETH to the original caller - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` accept native ETH via `msg.value` and swap it for the exact fee-token amount needed using Uniswap's `swapETHForExactTokens`. Any ETH sent beyond the amount required for the swap is refunded by the Uniswap router to whichever address called the router — which is `EvmHost` itself, not the original transaction sender. The excess is never forwarded back to `_msgSender()`.

### Finding Description
In `dispatch(DispatchPost)`: [1](#0-0) 

the same pattern repeats in `dispatch(DispatchGet)`: [2](#0-1) 

and in `fundRequest`: [3](#0-2) 

In each case, `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(fee, path, address(this), block.timestamp)` is invoked. Per Uniswap V2 Router semantics, `swapETHForExactTokens` refunds `msg.value - amountIn` back to `msg.sender` of that call. Since `EvmHost` is the caller of the router (not the end user who sent the transaction), any refund of unused ETH lands back in `EvmHost`'s own balance instead of being forwarded to `_msgSender()` (the `payer`/caller who actually overpaid). None of these three functions capture the router's return value or perform any subsequent transfer of unspent ETH back to the caller.

This is directly analogous to the reported `LienToken._payment` issue: a user who sends more native token than strictly required for the fee swap has the surplus silently retained by the receiving contract rather than returned to them, because the code assumes the entire `msg.value` is consumed without verifying/refunding the actual amount spent.

By contrast, other parts of this same codebase correctly implement this refund pattern — e.g. `IntentGatewayV2`/`ExtrinsicIntents._fillCrossChain` explicitly track `msgValue` after swaps/transfers and call `_sendValue(msg.sender, msgValue)` for any leftover: [4](#0-3) 

which confirms the intended design is to refund unused native value to the caller — a design `EvmHost.dispatch`/`fundRequest` fails to follow.

### Impact Explanation
Any unprivileged dispatcher app or end user who calls `dispatch()`/`fundRequest()` with native ETH (a very common, documented payment path — see `docs/content/developers/evm/messaging/post-requests.mdx` "Native Token Payment") and supplies `msg.value` even slightly above the exact quoted amount (which is unavoidable in practice due to price movement/slippage between quoting and execution) permanently loses the difference — it becomes stuck in the `EvmHost` contract's ETH balance with no mechanism shown to sweep/return it to the original payer. This is a direct loss of user funds on the standard message-dispatch path used by every app built on Hyperbridge (`HyperApp.dispatchWithFeeToken`/native dispatch flows, `HyperFungibleToken.send`, `IntentGateway` cross-chain settlement fee payment, etc.).

### Likelihood Explanation
High likelihood: front-end/SDK callers typically add a buffer (slippage/safety margin) to the native value sent for a Uniswap swap-based fee quote, since the exact on-chain price at execution time can differ from the quoted price at call time (see `HyperApp.quote()` using `getAmountsIn`, which is a pre-transaction estimate subject to slippage as documented in `docs/content/developers/evm/messaging/post-requests.mdx` lines 241-249: "Slippage: Yes (Uniswap swap)"). Every such over-estimation results in a loss for the caller, making this reachable on essentially any native-fee-paid dispatch.

### Recommendation
Track the actual amount spent by the swap (the Uniswap router returns `amounts[]`, or compute `spent = msg.value - address(this).balance_before_after_diff`) and refund the remainder to `_msgSender()` (or `post.payer`/`get`'s payer) with a low-level call, mirroring the pattern already used in `ExtrinsicIntents._fillCrossChain` (`_sendValue(msg.sender, msgValue)`), for `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest`.

### Proof of Concept
1. Caller invokes `EvmHost.dispatch(DispatchPost)` with `msg.value = 2 ether`, where `post.fee` in feeToken only requires `1 ether` worth of ETH to swap via `swapETHForExactTokens`.
2. `swapETHForExactTokens{value: 2 ether}(post.fee, path, address(this), block.timestamp)` executes: it spends `~1 ether` of ETH on the swap and refunds the remaining `~1 ether` to `msg.sender` of the call — which is `EvmHost` (since `EvmHost` is the direct caller of the router).
3. `EvmHost.dispatch` returns without forwarding any ETH back to the original transaction sender.
4. The original sender's excess `~1 ether` is now held in `EvmHost`'s balance instead of being returned to them, with no visible refund path in the reviewed code.

(Note: I was not able to fully verify within the available search budget whether `EvmHost` exposes an admin-only sweep/rescue function elsewhere in the file that could later recover this stranded ETH for governance/treasury purposes; even if such a function exists, it would return the funds to the protocol rather than the overpaying user, which still matches the reported bug class of "funds not returned to the payer.")

        if (msg.value > 0) {
            address[] memory path = new address[](2);

            path[0] = IUniswapV2Router02(uniswapV2).WETH();

            );

        }
