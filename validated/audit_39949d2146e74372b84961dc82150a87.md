## Title
Unsafe non-reverting ERC20 transfers in Tron `IntentGatewayV2.withdraw()` and `SweepDust` handling silently lose escrowed funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` mixes `SafeERC20` (used correctly for inbound `safeTransferFrom`/escrow deposits) with raw low-level `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` for outbound escrow payouts and dust sweeps. The code only checks that the low-level `call` did not revert (`success`), but never decodes/validates the ERC20 boolean return value itself. Non-compliant ERC20 tokens that return `false` on failure instead of reverting will be treated as a successful transfer, while escrow accounting is unconditionally decremented and the order is marked filled/refunded.

### Finding Description
`withdraw()` releases escrow to a `beneficiary` using: [1](#0-0) 

and the fee payout right after it: [2](#0-1) 

The `SweepDust` request handler does the same pattern: [3](#0-2) 

In every case, `success` only reflects whether the external call reverted — it does **not** decode `returndata` to confirm the token's boolean success flag. Some ERC20 tokens (e.g. legacy/non-standard tokens common on Tron-compatible chains) return `false` on a failed `transfer` rather than reverting. With this pattern, such a failed transfer is indistinguishable from a successful one: `success` is `true` (the call itself didn't revert), so the code proceeds to decrement `_orders[body.commitment][token]`, mark `_filled[body.commitment] = beneficiary`, and emit `EscrowReleased`/`EscrowRefunded`, even though the beneficiary received zero tokens.

This is inconsistent with the rest of the same file and the canonical EVM `IntentGatewayV2`/`IntentsBase` implementations, which correctly use `SafeERC20.safeTransfer`/`safeTransferFrom` for the analogous flows (`_withdraw` in `IntentsBase.sol`): [4](#0-3) 

The Tron file even imports `SafeERC20` and uses it for inbound transfers (`placeOrder`), showing the safe pattern was known but not applied consistently to the outbound payout/sweep paths: [5](#0-4) [6](#0-5) 

### Impact Explanation
This causes permanent loss of escrowed user funds when the escrowed token is a non-standard ERC20 that returns `false` instead of reverting on failed transfers (e.g. due to blacklist, paused state, or insufficient allowance/balance edge cases on the token side). Once `withdraw()` runs:
- The escrow ledger entry `_orders[body.commitment][token]` is decremented to zero, and `_filled[body.commitment]` is set, permanently marking the order as settled.
- The beneficiary never actually receives the tokens (transfer silently failed).
- There is no remaining code path to re-attempt or reclaim these funds, since the contract's internal accounting believes the payout already happened.

This is a permanent freezing/loss-of-funds bug reachable through the intents escrow redemption flow (`RedeemEscrow`/`RefundEscrow` handling and `SweepDust`), which are core token-custody operations of the intent gateway.

### Likelihood Explanation
Likelihood depends on the escrowed/output token being a non-standard ERC20 that returns `false` on failure rather than reverting (a known and non-trivial-but-real class of tokens). Given `IntentGatewayV2` is a generic, token-agnostic escrow/settlement contract intended to support arbitrary ERC20 assets across intents, and does not restrict the token to WETH/canonical assets, any deployment that accepts such a token as escrow/output/fee asset is exposed. The failure condition doesn't require attacker privilege — it can be triggered by ordinary transfer failure conditions on the token side (e.g. blacklisted beneficiary, paused token) during normal, unprivileged escrow redemption.

### Recommendation
Replace all raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` payout patterns in `evm/tron/contracts/apps/IntentGatewayV2.sol` (`withdraw()` for both token and fee payout, and the `SweepDust` handler) with OpenZeppelin's `SafeERC20.safeTransfer`, consistent with the rest of the codebase (`IntentsBase._withdraw`, `WrappedHyperFungibleTokenUpgradeable.onAccept`). This ensures both revert-on-failure and non-standard boolean-return tokens are handled safely, and escrow accounting is only updated when the transfer has truly succeeded.

### Proof of Concept
1. Deploy `IntentGatewayV2` (Tron variant) with a token `T` implementing ERC20 such that `transfer` returns `false` on failure instead of reverting (e.g. a blacklist-style token where `transfer` to a blacklisted address returns `false`).
2. A user places an order escrowing `T` via `placeOrder` (uses `safeTransferFrom`, succeeds normally).
3. An order is filled/refunded and `withdraw()` is invoked (via the `RedeemEscrow`/`RefundEscrow` ISMP request path) with `beneficiary` set to an address that causes `T.transfer` to return `false` (e.g. blacklisted or the token is paused for that address) — see: [1](#0-0) 
4. `token.call(...)` succeeds (does not revert) but returns encoded `false`. Since the code only checks `success` (the outer call outcome) and not the decoded boolean, it proceeds: `_orders[body.commitment][token] -= amount;`, `_filled[body.commitment] = beneficiary;`, and emits `EscrowReleased`/`EscrowRefunded`.
5. The beneficiary never receives token `T`, and the escrow record for this commitment is permanently zeroed/finalized — the funds are irrecoverably stuck in the contract.
