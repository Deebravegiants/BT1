### Title
Infinite loop in GRANDPA `AncestryChain::ancestry` walk via attacker-supplied cyclic header set — ([File: modules/consensus/grandpa/primitives/src/justification.rs])

### Summary
The GRANDPA `AncestryChain::ancestry` walk (used to validate justification vote ancestries and equivocation fraud proofs) walks `parent_hash` pointers through an attacker-supplied set of unverified headers until it reaches a `base` hash, with no bound on iteration count and no cycle detection. Because `parent_hash` is an arbitrary field chosen by whoever crafted the header set (not itself verified against any external chain), an attacker can submit a justification/fraud proof whose `votes_ancestries`/`unknown_headers` contain two or more headers whose `parent_hash` fields point at each other, forming a cycle that never reaches `base`. This causes the verification loop to spin forever on a single relayed message.

### Finding Description
`AncestryChain::ancestry` walks parent hashes: [1](#0-0) 

The map `self.ancestry` is built directly from the untrusted `votes_ancestries` field of a submitted `GrandpaJustification` (or `unknown_headers` of a `FinalityProof`), keyed by each header's own computed hash: [2](#0-1) 

The loop condition is only `current_hash != base`; on each iteration it looks up `current_hash` in the map and, if found, sets `current_hash = header.parent_hash()`. Nothing prevents `parent_hash` from pointing back to an already-visited hash in the same submitted set. Since `parent_hash` is just a struct field of the arbitrary header (not cryptographically bound to any real chain relationship in this function), a submitter can craft two headers A and B where `A.parent_hash = hash(B)` and `B.parent_hash = hash(A)`. If neither hash equals `base`, the loop alternates forever between the two map entries, never terminating (mirrors the CVE's own root cause of an unbounded walk over adversarial input).

This routine is reachable from two unprivileged, single-message entry points:
1. `verify_with_voter_set`, called during ordinary GRANDPA consensus-proof verification (`GrandpaConsensusClient::verify_consensus` → `verify_grandpa_finality_proof`/`verify_parachain_headers_with_grandpa_finality_proof`), which is driven by relayer-submitted consensus messages: [3](#0-2) [4](#0-3) 

2. `verify_fraud_proof`, which builds two `AncestryChain`s directly from attacker-controlled `unknown_headers` and calls `.ancestry(base, target)` on each, before any justification signature is checked: [5](#0-4) 

In both cases the header vectors are decoded straight from relayer-supplied proof bytes with no cycle/parent-hash validation prior to the ancestry walk.

### Impact Explanation
A relayer or any party able to submit a GRANDPA consensus proof or fraud proof (an unprivileged, single-transaction action) can craft a header set with a `parent_hash` cycle that never resolves to `base`. The verification call then loops indefinitely, consuming unbounded CPU/wasm execution weight within the block/extrinsic executing consensus verification. This blocks consensus-client updates for that state machine (route unable to deliver messages/finalize state), and if executed inside block-authoring/validation (weight-metered execution), it risks stalling or DoS'ing the chain processing that message — a denial-of-service impacting the GRANDPA consensus client's ability to progress, which then blocks all downstream ISMP message delivery relying on that light client.

### Likelihood Explanation
High reachability: both call sites are driven by relayer-submitted, otherwise-unauthenticated proof bytes (`verify_consensus`/`verify_fraud_proof`), decoded before any signature check gates the ancestry walk. Constructing two headers with fabricated `parent_hash` fields that reference each other's real hash is straightforward — it requires no cryptographic break, since `parent_hash` is not otherwise validated at this stage. The only barrier is normal extrinsic submission (fees/weight), consistent with an unprivileged actor able to reach this analog.

### Recommendation
Bound the ancestry walk with the size of the header set (e.g., `for _ in 0..ancestry.len()+1` with an explicit "route too long" error) and/or track visited hashes to detect cycles and return `Err(finality_grandpa::Error::NotDescendent)` immediately when a hash repeats, mirroring the CVE's fix of bounding/aborting on structurally impossible input rather than trusting it to terminate.

### Proof of Concept
1. Craft headers `A` and `B` (arbitrary content) such that `A.parent_hash = header_hash(B)` and `B.parent_hash = header_hash(A)` — trivial since `parent_hash` is a plain field, independent of the header's actual content hash.
2. Include `A` and `B` in `votes_ancestries` of a `GrandpaJustification` (or in `unknown_headers` of a `FinalityProof` used for `verify_fraud_proof`), with `base_hash`/`base` set to neither `hash(A)` nor `hash(B)`.
3. Submit this as the `proof` to `GrandpaConsensusClient::verify_consensus` (or as `proof_1`/`proof_2` to `verify_fraud_proof`).
4. `AncestryChain::ancestry(base, block)` is invoked with `block = hash(A)` (or `hash(B)`); the `while current_hash != base` loop alternates between `hash(A)` and `hash(B)` forever, since both are present in the map and neither equals `base`, causing unbounded execution / denial of service.

	fn ancestry(
		&self,
		base: H::Hash,
		block: H::Hash,
	) -> Result<Vec<H::Hash>, finality_grandpa::Error> {
		let mut route = vec![block];
		let mut current_hash = block;
		while current_hash != base {
			match self.ancestry.get(&current_hash) {
				Some(current_header) => {
					current_hash = *current_header.parent_hash();
					route.push(current_hash);
				},
				_ => return Err(finality_grandpa::Error::NotDescendent),
			};
		}
		Ok(route)
	}
