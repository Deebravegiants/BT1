This confirms the vulnerability. The `Registry.process` method validates only the HMAC over the raw body, but then trusts `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` — all of which are pulled directly from HTTP headers that are **not part of the signed payload**.### Title
Webhook shop-domain, topic, api-version, and webhook-id headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs **only** the raw request body [1](#0-0) , while `ShopifyAPI::Webhooks::Registry.process` validates the HMAC over that same body-only string and then trusts `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version`, all of which are read verbatim from HTTP headers that are excluded from the signature [2](#0-1) . This breaks the intended binding: `hmac verifies body` ≠ `hmac verifies (body, shop)`, so the tenant identity (`shop`) attached to a webhook event is unauthenticated even though the body's authenticity is proven.

### Finding Description
`Request#shop`, `#topic`, `#api_version`, and `#webhook_id` are all simple header reads [3](#0-2) . The HMAC computed for validation is `HMAC(secret, raw_body)` only [1](#0-0)  and `HmacValidator.validate` merely recomputes the signature over that signable string and compares it to the `hmac` header [4](#0-3) .

`Registry.process` raises only if the body's HMAC is invalid, then immediately builds `WebhookMetadata` using `request.shop` (and other headers) as ground truth to route the event to the host application's handler [2](#0-1) . Because `shop-domain` is never part of the signed bytes, any holder of one *validly-signed* body+HMAC pair for their own tenant (which every merchant naturally receives once they install the app and Shopify delivers webhooks to their endpoint) can replay that exact body/HMAC to the same webhook endpoint while substituting an arbitrary `shop-domain` header value. The signature check still passes — it only ever checked the body — but the host app will process the event as if it originated from the attacker-chosen shop.

This is the same bug class as the referenced report: a value used to authorize/attribute an action (`shop`, here analogous to the oracle price side used for fee direction) is decoupled from the value actually covered by the security check (the HMAC, analogous to using the wrong price side for verification vs. computation). Here the mismatch is between "bytes verified" (body) and "identity acted on" (shop-domain header).

### Impact Explanation
An attacker who is a legitimate, unprivileged merchant on their own shop (Shop A) can forge webhook deliveries that the host application will attribute to a different tenant (Shop B) merely by replaying a genuinely-signed body under a spoofed `shop-domain` header. Since host applications built on this SDK use `WebhookMetadata#shop` to select which tenant's data/session to update, this enables cross-tenant data injection/corruption — satisfying the "cross-tenant access" Critical impact category, since one tenant's traffic can be attributed to and processed against another tenant's records without ever compromising Shop B's credentials.

### Likelihood Explanation
Likelihood is elevated because the prerequisite (having one legitimately-signed webhook body from your own shop) is trivially available to any merchant who installs the app — no secret leakage, MITM, or privileged access to Shopify's systems is required, only ordinary use of the app as the attacker's own tenant, then a direct HTTP POST to the app's public webhook endpoint with a modified `shop-domain` header.

### Recommendation
Include the `shop-domain`, `topic`, `api-version`, and `webhook-id` headers as part of the signed material used for verification (or independently authenticate the shop via a signed, tenant-bound source such as a session lookup keyed by a value that is itself covered by the HMAC), so that the value the HMAC certifies matches the value the application acts on. At minimum, `to_signable_string` should incorporate the `shop` header so that spoofing it invalidates the signature.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a webhook (e.g. `orders/create`). Shopify delivers a request with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid-hmac-of-body>`, and some JSON body `B`.
2. Attacker captures this legitimately-received body `B` and its valid `hmac`.
3. Attacker POSTs the same body `B` and same `hmac` header to the app's webhook endpoint, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
4. `HmacValidator.validate` recomputes the signature over `B` only [1](#0-0)  — validation succeeds because the body is unchanged.
5. `Registry.process` invokes the handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: B, ...)` [5](#0-4) , causing the host application to process attacker-controlled event data as though it came from the victim shop.
