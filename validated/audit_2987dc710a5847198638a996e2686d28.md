## #Vulnerability found

### Title
Escrow credited from unmeasured pre-sweep balance instead of actual tokens received, allowing insolvent/unbacked escrow accounting - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
In the Tron variant of `IntentGatewayV2.placeOrder`, when an order uses a `predispatch` call, the escrow ledger `_orders[commitment][token]` is credited using the *requested* (fee-adjusted) input amount computed from a balance snapshot taken **before** the actual token sweep is executed, instead of the amount the gateway actually received after the sweep. This is the same root-cause pattern as the referenced Tokemak `flashRebalance` bug: crediting an internal accounting value from an unmeasured/assumed amount rather than the true post-transfer delta.

### Finding Description
In `placeOrder`'s predispatch branch, the contract:
1. Executes the user-supplied predispatch call via the external `dispatcher`.
2. Reads `balance = IERC20(token).balanceOf(dispatcher)` (or `dispatcher`'s native balance) — a snapshot taken **before** the sweep transfer occurs.
3. Emits `DustCollected` and, critically, credits escrow with `_orders[commitment][token] += reducedInputs[i].amount` using this pre-sweep balance/requested amount.
4. Only afterward does it call `ICallDispatcher(dispatcher).dispatch(abi.encode(transferCalls))` to actually move tokens from `dispatcher` to `address(this)`. [1](#0-0) 

There is no post-sweep verification that `address(this)`'s balance actually increased by the credited amount — unlike the mainline EVM `IntentGatewayV2.sol`, which explicitly snapshots `balancesBefore[i]` and computes `received = balanceOf(this) - balancesBefore[i]` after the sweep, then uses that measured `received` value (not the requested amount) to set `order.inputs[i].amount` before crediting escrow: [2](#0-1) 

Because the Tron contract never re-measures the gateway's actual balance after `dispatch(transferCalls)`, any token whose transfer to the gateway yields less than the pre-sweep `balance` (fee-on-transfer tokens, tokens with hooks that can siphon value, or a predispatch call/dispatcher path that does not deliver the full swept amount) results in `_orders[commitment][token]` recording more escrowed tokens than the gateway actually holds.

### Impact Explanation
The escrow map `_orders` backs subsequent `fillOrder` releases and `cancelOrder` refunds for every order sharing that token. If the credited amount exceeds the tokens actually transferred in:
- The gateway's aggregate escrow liabilities for that token exceed its real balance (unbacked/insolvent accounting).
- Later, legitimate `fillOrder`/`cancelOrder` calls for *other, unrelated* orders using the same token can revert with insufficient balance (denial of service), or a race to withdraw first can let one party drain tokens that were meant to back another user's escrow (loss of funds for the user whose order can no longer be honored).

This satisfies "permanent freezing of funds" / "unauthorized draining of another order's escrow" impact bar, reached via a single unprivileged `placeOrder` call with a predispatch call routed through a token that doesn't deliver the full swept balance to the gateway.

### Likelihood Explanation
Any user can call `placeOrder` with a `predispatch.call` and `predispatch.assets` populated, controlling which token/dispatcher call is used. Using a fee-on-transfer ERC20 as the input token (a scenario the mainline EVM contract explicitly guards against, per its own comment: "For fee-on-transfer tokens, the gateway receives less than the requested amount") is sufficient to trigger the discrepancy — no special privileges or governance access are required.

### Recommendation
Mirror the mainline EVM implementation: snapshot the gateway's own balance (`address(this)`) before executing `dispatch(transferCalls)`, execute the sweep, then compute `received = balanceOf(this) - balanceBefore` (or native balance delta) and use that measured `received` value (after protocol fee reduction) to credit `_orders[commitment][token]`, instead of crediting from the pre-sweep dispatcher balance / requested amount.

### Proof of Concept
1. Attacker deploys/uses a fee-on-transfer ERC20 `FOT` (e.g., 5% fee on transfer) as `order.inputs[0].token`, with a `predispatch.call` that simply no-ops or performs a benign dispatch, and `predispatch.assets` funding `dispatcher` with `FOT`.
2. `placeOrder` reads `balance = FOT.balanceOf(dispatcher)` == full pre-fee amount, and credits `_orders[commitment][FOT] += reducedInputs[0].amount` based on that full amount. [3](#0-2) 
3. `dispatch(transferCalls)` then executes `FOT.transfer(address(this), balance)`, which — being fee-on-transfer — delivers only `balance * 0.95` to the gateway.
4. `_orders[commitment][FOT]` now overstates the gateway's real `FOT` holdings by 5% of every such order's amount.
5. When enough such orders accumulate (or a single large one), a subsequent `fillOrder`/`cancelOrder` for a different, legitimately-funded `FOT` order reverts (DoS) because the real token balance is insufficient to cover all recorded escrow entries, or an attacker positions to withdraw first and capture tokens belonging to another user's escrow.
