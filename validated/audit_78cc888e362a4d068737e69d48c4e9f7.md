### Title
Webhook `shop-domain` header is trusted by `ShopifyAPI::Webhooks::Registry.process` without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC of the raw request body, then hands the caller-supplied `shop-domain` header straight to the app's handler as the identity of the shop the event belongs to. The `shop` field is never part of the signed material, so its value is fully attacker-controlled while still being accepted as "verified".

### Finding Description
`Registry.process` performs exactly one authenticity check before dispatching to the app's handler: [1](#0-0) 

The check is `Utils::HmacValidator.validate(request)`, which computes an HMAC over `to_signable_string`. For `Webhooks::Request`, that signable string is defined as only the raw HTTP body: [2](#0-1) 

The `shop` accessor, however, is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header, which is not part of `to_signable_string` and therefore not covered by the HMAC at all: [3](#0-2) 

`HmacValidator.validate` / `validate_signature` only ever look at `verifiable_query.hmac` and `verifiable_query.to_signable_string`, never at any shop identifier: [4](#0-3) 

After this single check passes, `Registry.process` builds `WebhookMetadata` directly from the unauthenticated `request.shop` and dispatches it to the app's handler: [5](#0-4) 

Because a single Shopify app has one `client_secret` shared across every shop that has installed it, the body-only HMAC computed with that secret is valid for a payload/signature pair regardless of which shop it actually came from. An attacker who has installed the app on their own (attacker-controlled) shop receives genuine `raw_body` + `hmac-sha256` pairs signed with the app's secret. They can then replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `Utils::HmacValidator.validate` still succeeds (it never looked at the shop header), and `Registry.process` forwards `shop: <victim-domain>` to the app's handler as if Shopify had reported this event for the victim shop.

This is exactly the "field acted on but not covered by the HMAC" identity-binding gap: the binding the gem implicitly claims to provide — `shop header == the shop whose secret produced the HMAC` — does not actually hold, since `shop` is excluded from the signed bytes entirely.

### Impact Explanation
Any host application that uses `data.shop` from `WebhookMetadata` (exactly as shown in the gem's own documentation example, `docs/usage/webhooks.md`) to look up the tenant/session record and apply the webhook body to it will apply attacker-chosen data to a victim shop's record. For mandatory compliance topics like `customers/redact`, `shop/redact`, or for lifecycle topics like `app/uninstalled`, an attacker-controlled body can be attributed to and acted on for a shop the attacker does not own, i.e., a cross-tenant write. This satisfies the cross-tenant-access impact category, since the only per-tenant field returned by this gem's webhook-processing API is forgeable without ever touching the target shop's credentials.

### Likelihood Explanation
Exploitation only requires the attacker to install the target app on their own shop (a normal, unprivileged action for any Shopify merchant/developer) in order to obtain valid `raw_body`/`hmac-sha256` pairs, and then send an HTTP POST to the app's public webhook endpoint with a forged `shop-domain` header. No access to the app's `client_secret`, to the victim's access token, or to Shopify infrastructure is required, and no rate limiting or other Shopify-side control prevents an attacker from POSTing directly to the app's own endpoint outside Shopify's delivery system.

### Recommendation
Bind the shop identity into the authenticity check instead of trusting an unsigned header:
- Require and use `Auth::Session` state for the shop parsed from a signed source (e.g., the JWT/OAuth-derived session store) to confirm the app has actually installed/registered a webhook for that shop, or
- Provide the caller with an explicit way to assert/verify the expected shop (e.g., checking `request.shop` against the shop registered when `register`/`register_all` was called for that topic) before dispatching to the handler in `Registry.process`.
- At minimum, document loudly in `Registry.process`/`docs/usage/webhooks.md` that `data.shop` is not part of the signed payload and must be independently validated by the host app against its own list of installed shops before being trusted.

### Proof of Concept
1. Attacker signs up for the target Shopify app on their own store `attacker.myshopify.com`, completing a normal OAuth install.
2. Shopify sends the attacker's app endpoint a legitimate webhook, e.g. `orders/create`, with headers:
   - `x-shopify-shop-domain: attacker.myshopify.com`
   - `x-shopify-hmac-sha256: <valid HMAC of raw_body computed with the app's client_secret>`
   - raw body: `{"id":1,...}`
3. Attacker captures this exact `raw_body` and `x-shopify-hmac-sha256` value.
4. Attacker crafts a new HTTP POST to the same app webhook endpoint, using the identical `raw_body` and `x-shopify-hmac-sha256`, but replaces the header with `x-shopify-shop-domain: victim.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` parses this, `Utils::HmacValidator.validate` succeeds because the check only hashes `raw_body`, and `Registry.process` invokes the app's handler with `WebhookMetadata.new(..., shop: "victim.myshopify.com", body: <attacker-controlled JSON>, ...)`, causing the host app to process attacker data attributed to the victim's tenant.
