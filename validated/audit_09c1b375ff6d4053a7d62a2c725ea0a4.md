### Title
Webhook `shop-domain` header is trusted for tenant identity without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable signature only over the raw request body, while the `shop-domain` header — used downstream as the tenant identity for dispatching webhook data — is read straight from unauthenticated headers. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then hands `request.shop` to the handler without ever binding it to the signature, breaking the equality `shop authenticated == shop the data is attributed to`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, `#api_version`, and `#webhook_id` are all read from HTTP headers that are never part of that signable string: [2](#0-1) 

`Utils::HmacValidator.validate` only recomputes and compares the HMAC over `verifiable_query.to_signable_string` (i.e. the body) against `verifiable_query.hmac` — it never touches `shop`: [3](#0-2) 

`Registry.process` checks the HMAC and then constructs `WebhookMetadata` using `request.shop` taken directly from the unauthenticated header, passing it to the app's handler as the tenant identity: [4](#0-3) 

Because the same `client_secret`/`api_secret_key` is shared by the app across all of its installed shops, a valid `(raw_body, hmac)` pair generated for one shop's webhook remains cryptographically valid when replayed with a different `shop-domain` header. The gem gives the host app no way to detect this substitution — `process` reports the webhook as HMAC-valid and forwards the attacker-chosen `shop` to the handler as if it were authenticated.

This is the exact identity-binding break the report's bug class targets: a field ("shop-domain") that is *acted on* (used as the tenant key for the handler) but *not covered by the HMAC*.

### Impact Explanation
Any user who is themselves a legitimate merchant of the app (an "unprivileged internet user" with respect to other tenants) can capture one of their own genuine webhook deliveries — raw body plus its valid `hmac-sha256` header — and replay it to the app's public webhook endpoint with the `shopify-shop-domain` (or `x-shopify-shop-domain`) header swapped to any other shop domain, including shops they don't control. `ShopifyAPI::Webhooks::Registry.process` will accept the request as authentic (HMAC check passes, since only the body is signed) and invoke the host app's handler with the forged `shop` value. Any host application built on this gem's stated contract — "the webhook is authentic if `HmacValidator.validate` succeeds" — will process data (installs/uninstalls, order updates, GDPR requests, etc.) under the wrong tenant's identity. This is a cross-tenant access/data-integrity break attributable to the gem's own webhook-processing API, not to host-app misuse.

### Likelihood Explanation
No secret material is required beyond something the attacker legitimately possesses (their own valid webhook deliveries for their own shop), and the app's webhook endpoint is by design internet-reachable. The only "skill" required is capturing one legitimate webhook and replaying it with an edited header — trivial with any HTTP proxy/tool. This is fully reachable through the gem's own documented `Registry.process` flow.

### Recommendation
- **Short term:** Include the `shop-domain` (and ideally `topic`, `webhook-id`, `api-version`) header values in the HMAC signable string in `ShopifyAPI::Webhooks::Request#to_signable_string`, matching whatever the actual Shopify signing scheme covers, or reject/re-verify the shop against session/tenant storage the host app already has for that specific webhook subscription before dispatch.
- **Long term:** Document explicitly, at the `Registry.process` and `Request` level, exactly which fields are and are not covered by the HMAC, so host apps cannot mistakenly treat unauthenticated header values (like `shop`) as verified tenant identity.

### Proof of Concept
```ruby
# Attacker owns/controls shop "attacker-shop.myshopify.com" and has installed the app,
# so they legitimately receive a real webhook with a valid HMAC for their own shop:
raw_body = '{"id":123,"note":"legit order for attacker-shop"}'
valid_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), app_client_secret, raw_body)
valid_hmac_b64 = Base64.encode64(valid_hmac)

# Attacker replays the SAME body+hmac but swaps the shop-domain header
# to a victim shop they do not control:
forged_headers = {
  "shopify-topic"        => "orders/create",
  "shopify-hmac-sha256"  => valid_hmac_b64,
  "shopify-shop-domain"  => "victim-shop.myshopify.com", # <-- forged, unauthenticated
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

# This passes HMAC validation because only raw_body is signed:
ShopifyAPI::Webhooks::Registry.process(request)
# => handler.handle(data: WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", ...))
# The host app's handler now processes attacker-controlled data attributed to "victim-shop".
```

          end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
