Based on the analysis, I found a concrete identity-binding gap in the webhook verification path.

### Title
Webhook `shop-domain` (and `topic`/`webhook_id`/`api_version`) header is trusted without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable signable string from the raw body only, while the shop attribution (`shop-domain` header) and other metadata (`topic`, `webhook_id`, `api_version`) are read from unauthenticated HTTP headers and handed to the app's webhook handler as trusted, verified data.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate` computes the signature exclusively over `to_signable_string` and compares it against the `hmac-sha256` header: [2](#0-1) 

`Registry.process` gates only on this HMAC check, then builds `WebhookMetadata` directly from the request's header-derived accessors (`request.topic`, `request.shop`, `request.webhook_id`, `request.api_version`) and hands them to the app's handler as verified data: [3](#0-2) 

`shop`, `topic`, `webhook_id`, and `api_version` are all sourced from raw HTTP headers, none of which participate in the HMAC computation: [4](#0-3) 

The identity binding that should hold is: `shop header == shop cryptographically bound to the signed payload`. Instead the gem only proves "these raw bytes were HMAC-signed with our `api_secret_key`" — it does not prove "this payload belongs to the shop named in the `shop-domain` header." Any request bearing a raw body whose HMAC matches (i.e., a genuine webhook body from *any* shop under the same app, replayed by a merchant/attacker who received it) can have its `shop-domain`, `topic`, `webhook_id`, or `api_version` header freely substituted, and `Registry.process` will pass the forged values straight through to the host app's handler as though Shopify vouched for them.

The gem's own documentation instructs the host app to key downstream side effects directly off `data.shop`, reinforcing that this field is expected to be trusted once `process` succeeds: [5](#0-4) 

### Impact Explanation
A user or party who legitimately receives real, HMAC-valid webhooks for one shop under an app (e.g., a merchant installing the app, or any actor able to capture a genuine webhook delivery) can replay the same raw body with a different `x-shopify-shop-domain` header value to the app's webhook endpoint. Because `HmacValidator` never binds the header to the signature, `Registry.process` accepts it as valid and calls the handler with attacker-chosen `shop`. Any host app that uses `data.shop` (as the gem's own docs recommend) to look up shop-scoped records, tokens, or to attribute the webhook event will attribute/act on the wrong tenant — a cross-tenant data-integrity/confidentiality break driven entirely by this gem's verification contract.

### Likelihood Explanation
Likelihood is constrained by the need for the attacker to first obtain one genuine, HMAC-valid webhook raw body under the target app (readily available to any merchant using the app, or anyone able to observe a webhook delivery, e.g. from their own store), after which crafting a forged HTTP POST with a different `shop-domain` header is trivial for an unprivileged actor with network access to the webhook endpoint - no `api_secret_key` or access token needed.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, `webhook_id`, `api_version`) in the signable string used for HMAC verification, or otherwise cryptographically bind them to the payload, so that `Registry.process` cannot be tricked into re-labelling a genuine webhook body with attacker-controlled shop/topic/version metadata.

### Proof of Concept
1. Attacker (a real merchant of the app, shop A) receives a genuine webhook: raw body `B`, header `x-shopify-hmac-sha256: H` (valid HMAC over `B` with the app's `api_secret_key`), header `x-shopify-shop-domain: shop-a.myshopify.com`.
2. Attacker POSTs to the app's webhook endpoint with the same body `B` and same `H`, but header `x-shopify-shop-domain: shop-b.myshopify.com` (a victim shop).
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...shop-domain: "shop-b.myshopify.com", hmac-sha256: H...})` is constructed.
4. `HmacValidator.validate(request)` succeeds because it only recomputes HMAC over `B`, which still matches `H` — see: [6](#0-5) 
5. `Registry.process` proceeds and invokes the handler with `shop: "shop-b.myshopify.com"`, even though the payload never originated from Shopify for shop B — see: [3](#0-2)
