### Title
Webhook shop identity spoofable because HMAC only covers the request body, not the `shop-domain` header - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` extracts the `shop` (and `topic`, `webhook_id`, `api_version`) fields directly from unauthenticated HTTP headers, while the HMAC signature that `Registry.process` validates is computed only over the raw request body (`to_signable_string` returns `@raw_body`). This breaks the binding "shop authenticated == shop acted upon": the HMAC proves the *body* came from Shopify's signing key, but it says nothing about which shop the webhook headers claim to be for.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Webhooks::Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cross-check against the HMAC: [2](#0-1) 

`Registry.process` validates the HMAC and then hands `request.shop` straight to the handler as trusted identity data: [3](#0-2) 

Because the signature is computed over the body only, and the `shop`/`topic`/`webhook_id` headers are excluded from `to_signable_string`, an attacker who has ever received/observed one legitimate Shopify webhook delivery (e.g. for their own shop, or a captured POST with body+HMAC) can replay the exact same body/HMAC pair while substituting the `x-shopify-shop-domain` header for a different shop domain. `OpenSSL.secure_compare` in `HmacValidator.validate_signature` will still pass because the signature check never inspects the header value: [4](#0-3) 

This exactly matches the analog class called out in the rules: "a field acted on but not covered by the HMAC." The `shop` field is acted upon (passed to `WebhookMetadata` and consumed by the host application's handler for data lookups/writes) but is not bound by the cryptographic signature.

### Impact Explanation
Any host application that follows this gem's documented pattern — trusting `WebhookMetadata#shop` (derived from `Request#shop`) as the authenticated tenant identifier once `Registry.process` succeeds — is exposed to cross-tenant data confusion: a webhook that was legitimately signed for shop A's payload can be delivered while claiming to originate from shop B, causing the app to write/update/notify against the wrong tenant's records. This is a cross-tenant boundary violation, matching the "Critical - cross-tenant access" impact bucket defined in scope.

### Likelihood Explanation
Exploitation requires the attacker to control or replay an HTTP POST to the app's public webhook endpoint with an already-valid (body, HMAC) pair — no `api_secret_key` or access token is needed, since the signature only binds the body, and the header can be freely rewritten by anyone able to send the request (the endpoint is a plain public webhook receiver). The main precondition is possessing one valid body/HMAC pair, which is plausible for an app owner/merchant that installed the app on their own store and receives their own legitimate webhooks (an "unprivileged internet user" with respect to other tenants). Likelihood is moderate: it requires knowledge of the internal architecture and one captured webhook, but no secret material.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the HMAC-signed payload verification, or otherwise validate the `shop-domain` header against known/registered shops (e.g., compare it against a shop this app installed with an offline session, and/or verify the webhook_id was actually registered for that shop) before invoking the handler. At minimum, document clearly that `WebhookMetadata#shop` is unauthenticated header data and must be independently verified by the host application before being trusted as a tenant identifier.

### Proof of Concept
1. App receives a legitimate Shopify webhook for `shop-a.myshopify.com` with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(secret, B)`.
2. Attacker (who owns/operates `shop-a` and thus legitimately received this webhook) resends the identical body `B` and signature `H`, but sets `x-shopify-shop-domain: shop-b.myshopify.com`.
3. `HmacValidator.validate` succeeds because it only re-computes the HMAC over `B` (`to_signable_string` = `@raw_body`): [5](#0-4) 
4. `Registry.process` calls the handler with `WebhookMetadata.new(... shop: request.shop ...)` where `request.shop` now reports `shop-b.myshopify.com` even though the signed payload was never authorized for that shop: [6](#0-5) 
5. Any host logic keyed off `data.shop` (e.g., "update order status for this shop") now operates on the wrong tenant.
