## Title
Webhook shop identity not covered by HMAC — cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` value from the unauthenticated `shopify-shop-domain` HTTP header, while the HMAC that `HmacValidator` checks only signs the raw request body. `ShopifyAPI::Webhooks::Registry.process` verifies the HMAC and then hands the unauthenticated `shop` value straight to the caller's webhook handler, so signature validity is not bound to shop identity.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` and `#hmac` are read independently from headers, with `shop` never entering the signed string: [2](#0-1) 

`HmacValidator.validate` computes/compares the signature purely from `to_signable_string` (the body), never touching `shop`: [3](#0-2) 

`Registry.process` validates the HMAC of the whole request, then dispatches to the handler using `request.shop` taken directly from the header, without any cross-check that this shop is the one the signed body actually belongs to: [4](#0-3) 

Because a single app's webhooks for *every* installed shop are signed with the same `Context.api_secret_key`/`client_secret`, a legitimate but malicious merchant who installs the app on their own store receives real `(raw_body, hmac)` pairs that pass `HmacValidator.validate` for any shop, not just their own. They can replay that exact body+HMAC to the app's public webhook endpoint while substituting the `shopify-shop-domain` (or `x-shopify-shop-domain`) header with a victim shop's domain. `HmacValidator.validate` still returns `true` (it never looks at the shop header), so `Registry.process` calls the handler with `shop: <victim shop>` and the attacker-controlled body — i.e., the equality the code implicitly relies on, `hmac-authenticated shop == shop acted upon`, does not hold; only `hmac-authenticated body == body acted upon` is actually enforced.

### Impact Explanation
Any host application that trusts `WebhookMetadata`/`request.shop` as the tenant key (a documented, intended usage of this gem's webhook API) can be made to apply another merchant's webhook body against the wrong shop's identity — a cross-tenant confused-deputy condition purely through this gem's own `Request`/`HmacValidator`/`Registry` code, not through host misuse of an undocumented API.

### Likelihood Explanation
Exploitation only requires the attacker to be a legitimate (even trial) installer of the target app — obtaining one valid `(body, hmac)` pair from their own store's webhook traffic — and the ability to send an HTTP request to the app's public webhook endpoint with a forged `shop-domain` header. No `api_secret_key`, access token, or privileged access is needed.

### Recommendation
Include the shop identity (and/or a per-shop secret/session-bound value) inside the HMAC-signable material, or have `Registry.process`/consumers independently authenticate the `shop` value (e.g., against a value derived from a per-shop signing key or session store) instead of trusting the raw header once the body's HMAC checks out.

### Proof of Concept
1. Install the app on `attacker.myshopify.com`; capture a legitimate webhook POST, e.g. body `{"id":1}` with header `shopify-hmac-sha256: <valid hmac of body>` and `shopify-shop-domain: attacker.myshopify.com`.
2. Resend the identical body and HMAC header to the app's webhook endpoint, replacing `shopify-shop-domain` with `victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses this into `shop == "victim.myshopify.com"`, `hmac` unchanged.
4. `ShopifyAPI::Utils::HmacValidator.validate(request)` returns `true` because it only checks `raw_body` against the HMAC.
5. `ShopifyAPI::Webhooks::Registry.process` invokes the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: <attacker's body>, ...)`, so the host application processes attacker-controlled data under the victim's tenant identity.
