### Title
HTTP Trigger requests are authorized before rate limiting is enforced, allowing unlimited unauthenticated JWT/authorized-key brute-force attempts against the CRE Gateway - ([File: core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go])

### Summary
`httpTriggerHandler.HandleUserTriggerRequest` performs JWT/authorized-key verification (`authorizeRequest`) before invoking the per-workflow rate limiter (`checkRateLimit`). Any request that fails authorization returns immediately and never reaches the rate-limit check, so failed authentication attempts are not throttled — the same root cause pattern as the reported OpenClaw bug (rate limiting applied only after auth succeeds).

### Finding Description
`HandleUserTriggerRequest` executes the following steps in order:
1. `validatedTriggerRequest`
2. `resolveWorkflowID`
3. `authorizeRequest` (verifies JWT signature/authorized key via `h.workflowMetadataHandler.Authorize`)
4. `checkRateLimit` (only reached if authorization succeeded) [1](#0-0) 

`authorizeRequest` calls `workflowMetadataHandler.Authorize` and returns an error immediately on failure, well before `checkRateLimit` is ever invoked: [2](#0-1) 

`checkRateLimit` — the per-workflow-owner throttle intended to bound abuse — is a separate, later step gated on prior successful authorization: [3](#0-2) 

Because rate limiting is scoped per resolved `workflowID`/`workflowOwner` (`h.userRateLimiter.AllowErr(ctx)` keyed by CRE context), and it is only reached after `authorizeRequest` succeeds, an attacker submitting repeated requests with invalid JWT signatures or unauthorized keys for a known/guessed `workflowID` triggers unlimited `authorizeRequest` failures with no throttling at this layer. This mirrors the GHSA-5m9r-p9g7-679c pattern exactly: pre-auth-success traffic bypasses the rate limiter that is meant to slow down credential-guessing.

### Impact Explanation
This weakens brute-force resistance against the CRE Gateway's HTTP Trigger authorization scheme (ECDSA/JWT-based authorized keys, per README "JWT Verification: All trigger requests must include valid JWT tokens" and "Workflow-Scoped Auth"). An unprivileged, unauthenticated client can send unlimited forged/invalid JWT trigger requests for a target `workflowID` without being throttled by the workflow-level rate limiter, since that limiter only fires after authorization passes. This increases the practical feasibility of forging trigger requests or exhausting gateway/DON resources by flooding authorization checks, and is consistent with CWE-307 (Improper Restriction of Excessive Authentication Attempts).

Note: whether an outer, request-agnostic limiter (e.g., `globalNodeRateLimiter`/`mtlsRequestRateLimiter` on `gatewayHandler`) applies to inbound user trigger requests before dispatch could not be conclusively confirmed from the available code — those limiters appeared scoped to node-originated/mTLS traffic rather than to `HandleUserTriggerRequest`'s user-request path specifically.

### Likelihood Explanation
The `workflowID` is a public, discoverable identifier (used in workflow selectors) and the endpoint is reachable directly from unprivileged/unauthenticated clients as documented ("Receiving inbound HTTP trigger requests"). No CAPTCHA or IP-based control is shown ahead of `authorizeRequest`. This makes the bypass straightforward to exploit for anyone able to reach the Gateway's HTTP trigger endpoint.

### Recommendation
Reorder `HandleUserTriggerRequest` so `checkRateLimit` (or an equivalent limiter keyed by request source/workflow) executes before `authorizeRequest`, ensuring both successful and failed authorization attempts consume rate-limit budget. Alternatively, add a pre-authorization rate limiter keyed on `workflowID`/source IP that always increments regardless of authorization outcome, mirroring the fix pattern in the referenced advisory (rate limit before auth success is required).

### Proof of Concept
1. Identify or guess a valid `workflowID` registered with the Gateway (workflow IDs are used in public selectors).
2. Repeatedly call `HandleUserTriggerRequest` (i.e., send crafted `MethodWorkflowExecute` JSON-RPC requests) with an invalid/forged JWT `Auth` header for that `workflowID`.
3. Observe that each request fails at `authorizeRequest` (per [2](#0-1) ) and returns before `checkRateLimit` is invoked, so no `429`/`ErrLimitExceeded` is ever produced for the guessing attempts — unlike the legitimate rate-limit test in `TestHttpTriggerHandler_HandleUserTriggerRequest_RateLimiting`, which only exercises the limiter on the success path.

func (h *httpTriggerHandler) HandleUserTriggerRequest(ctx context.Context, req *jsonrpc.Request[json.RawMessage], callback handlers.Callback, requestStartTime time.Time) error {
	triggerReq, err := h.validatedTriggerRequest(ctx, req, callback)
	if err != nil {
		return err
	}

	workflowID, err := h.resolveWorkflowID(ctx, triggerReq, req.ID, callback)
	if err != nil {
		return err
	}

	key, err := h.authorizeRequest(ctx, workflowID, req, callback)
	if err != nil {
		return err
	}

	if err = h.checkRateLimit(ctx, workflowID, req.ID, callback); err != nil {
		return err
	}

func (h *httpTriggerHandler) authorizeRequest(ctx context.Context, workflowID string, req *jsonrpc.Request[json.RawMessage], callback handlers.Callback) (*gateway_common.AuthorizedKey, error) {
	h.lggr.Debugw("authorizing request", "workflowID", workflowID, "requestID", req.ID)
	key, err := h.workflowMetadataHandler.Authorize(workflowID, req.Auth, req)
	if err != nil {
		h.handleUserError(ctx, req.ID, jsonrpc.ErrInvalidRequest, "Auth failure: "+err.Error(), callback)
		return nil, errors.Join(errors.New("auth failure"), err)
	}
	return key, nil
}

func (h *httpTriggerHandler) checkRateLimit(ctx context.Context, workflowID, requestID string, callback handlers.Callback) error {
	workflowRef, found := h.workflowMetadataHandler.GetWorkflowReference(workflowID)
	if !found {
		h.handleUserError(ctx, requestID, jsonrpc.ErrInvalidRequest, "workflow reference not found", callback)
		return errors.New("workflow reference not found")
	}

	orgID := h.resolveOrgID(ctx, workflowRef.workflowOwner)
	ctx = contexts.WithCRE(ctx, contexts.CRE{Owner: workflowRef.workflowOwner, Org: orgID, Workflow: workflowID})
	if err := h.userRateLimiter.AllowErr(ctx); err != nil {
		lggr := logger.With(h.lggr, platform.KeyWorkflowID, workflowID, platform.KeyWorkflowOwner, workflowRef.workflowOwner, "requestID", requestID, "err", err)
		if errLimited, ok := errors.AsType[limits.ErrorRateLimited](err); ok {
			switch errLimited.Scope {
			case settings.ScopeWorkflow:
				lggr.Errorf("failed to start execution: per workflow rate limit exceeded")
				h.metrics.IncrementWorkflowThrottled(ctx, h.lggr)
			default:
				lggr.Errorf("failed to start execution: unexpected rate limit for scope %s", errLimited.Scope)
			}
			h.handleUserError(ctx, requestID, jsonrpc.ErrLimitExceeded, "rate limit exceeded", callback)
			return err
		}
		return fmt.Errorf("failed to check rate limit: %w", err)
	}
	return nil
}
