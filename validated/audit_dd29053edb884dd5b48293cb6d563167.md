### Title
Fresh re-read of `ignore_user_centric_signups` config mid-signup allows backend enrollment/uniqueness verification to be silently skipped, marking signups successful without confirmation - (File: `src/plans/mod.rs`)

### Summary
`do_signup` snapshots the orb `Config` once at the start of a signup (`self_serve`, `pcp_v3`, etc.), but a security-relevant flag, `ignore_user_centric_signups`, is instead re-fetched with a brand-new `orb.config.lock().await` call at the moment the enrollment decision is made, long after biometric capture and pipeline processing have completed [1](#0-0) . This mirrors the reported anchor-bAsset bug class: a config value that governs how a previously-computed, pending result (here, a completed biometric capture/pipeline) is finalized can change between the start and end of a single processing unit, because nothing pins the value used for the finalization decision to the value observed when the operation began.

### Finding Description
In `MasterPlan::do_signup`, the initial config snapshot is destructured at function entry [1](#0-0) . Several seconds to tens of seconds later — after QR scanning, biometric capture, the biometric pipeline, and (in the FOSS build) fraud detection have all run — the enrollment path is chosen with a fresh, independent lock acquisition: [2](#0-1) 

If `user_centric_signup` (attacker/app-influenced data coming from `qr_codes.user_data`, itself derived from `backend::user_status::request`) is `true` and the freshly-read `ignore_user_centric_signups` is `false`, the code **never calls `enroll_user`** — i.e., it never invokes `enroll_user::Plan::run`, which is the only path that calls `signup_post::request` and polls `signup_poll::request` for the backend's genuine `Completed`/`success:true` confirmation and duplicate/uniqueness detection [3](#0-2) . Instead, `debug_report.enrollment_status` and `result.success` are set to `Success` purely from the locally-derived `signup_reason == SignupReason::Normal` [4](#0-3) .

The `ignore_user_centric_signups` value used for this critical decision is not the value that was in effect when the signup began; it is whatever the shared `Arc<Mutex<Config>>` holds at that exact moment. That shared config is concurrently, periodically overwritten in the background by the observer broker, independent of any in-flight signup: [5](#0-4) [6](#0-5) 

This is structurally identical to the reported bug class: a config value that determines how an already-in-flight/pending unit of work is finalized is allowed to be swapped out mid-flight, and the finalization step reads the *new* value rather than the value used to start/authorize the operation, causing the outcome to be computed against a mismatched configuration state.

### Impact Explanation
When this path is taken, the orb marks the signup as fully successful and produces a self-custody/personal-custody package upload for the user without ever obtaining the backend's confirmation that the biometric enrollment was accepted as unique (i.e., without the backend's own duplicate/fraud detection during `signup_poll`). This can result in a misattributed or effectively "self-certified" signup being recorded as a successful, verified enrollment, since `result.success` and `debug_report.enrollment_status` are forced to `Success`/`Success` locally rather than being derived from the backend's authoritative response.

### Likelihood Explanation
`ignore_user_centric_signups` and `self_serve` are backend-controlled, remotely-updatable config values fetched roughly every `CONFIG_UPDATE_INTERVAL` [7](#0-6) , and `user_centric_signup` originates from `authenticated_app_data`/user-status data associated with the QR flow [8](#0-7) . Any timing window between the config value observed at `do_signup` start and the value read fresh at the enrollment-decision point (spanning the multi-second QR scan, capture, and pipeline phases) is sufficient to trigger the inconsistency; no special privileges beyond controlling the user-status/app response are required to set `user_centric_signup=true`.

### Recommendation
Capture `ignore_user_centric_signups` (and any other config values that gate the enrollment/finalization decision) in the same initial `Config` snapshot taken at the start of `do_signup`, and use that single, pinned snapshot for the entire signup lifecycle rather than re-locking `orb.config` for individual decision points. Alternatively, always require the backend `enroll_user` round-trip (`signup_post` + `signup_poll`) for final success determination, and treat `user_centric_signup`/`ignore_user_centric_signups` purely as a reporting/telemetry distinction rather than a bypass of the authoritative backend verification step.

### Proof of Concept
1. Backend serves a config with `ignore_user_centric_signups = true` (or the orb currently holds this value from a previous download).
2. A signup begins; `do_signup` takes its initial `Config` snapshot at line 497, which does not include `ignore_user_centric_signups`.
3. During the multi-second QR scan / biometric capture / biometric pipeline phases, the observer broker's periodic `config_update` downloads a fresh config where `ignore_user_centric_signups` has flipped to `false` [9](#0-8) .
4. The user-status response for this signup sets `user_centric_signup = true`.
5. At line 639, `orb.config.lock().await.ignore_user_centric_signups` now reads `false`, so the condition `user_centric_signup && !ignore_user_centric_signups` is `true`, and `enroll_user` (the real backend verification call) is skipped entirely; `result.success` is set based solely on the local `signup_reason`.
