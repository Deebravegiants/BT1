## Title
Webhook shop identity spoofing via HMAC that only covers the request body, not the `shop` field used for tenant routing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC over the raw body only, while the `shop` value used by `Registry.process` to route webhook data to the merchant's handler is taken from an unauthenticated header and is never covered by the signature check. This is the same bug class as the reported issue: a value that is acted upon (here, tenant identity) is not covered by the integrity check that is supposed to bind it, so an attacker who can produce (or replay) any validly-signed body can attach it to an arbitrary shop identity.

### Finding Description
`Utils::HmacValidator.validate` computes and compares the HMAC using `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` returns only the raw JSON body: [2](#0-1) 

But `shop` is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, which is not part of the signed bytes at all: [3](#0-2) 

`Registry.process` validates the HMAC over the body, then unconditionally forwards `request.shop` (the unauthenticated header value) to the app's webhook handler as the authenticated tenant identifier: [4](#0-3) 

The broken binding, expressed as an equality that the library implies but does not enforce:
`shop_bytes_covered_by_HMAC == shop_value_delivered_to_handler_as_tenant_identity`

In reality: `shop_bytes_covered_by_HMAC` is empty (the signature never touches `shop`), while `shop_value_delivered_to_handler_as_tenant_identity` is a fully attacker-controlled HTTP header. Since every shop installed on a given app shares the same `client_secret`/HMAC key, any party who can obtain one validly HMAC-signed webhook body (e.g., by installing the app on their own free development store and capturing/replaying one of their own legitimate webhook deliveries) can resend that exact body with the `x-shopify-shop-domain` header changed to point at a different, victim shop. `Registry.process` will pass HMAC validation (because the body is unchanged and correctly signed) and will invoke the handler with `WebhookMetadata.shop` set to the attacker-chosen value.

### Impact Explanation
`WebhookMetadata.shop` is the field host applications are expected to trust as the authenticated tenant identity for the webhook (per the gem's own webhook handling contract, mirroring how `Auth::Session#shop` and `JwtPayload#shop` are used elsewhere as the tenant key). Because this value can be forged independently of the signature, an attacker can cause tenant-data mixups/cross-tenant confusion in the host application's webhook processing logic (e.g., mandatory `customers/data_request`, `customers/redact`, `shop/redact` topics, or any other registered topic) — the exact "field acted on but not covered by the HMAC" pattern flagged in the reference report, here manifesting as a cross-tenant identity binding failure rather than a zero-mint accounting failure.

### Likelihood Explanation
Any unprivileged internet user can trivially create a free Shopify development store, install any app that uses this gem for webhook processing, and receive real, validly-signed webhook deliveries for their own shop. Replaying such a body with a modified `shop-domain` header requires no access token, `api_secret_key`, or privileged access to the target — only the ability to send an HTTP POST to the app's public webhook endpoint, which is by definition internet-reachable.

### Recommendation
Do not treat `Webhooks::Request#shop` as authenticated tenant identity unless it is cryptographically bound to the signed payload. At minimum, document/require host applications to independently correlate `request.shop` against a shop they already have a stored, previously-verified session for, and/or extend `to_signable_string` (or add a supplementary check) so that the `shop` header is verified consistently with how Shopify's own webhook delivery is expected to be validated, rejecting mismatches before invoking `handler.handle`.

### Proof of Concept
1. Attacker installs the target app on their own throwaway/development Shopify store (`attacker-shop.myshopify.com`) and triggers a registered webhook topic (e.g. `orders/create`), capturing the raw body `B` and the resulting valid `x-shopify-hmac-sha256` value `H` (valid because `H = HMAC(client_secret, B)` and `client_secret` is shared across all installs of the app).
2. Attacker sends a POST to the app's webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H` (unchanged, still valid), but `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` passes because it only checks `B` against `H`.
4. `Registry.process` in `lib/shopify_api/webhooks/registry.rb` calls the app's handler with `WebhookMetadata.shop == "victim-shop.myshopify.com"`, even though the body content actually originated from the attacker's own shop — demonstrating the shop identity was never bound to the signature that is supposed to authenticate the request.
