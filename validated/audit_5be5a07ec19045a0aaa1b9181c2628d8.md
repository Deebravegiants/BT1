## Analysis Result

### Title
Cross-account address disclosure to connected dApp origins — `getConnectedAccounts` ignores per-origin wallet-account scoping (File: `features/connected-origins/module/connections.js`)

### Summary
The external report describes accounting corruption because a value meant to be scoped/restricted (the `output` token) was never excluded from a broader aggregate (`balances()`), causing unintended data to bleed across a supposed boundary. The Hydra analog is in `features/connected-origins/module/connections.js`: a per-origin trust/connection record stores a `walletAccount` (and accepts, but silently drops, an `accounts` restriction), yet `getConnectedAccounts()` aggregates and returns addresses for **every enabled wallet account** in the wallet to any origin that is merely `isTrusted` for one asset, instead of scoping the result to the account(s) the user actually connected to that origin.

### Finding Description
`ConnectedOrigins#add` accepts a `walletAccount` field intended to record which wallet account a given origin/dApp was connected to [1](#0-0) . `#addNewItem` even declares an `accounts` parameter apparently meant to restrict the connection to specific accounts, but `add()` never forwards `accounts` to it — it is effectively dead/unused input, so no account-level restriction is ever persisted via this path [2](#0-1) .

The account address cache itself, `#getAccounts`, is built over **all** enabled wallet accounts, not scoped per origin: [3](#0-2) .

Critically, `getConnectedAccounts({ origin })` — the method exposed on the public API surface reachable by connected dApps — only checks the single boolean `isTrusted({ origin })` flag and then loops over **every key** of the shared `#connectedAccountsAtom` (i.e., every enabled wallet account in the entire wallet), filtering only the *asset fields* via `assetNames`, never filtering by `value.walletAccount` or any per-account allowlist: [4](#0-3) .

This is exposed directly to the RPC/API layer used by connected web origins: [5](#0-4) .

The root cause mirrors the report's bug class: a field that is supposed to gate/limit which entity's balance-like data is included (`walletAccount`/`accounts` here, `output`/`lpTokens` there) is not actually applied at the point of aggregation, so the returned set silently includes entities (other wallet accounts) that were never authorized for that trust boundary (the connected origin).

### Impact Explanation
Any origin that is trusted for even a single connected asset can retrieve the default addresses of **all** other enabled wallet accounts in the user's wallet via `getConnectedAccounts`, not just the account(s) the user explicitly connected. This is a cross-account privilege bleed across the dApp-origin trust boundary: it defeats the purpose of per-origin/per-account connection scoping and discloses account topology/addresses that the user did not consent to share with that origin, which can be used for deanonymization/linking of a user's accounts by a malicious or compromised dApp.

### Likelihood Explanation
Reachable by any web page/dApp already granted a normal "connect" trust relationship (a routine, low-privilege event, not an admin action) — the only precondition is `isTrusted({ origin })` being true for that origin, which is the standard state after a user approves a wallet connection request. No special privileges, admin action, or malicious node/operator behavior is required, satisfying the "unprivileged user/dApp" trust-boundary criterion.

### Recommendation
In `getConnectedAccounts`, filter `Object.keys(accounts)` down to the account(s) actually recorded on the origin's connection record (`value.walletAccount` and/or a properly persisted `accounts`/`assetNames`-scoped allowlist), rather than returning every entry in `#connectedAccountsAtom`. Additionally, wire the currently-dropped `accounts` parameter in `add()`/`#addNewItem` through to the stored connection object and enforce it, so per-origin account scoping is both recorded and honored.

### Proof of Concept
1. User connects Wallet Account A to `https://dapp.example` for asset `ethereum`, approving trust for that origin (`connectedOrigins.add({ origin: 'https://dapp.example', connectedAssetName: 'ethereum', walletAccount: 'A' })`).
2. `isTrusted({ origin: 'https://dapp.example' })` now returns `true`.
3. The dApp calls the exposed API `connectedOrigins.getConnectedAccounts({ origin: 'https://dapp.example' })`.
4. Per `getConnectedAccounts` (`connections.js:249-273`), the method loops over every key in `#connectedAccountsAtom`, which was populated for **all** enabled wallet accounts (`connections.js:108-121`), not just `walletAccount: 'A'`.
5. Result: the dApp receives ethereum addresses for Wallet Accounts B, C, D, etc., even though the user only ever connected Account A to it — no `walletAccount` filter is applied anywhere in this call path.

```javascript
  getConnectedAccounts = async ({ origin }) => {
    const isTrusted = await this.isTrusted({ origin })
    if (!isTrusted) return []

    const value = await this.#getOrigin({ origin })
    const assetNames = [value.connectedAssetName, ...(value.assetNames ?? [])].filter(
      (name, index, ary) => Boolean(name) && ary.indexOf(name) === index
    )

    const activeWalletAccount = await this.#activeWalletAccountAtom.get()
    const accounts = await this.#connectedAccountsAtom.get()

    const connectedAccounts = []
    for (const name of Object.keys(accounts)) {
      if (name === activeWalletAccount) continue
      connectedAccounts.push({ name, addresses: pick(accounts[name].addresses, assetNames) })
    }

    connectedAccounts.unshift({
      name: activeWalletAccount,
      addresses: pick(accounts[activeWalletAccount].addresses, assetNames),
    })

    return connectedAccounts
  }
```
