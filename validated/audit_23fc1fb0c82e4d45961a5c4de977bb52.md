### Title
Webhook signature verifies only the raw body, not the `shop-domain`/`topic` headers used for tenant routing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`Webhooks::Request` computes its HMAC-signable content from the raw body alone, while the `shop` and `topic` values used to route and attribute the webhook are read from unsigned HTTP headers. `Registry.process` trusts these header-derived values for tenant identification after validating only the body's HMAC, allowing a shop that legitimately receives its own valid webhooks to relabel them as belonging to another shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop` and `topic` — the values used as the tenant/routing identity — are pulled straight from HTTP headers that are never included in the signed content: [2](#0-1) 

`Registry.process` validates the request's HMAC (which only covers `@raw_body`) and then immediately trusts `request.shop` and `request.topic` — both header-derived and unsigned — to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

The binding that should hold is:
`shop_used_for_tenant_attribution == shop_covered_by_hmac`

Here, `shop_used_for_tenant_attribution = header["shopify-shop-domain"]` while `shop_covered_by_hmac` doesn't exist at all — the HMAC only covers the body bytes. This is the identity-binding analog to the report's root cause: a value trusted for an authorization/identity decision (`contributor` instead of `msg.sender` in the report; `shop`/`topic` header instead of a signed field here) is not the value that was actually authenticated.

### Impact Explanation
Any shop that has the app installed receives genuine webhooks from Shopify with a valid `hmac-sha256` header computed over the body using the app's `client_secret`. Because the signature never binds to the `shop-domain` or `topic` headers, that same shop (an unprivileged/malicious merchant, not the app operator, and without access to `client_secret`) can resend the identical raw body + hmac pair to the app's webhook endpoint while substituting a different `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header. Since `Utils::HmacValidator.validate` only checks the body signature, the forged headers pass validation, and the host app's handler executes with `shop` attributed to a victim tenant it was never intended for. Depending on what the handler does (e.g. `customers/redact`, `shop/redact`, order/customer data ingestion), this can result in cross-tenant data corruption, unauthorized state changes attributed to another merchant, or processing of one tenant's data under another tenant's record — a cross-tenant boundary violation.

### Likelihood Explanation
Any merchant that installs the app already receives valid signed webhooks for their own shop, giving them a ready supply of valid `(raw_body, hmac)` pairs without needing the `client_secret`. Forging the `shop-domain`/`topic` header on replay requires only basic HTTP tooling, no privileged credentials, TLS interception, or social engineering — this is directly reachable through the gem's documented `Webhooks::Registry.process` entry point.

### Recommendation
Bind the shop (and ideally the topic) into the signed content, or otherwise verify them independently of the unsigned headers:
- Update `Request#to_signable_string` to include the `shop-domain` (and `topic`) alongside the raw body so the HMAC covers the values used for tenant attribution, or
- Cross-check `request.shop` against the shop associated with the session/subscription that the webhook was registered for before dispatching to the handler, rejecting mismatches.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker.myshopify.com` and receives a legitimate webhook, capturing the raw body `B` and its valid `X-Shopify-Hmac-Sha256` header `H` (computed by Shopify over `B` using the app's secret).
2. Attacker POSTs the same `B` and `H` to the app's public webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com` (and optionally a different `X-Shopify-Topic`).
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes HMAC over `request.to_signable_string` (`= @raw_body = B`) — validation succeeds because `B`/`H` were never altered.
4. `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` is built using the attacker-controlled `shop`/`topic` headers, and the app's handler processes data as if it originated from `victim.myshopify.com`. [3](#0-2) [4](#0-3)

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
