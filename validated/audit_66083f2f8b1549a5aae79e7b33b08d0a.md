### Title
Webhook `shop-domain` (and `topic`/`webhook-id`/`api-version`) headers are not covered by the HMAC signature, allowing cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC verification performed in `Utils::HmacValidator.validate` binds only the payload bytes to the app's `client_secret` — it does not bind the `shop-domain`, `topic`, `webhook-id`, or `api-version` HTTP headers. Those header values are nonetheless trusted downstream and handed to the webhook handler as the shop identity for the event. This breaks the intended equality "shop that produced this HMAC == shop the handler acts on," enabling an attacker who controls one shop that has installed the app to relabel a legitimately-signed webhook as belonging to a different (victim) shop.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
only the `@raw_body` is signed. The `shop`, `topic`, `webhook_id`, and `api_version` accessors all come straight from HTTP headers, which are not covered by that signable string: [2](#0-1) 

`Utils::HmacValidator.validate` verifies the HMAC using `Context.api_secret_key` (the app's single client secret, shared by every shop that installs the app) over `verifiable_query.to_signable_string`: [3](#0-2) 

`Registry.process` only checks this HMAC before dispatching to the handler with the *unverified* `request.shop`, `request.topic`, and `request.webhook_id`: [4](#0-3) 

The resulting `WebhookMetadata` struct — which host applications use to identify which tenant/shop the event belongs to — carries the shop value directly from the unauthenticated header: [5](#0-4) 

Because the HMAC secret is the app's `client_secret`, identical for all shops using the app, a legitimately-signed webhook body captured for one shop (e.g., an app installer's own store) remains cryptographically valid when replayed with a *different* `x-shopify-shop-domain` (and/or `x-shopify-topic`/`x-shopify-webhook-id`) header, since none of these headers feed into the HMAC computation. The identity binding "HMAC valid for secret S ⇒ event genuinely originated from shop X" does not hold; it only proves "some shop using this app's secret produced this body."

### Impact Explanation
An unprivileged attacker who merely installs the app on their own shop (a normal, unprivileged action any merchant can take) can obtain a validly-signed webhook body/HMAC pair, then replay it against the app's webhook endpoint while substituting the victim shop's domain in the `x-shopify-shop-domain` header. `Registry.process` will pass HMAC verification and invoke the handler with `data.shop` set to the victim's domain. Any host application logic that trusts `WebhookMetadata#shop` to select/update per-tenant state (e.g., marking a subscription active, updating billing status, processing `customers/redact` or `shop/redact` compliance actions, or triggering `app/uninstalled` cleanup) can be tricked into performing actions attributed to a shop the attacker does not control — a cross-tenant impact within the meaning of the program's High/Critical categories.

### Likelihood Explanation
The attacker only needs to be able to install the app (or otherwise trigger any webhook topic delivered to them) to obtain one valid `(body, hmac)` pair signed with the shared `client_secret`; from there, forging the shop header requires no cryptographic material and no privileged access, control of TLS, or leaked secrets — only the ability to send an HTTP request to the app's public webhook endpoint with a body/HMAC pair captured from a genuine delivery to their own shop.

### Recommendation
Include the `shop-domain` header (and ideally `topic`/`webhook-id`/`api-version`) in the bytes that are HMAC-verified, e.g. by having `Request#to_signable_string` concatenate the canonicalized headers with the raw body before hashing, or by having `Registry.process` independently cross-check `request.shop` against the shop that the caller expects/has a stored session for before invoking the handler with the header-derived value.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com`, triggering a subscribed webhook topic (e.g., `orders/create`). The app's server sends a POST with body `B` and header `x-shopify-hmac-sha256: HMAC(secret, B)` and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker (who runs a proxy or otherwise intercepts inbound requests to their own webhook endpoint, or simply reuses a delivered webhook they can inspect) captures `(B, HMAC)`.
3. Attacker replays a POST to the app's public webhook endpoint with the same body `B` and same `x-shopify-hmac-sha256` header, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `HmacValidator.validate` recomputes `HMAC(secret, B)` — identical to the original — and returns `true`, since `to_signable_string` never included the shop header: [1](#0-0) 
5. `Registry.process` dispatches to the handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", ...)`: [4](#0-3) 
6. Any host-app logic keyed on `data.shop` now executes as if the event genuinely originated from `victim-shop.myshopify.com`.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
