### Title
Unaccounted dispatcher balance is credited as "received" input, letting an order absorb externally-donated/leftover tokens as escrow without a matching contribution - (File: evm/src/apps/IntentGatewayV2.sol)

### Summary
`IntentGatewayV2.placeOrder`'s predispatch path measures how much of an input token was "actually received" by taking a **full balance snapshot** of the shared, persistent `dispatcher` contract and sweeping its **entire balance** back to the gateway, then comparing the gateway's balance before/after to derive `received`. Because the swept amount is `IERC20(token).balanceOf(dispatcher)` (the dispatcher's whole balance) rather than a value strictly tied to this order's own transfer, any token that lands on the shared `dispatcher` address from an unrelated source — direct transfers, dust left over from a previous/failed predispatch call, or residual amounts from another user's order — is folded into the current order's `received` figure and, when it is enough to satisfy `requiredAmount`, the order's declared `order.inputs[i].amount` is accepted unmodified. This mirrors the APEDAO bug class: a contract mistakes an unrelated, unaccounted-for token transfer into a shared/pair-like contract for a legitimate operation (there: a "sell"; here: the user's own deposit), and later a privileged accounting step ("godead"/skim there; the escrow-crediting step here) consumes that mis-attributed balance.

### Finding Description
In the predispatch branch of `placeOrder`: [1](#0-0) 

- `balancesBefore[i]` is taken on `address(this)` (the gateway) — not on the `dispatcher`.
- The sweep amount transferred from `dispatcher` to the gateway is `balance = IERC20(token).balanceOf(dispatcher)`, i.e. the dispatcher's *entire* current balance for that token, gated only by `balance < requiredAmount` reverting (line 274-275: `evm/src/apps/IntentGatewayV2.sol:274-275`).
- After the sweep, `received = balanceOf(gateway)_after - balancesBefore[i]`. If `received > order.inputs[i].amount`, the excess is only emitted as a `DustCollected` event; **if `received <= order.inputs[i].amount`... actually if `received == order.inputs[i].amount`, `order.inputs[i].amount` is left untouched** (the `else` branch only fires when `received <= order.inputs[i].amount`, keeping the user's originally declared amount when the check exactly matches or is satisfied by borrowed balance).

Because the `dispatcher` is a single shared contract used across all orders (per `_params.dispatcher`, also swept the same way in `IntentsBase._execute`, `evm/src/apps/intentsv2/IntentsBase.sol:498-533`), any balance sitting on it — whether from a prior order's incompletely-consumed predispatch call, a stuck/failed external DEX interaction, or a plain `IERC20.transfer` sent directly to the dispatcher address by an unrelated actor — is fungible with the current order's own contribution once measured only by `balanceOf`. An order placer can therefore satisfy `requiredAmount` (and thus have `order.inputs[i].amount` accepted as their full declared amount, forming the commitment and the `_orders[commitment][token]` escrow entry) using tokens they never personally transferred in this call, by relying on whatever balance already happens to sit on `dispatcher`.

### Impact Explanation
This corrupts the escrow accounting that backs cross-chain fulfillment: `order.inputs[i].amount` is committed into the order hash and into `_orders[commitment][token]` as the amount a solver is entitled to redeem on fill (`IntentsBase`/`IntentGatewayV2` fill logic elsewhere credits solvers based on this recorded amount). If that recorded amount is inflated using tokens the order-placer did not actually contribute (borrowed from dust/leftovers on the shared dispatcher), the protocol has effectively created escrow backing from thin air for that order — an unbacked-mint-equivalent inside the intents escrow, and a route by which value legitimately belonging to a previous order/party (its unswept dust) is silently reassigned to a different order's placer, i.e., theft of funds via mis-attributed balance accounting, matching the "unbacked mint"/"unauthorized app action" impact classes in scope.

### Likelihood Explanation
Reachable by any unprivileged caller of `placeOrder` with a predispatch call (`order.predispatch.call.length > 0`), which is a normal, documented feature path (fee-on-transfer support), so no special privilege is required. Triggering favorable conditions (dispatcher holding leftover balance) requires either waiting for/observing residual dust from a previous predispatch flow, or an attacker directly donating tokens to the known `dispatcher` address before calling `placeOrder`, both of which are cheap, permissionless actions available to any address that can send an ERC20 transfer.

### Recommendation
Snapshot the `dispatcher`'s balance for each input token *before* transferring the user's own predispatch assets to it (i.e., before line ~236 loop), and only ever sweep and credit the delta strictly attributable to this order's own transfer‑in and predispatch‑call output, rather than the dispatcher's absolute balance. Any pre‑existing balance on the dispatcher should be swept separately and accounted to protocol dust/an admin-recoverable balance, never folded into a specific order's `received`/`order.inputs[i].amount`.

### Proof of Concept
1. Dispatcher `D` (the shared `_params.dispatcher`) ends up holding `100` units of token `T` — either leftover from a previous order's predispatch call that didn't fully consume `T`, or from an attacker directly calling `T.transfer(D, 100)`.
2. Attacker calls `placeOrder` with `order.predispatch.assets = [{token: T, amount: 900}]` and `order.inputs = [{token: T, amount: 1000}]`, along with a no-op predispatch call.
3. In `placeOrder` (`evm/src/apps/IntentGatewayV2.sol:239-256`), attacker's `900 T` are transferred to `D`, bringing `D`'s balance of `T` to `1000`.
4. Sweep logic (`evm/src/apps/IntentGatewayV2.sol:263-289`) reads `balance = IERC20(T).balanceOf(D) = 1000`, passes the `balance < requiredAmount` check, and sweeps all `1000` to the gateway.
5. `received = 1000` exactly equals `order.inputs[0].amount = 1000`, so it stays unmodified (`evm/src/apps/IntentGatewayV2.sol:301-306`), and the order's commitment/escrow (`_orders[commitment][T] = 1000`) is created — even though the attacker only ever contributed `900 T`; the remaining `100 T` came from an unrelated source folded in by the balance-diff sweep.

            // Build sweep calls and snapshot gateway balances before the sweep.
            Call[] memory transferCalls = new Call[](inputsLen);
            uint256[] memory balancesBefore = new uint256[](inputsLen);
            for (uint256 i; i < inputsLen;) {
                if (order.inputs[i].amount == 0) revert InvalidInput();
                address token = address(uint160(uint256(order.inputs[i].token)));
                uint256 requiredAmount = order.inputs[i].amount;

                if (token == address(0)) {
                    uint256 balance = address(dispatcher).balance;
                    if (balance < requiredAmount) revert InsufficientNativeToken();
                    transferCalls[i] = Call({to: address(this), value: balance, data: ""});
                    balancesBefore[i] = address(this).balance;
                } else {
                    uint256 balance = IERC20(token).balanceOf(dispatcher);
                    if (balance < requiredAmount) revert InvalidInput();
                    transferCalls[i] = Call({
                        to: token,
                        value: 0,
                        data: abi.encodeWithSelector(IERC20.transfer.selector, address(this), balance)
                    });
                    balancesBefore[i] = IERC20(token).balanceOf(address(this));
                }

                unchecked {
                    ++i;
                }
            }

            ICallDispatcher(dispatcher).dispatch(abi.encode(transferCalls));

            // Measure actual received, emit dust for excess, update order.inputs.
            for (uint256 i; i < inputsLen;) {
                address token = address(uint160(uint256(order.inputs[i].token)));
                uint256 received;
                if (token == address(0)) {
                    received = address(this).balance - balancesBefore[i];
                } else {
                    received = IERC20(token).balanceOf(address(this)) - balancesBefore[i];
                }

                if (received > order.inputs[i].amount) {
                    uint256 dust = received - order.inputs[i].amount;
                    emit DustCollected(token, dust);
                } else {
                    order.inputs[i].amount = received;
                }

                unchecked {
                    ++i;
                }
            }
