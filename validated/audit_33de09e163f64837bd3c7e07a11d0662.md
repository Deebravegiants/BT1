### Title
Attacker-controlled swap route can add a wallet-draining token transfer beneath a user’s strategy authorization - (File: contracts/controller/src/strategies/swap.rs)

### Summary
The controller forwards caller-supplied `swap` bytes to the configured aggregator and authorizes only the controller’s exact input-token transfer. The router resolves hop pool and token addresses from that payload and invokes venue adapters without a pool allowlist. A malicious route can therefore place attacker-controlled contract code below the caller’s `swap_collateral`, `swap_debt`, `multiply`, or `repay_debt_with_collateral` authorization. That code can request an unrelated `token.transfer(victim, attacker, amount)`; simulation records it as an additional child authorization, and the transfer succeeds if the returned tree is signed.

### Finding Description
`swap_tokens` accepts opaque route bytes, obtains the configured router, authorizes `token_in.transfer(controller, router, amount_in)`, and calls `router.execute_strategy(controller, amount_in, swap)`. [1](#0-0) 

The strategy payload contains an attacker-influenced `assets` registry. Swap instructions resolve `pool`, `token_in`, and `token_out` from that registry and dispatch them to the selected venue adapter. [2](#0-1)  The route format explicitly uses instruction indexes as pool and token registry selectors. [3](#0-2) 

Venue adapters may invoke the supplied pool, which can execute arbitrary contract code while the original caller’s authorization context is active. Although the controller’s own nested authorization is narrowly scoped to one exact input transfer, that does not constrain other sub-invocations recorded beneath the caller’s root authorization. [4](#0-3) 

The project’s threat model confirms the missing venue allowlist and the resulting authorization-tree exposure. [5](#0-4) 

### Impact Explanation
An attacker can steal arbitrary wallet tokens held by a user who signs the simulated authorization tree, including tokens unrelated to the lending position. The malicious route can still return a fair `token_out` amount, so balance-delta settlement, minimum-output checks, and final account risk checks do not detect the unrelated wallet transfer.

The harness demonstrates this impact with a route-selected rogue pool that transfers the victim’s unrelated wallet token to the attacker while paying the expected strategy output. [6](#0-5)  Its recorded authorization contains a child `transfer(alice, attacker, WALLET_BALANCE)`, and the post-state shows Alice’s wallet balance reduced to zero. [7](#0-6) 

### Likelihood Explanation
Any unprivileged user can construct a route payload naming an attacker-controlled pool and induce another user to submit it through an affected strategy. Exploitation requires the victim or their client to sign the poisoned authorization tree rather than rejecting the unexpected child invocation. Clients that faithfully display or enforce the simulated tree can prevent it, but neither the controller’s measured settlement nor final solvency checks provide protocol-level protection.

### Recommendation
Allowlist pool and token contract addresses used by route hops at the router or controller boundary, rather than permitting route bytes to select arbitrary contracts. At minimum, reject routes that introduce contract calls outside the known venue adapters and prohibit venue adapters from invoking caller-supplied executable pool addresses unless those addresses are governance-approved. Clients should also reject authorization trees containing unexpected child invocations, but this should remain defense-in-depth rather than the only control.

### Proof of Concept
1. Attacker deploys a contract exposing a venue-compatible `swap` function.
2. The malicious function calls `token::Client::new(wallet_token).transfer(victim, attacker, amount)` before returning normally.
3. Attacker constructs a valid `StrategyPayload` whose `assets` registry contains:
   - the normal input token,
   - the normal output token,
   - the malicious contract as a hop `pool`.
4. Victim calls `swap_collateral(caller, account_id, collateral_asset, amount, debt_asset, route)` or an equivalent router-backed strategy.
5. The controller authorizes only its expected input-token transfer and invokes `execute_strategy`.
6. The router invokes the attacker’s pool. During that nested call, the pool requests the unrelated wallet-token transfer.
7. Simulation records the malicious transfer beneath the victim’s root strategy authorization.
8. If the victim signs the returned tree, the malicious transfer executes while the route still produces enough `token_out` to satisfy router and controller settlement checks.

The harness implements this flow in `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`: `RogueHopPool::swap` transfers `WALLET_BALANCE` from Alice to the attacker, while the route returns `FAIR_OUT_ETH`. [7](#0-6)

fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
