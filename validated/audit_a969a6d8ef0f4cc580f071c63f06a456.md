### Title
Webhook shop/topic identity spoofing via HMAC that only covers the request body - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its signable content as the raw body only, while the `shop-domain`, `topic`, `webhook-id`, and `api-version` fields come from headers that are never covered by the HMAC signature. `Registry.process` verifies the HMAC against the body and then trusts these unauthenticated headers to route and tag the payload delivered to the app's handler.

### Finding Description
The equality the HMAC is supposed to guarantee is: `shop_the_handler_believes_sent_this == shop_that_actually_produced_the_signed_bytes`. In `Request#to_signable_string`, only `@raw_body` is returned [1](#0-0) , so `HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:13-31`) only proves that "someone holding the app's `client_secret` produced this exact body." It says nothing about which shop or topic that body was associated with, because `shop`, `topic`, `webhook_id`, and `api_version` are read straight from headers, entirely outside the signed material [4](#0-3) .

`Registry.process` performs the HMAC check, then immediately trusts `request.shop` and `request.topic` to select a handler and populate `WebhookMetadata` passed into application code: [3](#0-2) 

Because a merchant who installs the app legitimately receives webhooks whose body+HMAC pair is valid for their own shop, that merchant (an "unprivileged" actor with respect to any *other* tenant) can capture one such valid `(raw_body, hmac)` pair and resend it to the app's public webhook endpoint with the `shop-domain` header rewritten to a victim shop's domain (and/or a different `topic`/`webhook_id`/`api_version`). The HMAC still validates because it is only a function of the untouched body, so `Registry.process` accepts the forged headers as authentic and calls the handler claiming the data belongs to the victim shop.

### Impact Explanation
This breaks the tenant-isolation binding the HMAC is meant to enforce: `Utils::HmacValidator.validate` returning `true` does not actually authenticate `shop` or `topic`, only the body bytes. Applications built on this gem's documented API (`ShopifyAPI::Webhooks::Registry.process`) rely on `WebhookMetadata#shop`/`#topic` being trustworthy once HMAC validation passes — that is the entire purpose of the HMAC check in a webhook receiver. An attacker who has ever legitimately triggered one webhook (by installing the app on their own store) can inject data attributed to an arbitrary victim shop into the merchant application's per-tenant state (e.g., triggering `orders/create`-style logic, mandatory `customers/redact`/`shop/redact` GDPR handlers, or any custom handler that persists/acts on `data.shop`), i.e., cross-tenant data injection/corruption without ever needing the `client_secret`.

### Likelihood Explanation
Any developer/attacker can install the target app on a free/dev Shopify store, which is enough to receive at least one legitimately-signed webhook body for a given topic. Because the signature is a straightforward HMAC-SHA256 over immutable bytes with no header binding, replaying that exact body with modified headers is trivial with any HTTP client — no cryptographic material, TLS interception, or elevated privileges are required.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, and ideally `webhook-id`) in the signed material used for HMAC verification, or otherwise cryptographically bind them to the body (e.g., concatenate them into the string that is HMAC'd, mirroring how `Auth::Oauth::AuthQuery#to_signable_string` binds `shop`/`host`/`state` into its signature [5](#0-4) ). At minimum, document/require that `shop-domain` returned in `WebhookMetadata` cannot be trusted to differ from the shop that installed the app.

### Proof of Concept
1. Attacker installs the target Shopify app on their own dev store `attacker.myshopify.com` and triggers a webhook, e.g. `orders/create`, capturing the raw POST body `B` and the `X-Shopify-Hmac-Sha256` header value `H` that Shopify computed over `B` with the app's real `client_secret`.
2. Attacker sends a new HTTP request to the app's webhook endpoint with:
   - Body: the same bytes `B`
   - Header `X-Shopify-Hmac-Sha256: H` (unchanged, still valid because it only signs `B`)
   - Header `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (forged)
   - Header `X-Shopify-Topic`: optionally forged to another registered topic
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` is constructed; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `B` against `H` [6](#0-5) .
4. The registered handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, so application logic processes attacker-controlled data as if it originated from the victim shop.
