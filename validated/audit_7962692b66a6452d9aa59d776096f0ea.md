## Title
`CallDispatcher.dispatch()` has no caller restriction, letting any address drain tokens/ETH held by the shared dispatcher - ([File: evm/src/utils/CallDispatcher.sol])

## Summary
The Gearbox report flagged that a privileged token-`approve`-style function accepted an arbitrary, unvalidated target with no allow-list check, letting any caller make the privileged contract execute an approval it was never meant to authorize. The closest reachable analog in Hyperbridge is `CallDispatcher.dispatch()`, a shared execution primitive used by `IntentGatewayV2`, `HyperFungibleToken`, and `WrappedHyperFungibleToken` to run untrusted `Call[]` arrays (including `approve` calls) on behalf of orders/cross-chain sends. `dispatch()` is `external` with **no caller restriction whatsoever** — it can be invoked directly by any address, not just by the apps that are supposed to own its execution context.

## Finding Description
`CallDispatcher.dispatch(bytes memory encoded)` decodes an arbitrary `Call[]` and executes every entry with `to.call{value: call.value}(call.data)`, with no `onlyGateway`/`onlyHost`/allow-list gate on `msg.sender`: [1](#0-0) 

The contract also exposes an unconditional `receive()`: [2](#0-1) 

By design, `IntentGatewayV2` and the HFT contracts transiently push order/message funds (ERC-20 tokens or native ETH) into this single shared `CallDispatcher` instance before invoking `dispatch()`, then sweep the residual balance back out: [3](#0-2) [4](#0-3) 

Documentation confirms it is used identically for `HyperFungibleToken`/`WrappedHyperFungibleToken` calldata execution, and even flags that the dispatcher "holds tokens temporarily during execution": [5](#0-4) 

Because `dispatch()` has no access control and the contract's `receive()` accepts ETH unconditionally from anyone, any value that ends up sitting on the `CallDispatcher` address — via a mistaken/direct ETH or ERC-20 transfer to it by any third party — is trivially stealable: any unprivileged caller can invoke `dispatch()` directly with a `Call[]` that moves that balance (via `transfer`/`approve`+`transferFrom`/raw ETH send) to an address of their choosing. This mirrors the Gearbox root cause precisely: a privileged execution primitive that is supposed to be invoked only by trusted orchestrators accepts unauthorized callers, with no allow-list restricting who may trigger its privileged action (arbitrary `approve`/transfer of tokens it holds).

## Impact Explanation
Any tokens or native ETH that land on the `CallDispatcher` address outside of the exact atomic happy-path sweep sequence (e.g., ETH sent directly to the contract, since `receive()` is unconditionally open, or ERC-20 tokens transferred to it directly by a user/integration by mistake) can be permanently stolen by any unprivileged third party, since `dispatch()` lets anyone run arbitrary calls — including `approve`/`transferFrom`/`transfer` — using whatever balance the shared dispatcher currently holds. Given the dispatcher is shared infrastructure across `IntentGatewayV2`, `HyperFungibleToken`, and `WrappedHyperFungibleToken`, this is a concrete unauthorized-fund-theft path reachable from a single unprivileged transaction, not a privileged-actor or governance issue.

## Likelihood Explanation
Exploitation requires no special role: any account can call `CallDispatcher.dispatch()` directly at any time. The precondition — the dispatcher holding a nonzero balance outside of an in-flight, atomic order/message execution — can occur from ordinary user error (sending ETH or tokens straight to the dispatcher address, which is a normal, easy-to-make mistake since the address is public and documented) or from any edge case where the sweep-back does not capture 100% of a balance. The attack itself is a single, cheap transaction with no timing dependency once funds are present.

## Recommendation
Restrict `dispatch()` to a caller allow-list of trusted, registered HyperApps (`IntentGatewayV2`, `HyperFungibleToken`, `WrappedHyperFungibleToken` instances) via an `onlyAuthorizedCaller` modifier, analogous to the Gearbox recommendation of validating against an allow-list before performing the privileged action. Additionally, consider removing the unconditional `receive()` or ensuring the dispatcher never carries a standing balance across transaction boundaries (e.g., self-destructing balances after each `dispatch()` call, or requiring the calling app to assert a pre/post-balance invariant of zero for uninvolved tokens).

## Proof of Concept
1. A user or integrator (or any third party) accidentally or incidentally sends ERC-20 tokens or ETH directly to the deployed `CallDispatcher` address (a publicly known, documented contract address, with an unconditional `receive()`).
2. An attacker observes the nonzero balance (`token.balanceOf(dispatcher)` or `dispatcher.balance`).
3. The attacker calls `CallDispatcher.dispatch(abi.encode(calls))` directly, with `calls = [{ to: token, value: 0, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, balance) }]` (or an `approve` + `transferFrom` pair for ETH-fee tokens), with no authorization check blocking the call.
4. The dispatcher executes the attacker-supplied call using its own held balance, transferring the funds to the attacker.

    receive() external payable {}

    /**
     *  @dev reverts if the target is not a contract or if any of the calls reverts.
     */
    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }

### Security

The `CallDispatcher` executes calls in its own context (not via `delegatecall`), so the HFT contract's storage is never at risk. If any call in the array reverts, the entire `onAccept` handler reverts — including the token mint/unlock. The request can then be retried by any relayer until the timeout expires. If no successful execution occurs before the timeout, the request times out and the sender is eligible for a refund on the source chain. Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution.

Existing `CallDispatcher` deployments are listed on the [contract addresses](/developers/evm/contract-addresses/mainnet) page.
