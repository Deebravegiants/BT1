### Title
Pausing `HyperFungibleToken`/`WrappedHyperFungibleToken` while a cross-chain transfer is in flight can freeze a user's burned tokens for an unbounded, governance-controlled period - (File: `sdk/packages/core/contracts/apps/HyperFungibleToken.sol`)

### Summary
`HyperFungibleToken.send()` burns the caller's tokens immediately and dispatches a cross-chain POST request with a timeout window. The only way for the user to recover funds if the message never gets delivered is via `onPostRequestTimeout()`, which re-mints the burned amount. However, `onPostRequestTimeout` is gated by `whenNotPaused`, the same pause flag the owner can toggle at will via `pause()`/`unpause()`. If the owner pauses the contract any time between the user's `send()` call and the timeout-refund delivery, the refund reverts and the user's tokens stay burned with no on-chain recovery path until governance decides to unpause — an unbounded freeze exactly analogous to the referenced Ubiquity `redemptionDelayBlocks` issue, where a pause imposed after the user already committed to redemption locks their funds for an unknown duration.

### Finding Description
The relevant lifecycle:
1. A user calls `send()`, which unconditionally burns the tokens and dispatches an ISMP POST request: [1](#0-0) 
2. If the request is never delivered before `timeoutTimestamp`, any relayer can permissionlessly submit a timeout proof to `IHandler.handlePostRequestTimeouts`, which calls `onPostRequestTimeout` on the token: [2](#0-1) 
3. `onPostRequestTimeout` re-mints the burned amount back to the sender as the refund, but is gated `whenNotPaused`: [3](#0-2) 
4. `pause()`/`unpause()` are owner-only and can be called at any time, independent of any pending sends: [4](#0-3) 

Because burning happens synchronously in `send()` but the corresponding refund path (`onPostRequestTimeout`) is subject to the *same* pause flag, a user who has already burned tokens and is waiting out the timeout window has no way to prevent (or bypass) the owner from pausing the contract in the interim. Once paused, the refund call simply reverts every time it's attempted, exactly mirroring the reported pattern where `collectRedemption` is blocked by a `require(!isRedeemPaused)` check imposed after the user already irreversibly committed (burning `uAD` / burning bridge tokens).

The same pattern exists identically in `WrappedHyperFungibleToken.onPostRequestTimeout` (`whenNotPaused`) and in the upgradeable variant `HyperFungibleTokenUpgradeable`/`WrappedHyperFungibleTokenUpgradeable`: [5](#0-4) [6](#0-5) 

### Impact Explanation
A user's tokens are burned unconditionally at `send()` time. If the owner pauses the contract before the timeout refund is delivered (whether intentionally, e.g., for a migration/incident response, or simply because pause coincides with an in-flight transfer), the user's funds are frozen with no recovery mechanism available on-chain — the refund call will keep reverting for as long as the contract stays paused, which is an owner/governance decision with no protocol-enforced bound. This satisfies "permanent/unbounded freezing of funds" for the affected user, matching the Medium-severity classification of the analog report.

### Likelihood Explanation
This requires no attacker at all — it is a straightforward interaction between two independently-invoked, permissionless/owner features: `send()` (callable by anyone) and `pause()` (owner-controlled, but plausible during any real incident, migration, or upgrade window). Any user with a cross-chain transfer in flight when a pause happens is affected; the described `redemptionDelayBlocks`-style window before finality (the ISMP timeout period, driven by `timeoutTimestamp` and challenge periods) creates a natural race condition where governance actions can outlast individual user transactions.

### Recommendation
Decouple the refund/recovery path from the general pause switch:
- Remove `whenNotPaused` from `onPostRequestTimeout` (and its Wrapped/Upgradeable equivalents) so that funds already burned in a not-yet-completed transfer can always be recovered once the ISMP timeout has genuinely elapsed, regardless of the current pause state of `send`/`onAccept`.
- Alternatively, track in-flight commitments and require that a redemption already burned before a pause was enacted remains redeemable, similar to the recommended fix of checking `unclaimedPoolCollateral` before finalizing a pause toggle in the original report.

### Proof of Concept
1. User calls `hft.send(SendParams{ amount: X, timeout: T, ... })`. Tokens are burned: [7](#0-6) 
2. Before delivery/timeout finalization, the destination or relaying infrastructure stalls, and the owner calls `hft.pause()` for unrelated reasons (e.g., responding to an incident on a different chain pairing).
3. Message never gets delivered before `timeoutTimestamp`; a relayer submits `handlePostRequestTimeouts` once the timeout proof is available, which calls `onPostRequestTimeout(incoming)` on the token.
4. Call reverts with `EnforcedPause` because of the `whenNotPaused` modifier: [8](#0-7) 
5. User's `X` tokens remain burned and unrecoverable until the owner calls `unpause()` — an action entirely outside the user's control and with no protocol-enforced time bound.

    function onPostRequestTimeout(PostRequestTimeout calldata incoming) external override onlyHost whenNotPaused {
        HyperFungibleToken.Message memory message = abi.decode(incoming.request.body, (HyperFungibleToken.Message));
        address refundee = _toAddr(message.from);

        if (_isWeth) {
            // Try a native-ETH push first; if the refundee cannot accept native value
            // (e.g. the caller used the ERC-20 deposit path in `send()` from a
            // non-payable contract), re-wrap the withdrawn ETH and deliver the
            // underlying WETH as an ERC-20 transfer so the timeout still settles and
            // funds are not permanently locked.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = refundee.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(refundee, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(refundee, message.amount);
        }

        emit Refunded({to: refundee, amount: message.amount});
    }
