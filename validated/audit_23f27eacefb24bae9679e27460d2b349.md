### Title
Webhook shop/topic attribution not covered by HMAC signature enables cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content solely from the raw request body [4](#0-3) , but the `shop`, `topic`, and `webhook_id` values used by `Registry.process` to route and attribute the webhook to a merchant are read directly from HTTP headers that are never included in that signature [2](#0-1) . This breaks the intended binding `hmac == sign(shop, topic, body)`; in reality `hmac == sign(body)` only, so `shop` (the tenant identity) is asserted, not authenticated.

### Finding Description
`HmacValidator.validate` calls `verifiable_query.to_signable_string` and compares it against the provided HMAC using `Context.api_secret_key` [5](#0-4) . For webhook requests, `to_signable_string` is defined to be exactly `@raw_body`, with no inclusion of the `shop-domain`, `topic`, or `webhook-id` headers [1](#0-0) . Once `Registry.process` confirms `Utils::HmacValidator.validate(request)` succeeds, it immediately trusts `request.shop` and `request.topic` (both plain header reads with no cryptographic binding) to construct `WebhookMetadata` and dispatch to the registered handler [3](#0-2) .

Because the app's `client_secret` (and therefore the HMAC key) is shared across every merchant that installs the app — it is not per-shop — any merchant who has legitimately installed the app can trigger a real webhook delivery for their *own* store and receive a validly-signed `(raw_body, hmac)` pair from Shopify. Since the signature covers only `raw_body`, that same `(raw_body, hmac)` pair remains valid when replayed to the app's public webhook endpoint with the `shop-domain` header rewritten to any other tenant's domain. `Registry.process` will accept it as authentic and hand the attacker-chosen body to the handler labeled as coming from the victim shop, since nothing in the verification path checks that the shop presented in the header is the shop that actually owns the signed body.

### Impact Explanation
This crosses the tenant boundary that `Utils::HmacValidator` is meant to enforce for webhook authenticity: an attacker-controlled body, signed only by proof of "some install of this app exists," is delivered to a downstream handler under an arbitrary victim shop identity. Depending on the handler logic (e.g., `orders/create`, `customers/data_request`, `app/uninstalled`), this can lead to cross-tenant data corruption, spoofed mandatory-compliance webhooks, or state changes recorded against the wrong tenant — matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Any unprivileged internet user can install the app for free on their own development/test store (a standard, unprivileged action), trigger any webhook topic they choose by performing an ordinary action in their own store (e.g., updating a product to trigger `products/update`), capture the resulting `(raw_body, hmac-sha256)` pair sent to the app's public endpoint, and replay it with a modified `x-shopify-shop-domain` header. No access to `api_secret_key`, an access token, or any privileged credential is required — only observation of a webhook that Shopify itself already delivered to the attacker's own installation.

### Recommendation
Bind the tenant/topic identity into the verified signable content, or otherwise cryptographically/contextually verify that the `shop-domain` header corresponds to the shop the payload was actually generated for (e.g., look up the shop from an app-maintained install registry keyed by a value that is itself covered by the signature, or require topic/shop to be echoed inside the signed body/webhook resource where Shopify includes it). At minimum, document and enforce that consumers must cross-check `request.shop` against an already-authenticated session/install record before trusting it, rather than passing it straight into `WebhookMetadata`.

### Proof of Concept
1. Install the target app on attacker-owned shop `attacker.myshopify.com`.
2. Perform an action that triggers a registered webhook topic (e.g., update a product) so Shopify sends a POST to the app's webhook endpoint with headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-topic: products/update`, `x-shopify-hmac-sha256: <valid HMAC of raw_body>`, and the JSON `raw_body`.
3. Capture this request (attacker controls their own network egress and can proxy/log it).
4. Replay the identical `raw_body` and `x-shopify-hmac-sha256` value to the same endpoint, but change `x-shopify-shop-domain` to `victim.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request.new` parses the forged headers and body [6](#0-5) ; `Utils::HmacValidator.validate` succeeds because it only checks `raw_body` against the HMAC [7](#0-6) .
6. `Registry.process` dispatches the handler with `shop: "victim.myshopify.com"` and the attacker's chosen body content, even though `victim.myshopify.com` never generated this webhook.

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
