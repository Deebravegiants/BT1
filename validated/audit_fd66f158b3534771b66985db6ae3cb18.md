Confirmed: the file imports `SafeERC20` and uses `using SafeERC20 for IERC20;` (deposit/escrow paths correctly use `safeTransferFrom`), but the `withdraw()` and `SweepDust` payout paths in `evm/tron/contracts/apps/IntentGatewayV2.sol` deliberately bypass `SafeERC20` and instead use a raw low-level `.call()`, checking only that the call didn't revert — not that the returned boolean is `true`.

### Title
Unchecked ERC20 return value in Tron IntentGatewayV2's `withdraw()`/`SweepDust` lets non-reverting, false-returning tokens silently "succeed" while escrow accounting is decremented - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
`evm/tron/contracts/apps/IntentGatewayV2.sol` escrows inputs on `placeOrder` using `SafeERC20.safeTransferFrom` [1](#0-0) , but pays escrow out in `withdraw()` (settlement/refund) and in the `SweepDust` admin-triggered branch of `onAccept()` using a raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` that only checks the low-level call `success` flag, never decoding/validating the returned boolean [2](#0-1) .

### Finding Description
`withdraw()` is the internal settlement function reached from two unprivileged/permissionless-relayed entry points:
- `onAccept()` handling `RequestKind.RedeemEscrow`/`RefundEscrow` after a solver's `fillOrder` on another chain settles via Hyperbridge [3](#0-2) 
- `onGetResponse()` after a user's cross-chain cancellation is verified [4](#0-3) 

Inside `withdraw()`, for every ERC20 token escrow entry, the code does:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
_orders[body.commitment][token] -= amount;
``` [5](#0-4) 

`success` here reflects only whether the external call reverted, not whether the token contract's `transfer()` actually moved funds. Any ERC20 implementation that returns `false` on failure instead of reverting (a broad "weird ERC20" class explicitly called out in OpenZeppelin's `SafeERC20`, which this same file already imports and uses elsewhere) will make this check pass even though no tokens were transferred to `beneficiary`. The same pattern recurs for the fee-token payout a few lines later [6](#0-5)  and for the `SweepDust` handler in `onAccept()` [7](#0-6) .

Contrast this with the canonical, non-Tron `evm/src/apps/intentsv2/IntentsBase.sol::_withdraw`, which correctly uses `IERC20(token).safeTransfer(beneficiary, amount)` for the identical operation [8](#0-7) , confirming the Tron variant is the outlier and that `SafeERC20` was already available (imported and used for `safeTransferFrom` in the escrow-in path) but not applied consistently to the escrow-out path.

### Impact Explanation
Because `_orders[body.commitment][token]` is decremented unconditionally once the raw `.call()` doesn't revert, a token that returns `false` on transfer failure (e.g. paused, blacklisted recipient, or an insufficient-balance edge case handled by returning `false` rather than reverting) causes the escrow accounting to record the withdrawal as complete while the beneficiary receives nothing. The escrowed tokens remain trapped in the `IntentGatewayV2` contract with no future code path to reclaim them for that commitment (the entry is already zeroed/decremented and `_filled`/order state is finalized), constituting a permanent freezing/loss of user or solver funds. This directly satisfies the "permanent freezing of funds" bar for a valid finding.

### Likelihood Explanation
Exploitability depends on the specific ERC20 token listed for an order's input assets. Since `IntentGatewayV2` is a generic, permissionless intent-settlement contract that accepts arbitrary ERC20 tokens specified by users at `placeOrder` time (not owner-allowlisted per the code shown), any user placing an order with such a non-compliant token is exposed, and the failure is silent — the transaction does not revert, so it may go unnoticed until the beneficiary reports missing funds. This is a realistic, single-transaction reachable path (via `fillOrder` → cross-chain settlement `onAccept`/`withdraw`, or cancellation `onGetResponse`/`withdraw`) rather than a contrived edge case.

### Recommendation
Use `SafeERC20.safeTransfer` (already imported and used elsewhere in this file via `using SafeERC20 for IERC20;`) instead of raw `.call()` for all three ERC20 payout sites in `withdraw()` and the `SweepDust` branch of `onAccept()`, e.g.:
```solidity
IERC20(token).safeTransfer(beneficiary, amount);
```
This correctly reverts on both call-level failures and standards-incompliant `false`-returning tokens, matching the behavior already implemented in `evm/src/apps/intentsv2/IntentsBase.sol`.

### Proof of Concept
1. Deploy (or use) an ERC20 token whose `transfer()` returns `false` instead of reverting when the transfer cannot be completed (e.g., recipient blacklisted, or a "weird" token following Tether-style semantics with an added `false`-return failure path).
2. A user calls `placeOrder` on the Tron `IntentGatewayV2`, escrowing this token as an input asset (escrowed correctly via `safeTransferFrom`).
3. A solver fills the order cross-chain; Hyperbridge delivers the `RedeemEscrow` message, and `onAccept` → `withdraw()` executes.
4. If the token's `transfer()` call to the solver `beneficiary` returns `false` (e.g., beneficiary transiently blacklisted or a token-specific failure condition) without reverting, `success` is `true`, so `_orders[commitment][token]` is decremented and the function proceeds to emit `EscrowReleased` — even though the solver's balance did not increase.
5. The escrowed tokens are now permanently unrecoverable: `_orders` no longer reflects any owed balance for that commitment, and there is no retry/recovery path in the contract.
