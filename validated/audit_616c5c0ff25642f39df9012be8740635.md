### Title
Webhook HMAC validation omits `shop-domain` and `topic` headers from the signed transcript, allowing cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, so the HMAC that Shopify computes and the gem verifies binds *only* the body bytes. The `shop-domain`, `topic`, `webhook-id`, and `api-version` values that `ShopifyAPI::Webhooks::Registry.process` actually acts on are read straight from unauthenticated HTTP headers and are never included in the signed transcript.

### Finding Description
`Request#hmac` and `Request#to_signable_string` define what is verified: [1](#0-0) [2](#0-1) 

`HmacValidator.validate` / `validate_signature` recompute the HMAC only over `to_signable_string`, i.e. `@raw_body`: [3](#0-2) 

But `Registry.process` dispatches to a handler using `request.topic`, `request.shop`, `request.webhook_id`, and `request.api_version` — all sourced directly from headers that are not part of the signed transcript: [4](#0-3) [5](#0-4) 

The identity binding that should hold is:

`hmac_valid(raw_body, api_secret_key) == true` should imply `shop header == shop that produced raw_body` and `topic header == topic that produced raw_body`.

Because `shop` and `topic` are excluded from the transcript, this equality does not hold. `Context.api_secret_key` is the single `client_secret` shared by the app across *all* installing shops (it is not a per-shop value; see the shared `Context.api_secret_key` used identically in `HmacValidator.validate`). Consequently, a valid `(raw_body, hmac)` pair produced for shop A's webhook delivery remains a valid `(raw_body, hmac)` pair when replayed with the `x-shopify-shop-domain` header changed to shop B, or with the `x-shopify-topic` header changed to a different topic whose body schema happens to overlap (e.g., topics with an effectively empty/static body such as `{}`). The handler will process the forged headers as authentic, attributing the action/data to the wrong shop or topic.

### Impact Explanation
This breaks the tenant-identity binding that Shopify webhook HMAC verification is meant to guarantee: “the shop and topic acted on equal the shop and topic that generated the signed payload.” An unprivileged merchant who installs the same multi-tenant app can capture their own genuinely-signed webhook deliveries (no TLS interception needed — they are the legitimate recipient) and replay the body+HMAC to the app's public webhook endpoint with a different `shop-domain`/`topic` header. Handlers that trust `WebhookMetadata#shop`/`#topic` (e.g., to look up or mutate per-shop records, or to react to mandatory topics like uninstall/redact) can be tricked into performing actions attributed to a different tenant — a cross-tenant integrity violation reachable purely over the internet without any credentials beyond being any customer of the app.

### Likelihood Explanation
Exploitability requires only: (1) being a legitimate installer of the target multi-tenant app (an unprivileged action), (2) capturing one's own valid webhook delivery, and (3) sending a crafted HTTP request to the app's public webhook endpoint with substituted headers. No secret material, TLS interception, or privileged access is required, making this practically exploitable wherever webhook handlers key behavior off `shop`/`topic` from `WebhookMetadata`.

### Recommendation
Bind the fields the handler actually acts on into the Fiat-Shamir-style transcript that is HMAC-verified:
- Either verify Shopify's HMAC per Shopify's documented scheme (body-only) but treat `shop-domain` and `topic` as merely advisory and re-derive/re-validate them from a trusted source (e.g., cross-check `shop` against the set of shops that have installed the app, and reject topics not registered for that shop via `Registry`), or
- Extend `to_signable_string` to canonically include `topic`, `shop-domain`, `webhook-id`, and `api-version`, and update validation to match Shopify's actual signing behavior for these headers if Shopify supports it.
- At minimum, add defense-in-depth checks in `Registry.process` that cross-validate `request.shop` against known/installed shops before dispatching to a handler, and add negative tests asserting that a valid body+HMAC with a mutated `shop-domain` or `topic` header is rejected.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (this is a normal, unprivileged app install).
2. Shopify sends a genuine webhook to the app, e.g. topic `app/uninstalled` with body `{}` and headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC over "{}">`.
3. Attacker replays this exact body and HMAC to the app's public webhook endpoint, but with `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` succeeds because it only checks `raw_body` ("{}") against the HMAC — unaffected by the header change (`lib/shopify_api/utils/hmac_validator.rb:26-31`, `lib/shopify_api/webhooks/request.rb:35-38`).
5. `Registry.process` invokes the registered `app/uninstalled` handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", ...)` (`lib/shopify_api/webhooks/registry.rb:188-200`), causing the app to perform uninstall-related cleanup/side effects attributed to the victim shop even though the victim never sent that webhook.
