### Title
Webhook shop-domain identity is not bound by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then trusts the unauthenticated `X-Shopify-Shop-Domain` (and topic/webhook-id) headers to attribute the payload to a specific tenant. Because the HMAC signable string is only the raw body, any two webhook deliveries that happen to carry the same body bytes produce the same valid signature regardless of which shop or topic header accompanies them, breaking the binding "shop authenticated == shop the app acts on."

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes/compares the HMAC exclusively against that signable string: [2](#0-1) 

`Registry.process` uses this validation as the sole authenticity check, then forwards the *unauthenticated* `request.shop`, `request.topic`, and `request.webhook_id` headers straight to the app's handler: [3](#0-2) 

`request.shop`, `request.topic`, and `request.webhook_id` are all pulled from headers that are never included in the signed material: [4](#0-3) 

An unprivileged internet user who controls any shop (e.g., a free trial store) can install the target app, wait for Shopify to deliver a legitimately-signed webhook whose body is predictable/constant (many topics, e.g. `app/uninstalled`, ship bodies that are empty `{}` or otherwise attacker-influenced), capture the `(raw_body, hmac)` pair, and then replay that exact body+HMAC to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` header (and/or topic header) for a victim shop's domain. `Utils::HmacValidator.validate` still returns `true` because the signature only ever covers the body, so `Registry.process` dispatches the forged event to the handler as if it originated from the victim shop, breaking the identity binding `shop authenticated (HMAC) == shop the handler acts on`.

### Impact Explanation
This allows cross-tenant data poisoning/spoofing: an attacker can make the host application believe an event (install/uninstall, order, GDPR, etc.) came from a shop it does not control, causing the app to write/delete per-shop state, revoke access, or perform actions attributed to a victim tenant that never sent the request. This crosses the tenant boundary this gem is responsible for enforcing on the app's behalf, matching the Critical cross-tenant-access category from the rules.

### Likelihood Explanation
Requires only an internet-accessible free/trial shop to obtain one legitimately-signed webhook, no `client_secret` or access token needed, and the app's webhook endpoint (built with this gem's documented `Registry.process` API) is public by design. The attack is a pure header-substitution replay, no cryptographic break needed.

### Recommendation
Include the shop domain (and ideally topic/webhook-id/api-version) in the HMAC signable string, or otherwise independently verify `request.shop` against a value that itself is authenticated (e.g., check that the shop is a session the app has record of installing, in addition to same-body HMAC check), before dispatching to handlers.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`.
2. Attacker triggers/receives a Shopify webhook whose body is fixed/predictable (e.g., an event with body `{}`), capturing `X-Shopify-Hmac-Sha256` and raw body.
3. Attacker POSTs to the app's webhook endpoint with the same raw body and HMAC header, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:26-31`) succeeds because only the body is checked; `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) dispatches the handler with `shop: "victim-shop.myshopify.com"`, causing the app to act on data attributed to a shop the attacker never controlled or sent the request from.
