### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats an HTTP request as authenticated for a given shop as soon as `Utils::HmacValidator.validate(request)` passes, and then hands `request.shop` — a value taken straight from an HTTP header — to the app's handler as the tenant identifier. But the HMAC only signs the raw body, never the shop header, so a valid signature proves the *body bytes* are Shopify-issued, not which shop they belong to.

### Finding Description
The bug class from the report is: a value that is *acted on* by the application is not actually covered by the cryptographic check that is supposed to authenticate the request — i.e. verified bytes ≠ trusted bytes.

- `Webhooks::Request#to_signable_string` returns only `@raw_body`: ` [1](#0-0) `
- `Webhooks::Request#shop`, `#topic`, `#webhook_id`, `#api_version` are all read straight out of caller-supplied HTTP headers (`shopify-shop-domain` / `x-shopify-shop-domain`, etc.), with no cryptographic binding to the body: ` [2](#0-1) `
- `Registry.process` validates only the HMAC-over-body, then immediately trusts `request.shop` (and `request.topic`) as the tenant/topic identity for dispatching to the handler: ` [3](#0-2) `

The identity equation the code implicitly assumes is:
`shop header value == shop that Shopify actually generated this signed payload for`

but the HMAC only proves:
`raw_body == bytes signed with app's client_secret`

These are not the same statement. Because a public app's `client_secret` (the HMAC key) is shared across *every* shop that installs the app, any merchant that installs the app can legitimately receive a genuinely-signed webhook for their own store (valid `hmac-sha256` header for that exact `raw_body`), then resend that identical `raw_body` + `hmac-sha256` header to the app's shared public webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header for a victim shop. `HmacValidator.validate` recomputes the signature over `raw_body` only and will accept it, because the body/secret pair used for the signature is unchanged — the forged header is never part of the signed material.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to help enforce: an attacker who is a legitimate (even free/trial) installer of the app can inject or replay events attributed to an arbitrary victim shop that is also using the app, because `request.shop` is exposed to and trusted by the handler with no signature backing. Depending on how the host app uses `data.shop` in `WebhookMetadata` (e.g., persisting order/customer data keyed by shop, processing GDPR `customers/redact`/`shop/redact` mandatory webhooks, or invalidating access tokens on `app/uninstalled`), this can lead to cross-tenant data corruption or spoofed lifecycle events for a shop the attacker does not control — matching the "cross-tenant access" criterion.

### Likelihood Explanation
Exploitation only requires: (1) the attacker be an installer/merchant of the target app (no elevated privilege needed — this is the "unprivileged internet user" scope, since installing a public app is unprivileged), and (2) the app's webhook endpoint to be a single shared HTTP endpoint receiving webhooks for all shops (the standard, documented pattern for this gem — a single `path` route reused across all merchants, per `docs/usage/webhooks.md`). No access token, `api_secret_key`, or TLS interception is required; the attacker only needs bytes that were already legitimately delivered to them by Shopify.

### Recommendation
`Webhooks::Request#to_signable_string`/the HMAC verification path binds only the body; the gem should not expose `shop`/`topic`/`webhook_id` to consumers as trusted values without also documenting/enforcing that callers must independently cross-check `request.shop` against a shop known to have an active session/installation before acting on the payload. Alternatively, the gem could require correlation between the resolved shop (from stored session data associated with the webhook subscription) and the header-supplied shop before dispatching to the handler.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`, so a webhook (e.g. `customers/redact`) is legitimately sent by Shopify to the app's shared webhook endpoint with a valid `X-Shopify-Hmac-Sha256` computed over the raw JSON body using the app's `client_secret`.
2. Attacker captures the exact `raw_body` and `hmac-sha256` header value delivered to their own installation.
3. Attacker sends a new HTTP POST directly to the app's public webhook route with the identical `raw_body` and `hmac-sha256` header, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `raw_body` against the shared secret (` [4](#0-3) `, ` [5](#0-4) `).
5. The handler is invoked with `WebhookMetadata(shop: "victim-shop.myshopify.com", topic: ..., body: ...)`, causing the app to process an attacker-controlled payload as if it originated from the victim shop.
