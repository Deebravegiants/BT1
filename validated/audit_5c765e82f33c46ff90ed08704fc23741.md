## Title
Webhook Shop-Domain and Topic Headers Are Not Covered by HMAC, Allowing Cross-Tenant Webhook Forgery/Replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw body only, while the `shop-domain`, `topic`, `webhook-id`, and `api-version` headers used to route and attribute the webhook to a tenant are never included in the signed bytes. Any party who can produce one legitimately-signed `(body, hmac)` pair (e.g. by triggering a webhook on their own, self-owned development shop) can replay that exact pair to the app's public webhook endpoint while freely rewriting the `shop-domain` and `topic` headers, causing the app to process the payload as if it came from a different, victim shop and/or a different topic than what Shopify actually signed.

### Finding Description
`HmacValidator.validate` verifies `verifiable_query.to_signable_string` against the received HMAC: [1](#0-0) 

For webhooks, `to_signable_string` returns only the raw request body: [2](#0-1) 

But `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers with no cryptographic binding to the signed body: [3](#0-2) 

`Registry.process` verifies only the HMAC of the body, then unconditionally trusts these unauthenticated header values to route the payload and identify the tenant to the handler: [4](#0-3) 

The identity binding that should hold is:
`bytes_covered_by_hmac == bytes_used_to_attribute_the_webhook_to_a_shop_and_topic`

In this gem, that equality does not hold:
`bytes_covered_by_hmac == raw_body` only, while `bytes_used_for_attribution == {shop-domain header, topic header}`, which are disjoint from the signed bytes.

Because the webhook endpoint is a public, internet-reachable HTTP endpoint (that's the whole point of webhook delivery), an unprivileged attacker can:
1. Obtain one legitimately Shopify-signed `(raw_body, hmac)` pair for a topic of their choosing, by installing their own app/dev store and triggering a real webhook (e.g. `orders/create` on their own store) — no victim credentials needed.
2. Replay that exact `raw_body` + `hmac` to the target app's webhook endpoint, but substitute the `x-shopify-shop-domain` header with the victim shop's domain and/or the `x-shopify-topic` header with an arbitrary registered topic.
3. `HmacValidator.validate` still passes, because it only checks `raw_body` against `hmac` — it never checks that this specific `(shop, topic)` pair is what Shopify actually signed.
4. `Registry.process` looks up a handler by the attacker-controlled `topic` header and invokes it with `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: ..., ...)`, using the forged `shop` value as the tenant identity for whatever the host application does next (e.g. writing/deleting data keyed by shop, billing actions, GDPR data requests, etc.).

### Impact Explanation
This breaks the shop-identity/tenant boundary that host applications rely on this gem to enforce: the gem's own `process` method hands the host app a `shop` value that it asserts was "HMAC validated," but the HMAC never actually covered that value. Any application that trusts `WebhookMetadata#shop` (as the docs and API surface imply it should) can be made to perform tenant-scoped operations against the wrong shop, or process a payload under the wrong topic handler — a cross-tenant confusion driven entirely by an unauthenticated header, satisfying the Critical "cross-tenant access" impact bar.

### Likelihood Explanation
Likelihood is high: the webhook endpoint is intentionally public and unauthenticated at the transport layer (that's how Shopify delivers webhooks), the attacker only needs one arbitrary legitimately-signed body (trivially obtainable from their own store/app), and no secrets, tokens, or privileged access to the victim are required — only knowledge of the target app's webhook URL and topic names, which are typically documented/public.

### Recommendation
Include the tenant- and routing-relevant headers (`shop-domain`, `topic`, and ideally `webhook-id`/`api-version`) in the signable string used for webhook HMAC verification, or otherwise cryptographically bind them to the body before trusting them in `Registry.process`/`WebhookMetadata`. At minimum, document and/or enforce that `shop` must be cross-checked against the app's own persisted session/shop records before being used for any lookup or action, since it is not currently authenticated by the HMAC check this gem performs.

### Proof of Concept
```ruby
# Attacker obtains a legitimately Shopify-signed webhook from their OWN store
raw_body = '{"id":1,"note":"hello"}'
valid_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), real_secret, raw_body) # this is signed by Shopify for attacker's own shop

# Attacker replays it against the target app's webhook endpoint with forged headers
headers = {
  "x-shopify-topic" => "customers/data_request",       # attacker-chosen topic, NOT covered by hmac
  "x-shopify-hmac-sha256" => Base64.encode64(valid_hmac), # still valid, since hmac only covers raw_body
  "x-shopify-shop-domain" => "victim-shop.myshopify.com" # forged, NOT covered by hmac
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) returns tr

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
