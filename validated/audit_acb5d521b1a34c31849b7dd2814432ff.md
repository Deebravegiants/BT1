### Title
Missing price/slippage protection in `BandwidthManager.purchase()` allows buyers to overpay when `tierPrice` changes mid-flight - ([File: evm/src/apps/BandwidthManager.sol])

### Summary
`BandwidthManager.purchase()` charges the caller based on the current on-chain value of `tierPrice[tier]`, which is a mutable price feed updated asynchronously by governance via an ISMP-delivered `SetTiers` message. The function accepts no expected-price or maximum-cost parameter, so a buyer who quotes a price off-chain (e.g. in a frontend) and later submits the transaction can be charged a materially different, larger amount if governance pushes a price update in between — the exact same class of bug as Sherlock M-4 in Napier's `Tranche.issue()`, where the exchange rate used at execution time could silently diverge from what the user expected off-chain, with no on-chain check to protect them.

### Finding Description
`purchase()` reads the live tier price and computes the exact amount to pull from the caller in a single step, with no bound supplied by the caller: [1](#0-0) 

The price itself is not fixed at deploy time — it is set and can be changed at any time via a `SetTiers` governance message delivered asynchronously from `pallet-bandwidth` on Hyperbridge, and takes effect immediately in `onAccept`: [2](#0-1) 

The docs confirm this asynchronous update path exists in production and that price consistency across chains depends on when each dispatch lands, i.e. no atomicity guarantee between a quote and a purchase: [3](#0-2) 

Because `purchase()` has no `maxAmount`/`expectedPrice18d` parameter, a buyer's transaction that is quoted off-chain (as documented in `docs/content/developers/evm/bandwidth/purchasing.mdx`'s `quote()` helper) can be front-run or simply land after a `SetTiers` update raises `tierPrice[tier]`, causing `safeTransferFrom` to pull a larger amount than the buyer expected — with no revert path to protect them, exactly mirroring the Tranche `issue()` root cause (an amount computed from a mutable on-chain rate at execution time, with no caller-supplied bound).

### Impact Explanation
A bandwidth purchaser can be charged in the fee token substantially more than they intended to pay for the same tier/months, with the excess pulled directly into the `BandwidthManager` contract (recoverable only by governance via `Withdraw`). Since tier prices can jump by governance decision (there is no cap on how much a `SetTiers` update can change a price), the potential overcharge is unbounded in the worst case, resulting in a direct loss of funds for the caller — satisfying the "concrete theft ... of funds" bar via an unprotected exchange-rate-dependent transfer, reachable by any unprivileged caller of `purchase()`.

### Likelihood Explanation
This requires no attacker action beyond ordinary transaction timing/mempool delay: any legitimate purchase transaction that is pending when a `SetTiers` update is delivered (a routine, expected governance operation per the documented lifecycle) will silently execute at the new price. Given the manager explicitly documents periodic price updates ("If you change a tier's price, dispatch the update to every chain...") as normal operation, the race condition is not a rare edge case but an expected consequence of the price-update mechanism combined with the missing slippage guard.

### Recommendation
Add a caller-supplied bound to `purchase()`, e.g. `uint256 maxAmount` (or `uint256 expectedPrice18d`), and revert (e.g. `PriceExceedsMax`) if the computed `amount` exceeds it — mirroring the fix pattern recommended in the referenced Napier report and already used elsewhere in this codebase (e.g. `amountOutMin` in swap wrappers) so buyers can enforce the price they quoted off-chain.

### Proof of Concept
1. Frontend calls `tierPrice(tier)` and computes `cost = quote(tier, months)` as shown in `docs/content/developers/evm/bandwidth/purchasing.mdx`, and the user approves exactly `cost`.
2. Before the user's `purchase()` transaction is mined, governance dispatches `dispatch_set_tiers` raising `tierPrice[tier]` (a normal, permissionless-to-observe operation delivered via `onAccept`/`SetTiers`).
3. The user's `purchase()` transaction executes against the new, higher `tierPrice[tier]`; `safeTransferFrom` now attempts to pull the new, larger `amount`.
4. Because the user only approved the old `cost`, either (a) the transaction reverts (denial of service — wasted gas, and repeated retries expose the user to fee volatility with no protection) or (b) if the user had granted a larger/infinite approval, the excess amount is silently pulled with no way for the transaction to revert on unfavorable pricing — the amount charged is entirely at the mercy of whatever price is live at execution, with `purchase()` providing no `maxAmount` guard to fall back on.

        external

        if (app.length == 0 || app.length > MAX_APP_LENGTH || chain.length == 0 || months == 0) {
            revert InvalidPurchase();
        }
        uint256 price18d = tierPrice[tier];
        if (price18d == 0) revert UnknownTier();

        uint256 total18d = price18d * months;
        address feeToken = IDispatcher(_host).feeToken();
        uint8 dec = IERC20Metadata(feeToken).decimals();
        uint256 scale = 10 ** (18 - dec);
        if (total18d % scale != 0) revert PriceNotRepresentable();
        uint256 amount = total18d / scale;

        IERC20(feeToken).safeTransferFrom(msg.sender, address(this), amount);

## Step 5 — Push tier prices to the manager

```rust
BandwidthPallet::dispatch_set_tiers(
    RawOrigin::Root.into(),
    StateMachine::Evm(8453),
    vec![
        (TierIndex::TierOne,   U256::from(50e18 as u128)),
        (TierIndex::TierTwo,   U256::from(200e18 as u128)),
        (TierIndex::TierThree, U256::from(500e18 as u128)),
        (TierIndex::TierFour,  U256::from(2_000e18 as u128)),
    ],
);
```

This dispatches a `SetTiers` message to the registered manager on `target`. The manager's `onAccept` writes `tierPrice[tier] = price18d` for each row and emits `TierSet(tier, price18d)`. Tiers not in the batch are left untouched.

Prices are 18-decimal regardless of the local fee token's decimals — the contract scales at purchase time. See [Purchasing → Decimal scaling](/developers/evm/bandwidth/purchasing#decimal-scaling) for the rules and the `PriceNotRepresentable()` failure mode.

Repeat for every chain that should sell the same tiers — tier prices are per-chain because the manager contract is per-chain.

<Callout type="warn" title="Keep prices in sync">
If you change a tier's price, dispatch the update to every chain where a manager is deployed — otherwise the same SKU costs different amounts depending on which chain a buyer is on. The pallet emits `TiersDispatched { target, count, commitment }` for each push so you can audit.
</Callout>
