Confirmed: all wrapper implementations (`GnosisUniswapV2Wrapper.sol`, `UniV3UniswapV2Wrapper.sol`, `UniV4UniswapV2Wrapper.sol`) correctly refund excess ETH back to `msg.sender`. However, in the `EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` functions, `EvmHost` itself is the caller of the wrapper (`msg.sender` from the wrapper's perspective is `EvmHost`, not the original user). This means any dust/excess ETH refunded by the swap call goes back to the `EvmHost` contract balance, not to the original transaction sender (`_msgSender()`). Since `EvmHost` has no `withdraw`/`recoverFunds` mechanism visible in the parts I inspected, and no `receive()` fallback was found in `EvmHost.sol` to reroute or reject such value, this class of bug is analogous to the reported `QVBaseStrategy` issue: native tokens can become stuck in the contract with no recovery path.

### Title
Excess native token payment for POST/GET dispatch fees and `fundRequest` gets stuck in `EvmHost` - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` accept `msg.value` and forward the entire value to a Uniswap V2-compatible router's `swapETHForExactTokens` to buy the exact fee amount needed in `feeToken()`. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
In all three functions, the router call is `IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(fee, path, address(this), block.timestamp)`, where the caller of the router is `EvmHost` itself, not the end user. Router implementations in this codebase (`UniV3UniswapV2Wrapper.swapETHForExactTokens`, `UniV4UniswapV2Wrapper.swapETHForExactTokens`, `GnosisUniswapV2Wrapper` variant) correctly refund unused ETH to `msg.sender` of the swap call: [4](#0-3)  and [5](#0-4) . Because `EvmHost` (not the original transaction sender) is that `msg.sender`, any ETH sent by a user in excess of the amount required to purchase `fee`/`amount`/`post.fee`/`get.fee` tokens is refunded back into the `EvmHost` contract's own balance rather than to `_msgSender()`. `EvmHost.sol` never checks that `msg.value` equals the exact amount required for the swap, nor does it forward the refunded dust back to the caller, and there is no visible `withdraw()`/`recoverFunds()` function to reclaim it. This mirrors the reported class of bug in `Transfer._transferAmount()`/`QVBaseStrategy._distribute()`, where failing to reconcile `msg.value` against the required amount permanently traps native tokens in the contract.

### Impact Explanation
Any user who overestimates the ETH needed for `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, or `fundRequest()` — for example due to slippage buffers or price movement between quoting and execution — will have the unused ETH permanently locked in `EvmHost`, since it is not the caller of the router and has no mechanism to sweep or return the dust. This is a direct, permanent freezing of user funds reachable from a single ordinary dispatch/fund transaction, which fits the "permanent freezing of funds" acceptance criterion.

### Likelihood Explanation
Likelihood is high: any caller who supplies native token payment for these fee functions with even a slightly larger `msg.value` than the router's computed input amount (which is essentially unavoidable without an exact off-chain quote matching on-chain execution atomically, given price-path/slippage between quoting and submission) will trigger the stuck-fund condition on every such call, with no user error required beyond ordinary overestimation.

### Recommendation
Have `EvmHost` capture the return value of `swapETHForExactTokens` (the amount actually spent) and forward `msg.value - amountSpent` back to `_msgSender()` in `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()`, mirroring the refund pattern already used in `IntentGatewayV2._fillCrossChain`/`placeOrder` where unspent `msgValue` is explicitly refunded via `_sendValue(msg.sender, msgValue)` (see e.g. [6](#0-5) ). Alternatively, add a permissioned `recoverFunds()`/`withdraw()` function on `EvmHost` to sweep stray native balance.

### Proof of Concept
1. Attacker/user calls `EvmHost.dispatch(DispatchPost)` (or `dispatch(DispatchGet)` / `fundRequest`) with `msg.value` set higher than the exact ETH input required to purchase `post.fee` units of `feeToken()` via the configured router.
2. `EvmHost` forwards the full `msg.value` to `swapETHForExactTokens{value: msg.value}(...)`.
3. The router/wrapper computes the exact ETH needed, performs the swap, and refunds the difference to its caller — `EvmHost` — per [4](#0-3) .
4. `EvmHost.dispatch`/`fundRequest` does not read the router's return value or forward any refund back to `_msgSender()`; the request/commitment logic proceeds unaware of the leftover ETH: [1](#0-0) .
5. The excess ETH remains in `EvmHost`'s balance indefinitely, with no `withdraw`/`recoverFunds` function found to retrieve it.
