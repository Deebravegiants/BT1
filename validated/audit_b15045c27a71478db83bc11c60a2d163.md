### Title
Webhook `shop` (and `topic`/`webhook_id`) header is trusted without HMAC coverage, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw body only, while the `shop`, `topic`, `api_version`, and `webhook_id` values are read from unauthenticated HTTP headers. `Registry.process` validates the HMAC and then unconditionally trusts `request.shop` as the tenant identity when dispatching to the handler, breaking the intended binding `hmac == HMAC(secret, body ‖ shop ‖ topic)` down to `hmac == HMAC(secret, body)`.

### Finding Description
`to_signable_string` only returns `@raw_body`: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are all pulled straight from HTTP headers with no cryptographic binding to the signed content: [2](#0-1) 

`HmacValidator.validate` only re-computes the signature over `to_signable_string` (i.e. the body) and compares against the `hmac-sha256` header: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts the unauthenticated `request.shop`, `request.topic`, and `request.webhook_id` as the identity/context passed to the app's handler: [4](#0-3) 

Because the app's `client_secret` (used as the HMAC key) is the same across every shop the app serves, a valid `(body, hmac)` pair generated from any one tenant's legitimate webhook delivery remains valid for that same body regardless of which `shop-domain` header accompanies it. An unprivileged attacker who is a merchant on their own shop (or who otherwise observes a valid webhook payload+HMAC delivered to their own server) can replay that exact `raw_body`/`hmac-sha256` pair to the app's public webhook endpoint while substituting an arbitrary `shop-domain` header. `HmacValidator.validate` still succeeds because the shop is not part of `to_signable_string`, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the body originated from the victim shop.

The identity-binding equality that should hold is:
`HMAC_valid ⇔ (body, shop, topic) all attested by Shopify`
but the code actually enforces only:
`HMAC_valid ⇔ body attested by Shopify`, then separately trusts `shop`/`topic` from unauthenticated headers.

### Impact Explanation
This is a cross-tenant identity-binding bypass: the webhook shop attribution — which downstream application code (via `WebhookHandler.handle`) uses to determine which merchant/tenant record to act on (e.g. `shop/redact`, `customers/redact`, order/product updates) — is not covered by the HMAC signature the gem validates. An attacker can make the app believe a webhook body belongs to a different shop than the one that generated it, which can lead to cross-tenant data corruption or disclosure depending on how the consuming application keys its data by `WebhookMetadata#shop`.

### Likelihood Explanation
Requires no privileged Shopify credentials, access token, or `client_secret` — only a single legitimate webhook delivery (obtainable by any merchant installing the app on their own store, or via a public webhook example) and the ability to POST to the app's public webhook receiver endpoint with a forged `shop-domain` header. This is directly reachable through the gem's own `Utils::HmacValidator` / `Webhooks::Registry.process` code path, not a host-application misuse.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in `Webhooks::Request#to_signable_string` (or otherwise cryptographically bind them, e.g. by validating the `shop` against the shop associated with a known/expected session before processing), so that any deviation from the signed identity fields invalidates the HMAC check, matching the binding Shopify already computes on outbound webhook signatures.

### Proof of Concept
1. App receives a legitimate webhook to attacker-controlled shop `attacker.myshopify.com`: body `B`, `shopify-hmac-sha256: H = HMAC(secret, B)`, `shopify-shop-domain: attacker.myshopify.com`.
2. Attacker resends the same `B` and `H` to the app's webhook endpoint but sets `shopify-shop-domain: victim.myshopify.com`.
3. `HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` recomputes `HMAC(secret, B)` (body only) and matches `H` — validation passes.
4. `Registry.process` in `lib/shopify_api/webhooks/registry.rb` (L188-199) builds `WebhookMetadata` with `shop: "victim.myshopify.com"` and dispatches it to the handler, which now processes attacker-supplied content as if it came from `victim.myshopify.com`.
