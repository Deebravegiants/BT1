### Title
Webhook `shop` domain is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, and `ShopifyAPI::Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb`) checks that signature against `Context.api_secret_key`. The `shop`, `topic`, `webhook_id`, and `api_version` values, however, are all read straight from HTTP headers (`shopify-shop-domain` / `x-shopify-shop-domain`) that are never included in the signed payload.

### Finding Description
`Request#shop` is defined as:
```ruby
def shop
  T.cast(shopify_header("shop-domain"), String)
end
``` [1](#0-0) 

while the signable string used for HMAC verification is just the raw body:
```ruby
def to_signable_string
  @raw_body
end
``` [2](#0-1) 

`Registry.process` trusts this unauthenticated header directly and forwards it to the app's handler as the shop identity for the event:
```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
``` [3](#0-2) 

The binding that should hold is: `hmac_verified(shop) == shop_acted_on`. Instead, the gem verifies only `hmac_verified(raw_body)` and separately trusts `shop_acted_on = header["x-shopify-shop-domain"]`, with no cryptographic link between the two. The gem's own documentation reinforces that developers are expected to treat `data.shop` as an authenticated field ("The shop domain of the webhook") after `Registry.process` "will verify the request did indeed come from Shopify." [4](#0-3) [5](#0-4) 

### Impact Explanation
Any unprivileged internet user can install the app on their own store (a normal, unprivileged action) and thereby receive genuinely Shopify-signed webhook deliveries — signed with the app's single shared `client_secret`/`api_secret_key`, not a per-shop secret. Because the HMAC covers only the raw body, the attacker can replay that exact `raw_body` + `hmac-sha256` header to the app's webhook endpoint while substituting an arbitrary victim `x-shopify-shop-domain` header value. `HmacValidator.validate` still succeeds (body untouched), and `Registry.process` calls the app's handler with `data.shop` set to the attacker-chosen victim shop domain, alongside attacker-controlled body content. Since the documented `data.shop` field is meant to identify which tenant a given webhook payload belongs to, and downstream apps commonly key persistence, redaction, or business logic off it (e.g., GDPR `customers/redact`, `shop/redact`), this allows cross-tenant event injection/spoofing — an app can be tricked into applying attacker-supplied webhook data to a victim shop's record.

### Likelihood Explanation
Requires only the ability to install the app on an attacker-controlled shop (no privileged access, no leaked credentials) and the ability to send a raw HTTP POST with a captured body/HMAC pair and a modified header. This is a mechanical replay a scripted unprivileged actor can perform.

### Recommendation
Bind the shop (and ideally topic/webhook_id) into the signed material, or otherwise authenticate the shop domain header against the shop that legitimately owns the webhook subscription. At minimum, include `shop-domain` in `to_signable_string`, or have `Registry.process` cross-check `request.shop` against an out-of-band trusted mapping of `webhook_id`/topic to shop before invoking the handler.

### Proof of Concept
1. Attacker installs the target Shopify app on their own dev store (`attacker.myshopify.com`) and registers a webhook topic (e.g. `orders/create`).
2. Shopify sends a legitimately signed webhook: `raw_body = B`, `hmac-sha256 = HMAC(api_secret_key, B)`, `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker captures this exact request and replays it to the same app endpoint, changing only the header to `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(api_secret_key, B)` — unchanged since `to_signable_string` only returns `@raw_body` — so validation passes.
5. `handler.handle` is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", body: <attacker-controlled B>, ...)`, and the app processes attacker data as if it belonged to the victim shop.
