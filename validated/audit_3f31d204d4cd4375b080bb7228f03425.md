Based on my investigation, I found a valid analog: the Tron-specific `IntentGatewayV2` implementation lacks the `ReentrancyGuard`/`nonReentrant` protection that the equivalent EVM mainnet contract has, while performing the exact reentrancy-prone pattern described in the report (external token transfers and arbitrary calldata dispatch interleaved with escrow state updates).

### Title
Missing ReentrancyGuard on Tron IntentGatewayV2's order placement/fill flow allows escrow manipulation via reentrancy - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The canonical EVM `IntentGatewayV2` composes `ReentrancyGuardTransient` and marks `placeOrder` with `nonReentrant` [1](#0-0) [2](#0-1) . The Tron variant of the same contract, however, is declared as `contract IntentGatewayV2 is HyperApp, EIP712` with no reentrancy guard inherited or applied anywhere in the file [3](#0-2) .

### Finding Description
The Tron order-placement/predispatch logic performs the same sequence of unprotected external interactions the external report flags as reentrancy-prone: it calls `IERC20(token).safeTransferFrom(msg.sender, dispatcher, amount)`, then invokes `ICallDispatcher(dispatcher).dispatch(order.predispatch.call)` — an arbitrary, attacker-supplied calldata execution — and then sweeps balances back via another `dispatch` call, all before or interleaved with escrow bookkeeping (`_orders[commitment][token] += reducedInputs[i].amount`) [4](#0-3) . The non-predispatch branch also calls `safeTransferFrom` directly before updating `_orders` [5](#0-4) . Because this contract has no `ReentrancyGuard`/`nonReentrant` modifier at all (unlike the EVM mainnet version), any external call in this chain — a malicious/hook-bearing ERC20 during `safeTransferFrom`, or the attacker-controlled `predispatch.call` payload executed via `ICallDispatcher` — can re-enter the gateway (e.g., call `placeOrder`/`fillOrder` again) before the current call's escrow accounting is finalized.

### Impact Explanation
An unprivileged user submitting an order (a normal `placeOrder`-equivalent transaction) can trigger reentrancy that corrupts the `_orders` escrow mapping — e.g., double-crediting escrow, or fill/withdraw logic reading inconsistent state — leading to theft of escrowed funds or permanent freezing of legitimate orders' escrow. This matches the "concrete theft or permanent freezing of funds" bar for Medium/High severity.

### Likelihood Explanation
Likelihood is meaningfully high because the attack surface is directly reachable by a single unprivileged transaction (placing an order with a malicious/hook token or via the `predispatch.call` field, which is fully attacker-controlled calldata dispatched through `ICallDispatcher`), and requires no privileged role, admin misbehavior, or off-chain component compromise.

### Recommendation
Add `ReentrancyGuard` (or `ReentrancyGuardTransient`, matching the mainnet EVM implementation) to the Tron `IntentGatewayV2` contract and apply `nonReentrant` to `placeOrder`, `fillOrder`, and any other state-mutating entry points that perform external token transfers or dispatch arbitrary calldata, mirroring the protection already present in `evm/src/apps/IntentGatewayV2.sol` [1](#0-0) .

### Proof of Concept
1. Attacker calls the Tron gateway's order-placement function with an input token that has a transfer hook (e.g., ERC-777-style) or with `predispatch.call` set to a payload that calls back into the gateway.
2. During `IERC20(token).safeTransferFrom(...)` or during `ICallDispatcher(dispatcher).dispatch(order.predispatch.call)` [6](#0-5) , control returns to attacker-controlled code before `_orders[commitment][token] += ...` is executed.
3. Because no `nonReentrant` guard exists anywhere in this contract, the attacker re-enters the gateway (e.g., invoking `fillOrder` on the not-yet-finalized commitment, or re-invoking order placement) to manipulate escrow state — claiming funds against an order whose escrow bookkeeping is still mid-update.

Note: I was unable to fully enumerate every function signature (`fillOrder`, `withdraw`, `cancelOrder`) in this specific Tron file within the available tool budget to confirm each one's full CEI ordering; the core finding — total absence of `ReentrancyGuard` inheritance in this contract, contrasted with its presence in the EVM mainnet twin — is confirmed directly from the contract declaration and the escrow-update code shown above.
