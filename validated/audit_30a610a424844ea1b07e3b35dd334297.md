### Title
Shop identity spoofing via webhook HMAC that authenticates only the payload body, not the `shop-domain` header used for tenant routing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authorizes a webhook purely by validating an HMAC that covers only the raw request body, then unconditionally trusts the `X-Shopify-Shop-Domain` header — which is *not* part of the signed material — to decide which tenant ("shop") the webhook belongs to. Any party who can obtain one validly-signed `(body, hmac)` pair for the shared, app-wide `api_secret_key` (e.g. by installing the app on their own store, an unprivileged action) can replay that exact pair while substituting an arbitrary `shop-domain` header, and the gem will report the webhook as valid and hand the attacker-chosen shop identity to the host application's handler. This breaks the identity binding `shop authenticated by HMAC == shop acted upon by the handler`, since the left side is actually empty (no shop is authenticated by the HMAC at all).

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

`shop` is read directly from an attacker-controllable HTTP header, entirely independent of the signed string: [2](#0-1) 

`Utils::HmacValidator.validate` computes and compares the signature only against `verifiable_query.to_signable_string` (i.e. the body), never incorporating the shop header: [3](#0-2) 

`Registry.process` gates entirely on that HMAC check and then forwards `request.shop` unchanged into `WebhookMetadata`, which is delivered to the app's webhook handler as the identity of the tenant the event belongs to: [4](#0-3) 

Because a single app has one shared `api_secret_key` used to sign webhooks for *every* installed shop, a `(body, hmac)` pair that is valid for the attacker's own shop is also valid bit-for-bit for a spoofed `shop-domain` header — the signature check cannot tell the difference, since the shop identity was never part of what was signed. An attacker who is simply an unprivileged merchant/installer of the target app (no `api_secret_key`, no access token, no leaked credentials needed) can:
1. Install the app on their own store and trigger any subscribed webhook topic to receive one legitimate `(raw_body, X-Shopify-Hmac-Sha256)` pair.
2. Replay that exact body and HMAC to the app's webhook endpoint while setting `X-Shopify-Shop-Domain` to a victim shop's domain.
3. `HmacValidator.validate` passes because it only checks the body-derived signature.
4. The handler executes with `WebhookMetadata#shop` equal to the victim's domain, i.e. cross-tenant identity confusion for any host logic keyed off this field (documented as the mechanism apps should use to identify the originating shop).

### Impact Explanation
This breaks the tenant/shop identity boundary the whole webhook subsystem exists to enforce, allowing an unprivileged app installer to make the library assert an arbitrary shop identity for a request it deems "verified." Any host application logic that relies on the gem's HMAC validation plus `WebhookMetadata#shop`/`request.shop` to select or mutate per-tenant state (the intended and documented use of this API) is exposed to cross-tenant access — qualifying as Critical impact (cross-tenant access) under the program's rules.

### Likelihood Explanation
Likelihood is meaningful but not trivial: the attacker must be able to become a legitimate installer of the target app (a normal, unprivileged step for any public app) to harvest one valid `(body, hmac)` sample, and must know/guess a victim shop domain (typically `*.myshopify.com`, often discoverable). No secret key, access token, or privileged account is required — only the gem's own HMAC-validation logic, which never binds the shop identity into the signed payload.

### Recommendation
Bind the shop identity into the material that is HMAC-verified, or otherwise cross-check `request.shop` against an independently trusted source of truth (e.g., the shop associated with the `webhook_id`/registration record stored by the host app) before dispatching to handlers. At minimum, `VerifiableQuery#to_signable_string` for webhook requests should not be the sole basis for trusting `shop`; `Registry.process` should require the caller/host app to confirm `request.shop` corresponds to a shop that actually has this webhook/topic registered, rather than treating HMAC-body-validity as proof of shop identity.

### Proof of Concept
```ruby
# 1. Attacker installs the app on their own store ("attacker-shop.myshopify.com")
#    and receives (or triggers) any legitimate webhook delivery, capturing:
raw_body = '{"id":1}'
valid_hmac = "<value taken from X-Shopify-Hmac-Sha256 header of that real delivery>"

# 2. Attacker replays the exact same body + hmac, but swaps the shop-domain header
spoofed_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => valid_hmac,       # unchanged, still valid for `raw_body`
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # arbitrary, attacker-chosen
  "x-shopify-webhook-id" => "any-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: spoofed_headers)

# 3. This does not raise, because HmacValidator only checks `raw_body` against the HMAC
ShopifyAPI::Webhooks::Registry.process(request)
# => handler.handle(data: WebhookMetadata.new(topic: "orders/create",
#                                              shop: "victim-shop.myshopify.com", # attacker-controlled
#                                              body: {...}, ...))
