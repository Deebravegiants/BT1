### Title
Webhook `shop`/`topic` identity is not bound to the HMAC, allowing cross‑tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC of the raw request body against the app's shared `api_secret_key`. The `shop`, `topic`, and `webhook_id` values — which are taken straight from unauthenticated HTTP headers — are never included in the signed content, yet they are trusted as the tenant identity that gets handed to the app's webhook handler.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop`, `topic`, and `webhook_id` are read directly from HTTP headers with no cross-check against the signed payload: [2](#0-1) [3](#0-2) 

`Utils::HmacValidator.validate` computes the HMAC purely over `to_signable_string` (i.e., only the body) using the app's `api_secret_key`, a secret shared across *every* shop that has the app installed: [4](#0-3) 

`Registry.process` performs this body-only check and then dispatches the handler using the header-derived, unauthenticated `shop`: [5](#0-4) 

Because the same `api_secret_key` signs webhooks for every shop that has the app installed, and only the body bytes are covered by the signature, a `(body, hmac)` pair that was legitimately generated for one tenant remains a valid signature no matter which `shop`/`topic` header it is paired with. The binding that should hold — `shop authenticated == shop delivered to the handler` — is broken: the field acted on (`request.shop`) is not the field verified by the HMAC (`request.to_signable_string`).

### Impact Explanation
An attacker who operates their own shop with the target app installed will legitimately receive real webhook deliveries — correctly signed with the app's shared secret — for topics such as `app/uninstalled`, `shop/redact`, or `customers/data_request`. By replaying the exact captured body + `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header with a victim shop's domain, `Utils::HmacValidator.validate` still returns `true` (the body signature is unaffected by header changes), and `Registry.process` calls the handler with `WebhookMetadata` claiming the victim shop as the source. If the host application's handler for topics like `app/uninstalled` or the mandatory GDPR topics performs destructive actions (deleting stored sessions/access tokens, purging shop data) keyed on `WebhookMetadata#shop`, the attacker can trigger those actions against a shop they do not control — a cross-tenant integrity/availability impact achievable without ever possessing the victim's credentials.

### Likelihood Explanation
Exploitability requires only that the attacker run their own store with the app installed (an unprivileged, self-service action) and be able to send an HTTP request to the app's public webhook endpoint with attacker-controlled headers — no access token, `client_secret`, or victim credentials are needed. The header/body decoupling is a structural property of `Webhooks::Request`/`HmacValidator` in this gem, not a misuse of a documented safeguard, so it is reachable by any external, unauthenticated party capable of receiving one legitimate webhook.

### Recommendation
Bind the identity fields into the signed content (or otherwise cryptographically tie `shop`/`topic`/`webhook_id` to the verified payload) before trusting them, e.g., by including them in `to_signable_string`, or by requiring host applications to independently corroborate the `shop` header against data embedded in the verified JSON body before acting on destructive/administrative topics. At minimum, document prominently that `WebhookMetadata#shop` is not authenticated by the HMAC and must not be used as the sole tenant key for irreversible actions.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and lets the app register for a sensitive topic (e.g., `app/uninstalled`).
2. Attacker uninstalls the app, capturing the resulting webhook POST: raw JSON body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
3. Attacker resends the identical `(B, H)` pair to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC-SHA256(api_secret_key, B)` and finds it matches `H` (headers were never part of the signed content), so validation succeeds.
5. The handler receives `WebhookMetadata.new(topic: "app/uninstalled", shop: "victim.myshopify.com", ...)` and, if it deletes the stored session/access token keyed by `shop`, effectively revokes/erases the victim tenant's data despite the attacker never having interacted with or compromised `victim.myshopify.com`.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
