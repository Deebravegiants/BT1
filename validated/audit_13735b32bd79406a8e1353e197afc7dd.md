### Title
Unbounded per-order bid accumulation in `BidCache` allows mempool memory-exhaustion DoS - (File: `modules/pallets/intents-coprocessor/rpc/src/lib.rs`)

### Summary
The intents RPC bid-watcher builds an in-memory `BidCache` from every `place_bid` extrinsic it observes entering the transaction pool, before those extrinsics are ever included in a block. Bids are keyed by order `commitment`, and each unique `(commitment, filler)` pair is pushed into an unbounded `Vec<BidEntry>` with no per-order or global cap, mirroring the QEMU 9p `v9fs_xattrcreate` pattern where repeated messages sharing the same identifier (`fid` / `commitment`) are accumulated without bound until the process runs out of memory.

### Finding Description
`BidCache::insert` [1](#0-0)  looks up (or creates) the `OrderBids` entry for a `commitment` and pushes a new `BidEntry` onto its `entries: Vec<BidEntry>` whenever the `filler` differs from an existing one. There is no limit on:
- the number of distinct `filler` entries that can accumulate under a single `commitment`, and
- the number of distinct `commitment` keys the top-level `HashMap` can hold.

The only bound applied anywhere in this pipeline is `MAX_ON_CHAIN_BIDS = 30`, but that limit is applied solely to the **on-chain** storage iteration in `get_bids_for_order` [2](#0-1) , not to the in-memory mempool cache.

Entries are populated directly from `run_bid_watcher`, which subscribes to the transaction pool's `import_notification_stream` and, for every transaction that decodes as a `place_bid` call, inserts it into the cache — before any block execution, weight/fee charging outcome, or finalization [3](#0-2) . `filler` is derived from the extrinsic's signed address and `user_op` is arbitrary attacker-controlled bytes with no size bound enforced by this cache path.

Cleanup only happens per `commitment`, and only after the full TTL window has elapsed for that order's `first_seen` timestamp [4](#0-3) . Within that TTL window (bid TTL is a fixed duration, e.g. 300s in tests), an attacker can keep submitting `place_bid` transactions signed by many distinct (even freshly generated, low-balance) accounts, each producing a new unique `filler`, driving `entries.push(entry)` unboundedly and growing process memory. This is directly analogous to the CVE: repeated protocol messages sharing one identifier (`fid` in QEMU's 9p, `commitment` here) that the handler keeps appending to an in-memory structure without any per-key cap, exhausting memory of the process handling requests.

### Impact Explanation
This cache lives inside the node process serving the `intents_getBidsForOrder` / `intents_subscribeBids` RPCs and is driven by the same node's transaction pool import stream — the same process that also runs consensus/block-production duties for a collator exposing this RPC. Sustained, cheap flooding of `place_bid` transactions with distinct signer accounts and large `user_op` payloads targeting one or a few `commitment` values can grow `BidCache` memory without bound until the process is OOM-killed, taking down the intents RPC endpoint and, if co-located with block production, degrading or halting the node's ability to relay/deliver intents and other ISMP traffic ("a route unable to deliver messages"). This is a Medium-severity availability issue matching the CVSS profile of the analog (local/network resource exhaustion, no confidentiality/integrity loss).

### Likelihood Explanation
Any unprivileged intent filler/solver can trigger this: `place_bid` is a normal signed extrinsic, requiring only enough balance to pass `validate_transaction` (existential balance / minimal fee), not inclusion in a block. Generating many throwaway signer accounts is cheap, and each produces a distinct `filler` that bypasses the "replace existing entry" de-dup path (`order.entries.iter_mut().find(|e| e.filler == filler)`) [5](#0-4) , forcing a genuine new `Vec` push each time. Because the cache is populated from the *ready pool* rather than finalized state, none of these transactions ever need to succeed, keeping the cost of the attack low relative to potential impact.

### Recommendation
- Bound the number of `entries` per `OrderBids` (e.g. cap at a small constant like `MAX_ON_CHAIN_BIDS`), evicting the lowest-value/oldest bid when the cap is exceeded.
- Bound the total number of distinct `commitment` keys tracked in `BidCache` (LRU eviction) independent of the TTL sweep.
- Enforce a maximum `user_op` byte size before insertion into the cache.
- Consider requiring a minimum bond/fee-tier check (already implied by `validate_transaction`) plus per-signer rate limiting in `run_bid_watcher` before calling `bid_cache.insert`.

### Proof of Concept
1. Attacker generates N funded (minimal balance) keypairs `k_1..k_N`.
2. For a target order `commitment C`, each `k_i` submits a `place_bid(C, user_op_i)` extrinsic with a large `user_op_i` payload; the extrinsic only needs to pass pool validation, not be included in a block.
3. `run_bid_watcher`'s `import_notification_stream` observes each transaction and calls `bid_cache.insert(C, filler_i, user_op_i)` [6](#0-5) , appending a new `BidEntry` to `OrderBids.entries` for every distinct `filler_i` [7](#0-6) .
4. Repeating with large N (and/or across many distinct `commitment` values and large `user_op` sizes) grows `BidCache`'s heap footprint unboundedly within the TTL window, with no cap in the codebase to stop it, eventually exhausting node memory.

	pub fn insert(
		&self,
		commitment: H256,
		filler: Vec<u8>,
		user_op: Vec<u8>,
	) -> Result<(), String> {
		let entry = BidEntry { filler: filler.clone(), user_op };

		let mut bids = self.bids.write().map_err(|e| format!("BidCache lock poisoned: {e}"))?;
		let order = bids
			.entry(commitment)
			.or_insert_with(|| OrderBids { first_seen: Instant::now(), entries: Vec::new() });
		if let Some(existing) = order.entries.iter_mut().find(|e| e.filler == filler) {
			*existing = entry;
		} else {
			order.entries.push(entry);
		}
		Ok(())
	}
