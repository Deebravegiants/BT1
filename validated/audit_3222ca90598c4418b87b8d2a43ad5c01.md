Based on the analog bug class — a mutating operation lacking a guard against re-invocation after a terminal/genesis state has already been reached — the strongest match I found in this codebase is in `Wallet.create()` / `Wallet.import()`.

### Title
Missing "wallet already exists" guard allows re-invoking `Wallet.create`/`Wallet.import` to overwrite the primary seed - (File: features/wallet/module/wallet.js)

### Summary
`GenesisGroup.purchase`/`commit` remained callable after the one-time "launch" event because they lacked a state check against the terminal state. In `features/wallet/module/wallet.js`, `create` and `import` are the functions that establish the wallet's one and only seed (the "genesis" event of the wallet), but unlike sibling seed-mutating methods in the same class, they contain no check for `exists()`/lock state before overwriting `SEED_KEY`.

### Finding Description
`Wallet.create` writes directly to `SEED_KEY` via `#setSeed` without first checking whether a wallet has already been created: [1](#0-0) 

`Wallet.import` simply validates the mnemonic and forwards straight into `create`: [2](#0-1) 

This is inconsistent with other mutating methods in the same module, which explicitly assert a required precondition state before proceeding, e.g. `addSeed` and `removeManySeeds` both call `#assertWalletIsUnlocked()` before touching storage: [3](#0-2) [4](#0-3) 

There is an `exists()` helper already defined in the class that checks for a pre-existing encrypted seed, but it is never consulted inside `create`/`import`: [5](#0-4) 

`#setSeed` will happily overwrite `SEED_KEY` (and the passphrase metadata) regardless of whether a seed is already present: [6](#0-5) 

The intended flow is documented as a one-way state machine where `CREATE`/`IMPORT` should only be reachable from the `Empty` state (no seed present), transitioning to `Locked`: [7](#0-6) 

However, this gating is only documented/implied at the `features/application` state-machine layer, not enforced inside `wallet.js` itself. I was not able to fully verify, within the available tool budget, whether `features/application/src/modules/application.ts` actually enforces this state check before dispatching to `wallet.create`/`wallet.import`, or whether these wallet methods are reachable directly (e.g. via the headless SDK's public `wallet` module surface) without that gate.

### Impact Explanation
If `create`/`import` can be invoked a second time (directly, or via any code path that bypasses the application-level state machine) after a wallet already exists, an attacker with local/API access could overwrite the user's `SEED_KEY` with an attacker-chosen mnemonic and passphrase. Since the attacker knows the new mnemonic, any funds later deposited to addresses derived from the replaced seed would be attacker-controlled — a direct wallet-compromise/seed-swap primitive. At minimum, it enables silent, unauthorized destruction of the original seed material (loss of funds access) for a user who has already completed onboarding.

### Likelihood Explanation
Likelihood depends entirely on whether the `features/application` layer's state machine (`Empty --> Locked : CREATE/IMPORT`) is the only path that invokes `wallet.create`/`wallet.import`, or whether these methods are also exposed/callable independently (e.g., directly through the headless module registry) once the app has already moved past the `Empty` state. I could not confirm this boundary within the current investigation, so likelihood is uncertain — this should be verified by checking every call site of `wallet.create`/`wallet.import` in `features/application` and the headless SDK for an explicit `exists()`/state guard.

### Recommendation
Add an explicit guard in `Wallet.create` (and thus `Wallet.import`, which delegates to it) that throws if `await this.exists()` is already true, mirroring the `#assertWalletIsUnlocked()` pattern used by `addSeed`/`removeManySeeds`. This makes the invariant "a wallet can only be created once" enforced at the module boundary itself, rather than relying solely on an external state machine to gate the call.

### Proof of Concept
Not executed — this report is based on static code review only. A concrete PoC would require confirming (via a Devin session with runtime access) whether `exodus.wallet.create({...})` or `exodus.wallet.import({...})` can be called a second time through the headless SDK after `exodus.application.create()`/`unlock()` has already completed, without the application module intercepting/rejecting the call.
