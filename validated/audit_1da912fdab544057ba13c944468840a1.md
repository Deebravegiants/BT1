## Title
Webhook `shop` domain header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
The Solidity report's core issue is a broken invariant: a value is *acted upon* by the code while a security-relevant check (there, a gas-limit assumption; the analog binding here, an HMAC signature) doesn't actually cover it. In `ShopifyAPI::Webhooks::Request`/`Registry`, the same class of bug exists: the webhook's `shop` domain (and `topic`, `api_version`, `webhook_id`) are read straight from unauthenticated HTTP headers, while the HMAC signature only covers the raw JSON body.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` (and `topic`, `api_version`, `webhook_id`) are pulled straight from HTTP headers with no signature coverage: [2](#0-1) 

`Registry.process` validates the HMAC using `HmacValidator.validate(request)`, which internally calls `verifiable_query.to_signable_string` — i.e. only the body — and then passes `request.shop` straight into the dispatched `WebhookMetadata` without any further binding to the signature: [3](#0-2) 

`HmacValidator.validate_signature` computes the HMAC purely from `verifiable_query.to_signable_string` (the body) and the app's shared `api_secret_key`: [4](#0-3) 

Because every shop installing the same app shares the same `api_secret_key` used to sign all of that app's webhooks, an attacker who controls (or has legitimately installed the app on) one shop can capture a validly-signed webhook body/HMAC pair from their own shop, then replay it to the app's webhook endpoint while substituting a different value in the `x-shopify-shop-domain` (or `shopify-shop-domain`) header. `HmacValidator.validate` will still return `true` because it never inspects the shop header — only the body bytes are checked. The resulting `WebhookMetadata` passed to the app's registered handler will report an attacker-chosen `shop` that the request was never actually signed for.

This is precisely the "bytes verified versus bytes parsed" / "field acted on but not covered by the HMAC" bug class: the field the handler trusts to select tenant (`shop`) is disjoint from the field the signature actually authenticates (`raw_body`).

### Impact Explanation
Any app built on this gem that uses `WebhookMetadata#shop` to determine which merchant/tenant a webhook payload belongs to (a very common pattern — e.g., looking up that shop's session/access token, or writing the payload into that shop's tenant data) can be tricked into attributing attacker-controlled webhook data to a different, victim shop. This crosses the tenant boundary using only a shared, non-per-shop secret, satisfying the "cross-tenant access" criterion.

### Likelihood Explanation
Requires the attacker to be able to install the same app on at least one shop (or otherwise obtain one validly-signed webhook body/HMAC pair for that app) and to send an HTTP request to the app's public webhook endpoint with a spoofed `shop-domain` header — both are unprivileged, internet-reachable actions once the app is installed by anyone. No access token, `client_secret`, or leaked credential is required from the attacker's side beyond being a legitimate (even free-trial) merchant of the target app.

### Recommendation
Include the shop domain (and topic) in the signable material actually verified by the HMAC check, or otherwise cryptographically bind the header-derived `shop` to the signed body before it is handed to application handlers, so that `Registry.process` cannot dispatch data under a `shop` value that wasn't part of what was authenticated.

### Proof of Concept
1. Install the target app on attacker-owned shop `attacker.myshopify.com`; capture a legitimate webhook delivery, including its raw body `B` and header `x-shopify-hmac-sha256: H` (valid because `H = HMAC(api_secret_key, B)`).
2. Replay a POST to the app's webhook endpoint with the same body `B` and header `H`, but set `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `HmacValidator.validate(request)` → `true` (only `B`/`H` are checked, per `lib/shopify_api/utils/hmac_validator.rb:26-31` and `lib/shopify_api/webhooks/request.rb:35-38`).
4. The registered handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed(B), ...)`, causing the app to process attacker-controlled data as though it came from the victim shop.
