### Title
Creator-controlled royalty updates let a token creator front-run marketplace settlements and drain seller/buyer proceeds - (File: `aptos-move/move-examples/marketplace/sources/token_offer.move`, `collection_offer.move`, `listing.move`)

### Summary
The Aptos marketplace example module computes the royalty owed on a sale by re-reading the token's live `Royalty` resource (`numerator`/`denominator`/`payee_address`) at settlement time, instead of snapshotting/bounding it when the listing or offer was created. Because the collection/token creator holds the `royalty::MutatorRef` and can call `royalty::update` at any time up to numerator == denominator (100%), a malicious creator can observe a pending `sell_tokenv1`/`sell_tokenv2` (token offer), `sell_tokenv1`/`sell_tokenv2` (collection offer), or listing-purchase transaction in the mempool and front-run it by maximizing their own royalty cut. This is the same bug class as the Story Protocol issue: an external/authority-controlled value that determines how much of an escrowed asset is redirected is read unvalidated and unbounded at execution time, with no caller-specified maximum enforced.

### Finding Description
In `token_offer.move::settle_payments` (and the structurally identical `collection_offer.move::settle_payments`), the royalty amount is computed directly from the royalty numerator/denominator supplied by the caller (which itself was read fresh from the token/collection at call time via `tokenv1::get_royalty` / `tokenv2::royalty`): [1](#0-0) [2](#0-1) 

There is no cap supplied by the buyer/seller at offer-creation time (`TokenOffer`/`CollectionOffer` only store `item_price`, `fee_schedule`, `expiration_time` — no `max_royalty_bps` or similar): [3](#0-2) 

The royalty percentage itself is fully controlled by whoever holds the `royalty::MutatorRef` for the token/collection (typically the creator), and `royalty::update` performs no rate-limiting, timelock, or "cannot exceed previously agreed value" check — it simply overwrites the resource: [4](#0-3) 

The only invariant enforced is `numerator <= denominator` inside `create()`, i.e., the royalty can legitimately be pushed all the way to 100%: [5](#0-4) 

`listing.move::compute_royalty` has the same read-at-settlement pattern, only clamped so the royalty cannot exceed the sale price (`bounded_percentage` uses `math64::min`), but it still allows the creator to seize up to 100% of the sale proceeds at the moment of purchase: [6](#0-5) [7](#0-6) 

Custody invariant broken: a seller accepting a token/collection offer, or a buyer completing a fixed-price purchase, expects proceeds to be split according to the royalty rate that existed when they decided to transact. Because the rate is re-read live from creator-controlled state with no user-specified maximum enforced by the settlement function, the creator can unilaterally redirect escrowed coins away from the seller by front-running the settlement transaction — exactly mirroring the unvalidated, unbounded external-call value in the original `RoyaltyModule._distributeRoyaltyTokensToPolicies` bug.

### Impact Explanation
A malicious/compromised token or collection creator can:
1. Watch the mempool for a pending `sell_tokenv1`/`sell_tokenv2` call against their token's `TokenOffer`/`CollectionOffer`, or a pending fixed-price `purchase` against a `Listing`.
2. Front-run it with a transaction calling `royalty::update` (via their `MutatorRef`) to raise the royalty numerator to (near) the denominator.
3. Let the victim's settlement transaction execute afterward — `settle_payments` will now extract up to the full escrowed price as "royalty" and deposit it to the creator's `royalty_payee` address instead of the seller, draining the seller's expected proceeds from an on-chain escrow (`CoinOffer<CoinType>`).

This is a custody-grade impact: it corrupts the split of escrowed `Coin<CoinType>` value, redirecting funds to an unprivileged (from the buyer/seller's perspective) creator-controlled address instead of the rightful seller, i.e., a supply/custody accounting corruption that moves value to the wrong holder.

### Likelihood Explanation
Requires only that the attacker (the token/collection creator) hold the standard `royalty::MutatorRef`, which is a normal capability creators are expected to have for legitimate royalty adjustments — no privileged governance or leaked key is needed. The attack is a straightforward mempool front-run (observe pending `sell_tokenv1`/`sell_tokenv2`/`purchase` tx, submit a higher-priority `royalty::update` tx). It is opportunistic and requires the creator to be actively malicious, but does not require any other party's cooperation or error.

### Recommendation
Snapshot the royalty rate (numerator/denominator/payee) at `TokenOffer`/`CollectionOffer`/`Listing` creation time and store it as part of the escrow resource, or require the accepting/purchasing party to supply a `max_royalty_bps` parameter that `settle_payments`/`compute_royalty` must not exceed, aborting the transaction otherwise (mirroring the `maxRts` fix used by Story Protocol).

### Proof of Concept
Conceptual sequence (Move pseudo-steps against `token_offer.move`):
1. Purchaser calls `token_offer::init_for_tokenv2` with `item_price = 500`, funding `CoinOffer<AptosCoin>` with 500 coins.
2. Seller submits `sell_tokenv2` expecting the current royalty (e.g., 5%) to apply, netting ~475 coins after commission.
3. Malicious creator observes the seller's `sell_tokenv2` transaction in the mempool and front-runs it with `royalty::update(mutator_ref, royalty::create(denominator, denominator, creator_addr))`, setting royalty to 100%.
4. Seller's `sell_tokenv2` executes afterward; `royalty::royalty(token)` now returns 100%, so `settle_payments` computes `royalty_charge = price * denominator / denominator = price = 500`, sending the entire 500 coins to the creator via `aptos_account::deposit_coins(royalty_payee, royalties)` at line 386, leaving the seller with 0 (or a failed `coin::extract` if commission also needs coins, causing DoS instead — either way the seller is harmed and did not consent to the new rate).

Note: full unit-test execution and confirmation of whether `aptos_token.move`'s public entry points expose an unrestricted `royalty` mutation function to arbitrary creators could not be completely verified within the indexed excerpts; a Devin session with full repo/build access would be needed to compile and run a concrete PoC test confirming exact coin balances before/after the front-run.

    /// Calculates a bounded percentage that can't go over 100% and handles 0 denominator as 0
    public inline fun bounded_percentage(amount: u64, numerator: u64, denominator: u64): u64 {
        if (denominator == 0) {
            0
        } else {
            math64::min(amount, math64::mul_div(amount, numerator, denominator))
        }
    }
