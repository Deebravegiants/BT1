### Title
Unchecked `U128` → `u64` downcast in `swap_token_amount_base_out` can silently truncate the computed swap input, enabling near-total pool drainage - (File: `program/src/math.rs`, `program/src/processor.rs`)

### Summary
The reported bug class (unchecked downcasting of an unbounded/attacker-influenced arithmetic result to a smaller integer type, causing catastrophic loss) has a plausible analog in the `SwapBaseOut`/`SwapBaseOutV2` instruction path. `Calculator::swap_token_amount_base_out` computes the required input amount as a `U128` with no upper bound check, and the caller in `processor.rs` truncates it to `u64` via `.as_u64()` before using it both as the slippage bound and as the actual amount transferred from the user.

### Finding Description
`Calculator::swap_token_amount_base_out` computes `amount_in` as `coin * amount_out / (pc - amount_out)` (or the symmetric PC2Coin case) entirely in `U128` arithmetic with only `checked_sub`/`checked_mul`/`checked_ceil_div` `.unwrap()` guards against sub-overflow/div-by-zero, but no bound restricting the final magnitude: [1](#0-0) 

An unprivileged caller of `process_swap_base_out` / `process_swap_base_in_v2`'s sibling `process_swap_base_out_v2` can choose `amount_out` arbitrarily close to `total_pc_without_take_pnl` (or `total_coin_without_take_pnl`), driving the denominator `(pc - amount_out)` toward `1`. This makes the numerator `coin * amount_out` dominate, and for realistic pool sizes (e.g. `coin`, `pc` on the order of `1e15` each) the resulting `amount_in` easily exceeds `u64::MAX` while still fitting comfortably inside `U128`.

The result is then downcast without a checked/`try_into` conversion: [2](#0-1) [3](#0-2) 

This mirrors the Solidity `uint96(result.totalAmountIn)` case exactly: an intermediate value computed in a wide type (`U128`/`uint256`) that can legitimately exceed the narrow target type (`u64`/`uint96`) is downcast without any check. Note that elsewhere in the same file, the authors clearly recognize the need for checked downcasts and use `Calculator::to_u64`, which uses `try_into` and returns `AmmError::ConversionFailure` on overflow: [4](#0-3) 
but the swap-input computation bypasses this safe helper and uses the raw, unchecked `.as_u64()` instead.

Downstream, the (possibly wrapped) `swap_in_after_add_fee` value is what is compared against `user_source.amount` / `max_amount_in`, and — critically — is the exact amount transferred from the user via `Invokers::token_transfer`, while `swap.amount_out` (near the full vault balance) is paid out to the user: [5](#0-4) 

### Impact Explanation
If the `.as_u64()` truncation behaves like a silent wraparound (as the `uint` crate's `construct_uint!`-generated types have historically done in some versions), an attacker can pay a tiny, wrapped-down amount of input tokens while withdrawing almost the entirety of the opposite vault's balance — a direct, unbounded theft of pooled LP/user funds and insolvency of the AMM. This would qualify as Critical/High under the stated "concrete theft or insolvent pool accounting" bar.

### Likelihood Explanation
I was not able to confirm from the indexed files which exact version of the `uint` crate's `construct_uint!` macro is vendored (i.e., whether `.as_u64()` in this build panics on overflow rather than truncating) — the crate version is set in `Cargo.toml`/`Cargo.lock`, which I could not inspect through the available search tools [6](#0-5) . If it panics, the practical impact is a denial-of-service/failed transaction rather than fund loss, weakening the analog; if it truncates silently (as the original Solidity report's downcast did), the impact is Critical as described above. This uncertainty should be resolved by checking the exact `uint` crate version pinned in the repo's `Cargo.lock` before treating this as a confirmed finding.

### Recommendation
Replace the raw `.as_u64()` calls following `swap_token_amount_base_out`/`swap_token_amount_base_in` fee-scaling with the existing checked helper `Calculator::to_u64`, and propagate an error (e.g., `AmmError::ConversionFailure` or a new `CalculationOverflow`) instead of truncating, mirroring the fix already applied in the referenced Sherlock report (switching to unchecked-but-wide types with explicit error propagation on overflow).

### Proof of Concept
Not independently confirmed in a live/test environment (no terminal/build access in this mode) — this write-up is based on static analysis of `program/src/math.rs` and `program/src/processor.rs`. To validate: instantiate a pool with `coin`/`pc` vault balances in the ~`1e15` range, call `SwapBaseOut` (or `SwapBaseOutV2`) with `amount_out = total_pc_without_take_pnl - 1`, and inspect whether `swap_in_after_add_fee` (post `.as_u64()`) is smaller than the mathematically correct `U128` result, and whether the actual token transfer uses the truncated value.

```rust
    pub fn swap_token_amount_base_out(
        amount_out: U128,
        total_pc_without_take_pnl: U128,
        total_coin_without_take_pnl: U128,
        swap_direction: SwapDirection,
    ) -> U128 {
        let amount_in;
        match swap_direction {
            SwapDirection::Coin2PC => {
                // (x + delta_x) * (y + delta_y) = x * y
                // (coin + amount_in) * (pc - amount_out) = coin * pc
                // => amount_in = coin * pc / (pc - amount_out) - coin
                // => amount_in = (coin * pc - pc * coin + amount_out * coin) / (pc - amount_out)
                // => amount_in = (amount_out * coin) / (pc - amount_out)
                let denominator = total_pc_without_take_pnl.checked_sub(amount_out).unwrap();
                amount_in = total_coin_without_take_pnl
                    .checked_mul(amount_out)
                    .unwrap()
                    .checked_ceil_div(denominator)
                    .unwrap()
            }
            SwapDirection::PC2Coin => {
                // (x + delta_x) * (y + delta_y) = x * y
                // (pc + amount_in) * (coin - amount_out) = coin * pc
                // => amount_out = coin - coin * pc / (pc + amount_in)
                // => amount_out = (coin * pc + coin * amount_in - coin * pc) / (pc + amount_in)
                // => amount_out = coin * amount_in / (pc + amount_in)

                // => amount_in = coin * pc / (coin - amount_out) - pc
                // => amount_in = (coin * pc - pc * coin + pc * amount_out) / (coin - amount_out)
                // => amount_in = (pc * amount_out) / (coin - amount_out)
                let denominator = total_coin_without_take_pnl.checked_sub(amount_out).unwrap();
                amount_in = total_pc_without_take_pnl
                    .checked_mul(amount_out)
                    .unwrap()
                    .checked_ceil_div(denominator)
                    .unwrap()
            }
        }
        return amount_in;
    }
```
