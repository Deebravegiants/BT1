### Title
`describeWithdrawal` reports `completed` with a mutable `pending_sign_id` as `txHash` for BTC withdrawals when run client-side - ([File: packages/intents-sdk/src/bridges/omni-bridge/omni-bridge.ts])

### Summary
For UTXO-chain (Bitcoin) withdrawals, `OmniBridge.describeWithdrawal` returns `status: "completed"` with `txHash` set to `transfer.utxo_meta?.pending_sign_id` when `typeof window !== "undefined"`, instead of waiting for `transfer.finalised?.transaction_hash`. The code's own comment acknowledges `pending_sign_id` "may change if the BTC transfer fails to be submitted," meaning a status already reported as final/completed can point to a hash that never confirms.

### Finding Description
The invariant that should hold is: for withdrawal index `i`, if `describeWithdrawal` reports `{status: "completed", txHash: H}`, then `H` must equal the eventual destination-chain (Bitcoin) transaction hash of that withdrawal — i.e., a hash that will not later change.

In `describeWithdrawal` at [1](#0-0) , for `isUtxoChain(destinationChain)` the code branches purely on the JS execution environment:
```
txHash = typeof window !== "undefined"
    ? transfer.utxo_meta?.pending_sign_id
    : transfer.finalised?.transaction_hash;
```
The adjacent comment explicitly states `pending_sign_id` "is not the finalised tx hash" and "may change if the BTC transfer fails to be submitted." Despite this, the function still returns `{ status: "completed", txHash: pending_sign_id }` (line 730) when running in a browser context — it does not gate on `finalised` at all for the client-side branch.

This value flows directly into `watchWithdrawal` in [2](#0-1) , which treats `status === "completed"` as terminal and resolves the poll with `{ hash: status.txHash }` — there is no re-check or reconciliation against `finalised.transaction_hash` afterward. No other guard (`validateAddress`, `compareAddresses`, `validateWithdrawal`, `matchesRequest`, or intents-contract signature/nonce checks) touches this status-reporting path, since this is purely a bridge-status polling function operating after the intent has already settled.

An unprivileged user withdrawing their own BTC (or any integrator running the SDK client-side, e.g., in a wallet extension or dApp frontend) will have `watchWithdrawal`/`waitForWithdrawalCompletion` resolve "completed" with a `pending_sign_id` that the bridge itself documents as subject to change if BTC submission fails and gets retried with a new transaction. The same withdrawal index, if checked from a server-side (Node) context, would correctly wait for `finalised.transaction_hash` before reporting completion — so the SAME withdrawal state produces two different reported outcomes purely based on `typeof window`.

### Impact Explanation
An integrator relying on the client-side SDK to detect withdrawal completion (a common pattern for wallet/dApp UIs) can persist/credit/refund based on `pending_sign_id`, then later have Bitcoin submission fail and be resubmitted with a genuinely different `transaction_hash`. Their stored "completed" record now references a hash that never confirms on-chain, corrupting reconciliation, double-crediting logic, or downstream refund automation. This matches the High-severity category "a status or hash misreport making an integrator credit or refund twice." It is repeatable for every BTC withdrawal run in a browser context and costs the attacker/triggering party nothing — it merely requires normal usage of the SDK client-side, not any adversarial input.

### Likelihood Explanation
Preconditions: withdrawal destination is a UTXO chain (Bitcoin) routed via Omni Bridge, and the SDK is executed in an environment where `window` is defined (any browser-based integrator, which is a common integration pattern for this SDK). No special attacker input, malicious solver, or relayer misbehavior is needed — the divergence is deterministic and triggered purely by the BTC submission failing/retrying, a documented, real occurrence per the code's own comment. This is not a "malicious RPC/bridge API" issue; the two data fields (`pending_sign_id`, `finalised.transaction_hash`) are both legitimately returned by the bridge API, and the bug is in this repo's choice of which one to trust and report as final. Given that BTC transfer submission failures are called out as a real occurrence in the code comment, likelihood is non-trivial and fully repeatable across affected withdrawals.

### Recommendation
Remove the `typeof window !== "undefined"` branch that returns `pending_sign_id` as a `completed` `txHash`. Either:
- Never report `status: "completed"` for UTXO chains until `transfer.finalised?.transaction_hash` is available (treat missing `finalised` as `pending` regardless of environment), or
- If a "fast" UI signal is desired for UX purposes, expose it via a distinct, clearly-provisional field (not as `status: "completed"` with a `txHash` that satisfies the STATUS TRUTH contract), so callers cannot mistake it for the final settled hash.

### Proof of Concept
```ts
// omni-bridge.test.ts
import { vi, describe, it, expect } from "vitest";

describe("describeWithdrawal - UTXO client-side hash mismatch", () => {
  it("reports completed with pending_sign_id client-side, differing from eventual finalised hash", async () => {
    vi.stubGlobal("window", {});

    const bridge = /* construct OmniBridge with mocked omniBridgeAPI */;
    vi.spyOn(bridge.omniBridgeAPI, "getTransfer").mockResolvedValue([
      {
        recipient: "btc:bc1qxyz...",
        utxo_meta: { pending_sign_id: "PENDING_HASH_1" },
        finalised: null,
      },
    ]);

    const status1 = await bridge.describeWithdrawal({
      landingChain: "btc",
      index: 0,
      withdrawalParams: {/* ... */},
      tx: { hash: "near-tx", accountId: "acc.near" },
    });
    expect(status1).toEqual({ status: "completed", txHash: "PENDING_HASH_1" });

    // Later, BTC submission is retried and produces a different final hash
    vi.spyOn(bridge.omniBridgeAPI, "getTransfer").mockResolvedValue([
      {
        recipient: "btc:bc1qxyz...",
        utxo_meta: { pending_sign_id: "PENDING_HASH_1" },
        finalised: { transaction_hash: "FINAL_HASH_2" },
      },
    ]);

    const status2 = await bridge.describeWithdrawal({
      landingChain: "btc",
      index: 0,
      withdrawalParams: {/* ... */},
      tx: { hash: "near-tx", accountId: "acc.near" },
    });

    // STATUS TRUTH violated: same withdrawal index reported two different "completed" hashes
    expect(status2.txHash).not.toEqual(status1.txHash);
    expect(status2).toEqual({ status: "completed", txHash: "FINAL_HASH_2" });

    vi.unstubAllGlobals();
  });
});
```
This demonstrates that for the identical withdrawal index, the first client-side call reports `completed` with `PENDING_HASH_1`, while the true/eventual (server-side-equivalent) hash is `FINAL_HASH_2` — a direct violation of "txHash reported as completed == the final destination-chain hash."
