## Title
Webhook shop/topic identity spoofing via HMAC that only covers the raw body — ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by HMAC-verifying the raw request body via `Utils::HmacValidator.validate`. However, `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` — none of the HTTP headers (`shop-domain`, `topic`, `api-version`, `webhook-id`) are included in the signed material. Those header-derived values are nevertheless what get passed on, unauthenticated, to the app's business logic as the tenant identity (`WebhookMetadata#shop`) and event type (`WebhookMetadata#topic`). This breaks the intended identity binding: `HMAC(secret, verified_bytes) == valid` should imply `shop == originating_shop`, but the gem only proves `HMAC(secret, body) == valid`; `shop` and `topic` are read from unauthenticated header bytes.

### Finding Description
`lib/shopify_api/webhooks/request.rb`: [1](#0-0) 
`shop`, `topic`, `api_version`, and `webhook_id` are all sourced purely from HTTP headers, while `to_signable_string` (the value that gets HMAC-verified) returns only `@raw_body`.

`lib/shopify_api/utils/hmac_validator.rb` computes and compares the HMAC strictly over `verifiable_query.to_signable_string`: [2](#0-1) 

`lib/shopify_api/webhooks/registry.rb#process` treats a valid body HMAC as sufficient authorization to hand the (header-derived, unauthenticated) `shop` and `topic` to the app's handler: [3](#0-2) 

Because the signature only binds the body, any two values `(body, hmac)` that are a valid Shopify-signed pair for **some** topic/shop can be replayed with a completely different `shop-domain` and `topic` header pair and will still pass `HmacValidator.validate`. The equality actually enforced is `HMAC(secret, body) == received_hmac`; the equality the app logic relies on — `shop header == shop that produced this HMAC` — is never checked.

### Impact Explanation
An unprivileged user who can install the target app on their own shop (a normal, unprivileged onboarding action) will legitimately receive real, validly-signed webhook deliveries (body + `X-Shopify-Hmac-Sha256`) from Shopify for their own shop. They can capture one such `(raw_body, hmac)` pair and replay it directly to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` header (and/or `X-Shopify-Topic` header) with a victim shop's domain / a different topic. `Registry.process` will accept it as authentic (body HMAC still matches) and invoke the app's handler with `shop: <victim shop>`, `topic: <attacker chosen>`, and `body: <attacker-influenced content from their own shop>`. This is a cross-tenant identity spoof: the attacker injects an event that the host application will treat as coming from another merchant's shop, potentially triggering shop-scoped side effects (data updates, uninstall/GDPR handling, billing events, etc.) keyed to the victim's shop. This satisfies the Critical "cross-tenant access" impact bucket.

### Likelihood Explanation
Requires only: (1) ability to install the app on an attacker-controlled shop (the normal, unprivileged path every merchant goes through) to obtain one genuine `(body, hmac)` pair, and (2) the ability to send an arbitrary HTTP POST to the app's public webhook endpoint with custom headers — no `api_secret_key`, access token, or privileged access is needed. This is directly exploitable by any internet user with a free Shopify dev/partner store.

### Recommendation
Bind the tenant/topic identity into the verified material instead of trusting unauthenticated headers:
- Include `shop`, `topic`, and any other header value used for authorization/routing decisions in the HMAC-signable string (Shopify's headers are not designed to be independently signed, so this can't be perfectly fixed client-side), **or**
- At minimum, document/require that hosts validate the `X-Shopify-Shop-Domain` header against the shop that the app actually expects/has an active session for before trusting it, and avoid using it as an unauthenticated identity key inside the gem's own `WebhookMetadata`.
- Consider rejecting webhook requests where the `shop-domain` header does not correspond to a shop with an active/known session for this app installation before dispatching to handlers.

### Proof of Concept
1. Install the target Shopify app on attacker-owned shop `attacker.myshopify.com`; capture a legitimate webhook delivery, e.g. `orders/create`, giving `(raw_body, hmac)`.
2. Send a forged HTTP request to the app's public webhook endpoint:
```
POST /webhooks
X-Shopify-Topic: orders/create
X-Shopify-Hmac-Sha256: <captured hmac>
X-Shopify-Shop-Domain: victim.myshopify.com
X-Shopify-Webhook-Id: <any>
X-Shopify-Api-Version: 2024-01

<captured raw_body>
```
3. `ShopifyAPI::Webhooks::Registry.process` computes `HmacValidator.validate` over `raw_body` only [4](#0-3) , which succeeds, and dispatches the handler with `shop: "victim.myshopify.com"` even though the payload actually originated from the attacker's own shop.
