### Title
Confirmed HRMP open-channel deposits can become permanently unreservable if a para offboards at the exact session boundary that processes the request - ([File: polkadot/runtime/parachains/src/hrmp.rs])

### Summary
`Pallet::process_hrmp_open_channel_requests` only creates the `HrmpChannels` entry and never touches reserved balances when either side of the channel fails the `is_valid_para` check, yet it unconditionally calls `decrease_open_channel_request_count` / `decrease_accepted_channel_request_count` and removes the entry from `HrmpOpenChannelRequestsList`/`HrmpOpenChannelRequests`. If a parachain scheduled for offboarding has a confirmed pending request at the same session boundary, the request is silently dropped and its `sender_deposit` reservation is never released, because the offboarding cleanup routine (`clean_hrmp_after_outgoing`) runs after this function in the same session-change hook and can no longer find the (already-removed) request to unreserve.

### Finding Description
`HrmpOpenChannelRequest` stores a `sender_deposit: Balance` that is reserved when `hrmp_init_open_channel` is called [1](#0-0) . The confirmation path (`hrmp_accept_open_channel`) marks `request.confirmed = true` and reserves the recipient's deposit, leaving the request queued in `HrmpOpenChannelRequestsList` for the next session boundary.

At the next session change, `Pallet::initializer_on_new_session` invokes `paras::Pallet::<T>::initializer_on_new_session` first (which finalizes lifecycle transitions and returns the list of `outgoing_paras` being offboarded this session) and only afterwards calls `hrmp::Pallet::<T>::initializer_on_new_session`, which internally runs `process_hrmp_open_channel_requests` before iterating `outgoing_paras` to call `clean_hrmp_after_outgoing`. By the time `process_hrmp_open_channel_requests` runs, `paras::Pallet::<T>::is_valid_para` already reflects the para's removal from the lifecycle map for a para offboarding in that very session.

Inside `process_hrmp_open_channel_requests`, for each confirmed request it checks `if paras::Pallet::<T>::is_valid_para(sender) && is_valid_para(recipient)` before inserting the `HrmpChannels` entry. If the check fails (because one side just became invalid), the function skips channel creation entirely but still falls through to decrement the open/accepted channel counters and remove the request from `HrmpOpenChannelRequestsList`/`HrmpOpenChannelRequests` — there is no `T::Currency::unreserve` call on this branch. When `clean_hrmp_after_outgoing` subsequently runs for that same outgoing para, it looks for pending requests still present in storage to refund; since the request was already deleted, it finds nothing to unreserve, and the sender's reserved deposit is orphaned permanently.

### Impact Explanation
The `sender_deposit` reserved via `ReservableCurrency::reserve` when the channel was initiated remains locked in the sender account's reserved balance indefinitely, with no on-chain state (`HrmpChannels`, `HrmpOpenChannelRequests`) referencing it and no automated or extrinsic path to unreserve it. This is a silent, permanent fund lock, violating the invariant that every reserved HRMP deposit must be either backing an active channel or returned to its owner.

### Likelihood Explanation
This requires a specific but realistic timing precondition: a parachain must have a confirmed (`hrmp_accept_open_channel`'d) but not-yet-processed HRMP open-channel request, and be scheduled to offboard (deregister) exactly at the next session boundary that also processes that request. Parachain offboarding is governance-triggered but the timing coincidence with a confirmed HRMP request can occur incidentally (e.g., a chain simultaneously winding down its parachain slot while an HRMP channel negotiation was in flight), or could be intentionally engineered by a chain operator who controls both when they schedule their own deregistration and when they call `hrmp_accept_open_channel`, so the loss is deterministic and repeatable once the ordering is set up.

### Recommendation
In `process_hrmp_open_channel_requests`, when `is_valid_para` fails for either `channel_id.sender` or `channel_id.recipient`, unreserve `request.sender_deposit` (and any recipient deposit already reserved) before removing the request from storage, mirroring the unreserve logic already present in `clean_hrmp_after_outgoing`. Alternatively, reorder the session-change hook so `clean_hrmp_after_outgoing` for `outgoing_paras` runs before `process_hrmp_open_channel_requests`, ensuring stale requests involving offboarding paras are refunded and purged before the open/accept processing loop runs.

### Proof of Concept
Rust integration test in `polkadot/runtime/parachains/src/hrmp/tests.rs`:
1. Register two paras, A (sender) and B (recipient), fund and reserve deposits via `Hrmp::hrmp_init_open_channel(A, B, ...)`.
2. Call `Hrmp::hrmp_accept_open_channel(B, A)` so the request is `confirmed = true`.
3. Before the next session change, schedule para B (or A) for offboarding (e.g., via `Paras::schedule_para_cleanup`/normal deregistration flow used elsewhere in the test suite).
4. Record `sender_account`'s `T::Currency::reserved_balance` prior to the session change.
5. Trigger the session change that runs `Initializer::on_new_session`, invoking both `paras::initializer_on_new_session` (offboarding B) and `hrmp::initializer_on_new_session` (processing the confirmed request).
6. Assert: `HrmpChannels::<Test>::get(&channel_id)` is `None` (channel not created); `HrmpOpenChannelRequests::<Test>::get(&channel_id)` is `None` (request removed); and `T::Currency::reserved_balance(sender_account)` is unchanged from before the session change (deposit still locked) — demonstrating the deposit is neither applied to a channel nor released.
