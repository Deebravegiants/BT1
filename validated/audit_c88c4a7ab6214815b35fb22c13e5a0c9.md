Webhook `shop`, `topic`, and `webhook-id` identity fields are not covered by the HMAC signature, allowing cross-tenant webhook spoofing via header substitution - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes/validates the HMAC exclusively over the raw HTTP body [1](#0-0) , while the `shop`, `topic`, `api_version`, and `webhook_id` values used to route and attribute the webhook are read directly from unauthenticated HTTP headers [2](#0-1) . `Registry.process` only checks the HMAC of the body before dispatching to the handler with the header-derived `shop` [3](#0-2) , and `WebhookMetadata.shop` is a plain struct field with no binding to the signed content [4](#0-3) . This is the same bug class as the Curve `useEth` report: a field that is acted upon (`shop`, used for tenant attribution) is not covered by the cryptographic binding (`HMAC` over `raw_body` only), so the equality `HMAC-authenticated(shop) == shop-used-for-tenant-routing` does not hold.

### Finding Description
`HmacValidator.validate` calls `verifiable_query.to_signable_string`, and for `Webhooks::Request` that method returns only `@raw_body` [1](#0-0) [5](#0-4) . The `shop`, `topic`, `webhook-id`, and `api-version` are pulled from headers (`shopify-shop-domain` / `x-shopify-shop-domain`, etc.) that are never included in `to_signable_string` and thus never authenticated by the HMAC [2](#0-1) .

`Registry.process` validates the HMAC and then immediately trusts `request.topic` and `request.shop` to select a handler and construct `WebhookMetadata` [3](#0-2) . Since `shop` is a T::Struct field with no further verification downstream, any consumer of `WebhookHandler#handle(data:)` that trusts `data.shop` to attribute the payload to a tenant is relying on an unauthenticated value.

Concretely: if a low-privilege merchant (unprivileged internet user relative to other tenants of a multi-tenant app) legitimately receives a Shopify webhook for their own shop A — a request with a genuine, correctly computed HMAC over some JSON body — they can capture that request and replay it to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and optionally `x-shopify-topic`/`x-shopify-webhook-id`) header to claim shop B (or any other tenant string). Because the HMAC only binds `raw_body`, `Utils::HmacValidator.validate` still succeeds (the body is untouched and was legitimately signed with the app's real secret by Shopify for shop A), yet `Registry.process` and the resulting `WebhookMetadata` will report the event as belonging to shop B [3](#0-2) .

### Impact Explanation
Any host application whose webhook handler indexes, upserts, or otherwise writes tenant-scoped data using `WebhookMetadata#shop` (the documented and only shop-attribution mechanism provided by this gem for webhook processing) can have data attributed to, or an action taken against, a different tenant than the one that actually generated the event — a cross-tenant integrity/confusion issue reachable without possessing the app's `client_secret`, access token, or the victim's credentials. This matches the "Critical - cross-tenant access" impact category since the boundary crossed is the shop/tenant identity binding that the gem is expected to enforce via the webhook signature.

### Likelihood Explanation
Likelihood is bounded by the fact that the attacker must first possess at least one legitimately signed webhook body for their own shop (any merchant that has installed the app can trigger events like `orders/create` on their own store) and control of the HTTP headers sent to the app's public webhook endpoint (headers are attacker-controlled unless the host application's web framework/proxy normalizes them, which is outside this gem's control). No `api_secret_key`, access token, or TLS interception is required — only ownership of a single low-privileged tenant account, which satisfies the "unprivileged internet user" analog requested.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, and ideally `webhook-id`) in the HMAC-signed payload, e.g. either request Shopify-style signing scopes that cover these headers, or perform an independent trust check where the host application must reconcile `request.shop` against a known/allow-listed tenant registered for that specific webhook subscription before invoking the handler. At minimum, document prominently that `WebhookMetadata#shop` is not itself HMAC-authenticated and that consuming applications must independently verify the shop against their own subscription/session records before trusting it for tenant-scoped writes.

### Proof of Concept
1. Attacker owns Shop A, installed on a multi-tenant app using this gem; app has a webhook endpoint wired to `ShopifyAPI::Webhooks::Registry.process`.
2. Attacker triggers or captures a legitimate Shopify webhook delivery for Shop A: headers include `x-shopify-hmac-sha256: <valid HMAC of body B>`, `x-shopify-shop-domain: shop-a.myshopify.com`, `x-shopify-topic: orders/create`, body `B`.
3. Attacker resends the exact same body `B` and HMAC header to the app's webhook endpoint, but replaces `x-shopify-shop-domain` with `shop-b.myshopify.com` (a victim tenant).
4. `Webhooks::Request.new(raw_body: B, headers: forged_headers)` builds successfully [6](#0-5) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `HMAC(B, secret)` against the untouched, still-valid signature [7](#0-6) .
5. The handler is invoked with `WebhookMetadata.new(shop: "shop-b.myshopify.com", body: parsed(B), ...)` [8](#0-7) , causing Shop A's data/event to be processed as if it belonged to Shop B.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
