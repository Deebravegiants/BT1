### Title
Missing Reentrancy Guard on Tron IntentGatewayV2 Order Functions Enables Escrow Draining - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The canonical EVM `IntentGatewayV2` was patched against a reentrancy class of bug (fee/escrow theft during native-token or token transfers made mid-fill) by inheriting `ReentrancyGuardTransient` and applying `nonReentrant` to `placeOrder`, `fillOrder`, and `cancelOrder`, in addition to setting `_filled[commitment]` before any external call (checks-effects-interactions). [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) 

The Tron deployment of the same contract, `evm/tron/contracts/apps/IntentGatewayV2.sol`, implements the identical order-escrow logic (`placeOrder`, `cancelOrder`, `onAccept`/`withdraw`) but does **not** inherit any reentrancy guard, and its `placeOrder`/`cancelOrder` functions are declared without `nonReentrant`: [5](#0-4) [6](#0-5) 

### Finding Description
This mirrors the C4 finding for `RocketJoeStaking.deposit()`: a function reads/uses state (`_orders[commitment][token]`, `_filled[commitment]`) to compute an amount to release, then performs an external value transfer, and only updates the remaining bookkeeping state around/after that transfer — with no guard preventing the same call frame from re-entering the function before the state is settled.

In the Tron contract:
- `placeOrder` transfers native TRX to the `dispatcher` and executes arbitrary calldata via `ICallDispatcher(dispatcher).dispatch(...)` *before* the escrow amounts (`_orders[commitment][token] += ...`) are fully recorded for every input, and it makes these external calls without any reentrancy lock: [7](#0-6) 
- `cancelOrder` dispatches to `withdraw(body, true)` for the same-chain path, which (per the shared implementation pattern in the sibling `IntentsBase._withdraw`) decrements per-token escrow and sends native value / ERC20 tokens to the beneficiary — again with no `nonReentrant` modifier on the entry point: [8](#0-7) 
- The contract's imports show no `ReentrancyGuard`/`ReentrancyGuardTransient` at all, unlike the corresponding mainnet EVM contract which explicitly added this guard as part of the CEI fix validated in `IntrinsicIntentsReentrancyTest.sol`: [9](#0-8) [10](#0-9) 

Because TRC20/ERC20-style tokens on Tron and any beneficiary/dispatcher contract can execute arbitrary code during a `.call{value}` or token transfer, a malicious dispatcher or beneficiary can re-enter `placeOrder`/`cancelOrder`/`fillOrder` (whichever is reachable on this contract) while escrow bookkeeping is only partially updated, repeating withdrawals against stale `_orders`/`_filled` state — the same "recompute pending value → transfer → update state" ordering flaw described in the RocketJoe report.

### Impact Explanation
If exploitable, this allows an attacker (acting as a malicious dispatcher, beneficiary, or filler) to drain escrowed input tokens or protocol-collected fees held by the Tron `IntentGatewayV2` contract, i.e., concrete theft of user/solver escrowed funds. This satisfies the "concrete theft ... of funds" bar for a valid finding.

### Likelihood Explanation
Medium. Exploitation requires a token or dispatcher contract in the call path (predispatch dispatcher, output token, or beneficiary) to regain control during a transfer, which is plausible for Tron-native TRC20 tokens or a compromised/malicious `_params.dispatcher`/beneficiary address, similar to how the original RocketJoe finding was rated Medium because it depended on a token relinquishing control during `transfer()`. The mainnet EVM `IntentGatewayV2` was hardened against exactly this scenario (see the CEI fix and dedicated `IntrinsicIntentsReentrancyTest.sol`), while the Tron variant was not brought up to the same standard.

### Recommendation
Bring `evm/tron/contracts/apps/IntentGatewayV2.sol` in line with the hardened `evm/src/apps/IntentGatewayV2.sol`:
1. Inherit `ReentrancyGuardTransient` (or a Tron-compatible reentrancy guard) and add `nonReentrant` to `placeOrder`, `fillOrder`, and `cancelOrder`.
2. Apply checks-effects-interactions: set `_filled[commitment]` (and decrement `_orders[commitment][token]`) before any external `.call`/token transfer, mirroring the fix already validated for the mainnet contract.

### Proof of Concept
Not independently reproduced against Tron bytecode/tooling (out of scope for static analysis here); the structural evidence is the side-by-side comparison of `evm/src/apps/IntentGatewayV2.sol` (guarded, CEI-compliant, with a dedicated reentrancy regression test suite) versus `evm/tron/contracts/apps/IntentGatewayV2.sol` (same escrow logic, no reentrancy guard, external calls interleaved with escrow-state updates in `placeOrder`/`withdraw`). A background engineering session with build/test tooling for the Tron contracts would be needed to write and run an equivalent `ReentrantBeneficiary`/malicious-dispatcher PoC against this specific file.

    function cancelOrder(Order calldata order, CancelOptions calldata options) public payable {
        bytes32 commitment = keccak256(abi.encode(order));

        // order has already been filled
        if (_filled[commitment] != address(0)) revert Filled();

        address hostAddr = host();
        bytes32 currentChain = keccak256(IDispatcher(hostAddr).host());
        bytes32 orderSource = keccak256(order.source);
        bytes32 orderDest = keccak256(order.destination);
        bool isSameChain = orderSource == orderDest;

        if (isSameChain) {
            // Same-chain: validate locally and refund immediately
            // only owner can cancel
            if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

            // Verify we're on the correct chain
            if (orderSource != currentChain) revert WrongChain();

            WithdrawalRequest memory body =
                WithdrawalRequest({commitment: commitment, tokens: order.inputs, beneficiary: order.user});

            withdraw(body, true);
