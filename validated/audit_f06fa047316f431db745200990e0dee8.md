This confirms the finding: the gem's own documentation (`docs/usage/webhooks.md:125` — "This will verify the request did indeed come from Shopify") explicitly claims `Registry.process` authenticates the request's origin, and `data.shop` is documented as the trusted shop identity for the handler to act on [1](#0-0) . But the HMAC only covers the raw body, never the `shop` header, so this guarantee is false at the gem level.

### Title
Webhook shop-domain field is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` exposes a `shop` accessor read from the `x-shopify-shop-domain` header [2](#0-1) , but `to_signable_string`—the value that `Utils::HmacValidator` actually authenticates—only returns the raw request body [3](#0-2) . `Registry.process` validates the HMAC and then unconditionally trusts `request.shop` to build the `WebhookMetadata` passed to the app's handler [4](#0-3) . The identity binding broken is: `HMAC-verified(raw_body)` ≠ `shop domain acted upon by the handler`. Any bytes that produce a valid HMAC over a given body remain valid for that body no matter which `shop` header accompanies it.

### Finding Description
The Revolution Protocol root cause pattern is "a parameter that materially changes downstream behavior/ownership is checked/read outside the cryptographically bound path." Here, the shop tenant identifier is exactly such a parameter: it determines whose data the app records the webhook against, per the gem's own documented handler contract (`data.shop`) [5](#0-4) .

`Utils::HmacValidator.validate` recomputes the signature purely from `verifiable_query.to_signable_string` and compares it against the supplied `hmac` [6](#0-5) . For a `Webhooks::Request`, `to_signable_string` is `@raw_body` only [7](#0-6) . The `hmac`, `shop`, `topic`, `webhook_id`, and `api_version` headers are parsed independently of the signed content [8](#0-7) .

Because an unprivileged actor can freely install the target app on their own development/trial Shopify store (no privileged credential required), they legitimately receive real webhook deliveries for *their own* shop, each with a valid `x-shopify-hmac-sha256` value computed over the body. Since the signature never binds to the shop header, the attacker can replay the exact same `(raw_body, hmac)` pair to the app's shared webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `Utils::HmacValidator.validate` still succeeds (raw_body unchanged), `Registry.process` still dispatches, and the handler is invoked with `WebhookMetadata.shop` equal to the victim's domain [9](#0-8) .

### Impact Explanation
This breaks the tenant isolation boundary the gem is documented to guarantee ("verify the request did indeed come from Shopify" for that shop) [10](#0-9) . A host application following the documented pattern (`perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)` [11](#0-10) ) will process attacker-controlled webhook bodies (e.g. `orders/create`, `customers/data_request`, `shop/redact`) under a victim shop's identity, causing cross-tenant data injection/corruption, spurious mandatory-compliance actions (e.g. triggering `shop/redact` logic against a shop that never requested it), or state confusion between tenants — this maps to the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Likelihood is high: the only prerequisite is the ability to install the app on any Shopify store (including a free development store), which is available to any unprivileged internet user with no access token, secret, or victim interaction required. Capturing one's own valid `(body, hmac)` pair and replaying it with a modified header is trivial and entirely within the attacker's control.

### Recommendation
Bind the shop domain (and ideally other identity-bearing headers such as topic and webhook-id) into the HMAC-signed content, e.g. by having `Webhooks::Request#to_signable_string` incorporate the shop header alongside the body, or by having `Registry.process` independently verify that `request.shop` corresponds to a shop the app has an active installation/session for before dispatching to the handler. At minimum, document prominently that `data.shop` is *not* cryptographically authenticated and must be cross-checked against known installed shops before being trusted.

### Proof of Concept
```ruby
# 1. Attacker installs the target app on their own shop "attacker.myshopify.com"
#    and receives a genuine Shopify webhook, e.g. for "orders/create":
raw_body = '{"id":1,"note":"legit order"}'
valid_hmac_header = Base64.encode64(
  OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)
)
# (attacker cannot compute this themselves, but Shopify sends it to them for their own shop)

# 2. Attacker replays the same body+hmac, but swaps the shop-domain header
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => valid_hmac_header,
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # not covered by HMAC
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

# 3. HMAC validation still succeeds because shop is never part of to_signable_string
ShopifyAPI::Webhooks::Registry.process(request)
# => handler.handle(data: WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", ...))
# The app now believes this webhook genuinely originated from victim-shop.myshopify.com.
```
