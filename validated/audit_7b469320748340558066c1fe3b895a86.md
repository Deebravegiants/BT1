### Title
Webhook `shop` identity is trusted for tenant dispatch but is not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then unconditionally trusts the `shopify-shop-domain` / `x-shopify-shop-domain` header as the tenant identifier passed to the app's handler. The header is never included in the signed bytes, so the binding "authenticated body == claimed shop" does not hold, exactly mirroring the M-1 pattern: a value that is *acted on* (here, tenant identity) is not covered by the cryptographic check that is supposed to authenticate the request.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are all read directly from HTTP headers and are not part of the signed string: [2](#0-1) 

`Registry.process` validates only the HMAC-over-body via `Utils::HmacValidator.validate(request)`, then immediately builds `WebhookMetadata` using `request.shop` (an unauthenticated header) as the tenant identity handed to the app's handler: [3](#0-2) 

`HmacValidator.validate_signature` computes the HMAC only over `verifiable_query.to_signable_string`, i.e. the body, and compares it with `OpenSSL.secure_compare`: [4](#0-3) 

`WebhookMetadata.shop` is a `const` field that host apps are expected to use as the tenant key when persisting/looking-up shop-scoped data from webhook payloads: [5](#0-4) 

The binding that should hold is: `HMAC_valid(body, secret) == true` implies `shop_header == shop_that_produced_body`. Because the shop header is outside the signed bytes, that equality is not enforced by the gem: a request with `body B`, a genuine HMAC for `B` (computed with the shared `api_secret_key`), and an attacker-chosen `shop-domain` header will still pass `Registry.process`'s HMAC check and be dispatched to the handler as if it originated from the attacker-chosen shop.

### Impact Explanation
This breaks the authentication binding between the cryptographically-verified payload and the tenant it is attributed to, enabling cross-tenant confusion: a party capable of producing (or replaying) any validly-HMAC'd body for the shared app secret (e.g., an actual merchant of the app, replaying their own legitimately-received webhook with the body kept intact) can relabel it as coming from an arbitrary other shop domain, since the shop domain is never part of what `HmacValidator` verifies. Any app that keys per-shop state, authorization decisions, or writes off of `WebhookMetadata#shop` (as the documented usage pattern instructs) can have data intended for shop A applied to shop B's tenant context, i.e., cross-tenant access to per-shop application state.

### Likelihood Explanation
The vulnerable path is the gem's own documented, first-class webhook processing flow (`Registry.process` + `Webhooks::Request`), used exactly as shown in `docs/usage/webhooks.md`: [6](#0-5) 
No misuse of the API is required — a host app calling `Registry.process` per the documented contract is still exposed, because the gem itself never checks that `request.shop` corresponds to the entity the HMAC actually authenticates.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) header values in the bytes that are HMAC-verified (e.g., verify a canonical string composed of body + shop + topic, or require the caller to separately confirm `request.shop` against a known/installed shop list before trusting it), so that the authenticated payload and the claimed tenant are cryptographically bound together rather than independently sourced.

### Proof of Concept
1. App installs on `shop-a.myshopify.com` and shares `api_secret_key` `S` with Shopify.
2. Shopify sends a webhook to the app for `shop-a.myshopify.com`: body `B`, header `x-shopify-hmac-sha256 = HMAC(S, B)`, header `x-shopify-shop-domain: shop-a.myshopify.com`.
3. An attacker (e.g., the merchant of `shop-a`, or anyone who can observe the delivered body/HMAC pair on the wire to the app's own endpoint) resends the same body `B` and the same valid HMAC, but replaces the `x-shopify-shop-domain` header with `shop-b.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)` which only checks `HMAC(S, B)` — this still passes because `B` is unchanged. [7](#0-6) 
5. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "shop-b.myshopify.com", body: parsed(B), ...)`, so the app processes/attributes shop-a's payload as belonging to shop-b. [8](#0-7)

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
