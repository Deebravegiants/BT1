### Title
Unbounded scrypt N/r/p parameters from attacker-controlled container metadata enable CPU/memory exhaustion DoS during decrypt() - ([File: libraries/secure-container/src/crypto.js])

### Finding Description
`decrypt()` in `libraries/secure-container/src/index.js` decodes an untrusted file's metadata via `conFile.decode()` and `conMetadata.decode()` **before** any passphrase or authenticity check succeeds, then immediately calls `conMetadata.decryptBlobKey(metadata, passphrase)`. [1](#0-0) 

`decryptBlobKey()` forwards `metadata.scrypt` (containing `n`, `r`, `p` decoded straight from the file as `UInt32BE`) unmodified into `boxDecrypt()`. [2](#0-1) 

`boxDecrypt()` merges the attacker-supplied params with defaults and calls `stretchPassphrase()`, which invokes `scrypt(passphrase, salt, { N: n, r, p, dkLen: 32 })` with **no upper-bound validation whatsoever** on `n`, `r`, or `p`. [3](#0-2) [4](#0-3) 

The metadata's binary struct defines `n`, `r`, `p` as raw `UInt32BE` fields with no range constraint at decode time either. [5](#0-4) 

Because scrypt's memory usage scales as `~128 * N * r` bytes, an attacker who controls the imported/decoded container (e.g., a crafted `.seco` backup file, QR-imported blob, or any file fed to `decrypt()`) can set extreme values (e.g., `N` near `2^32`, or moderate `N` with large `r`/`p`) to force allocation of gigabytes-to-petabytes of memory and/or pin the CPU for an extended, attacker-chosen duration — all before the checksum/passphrase correctness is meaningfully load-bearing for this cost (the checksum check in `decrypt()` at line 46-47 only validates `metadata`+`blob` integrity, not the sanity of `scrypt.n/r/p`, so a self-consistent malicious file passes the checksum check and still reaches `stretchPassphrase()`). [6](#0-5) 

No code path in `metadata.js`, `crypto.js`, or `file.js` clamps or rejects out-of-range `n`/`r`/`p` before invoking scrypt.

### Impact Explanation
This is a resource-exhaustion / availability issue, not a key- or secret-disclosure issue: no bypass of authentication, no wrong-account access, no signing occurs. The impact is that processing an attacker-crafted container (import/unlock flow) can hang or crash the process/tab (OOM) while the correct passphrase is otherwise available, denying the legitimate user access to their (unaffected, still-locked) wallet data until the operation is aborted/killed. This matches a Denial-of-Service / availability-degradation impact class rather than a wallet-compromise class; it does not enable unauthorized signing or secret disclosure.

### Likelihood Explanation
Preconditions: an attacker must get the victim to run `decrypt()` (or any higher-level import/restore flow built on `secure-container`) against an attacker-supplied file/blob, which is a realistic scenario for wallet backup import, QR import, or cross-app file-based restore features. No privileged state or secret is required — a crafted metadata region alone (32-byte salt + 3 `UInt32BE` fields) is sufficient, and the rest of the file can otherwise be well-formed enough to pass the checksum check. The attack is fully repeatable and deterministic once such an import path exists.

### Recommendation
Enforce sane upper (and lower) bounds on `n`, `r`, `p` immediately after `metadata.decode()` and/or inside `stretchPassphrase()`/`boxDecrypt()`, e.g., reject params where `n > 2^20`, `r > 16`, `p > 4`, or where the computed memory requirement (`128 * n * r`) exceeds a fixed ceiling (e.g., a few hundred MB), before calling `scrypt()`. Throw a clear validation error instead of proceeding.

### Proof of Concept
Add a fuzz/unit test in `libraries/secure-container/src/__tests__/metadata.test.js` or `crypto.test.js`:
1. Construct a `metadata` object via `metadata.create()`/`metadata.encode()` with `scrypt.n = 0xFFFFFFFF` (or `r = 0xFFFFFFFF`, `p = 0xFFFFFFFF`).
2. Call `metadata.decode()` on the encoded buffer and assert it decodes without rejecting the out-of-range values (demonstrating no validation at decode time).
3. Call `metadata.decryptBlobKey(metadata, 'any-passphrase')` (or `crypto.boxDecrypt`) and assert that it **should** throw a validation error for `n`/`r`/`p` exceeding defined safe limits, e.g.:
   ```js
   await t.rejects(
     () => cryptoModule.stretchPassphrase('pw', { salt, n: 0xFFFFFFFF, r: 8, p: 1 }),
     /scrypt parameters exceed allowed limits/
   )
   ```
   Currently this assertion fails because no such check exists — instead the call proceeds into `scrypt()` with attacker-chosen `N`, demonstrating the missing bound enforcement described above.
