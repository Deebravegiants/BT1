### Title
Webhook shop-domain (tenant) header is not covered by the HMAC signature, enabling cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body, so the HMAC verification performed by `Utils::HmacValidator` authenticates the *body bytes* but never binds them to the `shop`, `topic`, or `webhook_id` values that are read from separate, unsigned HTTP headers. Because the app's `api_secret_key` is shared across every shop that installs the app, any actor who can obtain one valid `(raw_body, hmac)` pair can resubmit it with a forged `x-shopify-shop-domain` header for a different tenant and still pass `HmacValidator.validate`, letting the forged request be dispatched to the app's webhook handler as if it came from another merchant's shop.

### Finding Description
`Request#to_signable_string` is defined as:

```ruby
sig { override.returns(String) }
def to_signable_string
  @raw_body
end
``` [1](#0-0) 

and `shop`, `topic`, `webhook_id`, `api_version` are all read straight from HTTP headers, entirely outside the signed material:

```ruby
def shop
  T.cast(shopify_header("shop-domain"), String)
end
``` [2](#0-1) 

`Utils::HmacValidator.validate_signature` computes the HMAC only over `verifiable_query.to_signable_string` (i.e. the raw body) and compares it to the `hmac` header:

```ruby
def validate_signature(verifiable_query, secret)
  received_signature = verifiable_query.hmac
  computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
  OpenSSL.secure_compare(computed_signature, T.must(received_signature))
end
``` [3](#0-2) 

`Webhooks::Registry.process` relies solely on this HMAC check before trusting `request.shop` as the tenant identity handed to the app's business logic:

```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
``` [4](#0-3) 

The binding that should hold is: `HMAC-verified(body) == HMAC-verified(body ∧ shop)`. In reality the gem only proves `HMAC-verified(body)`; the `shop` field consumed by `handler.handle` is never part of the signed data. Since `api_secret_key` is a single per-app secret shared across every shop that installs the app (not per-shop), any `(body, hmac)` pair valid for shop A is also a byte-for-byte valid pair for a forged request claiming to be shop B — the signature says nothing about which tenant the body belongs to.

### Impact Explanation
An unprivileged actor who can observe one legitimate `(raw_body, x-shopify-hmac-sha256)` pair delivered to the app (e.g., by installing the app on their own store and inspecting the webhook their own endpoint receives) can replay that exact body/HMAC combination while substituting an arbitrary `x-shopify-shop-domain` header value naming a different merchant that also installed the app. `HmacValidator.validate` will still return `true` because it only checks the body, and `Registry.process` will forward the forged event to the handler tagged with the victim shop's domain as `WebhookMetadata#shop`. Any app logic keyed on `data.shop` (order/customer/inventory sync, per-tenant data stores, audit trails) will process attacker-controlled data under another tenant's identity — a cross-tenant data-integrity/confusion issue reachable purely through this gem's exposed `Request`/`Registry` API, without any credentials beyond running the same app on one's own store.

### Likelihood Explanation
Any merchant who installs the target app can trivially capture a legitimate `(body, hmac)` pair for their own shop (their own endpoint receives it in cleartext). Re-issuing an HTTP request with a modified `shop-domain` header and the exact same body/HMAC is straightforward and requires no cryptographic secret, because the shared `api_secret_key` makes the signature tenant-agnostic. No rate limiting or additional authentication protects the endpoint beyond `HmacValidator.validate`, which this technique fully satisfies.

### Recommendation
Include the tenant-identifying headers (`shop-domain`, and ideally `topic`/`webhook_id`) in the material that is HMAC-verified, or otherwise cryptographically bind them to the body before trusting `request.shop` in `WebhookMetadata`. At minimum, `Utils::HmacValidator`/`Request#to_signable_string` should incorporate the shop domain into the signed string so that a body signed for one shop cannot be replayed as if it belonged to another.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store (`attacker.myshopify.com`) and configures a webhook endpoint they control to log incoming requests.
2. Shopify delivers a legitimate webhook to the attacker's endpoint with headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC of body>`, and some JSON `body`.
3. Attacker re-sends the identical `body` and `x-shopify-hmac-sha256` value to the app's public webhook endpoint, but replaces the header with `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses the forged headers/body; `Utils::HmacValidator.validate` recomputes the HMAC over `@raw_body` only, which matches, so `Registry.process` invokes the app's handler with `WebhookMetadata#shop == "victim.myshopify.com"` even though the payload never actually originated from Shopify on behalf of that shop.
