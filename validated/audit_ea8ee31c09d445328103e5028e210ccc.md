## Title
Webhook shop/topic identity is not cryptographically bound to the HMAC-verified body, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body. The shop domain, topic, and webhook id — the values used to attribute the event to a specific merchant tenant — are taken from separate HTTP headers that are never included in the signed bytes. An unprivileged attacker who legitimately installs the app on their own store can capture one genuine, HMAC-valid webhook delivery and replay it to the app's webhook endpoint with a forged `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`/`webhook-id`) header, causing the gem to hand the app a "verified" event that is falsely attributed to a different (victim) shop.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop`, `topic`, `api_version`, and `webhook_id` are read straight from headers with no cryptographic coverage: [2](#0-1) 

`Registry.process` verifies only the body HMAC via `Utils::HmacValidator.validate(request)`, then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

The binding that should hold is: `hmac_verified(body) == true` implies `(shop, topic, webhook_id)` were also issued by Shopify for that body. In fact, the equality that actually holds is only `hmac_verified(body)`, with `(shop, topic, webhook_id)` being attacker-controlled bytes copied verbatim from unauthenticated headers into the trusted metadata handed to the app.

Exploit path: an attacker installs the app on their own shop (an ordinary, unprivileged flow) and captures one real webhook delivery — a valid `(raw_body, hmac)` pair signed with the app's shared `api_secret_key`. The attacker then POSTs this exact body/HMAC pair to the same webhook endpoint again, but swaps `x-shopify-shop-domain` (and optionally `x-shopify-topic`/`x-shopify-webhook-id`) to a victim shop's domain. `HmacValidator.validate` still succeeds because it only checks the (unchanged) body against the (unchanged) HMAC: [4](#0-3) 

`Registry.process` then dispatches the handler with `shop: request.shop` pointing at the victim, even though the actual signed payload came from the attacker's own store.

### Impact Explanation
This breaks the tenant-authentication boundary the HMAC check is meant to enforce: an app handler that trusts `WebhookMetadata#shop` (e.g., to key stored sessions/tokens, delete a merchant's access token on a spoofed `app/uninstalled`, or drive per-shop business logic) can be tricked into acting on a different merchant's identity using attacker-supplied, cryptographically "verified" data. This is a cross-tenant identity-confusion issue reachable by any unprivileged app installer, matching the required Critical impact category (cross-tenant access).

### Likelihood Explanation
Likelihood is moderate-to-high for apps that rely on the shop/topic/webhook_id fields returned by this gem as authenticated: obtaining one legitimate webhook delivery only requires installing the app once on an attacker-controlled store (a fully unprivileged action), and replaying the captured request with a modified header requires no secret material.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signed/verified material (or otherwise cryptographically bind them to the body, e.g. by validating them against a value obtained through an authenticated, out-of-band channel such as a corresponding stored session lookup) before trusting them in `WebhookMetadata`. At minimum, document clearly that these header-derived fields are unauthenticated so integrators cannot assume tenant integrity from `Registry.process` alone, or add a call-time hook that lets consumers verify `shop` against their own session store prior to dispatch.

### Proof of Concept
1. Install the app on attacker-owned shop `attacker.myshopify.com`; capture a real webhook delivery, e.g. body `{}` with headers `x-shopify-hmac-sha256: <validHmac>`, `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-topic: app/uninstalled`.
2. Replay the exact same `raw_body`/`x-shopify-hmac-sha256` pair to the app's webhook endpoint, replacing `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` which passes (body/HMAC unchanged), then invokes the registered handler with `WebhookMetadata.new(topic: "app/uninstalled", shop: "victim-shop.myshopify.com", ...)`, causing the app to process a forged uninstall (or other) event for the victim tenant.
