### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant identity spoofing on replayed webhooks - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then trusts the unauthenticated `shop-domain` header to populate the tenant identity (`WebhookMetadata#shop`) handed to the app's handler. Because the HMAC only binds the body, and the app-wide `client_secret` used to sign webhooks is shared across every shop that has installed the app, any shop that receives one genuine webhook can replay that exact body with a forged `shop-domain` header pointing at a different, victim shop, and the signature will still validate.

### Finding Description
`Webhooks::Registry.process` validates the webhook using `Utils::HmacValidator.validate(request)`: [1](#0-0) 

The HMAC check calls `request.to_signable_string`, which for `Webhooks::Request` is defined as only the raw body: [2](#0-1) 

Meanwhile `shop`, `topic`, and `webhook_id` are all read directly from HTTP headers, independent of the signed bytes: [3](#0-2) 

`HmacValidator.validate` computes the digest only over `verifiable_query.to_signable_string` and compares it to the `hmac` header — it never incorporates `shop`, `topic`, or `webhook_id`: [4](#0-3) [5](#0-4) 

After validation succeeds, `request.shop` is passed unmodified into `WebhookMetadata`, which is handed to the app's handler as the trusted tenant identity for the event: [6](#0-5) 

The identity binding that should hold is:
`shop-domain header value == the shop for which this exact (body, hmac) pair was actually issued by Shopify`

That binding is never enforced by this gem — the HMAC is computed with the app's single, shop-independent `client_secret` (`Context.api_secret_key`) over the body alone, so the same signature is valid for that body regardless of which `shop-domain` header accompanies it.

### Impact Explanation
Any shop that has installed the app is, by design, a legitimate recipient of genuinely-signed webhook deliveries (the signing key is the app's `client_secret`, not a per-shop secret). An attacker who controls or has installed the app on their own (attacker-owned) shop can capture one authentic `(raw_body, hmac)` pair delivered to them, then resend an HTTP request to the app's webhook endpoint with the identical body/HMAC but with the `shopify-shop-domain` (or `x-shopify-shop-domain`) header rewritten to a victim shop's domain. `Registry.process` will accept it as valid (the HMAC still matches the body) and invoke the app's handler with `WebhookMetadata#shop` set to the victim's domain. Any handler logic that keys per-tenant state, session lookup, or data mutation off `data.shop` will then act as though the event genuinely originated from the victim shop — a cross-tenant confusion/spoofing primitive reachable by any unprivileged internet user who is simply able to install the app once on a shop they control.

### Likelihood Explanation
High. No secret material beyond routine app installation is required — the attacker only needs to become an app user (install the app on any shop, which is normal, unprivileged usage) to obtain at least one authentic `(body, hmac)` pair, then replay it with a forged header. No interception of victim traffic or possession of `api_secret_key` is needed.

### Recommendation
Bind the tenant identity into the signed material, or otherwise cryptographically tie the `shop-domain` header to the delivery: include `shop`, `topic`, and `webhook_id` in the HMAC computation (as Shopify's newer webhook formats/mTLS options allow), or cross-check the delivered `webhook_id`/topic against a per-shop expected set fetched from Shopify's API before trusting `WebhookMetadata#shop`, rather than trusting the raw header value as the sole tenant identity passed to handlers.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com`. Shopify sends a genuine webhook to the app's endpoint:
   - Headers: `shopify-shop-domain: attacker.myshopify.com`, `shopify-hmac-sha256: <valid-hmac-of-body>`, `shopify-topic: orders/create`
   - Body: `{"id": 123, ...}`
2. Attacker captures this request (it's their own traffic to their own installed app, e.g. via a debugging proxy).
3. Attacker resends the identical body and `shopify-hmac-sha256` value to the same webhook endpoint, but changes `shopify-shop-domain` to `victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Utils::HmacValidator.validate` recomputes the HMAC over the (unchanged) body and it matches, per: [7](#0-6) 
5. `Registry.process` invokes the app's handler with `WebhookMetadata.new(topic:, shop: "victim.myshopify.com", body:, ...)`, per: [8](#0-7) 
6. Any handler that trusts `data.shop` for tenant-scoped operations now operates under the victim's identity despite the event never having been issued for `victim.myshopify.com`.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
