### Title
Cross-message signature replay between `MultisigAccountCreationMessage` and `MultisigAccountCreationWithAuthKeyRevocationMessage` due to missing domain separation - (File: aptos-move/framework/aptos-framework/sources/multisig_account.move)

### Summary
`multisig_account::create_with_existing_account` and `multisig_account::create_with_existing_account_and_revoke_auth_key` both verify a signed message via `account::verify_signed_message`, but the two challenge structs they build — `MultisigAccountCreationMessage` and `MultisigAccountCreationWithAuthKeyRevocationMessage` — contain the exact same fields in the exact same order (`chain_id`, `account_address`, `sequence_number`, `owners`, `num_signatures_required`). Because Move's BCS serialization (used by `ed25519::signature_verify_strict_t`/`multi_ed25519::signature_verify_strict_t`) does not encode the struct's type/name, both structs produce byte-identical messages for the same field values. This is the same "one signature usable for two different actions" bug class described in the external report.

### Finding Description
`create_with_existing_account` builds: [1](#0-0) 

and `create_with_existing_account_and_revoke_auth_key` (per the corresponding generated doc, mirroring the source) builds a `MultisigAccountCreationWithAuthKeyRevocationMessage` with the identical field set and order: [2](#0-1) 

Both are verified through the same generic helper `account::verify_signed_message`, which just checks the raw signature against the serialized struct bytes with no type-tag/domain separator: [3](#0-2) 

Since a Move struct's BCS encoding is purely the concatenation of its field encodings (no struct name or type index is included), a signature an account owner produced to authorize `MultisigAccountCreationMessage{chain_id, account_address, sequence_number, owners, num_signatures_required}` is bit-for-bit identical to, and therefore also valid for, `MultisigAccountCreationWithAuthKeyRevocationMessage` with the same field values. The account's `chain_id`, `sequence_number`, `owners`, and `num_signatures_required` are all attacker/caller-supplied or externally observable, so an unprivileged transaction submitter can take a signature the user produced intending the non-destructive path (`create_with_existing_account`, which explicitly preserves auth-key-based control) and instead submit it to `create_with_existing_account_and_revoke_auth_key`.

This breaks the custody invariant that a user's signature should authorize exactly one intended action. Compare with `account.move`'s own challenge structs (`RotationProofChallenge`, `RotationCapabilityOfferProofChallengeV2`, `SignerCapabilityOfferProofChallengeV2`), which are each structurally distinct in field composition, incidentally providing some separation — but `multisig_account.move`'s two creation-message structs are not distinct, defeating that implicit protection.

### Impact Explanation
`create_with_existing_account_and_revoke_auth_key` immediately zeroes the account's auth key and revokes any signer/rotation capability once the migration succeeds: [4](#0-3) 

If a transaction sender replays a signature the account owner made only for the non-revoking `create_with_existing_account` path, the account's original key-based access is permanently destroyed without the owner's consent — a non-recoverable loss of control over an existing account being converted to multisig custody. This satisfies the "permanent lock or non-recoverable loss of ... resource-account-held value" and "unauthorized ... reassignment ... of resource-account control" custody impact categories.

### Likelihood Explanation
Medium: the attacker must be the one submitting the transaction (a relayer/sender pattern common to gasless/meta-transaction flows for multisig migration), and needs to intercept the off-chain signed message content, which is realistic since the signed payload is typically passed to a submitter service for on-chain relay. The user has no domain separator in the signed bytes to constrain how the signature is used, so the sender chooses which of the two entry functions to invoke.

### Recommendation
Add a domain-separating byte/tag (e.g. a `revoke_auth_key: bool` field or a distinguishing string/const) inside both `MultisigAccountCreationMessage` and `MultisigAccountCreationWithAuthKeyRevocationMessage` so their BCS-serialized bytes can never collide, mirroring the approach used to fix the external report (adding a unique salt/method identifier to the signed payload). Alternatively, verify a single unified challenge struct that includes an explicit `action` discriminant consumed by both entry points.

### Proof of Concept
1. Alice controls account `A` with an ed25519 key and wants to migrate to a multisig account without giving up her key (calls the non-revoking path).
2. She signs `MultisigAccountCreationMessage { chain_id, account_address: A, sequence_number: N, owners: [...], num_signatures_required: k }` and hands the bytes to a relayer to submit `create_with_existing_account`.
3. The relayer instead submits `create_with_existing_account_and_revoke_auth_key(A, owners, k, scheme, pubkey, same_signature_bytes, ...)`.
4. `account::verify_signed_message` reconstructs `MultisigAccountCreationWithAuthKeyRevocationMessage` with the same field values, serializes it via BCS, and successfully verifies Alice's signature against it (since the byte encoding is identical to what she actually signed).
5. The relayed call succeeds, `create_with_owners_internal` runs, and immediately after, `account::rotate_authentication_key_internal(multisig_account, ZERO_AUTH_KEY)` executes — permanently zeroing Alice's key-based access, an action she never authorized. [5](#0-4)

    public fun verify_signed_message<T: drop>(
        account: address,
        account_scheme: u8,
        account_public_key: vector<u8>,
        signed_message_bytes: vector<u8>,
        message: T,
    ) acquires Account {
        let auth_key = get_authentication_key(account);
        // Verify that the `SignerCapabilityOfferProofChallengeV2` has the right information and is signed by the account owner's key
        if (account_scheme == ED25519_SCHEME) {
            let pubkey = ed25519::new_unvalidated_public_key_from_bytes(account_public_key);
            let expected_auth_key = ed25519::unvalidated_public_key_to_authentication_key(&pubkey);
            assert!(
                auth_key == expected_auth_key,
                error::invalid_argument(EWRONG_CURRENT_PUBLIC_KEY),
            );

            let signer_capability_sig = ed25519::new_signature_from_bytes(signed_message_bytes);
            assert!(
                ed25519::signature_verify_strict_t(&signer_capability_sig, &pubkey, message),
                error::invalid_argument(EINVALID_PROOF_OF_KNOWLEDGE),
            );
        } else if (account_scheme == MULTI_ED25519_SCHEME) {
            let pubkey = multi_ed25519::new_unvalidated_public_key_from_bytes(account_public_key);
            let expected_auth_key = multi_ed25519::unvalidated_public_key_to_authentication_key(&pubkey);
            assert!(
                auth_key == expected_auth_key,
                error::invalid_argument(EWRONG_CURRENT_PUBLIC_KEY),
            );

            let signer_capability_sig = multi_ed25519::new_signature_from_bytes(signed_message_bytes);
            assert!(
                multi_ed25519::signature_verify_strict_t(&signer_capability_sig, &pubkey, message),
                error::invalid_argument(EINVALID_PROOF_OF_KNOWLEDGE),
            );
        } else {
            abort error::invalid_argument(EINVALID_SCHEME)
        };
    }
