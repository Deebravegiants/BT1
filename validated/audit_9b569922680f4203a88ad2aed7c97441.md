### Title
Duplicate withdrawals of the same PoA asset in one intent tx resolve to a single withdrawal record, causing status/txHash misreport - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`findMatchingWithdrawal` in `PoaBridge.describeWithdrawal` matches by `assetId` only, ignoring `WithdrawalIdentifier.index`, and the underlying limitation is explicitly acknowledged in the code's own comment. When a single NEAR intent tx contains two PoA withdrawals for the same `assetId` to different destinations/amounts, both `describeWithdrawal` calls (index 0 and index 1) query the same `withdrawal_hash: intentTx.hash` and both resolve to the same first matching array element via `Array.prototype.find`.

### Finding Description
The broken equality: STATUS TRUTH requires `(status, txHash)` returned for withdrawal `i` to correspond to the on-chain outcome of withdrawal `i` specifically. Instead:

- `createWithdrawalIdentifiers` (`packages/intents-sdk/src/core/withdrawal-watcher.ts:80-107`) assigns sequential `index` values per bridge route when multiple withdrawal params route to the same bridge (`PoaBridge`), so two same-asset PoA withdrawals in one call get `index: 0` and `index: 1`.
- `PoaBridge.describeWithdrawal` (`poa-bridge.ts:313-343`) calls `getWithdrawalStatusWithRetry` keyed only by `args.tx.hash` (the shared intent tx hash — identical for both withdrawal legs), then calls `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`.
- `findMatchingWithdrawal` (`poa-bridge.ts:418-427`) does `withdrawals.find((w) => nep141:${w.data.near_token_id} === assetId)` — matching by `assetId` string only, with **no use of `args.index`** to disambiguate between multiple entries for the same asset.
- The code comment directly above (`poa-bridge.ts:409-417`) states: *"NOTE: Currently only matches by assetId. This means multiple withdrawals of the same token in a single transaction are not supported. POA API doesn't currently support this case either."*

Exploit flow: an attacker (ordinary user) signs and publishes a MultiPayload with two `ft_withdraw` intents both for `nep141:btc.omft.near`, to two different destination addresses/amounts. `createWithdrawalIdentifiers` builds two `WithdrawalIdentifier`s (index 0, index 1) both pointing at the same `intentTx`. Both `describeWithdrawal` calls hit the same POA `getWithdrawalStatus` response array (which would contain two withdrawal records for that tx), and `Array.find` returns the *same first element* for both index-0 and index-1 lookups. Consequently both promises from `createWithdrawalCompletionPromises`/`waitForWithdrawalCompletion` can resolve to the identical `{status: "completed", txHash: X}`, even though two separate on-chain payouts exist (or, depending on array ordering, one payout is reported twice while the other is silently ignored).

None of the existing guards prevent this: `validateWithdrawal`, `compareAddresses`, `supports()` ordering, and `FeeExceedsAmountError` operate on withdrawal *creation*/fee validation, not on completion-status matching; there is no `index`-based disambiguation anywhere in `describeWithdrawal` or `findMatchingWithdrawal`.

### Impact Explanation
An integrator that credits or refunds a user based on `(status, txHash)` per withdrawal leg would either (a) credit/refund the same on-chain payout twice, believing two independent payouts occurred, or (b) never distinguish that one of the two legs is a duplicate report, meaning the actual second on-chain transfer's completion is never uniquely confirmed against the correct withdrawal leg. This is a status/hash misreport that can cause integrators to double-credit — matching the "High" severity category ("a status or hash misreport making an integrator credit or refund twice"). It is repeatable for any batch containing ≥2 same-asset PoA withdrawals in one intent tx, at zero attacker cost beyond normal withdrawal fees.

### Likelihood Explanation
Preconditions: attacker only needs to create a batch withdrawal (or multiple withdrawal params passed together to `signAndSendWithdrawalIntent`/`processWithdrawal`) with two `WithdrawalParams` sharing the same `assetId` routed to `PoaBridge` (e.g., `nep141:btc.omft.near` to two different destination addresses). This is fully within normal, unprivileged SDK usage — no misuse of a documented escape hatch is required from the *integrator's* side; the flaw is triggered purely by ordinary user/attacker-supplied withdrawal parameters. This is realistic and easily reproducible by any caller of the batch withdrawal API.

### Recommendation
Make `findMatchingWithdrawal` index-aware: sort matching candidates for the given `assetId` deterministically (e.g., by amount, per the comment's own suggestion) and select the entry corresponding to `args.withdrawalParams` position/`index` among same-asset withdrawals in the same tx, or throw an explicit "unsupported" error for duplicate-asset batches until the POA API supports per-withdrawal disambiguation, rather than silently returning a possibly-wrong record.

### Proof of Concept
Vitest test (mocking `poaBridge.httpClient.getWithdrawalStatus` only):
1. Mock `getWithdrawalStatus` to return `{ withdrawals: [{ status: "COMPLETED", data: { near_token_id: "btc.omft.near", transfer_tx_hash: "0xAAA" } }, { status: "COMPLETED", data: { near_token_id: "btc.omft.near", transfer_tx_hash: "0xBBB" } }] }` for the shared `withdrawal_hash`.
2. Construct two `WithdrawalIdentifier`s with identical `withdrawalParams.assetId: "nep141:btc.omft.near"`, same `tx`, but `index: 0` and `index: 1`.
3. Call `poaBridge.describeWithdrawal(wid0)` and `poaBridge.describeWithdrawal(wid1)`.
4. Assert equality-break: both resolve to `{ status: "completed", txHash: "0xAAA" }` — i.e. `result0.txHash === result1.txHash === "0xAAA"`, even though the mocked API state contains two distinct records (`0xAAA` and `0xBBB`), demonstrating that withdrawal index 1's true outcome (`0xBBB`) is never surfaced.
