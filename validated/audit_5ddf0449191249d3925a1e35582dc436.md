### Title
Webhook HMAC Validation Does Not Bind the `shop` Tenant Identifier to the Signed Payload, Enabling Cross-Tenant Webhook Spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary

### Finding Description
The gem's webhook processing path breaks the identity binding: `HMAC(body) == valid` should imply `shop == the shop that produced this event`, but in this library the two are decoupled.

`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`. Its `to_signable_string` returns only the raw HTTP body: [1](#0-0) 

The `shop` attribute, however, is read straight from the unauthenticated `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, which is never included in the signable string: [3](#0-2) 

`Registry.process` validates the HMAC over the body only, then forwards `request.shop` — the unverified header value — directly into `WebhookMetadata`, which the host application uses to attribute the event to a tenant: [2](#0-1) 

`HmacValidator.validate` only ever checks `verifiable_query.hmac` against `verifiable_query.to_signable_string`, so it never notices that `shop` was not part of what was signed: [4](#0-3) 

Because the app's `client_secret` (used to compute the HMAC) is shared across every shop that installs the app, any merchant who legitimately receives a genuine, correctly-signed webhook for their own store can replay that exact body/HMAC pair to the app's public webhook endpoint while substituting an arbitrary `shopify-shop-domain` header value naming a different, victim tenant. The signature still validates because the header is outside the signed content — breaking the equality `hmac_valid(body) == authentic(shop, body)` that the host application relies on for tenant attribution.

### Impact Explanation
This allows an unprivileged (but app-installing) actor to make the host application process and store webhook data under an arbitrary victim shop's identity — a cross-tenant data-integrity/confusion attack, matching the Critical "cross-tenant access" impact category, since the app has no library-level guarantee that the `shop` field passed to `WebhookMetadata` and used for tenant routing was ever bound to the cryptographic signature.

### Likelihood Explanation
Any entity that operates an installation of the app (a real, if low-privilege, merchant/tenant) can trivially capture one legitimate webhook it receives and replay it with a modified `shop` header from any internet-reachable location, since the webhook endpoint is a plain public HTTP endpoint and no header-to-signature binding exists in this gem's verification logic.

### Recommendation
Include the tenant-identifying header (`shop-domain`) in the value that is HMAC-verified, or otherwise cryptographically bind the claimed `shop` to the signed body before it is exposed via `WebhookMetadata`, so that a valid signature can only be replayed for the tenant it was originally issued for.

### Proof of Concept
1. Attacker legitimately installs the app on `attacker-shop.myshopify.com` and receives a genuine webhook: body `B`, header `shopify-hmac-sha256: HMAC(B, client_secret)`, `shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker resends the identical body `B` and HMAC header to the app's public webhook endpoint, but changes `shopify-shop-domain` to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `HmacValidator.validate(request)`, which only checks `HMAC(B, client_secret)` — it succeeds because `B` is untouched.
4. `request.shop` returns `"victim-shop.myshopify.com"`, and `WebhookMetadata.new(... shop: request.shop ...)` is passed to the host app's handler, which processes/stores the payload as belonging to the victim tenant.
