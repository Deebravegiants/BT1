## Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by checking the HMAC of the *raw request body*. The tenant identifier (`shop`) that is handed to the app's webhook handler is read directly from the `X-Shopify-Shop-Domain` HTTP header, which is never part of the HMAC-signed content. Any attacker who can obtain one legitimately-signed `(body, hmac)` pair (trivially available by installing the app on their own store) can replay that exact body/HMAC to the app's public webhook endpoint while substituting an arbitrary victim shop domain in the header, and the request will pass HMAC validation.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read straight from a header and is never included in the signed material: [2](#0-1) 

`Utils::HmacValidator.validate_signature` verifies exactly `verifiable_query.to_signable_string` against `verifiable_query.hmac`: [3](#0-2) 

`Registry.process` uses the HMAC check as the sole authentication gate, then forwards the untouched `request.shop` (and `request.topic`) to the app-supplied handler as the trusted tenant/topic identity: [4](#0-3) 

The identity binding that the caller assumes holds is:
`hmac_valid(request) == true` ⟹ `request.shop == the shop Shopify actually sent this webhook for`

In reality the equality that actually holds is only:
`hmac_valid(request) == true` ⟹ `request.raw_body was produced with the app's secret at some point (for some shop)`

Because `shop` (and `topic`, `webhook-id`, `api-version`) are excluded from `to_signable_string`, the binding between the HMAC-authenticated bytes and the shop the library reports to the handler is broken — this is exactly the "field acted on but not covered by the HMAC" class described in the prompt.

### Impact Explanation
An unprivileged internet user can:
1. Install the target app on their own (attacker-controlled) development/test shop — a normal, unprivileged action.
2. Receive one legitimately Shopify-signed webhook delivery (body + `X-Shopify-Hmac-Sha256`) for any topic the app registers (e.g. `app/uninstalled`, `orders/create`, etc.). No knowledge of `api_secret_key` is required — Shopify computes and delivers the signature.
3. Replay that exact `(raw_body, hmac)` pair to the app's public webhook endpoint, but with `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`) rewritten to name a victim shop.
4. `Utils::HmacValidator.validate` succeeds (it only checks the body), `Registry.process` accepts the request, and the handler is invoked with `WebhookMetadata#shop` set to the attacker-chosen victim shop domain.

Depending on what the host application does in its webhook handler (revoking access, deleting data, updating billing/subscription state, marking uninstall, etc. keyed off `shop`), this enables cross-tenant state corruption/impersonation — an unauthenticated attacker can make the app believe an event happened for a shop they do not control.

### Likelihood Explanation
High. No secrets, tokens, or privileged access are required — only the ability to install the app once on an attacker-owned shop (which any Shopify Partner/developer account can do) to harvest a valid body/HMAC pair, and the ability to send arbitrary HTTP requests to the app's public webhook endpoint.

### Recommendation
Bind the tenant identity to the signed content, e.g.:
- Include `shop`, `topic`, and `webhook_id` in the HMAC-signable string (would require coordinating with Shopify's actual signing scheme), or
- More practically, require that the caller/host application independently confirm `request.shop` corresponds to a shop with an active, known installation/session before trusting the webhook, and document this requirement explicitly in `Registry.process`/`WebhookMetadata`, or
- Have `Registry.process` refuse to process a webhook whose `shop` is not present in the app's session storage / a caller-supplied allow-list, instead of relying purely on body HMAC validity.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`, registering it for the `app/uninstalled` webhook.
2. Attacker triggers the event (e.g., uninstalls the app), and Shopify delivers:
   ```
   POST /webhooks
   X-Shopify-Topic: app/uninstalled
   X-Shopify-Hmac-Sha256: <valid-hmac-for-body>
   X-Shopify-Shop-Domain: attacker-shop.myshopify.com
   Body: {"id": ...}
   ```
3. Attacker replays the identical body and `X-Shopify-Hmac-Sha256` value to the same endpoint, but sets:
   ```
   X-Shopify-Shop-Domain: victim-shop.myshopify.com
   ```
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only re-hashes `@raw_body` and matches the header value — validation succeeds.
5. `handler.handle(data: WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", ...))` is invoked, and the host app's `app/uninstalled` handler executes for `victim-shop.myshopify.com`, e.g. deactivating/deleting the victim's real installation data.
