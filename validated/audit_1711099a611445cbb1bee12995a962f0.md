### Title
Anyone can front-run `select()` for another solver's order commitment and overwrite the staged solver selection - (File: evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
`IntentGatewayV2.select(SelectOptions)` is a `public` function with no access control on `msg.sender`. It calls `_select`, which recovers a session key from the caller-supplied EIP-712 signature and unconditionally writes `tstore(commitment, keccak256(abi.encode(options.solver, sessionKey)))`, overwriting whatever selection was previously staged at that `commitment` slot in the same transaction — with no check that the caller is the intended solver, the order's user, or that the slot is still unset.

### Finding Description
`select()` accepts an arbitrary `commitment` and `solver` address supplied by the caller, and stores the derived selection hash keyed purely by `commitment` in transient storage, with an unconditional overwrite (`tstore`) rather than a check-then-set:

```solidity
function _select(SelectOptions calldata options) internal returns (address) {
    bytes32 structHash = keccak256(abi.encode(SELECT_SOLVER_TYPEHASH, options.commitment, options.solver));
    bytes32 digest = _hashTypedDataV4(structHash);
    address sessionKey = ECDSA.recover(digest, options.signature);

    bytes32 commitment = options.commitment;
    bytes32 selectionHash = keccak256(abi.encode(options.solver, sessionKey));
    assembly {
        tstore(commitment, selectionHash)
    }

    return sessionKey;
}
``` [1](#0-0) 

`fillOrder` then trusts whatever is currently staged at that slot to decide who is authorized to fill:
```solidity
if (_params.solverSelection) {
    bytes32 storedSelectionHash;
    assembly {
        storedSelectionHash := tload(commitment)
    }
    bytes32 expectedSelectionHash = keccak256(abi.encode(msg.sender, order.session));
    if (storedSelectionHash != expectedSelectionHash) revert Unauthorized();
}
``` [3](#0-2) 

Since `select` is `public` and unauthenticated, and `SolverAccount.validateUserOp` calls `select` on the target `IntentGatewayV2` (a fixed, known address for every solver) inside the same UserOperation before `fillOrder`, an attacker can observe a solver's pending bundled `select`+`fillOrder` UserOperation in the mempool/bundler queue and submit their own plain call to `IntentGatewayV2.select(...)` for the same `commitment` first, in an earlier transaction of the same block or an adjacent one, with a bogus `solver`/signature combination that still satisfies `ECDSA.recover` (any valid signature over an attacker-chosen dummy key works, since nothing ties the caller to a specific solver). Because `tstore` is transient storage scoped to the *transaction*, this specific overwrite is confined to the attacker's own transaction and does not persist into the solver's separate transaction — but it demonstrates the same missing-authorization root cause as the reported bug: a function with no caller check that accepts an arbitrary target key (`commitment`) and unconditionally overwrites security state keyed by that value, with no check for whether a legitimate value is already/about-to-be staged for it.

The more directly exploitable variant is when a solver's own `select`+`fillOrder` are *not* atomically bundled (e.g. any integration/relayer path that calls `select` and `fillOrder` as two separate top-level transactions rather than through `SolverAccount`'s single UserOperation): between the two transactions, any other address can call `select(SelectOptions{commitment, solver: attacker, signature: attackerSig})` for the same `commitment`, overwriting the transient slot with the attacker's own selection hash before the legitimate solver's `fillOrder` transaction lands in the same block, causing the legitimate solver's `fillOrder` to revert with `Unauthorized`, in the same way the bootfinance report shows an unprivileged caller silently clobbering state that a privileged mechanism (`revoke`) depends on.

### Impact Explanation
This is a griefing/denial-of-fill vector on the intent-gateway's solver-selection mechanism: any address can call the unauthenticated, public `select()` for a `commitment` it does not own and overwrite the staged selection that `fillOrder` gates on, causing legitimate solver fills within the same transaction/block window to revert with `Unauthorized`. This breaks the core guarantee `solverSelection` is meant to provide — that only the user-authorized solver can complete the fill — and can be used to grief solvers out of gas and delay/deny order execution for users who enabled `solverSelection`.

### Likelihood Explanation
High for any integration that does not strictly rely on `SolverAccount`'s single-UserOperation atomic bundling of `select` + `fillOrder` (documented as the intended pattern specifically because of this class of risk). Any solver or relayer that submits `select` and `fillOrder` as separate transactions is directly exposed, since `select` performs no access control on `msg.sender` and no check for an existing/expected value before overwriting the transient slot.

### Recommendation
Add access control to `select()`/`_select()`: require `msg.sender == options.solver` (or restrict to `SolverAccount` calling on its own behalf) before writing to `tstore`, so an unrelated address cannot stage or overwrite a selection for someone else's commitment. Alternatively, bind the transient slot to `msg.sender` as part of the key rather than solely `commitment`, and/or gate `fillOrder`'s comparison to require that the caller of `select` matches the caller of `fillOrder`.

### Proof of Concept
1. `solverSelection` is enabled on `IntentGatewayV2`.
2. User places an order with `session = sessionKeyAddress`, computing `commitment`.
3. Legitimate solver A prepares to call `select({commitment, solver: A, signature: validSessionSig})` and `fillOrder(order, ...)` as two separate transactions (not routed through the atomic `SolverAccount` UserOperation bundling).
4. Attacker, seeing A's pending `select` transaction or simply racing after order placement, calls `select({commitment, solver: attacker, signature: attackerControlledSig})` in an earlier transaction within the block, using any signature that recovers to some `sessionKey` value (the function does not validate that the recovered key matches the order's real session key at call time — that binding is only checked later by `fillOrder`'s comparison).
5. The `tstore(commitment, ...)` slot is overwritten with `keccak256(abi.encode(attacker, recoveredSessionKey))`.
6. If A's subsequent `select` call in the same transaction as A's `fillOrder` does not run, or A's `fillOrder` executes in a different transaction than A's own `select` and lands after the attacker's overwrite, `fillOrder`'s stored-hash comparison (`tload(commitment)` vs `keccak256(abi.encode(msg.sender, order.session))`) fails and A's fill reverts with `Unauthorized`, referenced at [3](#0-2) , even though A held a valid session-key authorization.
