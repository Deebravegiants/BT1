### Title
Webhook shop/topic/webhook-id are trusted without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` signs and verifies only the raw request body via HMAC, while the `shop-domain`, `topic`, `webhook-id`, and `api-version` values are taken directly from unauthenticated HTTP headers and are never part of the signed material. `ShopifyAPI::Webhooks::Registry.process` then dispatches the handler using this unauthenticated `shop` value as the tenant identity, breaking the equality that should hold between "bytes verified" and "bytes acted on."

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The HMAC itself is read from the `hmac-sha256` header, and `shop`, `topic`, `webhook_id`, and `api_version` are all separately read from other headers that are not part of the signed payload: [2](#0-1) 

`HmacValidator.validate_signature` only compares the computed HMAC of `to_signable_string` (i.e., the body) against the received signature — it never incorporates `shop`, `topic`, or `webhook_id`: [3](#0-2) 

`Registry.process` validates only this body HMAC, then dispatches to the handler using the unauthenticated `request.shop` and `request.topic` values as the trusted tenant/topic context: [4](#0-3) 

Because the shop-domain header is not bound to the signature, any entity capable of obtaining one valid `(body, hmac)` pair for their own shop (e.g., an app's own merchant, who legitimately receives webhooks addressed to their own endpoint) can replay that same body/hmac pair while substituting the `shopify-shop-domain` header for a different shop. The signature still validates because it never covered the shop field, and the host application (via `WebhookMetadata.new(... shop: request.shop ...)`) will process the payload as if it belongs to the victim shop.

### Impact Explanation
This breaks the equality `shop authenticated == shop the data is attributed to`, allowing a merchant/attacker who controls their own valid webhook traffic to inject or misattribute webhook events to an arbitrary other shop domain in a multi-tenant host application, since the gem provides no cryptographic binding between the verified bytes (body) and the acted-upon identity (`shop`, `topic`, `webhook_id`). This is a cross-tenant integrity/authenticity failure in the primitive the gem is meant to provide (`Utils::HmacValidator.validate` / `Webhooks::Registry.process`).

### Likelihood Explanation
Any party that can obtain one legitimately-signed webhook body for their own shop (trivial for any merchant with the app installed, since webhooks are delivered without transport-level shop authentication beyond this HMAC) can immediately replay it with a forged `shop-domain` header — no access to `api_secret_key` or any privileged credential is required, only observation of one valid webhook delivery to their own endpoint.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the signable string used by `Request#to_signable_string` (or otherwise cryptographically bind them to the HMAC), so `HmacValidator.validate` fails if any of these attacker-controllable headers are altered relative to what was originally signed by Shopify.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and receives a legitimate webhook: body `{"foo":"bar"}`, header `shopify-shop-domain: attacker-shop.myshopify.com`, `shopify-hmac-sha256: <valid hmac of body>`.
2. Attacker resends the identical body and HMAC to the app's webhook endpoint but sets `shopify-shop-domain: victim-shop.myshopify.com`.
3. `HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` passes because it only checks the body against the HMAC.
4. `Registry.process` in `lib/shopify_api/webhooks/registry.rb` dispatches `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` to the handler, causing the host application to process attacker-supplied data under the victim shop's tenant context.
