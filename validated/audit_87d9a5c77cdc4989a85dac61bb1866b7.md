### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant data attribution - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely by checking an HMAC over the raw request body. The `shop` (and `topic`, `webhook_id`, `api_version`) values, which are taken from unauthenticated HTTP headers and handed to the app's handler as the tenant identifier, are never part of the signed data. Any party capable of obtaining one valid `(body, hmac)` pair for the app (e.g., by installing the app on their own store and receiving a real webhook) can replay that exact body/signature while substituting an arbitrary `X-Shopify-Shop-Domain` header, causing the host application to process the payload as if it belonged to a different, victim shop.

### Finding Description
`Registry.process` performs exactly one authenticity check: [1](#0-0) 

```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
``` [1](#0-0) 

`request.shop` is read straight from the `X-Shopify-Shop-Domain`/`shopify-shop-domain` HTTP header without any cryptographic binding: [2](#0-1) 

The HMAC that `HmacValidator.validate` checks is computed over `to_signable_string`, which for `Webhooks::Request` returns only the raw body: [3](#0-2) 

```ruby
sig { override.returns(String) }
def to_signable_string
  @raw_body
end
```

And `HmacValidator` simply HMACs that signable string with the app's shared `api_secret_key`: [4](#0-3) 

The identity binding that should hold is:
`shop header value == shop that actually produced/owns the signed body`

But because `shop` (and `topic`, `webhook_id`, `api_version`) are excluded from the signed bytes, the equality only holds by convention, not by proof. Anyone who possesses a legitimately-signed `(raw_body, hmac)` pair for the shared app secret — trivially obtainable by installing the target app on any store they control and capturing one real webhook delivery — can forge a new HTTP request with the same body/HMAC but an arbitrary `X-Shopify-Shop-Domain` header (a victim's shop) and pass `HmacValidator.validate` successfully, since `api_secret_key` is shared across all installations of the app, not per-shop.

The gem's own documentation instructs developers to trust `data.shop` from the handler as the tenant key after `Registry.process` "will verify the request did indeed come from Shopify": [5](#0-4) [6](#0-5) 

### Impact Explanation
This breaks the tenant identity binding at the core of the gem's webhook verification API: a value (`shop`) that host applications are told to trust and act on (e.g., `perform_later(shop_domain: data.shop, ...)`, per the documented example) is not covered by the cryptographic check that is supposed to prove authenticity. An attacker who controls even one shop installation of the target app can attribute their own webhook payloads to any other shop that has installed the app, corrupting per-tenant data isolation in any host application that follows the gem's documented usage pattern verbatim — a cross-tenant data-integrity violation.

### Likelihood Explanation
Moderate-to-high: the only prerequisite is installing the target Shopify app on an attacker-controlled development/free store (or any store the attacker can create) to capture one legitimately-signed webhook body/HMAC pair for that app's shared `api_secret_key`. No access token, refresh token, or `client_secret` needs to be stolen — the attacker only needs their own valid install, which is available to any unprivileged internet user who can install a public Shopify app. Header spoofing (`X-Shopify-Shop-Domain`) against the app's own webhook endpoint is trivial.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the value that is authenticated, or have `Registry.process` cross-check the `shop` header against an independently-verified source (e.g., a shop the app has an active, previously-established offline session for) before invoking the handler. At minimum, document prominently that `data.shop` from `Registry.process` is not covered by the HMAC and must not be treated as attacker-proof without additional verification against known installed shops.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and triggers a webhook (e.g. `orders/create`), capturing the raw POST body `B` and the `X-Shopify-Hmac-Sha256` header value `H` Shopify sent to the app's webhook endpoint.
2. Attacker sends a new POST request to the same app webhook endpoint with:
   - Body: `B` (unchanged)
   - `X-Shopify-Hmac-Sha256: H` (unchanged)
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (forged)
   - `X-Shopify-Topic: orders/create`
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `request.to_signable_string` (`= B`) using the shared `api_secret_key` and matches `H` — validation succeeds.
4. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker's order data>, ...)` and the host app (following the documented pattern) stores/processes attacker-controlled data under the victim shop's tenant identity.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
