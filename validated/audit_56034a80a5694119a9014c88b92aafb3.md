Audit Report

## Title
Response cache key omits `MaxResponseBytes`, allowing a workflow request's own response-size bound to be silently bypassed via a cached response fetched under a larger/unbounded limit - (File: core/services/gateway/handlers/capabilities/v2/response_cache.go)

## Summary
The gateway's HTTP action response cache keys entries via `req.Hash()`, which the code comment states covers only `(method, URL, headers, body, workflowOwner)`, and `TestRequestHash` confirms `CacheSettings` and `WorkflowID` do not affect the hash. [1](#0-0) [2](#0-1)  `MaxResponseBytes` is not part of the hash and is never re-checked on a cache hit in `Fetch()`, meaning a request with a small `MaxResponseBytes` can receive a previously cached body that was fetched and stored under a different (larger) `MaxResponseBytes`, bypassing the caller's own bound entirely. [3](#0-2) 

## Finding Description
In `makeOutgoingRequest`, when `req.CacheSettings.MaxAgeMs > 0`, the handler calls `h.responseCache.Fetch(httpCtx, req, callback, req.CacheSettings.Store)`, where `callback` wraps `httpclient.Send()` (the only place that enforces `MaxResponseBytes` via `http.MaxBytesReader`). [4](#0-3)  On a cache hit, `Fetch()` returns `cachedResp.response` directly without invoking `callback()` at all, so `httpclient.Send()`'s `maxReadBytes` enforcement is never reached for that request. [5](#0-4)  Since the cache key is derived from `req.Hash()` and (per the code comment and `TestRequestHash`) excludes non-content fields, two requests differing only in `MaxResponseBytes` will collide on the same cache entry, letting the second, more tightly-bounded request receive a body sized according to the first request's limit.

I was unable to directly inspect the `OutboundHTTPRequest.Hash()` implementation itself, since it lives in the external `chainlink-common` module (`github.com/smartcontractkit/chainlink-common/pkg/types/gateway`) rather than in this repository, so I could not fully confirm from source exactly which fields participate in the hash beyond what the doc comment and existing tests in this repo imply. However, the doc comment on `responseCache` explicitly enumerates `(method, URL, headers, body, workflowOwner)` as the hash inputs, and `TestRequestHash` explicitly demonstrates that `CacheSettings` and `WorkflowID` are excluded — no test exercises `MaxResponseBytes` variance, which is consistent with (but not from my direct inspection a 100% proof of) the claim that it's excluded too. [6](#0-5) 

## Impact Explanation
This is a same-`workflowOwner` cache collision, not a cross-tenant confidentiality break — the owner is part of the key per the doc comment. [7](#0-6)  The practical impact is that a node processing a workflow's outbound HTTP action can receive a larger response body than the `MaxResponseBytes` it specified for that particular request, defeating a resource/cost guard, but this does not cross the boundary between different users/workflow owners and does not constitute unauthorized fund movement, authentication bypass, or the impersonation/subscription-bypass categories emphasized in the required impact list. This narrows the applicability to the in-scope impact categories.

## Likelihood Explanation
Triggering requires the same workflow owner to issue two same-owner requests differing only in `MaxResponseBytes` for the same method/URL/headers/body with caching enabled — a plausible but narrow, self-inflicted scenario (the "attacker" and "victim" are the same owner). There is no cross-user or privilege-escalation angle demonstrated.

## Recommendation
Include `MaxResponseBytes` (or any response-size-affecting field) in the cache key, or validate/truncate the cached body against the current request's `MaxResponseBytes` before returning it from `Fetch()`.

## Proof of Concept
As described in the report: issue an `OutboundHTTPRequest` with `MaxResponseBytes: 1_000_000` and `CacheSettings.Store=true` against an endpoint returning ~900KB, then issue an otherwise-identical request (same owner/method/URL/headers/body) with `MaxResponseBytes: 1000`; since `Fetch()` uses `req.Hash()` (excluding `MaxResponseBytes` per the code comment) as the cache key, the second request receives the cached ~900KB body without `httpclient.Send()`'s `MaxBytesReader` ever being invoked for it. func (rc *responseCache) Fetch(ctx context.Context, req gateway.OutboundHTTPRequest, fetchFn func() gateway.OutboundHTTPResponse, storeOnFetch bool) gateway.OutboundHTTPResponse {
	cacheKey := req.Hash()
	cacheMaxAge := time.Duration(req.CacheSettings.MaxAgeMs) * time.Millisecond

	// Fast path: check cache without singleflight overhead.
	rc.cacheMu.RLock()
	cachedResp, exists := rc.cache[cacheKey]
	rc.cacheMu.RUnlock()
	if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
		rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
		return cachedResp.response
	}
