## Title
Webhook shop identity not covered by HMAC allows cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes and verifies the webhook HMAC over the raw request body only, while the `shop` (and `topic`/`api_version`/`webhook_id`) fields that `Registry.process` trusts and hands to the app's webhook handler are taken from unsigned HTTP headers. Because the app's webhook signing secret (`Context.api_secret_key`) is shared across every shop/tenant that has installed the app, an attacker who controls one installed shop can capture a validly-signed webhook body from their own tenant and replay it against the app's webhook endpoint with the `X-Shopify-Shop-Domain` header changed to a victim shop. The HMAC still validates (it only signs the body), and the handler is invoked believing the event belongs to the victim tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `shop`, `topic`, `api_version`, and `webhook_id` are read straight from attacker-visible/attacker-settable HTTP headers with no binding to the signature: [2](#0-1) 

`Registry.process` validates only the HMAC-over-body, then unconditionally trusts `request.shop` and forwards it as the tenant identity to the app's handler: [3](#0-2) 

`Utils::HmacValidator.validate` (the shared verifier used for both OAuth callbacks and webhooks) simply recomputes `HMAC(secret, to_signable_string)` and compares it to the supplied signature — for webhooks, `to_signable_string` never includes `shop`: [4](#0-3) 

This breaks the identity binding `HMAC-authenticated bytes == bytes the handler treats as this tenant's event`. For a multi-tenant app, `Context.api_secret_key` (the app's client secret) is the same for all installed shops, so a signature computed by Shopify for tenant A's webhook is also a valid signature for the identical body claimed to originate from tenant B — the shop header is never part of what was signed.

### Impact Explanation
This allows cross-tenant access/confusion: an attacker who is a legitimate merchant on their own store (an "unprivileged" party relative to other tenants of the app) can trigger genuine, validly-HMAC'd webhook deliveries to the shared app endpoint by taking ordinary actions in their own shop (e.g., creating an order, updating a product), capture the raw body + valid HMAC, and replay it to the app's webhook endpoint with the `shopify-shop-domain` header rewritten to the victim shop's domain. Because `Registry.process` only checks the body HMAC and then passes the attacker-chosen `shop` straight to `WebhookMetadata`, any application logic that uses `data.shop` to select the tenant record/session (a common integration pattern) can be made to write, delete, or act on the victim's data using the attacker's payload, or to falsify events "from" a shop the attacker doesn't operate. This matches the "cross-tenant access" High/Critical impact class.

### Likelihood Explanation
Likelihood is meaningful because the prerequisite (being an installed merchant of the app, i.e., an ordinary unprivileged app user) is trivial for many public/multi-tenant Shopify apps, and capturing/replaying one's own validly signed webhook body plus swapping a header is a simple HTTP replay — no secrets need to be broken since the attacker only needs a webhook that was legitimately signed for their own shop.

### Recommendation
Bind the shop (and topic/webhook id) to the signature, e.g. include the `X-Shopify-Shop-Domain`, `X-Shopify-Topic`, and `X-Shopify-Webhook-Id` header values in the string that is HMAC-verified (`to_signable_string`), or otherwise cryptographically bind the shop identity to the payload before trusting it in `Registry.process`/`WebhookMetadata`. At minimum, document clearly that `request.shop` is unauthenticated and must be cross-checked by the host application against a known, previously stored session for that shop before use.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker.myshopify.com` and triggers a webhook (e.g., `orders/create`) with a chosen body `B`.
2. Shopify sends `POST /webhooks` with headers `X-Shopify-Hmac-Sha256: HMAC(secret, B)`, `X-Shopify-Shop-Domain: attacker.myshopify.com`, body `B`.
3. Attacker resends the exact same request to the app's webhook endpoint but changes only `X-Shopify-Shop-Domain` to `victim.myshopify.com`.
4. `HmacValidator.validate` recomputes `HMAC(secret, B)` from `to_signable_string` (= `B`), which still matches, since the shop header was never part of the signed content — see [5](#0-4)  and [6](#0-5) .
5. `Registry.process` passes `shop: request.shop` = `"victim.myshopify.com"` to the app handler as if the event genuinely originated from the victim tenant — see [7](#0-6) .

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
