### Title
Webhook shop identity is not covered by HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` identity from the `X-Shopify-Shop-Domain` header, but the HMAC signature validated by `HmacValidator` only covers the raw request body, not the shop header. An attacker who possesses one valid `(body, hmac)` pair for a webhook (trivially obtainable by installing the app on an attacker-controlled shop and triggering any webhook) can replay that exact body/HMAC to the app's webhook endpoint while substituting the `shop-domain` header with a victim shop's domain. The signature check still passes because it only validates the body bytes, so the app processes attacker-supplied webhook data under the victim's shop identity.

### Finding Description
The webhook signature verification flow is:
- `HmacValidator.validate` computes/compares the signature over `verifiable_query.to_signable_string` only: [1](#0-0) 
- `Webhooks::Request#to_signable_string` returns only `@raw_body`, excluding all headers: [2](#0-1) 
- `Webhooks::Request#shop` is read straight from the unauthenticated `shopify-shop-domain` (or `x-shopify-shop-domain`) header, which is not part of the signed bytes: [3](#0-2) 
- `Registry.process` validates the HMAC over the body, then immediately hands `request.shop` (the unverified header) to the handler as the trusted tenant identity, with no cross-check against the signed payload: [4](#0-3) 

This is the exact bug class from the report: the HMAC verifies one set of bytes (the body), but a security-relevant field acted upon downstream (the shop/tenant identity) is not included in those verified bytes. Just as `GnosisTargetDispenserL2` accepted arbitrary bridged data without checking the L1 sender, this gem's webhook handler accepts an arbitrary `shop-domain` header without checking that it is bound to the HMAC-covered body.

**Identity binding broken:** `shop_used_for_tenant_routing (header, unauthenticated) != shop_embedded_in_hmac_signed_bytes (none — shop is not signed at all)`.

### Impact Explanation
An attacker with the ability to trigger even one legitimate webhook (e.g., by installing the app on their own, attacker-controlled shop and performing an action like `orders/create`) obtains a valid `(raw_body, X-Shopify-Hmac-Sha256)` pair signed with the app's `client_secret`. Because the signature does not cover the `shop-domain` header, the attacker can replay this exact body/HMAC pair to the app's webhook endpoint with the header changed to any victim shop domain. `HmacValidator.validate` will still return `true` (body bytes are unchanged), and `Registry.process` will dispatch the attacker-controlled payload to the handler tagged as belonging to the victim shop (`WebhookMetadata#shop`). Depending on how the host application persists or acts on webhook data (e.g., updating shop-scoped records, triggering redaction/compliance flows such as `customers/redact` or `shop/redact`, or writing data keyed by `shop`), this results in cross-tenant data corruption/confusion — an attacker forging events that appear to originate from a shop they do not control.

### Likelihood Explanation
Likelihood is realistic: any attacker can become a legitimate merchant/installer of the app for a nominal or free store and generate at least one signed webhook of any subscribed topic. Replaying an HTTP request with a different header value requires no special access to the app's `client_secret`, TLS interception, or any privileged account — it is a pure unprivileged internet request against the app's public webhook endpoint, satisfying the ask-only-mode's unprivileged-attacker requirement.

### Recommendation
Bind the `shop` value to the HMAC-signed content instead of trusting the header in isolation:
- Include the `shop-domain` header (and ideally `topic`, `webhook-id`) in the `to_signable_string` payload used for HMAC verification, or
- After HMAC validation, cross-validate `request.shop` against the shop identity embedded in `parsed_body` (Shopify webhook payloads typically include shop-scoped fields) or against a shop that the app already has an active, HMAC-verified session/installation for, rejecting requests where these disagree.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` and triggers a subscribed webhook topic (e.g. `orders/create`), capturing the raw POST body and the `X-Shopify-Hmac-Sha256` header sent by Shopify.
2. Attacker resends this exact `raw_body` and `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (`@raw_body` only) — this still matches, so validation passes: [5](#0-4) 
4. `request.shop` returns `"victim-shop.myshopify.com"` from the spoofed header, and `handler.handle` is invoked with `WebhookMetadata.new(... shop: request.shop ...)`, causing the app to process/attribute the attacker's forged payload to the victim shop: [6](#0-5)
