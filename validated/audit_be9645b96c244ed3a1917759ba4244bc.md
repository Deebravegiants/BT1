Audit Report

## Title
JWT/Bearer auth token logged in plaintext when the Vault gateway handler receives a JSON-RPC message - ([File: core/capabilities/vault/gw_handler.go])

## Summary
`GatewayHandler.HandleGatewayMessage` logs the entire inbound `jsonrpc.Request[json.RawMessage]` struct — including its `Auth` field carrying the caller's raw JWT/bearer token — at Debug level via `reqLggr.Debugw("received message from gateway", "req", req)`, before any authorization or redaction occurs. This runs unconditionally for every gateway-forwarded message on this hot path, unlike other call sites in the same package that deliberately avoid logging the raw token.

## Finding Description
`HandleGatewayMessage` at [1](#0-0)  is the entry point processing every JSON-RPC request relayed from the gateway to the Vault capability handler. Its first statement passes the whole `req` (a `*jsonrpc.Request[json.RawMessage]`) to a structured logger field. The `Auth` field of this same request type is confirmed to carry the caller's raw JWT across the codebase: it is read directly for authentication in `jwtBasedAuth.AuthorizeRequest` via `v.validateToken(ctx, req.Auth)` [2](#0-1) , it's explicitly populated with a minted token in tests via `req.Auth = mustMintVaultJWTForRequest(...)` [3](#0-2) , and it is deliberately stripped before re-marshalling outbound test requests via `outboundRequestWithoutAuth` (`req.Auth = ""`) [4](#0-3) .

Other call sites in the same package show the codebase treats `Auth` as sensitive: `authorizer.go`'s `AuthorizeRequest`/`authorizeRequest` log only `"hasAuth", req.Auth != ""` rather than the token value [5](#0-4) , and `GatewayVaultRequestProcessor.authorizeAndStamp` similarly logs `"hasAuth", req.Auth != ""` [6](#0-5) . No `MarshalLogObject`/custom redaction wrapper for `jsonrpc.Request` was found in this repo's index — the type is defined in the external `chainlink-common` dependency and is logged as a plain struct/value.

Critically, this `Debugw` call at line 182 executes before `AuthorizeRequest`/JWT validation, which only happens later inside `h.requestProcessor.ProcessRequest(ctx, req, ...)` at lines 194 and 201 of the same function. This means the token is logged regardless of whether it is later validated as legitimate or rejected, and fires for every message reaching this handler with no additional preconditions or gating.

## Impact Explanation
If Debug-level logging is enabled (a supported, non-privileged, operator-configurable logging level rather than a developer-only mode), every caller's JWT/bearer token used to authenticate Vault secret operations (`SecretsCreate`, `SecretsUpdate`, `SecretsDelete`, `SecretsList`) is written to node logs in cleartext, before authorization completes. Anyone with read access to those logs (log aggregation, monitoring/observability pipelines, support tooling) can extract a valid token and replay it within its validity window to impersonate the original token holder for Vault secret operations. This maps to an in-scope key/secret exfiltration and gateway request impersonation impact class.

## Likelihood Explanation
Likelihood is moderate: exploitation requires Debug-level logging to be enabled on the node and an attacker (or insider) with read access to node logs, but the vulnerable log statement itself is unconditional on the hot path — it fires for every gateway-forwarded JSON-RPC message to the Vault handler regardless of whether the accompanying token is ultimately valid or rejected, with no sampling or additional gating.

## Recommendation
Remove or redact the `Auth` field before logging the request in `HandleGatewayMessage`. Log only non-sensitive fields (`req.Method`, `req.ID`) or an explicit `"hasAuth", req.Auth != ""` boolean, consistent with the existing pattern already used in `gateway_vault_request_processor.go` and `authorizer.go`.

## Proof of Concept
1. Enable Debug-level logging on a Chainlink node running the Vault gateway handler (`GatewayHandler`).
2. As any client capable of reaching the gateway's vault JSON-RPC endpoint, send a request (e.g., `secrets_list`) with `Auth` set to a bearer JWT.
3. `GatewayHandler.HandleGatewayMessage` (`core/capabilities/vault/gw_handler.go:182`) executes `reqLggr.Debugw("received message from gateway", "req", req)` before `AuthorizeRequest` runs.
4. Inspect node logs: the "received message from gateway" entry contains the full raw JWT in the `req.Auth` field, in cleartext, independent of whether the token is subsequently accepted or rejected.
