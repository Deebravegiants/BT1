### Title
Donated tokens/ETH sitting in `EmporiumUpgradeable` are minted into a user's shielded UTXO via balance-diff accounting - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
`EmporiumUpgradeable.runAction` computes the output UTXO amount to shield purely from the *change* in the contract's own `address(this)` token/ETH balance around an arbitrary batch of calls, with no binding to what the executed operations actually produced. Because the contract has an unrestricted `receive()` and can receive ERC20 tokens from any address at any time, an attacker can pre-fund the Emporium contract with tokens/ETH, and the next legitimate `runAction` call will fold that donated balance into the caller's own shielded output UTXO, minting shielded value the depositing user never actually deposited or earned.

### Finding Description
`runAction` snapshots balances before and after executing the signed/unsigned operation batch: [1](#0-0) [2](#0-1) 

The resulting `balanceChange` (adjusted only by `deltaAmountChanges`, which the circuit/prover controls but which has no relation to *external* funds sent to the contract by third parties) is passed straight into `handleOut`, which mints a real UTXO for the caller and transfers the balance out to `msg.sender`: [3](#0-2) 

The contract accepts ETH from anyone via an unrestricted `receive()`: [4](#0-3) 

and it can likewise receive ERC20 tokens from any address via a plain `transfer`/`safeTransfer` call (no allow-list on the sender of incoming tokens). This is the same bug class as the referenced `LidoMevTxFeeVault` report: a contract whose ETH/token balance feeds directly into a value-distribution calculation accepts inbound value from unauthenticated senders, so that value gets folded into whichever party's calculation runs next.

This breaks the balance equation the whole Hinkal system relies on: the amount credited as a new shielded UTXO (`outUtxo.amount` in `handleOut`) is supposed to equal exactly what circomData-verified inputs/outputs and the executed ops produced, not "whatever token balance happens to sit in the contract at the moment `balancesAfter` is read." Once this UTXO is created it flows back into `Hinkal.sol`'s `_externalTransact` → `insertCommitments`, permanently adding a note to the shielded Merkle tree.

### Impact Explanation
This is a High/Critical-severity issue: it allows a user to have a legitimate, proof-verified `runAction` call mint a shielded UTXO larger than what they actually deposited/earned, backed by tokens that belong to whoever accidentally or maliciously sent them to `EmporiumUpgradeable` (e.g., another user's stuck relay fee, dust left from a prior failed op, or an attacker deliberately "gifting" tokens right before calling `runAction` themselves). This is effectively unbacked minting of shielded value / theft of funds sitting in the Emporium contract that were never authorized to be assigned to that particular UTXO.

### Likelihood Explanation
Likelihood is moderate: it requires that some ERC20/ETH balance be resident in the `EmporiumUpgradeable` contract at the time a legitimate `runAction` call executes — which can happen either accidentally (leftover dust from `payRelayFees`, a partially-failed op batch, or wallet interactions) or be deliberately engineered by an attacker who sends tokens to the contract right before invoking `runAction` themselves (no special privilege needed, any EOA can send ERC20/ETH to a contract address).

### Recommendation
Do not derive the minted UTXO amount from a raw before/after balance diff of the shared contract address. Instead:
- Track and account for funds by "operation" rather than by ambient contract balance, e.g. by having each op explicitly report the amount it moved, or by using a per-call transient/local accounting variable, not `address(this).balance` / `balanceOf(address(this))`.
- Alternatively, sweep or zero out (transfer to relay/owner or refuse) any pre-existing balance before starting the before/after measurement window so unrelated inbound funds can never be attributed to the current caller's UTXO.
- Reject/limit unauthenticated ETH and ERC20 inflows to the Emporium contract analogous to hardening the `receive()` function, similar to the recommendation in the referenced Lido report.

### Proof of Concept
1. Attacker calls `EmporiumUpgradeable`'s `receive()` (or transfers ERC20 tokens directly) to send `X` tokens/ETH to the Emporium contract, increasing its resident balance for `erc20TokenAddresses[i]`.
2. Any user (attacker themselves, or as a griefing/self-benefit trick even the same attacker) then submits a normal `transact` call through `Hinkal.sol` whose `externalActionData` routes to `EmporiumUpgradeable.runAction` for that same token, with legitimate `circomData`/proof for a small or zero net operation.
3. `runAction` snapshots `balancesBefore` (which already reflects the attacker's earlier donation) then executes the op batch; `balancesAfter` still includes the donated `X` since nothing in the flow removes it.
4. `balanceChange = balancesAfter - balancesBefore` at minimum includes any residual increase from the batch, but because `balancesBefore` was polluted at any point prior to the call (e.g., attacker sends `X` in the same block just before this transaction, or dust from prior failed calls remains), an attacker who controls both the "donation" and the "runAction" call (e.g., by front-running/bundling with the actual op) can cause `handleOut` to mint and transfer out `X` extra tokens to themselves as `msg.sender`, receiving funds they never legitimately deposited and creating a shielded UTXO for that inflated amount.

```text
            circomData.erc20TokenAddresses
        );

        UTXO[] memory utxoSet = new UTXO[](
            circomData.erc20TokenAddresses.length
        );

        uint256 utxoSetLength;

        for (uint256 i = 0; i < circomData.erc20TokenAddresses.length; i++) {
            int256 balanceChange = int256(balancesAfter[i]) -
                int256(balancesBefore[i]);

            if (deltaAmountChanges[i] < 0) {
                balanceChange -= deltaAmountChanges[i];
                // this equation reads: total change of emporium balance = what was moved to emporium (-deltaAmountChange) + how emporium balance changed through tx (balanceChange)
            }

            // the only case when balanceChange can be < 0, when there were some funds on emporium before the call
            if (balanceChange < 0) {
                revert BalanceChangeShouldBePositive();
            }

            UTXO memory utxoOut = handleOut(balanceChange, circomData, i);

            if (utxoOut.amount > 0) {
                utxoSet[utxoSetLength++] = utxoOut;
            }
        }
```

```text
    function handleOut(
        int256 balanceChange,
        CircomData calldata circomData,
        uint256 i
    ) internal returns (UTXO memory outUtxo) {
        // total change can be less than zero if there was some balance before the call -> that's why we have <=
        if (balanceChange <= 0) {
            return outUtxo;
        }

        transferERC20TokenOrETH(
            circomData.erc20TokenAddresses[i],
            msg.sender,
            uint256(balanceChange)
        );

        outUtxo = UTXO(
            uint256(balanceChange),
            circomData.erc20TokenAddresses[i],
            circomData.stealthAddressStructure,
            circomData.timeStamp
        );
    }
```
