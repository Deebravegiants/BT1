Based on the code analysis, this proposed vulnerability does not hold up.

#### Why the attack described is not exploitable

The denominator `total_stake` used in `calculate_alpenglow_points` comes from `reward_epoch_delegated_stakes.delegated_stakes`, which is a **frozen snapshot** computed exactly once per reward epoch in `Stakes::calculate_activated_stake`, by summing `delegation_activation_status(...).effective` (i.e., the same `delegation_effective_stake`-equivalent function) across *all* stake delegations present at that epoch boundary: [1](#0-0) [2](#0-1) 

Both the numerator (`stake_amount`, via `delegation_effective_stake`) and this frozen denominator are keyed to the exact same historical `epoch` argument (`rewarded_epoch`) and the same `stake_history`, so they represent the same point-in-time snapshot by construction: [3](#0-2) 

Crucially, the code explicitly guards against the "decoy stake activation/deactivation near the boundary" scenario the question raises. The comment in `calculate_block_reward` and the design of `RewardEpochDelegatedStakes` state this is deliberately snapshotted so that later mutations to the live `StakesCache` (which occur during multi-block partitioned reward distribution) don't skew the denominator: [4](#0-3) 

This exact scenario — stake accounts activating/deactivating around the reward epoch boundary — is directly covered by existing tests, including `test_stake_activating_deactivating`, `test_changing_total_stake`, and `test_recalculate_alpenglow_rewards_after_partial_distribution_uses_original_denominator`, all of which assert the denominator used for reward calculation stays consistent with the frozen epoch-boundary value regardless of subsequent stake changes: [5](#0-4) [6](#0-5) 

An unprivileged attacker delegating/undelegating their own decoy stake accounts cannot desynchronize the numerator and denominator for *other* delegators' `ag_points`, because:
1. Any stake account (attacker's or otherwise) that exists at the epoch boundary contributes identically to both the individual `stake_amount` computation (via `delegation_effective_stake` at `rewarded_epoch`) and the aggregate `total_stake` snapshot (via the same effective-stake logic summed in `calculate_activated_stake`).
2. If a stake account is closed/withdrawn *after* the snapshot but before distribution, it simply forfeits its own reward share (the denominator was already fixed including its contribution) — this causes at most an under-distribution to that departed account, not an over-distribution to remaining delegators, since the arithmetic `earned_credits * stake_amount / total_stake` is a per-delegator independent calculation bounded by the frozen `total_stake`.

Therefore, there's no reachable path for an unprivileged attacker to cause `sum(ag_points across delegators) * lamport_rate` to exceed the voter's allotted reward pool via timing of decoy stake (de)activation.
