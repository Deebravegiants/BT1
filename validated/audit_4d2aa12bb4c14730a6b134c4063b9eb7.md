## Title
LP Seeded at a Materially Off-Curve-Close Price via Budget-Capped Rebalance in Hostile HyperSwap Pre-Seed - (File: `packages/contracts/src/Bonding.sol`)

## Summary
CVE-2020-8227 is a class of bug where a client trusts unsanitized data from an untrusted counterparty (a malicious server) and, as a result, misplaces protected resources outside their intended, trusted boundary. The analogous trust boundary in alt.fun is the HyperSwap V2 `Pair` that `Bonding.finalizeGraduation` seeds: because pair creation and pre-funding are permissionless, an unrelated wallet fully controls the "untrusted response" (the pair's pre-existing reserves) that `Bonding` reads and trusts when computing how to correct the ratio before depositing protocol/curve LP. When the attacker's pre-seed ratio is extreme enough, `Bonding`'s own rebalance-swap budget cap prevents the correction from reaching the curve-close ratio, and the graduation still proceeds — permanently locking the protocol's LP into a pool priced materially away from the curve's closing price, exactly the "LP seeded away from the curve close price" harm called out as in-scope.

## Finding Description
`finalizeGraduation` → `_seedUniswapV2Direct` → `_seedRebalancing` → `_pairRebalance` computes a corrective swap `s` via `_noFeeSwapInput` to push the pre-seeded pair's reserves toward the cached curve-close ratio `(tokensForLP, ltFromPair)`, then caps it at `_swapBudget`, i.e. 99% of the available inventory on one side: [1](#0-0) [2](#0-1) 

`s` is silently truncated to `maxSwap` (`return s > maxSwap ? maxSwap : s;`) whenever the mathematically-required corrective input exceeds the 99% budget. There is no check afterward that the post-swap reserves are actually within any tolerance of the target ratio — `_routerDepositAndDispose` deposits whatever balanced subset the router's `quote()` allows at the (still skewed) post-swap ratio and unconditionally succeeds: [3](#0-2) 

Because `_ensureUniswapV2Pair` and `finalizeGraduation` are fully permissionless and operate on a HyperSwap pair anyone can `createPair`/`transfer`/`mint` into ahead of Phase 2, an attacker can choose reserves so lopsided (e.g. `reserveToken = tokensForLP/100`, `reserveLT = ltFromPair*200`) that the required corrective input is far beyond the 99% budget, guaranteeing the deposit lands ~2x or more off the curve's closing price. This is not a hypothetical edge case — it is precisely the scenario exercised (and knowingly accepted, not fixed) by the project's own `test_hostilePreSeed_budgetCappedSwap_isNotProfitable`: [4](#0-3) 

The root cause mirrors CVE-2020-8227's pattern: the contract accepts a response (pool reserves) generated entirely by an untrusted party without validating that the ultimate written state (the deposited LP) stays inside the intended trust boundary (the curve-close price band), and provides no reject/rescue path — deposit succeeds unconditionally regardless of how far the price actually diverges from the invariant `_prepareGraduationLiquidity` was designed to preserve.

## Impact Explanation
Every unit of protocol/curve-raised LT and every token reserved for LP (`LP_RESERVE`, 250M tokens) get locked via `LPLock.recordLock` into a pool priced away from the true curve-close marginal price — this is a direct, permanent mispricing of LP funds belonging to the protocol/creator/traders, satisfying the "LP seeded away from the curve close price" impact class. Because `LPLock` has no withdraw/rescue path in v1, the mispriced position cannot later be corrected by the protocol; it can only be arbitraged by third parties who additionally profit at the LP's expense (buying the underpriced side of the pool immediately post-graduation). The pre-seeder's own LP is confiscated/negative per the test, but the protocol's locked LP still opens and remains at the skewed price permanently.

## Likelihood Explanation
Any unrelated wallet can reach this: `factory.createPair(token, lt)` is permissionless, `transfer` + `pair.mint(attacker)` requires only cheap dust/small capital relative to the LP being seeded, and `finalizeGraduation` is itself permissionless so the attacker (or anyone) can trigger it once the pre-seed is in place. No privileged role, upgrade, or off-chain component is needed — only ordinary transactions from a single address timed between `_enterGraduating` (Phase 1) and `finalizeGraduation` (Phase 2). The only constraint is sizing the pre-seed ratio extreme enough to exceed the 99%-of-inventory swap budget, which is inexpensive relative to `tokensForLP`/`ltFromPair` for smaller graduations.

## Recommendation
Bound the acceptable post-rebalance price deviation in `_seedRebalancing`/`_routerDepositAndDispose` and fail closed rather than silently depositing at a materially skewed ratio: either revert (not brick-vulnerable if the fallback quarantines the pre-seed as a "toxic" pair and directs the protocol's LP to a freshly created replacement pair) or size `_swapBudget` dynamically so it always suffices to reach a bounded price-deviation tolerance, and only fall back to `_seedDirectMint` / accept the residual skew when the pre-existing reserves are provably negligible relative to `(tokensForLP, ltFromPair)` — not merely "budget exceeded."

## Proof of Concept
`test_hostilePreSeed_budgetCappedSwap_isNotProfitable` in `packages/contracts/test/TwoPhaseGraduation.t.sol` already demonstrates the mechanics end-to-end:
1. Launch and drive a token to `Lifecycle.Graduating` via `_enterGraduating`.
2. Front-run: attacker creates the HyperSwap pair and mints LP with `reserveToken = tokensForLP/100`, `reserveLT = ltFromPair*200` — a 20,000x skew.
3. Call permissionless `bonding.finalizeGraduation(tokenAddr)`.
4. Assertion confirms the pool opens at more than `1.2x` the curve-close price (`_poolPriceLtPerToken` vs. `ltFromPair/tokensForLP`), i.e., the protocol's locked LP is seeded materially away from curve-close, with no revert and no rescue path. [5](#0-4)

```text
    function _noFeeSwapInput(
        uint256 reserveIn,
        uint256 reserveOut,
        uint256 targetN,
        uint256 targetD,
        uint256 maxSwap
    ) internal pure returns (uint256) {
        if (reserveIn == 0 || reserveOut == 0 || targetN == 0 || targetD == 0 || maxSwap == 0) {
            return 0;
        }
        uint256 product = Math.mulDiv(reserveIn * reserveOut, targetN, targetD);
        uint256 newIn = Math.sqrt(product);
        if (newIn <= reserveIn) return 0;
        uint256 s = newIn - reserveIn;
        return s > maxSwap ? maxSwap : s;
    }
```

```text
    /// @notice M-02 reproducer. An LT-rich mint pre-seed so lopsided that the
    ///         TOKEN-side rebalance swap exhausts its full budget (~99% of
    ///         `tokensForLP`) without reaching the cached ratio, so the pool
    ///         deposits materially off curve-close. Finalize must still succeed
    ///         (no brick), the over-funded LT side must be confiscated to the
    ///         owner, and the pre-seeder must end net-negative.
    function test_hostilePreSeed_budgetCappedSwap_isNotProfitable() public {
        (address tokenAddr,) = _launchToken();
        _enterGraduating(tokenAddr);

        (uint256 tokensForLP, uint256 ltFromPair,,) = bonding.pendingGraduation(tokenAddr);

        // Extreme LT-rich shape: TOKEN side at 1% of target, LT side at 200x.
        // The optimal TOKEN-in swap to reach the cached ratio is ~1.4x
        // `tokensForLP`, so the 99%-of-`tokensForLP` budget cap binds and the
        // pool stays ~2x off curve-close after the swap.
        uint256 reserveToken = tokensForLP / 100;
        uint256 reserveLt = ltFromPair * 200;

        // M-02 precondition: the optimal swap exceeds the budget (this is the
        // budget-capped regime, distinct from the swap-rounds-to-zero fallback
        // covered by the dust tests above).
        assertGt(
            _noFeeSwapInputUncapped(reserveToken, reserveLt, tokensForLP, ltFromPair),
            (tokensForLP * 99) / 100,
            "setup: optimal rebalance swap must exceed the per-side budget (M-02 regime)"
        );

        deal(tokenAddr, griefer, reserveToken);
        address hyperPair = _grieferMintPreSeed(tokenAddr, reserveToken, reserveLt);
        uint256 grieferLp = MockHyperswapPair(hyperPair).balanceOf(griefer);
        uint256 ownerLtBefore = lt.balanceOf(bonding.owner());

        bonding.finalizeGraduation(tokenAddr);
        assertTrue(bonding.isGraduated(tokenAddr), "finalize must succeed despite an unrecoverable pre-seed");

        // The accepted residual: no bounded swap can correct a 200x LT-rich
        // pre-seed, so the pool opens materially off curve-close.
        assertGt(
            _poolPriceLtPerToken(hyperPair, tokenAddr),
            (((ltFromPair * 1e18) / tokensForLP) * 12) / 10,
            "M-02 regime: pool opens materially off curve-close"
        );
```
