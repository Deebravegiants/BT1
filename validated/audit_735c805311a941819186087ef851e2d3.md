### Title
Webhook shop domain and topic are trusted for dispatch without being covered by the HMAC signature, allowing replayed webhooks to be attributed to an arbitrary shop - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable content from the raw body only, while `shop`, `topic`, and `webhook_id` are read from unauthenticated HTTP headers and then passed straight into the app's webhook handler as trusted identifiers. This breaks the intended identity binding: `hmac_valid(body) == true` is treated as equivalent to `shop_header == true_originating_shop`, when in fact the HMAC never covers the shop header.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, and `#webhook_id` are pulled directly from HTTP headers with no cryptographic binding to the body or to each other: [2](#0-1) 

`Registry.process` validates only the HMAC over the body via `Utils::HmacValidator.validate(request)`, and once that passes, forwards `request.shop`, `request.topic`, and `request.webhook_id` — all header-derived and unauthenticated — into the handler as if they were verified: [3](#0-2) 

`HmacValidator.validate_signature` confirms the check is scoped strictly to the signable string (the body), never the headers: [4](#0-3) 

The identity binding that should hold is: `hmac_verified(raw_body) == true` implies `shop header == shop that produced raw_body`. In this implementation, the HMAC only proves the raw body wasn't tampered with — it says nothing about which shop, topic, or webhook-id it belongs to, because those values live entirely outside the signed content.

### Impact Explanation
Because the shop-identifying header is not bound to the signed body, a party that has ever received one legitimately-signed webhook body (e.g., from their own installed/test shop, since the signing secret is the app-wide `client_secret` shared across all shop installs of the app) can replay that exact `(raw_body, hmac-sha256 header)` pair to the app's webhook endpoint while substituting the `shopify-shop-domain` (and/or `shopify-topic`, `shopify-webhook-id`) header for a different, victim shop. `HmacValidator.validate` still returns `true` (the body and secret are unchanged), and `Registry.process` will dispatch to the handler with `WebhookMetadata#shop` set to the attacker-chosen victim shop domain. Any app logic keyed off `data.shop` (e.g., looking up per-shop session/state, crediting inventory, updating order status, sending notifications) can be triggered under a false tenant identity — a cross-tenant confusion/injection primitive reachable without possessing any merchant access token or the app's `client_secret`.

### Likelihood Explanation
Exploitation requires only network access to the app's public webhook endpoint plus possession of at least one previously delivered, validly-signed webhook body for any shop (attacker can obtain this trivially by installing the app on a shop they control, or intercepting/observing a delivered webhook for their own store). No credentials, session, or `api_secret_key` are needed by the attacker — they merely reuse the signature Shopify already produced. This is a straightforward HTTP replay with a header substitution, requiring no cryptographic work.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the signed content that is checked, or independently re-derive/verify the shop identity before trusting it for dispatch:
- Include `shop`, `topic`, and `webhook_id` in `Request#to_signable_string` (Shopify does not sign these today) — since that isn't controllable from this gem's implementation of the receiving side, apps must be documented to treat `WebhookMetadata#shop` as untrusted for authorization decisions, or
- Have `Registry.process`/`WebhookMetadata` require the caller to cross-check `shop` against a known, previously-registered shop/session store before acting on the payload, and explicitly document that only the body's authenticity — not the shop attribution — is guaranteed by `HmacValidator.validate`.

### Proof of Concept
1. Install the app on `attacker-shop.myshopify.com` and let Shopify deliver one legitimate webhook, capturing the exact `raw_body` and `x-shopify-hmac-sha256` header value.
2. Send a POST to the app's webhook endpoint with the same `raw_body` and same `x-shopify-hmac-sha256` header, but with `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses this into a `Request` whose `to_signable_string` is unchanged (still the same `raw_body`), so `Utils::HmacValidator.validate(request)` returns `true` per `lib/shopify_api/utils/hmac_validator.rb` lines 26-31.
4. `Registry.process` (lib/shopify_api/webhooks/registry.rb lines 188-200) invokes the app's handler with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, even though that shop never sent this webhook, demonstrating the identity-binding break.
