### Title
Panic-inducing unwrap()/checked_div(0) in `calc_take_pnl` permanently bricks Deposit/Withdraw/WithdrawPnl - ([File: program/src/processor.rs])

### Summary
The CVE-2017-5665 bug class is a crash triggered by attacker-influenced data hitting an unchecked/incorrectly-guarded arithmetic path in a parsing routine, causing a NULL pointer dereference. In `raydium-amm`, the analogous defect is in `Processor::calc_take_pnl`, where several `unwrap()` calls on `checked_sub`/`checked_div` results are not actually guarded against the failure conditions they are meant to prevent. When a pool's on-chain reserves and PnL bookkeeping reach a state that is fully reachable through ordinary swap/deposit/withdraw activity, this function will always panic, permanently aborting the instructions (`Deposit`, `Withdraw`, `WithdrawPnl`) that call it.

### Finding Description
`Processor::calc_take_pnl` computes an updated "post take-pnl" reserve point `(x2, y2)` from the pool's cached `target.calc_pnl_x` / `target.calc_pnl_y` and the current normalized reserves `x1`/`y1`:

<cite repo="Alyssadaypin/raydium-amm--022" path="program/src/processor.rs" start="199="209" /> [1](#0-0) 

```
let x2_power = Calculator::calc_x_power(target.calc_pnl_x.into(), target.calc_pnl_y.into(), x1, y1);
let x2 = x2_power.integer_sqrt();
let y2 = x2.checked_mul(y1).unwrap().checked_div(x1).unwrap();
...
let diff_x = U128::from(x1.checked_sub(x2).unwrap().as_u128());
let diff_y = U128::from(y1.checked_sub(y2).unwrap().as_u128());
```

Two independent unchecked failure modes exist here:

1. `checked_div(x1)` panics if `x1 == 0`. `x1` is `Calculator::normalize_decimal_v2(total_pc_without_take_pnl, amm.pc_decimals, amm.sys_decimal_value)` [2](#0-1) , computed with integer truncation: [3](#0-2) 
When `amm.pc_decimals > amm.coin_decimals`, `sys_decimal_value = 10^coin_decimals` [4](#0-3) , so `x1` truncates to `0` whenever `total_pc_without_take_pnl < 10^(pc_decimals - coin_decimals)` even though the raw pc reserve is non-zero. This is a normal, reachable state after ordinary swaps drain the pc side of the pool.

2. Even when `x1 != 0`, `x2 = sqrt(last_x * last_y * x1 / y1)` has no guarantee of being `<= x1`; whenever price/reserve movement makes `x2 > x1` (or `y2 > y1`), the `checked_sub(...).unwrap()` on the next line panics.

The only guard before entering this branch is a coarse product comparison: [5](#0-4) 
This comparison is computed in *native* (unnormalized) units restored via `Calculator::restore_decimal`, which does not prevent `x1` (normalized) from being `0` or `x2` from exceeding `x1`; it only guards against the "obviously stale" case.

`calc_take_pnl` is invoked from `process_deposit`, `process_withdraw`, and `process_withdrawpnl` [6](#0-5) [7](#0-6) [8](#0-7) , all of which are unprivileged, permissionless instructions reachable from a single transaction with attacker-chosen swap sizes over time.

Because `target.calc_pnl_x`/`calc_pnl_y` and the vault balances are persistent on-chain state that do not reset once this imbalance is created, and because `Deposit`, `Withdraw`, and `WithdrawPnl` all unconditionally call `calc_take_pnl` (as long as `amm.status != WithdrawOnly`), once the imbalance exists, *every* subsequent call to any of the three instructions will panic and abort — including the `WithdrawPnl` call that could otherwise correct `need_take_pnl_pc/coin` and the `Withdraw` call LPs need to exit the pool.

### Impact Explanation
Once the panic condition is reached, the pool becomes permanently unusable for `Deposit`, `Withdraw`, and `WithdrawPnl` — there is no other on-chain path to reset `target.calc_pnl_x/y` or the pool status flags that could unblock these calls (swap instructions do not go through `calc_take_pnl` in the same way and cannot repair the corrupted PnL bookkeeping). LPs lose the ability to withdraw their principal and pool owners lose the ability to withdraw accrued PnL, i.e. this results in **permanent freezing of user/LP funds** rather than a mere transient revert, satisfying the required impact bar.

### Likelihood Explanation
The precondition — a normalized reserve value truncating to zero, or a rounding mismatch making `x2 > x1` — is reachable purely through the natural sequence of unprivileged swap transactions that drain one side of the pool's reserves relative to accumulated `need_take_pnl_*`/`calc_pnl_*` state, particularly for token pairs with a large decimals gap (e.g., a 9-decimal token paired with a 0/2-decimal token). No privileged signer, validator collusion, or off-chain component is required; a single attacker (or even accidental market activity) submitting ordinary swap transactions can create the state.

### Recommendation
- Replace the unchecked `unwrap()`s in `calc_take_pnl` (`checked_div(x1)`, `checked_sub(x2)`, `checked_sub(y2)`) with proper error propagation (`ok_or(AmmError::...)?`) instead of panicking.
- Explicitly guard against `x1 == 0` / `y1 == 0` before doing the division, returning an `AmmError` instead of invoking `calc_take_pnl`'s risky math.
- Strengthen the pre-check at `program/src/processor.rs:190-192` to operate consistently in normalized units and reject/clamp cases where `x2 > x1` or `y2 > y1` rather than assuming the product comparison is sufficient.

### Proof of Concept
1. Create a pool with a large decimals gap, e.g. `pc_decimals = 9`, `coin_decimals = 0` (`sys_decimal_value = 1`).
2. Perform a sequence of ordinary `SwapBaseIn`/`SwapBaseOut` calls that (a) accumulate a non-zero `target_orders.calc_pnl_x`/`calc_pnl_y` via prior successful `Deposit`/`Withdraw` calls invoking `calc_take_pnl`, and then (b) drain `amm_pc_vault` down so that `total_pc_without_take_pnl` (raw) is greater than zero but less than `10^9` (so `Calculator::normalize_decimal_v2` truncates `x1` to `0`), while `pool_pc_amount * pool_coin_amount >= calc_pc_amount * calc_coin_amount` still holds using the native-unit values.
3. Call `Deposit`, `Withdraw`, or `WithdrawPnl`. `calc_take_pnl` enters the branch at `program/src/processor.rs:190`, computes `x2`, and panics at `y2 = x2.checked_mul(y1).unwrap().checked_div(x1).unwrap()` (division by zero) or at the subsequent `checked_sub(x2).unwrap()` if `x2 > x1`.
4. Because the on-chain state causing this condition persists, every subsequent `Deposit`/`Withdraw`/`WithdrawPnl` call against this pool will panic identically, permanently freezing LP withdrawals and PnL withdrawal for the pool.
