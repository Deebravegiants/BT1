## Title
`SignerCapabilityOfferProofChallengeV2` omits `chain_id`, enabling cross-chain replay of signer-capability grants - (File: `aptos-move/framework/aptos-framework/sources/account/account.move`)

### Summary
`account::offer_signer_capability` authorizes handing full `signer` control of an account to `recipient_address` based on a detached signature over a `SignerCapabilityOfferProofChallengeV2` struct [1](#0-0) . Unlike the sibling struct `RotationCapabilityOfferProofChallengeV2`, which was explicitly upgraded to add a `chain_id` field "to prevent replaying the challenge message" [2](#0-1) , `SignerCapabilityOfferProofChallengeV2` still lacks `chain_id`: [3](#0-2) . This is the same class of bug as the external report: a signed authorization message that grants control over an asset/account is not domain-separated by chain, so a signature valid on one chain can be replayed on another.

### Finding Description
The `offer_signer_capability` entry function builds the challenge purely from `sequence_number`, `source_address`, and `recipient_address`, with no `chain_id`: [4](#0-3) 

That struct is then verified via `verify_signed_message`, which only checks that the signature matches the account's current public key/auth key — it never checks anything chain-specific: [5](#0-4) 

Contrast this with the rotation-capability equivalent, which now explicitly includes `chain_id` in the signed challenge specifically to stop replay: [6](#0-5) 

Because the `signer_capability_sig_bytes` are submitted as plaintext entry-function arguments, once an `offer_signer_capability` transaction lands on any chain it is fully public. If the same account address/public key exists with the same `sequence_number` on another chain that also runs this framework module (e.g., a testnet and mainnet sharing genesis/derivation, a devnet reset, a hard fork, or a permissioned/L2-style chain built from this framework), the exact same `(signature, account_scheme, account_public_key_bytes, recipient_address)` tuple can be resubmitted there. `verify_signed_message` will accept it because nothing in the signed payload binds it to a specific chain, silently granting `signer` capability over the victim account to `recipient_address` on the second chain — full custody takeover (the recipient can call `create_authorized_signer`/`create_signer_with_capability` and take any action as that account, including moving all APT/fungible assets it holds) [7](#0-6) .

The root cause is unprivileged: no additional authority is required to replay an already-public signature; the framework itself fails to bind the challenge to the chain, which is the exact same missing-domain-separator invariant break as the `EntryPoint` report.

### Impact Explanation
`signer_capability_offer` grants the ability to fully impersonate the offering account (via `create_authorized_signer`/`create_signer_with_capability`), which can move APT, fungible assets, and any object/resources owned by that account. A cross-chain replay lets an attacker (or an unintended party controlling `recipient_address` on the replay chain) seize this capability without the victim's consent on that chain, which is a custody-grade full account takeover.

### Likelihood Explanation
This requires that the same account (same public key / auth key, same sequence number) exist on more than one chain instance running this framework code — a realistic and common scenario for Aptos-framework-based devnets/testnets/L2s/permissioned chains sharing genesis, chain resets, or hard forks. Since `offer_signer_capability` transactions and their embedded signature bytes are always public on-chain, the attacker needs no special privilege — only to notice the mismatch (missing `chain_id`) and copy a legitimate transaction's arguments onto the other chain in the matching sequence-number window.

### Recommendation
Add a `chain_id: u8` field to `SignerCapabilityOfferProofChallengeV2` (set via `chain_id::get()`), mirroring the fix already applied to `RotationCapabilityOfferProofChallengeV2`, and update `offer_signer_capability` to populate it. This is a breaking change to the struct's BCS layout, so it should be versioned (e.g., a `V3` struct) with a feature flag / migration path consistent with how other proof-challenge upgrades were rolled out in this module.

### Proof of Concept
1. On Chain A, Alice signs `SignerCapabilityOfferProofChallengeV2 { sequence_number: N, source_address: alice_addr, recipient_address: bob_addr }` and submits `offer_signer_capability(alice, sig, scheme, alice_pk, bob_addr)`. This succeeds and is now public in Chain A's transaction history, per the existing test flow at [8](#0-7) .
2. Assume Chain B runs the same framework and Alice's account exists there with an identical address/public key and sequence number `N` (e.g., a shared-genesis testnet/fork/permissioned deployment).
3. An observer extracts `(sig, scheme, alice_pk, bob_addr)` from Chain A's public transaction and submits the identical `offer_signer_capability` call on Chain B.
4. `verify_signed_message` on Chain B recomputes the same `SignerCapabilityOfferProofChallengeV2` (since it has no `chain_id` field, the byte-serialization is identical to Chain A's) and the signature verifies successfully — Bob (or whoever controls `bob_addr` on Chain B) now holds Alice's signer capability on Chain B without Alice ever authorizing it there.

Note: I could not fully verify whether any additional chain-binding exists elsewhere in the surrounding entry-function/prologue path (e.g., some outer wrapper enforcing chain-specific submission) beyond what `verify_signed_message` and the struct definition show; this assessment is based on the code paths retrieved above only.

        account_scheme: u8,
        account_public_key_bytes: vector<u8>,
        recipient_address: address
    ) acquires Account {
        let source_address = signer::address_of(account);
        ensure_resource_exists(source_address);
        assert!(exists_at(recipient_address), error::not_found(EACCOUNT_DOES_NOT_EXIST));

        // Proof that this account intends to delegate its signer capability to another account.
        let proof_challenge = SignerCapabilityOfferProofChallengeV2 {
            sequence_number: get_sequence_number(source_address),
            source_address,
            recipient_address,
        };
        verify_signed_message(
            source_address, account_scheme, account_public_key_bytes, signer_capability_sig_bytes, proof_challenge);

        // Update the existing signer capability offer or put in a new signer capability offer for the recipient.
        let account_resource = &mut Account[source_address];
        account_resource.signer_capability_offer.for.swap_or_fill(recipient_address);
    }

    public fun verify_signed_message<T: drop>(
        account: address,
        account_scheme: u8,
        account_public_key: vector<u8>,
        signed_message_bytes: vector<u8>,
        message: T,
    ) acquires Account {
        let auth_key = get_authentication_key(account);
        // Verify that the `SignerCapabilityOfferProofChallengeV2` has the right information and is signed by the account owner's key
        if (account_scheme == ED25519_SCHEME) {
            let pubkey = ed25519::new_unvalidated_public_key_from_bytes(account_public_key);
            let expected_auth_key = ed25519::unvalidated_public_key_to_authentication_key(&pubkey);
            assert!(
                auth_key == expected_auth_key,
                error::invalid_argument(EWRONG_CURRENT_PUBLIC_KEY),
            );

            let signer_capability_sig = ed25519::new_signature_from_bytes(signed_message_bytes);
            assert!(
                ed25519::signature_verify_strict_t(&signer_capability_sig, &pubkey, message),
                error::invalid_argument(EINVALID_PROOF_OF_KNOWLEDGE),
            );
        } else if (account_scheme == MULTI_ED25519_SCHEME) {
            let pubkey = multi_ed25519::new_unvalidated_public_key_from_bytes(account_public_key);
            let expected_auth_key = multi_ed25519::unvalidated_public_key_to_authentication_key(&pubkey);
            assert!(
                auth_key == expected_auth_key,
                error::invalid_argument(EWRONG_CURRENT_PUBLIC_KEY),
            );

            let signer_capability_sig = multi_ed25519::new_signature_from_bytes(signed_message_bytes);
            assert!(
                multi_ed25519::signature_verify_strict_t(&signer_capability_sig, &pubkey, message),
                error::invalid_argument(EINVALID_PROOF_OF_KNOWLEDGE),
            );
        } else {
            abort error::invalid_argument(EINVALID_SCHEME)
        };
    }
