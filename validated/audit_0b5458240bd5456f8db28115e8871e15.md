### Title
LT tokens donated directly to a curve `Pair` before graduation are permanently unrecoverable - ([File: packages/contracts/src/Pair.sol])

### Summary
alt.fun's curve `Pair` contract has no `skim`/rescue function, and unlike the two other places in the protocol that receive stray inbound transfers (`FeeVault.sweepDonations()` for USDC, and the post-graduation HyperSwap V2 pair's native `skim()` which `Bonding._seedUniswapV2Direct` explicitly invokes), a user who mistakenly `transfer`s the paired LT token directly to a curve `Pair` (instead of trading through `Zap`/`Bonding`) has those tokens permanently stuck with no on-chain path to recover them.

### Finding Description
`Pair.sol` only exposes `mint`, `swap`, `transferAsset`, `transferToken`, `getReserves`, `k`, `tokenBalance`, and `assetBalance` — all mutating functions are `onlyRouter` [1](#0-0) . There is no `skim` function analogous to Uniswap's.

The protocol's own documentation confirms LT donations directly to the curve pair are deliberately excluded from both the graduation threshold and the LP seed, and remain in the pair: `ltFromPair = assetReserve - virtualLtReserve` only drains the "real" LT raised by the curve, so a direct-transfer donation is never included in that amount [2](#0-1) .

`Router.graduate` only transfers the exact `amount` computed by `Bonding`, never the full `assetBalance()`, so any donated LT is explicitly "left behind" [3](#0-2) . The `Router.graduate` natspec itself acknowledges this is a "trust-assumption claim, not an on-chain guarantee," relying on `BONDING_ROLE` never being granted elsewhere and `Bonding` never calling `graduate` again once lifecycle has passed `Curve` [4](#0-3) . Once the token's lifecycle flips to `Graduating`/`Graduated`, `_prepareGraduationLiquidity`/`graduate` become unreachable for that pair, so any LT sitting in the pair beyond `ltFromPair` at that point is permanently orphaned — there is no `skim`, no rescue function, and no owner-only sweep anywhere in `Pair.sol` or `Router.sol` for this residue.

This is in contrast to the two other donation surfaces in the protocol that were explicitly hardened:
- `FeeVault.sweepDonations()` sweeps stray USDC to `feeTo` [5](#0-4) .
- The post-graduation HyperSwap V2 pair has native `skim()`, and `Bonding._seedUniswapV2Direct` calls it to reclaim donations into `Bonding` before seeding [6](#0-5) .

The curve `Pair` (pre-graduation) has no equivalent. Token-side donations (the launched token) are at least burned at graduation via `unsoldBurned` [7](#0-6) , but LT-side donations are neither burned nor returned to anyone — they are simply abandoned in the pair forever.

### Impact Explanation
Any unrelated wallet or trader who mistakenly sends the paired LT ERC-20 token directly to a curve `Pair` address (a plausible user error, since `Pair` holds the LT reserve and is a real, funded contract) permanently loses those funds. There is no recovery mechanism for the trader, the token creator, or the protocol — the LT is neither refunded, burned, nor swept to any party; it is simply inert dead weight in a contract that becomes unreachable once the token graduates.

### Likelihood Explanation
This requires only a plain `IERC20.transfer` from any address to a public, known `Pair` address (obtainable from `Bonding.tokenInfo(token).pair` or on-chain events) — the same trivial user-error vector called out in the original report. No privileged role, timing, or governance interaction is needed. Likelihood of at least occasional occurrence is realistic given users routinely mis-target contract addresses for token transfers, especially since `Pair` is a real contract holding real LT balance (unlike a purely internal accounting structure).

### Recommendation
Add a permissionless `skim`-style rescue function to `Pair.sol` (or a `Router`-mediated equivalent gated to `BONDING_ROLE`) that transfers any LT balance in excess of the stored `assetReserve` to a safe recipient (e.g., back to a caller-specified address before graduation, or swept to the protocol owner at/after graduation, mirroring `FeeVault.sweepDonations()` and the HyperSwap pair's `skim()`). Ensure this sweep is callable both pre- and post-graduation (the current design only reaches donated LT via `Router.graduate`, which becomes permanently unreachable after lifecycle transitions), so donated LT is not orphaned once the token leaves `Lifecycle.Curve`.

### Proof of Concept
1. `Bonding.launch(...)` creates a token and its `Pair` (curve) holding a virtual LT reserve.
2. A user, intending to interact with the token, mistakenly calls `IBounceLeveragedToken(lt).transfer(pairAddress, amount)` directly to the `Pair` address instead of going through `Zap.buy`.
3. The pair's real LT `assetBalance()` now exceeds the stored `assetReserve`, but `canGraduate`'s USD trigger and `_prepareGraduationLiquidity`'s `ltFromPair` computation both key off the stored reserve, not `assetBalance()` [8](#0-7) , so the donation is excluded from both trigger and LP seed.
4. When the token eventually graduates, `Router.graduate` drains only `ltFromPair` (excluding the donation) [9](#0-8) ; the donated LT remains in the (now-abandoned) curve `Pair`.
5. No function in `Pair.sol`, `Router.sol`, or `Bonding.sol` can move that residual LT out — it is permanently lost. This can be directly observed in the existing test `test_balances_divergeFromReserves`, which demonstrates the balance/reserve divergence pattern that underlies this issue [10](#0-9) .

    ///         Called by `Bonding._prepareGraduationLiquidity` during graduation
    ///         with `amount = stored assetReserve - virtualLtReserve` (i.e. the
    ///         real LT raised by the curve, excluding the virtual seed).
    /// @dev    Donation-resistant: passing an explicit `amount` instead of
    ///         draining `assetBalance()` ensures any LT that was donated
    ///         directly to the pair via `IERC20.transfer` is left behind and
    ///         excluded from LP seeding.
    ///
    ///         "Locked" here is a trust-assumption claim, not an on-chain
    ///         guarantee. `Pair.transferAsset` is gated by `onlyRouter`, and
    ///         `Router` only exposes it via this function and `sell`. Both
    ///         require `BONDING_ROLE`, which only `Bonding` holds. `Bonding`
    ///         in turn only calls `graduate` from
    ///         `_prepareGraduationLiquidity` — which is unreachable once the
    ///         token's lifecycle has flipped past `Curve`. So the leftover
    ///         is unreachable as long as (a) `BONDING_ROLE` is not granted
    ///         to any other address, and (b) future `Bonding` upgrades
    ///         preserve the lifecycle gate.
    function graduate(
        address token,
        uint256 amount
    ) external onlyRole(BONDING_ROLE) {
        address asset = assetTokenFor(token);
        address pairAddr = factory.getPair(token, asset);
        if (pairAddr == address(0)) revert PairNotFound();
        IPair(pairAddr).transferAsset(msg.sender, amount);
    }
