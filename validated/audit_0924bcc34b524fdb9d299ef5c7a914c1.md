### Title
Permissionless `pool.recapitalize` refunds tokens that were never paid, draining pool custody while the cash book still reports solvency - (File: contracts/pool/src/ops/recapitalize.rs)

### Summary
Like CVE-2026-20067 — incomplete error checking on an untrusted input field — the pool's `recapitalize` op never verifies that the declared `amount` was actually received before computing and paying out a "refund". The refund is `amount - applied`, where `applied = min(amount, backing_shortfall)`. On a solvent market the shortfall is zero, so `applied = 0` and `refund = amount`: the pool transfers `amount` of real custody to any unprivileged caller who never sent anything in. The cash book (`cache.cash`) is untouched by the refund, so the market continues to report itself solvent and admits exits that then fail inside the SAC transfer.

### Finding Description
`recapitalize::apply` in `contracts/pool/src/ops/recapitalize.rs:26-38` calls `accounting` and then unconditionally executes `outcome.cache.transfer_out(&payer, outcome.refund)`. `accounting` (lines 44-67) computes `applied = amount.min(guards::backing_shortfall(&cache))` and `refund = amount - applied`, crediting only `applied` to cash. The doc comment says "The controller transfers `amount` into the pool before this call", but nothing in the pool enforces that: there is no `require_auth`, no balance-delta measurement, and no check that inbound custody covers the refund. `Cache::transfer_out` (`contracts/pool/src/cache/cash.rs:46-53`) blindly transfers `params.asset_id` tokens from the pool address to `payer`.

The controller path `markets::recapitalize` (`contracts/controller/src/markets.rs:142-164`) does prefund via `transfer_amount_measured` and passes only the measured `received` to the pool — so through the controller the refund is the payer's own excess. But the pool entrypoint itself is callable directly: the protocol's own test `test_unfunded_recapitalize_leaves_the_cash_book_overstating_custody` (`contracts/pool/tests/flows.rs:3408-3483`) invokes `client().recapitalize(&hub(&t.asset), &payer, &custody)` with no payment, observes the pool's entire token balance leave (`token.balance(&t.pool) == 0`), the payer credited with `declared`, and `cash` still claiming the funds are present. A companion test confirms the payout is bounded by live custody, not the declared amount (`flows.rs:3489-3512`), so the theft is capped at — and equal to — the pool's full balance of that asset.

### Impact Explanation
- Theft of user funds: an attacker calls `pool.recapitalize(hub_asset, payer=attacker, amount=pool_balance)` on any solvent market (shortfall = 0 ⇒ refund = amount) and receives the pool's entire token custody without paying anything.
- Temporary freezing of funds / contract unable to operate from lack of token funds: because `debit_cash`/`require_reserves` (`cache/cash.rs:15-21`) read the inflated `cash` book rather than the real balance, subsequent `withdraw` calls pass the pool's own liquidity guard and revert inside the SAC `transfer` with `BalanceError = 10`. Suppliers cannot exit until the market is recapitalized, and `require_backed_market`/`backing_shortfall` (`guards.rs:52-66`) never sees the shortfall because the book was never debited — the pool reports solvency it does not have.

### Likelihood Explanation
Any unprivileged address can call the pool's `recapitalize` entrypoint with a self-controlled `payer` and an `amount` up to the pool's live token balance. No collateral, position, oracle price, or privileged role is needed; the attack is a single call per market and can be repeated across every (hub, token) book sharing the physical pool balance.

### Recommendation
The pool must not trust the caller's declared `amount`. Either (a) measure the actual inbound receipt inside `recapitalize` (balance-delta on `params.asset_id` around the call) and compute `applied`/`refund` from the measured value, or (b) require authorization from the stored controller address so only the controller's prefunded path can invoke it, or (c) debit `cash` for the refund so an unfunded refund cannot leave the book overstating custody.
