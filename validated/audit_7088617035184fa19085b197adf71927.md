### Title
Webhook `shop` (and `topic`/`webhook_id`) header is trusted without HMAC coverage, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats `Request#shop` as an authenticated field once `HmacValidator.validate` succeeds, but the HMAC signature computed by `HmacValidator` only covers the raw request body — never the `shop-domain` (or `topic`/`webhook-id`) HTTP header. This breaks the identity binding: `hmac_valid == true` should imply `shop == authenticated_shop`, but it only implies `body == authenticated_body`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

`HmacValidator.validate_signature` computes/compares the HMAC exclusively against that signable string: [2](#0-1) 

Meanwhile `Request#shop`, `#topic`, and `#webhook_id` are read directly and unverified from HTTP headers: [3](#0-2) 

`Registry.process` validates the HMAC and then dispatches the handler using `request.shop` as the tenant identity, with no additional check that the shop header corresponds to the shop that actually produced/authorized the signed body: [4](#0-3) 

The gem's own documentation instructs consuming apps to treat this exact combination as verified and to key business logic off `data.shop`: [5](#0-4) [6](#0-5) 

Since the HMAC secret (`Context.api_secret_key`) is the app's single client secret shared across every shop that installs the app, any merchant who installs the app — an ordinary unprivileged action requiring no special credential — receives genuinely-signed webhook bodies for their own shop. They can then replay that exact `(raw_body, hmac)` pair to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop. `HmacValidator.validate` still succeeds (it never looked at the header), and `Registry.process` calls the handler with `shop: <victim-domain>`, causing the host application to attribute attacker-controlled data to the victim's tenant.

### Impact Explanation
This crosses a tenant boundary: an app that stores/acts on webhook data keyed by `data.shop` (exactly as this gem's documentation recommends) can be made to ingest attacker-chosen webhook bodies (fake orders, `app/uninstalled`, `customers/data_request`, `shop/redact`, `products/update`, etc.) under an arbitrary victim shop identity. This is a cross-tenant access primitive achieved with no credentials beyond a normal, unprivileged app install — matching the Critical "cross-tenant access" category.

### Likelihood Explanation
High. No secret material, TLS interception, or privileged account is required — only installing the target app on any shop (which any merchant can do) and replaying a captured HTTP request with one header changed. The public webhook endpoint is, by design, internet-reachable.

### Recommendation
Bind the `shop`, `topic`, and `webhook_id` headers into the HMAC-verified content (or otherwise cryptographically bind them), e.g. by including them in `to_signable_string`, or by requiring the host application to look up the destination shop from its own webhook subscription record (keyed by `webhook_id`) rather than trusting the unauthenticated header. At minimum, the documentation and `WebhookMetadata` should stop presenting `shop` as verified when only the body is HMAC-covered.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` via normal OAuth (no special privilege needed).
2. App registers `orders/create` webhook; Shopify sends a legitimately HMAC-signed webhook to the app's public endpoint for the attacker's own store:
   - Body: `{"id": 1, "note": "hello"}`
   - Header: `x-shopify-hmac-sha256: <valid HMAC over body using app's shared client_secret>`
   - Header: `x-shopify-shop-domain: attacker.myshopify.com`
3. Attacker captures body + HMAC header, then re-sends to the same endpoint with:
   - Same body, same `x-shopify-hmac-sha256`
   - `x-shopify-shop-domain: victim.myshopify.com`
4. `Utils::HmacValidator.validate` returns `true` (verifies only the unchanged body).
5. `Registry.process` invokes the app's handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: {...}, ...)`, causing the host app to process/store attacker-controlled data as belonging to `victim.myshopify.com`.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
