### Title
Origin-scoped trust/auto-approve state in `ConnectedOrigins` is mutated using a caller-supplied `origin` value with no binding to the actual request origin - (File: `features/connected-origins/module/connections.js`)

### Summary
The reported MechMarketplace bug is a missing-authorization-binding issue: the `create` endpoint let any caller supply an arbitrary `serviceId` and mutate state keyed by that ID, with no check that the caller actually owned/controlled that ID. The `@exodus/connected-origins` feature exhibits the same root-cause shape: its privileged, trust-granting methods take a caller-supplied `origin` string and use it directly as the key to read/write per-origin trust and auto-approval state, without any mechanism (visible in this module or its API layer) that binds the `origin` argument to the identity of the actual caller of the RPC/API call.

### Finding Description
`ConnectedOrigins` (`features/connected-origins/module/connections.js`) exposes methods such as `add`, `untrust`, `isTrusted`, `isAutoApprove`, `setAutoApprove`, `setFavorite`, `connect`, `disconnect`, and `updateConnection`, all of which accept `{ origin, ... }` as plain data and operate on the origin record matching that string: [1](#0-0) [2](#0-1) [3](#0-2) 

These are surfaced verbatim (no wrapping/authorization check) through the public API layer: [4](#0-3) 

Nowhere in this module, its API definition, or its RPC exposure is the `origin` parameter cross-checked against the real origin of the message sender (e.g., `sender.tab.url`/`sender.origin` from the browser-extension messaging layer). The RPC/messaging plumbing (`libraries/browser-extension-rpc`, `libraries/browser-extension-channels`) does track `sender` metadata for messages, but that sender identity is not shown to be consulted by `ConnectedOrigins` methods before trusting the caller-supplied `origin` value: [5](#0-4) [6](#0-5) 

This mirrors the MechMarketplace flaw exactly: a privileged state-mutating operation is keyed by an identifier (`serviceId` → `origin`) that the caller fully controls and supplies as plain input, instead of the system deriving/verifying that identifier from the caller's actual, unforgeable identity.

### Impact Explanation
If this API surface is reachable from a less-trusted context than the wallet's own background/UI process (e.g., any code path that lets a connected dApp or content script invoke `connectedOrigins.*` with an attacker-chosen `origin`), a malicious site could:
- Call `setAutoApprove({ origin: '<other-already-trusted-site>', value: true })` to silently enable auto-approval of signing/transaction requests for a different, already-trusted origin, bypassing the user-confirmation flow for that other site.
- Call `add({ origin: '<other-site>', trusted: true, ... })` to forge trust/connection metadata for an origin it does not control, or `untrust`/`disconnect` to revoke another origin's legitimate connection (DoS of that dApp's wallet connection).
- Manipulate `connect`/`disconnect` to inject fake `activeConnections` entries for arbitrary origins, corrupting the connection state the wallet uses to decide what to auto-approve or display.

This is analogous in class to the mech marketplace bug: an unprivileged party manipulating security-relevant state keyed by an identity they don't own, leading to DoS and privilege bleed across origin boundaries, with `setAutoApprove` in particular touching a wallet-signing-adjacent trust boundary.

### Likelihood Explanation
This requires the `connectedOriginsApi` methods to actually be invocable by a less-privileged caller (i.e., that the origin binding is expected to be enforced by a layer above `ConnectedOrigins` that I could not locate in the indexed code — such as the RPC exposure layer used for the injected provider/content-script bridge). I could not confirm from the available index whether `connectedOriginsApi` is exposed only to the trusted extension UI/background (in which case this is not exploitable by a dApp) or also reachable through the content-script/page-injected RPC path shown in `libraries/browser-extension-rpc/content.js`. This uncertainty should be resolved before treating this as confirmed-exploitable; due to index size limits, some file contents (e.g., the exact wiring of which processes/contexts get access to `connectedOriginsApi`, and whether an origin-binding check exists elsewhere, such as in a consuming app's background script) may not be available in this index, and a full Devin session with complete file access would be needed to verify definitively.

### Recommendation
Ensure that any privileged `ConnectedOrigins` method that grants/revokes trust or auto-approve status (`add`, `setAutoApprove`, `setFavorite`, `connect`, `disconnect`, `untrust`, `updateConnection`) derives the `origin` it acts upon from the verified sender context of the RPC/message (e.g., `sender.tab.url`/`sender.origin` from the browser extension messaging layer), rather than trusting a caller-supplied `origin` field. If a caller-supplied `origin` is required for compatibility, validate it against the actual sender identity before performing any mutation, and reject mismatches the same way the reference fix requires `create` to be gated by the service's registered multisig.

### Proof of Concept
Conceptual analog (structure mirrors the reported test): any code path capable of invoking the `connectedOrigins` API (e.g., a malicious dApp reachable via the content-script/page RPC bridge, if that bridge indeed exposes this API) could call:
```js
await exodus.connectedOrigins.setAutoApprove({ origin: 'victim-dapp.com', value: true })
```
using its own connection, but supplying `origin: 'victim-dapp.com'` instead of its own origin. Per `setAutoApprove`'s implementation, this directly flips the auto-approve flag for `victim-dapp.com`'s stored record with no check that the caller is `victim-dapp.com`: [7](#0-6) 
I was not able to confirm in the index whether the concrete RPC exposure used in production actually allows an untrusted dApp to reach this method with an arbitrary `origin`; this would need to be verified directly against the exposure wiring (background script method registration) in a full checkout.

  connect = async ({ id, origin }) => {
    const value = await this.#getOrigin({ origin })

    if (!value) return

    const activeConnections = value.activeConnections || []
    const newConnection = { id, createdAt: Date.now() }
    const newConnections = uniqBy([...activeConnections, newConnection], 'id')

    await this.#setAttributes({ origin, attributes: { activeConnections: newConnections } })

export const createBackgroundRpc = ({
  name = DEFAULT_PORT_NAME,
  methods,
  serialize,
  deserialize,
  onData,
  onConnect,
  onDisconnect,
}) => {
  const rpcManager = new RPCManager()

  const handlePortConnect = (port) => {
    const id = port.sender.tab?.id || port.sender.documentId

    if (port.name !== name) return

    const rpc = createRpc({ port, methods, serialize, deserialize, onData })

    port.onDisconnect.addListener(() => {
      rpc.end()
      onDisconnect?.()
    })

    rpcManager.add(id, rpc)

    onConnect?.()
  }

  chrome.runtime.onConnect.addListener(handlePortConnect)

  return rpcManager
}
