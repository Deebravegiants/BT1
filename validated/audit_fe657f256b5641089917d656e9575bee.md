### Title
Same-address self-terminate + redeploy within one call stack allows storage-deposit charges to be silently discarded - (File: substrate/frame/revive/src/metering/storage.rs)

### Summary
`execute_postponed_deposits` coalesces per-contract `Charge` records keyed only by the contract's account address, not by contract lifetime. If a contract terminates and a new contract instance is redeployed at the same (deterministic, CREATE2-style) address within the same call stack, the stable sort followed by adjacent-merge logic treats the new instance's `Alive` charge as belonging to the same "terminated" entity, discarding it via the `(Terminated, Alive)` branch instead of applying it.

### Finding Description
`Charge` entries only carry a `contract: T::AccountId` field and a `ContractState` (`Alive{amount}` or `Terminated`) [1](#0-0) . There is no identifier distinguishing separate deployment "generations" at the same address.

In `execute_postponed_deposits`, all charges accumulated over the whole call stack are sorted purely by `contract` address (a stable sort) and then merged sequentially [2](#0-1) . For a sequence of pushes matching the described exploit — `Alive(X)` (storage write by original contract), `Terminated` (from `terminate()`), `Alive(Y)` (storage write by the redeployed contract at the same address) — the stable sort preserves this relative order since all three entries share the same address. The merge loop then:
1. Pushes `Alive(X)`.
2. Merges `Terminated` into it via the `(Alive, Terminated)` branch: subtracts `X` from `self.total_deposit` and sets state to `Terminated`.
3. Merges the new contract's `Alive(Y)` into it via the `(Terminated, Alive)` branch [3](#0-2) : subtracts `Y` from `self.total_deposit` as well, and leaves the state as `Terminated`.

Because the final coalesced state for the address is `Terminated`, the subsequent refund/charge loops that call `E::charge` only match on `ContractState::Alive` [4](#0-3) , so no hold/reserve is ever placed against the origin for the new contract's storage deposit `Y`. In addition, `self.total_deposit` (the value returned to the caller and presumably reflected in the extrinsic's reported deposit/weight accounting) is reduced by `Y`, meaning the deposit obligation for the redeployed contract's genuine, live storage usage vanishes entirely rather than being charged.

The root cause is that the coalescing algorithm assumes at most one "generation" of a contract can exist at a given address within a call stack (the `debug_assert!(false, "We never emit two terminates for the same contract.")` on the `(Terminated, Terminated)` branch confirms this single-lifetime assumption [5](#0-4) ), but nothing in `RawMeter`/`Charge` actually prevents or accounts for address reuse via terminate-then-redeploy in one transaction, which is a supported and common pattern with deterministic (CREATE2-style) contract addresses.

### Impact Explanation
An attacker-controlled contract (no privileged origin required — reachable from any signed extrinsic that instantiates/calls contracts, e.g. `pallet_revive::Pallet::call`/`instantiate` extrinsics) can construct a call stack that: instantiates a contract at a deterministic address, writes storage (accruing a charge), self-terminates, redeploys a new contract instance at the identical address, and writes storage again. The final `execute_postponed_deposits` will discard the second, legitimate storage deposit charge (`Y`) instead of collecting it, letting the caller avoid paying for real, persisted storage usage of the redeployed contract. This corrupts the pallet's global deposit accounting (`total_deposit` under-reports and no hold is ever reserved against origin for `Y`), directly matching the scoped impact.

### Likelihood Explanation
The preconditions are fully attacker-controlled and require no privileged origin, no leaked keys, and no external-chain assumptions: an attacker only needs to write and deploy a contract (or use an existing factory pattern) that performs instantiate → storage write → terminate → re-instantiate at the same salt/code-hash address → storage write, all within a single transaction's call stack. This is a standard, permissionless capability of the `pallet-revive` contract execution model since addresses are deterministically derived from deployer + salt + code hash. The bug is deterministic and fully repeatable once the sequence of operations is triggered.

### Recommendation
Track charge/terminate lifetimes independently of the bare account address — e.g., tag each `Charge` with a generation/lifetime identifier (incremented on each `terminate`+redeploy at the same address, or simply do not coalesce an `Alive` charge that is pushed *after* a `Terminated` marker for the same address; instead treat it as a new, separate charge entry). At minimum, when merging `(Terminated, Alive)`, the code should distinguish whether the `Alive` charge originates from before or after the termination event and only discard charges that occurred prior to (or as part of) the terminated lifetime, never those belonging to a subsequently redeployed instance.

### Proof of Concept
Rust integration test in `substrate/frame/revive/src/metering/storage/tests.rs` (or an `exec.rs`-level integration test):
1. Build a `RawMeter<T, MockExt, Root>` (or drive through real `exec.rs` instantiate/call/terminate flow).
2. Simulate: `absorb()` a nested meter producing charge `X` for contract address `A`; call `terminate(A, refunded)`; `absorb()` another nested meter producing charge `Y` for the same address `A` (representing the redeployed contract's storage write).
3. Call `execute_postponed_deposits(origin, exec_config)`.
4. Assert that `E::charge` was invoked with `Deposit::Charge(Y)` against contract `A` (i.e., the redeployed contract's own deposit is actually charged), and that the returned total deposit is `X_refund_adjustment + Y`, not `0` or negative-of-`Y`.
5. Expected (buggy) result: no charge call is made for `Y`, and `total_deposit` is reduced by `Y`, demonstrating the redeployed contract's storage deposit is never collected — proving the bug.
