Confirmed: `ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw body [1](#0-0) , while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from HTTP headers and are never included in the HMAC-signed material [2](#0-1) . `Registry.process` validates only `Utils::HmacValidator.validate(request)` (which hashes `to_signable_string`, i.e. the body) and then dispatches the handler using the unauthenticated `request.shop`/`request.topic` values [3](#0-2) .

### Title
Webhook tenant identity (`shop-domain` header) is not covered by HMAC verification, enabling cross-tenant event spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body via `Utils::HmacValidator.validate(request)` [4](#0-3) . The `shop` (and `topic`/`webhook_id`) values that the handler subsequently trusts as the tenant identity come from `X-Shopify-Shop-Domain`/`shopify-shop-domain` headers [5](#0-4) , but `Request#to_signable_string` only returns `@raw_body` [1](#0-0) . The header carrying the tenant identity is therefore never part of the signed/verified material.

### Finding Description
The identity binding that should hold is: `hmac == HMAC(secret, shop ‖ body)`, so that the verified bytes match the tenant the handler acts on. Instead, the gem verifies `hmac == HMAC(secret, body)` and then separately reads an *unauthenticated* `shop` header to build `WebhookMetadata` passed to the app's handler [6](#0-5) . Because the app's `client_secret`/`api_secret_key` is shared across every shop that installs the app, any tenant that can obtain one legitimately-HMAC-signed webhook body (e.g., by triggering a webhook from their own store, which they fully control) can replay that exact body to the shared webhook endpoint while substituting the `shop-domain` header for a different, victim shop. `Utils::HmacValidator.validate` will still return true, because it only checks the body bytes against the shared secret [7](#0-6) ; the mismatched `shop` header is never checked against anything.

### Impact Explanation
This breaks the tenant boundary the HMAC is meant to enforce: an attacker-controlled shop can forge webhook events that the host application will process as if they originated from an arbitrary other shop of its choosing, since `request.shop` flows unchecked into `WebhookMetadata.shop` [8](#0-7) . Any host application that uses `WebhookMetadata#shop` to select which tenant's data/session to mutate (a normal and expected usage pattern) can be tricked into writing/deleting/updating another merchant's data — a cross-tenant access impact.

### Likelihood Explanation
Any user who can install the app on their own Shopify store already has a full-fidelity attack primitive: legitimately signed webhook bodies with contents partly under their control (e.g., product/order payload fields they set) and the same shared `client_secret`. No secret material belonging to the victim tenant is required — only knowledge of the victim's `.myshopify.com` domain, which is often guessable/public. This is reachable purely through this gem's `Webhooks::Request`/`Registry.process` code path with no host-application misuse required.

### Recommendation
Include the shop-domain (and ideally topic) in the material that is verified, or explicitly require callers to bind the header-derived `shop` against a known/expected value (e.g., the shop associated with the session/webhook subscription) before dispatching to the handler. At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must not be trusted as a tenant identifier without independent verification (e.g., cross-checking against the app's own webhook subscription records).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and registers/triggers a webhook (e.g., `orders/create`) so Shopify sends a legitimately HMAC-signed payload to the app's shared webhook endpoint.
2. Attacker captures the raw body and the valid `shopify-hmac-sha256` value from that request.
3. Attacker resends the identical body + HMAC to the same endpoint, but sets `shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` recomputes `HMAC(secret, body)`, matches, and returns `true` (the `shop-domain` header was never part of the signed string) [9](#0-8) [10](#0-9) .
5. `Registry.process` dispatches the handler with `WebhookMetadata.new(... shop: request.shop ...)` set to `victim-shop.myshopify.com`, causing the host app to process attacker-controlled event data under the victim tenant's identity [8](#0-7) .
