Missing reentrancy protection in Tron IntentGatewayV2 fill/cancel path mirrors the pre-fix Ola-Finance-class reentrancy - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The main EVM `IntentGatewayV2` (`evm/src/apps/IntentGatewayV2.sol`) was patched against a reentrancy class identical in shape to the Ola Finance/Voltage incident (external call to an attacker-controlled beneficiary before critical state — `_filled[commitment]` — was finalized). That fix added `ReentrancyGuardTransient` with `nonReentrant` on `placeOrder`, `fillOrder`, and `cancelOrder`, plus a checks-effects-interactions reorder in `_fillSameChain`/`_fillCrossChain`. The parallel Tron deployment target, `evm/tron/contracts/apps/IntentGatewayV2.sol`, does **not** carry these protections: `cancelOrder` in that file has no `nonReentrant` modifier, and a repo-wide search of `evm/tron/**` for `nonReentrant`/`ReentrancyGuard` returns zero matches.

### Finding Description
`evm/src/apps/IntentGatewayV2.sol` inherits `ReentrancyGuardTransient` and guards `placeOrder`, `fillOrder`, and `cancelOrder` with `nonReentrant`: [1](#0-0) [2](#0-1) [3](#0-2) 

This was a deliberate fix for a reentrancy bug class documented in-repo: a malicious beneficiary's `receive()` hook, triggered by an ETH payout inside `_fillSameChain`/`_fillCrossChain`, could previously re-enter `fillOrder` before `_filled[commitment]` was set and steal escrowed tx fees or a second input's escrow via a net-zero self-fill: [4](#0-3) [5](#0-4) 

That bug class — external call to attacker-controlled code before authoritative state is finalized, enabling double-spend of escrowed value — is the same root-cause pattern as Ola Finance's ERC677 reentrancy loss.

The Tron variant of the same contract, `evm/tron/contracts/apps/IntentGatewayV2.sol`, implements `cancelOrder` without any `nonReentrant` guard: [6](#0-5) 

and a grep across the entire `evm/tron/` tree found no occurrence of `nonReentrant` or `ReentrancyGuard` at all, indicating the Tron fork never received the CEI/reentrancy-guard remediation applied to `evm/src/apps/IntentGatewayV2.sol`.

**Uncertainty**: I was not able to retrieve the Tron contract's `_fillSameChain`/`fillOrder`/`_withdraw`-equivalent internals within the tool budget (a targeted grep for `_filled[commitment] = msg.sender` / `function _fillSameChain` / `function fillOrder` in `evm/tron/**` returned no matches, suggesting the Tron contract is structured differently — possibly monolithic rather than split into `IntrinsicIntents`/`ExtrinsicIntents` — so exact line-level confirmation of the vulnerable ordering in the fill functions was not obtained). This finding is based on the confirmed absence of the reentrancy-guard modifier and the absence of any `ReentrancyGuard` import/usage anywhere in that directory, contrasted with the patched main contract and its accompanying regression tests describing the exact exploit this class enables.

### Impact Explanation
If the Tron `IntentGatewayV2`'s fill path shares the same non-CEI ordering that the main contract had before its fix (external TRX/token transfer to the beneficiary occurring before `_filled`/escrow bookkeeping is finalized), a malicious beneficiary contract can re-enter during that payout to self-fill additional outputs at zero net cost and drain a second escrowed input or the escrowed transaction fee — concrete theft of user/solver funds, matching the severity class of the referenced Ola Finance loss (~$4.67M).

### Likelihood Explanation
Reachable from a single unprivileged `fillOrder` transaction by any solver/attacker who controls the beneficiary contract of an order (or colludes with the order placer to set a malicious beneficiary), exactly as demonstrated by the existing PoC test contract (`ReentrantBeneficiary`) against the main EVM contract before the fix. No governance, admin, or privileged role is required.

### Recommendation
Audit `evm/tron/contracts/apps/IntentGatewayV2.sol` (and any other non-`evm/src` deployment forks) against the CEI fix and `ReentrancyGuardTransient`/`nonReentrant` protections already present in `evm/src/apps/IntentGatewayV2.sol` and its `IntrinsicIntents`/`ExtrinsicIntents` bases. Ensure `_filled[commitment]` (or its Tron equivalent) is set before any external value transfer in the fill paths, and add `nonReentrant` to `placeOrder`, `fillOrder`, and `cancelOrder` in the Tron contract, then re-run the equivalent of `IntrinsicIntentsReentrancyTest.sol` against the Tron build.

### Proof of Concept
The existing `evm/tests/foundry/IntrinsicIntentsReentrancyTest.sol` demonstrates the exact exploit pattern (armed `ReentrantBeneficiary` re-enters `fillOrder` from its `receive()` during the ETH payout) against the pre-fix ordering: [7](#0-6) 
The same PoC construction (deploy a malicious beneficiary contract, arm it with a self-fill reentrant payload, call `fillOrder` with an ETH/TRX output) should be replayed against a deployed instance of `evm/tron/contracts/apps/IntentGatewayV2.sol` to confirm whether its fill path lacks the CEI ordering and reentrancy guard, given no `nonReentrant`/`ReentrancyGuard` was found anywhere in that contract tree.

    function cancelOrder(Order calldata order, CancelOptions calldata options) public payable {
        bytes32 commitment = keccak256(abi.encode(order));

        // order has already been filled
        if (_filled[commitment] != address(0)) revert Filled();

        address hostAddr = host();
        bytes32 currentChain = keccak256(IDispatcher(hostAddr).host());
        bytes32 orderSource = keccak256(order.source);
        bytes32 orderDest = keccak256(order.destination);
        bool isSameChain = orderSource == orderDest;

        if (isSameChain) {
            // Same-chain: validate locally and refund immediately
            // only owner can cancel
            if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

            // Verify we're on the correct chain
            if (orderSource != currentChain) revert WrongChain();

            WithdrawalRequest memory body =
                WithdrawalRequest({commitment: commitment, tokens: order.inputs, beneficiary: order.user});

            withdraw(body, true);
