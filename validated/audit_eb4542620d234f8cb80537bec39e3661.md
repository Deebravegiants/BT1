### Analysis

The claimed broken equality would be: `actualAmount` used for the min-withdrawal check in `PoaBridge.createWithdrawalIntents` differs from the `actualAmount` used elsewhere (in `_estimateWithdrawalFee`), allowing an under-minimum withdrawal to slip through unchecked into a signed intent.

Tracing `IntentsSDK.createWithdrawalIntents` (called from `signAndSendWithdrawalIntent`, which is called from `processWithdrawal`): [1](#0-0) 

`actualAmount` is computed the same way (`feeInclusive ? amount - fee.amount : amount`) as in `_estimateWithdrawalFee`, and **both call sites** invoke `bridge.validateWithdrawal({ amount: actualAmount, ... })` *before* calling `bridge.createWithdrawalIntents`: [2](#0-1) 

`PoaBridge.validateWithdrawal` checks `args.amount < minWithdrawalAmount` against exactly this `actualAmount`, throwing `MinWithdrawalAmountError` before any intent is built or signed: [3](#0-2) 

The `skipMinAmountValidation` bypass only applies inside `_estimateWithdrawalFee`'s own call, and only when `amount === 0n && feeInclusive === false` (the placeholder fee-quote-only case), not in the real `createWithdrawalIntents` path used for signing: [4](#0-3) 

So for the exact scenario in the question — `amount` above `min_withdrawal_amount` but `amount - fee` below it — `validateWithdrawal` in `createWithdrawalIntents` throws `MinWithdrawalAmountError` **before** `PoaBridge.createWithdrawalIntents` runs, and before `relayerFee` is added back or any intent is signed [5](#0-4) .

Regarding the "adds `relayerFee` back onto `amount`" mechanism: `PoaBridge.createWithdrawalIntents` computes `intent.amount = actualAmount + relayerFee` where `relayerFee = getUnderlyingFee(feeEstimation, PoaBridge, "relayerFee")` [6](#0-5) . For the PoA route, `relayerFee` and `feeEstimation.amount` are populated from the same estimate call (`estimateWithdrawalFee` sets both `amount: relayerFee` and `underlyingFees[PoaBridge].relayerFee = relayerFee` from the identical value) [7](#0-6) , so `intent.amount = (amount - fee.amount) + relayerFee = amount` when both match — recovering the original requested `amount` as the signed debit, with the destination receiving `actualAmount = amount - fee`. This matches the invariant the question expects, not a divergence.

A caller could pass a mismatched/attacker-supplied `feeEstimation` object directly to `signAndSendWithdrawalIntent`/`processWithdrawal` (bypassing the SDK's own `estimateWithdrawalFee`), but even then the `validateWithdrawal` check inside `createWithdrawalIntents` re-validates `actualAmount` against `min_withdrawal_amount` using that same `feeEstimation.amount`, so the specific under-minimum-after-fee case is still caught before signing.
