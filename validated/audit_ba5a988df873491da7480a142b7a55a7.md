### Title
Unsigned `handle_unsigned` extrinsic runs full ISMP proof verification in `validate_unsigned` — free, unauthenticated CPU-exhaustion vector - ([File: modules/pallets/ismp/src/lib.rs])

### Summary
`pallet-ismp`'s `handle_unsigned` extrinsic is dispatched with `ensure_none` (no signature, no fee) [1](#0-0) , and its `ValidateUnsigned::validate_unsigned` implementation performs the *entire* message-execution pipeline — consensus proof verification (BEEFY/GRANDPA/SP1/sync-committee), MMR/trie state-proof verification, etc. — via `Self::execute(messages.clone())` before the transaction is even admitted to the pool [2](#0-1) . This mirrors the CVE-2026-23930 pattern: an unauthenticated actor sends a specifically crafted request that forces the server to perform disproportionate CPU work relative to the (zero) cost of submission.

### Finding Description
`validate_unsigned` is called by every node's transaction pool on gossip/import — not only by the block author — and it is not weight-metered the way in-block dispatch is (block weight limits apply to execution, not pool validation). The implementation unconditionally runs `Self::execute(messages.clone())`, which re-derives state machines, checks consensus clients, and — critically — executes the full cryptographic verification for whatever `Message` variants are included: BEEFY/SP1 consensus proof verification (`SP1Beefy.verifyConsensus` / `EcdsaBeefy.verifyMmrUpdateProof`-equivalent Rust paths), MMR multiproof verification, or trie-based state/membership proofs (`modules/ismp/state-machines/*`). None of this is gated behind a signature or fee — it is `ensure_none`, so submission is free [3](#0-2) .

Because the `provides` tag is derived from a content hash of the messages (`keccak_256(&tags.encode())` or, for consensus messages, a hash of `(consensus_state_id, consensus_proof)`) [4](#0-3) , an attacker can trivially mutate one byte of a large but syntactically-valid (or plausible) proof payload to produce a new, unique tag on every submission. Each such submission is re-validated (i.e., re-executes the full crypto verification) independently by every node that receives it over the network, before ultimately failing (`InvalidTransaction::BadProof`). There is no per-sender cost accounting, no incremental cost gate proportional to proof size beyond what `frame_system`'s generic extrinsic-length limits provide, and repeated resubmission with cosmetic mutations bypasses the pool's de-duplication (`provides`/`requires`).

This is structurally the same class of bug as the Zabbix CVE: a cheap, unauthenticated, syntactically valid-looking request triggers disproportionately expensive server-side computation (here: full consensus/Merkle/trie cryptographic verification) on every receiving node, with no economic disincentive.

### Impact Explanation
Every full/collator node in the Hyperbridge network executes `validate_unsigned` for every `handle_unsigned` extrinsic it receives via gossip, before block inclusion. An attacker can flood the network with unsigned extrinsics carrying maximally-sized/maximally-expensive (but ultimately invalid) proofs — e.g., large `PostRequestMessage`/`ResponseMessage` batches with big MMR multiproofs, or BEEFY/SP1/GRANDPA consensus messages with heavy signature-set verification — at zero cost, forcing disproportionate CPU consumption on every peer's mempool-validation path. This can degrade or halt block production/relaying network-wide (denial of service against the message-dispatch path itself), which the scope explicitly treats as in-scope ("a route unable to deliver messages").

### Likelihood Explanation
High. No privileged role, signature, or fee is required — `ensure_none` accepts anyone. The `provides` tag scheme allows straightforward bypass of pool-level de-duplication by content mutation, and the size of proofs eligible for submission is bounded only by generic block-length/extrinsic-size runtime parameters (which are deliberately set large, e.g. up to 8MB for chains with heavy GRANDPA proofs per the docs), not by any cost specific to `validate_unsigned`'s computational load.

### Recommendation
- Cheaply reject-fast in `validate_unsigned` before running `Self::execute`: perform structural/size sanity checks (e.g., cap number of requests/responses per batch, cap multiproof/authority-set sizes, cap message count) proportional to what is economically reasonable, and only run full cryptographic verification after those bounds pass.
- Consider moving expensive verification off the mempool-validation hot path, or rate-limiting/costing `validate_unsigned` per source peer (e.g., via `TransactionSource` differentiation, already available as a parameter but currently unused).
- Strengthen the transaction-pool de-duplication so that a byte-level mutation of an already-rejected/failed batch cannot trivially generate a new `provides` tag and force re-verification.

### Proof of Concept
1. Construct a `pallet_ismp::Call::handle_unsigned` with a `Message::Response`/`Message::Request` batch sized at or near the runtime's extrinsic-length limit, containing a large MMR multiproof and/or many `GetRequest`s each carrying many storage keys (as already exercised functionally, without a DoS angle, in the pallet's own test fixtures) [5](#0-4) .
2. Submit it as an unsigned extrinsic; `validate_unsigned` calls `Self::execute(messages.clone())`, running full trie/MMR verification (`verify_state_proof`, `MerkleMountainRange::VerifyProof` paths) before rejecting it as invalid.
3. Flip a single byte in the proof/body to produce a new content hash (`provides` tag), and resubmit repeatedly from many connections; each resubmission forces every receiving peer to redo the full, expensive verification for free.

			// `provides` tag from the messages themselves so that distinct submissions
			// never collide in the transaction pool.
			//
			// A consensus message that doesn't advance a state machine (e.g. a
			// validator-set rotation during sync) previously mapped to an empty request
			// list via the catch-all arm. Every such message therefore produced an
			// identical `provides` tag and a fixed priority of 100, so the pool rejected
			// any two of them with "Priority is too low (100 vs 100)". Hashing the
			// consensus message (excluding the signer, so equivalent submissions from
			// different relayers dedupe) gives each update a unique tag.
			let mut has_consensus = false;
			let mut tags = messages
				.into_iter()
				.map(|message| match message {
					Message::Consensus(ConsensusMessage {
						consensus_proof,
						consensus_state_id,
						..
					}) => {
						has_consensus = true;
						vec![H256(sp_io::hashing::keccak_256(
							&(consensus_state_id, consensus_proof).encode(),
						))]
					},
					Message::FraudProof(FraudProofMessage { proof_1, proof_2, .. }) => vec![
						H256(sp_io::hashing::keccak_256(&proof_1)),
						H256(sp_io::hashing::keccak_256(&proof_2)),
					],
					Message::Request(RequestMessage { requests, .. }) => requests
						.into_iter()
						.map(|post| hash_request::<Pallet<T>>(&Request::Post(post.clone())))
						.collect::<Vec<_>>(),
					Message::Response(message) => message
						.requests()
						.iter()
						.map(|request| hash_request::<Pallet<T>>(request))
						.collect::<Vec<_>>(),
					Message::Timeout(message) => message
						.requests()
						.iter()
						.map(|request| hash_request::<Pallet<T>>(request))
						.collect::<Vec<_>>(),
				})
				.collect::<Vec<_>>();
			tags.sort();

			if tags.is_empty() {
				return Err(TransactionValidityError::Invalid(InvalidTransaction::Call));
			}

			// this is so we can reject duplicate batches at the mempool level
			let msg_hash = sp_io::hashing::keccak_256(&tags.encode()).to_vec();
