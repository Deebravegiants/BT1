## Title
Webhook `shop-domain` header is trusted for tenant attribution but is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request body, then unconditionally trusts the separate `shop-domain` header as the tenant identity passed to the app's handler. Because the HMAC signable string never includes the shop, topic, or webhook-id headers, any party capable of producing one valid `(body, hmac)` pair for the app's shared `api_secret_key` can replay that pair while substituting an arbitrary `shop-domain` value, causing the app to process attacker-chosen webhook data under a victim shop's identity.

### Finding Description
The binding that should hold is:

`shop attributed to a webhook == shop that actually produced the signed body`

`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string`, and for webhooks that string is defined as just the raw body: [1](#0-0) 

The `shop` header is read completely independently and never enters the signable string: [2](#0-1) 

`Registry.process` validates the HMAC and, on success, forwards `request.shop` directly into the data given to the app's handler with no further check that this shop matches the body/HMAC or any known/registered shop: [3](#0-2) 

Because the `api_secret_key` is the same for every shop that installs the app (it is the app's own secret, not a per-shop secret), any merchant who has installed the app can legitimately obtain a valid `(raw_body, hmac)` pair by triggering an event in their own store (or by directly computing it, since the secret is invariant across shops for this key). Before/after the attacker's request sequence:

- Before: attacker has a genuine `(body_A, hmac_A)` webhook delivered for their own shop `A`.
- Attacker action: attacker (or any actor who can reach the webhook endpoint the host app exposes for this library) resends `body_A` with `hmac_A` unchanged, but with the `shop-domain` header set to victim shop `B`.
- After: `HmacValidator.validate` still succeeds (it only checked `body_A` against the shared secret), and `Registry.process` invokes the handler with `WebhookMetadata#shop == "B"` while the payload actually originated from shop `A`.

This breaks the identity binding between the cryptographically-verified bytes (body only) and the tenant identifier the host app's handler relies on (`shop`), which is exactly the "field acted on but not covered by the HMAC" class.

### Impact Explanation
Any webhook handler that uses `data.shop` to scope side effects (writing state, invalidating data, fulfilling orders, updating settings, looking up/storing sessions, etc.) can be tricked into acting on shop `B`'s tenant context using data forged/replayed by an unrelated shop `A`. This is a cross-tenant confusion primitive: the library provides no cryptographic guarantee that the `shop` value it hands to application code corresponds to the entity that produced the signed bytes, even though `Registry.process` presents the request as fully authenticated ("Invalid webhook HMAC" is the only check performed).

### Likelihood Explanation
Exploitation only requires the ability to (a) install the app on one's own shop (trivial for any Shopify merchant, since apps are typically installable by any store) to obtain one valid `(body, hmac)` pair, and (b) deliver an HTTP request with attacker-chosen headers to the webhook endpoint the host app exposes for this library, substituting the `shop-domain` header. No access to `api_secret_key`, tokens, or privileged accounts is required.

### Recommendation
Include the shop (and ideally topic/webhook-id) in the signable string used for webhook HMAC validation, or otherwise cryptographically/structurally bind the `shop-domain` header to the verified body (e.g., require the caller to independently confirm `shop` corresponds to a shop with an active session/installation before trusting it), so that the shop identity cannot be swapped independently of the signed payload.

### Proof of Concept
1. Install the app on shop `A`; capture a legitimate webhook delivery, yielding `raw_body` and its valid `x-shopify-hmac-sha256` value, both computed against the app's shared `api_secret_key` as in [4](#0-3) .
2. Send a new request to the host application's webhook endpoint using the same `raw_body`/`hmac` but with `x-shopify-shop-domain` (or `shopify-shop-domain`) set to victim shop `B`'s domain.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` per [5](#0-4) , which succeeds because only `raw_body` is hashed.
4. The registered handler is invoked with `WebhookMetadata#shop == "B"` even though the payload came from shop `A`, per [6](#0-5) .

        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end
