### Title
Unrestricted, shared `CallDispatcher` allows persistent ERC20 approvals that later drain funds legitimately routed through it by other orders/solvers - (File: evm/src/utils/CallDispatcher.sol)

### Summary
The Intent Gateway's `CallDispatcher` is a single, shared contract instance (`_params.dispatcher`) used by every order's `predispatch` and `output.call` execution across the entire protocol, for every user and solver. Its `dispatch()` function is `external` with **no access control whatsoever** — anyone can call it directly, and any order's attacker-controlled calldata is executed with the `CallDispatcher` itself as `msg.sender`. An unprivileged user can embed (or directly submit) an `IERC20.approve(attacker, type(uint256).max)` call through this shared contract. This creates a standing allowance that is never revoked. Because the sweep-back logic after execution only sweeps the specific tokens declared in *that* order's `inputs`/`output.assets` [1](#0-0) , any other token that later transiently lands in the same dispatcher — from a *different*, legitimate order's predispatch/postdispatch flow, or from a `HyperFungibleToken` cross-chain mint targeted at the dispatcher [2](#0-1)  — is silently exposed to the attacker's pre-planted approval.

This mirrors the HackerOne report's bug class: a low-privileged actor's inert-looking reference (here, an `approve()` routed through a shared object) causes no immediate harm, but silently converts into a disclosure/theft of value once an unrelated, higher-value party (a solver depositing real settlement funds, or another user's order) later interacts with that same shared object in the normal course of business.

### Finding Description
`CallDispatcher.dispatch()` executes an attacker-supplied `Call[]` with the dispatcher contract as caller, and has no restriction on who may invoke it or what it targets: [3](#0-2) 

This same `CallDispatcher` address is configured once in the gateway's `Params.dispatcher` and reused for every order's predispatch and postdispatch calldata execution, for every user, protocol-wide: [4](#0-3) [5](#0-4) 

Because it is unrestricted, an attacker can call `CallDispatcher.dispatch()` directly (no order needed) with `Call[] { to: TOKEN, data: approve(attacker, type(uint256).max) }`. This sets `TOKEN.allowance(dispatcher, attacker) = max` permanently — the dispatcher holds no owner and has no mechanism to revoke approvals it never intended to make.

The sweep/dust-collection logic that runs after legitimate calldata execution only accounts for the tokens explicitly declared by *that* order (`order.output.assets[i]` in `_execute`, `order.inputs[i]` in the predispatch flow): [6](#0-5) 

Any token that is not part of the currently-executing order's declared asset list — but which transiently passes through or is left on the dispatcher (e.g., an intermediate swap leg's output token, dust from a prior order, or tokens minted directly `to: CALL_DISPATCHER` by `HyperFungibleToken.send`) — is not covered by this sweep and can sit on the dispatcher's balance across separate transactions. Once such a balance exists, the attacker's previously-planted approval on that token lets them call `transferFrom(dispatcher, attacker, balance)` from an entirely separate transaction, without needing any order of their own and without the depositing party being aware their funds are at risk.

### Impact Explanation
An unprivileged actor can pre-position a permanent token allowance on a protocol-shared contract that later, unknowingly, holds real value deposited by solvers or other users as part of ordinary Intent Gateway settlement flows (predispatch swaps, postdispatch swaps, or `HyperFungibleToken` cross-chain calldata execution that mints directly to the dispatcher). This is a concrete theft-of-funds vector: value belonging to a party who never authorized or was aware of any relationship with the attacker can be drained the moment it becomes exposed on the shared dispatcher, exactly analogous to the original report where a low-privileged reference silently converts a private resource into a publicly exposed one once a higher-privileged party interacts with it.

### Likelihood Explanation
`CallDispatcher.dispatch()` requires no special role and no interaction with `IntentGatewayV2`/`ExtrinsicIntents` at all — the attacker can call it directly at any time to plant the approval, for any ERC20 token they anticipate will pass through the shared dispatcher (a small, enumerable set of tokens supported by the gateway/bridge). The attacker only needs to win a race against the dispatcher's own sweep logic for any token balance that is not part of the sweeping order's declared asset list, which is plausible whenever predispatch/postdispatch calldata performs multi-hop swaps, or whenever `HyperFungibleToken` mints funds directly to the dispatcher address ahead of executing arbitrary calls.

### Recommendation
- Restrict `CallDispatcher.dispatch()` to only be callable by the configured `IntentGatewayV2`/`ExtrinsicIntents` contract(s), not arbitrary external callers.
- Deploy a fresh, single-use `CallDispatcher` (or an ephemeral proxy/clone) per order execution instead of reusing one shared, long-lived instance across all users and orders, so no state (including approvals) can persist or leak between unrelated orders.
- After executing any calldata, explicitly revoke (`approve(_, 0)`) any approvals the dispatcher made to non-protocol addresses, or disallow `approve` calls to addresses outside an allow-list of known routers/protocols.
- Sweep the dispatcher's *entire* token balance for any token touched by the executed calldata (not just the tokens declared in the current order), to eliminate cross-order dust accumulation.

### Proof of Concept
1. Attacker calls `CallDispatcher.dispatch(abi.encode([Call{to: USDC, value: 0, data: approve(attacker, type(uint256).max)}]))` directly — no order placement required, since `dispatch()` has no access control (`evm/src/utils/CallDispatcher.sol:44`).
2. At any later time, a legitimate solver fills an unrelated order whose `output.call` routes USDC through the same shared `CallDispatcher` (e.g., an exact-output swap pattern as shown in `testPostdispatchTokenSweep`, `evm/tests/foundry/IntentGatewayV2Test.sol:1332-1440`), or a `HyperFungibleToken.send` mints USDC directly `to: CALL_DISPATCHER` for post-processing (`docs/content/developers/evm/hyper-fungible-token/hyper-fungible-token.mdx:149-162`).
3. If any USDC balance is left on the dispatcher outside the specific order's declared `output.assets`/`inputs` sweep set (e.g., due to an intermediate swap leg, rounding, or a token not tracked by that order), it is not swept back to the gateway.
4. The attacker calls `USDC.transferFrom(dispatcher, attacker, USDC.balanceOf(dispatcher))` using the standing approval from step 1, draining funds that belonged to the solver/user whose transaction unknowingly left them exposed on the shared dispatcher.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
