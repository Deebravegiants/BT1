Confirmed root cause. `Webhooks::Registry.process` at `lib/shopify_api/webhooks/registry.rb:189-200` validates the request solely via `Utils::HmacValidator.validate(request)`, which delegates to `Webhooks::Request#to_signable_string`, defined at `lib/shopify_api/webhooks/request.rb:35-38` as returning only `@raw_body`. The `shop`, `topic`, and `webhook_id` fields (from the `shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id` headers, `lib/shopify_api/webhooks/request.rb:15-33`) are read directly from HTTP headers and are **not included** in the HMAC-signed payload. `Registry#process` then passes `request.shop` straight into the `WebhookMetadata` handed to the app's handler (`lib/shopify_api/webhooks/registry.rb:198-199`) as the tenant identifier, with no cross-check that the signed body actually corresponds to that shop.

### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw body alone [1](#0-0)  while the `shop`, `topic`, and `webhook_id` values are taken unauthenticated from HTTP headers [2](#0-1) . `Webhooks::Registry.process` validates only this body-only HMAC before dispatching the request to the app's handler with the attacker-suppliable `shop` value [3](#0-2) .

### Finding Description
The binding this code should enforce is: `shop-bound-by-HMAC == shop-delivered-to-handler`. In reality:
- Before the request: Shopify signs a webhook body with the app's shared `api_secret_key` (the same secret is used for *all* shops/tenants of the app) and sends headers `shopify-hmac-sha256`, `shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`.
- `HmacValidator.validate` recomputes the HMAC over `request.to_signable_string`, which is just `@raw_body` [1](#0-0) , and compares it to the `hmac` header value with `OpenSSL.secure_compare` [4](#0-3) .
- After the request: because `shop`, `topic`, and `webhook_id` are pulled straight from headers with no cryptographic tie to the signed body [2](#0-1) , any party who can produce (or capture) one valid `(raw_body, hmac)` pair signed by the app's secret can pair that body with an arbitrary `shopify-shop-domain` / `shopify-topic` / `shopify-webhook-id` header set and still pass `HmacValidator.validate`.

Since `api_secret_key` is shared across all shops that install the app (it's not per-tenant), an unprivileged internet user who merely installs the app on their own store receives genuine, validly-signed webhooks for their own shop. They can replay that exact `(body, hmac)` pair to the app's webhook endpoint while substituting `shopify-shop-domain` (and/or `shopify-topic`) with a victim tenant's domain. `Registry.process` passes this attacker-controlled `shop` value directly into `WebhookMetadata` for the handler [5](#0-4) , so any host application that uses `data.shop` to select which tenant's records to update (a documented, expected usage pattern per the gem's test fixtures, e.g. `test/webhooks/registry_test.rb`) will attribute/act on data for the wrong tenant.

This is the direct analog of the H-02 report's root cause: a field ("delegatee"/receiver in the audit, "shop" here) is acted upon by privileged logic but is not covered by the authenticity check ("_delegate" call unauthenticated by the transfer amount vs. the HMAC leaving `shop` unauthenticated).

### Impact Explanation
This breaks the tenant-authentication binding for webhook delivery: an attacker with a legitimate (even free-tier) installation of the app can forge the tenant attribution of an otherwise validly-HMAC'd webhook, causing cross-tenant data confusion in the host application (data written/deleted under the wrong shop, or mandatory GDPR webhooks like `customers/redact`/`shop/redact` processed against a forged shop). This matches the Critical "cross-tenant access" impact category, since the vulnerability lives entirely in this gem's `Webhooks::Request`/`Webhooks::Registry` verification logic, not merely in host-app misuse of a documented API — the gem's own `VerifiableQuery`/`HmacValidator` abstraction advertises a signature check but silently excludes the very field (`shop`) used downstream for tenant identification.

### Likelihood Explanation
Likelihood is high for any app that installs on multiple shops (the normal case for a public app): every legitimate install grants the attacker a stream of validly-signed `(body, hmac)` pairs for topics they control (e.g. `orders/create` on their own test shop), which can then be replayed with a swapped `shop` header value at will. No access token, admin credentials, or `api_secret_key` knowledge is required — only the ability to trigger a webhook on one's own installed shop and forward the resulting raw request to the app's webhook endpoint with a modified header.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the HMAC-signable content, or otherwise cryptographically bind `shopify-shop-domain` to the signed body before trusting it in `Webhooks::Request#shop`. At minimum, `Webhooks::Registry.process` should cross-validate that the `shop` header corresponds to a shop with an active, known installation/session for the given webhook body, rather than trusting the header value produced independently of the HMAC computation in `lib/shopify_api/webhooks/request.rb`.

### Proof of Concept
1. Install the target app on attacker-owned shop `attacker.myshopify.com`. Configure/trigger a webhook subscription (e.g. `orders/create`) so Shopify delivers a request signed with the app's shared `api_secret_key`:
   - Headers: `shopify-hmac-sha256: <valid-hmac-of-body>`, `shopify-shop-domain: attacker.myshopify.com`, `shopify-topic: orders/create`, `shopify-webhook-id: <id>`
   - Body: `{"id": 1, ...}` (fully attacker-controlled content, since it's the attacker's own order data)
2. Capture the raw HTTP request, in particular the exact `raw_body` bytes and the `shopify-hmac-sha256` value.
3. Replay the request to the same webhook endpoint, unmodified except:
   - `shopify-shop-domain: victim-shop.myshopify.com`
4. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` is constructed from the tampered headers; `Utils::HmacValidator.validate(request)` still succeeds because `to_signable_string` only checks `@raw_body`, which is unchanged [1](#0-0) .
5. `Webhooks::Registry.process` dispatches the handler with `shop: "victim-shop.myshopify.com"` and the attacker's `body` [5](#0-4) , causing the host app to process attacker-controlled data as if it originated from the victim shop.
