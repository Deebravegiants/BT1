### Title
Webhook shop/topic identity is not covered by the HMAC signature, allowing cross-tenant impersonation - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
### Finding Description
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`), event type (`topic`), delivery id (`webhook_id`), and API version from unauthenticated HTTP headers, while the HMAC signature that `Utils::HmacValidator` verifies only covers the raw request body: [1](#0-0) 

```
def topic
  T.cast(shopify_header("topic"), String)
end

def shop
  T.cast(shopify_header("shop-domain"), String)
end
...
def to_signable_string
  @raw_body
end
```

`Utils::HmacValidator.validate` only checks the HMAC over `to_signable_string`, i.e. the raw body: [2](#0-1) 

`Registry.process` treats a successful HMAC check as proof that the *entire* request (including `shop`, `topic`, `webhook_id`, `api_version`) is authentic, and hands these unauthenticated header values straight to the app's webhook handler: [3](#0-2) 

The identity binding that should hold is:
`hmac_signed_bytes == bytes_that_determine_tenant/topic`

but in this implementation:
`hmac_signed_bytes (raw_body only) != bytes_used_for_tenant/topic (shop-domain, topic, webhook_id headers)`

The signature proves the body came from someone possessing `api_secret_key` (i.e., Shopify), but it proves nothing about which shop or topic that body belongs to, because those fields are carried in headers that sit entirely outside the signed byte range.

### Impact Explanation
Any legitimately-signed webhook body/HMAC pair (obtainable by an unprivileged attacker who merely owns/operates their own Shopify development store and receives a real webhook for it) can be replayed against the app's public webhook endpoint with the `shop-domain`, `topic`, `webhook_id`, or `api_version` headers altered. `Registry#process` will accept it (`Utils::HmacValidator.validate` passes because only the body is checked) and will dispatch it to the handler registered for the attacker-chosen `topic`, tagged with the attacker-chosen `shop`: [4](#0-3) 

Any host application that uses `WebhookMetadata#shop` to scope tenant data (the documented and expected usage pattern) will process attacker-supplied body content under an arbitrary victim shop identity, or under a topic the body was never intended for. This is a cross-tenant identity-binding break entirely rooted in this gem's `Request`/`HmacValidator`/`Registry` code, not in host-application misuse.

### Likelihood Explanation
The attacker only needs: (1) their own (or any) Shopify store to receive one legitimately signed webhook of any topic/body, and (2) the ability to send an HTTP POST to the target app's public webhook endpoint — both are unprivileged-internet-user capabilities. No access token, `client_secret`, or leaked credential is required.

### Recommendation
Include the identity-relevant headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signed payload used for HMAC verification (or otherwise cryptographically bind them to the body, e.g. by validating them against a separately authenticated channel), instead of only signing/verifying the raw body in `Request#to_signable_string`.

### Proof of Concept
1. Register two webhook handlers, one for topic `orders/create` and one for `shop/update`, in an app instance.
2. Obtain one legitimately Shopify-signed webhook (raw body `B`, header `x-shopify-hmac-sha256: H`) for any store the attacker controls (e.g., `attacker.myshopify.com`, topic `orders/create`).
3. Replay the exact same body `B` and header `H` to the app's webhook endpoint, but set `x-shopify-shop-domain: victim.myshopify.com` and, if desired, `x-shopify-topic: shop/update`.
4. `Utils::HmacValidator.validate` succeeds because it only recomputes the HMAC over `B`; `Registry.process` dispatches the handler for the (attacker-chosen) topic with `shop: "victim.myshopify.com"`, demonstrating that the shop/topic binding is unauthenticated.
