### Title
Webhook `shop`, `topic`, and `webhook_id` fields are not covered by the HMAC, allowing cross-tenant webhook spoofing via replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw body, while `shop`, `topic`, and `webhook_id` are read from unauthenticated HTTP headers. `Registry.process` uses these header-derived values to route and label the webhook payload, but they are never covered by the HMAC check that is supposed to prove "the request did indeed come from Shopify" (as the gem's own docs claim).

### Finding Description
`Utils::HmacValidator.validate` computes the expected signature purely from `verifiable_query.to_signable_string`. For `Webhooks::Request`, that method returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, and `webhook_id` are parsed straight from HTTP headers, with no cryptographic binding to the signed body: [2](#0-1) [3](#0-2) 

`Registry.process` validates the HMAC (which only checks the body), then immediately trusts `request.topic` (to route to a handler) and `request.shop` (to build `WebhookMetadata` handed to the app) without any re-validation that these header values were the ones actually signed by Shopify: [4](#0-3) 

The gem's own documentation states that `Registry.process` "will verify the request did indeed come from Shopify and then call the specified handler for that webhook," implying the `shop`/`topic`/`webhook_id` fields delivered to the handler are trustworthy/authenticated: [5](#0-4)  and that `data.shop` is "The shop domain of the webhook": [6](#0-5) 

This is the same bug class as the reference report: a value that is acted upon (tenant/shop identity, dispatch topic) is not the value that is covered by the cryptographic check (`LIEN_TOKEN.ownerOf(i)` vs `liensRemaining[i]`; here, HMAC-validated `raw_body` vs. header-derived `shop`/`topic`). The equality that should hold — "the shop/topic delivered to the handler == the shop/topic that Shopify actually signed for" — does not hold, because `shop`/`topic` are outside the signed payload.

### Impact Explanation
An attacker who legitimately installs the target app on their own low-privilege Shopify store can trigger any subscribed webhook topic (e.g., `orders/create`) for that store and capture the exact `(raw_body, X-Shopify-Hmac-Sha256)` pair Shopify sent. Because the HMAC only covers `raw_body`, the attacker can replay that identical body/HMAC pair to the app's webhook endpoint while forging the `X-Shopify-Shop-Domain` header (and/or `X-Shopify-Topic`, `X-Shopify-Webhook-Id`) to name a victim shop. `Registry.process` will pass `HmacValidator.validate` (body+HMAC still match) and will hand the host application a `WebhookMetadata` claiming the payload belongs to the victim shop/topic. Any host app that trusts `data.shop` to select the tenant record to update (exactly as the gem's own usage docs recommend: `perform_later(topic: data.topic, shop_domain: data.shop, ...)`) will apply the attacker's own webhook body to the victim tenant's data — a cross-tenant data-integrity break, consistent with the "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is moderate-to-high for merchant-vs-merchant scenarios: no access token, `api_secret_key`, or privileged Shopify account is required — only the ability to install the target app on any store (including a free/test store) and capture one legitimate webhook delivery, then replay it with a modified `shop-domain` header to the same public webhook endpoint. This is a purely gem-side design flaw (missing binding), not a host-application misuse of an undocumented API — the gem's own docs present `data.shop`/`data.topic` as trustworthy outputs of the verification step.

### Recommendation
Extend `to_signable_string` (or add a secondary check in `HmacValidator`/`Registry.process`) so that `shop`, `topic`, and `webhook_id` are cryptographically bound to the verified payload, e.g., by having callers additionally confirm `request.shop` against the shop associated with the session/webhook subscription that is expected to receive that topic, or by documenting explicitly that these header fields are NOT covered by the HMAC and must be independently re-validated by the host application before being trusted for tenant routing.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and subscribes to `orders/create`.
2. Attacker triggers an order creation, capturing the webhook POST: `raw_body = B`, header `X-Shopify-Hmac-Sha256 = H` (valid for `B`), `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker replays the exact same request to the app's public webhook endpoint, changing only `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (HMAC `H` is untouched since it never covered this header).
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `raw_body` against `H`: [7](#0-6) 
5. `WebhookMetadata` is built with `shop: "victim-shop.myshopify.com"` and handed to the host app's handler, which (per the gem's documented usage pattern) enqueues/attributes the attacker's order payload `B` to `victim-shop.myshopify.com`.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
