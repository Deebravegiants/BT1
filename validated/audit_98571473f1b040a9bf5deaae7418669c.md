Based on my investigation, I found a strong custody-grade analog in the `MultisigAccountTimeLock` mechanism.

### Title
Multisig timelock override threshold allows a colluding minority-plus-one to bypass the configured timelock, seizing early execution authority over the multisig-controlled assets - (File: aptos-move/framework/aptos-framework/sources/multisig_account.move)

### Summary
The external Astaria bug is a missing upper-bound/authority check on a duration parameter (`epoch <= currentEpoch + 1`), letting an unprivileged actor commit a lien whose exposure window exceeds the protocol's intended custody guarantee. The Aptos-native analog is `multisig_account::can_execute_with_timelock`, where the `override_threshold` field is validated only against being `> num_signatures_required` and `<= owners.length()` at set time [1](#0-0) , but the runtime check that is supposed to gate *early* (pre-timelock) execution treats reaching `override_threshold` as equivalent to full timelock expiry — an OR condition with no re-validation that the approving quorum is still the *timelock-authorized* threshold at the moment of owner-list mutation.

### Finding Description
`can_execute_with_timelock` computes execution eligibility as:
```
(override_threshold.is_some() && &num_approvals >= override_threshold.borrow()) || elapsed >= timelock
``` [2](#0-1) 

The timelock feature exists specifically as a custody control — to give owners a window to detect and reject a malicious/compromised-owner-initiated transaction before it executes against multisig-held assets (APT, coins, objects). However, the `override_threshold` path collapses that entire custody guarantee into a raw vote count comparison with no re-check that the owners who approved are still valid owners *and* that the owner list/threshold configuration wasn't itself just changed via a separate in-flight transaction. Because `MultisigAccountTimeLock` is a completely separate resource from `MultisigAccount`'s owner list, and `upsert_timelock` can be called by the multisig's own signer (i.e., via a prior multisig transaction) to set an `override_threshold` as low as `num_signatures_required + 1`, any transaction reaching normal quorum plus one extra approval executes **immediately**, fully defeating the timelock's purpose. This is confirmed by the test `test_implicit_vote_counts_toward_override`, which shows an owner's *implicit* (non-explicit) vote counts toward the override threshold in `can_execute` but not in `can_be_executed` [3](#0-2) , meaning the override can be reached with fewer explicit approvals than a human reviewer would expect from reading "3-of-3 override."

The custody invariant broken: a timelock configured to protect multisig-held value should require either full quorum-and-wait or an explicitly-and-separately-approved override; instead, one extra implicit vote (an owner merely calling the view function, or being counted automatically since they haven't voted) statistically satisfies "override" and the funds move before the safety window elapses.

### Impact Explanation
If exploited, an attacker who compromises or colludes with `num_signatures_required + 1` owners (rather than needing to wait out the full timelock) can drain, transfer, or reassign control of any asset held by the multisig account — APT balances, fungible asset stores, or object ownership — bypassing the delay that other, honest owners rely on to reject fraudulent transactions. This is a direct custody control bypass: the timelock is the only publicly documented protection against a fast rug-pull by a minority-plus-one of owners, and its override path effectively nullifies it whenever `override_threshold` is configured close to `num_signatures_required`.

### Likelihood Explanation
Medium-High. Exploitation requires the multisig to have configured a timelock with `override_threshold` (an opt-in feature), and requires collusion or compromise of a threshold-plus-one set of owners — the same trust assumption the timelock was designed to protect against for the *remaining* timelock duration. Because `override_threshold` only needs to satisfy `> num_signatures_required`, a very common configuration (e.g., `num_signatures_required + 1`) makes the bypass trivial to trigger under normal quorum-plus-one operation, likely well before most owners perceive that "timelock protection" is meaningfully in effect.

### Recommendation
Either remove the override-threshold fast path entirely, or require that override approvals be a distinct, explicitly-tagged vote (not reuse of the same approval count used for quorum, and not counting implicit non-votes), and require `override_threshold` to be set meaningfully higher (e.g., unanimous or `owners.length()`) with an explicit code comment/invariant preventing configurations where override ≈ quorum. Additionally, ensure `can_execute` and `can_be_executed` treat override consistently (currently one counts implicit votes toward override and the other does not), and re-validate override eligibility using only owners still present in the account at execution time.

### Proof of Concept
1. Owners `A, B, C` create a multisig with `num_signatures_required = 2`.
2. `upsert_timelock` is called to configure `timelock_period = 1 hour, override_threshold = Some(3)` intending "full unanimity required to skip the wait."
3. As shown by the existing test `test_implicit_vote_counts_toward_override` [3](#0-2) , `create_transaction` (auto-approves for `A`) plus one explicit `approve_transaction` from `B` yields `num_approvals = 2`; calling `can_execute(C, ...)` implicitly adds `C`'s vote (2+1=3) and reports execution allowed *without* `C` ever explicitly approving and *without* waiting for the 1-hour timelock, while `can_be_executed` (no implicit vote) correctly still blocks. Any caller who invokes the entry point using `can_execute`'s code path (`validate_multisig_transaction` when `multisig_v2_enhancement_feature_enabled()`) can execute a fund-moving transaction with only 2 of 3 owners' real approval, immediately, despite the configured 1-hour/3-of-3 override safeguard.

**Uncertainty note:** I could not fully trace `upsert_timelock`'s complete validation logic or confirm whether `validate_multisig_transaction`'s call to `can_execute` (vs. `can_be_executed`) is actually the path used by the on-chain VM prologue for standard execution, versus only being a view-only convenience function for wallets to pre-check. This distinction is critical to confirming actual on-chain exploitability versus a client-side display bug. I recommend a follow-up Devin session with full file access to trace `validate_multisig_transaction`'s live VM invocation path and `upsert_timelock`'s full validation logic before treating this as certain.

    inline fun can_execute_with_timelock(multisig_account: address, sequence_number: u64, num_approvals: u64): bool {
        if (exists<MultisigAccountTimeLock>(multisig_account)) {
            let multisig_account_resource = &MultisigAccountTimeLock[multisig_account];
            let timelock = multisig_account_resource.timelock_period;
            let override_threshold = multisig_account_resource.override_threshold;

            // Get the pending transaction to check if the timelock has expired
            // Assume that the transaction has already been checked to exist and is valid
            let pending_transaction = get_transaction(multisig_account, sequence_number);

            // Use subtraction to avoid overflow (now_seconds() >= creation_time_secs is always true)
            let elapsed = now_seconds() - pending_transaction.creation_time_secs;

            // If the number of approvals meets the override threshold, or the timelock has expired, allow execution
            (override_threshold.is_some() && &num_approvals >= override_threshold.borrow()) || elapsed >= timelock
        } else {
            true
        }
    }
