## Title
Direct token transfers to AMM vaults distort deposit, withdrawal and swap accounting - (File: `program/src/processor.rs`, `program/src/math.rs`)

### Summary
`process_deposit`, `process_withdraw`, `process_swap_base_in`, `process_swap_base_out`, `process_swap_base_in_v2`, `process_swap_base_out_v2`, and `process_initialize2` all derive pool reserves directly from the live SPL token account balances of the coin/pc vaults (`amm_coin_vault.amount`, `amm_pc_vault.amount`) rather than from an internally tracked, instruction-mediated balance. Because SPL token transfers to an arbitrary token account are permissionless, an attacker can transfer tokens directly into `amm_coin_vault`/`amm_pc_vault` outside of the AMM program's Deposit/Swap instructions and thereby manipulate the reserve values that drive LP-mint math, withdrawal-redemption math, and swap pricing math — the exact "direct transfer inflates internal accounting" bug class flagged in the report for Lido's `StEtherAdapter` (`STETH.balanceOf(address(this))`).

### Finding Description
`Calculator::calc_total_without_take_pnl_no_orderbook` takes the raw vault `amount` values as its `pc_amount`/`coin_amount` parameters: [1](#0-0) 

This function is called with `amm_pc_vault.amount` / `amm_coin_vault.amount` (read straight from the SPL token account, not from any AMM-internal ledger) in every liquidity- and swap-affecting instruction:
- Deposit: [2](#0-1) 
- Withdraw: [3](#0-2) 
- SwapBaseIn: [4](#0-3) 
- SwapBaseOut / v2 variants: [5](#0-4) [6](#0-5) [7](#0-6) 

Deposit LP minting is proportional to `deduct_coin_amount / total_coin_without_take_pnl` (or the pc-side equivalent) multiplied by `amm.lp_amount`: [8](#0-7) 

Withdrawal redemption is proportional to `withdraw.amount / amm.lp_amount` multiplied by `total_coin_without_take_pnl` / `total_pc_without_take_pnl`: [9](#0-8) 

Pool initialization also computes the initial LP supply directly from vault balances via `integer_sqrt`, so a pre-init direct transfer to the vaults before `Initialize2` is called changes the minted LP amount for the creator: [10](#0-9) 

Unlike the ERC-4626/Lido case (a single-asset vault where a donation to `STETH.balanceOf` directly inflates the redeemable value of existing shares against a fixed liability), Raydium's AMM is a constant-product design: both deposit and withdraw ratios are computed from the *current* pool ratio (`total_coin_without_take_pnl`/`total_pc_without_take_pnl`), and a one-sided donation changes that ratio. This can be leveraged to:
1. **Front-run a pending Deposit**: an attacker observes a queued deposit transaction (base-side deposit with `max_coin_amount`/`max_pc_amount` and optional `other_amount_min` slippage bound) and donates tokens to one vault immediately before it executes, shifting the coin/pc ratio so that the victim's `deduct_pc_amount`/`deduct_coin_amount` calculation (lines 1202-1255) forces the deposit to revert on `ExceededSlippage`, or (if slippage bounds are absent/loose) mints the victim fewer LP tokens than expected for their contribution while the donated tokens permanently sit in the vault, diluting the victim relative to LP holders (including the attacker if they also hold LP going in).
2. **Front-run a pending Withdraw**: similarly, donating to one vault right before a withdrawal skews `coin_amount`/`pc_amount` at line 1756-1761, causing the withdrawer to receive an unbalanced payout or to fail the `min_coin_amount`/`min_pc_amount` slippage check, forcing a revert/retry that the attacker can repeatedly grief.
3. **Corrupt swap pricing**: donating to one side just before a victim's swap changes `total_pc_without_take_pnl`/`total_coin_without_take_pnl` used in `swap_token_amount_base_in`/`swap_token_amount_base_out`, degrading the price the victim receives (classic sandwich-adjacent manipulation, but achievable via a plain SPL transfer with no swap instruction at all, bypassing any swap-specific protections).

### Impact Explanation
Because deposit/withdraw/swap math trusts the raw vault balance instead of a value updated exclusively through the program's own accounting (e.g., an internal reserve field incremented/decremented only by CPI-verified transfers), any unprivileged actor can permissionlessly alter the numerators/denominators used for LP minting, LP redemption and swap output for every other user's next instruction in the same slot/transaction ordering. This can cause victims to receive materially less than the constant-product invariant entitles them to, or can DoS deposits/withdrawals via forced slippage-check failures, both of which constitute fund loss or availability loss for LPs/swappers reachable from a single permissionless SPL token transfer plus a normal user transaction.

### Likelihood Explanation
Likelihood is high for the front-running/griefing variants because: transferring SPL tokens to a known, public vault address requires no special privilege, no signature from the AMM authority, and no interaction with the AMM program at all; the vault addresses (`amm.coin_vault`, `amm.pc_vault`) are public PDAs/accounts recorded in `AmmInfo`. The attacker only needs to observe a pending transaction in the mempool/leader schedule and race a donation transfer ahead of it, which is standard practice on Solana.

### Recommendation
Do not derive pool reserves solely from live SPL token vault balances. Maintain internal reserve counters in `AmmInfo`/state that are updated exclusively by the program during Deposit/Withdraw/Swap CPIs, and reconcile against the vault's actual balance defensively (e.g., take `min(internal_reserve, vault.amount)` or require they match within an expected delta, erroring out otherwise). At minimum, treat any unexpected excess in vault balance versus the last known internal state as un-attributed "PnL" to be swept via the existing `withdrawpnl` path rather than folding it directly into the ratio used for LP minting/redemption/swap pricing on the very next instruction.

### Proof of Concept
1. Attacker observes a victim's pending `Deposit` transaction (base_side = coin) with `max_coin_amount = C`, `max_pc_amount = P`, and `other_amount_min = M`.
2. Attacker submits a transaction transferring `Δpc` tokens directly (plain SPL `Transfer`) into `amm_pc_vault` before the victim's transaction lands, so `total_pc_without_take_pnl` increases by `Δpc` while `total_coin_without_take_pnl` is unchanged (see `program/src/math.rs:238-250`, called at `program/src/processor.rs:1147-1153`).
3. When the victim's Deposit executes, `deduct_pc_amount = invariant.exchange_coin_to_pc(C, Ceiling)` (`program/src/processor.rs:1202-1204`) is now computed against the inflated `total_pc_without_take_pnl`, increasing `deduct_pc_amount`. If `deduct_pc_amount > P` the deposit reverts with `ExceededSlippage` (`program/src/processor.rs:1206-1222`); if `other_amount_min` is unset or loose, the deposit instead proceeds but mints the victim `mint_lp_amount` computed off the skewed ratio (`program/src/processor.rs:1243-1250`), locking in an unfavorable, attacker-influenced entry price for the victim while the attacker's donated tokens remain in the vault and inflate the position of existing LP holders.
4. The identical technique applies symmetrically to `process_withdraw` (`program/src/processor.rs:1719-1761`) to force a withdrawal revert or skew the coin/pc payout ratio, and to any of the four swap entrypoints (`program/src/processor.rs:1940-1945`, `2154-2159`, `2342-2347`, `2533-2538`) to worsen the executed swap price for the victim.

```rust
    pub fn calc_total_without_take_pnl_no_orderbook<'a>(
        pc_amount: u64,
        coin_amount: u64,
        amm: &'a AmmInfo,
    ) -> Result<(u64, u64), AmmError> {
        let total_pc_without_take_pnl = pc_amount
            .checked_sub(amm.state_data.need_take_pnl_pc)
            .ok_or(AmmError::CheckedSubOverflow)?;
        let total_coin_without_take_pnl = coin_amount
            .checked_sub(amm.state_data.need_take_pnl_coin)
            .ok_or(AmmError::CheckedSubOverflow)?;
        Ok((total_pc_without_take_pnl, total_coin_without_take_pnl))
    }
```
