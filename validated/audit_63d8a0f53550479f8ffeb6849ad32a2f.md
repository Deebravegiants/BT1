### Title
Donation-Inflated `tokenBalance()` Underflows `Router._computeBuy`'s Overflow Cap, Permanently Bricking All Buys on the Curve - ([File: packages/contracts/src/Router.sol])

### Summary
`Router._computeBuy` caps `tokensOut` at `pair.tokenBalance()` (the live ERC20 balance) and then computes `cappedReserveToken = reserveToken - tokensOut`. If an attacker inflates `tokenBalance()` above the pair's virtual `reserveToken` by directly transferring the launched `Token` to the `Pair`, this subtraction underflows and reverts with a `Panic(0x11)`, since `Router` runs under Solidity 0.8's checked-arithmetic. This is the exact same bug class the codebase already fixed in `Bonding.previewLtUntilGraduation` (see the `realBalance >= reserveToken` donation-inflation guard at [1](#0-0) ), but the guard was never mirrored into `Router._computeBuy`, which is reachable from every `Zap.buy`.

### Finding Description
`Router._computeBuy` computes the uncapped `tokensOut` from the constant-product formula, then re-caps it against the real balance when the virtual/uncapped output would exceed sellable supply: [2](#0-1) 

`realBalance = pair.tokenBalance()` is a live `IERC20.balanceOf` read [3](#0-2) , which any address can inflate by directly `transfer`-ing the launched `Token` to the `Pair` (a permissionless ERC20 transfer, no special role required — Token is a standard `ERC20Upgradeable`, see [4](#0-3) ). If this donated balance pushes `tokensOut` (capped to `realBalance`) above `reserveToken` (the pair's virtual/stored token reserve, which direct transfers never touch), the line `cappedReserveToken = reserveToken - tokensOut` underflows.

This is precisely the underflow class the codebase itself documents as a historical bug in the sibling function: *"A TOKEN donation that drives `realBalance > reserveToken` previously underflowed `Bonding.previewLtUntilGraduation`'s supply leg, cascading into a `Zap.buy` DoS. Guard added; tests pin the fix"* [5](#0-4) . The fix landed only in `previewLtUntilGraduation` [1](#0-0) , which is a pure view/estimation helper. `Router._computeBuy` — the function that actually executes `Router.buy`, called by every `Bonding.buy`/`Zap.buy` on the curve — has the same shape of cap-then-subtract logic but no equivalent `realBalance >= reserveToken` guard.

Once `tokensOut > realBalance` is triggered by the uncapped constant-product output (which happens deterministically on the buy that empties or nearly empties the curve — the intended "overflow buy" scenario the cap exists for), and an attacker has pre-inflated `realBalance` above `reserveToken` via a plain token donation, `_computeBuy` reverts with a raw arithmetic Panic instead of executing the swap.

### Impact Explanation
Because `Router._computeBuy` is invoked by `Router.buy`, which is invoked by `Bonding.buy` on every curve trade, a single reverting call permanently DoSes that token's curve: no further `Zap.buy` can succeed on it. Since the curve can only be exited via `Bonding.sell`/`Zap.sell` (which uses `_computeSell`, unaffected) or via graduation, and graduation triggers (`canGraduate`) rely on `Pair` reserves that a stuck curve may never reach (the USD/supply thresholds may not yet be crossed), buyers are permanently locked out of buying into that token — a griefing/freezing vector reachable by any unprivileged wallet with the cost of one ERC20 transfer plus the gas to grief the curve into the overflow-cap regime.

### Likelihood Explanation
Reaching the overflow-cap branch (`tokensOut > realBalance`) is a normal, expected end-state of the curve (it's the mechanism that caps the final sellout buy), and the donation itself is a single unprivileged `Token.transfer(pair, X)` call — no special timing or race condition is required, only sizing the donation so that `realBalance` exceeds `reserveToken` by the time the curve approaches sellout. The attack is cheap (cost is only the donated tokens, which the attacker can acquire by buying on the same curve) and fully reproducible, matching the codebase's own regression test harness for the sibling bug (`_stageDonationAttack` in `test/Zap.t.sol`).

### Recommendation
Mirror the `previewLtUntilGraduation` guard into `Router._computeBuy`: before computing `cappedReserveToken = reserveToken - tokensOut`, check `if (tokensOut >= reserveToken) { ...handle degenerate/donation-inflated case... }` (e.g., clamp `tokensOut` to `reserveToken - 1` or otherwise avoid the underflow), consistent with the `OverflowCapDegenerate` handling already present for the `cappedReserveToken == 0` case.

### Proof of Concept
1. `Zap.createToken` launches a token; curve opens with `reserve0 = TOTAL_SUPPLY` (virtual) and real balance `curveSupply = 75%`.
2. An unprivileged attacker buys tokens (`Zap.buy`) to hold real `Token` balance, then `Token.transfer(pairAddr, donationAmount)` directly to the `Pair`, inflating `pair.tokenBalance()` (live ERC20 balance) without moving the stored `_pool.tokenReserve`.
3. A subsequent large buy through `Zap.buy`/`Bonding.buy` drives the uncapped constant-product `tokensOut` past `realBalance`, entering the `if (tokensOut > realBalance)` branch in `Router._computeBuy`.
4. If `realBalance` (inflated by the donation) exceeds `reserveToken`, `cappedReserveToken = reserveToken - tokensOut` underflows and the whole `Router.buy` call — and therefore every subsequent `Zap.buy` on this token — reverts with a Panic, permanently freezing the curve to buyers. (Precise sizing of the donation amount relative to curve depth is needed to land in this exact underflow window; `_drainAmountForCapHeadroom`/`_stageDonationAttack` in `test/Zap.t.sol` demonstrate the harness already used to hit the analogous `tokensOut > realBalance` regime, confirming the branch is practically reachable.)

```text
    function _computeBuy(
        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 amountInUsed, uint256 tokensOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        amountInUsed = amountIn;

        uint256 newReserveAsset = reserveAsset + amountInUsed;
        tokensOut = reserveToken - (k / newReserveAsset);

        uint256 realBalance = pair.tokenBalance();
        if (tokensOut > realBalance) {
            tokensOut = realBalance;
            uint256 cappedReserveToken = reserveToken - tokensOut;
            if (cappedReserveToken == 0) revert OverflowCapDegenerate();
            uint256 cappedReserveAsset = (k + cappedReserveToken - 1) / cappedReserveToken;
            amountInUsed = cappedReserveAsset - reserveAsset;
        }
    }
```
