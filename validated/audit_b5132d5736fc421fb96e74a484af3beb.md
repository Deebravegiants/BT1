### Title
Webhook `topic`, `shop-domain`, `webhook-id`, and `api-version` headers are not covered by the HMAC signature, enabling cross-tenant webhook forgery via replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `Registry.process` validates the HMAC solely against that body. The `topic`, `shop-domain`, `webhook-id`, and `api-version` values are read straight from unauthenticated HTTP headers and are then trusted to route/dispatch the payload and to populate `WebhookMetadata#shop`, which host applications use to attribute the payload to a specific merchant/tenant.

### Finding Description
`Request#hmac` and `to_signable_string` bind the HMAC to `@raw_body` only: [1](#0-0) [2](#0-1) 

`Registry.process` validates only that HMAC-over-body, then uses `request.topic` to select a handler and `request.shop` to populate the dispatched metadata, without any check that `shop`/`topic`/`webhook_id` are the values Shopify actually signed for that body: [3](#0-2) 

The identity binding that should hold is: `hmac == HMAC(secret, body ∥ shop ∥ topic ∥ webhook_id)`, i.e. the authenticated bytes should equal the bytes the application acts on. Instead the gem only enforces `hmac == HMAC(secret, body)`, while `shop`, `topic`, and `webhook_id` are parsed from headers that are entirely outside the signed bytes — the "bytes verified versus bytes parsed" identity-binding break called out in scope.

Because the header values are unauthenticated, any body+HMAC pair that a merchant/tenant is able to observe from their own legitimate webhook delivery (webhook endpoints are internet-reachable, unauthenticated HTTP endpoints controlled by the host application; the body payload for many topics is not secret to the shop that owns it) can be replayed to the same endpoint with a *different* `shopify-shop-domain` header. `Utils::HmacValidator.validate` will still pass because it only checks the body bytes, and `Registry.process` will call the handler with `WebhookMetadata#shop` set to the attacker-chosen shop, forging a webhook that appears to originate from a different tenant/merchant than the one that actually produced it.

### Impact Explanation
This is cross-tenant data/event injection: a party with access to one merchant's legitimate webhook body+HMAC can cause the receiving application to process/act on it as if it belongs to a different merchant (`shop` field is forged) — this maps to the in-scope "Critical - cross-tenant access" category, since host applications commonly key data storage/side effects directly off `WebhookMetadata#shop`.

### Likelihood Explanation
Requires an attacker (e.g. a malicious merchant/app-installer) to have first observed one valid `(body, hmac)` pair delivered to the app's public webhook endpoint (webhook endpoints are unauthenticated internet-facing routes by design), which is realistic since Shopify delivers webhooks for events the merchant itself can often trigger (e.g. `orders/create`, `app/uninstalled`, etc.) or observe. No possession of `api_secret_key` is required — only replay of previously-observed bytes with a modified header.

### Recommendation
Include `topic`, `shop`, and `webhook_id` (and ideally a nonce/timestamp) in the signable string that `HmacValidator` verifies, or otherwise cryptographically bind these header values to the payload before trusting them in `Registry.process`/`WebhookMetadata`. At minimum, reject requests whose header-derived `shop` is not one the app currently has an active installation/session for, in addition to fixing the signable-bytes binding.

### Proof of Concept
1. App exposes a webhook endpoint using `ShopifyAPI::Webhooks::Registry.process(request)`.
2. Attacker (a merchant with the app installed, or anyone who intercepts a delivery) captures a legitimately-delivered webhook `raw_body` and its `x-shopify-hmac-sha256` value for shop `victim-shop.myshopify.com`.
3. Attacker resends the same `raw_body` and same HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: attacker-shop.myshopify.com` (and/or a different `x-shopify-topic`/`x-shopify-webhook-id` if the handler is topic-keyed differently).
4. `Utils::HmacValidator.validate(request)` succeeds because it only hashes `@raw_body`.
5. `Registry.process` looks up the handler for `request.topic` and invokes it with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` — the host application now processes the victim's payload as belonging to the attacker's shop (or vice versa), corrupting per-tenant data/state.
