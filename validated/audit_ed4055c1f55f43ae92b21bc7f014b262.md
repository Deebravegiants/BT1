### Title
Webhook shop-domain attribution is not covered by the HMAC signature, allowing cross-tenant shop spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` authenticates a webhook by computing an HMAC over the raw body only, but the `shop` field that identifies which tenant the webhook belongs to is read from an HTTP header that is never included in the signed material. `Registry.process` trusts this unauthenticated `shop` value and forwards it to the app's handler as the tenant identifier.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is derived purely from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is disjoint from the signed content: [2](#0-1) 

`Utils::HmacValidator.validate` only checks `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)`, i.e., only the body is bound to the HMAC: [3](#0-2) 

`Registry.process` validates only this body-bound HMAC and then unconditionally trusts `request.shop`, passing it straight into `WebhookMetadata` for the app's handler to act on: [4](#0-3) 

The binding that is broken is: **shop authenticated by the HMAC (none, since shop isn't part of the signable string) versus shop used as the tenant key handed to the app (`request.shop` from an unauthenticated header)**. The `client_secret` used to sign webhooks is shared across every shop that has installed the app (multi-tenant apps use one `client_secret`, not a per-shop secret) — see `Context.api_secret_key` used identically in `HmacValidator` for both OAuth and webhook verification. This means any shop that has legitimately installed the app can obtain a validly-signed `(raw_body, hmac)` pair for its own webhook events, then replay that exact body/HMAC pair to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to a victim shop's domain. `HmacValidator.validate` still returns `true` because it never inspected the header, and `Registry.process` dispatches the payload to the handler labeled with the attacker-chosen victim shop.

### Impact Explanation
If the host application uses `WebhookMetadata#shop` (i.e., `request.shop`) as a session/tenant key — e.g., to look up the victim's `Session`/access token, to write into the victim's tenant-scoped data store, or to trigger tenant-scoped side effects (like GDPR redaction, order/customer updates, or webhook-driven billing/reconciliation) — an attacker with a valid app installation on their own shop can attribute arbitrary attacker-controlled webhook payloads to a different tenant. This is a cross-tenant access/confusion primitive: the attacker doesn't need the victim's credentials, only a legitimate (even minimal, free) install of the app on any shop, since the `client_secret`-based HMAC only proves "this came from an app-installed shop that received a genuine webhook," not "this event belongs to shop X."

### Likelihood Explanation
Exploitability depends entirely on how the host application built on this gem uses `WebhookMetadata#shop`/`request.shop`. The gem's own `Registry.process` performs no additional binding between the shop header and the signed body, so any consumer that trusts `request.shop` for tenant attribution without independent verification (e.g., cross-checking against Shopify's Admin API using a `Session` scoped for that exact shop, or maintaining a signed webhook-id ledger) inherits this gap. This mirrors Shopify's own documented webhook HMAC scheme (body-only signing), so it is a known characteristic of the protocol rather than a coding defect unique to this gem's HMAC math — but the gem exposes `request.shop` as if it were a trustworthy, verified field (it is returned unconditionally, with the same API shape as verified OAuth/JWT fields), which invites misuse.

### Recommendation
- Document explicitly, next to `Webhooks::Request#shop` and `WebhookMetadata#shop`, that this value is **not covered by the HMAC** and must not be trusted as an authenticated tenant identifier on its own.
- Where feasible, require callers to cross-check `request.shop` against an independently verified source (e.g., a `Session` already provisioned for that specific shop, or Shopify's webhook `X-Shopify-Webhook-Id` deduplication combined with a per-shop webhook secret if/when Shopify supports it).
- Consider raising `Errors::InvalidWebhookError` in `Registry.process` if the delivered `shop` does not correspond to a shop with an active, previously-established session/installation record known to the app (this check can only be enforced by documentation/guidance from the gem, since the gem itself has no session store).

### Proof of Concept
1. Attacker installs the target Shopify app on their own shop `attacker.myshopify.com` (a normal, unprivileged install — no special access required).
2. Attacker triggers/receives a genuine webhook for their own shop, capturing the raw POST body and the `X-Shopify-Hmac-Sha256` header (a validly-signed pair, since the app's `client_secret` is shared across all installs).
3. Attacker replays the identical `raw_body` + `hmac` header to the app's public webhook endpoint but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses this and `Utils::HmacValidator.validate` succeeds because `to_signable_string` never included the shop domain — see `lib/shopify_api/webhooks/request.rb:35-38` and `lib/shopify_api/utils/hmac_validator.rb:12-31`.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-199`) dispatches the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)`, causing the host app to act on attacker-controlled data as if it originated from the victim tenant.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
