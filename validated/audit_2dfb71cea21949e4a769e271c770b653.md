### Title
Webhook `shop-domain`/`topic`/`webhook_id` headers are trusted despite being excluded from the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw JSON body, while the shop identity (`shop-domain` header), `topic`, `api_version`, and `webhook_id` are read straight from unauthenticated HTTP headers. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which verifies only those body bytes, then passes the unverified header-derived `shop` value straight into `WebhookMetadata` handed to the app's handler.

### Finding Description [1](#0-0) 
`hmac`, `topic`, `shop`, `api_version`, and `webhook_id` are all read via `shopify_header(name)` from request headers, but `to_signable_string` returns only `@raw_body`. The HMAC therefore authenticates the JSON body bytes, never the header-derived shop/topic/version metadata. [2](#0-1) 
`Registry.process` validates `Utils::HmacValidator.validate(request)` (body-only) and then builds `WebhookMetadata.new(topic: request.shop, ... shop: request.shop, ...)`([sic] shop from header) and dispatches it to the registered handler as trusted data. [3](#0-2) 
The validator computes the signature purely from `verifiable_query.to_signable_string`, i.e. the raw body — nothing derived from headers is included in the signed message.

Because Shopify signs webhooks using the **app's single `client_secret`**, shared across all shops that install the app, any merchant who legitimately owns a shop that installs the app can trigger a real webhook (e.g. `orders/create`) with a valid HMAC for a given body. Since the header set (`shop-domain`, `topic`, `webhook_id`, `api_version`) is never covered by that signature, the same legitimately-signed request can be replayed to the app's webhook endpoint with those headers altered — most importantly `shop-domain` swapped for a victim shop's domain — and `HmacValidator.validate` will still return `true`, because it only re-hashes the untouched body. This breaks the identity binding: `shop_authenticated_by_hmac == shop_delivered_to_handler` does not hold; the header-derived `shop` is trusted with no cryptographic tie to the signed bytes.

### Impact Explanation
This is a cross-tenant identity confusion: a handler built on top of this gem receives `WebhookMetadata#shop` believing it was authenticated by Shopify's HMAC, when in fact it is fully attacker-controlled. Any app logic that scopes data writes, cache keys, background jobs, or session/token lookups by `data.shop` can be made to act on/for the wrong tenant (e.g. writing order data believed to belong to shop B into shop A's records, or triggering compliance/GDPR webhook handling — `shop/redact`, `customers/redact`, `customers/data_request` — for the wrong shop). This matches the "Critical: cross-tenant access" impact class since the shop-tenant boundary is broken via a spoofable, unauthenticated field.

### Likelihood Explanation
Moderate-to-low but concrete: the attacker needs to be an installer of the app (an "unprivileged" merchant relative to other tenants) able to trigger at least one real webhook delivery to the shared endpoint, then replay it with a modified `shop-domain` header (and any other headers) while keeping the JSON body byte-identical. No knowledge of `api_secret_key` is required — only observation/capture of one legitimately-delivered signed webhook, which the attacker's own shop naturally receives.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, `api_version`, `webhook_id`) in the HMAC-signed message, or otherwise cryptographically bind them to the body (e.g., concatenate them before hashing) in `Request#to_signable_string`, so that altering any of these header values invalidates the signature. At minimum, cross-check `shop-domain` against a value independently known/expected by the caller before trusting it.

### Proof of Concept
1. App installs on `attacker-shop.myshopify.com` and `victim-shop.myshopify.com`, both webhook events routed to the same `Registry.process` endpoint (same `api_secret_key`).
2. Attacker's own shop triggers `orders/create`; Shopify sends: body `B`, headers `{shop-domain: attacker-shop.myshopify.com, hmac-sha256: H(B, secret), topic: orders/create, webhook-id: W}`.
3. Attacker captures this legitimate request (it is delivered to the app's public endpoint they observe/control tooling around).
4. Attacker POSTs the same body `B` to the app's webhook endpoint again, but with header `shop-domain: victim-shop.myshopify.com`.
5. `Utils::HmacValidator.validate` recomputes `HMAC(secret, B)`, which still equals `H`, since `to_signable_string` returns only `B` — validation passes.
6. `Registry.process` builds `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and dispatches to the handler, which now processes attacker-controlled order data attributed to `victim-shop.myshopify.com`.
