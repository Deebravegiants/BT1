### Title
Webhook `shop` field is not covered by HMAC verification, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC of the raw request **body**, then forwards the `shop` value taken from an **unauthenticated HTTP header** to the application's webhook handler. Because the shop identity is never covered by the HMAC, any user who can obtain one validly-signed webhook (e.g. from their own installed shop) can replay it while forging the `shop` header to any value, causing the host application to process attacker-supplied webhook data under a victim shop's identity.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

The `shop` accessor is derived from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is completely separate from the signed material: [2](#0-1) 

`Registry.process` validates the request using `Utils::HmacValidator.validate(request)`, which only checks `verifiable_query.to_signable_string` (the body) against `Context.api_secret_key`: [3](#0-2) [4](#0-3) 

After this check passes, `request.shop` — the unauthenticated header value — is forwarded directly to the handler as the tenant identifier, with no cross-check against the body or any trusted-domain validation (`ShopValidator` is never invoked here): [5](#0-4) 

**Broken identity binding (as an equality):**
`HMAC_valid(body, api_secret_key) == true` is treated as proof of `(body, shop)` authenticity, but the actual signed equality is only `HMAC(body) == received_hmac`; `shop` is excluded from the signable string. Since `api_secret_key` is shared by the app across *every* installed shop, any shop that has installed the app can generate a validly-HMAC'd body (e.g., by triggering any webhook on their own store) and then replay that exact body with a forged `x-shopify-shop-domain` header pointing at a different (victim) shop. The HMAC check still passes because it never examined the header, and `WebhookMetadata.new(shop: request.shop, ...)` hands the forged shop value straight to the application's handler.

### Impact Explanation
This breaks the tenant boundary the whole webhook system is meant to enforce: an attacker who merely installs the app on their own shop (unprivileged internet user relative to other merchants) can inject arbitrary attacker-controlled payloads that the host application will process as if they originated from any other shop it serves — a cross-tenant data-confusion/injection primitive. Depending on how the host app's webhook handler acts on `shop` (e.g., updating per-shop settings, triggering per-shop side effects, writing to per-shop storage keyed by `shop`), this can lead to cross-tenant state corruption, privilege confusion, or data leakage between merchants of the same app.

### Likelihood Explanation
Any developer/merchant who can install the app (a normal, unprivileged onboarding action) can obtain a validly-signed webhook body for their own shop and replay it with a different `shop` header value, since nothing in this gem cross-checks the two. No access token, leaked secret, or privileged access is required — only that the attacker's own shop has the app installed and receives at least one real webhook.

### Recommendation
- Include the shop domain in the signed material used by `HmacValidator`, or otherwise cryptographically bind `shop` to the verified body (e.g., require the body's own `myshopify_domain` field, when present, to match the header, and reject mismatches).
- Validate `request.shop` with `ShopifyAPI::Utils::ShopValidator.sanitize!` before it is trusted/used, and document to consumers that `request.shop` must not be treated as authenticated unless bound to the signature.
- At minimum, warn library consumers in `WebhookMetadata`/`Registry.process` documentation that `shop` is not HMAC-protected and must be independently verified against known installed shops before being used for tenant-scoped actions.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and receives (or triggers) a legitimate webhook, capturing:
   - raw body `B`
   - valid header `x-shopify-hmac-sha256: HMAC(B, api_secret_key)`
2. Attacker replays a POST to the app's webhook endpoint with the same body `B` and same valid HMAC header, but sets:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers successfully (all required headers present).
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(B, api_secret_key)` and matches the attacker-supplied HMAC — validation succeeds because the shop header was never included in the signed string.
5. The registered handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the application to process attacker-controlled data as if it belonged to `victim-shop.myshopify.com`.
