### Title
Malicious swap route can attach an unrelated wallet-token transfer to `swap_collateral` authorization - (File: contracts/controller/src/strategies/swap.rs)

### Summary
The controller accepts caller-supplied opaque swap-route bytes and invokes the configured router while only constraining the controller's own input-token transfer. A crafted route can place attacker-controlled code below that call; code inside the route can request an unrelated `token.transfer(victim, attacker, amount)`, which simulation attaches as a child of the victim's `swap_collateral` authorization. If the victim signs that authorization tree, the unrelated wallet tokens move to the attacker even though the lending swap itself produces a valid output. [1](#0-0) [2](#0-1) 

### Finding Description
`swap_collateral` authenticates the caller and account owner/delegate, but the `swap` argument remains caller-controlled route data passed to `execute_strategy`. [3](#0-2) [1](#0-0) 

The controller's direct authorization is intentionally narrow: it authorizes only `amount_in` of `token_in` to the router, snapshots router input/output balances, rejects overspending, and requires positive measured output. [4](#0-3) [5](#0-4) 

Those measurements do not validate every nested invocation requested by route-selected contracts. The harness demonstrates that a route-named contract can call `token::Client::transfer(victim, attacker, amount)` for a token entirely unrelated to the lending market. [6](#0-5) [7](#0-6) 

In recording mode, the host places that transfer under the caller's `swap_collateral` authorization entry; in enforcing mode, the same route succeeds when the victim signs the tree containing that child. [8](#0-7) [9](#0-8) 

### Impact Explanation
This is theft of user funds outside the collateral amount intentionally routed through the strategy. The test moves the victim's entire unrelated wallet-token balance to the attacker while still depositing the expected `ETH` output into the victim's lending position. [10](#0-9) [11](#0-10) 

The economic swap can appear fair, so the protocol's input-spend and positive-output checks do not detect the unrelated transfer. [12](#0-11) 

### Likelihood Explanation
An unprivileged attacker can deploy the malicious hop contract and encode its address into the route supplied to `swap_collateral`; no privileged state or leaked key is needed. [13](#0-12) [14](#0-13) 

Exploitation requires the victim to sign the authorization tree returned by simulation. The host rejects the rogue transfer if that child is absent, which makes this a medium-severity authorization/UI spoofing analog rather than an unauthorized-transfer bug. [15](#0-14) [9](#0-8) 

### Recommendation
Do not expose opaque venue/router execution beneath an account-owner signature without a separately verified route manifest. Clients should decode the route, enumerate every venue and token address, simulate the exact envelope, and reject any authorization tree containing calls other than the expected controller call and exact input transfer. The protocol can reduce this class further by constraining routes to governance-approved venue contracts or by using a route executor that cannot request caller-authenticated actions unrelated to the declared route. [1](#0-0) [16](#0-15) 

### Proof of Concept
The existing regression test constructs a victim with USDC collateral and an unrelated wallet-token balance, routes `swap_collateral` through an attacker-controlled hop pool, and has that pool call `transfer(victim, attacker, WALLET_BALANCE)`. [17](#0-16) [7](#0-6) 

The simulation records the malicious transfer as a sub-invocation of the victim's `swap_collateral` authorization; after signing that tree, the victim's wallet balance becomes zero and the attacker's balance becomes `WALLET_BALANCE`, while the victim receives the expected ETH collateral output. [18](#0-17) [9](#0-8)

fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
