### Title
Cross-tenant webhook forgery via shop-domain header not covered by HMAC - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, and `ShopifyAPI::Webhooks::Registry.process` validates the HMAC against that body alone. The `shopify-shop-domain` header — which is the tenant identifier passed to the app's handler — is never included in the signed content. Because the app's `api_secret_key` is shared across every shop that installs the app, an attacker who installs the app on a shop they control can capture a legitimately-signed webhook and replay it to the same endpoint with the `shopify-shop-domain` header swapped to a victim shop, and the HMAC check still passes.

### Finding Description
`AuthQuery#to_signable_string` in OAuth deliberately includes every field it cares about (`code`, `host`, `shop`, `state`, `timestamp`) so the whole tuple is bound by the HMAC: [1](#0-0) 

By contrast, `Webhooks::Request` signs only the raw body: [2](#0-1) 

`shop` is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header, entirely outside the signed material: [3](#0-2) 

`Registry.process` validates only `Utils::HmacValidator.validate(request)` (which calls `to_signable_string` → body only) and then hands `request.shop` straight to the app's handler as the trusted tenant identity: [4](#0-3) 

`HmacValidator.validate` performs a byte-for-byte comparison of the computed vs. received HMAC over whatever `to_signable_string` returns — for webhooks that is body-only, so it never binds `shop`: [5](#0-4) 

**Binding that should hold:** `shop_header == shop_bound_by_hmac`. **Binding that actually holds:** `hmac_valid == HMAC(secret, body)` with no dependency on `shop_header` at all, i.e. `shop_header ∈ {any value}` is accepted as long as `body` matches some previously-signed payload.

Exploit path:
1. Attacker installs the target app on their own shop (a normal, unprivileged action — no special access token or credential needed beyond being any merchant).
2. Shopify delivers a genuine webhook to the app's shared webhook endpoint for the attacker's shop, signed with the app's `api_secret_key`, e.g. `orders/create` with `shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker replays the exact same raw body and `hmac-sha256` header to the same endpoint, but changes `shopify-shop-domain` to `victim-shop.myshopify.com`.
4. `HmacValidator.validate` recomputes HMAC over the (unchanged) body and it matches — validation passes.
5. `Registry.process` invokes the app's handler with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)`, so the app processes attacker-controlled data as if it belonged to the victim tenant.

### Impact Explanation
This breaks the tenant boundary the gem promises callers (`data.shop` is documented as "The shop domain of the webhook", per `docs/usage/webhooks.md` lines 12-16) is trustworthy. Depending on how the host app uses `data.shop` (e.g., to look up the shop's stored session/access token and act on its behalf, to update local shop records, or to process `app/uninstalled`/GDPR webhooks), this enables cross-tenant data corruption or unauthorized actions attributed to a victim shop — matching the "cross-tenant access" High/Critical impact category.

### Likelihood Explanation
Requires only that the attacker be able to install the app on a shop they control (any merchant can do this — no privileged credentials, no `api_secret_key`, no access token needed) and be able to replay an HTTP POST with modified headers to the app's public webhook endpoint. This is realistic for any multi-tenant app that shares a single webhook URL across shops, which is the pattern this gem's docs recommend.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the signed content verified for webhooks, or otherwise cryptographically bind the shop-domain header to the payload before trusting it as the tenant key — e.g., include the shop domain in `to_signable_string` for `Webhooks::Request`, or require callers to cross-check `request.shop` against the shop associated with the specific webhook registration/subscription id rather than trusting the header verbatim.

### Proof of Concept
```ruby
# 1. Attacker's own shop receives a legitimate webhook (signed by the shared app secret)
raw_body = '{"id":123,"note":"hello"}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)

legit_headers = {
  "shopify-topic" => "orders/create",
  "shopify-hmac-sha256" => Base64.encode64(hmac),
  "shopify-shop-domain" => "attacker-shop.myshopify.com",
  "shopify-webhook-id" => "wh_1",
  "shopify-api-version" => "2024-01",
}

# 2. Attacker replays identical body+hmac but swaps the shop-domain header
forged_headers = legit_headers.merge("shopify-shop-domain" => "victim-shop.myshopify.com")

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HMAC validation succeeds (body unchanged); handler receives shop: "victim-shop.myshopify.com"
```

          end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
