### Title
`HotBridge.describeWithdrawal` reports a withdrawal as `completed` without checking the `verified_withdraw` flag returned by the HOT API - ([File: packages/intents-sdk/src/bridges/hot-bridge/hot-bridge.ts])

### Summary
`HotBridge` parses a `verified_withdraw` boolean from the HOT API withdrawal-status response but never reads it before treating the withdrawal as finalized. The withdrawal is reported as `"completed"` with a destination `txHash` solely because a `hash` string exists for the matching `nonce`, regardless of whether the HOT API itself marked that withdrawal as unverified.

### Finding Description
`fetchWithdrawalHashFromApi` validates the API response against `HotApiWithdrawalSchema`, which explicitly includes a `verified_withdraw: v.boolean()` field: [1](#0-0) 

However, when looking up the matching withdrawal by `nonce`, the function only checks that `withdrawal?.hash` is a non-empty, valid hex string - it never inspects `withdrawal.verified_withdraw`: [2](#0-1) 

This hash is then propagated by `describeWithdrawal` as a `"completed"` status with a concrete `txHash`, which callers (e.g. `watchWithdrawal`, `waitForWithdrawalCompletion`, `createWithdrawalCompletionPromises`) treat as the final, authoritative outcome of the withdrawal: [3](#0-2) 

The equality that should hold is: *status reported to the integrator == actual on-chain settlement outcome*. By ignoring `verified_withdraw`, the SDK breaks this equality - it can report `"completed"` for a withdrawal that the HOT API itself has not verified as settled on the destination chain (e.g., a hash exists because a transaction was broadcast/attempted, but it later reverts, gets replaced, or never confirms).

### Impact Explanation
An integrator relying on `describeWithdrawal`/`waitForWithdrawalCompletion` to decide when to credit a user, release custody, or mark an off-chain ledger entry as final would act on a premature/incorrect "completed" status. If the unverified transaction later fails or is not the actual settling transaction, this can result in the integrator crediting/releasing funds based on a withdrawal that never actually completed, or later double-crediting once the bridge indexer surfaces the real, verified hash for the same nonce. This falls under "a status or hash misreport making an integrator credit or refund twice" (High impact).

### Likelihood Explanation
This code path is reached only as a fallback (`fetchWithdrawalHashFromApi`) when the primary bridge indexer fails or returns nothing, so it is not the default path — but it is still fully unprivileged and reachable by any caller of `describeWithdrawal` for EVM/Stellar/TON withdrawals when the indexer is degraded. No malicious actor input is required beyond the normal, permissionless flow of a withdrawal; the bug is purely in the SDK's own validation logic ignoring an explicit verification field it already parses.

### Recommendation
In `fetchWithdrawalHashFromApi`, require `withdrawal.verified_withdraw === true` in addition to a valid hex hash before returning the hash as a confirmed result; otherwise treat the withdrawal as still `"pending"`, consistent with how the bridge-indexer path is the designated source of truth.

### Proof of Concept
1. Bridge indexer request fails or times out for a withdrawal (`mockBridgeIndexerFailure` in tests demonstrates this branch is exercised).
2. HOT API fallback (`fetchWithdrawalHashFromApi`) returns a JSON payload where the matching `nonce` entry has `hash: "0x...` but `verified_withdraw: false` (e.g., a broadcast-but-unconfirmed or later-reverted transaction).
3. Current code at packages/intents-sdk/src/bridges/hot-bridge/hot-bridge.ts:565-579 ignores `verified_withdraw` and returns the hash.
4. `describeWithdrawal` returns `{ status: "completed", txHash }` to the caller, which an integrator uses to finalize the withdrawal, even though HOT itself has not verified the withdrawal as settled. [4](#0-3) [5](#0-4)

	private async fetchWithdrawalHashFromApi(
		nearTxHash: string,
		nonce: bigint,
		logger?: ILogger,
	): Promise<string | null> {
		try {
			const response = await withTimeout(
				() =>
					this.hotSdk.api.requestApi(
						`/api/v1/evm/bridge_withdrawal_hash?near_trx=${nearTxHash}`,
						{ method: "GET" },
					),
				{ timeout: HotBridge.API_FALLBACK_TIMEOUT_MS },
			);
			const data: unknown = await response.json();

			const parseResult = v.safeParse(HotApiWithdrawalResponseSchema, data);
			if (!parseResult.success) {
				logger?.debug("HOT API response parse failed", {
					issues: parseResult.issues,
				});
				return null;
			}

			const withdrawal = parseResult.output.withdrawals.find(
				(w) => w.nonce === nonce.toString(),
			);

			if (withdrawal?.hash) {
				const hash = withdrawal.hash.replace(/^0x/, "");
				if (isHex(hash)) {
					logger?.info("HOT withdrawal hash found via API fallback", {
						nearTxHash,
						nonce: nonce.toString(),
					});
					return hash;
				}
			}
			return null;
		} catch (error) {
			logger?.debug("HOT API fallback failed", { error, nearTxHash });
			return null;
		}
	}
