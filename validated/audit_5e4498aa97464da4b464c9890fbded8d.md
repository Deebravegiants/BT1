### Title
Webhook `shop` header is trusted for tenant identification but not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, but the `shop` value that is subsequently handed to the host application's handler as the tenant identifier is taken from an HTTP header that is never included in the signed payload.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop` is read from the `x-shopify-shop-domain` / `shopify-shop-domain` header, which is not part of that signable string: [2](#0-1) 

`Registry.process` validates the request purely via `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `to_signable_string` (the body) and compares it to the `hmac` header — it never checks `shop`: [3](#0-2) [4](#0-3) 

After this check passes, `request.shop` (the unauthenticated header value) is placed directly into `WebhookMetadata` and passed to the host app's handler as the tenant/shop identity for the delivered data: [5](#0-4) 

This breaks the intended binding: `hmac_valid(body, secret) == true` should imply `shop == the_shop_that_actually_sent_this_body`, but because `shop` is excluded from the signed content, that equality does not hold. Since the app's `client_secret`/HMAC secret is shared across all shops installing the app, any party able to trigger or capture one legitimate webhook delivery (topic + body + valid hmac) for a shop they control can replay that exact body/hmac pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header for a different (victim) shop. The HMAC validation still succeeds because it never inspected the header, and the host application's handler receives data purportedly belonging to the victim shop.

### Impact Explanation
This is a cross-tenant identity-binding failure: the value used to route/attribute webhook data to a specific merchant (`shop`) is not cryptographically bound to the payload that was verified. A host application that trusts `WebhookMetadata#shop` (as the library's own documented usage pattern encourages) to look up sessions, write records, or trigger shop-scoped actions can be made to act on data under the wrong shop's identity — a cross-tenant access impact.

### Likelihood Explanation
Requires the attacker to be able to send an HTTP POST to the app's public webhook endpoint with a captured/valid body+hmac pair (e.g., from a webhook fired to their own shop, or from any topic where the merchant fully controls the body content, such as `app/uninstalled` or a custom filtered webhook) and to freely set the `shop-domain` header, which any external caller of an HTTP endpoint can do. No secrets are required, since the vulnerability lies precisely in the field not needing to match the secret-bound content.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) inside the HMAC-signed content, or explicitly re-validate that the `shop` header matches an expected/registered shop for the topic before dispatching to handlers, so that the signature check binds `shop == verified_body.shop`.

### Proof of Concept
1. App receives a legitimate webhook for `attacker-shop.myshopify.com` with `raw_body = B` and header `x-shopify-hmac-sha256 = HMAC(secret, B)`. The attacker (who owns/controls this shop) captures `B` and the valid hmac.
2. Attacker POSTs to the app's webhook endpoint with the same `raw_body = B`, the same valid `hmac`, `x-shopify-topic` unchanged, but `x-shopify-shop-domain = victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(secret, B)` against the header — this passes since `B` and `hmac` are unchanged.
4. `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)` is delivered to the host app's handler, which believes the (attacker-controlled) body belongs to the victim shop.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
