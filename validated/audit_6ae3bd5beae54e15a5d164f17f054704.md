### Title
Webhook `shop` (and topic/id/version) values are trusted from unauthenticated headers while the HMAC only covers the raw body - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives its `shop`, `topic`, `api_version`, and `webhook_id` values directly from HTTP headers, but the HMAC signature computed by `Registry.process` only signs the raw request body. This breaks the binding: `shop-domain-header == shop-that-produced-hmac(body)` is never enforced, so an app that dispatches webhook data keyed by `request.shop` can be made to process a valid `(body, hmac)` pair under an attacker-chosen shop identity.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [3](#0-2) 

The `shop`, `topic`, `api_version`, and `webhook_id` accessors are read straight from the (attacker-controllable-in-transit) headers, with no cryptographic tie to the signed content: [4](#0-3) 

`Registry.process` validates only the HMAC of the body, then immediately passes `request.shop` (and the other header-derived fields) into `WebhookMetadata` for the handler to consume as the authoritative tenant identity, with no cross-check that this shop is the one that actually produced the HMAC: [2](#0-1) 

Because `secret == body-signing key` is shared across all shops installed on a given app (single `api_secret_key`/`old_api_secret_key` per `Context`), any valid `(raw_body, hmac)` pair computed with that secret — for example one legitimately produced for the attacker's own store — remains a valid signature no matter what `shop-domain` header accompanies it. The equality the gem should enforce, `hmac_signed_shop == request.shop`, is never checked; the gem instead treats `hmac_valid(body) == true` as sufficient proof that `request.shop` is authentic.

### Impact Explanation
An application built on this gem that uses `WebhookMetadata#shop` to select which merchant's data/tenant context a webhook payload applies to (the intended and documented usage) can be tricked into attributing an otherwise-legitimately-signed payload to a different shop than the one that generated it, since the header is never covered by the signature. This is a cross-tenant identity-binding break consistent with the Critical impact class (cross-tenant access) in scope for this analysis — the webhook consumer ends up acting on data under the wrong tenant's identity purely due to a gem-level verification gap, not due to any host misuse.

### Likelihood Explanation
Exploitability requires only network-level control between Shopify and the app's public webhook endpoint (i.e., ability to relay/replay a valid, previously-observed `(body, hmac)` pair with a substituted `shop-domain` header) or any intermediary capable of rewriting headers en route to the app; no `api_secret_key`, access token, or privileged account is needed by the attacker to perform the substitution itself, since the signature never covered the header they are changing. The bug is squarely inside this gem's own verification logic (`Registry.process` / `Request`), not a matter of the host ignoring documented behavior — the documented contract is "validate HMAC then trust request.shop," which is what `Registry.process` does.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signed content, or otherwise verify that any header field consumed by `WebhookMetadata` is bound to the same request the HMAC was computed for (e.g., have `Request#to_signable_string` incorporate a canonical form of the security-relevant headers, not just the raw body), and reject the webhook if that binding fails.

### Proof of Concept
1. A malicious merchant installs the app and receives a legitimate webhook delivery for their own shop `attacker.myshopify.com`, capturing the raw body `B` and its valid `X-Shopify-Hmac-Sha256` header `H = HMAC(secret, B)`.
2. The attacker (or an intermediary they control) relays a forged HTTP POST to the app's public webhook endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` (unchanged, still valid since it's over `B` only), but `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `HMAC(secret, B) == H`: [5](#0-4) 
4. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and the attacker's body `B`, causing the app to process/store data under the victim shop's identity.
