### Title
Route confusion in `AuroraEngineBridge` allows any nep141 token (incl. `nep141:plasma.omft.near`) to be routed via an attacker-supplied `auroraEngineContractId`/`proxyTokenContractId`, with unconditional `status: "completed"` reporting - (File: packages/intents-sdk/src/bridges/aurora-engine-bridge/aurora-engine-bridge.ts)

### Summary
`AuroraEngineBridge.supports()` only checks that `routeConfig.route === RouteEnum.VirtualChain` and that the `assetId` is a NEP-141 asset - it never checks that the asset is actually a token Aurora Engine (or the caller-named `auroraEngineContractId`) is authoritative for. `createWithdrawalIntents`/`validateWithdrawal` similarly perform no cross-check between `assetId`'s real custodian/bridge and the caller-supplied `routeConfig.auroraEngineContractId` / `proxyTokenContractId`. `describeWithdrawal` unconditionally returns `{ status: "completed", txHash: null }`.

### Finding Description
The claimed equality is: *the `receiver_id`/`msg`/chain encoded in the produced `ft_withdraw` intent must equal the real custodian/bridge contract for `assetId` and the chain the caller believes they are withdrawing to.*

Trace:
- `IntentsSDK.createWithdrawalIntents` (`packages/intents-sdk/src/sdk.ts:334-364`) iterates `this.bridges` in a fixed order (`IntentsBridge`, `AuroraEngineBridge`, `PoaBridge`, `HotBridge`, `OmniBridge`, `DirectBridge` — `sdk.ts:158-197`) and picks the **first** bridge whose `supports()` returns true.
- `AuroraEngineBridge.supports()` (`aurora-engine-bridge.ts:60-77`) only verifies `routeConfig.route === RouteEnum.VirtualChain` and `assetInfo.standard === "nep141"`. It performs **no check** that `assetId` (e.g. `nep141:plasma.omft.near`, a PoA-bridge-custodied native-XPL token) is a token that the caller-supplied `auroraEngineContractId` actually recognizes/bridges.
- `AuroraEngineBridge.validateWithdrawal()` (`aurora-engine-bridge.ts:128-142`) only validates that `destinationAddress` looks like an EVM address; it does not validate `routeConfig.auroraEngineContractId`/`proxyTokenContractId` against any known-good registry for the asset.
- `createWithdrawIntentPrimitive` (`aurora-engine-bridge-utils.ts:11-51`) builds the intent purely from caller input: `token: tokenAccountId` (parsed from `assetId`, e.g. `plasma.omft.near`), `receiver_id: params.auroraEngineContractId` (or `proxyTokenContractId` if set), `msg` = lower-cased hex of `destinationAddress` (optionally prefixed with `auroraEngineContractId:`). None of these values are cross-validated against the token's real bridge/custodian.
- Because `IntentsBridge` is checked before `AuroraEngineBridge` but only matches `RouteEnum.InternalTransfer`, and no other bridge in the list checks `RouteEnum.VirtualChain` before `AuroraEngineBridge`, any caller who sets `routeConfig: createVirtualChainRoute(auroraEngineContractId, proxyTokenContractId)` with `assetId: "nep141:plasma.omft.near"` will always be routed to `AuroraEngineBridge`, regardless of whether `plasma.omft.near`'s real bridge is Aurora Engine or the PoA bridge. `withdrawalParamsInvariant` (`aurora-engine-bridge-utils.ts:62-77`) only asserts `routeConfig.route === VirtualChain`, i.e., it re-checks the same weak invariant, not asset/bridge legitimacy.
- Finally, `AuroraEngineBridge.describeWithdrawal()` (`aurora-engine-bridge.ts:220-222`) unconditionally returns `{ status: "completed", txHash: null }` with **no on-chain verification** that the `ft_withdraw` call actually succeeded on the target chain/contract. Compare with `IntentsBridge.describeWithdrawal` (`intents-bridge.ts:97-101`), which at least ties status to the recorded NEAR tx hash.

Root cause: the SDK's `Bridge.supports()` contract is documented ("more specific bridges should be placed before more generic ones," `sdk.ts:154-157`) to rely on ordering + loose format checks, but `AuroraEngineBridge` accepts *any* nep141 `assetId` combined with *any* caller-chosen `auroraEngineContractId`/`proxyTokenContractId`, with no static or dynamic registry check that the combination is legitimate for the specific token. This is a gap in this repo's routing logic itself (`sdk.ts`, `aurora-engine-bridge.ts`), not merely a downstream contract quirk.

However, whether funds are *actually* misdelivered (rather than the NEAR transaction/cross-contract call reverting) depends on how the on-chain token contract (`plasma.omft.near`) and the named `auroraEngineContractId` contract process the resulting `ft_withdraw`/`ft_transfer_call`+`ft_on_transfer` sequence — e.g., whether an unrecognized token/contract combination panics and NEAR's promise-refund semantics roll back the transfer, or whether it silently succeeds and credits an unintended NEAR/EVM account. That on-chain behavior lives in `intents.near`/`omft`/Aurora Engine contracts, which are explicitly out of scope per the rules ("defects inside intents.near, bridge contracts... with no path through this repo"). I could not trace or verify that on-chain behavior from this repo alone, so I cannot confirm that funds are irrecoverably misdelivered without throwing — only that the SDK constructs and signs an intent with attacker-controlled `receiver_id`/`msg` without any repo-level legitimacy check, and unconditionally reports `"completed"` regardless of the real outcome.

### Impact Explanation
If the downstream contracts do accept the mismatched combination (which this repo cannot control or verify), the signed intent moves the user's own funds to a `receiver_id` chosen by the caller/integrator-forwarded `routeConfig`, not validated against the asset's real bridge — and the SDK reports `"completed"` unconditionally via `describeWithdrawal`, which is a status-misreport regardless of on-chain outcome. This matches "funds delivered to a wrong address/chain/contract" (Critical) if on-chain acceptance occurs, or at minimum "a status... misreport" (High) since `describeWithdrawal` never verifies the withdrawal's actual landing status. The party affected is the same unprivileged caller who chose the mismatched `routeConfig`/`assetId` pair, or an integrator who blindly forwards attacker-controlled `assetId`/`routeConfig` strings from an untrusted counterparty into `processWithdrawal`.

### Likelihood Explanation
Preconditions are trivial and entirely reachable by an unprivileged caller: construct `routeConfig: createVirtualChainRoute(auroraEngineContractId, proxyTokenContractId)` with any `assetId` of NEP-141 standard, no on-chain state or special privilege is required to reach `AuroraEngineBridge` inside this SDK. The uncertain part is purely what the *downstream* NEAR contracts do with the resulting `ft_withdraw` call — which this repo cannot enforce and which I could not verify from the code available here.

### Recommendation
In `AuroraEngineBridge.supports()`/`validateWithdrawal()` (`aurora-engine-bridge.ts`), validate that `assetId`'s token contract is actually registered/bridged by the specified `auroraEngineContractId` (e.g., via an on-chain registry lookup or a static allow-list keyed by `envConfig`), rejecting combinations where the caller-supplied `auroraEngineContractId`/`proxyTokenContractId` doesn't match the asset's real custodian. Additionally, make `describeWithdrawal` verify the actual NEAR/virtual-chain execution outcome (e.g., inspect the NEAR receipt for the `ft_withdraw`/`ft_on_transfer` result) instead of unconditionally returning `"completed"`.
