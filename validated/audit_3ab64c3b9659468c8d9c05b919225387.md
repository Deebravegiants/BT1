### Title
Webhook `shop` (and `topic`/`webhook-id`/`api-version`) identity fields are not covered by the HMAC signature, enabling cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies an inbound webhook solely by checking that `x-shopify-hmac-sha256` matches a signature computed over the raw request body. The `shop`, `topic`, `webhook-id`, and `api-version` values used to build the `WebhookMetadata` passed to the app's handler come from HTTP headers that are never included in the signed payload. Any party that can obtain one valid `(raw_body, hmac)` pair signed with the app's shared `api_secret_key` — trivially available to anyone who installs the app on their own store and receives a legitimate webhook — can replay that exact body/HMAC pair while swapping the `x-shopify-shop-domain` (and other) headers to point at a different, victim shop. The HMAC check still passes because it never covered those fields, and the handler is invoked believing the event legitimately originates from the victim shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are read straight from attacker-controllable HTTP headers with no cryptographic binding to the signature: [2](#0-1) 

`HmacValidator.validate` only recomputes and compares the signature over `to_signable_string` (i.e., the raw body): [3](#0-2) 

`Registry.process` relies exclusively on that HMAC check before constructing `WebhookMetadata` from the unverified headers and dispatching it to the app-registered handler: [4](#0-3) 

Because the `api_secret_key` used to sign webhooks is shared across every shop that installs the app (it is not per-shop), a signature that is valid for shop A's webhook body is *also* a valid signature for the exact same bytes claimed to originate from shop B — the signature proves only "signed by this app's secret," not "for this specific shop." This breaks the intended identity binding: `shop header used by the handler == shop that actually produced/is bound to the signed bytes` is not enforced; the check only proves `bytes verified == bytes parsed`, not that the claimed `shop` (or `topic`/`webhook_id`) is authentic.

### Impact Explanation
An attacker who legitimately installs the target app on their own (attacker-controlled) shop can capture a real webhook delivery — a valid `raw_body` + `x-shopify-hmac-sha256` pair signed with the app's shared secret. They can then replay that identical body/signature to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header (and optionally `topic`/`webhook-id`) with a victim shop's domain. The library will accept it as authentic and hand `WebhookMetadata` with the forged `shop` to the host application's handler, which typically uses `shop` to look up/act on that tenant's local records (e.g. applying an `orders/create`, `app/uninstalled`, or `customers/redact` payload against the wrong tenant). This is a cross-tenant data-integrity/action forgery: the app cannot distinguish "signed for shop A" from "signed for shop B" using this gem's verification.

### Likelihood Explanation
Likelihood is high for any attacker willing to install the target Shopify app on their own store (a normal, unprivileged action for a public/listed app) in order to harvest one signed webhook payload, then replay it with a modified shop header at the app's public webhook endpoint.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the value that is verified — e.g., include `shop`, `topic`, and `webhook_id` header values in the HMAC-covered signable string (matching what Shopify actually signs, if it differs), or require the host application to cross-check the `shop` in `WebhookMetadata` against an already-established, independently-verified session/subscription record before trusting it. At minimum, document prominently that `WebhookMetadata#shop` is not cryptographically bound by `Registry.process`'s HMAC check and must be validated by the consuming application against known installed shops.

### Proof of Concept
```ruby
# 1. Attacker installs the app on their own shop "attacker.myshopify.com"
#    and receives a legitimate webhook, capturing:
raw_body = '{"id":123,"note":"legit order"}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), api_secret_key, raw_body)
headers_attacker = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac),
  "x-shopify-shop-domain" => "attacker.myshopify.com",
}
# HMAC passes for attacker's own shop as expected.

# 2. Attacker replays the identical raw_body + hmac to the app's public
#    webhook endpoint, but swaps the shop header to a victim tenant:
headers_forged = headers_attacker.merge("x-shopify-shop-domain" => "victim.myshopify.com")

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers_forged)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate only checks raw_body signature (unchanged), so it PASSES.
# => Handler receives WebhookMetadata(shop: "victim.myshopify.com", topic: "orders/create", body: ...)
#    and the host app processes the forged event as if it came from the victim shop.
```
