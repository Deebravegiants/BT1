Confirmed: `Webhooks::Request#to_signable_string` returns only `@raw_body`, while `shop`, `topic`, and `webhook_id` are read straight from HTTP headers with no HMAC coverage. `Registry.process` validates only the HMAC over the body, then trusts `request.shop`/`request.topic` for dispatch.### Title
Webhook shop/topic identity spoofing via HMAC scope gap — ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw body only, while the `shop`, `topic`, and `webhook_id` values that `Registry.process` uses to dispatch and attribute the webhook are read straight from HTTP headers that are never covered by the HMAC. This breaks the identity binding: `hmac == HMAC(body)` is verified, but `shop_acted_on == shop_authenticated_by_hmac` is never enforced.

### Finding Description
`Webhooks::Request#to_signable_string` returns `@raw_body` exclusively: [1](#0-0) 

Meanwhile `shop`, `topic`, and `webhook_id` are extracted from headers (`shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`) with no cryptographic tie to the signed payload: [2](#0-1) 

`Registry.process` validates only the HMAC over the body, then unconditionally trusts `request.shop` and `request.topic` to route and attribute the event: [3](#0-2) 

`Utils::HmacValidator.validate` confirms nothing more than that the `hmac` matches `to_signable_string` (i.e., the body) under the configured secret: [4](#0-3) 

Because `shop`, `topic`, and `webhook_id` sit outside the signed scope, any party capable of submitting an HTTP POST to the app's webhook endpoint with a **previously observed, validly-signed body** (e.g., a webhook delivered to their own installed shop, which they legitimately receive with a correct HMAC) can resubmit that same body while substituting an arbitrary `shopify-shop-domain` and/or `shopify-topic` header. `Registry.process` will still consider the HMAC valid (it only checks the body) and will hand the forged `shop`/`topic` values to the registered handler as authoritative identity metadata (`WebhookMetadata#shop`, `#topic`). This is precisely the "field acted on but not covered by the HMAC" identity-binding break: the equality that should hold — `shop_used_for_dispatch == shop_that_produced_the_signed_bytes` — does not.

### Impact Explanation
An attacker who operates their own shop with the vulnerable app installed (an unprivileged, low-cost position — no leaked credentials or `api_secret_key` needed) legitimately receives HMAC-valid webhook deliveries for their own shop. By replaying that exact body against the app's webhook endpoint with a forged `shop-domain` header naming a different tenant, they can make the host application process/attribute that data as belonging to another merchant's tenant — a cross-tenant data-integrity violation reachable purely through this gem's own trust boundary (the gem asserts "HMAC valid" as a proxy for "this event, including shop and topic, is authentic," which is false). This satisfies the Critical impact bar of cross-tenant access via a boundary this gem itself is responsible for enforcing (webhook authenticity), not merely a host-application misuse of a documented API.

### Likelihood Explanation
Moderate-to-high: no secret material is required, only a legitimate install with normal webhook traffic on the attacker's own store (attacker fully controls when/what events fire, e.g., trigger low-value webhook topics repeatedly) and the ability to send arbitrary POST requests with custom headers to the app's public webhook endpoint (a standard capability for any internet client). The `topic`/`webhook_id` values are also unauthenticated, widening the confusion (mismatched topic vs. handler).

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signable string (or otherwise cryptographically bind them, e.g., by validating them against Shopify's expected format/registration and rejecting mismatches), so `HmacValidator.validate` authenticates the full identity tuple the handler acts on, not just the body bytes.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and receives a genuine webhook: body `B`, headers `shopify-shop-domain: attacker-shop.myshopify.com`, `shopify-topic: orders/create`, `shopify-hmac-sha256: H` (valid HMAC of `B`).
2. Attacker resends the identical body `B` and `H` to the same endpoint but with `shopify-shop-domain: victim-shop.myshopify.com`.
3. `Webhooks::Request.new` parses headers/body; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `HMAC(B) == H`: [5](#0-4) 
4. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and processes attacker-controlled body content as if it originated from the victim shop.

          received_signature = verifiable_query.hmac
