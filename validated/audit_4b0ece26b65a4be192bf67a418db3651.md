### Title
Webhook `shop` (tenant) identifier is not covered by the HMAC signature, allowing cross-tenant impersonation - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from unauthenticated headers and passed to the app's `WebhookHandler#handle` via `WebhookMetadata`. The HMAC that authenticates the webhook request never binds these header values, so the tenant-identifying `shop` field is not covered by the signature that is supposed to prove the request is legitimate.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
returning only `@raw_body`. Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are parsed straight out of HTTP headers with no relation to the signed payload: [2](#0-1) 

`Registry.process` validates the HMAC over `to_signable_string` (i.e., body only) and then forwards `request.shop` unchanged into `WebhookMetadata`, which is the only tenant identifier the host application's handler receives: [3](#0-2) [4](#0-3) 

The binding that should hold is: `HMAC-verified bytes == bytes that determine the tenant (shop)`. Here that equality is broken — `hmac == HMAC(body)`, but `shop` (the tenant boundary) is taken from an independent, unsigned header (`shopify-shop-domain` / `x-shopify-shop-domain`). The `HmacValidator.validate` call only proves the body/payload was signed with `Context.api_secret_key`; it says nothing about which shop that body belongs to: [5](#0-4) 

Because all apps built on a given platform share the same `api_secret_key` per-app (not per-shop) — every merchant's genuine webhook for a given app is signed with the identical secret — a party that legitimately receives one valid `(body, hmac)` pair for their own shop can replay that exact body/hmac pair while substituting the `shopify-shop-domain` header for a different (victim) shop domain. `HmacValidator.validate` will still pass because it only checks the body against the secret, not the header. `Registry.process` then hands the handler a `WebhookMetadata` claiming the victim shop, `data.shop`, causing the host application's handler logic (which typically uses `data.shop` to look up/act on the corresponding merchant's session or data) to operate against the wrong tenant.

### Impact Explanation
This breaks the tenant identity binding at the point where the gem hands verified data to the application: the app is told "this event is authenticated and belongs to shop X" when in fact only the body bytes were authenticated, not the shop. Any host application that uses `WebhookMetadata#shop` (as documented/intended) to select which merchant's session/access token to act on can be tricked into cross-tenant data exposure or cross-tenant actions triggered by an attacker-controlled webhook delivery claiming to be from a different shop. This matches the Critical "cross-tenant access" impact category, since it lets one shop's traffic be misattributed to another shop's tenant context without any privileged credential.

### Likelihood Explanation
Exploitation requires the ability to deliver an HTTP request to the app's webhook endpoint with attacker-chosen headers and a body/HMAC pair the attacker legitimately possesses (e.g., from their own shop's webhook deliveries, which is not a privileged secret). No access token, `api_secret_key`, or admin privilege is needed — only the ability to send an HTTP POST with a modified `shop-domain` header, since the gem does nothing to bind that header to the signed payload.

### Recommendation
Include the tenant-identifying fields (`shop`, and ideally `topic`) in the HMAC-covered signable string, or otherwise require the host application to independently verify that the `shop` header corresponds to a known/installed shop before trusting `WebhookMetadata#shop`. At minimum, `Webhooks::Registry.process` should not forward unauthenticated header-derived shop values as if they were verified by the HMAC check.

### Proof of Concept
1. App receives a legitimate webhook for shop `attacker-shop.myshopify.com` with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC(api_secret_key, B)`.
2. Attacker resends the identical `B`/`H` to the same webhook endpoint but changes the header `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(api_secret_key, B)` and compares to `H` — this still matches because the body `B` (the only signed data) is unchanged: [1](#0-0) [6](#0-5) 
4. `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` with `shop == "victim-shop.myshopify.com"` and dispatches it to the app's handler as an authenticated event for that shop: [3](#0-2) 
5. The handler, trusting `data.shop` as verified (per the gem's HMAC check), performs actions/lookups scoped to `victim-shop.myshopify.com` using attacker-controlled `body` content.
