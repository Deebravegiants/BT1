### Title
Missing Host/Origin Header Validation on Gateway User-Facing HTTP Server Enables DNS-Rebinding-Style Request Forgery - (File: core/services/gateway/network/httpserver.go)

### Summary
The Chainlink Gateway's user-facing HTTP server (`httpServer.handleRequest`) never validates the `Host` header of incoming requests, and by default (`CORSEnabled = false` per `core/scripts/gateway/sample_config.toml`) it performs no Origin validation at all before dispatching the raw request body to `s.handler.ProcessRequest`. This mirrors the Apollo MCP Server CVE-2026-35577 root cause: a StreamableHTTP-style local server that trusts any incoming connection's declared identity (Host/Origin) without validation, making it susceptible to DNS-rebinding attacks from a malicious webpage when bound to localhost or an internal interface without additional network controls.

### Finding Description
`httpServer.handleRequest` in [1](#0-0)  only performs Origin checks when `CORSEnabled` is true, and that check is scoped strictly to setting CORS response headers and short-circuiting `OPTIONS` preflight requests — it does not reject non-OPTIONS requests whose `Origin` fails `isAllowedOrigin`. When `CORSEnabled` is false, which is the default in the shipped sample configuration [2](#0-1) , there is no Origin or Host validation whatsoever — the server reads the body and forwards it straight to the configured handler's `ProcessRequest`: [3](#0-2) 

Critically, even in the `CORSEnabled=true` branch, a request lacking a matching `Origin` header (e.g., a raw `fetch()`/XHR request, or a DNS-rebound request where the browser still sends its true `Origin` but a rebound `Host`) still falls through to `ProcessRequest` — the code never blocks the request, it only omits the CORS response headers. Browsers making simple (non-preflighted) requests can still successfully execute cross-origin POSTs against this endpoint, and there is no server-side check on the `Host` header comparing it to an expected bound hostname, unlike the pattern implemented in the core web UI router's `secureMiddleware`/host-validation for the main web server (`core/web/router.go`). The Gateway's user API is precisely the internet-facing gateway surface referenced by this bug class: it accepts arbitrary JSON-RPC message envelopes from unprivileged clients and routes them by `Method` to handlers such as the capabilities `webAPITrigger`/`webAPITarget` handler and the Vault gateway handler.

### Impact Explanation
Because the HTTP transport layer performs no binding-based authentication, any downstream authorization is left entirely to the JSON-RPC message content and per-handler logic (e.g., HMAC/allowlist checks inside `HandleLegacyUserMessage`/handler-specific authorizers). If a Gateway user-server instance is deployed on localhost or an internal, unauthenticated interface (a supported and documented configuration, as shown by the sample config having no auth around `UserServerConfig`), a malicious website visited by an operator's browser could use DNS rebinding to resolve an attacker domain to the loopback/internal address after the browser's same-origin check, then issue arbitrary POST requests carrying attacker-controlled JSON-RPC payloads to the Gateway's `/user` path. Depending on which handler is registered for the DON/service, this could result in unauthorized triggering of `MethodWebAPITrigger` workflows, submission of Vault secret operations, or other privileged JSON-RPC calls the handler would otherwise expect only from trusted callers, effectively bypassing intended network-boundary trust assumptions.

### Likelihood Explanation
Exploitation requires the Gateway user-server to be reachable by a victim's browser (bound to localhost/LAN without VPN/firewall isolation) and requires the victim to visit an attacker-controlled page while the DNS rebinding attack resolves to the target's address — consistent with the CVSS 6.8/AC:H/UI:R rating of the referenced CVE. The Gateway is documented and designed to often run alongside/adjacent to nodes, and the default sample config ships with `CORSEnabled=false`, so no additional configuration change is needed to be exposed to this gap; the mitigating factor is that actual impact depends on what the registered handler does with unauthenticated request bodies.

### Recommendation
Add explicit `Host` header validation to `httpServer.handleRequest` (compare `r.Host` against an expected bound hostname/allowlist, rejecting mismatches with 400/403), and change the CORS/Origin logic so that when `CORSEnabled` is true (or a stricter mode is added), requests with a non-empty `Origin` header that fails `isAllowedOrigin` are rejected outright rather than merely omitting CORS headers. Additionally, consider requiring authentication for the user-facing Gateway endpoint by default, and document/enforce that the server should not be bound to permissive interfaces without such protections — analogous to the fix shipped in Apollo MCP Server 1.7.0.

### Proof of Concept
1. Deploy the Gateway with `UserServerConfig.CORSEnabled = false` (default per `sample_config.toml`) bound to `127.0.0.1:8080`.
2. From an attacker-controlled webpage visited by the operator, perform DNS rebinding so `evil.example.com` resolves to `127.0.0.1`.
3. Issue a cross-origin `fetch('http://evil.example.com:8080/user', {method:'POST', body: <jsonrpc envelope>})` from the malicious page.
4. Because `handleRequest` performs no Host validation and (with CORS disabled) no Origin validation, the raw body is passed to `s.handler.ProcessRequest`, and if the underlying JSON-RPC method/handler does not independently authenticate the caller, the forged request is processed as if it came from a legitimate local client. func (s *httpServer) handleRequest(w http.ResponseWriter, r *http.Request) {
```go
	if s.config.CORSEnabled {
		origin := r.Header.Get("Origin")
		if s.isAllowedOrigin(origin) {
			w.Header().Set("Access-Control-Allow-Origin", origin)
			w.Header().Set("Access-Control-Allow-Methods", "GET, POST, OPTIONS")
			w.Header().Set("Access-Control-Allow-Headers", "Content-Type")
		}

		// handle preflight requests
		if r.Method == http.MethodOptions {
			w.WriteHeader(http.StatusNoContent)
			return
		}
	}

	maxRequestBytes, err := s.config.MaxRequestBytesLimiter.Limit(r.Context())
	if err != nil {
		msg := "Failed to get request size limit"
		s.lggr.Errorw(msg, "err", err)
		http.Error(w, msg, http.StatusInternalServerError)
		return
	}
	source := http.MaxBytesReader(nil, r.Body, int64(maxRequestBytes))
	rawMessage, err := io.ReadAll(source)
	if err != nil {
		s.lggr.Error("error reading request", err)
		w.WriteHeader(http.StatusBadRequest)
		return
	}

	// Optionally extract jwt token from authorization header
	authHeader := r.Header.Get("Authorization")
	jwtToken := ""
	if authHeader != "" {
		jwtToken = strings.TrimPrefix(authHeader, "Bearer ")
	}

	startTime := time.Now()
	rawResponse, httpStatusCode := s.handler.ProcessRequest(r.Context(), rawMessage, jwtToken)
```
