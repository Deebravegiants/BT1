### Title
Webhook shop-domain identity is not covered by HMAC, allowing cross-tenant webhook forgery via replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so `Utils::HmacValidator.validate` only proves that `raw_body` was signed with the app's `api_secret_key` — it says nothing about which shop the webhook is "for." `Registry.process` nonetheless takes the tenant identity (`request.shop`) straight from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` header and hands it to the app's `WebhookHandler` as trusted tenant context.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
and `shop`, `topic`, `api_version`, and `webhook_id` are all pulled from headers that are never mixed into that signable string: [2](#0-1) 

`HmacValidator.validate` computes the HMAC purely over `to_signable_string` (i.e., the body bytes) and compares it to the `hmac` header: [3](#0-2) 

`Registry.process` then trusts the header-derived `request.shop` for tenant attribution once the body HMAC checks out: [4](#0-3) 

The binding that should hold is: `shop-domain-authenticated == shop-domain-used-for-tenant-dispatch`. Because `shop-domain` is not part of the signed bytes, that equality is not enforced by this gem — only the body content is authenticated, not the (topic, shop, api_version, webhook_id) tuple that `WebhookMetadata` exposes to the handler.

### Impact Explanation
An attacker who legitimately installs the target app on their own store (or otherwise obtains one genuine `(raw_body, hmac)` pair issued by Shopify for the app's secret) can replay that exact body/HMAC to the app's webhook endpoint while substituting the `shopify-shop-domain` (and `topic`/`webhook-id`) headers to point at a victim shop. `HmacValidator.validate` still returns `true` because it only checks the body, and `Registry.process` will invoke the app's handler with `WebhookMetadata.shop` set to the victim's domain. This is a cross-tenant data/event injection: the host application's handler will act on the victim shop's identity using attacker-controlled body content, which can corrupt per-tenant state (e.g., false `shop/redact` or `app/uninstalled` events, forged order/customer webhooks attributed to the wrong merchant).

### Likelihood Explanation
Requires no possession of the app's `api_secret_key` — only a legitimately obtained genuine webhook (as any real merchant installing the app would produce) that is then replayed with modified headers, which is achievable by any unprivileged internet user who can install the app once. Likelihood is moderate: it depends on the app's webhook endpoint accepting raw HTTP requests directly (typical for Rack apps using this gem) and on the handler trusting `WebhookMetadata.shop` without independent shop verification (which the gem's own docs/API implies is unnecessary since "the HMAC was already validated").

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the signed payload verification path, or explicitly document/require that `Registry.process` callers verify `request.shop` against an expected/registered shop before trusting it, rather than passing the raw header value straight into `WebhookMetadata` after only a body-HMAC check.

### Proof of Concept
1. Install the target app on attacker-owned shop `attacker.myshopify.com`; capture one legitimate webhook POST (raw body + `shopify-hmac-sha256` + `shopify-shop-domain: attacker.myshopify.com`) delivered by Shopify.
2. Replay the identical body and HMAC header to the app's webhook endpoint, but change `shopify-shop-domain` to `victim.myshopify.com` (and, if desired, `shopify-topic`/`shopify-webhook-id`).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `raw_body` against the HMAC [5](#0-4) .
4. The registered handler is invoked with `WebhookMetadata.new(... shop: "victim.myshopify.com" ...)` [6](#0-5) , causing the host app to process attacker-supplied data under the victim tenant's identity.

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
