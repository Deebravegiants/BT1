### Title
Webhook shop attribution is not covered by the HMAC signature, allowing cross-tenant shop-spoofing of webhook payloads - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` (and `topic`, `api_version`, `webhook_id`) that is handed to the app's webhook handler entirely from unauthenticated HTTP headers, while the HMAC signature that `Registry.process` verifies only covers the raw request body. This breaks the identity binding `shop-attribution-used-by-handler == shop-that-produced-the-signed-body`, letting anyone who can obtain one validly-signed webhook body (e.g. from their own shop's installation of the app) replay it with a forged `X-Shopify-Shop-Domain` header to make the app believe the payload originated from a different (victim) shop.

### Finding Description
`Utils::HmacValidator.validate` computes the HMAC purely over `verifiable_query.to_signable_string` and compares it to the `hmac` field: [1](#0-0) 

For webhooks, `to_signable_string` is defined as just the raw body, and `hmac` is read from the `hmac-sha256` header — but `shop`, `topic`, `webhook_id`, and `api_version` are all pulled from separate headers that are never mixed into the signed string: [2](#0-1) 

`Registry.process` validates only this body-HMAC, then trusts `request.shop` (and the other header-derived fields) verbatim when building the object passed to the app's handler: [3](#0-2) 

Crucially, the webhook signing secret is the app's `client_secret`, which is identical for every shop that has installed the app — it is not shop-specific. That means a valid `(raw_body, hmac)` pair obtained from a webhook legitimately delivered for shop A (e.g. an attacker's own test store) remains a cryptographically valid pair regardless of which shop-domain header is attached to it. Since the shop header is outside the HMAC's scope, an attacker can pair a validly-signed body with the `Shopify-Shop-Domain` header of an arbitrary victim shop, and `HmacValidator.validate` will still return `true`. This is the same class of bug as the reported issue: a field that downstream logic acts on (proposal/anchor timestamp there, shop attribution here) is not covered by the check that is supposed to bind it (the reward-period timestamp check there, the HMAC there here), so an attacker can supply/replay an unrelated value that still passes verification.

### Impact Explanation
This crosses a tenant boundary: the app relying on this gem's `ShopifyAPI::Webhooks::Registry.process` receives webhook data with an attacker-controlled `shop` value despite a "valid" HMAC check. Any app logic keyed off `WebhookMetadata#shop` (e.g., looking up/mutating the victim's stored session, access token, or shop-scoped records; triggering shop-scoped side effects such as data deletion for `customers/redact` or `shop/redact`) can be tricked into acting against the wrong tenant. This is a cross-tenant access/confusion vulnerability stemming directly from this gem's verification logic.

### Likelihood Explanation
The precondition (owning any shop that installs the target app, or otherwise obtaining one legitimately-signed webhook delivery) is realistic for a public/embeddable app — it does not require any leaked secret, TLS interception, or privileged account, since the "attacker" is simply an ordinary merchant/tenant of the same app. Forging headers on a raw HTTP replay to the app's own configured webhook endpoint requires no special access.

### Recommendation
Bind the shop (and other routing metadata) to the signed content, e.g. by including `shop`, `topic`, and `webhook_id` in `to_signable_string`, or by requiring the consuming app to independently verify that the shop asserted in the header matches a shop known to have that webhook subscription/topic combination, rather than trusting the header outright once the body-only HMAC passes.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and registers a webhook topic.
2. Shopify delivers a webhook to the app's endpoint with headers `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`, and some `raw_body`.
3. Attacker intercepts/replays this exact `(raw_body, hmac)` pair to the same endpoint but rewrites the header to `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers (only presence, not per-shop binding, is checked) and `Utils::HmacValidator.validate(request)` returns `true` because the HMAC only ever covered `raw_body`.
5. `Registry.process` invokes the app's handler with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)`, causing the app to process attacker-supplied data as if it came from the victim shop.
