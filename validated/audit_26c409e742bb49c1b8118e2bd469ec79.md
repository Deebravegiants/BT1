The claim is confirmed by direct code inspection: the `email` claim extraction at line 226-230 lacks a `return` statement after the error branch, unlike every other error path in the function. This is a real, verifiable bug.

Audit Report

## Title
Missing `return` after failed email-claim extraction lets OIDC login succeed and create an authenticated session with an empty email - (File: core/sessions/oidcauth/oidc.go)

## Summary
In `handleTokenExchange`, the type assertion `claims["email"].(string)` failure branch writes an error response via `c.String(...)` but does not call `return`, unlike all other error branches in the same function. Execution falls through, computes the RBAC role from `idClaims`, inserts a session row into `oidc_sessions` with `user_email = ""`, sets the session cookie, and returns a `200 OK` success body.

## Finding Description
Every other failure branch in `handleTokenExchange` returns immediately after writing an error response, e.g. the `id_token` extraction check and the `Verify`/`Claims`/`ExtractIDClaimValues` checks all end with `return`. [1](#0-0) 

The email extraction check omits the `return`: [2](#0-1) 

Because `c.String` does not abort a gin handler, execution proceeds to role mapping, `INSERT INTO oidc_sessions` with `strings.ToLower(email)` (empty string when the assertion fails), audit logging with the empty email, `ginSession.Set(...)`, `ginSession.Save()`, and finally a `200 OK` `{"success":true}` response that is appended after the earlier `500` body write: [3](#0-2) 

`AuthorizedUserWithSession` later trusts the DB row's `user_email`/`user_role` without further validation, so the resulting session cookie is fully authenticated for whatever role was derived: [4](#0-3) 

The same fall-through pattern exists at the `oidc_sessions` INSERT error branch, which also lacks a `return`. [5](#0-4) 

## Impact Explanation
This produces a valid, cookie-backed authenticated session with a role derived from group/ID claims but an empty/garbage `user_email`. This maps to node API authentication/session-integrity bypass: a session is created and considered valid by `AuthorizedUserWithSession` despite the identity assertion failing, and empty-email sessions collide in operations keyed on `user_email` (e.g. `ClearNonCurrentSessions`), producing cross-user session confusion and broken audit traceability. This is a legitimate in-scope impact class (authentication bypass / cross-user response corruption), though the resulting user's role and empty email is still constrained by valid group claims from the same signed token.

## Likelihood Explanation
The trigger requires the OIDC provider to return a validly-signed ID token whose claims map lacks a well-formed `email` field (missing, wrong type) while still containing usable group/role claims — an IdP misconfiguration/edge case reachable through the standard, unauthenticated `/oidc-login` → `/exchange` flow, not requiring any elevated privilege to initiate the request itself.

## Recommendation
Add `return` immediately after the `c.String(http.StatusInternalServerError, "Failed to get email from claims")` call so the handler aborts on failed email extraction, consistent with all other error branches in this function. Apply the same fix to the `oidc_sessions` INSERT error branch to prevent session cookie issuance on DB failure.

## Proof of Concept
1. Stand up a mock OIDC provider returning a validly signed ID token whose claims include a valid `groups`/role claim but omit `email` (or set it to a non-string, e.g. a number).
2. Complete `/oidc-login` to obtain `state`, then POST `code`/`state` to the `/sessions/exchange` handler (`handleTokenExchange`).
3. Observe: response body is a mangled write (`500` text followed by `200 {"success":true}` JSON) and a valid session cookie is set.
4. Inspect `oidc_sessions` table: a row exists with `user_email = ''` and `user_role` set to the mapped role.
5. Use the returned cookie against an authenticated endpoint and confirm it is accepted by `AuthorizedUserWithSession`, proving a session was created despite the failed email-claim check.

// AuthorizedUserWithSession will return the API user associated with the Session ID if it
// exists and hasn't expired
func (oi *oidcAuthenticator) AuthorizedUserWithSession(ctx context.Context, sessionID string) (clsessions.User, error) {
	if len(sessionID) == 0 {
		return clsessions.User{}, errors.New("session ID cannot be empty")
	}
	var foundUser clsessions.User
	err := sqlutil.TransactDataSource(ctx, oi.ds, nil, func(tx sqlutil.DataSource) error {
		// Query the oidc_sessions table for given session ID, user role and email are saved after the id claims is provided and validated
		var foundSession struct {
			UserEmail string
			UserRole  clsessions.UserRole
			Valid     bool
		}
		if err := tx.GetContext(ctx, &foundSession,
			"SELECT user_email, user_role, created_at + $2 >= now() as valid FROM oidc_sessions WHERE id = $1",
			sessionID, oi.config.SessionTimeout().Duration(),
		); err != nil {
			if errors.Is(err, sql.ErrNoRows) {
				return clsessions.ErrUserSessionExpired
			}
			return err
		}
		if !foundSession.Valid {
			// Sessions expired, purge
			return clsessions.ErrUserSessionExpired
		}
		foundUser = clsessions.User{
			Email: foundSession.UserEmail,
			Role:  foundSession.UserRole,
		}
		return nil
	})
	if err != nil {
		if errors.Is(err, clsessions.ErrUserSessionExpired) {
			if _, execErr := oi.ds.ExecContext(ctx, "DELETE FROM oidc_sessions WHERE id = $1", sessionID); execErr != nil {
				oi.lggr.Errorf("error purging stale OIDC session: %v", execErr)
			}
		}
		return clsessions.User{}, err
	}
	return foundUser, nil
}
