### Title
Creator fee balances in `FeeVault` become permanently frozen if the creator address is blacklisted by USDC, with `transferCreator` unable to rescue already-accrued balances - (File: `packages/contracts/src/FeeVault.sol`)

### Summary
`FeeVault.claim()` pays out a creator's entire pooled USDC balance by hardcoding the recipient to `msg.sender`, with no way to redirect the payout to an alternate address. [1](#0-0) 

If USDC (the fee asset) ever blacklists a creator's address, `usdc.safeTransfer(msg.sender, amount)` reverts unconditionally and that creator's entire accrued fee balance is permanently unrecoverable, matching the External Report's "recipient gets blacklisted" bug class.

### Finding Description
`FeeVault` accrues creator fees keyed by the `creator` address supplied by `Bonding` at accrual time: [2](#0-1) 

`creatorBalance[creator]` is a mapping the creator can only drain through `claim()`, which transfers to `msg.sender` with no beneficiary parameter and no admin override: [1](#0-0) 

The natural mitigation would be `Bonding.transferCreator`, which lets a creator reassign the `creator` field on `TokenInfo` for future fee attribution: [3](#0-2) 

However, `transferCreator` only updates `Bonding`'s `tokenInfo[tokenAddress].creator`, which changes *future* `accrue()` attribution. It does **not** touch `FeeVault.creatorBalance[oldCreator]`, and `FeeVault` exposes no function to move an existing balance from one creator address to another. So any USDC already accrued to a blacklisted creator address remains permanently stuck: `claim()` will always revert for that address (blacklist blocks the outbound `safeTransfer`), and there is no other withdrawal path in `FeeVault` for that specific creator's balance.

This is asymmetric with the protocol side: `claimProtocol()` pays a mutable, owner-controlled `feeTo` address, which the owner can rotate away from a blacklisted address via `setFeeTo` before claiming: [4](#0-3) [5](#0-4) 

No equivalent rescue mechanism exists for creators.

### Impact Explanation
Any USDC already accrued to a creator address that gets blacklisted by the USDC issuer becomes permanently frozen inside `FeeVault` — it cannot be claimed by that address, and no other address (including the creator via `transferCreator`, or the vault owner) can redirect or recover the specific `creatorBalance[creator]` entry. This is a permanent freezing of trader/creator funds, consistent with Medium severity per the report's own framing (low probability of blacklisting, but zero recovery path once it occurs).

### Likelihood Explanation
Requires the reserve fee asset (USDC) to add the creator's address to a blacklist — a low-probability but realistic event given USDC's built-in blacklist capability. Once it happens, the freeze is deterministic and total for that creator's balance, with no privileged or unprivileged action able to unstick it.

### Recommendation
Add a way for a creator to redirect their `FeeVault` balance to a different address, either by (a) allowing `claim(address to)` restricted to the creator calling for themselves, or (b) letting `Bonding.transferCreator` (or a new `FeeVault` function) migrate `creatorBalance[oldCreator]` to `newCreator` atomically when creator attribution changes, so a blacklisted creator can reassign both future attribution and already-accrued balance to a fresh address.

### Proof of Concept
1. `Zap` accrues creator fees via `FeeVault.accrue(token, creator, creatorAmount, protocolAmount, isBuy)` on every buy/sell as described in `docs/contracts-scope.md` — `creatorBalance[creator]` grows over time.
2. The creator's address is added to USDC's blacklist by the USDC issuer (external event, out of protocol's control).
3. Creator calls `Bonding.transferCreator(tokenAddress, newCreator)` hoping to redirect fees — this only updates `tokenInfo[tokenAddress].creator` for *future* accruals in `Bonding.sol` lines 738-748.
4. Creator (or anyone on their behalf) calls `FeeVault.claim()` — `usdc.safeTransfer(msg.sender, amount)` reverts because `msg.sender` (the old, blacklisted creator) is blocked by USDC.
5. `creatorBalance[oldCreator]` remains non-zero forever; no function in `FeeVault.sol` can move or pay out that specific balance to any other address.

        address token,

        if (creatorAmount > 0) {
            if (creator == address(0)) revert ZeroAddress();
            $.creatorBalance[creator] += creatorAmount;
            $.totalAccruedCreator += creatorAmount;
            $.lifetimeCreatorEarned[creator] += creatorAmount;
        }
        if (protocolAmount > 0) {
            $.protocolBalance += protocolAmount;
            $.lifetimeProtocolEarned += protocolAmount;
        }
        if ($.usdc.balanceOf(address(this)) < $.totalAccruedCreator + $.protocolBalance) {
            revert UnderfundedAccrual();
        }
        emit FeeAccrued(token, creator, creatorAmount, protocolAmount, isBuy);
    }

        FeeVaultStorage storage $ = _s();
        amount = $.creatorBalance[msg.sender];
        if (amount == 0) revert NothingToClaim();
        $.creatorBalance[msg.sender] = 0;
        $.totalAccruedCreator -= amount;
        $.usdc.safeTransfer(msg.sender, amount);
        emit CreatorFeesClaimed(msg.sender, amount);
    }

    function transferCreator(
        address tokenAddress,
        address newCreator
    ) external {
        if (newCreator == address(0)) revert ZeroAddress();
        TokenInfo storage info = _s().tokenInfo[tokenAddress];
        if (msg.sender != info.creator) revert NotCreator();
        if (newCreator == info.creator) revert InvalidInput();
        info.creator = newCreator;
        emit CreatorTransferred(tokenAddress, msg.sender, newCreator);
    }
