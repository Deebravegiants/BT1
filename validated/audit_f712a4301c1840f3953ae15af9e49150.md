### Title
Webhook `shop` and `topic` fields are not covered by the HMAC signature, allowing tenant/topic spoofing on webhook delivery - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, so the HMAC verification performed by `ShopifyAPI::Utils::HmacValidator.validate` only proves that `@raw_body` was signed by the app's shared client secret. The `shop-domain`, `topic`, and `api-version` headers are read directly from unauthenticated HTTP headers and handed to the registered webhook handler as trusted values, breaking the intended binding `shop authenticated by HMAC == shop delivered to handler`.

### Finding Description
`ShopifyAPI::Webhooks::Request` exposes `shop`, `topic`, and `api_version` purely from HTTP headers: [1](#0-0) 

But the value actually protected by the HMAC is only the raw body: [2](#0-1) 

`Registry.process` validates the HMAC over the raw body only, then immediately trusts `request.shop` and `request.topic` (both unauthenticated) to route and label the event for the handler: [3](#0-2) 

`HmacValidator.validate` computes the digest solely from `to_signable_string`, i.e., the raw body: [4](#0-3) 

The webhook signing secret (`Context.api_secret_key`) is the app's single client secret, shared across every shop that installs the app — it is not a per-shop secret. This mirrors the report's root cause pattern: a value that participates in identity/authorization decisions (`shop`) is not part of the data actually covered by the cryptographic check (`raw_body`), so the check answers a different question than the one the caller relies on.

### Impact Explanation
Any merchant who installs the app is, from the app's perspective, an "unprivileged internet user" with respect to every other tenant of the same app, yet they receive genuine Shopify-issued webhooks addressed to their own shop, valid HMAC included, because the HMAC key is shared across the whole app. Because `shop-domain` (and `topic`) are excluded from the signed bytes, that merchant can take a legitimate raw-body+HMAC pair from a webhook fired for their own store and resend it to the app's public webhook endpoint with the `shop-domain` header rewritten to any victim shop's domain (and/or the `topic` header rewritten to any topic they have a registered handler for). `Registry.process` will accept the forged request — the HMAC check passes because it only validates the body — and will invoke the host application's handler believing the event originated from the victim shop. This is a cross-tenant identity-binding break: the equality `shop verified by HMAC == shop delivered to handler` does not hold. Depending on what the host app does with webhook data (e.g. updating shop-scoped records, reacting to `app/uninstalled`, processing order/customer data under the spoofed tenant), this enables cross-tenant data confusion/corruption attributable to a spoofed shop identity.

### Likelihood Explanation
Any shop that has installed the app can trigger genuine webhook deliveries to itself (e.g. by performing normal store actions that fire subscribed topics), giving it a valid `(raw_body, hmac)` pair at will, with no special privilege beyond being an app-installing merchant. Rewriting the `X-Shopify-Shop-Domain` header on a replayed HTTP request requires no cryptographic material. This makes the attack straightforward for any tenant of a multi-tenant app built on this gem.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `api-version`, `webhook-id`) values in the signed material verified for a webhook, or independently verify that `request.shop` corresponds to a shop with a currently active/installed session before dispatching to the handler. At minimum, document and enforce that host applications must cross-check the `shop` header against their own tenant/session store rather than trusting it implicitly, and consider extending `to_signable_string` to bind identity-relevant headers as Shopify's HMAC validation contract intends.

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com` and triggers a store action that generates a subscribed webhook (e.g. `products/update`). They capture the raw POST body `B` and the `X-Shopify-Hmac-Sha256` header value `H` from the delivery to their own endpoint.
2. Attacker sends a new HTTP request to the app's public webhook endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` unchanged, but `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the headers/body; `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and succeeds (since `B`/`H` are an untouched, genuinely-signed pair).
4. The handler receives `WebhookMetadata.new(topic:, shop: "victim.myshopify.com", body: parsed(B), ...)`, believing the event came from the victim shop, even though it never occurred there. [3](#0-2)
