Audit Report

## Title
Missing `return` after failed OIDC email-claim extraction allows session creation and HTTP 200 success response with empty `user_email` - (File: core/sessions/oidcauth/oidc.go)

## Summary
In `handleTokenExchange`, after exchanging the OIDC code and verifying the ID token, the code extracts the `email` claim via a type assertion. When the assertion fails (claim missing or non-string), the handler logs an error and writes an HTTP 500 body via `c.String(...)`, but does not call `return`, unlike every other error branch in this function. Execution falls through, mapping the role, inserting a session row with `user_email = ''`, saving the session cookie, and returning HTTP 200 `{"success":true}` to the client.

## Finding Description
The relevant code path is: [1](#0-0) 

Compare this to every other failure branch in the same function, all of which correctly call `return` (e.g. state mismatch, exchange failure, missing `id_token`, verify failure, claims parse failure, role mapping failure): [2](#0-1) [3](#0-2) 

Because `return` is missing after line 229, execution proceeds to role mapping, session persistence with `strings.ToLower(email)` (an empty string), and finally session save and success response: [4](#0-3) 

No existing check, middleware, or validation intercepts this fall-through; the function has no deferred recovery or post-hoc validation of `email` before use. This is a genuine, verifiable code defect exactly as described in the claim. I also note the identical bug pattern exists at the `oidc_sessions` INSERT error branch (lines 257-260), which similarly omits `return` before falling through to `Audit` and session save — this reinforces that the control-flow defect is real and not an isolated one-off.

## Impact Explanation
This results in a session being created and a valid, cookie-backed authenticated session being handed to the client (HTTP 200, `{"success":true}`) with `user_email = ""` persisted in `oidc_sessions`, despite an internal error occurring. The audit log entry (`AuthLoginSuccessNo2FA`) records `email: ""`, degrading the audit trail's ability to attribute the login to a real identity. The `user_role` is still correctly derived from group claims, so a session with a legitimate role (potentially Admin, if the IdP's group claims map that way) is issued but is not tied to a real email identity — this weakens accountability and traceability of privileged sessions, which maps to the node API authentication/session-integrity impact category.

## Likelihood Explanation
This is directly reachable by any unauthenticated client completing the OIDC front-channel flow to `POST .../token-exchange`, provided the ID token or `/userinfo`-derived claims lack an `email` field (e.g., IdP misconfiguration, or an IdP under partial attacker control returning claims without `email` but with valid signature/verification for other reasons). This does not require operator or admin access, database access, or victim interaction — only a client capable of completing a normal OIDC exchange with a claims set lacking `email`. It is a pure control-flow defect, independent of the specific IdP, making it reproducible whenever the precondition (missing `email` claim) is met.

## Recommendation
Add the missing `return` statement immediately after writing the error response in the `email` extraction failure branch:
```go
email, ok := claims["email"].(string)
if !ok {
    oi.lggr.Errorf("Failed to get email from claims")
    c.String(http.StatusInternalServerError, "Failed to get email from claims")
    return
}
```
Also fix the analogous missing `return` after the `oidc_sessions` INSERT error at line 257-260, which has the same defect and would otherwise let a failed session insert be followed by an `Audit` call and a success response referencing a non-existent session row.
