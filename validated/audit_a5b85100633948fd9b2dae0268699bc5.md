### Title
Direct APT transfers to a `liquidity_pairs` pool object are untracked and become permanently unrecoverable after graduation - (File: `aptos-move/move-examples/bonding_curve_launchpad/sources/liquidity_pairs.move`)

### Summary
`liquidity_pairs.move` tracks custody of a bonding-curve pool's APT/FA reserves purely in two state fields, `apt_reserves` and `fa_reserves`, inside the `LiquidityPair` resource [1](#0-0) . These fields are updated only inside `swap_apt_to_fa` / `swap_fa_to_apt`, never reconciled against the actual APT balance held at the pool object's own account address [2](#0-1) . Because that address is a normal on-chain account (derived via `object::create_named_object`/`object::generate_signer`), anyone can send it APT directly with `aptos_account::transfer` or `coin::transfer` outside of the swap entry points, exactly like the reported "direct SOL transfer to escrow" bug-class. Unlike the Solana report, there is no invariant check here that would revert and halt the protocol; instead, the untracked surplus silently persists and — after "graduation" disables all pool functions — becomes permanently stuck with no code path to retrieve it.

### Finding Description
`register_liquidity_pair` creates the pool as an object with its own account (`liquidity_pair_signer`/`liquidity_pair_address`) and stores tracked reserve counters `apt_reserves`/`fa_reserves` [3](#0-2) . All subsequent APT movement in `swap_apt_to_fa` uses `aptos_account::transfer` to move real APT into `liquidity_pair_address`, and then separately updates the `apt_reserves` counter to the value computed by `get_amount_out` [4](#0-3) . Because `liquidity_pair_address` is just a regular account, any external actor can call `aptos_account::transfer`/`coin::transfer` to send it APT directly, entirely bypassing `swap_apt_to_fa`. This APT is now held by the object but is not reflected in `apt_reserves`.

All extraction of the pool's APT is gated exclusively by the tracked `apt_reserves`/`fa_reserves` values: `swap_fa_to_apt` pays out `aptos_account::transfer(&liquidity_pair_signer, swapper_address, apt_gained)` where `apt_gained` derives from `get_amount_out(liquidity_pair.fa_reserves, liquidity_pair.apt_reserves, ...)` [5](#0-4) , and `graduate()` moves only `apt_updated_reserves - 10%` (the tracked value) into the external DEX before permanently disabling the pool by setting `is_enabled = false` [6](#0-5) . Once `is_enabled` is false, `swap_apt_to_fa` reverts on `ELIQUIDITY_PAIR_DISABLED` [7](#0-6) , and `swap_fa_to_apt`/`graduate` are the only other functions capable of moving APT out of the pool's account. There is no exposed function that reconciles or sweeps a surplus balance that exceeds the tracked `apt_reserves`.

This is the same custody-invariant break as the reported issue — a custody-holding account's real balance can diverge from the protocol's internal accounting of that balance because only the swap code path updates the accounting — but the local consequence is different: rather than an invariant assert reverting all swaps (DoS), the excess value is silently absorbed and then permanently orphaned once the pool graduates and disables itself.

### Impact Explanation
Any APT sent directly to the pool object's address (whether before or after threshold/graduation) in excess of the tracked `apt_reserves` is not retrievable by any account, including the pool creator or protocol admin: no privileged sweep, no residual withdrawal, and post-graduation `is_enabled=false` blocks the only functions with authority to move funds out of the pool's signer. This is a permanent, non-recoverable loss of object-held APT, matching the custody impact gate for "permanent lock or non-recoverable loss of object-held ... value."

### Likelihood Explanation
Medium-high: sending APT to a known, computable object address (`get_pair_obj_address` is a `#[view]` function [8](#0-7) ) requires no special privilege — a plain `coin::transfer`/`aptos_account::transfer` from any account. It can happen accidentally (a user mistakenly sending APT to what they believe is a deposit address) or be triggered deliberately to grief a specific pool's economics before graduation.

### Recommendation
Add an explicit reconciliation/sweep mechanism: either (a) have swaps and `graduate()` read the pool's true APT balance (`coin::balance<AptosCoin>(liquidity_pair_address)`) rather than trusting only the `apt_reserves` counter, treating any surplus as part of the reserve, or (b) expose an authorized cleanup entry function that syncs `apt_reserves` to the real balance and/or sweeps any residual balance after `graduate()` to a designated recipient, analogous to the recommended fix in the original report.

### Proof of Concept
1. Observe/derive the pool's object address for a target FA via `liquidity_pairs::get_pair_obj_address(name, symbol)` [9](#0-8) .
2. From any account, call `aptos_account::transfer(attacker, pool_address, extra_apt)` directly — this is a standard framework entry function, not gated by the bonding-curve module.
3. Continue normal swaps until the pool graduates: `swap_apt_to_fa` triggers `graduate()` once `apt_updated_reserves > APT_LIQUIDITY_THRESHOLD` [10](#0-9) ; `graduate()` migrates only the tracked `apt_updated_reserves` amount and sets `is_enabled = false` [11](#0-10) .
4. The `extra_apt` sent in step 2 remains at `pool_address`, untracked by the migrated reserves, and with `is_enabled = false` there is no remaining function in the module capable of moving it out — the funds are permanently stranded.

    fun graduate(
        liquidity_pair: &mut LiquidityPair,
        fa_object_metadata: Object<Metadata>,
        transfer_ref: &TransferRef,
        apt_updated_reserves: u128,
        fa_updated_reserves: u128
    ) {
        // Disable Bonding Curve Launchpad pair and remove global freeze on FA.
