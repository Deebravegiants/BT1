### Title
Webhook shop-domain (and other Shopify headers) are trusted for tenant attribution without being covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a successful `Utils::HmacValidator.validate` call as proof that "the request did indeed come from Shopify" for the *entire* request, including which shop it belongs to. In reality the HMAC only covers the raw JSON body; the `shop`, `topic`, `webhook_id`, and `api_version` values, which come from HTTP headers, are never part of the signed bytes and are handed to the app's handler unauthenticated.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `to_signable_string` as simply the raw body: [1](#0-0) 

and derives `shop`, `topic`, `webhook_id`, `api_version` purely from HTTP headers via `shopify_header`: [2](#0-1) 

`Registry.process` verifies only this body-derived HMAC, then immediately trusts the header-derived `request.shop` (and topic/webhook_id/api_version) to build `WebhookMetadata` passed to the app's handler: [3](#0-2) 

`Utils::HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (the body, for webhooks) and compares against the `hmac-sha256` header: [4](#0-3) 

The gem's own documentation states processing "will verify the request did indeed come from Shopify and then call the specified handler for that webhook," and explicitly instructs apps to key business logic (e.g., enqueuing tenant-scoped jobs) off `data.shop`: [5](#0-4) [6](#0-5) 

**Broken binding:** `shop header value used for tenant attribution` ≠ `bytes covered by the HMAC (raw_body only)`. The `api_secret_key`/HMAC secret is identical across every shop that has installed the app, so knowledge of a valid `(raw_body, hmac)` pair from one's own shop is sufficient to produce a request that the library will validate as authentic for a body/hmac pair while claiming the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header of an entirely different, victim shop.

### Impact Explanation
An unprivileged internet user who runs their own Shopify store with the target app installed can:
1. Trigger a legitimate webhook event on their own shop (e.g. `orders/create`) and capture the raw body + valid `hmac-sha256` header Shopify sent them (this delivery goes to the app's public webhook endpoint, which is visible from the app's configuration/redirect URLs and is not secret).
2. Replay that exact `(body, hmac)` pair to the same app endpoint, substituting the `shop-domain` header with an arbitrary victim shop domain.
3. `HmacValidator.validate` still returns `true` (it only checks the body), so `Registry.process` calls the app's handler with `shop: <victim-shop>` and the attacker's own (or fabricated) body content attributed to the victim tenant.

Any host application that follows this gem's documented pattern of trusting `data.shop` for tenant-scoped side effects (looking up the victim's session/access token, writing to the victim's tenant-scoped data store, enqueuing jobs "for" the victim shop) will perform those actions under the wrong tenant identity — a cross-tenant data/action confusion rooted entirely in this gem's webhook verification logic, not in host misuse.

### Likelihood Explanation
Exploitation only requires installing the app on any (attacker-controlled) shop, which is normal unprivileged usage of a public app, and does not require the app's `client_secret`, an access token, or any privileged access — it uses only a legitimately-received webhook delivery from the attacker's own store.

### Recommendation
Bind the shop (and other trust-sensitive metadata) into the HMAC-verified data, or independently authenticate the shop out-of-band (e.g., cross-check `request.shop` against an app-installed shop list via a verified session) before trusting it. At minimum, `Utils::HmacValidator`/`Webhooks::Request` should not allow the signed body and the unsigned identity headers to diverge silently — document/require verification that the shop header matches an actual currently-installed shop, or compute the signature over a canonical string that includes the shop/topic headers so tampering invalidates the HMAC.

### Proof of Concept
1. Attacker owns `attacker-shop.myshopify.com` with the target app installed.
2. Trigger `orders/create` on `attacker-shop`; Shopify sends a POST to the app's webhook endpoint with headers `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`, and some JSON body.
3. Attacker resends the identical body and `X-Shopify-Hmac-Sha256` value to the same endpoint but with `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request#hmac` and `#shop` parse the (now-forged) headers; `Utils::HmacValidator.validate` succeeds because it only hashes `@raw_body`.
5. `Registry.process` invokes the app's handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: <attacker-controlled-or-replayed body>, ...)`, causing the host app to act on data attributed to `victim-shop` that Shopify never actually sent for that shop.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
