## Title
Webhook Shop-Tenant Spoofing via Unauthenticated `X-Shopify-Shop-Domain` Header - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates only the webhook **body** via HMAC, then trusts the `shop-domain` header — which is never covered by that signature — to determine which tenant/shop the event belongs to. Any party who can produce or replay one validly-signed `(body, hmac)` pair can freely relabel it to any target shop domain, breaking the binding between "HMAC-authenticated bytes" and "shop the app acts on behalf of."

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

`shop` is read from a separate, unsigned HTTP header: [2](#0-1) 

`Utils::HmacValidator.validate` only checks the signable string (the body) against the received HMAC — it never incorporates the `shop`, `topic`, or `webhook-id` headers into the signature computation: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately hands `request.shop` (the unauthenticated header value) to the app's handler as the tenant identity for the event, with no cross-check that this shop was the one the signature was actually computed for: [4](#0-3) 

The broken identity binding, stated as an equality that should hold but doesn't:
`shop authenticated by HMAC` ≠ `shop the handler acts on (request.shop)`.

Because the HMAC only signs `@raw_body`, an attacker who obtains any single valid `(raw_body, hmac)` pair signed with the app's secret — e.g. from a webhook fired against their own installed test/dev store, which is legitimate and requires no privileged access — can replay that exact body+HMAC to the app's public webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header for a victim shop. `Registry.process` will pass HMAC validation (since the body is untouched) and dispatch the handler with `shop: <victim-shop>`, `body: <attacker-controlled event content>`, causing the host app to record/act on forged data attributed to a shop the attacker never authenticated against.

### Impact Explanation
This crosses a tenant boundary: it allows an unprivileged internet user to inject webhook events that the app processes as belonging to a shop they do not control, without ever presenting the target shop's access token or any Shopify-issued credential for it. Depending on the handler (e.g. `app/uninstalled`, `shop/redact`, `customers/data_request`, order/customer webhooks), this enables cross-tenant data corruption, forged uninstall/redaction actions, or injection of attacker-chosen payloads into another merchant's app data — a cross-tenant access class of issue.

### Likelihood Explanation
Requires only network reachability to the app's public webhook endpoint and possession of one legitimately signed `(body, hmac)` pair, obtainable by installing/triggering a webhook on the attacker's own store (no special privilege). No access token, `api_secret_key`, or leaked credential is needed, satisfying the in-scope threat model.

### Recommendation
Bind the tenant identity into what is cryptographically verified. Either:
- Include `shop-domain` (and ideally `topic`/`webhook-id`) in the HMAC-signed payload/signable string used by `HmacValidator`, or
- Require the caller to separately verify that `request.shop` corresponds to a shop with an app installation/registered webhook subscription (e.g. cross-check against Shopify's webhook registration metadata) before dispatching to handlers, rather than trusting the header value directly in `Registry.process`.

### Proof of Concept
1. Install the app on attacker-controlled store `attacker.myshopify.com`.
2. Trigger any subscribed webhook (e.g. `app/uninstalled`) and capture the raw POST body `B` and header `X-Shopify-Hmac-Sha256: H` sent by Shopify — `H` is a valid HMAC of `B` under the app's real `api_secret_key`.
3. Replay a POST to the app's webhook endpoint with the same body `B` and header `H`, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `B` against `H` [5](#0-4) 
5. The handler is invoked with `shop: "victim-shop.myshopify.com"` and the attacker-supplied body, even though `victim-shop` never sent this event.
