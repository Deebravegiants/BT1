### Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant webhook replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its `to_signable_string` from the raw body only, and `HmacValidator` verifies the HMAC exclusively against that raw body. The `shop-domain` header, which `Webhooks::Registry.process` later uses as the authoritative tenant identifier passed to the app's webhook handler, is never included in the signed material. An attacker who can obtain any single valid `(raw_body, hmac)` pair for the app (e.g., by installing the app on their own store and triggering an event) can replay that exact body/HMAC pair while substituting an arbitrary `x-shopify-shop-domain` (or `shopify-shop-domain`) header value. The signature check still passes because it never looked at the shop header, and the handler is invoked believing the payload originated from the spoofed shop.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Webhooks::Request#shop` is read straight from an unauthenticated header with no cross-check against the signed body: [2](#0-1) 

`HmacValidator.validate_signature` recomputes the HMAC over `verifiable_query.to_signable_string` (the body) and compares it to the `hmac` header value using `OpenSSL.secure_compare`: [3](#0-2) 

`Registry.process` only calls this HMAC check, then forwards `request.shop` (the unauthenticated header) directly into the handler payload as the tenant identity: [4](#0-3) 

The equality that should hold is:
`shop_bound_by_signature == shop_acted_on_by_handler`

but in reality the code enforces:
`hmac == HMAC(body)` while `shop_acted_on_by_handler = header["shop-domain"]` (unbound).

Because the shop domain is never part of the signed payload, two different requests carrying the identical `(raw_body, hmac)` pair but different `shop-domain` headers are both treated as validly signed. This breaks the intended binding between "this HMAC proves the request came from Shopify for shop X" and "the handler processes data attributed to shop X."

### Impact Explanation
An app that keys tenant-scoped operations (data writes, cache invalidation, order/customer updates, uninstall/GDPR handling, etc.) off `WebhookMetadata#shop` inside its handler will act on the attacker-chosen shop instead of the shop that actually generated the event. This is a cross-tenant access vector: a single valid webhook capture from any shop (including a shop the attacker legitimately controls, e.g., a free/dev install) can be replayed against the app's endpoint while claiming to be any other merchant, since nothing about the shop identity is authenticated. This matches the Critical-tier "cross-tenant access" impact category.

### Likelihood Explanation
The only precondition is the ability to install the app on any store (even a free/dev store) and trigger one webhook of the topic of interest — a low bar for any unprivileged internet user who signs up for a Shopify dev/partner account. No secrets, tokens, or privileged access to the target shop are required. The replay itself is a trivial HTTP POST with a modified header, since `secure_compare` only guards the HMAC field and the shop header is read unconditionally.

### Recommendation
Bind the merchant identity to the signature. Options:
- Include the shop domain (and ideally topic/webhook-id) in the value that is HMAC-verified, or
- Independently verify that the shop presented in the header corresponds to a shop the app has an active, previously-established session/install for, before trusting it in the handler, and
- Reject/flag webhook requests where the header-derived shop cannot be corroborated against out-of-band knowledge (e.g., only accept webhooks for shops with a currently stored session/access token).

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` (a normal, unprivileged self-serve action) and triggers a webhook event (e.g. `orders/create`).
2. Attacker captures the resulting POST body `B` and its valid `x-shopify-hmac-sha256` header `H` (correctly computed by Shopify over `B` using the app's real `client_secret`).
3. Attacker resends an HTTP request to the app's webhook endpoint with:
   - Body: `B` (unchanged)
   - Header `x-shopify-hmac-sha256`: `H` (unchanged, still valid because only `B` is signed)
   - Header `x-shopify-shop-domain`: `victim-shop.myshopify.com` (spoofed)
   - Header `x-shopify-topic`: original topic (unchanged)
4. `Utils::HmacValidator.validate` passes because it only checks `HMAC(B) == H`.
5. `Registry.process` invokes the registered handler with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, even though the payload actually originated from the attacker's own store — demonstrating tenant-identity confusion driven purely by an unauthenticated header value.
