### Title
Webhook shop-domain identity bound only by unsigned header, not HMAC, enabling cross-tenant impersonation - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its verifiable HMAC signature over the raw body only, while the shop-identifying header (`X-Shopify-Shop-Domain`) that the gem passes to host-app webhook handlers as the tenant key is never included in the signed content.

### Finding Description
`Request#to_signable_string` returns `@raw_body`, and `HmacValidator.validate` computes/compares the HMAC purely against that string and the app's shared `api_secret_key` [1](#0-0) [6](#0-5) . Meanwhile `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are parsed directly and unverified from HTTP headers [2](#0-1) . `Registry.process` checks `HmacValidator.validate(request)` and then, on success, immediately trusts `request.shop` to build `WebhookMetadata` passed to the app's handler [3](#0-2) .

Because `api_secret_key` is the single app-wide secret (not per-shop), any tenant with a legitimately installed instance of the app can obtain a validly-HMAC'd webhook body for their own shop, then replay that exact body to the app's webhook endpoint with the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header rewritten to a victim shop's domain. `HmacValidator.validate` will still pass, because the shop header is not part of `to_signable_string`, and `Registry.process` will hand the forged `shop` value to the host app's handler as if it were an authentic webhook for the victim tenant. This breaks the identity binding: `shop authenticated by HMAC` (nothing — the shop is not covered at all) versus `shop trusted as the tenant key handed to the handler` (`request.shop`, straight from the header).

### Impact Explanation
Any application built on this gem that uses `WebhookMetadata#shop` (as documented) to scope database writes, cache invalidation, session lookups, or redact operations by shop, can be made to process a forged/replayed webhook body under another tenant's identity. This is a cross-tenant confusion vector directly caused by the gem's verification logic leaving a security-relevant field outside the signed payload.

### Likelihood Explanation
Exploitation only requires an attacker to control one legitimate installation of the target app (any merchant/tenant can install most public/embedded Shopify apps) and to know or guess a victim shop's `.myshopify.com` domain, which is generally discoverable/public. No secrets, tokens, or privileged access are required — only the ability to send an HTTP POST to the app's public webhook endpoint with a captured body and a modified header.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the HMAC-signed content, or otherwise cryptographically/contextually bind the shop header to the request/session before trusting it — e.g., include it in `to_signable_string`, or require the host app to reconcile `request.shop` against an independently verified session/tenant record before invoking the handler. At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must not be trusted as a tenant boundary without additional verification.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com`, triggering a legitimate webhook delivery with a valid `X-Shopify-Hmac-Sha256` header computed over the body.
2. Attacker captures the raw body and HMAC header of this delivery.
3. Attacker POSTs the same raw body and HMAC header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `HmacValidator.validate` succeeds because it only checks `raw_body` against the HMAC (`request.rb:35-38`, `hmac_validator.rb:26-31`).
5. `Registry.process` builds `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` and invokes the host app's handler, which processes attacker-supplied data as if it originated from the victim shop.
