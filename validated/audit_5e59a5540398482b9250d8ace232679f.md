## Title
Webhook `shop` (and `topic`) identity fields are not bound to the HMAC signature, enabling cross-tenant webhook spoofing — (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while the `shop` (and `topic`) values used by `ShopifyAPI::Webhooks::Registry.process` to dispatch webhook data to the host application's handler come from unauthenticated HTTP headers that are never included in the signed material.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

```ruby
def shop
  T.cast(shopify_header("shop-domain"), String)
end
...
def to_signable_string
  @raw_body
end
``` [1](#0-0) 

`Utils::HmacValidator.validate` only ever verifies `verifiable_query.to_signable_string` (i.e. the raw body bytes) against the HMAC header: [2](#0-1) 

`Registry.process` then trusts `request.shop` (and `request.topic`) — both taken directly from attacker-controllable HTTP headers — to build the `WebhookMetadata` that is handed to the host app's handler, after only checking that the *body* HMAC is valid:
```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
``` [3](#0-2) 

This breaks the identity binding the M-3 report describes as the bug class: the field actually **acted on** (`request.shop`, used by the app to select the tenant/session context) is not the field **covered by the HMAC** (only `@raw_body` is). In other words: `bytes verified (raw_body) != identity used (shop header)`.

### Impact Explanation
Because a single app-level `api_secret_key` is used to verify webhooks for *every* installed shop, a merchant who has legitimately installed the app on their own store (an "unprivileged internet user" from the perspective of any other tenant) receives real webhook deliveries with a valid `(raw_body, hmac)` pair for their own shop. They can replay that exact `raw_body`/`hmac` pair to the app's public webhook endpoint while swapping only the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header to name a victim shop. `HmacValidator.validate` still succeeds because it only checks the raw body against the HMAC — it never checks that the `shop` header matches the shop the HMAC was actually generated for. The host application's handler then processes attacker-supplied webhook content under the identity of a victim shop (`data.shop`), which can lead to cross-tenant data injection, spoofed events attributed to the wrong merchant, or incorrect authorization/session decisions if the handler uses `data.shop` to pick the tenant's session/access token before acting on `data.body`.

### Likelihood Explanation
Any user who can install the app on one shop (which is normal, unprivileged usage of a public app) can capture a legitimate `(raw_body, hmac)` pair delivered to their own endpoint and replay it with a forged shop header, since no attacker-side secret knowledge beyond a valid delivery is required. This is a low-effort, no-privilege attack against the identity-binding gap in this library's own `HmacValidator`/`Request` design.

### Recommendation
Include the identity-relevant fields (`shop`, `topic`, and ideally `webhook_id`/`api_version`) in the HMAC-signable string, or otherwise cryptographically bind them to the raw body before use, so `HmacValidator.validate` cannot succeed for a body whose declared shop/topic headers were swapped. At minimum, document and enforce that `request.shop` must never be trusted for tenant selection unless it is included in the signed payload.

### Proof of Concept
1. App merchant "Attacker" installs the app on `attacker-shop.myshopify.com`; Shopify sends a legitimate webhook: body `B`, header `X-Shopify-Hmac-Sha256: H` (valid HMAC of `B` with the app's `api_secret_key`), and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker replays this exact request to the app's public webhook endpoint but changes only the header to `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC of `@raw_body` (unchanged `B`) and compares it to `H` — validation succeeds.
4. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, i.e., attacker-controlled body content attributed to the victim shop. [3](#0-2) [4](#0-3)
