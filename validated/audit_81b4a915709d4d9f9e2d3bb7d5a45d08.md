### Title
Unbounded gzip decompression of remote token icon data enables memory-exhaustion DoS - ([File: adapters/storage-icons-browser/src/utils.js], [File: adapters/storage-icons-mobile/src/icons-storage.js])

### Summary
`unzipIcon` decompresses attacker-influenceable `token.icon` base64 data with `zlib.gunzip` (browser adapter) or `pako.ungzip` (mobile adapter) with no cap on decompressed output size. `storeIcons` in `IconsStorage` iterates over tokens fetched from the remote assets/tokens API and calls `#storeIcon` → `unzipIcon` for every token whose `icon` field is truthy, before any SVG size/shape validation occurs.

### Finding Description
`storeIcons` is invoked with token lists coming from remote API responses (e.g. via `assetsModule`'s custom-token flows and `#fetchIcon`), and for each token with an `icon` field it calls `#storeIcon`, which directly does: [1](#0-0) 
`unzipIcon` then decompresses the base64 payload with no output-size ceiling: [2](#0-1) 
The mobile adapter is structurally identical, using `pako.ungzip(arr, { to: 'string' })`, which also has no size bound: [3](#0-2) 
Only after full decompression does `cleanup`/`validate` from `@exodus/svg-safe` run, and that validator performs string tokenization/regex checks with no early size guard either — a `path`'s `d` attribute is capped at 50,000 chars, but this is a narrow, tag-specific check that doesn't bound overall decompressed buffer size before that point is reached: [4](#0-3) 
A crafted gzip payload with an extreme compression ratio (e.g. many megabytes/gigabytes of repeated bytes compressing to a small base64 string) would cause `gunzip`/`ungzip` to allocate the full decompressed buffer in memory before any validation logic runs, since no `maxOutputLength`-equivalent option is passed to either decompression call.

### Impact Explanation
This causes wallet-process memory exhaustion or a crash in the process handling `storeIcons`/`#fetchIcon` (browser background/service worker or mobile app process), matching an availability-disruption impact category (STORAGE_INTEGRITY / availability). It does not by itself lead to signing bypass or secret disclosure, but a crash during token/icon processing could disrupt wallet unlock/signing flows that share the same process.

### Likelihood Explanation
Feasibility depends on whether `token.icon` in the assets/tokens API response is genuinely attacker-influenceable. Based on the code reachable through `codebase_search`, `token.icon` is consumed directly from network responses without shape/size validation prior to decompression (`#fetchIcon`, `#storeIcons` in `assets-module.js` simply pass through `token.icon`). If the tokens/CTR API can be influenced by an unprivileged actor (e.g., a malicious/compromised custom-token entry, or a spoofable/unauthenticated response path), this is straightforward and repeatable to trigger, since no size validation exists anywhere in the call chain before full decompression completes.

### Recommendation
Enforce a maximum decompressed size in `unzipIcon` in both adapters — e.g. use `zlib.gunzip` with streaming and abort once output exceeds a threshold (a few hundred KB is generous for an SVG icon), or use `pako.Inflate` in chunked mode with a running size check and throw once the limit is exceeded. Reject/delete the icon and log rather than let the promise chain silently propagate unbounded memory growth.

### Proof of Concept
Unit/integration test plan:
1. Generate a gzip buffer of a highly repetitive string (e.g. `'A'.repeat(500_000_000)`) using `zlib.gzipSync`, compressing to a few KB.
2. Base64-encode it and pass it as `token.icon` to `IconsStorage#storeIcons([{ name: 'evil', icon: maliciousBase64 }])` (both browser and mobile adapters).
3. Assert that either: (a) `unzipIcon`/`storeIcons` rejects with a controlled "payload too large" error before completing decompression, and memory usage stays bounded (e.g., measured via `process.memoryUsage().heapUsed` delta assertion), or (b) if no limit exists, the test demonstrates unbounded memory growth / a hang, confirming the vulnerability.
4. Currently, since no size limit is enforced in `unzipIcon` ( [2](#0-1) , [3](#0-2) ), the expected assertion (bounded memory / early rejection) would fail, confirming the gap.

export const unzipIcon = async (base64) => {
  const buff = Buffer.from(base64, 'base64')
  const unzip = await new Promise((resolve, reject) => {
    gunzip(buff, (err, res) => {
      if (err) {
        reject(err)
        return
      }

      resolve(res)
    })
  })
  return cleanup(unzip.toString('utf8'))
}
