### Title
Precision loss in `pallet-hyper-fungible-token::on_accept` truncates the ERC20-denominated amount when converting down to local decimals, permanently losing the fractional remainder that was already burned/locked on the source chain - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
`pallet-hyper-fungible-token` bridges tokens between Substrate (nexus) and EVM chains. Because the EVM side is required to use decimals ≥ the local Substrate asset's decimals (`config.decimals >= local_decimals` enforced in `register_token`/`update_token`), every inbound `on_accept` must scale the incoming ERC20 `U256` amount *down* to the local balance type via `convert_to_balance`, which performs plain integer division. This division truncates, and the truncated remainder is money that has already been irrevocably removed from circulation on the source chain (burned by the EVM sender, or locked out of escrow/EVM supply) before the message ever reaches the pallet — the exact "burn-full-amount-then-credit-a-truncated-amount" pattern described in the reference report.

### Finding Description
`convert_to_balance` in `modules/pallets/hyper-fungible-token/src/impls.rs`: [1](#0-0) 

divides the incoming ERC20 `U256` amount by `10^(erc_decimals - local_decimals)` with **no remainder check and no compensation mechanism**. `register_token`/`update_token` guarantee `erc_decimals >= local_decimals`: [2](#0-1) 

so this division always truncates a real fractional value whenever the sender submits (or the ERC20-side arithmetic yields) an amount that is not an exact multiple of the scale factor.

This truncating conversion is invoked directly in `on_accept`, which mints/releases the *truncated* `amount` to the beneficiary after the EVM side has already burned (in `HyperFungibleToken`/`BridgeToken`'s own-burn model) or already had the corresponding value locked out of the pallet's nexus escrow (in the native/escrow model) the *full, untruncated* ERC20 amount: [3](#0-2) 

Contrast this with the outbound `send()` path, where the local (already-exact) amount is burned/escrowed first and then scaled *up* via `convert_to_erc20` (a multiplication, which is exact and loses nothing): [4](#0-3) [5](#0-4) 

Because outbound conversion is a lossless multiply and inbound conversion is a lossy divide, any value that is minted/burned on the EVM side using its full (higher) precision — arbitrary ERC20 transfer amounts, dust from ERC20 fee/DEX operations, or amounts that are not exact multiples of the pallet's registered scale — is truncated away on arrival at the Substrate side, with the fractional remainder gone: it was already deducted (burned) on EVM, and the destination pallet only credits the floor. There is no accounting entry anywhere in the pallet that tracks or allows recovery of this remainder (no analogous mechanism to a `currentDeposit`-style ledger correction).

The `on_timeout` refund path uses the same `convert_to_balance` division, but is not itself lossy in the common case because the erc20 amount being converted back was produced by the pallet's own `convert_to_erc20` multiplication (an exact round trip); the vulnerability is specific to genuinely inbound EVM→Substrate transfers where the ERC20-side amount did not originate from this pallet's exact-multiple encoding.

### Impact Explanation
Every EVM→Substrate transfer whose ERC20 amount is not a clean multiple of `10^(erc_decimals - local_decimals)` permanently loses the truncated remainder. For the concrete `BridgeToken` deployment, ERC20 decimals are 18 and nexus decimals are 12 (scale `10^6`), so up to `10^6 - 1` wei of the 18-decimal representation (≈1e-12 tokens) is lost per transfer — individually negligible, but as the report itself argues, this "accumulates rapidly in a high-frequency [bridging] environment," and for non-1e6-scale token pairs registered with less "clean" decimal gaps the loss per transaction can be proportionally larger. The dust is not recoverable by the user, the relayer, or governance: it is simply destroyed on the EVM side (burn) but never minted/released on the Substrate side, which is a permanent, protocol-level loss of user funds each time — the same root cause as the referenced `WithdrawRequest.amount` finding.

### Likelihood Explanation
This triggers on essentially every EVM→Substrate transfer that carries decimals in its low-order digits (i.e., is not an exact multiple of the configured scale), which for user-driven ERC20 transfer amounts is the common case rather than the exception. No malicious actor or special conditions are required — any unprivileged user who calls `send()`/`HyperFungibleToken.send` on the EVM side with an amount that doesn't align to the scale factor triggers the loss automatically on delivery.

### Recommendation
- Track and carry forward truncation dust (e.g., accumulate remainders per asset/chain and periodically sweep/credit them, or round amounts at the point of encoding on the EVM side so `on_accept` always receives an amount that divides exactly).
- Alternatively, require/enforce that only ERC20 amounts that are exact multiples of the registered scale factor can be dispatched (revert on the EVM side otherwise), preventing sub-unit dust from ever being burned in the first place.
- Add explicit remainder accounting (analogous to fixing `currentDeposit`/`WithdrawRequest.amount` in the referenced report) so no value is silently destroyed.

### Proof of Concept
1. Deploy `BridgeToken` (18 decimals) paired with the nexus `pallet-hyper-fungible-token` native asset (12 decimals, scale `10^6`), as configured in [6](#0-5) .
2. A user on EVM calls `send(amount = 1_000_000_000_000_000_001 wei)` (1 BRIDGE + 1 wei) which is not a multiple of `10^6`; the EVM contract burns the full `1_000_000_000_000_000_001` wei.
3. On delivery, `on_accept` calls `convert_to_balance(1_000_000_000_000_000_001, 18, 12)` → `1_000_000_000_000_000_001 / 10^6 = 1_000_000_000_000` (truncated), discarding the trailing `1` wei-equivalent fraction (`0.000001` wei) permanently — matching the `withdraw_amount=299 → amount_after_precision_loss=2` truncation pattern from the referenced SYMM report.

Because I could not fully trace every downstream ledger/escrow-reconciliation code path for the "native"/escrow model (e.g., whether `pallet_account()`'s escrow balance is separately reconciled anywhere to detect this drift), I cannot state with certainty whether the dust is merely "stuck" (frozen, recoverable in principle by governance intervention) versus truly unrecoverable; based on the code reviewed, no reconciliation or dust-recovery mechanism exists in this pallet.
