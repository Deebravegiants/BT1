## Authentication Bypass by Alternate Name Analog: `IntentGatewayV2.authenticate()` silently trusts unregistered source chains

The Tomcat CVE is a case where a realm accepts a "name" it never explicitly configured because a fallback/normalization path resolves the missing entry to something that incidentally matches. The same shape exists in `IntentGatewayV2`'s cross-chain module authentication.

### Finding

`authenticate()` gates every incoming `onAccept` request (escrow redemption, refund, dust sweep, param updates, new-deployment records) by checking that the sender module on the source chain matches a "known instance": [1](#0-0) 

```solidity
function instance(bytes calldata stateMachineId) public view returns (address) {
    address gateway = _instances[keccak256(stateMachineId)];
    return gateway == address(0) ? address(this) : gateway;
}

function authenticate(PostRequest calldata request) internal view {
    if (request.from.length != 20) revert InvalidInput();
    address module = address(bytes20(request.from));
    if (instance(request.source) != module) revert Unauthorized();
}
```

`_instances` is populated only via governance registering peer deployments [2](#0-1) . But `instance()` does not fail closed for a state machine that was never registered — it falls back to `address(this)`. Any state machine ID that the contract's admin never explicitly configured (a new chain Hyperbridge adds a consensus client for, a chain the gateway operator intentionally never rolled out to, etc.) is treated as an authenticated peer as long as the inbound `request.from` equals this contract's own address.

Because `IntentGatewayV2` instances are conventionally deployed at the same address across chains via CREATE2 with identical bytecode/salt, an attacker who can permissionlessly redeploy the same bytecode+salt through the same deterministic deployer on any EVM-compatible chain that Hyperbridge has a consensus client for — but that this gateway's admin never called `addInstance`/`NewDeployment` for — obtains full admin control of that "mirror" instance (the constructor sets `_admin = msg.sender`). From there they can dispatch a forged `PostRequest` with `from = address(this)` (their own contract, at the identical address) that the victim gateway will `authenticate()` successfully, since the unset mapping defaults to "self."

### Impact

`authenticate()` gates `RedeemEscrow`/`RefundEscrow`/`SweepDust`/`UpdateParams` kinds of `onAccept`, so a successful bypass lets an attacker forge escrow redemption or dust-sweep instructions and drain funds escrowed by `placeOrder`, or push malicious `UpdateParams`, from a chain the operator never intended to trust — a concrete theft-of-funds / unauthorized-app-action path reachable by anyone able to deploy on a chain Hyperbridge already has consensus support for.

### Caveat

I could only fully confirm this pattern in `evm/tron/contracts/apps/IntentGatewayV2.sol`. My last searches into `evm/src/apps/IntentGatewayV2.sol` and `evm/src/apps/intentsv2/IntentsBase.sol` (the mainline EVM implementation) returned matches but I ran out of iterations before reading their `instance()`/`authenticate()` bodies to confirm whether the mainline contract has the same self-address fallback or an explicit "unregistered → reject" gate. If you need certainty on whether the mainline (non-Tron) gateway shares this exact fallback, that should be checked directly — I recommend starting a Devin session with terminal/file access to read `evm/src/apps/intentsv2/IntentsBase.sol` in full and diff its `instance()`/`authenticate()` logic against the Tron variant shown above.
