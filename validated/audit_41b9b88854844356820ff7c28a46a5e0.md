### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing tenant/shop confusion on webhook replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop`, `topic`, `api_version`, and `webhook_id` values directly from HTTP headers, but `Utils::HmacValidator.validate` only verifies the HMAC over `to_signable_string`, which returns the raw request body — not the headers. This breaks the intended binding `hmac_verified(payload) == shop_used_for_tenant_routing(payload)`: the HMAC only authenticates the *body*, while the *shop* identity acted upon by `Webhooks::Registry.process` is read from an unauthenticated header.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, `#api_version`, and `#webhook_id` are read straight from HTTP headers, independent of the signed payload: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature only from `verifiable_query.to_signable_string` (i.e., the raw body) and compares it against the `hmac` header: [3](#0-2) 

`Webhooks::Registry.process` validates the HMAC and then immediately trusts `request.shop` (and `request.topic`) to build the `WebhookMetadata` passed to the app's handler, without any re-derivation from the signed body: [4](#0-3) [5](#0-4) 

Equality that should hold but doesn't:
`shop_bound_by_hmac(request) == shop_used_for_tenant_routing(request)`

Before request: for a legitimately-delivered webhook, `raw_body` and the `shopify-shop-domain` header both correspond to the same shop, so the equality holds by construction (not by verification).
After an attacker-controlled replay: the attacker keeps the original `raw_body`/`hmac` pair (still valid, since HMAC only signs the body) but swaps the `shopify-shop-domain` (and/or `shopify-topic`, `shopify-webhook-id`) header to a different shop/topic. `Utils::HmacValidator.validate` still returns `true` because the body is unchanged, yet `Registry.process` now routes the (unmodified) payload to the handler tagged with the attacker-chosen `shop`. The equality is broken: the HMAC-authenticated content and the tenant identity used for downstream routing/authorization no longer refer to the same shop.

### Impact Explanation
If a host application uses `WebhookMetadata#shop` (as the library instructs apps to, since it is the only field the library exposes for tenant identification) to determine which merchant's data record to update/look up, an attacker who can capture one legitimately-signed webhook body (e.g., from their own trial/dev shop, which they fully control and can trigger webhooks for) can replay that exact body to the app's public webhook endpoint while forging the `shop-domain` header to point at a different, victim shop. Because `HmacValidator.validate` never binds header values to the signature, the app will accept the payload as authentic for the *victim* shop, resulting in cross-tenant data confusion — an unprivileged internet user who merely operates their own shop instance can inject data (or trigger redact/data-request style actions) attributed to another merchant's tenant. This matches the in-scope "Critical – cross-tenant access" impact category, since the identity binding between authenticated bytes and the tenant key is broken by the library's own verification logic.

### Likelihood Explanation
The webhook endpoint is a public, unauthenticated HTTP endpoint by design (Shopify calls it without any session/OAuth token), so any internet user can send arbitrary HTTP requests to it. The only gate is `HmacValidator.validate`, which this analysis shows validates the body only. An attacker needs one valid `(raw_body, hmac)` pair — trivially obtainable by owning any development/trial shop and subscribing to a webhook topic the app processes — and can freely vary headers on replay. No secret material or privileged access is required, only observation of one legitimate webhook delivery to a shop the attacker controls.

### Recommendation
Include the security-relevant header values (`shop`, `topic`, `api_version`, `webhook_id`) in the signed material, or otherwise cryptographically bind them to the HMAC. Since Shopify's HMAC scheme signs only the body, the safer fix is for `Registry.process` (and any consumer) to treat `request.shop`/`request.topic` as provisional until corroborated by other means (e.g., look up the webhook subscription registered for that topic/shop pair, or require the app to independently confirm the shop from the body/session before acting), and to document clearly that these headers are unauthenticated so host apps do not use them as a sole tenant-authorization signal.

### Proof of Concept
1. Attacker installs the target app on their own controlled shop `attacker-shop.myshopify.com` and triggers a legitimate webhook (e.g. `orders/create`), capturing the resulting HTTP request: `raw_body` and the `x-shopify-hmac-sha256` header (`hmac`), which is valid for that `raw_body` under the app's `api_secret_key`.
2. Attacker crafts a new POST to the app's webhook endpoint with the identical `raw_body` and `x-shopify-hmac-sha256` header, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `raw_body` only and succeeds, per: [6](#0-5) 
4. `Registry.process` proceeds to call `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))` using the forged `shop` header value, per: [7](#0-6) 
5. Any host application logic keyed on `WebhookMetadata#shop` for tenant scoping now operates on `victim-shop.myshopify.com` using attacker-supplied body content, despite the HMAC never having authenticated that shop association.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
