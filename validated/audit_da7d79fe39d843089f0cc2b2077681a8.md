## Title
Duplicate input-token legs in same-chain partial fills allow a solver to drain another leg's escrow — (File: evm/src/apps/intentsv2/IntrinsicIntents.sol)

### Summary
`_fillSameChain` in `IntrinsicIntents.sol` computes per-leg escrow release using `order.inputs[i].amount` as the "total" for the proportional calculation, but the actual escrow balance is tracked only by `(commitment, token address)` in `_orders`, not per leg index. When two legs of the same order share the same input token, completing one leg first reads and sweeps the *entire* pooled escrow balance for that token — including the portion that rightfully belongs to the other, not-yet-filled leg — exactly mirroring the BlueBerry pattern where paying off a single debt share was used to release a proportion computed against the wrong aggregate.

### Finding Description
The escrow ledger is keyed only by `(commitment, token)`: [1](#0-0) 

`_fillSameChain` iterates output legs by index `i` and, for each leg, derives the escrow amount to release from `order.inputs[i]` — assuming a strict 1:1 correspondence between `inputs[i]` and `output.assets[i]`: [2](#0-1) 

Critically, when a leg is *fully* filled (`amountFilled == totalRequired`), the code does not release the leg's proportional share — it sweeps **the entire remaining balance held under that input token's key**:
```solidity
if (amountFilled == totalRequired) {
    escrowedAmount = _orders[commitment][address(uint160(uint256(order.inputs[i].token)))];
} else {
    escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired;
}
``` [3](#0-2) 

This is safe only if each input token appears in exactly one leg. Nothing in `IntentsBase`/`IntentGatewayV2.sol` enforces that `order.inputs` tokens are unique across legs, or that `inputs.length == output.assets.length` with a strict one-token-per-leg mapping — `Order.inputs` and `Order.output.assets` are independent arrays: [4](#0-3) 

If a user (or a colluding order placer/solver pair) constructs an order where two output legs `i` and `j` both specify `order.inputs[i].token == order.inputs[j].token`, `_orders[commitment][token]` holds the combined escrow for both legs. A solver that fully fills the *smaller* leg first triggers the `amountFilled == totalRequired` branch and receives the **whole pooled balance** for that token — including the amount that was escrowed against the other, unfilled leg — via `_withdraw`'s unconditional decrement: [5](#0-4) 

The subsequent fill of the other leg then either underflows/reverts (permanently freezing that leg — the user's escrow for it is gone) or, if some balance remains due to favorable ordering/rounding, releases less than proportionally owed to the second solver, i.e., a first-mover captures more than their entitled share of a shared escrow pool, exactly analogous to the BlueBerry issue where paying one debt token released collateral proportional to a share ratio that did not correctly scope to that debt token alone.

### Impact Explanation
This is a **fund-theft / permanent-freezing** vector reachable from a single `fillOrder` transaction by any solver — no privileged role required. A solver who is first to complete one leg of a multi-leg order that reuses an input token across legs can claim escrow that belongs to a different, not-yet-completed leg, either stealing user-escrowed funds outright or permanently stranding the remainder of the order (since a later `_withdraw` call for the other leg would underflow on `_orders[commitment][token] = escrowed - amount` and revert, leaving that leg's original output payment un-refundable through normal fill flow, and the user's own cancellation path (`_cancelSameChain`) reads the (already-drained) `_orders[commitment][token]` as `0`, so no refund is possible either. This satisfies the "concrete theft or permanent freezing of funds" bar.

### Likelihood Explanation
Likelihood depends on whether order placers (or an attacker crafting their own order and self-selecting as filler, or colluding with a solver) construct orders with duplicate input tokens across legs — nothing in `placeOrder`/`fillOrder` validation prevents this, and multi-leg orders with a shared settlement token per leg (e.g., paying multiple output legs from the same input asset pool) is a plausible/likely usage pattern for the Intent Gateway's multi-asset swap feature. An attacker fully controls order construction and fill ordering, making exploitation straightforward to trigger deliberately.

### Recommendation
Track escrow per (commitment, leg index) rather than per (commitment, token) — or, if tokens must remain the aggregation key, compute each leg's completing-fill release as `min(order.inputs[i].amount - alreadyReleased[i], _orders[commitment][token])` rather than sweeping the token's entire remaining balance whenever a single leg completes. Additionally, validate at `placeOrder` time that `inputs.length == output.assets.length` and, if the leg-index correspondence is load-bearing, either disallow duplicate `inputs[i].token` values across legs of the same order or maintain a per-leg escrow counter independent of the shared token-keyed map.

### Proof of Concept
1. User places an order with `inputs = [{token: USDC, amount: 100}, {token: USDC, amount: 900}]` and `output.assets = [{token: DAI, amount: 100}, {token: DAI, amount: 900}]` (two legs, same input token USDC, different output amounts). `_orders[commitment][USDC] = 1000`.
2. Solver A calls `fillOrder` providing `outputs[0] = 100 DAI` (fully completing leg 0), `outputs[1] = 0` (skip). In `_fillSameChain`, for `i = 0`: `amountFilled == totalRequired` → `escrowedAmount = _orders[commitment][USDC] = 1000` (the full pool, not the 100 owed to leg 0). `_withdraw` releases 1000 USDC to Solver A and sets `_orders[commitment][USDC] = 0`.
3. Solver B later tries to fill leg 1 (`outputs[1] = 900 DAI`). On completion, `_withdraw` attempts `_orders[commitment][USDC] = 0 - 900` → underflow revert, or (if implemented with a check) reads `escrowed == 0` → `revert UnknownOrder()`. The order becomes permanently stuck: the user's 900 USDC destined for leg 1 was stolen by Solver A in step 2, and Solver B cannot legitimately complete leg 1's exchange, nor can the user cancel/recover the leg-1 escrow since the shared balance is already zero.

*Note: I was unable to find an explicit test or validation path enforcing uniqueness of `inputs[i].token` across legs or `inputs.length == output.assets.length` within the indexed code; this analysis is based on the code paths cited above. A Devin session with full repository access could confirm whether `placeOrder`/tests elsewhere constrain multi-leg orders in a way that would prevent this scenario.*
