### Title
Webhook `shop-domain` header is trusted for tenant identification without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature only over the raw request body (`to_signable_string` returns `@raw_body`), while the `shop` (from the `x-shopify-shop-domain`/`shopify-shop-domain` header) is read directly from unauthenticated HTTP headers and passed on, unverified, as the tenant identifier to the app's webhook handler.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `HmacValidator.validate`/`validate_signature` compute and compare the HMAC exclusively against that signable string [2](#0-1) . Meanwhile `Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header with no cryptographic binding to the HMAC-signed body [3](#0-2) .

`Registry.process` validates the HMAC (`Utils::HmacValidator.validate(request)`) and then immediately forwards `request.shop` into `WebhookMetadata`, which is handed to the app's registered handler as the trusted tenant/shop for the event [4](#0-3) . The `WebhookMetadata` struct's `shop` field is a plain `String` with no verification step of its own [5](#0-4) .

This breaks the intended identity binding: `HMAC(raw_body, api_secret_key) == received_hmac` is verified, but `shop header == tenant used by handler` is **not** bound to that same HMAC. The gem's HMAC validation gives developers false confidence that "this webhook request, including which shop it's for, is authentic," when in fact only the JSON body content is authenticated — the shop attribution is not.

Because Shopify webhook payloads for many topics do not redundantly encode the shop domain inside the JSON body itself (the shop is conveyed via the header, by design, per Shopify's webhook delivery format), an attacker who can produce (or replay) a validly-HMAC'd body for topic X (e.g., from their own trial/development store, which they legitimately possess valid HMAC values for) can swap in a different `x-shopify-shop-domain` header value pointing at a victim shop. `Request` performs no cross-check that the header-supplied shop matches anything inside the signed body, and `HmacValidator` never includes the header in what it verifies.

### Impact Explanation
If a merchant's app naively uses `WebhookMetadata#shop` (as documented/intended, since this is the only shop field exposed by this library's webhook processing API) to look up the tenant's stored access token / data record and merges in the body content, an attacker can cause the app to process/attribute events under the wrong shop identity — a cross-tenant confusion where a request that is legitimately signed for shop A's payload gets attributed to shop B. This matches the report's "Critical - cross-tenant access" impact category: the identity boundary (which merchant/tenant this event belongs to) is not protected by the same authenticity mechanism (HMAC) that protects the payload, so the two can be decoupled by any party who can obtain even one validly-signed webhook body (e.g. by installing the app on their own free/dev store) and then send it to the app's webhook endpoint with a forged shop-domain header.

### Likelihood Explanation
Any unprivileged internet user who can install the app on a store they control (development stores are free and require no privileged Shopify relationship) can obtain arbitrarily many correctly-HMAC'd webhook bodies from Shopify for that store, then replay them directly to the app's public webhook endpoint with the `shop-domain` header altered to name a different, victim shop. The gem does nothing to prevent this since `Registry.process` never validates that `request.shop` is consistent with anything cryptographically verified. This requires no `api_secret_key`, no leaked token, and no privileged account — only the ability to send an HTTP request, matching the "unprivileged internet user" analog criteria in scope.

### Recommendation
Bind the shop domain into the value that is HMAC-verified, or otherwise cryptographically tie the header-derived tenant to the signed payload before trusting it:
- Include the `shop-domain` header (and ideally `topic`/`webhook-id`) as part of the string/material that `to_signable_string` returns, matching what Shopify actually signs, OR
- Require callers/handlers to independently confirm `WebhookMetadata#shop` corresponds to a shop for which they already have a corresponding valid, previously-established session/installation record before trusting it for any tenant-scoped action, and document this requirement prominently since the gem's `HmacValidator` does not cover it.
- At minimum, update documentation to explicitly warn that `WebhookMetadata#shop` is **not** covered by the HMAC and must not be used as the sole tenant identifier for security-sensitive operations.

### Proof of Concept
1. Attacker creates a free Shopify development store `attacker.myshopify.com` and installs the victim's app.
2. Attacker triggers a webhook topic the app subscribes to (e.g. `orders/create`) on their own store, capturing the full raw request Shopify sends, including a **valid** `x-shopify-hmac-sha256` value computed over the JSON body with the app's real `client_secret`.
3. Attacker replays this exact request to the app's public webhook endpoint, but changes only the `x-shopify-shop-domain` header to `victim.myshopify.com`.
4. Server-side, the app calls `ShopifyAPI::Webhooks::Registry.process(request)`:
   - `Utils::HmacValidator.validate(request)` succeeds, because it only checks `request.to_signable_string` (`@raw_body`) against the HMAC — both unchanged from the legitimate original request [6](#0-5) .
   - `request.shop` returns `"victim.myshopify.com"` (from the forged header) [3](#0-2) .
   - `WebhookMetadata.new(..., shop: request.shop, ...)` is passed to the app's handler, which — trusting the library's HMAC check as proof of authenticity for the whole request including `shop` — processes attacker-controlled body content under the victim's tenant identity [7](#0-6) .

This is confirmed purely from code inspection of `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`, and `lib/shopify_api/webhooks/registry.rb`; I was not able to execute a live end-to-end test against Shopify's servers to confirm Shopify's actual signing behavior matches this assumption (i.e., that Shopify does not itself also encode the shop into the signed body for all topics) — this is based on the header/body separation visible in this gem's own `Request` class and is consistent with Shopify's publicly documented webhook header format.
