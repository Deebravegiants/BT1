### Title
Wrong destination's txHash reported for batch withdrawals sharing the same assetId - ([File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts])

### Summary
`PoaBridge.describeWithdrawal` matches withdrawal status entries solely by `assetId` via `findMatchingWithdrawal`, ignoring `WithdrawalIdentifier.index` and `destinationAddress`. When an unprivileged user submits a batch withdrawal with two `withdrawalParams` entries using the same `assetId` but different `destinationAddress` values, both watchers resolve to the same matched entry, causing one destination's completion status/`txHash` to be misreported as belonging to the other destination.

### Finding Description
The broken equality: for each `wid.index`, `(chain, address)` of the reported `txHash` should equal `(chain, address)` in `withdrawalParams[wid.index]`. Instead:

- `createWithdrawalIdentifiers` in `packages/intents-sdk/src/core/withdrawal-watcher.ts` (lines 80-107) assigns `wid.index` per-route counter, independent of `destinationAddress`, and there is no dedup/validation rejecting two withdrawals with identical `assetId` but different `destinationAddress` in the same batch (checked `sdk.ts` `signAndSendWithdrawalIntent`, lines 689-743, and `IntentsSDK` batch flow — no such check exists).
- `PoaBridge.describeWithdrawal` (lines 313-343) calls `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)` (lines 418-427), which does `withdrawals.find((w) => nep141:${w.data.near_token_id} === assetId)` — matching purely by `assetId`, disregarding `args.index` and `args.withdrawalParams.destinationAddress`.
- The function's own docstring (lines 409-417) acknowledges: "Currently only matches by assetId. This means multiple withdrawals of the same token in a single transaction are not supported."
- Consequence: when `watchWithdrawal` (in `withdrawal-watcher.ts`, lines 20-78) calls `describeWithdrawal` separately for `wid.index=0` and `wid.index=1` (both `assetId: 'nep141:btc.omft.near'`, different `destinationAddress`), both calls run the identical `find` against the same unsorted `response.withdrawals` array and return the **same** first-matching entry — so at least one of the two calls reports a `txHash` (`withdrawal.data.transfer_tx_hash`) that actually corresponds to the other index's destination address, not its own.
- No existing guard (`validateWithdrawal`, `compareAddresses`, `supports()`, or the intents contract's signature/nonce checks) checks for or prevents duplicate-`assetId` batches with distinct destinations, since these only validate individual withdrawal legitimacy, not batch matching integrity.

### Impact Explanation
This is an off-chain status/txHash misreport in the SDK's watcher layer (not an on-chain fund misroute — actual on-chain transfers are executed correctly to their real destinations by the POA bridge). However, an integrator relying on `watchWithdrawal`/`describeWithdrawal` output to attribute completion and `txHash` to a specific user record will attribute the wrong `txHash` to the wrong `destinationAddress` for at least one of the two withdrawals in the batch. This can cause an integrator to credit/refund based on a misattributed transaction hash, matching the "status or hash misreport making an integrator credit or refund twice"-class High impact. The misreport is deterministic and repeatable for any batch containing ≥2 same-`assetId` withdrawals with different destinations.

### Likelihood Explanation
Preconditions: attacker only needs to be an ordinary user constructing (or having an integrator forward) a batch withdrawal with two entries sharing the same `assetId` (e.g., `nep141:btc.omft.near`) but distinct `destinationAddress` values — nothing in `signAndSendWithdrawalIntent`, `createWithdrawalIntents`, or `createWithdrawalIdentifiers` rejects this. Feasibility is high: no special privileges, quotes, or contract-side conditions are required beyond having funds to withdraw; cost is just the withdrawal amounts/fees. Repeatable on every batch containing duplicate-`assetId` different-destination entries.

### Recommendation
Fix `findMatchingWithdrawal` in `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts` to disambiguate entries sharing the same `assetId` by also matching on `destinationAddress` (and/or `amount`/`memo`) rather than `assetId` alone, or reject/serialize batches containing duplicate `assetId` with distinct destinations until the POA API and SDK support proper per-withdrawal correlation (e.g., a correlation ID returned by the bridge).

### Proof of Concept
Vitest test mocking only `poaBridge.httpClient.getWithdrawalStatus`:
1. Mock the HTTP response to return two withdrawal entries for `near_token_id: "btc.omft.near"`: entry A with `transfer_tx_hash: "0xhashA"`, entry B with `transfer_tx_hash: "0xhashB"`.
2. Construct `withdrawalParams[0]` = `{assetId: "nep141:btc.omft.near", destinationAddress: "addrA", ...}` and `withdrawalParams[1]` = `{assetId: "nep141:btc.omft.near", destinationAddress: "addrB", ...}`.
3. Call `bridge.describeWithdrawal({ ...wid for index 1, withdrawalParams: withdrawalParams[1] })`.
4. Assert: `result.txHash` should correspond to entry B (`addrB`'s transfer), i.e. equal `"0xhashB"`.
5. Observe actual behavior: `findMatchingWithdrawal` returns the array's first match (entry A, `"0xhashA"`) regardless of index/destination, so the assertion fails — demonstrating `withdrawalParams[1]`'s destination (`addrB`) is reported with `withdrawalParams[0]`'s txHash (`"0xhashA"`), breaking destination truth. 		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}
