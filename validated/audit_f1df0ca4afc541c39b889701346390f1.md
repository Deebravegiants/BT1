### Title
Missing slippage protection in `SwapFirstAssetTrader::refund_weight` allows sandwiching of XCM fee-swap refunds - (File: `cumulus/primitives/utility/src/lib.rs`)

### Summary
`SwapFirstAssetTrader`, a `WeightTrader` used to pay XCM execution fees by automatically swapping a user-supplied asset into the runtime's target fee asset via `pallet_asset_conversion`, refunds unused weight by calling `SwapCredit::swap_exact_tokens_for_tokens` with `amount_out_min` hard-coded to `None`, disabling the pallet's slippage-protection mechanism (the FRAME analog of Uniswap's `amountOutMinimum`/deadline check) for that swap.

### Finding Description
`buy_weight` swaps the user's supplied asset into the `Target` fee asset using `swap_tokens_for_exact_tokens`, which does enforce a bound (the `fee` amount is the exact output, so slippage is inherently bounded on that side). [1](#0-0) 

However, when unused weight is refunded, the excess `Target` asset is swapped back into the original payment asset via: [2](#0-1) 

Here `amount_out_min` is passed as `None`, which in `pallet_asset_conversion`'s `do_swap_exact_tokens_for_tokens`/`do_swap_exact_credit_tokens_for_tokens` skips the `ProvidedMinimumNotSufficientForSwap` check entirely: [3](#0-2) 

This is functionally the same defect as the Derby report's `Swap.swapTokensMulti` disabling Uniswap's deadline check by passing `block.timestamp`: the protocol-controlled swap that converts one token to another (Uniswap deadline vs. FRAME `amount_out_min`) has its price-protection parameter effectively neutralized (`block.timestamp` always "expires now" in Uniswap; `None` always "accept any price" in `pallet_asset_conversion`). In both cases the swap executes against whatever the AMM pool price is at execution time, with no floor.

`pallet_asset_conversion`'s pool constant-product price can be moved within the same block by anyone able to control transaction ordering (e.g., the block author, or via a preceding `swap_tokens_for_exact_tokens`/`add_liquidity`/`remove_liquidity` extrinsic placed immediately before the XCM-executing extrinsic), because Substrate block authors have complete control over intra-block extrinsic ordering.

### Impact Explanation
Whenever an XCM message pays weight fees through `SwapFirstAssetTrader` and ends up refunding unused weight (e.g., `BuyExecution` over-provisions weight relative to what the message actually consumes — a common, expected occurrence), the refund swap executes at whatever pool price is manipulated to at that moment, with no floor. The XCM sender (an ordinary, unprivileged user) receives less of the refunded asset back than the fair-market amount, and the value is captured by whoever manipulated the pool (e.g., a malicious block author or MEV actor able to influence extrinsic order within the block). This directly parallels the Sherlock M-38 impact: value transferred away from the protocol's clients (in this case, XCM senders receiving fee-asset refunds) to a sandwiching actor.

### Likelihood Explanation
`SwapFirstAssetTrader` is wired into real, non-mock chain configs — Asset Hub Westend, Asset Hub Rococo, Penpal, and the staking-async parachain runtime — so the path is reachable whenever those runtimes process XCM messages paying fees in a non-native asset via this trader. Refunds occur on essentially every such message (since exact weight consumption rarely matches the weight bought), making the vulnerable code path routinely exercised. The attacker only needs the ability to influence extrinsic ordering within a block (block authorship) or to submit competing swap/liquidity extrinsics targeting the same pool in the same block — a capability available to any collator/validator or, to a lesser extent, any user racing for inclusion order, without requiring a trusted role.

### Recommendation
Do not pass `None` for `amount_out_min` in `SwapFirstAssetTrader::refund_weight`. Compute a reasonable minimum acceptable output (e.g., via `QuotePrice::quote_price_exact_tokens_for_tokens` at the time of the refund, with a configurable slippage tolerance) and pass `Some(min_amount)` to `swap_exact_tokens_for_tokens`, mirroring the protection already applied on the `buy_weight` path. If no acceptable minimum can be computed (e.g., quoting fails), prefer keeping the excess in `Target` asset (skip the refund swap) over refunding at an unbounded price.

### Proof of Concept
1. Configure a runtime with `SwapFirstAssetTrader` as in `asset-hub-westend`/`asset-hub-rococo` XCM config, backed by a `pallet_asset_conversion` pool for `Target`/`OtherAsset` with modest liquidity.
2. A user sends an XCM message with `BuyExecution` using `OtherAsset`, over-provisioning weight (bought weight > weight actually consumed by the program).
3. `buy_weight` swaps `OtherAsset` → `Target` for the exact `fee` amount (bounded).
4. In the same block, before this message's extrinsic executes its trailing `refund_weight` step (or via ordering control as block author), a large `swap_tokens_for_exact_tokens`/`add_liquidity` operation shifts the pool's price against `Target`→`OtherAsset` conversion.
5. `refund_weight` executes `swap_exact_tokens_for_tokens(vec![Target, OtherAsset], refund, None)` — since `amount_out_min` is `None`, the swap succeeds at the manipulated, unfavorable price instead of reverting.
6. The user receives less `OtherAsset` refund than the pre-manipulation quote, while the manipulator profits by reversing their price-moving swap afterward — a classic sandwich, exactly analogous to the Derby `Swap.swapTokensMulti` deadline-disabling scenario.
