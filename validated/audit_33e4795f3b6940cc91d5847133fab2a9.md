### Title
Emporium `runAction` can drain protocol/other-users' native ETH held in the contract via unbalanced `op.value` transfers - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
`EmporiumUpgradeable.runAction` executes a signed/proven list of `EmporiumOperation`s, some of which forward native ETH (`op.value`) to arbitrary endpoints via `op.endpoint.call{value: op.value}(op.callData)` or via the user's `HinkalWallet.callHinkalWallet`. The end-of-function invariant check only reconciles balances for tokens present in `circomData.erc20TokenAddresses`. Because the caller/prover freely chooses which token addresses go into that array (it is only self-consistently hashed into `calldataHash`/`signedMessageHash`, never required to include `address(0)`), ETH moved out of the Emporium contract's own balance via `op.value` is never checked against any `deltaAmountChanges` entry, breaking the balance equation the contract otherwise enforces for ERC-20/ETH accounted flows.

### Finding Description
`runAction` computes `balancesBefore`/`balancesAfter` only for `circomData.erc20TokenAddresses` [1](#0-0) , then loops through `stack.ops` executing each operation, forwarding `op.value` in both the stateful (`invokeWallet`) and stateless call paths [2](#0-1) . After execution it enforces `balanceChange >= 0` per token, offset by `deltaAmountChanges`, and reverts with `BalanceChangeShouldBePositive` otherwise [3](#0-2) .

This equality is only enforced for the tokens listed in `circomData.erc20TokenAddresses`. Nothing in `CircomDataBuilder`/`HinkalHelper.performHinkalChecks` forces that array to contain `address(0)` (native ETH) whenever an `EmporiumOperation` moves ETH; the array is merely hashed as part of `calldataHash` (`getHashedCalldata`) and folded into `signedMessageHash`/`formBasicInput`, so the circuit/verifier only guarantees internal self-consistency of whatever token list the caller supplied, not that it covers every asset actually moved [4](#0-3) [5](#0-4) .

The Emporium contract can legitimately hold native ETH (it has a `receive() external payable {}`) [6](#0-5) , e.g. leftover from prior stateless operations, dust, or ETH intentionally parked for a later multi-step signed batch. A relayer/prover submitting a proof for the Emporium action can supply `circomData.erc20TokenAddresses` that excludes `address(0)` while still including `EmporiumOperation`s with non-zero `op.value` targeting an attacker-controlled `op.endpoint`. Since `erc20TokenAddresses` excludes ETH, `getBalancesForArray`/the post-loop equality never observes or constrains the ETH outflow, so the `BalanceChangeShouldBePositive` check cannot catch it — the ETH silently leaves the contract with no corresponding negative `deltaAmountChanges` entry to balance it.

This mirrors the report's bug class ("value moved by an external action but not counted in the balance equation") but manifests as an actual fund-drain rather than a revert: the equality `Δ(Emporium balance) == -Σ(deltaAmountChanges for tracked tokens)` is broken for the untracked ETH asset.

### Impact Explanation
This allows theft of native ETH balance held by the Emporium contract (protocol funds, leftover user ETH, or ETH sent to the contract by mistake/design between operations) to an arbitrary attacker-controlled address, with no accounting or reversion. Per the rules this qualifies as at least High severity ("theft ... of protocol/relay fees" / "unauthorised asset movement") because ETH the wallet/contract holds is moved without being represented in the balance/UTXO accounting that the rest of the protocol relies on for correctness.

### Likelihood Explanation
Medium: it requires (a) the Emporium contract to be holding a nonzero ETH balance at call time (plausible via its `receive()` function or leftover from prior stateless ops) and (b) a party able to submit a valid Hinkal proof/relay call with a crafted `EmporiumStack`/`circomData.erc20TokenAddresses` omitting `address(0)`. Anyone with the ability to run a normal Emporium action (any unprivileged relay/EOA using the standard flow) can attempt this — no admin/owner/relayer-trust assumption beyond the normal actor set is required.

### Recommendation
Enforce that whenever any `EmporiumOperation.value > 0` (i.e., native ETH is moved by an op), `address(0)` must be present in `circomData.erc20TokenAddresses` and included in the pre/post balance snapshot and equality check, OR unconditionally add `address(0)` to the tracked balances in `getBalancesForArray` inside `runAction` regardless of what the caller supplied in `erc20TokenAddresses`, so ETH inflow/outflow is always reconciled against `deltaAmountChanges`/UTXO accounting.

### Proof of Concept
1. Emporium holds `X` wei of ETH (via `receive()` or residual from a prior batch of operations).
2. Attacker (any actor able to submit a Hinkal-proven Emporium action) builds `circomData` with `erc20TokenAddresses = [someERC20]` (deliberately excluding `address(0)`), and `stack.ops = [{ endpoint: attackerAddr, invokeWallet: false, value: X, callData: "" }]`.
3. `getHashedCalldata`/`getSignedMessageHash` are computed self-consistently over this crafted `circomData`, so `performHinkalChecks` in `HinkalHelper.sol` (calldata hash integrity check) passes normally [7](#0-6) .
4. `runAction` executes the op: `attackerAddr.call{value: X}("")` succeeds, draining `X` wei from Emporium [8](#0-7) .
5. The post-loop balance/equality loop only iterates `circomData.erc20TokenAddresses` (`[someERC20]`), so the ETH outflow of `X` wei is never observed, never triggers `BalanceChangeShouldBePositive`, and no UTXO/fee accounting reflects the loss [3](#0-2) .
