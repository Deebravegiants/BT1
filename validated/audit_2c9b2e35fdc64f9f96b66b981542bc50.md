### Title
Webhook `shop` identity is trusted from an unauthenticated header while the HMAC only covers the request body - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating an HMAC over the raw body, then hands the handler a `shop` value read directly from the `x-shopify-shop-domain`/`shopify-shop-domain` header — a value that is never part of the signed material.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `HmacValidator.validate_signature` computes/compares the signature strictly against that signable string [2](#0-1) . Meanwhile `Request#shop` is read straight out of the (attacker-controlled, in a self-hosted webhook endpoint) HTTP header with no cross-check against the signed payload [3](#0-2) . `Registry.process` validates the HMAC and then immediately constructs `WebhookMetadata` using this unauthenticated `request.shop` [4](#0-3) , and the documented handler pattern uses `data.shop` directly as the tenant key for downstream work (e.g., `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) [5](#0-4) .

This breaks the intended identity binding: `hmac_valid(body, secret) == true` is treated as proof that `shop-domain header == originating shop`, but those are two independent, unbound values. Since the webhook HMAC secret (`Context.api_secret_key`, the app's client secret) is the same across every shop that installed the app — not a per-shop secret — any tenant of the app that receives legitimate webhooks can capture a valid `(raw_body, hmac)` pair from their own shop's webhook delivery and replay it to the app's webhook endpoint with the `shop-domain` header swapped to a victim shop. The signature still validates (it only covers `raw_body`), so `Registry.process` calls the handler with `shop: <victim-shop>` even though the body/HMAC only proves authenticity for the attacker's own shop.

### Impact Explanation
This is a cross-tenant identity confusion: an app built following this gem's documented pattern of keying work off `WebhookMetadata#shop` will process/attribute webhook data under a shop domain that the HMAC never authenticated. Depending on what the app does with `data.body` combined with `data.shop` (e.g., writing order/customer data keyed by shop, or triggering shop-scoped side effects), this enables cross-tenant data injection/corruption using only a legitimately-obtained webhook from the attacker's own low-privilege shop install — no `access_token`, no `api_secret_key` leak, and no privileged account needed.

### Likelihood Explanation
Any merchant/developer who installs the app (a normal, unprivileged action) automatically receives real webhooks with a valid HMAC for arbitrary bodies of their choosing (e.g., by editing their own store's products/orders to control the JSON body). Replaying that request to the app's public webhook endpoint with a forged `shop-domain` header requires no special access — just knowledge of the endpoint URL, which is typically the app's public callback path.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook-id`) into the value that is authenticated, rather than trusting it from an unsigned header:
- Prefer deriving the shop from a server-side registration/session lookup, or
- Include the shop domain in the signable string used for HMAC verification (matching what other Shopify SDKs do by validating the header value against the known set of shops that have webhooks registered, or by requiring the host app to independently confirm `request.shop` is a shop with an active session/registration before trusting `data.shop`), and document this requirement prominently since `WebhookMetadata#shop` is otherwise unauthenticated.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` (a normal, unprivileged installation).
2. Attacker triggers/observes a legitimate webhook delivery, capturing `raw_body` and the corresponding `x-shopify-hmac-sha256` value (valid because it was signed with the app's single, shared `api_secret_key`).
3. Attacker POSTs to the app's webhook endpoint reusing the same `raw_body` + `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `HmacValidator.validate` succeeds (it only checks `raw_body` against the HMAC) [6](#0-5) ; `Registry.process` invokes the handler with `WebhookMetadata(shop: "victim.myshopify.com", body: <attacker-chosen>, ...)` [4](#0-3) , causing the host app to act on `victim.myshopify.com`'s behalf using attacker-controlled body content.
