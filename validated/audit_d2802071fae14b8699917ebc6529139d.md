## Finding [1](#0-0) 

### Title
Stale user authorization status used for signup enrollment without re-validation - (File: src/plans/mod.rs)

### Summary
The `MasterPlan::scan_remaining_qr_codes`/`scan_user_qr_code` flow validates the user's QR-code session with the backend exactly once via `verify_user_qr_code`, caching the resulting `UserData` (authorization/eligibility status) inside `QrCodes::Both`. Unlike the operator QR-code, which carries a `timestamp` that is checked against `operator_qr_expiration_time` before being reused [2](#0-1) , the user's authorization status has no expiration tracking at all and is carried unchanged through the rest of the signup — including a fixed delay, biometric capture, and the biometric pipeline (which can itself take up to `MODEL_TIMEOUT` = 90s plus capture time) — before finally being used to build enrollment credentials and complete the signup [3](#0-2) . This mirrors the reported bug class: a value obtained once (share price / here, authorization state) is used later in a critical decision (fund transfer / here, signup enrollment) without being refreshed to reflect state changes that occurred in the intervening time.

### Finding Description
`verify_user_qr_code` calls `backend::user_status::request`, which returns a `UserData` struct describing whether the user is currently authorized to sign up (validity, `user_centric_signup`, keys, etc.) [4](#0-3) . This result is captured once in `handle_user_qr_code` and stored into the `QrCodes::Both` variant [5](#0-4) [6](#0-5) .

Only the *operator* QR-code carries a `timestamp` field, which is explicitly checked for staleness before being reused across the flow (`operator_data.timestamp.elapsed() < operator_qr_expiration_time`) [7](#0-6) . The user's `UserData` (the actual authorization decision) has no equivalent timestamp or expiration check anywhere in `QrCodes`, `ResolvedQrCodes`, or `do_signup`.

After the QR codes are resolved, `do_signup` proceeds through a multi-second/multi-minute pipeline — a fixed 3s sleep, `biometric_capture`, and `biometric_pipeline` (bounded by `MODEL_TIMEOUT` = 90s plus timeouts for iris/occlusion/face-identifier agents) [8](#0-7) [9](#0-8)  — before the originally fetched, now-stale `user_data` is used to build the `personal_custody_package::Credentials` and to determine `user_centric_signup` enrollment success/failure [10](#0-9) . No re-check of the user's backend authorization status is performed immediately before this consequential enrollment decision.

### Impact Explanation
If the user's authorization/session state on the backend changes during the capture+pipeline window (e.g., the session is consumed/invalidated elsewhere, revoked, or expires), the orb still completes enrollment and uploads the personal custody package using the stale, now-invalid `UserData`, potentially producing an unauthorized or misattributed signup. This is analogous to the reported DeFi issue where a stale price led to using outdated state for a critical financial operation — here the "stale state" is the once-fetched signup authorization decision, and the critical operation is biometric enrollment/credential issuance rather than a value transfer.

### Likelihood Explanation
Likelihood is limited by how long the backend authorization session normally stays valid and how quickly it could be invalidated during the capture window, but the gap between validation and use (seconds to ~90+ seconds for biometric pipeline alone, plus capture time) is deterministic and always present in every signup, since no re-validation call exists in this window.

### Recommendation
Track a timestamp for the user's `UserData` similarly to `OperatorData`, and re-validate (or at minimum re-check freshness against a configurable expiration window) the user's authorization status via `backend::user_status::request` immediately before using it to build credentials and enroll the user, rather than relying solely on the value captured at QR-code scan time.

### Proof of Concept
1. Scan operator QR-code, then user QR-code; `verify_user_qr_code` succeeds and caches `UserData` in `QrCodes::Both`.
2. On the backend, invalidate/expire the user's session (e.g., due to a concurrent signup attempt, session timeout, or fraud flag) during the several-second-to-90-second window while `biometric_capture` and `biometric_pipeline` run.
3. `do_signup` proceeds to use the original (now stale) `user_data` to build `personal_custody_package::Credentials` and complete enrollment, with no intermediate call re-verifying the user's authorization status [11](#0-10) .
