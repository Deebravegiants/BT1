This confirms the vulnerability. The gem's own docs (`docs/usage/webhooks.md#L14`, `#L26`) tell developers to trust `data.shop` as the tenant identifier for dispatching jobs (`perform_later(topic: data.topic, shop_domain: data.shop, ...)`), while the HMAC signature computed by `ShopifyAPI::Webhooks::Request` only covers the raw body, not the shop header. This is a direct match for the allowed analog class: "a field acted on but not covered by the HMAC."

### Title
Webhook `shop` field is trusted for tenant dispatch but is not covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives its HMAC-signable content solely from the raw request body, while the `shop` (tenant identifier) is read from an HTTP header that is never included in the signed payload. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then forwards `request.shop` verbatim to the app's webhook handler as the trusted tenant key, per the gem's own documented usage pattern.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
while `shop` is read independently from the `shopify-shop-domain`/`x-shopify-shop-domain` header: [2](#0-1) 

`HmacValidator.validate` computes the signature only from `verifiable_query.to_signable_string` and compares it to the `hmac` header: [3](#0-2) 

`Registry.process` accepts any request that passes this body-only HMAC check, then uses the unauthenticated `request.shop` value to build `WebhookMetadata` passed straight to the app's handler: [4](#0-3) 

The identity binding broken here is: **`shop` used for tenant dispatch ≠ `shop` covered by the HMAC that authenticates the request as genuinely originating from Shopify for that shop.** Since only the body is signed, a request with a given body+HMAC pair remains valid under `HmacValidator.validate` no matter what value is placed in the `shop-domain` header, because that header is never part of `to_signable_string`.

The gem's own documentation instructs developers to trust `data.shop` as the authoritative tenant key after `Registry.process` succeeds: [5](#0-4) 

### Impact Explanation
An attacker who controls a shop that has the target app installed receives genuine, validly-HMAC-signed webhooks from Shopify for their own shop/body content. Because the HMAC only signs the body, that attacker can resend the exact same body+HMAC pair to the app's webhook endpoint while substituting the `shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` still returns `true` (the body signature matches), so `Registry.process` calls the handler with `WebhookMetadata#shop` set to the victim's domain even though the payload was never actually generated for that shop. Any host application following the gem's documented pattern (keying jobs/records by `data.shop`) will process/inject attacker-controlled webhook content under the victim tenant's identity — a cross-tenant data injection/impersonation using only a validly-signed webhook the attacker legitimately received for their own shop.

### Likelihood Explanation
Requires only that the attacker operates a shop with the target app installed (a normal, unprivileged merchant relationship) — no access to the app's `client_secret`, no stolen tokens, and no interception of Shopify's traffic. The webhook endpoint is by definition internet-facing and unauthenticated aside from this HMAC check.

### Recommendation
Include the shop domain (and other trust-relevant headers such as topic/api-version/webhook-id) in the HMAC-signable string, or otherwise cryptographically bind the `shop` header value to the signed payload before it is exposed to `WebhookMetadata`/handler code.

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com` and receives a legitimate webhook, e.g. `orders/create`, with body `B` and header `shopify-hmac-sha256: H`, where `H = HMAC-SHA256(secret, B)`.
2. Attacker replays this exact request to the app's webhook endpoint, keeping body `B` and header `shopify-hmac-sha256: H` unchanged, but sets `shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `B` only and matches `H` — validation succeeds.
4. `handler.handle(data: WebhookMetadata.new(..., shop: "victim.myshopify.com", body: parsed_body_of_B, ...))` is invoked, and the host app (per the gem's documented pattern) processes/stores this attacker-supplied body under the victim shop's tenant identity.
