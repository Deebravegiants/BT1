## Title
Webhook `shop`/`topic`/`webhook_id` identity fields are trusted from unauthenticated headers while only the raw body is HMAC-covered - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw request body [1](#0-0) . The `shop`, `topic`, `api_version`, and `webhook_id` values that are handed to the app's handler as trusted identity/routing metadata (`WebhookMetadata`) come exclusively from HTTP headers, which `to_signable_string` never includes in the HMAC-signed payload [2](#0-1) .

### Finding Description
`Utils::HmacValidator.validate` computes the HMAC purely from `verifiable_query.to_signable_string`, and for `Webhooks::Request` that method returns only `@raw_body`: [3](#0-2) 
Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are read straight from caller-supplied headers with no cryptographic binding to the signed body: [4](#0-3) 
`Registry.process` validates the HMAC and then dispatches to the handler using `request.topic` and `request.shop` taken from those unauthenticated headers: [1](#0-0) 

The broken identity equality is: **`shop` field trusted by the handler == `shop` field authenticated by the HMAC**. In this gem's implementation, the HMAC only authenticates the byte-for-byte body content; it never authenticates which shop, topic, or webhook id that body is claimed to belong to.

### Impact Explanation
This matches the report's bug class ("a field acted on but not covered by the HMAC") but the practical exploitability is constrained: to produce a request that passes `Utils::HmacValidator.validate`, an attacker still needs a `(raw_body, hmac)` pair that is valid under the app's `api_secret_key` (or `old_api_secret_key`) — something only Shopify (holder of the secret) can produce. An attacker with no credentials cannot forge an arbitrary body+HMAC from scratch. The realistic abuse case is limited to an attacker who can *capture* one legitimately-signed webhook delivery (e.g. from a shared/misconfigured endpoint, logging, or a multi-tenant host app that fans out raw bodies) and then **replay it with a different `shopify-shop-domain` header** to make the host application process/attribute that data under a different tenant's context, since `Registry.process` will still validate successfully (the header change doesn't affect the HMAC) and will pass the attacker-chosen `shop` value straight to the handler as trusted. This is a cross-tenant identity-binding gap, but it requires possession of an already-signed webhook body, which is a meaningfully higher bar than the zero-credential unrigged scenarios the rules target (no leaked secret, but a captured, valid, signed message is still an access precondition not freely available to "any internet user").

### Likelihood Explanation
Low-to-moderate. Exploitation requires the attacker to first obtain a genuine `(body, hmac)` webhook pair for the target application (e.g., via network capture, a logging leak, or an SSRF elsewhere), which is not something an anonymous internet user can produce on demand. Absent that precondition, this is a design characteristic (Shopify's HMAC scheme only signs the body) rather than a bug unique to this gem's code, and host applications are expected to also validate `shop` against their own tenant/session records — the gem's docs do not claim to authenticate the shop header cryptographically.

### Recommendation
- Do not present `request.shop`, `request.topic`, or `request.webhook_id` as authenticated values without qualification in documentation/comments; make explicit that only `raw_body` bytes are HMAC-verified.
- Where feasible, cross-check `request.shop` against an existing, previously-established session/tenant record (e.g., a stored shop for the given `webhook_id`/topic) before invoking the handler, rather than trusting the header value implicitly.
- Consider surfacing a warning/log when the header-derived `shop` cannot be corroborated against any known session, to reduce blind trust in header-derived identity in `WebhookMetadata`.

### Proof of Concept
1. Capture one legitimately delivered webhook payload and its `shopify-hmac-sha256` header for shop A (e.g. via a shared logging pipeline or network vantage point).
2. Resend the identical `raw_body` and `hmac` header unchanged, but replace the `shopify-shop-domain` header with shop B's domain.
3. `Utils::HmacValidator.validate(request)` still returns `true` because only `@raw_body` is covered by the signature [3](#0-2) .
4. `Registry.process` dispatches the handler with `shop: request.shop` = shop B's domain and the body/data that was actually generated for shop A [5](#0-4) , causing the host application to attribute shop A's data to shop B's tenant context.

        sig { params(request: Request).void }
        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
