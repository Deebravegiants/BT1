### Title
Escrow accounting drifts from actual balance for rebasing tokens, enabling theft across unrelated orders - (File: `evm/src/apps/IntentGatewayV2.sol`, `evm/src/apps/intentsv2/IntrinsicIntents.sol`)

### Summary
`IntentGatewayV2` mitigates fee-on-transfer tokens by measuring the *actual* balance delta at deposit time and recording that measured amount as the order's escrow, but this measurement is a one-time snapshot. For a rebasing token (e.g. AMPL-style tokens, whose balance of every holder changes globally whenever `rebase()`/`_gonsPerFragment` changes), the gateway's stored escrow accounting (`_orders[commitment][token]`) becomes stale relative to the token contract's real balance for the gateway. Withdrawals (`cancelOrder`, `fillOrder`) pay out the stale recorded amount rather than a share proportional to the gateway's current actual balance, exactly the root cause identified in the THORChain H-01 report.

### Finding Description
On `placeOrder`, the gateway measures balance-before/after to determine the "received" amount for each input and stores that fixed number in `order.inputs[i].amount`/the escrow ledger: [1](#0-0) 

This correctly compensates for a one-time deduction (fee-on-transfer), as validated by the FOT test suite: [2](#0-1) 

However, once escrowed, `_orders[commitment][token]` is treated by `_cancelSameChain` and `_fillSameChain` as a permanently accurate, static claim on the gateway's token balance, and is transferred out via `_withdraw` without re-checking whether the gateway's *actual current* token balance still backs it: [3](#0-2) [4](#0-3) 

If a whitelisted input token is a rebasing token whose supply/balances are globally adjusted (via a `_gonsPerFragment`-style mechanism, exactly as AMPL in the original report), the sum of all outstanding `_orders[...]` entries for that token can diverge from the gateway's true balance after a rebase occurs between `placeOrder` and a later `cancelOrder`/`fillOrder`. Since withdrawals pay out the stale recorded number of tokens rather than a value derived from the live balance, whichever order is settled first can consume tokens that are actually needed to back a different, still-open order for the same token — draining funds belonging to other users, or leaving the last withdrawer unable to redeem their full recorded escrow (locked funds), mirroring steps 5–10 of the original AMPL exploit almost exactly.

### Impact Explanation
This allows theft of escrowed funds belonging to other orders/users sharing the same rebasing input token, or permanent underfunding/freezing of a legitimate order's payout — both concrete impacts explicitly in scope (theft and permanent freezing of funds) and reachable by any unprivileged user simply by placing and later cancelling/filling orders around a token rebase event, with no privileged role required.

### Likelihood Explanation
Likelihood depends on whether the deployment's input-token whitelist ever includes a rebasing token. The gateway shows deliberate, tested handling for fee-on-transfer tokens but no equivalent handling for globally rebasing balances, so if such a token is ever whitelisted, the exploit path is directly reachable by a single `placeOrder` + rebase-timed `cancelOrder`/`fillOrder`, matching the exact confirmed-High severity precedent in the source report (rebasing tokens are the higher-severity, distinct root cause from fee-on-transfer, per the judge's final ruling).

### Recommendation
Do not treat `_orders[commitment][token]` as an immutable claim on a fixed token count for tokens whose balance mechanics are non-static. Either explicitly exclude rebasing tokens from the input-token whitelist, or track escrow as a share of the gateway's total balance for that token (proportional accounting) and settle withdrawals against the live `balanceOf(address(this))` rather than the value snapshotted at `placeOrder` time.

### Proof of Concept
1. User A calls `placeOrder` with a rebasing token as input; gateway measures balance delta and records `_orders[commitment][token] = 1000`.
2. The rebasing token's `rebase()` is invoked (or self-triggered/frontrun), globally reducing every holder's balance, so the gateway's actual `balanceOf(address(this))` for that token drops to 500 while `_orders[...]` still reads 1000 for A and any newly placed order.
3. User B places a second order for the same token, gateway measures delta and records `_orders[commitment2][token] = 1000`; gateway's actual balance is now some value less than the sum of `1000 + 1000` due to the earlier rebase.
4. User A cancels their order first via `_cancelSameChain`, which reads `_orders[commitment][token] = 1000` and calls `_withdraw` to pay out 1000 tokens — more than A's proportional share of the shrunk pool.
5. User B later attempts to cancel/fill and finds the gateway's actual balance insufficient to cover their recorded `1000` escrow, resulting in a failed transfer or a reduced payout — funds have effectively been transferred from B's escrow to A.

    function _cancelSameChain(Order calldata order, bytes32 commitment) internal {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

        uint256 inputsLen = order.inputs.length;
        TokenInfo[] memory remainingTokens = new TokenInfo[](inputsLen);
        bool hasEscrow = false;
        for (uint256 i; i < inputsLen;) {
            address token = address(uint160(uint256(order.inputs[i].token)));
            uint256 escrowed = _orders[commitment][token];
            if (escrowed > 0) hasEscrow = true;
            remainingTokens[i] = TokenInfo({token: order.inputs[i].token, amount: escrowed});
            unchecked {
                ++i;
            }
        }
        if (!hasEscrow) revert UnknownOrder();

        WithdrawalRequest memory body =
            WithdrawalRequest({commitment: commitment, tokens: remainingTokens, beneficiary: order.user});

        _withdraw(body, true, true);
    }
