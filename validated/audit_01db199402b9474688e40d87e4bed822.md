### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`, `lib/shopify_api/utils/hmac_validator.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by verifying an HMAC over the raw request body, but the `shop` value that identifies *which tenant* the webhook belongs to is read from an HTTP header that is not included in that HMAC. Because the `api_secret_key` is a single, app-wide secret shared across every shop that installs the app (not a per-shop secret), any actor who can get one valid HMAC-signed body from Shopify for their own shop can replay that body with a forged `shop-domain` header pointing at a different, victim shop, and the gem will accept it as authentic and hand it to the app's handler as if it came from the victim.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` validates a webhook using: [1](#0-0) 

The HMAC check is delegated to `Utils::HmacValidator.validate`, which computes the signature over `verifiable_query.to_signable_string`: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` is defined to be **only the raw body** — it does not include `topic`, `shop`, `api_version`, or `webhook_id`: [3](#0-2) 

Yet `shop` (along with `topic`, `webhook_id`, `api_version`) — all values pulled from unauthenticated headers — is passed straight into `WebhookMetadata` and delivered to the app's registered handler as the trusted tenant identifier: [4](#0-3) [5](#0-4) 

The documented handler contract explicitly instructs app developers to trust `data.shop` as "The shop domain of the webhook": [6](#0-5) 

This breaks the intended identity binding:

`shop value used to attribute/process the webhook (request.shop, header-derived)` ≠ `shop value actually covered by the cryptographic proof (HMAC over raw_body only)`

Before the attack: attacker owns Shop A, which has the app installed, and receives a legitimately-signed webhook body `B` with a valid `x-shopify-hmac-sha256` for `B` (computed with the app's single, shared `api_secret_key`).

After the attack: attacker POSTs the exact same body `B` and its valid HMAC to the app's webhook endpoint, but sets `x-shopify-shop-domain` to Shop B (the victim's domain, also an app installer). `HmacValidator.validate` still returns `true` because the signable string (`B`) and HMAC match — the shop header was never part of what was signed. `Registry.process` then invokes the handler with `WebhookMetadata.new(shop: "shop-b.myshopify.com", body: parsed(B), ...)`, causing the app to process/attribute attacker-controlled data as if it originated from Shop B.

### Impact Explanation
This lets a low-privilege attacker (merely an installer of the target app on their own store) forge webhook events that are misattributed to a different tenant. Depending on how the host app trusts `data.shop` (e.g., to look up the correct shop's access token/session, update per-shop order/customer/inventory records, or trigger per-shop business logic), this enables cross-tenant data injection/corruption — the app acts on Shop B's tenant context using attacker-supplied payload content. This matches the "cross-tenant access" impact criterion.

### Likelihood Explanation
Likelihood is high for any app that has more than one shop installed (the normal SaaS multi-tenant case), since the `api_secret_key` is identical for all tenants of a given app. No secrets, TLS interception, or privileged accounts are required — only that the attacker installs the app on their own shop (a normal, unprivileged action) and can trigger at least one webhook delivery with content they influence (many webhook topics, e.g. `products/update`, `orders/create`, include attacker/merchant-controlled field values in the body).

### Recommendation
Include the tenant-identifying fields (`shop-domain`, `topic`, `api-version`, `webhook-id`) in the value that is HMAC-verified, or independently authenticate the `shop` header against the session/shop that is expected to be receiving webhooks (e.g., cross-check `request.shop` against records of shops that have that specific `webhook_id` registered) before trusting it in `WebhookMetadata`. At minimum, document prominently that `data.shop` from `WebhookMetadata` is **not** cryptographically bound by the HMAC and must not be used as an authoritative tenant identifier without additional server-side verification (e.g., verifying the webhook id belongs to the claimed shop via the app's own registration/database).

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com` and `victim-shop.myshopify.com` (both are legitimate tenants of the same third-party app, sharing one `api_secret_key`).
2. Attacker triggers an event on their own shop (e.g., updates a product) and captures Shopify's legitimate webhook POST: raw body `B` and header `x-shopify-hmac-sha256: H` (valid for `B`).
3. Attacker crafts a new POST to the app's webhook endpoint with the same body `B` and header `H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `request.to_signable_string` (== `B`) and compares to `H` — validation succeeds (as shown by `lib/shopify_api/utils/hmac_validator.rb:26-31` and `lib/shopify_api/webhooks/request.rb:35-38`).
5. `handler.handle(data: WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...))` is invoked, so the app processes attacker-supplied content as belonging to the victim shop.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
