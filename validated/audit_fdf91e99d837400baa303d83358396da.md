### Title
Unconstrained `calldataHash` public signal lets an attacker rebind a valid proof to a different `relay`/`feeStructure`/`hookData` and steal user funds - (File: circuits/MainEVMCircuit.circom, contracts/HinkalHelper.sol, contracts/CircomDataBuilder.sol)

### Summary
`CircomData.calldataHash` is meant to cryptographically bind a set of "auxiliary" transaction fields (`relay`, `feeStructure`, `hookData`, `externalActionData`, `onChainCreation`, `originalSender`, `extraData`, `slippageValues`, `emporiumMessage`, `encryptedOutputs`, `onChainEncryptedOutput`) to a specific zk-proof, so that a relayer/attacker cannot swap them after the user has generated the proof. In practice this binding is illusory: `calldataHash` is declared as a public circuit input but is never used in any constraint inside the circuit, so it does not actually restrict the proof at all.

### Finding Description
`CircomDataBuilder.getHashedCalldata` hashes the auxiliary fields into `circomData.calldataHash` [1](#0-0) , and `HinkalHelper.performHinkalChecks` only verifies this hash matches on-chain, purely as an EVM-side recomputation: [2](#0-1) 

`calldataHash` is then passed as one of the public inputs fed to the Groth16 verifier via `formBasicInput`: [3](#0-2) 

Inside `MainEVMCircuit.circom`, `calldataHash` is declared as a signal input (`signal input calldataHash;`) but, unlike `signedMessageHash` (which is wired into `SignatureVerifier` and thereby forces an EdDSA check), `calldataHash` is never assigned via `<==` nor checked via `===` against any other signal or subcomponent in the entire template body: [4](#0-3) [5](#0-4) 

Compare with `signedMessageHash`, which *is* actually wired into the EdDSA verifier and therefore genuinely constrained: [6](#0-5) 

Because an R1CS/Groth16 constraint system places no restriction on a public signal that never appears in any constraint, a previously-generated valid proof `(a, b, c)` remains valid for **any** value placed in the `calldataHash` slot of the public input array at verification time. This means the on-chain "authentication" of `relay`, `feeStructure`, `hookData`, `externalActionData`, `onChainCreation`, `originalSender`, `extraData`, `slippageValues`, `emporiumMessage`, `encryptedOutputs`, and `onChainEncryptedOutput` — which are supposed to be tied to the user's signed intent through `calldataHash` — provides no real cryptographic guarantee: an attacker only needs `getHashedCalldata(modifiedCircomData) == modifiedCalldataHash` to hold, which they trivially control since they can freely choose the modified fields and recompute the hash. This breaks the equality "the proof authorizes exactly the CircomData the user signed" for every field that is only covered by `calldataHash` (as opposed to fields directly wired into real circuit constraints, e.g., `erc20TokenAddresses`, `amountChanges`, `inputNullifiers`, `outCommitments`, which remain genuinely bound).

### Impact Explanation
The most direct exploitation path is fee/relay manipulation: `feeStructure` and `relay` are only protected by the broken `calldataHash` binding, and `Hinkal._internalTransact` directly uses `circomData.feeStructure` and `circomData.relay` to compute and pay out `relayFee` from the user's withdrawn funds: [7](#0-6) 

A malicious/observing relay can intercept a user's transaction (or replay a valid proof it was given to submit), replace `relay` with its own address and inflate `feeStructure.flatFee`/`feeStructure.variableRate`, recompute `calldataHash` accordingly, and resubmit — the SNARK proof still verifies (since `calldataHash` is unconstrained) and `performHinkalChecks`'s hash check still passes (since it is self-consistent), resulting in direct theft of user funds beyond what the user authorized. Similarly `hookData.postHookContract`/`preHookContract` can be swapped to attacker-controlled contracts that receive the full `circomData` and execute arbitrary logic via `ITransactHook`/`IPreTransactHook` [8](#0-7) , and `originalSender`/`extraData` can likewise be altered without invalidating the proof. This qualifies as Critical (direct theft of in-flight user funds / unauthorised asset movement never authorised by the prover).

### Likelihood Explanation
Any relay that processes user transactions (the intended untrusted-relay model of Hinkal) can perform this attack trivially: it only needs to modify calldata fields and recompute a keccak256 hash before calling `transact` with the same `(a,b,c)` proof and same core public inputs (root hash, nullifiers, commitments, amounts, signed message hash). No cryptographic break of Groth16 or Poseidon is required — it exploits a missing constraint in the circuit definition itself, so it is deterministic and repeatable for every transaction that flows through the affected fields.

### Recommendation
Add explicit circuit constraints binding `calldataHash` to the actual off-chain-hashed content, or restructure so that every field currently hashed into `calldataHash` (`relay`, `feeStructure`, `hookData`, `externalActionData`, `onChainCreation`, `originalSender`, `extraData`, `slippageValues`, `emporiumMessage`, `encryptedOutputs`, `onChainEncryptedOutput`) is either: (a) passed as genuine circuit public inputs that are wired into real constraints (as is done for `erc20TokenAddresses`/`amountChanges`/nullifiers/commitments), or (b) incorporated into the `signedMessageHash` preimage that is actually verified by `SignatureVerifier`, so that tampering with any of these fields invalidates the EdDSA/proof check rather than relying on an unconstrained "free" signal.

### Proof of Concept
1. User generates a valid proof for a withdrawal with `relay = R1`, `feeStructure = {flatFee: 0, variableRate: 10}` and computes `calldataHash1 = getHashedCalldata(circomData1)`.
2. Malicious relay `R2` intercepts the call before it lands on-chain (or is simply the intended relay), constructs `circomData2` identical except `relay = R2`, `feeStructure.variableRate = 10000` (i.e., taking the entire withdrawal as fee), and computes `calldataHash2 = getHashedCalldata(circomData2)`.
3. `R2` calls `Hinkal.transact(a, b, c, dimensions, circomData2)` reusing the original proof `(a, b, c)`.
4. `hinkalHelper.performHinkalChecks` recomputes `getHashedCalldata(circomData2) == circomData2.calldataHash` — passes trivially since both are self-consistently derived from `circomData2` [2](#0-1) .
5. `verifyProof(a, b, c, inputForCircom, ...)` still succeeds because `calldataHash` (now holding `calldataHash2`) is not constrained anywhere inside `MainEVMCircuit.circom`, so the Groth16 verification equation is unaffected by its value.
6. `_internalTransact` pays `relayFee` computed from the attacker's `feeStructure` to `R2` [7](#0-6) , draining the user's withdrawal to the malicious relay instead of the amount the user actually signed for.

  eddsaVerifier.enabled <== 1;
  eddsaVerifier.Ax <== spendingPublicKey[0];
  eddsaVerifier.Ay <== spendingPublicKey[1];
  eddsaVerifier.R8x <== eddsaSignature[0];
  eddsaVerifier.R8y <== eddsaSignature[1];
  eddsaVerifier.S <== eddsaSignature[2];

}
