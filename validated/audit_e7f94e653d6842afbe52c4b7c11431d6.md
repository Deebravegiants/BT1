### Title
Webhook tenant identity (`shop`) is not bound by the HMAC signature, allowing shop-header spoofing in `ShopifyAPI::Webhooks::Registry.process` - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while `Request#shop` (the tenant identity later trusted by the app) is read from the unsigned `X-Shopify-Shop-Domain` header. `Registry.process` verifies the HMAC over the body only, then forwards the unauthenticated `shop` value straight to the app's webhook handler.

### Finding Description
`Utils::HmacValidator.validate` computes and compares the HMAC solely against `to_signable_string`, which for webhook requests is defined as: [1](#0-0) 

Meanwhile `shop` (the tenant identifier) is pulled directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is never part of the signed material: [2](#0-1) [3](#0-2) 

`Registry.process` validates the HMAC and then immediately hands the unauthenticated `request.shop` to the app-supplied handler as the tenant context, with no cross-check that the header value matches any property of the signed body: [4](#0-3) 

The equality this breaks is: `shop_authenticated_by_hmac == shop_acted_on_by_handler`. In fact `shop_authenticated_by_hmac` is undefined — only the *body bytes* are authenticated, not the `shop` header — so the equality silently fails whenever the two values diverge.

### Impact Explanation
An unprivileged internet user who can install the target app on their own store (the normal, free installation flow for any Shopify app) receives genuine, correctly-HMAC-signed webhook deliveries for their own shop. Because the signature covers only the JSON body and not the `X-Shopify-Shop-Domain` header, that attacker can capture one such valid `(body, hmac)` pair and replay it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to a victim shop's domain. `HmacValidator.validate` still returns `true` (the body/HMAC pair is legitimately signed with the app's secret by Shopify), and `Registry.process` passes the forged `shop` value into `WebhookMetadata`, which the host application will typically use to look up/act on the victim tenant's data — a cross-tenant access path that requires no possession of `api_secret_key`, access tokens, or any privileged credential.

### Likelihood Explanation
Likelihood is bounded by two factors that keep this at a realistic but not "trivial" severity: (1) the attacker needs at least one genuine signed webhook body to replay (obtainable simply by installing the app once, which is not privileged), and (2) the value of the attack depends on whether the specific webhook topic's body content is shop-independent or attacker-controllable enough to be useful against another tenant (e.g., topics whose payload doesn't itself embed a shop id that the handler double-checks). Any host app that relies on the gem's `WebhookMetadata#shop` as an implicit trust boundary (as the gem's own API surface encourages, since it hands `shop` to the handler right after "validating" the webhook) is exposed.

### Recommendation
- Extend `VerifiableQuery`/`to_signable_string` for `Webhooks::Request` (or add a separate check in `Registry.process`) to bind the `shop-domain` header into what's verified, or otherwise require host apps to independently verify `shop` against an already-authenticated session/store record before trusting it — and document this loudly, since the current API implies the header is safe to consume once `HmacValidator.validate` passes.
- At minimum, mark `Request#shop`/`topic`/`api_version`/`webhook_id` as unauthenticated header data in the gem's documentation and in `WebhookMetadata`, making explicit that only the raw body is HMAC-verified.

### Proof of Concept
1. Attacker installs the target app on their own (unprivileged) development/trial store `attacker-shop.myshopify.com`, completing normal OAuth.
2. Shopify delivers a legitimate webhook, e.g. `POST /webhooks` with body `{}` and headers:
   - `X-Shopify-Hmac-Sha256: <valid hmac of "{}">`
   - `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`
   - `X-Shopify-Topic: some/topic`
3. Attacker replays the exact same body and `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, but changes `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: "{}", headers: forged_headers)` is constructed; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC only over `"{}"` and succeeds (as shown in `test/webhooks/registry_test.rb` setup, where only body+secret are hashed): [5](#0-4) 
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` despite the request never having been signed for that shop, and the host app processes/acts on data as if it legitimately came from the victim's store.

Note: I could not verify within this gem's index how every downstream `WebhookHandler` implementation in the wild uses `shop` (that logic lives in host applications), so the ultimate blast radius depends on host-app behavior; the root cause identified here — the identity/authentication gap between the HMAC-covered body and the header-derived `shop` — is fully confirmed within this gem's own code.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
