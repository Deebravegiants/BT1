### Title
Webhook shop-identity confusion — `shop-domain` header trusted despite not being covered by HMAC signature - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, never the `X-Shopify-Shop-Domain` (or topic/webhook-id) header. `Registry.process` validates the HMAC over that raw body, then unconditionally trusts `request.shop` (parsed straight from the unauthenticated header) to identify which tenant the webhook belongs to. Because every shop installing a given app shares the same `api_secret_key`, any low-privileged actor who can trigger one legitimate webhook delivery to their own store can replay that exact body/HMAC pair while swapping the shop-domain header to point at an arbitrary victim shop, and the HMAC check will still pass.

### Finding Description
The identity binding that should hold is:
`shop bound by HMAC == shop acted on by the webhook handler`

In this gem that binding is broken:

- `Request#to_signable_string` only returns `@raw_body`: [1](#0-0) 
- `Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic tie to the HMAC: [2](#0-1) 
- `Registry.process` validates only `Utils::HmacValidator.validate(request)` (i.e. body signature) and then forwards `request.shop` unchecked into the handler payload: [3](#0-2) 
- `HmacValidator.validate` computes the digest solely over `verifiable_query.to_signable_string` (the body, in this case) against `Context.api_secret_key`: [4](#0-3) 

Because the `api_secret_key` is shared across every merchant that installs the same public app, any merchant (an unprivileged internet user with respect to other tenants of the app) can:
1. Install the app on their own store and receive one legitimate webhook (body `B`, valid `hmac-sha256` header `H` computed with the shared secret).
2. Replay `B`/`H` to the app's webhook endpoint verbatim, but substitute the `X-Shopify-Shop-Domain` header with a victim shop's domain.
3. `HmacValidator.validate` still succeeds because it only checks that `H` is a valid HMAC of `B` — it never checks which shop `B`/`H` were issued for.
4. `Registry.process` then calls the app's handler with `WebhookMetadata.new(... shop: request.shop ...)` using the attacker-supplied victim shop domain, even though the payload actually originated from the attacker's own shop.

This crosses a tenant boundary: shop-scoped data (order/customer/product payloads, mandatory GDPR topics like `customers/redact`, `shop/redact`, etc.) can be injected and misattributed to any shop domain of the attacker's choosing, without ever needing that victim's credentials.

### Impact Explanation
This meets the Critical bar of "cross-tenant access": an attacker with no special privileges beyond installing the app on any single store can make the app record, process, or act on webhook data as if it belonged to a shop they do not own or control. Depending on what handlers do with `WebhookMetadata#shop` (e.g., updating billing state, cache invalidation, deleting merchant data on redaction topics, triggering downstream sync), this can produce data corruption, unauthorized state changes, or spurious GDPR erasure actions against a shop the attacker never authenticated to.

### Likelihood Explanation
Likelihood is high for any app author who trusts `WebhookMetadata#shop` (the officially exposed field) for tenant scoping — which is the documented/expected usage of this API. No `api_secret_key`, access token, or victim credentials are needed; only a legitimate but unprivileged install of the app on any shop and the ability to POST to the app's public webhook endpoint with attacker-controlled headers.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the HMAC-signed payload, or otherwise cryptographically bind the shop identity used by `Registry.process`/`WebhookMetadata` to the value validated by `HmacValidator`, rather than trusting the raw `X-Shopify-Shop-Domain` header independently of the signature.

### Proof of Concept
```ruby
# Attacker has a legitimate (but unprivileged) install on "attacker-shop.myshopify.com"
# and captures a real webhook delivery for it: body = raw_body, hmac = valid_hmac_header

spoofed_headers = {
  "x-shopify-topic" => real_topic,
  "x-shopify-hmac-sha256" => valid_hmac_header, # unchanged, still valid for raw_body
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # swapped
  "x-shopify-webhook-id" => real_webhook_id,
  "x-shopify-api-version" => real_api_version,
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: spoofed_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# HmacValidator.validate succeeds (HMAC only covers raw_body),
# handler.handle receives WebhookMetadata with shop: "victim-shop.myshopify.com"
