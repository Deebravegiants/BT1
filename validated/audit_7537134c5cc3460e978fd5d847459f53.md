### Title
Webhook HMAC covers only the raw body, not the `topic`/`shop-domain`/`webhook-id` headers that are trusted downstream - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Utils::HmacValidator.validate` only ever authenticates the exact string returned by `to_signable_string`. For webhooks, `Webhooks::Request#to_signable_string` returns just `@raw_body` [1](#0-0) , while `Registry.process` and the resulting `WebhookMetadata` act on `request.topic`, `request.shop`, `request.webhook_id`, and `request.api_version`, all of which come from HTTP headers that are never part of the signed string [2](#0-1) [3](#0-2) . A body that Shopify genuinely signed for the attacker's own shop/topic can therefore be re-delivered to the app's webhook endpoint with a forged `shop-domain`/`topic` header, and `HmacValidator.validate` will still return `true`.

### Finding Description
The binding the code implicitly relies on is:
`HmacValidator.validate(request) == true` implies `request.shop`, `request.topic`, `request.webhook_id`, `request.api_version` were all authenticated by Shopify.

That binding is false. `validate` only checks
`HMAC-SHA256(secret, request.to_signable_string) == request.hmac` [4](#0-3) ,
and `to_signable_string` for a webhook is defined as the raw request body alone [1](#0-0) . The `shop`, `topic`, `webhook_id`, and `api_version` accessors read directly from `@headers`, which are populated verbatim from the caller-supplied `headers:` hash in `initialize` [5](#0-4)  and are never mixed into the signable string.

`Registry.process` uses exactly these unauthenticated fields to route and act on the webhook:
```ruby
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
handler = @registry[request.topic]&.handler
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
  body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
``` [3](#0-2) 

Exploit flow: the attacker creates their own development shop, installs the app, and registers a webhook endpoint they control. Shopify delivers a genuinely signed webhook to that endpoint (valid `X-Shopify-Hmac-Sha256` over the raw body, plus `X-Shopify-Shop-Domain: attacker-shop.myshopify.com` and `X-Shopify-Topic: <topic>` headers). The attacker now has a byte-for-byte body and a matching HMAC that `HmacValidator.validate` will accept forever (the HMAC has no timestamp/nonce and is only over the body). The attacker replays that exact body + hmac to the target app's public webhook receiver endpoint, but substitutes `X-Shopify-Shop-Domain` with a victim merchant's domain and/or a different `X-Shopify-Topic`. `HmacValidator.validate` still returns `true` because it never inspected those headers, so the app's `Registry.process` dispatches the handler believing the payload authentically originated for the victim shop/topic — a cross-tenant/topic-confusion authentication bypass on the values the app actually acts on.

None of the existing guards catch this: `HmacValidator.validate` has no concept of headers [6](#0-5) ; `ShopValidator.sanitize!` is never invoked on `request.shop` in the webhook path (only used for OAuth-related host params, not `Webhooks::Request`); Sorbet typing only checks that `shop`/`topic` are `String`, not that they were part of the signed payload. By contrast, the OAuth path (`Auth::Oauth::AuthQuery#to_signable_string`) does include `code`, `host`, `shop`, `state`, and `timestamp` in the signed string [7](#0-6) , so the SIGNATURE COVERAGE invariant holds there — the gap is specific to the webhook `Request` class.

### Impact Explanation
An attacker who owns any development shop and registers any webhook endpoint can obtain an arbitrary number of genuinely Shopify-signed `(body, hmac)` pairs at will, then feed them to any target app's webhook receiver with forged `shop-domain`/`topic` headers. Because `Registry.process` trusts `request.shop` and `request.topic` to build `WebhookMetadata` passed to the app's handler, this is a cross-tenant authenticity bypass: the receiving app believes data legitimately belongs to a different shop/topic than the one Shopify actually signed it for. This is repeatable against arbitrary victim shops registered on the same app, for any topic the attacker can trigger on their own dev shop, and matches the Critical "authentication bypass" / cross-tenant class described in scope.

### Likelihood Explanation
Preconditions are minimal and entirely attacker-controlled: register a free/dev shop, install the target app, trigger any webhook topic on the dev shop to capture a valid `(raw_body, hmac)` pair, then send an HTTP POST to the target app's public webhook endpoint with forged shop/topic headers and the captured body/hmac. No secrets, tokens, or privileged access are required, and the attack is trivially repeatable and automatable against any app using this gem's default `Webhooks::Request`/`Registry.process` flow.

### Recommendation
Include the security-relevant headers (`shop-domain`, `topic`, and ideally `webhook-id`/`api-version`) in the value bound and checked before trusting them, e.g. either (a) have `to_signable_string` return a canonical concatenation of headers + body so a header swap invalidates the HMAC, or (b) explicitly document/enforce that `request.shop` and `request.topic` must be independently corroborated (e.g., against the shop for which the webhook subscription was registered) before being used to route/act, rather than trusting header values as if HMAC-verified.

### Proof of Concept
```ruby
# test/webhooks/request_header_spoof_test.rb
require "test_helper"

class RequestHeaderSpoofTest < Test::Unit::TestCase
  def setup
    ShopifyAPI::Context.setup(api_key: "key", api_secret_key: "secret", ...)
    @body = '{"id":1,"note":"hi"}'
    @hmac = Base64.strict_encode64(
      OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), "secret", @body)
    )
  end

  def test_hmac_validate_ignores_shop_and_topic_headers
    original = ShopifyAPI::Webhooks::Request.new(
      raw_body: @body,
      headers: {
        "X-Shopify-Hmac-Sha256" => @hmac,
        "X-Shopify-Topic" => "orders/create",
        "X-Shopify-Shop-Domain" => "attacker-shop.myshopify.com",
      },
    )
    assert ShopifyAPI::Utils::HmacValidator.validate(original)

    # Same body + same hmac, forged shop/topic headers
    forged = ShopifyAPI::Webhooks::Request.new(
      raw_body: @body,
      headers: {
        "X-Shopify-Hmac-Sha256" => @hmac,
        "X-Shopify-Topic" => "shop/redact", # different topic
        "X-Shopify-Shop-Domain" => "victim-shop.myshopify.com", # different shop
      },
    )
    # Demonstrates the broken binding: validate() still returns true
    # even though shop/topic differ from what was originally signed.
    assert ShopifyAPI::Utils::HmacValidator.validate(forged)
    assert_equal "victim-shop.myshopify.com", forged.shop
    assert_equal "shop/redact", forged.topic
  end
end
```
This shows both sides of the equality diverging: `HmacValidator.validate` returns `true` for both `original` and `forged` (the signature side matches), while `forged.shop`/`forged.topic` (the values `Registry.process` acts on) differ from the shop/topic actually covered by the signature — falsifying the SIGNATURE COVERAGE invariant.
