### Title
Fee-on-transfer tokens break escrow accounting in Tron `IntentGatewayV2.placeOrder` - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron fork of `IntentGatewayV2.placeOrder` credits the `_orders` escrow mapping with the user-requested input amount (minus protocol fee) instead of the amount actually received by the contract, unlike the canonical EVM implementation which was hardened against this exact issue.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol`, `placeOrder` computes `reducedInputs[i].amount` from `order.inputs[i].amount` — the amount the user *specified*, not what the contract actually received: [1](#0-0) 

For the non-predispatch path, the ERC-20 is pulled with `safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` with no balance check, and the escrow is then incremented by `reducedInputs[i].amount` (derived from the pre-transfer requested amount, not the post-transfer actual balance delta): [2](#0-1) 

The predispatch path has the same flaw — dust is only computed relative to `requiredAmount` (`order.inputs[i].amount`), and `_orders[commitment][token]` is still incremented by `reducedInputs[i].amount`, which was derived from the pre-transfer-fee requested amount: [3](#0-2) 

This contrasts with the canonical (non-Tron) `evm/src/apps/IntentGatewayV2.sol`, which was explicitly hardened: it snapshots balances before/after each `safeTransferFrom` and mutates `order.inputs[i].amount` to the actual delta received before computing the commitment and protocol-fee-adjusted escrow amount: [4](#0-3) 

The Tron variant never received this fix, so for any fee-on-transfer ERC-20 configured as an input token, the gateway will credit the escrow ledger (`_orders[commitment][token]`) with more tokens than it actually holds.

### Impact Explanation
Because `_orders` is a shared per-token ledger across all orders (`_orders[commitment][token]`), inflating one order's recorded escrow beyond the contract's real token balance creates an accounting shortfall in the pool. When solvers later call `fillOrder`/settlement withdrawal logic (`withdraw`) or users cancel and reclaim escrow, the contract may not hold enough of the token to honor all outstanding escrow claims, causing legitimate withdrawals for *other* users/orders to revert due to insufficient balance — a permanent freezing of funds. This is a fund-safety issue reachable by any unprivileged user simply placing an order with a fee-on-transfer token, matching the "permanent freezing of funds" acceptance criterion.

### Likelihood Explanation
Likelihood is a function of whether the deployed instance's `_params`/token list includes fee-on-transfer tokens on Tron (e.g., certain TRC20 tokens implement transfer taxes). Any single `placeOrder` call using such a token is sufficient to trigger the shortfall — no special privileges, front-running, or governance action required.

### Recommendation
Mirror the fix already applied in `evm/src/apps/IntentGatewayV2.sol`: snapshot the contract's token balance immediately before and after each `safeTransferFrom` (both in the direct path and the predispatch sweep path), use the actual balance delta as the received amount, and derive `reducedInputs`/`_orders` credits and the commitment hash from that measured amount rather than the caller-supplied `order.inputs[i].amount`.

### Proof of Concept
1. Deploy `IntentGatewayV2` (Tron variant) with a fee-on-transfer TRC20 token registered as a valid input asset, no protocol fee for simplicity.
2. User calls `placeOrder` with `order.inputs[0] = {token: FOT, amount: 1000e18}`; the FOT charges a 1% transfer fee, so the gateway actually receives `990e18`.
3. `safeTransferFrom(msg.sender, address(this), 1000e18)` is invoked; the contract's real FOT balance increases by only `990e18`.
4. `_orders[commitment][FOT] += reducedInputs[0].amount` credits `1000e18` (no protocol fee) — 10e18 more than the contract actually holds.
5. Repeat with other users/orders using the same token; eventually withdrawals/cancellations for some orders will revert with insufficient balance because cumulative `_orders` credits exceed the FOT balance actually escrowed in the contract, permanently freezing legitimate users' funds. (Equivalent behavior is already covered by the `FeeOnTransferToken` regression tests written against the fixed EVM contract — e.g. `testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived` — which would fail if run against this Tron contract's logic.) [5](#0-4)

    /// @notice Escrow correctly reflects actual received amount for fee-on-transfer tokens.
    function testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived() public {
        // Deploy a 1% fee-on-transfer token
        FeeOnTransferToken fot = new FeeOnTransferToken(100); // 1% = 100 bps
        fot.mint(user, 10000 * 1e18);

        uint256 inputAmount = 1000 * 1e18;
        uint256 expectedReceived = inputAmount - (inputAmount * 100) / 10000; // 990

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(fot)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 900 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        vm.startPrank(user);
        fot.approve(address(intentGateway), inputAmount);
        intentGateway.placeOrder(order, bytes32(0));
        vm.stopPrank();

        // Gateway should hold only what it actually received
        assertEq(
            fot.balanceOf(address(intentGateway)), expectedReceived, "Gateway balance should match received amount"
        );

        // Reconstruct the order as placeOrder would have mutated it
        order.user = bytes32(uint256(uint160(user)));
        order.source = host.host();
        order.nonce = 0;
        order.inputs[0].amount = expectedReceived;
        bytes32 commitment = keccak256(abi.encode(order));

        // Escrow should match actual received, not the user-specified amount
        assertEq(
            intentGateway._orders(commitment, address(fot)),
            expectedReceived,
            "Escrow should equal actual received amount"
        );
    }
