### Title
Webhook Shop/Topic Headers Are Not Covered by HMAC, Enabling Cross-Tenant Webhook Spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw request body only, while the `shop`, `topic`, and `webhook_id` values used to identify the tenant and dispatch the handler come from unauthenticated HTTP headers. `Registry.process` validates the HMAC and then trusts these header-derived values as the tenant identity, breaking the binding between "bytes that were HMAC-verified" and "bytes used to identify the shop."

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

The `shop`, `topic`, and `webhook_id` accessors are read straight from headers and are never part of the signed payload: [2](#0-1) 

`Utils::HmacValidator.validate` only verifies the `hmac` field against `verifiable_query.to_signable_string`, i.e. the body: [3](#0-2) 

`Registry.process` performs this HMAC check and then, on success, immediately trusts `request.shop` and `request.topic` (unauthenticated headers) to build the metadata passed to the app's webhook handler: [4](#0-3) 

Because the shop-domain and topic headers are not part of the HMAC-signable string, an attacker who legitimately receives one valid webhook body+HMAC pair (trivially obtainable by installing the app on their own free/dev Shopify store and triggering an event) can replay that exact body/HMAC pair to the app's public webhook endpoint while substituting arbitrary values for `X-Shopify-Shop-Domain` and `X-Shopify-Topic`. The HMAC check still passes because it only re-derives the signature from the untouched body, so `Registry.process` dispatches the handler believing the event originated from a different (victim) shop.

### Impact Explanation
This breaks the identity binding "shop authenticated by HMAC" vs. "shop used as the tenant key for handler dispatch," letting an attacker who never had access to the victim's data or the app's `client_secret` inject arbitrary attacker-controlled body content into the victim tenant's webhook-handling logic. Any host application that uses `WebhookMetadata#shop`/`#topic` to write to per-shop storage, trigger per-shop side effects, or select handler behavior will process the request as if authored by the victim shop, resulting in cross-tenant data injection/corruption — classified Critical under the target impact categories (cross-tenant access).

### Likelihood Explanation
The attacker only needs to be a legitimate, unprivileged user of the app on a shop they control (any developer/free store) to obtain one valid `(body, HMAC)` pair, then send a crafted HTTP POST to the app's publicly reachable webhook endpoint with swapped shop/topic headers. No secret, token, or privileged access is required — only network reachability to the endpoint, which is inherent to the webhook design.

### Recommendation
Include the tenant-identifying headers (`shop`, `topic`, and ideally `webhook_id`) in the value that is HMAC-verified, or independently authenticate/bind the shop header (e.g., cross-check against a previously established, authenticated mapping of registered webhook endpoints to shop, or require the shop domain be embedded in and covered by the signed payload) rather than trusting header values that sit outside the HMAC-signable string.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and triggers a webhook (e.g., `orders/create`), capturing the resulting HTTP request: body `B`, and header `X-Shopify-Hmac-Sha256: H` (valid, since `H = HMAC(secret, B)` per `lib/shopify_api/utils/hmac_validator.rb`).
2. Attacker sends a new POST to the same app's webhook endpoint with the identical body `B` and header `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the tampered headers; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only recomputes HMAC over `@raw_body` (`lib/shopify_api/webhooks/request.rb:36-38`), unaffected by the header change.
4. `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` using the attacker-supplied `victim-shop.myshopify.com` value (`lib/shopify_api/webhooks/registry.rb:198-199`) and invokes the app's handler, which now processes attacker-controlled body content attributed to the victim shop.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
