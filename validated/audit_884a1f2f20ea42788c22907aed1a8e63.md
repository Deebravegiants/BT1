### Title
Reentrant `IApp.onAccept`/`onGetResponse` callback can grief and permanently block delivery of unrelated batched messages in `HandlerV2` - (File: evm/src/core/HandlerV2.sol)

### Summary
`HandlerV2.handlePostRequests` and `HandlerV2.handleGetResponses` verify a Merkle multiproof for an entire batch, then loop a second time calling `host.dispatchIncoming(...)` for each leaf, which does the duplicate-receipt check and low-level `call` into the destination `IApp` **before** the outer loop has advanced to the next leaf. There is no reentrancy guard on `EvmHost.dispatchIncoming`/`HandlerV2.handlePostRequests`/`handleGetResponses`.

### Finding Description
In `handlePostRequests`, each iteration does:
```solidity
if (host.requestReceipts(leaf.request.hash()) != address(0)) revert DuplicateMessage();
host.dispatchIncoming(leaf.request, _msgSender());
``` [1](#0-0) 

`dispatchIncoming` stores the request receipt and then performs an untrusted low-level `call` to the destination app's `onAccept`:
```solidity
_requestReceipts[commitment] = relayer;
(bool success,) = address(destination).call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));
``` [2](#0-1) 

The same pattern exists for `handleGetResponses`/`dispatchIncoming(GetResponse)`, which additionally reads `_requestCommitments[commitment].fee` and pays out the relayer fee only after the callback returns. [3](#0-2) [4](#0-3) 

Because the batch's proof-verification pass and the duplicate-check pass are split into two separate loops over the same array, and each element's dispatch (including the external call into arbitrary app code) happens sequentially inside the second loop, a malicious destination app that is one of the batched messages can, from inside its own `onAccept`/`onGetResponse` callback, re-enter `handlePostRequests`/`handleGetResponses` with a single-element message containing the *next unprocessed leaf* of the very same outer batch (a legitimate, already-committed request/response with a valid, independently obtainable state proof). The reentrant call's own duplicate check passes (no receipt yet exists) and it successfully dispatches that request early, writing its receipt. Control then returns to the outer loop, which reaches that same leaf's duplicate check — which now reverts with `DuplicateMessage()` — causing the entire outer `handlePostRequests`/`handleGetResponses` transaction (and hence the whole relayer-submitted batch) to revert.

This is analogous in structure to CVE-2019-9820's class of bug: an object (here, a request/response's not-yet-processed state) is consumed/"freed" (receipt written) via a reentrant path while the outer loop still assumes it is unprocessed and "in use," and the outer code's subsequent access to that now-mutated state (the duplicate check) fails in a way that is fully attacker-controlled and unavoidable by an honest relayer batching unrelated messages together.

### Impact Explanation
An unprivileged actor that controls (or deploys) a destination application reachable via `IApp.onAccept`/`onGetResponse` can force any relayer-submitted batch that includes both their message and other victims' messages to permanently revert whenever both are batched together, and can repeat this for every batch attempt that includes the victim message, effectively producing a persistent denial-of-service on delivery of otherwise-valid, already-finalized cross-chain messages to honest destinations sharing a batch with the attacker's message — matching the "route unable to deliver messages" impact criterion. It also risks stalling relayer fee/reward accounting for the griefed messages since delivery (and associated fee payout in `dispatchIncoming(GetResponse)`) never completes.

### Likelihood Explanation
Any address can permissionlessly register itself as the destination `to`/`from` of a POST request or GET request by simply dispatching from a contract they control (`EvmHost.dispatch`), and any address can permissionlessly call `handlePostRequests`/`handleGetResponses` since these handler functions are unrestricted/permissionless by design. Triggering the reentrant call inside `onAccept`/`onGetResponse` requires only writing a malicious contract with the callback logic — no special privileges, timing, or governance access needed. The only precondition is that a relayer chooses to batch the victim's message together with the attacker's message in the same `handlePostRequests`/`handleGetResponses` array, which relayers routinely do to save gas.

### Recommendation
- Add a reentrancy guard (e.g., OpenZeppelin `ReentrancyGuard` / transient-storage lock) around `EvmHost.dispatchIncoming(...)` and `dispatchTimeOut(...)` so that a destination app's callback cannot re-enter the handler/host dispatch path mid-batch.
- Alternatively/in addition, make per-leaf duplicate-check-and-dispatch atomic against reentrancy by re-validating and isolating failures per leaf (e.g., wrap each `dispatchIncoming` call so a `DuplicateMessage` condition for an individual leaf is skipped/emits an event rather than reverting the entire batch), so a single griefed leaf cannot abort delivery of unrelated leaves in the same transaction.

### Proof of Concept
1. Attacker deploys `EvilApp` implementing `IApp.onAccept` that, on first invocation, immediately calls back into `HandlerV2.handlePostRequests` with a `PostRequestMessage` containing only `leaf[i+1]` (the next request in the outer batch, targeting an honest `VictimApp`), using a validly re-derived MMR proof for that single leaf (since the underlying state commitment is already stored on-chain and the leaf's proof is public).
2. Attacker dispatches a POST request from `EvilApp` (as `to`) and gets it included, together with an honest user's POST request to `VictimApp`, in the same relayer-submitted `PostRequestMessage.requests` array such that `EvilApp`'s leaf is processed before `VictimApp`'s leaf in `handlePostRequests`'s second loop: [1](#0-0) 
3. When `host.dispatchIncoming` calls `EvilApp.onAccept`, `EvilApp` reenters `handlePostRequests` with `VictimApp`'s leaf alone; that nested call passes the duplicate check (`requestReceipts` empty) and successfully dispatches to `VictimApp`, storing its receipt via `EvmHost.dispatchIncoming`: [5](#0-4) 
4. Execution returns to the outer `handlePostRequests` loop, which then reaches `VictimApp`'s leaf and reverts with `DuplicateMessage()`, aborting the entire outer transaction and rolling back both the `EvilApp` delivery (its earlier storage writes revert too, but so does the honest `VictimApp` delivery attempt in this transaction) and confirming the relayer's whole batch fails whenever these two messages are co-batched.
5. Repeating this for every batch containing the victim's message denies delivery indefinitely unless the relayer submits the victim's message alone, which is not guaranteed and defeats the purpose of `IHandlerV2.batchCall`/multi-leaf batching documented in [6](#0-5) .

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }

    function dispatchIncoming(GetResponse memory response, address relayer) external restrict(_hostParams.handler) {
        // replay protection
        bytes32 commitment = response.request.hash();
        _responseReceipts[commitment] = ResponseReceipt({
            relayer: relayer,
            responseCommitment: response.hash()
        });

        (bool success,) = _bytesToAddress(response.request.from)
            .call(abi.encodeWithSelector(IApp.onGetResponse.selector, IncomingGetResponse(response, relayer)));

        if (!success) {
            // so that it can be retried
            delete _responseReceipts[commitment];
            return;
        }

        // reward the relayer fee
        uint256 fee = _requestCommitments[commitment].fee;
        if (fee != 0) {
            IERC20(feeToken()).safeTransfer(relayer, fee);
        }
        emit GetRequestHandled({commitment: commitment, relayer: relayer});
    }
