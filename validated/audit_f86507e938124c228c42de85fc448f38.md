### Title
Signup is reported as successful to the backend while personal-custody biometric data (tier1/tier2 PCP) can be silently discarded by the data-uploader queue - ([File: src/agents/data_uploader.rs])

### Summary
`MasterPlan::do_signup` determines and reports signup/enrollment success (`enroll_user::Status::Success`, `signup_successful()`) based solely on the `signup_post`/`signup_poll` round trip completing and (for tier0) a blocking, retried upload. The tier1/tier2 personal-custody-package (PCP) uploads containing the user's encrypted iris/face biometric key material are pushed fire-and-forget into an in-memory bounded queue in the `data_uploader` agent and never awaited or checked before success is reported. That queue evicts the oldest pending item once a configured `dropping_threshold` is reached. This mirrors the ReaperVaultV2 bug class: the "full amount" (a fully successful signup with all committed side effects) is recorded/reported, while the actual delivered artifact (tier1/tier2 custody data) can be silently short of what was promised.

### Finding Description
In `src/plans/mod.rs`, `do_signup`: [1](#0-0) 
tier0 is uploaded synchronously with retries and checked (`upload_pcp_tier_0`, aborting the signup on failure), but tier1 and tier2 are simply sent as `Input::Pcp` messages into the `data_uploader` agent's port and never awaited: [2](#0-1) 

Success/failure of the overall signup is computed right after this, independent of whether tier1/tier2 ever reach the backend: [3](#0-2) 

Inside the `data_uploader` agent, each tier has its own `Queue` with a `blocking_threshold` and a `dropping_threshold`. When a new `Pcp` for a tier arrives and the queue is already at the tier's `dropping_threshold`, the **oldest** queued item for that tier is evicted before the new one is pushed: [4](#0-3) [5](#0-4) 

For the in-memory queue variant (the one actually constructed in `run`, since `Queue::new_memory()` is used and the persistent variant is dead code per `#[allow(dead_code)]`), `drop_oldest` simply calls `queue.pop_back()` with no persistence, no retry, and no signal back to the plan or backend that the tier1/tier2 package for a given `signup_id` was dropped: [6](#0-5) [7](#0-6) 

Additionally, `upload_pcp` itself gives up permanently (without ever notifying the caller) whenever the backend returns a 4xx client error: [8](#0-7) 

There is no correlation of `commit()`/drop events back to `signup_post`/`signup_poll` state, and `wait_queues` only blocks a *subsequent* signup from proceeding when the queue is at the `blocking_threshold` - it never re-validates or aborts a signup whose own tier1/tier2 package was dropped: [9](#0-8) [10](#0-9) 

The root cause parallels the ReaperVaultV2 finding: the code path that determines "the full obligation was met" (`result.success = true` / `enroll_user::Status::Success` / `signup_successful()`) is decoupled from the code path that determines "how much of the obligation was actually delivered" (whether tier1/tier2 upload completed, retried past network errors, or was evicted from the bounded queue). Just as `_withdraw()` rebased `value` to `vaultBalance` without correcting the loss/shares math, here the plan commits to "signup success" without correcting for tier1/tier2 delivery outcome.

### Impact Explanation
Tier1/tier2 PCP contents include the user's normalized iris/face images and key material used for the self-custody/recovery bundle (`personal_custody_package::Credentials`, `backend_iris_encrypted_private_key`, etc., built in `Plan::run` at `src/plans/mod.rs:1671-1751` and `src/plans/enroll_user.rs`). If these are evicted from the bounded queue (e.g., during a burst of consecutive signups on a busy orb, hitting `pcp_tier1_dropping_threshold`/`pcp_tier2_dropping_threshold`) or abandoned after a transient 4xx from the backend, the affected user's enrollment is still reported to the backend/UI as `Success` — the World ID credential/nullifier flow completes — while the corresponding biometric self-custody data for that signup is permanently lost with no user-facing indication and no retry. This is a concrete data-retention/loss defect in the biometric upload and retention pipeline: users are told (and the backend records) that their enrollment succeeded, but the biometric custody artifact backing that enrollment may never exist server-side.

### Likelihood Explanation
This is reachable through entirely normal, unprivileged signup flow (multiple ordinary users signing up in sequence on the same orb, or transient backend/network errors returning 4xx during tier1/2 upload) — no privileged access, malicious peer, or hardware tampering is required. The eviction and no-retry-on-4xx paths are deterministic given the documented thresholds and error-handling branches, though I was unable to inspect the exact configured values of `pcp_tier1_dropping_threshold`/`pcp_tier2_dropping_threshold`/`pcp_tier1_blocking_threshold`/`pcp_tier2_blocking_threshold` in `src/config.rs` and `src/backend/config.rs` (the grep matched but I could not view line-level defaults before the session ended), so I cannot state how many concurrent in-flight signups are required in practice to trigger eviction.

### Recommendation
Make signup/enrollment success reporting depend on confirmed delivery of all PCP tiers, not just tier0:
- Have `data_uploader` acknowledge per-`signup_id` completion (or failure) of tier1/tier2 uploads back to the plan (e.g., via a oneshot/callback keyed by `signup_id`), and gate `debug_report.signup_successful()` / the reported enrollment status on that acknowledgment, mirroring how `upload_pcp_tier_0` is awaited and checked today.
- Remove or bound the silent `drop_oldest` eviction; when a tier queue is full, prefer backpressure (block the new signup, as `wait_queues` partially does) over silently discarding another signup's biometric custody data, and if eviction is unavoidable, persist a record so the affected signup can be reported as degraded/retried rather than `Success`.
- On 4xx errors in `upload_pcp`, propagate the failure to the caller/signup result instead of breaking the retry loop silently.

### Proof of Concept
1. Configure (or rely on default) small `pcp_tier1_dropping_threshold`/`pcp_tier2_dropping_threshold` values relative to sustained signup throughput.
2. Run several signups back-to-back on the same orb such that tier1/tier2 `Pcp` pushes for an earlier signup accumulate in the `data_uploader` queue while later signups keep pushing new tier1/tier2 packages, per `src/agents/data_uploader.rs:143-145` this causes `drop_oldest()` to evict the earlier signup's still-unuploaded tier1/tier2 package.
3. Because `do_signup` in `src/plans/mod.rs:599-662` never waits on or checks the result of the tier1/tier2 `send()` calls, the earlier signup's `enroll_user::Status::Success` / `signup_successful()` is unaffected by the eviction — the backend and UI both report the signup as fully successful.
4. Separately, force the backend to return a 4xx for a tier1/2 upload attempt; `upload_pcp` (src/agents/data_uploader.rs:195-214) breaks out of retry permanently with no notification, producing the same outcome: reported success, missing custody data.

    async fn drop_oldest(&mut self) {
        match self {
            Self::Memory { queue } => {
                queue.pop_back();
            }
            Self::Persistent { path, queue, .. } => {
                let Some(id) = queue.pop_back() else { return };
                match ssd::perform_async(fs::remove_dir_all(path.join(id.to_string()))).await {
                    None => {
                        tracing::error!(
                            "Persistent queue is failed during drop_oldest, switching to memory"
                        );
                        *self = Self::new_memory();
                    }
                    Some(()) => {}
                }
            }
        }
    }
