## Finding

**OmniBridge.describeWithdrawal() trusts positional array index into an externally-ordered list, allowing a status/txHash misreport across different withdrawals in the same batch transaction.**

### Title
Omni Bridge withdrawal status/txHash misattributed by unordered array index in batch withdrawals - (File: `packages/intents-sdk/src/bridges/omni-bridge/omni-bridge.ts`)

### Summary
`OmniBridge.describeWithdrawal` resolves the completion status for a specific withdrawal by indexing directly into the array returned by `omniBridgeAPI.getTransfer({ transactionHash })` using `args.index`: [1](#0-0) 

This mirrors the reported bug class exactly: an identifier (`index`) that is supposed to uniquely and stably map to "this withdrawal" is instead a raw positional lookup into a mutable/externally-ordered collection, so a later caller (or a differently-ordered API response) can silently return another withdrawal's record under the queried index — analogous to how `OrderBook._insert` reused `index.length + 1` and silently overwrote another user's order.

### Finding Description
The codebase has already identified and fixed exactly this issue for the PoA bridge: [2](#0-1) 
The comment explicitly states: *"Response list is unsorted, so we match by assetId instead of index"*, and the changelog confirms this was a deliberate bug fix: *"Fix POA bridge withdrawal matching to use assetId instead of index"* (commit `8bbd5c6`), referenced in: [3](#0-2) 

However, `OmniBridge.describeWithdrawal` was never updated to follow the same pattern — it still performs a raw positional lookup `getTransfer(...)[args.index]` with no cross-check against `args.withdrawalParams` (no comparison of `recipient`/`destinationAddress`/`amount`): [4](#0-3) 

This `index` originates from `createWithdrawalIdentifiers`, which assigns sequential indexes per-route for withdrawals inside the same NEAR intent transaction (batch withdrawals, e.g., "USDC to Solana + BTC refund to Bitcoin" as described in the RFC doc): [5](#0-4) [6](#0-5) 

If the Omni Bridge indexer's `getTransfer` response ordering does not deterministically match the submission order of withdrawals within that NEAR tx (the same non-guarantee that necessitated the PoA fix), `describeWithdrawal` for withdrawal `index=0` can return the `txHash`/status belonging to withdrawal `index=1` (or vice versa), breaking the equality: *the status/txHash reported for withdrawal N is the on-chain outcome of withdrawal N*.

### Impact Explanation
An integrator relying on `sdk.createWithdrawalCompletionPromises` / `waitForWithdrawalCompletion` to determine when to credit a user or mark a withdrawal complete could receive a `completed` status with the wrong `txHash` for a given index in a batch withdrawal. This can cause the integrator to mark the wrong withdrawal as settled (crediting/refunding based on another withdrawal's completion), or attribute a destination chain's transaction hash to the wrong asset/recipient pairing — a status misreport that can lead to double-crediting or incorrect settlement records, matching the High-severity criteria ("a status or hash misreport making an integrator credit or refund twice").

### Likelihood Explanation
This requires a batch withdrawal (multiple withdrawals routed through Omni Bridge in a single NEAR transaction) combined with the Omni Bridge indexer returning transfers in an order that doesn't match submission order — the same condition PoA bridge maintainers already observed and fixed for their own API. Since Omni Bridge's `getTransfer` has no documented ordering guarantee here and no order-matching safeguard was added, this is plausible whenever multiple withdrawals share a NEAR tx hash.

### Recommendation
Match transfers returned by `getTransfer` using stable withdrawal-identifying fields (e.g., recipient address and amount/asset from `args.withdrawalParams`) rather than raw array position, consistent with the fix already applied in `poa-bridge.ts`'s `findMatchingWithdrawal`.

### Proof of Concept
1. Submit a batch withdrawal with two Omni Bridge withdrawals in one NEAR tx: withdrawal A (asset X → chain 1) at `index=0`, withdrawal B (asset Y → chain 2) at `index=1`.
2. Call `sdk.createWithdrawalCompletionPromises` — internally this calls `OmniBridge.describeWithdrawal` with `{ index: 0, tx }` and `{ index: 1, tx }` respectively.
3. If the Omni Bridge indexer returns `getTransfer({transactionHash: tx.hash})` with B's transfer object at position 0 and A's at position 1 (unsorted/reordered), `describeWithdrawal({index:0,...})` returns B's `txHash`/recipient chain data while the caller believes it is withdrawal A's result.
4. The integrator credits/settles withdrawal A using B's transaction hash and destination chain, misattributing the completion.

```typescript
	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const transfer = (
			await this.omniBridgeAPI.getTransfer({
				transactionHash: args.tx.hash,
			})
		)[args.index];

		if (transfer == null || transfer.recipient == null) {
			return { status: "pending" };
		}

		const destinationChain = getChain(transfer.recipient as OmniAddress);
		let txHash = null;
		if (
			isEvmChain(destinationChain) ||
			destinationChain === ChainKind.Sol ||
			destinationChain === ChainKind.Fogo ||
			destinationChain === ChainKind.Strk ||
			destinationChain === ChainKind.Aptos
		) {
			txHash = transfer.finalised?.transaction_hash;
		} else if (isUtxoChain(destinationChain)) {
			// pending_sign_id is not the finalised tx hash. In rare cases, the hash may
			// change if the BTC transfer fails to be submitted. We return fast hash for FE and
			// wait for final one (transfer.finalised?.transaction_hash) for BE.
			txHash =
				typeof window !== "undefined"
					? transfer.utxo_meta?.pending_sign_id
					: transfer.finalised?.transaction_hash;
		} else {
			return { status: "completed", txHash: null };
		}

		if (!txHash) {
			return { status: "pending" };
		}

		return { status: "completed", txHash };
	}
```

```markdown
Add `watchWithdrawals` and `describeWithdrawals` methods to enable granular tracking of batch withdrawal completion, allowing services to process each withdrawal independently as it completes.

## Problem Statement

The SDK supports batch withdrawals - multiple tokens withdrawn in a single intent. For example: USDC to Solana + BTC refund to Bitcoin.

Current `waitForWithdrawalCompletion` has limitations:

1. **Waits for slowest** - Fast withdrawal (Solana ~2s) blocked by slow withdrawal (Bitcoin ~1hr)
2. **All-or-nothing failure** - If one withdrawal fails, entire function throws
3. **No progress visibility** - Can't know which withdrawals completed until all finish
```
