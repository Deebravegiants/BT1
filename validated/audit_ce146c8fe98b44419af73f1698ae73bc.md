### Title
Webhook `shop` binding not covered by HMAC allows cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, so the HMAC signature validated by `HmacValidator` never covers the `X-Shopify-Shop-Domain` header. `Registry.process` nonetheless trusts that unauthenticated header value as the tenant identity passed to the app's webhook handler, breaking the binding between "shop whose secret produced a valid signature" and "shop the app believes the webhook is about."

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` recomputes an HMAC over `verifiable_query.to_signable_string` and compares it to the caller-supplied HMAC using the app's `api_secret_key`: [1](#0-0) 

For webhooks, `to_signable_string` is defined as just the raw JSON body: [2](#0-1) 

The `shop` (`shopify-shop-domain` / `x-shopify-shop-domain` header) is read independently and is **not** part of the signed string: [3](#0-2) 

`Registry.process` validates the HMAC over the body only, then dispatches to the app's handler using `request.shop` taken straight from that unauthenticated header: [4](#0-3) 

Because the same `api_secret_key` is shared across every shop that has installed the app, any merchant/attacker who installs the app on their own store (including a free development store) can obtain a genuinely valid `(body, hmac)` pair produced by Shopify for their own shop's event, then resend that exact pair to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. `HmacValidator.validate` still succeeds because the signature only ever certifies the body, not which shop it is claimed to belong to. The handler then receives `WebhookMetadata` with `shop` equal to the attacker-chosen victim domain, while the body content is actually the attacker's own data.

This is precisely the "field acted on but not covered by the HMAC" pattern: the app authenticates the payload bytes but binds an unauthenticated header value (shop identity) to that payload when invoking tenant-specific logic.

### Impact Explanation
Any handler logic that uses `data.shop` from `WebhookMetadata` to select, look up, or mutate per-tenant state (session lookup, billing, uninstall/redact handling, order/customer records, feature flags, etc.) can be made to act on the wrong tenant using attacker-supplied body content, since the shop identity is not cryptographically bound to the payload. This constitutes cross-tenant access/confusion — an unprivileged user with only their own shop install can inject events that the app associates with a victim shop of their choosing. This maps to the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is meaningful: no special access to the app's `client_secret`/access tokens is needed, no TLS interception is needed, and no privileged account is needed — any user able to install the app on any shop (including a free dev store) can generate valid `(body, hmac)` pairs at will and simply change the shop header on replay. The only requirement is that the app's webhook endpoint accepts unauthenticated inbound HTTP requests, which is standard for Shopify webhook consumers using this gem's `Webhooks::Registry`/`Webhooks::Request` API as documented.

### Recommendation
Bind the shop identity into the signed material used for webhook verification, or otherwise assert the shop out-of-band (e.g., compare `request.shop` against the shop actually registered as the owner of `request.webhook_id`, or require the host application to independently verify shop ownership before trusting `data.shop`). At minimum, document clearly that `WebhookMetadata#shop` is not cryptographically authenticated by `HmacValidator` and must not be trusted as a tenant key without additional verification.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a free/dev store is sufficient).
2. Attacker triggers any webhook topic the app subscribes to (e.g. `orders/create`) on their own shop, and captures the raw POST body and the `X-Shopify-Hmac-Sha256` header value sent to the app's webhook endpoint — this is a validly-signed `(body, hmac)` pair under the app's real `api_secret_key`.
3. Attacker resends this exact body and HMAC header to the app's public webhook endpoint, replacing `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks the HMAC against `request.to_signable_string` (the raw body) — validation succeeds: [5](#0-4) 
5. The registered handler is invoked with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, even though the payload actually originated from the attacker's own shop, letting the attacker inject arbitrary attacker-controlled webhook content attributed to the victim tenant.
