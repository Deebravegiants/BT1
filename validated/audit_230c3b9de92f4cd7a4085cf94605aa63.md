### Title
Webhook shop/topic identity headers are not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the trusted `shop`, `topic`, `webhook_id`, and `api_version` identity fields directly from unauthenticated HTTP headers, while the HMAC signature that `Registry.process` relies on to authenticate the request only covers the raw request body.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [1](#0-0)  and `HmacValidator.validate` computes/compares the HMAC exclusively over that signable string [2](#0-1) . However, `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all read straight from HTTP headers (`shopify-shop-domain`, `shopify-topic`, etc.) with no cryptographic binding to the signed body [3](#0-2) .

`Registry.process` validates only the HMAC and then forwards `request.shop` (an unauthenticated header value) straight into the `WebhookMetadata` passed to the app's handler: [4](#0-3) 

This is the same root-cause pattern as the referenced report: a field that is *acted on* (here, the `shop` identity used to attribute a webhook to a tenant) is not covered by the binding check (the HMAC), while a different, narrower piece of data (the raw body only) is what's actually verified.

### Impact Explanation
Any party capable of obtaining one genuine, validly-HMAC-signed webhook delivery for the app (e.g., by installing the app on their own store, which is an unprivileged, non-credentialed action) can replay that exact body to the app's webhook endpoint while rewriting the `x-shopify-shop-domain` (and/or `x-shopify-topic`/`x-shopify-webhook-id`) header to claim it belongs to a different, victim shop. Because those headers are excluded from the HMAC signable string, `HmacValidator.validate` still returns `true`, and the forged `shop` value is delivered to the host application's webhook handler as trustworthy. If the host application (following this gem's documented `WebhookMetadata#shop` contract) uses that value to look up/update per-tenant state (a normal, expected usage pattern for this gem), this enables cross-tenant data confusion/access attributable to the gem's identity-binding gap, matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Requires only the ability to receive one legitimately-signed webhook (trivially available to anyone who installs the app for their own shop, no privileged credentials needed) plus the ability to POST to the app's public webhook endpoint — both are unprivileged, internet-reachable actions. The header manipulation itself is a single HTTP header rewrite.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signable string used for HMAC verification (or otherwise cryptographically bind them to the request), so that any tampering with these identity headers invalidates the signature. At minimum, `Registry.process` should cross-check `request.shop` against a value derived from data that is actually covered by the HMAC (e.g., embedding the shop domain in the signed payload) before handing it to application code.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`; Shopify delivers a legitimate webhook with body `B` and header `x-shopify-hmac-sha256: HMAC(secret, B)`.
2. Attacker captures this request and replays it to the app's webhook endpoint, changing only `x-shopify-shop-domain` to `victim.myshopify.com` (and adjusting `topic`/`webhook_id` if desired) — the HMAC header is left untouched since it doesn't cover these fields.
3. `HmacValidator.validate` in [5](#0-4)  passes because it only checks `raw_body` against the signature.
4. `Registry.process` invokes the app's handler with `WebhookMetadata(shop: "victim.myshopify.com", ...)`, and any tenant-scoped action the handler performs (e.g., session/state lookups keyed on `shop`) is now executed under the wrong tenant identity.
