The gem's `WebhookHandler.handle` explicitly hands the merchant `shop` domain to the app for tenant-scoped logic (per `docs/usage/webhooks.md` line 25-26, the sample handler dispatches `shop_domain: data.shop`), while `Registry.process` only checks `Utils::HmacValidator.validate(request)`, whose signable string is the raw body alone.

### Title
Webhook `shop-domain` (and `topic`/`api-version`) headers are trusted for tenant identification without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, then forwards the shop-domain header verbatim to the app's handler as the trusted tenant identifier. Because the signature never covers the header, the two values are decoupled, breaking the binding `hmac_valid(body) == shop_is_authentic(shop_header)`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`, and `Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no relation to the signed bytes: [1](#0-0) [2](#0-1) 

`HmacValidator.validate` computes the signature exclusively over `verifiable_query.to_signable_string`, i.e. the body: [3](#0-2) 

`Registry.process` only checks this body-only HMAC, then builds `WebhookMetadata` directly from `request.shop` and dispatches it to the app's handler: [4](#0-3) 

The library's own documented usage pattern instructs apps to use `data.shop` as the tenant key for downstream processing (e.g. enqueuing per-shop jobs): [5](#0-4) 

So the equality the library implicitly promises to callers - `hmac_valid(raw_body) ⇒ shop_header_is_authentic` - does not hold. Anyone who obtains one legitimate `(raw_body, hmac)` pair from Shopify (e.g., a webhook delivered to their own store, which they fully control as an unprivileged merchant/attacker) can resend that exact same body+hmac to a victim app's webhook endpoint with an arbitrary `shopify-shop-domain` header value. `Registry.process` will accept it as valid (`Utils::HmacValidator.validate` only checks the body against the secret) and will call the app's handler with `WebhookMetadata(shop: <attacker-chosen shop>, body: <original body>, ...)`.

### Impact Explanation
This crosses a tenant boundary: the gem hands the app attacker-controlled shop attribution for a request that was never actually associated with that shop, while presenting it as authenticated ("HMAC validated"). Any app that follows the library's documented pattern of keying business logic, database writes, or job dispatch off `data.shop` (as literally shown in this gem's own docs) can be made to process/write data under, or attribute events to, a different merchant's tenant than the one that actually triggered the webhook - a cross-tenant access/confusion condition reachable by any unprivileged party with access to at least one legitimate webhook body/hmac pair (trivially obtainable by installing the app on their own free development store).

### Likelihood Explanation
Requires only that the attacker has received (or can obtain) one genuine webhook delivery for any topic/shop from Shopify to the same app's `client_secret` domain — no privileged credentials, no access token, and no interaction with `api_secret_key` are needed. Replaying the untouched body with a forged header is trivial for anyone who can send arbitrary HTTP requests to the app's public webhook endpoint.

### Recommendation
Do not trust the `shop-domain`, `topic`, `api-version`, or `webhook-id` headers as authenticated once HMAC validation only covers the body. Either:
1. Bind the shop domain (and other identifying headers) into the signable string used for HMAC computation, or
2. Require callers to cross-check `request.shop` against an independently-verified, already-authorized shop/session before acting on it, and document this requirement prominently since the current `docs/usage/webhooks.md` example does not do so.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and lets Shopify send a real webhook (e.g. `orders/create`) to the app's registered callback URL. Attacker captures the raw body `B` and the `x-shopify-hmac-sha256` header value `H` from that request (this is fully within the attacker's control, no secret needed).
2. Attacker sends a new HTTP POST to the same webhook endpoint with:
   - Body: exactly `B` (unmodified)
   - Header `x-shopify-hmac-sha256: H` (unmodified)
   - Header `x-shopify-shop-domain: victim-shop.myshopify.com` (forged)
   - Header `x-shopify-topic`: unchanged or attacker's choice
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate`, which recomputes HMAC over `B` only — it matches `H`, so validation passes: [6](#0-5) 
4. `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker's data>, ...)` is passed to the app's handler, which — per this gem's documented pattern — will act on data attributed to `victim-shop.myshopify.com` even though it originated from the attacker's own store.
