### Title
Webhook `shop` field is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only signs the raw request body, while the `shop` (and `topic`/`webhook_id`) values are read directly from unauthenticated HTTP headers. `Registry.process` validates the HMAC over the body alone, then trusts `request.shop` — taken from a header that was never part of the signed material — to attribute the webhook payload to a tenant. This breaks the intended binding: `HMAC(secret, signed_bytes) == received_hmac` should imply `signed_bytes` determines *every* field acted upon, but here `shop` is acted upon (passed to the handler as the tenant identifier) while being outside `signed_bytes`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read from the `shopify-shop-domain` / `x-shopify-shop-domain` header, which is not part of the signed string: [2](#0-1) 

`HmacValidator.validate` computes the HMAC only from `to_signable_string`, so it never checks the `shop` header: [3](#0-2) 

`Registry.process` validates the HMAC (body-only) and then unconditionally forwards `request.shop` to the handler as the tenant identity for the delivered body: [4](#0-3) 

Because `shop` is never covered by the signature, any HTTP client that possesses one valid `(raw_body, hmac)` pair signed with the app's secret — which it can legitimately obtain by triggering a webhook delivery to its **own** shop with the app installed — can resend that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `shop-domain` header. `HmacValidator.validate` still returns `true` (the signed bytes are unchanged), and `Registry.process` calls the handler with `shop` set to the attacker-chosen value while `body` is attacker-influenced content from their own store's webhook event. This is the equality that should hold but does not:
`signed_bytes(body) → HMAC valid` should imply `shop_used_by_handler == shop_that_originated_body`, but the gem allows `shop_used_by_handler` to be forged independently of `signed_bytes`.

### Impact Explanation
This is a cross-tenant identity-binding break: an unprivileged internet user who controls only their own installed shop can cause webhook payloads to be attributed to an arbitrary victim shop domain in the host application. Any downstream logic that uses `data.shop` to select which tenant's records to create/update (the gem's own documentation shows exactly this pattern — using `data.shop` to key job/storage operations) can be tricked into writing attacker-controlled webhook body data under another merchant's identity, i.e., cross-tenant data injection/corruption.

### Likelihood Explanation
Exploitation requires only: (1) the attacker operates any shop with the target app installed (a routine, low-privilege action for public apps), (2) they can intercept/replay their own inbound webhook HTTP request to the app's public webhook endpoint with a modified `shop-domain` header — trivial since HTTP headers are entirely attacker-controlled input to `Webhooks::Request.new(headers:)` and the gem does not perform any origin/IP verification of Shopify. No secrets, tokens, or privileged access are required.

### Recommendation
Include the `shop` (and ideally `topic`, `webhook_id`, `api_version`) values in the signed material verified against the HMAC, or otherwise cryptographically bind the shop identity to the signature — e.g., require the host application to independently verify the `shop-domain` header against a known/registered shop for that webhook subscription before trusting `request.shop`, and document this requirement prominently since the gem's own webhook doc/example encourages keying data purely off `data.shop`.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and subscribes to a webhook topic (e.g. `orders/create`).
2. Shopify legitimately delivers a webhook to the app's endpoint with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC over raw_body>`, and a body the attacker fully controls (e.g., by placing a crafted order in their own store).
3. Attacker intercepts this HTTP request (they are the recipient's network path is irrelevant — they can simply construct the identical body+HMAC pair themselves since they know the body and receive the genuine HMAC), then re-sends a new POST to the same webhook endpoint replacing only `x-shopify-shop-domain` with `victim-shop.myshopify.com`, keeping `raw_body` and `x-shopify-hmac-sha256` identical.
4. `HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` passes because it signs `raw_body` only.
5. `Registry.process` in `lib/shopify_api/webhooks/registry.rb:188-200` invokes the app's handler with `shop: "victim-shop.myshopify.com"` and `body` containing attacker-controlled data, causing the host app to process/store attacker data under the victim tenant.
