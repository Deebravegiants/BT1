### Title
Webhook shop-domain header is not covered by the HMAC, allowing cross-tenant webhook relabeling - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` value used downstream from the `x-shopify-shop-domain` HTTP header, but the HMAC that `ShopifyAPI::Webhooks::Registry.process` validates only signs the raw request body. Any attacker who can obtain one validly-signed webhook payload (e.g., by installing the app on their own shop and receiving real webhooks) can resend that exact body with the `x-shopify-shop-domain` header changed to a victim shop, and the gem will accept it as authentic and hand the attacker-chosen `shop` value to the handler.

### Finding Description
`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and compares it to the supplied `hmac`: [1](#0-0) 

For webhooks, `to_signable_string` returns only the raw body: [2](#0-1) 

But `shop` (the tenant identifier that gets forwarded to the app's handler) is read straight from the `x-shopify-shop-domain` header, which is not part of the signed bytes: [3](#0-2) 

`Registry#process` validates the HMAC and then trusts `request.shop` unconditionally to build the metadata passed to the app's handler: [4](#0-3) 

The binding that should hold is:
`shop verified by HMAC == shop used to route/attribute the webhook`

Here, the HMAC only covers `@raw_body`, so the equality is broken: `hmac(raw_body) valid` says nothing about which shop the header claims. An attacker who has captured one valid `(raw_body, hmac)` pair for their own shop can freely substitute any `x-shopify-shop-domain` value; `Utils::HmacValidator.validate` still returns `true` because it never inspects the header, and `Registry#process` will pass the forged `shop` straight to `handler.handle`.

### Impact Explanation
This breaks the tenant-identity boundary the gem is supposed to enforce for webhook processing: `Registry#process`'s only authenticity gate is the raw-body HMAC, yet it forwards an attacker-controllable `shop` string as if it were authenticated. Any host application that uses `WebhookMetadata#shop` to select which merchant's session/data record to update (the documented and expected usage pattern) can be tricked into attributing/processing a webhook under a different tenant's identity — a cross-tenant access primitive.

### Likelihood Explanation
Exploitation requires the attacker to possess at least one legitimately Shopify-signed webhook body for any shop (trivial: they can install the app themselves and receive real webhooks), then replay it to the app's webhook endpoint with a modified `x-shopify-shop-domain` header. No access to `api_secret_key` or any merchant token is needed, and the gem performs no additional binding check between the header and the signed payload.

### Recommendation
Include `shop` (and ideally `topic`, `webhook_id`) in the signed material checked by `Utils::HmacValidator`, or otherwise cryptographically bind the `x-shopify-shop-domain` header to the payload before trusting it (e.g., require the host app to independently confirm the shop against a known/expected value, and document that `request.shop` is unauthenticated header data derived independently of the HMAC).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and receives a legitimate webhook: raw body `B` with header `x-shopify-hmac-sha256: H` (valid signature over `B`) and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker resends the same `B`/`H` pair to the app's webhook endpoint but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Registry#process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (`= B`) — this still matches `H`, so validation passes: [5](#0-4) 
4. `WebhookMetadata` is built with `shop: request.shop` = `"victim-shop.myshopify.com"` and passed to the app's handler, which processes/attributes the webhook body under the victim shop's identity.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
