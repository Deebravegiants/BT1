The report's bug class — a beneficiary blacklisted by the payout asset permanently loses access to already-accrued funds because the withdraw function hardcodes `msg.sender` as recipient with no way to redirect — maps directly onto `FeeVault.claim()`.

### Title
Creator fee balances become permanently frozen in FeeVault if a creator's address is later blacklisted by USDC - (File: packages/contracts/src/FeeVault.sol)

### Summary
`FeeVault.claim()` pays out `creatorBalance[msg.sender]` directly to `msg.sender` with no recipient argument and no admin override. If a creator's address is ever blacklisted by the real USDC contract (a standard, admin-controlled mechanic on canonical USDC), all USDC already accrued to that creator becomes permanently unrecoverable, exactly mirroring the Ajna M-17 pattern where `repayDebt()`/`withdrawBonds()` hardcoded `msg.sender` as the fund recipient.

### Finding Description
`FeeVault.claim()` is:

```solidity
function claim() external nonReentrant returns (uint256 amount) {
    FeeVaultStorage storage $ = _s();
    amount = $.creatorBalance[msg.sender];
    if (amount == 0) revert NothingToClaim();
    $.creatorBalance[msg.sender] = 0;
    $.totalAccruedCreator -= amount;
    $.usdc.safeTransfer(msg.sender, amount);
    emit CreatorFeesClaimed(msg.sender, amount);
}
``` [1](#0-0) 

There is no `recipient` parameter — `safeTransfer` always targets `msg.sender`. Balances are accrued via `Zap._chargeFee` → `FeeVault.accrue(token, creator, creatorAmount, protocolAmount, isBuy)`, which credits `creatorBalance[creator]` where `creator` comes from `Bonding.tokenInfo(token).creator` at the time of the trade: [2](#0-1) [3](#0-2) 

The only redirect mechanism available is `Bonding.transferCreator(tokenAddress, newCreator)`, which only updates `tokenInfo[tokenAddress].creator` going forward for future `accrue()` calls — it does **not** touch the `creatorBalance` mapping already accumulated in `FeeVault` under the old address:
```solidity
function transferCreator(address tokenAddress, address newCreator) external {
    if (newCreator == address(0)) revert ZeroAddress();
    TokenInfo storage info = _s().tokenInfo[tokenAddress];
    if (msg.sender != info.creator) revert NotCreator();
    ...
    info.creator = newCreator;
}
``` [4](#0-3) 

So if a creator's address is blacklisted by USDC *after* fees have accrued but *before* `claim()` is called, `transferCreator()` cannot rescue the already-stuck balance: it can only redirect future accrual, and the creator can never call `claim()` themselves from the blacklisted address (any `safeTransfer` to it will revert on USDC's transfer hook). Unlike `claimProtocol()`, whose recipient (`feeTo`) can be repointed by the owner via `setFeeTo()`, there is no equivalent per-creator override — `creatorBalance` is a mapping keyed on the creator address itself, and the vault owner has no function to reassign or redirect an individual creator's stuck balance. [5](#0-4) 

`sweepDonations()` only rescues *unbacked* surplus (balance above `totalAccruedCreator + protocolBalance`) — it explicitly leaves backed creator balances untouched, so it provides no escape hatch either: [6](#0-5) 

### Impact Explanation
Every buy/sell against a launched token accrues 0.25% of the trade value to the token's creator in `FeeVault.creatorBalance`. If that creator address is later blacklisted by USDC — a real, admin-controlled feature of canonical USDC, not a hypothetical — 100% of that creator's already-earned, unclaimed USDC balance becomes permanently frozen in the vault with no recovery path, for as long as the creator keeps launching tokens and accruing fees under that address. This is a direct, permanent freezing of creator funds, matching the "medium" impact bar in the referenced report.

### Likelihood Explanation
Being added to USDC's blacklist is a low-probability event for any individual address (as the original report itself notes), so likelihood is low, but the freeze is total and irreversible once it happens — no owner action, `transferCreator` call, or user action can recover the already-accrued balance. Every active creator with unclaimed fees is exposed to this risk for as long as their balance remains unclaimed.

### Recommendation
Add a `recipient` (or `claim(address recipient)`) argument to `FeeVault.claim()` so a creator can direct payout to an alternate, non-blacklisted address, e.g.:
```solidity
function claim(address recipient) external nonReentrant returns (uint256 amount) {
    FeeVaultStorage storage $ = _s();
    amount = $.creatorBalance[msg.sender];
    if (amount == 0) revert NothingToClaim();
    $.creatorBalance[msg.sender] = 0;
    $.totalAccruedCreator -= amount;
    $.usdc.safeTransfer(recipient, amount);
    emit CreatorFeesClaimed(msg.sender, amount);
}
```
Alternatively/additionally, allow an owner-assisted migration function that moves a stuck `creatorBalance[oldCreator]` to a new address upon proof of ownership (e.g. signed message) once the old address is confirmed frozen.

### Proof of Concept
1. Creator `C` launches a token via `Zap.createToken`; `Bonding.tokenInfo(token).creator = C`.
2. Multiple trades occur via `Zap.buy`/`Zap.sell`; each call `Zap._chargeFee` → `FeeVault.accrue(token, C, creatorAmount, protocolAmount, isBuy)`, incrementing `creatorBalance[C]` — see accrual logic [2](#0-1) .
3. Real-world USDC issuer blacklists address `C` (e.g., due to an unrelated compliance flag, sanction list match, or compromised-key report).
4. `C` calls `Bonding.transferCreator(token, newAddress)` to protect *future* fees — this succeeds and updates `tokenInfo.creator`, but does nothing to the existing `creatorBalance[C]` already sitting in `FeeVault`.
5. `C` (or anyone) calls `FeeVault.claim()` from `C`'s wallet; `$.usdc.safeTransfer(msg.sender, amount)` reverts because USDC's `transfer` hook blocks transfers to/from a blacklisted address.
6. There is no `claim(address recipient)` variant, no owner-assisted redirect, and `sweepDonations()` explicitly excludes backed balances — `creatorBalance[C]` remains permanently locked in the vault.
