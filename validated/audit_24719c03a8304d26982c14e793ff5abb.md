### Title
No vulnerability — stale-salt rejection is already handled by automatic refresh-and-retry - ([File: packages/intents-sdk/src/intents/salt-manager.ts])

### Summary
`SaltManager.getCachedSalt()` does return the TTL-cached `currentSalt` without re-querying the contract, so a payload can theoretically be built with a salt that has just rotated on-chain. However, the SDK does not rely on `getCachedSalt()` alone for withdrawal execution: `signAndSendWithdrawalIntent`/`signAndSendIntent` route through `withSaltRetry`, which detects the exact on-chain rejection (`INVALID_SALT`) and automatically refreshes and retries, so the caller does not end up stranded.

### Finding Description
The claimed broken equality is: `salt embedded in built/signed payload == contract's current_salt at execution time`. Tracing `IntentPayloadBuilder.build()` → `this.saltManager.getCachedSalt()` (`packages/intents-sdk/src/intents/intent-payload-builder.ts:219-222`) confirms it can return a cached salt up to `SALT_TTL_MS` (5 min) old [2](#0-1)  without re-checking the chain, so in isolation the salt used to build a payload could differ from the contract's live `current_salt` if the contract rotates within that window [3](#0-2) .

However, when this builder is invoked through the SDK's actual withdrawal/intent-signing entry points (`signAndSendWithdrawalIntent`, `signAndSendIntent`), the build-and-publish sequence is wrapped in `withSaltRetry`, which passes the cached salt into the build function, and if the relayer/contract rejects the intent specifically because of an invalid salt (`RelayPublishRejectedError` with `code === "INVALID_SALT"`), the SDK calls `this.saltManager.refresh()` — which invalidates the cache and re-fetches `current_salt` from the chain — and retries the entire build-and-publish with the fresh salt [4](#0-3) . This means the on-chain contract's own signature/nonce verification (which necessarily validates the salt as part of nonce acceptance) is the ultimate authority, and any divergence is caught and self-healed automatically within the same call — not left for the "caller to manually retry."

### Impact Explanation
Since `withSaltRetry` transparently retries with a refreshed salt on the specific `INVALID_SALT` rejection code, no funds are stranded requiring manual intervention; the described "High" impact (withdrawal signed then failing on-chain, requiring manual retry) does not materialize through the documented SDK entry points.

### Likelihood Explanation
The raw `getCachedSalt()`/`build()` path exists as a lower-level API (e.g., for the standalone `IntentPayloadBuilder` used by integrators building payloads outside `signAndSendWithdrawalIntent`), where a caller could in principle build with a stale salt and sign it without automatic retry. But this requires the integrator to bypass the SDK's own retry-safe helper (`signAndSendWithdrawalIntent`/`signAndSendIntent`) and use the raw builder directly — which is a documented, intentional low-level API for server-side payload generation, not an attacker-controlled exploit path, and falls under the excluded category of "deliberately misusing a documented escape hatch."

### Recommendation
No fix required for the primary SDK flow. If desired, documentation for the standalone `IntentPayloadBuilder`/`ISaltManager` could be strengthened to advise integrators to call `refresh()` or handle `INVALID_SALT`-style rejections themselves when not using `signAndSendIntent`/`signAndSendWithdrawalIntent`.

### Proof of Concept
Not applicable — no distinct vulnerability found in the primary withdrawal-signing path; `withSaltRetry` in `packages/intents-sdk/src/sdk.ts:665-687` already handles the rotation scenario described in the question.

	private async withSaltRetry<T>(
		args: SignAndSendArgs,
		fn: (salt: Salt) => Promise<T>,
	): Promise<T> {
		try {
			const cachedSalt = await this.saltManager.getCachedSalt();

			return await fn(cachedSalt);
		} catch (err) {
			if (
				!(
					err instanceof RelayPublishRejectedError &&
					err.code === "INVALID_SALT"
				)
			)
				throw err;

			args.logger?.warn?.("Salt error detected. Refreshing salt and retrying");

			const newSalt = await this.saltManager.refresh();
			return fn(newSalt);
		}
	}
