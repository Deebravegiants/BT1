### Title
View-role users can retrieve bridge `OutgoingToken` secret via `GET /v2/bridge_types/:BridgeName` - (File: core/web/bridge_types_controller.go)

### Summary
The GitLab CVE-2019-15721 analog bug class is "an internal endpoint unintentionally allows a lower-privileged role to view/edit settings that should be restricted to a higher role." In this chainlink codebase, `BridgeTypesController.Show` is reachable by the lowest authenticated role (`view`) and returns the bridge's `OutgoingToken` — a live authentication secret — unredacted.

### Finding Description
The route `GET /v2/bridge_types/:BridgeName` is registered without any `auth.RequiresEditRole`/`RequiresRunRole` wrapper, unlike `Create`, `Update`, and `Destroy` on the same resource, which are explicitly gated behind `auth.RequiresEditRole` [1](#0-0) . This means any authenticated user with the lowest role, `UserRoleView`, can call `Show`, confirmed by the RBAC test map entry `{"GET", "/v2/bridge_types/MOCK", true, true, true}` (viewOnlyAllowed=true) [2](#0-1) .

`BridgeTypesController.Show` fetches the full `bridges.BridgeType` record and serializes it via `presenters.NewBridgeResource(bt)` with no field filtering based on role [3](#0-2) . The presenter struct includes `OutgoingToken` with a plain (non-`omitempty`) JSON tag, so it is always serialized into the response body [4](#0-3) .

`OutgoingToken` is a live secret: it's generated as a 24-byte random secret at bridge-creation time and stored in plaintext in the `outgoing_token` DB column (unlike `IncomingToken`, which is only hashed/salted server-side and never persisted in plaintext) [5](#0-4) . This token is meant to let the node authenticate itself to the external bridge/adapter when making outgoing calls — disclosing it lets a low-privilege viewer impersonate the node to that external adapter.

### Impact Explanation
Any node operator user granted only the `view` role (intended for read-only dashboards) can extract a live outgoing-authentication secret for any configured bridge by hitting `GET /v2/bridge_types/:BridgeName`. This is a privilege/role-boundary violation directly analogous to the GitLab CVE: a role meant to have read-only, non-sensitive access can retrieve a credential that should only be available to `edit`/`admin` roles. With the token, the view-role user could impersonate the chainlink node to the external adapter/bridge endpoint (request/response impersonation), potentially manipulating job-run pricing or observation data depending on how the adapter uses the outgoing token.

### Likelihood Explanation
High for any deployment that issues `view`-role API tokens/users (a supported, documented role: `chainlink admin users create --role view` [6](#0-5) ). No special conditions are needed — a single authenticated GET request with a valid view-role session/token is sufficient, and the RBAC test suite explicitly documents and asserts that this route returns non-Unauthorized/Forbidden for view-role clients [7](#0-6) , confirming this is intended, tested behavior rather than an edge case.

### Recommendation
Either (a) redact `OutgoingToken` from `presenters.NewBridgeResource` for all `Show`/`Index` responses and only reveal secrets from mutating (`Create`) responses, mirroring how `IncomingToken` is already handled with `omitempty` and only populated on `Create`, or (b) gate `GET /v2/bridge_types/:BridgeName` behind `auth.RequiresEditRole` similar to the write endpoints on the same resource.

### Proof of Concept
1. Create an API user with `--role view`: `chainlink admin users create --email view@x.com --role view`.
2. Authenticate as that user and call `GET /v2/bridge_types/<bridgeName>` for an existing bridge.
3. Observe the JSON response includes `"outgoingToken": "<secret>"` in the `bridges` resource body, confirmed by `presenters.NewBridgeResource` mapping `OutgoingToken` unconditionally [8](#0-7)  and the route's RBAC test allowing this for view role [2](#0-1) .

// Show returns the details of a specific Bridge.
func (btc *BridgeTypesController) Show(c *gin.Context) {
	ctx := c.Request.Context()
	name := c.Param("BridgeName")

	taskType, err := bridges.ParseBridgeName(name)
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	bt, err := btc.App.BridgeORM().FindBridge(ctx, taskType)
	if errors.Is(err, sql.ErrNoRows) {
		jsonAPIError(c, http.StatusNotFound, errors.New("bridge not found"))
		return
	}
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	jsonAPIResponse(c, presenters.NewBridgeResource(bt), "bridge")
}

// NewBridgeType returns a bridge type authentication (with plaintext
// password) and a bridge type (with hashed password, for persisting)
func NewBridgeType(btr *BridgeTypeRequest) (*BridgeTypeAuthentication,
	*BridgeType, error,
) {
	incomingToken := utils.NewSecret(24)
	outgoingToken := utils.NewSecret(24)
	salt := utils.NewSecret(24)

	hash, err := incomingTokenHash(incomingToken, salt)
	if err != nil {
		return nil, nil, err
	}

	return &BridgeTypeAuthentication{
		Name:                   btr.Name,
		URL:                    btr.URL,
		Confirmations:          btr.Confirmations,
		IncomingToken:          incomingToken,
		OutgoingToken:          outgoingToken,
		MinimumContractPayment: btr.MinimumContractPayment,
		UseConnectionManager:   btr.UseConnectionManager,
	}, &BridgeType{
		Name:                   btr.Name,
		URL:                    btr.URL,
		Confirmations:          btr.Confirmations,
		IncomingTokenHash:      hash,
		Salt:                   salt,
		OutgoingToken:          outgoingToken,
		MinimumContractPayment: btr.MinimumContractPayment,
		UseConnectionManager:   btr.UseConnectionManager,
	}, nil
}
