### Title
Webhook `shop` field is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC computed over the raw request body, but the `shop` value that is handed to the app's handler comes from an HTTP header that is never included in that signed payload. The binding "shop whose HMAC was verified" == "shop the handler is told the event came from" does not hold, allowing an attacker who controls their own shop to replay a legitimately-signed webhook while relabeling it as belonging to a different (victim) shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read independently from the `shopify-shop-domain`/`x-shopify-shop-domain` header and is never mixed into the signed string: [2](#0-1) 

`Utils::HmacValidator.validate` verifies the HMAC strictly against `to_signable_string` (i.e., the raw body only), independent of the `shop` accessor: [3](#0-2) 

`Registry.process` raises only if this body-only HMAC check fails, then forwards `request.shop` (the unauthenticated header value) straight into `WebhookMetadata` passed to the app's handler: [4](#0-3) 

Because the app's `client_secret`/webhook signing secret is shared across every shop that installs the app, any merchant can install the app on their own store, trigger a real webhook event, and capture a genuinely Shopify-signed `(raw_body, hmac-sha256)` pair for their own store. The identity binding this code should enforce is:

`shop authenticated by HMAC` == `shop acted upon by the handler`

Since `shop` is not part of the signed bytes, an attacker can replay the exact same `raw_body`/`hmac-sha256` pair to the app's public webhook endpoint while substituting the `shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` still succeeds (body+HMAC are unchanged and valid), and `Registry.process` calls the handler with `WebhookMetadata.new(... shop: request.shop ...)` reporting the victim's shop, even though the payload never actually originated from or concerns the victim shop.

### Impact Explanation
This breaks tenant isolation: an unprivileged attacker who merely installs the app on a shop they control can forge webhook events "from" any other shop that has installed the app, without ever obtaining the app's `client_secret` or any victim credentials. Any application logic keyed off `WebhookMetadata#shop` (order sync, subscription state, data deletion/GDPR webhooks, uninstall handling, etc.) can be manipulated to act against a different tenant's stored data using attacker-chosen content, which is a cross-tenant access impact.

### Likelihood Explanation
High feasibility: the attacker only needs a free/development store to install the target app (a normal, unprivileged action), trigger any webhook topic the app is registered for, capture the body and `hmac-sha256` header from the request Shopify sends, and resend it to the app's registered webhook endpoint with a modified `shop-domain` header. No secret material or privileged access is required.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the value that is HMAC-verified, e.g. include the `shopify-shop-domain` header value in the signable string used by `Request#to_signable_string`, or cross-check the header's shop domain against an already-known/authorized installation record before trusting it in `WebhookMetadata`. At minimum, document and enforce that `request.shop` must never be trusted unless it is cryptographically bound to the verified bytes.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (self-service, no privileges needed).
2. Attacker triggers a real event (e.g., creates an order) causing Shopify to POST a genuine, correctly HMAC-signed webhook to the app's endpoint:
   - Headers: `shopify-topic: orders/create`, `shopify-hmac-sha256: <valid-hmac-of-body>`, `shopify-shop-domain: attacker-shop.myshopify.com`
   - Body: `{...order json...}`
3. Attacker captures this raw body and the `shopify-hmac-sha256` value.
4. Attacker resends the identical body and `shopify-hmac-sha256` header to the same app endpoint, but sets `shopify-shop-domain: victim-shop.myshopify.com`.
5. `Utils::HmacValidator.validate` (called from `Registry.process`, `lib/shopify_api/webhooks/registry.rb:190`) validates successfully because it only checks `raw_body` against the HMAC.
6. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and attacker-controlled body content, believing it is a legitimate event from the victim shop.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
