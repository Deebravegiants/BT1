### Title
Webhook Tenant Spoofing via Unsigned Shop-Domain Header - ([File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC of the raw request body, then trusts the `shop` value taken from the `X-Shopify-Shop-Domain`/`shopify-shop-domain` header — a field that is never included in the signed payload — to build the `WebhookMetadata` passed to the app's handler.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0)  while `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers without being part of the signed string: [2](#0-1) .

`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` and compares it to the `hmac` value, using the app's shared `api_secret_key`: [3](#0-2) . Since `to_signable_string` for a webhook `Request` is just the body, this check only proves "this body was signed with our secret" — it proves nothing about which shop header accompanied it.

`Registry.process` then does:
```
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
...
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))
``` [4](#0-3) 

The identity binding that should hold is: `shop-header == shop-that-produced-this-signed-body`. Because the header is outside the HMAC's scope, this equality is never checked. An attacker who owns/controls one installed shop (tenant A) can capture a legitimate, validly-signed webhook body that Shopify sent for shop A (e.g., by installing the app on their own store and triggering an event), then replay that exact body to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a victim shop B. The HMAC still validates (it only checks the body against the shared secret, which is the same for all shops on the app), and `Registry.process` hands the handler `shop: "shop-b.myshopify.com"` together with shop A's body content, since the documented handler contract explicitly trusts `data.shop` as the tenant: [5](#0-4) .

Downstream, apps are documented and expected to use `data.shop` directly to route/attribute the webhook payload (e.g., `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) as shown in the gem's own usage example: [6](#0-5) . Because the gem itself performs the tenant-identifying step (extracting `shop` and handing it to the handler) after only validating the body's HMAC, the cross-tenant confusion originates inside this gem's `process` method, not merely from host-application misuse.

### Impact Explanation
This breaks the tenant boundary the gem is responsible for establishing before calling into app code: a payload cryptographically proven only to originate from *some* shop of the app can be attributed to *any* shop domain the attacker names in an unauthenticated header, resulting in cross-tenant data confusion/injection — data belonging to shop A being processed/stored/acted upon as if it belongs to shop B.

### Likelihood Explanation
Exploitation requires the attacker to install the app on their own store (an unprivileged, self-service action) to obtain one validly signed webhook body, and then send an HTTP POST to the app's public webhook endpoint with an altered shop header — no access token, `client_secret`, or privileged account is needed.

### Recommendation
Bind the shop (and ideally topic/webhook_id) into the signed material, or otherwise verify server-side that the `shop` header corresponds to a shop session/installation that is expected to be producing that specific webhook body/topic, rather than trusting the header value as-is once the body-only HMAC passes.

### Proof of Concept
1. Install the target app on attacker-owned store `attacker.myshopify.com`; trigger a webhook (e.g. `orders/create`) and capture the raw POST: body `B`, valid header `X-Shopify-Hmac-Sha256: H` (HMAC of `B` with the app's shared secret), and header `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Resend the exact same request to the app's webhook endpoint, keeping body `B` and `X-Shopify-Hmac-Sha256: H` unchanged, but replace the header with `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `B` against `H` using the shared secret [7](#0-6) .
4. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed(B), ...)` [8](#0-7) , causing the attacker-controlled body to be processed under the victim tenant's identity.
