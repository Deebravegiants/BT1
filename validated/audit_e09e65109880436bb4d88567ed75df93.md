### Title
Cross-signup frame carryover via `initial_inputs` in `Inner::into_shared_memory`/`spawn_shared_rx_task` - ([File: agentwire/src/port.rs])

### Summary
`Inner::into_shared_memory`'s `close` future drains up to two buffered-but-unconsumed frames from the shared-memory ring (`SharedMemory.input_count`/`input_index`) into an `InitialInputs` vec, which the calling broker code can then pass as `initial_inputs` into the next `into_shared_memory` call for a subsequent process/session. If the broker does not discard these buffered bytes between two consecutive signups, `spawn_shared_rx_task` will replay them (`initial_inputs.pop()`) as the very first frames delivered to the new `RemoteInner<T>` session before any freshly captured input.

### Finding Description
`Inner::into_shared_memory` (agentwire/src/port.rs:624-663) returns a `close` future that, on teardown, reads the shared ring's `input_count`/`input_index` header fields and copies any buffered-but-not-yet-consumed raw serialized bytes into an `InitialInputs = Vec<(Box<[u8]>, Instant)>` [1](#0-0) . This vector is explicitly designed to be handed back into a subsequent `into_shared_memory(name, init_state, initial_inputs)` call, and `spawn_shared_rx_task` pops entries off `initial_inputs` and writes them into the fresh shared memory ring as the first inputs, ahead of anything read from the `InnerRx<T>` channel [2](#0-1) . The mechanism has no notion of "session"/"signup" identity attached to the buffered bytes — it is a raw byte-preserving carry-over designed for process-recycling continuity (e.g., not losing a frame that was captured but not yet consumed when a subprocess is torn down/restarted), and is agnostic to whether the caller reuses it across the same logical session or a different one.

I located only a single call site of `into_shared_memory` in `agentwire/src/agent/process.rs`, but I was unable to fully confirm within available index/time whether the broker code that drives per-signup agent restarts (e.g. in `src/agents/qr_code.rs`, `src/agents/camera/mod.rs`, `src/brokers/orb.rs`) ever discards `InitialInputs` between distinct signups versus feeding it forward on every process restart regardless of signup boundary. This is the crux of exploitability and requires further investigation.

Separately, even if buffered frames from signup A did reach signup B's `RemoteInner<T>` as the first `recv()` results, I found `src/agents/image_notary.rs` binds captured frames to a `signup_id` at capture/notarization time [3](#0-2) , which is a plausible mitigation boundary — a leaked raw camera frame reused as the "first frame" of session B would still need to pass through the notary/pipeline logic that stamps the *current* signup's ID onto whatever frame arrives, and I was not able to confirm from the index whether the notary distinguishes "this frame is stale/from a different physical session" versus just tagging whatever bytes it receives with the currently-active signup_id.

### Impact Explanation
If exploitable, the impact would be one signup's raw sensor byte buffer (e.g., a QR code frame or camera frame) surviving process teardown and being fed as the first `recv()` result of the next signup's shared-memory channel, potentially causing stale/wrong-person frame data to be processed and time-stamped/tagged under a different signup_id — a session-isolation ("identity binding is exact") violation. However, I could not confirm the complete reachable path from a real broker signup-restart flow to this code, nor rule out that the broker always passes an empty `InitialInputs` on a fresh signup (which would fully neutralize this).

### Likelihood Explanation
Uncertain. The precondition requires: (1) a `SharedPort`-based agent process recycled via `into_shared_memory` between two signups, (2) at least one buffered-but-unconsumed frame in the ring at teardown time (`input_count` > 0), and (3) the broker/orb code explicitly threading the drained `InitialInputs` from session A's close future into session B's `into_shared_memory` call rather than discarding it. I was unable to verify point (3) with available tools/time — the single call site found in `agentwire/src/agent/process.rs` needs inspection to determine whether `initial_inputs` is reset to an empty `Vec::new()` on each new signup or genuinely carried across signup boundaries.

### Recommendation
Regardless of the above uncertainty, as a defensive measure: `InitialInputs` should be scoped/tagged with the signup/session identifier it was captured under, and the broker should explicitly clear/drop any leftover `InitialInputs` when starting a *new* signup (as opposed to a mere process-crash-and-restart within the *same* signup). Add an explicit `signup_id` (or generation counter) field alongside each buffered `(Box<[u8]>, Instant)` entry and assert it matches the current signup before replay, or simply pass `Vec::new()` whenever `into_shared_memory` is invoked at the start of a new signup rather than reusing the previous session's drained buffer.

### Proof of Concept
Because I could not confirm the actual broker call site behavior for signup boundaries within the available time/tools, I cannot assert this is currently exploitable end-to-end. A concrete PoC to validate/refute this would be:

1. Integration test in `agentwire/src/port.rs` (or a new test module) with a fake `SharedPort` type whose `Input` carries a one-byte "session marker".
2. Spawn `Inner::into_shared_memory` for "session A", send 2 tagged frames (marker=`A`), then invoke the returned `close` future to simulate abort/teardown, capturing the resulting `InitialInputs`.
3. Feed that same `InitialInputs` into a second `Inner::into_shared_memory` call for "session B" (simulating the exact broker call path used in `agentwire/src/agent/process.rs`), and have a `RemoteInner<T>::recv()` on the new shared memory.
4. Assert: if the codebase's real broker restart path (in `agentwire/src/agent/process.rs`) does zero out `initial_inputs` per new signup, `recv()` in session B should never observe marker `A`. If it does carry it forward, this confirms the vulnerability as described and the recommendation above should be applied.

This PoC/investigation should be completed with full file access to `agentwire/src/agent/process.rs` and the broker/agent-restart call sites in `src/brokers/orb.rs`, `src/agents/qr_code.rs`, and `src/agents/camera/mod.rs`, which the current index-based tools did not fully expose. I recommend starting a Devin session to access complete file contents and confirm/refute this finding definitively.
