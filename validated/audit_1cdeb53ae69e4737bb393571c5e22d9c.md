### Title
Webhook shop-domain and topic headers are not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC computed over the raw request body. The `shop-domain` and `topic` HTTP headers — which the library uses to decide *which shop* and *which topic* the payload is dispatched to the host app's handler for — are never included in the signed data. Any user who can obtain one genuinely-signed webhook body (e.g., by installing the app on their own store and receiving their own real webhooks) can replay that same body with a forged `shop-domain` and/or `topic` header, and the library will accept it as authentic for an arbitrary shop/topic.

### Finding Description
`Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

`Utils::HmacValidator.validate_signature` computes the signature exclusively over that signable string and compares it to the `hmac-sha256` header: [2](#0-1) 

`Registry.process` only checks this body-only HMAC before dispatching to the handler using the *unauthenticated* `shop` and `topic` headers: [3](#0-2) 

`Request#shop` and `Request#topic` are read directly from attacker-controllable HTTP headers with no cross-check against the signed body: [4](#0-3) 

**Identity binding broken (as equality):**
`hmac_valid(body) == true` is treated as proof that `(shop, topic, body)` all genuinely originated from Shopify for that shop/topic, when the gem only guarantees `hmac_valid(body) == true` for `body` alone. `shop` and `topic` are unauthenticated inputs smuggled in via headers that ride along with a validly-signed body.

**Attack path (unprivileged internet user, no credentials needed):**
1. Attacker installs the target app on their own store (any normal user can do this — it requires no privileged access to the victim or the app's secrets). Shopify delivers a webhook to the app's endpoint with a valid `x-shopify-hmac-sha256` for the attacker's own shop and topic, e.g. `topic=orders/create`, `shop-domain=attacker-shop.myshopify.com`.
2. Attacker captures this raw body and legitimate HMAC (both attacker-observable, since it's their own traffic).
3. Attacker POSTs the same raw body + HMAC to the app's public webhook endpoint again, but this time sets `x-shopify-shop-domain: victim-shop.myshopify.com` and/or a different `x-shopify-topic` value.
4. `HmacValidator.validate` still passes (only the body is checked), so `Registry.process` invokes the registered handler with `WebhookMetadata.new(topic: "attacker-chosen", shop: "victim-shop.myshopify.com", body: ...)`.
5. Any host application logic that trusts `data.shop`/`data.topic` from the handler (e.g., to look up or write per-tenant data, trigger uninstall/redact flows, or key a database write) now operates under the wrong shop identity — a cross-tenant data/action confusion originating entirely from this gem's verification gap.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook processing: an attacker fully controls which shop identity a genuinely-signed payload is attributed to, and which topic handler processes it. Depending on host app logic (e.g., `shop/redact`, `customers/data_request`, or shop-scoped side effects keyed by `data.shop`), this enables cross-tenant access/action on behalf of another merchant purely from unprivileged internet-facing requests — meeting the "cross-tenant access" Critical impact bucket.

### Likelihood Explanation
High. Any user can self-register the app on a free/dev store to legitimately obtain a validly-signed webhook body, then replay it with modified headers against the app's public webhook endpoint. No access token, `client_secret`, or privileged account is required — only normal app installation, which this gem's own webhook processing flow exposes to.

### Recommendation
Bind `shop` and `topic` (and any other value the host app dispatches on) into the signed data, or independently verify them against Shopify (e.g., cross-check `shop-domain` against the session/shop the webhook was registered for, and include `topic`/`shop-domain` in `to_signable_string`, mirroring how `AuthQuery#to_signable_string` binds `shop`/`host` into its HMAC). At minimum, document and enforce that host apps must not trust `WebhookMetadata#shop`/`#topic` without an independent registration-time association check keyed off the raw body content.

### Proof of Concept
```ruby
# 1. Attacker installs app on their own store; Shopify sends a real webhook:
raw_body = '{"id":1,"note":"legit order for attacker-shop"}'
real_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), APP_SECRET, raw_body)

# Attacker captures raw_body + Base64.encode64(real_hmac) from their own traffic.

# 2. Attacker replays the same body/hmac against the app's public webhook endpoint,
#    but swaps the shop-domain and topic headers:
forged_headers = {
  "x-shopify-topic"        => "shop/redact",                     # attacker-chosen
  "x-shopify-hmac-sha256"  => Base64.encode64(real_hmac),         # reused, still valid for raw_body
  "x-shopify-shop-domain"  => "victim-shop.myshopify.com",        # attacker-chosen
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) succeeds because it only checks raw_body,
#    and the handler for "shop/redact" is invoked with shop: "victim-shop.myshopify.com".
``` [3](#0-2)
