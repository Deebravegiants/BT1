The docs explicitly document that `Registry.process` "will verify the request did indeed come from Shopify" (line 125 of `docs/usage/webhooks.md`), and describe `data.shop` as "The shop domain of the webhook" without any caveat that it is unverified — so a host app relying on this documented contract to scope data by shop is a legitimate use of the gem's own documented API, not host misuse.

I confirmed the root cause: `HmacValidator.validate` only checks `verifiable_query.to_signable_string`, and for webhooks that is exclusively `@raw_body`.### Title
Webhook Shop-Domain Header Is Not Covered by HMAC Verification, Enabling Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook as "verified" once `Utils::HmacValidator.validate` succeeds, and then trusts `request.shop` (taken straight from the `x-shopify-shop-domain`/`shopify-shop-domain` header) as the authenticated tenant identity handed to the app's handler. The HMAC, however, is computed only over the raw request body, never over the shop-domain, topic, or webhook-id headers. Any actor who can obtain one genuine `(body, hmac)` pair signed by the app's shared `client_secret` — trivially achievable by installing the app on their own store, an unprivileged action — can replay that body with a forged shop-domain header and still pass verification.

### Finding Description
The identity binding that should hold is:

`shop domain claimed in the request == shop domain that produced the HMAC-signed bytes`

but the code only proves:

`hmac == HMAC(api_secret_key, raw_body)`

`to_signable_string` for a webhook request returns solely `@raw_body`: [1](#0-0) 

`shop` (and `topic`, `webhook_id`, `api_version`) are pulled straight from unauthenticated headers, entirely outside the signed material: [2](#0-1) 

`HmacValidator.validate`/`validate_signature` only ever checks the `VerifiableQuery`'s signable string (the raw body, for webhooks) against the provided `hmac`; it never touches the shop or topic headers: [3](#0-2) 

`Registry.process` gates entirely on that same HMAC check, then forwards `request.shop` to the handler as `WebhookMetadata.shop` — the value the host app is documented to trust as "the shop domain of the webhook": [4](#0-3) [5](#0-4) 

The gem's own documentation states that `Registry.process` "will verify the request did indeed come from Shopify" and describes `data.shop` simply as "The shop domain of the webhook," with no caveat that this field is unauthenticated: [6](#0-5) [7](#0-6) 

For a multi-tenant public app, `Context.api_secret_key` (the app's `client_secret`) is the same value used by Shopify to sign webhooks for every shop that has installed the app — it is not shop-specific. Consequently, an unprivileged attacker who installs the app on their own store receives genuine `(raw_body, hmac)` pairs. They can then send that exact body to the app's webhook endpoint with the `x-shopify-shop-domain` header rewritten to a victim shop, and any topic they choose (subject to controlling the body content enough to match a registered topic/schema). `HmacValidator.validate` still returns `true` because the signed bytes (the body) are unchanged, and `Registry.process` dispatches to the handler with `WebhookMetadata.shop` set to the forged victim domain.

### Impact Explanation
This is a cross-tenant identity-binding break: the shop identity delivered to the app's business logic is not bound to the entity that actually produced the signed payload. Any host application that scopes side effects (data writes, GDPR redaction flows, order/customer processing, cache invalidation, feature flags) by `data.shop` as documented can have those actions triggered against an arbitrary victim tenant by an attacker who only needs to be a legitimate (even free/trial) installer of the app on their own store. This matches the "Critical - cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high for any multi-tenant public app: installing the app on one's own shop requires no special privilege, and obtaining a valid `(body, hmac)` pair is a normal side effect of that installation (e.g., triggering `orders/create` or the mandatory `customers/data_request`/`shop/redact` topics on the attacker's own store). Replaying with a modified header requires no cryptographic secret at all.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the HMAC-covered material, or otherwise cryptographically bind the header-derived `shop` value to the request before exposing it via `WebhookMetadata`. At minimum, update `Utils::HmacValidator`/`Webhooks::Request` so `to_signable_string` incorporates the shop-domain header, and clearly document in `docs/usage/webhooks.md` that `data.shop` is not authenticated unless such binding is added, so host apps cannot inadvertently rely on it as a trusted tenant identifier.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`, completing OAuth normally (no special privilege required).
2. Attacker triggers a webhook topic handled by the app (e.g. `customers/data_request`) on their own store, capturing the raw POST body and the `x-shopify-hmac-sha256` value Shopify sends — both signed with the app's shared `api_secret_key`.
3. Attacker replays this exact `raw_body`/`hmac` pair to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `raw_body` against `hmac` (`lib/shopify_api/utils/hmac_validator.rb:12-31`, `lib/shopify_api/webhooks/request.rb:35-38`).
5. The registered handler is invoked with `WebhookMetadata.shop == "victim-shop.myshopify.com"` even though the payload was produced by, and for, the attacker's own store, letting the attacker inject/trigger tenant-scoped side effects against the victim.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
