## Title
Non-EOA (smart contract) beneficiaries permanently lose bridged funds when `HyperFungibleToken` transfers land on a Substrate destination - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
The `pallet-hyper-fungible-token` `on_accept` handler derives the Substrate `AccountId` for an incoming transfer's beneficiary by zero-padding a 20-byte EVM address directly into a 32-byte account, with no verification that any private key controls that account. The only mechanism the pallet provides for later authorizing spends from such a derived account is an ECDSA signature recovery scheme that requires a secp256k1 private key — something a smart-contract address fundamentally cannot possess. This is the same class of bug as the reported NFT-migration issue: a non-EOA address on the source chain is mapped to a destination-chain address/account that the non-EOA holder cannot control, causing tokens to be permanently frozen.

### Finding Description
When an EVM `HyperFungibleToken`/`WrappedHyperFungibleToken` `send()` call targets a Substrate `pallet-hyper-fungible-token` deployment, the `to` field of the `Message` may be either 32 bytes (a native Substrate `AccountId`) or 20 bytes (an EVM-style address). In `on_accept`, the pallet handles the 20-byte case by simple zero-padding, with no distinction between EOAs and contracts: [1](#0-0) 

The resulting `beneficiary` `AccountId` then directly receives minted or escrow-released tokens: [2](#0-1) 

The default `EvmToSubstrate` implementation used by production runtimes performs the identical zero-padding, confirming this is the intended, non-cryptographic address scheme: [3](#0-2) 

The pallet does provide a way to *dispatch* a runtime call as this derived `beneficiary` origin — via `Message.data` calldata carrying a `MultiSignature`. Critically, the ECDSA branch recovers the signer's Ethereum address from a raw secp256k1 signature and checks that `EvmToSubstrate::convert(eth_address) == beneficiary`: [4](#0-3) 

This is the *only* path by which the holder of an EVM-address-derived beneficiary account can move funds out of it (transfer, swap, withdraw, etc., via an arbitrary `runtime_call` dispatched with `RawOrigin::Signed(beneficiary)`), because the derived `AccountId` is not a valid sr25519/ed25519 public key and cannot be used to sign ordinary Substrate extrinsics.

An EOA can reconstruct the required ECDSA signature because it holds the secp256k1 private key for its EVM address. A smart contract cannot: contracts have no private key and cannot produce a `secp256k1_ecdsa_recover`-compatible signature over the `(nonce, runtime_call)` payload. Consequently, whenever the beneficiary of an EVM→Substrate `HyperFungibleToken` transfer is a smart-contract address (rather than an EOA) — e.g., a vault, multisig, DAO treasury, or any programmatic recipient specified as a raw 20-byte address — the minted tokens land in a Substrate account that has no possible way to ever be spent from, by any mechanism the pallet exposes.

This mirrors the reported bug precisely: an address type valid and controllable on the source chain (an EVM contract) is mapped, during a cross-chain migration/transfer, to a destination-chain representation (a zero-padded `AccountId32`) that the original holder cannot control, permanently losing the bridged value.

### Impact Explanation
Funds minted or released to a smart-contract-derived beneficiary account on the Substrate destination are permanently and irrecoverably frozen — there is no code path in `pallet-hyper-fungible-token`, or the wider ISMP/HFT stack, that allows a contract (lacking a secp256k1 private key) to dispatch a call as that derived account. Any user or integrator bridging tokens from an EVM chain to a Substrate chain using a contract address as the `to` recipient (a normal, encouraged usage pattern per the SDK docs: `"Recipient on destination chain (20 bytes for EVM, 32 bytes for substrate)"`) will suffer total, permanent loss of the transferred amount. This satisfies "permanent freezing of funds" for High severity.

### Likelihood Explanation
Likelihood is significant because: (1) the 20-byte `to` encoding is a first-class, documented, and tested code path (not an edge case) in the HFT cross-chain message format; (2) nothing in `send()`, the SDK, or `on_accept` distinguishes or warns against non-EOA recipients; (3) common integration patterns (bridging to a vault, a DeFi protocol contract, or any programmatic recipient) would naturally specify a contract address as `to`. Because this requires no attacker action — it is a routine, unprivileged token-bridge transfer that is silently unrecoverable — the likelihood of accidental fund loss is high whenever the destination is a Substrate chain and the specified recipient is a contract address.

### Recommendation
- Reject or explicitly flag 20-byte `to` recipients in `on_accept` when the destination requires proof of key ownership, or require the sender to additionally supply a genuine 32-byte Substrate `AccountId` for the beneficiary rather than relying on address zero-padding.
- Alternatively, implement an explicit "claim" mechanism analogous to a mirror/wrapped token: mint to a chain-custodied intermediate account keyed by the source (chain, address) pair, and allow the true controller (proven via ISMP-relayed proof of a call originating from the exact source contract) to redeem — rather than directly minting into an unprovable derived `AccountId`.
- At minimum, document prominently (and enforce at the SDK layer) that 20-byte recipients on Substrate destinations must be EOAs, and add a runtime-level check/warning path that reverts transfers whose `to` resolves to a known contract address structure where feasible.

### Proof of Concept
1. Deploy `HyperFungibleToken` on an EVM chain (e.g. `EVM-1`) paired with `pallet-hyper-fungible-token` on a Substrate chain (module id `pall_hft`), following the standard registration flow (`addChain`/`register_token`).
2. From a smart contract `C` (e.g. a simple vault with no ECDSA signing capability) on the EVM chain, call:
   ```solidity
   hft.send(HyperFungibleToken.SendParams({
       dest: StateMachine.polkadot(paraId),
       to: abi.encodePacked(address(C)),   // 20-byte contract address as beneficiary
       amount: 1000e18,
       timeout: 3600,
       relayerFee: 0,
       data: ""
   }));
   ```
3. On the Substrate side, `on_accept` ( [5](#0-4) ) computes `beneficiary` by zero-padding `address(C)` into a 32-byte `AccountId`, and mints/transfers the tokens there.
4. Attempt to move these tokens: the only pallet-provided mechanism is submitting a follow-on `HyperFungibleToken` message with `data` containing a `SubstrateCalldata` with a `MultiSignature::Ecdsa` recovering to `address(C)`. Since `C` is a contract with no private key, it is structurally impossible to produce this signature (or any sr25519/ed25519 signature for the account), so the funds credited to `beneficiary` can never be spent.

/// Converts an EVM address to a substrate AccountId
pub trait EvmToSubstrate<T: frame_system::Config> {
	fn convert(addr: H160) -> T::AccountId;
}

/// Default implementation: zero-pads the 20-byte address into a 32-byte AccountId
impl<T: frame_system::Config> EvmToSubstrate<T> for ()
where
	<T as frame_system::Config>::AccountId: From<[u8; 32]>,
{
	fn convert(addr: H160) -> <T as frame_system::Config>::AccountId {
		let mut account = [0u8; 32];
		account[12..].copy_from_slice(&addr.0);
		account.into()
	}
}
