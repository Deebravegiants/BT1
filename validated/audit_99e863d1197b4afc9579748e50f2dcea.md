### Title
Webhook `shop-domain` (and `topic`/`webhook-id`) identity fields are trusted unauthenticated while only the raw body is HMAC-covered - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then passes the caller-supplied `shop-domain` header straight through to the app's handler as the tenant identity, without that header ever being covered by the HMAC computation.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` is invoked on the `Request` object, and the signable string used for verification is defined as just the raw body: [1](#0-0) 

The `shop`, `topic`, `api_version`, and `webhook_id` accessors are all read directly from HTTP headers that are never included in `to_signable_string`, and therefore never validated by the HMAC check: [2](#0-1) 

`Registry.process` performs the HMAC check and then immediately hands `request.shop` (and `request.topic`) to the application's handler as trusted tenant identity, with no additional binding between the verified body and the unverified `shop` header: [3](#0-2) 

This is structurally the same class of bug as the `MainVault` report: a value that is *acted upon* (`shop`, used by the handler to select/attribute a tenant) is not part of the data set that is cryptographically bound (`raw_body`) by the equality check the code relies on for authenticity — i.e. `HMAC(raw_body) == received_hmac` says nothing about `shop == verified_shop`. Any host application that uses `request.shop` (as the documented `WebhookMetadata#shop` field is intended to be used) to determine which merchant/tenant a webhook belongs to is trusting an attacker-controlled header field whose integrity was never checked.

### Impact Explanation
If a host application relies on `ShopifyAPI::Webhooks::Registry.process` and the resulting `WebhookMetadata#shop` value to route webhook data to per-tenant storage/business logic (exactly the documented usage pattern, see `docs/usage/webhooks.md`), an attacker who can produce any request with a body/HMAC pair that is valid under the app's shared `client_secret` (e.g. by replaying/relaying a legitimate webhook originally sent for their own store) can freely rewrite the `x-shopify-shop-domain` header to name a different, victim tenant. Because the gem itself never checks that the header-derived `shop` is consistent with anything HMAC-covered, the request is accepted as authentic and processed under the attacker-chosen shop identity. This enables cross-tenant data injection/processing — the kind of tenant-isolation ("shop authenticated versus shop used") break called out as in-scope.

### Likelihood Explanation
This requires the attacker to control (or intercept/relay) at least one syntactically valid webhook delivery for some shop under the same app (all shops installing a public app share the same `client_secret`, so any of the app's other merchants — or the attacker's own trial/dev store — can legitimately generate a validly-signed body). No access to the target's access token, `client_secret`, or TLS interception is required; only reachable, gem-internal logic (`Request`/`Registry.process`) is involved, and the vulnerable code path is exactly the one documented for host apps to use in `docs/usage/webhooks.md`.

### Recommendation
Bind the `shop-domain` (and ideally `topic`/`webhook-id`) header values into the HMAC-signable data, or otherwise cryptographically tie them to the verified body (e.g. by including them in the signed payload envelope), so that `HmacValidator.validate` fails if any of these identity-bearing headers are altered relative to what Shopify actually sent for that specific delivery.

### Proof of Concept
1. App B has webhooks registered for topic `orders/create` and uses `WebhookMetadata#shop` from `Registry.process` to look up and update the shop's local order records.
2. Attacker installs App B on their own throwaway store `attacker.myshopify.com` and receives a legitimately-signed `orders/create` webhook: body `{...}` with header `x-shopify-hmac-sha256: <valid HMAC over body with client_secret>` and `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker relays this exact body/HMAC pair to the app's webhook endpoint but swaps the header to `x-shopify-shop-domain: victim.myshopify.com` (and adjusts `topic`/`webhook-id` freely, as needed).
4. `ShopifyAPI::Utils::HmacValidator.validate` succeeds because it only checks `HMAC(raw_body)` [4](#0-3) , and `Registry.process` dispatches the handler with `shop: "victim.myshopify.com"` [5](#0-4) , causing the app to process attacker-controlled order data under the victim's tenant.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
