### Title
Hostile pre-seed of the HyperSwap V2 TOKEN/LT pair can permanently mis-price the graduated LP away from the curve-close price - ([File: packages/contracts/src/Bonding.sol])

### Summary
`Bonding._seedRebalancing` / `_pairRebalance` correct a hostile pre-seed of the post-graduation HyperSwap V2 pair by swapping toward the curve-close ratio, but the corrective swap is capped by `_swapBudget` at 99% of **this graduation's own** token/LT inventory (`tokensForLP`, `ltFromPair` — both bounded by fixed, small protocol constants), not by whatever is required to fully neutralize an oversized pre-seed. An attacker who funds a sufficiently large pre-seed of the pair (via `IUniswapV2Pair.mint`) before `finalizeGraduation` runs can make the required corrective swap exceed the fixed budget, so the pool is left only partially rebalanced. `_routerDepositAndDispose` then deposits the graduation's liquidity at that still-skewed ratio (`addLiquidity(..., 1, 1, ...)`, with no check that the post-swap ratio actually reached the curve-close target), permanently seeding the graduated LP away from the curve's true closing price.

### Finding Description
`_seedUniswapV2Direct` routes any pre-seeded pair (`totalSupply() > 0`) into `_seedRebalancing`: [1](#0-0) 

For a "mint pre-seed" (Regime 3), the pool is nudged toward the curve-close ratio with a single direct `pair.swap`, sized by `_noFeeSwapInput` and capped by `maxSwap`: [2](#0-1) 

The cap itself is derived only from the graduation's own inventory (`_ltSwapInventory(lt, protectedLT)` or the contract's own token balance), never from the size of the attacker's pre-seed: [3](#0-2) 

`tokensForLP` is bounded by the fixed `LP_RESERVE` constant and `ltFromPair` is bounded by the fixed `graduationThresholdUsd`/`VIRTUAL_LIQUIDITY_USD` economics set once at `initialize`: [4](#0-3) 

The required swap input to fully close an arbitrary ratio gap grows with the *size* of the pre-seed (`s = sqrt(reserveIn·reserveOut·targetN/targetD) − reserveIn`), while `maxSwap` is a fixed, small, protocol-constant-bounded number: [5](#0-4) 

Consequently an attacker who funds the pre-seed large enough (their own capital, no privilege required) makes `s` exceed `maxSwap`; the swap only partially corrects the ratio, and `_pairRebalance`/`_seedRebalancing` proceed to deposit at whatever ratio remains via `_routerDepositAndDispose`, with `addLiquidity(min0=1, min1=1)` and **no check that the resulting ratio matches the curve-close price**: [6](#0-5) 

The code's own natspec acknowledges the cap is a fixed fraction of a fixed inventory and only claims to prevent bricking — it does not claim (nor does the code enforce) that the final pool ratio converges on the curve-close price for pre-seeds sized beyond that budget: [7](#0-6) 

### Impact Explanation
This lets any unprivileged wallet — before `finalizeGraduation` is called on a `Lifecycle.Graduating` token — pre-create/pre-seed the HyperSwap V2 `TOKEN/LT` pair (via `Factory.createPair` + `pair.mint`) with a ratio and size deliberately chosen to exceed alt.fun's fixed correction budget. The permissionless `finalizeGraduation` (callable by anyone, including a keeper) then seeds the protocol's real curve-raised LT and 250M reserved tokens into that pool at a ratio that is *not* the curve's actual closing price — an explicit fund-freezing/mispricing impact called out in scope ("an LP seeded away from the curve close price"). Because the attacker's own pre-existing LP position benefits from the graduated pool opening away from fair value, they can immediately arbitrage the mispriced pool against the true curve-close price, extracting value at the expense of legitimate token holders and the protocol's own deposited LT/token liquidity, which is permanently locked via `LPLock.recordLock` and cannot be corrected afterward.

### Likelihood Explanation
Reachable by any unrelated wallet with capital, no special privileges, no governance/keys required — only a large enough LT/TOKEN pre-seed mint on the not-yet-existing (or freshly created) HyperSwap V2 pair, timed before `finalizeGraduation` runs (which is itself permissionless and can be delayed/front-run by the attacker calling `pair.mint` first). The needed pre-seed size is bounded only by the attacker's own capital and by the protocol's small, fixed `LP_RESERVE`/`graduationThresholdUsd`-derived budget, making this practically achievable for any token graduating with the protocol's default (fixed) parameters.

### Recommendation
Scale the corrective-swap budget to the actual pre-seed size (e.g., use the full donated/pre-seeded reserves, not just the graduation's own inventory) so the rebalance can always converge on the curve-close ratio, or explicitly verify post-swap that the deposit ratio is within an acceptable tolerance of `tokensForLP/ltFromPair` before calling `addLiquidity`, reverting/queuing (rather than silently depositing) when the pre-seed cannot be fully neutralized within budget.

### Proof of Concept
1. Token `T` is trading on `Bonding`'s curve and is about to graduate (`canGraduate(T) == true`), so `tokensForLP`/`ltFromPair` will be pinned at some small, fixed-magnitude values once `_enterGraduating` runs.
2. Before `finalizeGraduation(T)` is mined, attacker calls `Factory(uniswapV2Factory).createPair(T, lt)` (or it doesn't exist yet, so `_ensureUniswapV2Pair` will just adopt whatever pair exists) and self-funds a mint into the pair with a large, deliberately hostile `(T, lt)` ratio, sized well beyond `LP_RESERVE`/`graduationThresholdUsd` in absolute magnitude — i.e., large enough that `_noFeeSwapInput`'s required `s` exceeds `_swapBudget(graduation inventory)`.
3. Anyone calls `finalizeGraduation(T)`. `_seedRebalancing` detects `totalSupply() > 0`, computes the corrective swap, but `_pairRebalance` clamps it at `maxSwap` (99% of the graduation's fixed inventory) — insufficient to reach the target ratio.
4. `_routerDepositAndDispose` deposits the remaining `remToken`/`remLT` via `addLiquidity(..., 1, 1, ...)` at the still-skewed post-swap ratio; `LPLock.recordLock` locks the resulting LP permanently.
5. The graduated pool now trades at the attacker's chosen (not curve-close) price; the attacker's own pre-existing LP share captures the mispricing, which they realize by trading against/withdrawing around the true price once public trading resumes.

    /// @dev Cap the rebalance swap at 99% of the available side's budget,
    ///      so the subsequent `addLiquidity` always has a non-zero amount
    ///      of BOTH sides to deposit. Without this, an extreme hostile
    ///      pre-seed (massively imbalanced reserves) drives the
    ///      unconstrained `_noFeeSwapInput` past our per-side budget,
    ///      `_pairRebalance` clamps to the full budget, and the swap
    ///      consumes 100% of one side. `_routerDepositAndDispose` then
    ///      skips `addLiquidity` (`remToken == 0` or `remLT == 0`),
    ///      `finalizeGraduation` returns `liquidity = 0`, and
    ///      `LPLock.recordLock(...)` records a zero-sized lock — the
    ///      attacker's pre-existing LP becomes 100% of the pool. Reserving
    ///      1% guarantees the deposit leg always lands AND mints non-zero
    ///      LP at the post-swap ratio. The 1% comes off the swap, not the
    ///      deposit — for any realistic pre-seed `s_unconstrained` is
    ///      orders of magnitude below `maxSwap`, so the cap doesn't bind
    ///      and behaviour is unchanged. It only kicks in for catastrophic
    ///      pre-seeds beyond our budget capacity, where the alternative
    ///      is bricking.
    function _swapBudget(
        uint256 budget
    ) internal pure returns (uint256) {
        return (budget * 99) / 100;
    }

    function _noFeeSwapInput(
        uint256 reserveIn,
        uint256 reserveOut,
        uint256 targetN,
        uint256 targetD,
        uint256 maxSwap
    ) internal pure returns (uint256) {
        if (reserveIn == 0 || reserveOut == 0 || targetN == 0 || targetD == 0 || maxSwap == 0) {
            return 0;
        }
        uint256 product = Math.mulDiv(reserveIn * reserveOut, targetN, targetD);
        uint256 newIn = Math.sqrt(product);
        if (newIn <= reserveIn) return 0;
        uint256 s = newIn - reserveIn;
        return s > maxSwap ? maxSwap : s;
    }
