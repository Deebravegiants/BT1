### Title
Webhook shop-domain identity is trusted from an unauthenticated header while the HMAC only binds the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, so the HMAC signature validated by `HmacValidator.validate` binds nothing but the payload bytes. The `shop`, `topic`, and `webhook_id` fields — which are read straight from HTTP headers and then dispatched to the app's handler as the tenant identity — are never covered by that signature.

### Finding Description
`ShopifyAPI::Webhooks::Request` exposes: [1](#0-0) 
`hmac` is derived from the `hmac-sha256` header, while `shop`, `topic`, and `webhook_id` are pulled from separate headers (`shop-domain`, `topic`, `webhook-id`). Crucially, `to_signable_string` returns only `@raw_body` — it does not fold in `shop`, `topic`, or `webhook_id`.

`Registry.process` then does: [2](#0-1) 
It validates `Utils::HmacValidator.validate(request)`, which only proves the raw body was signed by the app's `client_secret` — it says nothing about which shop the header claims to be from. The `request.shop` value, taken verbatim from the unauthenticated `x-shopify-shop-domain` header, is then handed to the app's webhook handler as the tenant identity (`WebhookMetadata.new(... shop: request.shop ...)`).

This is a textbook identity-binding gap: bytes verified (raw body under a single app-wide secret) ≠ bytes/fields acted upon (`shop`, `topic`, `webhook_id` headers). Because the HMAC secret (`client_secret`) is shared by the app across **all** shops that install it, any party capable of producing (or replaying) one valid `(raw_body, hmac)` pair for the app — e.g., a merchant who installed the app and can see/replay their own legitimate webhook deliveries — can resend that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` (and `x-shopify-topic`/`x-shopify-webhook-id`) header value naming a different, victim shop. `HmacValidator.validate` still returns `true` because it only checks the body, so `Registry.process` will happily dispatch the forged event to the handler tagged with the victim shop's domain.

### Impact Explanation
This breaks the equality that should hold: `shop claimed by header == shop cryptographically bound by the signature`. Since it does not hold, an attacker can impersonate arbitrary shops in the eyes of the app's webhook handler, causing the app to execute shop-scoped side effects (e.g., customer/order data mutation, GDPR redaction triggers, inventory updates) attributed to a tenant the attacker does not control — a cross-tenant confusion/spoofing condition using only the app's own (shared) HMAC secret side effect, no access token or credentials of the victim required.

### Likelihood Explanation
The prerequisite is modest: the attacker only needs to have received (or captured) one legitimate webhook delivery for *any* shop using the target app (e.g., by being a merchant/customer of that app themselves), since the same `client_secret` signs webhooks for every installed shop. From there, forging the shop-domain header on a replayed request is trivial (webhook receiving endpoints are typically plain HTTP(S) POST handlers with no additional shop allow-listing performed by this gem).

### Recommendation
Bind the shop (and ideally topic/webhook_id) into the value that is verified, not just trusted post hoc: either have `to_signable_string` fail fast unless the caller independently confirms `shop` against a known/registered shop for this app before invoking the handler, or maintain a registry of expected shop-domains-per-webhook and cross-check `request.shop` against that registry after HMAC success, rejecting mismatches. At minimum, document prominently that `request.shop` is unauthenticated header data and must not be trusted as a tenant boundary by itself.

### Proof of Concept
1. App "AwesomeApp" is installed on `shop-a.myshopify.com` and `shop-b.myshopify.com` (same `client_secret` for both, since Shopify signs all app webhooks with the app-level secret).
2. Attacker (the operator of `shop-a.myshopify.com`) receives a legitimate webhook delivery for their own shop:
   - Body: `{"id":123,"note":"hi"}`
   - Header `x-shopify-hmac-sha256: <valid-hmac-of-body>`
   - Header `x-shopify-shop-domain: shop-a.myshopify.com`
3. Attacker POSTs the exact same body and HMAC header to the app's webhook endpoint again, but changes the header to `x-shopify-shop-domain: shop-b.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)` [3](#0-2)  — this only recomputes the HMAC over `@raw_body` [4](#0-3)  and succeeds because the body is unchanged.
5. The handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` where `shop` is `shop-b.myshopify.com` [5](#0-4) , causing the app to process attacker-controlled data as an authentic event from `shop-b`, despite the attacker having no relationship to `shop-b`.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
