Confirmed: this gem's own documentation and code establish `ShopifyAPI::Webhooks::Registry.process` as "will verify the request did indeed come from Shopify" [1](#0-0) , and the `data.shop` field handed to app handlers is explicitly documented as authenticated shop identity [2](#0-1) . This is the gem's own guarantee, not host-app misuse, so it's in scope.

### Title
HMAC verification excludes shop-domain/topic headers, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while the shop identity (`shop-domain` header) and topic used by `Registry.process` to route/act on the webhook are read directly from unauthenticated HTTP headers and never included in the HMAC-signed material.

### Finding Description
`Registry.process` verifies a webhook solely via `Utils::HmacValidator.validate(request)` and then trusts `request.shop`/`request.topic` to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

The HMAC validator computes/verifies the signature only over `verifiable_query.to_signable_string`: [4](#0-3) 

And `Request#to_signable_string` returns just `@raw_body`, while `shop`, `topic`, `api_version`, and `webhook_id` are read from HTTP headers that are entirely outside the signed value: [5](#0-4) 

The identity binding broken is: `shop_used_by_handler (header, unauthenticated) != shop_covered_by_hmac (none, since HMAC only covers raw_body)`. Because the `X-Shopify-Shop-Domain` and `X-Shopify-Topic` headers are never part of the signable string, any party capable of relaying a byte-identical body with a valid HMAC (e.g., replaying a webhook body previously delivered to the same endpoint for shop A, which is the app developer's own webhook URL and thus reachable by any internet client per the documented pattern) can swap the `shop-domain`/`topic` headers while keeping the original valid HMAC unchanged, since the signature never depended on those headers.

### Impact Explanation
This breaks the identity binding between "shop whose data the HMAC was computed for" and "shop the handler is told the webhook came from" (`data.shop`), which the library's own documentation guarantees is the verified shop [2](#0-1) . Handlers built on this gem's contract (topic/shop are trusted because `process` "will verify the request did indeed come from Shopify") will act on attacker-chosen shop/topic values, enabling cross-tenant confusion in downstream processing (e.g., a handler that revokes/updates data keyed by `data.shop`, or dispatches per-topic side effects keyed by `data.topic`, can be triggered for a shop/topic the attacker chooses while reusing a validly-HMAC'd body).

### Likelihood Explanation
Low-to-moderate: exploitation requires the attacker to possess at least one legitimately-HMAC'd raw body (e.g., from a previously observed/delivered webhook to the app's public endpoint) and resend it with modified `shop-domain`/`topic` headers to the same public endpoint; no secret material is required since the signature check never covers those headers.

### Recommendation
Include `shop`, `topic`, `api_version`, and `webhook_id` in the signable string verified by `Utils::HmacValidator`, or otherwise cryptographically bind these header-derived fields to the HMAC before trusting them in `WebhookMetadata`, e.g.:

```ruby
sig { override.returns(String) }
def to_signable_string
  "#{shop}|#{topic}|#{webhook_id}|#{@raw_body}"
end
```

### Proof of Concept
1. App's webhook endpoint receives a legitimate webhook for `shop-a.myshopify.com`, topic `orders/create`, with a valid `X-Shopify-Hmac-Sha256` computed over the JSON body.
2. Attacker (or any actor able to POST to the app's public webhook URL, e.g. by replaying the intercepted/cached request) resends the identical raw body but sets `X-Shopify-Shop-Domain: shop-b.myshopify.com` and/or `X-Shopify-Topic: shop/redact`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` parses these headers, and `Utils::HmacValidator.validate(request)` succeeds because it only recomputes the HMAC over `@raw_body`, which is unchanged.
4. `Registry.process` invokes the registered handler for the (attacker-modified) topic with `WebhookMetadata.new(topic: "shop/redact", shop: "shop-b.myshopify.com", body: ..., ...)`, causing the handler to act on the wrong shop/topic despite HMAC validation "succeeding." [6](#0-5)

```ruby
        sig { params(request: Request).void }
        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
```
