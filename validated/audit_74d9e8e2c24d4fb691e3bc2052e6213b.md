### Title
Permanent market freeze when accrued RAY value overflows before the index cap - (File: common/src/rates/simulate.rs)

### Summary
A sufficiently large market can reach a state where every subsequent interest-accrual attempt panics because `borrowed * borrow_index` exceeds the `i128` RAY-value domain before `borrow_index` reaches `MAX_BORROW_INDEX_RAY`. [1](#0-0) [2](#0-1) 

### Finding Description
`accrue_step` calculates `borrowed_original` and `supplied_original` through `scaled_to_original`, which is a non-widening `Ray::mul`. [3](#0-2) [2](#0-1)  The borrow index is capped only after that value calculation, so a large `borrowed` balance can overflow `scaled_to_original` before `update_borrow_index` can clamp the index. [4](#0-3)  `global_sync` runs this calculation for every market accrual, including the permissionless `update_indexes` path. [5](#0-4) [6](#0-5)  The controller exposes that path through `update_indexes(caller, assets)` after only caller authorization. [7](#0-6) [8](#0-7) 

### Impact Explanation
Once the product overflows, any operation that must accrue the affected market reverts before repayment or withdrawal state can be updated. [9](#0-8) [10](#0-9)  The repository’s own regression test demonstrates `MATH_OVERFLOW`, then shows both withdrawal and repayment failing with the same error. [11](#0-10)  This permanently freezes supplier funds and prevents borrowers or liquidators from reducing debt in the affected market, satisfying permanent freezing of funds and contract-operation failure for that market. [12](#0-11) 

### Likelihood Explanation
The attack requires an extremely large market, sustained high utilization, and enough elapsed time for index growth to make `borrowed * borrow_index` exceed the `i128` RAY domain. [13](#0-12)  An unprivileged participant can establish the required position through ordinary `supply`, `borrow`, and later `update_indexes` calls when the deployed spoke caps and available liquidity admit those amounts. [14](#0-13) [15](#0-14)  The substantial capital and elapsed-time requirements reduce likelihood, but the result is deterministic once the market enters the overflowing state. [11](#0-10) 

### Recommendation
Accrue with a widened intermediate such as `I256` and explicitly classify overflow before committing an index update. [16](#0-15)  Enforce market and spoke caps against the maximum future `shares * index` product, not only against the admitted token-unit cap, so a reachable index cannot overflow the stored scaled totals. [17](#0-16) [18](#0-17)  Alternatively, clamp the borrow index before value calculations when continued accrual would exceed the representable market value, ensuring repayment and withdrawal remain executable. [19](#0-18) 

### Proof of Concept
The existing test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` reproduces the state transition. [20](#0-19)  It supplies `BILLION * 10^18` units of an 18-decimal asset, borrows 98% of it, repeatedly advances one-year intervals, and invokes `update_indexes` until accrual returns `MATH_OVERFLOW`. [21](#0-20)  The test confirms the failure occurs while `borrow_index` remains below `MAX_BORROW_INDEX_RAY`, then demonstrates that both `withdraw` and `repay` fail with the same overflow. [22](#0-21)

/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);

**File:** docs/reference/formulas.md (L407-417)
```markdown
A cap is in native token units. Entry compares stored scaled usage plus the
new scaled amount with the cap floor-converted at the current index. Zero cap
allows no positive exposure. Exits subtract usage without checking caps;
missing usage rows and zero exit deltas are no-ops. Cap→scaled conversion
saturates at `i128::MAX` (`calculate_scaled_cap`), so the entry check fails
open instead of trapping. A saturated scaled cap does not enforce the
configured asset-unit limit. An admitted cap saturates only at an index below
one RAY. Only a bad-debt write-down moves the supply index below one RAY; at
its floor (`RAY / 1000`), a supply cap above 1/1000 of the admitted maximum
saturates. The borrow index never falls below one RAY, so an admitted borrow
cap cannot saturate. Position conversion still rejects overflow.
```
