## Title
Unchecked-length signature copy in BEEFY `Vote` → `SignatureWithAuthorityIndex` conversion can panic on malformed proof data - (File: `evm/rust/src/conversions.rs`)

### Summary
CVE-2021-30184 is a buffer-overflow class bug caused by GNU Chess writing attacker-controlled, insufficiently length-validated data into a fixed-size buffer. The closest reachable analog in Hyperbridge is an unchecked `copy_from_slice` from a variable-length, attacker/relayer-supplied byte buffer into a fixed-size `[u8; 65]` array while converting a BEEFY `Vote` into a `SignatureWithAuthorityIndex`.

### Finding Description
`impl From<Vote> for SignatureWithAuthorityIndex` takes the Solidity-side `Vote.signature` field — a dynamic `bytes` value with no length guarantee — and copies it directly into a fixed 65-byte array without first checking its length: [1](#0-0) 

```rust
impl From<Vote> for SignatureWithAuthorityIndex {
	fn from(value: Vote) -> Self {
		let sig_bytes = value.signature.to_vec();
		let mut signature: TSignature = [0u8; 65];
		signature.copy_from_slice(&sig_bytes);
		...
```

`Vote.signature` is declared as an arbitrary-length `bytes` field in the Solidity struct definition, not a fixed `bytes65`: [2](#0-1) 

Elsewhere in the same codebase, every comparable signature-copy site explicitly guards the length before calling `copy_from_slice`, and one such fix is documented in a regression test as closing exactly this bug class ("a wasm trap reachable from untrusted input"): [3](#0-2) [4](#0-3) [5](#0-4) 

The `From<Vote>` implementation in `evm/rust/src/conversions.rs` is the one place in the surveyed BEEFY signature-handling code that omits this check: if `value.signature` is not exactly 65 bytes (e.g., 0 bytes, 64 bytes, or 66+ bytes), `Vec<u8>::copy_from_slice` panics with a length-mismatch error.

### Impact Explanation
In Rust, an out-of-bounds/length-mismatched `copy_from_slice` is a checked panic (process abort/wasm trap), not a memory-corruption write as in the original C-based CVE. If this conversion path executes inside a node's runtime or relayer process on data derived from an externally-supplied BEEFY proof (a `RelayChainProof`/`Vote` set relayed from an EVM host to a Substrate consensus client, or vice versa), a malformed `signature` length would crash that process — a liveness/availability impact on the consensus-verification path rather than confirmed fund loss.

### Likelihood Explanation
I could not fully confirm, within the available tool budget, whether `From<Vote> for SignatureWithAuthorityIndex` is invoked on a path that consumes untrusted, externally-supplied proof bytes (e.g., a relayer/light-client verification flow processing a submitted consensus message) versus only being used to re-encode locally-generated, already-validated signatures produced by the prover itself (`impl From<MmrProof> for RelayChainProof`, which goes the opposite direction — Substrate → EVM `Vote`, using signatures already fixed at `[u8; 65]`). The directionality of the conversions in this file suggests `From<Vote>` exists specifically to decode EVM-sourced `Vote` values back into Substrate types, which would imply it is reachable from proof data that did not originate as a validated Rust `[u8;65]` signature. However, without tracing the concrete call site that invokes `SignatureWithAuthorityIndex::from(vote)`, I cannot confirm with certainty that this is reachable from a single unprivileged relayed proof versus only from prover-internal, self-generated data (which the scope rules require excluding as "prover-only").

### Recommendation
Add an explicit length check before the `copy_from_slice` in `From<Vote> for SignatureWithAuthorityIndex`, mirroring the pattern already used in `modules/consensus/beefy/prover/src/lib.rs` and `modules/utils/crypto/src/verification.rs`:
```rust
if sig_bytes.len() != 65 {
    // return an error / skip instead of panicking
}
```
and propagate a `TryFrom`-style fallible conversion instead of an infallible `From` if this type is ever constructed from untrusted-length data.

### Proof of Concept
Not independently verified against a live call site due to remaining uncertainty about invocation context (see Likelihood Explanation). Conceptually: supply a `Vote { signature: bytes of length != 65, authorityIndex }` to whatever code path calls `SignatureWithAuthorityIndex::from(vote)`; the `copy_from_slice` panics/traps.
