## Finding: DoS in permissionless crowdloan refund loop via a single failing transfer

### Title
Single failing transfer in `Pallet::refund` aborts the whole batch and can permanently block refunds to unrelated contributors - (File: `polkadot/runtime/common/src/crowdloan/mod.rs`)

### Summary
The Sherlock report describes a pattern where a *direct, unwrapped token transfer to an untrusted recipient inside a shared code path* can revert and block funds recovery for everyone, because the transfer's success is not decoupled from the rest of the operation. The closest analog in this codebase is `pallet-crowdloan`'s permissionless `refund` extrinsic, which loops over many contributors and performs a direct `Currency::transfer` to each of them using the `?` operator, so a single failing transfer aborts the entire dispatchable (rolling back all transfers already performed within that call).

### Finding Description
`refund` iterates over contributions stored in the crowdloan child-trie and, for each contributor, executes: [1](#0-0) 

```
let mut refund_count = 0u32;
let contributions = Self::contribution_iterator(fund.fund_index);
let mut all_refunded = true;
for (who, (balance, _)) in contributions {
    if refund_count >= T::RemoveKeysLimit::get() {
        all_refunded = false;
        break;
    }
    CurrencyOf::<T>::transfer(&fund_account, &who, balance, AllowDeath)?;
    CurrencyOf::<T>::reactivate(balance);
    Self::contribution_kill(fund.fund_index, &who);
    fund.raised = fund.raised.saturating_sub(balance);
    refund_count += 1;
}
``` [2](#0-1) 

The `?` after `CurrencyOf::<T>::transfer(...)` propagates any transfer failure directly out of the dispatchable. Since FRAME extrinsics are all-or-nothing (a failing dispatchable rolls back every storage/balance mutation performed during its execution), if the transfer to *any single contributor* in the batch fails, the entire `refund` call fails and reverts — including the refunds to every other contributor already processed earlier in the same loop iteration. The `refund` call is permissionless (`ensure_signed(origin)?` only) and re-callable by anyone, but because it always begins iterating from the same child-trie ordering, a permanently-failing entry at (or before) the point where the transfer keeps failing will cause the extrinsic to fail at the exact same contributor every time it is called, blocking refunds to all subsequent contributors in the iteration order indefinitely.

This mirrors the reported bug's root cause: a single, uncontrollable, per-recipient transfer failure embedded inside a shared/looped operation blocks legitimate operations (repayment/refund) for everyone else sharing that code path, with no escrow/skip/try-catch fallback.

Contrast this with pallets in this same codebase that were clearly hardened against exactly this class of bug: `pallet-nomination-pools` migration code catches the transfer error and logs a warning without aborting the loop [3](#0-2) , and `pallet-staking`/`pallet-staking-async` payout logic treats a failed/absent payout as "skip this staker, continue with the rest" rather than propagating a hard error [4](#0-3) [5](#0-4) . The crowdloan `refund` loop does not follow this pattern.

### Impact Explanation
If a transfer to one contributor in the refund iteration fails (e.g., the contributor's account was later reaped/killed for reasons unrelated to the crowdloan, and the stored contribution amount is below the runtime's `ExistentialDeposit`, causing the `AllowDeath` transfer's implicit account-creation check to fail), all subsequent contributors in the same and future `refund` calls are blocked from being refunded, since the loop always resumes at the same failing entry. This can permanently strand crowdloan funds that should have been returned to contributors, with no built-in escrow/skip mechanism, unlike the fixed `LiquidityManager.sol`.

### Likelihood Explanation
I could not fully verify, within the available tool budget, whether `pallet-crowdloan`'s `contribute` path enforces a `MinContribution` at or above the runtime `ExistentialDeposit`, which is the key precondition needed to trigger the failure deterministically (I located the `contribute`/`contribute_all` call sites but ran out of iterations before reading `do_contribute`'s validation logic). If `MinContribution >= ExistentialDeposit` in all deployed runtimes, the described trigger via dust contribution amounts would not be reachable, significantly lowering likelihood. Additionally, the on-chain `pallet-crowdloan` (relay-chain auction crowdloans) is a legacy/mostly-inactive mechanism now that parachain auctions have ended; most outstanding crowdloan refunds are instead handled by `cumulus/pallets/ah-ops`'s `withdraw_crowdloan_contribution`, which is a **per-user** call (not a shared loop) and therefore does not exhibit this "block everyone else" characteristic [6](#0-5) .

### Recommendation
In `Pallet::refund`, do not use `?` to propagate a single contributor's transfer failure out of the loop. Instead, catch the transfer error (e.g., via `let _ = CurrencyOf::<T>::transfer(...).map_err(...)` and skip/log), continue processing the remaining contributors, and leave the failed contributor's entry in the child-trie for later manual/governance recovery — mirroring the pattern already used in `pallet-nomination-pools`'s migration code and `pallet-staking`'s payout logic.

### Proof of Concept
Not fully constructible without confirming the `MinContribution` vs `ExistentialDeposit` relationship in `do_contribute` (unverified due to tool-call budget). Conceptually: (1) a contributor's account is later reaped to zero balance/killed by unrelated activity while retaining a small crowdloan contribution below `ExistentialDeposit`; (2) crowdloan ends and `refund` is called; (3) the loop reaches this contributor and `CurrencyOf::transfer(..., AllowDeath)` fails because it would create a new account with a sub-ED balance; (4) the whole `refund` extrinsic reverts, including refunds already applied to earlier contributors in the same call, and repeated calls fail identically, permanently blocking refunds for that fund's remaining contributors.

		/// Automatically refund contributors of an ended crowdloan.
		/// Due to weight restrictions, this function may need to be called multiple
		/// times to fully refund all users. We will refund `RemoveKeysLimit` users at a time.
		///
		/// Origin must be signed, but can come from anyone.
		#[pallet::call_index(3)]
		#[pallet::weight(T::WeightInfo::refund(T::RemoveKeysLimit::get()))]
		pub fn refund(
			origin: OriginFor<T>,
			#[pallet::compact] index: ParaId,
		) -> DispatchResultWithPostInfo {
			ensure_signed(origin)?;

			let mut fund = Funds::<T>::get(index).ok_or(Error::<T>::InvalidParaId)?;
			let now = frame_system::Pallet::<T>::block_number();
			let fund_account = Self::fund_account_id(fund.fund_index);
			Self::ensure_crowdloan_ended(now, &fund_account, &fund)?;

			let mut refund_count = 0u32;
			// Try killing the crowdloan child trie
			let contributions = Self::contribution_iterator(fund.fund_index);
			// Assume everyone will be refunded.
			let mut all_refunded = true;
			for (who, (balance, _)) in contributions {
				if refund_count >= T::RemoveKeysLimit::get() {
					// Not everyone was able to be refunded this time around.
					all_refunded = false;
					break;
				}
				CurrencyOf::<T>::transfer(&fund_account, &who, balance, AllowDeath)?;
				CurrencyOf::<T>::reactivate(balance);
				Self::contribution_kill(fund.fund_index, &who);
				fund.raised = fund.raised.saturating_sub(balance);
				refund_count += 1;
			}

			// Save the changes.
			Funds::<T>::insert(index, &fund);

			if all_refunded {
				Self::deposit_event(Event::<T>::AllRefunded { para_id: index });
				// Refund for unused refund count.
				Ok(Some(T::WeightInfo::refund(refund_count)).into())
			} else {
				Self::deposit_event(Event::<T>::PartiallyRefunded { para_id: index });
				// No weight to refund since we did not finish the loop.
				Ok(().into())
			}
		}
