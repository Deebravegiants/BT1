### Title
`TokenExchange.exchange_token` sends the app's `client_secret` to an unvalidated host derived from the JWT `dest` claim - ([File: lib/shopify_api/auth/token_exchange.rb])

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` builds the shop host used to receive the app's `client_secret` directly from the JWT payload's `dest` claim, with no domain-format validation. This is inconsistent with the sibling method `migrate_to_expiring_token` in the same module, which explicitly validates the shop via `Utils::ShopValidator.sanitize!` before using it to build the request host.

### Finding Description
`exchange_token` decodes the caller-supplied session token with `ShopifyAPI::Auth::JwtPayload.new(session_token)` and takes `dest_shop = jwt_payload.shop`. [1](#0-0) 

`JwtPayload#shop` performs no validation beyond stripping a literal `"https://"` prefix from the `dest` claim - it does not check that the resulting string is a `*.myshopify.com` domain or matches any Shopify-owned host pattern: [2](#0-1)  The JWT's own signature/claim validation only checks `aud == Context.api_key` (the app identity), never the `dest` value's format: [3](#0-2) 

`exchange_token` then constructs a `Session` from this unvalidated `dest_shop` and passes it straight into `Clients::HttpClient`, together with a body containing `client_secret: ShopifyAPI::Context.api_secret_key`: [4](#0-3) 

`HttpClient#initialize` uses `session.shop` verbatim to build the destination URI (`@base_uri = "https://#{api_host || session.shop}"`), with no allow-list or regex check on the host: [5](#0-4) 

This is the asymmetry that breaks the intended binding "host that receives the `client_secret`" == "a validated Shopify shop host": the sibling method `migrate_to_expiring_token`, which follows the exact same code shape (build session, POST body containing `client_secret` to `/admin/oauth/access_token`), explicitly calls `Utils::ShopValidator.sanitize!(shop)` first and raises `InvalidShopError` for non-Shopify domains before using the value as the request host: [6](#0-5)  `exchange_token` has no equivalent call.

### Impact Explanation
If a caller can influence or obtain a validly-signed session token whose `dest` claim is not constrained to `*.myshopify.com` (e.g. `dest` value inherited from an unusual/legacy or malformed session-token-issuing context, or an app that stores/relays session tokens from less-trusted sources before calling `exchange_token`), the gem will POST the app's `client_secret` to whatever host is embedded in `dest`, without any host validation - unlike the parallel `migrate_to_expiring_token` path which enforces `ShopValidator.sanitize!`. This is a credential-leakage-into-network-request (SSRF-with-credentials-style) risk carrying the app's `client_secret`, matching the High severity impact class (SSRF with the app's credentials / credential leakage) once any path exists for `dest` to diverge from a genuine Shopify domain. Because JWT signature validation only confirms the token was signed with the app's shared secret and matches `aud`, and never independently confirms the `dest` claim is a legitimate Shopify domain, the trust boundary "signed session token" is not equivalent to "safe destination host" - the gem asserts this equivalence implicitly by skipping the sanitize step that its own codebase applies elsewhere for the same kind of request.

### Likelihood Explanation
Exploitability is contingent on how host applications obtain and pass `session_token` into `exchange_token` (this gem does not itself accept arbitrary network input directly into `dest`), and I could not fully verify within available context whether Shopify's session-token issuance guarantees `dest` is always constrained to `*.myshopify.com`-style hosts in every supported deployment mode (e.g. checkout UI extensions and spin/dev domains are explicitly supported and less constrained, as shown in `jwt_payload_test.rb`'s `test_decode_jwt_payload_succeeds_with_spin_domain`). Given the explicit, deliberate `ShopValidator.sanitize!` guard added in `migrate_to_expiring_token` for the identical `client_secret`-POST pattern, its absence in `exchange_token` is a genuine internal inconsistency in this gem's own code, not merely a host-application misuse issue.

### Recommendation
Add the same `Utils::ShopValidator.sanitize!(dest_shop)` (or equivalent strict domain validation) call in `exchange_token` immediately after computing `dest_shop = jwt_payload.shop`, before constructing `shop_session` and issuing the HTTP request that carries `client_secret`, mirroring the guard already present in `migrate_to_expiring_token`.

### Proof of Concept
Not independently reproducible from the indexed context alone: reproducing this requires constructing (or obtaining) a session token whose `dest` claim resolves to a non-`myshopify.com` host while still passing `JwtPayload`'s `aud`/signature checks, then observing that `TokenExchange.exchange_token` issues its `client_secret`-bearing POST to that host without any `ShopValidator.sanitize!`-style rejection - in contrast to calling `TokenExchange.migrate_to_expiring_token(shop: "attacker.example", ...)`, which is shown in the existing test suite to raise `ShopifyAPI::Errors::InvalidShopError` for exactly this kind of non-Shopify host.
