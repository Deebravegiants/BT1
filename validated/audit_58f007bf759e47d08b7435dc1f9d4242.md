### Title
`borrow`/`withdraw` accept arbitrary contract recipients, permanently stranding funds sent to tokenless protocol contracts - ([File: contracts/controller/src/positions/mod.rs])

### Summary
`Controller::borrow` and `Controller::withdraw` take a `to: Option<Address>` payout destination. The only recipient validation is `require_external_recipient`, which rejects exactly two addresses — the pool and the controller itself — with `FlashLoanError::InvalidFlashloanReceiver` [1](#0-0) . Any other contract address is accepted. Protocol contracts like the position NFT (`contracts/position-nft`), governance, and the price aggregator expose no entrypoint that moves arbitrary held tokens out, so a borrow or withdrawal paying one of them strands the funds permanently while the debt position or collateral burn is already recorded.

### Finding Description
Both flows resolve `recipient = to.unwrap_or(caller)` and pass `require_external_recipient` before settlement:

- `process_borrow` resolves `to` and calls `require_external_recipient`, then `settle_borrow` pushes real tokens from the pool to `recipient` and merges the debt [2](#0-1) .
- `process_withdraw` does the same for collateral, paying `recipient` inside `settle_withdraw` [3](#0-2) .
- The guard itself only compares against `env.current_contract_address()` and `cached_pool_address()` [1](#0-0) .

The pool and controller were blocked because "the pool debits cash without moving tokens" and "controller receipts would remain unclaimed" — the exact same stranding applies to every other tokenless contract in the system. The position NFT contract's interface contains only NFT/account-management methods (`mint`, `burn`, `transfer`, `approve`, `renew`, `upgrade`); nothing sweeps an arbitrary SEP-41 token balance [4](#0-3) . Neither governance nor the price aggregator exposes a user-reachable token withdrawal. Unlike the original ECO finding, contract *callers* are a deliberate, supported design here (direct invoker auth satisfies `caller.require_auth()`, and integrations are documented to pass `current_contract_address()` as `caller`) [5](#0-4)  — the unguarded piece is the *recipient* parameter, which is precisely the "`to` is a contract" half of the reported bug class.

### Impact Explanation
Permanent freezing of funds. An owner or delegate calling `borrow(account_id, legs, Some(position_nft_addr))` records the full debt on the account while the borrowed tokens sit inside a contract with no function to release them; likewise `withdraw` burns the collateral position and pays the NFT contract. The account holder still owes the debt (or has lost the collateral share) and can never recover the tokens — identical impact to tokens locked in `L1ECOBridge` by a contract deposit, but reachable through a documented parameter rather than an accidental `msg.sender`.

### Likelihood Explanation
Low-to-moderate: it requires an authorized caller to pass a protocol contract address as `to`, i.e., caller error. However, no attacker privilege is needed, the path is fully on-chain, integrator contracts routinely construct `to` programmatically, and the code itself acknowledges this failure mode by rejecting two of the contracts — the list is simply incomplete.

### Recommendation
Reject all protocol-owned contract addresses, not just pool and controller. Maintain a registry-style check (e.g., compare `to` against pool, controller, position NFT, governance, and price aggregator addresses stored in `Context`/storage), or invert the policy: allow `to` only when it is `caller`/the account owner, since paying a third party at all is an authorized transfer of account value. At minimum, extend `require_external_recipient` to cover the position NFT and governance contracts.

### Proof of Concept
1. Alice supplies USDC collateral on `account_id = A`.
2. Alice (or her delegate) calls `borrow(caller=alice, account_id=A, borrows=[(hub_asset, 1000e7)], to=Some(POSITION_NFT_ADDRESS))`.
3. `require_external_recipient` passes — the NFT contract is neither the pool nor the controller [1](#0-0) .
4. `pool_borrow_call` transfers 1000 tokens to the NFT contract; the debt position is recorded on `A` [6](#0-5) .
5. No entrypoint on `position-nft` can move the token balance; the 1000 tokens are permanently locked while `A`'s debt remains fully enforceable and liquidatable.

(The same shape applies via `withdraw(..., to=Some(NFT_ADDR))`, which burns the supply position and strands the payout.)

pub(crate) fn require_external_recipient(env: &Env, cache: &mut Context, recipient: &Address) {
    let pool = cache.cached_pool_address();
    assert_with_error!(
        env,
        *recipient != env.current_contract_address() && *recipient != pool,
        FlashLoanError::InvalidFlashloanReceiver
    );
}
