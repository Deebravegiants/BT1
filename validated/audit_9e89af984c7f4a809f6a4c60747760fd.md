Based on the source line hint (`Cooler.sol#L123`'s core issue: an ERC-20 transfer that can silently fail while the surrounding state assumes it succeeded, permanently locking the user's underlying asset), the closest reachable analog in this codebase is in the **Tron-flavored `IntentGatewayV2`**'s escrow release path, which — unlike its EVM sibling — uses raw low-level calls with `IERC20.transfer.selector` and only checks that the call didn't revert, never decoding the returned boolean.

### Title
Escrowed-token release in Tron `IntentGatewayV2.withdraw` does not verify the ERC-20 return value, permanently freezing user/solver funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`withdraw()` in the Tron variant of `IntentGatewayV2` releases escrowed tokens to a beneficiary using a raw `.call` with the `transfer` selector, checking only that the low-level call itself did not revert (`success`), never decoding/asserting the ERC-20 return data. It then unconditionally decrements the escrow accounting and (on finalize) marks the order filled, regardless of whether the token actually moved.

### Finding Description
`withdraw()` is invoked from `onAccept()` for `RedeemEscrow`/`RefundEscrow` messages and from `onGetResponse()` for cancellation refunds — both reachable purely by relayed ISMP messages/proofs, i.e. by an unprivileged relayer delivering a message dispatched by the counterpart `IntentGateway` on another chain. [1](#0-0) 

For every ERC-20 token in the withdrawal, it does:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
_orders[body.commitment][token] -= amount;
```
This only reverts if the external call itself reverts. Many ERC-20-like tokens (particularly common on Tron/TRC-20, and by spec for any non-reverting ERC-20 that returns `false` on failure) return `false` instead of reverting when a transfer cannot be completed (e.g., paused token, blacklisted recipient, transfer-amount edge cases). In that case `success` is `true` (the call didn't revert) but no tokens were actually transferred, yet the code proceeds to decrement `_orders[...]`, set `_filled[commitment] = beneficiary`, and emit `EscrowReleased`/`EscrowRefunded`.

This is in contrast to the canonical EVM `IntentGatewayV2`/`IntentsBase._withdraw`, which uses `SafeERC20.safeTransfer`, correctly reverting on a `false` return. [2](#0-1) 

Once `_orders[body.commitment][token]` is decremented to zero and `_filled[commitment]` is set, there is no remaining code path to re-attempt delivery of that escrow to the rightful beneficiary — the tokens remain trapped in the `IntentGatewayV2` contract, unbacked by any accounting entry, unrecoverable by the user or solver who was supposed to receive them.

### Impact Explanation
This is a permanent freezing-of-funds bug: the user's (or solver's) escrowed input tokens become permanently stuck in the contract once escrow state is finalized without the underlying transfer succeeding — exactly analogous to the referenced report where a borrower could not retrieve their collateral due to improper handling of the token transfer call. Any token used with the Tron `IntentGatewayV2` that returns `false` on a failed transfer (rather than reverting) exposes every user of that gateway to unrecoverable loss of escrowed principal.

### Likelihood Explanation
Triggering this only requires a relayer to deliver a legitimate `RedeemEscrow`/`RefundEscrow` ISMP message (or GET response for cancellation) for an order whose token momentarily cannot complete the transfer (paused, blacklist, TRC-20 quirks, or any non-reverting-false-return token) — no privileged role or malicious actor is needed; a normal delivery under normal conditions with such a token variant is enough.

### Recommendation
Use `SafeERC20.safeTransfer` (as already done in `evm/src/apps/intentsv2/IntentsBase.sol`) instead of a raw `.call` + `success`-only check in `evm/tron/contracts/apps/IntentGatewayV2.sol`'s `withdraw()` and `onAccept()`'s `SweepDust` handling, so a `false` return value causes a revert rather than silently finalizing escrow accounting against a transfer that never happened.

### Proof of Concept
1. Configure an order whose input/output token is a TRC-20/ERC-20 implementation that returns `false` (instead of reverting) when a `transfer` call cannot be completed (e.g., temporarily paused or blacklisted recipient).
2. Complete the normal cross-chain fill flow so a `RedeemEscrow`/`RefundEscrow` message targets this `IntentGatewayV2` instance.
3. Have a relayer deliver the message via `onAccept()` at a moment the token's `transfer` call returns `false` for the beneficiary (e.g., beneficiary momentarily blacklisted/paused).
4. `withdraw()` treats the low-level call as successful (`success == true`), decrements `_orders[commitment][token]`, marks `_filled[commitment]`, and emits `EscrowReleased`/`EscrowRefunded` — even though the beneficiary's balance never changed.
5. The beneficiary's tokens are now permanently stuck in the `IntentGatewayV2` contract with no remaining escrow accounting entry to redeem them.
