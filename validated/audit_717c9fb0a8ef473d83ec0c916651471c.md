### Title
Webhook shop-tenant identity (`shop-domain` header) is not covered by the HMAC signature, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so `ShopifyAPI::Utils::HmacValidator.validate` cryptographically authenticates the body bytes only. The `shop` value that `ShopifyAPI::Webhooks::Registry.process` extracts and passes on to the app's handler as the tenant identifier comes exclusively from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, which is never included in the signed payload. An attacker who possesses one valid `(raw_body, hmac)` pair — trivially obtainable by installing the app on their own store and receiving one legitimate webhook — can replay that exact body/HMAC pair to the app's public webhook endpoint while substituting an arbitrary victim shop domain in the header, and the signature will still validate.

### Finding Description
The relevant binding that should hold is:

`shop_used_for_tenant_dispatch == shop_cryptographically_bound_by_signature`

In this gem that equality is broken:
- `Request#to_signable_string` returns `@raw_body` only [1](#0-0) 
- `Request#shop` reads the tenant identity purely from the unauthenticated `shopify-shop-domain` header [2](#0-1) 
- `HmacValidator.validate` signs/verifies `to_signable_string`, i.e., the body only [3](#0-2) 
- `Registry.process` validates the HMAC and then forwards `request.shop` (the header-derived value) straight to the app handler as the authoritative tenant for the event, with no additional cross-check between the header and any signed content [4](#0-3) 

Because the header is outside the HMAC's signed scope, any party holding a single genuine `(body, hmac)` pair for the app's `client_secret` can freely re-target that payload at a different shop identity by only changing the header value, and the gem will report it to the host application as if it originated from that other shop.

### Impact Explanation
This is a cross-tenant data-confusion vector: the host application relies on `WebhookMetadata#shop` from `Registry.process` to select which merchant's records to update/act on. An unprivileged attacker who has run the app against any shop they control (e.g., a free development store) can harvest one valid body/HMAC pair and then submit that same pair against the shared webhook endpoint while claiming an arbitrary victim shop domain, injecting attacker-controlled webhook data (whatever body they generated) attributed to a shop they do not own/administer. Depending on how the host app trusts `data.shop`, this enables cross-tenant state corruption/injection using the app's own trusted webhook channel — matching the "cross-tenant access" Critical-impact category, since it breaks the shop-identity binding entirely.

### Likelihood Explanation
Medium-to-High: no privileged credentials, tokens, or TLS interception are required. The attacker only needs to be able to install the target app on any shop they control (often free/self-serve) to legitimately receive one valid webhook, and the webhook receiver endpoint is intentionally public/unauthenticated (protected only by this HMAC check) per the gem's documented usage. Replaying with a substituted header requires nothing beyond basic HTTP tooling.

### Recommendation
Bind the shop identity into the signed material, or otherwise cryptographically tie the `shop-domain` header to the request, e.g., include the header value in `to_signable_string` (mirroring how `AuthQuery#to_signable_string` explicitly enumerates every field, including `shop`, that must be covered) so `HmacValidator.validate` fails whenever the header is altered independently of the body:

```ruby
sig { override.returns(String) }
def to_signable_string
  "#{shop}\n#{@raw_body}"
end
```
(with the corresponding compute-time signature also incorporating the shop domain), or reject the request if the header-provided shop cannot otherwise be corroborated.

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com` and receives a real webhook: headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid-hmac-of-body>`, plus `raw_body`.
2. Attacker POSTs the identical `raw_body` and `x-shopify-hmac-sha256` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `raw_body` against the HMAC — this still passes [5](#0-4) .
4. The handler is invoked with `WebhookMetadata.new(... shop: "victim.myshopify.com" ...)`, and the host app processes attacker-controlled data as though it were an authentic event from `victim.myshopify.com` [6](#0-5) .
