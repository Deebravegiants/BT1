## Title
Unsigned `handle_unsigned` lets any relayer submit cheap consensus updates that evict pending state commitments from `BoundedStateCommitments`, causing legitimate proof-based message delivery to permanently fail - (File: `modules/pallets/ismp/src/lib.rs`)

### Summary
`insert_bounded_state_commitment` retains only `state_machine_commitment_cap(id)` (default `MAX_STATE_MACHINE_COMMITMENTS = 10_240`) heights per state machine in a FIFO queue, evicting the oldest entries once the cap is exceeded. [1](#0-0)  `handle_unsigned` is a permissionless, unsigned extrinsic that anyone can call with a batch of consensus/state-machine-update messages, and each accepted state-machine update inserts a new height via this function. [2](#0-1)  This mirrors the reported bug class: a hard capacity limit on a per-key collection (there: `TOKEN_ADDRESS_LIMIT` on funded token addresses; here: `StateMachineCommitmentCap` on retained heights) can be filled up by an unprivileged, low-cost actor faster than legitimate/needed entries are consumed, permanently displacing state the protocol still needs.

### Finding Description
`BoundedStateCommitments` / `BoundedStateMachineUpdateTime` are capped per `StateMachineId` and managed as a strict FIFO via `StateCommitmentQueue`/`CommitmentQueueStates`. [3](#0-2)  Every time a new height is submitted for a chain (via consensus client updates processed inside `handle_unsigned` → `Pallet::execute` → `store_state_machine_commitment` → `insert_bounded_state_commitment`), the queue's tail advances and, once `tail - head > cap`, the oldest `MAX_COMMITMENT_EVICTIONS_PER_INSERT` (4) entries are evicted regardless of whether they are still needed to verify in-flight proofs. [4](#0-3) [2](#0-1) 

`handle_unsigned` requires no signed origin and no economic stake beyond gas/weight — "this is an unsigned extrinsic that permits anyone execute ISMP messages for free, provided they have valid proofs and the messages have not been previously processed." [2](#0-1)  Any relayer capable of producing valid consensus proofs for a fast-finalizing source chain (or any chain whose light client accepts many sequential/cheap height updates) can therefore push a burst of legitimate-but-otherwise-worthless state-machine updates purely to advance the FIFO tail. Once `tail - head` exceeds the configured cap, the oldest heights are evicted from `BoundedStateCommitments`, and a request/response membership/non-membership proof anchored at one of those evicted heights can no longer be verified on this host — `state_machine_commitment` fails for the evicted height, as demonstrated directly by the pallet's own test `commitment_queue_evicts_oldest_when_cap_is_reached` and `lowering_the_cap_drains_the_queue_gradually`. [5](#0-4) [6](#0-5) 

This is precisely the "inconsistent, timing-dependent capacity limit" DoS pattern from the report: the fill order (which heights get evicted) is dictated by insertion timing, not by relevance, so an attacker can race ahead of a slow relayer who is trying to deliver a pending, still-valid message whose proof height is near the queue head. Once evicted, that height's commitment is gone and the pending message can never be verified/delivered on this state machine — a permanent denial of the route for that message (and any other message anchored at an evicted height), matching the "route unable to deliver messages" acceptance criterion.

Mitigations exist but only partially close the gap: `MAX_COMMITMENT_EVICTIONS_PER_INSERT` limits how many entries a single insertion can evict, and governance can raise `StateMachineCommitmentCap` per chain via `update_commitment_caps` (root/`AdminOrigin` only). [7](#0-6)  Neither prevents an attacker with a fast-finalizing/cheap-to-update light client from sustaining eviction pressure over many blocks to outrun a slower relayer's honest proof submission for that same chain.

### Impact Explanation
If an attacker evicts the height that anchors a pending, unexpired POST/GET request or response before a relayer can submit its proof, that message can never be delivered on this host chain — its `handle_unsigned` proof verification will fail permanently once the commitment is gone (per the eviction test above). Any escrowed funds, cross-chain token mints, or intents/escrow settlements that depend on that specific message being delivered are frozen or lost the same way as a normal request timeout, but induced deliberately and for a specific victim height rather than by natural network delay. Because `handle_unsigned` messages cost only gas/weight (no on-chain fee is charged to the submitter for consensus updates), this is a low-cost, unprivileged attack vector on message delivery reliability — a High-severity availability/fund-freezing issue on any chain configured with a state-machine commitment cap tight relative to that chain's honest relayer latency.

### Likelihood Explanation
Exploitability depends on the attacker being able to produce a stream of valid consensus-client updates for the targeted source chain cheaply and quickly (e.g., a fast-finalizing L2/parachain light client, or any consensus client that accepts closely-spaced height submissions). This is realistic for chains with high default caps sized for very frequent finality (the doc note explicitly says fast-finalizing chains "need a much larger cap"), meaning the attack surface scales with the very chains this cap-per-cadence design targets. [8](#0-7)  The attack requires no governance/admin privilege and is reachable purely through the permissionless `handle_unsigned` extrinsic that already exists for legitimate relayers.

### Recommendation
- Do not evict a height while it still anchors any outstanding, unexpired request/response that has not yet been proven/delivered; track "in-use" heights (e.g., a reference count or a minimum-safe-height watermark derived from outstanding request timeouts) and skip/defer eviction for those, similar in spirit to how `delete_state_commitment` already special-cases the "latest" height.
- Alternatively, tie the effective retention depth to the chain's configured request/response timeout window rather than (or in addition to) a fixed entry count, so the cap can never be raced faster than the slowest honest relayer's expected proof-submission latency.
- Consider rate-limiting or requiring a bond/fee for `handle_unsigned` submissions that only advance consensus state without accompanying request/response messages, to raise the cost of pure eviction-griefing.

### Proof of Concept
The existing unit tests already demonstrate the mechanics an attacker would exploit — no new PoC code is required to prove the eviction happens, only to show it can be triggered by an unprivileged party via repeated `handle_unsigned` calls instead of direct test-harness calls:
1. `commitment_queue_evicts_oldest_when_cap_is_reached` sets a cap of 3 for a `StateMachineId`, then stores heights 1..5, showing heights 1 and 2 become unqueryable (`state_machine_commitment(...).is_err()`) while only 3..5 remain. [5](#0-4) 
2. In production, `store_state_machine_commitment` is invoked from consensus-client message handling triggered by `handle_unsigned`, which is `ensure_none`-gated (no signer required) and processes attacker-supplied `messages: Vec<Message>` in a single call. [2](#0-1) 
3. An attacker who can produce 5+ valid consensus updates for a victim's source chain (cap permitting) submits them via `handle_unsigned` before the victim's relayer submits its request/response proof anchored at height 1 or 2; the victim's proof then fails verification because `BoundedStateCommitments` no longer holds that height, exactly as `state_machine_commitment(...).is_err()` shows in the test.

	/// Per-chain FIFO queue of heights retained in [`BoundedStateCommitments`]
	/// and [`BoundedStateMachineUpdateTime`], keyed by a monotonically
	/// increasing insertion index. Insertion order matches height order because
	/// consensus updates only ever advance a state machine, so evicting at the
	/// head removes the oldest height. Entries whose height was vetoed via
	/// `delete_state_commitment` are left in place and become harmless no-ops
	/// when their index is evicted.
	///
	/// Each insertion touches O(1) small storage items, so the per-chain cap
	/// can grow without adding I/O or PoV weight to the insert path.
	#[pallet::storage]
	pub type StateCommitmentQueue<T: Config> = StorageDoubleMap<
		_,
		Blake2_128Concat,
		StateMachineId,
		Twox64Concat,
		u64,
		u64,
		OptionQuery,
	>;

	/// Head/tail indices for [`StateCommitmentQueue`], per chain.
	#[pallet::storage]
	pub type CommitmentQueueStates<T: Config> =
		StorageMap<_, Blake2_128Concat, StateMachineId, CommitmentQueueState, ValueQuery>;

	/// Per-chain override for the number of state commitments retained. Chains
	/// with faster finality emit state machine updates more frequently and
	/// need a deeper queue to retain the same wall-clock window of provable
	/// heights. Falls back to [`MAX_STATE_MACHINE_COMMITMENTS`] when unset.
	#[pallet::storage]
	pub type StateMachineCommitmentCap<T: Config> =

		/// Set the number of state commitments retained per chain, overriding
		/// [`MAX_STATE_MACHINE_COMMITMENTS`]. Size each cap to the chain's
		/// finality cadence: `desired retention window / finality interval`.
		/// Raising a cap simply pauses eviction until the queue grows into it;
		/// lowering one drains the excess gradually, bounded by
		/// [`MAX_COMMITMENT_EVICTIONS_PER_INSERT`] per subsequent insertion.
		///
		/// The dispatch origin for this call must be `T::AdminOrigin`.
		#[pallet::weight(<T as frame_system::Config>::DbWeight::get().writes(commitment_caps.len() as u64))]
		#[pallet::call_index(5)]
		pub fn update_commitment_caps(
			origin: OriginFor<T>,
			commitment_caps: BTreeMap<StateMachineId, u32>,
		) -> DispatchResult {
			T::AdminOrigin::ensure_origin(origin)?;

			ensure!(
				commitment_caps.values().all(|cap| *cap > 0),
				Error::<T>::InvalidCommitmentCap
			);
			for (id, cap) in commitment_caps {
				StateMachineCommitmentCap::<T>::insert(id, cap);
			}

			Ok(())
		}

	impl<T: Config> Pallet<T> {
		/// Number of state commitments retained for `id`: the
		/// [`StateMachineCommitmentCap`] override if set, otherwise
		/// [`MAX_STATE_MACHINE_COMMITMENTS`].
		pub fn state_machine_commitment_cap(id: StateMachineId) -> u32 {
			StateMachineCommitmentCap::<T>::get(id).unwrap_or(MAX_STATE_MACHINE_COMMITMENTS)
		}

		/// Insert a state commitment into the bounded map. ISMP does not allow
		/// duplicate state updates so we don't have an overwrite path.
		///
		/// Appends the height to the per-chain [`StateCommitmentQueue`] and, once
		/// the chain's cap is exceeded, evicts oldest-first from the queue head.
		/// Evictions are limited to [`MAX_COMMITMENT_EVICTIONS_PER_INSERT`] per
		/// call so a lowered cap drains over many insertions rather than in one.
		pub fn insert_bounded_state_commitment(
			height: StateMachineHeight,
			commitment: StateCommitment,
		) {
			let cap = Self::state_machine_commitment_cap(height.id).max(1) as u64;
			let mut state = CommitmentQueueStates::<T>::get(height.id);

			StateCommitmentQueue::<T>::insert(height.id, state.tail, height.height);
			state.tail += 1;

			let excess = (state.tail - state.head)
				.saturating_sub(cap)
				.min(MAX_COMMITMENT_EVICTIONS_PER_INSERT as u64);
			for _ in 0..excess {
				if let Some(old) = StateCommitmentQueue::<T>::take(height.id, state.head) {
					BoundedStateCommitments::<T>::remove(height.id, old);
					BoundedStateMachineUpdateTime::<T>::remove(height.id, old);
				}
				state.head += 1;
			}

			CommitmentQueueStates::<T>::insert(height.id, state);
			BoundedStateCommitments::<T>::insert(height.id, height.height, commitment);
		}

fn commitment_queue_evicts_oldest_when_cap_is_reached() {
	let mut ext = new_test_ext();
	ext.execute_with(|| {
		let host = Ismp::default();
		let id = queue_test_state_machine();

		pallet_ismp::Pallet::<Test>::update_commitment_caps(
			RuntimeOrigin::root(),
			BTreeMap::from([(id, 3)]),
		)
		.unwrap();

		for height in 1..=5u64 {
			let at = StateMachineHeight { id, height };
			host.store_state_machine_commitment(at, queue_test_commitment()).unwrap();
			host.store_state_machine_update_time(at, Duration::from_secs(height)).unwrap();
		}

		for height in 1..=2u64 {
			let at = StateMachineHeight { id, height };
			assert!(host.state_machine_commitment(at).is_err());
			assert!(host.state_machine_update_time(at).is_err());
		}
		for height in 3..=5u64 {
			let at = StateMachineHeight { id, height };
			assert!(host.state_machine_commitment(at).is_ok());
			assert!(host.state_machine_update_time(at).is_ok());
		}
		assert_eq!(
			CommitmentQueueStates::<Test>::get(id),
			CommitmentQueueState { head: 2, tail: 5 }
		);
	})
}

#[test]
fn lowering_the_cap_drains_the_queue_gradually() {
	let mut ext = new_test_ext();
	ext.execute_with(|| {
		let host = Ismp::default();
		let id = queue_test_state_machine();
		let store = |height: u64| {
			host.store_state_machine_commitment(
				StateMachineHeight { id, height },
				queue_test_commitment(),
			)
			.unwrap();
		};

		pallet_ismp::Pallet::<Test>::update_commitment_caps(
			RuntimeOrigin::root(),
			BTreeMap::from([(id, 8)]),
		)
		.unwrap();
		for height in 1..=8u64 {
			store(height);
		}
		assert_eq!(
			CommitmentQueueStates::<Test>::get(id),
			CommitmentQueueState { head: 0, tail: 8 }
		);

		pallet_ismp::Pallet::<Test>::update_commitment_caps(
			RuntimeOrigin::root(),
			BTreeMap::from([(id, 2)]),
		)
		.unwrap();

		// 9 live vs cap 2: only MAX_COMMITMENT_EVICTIONS_PER_INSERT entries are
		// evicted per insertion, so the excess drains over several insertions.
		store(9);
		assert_eq!(
			CommitmentQueueStates::<Test>::get(id),
			CommitmentQueueState { head: 4, tail: 9 }
		);
		store(10);
		assert_eq!(
			CommitmentQueueStates::<Test>::get(id),
			CommitmentQueueState { head: 8, tail: 10 }
		);
		store(11);
		assert_eq!(
			CommitmentQueueStates::<Test>::get(id),
			CommitmentQueueState { head: 9, tail: 11 }
		);
		// At the cap: steady state, one eviction per insertion.
		store(12);
		assert_eq!(
			CommitmentQueueStates::<Test>::get(id),
			CommitmentQueueState { head: 10, tail: 12 }
		);
		assert!(host.state_machine_commitment(StateMachineHeight { id, height: 10 }).is_err());
		assert!(host.state_machine_commitment(StateMachineHeight { id, height: 11 }).is_ok());
		assert!(host.state_machine_commitment(StateMachineHeight { id, height: 12 }).is_ok());
	})
}
