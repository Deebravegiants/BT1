## Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
The `ShopifyAPI::Webhooks::Request#to_signable_string` method returns only the raw HTTP body when computing/validating the webhook HMAC signature. The `shop` field, however, is read directly from the `shopify-shop-domain` HTTP header and is never included in the signed payload. Since a single app has one `client_secret` shared across every installed shop, any entity capable of producing a valid `(raw_body, hmac)` pair for one shop (e.g., a legitimate merchant who has installed the app and can observe/replay their own genuine webhook deliveries) can re-send that exact body+hmac pair while substituting a different `shopify-shop-domain` header value. The HMAC validation will still pass because it only checks the body, letting the attacker impersonate another tenant.

### Finding Description
The relevant binding that should hold is:
`hmac == HMAC(client_secret, raw_body + shop)` for the specific `shop` the request claims to be from.

Instead, the code implements:
`hmac == HMAC(client_secret, raw_body)` — independent of `shop`.

Evidence:
- `to_signable_string` only returns `@raw_body`, excluding shop/topic/etc.: [1](#0-0) 
- `shop` is parsed straight from an attacker-controllable header with no cross-check: [2](#0-1) 
- `Registry.process` validates only the HMAC over the request (which as shown above ignores `shop`), then dispatches the handler using the unauthenticated `request.shop`: [3](#0-2) 
- `HmacValidator.validate_signature` computes the digest exclusively from `verifiable_query.to_signable_string`, confirming the shop is never part of the signed material: [4](#0-3) 

Because `client_secret` (and therefore the HMAC key) is identical for every shop that has installed the app, any shop that receives real webhooks from Shopify can capture a valid `(body, hmac)` pair and replay it against the app's webhook endpoint with a forged `shopify-shop-domain` header pointing at a victim shop. The HMAC check in `Registry.process` still succeeds, and the handler receives `WebhookMetadata` with the attacker-chosen `shop` value trusted as authentic.

### Impact Explanation
This breaks the tenant isolation that webhook consumers rely on: applications typically use `WebhookMetadata#shop` to decide which merchant's data/session to update. An attacker who has legitimately installed the app (an "unprivileged internet user" relative to other tenants) can forge webhook deliveries attributed to any other shop using the same app, resulting in cross-tenant data injection/corruption — satisfying the "cross-tenant access" High-impact criterion.

### Likelihood Explanation
Exploitation only requires the attacker to install the same public app (a normal, unprivileged action) and observe one legitimate webhook delivery for their own shop (many topics, e.g. `products/update`, are attacker-triggerable on their own store). No access to `client_secret`, tokens, or the target shop is required, making this practically reachable for any app relying on the gem's built-in webhook HMAC validation as a source of shop identity.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the signed material, or otherwise require host applications to validate that `request.shop` corresponds to a shop with an active, expected installation before trusting it. At minimum, document prominently that the HMAC only authenticates the request as originating from Shopify with the correct `client_secret`, and does **not** authenticate the `shop-domain` header — so callers must independently verify the shop against their own known-shops table before acting on `WebhookMetadata#shop`.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook (e.g., `products/update`), capturing the raw POST body and the `x-shopify-hmac-sha256` header Shopify sends — this HMAC is valid because it's computed over the body with the shared `client_secret`.
2. Attacker resends the identical body and HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC solely from `raw_body` [1](#0-0)  — validation passes.
4. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` [5](#0-4) , causing the host app to process attacker-supplied data as if it originated from the victim shop.
