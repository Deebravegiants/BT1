### Title
Webhook Shop-Domain Spoofing: HMAC Signature Covers Only the Request Body, Not the `shop-domain` Identity Header - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, and `ShopifyAPI::Utils::HmacValidator` verifies the HMAC exclusively against that body. The `shop` value used to dispatch the webhook to application handlers is read straight from the `x-shopify-shop-domain`/`shopify-shop-domain` header, which is never included in the signed material. Anyone who can obtain one valid `(body, hmac)` pair signed with the app's shared secret — for example, a merchant who has legitimately installed the same multi-tenant app on their own store and receives real webhook deliveries — can replay that exact body/HMAC pair while substituting an arbitrary `shop-domain` header. `HmacValidator.validate` will still succeed because the signature never covered the shop field, and `Registry.process` will hand the forged shop identity to the handler.

### Finding Description
`Request#hmac` is derived from the `hmac-sha256` header and `Request#to_signable_string` returns `@raw_body` only: [1](#0-0) 

`Request#shop` is parsed from the `shop-domain` header with no cryptographic binding to the body or signature: [2](#0-1) 

`HmacValidator.validate_signature` recomputes the signature only from `to_signable_string` (i.e. the body) and compares it to the received HMAC: [3](#0-2) 

`Registry.process` validates the HMAC and then constructs `WebhookMetadata` using the unauthenticated `request.shop`, which is passed directly to the app's handler as the trusted tenant identifier: [4](#0-3) 

The identity binding that should hold is: `shop-header == shop-cryptographically-bound-to-signature`. Because the signature is computed only over the body, this equality never holds — the gem hands `WebhookMetadata#shop` to application code as if it were verified, when in fact only the body bytes were verified, not the shop claim. An app that trusts `WebhookMetadata#shop` to select which tenant's data/session to mutate (a very common and intended usage pattern for the `Webhooks::Registry` API) is exposed to cross-tenant data confusion: a merchant with a legitimate installation of the same multi-tenant app can trigger their own webhook deliveries (attacker fully controls the body content indirectly by manipulating data in their own store, e.g. `orders/create` payloads), capture the valid `(body, hmac)` pair signed with the shared `api_secret_key`, and replay it to the app's endpoint with the `shop-domain` header rewritten to point at a victim shop. The HMAC check passes, and the handler executes attacker-controlled body content under the victim shop's identity.

### Impact Explanation
This breaks the tenant isolation boundary of the webhook processing API: an attacker who is a legitimate but unprivileged tenant of a multi-tenant app can impersonate another tenant (shop) for any topic the app has registered a handler for, causing the handler to process attacker-controlled data (order/customer/product fields from the attacker's own store) under a victim shop's identity. This matches the "Critical - cross-tenant access" impact category, since it crosses the shop/tenant boundary using only capabilities available to any app-installing merchant, with no access token, secret leakage, or privileged access required beyond normal app installation.

### Likelihood Explanation
Any merchant who installs the app (a normal, unprivileged action for a public/multi-tenant Shopify app) automatically receives genuinely signed webhook deliveries for their own shop. Capturing a valid `(body, hmac)` pair requires no special access — it is simply an HTTP request the app already sends to the merchant's registered endpoint, or one that the merchant can capture via a proxy in front of their own installation. Only the `shop-domain` header must be modified in the replay; no cryptographic material needs to be forged. This makes exploitation straightforward for anyone who can install the target app on a shop they control.

### Recommendation
Bind the shop (and ideally the topic/webhook-id) into the material that is HMAC-verified, or otherwise cryptographically tie the `shop-domain` header to the signed payload before it is exposed via `WebhookMetadata#shop`. At minimum, document prominently that `request.shop` / `WebhookMetadata#shop` is not covered by the HMAC and that host applications must independently verify the shop against their own list of installed/authorized shops (e.g. checking it against a known session) before trusting it for any tenant-scoped action.

### Proof of Concept
1. Install the target multi-tenant app on attacker-controlled shop `attacker.myshopify.com`; the app's shared `api_secret_key` is common to all installations.
2. Trigger a webhook delivery for a subscribed topic (e.g. `orders/create`) by creating an order in the attacker's own store, with attacker-chosen field values embedded in the JSON body.
3. Capture the resulting HTTP request, in particular the raw body and the `x-shopify-hmac-sha256` header (a valid HMAC over that body, computed with the shared secret).
4. Resend that identical body and HMAC header to the app's webhook endpoint, but replace `x-shopify-shop-domain` with `victim.myshopify.com`.
5. `HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:13-22`) succeeds because it only checks the body's signature. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:189-200`) then invokes the app's handler with `WebhookMetadata#shop == "victim.myshopify.com"` and attacker-controlled body content, causing the app to process attacker data as if it originated from the victim shop.
