### Title
Passphrase-cache TTL bypass: `maxTtl` hard cap is never enforced once `inactiveAt` is set - ([File: features/application/src/modules/passphrase-cache.ts])

### Summary
`PassphraseCache.get()` in `features/application/src/modules/passphrase-cache.ts` decides whether to hand back the cached wallet passphrase based on two independent, non-composed timestamp checks: an "activity window" check (`inactiveAt + ttl > Date.now()`) and a "hard cap" check (`addedAt + maxTtl > Date.now()`). Once `inactiveAt` is set, only the activity-window branch is evaluated and the `maxTtl` cap is never consulted again, so the cached passphrase can be kept alive indefinitely by repeatedly refreshing `inactiveAt` before each `ttl` window elapses.

### Finding Description
The cache stores `ADDED_AT_KEY` (when the passphrase was cached) and, separately, `INACTIVE_AT_KEY` (when the app was last considered "inactive", e.g. backgrounded/unloaded): [1](#0-0) 

```
async get() {
  ...
  if (passphrase) {
    if (inactiveAt) {
      if (inactiveAt + ttl > Date.now()) {
        return passphrase          // <-- maxTtl never checked here
      }
    } else if (addedAt + this.#maxTtl > Date.now()) {
      return passphrase
    }
    ...clear()
  }
}
```

`inactiveAt` is set by `scheduleClear()`, which is called from `Application.unload()` and from the public `restartAutoLockTimer()` API: [2](#0-1) [3](#0-2) 

`restartAutoLockTimer` is exposed directly on the application API surface (`exodus.application.restartAutoLockTimer()`): [4](#0-3) [5](#0-4) 

Each call to `scheduleClear()` unconditionally overwrites `INACTIVE_AT_KEY` with the current time and (re)schedules the clear alarm using the current `ttl`: [6](#0-5) 

Because `get()`'s "activity period" branch is self-referential (it only compares `inactiveAt` to itself + `ttl`, never to `addedAt`), calling `restartAutoLockTimer()` (or triggering `unload`/`load` cycles, e.g. via app backgrounding) at intervals shorter than `ttl` resets the window forever and the `config.maxTtl` absolute cap — the security control meant to force re-entry of the passphrase after a bounded maximum period regardless of activity — is never reached. This mirrors the Teller `_canLiquidateLoan` bug class: a time check anchored to a "last action" timestamp (`lastRepaidTimestamp` / `inactiveAt`) is used in place of a check anchored to the fixed reference point (`due date` / `addedAt`+cap), letting the actor perpetually reset the window and defeat the intended bound.

### Impact Explanation
The decrypted wallet passphrase is meant to be evicted from cache after `config.maxTtl` at the latest, this is the documented hard boundary independent of activity. This bug lets that boundary be bypassed entirely: as long as `restartAutoLockTimer()` (or normal app foreground/background cycling that triggers `unload`) happens more often than the configured `ttl`, the passphrase remains cached and `autoUnlock()`/`getMnemonic`/`restoreFromCurrentPhrase` will keep succeeding using the stale cached passphrase far beyond the intended maximum retention window: [7](#0-6) 

This extends the exposure window of the sensitive passphrase in unsafe/plain storage well past the security-configured limit, increasing the risk of secret disclosure to anyone (malware, another local process, or a physically-present attacker) able to read that storage or trigger the cached auto-unlock flow.

### Likelihood Explanation
`restartAutoLockTimer` is a normal, unprivileged, documented application API call, not a privileged operation, so any code with access to the `exodus.application` API can trigger it. It is also invoked implicitly by ordinary app lifecycle events (`unload`), so this can occur without any deliberate attacker action, purely as a byproduct of normal background/foreground app usage patterns, making the mis-enforced cap practically always reachable.

### Recommendation
In `PassphraseCache.get()`, always enforce the absolute cap regardless of activity state, e.g.:
```
if (passphrase) {
  const withinMaxTtl = addedAt + this.#maxTtl > Date.now()
  const withinActivityWindow = inactiveAt && inactiveAt + ttl > Date.now()
  if (withinMaxTtl && (withinActivityWindow || !inactiveAt)) {
    return passphrase
  }
  ...clear()
}
```
i.e., compute liveness relative to the fixed `addedAt` reference (the "due date" analog) and never let the "last inactive" timestamp alone extend validity past `addedAt + maxTtl`.

### Proof of Concept
1. Configure `application` with `config.maxTtl = 5` minutes and `autoLockTimer` (`ttl`) = 5 minutes as well (`ttl <= maxTtl`, which is enforced in `changeTtl` via `Math.min(this.#maxTtl, ttl)`).
2. `application.unlock({ passphrase })` → `passphraseCache.set(passphrase)` sets `addedAt = t0`.
3. Every 4 minutes, call `exodus.application.restartAutoLockTimer()` (or simulate app backgrounding causing `application.unload()`), which sets `inactiveAt = now` each time via `scheduleClear()`.
4. At `t0 + 30` minutes (well past `maxTtl` = 5 minutes), call `passphraseCache.get()` / trigger `autoUnlock()`. Because `inactiveAt` was refreshed 4 minutes ago, `inactiveAt + ttl > Date.now()` is true, and the passphrase is returned/used for auto-unlock — despite `addedAt + maxTtl` having elapsed 25 minutes earlier.
