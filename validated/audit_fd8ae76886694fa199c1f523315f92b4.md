### Title
Unbounded attacker-controlled loops in BEEFY consensus verification allow gas/weight-exhaustion DoS during ISMP message processing - ([File: evm/src/consensus/EcdsaBeefy.sol])

### Summary
Both the Solidity and Rust BEEFY verifiers loop over relayer-supplied arrays (`votes`, `payload`, `parachains`) whose length is bounded only below (supermajority participation check) but never above. This mirrors the CVE-2023-0411 bug class ("excessive loops... allows denial of service via packet injection or crafted capture file") — a single untrusted, unsigned proof can drive the verifier to iterate over an attacker-chosen number of expensive operations (`ECDSA.recover`/`secp256k1_recover`) before any economic cost is charged.

### Finding Description
In `EcdsaBeefy.verifyMmrUpdateProof`, `sigLen` is read directly from `relayProof.signedCommitment.votes.length` [1](#0-0) , only lower-bounded via `checkParticipationThreshold(sigLen, authoritySet.len)` [2](#0-1) . There is no upper cap, and the subsequent loop performs one `ECDSA.recover` per vote [3](#0-2) . A second unbounded loop scans `commitment.payload` for the MMR-root entry [4](#0-3) , and `verifyParachainHeaderProof` loops over an attacker-supplied `parachains` array, SCALE-decoding a full header per entry [5](#0-4) .

The equivalent Rust verifier (`modules/consensus/beefy/verifier/src/lib.rs`) has the identical structure: `signatures_length` is taken from the untrusted proof, checked only against the participation threshold, and then a loop performs an EC recovery for every signature entry before the merkle multi-proof is even checked [6](#0-5) .

Critically, on the Substrate side this verification runs inside `pallet_ismp::handle_unsigned`, which is invoked during `ValidateUnsigned::validate_unsigned` — i.e., `Self::execute(messages.clone())` (which includes the full consensus-verification loop) runs on every node that receives the unsigned extrinsic during transaction-pool gossip validation, before any fee is charged and before the extrinsic is included in a block [7](#0-6) . No `BoundedVec`/max-length constraint on `votes`, `payload`, or `parachain_headers` was found anywhere in the message types, pallet config, or weight annotation for `handle_unsigned` (`#[pallet::weight(weight())]`) [8](#0-7) .

### Impact Explanation
An attacker can craft a single BEEFY consensus message (or `ParachainProof`) with an arbitrarily large `votes`/`signatures`/`parachains` array. On EVM, this inflates gas cost per verification call, potentially forcing legitimate relayers' calls (or gas-limited batched calls) toward the block gas limit, degrading throughput of consensus updates — a "route unable to deliver messages" condition for the affected BEEFY consensus client. On the Substrate/pallet-ismp side, the effect is worse: because unsigned-transaction validation re-executes the entire message handling pipeline (including EC-recovery loops) for free on every propagating node, an attacker can submit unsigned extrinsics with oversized arrays to force full nodes across the network to repeatedly perform expensive cryptographic loops with no fee paid, which is a resource-exhaustion/DoS vector against the relay/consensus-update path.

### Likelihood Explanation
Medium. The message is fully attacker-controlled (an unsigned ISMP message, or a submitted consensus proof to the `verify()` entrypoint), requires no privileged role, and the missing upper bound is confirmed by reading the full verification code paths in both the Solidity and Rust BEEFY verifiers. However, actual severity is capped by protocol-level implicit limits (block gas limit on EVM; transaction size/weight limits on Substrate), and I could not confirm within the available context whether a max-extrinsic-length or transaction-pool byte-size limit indirectly caps the array in practice — this constrains but does not eliminate the exposure.

### Recommendation
Add explicit upper bounds (e.g., `MAX_BEEFY_VOTES`, `MAX_PAYLOAD_ITEMS`, `MAX_PARACHAIN_HEADERS_PER_PROOF`) enforced before iterating in both `EcdsaBeefy.verifyMmrUpdateProof`/`verifyParachainHeaderProof` (Solidity) and `verify_mmr_update_proof`/`verify_parachain_headers` (Rust), rejecting proofs whose array lengths exceed a sane multiple of the maximum expected authority-set size or parachain count. On the Substrate side, additionally bound message batch composition checked in `validate_unsigned` prior to invoking `Self::execute`, so unbounded arrays are rejected cheaply (e.g., a size/length pre-check on the decoded message) before the expensive verification loop runs.

### Proof of Concept
Not verifiable in this read-only ask session (no ability to execute or fuzz the contracts/pallets). Conceptually: construct a `BeefyConsensusProof` where `RelayChainProof.signedCommitment.votes` contains N synthetic (even invalid) signature entries — enough to satisfy `checkParticipationThreshold` doesn't require rejecting the extras since the threshold check only enforces a lower bound (`sigLen >= 2/3+1`), not an upper one, so N can be inflated arbitrarily beyond genuine authority-set size while still passing the participation check as long as the true valid subset also passes; submit as an unsigned `Message::Consensus` to `handle_unsigned` and observe validation-time CPU cost scale linearly with N on every node validating the extrinsic.
