### Title
`Oauth.begin_auth` sends the app's `client_id` and requested OAuth scopes to an attacker-controlled `shop` host because the `shop` parameter is never passed through `ShopValidator` before being used to build the authorization redirect URL - ([File: lib/shopify_api/auth/oauth.rb])

### Summary
Every other credential-exchange entry point in this gem (`ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, `TokenExchange.migrate_to_expiring_token`) validates the caller-supplied `shop` string with `Utils::ShopValidator.sanitize!` before using it to build a request host. [1](#0-0) [2](#0-1) [3](#0-2)  `Oauth.begin_auth`, however, takes the `shop:` argument and feeds it directly, unsanitized, into `auth_base_uri(shop)` to construct the URL the merchant's browser is redirected to. [4](#0-3) 

### Finding Description
`begin_auth` builds the authorization redirect as:

```ruby
auth_route = auth_base_uri(shop) + "/oauth/authorize?#{query_string}"
```
where `auth_base_uri` is simply `"https://#{shop}/admin"` for any `shop` string containing no further checks. [5](#0-4) 

The `query_string` embeds the app's `client_id` (the OAuth `client_id`, considered sensitive app identity/configuration data), the requested `scope`, the `redirect_uri`, and a `state` nonce. [6](#0-5) 

The library's own documentation for `begin_auth` shows the canonical caller pattern taking `shop` straight from an inbound request header with no sanitization step shown before calling into the gem:

```ruby
shop = request.headers["Shop"]
auth_response = ShopifyAPI::Auth::Oauth.begin_auth(shop: domain, redirect_path: "/auth/callback")
``` [7](#0-6) 

Because the gem itself provides `Utils::ShopValidator` specifically to guard against exactly this class of problem (unbounded `shop` values reaching a request host) and applies it consistently in `ClientCredentials`, `RefreshToken`, and `TokenExchange.migrate_to_expiring_token`, [8](#0-7)  the omission in `begin_auth` is an inconsistency in the gem's own trust boundary, not merely a host-application misuse of a documented API — the sibling methods performing an equivalent action (building an admin host from a `shop` string) treat `shop` as untrusted input requiring validation, while `begin_auth` treats it as trusted.

The broken binding, stated as an equality that should hold but doesn't:
`host receiving {client_id, scope, redirect_uri, state}` == `ShopValidator.sanitize!(shop)` — instead the actual binding is `host receiving {client_id, scope, redirect_uri, state}` == `raw shop` (attacker-controllable, no `.myshopify.com`/trusted-domain constraint, no scheme/host validation, no `@`-stripping like `ShopValidator` performs).

### Impact Explanation
An attacker who controls (or can influence) the `shop` value passed into `begin_auth` — e.g. via a `shop` query/header parameter on the app's login route, matching the pattern shown in this gem's own documentation — can cause the merchant's browser to be redirected to `https://attacker-controlled-host/admin/oauth/authorize?client_id=<APP_CLIENT_ID>&scope=<REQUESTED_SCOPES>&redirect_uri=<APP_CALLBACK_URL>&state=<NONCE>`. This discloses the app's `client_id` and requested scope set to an attacker-chosen host and enables a forced/spoofed OAuth completion flow: the attacker's page can mimic the Shopify consent screen and redirect the victim's browser back to the legitimate `redirect_uri` with an attacker-supplied `code`/`shop` pair, or otherwise manipulate the flow before the merchant ever reaches Shopify. This matches the "session fixation or forced OAuth completion" High-severity category, since the identity binding between "the host performing the OAuth handshake" and "an actual, validated Shopify shop domain" is not enforced by the gem at the point the flow begins.

### Likelihood Explanation
Likelihood depends on the host application passing user/attacker-influenced input as `shop` into `begin_auth` without its own additional sanitization — which is exactly the pattern shown in this gem's official usage documentation (`shop = request.headers["Shop"]`), so a developer following the documented example is exposed. Given the gem exports and uses `ShopValidator` in three sibling OAuth-adjacent methods for this precise purpose, its absence in `begin_auth` is a gap in the gem, not solely a downstream misuse.

### Recommendation
Call `Utils::ShopValidator.sanitize!(shop)` (or `sanitize_shop_domain`) at the start of `Oauth.begin_auth` and use the validated/sanitized shop value when constructing `auth_base_uri`, mirroring the pattern already used in `ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, and `TokenExchange.migrate_to_expiring_token`.

### Proof of Concept
```ruby
ShopifyAPI::Context.setup(api_key: "APP_CLIENT_ID", api_secret_key: "secret", ...)

# Attacker-influenced shop value reaching the documented begin_auth call pattern
attacker_shop = "attacker.example"

result = ShopifyAPI::Auth::Oauth.begin_auth(
  shop: attacker_shop,
  redirect_path: "/auth/callback",
)

result[:auth_route]
# => "https://attacker.example/admin/oauth/authorize?client_id=APP_CLIENT_ID&scope=...&redirect_uri=https://legit-app.com/auth/callback&state=...&grant_options%5B%5D="
```
No `ShopifyAPI::Errors::InvalidShopError` is raised; the app's `client_id`, requested `scope`, and callback `redirect_uri` are sent verbatim to `attacker.example`, unlike the equivalent host-construction paths in `ClientCredentials`, `RefreshToken`, and `TokenExchange.migrate_to_expiring_token`, which reject non-Shopify domains via `ShopValidator.sanitize!`.         def begin_auth(shop:, redirect_path:, is_online: true, scope_override: nil)
          scope = if scope_override.nil?
            ShopifyAPI::Context.scope
          elsif scope_override.is_a?(ShopifyAPI::Auth::AuthScopes)
            scope_override
          else
            ShopifyAPI::Auth::AuthScopes.new(scope_override)
          end

          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = SecureRandom.alphanumeric(NONCE_LENGTH)

          cookie = SessionCookie.new(value: state, expires: Time.now + 60)

          query = {
            client_id: ShopifyAPI::Context.api_key,
            scope: scope.to_s,
            redirect_uri: "#{ShopifyAPI::Context.host}#{redirect_path}",
            state: state,
            "grant_options[]": is_online ? "per-user" : "",
          }

          query_string = URI.encode_www_form(query)
          auth_route = auth_base_uri(shop) + "/oauth/authorize?#{query_string}"

          { auth_route: auth_route, cookie: cookie }
        end

        sig { params(shop: String).returns(String) }
        def auth_base_uri(shop)
          return "https://#{shop}/admin" unless defined?(DevServer) && shop.include?(".my.shop.dev")

          # For first-party apps in development only, we leverage DevServer to build the admin base URI
          admin_web = T.unsafe(Object.const_get("DevServer")) # rubocop:disable Sorbet/ConstantsFromStrings
            .new("admin-web")
          admin_host = admin_web.host!(nonstandard_host_prefix: "admin")
          shop_name = shop.split(".").first

          "https://#{admin_host}/store/#{shop_name}"
        end

**File:** docs/usage/oauth.md (L180-199)

class ShopifyAuthController < ApplicationController
  def login
    shop = request.headers["Shop"]

    # Builds the authorization URL route to redirect the user to
    auth_response = ShopifyAPI::Auth::Oauth.begin_auth(shop: domain, redirect_path: "/auth/callback")

    # Store the authorization cookie
    cookies[auth_response[:cookie].name] = {
      expires: auth_response[:cookie].expires,
      secure: true,
      http_only: true,
      value: auth_response[:cookie].value
    }

    # Redirect the user to "auth_response[:auth_route]" to allow user to grant the app permission
    # This will lead the user to the Shopify Authorization page
    head 307
    response.set_header("Location", auth_response[:auth_route])
  end
```
