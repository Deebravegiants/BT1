Confirmed: `WebhookMetadata` carries `shop` directly to the handler as documented — `data.shop` is described in docs as "The shop domain of the webhook" and is meant to identify which tenant the webhook belongs to [1](#0-0) , with the recommended usage pattern being to key background jobs off it, e.g. `perform_later(topic: data.topic, shop_domain: data.shop, ...)` [2](#0-1) .

### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing tenant-identity spoofing on an otherwise-valid webhook - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC over the raw body only, while the `shop` (tenant identity) is read from a separate, unsigned HTTP header. `ShopifyAPI::Webhooks::Registry.process` verifies only the body signature and then hands the unauthenticated `shop` value straight to the app's handler, breaking the intended binding between "bytes verified" and "identity acted on."

### Finding Description
`Request#to_signable_string` returns `@raw_body` exclusively: [3](#0-2) 

The `shop` accessor, however, is derived from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of the signed content at all: [4](#0-3) [5](#0-4) 

`Registry.process` validates only `Utils::HmacValidator.validate(request)` (i.e., the body HMAC) before dispatching to the handler with `request.shop` taken at face value: [6](#0-5) 

`Utils::HmacValidator.validate_signature` computes the HMAC using `verifiable_query.to_signable_string`, which for a webhook `Request` is the raw body — the `shop` header is simply never fed into the signature computation: [7](#0-6) 

Because Shopify signs webhook bodies with the single app-wide `client_secret` (shared across every shop that has the app installed) rather than a per-shop secret, any two webhook deliveries with byte-identical bodies produce byte-identical, valid HMACs regardless of which shop they originated from. An attacker who legitimately installs the app on their own shop (unprivileged internet user, no special credential needed beyond installing a free app) receives real, correctly-signed webhook deliveries for topics with predictable/duplicable bodies (e.g., `app/uninstalled`, `shop/redact`, or any topic whose payload the attacker fully controls, such as by creating a matching resource). The attacker can then replay that exact `(raw_body, hmac)` pair to the app's webhook endpoint while substituting an arbitrary victim `shop-domain` header value. `Registry.process` will validate the (still-correct) body HMAC and dispatch to the handler as if the event belonged to the victim shop.

The broken identity binding, stated as an equality that fails to hold:
`shop used by handler (Request#shop, from unsigned header) == shop whose secret/content produced the HMAC (none — the signed content contains no shop identity at all)`.

### Impact Explanation
This is a cross-tenant identity-spoofing vector: the gem authenticates *content* (the body) but the handler and any downstream app logic act on an *unauthenticated* tenant identifier (`data.shop`) as if it were verified, per the documented handler contract. This matches the report's bug class of "a field acted on but not covered by the HMAC," and if the host application uses `data.shop` to select which tenant's records to mutate (as the gem's own documentation example demonstrates), an attacker can cause writes/queues to be attributed to, or trigger side effects against, a shop they do not control — a cross-tenant access impact.

### Likelihood Explanation
Requires only that the attacker control one shop where the app is installed (an unprivileged, self-service action) and be able to trigger a webhook whose body they can reproduce or predict; no `api_secret_key`, access token, or other privileged credential is needed since the gem never binds `shop` into the signed material. Likelihood is bounded by which topics have attacker-shapeable/predictable bodies, but the underlying binding gap in the gem is unconditional.

### Recommendation
Include the shop-domain header (and other identity-relevant headers such as `webhook-id`) in `to_signable_string`, or have `Registry.process` independently verify that the delivered `shop` corresponds to a shop for which this app+topic combination was actually registered before invoking the handler, rather than trusting the header value once the body HMAC passes.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook for a topic whose body is attacker-controlled or predictable (e.g. by editing a resource to a known state), receiving a genuine request with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid-hmac-of-body>`, and body `B`.
2. Attacker resends the same `raw_body: B` to the app's webhook endpoint, replacing the header with `x-shopify-shop-domain: victim-shop.myshopify.com`, keeping the original valid `hmac-sha256` value.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: spoofed_headers)` is constructed; `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because `to_signable_string` only checks `B` [3](#0-2) .
4. The handler is invoked with `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body:, ...)`, and any app logic keyed on `data.shop` operates as though the event genuinely originated from the victim shop [8](#0-7) .
