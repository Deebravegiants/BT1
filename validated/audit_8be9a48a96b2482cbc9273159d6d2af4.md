## Title
Webhook HMAC validation covers only the raw body, allowing shop identity spoofing via header forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by checking `Utils::HmacValidator.validate(request)`, which computes the HMAC over `Webhooks::Request#to_signable_string`. That method returns only the raw HTTP body, never the `shop`, `topic`, `webhook_id`, or `api_version` values that are pulled straight from HTTP headers and then handed to the app's handler as trusted tenant-identifying data.

### Finding Description
`HmacValidator.validate` verifies `computed_signature == received_signature` where `computed_signature` is derived exclusively from `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` returns `@raw_body` only: [2](#0-1) 

Yet `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from unauthenticated headers: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` (and the other header-derived fields) as the identity of the webhook's origin when constructing `WebhookMetadata` passed to the app's handler: [4](#0-3) 

The identity binding that should hold is: `shop authenticated by the HMAC` == `shop the handler is told owns this data`. Because the HMAC is computed only over the raw body, this equality never actually holds — the `shop-domain` (and `topic`/`webhook_id`) header is never part of what's cryptographically bound. Any unprivileged internet user who can install the app on their own store (which is the normal, permission-less onboarding flow for any public Shopify app) can trigger a webhook to their own store, capture the legitimate `(body, hmac)` pair Shopify sends, and then replay that exact body + HMAC to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header for a victim shop. `HmacValidator.validate` will still pass because it never inspected those headers, and `Registry.process` will dispatch to the handler believing the (forged) victim shop sent this payload.

This is the same root-cause shape as the referenced report: a value used to make identity/authorization decisions (there, `eligibility`/`toggle` on a linked tophat; here, the `shop` tenant identity) is not actually bound by the mechanism relied upon to make it trustworthy (there, hat immutability; here, the HMAC signature) — so the trust boundary silently doesn't cover the field being acted upon.

### Impact Explanation
Any handler logic that keys off `WebhookMetadata#shop` to look up or mutate per-tenant state (e.g., "find this shop's record and update/delete it", or trigger uninstall/deauthorization side effects) can be made to act on the wrong tenant's data because the `shop` value was never authenticated — only the body bytes were. This is a cross-tenant integrity issue at the gem's trust boundary: apps built on this gem's documented API (`Registry.process`) are led to believe `request.shop` is Shopify-attested when it is not.

### Likelihood Explanation
Exploitability requires no privileged credentials: any internet user can create a free/dev Shopify store, install the target app, and receive a legitimate signed webhook of their choosing (many webhook bodies, e.g. `app/uninstalled`, are static/predictable), then replay it with a forged shop header. This requires no `api_secret_key`, access token, or leaked credential — only the ability to install the target app on an attacker-controlled shop, which is normal unprivileged usage.

### Recommendation
Include the `shop-domain`, `topic`, and other Shopify-supplied headers relied upon by handlers in the HMAC-signable material (or otherwise cryptographically bind them, e.g., by having `Registry.process` independently verify that the shop is a known/expected installation before dispatching), so that the identity fields acted upon by handler code are the same bytes covered by the signature verification.

### Proof of Concept
1. Attacker installs the target app on their own Shopify dev store (`attacker-shop.myshopify.com`), which is unprivileged self-service.
2. Attacker triggers a webhook event (e.g., `app/uninstalled`) on their own store and captures the raw POST body and the `X-Shopify-Hmac-Sha256` header Shopify sends — this is a valid `(body, hmac)` pair signed with the app's `client_secret`.
3. Attacker replays that exact body and HMAC header to the app's webhook endpoint, but changes `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb`) passes because it only checks the body bytes.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb`, line 198) constructs `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and dispatches to the app's handler, which now processes an uninstall (or other) event attributed to a shop that never sent it.
