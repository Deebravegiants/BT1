### Title
Griefing via permissionless `TransferToGasKey` deposits blocking gas-key deletion and account deletion - (File: runtime/runtime/src/access_keys.rs)

### Summary
`action_transfer_to_gas_key` accepts a deposit and unconditionally adds it to the target gas key's balance with no check on who is allowed to fund the key or by how much. Because gas-key deletion (and, transitively, account deletion) is gated on the gas key balance being at or below a hard-coded `MAX_BALANCE_TO_BURN` threshold, an attacker who knows a victim's gas-key public key can send a tiny `TransferToGasKey` deposit that pushes the balance above the threshold, causing the victim's subsequent `DeleteKey`/`DeleteAccount` transactions to fail deterministically — the same "front-run with a small value to flip a threshold check and fail the victim's legitimate transaction" pattern described in the Papr `reduceDebt` report.

### Finding Description
`action_transfer_to_gas_key` looks up the access key by `(account_id, public_key)` and does a plain `checked_add` of `action.deposit` into `gas_key_info.balance`, with no restriction tying the caller (`predecessor_id` of the receipt) to the account owner: [1](#0-0) 

This action is documented as a "dedicated action" for moving balance into a gas key, distinct from and not requiring the `FullAccess`-only permission checks that gate owner-restricted actions like `AddKey`/`DeleteKey`/`DeployContract`/`Stake`/`DeleteAccount`: [2](#0-1) 

Deleting a gas key is only permitted while its balance is at or below `GasKeyInfo::MAX_BALANCE_TO_BURN` (1 NEAR); otherwise it fails with `GasKeyBalanceTooHigh` and the key is left intact: [3](#0-2) 

The same balance-burn cap and `GasKeyBalanceTooHigh` check is also applied when summing all gas-key balances during full account deletion: [4](#0-3) 

Because any account can submit a receipt carrying a `TransferToGasKey` action against another account's gas key (the action mutates only the *receiver's* `GasKeyInfo.balance`, mirroring the permissionless nature of a plain `Transfer`), an attacker can:
1. Observe or otherwise learn a victim's gas-key public key (gas keys are visible on-chain via access-key queries once used, or via mempool observation of a pending `AddKey`/usage transaction).
2. Send a `TransferToGasKey` action with a deposit that brings `gas_key_info.balance` above `MAX_BALANCE_TO_BURN` before the victim's own `DeleteKey`/`DeleteAccount` transaction executes.
3. The victim's transaction, which was valid when signed/submitted, now fails with `ActionErrorKind::GasKeyBalanceTooHigh` because the state it depends on (the gas key's balance) was mutated by an unrelated, unprivileged party in between.

This is structurally identical to the Papr `_reduceDebtWithoutBurn` griefing: a threshold/underflow-style state check (`amount > _vaultInfo[...].debt` in Papr; `balance > MAX_BALANCE_TO_BURN` in nearcore) can be flipped by a third party with a tiny, cheap deposit right before the victim's transaction executes, deterministically failing the victim's otherwise-correct transaction.

### Impact Explanation
The attack does not steal funds directly (the deposited NEAR remains attributed to the gas key and is ultimately burned when the key is eventually deleted, or refunded to the account via `WithdrawFromGasKey` by the owner), but it produces a persistent denial-of-service on the victim's ability to delete a specific gas key or delete their account, since every retry can be repeatedly griefed by the attacker with a fresh tiny deposit for a negligible, repeatable cost. This blocks account/key lifecycle operations (`DeleteKey`, `DeleteAccount`) for an affected account, which is an availability/griefing impact rather than a token-theft impact.

### Likelihood Explanation
Likelihood is moderate: the attacker needs to know the target gas-key public key and to time the deposit ahead of the victim's `DeleteKey`/`DeleteAccount` transaction (mempool visibility or repeated speculative griefing). No special privileges are required — this is reachable by any unprivileged account submitting a standard `TransferToGasKey` action, and the deposit cost required to cross the 1 NEAR threshold is bounded and cheap relative to disrupting an account's key management.

### Recommendation
Restrict `TransferToGasKey` deposits so they cannot be used to push a gas key over `MAX_BALANCE_TO_BURN` from an unauthorized predecessor, or decouple the deletion threshold from externally-toppable balance, e.g.:
- Require `predecessor_id == account_id` (or an explicit opt-in) for `TransferToGasKey`, similar to the actor-permission checks already applied to other owner-only account-mutating actions, or
- On `DeleteKey`/`DeleteAccount`, only burn up to `MAX_BALANCE_TO_BURN` and refund the excess back to the depositor(s)/account instead of unconditionally rejecting the deletion when balance exceeds the cap, so third-party deposits cannot block key/account deletion.

### Proof of Concept
1. Victim Alice owns account `alice.near` with a gas key `pk_A` whose `GasKeyInfo.balance` is `0`.
2. Alice broadcasts a `DeleteKey(pk_A)` transaction to clean up the key (valid at submission time, since `balance (0) <= MAX_BALANCE_TO_BURN`).
3. Attacker Bob observes `pk_A` (from a prior on-chain use of the key or from watching the mempool) and submits a `TransferToGasKey { public_key: pk_A, deposit: 1 yoctoNEAR over 1 NEAR }` action receipt targeting `alice.near`, which succeeds unconditionally via `action_transfer_to_gas_key` (`runtime/runtime/src/access_keys.rs:257-288`) because no actor-permission check restricts who may fund another account's gas key.
4. If Bob's transfer lands before Alice's `DeleteKey`, `gas_key_info.balance` now exceeds `GasKeyInfo::MAX_BALANCE_TO_BURN`, so `delete_gas_key` (`runtime/runtime/src/access_keys.rs:93-111`) returns `ActionErrorKind::GasKeyBalanceTooHigh`, and Alice's `DeleteKey` transaction fails.
5. Bob can repeat this cheaply against any retry, indefinitely blocking Alice from deleting that gas key (or her whole account, which sums gas-key balances against the same cap).

**Uncertainty note:** I was not able to fully confirm, within the available tool budget, whether `TransferToGasKey` is excluded from the `check_actor_permissions` gate in `runtime/runtime/src/actions.rs` (the file where that permission dispatch lives) — I located the function and its usages but ran out of iterations before reading its full body. The finding above is based on strong circumstantial evidence: `action_transfer_to_gas_key` itself contains no actor/permission check [1](#0-0) , and the protocol-model documentation explicitly separates it from the owner-only, `FullAccess`-gated actions [5](#0-4) . If `check_actor_permissions` in `runtime/runtime/src/actions.rs` does in fact restrict `TransferToGasKey` to `predecessor_id == account_id`, this specific griefing vector would not be exploitable by a third party, and this report should be treated as unconfirmed pending review of that function.

```rust
pub(crate) fn action_transfer_to_gas_key(
    state_update: &mut TrieUpdate,
    result: &mut ActionResult,
    account_id: &AccountId,
    action: &TransferToGasKeyAction,
) -> Result<(), RuntimeError> {
    let Some(mut access_key) = get_access_key(state_update, account_id, &action.public_key)? else {
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };
    let Some(gas_key_info) = access_key.gas_key_info_mut() else {
        // Key exists but is not a gas key
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };

    gas_key_info.balance = gas_key_info.balance.checked_add(action.deposit).ok_or_else(|| {
        RuntimeError::StorageError(StorageError::StorageInconsistentState(
            "gas key balance integer overflow".to_string(),
        ))
    })?;
    set_access_key(state_update, account_id.clone(), action.public_key.clone(), &access_key);
    Ok(())
}
```
