### Title
DelegateAction (NEP-366 meta-transaction) signatures omit any chain-specific commitment, enabling cross-chain replay - (File: `core/primitives/src/action/delegate.rs`, `core/primitives/src/signable_message.rs`, `runtime/runtime/src/actions.rs`)

### Summary
The `DelegateAction`/`DelegateActionV2` signing scheme (NEP-366/NEP-611 "meta transactions") hashes only `sender_id`, `receiver_id`, `actions`, `nonce`, `max_block_height`, `public_key` under a fixed `MessageDiscriminant`. Unlike ordinary `SignedTransaction`s, which embed a recent `block_hash` that only exists on one specific chain, a `SignedDelegateAction`/`VersionedSignedDelegateAction` contains nothing that binds the signature to a particular chain/genesis. Replay protection is delegated entirely to the signer's on-chain access-key nonce state, which is independent per chain.

### Finding Description
`DelegateAction::get_nep461_hash` / `VersionedDelegateActionPayload::get_nep461_hash` build the signed payload as `SignableMessage{ discriminant, msg }` and hash it with borsh serialization: [1](#0-0)  and [2](#0-1) . The fields that go into this hash are only `sender_id`, `receiver_id`, `actions`, `nonce`, `max_block_height`, `public_key` [3](#0-2)  — there is no genesis hash, `chain_id`, or any other value that ties the signature to a specific nearcore-based network. The `MessageDiscriminant` is a fixed constant per NEP (366/611), the same on every deployment of nearcore code, so it cannot serve as a chain identifier either [4](#0-3) .

Contrast this with plain `SignedTransaction`s, whose signed hash includes `block_hash`, a value pulled from a recent block on the specific chain that processes it, giving them natural chain-scoping [5](#0-4) .

On execution, `apply_delegate_action` only checks the signature validity, `max_block_height` (an absolute height, not a chain-unique value), and that `sender_id` matches the receipt receiver [6](#0-5) . The actual replay defense is `validate_delegate_action_key`, which compares `delegate_action.nonce()` against the access key's `current_nonce` stored in that account's on-chain state and rejects nonces `<= current_nonce` [7](#0-6) . This nonce state is purely local per-chain account state — it is not derived from anything chain-specific in the signed payload.

Because nothing in the signed bytes commits to a chain identity, if the same account id, the same public key, and a matching (not-yet-consumed) nonce exist on more than one nearcore-derived network — e.g. a forked/duplicated chain, a state-snapshot-seeded sandbox/testnet, or any other independent deployment of nearcore sharing genesis/account state — a `SignedDelegateAction` captured from one chain can be wrapped in a fresh outer transaction and resubmitted verbatim on the other chain. The outer transaction's own `block_hash`/nonce checks are satisfied locally on that second chain, and the inner delegate signature verifies unchanged, so the delegated action (fund transfers, key additions, etc.) executes a second time.

### Impact Explanation
If exploitable, this allows unauthorized replay of a signer's authorized action (e.g., a `Transfer`, `AddKey`, or arbitrary function call bundled in a `DelegateAction`) on a chain other than the one the user intended to authorize it for, resulting in unauthorized state/balance changes on that second chain without the sender's fresh consent for that specific network.

### Likelihood Explanation
This requires the same account id + public key + un-advanced nonce to exist across two independently-operated nearcore-based networks (e.g., a forked chain, a resynced/rolled-back chain, or a sandbox seeded from real state) and a relayer or observer willing to resubmit the captured `SignedDelegateAction`. This is a narrower precondition than the original report's scenario (a single contract deployed identically to two live L1/L2 chains sharing the same EOA address space), since nearcore mainnet/testnet do not normally share account state. The likelihood is therefore low-to-moderate and highly dependent on deployment/operational practices (forks, snapshots, multi-network reuse of the same keys), rather than being exploitable against the standard single mainnet + testnet topology.

### Recommendation
Include a chain-specific value (e.g., the chain's genesis hash or a configured `chain_id`) in the `SignableMessage`/`DelegateAction` payload that is hashed and signed, similar to how ordinary transactions are scoped by a recent `block_hash`. This would make a `SignedDelegateAction`/`VersionedSignedDelegateAction` cryptographically bound to the specific chain it was authorized for, preventing replay across any other nearcore-based deployment even when account/key state happens to coincide.

### Proof of Concept
1. On chain A, a user signs a `DelegateAction` (`sender_id=alice.near`, `nonce=N`, `actions=[Transfer{...}]`) via `SignedDelegateAction::sign` [8](#0-7) , and a relayer submits it, advancing `alice.near`'s access key nonce past `N` on chain A.
2. Chain B is a separate nearcore-based network (fork/snapshot/other deployment) where account `alice.near` exists with the same public key and an access key nonce still `< N` (e.g., seeded from an earlier state snapshot of chain A, or independently created with a lower nonce).
3. An observer/relayer takes the identical `SignedDelegateAction` bytes captured from chain A and wraps them in a new outer `SignedTransaction` (with a valid `block_hash`/nonce for chain B) and submits it to chain B.
4. `apply_delegate_action` on chain B calls `signed_delegate_action.verify()` [9](#0-8) , which succeeds because the hashed payload has no chain-binding data, and `validate_delegate_action_key` accepts nonce `N` since chain B's stored nonce is still `< N` [10](#0-9) , causing the delegated `Transfer` (or other action) to execute again on chain B without a fresh authorization from `alice.near` for that chain.

pub(crate) fn apply_delegate_action(
    state_update: &mut TrieUpdate,
    apply_state: &ApplyState,
    action_receipt: &VersionedActionReceipt,
    sender_id: &AccountId,
    signed_delegate_action: VersionedSignedDelegateActionRef<'_>,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    if !signed_delegate_action.verify() {
        result.result = Err(ActionErrorKind::DelegateActionInvalidSignature.into());
        return Ok(());
    }
    let delegate_action = signed_delegate_action.delegate_action();
    if apply_state.block_height > delegate_action.max_block_height() {
        result.result = Err(ActionErrorKind::DelegateActionExpired.into());
        return Ok(());
    }
    if delegate_action.sender_id().as_str() != sender_id.as_str() {
        result.result = Err(ActionErrorKind::DelegateActionSenderDoesNotMatchTxReceiver {
            sender_id: delegate_action.sender_id().clone(),
            receiver_id: sender_id.clone(),
        }
        .into());
        return Ok(());
    }
