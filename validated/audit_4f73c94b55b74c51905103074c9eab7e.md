## Analog Found

### Title
Permissionless `Initialize2` allows squatting/front-running of AMM pools via attacker-chosen `market` seed - (File: `program/src/processor.rs`)

### Summary
`process_initialize2` derives all of the pool's core accounts (`AmmInfo`, `TargetOrders`, LP mint, coin/pc vaults) as PDAs seeded solely by the `market_info.key` pubkey supplied in the instruction, and the instruction can be invoked by any signer with no authorization check tying the caller to that market. This mirrors the reported `DebtToken.mint` bug class: a function that should require authorization (like `create`) is reachable by anyone with an attacker-chosen id, letting an attacker pre-empt/squat the id and permanently block the legitimate action for that id.

### Finding Description
`process_initialize2` accepts a `market_info` account that is explicitly documented as unchecked filler: [1](#0-0) [2](#0-1) 

That `market_info.key` is then used as the sole seed (together with fixed suffixes like `AMM_ASSOCIATED_SEED`, `LP_MINT_ASSOCIATED_SEED`, `TARGET_ASSOCIATED_SEED`) to derive the PDA addresses for the AMM account, LP mint, target-orders account and vaults: [3](#0-2) 

The account-creation helper only checks that the derived PDA matches the address seeded from `market_account.key`, and that the account is not already owned by the program (`RepeatCreateAmm`) — there is no check that the caller is authorized to create a pool for that specific `market_info` value: [4](#0-3) 

`process_initialize2` itself only checks that the signer (`user_wallet_info`) is a signer, that the config/fee/authority PDAs match, and that supplied mints differ — it never validates that the caller has any special relationship to `market_info`: [5](#0-4) 

Because the AMM/target-orders/LP-mint/vault PDAs are permanently and uniquely bound to the `market` pubkey, and the `generate_amm_associated_*` helpers reject re-creation once owned by the program (`RepeatCreateAmm`), the first caller to submit `Initialize2` for a given `market` pubkey permanently claims that pool's PDA space. This is directly analogous to the reported issue: an unprivileged function (`mint`/`Initialize2`) that should be gated the same way as an authorized-only counterpart (`create`) is left open, letting an attacker mint/claim an arbitrary id (token id / market-seeded PDA) ahead of the legitimate party and halt/deny their subsequent operation.

### Impact Explanation
Any unprivileged actor can front-run the creation of a Raydium pool for any target OpenBook/Serum market by calling `Initialize2` first with that market's pubkey and a minimal amount of coin/pc tokens (only constrained by the non-zero-vault check). Once initialized, the PDAs for `AmmInfo`, LP mint, target orders, and vaults for that market are permanently owned by the program, so any subsequent legitimate `Initialize2` call for the same market fails with `RepeatCreateAmm`, permanently preventing the real pool from ever being created at the canonical address. Integrators, aggregators, and end users who rely on the deterministic PDA address for a given market are permanently denied the legitimate pool, which is a durable denial-of-service against the protocol's core pool-creation flow.

### Likelihood Explanation
The `market_info` account has no ownership or program validation and is described in code comments as usable by "any account." Any signer with minimal token amounts can front-run pool creation for a specific market pubkey merely by observing an upcoming legitimate `Initialize2` transaction in the mempool (or predicting a market that will be used) and submitting their own `Initialize2` first. No privileged key or special access is required, and the transaction is a single instruction reachable by anyone.

### Recommendation
Add validation in `process_initialize2` that `market_info` is genuinely owned by the expected market program (e.g., check `market_info.owner == openbook_program::id()` or equivalent) and/or restrict pool creation to an authorized creator (similar to the fix applied for `DebtToken.mint`, which made the function internal/authorization-gated). At minimum, the accepted market account should be validated as a real market account before being used to derive and permanently claim the pool's PDA space.

### Proof of Concept
1. Attacker observes (or anticipates) that a legitimate project intends to create a Raydium pool for market `M`.
2. Attacker submits `Initialize2` with `market_info = M`, their own wallet as `user_wallet_info`, and minimal `init_coin_amount`/`init_pc_amount` (just enough to pass the non-zero vault check).
3. `generate_amm_associated_account`/`generate_amm_associated_spl_mint`/`generate_amm_associated_spl_token` succeed because the PDAs derived from `M` are unowned, and the attacker's transaction completes, permanently assigning the `AmmInfo`, LP mint, target-orders, and vault PDAs for market `M` to the attacker-initialized pool.
4. When the legitimate project later calls `Initialize2` for the same market `M`, `generate_amm_associated_account` finds the PDA already owned by the program and returns `AmmError::RepeatCreateAmm`, permanently blocking legitimate pool creation for that market.

    fn generate_amm_associated_account<'a, 'b: 'a>(
        program_id: &Pubkey,
        assign_to: &Pubkey,
        market_account: &'a AccountInfo<'b>,
        associated_token_account: &'a AccountInfo<'b>,
        user_wallet_account: &'a AccountInfo<'b>,
        system_program_account: &'a AccountInfo<'b>,
        _rent_sysvar_account: &'a AccountInfo<'b>,
        associated_seed: &[u8],
        data_size: usize,
    ) -> ProgramResult {
        let (associated_token_address, bump_seed) = get_associated_address_and_bump_seed(
            &program_id,
            &market_account.key,
            associated_seed,
            program_id,
        );
        if associated_token_address != *associated_token_account.key {
            msg!("Error: Associated token address does not match seed derivation");
            return Err(AmmError::ExpectedAccount.into());
        }
        if associated_token_account.owner == system_program_account.key {
            let associated_account_signer_seeds: &[&[_]] = &[
                &program_id.to_bytes(),
                &market_account.key.to_bytes(),
                associated_seed,
                &[bump_seed],
            ];
            let rent = Rent::get()?;
            let required_lamports = rent
                .minimum_balance(data_size)
                .max(1)
                .saturating_sub(associated_token_account.lamports());
            if required_lamports > 0 {
                invoke(
                    &system_instruction::transfer(
                        user_wallet_account.key,
                        associated_token_account.key,
                        required_lamports,
                    ),
                    &[
                        user_wallet_account.clone(),
                        associated_token_account.clone(),
                        system_program_account.clone(),
                    ],
                )?;
            }
            invoke_signed(
                &system_instruction::allocate(associated_token_account.key, data_size as u64),
                &[
                    associated_token_account.clone(),
                    system_program_account.clone(),
                ],
                &[&associated_account_signer_seeds],
            )?;
            invoke_signed(
                &system_instruction::assign(associated_token_account.key, assign_to),
                &[
                    associated_token_account.clone(),
                    system_program_account.clone(),
                ],
                &[&associated_account_signer_seeds],
            )?;
        } else {
            associated_token_address.log();
            return Err(AmmError::RepeatCreateAmm.into());
        }
        Ok(())
    }
