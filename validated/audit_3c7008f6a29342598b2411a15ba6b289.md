## Title
`validateStellarAddress` lacks base32/CRC16 checksum verification, allowing malformed Stellar addresses to pass `validateAddress` - (File: `packages/intents-sdk/src/lib/validateAddress.ts`)

### Finding Description
`validateStellarAddress` only checks the shape `/^G[A-Z0-9]{55}$/` with no base32 decode or CRC16 checksum verification, unlike other chains in the same file that do verify checksums (e.g. `validateBtcBase58Address`, `validateTronBase58Address`, `validateLitecoinBase58Address`, `validateDashAddress` all verify double-SHA256 checksums before returning `true`). [1](#0-0) 

For `PoaBridge.validateWithdrawal`, once `validateAddress` returns `true`, the flow proceeds to POA's supported-tokens/min-amount checks and (for XRPL only) an on-chain sanity check; there is no Stellar-specific on-chain verification in `PoaBridge`, so a malformed-but-regex-matching Stellar string would pass all local checks. [2](#0-1) 

For `HotBridge.validateWithdrawal`, after `validateAddress` passes, Stellar destinations go through `this.hotSdk.stellar.isTrustlineExists(destinationAddress, token)`, which is a call into the external `@hot-labs/omni-sdk` package (not in this repo). [3](#0-2) 

I could not locate the implementation of `HotOmniSdk`'s `stellar.isTrustlineExists` in this repository — it lives in the third-party `@hot-labs/omni-sdk` dependency, which is out of scope per the audit rules ("defects inside... third-party SDKs with no path through this repo"). Whether that external call rejects a checksum-invalid strkey (most Stellar SDKs' `StrKey.decodeEd25519PublicKey`/Horizon account lookups do perform CRC16 validation and would throw/404 on a bad checksum) cannot be verified from this codebase, so I cannot confirm that the "bad-CRC16-but-regex-valid" string actually survives `isTrustlineExists` to reach `buildGaslessWithdrawIntent` unmodified via the HOT path.

For the regex-format bug itself (independent of the trustline call), the receiver is indeed forwarded unmodified into `buildGaslessWithdrawIntent({ receiver: args.withdrawalParams.destinationAddress, ... })` with only a same-value amount sanity `assert`, no address re-validation. [4](#0-3) 

### Impact Explanation
If a checksum-invalid but format-matching Stellar address ('G' + 55 alphanumeric chars) is accepted by `validateAddress`, and no downstream layer (POA's bridge API, HOT's `isTrustlineExists`, or the Stellar network's own transaction submission) rejects it, funds would be misrouted to a string that decodes to no real ed25519 public key — an unrecoverable loss, matching "funds delivered to a wrong address... with no recovery" (Critical). This is a real gap in `validateAddress`'s Stellar path.

### Likelihood Explanation
For the `PoaBridge` route, `validateWithdrawal` performs no additional Stellar-specific verification beyond `validateAddress` and the POA HTTP API's own token/min-amount checks — I found no code in this repo that would independently verify the Stellar checksum for POA-routed Stellar withdrawals. Whether the POA bridge's remote HTTP service (`poaBridge.httpClient.getWithdrawalEstimate`/withdrawal submission) validates the checksum server-side is outside this repo and cannot be confirmed or denied here (it's an external bridge API, explicitly out of scope per the rules).

For the `HotBridge` route, the only Stellar-specific gate is `isTrustlineExists`, which lives entirely in the external `@hot-labs/omni-sdk` and is out of scope for this repo's audit ("defects inside... third-party SDKs with no path through this repo"). I cannot confirm within this repository whether that call would reject a bad-checksum address before or after constructing the withdrawal intent.

### Recommendation
Harden `validateStellarAddress` in `packages/intents-sdk/src/lib/validateAddress.ts` to perform a real Stellar strkey decode: base32-decode the address, verify the version byte (`0x30` for `G`/ed25519 public key), verify the CRC16-XModem checksum over version+payload, and confirm total decoded length (35 bytes: 1 version + 32 payload + 2 checksum), mirroring the checksum-verification pattern already used for Bitcoin/Tron/Litecoin/Dash addresses in the same file.

### Proof of Concept
Not provided as a full finding — see analysis: the regex-only weakness in `validateStellarAddress` is real and verifiable directly, but the question's specific chain to `HotBridge.createWithdrawalIntents`/`buildGaslessWithdrawIntent` depends on the behavior of `isTrustlineExists`, whose implementation is in the external `@hot-labs/omni-sdk` package and not present in this repository's index. A vitest test confirming `validateAddress(badChecksumAddress, Chains.Stellar) === true` is straightforward and would succeed given the current regex-only implementation; asserting that `HotBridge.createWithdrawalIntents` forwards it unchanged additionally requires mocking `hotSdk.stellar.isTrustlineExists` to resolve `true` (bypassing that external check), at which point the forwarding behavior shown in `hot-bridge.ts` lines 224-251 does confirm the receiver is passed through unmodified.
