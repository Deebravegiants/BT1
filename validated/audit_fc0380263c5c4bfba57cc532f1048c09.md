### Title
Webhook Authenticity Is Verified Only Over the Raw Body, Allowing the `shop`, `topic`, and `webhook_id` Fields to Be Forged Independently of the HMAC - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook request as authenticated ("verified to come from Shopify") once `Utils::HmacValidator.validate` succeeds, and hands the handler a `WebhookMetadata` struct whose `shop` field is documented as "The shop domain of the webhook". However, the HMAC signature only covers the raw request body — the `shop-domain`, `topic`, `webhook_id`, and `api_version` header fields are never part of the signed material, so they can be swapped after a legitimately signed payload is obtained.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from unauthenticated HTTP headers: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (the body) and compares it against the `hmac-sha256` header: [3](#0-2) 

`Registry.process` gates on that same HMAC check and then constructs `WebhookMetadata` directly from `request.shop`, `request.topic`, and `request.webhook_id` — none of which were part of the signed bytes: [4](#0-3) 

This is the binding break called out in the rules: **bytes verified (raw body) vs. bytes/fields acted on (`shop-domain`, `topic`, `webhook_id` headers)**. The equality that should hold — "the shop identity Shopify signed for" == "the shop identity the handler receives" — does not, because the signature never covers the shop identity at all.

The gem's own documentation reinforces the false sense of binding: it states that `Registry.process` "will verify the request did indeed come from Shopify" and lists `data.shop` as a trustworthy field for the handler to act on: [5](#0-4) [6](#0-5) 

### Impact Explanation
An attacker who controls any single shop that has this app installed (an "unprivileged internet user" relative to other merchants, just an app user on their own tenant) can trigger a legitimate webhook for their own store — this produces a validly signed body/HMAC pair. Because the signature does not cover `shop-domain`, `topic`, or `webhook_id`, the attacker can replay that exact signed body to the app's webhook endpoint while substituting a different `shop-domain` (and/or `topic`/`webhook_id`) header. `HmacValidator.validate` still succeeds (it only checks the body), and the handler receives `WebhookMetadata` claiming the payload originated from an arbitrary victim shop. Any handler logic that scopes tenant data, deduplication, or state transitions by `data.shop` (as the docs instruct: `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) can be made to attribute attacker-supplied content to a different merchant's tenant — a cross-tenant confusion primitive rooted entirely in this gem's signature scope.

### Likelihood Explanation
Likelihood is moderate to high: exploitation only requires the attacker to operate their own Shopify store with the target app installed (no leaked secrets, no privileged access, no TLS interception), capture one legitimate webhook delivery, and resend it with edited headers to the app's public webhook endpoint. The gem performs no additional binding check between body and headers.

### Recommendation
Include the security-relevant headers (`shop-domain`, `topic`, `webhook_id`, `api_version`) in the HMAC-signed material, or otherwise cryptographically bind them to the body before exposing them via `WebhookMetadata`, so that `Registry.process` cannot be tricked into attributing an attacker-controlled payload to an arbitrary shop.

### Proof of Concept
1. Attacker's own store `attacker.myshopify.com` has the vulnerable app installed and webhooks registered (e.g., `orders/create`).
2. Attacker performs an action that triggers a real webhook delivery; Shopify computes `hmac-sha256` over the JSON body using the app's `client_secret` and sends headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-topic: orders/create`, `x-shopify-hmac-sha256: <valid>`.
3. Attacker intercepts/replays this exact body+HMAC to the app's webhook endpoint but rewrites `x-shopify-shop-domain` to `victim.myshopify.com` (and/or changes `x-shopify-webhook-id`/`x-shopify-topic`).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `raw_body` against the signature — validation passes.
5. The registered handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", topic: ..., body: <attacker's order data>, ...)`, believing the payload is authentic for `victim.myshopify.com`, per: [4](#0-3)

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
