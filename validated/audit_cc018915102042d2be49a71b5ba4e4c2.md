## Finding

### Title
Webhook `shop` (and `topic`/`webhook_id`) header values are trusted for tenant identification without being covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then uses the unauthenticated `shop-domain` header value as the tenant identifier passed to the app's handler. Because the signature never covers this header, an attacker who can obtain any single valid `(body, hmac)` pair for the configured `client_secret` can replay it with an arbitrary `shop-domain` header and have the handler believe the payload originated from a different (victim) shop.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes and compares an HMAC over `verifiable_query.to_signable_string`: [1](#0-0) 

For webhook requests, `to_signable_string` returns only the raw HTTP body: [2](#0-1) 

But `shop`, `topic`, `api_version`, and `webhook_id` are all read straight from HTTP headers, which are never part of the signed material: [3](#0-2) 

`Registry.process` validates only the HMAC (i.e., only the body) and then forwards the *unauthenticated* `request.shop` value straight to the app's handler as the tenant identity: [4](#0-3) 

This is precisely the identity-binding break the report class describes: a field (`shop`) that is acted upon (used as the tenant key passed to `WebhookMetadata`) is not covered by the cryptographic check (`HmacValidator.validate` only signs `@raw_body`). The equality that should hold — `authenticated_bytes == bytes_the_handler_trusts_for_tenant_identity` — does not hold, because `authenticated_bytes` is the body while `bytes_the_handler_trusts_for_tenant_identity` is the `shop-domain` header.

### Impact Explanation
Any actor who can obtain one legitimately-signed webhook body for the app (e.g. by installing the app on their own store and receiving a real webhook, or by triggering any webhook topic on a shop they control) can capture that `(raw_body, hmac)` pair. Because the HMAC is independent of the `shop-domain`, `topic`, and `webhook_id` headers, the attacker can resend the identical body/HMAC to the app's webhook endpoint while setting the `shopify-shop-domain` header (and/or `shopify-topic`, `shopify-webhook-id`) to any value they choose. `Registry.process` will accept it as valid (HMAC check passes) and hand the handler a `WebhookMetadata` claiming to be from an arbitrary shop, causing the host application to act on/store data under the wrong tenant — i.e., cross-tenant data confusion/injection using data the attacker fully controls.

### Likelihood Explanation
Any developer/merchant that can install the app on a shop they control (a normal, low-privilege action) can generate a validly-signed webhook for arbitrary body content of their choosing (e.g. an `orders/create` webhook with attacker-chosen JSON) and then replay it against the app's public webhook endpoint with a spoofed `shop-domain` header. No access to `api_secret_key`, access tokens, or the target shop's credentials is required.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signed material verified by the HMAC check, or otherwise cryptographically bind the header-derived tenant identity to the signed payload before it is handed to application handlers (e.g., require that `shop` matches an out-of-band verified session/shop registered for that webhook subscription, not solely a header value accompanying a body-only HMAC).

### Proof of Concept
1. Install the app on `attacker-shop.myshopify.com` (a shop the attacker fully controls) and capture any incoming webhook, e.g. `orders/create`, with its raw body and the `X-Shopify-Hmac-Sha256` value — both are valid because they were generated by real Shopify infrastructure using the app's `client_secret`.
2. Craft an HTTP POST to the app's webhook endpoint using the exact same raw body and HMAC header, but replace the `X-Shopify-Shop-Domain` header with `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb:189-190`) calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks the (unchanged) raw body against the HMAC.
4. The handler receives `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body: <attacker-controlled>, ...)` and the host application processes attacker-controlled data as if it came from `victim-shop.myshopify.com`.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
