Confirmed: `Registry.process` dispatches to a handler using `request.topic` and `request.shop`, both taken directly from HTTP headers, while `HmacValidator.validate` only authenticates `request.to_signable_string`, which returns the raw body exclusively.### Title
Webhook `shop` and `topic` identity fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/registry.rb`, `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely via `Utils::HmacValidator.validate(request)`, which computes/verifies the HMAC only over `request.to_signable_string` (the raw body). It then dispatches the handler using `request.shop` and `request.topic`, both of which are read directly from HTTP headers that are never included in the signed material. This breaks the intended identity binding `shop authenticated == shop acted upon`, allowing a party who already possesses one validly-signed webhook body/signature pair to relabel it for any tenant/topic.

### Finding Description
`HmacValidator.validate` computes the signature exclusively from `verifiable_query.to_signable_string`: [1](#0-0) 

`Webhooks::Request#to_signable_string` returns only the raw body, while `shop`, `topic`, `api_version`, and `webhook_id` are parsed straight from unauthenticated headers: [2](#0-1) 

`Registry.process` then trusts these unauthenticated header-derived fields to select the handler and to build `WebhookMetadata` for it, without verifying that `shop`/`topic` were part of the signed payload: [3](#0-2) 

The identity binding that should hold is:
`HMAC-verified(bytes) == bytes that determine the tenant (shop) and business action (topic) dispatched to the handler`

Here, the HMAC only verifies the body bytes, while `shop` and `topic` — the two fields that determine *which tenant* and *which business event* the handler executes for — come from headers outside that verified scope. Any request whose body produces a valid signature (e.g., a webhook the attacker's own shop legitimately received, since the same `api_secret_key` signs all webhooks for the app across every installed shop) can be replayed with arbitrary `shop-domain`/`topic`/`webhook-id` header values and will still pass `HmacValidator.validate`, since those headers never entered the signable string.

### Impact Explanation
A merchant who has the app installed on their own store (an unprivileged actor relative to other tenants) can capture one genuinely HMAC-signed webhook delivery and replay it directly to the app's public webhook endpoint with the `shopify-shop-domain` header changed to a victim shop and/or the `shopify-topic` header changed to a different registered topic. `Registry.process` will treat this as an authentic event for the victim shop/topic and invoke the app's handler with attacker-controlled `WebhookMetadata#shop`/`#topic`, while `#body` is only constrained to be *some* body the attacker already had a valid signature for. This crosses the tenant boundary the HMAC check is supposed to enforce, matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is bounded by the attacker needing at least one legitimately signed webhook payload, which any merchant with the app installed can obtain for free (Shopify sends many webhooks automatically, e.g. `app/uninstalled`, `shop/update`), and no `access_token`, `client_secret`, or other privileged credential is required — only the ability to POST to the app's own public webhook endpoint with modified headers.

### Recommendation
Include the identity-critical fields (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signed/verified material, or otherwise cryptographically bind them to the body, so that `Utils::HmacValidator.validate` fails whenever any of these headers are altered relative to what Shopify actually sent. At minimum, `Webhooks::Request#to_signable_string` should incorporate `shop`, `topic`, and `webhook_id` so `Registry.process` cannot dispatch attacker-controlled tenant/topic values under a signature that only covers the body.

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com`; capture any inbound webhook POST (body `B`, header `x-shopify-hmac-sha256: H`, where `H = HMAC(secret, B)`).
2. Replay the identical request to the app's webhook endpoint, but set:
   - `x-shopify-shop-domain: victim.myshopify.com`
   - `x-shopify-topic: <topic of interest, e.g. app/uninstalled or orders/create>`
   - Keep body `B` and hmac header `H` unchanged.
3. `HmacValidator.validate` recomputes `HMAC(secret, B)`, which still equals `H`, so validation passes: [4](#0-3) 
4. `Registry.process` looks up the handler for the forged topic and invokes it with `shop: "victim.myshopify.com"`, `topic: <forged topic>`: [3](#0-2) 
5. The app's business logic executes as if Shopify itself sent this event for `victim.myshopify.com`, even though nothing about `shop` or `topic` was ever cryptographically verified.
