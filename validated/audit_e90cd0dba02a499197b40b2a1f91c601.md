### Title
Spot-reserve Aquarius LP pricing lets an unprivileged user inflate LP collateral value within the sanity band - (File: contracts/price-aggregator/src/providers/aquarius.rs)

### Summary
The Notional bug class is an oracle value computed from the most recent manipulable state instead of a time-weighted average. XOXNO Lending reproduces this shape in its Aquarius LP pricing: `read()` prices an LP share from the pool's *current* `get_reserves()` and `get_total_shares()` with no smoothing, no TWAP, and no tolerance check (LP sources are exempted from both). An unprivileged user can move the fair price inside the wide configured sanity band by donating underlying tokens directly to the pool contract between the reserve read and the borrow, over-valuing LP collateral to borrow beyond its real worth.

### Finding Description
`contracts/price-aggregator/src/providers/aquarius.rs::read` resolves the two leg prices, then reads `aquarius_pool_reserves_call` and `aquarius_total_shares_call` in the same transaction and feeds them into `fair_lp_price_wad` / `fair_stable_lp_price_wad`. The price is therefore a pure spot function of live pool reserves — exactly the "relies only on the latest state" pattern of `updateRateOracle`.

- Constant product: `total_value = 2 * sqrt(value_a * value_b)` (`common/src/oracle/lp.rs:75-84`). Donating token A to the pool raises `value_a` without minting shares; the fair price scales as `sqrt(1 + donation/reserve_value)`. To double the LP price an attacker donates ~3× one leg's value.
- Stable: `fair = D * min(price_a, price_b) / share_supply` (`common/src/oracle/lp_stable.rs:96-109`). `D` grows roughly linearly with total normalized reserves, so a one-sided donation inflates the LP price almost linearly — far cheaper per unit of manipulation.

Crucially, LP sources are exempted from the two defenses other oracles get: `validate_asset_oracle` skips `validation::smoothing` and `validate_oracle_tolerance` whenever the oracle has an Aquarius LP source (`contracts/price-aggregator/src/admin.rs:181-197`), so there is no TWAP requirement and no dual-source deviation check. The only bound is `min/max_sanity_price_wad`, and deployed bands are very wide — e.g. mainnet XLMAQUA_LP spans `5_356_670_329_052_813` to `53_566_703_290_528_136` WAD, a 10× range (`configs/ops/mainnet/a1795e5298bbbc23c4a02605f08b51db656a9e671e8845b160130d3b2853f44c.json:43-44`), and `MAX_LP_SANITY_BAND_BPS` permits this.

An unprivileged attacker path:

1. Supply LP shares of an Aquarius-backed market as collateral via controller `supply` (or use existing collateral).
2. In the same ledger, transfer the cheaper/underlying token directly to the Aquarius pool address (a plain `token.transfer`, allowed to any address), inflating `get_reserves()` while `get_total_shares()` is unchanged.
3. Call controller `borrow`, which resolves the LP price through the aggregator and values the collateral at the inflated fair price, then withdraw the borrowed assets.
4. Later, redeem their own LP shares (attacker-held share fraction recovers a pro-rata part of the donation); the remainder is the manipulation cost.

Because the read is spot, there is no window the attacker must maintain — analogous to the report's guarantee that the manipulated "last state" is what gets consumed.

### Impact Explanation
Inflating collateral price inside the sanity band lets the attacker pass `calculate_account_risk_totals`/`MinBorrowCollateralNotMet` checks with collateral whose true value is far lower, and borrow assets worth more than the collateral. The position is immediately undercollateralized once the donation stops being counted; even after liquidation, residual bad debt is socialized to suppliers via `apply_bad_debt_to_supply_index`. This is theft of user funds / protocol insolvency.

### Likelihood Explanation
Requires that an Aquarius LP token is listed as collateral with a wide sanity band (mainnet deployments show bands up to ~10×) and that the attacker can fund a donation large enough to move the spot price to a profitable level. For stable pools the cost is roughly linear in the target overvaluation; the attacker can also pre-own most of the LP supply so donation cost is largely recycled. No privileged access, timing window, or third-party cooperation is needed — only own token transfers and normal controller calls.

### Recommendation
Do not price LP shares from raw spot reserves alone. Options: require `min_pool_value_wad` to be high and tighten LP sanity bands toward parity; validate that `get_reserves()` matches token balances expected from share accounting (reject donation-inflated reads where Aquarius exposes a distinct reserve accounting vs balance); or value LP collateral at the *lower* of fair price and the min leg-value-implied price (`2*min(v_a, v_b)` for CP, which donations of a single leg cannot inflate at all).

### Proof of Concept
1. Deployed mainnet oracle for XLMAQUA_LP: single `AquariusLp` source, sanity band `[5.35e15, 5.35e16]` WAD.
2. `aquarius.rs::read` (lines 90-114): `reserve_a, reserve_b` come from `try_get_reserves()` at read time; `fair_lp_price_wad` computes `2*sqrt(v_a*v_b)/shares`.
3. `admin.rs:191-197`: `smoothing` and tolerance validation skipped for LP oracles — no TWAP records, no second leg to disagree.
4. Attacker supplies 1,000 LP shares (true price P). Donates XLM to the pool until `value_a` is 9× → fair price ≈ 3P, still under the 10× band → `resolve` returns 3P.
5. `borrow` against collateral now valued at 3× → withdraw; let position go bad; suppliers absorb via supply-index write-down (`contracts/pool/src/interest.rs:73-89`).
