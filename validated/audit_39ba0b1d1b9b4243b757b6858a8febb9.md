## Title
Simplex Uniswap V4 venue pricing uses unprotected pool spot price (`sqrtPriceX96`/`token0Price`/`token1Price`) for LP-funded fills, guarded only by a static reference deviation check rather than a manipulation-resistant TWAP - (File: `sdk/packages/simplex/src/funding/uniswapV4/UniswapV4FundingPlanner.ts`)

### Summary
The Real Wagmi finding is a `slot0`-manipulation bug: reading the pool's *current* `sqrtPriceX96`/tick to price LP shares lets an attacker move the spot price in one transaction and skew a downstream mint/withdraw calculation. Hyperbridge's Simplex solver has the same root-cause pattern: `UniswapV4FundingPlanner.computeDirectPoolPriceUsd` derives the USD price of an "exotic" token directly from the live Uniswap V4 pool's spot mid (`sdkPool.token0Price`/`token1Price`, itself computed from `sqrtPriceX96`), and that price is used both to quote/accept an order (`resolveLegRates` in `fx.ts`) and to size the on-chain liquidity withdrawal that funds the fill (`planWithdrawalForToken`). The only defense is `checkPriceGuard`, which compares the live quote against a static, operator-configured `referencePrice`/`maxDeviationBps` — not a TWAP, not an execution-cost-aware check, and not tied to the actual trade size or pool depth.

### Finding Description
`getExoticTokenPrice` → `computeDirectPoolPriceUsd` reads the pool's current mid price straight off `V4Pool.token0Price`/`token1Price`, which is derived from the pool's current `sqrtPriceX96` (functionally the V4 analogue of Uniswap V3's `slot0`): [1](#0-0) 

That price feeds `resolveLegRates`, which is the only pricing path for curveless pairs, and is validated solely against a static reference: [2](#0-1) 

The documented design confirms the guard checks deviation from a static reference, not execution cost or size impact, and that the "raw pool mid" is used with no size/impact term: [3](#0-2) 

Critically, the *same* live pool state (refreshed immediately before planning) also determines how much liquidity is withdrawn to physically fund the fill: [4](#0-3) [5](#0-4) 

Because the withdrawal and the order fill are executed atomically as ERC-7821 batch calls prepended to the same UserOperation: [6](#0-5) 

an unprivileged order submitter can, within (or immediately ahead of, in the same block) the transaction that triggers a solver's fill, move the pool's spot price via a swap so that: (1) the quote accepted by `resolveLegRates`/`referenceRate` is skewed but still inside `maxDeviationBps` of the static `referencePrice`, and (2) `computeDirectPoolPriceUsd`/`getExoticTokenPrice` misprices the token used to size the liquidity decrease in `planWithdrawalForToken`. This lets the attacker cause the solver to withdraw and hand over more of the exotic token than the fair value of the order, extracting value from the solver's Uniswap V4 position in a single atomic sequence — exactly the "most recent data point, extremely easy to manipulate" pattern described in the source report, just applied to Simplex's LP-funded pricing path instead of Real Wagmi's `Multipool`.

### Impact Explanation
A manipulated spot price used both for acceptance pricing and for sizing the physical LP withdrawal lets an attacker extract funds from the solver's Uniswap V4 inventory beyond what a fair/TWAP price would allow, since the only defense (`checkPriceGuard`) is a static-reference bound, not a manipulation-resistant oracle and not scaled to the trade's price impact or the pool's fee tier. This is a concrete funds-theft vector against solver-held liquidity reachable from a single dispatched intent/order — matching the "concrete theft ... unauthorized app action" acceptance criteria.

### Likelihood Explanation
Likelihood is bounded by two factors that reduce but do not eliminate exploitability: (a) `checkPriceGuard`'s `maxDeviationBps` limits how far the attacker can push the price before the order is simply rejected, and (b) the withdrawal and fill happen atomically in the *same* UserOperation, so the attacker would need to influence pool state either just before that atomic bundle lands or via a hook/flash-swap nested inside the batch itself. Within the allowed deviation band, however, no size- or fee-tier-aware check exists, and thin/less-liquid pools (the intended target of this whole funding path, since it exists specifically for "exotic" long-tail tokens) are the easiest to move meaningfully within a bounded percentage. This is realistically triggerable by any order submitter targeting a venue-priced pair with an LP position configured, without any privileged role.

### Recommendation
Do not price LP-funded fills or size liquidity withdrawals from the pool's instantaneous spot price alone. Use a time-weighted average price (TWAP) over a manipulation-resistant window (as Uniswap V4 pools/hooks or an external TWAP oracle can provide) for `computeDirectPoolPriceUsd`, and make `checkPriceGuard` deviation checks relative to that TWAP rather than (or in addition to) a static operator-set `referencePrice`. Additionally, scale the guard's tolerated deviation to the trade's notional size and the pool's available depth/fee tier so a large withdrawal cannot be sized off a price that is only "not too far" from a stale reference but still meaningfully manipulated for that specific withdrawal size.

### Proof of Concept
1. Operator configures a `[vault.uniswapV4]` position for a thin exotic/USD pool with `referencePrice`/`maxDeviationBps` set generously (or the pool naturally trades within that band).
2. Attacker submits (or arranges for) a swap against the same V4 pool that moves `sqrtPriceX96` so `token0Price`/`token1Price` shifts favorably, while staying within `maxDeviationBps` of the static `referencePrice` — passing `checkPriceGuard`.
3. Attacker places/triggers an order on Simplex targeting that curveless pair. `resolveLegRates` prices the leg from the manipulated venue quote (`sdkPool.token1Price`/`token0Price`), and `getExoticTokenPrice`/`computeDirectPoolPriceUsd` is used again when `planWithdrawalForToken` sizes the liquidity decrease needed to fund the fill.
4. Because withdrawal and fill execute atomically in one UserOperation, the solver's position is drained at the manipulated price, delivering more value to the attacker's output than the fair (TWAP) price would allow, with no additional check tying the guard's tolerance to trade size or pool depth.

Note: I could not fully inspect the body of `checkPriceGuard` itself (only its call sites and doc description were available within the index/tool budget), so the exact bound formula (e.g., whether it also considers pool liquidity) is inferred from the accompanying design note in `venue-pricing-uniswap-v4-funded-pairs.md` rather than directly read from the guard's implementation.

```typescript
			return {
				exoticToken: c0,
				priceUsd: new Decimal(sdkPool.token0Price.toFixed(18)),
			}
		}

		return null
	}
```

```markdown

`computeDirectPoolPriceUsd` returns the **raw pool mid** derived from `sqrtPriceX96`. The pool's
fee tier is read and stored on the hydrated position (`pos.fee`) but never applied to the price,
and there is no size or impact term — `computeLegPolicyOutput` extends the mid linearly across the
whole priced quantity. `checkPriceGuard` is the only defense on this path, and it checks deviation
from a static reference, not execution cost. A venue-priced pair that has to swap through its own
pool to source inventory pays a fee tier it never quoted against.
```

```text
When the solver's wallet balance on the destination chain is insufficient to fill an order, Simplex can automatically withdraw liquidity from on-chain positions to cover the deficit. Withdrawal calls are prepended to the UserOperation as ERC-7821 batch calls, making the funding atomic with the fill.

Configured under the top-level `[vault.uniswapV4]` block. Decreases liquidity from concentrated Uniswap V4 positions via PositionManager NFTs. Slippage tolerance is set by `spreadBps` (default 50 bps / 0.50%), deadline defaults to the order's deadline. Each position needs a `chain` and a `tokenId` (the ERC-721 position NFT ID); pool details are read on-chain at startup.
```
