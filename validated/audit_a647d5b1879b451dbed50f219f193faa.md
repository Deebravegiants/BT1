### Title
Webhook `shop` identity is taken from an unauthenticated header not covered by the HMAC - (File: lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies only that the raw request body matches its HMAC, then trusts the `shop-domain` header verbatim to attribute the webhook to a tenant, even though that header is never part of the HMAC-signed bytes.

### Finding Description
`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string`, and `Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
The `shop`, `topic`, and `webhook_id` accessors instead read straight from HTTP headers, which are not part of the signed payload at all: [2](#0-1) 
`Registry.process` validates the HMAC and, on success, unconditionally uses `request.shop` (the unverified header) to construct the `WebhookMetadata` handed to the app's handler: [3](#0-2) 

The identity binding that should hold is: `shop authenticated by HMAC == shop used for tenant-scoped processing`. Here, the HMAC only authenticates the byte-string `raw_body`; it does not authenticate which shop the payload is attributed to. Any party capable of capturing one legitimately-signed webhook body/HMAC pair (e.g., via a logging proxy, shared ngrok tunnel, misconfigured intermediary, or a webhook-forwarding service many merchants use) can replay that exact `raw_body` + `hmac-sha256` header pair while substituting an arbitrary `shop-domain` header. `HmacValidator.validate` will still return `true` because it never inspects the `shop` header, and `Registry.process` will hand the payload to the app's handler labeled as coming from the attacker-chosen shop.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to preserve for webhook delivery: an app that keys any per-shop side effect (writing to a shop's DB record, granting entitlements, triggering shop-scoped GDPR actions, etc.) off `WebhookMetadata#shop` can be made to apply another shop's genuine event data under a victim/attacker-chosen shop identifier, i.e., cross-tenant data ingestion despite HMAC verification passing. This matches the Critical criterion "cross-tenant access" since the HMAC check — the sole authentication mechanism offered by this gem for webhooks — gives a false sense that the entire `WebhookMetadata` (including `shop`) is authenticated.

### Likelihood Explanation
Exploitation requires the attacker to have observed one valid `raw_body`/`hmac-sha256` pair for any shop (not necessarily the target), which is plausible in setups using webhook relaying/logging proxies, shared development tunnels, or any component that can see raw webhook traffic without the `client_secret`. No access to `api_secret_key` or an access token is required, matching the analog's identity-binding-break class described in the report (a field acted upon — `shop` — not covered by the HMAC).

### Recommendation
Include the `shop-domain` header (and `topic`/`webhook_id` if they drive behavior) in the signable string used for HMAC verification, or otherwise cryptographically bind the shop identity to the signed payload before it is trusted in `Registry.process` and exposed via `WebhookMetadata#shop`.

### Proof of Concept
1. Capture (via any intermediary with visibility into raw webhook traffic) a legitimate webhook request: `raw_body = '{"id":123,...}'` with header `x-shopify-hmac-sha256: <valid signature over raw_body>` originally sent for `x-shopify-shop-domain: shop-a.myshopify.com`.
2. Replay the identical `raw_body` and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but set `x-shopify-shop-domain: shop-b.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds successfully; `Utils::HmacValidator.validate(request)` returns `true` because it only checks `raw_body` against the HMAC: [4](#0-3) 
4. `Registry.process` proceeds and calls the registered handler with `WebhookMetadata.new(topic:, shop: "shop-b.myshopify.com", body:, ...)`, i.e., shop-a's genuine event data is delivered and processed as if it belonged to shop-b. [5](#0-4)
