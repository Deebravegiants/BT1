Audit Report

## Title
Terminated-contract address can be indefinitely blocked from redeployment via strict-FIFO `DeletionQueue` head-of-line blocking (`PendingDepositCleanup`) - (File: `substrate/frame/revive/src/storage.rs`)

## Summary
`ContractInfo::new` rejects re-instantiation at an address whose fallback account still has `NativeDepositOf` rows pending cleanup, and those rows are only cleared by the lazy `on_idle` FIFO drain in `process_deletion_queue_batch`. Because the queue is a strict ring-buffer that never advances past an incomplete head entry, an attacker can permanently stall the queue behind slow-draining decoy entries, indefinitely blocking redeployment at a victim address.

## Finding Description
`ContractInfo::new` checks `NativeDepositOf::<T>::iter_prefix(&account_id).next().is_some()` and returns `Error::PendingDepositCleanup` if any row remains for the address's fallback account. [1](#0-0) 

These rows are cleared only via `process_deletion_queue_batch`, which loads `DeletionQueueManager` and calls `queue.next()`, which always returns the entry at the current `delete_counter` — never a later entry. [2](#0-1) 

The processing loop charges per-entry overhead, then attempts to fully drain `NativeDepositOf::clear_prefix` for the head entry; if `result.maybe_cursor.is_some()` (drain incomplete), it `break`s without removing the entry, leaving it at `delete_counter` for the next call. The same head-of-line blocking applies to phase 2 (`child::kill_storage`) via `KillStorageResult::SomeRemaining`. [3](#0-2) 

`remove()` only advances `delete_counter` by one, and only after both phases fully complete for that entry, confirming this is a strict FIFO with no skip-ahead or round-robin mechanism. [4](#0-3) 

I confirmed no `MaxDeletionQueueDepth`/queue-depth cap exists in `pallet_revive` to bound how many decoy entries an attacker can enqueue ahead of a victim, and confirmed `queue_for_deletion` simply appends via `insert()` at `insert_counter` with no ordering guard. [5](#0-4) [6](#0-5) 

None of the existing guards (`DuplicateContract`, weight metering, per-entry budgeting) address cross-entry ordering; they only bound work within a single `on_idle` call, not which entry is attempted next across calls. The exploit path is reachable through ordinary unprivileged extrinsics: instantiate contracts, grow storage across many distinct contributor accounts (seeding many `NativeDepositOf` rows per contract, as exercised by the existing `MultiContributorStorage` test fixture), terminate them to enqueue `DeletionQueueItem`s, then terminate the victim last so its entry lands behind the decoys in FIFO order. [7](#0-6) 

## Impact Explanation
This is a durable, attacker-sustained denial-of-service against a specific contract address: as long as the attacker keeps at least one slow-draining decoy ahead of the victim's `DeletionQueueItem`, `ContractInfo::new` will keep returning `PendingDepositCleanup` for that address, blocking redeployment (e.g., CREATE2-style deterministic-salt patterns). It also degrades global cleanup throughput for all entries behind the stuck head, since the shared queue cannot make progress past it. This matches an in-scope availability/denial-of-service impact in the `pallet_revive` contracts subsystem, reachable purely through normal user-level extrinsics (instantiate, storage writes, terminate) with no privileged access required.

## Likelihood Explanation
The attack is fully reachable by an unprivileged user: instantiate, storage growth, and self-termination are all standard user-triggered paths. The only cost is the deposit required to seed enough `NativeDepositOf` rows or child-trie entries per decoy to exceed a single `on_idle` weight budget — a bounded but non-prohibitive cost, and one the attacker can size to their own resources and refresh indefinitely by adding more decoys before the queue catches up. There is no protocol-level cap on deletion-queue depth or per-address drain time to prevent this.

## Recommendation
Decouple per-entry drain progress from strict head-of-line ordering — e.g., persist a resumable cursor per entry and enforce a bounded weight budget per entry per `on_idle` call, advancing to the next queue slot within the same call once that budget is exhausted rather than breaking out entirely. Alternatively, clear a terminated contract's `NativeDepositOf` prefix eagerly (or via a bounded first pass) at termination time, decoupling the `PendingDepositCleanup` check from the shared FIFO queue's global progress.

## Proof of Concept
1. Instantiate N decoy contracts using the `MultiContributorStorage` pattern; have K distinct contributor accounts each grow storage on each decoy to seed K `NativeDepositOf` rows and/or large child-trie storage per decoy.
2. Terminate all N decoys in order via `queue_for_deletion`, enqueuing their `DeletionQueueItem`s ahead of the victim's.
3. Instantiate the victim contract at a deterministic address `A`, grow its storage, then terminate it, placing its entry behind all decoys in the FIFO (`DeletionQueue::<Test>::iter().count() == N + 1`).
4. Attempt to re-instantiate at `A`; assert it fails with `Error::<Test>::PendingDepositCleanup` per the check at `storage.rs:205-212`.
5. Call `on_idle` repeatedly with a weight budget insufficient to fully drain the first decoy's `NativeDepositOf` prefix or child trie in one call (per the break conditions at `storage.rs:449` and `storage.rs:464-468`); after each call, re-attempt instantiation at `A` and confirm it still fails while any decoy entry remains ahead of it in the queue.
6. Scale N and K and observe that the number of `on_idle` calls required before `A` becomes redeployable grows with the pre-seeded backlog size, demonstrating attacker-controlled, unbounded delay rather than a fixed bound.
