### Title
Unrestricted route-selected contracts can add wallet-draining calls to the signer’s authorization tree - (File: contracts/controller/src/strategies/swap.rs)

### Summary
Controller swap strategies accept opaque caller-supplied route bytes and execute the route inside the caller’s `require_auth` context. [1](#0-0) [2](#0-1)  A malicious route pool can therefore request an unrelated token transfer from the victim during the swap, which simulation records as a child authorization and executes if the victim signs that tree. [3](#0-2) [4](#0-3) 

### Finding Description
`swap_collateral`, `swap_debt`, `multiply`, and `repay_debt_with_collateral` authenticate the caller, then pass attacker-influenced `swap` bytes into `swap_tokens`. [5](#0-4) [6](#0-5)  The controller authorizes only the router’s exact input transfer, but this does not isolate the caller’s authorization from later route-selected external calls. [2](#0-1)  Route decoding treats `idx_a` as an arbitrary asset-registry address and performs only index and structural validation, not venue or pool admission. [7](#0-6) [8](#0-7)  A Soroswap-labelled hop invokes caller-selected pool code through `get_reserves` and `swap`, and the dispatcher validates only the router’s token balance deltas afterward. [9](#0-8) [10](#0-9) [11](#0-10)  During that `swap` call, malicious pool code can invoke `wallet_token.transfer(victim, attacker, amount)`, which joins the victim’s authorization tree and executes if signed. [12](#0-11) [13](#0-12) 

### Impact Explanation
A victim who signs the simulated authorization tree loses arbitrary unrelated wallet tokens while still receiving a valid swap output and passing the controller’s final account checks. [14](#0-13) [15](#0-14)  The measured-output and minimum-output checks bound only the routed assets, not additional calls authorized beneath the victim’s top-level signature. [16](#0-15) [17](#0-16)  This is theft of user funds, with impact bounded by the token balances and malicious transfers included in the signed authorization tree. [18](#0-17) 

### Likelihood Explanation
An unprivileged attacker can deploy the malicious pool, encode it into a route, and distribute that route as a seemingly profitable swap. [19](#0-18) [20](#0-19)  Exploitation requires the victim to submit the poisoned route and sign a simulation whose authorization tree contains the extra transfer, so it depends on route-source deception or insufficient client-side authorization display. [14](#0-13)  The malicious hop can still satisfy the measured input/output and min-out checks, making the lending transaction itself succeed. [11](#0-10) [21](#0-20) 

### Recommendation
Constrain route pool addresses to a governance-managed venue/pool allowlist rather than accepting arbitrary `assets[idx_a]` contracts. [7](#0-6) [3](#0-2)  Until route contracts are allowlisted, clients must decode the complete payload and reject any authorization tree containing children other than the expected input transfer or expected controller authorization. [17](#0-16) 

### Proof of Concept
1. Deploy a malicious contract exposing `get_reserves` and Soroswap-compatible `swap`; `get_reserves` returns positive reserves, while `swap` calls `token::Client::new(env, wallet_token).transfer(victim, attacker, victim_balance)` and then transfers sufficient `token_out` to the router. [9](#0-8) [12](#0-11) 
2. Construct a strategy payload whose `assets` registry contains the malicious pool, victim-held `token_in`, and `token_out`, with a Soroswap `Swap` instruction referencing those indices. [19](#0-18) [22](#0-21) 
3. Have the victim call `swap_collateral(caller, account_id, current, amount, new, swap)` with that route. [23](#0-22) [24](#0-23) 
4. Simulation records the malicious `wallet_token.transfer(victim, attacker, amount)` as a child of the victim’s controller authorization. [25](#0-24) 
5. If the victim signs the returned tree, the strategy completes and the attacker receives the unrelated wallet tokens. [18](#0-17)

That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
