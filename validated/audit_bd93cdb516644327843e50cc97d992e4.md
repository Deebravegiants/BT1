## Analysis Result [1](#0-0)  confirms that in `ShopifyAPI::Webhooks::Request`, the HMAC-signable representation (`to_signable_string`) is defined as only `@raw_body`, while `shop`, `topic`, `webhook_id`, and `api_version` are all pulled from unauthenticated HTTP headers via `shopify_header`. Compare this to `ShopifyAPI::Auth::Oauth::AuthQuery#to_signable_string` [2](#0-1) , which explicitly folds `shop` into the signed string — showing the library's own established pattern of binding the shop identity into the HMAC when it matters. The webhook path breaks that same pattern.

`ShopifyAPI::Webhooks::Registry.process` validates only the HMAC via `Utils::HmacValidator.validate(request)`, then forwards the unauthenticated `request.shop` directly to the app's handler: [3](#0-2) .

### Title
Webhook `shop` (and `topic`/`webhook-id`) header not bound by HMAC allows cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body, so the HMAC validated by `Utils::HmacValidator.validate` in `ShopifyAPI::Webhooks::Registry.process` never covers the `shop`, `topic`, `webhook_id`, or `api_version` values that are read from HTTP headers and handed to the host app's handler as trusted, shop-scoped data.

### Finding Description
The equality that should hold is: **shop asserted in the `x-shopify-shop-domain` header == shop cryptographically bound into the HMAC-signed payload**. It does not hold here.

- `Request#to_signable_string` (`@raw_body` only) [4](#0-3)  is the only input to `HmacValidator.validate_signature`/`compute_signature` [5](#0-4) .
- `Request#shop`, `#topic`, `#webhook_id`, `#api_version` are read straight from headers with no cryptographic tie to the body [6](#0-5) .
- `Registry.process` only checks the HMAC and then trusts `request.shop` when constructing `WebhookMetadata` passed to the host app's handler [3](#0-2) .

Because the app's `client_secret` (and thus the HMAC key) is shared across every shop that installs the app, any entity that can install the app on their own store (an unprivileged tenant, not a privileged account) receives valid `(raw_body, hmac)` pairs signed with that shared secret. That same attacker can then send a request to the app's webhook endpoint with the original valid `raw_body`/`hmac` but an attacker-chosen `x-shopify-shop-domain` header value (e.g. a victim shop's domain). `HmacValidator.validate` still succeeds because it never looks at the shop header, and `Registry.process` forwards the spoofed shop identity to the handler as if Shopify itself had asserted it for that body.

This is the analog of the reported bug class: a value acted upon (`position.amount` / here, `shop`) is not verified against the ground truth that actually crossed the trust boundary (`balance-before/after` / here, the HMAC-covered bytes), letting an attacker present numbers/identities that look "positionally" valid while diverging from reality.

### Impact Explanation
This crosses a tenant boundary: the host application (which relies on `data.shop` from `WebhookMetadata` to route/attribute business logic — the documented and expected way to use this gem's webhook API, per `docs/usage/webhooks.md`) can be made to process fabricated webhook events "from" a shop that never sent them, using data (and possibly type/topic) chosen by the attacker within the constraints of a body they can produce a valid HMAC for. This is a cross-tenant identity spoofing primitive.

### Likelihood Explanation
Requires only that the attacker be able to install the app on their own shop (a standard, unprivileged action) and be able to send arbitrary HTTP requests to the app's public webhook endpoint — no leaked credentials, no privileged account, and no access to `api_secret_key` are needed since the attacker leverages a legitimately-signed message they themselves received.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the value that is HMAC-verified, or otherwise cryptographically/contextually tie the header-derived shop to the specific installation the webhook subscription belongs to, mirroring the pattern already used in `ShopifyAPI::Auth::Oauth::AuthQuery#to_signable_string`, which includes `shop` in the signed string.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com`, triggering a real webhook delivery with a valid `x-shopify-hmac-sha256` computed over some `raw_body` using the app's shared `client_secret`.
2. Attacker captures `(raw_body, hmac)` from that delivery.
3. Attacker POSTs the same `raw_body` and `hmac` to the app's public webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` — passes, because the HMAC only covers `raw_body` (`lib/shopify_api/webhooks/request.rb:35-38`).
5. The handler is invoked with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), and the host app processes attacker-supplied data as if it originated from the victim shop.

          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)

        end

          )
