## Analysis

The function `AccountsDb::many_ref_accounts_can_be_moved` at [1](#0-0)  computes `required_ideal_packed` using `(alive_bytes as u64 / tuning.ideal_storage_size + 1)`. This formula is provably an over-estimate (or exact match) of the true `ceil(alive_bytes / ideal_storage_size)` in the no-fragmentation case: when there's a remainder, `floor(B/I)+1 == ceil(B/I)`; when it divides evenly, `floor(B/I)+1` is one *more* than the minimal count. So this heuristic never under-counts relative to the ideal (fragmentation-free) case, meaning `i_last` is never pushed higher than warranted from that angle — it can only be overly conservative, causing early rejection (`return false`), not permissive misplacement.

It's true that per-account fragmentation in `PackedAncientStorage::pack` (which cannot split an account across storages) can cause the *actual* number of packed storages to exceed even `required_ideal_packed` — for example, several same-sized accounts whose total is an exact multiple of `ideal_storage_size` can still fragment into one extra storage due to the "won't split an account across boundary" logic at [2](#0-1) . However, this discrepancy does not propagate into a slot-freshness violation because `combine_ancient_slots_packed_internal` has an explicit hard guard right after calling `PackedAncientStorage::pack`: [3](#0-2) 

This check aborts the entire packing attempt (returning without writing anything) whenever the actual number of packed storages exceeds the number of available target slots — which is exactly the fragmentation scenario described. The heuristic in `many_ref_accounts_can_be_moved` is only a cheap pre-filter to avoid unnecessary work; the authoritative safety net is this length check combined with the `target_slots_sorted.iter().rev().zip(packed_contents)` pairing in `write_packed_storages`, which always maps the first-packed storage (containing the highest-slot `many_refs_newest` accounts, since `many_refs_newest` is sorted `Reverse` by slot before packing, see [4](#0-3) ) to the highest available target slot, at [5](#0-4) .

Additionally, ancient-slot packing/shrinking is a purely local storage-layout optimization performed on already-rooted slots; it does not affect bank hash computation or consensus, so even a hypothetical misplacement (which the guard above prevents) would not itself cause cross-node bank-hash divergence — it would only be a local storage bug, mitigated by the abort-and-retry design (`log::info!` + early `return`) visible at [6](#0-5) .
