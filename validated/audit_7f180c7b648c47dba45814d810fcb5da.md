### Title
`Oauth.validate_auth_callback`/`begin_auth` send `client_id`/`client_secret` to an unsanitized `shop` host, unlike sibling grant flows - ([File: lib/shopify_api/auth/oauth.rb])

### Summary
`ShopifyAPI::Auth::ClientCredentials.client_credentials`, `ShopifyAPI::Auth::RefreshToken.refresh_access_token`, and `ShopifyAPI::Clients::Graphql::Storefront` all call `Utils::ShopValidator.sanitize!(shop)` before using the caller-supplied `shop` string to build the request host that will receive `client_id`/`client_secret`. `ShopifyAPI::Auth::Oauth.begin_auth` and `ShopifyAPI::Auth::Oauth.validate_auth_callback`, which implement the exact same class of operation (constructing an OAuth host and POSTing the app's `client_id`/`client_secret` plus the authorization `code` to it), never call `ShopValidator` at all.

### Finding Description
`ShopValidator.sanitize!` (`lib/shopify_api/utils/shop_validator.rb:56-64`) enforces that a `shop` value resolves to a host under `TRUSTED_SHOPIFY_DOMAINS` (`myshopify.com`, `myshopify.io`, `shopify.com`, `spin.dev`, `shop.dev`) before it is allowed to become the destination of a credentialed request. Three call sites in the gem apply this check as the binding "the host that receives the app's client_id/client_secret == a trusted Shopify domain": [1](#0-0) [2](#0-1) 

`Oauth.begin_auth` and `Oauth.validate_auth_callback`, however, take the `shop` argument directly and feed it into `auth_base_uri(shop)`, which builds `"https://#{shop}/admin"` with no domain-trust check: [3](#0-2) [4](#0-3) [5](#0-4) 

Note `AuthQuery#shop` (`lib/shopify_api/auth/oauth/auth_query.rb`) is HMAC-covered so an attacker cannot forge `auth_query.shop` on a genuine Shopify redirect. But `validate_auth_callback` builds `null_session = Auth::Session.new(shop: auth_query.shop)` and posts `client_id`/`client_secret`/`code` to `https://#{auth_query.shop}/admin/oauth/access_token` with no independent domain-format check inside the gem — the trust boundary relies entirely on the caller constructing `AuthQuery` from the exact untouched query string on the callback route with `state`/`hmac` intact, and there is no defense-in-depth `ShopValidator` check at this layer the way there is for `ClientCredentials`/`RefreshToken`. More directly, `begin_auth`'s `shop:` parameter (which the docs explicitly say comes straight from an app-supplied header, e.g. `request.headers["Shop"]` — see `docs/usage/oauth.md:180-185`) is never validated by the gem before it's turned into the OAuth authorize host, unlike every other equivalent grant method in the same module family.

This is a root-cause "field acted on but not covered by an equality/binding check" pattern analogous to the reported bug class: `ClientCredentials`/`RefreshToken` treat "shop host that receives client_secret" as bound to "trusted Shopify domain," while `Oauth.begin_auth`/`validate_auth_callback` — despite performing the identical operation (sending `client_id`+`client_secret`+ authorization code to a shop-derived host) — omit that binding entirely.

### Impact Explanation
If a host application passes an unsanitized, request-derived `shop` string into `begin_auth` (which the gem's own documentation shows as the intended usage pattern, taking it from a request header), the library will construct an OAuth authorize URL and, on callback, POST the app's `client_id` and `client_secret` to whatever host string was supplied — with no gem-level check that it is `*.myshopify.com` or another trusted Shopify domain. Since `ClientCredentials` and `RefreshToken` demonstrate the library's own established practice of validating `shop` before it becomes a credentialed request target, `Oauth`'s omission is inconsistent and removes a safety net that would otherwise prevent leaking `client_secret` to a non-Shopify host if the host application forgets or fails to validate the `shop` domain itself upstream. This matches "SSRF/credential leakage carrying the app's `client_secret` to a host not verified to be Shopify," a High-severity impact class per the rules.

### Likelihood Explanation
Exploitation requires the host application to pass through an unsanitized shop value to `begin_auth`/`validate_auth_callback` (e.g., from a request header or query param, exactly as the gem's own official documentation example shows). This is not a defect in Shopify's own request flow (the HMAC on `auth_query` prevents forging Shopify's callback data), but it is a real, reachable gap in the gem's API surface: the gem provides `ShopValidator` and uses it in three sibling flows, yet documents and implements the OAuth authorization-code flow without it, making it easy for integrators to unknowingly build a vulnerable app by following the documented pattern.

### Recommendation
Call `Utils::ShopValidator.sanitize!(shop)` (or `sanitize_shop_domain`) at the top of `Oauth.begin_auth` and `Oauth.validate_auth_callback` before using `shop`/`auth_query.shop` to construct `auth_base_uri` or the `null_session`, mirroring the pattern already used in `ClientCredentials.client_credentials` and `RefreshToken.refresh_access_token`. Raise `Errors::InvalidShopError` for untrusted domains, exactly as those two methods do.

### Proof of Concept
Conceptual reachable path (library-level, no external report code applicable since this is a Ruby gem, not the Solidity contract from the report):
```ruby
# Host app (following the gem's own documented pattern in docs/usage/oauth.md):
shop = request.headers["Shop"]  # attacker-controlled, e.g. "attacker.example.com"
auth_response = ShopifyAPI::Auth::Oauth.begin_auth(shop: shop, redirect_path: "/auth/callback")
# => auth_response[:auth_route] == "https://attacker.example.com/admin/oauth/authorize?..."
# No ShopifyAPI::Errors::InvalidShopError is raised, unlike:
ShopifyAPI::Auth::ClientCredentials.client_credentials(shop: "attacker.example.com")
# => raises ShopifyAPI::Errors::InvalidShopError, "shop must be a trusted Shopify domain..."

        def begin_auth(shop:, redirect_path:, is_online: true, scope_override: nil)
          scope = if scope_override.nil?
            ShopifyAPI::Context.scope
          elsif scope_override.is_a?(ShopifyAPI::Auth::AuthScopes)
            scope_override
          else
            ShopifyAPI::Auth::AuthScopes.new(scope_override)
          end

          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = SecureRandom.alphanumeric(NONCE_LENGTH)

          cookie = SessionCookie.new(value: state, expires: Time.now + 60)

          query = {
            client_id: ShopifyAPI::Context.api_key,
            scope: scope.to_s,
            redirect_uri: "#{ShopifyAPI::Context.host}#{redirect_path}",
            state: state,
            "grant_options[]": is_online ? "per-user" : "",
          }

          query_string = URI.encode_www_form(query)
          auth_route = auth_base_uri(shop) + "/oauth/authorize?#{query_string}"

          { auth_route: auth_route, cookie: cookie }
        end

        def validate_auth_callback(cookies:, auth_query:)
          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state

          null_session = Auth::Session.new(shop: auth_query.shop)
          body = {
            client_id: Context.api_key,
            client_secret: Context.api_secret_key,
            code: auth_query.code,
            expiring: Context.expiring_offline_access_tokens ? 1 : 0, # Only applicable for offline tokens
          }

          client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
          response = begin
            client.request(
              Clients::HttpRequest.new(
                http_method: :post,
                path: "access_token",
                body: body,
                body_type: "application/json",
              ),
            )
          rescue ShopifyAPI::Errors::HttpResponseError => e
            raise Errors::RequestAccessTokenError,
              "Cannot complete OAuth process. Received a #{e.code} error while requesting access token."
          end

          session_params = T.cast(response.body, T::Hash[String, T.untyped]).to_h
          session = Session.from(shop: auth_query.shop,
            access_token_response: Oauth::AccessTokenResponse.from_hash(session_params))

        sig { params(shop: String).returns(String) }
        def auth_base_uri(shop)
          return "https://#{shop}/admin" unless defined?(DevServer) && shop.include?(".my.shop.dev")

          # For first-party apps in development only, we leverage DevServer to build the admin base URI
          admin_web = T.unsafe(Object.const_get("DevServer")) # rubocop:disable Sorbet/ConstantsFromStrings
            .new("admin-web")
          admin_host = admin_web.host!(nonstandard_host_prefix: "admin")
          shop_name = shop.split(".").first

          "https://#{admin_host}/store/#{shop_name}"
        end
