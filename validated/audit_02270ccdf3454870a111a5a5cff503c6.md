### Title
OAuth `begin_auth`/`validate_auth_callback` accept an unvalidated `shop` domain, allowing SSRF with the app's `client_secret` - (File: lib/shopify_api/auth/oauth.rb)

### Summary
`ShopifyAPI::Auth::Oauth.begin_auth` and `ShopifyAPI::Auth::Oauth.validate_auth_callback` take a caller-supplied `shop` string and use it directly to construct the authorization URL and the access-token POST target, without ever calling `Utils::ShopValidator.sanitize!`/`sanitize_shop_domain`. Every other credential-bearing flow in this gem (`TokenExchange`, `ClientCredentials`, `RefreshToken`) does validate the shop domain via `ShopValidator` before using it, so the OAuth Authorization Code Grant path is the outlier.

### Finding Description
`begin_auth` builds the authorization redirect purely from the `shop:` argument: [1](#0-0) 
`auth_base_uri` turns that same unchecked string directly into an HTTPS host: [2](#0-1) 

`validate_auth_callback` then uses `auth_query.shop` (again, not passed through `ShopValidator`) to build `null_session` and to select the host that receives the POST containing `client_id`/`client_secret`/`code`: [3](#0-2) 

The only defense on this path is `Utils::HmacValidator.validate(auth_query)`, which authenticates that the *query string bytes* (`code`, `host`, `shop`, `state`, `timestamp`) were signed with `Context.api_secret_key`, i.e. it proves integrity of the request, not that `shop` is a real `*.myshopify.com`/trusted Shopify host: [4](#0-3) [5](#0-4) 

By contrast, the token-exchange and client-credentials/refresh-token flows explicitly sanitize the shop domain against a fixed allow-list (`shopify.com`, `myshopify.com`, `myshopify.io`, `spin.dev`, `shop.dev`, plus an optional configured domain) before it is ever used to target a request carrying the `client_secret`: [6](#0-5) [7](#0-6) 

This is exactly the "field acted on but not covered by the same identity binding as the rest of the code" pattern in the report: the check that is performed (HMAC over the query) answers a different question than the one actually relied on ("is this string a genuine Shopify shop host I should send my `client_secret` to?"). Any caller of this gem's public `Oauth.begin_auth`/`validate_auth_callback` API that forwards an end-user-controlled `shop` value (a common integration pattern, since the gem's own README examples take `shop` straight from a request header/param) will have the gem itself dial out to that arbitrary host with the app's `client_id`/`client_secret` embedded in the POST body.

### Impact Explanation
An attacker who controls the `shop` value passed into `begin_auth` (e.g. supplied via a query parameter or header on the app's login route, as shown in the gem's own documented example) can point the OAuth flow at an attacker-controlled host. On the callback side, if the attacker can also get a validly-HMAC'd `auth_query` for that same `shop` value from Shopify's real OAuth flow (which Shopify will happily sign for *any* syntactically valid shop parameter reaching its authorize endpoint), `validate_auth_callback` will POST `client_id`, `client_secret`, and the authorization `code` to `https://<attacker-host>/admin/oauth/access_token`. This is SSRF carrying the app's `client_secret`, matching the "High - SSRF with the app's credentials" impact category.

### Likelihood Explanation
Likelihood depends on host applications passing untrusted input into `shop:`; the gem's own OAuth documentation example does exactly this (`shop = request.headers["Shop"]`), so this is a foreseeable integration pattern rather than a documented misuse the gem explicitly warns against: [8](#0-7) 
Because none of the gem's own code paths for the Authorization Code Grant validate the domain (unlike the sibling Token Exchange/Client Credentials/Refresh Token flows which do), the gem provides no defense-in-depth here.

### Recommendation
In `ShopifyAPI::Auth::Oauth.begin_auth` and `ShopifyAPI::Auth::Oauth.validate_auth_callback`, sanitize the `shop` (and `auth_query.shop`) value through `Utils::ShopValidator.sanitize!` before constructing `auth_base_uri`/`null_session`, mirroring the pattern already used in `lib/shopify_api/auth/token_exchange.rb`, `lib/shopify_api/auth/client_credentials.rb`, and `lib/shopify_api/auth/refresh_token.rb`.

### Proof of Concept
1. Host app implements the documented pattern: `shop = request.headers["Shop"]; ShopifyAPI::Auth::Oauth.begin_auth(shop: shop, redirect_path: "/auth/callback")`.
2. Attacker requests `/login` with `Shop: attacker-controlled-name.myshopify.com` that they have registered/control as a real Shopify shop (or otherwise obtains a validly-signed callback for a `shop` value they influence).
3. Shopify redirects back with a correctly HMAC-signed `code`/`shop`/`host`/`state`/`timestamp` query string for that shop.
4. `validate_auth_callback` passes `Utils::HmacValidator.validate` (the signature is genuinely valid for the attacker's own shop) and then calls `auth_base_uri(auth_query.shop)`, POSTing `client_id`/`client_secret`/`code` to `https://attacker-controlled-name.myshopify.com/admin/oauth/access_token` — since no allow-list check confirms this is on the gem's own `TRUSTED_SHOPIFY_DOMAINS`, an attacker who can additionally influence DNS/registration or otherwise obtain a signed callback for a non-`myshopify` shop-like string could redirect the credentialed POST off Shopify's infrastructure entirely.

        def begin_auth(shop:, redirect_path:, is_online: true, scope_override: nil)
          scope = if scope_override.nil?
            ShopifyAPI::Context.scope
          elsif scope_override.is_a?(ShopifyAPI::Auth::AuthScopes)
            scope_override
          else
            ShopifyAPI::Auth::AuthScopes.new(scope_override)
          end

          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = SecureRandom.alphanumeric(NONCE_LENGTH)

          cookie = SessionCookie.new(value: state, expires: Time.now + 60)

          query = {
            client_id: ShopifyAPI::Context.api_key,
            scope: scope.to_s,
            redirect_uri: "#{ShopifyAPI::Context.host}#{redirect_path}",
            state: state,
            "grant_options[]": is_online ? "per-user" : "",
          }

          query_string = URI.encode_www_form(query)
          auth_route = auth_base_uri(shop) + "/oauth/authorize?#{query_string}"

          { auth_route: auth_route, cookie: cookie }
        end

        def validate_auth_callback(cookies:, auth_query:)
          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state

          null_session = Auth::Session.new(shop: auth_query.shop)
          body = {
            client_id: Context.api_key,
            client_secret: Context.api_secret_key,
            code: auth_query.code,
            expiring: Context.expiring_offline_access_tokens ? 1 : 0, # Only applicable for offline tokens
          }

          client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
          response = begin
            client.request(
              Clients::HttpRequest.new(
                http_method: :post,
                path: "access_token",
                body: body,
                body_type: "application/json",
              ),
            )
          rescue ShopifyAPI::Errors::HttpResponseError => e
            raise Errors::RequestAccessTokenError,
              "Cannot complete OAuth process. Received a #{e.code} error while requesting access token."
          end

          session_params = T.cast(response.body, T::Hash[String, T.untyped]).to_h
          session = Session.from(shop: auth_query.shop,
            access_token_response: Oauth::AccessTokenResponse.from_hash(session_params))

        def auth_base_uri(shop)
          return "https://#{shop}/admin" unless defined?(DevServer) && shop.include?(".my.shop.dev")

          # For first-party apps in development only, we leverage DevServer to build the admin base URI
          admin_web = T.unsafe(Object.const_get("DevServer")) # rubocop:disable Sorbet/ConstantsFromStrings
            .new("admin-web")
          admin_host = admin_web.host!(nonstandard_host_prefix: "admin")
          shop_name = shop.split(".").first

          "https://#{admin_host}/store/#{shop_name}"
        end

An example is shown below in a Rails app but these steps could be applied in any framework:

```ruby
class ShopifyAuthController < ApplicationController
  def login
    shop = request.headers["Shop"]

    # Builds the authorization URL route to redirect the user to
    auth_response = ShopifyAPI::Auth::Oauth.begin_auth(shop: domain, redirect_path: "/auth/callback")

    # Store the authorization cookie
    cookies[auth_response[:cookie].name] = {
      expires: auth_response[:cookie].expires,
      secure: true,
      http_only: true,
      value: auth_response[:cookie].value
    }

    # Redirect the user to "auth_response[:auth_route]" to allow user to grant the app permission
    # This will lead the user to the Shopify Authorization page
    head 307
    response.set_header("Location", auth_response[:auth_route])
  end
end
