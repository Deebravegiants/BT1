### Title
Webhook `shop` identity is trusted for tenant dispatch without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [1](#0-0) , and `Registry.process` validates the HMAC over exactly that string before dispatching to the app's handler [2](#0-1) . The `shop` value passed to the handler comes straight from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` header [3](#0-2) , which is never part of the HMAC-signed material. This is the same bug class as the report: a field (`shop`) is acted on (used as the tenant key handed to `WebhookMetadata`/the host app) but is not covered by the identity-binding check (the HMAC).

### Finding Description
`Request#hmac` decodes the `hmac-sha256` header, and `HmacValidator.validate` recomputes an HMAC over `verifiable_query.to_signable_string` and compares it with `OpenSSL.secure_compare` [4](#0-3) . For webhook requests, `to_signable_string` is defined as simply `@raw_body` [1](#0-0)  — the topic, shop domain, webhook id and api version headers are excluded from the signed content entirely.

`Registry.process` only checks `Utils::HmacValidator.validate(request)` and then immediately builds `WebhookMetadata` using `request.shop`, `request.topic`, etc., handing them to the app's registered handler as trusted, verified data [2](#0-1) . `WebhookMetadata.shop` is a plain `String` const with no further validation performed by the gem [5](#0-4) .

Because the HMAC only binds the body bytes, and does not bind the `shop` header, **the same body+HMAC pair is valid for every shop**. Any body that a legitimate webhook has been delivered with (with its accompanying valid HMAC, computed from the shared `api_secret_key`) can be re-sent to the app's webhook endpoint with the `shop-domain` header swapped to a different, victim shop's domain, and `Registry.process` will accept it as authentic and dispatch it to the handler labelled as coming from the victim shop. This breaks the equality that should hold: `shop authenticated by HMAC == shop delivered to the handler as WebhookMetadata#shop`. Instead the gem enforces only `body authenticated by HMAC == body delivered`, while `shop` is parsed but never verified.

### Impact Explanation
This qualifies as cross-tenant data confusion at the identity-binding layer that this gem is responsible for: the library's own webhook verification API (`Registry.process` / `HmacValidator.validate`) is the mechanism host applications rely on to trust `WebhookMetadata#shop` as an authenticated tenant identifier. Because the gem does not bind `shop` to the signature, any application that uses `data.shop` from `WebhookMetadata` to select which merchant/tenant's data to update (the officially documented and expected usage pattern, see `lib/shopify_api/webhooks/webhook_handler.rb`) can be made to apply a payload intended for shop A to shop B's tenant context, without the attacker ever needing the app's `client_secret` or an access token — only a previously observed legitimate webhook body+HMAC pair (e.g., their own shop's own outbound webhook, which any shop that has installed the app naturally receives).

### Likelihood Explanation
Medium-High: exploitation requires only a body/HMAC pair from any real webhook delivery (which an attacker who installs the app on their own shop trivially obtains from their own legitimate webhooks) and the ability to POST directly to the app's public webhook endpoint with a modified `shop-domain` header — no secret material, TLS interception, or privileged account needed. The only constraint is that many webhook bodies for different topics/resources don't collide across shops with meaningfully identical content, so the practical exploitability depends on the topic (e.g., `app/uninstalled`, `shop/update`, or webhooks with generic/empty bodies like `{}` are trivially replayable across shop identities since body content is shop-independent for these topics, as also seen in the library's own tests using `raw_body: "{}"`).

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the signable content verified by `HmacValidator`, or otherwise require the caller/host framework to independently authenticate `shop` against a known, previously-registered shop before trusting `WebhookMetadata#shop`. Concretely, change `Request#to_signable_string` to bind `shop`, `topic`, and `webhook_id` alongside `@raw_body` so that the HMAC actually authenticates the full identity tuple the handler will act on, not just the JSON body.

### Proof of Concept
1. Attacker installs the app on shop `attacker.myshopify.com` and lets Shopify deliver a real webhook, e.g. `app/uninstalled` with a body like `{}`. The delivery includes headers:
   ```
   x-shopify-topic: app/uninstalled
   x-shopify-hmac-sha256: <valid HMAC of "{}">
   x-shopify-shop-domain: attacker.myshopify.com
   ```
2. Attacker replays the exact same body and HMAC to the app's webhook endpoint, only changing the shop header:
   ```
   x-shopify-topic: app/uninstalled
   x-shopify-hmac-sha256: <same valid HMAC of "{}">
   x-shopify-shop-domain: victim.myshopify.com
   ```
3. `HmacValidator.validate` recomputes HMAC over `@raw_body` ("{}") only [1](#0-0)  — signature matches, since `shop` was never part of the signed bytes.
4. `Registry.process` dispatches to the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", topic: "app/uninstalled", ...)` [2](#0-1) , and the host app processes an uninstall/state-changing action against `victim.myshopify.com`'s tenant record despite the request never having been sent by Shopify for that shop.
