### Title
Divide-by-zero panic in `InvariantToken` deposit math when pool reserves net of PnL reach zero - ([File: program/src/math.rs])

### Summary
`Processor::process_deposit` computes `total_pc_without_take_pnl` / `total_coin_without_take_pnl` and feeds them as the denominators of `InvariantToken::exchange_coin_to_pc` / `exchange_pc_to_coin`, which perform `checked_div(...).unwrap()`. If either of those values is exactly `0` while `amm.lp_amount` is still non-zero, the `unwrap()` on the `None` returned by `checked_div` panics, aborting the transaction and permanently blocking deposits into that pool. This mirrors the CVE-2016-10219 bug class: an unchecked division whose divisor can reach zero through normal, attacker-influenceable state, causing a crash instead of a controlled error.

### Finding Description
`calc_total_without_take_pnl_no_orderbook` derives the "net of PnL" reserves purely with `checked_sub`, which only errors on underflow — it happily returns `0` when a vault balance equals the accumulated `need_take_pnl_pc`/`need_take_pnl_coin`: [1](#0-0) 

`process_deposit` uses these net reserves to build an `InvariantToken`, guarding only against `amm.lp_amount == 0`, not against the reserve values themselves being zero: [2](#0-1) 

`InvariantToken::exchange_coin_to_pc` and `exchange_pc_to_coin` then divide by `self.token_coin` / `self.token_pc` respectively (i.e., by `total_coin_without_take_pnl` / `total_pc_without_take_pnl`) using `checked_div(...).unwrap()`, which panics on a zero divisor instead of returning `None`/an error: [3](#0-2) 

Because `need_take_pnl_pc`/`need_take_pnl_coin` are accrued from ordinary swap activity via `calc_take_pnl` (called on every deposit/withdraw and, in orderbook-integrated builds, on swaps) and are only bounded by the vault balances at the time of accounting, it is possible to drive `total_pc_without_take_pnl` or `total_coin_without_take_pnl` to exactly zero for a live pool that still has outstanding LP supply (`amm.lp_amount != 0`), e.g. once accumulated PnL for one side reaches the vault balance for that side: [4](#0-3) 

Once that state is reached, any subsequent `Deposit` instruction (base-coin path calls `exchange_coin_to_pc`, base-pc path calls `exchange_pc_to_coin`) will trigger `checked_div(0).unwrap()` and panic, failing the transaction unconditionally.

### Impact Explanation
A panic aborts the transaction rather than corrupting state directly, but since the divisor condition is a property of the pool's persistent on-chain state (vault balances vs. accumulated `need_take_pnl_*`), every future `Deposit` transaction against that pool will hit the same panic until the imbalance is otherwise resolved (which itself may require deposits/withdraws that are now impossible). This effectively creates a **permanent denial-of-service on liquidity deposits** for the affected pool, freezing further LP participation and blocking price-stabilizing deposits — a direct availability/funds-freezing impact reachable by an unprivileged pool participant, consistent with the CVE-2016-10219 divide-by-zero crash pattern.

### Likelihood Explanation
Reaching the exact zero-reserve condition requires the accumulated `need_take_pnl_pc`/`need_take_pnl_coin` for one side to equal that side's vault balance precisely, which is influenced by normal swap fee/PnL accrual over time and pool-specific parameters (fee ratios, decimals) rather than a single attacker-crafted transaction. This makes the condition plausible but not trivially forced in one step, lowering likelihood relative to the strict severity of the outcome.

### Recommendation
Guard both `InvariantToken` and `InvariantPool` division paths (and the underlying `checked_div(...).unwrap()` calls in `math.rs`) with explicit zero-checks that return `AmmError::CalculationExRateFailure` (or similar) instead of panicking, and consider rejecting deposit/withdraw processing early when `total_pc_without_take_pnl == 0 || total_coin_without_take_pnl == 0` even if `amm.lp_amount != 0`.

### Proof of Concept
1. Over time, swap activity accrues `need_take_pnl_pc` (or `need_take_pnl_coin`) via `Processor::calc_take_pnl` until it equals the corresponding vault's token balance while `amm.lp_amount` remains non-zero.
2. A user submits a normal `Deposit` instruction (base_side = 0 or 1, depending on which side hit zero).
3. `calc_total_without_take_pnl_no_orderbook` returns `0` for the affected side (`program/src/math.rs:238-250`).
4. `InvariantToken::exchange_coin_to_pc`/`exchange_pc_to_coin` executes `checked_div(0).unwrap()` (`program/src/math.rs:378-424`), panicking and aborting the transaction — and every subsequent deposit attempt against the pool.

    pub fn calc_total_without_take_pnl_no_orderbook<'a>(
        pc_amount: u64,
        coin_amount: u64,
        amm: &'a AmmInfo,
    ) -> Result<(u64, u64), AmmError> {
        let total_pc_without_take_pnl = pc_amount
            .checked_sub(amm.state_data.need_take_pnl_pc)
            .ok_or(AmmError::CheckedSubOverflow)?;
        let total_coin_without_take_pnl = coin_amount
            .checked_sub(amm.state_data.need_take_pnl_coin)
            .ok_or(AmmError::CheckedSubOverflow)?;
        Ok((total_pc_without_take_pnl, total_coin_without_take_pnl))
    }
