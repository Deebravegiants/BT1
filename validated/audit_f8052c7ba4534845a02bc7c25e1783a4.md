### Title
Cookie-derived session identifier is returned unauthenticated, breaking the binding between the returned session id and the actually-authenticated shop/user - (File: `lib/shopify_api/utils/session_utils.rb`)

### Summary
`ShopifyAPI::Utils::SessionUtils.current_session_id` (used by non-embedded apps, and as a fallback for embedded apps) returns the raw value of the `SESSION_COOKIE_NAME` cookie verbatim, with no cryptographic verification that the value actually originated from a completed OAuth flow for the shop it is later used to look up.

### Finding Description
The identity binding that must hold is: `session_id returned by the gem == session_id assigned by this gem's own OAuth flow for a session belonging to the requesting browser`.

In `lib/shopify_api/utils/session_utils.rb`:
```ruby
def cookie_session_id(cookies)
  cookies[Auth::Oauth::SessionCookie::SESSION_COOKIE_NAME]
end
```
`current_session_id` calls `cookie_session_id` directly for non-embedded apps [1](#0-0) , and this raw string is the only value returned to the caller [2](#0-1) . Unlike the embedded-app path, which derives the id from a cryptographically verified JWT (`Auth::JwtPayload`, HMAC-checked against `Context.api_secret_key`) [3](#0-2) , the cookie path performs zero verification of the bytes it reads — it does not check an HMAC, a signature, or any binding to the shop that set it.

The gem's own documentation instructs non-embedded apps to feed raw browser cookies straight into this method and use the returned string to look up a `Session` (containing the access token) from the app's session storage: `MyApp::SessionRepository.retrieve_session_for_shop(shop)` pattern, keyed by the `session.id` value [4](#0-3) . The `Session#id` used as the storage key is deterministic and predictable: `"offline_#{shop}"` or `"#{shop}_#{user_id}"` [5](#0-4) , matching the same pattern used in `Session.from` [6](#0-5) .

Because the cookie value is opaque, attacker-writable in any context where cookie injection/fixation is possible (e.g., a subdomain cookie-tossing scenario, a shared/misconfigured cookie jar, or any endpoint that reflects/sets cookies without `HttpOnly`/`Secure` enforcement by the host framework), and unauthenticated by this gem, an unprivileged party who can influence the `SESSION_COOKIE_NAME` cookie sent with a request can set it to a *guessed* target session id (e.g., `offline_victim-shop.myshopify.com`), and `current_session_id` will hand that id straight back as if it were a validated session identifier for the current browser.

### Impact Explanation
If an application follows this gem's documented pattern verbatim — using the cookie-derived id directly as the session-storage lookup key without additional binding to the OAuth `state`/HMAC — this collapses the tenant boundary: an unprivileged user can obtain the `ShopifyAPI::Auth::Session` (containing another shop's access token) for a predictable id, which qualifies as cross-tenant access / access-token theft, matching the required Critical impact category.

### Likelihood Explanation
Exploitability depends on an attacker being able to set or influence the `SESSION_COOKIE_NAME` cookie value on a victim's browser for a request to the app (cookie fixation/injection), which is a real class of unprivileged-attacker techniques (e.g., sibling-subdomain cookie tossing, response-splitting, or app endpoints that don't scope/`Secure`/`HttpOnly` the cookie as recommended). The gem provides no defense-in-depth (no signature/HMAC on the cookie value) even though it explicitly documents this value as authoritative for retrieving the authenticated session, making the likelihood non-trivial once any cookie-injection vector exists in the surrounding stack.

### Recommendation
Do not treat the raw `SESSION_COOKIE_NAME` cookie value as a trusted session identifier. Sign/HMAC the cookie value (similar to `Utils::HmacValidator`) when it is issued in `Auth::Oauth::SessionCookie`, and verify that signature inside `cookie_session_id` before returning it, so the returned session id is cryptographically bound to a session this gem itself created rather than to whatever bytes a client presents.

### Proof of Concept
1. App is non-embedded; user completes OAuth normally, and the app sets `SESSION_COOKIE_NAME` to `session.id` (e.g., `offline_victim-shop.myshopify.com`), as documented in `docs/usage/oauth.md` (`validate_auth_callback` output) [7](#0-6) .
2. An unprivileged attacker who can set/inject this cookie on their own request (e.g., via a cookie-fixation vector in a co-hosted subdomain, or a leaked/guessable value since the id is deterministic: `"offline_#{shop}"`) sends a request with `SESSION_COOKIE_NAME = "offline_victim-shop.myshopify.com"`.
3. The app calls:
```ruby
ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)
```
4. `cookie_session_id` returns `"offline_victim-shop.myshopify.com"` unmodified and unverified [2](#0-1) .
5. The app looks up `MyApp::SessionRepository.retrieve_session_for_shop("offline_victim-shop.myshopify.com")` per the documented pattern [8](#0-7)  and obtains the victim shop's `Session`, including its `access_token`, granting the attacker cross-tenant API access.

#### Cookie
Cookie based authentication is not supported for embedded apps due to browsers dropping support for third party cookies due to security concerns. Non-embedded apps are able to use cookies for session storage/retrieval.

For *non-embedded* apps, you can pass the cookies into:
 - `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, true)` for online (user) sessions or
 - `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)` for offline (store) sessions.
