### Title
`EvmHost.dispatchIncoming` silently swallows POST-request delivery failures with no status returned to the relayer or caller - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.dispatchIncoming(PostRequest, address)` delivers an incoming POST request to its destination module via a low-level `.call()`. On any failure — the destination having no code, or `IApp.onAccept` reverting — the function does not revert and returns no status; it just deletes the receipt and returns silently. `HandlerV2.handlePostRequests`, the entry point relayers use to submit these batches, never inspects any return value from `dispatchIncoming` (it is `external ... returns nothing`), so there is no on-chain signal distinguishing "request delivered" from "request silently dropped" other than optionally parsing for the absence of a `PostRequestHandled` event off-chain.

### Finding Description
`dispatchIncoming` is defined as: [1](#0-0) 

Key excerpt:
```
function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
    address destination = _bytesToAddress(request.to);
    uint256 size;
    assembly { size := extcodesize(destination) }
    if (size == 0) {
        // instead of reverting the entire batch, early return here.
        return;
    }
    bytes32 commitment = request.hash();
    _requestReceipts[commitment] = relayer;
    (bool success,) = address(destination).call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));
    if (!success) {
        delete _requestReceipts[commitment];
        return;
    }
    emit PostRequestHandled({commitment: commitment, relayer: relayer});
}
```
This function is called from `HandlerV2.handlePostRequests`, which iterates over a batch of leaves and calls `host.dispatchIncoming(leaf.request, _msgSender())` for each one without capturing or checking any return value: [2](#0-1) 

The function has void return type, and every failure path (`size == 0`, `!success`) is handled identically to the success path from the caller's perspective — there is no distinction surfaced on-chain. This is analogous to the reported `SafeGuard.checkTransaction` issue: a function whose entire purpose is to gate/verify an action ends up not communicating the actual pass/fail status of that check back through its interface, instead relying only on an emitted event (`PostRequestHandled`) that fires exclusively on the success path, and silence on failure. A caller (or an on-chain integrator building on top of the handler, e.g. a fee-accounting or relayer-incentive contract) that expects a return value or a revert on failure has no reliable way to determine, from the call itself, whether the request was actually delivered.

### Impact Explanation
Any contract or protocol logic composing with `HandlerV2.handlePostRequests`/`EvmHost.dispatchIncoming` on-chain (e.g. batched relayer accounting, or future extensions built atop this handler that assume dispatch either succeeds or reverts) cannot distinguish success from failure without off-chain event indexing. Because the design intentionally allows partial batch failures to be retried later (receipts deleted on failure), a relayer's transaction can "succeed" from the EVM's perspective while zero of the batched requests were actually delivered, and nothing in the call's return data indicates this. This does not itself cause fund loss in the current EvmHost fee model (no relayer fee is paid for POST-request delivery in this path), but it is a structural design gap consistent with the reported bug class — a status-check function whose caller cannot observe the actual check outcome on-chain — and could lead to unauthorized app-state assumptions or missed retries by any downstream on-chain consumer that relies on the call succeeding as a proxy for delivery.

### Likelihood Explanation
Every relayer-submitted `handlePostRequests` batch exercises this path when a destination reverts `onAccept` or has no code — a common, easily triggered condition (e.g., destination contract paused, reverting on a malformed payload, or simply not yet deployed). No privileged role is required; any relayer submitting a proof triggers this code path routinely.

### Recommendation
Have `dispatchIncoming` return a status (e.g. `bool` or an enum distinguishing `Delivered`, `NoCode`, `AcceptReverted`) so `HandlerV2` (and any future on-chain consumer) can act on the actual outcome rather than relying solely on emitted events for off-chain interpretation. At minimum, emit a distinct event (e.g. `PostRequestDeliveryFailed`) on every failure branch (both the `size == 0` and `!success` cases) so failures are observable on-chain symmetrically with the success case, rather than being silent no-ops.

### Proof of Concept
1. A relayer submits `HandlerV2.handlePostRequests` with a batch containing a `PostRequestLeaf` whose destination is either an address with no deployed code, or a contract whose `onAccept` reverts.
2. `host.dispatchIncoming(leaf.request, _msgSender())` executes: `size == 0` → immediate silent `return`, or `.call()` fails → receipt deleted and silent `return`.
3. The overall `handlePostRequests` transaction succeeds (no revert), and `PostRequestHandled` is never emitted for that leaf.
4. Any on-chain or off-chain observer relying purely on the transaction's success/return status (rather than diffing emitted events) cannot tell that the request was never delivered. [3](#0-2) [4](#0-3)

```text
    /**
     * @dev Dispatch an incoming POST request to destination module
     * @param request - post request
     */
    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }
```

```text
    function handlePostRequests(IHost host, PostRequestMessage calldata request) external notFrozen(host) {
        uint256 timestamp = block.timestamp;
        uint256 delay = timestamp - host.stateMachineCommitmentUpdateTime(request.proof.height);
        uint256 challengePeriod = host.challengePeriod();
        if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();

        uint256 requestsLen = request.requests.length;
        MerkleMountainRange.Leaf[] memory leaves = new MerkleMountainRange.Leaf[](requestsLen);

        for (uint256 i = 0; i < requestsLen; ++i) {
            PostRequestLeaf memory leaf = request.requests[i];
            // check destination
            if (!leaf.request.dest.equals(host.host())) revert InvalidMessageDestination();
            // check time-out
            if (timestamp >= leaf.request.timeout()) revert MessageTimedOut();
            leaves[i] = MerkleMountainRange.Leaf(leaf.index, leaf.request.hash());
        }

        bytes32 root = host.stateMachineCommitment(request.proof.height).overlayRoot;
        if (root == bytes32(0)) revert StateCommitmentNotFound();
        bool valid = MerkleMountainRange.VerifyProof(root, request.proof.multiproof, leaves, request.proof.leafCount);
        if (!valid) revert InvalidProof();

        for (uint256 i = 0; i < requestsLen; ++i) {
            PostRequestLeaf memory leaf = request.requests[i];
            // duplicate request?
            if (host.requestReceipts(leaf.request.hash()) != address(0)) revert DuplicateMessage();
            host.dispatchIncoming(leaf.request, _msgSender());
        }
    }
```
