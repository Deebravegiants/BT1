### Title
Fee-on-transfer/deflationary token input escrow over-crediting in `placeOrder()` breaks `withdraw()`/`cancelOrder()` accounting - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
In the Tron variant of `IntentGatewayV2.placeOrder()`, the escrowed amount recorded in `_orders[commitment][token]` is derived from the user-supplied `order.inputs[i].amount` (minus protocol fee) instead of the token amount actually received by the contract via `safeTransferFrom`/sweep. If the input token charges a transfer fee (fee-on-transfer / deflationary ERC20/TRC20), the contract's real balance will be lower than the escrow bookkeeping claims, exactly analogous to the reported Kairos `claim()` bug where `loan.payment.paid` is set to the nominal amount rather than the actually-received amount.

### Finding Description
`placeOrder()` computes `reducedInputs` (escrow amount after protocol fee) purely from the nominal, user-specified `order.inputs[i].amount`: [1](#0-0) 

It then transfers tokens using `safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` (or via the dispatcher sweep in the predispatch branch) **without measuring actual balance received**, and credits escrow with `reducedInputs[i].amount`: [2](#0-1) 

The predispatch branch is similarly flawed: it measures `balance = IERC20(token).balanceOf(dispatcher)` before the sweep call, computes `dust = balance - requiredAmount`, but credits `_orders[commitment][token] += reducedInputs[i].amount` — a value still derived from the original nominal `order.inputs[i].amount`, not the amount actually transferred into `address(this)` after the sweep call executes (which can itself be fee-reduced): [3](#0-2) 

This is the exact bug class from the external report: the accounting ledger (`_orders[commitment][token]`, analogous to `loan.payment.paid`) is set to a computed/nominal value rather than the actual token balance delta, so it diverges from the contract's true holdings whenever the input asset applies a transfer fee.

Contrast this with the fixed, non-Tron `IntentGatewayV2.sol` in the main `evm/src` and `sdk/packages/core/contracts` trees, which explicitly snapshot balances before/after each transfer and mutate `order.inputs[i].amount` to the *actual received* amount before computing `reducedInputs`/commitment/escrow: [4](#0-3) 
The Tron variant lacks this balance-delta measurement entirely, confirming this is a real regression/divergence rather than a false positive.

The escrow value is later relied upon by `withdraw()` (invoked from `cancelOrder()` for same-chain refunds, and from `onAccept()` for `RedeemEscrow`/`RefundEscrow` cross-chain requests) to release exactly the escrowed amount to the beneficiary/filler: [5](#0-4) [6](#0-5) 

### Impact Explanation
When a fee-on-transfer token is used as an input asset, `_orders[commitment][token]` will record more tokens than the gateway actually holds for that order. When `withdraw()` attempts to pay out this over-stated amount (to a filler on redeem, or to the user on cancel/refund), the transfer will either revert (leaving funds permanently stuck/unredeemable since the on-chain proof/commitment cannot be regenerated with a different amount once committed) or, in a multi-order/shared-liquidity contract, silently drain the balance intended for other unrelated orders' escrow, causing insolvency and permanent loss of funds for other users. This matches the "loss of user funds caused by stuck/insolvent claims" impact class validated by the analog rules (permanent freezing of funds / unsound accounting reachable by an unprivileged token depositor placing an order).

### Likelihood Explanation
Likelihood is high for any deployment that lists a fee-on-transfer, deflationary, or otherwise non-standard-transfer ERC20/TRC20 token as a supported `order.inputs[i].token`. Any ordinary user calling the unprivileged, publicly reachable `placeOrder()` with such a token as input triggers the flaw — no special privileges or governance action required.

### Recommendation
Mirror the fix already present in the canonical `evm/src/apps/IntentGatewayV2.sol`: for every token transfer into the gateway (direct `safeTransferFrom` and the predispatch/dispatcher sweep path), snapshot `balanceOf(address(this))` before and after the transfer, and use the balance delta (not the nominal request amount) both to compute protocol fees/`reducedInputs` and to credit `_orders[commitment][token]`. Apply this fix consistently to the Tron variant (`evm/tron/contracts/apps/IntentGatewayV2.sol`).

### Proof of Concept
1. Deploy `IntentGatewayV2` (Tron variant) and a TRC20 token with e.g. a 1% transfer fee (functionally identical to `FeeOnTransferToken` used in the existing test suite for the non-Tron contract, e.g. `evm/tests/foundry/IntentGatewayV2SameChainTest.sol` lines 2689-2735).
2. User approves and calls `placeOrder()` with `order.inputs[0] = {token: feeToken, amount: 1000e18}`.
3. `safeTransferFrom` at line 459 moves `1000e18` nominally but the gateway's actual balance increases by only `990e18` (1% fee burned/redirected).
4. `_orders[commitment][feeToken]` is nonetheless credited with `reducedInputs[0].amount` derived from the full `1000e18` (minus protocol fee, if any) — i.e., escrow bookkeeping shows ~1000e18 (or reduced-by-protocol-fee amount) while actual contract balance is only 990e18.
5. When the order is later cancelled (`cancelOrder` → `withdraw`) or filled cross-chain (`onAccept` → `withdraw` with `RedeemEscrow`), the contract attempts to transfer out the escrowed (overstated) amount, which exceeds its actual token balance for that token — reverting the withdrawal or consuming balance escrowed for other orders.
