### Title
`OmniBridge.describeWithdrawal` reports `"completed"` for NEAR/unmapped destinations without checking on-chain finalization - ([File: packages/intents-sdk/src/bridges/omni-bridge/omni-bridge.ts])

### Summary
`OmniBridge.describeWithdrawal` decides withdrawal status by branching on `destinationChain`. For EVM chains, `Sol`, `Fogo`, `Strk`, `Aptos` it reads `transfer.finalised?.transaction_hash`; for UTXO chains (`Btc`, `Zcash`) it reads `transfer.utxo_meta?.pending_sign_id` / `transfer.finalised?.transaction_hash`. For every other `destinationChain` (the `else` branch), it unconditionally returns `{ status: "completed", txHash: null }` — without ever inspecting `transfer.finalised` (i.e. without checking whether the transfer actually settled on-chain). [1](#0-0) 

### Finding Description
The function is supposed to preserve the equality "reported status == verified on-chain outcome". For the explicitly enumerated chains this equality is enforced by reading `transfer.finalised` (or the UTXO pending-sign-id) and falling back to `"pending"` when the hash is absent: [2](#0-1) 

But the `else` branch — reached for any `destinationChain` not in `{Eth, Base, Arb, Bnb, Abs, Pol, HlEvm} ∪ {Sol, Fogo, Strk, Aptos} ∪ {Btc, Zcash}` (per `isEvmChain`, and the explicit list, and `isUtxoChain`/`UTXO_CHAINS`) — skips this verification entirely and reports `"completed"` purely because `transfer.recipient` was non-null. `ChainKind.Near` and any chain added to the Omni Bridge protocol in the future but not yet added to this branch fall into this bucket. This mirrors the report's bug class: a state/status ("Late"/default in the original report, "completed" here) is asserted from an incomplete signal rather than the verified on-chain condition — the equality "reported == actual on-chain settlement" is broken for this code path. [3](#0-2) 

### Impact Explanation
`describeWithdrawal` return value is the SDK's canonical completion signal, consumed by polling/settlement flows (e.g. `waitForWithdrawalCompletion`) that integrators use to credit or refund users. If a withdrawal lands on a chain that falls into this catch-all `else` (NEAR-destined Omni transfers, or any chain kind added to `@omni-bridge/core` before this SDK's branch is updated), the SDK will report `"completed"` the moment the transfer record with a recognized recipient appears — even if the underlying transfer has not finalized or later fails. An integrator relying on this status could credit/settle the withdrawal prematurely, and if the transfer subsequently fails or is reprocessed, this can lead to a double credit/refund, matching the "status or hash misreport making an integrator credit or refund twice" High-impact category.

### Likelihood Explanation
Likelihood is moderate: it requires a withdrawal whose destination resolves to a `ChainKind` outside the explicitly handled EVM/Sol/Fogo/Strk/Aptos/UTXO set (e.g., NEAR-native destination transfers processed via Omni Bridge, or any newly supported chain in `@omni-bridge/core` not yet reflected in this branch — a real maintenance hazard given `CHAIN_MAPPINGS` is already updated ad hoc as chains are added). No attacker action is required; it happens automatically whenever such a transfer is observed by `getTransfer`.

### Recommendation
Do not treat "unrecognized/other destination chain" as proof of completion. Either:
1. Explicitly handle `ChainKind.Near` (checking `transfer.finalised`) instead of relying on the fallthrough `else`, and
2. For genuinely unhandled/unknown chains, return `{ status: "pending" }` (or throw) rather than `{ status: "completed", txHash: null }`, so that unverified destinations never get reported as settled.

### Proof of Concept
1. Initiate an Omni Bridge withdrawal whose `transfer.recipient` resolves (via `getChain`) to `ChainKind.Near` (or any chain kind not yet present in the `isEvmChain(...) || Sol || Fogo || Strk || Aptos` list and not in `UTXO_CHAINS`).
2. Call `describeWithdrawal`; as soon as `omniBridgeAPI.getTransfer` returns a transfer object with a non-null `recipient` for that index — before `transfer.finalised` is ever populated — the function returns `{ status: "completed", txHash: null }`.
3. An integrator/consumer polling this status treats the withdrawal as settled and credits the user, while the underlying on-chain transfer may still be pending or may ultimately fail, producing a status that does not reflect the true on-chain outcome. [4](#0-3)

		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const transfer = (
			await this.omniBridgeAPI.getTransfer({
				transactionHash: args.tx.hash,
			})
		)[args.index];

		if (transfer == null || transfer.recipient == null) {
			return { status: "pending" };
		}

		const destinationChain = getChain(transfer.recipient as OmniAddress);
		let txHash = null;
		if (
			isEvmChain(destinationChain) ||
			destinationChain === ChainKind.Sol ||
			destinationChain === ChainKind.Fogo ||
			destinationChain === ChainKind.Strk ||
			destinationChain === ChainKind.Aptos
		) {
			txHash = transfer.finalised?.transaction_hash;
		} else if (isUtxoChain(destinationChain)) {
			// pending_sign_id is not the finalised tx hash. In rare cases, the hash may
			// change if the BTC transfer fails to be submitted. We return fast hash for FE and
			// wait for final one (transfer.finalised?.transaction_hash) for BE.
			txHash =
				typeof window !== "undefined"
					? transfer.utxo_meta?.pending_sign_id
					: transfer.finalised?.transaction_hash;
		} else {
			return { status: "completed", txHash: null };
		}

		if (!txHash) {
			return { status: "pending" };
