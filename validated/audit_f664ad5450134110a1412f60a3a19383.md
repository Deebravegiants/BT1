### Title
Unbounded loop in `object::root_owner()` allows attacker-created ownership cycles to permanently disable code-upgrade and lazy self-init custody gates - (File: aptos-move/framework/aptos-framework/sources/object.move)

### Summary
`object::root_owner()` walks the object-ownership chain with no depth bound, unlike the sibling functions `owns()` and `verify_ungated_and_descendant()` which both enforce `MAXIMUM_OBJECT_NESTING`. Because `object::transfer`/`transfer_to_object` only validate that the signer transitively owns the *object being moved* (via `verify_ungated_and_descendant`), and never validate anything about the destination address, a user who directly owns two or more objects can sequence ordinary transfers to make those objects mutually own each other, creating a genuine ownership cycle. Any later call into `root_owner()` on an object in (or descending from) that cycle never terminates and aborts on out-of-gas. This function is depended on by `aptos_framework::code::publish_package` (to record the deploy-time owner of an object-hosted module) and by `aptos_framework::init::assert_may_self_initialize` (the ownership gate that authorizes lazy `self`-initialization of object-hosted modules). Poisoning the ownership chain therefore permanently blocks code upgrades and lazy self-initialization for any code object whose ownership chain contains a cycle. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`root_owner()` is implemented as:

```
public fun root_owner<T: key>(self: Object<T>): address {
    let obj_owner = self.owner();
    while (is_object(obj_owner)) {
        obj_owner = address_to_object<ObjectCore>(obj_owner).owner();
    };
    obj_owner
}
``` [1](#0-0) 

It has no loop bound, in contrast to `owns()`:
```
let count = 0;
while (owner != current_address) {
    count += 1;
    assert!(count < MAXIMUM_OBJECT_NESTING, error::out_of_range(EMAXIMUM_NESTING));
    ...
}
``` [4](#0-3) 

and `verify_ungated_and_descendant()`, which has the same bound: [3](#0-2) 

Crucially, `transfer_raw()` — used by `transfer`, `transfer_call`, and `transfer_to_object` — only checks that the *signer* transitively owns the object being moved; it never inspects the destination's ownership chain:
```
public fun transfer_raw(owner: &signer, object: address, to: address) {
    let owner_address = signer::address_of(owner);
    verify_ungated_and_descendant(owner_address, object);
    transfer_raw_inner(object, to);
}
``` [2](#0-1) 

Because of this, a user who owns two objects `X` and `Y` directly can:
1. `transfer_to_object(owner, X, Y)` — valid, since `owner` directly owns `X` (`X.owner` becomes `Y`'s address).
2. `transfer_to_object(owner, Y, X)` — also valid, since `owner` still directly owns `Y` at that moment (`Y.owner` becomes `X`'s address).

After step 2, `X.owner == Y_addr` and `Y.owner == X_addr`: a genuine 2-node ownership cycle, created entirely with legitimately-authorized, unprivileged transfers. The same technique generalizes to n-node cycles and to poisoning any ancestor of a *third-party* object: if an attacker at some point legitimately owns an object `A` that sits somewhere in the ancestor chain of a victim's object `C` (`C -> ... -> B -> A -> attacker`), the attacker can transfer `A` into the descendant chain (e.g. transfer `A` to be owned by `C`), closing the loop `A -> C -> ... -> B -> A` without needing the victim's cooperation, since the attacker only needs to sign the transfer of `A`, which they own.

Once such a cycle exists, `root_owner()` never terminates for any object in the cycle and its descendants. This is consumed by:
- `code::publish_package`, which calls `root_owner()` to record the object's transitive owner for lazy-init gating on every (re)publish for object-hosted code: [5](#0-4) 
- `init::assert_may_self_initialize`, the authorization gate for `internal_maybe_initialize`, which is the only mechanism guarding lazy self-init of object-hosted modules: [6](#0-5) 

Both call paths will run indefinitely (in practice: consume all transaction gas and abort) once the object is caught in a cycle, so every transaction attempting to upgrade the code object (`object_code_deployment::upgrade` → `code::publish_package_txn` → `code::publish_package`) or to trigger `internal_maybe_initialize` for that module will always fail.

### Impact Explanation
This breaks a custody invariant explicitly called out in the code's own design intent: `init.move`'s comment states self-init and the owner-recording mechanism exist specifically to prevent "the caller could mint a signer for an object it no longer controls," i.e., to gate code-object/authority control by true, current ownership. The unbounded `root_owner()` loop turns that same mechanism into a permanent-denial vector:
- The code-object's upgrade authority becomes permanently unusable — `object_code_deployment::upgrade()` will always abort on gas exhaustion for a poisoned object, so the legitimate owner can never again publish a new version of the package.
- Any resources or capabilities gated behind `init::internal_maybe_initialize` (lazy self-init, per the module's own documented use case for creating admin/treasury resources under the object's own address) become permanently unreachable — a non-recoverable loss of the ability to control or initialize object-held state/value tied to that code object.
- Because cycle creation only requires the attacker to legitimately own one object anywhere in the *ancestor* chain of a victim's object (not the victim's object itself), this is not purely self-inflicted: an attacker who is (or becomes, even temporarily) an ancestor-object owner in a composed/nested object hierarchy can permanently disable upgrade/init authority for descendant code objects they do not own.

This is a High-severity finding: it is an unprivileged, on-chain-provable mechanism that produces a permanent, non-recoverable loss of custody/control authority (upgrade rights, self-init rights) over a live code object, with no recovery path since the corrupted state (the cyclic `owner` fields in `ObjectCore`) cannot itself be un-poisoned by any existing function (all of which either use the same unbounded `root_owner()` or require successfully computing it).

### Likelihood Explanation
Medium-High. Creating the cycle requires only two ordinary, permission-checked `object::transfer`/`transfer_to_object` calls by a signer who legitimately owns both endpoints at the time of each individual transfer — no bugs are needed in the transfer path itself, only the documented behavior of `transfer_raw`/`verify_ungated_and_descendant`, which never validates the destination side. Any protocol using nested object hierarchies (vaults-of-vaults, sub-accounts implemented as objects, marketplace/staking wrappers) combined with `LAZY_MODULE_INITIALIZATION` for its code objects is exposed. The main uncertainty is how commonly deep, attacker-influenceable ancestor chains occur in production usage versus purely self-inflicted (single-user) cycles — self-inflicted cycles are trivial and always exploitable; third-party impact depends on specific composed-object topologies, which I could not fully enumerate from the indexed code alone.

### Recommendation
Add the same `MAXIMUM_OBJECT_NESTING` depth bound used in `owns()` and `verify_ungated_and_descendant()` to `root_owner()`, aborting (e.g. with `EMAXIMUM_NESTING`) instead of looping unboundedly when the configured depth is exceeded. Additionally, consider proactively rejecting transfers that would create a cycle (e.g., have `transfer_raw`/`transfer_to_object` also verify that `to` is not already a descendant of `object`, mirroring the existing "descendant" check but applied to the destination), which would prevent the corrupted state from being creatable at all rather than merely bounding the cost of detecting it.

### Proof of Concept
1. As user `U`, create two objects: `X = object::create_object(U)`, `Y = object::create_object(U)` (both directly owned by `U`).
2. Deploy a package to `X` via `object_code_deployment::publish` with `LAZY_MODULE_INITIALIZATION` enabled, so `init::record_deploy_owner` records `root_owner(X) == U` for the module.
3. Call `object::transfer_to_object(U, object_from_constructor_ref(X), Y_object)` — succeeds; `X.owner = Y_addr`.
4. Call `object::transfer_to_object(U, object_from_constructor_ref(Y), X_object)` — succeeds; `Y.owner = X_addr`. Now `X.owner == Y_addr` and `Y.owner == X_addr` (a 2-cycle).
5. Call the object-hosted entry function that invokes `init::internal_maybe_initialize` (as in the `object::test::run` pattern used in `init_module_api.rs`), or call `object_code_deployment::upgrade` on `X`.
6. `init::assert_may_self_initialize` → `object::address_to_object::<ObjectCore>(X).root_owner()` (and, on upgrade, `code::publish_package`'s owner-recording call) enters `while (is_object(obj_owner)) { ... }` alternating between `X` and `Y` forever, exhausting all transaction gas — the transaction always aborts, and no future call can ever succeed, permanently locking upgrade/self-init authority over `X`.     /// This checks that the destination address is eventually owned by the owner and that each
    /// object between the two allows for ungated transfers. Note, this is limited to a depth of 8
    /// objects may have cyclic dependencies.
    fun verify_ungated_and_descendant(owner: address, destination: address) {
        let current_address = destination;
        assert!(
            exists<ObjectCore>(current_address),
            error::not_found(EOBJECT_DOES_NOT_EXIST),
        );

        let object = borrow_global<ObjectCore>(current_address);
        assert!(
            object.allow_ungated_transfer,
            error::permission_denied(ENO_UNGATED_TRANSFERS),
        );

        let current_address = object.owner;
        let count = 0;
        while (owner != current_address) {
            count += 1;
            assert!(count < MAXIMUM_OBJECT_NESTING, error::out_of_range(EMAXIMUM_NESTING));
            // At this point, the first object exists and so the more likely case is that the
            // object's owner is not an object. So we return a more sensible error.
            assert!(
                exists<ObjectCore>(current_address),
                error::permission_denied(ENOT_OBJECT_OWNER),
            );
            let object = borrow_global<ObjectCore>(current_address);
            assert!(
                object.allow_ungated_transfer,
                error::permission_denied(ENO_UNGATED_TRANSFERS),
            );
            current_address = object.owner;
        };
    }

    /// Note: intentionally not using `self` as first argument, as a.owns(b) syntax would be ambiguous.
    public fun owns<T: key>(object: Object<T>, owner: address): bool {
        let current_address = object.object_address();

        assert!(
            exists<ObjectCore>(current_address),
            error::not_found(EOBJECT_DOES_NOT_EXIST),
        );

        if (current_address == owner) {
            return true
        };

        let object = borrow_global<ObjectCore>(current_address);
        let current_address = object.owner;

        let count = 0;
        while (owner != current_address) {
            count += 1;
            assert!(count < MAXIMUM_OBJECT_NESTING, error::out_of_range(EMAXIMUM_NESTING));
            if (!exists<ObjectCore>(current_address)) {
                return false
            };

            let object = borrow_global<ObjectCore>(current_address);
            current_address = object.owner;
        };
        true
    }
