### Title
Webhook `shop`, `topic`, `api-version`, and `webhook-id` are trusted from unauthenticated headers while the HMAC only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so `Utils::HmacValidator.validate` verifies solely the request body against the app's `api_secret_key`. The `shop`, `topic`, `api_version`, and `webhook_id` values are read straight from HTTP headers and are never included in the signed string, yet `Registry.process` immediately trusts `request.shop` as the tenant identity dispatched to the app's handler.

### Finding Description
`Request#hmac` and `Request#to_signable_string` derive the HMAC comparison purely from `@raw_body`: [1](#0-0) [2](#0-1) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all pulled straight from headers with no binding to the signed payload: [3](#0-2) 

`Utils::HmacValidator.validate` (from the earlier search) computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the supplied `hmac`, so it only proves the *body* bytes were signed by `api_secret_key` — it says nothing about which shop the header claims to be from.

`Registry.process` then trusts `request.shop` as the tenant identity for dispatch without any additional binding: [4](#0-3) 

Because `api_secret_key` is the same secret for every shop that has installed a given app (it's the app's client secret, not a per-shop secret), an attacker who legitimately installs the public app on their own store will receive real webhook deliveries with a valid `x-shopify-hmac-sha256` computed over some body. Since the header carrying `shop-domain` is never part of the signed bytes, the attacker can replay the exact same body + valid HMAC to the app's webhook endpoint while substituting `x-shopify-shop-domain` (or `shopify-shop-domain`) with a victim shop's domain. `HmacValidator.validate` will still pass (the body/HMAC pair is unchanged and valid), and `Registry.process` will hand the handler a `WebhookMetadata` object whose `shop` field is the attacker-chosen victim domain, `topic` is attacker-chosen, and `webhook_id`/`api_version` are attacker-chosen too.

This breaks the identity binding: `HMAC(secret, raw_body) valid` should imply `shop header == shop that actually produced this event`, but the header is outside the signed data, so the equality does not hold.

### Impact Explanation
Any host application that uses `data.shop` from `WebhookMetadata` to look up/update per-tenant state (e.g., marking a shop uninstalled on `app/uninstalled`, invalidating stored access tokens, triggering resyncs, or writing merchant-scoped records) can be made to act on an arbitrary victim shop chosen by an attacker who only needs to install the app once on a shop they control. This is a cross-tenant action: an unprivileged installer of the app can forge events attributed to any other merchant using the same app, since the signing secret is shared across all installs.

### Likelihood Explanation
Any developer/attacker can install a legitimate public Shopify app for free on their own development store, capture one valid webhook delivery (body + HMAC), and replay it with a modified `shop-domain` header value to the app's own webhook endpoint. No access token, TLS interception, or leaked credential is required — only normal, unprivileged use of the app installation flow plus the ability to send an HTTP request with attacker-chosen headers, since HMAC validation in this gem never binds the header set to the signed payload.

### Recommendation
Include `shop`, `topic`, `api_version`, and `webhook_id` (all Shopify-supplied identity fields) in the bytes that are HMAC-verified, or otherwise cryptographically bind them to the signed body, so header tampering causes HMAC validation to fail. At minimum, `to_signable_string` should concatenate the raw body with the shop-domain header (in the same way Shopify's real webhook signature scheme is documented to only cover the body — if that's unavoidable, the gem should require callers to independently verify the `shop` header value against a known/registered shop before trusting `WebhookMetadata#shop`, and document this gap explicitly).

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com`, triggering a legitimate webhook (e.g., `app/uninstalled`) delivery with body `B` and header `x-shopify-hmac-sha256: H = HMAC-SHA256(api_secret_key, B)`.
2. Attacker replays the request to the app's webhook endpoint, keeping body `B` and header `x-shopify-hmac-sha256: H` unchanged, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: ...)` is constructed; `Utils::HmacValidator.validate(request)` succeeds because `to_signable_string` only checks `B` against `H`. [2](#0-1) 
4. `Registry.process(request)` dispatches to the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: ..., body: parsed_body, ...)`. [5](#0-4) 
5. Any handler logic keyed on `data.shop` (e.g., deleting session/token records for that shop on `app/uninstalled`) now executes against the victim tenant, even though the event never originated from Shopify for that shop.

          unless handler
