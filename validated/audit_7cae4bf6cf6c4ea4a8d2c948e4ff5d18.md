### Title
Webhook `shop`, `topic`, `webhook_id` and `api_version` fields are trusted from unauthenticated headers while the HMAC only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw HTTP body only, but the `shop`, `topic`, `webhook_id`, and `api_version` values consumed by the application handler are parsed straight out of HTTP headers that are never covered by that HMAC. This breaks the intended binding: "the tenant (`shop`) that the HMAC authenticates" should equal "the tenant that the handler acts on," but the gem authenticates only the body bytes and blindly trusts the header-derived `shop` for tenant routing.

### Finding Description
`Request#to_signable_string` returns solely `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are read directly from HTTP headers with no cryptographic tie to the body or to each other: [2](#0-1) 

`Registry.process` validates only the HMAC of the body via `HmacValidator.validate`, then immediately trusts `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` to build the `WebhookMetadata` handed to the app's handler: [3](#0-2) 

`HmacValidator.validate` / `validate_signature` compute the signature only over `verifiable_query.to_signable_string`, i.e., the raw body for webhooks: [4](#0-3) 

`WebhookMetadata` (and thus the handler contract) carries `shop`, `topic`, `webhook_id`, `api_version` as if they were authenticated facts about the request: [5](#0-4) 

The identity binding that should hold is: `shop authenticated-by-HMAC == shop used-for-tenant-routing`. Because the HMAC is computed only from the body and the header-derived `shop` (and `topic`/`webhook_id`) are never included in the signable string, that equality is not enforced anywhere in the gem. Any bytes with a valid HMAC for *some* previously-observed body can be re-submitted with an arbitrary `shopify-shop-domain` (or `x-shopify-shop-domain`) header, an arbitrary `shopify-topic`, and arbitrary `shopify-webhook-id`, and `process` will accept it as valid and dispatch it to the handler labeled with the attacker-chosen `shop`/`topic`/`webhook_id` — none of which needs to match what Shopify actually sent.

### Impact Explanation
This is a cross-tenant data-integrity break at the trust boundary the gem is supposed to enforce: `Registry.process` is documented as verifying "the request did indeed come from Shopify," but it only verifies that *some* body was HMAC-signed with the app's secret at some point — it does not verify which shop, topic, or webhook that body belongs to. An attacker who can capture (e.g., via a compromised intermediary, logging pipeline, or replay of a webhook the app itself exposed/echoed) one legitimate `(raw_body, hmac)` pair for shop A can resubmit it to the app's webhook endpoint with the `shop-domain` header rewritten to shop B. `Registry.process` will pass HMAC validation and call the handler with `WebhookMetadata(shop: "B", ...)`, causing the host application (which trusts `WebhookMetadata#shop` as authenticated, per the library's own contract) to process shop A's data under shop B's tenant context — a cross-tenant data confusion. This matches the "High" impact class of a scope/binding check that answers permissively across a tenant boundary.

### Likelihood Explanation
Exploitation requires the attacker to already possess at least one valid `(raw_body, hmac)` pair generated by Shopify for the target app (a replay primitive), which is a real-world condition (webhook deliveries are not one-time-use tokens and the library performs no nonce/timestamp/replay protection either — `Request` has no timestamp or idempotency check, only a `webhook_id` that is itself unauthenticated). No possession of `api_secret_key` or any credential is required: the attacker reuses a previously valid signature, they don't need to forge one. The likelihood is moderate — it depends on the operational ability to intercept or replay a legitimate delivery — but no privileged secret is needed, matching the rule's constraint against findings that require the app's `api_secret_key`.

### Recommendation
Include the identity-critical fields (`shop`, `topic`, `webhook_id`) inside the HMAC-signable content, or otherwise cryptographically bind them to the body (e.g., verify against Shopify's webhook `Api-Version`/`shop` via a secondary authenticated channel or idempotency store keyed by `webhook_id` with replay protection). At minimum, document and/or enforce that `WebhookMetadata#shop`/`#topic` are not authenticated by the HMAC and must not be trusted for tenant-routing decisions without additional verification (e.g., cross-checking against a known/expected shop for the registered handler).

### Proof of Concept
1. Attacker captures one legitimate webhook delivery to the app for `shop-a.myshopify.com`: raw body `B` with a valid `X-Shopify-Hmac-Sha256` header `H` computed by Shopify over `B` using the app's secret.
2. Attacker resends `POST /webhook` with the same body `B` and header `H`, but sets:
   - `X-Shopify-Shop-Domain: shop-b.myshopify.com`
   - `X-Shopify-Topic: <any registered topic>`
   - `X-Shopify-Webhook-Id: <arbitrary>`
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` is constructed; `request.hmac` recomputes fine because it is derived from the untouched `H` header, and `to_signable_string` returns `B` unchanged. [6](#0-5) 
4. `ShopifyAPI::Webhooks::Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which succeeds because `B`'s HMAC over the (unchanged) body matches. [7](#0-6) 
5. The handler registered for that topic receives `WebhookMetadata.new(shop: "shop-b.myshopify.com", ...)`, and shop A's body/data is now processed and attributed to shop B by the host application, which trusts this field as authenticated per the gem's contract.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
