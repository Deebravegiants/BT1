### Title
Webhook `shop`, `topic`, and `webhook_id` fields are trusted by `Registry.process` without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then unconditionally trusts the `shop`, `topic`, `webhook_id`, and `api_version` values taken from HTTP headers - none of which are included in the signed bytes - and hands them to the host application's handler as the authoritative tenant identity for the payload.

### Finding Description
`Utils::HmacValidator.validate` computes `HMAC-SHA256(api_secret_key, verifiable_query.to_signable_string)` and compares it to the `hmac` value with a constant-time comparison: [1](#0-0) 

For webhooks, `to_signable_string` returns only the raw HTTP body: [2](#0-1) 

But `shop`, `topic`, `webhook_id`, and `api_version` are all parsed straight from HTTP headers, which are never part of the signable string: [3](#0-2) 

`Registry.process` validates only the HMAC of the body, then immediately builds the handler's trusted metadata from those unauthenticated header fields: [4](#0-3) 

`WebhookMetadata#shop` is the only tenant-identifying field passed to the app's `WebhookHandler#handle`, and the gem's own interface treats it as authoritative: [5](#0-4) 

The identity binding the gem is supposed to enforce is: `HMAC-verified bytes == bytes the handler acts on for tenant attribution`. Here that equality is broken: the verified bytes are `raw_body` only, while the handler acts on `(raw_body, shop_header)` where `shop_header` is unauthenticated. This is exactly a "field acted on but not covered by the HMAC" break of an identity binding.

### Impact Explanation
Any actor who can install the app on their own (unprivileged, self-controlled) shop receives real, correctly-HMAC-signed webhook deliveries for that shop's own data. Because the signature covers only the body and not the shop-domain header, that attacker can capture one legitimate `(raw_body, hmac)` pair and replay it to the app's public webhook endpoint with the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header rewritten to a victim shop of the attacker's choosing. `Registry.process` will accept the request as valid (the HMAC still matches the unmodified body) and dispatch it to the handler with `shop: "victim-shop.myshopify.com"`. If the host app uses `WebhookMetadata#shop` to key data writes, cache invalidation, or session/session-token lookups (which is the gem's documented usage pattern), attacker-controlled content is attributed to and processed under another merchant's tenant - a cross-tenant data-integrity/confusion issue achieved without any access token, `client_secret`, or privileged credential.

### Likelihood Explanation
The prerequisite is only that the attacker installs the app on a shop they control (a normal, unprivileged action any developer/merchant can take) and can send arbitrary HTTP requests to the app's public webhook endpoint - no secret material, TLS interception, or social engineering is required. The header-spoofing step is trivial once one valid webhook body/HMAC pair has been observed.

### Recommendation
Include the shop domain (and ideally topic/webhook id) inside the HMAC-covered signable string, or otherwise cryptographically bind the header-derived tenant identity to the verified payload before constructing `WebhookMetadata`, so that `Registry.process` cannot be satisfied by a body signed for one shop paired with a `shop-domain` header claiming another shop.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and receives a legitimate webhook: body `B`, header `X-Shopify-Hmac-Sha256: H` (valid for `B` under the app's `api_secret_key`), `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker resends the same `B` and `H` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` recomputes HMAC over `B` only, matches `H`, returns `true` (`lib/shopify_api/utils/hmac_validator.rb:26-31`).
4. `Registry.process` proceeds, builds `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body: parsed(B), ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`) and invokes the host handler as if `B` genuinely originated from `victim-shop.myshopify.com`.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
