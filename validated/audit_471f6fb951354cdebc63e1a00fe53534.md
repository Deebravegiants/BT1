### Title
Unchecked zero-address recipient in `WrappedHyperFungibleToken` native-ETH delivery causes permanent loss of bridged funds - ([File: sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol])

### Summary
`WrappedHyperFungibleToken.onAccept` and `onPostRequestTimeout` decode a beneficiary/refundee address from the cross-chain message body using `_toAddr`, which only validates the byte length (`== 20`) and never checks that the decoded address is non-zero, before pushing native ETH to it with a raw low-level `.call{value: ...}("")`.

### Finding Description
`_toAddr` is the sole gate on the address that money is sent to: [1](#0-0) 

In `onAccept`, when the underlying asset is WETH, the contract unwraps ETH and attempts a native push to `beneficiary` derived from `message.to` via `_toAddr`: [2](#0-1) 

The same unchecked pattern exists on the timeout/refund path: [3](#0-2) 

and is duplicated identically in the upgradeable variant: [4](#0-3) 

This is the same bug class as the external report: an address obtained from an untrusted/uncontrolled source (there, a third-party `treasury()`/`devfund()` interface call; here, an address decoded from an ISMP-delivered message payload) is used directly in a value-moving call without an existence/non-zero check. The critical difference from the sibling non-WETH branch (`IERC20(_underlying).safeTransfer(beneficiary, ...)`) is that `safeTransfer`/`_mint` calls into a real ERC20 implicitly revert or fail when the target is the zero address (OpenZeppelin's `_mint`/most ERC20 transfer implementations reject `address(0)`). A raw `.call{value: amount}("")` to `address(0)` has no such protection — it is indistinguishable from a call to any other address with no code and simply returns `success = true`, silently consuming the ETH with no possibility of recovery.

Because `sent == true` in this case, the fallback re-wrap-and-ERC20-`safeTransfer` branch is never reached, so there is no secondary protection.

### Impact Explanation
If `message.to` (populated by the sender's `SendParams.to` on the home chain and forwarded verbatim through the ISMP POST body) decodes to the zero address — whether by user/integrator error, a misconfigured relayer/gateway peer, or a malicious upstream contract that constructs the cross-chain call on behalf of a victim — the unwrapped native ETH is sent to `address(0)` and is permanently and unrecoverably lost. This is a genuine "permanent freezing/loss of funds" impact: the user's tokens were already burned on the source chain (`_burn(msg.sender, params.amount)` in `send()`), so the value is destroyed on both ends of the bridge with no path to refund, since delivery formally "succeeded" (`onAccept` does not revert).

### Likelihood Explanation
Reachable from a single normal `send()` call (an ordinary token bridge transfer) followed by ordinary relayer proof delivery — no privileged role is required on either the sender or relayer side. The only precondition is that the 20-byte `to`/`from` field of the message decodes to zero, which can happen from a simple integration/encoding mistake in a calling contract, from a griefing dApp routing user funds through this bridge with attacker-controlled recipient encoding, or from a malformed/adversarial peer-chain HFT contract sending a well-formed but zero-recipient message that this chain's peer-address check does not filter (the check validates `request.from`, not the beneficiary encoded inside `message.to`).

### Recommendation
In `_toAddr`, or immediately after decoding `beneficiary`/`refundee` in `onAccept`/`onPostRequestTimeout` (both `WrappedHyperFungibleToken.sol` and `WrappedHyperFungibleTokenUpgradeable.sol`), explicitly reject `address(0)` before performing the native `.call{value: ...}("")`, mirroring the implicit zero-address protection that the ERC20 (`safeTransfer`/`_mint`) branch already benefits from. Alternatively, route the native-ETH push through a helper that treats a call to `address(0)` (or any account with no code, if that's a possible griefing vector) as `sent = false`, forcing the WETH re-wrap-and-ERC20-transfer fallback, which will itself revert cleanly on a zero address.

### Proof of Concept
1. On the home chain, an integrator (or a user misencoding a beneficiary) calls `send(SendParams{ to: bytes20(0), amount, dest: <wrapped-chain>, ... })` on the canonical `HyperFungibleToken`. `_burn(msg.sender, amount)` executes, and an ISMP POST is dispatched with `Message.to = bytes(0)^20`.
2. A relayer relays the request; on the destination chain the `WrappedHyperFungibleToken` (configured for WETH, `_isWeth = true`) receives it via `onAccept`.
3. `beneficiary = _toAddr(message.to) = address(0)` passes the length check (20 bytes of zero).
4. `IWETH(_underlying).withdraw(message.amount)` unwraps ETH; `beneficiary.call{value: message.amount}("")` is executed against `address(0)`, which returns `sent = true` (a call with empty data and no code at the target trivially succeeds).
5. `amount` of native ETH is now held by no one (sent to `address(0)`), while the equivalent tokens were already burned on the source chain — funds are permanently lost with no revert, no event indicating failure, and no fallback recovery path executed.
