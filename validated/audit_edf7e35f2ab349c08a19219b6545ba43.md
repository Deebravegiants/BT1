## Analysis

The external report concerns fee‑on‑transfer tokens breaking the invariant between the "amount requested" and "amount actually received" by a contract, and the accounting being derived from the requested/parameter value instead of the measured balance delta.

Hyperbridge's main EVM `IntentGatewayV2.placeOrder` (`evm/src/apps/IntentGatewayV2.sol`) was explicitly hardened against this class of bug: it measures `balanceOf` before/after every `safeTransferFrom` and mutates `order.inputs[i].amount` to the actual amount received before computing the commitment and crediting escrow [1](#0-0) , and this is explicitly exercised by fee-on-transfer tests [2](#0-1) .

However, the Tron variant of the same contract, `evm/tron/contracts/apps/IntentGatewayV2.sol`, still contains the vulnerable pattern the report describes: it performs `IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` and then unconditionally credits escrow with `reducedInputs[i].amount`, which is computed directly from `order.inputs[i].amount` (the caller-specified/requested amount) rather than from any measured balance delta [3](#0-2) . The same flawed pattern also appears on the predispatch path, where escrow is credited with `reducedInputs[i].amount` while the actual balance swept could be less for fee-on-transfer tokens [4](#0-3) .

Later, when escrow is released — either as a refund on cancellation or as a cross-chain settlement payout — `_withdraw` decrements `_orders[commitment][token]` by the escrowed amount and calls `IERC20(token).safeTransfer(beneficiary, amount)` [5](#0-4) . Since the escrow bookkeeping for a fee-on-transfer token overstates what the Tron `IntentGatewayV2` contract actually holds, this transfer can fail (freezing the user's escrowed funds) or, because the ERC20 balance held by the gateway is a single shared pool across all commitments, an inflated escrow entry for one order can exceed the actual token reserve and starve/insolvent other legitimate orders' withdrawals of the same token.

### Title
Tron `IntentGatewayV2.placeOrder` credits escrow with the requested amount instead of the actual fee-on-transfer-adjusted amount received - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron deployment of `IntentGatewayV2.placeOrder` escrows `reducedInputs[i].amount`, which is derived from the user-supplied `order.inputs[i].amount`, instead of the amount the contract actually received via `safeTransferFrom`/predispatch sweep. For fee-on-transfer ERC20 tokens, this causes escrow accounting to exceed the real token balance held by the gateway.

### Finding Description
In `placeOrder`, the non-predispatch branch calls `IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` and then does `_orders[commitment][token] += reducedInputs[i].amount` without ever checking the gateway's actual balance change [3](#0-2) . The predispatch branch has the same issue for the dispatcher-to-gateway sweep, crediting escrow with `reducedInputs[i].amount` derived from the nominal requested amount rather than the measured post-sweep balance [4](#0-3) . This is the exact bug class fixed in the primary EVM contract, which snapshots balances and mutates `order.inputs` to the delta actually received before computing escrow and the commitment hash [6](#0-5) ; the Tron contract was not updated with the same fix.

### Impact Explanation
When `_withdraw` later releases escrow — on order cancellation/refund or on a solver's cross-chain `RedeemEscrow` fill — it transfers out the recorded (inflated) `_orders[commitment][token]` amount via `IERC20(token).safeTransfer` [7](#0-6) . Because the gateway's real balance of the fee-on-transfer token is lower than the sum of what's recorded across all commitments, this can (a) revert and permanently freeze the user's own escrowed input for that order, or (b) succeed by consuming reserves that were actually funded by other users' orders in the same token, causing other legitimate withdrawals to subsequently fail — a shared-pool insolvency that freezes/misallocates other users' escrowed funds.

### Likelihood Explanation
Any unprivileged user can trigger this by calling `placeOrder` with a fee-on-transfer token as an input asset — no special permissions or contract state are required, only the existence of a deployed fee-on-transfer ERC20 that solvers/users choose to trade via the Tron `IntentGatewayV2`.

### Recommendation
Apply the same fix used in `evm/src/apps/IntentGatewayV2.sol`: snapshot the gateway's/dispatcher's token balance before each transfer, compute the actually-received amount as the post-transfer balance delta, and use that measured amount (not the caller-requested `order.inputs[i].amount`) both for the commitment hash and for crediting `_orders[commitment][token]`.

### Proof of Concept
1. Deploy a fee-on-transfer ERC20 (e.g., 1% fee) and mint tokens to a user.
2. User calls Tron `IntentGatewayV2.placeOrder` with `order.inputs[0]` = `{token: FOT, amount: 1000e18}`, approving the gateway for `1000e18`.
3. `safeTransferFrom` moves `1000e18` from user, but the gateway's actual `balanceOf` only increases by `990e18` due to the transfer fee.
4. `_orders[commitment][FOT]` is nonetheless credited with `990e18 * (1 - protocolFeeBps)` derived from the nominal `1000e18` input rather than the true `990e18` received (in the no-protocol-fee case, credited with the full nominal `1000e18` instead of `990e18`).
5. On order cancellation/refund or cross-chain redeem, `_withdraw` attempts `safeTransfer(beneficiary, escrowedAmount)` for an amount exceeding the gateway's actual FOT balance, reverting (freezing funds) or depleting balance backing other users' escrowed orders in the same token.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
