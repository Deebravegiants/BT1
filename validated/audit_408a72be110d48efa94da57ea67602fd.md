### Title
Webhook shop/topic/metadata spoofing via unauthenticated headers not covered by HMAC - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw request body, then trusts the `shop`, `topic`, `api_version`, and `webhook_id` values taken from HTTP headers — none of which are covered by that signature — and hands them unchecked to the app's `WebhookHandler`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, and `hmac` is read from the `hmac-sha256`/`x-shopify-hmac-sha256` header, so the HMAC check performed by `Utils::HmacValidator.validate` binds nothing but the JSON body bytes to the app's shared `api_secret_key`. [1](#0-0) 
`shop`, `topic`, `api_version`, and `webhook_id` are all pulled straight from headers with no cryptographic binding to the signed body. [2](#0-1) 

`Registry.process` checks only that the HMAC validates, then constructs `WebhookMetadata` directly from the unauthenticated header-derived fields and dispatches it to the app's handler: [3](#0-2) 

`WebhookMetadata.shop` is a plain `String` field with no validation that it matches anything cryptographically tied to the request: [4](#0-3) 

The identity binding that should hold is: `shop-that-signed-the-payload == shop-attributed-to-the-payload-by-the-gem`. Because the HMAC only covers `raw_body` and the app's `api_secret_key`/`client_secret` is shared across *every* shop that has installed the app (it is not per-tenant), any unprivileged merchant who installs the app can:
1. Legitimately trigger a webhook for their own shop, capturing a validly-signed `(raw_body, hmac)` pair.
2. Replay that exact body/HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and optionally `x-shopify-topic`/`x-shopify-webhook-id`) header to name a *different, victim* shop.
3. `Utils::HmacValidator.validate` still passes, because the signature only ever attested to the body bytes, and the same `api_secret_key` is valid for all shops of the app.

The gem then calls the host app's handler with `WebhookMetadata#shop` set to the victim shop's domain, even though the payload actually originated from the attacker's own shop. Any host application that uses `data.shop` from the callback to key its own per-tenant storage (the documented, expected usage of this API) will now write attacker-controlled data under the victim shop's identity — a cross-tenant data/action confusion.

### Impact Explanation
This is a cross-tenant boundary break: an unprivileged app-installer can make the library attribute their own (attacker-controlled) webhook payload to an arbitrary other shop's identity, because the gem exposes `shop` (and other header fields) as trusted, HMAC-verified data when in fact only the body is verified. Per the severity rubric this falls under Critical (cross-tenant access), since the gem's own API misrepresents unauthenticated header data as authenticated to the calling application.

### Likelihood Explanation
Likelihood is Medium-High: exploitation requires only that the attacker be a legitimate installer of the same public app (no special privilege, no access token or secret needed), and requires guessing/knowing a victim shop's `.myshopify.com` domain, which is often discoverable or guessable. Capturing your own valid signed webhook body is trivial for anyone who has installed the app.

### Recommendation
Do not treat header-derived fields (`shop`, `topic`, `api_version`, `webhook_id`) as authenticated. Either include them in the HMAC-signed payload construction (Shopify does not currently sign headers, so this would need to be a documentation/consumer-side warning), or, at minimum, have `Registry.process`/`Request` clearly document that `shop` is unauthenticated and require host apps to cross-check it against an expected/installed-shop allowlist before trusting it, rather than exposing it as a plain field of `WebhookMetadata` with no such caveat.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` and receives a real webhook delivery: body `{"id":123,...}` with header `x-shopify-hmac-sha256: <valid-hmac-of-body>` and `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker POSTs the identical body and HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers, `Utils::HmacValidator.validate(request)` succeeds (body/HMAC unchanged) — see `lib/shopify_api/utils/hmac_validator.rb` lines 12-22.
4. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))` with `shop == "victim.myshopify.com"` — `lib/shopify_api/webhooks/registry.rb` lines 188-200.
5. The host app's handler processes attacker-controlled data as if it belongs to `victim.myshopify.com`.
