### Title
Tron `IntentGatewayV2.withdraw()`/`SweepDust` use raw low-level `.call` for ERC20 transfers without checking the returned boolean, silently treating failed transfers as successful escrow releases - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
In the Tron variant of `IntentGatewayV2`, the escrow-redemption path (`withdraw()`) and the `SweepDust` handler perform outgoing ERC20 transfers using a raw low-level `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` and only check that the call itself did not revert (`success`), never decoding/validating the returned boolean. Any TRC20/ERC20 token that returns `false` on a failed transfer instead of reverting (a common pattern for blacklist/pausable/fee-on-transfer tokens, and notably USDT-style tokens frequently deployed on Tron) will have its failed transfer treated as successful. Escrow accounting is decremented and the order is marked filled/refunded regardless of whether tokens actually moved, permanently freezing the beneficiary's funds inside the contract with no way to re-claim them.

### Finding Description
`withdraw()` is the internal function invoked by `onAccept` for `RedeemEscrow`/`RefundEscrow` requests and by `onGetResponse` for GET-response-driven refunds. For every escrowed token it does: [1](#0-0) 

The `success` boolean from a low-level `.call` only reflects whether execution reverted — it does **not** verify the ABI-encoded return value of `transfer()`. Non-standard-but-widely-used tokens (e.g. tokens that return `false` on blacklisted recipients, insufficient balance edge cases, or paused states) will make the call succeed (`success == true`) while the actual token balance is never moved. The code proceeds to unconditionally decrement `_orders[body.commitment][token]` and mark the order as filled/refunded via `_filled[body.commitment] = beneficiary` and the `EscrowReleased`/`EscrowRefunded` events.

The same unchecked pattern is used for the fee-token payout in the same function and in the `SweepDust` branch of `onAccept`: [2](#0-1) [3](#0-2) 

This is materially different from the rest of the codebase (including the EVM-mainline `IntentGatewayV2.sol` and `IntentsBase.sol`), which correctly use OpenZeppelin's `SafeERC20.safeTransfer`/`safeTransferFrom` (which decode and enforce the returned boolean, or tolerate no-return tokens safely): [4](#0-3) 

Because the Tron contract explicitly imports and aliases `SafeERC20` (`using SafeERC20 for IERC20;`) but bypasses it specifically in `withdraw()` and the `SweepDust` handler in favor of raw `.call`, this is a genuine deviation rather than intentional design for non-standard tokens — the raw-call path does not even inspect the returned bytes to detect the false case, unlike the pattern OpenZeppelin's helpers use.

### Impact Explanation
`withdraw()` is reached via `onAccept`, which is called by the trusted `host` after processing an inbound, cross-chain-relayed `RedeemEscrow`/`RefundEscrow` ISMP message, or via `onGetResponse` for a GET-response-triggered refund. Both paths are part of the core intent-fulfillment/refund flow that every solver and every order beneficiary depends on to receive escrowed funds after fulfilling or cancelling a cross-chain intent. If the escrowed token silently returns `false` instead of reverting (a realistic scenario on Tron, where TRC20/USDT-style tokens are common and diverge from strict ERC20 semantics, and also for any blacklist/pausable ERC20 bridged there), the beneficiary's tokens remain stuck in the `IntentGatewayV2` contract while the protocol's internal accounting (`_orders[...]`, `_filled[...]`) is updated as if the transfer succeeded. This is a permanent loss/freezing of the beneficiary's escrowed funds — the order can never be re-withdrawn because `_filled` is already set and the escrow balance already zeroed out, with no separate recovery mechanism in this function.

### Likelihood Explanation
Likelihood is high in practice given that Tron-native and many bridged tokens historically deviate from strict ERC20 return-value semantics (e.g., some TRC20 tokens/adaptations return `false` rather than reverting on blacklist checks or insufficient allowance/edge conditions). Any token onboarded to this Tron deployment of `IntentGatewayV2` with such semantics will trigger the bug on every failed transfer condition (blacklist, pause, edge-case balance), and the trigger requires no privileged access — it is purely a property of the token contract combined with a normal `RedeemEscrow`/`RefundEscrow`/`SweepDust` delivery that any relayer can carry through the normal flow.

### Recommendation
Replace the raw low-level `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `withdraw()` (both the per-token loop and the fee-token payout) and in the `SweepDust` branch of `onAccept` with `IERC20(token).safeTransfer(...)`, consistent with the rest of the codebase (`IntentsBase.sol`, EVM-mainline `IntentGatewayV2.sol`). `SafeERC20.safeTransfer` correctly decodes the return value when present and reverts on `false`, while still tolerating tokens that omit the return value entirely, closing the gap without reintroducing the original Kairos-style false-revert issue.

### Proof of Concept
1. Onboard a TRC20 token to this Tron `IntentGatewayV2` deployment whose `transfer()` implementation returns `false` (rather than reverting) when the recipient is blacklisted or under some other guarded condition — this mirrors real-world USDT-style token behavior common on Tron.
2. A solver escrows this token via the normal intent-fill flow; `_orders[commitment][token]` is credited.
3. Hyperbridge delivers a `RedeemEscrow` request naming a `beneficiary` address that the token's `transfer()` will reject (returns `false`, does not revert).
4. `onAccept` → `withdraw()` executes `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))`; the call itself does not revert, so `success == true` even though no tokens were transferred.
5. `_orders[commitment][token] -= amount` and `_filled[commitment] = beneficiary` proceed; `EscrowReleased` is emitted.
6. The tokens remain permanently locked in the `IntentGatewayV2` contract balance, unattributed to any recoverable order, while the protocol believes the beneficiary was paid.
