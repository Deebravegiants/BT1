### Title
Arbitrum BoLD consensus client accepts unconfirmed, in-challenge-window assertions as final state, allowing forged/rolled-back state roots to be used before confirmation - ([File: modules/ismp/clients/arbitrum/src/lib.rs])

### Summary
The Morph report describes a rollup that checks a batch's linkage to a prior finalized state (`prevStateRoot`) only at `finalizeBatch()` time, not at `commitBatch()` time — letting a committed-but-unfinalized (and potentially fraudulent) batch be treated as trustworthy before it is actually final, enabling theft of challenge deposits and a chain freeze. The analogous flaw exists in Hyperbridge's Arbitrum BoLD consensus verifier: `verify_arbitrum_bold` accepts an `AssertionNode` as a source of truth for a `StateCommitment` as soon as it exists in the L1 rollup's `_assertions` mapping and has no active sibling (no ongoing challenge at proof time), without checking that the assertion has actually passed Arbitrum's confirmation/challenge deadline.

### Finding Description
`verify_arbitrum_bold` in [1](#0-0)  recomputes the `assertion_hash` from the untrusted proof fields and merely checks that this hash exists as a key in the RollupCore's `_assertions` storage map. In Arbitrum BoLD/Nitro, an `AssertionNode` is written to this map optimistically the moment `newStakeOnNewAssertion`/`newStakeOnExistingAssertion` creates it — well before the multi-day challenge/confirmation period elapses. Existence in `_assertions` therefore only proves the assertion was *proposed*, not that it was *confirmed*.

The only additional safety check performed is against the *parent* assertion's `secondChildBlock` field to detect whether a rival sibling assertion currently exists [2](#0-1) . This detects a fork at the parent, but:
- It says nothing about whether *this* assertion itself has completed its confirmation window (`confirmPeriodBlocks`/deadline) — an honest assertion can still be successfully challenged and never confirmed even if no rival exists yet at proof-submission time.
- A malicious proposer can submit a plausible, unchallenged assertion whose `after_state` corresponds to an invalid state transition; if no fisherman/challenger acts within the window in which the ISMP proof is generated and relayed, this state commitment is accepted by `verify_arbitrum_bold` and immediately fed into Hyperbridge's `state_machine_map`, which flows into `update_client` in [3](#0-2) , storing it as a verified `StateCommitment` for that height.

This mirrors Rollup.sol precisely: acceptance of "committed" data before the point at which the underlying rollup's own dispute-resolution mechanism has actually finalized it. The only mitigating factor present is the `ChallengePeriodNotElapsed` gate enforced generically for consuming a state commitment (`verify_delay_passed` in [4](#0-3) , used in [5](#0-4)  and enforced on-chain in HandlerV2 in [6](#0-5) ). That gate, however, is a *configurable* per-state-machine `challenge_period` value stored via `store_challenge_period` [7](#0-6) , and there is nothing in the Arbitrum verifier code path that ties this delay to Arbitrum's actual on-chain `confirmPeriodBlocks`/deadline for the specific assertion being proven. If it is configured shorter than Arbitrum's real confirmation window (or 0, as is valid per `verify_delay_passed`'s `delay_period.as_secs() == 0` short-circuit), an unconfirmed and potentially invalid assertion's state root becomes usable for message delivery well before Arbitrum guarantees its finality.

### Impact Explanation
If a malicious or buggy assertion (state root not actually the correct Arbitrum state transition) is accepted before confirmation, and the configured `challenge_period` for that state machine is insufficient relative to Arbitrum's real confirmation window, it enables:
- Forged/incorrect state commitments being trusted by Hyperbridge, which underlies membership/non-membership proofs for cross-chain message delivery — i.e. forged message delivery or unsound state commitment, the exact category called out as in-scope impact.
- Because Hyperbridge's own consensus state also tracks `finalized_height` from this same assertion (`consensus_state.finalized_height = state.height.height` in ismp-arbitrum's `verify_consensus`), later legitimate assertions must build on this potentially-false height, which can strand or "freeze" the client's progression analogous to the original Morph chain freeze if the assertion is later invalidated (Hyperbridge has no fraud-proof handling here — `verify_fraud_proof` is unimplemented, only returning `FraudProofUnimplemented`).

### Likelihood Explanation
This requires an operator misconfiguration (challenge_period shorter than Arbitrum's real confirmation window) or reliance solely on the "no active sibling" check as sufficient finality proof, which is a plausible integration mistake given the check is easy to conflate with actual confirmation. The Fishermen blacklist mechanism (`FishermanBlacklist::is_arbitrum_claim_blacklisted`) is a reactive, off-chain-watcher-dependent safeguard, not a proof-time guarantee of confirmation status, so it does not eliminate the window of exposure.

### Recommendation
- In `verify_arbitrum_bold`, additionally require and verify a storage proof of the assertion's confirmation status (e.g., that the assertion has been confirmed on L1, or that `block.number` in the referenced L1 state commitment is past the assertion's recorded confirmation deadline) rather than only checking for the absence of a sibling.
- Alternatively/complementarily, enforce a hard-coded or governance-set minimum challenge period per Arbitrum state machine that is provably ≥ the chain's `confirmPeriodBlocks`, rather than allowing an arbitrary/zero `challenge_period` to be configured independently of the consensus client's actual finality assumptions.

### Proof of Concept
Conceptual (no PoC harness available in the indexed code):
1. Attacker (or any assertion proposer) calls `newStakeOnNewAssertion` on Arbitrum's RollupCore with a valid-looking but incorrect `after_state`, building on a legitimate `previous_assertion_hash`. This writes an `AssertionNode` to `_assertions` and leaves the parent's `secondChildBlock == 0` (no rival yet).
2. Relayer submits an `ArbitrumBoldProof` to Hyperbridge referencing this assertion. `verify_arbitrum_bold` confirms `assertion_hash` exists in `_assertions` and `secondChildBlock == 0`, and accepts the `after_state.global_state` as the new `StateCommitment` for that Arbitrum height [8](#0-7) .
3. If the configured `challenge_period` for this state machine elapses (or is 0) before Arbitrum's real confirmation deadline, `handlePostRequests`/`validate_state_machine` treat this commitment as final and allow message delivery/membership proofs against it [9](#0-8) .
4. If the assertion is later successfully challenged on L1 (rival submitted, secondChildBlock becomes non-zero, and the honest assertion wins), the state commitment Hyperbridge already used was never actually valid, but Hyperbridge has no fraud-proof mechanism (`verify_fraud_proof` unimplemented) to retroactively invalidate messages already delivered against it.

	payload: ArbitrumBoldProof,
	root: H256,
	rollup_core_address: H160,
	consensus_state_id: ConsensusStateId,
) -> Result<IntermediateState, Error> {
	let storage_root =
		get_contract_account::<H>(payload.contract_proof, &rollup_core_address.0, root)?
			.storage_root
			.0
			.into();

	let header: Header = payload.arbitrum_header.as_ref().into();
	if &payload.after_state.global_state.send_root[..] != &payload.arbitrum_header.extra_data {
		Err(Error::HeaderExtraDataMismatch)?
	}

	let block_number = payload.arbitrum_header.number.low_u64();
	let timestamp = payload.arbitrum_header.timestamp;
	let state_root = payload.arbitrum_header.state_root.0.into();

	let header_hash = header.hash::<H>();
	if payload.after_state.global_state.block_hash != header_hash {
		Err(Error::HeaderHashMismatch)?
	}

	let assertion_hash = compute_assertion_hash(
		payload.previous_assertion_hash,
		payload.after_state.hash(),
		payload.sequencer_batch_acc,
	);

	let assertion_hash_key = derive_map_key::<H>(assertion_hash.0.to_vec(), ASSERTIONS_SLOT);

	// Only valid assertions nodes are inserted in the rollup storage
	// A Some() value from the proof asserts that this assertion is valid and exists in storage
	// https://github.com/OffchainLabs/nitro-contracts/blob/94999b3e2d3b4b7f8e771cc458b9eb229620dd8f/src/rollup/RollupCore.sol#L542

	get_value_from_proof::<H>(assertion_hash_key.0.to_vec(), storage_root, payload.storage_proof)?
		.ok_or(Error::InvalidAssertion)?;

	// secondChildBlock bytes.
	let parent_key =
		derive_map_key::<H>(payload.previous_assertion_hash.0.to_vec(), ASSERTIONS_SLOT);

		get_value_from_proof::<H>(parent_key.0.to_vec(), storage_root, payload.challenge_proof)?
			.ok_or(Error::ParentAssertionNotFound)?;
	let parent_word_bytes = <alloy_primitives::Bytes as Decodable>::decode(&mut &*parent_word_raw)
		.map_err(|_| Error::DecodeParentAssertionWord(format!("{:?}", parent_word_raw)))?
		.0
		.to_vec();
	if parent_word_bytes.len() > 32 {
		Err(Error::ParentAssertionTooLong)?
	}
	let mut word = vec![0u8; 32 - parent_word_bytes.len()];

	// secondChildBlock occupies bytes word[16..24].

pub fn verify_delay_passed<H>(host: &H, proof_height: &StateMachineHeight) -> Result<bool, Error>
where
	H: IsmpHost,
{
	let update_time = host.state_machine_update_time(*proof_height)?;
	let delay_period = host
		.challenge_period(proof_height.id)
		.ok_or(Error::ChallengePeriodNotConfigured { state_machine: proof_height.id })?;
	let current_timestamp = host.timestamp();
	Ok(delay_period.as_secs() == 0 || current_timestamp.saturating_sub(update_time) > delay_period)
}

pub fn validate_state_machine<H>(
	host: &H,
	proof_height: StateMachineHeight,
) -> Result<Box<dyn StateMachineClient>, Error>
where
	H: IsmpHost,
{
	// Ensure consensus client is not frozen
	let consensus_client_id = host.consensus_client_id(proof_height.id.consensus_state_id).ok_or(
		Error::ConsensusStateIdNotRecognized {
			consensus_state_id: proof_height.id.consensus_state_id,
		},
	)?;
	let consensus_client = host.consensus_client(consensus_client_id)?;
	// Ensure client is not frozen
	host.is_consensus_client_frozen(proof_height.id.consensus_state_id)?;

	// Ensure delay period has elapsed
	if !verify_delay_passed(host, &proof_height)? {
		return Err(Error::ChallengePeriodNotElapsed {
			state_machine_id: proof_height.id,
			current_time: host.timestamp(),
			update_time: host.state_machine_update_time(proof_height)?,
		});
	}

	consensus_client.state_machine(proof_height.id.state_id)
}
