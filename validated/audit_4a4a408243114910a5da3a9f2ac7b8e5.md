### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant shop spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signable string from the raw body alone, while the `shop` (tenant identity) is read from an unauthenticated header. `Registry.process` trusts this header value and hands it to the app's webhook handler as the tenant identifier, without it ever being covered by the HMAC check.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `Request#shop` is derived purely from the `shopify-shop-domain`/`x-shopify-shop-domain` header [2](#0-1) . `Registry.process` validates only `Utils::HmacValidator.validate(request)`, i.e. it checks that the body's HMAC matches, then forwards `request.shop` (the unauthenticated header) straight into `WebhookMetadata` passed to the app's handler [3](#0-2) .

The identity binding that should hold is: `shop claimed in metadata == shop cryptographically bound to the signed payload`. Here that equality is broken — the HMAC only binds the body bytes, not the shop header, so `verified(body) ≠ verified(shop)`.

Because the webhook HMAC secret (`Context.api_secret_key`) is shared across every shop that installs a given app (multi-tenant), any merchant who installs the app receives their own genuinely-signed webhook deliveries (valid body + HMAC computed with the app's single shared secret). Since the `shop-domain` header is excluded from the signable string, that same attacker-obtained `(raw_body, hmac)` pair can be re-submitted to the app's webhook endpoint with the `shopify-shop-domain` header rewritten to a victim's shop domain. `HmacValidator.validate` still succeeds (only the body/HMAC pair is checked, `OpenSSL.secure_compare` over `compute_signature(request.to_signable_string, secret)` vs. the request's `hmac`) [4](#0-3) , yet the handler is invoked believing the event originated from the victim shop.

By contrast, the OAuth callback path in this same gem does this correctly: `AuthQuery#to_signable_string` explicitly folds `shop` into the signed parameter set [5](#0-4) , so `shop` cannot be swapped post-signature there. The webhook path lacks this binding for `shop`.

### Impact Explanation
Any app built on this gem that uses `WebhookMetadata#shop` for tenant-scoped logic (e.g., crediting/updating/deleting data keyed by shop, looking up a `Session` by shop to act on the merchant's behalf) can be tricked into acting as if an event happened for a different, victim tenant. This is a cross-tenant boundary violation stemming directly from the gem's webhook request/registry implementation, matching the "Critical – cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires only that the attacker be a legitimate (even free/trial) installer of the target app — no special privilege, no access to `api_secret_key`, and no interception of the victim's traffic. The attacker triggers a real webhook to their own shop (fully within their control, e.g. by performing an action that fires a subscribed topic), captures the resulting `(raw_body, hmac)` from their own endpoint logs, and replays it to the app's public webhook endpoint with a forged `shop-domain` header. This is a purely unprivileged-internet-user attack path.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the HMAC-covered signable string for webhooks, or otherwise cryptographically bind the header-derived `shop` value to the signed payload before it is trusted — mirroring how `AuthQuery` binds `shop` into its `to_signable_string`. At minimum, `Registry.process` should not propagate an unauthenticated `shop` claim into `WebhookMetadata` without validating it against something Shopify actually signs.

### Proof of Concept
1. App "X" is installed by both `attacker.myshopify.com` and `victim.myshopify.com`.
2. Attacker triggers a webhook-firing action on their own shop; Shopify delivers a POST to the app's webhook endpoint with headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC of raw_body computed with app's shared secret>`, and some `raw_body`.
3. Attacker captures this exact `raw_body` and `hmac` value.
4. Attacker POSTs the same `raw_body` to the app's webhook endpoint again, this time setting `x-shopify-shop-domain: victim.myshopify.com` (keeping the same valid `hmac`).
5. `ShopifyAPI::Webhooks::Registry.process` calls `HmacValidator.validate(request)`, which passes because it only checks `raw_body` against `hmac` [6](#0-5) .
6. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: ..., ...)` [7](#0-6) , causing the app to process attacker-controlled data as though it belongs to the victim's tenant.
