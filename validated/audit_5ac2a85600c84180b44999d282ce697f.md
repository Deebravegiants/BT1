### Title
Fee-handler side effect can revert the entire batch, blocking consensus updates and message delivery on Hyperbridge - ([File: modules/pallets/ismp/src/impls.rs])

### Summary
`pallet-ismp`'s `execute()` runs all incoming `handle_incoming_message` calls (consensus updates, POST/GET requests, responses, timeouts) first, then, as a final step, invokes `T::FeeHandler::on_executed(...)` and propagates any error from it with `?`. Because `execute` is a single Substrate dispatchable, an `Err` return rolls back **all** storage mutations performed earlier in the same call — including successfully verified consensus updates and successfully delivered/dispatched messages — purely because the trailing, non-core fee/incentive side effect failed.

### Finding Description
`Pallet::<T>::execute` in [1](#0-0)  processes a batch of `Message`s via `handle_incoming_message`, collects the resulting events, and only after all of that succeeds calls:

```rust
T::FeeHandler::on_executed(messages_with_weights, events.clone())
    .map_err(|_| Error::<T>::ErrorChargingFee)?;
``` [2](#0-1) 

`FeeHandler::on_executed` is a pluggable hook — the shipped `WeightFeeHandler` implementation calls `C::transfer(&account, &treasury_account, fee, ExistenceRequirement::KeepAlive)` for each message and propagates a `DispatchError` if the transfer fails (e.g., insufficient balance, existential-deposit violation) [3](#0-2) . Other implementations chain via the tuple impl, so *any* configured fee/incentive handler in the tuple can fail the whole call [4](#0-3) .

Because Substrate `#[pallet::call]` dispatchables are atomic — a `DispatchResult::Err` return rolls back all storage writes performed during that call — a single failing fee transfer at the very end of `execute()` reverts everything that happened earlier in the same batch: consensus-client state updates, membership-proof-verified request/response deliveries, `on_accept`/`on_response`/`on_timeout` module callback effects, and the offchain-committed leaves. This is structurally the same failure mode as the QuickSwap/StellaSwap finding: a secondary, incentive-related external call (`AlgebraVirtualPool` callback / here, `FeeHandler::on_executed`) is wired into the mandatory success path of the core operation (swap / here, message delivery), so a revert in the secondary call blocks the primary function.

An attacker (or simply an under-funded relayer/originator account) can force this: since the fee-paying account is derived from the message signer's recovered public key and is not validated for solvency up-front, a relayer can submit a batch containing one message whose signer/originator account lacks sufficient balance (or would dip below the existential deposit) alongside otherwise-valid consensus or request/response messages. `on_executed`'s transfer fails, `execute()` returns `Err(Error::<T>::ErrorChargingFee)`, and the entire batch — including unrelated, otherwise valid consensus updates and message deliveries — is rolled back and must be resubmitted.

### Impact Explanation
This can degrade message delivery for **all** requests/responses/consensus updates bundled with (or batched alongside) a fee-charging failure, not just the offending message. Since `pallet-ismp` treats delivery in batches (`Vec<Message>` per `execute` call), a relayer that unknowingly (or maliciously) includes one message from an insolvent account can cause the whole batch's consensus and message state to fail to commit — a denial-of-service on relayed consensus/message updates for that batch, requiring costly resubmission and potentially causing challenge-period/timeout misses for otherwise-valid, time-sensitive requests. This is a Medium-severity liveness/DoS impact on the core message-delivery path (`route unable to deliver messages`), matching the category of the referenced bug.

### Likelihood Explanation
Likelihood is moderate: it requires either (a) an account whose recovered signer key has insufficient/near-existential balance being included as a message signer in a relayed batch, or (b) a relayer deliberately batching such a message to grief other relayers'/users' pending consensus or request deliveries. Since relayers construct batches themselves and message signer accounts are not required to pre-fund before submission, this condition is reachable without any privileged access — any permissionless submitter of a `RequestMessage`/`ResponseMessage`/`ConsensusMessage` batch can trigger it.

### Recommendation
Short term: make `FeeHandler::on_executed` failures non-fatal to the already-processed messages — e.g., emit an event/log and skip fee collection for the failing entry rather than propagating the error with `?` for the whole batch, mirroring how `dispatchIncoming` in `EvmHost.sol` isolates external-call failures with `(bool success,) = ...call(...)` instead of letting a revert propagate. Long term, decouple fee charging from message execution atomicity entirely: charge fees per-message (so one message's failed transfer only forfeits/repeats that message) rather than as a single post-hoc, batch-wide side effect that can roll back verified consensus state and delivered requests/responses.

### Proof of Concept
1. Configure a runtime with `type FeeHandler = WeightFeeHandler<AccountId, Balances, WeightToFee, TreasuryPalletId, true>` (fees enabled), as shown in the crate docs [5](#0-4) .
2. Submit a `RequestMessage`/`ResponseMessage` batch to `pallet-ismp`'s unsigned/relayer entry point containing:
   - One legitimate `ConsensusMessage` or `RequestMessage` whose processing would otherwise succeed and update consensus/state commitments.
   - One `RequestMessage`/`ResponseMessage` whose signature recovers to an account with zero or near-existential-deposit balance.
3. `handle_incoming_message` processes both entries successfully (message validity, proofs, and `on_accept` do not check the signer's balance) and collects events in `Pallet::<T>::execute` [6](#0-5) .
4. `T::FeeHandler::on_executed` iterates messages and calls `C::transfer(...)` for the under-funded account's message; the transfer fails with `DispatchError` (insufficient balance / below existential deposit) [7](#0-6) .
5. `execute()` returns `Err(Error::<T>::ErrorChargingFee)` [2](#0-1) , causing the whole extrinsic (and therefore the whole batch, including the otherwise-valid consensus/request update) to roll back.
6. Repeat submission is required, and the same griefing pattern can be repeated by any relayer including such a message in future batches.

Note: I was unable to directly view the extrinsic wrapper (`handle`/`handle_unsigned` call site) in `modules/pallets/ismp/src/lib.rs` due to tool limits in this session, so the exact atomicity boundary (single extrinsic vs. sub-transaction) should be double-checked directly in that file to confirm the rollback scope precisely.

	pub fn execute(messages: Vec<Message>) -> Result<Vec<events::Event>, Error<T>> {
		let host = Pallet::<T>::default();

		let message_results = messages
			.iter()
			.map(|msg| handle_incoming_message(&host, msg.clone()))
			.collect::<Result<Vec<_>, _>>()
			.map_err(|err| {
				log::debug!(target: "ismp", "Handling Error {:#?}", err);
				Pallet::<T>::deposit_event(Event::<T>::Errors { errors: vec![err.into()] });
				Error::<T>::InvalidMessage
			})?;

		let messages_with_weights = message_results
			.iter()
			.zip(messages)
			.map(|(result, message)| MessageWithWeight { message, weight: result.weight() })
			.collect::<Vec<_>>();

		let events = message_results
			.into_iter()
			// check that requests will be successfully dispatched
			// so we can not be spammed with failing txs
			.map(|result| match result {
				MessageResult::Request { events, .. } |
				MessageResult::Response { events, .. } |
				MessageResult::Timeout { events, .. } => events,
				MessageResult::ConsensusMessage(events) => events.into_iter().map(Ok).collect(),
				MessageResult::FrozenClient(_) => vec![],
			})
			.flatten()
			.collect::<Result<Vec<_>, _>>()
			.map_err(|err| {
				log::debug!(target: "ismp", "Handling Error {:#?}", err);
				Pallet::<T>::deposit_event(Event::<T>::Errors { errors: vec![err.into()] });
				Error::<T>::InvalidMessage
			})?;

		T::FeeHandler::on_executed(messages_with_weights, events.clone())
			.map_err(|_| Error::<T>::ErrorChargingFee)?;

		for event in events.clone() {
			// deposit any relevant events
			Pallet::<T>::deposit_event(event.into());
		}

		Ok(events)
	}
