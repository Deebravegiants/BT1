### Title
Permissionless replay of stale `MultisigAccountCreationMessage` signature can convert an account into a multisig without the owner's current consent - (File: `aptos-move/framework/aptos-framework/sources/multisig_account.move`)

### Summary
`multisig_account::create_with_existing_account` (and its auth-key-revoking sibling `create_with_existing_account_and_revoke_auth_key`) let **any caller** submit a previously-collected owner signature to convert an existing account into a multisig account. The signed message's only anti-replay protection is the target account's current `sequence_number`; it has no expiration/deadline field. As long as the target account does not send any other transaction (sequence number unchanged), the signature remains valid indefinitely and can be replayed by whoever holds it — not necessarily the intended party — at any point in the future, forcibly converting the account into a multisig with the owner set frozen at signing time.

### Finding Description
`create_with_existing_account` takes no `&signer` for the target account — it is a fully permissionless entry function: [1](#0-0) 

The replay protection is limited to `account::get_sequence_number(multisig_address)`, fetched live at call time and baked into `MultisigAccountCreationMessage`: [2](#0-1) 

There is no deadline/expiry field in this message, unlike, e.g., orderless-transaction nonces which are bound to a `txn_expiration_time` window enforced in `nonce_validation::check_and_insert_nonce`: [3](#0-2) 

Because `multisig_address`'s sequence number only changes when *that* account sends a transaction, a user who signs this message off-chain (e.g., to authorize a dApp-driven "convert to multisig" flow) but never submits any other transaction leaves the signature exploitable indefinitely: anyone who obtained the signed bytes (a relaying dApp backend, a would-be co-owner, a leaked mempool/API log) can submit `create_with_existing_account` at an arbitrary later time, converting the account into a multisig controlled by the owner set/threshold fixed at signing time — even if the signer no longer wants that outcome (e.g., they changed their mind, or a proposed co-owner is no longer trusted).

This mirrors the `ServiceManager.registerAgentsWithSignature` root cause exactly: the message hash uses only a mutable, action-scoped anti-replay value (sequence_number / nonce) with no deadline, so a stored signature is valid forever unless invalidated by unrelated activity.

### Impact Explanation
Successful replay reassigns ownership/control authority over a live account: the account's authentication key stays under the original owner's key by default, but `MultisigAccount` resource and `owners`/`num_signatures_required` are attached unconditionally, and the account is now recognized on-chain as a multisig requiring the frozen owner set's cooperation for any multisig-gated flows built on top of it. If combined with `create_with_existing_account_and_revoke_auth_key` (same signature scheme, no deadline), the auth key is rotated to `0x0`, permanently and irrevocably transferring exclusive control from the original key-holder to the fixed owner set from the stale signed message: [4](#0-3) 

If any embedded co-owner is later untrusted, absent, or malicious, funds/assets held by that account can become permanently locked or subject to unauthorized multisig control — a custody-grade impact (unauthorized takeover of multisig/account control, potential permanent lock of account-held value).

### Likelihood Explanation
Exploitation requires only: (1) a previously signed `MultisigAccountCreationMessage`/`...WithAuthKeyRevocationMessage` obtained by a non-owner party (via a compromised or malicious front-end/relay, a co-owner who was supposed to be one of several signers, or simple signature leakage), and (2) the target account not transacting in the interim so its sequence number stays constant. Because typical low-activity or long-dormant accounts (a common custody pattern, e.g. cold accounts intended for later multisig migration) rarely change sequence number, this window can be long, making likelihood realistic though it requires signature exposure to an untrusted party first.

### Recommendation
Add an explicit `expiration_timestamp` (or similar deadline) field to `MultisigAccountCreationMessage` and `MultisigAccountCreationWithAuthKeyRevocationMessage`, include it in the signed struct, and assert `timestamp::now_seconds() <= expiration_timestamp` in `create_with_existing_account` / `create_with_existing_account_and_revoke_auth_key` before accepting the signature — mirroring the pattern already used for orderless-transaction nonces in `nonce_validation.move`.

### Proof of Concept
1. Alice controls account `A` (regular auth key, holding APT). A dApp asks her to sign a `MultisigAccountCreationMessage{chain_id, account_address: A, sequence_number: N, owners: [A, B, C], num_signatures_required: 2}` intending an immediate on-chain conversion to a 2-of-3 multisig.
2. Alice signs but the dApp/backend does not submit the transaction right away (or Alice changes her mind and never asks it to be submitted).
3. Alice does not send any other transaction from `A`; her sequence number stays `N`.
4. Months later, `B` (a proposed co-owner who no longer should be trusted, or the dApp backend itself) calls `multisig_account::create_with_existing_account(A, [A,B,C], 2, ..., stored_signature, ...)`. Since `account::get_sequence_number(A) == N` still holds, `account::verify_signed_message` succeeds and `A` is unexpectedly converted into a 2-of-3 multisig account controlled by `B` and `C`, without Alice's renewed consent, potentially locking her exclusive access to funds held at `A`.

    /// Creates a new multisig account on top of an existing account and immediately rotate the origin auth key to 0x0.
    ///
    /// Note: If the original account is a resource account, this does not revoke all control over it as if any
    /// SignerCapability of the resource account still exists, it can still be used to generate the signer for the
    /// account.
    public entry fun create_with_existing_account_and_revoke_auth_key(
        multisig_address: address,
        owners: vector<address>,
        num_signatures_required: u64,
        account_scheme: u8,
        account_public_key: vector<u8>,
        create_multisig_account_signed_message: vector<u8>,
        metadata_keys: vector<String>,
        metadata_values: vector<vector<u8>>,
    ) {
        // Verify that the `MultisigAccountCreationMessage` has the right information and is signed by the account
        // owner's key.
        let proof_challenge = MultisigAccountCreationWithAuthKeyRevocationMessage {
            chain_id: chain_id::get(),
            account_address: multisig_address,
            sequence_number: account::get_sequence_number(multisig_address),
            owners,
            num_signatures_required,
        };
        account::verify_signed_message(
            multisig_address,
            account_scheme,
            account_public_key,
            create_multisig_account_signed_message,
            proof_challenge,
        );

        // We create the signer for the multisig account here since this is required to add the MultisigAccount resource
        // This should be safe and authorized because we have verified the signed message from the existing account
        // that authorizes creating a multisig account with the specified owners and signature threshold.
        let multisig_account = &create_signer(multisig_address);
        create_with_owners_internal(
            multisig_account,
            owners,
            num_signatures_required,
            option::none<SignerCapability>(),
            metadata_keys,
            metadata_values,
        );

        // Rotate the account's auth key to 0x0, which effectively revokes control via auth key.
        let multisig_address = address_of(multisig_account);
        account::rotate_authentication_key_internal(multisig_account, ZERO_AUTH_KEY);
        // This also needs to revoke any signer capability or rotation capability that exists for the account to
        // completely remove all access to the account.
        if (account::is_signer_capability_offered(multisig_address)) {
            account::revoke_any_signer_capability(multisig_account);
        };
        if (account::is_rotation_capability_offered(multisig_address)) {
            account::revoke_any_rotation_capability(multisig_account);
        };
