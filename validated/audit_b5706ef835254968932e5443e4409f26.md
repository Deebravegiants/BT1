Audit Report

## Title
Bridge and External Initiator `OutgoingToken` secrets disclosed to view-only users via unrestricted GET endpoints - ([File: core/web/router.go])

## Summary
`GET /v2/bridge_types`, `GET /v2/bridge_types/:BridgeName`, and `GET /v2/external_initiators` are registered in the `authv2` group without any elevated-role middleware, so an authenticated user with only `UserRoleView` can call them. The presenters for these resources unconditionally serialize `OutgoingToken`, a secret used to authenticate outbound/inbound calls to external adapters/initiators, resulting in secret disclosure to the lowest-privilege role.

## Finding Description
The role-check middleware `auth.RequiresRunRole`, `auth.RequiresEditRole`, and `auth.RequiresAdminRole` explicitly reject `UserRoleView` sessions [1](#0-0) , and roles are defined with `UserRoleView` as the lowest tier [2](#0-1) . However, in `v2Routes`, the three read routes in question are registered with no such wrapper — only `paginatedRequest(...)` or nothing at all: [3](#0-2) 

`BridgeTypesController.Index`/`.Show` build the response via `presenters.NewBridgeResource`, whose `BridgeResource.OutgoingToken` field lacks `omitempty` (unlike `IncomingToken`, which is intentionally hidden after creation) [4](#0-3) . Likewise, `ExternalInitiatorsController.Index` builds the response via `presenters.NewExternalInitiatorResource`, whose `ExternalInitiatorResource.OutgoingToken` is also unconditionally serialized [5](#0-4) . `OutgoingToken` is a genuine secret generated with `utils.NewSecret(24)` at bridge creation time and stored as `outgoing_token` [6](#0-5) , used by the node to authenticate itself to external adapters/initiators.

The existing RBAC test suite confirms this is the actual, currently-shipping behavior rather than a hypothetical: the routes are explicitly marked `viewOnlyAllowed: true` in `routesRolesMap` [7](#0-6) , and `TestRBAC_Routemap_ViewOnly` asserts that view-role requests to these routes do NOT receive `401`/`403` [8](#0-7) .

## Impact Explanation
Any authenticated `view`-role user (intended for read-only dashboard/monitoring access with no mutation rights) can retrieve `OutgoingToken` for every configured bridge and external initiator. Since this token authenticates outbound requests from the node to external adapters (and is used by external initiators to authenticate their own requests back to the node), its disclosure to an unprivileged role constitutes secret/credential exfiltration and enables impersonation of the node's outbound identity toward external systems — exceeding the intended `view` privilege boundary. This maps to the "key/secret exfiltration" impact class.

## Likelihood Explanation
This requires only a pre-existing `view`-role session or API token — the lowest privilege tier, commonly provisioned for read-only dashboard/monitoring purposes — and a single unauthenticated-role-elevation-free GET request. No race condition, timing bypass, or additional exploit chain is needed; the RBAC test suite already documents and asserts this exact behavior as passing (`viewOnlyAllowed: true`), confirming it reliably reproduces on the current code.

## Recommendation
Wrap `GET /v2/bridge_types`, `GET /v2/bridge_types/:BridgeName`, and `GET /v2/external_initiators` with `auth.RequiresEditRole` (or higher), consistent with the mutating routes on the same resources. Alternatively/additionally, strip `OutgoingToken` from the presenter response for `view`-role callers (e.g., add `omitempty` and only populate it for privileged callers), mirroring how `IncomingToken` is already treated as create-time-only. Apply the same audit to any other presenter that unconditionally serializes secret fields on routes reachable by `view` role.

## Proof of Concept
1. Create a user with `UserRoleView` (e.g. via `admin users create --role view`).
2. Authenticate as that user and issue `GET /v2/bridge_types` (or `GET /v2/external_initiators`).
3. Observe the JSON response body includes `outgoingToken` for each configured resource despite the caller only holding `view` role.
4. This is directly validated by the existing `TestRBAC_Routemap_ViewOnly` test in `core/web/auth/auth_test.go`, which asserts `resp.StatusCode` is not `401`/`403` for these routes under a `view`-role client, confirming successful (unauthorized) access to the secret-bearing payload.
