### Title
`describeWithdrawal` in OmniBridge reports completion by array index without validating the transfer belongs to the requested withdrawal - ([File: packages/intents-sdk/src/bridges/omni-bridge/omni-bridge.ts])

### Summary
`OmniBridge.describeWithdrawal` selects the transfer to report on purely by array position (`[args.index]`) from `omniBridgeAPI.getTransfer({ transactionHash })`, with no check that the selected transfer's `recipient`/`token`/`amount` actually corresponds to the `withdrawalParams` (`destinationAddress`, `assetId`, `amount`) that were requested for that index. This breaks the equality "status reported == actual on-chain outcome of the requested withdrawal."

### Finding Description [1](#0-0) 

```
async describeWithdrawal(
    args: WithdrawalIdentifier & { logger?: ILogger },
): Promise<WithdrawalStatus> {
    const transfer = (
        await this.omniBridgeAPI.getTransfer({
            transactionHash: args.tx.hash,
        })
    )[args.index];

    if (transfer == null || transfer.recipient == null) {
        return { status: "pending" };
    }
    ...
    return { status: "completed", txHash };
}
```

The function fetches all transfers associated with a NEAR transaction hash and blindly picks the one at `args.index`, then reports it as `completed` with the discovered `txHash`, without ever comparing `transfer.recipient` to `args.withdrawalParams.destinationAddress` or `transfer.token_id`/`amount` to the requested asset/amount.

Contrast this with the sibling `PoaBridge.describeWithdrawal`, which explicitly documents and guards against exactly this class of bug: [2](#0-1) 

```
async describeWithdrawal(
    args: WithdrawalIdentifier & { logger?: ILogger },
): Promise<WithdrawalStatus> {
    const response = await this.getWithdrawalStatusWithRetry(args);

    // Response list is unsorted, so we match by assetId instead of index
    const withdrawal = findMatchingWithdrawal(
        response.withdrawals,
        args.withdrawalParams.assetId,
    );
    ...
```

The PoA bridge test suite even has a regression test titled `"matches withdrawal by assetId, not by index"` confirming the API can return withdrawal entries out of order for a single transaction. `OmniBridge` has no equivalent safeguard: when a single NEAR transaction produces multiple omni transfers (e.g., a batch of `ft_withdraw` intents to different chains/tokens in one tx, which the SDK itself supports via `withdrawalParams: WithdrawalParams[]` and per-item `index`), and the bridge API returns them in an order that doesn't match the order the SDK submitted them in, `describeWithdrawal` will attach the wrong transfer's `txHash`/status to the wrong logical withdrawal.

### Impact Explanation
This is a status/hash misreport: an integrator or the SDK's own `waitForWithdrawalCompletion`/`createWithdrawalCompletionPromises` flows would receive a `{ status: "completed", txHash }` for withdrawal N that actually corresponds to a different withdrawal M (different destination address, asset, or amount). An integrator that credits or marks a withdrawal complete based on this report could:
- Mark the wrong destination/withdrawal as fulfilled (double credit risk if the true withdrawal for that slot never gets reported/credited, while a mismatched one is credited as done),
- Cause a user's actual withdrawal to appear "stuck" while an unrelated transfer's hash is attached to it, requiring manual reconciliation.

This matches the "High" bucket: "a status or hash misreport making an integrator credit or refund twice" / "a withdrawal stuck until manual intervention."

### Likelihood Explanation
Requires a NEAR transaction with multiple omni-bridge withdrawals bundled (multiple intents in one signed payload landing on Omni Bridge routes), which the SDK explicitly supports (`WithdrawalParams[]`, per-item `index`). Likelihood of the underlying API returning transfers in a non-request order for the same tx hash could not be independently confirmed for the Omni Bridge API (unlike POA Bridge, where this was verified and specifically regression-tested) — this is the primary uncertainty in this finding. Given that the sibling bridge implementation had to be hardened for precisely this issue, it's reasonable to treat OmniBridge as exposed to the same class of risk unless the Omni Bridge API guarantees stable ordering (which was not verifiable from the code in scope).

### Recommendation
In `describeWithdrawal`, after fetching transfers, do not select by raw array index. Instead, match the transfer whose `recipient` (decoded chain/address) and token/asset correspond to `args.withdrawalParams.destinationAddress` and `args.withdrawalParams.assetId` (mirroring `findMatchingWithdrawal` used in `PoaBridge`), falling back to index only as a last resort/tie-breaker when multiple transfers match the same criteria.

### Proof of Concept
Could not be fully constructed without access to the actual Omni Bridge API's real-world ordering behavior for multi-transfer NEAR transactions — the `omni-bridge.test.ts` suite mocks `BridgeAPI.prototype.getTransfer` to return single-element arrays for each index, so it doesn't currently exercise the multi-withdrawal-per-tx ordering scenario, making it impossible to confirm from the test suite alone whether index-based lookup is safe in production against the real API. This is flagged as the key unverified assumption behind the finding.

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const transfer = (
			await this.omniBridgeAPI.getTransfer({
				transactionHash: args.tx.hash,
			})
		)[args.index];

		if (transfer == null || transfer.recipient == null) {
			return { status: "pending" };
		}

		const destinationChain = getChain(transfer.recipient as OmniAddress);
		let txHash = null;
		if (
			isEvmChain(destinationChain) ||
			destinationChain === ChainKind.Sol ||
			destinationChain === ChainKind.Fogo ||
			destinationChain === ChainKind.Strk ||
			destinationChain === ChainKind.Aptos
		) {
			txHash = transfer.finalised?.transaction_hash;
		} else if (isUtxoChain(destinationChain)) {
			// pending_sign_id is not the finalised tx hash. In rare cases, the hash may
			// change if the BTC transfer fails to be submitted. We return fast hash for FE and
			// wait for final one (transfer.finalised?.transaction_hash) for BE.
			txHash =
				typeof window !== "undefined"
					? transfer.utxo_meta?.pending_sign_id
					: transfer.finalised?.transaction_hash;
		} else {
			return { status: "completed", txHash: null };
		}

		if (!txHash) {
			return { status: "pending" };
		}

		return { status: "completed", txHash };
	}
