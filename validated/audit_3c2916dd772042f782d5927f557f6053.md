### Title
Webhook shop/topic identity not bound to HMAC, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `Utils::HmacValidator.validate` verifies the HMAC solely against that body. The `shop`, `topic`, `webhook_id`, and `api_version` values are read straight from HTTP headers that are never part of the signed material, yet they are trusted downstream to identify which merchant/tenant the event belongs to.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 

and `shop`/`topic`/`webhook_id`/`api_version` are pulled directly from unauthenticated headers: [2](#0-1) 

`Registry.process` validates only this body-bound HMAC before dispatching to the handler with the attacker-influenced `shop`: [3](#0-2) 

Because every shop that installs the same app is delivered webhooks signed with the **same** `Context.api_secret_key`, an attacker who controls a shop (e.g. a free Partner/dev store) that has the app installed can capture one legitimate webhook (valid `body` + `hmac`) delivered to their own store, then replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`) header with a victim shop's domain. `HmacValidator.validate` only checks `OpenSSL.secure_compare(computed_signature, hmac)` over the raw body — the `shop` field is never part of the signed bytes, so this replay passes validation unchanged, and `WebhookMetadata` is built with the attacker-chosen `shop` value.

This is exactly the "field acted on but not covered by the HMAC" identity-binding break described in the bug-class hint: the binding `hmac_signed_bytes == authenticated_shop_identity` does not hold, because `shop` is never part of `hmac_signed_bytes`.

### Impact Explanation
Any application built on this gem that uses `WebhookMetadata#shop` from `Registry.process` to select which tenant/session/data to act on (the documented and expected usage pattern for multi-tenant Shopify apps) can be made to process a forged, cross-tenant event: an attacker-authored payload (captured from their own store) gets attributed to a victim shop. Depending on the webhook topic handled (e.g. `app/uninstalled`, `customers/data_request`, `shop/redact`, or app-specific data-sync webhooks), this can trigger destructive or data-exfiltrating actions against a victim tenant the attacker does not own — a cross-tenant access impact.

### Likelihood Explanation
Exploitation only requires the attacker to install the app on a shop they control (trivial via a free development/partner store) to obtain one genuinely signed `(body, hmac)` pair, and to be able to reach the target app's webhook endpoint with custom headers (webhook endpoints are internet-facing by design). No access token, `client_secret`, or privileged account is needed.

### Recommendation
Bind the tenant identity to the signed material instead of trusting unauthenticated headers: verify that the `shop` (and ideally `topic`/`webhook_id`) reported for a webhook matches an independently-known, authenticated relationship (e.g., cross-check the shop against a previously stored access-token/session record, or include the shop domain in the HMAC computation if Shopify's delivery format is extended to allow it). At minimum, document prominently that `Request#shop`/`#topic` are unauthenticated and must not be trusted for tenant selection without an additional authorization check against stored session/shop state.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a store they control) and lets Shopify deliver a genuine webhook, capturing the raw body `B` and header `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC-SHA256(secret, B)`).
2. Attacker POSTs to the app's webhook endpoint with:
   - Body: `B` (unchanged)
   - `X-Shopify-Hmac-Sha256: H` (unchanged)
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (forged)
   - `X-Shopify-Topic:` unchanged or another topic value present in `B`'s original delivery
3. `ShopifyAPI::Webhooks::Request.new` builds a request object where `hmac` still equals `H` and `to_signable_string` still equals `B`.
4. `Utils::HmacValidator.validate` recomputes `HMAC-SHA256(secret, B)` and matches `H`, so validation succeeds despite the forged shop header.
5. `Registry.process` invokes the registered handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the host app to act as if the event originated from the victim shop.
