Confirmed root cause: `Webhooks::Request#to_signable_string` (the HMAC-covered payload) is only `@raw_body` [1](#0-0) , while `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from HTTP headers that are never included in the signable string [2](#0-1) . `Registry.process` validates only the HMAC of the request and then trusts `request.shop`/`request.topic`/`request.webhook_id` verbatim when building `WebhookMetadata` passed to the app's handler [3](#0-2) .

### Title
Webhook shop/topic/webhook-id identity spoofing via header fields not covered by HMAC — cross-tenant webhook confusion (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating `Utils::HmacValidator.validate(request)`, which computes the signature only over `request.to_signable_string`, i.e. the raw request body [4](#0-3) [1](#0-0) . The `shop`, `topic`, `webhook_id`, and `api_version` values are pulled directly from HTTP headers (`X-Shopify-Shop-Domain`, `X-Shopify-Topic`, `X-Shopify-Webhook-Id`, `X-Shopify-Api-Version`) which are never part of the HMAC-signed bytes [2](#0-1) . Because the app's `client_secret` (used to sign webhooks) is shared across every shop that has installed the app, any shop that has installed the app can capture one of its own genuine, validly-signed webhook deliveries (body + HMAC) and replay it to the app's webhook endpoint with the `shop`/`topic`/`webhook-id` headers swapped to point at a different tenant. `HmacValidator.validate` will still pass (it only checks the body against the shared secret), so `Registry.process` will dispatch the handler with attacker-chosen `shop`/`topic`/`webhook_id` metadata [5](#0-4) , breaking the binding: `HMAC(body, client_secret) valid` ⇏ `shop header == shop that actually sent this body`.

### Finding Description
The gem's webhook authenticity check is: "if the HMAC over the raw body verifies with our client secret, the request is a genuine Shopify webhook." That reasoning is only sound if the fields the app *acts on* to determine which tenant/topic the payload belongs to are also covered by that same signature. Here they are not:
- `hmac` is computed from `X-Shopify-Hmac-Sha256` and verified against `@raw_body` only [6](#0-5) [1](#0-0) .
- `shop`, `topic`, and `webhook_id` are read straight from attacker-controllable HTTP headers, with no cross-check against the body contents or against the shop that the caller is expected to be [7](#0-6) .
- `Registry.process` uses these unauthenticated header values as-is to build `WebhookMetadata` and hand off to the registered handler [3](#0-2) .

Since `client_secret` is one value per app (not per shop), a merchant who has legitimately installed the app receives real webhooks signed with the exact same secret used for every other merchant's shop. That merchant is an "unprivileged internet user" with respect to any other tenant of the app. By replaying a captured `(raw_body, hmac)` pair with a forged `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header, they can make the host application believe the payload originated from a different shop or represents a different topic/webhook, since none of those identity fields are bound to the signature.

### Impact Explanation
This breaks the shop-identity binding that host applications rely on to scope webhook side effects (e.g., updating per-shop records, billing, redact/GDPR topics) to the correct tenant, resulting in cross-tenant data confusion: an attacker-controlled body can be attributed to a victim shop, or a stale/benign webhook can be replayed under an attacker-chosen topic (e.g., relabeling a low-sensitivity webhook as `shop/redact` or `app/uninstalled`) to trigger unintended handler logic for another tenant. This matches the Critical "cross-tenant access" impact category since it lets one tenant inject events attributed to another tenant purely by manipulating headers outside the signed envelope.

### Likelihood Explanation
Requires only that the attacker be a legitimate (even free/trial) installer of the target app — no access to `api_secret_key`, no access token theft, and no privileged Shopify staff access. They only need to observe one of their own real webhook deliveries (trivial, since it's delivered to their own configured endpoint or can be intercepted via a proxy they control) and replay it with modified headers. Whether it is *exploitable* end-to-end still depends on how much the specific host application trusts `WebhookMetadata#shop`/`#topic` without additional checks, but the gem itself provides no protection and its documented contract implies `Registry.process` is the full authenticity check.

### Recommendation
Include the identity-relevant headers (`shop`, `topic`, `webhook_id`, `api_version`) in the HMAC signable string (or otherwise bind them cryptographically to the payload/signature) so that any header tampering invalidates the signature, mirroring the fix pattern for the referenced report class (bind every field that downstream logic acts on to the same integrity check used for authentication).

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; wait for any webhook, e.g. `orders/create`, to be delivered to the app's webhook endpoint with headers `X-Shopify-Hmac-Sha256: <H>`, `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Topic: orders/create`, `X-Shopify-Webhook-Id: <id>` and raw body `B`.
2. Replay the exact same request to the app's webhook endpoint, changing only `X-Shopify-Shop-Domain` to `victim.myshopify.com` (and/or `X-Shopify-Topic` to a topic the app treats specially, e.g. `shop/redact`).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC-SHA256(client_secret, B)` and compares it to the unchanged `X-Shopify-Hmac-Sha256` value — validation succeeds because `B` is unchanged [8](#0-7) .
4. The handler is invoked with `WebhookMetadata.new(topic: "shop/redact", shop: "victim.myshopify.com", body: <attacker's original body>, ...)` [5](#0-4) , even though `victim.myshopify.com` never sent this request.
