### Title
Webhook Shop-Domain Spoofing via HMAC Scope Gap Enables Cross-Tenant Event Injection - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
The gem's webhook HMAC verification only covers the raw request body. The `shop-domain`, `topic`, and `webhook-id` headers — which are the identity fields the library hands to the app's handler as the authoritative tenant/event context — are never included in the signed bytes. An unprivileged attacker who owns any Shopify shop and can obtain one valid (body, HMAC) pair from a legitimate webhook delivery to their own store can replay that exact body with a forged `shop-domain` header pointing at a victim shop, and the library will accept it as authentic.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate_signature` computes and compares the HMAC exclusively over that signable string: [2](#0-1) 

Meanwhile, `shop`, `topic`, and `webhook_id` are read straight from unauthenticated HTTP headers with no cryptographic binding to the signature at all: [3](#0-2) 

`Registry.process` verifies the HMAC and then dispatches to the app's handler using `request.shop` as the trusted tenant identifier for the event, with no additional check that `shop` corresponds to the signed body: [4](#0-3) 

**Broken identity binding (equality that should hold but doesn't):**
`shop header value used to attribute the event == shop that Shopify actually signed the payload for`

Before request: Shopify signs `(body_A, hmac_A)` for `shop = attacker-shop.myshopify.com`, delivered with header `shopify-shop-domain: attacker-shop.myshopify.com`.

After attacker's request: attacker resends `(body_A, hmac_A)` unchanged (so `HmacValidator.validate` still passes, since it only checks `body_A`/`hmac_A`), but sets `shopify-shop-domain: victim-shop.myshopify.com`. `Registry.process` still passes validation and invokes `handler.handle(data: WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body: parsed_body_A, ...))` — the app now processes an attacker-supplied body under the victim's tenant identity, with the library asserting it is authentic.

This exactly parallels the report's root-cause class: a field that is acted upon (here, `shop`, used to route/attribute the event to a tenant) is not covered by the authenticating signature (here, the HMAC), so its trust is illusory.

### Impact Explanation
This breaks the tenant boundary the whole `ShopifyAPI::Webhooks` subsystem exists to enforce: host applications rely on `WebhookMetadata#shop` (sourced from `request.shop`) as a trustworthy, HMAC-verified indicator of which merchant/tenant the event belongs to. An attacker who legitimately controls any single Shopify store (installing a free/trial app, at no privileged cost) can:
- Get Shopify to sign an arbitrary body of their choosing for their own shop (e.g., by editing a product/order to embed attacker-chosen content, or by using any webhook topic whose payload content they control).
- Replay that valid `(body, hmac)` pair with a forged `shop-domain` header naming any victim shop.
- Cause the app to process attacker-controlled webhook content as if it originated from — and pertains to — the victim tenant.

Depending on how the host app uses the `shop` and `topic` fields (which is the intended integration pattern the gem documents), this enables cross-tenant data injection/corruption, spoofing of lifecycle events (e.g., forging `app/uninstalled`, GDPR `shop/redact`, `customers/data_request`, etc., for a victim shop attacker does not own), or otherwise causing state or side effects to be applied to a shop the attacker has no authorization over. This is a cross-tenant integrity/authentication violation attributable entirely to the gem's HMAC scope, matching the required "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high: no special privileges, no leaked secrets, and no access to `api_secret_key` are required. The only requirement is that the attacker operate any ordinary Shopify store with the target app installed (a normal, unprivileged action any internet user can take), then capture and replay one legitimate webhook delivery with a modified header — an entirely client-side, unauthenticated HTTP manipulation.

### Recommendation
Bind the identity headers into the signed material, or otherwise cryptographically tie `shop`, `topic`, and `webhook_id` to the HMAC verification step:
- Extend `Utils::VerifiableQuery`/`HmacValidator` so that webhook validation computes/compares the HMAC over a canonical representation that includes `shop-domain` (and ideally `topic`/`webhook-id`), not just the raw body, OR
- After HMAC validation, independently verify `request.shop` against session/app-install state (e.g., confirm the shop is a store known to have this app installed) rather than trusting the header outright, and reject mismatches before invoking the handler.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a webhook (e.g., edits a product to include attacker-chosen JSON content in `body`). Shopify delivers:
   ```
   POST /webhooks
   x-shopify-topic: products/update
   x-shopify-hmac-sha256: <valid HMAC of body over app's real secret>
   x-shopify-shop-domain: attacker-shop.myshopify.com
   x-shopify-webhook-id: <id>
   Body: { ...attacker-controlled JSON... }
   ```
2. Attacker replays the identical body and `x-shopify-hmac-sha256` value to the app's webhook endpoint, only changing:
   ```
   x-shopify-shop-domain: victim-shop.myshopify.com
   ```
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `body`/`hmac` [5](#0-4) .
4. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and the attacker-crafted body, believing it is an authentic event for the victim tenant.
