### Title
Emporium Min-circuit path (`erc20TokenAddresses.length==0`) bypasses all balance/UTXO accounting, allowing theft of any resident token balance in Emporium - ([File: contracts/CircomDataBuilder.sol], [File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol], [File: contracts/Hinkal.sol])

### Summary
When `circomData.externalActionData.externalActionId == HINKAL_EMPORIUM_ACTION_ID && circomData.erc20TokenAddresses.length == 0`, `CircomDataBuilder.formInputForCircom` routes to `formInputEmporiumMin`, whose public-input vector is only `[emporiumMessage, timeStamp, calldataHash]`, matching the `MainEVMCircuitMin` circuit which contains no `rootHashHinkal`, nullifier, `erc20TokenAddresses`, or `amountChanges` signals at all. Because every downstream balance-accounting loop in `Hinkal.transact` and `EmporiumUpgradeable.runAction` is keyed on `circomData.erc20TokenAddresses.length`, an empty array makes them all no-ops, letting an attacker's `EmporiumStack` "CASE 2" stateless op transfer any ERC20 balance resident in the Emporium contract with zero on-chain accounting.

### Finding Description
The claimed broken equality is: `net tokens leaving Emporium via this action == -deltaAmountChanges credited into the proof`. For the Min path this equality is never evaluated because `deltaAmountChanges`/`amountChanges` do not exist in scope at all.

Trace:
- `CircomDataBuilder.formInputEmporiumMin` (`contracts/CircomDataBuilder.sol:150-161`) builds only 3 public signals — `emporiumMessage`, `timeStamp`, `calldataHash`.
- `circuits/MainEVMCircuitMin.circom:6-18` confirms the Min template only has `outTimeStamp`, `calldataHash` as public inputs and a private `messageSeed` whose Poseidon hash is checked against `emporiumMessage` — no UTXO root, nullifier, token, or amount signals exist anywhere in this circuit.
- In `Hinkal.transact` (`contracts/Hinkal.sol:97-147`), the balance-diff/slippage/UTXO-matching loop iterates `circomData.erc20TokenAddresses.length` times; with length `0` this loop performs zero iterations, so no balance check of any kind is performed for the transaction.
- `_externalTransact` (`contracts/Hinkal.sol:234-261`) builds `deltaAmountChanges` with length equal to `circomData.erc20TokenAddresses.length` (i.e. empty) and passes it to `EmporiumUpgradeable.runAction`.
- `EmporiumUpgradeable.runAction` (`contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol:76-160`) executes every `EmporiumOperation` in the attacker-supplied `EmporiumStack`. For "CASE 2: Stateless Interaction" (`EmporiumUpgradeable.sol:102-113`), it performs an arbitrary `op.endpoint.call{value: op.value}(op.callData)` as long as the selector isn't `callHinkalWallet`/`doSendToRelay`. If `stack.signerAddress == address(0)`, `verifyWallet` (`EmporiumUpgradeable.sol:302-316`) returns immediately without any signature check, so the attacker fully controls the op contents.
- After the ops run, the balance-reconciliation loop (`EmporiumUpgradeable.sol:132-159`) — which is the only code that would detect/convert an unexpected balance decrease/increase into an accounted UTXO or revert — also iterates over `circomData.erc20TokenAddresses`, which is empty, so it performs zero iterations and enforces nothing.

Exploit flow: attacker submits `Hinkal.transact` with a Min-circuit proof (`erc20TokenAddresses = []`, `amountChanges = []`), `externalActionId = HINKAL_EMPORIUM_ACTION_ID`, and `externalActionMetadata` encoding an `EmporiumStack{signerAddress: address(0), ops: [{endpoint: dustToken, invokeWallet: false, callData: abi.encodeCall(IERC20.transfer, (attackerEOA, dustAmount))}]}`. The CASE 2 branch executes `dustToken.transfer(attackerEOA, dustAmount)` with `msg.sender == Emporium`, moving out any ERC20 balance currently sitting in the Emporium contract (e.g., dust left behind by a prior action that swapped/transferred an unlisted token into Emporium without ever declaring it in `erc20TokenAddresses`). Neither `Hinkal.transact`'s balance loop nor `EmporiumUpgradeable.runAction`'s balance loop execute because both are gated on the (attacker-chosen, zero) length of `erc20TokenAddresses`, so the transfer is entirely unconstrained and unaccounted.

Existing guards do not stop this: `performHinkalChecks`/`dimensionsCheck`/`checkOnchainCreation` validate array-length consistency and calldata-hash integrity but never require `erc20TokenAddresses.length > 0`; `verifyProof` only checks the (deliberately minimal) Min public-input vector; `rootHashExists`, `insertNullifiers` are unrelated to this token-balance path since the Min circuit never binds a Merkle root or nullifier; `onlyAllowedRecipient` only restricts the caller of `runAction` to be the Hinkal contract itself, not what the op inside the stack does.

### Impact Explanation
Direct theft of any ERC20 balance held by the Emporium contract (dust from previous unlisted-token operations, or any token accidentally/incidentally resident there) with zero on-chain accounting or reversion — matching the Critical category "direct theft of shielded or in-flight user funds" since such dust originates from a prior user's action that was never converted into a tracked UTXO. The attack is repeatable for every distinct ERC20 balance the Emporium contract holds and requires no privileged role, only the ability to submit a self-generated Min-circuit proof.

### Likelihood Explanation
Preconditions: (1) some ERC20 token balance must already be resident in the Emporium contract and not currently listed as part of an in-flight accounted action (e.g., left over from a prior CASE 2 op that interacted with a token not declared in `erc20TokenAddresses`), and (2) the attacker must know/discover the token address and amount (observable on-chain via `balanceOf`). Generating a valid Min-circuit proof only requires knowledge of a `messageSeed` chosen by the attacker themselves — trivial, since they are proving their own message, not spending anyone else's UTXO. No signature check is required because `stack.signerAddress` can be `address(0)`. This makes the attack cheap, fully attacker-controlled, and repeatable against any future dust that accumulates.

### Recommendation
Do not gate the balance-reconciliation/accounting loops in `Hinkal.transact` and `EmporiumUpgradeable.runAction` purely on `circomData.erc20TokenAddresses.length`. Either (a) forbid the Min-circuit path from executing CASE 2 stateless calls to arbitrary endpoints (restrict Min-circuit `EmporiumStack` to invoke-wallet-only or non-token-affecting calls), or (b) require the Min circuit/public inputs to still commit to and constrain a snapshot of Emporium's full token balance set (or at minimum require any token balance change resulting from ops to be swept/verified regardless of whether it appears in `erc20TokenAddresses`), or (c) require `erc20TokenAddresses.length > 0` whenever an `EmporiumStack` contains any CASE 2 op touching ERC20 `transfer`/`transferFrom`-capable selectors.

### Proof of Concept
Hardhat test plan:
1. Deploy `Hinkal`, `EmporiumUpgradeable`, an ERC20 test token, and register Emporium as an external action with `HINKAL_EMPORIUM_ACTION_ID`.
2. Simulate "dust": have a legitimate prior `transact` (or a direct `token.transfer` to the Emporium contract address) leave `dustAmount` of `dustToken` sitting in Emporium's balance without it being included in that action's `erc20TokenAddresses`.
3. As attacker EOA, construct `CircomData` with `erc20TokenAddresses = []`, `amountChanges = []`, `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `externalActionMetadata` = ABI-encoded `EmporiumStack{signerAddress: address(0), ops: [{endpoint: dustToken, invokeWallet: false, value: 0, callData: abi.encodeCall(IERC20.transfer, (attackerEOA, dustAmount))}]}`.
4. Generate a valid Min-circuit proof locally for `MainEVMCircuitMin` using an attacker-chosen `messageSeed`, matching `emporiumMessage`, `timeStamp`, `calldataHash`.
5. Call `Hinkal.transact(a, b, c, dimensions, circomData)` from the attacker EOA.
6. Assert: (a) `token.balanceOf(attackerEOA)` increases by `dustAmount`; (b) `circomData.amountChanges.length == 0` and no `require` inside `Hinkal.transact`'s balance loop or `EmporiumUpgradeable.runAction`'s balance loop executed (loop trip count == 0, verifiable via coverage or by removing dust precondition and showing no revert path exists); (c) no nullifier was inserted/consumed corresponding to `dustAmount`, confirming the theft is entirely unaccounted.
