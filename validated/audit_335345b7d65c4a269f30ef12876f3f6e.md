Audit Report

## Title
`reward_per_token` rounds to zero due to insufficient `PRECISION_SCALING_FACTOR` in `pallet-asset-rewards` - (File: `substrate/frame/asset-rewards/src/lib.rs`)

## Summary
`pallet-asset-rewards` computes a per-block accumulator (`reward_per_token_stored`) using a fixed scaling constant `PRECISION_SCALING_FACTOR` set to `4096` [1](#0-0) . When `total_tokens_staked` is large relative to `reward_rate_per_block * blocks_elapsed * 4096`, integer division truncates the per-block reward delta to zero, permanently losing that block's reward slice for all stakers in the pool.

## Finding Description
`reward_per_token` computes `reward_per_token_stored + (reward_rate_per_block * blocks_elapsed * PRECISION_SCALING_FACTOR) / total_tokens_staked` [2](#0-1) . Because `PRECISION_SCALING_FACTOR` is only `4096` (2^12) rather than a larger fixed-point base like `1e18`, the numerator can easily be smaller than `total_tokens_staked` for realistic pools (e.g., staking assets with 12-18 decimal precision and modest reward rates), causing the division to truncate to `0`. `derive_rewards` then divides the accumulated delta by the same small `PRECISION_SCALING_FACTOR` [3](#0-2) , so any zero rounding in the intermediate step is not recoverable — `reward_per_token_stored` never accumulates the lost fraction. There is no minimum-stake guard, reward-rate validation, or alternative wide-precision (e.g., `U256`) intermediate calculation in this pallet to mitigate the issue, unlike `pallet-nomination-pools`'s `balance_to_point`/`point_to_balance`, which explicitly use `U256` intermediates [4](#0-3) . This function is called on every staker interaction via `update_pool_and_staker_rewards` [5](#0-4) .

## Impact Explanation
Stakers permanently lose yield whenever the per-block reward delta rounds down to zero — this is a real, structural precision-loss flaw, not a contrived edge case, since it is entirely plausible for a pool operator to create a pool with a large-decimal staking asset and modest emission rate without violating any pallet invariant.

## Likelihood Explanation
No privileged action is required by the exploiting party; only the pool creator's parameter choice (a plausible, non-malicious configuration of `reward_rate_per_block` relative to `total_tokens_staked`) needs to occur. Any staker using the standard `stake`/`unstake`/`claim_rewards` extrinsics will experience this precision loss under such conditions, and it will silently, repeatedly occur without any recovery mechanism.

## Recommendation
Increase `PRECISION_SCALING_FACTOR` to a substantially larger value (e.g. `1e18`) or switch to a wide-precision (`U256`) intermediate computation in `reward_per_token`/`derive_rewards`, mirroring the pattern already used in `pallet-nomination-pools`'s `balance_to_point`, or adopt a `FixedU128`/`RewardCounter`-style fixed-point accumulator as used by `pallet-nomination-pools`.

## Proof of Concept
1. Create an asset-rewards pool with a staking asset using 12-decimal precision, `total_tokens_staked = 10_000 * 10^12`, and `reward_rate_per_block = 1000`.
2. After 1 block elapses, `reward_per_token` computes `1000 * 1 * 4096 / (10_000 * 10^12) = 4_096_000 / 10^16 = 0` due to integer truncation.
3. Repeating this over many blocks under the same conditions shows `reward_per_token_stored` never increases and `derive_rewards` yields `0` for all stakers, confirming rewards are permanently lost despite ongoing pool emissions.
