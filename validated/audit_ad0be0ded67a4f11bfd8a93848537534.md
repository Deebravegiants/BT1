### Title
Webhook `shop` domain is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` reads the tenant identifier (`shop`) straight out of the `X-Shopify-Shop-Domain` HTTP header, but the HMAC signature that `HmacValidator` verifies only covers the raw request body, not this header. Because the webhook signing secret (`api_secret_key`) is shared by every shop that installs the same app, anyone who has installed the app on their own store can capture a validly-signed webhook and replay it to the host app's webhook endpoint with the shop-domain header rewritten to point at a different, victim shop. `HmacValidator.validate` still passes (it only re-hashes the untouched body), so `Registry.process` will hand the handler a `WebhookMetadata` whose `shop` field names an arbitrary tenant the attacker does not control.

### Finding Description
`VerifiableQuery#to_signable_string` for a webhook request returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, however, is derived purely from an unauthenticated header: [2](#0-1) 

`HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` (i.e., the body only) and compares it with the `hmac` header: [3](#0-2) 

`Registry.process` trusts this HMAC check as the sole authentication step, then forwards the untrusted `request.shop` value straight into the handler's `WebhookMetadata`: [4](#0-3) 

This breaks the identity binding: `shop == "the tenant whose data this webhook body describes"` should hold, but the code only proves `hmac == HMAC(body, api_secret_key)`. Since `api_secret_key` is per-app (not per-shop), any legitimate installer of the app can obtain a validly-signed body/HMAC pair for their own shop and then submit it with an arbitrary `X-Shopify-Shop-Domain` value. The library performs no check that the signed body actually originates from, or is scoped to, the shop named in the header.

### Impact Explanation
This is a cross-tenant identity confusion: a host application built on this gem uses `WebhookMetadata#shop` (sourced from `request.shop`) to decide which tenant's records to update, e.g. app-uninstall cleanup, order data ingestion, or `customers/redact`/`shop/redact` compliance processing. An attacker who merely installs the app on their own shop can forge webhooks that are processed by the host app under a victim shop's identity, since the signature check never binds the signed bytes to the shop header. Depending on the handler, this can lead to cross-tenant data corruption, spurious deletion/redaction actions performed against another merchant's account, or state confusion that undermines per-tenant isolation — matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation only requires an attacker to be a legitimate (unprivileged) installer of the target app — a capability any internet user has for public Shopify apps — and the ability to intercept/replay one of their own genuine webhook deliveries with a modified header, which is trivial once the body+HMAC pair is captured (no cryptographic secret needs to be broken). The gem provides no additional binding (e.g., signing the shop domain, or requiring the shop to match an already-known installation) to prevent this, so likelihood is high wherever a host app trusts `WebhookMetadata#shop` for tenant selection.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) as part of the HMAC-signed content, or independently verify that `request.shop` corresponds to a shop with a known, previously-established session/installation for this app before dispatching to the handler. At minimum, document and enforce that host applications must cross-check `request.shop` against their own installation records rather than trusting it as authenticated solely because the body-only HMAC validated.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`.
2. Attacker triggers/receives a real webhook from Shopify, e.g. `orders/create`, with body `B` and header `X-Shopify-Hmac-Sha256: H = HMAC_SHA256(api_secret_key, B)`.
3. Attacker resends the same `(B, H)` pair to the host application's webhook endpoint but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses `shop` from the forged header: [2](#0-1) 
5. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `B` only and matches `H`, so validation succeeds: [5](#0-4) 
6. The handler is invoked with `WebhookMetadata.new(... shop: request.shop ...)` equal to `"victim-shop.myshopify.com"`, even though the body actually originated from the attacker's own shop, allowing the host app to act on victim-shop's behalf with attacker-controlled body data: [6](#0-5)

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

          end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
