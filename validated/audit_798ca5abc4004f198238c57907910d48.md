### Title
Simplex solver prices exotic tokens from a single spot Uniswap V4 pool with no TWAP/impact accounting, so an attacker can manipulate the spot price within an optional, statically-bounded guard to extract solver funds - ([File: sdk/packages/simplex/src/funding/uniswapV4/UniswapV4FundingPlanner.ts])

### Summary
The Simplex intent-solver's pool-based pricing strategy computes an exotic token's USD price directly from `sqrtPriceX96` of the most-liquid configured Uniswap V4 position and uses that instantaneous spot price both to quote bids and to size actual liquidity withdrawals used to fund a fill. [1](#0-0)  The only defense against a manipulated/thin pool is `checkPriceGuard`, comparing against a static `referencePrice`/`maxDeviationBps` pair that is optional per-chain configuration — omitting it (or setting too wide a tolerance) leaves the chain completely unguarded, and even when configured it only bounds deviation from a stale reference, not execution slippage or the pool's own fee tier. [2](#0-1) 

### Finding Description
`UniswapV4FundingPlanner.getExoticTokenPrice` derives the USD price of the exotic asset purely from `sdkPool.token0Price`/`token1Price`, i.e., the current tick/`sqrtPriceX96` of the on-chain pool, selecting the position with the largest configured pool liquidity: [1](#0-0) [3](#0-2) 

This is the exact bug class behind the Solend incident: a price is read directly off an AMM/pool state ("oracle") that any actor can move within a single transaction (e.g., a large swap or flash-loan-funded trade), rather than from a manipulation-resistant TWAP or external price feed. The documentation for this feature explicitly acknowledges the exposure: "Pool-based pricing trusts the live pool, which leaves the solver exposed to a manipulated, stale, or thin pool returning a bad quote." [4](#0-3) 

The only mitigation, `checkPriceGuard` (referenced in `sdk/packages/simplex/src/strategies/fx.ts` and `sdk/packages/simplex/src/core/boot.ts`), is:
- Optional — a chain with no `referencePrice`/`maxDeviationBps` pair is "left unguarded" per the docs. [5](#0-4) 
- Bound only to the two fields set together at config time in `boot.ts`: [6](#0-5) 
- A pure deviation check against a static number, not a TWAP, not an execution-cost/slippage model. The engineering notes explicitly state: "`checkPriceGuard` is the only defense on this path, and it checks deviation from a static reference, not execution cost." [7](#0-6) 

Because the same spot price feeds both (a) the bid/quote computation and (b) the actual withdrawal sizing via `planWithdrawalForToken` → `findLiquidityForDeficit` (binary search against the pool's spot-derived amounts) [8](#0-7) , an attacker who moves the pool price within `maxDeviationBps` (or on an unguarded chain, arbitrarily) can induce the solver to quote and fill orders at an economically unfavorable rate relative to the pool's/liquidity's true value, extracting value from the solver's LP position on a single intent fill.

### Impact Explanation
An attacker reachable only via submitting an ordinary cross-chain intent (an unprivileged user of the intent gateway/solver) can manipulate the reference AMM pool immediately before submitting/timing an order that the vulnerable solver picks up, causing the solver to withdraw liquidity and deliver output tokens priced off the manipulated spot rate. This directly causes concrete monetary loss to the solver's Uniswap V4-backed inventory — the same bad-debt/loss pattern as the Solend USDH/Kamino isolated-pool oracle incident, where a manipulable on-chain price feed with insufficient guardrails let an attacker extract funds from a specific pool/position. This is High severity because it is a direct-fund-loss vector reachable from a single externally submitted order/fill against the solver's own capital.

### Likelihood Explanation
Likelihood is elevated because:
1. The `referencePrice`/`maxDeviationBps` guard is opt-in per chain — deployments without it are fully exposed. [5](#0-4) 
2. Even guarded chains only bound the deviation from a static reference, not the fee-tier or slippage impact of actually swapping through the pool to satisfy the withdrawal, so an attacker can stay inside the deviation bound while still profiting from the mispricing. [7](#0-6) 
3. The pool selected for pricing is simply "the most-liquid qualifying pool," which can still be relatively thin/manipulable compared to CEX-level liquidity for an exotic pair. [9](#0-8) 

### Recommendation
- Use a manipulation-resistant TWAP (or an external oracle cross-check) rather than raw `sqrtPriceX96` spot price for `computeDirectPoolPriceUsd`.
- Make the `referencePrice`/`maxDeviationBps` guard mandatory (not optional) for any chain using Uniswap V4 pool-based pricing.
- Incorporate the pool's own fee tier and expected swap/price-impact cost into the price guard so that in-bound deviation cannot still be profitably exploited during the actual liquidity withdrawal.
- Rate-limit or require multi-block price confirmation before sizing large withdrawals against a single spot read.

### Proof of Concept
1. Attacker identifies a Simplex solver configured with `[vault.uniswapV4]` pool-based pricing for an exotic/stable pair, either with no `referencePrice` guard or with a wide `maxDeviationBps`. [10](#0-9) 
2. Attacker swaps a large amount through the underlying Uniswap V4 pool (same pool used by `UniswapV4FundingPlanner`) to move `sqrtPriceX96`/tick, shifting `token0Price`/`token1Price` away from the true market price but within any configured deviation bound.
3. Attacker submits (or waits for) a cross-chain intent order that the solver's `FXFiller`/`UniswapV4FundingPlanner` prices using `getExoticTokenPrice`, which reads the manipulated spot price. [1](#0-0) 
4. The solver withdraws liquidity via `planWithdrawalForToken`, sized against the manipulated price, and fills the order — delivering more value than it should relative to true market price. [11](#0-10) 
5. Attacker reverses the initial pool swap (or lets arbitrageurs restore the price), retaining the mispriced fill proceeds — net profit at the solver's expense.

Note: Full verification of `checkPriceGuard`'s exact deviation-check code path in `sdk/packages/simplex/src/strategies/fx.ts` was not completed within the available exploration; the description above is based on the documented behavior and the flow notes confirming it only checks static deviation, not execution cost. 	async getExoticTokenPrice(chain: string, exoticToken: string): Promise<Decimal | null> {
		const state = this.stateByChain.get(chain)
		if (!state || !state.isHydrated()) return null

		try {
			await state.refresh()
		} catch (err) {
			this.logger.error({ err, chain }, "Failed to refresh state for price query")
			return null
		}

		const tokenLower = exoticToken.toLowerCase()
		let bestPrice: Decimal | null = null
		let bestLiquidity = 0n

		for (const pos of state.allPositions()) {
			if (pos.currency0.toLowerCase() !== tokenLower && pos.currency1.toLowerCase() !== tokenLower) continue
			const sdkPool = state.getSdkPool(pos.tokenId)
			if (!sdkPool) continue

			const result = this.computeDirectPoolPriceUsd(pos, sdkPool, chain)
			if (result && result.exoticToken.toLowerCase() === tokenLower) {
				const poolLiquidity = state.getPoolLiquidity(pos.tokenId)
				if (poolLiquidity > bestLiquidity) {
					bestPrice = result.priceUsd
					bestLiquidity = poolLiquidity
				}
			}
		}

		if (bestPrice) {
			this.logger.debug({ chain, token: tokenLower, priceUsd: bestPrice.toString() }, "Exotic token price computed")
		}
		return bestPrice
	}

	private computeDirectPoolPriceUsd(
		pos: HydratedV4Position,
		sdkPool: V4Pool,
		chain: string,
	): { exoticToken: string; priceUsd: Decimal } | null {
		const usdc = this.configService.getUsdcAsset(chain).toLowerCase()
		const usdt = this.configService.getUsdtAsset(chain).toLowerCase()
		const c0 = pos.currency0.toLowerCase()
		const c1 = pos.currency1.toLowerCase()

		if (c0 === usdc || c0 === usdt) {
			// currency0 is stable → exotic is currency1
			// token1Price = "token0 per token1" = USD per exotic
			return {
				exoticToken: c1,
				priceUsd: new Decimal(sdkPool.token1Price.toFixed(18)),
			}
		}

		if (c1 === usdc || c1 === usdt) {
			// currency1 is stable → exotic is currency0
			// token0Price = "token1 per token0" = USD per exotic
			return {
				exoticToken: c0,
				priceUsd: new Decimal(sdkPool.token0Price.toFixed(18)),
			}
		}

		return null
	}

	async planWithdrawalForToken(
		destChain: string,
		solver: HexString,
		tokenOutLower: string,
		amountNeeded: bigint,
		deadlineTimestamp?: bigint,
	): Promise<FundingPlanResult> {
		const noopResult: FundingPlanResult = { calls: [], credited: 0n }

		this.logger.debug(
			{
				destChain,
				solver,
				tokenOutLower,
				amountNeeded: amountNeeded.toString(),
			},
			"UniswapV4 planWithdrawalForToken called",
		)

		if (amountNeeded <= 0n) return noopResult

		const state = this.stateByChain.get(destChain)
		if (!state || !state.isHydrated()) {
			this.logger.debug(
				{ destChain, hasState: !!state, isHydrated: state?.isHydrated() },
				"UniswapV4 no state or not hydrated",
			)
			return noopResult
		}

		const mutex = this.mutexByChain.get(destChain)!
		return mutex.runExclusive(async () => {
			// Refresh on-chain state for this chain right before planning so
			// liquidity and price data are as fresh as possible.
			await state.refresh()

			const tokenNeed = tokenOutLower.toLowerCase()
			const candidates = state
				.positionsForToken(tokenNeed)
				.sort((a, b) => (b.remainingLiquidity > a.remainingLiquidity ? 1 : -1))

			this.logger.debug(
				{
					tokenNeed,
					candidateCount: candidates.length,
					candidates: candidates.map((c) => ({
						tokenId: c.tokenId.toString(),
						remainingLiquidity: c.remainingLiquidity.toString(),
						currency0: c.currency0,
						currency1: c.currency1,
					})),
				},
				"UniswapV4 candidates found",
			)

			let remaining = amountNeeded
			const allCalls: ERC7821Call[] = []
			let totalCredited = 0n

			for (const pos of candidates) {
				if (remaining <= 0n) break

				const availLiq = state.remaining(pos.tokenId)
				if (availLiq === 0n) continue

				const isToken0 = pos.currency0.toLowerCase() === tokenNeed

				// Bump the target by the slippage tolerance (10 bps) so the V4
				// withdrawal overshoots the exact amount needed.  This ensures
				// that even in the worst-case slippage scenario the credited
				// tokens still cover the fill requirement, avoiding a wasted
				// revert on the entire ERC-7821 batch.
				const slippageBps = BigInt(this.slippageTolerance.numerator.toString()) * 10_000n / BigInt(this.slippageTolerance.denominator.toString())
				const bufferedRemaining = remaining + (remaining * slippageBps) / 10_000n

				// Use binary search to find the minimal liquidity that covers the buffered target
				const neededLiq = this.findLiquidityForDeficit(state, pos, isToken0, bufferedRemaining)
				if (neededLiq <= 0n) continue

				const cappedLiq = neededLiq > availLiq ? availLiq : neededLiq

				// Resolve the percentage the calldata will carry *before* pricing the
				// withdrawal, and price it from the liquidity that percentage actually
				// decreases. Pricing `cappedLiq` instead over-credits by the SDK's
				// truncation, and the fill sized against that credit reverts.
				const removal = liquidityRemoval(pos.liquidity, cappedLiq)
				if (!removal) continue

				// Build SDK Position to compute expected amounts
				const sdkPosition = state.buildSdkPosition(pos.tokenId, removal.liquidity)
				if (!sdkPosition) continue

				// The SDK Position computes amounts for the given liquidity
				const amount0 = BigInt(sdkPosition.amount0.quotient.toString())
				const amount1 = BigInt(sdkPosition.amount1.quotient.toString())
				const credit = isToken0 ? amount0 : amount1

				this.logger.debug(
					{
						tokenId: pos.tokenId.toString(),
						isToken0,
						sqrtPriceX96: pos.sqrtPriceX96.toString(),
						neededLiq: neededLiq.toString(),
						availLiq: availLiq.toString(),
						cappedLiq: cappedLiq.toString(),
						removedLiq: removal.liquidity.toString(),
						amount0: amount0.toString(),
						amount1: amount1.toString(),
						credit: credit.toString(),
						requestedDeficit: remaining.toString(),
						bufferedDeficit: bufferedRemaining.toString(),
					},
					"UniswapV4 per-position calculation",
				)

				if (credit === 0n) continue

				// Use V4PositionManager.removeCallParameters to generate the calldata
				// This encodes DECREASE_LIQUIDITY + TAKE_PAIR actions internally
				const call = this.buildRemoveLiquidityCall(state, pos, removal.percentage, deadlineTimestamp)
				if (!call) continue

				allCalls.push(call)
				totalCredited += credit
				remaining -= credit
				state.consume(pos.tokenId, removal.liquidity)

## Uniswap price guards

Pool-based pricing trusts the live pool, which leaves the solver exposed to a manipulated, stale, or thin pool returning a bad quote. To bound that risk, give a position a **`referencePrice`** and **`maxDeviationBps`**. Whenever the pool quote on that chain drifts more than `maxDeviationBps` above or below the reference, the solver refuses to fill — the order is rejected before any bid is submitted.

`referencePrice` is expressed in **exotic tokens per USD**, the same units as the bid/ask curves. The two fields must be set together; omit both to leave the chain unguarded.

```toml lineNumbers
[vault.uniswapV4]
# referencePrice is the expected cNGN per USD;
# reject if the quote is more than 2% off.
# The two go together — one without the other is rejected.
[[vault.uniswapV4.positions]]
chain           = "EVM-8453"
tokenId         = "2087350"
referencePrice  = "1575"
maxDeviationBps = 200
```

`computeDirectPoolPriceUsd` returns the **raw pool mid** derived from `sqrtPriceX96`. The pool's
fee tier is read and stored on the hydrated position (`pos.fee`) but never applied to the price,
and there is no size or impact term — `computeLegPolicyOutput` extends the mid linearly across the
whole priced quantity. `checkPriceGuard` is the only defense on this path, and it checks deviation
from a static reference, not execution cost. A venue-priced pair that has to swap through its own
pool to source inventory pays a fee tier it never quoted against.
