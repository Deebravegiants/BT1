## Custody Analog Found: Replayable `transfer_from` approval signature in the USDK stablecoin example

### Title
Non-consuming nonce allows unlimited replay of `transfer_from` approval signatures, draining fungible-asset balances - ([File: aptos-move/move-examples/fungible_asset/stablecoin/sources/usdk.move])

### Summary
`usdk::transfer_from` implements an ERC20-`permit`-style delegated-transfer flow: the token owner signs an off-chain `Approval` message authorizing a `spender` to move `amount` tokens, and any address can submit that signature on-chain. The "nonce" field of the signed message is set to `account::get_sequence_number(from)` [1](#0-0) , but nothing in `transfer_from` increments, consumes, or otherwise invalidates that sequence number, and the module provides no `revoke_approval`/cancel function. Since `from` is not the transaction sender in this flow, `from`'s account sequence number is not advanced by this call — it only changes when `from` itself submits a transaction. As a result, the same signed `Approval` message remains valid and can be resubmitted an unlimited number of times by the spender (or by anyone who obtains the signature bytes), each time transferring `amount` again, until `from` happens to issue an unrelated transaction.

### Finding Description
`transfer_from` builds the challenge struct entirely from on-chain/caller-supplied state:
```
let expected_message = Approval {
    owner: from,
    to: to,
    nonce: account::get_sequence_number(from),
    chain_id: chain_id::get(),
    spender: signer::address_of(spender),
    amount,
};
account::verify_signed_message(from, from_account_scheme, from_public_key, proof, expected_message);
``` [1](#0-0) 

Compare this to the framework's own capability-delegation patterns (`offer_signer_capability`, `offer_rotation_capability`, `rotate_authentication_key`), which likewise embed `sequence_number` in the signed challenge, but those flows are always executed by the account itself (`account: &signer`) so the sequence number is guaranteed to increment as a side effect of the enclosing transaction, and they additionally expose `revoke_signer_capability` / `revoke_any_signer_capability` for explicit revocation [2](#0-1) . `transfer_from` breaks that invariant: the signer of the enclosing transaction is `spender`, not `from`, so `from`'s sequence number is untouched by a successful `transfer_from` call. The "nonce" therefore does not behave as a nonce at all — it is effectively a static value that stays constant across arbitrarily many uses of the same signature, and the module has no mechanism (no mapping of used nonces, no explicit approval-cancellation entry function) to invalidate a previously issued approval.

The actual value transfer happens via `primary_fungible_store::transfer_with_ref(transfer_ref, from, to, amount)` [3](#0-2) , using the privileged `TransferRef` stored in `Management` [4](#0-3) , so each replay moves real custody of the fungible asset out of `from`'s primary store regardless of `from`'s actual current intent.

### Impact Explanation
This is a direct custody break for a fungible-asset holder: any party who has ever obtained a single validly signed `Approval` (e.g., a spender who was authorized once for `amount`) can call `transfer_from` repeatedly, draining `from`'s balance far beyond the amount the owner intended to authorize, for as long as `from`'s account sequence number remains unchanged (which can be indefinitely for a wallet that primarily *receives* funds and rarely submits transactions itself). Because `to` is fixed inside the signed struct but nothing prevents replay, the spender can also front-run and race to reuse the signature multiple times in quick succession before the owner notices. There is no way for the owner to invalidate a leaked/stale approval short of rotating their auth key or otherwise forcing their own sequence number to change — matching the exact "no revocation" gap called out in the external report.

### Likelihood Explanation
Likelihood is high in any deployment that reuses this example pattern for a live stablecoin: `transfer_from` is a `public fun` reachable by anyone holding a copy of a previously issued signature, requires no special privilege from the caller, and the missing consumption is a straightforward logic gap rather than a rare edge case — it triggers on the very first successful call and every call thereafter.

### Recommendation
Bind the approval to a monotonically increasing, explicitly-stored nonce per `(owner)` (or per `(owner, spender)`) that is incremented on-chain inside `transfer_from` itself, independent of the owner's account sequence number, and provide an explicit `revoke_approval`/`increment_nonce` entry function the owner can call to invalidate outstanding signatures. Alternatively, add a `deadline`/single-use marker consumed atomically with the transfer.

### Proof of Concept
1. `owner` (`from`) signs one `Approval{owner: from, to: attacker, nonce: account::get_sequence_number(from), chain_id, spender: attacker, amount: 100}` and hands it to `attacker` as a one-time authorization for 100 USDK.
2. `attacker` calls `usdk::transfer_from(attacker_signer, proof, from, scheme, pubkey, attacker, 100)`. This succeeds, transferring 100 USDK; `from`'s account sequence number is untouched because `from` was not the transaction signer.
3. `attacker` calls `usdk::transfer_from` again with the identical `proof` bytes. `account::get_sequence_number(from)` is unchanged, so `expected_message` reconstructs identically and `account::verify_signed_message` succeeds again, transferring another 100 USDK.
4. Repeat step 3 until `from`'s balance (or supply available to `from`) is exhausted, or until `from` happens to submit an unrelated transaction that finally bumps their sequence number.
