### Title
Unbacked shielded-value minting via attacker-controlled `balanceOf` mirroring on duplicate/aliased token slots - (File: contracts/Hinkal.sol :: transact / _internalTransact)

### Summary
`Hinkal.transact` validates deposits/withdrawals for each `erc20TokenAddresses[i]` purely by comparing `balanceOf(address(this))` snapshots taken before and after `_internalTransact` runs. Because `erc20TokenAddresses` entries are never required to be unique or to belong to a whitelisted/registered real asset, and `getBalancesForArray`/`getERC20OrETHBalance` blindly call `balanceOf` on any attacker-supplied contract [1](#0-0) , an attacker can deploy a "double-entry" token `B` whose `balanceOf` mirrors another real token `A`'s live balance while its `transfer`/`transferFrom` move no real value. This lets the exact-equality check `balanceDif == amountChanges[i]` pass for slot `B` with zero real backing, minting shielded UTXO value with no corresponding asset in the vault.

### Finding Description
The equality claimed broken is: **real value entering/leaving Hinkal for slot `i` == `amountChanges[i]` credited/debited to the shielded merkle tree for slot `i`.**

For an internal transact (`externalActionId == 0`), `utxoSet` is left as its default empty array (never populated by `_internalTransact`) [2](#0-1) , so `utxoAmount` is always `0` for every `i` in the post-transfer loop. Since `onChainCreation[i]` must be `false` for internal transactions (enforced by `checkOnchainCreation`) [3](#0-2) , the strict equality in `Hinkal.transact` collapses to:

```
balanceDif[i] == amountChanges[i]
``` [4](#0-3) 

`balanceDif[i]` is computed purely from `getBalancesForArray(circomData.erc20TokenAddresses)` snapshots calling `balanceOf` on whatever addresses the attacker supplied [1](#0-0) . Neither `Hinkal.transact` nor `HinkalHelper.dimensionsCheck` enforces that `erc20TokenAddresses` entries are unique or reference independent, legitimate ERC20 contracts [5](#0-4) .

Exploit flow:
1. Attacker deploys real token `A` (or uses any existing ERC20) and a malicious contract `B` whose `balanceOf(account)` simply returns `IERC20(A).balanceOf(account)` (a live mirror, not a snapshot), and whose `transfer`/`transferFrom` are no-ops that return `true` without moving any value.
2. Attacker calls `Hinkal.transact` with `erc20TokenAddresses = [A, B]`, `amountChanges = [Y, Y]`, `onChainCreation = [false, false]`, a valid SNARK proof (self-generated, since the prover fully controls the private inputs/UTXO outputs it wants to create for both slots), `externalActionId = 0`.
3. `_internalTransact` iterates: for slot `A`, `deltaAmountChange = Y > 0`, so it calls `A.transferFrom(attacker, hinkal, Y)` — a genuine transfer, increasing `A`'s real balance by `Y` (and `B.balanceOf` mirrors this same increase live). For slot `B`, `deltaAmountChange = Y > 0` too, so it calls `B.transferFrom(attacker, hinkal, Y)` — attacker's own no-op code, no value moves.
4. Post-call snapshot: `newBalances[A] - oldBalances[A] = Y` (real) and `newBalances[B] - oldBalances[B] = Y` (mirrored from `A`'s real change, not from any real `B` transfer).
5. Both equality checks pass: `balanceDif[A] == amountChanges[A] (=Y)` and `balanceDif[B] == amountChanges[B] (=Y)` [6](#0-5) .
6. `insertCommitments` then commits the new shielded outputs constrained by the circuit's `inTotal + amountChanges === outTotal` per slot, crediting `Y` of shielded value for slot `A` and *another* `Y` of shielded value for slot `B` to the off-chain UTXO tree, even though only `Y` of real, single-asset value ever entered the vault (the vault holds only `Y` worth of token `A`; slot `B` has zero independent backing).

This yields the shielded tree believing it holds `2Y` of spendable value (`Y` tagged as token A, `Y` tagged as token B) backed by only `Y` real assets — direct minting of shielded value without backing.

Regarding the negative-`slippageValues[i]` framing in the question: the floor check `balanceDif >= slippageValues[i]` is not actually the binding constraint here — the strict equality (`balanceDif == amountChanges[i]`) is what gates correctness for the internal-transact path, and it holds exactly due to the mirrored `balanceOf`, independent of slippage sign. A negative `slippageValues[i]` would only additionally allow a *loss* variant (e.g., a partially-backed withdrawal or a slot where the real balance decreases more than `amountChanges[i]` implies) to also slip past the `>=` floor, but the primary insolvency mechanism is the aliased/mirrored `balanceOf`, not the slippage floor.

None of the existing guards (`performHinkalChecks`, `dimensionsCheck`, `checkOnchainCreation`, `verifyProof`, `rootHashExists`, `insertNullifiers`) validate that distinct `erc20TokenAddresses` entries correspond to economically independent assets; they only check array-length consistency and internal/on-chain-creation semantics [5](#0-4) . The zk circuit constrains only the relationship between `amountChanges`, nullified inputs, and created outputs per declared token slot — it has no on-chain knowledge of whether the `erc20TokenAddresses[i]` values are distinct real assets, since token addresses are contract-level (not circuit-constrained) fields of `CircomData`.

### Impact Explanation
The attacker mints shielded UTXO value in the merkle tree that is not backed by any real deposited asset for one of the declared token slots, directly matching "minting shielded value without backing (protocol insolvency)" — Critical impact. The phantom UTXO (tagged to the fabricated/mirrored token `B`) is a validly provable, spendable commitment that can later be nullified in a further `transact` call; depending on how the attacker structures subsequent redemption (e.g., reusing token `B`'s mirror against a *different, unrelated* real token holding of Hinkal at withdrawal time, or combining with swaps/other paths), this can escalate to directly draining real assets belonging to other users, since `B`'s `balanceOf` mirrors whatever real balance Hinkal currently holds under the aliased address at call time — not a value pinned to the attacker's own contribution. This is repeatable per transaction and costs the attacker only the gas and the deployment of the malicious token contract.

### Likelihood Explanation
No privileged role is required: the attacker only needs to be able to call `Hinkal.transact` as an ordinary depositor, deploy an arbitrary token contract, and generate a valid proof for their own chosen UTXO outputs and `amountChanges` — all explicitly within the attacker's allowed capabilities per the rules. No tree state precondition is needed beyond a valid Merkle root for the (attacker-controlled) input nullifiers/outputs. The only requirement is that `erc20TokenAddresses` be allowed to contain a token whose `balanceOf` the attacker fully controls, which is true for any address since there is no token whitelist or uniqueness check in `dimensionsCheck` or `performHinkalChecks`. This makes the attack straightforward and fully repeatable.

### Recommendation
Enforce that all entries in `circomData.erc20TokenAddresses` are pairwise distinct addresses (reject duplicates) as part of `dimensionsCheck`/`performHinkalChecks`, and additionally require that each token address be present on a governance-maintained allowlist of vetted ERC20 contracts before it can be used in `transact`. Relying solely on `balanceOf` deltas from arbitrary, attacker-deployed contracts as ground truth for real value transferred is fundamentally unsafe; the balance-diff accounting should only be trusted for tokens whose bytecode/behavior has been vetted (e.g., via a registry maintained by `DEFAULT_ADMIN_ROLE`/`HINKAL_HELPER_MANAGER`).

### Proof of Concept
Foundry test plan:
1. Deploy `MockERC20 A` (standard, mintable) and `MirrorToken B` where `B.balanceOf(addr) => A.balanceOf(addr)` and `B.transfer`/`B.transferFrom` are no-ops returning `true`.
2. Mint `Y` tokens of `A` to attacker, `attacker.approve(hinkal, Y)` on `A` (approval to `B` may be omitted since `B.transferFrom` never checks/uses allowance).
3. Craft `CircomData` with `erc20TokenAddresses = [A, B]`, `amountChanges = [Y, Y]`, `onChainCreation = [false, false]`, `slippageValues = [0, 0]` (or negative, per the question's variant), `externalActionData.externalActionId = 0`, `externalActionData.externalAddress = attacker`, with locally-generated valid nullifiers/commitments/proof for both slots.
4. Call `Hinkal.transact(...)`.
5. Assert:
   - `A.balanceOf(hinkal)` increased by exactly `Y` (real vault asset delta for slot A).
   - `B.balanceOf(hinkal)` also reports `+Y` (mirrored), yet `B` (attacker-controlled) never received or transferred any independent real value — assert no state change occurred in any independent ledger backing `B` beyond `A`'s.
   - Both `require` checks in `Hinkal.transact` (lines 111-114 and 137-146) pass, and the transaction succeeds without revert.
   - Vault's real total asset value (`Y`, all in `A`) is strictly less than the sum of shielded UTXO value now committed across both slots (`2Y`), proving `net tokens entering Hinkal (Y) < sum(amountChanges) (2Y)`.
