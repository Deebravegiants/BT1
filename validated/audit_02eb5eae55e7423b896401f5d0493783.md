### Title
Webhook shop identity spoofing via unauthenticated `shop-domain` header not covered by HMAC - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook by checking the HMAC only over the raw request body, but the `shop` value handed to the app's handler is read from an HTTP header that is never included in that HMAC computation.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, and `#hmac` and `#shop` are both parsed from separate, independently-controlled HTTP headers: [1](#0-0) 

`ShopifyAPI::Utils::HmacValidator.validate` verifies only that `HMAC(api_secret_key, raw_body) == received_hmac`; it has no knowledge of, and does not bind to, the `shop-domain` header at all: [2](#0-1) 

`Registry.process` accepts the request once this body-only HMAC check passes, then constructs the `WebhookMetadata` handed to the app's handler using `request.shop` taken straight from the unauthenticated header: [3](#0-2) 

The identity binding that should hold is: `shop-domain header == shop that the (raw_body, hmac) pair was actually signed for`. Because the HMAC is computed over `raw_body` alone and the app's shared `api_secret_key` is identical across every shop that has the app installed, any two values `(raw_body, hmac)` that are valid for one shop remain "valid" (per `HmacValidator.validate`) no matter what `shop-domain` header accompanies them. The gem's own documentation states that `Registry.process` "will verify the request did indeed come from Shopify" and exposes `data.shop` as trusted shop identity for the handler to act on, reinforcing that host apps are expected to trust `data.shop` once `process` succeeds.

### Impact Explanation
An attacker who is a legitimate (unprivileged) merchant with the target app installed on their own shop can trigger any webhook topic they can influence (e.g. `orders/create`, `products/update`) to obtain a valid `(raw_body, hmac)` pair signed with the app's single, shared `api_secret_key`. They can then send that identical body/HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header with a victim shop's domain. `HmacValidator.validate` still succeeds because it only checks `raw_body` against the secret, and `Registry.process` will invoke the handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain. Any host app that uses `data.shop` (as documented) to look up per-tenant state, attribute the payload, or drive tenant-scoped side effects will process attacker-supplied data under the wrong tenant identity — a cross-tenant confusion condition rooted entirely in this gem's webhook verification logic.

### Likelihood Explanation
Exploitation requires only that the attacker be an ordinary merchant able to install the app (a standard, unprivileged actor for a public/embedded Shopify app) and generate at least one webhook event for their own store — no access to `api_secret_key`, access tokens, or any other credential is needed. The header can be freely set by any HTTP client making the direct POST to the app's webhook route.

### Recommendation
Bind the shop identity into the verified signature space: include the `shop-domain` (and ideally `topic`/`webhook-id`) header value in `to_signable_string`/the HMAC computation, or otherwise cryptographically tie the verified body to the claimed shop domain before it is handed to `WebhookMetadata`/the handler in `Registry.process`.

### Proof of Concept
1. App merchant "attacker.myshopify.com" has the target app installed and receives a legitimate webhook for `orders/create`, capturing `raw_body` and `X-Shopify-Hmac-Sha256` from that request.
2. Attacker POSTs to the app's registered webhook route with the same `raw_body` and `X-Shopify-Hmac-Sha256` value, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb:189-190`) calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `HMAC(api_secret_key, raw_body)`.
4. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, causing the host app to process the attacker's order data as if it belonged to `victim-shop.myshopify.com`.
