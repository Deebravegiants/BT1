### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` binds the HMAC signature to the raw request body only, but `ShopifyAPI::Webhooks::Registry.process` trusts the unauthenticated `shop-domain` header to attribute the delivered payload to a tenant. This is the same class of bug as the reported issue: a field that is acted upon (`shop`) is not covered by the integrity check (`hmac`) that is meant to authenticate the whole request.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header, independent of the HMAC input: [2](#0-1) 

`HmacValidator.validate` verifies the HMAC exclusively against `verifiable_query.to_signable_string`, i.e. the body bytes, using `Context.api_secret_key`: [3](#0-2) 

`Registry.process` checks only that HMAC validation passes, then immediately hands the handler the header-derived `shop` alongside the HMAC-verified body, with no cross-check that the body was ever produced for that shop: [4](#0-3) 

Equality that should hold but does not: `shop` used to route/attribute the webhook == `shop` the HMAC-signed payload was actually generated for. Since the signature only binds `body`, an attacker who owns any store that has the app installed (an ordinary, unprivileged merchant/internet user — no `api_secret_key` needed) can capture one of their own legitimately-signed webhook deliveries (correct body + correct HMAC, because Shopify itself signs it with the shared secret for their own shop) and replay that exact `body`/`hmac` pair to the app's webhook endpoint while substituting the `shop-domain` header of a different, victim shop. `HmacValidator.validate` still succeeds (it never looks at the shop header), and `Registry.process` calls the handler with `shop: <victim-shop>` and `body: <attacker's own data>` — i.e., the attacker gets to inject content attributed to a tenant they do not own.

### Impact Explanation
This breaks the tenant boundary the webhook signature is supposed to guarantee: `Registry.process` (and therefore any host application built on `ShopifyAPI::Webhooks::WebhookHandler#handle`) will process attacker-controlled webhook bodies as if they legitimately originated from a victim shop. Depending on how the host app's handler uses `WebhookMetadata#shop` to decide which merchant record to mutate (e.g., orders, app-uninstall, GDPR/compliance topics), this enables cross-tenant data injection/corruption — a Critical-class cross-tenant access impact per the finding classification.

### Likelihood Explanation
The prerequisite is only a store where the app is installed (freely obtainable by any developer/merchant via a Shopify Partner dev store) that receives at least one real webhook delivery. No possession of `api_secret_key`, access tokens, or any privileged credential is required, and no TLS interception is needed — the attacker simply re-POSTs a previously-observed valid `(body, hmac)` pair with a different `shop-domain` header value to the app's public webhook endpoint. This is directly reachable through the gem's own `Registry.process`/`HmacValidator.validate` code path exactly as documented for host apps to use.

### Recommendation
Bind the shop identity into the value that is HMAC-verified, or otherwise cryptographically tie the header to the payload before it is trusted:
- Include the `shop-domain` header in `Request#to_signable_string` (or otherwise combine it with the body before computing/comparing the HMAC), matching how Shopify signs the payload, so that a mismatch between the signed shop and the header shop causes validation to fail; or
- Have `Registry.process` cross-check `request.shop` against an independently-authenticated source (e.g., a known/allow-listed set of installed shop domains for the app) before invoking the handler, rather than trusting the raw header once the body-only HMAC passes.

### Proof of Concept
1. Attacker installs the app on their own store `attacker.myshopify.com` and triggers any webhook (e.g., `orders/create`), capturing the real headers/body that Shopify sends, including a valid `x-shopify-hmac-sha256` computed over the raw body with the app's shared secret.
2. Attacker replays that exact `raw_body` and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers (all required headers are present), `Utils::HmacValidator.validate` succeeds because it only checks the body against the shared secret (`lib/shopify_api/utils/hmac_validator.rb:12-31`, `lib/shopify_api/webhooks/request.rb:35-38`), and `Registry.process` invokes the app's handler with `shop: "victim-shop.myshopify.com"` and the attacker's own body content (`lib/shopify_api/webhooks/registry.rb:188-199`).

        def validate(verifiable_query)

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
