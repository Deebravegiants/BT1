### Title
Webhook `shop` (and `topic`/`api_version`/`webhook_id`) headers are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so `Utils::HmacValidator.validate` authenticates the *body bytes* but never the `shop-domain`, `topic`, `api-version`, or `webhook-id` headers that `Registry.process` subsequently trusts and forwards to application handlers.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
which is the only material the HMAC covers, per `HmacValidator.validate_signature`: [2](#0-1) 

`Registry.process` gates on this HMAC check and then, without any further verification, builds tenant-identifying metadata straight from the unauthenticated headers: [3](#0-2) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors are all pulled directly from HTTP headers with no cryptographic binding to the signed body: [4](#0-3) 

The identity-binding equality this breaks: `HMAC(secret, signed_bytes)` should equal `HMAC(secret, bytes_that_determine_tenant_attribution)`, but here `signed_bytes == raw_body` while `tenant_attribution == shop-domain header`, which are disjoint. Any party that can obtain one valid `(raw_body, hmac)` pair for the shared app secret — e.g., an unprivileged attacker who installs the app on their own shop and receives its own legitimate webhook delivery — can replay that exact `(raw_body, hmac)` pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` (and `topic`/`webhook-id`) header. `HmacValidator.validate` will still succeed because it never inspects those headers, and `Registry.process` will invoke the topic handler with `WebhookMetadata.shop` set to the attacker-chosen victim shop domain.

### Impact Explanation
This is a cross-tenant identity-binding failure: it lets an app-installing shop forge webhook events that appear to originate from a different (victim) shop, because the `api_secret_key` used for HMAC is shared across all shops using the same app, and the shop attribution is unauthenticated. Depending on how the host application's webhook handlers use `WebhookMetadata.shop` (e.g., to look up/mutate per-shop records, deauthorize shops, or drive `customers/redact`/`shop/redact` compliance workflows), this can enable cross-tenant data corruption or spoofed compliance actions attributed to a shop the attacker does not control.

### Likelihood Explanation
Requires only that the attacker be able to install the target app on a shop they control (a normal, unprivileged action for any Shopify merchant) and capture one of their own webhook deliveries — no access token, `client_secret`, or privileged account is required. This is a realistic, low-effort attack path.

### Recommendation
Bind the `shop` (and ideally `topic`) header into the signed material, or otherwise cryptographically verify that the `shop-domain` header matches an actual registration/session known to the app, before constructing `WebhookMetadata`. At minimum, document/require that `Registry.process` callers cross-check `request.shop` against a session store keyed by the authenticated relationship, rather than trusting the header outright.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and registers for a webhook topic (e.g. `orders/create`).
2. Shopify delivers a webhook to the attacker's endpoint with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC of raw body>`, and some `raw_body`.
3. Attacker replays the identical `raw_body` and `x-shopify-hmac-sha256` to the same app's webhook endpoint but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers (no signature involvement), `Utils::HmacValidator.validate` returns `true` (it only checks the body against the shared secret), and `Registry.process` invokes the handler with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", ...)`, as shown in [5](#0-4) .
