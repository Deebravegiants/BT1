Based on my analysis, this bug class **does have a valid analog** in the Raydium AMM program, distinct from (and not fully mitigated by) the `Initialize2` minimum-liquidity lock.

### Title
Missing minimum-LP-output slippage protection in `process_deposit` enables share-price-inflation (donation) attack against subsequent depositors - (File: `program/src/processor.rs`)

### Summary
`process_deposit` computes the amount of LP tokens minted to a depositor as a ratio of the depositor's input against the pool's *live token-vault balances*, using `amm.lp_amount` as the tracked total-supply denominator. Because SPL token vault balances can be inflated by anyone via a plain token transfer (no `deposit()` call required), and because `DepositInstruction` provides no way for the caller to specify a minimum acceptable LP output, a depositor can be forced to receive a disproportionately small number of LP tokens for their contribution while the excess value accrues to the existing LP holder(s) — the classic ERC4626 / Uniswap-V2 "first depositor" share-inflation attack.

### Finding Description
In `process_deposit`, the pool's coin/pc totals are read directly from the vault token accounts' live balances: [1](#0-0) 

These totals (after `calc_take_pnl` adjustment) are then used to compute how many LP tokens to mint, using `amm.lp_amount` (the internally tracked total LP supply) as denominator: [2](#0-1) [3](#0-2) 

`DepositInstruction` only exposes `max_coin_amount`, `max_pc_amount`, `base_side`, and `other_amount_min` — none of which bound the number of LP tokens minted: [4](#0-3) 

The only guard on the minted amount is that it must be nonzero: [5](#0-4) 

This means a majority LP holder (trivially achievable, since anyone can call `Initialize2` to create a pool and become its dominant/sole LP holder) can, immediately before a victim's deposit transaction lands, transfer additional coin/pc tokens directly into `amm_coin_vault`/`amm_pc_vault` (a plain SPL `Transfer`, requiring no interaction with the Raydium program at all). This inflates `total_coin_without_take_pnl`/`total_pc_without_take_pnl` without changing `amm.lp_amount`, so the victim's `mint_lp_amount = coin_input / total_coin_total * amm.lp_amount` shrinks proportionally — the victim deposits real tokens but receives LP tokens representing only a fraction of their contributed value. The donated + victim's tokens now sit in the vaults, and the attacker's pre-existing LP share (still large relative to the diluted-share math) can later be redeemed via `Withdraw` to reclaim the donated funds plus the value stolen from the victim.

The `InitLpAmountTooLess` check in `process_initialize2` only defends against the degenerate "1 wei first deposit" case at pool-creation time by requiring `sqrt(init_pc_amount * init_coin_amount) > 10^decimals`: [6](#0-5) 
It does not prevent a moderately-capitalized pool creator from later donating disproportionately large amounts to the vaults to manipulate the ratio against any *subsequent* depositor, since the attacker's minted LP share (`liquidity - 10^decimals`) still represents nearly 100% of `amm.lp_amount` for any non-trivial pool size, and no minimum-output check exists on the `Deposit` path.

### Impact Explanation
A depositor's assets can be diluted/stolen by a pool's dominant LP holder through pure token donation (no permissioned call needed), transferring value from an unsuspecting depositor to the attacker. This is a concrete, permanent loss of user funds for the victim, and constitutes unbacked/disproportionate LP minting relative to contributed value — matching the High severity of the referenced report's bug class.

### Likelihood Explanation
Exploitability requires only: (1) being the pool creator/dominant LP (attainable by anyone via `Initialize2`), (2) monitoring the mempool/blockspace for an incoming `Deposit` transaction from a target pool, and (3) front-running it with a plain SPL token transfer to the vault accounts. No privileged signer, leaked key, or validator collusion is required — this is reachable from a single unprivileged transaction with attacker-chosen accounts and data, satisfying the "swapper/LP/pool-creator" reachability constraint.

### Recommendation
Add a `minimum_lp_amount` (or equivalent slippage bound) parameter to `DepositInstruction`/`process_deposit` so depositors can bound the minimum LP tokens they are willing to accept, analogous to `min_coin_amount`/`min_pc_amount` already present on `Withdraw`. Additionally, consider tracking pool reserves internally (updated only through `Deposit`/`Withdraw`/`Swap` instructions) rather than trusting live vault balances, to make direct-transfer donations unable to affect share-minting math.

### Proof of Concept
1. Attacker calls `Initialize2` with `init_coin_amount = init_pc_amount = X` (X large enough to satisfy `InitLpAmountTooLess`), becoming the pool's dominant LP holder, receiving `liquidity - 10^decimals` LP tokens where `liquidity = sqrt(X*X) = X`.
2. Victim submits a `Deposit` transaction with `max_coin_amount = Y`, `base_side = 0`.
3. Before the victim's transaction lands, attacker submits plain SPL `Transfer` instructions sending a large amount `Z >> X` of coin and pc tokens directly to `amm_coin_vault`/`amm_pc_vault` (referenced at `program/src/processor.rs:1138-1140`), inflating `total_coin_without_take_pnl`/`total_pc_without_take_pnl`.
4. Victim's deposit executes: `mint_lp_amount = Y / (X + Z) * amm.lp_amount` (per `program/src/math.rs:456-477`) is now much smaller than fair value proportional to `Y`; the only enforced check is `mint_lp_amount != 0` (`program/src/processor.rs:1323-1325`), so the transaction succeeds despite the victim receiving a disproportionately small LP allocation.
5. Attacker calls `Withdraw` with their LP tokens, redeeming their now-inflated share of the pool — recovering their donated `Z` plus a portion of the victim's stolen deposit.
