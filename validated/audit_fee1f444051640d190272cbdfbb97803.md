### Title
Webhook `shop` and `topic` identity fields are not bound by the HMAC signature, allowing cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC that `Utils::HmacValidator` verifies covers exclusively `@raw_body`. The `shop`, `topic`, `webhook_id` and `api_version` values — all of which are read straight from unauthenticated HTTP headers and then acted upon by `Registry.process` — are never part of the signed content. This mirrors the reported bug class: a value the code treats as trustworthy/proportional to a validated quantity (here, "this request's `shop`/`topic` headers are as authentic as its HMAC-verified body") is never actually covered by that validation.

### Finding Description
`Registry.process` validates a webhook using only the body-derived HMAC: [1](#0-0) 

and then dispatches based on `request.topic` and hands `request.shop` straight to the handler as the tenant identifier: [2](#0-1) 

`Request#to_signable_string` only returns `@raw_body`: [3](#0-2) 

while `shop`, `topic`, `webhook_id`, and `api_version` are pulled unauthenticated from headers: [4](#0-3) 

Contrast this with the OAuth `AuthQuery`, where `to_signable_string` explicitly folds `shop` (and every other identity-relevant field) into the signed payload before HMAC verification: [5](#0-4) 

So the equality the code implicitly assumes is:
`HMAC-verified(raw_body)` == `HMAC-verified(shop, topic, webhook_id, api_version, raw_body)`

but only the left side is actually true. Because `Context.api_secret_key` (the `client_secret`) is a single value shared by the app across every shop on which it is installed, any party capable of producing one valid `(raw_body, hmac)` pair for the app — e.g., an attacker who installs the same public app on their own store and captures its genuine webhook deliveries — can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header (any other merchant's shop) and/or `shopify-topic` header. `Utils::HmacValidator.validate` will accept it because it never looks at those headers, and `Registry.process` will invoke the handler with `WebhookMetadata` carrying the attacker-chosen `shop`/`topic`, causing the host application to act as though the event belongs to a different tenant.

### Impact Explanation
This breaks the tenant boundary the gem's own HMAC check is supposed to establish: the `shop` value that downstream `WebhookHandler` implementations use to key per-merchant state (session revocation, GDPR data-request/redact processing on `MANDATORY_TOPICS`, uninstall handling, etc.) is attacker-controlled and unauthenticated, even though the request passed HMAC validation. This is a cross-tenant integrity issue — an attacker can trigger tenant-scoped side effects (e.g. forcing an "uninstalled"/"redact" style event) for a shop they do not control, using only a body+HMAC pair legitimately obtained from their own, unrelated installation of the same app.

### Likelihood Explanation
Likelihood is high: no secret, token, or privileged access is required beyond installing the target app on any store the attacker controls (or otherwise obtaining any one genuine webhook delivery for that app, since bodies for many topics contain no attacker-specific secrets). The attacker only needs to replay the exact bytes and swap headers, which `Utils::HmacValidator.validate` and `Webhooks::Registry.process` do not detect.

### Recommendation
Include the identity-relevant headers (`shop`, `topic`, `webhook_id`, `api_version`) in the signable payload used for HMAC verification, or otherwise cryptographically bind them to the body before computing/checking the signature, mirroring what `Auth::Oauth::AuthQuery#to_signable_string` already does for `shop` in the OAuth flow. At minimum, `Registry.process` should refuse to act on a `shop` value that was not itself covered by the verified signature.

### Proof of Concept
1. Attacker installs the target public app on `attacker-shop.myshopify.com`; Shopify delivers a genuine webhook to the app's callback URL with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: app/uninstalled`, `x-shopify-hmac-sha256: <valid HMAC over raw body>`.
2. Attacker captures `raw_body` and the valid `hmac` value (both are visible to them since it's their own shop/webhook).
3. Attacker POSTs the identical `raw_body` and `hmac` to the same endpoint, but replaces the header with `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb`) recomputes the HMAC over `raw_body` only, which still matches, so validation passes.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-199`) invokes the registered `app/uninstalled` handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", ...)`, causing the host application to process an uninstall/redact/etc. event for a shop the attacker never installed the app on.
