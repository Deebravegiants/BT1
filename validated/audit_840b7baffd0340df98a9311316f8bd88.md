### Title
Unauthenticated TCP livestream listener on port 9201 lets any network client redirect raw biometric camera frames (IrEyeFrame/IrFaceFrame/RgbFrame) to an attacker-controlled IP - (File: src/agents/livestream/upstream.rs)

### Summary
`Upstream::new` binds an unauthenticated `TcpListener` on `0.0.0.0:9201`, and `Upstream::poll_next` emits `Event::Connected(addr)` for any accepted connection with no credential, token, or session check. The livestream agent's `run` loop (src/agents/livestream/mod.rs) reacts to this event by unconditionally constructing `Downstream::new(addr.ip())`, which opens a UDP video sink that streams subsequently-received `Input::IrEyeFrame`, `Input::IrFaceFrame`, and `Input::RgbFrame` camera data to that IP on port 9200.

### Finding Description
`Upstream::poll_next` (src/agents/livestream/upstream.rs:45-74) calls `self.listener.poll_accept(cx)` and, on any successful TCP accept, immediately returns `Event::Connected(addr)` — there is no authentication handshake, token exchange, or peer allow-list check performed before this event fires. [1](#0-0) 

The livestream `Agent::run` loop (src/agents/livestream/mod.rs:185-188) handles `Event::Connected(addr)` by directly instantiating `Downstream::new(addr.ip())`, replacing whatever downstream target was previously set (including a legitimate/no target), with zero binding to a signup or session identity: [2](#0-1) 

`Downstream::new` (src/agents/livestream/downstream.rs:18-46) sets a GStreamer `udpsink` `host` property to `addr.to_string()` and `port` to 9200, then starts pushing frames as soon as `gpu.render` produces buffer callbacks that invoke `downstream.push(&buffer)`: [3](#0-2) 

Once `downstream` is `Some`, every subsequent `Input::IrEyeFrame`, `Input::IrFaceFrame`, `Input::RgbFrame` (and other camera frame types) received by the agent loop is rendered and pushed to that downstream target unconditionally (src/agents/livestream/mod.rs:118-131, 197-200): [4](#0-3) 

There is no code path in `Upstream`, `Downstream`, or the agent `run` loop that checks whether a signup is in progress, verifies the connecting peer against a backend-issued token, or restricts the accepted `SocketAddr` to a pre-authorized destination. Any TCP client capable of reaching port 9201 on the orb's network interface becomes the new video-stream destination for raw IR eye/face and RGB frames, overriding any prior legitimate connection.

### Impact Explanation
This is a raw biometric image disclosure vulnerability: an unauthenticated network peer can cause the orb to redirect its live IR eye, IR face, and RGB camera streams (used during signup for iris/face capture) to an address of the attacker's choosing over UDP. This matches the Worldcoin/Orb bounty category of "biometric data disclosure" / "unauthorized access to raw biometric imagery," since the invariant that raw camera frames must only be routed to a backend-authorized, signup-bound destination is violated purely by connecting a TCP socket to port 9201 — no signup participation, credentials, or operator interaction is required by the attacker.

### Likelihood Explanation
Feasibility depends entirely on network reachability of TCP port 9201 (and being able to receive UDP on port 9200) on the orb, which is deployment/network-dependent and gated behind the `livestream` cargo feature and the `--livestream` CLI flag (src/cli.rs:14-17) — i.e., the feature must be compiled in and explicitly enabled at orb startup by an operator for the listener to exist at all. I was not able to fully confirm from available code whether `--livestream` is enabled by default in production Orb deployments or is a debug/manual-testing-only mode (this requires inspecting deployment/ops configuration, which is outside the indexed code). If enabled, exploitation only requires a bare TCP connect from any host that can route to the orb — trivially repeatable and requires no special access, matching the "unprivileged network client" threat model.

### Recommendation
Require the livestream `Upstream` listener to authenticate incoming connections (e.g., via a pre-shared token/mTLS/backend-issued signup session credential) before emitting `Event::Connected`, and bind the `Downstream` target only to an address that has been explicitly authorized by the backend for the active signup session, rejecting/closing unauthenticated connections instead of redirecting frame delivery to them.

### Proof of Concept
Integration test plan:
1. Start the livestream `Agent` (or a harness wrapping `Upstream`) bound to `127.0.0.1:9201`.
2. Simulate an in-progress signup by feeding `Input::Phase`, `Input::IrEyeFrame`, etc. into the agent's port.
3. From a second, unauthenticated TCP client (no token/session context), connect to `127.0.0.1:9201`.
4. Assert that `Upstream::poll_next` yields `Event::Connected(addr)` for this connection (demonstrating no auth gate), and that the agent loop calls `Downstream::new(addr.ip())`.
5. Feed further `Input::IrEyeFrame`/`Input::RgbFrame` inputs and assert (via a mock/spy `Downstream::push`) that frame data is now being routed to the attacker's `addr` rather than any backend-authorized destination — expected assertion: frame push occurs with no credential check, proving unauthorized biometric data disclosure.
