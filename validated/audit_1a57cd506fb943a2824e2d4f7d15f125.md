### Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` authenticates an inbound webhook solely by HMAC-signing the raw request body, while the `shop` (tenant) identity that the handler later trusts is read from an unsigned HTTP header. Anyone able to obtain one valid `(body, hmac)` pair for the shared app secret — e.g. a merchant who has installed the same app on their own store and receives a legitimate webhook — can resend that exact payload to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to a victim shop, and `Utils::HmacValidator.validate` will still accept it.

### Finding Description
`Request#to_signable_string` returns only the raw body: [1](#0-0) 

but `shop` (and `topic`, `webhook_id`, `api_version`) are pulled straight from HTTP headers that are never part of the signed string: [2](#0-1) 

`HmacValidator.validate` computes and compares the HMAC only against `verifiable_query.to_signable_string`, i.e. the body: [3](#0-2) 

`Registry.process` checks that HMAC first, then immediately trusts `request.shop` (the unsigned header) as the tenant identity passed to the app's webhook handler: [4](#0-3) 

The identity binding that should hold is: `bytes verified by HMAC == bytes the shop identity is derived from`. Here `bytes_verified = raw_body` but `shop_identity = headers["shop-domain"]`, which are disjoint. Because the app's `api_secret_key` (used by `HmacValidator`) is the same secret Shopify uses to sign every webhook for every shop that has the app installed, any party who has installed the app on their own store (or otherwise legitimately received one authentic webhook, e.g. via `app/uninstalled` on their own shop) can capture a valid `(raw_body, hmac)` pair and replay it with a different `shop-domain` header pointing at another merchant's shop. The signature still validates, and `WebhookMetadata` is constructed with the attacker-chosen `shop`, so the host application processes data under a victim tenant's identity.

### Impact Explanation
This breaks the tenant boundary that webhook processing is meant to preserve: an unprivileged party (any merchant who has installed the app, or anyone who intercepts a webhook body) can make the app believe an authentic-looking webhook belongs to a different, arbitrary shop. Depending on how the host application keys its business logic off `WebhookMetadata#shop` (e.g. deletion/deauthorization flows, data updates, billing events), this enables cross-tenant data manipulation — meeting the "cross-tenant access" High/Critical impact bar.

### Likelihood Explanation
Likelihood is realistic but not trivial: the attacker needs at least one genuine `(body, hmac)` pair signed with the app's shared secret. The simplest path is a merchant who installs the app on their own store, triggers a webhook with predictable/attacker-controlled content (e.g. `app/uninstalled`, or any topic whose payload the attacker fully controls through their own store data), captures the resulting body+HMAC, then replays it against the same endpoint with a forged `shop-domain` header naming a different installed shop.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the value that is HMAC-verified, or otherwise cryptographically tie the header-derived shop to the specific installation (e.g., verify the shop against a per-shop-installation record before dispatch, and reject if it does not match the source of the raw body). At minimum, `to_signable_string` should not be the only channel of trust for the tenant identity used downstream; the handler dispatch should independently confirm that `request.shop` corresponds to a shop this app instance actually expects to receive webhooks for that specific webhook_id/registration.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com`.
2. Attacker triggers (or waits for) a webhook whose body is fully known/attacker-influenced, e.g. `app/uninstalled` with body `{}`, and Shopify sends:
   - Headers: `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC of "{}">`
   - Body: `{}`
3. Attacker resends the same request to the app's webhook endpoint, replacing the header with `x-shopify-shop-domain: victim.myshopify.com` (leaving body and HMAC untouched).
4. `Registry.process` calls `Utils::HmacValidator.validate(request)` — this passes because it only checks the raw body against the HMAC: [5](#0-4) 
5. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"`, even though Shopify never sent this webhook for that shop.
