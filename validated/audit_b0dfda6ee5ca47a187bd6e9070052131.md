### Title
Per-call floor rounding in `accrue`'s `reserve-inc` calculation lets anyone permanently zero out the DAO treasury's protocol fee via frequent tiny-delta calls - ([File: mainnet/contracts/vault/v0-vault-sbtc.clar])

### Summary
`accrue` computes the protocol's fee (`reserve-inc`) as `mul-div-down` of the *per-call* debt increase, not of the cumulative real interest. Because `accrue` is a fully public function with no cooldown or minimum-interval guard, an unprivileged caller can invoke it every block, keeping each call's `debt-delta` below the rounding threshold `ceil(BPS / fee-reserve)`. This makes `reserve-inc` truncate to `0` on every single call forever, even though `index` (and hence real borrower debt via `mul-div-up`) keeps climbing, permanently denying `.dao-treasury` its `treasury-lp` mint.

### Finding Description
The intended invariant is:
`sum_over_calls(reserve-inc_i) == mul-div-down(sum_over_calls(true-delta_i), fee-reserve, BPS)`

i.e. the total fee minted to the DAO treasury should equal the fee rate applied to the total interest that accrued to borrowers over time.

In `accrue`: [1](#0-0) [1](#0-0) 

```
(old-debt (mul-div-down scaled-principal idx INDEX-PRECISION))
(new-debt (mul-div-down scaled-principal next INDEX-PRECISION))
(debt-delta (if (> new-debt old-debt) (- new-debt old-debt) u0))
(reserve-inc (mul-div-down debt-delta (var-get fee-reserve) BPS))
```

`old-debt` for call *i+1* is always exactly `new-debt` of call *i* (both read fresh from `var-get index`/`next-index`), so `debt-delta` telescopes correctly across calls - but `reserve-inc = mul-div-down(debt-delta, fee-reserve, BPS)` is floored **per call**, not on the aggregated delta. Flooring `N` small increments independently loses strictly more precision than flooring their sum once. Concretely, for any `fee-reserve < BPS`, whenever a call's `debt-delta` stays below `ceil(BPS / fee-reserve)` (e.g. below 5 raw units for a 20% fee), `reserve-inc` computes to `0` for that call, guaranteed, via [2](#0-1) .

`accrue` has no access control (`check-caller-auth` is never invoked) and no minimum time-since-last-update guard: [3](#0-2) 

`last-update` is reset to `stacks-block-time` whenever `index` or `lindex` actually changes: [4](#0-3) 

This means every time an attacker triggers even a 1-raw-unit `index` bump, the accrual clock resets, so the next call again starts from a near-zero `time-delta`, via `next-index`'s `calc-multiplier-delta`: [5](#0-4) 

Exploit flow: an unprivileged attacker (any Stacks account, zero collateral/deposit required) submits `(contract-call? .v0-vault-sbtc accrue)` once per new Stacks block indefinitely. As long as the resulting `Δidx` per call keeps `debt-delta` under the rounding threshold, `reserve-inc` is `0` on every call, `treasury-lp` is never minted to `.dao-treasury`, while `index`/`total-debt` (visible via `mul-div-up` in `total-debt`/`calc-cumulative-debt`) continue to genuinely grow and get repaid by borrowers into `assets`, entirely benefiting existing `zft` holders (share price appreciation) with zero cut for the DAO.

No existing guard prevents this: there is no rate limit, minimum interval, or batching of the fee calculation over a coarser window; `check-caller-auth` is not applied to `accrue`.

### Impact Explanation
Each qualifying call permanently loses `mul-div-down(debt-delta, fee-reserve, BPS)` (up to `floor((ceil(BPS/fee-reserve)-1) * fee-reserve / BPS)` raw underlying units, i.e. up to just-under-1-unit of loss per call) that can never be recovered, because the fee is computed as an ephemeral local variable and discarded once `reserve-inc` rounds to `0` - there is no residual/carry-forward accounting. Repeated indefinitely across the vault's entire lifetime, this can drive the DAO treasury's realized protocol fee for that vault to `0` regardless of the real total interest paid by borrowers, which is a permanent freezing (in practice, total loss) of the DAO's unclaimed yield share - matching the "High: permanent freezing of unclaimed yield" category. Loss is borne solely by `.dao-treasury`; existing lenders/`zft` holders are unaffected or even benefit (all interest flows through to `assets`/share price instead of being split off as `treasury-lp`).

### Likelihood Explanation
- Preconditions: none beyond an existing borrow position generating some interest (attacker does not need to be the borrower).
- Capital cost: only Stacks transaction fees for calling `accrue()` every block; `accrue` requires no deposit, no collateral, no special trait/receiver.
- Feasibility: fully deterministic given rate/principal magnitudes; the attacker only needs to observe `get-next-index`/`get-interest-rate` (both read-only) to confirm `debt-delta` stays under the rounding threshold and adjust call frequency accordingly.
- Repeatability: unbounded - can be sustained for the life of the vault by any single unprivileged account.

### Recommendation
Do not floor the fee on a per-call incremental basis. Either (a) track fee accrual using the same running-index approach as `total-debt` (compute `reserve-inc` from `mul-div-up`/`mul-div-down` applied to the *cumulative* fee-adjusted index rather than per-call deltas), or (b) accumulate a persistent remainder/dust variable across calls so unflushed fractional fee amounts are carried forward and eventually minted once they cross a whole-unit threshold, or (c) add a minimum-interval guard on `accrue` so `debt-delta` per call is always large enough that rounding loss is negligible relative to `fee-reserve`.

### Proof of Concept
Clarinet/vitest simnet plan:
1. Deploy `v0-vault-sbtc`, `initialize`, set `fee-reserve` to e.g. `2000` (20%) and configure `points-ir` so `interest-rate()` returns a nonzero rate at some utilization.
2. Have an authorized test market call `system-borrow` to create a nonzero `principal-scaled`/`total-borrowed` and non-zero utilization.
3. Mine blocks one at a time (small, realistic `stacks-block-time` deltas), calling `(contract-call? .v0-vault-sbtc accrue)` after every block for N iterations (e.g. N=200).
4. After each call, record `get-index` and the `zft` balance of `.dao-treasury`.
5. Assert: `zft` balance of `.dao-treasury` is unchanged (`0` `treasury-lp` minted) across all N calls, while cumulative `get-index` increase (`index_final - index_initial`) is strictly positive and, via `get-debt`, shows borrower debt has genuinely grown.
6. As a control, reset state and instead call `accrue` once after the same total elapsed time (single large `time-delta`): assert `treasury-lp` minted to `.dao-treasury` is now nonzero and equals `mul-div-down(total-debt-delta, fee-reserve, BPS)`, proving the aggregate invariant holds only when accrual is not chunked into attacker-controlled tiny steps.
