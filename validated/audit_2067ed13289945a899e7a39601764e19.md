### Title
Unauthenticated cross-chain calldata execution allows account impersonation - (File: modules/pallets/hyper-fungible-token/src/module.rs)

### Summary
`pallet-hyper-fungible-token`'s `on_accept` handler executes an attacker-suppliable `SubstrateCalldata.runtime_call` as a `Signed` origin derived from the ISMP message's `from` field whenever `SubstrateCalldata.signature` is `None`. That `from` value is not the actual key-holder's identity verified by a signature — it is copied verbatim from `abi.encodePacked(msg.sender)` set by the EVM-side `send()` caller [1](#0-0) , or the equivalent field in `HyperFungibleToken.sol`'s `Message` struct [3](#0-2) . Any caller of `send()` on the source chain fully controls `msg.sender` for that call (e.g. by calling from a fresh throwaway EOA or contract), so they effectively choose the `from` value embedded in the bridged message.

### Finding Description
The vulnerable path is `<T as Config> impl IsmpModule for Pallet<T>::on_accept`:

```rust
let origin = if let Some(signature) = substrate_data.signature {
    // ... signature verification against beneficiary's account nonce ...
    beneficiary.clone()
} else {
    let from_bytes = message.from.as_ref();
    if source.is_evm() {
        T::EvmToSubstrate::convert(H160::from_slice(&from_bytes[from_bytes.len() - 20..]))
    } else {
        let mut account = [0u8; 32];
        account.copy_from_slice(from_bytes);
        account.into()
    }
};
...
runtime_call.dispatch(RawOrigin::Signed(origin.clone()).into())
``` [4](#0-3) 

When `signature` is present, the pallet cryptographically verifies (via ed25519/sr25519/ecdsa) that whoever controls the `beneficiary` account's key authorized `(nonce, runtime_call)` — this is a proper authentication path. However, when `signature` is `None`, the code silently falls back to deriving the dispatch origin purely from `message.from`, with zero cryptographic proof that the account referenced by that address consented to the call. The only gate applied is `BaseCallFilter`, which restricts *which* calls are runtime-wide filtered, not *who* may issue them [5](#0-4) .

Because `message.from` is attacker-chosen on the source chain (it is simply `abi.encodePacked(msg.sender)` of whoever calls `send()`), any unprivileged relayer/user can bridge a token transfer whose message body sets `from` to an arbitrary EVM address (or, for substrate sources, an arbitrary 32-byte value) and simultaneously embeds `SubstrateCalldata { signature: None, runtime_call: <attacker-chosen call> }`. Since `EvmToSubstrate::convert` deterministically maps EVM address bytes to a substrate `AccountId` (zero-padding by default per `impl<T> EvmToSubstrate<T> for ()`) [6](#0-5) , this lets the attacker cause the pallet to dispatch a `Signed` call as *any* account that has ever bridged into that chain via this pallet, without ever controlling that account's private key. This is functionally identical in class to the CVE-2024-12909 bug hint: attacker-controlled input reaches a privileged execution sink (there, arbitrary SQL/RCE via `run_sql_query`; here, arbitrary `RuntimeCall::dispatch` as a forged `Signed` origin) with no proof of authorization tying the input to the acting principal.

### Impact Explanation
This allows unauthorized dispatch of arbitrary allowed runtime calls under the identity of any account (impersonation) — e.g. `Balances::transfer_all` draining that account's balance to an attacker-controlled destination, `Assets::approve_transfer`/`transfer` if not filtered, or any other dispatchable not excluded by the runtime's `BaseCallFilter`. This maps to "unauthorized app action" per the validation rubric, and depending on the deployed `BaseCallFilter` configuration can lead directly to theft of funds from arbitrary previously-bridged accounts, satisfying the Critical/High impact bar (concrete theft of funds via forged authorization).

### Likelihood Explanation
Exploitation requires only a single unprivileged `send()` call on the EVM-side `HyperFungibleToken`/`WrappedHyperFungibleToken` contract with a crafted `data` payload — no special privileges, no proof-forgery, and no race condition are needed. Any account whose derived substrate `AccountId` this pallet has, e.g. because it previously bridged funds in the normal course of use, is a valid impersonation target once its EVM/from address is known (addresses are public on-chain data).

### Recommendation
Never derive a `Signed` dispatch origin from unauthenticated message fields. Require `SubstrateCalldata.signature` to always be present and verified before dispatching `runtime_call` under `RawOrigin::Signed`, or restrict the no-signature path to a lower-privilege origin (e.g. dispatch as the pallet's own account, or require an explicit opt-in registration mapping source `from` bytes to destination accounts that only the account owner can set). At minimum, reject `on_accept` messages containing calldata when `signature.is_none()` rather than silently deriving a spendable origin from attacker-supplied bytes.

### Proof of Concept
1. Attacker deploys/uses any EOA `E` on the EVM source chain that they do not need to control long-term.
2. Attacker calls `HyperFungibleToken.send()` (or `WrappedHyperFungibleToken.send()`) from `E`, with `params.data` = ABI-encoded `Call[]`/SCALE `SubstrateCalldata { signature: None, runtime_call: <SCALE-encoded pallet_balances::transfer_all(dest: attacker_dest, keep_alive: false)> }`, targeting the destination substrate chain where `pallet-hyper-fungible-token` is configured.
3. The EVM contract sets `message.from = abi.encodePacked(msg.sender)` = `E`'s address [1](#0-0) , and dispatches the ISMP POST request.
4. On delivery, `on_accept` decodes the message, sees `substrate_data.signature == None`, and derives `origin = EvmToSubstrate::convert(H160(E))` [7](#0-6) .
5. If the substrate `AccountId` derived from `E` happens to hold a balance (e.g. `E`'s corresponding account previously received bridged tokens, which any observer can arrange for a target by having them bridge normally, or by simply choosing `E` to match a known victim's mapped account), the pallet dispatches `runtime_call.dispatch(RawOrigin::Signed(origin))` [8](#0-7) , executing `transfer_all` and draining the victim account's balance to the attacker, with no signature ever having been produced by the victim.
