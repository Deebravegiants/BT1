### Title
Webhook `shop-domain`, `topic`, `webhook-id` and `api-version` headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its verifiable signable content from the raw request body only, while the shop, topic and other identifying fields come from HTTP headers that are never included in the HMAC computation. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then trusts `request.shop`/`request.topic` taken from those unauthenticated headers when dispatching to the registered handler. This is exactly the "field acted on but not covered by the HMAC" class of bug described in the external report (there, the `Transfer` event was emitted with semantics inconsistent with the balances actually moved; here, the webhook metadata trusted by the handler is inconsistent with what the signature actually covers).

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `Request#shop`, `#topic`, `#api_version`, and `#webhook_id` are all read directly from HTTP headers, independent of the signed body: [2](#0-1) 

`Registry.process` validates the HMAC via `Utils::HmacValidator.validate(request)`, which only proves the `raw_body` was signed with the app's secret — it proves nothing about the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers accompanying that body: [3](#0-2) 

The HMAC secret (`Context.api_secret_key`) is the same for every shop that installs the app (or every request under a custom app's single secret), so once an attacker's own shop or the attacker's own tap on a legitimate webhook produces one validly-signed `(raw_body, hmac)` pair, that exact pair remains valid no matter what `shop-domain`/`topic`/`webhook-id` headers are attached on replay to the app's webhook endpoint. The binding that should hold is:
`hmac-verified(raw_body) == (shop, topic, webhook_id) trusted by handler`
but the implementation only enforces `hmac-verified(raw_body)`, while `(shop, topic, webhook_id)` are supplied by attacker-controlled, unauthenticated headers.

Compare this to `Auth::Oauth::AuthQuery`, where `shop`, `host`, `state`, `code`, and `timestamp` are all explicitly included in `to_signable_string` and therefore cryptographically bound to the HMAC: [4](#0-3) 

The webhook `Request` class breaks this same pattern by excluding the identifying header fields from the signable content.

### Impact Explanation
Because `shop` is not bound to the HMAC, an attacker who owns (or briefly controls) any shop that has the app installed can capture one genuinely Shopify-signed webhook body/HMAC pair from their own store, then replay that exact `(raw_body, hmac)` to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header (and/or `X-Shopify-Topic`) for a different, victim tenant. `Registry.process` will validate the HMAC successfully and hand `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` to the app's handler labeled with the attacker-chosen shop/topic instead of the shop that actually produced the payload. For handlers that key state, GDPR redaction, billing, or authorization decisions off the `shop` field of `WebhookMetadata` (which is the gem's documented way to identify the originating tenant), this produces cross-tenant data confusion or spoofed mandatory-compliance webhooks (e.g. spoofing a `customers/data_request` or `shop/redact` event for a shop the attacker does not control). This matches the "cross-tenant access" criterion for a Critical-impact finding in the given scope.

### Likelihood Explanation
Exploitation requires the attacker to obtain at least one legitimately-signed webhook body from any store using the app (trivial for an attacker who installs the app on their own development/test store, or intercepts a webhook delivered to their own shop) and the ability to send an HTTP request to the target app's public webhook endpoint with custom headers, which is standard unprivileged-internet-user capability. No `api_secret_key`, access token, or other credential is needed by the attacker. The likelihood is high for any app whose webhook handler logic differentiates behavior/data by the `shop` or `topic` metadata field.

### Recommendation
Include the identifying header fields (`shop`, `topic`, `webhook_id`, `api_version`) in the HMAC-signable content in `Request#to_signable_string`, or otherwise cryptographically bind them (e.g., by validating against Shopify's known valid shop list, or by only trusting `shop`/`topic` when they are echoed back by Shopify in a signed envelope). At minimum, document clearly that `WebhookMetadata#shop` and `#topic` are unauthenticated header values and must never be used by consuming applications for tenant/authorization decisions without independent verification (e.g., confirming the shop is a known installed shop before acting).

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` (or otherwise triggers/observes any webhook delivery to that shop).
2. Shopify delivers a webhook with a valid `X-Shopify-Hmac-Sha256` computed over the raw JSON body using the app's shared `client_secret`, along with headers `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Topic: customers/data_request`.
3. Attacker captures the raw body and the valid HMAC value.
4. Attacker sends a forged HTTP POST to the app's registered webhook endpoint using the exact same raw body and HMAC header, but replaces `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com` (and/or a different `X-Shopify-Topic`).
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `raw_body` against the HMAC — see [5](#0-4)  and [1](#0-0) .
6. The handler is invoked with `WebhookMetadata` reporting `shop: "victim-shop.myshopify.com"`, `topic: "customers/data_request"`, even though the payload never actually originated from that shop — see [6](#0-5) .
