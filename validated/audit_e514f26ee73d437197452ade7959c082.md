### Title
Webhook shop attribution is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`Webhooks::Request#shop` is read directly from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, but `Webhooks::Request#to_signable_string` (the string covered by the HMAC check) only includes the raw request body. Because the tenant-identifying `shop` value is not bound into the signature, an attacker who possesses one valid `(raw_body, hmac)` pair for their own shop can replay it to the app's webhook endpoint with a forged `shop-domain` header claiming to be a different merchant, and `Registry.process` will accept it as authentic and hand the forged shop identity to the app's webhook handler.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`: [1](#0-0) [2](#0-1) 

`hmac` is read from the `hmac-sha256` header, and `shop` from the `shop-domain` header, but `to_signable_string` returns only `@raw_body`. `Utils::HmacValidator.validate` computes `HMAC(api_secret_key, verifiable_query.to_signable_string)` and compares it with `verifiable_query.hmac`: [3](#0-2) 

Since only the body is part of the signable string, the HMAC proves the body was produced/known by someone holding `api_secret_key` (normally Shopify), but it proves nothing about which shop the request is attributed to. `Registry.process` nevertheless treats a passing HMAC check as authorization to dispatch the request's `shop` value straight to the handler: [4](#0-3) 

The binding that should hold is: `shop == the tenant whose data actually produced/authorizes raw_body`. Instead, the code only verifies `hmac == HMAC(secret, raw_body)`, independent of `shop`. Any party that has legitimately received one authentic webhook for their own shop (i.e., a valid `(raw_body, hmac)` pair — trivially obtainable since a merchant installing the app receives real webhooks for their own store) can resend that exact body/HMAC to the app's public webhook endpoint while substituting an arbitrary `shopify-shop-domain` header. The signature still validates, because it never covered that header, and `WebhookMetadata.shop` will contain the attacker-chosen value.

### Impact Explanation
`Registry.process` passes the (spoofable) `shop` value into `WebhookMetadata` which is handed to the app-registered `WebhookHandler`. Apps commonly key merchant/tenant-scoped storage, redaction, or business logic (e.g., `shop/redact`, `customers/data_request`, order/customer sync) off this `shop` value. Because it is unauthenticated, an attacker holding one valid webhook payload/signature for their own tenant can cause the handler to execute logic attributed to a different, arbitrary shop — a cross-tenant confusion that can corrupt or leak another merchant's data depending on what the host app does with `data.shop`. This matches the "Critical - cross-tenant access" impact category, since the shop identity binding that the HMAC is supposed to protect is broken.

### Likelihood Explanation
Likelihood is realistic for any actor who has legitimate access to their own store's webhook traffic (any merchant that installs the app, or anyone able to observe one webhook delivery, e.g., via their own test shop). No knowledge of `api_secret_key` is required — only replay of a body/signature pair that was legitimately produced for a different, attacker-controlled `shop`, with the `shop-domain` header changed. The gem provides no mechanism to bind headers into the signature, so every consumer of this library inherits the exposure.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) as part of the HMAC-covered signable string, or otherwise verify that the `shop-domain` header value is consistent with an independently authenticated source (e.g., match against session/shop state already known to the app) before trusting it in `WebhookMetadata`. At minimum, document that `data.shop` from `Webhooks::Request` is not cryptographically bound to the payload and must not be trusted as a tenant boundary without additional verification.

### Proof of Concept
1. App receives a legitimate Shopify webhook for `shop-a.myshopify.com`: raw body `B`, header `x-shopify-hmac-sha256: H` where `H = HMAC-SHA256(secret, B)`, and `x-shopify-shop-domain: shop-a.myshopify.com`.
2. Attacker (who owns/controls `shop-a`, or otherwise captured this delivery) resends an HTTP POST to the app's webhook endpoint with the same body `B` and same `H`, but sets `x-shopify-shop-domain: shop-b.myshopify.com`.
3. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` recomputes `HMAC(secret, B)`, which still equals `H`, so validation passes.
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-199`) proceeds and calls the registered handler with `WebhookMetadata.new(topic:, shop: "shop-b.myshopify.com", body: parsed(B), ...)`, causing the app to process/attribute the webhook payload to `shop-b` even though it never originated from or was authorized for `shop-b`.
