Based on the code, this is a real, confirmed vulnerability.

### Title
`describeWithdrawal` for PoA bridge batches matches by `assetId` only, causing two same-token withdrawals with different destinations to report identical status/txHash - (File: `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`)

### Summary
`PoaBridge.describeWithdrawal` (lines 313-343) calls `findMatchingWithdrawal` (lines 418-427), which selects a PoA API withdrawal record purely by matching `nep141:${w.data.near_token_id} === assetId`, never using `args.index`, `args.withdrawalParams.amount`, or `args.withdrawalParams.destinationAddress`. Nothing upstream (`supports`, `validateWithdrawal`, `createWithdrawalIdentifier`, `processWithdrawal`, `waitForWithdrawalCompletion`) rejects or disambiguates a batch containing two withdrawals of the same `assetId` to different `destinationAddress`es, so both indices resolve to the same record.

### Finding Description
The equality that should hold is: for withdrawal index *i*, the `(status, txHash)` returned by `describeWithdrawal({index: i, withdrawalParams: withdrawalParams[i], tx})` must equal the on-chain outcome of the withdrawal actually sent to `withdrawalParams[i].destinationAddress`. `findMatchingWithdrawal` breaks this because it matches only on `nep141:${w.data.near_token_id} === assetId`: [1](#0-0) 

The comment in the code itself acknowledges the limitation ("multiple withdrawals of the same token in a single transaction are not supported"), but nothing enforces this assumption at any call site — there is no check in `supports()` [2](#0-1) , `validateWithdrawal()` [3](#0-2) , or in `PoaBridge.describeWithdrawal` itself [4](#0-3)  that rejects a batch with duplicate `assetId`.

`sdk.processWithdrawal` / `signAndSendWithdrawalIntent` explicitly support batch mode with an array of `withdrawalParams`, each independently specifying `destinationAddress` and `amount` [5](#0-4) , and README documents "Batch Withdrawals" as a supported feature [6](#0-5) . An unprivileged caller (an ordinary SDK user with their own funds) can call `processWithdrawal({withdrawalParams: [ {assetId: X, destinationAddress: A, amount: a}, {assetId: X, destinationAddress: B, amount: b} ]})`. Both withdrawals produce PoA bridge intents for the same NEP-141 token; the PoA indexer returns withdrawal records keyed by `near_token_id`, and if two records for the same token exist in the response, `findMatchingWithdrawal` returns `withdrawals.find(...)`, i.e. the *first* array element matching the assetId, regardless of which index (0 or 1) is asking. Since the array order is stated as unsorted ("Response list is unsorted, so we match by assetId instead of index" — line 318), index 0's `describeWithdrawal` call and index 1's `describeWithdrawal` call can both resolve to the same record — reporting withdrawal 1's `txHash` for withdrawal 0, or vice versa.

No later step disambiguates: `waitForWithdrawalCompletion` and `createWithdrawalCompletionPromises` in `sdk.ts` simply call `watchWithdrawal`/`describeWithdrawal` per index without any additional filtering by `destinationAddress` or `amount` [7](#0-6) .

### Impact Explanation
An integrator that credits/refunds a user based on per-index `(status, txHash)` from a batch `processWithdrawal`/`waitForWithdrawalCompletion` call can attribute the wrong destination's completed transaction to the wrong withdrawal index, or report both indices as "completed" using the same `txHash` when only one has actually landed. This can cause the integrator to credit the wrong destination address as completed, or double-credit based on a single real transfer, matching the "status or hash misreport making an integrator credit or refund twice" High-impact category. It is repeatable on every batch call containing two withdrawals with matching `assetId` that resolve to a matching-token record in the PoA API response array.

### Likelihood Explanation
Preconditions: caller submits a batch withdrawal (`processWithdrawal` or `signAndSendWithdrawalIntent` in array mode) containing two or more entries with the same `assetId` but different `destinationAddress`/`amount`, routed to the PoA bridge. There is no validation anywhere in `PoaBridge` or `sdk.ts` preventing this — batch withdrawals of the same token are explicitly documented as supported at the SDK level, while only the low-level PoA matching code has an internal, unenforced comment noting the limitation. This is trivially reachable by any ordinary SDK caller, at zero additional cost, and is deterministic given a batch with duplicate `assetId` PoA withdrawals.

### Recommendation
Either (a) explicitly reject/validate at `processWithdrawal`/`signAndSendWithdrawalIntent` time when a batch contains two or more PoA-bridge withdrawals sharing the same `assetId`, throwing a clear "unsupported: duplicate assetId in batch" error, until the PoA API supports disambiguation; or (b) implement the sorting-based matching the code comment already proposes (sort withdrawal params and API results by amount per `assetId`, since relayer fees are equal for same-token withdrawals) inside `findMatchingWithdrawal`, and add an assertion that the destinationAddress on the matched record's underlying tx corresponds to the expected destination before returning the result.

function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

	public createWithdrawalCompletionPromises(
		params: CreateWithdrawalCompletionPromisesParams,
	): Array<Promise<TxInfo | TxNoInfo>> {
		const { withdrawalParams, intentTx, signal, logger } = params;

		const widsPromise = createWithdrawalIdentifiers({
			bridges: this.bridges,
			withdrawalParams,
			intentTx,
		});

		// Track the last promise per HOT bridge landing chain for sequential waiting.
		// HOT bridge processes withdrawals sequentially per chain with ~30s gaps,
		// so polling in parallel would cause later withdrawals to timeout.
		const hotChainLastPromise = new Map<Chain, Promise<TxInfo | TxNoInfo>>();

		return withdrawalParams.map(async (_, index) => {
			const wids = await widsPromise;
			const entry = wids[index];
			assert(entry != null, `Missing wid for index ${index}`);

			// Only apply sequential waiting for HOT bridge
			if (entry.bridge.route === RouteEnum.HotBridge) {
				const landingChain = entry.wid.landingChain;
				const previousPromise = hotChainLastPromise.get(landingChain);

				const sequentialPromise = (async () => {
					if (previousPromise) {
						// Wait for previous withdrawal to same chain to complete.
						// Use allSettled to continue even if previous fails.
						await Promise.allSettled([previousPromise]);
					}
					return watchWithdrawal({
						bridge: entry.bridge,
						wid: entry.wid,
						signal,
						logger,
					});
				})();

				hotChainLastPromise.set(landingChain, sequentialPromise);
				return sequentialPromise;
			}

			// Non-HOT bridges: parallel polling (existing behavior)
			return watchWithdrawal({
				bridge: entry.bridge,
				wid: entry.wid,
				signal,
				logger,
			});
		});

	public async signAndSendWithdrawalIntent(
		args:
			| SignAndSendWithdrawalArgs<WithdrawalParams>

		let withdrawalParamsArray: WithdrawalParams[];
		let feeEstimations: FeeEstimation[];
		if (isBatchMode(args)) {
			withdrawalParamsArray = args.withdrawalParams;
			feeEstimations = args.feeEstimation;
		} else {
			withdrawalParamsArray = [args.withdrawalParams];
			feeEstimations = [args.feeEstimation];
		}

		const intentsP = zip(withdrawalParamsArray, feeEstimations).map(
			([withdrawalParams, feeEstimation]) => {
				return this.createWithdrawalIntents({
					withdrawalParams,
					feeEstimation,
					referral: args.referral ?? this.referral,
					logger: args.logger,
				});
			},
		);

		const intents = (await Promise.all(intentsP)).flat();

			const relayParams =
