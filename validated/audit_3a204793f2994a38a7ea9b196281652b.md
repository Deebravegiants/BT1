## Custody Analog Found

### Title
Missing `chain_id` in `SignerCapabilityOfferProofChallengeV2` enables cross-chain replay of signer-capability delegation - (File: `aptos-move/framework/aptos-framework/sources/account/account.move`)

### Summary
The external report's root cause is a signed authorization struct that omits `chain_id`, letting a signature intended for one chain be replayed on another. The same class of bug exists in Aptos's `account::offer_signer_capability` entry function: its proof-of-authorization struct, `SignerCapabilityOfferProofChallengeV2`, does not include `chain_id`, unlike its sibling `RotationCapabilityOfferProofChallengeV2`, which was explicitly hardened with a `chain_id` field for exactly this reason.

### Finding Description
`account.move` defines two "V2" delegation-proof structs used to authorize capability delegation via an explicit off-chain-style message signature (separate from the outer transaction signature): [1](#0-0) 

`RotationCapabilityOfferProofChallengeV2` includes `chain_id`, and the doc comment explicitly states this was added "to prevent replaying the challenge message": [2](#0-1) 

`SignerCapabilityOfferProofChallengeV2`, despite being the "V2" (i.e., the hardened successor to the deprecated `SignerCapabilityOfferProofChallenge`), was never given the same `chain_id` field: [3](#0-2) 

This struct is built and verified in `offer_signer_capability`, using only a dynamically-fetched `sequence_number` and addresses — no chain identifier: [4](#0-3) 

`multisig_account.move`, which was written after this pattern was recognized as a risk, follows the correct convention and explicitly documents why `chain_id` is required ("Chain id is included to prevent cross-chain replay"): [5](#0-4) 

This shows the codebase is fully aware of the cross-chain replay risk for offline-signed capability-delegation messages, and mitigated it in two of three analogous structs (`RotationCapabilityOfferProofChallengeV2`, `MultisigAccountCreationMessage`) but not in `SignerCapabilityOfferProofChallengeV2`.

### Impact Explanation
The signer capability obtained via `offer_signer_capability`/`SignerCapabilityOfferProofChallengeV2` allows the `recipient_address` to call `create_authorized_signer` and mint a full `signer` for the source account, i.e., complete custody control over any APT, fungible assets, objects, or resource-account-derived value held at that address. If the same account address, with a matching `sequence_number`, exists on two Aptos-framework-compatible chains/networks (e.g., mainnet vs. a testnet/previewnet or an independent Aptos-framework fork sharing genesis/derivation), a signer-capability delegation message signed for use on one chain remains a valid, verifiable proof on the other chain, letting the same delegation be replayed there without the account owner's consent for that chain. This is a genuine unprivileged-authority-break primitive matching the "Custody Pivots" criteria (multisig/resource-account authority leaking to an unintended holder), potentially resulting in unauthorized signer-capability takeover and asset theft.

### Likelihood Explanation
Medium. Exploitation requires: (1) the same account address to exist across two chains sharing the Aptos Move framework's `account` module logic, and (2) the account's `sequence_number` to coincide at delegation time (most reliably true for freshly created accounts with `sequence_number == 0`, which is a common state for many users/dApps deploying to multiple networks with the same keys). This is a narrower precondition than a fully general cross-chain replay, but it is a real, non-hypothetical scenario for wallets/dApps that reuse the same key material across Aptos mainnet and other Aptos-compatible networks — precisely the scenario the framework's own `RotationCapabilityOfferProofChallengeV2` fix was designed to prevent.

### Recommendation
Add a `chain_id: u8` field to `SignerCapabilityOfferProofChallengeV2`, mirroring `RotationCapabilityOfferProofChallengeV2`, and populate it via `chain_id::get()` in `offer_signer_capability`:
```move
struct SignerCapabilityOfferProofChallengeV2 has copy, drop {
    chain_id: u8,
    sequence_number: u64,
    source_address: address,
    recipient_address: address,
}
```
and in `offer_signer_capability`:
```move
let proof_challenge = SignerCapabilityOfferProofChallengeV2 {
    chain_id: chain_id::get(),
    sequence_number: get_sequence_number(source_address),
    source_address,
    recipient_address,
};
```
This is a breaking change to the struct's BCS layout and signing convention, so it would need to be introduced as a new version (e.g., `SignerCapabilityOfferProofChallengeV3`) with a corresponding new entry function, deprecating the current one, following the same migration pattern used for `RotationCapabilityOfferProofChallenge` → `V2`.

### Proof of Concept
1. User creates account `A` with the same private key/derivation on both Chain-1 (e.g., mainnet) and Chain-2 (e.g., a compatible Aptos-framework fork or test network), both with `sequence_number == 0` for `A`.
2. User (or a compromised dApp acting on the user's behalf) signs a `SignerCapabilityOfferProofChallengeV2 { sequence_number: 0, source_address: A, recipient_address: R }` intending to delegate signer capability to `R` on Chain-1 only, and submits it via `offer_signer_capability` on Chain-1.
3. Attacker captures `signer_capability_sig_bytes` from the Chain-1 transaction.
4. If `R` also exists on Chain-2, and `A`'s `sequence_number` on Chain-2 is still `0`, the attacker (or `R`) submits the identical `signer_capability_sig_bytes`/`account_public_key_bytes` to `offer_signer_capability` on Chain-2, signed as a fresh Chain-2 transaction by `A`'s key reused there (or via any account that can still invoke the entry function as `A`, e.g., in bridged/shared-key deployments). Verification succeeds because the struct's `verify_signed_message` check has no chain-specific input.
5. `R` now holds `A`'s signer capability on Chain-2 as well, despite the user never intending delegation there, and can call `create_authorized_signer(R, A)` to fully control `A`'s assets on Chain-2.

**Caveat:** I could not find any additional runtime binding (e.g., a global chain-specific `account_address`/genesis hash prefix folded into `verify_signed_message` itself) that would independently block this replay; the mitigation appears to rely solely on the presence/absence of `chain_id` inside each specific proof-challenge struct, which is inconsistent between `SignerCapabilityOfferProofChallengeV2` and its sibling structs.

```text
    /// Offers signer capability on behalf of `account` to the account at address `recipient_address`.
    /// An account can delegate its signer capability to only one other address at one time.
    /// `signer_capability_key_bytes` is the `SignerCapabilityOfferProofChallengeV2` signed by the account owner's key
    /// `account_scheme` is the scheme of the account (ed25519 or multi_ed25519).
    /// `account_public_key_bytes` is the public key of the account owner.
    /// `recipient_address` is the address of the recipient of the signer capability - note that if there's an existing
    /// `recipient_address` in the account owner's `SignerCapabilityOffer`, this will replace the
    /// previous `recipient_address` upon successful verification (the previous recipient will no longer have access
    /// to the account owner's signer capability).
    public entry fun offer_signer_capability(
        account: &signer,
        signer_capability_sig_bytes: vector<u8>,
        account_scheme: u8,
        account_public_key_bytes: vector<u8>,
        recipient_address: address
    ) acquires Account {
        let source_address = signer::address_of(account);
        ensure_resource_exists(source_address);
        assert!(exists_at(recipient_address), error::not_found(EACCOUNT_DOES_NOT_EXIST));

        // Proof that this account intends to delegate its signer capability to another account.
        let proof_challenge = SignerCapabilityOfferProofChallengeV2 {
            sequence_number: get_sequence_number(source_address),
            source_address,
            recipient_address,
        };
        verify_signed_message(
            source_address, account_scheme, account_public_key_bytes, signer_capability_sig_bytes, proof_challenge);

        // Update the existing signer capability offer or put in a new signer capability offer for the recipient.
        let account_resource = &mut Account[source_address];
        account_resource.signer_capability_offer.for.swap_or_fill(recipient_address);
    }
```
