### Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant webhook replay — (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `#shop` is read from an independent, unauthenticated header. `Utils::HmacValidator.validate` verifies the HMAC exclusively against `to_signable_string`, so the `shop-domain` header is never bound to the signature. A holder of any single legitimately-signed webhook payload can replay it verbatim while swapping the `x-shopify-shop-domain` header to a different tenant, and the gem will report the webhook as valid and hand the attacker-chosen shop to the application's handler.

### Finding Description
`Request#to_signable_string` only returns `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic tie to the body or the HMAC: [2](#0-1) 

`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (the body) and compares it with `verifiable_query.hmac`: [3](#0-2) 

`Registry.process` gates only on this HMAC check, then immediately trusts `request.shop` and forwards it to the application handler as the tenant identifier: [4](#0-3) 

The binding that should hold is:
`shop asserted to the handler (request.shop) == shop cryptographically bound by the HMAC (the signed bytes)`

Because `to_signable_string` excludes the shop header, this equality never holds — the HMAC only proves "this body was signed with the app secret at some point for some shop," not "this body belongs to this shop." An unprivileged party who can obtain one legitimate webhook delivery for any shop that installed the app (e.g., their own development/test store, which requires no special privilege beyond installing the app) can capture the `(raw_body, hmac)` pair and resend it to the app's webhook endpoint with an arbitrary `x-shopify-shop-domain` value. `HmacValidator.validate` will still succeed because it never inspects the header, and `Registry.process` will call the handler with `WebhookMetadata#shop` set to the attacker-chosen tenant while the `body` still contains the original shop's data.

### Impact Explanation
This breaks the tenant-authentication boundary that `Registry.process`/`WebhookMetadata` is designed to provide: application code that uses `WebhookMetadata#shop` as the authoritative tenant key (a documented, expected usage pattern of this gem, since the gem is the one asserting `shop` alongside a validated HMAC) can be tricked into attributing genuine webhook payloads (e.g., `app/uninstalled`, `customers/redact`, order/customer data) to the wrong merchant. Depending on how the host app keys its data store off this field, this enables cross-tenant data confusion/leakage, which maps to the Critical "cross-tenant access" category in the impact list, since the boundary crossed is the shop/tenant identity that the gem itself is supposed to authenticate via HMAC.

### Likelihood Explanation
Exploitation requires the attacker to have received at least one legitimate webhook for some shop that installed the target app (trivial via their own free/dev store, no leaked credentials or `api_secret_key` needed) and the ability to POST to the app's public webhook endpoint with custom headers (also trivial, since Shopify webhook endpoints are public HTTP endpoints by design). The `hmac-sha256` header and body are reused verbatim, so no cryptographic secret ever needs to be known or brute-forced.

### Recommendation
Bind the shop identity into the signed material verified by this gem, e.g., have `HmacValidator` (or a dedicated webhook validator) verify the `shop-domain` header against an application-supplied allow-list of installed shops before trusting it, or clearly document in `WebhookMetadata` that `shop` is unauthenticated and must be independently verified by the host app against its own session store before use as a tenant key.

### Proof of Concept
1. App developer installs their own test app on `attacker-shop.myshopify.com` and receives a legitimate webhook, capturing `raw_body` and the `x-shopify-hmac-sha256` header value.
2. Attacker POSTs the identical `raw_body` and `x-shopify-hmac-sha256` to the victim app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` parses this into a `Request` whose `hmac` still matches (`Digest.hexencode(Base64.decode64(...))` of the reused header) and whose `shop` is `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `to_signable_string` (the reused body) — see `lib/shopify_api/utils/hmac_validator.rb:12-31` and `lib/shopify_api/webhooks/request.rb:35-43`.
5. The handler is invoked with `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body: <attacker's original shop's data>, ...)` — see `lib/shopify_api/webhooks/registry.rb:198-199` — causing the host app to process attacker-shop data as if it belonged to `victim-shop`.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
