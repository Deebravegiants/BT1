### Title
Webhook Shop-Domain Header Is Not Covered by HMAC Verification, Enabling Cross-Tenant Webhook Spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` claims to "verify the request did indeed come from Shopify" before invoking the app's handler, but the HMAC signature it checks only covers the raw request body. The `shop` (and `topic`/`webhook_id`) fields that identify *which tenant* the webhook belongs to are read straight from unauthenticated HTTP headers and are never included in the signed content.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate_signature` computes the HMAC exclusively over that signable string and compares it against the `hmac-sha256` header: [2](#0-1) 

Meanwhile `Registry.process` reads `request.shop`, `request.topic`, and `request.webhook_id` directly from headers and forwards them, unauthenticated, into the app's handler as the tenant identity for the event: [3](#0-2) [4](#0-3) 

The identity binding that should hold is: `hmac == HMAC(secret, body ‖ shop ‖ topic)`. What is actually enforced is: `hmac == HMAC(secret, body)`, with `shop` and `topic` accepted from unauthenticated header bytes. This is exactly the "field acted on but not covered by the HMAC" pattern: the bytes that are cryptographically verified (`raw_body`) are not the same bytes that are trusted and acted upon (`shop`).

The gem's own documentation reinforces the false sense of security: "This will verify the request did indeed come from Shopify": [5](#0-4) 

### Impact Explanation
Because the `shop` header is never bound to the signature, any request carrying a *validly signed body* (which the attacker can obtain by receiving one genuine webhook delivered to their own store, where the body content is entirely attacker-controlled, e.g. an order/product they create) can be replayed to the app's webhook endpoint with the `x-shopify-shop-domain` (or `shopify-shop-domain`) header changed to an arbitrary victim shop domain. The signature still validates (it only checked the body), and `Registry.process` will invoke the registered handler with `WebhookMetadata#shop` set to the attacker-chosen victim shop. If the host application uses this `shop` value to look up/update per-tenant records (a documented and expected usage pattern per the `docs/usage/webhooks.md` example, `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), this results in cross-tenant data confusion/injection — attacker-controlled webhook payload written under a victim shop's identity.

### Likelihood Explanation
Likelihood is high for any app that: (a) registers HTTP webhooks via this gem, and (b) trusts `data.shop` from the callback without independently cross-checking it against the concrete registered `webhook_id`/subscription for that topic. No possession of `api_secret_key`, access tokens, or any privileged account is required — only the ability to receive one legitimately signed webhook for any shop (including a free/trial shop the attacker controls) and replay it with a substituted shop header to the app's public webhook endpoint.

### Recommendation
Bind the tenant identity into the verified signature computation, or otherwise cryptographically/authoritatively verify the `shop` and `webhook_id` against Shopify (e.g., re-query the webhook subscription owner via the Admin API, or require the host app to validate `shop` against an existing installed-session record before trusting the payload) rather than accepting the header value at face value once the body-only HMAC passes. At minimum, update `HmacValidator`/`Request#to_signable_string` to include `shop`, `topic`, and `webhook_id` in the signed content so header tampering invalidates the signature.

### Proof of Concept
1. Attacker installs the target app on a shop they control (e.g., a free development store `attacker-shop.myshopify.com`) and triggers a webhook event (e.g., creates an order) that the app is subscribed to.
2. Attacker's server captures the genuine webhook POST: raw body `B` and header `x-shopify-hmac-sha256: H` (a valid HMAC over `B` using the app's real secret, computed by Shopify).
3. Attacker sends a new POST request directly to the app's public webhook endpoint with the same body `B` and same `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate` passes because it only checks `B` against `H`.
5. `ShopifyAPI::Webhooks::Registry.process` invokes the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: B, ...)`, causing the attacker's crafted body to be processed under the victim shop's identity.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
