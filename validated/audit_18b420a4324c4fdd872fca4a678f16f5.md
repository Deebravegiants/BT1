## Finding

### Title
Storage-deposit cache key collision in `DirectBridge.getCachedStorageDepositValue` returns wrong account's balance, causing incorrect storage-deposit fee calculation - (File: `packages/intents-sdk/src/bridges/direct-bridge/direct-bridge.ts`)

### Summary
`DirectBridge.getCachedStorageDepositValue` builds its cache key by naively concatenating `contractId` and `accountId` with no delimiter: `` `${contractId}${accountId}` ``. Because NEAR account IDs are composed of the same alphabet used for both parts of the key (letters, digits, `.`, `-`, `_`), two different `(contractId, accountId)` pairs can produce an identical concatenated string. When that happens, `estimateWithdrawalFee` for one token/destination pair silently reuses the cached `[minStorageBalance, userStorageBalance]` tuple that was actually computed for a different token/destination pair.

The key is built by string concatenation with no separator between `contractId` and `accountId`. Since both are valid NEAR account IDs (lowercase letters, digits, `.`, `-`, `_`, 2–64 chars), the split point between the two components is not recoverable from the resulting string. Two withdrawal requests for different tokens/destinations can produce the same key, e.g.:

- Request A: `contractId = "aaa.near"`, `accountId = "bbb.near"` → key = `"aaa.nearbbb.near"`
- Request B: `contractId = "aaa.nearbb"`, `accountId = "b.near"` → key = `"aaa.nearbbb.near"` (identical)

This is the exact bug class described in the fast-jwt advisory: a cache key builder that is not guaranteed to be unique per logical entity, letting the cache return data belonging to a *different* entity (there: a JWT payload; here: a different token's/account's storage-balance tuple).

The result is consumed directly in `estimateWithdrawalFee`: [2](#0-1) 

```
const [minStorageBalance, userStorageBalance] =
    await this.getCachedStorageDepositValue(
        tokenAccountId,
        args.withdrawalParams.destinationAddress,
    );

if (minStorageBalance <= userStorageBalance) {
    return {
        amount: 0n,
        ...
        underlyingFees: {
            [RouteEnum.NearWithdrawal]: { storageDepositFee: 0n },
        },
    };
}
```

If request A is served first and its result is cached (destination has sufficient storage), and request B later collides onto the same key, the SDK will conclude request B's destination account also has sufficient storage even though it was never checked — skipping the required storage-deposit fee entirely. The zero storage-deposit fee then flows into `createWithdrawalIntents`, which uses it to build the on-chain `ft_withdraw`/transfer intent's `storageDeposit` field: [3](#0-2) 

```

    amount: args.withdrawalParams.amount,
    storageDeposit: getUnderlyingFee(
        args.feeEstimation,
        RouteEnum.NearWithdrawal,

    ),
    ...
});
```

### Impact Explanation
When the actual destination account does not have the required NEP-141 storage balance registered and the omitted storage-deposit fee (0n from the cache-collision result) is used, the on-chain transfer to that account can fail for lack of storage registration. This results in a withdrawal that does not land as expected and requires manual intervention/investigation to resolve — matching the High-severity category "a withdrawal stuck until manual intervention" from the assessment rules. Conversely, the collision can also cause an unrelated legitimate account's cached balance to trigger an unnecessary/incorrect storage-deposit fee being charged to another user, which is an overcharge on a fee that should not have applied.

The SDK's `storageDepositCache` has a 1-hour TTL and is shared across all withdrawal requests handled by one `DirectBridge` instance, so any integrator/service processing withdrawals for multiple tokens/destinations over that window is exposed — no malicious actor is required to trigger the collision, only ordinary usage with unlucky account-id/contract-id string boundaries.

### Likelihood Explanation
Exploitability does not require privileged access; it only requires that the caller construct a `contractId`/`destinationAddress` pair whose concatenation matches an already-cached key. Because NEP-141 contract IDs and NEAR account IDs share the same character set, and applications can choose their withdrawal destination address freely, an attacker (or even a bystander via unlucky overlap in a multi-tenant integrator) could deliberately craft a destination address to force a collision with a known/prior cache entry (e.g., a token/account combo known to have sufficient storage), suppressing the storage-deposit fee for their own withdrawal to an account that actually lacks storage.

### Recommendation
Use an unambiguous, delimiter-safe cache key, e.g. include a fixed-width hash or an explicit separator that cannot appear as part of either component (NEAR account IDs cannot contain characters like `\0` or `|` in a way that creates ambiguity), such as `` `${contractId}::${accountId}` `` with validation that the delimiter cannot occur inside either sub-string, or better, use a two-level `Map`/composite key (`Map<contractId, Map<accountId, value>>`) or a JSON-stringified array `JSON.stringify([contractId, accountId])`.

### Proof of Concept
1. `DirectBridge` instance handles a withdrawal for `contractId = "aaa.near"`, `accountId = "bbb.near"`. `getCachedStorageDepositValue` computes and caches `storageDepositCache.set("aaa.nearbbb.near", [min, balance])` where `balance >= min` (sufficient storage).
2. A subsequent (or concurrent, within the 1-hour TTL) withdrawal request targets `contractId = "aaa.nearbb"`, `accountId = "b.near"`. The computed key is again `"aaa.nearbbb.near"`.
3. `getCachedStorageDepositValue` returns the cached tuple from step 1 without ever checking the real storage balance of `"b.near"` on the `"aaa.nearbb"` token contract.
4. `estimateWithdrawalFee` sees `minStorageBalance <= userStorageBalance` from the stale/foreign entry and returns `storageDepositFee: 0n`, even though the actual destination account may not have storage registered on that token contract.
5. The withdrawal intent is built with `storageDeposit: 0n`, and the on-chain transfer to the real destination account can fail due to missing storage registration, leaving the withdrawal stuck.

	private async getCachedStorageDepositValue(
		contractId: string,
		accountId: string,
	): Promise<[MinStorageBalance, StorageDepositBalance]> {
		const key = `${contractId}${accountId}`;
		const cached = this.storageDepositCache.get(key);
		if (cached !== undefined) {
			return cached;
		}

		const result = await Promise.all([
			getNearNep141MinStorageBalance({
				contractId: contractId,
				nearProvider: this.nearProvider,
			}),
			getNearNep141StorageBalance({
				contractId: contractId,
				accountId: accountId,
				nearProvider: this.nearProvider,
			}),
		]);

		if (result[1] >= result[0]) {
			this.storageDepositCache.set(key, result);
		}

		return result;
	}
