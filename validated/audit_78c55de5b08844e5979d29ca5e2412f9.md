Confirmed: `Registry.process` validates the HMAC solely against the raw request body via `request.to_signable_string` returning `@raw_body`, while `request.shop` and `request.topic` are read straight from HTTP headers that carry zero HMAC coverage. [1](#0-0) 

### Title
Webhook `shop` (and `topic`) identity is not bound by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so `Utils::HmacValidator.validate` in `Registry.process` authenticates nothing but the request body bytes. The `shop` and `topic` values that `Registry.process` hands to the app's `WebhookHandler` are read directly from HTTP headers (`shopify-shop-domain`, `shopify-topic`) that are completely outside the signed data.

### Finding Description
`Request#hmac` and `Request#to_signable_string` are defined as: [2](#0-1) 

`shop` is taken verbatim from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no relation to the HMAC computation. `Registry.process` then does: [3](#0-2) 

The identity binding that should hold is: `hmac == HMAC(secret, body || shop || topic)`. Instead the gem only enforces `hmac == HMAC(secret, body)`, leaving `shop` (and `topic`) entirely unauthenticated. Because a single `api_secret_key` is shared by the app across *all* installed shops, any merchant who has installed the app (or any attacker who can trigger a legitimately-signed webhook for their own shop, e.g. by placing an order or updating a product on their own store) can capture a validly-signed `(body, hmac)` pair, then replay that exact body/HMAC to the app's webhook endpoint while substituting the `shopify-shop-domain` header for an arbitrary victim shop domain. `HmacValidator.validate` still succeeds because it only recomputes the HMAC over `@raw_body`, and `Registry.process` will invoke the app's handler with `WebhookMetadata` carrying the attacker-chosen `shop` value alongside the replayed body.

### Impact Explanation
This breaks the shop-to-payload binding that host applications rely on to attribute incoming webhook data to the correct tenant. Depending on how a host app's `WebhookHandler` implementation uses `WebhookMetadata#shop` (e.g., to look up/update the correct merchant record, credentials, or state), an attacker can inject forged data attributed to a shop they do not own/operate, achieving cross-tenant data corruption within the app's own storage driven entirely through this gem's webhook verification path.

### Likelihood Explanation
Exploitability requires the attacker to control at least one shop that has the app installed (to legitimately trigger a signed webhook of their choosing) and the ability to POST directly to the app's webhook endpoint with custom headers (not gated behind any other secret). Both are realistic for any unprivileged merchant/developer who installs a public app.

### Recommendation
Include `shop` (and ideally `topic`/`webhook_id`) in the signed material verified for webhooks, or otherwise cryptographically bind the header-derived `shop` to the request before passing it to `WebhookMetadata`/the handler, e.g. by validating that the `shop` claimed in headers matches an expected value tracked per-installation rather than trusting the header unconditionally.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers any webhook subscribed by the app (e.g. `orders/create`), capturing the raw POST body and its `shopify-hmac-sha256` header — both valid since they were genuinely signed by Shopify using the app's shared `client_secret`.
2. Attacker POSTs the exact same `raw_body` and `shopify-hmac-sha256` value to the app's webhook endpoint, but sets `shopify-shop-domain: victim-shop.myshopify.com` and `shopify-topic` to the desired handler topic.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, raw_body)` and matches — [4](#0-3)  passes.
4. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...)` [5](#0-4) , causing the app to process attacker-controlled data as if it originated from the victim shop.
