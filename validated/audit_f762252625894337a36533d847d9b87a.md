### Title
Unanchored `indexOf('://')` scan in `hostnameFromString` lets an embedded scheme spoof the resolved hostname, causing exodus.io-scoped secret headers to attach to non-exodus.io requests - (File: adapters/fetch-factory/src/hostname.js)

### Summary
`hostnameFromString` locates the authority component of a URL by scanning for the first occurrence of `://` anywhere in the string, rather than requiring it to follow a scheme at the start of the string. A relative path/URL such as `/proxy?next=https://exodus.io/leak` therefore resolves to hostname `exodus.io`, even though the actual `fetch` call target is the relative path itself (resolved against whatever base the runtime/environment applies), not `https://exodus.io`. `FetchFactory#buildHeaders` then matches `exodus.io` in `headerConfigs` and attaches exodus.io-scoped secret headers (e.g. `x-api-key`, `x-exodus-app-id`) to that mismatched request.

### Finding Description
- `hostnameFromString` (`adapters/fetch-factory/src/hostname.js:11-37`) does `url.indexOf(PROTOCOL_SEPARATOR)` with no anchoring/requirement that the match be at index 0 or preceded by a valid scheme token. [1](#0-0) 
- For input `/proxy?next=https://exodus.io/leak`, `indexOf('://')` finds the occurrence inside the query string, slices from there, then trims at the next `/` to yield `exodus.io`, which passes `isValidHostname`. [2](#0-1) 
- `FetchFactory#create()` passes the *same original string* (not the embedded URL) to `this.fetchFn(url, options, ...)` — the actual network call target is whatever `url` string is (a relative path in this scenario), while `#buildHeaders` used the spoofed hostname to select header config. [3](#0-2) 
- `#buildHeaders` looks up `this.headerConfigs` by the resolved hostname (exact match or subdomain suffix match) and attaches any matched per-host headers, e.g. secrets configured via `setHeaders(secretHeader, ['exodus.io'])` or `setDefaultExodusIdentifierHeaders`. [4](#0-3) 
- There is no check that the actual fetch destination equals the resolved hostname before attaching secret headers, and no restriction that the scheme separator must appear at the very start of the string (i.e., a proper absolute-URL check like `^[a-z][a-z\d+\-.]*:\/\//i` at index 0).

### Impact Explanation
If a caller constructs a `FetchFactory`-produced fetch call using a string that is not itself the final request target but contains an embedded `exodus.io` URL later in the string (e.g., a relative proxy/forwarder path, a query parameter, or path segment), the factory will misattribute exodus.io-scoped secret headers (`x-api-key`, `x-exodus-app-id`, `x-exodus-version`) to that request. Since `fetchFn` is invoked with the original (non-exodus.io) string/target, those secrets are transmitted to whatever host actually services that relative/attacker-influenced request, disclosing backend API keys and app-identifier headers to non-Exodus infrastructure. This matches a secret-disclosure impact that can enable replay of authenticated backend calls feeding remote-config/price data.

### Likelihood Explanation
Exploitability strictly depends on a caller passing a `FetchFactory`-wrapped fetch a URL/path string that (a) is not directly resolved as `https://exodus.io/...` at the network layer and (b) contains an embedded `://exodus.io` substring later in the string — for example a proxy/relative endpoint that echoes or forwards a `next=`/`url=` query parameter. I could not find, within the indexed portions of this repo, a concrete caller site that constructs such attacker-influenced relative strings and feeds them into a `FetchFactory` instance configured with `exodus.io`-scoped secrets; all located call sites in tests/README use direct absolute `https://exodus.io/...` strings as both the parsing target and the fetch target. [5](#0-4)  Whether such a vulnerable caller exists elsewhere in the broader wallet codebase (outside the indexed subset) is unconfirmed.

### Recommendation
Anchor the scheme/authority detection so it only matches an absolute URL at the start of the string, e.g. require `/^[a-z][a-z\d+.-]*:\/\//i.test(url)` before running `indexOf('://')`, or better, use the platform `URL` parser with a defined base and reject/short-circuit when the input is relative rather than manually scanning for `://`. Additionally, `#buildHeaders` should derive the hostname from the exact value that will be passed to `fetchFn`, not from a separately-parsed string that could diverge from the real network destination.

### Proof of Concept
```js
import { FetchFactory, hosts } from '../src/index.js'

test('embedded exodus.io URL in a relative path must not leak secret headers', async () => {
  const fetchFn = async (url, opts = {}) => Object.fromEntries(opts.headers)
  const fetchFactory = new FetchFactory(fetchFn)

  fetchFactory.setHeaders({ 'x-custom-header': 'secret-value' }, [hosts.EXODUS_HOST])

  // Real destination is a relative path; embeds an exodus.io URL only inside the query string
  const maliciousUrl = '/proxy?next=https://exodus.io/leak'

  const result = await fetchFactory.create()(maliciousUrl)

  // Expect NO exodus.io-scoped header to be attached since the real target is not exodus.io
  expect(result['x-custom-header']).toBeUndefined()
})
```
Currently, `hostnameFromString('/proxy?next=https://exodus.io/leak')` returns `'exodus.io'`, causing this test to fail (the secret header is attached), confirming the vulnerability.

function hostnameFromString(url) {
  const protocolSeparatorStart = url.indexOf(PROTOCOL_SEPARATOR)
