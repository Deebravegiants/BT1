## Title
Webhook shop-tenant confusion — HMAC covers only the raw body, not the `shop-domain` header, allowing replay with a spoofed tenant identity — (File: `lib/shopify_api/webhooks/request.rb`)

## Summary
`ShopifyAPI::Webhooks::Request` exposes a `shop` attribute that is read directly from the `x-shopify-shop-domain` / `shopify-shop-domain` HTTP header [1](#0-0) , but the HMAC signature verified by `HmacValidator.validate` is only computed over `to_signable_string`, which returns the raw request body and nothing else [2](#0-1) . `Registry.process` trusts `request.shop` to attribute the delivered payload to a specific merchant without any cryptographic binding between that header and the signed bytes [3](#0-2) .

## Finding Description
The identity binding that should hold is:

`shop authenticated by HMAC == shop attributed to the webhook payload (request.shop)`

`HmacValidator.validate_signature` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to `verifiable_query.hmac` [4](#0-3) . For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` [2](#0-1) ; the `shop-domain` header used for `request.shop` is never included in the signed material.

Because Shopify webhook HMACs are computed with the app's single `client_secret`, shared across every shop that installs the app, any shop that installs the app receives valid `(body, hmac)` pairs. An unprivileged internet user who installs the app on a shop they control (which they are free to do — this only requires being an "unprivileged internet user" from the app's perspective) can capture a legitimately-signed webhook request from their own shop, then replay that exact `(raw_body, hmac)` pair to the same public webhook endpoint while changing only the `x-shopify-shop-domain` (or `shopify-shop-domain`) header to name a different (victim) shop that also uses the app. `HmacValidator.validate` still succeeds because it only checks the body, and `Registry.process` passes the attacker-controlled `request.shop` straight into `WebhookMetadata` for the handler to act on [3](#0-2) .

Evaluating both sides of the equality:
- Before: attacker's own shop sends `(body_A, hmac_A)`, `shop-domain: shop-A.myshopify.com` → `hmac` valid, `shop` = shop-A (correct).
- After: attacker resends `(body_A, hmac_A)` with `shop-domain: shop-B.myshopify.com` → `hmac` still valid (same body, same secret), but `shop` = shop-B, a tenant the attacker never controlled data for.

The equality that should hold (`hmac-authenticated bytes == bytes that determine which tenant this payload is attributed to`) is broken because the tenant identifier lives in an unsigned header while the signature only covers the body.

## Impact Explanation
This is a cross-tenant confusion: a handler that uses `WebhookMetadata#shop` to decide which merchant record to update (order status, inventory, uninstall/GDPR handling, etc.) can be made to apply attacker-supplied body content under a victim shop's identity, without ever needing the victim's credentials, access token, or `client_secret`. This matches the "Critical — cross-tenant access" impact bucket, since the confused shop identifier crosses a tenant boundary using only a replayed, still-validly-signed request.

## Likelihood Explanation
The prerequisite is modest: the attacker only needs to install the target app on a shop they control (a normal, unprivileged action for any Shopify merchant/developer), capture one webhook delivery for a topic of interest, and replay it to the app's public webhook endpoint with a modified shop header. No secrets, tokens, or privileged access are required, and the replayed request is indistinguishable from a legitimate one by this gem's own verification logic (`HmacValidator`, `Webhooks::Registry.process`).

## Recommendation
Bind the tenant identity into the verified material, or otherwise cross-check it against a trusted source before use:
- Include the `shop-domain` header (and ideally `webhook-id`/timestamp for replay protection) in `to_signable_string`, matching it against the value Shopify itself signs, or
- Require callers/`Registry.process` to verify `request.shop` against the shop already known to be associated with the app installation before invoking the handler, and
- Document explicitly in `docs/usage/webhooks.md` that consumers must not trust `WebhookMetadata#shop` without an independent shop-installation check, since the current HMAC does not bind it.

## Proof of Concept
1. Install the target app on `attacker-shop.myshopify.com`; trigger a webhook (e.g. `orders/create`) and capture the raw POST: body `B`, header `x-shopify-hmac-sha256: H`, `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Confirm `H` validates: `ShopifyAPI::Utils::HmacValidator.validate(ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {"x-shopify-hmac-sha256"=>H, "x-shopify-topic"=>"orders/create", "x-shopify-shop-domain"=>"attacker-shop.myshopify.com"}))` returns `true`.
3. Replay the identical `B`/`H` to the same webhook endpoint but set `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `HmacValidator.validate` still returns `true` (per `lib/shopify_api/utils/hmac_validator.rb:26-31`, only `B` is checked), so `Registry.process` invokes the registered handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: parsed(B), ...)` (`lib/shopify_api/webhooks/registry.rb:188-199`), causing the host application to act on attacker-controlled data attributed to `victim-shop`.
