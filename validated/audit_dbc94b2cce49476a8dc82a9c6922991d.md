### Title
Embedded-app cookie fallback in `SessionUtils.current_session_id` accepts an unsigned, attacker-guessable session identifier when the JWT is simply omitted - ([File: lib/shopify_api/utils/session_utils.rb])

### Summary
`SessionUtils.current_session_id` is documented and used by host apps as the trusted source of the "current" session id, which is then looked up directly in the app's session storage to retrieve the shop's access token. When `Context.embedded?` is true but no `shopify_id_token` is supplied, the method falls back to reading the raw, unsigned `shopify_app_session` cookie value and returns it verbatim as the session id, with no cryptographic binding to any authenticated event. Because legitimate offline session ids are constructed deterministically as `"offline_#{shop}"` (public shop domain), an attacker who never had `api_secret_key` can supply that exact string as a cookie value and have it accepted as the current session id.

### Finding Description
The claimed invariant is:
`session_id returned by current_session_id(nil, cookies, online) == an id that was only ever produced by a party who completed a genuine OAuth exchange or held a validly-signed shopify_id_token`.

Tracing the code:
- `current_session_id` (lib/shopify_api/utils/session_utils.rb:19-37): when `Context.embedded?` is true and `shopify_id_token` is `nil`/absent, it does not error out or require re-authentication; it falls into the `else` branch and calls `cookie_session_id(cookies)`. [1](#0-0) 
- `cookie_session_id` (lib/shopify_api/utils/session_utils.rb:68-71) performs **no signature or HMAC verification** — it simply returns `cookies[SESSION_COOKIE_NAME]` as-is. [2](#0-1) 
- Offline session ids used throughout the gem are deterministic and derived solely from the public shop domain: `offline_session_id(shop) => "offline_#{shop}"`. [3](#0-2) 
- Crucially, for embedded apps the gem's own OAuth callback handler `Oauth.validate_auth_callback` deliberately **never sets a real cookie value** — it emits an already-expired, empty-value cookie (`value: "", expires: Time.now`), precisely because embedded apps are expected to rely exclusively on the JWT (`shopify_id_token`), not cookies. [4](#0-3) 

This confirms the cookie path is not meant to be reachable for embedded apps at all — yet `current_session_id` still accepts it whenever the caller simply omits the `shopify_id_token` argument (e.g., attacker sends no `Authorization` header). Since the value is never checked against any signature, HMAC, or session store binding *inside this method*, and the id format for offline sessions is fully predictable from public information (the shop's `.myshopify.com` domain), an attacker can set `Cookie: shopify_app_session=offline_<victim-shop>.myshopify.com` and omit the `Authorization` header entirely. `current_session_id` returns `"offline_<victim-shop>.myshopify.com"` — the exact primary key host apps use in their session storage to retrieve that shop's real, previously-issued offline access token (per the documented pattern in `docs/getting_started.md`, out of scope for citation but confirming intended usage). No guard in this file (`HmacValidator`, `ShopValidator`, JWT `aud`/`exp` checks, `Context.embedded?`) applies to this branch, because none of those checks are invoked on the cookie fallback path.

### Impact Explanation
If the host app follows the gem's documented pattern of calling `current_session_id` and using the returned string to load a `Session` (and its `access_token`) from storage, an attacker gains a merchant's offline access token merely by knowing the shop's domain and sending a crafted cookie — no signature, secret, or valid callback is required. This is repeatable against any shop domain the attacker can guess or observe (shop domains are frequently public/observable), constituting cross-tenant authentication bypass and access-token theft — Critical severity.

### Likelihood Explanation
Preconditions: the host app is configured `embedded: true` (as required by the question) and uses `SessionUtils.current_session_id` as documented, with the attacker simply omitting the `Authorization`/`shopify_id_token` and supplying a guessed cookie. This requires no secrets, no privileged access, and no interaction with the victim beyond knowing/guessing the shop's `.myshopify.com` domain, making it low-cost and repeatable.

### Recommendation
For embedded apps, `current_session_id` should never accept the cookie fallback at all — treat a missing/absent `shopify_id_token` for an embedded app as a hard failure (raise `Errors::MissingJwtTokenError`), removing the `else` branch entirely from the `Context.embedded?` case, consistent with the fact that `Oauth.validate_auth_callback` never issues a usable cookie for embedded apps.

### Proof of Concept
```ruby
# test/utils/session_utils_test.rb (proof)
def test_embedded_app_rejects_missing_jwt_even_with_forged_offline_cookie
  ShopifyAPI::Context.setup(..., embedded: true)

  guessed_cookie = { "shopify_app_session" => "offline_victim-shop.myshopify.com" }

  # Attacker never sends shopify_id_token (no Authorization header)
  assert_raises(ShopifyAPI::Errors::MissingJwtTokenError) do
    ShopifyAPI::Utils::SessionUtils.current_session_id(nil, guessed_cookie, false)
  end
end
```
Current behavior (unpatched): the call above returns `"offline_victim-shop.myshopify.com"` successfully instead of raising, demonstrating that the returned session id equals the attacker-guessed string rather than a value tied to any authenticated event — violating the claimed binding.
