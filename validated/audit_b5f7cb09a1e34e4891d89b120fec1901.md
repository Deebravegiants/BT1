### Title
Unrestricted route callbacks can add unauthorized token transfers to a caller’s signed authorization tree - ([File: contracts/controller/src/strategies/swap.rs])

### Summary

The controller accepts caller-supplied swap routes and invokes the configured router after authorizing only the controller’s input transfer, but the controller’s balance checks do not constrain which downstream contracts the route invokes. A malicious route can cause a nested third-party contract to request a token transfer from the caller; transaction simulation records that transfer as a child of the caller’s `swap_collateral` authorization, and signing the simulated tree authorizes the theft. [1](#0-0) [2](#0-1) 

### Finding Description

`swap_collateral` is callable by the account owner or delegate and accepts an arbitrary encoded `swap` payload for converting withdrawn collateral into another asset. [3](#0-2) [4](#0-3) 

`swap_tokens` snapshots only the controller’s input and output balances, authorizes one exact `token_in.transfer(controller, router, amount_in)`, invokes `router.execute_strategy`, and then verifies that the router did not overspend the input and returned a positive output. [5](#0-4) 

Those checks bound the router’s use of controller-held swap funds, but they do not validate contracts reached while interpreting the route or prevent route-selected code from initiating an unrelated `token.transfer(caller, attacker, amount)` under the caller’s authorization. [6](#0-5) 

The repository’s auth-tree PoC demonstrates this behavior: simulation places a rogue pool’s unrelated wallet-token transfer as a sub-invocation beneath Alice’s `swap_collateral` authorization. [7](#0-6) 

When Alice signs the simulated poisoned tree, the unrelated wallet-token transfer succeeds while the route still returns a valid swap output and deposits it into her position. [8](#0-7) 

### Impact Explanation

An attacker can steal arbitrary transferable tokens held by a `swap_collateral` caller, including tokens unrelated to the lending position and not supplied to the protocol. [9](#0-8) [10](#0-9) 

This constitutes theft of user funds and is not limited to the collateral amount routed through the swap. [11](#0-10) 

### Likelihood Explanation

The attack requires the victim to submit a malicious route and sign the authorization tree containing the unexpected token transfer, so exploitation depends on a malicious route provider, compromised client, or wallet UI that does not clearly distinguish nested authorization requests. [12](#0-11) [13](#0-12) 

Because the malicious transfer appears in the transaction’s authorization data rather than only in the encoded route, a correctly implemented wallet can block it, making this a **Medium** rather than an unconditional critical issue. [14](#0-13) 

### Recommendation

Restrict swap routes to audited venue contracts or a protocol-controlled pool registry instead of allowing arbitrary route-selected contract addresses. [15](#0-14) 

If arbitrary routes remain supported, clients and wallets should simulate the transaction and reject any caller authorization tree containing sub-invocations other than the expected input-token transfer required by the strategy. [16](#0-15) 

The expected authorization shape should also be documented for every route-bearing entrypoint, including `multiply`, `swap_debt`, `swap_collateral`, and `repay_debt_with_collateral`. [17](#0-16) [18](#0-17) 

### Proof of Concept

The test harness builds a victim account with supplied USDC and an unrelated wallet-token balance, then encodes a route whose `hop_pool` is an attacker-deployed contract configured to transfer that wallet token to the attacker. [19](#0-18) [11](#0-10) 

The route is submitted through `swap_collateral(alice, account_id, USDC_hub_asset, amount, ETH_hub_asset, route)`. [20](#0-19) 

During router execution, the route-selected contract calls `token.transfer(alice, attacker, WALLET_BALANCE)` on the unrelated token. [21](#0-20) 

Simulation records that transfer as a child of Alice’s `swap_collateral` authorization, and signing that tree allows the call to complete with Alice’s wallet balance reduced to zero and the attacker receiving `WALLET_BALANCE`. [2](#0-1) [8](#0-7)
