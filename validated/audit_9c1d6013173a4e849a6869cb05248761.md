### Title
Reachable `assert!` in epoch-reward-commission distribution can panic/halt the validator on a legitimate accounting edge case - (File: `runtime/src/bank/partitioned_epoch_rewards/calculation.rs`)

### Summary
`Bank::distribute_reward_commissions` contains an `assert!` that checks a global accounting invariant across independently-computed lamport totals (`point_value.rewards >= distributed_lamports + distributed_to_incinerator_lamports + burned_lamports + total_stake_rewards_lamports`). This is the same bug class as the reported Dynamo4626 issue: a hard revert/panic on an accounting invariant that is expected to always hold, but is computed from multiple independently-derived, floating/rounded sub-calculations. If any edge case causes the sum to (even slightly) exceed `point_value.rewards`, every validator that reaches this code path at the epoch boundary will panic, rather than gracefully handling the condition.

### Finding Description
The assert lives in `distribute_reward_commissions` [1](#0-0) , which is invoked from `begin_partitioned_rewards` at every epoch boundary for every bank (i.e., every validator, not just the leader) [2](#0-1) . The invariant asserted is: [3](#0-2) 

`point_value.rewards` is the epoch's total inflation reward budget computed earlier, independently, via `calculate_epoch_inflation_rewards` or (for Alpenglow epochs) a persisted `EpochInflationAccountState` value [4](#0-3) . The right-hand side of the assert is the sum of commission-account distribution amounts (loaded and paid just before the assert, deferred specifically so intervening account mutations, e.g. "VAT burns", are reflected — see the comment at lines 369-372) plus `total_stake_rewards_lamports`, which was computed earlier as part of `stake_rewards` at calculation time.

This mirrors exactly the vault bug pattern: two independently-derived totals (one is a "ceiling"/budget calculated up-front, the other is the sum of amounts actually paid out, calculated separately and with intervening state mutation) are asserted to satisfy an ordering invariant, and any real-world drift between them (rounding, an intervening account mutation reducing/increasing available lamports, double counting adjustments, etc.) causes a hard `panic!` instead of a controlled/graceful degradation. The code repo's own tests explicitly probe near this exact boundary — `test_alpenglow_partitioned_rewards_use_epoch_start_budget_after_burn` intentionally engineers a scenario where a recorded payout exceeds a recalculated ceiling due to an intervening burn between reward calculation and freeze/distribution [5](#0-4) , demonstrating that the codebase itself acknowledges the ceiling and the paid amount can legitimately diverge due to intervening mutations — which is the exact "partial loss/legitimate value drift" scenario described in the external report.

### Impact Explanation
Unlike the vault bug (which merely DoS's a single vault contract), an `assert!` panic inside `Bank::distribute_reward_commissions` runs on the **critical, mandatory, unprivileged epoch-boundary path** executed by every validator that processes/replays the relevant slot. A panic here would crash the validator process (or at minimum abort bank creation for that slot), producing a cluster-wide halt or fork/divergence at every epoch boundary once triggered, since all validators independently execute this exact code with the same on-chain state. This is strictly more severe than the reported vault issue because it is a consensus-critical path, not an isolated contract function.

### Likelihood Explanation
This is a low-but-nonzero likelihood defensive assertion meant to catch programming/logic bugs, not attacker input. Because `point_value.rewards`, `total_stake_rewards_lamports`, and the commission distribution amounts are computed via distinct code paths, with commission account loading/rewarding intentionally deferred until distribution time to account for "intervening account mutations" (per the code's own comment), any accounting edge case — e.g., a rounding or double-adjustment bug in commission math, or additional VAT/Alpenglow-related burns not accounted for in the up-front point-value budget — can trigger this in production during ordinary (non-malicious) epoch transitions. This is analogous to the reported vault scenario where a legitimate partial loss (not an attack) triggered an assert that should have degraded gracefully.

### Recommendation
Follow the same remediation pattern as the referenced fix: replace the `assert!` with a recoverable path. Since this runs inside consensus-critical bank construction, an `assert!`/panic is far too destructive for a condition that can legitimately occur due to intervening account mutations; the code should instead clamp/saturate the values (e.g., cap `distributed_lamports`/burn any excess, or downgrade to a `warn!`/`datapoint_error!` and continue) rather than crashing the validator. At minimum, this invariant should be verified via fuzz/property testing across all Alpenglow/Tower epoch-type and VAT-burn interleavings to ensure it can never legitimately fail in production before being downgraded from a hard panic to a recoverable branch.

### Proof of Concept
A full reproduction requires driving the reward calculation and distribution phases through a specific interleaving of vote-account commission changes and VAT/incinerator burns between `calculate_rewards_for_partitioning` (which fixes `point_value.rewards`) and `distribute_reward_commissions` (which computes the actual paid amounts). The codebase's own test `test_alpenglow_partitioned_rewards_use_epoch_start_budget_after_burn` [6](#0-5)  demonstrates that the recorded payout can legitimately exceed a recalculated post-burn ceiling in this window; extending that scenario to also route lamports through `distribute_reward_commissions`'s commission-loading path (rather than only `calculate_epoch_inflation_rewards`) would be required to trigger the specific `assert!` at line 398 directly — this was not verified to actually panic within the scope of this review, and would require running the test suite / constructing a targeted integration test to confirm exploitability versus the assertion always holding in practice.

    #[test]
    fn test_alpenglow_partitioned_rewards_use_epoch_start_budget_after_burn() {
        let validator_keypairs = vec![genesis_utils::ValidatorVoteKeypairs::new_rand()];
        let GenesisConfigInfo {
            mut genesis_config, ..
        } = genesis_utils::create_genesis_config_with_alpenglow_vote_accounts(
            1_000_000_000 * LAMPORTS_PER_SOL,
            &validator_keypairs,
            vec![100 * LAMPORTS_PER_SOL],
        );
        genesis_config.epoch_schedule = EpochSchedule::new(SLOTS_PER_EPOCH);
        let features_to_deactivate = crate::slot_params::slot_time_feature_ids().to_vec();
        deactivate_features(&mut genesis_config, &features_to_deactivate);

        let (bank, bank_forks) =
            Bank::new_for_tests(&genesis_config).wrap_with_bank_forks_for_tests();
        let bank = Bank::new_from_parent_with_bank_forks(
            bank_forks.as_ref(),
            bank,
            SlotLeader::default(),
            SLOTS_PER_EPOCH,
        );
        assert_eq!(bank.epoch(), 1);

        let recorded_budget = EpochInflationAccountState::new_from_bank(&bank)
            .and_then(|state| state.inflation_rewards_for_epoch(bank.epoch()))
            .expect("epoch-start inflation budget must be persisted");
        // Alpenglow rewards are rounded down once per slot, so this is the largest
        // payout that can actually have been recorded during the epoch.
        let recorded_payout = recorded_budget / SLOTS_PER_EPOCH * SLOTS_PER_EPOCH;

        let vote_pubkey = validator_keypairs[0].vote_keypair.pubkey();
        let mut vote_account = bank.get_account(&vote_pubkey).unwrap();
        let VoteStateVersions::V4(mut vote_state) = vote_account
            .deserialize_data::<VoteStateVersions>()
            .unwrap()
        else {
            panic!("unexpected vote state version");
        };
        let last_credits = vote_state
            .epoch_credits
            .last()
            .map(|(_epoch, final_credits, _initial_credits)| *final_credits)
            .unwrap_or_default();
        vote_state
            .epoch_credits
            .push((bank.epoch(), last_credits + recorded_payout, last_credits));
        vote_account
            .serialize_data(&VoteStateVersions::V4(vote_state))
            .unwrap();
        bank.store_account(&vote_pubkey, &vote_account);

        // Freezing burns the VAT transferred to the incinerator at the epoch
        // boundary, reducing capitalization after the reward budget was fixed.
        bank.freeze();
        let recalculated_ceiling =
            bank.calculate_epoch_inflation_rewards(bank.capitalization(), bank.epoch());
        assert!(
            recorded_payout > recalculated_ceiling,
            "the test must reproduce a payout above the post-burn ceiling: \
             recorded_payout={recorded_payout}, recalculated_ceiling={recalculated_ceiling}"
        );

        let bank = Bank::new_from_parent(
            bank,
            SlotLeader::default(),
            SLOTS_PER_EPOCH.saturating_mul(2),
        );
        assert_eq!(bank.epoch(), 2);

        let epoch_rewards = bank.get_epoch_rewards_sysvar();
        let EpochRewardStatus::Active(EpochRewardPhase::Calculation(calculation_status)) =
            &bank.epoch_reward_status
        else {
            panic!("{:?} not active calculation", bank.epoch_reward_status);
        };
        let stake_rewards = calculation_status
            .all_stake_rewards
            .enumerated_rewards_iter()
            .map(|(_index, reward)| reward.inflation.stake_reward)
            .sum::<u64>();
        assert_eq!(epoch_rewards.total_rewards, recorded_budget);
        assert_eq!(
            epoch_rewards.distributed_rewards + stake_rewards,
            recorded_payout,
            "every recorded reward lamport must still be paid"
        );
    }
