### Title
Third-party `supply` restamps an arbitrary account's cached risk tuple to the current (potentially worse) listing config, enabling forced liquidation - (File: contracts/controller/src/positions/supply.rs)

### Summary
The Pterodactyl bug is a "user-controlled key dereferences an arbitrary stored object" flaw: `confirmation_token` lets an attacker pick which cache entry the auth code reads, loading another user's credentials. In XOXNO Lending the analog shape is `supply(caller, account_id, spoke_id, assets)`: `account_id` is a user-supplied key into `AccountMeta`/`SupplyPositions` storage, and the third-party guard only verifies that each supplied asset is an *existing* supply position — it never requires owner or delegate authorization. Because each supplied leg unconditionally calls `refresh_supply_risk_params` with `RiskRefreshScope::FullTuple`, an unprivileged address can force another account's cached entry LTV / liquidation threshold / liquidation bonus / fees to be restamped to the *current* spoke-asset config, which may be strictly worse than the parameters the position was opened under.

### Finding Description
`process_supply` resolves `account_id` via `load_or_create_account` under `AccountGuard::Supply`, which only checks `require_spoke_match` — no ownership check for existing accounts (`contracts/controller/src/account.rs` lines 99–111). The only third-party restriction is `require_third_party_existing_supply`, which requires every supplied `hub_asset` to already exist in `account.supply_positions` (`contracts/controller/src/positions/supply.rs` lines 86–97).

Every deposit leg then flows through `merge_supply_leg`, which calls `refresh_supply_risk_params(..., RiskRefreshScope::FullTuple)` *before* applying the new scaled amount (`supply.rs` lines 288–296). Per the documented design ("Supply, withdraw, and update_account_threshold can refresh them"), the per-position `entryLtvBps`, `entryLiquidationThresholdBps`, `entryLiquidationBonusBps`, and `entryLiquidationFeesBps` are cached risk weights stamped at entry time, and health factor is computed from these cached values.

This means:

1. An account opened when a market had, e.g., liquidation threshold 80% retains that stamp indefinitely.
2. Governance later tightens the listing (lower LTV/threshold, higher bonus/fees) — existing accounts keep their better stamps because restamping only happens on their own actions.
3. An attacker supplies a dust amount of a market the victim already holds. The check at lines 86–97 passes (position exists), and the leg refreshes the victim's `entry_*` tuple to the new, worse config.
4. The victim's health factor drops immediately. If it crosses below 1.0, the attacker calls `liquidate` and seizes collateral at the liquidation bonus — a discount paid by the victim.

The asymmetry: the owner benefits from grandfathered parameters only because restamping is voluntary; the attacker converts an informational `account_id` into a write path over the victim's risk state, exactly mirroring the report's "user-controlled key selects another user's stored data."

### Impact Explanation
Theft of user funds: a victim account near the boundary under its grandfathered thresholds becomes liquidatable after the forced restamp, and the attacker captures the liquidation bonus on seized collateral. Even when the account does not immediately fall below HF 1.0, forced application of higher `entry_liquidation_fees`/`bonus` worsens the victim's eventual liquidation outcome. The cost to the attacker is a dust supply (which stays credited to the victim), making the attack cheap whenever a market config has been tightened after positions were opened.

### Likelihood Explanation
Requires a governance risk-parameter tightening (lower LTV/liquidation threshold or higher fees/bonus) on a market where a victim holds an existing supply position and is close to liquidation under the old params — a routine occurrence as listings age and parameters are retuned. The attacker needs no authorization, no timing beyond normal submission, and the dust cost is the only expense. Reachable by any unprivileged address via `controller.supply(account_id = victim, spoke_id, [(hub_asset, dust)])`.

### Recommendation
Extend `require_third_party_existing_supply` (or the account guard) so that supplying to an existing non-zero `account_id` requires `require_owner_or_delegate`, matching the authorization model used by `withdraw`, `multiply`, and `migrate_from_blend`. If permissionless top-ups to existing positions are a deliberate feature, skip `refresh_supply_risk_params` (or use a non-downgrading scope, e.g., only refresh when the new tuple is not worse for the position holder) in `merge_supply_leg` when the caller is not the owner/delegate.

### Proof of Concept
1. Governance lists asset X with liquidation_threshold 8500 bps; victim supplies X (position stamped at 8500) and borrows against it.
2. Governance later reduces X's liquidation_threshold to 7000 bps. Victim's stored stamp remains 8500 and HF stays healthy.
3. Attacker calls `supply(caller = attacker, account_id = victim_id, spoke_id, [(X, 1)])`. `require_third_party_existing_supply` passes since the victim already holds X; `merge_supply_leg` calls `refresh_supply_risk_params` with `FullTuple`, overwriting the victim's entry tuple with 7000 bps.
4. Victim's recomputed HF falls below 1.0. Attacker calls `liquidate` on the victim account and seizes collateral at the (newly stamped, higher) liquidation bonus.

Note: I was unable to inspect `refresh_supply_risk_params` in `risk/params.rs` within the available iterations to confirm whether the refresh is unconditionally applied or merge-guarded; the finding assumes the documented behavior that supply refreshes the full entry tuple, which `merge_supply_leg`'s unconditional call at lines 288–296 supports.
