### Title
Missing ERC20 return-value validation in Tron IntentGatewayV2 outbound transfers leads to silent transfer failures and permanent loss of escrowed funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron deployment of `IntentGatewayV2` uses `SafeERC20.safeTransferFrom` for pulling tokens into escrow, but reverts to raw low-level `.call()` for paying tokens *out* of escrow in `withdraw()` and in the `SweepDust` branch of `onAccept()`. These calls only check that the low-level call did not revert (`success`), never decoding and checking the boolean return value the ERC20 standard requires callers to validate. A token that returns `false` on `transfer` instead of reverting will pass the `!success` check while silently failing to deliver funds, yet the contract still finalizes escrow accounting as if the transfer succeeded.

### Finding Description
`SafeERC20 for IERC20` is imported and used for all *inbound* transfers, e.g. `IERC20(token).safeTransferFrom(msg.sender, ...)` in `placeOrder` (`evm/tron/contracts/apps/IntentGatewayV2.sol:405,459,484`). [1](#0-0) 

However, outbound transfers in `withdraw()` bypass `SafeERC20` and use a raw low-level call, checking only that the call itself didn't revert:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
``` [2](#0-1) 

The same pattern is repeated for fee redemption: [3](#0-2) 

and for `SweepDust` handling inside `onAccept()`: [4](#0-3) 

Per EIP-20, "callers MUST handle `false` from returns" — a `false` return does not revert the call, so `success` is `true` even though the transfer failed. None of these three call sites decode `returndata` to validate the boolean, unlike `SafeERC20`, which checks both call success and (if return data is present) that it decodes to `true`.

Immediately after each of these unchecked transfers, the contract irreversibly updates state:
- `withdraw()` decrements `_orders[body.commitment][token] -= amount`, sets `_filled[body.commitment] = beneficiary`, and emits `EscrowReleased`/`EscrowRefunded` — regardless of whether the beneficiary actually received tokens. [5](#0-4) 

### Impact Explanation
Both `withdraw()` (triggered by an incoming `RedeemEscrow`/`RefundEscrow` message that any relayer can deliver once produced on the source chain) and the `SweepDust` handler are entry points reachable in the normal course of settling user-placed orders — `order.inputs`/output tokens are attacker/user-controlled addresses chosen at `placeOrder` time. If the escrowed or swept token is one that returns `false` instead of reverting on failure (a known real-world ERC20 pattern, e.g. old-style ZRX-style tokens, paused/blacklist-capable tokens, or a token deliberately crafted by a malicious order-placer), the beneficiary/solver never receives their funds, yet:
- the escrow mapping (`_orders`) is decremented to zero,
- the order is marked `_filled`,
- the corresponding event is emitted as if settlement succeeded.

Because the order is now permanently marked filled/refunded, there is no remaining code path to reclaim the un-transferred tokens still sitting in the contract — this is a permanent freezing of user/solver funds inside the `IntentGatewayV2` contract on Tron.

### Likelihood Explanation
The path is triggered by completely standard, unprivileged protocol usage: a user places an order with an arbitrary ERC20 as input/output token (`placeOrder`), a solver fills it, and the resulting `RedeemEscrow`/`RefundEscrow`/`SweepDust` message is delivered by any relayer through the normal ISMP flow. No admin or governance action is required, and Tron's own token ecosystem (TRC20) — including USDT-Tron style tokens with unusual/legacy transfer semantics — makes false-returning-on-failure tokens a realistic scenario for this specific deployment.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `withdraw()` (both the token loop and the fee redemption) and in the `SweepDust` branch of `onAccept()` with `IERC20(token).safeTransfer(beneficiary, amount)`, consistent with the `SafeERC20` usage already applied to inbound transfers (`safeTransferFrom`) in the same contract.

### Proof of Concept
1. User calls `placeOrder` with `order.inputs[0].token` set to a custom ERC20 ("EvilToken") that returns `false` on `transfer` when a condition is met (e.g., recipient is blacklisted, or simply always returns `false` without reverting) — accepted since inbound uses `safeTransferFrom` from the user, which the user controls and can make succeed.
2. Order is filled cross-chain; the source chain gateway receives a `RedeemEscrow`/`RefundEscrow` message with `beneficiary` set to the blacklisted/never-payable address (or simply relies on EvilToken always returning `false`).
3. `onAccept` → `withdraw()` executes `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))`; EvilToken's `transfer` returns `false` without reverting, so `success == true`.
4. `_orders[body.commitment][token] -= amount` zeroes out escrow accounting, `_filled[commitment]` is set, and `EscrowReleased`/`EscrowRefunded` is emitted — but `beneficiary`'s token balance never increased.
5. The `amount` of EvilToken remains stranded in the `IntentGatewayV2` contract with no accounting path or function to recover it, since the order is already finalized.
