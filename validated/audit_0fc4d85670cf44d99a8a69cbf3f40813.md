### Title
`HyperFungibleToken.addChain` allows registering the local chain as a peer, permanently burning user funds on a self-referential transfer - (File: sdk/packages/core/contracts/apps/HyperFungibleToken.sol)

### Summary
`HyperFungibleToken.addChain` (and the equivalent in `HyperFungibleTokenUpgradeable`, `WrappedHyperFungibleToken`, `WrappedHyperFungibleTokenUpgradeable`) lets the owner register any `chainId`/`moduleId` pair with no check that `chainId` differs from the contract's own state machine identifier [1](#0-0) . If the local chain ID is ever registered as a "supported chain" (operator mistake, copy-paste of a peer list, or scripted deployment bug), `send()` will burn the caller's tokens and dispatch an ISMP POST request whose `dest` equals the chain it was dispatched from [2](#0-1) . This is structurally identical to the reported Wormhole NTT `setPeer` bug: a same-chain "peer" configuration lets a normal, unprivileged token holder trigger a burn that can never be completed by a matching mint, permanently destroying their funds.

### Finding Description
`_buildDispatchPost` only checks that the destination is *registered* (`dest.length == 0` reverts), not that it differs from the local chain [3](#0-2) . `send()` unconditionally burns from the caller before dispatch [4](#0-3) .

The dispatched `PostRequest` has `source == dest == host.host()`. On the relaying side, `HandlerV2.handlePostRequests` only verifies `leaf.request.dest.equals(host.host())` [5](#0-4) , which trivially passes for a self-referential request — but delivering it requires a state/consensus proof of "the destination chain" (i.e., this same chain) verified through a `consensusClient`/state-machine client. Hyperbridge's consensus and state-machine clients are built to attest to *remote* chains' state, not the local chain's own live state; `pallet-ismp`'s equivalent check in `handlers::request::handle` requires `source_chain != msg.proof.height.id.state_id` unless the host is configured as a proxy [6](#0-5) , so there is no supported path to prove and finalize this chain's own state back to itself for message delivery. In practice such a request can never be delivered; it can also never be legitimately timed out and refunded through the normal HFT flow either, unless a relayer/anyone submits a timeout message after `params.timeout` elapses.

This precisely mirrors the reported bug: `NttManager::setPeer` allowed the same-chain address to be registered as a peer, so `transfer()` sent tokens that could never be executed on the "destination" (which was the same chain), permanently stranding funds. Here, `addChain` has the same missing same-chain guard, and `send()` is the unprivileged, single-transaction trigger any token holder can use once the misconfiguration exists.

### Impact Explanation
Once the same-chain ID is (even accidentally) registered via `addChain`, every unprivileged user who calls `send()` with that chain as destination burns real value with no reachable path to mint it back on delivery, and no assurance that a timeout-based refund will materialize (timeout still requires an active relayer/permissionless caller to submit a valid timeout proof — plausible, but not guaranteed, and the burn is real and immediate). This is a direct, permanent loss-of-funds vector for end users of any `HyperFungibleToken`/`WrappedHyperFungibleToken` deployment that hits this misconfiguration, matching "permanent freezing of funds" impact criteria.

### Likelihood Explanation
Likelihood is moderate: it requires an owner/operator misconfiguration (e.g., accidentally passing the current chain's `StateMachine` id into `addChain`, a common mistake when scripting peer registration across many chains, exactly the scenario called out in the original report). Given there is no validation anywhere in `addChain`/`configure` to prevent it, and multiple similar contracts in the repo (`HyperFungibleToken`, `HyperFungibleTokenUpgradeable`, `WrappedHyperFungibleToken`, `WrappedHyperFungibleTokenUpgradeable`) share this same unguarded pattern, the probability of at least one deployment doing this across many chains is non-trivial, and its impact once triggered is deterministic burn-with-no-delivery for every affected `send()` call.

### Recommendation
In `addChain` (and its equivalents in the upgradeable/wrapped variants), reject registrations where `chainId` equals the contract's own host state machine id, e.g.:
```solidity
function addChain(bytes calldata chainId, bytes calldata moduleId) external onlyOwner {
    if (keccak256(chainId) == keccak256(IHost(_host).host())) revert SameChainNotAllowed();
    _supportedChains[chainId] = moduleId;
}
```
Additionally consider re-validating `params.dest != host()` inside `send()`/`_buildDispatchPost` as defense in depth, so that even a pre-existing bad registration cannot be exploited by `send()`.

### Proof of Concept
1. Owner deploys `HyperFungibleToken` on chain `EVM-1` and calls `configure(...)` with the local `IsmpHost`.
2. Owner mistakenly calls `addChain(StateMachine.evm(1), abi.encodePacked(someAddress))` — registering the token's own chain as a "peer" (identical class of mistake to the original report's `setPeer(localChainId, ...)`).
3. Any user calls `send({dest: StateMachine.evm(1), to: recipientBytes, amount: X, timeout: T, relayerFee: 0, data: ""})`.
4. `_burn(msg.sender, X)` executes immediately [7](#0-6) ; the dispatched `PostRequest` has `source == dest`.
5. No consensus/state-machine client path exists to prove this chain's own state back to itself for `HandlerV2.handlePostRequests` to deliver the message and mint on "destination" — the request is undeliverable, and the user's tokens are burned with no completed mint. The only possible recovery is a timeout-refund via `onPostRequestTimeout` after `T` seconds, and only if `timeout != 0` and someone actually submits the timeout proof, otherwise the funds are permanently gone [8](#0-7) .

```text
    function _buildDispatchPost(SendParams calldata params) internal view returns (DispatchPost memory) {
        bytes memory dest = _supportedChains[params.dest];
        if (dest.length == 0) revert UnsupportedChain();

        bytes memory body = abi.encode(Message({
            from: abi.encodePacked(msg.sender),
            to: params.to,
            amount: params.amount,
            data: params.data
        }));

        return DispatchPost({
            dest: params.dest,
            to: dest,
            body: body,
            timeout: params.timeout,
            fee: params.relayerFee,
            payer: msg.sender
        });
    }
```
