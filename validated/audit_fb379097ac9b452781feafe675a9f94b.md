### Title
`PoaBridge.describeWithdrawal()` misreports withdrawal status/txHash when multiple withdrawals of the same asset are batched in one intent - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal()` deliberately abandons index-based matching and instead matches a withdrawal record from the POA Bridge API purely by `assetId`, on the stated assumption that "the response list is unsorted." When a single NEAR transaction contains two or more withdrawal intents for the same asset (a supported batching pattern in this SDK, e.g. `withdrawalParams: [withdrawalParams, withdrawalParams]` used in `sdk.createWithdrawalCompletionPromises.test.ts`), every `describeWithdrawal` call for that asset resolves against the same/first matching record, so distinct withdrawals at different indices can be reported with the same `status`/`txHash` even though only one of them has actually completed on-chain.

### Finding Description
`describeWithdrawal()` calls `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`, matching solely by `assetId`, with an explicit comment justifying the choice: "Response list is unsorted, so we match by assetId instead of index." [1](#0-0) 

The `index` field on `WithdrawalIdentifier` — produced by `createWithdrawalIdentifier()` for each withdrawal in a batch — is not used at all to disambiguate which record in `response.withdrawals` corresponds to which withdrawal: [2](#0-1) 

The SDK explicitly supports issuing multiple withdrawals with identical `withdrawalParams` (same `assetId`) inside one NEAR transaction and tracking each with its own promise/index via `sdk.createWithdrawalCompletionPromises`: [3](#0-2) 

Because `findMatchingWithdrawal` keys only on `assetId` (or the derived `near_token_id`, per the regression comment "Matching must use near_token_id, not defuse_asset_identifier"), two withdrawal calls for the same asset in the batch will both resolve to whichever matching entry `findMatchingWithdrawal` returns (effectively the first match), rather than each to its own on-chain record: [4](#0-3) 

This breaks the equality that should hold for every withdrawal: `status/txHash reported for withdrawal[i] == the on-chain outcome of withdrawal[i]`. Instead, `withdrawal[i]` can be reported using `withdrawal[j]`'s outcome.

### Impact Explanation
`watchWithdrawal()`/`createWithdrawalCompletionPromises()` treat a `"completed"` status with a `txHash` as authoritative proof that funds landed, resolving the caller's promise for that specific withdrawal index: [5](#0-4) 

If an integrator batches two same-asset withdrawals (e.g., to two different destination addresses or amounts) in a single NEAR transaction and relies on per-index `describeWithdrawal`/completion promises to know when each withdrawal is safe to consider settled, a completed status for the wrong index can cause the integrator to treat an unfinished withdrawal as finished (crediting/releasing downstream funds or clearing an internal ledger entry before the real transfer confirms), or to misreport the wrong destination's `txHash` for a support ticket / reconciliation record. This matches the "status or hash misreport making an integrator credit or refund twice" impact class (High).

### Likelihood Explanation
This requires no malicious actor — it triggers whenever a legitimate integrator batches ≥2 withdrawals of the same asset (a pattern the SDK's own APIs and tests explicitly support) through the POA bridge route. Given that `assetId`-based matching is described as an intentional design decision (not a bug fix in progress), and the SDK actively supports index-tracked batch withdrawals, the likelihood of hitting this in production batching flows is non-trivial for integrators using multiple same-token withdrawals per transaction.

### Recommendation
Match POA `withdrawals` records to `WithdrawalIdentifier` using a unique on-chain distinguishing key (e.g., the withdrawal's request/receipt index or a nonce/log index returned by the POA bridge API) rather than `assetId` alone, so that each `index` in a batched, same-asset withdrawal is deterministically bound to its own on-chain record. If the POA API truly cannot expose a stable per-request key, disallow/warn against batching multiple same-asset withdrawals in a single transaction, or fall back to matching by `(assetId, destinationAddress, amount)` tuple to reduce (though not eliminate) collision risk.

### Proof of Concept
1. Caller submits one NEAR transaction with two `ft_withdraw` intents for `nep141:btc.omft.near`: intent[0] sends 100000n to address A, intent[1] sends 100000n to address B (equal amounts, different destinations — a realistic batch payout).
2. Caller calls `sdk.createWithdrawalCompletionPromises` (as exercised in `sdk.createWithdrawalCompletionPromises.test.ts`) with `withdrawalParams: [paramsA, paramsB]`, producing `WithdrawalIdentifier`s with `index: 0` and `index: 1`.
3. Only the withdrawal to address A actually confirms on the POA relayer side; the withdrawal to address B is still pending.
4. `PoaBridge.describeWithdrawal()` for `index: 1` (address B) calls `findMatchingWithdrawal(response.withdrawals, "nep141:btc.omft.near")`, which returns the completed record for address A because both entries share the same `assetId`/`near_token_id`.
5. The caller's promise for `index: 1` resolves with `{ status: "completed", txHash: <address-A's-tx-hash> }`, causing the integrator to believe B's withdrawal succeeded and to record/act on A's transaction hash for B's payout — while B's actual withdrawal may later fail or complete with a different, unrecorded hash.

		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };

			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {

				status: "completed",
