### Title
Emporium `payRelayFees` skips the variable-rate relay fee when a signer wallet is used, permanently underpaying relays - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
`EmporiumUpgradeable.payRelayFees` computes the relay's fee differently depending solely on whether `signerAddress` (the Emporium `HinkalWallet` owner) is `address(0)` or not. For the non-wallet path it charges `flatFee` **plus** the `variableRate` cut of the withdrawn amount via `hinkalHelper.calculateRelayFee`, but for the wallet-invoked path it charges **only** `flatFee`, silently dropping the variable-rate portion entirely. This mirrors the reported bug class: the same `FeeStructure` (same `feeToken`, `flatFee`, `variableRate`) produces two different, inconsistent fee outcomes depending on which code path is taken, breaking the equality that a given fee structure should yield a consistent relay payment for a given withdrawn amount.

### Finding Description
`payRelayFees` in [1](#0-0)  branches on `signerAddress`:

- When `signerAddress == address(0)` (non-wallet / relay-funded flow), `relayFee = $._hinkalHelper.calculateRelayFee(sumAbs, flatFee, feeStructure.variableRate)`, which applies the full formula `flatFee + variableRate% * (sumAbs - flatFee)` as implemented in [2](#0-1) .
- When `signerAddress != address(0)` (stateful `HinkalWallet`-invoked flow used for `invokeWallet` operations), `relayFee = flatFee` only — the variable-rate cut of the withdrawn amount is never computed or paid.

Both branches use the *same* `circomData.feeStructure` (same `feeToken`/`flatFee`/`variableRate`) and the same `deltaAmountChanges[i]` (the withdrawn amount from Emporium). The `variableRate` field is never checked against `stack.maxFee` in `verifyWallet` — only `flatFee` is bounded there [3](#0-2) , and `variableRate` is not part of the EIP-712 signed `EmporiumSignature` payload either [4](#0-3) , so it plays no role in the wallet-path calculation at all — it is simply dropped.

Compare this to the direct-transact path in `Hinkal._internalTransact`, which always applies both `flatFee` and `variableRate` uniformly regardless of caller identity [5](#0-4) , and to `ExternalActionSwap`, which likewise always applies `calculateRelayFee` with the variable rate [6](#0-5) . Only the Emporium wallet-invoked branch deviates, breaking the equality that the relay fee owed for withdrawing `sumAbs` of `feeToken` under a given `FeeStructure` should be identical across all execution paths.

### Impact Explanation
This causes a permanent underpayment/loss of protocol relay fees: any time a `runAction` is executed through the `HinkalWallet` (`signerAddress != address(0)`) code path — which is a first-class, documented execution mode of Emporium (`op.invokeWallet == true`) — the relay collects only the flat fee and permanently forfeits the variable-rate percentage of the withdrawn/moved amount that it would otherwise be entitled to on every other path in the protocol. This matches the "High - theft or permanent freezing of protocol/relay fees" impact category: relay fee revenue that should have been collected on withdrawals routed through a `HinkalWallet` is never collected and is unrecoverable.

### Likelihood Explanation
The wallet-invoked (`invokeWallet`) path is a normal, intended usage mode of Emporium operations (stateful interactions such as approvals plus calls through a user's `HinkalWallet`), not an edge case. Any user constructing an `EmporiumStack` with a non-zero `signerAddress` and at least one negative `deltaAmountChanges[i]` for the `feeToken` triggers the shortfall automatically — no special privilege beyond being a normal Emporium user is required, and the discrepancy is deterministic and reproducible on every such transaction.

### Recommendation
Make the fee computation path-independent: always compute `relayFee` via `hinkalHelper.calculateRelayFee(sumAbs, flatFee, feeStructure.variableRate)` regardless of `signerAddress`, and route the resulting fee to the relay either directly (`sendToRelay`) or via the wallet (`sendToRelayFromWallet`) based on `signerAddress`, but never change the fee formula itself based on the payment channel.

### Proof of Concept
1. Attacker (any unprivileged EOA) constructs an Emporium `EmporiumStack` with `signerAddress = walletAddr` (their own `HinkalWallet`), a valid EIP-712 signature, and at least one `EmporiumOperation` with `invokeWallet = true`, per `runAction`'s dispatch logic [7](#0-6) .
2. `circomData.feeStructure = {feeToken: X, flatFee: F, variableRate: R}` with `R > 0`, and `deltaAmountChanges[i] < 0` for token `X` (e.g., a large withdrawal of `sumAbs` from the Emporium contract's balance).
3. `verifyWallet` only requires `feeStructure.flatFee <= stack.maxFee`; `variableRate` is unconstrained by the signature [3](#0-2) .
4. In `payRelayFees`, since `signerAddress != address(0)`, `relayFee = flatFee = F` is sent to the relay [8](#0-7) .
5. Had the identical `sumAbs`/`feeStructure` been processed through the `signerAddress == address(0)` branch (or through `Hinkal._internalTransact`/`ExternalActionSwap`), the relay would have received `F + R% * (sumAbs - F)`, strictly greater than `F` for `R > 0` and `sumAbs > F`.
6. The relay permanently loses the `R% * (sumAbs - F)` portion of its fee for every withdrawal routed through the wallet-invoked Emporium path, with no on-chain mechanism to recover it.

    function payRelayFees(
        CircomData calldata circomData,
        address signerAddress,
        int256[] calldata deltaAmountChanges
    ) internal {
        FeeStructure calldata feeStructure = circomData.feeStructure;

        bool foundToken = false;

        for (uint256 i = 0; i < circomData.erc20TokenAddresses.length; i++) {
            // tokens deposited into Emporium are not charged
            if (deltaAmountChanges[i] >= 0) {
                continue;
            }

            address erc20TokenAddress = circomData.erc20TokenAddresses[i];
            bool isFeeToken = erc20TokenAddress == feeStructure.feeToken;

            if (isFeeToken) {
                foundToken = true;
            }

            uint256 relayFee = 0;
            uint256 flatFee = isFeeToken ? feeStructure.flatFee : 0;

            if (signerAddress == address(0)) {
                uint256 sumAbs = uint256(-deltaAmountChanges[i]);

                EmporiumStorageVars storage $ = _getEmporiumStorage();
                relayFee = $._hinkalHelper.calculateRelayFee(
                    sumAbs,
                    flatFee,
                    feeStructure.variableRate
                );
            } else {
                relayFee = flatFee;
            }

    function calculateRelayFee(
        uint256 balance,
        uint256 flatFee,
        uint256 variableRate
    ) public pure returns (uint256 relayFee) {
        require(balance >= flatFee, "Relay Fee is over withdraw amount");
        uint256 recipientAmount = ((10000 - variableRate) *
            (balance - flatFee)) / 10000;
        relayFee = balance - recipientAmount;
    }
