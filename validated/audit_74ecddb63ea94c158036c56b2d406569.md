### Title
Webhook HMAC only covers the request body, not the `shop-domain` header, allowing shop-identity spoofing on legitimately signed webhook payloads - ([File: lib/shopify_api/webhooks/request.rb], [File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` claims to "verify the request did indeed come from Shopify" before invoking the app's handler with a `shop` value that the handler is expected to trust as an authenticated tenant identifier. In reality, the HMAC signature only covers the raw request body, never the `shop-domain` header that is used to populate `WebhookMetadata#shop`. This breaks the identity binding: `shop` claimed in the header ≠ `shop` actually authenticated by the HMAC.

### Finding Description
`Request#to_signable_string` returns only the raw body: [1](#0-0) 

while `Request#shop` is read directly from an unauthenticated header: [2](#0-1) 

`Utils::HmacValidator.validate` computes and compares the signature strictly against `to_signable_string`: [3](#0-2) 

`Registry.process` calls that validator and, once it passes, unconditionally forwards `request.shop` (the unauthenticated header) to the app's handler as verified tenant metadata: [4](#0-3) 

The library's own documentation instructs developers that `Registry.process` "will verify the request did indeed come from Shopify and then call the specified handler," and shows the `data.shop` field being used directly to key business logic (e.g., `perform_later(shop_domain: data.shop, ...)`): [5](#0-4) 

Because a Shopify app's `client_secret` (`Context.api_secret_key`) is shared across *all* shops that install the app — not scoped per-tenant — any unprivileged internet user can install the app on their own (attacker-controlled) shop and receive a webhook that is legitimately HMAC-signed with the app's secret over some body `B`. Since the header carrying the shop identity is outside the signed bytes, that attacker can replay the exact same `(raw_body, hmac)` pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. `HmacValidator.validate` still succeeds (it only checks the body/HMAC pair), and `Registry.process` passes the forged `shop` straight to the handler as if it had been authenticated, breaking the equality `shop_authenticated == shop_delivered_to_handler`.

### Impact Explanation
This allows cross-tenant identity spoofing: a party with no privileged relationship to a victim shop can cause the host application to execute webhook-driven, shop-scoped logic (e.g. mandatory GDPR webhooks like `shop/redact`, `customers/redact`, `customers/data_request`, or ordinary business webhooks) attributed to the wrong shop. This directly falls into the "cross-tenant access" Critical-impact category, since the identity binding the gem is supposed to guarantee (payload came from, and pertains to, the shop named in the metadata) does not actually hold.

### Likelihood Explanation
The attacker only needs the ability to install the target app on a shop they control (a normal, unprivileged action available to any merchant/developer), then capture one legitimate webhook delivery and replay it with a modified header value against the app's public webhook endpoint. No access to `api_secret_key`, tokens, or victim credentials is required, and the flaw is exercised purely through the gem's documented `Registry.process` API.

### Recommendation
Bind the shop (and other webhook identity headers such as topic/api-version) into the signed material that `HmacValidator` verifies, or otherwise cryptographically tie the `shop-domain` header to the signature (e.g., verify shop against a per-install allow-list before trusting `data.shop`), rather than allowing any header outside the HMAC to be treated as authenticated.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com`, obtaining a genuine webhook delivery for topic `customers/data_request` with body `B`, signed via HMAC-SHA256 using the app's `client_secret` as `H`.
2. Attacker sends an HTTP POST to the app's webhook endpoint with the same body `B` and same `X-Shopify-Hmac-Sha256: H` header, but replaces `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `H` against `HMAC(client_secret, B)` — this still passes.
4. `Registry.process` invokes the registered handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)`, i.e., the host app's business logic (as shown in `docs/usage/webhooks.md`, e.g. `perform_later(shop_domain: data.shop, webhook: data.body)`) now executes as if the legitimate victim shop sent this webhook/body, even though it was forged by the attacker.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
