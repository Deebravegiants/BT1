Confirmed: the current production `IntentGatewayV2.sol` (evm/src/apps/IntentGatewayV2.sol) is composed of `IntentsBase.sol` + `ExtrinsicIntents.sol` + `IntrinsicIntents.sol`, and the single `_sendValue` helper defined in `IntentsBase.sol` is what all cross-chain and same-chain escrow releases use for native-ETH payouts.

### Title
Cross-chain escrow release/refund permanently reverts and locks native-ETH input funds when the beneficiary/user cannot receive ETH - (File: evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
`IntentsBase._sendValue` performs a raw `call{value: amount}("")` and reverts with `InsufficientNativeToken` on failure, with no fallback path. This helper backs `_withdraw`, the function that releases escrowed native ETH to a beneficiary on `RedeemEscrow`/`RefundEscrow` delivery. Because `onAccept` failures in `EvmHost.dispatchIncoming` are simply retried (never bypassed or force-settled), a beneficiary that cannot accept plain ETH transfers causes the message to permanently fail on every retry, freezing the escrowed native ETH forever.

### Finding Description
`IntentsBase._sendValue` is defined as: [1](#0-0) 

It is invoked from `_withdraw`, the routine that pays out escrowed order inputs to a beneficiary for both refunds and fills: [2](#0-1) 

For cross-chain orders, `_withdraw` is reached from `ExtrinsicIntents.onAccept`, which handles Hyperbridge-delivered `RedeemEscrow` (pay the solver) and `RefundEscrow` (pay back `order.user`) messages: [3](#0-2) 

The destination address for this ETH push — `order.user` (for a `RefundEscrow` after a source-side or destination-side cancel) or the solver's chosen beneficiary (for `RedeemEscrow`) — is attacker/user-controlled input encoded in the order and comes from a different chain's message, so the contract has no way to validate in advance whether that address can receive ETH.

Delivery of `onAccept` calls happens through `EvmHost.dispatchIncoming`, which treats a revert as "temporarily undeliverable" and simply deletes the replay-protection receipt so the message can be retried later — it never skips or force-settles a failing call: [4](#0-3) 

If `order.user` (or the solver beneficiary) is a contract without a payable `receive`/`fallback`, or one whose fallback consumes more gas than forwarded, `_sendValue` will revert on every single retry attempt — the outcome is deterministic and does not depend on gas price, block state, or relayer behavior. Because the entire `onAccept` call reverts atomically, the escrow decrement in `_orders` is rolled back together with the failed payout, so the native ETH remains locked in the gateway with no code path capable of ever releasing it to that recipient.

This mirrors the PartyDAO finding: `LibAddress.transferEth` uses an unguarded `call{value: amount}` that reverts `_burn`/`_transfer` outright when the receiver cannot accept ETH, permanently blocking the contributor's refund/voting power. Here, `IntentsBase._sendValue` has the identical unguarded pattern and is on the only payout path for native-ETH order inputs.

Notably, the codebase already recognizes and mitigates this exact bug class elsewhere: `WrappedHyperFungibleToken.onAccept`/`onPostRequestTimeout` explicitly try a native push first and, on failure, re-wrap to WETH and deliver via ERC-20 `safeTransfer` instead of reverting: [5](#0-4) 

`IntentsBase._sendValue`/`_withdraw` has no equivalent fallback, showing the gap is an oversight rather than an accepted design tradeoff.

### Impact Explanation
Any user (or solver) who places/fills a cross-chain intent order with a native-ETH (`address(0)`) input leg while using — or later becoming, e.g. via a proxy upgrade or a rug-pulled fallback — a smart-contract address that cannot accept plain ETH transfers will have that ETH permanently and unrecoverably locked inside `IntentGatewayV2` once the corresponding `RedeemEscrow`/`RefundEscrow` message is dispatched. There is no admin sweep, no alternate withdrawal function, and no WETH-wrap fallback for this path, so the funds are frozen indefinitely — this satisfies "permanent freezing of funds" for the affected order. It also griefs the settlement flow: an order can never finalize/refund on the source chain, so on the destination side output tokens or state changes tied to that order may be stranded too.

### Likelihood Explanation
Likelihood is Medium: it requires the `order.user` or the solver-designated beneficiary to be a contract without a working ETH receiver, which is plausible for AA wallets, multisigs with custom fallback restrictions, or vaults that intentionally reject bare ETH (to force WETH-only flows), and it requires the order to include a native-ETH input. No malicious privileged party is needed — it can be triggered unintentionally by any ordinary user/solver interacting with the permissionless `placeOrder`/`fillOrder`/`cancelOrder` entry points, and once the message is dispatched cross-chain the failure mode is deterministic and unrecoverable.

### Recommendation
In `IntentsBase._sendValue` (and equivalently in `IntentGatewayV2.sol`'s same-chain `_sendValue`), mirror the pattern already used by `WrappedHyperFungibleToken`: attempt the native push, and on failure wrap the amount into WETH and deliver it via `safeTransfer` to the beneficiary instead of reverting the whole payout. Alternatively, escrow the failed native-ETH payout in a per-recipient claimable balance (pull-payment pattern) so a hostile/incompatible beneficiary address cannot block finalization of the order or lock the funds.

### Proof of Concept
1. User places a cross-chain `Order` on chain A with a native ETH input leg (`token == address(0)`), setting `order.user` to a contract address `C` that has no `receive()`/payable `fallback()` (e.g., a plain non-payable multisig or an intentionally ETH-rejecting vault).
2. The order is later cancelled from the destination chain (or expires without a fill), causing Hyperbridge to dispatch a `RefundEscrow` POST request back to chain A targeting `IntentGatewayV2`.
3. `EvmHost.dispatchIncoming` calls `onAccept` → `ExtrinsicIntents.onAccept` (`RequestKind.RefundEscrow`) → `IntentsBase._withdraw` → `_sendValue(C, amount)`.
4. `C.call{value: amount}("")` fails because `C` has no payable receiver; `_sendValue` reverts with `InsufficientNativeToken`, unwinding the entire `onAccept` call.
5. `EvmHost.dispatchIncoming` catches the failed call, deletes `_requestReceipts[commitment]`, and returns — allowing indefinite retries, all of which fail identically because `C`'s bytecode/fallback never changes.
6. The escrowed native ETH for this order remains locked in `IntentGatewayV2` permanently, with no available function to redirect or reclaim it to a different, ETH-capable address.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }
