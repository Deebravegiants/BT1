### Title
CORS wildcard-origin allowlist bypass via unanchored suffix match - ([File: core/services/gateway/network/httpserver.go])

### Summary
The Gateway's HTTP server validates the `Origin` header against `CORSAllowedOrigins` using an unanchored `strings.HasSuffix` check for wildcard entries (e.g. `*.remix.com`), allowing any origin whose hostname merely ends with the allowed suffix — including attacker-controlled domains like `evilremix.com` — to be treated as allowed.

### Finding Description
`isAllowedOrigin` splits both the incoming `Origin` header and each configured allowed origin into scheme/host/port, then for wildcard entries strips the `*.` prefix and checks `strings.HasSuffix(originHost, allowedHost)`: [1](#0-0) 

This is not boundary-checked. If an operator configures `CORSAllowedOrigins = ["*.remix.com"]`, the allowed host becomes `remix.com` after stripping `*.`, and any origin hostname ending in that literal string — e.g. `evilremix.com`, `attacker-remix.com`, or even `notremix.com` — satisfies `HasSuffix` and is incorrectly treated as allowed, because there is no check that the preceding character is a `.` (i.e., no true subdomain boundary is enforced).

This is directly analogous to the reported bug class (CWE-20/CWE-601 allowlist bypass): a permissive/experimental allowlist matcher that is supposed to restrict to a specific domain or its subdomains but can be satisfied by an attacker-chosen value that merely matches the suffix string, not the intended domain hierarchy.

The check is invoked from `handleRequest`, which is the entry point for all requests to the internet-facing Gateway HTTP server: [2](#0-1) 

`CORSAllowedOrigins` is an operator-configurable, real-world config value (used in `core/scripts/gateway/sample_config.toml` and `sample_config_tls.toml`), so wildcard patterns like `*.example.com` are an expected/supported configuration pattern, not a contrived edge case.

### Impact Explanation
When `isAllowedOrigin` returns true, the server reflects the attacker's `Origin` value into `Access-Control-Allow-Origin`, enabling a malicious webpage hosted on a domain that merely shares a suffix with an allowed pattern (e.g. `evil-remix.com` when `*.remix.com` is allowlisted) to make cross-origin browser requests to the Gateway and read responses via JavaScript. Combined with the gateway's JWT/Bearer-token extraction path in `handleRequest` (`Authorization` header handling), this creates a path for an unprivileged, remote attacker to trick a victim's browser into leaking gateway responses (message envelopes/handler responses) cross-origin to an attacker-controlled origin — a cross-user response confusion / allowlist bypass consistent with the reported bug class. Severity is moderated by the requirement that the operator configure a wildcard entry and that `CORSEnabled` be true, and by the fact that `Access-Control-Allow-Credentials` is not set in this handler, which limits (but does not eliminate, e.g. for token-based auth flows) exposure of credentialed responses.

### Likelihood Explanation
Exploitation requires: (1) the gateway operator has enabled CORS and configured at least one wildcard allowed origin (a documented/sample configuration pattern), and (2) the attacker registers or controls a domain sharing the suffix string of the allowed pattern (trivial and cheap to do, e.g. registering `notremix.com` to match `*.remix.com`), and (3) getting a victim to visit an attacker page that issues cross-origin requests to the gateway. No special privileges or insider access are needed beyond domain registration and getting the victim to load a page — a reachable, unprivileged-actor path.

### Recommendation
Fix the wildcard suffix check to enforce a proper subdomain boundary, e.g.:
```go
if strings.HasPrefix(allowedHost, "*.") {
    suffix := allowedHost[1:] // keep leading dot: ".remix.com"
    if originHost == allowedHost[2:] || strings.HasSuffix(originHost, suffix) {
        return true
    }
}
```
i.e., match on `.remix.com` (with the leading dot) rather than `remix.com`, so `evilremix.com` no longer satisfies the suffix check while `foo.remix.com` still does. Add regression tests covering sibling-suffix domains (`notremix.com`, `evil-remix.com`) to ensure they are rejected.

### Proof of Concept
1. Configure the gateway with:
```toml
CORSEnabled = true
CORSAllowedOrigins = ["https://*.remix.com"]
```
2. Send an HTTP request to the gateway endpoint with header `Origin: https://evilremix.com`.
3. In `isAllowedOrigin`, `allowedHost` becomes `remix.com` after stripping `*.`; `strings.HasSuffix("evilremix.com", "remix.com")` returns `true`, so the request is treated as allowed and the server responds with `Access-Control-Allow-Origin: https://evilremix.com`, `Access-Control-Allow-Methods`, and `Access-Control-Allow-Headers` headers as shown in `handleRequest`: [3](#0-2) 
4. A page hosted on `https://evilremix.com` can now issue cross-origin fetches to the gateway and read the responses in the browser, despite not being an intended member of the `*.remix.com` allowlist.

func (s *httpServer) handleRequest(w http.ResponseWriter, r *http.Request) {
	if s.config.CORSEnabled {
		origin := r.Header.Get("Origin")
		if s.isAllowedOrigin(origin) {
			w.Header().Set("Access-Control-Allow-Origin", origin)
			w.Header().Set("Access-Control-Allow-Methods", "GET, POST, OPTIONS")
			w.Header().Set("Access-Control-Allow-Headers", "Content-Type")
		}

		// handle preflight requests
		if r.Method == http.MethodOptions {
			w.WriteHeader(http.StatusNoContent)
			return
		}
	}
