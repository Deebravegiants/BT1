### Title
Unbounded gas forwarded to arbitrary beneficiary/solver addresses in native-token settlement paths enables EIP‑7702 gas griefing/siphoning - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`IntentsBase._withdraw`, `IntrinsicIntents._fillSameChain`, and `ExtrinsicIntents._fillCrossChain` (and their Tron mirror `evm/tron/contracts/apps/IntentGatewayV2.sol`) settle native-token legs of Intent Gateway orders with a raw `.call{value: amount}("")` to an attacker-influenced `beneficiary` address, forwarding essentially all remaining gas with no cap. This is the exact bug class from the report — an "EOA" recipient that used to be gas-cheap because it had no code can, post EIP‑7702, carry a delegation designator whose fallback runs arbitrary logic funded by whoever executes the settlement (the relayer delivering the cross-chain message, or the solver executing a same-chain fill).

### Finding Description
In `IntrinsicIntents._fillSameChain`:
```solidity
// evm/src/apps/intentsv2/IntrinsicIntents.sol:95-100
if (token == address(0)) {
    if (msgValue < beneficiaryTotal + protocolShare) revert InsufficientNativeToken();
    msgValue -= (beneficiaryTotal + protocolShare);
    (bool sent,) = beneficiary.call{value: beneficiaryTotal}("");
    if (!sent) revert InsufficientNativeToken();
``` [1](#0-0) 

and `ExtrinsicIntents._fillCrossChain` uses `_sendValue(beneficiary, beneficiaryTotal)` for the same purpose: [2](#0-1) 

The escrow-release path, `IntentsBase._withdraw`, does the equivalent for the *source-chain* settlement that fires when a relayer delivers a `RedeemEscrow`/`RefundEscrow` ISMP message via `onAccept`:
```solidity
// evm/src/apps/intentsv2/IntentsBase.sol:465-469
if (token == address(0)) {
    _sendValue(beneficiary, amount);
} else {
    IERC20(token).safeTransfer(beneficiary, amount);
}
``` [3](#0-2) 

The Tron variant makes the unbounded-gas pattern explicit at both the fill and settlement sites: [4](#0-3) 

None of these transfer sites cap the gas forwarded to `beneficiary`. `beneficiary` is attacker-controlled: it is `order.output.beneficiary` at order-placement time, or `_toAddr`-derived from the `WithdrawalRequest.beneficiary` embedded in the cross-chain message body that a solver constructs when calling `fillOrder`. Prior to EIP-7702, if `beneficiary` was an EOA the `.call{value}("")` was cheap because there was no code to execute. With EIP-7702, the same EOA can carry a delegation designator, turning the "plain ETH transfer" into an arbitrary-code execution that receives ~all remaining gas (identical mechanics to the ERC-1155 `onERC1155Received` unbounded-gas forward described in the report, just via a value-call fallback instead of a token-receiver hook).

The dangerous instance is `_withdraw`, because it executes inside `onAccept`, which is invoked by the ISMP host when a **relayer** submits a batched settlement message (`HandlerV2.handlePostRequests`/`batchCall`) — an unprivileged, permissionless action. A solver who fills an order with a beneficiary set to their own EIP-7702-delegated EOA can, at settlement time, consume the relayer-funded gas budget for expensive computation, subsidizing otherwise-unprofitable on-chain actions at the relayer's expense — the same "siphon gas" attack vector 1 in the report. If `_withdraw`/settlement is reached as part of a larger batched relay transaction (multiple ISMP messages processed together via `batchCall`/`handlePostRequests`), a griefer can also burn enough gas to push a subsequent, unrelated message in the same batch into an out-of-gas failure, an analogue of attack vector 2 (misattributed OOG failures) — though this repo could not be fully confirmed to atomically abort the whole batch on a single message's OOG revert versus isolating failures per-message with the tool budget available; this specific batch-atomicity detail is unverified.

### Impact Explanation
An EIP-7702-delegated solver/beneficiary can force the relayer (an unprivileged, permissionless actor who is nonetheless paying real gas to deliver value on others' behalf) to fund unbounded computation during escrow release, and can potentially cause denial-of-service to co-batched settlement messages. This is a concrete gas-theft/DoS vector against the Intent Gateway's native-token settlement, reachable purely by placing/filling an intent order and setting one's own beneficiary to a 7702-delegated address — no privileged role required. Because native-token amounts released via `_withdraw`/`_fillSameChain`/`_fillCrossChain` are real escrowed user funds, a stalled or reverted settlement transaction can also delay or endanger delivery of that value.

### Likelihood Explanation
Medium-High: EIP-7702 is live on mainnet Ethereum, and nothing in `IntentGatewayV2`/`IntentsBase`/`ExtrinsicIntents`/`IntrinsicIntents` restricts `beneficiary` to being a non-code address or caps forwarded gas on the native-token leg. Any user or solver can set `order.output.beneficiary` (fill-time) or the `WithdrawalRequest.beneficiary` (embedded in the cross-chain message body they construct) to a self-controlled EIP‑7702 EOA, requiring no coordination with other actors.

### Recommendation
Cap the gas forwarded on every native-token payout to an externally-supplied `beneficiary`/`solver` address (e.g., `beneficiary.call{value: amount, gas: SAFE_GAS_CAP}("")`), consistent across `IntentsBase._withdraw`, `IntrinsicIntents._fillSameChain`, `ExtrinsicIntents._fillCrossChain`, and the Tron `IntentGatewayV2.withdraw`/fill paths, and treat any failure from insufficient forwarded gas as a distinguishable event so it cannot be misattributed to unrelated batched messages.

### Proof of Concept
1. Attacker deploys a contract whose fallback performs expensive storage writes and then returns normally (no revert), and delegates their EOA to it via an EIP-7702 authorization.
2. Attacker places a same-chain order (or bids as solver on a cross-chain order) with `order.output.beneficiary`/`WithdrawalRequest.beneficiary` set to their own delegated EOA.
3. On fill (`IntrinsicIntents._fillSameChain`) or on relayer-driven settlement (`IntentsBase._withdraw` via `onAccept`), the contract executes `beneficiary.call{value: amount}("")` / `_sendValue(beneficiary, amount)` with no gas cap.
4. The attacker's delegated fallback consumes the vast majority of remaining gas performing storage writes it would otherwise be unable to afford, subsidized by the solver's own tx (same-chain) or, more critically, by the relayer's tx (cross-chain settlement) — demonstrating gas-cost siphoning; if this settlement call is part of a larger batched relay transaction, the exhausted gas can also push later leaves in the same batch to revert with out-of-gas.
