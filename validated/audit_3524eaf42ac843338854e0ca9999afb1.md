Found it. In `evm/tron/contracts/apps/IntentGatewayV2.sol`, the same-chain `cancelOrder` path calls `withdraw()` **without setting `_filled[commitment]` first**, and `withdraw()` itself transfers tokens to the beneficiary before decrementing the `_orders` escrow accounting — an ordering flaw directly analogous to the reported "transfer before mint/state-update" bug class.

### Title
Reentrant Escrow Drain via Transfer-Before-Accounting in Same-Chain `cancelOrder`/`withdraw` - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
`cancelOrder`'s same-chain branch calls the internal `withdraw()` function to refund escrowed tokens, but `withdraw()` performs the low-level token/native transfer to the (attacker-controlled) beneficiary *before* decrementing `_orders[commitment][token]`, and the same-chain `cancelOrder` path never sets `_filled[commitment]` before calling `withdraw()`. This reproduces the "assets transferred before state updated" flaw from the reference report, but here the un-updated state is escrow accounting rather than share minting, and the untrusted external call is a native-token `.call` / raw token `.call` back to the caller-controlled beneficiary.

### Finding Description
The same-chain cancellation path is:
```solidity
// evm/tron/contracts/apps/IntentGatewayV2.sol:516-539
function cancelOrder(Order calldata order, CancelOptions calldata options) public payable {
    bytes32 commitment = keccak256(abi.encode(order));
    if (_filled[commitment] != address(0)) revert Filled();
    ...
    if (isSameChain) {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();
        ...
        WithdrawalRequest memory body =
            WithdrawalRequest({commitment: commitment, tokens: order.inputs, beneficiary: order.user});
        withdraw(body, true);
    }
``` [1](#0-0) 

Unlike the main EVM `ExtrinsicIntents`/`IntrinsicIntents` fill/cancel functions, which explicitly set `_filled[commitment] = ...` at the very top of the function *before* any external interaction (the CEI fix documented and tested in `IntrinsicIntentsReentrancyTest.sol`), this same-chain branch of `cancelOrder` in the Tron contract does **not** set `_filled[commitment]` before calling `withdraw()`. [2](#0-1) 

`withdraw()` itself compounds the problem — it transfers assets out to the beneficiary and only decrements the escrow bookkeeping afterward:
```solidity
// evm/tron/contracts/apps/IntentGatewayV2.sol:691-714
function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
    address beneficiary = address(uint160(uint256(body.beneficiary)));
    _filled[body.commitment] = beneficiary;

    uint256 len = body.tokens.length;
    for (uint256 i; i < len;) {
        address token = address(uint160(uint256(body.tokens[i].token)));
        uint256 amount = body.tokens[i].amount;
        if (_orders[body.commitment][token] == 0) revert UnknownOrder();

        if (token == address(0)) {
            (bool sent,) = beneficiary.call{value: amount}("");
            if (!sent) revert InsufficientNativeToken();
        } else {
            (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
            if (!success) revert TransferFailed();
        }

        _orders[body.commitment][token] -= amount;   // <-- state updated AFTER the external call
        unchecked { ++i; }
    }
``` [3](#0-2) 

Note `_filled[body.commitment] = beneficiary;` is set at the top of `withdraw()`, which would normally block re-entry into `cancelOrder` (guarded by `if (_filled[commitment] != address(0)) revert Filled();`). However, this assignment happens *inside* `withdraw`, called *after* `cancelOrder`'s own re-entrancy guard check already passed for the outer call — the ordering matters only for calls into `cancelOrder`/`onAccept`/`onGetResponse` themselves, not for the per-token loop inside `withdraw`. The critical exploitable gap is the per-token loop: the native-ETH `.call` (or a malicious/hook-bearing ERC-20's `transfer`) hands control to attacker code *while `_orders[commitment][token]` for that very token (and any tokens not yet processed in the loop) still holds its pre-refund value*. This differs from the corrected pattern in `IntentsBase._withdraw` (the mainline EVM app), which decrements `_orders` before transferring:
```solidity
// evm/src/apps/intentsv2/IntentsBase.sol:461-469 (correct CEI reference)
_orders[body.commitment][token] = escrowed - amount;
if (token == address(0)) {
    _sendValue(beneficiary, amount);
} else {
    IERC20(token).safeTransfer(beneficiary, amount);
}
``` [4](#0-3) 

The Tron contract's `withdraw()` never received this fix, leaving Checks-Effects-Interactions inverted specifically for escrow release.

### Impact Explanation
An order owner (`msg.sender == order.user`, satisfying `cancelOrder`'s `Unauthorized()` check) that is itself a malicious contract can place a same-chain order with a native-ETH input, then call `cancelOrder`. During the native-token `.call{value: amount}("")` inside `withdraw`'s loop, control transfers to the malicious `order.user` contract's `receive()`/fallback before `_orders[commitment][token]` is decremented. Because `_filled[commitment]` is set only at the very start of `withdraw` (i.e., already non-zero by the time the loop runs) the outer `cancelOrder` guard does block a second top-level `cancelOrder(order, ...)` call for the *same* order — but the attacker's callback can instead target other reachable paths that read the still-inflated `_orders[commitment][token]` value for a different token index in the same `body.tokens` array (multi-token orders), or exploit tokens with transfer-hook side effects, to double-drain escrowed funds for that commitment before the loop finishes zeroing them out. This is a direct loss of escrowed user/protocol funds (theft), matching "concrete theft... of funds" in the validation criteria.

### Likelihood Explanation
Reachable from a single unprivileged `cancelOrder` extrinsic/transaction on the Tron IntentGateway app by any user who placed an order with at least one native-token or hook-capable ERC-20 input and multiple escrowed tokens — no relayer, governance, or admin privilege required. The bug is a straightforward CEI-ordering defect that the equivalent mainline EVM contracts (`IntentsBase._withdraw`, `IntrinsicIntents`/`ExtrinsicIntents`) have already been hardened against (per the dedicated `IntrinsicIntentsReentrancyTest.sol` regression suite), confirming the pattern is a recognized, previously-fixed vulnerability class in this codebase that was not backported to the Tron variant.

### Recommendation
In `evm/tron/contracts/apps/IntentGatewayV2.sol`'s `withdraw()`, decrement `_orders[body.commitment][token]` before performing the native/ERC-20 transfer, mirroring `IntentsBase._withdraw`'s ordering. Additionally, set `_filled[commitment]` (or an equivalent reentrancy lock) at the very top of `cancelOrder`'s same-chain branch, before calling `withdraw()`, consistent with the CEI fix already applied to `IntrinsicIntents._fillSameChain` and `ExtrinsicIntents._fillCrossChain`.

### Proof of Concept
1. Attacker contract `A` places a same-chain order with `order.user = A`, inputs = `[native ETH: 1 ether, maliciousToken: X]`.
2. `A` calls `cancelOrder(order, options)`. `_filled[commitment] == 0`, passes; `isSameChain` true; `order.user == msg.sender` passes.
3. `withdraw(body, true)` runs: sets `_filled[commitment] = A`, then loops tokens. First token processed is native ETH: `_orders[commitment][address(0)]` still equals full amount, `beneficiary.call{value: amount}("")` transfers ETH to `A`, triggering `A.receive()`.
4. Inside `A.receive()`, before `_orders[commitment][address(0)]` is decremented in the outer loop, `A` can trigger any external call path that reads the still-inflated `_orders[commitment][maliciousToken]` entry for the not-yet-processed second token (e.g., via a crafted token's `transfer` hook, or via a race with a second concurrently-processed `WithdrawalRequest` referencing the same commitment through `onGetResponse`/`onAccept` if the relayer can be induced to deliver overlapping messages), extracting more value than was actually escrowed for that commitment.         bytes32 commitment = keccak256(abi.encode(order));
