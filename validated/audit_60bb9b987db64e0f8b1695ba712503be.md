## Analog Found

### Title
`BandwidthManager.purchase()` reverts for fee tokens with more than 18 decimals due to unchecked `18 - dec` underflow - (File: `evm/src/apps/BandwidthManager.sol`)

### Summary
`BandwidthManager.purchase()` computes a decimal-scaling factor as `10 ** (18 - dec)` where `dec = IERC20Metadata(feeToken).decimals()`. If the configured fee token has more than 18 decimals, `18 - dec` underflows a `uint8`/`uint256` subtraction and reverts under Solidity ≥0.8's built-in overflow checks, permanently bricking every call to `purchase()` — identical in root cause to the DODOv3 `parseAllPrice` bug (`18 - tokenDecimal` reverting for tokens with >18 decimals, e.g. NEAR's 24 decimals).

### Finding Description
`purchase()` is reachable by any unprivileged caller and unconditionally performs: [1](#0-0) 

`feeToken` is read from `IDispatcher(_host).feeToken()`, the protocol-wide fee token also used for relayer fees elsewhere: [2](#0-1) 

The project's own documentation acknowledges this exact limitation, mirroring the sponsor's response in the DODOv3 report that decimals-over-18 tokens will simply not be supported: [3](#0-2) 

Since `feeToken` is a single, protocol-wide configuration value (not validated for `decimals() <= 18` anywhere in `BandwidthManager.sol`), if it is ever set to a token with decimals greater than 18 (e.g. a token like NEAR at 24 decimals used as the network's canonical fee token), the subtraction `18 - dec` underflows and every subsequent call to `purchase()` reverts — a complete, permanent denial of the bandwidth-purchase route for every unprivileged buyer, until the fee token is reconfigured to a ≤18-decimal token.

### Impact Explanation
This is a route-availability bug: once triggered, `BandwidthManager.purchase()` becomes permanently unusable for all callers (every transaction reverts deterministically), which matches the "route unable to deliver messages" impact class — apps relying on bandwidth top-ups can no longer purchase bandwidth credits at all, with no on-chain remediation short of a fee-token migration. This is a Medium-severity availability/compatibility issue rather than a fund-theft bug, consistent with the judged severity of the original DODOv3 report.

### Likelihood Explanation
Likelihood is contingent on the host's configured fee token having more than 18 decimals — a configuration state controlled by protocol/host setup, not by an attacker. However, as the original report established, standard ERC20 tokens with >18 decimals do exist in production (e.g., NEAR at 24 decimals), so this is a real compatibility gap rather than a purely theoretical one, and the affected code path (`purchase()`) is triggered by ordinary unprivileged users, not by any privileged actor.

### Recommendation
Do not assume `dec <= 18`. Either:
- Validate at fee-token configuration time (e.g., in the host's fee-token setter or in `BandwidthManager`) that the token's `decimals()` is `<= 18`, rejecting configuration otherwise, or
- Generalize the scaling logic to handle `dec > 18` symmetrically (scale up 18-decimal tier prices when `dec < 18`, scale down when `dec > 18`), e.g. by computing the amount as `total18d * 10**dec / 10**18` using higher precision arithmetic instead of `10 ** (18 - dec)`.

### Proof of Concept
1. Host is configured (via `IDispatcher(_host).feeToken()`) to use a fee token with `decimals() == 24` (e.g., a NEAR-like token).
2. Any user calls `BandwidthManager.purchase(app, tier, months, chain)` with a valid, configured `tier`.
3. Inside `purchase()`, `uint8 dec = 24; uint256 scale = 10 ** (18 - dec);` — `18 - 24` underflows in `uint256` arithmetic (Solidity ≥0.8 checked math), reverting the transaction.
4. Every future call to `purchase()` reverts identically, permanently disabling bandwidth purchases for that host deployment until the fee token is changed. [4](#0-3)

```text
    function purchase(bytes calldata app, uint256 tier, uint256 months, bytes calldata chain)
        external
        returns (bytes32 commitment)
    {
        if (app.length == 0 || app.length > MAX_APP_LENGTH || chain.length == 0 || months == 0) {
            revert InvalidPurchase();
        }
        uint256 price18d = tierPrice[tier];
        if (price18d == 0) revert UnknownTier();

        uint256 total18d = price18d * months;
        address feeToken = IDispatcher(_host).feeToken();
        uint8 dec = IERC20Metadata(feeToken).decimals();
        uint256 scale = 10 ** (18 - dec);
        if (total18d % scale != 0) revert PriceNotRepresentable();
        uint256 amount = total18d / scale;

        IERC20(feeToken).safeTransferFrom(msg.sender, address(this), amount);
```
