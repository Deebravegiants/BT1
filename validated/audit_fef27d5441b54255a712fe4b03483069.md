### Title
Silent-failure ERC20 transfers in Tron `IntentGatewayV2.withdraw()` and `SweepDust` handler cause permanent freezing of escrowed order funds - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron deployment of `IntentGatewayV2` uses raw low-level `.call()` with the `IERC20.transfer.selector` and only checks that the *call did not revert* (`success`), never decoding/validating the returned boolean. This is the exact bug class flagged in the reference report ("`transfer()`/`transferFrom()` should not be used when interacting with arbitrary ERC20 tokens" — should use OpenZeppelin's `safeTransfer`/`safeTransferFrom`), except here it is worse because even the raw ABI-encoded return value is never inspected.

### Finding Description
In `withdraw()`, which is invoked from `onAccept()` for `RequestKind.RedeemEscrow` / `RequestKind.RefundEscrow` messages, escrowed tokens are paid out via: [1](#0-0) 

Specifically, token payouts and fee payouts are performed with:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
``` [2](#0-1) [3](#0-2) 

The `success` boolean from a low-level `.call()` only indicates whether the callee reverted — it does not reflect the boolean return value that a compliant ERC20 `transfer()` is expected to return. Any ERC20-like token (a category common on Tron, e.g. legacy/non-standard TRC20 tokens) that returns `false` on a failed transfer instead of reverting will make this call return `success == true` even though no tokens moved. Because the check does not decode `returndata` and compare against `abi.decode(data, (bool))`, the contract proceeds as if the payout succeeded.

Immediately after this "successful" transfer, the function unconditionally marks the order as settled:
```solidity
_filled[body.commitment] = beneficiary;   // set at function entry
...
_orders[body.commitment][token] -= amount; // escrow accounting decremented
``` [4](#0-3) 

Since `_filled[body.commitment]` is set and the escrow balance is deducted regardless of whether the beneficiary actually received tokens, there is no path to retry or reclaim the funds — they remain locked in the `IntentGatewayV2` contract forever while the protocol's bookkeeping shows the order as filled/refunded.

The identical unchecked-success pattern is also used in the `SweepDust` handler:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, req.beneficiary, amount));
if (!success) revert TransferFailed();
``` [5](#0-4) 

By contrast, the deposit-side transfers in the same file correctly use OpenZeppelin's `SafeERC20.safeTransferFrom`, which validates the return data: [6](#0-5) [7](#0-6) 

showing the pattern is inconsistent within the contract: inbound transfers are hardened, outbound payouts (the withdraw/settlement path that resolves escrow accounting) are not.

### Impact Explanation
This is a reachable fund-freezing bug for any order settled through this Tron `IntentGatewayV2` where the input/output token is an ERC20 implementation that signals transfer failure via a `false` return rather than a revert (a well-documented weird-ERC20 class, and a real concern on Tron where TRC20 tokens frequently deviate from strict EVM ERC20 semantics). Once `withdraw()` is invoked (triggered by a legitimately delivered `RedeemEscrow`/`RefundEscrow` ISMP message — reachable by any relayer completing the normal intent-fill/refund flow, not requiring any privileged role), the escrow accounting is finalized and the order marked filled even if the token transfer silently failed. The escrowed tokens remain stranded in the contract with no recovery mechanism, constituting a permanent loss of user/solver funds. The same applies to the `SweepDust` payout path.

### Likelihood Explanation
Likelihood is proportional to how many order input/output tokens configured for this Tron gateway are non-standard ERC20s that return `false` rather than reverting on failure (e.g., insufficient balance/allowance edge cases, blacklisted addresses in some stablecoin implementations, or paused-token states). Given the file is explicitly built for Tron — a network known for widespread ERC20-token nonconformance — the exposure is realistic rather than purely theoretical, and requires no attacker privilege: it is triggered by the normal order-settlement flow whenever the destination token misbehaves.

### Recommendation
Replace all raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` payout patterns in `withdraw()` and the `SweepDust` handler with OpenZeppelin's `SafeERC20.safeTransfer()` (the contract already imports and uses `SafeERC20` for the deposit side), so that both call failure and a `false` return value revert the transaction, preventing escrow state from being finalized without the beneficiary actually receiving funds.

### Proof of Concept
1. Configure (or have the protocol configure) an order whose input/output token is a non-standard ERC20 deployed on Tron that returns `false` instead of reverting when a `transfer()` fails (e.g., due to blacklist/pause logic, common among Tron-based stablecoin forks).
2. A solver fills the order; hyperbridge relays a `RedeemEscrow` request to the Tron `IntentGatewayV2`, invoking `onAccept` → `withdraw()`.
3. Have the token's `transfer()` return `false` for this call (e.g., beneficiary transiently blacklisted, or contract paused) without reverting.
4. `token.call(...)` returns `success == true` (the call didn't revert), so `if (!success) revert TransferFailed();` does not trigger.
5. `_filled[body.commitment]` is already set and `_orders[body.commitment][token] -= amount` executes, marking the order as fully settled even though the beneficiary received nothing.
6. The escrowed tokens remain permanently locked in the `IntentGatewayV2` contract with no code path to reclaim them, since the commitment is now marked filled and the escrow balance zeroed out.
