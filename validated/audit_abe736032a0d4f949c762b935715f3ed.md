### Title
JWT replay-protection check-then-act race in `WorkflowMetadataHandler.Authorize` allows duplicate authorization of a single-use signed workflow-trigger request - (File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go)

### Summary
`WorkflowMetadataHandler.Authorize` is the unprivileged, internet-facing authorization gate for the HTTP trigger capability of the gateway: it verifies a user-supplied signed JWT bound to a specific JSON-RPC request digest, checks the JWT's `jti` against a replay cache, and only *afterwards* records the `jti` as used. The "check" (`isReplay`) and the "commit" (`recordUsage`) are two separate, independently-locked operations with no atomicity across the whole `Authorize` call, so two requests racing on the same signed JWT can both pass the replay check before either commits, defeating the intended one-time-use guarantee — the same failure pattern as the front-running finding in the reference report, where a privileged/serializing check and the state-changing action it gates are separated in time and can be won by a racing party.

### Finding Description
`Authorize` is called from `httpTriggerHandler.authorizeRequest` for every unprivileged, internet-facing HTTP-trigger request received by the gateway [1](#0-0) .

Inside `Authorize`, the JWT is verified against the request digest, and then the replay cache is consulted and updated in two disjoint critical sections: [2](#0-1) 

The replay cache implementation confirms the check and the write are guarded by separate lock acquisitions rather than one atomic "check-and-set": [3](#0-2) 

`isReplay` takes an `RLock`, reads, and releases the lock; only later, after the signer/authorized-key lookup succeeds, does `recordUsage` take a separate `Lock` to mark the `jti` used. Between those two operations there is no lock held across `Authorize`'s whole body, so if two goroutines invoke `Authorize` concurrently with the exact same JWT (same `jti`, same request digest — e.g. the client retries the same POST, or a malicious intermediary/duplicate the HTTP request), both can execute `isReplay` and observe "not yet used" before either calls `recordUsage`. Both would then be treated as validly authorized for that request/JWT, even though the JWT (and the accompanying `CreateRequestJWT` documentation) explicitly states the `jti` exists "for replay protection" and is meant to make the signed authorization single-use [4](#0-3) .

This is structurally the same bug class as the reported `setAmicableResolution` issue: a value is read to make an authorization/serialization decision, and the corresponding "commit" that would prevent a second actor from also succeeding happens later, so a second concurrent execution path can slip through the gap and act on stale state.

### Impact Explanation
Successful exploitation lets an unprivileged client (or an intermediary capable of duplicating a single request) get a single client-signed, single-use trigger authorization treated as valid twice concurrently, defeating the intended replay/idempotency guarantee of the JWT-based authorization path exposed to external, unprivileged callers of the gateway. Downstream, `HandleUserTriggerRequest` does have a second, independent dedup keyed by `req.ID` in `setupCallback` (guarded by `callbacksMu`) which in the common case (identical `req.ID` for both racing requests) prevents true double execution of a workflow run [5](#0-4) . I could not conclusively determine from the indexed code whether any code path allows two *different* `req.ID`s to be authorized by the same JWT (the JWT digest binds to the full request via `req.Digest()`, which is expected to include the ID, but the exact `Digest()` implementation used for `jsonrpc.Request` was not available in the index to confirm whether ID is included). If `Digest()` does not strongly bind the `jti` to a single immutable `req.ID`, this race could enable two distinct callback registrations (and thus two real workflow executions) from one signed authorization. Given this residual uncertainty, the concrete, provable impact of the authorization-layer race itself is: (1) violation of the single-use JWT invariant at the authorization layer, and (2) a real (if narrower) race window where the "already been used" replay defense — the component explicitly designed to prevent duplicate authorization of a signed request — can be bypassed by concurrent requests, which is a genuine authentication/replay-control bypass even if a downstream defense-in-depth control (`callbacks` map) currently limits full double-execution impact.

### Likelihood Explanation
Likelihood is moderate: it requires two requests bearing the identical signed JWT to be processed by the gateway concurrently, which is achievable by any unprivileged client simply firing the same POST twice in parallel (a trivial, self-inflicted or attacker-triggered race, no special privileges needed), and the `jwtReplayCache.isReplay`/`recordUsage` gap is unconditionally present on every call to `Authorize` — there is no serialization mutex spanning the check and the commit.

### Recommendation
Make the replay check-and-record atomic: hold a single lock (or use an atomic "insert-if-absent" map operation, e.g. `LoadOrStore` semantics) that performs the existence check and the recording of `jti` in one critical section, rejecting the request if another goroutine already reserved that `jti`. For example, refactor `jwtReplayCache` to expose a single `ClaimIfUnused(jti string) bool` method that acquires the write lock once, checks for existence, and if absent inserts it, returning false if it was already present — and have `Authorize` call this once instead of the separate `isReplay` + `recordUsage` calls, ideally reserving the `jti` before performing the (comparatively expensive) authorized-key lookup so a losing racer fails fast.

### Proof of Concept
1. Client signs one `JWTClaims` (with digest bound to a specific `jsonrpc.Request`) via `CreateRequestJWT`, producing a single JWT with one `jti`.
2. Client sends two HTTP requests to the gateway carrying the identical signed JWT and identical JSON-RPC request body concurrently (e.g., via two goroutines/parallel curl invocations hitting the same gateway endpoint at the same instant).
3. Both requests are routed to `httpTriggerHandler.authorizeRequest` → `WorkflowMetadataHandler.Authorize` concurrently.
4. Both goroutines execute `h.jwtCache.isReplay(claims.ID)` before either has called `h.jwtCache.recordUsage(claims.ID)`, so both observe `exists == false` and proceed past the replay check [6](#0-5) .
5. Both calls succeed in the authorized-key lookup and both call `recordUsage`, i.e., both callers receive `key, nil` from `Authorize` — demonstrating that the single-use JWT was accepted twice, contrary to the "JWT token has already been used" invariant the code otherwise enforces for sequential replays (as shown by the passing sequential-replay test) [7](#0-6) .

func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
}

func (cache *jwtReplayCache) isReplay(jti string) bool {
	cache.mu.RLock()
	defer cache.mu.RUnlock()

	_, exists := cache.cache[jti]
	return exists
}

func (cache *jwtReplayCache) recordUsage(jti string) {
	cache.mu.Lock()
	defer cache.mu.Unlock()

	cache.cache[jti] = time.Now()
}
