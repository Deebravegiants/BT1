## Title
Webhook `shop-domain` (and `topic`/`webhook-id`) headers are trusted without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the shop identity (`shopify-shop-domain`/`x-shopify-shop-domain` header) and other metadata (`topic`, `webhook-id`) are read directly from unauthenticated HTTP headers and handed to the app's webhook handler as trusted tenant identity. This breaks the binding `HMAC(secret, signed_bytes) == HMAC(secret, bytes_the_app_acts_on)` because the "bytes acted on" (the shop) are not part of `signed_bytes`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `shop`, `topic`, and `webhook_id` are pulled straight from request headers with no cryptographic binding to the signature: [2](#0-1) 

`Registry.process` validates only the body HMAC, then forwards the header-derived `shop` value unchanged into `WebhookMetadata`, which the host application uses to attribute the payload to a tenant: [3](#0-2) 

This is structurally identical to the reported bug class: the value that is checked (`earned`, computed from `totalSupplyInValue`) is not the value that is actually compared/transferred against real balance (`bal`, in different units) — here, the value that is *cryptographically verified* (the raw body) is not the value that is *acted upon as the identity key* (`shop-domain` header). Because the app's `client_secret` is shared across every shop that installs the same app, any shop that legitimately receives one authentic webhook (with a valid HMAC over some body) can replay that exact body+HMAC pair to the app's webhook endpoint while substituting the `shop-domain` header for a victim shop. `Utils::HmacValidator.validate` will still pass because it only checks the body bytes: [4](#0-3) 

### Impact Explanation
If the host application uses `WebhookMetadata#shop` (as documented/intended usage of this gem) to key data storage, trigger actions, or invalidate/refresh state for a specific merchant, an attacker who controls one legitimate shop installation of the app can forge webhook events attributed to any other shop using that same app, causing cross-tenant data corruption or unauthorized actions under the victim shop's identity. Cross-tenant access is listed as a Critical-impact category.

### Likelihood Explanation
Requires the attacker to operate one legitimate shop with the target app installed (achievable by any merchant) in order to obtain one valid `(raw_body, hmac)` pair — no `api_secret_key`, access token, or privileged account access is needed. The header substitution itself is trivial (a normal unauthenticated HTTP POST to the app's webhook endpoint with attacker-controlled headers).

### Recommendation
Bind the tenant/topic identity into the signed material, or otherwise cryptographically verify it: e.g., after HMAC validation, cross-check the header-derived `shop` against a known, previously-established shop/session record before trusting it, or require the host app to correlate `shop` with the specific webhook subscription/session rather than trusting the raw header value implicitly. At minimum, document that `shop`, `topic`, and `webhook_id` in `WebhookMetadata` are unauthenticated header values and must not be used as the sole tenant key without an independent verification step (e.g., matching against a session store keyed by an already-verified shop).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a real event (e.g. an order update) so Shopify sends a legitimate webhook: raw body `B` and header `shopify-hmac-sha256: HMAC(client_secret, B)`.
2. Attacker captures `B` and the HMAC value.
3. Attacker POSTs to the app's webhook endpoint with the same `B` and same HMAC header, but sets `shopify-shop-domain: victim-shop.myshopify.com` (and optionally any `shopify-topic`/`shopify-webhook-id`).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only hashes `@raw_body` and succeeds. `WebhookMetadata.shop` is set to `victim-shop.myshopify.com`, and the handler processes attacker-controlled data as if it originated from the victim shop.
