Audit Report

## Title
NULL Pointer Dereference via Unchecked `req.Params` in Vault `handlePublicKeyGet` - (File: core/capabilities/vault/gw_handler.go)

## Summary
`HandleGatewayMessage` routes `vaulttypes.MethodPublicKeyGet` requests directly to `handlePublicKeyGet` without going through `GatewayVaultRequestProcessor.ProcessRequest`, which is the only place in this handler that performs a `req.Params == nil` check before the params are used. `handlePublicKeyGet` unconditionally dereferences `*req.Params` in `json.Unmarshal(*req.Params, r)`, so a JSON-RPC request for this method with `params` omitted causes a nil-pointer dereference panic.

## Finding Description
In `HandleGatewayMessage` [1](#0-0) , requests for `MethodSecretsCreate`/`MethodSecretsUpdate`/`MethodSecretsDelete`/`MethodSecretsList` are first passed to `h.requestProcessor.ProcessRequest`, whose per-method handlers explicitly check `if req.Params == nil` before use, e.g. `processCreateSecretsRequest`/`processUpdateSecretsRequest`/`processDeleteSecretsRequest` in `gateway_vault_request_processor.go`. By contrast, `MethodPublicKeyGet` is dispatched straight to `h.handlePublicKeyGet(ctx, gatewayID, req)` with no prior validation [2](#0-1) .

`handlePublicKeyGet` then dereferences `req.Params` without any nil check: [3](#0-2) 

This is confirmed by direct comparison with the other four handler functions in the same file (`handleSecretsCreate`, `handleSecretsUpdate`, `handleSecretsDelete`, `handleSecretsList`) — although those also call `json.Unmarshal(*req.Params, ...)` without a local nil check, they are only reached *after* `ProcessRequest` has already validated `req.Params != nil` for their respective methods, as the dispatch logic shows: response is only computed by these secondary handlers if `response == nil` after the first switch, meaning the request already passed through the processor's authorization/validation pipeline [4](#0-3) . `handlePublicKeyGet` has no equivalent gate, and also performs no authorization check at all in this path.

The test suite (`gw_handler_test.go`) exercises nil/invalid params handling only for `MethodSecretsCreate` and `MethodSecretsDelete` (via the validated pipeline) and does not cover `MethodPublicKeyGet` with nil params, so this gap is not caught by existing tests.

## Impact Explanation
A JSON-RPC request is valid without a `params` field per spec, so an unprivileged actor able to reach the gateway connector's message dispatch for the Vault handler (any peer able to address a message to `vaulttypes.Methods`, which includes `MethodPublicKeyGet`) can trigger `*req.Params` on a `nil` `*json.RawMessage`, causing a panic in the goroutine/call path executing `HandleGatewayMessage`. Depending on whether an upstream caller in the connector recovers panics (not confirmed as present in `core/services/gateway/connector/connector.go` based on available search), this can crash the request-handling goroutine or destabilize the node process — a denial-of-service condition. This falls into the "unauthorized/no-auth-required disruption of node capability service" impact class, consistent with an in-scope DoS finding since it requires no credentials, prior session, or elevated privilege and bypasses all authorization logic in this handler.

## Likelihood Explanation
High. Triggering the panic requires only sending a syntactically valid JSON-RPC request with method `MethodPublicKeyGet` and no `params` field through the gateway connector — no key material, session, or elevated role needed. This makes it trivially and repeatably exploitable by any gateway-reachable actor.

## Recommendation
Add an explicit `if req.Params == nil` check at the start of `handlePublicKeyGet`, mirroring `processCreateSecretsRequest`/`processUpdateSecretsRequest`/`processDeleteSecretsRequest`, returning an `api.UserMessageParseError` (or a dedicated `InvalidVaultParamsError`) response instead of dereferencing the nil pointer. Additionally, audit whether the gateway connector's message-processing loop recovers from panics in `GatewayConnectorHandler.HandleGatewayMessage` implementations generally, as a defense-in-depth measure against similar bugs in this or other capability handlers.

## Proof of Concept
1. Start a node with the Vault capability's `GatewayHandler` registered.
2. Via the gateway connector, send:
```json
{"jsonrpc":"2.0","id":"1","method":"<vaulttypes.MethodPublicKeyGet value>"}
```
(omitting `params` entirely).
3. `HandleGatewayMessage` routes this to `handlePublicKeyGet` (core/capabilities/vault/gw_handler.go:207-208), which executes `json.Unmarshal(*req.Params, r)` at line 366 with `req.Params == nil`, causing a nil-pointer dereference panic.
4. As a Go unit test: construct a `*jsonrpc.Request[json.RawMessage]{Method: vaulttypes.MethodPublicKeyGet, ID: "1", Params: nil}` and call `handler.HandleGatewayMessage(ctx, "gateway-1", req)` directly (as done for other methods in `gw_handler_test.go`); observe the panic instead of a structured error response.
