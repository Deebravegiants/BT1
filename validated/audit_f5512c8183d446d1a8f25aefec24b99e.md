Audit Report

## Title
CORS Origin Allowlist Bypass via Unanchored Suffix Match - (File: core/services/gateway/network/httpserver.go)

## Summary
The gateway's wildcard CORS origin check in `isAllowedOrigin` uses `strings.HasSuffix(originHost, allowedHost)` without requiring a `.` boundary before the match, so a lookalike domain that merely ends with the same characters as an allowed suffix (e.g., `evilethereum.org` against allowed `*.ethereum.org`) is incorrectly treated as a valid subdomain. This lets an attacker-controlled origin pass the allowlist check and receive a reflected `Access-Control-Allow-Origin` header from the gateway.

## Finding Description
In `isAllowedOrigin`, when a configured entry starts with `*.`, the code strips the prefix and does a bare `strings.HasSuffix` comparison against the origin host: [1](#0-0) 
This has no check for a preceding `.` character, so `strings.HasSuffix("evilethereum.org", "ethereum.org")` returns `true` even though `evilethereum.org` is not a subdomain of `ethereum.org`. The value is fully attacker-controlled via the `Origin` request header and is reflected verbatim into the response in `handleRequest`: [2](#0-1) 
No other validation (auth middleware, role checks, or additional sanitization) intervenes before this reflection — CORS is the only gate here, and it is broken by the missing boundary check.

## Impact Explanation
This is a genuine allowlist-bypass bug: an attacker who registers/controls a domain ending with the configured wildcard suffix (no dot required, e.g. `evilethereum.org`, `notethereum.org`) can cause the gateway to respond with `Access-Control-Allow-Origin` reflecting that attacker-controlled origin, along with permissive `Access-Control-Allow-Methods`/`Access-Control-Allow-Headers`. This maps to the in-scope "allowlist bypass" impact category for the gateway's CORS protection, since it directly undermines the operator's explicit origin restriction and could allow an in-browser script hosted on the lookalike domain to make authenticated cross-origin requests to the gateway and read JSON-RPC responses.

## Likelihood Explanation
Exploitation requires only registering a domain string ending in the configured suffix and sending a request with a spoofed `Origin` header — this is fully within reach of an unprivileged client and requires no credentials, node access, or operator privileges. It is deterministic and repeatable given a matching wildcard CORS configuration.

## Recommendation
Require a `.` boundary before the suffix match, e.g. check `strings.HasSuffix(originHost, "."+allowedHost)` (in addition to the already-handled exact match case), so only genuine subdomains like `foo.ethereum.org` match and lookalikes like `evilethereum.org` are rejected.

## Proof of Concept
1. Start the gateway HTTP server with `CORSEnabled: true` and `CORSAllowedOrigins: []string{"https://*.ethereum.org"}` (as done in `startNewServer` in `core/services/gateway/network/httpserver_test.go`).
2. Send a POST request to the gateway path with header `Origin: https://evilethereum.org`.
3. Observe the response includes `Access-Control-Allow-Origin: https://evilethereum.org`, `Access-Control-Allow-Methods: GET, POST, OPTIONS`, and `Access-Control-Allow-Headers: Content-Type`, confirming the bypass — this can be added as a new test case alongside the existing `TestHTTPServer_HandleRequest_CORSEnabled_FromNotAllowedOriginWildcards` test, asserting `resp.Header.Get("Access-Control-Allow-Origin")` is non-empty for the `evilethereum.org` origin against the `*.ethereum.org` wildcard.
