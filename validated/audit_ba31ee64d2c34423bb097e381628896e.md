### Title
Missing Snapshot-Consistency Checks in Phantom Order Price Aggregation Allows Liquidity-Manipulation Front-Running of the Published FX Rate - (File: `sdk/packages/sdk/src/protocols/intents/phantom-aggregation.ts`)

### Summary
`aggregatePhantomBids` weights and selects a phantom order's published FX rate by reading each bidding solver's **live** on-chain balance and Uniswap V4 position state at the moment the bid window closes, with no check that this state matches anything the solver committed to when it placed its bid, and no tick/liquidity range validation of any kind. Because the window-close block (`created_at_block + window`) is fully deterministic and known in advance from on-chain configuration, an attacker can flash-manipulate a Uniswap V4 position's liquidity/tick just before that block to inflate `positionAmountOfToken`, win the `weightedMedian` selection, and have that manipulated quote become the verbatim published exchange rate — directly analogous to the reported `_decodeAndReward(currentOnly=true)` bug where a reward/price computation trusts the current tick/liquidity without validating it against an expected, pre-committed value.

### Finding Description
`runAggregation` (`sdk/packages/sdk/src/protocols/intents/phantom-aggregation.ts:1286-1566`) computes, per solver bid, a "weight" used to filter and to feed `weightedMedian`: [1](#0-0) 

The weight is built from `readPosition`/`positionAmountOfToken`, which reads a Uniswap V4 `PositionManager`/`StateView` **at the time the aggregation runs** — a live `eth_call`, not a value pinned to, or cross-checked against, any state the solver referenced when it signed its bid: [2](#0-1) 

The only integrity check performed is that the declared `tokenId` is still owned by the bidding solver (`entry.state.owner !== normalizedSolver`) — there is no verification of the pool's current tick, `sqrtPriceX96`, or the position's liquidity against any value declared/signed at bid time, and no minimum bid-window dwell time enforced on the liquidity itself. This mirrors exactly the root cause in the external report: a reward/price path (`currentOnly` in Angstrom, `weightedMedian` weighting here) consumes "current" on-chain state without validating it matches an expected value, so it can be manipulated in the same or an adjacent block as the triggering event.

The triggering event is fully deterministic and publicly known ahead of time: `on_finalize` emits `PhantomBidWindowExhausted` for a commitment exactly at `info.created_at_block + window`, where `window` (governance-set, but readable on-chain) and `created_at_block` are both public: [3](#0-2) 

So an attacker (an unprivileged intent solver — an explicitly in-scope actor) can:
1. Watch `PhantomOrderRegistered` to learn `created_at_block` and read `phantomTimings()` to compute the exact exhaustion block.
2. Place a bid (`place_bid`) declaring a Uniswap V4 position it owns, quoting an aggressive rate.
3. Just before/at the exhaustion block, flash-mint or shift liquidity into that position's tick range (or move the pool's price into the declared range via a swap) to make `positionAmountOfToken` report an inflated backing amount, then withdraw the liquidity immediately after.
4. Because `weightedMedian` is documented to return one bidder's exact quote verbatim once that bidder holds over half the leg's weight, this manipulated bid becomes *the* published rate.

The published rate flows straight into `updateLiquidityPools` → pool `sellRate`/`buyRate`, which are consumed by Simplex fillers to price real, fund-moving `fillOrder` transactions: [4](#0-3) 

### Impact Explanation
A manipulated phantom price is not a cosmetic index bug: it is the input Simplex-driven fillers and any other rate consumer use to price real cross-chain `fillOrder` executions of user escrow. An attacker who can transiently inflate a Uniswap V4 position's reported liquidity/tick range at a fully predictable snapshot block can force an artificial, favorable rate to be published, causing real intent fills to settle against a manipulated price — a direct analog of the "price slippage exceeds expectations" and "disproportionate rewards" impact in the source report, resulting in fund loss to counter-parties trading against the skewed rate. This is High impact because it corrupts a price oracle consumed for real on-chain settlement, using only inventory the attacker controls (no privileged access required).

### Likelihood Explanation
Medium: it requires capital to manipulate the position's liquidity/tick momentarily (flash-loanable, as in the original report) and requires monitoring/timing to land the manipulation at the deterministic, publicly-known window-close block. No governance or validator collusion is required — a single solver acting alone, using the standard `place_bid` path, can attempt this, making it reachable from a single unprivileged actor.

### Recommendation
Pin the Uniswap V4 state read used for weighting to a specific, bid-time-committed reference rather than "live at aggregation time": e.g., require the bid declaration to commit to the pool's tick/liquidity/sqrtPriceX96 observed at bid-submission time (via a signed oracle observation or a TWAP over a window that cannot be manipulated in a single block), and reject/re-verify at aggregation time that the position's liquidity has not moved beyond a tolerance since the bid was placed — analogous to adding the `WrongEndLiquidity`/`WrongTick` checks recommended in the source report. At minimum, require a minimum liquidity-dwell time (e.g., liquidity present for N blocks prior to the snapshot) before a declared position is allowed to count toward `weightedMedian` weight.

### Proof of Concept
1. Configure a phantom order (`set_phantom_order_config`) with a known `interval_blocks`/`bid_window`; observe `PhantomOrderRegistered.created_at_block` and compute the deterministic exhaustion block via `phantom_bid_window()`.
2. As solver A, call `place_bid` declaring a Uniswap V4 `tokenId` for a position currently holding negligible liquidity, quoting an aggressive `fillOrder` price for a leg.
3. In the block immediately preceding (or at) the computed exhaustion block, mint a large, tightly-ranged liquidity position (or swap to move `sqrtPriceX96` into a declared wide range) so that `positionAmountOfToken` reports a large backing amount for solver A at the moment `runAggregation`'s `readPosition` call executes.
4. Immediately after the snapshot, burn/withdraw the liquidity.
5. Observe that `weightedMedian` selects solver A's quote verbatim as the leg's `medianPrice` (per `sdk/packages/sdk/src/tests/phantomAggregation.test.ts:956-1009`, which already demonstrates that a declared V4 position with zero token balance is sufficient to give a bid a decisive, controllable weight), and that this price is persisted into the pool's `sellRate`/`buyRate` used by real fillers.

2. Per leg, a solver's quote is weighted by **its balance of that leg's OUTPUT token on the destination chain** — the inventory that actually backs the leg. Zero-weight quotes are dropped entirely, not down-weighted: they never reach the median, `bidCount`, or the bidder list. A leg where no bidder holds the output token is absent from the result, exactly as if nobody quoted it.

3. The leg's price is `weightedMedian` of the backed quotes — a **selection**, not a blend. It returns one bidder's exact integer, so a solver holding over half the leg's weight sets the published price verbatim, and the result can never be a value nobody quoted. `lowestPrice` and `highestPrice` are deliberately overwritten with the median so consumers cannot read an outlier bid as a tradeable bound.
