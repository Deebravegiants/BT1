### Title
Fee-on-transfer input tokens cause escrow over-crediting and stuck/drainable funds in `IntentGatewayV2.placeOrder` (Tron) - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron deployment of `IntentGatewayV2.placeOrder` escrows input tokens by pulling the *declared* `order.inputs[i].amount` via `safeTransferFrom` and then crediting that same declared (fee-reduced only by protocol fee, not by token transfer fee) amount to the order's escrow ledger, instead of measuring the actual balance received. This reproduces exactly the fee-on-transfer accounting bug described in the external report for Allo's `_fundPool`.

### Finding Description
In the non-predispatch branch of `placeOrder`, the gateway does: [1](#0-0) 

```solidity
} else {
    for (uint256 i; i < inputsLen;) {
        if (order.inputs[i].amount == 0) revert InvalidInput();
        address token = address(uint160(uint256(order.inputs[i].token)));
        if (token == address(0)) {
            if (msgValue < order.inputs[i].amount) revert InsufficientNativeToken();
            msgValue -= order.inputs[i].amount;
        } else {
            IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
        }

        // Store reduced amount (after protocol fees) in escrow
        _orders[commitment][token] += reducedInputs[i].amount;
        ...
```

`reducedInputs[i].amount` is derived purely from `order.inputs[i].amount` minus the protocol fee basis points — it never reflects the token's own transfer-fee deduction: [2](#0-1) 

If the input token is a fee-on-transfer ERC-20, the gateway's real balance increase from `safeTransferFrom` is strictly less than `order.inputs[i].amount`, yet `_orders[commitment][token]` is credited with the full (pre-transfer-fee) `reducedInputs[i].amount`. Because `_orders` is a shared per-token/per-commitment accounting map backed by a single pooled token balance for the whole contract (not per-order segregated custody), this creates a ledger of IOUs that exceeds the actual tokens held.

When the order is later redeemed, `withdraw()` transfers out the full escrowed (over-accounted) amount and decrements the ledger by that same amount: [3](#0-2) 

```solidity
function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
    ...
    if (token == address(0)) {
        (bool sent,) = beneficiary.call{value: amount}("");
        ...
    } else {
        (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
        if (!success) revert TransferFailed();
    }
    _orders[body.commitment][token] -= amount;
```

Because the real token balance is smaller than the sum of all outstanding escrow entries for that token, either (a) redemption of an order fails outright with `TransferFailed()` because the contract's actual balance is insufficient, permanently stranding that order's escrow, or (b) an earlier order's redemption succeeds by consuming real tokens that were actually funded by a *different* user's deposit, effectively draining other users' orders to cover the shortfall of fee-affected ones.

Notably, the primary EVM `IntentGatewayV2` in `evm/src/apps/IntentGatewayV2.sol` was already hardened against exactly this class of bug — it snapshots balances before/after every `safeTransferFrom` and mutates `order.inputs[i].amount` to the actually-received amount before computing the commitment and escrow: [4](#0-3) 

The Tron contract lacks this fix, both in the plain-transfer branch shown above and in the predispatch branch, where the escrow credit uses `reducedInputs[i].amount` (still derived from the declared, not the transferred, amount) rather than the truly measured post-transfer balance delta: [5](#0-4) 

### Impact Explanation
This is a single-user-reachable path (`placeOrder`, an unprivileged, permissionless entry point) that leads to either permanent freezing of escrowed funds for a fee-on-transfer input order (recipient can never fully redeem) or effective theft/drainage of other users' escrowed principal, since redemptions are paid out of a shared pooled balance rather than segregated real custody per order. Both outcomes match the accepted severity bar (concrete theft or permanent freezing of funds).

### Likelihood Explanation
Likelihood depends on whether fee-on-transfer tokens are permitted as gateway inputs on the Tron deployment. Given the protocol's stated design goal of supporting arbitrary ERC-20 tokens as intent inputs and that the sibling EVM implementation was explicitly patched for this exact scenario (comment: "For fee-on-transfer tokens, the gateway receives less than the requested amount"), the Tron contract's omission of the same fix is a real, exploitable gap whenever any listed input token later becomes fee-on-transfer (e.g., via a token upgrade/parameter change) or a fee-on-transfer token is added as a supported/whitelisted input.

### Recommendation
Apply the same fix used in `evm/src/apps/IntentGatewayV2.sol`: measure the actual token balance delta before/after each `safeTransferFrom` (and after the predispatch sweep) in `evm/tron/contracts/apps/IntentGatewayV2.sol`, and use that measured amount — not the declared `order.inputs[i].amount` — both for computing `reducedInputs`/the commitment hash and for crediting `_orders[commitment][token]`.

### Proof of Concept
1. Deploy `IntentGatewayV2` (Tron) with an ERC-20 input token that charges a transfer fee (e.g., 2%) on `transferFrom`.
2. User calls `placeOrder` with `order.inputs[0].amount = 1000` of the fee token; approves the gateway for 1000.
3. `safeTransferFrom(msg.sender, address(this), 1000)` executes; due to the 2% fee, the gateway's real token balance increases by only 980.
4. `_orders[commitment][token] += reducedInputs[0].amount` credits the full 1000 (minus only protocol fee, if any) to the escrow ledger — not 980.
5. When a solver/relayer triggers `withdraw()` for this order (or for a batch of orders sharing the same token), the contract attempts to `transfer` more tokens than its actual balance can support once all outstanding escrow claims are summed, causing `TransferFailed()` reverts for some orders (frozen funds) or allowing one order's redemption to consume tokens that were actually deposited by another user (fund drainage) — reproducing the exact "declared vs. actual balance" mismatch described in the original Allo `_fundPool` report.
