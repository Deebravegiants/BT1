### Title
Unauthenticated `EmporiumOperation`s let an attacker drain any ERC-20 allowance held by the Emporium contract and claim it as their own withdrawal - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
`EmporiumUpgradeable.verifyWallet` skips *all* signature verification whenever `stack.signerAddress == address(0)` [1](#0-0) , so any attacker who submits their own `Hinkal.transact` proof can supply an arbitrary, unsigned "stateless" `EmporiumOperation` list that is executed with `msg.sender == EmporiumUpgradeable` (`op.endpoint.call{value: op.value}(op.callData)`) [2](#0-1) . `runAction` then attributes every token that lands in the contract during that call to the attacker's own output UTXO simply by diffing balances before/after, only netting out `deltaAmountChanges` when it is negative [3](#0-2) . Any leftover ERC-20 allowance that names the Emporium contract as spender (set intentionally or accidentally by a prior op/user) can therefore be pulled in via a crafted `transferFrom` call and paid straight out to the attacker, with `deltaAmountChanges[i] == 0` for that token.

### Finding Description
The invariant that should hold is: **tokens leaving the action to the caller in a tx == `-deltaAmountChanges` Hinkal sent that action in that same tx.** In `runAction`, `balanceChange[i] = balancesAfter[i] - balancesBefore[i]`, adjusted by `-deltaAmountChanges[i]` only when `deltaAmountChanges[i] < 0` [3](#0-2) ; the resulting `balanceChange` is paid out unconditionally to `msg.sender` via `handleOut` -> `transferERC20TokenOrETH` [4](#0-3) . This accounting silently assumes that any balance increase between the "check" (`balancesBefore`) and the "write" (`balancesAfter`) came only from the ops the *signer* authorized. That assumption is false because:

1. `verifyWallet` only checks the EIP-712 signature over `stack.ops` when `stack.signerAddress != address(0)`; when it is `address(0)` the function returns immediately after marking the message used, performing **no authentication of the ops array at all** [5](#0-4) .
2. In this unauthenticated "CASE 2: Stateless Interaction" branch, `runAction` blindly executes `op.endpoint.call{value: op.value}(op.callData)` for any endpoint/calldata the attacker chooses, as long as the selector isn't `callHinkalWallet`/`doSendToRelay` [6](#0-5) . That call's `msg.sender` is the `EmporiumUpgradeable` contract itself.
3. If a persistent ERC-20 `approve` naming the Emporium contract as spender exists — e.g. left by a prior legitimate Emporium op (a swap-style approve-then-call sequence that didn't reset the allowance to 0, or an approval granted by any external holder to the Emporium contract address) — the attacker's unsigned op can call `token.transferFrom(approver, address(this), amount)`. Because `msg.sender == address(this) == the approved spender`, the ERC20 contract permits it.
4. That pulled-in amount increases `balancesAfter[i]` relative to `balancesBefore[i]` measured inside the *attacker's own* transaction, with `deltaAmountChanges[i]` for that token left at `0` (the attacker declares no deposit for it). `runAction` therefore treats the entire pulled amount as the legitimate output of the attacker's action and forwards it via `handleOut` as a fresh UTXO/transfer to the attacker.
5. None of the existing guards stop this: `onlyAllowedRecipient` only checks that the caller of `runAction` is Hinkal, not that the ops are authorized [7](#0-6) ; `performHinkalChecks`/`dimensionsCheck`/circuit constraints (`inTotal + amountChanges === outTotal`) only validate the declared `amountChanges`/`deltaAmountChanges` inside the Hinkal proof, they have no visibility into what `runAction`'s internal `ops` do to the Emporium contract's actual token balances.

### Impact Explanation
An unprivileged attacker can steal any ERC-20 tokens for which the Emporium contract currently holds spender allowance from any address (a leftover approval from a previous legitimate op, a mis-configured integration, or tokens deliberately staged by the attacker via a hook/hook-controlled approver to widen the window). The stolen value is minted into the attacker's own shielded UTXO / paid to their address without any corresponding negative `deltaAmountChanges`, i.e. direct theft of protocol/user funds that were never accounted for in that transaction's ZK-verified amount changes. This is repeatable for every stale/available approval and matches Critical: direct theft of shielded or in-flight user funds.

### Likelihood Explanation
The only precondition is that some ERC-20 allowance exists with the Emporium contract as spender — a state that can arise from completely normal Emporium usage (approve-then-swap op patterns commonly leave non-zero residual allowances) or be engineered by the attacker themselves using a hook/endpoint/token they control, then exploited in a follow-up transaction. The attack costs only one `Hinkal.transact` call with a self-generated proof and a crafted `externalActionMetadata`; no signature, privileged role, or victim cooperation is required because `verifyWallet` never checks stateless ops. This makes exploitation cheap, reliable, and repeatable.

### Recommendation
Do not allow fully unauthenticated `EmporiumOperation`s to call arbitrary endpoints from the Emporium contract's own identity. Either (a) require a valid signature for *every* op regardless of `signerAddress`, or (b) restrict the stateless-call target/calldata surface (e.g. an allow-list of endpoints/selectors) so `address(this)`-scoped ERC-20 allowances can never be redirected by an unrelated caller, and (c) revoke/zero any approvals granted during an action before `runAction` returns rather than leaving them persistent across transactions. Additionally, `handleOut`'s balance-diff accounting should not credit balance increases that cannot be traced to the declared `deltaAmountChanges` or to funds already resident in the contract at message start under the same action.

### Proof of Concept
Foundry test plan:
1. Deploy `EmporiumUpgradeable`, a mock ERC20 `token`, and a "victim" address that (simulating a prior op or stray approval) calls `token.approve(address(emporium), amount)`.
2. As the attacker, call `Hinkal.transact` with a self-generated proof for a dummy/zero UTXO, targeting the Emporium external action, with `erc20TokenAddresses = [token]`, `deltaAmountChanges[0] == 0` (no real deposit), and `externalActionMetadata` encoding an `EmporiumStack` with `signerAddress = address(0)` and one stateless `EmporiumOperation{endpoint: token, callData: abi.encodeCall(IERC20.transferFrom, (victim, address(emporium), amount))}`.
3. Assert before: `token.balanceOf(emporium) == 0`, `deltaAmountChanges[0] == 0`.
4. Run the transaction; assert `runAction` succeeds and returns a UTXO of `amount` for `token`, and/or `token.balanceOf(attackerRecipient) == amount`.
5. Assert the broken invariant: tokens leaving the action (`amount`) != `-deltaAmountChanges[0]` (`0`), proving funds left the action uncorrelated with any declared Hinkal-verified deposit.
