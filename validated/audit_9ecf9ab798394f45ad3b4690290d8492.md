### Title
`restoreAtom` set to `false` prematurely due to uncoordinated concurrent `Hook.AssetsSynced` firings from `unlock()`'s `#restoreIfNeeded` and `addSeed()` - ([File: features/application/src/plugins/lifecycle.ts])

### Summary
`applicationLifecyclePlugin#onAssetsSynced` unconditionally sets `restoreAtom.set(false)` whenever `Hook.AssetsSynced` fires, but two independent, non-coordinated code paths — `Application#unlock` → `#restoreIfNeeded` and `Application#addSeed` — both fire `Hook.AssetsSynced` on their own timelines with no shared lock or reference count. When `addSeed()` is called immediately after `unlock()`, `#restoreIfNeeded`'s `AssetsSynced` firing (gated only by the primary-wallet `RESTORE_FLAG`, not by `restoringAssetsAtom`) can race ahead and reset `restoreAtom` to `false` while the newly added seed's assets are still being restored per `restoringAssetsAtom`.

### Finding Description
`unlock()` starts `#restoreIfNeeded()` without awaiting it (`void this.#restoreIfNeeded()`), so `unlock()` resolves while that background task is still running: [1](#0-0) 

Inside `#restoreIfNeeded`, the decision to fire `Hook.AssetsSynced` depends solely on the persisted `RESTORE_FLAG` (`isRestoring()`), not on `restoringAssetsAtom`. If the primary wallet is already restored (typical unlock of an existing wallet), it proceeds straight to `this.fire(Hook.AssetsSynced)`: [2](#0-1) 

`addSeed()` runs a sequential chain: it sets `restoreAtom = true` via `Hook.AddSeed`, then awaits `Hook.RestoreSeed`, whose handler in `restore-progress-tracker` calls `restoreProgressTracker.restoreAll(true)` (which repopulates `restoringAssetsAtom` for all currently enabled base assets, including the new seed's) and blocks on `waitAllAssetsRestored()` until `restoringAssetsAtom` is empty, before finally firing its own `Hook.AssetsSynced`: [3](#0-2) [4](#0-3) 

Both flows converge on the same handler, which blindly overwrites the shared, non-scoped `restoreAtom` with `false` on every `AssetsSynced` firing, with no check of `restoringAssetsAtom` or any counter tracking overlapping restore operations: [5](#0-4) 

Because `#restoreIfNeeded`'s `AssetsSynced` firing is independent of and unaware of `addSeed`'s in-progress `restoringAssetsAtom` state, if it completes first (e.g., because the primary wallet's `RESTORE_FLAG` is already false and its own check resolves quickly) while `addSeed`'s `waitAllAssetsRestored()` is still pending (attacker-delayed sync of the new seed's assets), `restoreAtom` is set to `false` even though `restoringAssetsAtom` still contains entries for assets under restoration. `restoreAtom` is a public atom relayed to the UI/API layer via `createAtomObserver({ port, atom: restoreAtom, event: 'restore' })`, so external consumers observe a premature "restore complete" signal: [6](#0-5) [7](#0-6) 

### Impact Explanation
This is a state-consistency/logic race rather than a key-disclosure or signing-bypass bug: `restoreAtom` briefly (until `addSeed`'s own delayed `AssetsSynced` fires) reports `false` while the newly added seed's assets are still restoring per `restoringAssetsAtom`. This could cause UI/API consumers that gate "wallet ready" behavior on `restoreAtom` (rather than the more granular `restoringAssetsAtom`) to expose an under-restored account state (e.g., showing balances/addresses for the new seed prematurely) before restore truly completes. It does not itself allow unauthorized signing, secret disclosure, or account/origin authorization bypass — the underlying `restoringAssetsAtom` remains accurate and any consumer that checks it directly (as `restore-progress-tracker`'s own `onRestore`/`onRestoreSeed` do) is unaffected.

### Likelihood Explanation
Requires: (1) the attacker/caller controlling call ordering to invoke `addSeed()` immediately after `unlock()` — a legitimate application-level call pattern requiring no privilege beyond normal SDK usage; (2) an existing unlocked wallet where `RESTORE_FLAG` is already false, so `#restoreIfNeeded`'s check resolves before `addSeed`'s `waitAllAssetsRestored()`; (3) attacker-influenced network delay for the new seed's tx-log-monitor sync (feasible since `restoreProgressTracker` reacts to `txLogMonitors` events fed by chain RPC responses). These are plausible but require precise timing and are inherently racy (order not deterministic), which limits reliability of exploitation. The condition is real in the code as written — there is no synchronization primitive preventing it.

### Recommendation
Make `onAssetsSynced` (or `restoreAtom` derivation) check `restoringAssetsAtom` before clearing `restoreAtom`, e.g., only set `restoreAtom` to `false` when `restoringAssetsAtom` is empty (mirroring the guard already used in `restore-progress-tracker`'s `waitAllAssetsRestored`), or replace the independent boolean `restoreAtom` with a derived/reference-counted atom computed directly from `restoringAssetsAtom` plus in-flight restore flags, eliminating the possibility of two uncoordinated writers desynchronizing it.

### Proof of Concept
Integration test (mirroring `sdks/headless/__tests__/restore-complete.integration-test.js`):
1. Start app, create/import a wallet, `unlock()` with an already-restored primary seed (`RESTORE_FLAG` false).
2. Immediately call `addSeed({ mnemonic })` without awaiting any settling delay.
3. Before emitting the `txLogMonitors` `after-tick-multiple-wallet-accounts` event for the new seed's ethereum asset, assert via `restoringAssetsAtom` that `ethereum: true` is still present.
4. Assert that `restoreAtom` (observed via the `restore` port event) does **not** report `false` while `restoringAssetsAtom` still has non-empty entries for the new seed's assets — i.e., that `restoreAtom` transitions to `false` only after emitting `after-tick-multiple-wallet-accounts` for `ethereum` and `restoringAssetsAtom` becomes `{}`.
5. Expected (failing) result under current code: `restoreAtom` reports `false` from `#restoreIfNeeded`'s own `AssetsSynced` firing before step 4's tick is emitted, violating the invariant that persisted restore-flag consistency must not decouple from per-asset restore completion tracked in `restoringAssetsAtom`.
