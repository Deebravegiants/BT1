### Title
Permanent market freeze via i128 overflow in RAY-scaled index accrual — every verb traps on `MathOverflow` - (File: common/src/rates/scaling.rs)

### Summary
The analog of "a malformed frame crashes the whole process" is an arithmetic trap that permanently wedges a market: once accrued RAY-scaled market totals exceed the `i128` domain, `scaled_to_original` panics inside `mul_div_half_up` with `GenericError::MathOverflow`. Because every entrypoint accrues interest first (`update_indexes`, `supply`, `borrow`, `withdraw`, `repay`, `liquidate`, `clean_bad_debt`, `flash_*`), a single `MathOverflow` inside accrual bricks the entire market — the closest shape to a process crash in a Soroban contract.

### Finding Description
Index accrual converts scaled positions to original RAY value via `scaled.mul(env, index)`, which routes to `mul_div_half_up`. That function panics with `MathOverflow` whenever `x * y / d` does not fit `i128`. The docs in `docs/reference/formulas.md` (numeric limits) admit the admitted cap maximum (~170 billion whole tokens) and the index ceiling (10^36) do not jointly guarantee accrued values fit the RAY domain: "Value overflow can occur before the index ceiling and block repayment/withdrawal because those operations accrue first."

The repo's own harness test proves it end-to-end: `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` (tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-356) seeds a ~170-billion-token 18-decimal market at 98% utilization on the XLM rate curve, advances time, and observes `try_update_indexes_for` return `MATH_OVERFLOW` *before* `borrow_index` reaches `MAX_BORROW_INDEX_RAY`. After that, `try_withdraw_raw` and `try_repay` both fail with `MATH_OVERFLOW` — the index cap that would have stopped accrual never engages because the value conversion overflows first.

### Impact Explanation
Permanent freezing of funds. Once accrued totals exceed the `i128` boundary, every state-changing entrypoint on that (hub, token) book reverts deterministically — the panic happens inside accrual, before any leg executes. Suppliers cannot withdraw, borrowers cannot repay, liquidators cannot liquidate, and `update_indexes`/`recapitalize` cannot advance the market past the failing conversion. Unlike a transient revert, there is no input that avoids the trap, since the overflowing quantity is the stored market total itself. All funds held by that market's pool book are permanently locked.

### Likelihood Explanation
Medium-low. An unprivileged attacker must hold a near-cap position (~170 billion whole-token cap domain) at sustained high utilization on a steep rate curve for the index to grow ~170× (the harness reaches the cliff only after multiple simulated years at ~98% utilization). The attack requires substantial capital and an already-admitted whale-scale market, but no privileged action, no oracle manipulation, and no leaked keys — it is reachable purely through `supply`/`borrow` and time. Severity lands at Medium: permanent freeze of an entire market's funds, but gated by extreme scale and duration.

### Recommendation
Make accrual saturate rather than panic: when the accrued index would push `scaled * index` past `i128::MAX`, clamp the index to the largest value whose value conversion still fits (mirroring `calculate_scaled_cap`'s `mul_div_floor_saturating` fail-open design), or gate accrual on the `MAX_BORROW_INDEX_RAY` ceiling *before* the value conversion so the cap engages first. Alternatively, reduce admitted caps so that `cap_max * index_ceiling` provably fits the RAY domain, turning the documented arithmetic limit into an enforced invariant.

### Proof of Concept
The repository already contains a runnable demonstration:

```rust
// tests/test-harness/tests/controller/large_positions_and_long_horizons.rs
let principal = BILLION * 10i128.pow(18);          // ~170B-token-scale market
t.supply_raw(BOB, "BIG18", principal);
let debt = principal / 100 * 98;                   // 98% utilization
t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
t.borrow_raw(ALICE, "BIG18", debt);

loop {
    t.advance_time(YEAR_SECS);
    if let Err(e) = t.try_update_indexes_for(&["BIG18"]) { break e; }
}
// e == MATH_OVERFLOW, while borrow_index < MAX_BORROW_INDEX_RAY
// Then both revert:
assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
```

The trap site is `scaled_to_original` → `Ray::mul` → `mul_div_half_up`, which panics with `MathOverflow` when the product exceeds `i128`; since accrual precedes every verb, the market is frozen permanently.
