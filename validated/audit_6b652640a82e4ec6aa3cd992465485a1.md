This confirms the vulnerability. The documentation at `docs/usage/webhooks.md` line 125 explicitly states that `ShopifyAPI::Webhooks::Registry.process` "will verify the request did indeed come from Shopify" — but the verification only covers the raw body, not the identity headers that the gem itself parses and exposes to the handler as the trusted `shop` value.

### Title
Webhook HMAC Verification Excludes Shop/Topic Identity Headers, Enabling Cross-Tenant Webhook Spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , so `Utils::HmacValidator.validate` in `Registry.process` cryptographically authenticates only the request body bytes [2](#0-1) . The `shop`, `topic`, `webhook_id`, and `api_version` values are read directly from unauthenticated HTTP headers [3](#0-2)  and are passed straight into `WebhookMetadata` as the trusted tenant identity for the handler [4](#0-3) .

### Finding Description
The identity binding that should hold is: `hmac` authenticates ⇔ (`raw_body` bytes AND `shop`/`topic` header bytes) are both genuine. Instead, the gem's HMAC check only binds the `raw_body`, while `shop` (and `topic`, `webhook_id`, `api_version`) are taken from headers that are never part of the signed material [5](#0-4) . `Utils::HmacValidator.validate` simply recomputes an HMAC over `verifiable_query.to_signable_string` and compares it to the `hmac` header value [6](#0-5) ; for `Request`, `to_signable_string` is body-only.

An attacker who legitimately operates their own Shopify store with the app installed can trigger a genuine webhook for their own shop (e.g., `orders/create`), capturing a raw body and a valid `hmac-sha256` value signed with the app's shared `api_secret_key`. Because the signature never covers the `shop-domain` header, the attacker can POST that exact `(raw_body, hmac)` pair directly to the app's webhook endpoint while substituting the `shop-domain` header (and optionally `topic`) with a victim shop's domain. `HmacValidator.validate` still succeeds because it checks only `raw_body` [1](#0-0) , and `Registry.process` then dispatches the handler with `shop: request.shop` set to the victim's domain [4](#0-3) , while `body` contains attacker-controlled content.

### Impact Explanation
This breaks the tenant boundary the documentation promises ("will verify the request did indeed come from Shopify") [7](#0-6) . Host applications reasonably treat `data.shop` from `WebhookMetadata` as an authenticated tenant identifier (the gem's own docs instruct handlers to key off `data.shop`, e.g. `perform_later(topic: data.topic, shop_domain: data.shop, ...)`) [8](#0-7) . An attacker who is merely a legitimate merchant of their own installed shop can forge webhook deliveries that appear to originate from a different (victim) shop with attacker-chosen body content, since the signature verification never binds `shop` to the payload. Depending on how the host app uses `data.shop` (e.g., to look up per-shop session/access tokens, or to write/update per-shop records such as customer/order data or mandatory `shop/redact`/`customers/redact`/`customers/data_request` compliance topics), this enables cross-tenant data corruption or spoofed compliance actions against a shop the attacker does not control.

### Likelihood Explanation
Exploitation only requires the attacker to control one shop with the app installed (an unprivileged, self-service condition — any developer can install a public/custom app on a test store) and the ability to send arbitrary HTTP requests to the app's public webhook endpoint (which is inherently internet-reachable by design). No access token, `client_secret`, or victim credentials are required.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, and ideally `webhook-id`/`api-version`) in the HMAC-signed material, or otherwise cryptographically bind them to the body before trusting `request.shop`/`request.topic`. If a canonical construction of headers+body cannot be introduced without breaking compatibility with Shopify's own signature scheme (which only signs the body), host-application guidance should be updated to explicitly warn that `data.shop` is not authenticated by this gem and must be independently validated against a known/installed shop list before being used for any privileged or tenant-scoping operation.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com` and trigger a real webhook (e.g. `orders/create`) to capture a legitimate raw body `B` and its `X-Shopify-Hmac-Sha256` header `H` (valid because `HMAC(api_secret_key, B) == H`, per `HmacValidator.validate` [9](#0-8) ).
2. POST directly to the app's webhook route with:
   - Body: `B` (unchanged)
   - Header `X-Shopify-Hmac-Sha256: H` (unchanged, still valid since body is unchanged)
   - Header `X-Shopify-Shop-Domain: victim.myshopify.com` (forged, attacker's target)
   - Header `X-Shopify-Topic: orders/create` (or another registered topic)
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `raw_body` against `H` [1](#0-0) .
4. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and attacker-controlled `body`, despite the victim shop never having sent this webhook [4](#0-3) .
