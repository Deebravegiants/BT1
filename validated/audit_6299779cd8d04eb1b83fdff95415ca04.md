## Finding

### Title
Missing fee-exceeds-amount guard in `createWithdrawalIntents()` allows an out-of-range debit when a caller supplies its own `feeEstimation` - (File: `packages/intents-sdk/src/sdk.ts`)

### Summary
`IntentsSDK.createWithdrawalIntents()` computes the on-chain withdrawal amount as `amount - feeEstimation.amount` for fee-inclusive withdrawals without ever checking that `feeEstimation.amount < amount`. The equivalent, correct check exists only in the sibling method `_estimateWithdrawalFee()`.

### Finding Description
`_estimateWithdrawalFee()` explicitly guards the subtraction: [1](#0-0) 

But `createWithdrawalIntents()`, which is a public API (also part of `IIntentsSDK`) and is the method actually used to build the intent that gets signed and broadcast, performs the same subtraction with no equivalent check: [2](#0-1) 

`feeEstimation` is not an opaque, SDK-internal value — it is a plain caller-suppliable object (`{ amount: bigint; quote; underlyingFees }`), and both `processWithdrawal()` and `signAndSendWithdrawalIntent()` accept it directly from the caller instead of forcing a fresh call to `estimateWithdrawalFee()`: [3](#0-2) [4](#0-3) 

When `args.feeEstimation` is supplied by the caller in `processWithdrawal()`, step 1 skips `estimateWithdrawalFee()` (and thus its `FeeExceedsAmountError` guard) entirely, and the raw value flows straight into `createWithdrawalIntents()` via `signAndSendWithdrawalIntent()`.

The broken equality: for `feeInclusive: true`, the invariant the code intends to hold is `0 ≤ actualAmount = amount − fee < amount`. That invariant is enforced in one call path (`estimateWithdrawalFee`) but not in the other (`createWithdrawalIntents` / `processWithdrawal` with a pre-supplied `feeEstimation`), so a stale, mismatched, or otherwise incorrect `feeEstimation.amount` (e.g., reused from another asset/route, or from an earlier quote for a different `withdrawalParams.amount` in a batch/retry flow) can silently produce a debited/withdrawn amount that does not correspond to "amount minus fee, once."

### Impact Explanation
If `feeEstimation.amount` exceeds `withdrawalParams.amount`, `actualAmount` goes negative and gets threaded into bridge-specific intent builders (e.g. `deriveOmniWithdrawIntentParams`) where further arithmetic is performed on it (e.g. adding UTXO fees) before being serialized into the `ft_withdraw`/`mt_withdraw` intent amount. Because there is no upfront rejection, the resulting intent silently encodes an amount inconsistent with what the caller declared as the withdrawal ceiling, which can mis-debit the user's intents balance relative to what they authorized (fee overcharge / incorrect debit), matching the "amount debited that is not amount plus fee once" analog class.

### Likelihood Explanation
Requires the integrator/caller to pass a `feeEstimation` that was not obtained from a matching, current `estimateWithdrawalFee()` call for the exact same `withdrawalParams` (e.g., reusing a fee quote across a retry, batch, or asset swap). This is a plausible integration mistake since the public type signatures of `processWithdrawal`/`signAndSendWithdrawalIntent`/`createWithdrawalIntents` do not enforce freshness or matching, and nothing in `createWithdrawalIntents` re-validates the relationship.

### Recommendation
Add the same `feeEstimation.amount < withdrawalParams.amount` (for `feeInclusive: true`) check inside `createWithdrawalIntents()` (and/or centralize the `actualAmount` computation + guard in one shared helper used by both `_estimateWithdrawalFee` and `createWithdrawalIntents`), throwing `FeeExceedsAmountError` whenever the invariant is violated, regardless of whether the caller supplied their own `feeEstimation`.

### Proof of Concept
1. Call `sdk.estimateWithdrawalFee({ withdrawalParams: paramsA })` to get `feeEstimationA` (large fee, e.g. for a different/larger amount or asset).
2. Call `sdk.processWithdrawal({ withdrawalParams: paramsB (small amount, feeInclusive: true), feeEstimation: feeEstimationA })` — reusing the stale estimation.
3. `processWithdrawal` skips `estimateWithdrawalFee()` (feeEstimation already provided) and goes straight to `signAndSendWithdrawalIntent` → `createWithdrawalIntents`, where `actualAmount = paramsB.amount - feeEstimationA.amount` is computed and used to build/sign the withdrawal intent without ever throwing `FeeExceedsAmountError`, even though `feeEstimationA.amount >= paramsB.amount`. 				});
