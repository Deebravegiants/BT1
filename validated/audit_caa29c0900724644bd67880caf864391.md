### Title
Order creator can weaponize a blacklistable/pausable escrow input token to permanently block `_withdraw`, freezing escrow and stiffing the solver who already paid out - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentsBase._withdraw` uses `IERC20.safeTransfer` to release escrowed input tokens to a beneficiary (the filling solver or the refunded user), and this transfer is invoked from `ExtrinsicIntents.onAccept` / `onGetResponse`, which are the Hyperbridge message-delivery callbacks for cross-chain intents. Analogous to the Cooler `onRepay` bug — where a lender can revert a callback to force a default and seize collateral it wouldn't otherwise get — a party who controls the escrowed input token's transfer behavior (an "unprivileged" order creator, since users choose the input token when placing an order) can make that token permanently revert transfers to a specific counterparty (e.g., a blacklist or pausable token), causing the `RedeemEscrow` delivery to fail forever while the solver has already unconditionally delivered outputs on the destination chain.

### Finding Description
`_fillCrossChain` in `evm/src/apps/intentsv2/ExtrinsicIntents.sol` (lines 164–220) requires the solver to push output tokens to the beneficiary *before* the escrow release message is even dispatched: [1](#0-0) 

Only after those output transfers succeed does the contract dispatch a `RedeemEscrow` POST request back to the source chain via `_post`, whose eventual delivery invokes `onAccept` → `_withdraw(body, false, true)`: [2](#0-1) 

`_withdraw` (in `IntentsBase.sol`) unconditionally attempts `IERC20(token).safeTransfer(beneficiary, amount)` for every escrowed input token, where `token` is chosen by the **order creator** at `placeOrder` time and `beneficiary` is the solver who filled the order: [3](#0-2) 

If this token has admin-controlled transfer restrictions (blacklist, pause, allowlist-only recipients — common in USDC/USDT-style tokens and many others), the order creator can, after observing the solver's `OrderFilled` output-side transfer, blacklist the solver's address on the input token. `safeTransfer` then reverts inside `onAccept`. Per `EvmHost.dispatchIncoming` (lines 794-818), a failed `onAccept` call causes the request receipt to be deleted so the message "can be retried": [4](#0-3) 

But because the blacklist condition is persistent and entirely under the order creator's control, every retry of the same `RedeemEscrow` delivery will keep failing indefinitely. There is no fallback path (no try/catch to skip the bad token and still finalize/mark filled) — the entire `onAccept` call, including `_filled[commitment] = beneficiary` and the release of any other escrowed tokens/fees in the same withdrawal request, is reverted as one atomic unit each time. The solver, who already unconditionally delivered value on the destination chain in `_fillCrossChain`, receives nothing, and the escrow is permanently stuck in the source contract.

This mirrors the Cooler `onRepay` bug exactly in structure: an unprivileged counterparty (there, the lender via `onRepay`; here, the order creator via a controllable ERC-20) can intentionally and repeatedly fail a settlement callback/transfer to induce a "default" that benefits them (keeping the solver's output for free) at the solver's expense, and the protocol has no timeout/rescue mechanism at all for this cross-chain leg (`ExtrinsicIntents` has no `onPostRequestTimeout` override, and even if it did, POST requests dispatched with `timeout: 0` in `_post` never expire).

### Impact Explanation
- **Theft**: The solver irreversibly transfers output assets to the beneficiary on the destination chain in `_fillCrossChain`, but can be permanently denied the escrowed input tokens they were promised, since the order creator controls the input token's blacklist state and can target the solver's specific address after the fill.
- **Permanent freezing of funds**: The escrowed input tokens (and any other tokens bundled in the same `WithdrawalRequest`, plus accumulated protocol fees for that commitment) become permanently locked in the source `IntentGatewayV2`/`ExtrinsicIntents` contract, since `_withdraw` has no per-token isolation or try/catch and the message has `timeout: 0` (never expires, so no alternate refund path activates).
- This is directly reachable by any unprivileged intent solver participating in the normal cross-chain fill flow with an order whose input token is chosen adversarially by the order creator — no admin/governance privilege is required to trigger the freeze.

### Likelihood Explanation
Medium-to-High. The order creator fully controls which token is used as escrow input when calling `placeOrder`, and can freely choose a token with owner-controlled blacklist/pause functionality (e.g., a custom ERC-20, or by acquiring blacklist authority over a token they control). The only precondition is that a solver is willing to fill an order denominated in such a token — a solver who does not carefully vet the input token's admin-control surface (or is targeted specifically) is exposed. Since `RedeemEscrow` messages carry `timeout: 0` and never expire, and `EvmHost.dispatchIncoming` merely deletes the receipt on failure to permit indefinite retries rather than providing any alternative resolution, there is no protocol-level safety valve once the token is weaponized.

### Recommendation
- In `IntentsBase._withdraw`, isolate each token transfer so a single failing token cannot block finalize/other-token releases in the same withdrawal — e.g., wrap each `safeTransfer` in a low-level call/try-catch, and on failure record the stuck balance as claimable/escrowed-for-later instead of reverting the whole batch.
- Always finalize `_filled[body.commitment]` and settle whichever tokens transfer successfully even if one token's transfer reverts, so the solver at least receives the tokens that are transferable.
- Provide a rescue/timeout path (non-zero timeout plus an `onPostRequestTimeout` handler) so that if the destination-side settlement can never be delivered, the solver (or the protocol) has a way to recover value rather than an indefinite retry loop with no expiry.
- Consider validating/allowlisting acceptable input token types at order-creation time, or require solvers to simulate the full redemption path (including the destination-chain transfer to themselves) before committing outputs.

### Proof of Concept
1. Order creator deploys or controls `EvilToken`, an ERC-20 with an owner-gated `blacklist(address)` that makes `transfer`/`transferFrom` to a blacklisted address revert.
2. Order creator calls `placeOrder` with `order.inputs = [{token: EvilToken, amount: X}]`, escrowing `X` `EvilToken` on the source chain via `IntentGatewayV2`/`IntrinsicIntents`.
3. A solver observes the order, calls `fillOrder`/`_fillCrossChain` on the destination chain, unconditionally transferring the required output assets to the order's beneficiary (per lines 186–199 of `ExtrinsicIntents.sol`).
4. `_fillCrossChain` dispatches the `RedeemEscrow` POST request back to the source chain (`_post`, line 207-212).
5. Before (or as soon as) the relayer delivers this request to the source-chain gateway's `onAccept`, the order creator calls `EvilToken.blacklist(solver)`.
6. When `EvmHost.dispatchIncoming` invokes `onAccept` → `_withdraw`, `IERC20(EvilToken).safeTransfer(solver, X)` reverts; the whole `onAccept` call reverts, the request receipt is deleted (per `EvmHost.sol` lines 812-816), and the message can be resubmitted — but every resubmission fails identically since the blacklist persists.
7. Result: the solver has permanently lost the output assets given to the beneficiary, and `X` `EvilToken` (plus any bundled tokens/fees in the same `WithdrawalRequest`) remain frozen in escrow indefinitely, with no timeout or rescue mechanism to recover it.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }
