### Title
Webhook shop-domain identity spoofing — HMAC only covers the body, not the `shop-domain` header - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable signable string from the raw request body only, while the `shop` (tenant) identity is read from an unauthenticated HTTP header. `Registry.process` validates the HMAC against the body and then hands the header-derived `shop` straight to the app's webhook handler as the tenant identity, without that value ever being covered by the signature.

### Finding Description
`Webhooks::Request#to_signable_string` returns `@raw_body` exclusively: [1](#0-0) 

Meanwhile `Request#shop` is parsed straight out of the `x-shopify-shop-domain` (or `shopify-shop-domain`) header, which is not part of the signable string: [2](#0-1) 

`Utils::HmacValidator.validate` only checks `verifiable_query.to_signable_string` (i.e., the body) against the HMAC secret: [3](#0-2) 

`Registry.process` validates the HMAC and then forwards `request.shop` (the unauthenticated header value) directly to the handler as the tenant identity, with no cross-check against the body or any other authenticated claim: [4](#0-3) 

This reproduces the report's bug class exactly: a field that is acted upon (here, the `shop` used to route/attribute the webhook event to a tenant) is not covered by the HMAC that is supposed to authenticate the whole message. The binding that should hold is:
`shop_used_by_handler == shop_that_signed_the_body`
but the code only enforces `hmac(body) == received_hmac`; it never enforces `shop ∈ signed_data`.

Because the app's `api_secret_key` (the HMAC key) is shared across every shop that installs the same app, any attacker who can install the app on their own store (an "unprivileged internet user" with respect to any other tenant) can obtain a batch of validly-signed webhook bodies/HMACs from Shopify for their own shop. They can then replay one of these bodies to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop's domain. `HmacValidator.validate` still returns `true` because it only checks the (unmodified) body, and `Registry.process` will invoke the handler with `WebhookMetadata` claiming the victim's shop, even though the payload was never actually signed/originated for that shop.

### Impact Explanation
This crosses a tenant boundary: an attacker-controlled request can be attributed to an arbitrary victim shop domain despite the cryptographic authentication mechanism (HMAC) being satisfied. Any host application that trusts `data.shop` from the webhook handler to select which merchant's records to create/update/delete (a documented and expected use of `WebhookMetadata#shop`) can be tricked into mutating or leaking a different tenant's data using attacker-supplied body content, resulting in cross-tenant access — one of the explicitly in-scope Critical impacts.

### Likelihood Explanation
Exploitation requires only: (1) the attacker's own legitimate installation of the target app (which yields real, validly-signed webhook payload/HMAC pairs since the HMAC key is the app-wide `client_secret`, not shop-specific), and (2) the ability to send an arbitrary HTTP request to the app's public webhook endpoint with a modified `shop-domain` header — both of which are available to any unprivileged internet user/merchant of a multi-tenant app. No leaked credentials, TLS interception, or privileged access is required.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the HMAC-covered signable data, or otherwise cross-verify the header-derived shop against an independently authenticated source (e.g., validate that the `shop` header matches a shop record already known to have generated a matching signed payload, or include the header values in the signature computation Shopify performs so `to_signable_string` covers headers relevant to routing). At minimum, document and warn that `WebhookMetadata#shop` is not itself authenticated by the HMAC check and must not be used as the sole tenant-authorization boundary without additional verification.

### Proof of Concept
```ruby
# Attacker has legitimately installed the target app on their own shop
# "attacker-shop.myshopify.com" and receives a real webhook:
body = '{"id":1,"note":"hello"}'
real_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), Context.api_secret_key, body)

# Attacker replays the SAME body/hmac pair to the app's webhook endpoint,
# but swaps the shop-domain header to the victim's shop:
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(real_hmac),   # still valid, body unchanged
  "x-shopify-shop-domain" => "victim-shop.myshopify.com",  # attacker-controlled, unsigned
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) returns true (body/hmac match)
# => handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...))
# The host app now processes attacker-controlled data as if it belongs to victim-shop.
