## Analysis Result

### Title
Emporium relay fee bypass — the `variableRate` fee component is skipped whenever a user routes the withdrawal through the wallet-signed (`signerAddress != address(0)`) code path - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`EmporiumUpgradeable.payRelayFees` computes the relay fee for every withdrawn token in two mutually exclusive ways depending solely on whether `stack.signerAddress` is the zero address or not. When `signerAddress == address(0)` the fee equals `flatFee + variableRate% * amount` (via `IHinkalHelper.calculateRelayFee`), but when `signerAddress != address(0)` the fee is **only** `flatFee` — the `variableRate` component is never applied. A user who owns any deployed `IHinkalWallet` can simply set `stack.signerAddress` to that wallet's address (signing the `EmporiumStack` themselves, which is trivial since they own the wallet) even when none of the ops actually require `invokeWallet`, and thereby completely skip the proportional (`variableRate`) protocol/relay fee, paying only the fixed `flatFee`.

### Finding Description
`payRelayFees` branches purely on `signerAddress`, not on whether the wallet path is functionally necessary: [1](#0-0) 

- If `signerAddress == address(0)`: `relayFee = calculateRelayFee(sumAbs, flatFee, variableRate)` — a percentage-based fee proportional to the withdrawn amount is charged.
- If `signerAddress != address(0)`: `relayFee = flatFee` only — no percentage is ever applied, regardless of how large `sumAbs` is.

The only gate on using the `signerAddress != address(0)` branch is a valid EIP-712 signature over the `EmporiumStack` (`verifyWallet`), which any user can produce themselves for their own `IHinkalWallet` deployment: [2](#0-1) 

Nothing forces the individual operations (`stack.ops`) to actually use `op.invokeWallet == true`; a user can supply an `EmporiumStack` with `signerAddress` set to their own wallet while performing only stateless calls (`invokeWallet == false`), purely to switch `payRelayFees` into the flat-fee-only branch: [3](#0-2) 

This is structurally identical to the referenced M-28 pattern: a fee that is intended to apply to a withdrawal is only charged in one code path/condition, and a user can trivially steer execution into the untaxed path without changing the economic substance of the operation (the amount withdrawn from the shielded pool is identical either way).

### Impact Explanation
The relay/protocol is deprived of the `variableRate` percentage fee it is designed to collect on Emporium withdrawals. For any sizeable withdrawal this is a direct, repeatable loss of protocol/relay fee revenue with no cap besides the (usually much smaller) `flatFee`. This matches the "High — theft ... of protocol/relay fees" impact category.

### Likelihood Explanation
Any unprivileged EOA that deploys or already owns a minimal `IHinkalWallet` contract can perform this at will, for every Emporium withdrawal, with no dependency on relayer error, price oracles, or other users' keys — only their own signature over an `EmporiumStack` they construct.

### Recommendation
Compute `relayFee` using the same `flatFee + variableRate% * sumAbs` formula regardless of `signerAddress`, and route the resulting fee via `sendToRelayFromWallet` when `signerAddress != address(0)` instead of collapsing it to `flatFee` only.

### Proof of Concept
1. User deploys/owns an `IHinkalWallet` instance and signs an `EmporiumStack{ signerAddress: <own wallet>, ops: [ ...stateless calls, invokeWallet:false... ], maxFee: flatFee }` (satisfies `FeeExceedsSignedMax` check since `flatFee <= maxFee`).
2. User submits a valid Hinkal `transact()` with `externalActionId` pointing at `EmporiumUpgradeable`, withdrawing a large `sumAbs` amount of a token via `deltaAmountChanges[i] < 0`.
3. In `runAction`, since `stack.signerAddress != address(0)`, ops execute via CASE 2 (stateless, no wallet call actually needed) or trivially via CASE 1 with a no-op wallet call.
4. `payRelayFees` is invoked with the non-zero `signerAddress`, computing `relayFee = flatFee` only (bypassing `variableRate * sumAbs`), versus the `calculateRelayFee(...)` amount that would have been charged had `signerAddress == address(0)`.
5. Relay/protocol receives only the flat fee, losing the intended proportional fee on the withdrawal.

    function verifyWallet(
        EmporiumStack memory stack,
        CircomData calldata circomData
    ) internal {
        EmporiumStorageVars storage $ = _getEmporiumStorage();

        if ($.usedMessages[circomData.emporiumMessage]) {
            revert UsedMessage();
        }

        $.usedMessages[circomData.emporiumMessage] = true;

        if (stack.signerAddress == address(0)) {
            return;
        }

        bytes32 hashedMessage = _hashTypedDataV4(
            keccak256(
                abi.encode(
                    EMPORIUM_SIGNATURE_TYPEHASH,
                    circomData.emporiumMessage,
                    _hashEmporiumOps(stack.ops),
                    stack.maxFee,
                    stack.deadline
                )
            )
        );

        (address recoveredAddress, ECDSA.RecoverError err) = ECDSA.tryRecover(
            hashedMessage,
            stack.v,
            stack.r,
            stack.s
        );
        bool verified = err == ECDSA.RecoverError.NoError &&
            recoveredAddress == stack.signerAddress;
        if (!verified) {
            revert InvalidSignature();
        }

        if (block.timestamp > stack.deadline) {
            revert SignatureExpired();
        }

        if (circomData.feeStructure.flatFee > stack.maxFee) {
            revert FeeExceedsSignedMax();
        }
    }
