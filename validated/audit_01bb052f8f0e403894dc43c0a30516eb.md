### Title
Deterministic, unsigned offline session-cookie value enables cross-tenant session hijacking - ([File: lib/shopify_api/utils/session_utils.rb])

### Summary
For non-embedded apps, the gem sets the `shopify_app_session` cookie value equal to the deterministic string `"offline_#{shop}"` (or `"#{shop}_#{user_id}"` for online sessions) and later trusts whatever value is presented in that cookie as the session ID with no cryptographic binding to `Context.api_secret_key`. Because the shop domain is public/guessable, an attacker can construct this exact string themselves and present it as a `Cookie` header on their own raw HTTP request (no XSS or victim browser interaction needed) to have the host app resolve and use the victim's stored session/access token.

### Finding Description
The broken binding: `SESSION_ID_RETURNED == UNVERIFIED_COOKIE_BYTES` (an attacker-supplied cookie value is returned unchecked) instead of `SESSION_ID_RETURNED == HMAC(Context.api_secret_key, cookie_bytes)` or an unguessable, unforgeable per-session opaque token.

Path: `Oauth.validate_auth_callback` builds the non-embedded session cookie with `value: session.id` [5](#0-4) . `Session.from` computes `id = "offline_#{shop}"` for offline tokens, purely from the public shop domain string, with no random/secret component [6](#0-5) . Later, `SessionUtils.current_session_id` (non-embedded branch) and `cookie_session_id` simply read `cookies[SessionCookie::SESSION_COOKIE_NAME]` and return it as-is, performing no HMAC/signature verification against `Context.api_secret_key` [7](#0-6) . The documentation confirms the host app is expected to use this returned value directly as the key to fetch the persisted `Session` (with `access_token`) from its own storage [8](#0-7) .

Attacker request: knowing (or discovering, e.g. from the app listing, storefront, or public install flow) a target shop's `.myshopify.com` domain, the attacker sends any HTTP request of their own to a protected route of the host app with header `Cookie: shopify_app_session=offline_victim-shop.myshopify.com`. `current_session_id` returns that exact string unmodified. The host app looks up its session store by that ID (per the documented pattern) and obtains the victim's persisted `Session`, including `access_token`, letting the attacker impersonate the victim shop's server-to-server API access.

Existing guards do not help here: `HmacValidator.validate` and `state == auth_query.state` only protect the initial OAuth callback exchange, not the later use of the cookie as a session pointer [9](#0-8) ; `Context.embedded?` only routes non-embedded apps into the unchecked cookie path [10](#0-9) ; there is no JWT/`aud`/`dest` check in this code path since it's cookie-based, not token-based.

### Impact Explanation
Critical — cross-tenant access to another merchant's stored access token/session. Any unprivileged attacker who can guess or learn a victim shop's myshopify.com domain (routinely discoverable) can, without ever touching the victim's browser, obtain the host app's session object for that shop and thus its Shopify Admin API access token, enabling repeated cross-tenant data access/actions limited only by the app's granted scopes. This is repeatable against any shop whose domain is known and applies to every non-embedded app built with this gem's documented pattern.

### Likelihood Explanation
Preconditions: app is configured as non-embedded (`is_embedded: false`), uses the Authorization Code Grant flow, and follows the documented pattern of using `current_session_id`'s return value as a session-storage lookup key. Attacker cost is trivial — one crafted HTTP request with a guessable Cookie header value, no secrets, no XSS, no victim interaction required. Since shop domains are typically public/enumerable, feasibility is high and the attack is fully repeatable across shops.

### Recommendation
Do not use the deterministic `session.id` (or any predictable value) directly as the bearer cookie value. Instead, generate a cryptographically random, unguessable session identifier (or an HMAC-signed value keyed on `Context.api_secret_key` binding to the actual session, with expiry) to store in the cookie, and verify that signature/binding in `cookie_session_id`/`current_session_id` before trusting the cookie as an identifier for session-store lookups.

### Proof of Concept
```ruby
# test/utils/session_utils_test.rb (new test)
def test_offline_cookie_session_id_is_forgeable_from_public_shop_domain
  ShopifyAPI::Context.stubs(:embedded?).returns(false)

  victim_shop = "victim-shop.myshopify.com"
  forged_cookie_value = "offline_#{victim_shop}" # attacker computes this without any secret

  cookies = { ShopifyAPI::Auth::Oauth::SessionCookie::SESSION_COOKIE_NAME => forged_cookie_value }

  # No HMAC/signature check performed; attacker-chosen value is returned verbatim
  returned_id = ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)

  assert_equal(forged_cookie_value, returned_id)
  assert_equal(ShopifyAPI::Auth::Session.from(
    shop: victim_shop,
    access_token_response: ShopifyAPI::Auth::Oauth::AccessTokenResponse.from_hash({ "access_token" => "shpat_victim" }),
  ).id, returned_id) # demonstrates the forged cookie collides with the victim's real session ID
end
```
This confirms `current_session_id` performs no cryptographic verification and returns an attacker-supplied, publicly-derivable string identical to the victim's real session ID, which a host app would use to fetch the victim's stored access token.

        def current_session_id(shopify_id_token, cookies, online)
          if Context.embedded?
            if shopify_id_token

#### Cookie
Cookie based authentication is not supported for embedded apps due to browsers dropping support for third party cookies due to security concerns. Non-embedded apps are able to use cookies for session storage/retrieval.

For *non-embedded* apps, you can pass the cookies into:
 - `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, true)` for online (user) sessions or
 - `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)` for offline (store) sessions.
