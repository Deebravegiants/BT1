### Title
Webhook Shop Identity Not Bound to HMAC Signature Enables Cross-Tenant Webhook Spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable payload from the raw request body only, while the `shop` (and `topic`, `webhook_id`, `api_version`) values are taken unverified from HTTP headers. `Registry.process` validates the HMAC and then trusts `request.shop` for dispatch, without that value ever being bound to the signature. Any user who can obtain one valid `(body, hmac)` pair signed with the app's shared `api_secret_key` — which every merchant who installs the app naturally receives via their own webhook deliveries — can replay that pair with an arbitrary `shop-domain` header and have it accepted as authentic for a different shop.

### Finding Description
The webhook signature is validated via `Utils::HmacValidator.validate(request)`, which calls `request.to_signable_string` to build the signed message: [1](#0-0) 

```ruby
sig { override.returns(String) }
def to_signable_string
  @raw_body
end
```

Only `@raw_body` is part of the signable string. `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from headers with no cryptographic binding: [2](#0-1) 

The HMAC check happens in `Registry.process`, and immediately afterward `request.shop` (an unauthenticated header value) is handed to the app's webhook handler as the tenant identity: [3](#0-2) 

```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
```

The equality that should hold is: `shop asserted in HMAC-signed payload == shop the handler acts on`. Instead, the gem only verifies `HMAC(secret, raw_body) == received_hmac`; the `shop` header is never included in that computation, so the check actually enforces `HMAC(secret, raw_body) == received_hmac` while the handler acts on `headers["shopify-shop-domain"]`, an independent, unauthenticated field.

Because Shopify apps use a single `api_secret_key`/`client_secret` shared across every merchant installation, any merchant who installs the app is a valid, unprivileged recipient of real webhooks signed with that same secret. Such a merchant can:
1. Receive a legitimate webhook for their own shop (e.g., an `app/uninstalled` or GDPR webhook whose body carries no shop-specific data beyond what they already know), obtaining a valid `(raw_body, hmac)` pair.
2. Replay that exact body and HMAC to the target application's public webhook endpoint, substituting the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header with a victim shop's domain.
3. `Utils::HmacValidator.validate(request)` returns `true` because it only checks the body against the secret, and `Registry.process` dispatches the handler with `shop: <victim shop>`.

This breaks the identity binding between the authenticated bytes (body) and the tenant identifier (`shop`) that the host application relies on to attribute the event.

### Impact Explanation
This qualifies as Critical — cross-tenant access: a merchant using the app can forge webhook events that the host application attributes to a different merchant's shop, despite the HMAC check passing. Depending on how the host app uses `WebhookMetadata#shop` (e.g., updating per-shop billing state, disabling a shop's access, deleting shop data on `shop/redact` style webhooks, or triggering session/token invalidation), this can lead to cross-tenant data corruption or unauthorized actions against a shop the attacker does not own.

### Likelihood Explanation
Likelihood is moderate: the attacker doesn't need the `api_secret_key` directly — only to be a legitimate (even trial) installer of the app to receive one authentically-signed webhook, then replay it with a modified header at the app's public webhook receiver endpoint, which is by design reachable from the internet.

### Recommendation
Include `shop` (and ideally `topic`/`webhook_id`) in the HMAC-signed payload verification, or otherwise cryptographically bind the header-derived `shop` value to the signed body (e.g., by having the host verify the resolved `shop`'s registered webhook secret matches, or by requiring library consumers to cross-check the `shop` against a known/expected installation before trusting `WebhookMetadata#shop`). At minimum, document clearly in `lib/shopify_api/webhooks/request.rb` and `registry.rb` that `shop`/`topic`/`webhook_id` headers are unauthenticated relative to the HMAC and must not be trusted for tenant attribution without additional verification.

### Proof of Concept
1. Install the target app on shop `attacker.myshopify.com` and capture a legitimate webhook delivery: raw body `B` and header `X-Shopify-Hmac-Sha256: H` (valid for `HMAC(secret, B) == H`), where `B`'s JSON content contains no shop-identifying fields relevant to the handler's logic (e.g. a generic ping/compliance webhook).
2. Send a POST to the app's webhook endpoint with:
   - Body: `B` (unchanged)
   - Header `X-Shopify-Hmac-Sha256: H` (unchanged)
   - Header `X-Shopify-Shop-Domain: victim.myshopify.com` (changed)
   - Header `X-Shopify-Topic`: original topic
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` — [4](#0-3)  — which returns `true` because only `B` is checked.
4. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", ...)` — [5](#0-4)  — and the host application processes the event as if it originated from `victim.myshopify.com`, despite the attacker never having any relationship with that shop.
