### Title
Webhook `shop` identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, deliberately excluding the `shopify-shop-domain` header from the HMAC-signed material. `ShopifyAPI::Webhooks::Registry.process` uses this signable string to validate authenticity, then trusts `request.shop` — taken from the unauthenticated header — as the tenant identity passed to the app's handler. Compare this with `ShopifyAPI::Auth::Oauth::AuthQuery#to_signable_string`, which explicitly includes `shop` in the signed string, binding the shop claim to the signature for OAuth callbacks. The webhook path has no equivalent binding.

### Finding Description
The equality that should hold is: `shop value verified by the signature == shop value acted on by the handler`. For webhooks this equality is broken.

`Webhooks::Request#to_signable_string` only returns `@raw_body`: [1](#0-0) 

`Webhooks::Request#shop` is read straight from an attacker-controllable HTTP header with no cryptographic tie to the HMAC: [2](#0-1) 

`Utils::HmacValidator.validate`/`validate_signature` only checks `verifiable_query.to_signable_string` (i.e., the raw body) against the received HMAC — it never considers `shop`: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately forwards the unauthenticated `request.shop` to the handler as the tenant identity: [4](#0-3) 

By contrast, the OAuth callback flow explicitly folds `shop` into the signed string, proving the library's own authors know how to bind an identity claim to an HMAC when it matters: [5](#0-4) 

Because the webhook signature covers only body bytes, any body/HMAC pair that was legitimately signed by Shopify for the attacker's own shop remains valid HMAC-wise even after the `x-shopify-shop-domain` (or `shopify-shop-domain`) header is swapped to a different, victim shop. `Utils::HmacValidator.validate` will report success, and `Registry.process` will hand `WebhookMetadata.new(shop: "<victim-shop>", body: <attacker-controlled-but-Shopify-signed-JSON>, ...)` to the app's handler as if it genuinely originated from the victim tenant.

### Impact Explanation
An attacker who installs the app on their own shop (a normal, unprivileged action available to anyone) can generate genuinely-signed webhook bodies for topics they control (e.g. `orders/create`, `customers/update`, app-specific topics), then replay the exact body/HMAC pair to the app's webhook endpoint with the shop header changed to a victim's `myshopify.com` domain. Any handler that trusts `data.shop` to select the tenant record to update (a documented, intended usage per `docs/usage/webhooks.md`) will apply attacker-controlled data under the victim's tenant identity — a cross-tenant data integrity/injection issue that breaks the identity binding the gem is otherwise careful to enforce in `AuthQuery`.

### Likelihood Explanation
Likelihood is bounded by the fact that the attacker needs at least one genuinely-signed body for some topic (trivially obtainable by installing the app on any shop they control and triggering an event) and must be able to reach the app's public webhook endpoint directly (bypassing Shopify's delivery infrastructure), which is generally possible since the endpoint is a normal HTTP route with no additional binding to Shopify's IP ranges enforced by this gem.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) claim in the material verified against the HMAC, or otherwise cryptographically bind the shop identity to the signed payload before it is handed to `WebhookMetadata`, mirroring the approach already used in `Auth::Oauth::AuthQuery#to_signable_string`.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and registers a webhook (e.g. `orders/create`).
2. Attacker triggers the event; Shopify sends a genuinely signed webhook: body `B`, header `x-shopify-hmac-sha256: H = HMAC(secret, B)`, header `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker captures this request (any tool intercepting their own traffic) and replays it to the app's webhook endpoint, changing only `x-shopify-shop-domain` to `victim-shop.myshopify.com`, keeping `B` and `H` unchanged.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: ...)` is built; `Utils::HmacValidator.validate` recomputes HMAC over `B` only, matches `H`, and returns `true` (`lib/shopify_api/utils/hmac_validator.rb:12-31`, `lib/shopify_api/webhooks/request.rb:35-38`).
5. `Registry.process` invokes the app handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)` (`lib/shopify_api/webhooks/registry.rb:188-200`), causing the app to process attacker-controlled data under the victim tenant's identity.
