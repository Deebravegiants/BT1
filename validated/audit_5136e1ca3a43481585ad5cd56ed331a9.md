### Title
Webhook `shop`, `topic`, and `webhook_id` headers are not bound by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, while `#shop`, `#topic`, `#webhook_id`, and `#api_version` are read straight from unauthenticated HTTP headers [1](#0-0) . `Registry.process` validates only the HMAC-over-body and then blindly trusts these header-derived fields when building `WebhookMetadata` for the app's handler [2](#0-1) . Because the HMAC secret (`Context.api_secret_key`) is the app's single `client_secret` shared across every merchant that has installed the app — not a per-shop secret — any installed merchant can capture one legitimately Shopify-signed `(body, hmac)` pair from their own store's webhook traffic and replay it to the app's webhook endpoint with a forged `x-shopify-shop-domain` (and/or `x-shopify-topic`) header pointing at a different tenant.

### Finding Description
The identity binding that should hold is:
`shop_header == shop_authenticated_by_hmac`

In this gem, however:
- `HmacValidator.validate` recomputes the signature only over `verifiable_query.to_signable_string` [3](#0-2) .
- For webhooks, `to_signable_string` is exactly `@raw_body` [4](#0-3) , so the HMAC proves only "this body was signed with `api_secret_key`" — it says nothing about which shop or topic the body belongs to.
- `#shop`, `#topic`, `#webhook_id`, `#api_version` come straight from `shopify_header(...)`, i.e., attacker-controlled HTTP headers on the inbound request [5](#0-4) .
- `Registry.process` checks `Utils::HmacValidator.validate(request)` and, once it passes, forwards `request.shop`, `request.topic`, and `request.webhook_id` straight into `WebhookMetadata` handed to the app's handler with no cross-check that these values were actually the ones Shopify associated with that signed body [2](#0-1) .

`api_secret_key` is the app's `client_secret`, which is identical for every shop that has the app installed (it is not shop-specific). Consequently, a merchant that has legitimately installed the app (an "unprivileged internet user" relative to other tenants of the same app) can:
1. Trigger a real webhook delivery to their own endpoint (e.g., `orders/create`) and capture the genuine `(raw_body, x-shopify-hmac-sha256)` pair Shopify sent them.
2. Replay that exact body and HMAC to the app's webhook endpoint, but with `x-shopify-shop-domain` (and optionally `x-shopify-topic`/`x-shopify-webhook-id`) rewritten to point at a victim shop.
3. `HmacValidator.validate` still succeeds, because it only checks the body against the shared secret, never the shop header.
4. `Registry.process` invokes the app's handler with `WebhookMetadata(shop: "<victim-shop>.myshopify.com", topic: ..., body: <attacker-supplied-but-genuinely-signed>, ...)`.

If the host application uses `WebhookMetadata#shop` to select or mutate per-tenant state (a common pattern for webhook handlers, e.g., "look up victim's session/store and update order data"), this results in cross-tenant data injection/corruption using a signature that was never bound to that tenant.

### Impact Explanation
This breaks the tenant isolation boundary the HMAC is meant to enforce: authentication of "this body came from Shopify for our app" is silently conflated with "this body belongs to shop X," when only the former is actually verified. Under the accepted impact categories this constitutes **cross-tenant access** (Critical), since one merchant of the app can cause the app to process/attribute another merchant's webhook data under their identity.

### Likelihood Explanation
Medium-to-High. It only requires being a legitimate, unprivileged customer/merchant of the target app (no leaked secrets, no privileged account, no TLS interception) — installing the app and triggering any webhook is normal, self-service behavior. The replay itself is a trivial HTTP request with rewritten headers, since the signature check never inspects them.

### Recommendation
Include the tenant-identifying headers (`shop-domain`, `topic`, and ideally `webhook-id`/`api-version`) in the signable content used for HMAC verification, or otherwise cryptographically bind them (e.g., verify `shop` against a per-shop stored secret/session rather than the shared `api_secret_key`, or require the host application to independently confirm the shop is one it has an active session for before trusting webhook attribution). At minimum, document that `WebhookMetadata#shop`/`#topic` are NOT authenticated by the HMAC and must not be trusted for tenant selection without additional verification.

### Proof of Concept
```ruby
# Attacker installs the app on their own shop "attacker.myshopify.com"
# and captures a real Shopify webhook delivery to their endpoint:
raw_body = '{"id":1,"note":"hello"}'
real_hmac = <captured x-shopify-hmac-sha256 header from Shopify's genuine delivery>

# Attacker replays the exact same (body, hmac) to the app's webhook endpoint,
# but swaps the shop-domain header to target a different, victim tenant:
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => real_hmac,          # unchanged, still valid: only signs raw_body
  "x-shopify-shop-domain" => "victim-shop.myshopify.com",  # forged, not covered by HMAC
  "x-shopify-webhook-id" => "attacker-chosen-id",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) returns true (body+secret match),
#    handler is invoked with WebhookMetadata(shop: "victim-shop.myshopify.com", ...)
