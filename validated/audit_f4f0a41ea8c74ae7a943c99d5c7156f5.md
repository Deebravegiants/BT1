### Title
`TokenExchange.exchange_token` sends the app's `client_secret` to a host derived from the JWT `dest` claim without domain validation, unlike sibling OAuth flows - ([File: lib/shopify_api/auth/token_exchange.rb])

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` derives the request target host for the token-exchange call directly from the session token's `dest` claim (`jwt_payload.shop`) and never runs it through `ShopifyAPI::Utils::ShopValidator.sanitize!`, even though every other credential-bearing flow in the same file (`migrate_to_expiring_token`) and in `ClientCredentials.client_credentials` now enforces that validation.

### Finding Description
`exchange_token` builds `dest_shop = jwt_payload.shop` [1](#0-0)  and immediately uses it, unsanitized, to construct the session/host that receives the app's `client_secret`: [2](#0-1) 

`JwtPayload#shop` performs no domain-format validation - it only strips a literal `"https://"` prefix from the `dest` claim: [3](#0-2) 

`HttpClient#initialize` then builds the outbound request URL directly from `session.shop`: [4](#0-3) 

Contrast this with `migrate_to_expiring_token` in the very same module, which explicitly validates the shop before using it to build the session/host: [5](#0-4) 

and `ClientCredentials.client_credentials`, which does the same: [6](#0-5) 

The `ShopValidator` module (added in 16.3.0 specifically to reject `attacker.example`/similar look-alike domains and enforce `TRUSTED_SHOPIFY_DOMAINS`) exists precisely to close this class of host-binding bug: [7](#0-6)  — but it was never wired into `exchange_token`.

The binding that should hold is: `host that receives client_secret == a validated Shopify-owned domain`. Currently the equality actually enforced is only `aud claim == Context.api_key` [8](#0-7) , with no constraint tying `dest` to a `myshopify.com`/`myshopify.io`/`spin.dev`/`shop.dev` suffix.

### Impact Explanation
Because the JWT is signed with `Context.api_secret_key` (a secret shared only between the app and Shopify), an unprivileged internet user cannot forge an arbitrary `dest` value without already possessing that secret. This significantly limits practical exploitability. However, this is a latent, exploitable-if-source-of-token-is-compromised gap in defense-in-depth: this file's own sibling functions (`migrate_to_expiring_token`, `ClientCredentials`) demonstrate that the maintainers consider unvalidated `shop`/`dest`-derived hosts a real risk worth mitigating via `ShopValidator.sanitize!`. `exchange_token` is the one OAuth-secret-bearing path left without it, so if any means exists to influence the `dest` claim of a token that still passes `aud` verification (e.g., ambiguous/legacy issuers, non-Shopify token issuers if `iss`/`dest` binding is ever loosened, or embedding contexts where `dest` isn't strictly re-validated by callers), the app's `client_secret` and code exchange could be sent to an attacker-influenced host — an SSRF-with-credentials pattern (High per the rubric).

### Likelihood Explanation
Low-to-moderate on its own given the current JWT signature requirement, but the inconsistency with `migrate_to_expiring_token`/`ClientCredentials` in the same module indicates this is a real regression/gap rather than a deliberate design choice, and it is the most credential-sensitive of the three flows (it's the primary OAuth path for embedded apps using session tokens).

### Recommendation
Apply the same `Utils::ShopValidator.sanitize!(dest_shop)` validation in `exchange_token` before constructing `shop_session`, exactly as done in `migrate_to_expiring_token` and `ClientCredentials.client_credentials`, so the host that receives `client_secret` is always constrained to `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`.

### Proof of Concept
Not independently reproducible as a concrete unprivileged-attacker exploit within this gem alone, because forging the `dest` claim requires the app's `client_secret` (a privileged credential explicitly out of scope). The finding is a code-consistency/defense-in-depth gap: `exchange_token`'s host-binding validation is weaker than its sibling functions in the identical file, contradicting the stated purpose of `ShopValidator` (rejecting attacker-controlled/look-alike domains, per `test/utils/shop_validator_test.rb` cases like `test_rejects_attacker_controlled_domain` and `test_rejects_similar_looking_domain`).
