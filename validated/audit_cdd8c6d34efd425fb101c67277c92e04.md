Audit Report

## Title
Fee-on-transfer / non-standard ERC20 tokens cause XCM value inflation in `ERC20Transactor::withdraw_asset_with_surplus` and custody-account drain in `deposit_asset_with_surplus` - (File: `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`)

## Summary
`ERC20Transactor`, which bridges XCM's `TransactAsset` interface to arbitrary ERC20 contracts hosted on `pallet-revive`, issues a Solidity `transfer(to, value)` call and treats a `true` boolean return as proof that exactly `amount` moved, without ever reading actual on-chain balances before/after the call. For fee-on-transfer, burn-on-transfer, or rebasing ERC20 tokens, the real amount credited to/debited from the custody account (`TransfersCheckingAccount`) can diverge from `amount`, while the XCM holding register still records the full, requested `amount`.

## Finding Description
In `withdraw_asset_with_surplus`, the transactor calls `IERC20::transferCall` for `amount` from `who` to the checking account, and on a `true` return unconditionally mints `AssetsInHolding::new_from_fungible_credit(..., Erc20Credit(amount))` [1](#0-0) . If the token deducts a fee or otherwise fails balance-additivity, `TransfersCheckingAccount` receives less than `amount`, yet the returned holding claims the full amount, which can subsequently be deposited/settled elsewhere as backed value.

The mirrored `deposit_asset_with_surplus` transfers `amount` out of the checking account to the beneficiary and, on `Ok(true)`, treats the operation as fully settled with no verification the beneficiary received `amount` [2](#0-1) . Any shortfall due to a fee-on-transfer token becomes an unrecoverable, unaccounted loss from the shared custody account.

This is wired into the live runtime: `ERC20Transactor` is part of `AssetTransactors` in `asset-hub-westend`'s `XcmConfig::AssetTransactor`, alongside `FungibleTransactor`, `FungiblesTransactor`, `ForeignFungiblesTransactor`, and `UniquesTransactor` [3](#0-2) , and is invoked by `xcm_executor::Config::AssetTransactor` for `WithdrawAsset`/`DepositAsset` handling [4](#0-3) . `ERC20Matcher` matches *any* local `AccountKey20` location purely by shape (no registry/whitelist check) [5](#0-4) , meaning any contract deployed via `pallet-revive` (a permissionless action) is automatically matched and transactable through this path.

By contrast, `pallet-assets::do_transfer`, used by FRAME-native transactors, returns the *actual* amount moved rather than assuming the requested amount [6](#0-5) , and `fungible::transfer` performs balance mutations directly under the pallet's control with no external contract call whose side effects can diverge [7](#0-6) . `ERC20Transactor` is architecturally distinct in that it performs an external, arbitrary-contract call and trusts the requested amount instead of measuring the actual balance delta.

## Impact Explanation
An attacker can deploy a fee-on-transfer/non-standard ERC20 contract via `pallet-revive`, which is automatically matched by `ERC20Matcher` since it checks only the `AccountKey20` location shape, not a registry. Executing an XCM program with `WithdrawAsset` on such a token yields a holding register recording the full requested `amount`, while `TransfersCheckingAccount` actually receives less. If this inflated holding is subsequently deposited/settled as backed value (e.g., via `DepositAsset` to another location, or exchanged), it constitutes value inflation relative to what the custody account actually holds. Symmetrically, repeated `deposit_asset_with_surplus` calls against such a token can drain more from `TransfersCheckingAccount` than the aggregate amounts recorded as consumed by the XCM executor. Both paths are triggerable by an unprivileged user with no governance or trusted-role involvement.

## Likelihood Explanation
Deploying arbitrary contracts on `pallet-revive` is permissionless, and `ERC20Matcher`'s `IsLocalAccountKey20`/`AccountKey20ToH160` checks are purely structural, with no asset registration or allow-list gate visible at the transactor/matcher level. `ERC20Transactor` is concretely wired into `asset-hub-westend`'s `AssetTransactors` tuple and `xcm_executor::Config`, making the path reachable through ordinary `pallet_xcm::execute`/XCM message processing by any signed account. This makes exploitation feasible and repeatable, limited only by the attacker's ability to fund gas/storage deposits for the ERC20 transfer calls.

## Recommendation
In both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus`, measure the counterparty's actual on-chain ERC20 balance before and after the `bare_call` (or otherwise derive the real transferred amount), and use that observed delta — not the requested `amount` and not merely the boolean return value — to construct the `AssetsInHolding` credit/debit and to determine settlement success.

## Proof of Concept
1. Deploy a fee-on-transfer ERC20 contract via `pallet-revive` (e.g., charging 1% on every `transfer`), which is permissionless.
2. Its `AccountKey20` location is automatically matched by `ERC20Matcher` without any registry step, per `IsLocalAccountKey20`/`AccountKey20ToH160`.
3. Submit an XCM program via `pallet_xcm::execute` containing `WithdrawAsset` for `amount` of this token from an account holding it; `ERC20Transactor::withdraw_asset_with_surplus` transfers `amount` to `TransfersCheckingAccount` (which actually receives `amount * 0.99`), but returns `AssetsInHolding` crediting the full, un-discounted `amount`.
4. Chain a `DepositAsset` instruction that settles this holding as `amount` (not `amount * 0.99`) elsewhere, creating a measurable 1% discrepancy between the custody account's real ERC20 balance and the system's recorded backing; repeatable to compound the shortfall.

/// `Contains<Location>` implementation that matches locations with no parents,
/// a `PalletInstance` and an `AccountKey20` junction.
pub struct IsLocalAccountKey20;
impl Contains<Location> for IsLocalAccountKey20 {
	fn contains(location: &Location) -> bool {
		matches!(location.unpack(), (0, [AccountKey20 { .. }]))
	}
}

/// Fallible converter from a location to a `H160` that matches any location ending with
/// an `AccountKey20` junction.
pub struct AccountKey20ToH160;
impl MaybeEquivalence<Location, H160> for AccountKey20ToH160 {
	fn convert(location: &Location) -> Option<H160> {
		match location.unpack() {
			(0, [AccountKey20 { key, .. }]) => Some((*key).into()),
			_ => None,
		}
	}

	fn convert_back(key: &H160) -> Option<Location> {
		Some(Location::new(0, [AccountKey20 { key: (*key).into(), network: None }]))
	}
}

/// [`xcm_executor::traits::MatchesFungibles`] implementation that matches
/// ERC20 tokens.

	MatchedConvertedConcreteId<H160, u128, IsLocalAccountKey20, AccountKey20ToH160, TryConvertInto>;
