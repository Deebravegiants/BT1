### Title
Duplicate `address(0)` in `erc20TokenAddresses` causes `handleOut` to double-credit a single real ETH balance delta - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`EmporiumUpgradeable.runAction` snapshots `balancesBefore`/`balancesAfter` once for the whole `erc20TokenAddresses` array before running any `handleOut` calls, and computes `balanceChange` per index independently. If `address(0)` appears at two indices, both indices read the *same* `balancesBefore[i]`/`balancesAfter[i]` pair for the single real ETH delta and each independently produce a positive `balanceChange`, so `handleOut` is invoked twice and pays out ETH twice for one real inflow.

### Finding Description
Broken equality: `sum(handleOut outUtxo.amount for all i where erc20TokenAddresses[i]==address(0))` should equal the single real ETH balance delta Emporium experienced, but it does not when the address is duplicated.

Trace:
- `balancesBefore = getBalancesForArray(circomData.erc20TokenAddresses)` and later `balancesAfter = getBalancesForArray(...)` are taken once, at fixed points, for the *entire* array [1](#0-0) [2](#0-1) . Since `getERC20OrETHBalance(address(0))` just reads `address(this).balance` at call time, if index 0 and index 5 both equal `address(0)`, `balancesBefore[0]==balancesBefore[5]` and `balancesAfter[0]==balancesAfter[5]` [3](#0-2) .
- The per-index loop computes `balanceChange = balancesAfter[i]-balancesBefore[i]`, optionally adjusted by `deltaAmountChanges[i]` (attacker-controlled, independently settable per index), then calls `handleOut(balanceChange, circomData, i)` [4](#0-3) .
- `handleOut` only checks `balanceChange <= 0` to skip; it never re-checks the *actual live* Emporium ETH balance against what has already been paid out in a prior loop iteration, and it unconditionally calls `transferERC20TokenOrETH(erc20TokenAddresses[i], msg.sender, uint256(balanceChange))` [5](#0-4) .
- With `deltaAmountChanges[0]` and `deltaAmountChanges[5]` set independently (e.g. one negative to represent "funds moved into Emporium" and one left at 0), the attacker can make both index-0 and index-5 `balanceChange` values independently positive from the *same* underlying real ETH movement, so `handleOut` runs twice, each transferring `uint256(balanceChange)` wei to `msg.sender` (the Hinkal contract) and each returning its own `outUtxo` of that amount with `erc20Address = address(0)`.
- No check anywhere rejects duplicate entries in `erc20TokenAddresses`: `dimensionsCheck`, `checkOnchainCreation`, and `performHinkalChecks` in `HinkalHelper.sol` only validate array *lengths* and per-index constraints, never uniqueness of `erc20TokenAddresses` [6](#0-5) [7](#0-6) .
- Back in `Hinkal.sol`, the post-transact balance-equation check aggregates `utxoAmount` by matching `utxoSet[j].erc20Address == circomData.erc20TokenAddresses[i]` — this sums *both* duplicate UTXOs into `utxoAmount` for **each** of index 0 and index 5, and compares against `balanceDif` computed from Hinkal's own live balance (which really did receive double ETH from Emporium) [8](#0-7) . Because both sides of the check are inflated by the same duplication, the `require` passes for both index 0 and index 5 — the existing invariant does not detect the double-issuance because it is self-consistent under duplication.
- The circuit's `inTotal + amountChanges === outTotal` constraint operates per token-slot index; it has no cross-index uniqueness constraint on `erc20TokenAddresses`, so an attacker (fully controlling their own proof/witness generation) can supply valid, internally consistent output commitments for both index-0 and index-5 slots.

Net effect: for one genuine ETH inflow into Emporium of amount `D`, two `UTXO(amount=D, address(0), ...)` are produced and passed to `Hinkal.transact`'s insertion logic instead of one — double the ETH value is credited into the shielded UTXO set relative to the real, singular balance delta.

### Impact Explanation
This is unbacked issuance of shielded value: the shielded pool receives credit for two ETH UTXOs of amount `D` each from a single real `D` ETH balance change in Emporium, i.e., minting shielded value without backing. If Emporium holds any residual/parked ETH (dust from other in-flight actions, previously stuck funds, or attacker-seeded value via other ops in the same `stack.ops` batch), the second `handleOut` transfer can succeed against that residual balance, physically draining real ETH out of Emporium while crediting the attacker with 2x UTXO value for 1x real economic event. This matches the Critical category: minting shielded value without backing / direct theft of protocol-held funds.

### Likelihood Explanation
The attacker is a fully unprivileged actor: they control `CircomData.erc20TokenAddresses` (can place `address(0)` at two indices), `deltaAmountChanges` (via the external action's parameters), and their own proof generation for their own UTXOs, and can craft `stack.ops` to produce a genuine ETH balance increase in Emporium (e.g. a swap that yields ETH). No privileged role, whitelisted relay, or victim key is required — only that `runAction` be reached through a normal `Hinkal.transact` call for an Emporium external action, which is standard usage. The attack is repeatable per transaction, limited only by how much residual ETH balance Emporium happens to hold or how much the attacker can seed via their own ops.

### Recommendation
De-duplicate `erc20TokenAddresses` before processing (revert if any address appears more than once), or track and re-derive the live contract balance immediately before each `handleOut` call (rather than relying on a single stale `balancesAfter` snapshot for all indices) so that a second `handleOut` for the same underlying token/ETH cannot claim a balance delta already consumed by an earlier iteration in the same call.

### Proof of Concept
Foundry test plan:
1. Deploy `EmporiumUpgradeable`, `Hinkal`, `HinkalHelper` with a mock `IHinkalWallet`/endpoint that, when called via `op.callData`, performs a real action increasing Emporium's ETH balance by `D` (e.g., unwrap WETH held by Emporium into ETH, or a mock swap endpoint that sends `D` ETH to Emporium via `.call`).
2. Craft `circomData.erc20TokenAddresses = [address(0), tokenA, tokenB, tokenC, tokenD, address(0)]` (index 0 and index 5 both `address(0)`), with `deltaAmountChanges[0]` and `deltaAmountChanges[5]` set independently (e.g. `deltaAmountChanges[0] = 0`, `deltaAmountChanges[5] = 0`, both non-negative so no subtraction occurs and both indices read the identical raw `balancesAfter[i]-balancesBefore[i] = D`).
3. Call `runAction` (through `Hinkal.transact` with a valid proof for this witness, or directly against `EmporiumUpgradeable` if `onlyAllowedRecipient` allows a test harness) and capture the returned `UTXO[] utxoSet`.
4. Assert: `utxoSet` contains two entries with `erc20Address == address(0)` and `amount == D` each — i.e. total credited amount `== 2*D`.
5. Assert the broken equality: real Emporium/Hinkal ETH balance delta for this action `== D`, while `sum(outUtxo.amount for erc20Address==address(0)) == 2*D`, demonstrating `2*D != D`.

    function handleOut(
        int256 balanceChange,
        CircomData calldata circomData,
        uint256 i
    ) internal returns (UTXO memory outUtxo) {
        // total change can be less than zero if there was some balance before the call -> that's why we have <=
        if (balanceChange <= 0) {
            return outUtxo;
        }

        transferERC20TokenOrETH(
            circomData.erc20TokenAddresses[i],
            msg.sender,
            uint256(balanceChange)
        );

        outUtxo = UTXO(
            uint256(balanceChange),
            circomData.erc20TokenAddresses[i],
            circomData.stealthAddressStructure,
            circomData.timeStamp
        );
    }
