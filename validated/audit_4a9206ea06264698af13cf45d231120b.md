Based on my research, the strongest concrete analog to the `Gateway.query()` missing-validation bug class exists in `src/backend/user_status.rs`'s `request` function.

### Title
Missing Validation of `qr_code.user_data_hash` Length/Content Allows Bypass of User-Data Verification - (File: `src/backend/user_status.rs`)

### Summary
`Gateway.query()` fails to validate that critical parameters (`dstChainId`, `height`, `slot`, `message`) are non-zero/non-empty before use, allowing malformed input to be silently accepted. The analog in orb-core is in `backend::user_status::request`, where the `user_data_hash` field taken from the scanned user QR code is checked only for presence (`Option::is_some`), never for content validity (length, format, or emptiness) before being passed into `user_data.verify(user_data_hash)`.

### Finding Description
In the "new" QR-code format branch, the code only guards against a missing hash: [1](#0-0) 
There is no check that `user_data_hash` itself is a well-formed, non-empty, correctly-sized digest before it is handed to `user_data.verify()`. `user_data_hash` originates directly from `qr_scan::user::Data::user_data_hash`, which is populated from `decode_qr(code)` parsing an attacker/user-controlled QR code string: [2](#0-1) 
The struct itself declares this field as an unconstrained `Option<Vec<u8>>`: [3](#0-2) 
Because no length/format constraint is enforced on the orb-core side before calling `verify()`, correctness of this security gate depends entirely on the external `orb_qr_link::UserData::verify` implementation, which is outside this repo's index and could not be inspected to confirm it rejects malformed/empty hash inputs.

### Impact Explanation
If `verify()` does not itself perform strict length/format checks on an attacker-supplied hash (e.g., an empty or truncated byte vector), this creates the same class of issue as the reported `Gateway.query()` bug: an unvalidated field silently passed through to a security-critical check, potentially allowing binding of user-provided identity/app data to a signup session without a properly verified hash — a form of misattributed signup / identity-binding weakness.

### Likelihood Explanation
Likelihood is **uncertain and unverified** — the exploitability hinges entirely on the internal behavior of `orb_qr_link::UserData::verify`, which is an external crate not present in the indexed codebase. Without confirming that `verify()` independently guards against malformed/empty hashes, this cannot be escalated beyond a plausible analog based on the reported bug class.

### Recommendation
Add explicit input validation in `backend::user_status::request` before calling `verify()`: reject `user_data_hash` values that are empty or do not match the expected digest length, mirroring the recommended pattern from the referenced report (explicit `if hash.is_empty() { return Err(...) }`-style guards) rather than relying solely on downstream library behavior.

### Proof of Concept
Not independently confirmed — this analog is speculative pending inspection of `orb_qr_link::UserData::verify`'s internal validation. No proof-of-concept exploit path could be constructed from the orb-core repository alone, since the security boundary is enforced (or not) inside an external, unindexed crate.
