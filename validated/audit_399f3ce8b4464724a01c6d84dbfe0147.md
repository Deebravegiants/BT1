### Title
Webhook `shop` field is not covered by the HMAC signature, allowing shop-domain spoofing in `ShopifyAPI::Webhooks::Registry.process` - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC computed over the request only authenticates the JSON payload, not the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header. `ShopifyAPI::Webhooks::Registry.process` validates that HMAC and then trusts `request.shop` as the identity of the shop the webhook is "from," passing it straight through to the app's handler.

### Finding Description
`Utils::HmacValidator.validate` computes/compares the signature using `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` is defined as just the raw body: [2](#0-1) 

But `shop` is read directly from the (unsigned) header: [3](#0-2) 

`Registry.process` validates the HMAC and then forwards `request.shop` to the app's handler as the authenticated tenant identifier, without any additional binding between the signed body and the shop header: [4](#0-3) 

The gem's own documentation states that `Registry.process` "will verify the request did indeed come from Shopify" and describes `data.shop` as "The shop domain of the webhook" without qualification: [5](#0-4) [6](#0-5) 

This creates a broken identity binding: `shop header value == authenticated shop`, when in fact only `body == HMAC(secret, body)` is verified. Since the `api_secret_key` used to compute the HMAC is a single, per-app secret (not per-shop), any merchant who has installed the app on their own store can obtain a validly-signed webhook body/HMAC pair for their own shop (Shopify sends it to them), then replay that exact body+HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a victim shop that also has the app installed. `Registry.process` will accept it as valid (body HMAC still matches, since HMAC never covered the header) and hand the handler `shop: <victim-shop>` alongside attacker-controlled body content.

### Impact Explanation
This lets an unprivileged app user (any merchant who has installed the same app) forge webhook events attributed to a different tenant (a cross-tenant identity binding bypass). Depending on how the host app's webhook handler uses `data.shop` (e.g. to look up the victim's stored access token/session, to update per-shop billing/subscription state, or to act on the victim's data via mandatory topics like `customers/redact`/`shop/redact`), this can lead to cross-tenant data corruption or actions performed under the wrong shop's identity — satisfying the "cross-tenant access" bar, since the boundary broken is exactly `shop-authenticated-by-signature` vs `shop-header-used-as-identity`.

### Likelihood Explanation
Requires the attacker to control an app installation (any merchant installing the same public app), be able to trigger at least one webhook to themselves, and know/guess a victim's shop domain (often discoverable/public, e.g. `victim.myshopify.com`). No access token, `client_secret`, or elevated privilege is needed — only normal use of the app as a merchant.

### Recommendation
Bind the shop identity to the signed payload. Either:
- Include the shop domain header in the HMAC-signed material (which requires a Shopify-side change since Shopify itself signs only the body), or
- Cross-check `request.shop` against the shop associated with the specific webhook subscription/session expected for that route/topic before invoking the handler, and reject mismatches, or
- Document explicitly (and enforce in `Registry.process`) that `data.shop` is unauthenticated and must be independently verified by the host application against a known, previously-established session before being trusted for any tenant-scoped action.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` and lets it register a webhook (e.g. `orders/create`).
2. Shopify sends attacker a genuine webhook: body `B`, header `X-Shopify-Hmac-Sha256: HMAC(secret, B)`, `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. Attacker replays the exact same body `B` and HMAC header to the app's public webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(secret, B)` — still valid.
5. Handler is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", body: B, ...)`, i.e., the app processes attacker-supplied content as if it originated from the victim shop.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
