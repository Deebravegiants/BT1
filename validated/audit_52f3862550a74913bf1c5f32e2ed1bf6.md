## Title
Malicious order creator can permanently freeze a solver's escrowed compensation by using an unblockable/blacklistable ERC-20 as an order input token - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentGatewayV2`/`ExtrinsicIntents` lets an order creator choose **any** ERC-20 address as an `order.inputs[i].token` with no allowlist or safety check [1](#0-0) . A solver who fills the order delivers real, valuable output assets directly to the beneficiary *before* the source-chain escrow is released [2](#0-1) . Release of that escrow happens later, via `_withdraw()`, which loops over `body.tokens` and calls `IERC20(token).safeTransfer(beneficiary, amount)` for each one, with no isolation between tokens and no try/catch [3](#0-2) . If the malicious creator's input token is (or becomes, e.g. via a pause/blacklist hook they control) unable to transfer to the intended recipient, this call reverts every single time, permanently blocking the whole `_withdraw` invocation — including release of any *other*, legitimate tokens bundled in the same multi-input order — mirroring the reported pattern where a single malicious/broken external asset call blocks liquidation and freezes funds owed to an honest counterparty.

### Finding Description
1. `placeOrder` accepts arbitrary `order.inputs[i].token` addresses supplied by the order creator, transferring/escrowing them with `IERC20(token).safeTransferFrom` and recording the amount per-commitment in `_orders[commitment][token]` [1](#0-0) . There is no vetting of the token's transfer semantics.
2. When a solver fills a cross-chain order, they immediately pay the beneficiary real value (`safeTransferFrom(msg.sender, beneficiary, totalRequired + beneficiaryShare)` or native ETH) and only afterward dispatch a `RedeemEscrow` message meant to release the source-chain escrow to the solver [2](#0-1) .
3. On the source chain, `onAccept` routes `RedeemEscrow`/`RefundEscrow` requests straight into `_withdraw()`, with no per-token error handling [4](#0-3) .
4. `_withdraw()` sets `_filled[body.commitment]` before iterating, then loops over every escrowed token and calls `safeTransfer`; if the malicious token's transfer to the solver (or beneficiary) unconditionally reverts, the whole `_withdraw()` call reverts, undoing state changes in that transaction [3](#0-2) .
5. `EvmHost.dispatchIncoming` catches the `onAccept` failure and simply deletes the request receipt "so it can be retried" [5](#0-4) , but retries are useless when the malicious token is designed to always revert (e.g., an owner-controlled pause/blacklist), so the escrow — and the solver's rightful compensation — is permanently stuck. Because the loop processes *all* tokens in the order atomically, any other legitimate tokens escrowed alongside the malicious one in a multi-input order are frozen too.

This is the same root-cause class as the reported bug: an external call into an asset the malicious party controls, invoked from a critical settlement/liquidation path with no failure isolation, lets that party retroactively brick redemption after already receiving value from an honest counterparty.

### Impact Explanation
An honest solver who has already delivered the full output value to the beneficiary can be permanently denied their escrowed input compensation, a direct, deliberate theft/loss of funds vector. Because `_withdraw` bundles all of an order's input tokens into a single atomic call, other legitimate tokens escrowed in the same order are frozen as collateral damage. This is a concrete, permanent freezing of funds reachable from a single `fillOrder` transaction by an honest relayer/solver acting on a maliciously crafted order.

### Likelihood Explanation
The attack requires only a standard, easily obtained capability: deploying (or using) an ERC-20 with owner-controlled pause/blacklist semantics and placing a normal, unprivileged `placeOrder` call — the same "malicious liquidity provider" capability level as the original report (a party providing an asset into a shared settlement flow who can later render that asset's transfer function permanently reverting). No governance, admin, or protocol-level privilege is needed.

### Recommendation
Isolate per-token transfers in `_withdraw` so a single failing token cannot block release of other tokens in the same order (e.g., wrap each `safeTransfer` in a try/catch and record a per-token "stuck" state that can be swept separately, or use a pull-based withdrawal pattern per token). Additionally, consider requiring solvers/relayers to be able to identify and skip provably non-transferable tokens before committing to fill an order with them as inputs.

### Proof of Concept
1. Attacker deploys `EvilToken`, a standard ERC20 with an owner-controlled `blacklist(address)` that makes `transfer`/`transferFrom` to a blacklisted address always revert.
2. Attacker calls `placeOrder` with `order.inputs = [{token: EvilToken, amount: X}]` and a legitimate `order.output` (e.g., requesting USDC), following the normal flow in `evm/src/apps/IntentGatewayV2.sol` `placeOrder` [1](#0-0) .
3. An honest solver calls `fillOrder`, which immediately transfers the requested USDC to the attacker's beneficiary address, then dispatches `RedeemEscrow` [2](#0-1) .
4. Before the `RedeemEscrow` message is delivered/relayed, the attacker calls `EvilToken.blacklist(solver)`.
5. When the relayer delivers the `RedeemEscrow` message, `onAccept` → `_withdraw` attempts `IERC20(EvilToken).safeTransfer(solver, amount)`, which reverts every time [3](#0-2) . `EvmHost.dispatchIncoming` deletes the receipt to allow a retry [5](#0-4) , but every retry fails identically — the solver's escrowed compensation (and any other tokens bundled in the same order) is permanently frozen while the attacker already received the solver's legitimate output tokens.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
