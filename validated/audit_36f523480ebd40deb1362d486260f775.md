### Title
Webhook HMAC signs only the request body, not the `shop-domain`/`topic` headers, allowing HMAC-valid webhooks to be replayed with a forged tenant identity - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes and validates its HMAC over the raw body only, while `topic`, `shop`, `api_version`, and `webhook_id` are all read from unauthenticated HTTP headers. `Registry.process` accepts any request whose body/HMAC pair is valid for the app's shared `api_secret_key`, then dispatches to the handler using the unauthenticated `shop` header as the tenant identity, without checking that this shop matches the content of the signed body.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop`, `topic`, `api_version`, and `webhook_id` are pulled straight from headers that are never fed into the HMAC computation: [2](#0-1) 

`Registry.process` validates the HMAC over the body, then immediately trusts `request.shop` (and `request.topic`) to build the `WebhookMetadata` handed to the app's handler: [3](#0-2) 

Because the `api_secret_key` is shared across every shop that installs the app, `HMAC(body, secret)` is identical regardless of which merchant the body actually belongs to. This breaks the binding `shop asserted in header == shop bound by HMAC`: the gem proves "this body was produced by our app's key" but never proves "this body belongs to the shop named in this header."

### Impact Explanation
An unprivileged installer of the app (Shop A) can capture one of their own genuine webhook deliveries (valid body + valid HMAC) and replay that exact HTTP request to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a different, victim merchant's domain (Shop B). `Utils::HmacValidator.validate` still returns `true` because it only checks the body against the secret, and `Registry.process` will hand the handler `WebhookMetadata` claiming `shop: "shopB.myshopify.com"` together with Shop A's payload. Any host application that uses `request.shop`/`data.shop` as the tenant key when writing or reconciling data (a documented, expected usage of this gem's API) will attribute attacker-controlled content to another tenant — a cross-tenant data-integrity/confusion issue.

### Likelihood Explanation
Requires no credentials beyond being a normal, unprivileged app installer capable of receiving one legitimate webhook from their own store and being able to reach the app's public webhook endpoint directly (which is the whole point of a webhook endpoint). No `api_secret_key`, access token, or TLS interception is needed.

### Recommendation
Bind the tenant/topic identity into the signed material, e.g. compute/verify the HMAC over a canonical string that includes `shop-domain` and `topic` in addition to the raw body (or otherwise cryptographically bind the header claims to the payload), and have `Registry.process`/`HmacValidator` reject requests where these fields aren't covered by the signature.

### Proof of Concept
1. App installed on `shopA.myshopify.com`; attacker (merchant of Shop A) receives a real webhook: body `B`, header `X-Shopify-Hmac-Sha256: HMAC(B, secret)`, header `X-Shopify-Shop-Domain: shopA.myshopify.com`.
2. Attacker resends the identical body `B` and HMAC header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: shopB.myshopify.com`.
3. `Utils::HmacValidator.validate(request)` returns `true` (only `@raw_body` is signed) — see `Request#to_signable_string` at `lib/shopify_api/webhooks/request.rb:35-38`.
4. `Registry.process` dispatches to the topic handler with `shop: "shopB.myshopify.com"` and Shop A's body content — `lib/shopify_api/webhooks/registry.rb:198-199` — despite Shop B never having sent this webhook.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
