### Title
Attacker-controlled overcapture wavelength parameter triggers `assert_eq!` panic in `Configuration::parse_wavelength_configuration`, crashing the signup biometric-capture pipeline - ([File: src/plans/biometric_capture/overcapture.rs])

### Summary
When the `Overcapture` signup-extension mode is selected via the QR `parameters` field, the wavelength sub-parameter is parsed with `u8::from_str_radix(_, 8)` and passed straight into `Configuration::new` without range validation. Any parsed value greater than `7` (e.g. QR parameter string `"10"`, which is valid octal notation for decimal `8`) causes `Configuration::parse_wavelength_configuration` to hit an `assert_eq!` that always requires exactly 3 binary digits, panicking instead of failing gracefully.

### Finding Description
The attacker-controlled QR `parameters` capture group (regex `[a-z0-9:]+`) is parsed in `qr_scan::user::Data::from_signup_extension` [1](#0-0)  and stored unvalidated in `SignupExtensionConfig::parameters`. When the mode is `Overcapture`, this string is consumed in `overcapture::Plan::from`:

```
let (wavelength_parameter, duration_parameter) = ... parameters.split_once(':')...
    parse_u8_octal(wavelength, 1) ...
let configuration = Configuration::new(wavelength_parameter, duration_parameter);
``` [2](#0-1) 

`parse_u8_octal` only guards against radix-8 parse *failure* (e.g. digits `8`/`9`), falling back to a default; it does **not** guard against a syntactically valid octal string whose decimal value exceeds 7:
```
fn parse_u8_octal(src: &str, default: u8) -> u8 {
    u8::from_str_radix(src, 8).unwrap_or(default)
}
``` [3](#0-2) 

`Configuration::new` then calls `parse_wavelength_configuration`, which formats the value as a fixed-width 3-bit binary string and asserts its length is exactly 3:
```
fn parse_wavelength_configuration(configuration_value: u8) -> VecDeque<IrLed> {
    let binary_repr = format!("{configuration_value:0>3b}");
    assert_eq!(binary_repr.chars().count(), 3, "Overcapture wavelength parameter needs to be octal (<=3 bit)!");
    ...
}
``` [4](#0-3) 

Any value in `8..=255` (e.g. the attacker QR parameter string `"10"`, `"11"`, ..., `"377"`) parses successfully as octal but produces a `>3`-character binary representation, so the `assert_eq!` fails and the task panics. This code path is reachable directly from `biometric_capture()` in the signup state machine, invoked unconditionally when `SignupMode::Overcapture` is selected:
```
qr_scan::user::SignupMode::Overcapture => {
    tracing::info!("Overcapture extension: activated");
    biometric_capture::overcapture::Plan::from(plan).run(orb).await?
}
``` [5](#0-4) 

No validation exists between QR parsing (`src/plans/qr_scan/user.rs`) and this panic site that would reject an out-of-range wavelength parameter before it reaches capture configuration construction; the only existing guard (`parse_u8_octal`'s `unwrap_or`) is insufficient because it only catches parse errors, not out-of-range-but-parseable octal strings.

### Impact Explanation
A crafted QR code causes an unconditional Rust panic during the biometric-capture phase of signup. Depending on the panic-handling/task-supervision behavior of the broker/agent runtime, this either aborts the current signup's async task (denial of service for that signup) or, if the panic propagates past a catch boundary, can bring down the `biometric_capture` agent/process, which per the question's invariant would "wedge" the signup state machine and could affect subsequent signups on the same orb. This corresponds to a signup-availability/DoS impact rather than data disclosure or identity compromise.

### Likelihood Explanation
Requires the `internal-data-acquisition` feature to be compiled in and both operator and user QR codes to enable the signup extension with `Overcapture` mode — preconditions stated in the question. Given that precondition, the exploit is trivial and fully deterministic: any operator/user QR pair encoding `Overcapture` mode with a wavelength parameter octal-string ≥ `"10"` (decimal 8) reliably triggers the panic on every signup attempt, no timing or race conditions needed. The feature is explicitly gated behind `internal-data-acquisition` (an internal/test build flag) and is not present in production QR parsing when that feature is disabled (`#[cfg(feature = "internal-data-acquisition")]` gates the regex and parsing route in `src/plans/qr_scan/user.rs`), which limits real-world exposure to internal/debug builds only.

### Recommendation
Validate the wavelength parameter range (0–7) immediately after parsing in `overcapture::Plan::from`, returning a safe default (or explicitly failing the extension/signup) instead of passing an unbounded `u8` into `Configuration::new`. Replace the `assert_eq!` in `parse_wavelength_configuration` with non-panicking, fail-closed handling (e.g. clamp to 0–7 or return a `Result`/`Option` and abort just the extension gracefully with a logged/telemetry error), ensuring malformed configuration values cannot panic the capture pipeline. Apply the same bounds check to the analogous octal-parsing/config-construction code in `focus_sweep.rs` and `mirror_sweep.rs`, which follow the identical `u8::from_str_radix(_, 8)` pattern.

2. Integration test driving `MasterPlan::do_signup` (or the `biometric_capture` helper in `src/plans/mod.rs`) with an operator+user QR pair encoding `userid:<uuid>:1::5:10::` (mode Overcapture, wavelength param `"10"`), asserting the signup returns a graceful `Err`/failure result rather than the task/process panicking or hanging.
3. Fuzz `parse_u8_octal`/`Configuration::new` over the full `0..=255` domain, asserting no panics occur for any input (currently fails for `8..=255`).
