### Title
Unvalidated route can append unauthorized token transfers beneath `swap_collateral` authorization - (File: contracts/controller/src/strategies/swap.rs)

### Summary
An unprivileged attacker can craft a swap route that places attacker-controlled code beneath a victim’s `swap_collateral` call. That code can request an unrelated `token.transfer(victim, attacker, amount)` that simulation records as a child authorization and executes when the victim signs the returned authorization tree. [1](#0-0) 

### Finding Description
`swap_collateral` permits arbitrary caller-supplied `swap` bytes and delegates execution to `swap_tokens`. [2](#0-1)  `swap_tokens` authorizes only the controller’s exact input-token transfer and then invokes the configured router under the flash guard, but it does not constrain authorization children or venue calls. [3](#0-2) 

The in-repo reproduction shows the attacker-controlled router invoking a route-selected malicious pool during `execute_strategy`. [4](#0-3)  The malicious pool calls `token.transfer(victim, attacker, WALLET_BALANCE)` even though the wallet token is not protocol collateral. [5](#0-4)  Simulation records that transfer as a child of the victim’s `swap_collateral` authorization. [6](#0-5)  Enforcing mode rejects an honest authorization tree but accepts and executes the theft when the poisoned child is signed. [7](#0-6) 

### Impact Explanation
A signed malicious route can steal arbitrary wallet tokens accessible through token authorization, independently of the collateral amount being routed. The documented reproduction drains `77_770_000_000` units of an unrelated token and leaves the victim with zero while the attacker receives the full balance. [8](#0-7) 

### Likelihood Explanation
An attacker only needs to provide a malicious route payload; the route-selected pool can be attacker-deployed and does not need privileged protocol access. [9](#0-8)  Exploitation requires the victim’s client or wallet to sign the simulated poisoned authorization tree, so it is not fully unilateral, but an ordinary client that accepts simulation output without validating children makes the path reachable. [10](#0-9) 

### Recommendation
Do not rely on clients to reject poisoned authorization trees. Restrict route execution to verified venue contracts or isolate router callbacks under an authorization context that cannot inherit the user’s `swap_collateral` authorization. At minimum, reject authorization trees containing children beyond the expected input-token transfer and document route decoding requirements for `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, `multiply`, and direct router execution.

### Proof of Concept
The repository contains a complete test, `simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry`, which configures a router that invokes attacker-selected pool code, records an unauthorized wallet-token transfer beneath `swap_collateral`, and moves the victim’s balance to the attacker. [1](#0-0)  The companion enforcing-mode test shows the identical signed tree succeeds and empties the victim’s unrelated wallet token. [8](#0-7)

```markdown
That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap
```
