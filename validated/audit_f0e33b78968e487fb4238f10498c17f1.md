### Title
Webhook shop-domain header is not covered by HMAC verification, allowing shop attribution spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC computed by `Utils::HmacValidator` signs the request body exclusively. The `shop` value (read from the `x-shopify-shop-domain`/`shopify-shop-domain` header) is never included in the signed bytes, yet `Registry.process` forwards this unauthenticated header value directly to the app's `WebhookHandler` as the tenant identifier.

### Finding Description
`Request#hmac`, `#topic`, `#shop`, `#api_version`, and `#webhook_id` are all read from HTTP headers [1](#0-0) , but `#to_signable_string` only returns the raw body [2](#0-1) . `Registry.process` validates the request purely via `Utils::HmacValidator.validate(request)` — which calls `to_signable_string` — and then, without any additional binding check, builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` and hands it to the registered handler [3](#0-2) . `HmacValidator.validate` computes the signature strictly over `verifiable_query.to_signable_string` using the app's `api_secret_key` [4](#0-3) .

This breaks the identity binding: `HMAC(body) == received_hmac` is treated as authorizing `shop == header["shopify-shop-domain"]`, even though `shop` is never part of the signed bytes. Anyone who can obtain one legitimate `(raw_body, hmac)` pair signed with the app's shared `api_secret_key` — trivially available to an unprivileged internet user by installing the app on their own free/dev store and receiving a real webhook for their own shop — can replay that exact body+HMAC pair to the app's public webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header. `HmacValidator.validate` still returns `true` (the body/HMAC pair is genuinely valid), and `Registry.process` will invoke the handler with `WebhookMetadata#shop` set to the attacker-chosen shop, misattributing the attacker's own webhook payload/topic to a victim tenant.

### Impact Explanation
This is a cross-tenant identity-binding break: the gem authenticates the payload bytes but lets an attacker freely control which tenant (`shop`) that authenticated payload is attributed to when it's handed to the host application. Any app that uses `data.shop` from `WebhookMetadata` to key storage, trigger per-shop side effects (e.g., updating that shop's local state, billing, or provisioning) is vulnerable to cross-tenant data injection/confusion, since the gem itself performs no verification tying `shop` to the HMAC-covered bytes.

### Likelihood Explanation
Exploitation requires only that the attacker be able to install the target app on any shop they control (including a free Shopify dev/partner store) — no `api_secret_key`, no access token, and no privileged account for the app owner is needed. This is a normal, unprivileged capability for anyone able to create a Shopify partner/dev account, making the likelihood high wherever a host app trusts `WebhookMetadata#shop` from `Registry.process`.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the HMAC-signed bytes, or independently verify that `request.shop` matches a shop that is actually installed/expected for that specific webhook delivery (e.g., cross-check against the topic's expected recipient before dispatching to the handler). At minimum, document that `WebhookMetadata#shop` is not cryptographically bound to the payload and must not be trusted for tenant attribution without additional verification.

### Proof of Concept
1. Attacker installs the target Shopify app on their own dev store `attacker.myshopify.com` and registers for a webhook topic (e.g., `orders/create`).
2. Shopify delivers a legitimate webhook to the app's callback URL with a body `B` and a valid `X-Shopify-Hmac-Sha256` header `H = HMAC-SHA256(api_secret_key, B)`, plus `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. Attacker captures `(B, H)` and replays them to the same endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {..., "x-shopify-hmac-sha256" => H, "x-shopify-shop-domain" => "victim.myshopify.com"})` is constructed.
5. `Utils::HmacValidator.validate(request)` returns `true` because it only checks `HMAC(B) == H`, both of which are genuinely valid [5](#0-4) .
6. `Registry.process` invokes the handler with `WebhookMetadata#shop == "victim.myshopify.com"` even though the payload actually originated from and describes `attacker.myshopify.com` [6](#0-5) .
