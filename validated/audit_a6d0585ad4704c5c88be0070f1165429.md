### Title
Webhook topic and shop-domain headers are unauthenticated and let a replayed body drive handler selection and shop identity for another tenant - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`HmacValidator.validate` only authenticates the raw request body (`to_signable_string` returns `@raw_body`), never the `topic` or `shop-domain` headers. `Registry.process` uses those unauthenticated headers to select the handler and to populate `WebhookMetadata#shop`, so an attacker who legitimately received one valid signed webhook can replay it while relabeling the topic and shop headers, causing the app to run an arbitrary handler with an arbitrary victim shop attached to attacker-controlled body content.

### Finding Description
The broken binding is: `signature_valid(request) == (request.topic, request.shop, request.parsed_body all authentic)`. In reality only `@raw_body` is covered.

- `Webhooks::Request#to_signable_string` returns `@raw_body` only: [1](#0-0) 
- `topic` and `shop` are read straight from attacker-controlled headers with no cross-check against the signed payload: [2](#0-1) 
- `HmacValidator.validate_signature` computes the HMAC over exactly `verifiable_query.to_signable_string` (i.e., the body) and compares it to the `hmac` header; nothing else is folded into the signable string: [3](#0-2) 
- `Registry.process` validates the HMAC, then immediately dispatches on `request.topic` and forwards `request.shop` and `request.parsed_body` into the handler, with no additional authorization tying topic/shop to the signature: [4](#0-3) 

Attack flow: the attacker installs the app on their own development shop and legitimately receives one real webhook delivery consisting of `(raw_body = B, x-shopify-hmac-sha256 = H)` where `H = HMAC(api_secret_key, B)`. Because `H` depends only on `B`, the attacker can POST directly to the app's webhook endpoint with the *same* `B` and `H` (so the HMAC check in `HmacValidator.validate` still passes) while freely setting `x-shopify-topic` to any registered topic and `x-shopify-shop-domain` to a victim merchant's domain. `Registry.process` looks up the handler for the attacker-chosen topic and calls `handler.handle` with `shop: request.shop` set to the victim's domain and `body: request.parsed_body` derived from the attacker's own captured body `B`. Any host-app handler logic that trusts `WebhookMetadata#shop` as an authenticated tenant identifier (e.g., to look up or mutate per-shop state) is now driven by attacker-controlled data labeled as the victim.

None of the existing guards prevent this: `HmacValidator.validate` only checks `to_signable_string` (body) integrity, not header integrity; there is no `ShopValidator.sanitize!` or equivalent call on `request.shop` in this path; `Registry.process` performs no per-topic or per-shop authorization before invoking the handler.

### Impact Explanation
This is a Critical authentication-bypass class: a request whose signature only proves "this body byte-sequence was HMAC'd once by Shopify for *some* delivery" is accepted by the app as an authentic webhook for an arbitrary topic and an arbitrary victim shop. The attacker gains the ability to invoke any registered webhook handler with a forged shop identity and attacker-chosen (previously captured) body content, once per captured valid `(body, hmac)` pair. This is repeatable against arbitrary victim shop domains simply by changing the `x-shopify-shop-domain` header on replay, and the blast radius is cross-tenant: one attacker-controlled delivery can be mislabeled as belonging to any other merchant using the app.

### Likelihood Explanation
Preconditions are modest and entirely within the described unprivileged attacker capability: register/own a development shop, install the target app, and receive at least one legitimately signed webhook delivery to capture a valid `(raw_body, hmac)` pair. No secrets (`api_secret_key`, access tokens) are needed. The attacker directly controls all headers when POSTing to the app's webhook endpoint. This is a low-cost, fully repeatable attack against any topic the app has registered a handler for.

### Recommendation
Include the `topic` and `shop-domain` headers (and any other header the app logic keys on) inside the HMAC-covered signable string, or otherwise cryptographically bind them to the body before verification, so a replayed body cannot be relabeled with a different topic or shop. Additionally, `Registry.process` should not trust `request.shop` as an authenticated tenant identifier for any authorization decision without an independent check (e.g., validating that the shop has an active, matching session/webhook registration for that topic and webhook id).

### Proof of Concept
minitest sketch (WebMock/Mocha, no live shop):
```ruby
test "same signed body accepted for two different shop-domain headers" do
  ShopifyAPI::Context.setup(api_key: "key", api_secret_key: "secret", ...)
  raw_body = '{"id":1}'
  hmac = Base64.encode64(OpenSSL::HMAC.digest("sha256", "secret", raw_body))

  received_shops = []
  handler = Class.new do
    define_method(:handle) { |data:| received_shops << data.shop }
  end.new
  ShopifyAPI::Webhooks::Registry.add_registration(topic: "orders/create", delivery_method: :http, path: "/x", handler: handler)

  headers1 = { "x-shopify-topic" => "orders/create", "x-shopify-hmac-sha256" => hmac, "x-shopify-shop-domain" => "attacker.myshopify.com" }
  headers2 = { "x-shopify-topic" => "orders/create", "x-shopify-hmac-sha256" => hmac, "x-shopify-shop-domain" => "victim.myshopify.com" }

  ShopifyAPI::Webhooks::Registry.process(ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers1))
  ShopifyAPI::Webhooks::Registry.process(ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers2))

  assert_equal ["attacker.myshopify.com", "victim.myshopify.com"], received_shops
end
```
Both calls succeed (no `Errors::InvalidWebhookError` raised) despite the second header set never having been signed for `victim.myshopify.com`, proving the shop binding is broken.
