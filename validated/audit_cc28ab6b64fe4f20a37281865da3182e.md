### Title
Webhook shop identity is not covered by HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies the webhook HMAC over the raw request body only, then passes the `shop-domain` HTTP header — which is never part of the signed payload — into the handler as trusted shop identity. An unprivileged app installer can capture a genuinely Shopify-signed webhook body+HMAC pair for their own shop, then replay it to the app's webhook endpoint with a forged `shop-domain` header pointing at a victim shop, and the signature will still validate.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The shop identity is read from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, a value that is not part of the signed material: [2](#0-1) 

`Registry.process` validates the HMAC and then hands the header-derived `shop` straight to the app's handler as trusted metadata, without any check that the shop belongs to the same request/signature context: [3](#0-2) 

The documented `WebhookMetadata` contract tells app developers that `data.shop` is "The shop domain of the webhook," encouraging them to trust it directly (e.g., to look up which merchant's stored session/access token to act on): [4](#0-3) [5](#0-4) 

The identity binding broken is: `shop authenticated by HMAC` (which is actually `none` — HMAC only proves knowledge of `api_secret_key` over the body bytes) `!=` `shop acted upon` (the attacker-controlled header value delivered to the handler as `WebhookMetadata#shop`). Any unprivileged internet user who can install the app on their own store (a normal, unprivileged action for public apps) receives genuinely Shopify-signed webhook bodies for their own store's events. Because the header is not covered by the signature, that exact signed body can be replayed to the endpoint with the `shop-domain` header swapped to any victim shop domain, and `Utils::HmacValidator.validate(request)` still returns `true`.

### Impact Explanation
This is a cross-tenant identity-binding break inside the gem's own webhook verification path: the gem asserts message integrity (`Invalid webhook HMAC.`) but delivers an unauthenticated tenant identifier as if it had been verified together with the payload. Any app built on this gem's documented API (i.e., using `data.shop` per the documented contract, without the app author independently re-deriving/verifying shop identity) is exposed to cross-tenant confusion: writes, side effects, or API calls attributed to the attacker's own webhook body can be executed against a victim merchant's records purely because the trusted `shop` value is forgeable. This matches the Critical/High "cross-tenant access" impact category, since the vulnerability lives in the gem's `Webhooks::Registry`/`Webhooks::Request` verification logic rather than in host-application misuse of an undocumented API.

### Likelihood Explanation
Likelihood is high given the low bar to exploit: any unprivileged internet user who can install the target app on a store they control (typical for public/free apps) can trigger a real webhook and capture its raw body + `X-Shopify-Hmac-Sha256`, then simply resend the same bytes with a different `X-Shopify-Shop-Domain` header to the app's public webhook endpoint. No secrets, tokens, or privileged access are required — the whole point of the attack is that the header can be swapped freely without invalidating the HMAC.

### Recommendation
Bind the shop identity into the material that is checked, not just delivered separately. Concretely:
- Include the `shop-domain` header (and ideally `webhook-id`, `api-version`) in `to_signable_string`/the value verified by `Utils::HmacValidator`, or
- Require apps to independently correlate `request.shop` against the shop associated with the stored session/access token used to make any follow-up API calls, and document this requirement prominently, or
- At minimum, validate that `request.shop` is a shop that is actually installed/known to the app (e.g., has a stored session) before invoking the handler, rejecting unknown/mismatched shops in `Registry.process`.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (a normal, unprivileged action).
2. Attacker triggers a real event (e.g., `orders/create`) on their own store, causing Shopify to POST a webhook to the app's endpoint with headers including `X-Shopify-Hmac-Sha256: <valid-hmac-for-body>` and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker captures the exact raw body and `X-Shopify-Hmac-Sha256` value.
4. Attacker resends the identical raw body and `X-Shopify-Hmac-Sha256` to the same webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
5. `Utils::HmacValidator.validate(request)` in `Registry.process` verifies the HMAC against `to_signable_string` (the raw body only) and passes — the header change has no effect on the check: [6](#0-5) 
6. The app's handler receives `WebhookMetadata.shop == "victim-shop.myshopify.com"` with attacker-chosen body content, and if it uses `data.shop` to select the merchant record/session to act on (as documented), it performs that action against the victim's tenant instead of the attacker's own.
