### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant shop spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body, and `ShopifyAPI::Webhooks::Registry.process` verifies the HMAC over that raw body alone. The `shop` value passed to the app's handler is read straight from the `shopify-shop-domain` header, which is never part of the signed content. An attacker who can obtain one genuine, validly-signed webhook payload (e.g., by installing the target app on their own shop and triggering a webhook) can replay that exact body to the victim app's webhook endpoint while substituting the `shop-domain` header for a different shop that also has the app installed. The HMAC still validates (it only checks the body), and the handler receives attacker-chosen `shop` bound to genuine-but-misattributed data.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 

and `shop` is read independently from headers, with no cryptographic tie to the signed body: [2](#0-1) 

`HmacValidator.validate` computes the signature only from `verifiable_query.to_signable_string` (the raw body) and compares it to the `hmac` header: [3](#0-2) 

`Registry.process` checks only this body HMAC before dispatching to the handler with `shop: request.shop` taken straight from the header: [4](#0-3) 

The identity binding that should hold is: `shop-domain header == shop that produced/owns the signed body`. Because the HMAC only covers `@raw_body`, this equality is never checked. Any unprivileged internet user who has installed the app on a shop they control (a completely legitimate, unprivileged install) can:
1. Capture a real webhook delivery for their own shop (body + valid `x-shopify-hmac-sha256` computed by Shopify with the app's shared `api_secret_key`).
2. Replay the identical raw body to the app's webhook endpoint, but with the `x-shopify-shop-domain` (or `shopify-shop-domain`) header changed to another shop that has also installed the app.
3. Because `to_signable_string` doesn't include the header, `HmacValidator.validate` still succeeds, and `Registry.process` invokes the handler with `WebhookMetadata#shop` equal to the attacker-chosen victim shop, while `body` is the attacker's own (but genuinely-signed) data.

The host application's webhook handler (per the documented usage pattern) trusts `data.shop` as the tenant identifier to route/store the payload, per the gem's own documentation: [5](#0-4) 

This breaks the shop-identity binding that the handler relies on, letting the attacker inject data attributed to a shop they do not control — a cross-tenant confusion enabled purely by this gem's signature-verification scope, not by any application misuse.

### Impact Explanation
This is a cross-tenant data-integrity issue: an unprivileged attacker (who only needs to be able to install the target app on any shop, which is normal/expected for a public app) can cause the app to process and persist webhook data under a different, victim shop's identity. Depending on the handler's use of `data.shop` (e.g., updating shop-scoped records, redact/GDPR webhooks, order/customer sync), this can lead to data corruption, unauthorized writes attributed to another tenant, or triggering compliance-sensitive flows (like `customers/redact`) against a shop the attacker doesn't own — a cross-tenant boundary violation.

### Likelihood Explanation
Moderate-to-high for apps that are installable by the public (the standard Shopify app model): the only prerequisite is the attacker's own legitimate install of the target app, which is not a privileged position, and capturing/replaying their own webhook traffic to the app's public webhook endpoint with a modified header is trivial (no secret or token needed since `api_secret_key` is never exposed to the attacker; they simply reuse an HMAC that was already validly computed for their own body).

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the value verified by the HMAC — for example, verify the shop domain against the registered/expected shop for that webhook subscription (or otherwise cross-check that the delivered `shop-domain` header matches a shop known to have an active subscription/session before trusting it), rather than trusting an unauthenticated header field purely because the (body-only) HMAC passed.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a normal, unprivileged action).
2. Attacker triggers a webhook (e.g. `orders/create`) for their own shop and captures the raw POST body `B` and the resulting valid `x-shopify-hmac-sha256` value `H` (computed by Shopify using the app's shared `api_secret_key`, which the attacker never sees but doesn't need to).
3. Attacker POSTs to the victim app's webhook endpoint with:
   - Headers: `x-shopify-topic: orders/create`, `x-shopify-hmac-sha256: H`, `x-shopify-shop-domain: victim-shop.myshopify.com`
   - Body: `B` (unchanged)
4. `HmacValidator.validate` recomputes the HMAC over `B` only [3](#0-2)  and it matches `H`, so `Registry.process` calls the handler with `shop: "victim-shop.myshopify.com"` [4](#0-3) , even though the data actually originated from `attacker-shop.myshopify.com`.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
