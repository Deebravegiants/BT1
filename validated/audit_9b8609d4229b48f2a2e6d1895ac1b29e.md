### Title
`supply-collateral-add` double-pulls the underlying token, permanently stranding the user's first transfer in the market contract - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`supply-collateral-add` transfers the underlying token from the user into the market contract, then invokes the vault's deposit path inside an `as-contract?` capability block. The vault's internal `receive-underlying` helper re-sources the deposit directly from the original user account rather than from the tokens the market just received, causing the user to pay the deposit amount twice while the first transfer sits permanently unusable in the market contract.

### Finding Description
In `supply-collateral-add`, Step 1 explicitly moves `amount` of the underlying `ft` from the user (`account`) to the market contract (`current-contract`): [1](#0-0) 

Step 2 then calls `vault-deposit` for the *same* `account` inside a capability-granting `as-contract?` block, expecting the market to be able to spend the tokens it just custodied: [2](#0-1) 

However, the vault's `deposit` entrypoint sources funds via `receive-underlying`, which performs its own SIP-010 `transfer` call using `account` (the original user) as the sender, not the market contract that now actually holds the balance: [3](#0-2) [4](#0-3) 

Because Clarity SIP-010 transfers are authorized on `tx-sender`/`sender` identity (there is no ERC20-style allowance/`approve` step to redirect custody), and `tx-sender` remains the original user throughout the `as-contract?` call, this second `transfer` pulls a *second* `amount` directly from the user's wallet rather than consuming the `amount` the market already collected in Step 1. The tokens moved into the market contract in Step 1 are never referenced again anywhere in `supply-collateral-add`, and the market contract exposes no function to return or reuse orphaned underlying balances of this kind (unlike `dao-treasury.clar`'s `withdraw`, which is DAO-gated and not available to depositors) — so this exactly mirrors the original bug class: a value identity ("tokens moved into a contract equal tokens actually consumed downstream") is broken, and the surplus becomes permanently stuck.

### Impact Explanation
Every call to `supply-collateral-add` requires the user to hold and pay `2 * amount` of the underlying token to mint shares/collateral for only `1 * amount`. The first `amount`, transferred to the market contract in Step 1, is permanently frozen there with no recovery path for the depositor. This is a permanent freezing of user funds each time the function is used, and at protocol scale, an accumulating pool of stranded user funds sitting unaccounted-for inside the market contract.

### Likelihood Explanation
This triggers on every ordinary call to `supply-collateral-add` by any unprivileged user attempting to deposit-and-collateralize in one transaction — it does not require any special privilege, market condition, or attacker behavior, only that the function is used as designed and the user holds sufficient balance to complete both transfers (if they don't, the second transfer simply reverts, but any user who does have 2x the balance will lose the first `amount`).

### Recommendation
Restructure `supply-collateral-add` so that the market forwards the tokens it already custodied to the vault (i.e., the vault's deposit path should consume the balance held by the market/`current-contract`, analogous to adding the missing `approve()`/token-forwarding step in the original report), rather than having the vault independently re-pull funds from the original user account. Alternatively, remove the Step 1 transfer entirely and let the vault's `receive-underlying` perform the single, sole transfer from the user.

### Proof of Concept
1. User holds `2 * amount` of `sbtc` and calls `market.supply-collateral-add(sbtc-ft, amount, min-shares, price-feeds)`.
2. Step 1 executes `(contract-call? ft transfer amount account current-contract none)` — user balance now `1 * amount`, market balance now `amount`. [1](#0-0) 
3. Step 2 enters `as-contract?` and calls `vault-deposit`, which internally calls the vault's `deposit`, which calls `receive-underlying amount account`, executing `(contract-call? .sbtc transfer amount account current-contract none)` a second time, pulling from the user again — user balance now `0`, vault balance now `amount`. [3](#0-2) 
4. User receives shares/zToken collateral worth only `1 * amount`, but the market contract still holds the first `amount` transferred in step 2, with no function in `v0-4-market.clar` to reclaim or apply it — those funds are permanently stuck.
