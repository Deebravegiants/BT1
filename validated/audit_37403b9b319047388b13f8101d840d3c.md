### Title
Unrestricted arbitrary call in `EmporiumUpgradeable.runAction`'s stateless op path lets an attacker drain any token balance stranded on the action contract - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
`EmporiumUpgradeable.runAction` executes attacker-supplied `EmporiumOperation` entries via a raw low-level `call` whenever `invokeWallet` is false (the "Stateless Interaction" branch), with no restriction on `op.endpoint` or `op.callData` other than blocking the two `IHinkalWallet` selectors. Because the post-call balance-diff check (`balanceChange`) is only computed for tokens the attacker chooses to list in `circomData.erc20TokenAddresses`, and because the raw call can send tokens directly to an arbitrary address rather than back to the Emporium contract, an attacker can craft an op that calls `token.transfer(attacker, amount)` (or a router function specifying themselves as recipient) to pull out any ERC20 balance sitting on the Emporium contract — including value stranded there by a previous user's swap/refund — completely outside the accounted `-deltaAmountChanges` flow.

### Finding Description
The invariant that should hold for every `runAction` call is: *tokens leaving the action contract in a tx == -deltaAmountChanges Hinkal sent to it in that tx*. This is enforced only via the `balanceChange`/`handleOut` logic: [1](#0-0) 

That loop only iterates over `circomData.erc20TokenAddresses`, an attacker-controlled array (this is the attacker's own transaction), so any token not listed there is never checked at all.

The `ops` array itself is decoded straight from attacker-controlled `externalActionMetadata`: [2](#0-1) 

and for the stateless branch (`invokeWallet == false`, or `stack.signerAddress == address(0)`), the only guard is the selector check for `callHinkalWallet`/`doSendToRelay`; the call target and calldata are otherwise fully free: [3](#0-2) 

`verifyWallet` only checks an EIP-712 signature when `stack.signerAddress != address(0)`; when it is zero (the stateless path used here) no signature is required at all: [4](#0-3) 

**Exploit flow**: Suppose a prior legitimate user's Emporium swap left surplus output tokens (or a partial input refund) sitting on the Emporium contract instead of being fully swept via `handleOut` (e.g. the router refunds asynchronously, or leaves dust after the balance snapshot). This balance now simply sits as ERC20 balance on the Emporium contract address. An attacker then calls `Hinkal.transact` with their own valid proof for their own (possibly zero-value) UTXOs, setting `circomData.externalActionData.externalActionMetadata` to an `EmporiumStack` whose `ops` array contains a single stateless op:
```
op.endpoint = strandedToken;
op.callData = abi.encodeWithSelector(IERC20.transfer.selector, attacker, strandedAmount);
op.invokeWallet = false;
```
Because this call executes with `msg.sender == EmporiumUpgradeable` (it's a low-level call originating from `runAction`), it moves `strandedAmount` of `strandedToken` directly from the Emporium contract to the attacker's EOA. If the attacker simply omits `strandedToken` from `circomData.erc20TokenAddresses`, the `balancesBefore`/`balancesAfter`/`balanceChange` loop never even measures that token, so `BalanceChangeShouldBePositive` can never fire and no accounting ties the stolen amount back to `deltaAmountChanges`. Even if the token is included, the transfer bypasses the Emporium contract's own balance change entirely by sending straight to the attacker instead of back to the contract, so `balanceChange` for that token would show `0` (no theft detected) while `strandedAmount` real tokens left the contract to the attacker.

This breaks the target invariant directly: tokens leaving the action (`strandedAmount`) is unequal to `-deltaAmountChanges` Hinkal sent it in that tx (`0`), and none of `performHinkalChecks`, `verifyProof`, `rootHashExists`, or the `balanceChange`/`BalanceChangeShouldBePositive` guard prevent it, because those guards are scoped to attacker-chosen tokens and to net balance changes on the contract itself — not to arbitrary calls that route funds directly out to a third party.

### Impact Explanation
Any value parked on the Emporium contract — stranded router refunds/surplus from another user's in-flight or completed swap, dust left after prior `handleOut` calls, or fees en route — can be stolen outright by any unprivileged attacker who can submit a normal `Hinkal.transact` call for their own UTXOs. This is direct theft of in-flight/protocol-held user funds, matching the Critical severity category. It is repeatable: any time stray balance accumulates on the action contract, any attacker's next transaction can sweep it.

### Likelihood Explanation
Preconditions: some ERC20 balance must be resident on the `EmporiumUpgradeable` contract that is not being tracked/claimed in the current transaction (e.g., leftover from an earlier user's refund, dust, or fees). This is plausible in normal operation of a router-integrated swap/execution engine and requires no special timing beyond "wait until the target token balance is non-zero." The attack itself costs only a normal Hinkal transaction (gas + a valid proof for the attacker's own funds) — no privileged role, no signature forgery, and no interaction with `verifiers/` internals is required, since the exploit is a plain unrestricted low-level call in `runAction`.

### Recommendation
Restrict the stateless `EmporiumOperation` execution so that arbitrary calls cannot move Emporium-held token balances to addresses other than the Emporium contract itself, or otherwise require every token touched by an op to be declared in `circomData.erc20TokenAddresses` and be fully accounted for by the `balanceChange`/`handleOut` invariant (e.g., disallow direct ERC20 `transfer`/`transferFrom` calls to arbitrary endpoints, or forbid ops from specifying a recipient other than `address(this)`/msg.sender-checked flows). At minimum, ensure the balance-diff accounting is computed over the full set of tokens actually touched by the ops (not just the attacker-chosen `erc20TokenAddresses` array) so any residual/stray balance leaving the contract in a transaction is always required to net out against that transaction's declared `deltaAmountChanges`.

### Proof of Concept
Foundry plan:
1. Deploy `EmporiumUpgradeable`, `Hinkal`, and a mock ERC20 `TokenB`.
2. Seed the residual: directly `deal`/mint `TokenB` to the `EmporiumUpgradeable` contract address to simulate a stranded refund from a prior transaction (`strandedAmount`).
3. As an unprivileged attacker, build a valid `CircomData`/proof for a trivial transaction (e.g., zero net token movement, or a small deposit of a different token `TokenA`) that targets `EmporiumUpgradeable` as the external action, with `externalActionMetadata` encoding an `EmporiumStack` containing one stateless op: `endpoint = address(TokenB)`, `callData = abi.encodeWithSelector(IERC20.transfer.selector, attacker, strandedAmount)`, `invokeWallet = false`, `signerAddress = address(0)`.
4. Do not include `TokenB` in `circomData.erc20TokenAddresses`.
5. Call `Hinkal.transact(...)`.
6. Assert: `TokenB.balanceOf(attacker)` increased by `strandedAmount`, and `TokenB.balanceOf(EmporiumUpgradeable)` decreased by `strandedAmount`, while `deltaAmountChanges` for `TokenB` in this transaction was never declared (array doesn't contain `TokenB`) — i.e., tokens leaving the action (`strandedAmount`) != `-deltaAmountChanges` sent to it that tx (`0`), proving the invariant break and fund theft.
