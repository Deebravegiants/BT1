### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature only over the raw request body, while the `shop`, `topic`, `api_version`, and `webhook_id` fields are read directly from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` validates only the HMAC over the body, then passes `request.shop` (unauthenticated) into the handler as the tenant identifier, breaking the binding between the verified signature and the shop attributed to the request.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile, `shop` (and `topic`, `api_version`, `webhook_id`) are pulled straight from HTTP headers with no cryptographic binding to the signed payload: [2](#0-1) 

`Registry.process` validates the HMAC (which only covers `raw_body`) and then dispatches to the handler using the unauthenticated `request.shop`, `request.topic`, etc.: [3](#0-2) 

The identity-binding equality that should hold is:
`hmac(raw_body, shared_secret) valid` ⟺ `(shop, topic, raw_body)` is exactly what Shopify sent.

Because `to_signable_string` only signs `raw_body`, the actual guarantee reduces to:
`hmac(raw_body, shared_secret) valid` ⟺ `raw_body` is exactly what Shopify sent for *some* shop — with `shop-domain` free to be substituted by whoever delivers the request to the app's webhook endpoint.

An unprivileged actor who controls their own Shopify store (a normal merchant/app-installer, not a privileged account and without needing the app's `client_secret`) can:
1. Install the app on their own store and trigger any webhook topic the app subscribes to (e.g., `orders/create`), which Shopify signs and delivers with a correct `X-Shopify-Hmac-Sha256` over the raw body.
2. Capture this legitimately-signed `(raw_body, hmac)` pair.
3. Replay the request to the app's webhook endpoint, but rewrite the `X-Shopify-Shop-Domain` header to a victim shop's domain.
4. Since `HmacValidator.validate` only re-derives the signature from `raw_body` (`to_signable_string`), the check passes, and `Registry.process` calls the app's handler with `WebhookMetadata.new(shop: <victim shop>, ...)`.

This lets the attacker feed forged/attacker-chosen webhook bodies into the app's per-shop business logic while impersonating a different (victim) shop — a cross-tenant confusion vulnerability rooted entirely in the gem's own signature-scope design.

### Impact Explanation
This is a cross-tenant access issue: the webhook handler attributes attacker-supplied, cryptographically-"valid" data to an arbitrary victim shop of the attacker's choosing, since the `shop` field used for tenant routing/storage is outside the HMAC's protected scope. Depending on what the host app does in its webhook handler (e.g., updating per-shop state, deleting data, triggering side effects keyed by `shop`), this can corrupt or leak data across shop boundaries without ever touching the app's `client_secret` or any access token.

### Likelihood Explanation
Any merchant who can install the app on their own store (an unprivileged, self-service action) can obtain a validly-signed `(raw_body, hmac)` pair for arbitrary webhook topics/content originating from their own shop, then simply swap the `shop-domain` header when re-delivering the request to the app's public webhook endpoint. No credential theft, TLS interception, or privileged access is required — only the ability to send an HTTP request with attacker-chosen headers to the app's endpoint, which is the gem's documented integration point.

### Recommendation
Include `shop`, `topic`, and `webhook_id` (in addition to the raw body) in the value that is HMAC-verified, or otherwise cryptographically bind the shop-domain header to the signature before it is used for tenant attribution. If Shopify's protocol does not sign these headers, the gem should not treat `request.shop` as trusted for authorization/tenant-scoping purposes without an additional binding check (e.g., cross-referencing against a shop known to be currently installed/authorized, using a stored offline session, rather than trusting the header verbatim).

### Proof of Concept
```ruby
# Attacker installs the app on their own shop "attacker.myshopify.com"
# and triggers e.g. an orders/create webhook, capturing the legitimate delivery:
raw_body = '{"id":1,"malicious":"payload"}'
valid_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), app_secret, raw_body)
# (app_secret unknown to attacker, but Shopify computed and delivered this HMAC
#  for the attacker's own legitimately-installed shop)

# Attacker now replays the exact same body+hmac to the app's public webhook
# endpoint, but swaps the shop-domain header:
forged_headers = {
  "shopify-topic" => "orders/create",
  "shopify-hmac-sha256" => Base64.encode64(valid_hmac),
  "shopify-shop-domain" => "victim-shop.myshopify.com", # not covered by HMAC
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# HmacValidator.validate(request) passes (it only checks raw_body),
# and the handler is invoked with shop: "victim-shop.myshopify.com"
# even though that shop never sent this webhook.
```
