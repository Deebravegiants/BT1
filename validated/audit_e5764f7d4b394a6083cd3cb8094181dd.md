## Analog Found: Tron `IntentGatewayV2.placeOrder` doesn't account for fee-on-transfer tokens

### Title
Escrow accounting in `IntentGatewayV2.placeOrder` (Tron variant) credits nominal amount instead of actual tokens received, causing insolvency with fee-on-transfer tokens - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron deployment of `IntentGatewayV2.sol` credits escrow storage `_orders[commitment][token]` with the user-specified/protocol-fee-reduced `order.inputs[i].amount` without ever measuring what the contract actually received via `safeTransferFrom`. The mainline EVM version of the same contract (`evm/src/apps/IntentGatewayV2.sol`) was explicitly patched to record the *actual received* balance delta to defend against fee-on-transfer tokens, but this fix was not carried over to the Tron contract, leaving it vulnerable to the exact analog of the reported Allo.sol bug class.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol::placeOrder`, the non-predispatch escrow path does: [1](#0-0) 

The contract calls `IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` and then unconditionally credits `_orders[commitment][token] += reducedInputs[i].amount`, where `reducedInputs[i].amount` is derived directly from `order.inputs[i].amount` (only reduced by the protocol fee) computed earlier in the function: [2](#0-1) 

There is no balance-before/balance-after measurement, unlike the fixed EVM mainline version which explicitly computes `order.inputs[i].amount = IERC20(token).balanceOf(address(this)) - balBefore;` before crediting escrow: [3](#0-2) 

The same discrepancy occurs in the predispatch branch of the Tron contract, which credits `reducedInputs[i].amount` into escrow while only checking `balance < requiredAmount` on the dispatcher, again never reconciling actual amount swept to the gateway with what gets recorded: [4](#0-3) 

When a fee-on-transfer token is used as an order input, the gateway will actually hold less than `_orders[commitment][token]` records. This is precisely the bug class from the referenced report: the pool/escrow "believes" it received the full nominal amount when it actually received less due to transfer-fee deduction.

### Impact Explanation
Because `withdraw()` (invoked from `onAccept` for `RedeemEscrow`/`RefundEscrow`, or directly from `cancelOrder` on same-chain) transfers out `body.tokens[i].amount` based on the over-credited `_orders[commitment][token]` value: [5](#0-4) 

the recorded escrow balance for that specific order commitment exceeds the actual token balance held by the contract for that order. Since the gateway is a shared pool across many concurrent orders, this shortfall means:
- The affected order's beneficiary/solver either cannot be paid in full (transfer reverts due to insufficient token balance) — freezing funds for that order, or
- If the pool has surplus balance from other unrelated orders' full-amount tokens sitting in the same contract, the shortfall is silently paid out of other users' escrowed principal, breaking the escrow's fund segregation and enabling one order's fee-on-transfer input to drain balance backing other orders.

Either outcome maps to "concrete theft or permanent freezing of funds" via broken escrow accounting, satisfying the required Medium+ impact bar.

### Likelihood Explanation
This is reachable by any unprivileged user simply calling `placeOrder` with a fee-on-transfer ERC20 as an input token — no special privileges, admin action, or governance step is required. The user experience is identical for token bridgers/intent solvers targeted by the escaped-scope rules (intent escrow). The bug is deterministic whenever the input token contract charges a transfer fee (a known, common token pattern), making exploitation trivial and reliably reproducible.

### Recommendation
Apply the same fix already present in `evm/src/apps/IntentGatewayV2.sol` to the Tron variant: measure `balanceOf(address(this))` before and after each `safeTransferFrom` (and after each predispatch sweep) and use the actual received delta — not the nominal `order.inputs[i].amount` — both for computing `reducedInputs`, the `commitment` hash, and for the amount credited into `_orders[commitment][token]`.

### Proof of Concept
1. Deploy a fee-on-transfer ERC20 token (e.g., 1% fee) as in the existing test harness `FeeOnTransferToken` used for the mainline EVM contract tests.
2. Call `IntentGatewayV2.placeOrder` on the Tron contract with this token as `order.inputs[0]`, `amount = 1000e18`.
3. `safeTransferFrom` moves 1000e18 requested but the gateway's `balanceOf` only increases by 990e18 (1% fee burned/redirected).
4. `_orders[commitment][token]` is nonetheless credited with `reducedInputs[0].amount` derived from the full `1000e18` (minus only protocol fee, if any) — i.e., an escrow record larger than the actual 990e18 held.
5. When `withdraw()` is later invoked for this commitment attempting to pay out the recorded (over-stated) amount, it either reverts (freezing the order) if the pool has no surplus, or successfully drains tokens belonging to other orders' escrow balances co-mingled in the same contract, violating segregation of escrowed funds. [6](#0-5) (equivalent test already exists and passes for the fixed mainline EVM contract, confirming the absence of such a test/fix for the Tron contract is the gap being exploited.)

    /// @notice Escrow correctly reflects actual received amount for fee-on-transfer tokens.
    function testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived() public {
        // Deploy a 1% fee-on-transfer token
        FeeOnTransferToken fot = new FeeOnTransferToken(100); // 1% = 100 bps
        fot.mint(user, 10000 * 1e18);

        uint256 inputAmount = 1000 * 1e18;
        uint256 expectedReceived = inputAmount - (inputAmount * 100) / 10000; // 990

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(fot)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 900 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        vm.startPrank(user);
        fot.approve(address(intentGateway), inputAmount);
        intentGateway.placeOrder(order, bytes32(0));
        vm.stopPrank();

        // Gateway should hold only what it actually received
        assertEq(
            fot.balanceOf(address(intentGateway)), expectedReceived, "Gateway balance should match received amount"
        );

        // Reconstruct the order as placeOrder would have mutated it
        order.user = bytes32(uint256(uint160(user)));
        order.source = host.host();
        order.nonce = 0;
        order.inputs[0].amount = expectedReceived;
        bytes32 commitment = keccak256(abi.encode(order));

        // Escrow should match actual received, not the user-specified amount
        assertEq(
            intentGateway._orders(commitment, address(fot)),
            expectedReceived,
            "Escrow should equal actual received amount"
        );
    }
