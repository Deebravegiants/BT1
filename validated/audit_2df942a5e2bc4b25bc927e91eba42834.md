### Title
Webhook shop-tenant identity is not bound to the HMAC, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC signature validated by `Utils::HmacValidator.validate` covers the body bytes exclusively. The `shop` (tenant) identity read from the `x-shopify-shop-domain`/`shopify-shop-domain` header is never part of the signed material, yet `Registry.process` passes that unauthenticated header value straight into `WebhookMetadata` and hands it to the host app's handler as the authoritative tenant identifier.

### Finding Description
`Registry.process` does:
```ruby
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
...
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))
``` [1](#0-0) 

`HmacValidator.validate` verifies `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)` [2](#0-1) , and for `Webhooks::Request`, `to_signable_string` returns only `@raw_body` — the `shop`, `topic`, `webhook_id`, and `api_version` headers are excluded from the signable string entirely [3](#0-2) .

The binding that should hold is: `shop-used-by-handler == shop-covered-by-hmac`. In this implementation that equality does not hold — `request.shop` is read from a raw header via `shopify_header("shop-domain")` with zero cryptographic tie to the signed body [4](#0-3) .

Because the same `api_secret_key` is used to sign every webhook the app receives across all installed shops, an attacker who legitimately controls one shop that has installed the target app (e.g., a free development store) can capture a genuine `(body, hmac)` pair delivered to their own webhook endpoint, then replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `Utils::HmacValidator.validate` still succeeds because it only checks the body bytes, and `Registry.process` forwards the attacker-chosen `shop` value into `WebhookMetadata` as if it were verified. Any handler logic that uses `data.shop` to select a tenant record, session, or access token will operate on the wrong tenant.

### Impact Explanation
This breaks tenant isolation: a signed webhook payload from shop A can be relayed and accepted as if it originated from shop B, since the gem asserts the request is authentic (HMAC valid) while allowing an unauthenticated field to determine which tenant the payload is attributed to. This matches the Critical "cross-tenant access" category, since apps built on this library's documented `Registry.process` / `WebhookHandler` API receive an attacker-influenced tenant identity despite a passing signature check.

### Likelihood Explanation
Exploitation only requires an attacker to operate any shop that has the target app installed (trivially obtainable via a free Shopify partner development store) and to be able to send arbitrary HTTP requests to the app's public webhook endpoint — no access token, `client_secret`, or privileged access is required. The gem performs no correlation between the signed body and the shop header, so the replay works unmodified against any app relying solely on `Utils::HmacValidator.validate` plus `request.shop`/`WebhookMetadata#shop`.

### Recommendation
Include the shop domain (and ideally topic/webhook id) inside the HMAC-covered signable string, or otherwise cryptographically bind the `shop-domain` header to the signed body before trusting it in `WebhookMetadata`. At minimum, document that `request.shop` is unauthenticated and must be cross-checked by the host application against a known installed-shop list before being used as a tenant key.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and lets Shopify deliver a legitimate webhook, capturing `raw_body` and the `x-shopify-hmac-sha256` header (both are visible to the attacker's own endpoint).
2. Attacker sends a POST to the target app's webhook route with:
   - `raw_body`: unchanged from step 1 (so `to_signable_string` and thus the HMAC stay valid).
   - `x-shopify-hmac-sha256`: unchanged from step 1.
   - `x-shopify-shop-domain`: rewritten to `victim.myshopify.com`.
   - `x-shopify-topic`, `x-shopify-webhook-id`: optionally rewritten too (also unauthenticated).
3. `ShopifyAPI::Webhooks::Request.new` accepts the headers [5](#0-4) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because only `@raw_body` is hashed [6](#0-5) .
4. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", ...)` and processes attacker-controlled data as though it belongs to the victim tenant.

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
