### Title
Permanent freezing of escrowed intent funds via blacklistable token transfer to solver/user in `_withdraw` - (`evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentsBase._withdraw()` releases escrowed input tokens directly to the `beneficiary` address (the solver on fill, or the user on cancel/refund) via `IERC20(token).safeTransfer(beneficiary, amount)`, with no fallback if the transfer reverts. If the escrowed input token is a blacklistable stablecoin (e.g. USDC) and the beneficiary's address becomes blacklisted after the order was placed, the transfer permanently reverts, mirroring the "Risk using Blacklistable tokens" pattern from the referenced Cooler.sol audit finding.

### Finding Description
`_withdraw` is the single code path used to release escrow for both cross-chain settlement (`RedeemEscrow` to the solver) and refunds (`RefundEscrow`/same-chain cancel to the user): [1](#0-0) 

For cross-chain orders, this function is invoked from `onAccept`, the ISMP message-delivery entrypoint called by the host when a relayer submits the settlement/refund message: [2](#0-1) 

Because the escrow-decrement, `_filled[commitment]` finalize write, and the `safeTransfer` all happen in the same function without try/catch, a single reverting transfer (e.g., a blacklisted beneficiary on a USDC-like escrowed token) reverts the entire `onAccept` call. This is unlike a normal user-initiated payment failure — here the beneficiary address is fixed at order-placement time (`order.output.beneficiary` for fills, `order.user` for refunds) and cannot be changed by the relayer or any permissionless actor, so:
- The ISMP message can never be successfully delivered/finalized — every relayer retry of the same commitment hits the same revert, permanently blocking that message route.
- The escrowed input tokens remain locked in the gateway indefinitely, since the order can never be marked `_filled` (finalize never completes) and no alternate recovery path exists (cancellation targets the same beneficiary-dependent path via `_withdraw` as well, e.g., `_cancelSameChain` calling `_withdraw(body, true, true)`).

This matches the `_cancelSameChain` and `_fillSameChain` same-chain flow too, which calls the identical `_withdraw`/`safeTransferFrom`-to-beneficiary pattern: [3](#0-2) 

### Impact Explanation
This is a Medium-severity permanent freezing-of-funds bug: any order whose input token is blacklistable and whose solver (for redeem) or original user (for refund) gets blacklisted after order placement locks that escrow forever and permanently blocks the corresponding cross-chain settlement/refund message from ever being delivered — satisfying the "route unable to deliver messages" and "permanent freezing of funds" acceptance criteria.

### Likelihood Explanation
Requires only that: (1) the escrowed input token is a blacklistable stablecoin (USDC and similar are explicitly used as escrow/fee tokens throughout the gateway's tests and fee-token flows), and (2) the beneficiary address is later blacklisted by the token issuer — an externally-triggered event outside gateway control, not requiring any privileged/malicious actor within Hyperbridge. Given USDC's prevalence as a bridged/escrowed asset, this is a realistic, moderate-likelihood scenario for any long-lived pending order.

### Recommendation
Do not perform direct pushes to a fixed beneficiary inside the same atomic finalize step. Options:
1. Wrap the `safeTransfer`/`safeTransferFrom` call in a try/catch and, on failure, credit the beneficiary's balance to an internal pull-based ledger (a "claimable" mapping) rather than reverting the whole `onAccept`/finalize call, so the order can still be finalized and the ISMP message delivered.
2. Alternatively, split "mark as filled/refunded" and "push tokens" into two independent steps, so a stuck transfer to a blacklisted beneficiary doesn't block message finalization or a retryable relayer delivery.

### Proof of Concept
1. User places a cross-chain order escrowing USDC as input, with `order.output.beneficiary` ultimately resolving to solver `S`.
2. Solver `S` fills the order on the destination chain; a `RedeemEscrow` message is dispatched back to the source chain naming `S` as beneficiary.
3. Before the message is relayed and processed, Circle blacklists `S`'s address on the source-chain USDC contract.
4. Relayer submits the proof; `onAccept` → `_withdraw` attempts `IERC20(USDC).safeTransfer(S, amount)`, which reverts because `S` is blacklisted.
5. Every subsequent relayer retry of the same commitment reverts identically — the message can never be delivered, and the escrowed USDC is permanently stuck in the `IntentGatewayV2`/`ExtrinsicIntents` contract with no path for the user or solver to recover it.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

    function _cancelSameChain(Order calldata order, bytes32 commitment) internal {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

        uint256 inputsLen = order.inputs.length;
        TokenInfo[] memory remainingTokens = new TokenInfo[](inputsLen);
        bool hasEscrow = false;
        for (uint256 i; i < inputsLen;) {
            address token = address(uint160(uint256(order.inputs[i].token)));
            uint256 escrowed = _orders[commitment][token];
            if (escrowed > 0) hasEscrow = true;
            remainingTokens[i] = TokenInfo({token: order.inputs[i].token, amount: escrowed});
            unchecked {
                ++i;
            }
        }
        if (!hasEscrow) revert UnknownOrder();

        WithdrawalRequest memory body =
            WithdrawalRequest({commitment: commitment, tokens: remainingTokens, beneficiary: order.user});

        _withdraw(body, true, true);
