### Title
Webhook shop identity spoofing via HMAC that only covers the request body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authorizes a webhook based solely on `Utils::HmacValidator.validate(request)`, but the HMAC signature only covers the raw request body — never the `shop-domain`, `topic`, `webhook-id` or `api-version` headers. Because the tenant identity (`shop`) handed to the application's webhook handler is read straight from an unauthenticated header, a validly-signed body can be replayed with a forged `shop-domain` header to make the receiving app process data under a different merchant's identity.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes/compares the signature exclusively over that signable string: [2](#0-1) 

Yet `Registry.process` trusts `request.shop` (and `request.topic`, `request.webhook_id`, `request.api_version`), which are read directly from the `shopify-shop-domain` / `x-shopify-shop-domain` header, to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) [4](#0-3) 

The identity binding that should hold is:

`shop used by the handler (request.shop, header-derived) == shop that produced/authorized the signed body`

This equality is never enforced — the header is not part of the HMAC input, so it can be modified freely without invalidating `hmac`.

### Impact Explanation
The app's client secret (`Context.api_secret_key`) is shared across every shop that installs the app; Shopify signs every merchant's webhook body with that same secret. An attacker who legitimately installs the app on their own store receives genuinely HMAC-signed webhook deliveries for their own shop. Because the signature never covers the `shop-domain` header, the attacker can replay the exact same `(raw_body, hmac)` pair to the app's public webhook endpoint while substituting the `shop-domain` header with a victim merchant's domain. `Registry.process` will pass HMAC validation and invoke the registered handler with `WebhookMetadata#shop` set to the victim's domain while the body content actually belongs to the attacker. Any handler that uses `data.shop` to key merchant records (the documented and expected usage pattern) can be tricked into writing/merging attacker-controlled data into another tenant's records — a cross-tenant data-integrity/confusion issue reachable by any unprivileged internet user who can install the app once.

### Likelihood Explanation
Likelihood is high for any app that relies on `WebhookMetadata#shop` (or `Request#shop`) to select the tenant record to update, without independently confirming that the shop actually owns the resource IDs contained in the body (order id, customer id, etc.). Obtaining a valid `(body, hmac)` pair requires nothing more than installing the app as any ordinary merchant and receiving one webhook — no access to `api_secret_key` or any other credential is needed.

### Recommendation
- Short term: include the `shop-domain` (and ideally `topic`, `webhook-id`) header values in the signed payload verification path, or independently verify that `request.shop` matches a shop the app expects to be receiving this specific webhook for (e.g., cross-check against the session/store record before trusting the header).
- Long term: document/require that webhook handlers must never trust `WebhookMetadata#shop` for authorization purposes without an additional binding to the signed body (e.g., embedding shop identity inside the payload itself, or requiring apps to validate resource ownership against their own session store).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and lets Shopify deliver a normal webhook (e.g. `orders/create`) to the app's public webhook endpoint. Attacker captures the raw POST: body `B`, header `X-Shopify-Hmac-Sha256: H` (valid because it is computed by Shopify over `B` with the shared `client_secret`), and header `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker resends the exact same request to the app's webhook endpoint, keeping body `B` and header `X-Shopify-Hmac-Sha256: H` unchanged, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `Webhooks::Request#hmac` still decodes to `H`; `Utils::HmacValidator.validate` recomputes the signature over `B` only and it matches, so `Registry.process` proceeds.
4. `Registry.process` builds `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)` and invokes the app's handler, which now believes the (attacker-supplied) order/customer data in `B` belongs to `victim-shop.myshopify.com`.
