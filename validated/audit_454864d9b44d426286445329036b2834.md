### Title
Lost-update / hardware-wallet resurrection race between `createMany`/`updateMany` and `#replaceAll` fusion sync - (File: `features/wallet-accounts/src/module/wallet-accounts.ts`)

### Summary
`#replaceAll` and `createMany` are each wrapped independently in `makeConcurrent({ concurrency: 1 })`, which only serializes calls to the *same* wrapped function — it does not create a shared mutex between them. Because `#persistWalletAccounts` merges a full stale snapshot of `walletAccounts` on top of a freshly re-read atom value, a `#replaceAll` write (e.g. disabling/removing a hardware account via fusion sync) that lands between `createMany`'s initial read and its final persist can be silently overwritten, resurrecting the removed/disabled account.

### Finding Description
`createMany` (and `create`) is guarded by its own `makeConcurrent({ concurrency: 1 })` instance at [1](#0-0) , and `#replaceAll` is guarded by a *separate* `makeConcurrent({ concurrency: 1 })` instance at [2](#0-1) . `makeConcurrent` only limits concurrent invocations of the exact function it wraps; it provides no cross-function locking, so a `#replaceAll` run (triggered by an incoming fusion channel event, see the `processOne` handler at [3](#0-2) ) can fully execute concurrently with an in-flight `createMany`/`updateMany` call.

`createMany` takes a snapshot of the current accounts at the start: [4](#0-3) . It builds its `walletAccounts` local map as a **full copy** of that stale snapshot plus the newly created entries (lines 354-407), then hands that entire map to `#persistWalletAccounts` at [5](#0-4) .

`#persistWalletAccounts` does re-read the atom right before writing: [6](#0-5) . However the merge is `{ ...currentWalletAccounts, ...walletAccounts }` — since `walletAccounts` contains **every** pre-existing key (not just the delta of newly created accounts), any concurrent modification made to those keys between `createMany`'s initial read and this merge (e.g. `#replaceAll` disabling or deleting a hardware account) is unconditionally clobbered by the stale values still present in `walletAccounts`.

Concretely:
1. `createMany` reads state A (hardware account `X` still enabled) at line 353, copies it into local `walletAccounts`.
2. Concurrently, a fusion sync event fires `#replaceAll`, which (independently, its own read-compute-write is internally synchronous, per the comment at lines 265-268) reads state A, computes that `X` should be disabled/removed, and writes state B via `this.#walletAccountsInternalAtom.set(updatedWalletAccounts)` at line 323.
3. `createMany` finishes its synchronous account-creation logic (still using the stale, pre-disable copy of `X`) and calls `#persistWalletAccounts` at line 409.
4. `#persistWalletAccounts` re-reads the atom (now state B, with `X` disabled/removed) at line 207, but `containWalletAccounts` check fails to short-circuit (the new account isn't in B yet), so it proceeds to merge `{ ...B, ...walletAccounts(stale, includes enabled X) }` and writes it — resurrecting `X` in its pre-disable state.

There is no version/CAS check, diff-only merge, or shared lock preventing this; `containWalletAccounts` only guards an early-return optimization, not the actual merge safety.

### Impact Explanation
A previously disabled or removed hardware wallet account can be silently resurrected (re-enabled with its original state) by a stale write from a concurrent `createMany`/`updateMany` call, or conversely a legitimate disable/removal action performed via fusion sync can be lost. This is a persistence/state-integrity violation touching consent-relevant wallet account state (hardware account presence/enablement), matching a "loss of update / state resurrection" impact rather than key or fund disclosure.

### Likelihood Explanation
Triggering requires only unprivileged local timing control: an attacker able to influence fusion channel event delivery timing (e.g., during device pairing/fusion sync, which is network/IPC driven) concurrently with a normal `create()`/`update()` call from the user or another module. No privileged access, key material, or social engineering is required — only precise interleaving of two async operations that already run without mutual exclusion. This is plausible but requires winning a timing window between an atom read and a later atom write, so likelihood is moderate rather than trivial.

### Recommendation
Serialize all mutating operations (`#replaceAll`, `createMany`, `updateMany`, `disableMany`, `removeMany`, `setAccounts`) on a single shared `makeConcurrent`/mutex group (or route them all through one write queue keyed on `#walletAccountsInternalAtom`), and change `#persistWalletAccounts`'s merge to apply only the actual delta (changed/added keys) computed against the freshly re-read state, rather than spreading an entire stale snapshot on top of the current state.

### Proof of Concept
Integration/invariant test:
1. Seed `walletAccountsInternalAtom` with a hardware account `hw1` (enabled).
2. Fire two concurrent operations without awaiting sequentially:
   - `walletAccounts.createMany([{ ... }])` (a new exodus account creation) — stall its internal `#wallet.getPrimarySeedId()`/atom read with a controllable async mock so the race window is deterministic.
   - `walletAccounts['#replaceAll']`-equivalent path: push a fusion channel event whose payload disables/removes `hw1`.
3. `await Promise.all([...])`.
4. Assert final `walletAccountsInternalAtom.get()` state: `hw1` must remain disabled/removed (matching sequential-consistency expectation where the fusion disable is applied after or merged correctly with the create), and the newly created account must also be present. A failing/vulnerable implementation will show `hw1` back in its enabled/original state, violating sequential-consistency and demonstrating the lost-update/resurrection race.
