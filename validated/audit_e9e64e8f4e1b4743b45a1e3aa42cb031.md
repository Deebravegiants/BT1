### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) header is trusted for tenant attribution despite not being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes the webhook's HMAC over the raw body only, but exposes the `shop`, `topic`, `webhook_id`, and `api_version` HTTP headers as trusted, authoritative fields that `Registry.process` forwards unchanged to the host application's handler via `WebhookMetadata`. None of these header values are covered by the cryptographic signature, so any request bearing a *validly signed body* (which an attacker can obtain by triggering a real webhook on their own, legitimately installed, shop) can be replayed with an arbitrary `shop-domain` header, causing the gem to report the event as belonging to a different (victim) tenant.

### Finding Description
The HMAC signature is verified with `Utils::HmacValidator.validate`, which calls `verifiable_query.to_signable_string`. For webhooks, `to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `hmac`, `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from HTTP headers with no cross-check tying `shop` (or the other identifying headers) to the signed bytes: [2](#0-1) 

`Registry.process` validates only that the HMAC matches the body, then blindly trusts `request.shop` (and `request.topic`, `request.webhook_id`, `request.api_version`) as the tenant/context identity passed to the handler: [3](#0-2) 

`WebhookMetadata.shop` is a plain `String` field with no further verification, and the gem's own documentation instructs host apps to use `data.shop` directly to route/attribute work (e.g., `perform_later(topic: data.topic, shop_domain: data.shop, ...)`): [4](#0-3) 

The equality the gem implicitly claims is: `shop header == identity of the merchant whose data produced this HMAC-signed body`. In reality the HMAC only proves `body == HMAC⁻¹(secret, hmac)`; it proves nothing about which shop the body came from. Since the app's `api_secret_key` is shared across every shop that installs the app, an unprivileged attacker who installs the app on their own store can trigger a real webhook (e.g., `orders/create`) and receive a body+HMAC pair that Shopify legitimately signed with the app's secret. The attacker can then POST that exact body/HMAC pair to the app's webhook endpoint while substituting the `shop-domain` header (and, if desired, `topic`/`webhook_id`) with a victim shop's domain. `HmacValidator.validate` still succeeds (it only checks the body), and `Registry.process` reports the event as originating from the victim shop.

### Impact Explanation
This is a cross-tenant identity-binding break: the gem asserts a "verified" `shop` value to the host application's webhook handler that is not actually bound to the HMAC proof. Any host app that follows the gem's documented pattern of trusting `data.shop` to select which merchant's records to update, notify, or act on can be tricked into applying an attacker-controlled event/body under another merchant's identity — a cross-tenant confusion vulnerability.

### Likelihood Explanation
The attacker only needs to be an installer of the public app on their own store (no leaked credentials, no privileged account) and the ability to send an arbitrary HTTP POST to the app's public webhook endpoint — both are unprivileged-internet-user capabilities. Obtaining a validly-signed body is trivial (trigger any webhook-generating action in their own store).

### Recommendation
Bind the `shop` (and other identifying metadata) into the signed payload, or independently verify the `shop` header against the shop associated with the specific `webhook_id`/subscription (e.g., cross-reference against a known/registered shop record) before trusting it in `WebhookMetadata`. At minimum, document prominently that `shop`, `topic`, `webhook_id`, and `api_version` are **not** cryptographically bound to the HMAC and must not be used as an authorization or tenant-attribution boundary without additional verification (e.g., checking against a shop record with an active access token).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook subscription event (e.g., updates an order), causing Shopify to POST a body `B` with a header `x-shopify-hmac-sha256: H` to the app's callback URL, where `H = HMAC-SHA256(app_secret, B)`.
2. Attacker intercepts/observes this legitimate request (e.g., via a proxy in their own browser/server they control, since it's their own webhook delivery).
3. Attacker crafts a new POST to the same app webhook endpoint with:
   - Body: `B` (unchanged)
   - Header `x-shopify-hmac-sha256`: `H` (unchanged, still valid since HMAC only covers `B`)
   - Header `x-shopify-shop-domain`: `victim-shop.myshopify.com` (forged)
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only compares `HMAC(app_secret, B)` to `H`.
5. `Registry.process` invokes the handler with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)`, causing the host app to process the attacker's data as if it belonged to `victim-shop`.
