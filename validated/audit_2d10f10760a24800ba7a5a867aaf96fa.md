### Title
Predictable, unsigned session identifier stored in a plain cookie enables session fixation / cross-tenant session hijack - (File: `lib/shopify_api/utils/session_utils.rb`, `lib/shopify_api/auth/session.rb`, `lib/shopify_api/auth/oauth/session_cookie.rb`)

### Summary
For non-embedded apps (and as a fallback for embedded apps without a JWT), `ShopifyAPI::Utils::SessionUtils.current_session_id` trusts the raw value of the `shopify_app_session` cookie as the authoritative session identifier used to look up a merchant's stored `Session` (and therefore their access token) — with no cryptographic binding between the cookie bytes and the identity that set them. Combined with the fact that `Session` IDs are deterministically derived from public/guessable data (`"offline_#{shop}"` or `"#{shop}_#{associated_user_id}"`), this breaks the intended binding: `cookie value == authenticated shop's session id`, versus what actually happens: `cookie value == attacker-chosen bytes`.

### Finding Description
`ShopifyAPI::Auth::Session.from` builds session ids purely from the shop domain and user id, with no random or secret component: [1](#0-0) 

These ids are placed verbatim into a plaintext cookie value after OAuth completes for non-embedded apps: [2](#0-1) 

`SessionCookie` itself carries no signature or MAC — it is a plain `name`/`value`/`expires` struct: [3](#0-2) 

On every subsequent request, `SessionUtils.current_session_id` reads this cookie back and returns its value unchanged as the session id to be used for storage lookup, performing no validation that the value corresponds to a session actually issued to the requester: [4](#0-3) [5](#0-4) 

Because the id format (`offline_#{shop}` or `#{shop}_#{user_id}`) is fully deterministic and the shop domain is public information (and user ids are often low, sequential integers), any unprivileged internet user who can influence the victim's cookie jar for the app's domain (e.g. cookie tossing from a sibling/subdomain, a response-splitting or header-injection bug in the host app, or simply supplying the value directly against a non-browser client that trusts the header) can set `shopify_app_session=offline_victim-shop.myshopify.com`. The gem's `current_session_id` will hand that attacker-chosen string straight to the host application's session storage as if it were the caller's own authenticated session id. If the host looks up a `Session` object with that id, it retrieves the victim merchant's stored access token and serves it to the attacker's request — a cross-tenant session fixation, breaking the identity binding `session id ⇔ the party that completed OAuth for that shop`.

This is the JWT/HMAC-verification pattern's exact structural analog: whereas `Auth::Oauth::AuthQuery`'s fields are protected by an HMAC computed with `Context.api_secret_key` before being trusted, and `Auth::JwtPayload` requires a valid HS256 signature before any claim is trusted, the cookie-derived session id path has **no equivalent verification step** — `cookie_session_id` (`lib/shopify_api/utils/session_utils.rb:68-71`) simply returns `cookies[...]` unchecked.

### Impact Explanation
This directly maps to the "session fixation" High-impact category: an unprivileged network attacker can force or hijack a session bound to another merchant's shop, resulting in the host application retrieving and using another tenant's stored access token on the attacker's behalf — a cross-tenant access condition.

### Likelihood Explanation
The precondition is that an attacker can set an arbitrary value for the `shopify_app_session` cookie in the victim's browser for the app's origin (or directly control the header value against a non-browser client). This is a common bug class (cookie tossing on shared parent/sibling domains, reflected cookie-setting bugs, or lax `SameSite`/domain scoping in host apps) and is made trivially exploitable here specifically because the target value is 100% deterministic and requires no guessing — the attacker only needs to know the victim's shop domain (public) and, for online sessions, the numeric Shopify user id.

### Recommendation
Do not use a raw, predictable string as both the cookie value and the session-storage lookup key. Either:
- Use a randomly generated, unguessable session cookie value that is mapped server-side to the real session id (indirection), or
- HMAC/sign the cookie value with `Context.api_secret_key` and verify the signature in `SessionUtils.current_session_id`/`cookie_session_id` before trusting it, mirroring the `Utils::HmacValidator` pattern already used for OAuth callbacks.

### Proof of Concept
1. Merchant `victim-shop.myshopify.com` completes OAuth for a non-embedded install; `ShopifyAPI::Auth::Oauth.validate_auth_callback` sets cookie `shopify_app_session=offline_victim-shop.myshopify.com` [6](#0-5) .
2. An attacker who can set a cookie for the app's origin on a different (target) browser sets `shopify_app_session=offline_victim-shop.myshopify.com` directly — no secret or guessing required, since the id is derived only from the public shop domain (`lib/shopify_api/auth/session.rb:116`).
3. When that browser calls the host app, it calls `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)`, which returns `"offline_victim-shop.myshopify.com"` unchanged (`lib/shopify_api/utils/session_utils.rb:19-37,63-71`).
4. The host app's session storage returns the victim's persisted `Session` (including `access_token`), and the attacker's subsequent Admin API calls run under the victim's stored access token.
