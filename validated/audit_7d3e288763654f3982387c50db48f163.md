### Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw JSON body, so `Utils::HmacValidator.validate` only proves that the *body bytes* were signed by the app's `client_secret`. The `shop` value that `Registry.process` extracts and forwards to the webhook handler comes from the `X-Shopify-Shop-Domain` header, which is completely outside the HMAC's signed content. Because a single `api_secret_key` is shared across every shop that installs the app, any merchant who has the app installed can replay a legitimately-signed webhook they received for their own store while swapping only the shop-domain header, and the HMAC check will still pass — binding the wrong tenant identity to trusted (and cryptographically "verified") request data.

### Finding Description
The equality the code implicitly (and incorrectly) assumes is:

`shop asserted by X-Shopify-Shop-Domain header == shop that produced the HMAC-signed body`

but the gem never enforces this. The signable string is defined as: [1](#0-0) 

`shop` is read straight from an unauthenticated header, disjoint from the signed bytes: [2](#0-1) 

`Registry.process` validates the HMAC only over `request` (i.e., only the body), then immediately trusts `request.shop` as the tenant identity passed to the app's handler: [3](#0-2) 

`HmacValidator.validate` computes/compares the signature purely against `to_signable_string`, i.e., the raw body — it has no knowledge of, or binding to, the shop header at all: [4](#0-3) 

Since `Context.api_secret_key` is the single app-wide client secret shared by every shop that installs the app, a shop's own legitimately delivered webhooks are valid, HMAC-signed `(body, hmac)` pairs under that same shared secret. Nothing prevents an attacker who controls one installed shop from capturing such a pair and re-submitting it to the app's webhook endpoint with a forged `X-Shopify-Shop-Domain` (or `X-Shopify-Webhook-Id`) header pointing at a different, victim shop. `Registry.process` will validate the HMAC (body unchanged, so it passes) and then hand the handler a `WebhookMetadata` object asserting the victim's shop domain alongside attacker-chosen body content.

### Impact Explanation
Any host application that relies on `WebhookMetadata#shop` (as forwarded by this gem) to scope tenant data — e.g., updating per-shop settings, writing customer/order records, or triggering actions "for" a shop based on webhook content — can be made to attribute attacker-controlled webhook payloads to an arbitrary victim shop. This is a cross-tenant integrity/confusion vulnerability rooted entirely in this gem's `Request`/`Registry` design: the field used to identify the tenant (`shop`) is never bound to the cryptographic proof of authenticity (`hmac`), even though the gem presents `HmacValidator.validate(request)` as if it authenticates the whole request.

### Likelihood Explanation
Exploitation requires only that the attacker be a legitimate merchant with the app installed (no special access, no leaked secrets, no privileged account) — precisely the "unprivileged internet user" class this analysis targets. They need nothing more than a webhook payload their own store already legitimately received (fully within their control to trigger, e.g. by placing an order) and the ability to POST an HTTP request with a modified header to the app's public webhook endpoint.

### Recommendation
Include the identity fields that the application relies on (at minimum `shop`, and ideally `topic`/`webhook-id`) in the HMAC-signable content, or otherwise cryptographically bind the header-derived `shop` to the verified payload before it is handed to `WebhookMetadata`/the handler. At minimum, document and/or enforce that `shop` must be cross-checked against a known, previously-authorized shop record before being trusted as a tenant key.

### Proof of Concept
1. App merchant "attacker.myshopify.com" has the app installed and receives a legitimate `orders/create` webhook:
   - Headers: `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`
   - Body: `{"id": 1, ...attacker-controlled order fields...}`
2. Attacker replays this exact body and HMAC to the app's public webhook endpoint but changes the header to `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `Request#to_signable_string` returns the (unmodified) raw body, so `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:12-31`) still succeeds because the signature was computed over the body only.
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-199`) passes `shop: request.shop` = `"victim.myshopify.com"` to the app's handler, along with the attacker's forged body content, despite the HMAC never having validated any binding between this shop and this body.
