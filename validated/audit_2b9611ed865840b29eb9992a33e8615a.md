The Nomad bug is a DoS caused by an **unbounded, attacker-growable queue** that must be linearly scanned (`contains()` iterating `_q.first..=_q.last`) to validate a root. I searched the in-scope Raydium AMM surface (`Initialize2`, `Deposit`, `Withdraw`, the four swap instructions, PDA/account checks, `AmmInfo`/`AmmConfig`/`TargetOrders` loading, swap/LP math, decimal normalization, pnl accounting, and the SPL CPIs in `invokers.rs`) for an analogous pattern and found none.

The only queue-like data structure in scope is `TargetOrders`, which contains fixed-size arrays (`buy_orders: [TargetOrder; 50]`, `sell_orders: [TargetOrder; 50]`, `replace_buy_client_id`/`replace_sell_client_id: [u64; MAX_ORDER_LIMIT]`) [1](#0-0) . These are fixed-capacity, not attacker-growable, and per the instruction docs the `target_orders` account is explicitly "no longer used in the contract" for the swap paths [2](#0-1) . No code in `process_deposit`, `process_swap_base_in`, or `process_swap_base_out` iterates over a dynamically-sized, user-appendable collection to validate state — these functions perform fixed-size decimal/pnl math and direct account/field comparisons instead [3](#0-2) [4](#0-3) .

Since there is no unbounded queue an unprivileged swapper/LP can grow and force an O(n) or worse scan during a reachable instruction, the Nomad-style queue-DoS bug class does not have a valid analog in the in-scope code.

        let _market_info = next_account_info(account_info_iter)?;
