### Title
Archived position-NFT `Owner` entry permanently orphans a live account — bad debt cannot be liquidated or socialized — (File: contracts/controller/src/storage/account.rs)

### Summary
`try_account_owner` resolves account ownership exclusively through the position-NFT `owner_of` read, and returns `None` when that read fails, which `get_account`/`account_owner` convert into `AccountNotFound`. The NFT's `Owner(token_id)` entry is a persistent key with a finite user-window TTL; it is only renewed by `PositionNft::renew`/`renew_account` paths, while `account_exists` renews only `ControllerKey::AccountMeta`. An unprivileged keeper can keep `AccountMeta` alive past the `Owner` entry's expiry, at which point every path that loads the account — `liquidate`, `clean_bad_debt`, `force_socialize_bad_debt`, `withdraw`, `repay` — traps on a dereference of a missing object, the exact analog of the CVE-2022-38096 NULL-deref class (state pointer resolves to nothing → permanent failure on that object).

### Finding Description
`try_account_owner` fails closed on any failed NFT lookup: `try_get_position_nft(env)?` then `nft_try_owner_of_call`, returning `None` on missing/burned/archived token (contracts/controller/src/storage/account.rs:35-44). `get_account` turns that `None` into `AccountNotFound` (account.rs:146-149). The NFT `Owner(token_id)` entry is persistent storage renewed only to the user window at mint and on explicit renew (contracts/position-nft/src/contract.rs:34-46, 68-76). `account_exists` renews only `AccountMeta` — not the position maps and not the NFT `Owner` entry — so an attacker can cheaply keep the metadata leg alive while the ownership leg archives. Once `Owner` is archived, `Base::owner_of` traps, `PositionNft::renew` itself panics on the existence check (contract.rs:109-115), and no path can restore the entry: the controller's own `renew_account` calls the NFT renew, so recovery is impossible.

The test suite confirms the resulting state is terminal: with the owner leg unreadable and all controller-side entries intact, `try_liquidate` returns `ACCOUNT_NOT_FOUND` and both `try_clean_bad_debt` and `try_force_socialize_bad_debt` fail identically (tests/test-harness/tests/controller/position_nft_ttl_and_ownership_reads.rs:286-333).

### Impact Explanation
Permanent freezing of funds and protocol insolvency. The orphaned account's collateral shares can never be withdrawn (every owner path loads `get_account`), its debt can never be liquidated, repaid-into, or socialized — `socialize_bad_debt` dereferences the same missing owner and aborts, so even a dust-eligible bad-debt book is stuck on `get_spoke_usage` totals forever, and the physical pool cash backing the dead collateral is locked. A targeted attacker can pick a large undercollateralized or dormant position, hold `AccountMeta` alive via the permissionless `account_exists`, wait out the `Owner` TTL, and permanently strand both the victim's collateral and the market's bad-debt wind-down.

### Likelihood Explanation
Likelihood is moderate: it requires the victim to leave the account untouched beyond the user TTL window while an attacker periodically calls the gas-cheap `account_exists` — no authorization, no privileged role, no NFT burn needed. Dormant accounts with collateral are common in lending markets, and the attacker's only cost is a periodic read call.

### Recommendation
Decouple account liveness from the NFT `Owner` entry's TTL, or make `owner_of`-independent recovery possible:

- Store a durable `owner` fallback in `AccountMeta` (or an owned persistent entry renewed with it) and have `try_account_owner` fall back to it when the NFT read fails, treating NFT ownership as authoritative only while readable.
- Alternatively, have `account_exists` (and every controller path that renews `AccountMeta`) also renew the NFT `Owner` entry via the existing permissionless `PositionNft::renew`, so no asymmetric expiry is reachable.
- Add a recovery path in `PositionNft` (e.g., controller-only `restore_owner(token_id, owner)` callable from a `recapitalize`-style recovery verb) so an archived `Owner` entry does not permanently brick liquidation and bad-debt cleanup.

### Proof of Concept
```rust
// Harness sketch (see tests/test-harness/tests/controller/
// position_nft_ttl_and_ownership_reads.rs for the burn-based twin).
let mut t = LendingTest::new().standard_two_asset().build();
t.supply(VICTIM, "USDC", 10_000.0);
t.borrow(VICTIM, "ETH", 3.0);
let id = t.account_id(VICTIM);

// Attacker keeps only AccountMeta alive; victim stays dormant.
loop_until_owner_ttl_expires(|| {
    t.ctrl_client().account_exists(&id); // renews AccountMeta only
});

// Owner(token_id) has archived; account state is still live.
assert!(t.account_exists(id));

// PositionNft::renew panics on owner_of -> no recovery.
// Every account-loading path fails closed:
t.set_price("USDC", usd_cents(50)); // position now liquidatable
assert_contract_error(t.try_liquidate(LIQUIDATOR, VICTIM, "ETH", 1.0),
                      errors::ACCOUNT_NOT_FOUND);
assert_contract_error(flatten(t.ctrl_client().try_clean_bad_debt(&KEEPER, &id)),
                      errors::ACCOUNT_NOT_FOUND);
assert_contract_error(flatten(t.ctrl_client().try_force_socialize_bad_debt(&id)),
                      errors::ACCOUNT_NOT_FOUND);
// Bad debt is permanent; collateral is permanently frozen.
```

The burn-based equivalents already pass as tests in `position_nft_ttl_and_ownership_reads.rs:286-333`; the TTL path produces the identical terminal state without any privileged call.
