## Title
`coin::freeze_coin_store` freezes only the legacy `CoinStore`, not the paired FungibleAsset primary store, letting a "frozen" holder keep transferring the same balance - (File: `aptos-move/framework/aptos-framework/sources/coin.move`)

### Summary
Aptos coins now have two parallel custody representations for the same underlying value: the legacy `CoinStore<CoinType>` and the paired `FungibleStore` created via `coin::ensure_paired_metadata`/`primary_fungible_store`. This mirrors the ERC721/ERC1155 dual-standard issue in the original report: a single asset can be moved through two different code paths, and a security check applied to one path silently fails to cover the other. Here, `freeze_coin_store` sets `frozen = true` only on the `CoinStore<CoinType>` resource [1](#0-0) , while the modern `coin::transfer`/`deposit`/`withdraw` entry points route balance through `primary_fungible_store`, which checks frozen state on the FA `FungibleStore`, not `CoinStore.frozen` [2](#0-1) .

### Finding Description
`coin::freeze_coin_store<CoinType>` / `unfreeze_coin_store` mutate only `borrow_global_mut<CoinStore<CoinType>>(account_addr).frozen` [3](#0-2) . This is the only entry point guarded by `FreezeCapability<CoinType>` for restricting a coin holder.

However, coin balances also exist as `FungibleAsset` in a "paired" `FungibleStore` object, created by `ensure_paired_metadata` and used by `primary_fungible_store` [4](#0-3) . Modern coin operations — `coin::transfer`, `coin::deposit`, `coin::withdraw` — no longer touch `CoinStore.frozen` at all; they call `primary_fungible_store::withdraw`/`deposit`, which operate on the FA `FungibleStore` and enforce freeze state via `fungible_asset::is_frozen`/sanity checks tied to that store, completely independent of `CoinStore.frozen` [5](#0-4) [2](#0-1) .

The freeze/unfreeze primitive for the FA side is a completely different capability: `TransferRef::set_frozen_flag`, gated by `PairedFungibleAssetRefs.transfer_ref_opt`, not by `FreezeCapability<CoinType>` [6](#0-5) . `freeze_coin_store` never calls this.

Consequently, once a holder has any balance in the paired FA primary store (which happens automatically the moment a value transfer occurs through `coin::deposit`/`transfer`, or via `migrate_to_fungible_store`), calling `freeze_coin_store` on that holder's `CoinStore` has **no effect** on funds sitting in — or moving through — the FA store. The holder can continue to call `primary_fungible_store::transfer`, `dispatchable_fungible_asset::transfer`, or even `coin::transfer` itself (which now writes to the FA store, not `CoinStore`) to move the "frozen" balance freely.

This is the same class of bug as the ERC721/ERC1155 duplicate-interface issue: an authority (compliance/freeze capability holder) reasonably assumes a single check governs the asset, but because the asset has two live custody representations, one of which the check does not cover, the invariant "frozen state blocks transfer" is broken for the majority of real-world flow.

### Impact Explanation
Freeze capability is a custody-control primitive used for compliance, sanctions enforcement, or incident response on coin holders (e.g., a stolen-funds freeze). If `freeze_coin_store` is believed to halt an account's ability to move `CoinType` value but the balance actually lives in (or is later moved into) the paired FA store, the holder retains full, unimpeded custody and transfer rights over the value. This breaks a core custody invariant: "freeze control must be enforceable over all live representations of the asset." Since APT itself and most tokens are being migrated to primary-fungible-store-backed accounting, this affects mainnet-relevant, high-value asset control.

### Likelihood Explanation
Likelihood is high for any `CoinType` that has an active coin/FA pairing (created via `create_pairing`/`ensure_paired_metadata`, which happens automatically on first `coin::deposit`/`transfer`/`withdraw` call for a type). Any freeze-capability holder invoking the legacy `freeze_coin_store` API without independently also disabling ungated transfer or setting the FA-side frozen flag will produce this gap; no privileged bypass is needed by the attacker — they simply keep using normal transfer functions on their own account.

### Recommendation
Make `freeze_coin_store`/`unfreeze_coin_store` also set the frozen flag on the paired FungibleStore (via the stored `TransferRef` in `PairedFungibleAssetRefs`), or deprecate/disallow use of `freeze_coin_store` once a coin has a paired FA metadata object and require callers to use the FA-native freeze path (`primary_fungible_store::set_frozen_flag`) that acts on the actual custody store used by `coin::transfer`/`deposit`/`withdraw`.

### Proof of Concept
1. Coin type `X` is initialized, `FreezeCapability<X>` granted to an issuer/compliance account.
2. User `A` performs any `coin::deposit`/`coin::transfer`/`coin::withdraw` of `X`, which lazily creates the paired FA metadata and moves `A`'s balance into `A`'s primary `FungibleStore` for `X` (`ensure_paired_metadata` + `primary_fungible_store::deposit`) — see `coin::transfer` and `coin::deposit` at [5](#0-4) .
3. Issuer calls `coin::freeze_coin_store<X>(A, &freeze_cap)`, setting `CoinStore<X>[A].frozen = true` [1](#0-0) .
4. `A` calls `coin::transfer<X>(A, B, amount)` or `primary_fungible_store::transfer` directly. Since `A`'s balance is in the FA store (with 0 or negligible balance in `CoinStore<X>`), the transfer succeeds because it never inspects `CoinStore<X>.frozen`.
5. `A` has fully bypassed the freeze, retaining custody/transfer control the issuer believed was revoked.

I was unable to execute this against a live Move VM/test harness in this session (read-only code index), so step 4's exact abort/success behavior should be confirmed with a unit test exercising `freeze_coin_store` followed by `coin::transfer` on an account whose balance lives in the paired FA store, to fully validate the exploit path before remediation.
