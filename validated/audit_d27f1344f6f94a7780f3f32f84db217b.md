### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) headers are not covered by the HMAC, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw body, so the HMAC signature Shopify sends only authenticates the JSON payload bytes, not the `shop-domain`, `topic`, `webhook-id`, or `api-version` HTTP headers. `Registry.process` treats the request as fully authentic (`raise ... unless Utils::HmacValidator.validate(request)`) and hands `request.shop` straight to the app's `WebhookHandler` via `WebhookMetadata`, so any component that trusts `data.shop` to select per-tenant state is trusting an unauthenticated header.

### Finding Description
The identity binding that should hold is: `hmac == HMAC(secret, raw_body ∪ shop ∪ topic ∪ webhook_id ∪ api_version)`. In reality it is `hmac == HMAC(secret, raw_body)` only [1](#0-0) , while `shop`, `topic`, `webhook_id`, and `api_version` are read from headers that sit entirely outside the signed material [4](#0-3) , [5](#0-4) .

`HmacValidator.validate` only checks `verifiable_query.to_signable_string` against the secret [6](#0-5) , which for a `Webhooks::Request` is exactly the raw body and nothing else. `Registry.process` gates entirely on this single check before dispatching to the app-supplied handler with `WebhookMetadata.new(topic: request.shop, ... )` — actually `shop: request.shop`, `topic: request.topic`, etc. — all sourced from the unauthenticated headers [3](#0-2) .

Because an app owner (or any attacker who has ever legitimately installed the app on a shop they control) can capture one valid `(raw_body, hmac)` pair for their own tenant, they can freely replay it to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` (or `shopify-shop-domain`) header for a victim shop's domain. The signature still validates because the signature never covered that header, yet the app's handler receives `WebhookMetadata#shop == "victim-shop.myshopify.com"` paired with attacker-controlled body content. Any handler logic that uses `data.shop` to select which tenant's session/storage to update (a common and encouraged pattern per `docs/usage/webhooks.md`) will apply attacker-supplied webhook content under the victim's identity — a cross-tenant write/confusion primitive rooted entirely in this gem's `Request`/`Registry` design, not in host-application misuse.

### Impact Explanation
This breaks the tenant identity binding between the cryptographically verified payload and the shop it is attributed to, enabling cross-tenant data confusion: content that was only ever signed for shop A can be delivered to the application labeled as belonging to shop B. Depending on how the host app's `WebhookHandler#handle` implementation keys per-shop state (which is the intended, documented usage of `WebhookMetadata#shop`), this can corrupt or leak another merchant's data — matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Any actor who can install the target app on a shop they control (a normal, unprivileged onboarding flow, not a privileged action) can obtain arbitrarily many valid `(body, hmac)` pairs for topics they choose, then replay them with a forged `shop-domain` header at the public webhook endpoint. No access token, `client_secret`, or TLS interception is required — only observation/control of one's own tenant's outbound webhooks.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `webhook-id`, `api-version`) header values in the HMAC-signed material, or independently verify that `request.shop` corresponds to a shop with an active, registered webhook subscription for the given `webhook_id`/`topic` before constructing `WebhookMetadata`. At minimum, `Request#to_signable_string` in `lib/shopify_api/webhooks/request.rb` should not omit fields that downstream handlers are expected to trust for tenant scoping.
