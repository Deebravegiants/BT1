### Title
Stale `operator_qr_expiration_time` config snapshot in `MasterPlan::run` allows a shortened QR-expiration policy update to be ignored for the lifetime of the signup loop - ([File: src/plans/mod.rs])

### Summary
`MasterPlan::run` captures the `operator_qr_expiration_time` config value once, before entering its signup loop, and reuses that stale value for every iteration to decide whether a previously scanned operator QR code is still valid. Meanwhile, the backend can push a new configuration (with a different `operator_qr_expiration_time`) at any time via the background config-update task, and `do_signup` re-reads the config fresh on every signup. The two code paths that gate the same "is this operator QR still valid" decision therefore consult two different snapshots of the same config value, exactly analogous to the reported bug where changing `stakeToken` did not account for state (locked balances/records) created under the previous configuration.

### Finding Description
`MasterPlan::run` destructures `Config` (including `operator_qr_expiration_time`) once at the top of the function, outside its `loop { ... }`: [1](#0-0) 

This same, never-refreshed `operator_qr_expiration_time` value is threaded into `scan_initial_qr_codes`, which is the function that decides whether an already-cached `OperatorData` (holding the operator QR code plus a `timestamp` from when it was scanned) is still considered valid or must be rescanned: [2](#0-1) 

`OperatorData`/`QrCodes` persist across loop iterations (`initial_qr_codes` is declared outside the loop), so a single scanned operator QR code can be reused for many subsequent signups as long as `ts.elapsed() > operator_qr_expiration_time` is false, using the *original* boot-time value of `operator_qr_expiration_time`.

In contrast, `do_signup` re-reads the config from the shared `Arc<Mutex<Config>>` fresh on every signup: [3](#0-2) 

The shared config object itself can be swapped out at any time by the background observer task, which downloads a new config from the backend and replaces the whole object: [4](#0-3) 

If an operator (backend administrator) updates `operator_qr_expiration_time` to a *shorter* value (e.g., to force more frequent re-verification of an operator's badge, perhaps in response to a compromised/stolen operator QR code), the already-running `orb-core` process never refreshes the value used by `scan_initial_qr_codes`. The stale, longer expiration window governing whether the cached operator QR must be rescanned continues to apply for the entire remaining lifetime of the `MasterPlan::run` loop (which can span many independent signups), even though `do_signup`'s own config re-read would reflect the new, shorter value for other purposes within the same signup.

### Impact Explanation
This creates a signup-authorization inconsistency: policy tightening intended to shorten how long an operator's QR code/session can be trusted between signups is silently ignored by the code path that actually governs whether to force a fresh operator QR scan. An operator badge whose validity window was intentionally reduced by the backend continues to authorize new signups under the old, longer window for as long as the orb-core process keeps running, undermining the intended freshness/re-authentication guarantee for operator-initiated signups.

### Likelihood Explanation
No attacker action beyond normal operation is required — this triggers automatically whenever the backend changes `operator_qr_expiration_time` while an orb is running its master loop (a supported, expected configuration hot-reload path, since `Config::download` runs periodically and unconditionally swaps in the new config). The condition is deterministic: `run()`'s locally captured value is never re-read for the remainder of the process's `loop`.

### Recommendation
Re-read `operator_qr_expiration_time` (and other config fields consumed at the top of `MasterPlan::run`) from `orb.config` on each loop iteration instead of capturing it once before the loop, so that policy updates from the backend take effect for the operator-QR-freshness check exactly as they do for the checks performed inside `do_signup`.

### Proof of Concept
1. Orb boots; `MasterPlan::run` captures `operator_qr_expiration_time = T1` (e.g., 60 minutes) at line 329-336 of `src/plans/mod.rs`.
2. Operator scans their QR code; `scan_initial_qr_codes` stores `OperatorData { timestamp: now, .. }`.
3. Backend operator shortens the policy, setting `operator_qr_expiration_time = T2` (e.g., 5 minutes), intending that operator QR codes must be rescanned after 5 minutes.
4. The background `config_update` task in `src/brokers/observer.rs` downloads the new config and swaps `*config.lock().await = new_config`, so `orb.config` now holds `T2`.
5. Back in the still-running `MasterPlan::run` loop, `scan_initial_qr_codes` is called again with the original, stale `T1` (never re-read), so `ts.elapsed() > T1` remains false well past the new 5-minute window — the operator QR is treated as still valid and additional signups proceed under it without a rescan, contrary to the newly configured policy.

    async fn scan_initial_qr_codes(
        &mut self,
        orb: &mut Orb,
        qr_codes: &mut QrCodes,
        self_serve: bool,
        operator_qr_expiration_time: Duration,
    ) -> Result<()> {
        if self_serve
            && qr_codes
                .operator_timestamp()
                .map_or(true, |ts| ts.elapsed() > operator_qr_expiration_time)
        {
            loop {
                let qr_capture_start = Instant::now();
                let operator_qr_code =
                    self.scan_operator_qr_code(orb, None).await?.expect("to never timeout");
                let Some(operator_qr_code) =
                    self.handle_magic_operator_qr_code(orb, operator_qr_code).await?
                else {
                    continue;
                };
                let Some((_, operator_location_data)) =
                    self.verify_operator_qr_code(orb, &operator_qr_code, qr_capture_start).await?
                else {
                    continue;
                };
                *qr_codes = QrCodes::Operator {
                    operator_data: OperatorData {
                        qr_code: operator_qr_code,
                        location_data: operator_location_data,
                        timestamp: Instant::now(),
                    },
                };
                break;
            }
        }
        Ok(())
    }

    fn config_update(&mut self, observer: &mut Observer) -> Result<()> {
        if self.before_config_update()? {
            match observer.config_update.as_mut().map(future::FutureExt::now_or_never) {
                Some(None) => return Ok(()),
                Some(Some(result)) => result??,
                None => {}

            let config = Arc::clone(&observer.config);
            let ui = observer.ui.clone();
            observer.config_update = Some(tokio::spawn(async move {
                if let Ok(new_config) = Config::download().await {
                    *config.lock().await = new_config;
                    config.lock().await.propagate_to_ui(ui.as_ref());
                }
                Ok(())
            }));
        }
        Ok(())
    }
