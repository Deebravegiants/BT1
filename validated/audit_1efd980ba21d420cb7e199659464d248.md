## Finding

### Title
Webhook shop identity is not covered by the HMAC signature, enabling cross-tenant webhook forgery - (`File: lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by verifying an HMAC over the raw request body, then blindly trusts the `X-Shopify-Shop-Domain` header (exposed as `request.shop`) as the tenant identity handed to the app's webhook handler. Because the HMAC secret (`Context.api_secret_key`) is a single value shared across *every* shop that has installed the app, a legitimately-onboarded (unprivileged) merchant can obtain a validly-signed webhook body for their own shop and replay it with a forged shop-domain header, causing the receiving app to process the payload as if it originated from a victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw HTTP body: [1](#0-0) 

`shop` is read from an unsigned header (`shopify-shop-domain` / `x-shopify-shop-domain`) with no cryptographic tie to the signature: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over `to_signable_string` (i.e., the body) using the app's static `api_secret_key`, which is identical for every shop that installed the app — it is not per-tenant: [3](#0-2) 

`Registry.process` validates only that HMAC, then constructs `WebhookMetadata` using the unauthenticated `request.shop` value and dispatches it straight to the app-supplied handler: [4](#0-3) 

**Equality that should hold but doesn't:** `shop_that_signed_this_body == shop_the_handler_is_told_it_is_for`. In reality, the HMAC only proves "this body was produced with this app's secret" — a fact true for *any* shop that has installed the app — while `shop` is a free-form header value never included in the signed material. An attacker who is a normal merchant with the app installed on their own store receives genuine, correctly-HMAC'd webhook deliveries (e.g., via Shopify's built-in webhook test/send feature, or simply by triggering any subscribed event on their own store). They can capture such a delivery and resend it to the app's webhook endpoint, substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. The HMAC still validates (it only checks the body), so `Registry.process` proceeds and calls the handler with `WebhookMetadata#shop == "victim-shop.myshopify.com"`.

### Impact Explanation
This breaks the tenant/shop identity binding relied upon by every consumer of this gem to key per-shop state, session lookups, and data-processing decisions from webhooks. Concretely:
- Mandatory GDPR webhook topics such as `shop/redact` and `customers/redact` are registered/dispatched through this same path; if a host app naively deletes/purges data keyed by `WebhookMetadata#shop`, a forged webhook lets an unprivileged attacker trigger data deletion for a shop they don't control.
- Any app logic gating on shop-scoped events (installs/uninstalls, order/customer processing, entitlement changes) can be spoofed cross-tenant, since the identity used to select "which shop's data/session to touch" is attacker-controlled while the code path presents it as Shopify-authenticated.
This qualifies as cross-tenant access (Critical), since the vulnerability lets one authenticated tenant (merchant) impersonate another tenant purely through this gem's webhook verification/dispatch contract, without needing the app's `client_secret`, an access token, or any privileged account.

### Likelihood Explanation
Exploitation requires only: (1) installing the target app as an ordinary merchant (a routine, unprivileged action any Shopify merchant can do if the app is publicly installable), and (2) capturing one genuine webhook delivery from their own shop and resending it to the app's public webhook endpoint with a modified shop-domain header. No secret leakage, TLS interception, or social engineering is needed — the app's own webhook secret is, by design, identical for every installing shop, and this gem never binds the shop identity into the signed payload or otherwise cross-checks it.

### Recommendation
Do not treat `shop` from `Webhooks::Request` as authenticated by the HMAC. Either:
- Include the shop domain in the signed material checked by `HmacValidator` (not possible without changing Shopify's webhook signing scheme), or, more practically,
- Require/encourage callers of `Registry.process`/`WebhookMetadata` to cross-validate `shop` against a known, previously-stored session/shop record (e.g., only accept `shop` values for shops the app has valid, on-file sessions/access tokens for) before acting on the payload, and document this requirement prominently since the gem currently implies HMAC validation alone is sufficient to trust `WebhookMetadata#shop`.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com`.
2. Attacker triggers (or uses Shopify's "Send test notification") any subscribed webhook topic, capturing the raw body `B` and the resulting `X-Shopify-Hmac-Sha256` header `H = HMAC-SHA256(api_secret_key, B)`.
3. Attacker resends an HTTP request to the app's webhook endpoint with the same body `B` and header `H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and `X-Shopify-Topic` to a topic of interest, e.g. `shop/redact`).
4. `ShopifyAPI::Utils::HmacValidator.validate(request)` returns `true` because it only checks `HMAC-SHA256(api_secret_key, B) == H`, which still matches.
5. `ShopifyAPI::Webhooks::Registry.process` invokes the app's handler with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, causing the host application to act on the victim shop's tenant context using attacker-supplied data.
