### Title
Webhook HMAC Covers Only the Raw Body, Allowing Cross-Tenant Shop/Topic Spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so `Utils::HmacValidator.validate` only proves that the *body bytes* were signed with the app's `client_secret` — it proves nothing about the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers that `Registry.process` reads and hands to the app's handler. This breaks the identity binding: "bytes verified" (the JSON body) ≠ "bytes parsed and trusted" (the shop/topic headers used for tenant routing).

### Finding Description
`Request#hmac` decodes the `hmac-sha256` header and `Request#to_signable_string` returns `@raw_body` only: [1](#0-0) 

`HmacValidator.validate` calls `verifiable_query.to_signable_string` and HMAC-compares it against the `hmac` field — i.e. it validates the body, nothing else: [2](#0-1) 

`Registry.process` only checks `Utils::HmacValidator.validate(request)` and then forwards `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` (all read straight from unauthenticated HTTP headers) to the app's handler as trusted `WebhookMetadata`: [3](#0-2) 

Because the app's `client_secret` (and therefore the resulting HMAC of a given body) is the same across every shop that has installed the app, any unprivileged user who installs the app on their own store receives real webhook deliveries with a valid `(body, hmac)` pair. Since the shop/topic headers are not part of the signed material, that same `(body, hmac)` pair remains valid no matter what `shop-domain`/`topic`/`webhook-id` headers are sent alongside it. An attacker can therefore POST the captured body/HMAC to the app's public webhook endpoint with a forged `shop-domain` header naming a different (victim) tenant, and `Registry.process` will accept it as authentic, handing the handler a `WebhookMetadata` whose `shop` is attacker-chosen but is treated by the host app as authenticated tenant identity for scoping data lookups/mutations against that shop's stored session.

### Impact Explanation
This is a cross-tenant confusion vector: the gem lets an attacker forge the tenant-identifying field (`shop`) of an accepted, "HMAC-validated" webhook, causing the host application to process attacker-controlled data under a victim shop's identity/session. This matches the Critical "cross-tenant access" category, since the tenant boundary (shop) is not covered by the only integrity check the gem performs.

### Likelihood Explanation
Likelihood is significant but not trivial: the attacker needs at least one genuine `(body, hmac)` pair, which any unprivileged party can obtain simply by installing the app on their own store and receiving a real webhook delivery (no secret leak, no privileged access required). From there, forging headers on a replayed POST to the app's public webhook endpoint requires only standard HTTP tooling.

### Recommendation
Bind the shop/topic/webhook-id/api-version headers into the signed material that `Utils::HmacValidator` verifies (e.g., include the canonicalized headers, or independently re-derive/verify `shop` against a known, previously-authenticated session before trusting it), so that the HMAC check enforces the full identity of the webhook event, not just the JSON body bytes.

### Proof of Concept
1. Install the target app on an attacker-owned development store; capture a legitimate webhook POST, e.g. `orders/create`, noting the raw body `B` and the `X-Shopify-Hmac-Sha256` header value `H` (valid because `H = HMAC(client_secret, B)`).
2. Craft a new POST to the app's webhook endpoint with the same body `B` and the same `X-Shopify-Hmac-Sha256: H`, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com` and any desired `X-Shopify-Topic`/`X-Shopify-Webhook-Id`.
3. `ShopifyAPI::Webhooks::Request.new` parses these headers unchanged: [4](#0-3) 
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `B`/`H`, then invokes the handler with `shop: "victim-shop.myshopify.com"`: [5](#0-4) 
5. The host application's handler now processes attacker-supplied data as if it were an authentic event from `victim-shop.myshopify.com`, breaking the shop/tenant identity binding.

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
