## Title
Webhook Shop/Topic Identity Not Covered by HMAC Signature Enables Cross-Tenant Webhook Forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC signable string from only the raw request body, while the `shop`, `topic`, `webhook_id`, and `api_version` fields are read verbatim from unauthenticated HTTP headers and then handed directly to the app's webhook handler as trusted tenant context.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns `@raw_body` only [1](#0-0) , and `shop`, `topic`, `webhook_id`, `api_version` are all pulled straight from HTTP headers with no cryptographic binding to the body or to each other [2](#0-1) .

`ShopifyAPI::Webhooks::Registry.process` validates the request purely via `Utils::HmacValidator.validate(request)`, which in turn verifies `to_signable_string` (i.e., only the raw body bytes) against `Context.api_secret_key` [3](#0-2) [4](#0-3) . Once this passes, `request.shop` (an unsigned header value) is forwarded unchecked into `WebhookMetadata` and passed to the app's handler as the authoritative tenant identifier [5](#0-4) .

Since `client_secret`/`api_secret_key` used for HMAC signing is shared across **all** shops that have installed a given app (it's a per-app secret, not per-shop), any merchant who installs the app can capture a validly-signed `(raw_body, hmac)` pair delivered to their own store's webhook endpoint. The `shop`/`topic`/`webhook_id` headers, being unauthenticated, can then be freely rewritten and replayed against the same public webhook endpoint while still passing `HmacValidator.validate`, because the signature check never covers those fields — this breaks the intended binding: `shop header == shop that produced the signed body`.

### Impact Explanation
This is a cross-tenant access vector: the app's webhook handler (per this gem's documented usage pattern, e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)` [6](#0-5) ) will process attacker-supplied body content while believing it originates from a victim shop, since `data.shop` is taken from the unsigned header. Depending on the host app's logic, this can inject or mutate data under another tenant's namespace, satisfying the Critical "cross-tenant access" criterion.

### Likelihood Explanation
Any user who can install the app on their own store (a fully unprivileged/self-service action for public apps) can obtain a genuine `(body, hmac)` pair from their own webhook deliveries and then send that exact byte-for-byte payload to the shared webhook endpoint with a forged `X-Shopify-Shop-Domain`/`X-Shopify-Topic` header of their choosing. No access token, `client_secret`, or privileged credential is required — this is achievable purely through documented webhook processing behavior in `lib/shopify_api/webhooks/`.

### Recommendation
Bind the `shop`, `topic`, and `webhook_id` values into the signable material verified by `HmacValidator`, or otherwise cross-check them against Shopify's canonical webhook metadata (e.g., resolve the topic/shop via the `webhook_id` through the Admin API) before trusting them as tenant context. At minimum, document that `data.shop`/`data.topic` are unauthenticated and must not be used as the sole tenant key without additional verification.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and receives a legitimate webhook: body `B`, header `X-Shopify-Hmac-Sha256: H` (valid signature of `B` under the app's shared `api_secret_key`), `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Attacker sends a new HTTP POST to the app's public webhook endpoint with the identical body `B` and `H`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers, and `Registry.process` calls `HmacValidator.validate(request)`, which only checks `H` against `B` — it passes [7](#0-6) .
4. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and attacker-controlled `body`, processing it as if it came from the victim tenant.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

        end

          received_signature = verifiable_query.hmac
