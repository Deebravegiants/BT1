## Analog Found: Unchecked Low-Level ERC20 `transfer` in Tron `IntentGatewayV2.withdraw()`

### Title
Unsafe raw `.call()` to ERC20 `transfer` ignores return-value in escrow withdrawal, permanently freezing user/solver funds for non-reverting-false tokens - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` imports and uses `SafeERC20` for input escrow (`placeOrder` uses `safeTransferFrom`), but its escrow-release path (`withdraw()`) and the `SweepDust` admin handler bypass `SafeERC20` and instead make a raw low-level `.call()` to the `transfer` selector, checking only that the call didn't revert — not that the token's returned boolean is `true`.

### Finding Description
`IntentGatewayV2` (Tron) declares `using SafeERC20 for IERC20;` [1](#0-0)  and correctly uses `safeTransferFrom` when escrowing inputs in `placeOrder` [2](#0-1) . However, the `withdraw()` function — which releases escrowed tokens to a beneficiary when a `RedeemEscrow`/`RefundEscrow` message is delivered via `onAccept` — instead performs:

```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
``` [3](#0-2) 

The same pattern is used for fee transfers and dust sweeping in the same function/handler: [4](#0-3) [5](#0-4) 

`bool success` from a low-level `.call()` only reflects whether the callee reverted — it does not validate the ABI-encoded boolean return value of `transfer`. Any ERC20 token that returns `false` on a failed transfer (instead of reverting) — e.g., tokens with blacklist/pause logic — will cause `success == true` even though no tokens moved.

Immediately afterward, escrow accounting is unconditionally decremented and the order is finalized: [6](#0-5) 

### Impact Explanation
Because `_orders[body.commitment][token] -= amount` executes and `_filled[body.commitment] = beneficiary` is set regardless of whether the token transfer actually succeeded, a failed-but-non-reverting `transfer` call permanently freezes the beneficiary's expected output: the escrow slot is emptied and the order is marked filled/refunded, so the funds can never be reclaimed by the intended solver or user, and they remain permanently stuck in the `IntentGatewayV2` contract balance with no recovery path. This is a direct, unbacked-freeze-of-funds impact on the intents escrow settlement flow, reachable purely by delivering a relayed cross-chain settlement message (`onAccept` → `withdraw`) for an order that uses such a token.

### Likelihood Explanation
This path is reached anytime a cross-chain order is filled or refunded and the escrowed/output token is a non-standard ERC20 that can return `false` on failure (a documented category of "weird ERC20" tokens routinely enumerated in intents/bridge audits). Any user or solver placing an order denominated in such a token — either intentionally or because the token is later paused/blacklists an address — triggers the vulnerable branch without needing any privileged role.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` pattern in `withdraw()` and the `SweepDust` handler with `IERC20(token).safeTransfer(beneficiary, amount)`, consistent with the `SafeERC20` usage already present elsewhere in the same file (e.g., `placeOrder`'s `safeTransferFrom` calls).

### Proof of Concept
1. Deploy a mock ERC20 whose `transfer` returns `false` instead of reverting when the recipient is blacklisted (mirrors real-world non-compliant tokens).
2. User places a cross-chain order on the source chain escrowing this token via `placeOrder` (uses `safeTransferFrom`, succeeds normally).
3. Solver fills the order on the destination chain; the source-chain `IntentGatewayV2.onAccept` is invoked with a `RedeemEscrow` request once the fill message is relayed.
4. `withdraw()` is called with the solver as beneficiary; if the beneficiary is blacklisted (or the token conditionally returns `false`), `token.call(...)` still returns `success == true` (call didn't revert) even though `transfer` internally returned `false` and moved no tokens.
5. `_orders[body.commitment][token] -= amount` executes, `_filled[...]` is set, and `EscrowReleased` is emitted — the beneficiary receives nothing and the escrowed tokens remain stuck in the contract permanently, with no code path to retry or reclaim them.
