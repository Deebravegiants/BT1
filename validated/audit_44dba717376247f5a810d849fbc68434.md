Webhook `shop` identity is parsed from an unauthenticated header while the HMAC only covers the raw body, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook request as authenticated once `Utils::HmacValidator.validate` succeeds, and then dispatches the handler using `request.shop` taken from an HTTP header. The HMAC, however, is computed only over the raw request body, so the `shop` (and `topic`/`webhook_id`) attributes are never part of the signed bytes. An attacker who legitimately receives even one genuinely-signed webhook (e.g., by installing the app on their own Shopify development store) can replay that exact `(raw_body, hmac)` pair while substituting the `x-shopify-shop-domain` header for a victim shop's domain, and the request will still pass verification and be dispatched to the app's handler as if it came from the victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements the `Utils::VerifiableQuery` interface, which requires `hmac` and `to_signable_string`: [1](#0-0) 

For webhook requests, `to_signable_string` returns only the raw body, while `shop`, `topic`, `api_version`, and `webhook_id` are all pulled from HTTP headers that are entirely outside the signed data: [2](#0-1) 

`Utils::HmacValidator.validate` computes and compares the signature strictly against `to_signable_string`: [3](#0-2) 

`Registry.process` accepts the request purely on this HMAC check, then forwards the *header-derived* `shop` value straight to the app's handler as trusted identity: [4](#0-3) 

The equality the system is supposed to guarantee is: `shop delivered to handler == shop that produced/authorized the signed bytes`. In fact the code only proves `hmac == HMAC(raw_body, secret)`; it says nothing about which shop that body belongs to. Any two requests with the same body and same valid hmac but different `shop-domain` headers are treated identically as "verified" and are routed with whatever shop header the caller supplies. The gem's own documentation states that `Registry.process` "will verify the request did indeed come from Shopify," implying the whole webhook (including its shop attribution) is authenticated — but only the body bytes are actually checked (`docs/usage/webhooks.md`, "Process a Webhook" section).

### Impact Explanation
This breaks the shop/tenant identity binding at the point where the gem hands data to the host application. A user who has installed the app on their own (attacker-controlled) shop receives genuine, correctly-signed webhook deliveries for their own shop's events. By capturing one such `(raw_body, hmac)` pair and re-sending it to the app's webhook endpoint with the `x-shopify-shop-domain` (or `shopify-shop-domain`) header changed to a victim shop's domain, the attacker causes `ShopifyAPI::Webhooks::WebhookMetadata` to be built with `shop: <victim>` even though the body's content and cryptographic signature never involved the victim shop at all. Any host application that keys business logic on `data.shop` (as the gem's own documentation example does: `perform_later(topic: data.topic, shop_domain: data.shop, ...)`) will process attacker-supplied data as if it were authoritative content from the victim tenant — this is a cross-tenant data-integrity/authentication bypass reachable by any unprivileged user who can install the app on any shop (including a free development store), with no access token, `client_secret`, or credential theft required.

### Likelihood Explanation
Likelihood is high: any developer can install the target Shopify app on a free/dev store, capture one legitimate webhook (trivial, e.g., via a public endpoint or by triggering a store event), and replay it with a modified `shop-domain` header. No special privileges, secrets, or timing conditions are required, and the vulnerable code path (`Request#hmac`/`to_signable_string` and `Registry.process`) is exercised on every webhook delivery.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the value that is verified, not just trusted post-hoc from headers:
- Include the `shop-domain` (and `topic`) header value inside `to_signable_string` (analogous to how `Oauth::AuthQuery#to_signable_string` includes `shop`), or
- Require host applications to independently confirm that the `shop` in `WebhookMetadata` corresponds to a shop with an active app installation/session before processing, and document this explicitly rather than implying `process` fully "verifies the request did indeed come from Shopify" for all fields.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and registers a webhook (e.g. `orders/create`).
2. Attacker triggers an order-create event on their own store; Shopify sends a webhook POST with headers `x-shopify-hmac-sha256: <valid hmac of raw_body>` and `x-shopify-shop-domain: attacker.myshopify.com`, and some `raw_body`.
3. Attacker captures the exact `raw_body` and `x-shopify-hmac-sha256` value.
4. Attacker re-sends the identical `raw_body` and `x-shopify-hmac-sha256` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds a request whose `hmac` check passes (`to_signable_string` only ever considered `raw_body`), and `Registry.process` dispatches to the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)`.
6. The host application's handler (per the gem's documented pattern `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) processes attacker-controlled data under the victim shop's identity.
