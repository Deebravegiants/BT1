### Title
Withdraw Instruction Allows Optional/Absent Slippage Protection, Enabling Sandwich Attacks on LP Withdrawals - (File: program/src/processor.rs, program/src/instruction.rs)

### Summary
Unlike the GMX report's decrease/close position paths that hardcode `minOut: 0`, this program's analog is the `Withdraw` instruction, whose slippage-protection fields (`min_coin_amount`, `min_pc_amount`) are optional (`Option<u64>`) at both the wire-format and enforcement level. When these fields are omitted, `process_withdraw` skips the slippage check entirely and executes the withdrawal at whatever price the pool state dictates at execution time, exposing withdrawing LPs to sandwich/front-running attacks.

### Finding Description
The `WithdrawInstruction` struct defines `min_coin_amount` and `min_pc_amount` as `Option<u64>`: [1](#0-0) 

The instruction unpacker allows the caller to omit these fields entirely — if fewer than 16 trailing bytes are supplied, both default to `None`: [2](#0-1) 

In `process_withdraw`, the slippage check is only performed `if withdraw.min_coin_amount.is_some() && withdraw.min_pc_amount.is_some()`. If either is `None`, the withdrawal proceeds unconditionally with the `coin_amount`/`pc_amount` computed from the current (potentially manipulated) pool reserves: [3](#0-2) 

This is directly analogous to the GMX report's root cause: a state-changing, fund-moving instruction (`decreasePosition`/`closePosition` there, `Withdraw` here) that computes an output amount based on live market/pool state but does not enforce a minimum-received bound, because the protection mechanism is bypassable (hardcoded `minOut: 0` in GMX, `Option::None` here).

Contrast this with `SwapInstructionBaseIn`/`SwapInstructionBaseOut`, where `minimum_amount_out`/`max_amount_in` are non-optional `u64` fields that are unconditionally checked (`swap_amount_out < swap.minimum_amount_out` and `swap.max_amount_in < swap_in_after_add_fee` both return `AmmError::ExceededSlippage` if violated): [4](#0-3) [5](#0-4) 

The `Deposit` path similarly guards `other_amount_min` optionally, but deposit already self-bounds risk via `max_coin_amount`/`max_pc_amount` (a hard cap on the side not marked as `base_side`), so the exposure is asymmetric and smaller there. `Withdraw` has no equivalent hard cap on the amounts a user receives — `coin_amount`/`pc_amount` are entirely output-side and only protected by the optional min check.

### Impact Explanation
An attacker (e.g., an MEV searcher/validator with mempool visibility, or a sandwicher submitting bracketing swap transactions) can observe a pending `Withdraw` transaction with `min_coin_amount`/`min_pc_amount` set to `None` and sandwich it: swap to skew the pool ratio immediately before the victim's withdraw executes, causing the victim to receive far less of one asset (and disproportionately more of the other) than expected, then reverse the swap afterward to extract the difference. This results in direct loss of user/LP funds, matching the "unfavourable trade execution" impact class described in the source report.

### Likelihood Explanation
Any client (or a compromised/naive integration) that constructs a `Withdraw` instruction without supplying the optional slippage bounds is immediately exposed — no privileged access or non-default build is required. The vulnerability is reachable from a single submitted transaction with attacker-chosen accounts/data (the sandwiching swap transactions), which is the standard exploitation vector for AMM sandwich attacks and does not depend on any off-chain, RPC, or validator misbehavior beyond ordinary transaction ordering that is common on public mempools/leader schedules.

### Recommendation
Make `min_coin_amount` and `min_pc_amount` mandatory (non-optional `u64`) fields on `WithdrawInstruction`, and enforce the slippage check unconditionally in `process_withdraw`, mirroring the unconditional enforcement already used in `process_swap_base_in`/`process_swap_base_out`. If backward compatibility for the optional wire format must be preserved, at minimum reject the instruction (or require explicit acknowledgment) when both bounds are absent, rather than silently skipping protection.

### Proof of Concept
1. Victim submits a `Withdraw` instruction (tag `4`) encoding only `amount` (8 bytes), omitting the trailing 16 bytes for `min_coin_amount`/`min_pc_amount`, per the unpack logic at [2](#0-1)  — both fields decode to `None`.
2. Attacker observes this pending transaction and front-runs it with a large `SwapBaseIn`/`SwapBaseOut` that skews `amm_coin_vault`/`amm_pc_vault` reserves in their favor.
3. Victim's `Withdraw` executes against the skewed reserves; because `withdraw.min_coin_amount.is_some() && withdraw.min_pc_amount.is_some()` is `false`, the check at [6](#0-5)  is bypassed, and the victim receives `coin_amount`/`pc_amount` computed from the manipulated pool state.
4. Attacker back-runs with the reverse swap to restore reserves and capture the value extracted from the victim's below-market withdrawal.
