## Analysis: Denial-of-service via unprivileged vault "donation" front-running deposits

### Title
Deposit DoS via direct SPL-token donation into `amm_coin_vault`/`amm_pc_vault` inflating LP mint-rate denominator - (File: `program/src/processor.rs`, `program/src/math.rs`)

### Summary
`process_deposit` computes the pool's live reserves directly from the raw SPL token account balances of `amm_coin_vault`/`amm_pc_vault` rather than from an internally-tracked, deposit-gated accounting value. Because these vaults are ordinary SPL token accounts owned by the AMM authority PDA, any unprivileged holder can `spl_token::transfer` tokens into them outside of the `Deposit` instruction. An attacker who front-runs a legitimate depositor's transaction can inflate one side of the reserves just before the victim's `Deposit` lands, causing the LP-mint calculation to floor to zero and the victim's transaction to revert — the same "well-funded first user manipulates share price via direct token donation" bug class as the referenced report, adapted to Raydium's constant-product LP-mint path.

### Finding Description
`process_deposit` reads the vaults' actual token balances and feeds them into `Calculator::calc_total_without_take_pnl_no_orderbook`: [1](#0-0) 

That helper simply subtracts the tracked `need_take_pnl_*` amounts from the *live* vault balances — it has no way to distinguish tokens that arrived through `Deposit`/`Swap` from tokens sent directly via a bare SPL `transfer`: [2](#0-1) 

The resulting `total_coin_without_take_pnl` / `total_pc_without_take_pnl` are then used as the denominator for the LP-mint ratio: [3](#0-2) 

`InvariantPool::exchange_token_to_pool` performs `pool_total_amount * token_input / token_total` with `RoundDirection::Floor`: [4](#0-3) 

If an attacker inflates `token_total` (the vault balance) shortly before the victim's deposit executes, the victim's `mint_lp_amount` can round down to zero. The processor explicitly guards this case by reverting the whole transaction: [5](#0-4) 

Because the vault accounts are checked only for identity/ownership (not for "no external transfers happened"), the donation itself is unauthenticated and unprivileged: [6](#0-5) 

The same pattern of trusting raw vault balances is also used in swap and withdraw paths, meaning a donation griefing a deposit can equally distort the price seen by the very next swap or the payout ratio seen by the next withdraw: [7](#0-6) [8](#0-7) 

### Impact Explanation
This is a griefing/denial-of-service vector, not a direct fund-theft vector: because Raydium's constant-product deposit requires *proportional* amounts on both sides (unlike a single-asset ERC-4626 vault), an attacker cannot simply steal an honest depositor's principal the way the referenced report describes for a share-based vault. However, an attacker can:
- Cause a targeted victim's `Deposit` transaction to revert (`AmmError::InvalidInput`/`AmmError::ExceededSlippage`) by donating tokens to skew the ratio right before the victim's transaction lands, wasting the victim's gas/fees and blocking their intended LP entry at the price they expected.
- Repeatedly grief a specific pool's deposit flow with a well-funded front-running bot, degrading usability of Deposit for a specific pool (matches the "Denial of Service by well funded first user" bug class, but as a per-transaction griefing effect on `Deposit` rather than a permanent freeze of pool funds).

This does not create insolvent pool accounting, unbacked LP minting, or unauthorized privileged effects — the check at line 1323 blocks the zero-mint case, so no LP tokens are minted incorrectly and no funds are moved on a failed transaction.

### Likelihood Explanation
Moderate. It requires mempool visibility (or Solana-equivalent leader-slot/priority-fee racing) to time the donation transfer immediately before the victim's `Deposit`, and only affects a single targeted transaction rather than causing lasting harm to the pool. It does not require any privileged role — any token holder can call the SPL Token program's `Transfer` instruction directly into `amm_coin_vault`/`amm_pc_vault`.

### Recommendation
Track pool reserves using an internally accounted value (updated only through `Deposit`/`Swap`/`Withdraw`/`Initialize2`) instead of trusting the live SPL token account balances of `amm_coin_vault`/`amm_pc_vault` at line 1148-1153 (and equivalently in swap/withdraw paths). Alternatively/additionally, reconcile any balance surplus above the tracked reserve into `need_take_pnl_*` (or a similar sink) so unsolicited transfers cannot influence the LP-mint or swap-rate denominators.

### Proof of Concept
1. Attacker monitors the mempool/upcoming slot for a victim's `Deposit` instruction on a target Raydium pool.
2. Immediately before the victim's transaction, attacker submits a plain SPL Token `Transfer` sending tokens directly into `amm_coin_vault` (no interaction with the Raydium program required), inflating `amm_coin_vault.amount`.
3. Victim's `Deposit` executes; `calc_total_without_take_pnl_no_orderbook` returns an inflated `total_coin_without_take_pnl` (processor.rs:1148-1153).
4. `InvariantPool::exchange_token_to_pool` computes `mint_lp_amount = amm.lp_amount * deduct_coin_amount / total_coin_without_take_pnl` (math.rs:456-477), which rounds to 0 for the victim's chosen deposit amount.
5. The processor detects `mint_lp_amount == 0` and reverts the victim's transaction with `AmmError::InvalidInput` (processor.rs:1319-1325), denying the victim's deposit at their intended price/slippage settings.

```rust
    pub fn calc_total_without_take_pnl_no_orderbook<'a>(
        pc_amount: u64,
        coin_amount: u64,
        amm: &'a AmmInfo,
    ) -> Result<(u64, u64), AmmError> {
        let total_pc_without_take_pnl = pc_amount
            .checked_sub(amm.state_data.need_take_pnl_pc)
            .ok_or(AmmError::CheckedSubOverflow)?;
        let total_coin_without_take_pnl = coin_amount
            .checked_sub(amm.state_data.need_take_pnl_coin)
            .ok_or(AmmError::CheckedSubOverflow)?;
        Ok((total_pc_without_take_pnl, total_coin_without_take_pnl))
    }
```

    /// Exchange rate
    pub fn exchange_token_to_pool(
        &self,
        pool_total_amount: u64,
        round_direction: RoundDirection,
    ) -> Option<u64> {
        Some(if round_direction == RoundDirection::Floor {
            U128::from(pool_total_amount)
                .checked_mul(self.token_input.into())
                .unwrap()
                .checked_div(self.token_total.into())
                .unwrap()
                .as_u64()
        } else {
            U128::from(pool_total_amount)
                .checked_mul(self.token_input.into())
                .unwrap()
                .checked_ceil_div(self.token_total.into())
                .unwrap()
                .as_u64()
        })
    }
