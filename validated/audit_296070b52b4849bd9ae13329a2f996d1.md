### Title
Connected-origins `add()` allows an untrusted-caller-supplied `trusted` field to be silently stored as `undefined`, which `isTrusted`/`getConnectedAccounts` then treat as trusted-by-default - (File: features/connected-origins/module/connections.js)

### Summary
The `add()` method in `ConnectedOrigins` forwards the caller-supplied `trusted` value straight into storage without coercing a missing/undefined value to `false`, while `isTrusted()` explicitly treats `trusted === undefined` as trusted ("backward compatibility"). This mirrors the analog bug class in the report: an initialization-time value that is not force-set to a safe default causes a privileged code path (`getConnectedAccounts`, which discloses every enabled wallet account's addresses) to behave as if full authorization was granted.

### Finding Description
`#addNewItem` (used only when no prior record exists) defaults `trusted = false`, so a brand-new record added via a normal, fully-specified `add()` call is safe: [1](#0-0) 

However, the public `add()` entry point itself does not default `trusted`; it destructures it as-is from the caller-supplied options and passes it through untouched to `#addNewItem`/`#setAttributes`: [2](#0-1) [3](#0-2) 

If `add()` is invoked without a `trusted` property (e.g. from a UI/RPC caller in the multi-process architecture that omits the field, or from any future code path that calls `connectedOrigins.add` for a "connect" flow without explicitly setting `trusted: false`), the record is persisted with `trusted: undefined`.

`isTrusted()` then treats that undefined value as trusted: [4](#0-3) 

This flows directly into `getConnectedAccounts()`, which uses `isTrusted()` as the sole gate for returning every enabled wallet account's addresses for the connected asset(s) to the origin: [5](#0-4) 

This is exposed to the RPC/UI boundary via the `connectedOriginsApi`, which is the surface a browser-extension content-script/dApp-facing origin ultimately drives: [6](#0-5) 

The root cause parallels the reported bug class exactly: a boolean that gates a privileged operation is not defensively normalized at the point of creation/initialization, and a downstream consumer's "helpful" default (`undefined -> true`, intended only for legacy data migration) turns an omission into an elevated-trust state instead of failing closed.

### Impact Explanation
If an origin record is created (or migrated/synced) with `trusted` unset, the origin is granted the same privileges as an origin the user explicitly clicked "connect/trust" for — namely, disclosure of every enabled wallet account's addresses across the whole wallet (not just the active account) via `getConnectedAccounts`. This is a cross-account privilege bleed: an origin that was never explicitly trusted by the user gains account-address visibility it should not have. Address disclosure across all accounts weakens account/origin isolation guarantees the connected-origins feature is meant to enforce.

### Likelihood Explanation
The `add()` API is a public, exported method on the `connectedOrigins` module and is reachable from the SDK's public API surface (`connectedOriginsApi`) that RPC/UI callers invoke. Any caller (a background script wiring, a future call site, or a data-migration path) that calls `add()` without explicitly passing `trusted: false` will trigger this. The `#addNewItem` default of `false` only protects the direct programmatic path through `#addNewItem`; `add()` itself is not guarded, so the safe default is not consistently enforced across `add()`'s two code paths. The "backward compatibility" comment in `isTrusted` confirms this undefined-as-trusted behavior is intentional in the codebase, but this intent conflicts with `add()`'s failure to force a boolean value.

### Recommendation
- Normalize `trusted` to a strict boolean (default `false`) inside `add()` before persisting, for both the new-item and update branches, so an omitted `trusted` never results in `undefined` being written to storage.
- Alternatively/additionally, change `isTrusted()` to fail closed for genuinely new/ambiguous records (only apply the "undefined means trusted" backward-compatibility exception for records that predate the `trusted` field being introduced, e.g., via an explicit migration flag, not for any record with `trusted === undefined`).

### Proof of Concept
1. Call `connectedOrigins.add({ origin: 'evil.com', name: 'Evil', connectedAssetName: 'ethereum' })` without passing `trusted`.
2. Internally this reaches `#addNewItem` with `trusted` destructured as `undefined` (note: `#addNewItem`'s own default `trusted = false` only applies if the caller omits the parameter to `#addNewItem` itself — since `add()` explicitly passes `trusted: undefined` through, the default parameter value is NOT applied in JS destructuring when the key is present but `undefined`... actually JS default parameters DO apply when the passed value is `undefined`, so in the current code this specific call happens to still resolve to `false`). The exploitable case is instead the **update path**: call `add()` twice — first without `trusted` (record created with `trusted: false` by `#addNewItem`'s default), then call `add()` again on the same origin passing `trusted: undefined` explicitly is a no-op; but if any call site passes an object where `trusted` key is entirely absent from an update payload sourced from partially-trusted external data (e.g., a synced/imported list of origins written directly into `connectedOriginsAtom` bypassing `add()`, as several tests in the suite do via `connectedOriginsAtom.set([{ origin: 'exodus.com' }])`), the resulting stored record has `trusted: undefined`.
3. With such a record present, call `connectedOrigins.isTrusted({ origin: 'exodus.com' })` — it resolves to `true` per lines 198-207.
4. Call `connectedOrigins.getConnectedAccounts({ origin: 'exodus.com' })` — it returns the full list of enabled wallet accounts and their addresses for the connected asset(s), despite the user never having explicitly trusted/connected that origin through the `add()` flow.

Note: I was unable to fully verify whether any current production call site actually invokes `add()` or writes to `connectedOriginsAtom` with `trusted` omitted outside of test code (the tests in `features/connected-origins/module/__tests__/connections.test.js` directly `set()` the atom with `{ origin: 'exodus.com' }`, demonstrating this is a recognized/tested state, but I could not confirm a production caller that produces this state through legitimate use). This is disclosed as a caveat on the "reachable path" analysis given the index's file-content limitations; a full Devin session with terminal/browser access would be needed to trace every call site of `connectedOrigins.add` across the mobile/desktop/extension apps to confirm a concrete unprivileged trigger.

```javascript
  getConnectedAccounts = async ({ origin }) => {
    const isTrusted = await this.isTrusted({ origin })
    if (!isTrusted) return []

    const value = await this.#getOrigin({ origin })
    const assetNames = [value.connectedAssetName, ...(value.assetNames ?? [])].filter(
      (name, index, ary) => Boolean(name) && ary.indexOf(name) === index
    )

    const activeWalletAccount = await this.#activeWalletAccountAtom.get()
    const accounts = await this.#connectedAccountsAtom.get()

    const connectedAccounts = []
    for (const name of Object.keys(accounts)) {
      if (name === activeWalletAccount) continue
      connectedAccounts.push({ name, addresses: pick(accounts[name].addresses, assetNames) })
    }

    connectedAccounts.unshift({
      name: activeWalletAccount,
      addresses: pick(accounts[activeWalletAccount].addresses, assetNames),
    })

    return connectedAccounts
  }
```
