## Finding

### Title
Webhook shop-domain header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `ShopifyAPI::Webhooks::Registry.process` treats the `shopify-shop-domain` header as the trusted tenant identifier passed to the app's webhook handler. Because the HMAC signature never covers the shop header, an attacker who possesses one valid `(raw_body, hmac)` pair (e.g., from a webhook legitimately delivered to a shop they control) can replay it with an arbitrary `shop-domain` header value and have it accepted as coming from a different shop.

### Finding Description
`Request#hmac` and `Request#to_signable_string` are used by `Utils::HmacValidator.validate` to verify webhook authenticity: [1](#0-0) 

`to_signable_string` returns `@raw_body` only — it does not include the `shop` (or `topic`, `webhook_id`) header value. `HmacValidator.validate_signature` computes `OpenSSL::HMAC.hexdigest` over that signable string and compares it to the header-supplied HMAC using `OpenSSL.secure_compare`: [2](#0-1) 

`Registry.process` gates on this HMAC check and then constructs `WebhookMetadata` directly from `request.shop`, which is read straight from the unauthenticated `shopify-shop-domain` header: [3](#0-2) [4](#0-3) 

The binding that should hold is:
`shop authenticated by HMAC == shop delivered to the app's handler`

but the actual binding enforced is:
`body authenticated by HMAC != shop delivered to the app's handler`

The `shop` field is passed through to the handler (`WebhookMetadata#shop`) as if it were verified, yet it is never part of the signed payload. This is the same class of bug called out in the rules — "a field acted on but not covered by the HMAC."

This differs from the OAuth callback path, where `shop` IS included in the signed string (`Auth::Oauth::AuthQuery#to_signable_string` includes `shop`) and is therefore properly bound to the HMAC: [5](#0-4) 

### Impact Explanation
An attacker who legitimately controls one shop that has the app installed receives real webhook deliveries containing a valid `(raw_body, x-shopify-hmac-sha256)` pair signed with the app's `client_secret` — this pair is visible to the attacker without ever needing the secret itself. By replaying that exact body and HMAC to the app's public webhook endpoint while substituting the `shopify-shop-domain` header with a victim shop's domain, the attacker causes `ShopifyAPI::Webhooks::Registry.process` to invoke the app's handler with `WebhookMetadata#shop` set to the victim shop, while the actual signed content still originates from the attacker's own shop. Any host application logic that trusts `data.shop` to select per-tenant credentials, records, or state (the documented purpose of this field) can be tricked into cross-tenant data association — e.g. writing attacker-controlled webhook content under the victim shop's tenant record. This satisfies the "cross-tenant access" criteria in scope.

### Likelihood Explanation
Exploitation requires only: (1) the attacker's own legitimate installation of the app on any shop (a normal unprivileged merchant/developer capability), (2) capture of one webhook body+HMAC pair delivered to that shop (trivial, as it's their own endpoint), and (3) the ability to send an HTTP request to the app's public webhook endpoint with a forged `shop-domain` header — no `api_secret_key`, access token, or privileged access is needed. The gem's documented API (`Registry.process`) is used exactly as intended by the host app; the vulnerability is in the gem's own trust boundary, not a misuse by the host application.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) header values in the HMAC-signed material verified by `Utils::HmacValidator`, or otherwise cryptographically bind the tenant identifier to the payload before it is handed to `WebhookMetadata`/handlers, so that a valid signature over one shop's payload cannot be replayed under a different shop's identity.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and receives a legitimate webhook: `raw_body = B`, header `shopify-hmac-sha256 = HMAC(secret, B)`, header `shopify-shop-domain = attacker-shop.myshopify.com`.
2. Attacker sends a POST to the host app's webhook endpoint with the same `raw_body = B` and same `shopify-hmac-sha256`, but sets `shopify-shop-domain: victim-shop.myshopify.com`.
3. `Webhooks::Request.new` accepts the headers (all required headers present) at [6](#0-5) .
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because `to_signable_string` only checks `raw_body = B`, unaffected by the shop header, at [7](#0-6) .
5. The handler is invoked with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)`, despite the payload actually being signed for the attacker's own shop.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
