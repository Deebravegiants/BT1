### Title
Cross-chain order refund/fill permanently reverts and locks escrowed funds if beneficiary is a blacklisted ERC20 address - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`IntentsBase._withdraw` releases escrowed order tokens to a `beneficiary` using `IERC20.safeTransfer` with no fallback or alternate-recipient mechanism. If the escrowed input token is a blacklistable ERC20 (e.g. USDC) and the `beneficiary` (the order's `user` on refund, or the filler/solver on release) is blacklisted by the token issuer, the transfer permanently reverts, which reverts the entire withdrawal call and leaves the escrowed tokens stuck in the `IntentGatewayV2` contract with no way to redirect them to another address.

### Finding Description
`_withdraw` (called on both cross-chain delivered `RedeemEscrow`/`RefundEscrow` messages via `onAccept`, and on same-chain fill/cancel paths in `IntrinsicIntents._fillSameChain` / `_cancelSameChain`) unconditionally does: [1](#0-0) 

The `beneficiary` is taken directly from the `WithdrawalRequest.beneficiary` field, which for a refund is fixed to `order.user` and cannot be changed by anyone — not even the order creator themselves: [2](#0-1) 

This matches the documented cross-chain design as well: "the refund always goes to `order.user`" and the beneficiary cannot be altered by the caller who triggers the cancellation/refund: [3](#0-2) 

If `order.user` (or, on the fill path, the solver `beneficiary`) is blacklisted for the escrowed ERC20 token, `IERC20(token).safeTransfer(beneficiary, amount)` reverts on every attempt. Because there is:
- no per-token fallback (unlike `WrappedHyperFungibleToken.onPostRequestTimeout`, which retries with a wrapped-ETH transfer if a native push to the refundee fails — see `evm/src/apps/intentsv2` vs. `sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol:344-365`), and
- no function to update `WithdrawalRequest.beneficiary` or redirect escrowed funds to a new address,

the escrowed tokens become permanently stuck in the `IntentGatewayV2` contract. Worse, for the cross-chain refund path, this failure occurs inside `onAccept`, the handler invoked by the authorized relayer delivering a Hyperbridge-verified message — a revert there blocks finalization of that specific cross-chain refund message indefinitely, since there is no alternate recipient path and the message body (fixed beneficiary) cannot be resubmitted with a different address.

### Impact Explanation
Escrowed input tokens for an order whose `user` (refund case) or selected solver (fill case) is blacklisted by the token issuer become permanently frozen inside the `IntentGatewayV2` contract — the funds can never be withdrawn by that party or reassigned to a different address, matching the "permanent freezing of funds" class of impact. Unlike the `WrappedHyperFungibleToken`/`HyperFungibleToken` bridge apps, which include explicit fallback logic to avoid getting stuck (native push retried as ERC20 push, or re-minting on timeout to the original sender regardless of blacklist since minting is unconditional), `IntentsBase._withdraw` has no equivalent safeguard.

### Likelihood Explanation
Any order that escrows a blacklist-capable stablecoin such as USDC as an input token is exposed if the order creator's or solver's address is later added to that token's blacklist before the refund/fill settles — a realistic, externally-triggered (by the token issuer, not by any Hyperbridge component) scenario, requiring no malicious action from any Hyperbridge participant. This is reachable from ordinary user flows: `placeOrder`, `cancelOrder` (same-chain or cross-chain), and `fillOrder`, all of which route through `_withdraw`.

### Recommendation
Add a fallback withdrawal path in `_withdraw` (and `_sweepDust`) similar to the pattern already used in `WrappedHyperFungibleToken`: if `safeTransfer` to the intended beneficiary fails, escrow the tokens under a claimable balance keyed by `(beneficiary, token)` that can later be claimed by the beneficiary specifying an alternate receiver, or allow the order creator to designate a new recipient address for stuck refunds. At minimum, avoid a hard revert that blocks message finalization — catch the transfer failure and credit an internal "pending withdrawal" balance withdrawable to any address the beneficiary later authorizes.

### Proof of Concept
1. User places a cross-chain order via `IntentGatewayV2`/`ExtrinsicIntents`, escrowing USDC as an input token, with `order.user = Alice`.
2. Before the order is filled, Alice's address is added to USDC's blacklist by the token issuer.
3. Order expires without being filled; a relayer (or Alice, per `cancel-from-dest.ts`) triggers cancellation, and Hyperbridge delivers the `RefundEscrow` message to `onAccept` on the source chain, which calls `_withdraw(body, true, true)` with `beneficiary = order.user = Alice`.
4. `IERC20(USDC).safeTransfer(Alice, amount)` reverts because Alice is blacklisted.
5. The entire `onAccept` transaction reverts; `_orders[commitment][USDC]` is never decremented, and no mechanism exists to redirect the refund to a different address — the escrowed USDC is permanently stuck in the `IntentGatewayV2` contract.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

    function _cancelSameChain(Order calldata order, bytes32 commitment) internal {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

        uint256 inputsLen = order.inputs.length;
        TokenInfo[] memory remainingTokens = new TokenInfo[](inputsLen);
        bool hasEscrow = false;
        for (uint256 i; i < inputsLen;) {
            address token = address(uint160(uint256(order.inputs[i].token)));
            uint256 escrowed = _orders[commitment][token];
            if (escrowed > 0) hasEscrow = true;
            remainingTokens[i] = TokenInfo({token: order.inputs[i].token, amount: escrowed});
            unchecked {
                ++i;
            }
        }
        if (!hasEscrow) revert UnknownOrder();

        WithdrawalRequest memory body =
            WithdrawalRequest({commitment: commitment, tokens: remainingTokens, beneficiary: order.user});

        _withdraw(body, true, true);
    }

### Cancel from the Destination Chain

Cancelling from the destination chain is simpler and does not require a storage proof. The destination gateway immediately marks the order as settled, blocking any future fill attempts, and sends a refund message to the source chain via Hyperbridge. When the message arrives, the source chain authenticates it as coming from the registered destination gateway and returns the escrowed tokens to the original user.

Before and **at** the order deadline only the order creator can trigger this path. From the first destination block after the deadline, anyone may call. This lets relayers act on behalf of users whose orders have expired without being filled, providing a recovery mechanism that does not require the user to be online. The caller pays the dispatch cost, but cannot change `WithdrawalRequest.beneficiary`: the refund always goes to `order.user`.
