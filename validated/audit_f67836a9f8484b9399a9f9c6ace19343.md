## Title
Missing Role-Based Authorization on `/v2/debug/pprof/*` Endpoints - ([File: core/web/router.go])

## Summary
The `/v2/debug/pprof/*` routes registered by `metricRoutes` are mounted on the `authv2` router group, which only enforces authentication (valid session or API token) via `auth.Authenticate(...)`, with no `auth.RequiresEditRole`/`auth.RequiresRunRole`/`auth.RequiresAdminRole` wrapper as used by nearly every other sensitive endpoint in the same router. This allows any authenticated user — including one holding only the lowest `UserRoleView` role — to retrieve Go runtime profiling data (heap dumps, goroutine stacks, CPU profiles, command-line args) via `GET /v2/debug/pprof/*`.

## Finding Description
`metricRoutes` registers the standard `net/http/pprof` handlers on a route group without any role check: [1](#0-0) 

It is invoked directly on `authv2`, immediately after other endpoints that are explicitly wrapped in `auth.RequiresEditRole`: [2](#0-1) 

`authv2` itself is created with only authentication middleware — no role requirement: [3](#0-2) 

By contrast, comparable/adjacent sensitive endpoints in the same file are explicitly role-gated, e.g. user management (admin), forwarders (edit), and vault DKG export/verify (edit): [4](#0-3) [5](#0-4) 

The role-check middleware itself confirms that `RequiresRunRole`/`RequiresEditRole`/`RequiresAdminRole` are the only mechanisms beyond bare authentication that gate access by role, and that `metricRoutes`'s handlers bypass this mechanism entirely since they are never wrapped by any of these functions.

This matches the described root cause: an endpoint that exposes detailed internal runtime state is reachable by any authenticated user regardless of role, because it was never wrapped in the role-check middleware applied to comparable endpoints elsewhere in the router.

## Impact Explanation
`pprof` heap/goroutine dumps can expose in-memory secrets (key material, session data), `cmdline` reveals process invocation details, and `profile`/`trace` can be leveraged to induce CPU load. This is an information-disclosure / authorization-bypass issue: a low-privilege authenticated user (`UserRoleView`) gains access to node-internal diagnostic data that should require, at minimum, edit/admin-level trust, consistent with the Chainlink node API authorization/role-bypass impact category.

## Likelihood Explanation
Exploitation requires only a valid low-privilege session or API token — no race condition, no special timing, no elevated setup. Any legitimate view-only user account (which node operators may create for read-only dashboards/monitoring integrations) can issue a simple `GET /v2/debug/pprof/heap` and receive live profiling data. This is trivially reproducible and repeatable.

## Recommendation
Wrap the `pprofGroup` routes in `metricRoutes` with `auth.RequiresAdminRole` (or at minimum `auth.RequiresEditRole`), consistent with how other operationally-sensitive endpoints (`/keys/*/export`, `/keys/*/import`, `/vault/dkg_results/*`) are protected. Alternatively/additionally, gate the entire `/v2/debug/pprof` mount behind an explicit config flag so it is disabled by default in production deployments.

## Proof of Concept
1. Provision a Chainlink node user or API token with `UserRoleView` (lowest role).
2. Authenticate as this user via `POST /sessions` (session cookie) or use the API token headers (`X-API-KEY`/`X-API-SECRET`).
3. Send `GET /v2/debug/pprof/heap` (or `/goroutine`, `/cmdline`, `/profile`) with the view-only credentials.
4. Observe HTTP 200 with pprof binary/text profile data returned, rather than a `403`/`401 Unauthorized` that would result if the route were wrapped in `auth.RequiresEditRole` or `auth.RequiresAdminRole` as seen elsewhere in `v2Routes`.

A Go integration test using `httptest` against the router (constructing a view-role user session/token and asserting a 200 response body contains pprof profile markers on `/v2/debug/pprof/heap`) would concretely demonstrate the gap.
