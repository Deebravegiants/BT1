### Title
Repeated `+1` K-slack exploitation in `Pair.swap` can erode `assetReserve` below the recovered virtual reserve, causing a permanent arithmetic-underflow Panic that bricks a curve forever - ([File: packages/contracts/src/Pair.sol], [File: packages/contracts/src/Bonding.sol])

### Summary
`Pair.swap` enforces the constant-product invariant with a `+1` slack on both sides: [1](#0-0) 

Every buy/sell round trip through `Router._computeBuy` / `Router._computeSell` is checked only against `(newTokenReserve+1)*(newAssetReserve+1) >= k`, not the strict product `>= k`. This lets an unprivileged trader who repeatedly buys and sells extract a small amount of real value from the pair on every round trip (the slack scales with the reserve sizes, which are large because `tokenReserve` is seeded at the full `TOTAL_SUPPLY`). Repeated over many transactions, this erodes the pair's stored `assetReserve` toward — and potentially below — the launch-time virtual LT reserve that `Bonding` recovers as `k() / TOTAL_SUPPLY()`.

Three call sites in `Bonding.sol` perform an *unguarded* subtraction of that recovered virtual reserve from the live `assetReserve`: [2](#0-1) [3](#0-2) [4](#0-3) 

If `assetReserve` ever drops below `_launchTimeVirtualLtReserve(...)`, these subtractions underflow and revert with a Solidity Panic. The developers were clearly aware of this exact underflow risk and defended against it in exactly one place — `finalizeGraduation`, which uses an explicit saturating subtraction "to keep finalize from bricking on a Panic": [5](#0-4) 

but `canGraduate`, `previewLtUntilGraduation`, and `_prepareGraduationLiquidity` were left unguarded.

### Finding Description
`canGraduate` is invoked on **every single buy** via `_executeBuy`: [6](#0-5) 

and also directly by the permissionless `triggerGraduation` and by `sell`: [7](#0-6) [8](#0-7) 

Once `assetReserve` (the stored reserve mutated only by `Pair.swap`) is pushed below the recovered virtual reserve, every call to `canGraduate(token)` reverts with an arithmetic Panic instead of returning `false`. Because `buy`, `sell`, and `triggerGraduation` all transitively call `canGraduate`, **the entire curve for that token becomes permanently unusable**: no further buys, no further sells, and no path to `_enterGraduating`/`finalizeGraduation` (which is only reachable through `canGraduate` returning `true` inside `_executeBuy` or `triggerGraduation`). All curve-locked LT and the 750M curve-supply tokens held in `Pair` become permanently frozen, since there is no admin rescue path for a `Pair` stuck in `Lifecycle.Curve`.

The root cause is the same bug class as the OpenLDAP report: an unbounded/unvalidated input (here, an attacker-crafted sequence of trades exploiting the documented `+1` K-slack) reaches an arithmetic operation that is not defensively bounded, causing a crash (Panic revert) in a code path that is on the hot/critical path for every subsequent operation, rather than a graceful DoS-guard as was correctly implemented in the sibling function `finalizeGraduation`.

### Impact Explanation
This is a permanent freezing-of-funds bug reachable by any unprivileged trader: it locks all LT raised on the curve, all unsold curve tokens, and blocks the creator's and every trader's ability to trade or graduate, with no recovery path in the current contract set. This satisfies the "concrete... permanent freezing of trader, creator or LP funds" bar for High severity.

### Likelihood Explanation
Reachability requires only sequences of ordinary `Zap.buy`/`Zap.sell` calls (or direct `Bonding.buy`/`sell` calls through an allowlisted router) by a single unprivileged address, repeated enough times to erode the slack-induced drift down to the virtual-reserve floor. The magnitude of drift per round trip and the number of round trips needed depend on the pair's reserve sizes at the time of the attack (larger `tokenReserve`/`assetReserve` mean larger per-swap slack, but also a larger buffer to erode), so likelihood is data-dependent and would need to be confirmed with a concrete numeric simulation against `TOTAL_SUPPLY`, `VIRTUAL_LIQUIDITY_USD`, and realistic `exchangeRate()` values — this repo's own comments flag the `+1` slack and virtual-reserve subtraction as sensitive, unguarded areas, but I could not fully quantify the exact number of round trips required within the available tool budget.

### Recommendation
- Mirror the saturating-subtraction defense already used in `finalizeGraduation` (`packages/contracts/src/Bonding.sol:1015-1020`) in `canGraduate`, `previewLtUntilGraduation`, and `_prepareGraduationLiquidity`, so that `assetReserve < _launchTimeVirtualLtReserve(...)` degrades gracefully (e.g., treat `realLtRaised`/`ltFromPair` as `0`) instead of Panicking.
- Separately, tighten or remove the `+1` slack in `Pair.swap`'s invariant check (`packages/contracts/src/Pair.sol:71-73`), or bound cumulative slack leakage across swaps, so the stored `assetReserve` cannot drift below its true accounted floor over many round trips.

### Proof of Concept
Conceptual PoC (exact numeric parameters need on-chain/fork simulation to size the required number of round trips against a real `Pair`'s `tokenReserve`/`assetReserve`/`k`):
1. Launch a token via `Bonding.launch` and let a creator seed buy occur, giving the pair non-trivial `tokenReserve`/`assetReserve`.
2. As an unprivileged trader, repeatedly call `Zap.buy` then `Zap.sell` (round trip) on the same token. Each round trip is checked by `Pair.swap` against `(newTokenReserve+1)*(newAssetReserve+1) >= k`, which is strictly looser than the true `newTokenReserve*newAssetReserve >= k`, letting a small amount of real value leak out of the pair on every round trip.
3. Repeat until the stored `assetReserve` drifts below `_launchTimeVirtualLtReserve(token, pair) = Pair.k() / Token.TOTAL_SUPPLY()`.
4. Call `Bonding.triggerGraduation(token)` (or perform one more buy) — `canGraduate` executes `assetReserve - _launchTimeVirtualLtReserve(...)` (`packages/contracts/src/Bonding.sol:692`), which underflows and reverts with a Panic.
5. From this point, every `buy`, `sell`, and `triggerGraduation` call on this token reverts permanently, freezing all LT and tokens held by the `Pair`.

        uint256 tokenIn,
        uint256 tokenOut,
        uint256 assetIn,
        uint256 assetOut
    ) external onlyRouter returns (bool) {
        uint256 newTokenReserve = (_pool.tokenReserve + tokenIn) - tokenOut;
        uint256 newAssetReserve = (_pool.assetReserve + assetIn) - assetOut;
        if ((newTokenReserve + 1) * (newAssetReserve + 1) < _pool.k) revert KInvariantViolated();

        _pool.tokenReserve = newTokenReserve;
        _pool.assetReserve = newAssetReserve;
        emit Swap(tokenIn, tokenOut, assetIn, assetOut);
        return true;
    }
