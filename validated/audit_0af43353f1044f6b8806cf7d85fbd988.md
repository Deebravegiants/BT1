### Title
Signup can be marked as "success" without the credential/PCP package ever being built or uploaded - (File: src/plans/mod.rs)

### Summary
`MasterPlan::do_signup` computes the final `success` flag for a user-centric signup purely from `signup_reason == SignupReason::Normal`, a value derived only from pipeline/fraud results, while the actual credential/PCP build-and-upload step is gated behind a *separate, independent* `if let Ok(mut credentials) = qr_codes.try_into()` check that can silently fail (`Err(())`) and skip PCP creation/upload entirely. Because the success computation does not depend on whether that block executed, a signup can be reported as successful even though no Personal Custody Package was ever produced or sent to the backend - the same "unrelated flag/value gets folded into a returned result even when it shouldn't be" pattern as `VeryFastRouter.swap()` mixing `outputAmount` into `ethAmount` based on a flag that may not correspond to reality.

The `if let Ok(mut credentials) = qr_codes.try_into()` (`TryInto<personal_custody_package::Credentials>` impl, `src/plans/mod.rs:1898-1938`) only succeeds if every backend key field (`backend_iris_public_key`, `backend_normalized_iris_public_key`, `backend_face_public_key`, `self_custody_user_public_key`, etc.) is `Some`. If any is `None` — e.g., the "old QR-code format" branch in `backend::user_status::request` (`src/backend/user_status.rs:245-...`) which returns `UserData` with all backend key fields left unset — the `if let` silently evaluates to `false` and the entire credential/PCP-building/upload block is skipped with **no error surfaced and no effect on `signup_reason` or `success`**.

Meanwhile `success` (and thus `enroll_user::Status::Success` written into the `debug_report`) is computed **solely** from `user_centric_signup` and `signup_reason`, values that come from the biometric pipeline/fraud outcome and a QR-derived boolean — not from whether the PCP/credentials were actually built and uploaded. This mirrors the reported bug class exactly: a value (`outputAmount`/here, the "was PCP uploaded" fact) is supposed to gate what gets folded into a returned result (`ethAmount`/here, `success`), but the code path that would normally couple them can diverge, and the returned/reported value is computed independently of the real state, only being kept in check by other conditions that are not intrinsically tied to the same guard (in the router: `order.isETHSell`; here: the disjoint `try_into()` Ok/Err branch vs. `signup_reason`).

### Impact Explanation
If this divergence is reached, the Orb would report a signup as `Success` (and drive the corresponding UI/backend status/dbus signal via `debug_report.enrollment_status`/`SignupResult.success`) while the user's actual identity credential package was never built nor uploaded to the backend. This is a form of misattributed/incorrectly-reported signup outcome: the local success state and the backend's actual record of the signup can disagree, which could affect downstream fraud-prevention and audit assumptions (e.g. relying on `enrollment_status`/`signup_successful` telemetry as ground truth of a completed enrollment). As in the original report, the practical blast radius is limited because in normal backend operation the key fields populated in `UserData` are always set together (`Some`s all-or-nothing) when `valid == true` in `backend::user_status::request`, so under expected backend behavior the divergence should not occur.

### Likelihood Explanation
Low-to-medium. The divergence requires the backend/`user_status` response to be in the legacy/"old QR-code" shape (missing backend key material) while simultaneously `user_data.user_centric_signup` is `true` and the biometric pipeline/fraud check pass (`signup_reason == SignupReason::Normal`). This depends on backend-side data consistency rather than a value directly supplied by an unprivileged local user, so it is not straightforwardly triggerable purely by a malicious QR code presented to the Orb; it would require a backend/QR-data inconsistency (accidental misconfiguration or a state where legacy vs. user-centric fields disagree), analogous to the router bug requiring `order.isETHSell` to be misconfigured.

### Recommendation
Make the `success`/`enrollment_status` computation for the user-centric-signup branch depend on whether `qr_codes.try_into()` (and the subsequent `build_pcp`/`upload_pcp_tier_0`/tier1/tier2 upload) actually succeeded, rather than relying solely on `signup_reason`. Concretely, track a boolean (e.g., `pcp_uploaded: bool`) set only when the `if let Ok(...)` block completes all required uploads, and require it to be `true` (in addition to `signup_reason == SignupReason::Normal`) before setting `success = true` / `enroll_user::Status::Success` in the `user_centric_signup` path. Additionally, log/alert when `qr_codes.try_into()` returns `Err(())` for a `user_centric_signup` QR, since this indicates a data inconsistency that should not silently pass through.

### Proof of Concept
Not independently exploitable by an external/unprivileged party without a backend-side data inconsistency; the conceptual trigger is:
1. Backend's `/status` endpoint returns `valid: true` for a user QR code but supplies the legacy/`UserData` shape lacking `backend_keys` (all `None`) — see the `else` branch at `src/backend/user_status.rs` after line ~245 — while also returning `user_centric_signup: true` in `authenticated_app_data`.
2. Orb completes `scan_remaining_qr_codes` → `do_signup`, runs biometric capture and pipeline; pipeline/fraud checks pass (`signup_reason == SignupReason::Normal`).
3. `qr_codes.try_into()` in `src/plans/mod.rs:574` returns `Err(())` because the required `Option` backend key fields are `None`, so the whole `if let` block (PCP build + `upload_pcp_tier_0`/tier1/tier2 upload) is skipped entirely — no credential package reaches the backend.
4. `success = user_centric_signup && signup_reason == SignupReason::Normal` evaluates to `true` regardless, and `result.success` / `debug_report.enrollment_status` report `Success` even though no PCP was uploaded. [3](#0-2) [2](#0-1) [4](#0-3) [5](#0-4)
