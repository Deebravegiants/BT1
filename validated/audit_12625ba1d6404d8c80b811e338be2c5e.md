### Title
Inconsistent mid-signup snapshots of the shared `Config` allow a background config refresh to desynchronize enrollment-attribution decisions within a single signup - ([File: src/plans/mod.rs])

### Summary
`do_signup` in `src/plans/mod.rs` takes a *snapshot* of `orb.config` (an `Arc<Mutex<Config>>`) at the very start of the signup by destructuring `*orb.config.lock().await` [1](#0-0) , and immediately afterward takes a *second, independent* snapshot for the debug report by cloning the config again [2](#0-1) . Later in the same signup, a config-derived flag (`ignore_user_centric_signups`) is read a *third* time, freshly, to decide how the signup outcome is attributed [3](#0-2) . Because `Config` is stored behind a shared `Mutex` that is refreshed from the backend independently of the signup lifecycle (`Config::download_and_store`) [4](#0-3) , these three reads are not guaranteed to observe the same configuration value. This mirrors the ZeroLend `reserveFactor` bug class: a single logical operation (one signup) that should apply one consistent global-parameter snapshot end-to-end instead reads the shared mutable parameter multiple times at different phases, so a value change that lands between those reads causes the operation to use inconsistent parameter values across its sub-steps.

### Finding Description
`do_signup` begins by binding several config fields (including `self_serve`, `pcp_v3`, `operator_qr_expiration_time`, relay timeouts) from one lock of `orb.config` [1](#0-0) . It then builds the `DebugReport` using a *second, separately-acquired* lock/clone of the same `Config` object [2](#0-1) . Both of these occur before biometric capture, the biometric pipeline, and fraud detection run - phases that can take a non-trivial amount of wall-clock time (QR scanning, sleep for 3000ms, biometric capture, biometric pipeline, fraud detection) [5](#0-4) .

After all that work completes, the code decides how to record/attribute the signup result: if `user_centric_signup` is true **and** the *freshly read* `orb.config.lock().await.ignore_user_centric_signups` is false, the signup success is derived purely from the locally-computed `signup_reason` (client-trusted path); otherwise the code performs a full server-side `enroll_user` call whose result determines success [6](#0-5) . This decision reads `ignore_user_centric_signups` from the config a third, independent time, not from either of the two snapshots taken at the top of the function.

`Config` is shared through `Arc<Mutex<Config>>` and can be overwritten at any point by `Config::download_and_store`, which fetches a new config from the backend and swaps the entire struct into the mutex [4](#0-3) . This download path is invoked at boot (`src/bin/orb-core.rs`) and is architecturally independent of any particular signup's lifecycle - there is no mechanism visible in `do_signup` that pins/caches a single, consistent `Config` snapshot for the full duration of one signup. As a result, if the backend config is refreshed while a signup is mid-flight (e.g., an operator toggles `ignore_user_centric_signups` or `pcp_v3` between the moment `do_signup` starts and the moment the enrollment-attribution decision is made), the enrollment-attribution decision uses a different value of the flag than the one implicitly assumed when the earlier phases of the same signup ran (e.g., `pcp_v3` used to build/format the personal custody package credentials at line ~576-579, vs. `ignore_user_centric_signups` read only at the very end).

This is directly analogous to the ZeroLend bug: `updateState`/`_accrueToTreasury` used two different reads of `reserveFactor` (one implicit via the cached liquidity rate, one explicit and fresh) within what should be a single atomic update, producing a treasury/user shortfall. Here, `do_signup` uses multiple independent reads of the shared, backend-mutable `Config` across the phases of a single signup, where the correctness of the enrollment-attribution branch depends on the flag being the one in effect when the rest of the signup's logic (QR/credential handling, PCP version selection) was decided.

### Impact Explanation
If `ignore_user_centric_signups` (or other config flags consumed at different points, e.g. `pcp_v3`) changes mid-signup due to a backend config refresh, the same signup can be processed with mixed semantics: the credentials/PCP package might be built under one policy (e.g., `pcp_v3 = true`) while the enrollment attribution/success determination is evaluated under a different, later-read policy for `ignore_user_centric_signups`. This can misattribute a signup's success/failure status - e.g., a signup that should have gone through mandatory server-side `enroll_user` validation could instead be marked successful purely based on the client-supplied `user_centric_signup` flag and locally computed `signup_reason`, if the flag flips to `ignore_user_centric_signups = false` after the earlier decision points were already committed. This is a cross-phase state-consistency bug that can cause incorrect signup outcome attribution (accepted vs. rejected) without any config re-validation across the whole signup transaction.

### Likelihood Explanation
The precondition (a backend config change landing exactly inside the multi-second window of one signup) is a normal operational event, not an attacker-controlled or admin-misuse scenario - operators/backend routinely push updated orb configuration, and a single signup (QR scan + 3s wait + biometric capture + biometric pipeline + fraud check) takes long enough for this race to be plausible. No special privileges or malicious actors are required; this is a genuine broken-functionality defect from inconsistent handling of a mutable shared parameter within one atomic business operation, consistent with how the original issue was ultimately judged (broken functionality, not admin error).

### Recommendation
Snapshot the entire `Config` exactly once at the start of `do_signup` (or at `start_signup`) and thread that single, immutable snapshot through all subsequent phases (biometric capture, pipeline, fraud detection, PCP building, and the enrollment-attribution decision), instead of re-acquiring `orb.config.lock().await` at multiple, independent points during the same signup. This guarantees that all decisions within one signup - including the `ignore_user_centric_signups` check - are made against one consistent configuration state, eliminating the cross-phase inconsistency analogous to caching `lastReserveFactor` for the duration of a single state update in the ZeroLend fix.

### Proof of Concept
Not independently reproducible without runtime access to the orb's config-refresh scheduling and a live signup; conceptually:
1. Start a signup; `do_signup` reads `Config` at line 497-506 and again at line 513-518, with `pcp_v3 = false` and `ignore_user_centric_signups = true` in effect.
2. During biometric capture/pipeline (multi-second window), the backend pushes an updated config (`Config::download_and_store`) that flips `ignore_user_centric_signups` to `false`.
3. At line 639, `do_signup` re-reads `orb.config.lock().await.ignore_user_centric_signups`, now `false`, causing the function to take the `enroll_user` branch instead of the client-trusted `user_centric_signup` branch (or vice versa if the flag flips the other direction), producing an enrollment-attribution outcome inconsistent with the configuration state that governed the earlier stages of the very same signup.

    /// configuration object, and stores the updated configuration to the file

    pub async fn download_and_store(config: Arc<Mutex<Config>>) -> Result<()> {
        *config.lock().await = Self::download().await.map_err(|e| {
            tracing::error!("Failed to download config: {:?}", e);
            e
        })?;
        let config_to_store = config.lock().await;
        tracing::info!("Downloaded latest config: {:?}", config_to_store);
        config_to_store.store().await.map_err(|e| {
            tracing::error!("Config downloaded but failed to be stored: {:?}", e);
            e
        })
    }
