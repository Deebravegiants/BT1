### Title
Reward-per-token underflow after pool expiry locks out subsequent stakers - (File: `substrate/frame/asset-rewards/src/lib.rs`)

### Summary
The `pallet-asset-rewards` (FRAME Staking Rewards Pallet) contains the same class of bug described in the external report: a "reward per token" accumulator computes an elapsed-time (here, elapsed-block) delta between the pool's `last_update_block` and the applicable end block, and this subtraction can underflow once the pool has expired and has already been updated once past its expiry block. This mirrors the Solidity `_rewardPerToken()` bug where `lastUpdateTime` ends up greater than `periodFinish` after the first post-expiry claim, causing every subsequent claim to revert.

### Finding Description
`reward_per_token` computes the reward accrued since the last update: [1](#0-0) 

The elapsed blocks are computed as:
```
Self::last_block_reward_applicable(pool_info.expiry_block).ensure_sub(pool_info.last_update_block)?
```
`last_block_reward_applicable` clamps to `min(now, expiry_block)`: [2](#0-1) 

However, `update_pool_rewards` — which persists `last_update_block` after every interaction — does **not** clamp to `expiry_block`; it unconditionally stores the current block number:
```
new_pool_info.last_update_block = T::BlockNumberProvider::current_block_number();
``` [3](#0-2) 

Sequence of events (directly analogous to the Solidity report):
1. Pool `expiry_block` passes.
2. Any staker calls `stake`, `unstake`, or `harvest_rewards`, all of which call `update_pool_and_staker_rewards` → `reward_per_token` → `update_pool_rewards`. See e.g. `harvest_rewards`: [4](#0-3) 
   On this first post-expiry call, `pool_info.last_update_block` is still `<= expiry_block`, so `reward_per_token` succeeds. But `update_pool_rewards` then stores `last_update_block = now` (which is `> expiry_block`).
3. Any subsequent staker (or the same staker again) calls `stake`/`unstake`/`harvest_rewards`. Now `last_block_reward_applicable(expiry_block)` returns `expiry_block` (since `now > expiry_block`), while `pool_info.last_update_block > expiry_block`. The subtraction `expiry_block.ensure_sub(last_update_block)` underflows.

Because the pallet uses `ensure_sub` (from `EnsureSub`), the underflow does not panic but returns `Err(ArithmeticError::Underflow)`, propagating as a `DispatchError` that aborts the extrinsic. [5](#0-4) 

This is functionally identical to the reported Solidity issue: the first user to touch the pool after expiry succeeds and "poisons" the stored update marker, and every other participant's `harvest_rewards`/`stake`/`unstake` call thereafter fails.

### Impact Explanation
Any pool with more than one staker that runs to expiry will have only the first post-expiry caller succeed; every other staker's `harvest_rewards` call (and also `stake`/`unstake`, which also update rewards first) will unconditionally fail with an arithmetic error, permanently preventing them from harvesting rewards or unstaking through the normal path for that pool once it has expired. Since `unstake` also requires the reward update step to succeed, stakers could even become unable to withdraw their staked (frozen) assets normally, which is a stronger impact than the original Solidity report where the underlying token could still eventually be reclaimed in a future period — here, `pallet-asset-rewards` pools do not automatically enter a "new period"; the pool must be manually re-configured by the admin (`set_pool_reward_rate_per_block`/`set_pool_expiry_block`) to recover, and even then, the poisoned `last_update_block` bug would resurface at the next expiry.

### Likelihood Explanation
High for any pool that is allowed to run past its `expiry_block` while more than one account is staked, which is the pallet's expected normal end-of-life behavior (pools are explicitly designed to expire, see `cleanup_pool` and `PoolCleanedUp`). No privileged role or special conditions are required — it is triggered by ordinary unprivileged `harvest_rewards`/`stake`/`unstake` calls made by any two stakers after expiry.

### Recommendation
Clamp `last_update_block` to the pool's `expiry_block` when persisting it in `update_pool_rewards`, mirroring the recommended Solidity fix:
```rust
new_pool_info.last_update_block =
    Self::last_block_reward_applicable(pool_info.expiry_block);
```
This guarantees `last_update_block` never exceeds the value later used as the clamp in `last_block_reward_applicable`, eliminating the underflow for all subsequent callers.

### Proof of Concept
Conceptual reproduction using the pallet's own call surface (adapting the existing test harness in `substrate/frame/asset-rewards/src/tests.rs`):
1. Create a pool with a near-term `expiry_block`, e.g. `expiry_block = now + 10`.
2. Have `alice` and `bob` both `stake` into the pool.
3. Advance the chain past `expiry_block`.
4. `alice` calls `harvest_rewards` — succeeds, and internally sets `Pools::<T>::get(pool_id).last_update_block = current_block_number()` (> `expiry_block`).
5. `bob` calls `harvest_rewards` (or `unstake`) — `reward_per_token` computes `last_block_reward_applicable(expiry_block) = expiry_block`, then `expiry_block.ensure_sub(last_update_block)` underflows, returning `Err(ArithmeticError::Underflow)`, and `bob`'s extrinsic fails.

I was not able to fully verify whether `substrate/frame/asset-rewards/src/tests.rs` already contains a regression test that specifically covers this two-staker-post-expiry scenario (the grep found only generic matches on `expiry_block`/`reward_per_token`/`last_update_block` without confirming test outcomes), so it's uncertain whether this has already been identified/fixed upstream in this exact pallet; this should be confirmed by running the pallet's test suite or writing the PoC test above.

		/// Derives the current reward per token for this pool.
		pub(super) fn reward_per_token(
			pool_info: &PoolInfoFor<T>,
		) -> Result<T::Balance, DispatchError> {
			if pool_info.total_tokens_staked.is_zero() {
				return Ok(pool_info.reward_per_token_stored);
			}

			let rewardable_blocks_elapsed: u32 =
				match Self::last_block_reward_applicable(pool_info.expiry_block)
					.ensure_sub(pool_info.last_update_block)?
					.try_into()
				{
					Ok(b) => b,
					Err(_) => return Err(Error::<T>::BlockNumberConversionError.into()),
				};

			Ok(pool_info.reward_per_token_stored.ensure_add(
				pool_info
					.reward_rate_per_block
					.ensure_mul(rewardable_blocks_elapsed.into())?
					.ensure_mul(PRECISION_SCALING_FACTOR.into())?
					.ensure_div(pool_info.total_tokens_staked)?,
			)?)
		}
