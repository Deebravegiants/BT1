### Title
Webhook Shop-Domain Header Not Covered by HMAC Allows Cross-Tenant Webhook Spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw request body only, while the `shop`, `topic`, `api_version`, and `webhook_id` fields used by `ShopifyAPI::Webhooks::Registry.process` and passed to the host app's webhook handler are taken from unauthenticated HTTP headers.

### Finding Description
`Registry.process` validates a webhook by calling `Utils::HmacValidator.validate(request)` [1](#0-0) , which computes an HMAC over `request.to_signable_string`. That method returns only `@raw_body` [2](#0-1) . Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all derived from request headers via `shopify_header`, none of which participate in the signature [3](#0-2) . After validation succeeds, `Registry.process` builds `WebhookMetadata` directly from these unauthenticated header values and dispatches it to the app's handler as the trusted shop/tenant identity [4](#0-3) .

The identity binding that should hold is: `shop value the HMAC was computed to authenticate == shop value the app acts on`. Because the HMAC only covers the raw body bytes and never binds `shop-domain`, this equality is broken: any HTTP client (not just Shopify) that obtains one valid `(raw_body, hmac)` pair for a webhook event — e.g., by owning a store that installed the app and receiving a legitimate webhook for their own shop — can resend that exact body/HMAC to the app's webhook endpoint with an arbitrary `shopify-shop-domain` (or `x-shopify-shop-domain`) header. `HmacValidator.validate` will still pass because it re-derives the same signature over the same body using the app's `api_secret_key` [5](#0-4) , but the `shop` field delivered to the handler is now attacker-chosen, not the shop that Shopify actually attributed the event to.

### Impact Explanation
This crosses a tenant boundary: the app receives webhook data it correctly proves came from "some shop known to the app" (via a valid HMAC using the shared `api_secret_key`), but the specific shop identity attached to that data is forgeable. If the host application uses `WebhookMetadata#shop` to route the event body to a merchant's records (e.g., updating `orders/paid` or `customers/data_request` data keyed by `shop`), an attacker who controls one shop installed on the app can inject data/events attributed to a different, arbitrary shop domain, resulting in cross-tenant data corruption or disclosure. This qualifies as cross-tenant access under the impact criteria.

### Likelihood Explanation
Requires only an unprivileged actor with a single relevant valid `(body, hmac)` pair — obtainable by installing the app on any shop and receiving one real webhook — and the ability to send arbitrary HTTP requests with custom headers to the app's public webhook endpoint. No access token, `client_secret`, or privileged Shopify account is needed. Likelihood is high wherever the host app trusts `WebhookMetadata#shop` without independently re-validating it against session/store records.

### Recommendation
Include `shop`, `topic`, `api_version`, and `webhook_id` in the HMAC-signable string (or otherwise cryptographically bind them to the body, e.g., by having the host app independently verify `shop` against its own installed-shops list) before trusting them in `Registry.process`, mirroring how `Auth::Oauth::AuthQuery#to_signable_string` includes `shop` in its signed payload [6](#0-5) .

### Proof of Concept
1. Install the target app on shop `attacker.myshopify.com`; receive a legitimate webhook: raw body `B`, header `x-shopify-hmac-sha256: H` (valid HMAC over `B` with the app's shared secret), `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-topic: orders/paid`.
2. Replay the exact same `(B, H)` to the app's public webhook endpoint, but set `x-shopify-shop-domain: victim.myshopify.com`.
3. `Registry.process` calls `HmacValidator.validate`, which recomputes HMAC over `B` only and succeeds since `H` was a valid signature for `B` [1](#0-0) .
4. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed(B), ...)` [7](#0-6)  and processes attacker-supplied order/customer data as if it belonged to `victim.myshopify.com`.
