### Title
Webhook `shop` (tenant) attribution is not covered by HMAC verification - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while the `shop-domain` header used to attribute the webhook to a tenant is never included in that signed content. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then trusts `request.shop` as the tenant identity when dispatching to the app's handler, so the "this body was signed by Shopify" guarantee is not bound to "this body belongs to this shop."

### Finding Description
`Utils::HmacValidator.validate` recomputes an HMAC over `verifiable_query.to_signable_string` and compares it (via `OpenSSL.secure_compare`) to the `hmac` field of the object [5](#0-4) . For `ShopifyAPI::Webhooks::Request`, `to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop`, `topic`, `api_version`, and `webhook_id` are all pulled from unauthenticated HTTP headers [6](#0-5) .

`Registry.process` only checks `Utils::HmacValidator.validate(request)` before constructing `WebhookMetadata` with `shop: request.shop` and dispatching it to the app-registered handler [3](#0-2) . There is no check binding the signed body to the `shop-domain` header value. This breaks the equality that should hold: `shop authenticated by HMAC == shop delivered to the handler`. Instead, the gem only guarantees `body integrity (via secret) == raw_body`, and separately trusts the `shop-domain` header verbatim.

The library's own docs describe `Registry.process` as verifying "the request did indeed come from Shopify" before invoking the handler [4](#0-3) , giving app developers no indication that the `shop` field of `WebhookMetadata` requires independent verification.

### Impact Explanation
Because the `api_secret_key` used to compute the HMAC is shared by the app across every shop that installs it, any merchant that installs the app (an ordinary, unprivileged action) can generate legitimately-signed webhook bodies from data they fully control in their own store (e.g., a product/order field value they set). Since the `shop-domain` header carrying the tenant identity is not part of the signed content, that same `(raw_body, hmac)` pair remains valid regardless of which `shop-domain` header accompanies it when POSTed to the app's webhook endpoint. If a request with the same body/HMAC is delivered with a different `shop-domain` header, `Registry.process` will accept it and hand the attacker-chosen body to the handler as if it belonged to a different shop — a cross-tenant data/identity confusion at the shop attribution layer.

### Likelihood Explanation
Exploitability depends on the app's webhook endpoint being reachable for direct/replayed POSTs (which is typically the case, since these endpoints authenticate solely via this HMAC check) and on an attacker being able to obtain a valid `(raw_body, hmac)` pair, which they can via legitimate webhook delivery to their own installation with attacker-controlled body content. No access to `api_secret_key`, access tokens, or privileged accounts is required.

### Recommendation
Bind the shop identity into what is verified before it is trusted: either include `shop-domain` (and `topic`/`api_version`/`webhook_id`, as needed) in the value passed to `to_signable_string`/HMAC comparison, or independently verify that `request.shop` corresponds to a shop with an active session/installation for this app before dispatching to the handler, rather than trusting the raw header value as-is.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and configures an order/product field with fully attacker-controlled content, e.g. a webhook topic they are subscribed to.
2. Shopify delivers a legitimately HMAC-signed webhook for `attacker.myshopify.com` to the app's webhook endpoint; the raw body and `X-Shopify-Hmac-Sha256` value are a valid pair for the app's shared secret.
3. Attacker resends the exact same raw body and HMAC header to the app's webhook endpoint, but substitutes `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses the headers, `Utils::HmacValidator.validate` succeeds because it only checks the raw body [7](#0-6) , and `Registry.process` dispatches `WebhookMetadata` with `shop: "victim.myshopify.com"` and attacker-controlled `body` to the app's handler [8](#0-7) .
5. The app's handler, trusting `data.shop`, processes/stores attacker-controlled data under the victim's tenant.
