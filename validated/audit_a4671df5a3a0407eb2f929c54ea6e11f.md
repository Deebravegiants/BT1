### Title
Webhook shop-domain spoofing via HMAC that covers only the raw body, not the `X-Shopify-Shop-Domain` header - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` verifies webhook authenticity via `Utils::HmacValidator`, but the HMAC signable string is derived solely from the raw request body. The `shop` (tenant identity) that is handed to the webhook handler is read directly from an HTTP header that is never included in the HMAC computation, so a valid HMAC does not bind the request to the shop it claims to be from.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic tie to the body or to the HMAC: [2](#0-1) [3](#0-2) 

`Registry.process` validates the HMAC over the whole `request` object (i.e., over the signable string, which is just the body) and then, once that check passes, unconditionally forwards `request.shop` to the app's handler: [4](#0-3) 

Compare this to `Utils::HmacValidator`, which recomputes the HMAC exclusively over `verifiable_query.to_signable_string` and does a constant-time compare against the received HMAC: [5](#0-4) 

The identity binding the gem should provide is:
`HMAC_valid(body) ⇒ shop_verified == shop_used_by_handler`

But what is actually implemented is:
`HMAC_valid(body only)` while `shop_used_by_handler = header value, unauthenticated`

So the equality the gem is supposed to guarantee — that the `shop` passed to `WebhookMetadata`/the handler is the same shop the HMAC vouches for — does not hold. Any bytes that make it through header parsing for `shop-domain` are trusted, regardless of what the HMAC covers.

This is directly analogous to the reported smart-contract bug: `liquidationInitialAsk` was checked against `amount` but not against the broader `potentialDebt` that the value is later relied upon for; here, the HMAC is checked against `raw_body` but the `shop` field, which the handler relies on for tenant attribution, is never part of what's checked.

### Impact Explanation
An unprivileged internet user who can obtain any single legitimately-signed webhook delivery for the app (e.g., by installing the app on their own trial/free development store and capturing an `orders/create`, `app/uninstalled`, or `shop/update` webhook their store legitimately receives) possesses a `(raw_body, hmac)` pair that will always pass `HmacValidator.validate`, because `api_secret_key` is shared by the app across every merchant that installs it — only the body is bound to the signature, not the shop. The attacker can then replay that exact body/HMAC to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header value naming a victim shop. The HMAC check still succeeds (it never looked at the header), and `Registry.process` calls the app's handler with `WebhookMetadata.new(... shop: request.shop ...)` set to the victim's domain. Any host application that uses `shop` from the webhook payload to look up/mutate per-tenant state (uninstall cleanup, order/customer records, billing, etc.) will act on the wrong tenant's data — a cross-tenant data-confusion/integrity issue.

### Likelihood Explanation
Getting one valid `(body, hmac)` pair only requires installing the target app on any shop the attacker controls (freely obtainable Shopify development/trial stores), which is a normal, low-privilege, self-service action, not a credential leak or social engineering. Forging the header value requires nothing more than crafting an HTTP request, and topic/webhook_id mismatches are not required to be internally consistent with the shop, so this is realistically reachable by any unprivileged actor who can install the app once.

### Recommendation
Bind the shop identity into what is cryptographically verified, or otherwise disallow using the raw header value unless it is corroborated:
- Include the `shop-domain` (and ideally `topic`, `webhook-id`, `api-version`) header values in the HMAC-covered signable string (this requires updating server-side signing on Shopify's side and is not something the gem can unilaterally change), or
- At minimum, require applications to cross-check `request.shop` against a shop they already have an active `Session`/installation record for before processing, and document in `Registry.process` that `request.shop` is unauthenticated and must not be trusted for tenant attribution on its own.
- Add a test asserting that tampering with the `shop-domain` header while keeping body/HMAC intact is detected/rejected once such a binding is added.

### Proof of Concept
```ruby
require "shopify_api"

# Attacker installs the app on their own dev store and captures a legitimate webhook
raw_body = '{"id":123,"note":"legit order from attacker-owned store"}'
hmac = Base64.encode64(
  OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)
)

# Attacker replays it, swapping only the shop-domain header to point at a victim shop
spoofed_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => hmac,
  "x-shopify-shop-domain" => "victim-shop.myshopify.com",  # not covered by HMAC
  "x-shopify-webhook-id" => "any-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: spoofed_headers)

# Passes HMAC validation because only raw_body is checked
ShopifyAPI::Webhooks::Registry.process(request)
# => handler.handle(data: WebhookMetadata.new(topic: "orders/create",
#                                              shop: "victim-shop.myshopify.com",  # attacker-controlled
#                                              body: {...}, ...))
```
`Utils::HmacValidator.validate(request)` returns `true` even though `shop` was changed, because `to_signable_string` never included it: [1](#0-0) [6](#0-5)
