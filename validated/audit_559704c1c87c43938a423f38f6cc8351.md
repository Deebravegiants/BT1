### Title
Unguarded division in `calc_take_pnl` panics (division-by-zero) when pool reserves are driven to zero, permanently freezing the pool - ([File: program/src/processor.rs])

### Summary
Raydium AMM's `Processor::calc_take_pnl` performs an unchecked `checked_div(x1)` where `x1` is derived directly from the pool's live PC (or coin) reserve after subtracting the accumulated `need_take_pnl_*` amount. If that residual reserve is driven to exactly zero, the division panics, aborting every subsequent `Swap`, `Deposit` and `Withdraw` instruction that reaches this code path — a class of bug directly analogous to CVE-2017-11464 (unguarded division causing SIGFPE on attacker-influenced input in `box_blur_line`).

### Finding Description
`calc_take_pnl` computes a rebalanced "x2/y2" pair using the pool's live totals: [1](#0-0) 

`x1`/`y1` are passed in from `Calculator::normalize_decimal_v2(total_pc_without_take_pnl, ...)` and `normalize_decimal_v2(total_coin_without_take_pnl, ...)`, where the totals are computed by subtracting the accumulated `need_take_pnl_pc`/`need_take_pnl_coin` from the live vault balances with only an underflow guard, not a nonzero guard: [2](#0-1) 

`calc_take_pnl` is invoked by every `Swap`, `Deposit`, and `Withdraw` code path (whenever `amm.status != WithdrawOnly` and current-k ≥ last-k), and it self-mutates the persisted state by subtracting the newly computed PNL amounts from `total_pc_without_take_pnl`/`total_coin_without_take_pnl` and adding them to `amm.state_data.need_take_pnl_pc`/`need_take_pnl_coin`: [3](#0-2) 

Because `total_pc_without_take_pnl - pc_pnl_amount` is not checked to remain strictly positive before it is persisted (via `need_take_pnl_pc` growing), an unprivileged swapper who repeatedly submits swaps that accrue PNL can, over a sequence of transactions, drive `need_take_pnl_pc` (or `need_take_pnl_coin`) to exactly equal the corresponding vault balance. On the very next instruction that reaches `calc_take_pnl` (any ordinary swap, deposit, or withdraw), `calc_total_without_take_pnl_no_orderbook` will yield `total_pc_without_take_pnl == 0` (or coin == 0), making `x1` (or `y1`) equal to `0`. The unguarded `checked_div(x1)` at `processor.rs:208` then returns `None`, and the subsequent `.unwrap()` panics, aborting the transaction with a runtime error analogous to the CVE's unguarded-division SIGFPE.

### Impact Explanation
Once the reserve side has been driven to exactly zero, every future call into `calc_take_pnl` — triggered by `Swap` (base-in/base-out and V2 variants), `Deposit`, and `Withdraw` — panics as long as the PNL-taking branch condition (`pool_pc*pool_coin >= calc_pc*calc_coin`) holds, which is the common case for an actively-traded pool. This constitutes a permanent denial-of-service that freezes LP and trader funds in the pool: liquidity providers can no longer withdraw, and swaps can no longer execute, with no privileged recovery instruction shown in the reachable set (`Initialize2`, `Deposit`, `Withdraw`, swap instructions) to reset `need_take_pnl_*` back below the vault balance from an unprivileged context.

### Likelihood Explanation
The path is reachable from a single, unprivileged, attacker-controlled transaction stream (repeated `SwapBaseIn`/`SwapBaseOut` calls with attacker-chosen `amount_in`/`amount_out`), requiring no signer other than the swapper themselves. Exploitability depends on being able to steer the integer-truncated PNL residual to exactly zero, which is more tractable on low-decimal / low-liquidity pools where integer division rounding artifacts are coarser, but the underlying code contains no defensive check preventing it in any pool.

### Recommendation
- In `calc_total_without_take_pnl_no_orderbook` and `calc_take_pnl`, explicitly reject (return `AmmError`) any state where the resulting `total_pc_without_take_pnl` or `total_coin_without_take_pnl` (and therefore `x1`/`y1`) would be zero, rather than relying on downstream `.unwrap()`.
- Replace the `.unwrap()` on `checked_div(x1)` (and the analogous `checked_div` calls in `math.rs`, e.g. `calc_x_power`) with explicit error propagation (`ok_or(AmmError::...)?`) so a would-be zero-denominator produces a graceful `ProgramError` instead of a panic.
- Add an invariant check ensuring `need_take_pnl_pc < vault_pc.amount` and `need_take_pnl_coin < vault_coin.amount` is maintained after every PNL update in `calc_take_pnl`.

### Proof of Concept
1. An unprivileged user repeatedly calls `SwapBaseIn`/`SwapBaseOut` against a pool, choosing `amount_in`/`amount_out` values across many transactions such that each call's PNL-taking branch in `calc_take_pnl` (processor.rs:190-260) incrementally increases `need_take_pnl_pc` (or `need_take_pnl_coin`) toward the vault's live balance.
2. On the transaction where `need_take_pnl_pc` becomes exactly equal to `amm_pc_vault.amount`, `calc_total_without_take_pnl_no_orderbook` (math.rs:238-250) returns `total_pc_without_take_pnl == 0` for that and all subsequent calls.
3. Any following `Swap`, `Deposit`, or `Withdraw` instruction that reaches the PNL branch in `calc_take_pnl` calls `Calculator::normalize_decimal_v2(0, ...)` → `x1 = 0`, then `x2.checked_mul(y1).unwrap().checked_div(x1).unwrap()` (processor.rs:208) returns `None` and panics, aborting the transaction and leaving the pool permanently unusable for swaps/withdrawals from that point forward.

```rust
    pub fn calc_total_without_take_pnl_no_orderbook<'a>(
        pc_amount: u64,
        coin_amount: u64,
        amm: &'a AmmInfo,
    ) -> Result<(u64, u64), AmmError> {
        let total_pc_without_take_pnl = pc_amount
            .checked_sub(amm.state_data.need_take_pnl_pc)
            .ok_or(AmmError::CheckedSubOverflow)?;
        let total_coin_without_take_pnl = coin_amount
            .checked_sub(amm.state_data.need_take_pnl_coin)
            .ok_or(AmmError::CheckedSubOverflow)?;
        Ok((total_pc_without_take_pnl, total_coin_without_take_pnl))
    }
```
