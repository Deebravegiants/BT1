### Title
Same-`assetId` withdrawals in one transaction collapse onto a single status/txHash, causing double-credit or missed-credit misreporting - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`findMatchingWithdrawal` in both `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts` and `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts` matches PoA withdrawal-status records solely by `nep141:${w.data.near_token_id} === assetId`, ignoring `amount`/`destinationAddress`. When a single NEAR transaction contains two withdrawals of the same token to different destinations/amounts, both `describeWithdrawal({index:0,...})` and `describeWithdrawal({index:1,...})` resolve to the same array element (`Array.prototype.find` always returns the first match), so both indices report identical `status`/`txHash`.

### Finding Description
The broken equality is: for withdrawal `i` in `{0,1}`, `(status_i, txHash_i)` should equal the true on-chain outcome of withdrawal `i`; instead both collapse to the outcome of `withdrawals.find(w => nep141:${w.data.near_token_id} === assetId)`, i.e. the first bridge-indexer record with a matching token, regardless of `index`, `amount`, or destination.

Code path: `PoaBridge.describeWithdrawal` (packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts:313-343) calls `getWithdrawalStatusWithRetry` then `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)` (lines 319-322, function at 418-427). The comment at lines 409-417 explicitly documents that "multiple withdrawals of the same token in a single transaction are not supported." The identical pattern and comment exist in `waitForWithdrawalCompletion.ts` lines 135-153.

An unprivileged user (or a counterparty whose withdrawal request is forwarded by an integrator) can construct an intent with two PoA withdrawal legs for the same `assetId` (e.g., two `nep141:zec.omft.near` transfers) with different `amount` and `destinationAddress`. Once both land in the same NEAR transaction and the PoA bridge processes and completes both transfers (each producing its own `transfer_tx_hash` in the indexer's `withdrawals` array), any caller invoking `describeWithdrawal`/`waitForWithdrawalCompletion` with `index:0` and `index:1` gets the exact same `WithdrawalStatus` (same `txHash`), because `index` is never used in the matching logic — only `assetId`.

Existing guards (`validateWithdrawal`, `compareAddresses`, `supports()`, `FeeExceedsAmountError`, contract-level nonce/signature checks) operate on withdrawal creation/estimation and do not touch withdrawal-status matching after submission, so none of them prevent this collapse.

### Impact Explanation
An integrator polling both withdrawal identifiers to confirm delivery and reconcile off-chain ledgers/credits will observe two "completed" results sharing one `txHash`/`amount`, leading it to believe the second withdrawal's on-chain destination and amount are the first withdrawal's — it may credit or refund the wrong amount twice against a single real payout, or fail to recognize the second withdrawal's genuine delivery to a different address. This is a status/hash misreport that induces a double-credit/refund — matching the High/Critical bucket for "a status or hash misreport making an integrator credit or refund twice." Repeatable on every multi-leg same-token withdrawal transaction.

### Likelihood Explanation
Requires: PoA route, two withdrawals in the same transaction sharing `assetId` but differing amount/destination, and both indexed as COMPLETED by the bridge indexer. This is entirely attacker/integrator-controllable — an ordinary user constructing a single intent transaction with two same-token PoA withdrawal legs, no privileged access needed. Feasibility is confirmed by the code comment itself acknowledging this exact scenario is unhandled.

### Recommendation
Disambiguate matching using more than `assetId`: match by `amount` and `destinationAddress` (or `destinationMemo`) in addition to token id, or reject/merge multiple same-`assetId` withdrawals at intent-construction time (`createWithdrawalIntents`/withdrawal-params validation) so this ambiguous state can never be submitted. If the PoA API cannot disambiguate multiple same-token records, sort both the local withdrawal params and the returned `withdrawals` by `amount` (as the existing comment suggests) and match by position, or reject the batch outright with a clear error until the PoA API supports proper disambiguation.

### Proof of Concept
```ts
// vitest, mocking only HTTP layer (poaBridge.httpClient.getWithdrawalStatus)
import { describe, it, expect, vi } from "vitest";
import { PoaBridge } from "./poa-bridge";
import * as poaBridgeHttp from "@defuse-protocol/internal-utils"; // mock poaBridge.httpClient.getWithdrawalStatus

it("collapses two same-assetId withdrawals onto one txHash", async () => {
  const assetId = "nep141:zec.omft.near";

  vi.spyOn(poaBridgeHttp.poaBridge.httpClient, "getWithdrawalStatus").mockResolvedValue({
    withdrawals: [
      { status: "COMPLETED", data: { near_token_id: "zec.omft.near", transfer_tx_hash: "TX_A", amount: "100000" } },
      { status: "COMPLETED", data: { near_token_id: "zec.omft.near", transfer_tx_hash: "TX_B", amount: "50000" } },
    ],
  });

  const bridge = new PoaBridge({ envConfig, xrplRpcUrls: [] });

  const status0 = await bridge.describeWithdrawal({
    index: 0,
    withdrawalParams: { assetId, amount: 100000n, destinationAddress: "addrA" } as any,
    tx: { hash: "sometx" } as any,
    landingChain: "..." as any,
  });

  const status1 = await bridge.describeWithdrawal({
    index: 1,
    withdrawalParams: { assetId, amount: 50000n, destinationAddress: "addrB" } as any,
    tx: { hash: "sometx" } as any,
    landingChain: "..." as any,
  });

  // Broken equality: both indices report the SAME txHash (TX_A), though
  // withdrawal 1 actually completed with TX_B / amount 50000 to addrB.
  expect(status0).toEqual({ status: "completed", txHash: "TX_A" });
  expect(status1).toEqual({ status: "completed", txHash: "TX_A" }); // should be TX_B — proves STATUS_TRUTH fails for index 1
});
```
