### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant shop spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) for an incoming webhook from the `X-Shopify-Shop-Domain` HTTP header, but the HMAC signature that `Utils::HmacValidator` verifies is computed only over the raw request body. The header used to route/attribute the webhook to a specific merchant is therefore never authenticated, breaking the binding `shop authenticated == shop acted upon`.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `#shop` is read straight from the (attacker-controllable, header-level) `shopify-shop-domain`/`x-shopify-shop-domain` value: [2](#0-1) 

`Utils::HmacValidator.validate` computes and compares the HMAC solely against `to_signable_string`, i.e. the raw body bytes, using the app's shared `api_secret_key`: [3](#0-2) 

`Webhooks::Registry.process` accepts a webhook once `Utils::HmacValidator.validate(request)` succeeds, and then dispatches to the app's handler using `request.shop` — the unauthenticated header value — as the tenant identifier for the delivered data: [4](#0-3) 

Because Shopify signs webhooks with the app's single `client_secret` regardless of which of the app's installed shops triggered the event, the HMAC is a shared secret across all tenants of the same app — it authenticates "this body was produced by Shopify for *some* shop running this app," not "this body belongs to shop X." Since the `shop-domain` header sits outside the signed content, any party who can obtain one validly-signed webhook delivery for a shop they control (e.g., by installing the app on a shop they own, or observing/replaying a delivery) can resend the same body with the `shop-domain` header rewritten to a victim merchant's domain. `HmacValidator.validate` still returns `true` because the signable string (raw body) is unchanged, and the registry then invokes the app's handler believing the data belongs to the victim shop.

### Impact Explanation
This breaks the binding "shop authenticated via HMAC" == "shop the application acts on," enabling cross-tenant data confusion: an attacker-controlled shop can cause the app to process/store data (orders, customers, app-uninstall, GDPR, etc.) under a victim merchant's shop identifier. Depending on how the host application keys its data store or session lookups by `WebhookMetadata#shop`, this can lead to writing attacker-controlled data into a victim tenant's records, or triggering shop-scoped actions (e.g., de-provisioning, cache invalidation, billing state changes) against a shop that never sent the webhook — a cross-tenant access impact.

### Likelihood Explanation
Exploitation requires network access to the app's webhook endpoint and a source of one validly HMAC-signed payload — trivially obtained by installing the app on any shop (including a free/dev store) or by capturing/replaying one's own legitimate webhook deliveries, then modifying the shop-domain header on resend. No possession of the `api_secret_key`, an access token, or any victim credential is required, since the header is unauthenticated and freely attacker-controlled in the replayed request.

### Recommendation
Include the shop domain (and ideally topic/api-version) as part of the HMAC-signed material, or independently bind the header value to the shop that Shopify's signature actually attests to. If Shopify's webhook signing does not include the shop domain in the signable payload, `ShopifyAPI::Webhooks::Registry.process` should cross-check `request.shop` against an out-of-band trusted source (e.g., a known/installed-shop allowlist maintained by the host app, verified independently of the header) before dispatching to handlers, and document to consumers that they must not treat `shop-domain` as authenticated without such a check. At minimum, update `Webhooks::Request#to_signable_string`/documentation to make explicit that `shop` is unauthenticated so integrators do not rely on it for tenant isolation.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a shop they control) and lets Shopify deliver a legitimate webhook (e.g., `orders/create`) to the app's webhook endpoint. The delivery includes a valid `X-Shopify-Hmac-Sha256` header computed over the raw body with the app's `api_secret_key`, and an `X-Shopify-Shop-Domain: attacker-shop.myshopify.com` header.
2. Attacker resends the exact same raw body and HMAC header to the same endpoint, but replaces the header with `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` recomputes the HMAC over the (unchanged) raw body and it matches, so `Webhooks::Registry.process` proceeds and calls the registered handler with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com", body: request.parsed_body ...)`, causing the app to process attacker-supplied data as if it originated from the victim's shop.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
