### Title
`validate_auth_callback` sends the app's `client_secret` and authorization `code` to a shop host that is never checked against `ShopValidator`'s trusted-domain list - (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
`ShopifyAPI::Auth::Oauth.validate_auth_callback` builds the OAuth token-exchange request using `auth_query.shop` as the destination host for the POST that carries `client_secret` and the authorization `code`, but unlike every other credential-issuing flow in the gem (`ClientCredentials.client_credentials`, `TokenExchange.exchange_token`/`migrate_to_expiring_token`), it never runs `Utils::ShopValidator.sanitize!` on that value before using it to construct the outbound request host.

### Finding Description
The identity binding that should hold is: *the host that receives `client_secret` == a value proven to be a genuine `*.myshopify.com`/trusted Shopify domain*. In `lib/shopify_api/auth/oauth.rb`:

```ruby
def validate_auth_callback(cookies:, auth_query:)
  ...
  raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
  ...
  null_session = Auth::Session.new(shop: auth_query.shop)
  body = {
    client_id: Context.api_key,
    client_secret: Context.api_secret_key,
    code: auth_query.code,
    ...
  }
  client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
``` [1](#0-0) 

`Clients::HttpClient#initialize` derives the destination host directly from `session.shop` with no further validation:
```ruby
@base_uri = T.let("https://#{api_host || session.shop}", String)
``` [2](#0-1) 

The only check performed on `auth_query.shop` before it is used as the request host is `Utils::HmacValidator.validate(auth_query)`, which verifies that `code`, `host`, `shop`, `state`, and `timestamp` were jointly signed with `api_secret_key`: [3](#0-2) [4](#0-3) 

This HMAC check proves the *content* was signed by the party holding `api_secret_key` — it does **not** independently constrain `shop` to be a `*.myshopify.com`/trusted Shopify domain string. Every other place in the codebase that turns a caller-controlled `shop` string into a request host runs it through `Utils::ShopValidator.sanitize!` first, e.g.:
```ruby
validated_shop = Utils::ShopValidator.sanitize!(shop)
shop_session = ShopifyAPI::Auth::Session.new(shop: validated_shop)
``` [5](#0-4) 

`validate_auth_callback` is the only credential-sending flow (it sends `client_secret` in the body) that skips this sanitize step and instead uses `auth_query.shop` verbatim to build `null_session` and, downstream, the request host.

### Impact Explanation
Because the host application constructs `AuthQuery` from raw query parameters (as documented in `docs/usage/oauth.md`, `ShopifyAPI::Auth::Oauth::AuthQuery.new(request.parameters.symbolize_keys.except(:controller, :action))`) and this gem performs no `ShopValidator` normalization on `shop` in this path, the only defense against `shop` being a non-Shopify host is the HMAC check tying `shop` to a signature computed with `api_secret_key`. If that binding is ever satisfied for a value outside `*.myshopify.com`/trusted domains — for example, through any weakness in how the host app sources/handles the callback parameters, or a permissive interpretation of what counts as a validly-signed `shop` — `client_secret` and the authorization `code` are sent by the gem itself to that arbitrary host, which is credential exfiltration of the app's `client_secret` (Critical impact per the given rules). The absence of the same `ShopValidator.sanitize!` call that guards every sibling credential flow is the concrete gap: the gem provides no defense-in-depth here, unlike `client_credentials.rb`, `refresh_token.rb`, and `token_exchange.rb`.

### Likelihood Explanation
Exploitability strictly depends on getting a `shop` value accepted by `Utils::HmacValidator.validate` that is not itself a legitimate Shopify domain — normally this requires knowledge of `api_secret_key`, which is out of scope per the rules ("anything requiring... the app's `client_secret`" is excluded, and by symmetry a scenario requiring the attacker to already forge a valid HMAC is not attacker-reachable without the secret). I could not identify an unprivileged path that produces a validly-HMAC'd `AuthQuery` with a non-Shopify `shop` without already possessing `api_secret_key`. This lowers likelihood significantly and I could not fully confirm a standalone unauthenticated trigger within the scope of this gem's code alone.

### Recommendation
Call `Utils::ShopValidator.sanitize!(auth_query.shop)` in `validate_auth_callback` before constructing `null_session`/`Session.from`, mirroring `ClientCredentials.client_credentials` and `TokenExchange`, so the host that receives `client_secret` is defense-in-depth-bound to the `ShopValidator::TRUSTED_SHOPIFY_DOMAINS` allowlist rather than relying solely on the HMAC check.

### Proof of Concept
Not independently demonstrable within this gem alone: constructing a passing `AuthQuery` with a `shop` outside `*.myshopify.com` requires a validly computed HMAC, which requires `api_secret_key`. No further unprivileged trigger was found in `lib/shopify_api/**` (excluding generated REST resources) that allows bypassing `Utils::HmacValidator.validate` to reach `Clients::HttpClient` with an attacker-chosen host while carrying `client_secret`.

        def validate_auth_callback(cookies:, auth_query:)
          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state

          null_session = Auth::Session.new(shop: auth_query.shop)
          body = {
            client_id: Context.api_key,
            client_secret: Context.api_secret_key,
            code: auth_query.code,
            expiring: Context.expiring_offline_access_tokens ? 1 : 0, # Only applicable for offline tokens
          }

          client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
