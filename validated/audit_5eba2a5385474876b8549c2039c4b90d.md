### Title
Webhook shop tenant identity is not bound by the HMAC signature, enabling cross-tenant webhook replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature exclusively over the raw request body, but delivers `shop`, `topic`, `webhook_id` and `api_version` from unauthenticated HTTP headers that are never covered by that signature. `Registry.process` validates only the body HMAC and then trusts the header-derived `shop` value to identify the tenant the webhook belongs to when dispatching to the app's handler.

### Finding Description
`Utils::VerifiableQuery`/`HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the `hmac` value. For `Webhooks::Request`, `to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from HTTP headers with no cryptographic binding to the signed payload: [2](#0-1) 

`Registry.process` validates the HMAC of the body, then immediately trusts `request.shop` (and `request.topic`) as the tenant/routing identity handed to the host application's handler: [3](#0-2) 

This breaks the intended identity binding: **shop (tenant) acted upon == shop authenticated by the HMAC**. In reality, the HMAC only authenticates "this body byte-string was produced with the app's secret at some point," it says nothing about which shop/tenant that body belongs to. Because the same shared `client_secret` computes an identical HMAC for a given body regardless of which merchant sent it, an unprivileged internet user who is themselves a merchant/installer of the app (i.e., can legitimately receive real, correctly-HMAC'd webhooks for their own store) can capture one of their own valid webhook deliveries and re-POST it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header rewritten to point at a different shop. The HMAC still validates (same body, same secret), and `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload belongs to the victim shop, when it never originated from Shopify for that tenant at all.

### Impact Explanation
This is a cross-tenant data confusion vector: a host application that uses `request.shop` from `WebhookMetadata` to decide which tenant's records to create/update/delete based on webhook payload will process a replayed message under an incorrect, attacker-chosen tenant identity, without possession of the app's `client_secret`, access token, or any privileged credential. This matches the High-impact "cross-tenant access" category defined for this analysis, since it lets one tenant inject data attributed to another tenant purely by controlling unauthenticated headers.

### Likelihood Explanation
Likelihood is High for any legitimate merchant/attacker who has installed the app (a normal, unprivileged capability — installing an app and receiving your own webhooks requires no special access) because:
- They naturally receive real, correctly signed webhooks for their own shop.
- Nothing in `Webhooks::Request`/`Registry.process` prevents replaying that exact body with a different `shop-domain` header — the HMAC check passes unchanged.
- The vulnerable code path (`Registry.process`) is the exact documented mechanism apps are told to use for verifying inbound webhooks.

### Recommendation
Include the tenant-identifying headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signed material, or otherwise cryptographically bind them to the HMAC-verified payload (e.g., verify by recomputing over `headers + body`, or require the host app to independently confirm `shop` against a known/authorized session before trusting `WebhookMetadata#shop`). At minimum, document that `request.shop` is unauthenticated and must be cross-checked against an existing, previously-established session for that shop before acting on the payload.

### Proof of Concept
1. App merchant M installs the app; Shopify sends a real webhook to the app with body `B`, header `X-Shopify-Hmac-Sha256: H(secret, B)`, and `X-Shopify-Shop-Domain: m.myshopify.com`.
2. M (an unprivileged internet user relative to other tenants) intercepts this legitimate request to their own endpoint (e.g., via a proxy they control) and resends it to the app's public webhook endpoint, unchanged except `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `Utils::HmacValidator.validate(request)` in `Registry.process` recomputes the HMAC only over `@raw_body`, which is unchanged — validation succeeds. [4](#0-3) 
4. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed_body_from_M, ...)` and processes M's data as if it belonged to `victim`.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
