Confirmed: the `shop` field delivered to the app's webhook handler is sourced entirely from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, and the HMAC signature only covers the raw request body (`to_signable_string` returns `@raw_body`), never the `shop`, `topic`, or `webhook_id` headers. This is a genuine binding break inside this gem's own code (`lib/shopify_api/webhooks/request.rb` and `lib/shopify_api/webhooks/registry.rb`), matching the analog class "a field acted on but not covered by the HMAC."

### Title
Webhook tenant identity (`shop`) is taken from an unauthenticated header not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC validated by `Utils::HmacValidator.validate` covers exclusively the JSON body bytes. Meanwhile `Registry.process` extracts the tenant identity (`shop`) from the `shopify-shop-domain`/`x-shopify-shop-domain` header — which is completely outside the signed bytes — and hands it directly to the app's `WebhookHandler#handle` via `WebhookMetadata#shop` as trusted tenant context.

### Finding Description
`lib/shopify_api/webhooks/request.rb` defines: [1](#0-0) [2](#0-1) 

`shop` is read straight from the request header via `shopify_header("shop-domain")`, while `to_signable_string` (the value that is HMAC-verified) is only the raw body. `Utils::HmacValidator.validate` only ever compares the HMAC over `to_signable_string`: [3](#0-2) 

`Registry.process` then trusts `request.shop` (unauthenticated) equally alongside the HMAC-checked body, packaging it into `WebhookMetadata` that is delivered to the app's handler as authoritative tenant identity: [4](#0-3) 

The gem's own documentation instructs integrators to treat `data.shop` as the shop domain of the webhook and use it directly to attribute data (e.g., `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`): [5](#0-4) 

The broken identity equality is: `shop_header_value == tenant_the_signature_actually_authenticates`. Since the signature is computed only over body bytes, any request whose body-plus-HMAC pair is valid for *some* shop (e.g., a shop the attacker legitimately controls or has installed the app on) can be replayed to the same endpoint with the `shop-domain` header rewritten to name a different, victim shop. `Utils::HmacValidator.validate` will still return `true` because it never inspects the header, and `Registry.process` will construct `WebhookMetadata` attributing the (attacker-controlled) body to the victim shop.

### Impact Explanation
This crosses a tenant boundary: an app builder who follows the gem's documented pattern of trusting `data.shop` for record attribution (as shown in the gem's own usage docs) can have webhook data misattributed to a different merchant than the one that actually produced/signed it, since the HMAC never binds the claimed tenant to the payload. This matches the "shop authenticated versus the shop stored as a session key" cross-tenant analog class called out in scope, and can lead to cross-tenant data confusion in downstream processing.

### Likelihood Explanation
An attacker who installs the app on their own (attacker-controlled) shop obtains legitimately signed webhook bodies/HMACs for arbitrary topics they can trigger (e.g., `orders/create`), since Shopify signs and delivers real webhooks to any installed shop, including the attacker's own. The attacker then only needs to replay that valid body+HMAC pair to the app's webhook endpoint with a forged `shop-domain` header value, which requires no secrets, tokens, or privileged access — just standard internet access to the public webhook endpoint.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) in the HMAC-covered signable content, or independently verify the `shop` header against a value cryptographically derived from data inside the signed body/metadata rather than trusting the header verbatim. At minimum, document prominently that `data.shop` must not be used for tenant attribution without additional server-side verification (e.g., cross-checking against the shop's stored, previously-verified domain), since the current documented usage pattern encourages exactly this misuse.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com`; trigger a real webhook (e.g. `orders/create`) to obtain a body `B` with a valid `shopify-hmac-sha256` value `H` (`Base64(HMAC-SHA256(client_secret, B))`), computed by Shopify.
2. Replay the exact same `B`/`H` pair to the app's webhook endpoint, but set `shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request#hmac` decodes `H` and `Utils::HmacValidator.validate` recomputes `HMAC-SHA256(client_secret, B)`, matching `H` — the check passes because it never touches the `shop-domain` header: [6](#0-5) 
4. `Registry.process` calls the app handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: B, ...)`, causing the attacker's own webhook data to be processed and attributed as if it belonged to `victim.myshopify.com`.
