### Title
Missing uniqueness enforcement on `erc20TokenAddresses` lets a single real transfer double-count in `Hinkal.transact`'s per-index `balanceDif` check, minting shielded value without backing - (File: contracts/Hinkal.sol)

### Summary
`Hinkal.transact` snapshots `oldBalances`/`newBalances` per array *index* via `getBalancesForArray` and then validates each index independently against `amountChanges[i] + utxoAmount`. Neither `dimensionsCheck` nor `checkOnchainCreation` in `HinkalHelper.sol` enforce that `circomData.erc20TokenAddresses` entries are distinct/non-aliased, so an attacker can make two indices reference the same underlying token balance (trivially the same address twice, or a custom "twin" token where two addresses share one storage-backed balance) and have a single real transfer satisfy two independent `balanceDif` equations, minting two sets of shielded value from one real deposit.

### Finding Description
Equality claimed to hold: for each index `i`, `balanceDif[i] == (onChainCreation[i] ? 0 : amountChanges[i]) + utxoAmount[i]` [1](#0-0) , with the intended global invariant "net tokens entering Hinkal == sum(amountChanges) + sum(on-chain UTXO amounts)".

Root cause: `balanceDif` is derived per-index from `getBalancesForArray(circomData.erc20TokenAddresses)`, which simply calls `balanceOf`/`address(this).balance` for each entry in the array independently [2](#0-1) . No code path deduplicates or checks distinctness of `erc20TokenAddresses`. `dimensionsCheck` only checks array *lengths* match `dimensions.tokenNumber`, never that addresses are unique [3](#0-2) , and `checkOnchainCreation` only validates `amountChanges[i]==0` / zero nullifiers when `onChainCreation[i]` is true, again per-index, with no cross-index consistency check [4](#0-3) .

Exploit flow (pure `transact`, no privileged role needed):
1. Attacker crafts `circomData.erc20TokenAddresses = [A, A]` (or `[A, B]` where `B` is an attacker-deployed token whose `balanceOf(vault)` reads/aliases the same underlying storage as `A`).
2. Index 0: `amountChanges[0] = +amount`, a genuine deposit; `_internalTransact` performs one real `transferERC20TokenFromOrCheckETH` moving `amount` real tokens of `A` into the vault [5](#0-4) . This makes `newBalances[0]-oldBalances[0] = amount`, matching `amountChanges[0]`.
3. Index 1: also address `A` (or its alias `B`), with the attacker's own valid ZK proof constructing a shielded output for that slot with `amountChanges[1] = +amount` and no real second transfer. Because `newBalances[1]` and `oldBalances[1]` are computed by re-reading the *same* real balance already moved in step 2, `balanceDif[1] = newBalances[1]-oldBalances[1] = amount` as well — even though zero additional real tokens entered the vault for this second index.
4. The check `balanceDif[1] == amountChanges[1] + utxoAmount[1]` (`amount == amount + 0`) passes spuriously, and the circuit's own per-slot ledger constraint (`inTotal+amountChanges===outTotal`) is satisfied purely algebraically since the attacker controls their own nullifiers/UTXOs for that slot.
5. Result: one real transfer of `amount` backs two independently-verified deposit slots of `amount` each, so `insertCommitments` mints shielded UTXOs worth `2*amount` for token `A` while the vault only received `amount`.

Existing guards do not stop this: `verifyProof`/`buildVerifierId` only check the ZK relation per declared public inputs, not real-world balance aliasing; `rootHashExists`/`insertNullifiers` police double-spending of *existing* leaves, not creation of new unbacked leaves; `performHinkalChecks`'s `dimensionsCheck`/`checkOnchainCreation` never assert uniqueness of `erc20TokenAddresses`; and the balance/slippage `require`s in `transact` operate strictly per-index, blind to cross-index aliasing of the same real balance.

Note: `Hinkal.prooflessDeposit` itself is not vulnerable to this — its `_handleTransfersFromProoflessDeposit` measures `balanceBefore`/`balanceAfter` immediately around each specific real `transferERC20TokenFromOrCheckETH` call per unique token, so every minted on-chain commitment there is backed by an actually-observed balance delta at that instant [6](#0-5) . `prooflessDeposit` and `transact` are also separate, non-chained entrypoints protected individually by `nonReentrant`, so the literal claim that "routing a prooflessDeposit call" makes `transact`'s check pass is not an accurate call path — the actual bug lives entirely inside `transact`'s own per-index balance snapshotting.

### Impact Explanation
An attacker can mint shielded UTXOs backed by less real value than deposited, directly matching the Critical category "minting shielded value without backing (protocol insolvency)". The attacker gains `amount` of freely-minted shielded balance per repeated/aliased index for every real `amount` deposited, and this is repeatable per transaction (can be scaled by repeating the aliased address N times in the array, subject to `dimensions.tokenNumber` limits), enabling systematic draining of the vault's real reserves once the fraudulent UTXOs are later withdrawn by any other legitimate-looking `transact` call.

### Likelihood Explanation
Preconditions are minimal and fully within an unprivileged attacker's control: they only need to (a) build valid Circom inputs/proof for their own UTXOs (a normal user capability), (b) list an aliased/duplicate address twice in `erc20TokenAddresses`, and (c) optionally deploy a custom token exposing two addresses over one balance for less trivial cases (the same-address duplication case requires no custom token at all). No special tree state, no relayer, no privileged role is needed. Cost is a single `transact` call.

### Recommendation
Enforce strict uniqueness of `circomData.erc20TokenAddresses` in `dimensionsCheck` (or a dedicated check in `performHinkalChecks`), rejecting any transaction where the same address (or any two addresses proven to reference the same balance, if that's feasible) appears more than once. Additionally, consider aggregating `balanceDif` accounting per unique token address rather than per raw array index before comparing to the sum of `amountChanges`/`utxoAmount` for that token, so that balance changes cannot be attributed to more than one shielded ledger entry.

### Proof of Concept
Foundry test plan:
1. Deploy a standard ERC20 `TokenA`, mint balance to attacker, approve Hinkal.
2. Build `circomData` with `erc20TokenAddresses = [TokenA, TokenA]`, `amountChanges = [amount, amount]`, `onChainCreation = [false, false]`, valid nullifiers/proof for a locally-run circuit that treats slot 0 and slot 1 as independent deposits of `amount` each (in_total=0, out_total=amount per slot).
3. Call `transact` with `externalActionData.externalAddress = attacker` and only ONE real transfer of `amount` occurring via `_internalTransact`'s deltaAmountChange>0 branch for index 0 (index 1 aliases the same address, so no extra transfer executes, yet its `balanceDif` still equals `amount` because it reads the same post-transfer balance).
4. Assert: `TokenA.balanceOf(vault) - balanceBefore == amount` (only one real deposit), while `sum(amountChanges) + sum(utxoAmount) == 2*amount` (two shielded outputs credited) — proving `vault balance delta < credited shielded value`, violating the intended invariant `net tokens entering Hinkal == sum(amountChanges) + sum(on-chain UTXO amounts)`.

        TokenWithAmount[] memory uniqueTokens,
        uint256 uniqueCount
    ) private {
        for (uint256 i = 0; i < uniqueCount; i++) {
            address erc20Address = uniqueTokens[i].erc20Address;
            uint256 amount = uniqueTokens[i].amount;

            uint256 balanceBefore = getERC20OrETHBalance(erc20Address);
            if (erc20Address == address(0)) balanceBefore -= msg.value;

            transferERC20TokenFromOrCheckETH(
                erc20Address,
                msg.sender,
                address(this),
                amount
            );

            uint256 balanceAfter = getERC20OrETHBalance(erc20Address);

            require(
                balanceAfter - balanceBefore == amount,
                "proofless deposit balances must be equal"
            );
        }
    }
