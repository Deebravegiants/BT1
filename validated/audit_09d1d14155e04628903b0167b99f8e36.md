## Title
Webhook shop/topic identity spoofing via HMAC that only covers the raw body - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook by checking `Utils::HmacValidator.validate(request)`, but the HMAC signature only ever covers the raw request body — never the `shop-domain`, `topic`, `api-version`, or `webhook-id` headers that the handler is dispatched and keyed on.

### Finding Description
`Webhooks::Request#to_signable_string` returns `@raw_body` only, and `#hmac` decodes the `X-Shopify-Hmac-Sha256` header: [1](#0-0) 

`Registry.process` uses the validated request's `topic` to look up the handler and, critically, forwards `request.shop` (read straight from the `shopify-shop-domain` header) into `WebhookMetadata` given to the app's handler: [2](#0-1) 

`HmacValidator.validate` computes the HMAC purely over `to_signable_string`, i.e. the raw body — it never mixes in `shop`, `topic`, or any other header: [3](#0-2) 

Because the signature is only `HMAC(secret, raw_body)`, any two webhook deliveries with an identical (or attacker-reproducible) body produce the identical, valid HMAC digest regardless of which shop or topic header accompanies it. The identity binding broken is:
`HMAC-verified bytes (raw_body) != identity fields the handler trusts (shop-domain, topic header)`.

An unprivileged attacker who can submit HTTP requests to the app's webhook endpoint (the endpoint is public — that's the whole point of a webhook receiver) can take **any previously observed valid `(raw_body, hmac)` pair** (e.g., a webhook for their own trial/dev shop, which they fully control and can generate legitimate webhooks from), and replay it with a forged `shopify-shop-domain` header pointing at a **different, victim tenant**. `HmacValidator.validate` will still return `true` because it only checks the body signature, and `Registry.process` will happily hand the handler a `WebhookMetadata` claiming `shop: <victim-shop>` with attacker-controlled `body`.

### Impact Explanation
This is a cross-tenant identity-confusion primitive: the shop identity that gates a multi-tenant app's data model (which merchant's data to update/delete/react to) is not authenticated by the HMAC at all — it's taken from an unauthenticated header. Any host app that follows this gem's documented `WebhookMetadata#shop` field (as the samples in `docs/usage/webhooks.md` instruct) to select the tenant record to act on can be made to apply another shop's legitimately-signed webhook payload against a victim tenant, or vice versa (attacker's own shop content injected against a victim's shop id). Depending on the topic (e.g. `app/uninstalled`, `shop/redact`, `customers/data_request`), this can trigger cross-tenant data mutation, deletion, or disclosure routed to/from the wrong merchant — satisfying the "cross-tenant access" Critical criterion.

### Likelihood Explanation
Exploitability requires only network access to the app's public webhook endpoint (no credentials, no `api_secret_key`, no access token). The attacker needs one valid `(body, hmac)` pair, which they can trivially obtain by installing the app on their own free development store and triggering a webhook for a body they control (e.g., `customers/redact` payload, or any topic whose body content they can shape), then replaying it with a different `shop-domain` header value. Because `HmacValidator.validate` is the *only* gate in `Registry.process`, and it is header-blind, this is directly reachable through this gem's own verification API exactly as documented for consumers.

### Recommendation
Bind the shop (and ideally topic) into the value that is HMAC-verified, or otherwise authenticate the `shop-domain` header independently — e.g., include the `shop-domain`/`topic` headers in the signable string (this deviates from Shopify's wire format, so instead: after verifying the body HMAC, cross-check `request.shop` against the shop that the app already has an active, distinct session/webhook-registration record for that topic, rejecting shops it did not register the webhook for) before dispatching to `WebhookHandler#handle`. At minimum, `Registry.process` and the docs should explicitly warn that `WebhookMetadata#shop` is **not** covered by the HMAC and must not be trusted for tenant selection without additional verification (e.g. comparing against a shop that is known to have this webhook subscription active).

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` (a shop they own) and lets it register for topic `customers/redact`.
2. Shopify sends a legitimately signed webhook to the app: body `B`, header `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, header `X-Shopify-Hmac-Sha256: H = Base64(HMAC-SHA256(secret, B))`.
3. Attacker captures `(B, H)` (e.g., via their own logging, since it's *their* webhook).
4. Attacker crafts a new POST to the app's webhook endpoint with the same raw body `B` and same `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Utils::HmacValidator.validate(request)` calls `compute_signature(request.to_signable_string, secret)`, which only depends on `B` — the forged shop header is irrelevant to the check, so validation succeeds. [4](#0-3) 
6. `Registry.process` proceeds, builds `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed_body, ...)` and invokes the app's handler with attacker-chosen `body` attributed to the victim shop. [5](#0-4)

          received_signature = verifiable_query.hmac
