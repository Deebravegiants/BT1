Confirmed: `WebhookMetadata` at [1](#0-0)  exposes `shop` as a first-class field the host application's `WebhookHandler#handle` is expected to trust for tenant identification, and this `shop` value is sourced directly from an unauthenticated HTTP header.

### Title
Webhook `shop`/`topic` identity headers are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw request body, never the `shop-domain` or `topic` headers. `Registry.process` validates the HMAC over that body-only string and then unconditionally trusts `request.shop` and `request.topic` — values read straight from headers — to build the `WebhookMetadata` handed to the app's handler. This is the same identity-binding gap as the `bps()` bug: a value that is *acted upon* (the shop the data is attributed to) is never part of the *verified* bytes.

### Finding Description
- The HMAC is computed and checked only over `@raw_body`: [2](#0-1) 
- `shop`, `topic`, `webhook_id`, and `api_version` are read directly from headers with no cryptographic binding to the signature: [3](#0-2) 
- `Registry.process` validates only the HMAC of the body, then immediately trusts `request.shop`/`request.topic` for dispatch and metadata construction: [4](#0-3) 
- `HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` — i.e., it only ever verifies the body string, never the headers: [5](#0-4) 

The equality the code implicitly (and wrongly) assumes is: `HMAC-valid body ⇒ shop header is authentic`. In reality `HMAC-valid(body)` only proves the body bytes were signed by Shopify with *this app's* `client_secret` — a secret shared across *every* merchant that has installed the app, not scoped per-shop. It says nothing about which shop's webhook delivery originated the request. Any party who can trigger a genuine webhook delivery for **their own** shop (any real Shopify merchant/developer, including a free dev store) legitimately receives a `(body, x-shopify-hmac-sha256)` pair signed with the app's secret. Because the header carrying the shop identity is excluded from `to_signable_string`, that exact `(body, hmac)` pair remains valid when replayed to the app's webhook endpoint with an arbitrary `shop-domain` header substituted for a victim shop.

### Impact Explanation
This breaks the tenant boundary the gem is documented to provide via `WebhookMetadata#shop`, which downstream handlers use to attribute the webhook body to a specific merchant: [1](#0-0) . An attacker who legitimately installs the app on their own store can capture a validly-signed webhook and replay it with a forged `shop-domain` header, causing the host application to process attacker-controlled data as if it belonged to a different, victim merchant — a cross-tenant access/data-injection primitive. This meets the Critical bar (cross-tenant access) defined in scope.

### Likelihood Explanation
Any Shopify merchant/developer who has installed the target app on any store (including a free development store) can generate an arbitrary number of genuinely-signed `(body, hmac)` pairs for topics of their choosing, then freely swap the `shop-domain` (and even `topic`) header before delivering the request to the app's public webhook endpoint. No secrets, tokens, or privileged access to the victim are required — only the ability to install the app once, which is the normal, expected way of using this gem.

### Recommendation
Bind the shop (and ideally topic) identity into the verified material. Concretely, `Webhooks::Request#to_signable_string` should not be the only server-side trust anchor for `shop`; the gem should either:
1. Require callers/hosts to independently confirm that `request.shop` corresponds to a shop with an active, stored session/installation before dispatching (i.e., look up an existing session by `request.shop` and reject if none exists), and/or
2. Document/enforce that the raw body's own shop-identifying content (e.g., `Content-Type`/domain fields embedded by Shopify in the JSON payload where available) is cross-checked against the header, rather than trusting the header alone as an identity source passed to `WebhookHandler#handle`.

At minimum, the gem's documentation and `Registry.process` should make explicit that `request.shop`/`request.topic` are **not** authenticated by the HMAC check and must not be used as the sole tenant/topic discriminator without an additional server-side authorization lookup.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (a normal, unprivileged action available to any developer/merchant).
2. Attacker registers a webhook (e.g. `customers/create`) and triggers it on their own shop with an attacker-chosen body, e.g. `{"id":1,"email":"attacker@evil.com","note":"payload"}`.
3. Shopify legitimately delivers this webhook to the app's endpoint with headers computed by Shopify using the app's real `client_secret`:
   ```
   x-shopify-topic: customers/create
   x-shopify-hmac-sha256: <valid HMAC of the JSON body>
   x-shopify-shop-domain: attacker-shop.myshopify.com
   ```
4. Attacker captures this exact `(body, x-shopify-hmac-sha256)` pair (they receive it themselves; no interception of victim traffic needed) and replays it to the same endpoint, changing only:
   ```
   x-shopify-shop-domain: victim-shop.myshopify.com
   ```
5. `ShopifyAPI::Webhooks::Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `to_signable_string` (`@raw_body`), unchanged from step 3.
6. The handler is invoked with `WebhookMetadata.new(topic: "customers/create", shop: "victim-shop.myshopify.com", body: {"id"=>1,"email"=>"attacker@evil.com", ...}, ...)`, causing the host app to attribute attacker-controlled data to `victim-shop.myshopify.com`, demonstrating the cross-tenant identity-binding failure.
