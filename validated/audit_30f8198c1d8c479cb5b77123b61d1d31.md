### Title
Unbounded `order.inputs` array length lets a user permanently freeze their own escrow and DoS cross-chain settlement delivery - ([File: evm/src/apps/IntentGatewayV2.sol])

### Summary
`placeOrder()` in `IntentGatewayV2.sol` accepts a caller-supplied `order.inputs` array with no maximum length check, and every downstream consumer of that order (`placeOrder` itself, `fillOrder`/`_withdraw`, and the cross-chain `onAccept`/`withdraw` path) iterates the full array in an unbounded `for` loop. This mirrors the LockedStaking `getRewardsWeight()` bug class: a storage/message-derived array with no cap, iterated in a function that can revert once the array is large enough to exceed the tx/block gas limit — except here the "owner-controlled" mitigation from the original report doesn't apply, because the array length is chosen entirely by an untrusted, unprivileged order-placer.

### Finding Description
`placeOrder()` only checks `order.inputs.length == 0` and rejects duplicate tokens; it never bounds the array's upper size: [1](#0-0) 

The function then loops over `inputsLen` several times (fee-token swap setup, transfer-and-record loop, escrow-credit loop): [2](#0-1) [3](#0-2) [4](#0-3) 

Because `order.inputs` is embedded in the order and its commitment, the *same length* must be replayed by every later consumer of that commitment:
- `_withdraw()` in `IntentsBase.sol`, which iterates `body.tokens` (mirroring `order.inputs`) on every fill, cancel, and cross-chain settlement: [5](#0-4) 
- `onAccept()`, which is invoked by the EVM `IsmpHost` when a relayer delivers a `RedeemEscrow`/`RefundEscrow` cross-chain message — i.e. an unprivileged relayer-triggered dispatch path — and calls `_withdraw()` with the attacker-chosen token list: [6](#0-5) 
- Same-chain cancellation, `_cancelSameChain()`, which rebuilds a `remainingTokens` array of size `order.inputs.length` and again feeds it to `_withdraw()`: [7](#0-6) 

No maximum-length constant or `revert` on an oversized `inputs` array exists anywhere in the intents apps (`IntentGatewayV2.sol`, `IntentsBase.sol`, `IntrinsicIntents.sol`, `ExtrinsicIntents.sol`); a grep for `MAX_INPUTS`/length caps found none in `evm/src/apps/**`.

Because the placer fully controls the number of `TokenInfo` entries (subject only to having enough distinct ERC-20 approvals/balances, or reusing dust-amount transfers), they can construct an order with an arbitrarily large `inputs` array. The resulting commitment then requires every future interaction — `fillOrder`, `cancelOrder`, and crucially the ISMP `onAccept` delivery of the cross-chain settlement message — to loop over that same array length. If the array is sized so the loop's gas cost exceeds the practical/block gas limit, the settlement message can never be delivered: `HandlerV2`/relayer submission of the `RedeemEscrow`/`RefundEscrow` request will always revert inside `onAccept -> _withdraw`, exactly the "function will always revert" failure mode from the reference report.

### Impact Explanation
Unlike the audited `LockedStaking.getRewardsWeight()`, where only the trusted owner controls array growth, here the array length is chosen by an arbitrary, unprivileged user at order placement. This lets an attacker:
- Permanently freeze their own escrowed input tokens by making them unwithdrawable by any solver/relayer (denial of settlement — funds get stuck, unable to be redeemed or refunded, since even the refund path goes through the same unbounded `_withdraw()` loop).
- More importantly, make the destination-chain settlement request from Hyperbridge (`RedeemEscrow`) undeliverable: since `onAccept()` is invoked as part of ISMP request delivery, a relayer trying to deliver this specific commitment's message will have its transaction always revert, potentially forcing a timeout/never-processed state for the associated cross-chain message and permanently locking the corresponding escrow with no way to reach the solver or the refund path either (both call the same `_withdraw`).

This qualifies as a Medium-severity fund-freezing/DoS-of-message-delivery bug reachable from a single unprivileged `placeOrder` transaction.

### Likelihood Explanation
Likelihood is Medium: constructing such an order requires the attacker to actually possess/approve a large number of distinct ERC-20 tokens (or reuse very small amounts of a few tokens is not sufficient — the array uses `TokenInfo{token, amount}` and duplicate tokens are rejected via `_orders[commitment][token] != 0` checks, so the attacker needs genuinely distinct token addresses, though these do not need to be "real" tokens — cheap throwaway ERC-20 deployments are trivial and inexpensive on most EVM chains). This lowers the cost of the attack significantly compared to needing genuinely valuable assets, but it does require some up-front effort (deploying/approving many token contracts) and is limited to freezing the attacker's own future settlement, unless combined with griefing another route (e.g., forcing a relayer to repeatedly attempt-and-fail delivery, burning relayer gas without payout).

### Recommendation
Add an explicit maximum bound on `order.inputs.length` (and correspondingly on `order.output.assets.length`) enforced in `placeOrder()`, similar to the post-audit fix applied to `LockedStaking` (`rewards` array). Reject orders whose `inputs`/`outputs` array exceeds a conservative cap sized so that the worst-case `_withdraw()` loop (transfers + `_orders` mapping writes) safely fits well within a typical block gas limit, leaving headroom for the surrounding `onAccept`/message-verification overhead.

### Proof of Concept
1. Attacker deploys `N` cheap mock ERC-20 tokens (or reuses tokens with trivial balances) and approves `IntentGatewayV2` for each.
2. Attacker calls `placeOrder(order, graffiti)` with `order.inputs` containing `N` distinct `TokenInfo` entries (large `N`, e.g. several hundred), each with a minimal `amount`. `placeOrder()` succeeds because there is no length cap — only the attacker pays the (large but self-funded) gas for placement.
3. A solver later calls `fillOrder()` (cross-chain path) and dispatches the settlement message; when Hyperbridge/relayer attempts to deliver the resulting `RedeemEscrow` request via `onAccept()` on the source chain, the internal `_withdraw()` loop over `N` tokens consumes gas exceeding what a block/tx can practically supply, causing the delivery transaction to always revert.
4. Because both `RedeemEscrow` and `RefundEscrow`/cancellation paths funnel through the same `_withdraw()` loop over the same `order.inputs`-length array, the escrowed funds for that commitment become permanently unredeemable and unrefundable.

    function _cancelSameChain(Order calldata order, bytes32 commitment) internal {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

        uint256 inputsLen = order.inputs.length;
        TokenInfo[] memory remainingTokens = new TokenInfo[](inputsLen);
        bool hasEscrow = false;
        for (uint256 i; i < inputsLen;) {
            address token = address(uint160(uint256(order.inputs[i].token)));
            uint256 escrowed = _orders[commitment][token];
            if (escrowed > 0) hasEscrow = true;
            remainingTokens[i] = TokenInfo({token: order.inputs[i].token, amount: escrowed});
            unchecked {
                ++i;
            }
        }
        if (!hasEscrow) revert UnknownOrder();

        WithdrawalRequest memory body =
            WithdrawalRequest({commitment: commitment, tokens: remainingTokens, beneficiary: order.user});

        _withdraw(body, true, true);
    }
