### Title
Caller-controlled swap routes inject arbitrary venue code into the caller’s authorization tree, enabling theft of unrelated wallet tokens - (File: contracts/controller/src/strategies/swap.rs) [1](#0-0) 

### Summary
Critical: the public strategy entrypoints accept an opaque `StrategySwap` byte payload and execute it through the swap router while the account owner’s `require_auth` authorization is active. [2](#0-1) [3](#0-2)  A payload-named venue can therefore invoke `token.transfer(caller, attacker, amount)` for an unrelated token as a child invocation beneath the caller’s signed controller authorization. [4](#0-3) 

### Finding Description
`swap_collateral(caller, account_id, current, amount, new, swap)` authenticates `caller`, verifies ownership or delegation, withdraws collateral, and passes the caller-provided `swap` bytes to the swap path. [5](#0-4) [6](#0-5)  The shared swap helper snapshots only the controller’s input and output token balances, authorizes the router to spend the exact controller-held input, and invokes `execute_strategy(controller, amount_in, swap)`. [7](#0-6)  The subsequent checks bound only controller input spend and require positive controller output; they do not inspect nested invocations or token transfers charged to `caller`. [8](#0-7) 

Because route venue addresses are supplied by the payload rather than constrained to an on-chain allowlist, a malicious venue can execute during the router call. [9](#0-8)  That venue can call a Stellar token’s `transfer` function with the strategy caller as `from`; simulation records this unexpected transfer as a child of the caller’s `swap_collateral` authorization, and enforcement executes it when that recorded tree is signed. [10](#0-9) [11](#0-10)  The malicious route can simultaneously return a fair output, so all controller balance checks and final account risk checks can pass while the unrelated wallet-token theft succeeds. [12](#0-11) 

The same `StrategySwap` sink is reachable through `swap_debt`, `repay_debt_with_collateral`, `multiply`, and `multiply`’s third-asset `convert_swap` path. [13](#0-12) [14](#0-13) [15](#0-14) [16](#0-15) 

### Impact Explanation
An attacker can steal any token held by the account owner or delegate that signs the poisoned authorization tree, including assets unrelated to the lending position and not listed by the protocol. [17](#0-16) [10](#0-9)  The loss is not bounded by the submitted swap input, minimum output, controller overspend check, or final position risk check. [8](#0-7) [18](#0-17) 

### Likelihood Explanation
The malicious venue must be reached by a submitted route and the victim must sign the authorization tree containing its nested transfer. [19](#0-18)  A crafted or substituted route can cause normal transaction simulation to record that poisoned child invocation, so signing the simulated tree makes the theft deterministic while preserving a valid-looking swap output. [20](#0-19) 

### Recommendation
Do not allow route payloads to name arbitrary venue contracts while a caller authorization is active; resolve venues only from governance-approved immutable adapters or a verified pool registry whose code cannot make caller-scoped token transfers. [1](#0-0) [4](#0-3)  Until venue identities are constrained on-chain, clients must decode both the route and simulated authorization tree and reject any child invocation other than the expected input transfer. [21](#0-20) 

### Proof of Concept
1. Alice owns a lending account, has supplied USDC, and holds an unrelated `WALLET_TOKEN` in her wallet. [22](#0-21) 
2. The attacker deploys a venue contract storing `(victim = Alice, token = WALLET_TOKEN, to = attacker, amount = Alice's balance)`. [23](#0-22) 
3. The attacker constructs `swap` bytes whose route invokes that venue while declaring USDC input and ETH output with a fair `min_out`. [24](#0-23) 
4. Alice calls `swap_collateral(alice, account_id, usdc_key, amount, eth_key, malicious_swap)`. [25](#0-24) 
5. During router execution, the venue calls `WALLET_TOKEN.transfer(Alice, attacker, balance)`. [10](#0-9) 
6. Simulation places that transfer under Alice’s `swap_collateral` authorization; after she signs the simulated tree, Alice’s unrelated wallet token balance becomes zero and the attacker receives it while the strategy still deposits the expected ETH output. [26](#0-25) [19](#0-18)

#[test]
fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
