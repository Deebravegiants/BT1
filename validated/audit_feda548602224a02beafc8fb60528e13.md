### Title
Unallowlisted swap-route pool executes attacker code under the caller's authorization, draining arbitrary wallet tokens - (File: contracts/swap-aggregator/src/venues/mod.rs)

### Summary
The swap router decodes the `pool` address for every hop straight from the caller-supplied `assets` registry in `swap_xdr`, keeps no allowlist of venues or pools, and `invoke_contract`s whatever address is named. A malicious "pool" contract runs on the call stack beneath the caller's `require_auth` entry, so any `token.transfer(caller, attacker, X)` it issues is recorded into the caller's auth tree by simulation and executes once the caller signs that tree. This is the on-chain analog of a parameter/command-injection bug: an unsanitized user-controlled parameter (the pool address) selects the code that executes inside a privileged authorization context.

### Finding Description
`execute_strategy(sender, total_in, swap_xdr)` authenticates only `sender` and then trusts the payload's address registry. In `execute_op`, `hop.pool = ctx.assets.get_unchecked(op.idx_a)` is taken verbatim from the XDR — no venue whitelist, no pool verification ( [1](#0-0) ). `dispatch_hop` then calls the venue adapter, which `invoke_contract`s `ctx.hop.pool` directly (e.g., Phoenix `env.invoke_contract(&ctx.hop.pool, "swap", ...)`, Comet `swap_exact_amount_in`, Aquarius `invoke_pool_swap`) ( [2](#0-1) [3](#0-2) ).

The attacker deploys a contract exposing a `swap`-compatible function that does `token::Client::new(&env, &victim_wallet_token).transfer(&victim, &attacker, &amount)`. Because the rogue call sits under the router call which sits under the user's `execute_strategy` (or controller `swap_collateral`) `require_auth`, the token's `from.require_auth()` is satisfied only by a child entry inside the caller's signed authorization tree. `simulateTransaction` records exactly that poisoned tree, and a wallet/client that signs the simulated tree authorizes the theft. The measured-balance checks in `dispatch_hop` only police the router's own input/output balances — they do not constrain what else the pool does, and the min-out and residual checks are orthogonal.

The same path is reachable through every controller strategy that forwards a user-supplied `swap_xdr` (`swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, `multiply`), plus direct `execute_strategy` calls.

### Impact Explanation
Theft of user funds. The loss is not bounded by the routed `total_in`, the payload `min_out`, or the controller's post-swap risk gates: the rogue pool can transfer any token the victim holds, for its entire balance, to the attacker. The harness test demonstrates a victim losing `WALLET_BALANCE` of an unrelated token while still receiving a "fair" swap output ( [4](#0-3) ).

### Likelihood Explanation
Any unprivileged address can build the payload and deploy the rogue pool — no privileged role, leaked key, or off-chain component is needed. The exploit does require the victim to sign the poisoned auth tree returned by simulation; the threat model itself acknowledges "the loss is then the caller's wallet... A client must decode the route it signs", placing the entire defense on off-chain client behavior with no on-chain mitigation ( [5](#0-4) ). Routes are described as "built off-chain and passed as XDR", so realistic users sign whatever tree the route produces.

### Recommendation
Maintain an on-chain allowlist of venue pool addresses (or venue factories whose pool instances can be verified on-chain, e.g., via pool `token`/`get_tokens` identity checks plus a registry) and reject payload pools not on it, in `Program::decode`/`execute_op`. Alternatively, bind each hop to a venue-verified pool derived from trusted state rather than the caller's `assets` registry.

### Proof of Concept
1. Attacker deploys `RogueHopPool` with plan `(victim, victim_wallet_token, attacker, amount)`; its `swap()` calls `token.transfer(victim, attacker, amount)` ( [6](#0-5) ).
2. Victim submits `swap_collateral` (or direct `execute_strategy`) with a route whose `assets` registry names `RogueHopPool` as the hop pool.
3. Simulation records the stolen `transfer` as a child of the victim's auth entry; the victim signs the simulated tree (`assert_eq!(recorded, vec![(alice, poisoned_root)])`, `assert_eq!(s.wallet(&alice), 0)`) ( [7](#0-6) ).
4. With the signed poisoned tree, the rogue transfer executes and the attacker's balance equals `WALLET_BALANCE` ( [8](#0-7) ).
