### Title
Direct `Token` donation to `Pair` can permanently disable the supply-based graduation trigger, freezing curve-raised LT and the launch-time LP allocation - ([File: packages/contracts/src/Router.sol])

### Summary
`Router._computeBuy`'s overflow-cap logic and `Bonding.canGraduate`'s supply trigger both silently depend on an invariant that the Pair's *stored* virtual token reserve (`_pool.tokenReserve`) and its *live* ERC20 balance (`tokenBalance()`) are permanently locked together by a constant gap of `LP_RESERVE` (250M) tokens. That gap is maintained only by Router-mediated buys/sells; it is not re-derived or defended against a direct `IERC20(token).transfer(pair, amount)` from any token holder. A sufficiently large donation collapses the gap and can permanently prevent `tokenBalance() == 0` from ever becoming true again, disabling the supply-side graduation trigger for that token.

### Finding Description
`Pair.mint` fixes the invariant at launch: `_pool.tokenReserve` is seeded at `TOTAL_SUPPLY` (1e9) while only `curveSupply` (750M) real tokens are transferred to the pair — the two are meant to always differ by exactly `LP_RESERVE` (250M) as trading proceeds, since every `swap()` call decrements the stored `tokenReserve` by exactly the real `tokensOut` transferred out (or increments it by exactly `tokensIn` transferred in on a sell): [1](#0-0) 

`Router._computeBuy` relies on this lockstep to decide when to engage the "overflow cap" (the last buy that would exceed the pair's real supply): it compares the AMM-formula `tokensOut` (bounded above by the *stored* `reserveToken`) against `pair.tokenBalance()` (the *live* ERC20 balance): [2](#0-1) 

`Bonding.canGraduate`'s supply leg independently reads the same live balance directly: [3](#0-2) 

Because `Token` is a standard ERC20 that any buyer legitimately holds after `Zap.buy`, nothing stops a holder from calling `IERC20(token).transfer(pair, D)` directly, bypassing `Router` entirely. This increases the *live* `tokenBalance()` by `D` while leaving the *stored* `_pool.tokenReserve` untouched, shrinking the `tokenReserve - tokenBalance` gap from `LP_RESERVE` down to `LP_RESERVE - D`. The project's own test suite documents this exact invariant and its criticality: [4](#0-3) 

If `D ≥ LP_RESERVE` (250M tokens, i.e., one third of the 750M `curveSupply` ever in circulation), the gap becomes `≤ 0` and stays that way permanently: `_pool.tokenReserve` can only ever decrease further via legitimate buys, and nothing ever repairs the stored/live divergence except the one-shot `_prepareGraduationLiquidity` burn that runs only *after* the lifecycle has already left `Curve`. With the gap gone, the uncapped `tokensOut` computed from the stored reserves (`tokensOut = reserveToken - k/newReserveAsset`, always `< reserveToken`) can never exceed the now-inflated `realBalance = pair.tokenBalance()`, so the `tokensOut > realBalance` branch in `_computeBuy` (lines 140-147) can never fire again — the pair's live token balance can no longer be driven to zero by ordinary curve buys. `Bonding.canGraduate`'s supply leg (`IPair(pair).tokenBalance() == 0`) is thereby permanently disabled for that token, exactly mirroring the source report's pattern: two representations of the same conceptual quantity (`stored virtual reserve` vs. `live ERC20 balance`) that downstream trust logic assumes move in lockstep, but which an attacker can force to permanently diverge with a single unprivileged, malformed-relative-to-the-model input (a direct donation, analogous to the malformed duplicate-`tree` commit).

### Impact Explanation
Once the supply trigger is permanently disabled, the token's only remaining path to graduation is the USD trigger (`realLtRaised × exchangeRate ≥ graduationThresholdUsd`). The docs themselves acknowledge scenarios where this leg can stall indefinitely — e.g., a retired/de-registered BounceTech LT whose `exchangeRate` "stops tracking the underlying" and "the USD trigger... can't ripen further" (see `docs/contracts-scope.md` lines 77 and `Bonding.sol` comments at lines 664-672), or simply a token whose LT never appreciates enough. In such cases the token is permanently stuck in `Lifecycle.Curve`: `Router.graduate` / `Bonding._prepareGraduationLiquidity` are unreachable outside the Graduating/Graduated lifecycle transitions, so the curve-raised LT and the reserved 250M-token LP allocation held in `Bonding` can never be drained into a HyperSwap V2 pool via `finalizeGraduation`. This is a permanent freeze of creator/trader-raised LT and the LP token allocation for that token, triggerable by a single unprivileged wallet.

### Likelihood Explanation
The attack requires the attacker to acquire and then donate at least `LP_RESERVE` (250M) tokens — a full third of the maximum circulating `curveSupply` (750M) — which is capital-intensive but entirely feasible, particularly cheaply right after launch while curve prices are low, and requires no special role, no signing key, and no interaction with `BONDING_ROLE`-gated functions: just an ordinary `Zap.buy` followed by a plain `IERC20.transfer` to the `Pair` address. The effect is irreversible once triggered (the stored `tokenReserve` never regains the lost headroom outside of graduation itself, which this attack blocks), making it a credible medium/high-likelihood griefing vector for any token whose USD trigger is slow or stuck.

### Recommendation
Do not derive the overflow-cap/supply-trigger logic from the pair's raw `IERC20.balanceOf`. Either (a) track real token outflow/inflow in dedicated `Pair` storage updated only by `Router`-mediated `swap()` calls (mirroring how `assetReserve`/`k` are already tracked in `_pool`), so donations cannot be conflated with curve-mediated balance changes, or (b) explicitly subtract any donation surplus (`tokenBalance() - expectedRealBalance`) before comparing against `realBalance` in `_computeBuy`, treating excess live balance the same defensive way `_prepareGraduationLiquidity` already treats donated LT — i.e., make the supply trigger and overflow cap immune to direct-transfer griefing the same way the USD trigger and LP seeding were already hardened against donation (see the existing "donation resistance" fix referenced in `GraduationInvariants.t.sol` around line 423).

### Proof of Concept
```solidity
// Using the existing test harness in packages/contracts/test/*.t.sol

function test_poc_donationDisablesSupplyTrigger() public {
    // 1. Launch a token with no seed buy (750M real tokens sit in the pair).
    (address tokenAddr, address pairAddr) = _launchNoSeed();

    // 2. Keep exchange rate flat/low so the USD trigger never fires
    //    (simulates a stalled/retired LT scenario the docs themselves describe).
    lt.setExchangeRate(0.0001 ether);

    // 3. Attacker buys a large slice of the curve legitimately via Zap/Bonding,
    //    accumulating >= LP_RESERVE (250M) worth of `tokenAddr`.
    uint256 acquired = _buy(tokenAddr, attacker, /* enough LT to acquire ~300M tokens */ 60_000_000 ether);
    assertGe(IERC20(tokenAddr).balanceOf(attacker), 250_000_000 ether);

    // 4. Attacker donates 250M+ tokens directly to the Pair, bypassing Router.
    vm.prank(attacker);
    IERC20(tokenAddr).transfer(pairAddr, 250_000_000 ether);

    // 5. Gap `reserveToken - tokenBalance()` is now <= 0. Buy out the rest of
    //    the *organic* curve supply — the overflow-cap branch in
    //    Router._computeBuy never engages, so tokenBalance() never reaches 0.
    uint256 pushes;
    while (IPair(pairAddr).tokenBalance() > 0 && pushes < 500) {
        _buy(tokenAddr, trader2, 1_000_000 ether);
        pushes++;
    }

    // Expected: tokenBalance() stays > 0 forever (supply trigger dead),
    // and with exchangeRate flat, canGraduate() stays false permanently.
    assertGt(IPair(pairAddr).tokenBalance(), 0, "supply trigger permanently disabled by donation");
    assertFalse(bonding.canGraduate(tokenAddr), "token can never graduate");
}
```
Note: the exact `acquired`/donation sizing depends on live `VIRTUAL_LIQUIDITY_USD`/`LP_RESERVE` constants; the PoC illustrates the mechanism (donate ≥ `LP_RESERVE` tokens directly to `Pair`) rather than exact production-sized numbers, which were not independently re-derived here due to the size of the constants table not being fully re-verified in this pass — a background agent should confirm `LP_RESERVE`'s exact value and the cheapest way to acquire it pre-graduation before relying on this PoC verbatim.

    function _computeBuy(
        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 amountInUsed, uint256 tokensOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        amountInUsed = amountIn;

        uint256 newReserveAsset = reserveAsset + amountInUsed;
        tokensOut = reserveToken - (k / newReserveAsset);

        uint256 realBalance = pair.tokenBalance();
        if (tokensOut > realBalance) {

            uint256 cappedReserveToken = reserveToken - tokensOut;
            if (cappedReserveToken == 0) revert OverflowCapDegenerate();
            uint256 cappedReserveAsset = (k + cappedReserveToken - 1) / cappedReserveToken;
            amountInUsed = cappedReserveAsset - reserveAsset;
        }
    }
