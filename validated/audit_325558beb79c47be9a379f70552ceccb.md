### Title
Webhook `shop` identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates only the HMAC over the raw request body before dispatching the webhook to the app's handler. The `shop` value handed to the handler is read directly from the unauthenticated `X-Shopify-Shop-Domain`/`shopify-shop-domain` HTTP header, which is not part of the signed data at all.

### Finding Description
`Utils::HmacValidator.validate` computes and compares the HMAC over `verifiable_query.to_signable_string`. For a webhook `Request`, `to_signable_string` returns only `@raw_body`: [2](#0-1) 

None of the identifying headers — `shop`, `topic`, `webhook_id`, `api_version` — are included in the signable string: [4](#0-3) 

`Registry.process` then trusts `request.shop` (the raw header) to build `WebhookMetadata` passed to the app's handler, immediately after HMAC validation succeeds: [3](#0-2) 

The identity binding that should hold is: `hmac_valid(body)` implies `shop_header == the shop that actually produced this signed body`. That equality is never checked — the HMAC only proves the payload's *body* bytes originated from a party who knows `api_secret_key` (i.e., genuinely from Shopify for some shop), but it says nothing about *which* shop the header claims to be. Because the HMAC covers `@raw_body` only, any two webhook deliveries with identical bodies (e.g. topics with empty/shop-independent bodies such as `{}` , or any two payloads that happen to be byte-identical) will produce the *same valid HMAC value* under the same `api_secret_key`, regardless of shop.

This lets a party who legitimately installs the app on their own store (an ordinary, unprivileged Shopify merchant action — no `api_secret_key`, access token, or other credential is required) capture one authentically-signed webhook delivery, then replay the exact same body + `hmac-sha256` header to the app's webhook endpoint while substituting the `shop-domain` header with a different, victim shop's domain. `HmacValidator.validate` will still succeed (the body and HMAC pair is genuinely valid), and `Registry.process` will hand the handler `shop: <victim-shop>` — a value that was never authenticated.

### Impact Explanation
If the host application's webhook handler uses `data.shop` (per `docs/usage/webhooks.md` and `WebhookMetadata`) to look up tenant-specific state, trigger per-tenant side effects (e.g. processing `app/uninstalled` cleanup, disabling billing, updating cached shop data), this allows an attacker who controls only their own shop to make the app believe an event happened on a shop they do not own — a cross-tenant action performed against another merchant's account without ever needing that merchant's credentials or the app's `client_secret`. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitability only requires: (1) installing the app on an attacker-controlled/free development store (an unprivileged action any internet user can perform if the app is public), (2) capturing one genuine webhook delivery with a body that doesn't itself encode shop-specific identifiers (common for several topics, e.g. `app/uninstalled` bodies are often `{}`), and (3) replaying it with a forged `shop-domain` header. No secret material or elevated access is needed, and the library's own `HmacValidator`/`Registry.process` code path provides no defense against this because the shop header is architecturally outside the signed payload.

### Recommendation
Do not treat `request.shop` as trusted merely because the body HMAC validated. At minimum, document/require host applications to cross-check `WebhookMetadata#shop` against the shop associated with the currently active/stored session before performing any tenant-scoped action, or extend `Webhooks::Registry.process` to require the caller to supply/verify the expected shop out-of-band (e.g., match against a registered shop before dispatch). Longer-term, this is an inherent property of Shopify's webhook signing scheme (HMAC over body only), so the mitigation belongs at the gem's documentation/handler-contract level: explicitly warn implementers that `shop` in `WebhookMetadata` is not cryptographically bound to the signature and must not be used as an authorization decision on its own.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (ordinary self-service action).
2. App fires an `app/uninstalled` webhook (or any topic with a fixed/empty body) to the app's webhook endpoint; attacker captures the raw request, including the `shopify-hmac-sha256` header and `{}` (or whatever fixed) body.
3. Attacker replays the identical body and `shopify-hmac-sha256` header to the same endpoint, but sets `shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate(request)` succeeds because it only checks the (unchanged) body against the (unchanged) HMAC:
```ruby
# lib/shopify_api/utils/hmac_validator.rb
def validate_signature(verifiable_query, secret)
  received_signature = verifiable_query.hmac
  computed_signature = compute_signature(verifiable_query.to_signable_string, secret) # = raw_body only
  OpenSSL.secure_compare(computed_signature, T.must(received_signature))
end
```
5. `Registry.process` dispatches the handler with `shop: "victim-shop.myshopify.com"`, even though that shop never sent this webhook.
