This confirms it: the doc explicitly says `Registry.process` "will verify the request did indeed come from Shopify" as a whole, and the app is instructed to trust `data.shop` from the webhook (`docs/usage/webhooks.md` lines 12-14, 25-26) — but the gem's own `Request#shop` reads the unauthenticated `shopify-shop-domain` header, while the HMAC (`Utils::HmacValidator.validate`) only ever signs `to_signable_string`, which for `Webhooks::Request` returns just `@raw_body`.

### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) exclusively from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, which is never included in the HMAC-signed material. `Registry.process` validates only that the raw body's HMAC is correct, then forwards the header-derived `shop` to the host application's handler unchecked. Because the signature does not bind `shop` to the body, any request bearing a previously-observed valid `(body, hmac)` pair can be replayed with an arbitrary `shop` header and will still pass `Utils::HmacValidator.validate`.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Webhooks::Request#shop` is read straight from an attacker-controllable header, with no cryptographic binding to the signed body: [2](#0-1) 

`Registry.process` validates the HMAC over the request (i.e., over the body only) and then constructs `WebhookMetadata` using `request.shop` and `request.topic`, both taken from headers that are outside the signed scope, passing them straight to the host app's handler: [3](#0-2) 

`Utils::HmacValidator.validate` only computes/compares the signature against `verifiable_query.to_signable_string`, i.e. the body — it has no notion of `shop` at all: [4](#0-3) 

The equality the gem is implicitly supposed to guarantee is: `shop delivered to the handler == shop that the signed body was actually generated for`. In reality the gem guarantees only `hmac(body) == hmac(body)`; `shop` is disjoint from the signed material. The gem's own documentation instructs host apps to trust `data.shop` directly for tenant-scoped processing (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), reinforcing that this field is meant to be an authenticated identity claim, not an arbitrary passthrough header: [5](#0-4) 

**Attack path (no `api_secret_key` needed):** Because a single app-level `api_secret_key` signs webhooks for every shop that installs the app, any merchant that has installed the app (an "unprivileged" tenant with no special access) legitimately receives real Shopify webhooks for their own shop — each with a valid `(raw_body, hmac)` pair addressed to their own `shop-domain` header. That merchant can capture such a webhook and replay the exact same HTTP request to the app's webhook endpoint while only changing the `X-Shopify-Shop-Domain` header to a victim shop's domain. The HMAC still validates (it only covers the body), but `Registry.process` will now hand `WebhookMetadata` to the handler claiming the data belongs to the victim shop.

### Impact Explanation
If the host application relies on `data.shop` from `WebhookMetadata` to select the tenant context for storing or acting on webhook data (exactly as the gem's own documentation recommends), an attacker-controlled shop label lets one tenant's webhook body be attributed to and processed under a different, victim tenant. This is a cross-tenant integrity/authentication violation: the gem is providing a false authenticity guarantee ("this is verified as a signed request `for shop X`") when it has not actually authenticated the `shop` claim at all.

### Likelihood Explanation
Medium likelihood: it requires the attacker to be a real, currently-installed merchant of the target app (so they can observe at least one legitimate webhook and its HMAC), and it requires the host app to key tenant/session lookups off `data.shop` — a pattern the gem's own docs actively recommend. No secret material, access token, or privileged account is needed; only an ordinary merchant installation and header manipulation on replay.

### Recommendation
Extend the webhook signature verification surface to bind `shop` (and ideally `topic`/`webhook-id`) into the value that is HMAC-validated, or otherwise cryptographically tie the `shopify-shop-domain` header to the signed payload before it is trusted by `Registry.process`/exposed via `WebhookMetadata`. At minimum, document prominently that `data.shop` is unauthenticated header data and must be cross-checked against the app's own shop/session records (e.g., verifying an active offline session exists for that shop) before being used for tenant-scoped lookups.

### Proof of Concept
1. App merchant M installs the app; Shopify delivers a legitimate webhook to the app: body `B`, header `X-Shopify-Shop-Domain: m-shop.myshopify.com`, and `X-Shopify-Hmac-Sha256: H` where `H = HMAC-SHA256(api_secret_key, B)`.
2. M (acting as attacker) captures this request and resends it to the same webhook endpoint, keeping body `B` and header `X-Shopify-Hmac-Sha256: H` unchanged, but replacing the shop header with `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC-SHA256(api_secret_key, B)` and finds it equals `H` — validation passes, since `shop` was never part of the signed content (`lib/shopify_api/webhooks/request.rb` lines 35-38, `lib/shopify_api/utils/hmac_validator.rb` lines 12-31).
4. `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: "victim-shop.myshopify.com", body: request.parsed_body, ...)` and invokes the host handler (`lib/shopify_api/webhooks/registry.rb` lines 188-199).
5. The host handler, following the gem's documented usage pattern, processes/stores webhook body `B` under `victim-shop.myshopify.com`'s tenant context — a cross-tenant data-integrity violation achieved with no credentials beyond ordinary app installation.
