## Title
Webhook HMAC only signs the raw body, allowing shop/topic impersonation across tenants - (`lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

## Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request body, then forwards the `shop`, `topic`, `webhook_id`, and `api_version` values taken from unauthenticated HTTP headers to the app's handler. Because those identity fields are never included in the signed payload, any party capable of obtaining one genuinely-signed webhook (e.g. a merchant who installs the app on their own store and receives real webhooks for it) can replay that valid body+HMAC pair to the app's webhook endpoint while substituting an arbitrary `shop-domain` header, causing the app to process an event as if it originated from a victim tenant.

## Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors are all derived from HTTP headers, which are not part of the signed data: [2](#0-1) 

`Utils::HmacValidator.validate` verifies the HMAC solely against `to_signable_string`, i.e. the raw body: [3](#0-2) 

`Registry.process` uses this check as the sole authentication gate, then trusts `request.shop` and `request.topic` (both unauthenticated header values) to build the `WebhookMetadata` passed to the app's handler: [4](#0-3) 

This breaks the intended binding: `HMAC-verified body == authenticated event` should also imply `shop header == authenticated shop`, but the library only proves the former. Because a single `client_secret` is shared by the app across every merchant installation, a merchant on their own shop can legitimately receive a validly-signed webhook (any topic, e.g. `orders/create`), then resend that exact body/HMAC pair to the app's public webhook endpoint with a forged `shopify-shop-domain` (and/or `shopify-topic`) header naming a different, victim shop. `Registry.process` will accept it as an authentic event for the victim shop.

## Impact Explanation
This allows cross-tenant impersonation: an unprivileged actor who is merely a legitimate installer of the app on their own store (no `api_secret_key`, no access token, no privileged account needed) can inject spoofed webhook events attributed to another tenant's shop domain. Depending on how the host app's webhook handlers key their side effects (e.g. updating records, revoking access, processing GDPR `customers/redact`/`shop/redact` events, syncing data) by `data.shop`, this can lead to cross-tenant data corruption or state confusion — matching the "cross-tenant access" Critical impact category.

## Likelihood Explanation
Any merchant who installs the app on their own store can trivially obtain one authentic HMAC-signed webhook body (Shopify sends these automatically), and replaying it with a modified `shop-domain`/`topic` header requires no special tooling. The only barrier is the app being reachable and processing the forged shop value meaningfully, which is the entire purpose of `WebhookMetadata#shop`.

## Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the signed/verified string (or otherwise cryptographically bind them, e.g. by validating that the `shop` header matches a shop registered/expected for that specific webhook subscription) rather than trusting header values that fall outside the HMAC's scope. At minimum, document that `WebhookMetadata#shop`/`#topic` are not authenticated by the HMAC and must be independently verified by the consuming application before being trusted for tenant-scoping decisions.

## Proof of Concept
1. Attacker (a normal merchant) installs the app on `attacker-shop.myshopify.com` and configures a webhook subscription (e.g. `orders/create`).
2. Shopify sends the attacker's app endpoint a legitimately-signed webhook: body `B`, header `shopify-hmac-sha256: HMAC(secret, B)`, `shopify-shop-domain: attacker-shop.myshopify.com`, `shopify-topic: orders/create`.
3. Attacker replays the exact same body `B` and HMAC header to the app's webhook endpoint, but changes `shopify-shop-domain` to `victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:12-31`) succeeds because it only checks `B` against the HMAC, ignoring headers.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) invokes the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, and the app processes the event as belonging to the victim tenant.

          received_signature = verifiable_query.hmac
