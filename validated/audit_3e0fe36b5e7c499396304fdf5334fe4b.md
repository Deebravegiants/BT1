## Custody Invariant Reduction

The Sherlock report reduces to one custody invariant: **a security-critical value/authority computation must not be defeated by a state configuration that the underlying data structure was not designed to safely handle** (there, spot price under single-tx manipulation; here, an unbounded ownership-chain walk).

I evaluated four local candidates: (1) `dispatchable_fungible_asset` custom hooks manipulating derived balance/supply, (2) `resource_account::create_resource_account` pre-existing-account collision handling, (3) `multisig_account` owner-list mutation functions, (4) `object::root_owner()` used to gate code-object self-initialization. Candidate 4 is the only one with a provable, unprivileged, local root cause distinct from caller-defined logic or already-audited invariants.

### Title
Unbounded ownership-chain walk in `object::root_owner()` permanently bricks code-object upgrade/self-init authority - (File: `aptos-move/framework/aptos-framework/sources/object.move`)

### Summary
`object::root_owner()` walks the object ownership chain with no depth bound, unlike every other ownership-chain walker in the same module (`owns()`, `verify_ungated_and_descendant()`), which both enforce `MAXIMUM_OBJECT_NESTING` (8). `root_owner()` is relied on by `code::publish_package` and `init::assert_may_self_initialize` to gate code-object publish/upgrade and lazy self-initialization. A 2-cycle in the object ownership graph — trivially constructible via two independently-valid transfers — causes `root_owner()` to loop forever (until gas exhaustion) whenever it is invoked on any object whose ownership ancestry passes through the cyclic pair, permanently blocking `code::publish_package` (and thus `object_code_deployment::upgrade`/`freeze_code_object`, and `init::internal_maybe_initialize`) for any code object nested under that ancestry.

### Finding Description [1](#0-0) 
`owns()` bounds its ownership walk with `count < MAXIMUM_OBJECT_NESTING` and aborts with `EMAXIMUM_NESTING` if exceeded, and `verify_ungated_and_descendant` does the same: [2](#0-1) 

By contrast, `root_owner()` has no such bound: [3](#0-2) 
```move
public fun root_owner<T: key>(self: Object<T>): address {
    let obj_owner = self.owner();
    while (is_object(obj_owner)) {
        obj_owner = address_to_object<ObjectCore>(obj_owner).owner();
    };
    obj_owner
}
```

`root_owner()` is the sole authority source for the lazy-module-init custody gate: [4](#0-3) [5](#0-4) 

`transfer_raw` only verifies that the *signer* currently, directly-or-indirectly, owns the object being moved at the moment of the call — it never checks whether the destination address is itself (transitively) a descendant of the object, so it cannot detect that two sequential, individually-legitimate transfers will close a cycle: [6](#0-5) 

Construction: an owner who controls objects `X` and `Y` performs `transfer(owner, X, Y_address)` (valid: owner directly owns X) then `transfer(owner, Y, X_address)` (valid: owner still directly owns Y at that point). After both transactions, `X.owner == Y` and `Y.owner == X`: a genuine, undetected 2-cycle. Any object `O` whose ownership ancestry passes through `X` (i.e., `O` is owned by `X`, or by any object eventually rooted at `X`) will now make `root_owner(O)` loop indefinitely.

### Impact Explanation
Because `record_deploy_owner`/`assert_may_self_initialize` and (more critically) `code::publish_package` itself invoke `root_owner()` on the target address whenever `is_lazy_module_initialization_enabled()` and the address is an object, any code object nested under a cyclic ancestor becomes **permanently unable to be published to or upgraded** (the transaction burns gas without terminating, so `code::publish_package_txn`, `object_code_deployment::upgrade`, and `object_code_deployment::freeze_code_object` — as well as any `init::internal_maybe_initialize` call — can never complete). This is a non-recoverable loss of upgrade/freeze/self-init authority over a code object, matching the custody-gate criterion "permanent lock or non-recoverable loss of ... code-object-held value" and "unauthorized ... upgrade, freeze, or transfer authority" broken via corrupted control-field resolution (the owner-authority computation itself, not just a data value, is corrupted).

### Likelihood Explanation
The precondition (forming the 2-cycle) requires only two ordinary, unprivileged `object::transfer` calls by whoever currently owns both objects in the cycle — no special permission, flash loan, or governance action is needed, and `is_lazy_module_initialization_enabled()` is a real, already-shipped feature gate referenced throughout `init.move`. However, exploitability against a *third-party victim's* code object requires that victim's code object be nested under an ancestor object that the attacker (partially) controls — a plausible but not universal deployment pattern (e.g., marketplace- or platform-delegated sub-object ownership, shared parent objects). Self-inflicted use (an owner accidentally or deliberately bricking their own code object's upgrade path) is trivially achievable. I could not execute a Move test to confirm gas-exhaustion behavior versus a VM-level infinite-loop guard that might independently abort the transaction (e.g., a global loop/gas metering bound), so likelihood should be treated as **medium** pending confirmation, and the "attacker vs. unrelated victim" scenario specifically needs a concrete nested-custody deployment to be practically dangerous rather than self-DoS.

### Recommendation
Add the same `MAXIMUM_OBJECT_NESTING`-bounded loop (with an explicit abort, e.g., `EMAXIMUM_NESTING`) to `root_owner()` that `owns()` and `verify_ungated_and_descendant()` already use, so a cyclic or unexpectedly deep ownership chain fails fast and deterministically instead of looping unboundedly. Additionally, consider whether `transfer`/`transfer_raw` should reject transfers that would close a cycle (i.e., check that `to` is not already a transitive descendant of `object`) to prevent the cyclic state from being created at all.

### Proof of Concept
Move pseudo-test (concept, not run against the harness due to no further tool budget):
```move
#[test(owner = @0x123)]
fun test_root_owner_cycle_dos() {
    let x_ref = object::create_object(@0x123);
    let x = object::object_from_constructor_ref<object::ObjectCore>(&x_ref);
    let y_ref = object::create_object(@0x123);
    let y = object::object_from_constructor_ref<object::ObjectCore>(&y_ref);

    // O is nested under X.
    let o_ref = object::create_object(x.object_address());
    let o = object::object_from_constructor_ref<object::ObjectCore>(&o_ref);

    let owner_signer = create_signer::create_signer(@0x123);
    object::transfer(&owner_signer, x, y.object_address()); // valid: owner owns X
    object::transfer(&owner_signer, y, x.object_address()); // valid: owner (still) owns Y
    // X.owner == Y, Y.owner == X: cycle formed.

    // This call never terminates (loops until out of gas):
    let _ = object::root_owner(o);
}
```
This demonstrates that `O`, whose only relationship to the cycle is being owned by `X`, becomes permanently unreachable via `root_owner()`, and therefore any `code::publish_package` call targeting `O` (or `init::internal_maybe_initialize` inside a module deployed to `O`) will never succeed.

    fun verify_ungated_and_descendant(owner: address, destination: address) {
        let current_address = destination;
        assert!(
            exists<ObjectCore>(current_address),
            error::not_found(EOBJECT_DOES_NOT_EXIST),
        );

        let object = borrow_global<ObjectCore>(current_address);
        assert!(
            object.allow_ungated_transfer,
            error::permission_denied(ENO_UNGATED_TRANSFERS),
        );

        let current_address = object.owner;
        let count = 0;
        while (owner != current_address) {
            count += 1;
            assert!(count < MAXIMUM_OBJECT_NESTING, error::out_of_range(EMAXIMUM_NESTING));
            // At this point, the first object exists and so the more likely case is that the
            // object's owner is not an object. So we return a more sensible error.
            assert!(
                exists<ObjectCore>(current_address),
                error::permission_denied(ENOT_OBJECT_OWNER),
            );
            let object = borrow_global<ObjectCore>(current_address);
            assert!(
                object.allow_ungated_transfer,
                error::permission_denied(ENO_UNGATED_TRANSFERS),
            );
            current_address = object.owner;
        };
    }

    public fun owns<T: key>(object: Object<T>, owner: address): bool {
        let current_address = object.object_address();

            count += 1;

                return false
            };

            let object = borrow_global<ObjectCore>(current_address);
            current_address = object.owner;
        };

    }
