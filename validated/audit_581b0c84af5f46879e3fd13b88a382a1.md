### Title
Webhook `shop-domain` (and `topic`/`webhook-id`) header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC verification performed by `Utils::HmacValidator.validate` binds solely to `@raw_body`. The `shop-domain`, `topic`, `webhook-id`, and `api-version` headers — which are trusted and propagated into `WebhookMetadata` used by application handlers — are never included in the signed material.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` verifies the incoming webhook via: [1](#0-0) 

The HMAC check delegates to `Utils::HmacValidator.validate`, which recomputes the signature over `verifiable_query.to_signable_string` and compares it to the `hmac` field: [2](#0-1) 

For webhook requests, `to_signable_string` returns *only* the raw JSON body — none of the Shopify-supplied headers: [3](#0-2) 

Yet `shop`, `topic`, `api_version`, and `webhook_id` — all derived from unauthenticated headers — are handed directly to the application's webhook handler as trusted identity/tenant fields: [4](#0-3) [5](#0-4) 

Because the HMAC secret (`api_secret_key`) is a single, app-wide client secret shared across *every* installed shop (not per-tenant), an attacker who has installed the app on their own shop legitimately receives correctly-signed webhook deliveries for their own tenant. Since the header `shop-domain` (and `topic`/`webhook-id`) is excluded from the signed content, the attacker can replay that same body+HMAC pair to the app's webhook endpoint while substituting the `shopify-shop-domain` header with a victim shop's domain. `Utils::HmacValidator.validate` will still accept the forged request because the body bytes are unchanged, and the application's handler will process the payload believing it originated from the victim shop, breaking the identity binding: `shop asserted in the unauthenticated header == shop the HMAC actually authenticates`.

This is the exact bug class described in the external report ("a field acted on but not covered by the HMAC"), translated to this gem's webhook verification path rather than the OAuth callback path (where `shop` *is* included in `AuthQuery#to_signable_string` and thus correctly bound): [6](#0-5) 

### Impact Explanation
This crosses a tenant boundary: data that is only integrity-protected as "some app-signed body" is presented to the host application as "data belonging to shop X" without X being covered by the signature. A host application relying on `WebhookMetadata#shop` to scope database writes, trigger per-merchant side effects, or route `shop/redact`/`customers/redact`/`customers/data_request` compliance webhooks would process (or forge) tenant-scoped events under another merchant's identity — a cross-tenant access/injection primitive, matching the "Critical - cross-tenant access" impact category.

### Likelihood Explanation
Any unprivileged internet user who can install the app on a shop they control (which is normal, unauthenticated app installation) receives legitimately-signed webhooks for their own shop. Replaying the body with a spoofed `shop-domain` header requires no secrets, no privileged account, and no interception — only observing one's own webhook traffic and resending an HTTP POST with a modified header. This is straightforward and reliably reproducible.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `webhook-id`, `api-version`) header values in the HMAC-signed material, or otherwise cryptographically bind them to the payload before trusting them in `WebhookMetadata`. At minimum, document/enforce that host applications must independently validate `data.shop` against a known/installed shop list rather than trusting it as authenticated by the HMAC check performed by this gem.

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com`; capture a legitimately delivered webhook, e.g. `orders/create`, with body `B` and header `shopify-hmac-sha256: H` (valid HMAC of `B` under the app's shared `api_secret_key`).
2. Replay the exact same request to the app's webhook endpoint, changing only the header:
   `shopify-shop-domain: victim-shop.myshopify.com` (leaving body `B` and `shopify-hmac-sha256: H` unchanged).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `request.to_signable_string` == `B` only, and it matches `H`, so validation succeeds: [7](#0-6) 
4. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: B, ...)`, i.e., attacker-controlled data is processed as if it belongs to `victim-shop.myshopify.com`: [8](#0-7)

          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
