### Title
Token Exchange trusts the unvalidated JWT `dest` claim as the OAuth host, sending the app's `client_secret` to an attacker-controlled domain - (File: lib/shopify_api/auth/token_exchange.rb)

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` derives the shop/host it will send the app's `client_id`/`client_secret` to directly from the JWT's `dest` claim, without ever validating that this value is a trusted `*.myshopify.com`/`*.myshopify.io`/`*.spin.dev`/`*.shop.dev` domain. This breaks the identity binding that every other credential-issuing OAuth call in this gem enforces: `shop_used_as_request_host == shop_validated_as_trusted_shopify_domain`.

### Finding Description
`JwtPayload` decodes the JWT with the app's own secret and checks only that `aud == Context.api_key` [1](#0-0) . It performs no validation of `dest`/`iss` against Shopify's trusted domain list; `shop` is simply `@dest.gsub("https://", "")` [2](#0-1) .

`TokenExchange.exchange_token` takes this unvalidated `dest_shop` and uses it directly to build the `Session` that becomes the request host:
```
jwt_payload = ShopifyAPI::Auth::JwtPayload.new(session_token)
dest_shop = jwt_payload.shop
...
shop_session = ShopifyAPI::Auth::Session.new(shop: dest_shop)
...
client = Clients::HttpClient.new(session: shop_session, base_path: "/admin/oauth")
``` [3](#0-2) 

`Clients::HttpClient#initialize` builds the outbound request URI straight from `session.shop`: `@base_uri = "https://#{api_host || session.shop}"` [4](#0-3) . The subsequent POST to `#{base_uri}/admin/oauth/access_token` carries `client_id` and `client_secret` in the body [5](#0-4) .

By contrast, the two sibling credential-exchange flows in the same module and elsewhere in the gem explicitly sanitize the `shop` before using it as the request host:
- `TokenExchange.migrate_to_expiring_token` calls `Utils::ShopValidator.sanitize!(shop)` before building the session/host [6](#0-5) .
- `RefreshToken.refresh_access_token` likewise calls `Utils::ShopValidator.sanitize!(shop)` [7](#0-6) .
- `ShopValidator` exists specifically to enforce that a shop string resolves to one of `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`) and raises `Errors::InvalidShopError` otherwise [8](#0-7) [9](#0-8) .

`exchange_token` is the one path in this trio that skips this check entirely — it only verifies the JWT signature/audience, not that the *value used as the network destination* is a legitimate Shopify host. This is exactly the AssetManager bug-class analog: a field that is authenticated for one purpose (JWT audience/signature integrity) is silently reused, unchecked, for a *different* security-sensitive purpose (selecting the host that receives the client secret), because the code that would normally enforce that binding (`ShopValidator.sanitize!`) is not invoked on this path.

### Impact Explanation
If an attacker can get an app to process a session token whose `dest` claim points to a non-Shopify host (the JWT is still validly signed by the app's own `api_secret_key` — this can occur wherever the host application passes through an externally supplied token string to `exchange_token`, e.g. tokens forwarded from a customized App Bridge integration or a token replayed from a different, attacker-controlled app configuration that shares the same client credentials in a multi-environment setup), the gem will issue an HTTPS POST containing the merchant app's `client_id` and `client_secret` to that attacker-chosen host. This is SSRF carrying the app's credentials to an arbitrary destination, matching the High-severity criteria (SSRF with the app's credentials / credential leakage).

### Likelihood Explanation
Exploitability depends on the host application handing `exchange_token` a session token whose `dest` was not otherwise pre-validated against a Shopify domain — the gem's own public API contract for `exchange_token` accepts a raw token string and performs no domain check, unlike its sibling `migrate_to_expiring_token`/`refresh_access_token`. Given the JWT is signed with the app's own secret, obtaining a validly-signed token with an arbitrary `dest` requires some other primitive (e.g., an app that also embeds an id-token minting/relaying flow, or reuse/misissue of tokens across environments sharing a secret) — this is not a network-reachable, unauthenticated exploit against `shopify_api` in isolation, so likelihood is more limited than a straightforward host-header analog, but the root-cause gap (no `ShopValidator` check compared to sibling methods) is concrete and verifiable in code.

### Recommendation
In `TokenExchange.exchange_token`, validate `dest_shop` through `Utils::ShopValidator.sanitize!` (as already done in `migrate_to_expiring_token` and `refresh_access_token`) before constructing `shop_session`/`Clients::HttpClient`, so the host used for the credential-bearing `access_token` request is always constrained to `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`.

### Proof of Concept
1. Obtain (or coerce the host app into passing) a session token whose payload has `aud` equal to the app's configured `api_key` and `dest` set to `https://attacker.example.com`, signed with the app's `api_secret_key` (e.g., via a shared-secret misconfiguration or a token-minting path elsewhere in the deployment).
2. Call `ShopifyAPI::Auth::TokenExchange.exchange_token(session_token: token, requested_token_type: ...)`.
3. `JwtPayload.new` accepts the token because signature and `aud` check pass [1](#0-0) ; `dest_shop` becomes `attacker.example.com`.
4. `Clients::HttpClient` builds `@base_uri = "https://attacker.example.com"` and POSTs the OAuth body — including `client_id` and `client_secret` — to `https://attacker.example.com/admin/oauth/access_token` [4](#0-3) [10](#0-9) , exfiltrating the app's `client_secret` to the attacker's server.
