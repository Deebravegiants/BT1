### Title
Missing access control on `Bonding.initializeBounceGlobalStorage()` lets an attacker permanently hijack the LT-registry gate on legacy proxy upgrades - (File: `packages/contracts/src/Bonding.sol`)

### Summary
`Bonding.initializeBounceGlobalStorage()` is guarded only by `reinitializer(2)` and a "not already set" check — it has no `onlyOwner` (or any caller restriction) at all [1](#0-0) . This is the same bug class as the external report's `CollateralManager.setCollateralEscrowBeacon()`: a privileged one-shot setter that anyone can call.

### Finding Description
`bounceGlobalStorage` is the pointer `Bonding.launch()` uses to resolve the trusted `IBounceFactory` and validate that an LT is genuine via `ltExists()` — the code comment explicitly states this check exists because "`Zap.createToken` is permissionless; without this gate a fake LT could siphon USDC inside `mint`" [2](#0-1) .

For proxies deployed before this storage slot existed, the natspec states the function is meant to be "invoked atomically via `upgradeToAndCall`" by the owner, and the `address(0)` guard is described as closing "the reinitializer-front-run window on fresh proxies that haven't been initialised yet" [1](#0-0) . However, the function itself carries no `onlyOwner`/role check — it is `external` with only the `reinitializer(2)` modifier gating a one-time call, and an `InvalidInput` check that only blocks a *second* call once `bounceGlobalStorage` is non-zero. If the owner upgrades a legacy proxy via a plain `upgradeTo` (rather than the intended atomic `upgradeToAndCall`), there is a window in which `$.bounceGlobalStorage` is still `address(0)` and any unrelated wallet can call `initializeBounceGlobalStorage(maliciousContract)` first, permanently locking in an attacker-controlled `IBounceGlobalStorage`.

### Impact Explanation
Once `bounceGlobalStorage` points at an attacker-controlled contract, `Bonding.launch()`'s `IBounceFactory($.bounceGlobalStorage.factory()).ltExists(params.ltAddress)` check can be made to always return `true` [3](#0-2) . This defeats exactly the protection the natspec describes: any address, including a malicious "LT" contract that lies about `exchangeRate()`/`mint`/`redeem`, can now be used to launch a token through `Zap.createToken`, letting the attacker siphon the USDC that `Zap` `forceApprove`s into the fake LT's `mint`. Because the reinitializer can only fire once, the corruption is permanent for that proxy short of another UUPS upgrade.

### Likelihood Explanation
This requires the specific operational sequence of the owner performing a non-atomic upgrade on a legacy Bonding proxy (one that pre-dates the `bounceGlobalStorage` slot). It is not reachable on freshly-deployed proxies, since `initialize()` already sets `bounceGlobalStorage` to a non-zero value, permanently blocking `initializeBounceGlobalStorage` via the `InvalidInput` guard [4](#0-3) . The likelihood is therefore contingent on a legacy-migration path existing and the owner not using `upgradeToAndCall`, but the missing access-control is a real code-level defect independent of that operational assumption — any transaction submitted by an unprivileged address in that window succeeds.

### Recommendation
Add `onlyOwner` to `initializeBounceGlobalStorage()`, matching the pattern already used on `setBounceGlobalStorage()` [5](#0-4) , so that only the protocol multisig can complete the backfill, closing the front-run window regardless of whether the upgrade is atomic.

### Proof of Concept
1. Assume a legacy `Bonding` proxy exists at version 1 (initialized before the `bounceGlobalStorage` field/slot existed), so `$.bounceGlobalStorage == address(0)`.
2. Owner calls `upgradeTo(newImpl)` (non-atomic — no `data` payload) to add the `initializeBounceGlobalStorage` capability.
3. Before the owner's follow-up transaction lands, an attacker submits `bonding.initializeBounceGlobalStorage(maliciousGlobalStorage)` directly — no modifier prevents this since the only guard is `reinitializer(2)` and the zero-check on `$.bounceGlobalStorage` [6](#0-5) .
4. `$.bounceGlobalStorage` is now permanently set to `maliciousGlobalStorage`; the owner's own follow-up call reverts with `InvalidInput`.
5. Attacker's `maliciousGlobalStorage.factory()` returns a factory whose `ltExists()` always returns `true`, so `Bonding.launch()`'s fake-LT gate is defeated [2](#0-1) , and any subsequent `Zap.createToken` call using a malicious LT contract can siphon USDC during `mint`.

    /// @notice Backfill `bounceGlobalStorage` on a proxy deployed before this
    ///         slot existed. Invoked atomically via `upgradeToAndCall`. The
    ///         `address(0)` guard closes the reinitializer-front-run window on
    ///         fresh proxies that haven't been initialised yet.
    function initializeBounceGlobalStorage(
        address bounceGlobalStorage_
    ) external reinitializer(2) {
        if (bounceGlobalStorage_ == address(0)) revert ZeroAddress();
        BondingStorage storage $ = _s();
        if (address($.bounceGlobalStorage) != address(0)) revert InvalidInput();
        $.bounceGlobalStorage = IBounceGlobalStorage(bounceGlobalStorage_);
        emit BounceGlobalStorageUpdated(address(0), bounceGlobalStorage_);
    }
