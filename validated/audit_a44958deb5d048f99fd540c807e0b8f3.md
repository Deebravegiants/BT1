### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) headers are trusted for tenant routing without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC of the **raw body**. The `shop`, `topic`, `webhook_id`, and `api_version` values used to route and process the webhook come from separate HTTP headers that are never covered by that signature. An attacker who can obtain any one valid `(raw_body, hmac)` pair for the app (e.g. by triggering a webhook for their own shop) can replay that exact body/HMAC pair to the app's public webhook endpoint while freely rewriting the `shop-domain` header to any victim shop. The signature still validates, and the forged shop value is handed straight to the app's handler as authenticated data.

### Finding Description
`Registry.process` only checks body integrity: [1](#0-0) 

`HmacValidator.validate` calls `verifiable_query.to_signable_string`, and for webhook requests that method returns only the raw body: [2](#0-1) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors all read from HTTP headers that are completely outside the signed payload: [3](#0-2) 

`process` then forwards this unauthenticated `shop` value directly into `WebhookMetadata`, which the app's handler uses to decide which tenant's data to update: [4](#0-3) 

The identity binding that is broken is:

`shop authenticated by HMAC` ≠ `shop used by the handler to select the tenant`

Because the HMAC only proves "this body was signed with the app's secret," not "this body belongs to shop X," any request carrying a previously-observed valid `(body, hmac)` pair passes `Utils::HmacValidator.validate` regardless of what `shop-domain`/`topic`/`webhook-id` headers accompany it. This directly matches the report's abstract bug class: "a field acted on but not covered by the HMAC" (analogous to Homora's mismatch between the token whitelisted-for-borrow check and the token used for the actual repay operation — a control on one field is used to gate a decision made about a different, unguarded field).

### Impact Explanation
This is a cross-tenant confusion vector: an attacker can cause the app to process a genuine, validly-signed webhook body as if it belonged to an arbitrary victim shop, since the shop identity used for routing/processing is not cryptographically bound to the signed content. Depending on how the host application's webhook handler uses `WebhookMetadata#shop` (e.g., looking up the tenant's session/access token by that shop string, updating that tenant's local records, or triggering an action attributed to that tenant), this can lead to cross-tenant data corruption or an app performing actions against the wrong merchant's data/session — a cross-tenant access impact.

### Likelihood Explanation
The attacker needs at least one legitimate `(raw_body, hmac)` pair from the target app (trivially obtainable by installing the app on any shop the attacker controls, or from a public webhook example if the app logs deliveries) and the app's public webhook URL. No access token, `client_secret`, or privileged account is required — this is exploitable by any unprivileged internet user who can install the target app on a shop they control and observe one webhook delivery, then replay it with a forged `shop-domain` header directly to the app's endpoint.

### Recommendation
Bind the tenant identity to the signed payload instead of trusting a header that sits outside the HMAC:
- Include `shop`, `topic`, and `webhook_id` in the signable string used for HMAC validation (mirroring how `AuthQuery#to_signable_string` binds all OAuth-relevant fields), or
- Require host applications to cross-check the `shop` header against the shop embedded in the parsed JSON body (most Shopify webhook payloads include the resource but not always the shop, so this needs verification per topic), or
- At minimum, document prominently that `WebhookMetadata#shop`/`topic`/`webhook_id` are **not** authenticated by `HmacValidator.validate` and must not be used as the sole tenant-selection key without an additional binding (e.g. verifying the shop has an active, matching session/webhook registration for that specific delivery).

### Proof of Concept
1. Attacker installs the target Shopify app on their own dev store `attacker.myshopify.com` and triggers any webhook topic the app subscribes to (e.g. `products/update`). They capture the raw request body `B` and the `x-shopify-hmac-sha256` header value `H` sent by Shopify to the app's public webhook endpoint (via a proxy/logging tool on their own server, or via Shopify's webhook delivery logs).
2. Attacker crafts a new HTTP POST to the same app webhook endpoint using the exact same body `B` and header `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. Server-side, `ShopifyAPI::Webhooks::Request.new` parses headers/body; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `HMAC(B, client_secret) == H`, per `to_signable_string` returning only `@raw_body`.
4. The handler receives `WebhookMetadata` with `shop == "victim.myshopify.com"` even though the payload actually originated from, and was signed for, the attacker's own shop — demonstrating the forged tenant binding.

        sig { params(request: Request).void }
        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
