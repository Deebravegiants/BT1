## Title
Incorrect decimal scaling in HyperFungibleToken cross-chain amount conversion causes unbacked minting / fund loss - (`modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
The `hyper-fungible-token` pallet converts token amounts between the local Substrate asset's decimals and the remote ERC20's decimals using `convert_to_balance` and `convert_to_erc20`. Both helpers compute the scaling exponent with `erc_decimals.saturating_sub(local_decimals)`, which silently becomes `0` whenever `local_decimals > erc_decimals`. In that case no scaling at all is applied in either direction, even though the correct behavior requires scaling in the *opposite* direction (multiply instead of divide, or vice versa). This is the exact "decimals not checked/handled" bug class from the referenced Gearbox report, but here it corrupts amounts moved across the bridge instead of a price feed.

### Finding Description [1](#0-0) 

```rust
pub fn convert_to_balance<B: core::str::FromStr>(
    value: U256, erc_decimals: u8, local_decimals: u8,
) -> Result<B, B::Err> {
    let dec_str = (value /
        U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
    .to_string();
    dec_str.parse::<B>()
}

pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
    U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
```

Both functions only handle the case `erc_decimals >= local_decimals` correctly (dividing/multiplying by `10^(erc_decimals - local_decimals)`). When `erc_decimals < local_decimals` (e.g. bridging a native asset with 18 decimals against a remote ERC20 with 6 decimals — a completely ordinary, non-malicious configuration), `saturating_sub` returns `0`, so the scale factor becomes `10^0 = 1` and **no conversion happens at all**, in either function.

These helpers are used on both the outbound and inbound paths:
- Outbound `send`: [2](#0-1) 
- Inbound `on_accept` (mint/transfer to beneficiary): [3](#0-2) 
- Inbound `on_timeout` (refund): [4](#0-3) 

`send` is a permissionless, signed extrinsic reachable by any user: [5](#0-4) 

### Impact Explanation
When a token pair is registered with `local_decimals > erc_decimals` (a normal configuration, not an admin error — e.g. native currency at 18 decimals bridged to a 6-decimal ERC20):

- On `send`, `convert_to_erc20(amount, erc_decimals, local_decimals)` fails to divide down by `10^(local_decimals - erc_decimals)`. The full unscaled `amount` (in 18-decimal units) is embedded as the ERC20 `amount` in the dispatched message. The destination `HyperFungibleToken` contract mints that raw number of base units of its 6-decimal ERC20 — i.e. `10^(local_decimals - erc_decimals)` (e.g. `1e12`) times the tokens actually escrowed on the source chain. This is an **unbacked mint**: a user escrows a small amount and mints a vastly larger balance on the destination chain.
- Conversely, on `on_accept`/`on_timeout`, the same bug applied to an inbound flow (where the source's erc_decimals < destination local_decimals) causes the recipient to be credited `10^(local_decimals - erc_decimals)` times *less* than intended — a **permanent loss/freezing of funds** for the bridging user, since the correct amount was burned/escrowed on the source but only a negligible fraction is minted/released on the destination.

Both outcomes are Critical: one directly creates unbacked value out of thin air, draining the bridge's backing guarantee; the other permanently strands user funds.

### Likelihood Explanation
This does not require any malicious admin or governance action — it triggers under a legitimate, expected configuration where the remote ERC20's decimals differ from (are lower than) the local asset's decimals, which is common (e.g. 18-decimal native asset vs. 6-decimal stablecoin-style ERC20). Any user can trigger it with a single `send` extrinsic once such a token pair is registered, or simply by using an existing route where this decimals relationship holds.

### Recommendation
Fix both helpers to scale in the correct direction regardless of which side has more decimals, e.g.:

```rust
pub fn convert_to_balance<B: core::str::FromStr>(value: U256, erc_decimals: u8, local_decimals: u8) -> Result<B, B::Err> {
    let dec_str = if erc_decimals >= local_decimals {
        (value / U256::from(10u128.pow((erc_decimals - local_decimals) as u32))).to_string()
    } else {
        (value * U256::from(10u128.pow((local_decimals - erc_decimals) as u32))).to_string()
    };
    dec_str.parse::<B>()
}

pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
    if erc_decimals >= local_decimals {
        U256::from(value) * U256::from(10u128.pow((erc_decimals - local_decimals) as u32))
    } else {
        U256::from(value) / U256::from(10u128.pow((local_decimals - erc_decimals) as u32))
    }
}
```
Add unit tests covering both directions of the decimals relationship (`erc_decimals > local_decimals` and `erc_decimals < local_decimals`) to prevent regression.

### Proof of Concept
1. Governance registers a token pair via `register_token`/`update_token` where the local native asset has `T::Decimals = 18` and the remote chain's `Precisions` entry (`erc_decimals`) is `6` — a realistic pairing.
2. A user calls `send` with `amount = 1_000_000_000_000_000_000` (1 whole token, 18 decimals). The pallet escrows exactly 1 token natively: [6](#0-5) 
3. `convert_to_erc20(1e18, erc_decimals=6, local_decimals=18)` computes `10u128.pow(6u8.saturating_sub(18) as u32) = 10u128.pow(0) = 1`, so `erc20_amount = 1e18` (unscaled): [7](#0-6) 
4. The dispatched `Message.amount` field carries `1e18`. The destination `HyperFungibleToken` contract (6-decimal ERC20) mints `1e18` raw base units to the recipient — equivalent to `1,000,000,000,000` (one trillion) whole tokens — for an escrow that only backs 1 whole native token, confirming the unbacked-mint impact.
