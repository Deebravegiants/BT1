### Title
Stale cached oracle prices remain authoritative across a `flash_position` governance callback - (File: contracts/controller/src/strategies/flash_position.rs)

### Summary

`flash_position` prefetches every account, debt, and collateral price into an invocation-local `Context`, then mints debt and calls the attacker-selected receiver before final solvency checks. That receiver can execute a ready governance operation against the price aggregator during the callback. Because `Context::fetch_prices` retains already cached feeds, the post-callback solvency check continues to use the pre-execution oracle configuration and price. A borrower can therefore open an undercollateralized position immediately after an oracle change has already been applied on-chain.

### Finding Description

`process_flash_position` builds `extra_assets`, calls `prefetch_strategy_prices`, and only then enters the guarded mint-and-callback window. [1](#0-0) 

The callback executes before collateral collection, deposits, and `strategy_finalize`. [2](#0-1) 

`prefetch_strategy_prices` loads all relevant token prices into `Context`. [3](#0-2)  `Context::fetch_prices` intentionally skips any asset already present in `token_prices`, so an aggregator configuration change during the callback does not refresh that feed. [4](#0-3) 

Governance permits anyone to execute a ready scheduled operation when `executor` is `None`, and `execute` invokes the scheduled target before deleting the operation. [5](#0-4)  Oracle configuration and tolerance operations are schedulable `AdminOperation` variants. [6](#0-5) 

The destructive state change also happens before the callback: `mint_and_forward` calls `borrow_into_controller`, verifies the measured receipt, and transfers the borrowed tokens to the receiver. [7](#0-6)  Finalization then evaluates the mutated account through `enforce_post_pool_solvency` using the same stale `Context`. [8](#0-7) 

### Impact Explanation

An attacker can withdraw real borrowed tokens while the account’s final health is evaluated under an obsolete price or oracle source. If the ready oracle operation materially lowers collateral value or raises debt value, the transaction leaves a debt position that is insolvent under the configuration now stored on-chain.

That converts a governance-approved oracle change into an undercollateralized borrow. The attacker keeps the borrowed assets; subsequent liquidation and bad-debt cleanup socialize any shortfall across suppliers, causing protocol insolvency or loss of user funds.

### Likelihood Explanation

Exploitation requires three conditions:

1. A governance oracle operation has already become `Ready` and remains within its execution window.
2. The operation materially changes the valuation of the chosen debt or collateral asset.
3. The attacker controls a Wasm flash-position receiver and enough collateral or an existing account to satisfy the stale-price check.

The attacker does not need a privileged role: `execute` accepts `executor = None`, and `flash_position` is available to the account owner for `account_id = 0` or an existing owned account. The callback is an intended external execution point, and no code invalidates the `Context` price cache after it returns.

### Recommendation

Treat oracle-affecting state as versioned input to the risk calculation.

- Store an aggregator configuration/version epoch in each fetched `PriceFeed` or `Context` entry.
- Re-check that epoch after every external callback and before `strategy_finalize`.
- Alternatively, refetch all valuation inputs after `invoke_receiver` and fail if the accepted feed’s configuration metadata changed.
- If Soroban exposes no suitable oracle epoch, add one to price-aggregator configuration writes and expose it through `fetch_prices`.
- Apply the same invalidation boundary to `multiply`, `swap_debt`, `swap_collateral`, `repay_debt_with_collateral`, and `migrate_from_blend` wherever prices or risk parameters are cached before router, receiver, or external-pool calls.

### Proof of Concept

Assume governance has a ready `ConfigureAssetOracle` operation that switches `COLLATERAL` to a feed reporting half the prior price.

1. Attacker deploys `AttackerReceiver` implementing `execute_flash_position`.
2. Attacker calls:

   ```text
   controller.flash_position(
       caller = attacker,
       account_id = 0,
       spoke_id = S,
       mode = Multiply,
       debt = (hub_id = H, asset = DEBT),
       amount = B,
       receiver = attacker_receiver,
       data = encoded_plan,
       collaterals = [((H, COLLATERAL), minimum)],
       refund_assets = []
   )
   ```

3. Before the callback, the controller caches the current `DEBT` and `COLLATERAL` prices via `prefetch_strategy_prices`.
4. Inside `execute_flash_position`, the receiver calls:

   ```text
   governance.execute(
       executor = None,
       target = price_aggregator,
       function = configure_asset_oracle,
       args = scheduled_args,
       predecessor = zero_hash,
       salt = scheduled_salt
   )
   ```

   Governance executes the ready operation and changes the oracle configuration.

5. The receiver transfers exactly `minimum` `COLLATERAL` back to the controller and returns.
6. `process_deposit` records the collateral, but `strategy_finalize` still uses the pre-callback cached `COLLATERAL` price. The stale valuation reports HF ≥ 1 even though the newly active oracle configuration values the position below 1.
7. The transaction commits. The attacker has received `B` units of `DEBT`, while the new account is already undercollateralized. A later liquidation cannot recover the full debt, leaving the deficit to suppliers.

    pub(crate) fn fetch_prices(&mut self, assets: &Vec<Address>) {
