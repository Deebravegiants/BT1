### Title
Malformed relay-chain storage proof silently drops parachain header updates instead of failing verification - ([File: modules/ismp/state-machines/substrate/src/lib.rs])

### Summary
`read_proof_check_for_parachain` — used by `ParachainConsensusClient::verify_consensus` to extract sibling-parachain headers from a relay-chain storage proof — treats a `sp_state_machine::TrieError::IncompleteDatabase` for an individual key as "skip this key" (`continue`) rather than failing the whole proof, mirroring the nilfs2 pattern of silently mis-treating a failed read as if the entry were simply absent/empty instead of rejecting the operation.

### Finding Description
`read_proof_check_for_parachain` iterates the requested keys against a `TrieDB` built from the relayer-supplied `storage_proof` nodes: [1](#0-0) 

Only the trie root's presence is checked up front (`db.contains(root, EMPTY_PREFIX)`); it does not verify that every requested key resolves with a complete, valid node path. When `trie.get(raw_key)` returns `Err(TrieError::IncompleteDatabase(_))` — which happens whenever the supplied proof omits internal nodes needed to reach a given leaf — the function does `continue`, leaving that key entirely out of the returned `BTreeMap`, and returns `Ok(result)` for the batch as a whole.

This function is the sole extraction path used by the parachain consensus client to read every registered sibling parachain's header from a single relay-chain proof: [2](#0-1) 

Because a relayer fully controls the raw `storage_proof: Vec<Vec<u8>>` nodes in `ParachainConsensusProof` (decoded straight from the submitted proof bytes), they can construct a proof that is valid for the trie root and complete for most parachain keys, but deliberately missing the intermediate nodes on the path to one specific parachain's `Heads` entry. `trie.get()` for that key then fails with `IncompleteDatabase`, the loop `continue`s, that key is dropped from `headers`, and the subsequent `let Some(header) = header else { continue };` in `verify_consensus` treats the missing entry exactly like "no update" — `verify_consensus` still returns `Ok(..)` for the rest of the batch. There is no error, no partial-failure signal, and no distinction between "this parachain genuinely has no update this round" and "the prover intentionally starved this key's proof path."

This is the direct analog of the nilfs2 bug class: on a failed/incomplete read of one entry in a loop, the code silently proceeds as if that entry were empty/absent instead of failing the whole operation, letting an attacker manufacture the "empty" outcome for an entry that is not actually empty.

### Impact Explanation
Any relayer submitting a `ParachainConsensusClient::verify_consensus` proof can selectively and repeatedly suppress the state-commitment update for a targeted sibling parachain (i.e., a specific ISMP state machine), while all other parachains' updates go through normally and the call still succeeds. This lets an unprivileged relayer permanently stall `StateMachineHeight` progression for a chosen destination state machine — the exact "route unable to deliver messages" condition called out as in-scope impact, since ISMP messages destined for or requiring proofs against that state machine's state commitments can never be finalized as long as the attacker keeps supplying incomplete proofs for that key. It does not require compromising governance, a collator, or the network — it is achievable from a single relayed consensus-update transaction.

### Likelihood Explanation
High. Constructing a Merkle/Patricia trie proof that is valid for the checked root but incomplete along the path to one specific key is a standard, well-understood technique (simply omit intermediate proof nodes for that path) and requires no special access — any account able to submit the parachain consensus update extrinsic can do it repeatedly, at will, for any single target parachain key.

### Recommendation
In `read_proof_check_for_parachain`, treat `TrieError::IncompleteDatabase` the same as any other trie error — return `Err(...)` and reject the whole proof — rather than `continue`. If a "best-effort" mode is genuinely required elsewhere, it must never be used for the set of `Parachains::<T>::iter_keys()` driving consensus updates; the batch should be all-or-nothing so a proof cannot be crafted to exclude an arbitrarily chosen key while still validating for the rest.

### Proof of Concept
1. Attacker enumerates the registered parachain IDs via `Parachains::<T>::iter_keys()` (public storage) and picks a target `para_id` whose `Heads` update they want to suppress.
2. Attacker builds a legitimate relay-chain storage proof for the current block that includes complete trie nodes for every other parachain's `Heads` key, but deliberately strips the internal nodes needed to resolve the target `para_id`'s key (keeping only enough nodes so `db.contains(root, EMPTY_PREFIX)` succeeds).
3. Attacker submits this as `ParachainConsensusProof.storage_proof` via the normal consensus-update path invoking `ParachainConsensusClient::verify_consensus`.
4. `read_proof_check_for_parachain` returns `Ok` with the target key absent from `headers` (via the `IncompleteDatabase` → `continue` branch); `verify_consensus` returns `Ok((state, intermediates))` without an entry for the target parachain's `StateMachineId`.
5. Repeating this on every consensus update indefinitely prevents any new `StateCommitmentHeight` from ever being recorded for the targeted parachain, blocking all ISMP membership/non-membership proofs (and thus message delivery/timeouts) that depend on its state commitments.
