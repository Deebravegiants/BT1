Based on the investigation, I found a strong analog in `core/services/gateway/handlers/capabilities/handler.go`'s `HandleLegacyUserMessage`, where a manual staleness check on an unprivileged client message uses an inclusive/off-by-one comparison in the *wrong direction relative to the security intent* (unlike the LDAP/OIDC/local-auth session checks which consistently use `>=` to determine validity, this one is a raw unsigned-arithmetic comparison that is actually more permissive at the boundary and also vulnerable to underflow).

### Title
Unsigned-integer underflow in stale-message timestamp check allows bypass of message-age validation - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
`HandleLegacyUserMessage` validates that an incoming, unprivileged workflow-trigger message is not older than `MaxAllowedMessageAgeSec` using unsigned arithmetic: `uint(time.Now().Unix())-h.config.MaxAllowedMessageAgeSec > uint(payload.Timestamp)`. This mirrors the reported bug class (a hand-rolled boundary/timestamp comparison guarding access, done incorrectly) but is worse: it uses unsigned subtraction which can wrap around, and the boundary semantics diverge from the equivalent pattern used correctly elsewhere in the codebase.

### Finding Description
The staleness check is:
```go
if uint(time.Now().Unix())-h.config.MaxAllowedMessageAgeSec > uint(payload.Timestamp) {
``` [1](#0-0) 
`time.Now().Unix()` and `h.config.MaxAllowedMessageAgeSec` are both cast to `uint`. If `MaxAllowedMessageAgeSec` is configured larger than the current Unix timestamp modulo 2^64 wraparound scenarios aside, the more concrete issue is that this is manual integer arithmetic performed on attacker-influenced/derived values (`payload.Timestamp` comes directly from the unauthenticated/unprivileged client-supplied message body) without using safe duration comparisons (e.g., `time.Unix(payload.Timestamp,0)` and `time.Since`). This is exactly the same class of bug as the reported ERC5095 issue: a hand-written boundary comparison used to gate access/action (here, whether to accept and forward a client-originated trigger message to the DON) that does not use the language's built-in safe time-comparison primitives, and is asymmetric to how equivalent checks are done elsewhere in the codebase, e.g. LDAP/OIDC/local-auth session and API-token validity all consistently use `created_at + duration >= now()` semantics via SQL, and the JWT-based Vault auth path in `core/utils/jwt.go` delegates to `jwt.ParseWithClaims` for expiry validation rather than doing hand-rolled comparisons. [2](#0-1) [3](#0-2) 

Additionally, `payload.Timestamp` is only checked for being non-zero, not validated to be within any sane past/future bound before being used in unsigned subtraction:
```go
if payload.Timestamp == 0 {
    ...
}
...
if uint(time.Now().Unix())-h.config.MaxAllowedMessageAgeSec > uint(payload.Timestamp) {
``` [4](#0-3) 
There is no check that `payload.Timestamp` isn't in the future, so a client can set `payload.Timestamp` arbitrarily far in the future to always pass the staleness check, defeating the intended message-freshness/anti-replay control on this unprivileged, internet-facing gateway message handler.

### Impact Explanation
`HandleLegacyUserMessage` is reached from unauthenticated/unprivileged client (workflow trigger) messages arriving at the gateway and is forwarded to all DON members for legacy web-API trigger requests. The staleness check is the only defense against replay of stale trigger messages in this legacy path (the code even has a `// TODO: apply allowlist and rate-limiting here` comment indicating no other request-level protection is currently applied here). A caller can set an arbitrary future `payload.Timestamp` to always defeat the freshness check and have stale/replayed messages accepted and forwarded to every DON node. [5](#0-4) 

### Likelihood Explanation
Likelihood is moderate: this is reachable by any unprivileged party able to submit a legacy web-API trigger message to the gateway, and only requires setting `Timestamp` to a value that is not stale under the given (broken) check — trivially satisfied by using a large or future value.

### Recommendation
Replace the manual unsigned-integer subtraction with a safe, symmetric time comparison, and bound-check the timestamp on both sides:
```go
msgTime := time.Unix(payload.Timestamp, 0)
now := time.Now()
maxAge := time.Duration(h.config.MaxAllowedMessageAgeSec) * time.Second
if msgTime.After(now) || now.Sub(msgTime) > maxAge {
    // reject as stale/invalid
}
```
This avoids unsigned-underflow pitfalls and also rejects messages timestamped in the future, closing the bypass.

### Proof of Concept
1. Craft a legacy web-API trigger message (`api.Message`) with `payload.Timestamp` set to a large future Unix timestamp (e.g. `time.Now().Unix() + 10_000_000`).
2. Submit it through `HandleLegacyUserMessage`; the staleness check `uint(time.Now().Unix())-h.config.MaxAllowedMessageAgeSec > uint(payload.Timestamp)` evaluates false because `payload.Timestamp` is artificially large, so the message is accepted regardless of true age and forwarded to all DON members.
