### Title
Webhook `shop` identity is trusted from an unauthenticated header while only the raw body is HMAC-verified - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#shop` reads the tenant identity straight from the `X-Shopify-Shop-Domain` HTTP header, but `HmacValidator.validate` only verifies the raw request body (`to_signable_string` returns `@raw_body`), not the header. Any caller who can produce a request with a valid-looking HMAC for a chosen body (or replay/forge a request that a host app naively forwards) can freely set the `shop-domain` header to any value, and `Registry.process` will hand that attacker-controlled shop identity to the app's webhook handler as trusted tenant context.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
It returns only `@raw_body`. The `shop`, `topic`, and `webhook-id` values are pulled from headers instead: [2](#0-1) 
`Registry.process` validates the HMAC over that signable string (the body) and then immediately trusts `request.shop` as the tenant identity passed to the handler: [3](#0-2) 
`HmacValidator.validate`/`validate_signature` compute the HMAC purely over `verifiable_query.to_signable_string`: [4](#0-3) 

The binding that should hold is: `shop header == shop cryptographically bound inside the HMAC-covered payload`. Instead, the code only proves "the body bytes came from Shopify"; it never proves "the shop header describing which tenant sent this body came from Shopify." Because the body is JSON and the `shop_domain`/`shop_id` fields inside typical webhook payloads are not what `WebhookMetadata` uses for tenant identity — it's the header value returned by `Request#shop` — an app can be handed a body that is genuinely signed for Shop A's topic/payload but tagged in the header as belonging to Shop B. This is exactly the class of bug in the reference report: a field that is *acted upon* (the delegate/shop) is not the field that is *covered by the authenticity check* (the HMAC/mint gating), letting one identity be substituted for another after validation passes.

### Impact Explanation
If a host application uses `WebhookMetadata#shop` (as returned by this gem) to look up per-tenant state, credentials, or to route to per-merchant logic without independently re-validating the shop against something HMAC-bound, an attacker who can influence only the header (e.g., via a proxy misconfiguration, and more importantly via any legitimate previously-observed valid signed payload replayed with a swapped header) can make the library assert an incorrect tenant identity as authenticated. This crosses a tenant boundary (cross-tenant confusion), matching the Critical "cross-tenant access" impact category, since the gem itself provides no primitive that binds `shop` to the HMAC.

### Likelihood Explanation
Exploitability is bounded by how strictly Shopify's edge enforces header/body consistency and by whether the host app trusts `request.shop`/`WebhookMetadata#shop` for authorization decisions — that host behavior is outside this gem, so likelihood in isolation is moderate. However, the root cause — `to_signable_string` never including `shop` — is fully verifiable purely from this gem's code and is a design gap independent of any specific host app, which is what the report's rules ask to assess (documented API/library behavior, not host misuse).

### Recommendation
Include the `shop` (and ideally `topic`/`webhook-id`) header values in the string that is HMAC-verified, or otherwise cryptographically bind them to the payload before `Registry.process` treats `request.shop` as authenticated tenant identity.

### Proof of Concept
```ruby
raw_body = '{"id":1,"foo":"bar"}'
secret = ShopifyAPI::Context.api_secret_key
valid_hmac = Base64.strict_encode64(OpenSSL::HMAC.digest("sha256", secret, raw_body))

# HMAC is valid for the body regardless of which shop header is attached
request = ShopifyAPI::Webhooks::Request.new(
  raw_body: raw_body,
  headers: {
    "x-shopify-topic" => "orders/create",
    "x-shopify-hmac-sha256" => valid_hmac,
    "x-shopify-shop-domain" => "victim-shop.myshopify.com", # attacker-chosen, not covered by HMAC
  },
)

ShopifyAPI::Utils::HmacValidator.validate(request) # => true, even though "shop-domain" was never signed
```

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
