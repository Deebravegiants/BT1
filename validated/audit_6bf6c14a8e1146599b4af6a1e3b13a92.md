## Title
Webhook shop-domain (tenant identity) is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable content as only the raw request body, while the `shop` (tenant identity), `topic`, `webhook_id`, and `api_version` are all read directly from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then hands the handler a `WebhookMetadata` struct built from those header-derived, unsigned fields — including `shop`, which host applications use as the tenant key for any subsequent database/session lookups.

### Finding Description
The signable content for a webhook request is defined as just the body: [1](#0-0) 

But the shop identity, topic, and other metadata are pulled straight from headers with no cryptographic binding to that body: [2](#0-1) 

`Registry.process` validates the HMAC against the body only, then trusts `request.shop` (and `request.topic`) to build the metadata passed to the app's handler: [3](#0-2) 

This breaks the intended identity binding: `shop authenticated (by Shopify via HMAC) == shop the handler acts on`. Here, `HMAC-verified bytes (body) != bytes actually trusted for tenant attribution (shop-domain header)`. Any legitimate `(raw_body, hmac)` pair — for example one the attacker generates by installing the app on their own shop and triggering a webhook with a predictable/empty body such as `{}` — remains valid when replayed with a forged `x-shopify-shop-domain` header pointing at a victim shop, since the header is never part of `to_signable_string`.

### Impact Explanation
Because `WebhookMetadata#shop` is trusted by host applications as the tenant key for state changes (e.g. updating a shop's data, uninstall handling, compliance webhooks like `shop/redact`, `customers/redact`), an attacker who can obtain any valid `(body, hmac)` pair for their own app installation can replay it with an arbitrary victim `shop-domain` header. This lets an unprivileged party masquerade as a different shop and make the app perform tenant-scoped mutations attributed to that other shop — a cross-tenant access violation, without possessing the victim's access token, session, or the app's `client_secret`.

### Likelihood Explanation
The attacker only needs the ability to POST arbitrary bytes and headers to the app's public webhook endpoint (as documented, the endpoint forwards `request.headers.to_h` and `request.raw_post` straight into `ShopifyAPI::Webhooks::Request.new` — no gem-level restriction on origin). Obtaining a valid `(body, hmac)` pair is trivial for topics with fixed/empty bodies or by triggering webhooks on their own installed shop, since many webhook payloads are predictable or attacker-controlled through their own actions.

### Recommendation
Include the shop-domain (and ideally topic/api-version/webhook-id) in the HMAC-covered signable content, or otherwise cryptographically bind the header-derived shop value to the signed body (e.g., Shopify-recommended verification should validate the full raw body per-shop context, and the gem should not expose an unauthenticated `shop` accessor as trustworthy metadata separate from what was actually signed).

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com` and subscribe to a webhook topic with a fixed/empty body (e.g. one that sends `{}`).
2. Capture the legitimate `x-shopify-hmac-sha256` header Shopify sends for that request/body.
3. Replay the same raw body and HMAC header to the app's webhook endpoint, but set `x-shopify-shop-domain: victim.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` in `Registry.process` succeeds because it only checks the body against the HMAC.
5. `WebhookMetadata.new(... shop: request.shop ...)` is built with `shop = "victim.myshopify.com"`, and the app's handler performs tenant-scoped actions believing the event came from the victim shop.
