### Title
Webhook shop identity is not covered by the HMAC signature, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then trusts the `shop` (and `topic`/`webhook_id`) values taken from unsigned HTTP headers when building the `WebhookMetadata` passed to the app's handler. Because the app's `api_secret_key` is shared across every shop that has installed the app, any merchant who has the app installed can capture one of their own legitimately-signed webhooks and replay it to the app's public webhook endpoint with the `X-Shopify-Shop-Domain` header changed to point at a different, victim shop. The signature still validates because the shop identity was never part of the signed message, so the handler executes attacker-supplied body content under a spoofed victim `shop` value — this is directly analogous to the "field acted on but not covered by the HMAC" report class from the bounty prompt.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

`hmac`, `shop`, `topic`, `api_version`, and `webhook_id` are all read from HTTP headers that are not part of the signed string: [2](#0-1) 

`Utils::HmacValidator.validate` only checks that `hmac` matches `HMAC(secret, to_signable_string)`, i.e. `HMAC(secret, raw_body)`: [3](#0-2) 

`Registry.process` uses this same validation and then forwards the unauthenticated `request.shop` (and topic/webhook_id) straight into the data given to the app's handler: [4](#0-3) 

The library's own documentation instructs developers to trust `data.shop` as "The shop domain of the webhook" and use it directly to key application data (`shop_domain: data.shop`): [5](#0-4) 

The binding that should hold is: `shop domain claimed in the request == shop domain the HMAC signature was computed for`. In this implementation that equality is never enforced — the HMAC only proves "some shop that knows the app's `api_secret_key` produced this body," not "this specific shop domain produced this body." Since `api_secret_key` is one value shared by the app across all installed shops (not per-shop), any single existing merchant of the app can compute a fully valid HMAC over an arbitrary body (e.g., from their own real webhook deliveries) and then relabel the `shop-domain` header to any other merchant using the same app.

### Impact Explanation
This breaks the tenant isolation the gem is expected to provide: an unprivileged party (any merchant who has installed the app — no special access, tokens, or `client_secret` needed) can forge a webhook that the app will process as if it originated from a different shop. Depending on how the host app uses `data.shop`/`data.body` (as documented, e.g. keying jobs, orders, or records by shop domain), this enables cross-tenant data injection/corruption — a merchant can inject fabricated `orders/create`, `app/uninstalled`, or similar events attributed to a victim shop, using content of their choosing (since the body itself is fully attacker-controlled, only bound to the shared app secret rather than to their own shop). This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high for any real-world deployment: obtaining a validly signed webhook body requires nothing more than installing the target app on any shop (which is the normal, unprivileged way to become an app merchant) and observing one's own webhook traffic. No secrets, tokens, or elevated privileges belonging to another tenant are required — only changing one HTTP header on replay.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the signed material that `HmacValidator` verifies, or otherwise cryptographically tie the `shop-domain` header to the signature (e.g., include it in the computed digest, or require callers to independently verify that the `shop-domain` header corresponds to a shop with an active, previously-established session/installation before trusting it). At minimum, update `Webhooks::Request#to_signable_string` so the signature covers the shop domain, and update the documentation to stop presenting `data.shop` as trustworthy on its own.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a normal, unprivileged action for any Shopify merchant).
2. Shopify sends attacker a legitimate webhook, e.g. `orders/create`, with headers `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, and some JSON body.
3. Attacker replays this exact body and HMAC to the app's public webhook endpoint, but changes `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request#hmac`/`#to_signable_string` only look at the body and the (attacker-controlled) `hmac` header — `HmacValidator.validate` succeeds because the body/HMAC pair is genuinely valid for the shared `api_secret_key`. [6](#0-5) 
5. `Registry.process` calls the app's handler with `shop: "victim-shop.myshopify.com"` and the attacker-chosen body, even though this event never came from Shopify on behalf of that shop.
