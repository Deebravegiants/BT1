### Title
Escrow over-crediting in Tron `IntentGatewayV2.placeOrder` when input token is fee-on-transfer or non-reverting on shortfall - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2.placeOrder` credits escrow using the user-specified `order.inputs[i].amount` (via `reducedInputs[i].amount`) rather than the amount actually received by the gateway, unlike the hardened EVM mainnet implementation which measures balance-before/after around every `safeTransferFrom`.

### Finding Description
In the EVM implementation (`evm/src/apps/IntentGatewayV2.sol`, non-predispatch branch), the contract explicitly guards against fee-on-transfer / non-standard ERC20 behavior:

```solidity
uint256 balBefore = IERC20(token).balanceOf(address(this));
IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
order.inputs[i].amount = IERC20(token).balanceOf(address(this)) - balBefore;
``` [1](#0-0) 

`order.inputs[i].amount` is then mutated to the *actual* received amount before the protocol fee and commitment are computed, so escrow (`_orders[commitment][token]`) is always backed 1:1 by real token balance held by the gateway.

The Tron port (`evm/tron/contracts/apps/IntentGatewayV2.sol`) does not perform this balance check in its equivalent non-predispatch branch:

```solidity
} else {
    for (uint256 i; i < inputsLen;) {
        if (order.inputs[i].amount == 0) revert InvalidInput();
        address token = address(uint160(uint256(order.inputs[i].token)));
        if (token == address(0)) {
            if (msgValue < order.inputs[i].amount) revert InsufficientNativeToken();
            msgValue -= order.inputs[i].amount;
        } else {
            IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
        }

        // Store reduced amount (after protocol fees) in escrow
        _orders[commitment][token] += reducedInputs[i].amount;
        ...
    }
}
``` [2](#0-1) 

Here `reducedInputs[i].amount` is derived from `order.inputs[i].amount` — the user-declared amount — not from any measured balance delta. If the ERC20/TRC20 input token is fee-on-transfer, or is a non-standard token that silently transfers less than requested on an over-withdrawal/insufficient-balance condition instead of reverting (the exact bug class from the external report), the gateway will credit the escrow ledger `_orders[commitment][token]` for more tokens than it actually holds. This is the identical root cause as the cited Allo.sol `_fundPool` issue: trusting the nominal transfer amount instead of verifying the delta actually received.

This is directly reachable by any unprivileged user calling `placeOrder` with an attacker-chosen or non-standard input token — no privileged role is required.

### Impact Explanation
Because escrow accounting (`_orders[commitment][token]`) is the source of truth used later by `fillOrder`/redeem/cancel-refund paths to determine how much of the input token a solver or the original depositor can claim, over-crediting escrow relative to the gateway's real token balance creates a shortfall: once solvers fill and later withdraw/redeem escrowed inputs, the contract will run out of real tokens before all legitimate escrow claims are honored, permanently freezing funds for whichever order/claim is serviced last (insolvency across all orders sharing that token, not just the one placed with the deficient token). This matches the "Medium/High, permanent freezing of funds" acceptance criteria.

### Likelihood Explanation
Likelihood is Medium-to-High for the Tron deployment specifically: TRC20 tokens are not guaranteed to follow strict revert-on-insufficient-balance semantics, and fee-on-transfer tokens are common enough (as the project's own EVM test suite for the mainnet contract explicitly tests fee-on-transfer scenarios, showing the team is aware of this token class) that this is a foreseeable, easily triggerable condition purely by a user choosing to place an order with such a token as input — no colluding party or privileged action needed.

### Recommendation
Apply the same balance-delta pattern used in `evm/src/apps/IntentGatewayV2.sol` (lines 320-322) to the Tron contract's non-predispatch branch: snapshot `balanceOf(address(this))` before `safeTransferFrom`, compute actual received as the post-transfer delta, mutate `order.inputs[i].amount` to that value, and only then compute `reducedInputs`/protocol fee and credit `_orders[commitment][token]`. Ensure the predispatch branch (lines 387-449) — which does perform a dust-computed balance check but still credits `_orders[commitment][token] += reducedInputs[i].amount` derived from the pre-declared `order.inputs[i].amount` rather than the freshly measured balance — is updated identically so escrow can never exceed what the gateway actually custodies.

### Proof of Concept
1. Deployer/attacker registers or a user selects a TRC20 "FaultyToken" as an input asset for `placeOrder`, where `transferFrom` either applies a transfer fee or silently caps the transferred amount below the requested amount instead of reverting (as in the reference report's PoC).
2. User calls `placeOrder` with `order.inputs[0] = {token: FaultyToken, amount: 1000}`, having only 900 FaultyToken balance/allowance behavior that yields 900 actually transferred.
3. `IERC20(token).safeTransferFrom(msg.sender, address(this), 1000)` succeeds per the token's non-standard semantics but only moves 900 tokens to the gateway [3](#0-2) .
4. `_orders[commitment][token] += reducedInputs[i].amount` credits escrow based on the original 1000 (minus protocol fee), i.e. more than the 900 tokens actually held [4](#0-3) .
5. When a solver later fills the order and the gateway attempts to release/refund the escrowed input amount, the contract's real FaultyToken balance is insufficient to cover all outstanding escrow entries for that token, causing later legitimate claims to revert/fail — a permanent freeze of funds for those orders.
