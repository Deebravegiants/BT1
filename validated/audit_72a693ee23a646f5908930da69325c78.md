### Title
Stale per-owner votes on pending `MultisigTransaction`s are never invalidated when an owner is removed and later re-added, allowing resurrection of a prior approval without a fresh signature - (File: `aptos-move/framework/aptos-framework/sources/multisig_account.move`)

### Summary
`MultisigTransaction.votes` is a `SimpleMap<address, bool>` keyed purely by owner address [1](#0-0) . `update_owner_schema` (invoked by `add_owners`/`remove_owners`/`swap_owner(s)`) mutates only `MultisigAccount.owners`; it never touches the `votes` map of any pending `MultisigTransaction` [2](#0-1) . Approval counting (`num_approvals_and_rejections_internal`) simply iterates the **current** owners list and looks up each owner's vote in the transaction's `votes` map [3](#0-2) . This correctly *excludes* a removed owner's stale vote while they are absent from `owners` (as shown by `test_validate_transaction_should_not_consider_removed_owners` [4](#0-3) ), but if that same address is subsequently re-added as an owner, the old entry in `votes` is still present and is counted again automatically, without the owner casting a new vote.

### Finding Description
The bug class mirrors the reported issue: state tied to a per-entry record ("has this owner approved this transaction?") is not properly reset when the parent collection (the owner set) is mutated. In the original report, `fees_ratio` was wrongly reset on every currency addition; here the analogous invariant is broken in the opposite direction — a per-owner vote record that *should* be invalidated when that owner's membership is revoked is instead left dangling in storage and silently reactivated the moment the address becomes an owner again.

Concretely:
1. Owner `O` votes to approve pending transaction `T` via `vote_transanction`, which does `votes.add(owner_addr, approved)` [5](#0-4) .
2. `O` is removed via `remove_owners`/`swap_owner`. `T` still exists in `multisig_account_resource.transactions` (transactions are only deleted upon execution/rejection), and `T.votes` still contains `O -> true`, since `update_owner_schema` never prunes any transaction's `votes` map [6](#0-5) .
3. `O` (or the same address, e.g. reused key/rotating custodian) is later re-added as an owner via `add_owners`/`swap_owner`, which only appends to `owners` and validates uniqueness — it does not require or check any transaction-specific re-vote [7](#0-6) .
4. Any subsequent call to `num_approvals_and_rejections`/`can_be_executed` iterates the (now updated) `owners` vector, finds `O` is an owner again, looks up `T.votes` and finds the stale `true` entry, and counts it as a live approval — even though `O` never re-approved `T` after being re-instated [8](#0-7) .

This corrupts the custody accounting invariant that "the number of approvals for a k-of-n multisig transaction reflects the number of *currently authorized* owners who freshly signed off on it." A stale, resurrected vote can push a transaction over the `num_signatures_required` threshold and let it execute (e.g., a `TransferRef`/coin/FA withdrawal payload, an upgrade to a code object owned by the multisig, or another `remove_owner`/`rotate` action) without the required number of genuinely current approvals.

### Impact Explanation
Multisig accounts on Aptos are frequently used as resource accounts holding APT, fungible assets, or as the upgrade/ownership authority for code objects. If the approval threshold can be inflated by a stale vote that was never re-confirmed after an owner's membership was revoked and restored, an attacker who can influence the timing/sequence of owner churn (e.g., a compromised or since-rotated owner key that's later reinstated, or a workflow where the same owner address cycles through removal/re-addition for unrelated reasons) can cause a pending transaction to reach quorum and execute custody-affecting payloads (fund transfers, ownership/upgrade actions) with fewer genuinely fresh approvals than the configured `num_signatures_required`. This directly undermines the k-of-n custody guarantee that protects multisig-held value.

### Likelihood Explanation
This requires a specific but plausible sequence: an owner votes on a pending transaction, is removed, and is later re-added while that transaction is still pending (transactions can remain pending — only executed/rejected ones are deleted, and up to `MAX_PENDING_TRANSACTIONS = 20` can be queued [9](#0-8) ). Owner churn (swap_owner, rotation, temporary removal for key-rotation purposes) is a normal, expected multisig operation, so the preconditions are realistic in production multisig usage rather than requiring privileged/anomalous behavior beyond normal owner-management actions.

### Recommendation
When an owner is removed in `update_owner_schema`, iterate all pending `MultisigTransaction`s and remove that owner's entry from each `votes` map (or maintain a per-transaction "eligible voter snapshot"/generation counter that invalidates old votes on membership change), so that a re-added owner must cast a fresh vote before their approval counts again.

### Proof of Concept
1. Create a 2-of-3 multisig with owners `[O1, O2, O3]`.
2. `O1` creates transaction `T` (sequence number 1).
3. `O2` approves `T` (`votes = {O2: true}`); this alone is insufficient (needs 2).
4. Multisig executes `remove_owners([O2])` then `add_owners([O2])` (two ordinary owner-management transactions), restoring `owners = [O1, O2, O3]` — `T.votes` still contains `{O2: true}` throughout, untouched by `update_owner_schema`.
5. `O1` approves `T` (`votes = {O1: true, O2: true}`).
6. `can_be_executed(multisig, 1)` now returns true because `num_approvals_and_rejections_internal` counts both `O1` and `O2`'s votes — even though `O2` never re-approved `T` after being reinstated — and `T` executes. [3](#0-2)  shows the counting logic that has no notion of "vote must be cast after last re-addition," and [10](#0-9)  shows `update_owner_schema` never touches `transactions[*].votes`.

    inline fun num_approvals_and_rejections_internal(owners: &vector<address>, transaction: &MultisigTransaction): (u64, u64) {
        let num_approvals = 0;
        let num_rejections = 0;

        let votes = &transaction.votes;
        owners.for_each_ref(|owner| {
            if (simple_map::contains_key(votes, owner)) {
                if (*simple_map::borrow(votes, owner)) {
                    num_approvals += 1;
                } else {
                    num_rejections += 1;
                };
            }
        });

        (num_approvals, num_rejections)
    }

    inline fun num_approvals_and_rejections(multisig_account: address, sequence_number: u64): (u64, u64) {

    /// Add new owners, remove owners to remove, update signatures required.
    fun update_owner_schema(
        multisig_address: address,
        new_owners: vector<address>,
        owners_to_remove: vector<address>,
        optional_new_num_signatures_required: Option<u64>,
    ) {
        assert_multisig_account_exists(multisig_address);
        let multisig_account_ref_mut =
            borrow_global_mut<MultisigAccount>(multisig_address);
        // Verify no overlap between new owners and owners to remove.
        new_owners.for_each_ref(|new_owner_ref| {
            assert!(
                !vector::contains(&owners_to_remove, new_owner_ref),
                error::invalid_argument(EOWNERS_TO_REMOVE_NEW_OWNERS_OVERLAP)
            )
        });
        // If new owners provided, try to add them and emit an event.
        if (new_owners.length() > 0) {
            multisig_account_ref_mut.owners.append(new_owners);
            validate_owners(
                &multisig_account_ref_mut.owners,
                multisig_address
            );
            emit(AddOwners { multisig_account: multisig_address, owners_added: new_owners });
        };
        // If owners to remove provided, try to remove them.
        if (owners_to_remove.length() > 0) {
            let owners_ref_mut = &mut multisig_account_ref_mut.owners;
            let owners_removed = vector[];
            owners_to_remove.for_each_ref(|owner_to_remove_ref| {
                let (found, index) =
                    vector::index_of(owners_ref_mut, owner_to_remove_ref);
                if (found) {
                    vector::push_back(
                        &mut owners_removed,
                        vector::swap_remove(owners_ref_mut, index)
                    );
                }
            });
            // Only emit event if owner(s) actually removed.
            if (owners_removed.length() > 0) {
                emit(
                    RemoveOwners { multisig_account: multisig_address, owners_removed }
                );
            }
        };
