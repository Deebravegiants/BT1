Audit Report

## Title
Missing `return` after failed email-claim extraction lets the OIDC login flow continue and issue a valid authenticated session - (File: `core/sessions/oidcauth/oidc.go`)

## Summary
In `oidcAuthenticator.handleTokenExchange`, when the verified `id_token`'s `email` claim is missing or not a string, the handler logs the error and writes an HTTP 500 response via `c.String(...)` but does not `return`. Execution falls through to role mapping, an `oidc_sessions` INSERT, an audit-success log, session-cookie assignment, and a final `200 OK` JSON response.

## Finding Description
The code path is exactly as cited: [1](#0-0) 
There is no `return` statement after the `c.String(http.StatusInternalServerError, ...)` call, unlike every other error branch in the same function which does return (e.g. the state check, token exchange, id_token verification, claims parsing, and ID-claims-extraction branches immediately preceding it). Execution therefore falls through into role mapping via `IDClaimsToUserRole`, the `INSERT INTO oidc_sessions (...) VALUES ($1, $2, $3, now())` using `strings.ToLower(email)` (empty string, since the type assertion failed and `email` retains its zero value), the audit log call, `ginSession.Set(...)`/`ginSession.Save()`, and finally `c.JSON(http.StatusOK, ExchangeTokenResponse{Success: true})`. [2](#0-1) 

This breaks the fail-closed assumption of the handler: an internal error condition (missing/invalid email claim) is logged and a 500 status is written, but the response is not terminated, so a fully valid, cookie-backed session is still created and returned with `Success: true`. `AuthorizedUserWithSession` subsequently trusts the `user_email`/`user_role` columns from this row without further validation: [3](#0-2) 

No other authentication/authorization check downstream catches this — the session cookie set via `ginSession.Set(webauth.SessionIDKey, clSession.ID)` is indistinguishable from a normal successful login for all subsequent authenticated API calls.

## Impact Explanation
This falls into the "node API authentication or role bypass" impact category. A client whose OIDC/OAuth2 flow produces a validly-signed `id_token` lacking a string `email` claim (e.g., IdP configuration omitting `email` scope, non-verified accounts, service accounts, or claim manipulation permitted by a given IdP) still receives a functioning, cookie-authenticated Chainlink session with a role derived from group/role claims (up to `UserRoleAdmin` if the token happens to carry admin group claims), despite the handler having already signaled an internal error. This is a genuine violation of intended fail-closed behavior in `WebServer.OIDC` authentication, not a cosmetic bug — the HTTP response body still claims `Success: true` and a real session row is persisted and later trusted by `AuthorizedUserWithSession`.

## Likelihood Explanation
Reaching the code requires only completing the standard `/oidc-login` → provider → callback redirect flow against the operator's configured OIDC provider — no pre-existing node privileges are needed. However, triggering the specific defect requires an `id_token`, correctly signed by the configured `ProviderURL`, that omits (or type-mismatches) the `email` claim while still authenticating the user via the standard flow. This depends on the specific IdP's claim behavior/configuration rather than being freely triggerable against an arbitrary IdP by an anonymous outsider with no account — it is a real, code-level bug reachable in realistic (if not universal) IdP configurations, matching the CVE-2016-3085 "log-but-don't-return" bug class described.

## Recommendation
Add an explicit `return` immediately after the failed email-claim branch:
```go
email, ok := claims["email"].(string)
if !ok {
    oi.lggr.Errorf("Failed to get email from claims")
    c.String(http.StatusInternalServerError, "Failed to get email from claims")
    return
}
```
Additionally audit the two other non-returning error branches in the same function — the `oidc_sessions` INSERT failure at lines 257-260 — which has the identical missing-`return` defect and should also be fixed, since it currently allows a session to be created/cookie set even if the DB insert reportedly failed.

## Proof of Concept
1. Configure `WebServer.AuthenticationMethod = 'oidc'` with a valid OIDC provider.
2. Obtain a validly-signed `id_token` from that provider that includes the configured role-mapping group claim (e.g. `AdminClaim`) but omits the `email` claim, or returns it as a non-string type.
3. Complete the redirect flow (`/oidc-login` → provider → callback) and submit the resulting `code`/`state` to the token-exchange endpoint that invokes `handleTokenExchange`.
4. Observe: despite the HTTP 500 body written for the missing-email branch, the handler still returns `http.StatusOK` with `Success: true`, sets a session cookie, and inserts a row into `oidc_sessions` with the mapped role — confirmable via a Go handler-level unit test that stubs `claims` without an `email` key and asserts both that `c.String` was called with 500 AND that `c.JSON(http.StatusOK, ...)` is also invoked (proving the missing `return`), or via an integration test hitting the real route with a crafted OIDC provider mock.

func (oi *oidcAuthenticator) AuthorizedUserWithSession(ctx context.Context, sessionID string) (clsessions.User, error) {
	if len(sessionID) == 0 {
		return clsessions.User{}, errors.New("session ID cannot be empty")
	}
	var foundUser clsessions.User
	err := sqlutil.TransactDataSource(ctx, oi.ds, nil, func(tx sqlutil.DataSource) error {
		// Query the oidc_sessions table for given session ID, user role and email are saved after the id claims is provided and validated
		var foundSession struct {
			UserEmail string
			UserRole  clsessions.UserRole
			Valid     bool
		}
		if err := tx.GetContext(ctx, &foundSession,
			"SELECT user_email, user_role, created_at + $2 >= now() as valid FROM oidc_sessions WHERE id = $1",
			sessionID, oi.config.SessionTimeout().Duration(),
		); err != nil {
			if errors.Is(err, sql.ErrNoRows) {
				return clsessions.ErrUserSessionExpired
			}
			return err
		}
		if !foundSession.Valid {
			// Sessions expired, purge
			return clsessions.ErrUserSessionExpired
		}
		foundUser = clsessions.User{
			Email: foundSession.UserEmail,
			Role:  foundSession.UserRole,
		}
		return nil
