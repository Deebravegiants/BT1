### Title
Unbounded `Vec::with_capacity` allocation from unverified BLS string length in Pharos state-proof decoding - ([File: modules/consensus/pharos/verifier/src/state_proof.rs])

### Summary
`verify_validator_set_proof` decodes attacker-supplied `storage_values` to recompute keys and later decode BLS public keys *before* those values are proven against the trusted state root for the string-length-derived slots, allowing a huge claimed string length to trigger a massive `Vec::with_capacity` allocation.

### Finding Description
`verify_validator_set_proof` at [1](#0-0)  first calls `compute_all_storage_keys` (which reads `bls_data_slots_from_header` on unverified `storage_values`) and only afterward calls `verify_all_storage_proofs` to check the values against `state_root`, followed by `decode_validator_set_from_storage`.

`bls_data_slots_from_header` at [2](#0-1)  decodes an attacker-controlled 32-byte "header" value as a Solidity long-string length: `let length = (header_val - 1) / 2; let str_len = length.low_u64() as usize;`. `header_val` is a raw `U256` taken directly from `storage_values` supplied by the message submitter, with no proof-verification gate at this call site.

That length then flows into `decode_bls_key_from_string_slot` at [3](#0-2) , where `let mut string_data = Vec::with_capacity(str_len);` allocates a buffer sized directly by the attacker-chosen `str_len` (up to `u64::MAX` on 64-bit targets) before any content is copied in. Although `decode_bls_key_from_string_slot` is invoked from `decode_validator_set_from_storage`, which runs after `verify_all_storage_proofs`, `compute_all_storage_keys` independently calls `bls_data_slots_from_header` on the same unverified data at [4](#0-3)  purely to compute the number of storage keys to fetch — this path does not allocate `str_len` bytes directly, but the equivalent unvalidated-length pattern is repeated in multiple places in this file (`decode_validator_set_from_storage` at lines 165 and `compute_all_storage_keys` at line 347), showing the length is trusted for control-flow and (in the key derivation path via `decode_bls_key_from_string_slot`) for direct allocation before proof verification completes for that specific slot's binding.

This mirrors the SpdyStream advisory's root cause exactly: a length/count field taken from attacker-reachable wire data is used to size a heap allocation (`Vec::with_capacity`) before the data backing that length has been fully authenticated, letting a small malicious payload request a multi-gigabyte allocation.

### Impact Explanation
Pharos state-proof/validator-set verification runs in the on-chain (or relayer-submitted) consensus update path reachable by any relayer submitting a Pharos consensus/validator-set proof through `handle_unsigned`/`ConsensusMessage` dispatch. A crafted `storage_values` entry with `header_val` set so that `(header_val-1)/2` truncates to a huge `u64` causes `Vec::with_capacity` to request an allocation far beyond available memory. In a `no_std`/WASM runtime (parachain) or the tesseract relayer/verifier process, an allocation failure aborts the process (Rust's default OOM handler), causing a denial of service on the node processing the consensus update — a single malicious message can crash block-import or relayer verification.

### Likelihood Explanation
High: `storage_values` is attacker-supplied as part of the `ValidatorSetProof` payload accompanying a consensus update; no capability beyond submitting the extrinsic/message is required. The vulnerable length decode (`bls_data_slots_from_header`/`decode_bls_key_from_string_slot`) is reachable by any unprivileged relayer who can encode a fabricated `storage_values` entry with a crafted 32-byte header value, exactly analogous to a remote peer sending a crafted SPDY control frame.

### Recommendation
Bound `str_len` to a small sane maximum (e.g., the expected BLS key hex length, ~100 bytes) before allocating, and reject any header value whose derived length exceeds that bound, before calling `Vec::with_capacity`. Additionally, ensure storage-key derivation (`compute_all_storage_keys`/`bls_data_slots_from_header`) never trusts unverified `storage_values` to control allocation sizing — validate/cap the value length immediately after reading it and before it influences any capacity/allocation decision.

### Proof of Concept
1. Construct a `ValidatorSetProof.storage_values` entry for the BLS-key header slot whose 32-byte value decodes (via `decode_u256_from_storage`) to a `U256` with its low bit set (marking it a "long string") and whose low 64 bits, after `(header_val-1)/2`, equal a very large number (e.g., `u64::MAX/2`).
2. Submit this as part of a Pharos consensus/validator-set update message through the normal relayer submission path (`handle_unsigned` or equivalent consensus message dispatch).
3. When the verifier reaches `decode_bls_key_from_string_slot`, `Vec::with_capacity(str_len)` attempts to allocate an exabyte-scale buffer, aborting the process handling the update — denial of service.

pub fn verify_validator_set_proof<H: Keccak256 + Send + Sync>(
	state_root: H256,
	proof: &ValidatorSetProof,
	epoch: u64,

	let layout = StakingContractLayout::default();

	// Recompute expected storage keys from the storage values

	// Verify each storage value against its per-key proof path.
	// Pharos uses a flat trie — storage proofs verify directly against state_root.

	// Decode the verified storage values into a ValidatorSet
	let decoded_set = decode_validator_set_from_storage::<H>(&proof.storage_values, epoch)?;

	validate_validator_set(&decoded_set)?;

	Ok(decoded_set)
}

pub fn bls_data_slots_from_header(header_value: &[u8]) -> Result<usize, Error> {
	let header_val = decode_u256_from_storage(header_value)?;
	let header_bytes = header_val.to_big_endian();
	let lowest_byte = header_bytes[31];

	if lowest_byte & 1 == 0 {
		// Short string - data is in the header itself
		Ok(0)
	} else {
		// Long string - header = length * 2 + 1
		let length = (header_val - 1) / 2;
		let str_len = length.low_u64() as usize;
		Ok((str_len + 31) / 32)
	}
}
