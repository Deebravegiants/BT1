### Title
Direct LT transfers into `Bonding` for an already-`Graduated` token are permanently unrecoverable - ([File: packages/contracts/src/Bonding.sol])

### Summary
Analogous to the FantiumClaimingV1 issue — where an athlete's funds sent to a *closed* distribution can never be recovered because the only sweep/close path is gated on the *pre-closed* state — alt.fun's `Bonding.sol` only sweeps stray LT held by the contract while a token is in `Lifecycle.Graduating`. Once a token reaches the terminal `Lifecycle.Graduated` state, any LT that lands in `Bonding` (via a direct, unprivileged `IERC20.transfer`) has no code path back out: there is no owner-only or permissionless rescue/sweep function scoped to that state, mirroring the report's "funds sent after close are stuck forever" bug class.

### Finding Description
`Bonding.finalizeGraduation` is the only function in the contract that moves LT out of `Bonding` to a recipient other than the LP pair: [1](#0-0) 

It is gated by `if (info.lifecycle != Lifecycle.Graduating) revert NotGraduating();`, i.e. it can only run exactly once per token, while the token sits in the `Graduating` state between phase 1 (`_enterGraduating`) and phase 2. The actual sweep logic, `_sweepLTToOwner`, is `internal` and only ever invoked from inside `finalizeGraduation`: [2](#0-1) 

After `finalizeGraduation` runs, `info.lifecycle` is permanently set to `Lifecycle.Graduated` (line 1027) and can never transition back to `Graduating` or be re-entered — `triggerGraduation` explicitly reverts with `TokenNotTrading` for any lifecycle other than `Curve`: [3](#0-2) 

A grep of every function in `Bonding.sol` shows no owner-only or permissionless `rescue`/`recover`/`sweep`/`withdraw` entry point exists in this contract (unlike `FeeVault.sol`, which does have such functions). Consequently, if an LT holder mistakenly `transfer()`s LT directly to the `Bonding` contract address for a token that is already `Graduated` — the exact "sent to the closed distribution" scenario from the external report, just mapped onto alt.fun's terminal lifecycle state instead of a `closeDistribution` flag — those funds sit in `Bonding` with no function that can ever move them out. This is a direct, unprivileged ERC20 transfer into `Bonding`, explicitly one of the permitted analog reach vectors.

The protocol's own documentation acknowledges the underlying "stray LT in Bonding" hazard but only in the context of overlapping *in-flight* graduations, not the fully-terminal post-`Graduated` case: [4](#0-3) 

### Impact Explanation
Any LT sent directly to `Bonding` after a token's lifecycle has advanced to `Graduated` is permanently frozen — it can never be swept to the owner, returned to the sender, or otherwise recovered by any function in the contract. This is a permanent freezing of funds, identical in kind to the original report's core harm (an athlete's contribution becoming permanently unreachable once the target state is terminal).

### Likelihood Explanation
This requires an unprivileged actor (the LT holder themself, by mistake, or anyone else) to send LT directly to the `Bonding` contract's address for a token that has already graduated — a plausible fat-finger/confusion scenario given that `Bonding` is a well-known, publicly-known contract address that legitimately holds LT during the `Graduating` window. Since there is no time pressure or precise race condition needed (the terminal `Graduated` state persists forever), the window to trigger this is unbounded, but it still relies on user error rather than being triggerable purely programmatically by an attacker for profit — Medium likelihood.

### Recommendation
Add an owner-gated (or otherwise appropriately restricted) rescue function to `Bonding.sol` that can sweep any LT (or Token) balance held by the contract that is not currently earmarked by an in-flight `pendingGraduation` entry, regardless of the calling token's lifecycle state — i.e., decouple the sweep capability from the `Lifecycle.Graduating` gate that currently only lives inside `finalizeGraduation`. This mirrors the original recommendation of "don't let the state machine's terminal branch become an unrecoverable sink for misdirected funds."

### Proof of Concept
1. Launch and trade a token through its full lifecycle: `Bonding.launch` → buys via `Zap`/`Bonding.buy` until `canGraduate` is true → `_enterGraduating` fires → call `Bonding.finalizeGraduation(tokenAddress)`. `info.lifecycle` is now `Lifecycle.Graduated` permanently.
2. Any address, e.g. by mistake, calls `IERC20(lt).transfer(address(bonding), amount)` — a plain unprivileged ERC20 transfer, no special role required.
3. Attempt every state-changing path in `Bonding.sol` capable of moving LT out of the contract (`finalizeGraduation`, `triggerGraduation`, `buy`, `sell`): all of them revert for this token (`NotGraduating`, `TokenNotTrading`, or are simply not reachable for a `Graduated` token), and no `rescue`/`sweep`/`withdraw` function exists.
4. The transferred `amount` of LT is now permanently stranded in `Bonding` with zero code path to retrieve it — confirmed by the absence of any matching `rescue|recover|sweep|withdraw` function in `packages/contracts/src/Bonding.sol` (verified via repository-wide search, which found such functions only in `FeeVault.sol`).

    function finalizeGraduation(
        address tokenAddress
    ) external nonReentrant {
        BondingStorage storage $ = _s();
        TokenInfo storage info = $.tokenInfo[tokenAddress];
        if (info.lifecycle != Lifecycle.Graduating) revert NotGraduating();

        address lt = info.ltAddress;
        PendingGraduation memory p = $.pendingGraduation[tokenAddress];

        // Anything in this contract beyond `p.ltFromPair` belongs to a
        // concurrent graduation on the same LT (Phase 1 transferred it
        // via `Router.graduate`) or to stray dust. Either way it is
        // off-limits to this graduation's deposit and sweep — see
        // `_routerDepositAndDispose` and `_sweepLTToOwner`.
        // Saturating subtract: a balance below `p.ltFromPair` shouldn't
        // be reachable in normal operation, but we keep finalize from
        // bricking on a Panic if any future code path or non-canonical
        // LT briefly violates the invariant.
        uint256 ltBalance = IERC20(lt).balanceOf(address(this));
        uint256 protectedLT = ltBalance > p.ltFromPair ? ltBalance - p.ltFromPair : 0;

        address lpPair = _ensureUniswapV2Pair(tokenAddress, lt);
        uint256 liquidity = _seedUniswapV2Direct(tokenAddress, lt, lpPair, p.tokensForLP, p.ltFromPair, protectedLT);

        _sweepLTToOwner(lt, protectedLT);

**File:** packages/contracts/src/Bonding.sol (L1036-1051)
```text
    /// @dev Send LT held by this contract above `keep` to the owner,
    ///      emitting `LTRescued`. Called at the end of
    ///      `finalizeGraduation` with `keep = protectedLT` (any escrow
    ///      that doesn't belong to this graduation), so only THIS
    ///      graduation's rebalance residue lands on the owner. No-op on
    ///      the empty-pair fast path (nothing to sweep).
    function _sweepLTToOwner(
        address lt,
        uint256 keep
    ) internal {
        uint256 bal = IERC20(lt).balanceOf(address(this));
        if (bal <= keep) return;
        uint256 amount = bal - keep;
        address recipient = owner();
        IERC20(lt).safeTransfer(recipient, amount);
        emit LTRescued(lt, recipient, amount);
```

**File:** packages/contracts/AGENTS.md (L216-221)
```markdown
Two scenarios this guards against:

- **Concurrent graduations on the same LT.** Two tokens A and B share an LT and both reach `Lifecycle.Graduating` before either finalizes (the keeper takes ~60s and popular LTs see overlap). Without `protectedLT`, A's finalize would treat the full balance as its own and either sweep B's escrow to the owner (bricking B's later finalize) or — for hostile-pre-seed graduations — deposit it into A's locked LP. With it, A only ever sees `ltFromPair_A` and B is preserved.
- **Cross-token LT residue.** Old residue or a misdirected transfer sitting in `Bonding` would otherwise be visible to `_routerDepositAndDispose`'s `balanceOf(this)` read and could be silently consumed into a future graduation's locked LP. With `protectedLT`, contamination stays in `Bonding` and the deposit only sees this graduation's earmark.

The auto-sweep emits `LTRescued(lt, owner, amount)` for indexer observability. The dedicated regression tests for these edge cases were removed alongside `HostilePreSeed.t.sol`; future changes to `finalizeGraduation` / `_routerDepositAndDispose` / `_sweepLTToOwner` should add targeted coverage if the behaviour is non-obvious from the unit-level tests in `TwoPhaseGraduation.t.sol`.
```
