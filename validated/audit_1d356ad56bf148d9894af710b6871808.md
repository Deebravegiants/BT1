## Title
EvmHost's native-token dispatch path fails to refund unspent ETH after Uniswap swap, permanently trapping user overpayments - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` allow callers to pay relayer fees with native ETH by internally swapping `msg.value` for the exact fee-token amount needed via `IUniswapV2Router02.swapETHForExactTokens`. Uniswap V2's `swapETHForExactTokens` refunds unspent ETH to its immediate caller — but here the caller is `EvmHost` itself, not the original end user, since `EvmHost` calls the router on the user's behalf.

### Finding Description
In `EvmHost.dispatch(DispatchPost)`: [1](#0-0) 

the same pattern repeats in `dispatch(DispatchGet)`: [2](#0-1) 

and in `fundRequest()`: [3](#0-2) 

In each case, the entire `msg.value` is forwarded to the Uniswap V2 router with `address(this)` (the `EvmHost` contract) as the recipient. Uniswap V2's `swapETHForExactTokens` implementation only swaps the exact amount of ETH needed to produce `fee` output tokens, and refunds the leftover ETH to `msg.sender` of the router call — which is `EvmHost`, not the original transaction sender. None of these three functions capture the router's return value, track the actual ETH spent, or forward any leftover ETH back to `_msgSender()`/`payer`.

This is the exact bug class from the referenced report: partial spend during a swap (here, whenever `msg.value` exceeds the ETH cost of acquiring `fee` fee-tokens) leaves ETH stranded in the contract instead of being returned to the payer.

Contrast this with the codebase's own `IntentGatewayV2.placeOrder`, which performs the identical Uniswap fee-swap but explicitly refunds unspent value: [4](#0-3) 

`EvmHost` has no equivalent refund step after its swap calls.

### Impact Explanation
Any user calling `dispatch()` or `fundRequest()` with `msg.value` greater than the ETH cost of the requested fee amount (which is the normal case, since callers must overestimate ETH price to avoid reverts on slippage) permanently loses the difference — it accumulates inside `EvmHost` with no user-facing withdrawal mechanism, and no code path was found in `EvmHost.sol` that returns this stranded ETH to depositors. This is a direct, unrecoverable loss of funds for every user who dispatches a POST/GET request or funds a request using native ETH, scaling with the number of calls and the overpayment margin each caller must supply to avoid reverts — a High severity impact matching the referenced audit finding.

### Likelihood Explanation
This is triggered on the default/expected usage path documented for `EvmHost`: users are explicitly instructed to send native token via `msg.value` and let the Host swap it for the fee token, exactly as shown in the project's own documentation. Because on-chain price quotes always carry some margin/slippage buffer, essentially every native-token dispatch overpays by some amount, making the loss deterministic and near-certain on every such call, not just an edge case.

### Recommendation
In `EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()`, capture the `amounts` array returned by `swapETHForExactTokens` and compute `msg.value - amounts[0]` as the unspent ETH, then forward that unspent amount back to `_msgSender()` (or `post.payer`) at the end of the function — mirroring the refund pattern already implemented in `IntentGatewayV2.placeOrder` (`evm/src/apps/IntentGatewayV2.sol#L394-397`).

### Proof of Concept
1. Caller invokes `EvmHost.dispatch{value: 5 ether}(post)` where `post.fee` only costs 0.01 ETH worth of `feeToken` at current Uniswap price.
2. Inside `dispatch`, `IUniswapV2Router02.swapETHForExactTokens{value: 5 ether}(post.fee, path, address(this), block.timestamp)` executes, spending only ~0.01 ETH and refunding the remaining ~4.99 ETH to `address(this)` (`EvmHost`), per standard UniswapV2Router02 behavior.
3. `dispatch()` returns without forwarding any ETH back to the caller; the ~4.99 ETH remains in `EvmHost`'s balance indefinitely.
4. Repeating this for many callers accumulates significant stranded ETH in `EvmHost` with no code path in `EvmHost.sol` to return it to the original payers.
