### Title
Tron IntentGatewayV2 uses unchecked low-level `.call` for ERC20 transfers in escrow withdrawal, silently accepting failed transfers from non-standard tokens - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron variant of `IntentGatewayV2` implements escrow release (`withdraw`) and dust sweeping (`onAccept`/`SweepDust`) with a raw low-level `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` and only checks that the *call itself* did not revert (`success`). It never decodes and checks the boolean return value of `transfer()`. This is the exact bug class from the referenced report (tokens whose `transfer`/`transferFrom` do not behave per strict ERC20 semantics break protocol accounting) but manifests in the opposite direction: instead of reverting on tokens with no return value, this code silently *accepts* tokens that return `false` on failure without reverting, and still decrements escrow / marks the order filled as if the transfer succeeded.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol`, the internal `withdraw()` function (called from `onAccept` for `RedeemEscrow`/`RefundEscrow` and from `onGetResponse`) transfers escrowed ERC20 tokens like this: [1](#0-0) 

```solidity
if (token == address(0)) {
    (bool sent,) = beneficiary.call{value: amount}("");
    if (!sent) revert InsufficientNativeToken();
} else {
    (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
    if (!success) revert TransferFailed();
}

_orders[body.commitment][token] -= amount;
```

`success` here only reflects whether the low-level call reverted, not whether the ERC20 `transfer` call returned `true`. Per the ERC20 spec, a compliant token can return `false` to indicate a failed transfer without reverting (e.g., insufficient allowance/balance edge cases in certain implementations, or a token deliberately implementing "soft-fail" semantics). Because the return data is discarded, such a `false` return is treated identically to a successful transfer: `_orders[body.commitment][token] -= amount` still executes and, on `finalize`, the order is marked filled/refunded via `_filled[body.commitment] = beneficiary` and `EscrowReleased`/`EscrowRefunded` is emitted — even though the beneficiary received nothing.

The same unchecked pattern also appears in the `SweepDust` handler and the transaction-fee payout in the same function: [2](#0-1) [3](#0-2) 

This directly contrasts with the corresponding EVM-mainline implementation (`evm/src/apps/intentsv2/IntentsBase.sol`), which correctly uses OpenZeppelin's `SafeERC20.safeTransfer`, decoding and enforcing the boolean return: [4](#0-3) 

The Tron fork of `IntentGatewayV2` diverged from this safe pattern and reintroduced the unchecked-return-value class of bug.

### Impact Explanation
`withdraw()` is the function that releases escrowed user/solver funds after a cross-chain intent fill or cancellation (`RedeemEscrow`/`RefundEscrow`/GET-response refund paths). If any escrowed input token on Tron does not strictly follow the "revert on failure" convention (returns `false` instead), the escrow accounting will be permanently decremented and the order will be finalized as filled/refunded, while the beneficiary (solver or user) receives zero tokens. This is a permanent, unrecoverable freezing/loss of escrowed funds — the tokens remain locked in the contract with no accounting path left to reclaim them, since `_orders[commitment][token]` has already been decremented to zero and `_filled[commitment]` is set, blocking any retry.

### Likelihood Explanation
This is reachable by any ordinary user of the protocol: any account can place an order (`placeOrder`) using an ERC20 token as input, and any solver can fill it cross-chain, triggering the `RedeemEscrow`/`RefundEscrow` message that is delivered via `onAccept` to `withdraw()` on the Tron IntentGateway instance — no privileged role is required. The likelihood is directly tied to whether any token integrated as an escrowable asset on the Tron deployment exhibits non-reverting `transfer` failures (a known real-world token behavior class, distinct from but adjacent to the referenced USDT-style non-standard-return issue). Given IntentGateway is designed to support arbitrary ERC20 tokens as intent inputs/outputs, this is a realistic integration risk specific to the Tron contract variant.

### Recommendation
Replace the raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `withdraw()` and the `SweepDust` handler in `evm/tron/contracts/apps/IntentGatewayV2.sol` with OpenZeppelin's `SafeERC20.safeTransfer`, matching the pattern already used correctly in `evm/src/apps/intentsv2/IntentsBase.sol`. This ensures both call-revert and boolean-false-return failure modes cause the transaction to revert, keeping escrow accounting consistent with actual token movement.

### Proof of Concept
1. Deploy the Tron `IntentGatewayV2` and register a mock ERC20 token whose `transfer` function returns `false` on failure (e.g., when the contract's own balance is insufficient) rather than reverting — a legally valid, if non-ideal, ERC20 implementation.
2. Have a user `placeOrder` escrowing this token as an input.
3. Externally drain/manipulate the gateway's balance of this token to be insufficient at withdrawal time (or use a token that returns `false` unconditionally for the beneficiary address to simulate a blocked/blacklisted recipient).
4. Trigger `withdraw()` via the `RedeemEscrow` path (simulate `onAccept` with a `WithdrawalRequest` as in the existing test `testOnAcceptRedeemEscrow` pattern used for the mainline contract, applied to the Tron contract): the low-level `.call` succeeds (does not revert) but returns `abi.encode(false)`.
5. Observe that `withdraw()` does not revert, `_orders[commitment][token]` is decremented, `_filled[commitment]` is set, and `EscrowReleased` is emitted — while the beneficiary's token balance is unchanged, demonstrating permanent loss of the escrowed funds.
