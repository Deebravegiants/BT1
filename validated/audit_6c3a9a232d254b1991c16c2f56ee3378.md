The SafeERC20 finding is Ethereum/Solidity-specific: it addresses ERC20 tokens (like USDT) whose `transfer()`/`transferFrom()` do not return a `bool`, causing calls decoded via the standard `IERC20` ABI to revert or behave unexpectedly, which is why OpenZeppelin's `SafeERC20` wrapper is recommended.

This codebase is a Solana program, not an EVM contract. All token movements go through `Invokers::token_transfer` and `Invokers::token_transfer_with_authority` in `program/src/invokers.rs`, which build an `spl_token::instruction::transfer` instruction and execute it via `solana_program::program::invoke_signed`, propagating any CPI failure directly as a `ProgramError` [1](#0-0) [2](#0-1) . Solana's cross-program invocation model does not rely on decoding an ABI-encoded boolean return value the way Solidity's low-level `call` does — a failed SPL Token transfer aborts the whole transaction with an error propagated through `invoke_signed`, so there is no code path where a "silent failure" (return-value-less token) could leave the AMM in an inconsistent state. This applies uniformly across all reachable call sites, including deposit [3](#0-2) , withdraw [4](#0-3) , withdrawpnl [5](#0-4) , and the swap instructions [6](#0-5) [7](#0-6) .

Since the SPL Token program (unlike some ERC20 implementations) always returns a proper program-level success/error result that the runtime enforces, there is no reachable analog to the "missing return-value check" bug class within the scope defined (Initialize2, Deposit, Withdraw, swap instructions, invokers.rs).
