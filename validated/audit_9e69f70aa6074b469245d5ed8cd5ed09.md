### Title
Griefing via ETH transfer revert in IntentGatewayV2 `_withdraw`/`withdraw` permanently blocks cross-chain escrow settlement and relayer message delivery - (File: `evm/src/apps/intentsv2/IntentsBase.sol`, `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`IntentsBase._sendValue()` and the Tron `IntentGatewayV2.withdraw()` push native ETH to `beneficiary` with a raw `.call{value: amount}("")` and `require`/`revert`-on-failure semantics, exactly like the `forceCancelOrder()` pattern in the external report. These functions are reached from `onAccept()` and `onGetResponse()` — callback entrypoints triggered by an unprivileged relayer delivering a cross-chain `RedeemEscrow`/`RefundEscrow` message or GET response. If the order's `beneficiary` address is a contract that reverts on receiving ETH (intentionally or not), the whole delivery transaction reverts, and since these ISMP callbacks have no separate "claim" fallback, the relayer can never successfully deliver the message.

### Finding Description
`_sendValue` in `evm/src/apps/intentsv2/IntentsBase.sol` (lines 418-422):
```solidity
function _sendValue(address to, uint256 amount) internal {
    (bool sent,) = to.call{value: amount}("");
    if (!sent) revert InsufficientNativeToken();
}
```
This is invoked from `_withdraw()` (lines 451-470), which is called by:
- `ExtrinsicIntents.onAccept()` for `RequestKind.RedeemEscrow` / `RequestKind.RefundEscrow` (`evm/src/apps/intentsv2/ExtrinsicIntents.sol:330-337`) — an ISMP POST callback delivered by a relayer,
- `ExtrinsicIntents.onGetResponse()` (`evm/src/apps/intentsv2/ExtrinsicIntents.sol:360-366`) — an ISMP GET response callback also delivered by a relayer.

The equivalent Tron implementation in `evm/tron/contracts/apps/IntentGatewayV2.sol` (`withdraw()`, lines 691-714) has the identical pattern:
```solidity
if (token == address(0)) {
    (bool sent,) = beneficiary.call{value: amount}("");
    if (!sent) revert InsufficientNativeToken();
}
```
and is likewise reached from `onAccept` (line 634) and `onGetResponse` (line 742).

`beneficiary` in `WithdrawalRequest` is set to `order.user` (for a refund) or the filler/solver address (for a redeem) at order-placement/fill time — the order creator fully controls this value when placing the order, and a solver controls it when filling. If the beneficiary is set to a contract with no `receive()`/payable `fallback()`, or one that deliberately reverts, every subsequent call to `onAccept`/`onGetResponse` that attempts to pay that address in native ETH permanently reverts.

Unlike the `WrappedHyperFungibleToken.onAccept`/`onPostRequestTimeout` handlers (`sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol:299-365`), which explicitly guard against this by falling back to delivering wrapped ERC-20 tokens when the native push fails (`if (!sent) { IWETH(...).deposit(...); IERC20(...).safeTransfer(...); }`), the Intent Gateway's `_sendValue`/`withdraw` have no such fallback — they always revert on failure.

### Impact Explanation
Because `onAccept`/`onGetResponse` are the terminal handlers for ISMP messages routed through Hyperbridge, a permanent revert here means:
- The relayer cannot successfully deliver the `RedeemEscrow`/`RefundEscrow` POST message or the GET response — the message is stuck in an undeliverable state. Since these particular requests are constructed with `timeout: 0` in several cancel/redeem flows (see `_cancelFromSource`/`_cancelFromDest` in `ExtrinsicIntents.sol` and the Tron equivalent), they may never time out, so the underlying escrowed input tokens (potentially ERC-20 and ETH together, since `_withdraw` iterates over all `body.tokens`) become **permanently frozen** in the gateway contract, unable to be delivered or refunded through any code path.
- Any user or solver — by simply setting `beneficiary`/`order.user` to a non-payable or reverting contract at order placement/fill time — can grief the specific order's settlement. In multi-token withdrawal loops, this also blocks release of the co-escrowed ERC-20 tokens in the same `WithdrawalRequest`, since the loop reverts entirely on the first failed native transfer.

This matches the "permanent freezing of funds" / "route unable to deliver messages" impact categories, reachable from a single relayed message delivery by an unprivileged relayer.

### Likelihood Explanation
Low-to-medium likelihood: the attacker must control (or convince the counterparty to use) a beneficiary address that is a contract designed to revert on ETH receipt, and it only affects orders whose escrow/output includes native ETH (`token == address(0)`). It could occur unintentionally too — any non-payable smart-contract beneficiary would trigger the same permanent freeze, without any malicious intent, matching the "not-necessarily-intentional" scenario the original report calls out.

### Recommendation
Adopt the same defensive pattern already used in `WrappedHyperFungibleToken`/`WrappedHyperFungibleTokenUpgradeable`: on a failed native-ETH push in `_sendValue` (`IntentsBase.sol`) and in the Tron `withdraw()` function, do not revert the whole delivery. Instead, either:
1. Credit the amount to a per-beneficiary pending-withdrawal balance that the beneficiary (or anyone on their behalf) can claim later via a separate `claim()` function, or
2. Wrap the native ETH into the fee/host wrapped token and deliver it as an ERC-20 transfer instead (mirroring the WETH-mode fallback already implemented in `WrappedHyperFungibleToken.onAccept`).

This ensures `onAccept`/`onGetResponse` callbacks driven by relayers can never be permanently blocked by a hostile or non-payable beneficiary, and Hyperbridge message delivery/finality is preserved regardless of recipient behavior.

### Proof of Concept
1. Solver/user places or fills a cross-chain order (`ExtrinsicIntents`/same-chain `IntrinsicIntents`) with `output.beneficiary` (or `order.user` for refund path) set to a deployed contract `Griefer` that has no `receive()`/payable `fallback()` (or one that explicitly `revert()`s).
2. Order includes a native-ETH (`token == address(0)`) leg in `inputs`/`output.assets`.
3. Trigger the cross-chain redeem/refund flow: a relayer submits the ISMP proof, and Hyperbridge's host calls `IApp.onAccept()` (or `onGetResponse()`) on `IntentGatewayV2`/`ExtrinsicIntents`.
4. Inside `_withdraw()`/`withdraw()`, `_sendValue(beneficiary, amount)` executes `beneficiary.call{value: amount}("")`, which fails because `Griefer` rejects ETH.
5. The call reverts with `InsufficientNativeToken()` (or `TransferFailed()` on Tron), causing the entire `onAccept`/`onGetResponse` transaction — and therefore the relayer's message delivery — to fail. Since the request has `timeout: 0` in the affected cancel paths, no future timeout path exists to unwind the escrow, permanently freezing the co-escrowed tokens for that commitment.     function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;

                ++i;
            }
        }
