### Title
Non-Embedded Session ID Derived Directly From Unauthenticated Cookie Bytes Enables Cross-Tenant Session Hijacking - (File: `lib/shopify_api/utils/session_utils.rb`)

### Summary
For non-embedded apps, `ShopifyAPI::Utils::SessionUtils.current_session_id` returns the session identifier by reading it verbatim out of the `shopify_app_session` cookie, with no cryptographic binding (no HMAC, no signature, no server-side nonce lookup) tying that value back to the OAuth flow that created it.

### Finding Description
During the OAuth callback, `ShopifyAPI::Auth::Oauth.validate_auth_callback` builds a `SessionCookie` whose `value` is simply `session.id` [1](#0-0)  . That `id` is deterministically derived from public information: for offline sessions it is `"offline_#{shop}"`, and for online sessions it is `"#{shop}_#{user_id}"` [2](#0-1) . This cookie is stored as a plain (unsigned) value on the browser.

Later, when the host app wants to identify "who is making this request", it is instructed by the gem's own documentation to call `SessionUtils.current_session_id(nil, cookies, online)` for non-embedded apps [3](#0-2) . Internally this resolves to `cookie_session_id`, which does nothing more than return the raw cookie value: [4](#0-3) . There is no HMAC check, no signature, and no verification that the value actually originated from a completed OAuth handshake for that browser — contrast this with the embedded-app path, where the equivalent identifier is only accepted after being extracted from a `JwtPayload` that is HMAC-verified with `Context.api_secret_key` [5](#0-4) .

The binding that should hold is: `cookie value == an identifier the server can prove it minted for this specific authenticated browser session`. Instead the gem accepts: `cookie value == any string the client presents`. Because the identifier space is trivially predictable from the public shop domain (`offline_{shop}.myshopify.com`), an attacker only needs to know (or guess) a victim shop's domain to construct a valid-looking session ID and place it directly in their own cookie jar.

### Impact Explanation
Any host application that follows the gem's documented pattern (`current_session_id` → look up `Session` in `SessionRepository` → use `Session.access_token` for API calls, as shown in `docs/usage/oauth.md`) is exposed to cross-tenant session hijacking: an attacker forges the `shopify_app_session` cookie to `offline_{target-shop}.myshopify.com`, and the host app resolves this to the target shop's stored `Session`, including its persisted offline access token. This lets the attacker act as the target merchant against the app's own backend — a cross-tenant access / credential exposure impact.

### Likelihood Explanation
The attack requires only knowledge of the target's `.myshopify.com` domain (frequently public/discoverable) and the ability to set an arbitrary cookie value in the attacker's own browser — no access to `api_secret_key`, access tokens, or the merchant's browser is required. The identifier format (`offline_#{shop}` / `#{shop}_#{user_id}`) is fixed and documented in the code itself, making guessing trivial once the pattern is known.

### Recommendation
Do not use the raw session-id string as a bearer credential. Bind the cookie to server-side, unguessable session state (e.g., store a random opaque token in the cookie that maps to the session record server-side, or sign/HMAC the cookie value with `Context.api_secret_key` and verify it in `cookie_session_id` before trusting it), mirroring the verification already performed for the embedded/JWT path.

### Proof of Concept
1. Merchant `victim-shop.myshopify.com` installs a non-embedded app; `validate_auth_callback` sets cookie `shopify_app_session=offline_victim-shop.myshopify.com`.
2. Attacker, using their own browser/session with the same app, manually sets their `shopify_app_session` cookie to `offline_victim-shop.myshopify.com`.
3. Attacker requests any authenticated endpoint of the host app; the app calls `SessionUtils.current_session_id(nil, attacker_cookies, false)`, which returns `"offline_victim-shop.myshopify.com"` unchanged [6](#0-5) .
4. The host app looks up this ID in its `SessionRepository` (per the documented pattern) and retrieves the victim shop's `Session`, including its access token, letting the attacker impersonate the victim's app session.
