## Title
Webhook shop/topic identity spoofing via unauthenticated headers not covered by HMAC - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request **body**, but then dispatches the webhook handler using the `shop`, `topic`, `webhook_id`, and `api_version` values taken from HTTP **headers**, none of which are covered by that signature. This breaks the intended binding `authenticated_bytes == bytes_the_handler_acts_on`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors are all read directly from HTTP headers, which are not part of the signed content: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` (i.e. just the body) and compares it against the `hmac` header: [3](#0-2) 

`Registry.process` uses this validation result to gate processing, then immediately trusts the unauthenticated header-derived `shop`, `topic`, and `webhook_id` to build the `WebhookMetadata` dispatched to the app's handler: [4](#0-3) 

Because the same `api_secret_key` is shared across every shop that installs a given app, any tenant of that app can capture a legitimately-signed `(body, hmac)` pair delivered to their own store (e.g. from a webhook they can trigger, such as `orders/create` or `app/uninstalled`), then replay that exact body and HMAC value to the same app's webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) header with an arbitrary victim shop's domain. `HmacValidator.validate` still succeeds because it only checks the body bytes, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the event belongs to the victim shop. This is exactly the "bytes verified versus bytes parsed" identity-binding failure: the equality that should hold is `hmac_signed_bytes == bytes_used_to_identify_the_tenant`, but here `hmac_signed_bytes = raw_body` while `tenant_identity = header["x-shopify-shop-domain"]`, which are disjoint.

### Impact Explanation
This allows a malicious but otherwise unprivileged merchant/tenant of a multi-tenant app to forge webhook events attributed to another shop (cross-tenant), tricking the host application into acting on forged/attacker-controlled data (order data, uninstall notifications, GDPR events, etc.) as if it originated from a victim tenant. This matches the "Critical - cross-tenant access" impact category since it crosses a tenant boundary using only the shared, already-known app secret indirectly (via HMAC bytes captured from a legitimately delivered webhook), without needing the app's `client_secret` or any merchant's access token directly.

### Likelihood Explanation
Likelihood is moderate-to-high in practice: any developer/merchant who installs the app on their own store can trivially capture a real `(raw_body, hmac-sha256)` pair from Shopify's genuine webhook delivery (via server logs, a debugging proxy, or a webhook echo endpoint) and replay it against the same publicly reachable webhook endpoint with modified identity headers, since HTTP header spoofing to a server-side endpoint requires no special access.

### Recommendation
Include the shop domain, topic, and webhook id in the value that is HMAC-verified (or otherwise cryptographically bind them), rather than trusting header values independently of the signed body. At minimum, `Request#to_signable_string` should incorporate the header-derived `shop`/`topic`/`webhook_id` fields so `HmacValidator.validate` fails if any of them are altered relative to what Shopify originally signed for that specific delivery.

### Proof of Concept
1. Install the target app on shop `attacker.myshopify.com` and configure a webhook (e.g. `orders/create`).
2. Trigger a real order event; capture the resulting POST including the raw body and the `x-shopify-hmac-sha256` header sent by Shopify to the app's webhook endpoint.
3. Replay the identical HTTP POST (same body, same `x-shopify-hmac-sha256`) to the same app endpoint, but set `x-shopify-shop-domain: victim.myshopify.com`.
4. `Utils::HmacValidator.validate` succeeds (body unchanged), and `Registry.process` dispatches the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", topic: ..., body: <attacker's data>, ...)`, causing the host app to process attacker-controlled data as though it came from the victim tenant.
