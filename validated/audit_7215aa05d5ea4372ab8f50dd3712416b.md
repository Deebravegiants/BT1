### Title
Webhook shop identity spoofing — HMAC signs only the raw body while the tenant-identifying shop domain comes from an unsigned header ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` value used for tenant attribution from the `X-Shopify-Shop-Domain` HTTP header, but the HMAC signature that `Registry.process` validates only covers the raw request body. The shop identifier that downstream handlers rely on to scope data per-tenant is never bound to the cryptographic signature, breaking the equality `HMAC-authenticated-bytes == bytes-acted-on`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, however, is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header, which is not part of the signed payload: [2](#0-1) 

`Registry.process` validates the HMAC of the `Request` object and, upon success, unconditionally trusts `request.shop` (i.e., the header value) to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

Because `HmacValidator.validate` only recomputes the HMAC over `to_signable_string` (the raw body) and compares it to the `hmac-sha256` header, the check passes regardless of what value is present in the `shop-domain` header. Any request carrying a body+HMAC pair that is valid for shop A, but with the `X-Shopify-Shop-Domain` header swapped to shop B, will pass `process` and dispatch `WebhookMetadata.new(..., shop: "B", ...)` to the app's handler — even though the signature only proves the body originated with the app's secret, not that shop B is the source.

This is the exact bug class in the report: an unrestricted/unbound field (there, an attacker-supplied `dLoopCore` address not checked against any trusted registry; here, an attacker-controlled `shop` header not checked against the HMAC-covered content) is used downstream to drive tenant-scoped logic.

### Impact Explanation
Any app built on this gem that uses `WebhookMetadata#shop` to key per-tenant storage, permissions, or trust decisions (a documented, intended usage of `WebhookHandler#handle`) can be made to attribute a genuine, validly-signed webhook event to the wrong shop. This is a cross-tenant identity-binding break: data or state changes intended for shop A (e.g., `app/uninstalled`, `customers/data_request`, `shop/redact`) can be attributed to shop B purely by manipulating an unsigned header, without possessing the app's `client_secret`. This matches the "cross-tenant access" High/Critical impact category in scope.

### Likelihood Explanation
Exploitation requires the attacker to be able to submit an HTTP request to the app's webhook endpoint with a header they control alongside a body+HMAC pair they can obtain (e.g., by capturing/replaying a legitimate delivery to their own installed shop, which is something any unprivileged merchant/developer can generate for themselves). No leaked secret, TLS interception, or privileged account is required — only the ability to POST to the public webhook endpoint, which is inherent to how Shopify webhooks work.

### Recommendation
Bind the shop identity to the signed payload rather than trusting an unsigned header: either include the shop domain in the HMAC-signable string, or require callers to independently verify that the header's `shop` value matches a shop the app has records for (e.g., a shop with an active session/installation) before trusting it for tenant-scoped operations. At minimum, document prominently that `WebhookMetadata#shop` is not itself HMAC-verified and must not be used as the sole tenant key without additional server-side verification.

### Proof of Concept
1. App receives a legitimate webhook for its own test shop (`shop-a.myshopify.com`) with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC(secret, B)`.
2. Attacker resends the same body `B` and header `H` to the app's webhook endpoint, but replaces `X-Shopify-Shop-Domain: shop-a.myshopify.com` with `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes HMAC over `raw_body` (`B`) — validation succeeds because `B` and `H` are unchanged. [4](#0-3) 
4. `handler.handle` is invoked with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: <shop-a's data>, ...)`, causing the app to process shop-a's webhook payload under victim-shop's tenant context.
