### Title
Webhook shop-domain (and topic/webhook-id/api-version) headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its `hmac` from the `hmac-sha256`/`x-shopify-hmac-sha256` header and verifies it against `to_signable_string`, which returns only the raw request body. The `shop`, `topic`, `webhook_id`, and `api_version` values are read from separate HTTP headers that are never included in the HMAC-covered material, yet `Registry.process` forwards `request.shop` (and the other header-derived fields) directly into the app's handler as the trusted tenant identifier.

### Finding Description
`VerifiableQuery#to_signable_string` for `Webhooks::Request` is defined as: [1](#0-0) 
only the `@raw_body` is signed. The `shop`, `topic`, `webhook_id`, and `api_version` accessors instead read straight from HTTP headers with no cryptographic binding: [2](#0-1) 

`Registry.process` validates only the HMAC of the body, then passes `request.shop` — an unauthenticated header value — into the handler as the tenant identity: [3](#0-2) 

`HmacValidator.validate` confirms this: it only ever hashes `verifiable_query.to_signable_string`, i.e. the body, against the secret: [4](#0-3) 

This is the same bug class as the report's nonce issue: a value that identifies "which record/tenant this update applies to" (there: `addressToWithdrawalNonce[...][supplier]`; here: the `shop` used to route/handle the webhook) is accepted and acted upon without the binding check that would guarantee it actually belongs to the signed payload. Here the equality that should hold — `shop-header == shop-that-produced-this-signed-body` — is never checked; only `hmac(body) == hmac_header` is checked.

Any entity that can install the target app on their own (attacker-owned) shop legitimately receives valid `body` + `hmac-sha256` header pairs from Shopify (computed with the app's real `client_secret`/`api_secret_key`, which the attacker never needs to know). Because the headers are outside the signed material, the attacker can resend that exact `body`/`hmac` pair to the app's webhook endpoint while substituting `x-shopify-shop-domain` (and optionally `x-shopify-topic`/`x-shopify-webhook-id`) with a victim shop's domain. `HmacValidator.validate` still succeeds (body unchanged), and `Registry.process` hands the handler a `WebhookMetadata` claiming to be from the victim shop, `shop: request.shop` while the body content is actually the attacker's own webhook payload.

### Impact Explanation
This breaks the tenant-authentication boundary the gem is expected to enforce for webhook delivery: apps built on this library rely on `request.shop`/`WebhookMetadata#shop` being an authentic, Shopify-verified value once `HmacValidator.validate` passes. An attacker can cause the app to process attacker-controlled webhook content under an arbitrary victim shop's identity, leading to cross-tenant data corruption or unauthorized actions being taken against another merchant's resources (e.g., an app that syncs order/product data keyed by `data.shop` could write attacker data into the victim's tenant record, or trigger side effects scoped to the victim). This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
The attack requires no possession of the app's `client_secret`/`api_secret_key`, no privileged account, and no TLS interception — only that the attacker can install the app on their own store (or otherwise obtain one genuine signed webhook body/hmac pair) and can send an arbitrary HTTP request to the app's public webhook endpoint with a modified `shop-domain` header, something entirely within reach of an unprivileged internet user.

### Recommendation
Include the `shop`, `topic`, `webhook_id`, and `api_version` header values in the HMAC-signed material (or otherwise cryptographically bind them to the body, e.g., verify them against a signed claim), so that `HmacValidator.validate` fails if any of these identity-carrying headers are altered relative to what Shopify actually signed for that shop.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; trigger any webhook (e.g. `orders/create`) so Shopify sends a legitimate request with body `B` and header `x-shopify-hmac-sha256: H` (computed by Shopify from `B` and the app's real secret).
2. Replay the request to the app's webhook endpoint, keeping `raw_body = B` and `x-shopify-hmac-sha256 = H` unchanged, but set `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...shop-domain: "victim.myshopify.com", hmac: H...})` is constructed; `Utils::HmacValidator.validate(request)` returns `true` because it only checks `H` against `HMAC(secret, B)`, per [5](#0-4)  and [6](#0-5) .
4. `Registry.process` invokes the app's handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed B, ...)`, per [7](#0-6) , so the app performs the webhook's effects against the victim tenant using attacker-chosen body content.
