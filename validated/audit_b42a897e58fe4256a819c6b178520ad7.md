## Analysis

This is a valid analog. The root cause mirrors the AvailBridge issue: a payable dispatch function that accepts more native token than required for the fee and never returns the excess to the caller.

### Title
EvmHost.dispatch() and fundRequest() do not refund excess native token overpaid for the fee-token swap - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` accept an arbitrary `msg.value` and swap it into `feeToken` via `swapETHForExactTokens`, but they never capture the router's returned `amounts` array nor forward any leftover ETH back to the original caller.

### Finding Description
In `EvmHost.dispatch(DispatchPost)`, when `msg.value > 0` the function calls: [1](#0-0) 

`swapETHForExactTokens(post.fee, path, address(this), block.timestamp)` is called with `{value: msg.value}`. Uniswap V2's router computes the exact ETH input required (`amounts[0]`) to produce `post.fee` tokens, performs the swap, and refunds `msg.value - amounts[0]` — but that refund is sent to `msg.sender` of the router call, which is `EvmHost` itself, not the original transaction sender (`_msgSender()`). `EvmHost` neither captures the return value of `swapETHForExactTokens` nor forwards any of that leftover ETH back to the caller who supplied it. The same pattern repeats in `dispatch(DispatchGet)`: [2](#0-1) 

and in `fundRequest`: [3](#0-2) 

By contrast, the codebase demonstrates the correct pattern elsewhere: `IntentGatewayV2.placeOrder` captures `amounts[0]` from the swap, deducts it from the tracked `msgValue`, and explicitly refunds any leftover native token to the caller: [4](#0-3) 

`EvmHost.dispatch`/`fundRequest` lack this accounting and refund step entirely, so any ETH sent above what the swap actually consumes remains trapped inside the `EvmHost` contract.

### Impact Explanation
Because `dispatch()` is the primary permissionless entry point used by every application/module dispatching a cross-chain POST/GET request with native-token payment (as documented in the SDK/app patterns, e.g. `IDispatcher(_host).dispatch{value: msg.value}(post)`), any caller who supplies `msg.value` greater than the exact swap input required for `post.fee`/`get.fee` permanently loses the difference — the funds are not returned to them and there is no visible mechanism in `EvmHost` to reclaim stray native ETH held by the contract. This constitutes a permanent loss of user funds (Medium severity, consistent with the original AvailBridge report), scaling with every native-token dispatch made with an estimated/rounded-up `msg.value`.

### Likelihood Explanation
Likelihood is high because exact-input sizing for `swapETHForExactTokens` is impractical for callers (Uniswap V2 pricing changes with pool reserves/slippage between quote and execution), so in practice most integrators/documented examples send `msg.value` with some buffer, guaranteeing an overpayment on nearly every native-token dispatch call unless a caller can compute the on-chain price to the wei.

### Recommendation
Capture the return value of `swapETHForExactTokens` (`amounts[0]`) in `EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest`, and refund `msg.value - amounts[0]` back to `_msgSender()` (mirroring the pattern already implemented in `IntentGatewayV2.placeOrder`/`fillOrder`).

### Proof of Concept
1. Caller calls `EvmHost.dispatch{value: 5 ether}(post)` where `post.fee` only requires `0.01 ether` worth of ETH to swap for the exact fee-token amount.
2. `swapETHForExactTokens(post.fee, path, address(this), deadline)` executes, consuming `~0.01 ether` and refunding `~4.99 ether` to `msg.sender`, i.e., the `EvmHost` contract (per standard `UniswapV2Router02` behavior: `if (msg.value > amounts[0]) TransferHelper.safeTransferETH(msg.sender, msg.value - amounts[0]);`).
3. `EvmHost.dispatch` does not read the swap's return value or forward any ETH back to the caller; the `4.99 ether` remains locked in the `EvmHost` contract balance with no code path found (in the reviewed sections) to return it to the original caller.

Note: I was unable to fully enumerate every function in `EvmHost.sol` (only partial ranges were reviewed) to conclusively rule out an admin/owner sweep function for stray native ETH; a Devin session with full file access would be needed to confirm whether such a recovery path exists. If confirmed absent, the funds are permanently unrecoverable by the original payer.
