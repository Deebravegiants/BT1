This confirms the pattern. The library's own documentation explicitly says `ShopifyAPI::Webhooks::Registry.process` "will verify the request did indeed come from Shopify" [1](#0-0) , and passes `data.shop` to the handler as the trusted tenant identity [2](#0-1) . ### Title
Webhook shop-domain identity spoofing via HMAC that only covers the request body, not the `shop` header - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely by checking `Utils::HmacValidator.validate(request)` [3](#0-2) . The HMAC is computed over `request.to_signable_string`, which is defined as `@raw_body` only [4](#0-3) . The `shop` value returned by `request.shop`, however, is read directly from the unauthenticated `shopify-shop-domain` / `x-shopify-shop-domain` header [5](#0-4) . That `shop` value is then forwarded, without any independent verification, into `WebhookMetadata` and handed to the app's handler as the trusted tenant identifier [6](#0-5) .

### Finding Description
The identity binding that should hold is: `shop header value == shop that the HMAC-secret holder actually intended this body for`. Here that binding is broken — the HMAC only proves "whoever set the `hmac-sha256` header knows `api_secret_key` and hashed this exact body"; it says nothing about which `shop-domain` header accompanies that body. Since `to_signable_string` for `Webhooks::Request` returns solely `@raw_body` [4](#0-3) , the `shop` field is a field "acted on but not covered by the HMAC."

Concretely: any party that has received one legitimate webhook delivery from Shopify for a shop they control (e.g., their own merchant test store, or via a "send test notification" from the Shopify admin) possesses a valid `(raw_body, hmac-sha256)` pair. Because the header carrying the shop domain is excluded from the signed content, that same `(raw_body, hmac)` pair remains "valid" under `HmacValidator.validate` no matter what `shopify-shop-domain` header value is attached to the replayed request. An attacker can therefore replay their own genuine webhook body/HMAC to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header (e.g. a victim shop's domain), and `Registry.process` will accept it as valid and dispatch it to the handler with `data.shop` set to the attacker-chosen value [7](#0-6) .

### Impact Explanation
This breaks the shop/tenant identity binding that the library's own documentation promises is verified ("This will verify the request did indeed come from Shopify" [1](#0-0) , with `shop` documented as "The shop domain of the webhook" [8](#0-7) ). Any host application that follows this documented contract and uses `data.shop` to select which merchant's session/store data to act on (the exact usage shown in the gem's own example handler [9](#0-8) ) is exposed to cross-tenant data injection: an attacker can make the app process fabricated (attacker-authored, since only the body content, which the attacker controls when it's their own store's webhook, is signed) webhook events under a victim shop's identity. This is a cross-tenant identity-binding bypass rooted entirely in this gem's own `HmacValidator`/`Webhooks::Request` design, not in host misuse.

### Likelihood Explanation
Likelihood is high for a determined attacker who is themselves a legitimate merchant/user of the app (a common "unprivileged internet user" position for multi-tenant Shopify apps): they can trivially obtain a valid `(body, hmac)` pair from their own shop's webhook traffic or Shopify's admin "send test notification" feature, then replay it with a forged shop-domain header to any exposed webhook endpoint that uses this gem's `Registry.process`.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the signed material used for validation, or independently re-verify that the shop header matches a shop the app expects/has an active session for before trusting `request.shop`. At minimum, document explicitly that `request.shop` is NOT authenticated by `HmacValidator.validate` and must not be trusted as a tenant identifier without additional verification (e.g., cross-checking against a known/installed shop list) — this contradicts the current documentation, which describes `process` as verifying "the request did indeed come from Shopify."

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker-shop.myshopify.com` and triggers (or waits for) a real webhook, e.g. `orders/create`, capturing the raw POST body `B` and the `x-shopify-hmac-sha256` header value `H` that Shopify sent.
2. `H` is `HMAC-SHA256(api_secret_key, B)`; per `HmacValidator.validate_signature`, this is exactly what is recomputed and compared [10](#0-9) .
3. Attacker sends a new POST request to the app's webhook endpoint with body `B` unchanged, header `x-shopify-hmac-sha256: H` unchanged, but `x-shopify-shop-domain: victim-shop.myshopify.com` (any target shop domain the app services).
4. `ShopifyAPI::Webhooks::Request.new` builds successfully (all three required headers present) [11](#0-10) ; `request.hmac` decodes `H`, and `request.to_signable_string` returns `B`, so `HmacValidator.validate` returns `true` [3](#0-2) .
5. `Registry.process` dispatches to the registered handler with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)` [7](#0-6) , causing the app to process attacker-controlled webhook content under the victim shop's identity.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
