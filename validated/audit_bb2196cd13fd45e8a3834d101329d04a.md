### Title
Incomplete secret masking in HTTP debug-request logging allows disclosure of non-"password" sensitive fields (e.g. `oldPassword`/`newPassword` casing gaps and any non-password secret keys) - (File: core/web/router.go)

### Summary
The Jenkins CVE-2019-10367 root cause is that a secret-masking mechanism existed but had an incomplete implementation path that let sensitive values reach the log file unmasked. Chainlink's HTTP web server has an analogous structure: request bodies are logged at `Debug` level via `loggerFunc`, and a bespoke `isBlacklisted`/`redact` mechanism attempts to mask sensitive fields — but it only recognizes keys containing the substring `"password"`, leaving other categories of secrets sent in JSON request bodies (e.g., new-user creation fields, LDAP `password`-adjacent keys, or any future field not named "*password*") unmasked in the debug log.

### Finding Description
`loggerFunc` in <cite repo="Alyssadaypin/chainlink--016" path="core/web/router.go" start="533-568" /> reads the entire raw request body for every API call and logs it at `Debug` level via `readBody`, which calls `readSanitizedJSON`. That function walks the top-level JSON keys and masks only fields whose key is in a hard-coded `blacklist` or contains the substring `"password"`:

<cite repo="Alyssadaypin/chainlink--016" path="core/web/router.go" start="643-658" />

This mirrors the Jenkins bug pattern precisely: the plugin's fix (SECURITY-1279) added secret-field detection but missed one specific logger (`DataBoundConfigurator`) which logged secrets unmasked. In Chainlink's case, `readSanitizedJSON` in `core/web/router.go` is the single chokepoint responsible for masking *all* sensitive HTTP request fields across the entire API surface, but its detection logic is a narrow keyword match (`"password"`) rather than a type-based mechanism (unlike the config/secrets subsystem, which uses `models.Secret`/`config.SecretString` types that self-redact via `MarshalText`, see <cite repo="Alyssadaypin/chainlink--016" path="core/store/models/secrets.go" start="1-13" />). Any request field carrying a secret that is not named with "password" (for example a bridge's `confirmations`/`url`, or any future token/secret field added to a JSON API request) will be logged in cleartext at `Debug` level. Additionally, `readSanitizedJSON` only inspects **top-level** keys of the parsed JSON map — nested objects/arrays are not recursively redacted, so a nested secret field (e.g. `{"credentials": {"password": "..."}}`) would bypass masking entirely because `isBlacklisted` is only invoked on the outer map's keys, not on any nested map keys.

### Impact Explanation
If Debug-level logging is enabled (a supported, documented log level for the node operator), any sensitive value passed to the JSON API — including nested secret fields — can be written to the node's log file in cleartext. Because chainlink logs are frequently shipped to centralized logging/observability platforms (Loki, Splunk, etc.) or included in support bundles, this creates a persistent secondary storage location for what should be one-time-use or masked secrets, potentially readable by anyone with log access (log aggregation admins, SRE, or an attacker who gains read access to log storage). This matches CWE-532's core impact: sensitive information disclosure via log files.

### Likelihood Explanation
Exploitability requires only that the node operator has Debug-level HTTP logging enabled (a normal operational configuration, not an exotic one) and that a client (any authenticated API user, or in some paths even unauthenticated login attempts) sends a request containing a secret-bearing field that is nested or not named with "password". Given the narrow, keyword-based, top-level-only redaction logic, this is a design limitation rather than a rare edge case, making it moderately likely to occur in real deployments, but it's bounded by the requirement that Debug logging be active and that a secret-bearing endpoint be exercised.

### Recommendation
Replace the substring/blacklist-based top-level JSON masking in `readSanitizedJSON` (and `redact` for query params) in `core/web/router.go` with a recursive redaction function that traverses nested maps/arrays, and expand the sensitive-key detection beyond `"password"` to also match `token`, `secret`, `key`, `credential`, etc., or (better) adopt the same type-driven `config.SecretString`/`config.SecretURL` self-redacting model already used in `core/store/models/secrets.go` for all sensitive HTTP request/response DTOs, ensuring masking is enforced at the type level rather than by a fragile keyword list.

### Proof of Concept
1. Enable Debug-level logging on a chainlink node (`Log.Level = 'debug'`).
2. Send a JSON API request containing a nested object with a sensitive field, e.g. `POST /v2/some_endpoint` with body `{"credentials": {"password": "supersecret"}}`.
3. Because `readSanitizedJSON` (<cite repo="Alyssadaypin/chainlink--016" path="core/web/router.go" start="608-629" />) only checks top-level keys (`dst` map), the nested `password` key is never inspected by `isBlacklisted`, and the full nested object—including the plaintext secret—is written to the log via `loggerFunc`'s `"body"` field.
4. Inspect the node's log output at Debug level; the plaintext secret is present unmasked.
