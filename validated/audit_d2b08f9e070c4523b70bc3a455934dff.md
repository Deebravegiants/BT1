### Title
Webhook `shop` identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by HMAC-verifying the **request body** only, then trusts the `shop`, `topic`, `api-version`, and `webhook-id` values from **HTTP headers that are never included in the signed content**. Any actor who has obtained one genuinely-signed webhook payload (trivially available to anyone who installs the app on their own store) can replay that exact body/HMAC pair while substituting an arbitrary `shop-domain` header, and the app-supplied handler will process it as if it came from a different, unrelated shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

and `#shop` is read straight from the unauthenticated `shopify-shop-domain` / `x-shopify-shop-domain` header: [2](#0-1) 

`Registry.process` validates the HMAC over that signable string (the body) and, once it passes, immediately builds `WebhookMetadata` using `request.shop` — a value that was never covered by the HMAC: [3](#0-2) 

`Utils::HmacValidator.validate` computes `HMAC-SHA256(api_secret_key, signable_string)` and compares it to the header-supplied digest: [4](#0-3) 

The equality this breaks: the identity the app trusts, `handler.handle(shop: request.shop)`, is assumed to equal the identity that produced/authorized the HMAC-signed bytes, `HMAC(api_secret_key, raw_body)`. In reality only the body is bound to the secret; the shop header is completely outside that binding, exactly matching the "field acted on but not covered by the HMAC" bug class from the report (where `stake_owner` was never checked against the actual invoker).

### Impact Explanation
Because a single `api_secret_key` is shared by the app across **all** shops that install it, an unprivileged internet user can install the target app on their own (attacker-controlled) shop, trigger any webhook topic on that shop to receive a validly signed `(body, hmac)` pair, and then replay that exact pair to the app's webhook endpoint with an arbitrary `shop-domain` header pointing at a victim shop. The app's registered webhook handler will execute business logic (e.g., order/customer/app-uninstalled processing, data sync, cache invalidation) attributed to the victim shop using attacker-controlled body content, resulting in cross-tenant data confusion/injection — a High/Critical-class cross-tenant impact per the given rubric, since it crosses a tenant (shop) boundary using only the attacker's own legitimately-issued credentials.

### Likelihood Explanation
Likelihood is high for any app that keys tenant data or authorization decisions off the `shop` value from `WebhookMetadata` (the documented/expected usage pattern) rather than independently cross-checking it. No access token, `client_secret`, or privileged account is required — only the ability to install the app on any shop (a normal, unprivileged action) and to send arbitrary HTTP requests to the app's own public webhook endpoint.

### Recommendation
Do not trust `shop-domain` (or `topic`/`api-version`/`webhook-id`) headers independently of the signed body. Either include the shop domain in the HMAC-signable content, or require the consuming app to verify the header-provided shop against a shop already known to be associated with that exact HMAC/body pair (e.g., by validating the shop is part of a previously established mapping) before dispatching to the handler.

### Proof of Concept
1. Install the target Shopify app on attacker-owned shop `attacker.myshopify.com`; trigger a webhook (e.g., `orders/create`) — Shopify sends a body `B` with header `X-Shopify-Hmac-Sha256: HMAC(secret, B)` and `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Capture `B` and its valid HMAC.
3. POST to the app's webhook endpoint with the same `B` and same `X-Shopify-Hmac-Sha256`, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `Utils::HmacValidator.validate` succeeds (it only checks `B` against the secret), and `Registry.process` invokes the app's handler with `shop: "victim.myshopify.com"`, `body: parsed(B)` — data the attacker fully controls, attributed to a shop the attacker does not own. [3](#0-2) [5](#0-4)
