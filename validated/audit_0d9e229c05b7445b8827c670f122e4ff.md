## Title
Webhook `shop` (tenant) header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then trusts the `shop-domain` header — which is *not* part of the signed content — to determine which tenant/store the payload belongs to. Anyone who can obtain one legitimately-signed `(body, hmac)` pair (e.g. from their own Shopify store, which sends genuine webhooks signed with the same app-wide `client_secret`) can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `shop-domain` header, causing the app to process/store that payload under a different, victim tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes/compares the HMAC exclusively against that signable string: [2](#0-1) 

`Registry.process` uses this validation as the sole authentication gate, then immediately forwards `request.shop` (parsed straight from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` header) to the app's handler as the tenant identifier, alongside the verified body: [3](#0-2) 

The `shop` accessor is a raw, unsigned header read: [4](#0-3) 

Because the HMAC key (`Context.api_secret_key`) is shared across every shop installed on the app, an attacker who owns any single store on the app can point that store's webhook subscription at their own listener, capture a genuine `(raw_body, hmac)` pair, and then POST it to the target app's webhook endpoint with the `shop-domain` header rewritten to a different (victim) shop. The HMAC still validates (it only covers the body), so `Registry.process` calls the handler with `WebhookMetadata.new(shop: <victim-shop>, body: <attacker-controlled body>, ...)` — breaking the identity binding `hmac-signed-content == data acted upon` (the tenant key `shop` is acted on but never covered by the signature).

### Impact Explanation
This breaks tenant isolation: the app's webhook handler (which typically looks up the merchant's stored access token/session and mutates data keyed by `shop`) can be made to process attacker-supplied webhook bodies under an arbitrary victim shop's identity — a cross-tenant data-integrity/confusion issue that can corrupt another merchant's records or trigger business logic (e.g., app/uninstall, order, fulfillment side effects) attributed to a shop the attacker doesn't own.

### Likelihood Explanation
Requires only that the attacker controls at least one shop installation of the target app (a normal, unprivileged merchant account) — no access to the app's `client_secret`, no TLS interception, and no privileged Shopify access is needed. This is trivially reachable via any exposed webhook endpoint built on `ShopifyAPI::Webhooks::Registry.process`.

### Recommendation
Do not trust the `shop-domain` webhook header as an authenticated tenant identifier on its own. Either bind the shop to the registration/subscription that was actually created for that tenant (validate that the resolved `webhook_id`/topic registration belongs to the claimed shop before dispatch), or extend the HMAC-covered signable content to include the shop domain (per Shopify's webhook verification guidance, apps should still validate the caller's shop against the shop for which a specific webhook was registered) rather than relying on the header value asserted by the caller.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and configures a webhook (e.g. `orders/create`) to point at an interceptor they control, capturing a genuine `(raw_body, x-shopify-hmac-sha256)` pair.
2. Attacker sends a POST to the target app's real webhook endpoint with the exact same `raw_body` and `hmac` headers, but sets `shopify-shop-domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` succeeds (it only checks `raw_body` against `Context.api_secret_key`), and `Registry.process` invokes the handler with `shop: "victim-shop.myshopify.com"` and the attacker's body, as shown at [5](#0-4) .
