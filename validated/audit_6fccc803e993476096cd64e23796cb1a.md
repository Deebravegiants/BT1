### Title
Webhook `shop` (tenant) identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` is documented as verifying "the request did indeed come from Shopify" before invoking the app's handler with a `WebhookMetadata` object that includes the `shop` domain. In reality, the HMAC signature only authenticates the raw request body — the `shop-domain` header used to populate `data.shop` is never included in the signed material, so it can be swapped freely on any request that carries a *valid but unrelated* HMAC/body pair.

### Finding Description
`ShopifyAPI::Webhooks::Request` mixes in `Utils::VerifiableQuery` and implements: [1](#0-0) [2](#0-1) 

`to_signable_string` returns only `@raw_body`, meaning `Utils::HmacValidator.validate` (`OpenSSL::HMAC.hexdigest(secret, raw_body)` compared to `hmac-sha256`) verifies **the body bytes only**: [3](#0-2) 

`Registry.process` performs exactly that check and then unconditionally trusts `request.shop` (sourced from the `shop-domain` header) to build the `WebhookMetadata` passed to the app's handler: [4](#0-3) 

The gem's own documentation instructs developers to key business logic — including background job dispatch — directly off `data.shop`, and explicitly claims the `process` call "will verify the request did indeed come from Shopify": [5](#0-4) [6](#0-5) 

The binding that is broken: `hmac-verified(raw_body) == true` is treated as if it implied `shop-domain header == genuine originating shop`, but the two are independent — the equality `signed_bytes == verified_bytes` holds only for the body, while `claimed_shop (header) == actual_shop (unauthenticated)` is never checked.

### Impact Explanation
Any actor who can obtain one legitimate `(raw_body, hmac-sha256)` pair for the target app — e.g., by installing the app on their own (attacker-controlled) shop and receiving a single real webhook delivery — can replay that exact body/HMAC pair while substituting an arbitrary `shop-domain` (or `x-shopify-shop-domain`) header value naming a victim shop. Because `to_signable_string` never includes the shop header, `HmacValidator.validate` still returns `true`, and `Registry.process` calls the handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain. Any host application following the gem's documented pattern (persisting/job-queuing per `data.shop`) will process or store data under the wrong tenant, resulting in cross-tenant data confusion — writes, job triggers, or state changes attributed to a shop the attacker doesn't control.

### Likelihood Explanation
High: the only prerequisite is possession of one real webhook delivery's raw body and its accompanying HMAC header, which is trivially obtainable by any developer/merchant who installs the target app on a shop they control (no `api_secret_key`, access token, or privileged account needed). The replay itself is a simple HTTP POST with a modified header, exploitable at will and repeatably against any registered webhook topic.

### Recommendation
Include the shop (and topic/webhook id) in the material that is authenticated, or otherwise cryptographically/contextually bind the `shop-domain` header to the verified body — e.g., verify that the shop presented in the webhook maps to a shop with an active, previously-persisted subscription/session before dispatching to the handler, and update `Utils::VerifiableQuery`/`Request#to_signable_string` (or `Registry.process`) so that spoofed shop headers cannot ride along with a validly-signed but unrelated body.

### Proof of Concept
```ruby
# 1. Attacker installs the target app on their own shop "attacker.myshopify.com"
#    and receives one genuine webhook delivery, capturing:
raw_body = '{"id":1,"note":"hi"}'
hmac     = "<value of x-shopify-hmac-sha256 from the genuine delivery>"

# 2. Attacker replays the exact same body/HMAC pair, but swaps the shop header
#    to point at a victim shop that also uses the app.
headers = {
  "x-shopify-topic"       => "orders/create",
  "x-shopify-hmac-sha256" => hmac,               # unchanged, still validates raw_body
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # spoofed, not covered by HMAC
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) returns true (body signature intact)
# => handler.handle(data: WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", ...))
#    is invoked, causing the app to act on/attribute data to the victim tenant.
```

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
