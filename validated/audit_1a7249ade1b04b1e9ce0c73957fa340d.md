### Title
Malicious ERC-20 among order inputs permanently blocks `_withdraw`/`withdraw`, freezing the solver's entire escrow reward - (File: evm/src/apps/intentsv2/IntentsBase.sol / evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
`IntentGatewayV2.placeOrder` accepts an arbitrary set of `order.inputs` tokens supplied by the user with no whitelist check [1](#0-0) . Once a solver fills the order, the settlement path (`onAccept` → `withdraw`/`_withdraw`) iterates over `body.tokens` and transfers each escrowed token to the beneficiary in a single loop, reverting the whole function if any single transfer fails [2](#0-1) . The same unguarded loop-and-revert pattern exists in the Tron deployment's `withdraw()` [3](#0-2) .

### Finding Description
A user placing an order can escrow a mix of legitimate tokens and a self-deployed malicious ERC-20 (e.g., one whose `transfer()` always reverts) as part of `order.inputs`, since `placeOrder` performs no allow-list validation on input token addresses [4](#0-3) .

A solver, unaware of the malicious token, fills the order by delivering the requested outputs and dispatches a `RedeemEscrow` request back to the source chain. When that request is delivered, `onAccept` decodes the `WithdrawalRequest` and calls `_withdraw`/`withdraw`, which loops through `body.tokens` calling `safeTransfer`/`.call` for each token in turn [5](#0-4) . Because the malicious token's `transfer` unconditionally reverts, the entire `_withdraw` call reverts — including the release of every other legitimate token escrowed for that same order and the accumulated transaction fee payout [6](#0-5) .

Per the codebase's own documented decision, the Intent Gateway dispatches its cross-chain settlement messages with no timeout, unlike token-bridge apps that gate `onPostRequestTimeout` on the token [7](#0-6) . This means the `RedeemEscrow` request can be retried indefinitely by relayers but will always fail identically (the malicious token always reverts), so it can never succeed and can never time out to trigger any refund path either. The solver's legitimately earned escrowed input tokens (and fees) are frozen permanently, with no recovery mechanism — the exact "loop over an attacker-chosen token list reverts the whole batch" bug class from the reference report, but here it results in permanent fund freezing for the solver rather than merely blocking a single claim retry.

The same-chain fill path (`IntrinsicIntents._fillOrder` → `_withdraw`) is equally affected, since it reuses the identical `_withdraw` loop [8](#0-7) .

### Impact Explanation
Any order creator can weaponize a self-deployed malicious ERC-20 as one of several `order.inputs`. Once a solver commits real capital/output tokens to fill the order, the source-chain settlement of `RedeemEscrow` is permanently unrepeatable-success, freezing 100% of that solver's escrowed reward (all input tokens, not just the malicious one) and the accompanying transaction fee, with no timeout-triggered refund available. This is a permanent freezing-of-funds condition reachable from a single order placement — High severity.

### Likelihood Explanation
Any unprivileged user can deploy a trivial malicious ERC-20 and include it as one of the `order.inputs` when calling `placeOrder`; no special privileges, governance, or race conditions are required. Solvers have no on-chain way to detect or reject malicious tokens before committing to fill an order, and the exploit is deterministic once a solver fills it.

### Recommendation
Isolate per-token transfers in `_withdraw`/`withdraw` so a single failing transfer cannot block release of the other tokens or the fee payout (e.g., wrap each transfer in a try/catch or low-level call that is individually accounted for and retried/skipped without reverting the whole function), and/or restrict `order.inputs` to a protocol-maintained token whitelist so solvers can't be tricked into filling orders backed by adversarial tokens.

### Proof of Concept
1. Attacker deploys `MaliciousToken` whose `transfer()` always reverts.
2. Attacker calls `placeOrder` with `order.inputs = [ {USDC, 1000}, {MaliciousToken, 1} ]` and a legitimate-looking `output` (e.g., DAI) [9](#0-8) .
3. A solver, seeing a profitable DAI→USDC/Malicious swap, calls `fillOrder`, delivering DAI to the beneficiary and dispatching the `RedeemEscrow` request to the source chain.
4. On delivery, `onAccept` calls `withdraw`/`_withdraw` with `body.tokens = [USDC, MaliciousToken]`; the loop reaches `MaliciousToken.transfer` and reverts, rolling back the USDC release as well [10](#0-9) .
5. Because the Intent Gateway dispatches with no timeout [7](#0-6) , every relayer retry of the same message hits the identical revert — the solver's escrowed USDC reward is frozen permanently.
