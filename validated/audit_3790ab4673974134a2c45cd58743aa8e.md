### Title
Webhook `shop` identity is trusted from an HMAC-unsigned header while only the raw body is signature-verified - ([File: lib/shopify_api/webhooks/registry.rb])

### Summary
`Registry.process` verifies only the raw request body against the `X-Shopify-Hmac-Sha256` header, then passes `request.shop` — read from the separate `X-Shopify-Shop-Domain` header, which is not covered by the HMAC — straight into the `WebhookMetadata` handed to the app's handler as the authoritative tenant identifier.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `Registry.process` validates the webhook solely via `Utils::HmacValidator.validate(request)`, i.e. `HMAC(secret, raw_body) == X-Shopify-Hmac-Sha256` [2](#0-1) . The `shop` value used downstream, however, is read from the `shop-domain` header via `Request#shop`, entirely outside the signed material [3](#0-2) . `Registry.process` then constructs `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` and forwards it to the registered handler [4](#0-3) , with no additional cross-check that the signed body actually corresponds to that claimed shop.

The identity binding that should hold is: `shop asserted in header == shop the HMAC vouches for`. Because the HMAC only covers `@raw_body`, this equality is never actually checked by the gem — it is silently assumed. Any party in possession of one valid `(raw_body, hmac)` pair signed with the app's secret (e.g., an attacker who owns a shop that has this app installed, receives their own legitimate webhooks, and can therefore compute or replay a valid signature for a body they control) can send a request with an arbitrary `X-Shopify-Shop-Domain` header while keeping the same signed body, and the gem will treat the request as originating from the spoofed shop.

### Impact Explanation
If a host application uses `WebhookMetadata#shop` to select per-tenant data (session/access-token lookup, database scoping, `shop`-redact/data-request routing, etc.), an attacker-controlled shop value combined with a self-supplied signed body can result in cross-tenant data operations being executed against the wrong shop's context — e.g. writing/deleting/redacting a different shop's records, or triggering privileged shop-scoped webhook handlers (such as `shop/redact`) against an unintended tenant. This matches the "cross-tenant access" class in Critical impact.

### Likelihood Explanation
Exploitability requires the attacker to be able to produce at least one raw body whose HMAC they can control or intercept and replay with a substituted `X-Shopify-Shop-Domain` header — trivially achievable by any developer/merchant who has legitimately installed the app on their own store (an "unprivileged internet user" relative to other tenants) and can trigger a webhook to their own endpoint, then replay it with a different shop header against the app's webhook endpoint. No `api_secret_key`, access token, or TLS interception is needed, only observation of one's own legitimately-received webhook.

### Recommendation
Include the shop domain (and ideally topic/webhook id) as part of the HMAC-signed material verified by `HmacValidator`, or have `Registry.process` independently verify that `request.shop` matches a shop the app has previously registered a webhook subscription for, rather than trusting the unauthenticated header value directly. At minimum, document and enforce that `WebhookMetadata#shop` must never be used for tenant-authorization decisions without an independent binding check.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and receives (or self-triggers) a legitimate webhook: body `B`, header `X-Shopify-Hmac-Sha256: HMAC(secret, B)`.
2. Attacker sends a POST to the app's webhook endpoint with the same body `B` and the same valid HMAC header, but replaces `X-Shopify-Shop-Domain: attacker-shop.myshopify.com` with `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate(request)` succeeds because it only checks `B` against the HMAC [5](#0-4) .
4. `Registry.process` builds `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` [4](#0-3)  and invokes the app's handler as if the (attacker-crafted) body genuinely originated from the victim shop.

```ruby
        sig { params(request: Request).void }
        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
```
