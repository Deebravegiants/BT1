### Title
IntentGatewayV2 (Tron) escrows the requested amount instead of the actual token balance received, breaking accounting for fee-on-transfer/deflationary/rebasing tokens - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
`placeOrder` in the Tron variant of `IntentGatewayV2` credits `_orders[commitment][token]` with the user-requested `order.inputs[i].amount` (minus protocol fee), but never verifies that this is the amount the contract actually received via `safeTransferFrom`. The mainline EVM `IntentGatewayV2.sol` was hardened against exactly this class of bug (fee-on-transfer support, verified by tests such as `testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived`), but the Tron port still has the old, unmeasured pattern.

### Finding Description
In the non-predispatch branch of `placeOrder`: [1](#0-0) 

the contract does:
```solidity
IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
_orders[commitment][token] += reducedInputs[i].amount;
```
`reducedInputs[i].amount` is derived purely from `order.inputs[i].amount` (the user-declared amount) minus the protocol fee percentage, computed *before* any transfer occurs: [2](#0-1) 

There is no `balanceOf` check before/after the `safeTransferFrom` to determine what the gateway actually received, unlike the fixed mainline EVM contract, whose equivalent branch explicitly re-measures the balance:
```solidity
uint256 balBefore = IERC20(token).balanceOf(address(this));
IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
order.inputs[i].amount = IERC20(token).balanceOf(address(this)) - balBefore;
``` [3](#0-2) 

The predispatch branch of the Tron contract does perform a `balanceOf`-based dust calculation for the dispatcher-forwarding step (lines 416-446), but the credited escrow amount there is still `reducedInputs[i].amount` (declared amount minus protocol fee), not the measured `balance` variable that was just computed — so even the "dust-aware" branch still escrows based on the declared amount rather than the true received amount: [4](#0-3) 

For any ERC20 with non-1:1 transfer semantics (fee-on-transfer, deflationary burn-on-transfer, or a rebasing token whose balance can shrink between the transfer and later inspection), the amount recorded in `_orders[commitment][token]` will exceed the token balance the gateway actually custodies for that specific order. Because `_orders` is a shared per-token ledger across all orders in the contract, this overstatement is not merely cosmetic — it inflates the contract's total claimed liabilities for that token beyond its actual token balance.

### Impact Explanation
This is directly analogous to the reported OpenQ issue: recording a nominal "volume" that diverges from actual custodied token balance for non-standard ERC20s. When the order is later filled/redeemed (`withdraw`, triggered via `onAccept`/`RedeemEscrow` or `cancelOrder`/`RefundEscrow`), the contract will attempt to pay out the escrowed (inflated) amount from its aggregate token balance. Since `_orders[commitment][token]` is over-credited relative to real holdings, this creates a shortfall that is paid for out of other users' escrowed balances of the same token — i.e., later orders using that same fee-on-transfer/rebasing token cannot be fully redeemed or refunded, resulting in a race where whoever redeems first drains real balance backing other users' legitimate escrows. This is a fund-freezing/loss-of-funds condition reachable directly from `placeOrder`, an unprivileged, permissionless entry point.

### Likelihood Explanation
Likelihood depends on whether any token registered/used with this Tron `IntentGatewayV2` deployment has fee-on-transfer, deflationary, or rebasing semantics. The mainline EVM contract's test suite explicitly anticipates and defends against fee-on-transfer tokens as a first-class concern for this protocol (`testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived`, `testPlaceOrder_FeeOnTransferToken_WithProtocolFee`), indicating the team already treats such tokens as an expected, in-scope input rather than an edge case. The Tron variant has no equivalent test or guard, so if the deployment is used with any such token, the shortfall is realized on every single `placeOrder` call using it.

### Recommendation
In `evm/tron/contracts/apps/IntentGatewayV2.sol`'s `placeOrder`, mirror the mainline EVM fix: measure `balanceOf(address(this))` immediately before and after each `safeTransferFrom` (or after the dispatcher-forwarding sweep) and use that delta — not the user-declared `order.inputs[i].amount` — as the basis for `reducedInputs`/`_orders[commitment][token]` credit and for the commitment hash. This ensures the escrow ledger for each order always matches what the gateway can actually redeem, for both the predispatch and non-predispatch code paths.

### Proof of Concept
1. Deploy `IntentGatewayV2` (Tron variant) with a token `T` that charges a 1% fee-on-transfer (or is otherwise non-standard, e.g. rebasing).
2. User A calls `placeOrder` with `order.inputs[0] = {token: T, amount: 1000}`. `safeTransferFrom` moves only 990 `T` into the gateway (fee burned), but `_orders[commitment][T]` is credited with ~1000 (minus protocol fee if any) — see lines 452-464 in `evm/tron/contracts/apps/IntentGatewayV2.sol`.
3. Repeat with User B placing another order for `T`.
4. The gateway's actual `T` balance is now less than the sum of `_orders[...][T]` across both orders (990+990 = 1980 actual vs 1000+1000=2000 recorded, roughly, before protocol fee).
5. When both orders attempt to be redeemed/cancelled via `withdraw`, the last one to redeem is unable to receive its full recorded escrow because insufficient `T` balance remains in the contract — either reverting (freezing funds) or, if `withdraw` doesn't itself re-check `balanceOf`, silently transferring less than owed / draining tokens meant for other users. (The exact behavior of `withdraw` under insufficient balance was not fully confirmed within available tool calls, since the function body could not be retrieved before the iteration limit; however, the over-crediting of `_orders` at `placeOrder` time is confirmed directly from the code shown.)
