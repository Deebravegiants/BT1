## Title
Webhook shop-domain field is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

## Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` value used to identify the tenant from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, but the HMAC signature validated by `Utils::HmacValidator` is computed only over the raw request body. The `shop` field that `Registry.process` hands to application handlers is therefore never bound to the cryptographic signature that "proves" the webhook is authentic, breaking the identity equality `shop authenticated == shop the signature actually covers`.

## Finding Description
`Registry.process` authorizes a webhook purely by validating the HMAC of the request: [1](#0-0) 

The HMAC check delegates to `Utils::HmacValidator.validate`, which recomputes the signature over whatever `to_signable_string` returns and compares it to the received `hmac` value: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` returns only the raw body — it does **not** include the shop domain, topic, or webhook id: [3](#0-2) 

Yet immediately after the HMAC check succeeds, `Registry.process` builds a `WebhookMetadata` object using `request.shop`, which is read straight from the unauthenticated header, and passes it to the app's handler as the tenant identifier: [4](#0-3) [5](#0-4) 

The equality that should hold is: `shop bound by the HMAC-verified signature == shop the handler uses to select/act on tenant data`. In this implementation that equality is `∅ (body) == shop-domain header`, i.e. the shop identity is never covered by the signature at all. `Registry.process` is the only in-scope entry point that turns raw, attacker-influenced headers into a "verified" `WebhookMetadata`, so any tenant scoping decision the host application makes off `data.shop` is only as trustworthy as an unauthenticated HTTP header.

## Impact Explanation
An attacker who owns/controls any Shopify store that has the target app installed (trivial to obtain via a free/dev store) will receive genuine, validly-signed webhook deliveries from Shopify for events in that store. Because the signature covers only the body, the attacker can take that exact signed body/HMAC pair and resend it to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. `Utils::HmacValidator.validate` will still pass (the body is unchanged and correctly signed with the app's real `api_secret_key`), and `Registry.process` will invoke the app's handler with `WebhookMetadata#shop` set to the victim's domain. Any app logic that trusts `data.shop` to scope database writes, trigger notifications, or reconcile records for that tenant will act on attacker-supplied content under the wrong tenant identity — a cross-tenant access/data-integrity breach that requires no credentials belonging to the victim shop.

## Likelihood Explanation
Exploitation only requires: (1) installing the target app on any shop the attacker controls (trivially available for any public app), and (2) the ability to replay an HTTP request with a modified header, which does not require breaking cryptography or possessing the app's `client_secret`. The library provides no shop-domain binding or allow-listing to mitigate this, so any consuming app that follows the gem's documented `Registry.process` usage exactly as shown in `docs/usage/webhooks.md` inherits the exposure.

## Recommendation
Bind the shop domain (and ideally topic/webhook id) into the HMAC-signable content, or otherwise cryptographically bind them, e.g. by including the relevant headers in `to_signable_string`, or by requiring/validating that `request.shop` matches a shop for which the app holds an active, previously-authenticated session/access token before invoking the handler. At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must be cross-checked by the host application against its own store of installed shops before being trusted for tenant-scoped operations.

## Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and triggers a webhook event (e.g. `orders/create`) in their own store.
2. Shopify delivers a genuine POST to the app's webhook endpoint with body `B` and header `X-Shopify-Hmac-Sha256: HMAC(secret, B)`, plus `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker intercepts/replays this exact request but changes only the `X-Shopify-Shop-Domain` header to `victim-shop.myshopify.com`, leaving `B` and the HMAC header untouched.
4. `ShopifyAPI::Webhooks::Registry.process` is called with a `Request` built from these headers:
   - `Utils::HmacValidator.validate(request)` recomputes `HMAC(secret, B)` — matches, validation passes (`lib/shopify_api/utils/hmac_validator.rb` lines 12-31; `lib/shopify_api/webhooks/request.rb` lines 35-38).
   - `request.shop` returns `"victim-shop.myshopify.com"` (`lib/shopify_api/webhooks/request.rb` lines 20-23).
   - The registered handler is invoked with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)` (`lib/shopify_api/webhooks/registry.rb` lines 196-200), even though the payload originated entirely from the attacker's own shop.
5. Any application logic keyed off `data.shop` now processes attacker-controlled content as if it belongs to `victim-shop.myshopify.com`.
