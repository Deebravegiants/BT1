## Title
Webhook shop-domain identity binding bypass via HMAC that only covers the request body - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) from an HTTP header, but the HMAC signature validated by `ShopifyAPI::Utils::HmacValidator` is computed only over the raw request body. This breaks the binding `HMAC-verified bytes == bytes the app trusts for tenant attribution`, allowing a caller who already possesses one valid `(body, hmac)` pair for a shared app secret to relabel that payload as belonging to a different shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is never included in the signable string: [2](#0-1) 

`HmacValidator.validate` only recomputes the HMAC over `verifiable_query.to_signable_string` (i.e., the body) and compares it against the `hmac` header: [3](#0-2) 

`Registry.process` performs this body-only HMAC check and then, if it passes, hands the *unverified* `request.shop` straight to the host application's handler as the tenant identifier: [4](#0-3) 

Because Shopify apps share a single `api_secret_key` across every installed shop, a party that has legitimately received one webhook delivery for shop A (with a valid `body`/`hmac` pair) can resend the identical body and hmac to the app's webhook endpoint while substituting the `shop-domain` header for shop B. `HmacValidator.validate` will still succeed (it never looks at the shop header), and `Registry.process` will pass `shop: "B"` to the handler even though the signed body was never produced for shop B. This is exactly the "field acted on but not covered by HMAC" class of bug: `request.shop` is *acted on* (used as the tenant key by the handler) but not *covered* by the cryptographic check that gates that action.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook delivery: an app relying on `WebhookMetadata#shop` (as populated by `Registry.process`) to scope data writes/reads per merchant can be made to apply shop-A's webhook payload to shop-B's tenant context, i.e., cross-tenant data corruption/access — a Critical-impact category per the given classification (cross-tenant access), reached purely through crafted HTTP requests to the app's public webhook endpoint, with no access token or secret required.

### Likelihood Explanation
Exploitation requires the attacker to obtain at least one legitimate `(body, hmac)` pair, which is trivial for any merchant/attacker who has their own shop install the vulnerable app (webhook deliveries are sent to app-controlled endpoints, so the attacker's own shop naturally receives valid signed payloads). Replaying that pair with a different `shop-domain` header against the same shared endpoint is a simple, repeatable HTTP request — no cryptographic material or privileged access is needed.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) values in the HMAC-signable content, or otherwise cryptographically bind the shop-domain header to the signed body (e.g., verify the header against a topic/shop pair returned by Shopify's official webhook signature scheme, or require the host app to reconcile `shop` against a value independently obtained from a store/session lookup rather than trusting the header outright). At minimum, document that `request.shop` is unauthenticated and must not be used as the sole tenant-scoping key without additional verification.

### Proof of Concept
1. App installs on `shop-a.myshopify.com`; Shopify delivers a webhook with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(secret, B)`.
2. Attacker (who controls `shop-a`, e.g. via their own dev store) captures `(B, H)`.
3. Attacker POSTs to the same app's shared webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H` (unchanged), but `x-shopify-shop-domain: shop-b.myshopify.com`.
4. `HmacValidator.validate` recomputes HMAC over `B` only and succeeds: [5](#0-4) 
5. `Registry.process` invokes the handler with `WebhookMetadata.new(... shop: "shop-b.myshopify.com" ...)` even though `B` was never signed for `shop-b`: [6](#0-5) 
6. Any host-app logic keyed on `data.shop` now processes shop-A's payload under shop-B's tenant context.
