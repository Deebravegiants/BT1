### Title
Webhook shop-domain identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` trusts the `shop` (from the `x-shopify-shop-domain`/`shopify-shop-domain` header) to attribute an incoming webhook to a tenant, but the HMAC signature validated by `Utils::HmacValidator` only covers the raw request body, not this header. An attacker who can obtain a validly-signed webhook for their own shop can replay it against the app's webhook endpoint with a forged `shop`/`topic` header and have it accepted and processed as if it belonged to a victim tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop`, `topic`, `api_version`, and `webhook_id` are all read straight from HTTP headers that are never included in the signed content: [2](#0-1) 

`Utils::HmacValidator.validate` computes and compares the HMAC solely against `to_signable_string` (i.e. the body): [3](#0-2) 

`Registry.process` only checks this body-only HMAC before dispatching the webhook, and then forwards the unauthenticated `request.shop` value straight to the app's handler as the tenant identity for the event: [4](#0-3) 

The header presence check in the constructor only verifies that a `shop-domain` header exists, not that it is bound to the signature: [5](#0-4) 

This breaks the identity binding: `shop` used by the signature (∅, not present) ≠ `shop` trusted by the handler (header value). Concretely, Shopify signs a webhook’s HMAC using the app's `client_secret` over the body only. Any user who installs the app on their own store (a normal, unprivileged action) can trigger an event, capture the legitimately-signed `(body, hmac)` pair from Shopify's real delivery, and then re-POST that exact body/hmac pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and optionally `x-shopify-topic`) header with a victim shop's domain. Because neither header is part of the signed content, `HmacValidator.validate` still succeeds, and `Registry.process` dispatches the payload to the handler tagged with the victim's shop, exactly matching the report's bug class: an identity field ("shop") is acted upon by downstream logic but is not covered by the cryptographic binding (HMAC) meant to authenticate the request.

### Impact Explanation
Any handler implemented on top of `WebhookMetadata#shop` (e.g. updating per-tenant state, revoking access, provisioning resources, writing to a tenant-scoped datastore) can be manipulated into acting on behalf of an arbitrary victim shop using attacker-controlled webhook content. This is a cross-tenant access issue: an unprivileged user (who can install/trigger events on any shop, including their own trial store) can make the app believe an event with attacker-influenced content originated from a different tenant.

### Likelihood Explanation
Exploitation only requires the ability to install the target app (or any app sharing the client_secret/environment) on an attacker-controlled shop and trigger any webhook topic, then capture and replay the signed body with a modified shop/topic header to the public webhook endpoint. No access to the app's `client_secret`, access tokens, or victim credentials is required, only network access to the app's public webhook URL, which is inherent to how Shopify webhook endpoints must be exposed.

### Recommendation
Bind the shop (and ideally topic) to the signed content, or otherwise cryptographically or out-of-band verify that the shop-domain header actually corresponds to the shop that Shopify signed the payload for (e.g., look up the specific shop's own webhook secret/session before trusting `request.shop`, or include header values in `to_signable_string` if Shopify's webhook signing scheme is updated to support it). At minimum, document that `request.shop` must not be treated as authenticated by the HMAC and require host applications to independently corroborate the shop identity (e.g., against known installed shops) before acting on webhook data.

### Proof of Concept
1. Install the target app on an attacker-owned shop `attacker.myshopify.com`.
2. Trigger a webhook event (e.g. `shop/update`) so Shopify sends a POST to the app's webhook endpoint with a body `B` and a valid `x-shopify-hmac-sha256` computed as `HMAC-SHA256(client_secret, B)`.
3. Intercept/capture `(B, hmac)`.
4. Replay a new POST to the same endpoint with the same `B` and `hmac`, but with `x-shopify-shop-domain: victim.myshopify.com` (and topic changed if desired).
5. `ShopifyAPI::Utils::HmacValidator.validate` succeeds because it only checks `B` against `hmac`; `ShopifyAPI::Webhooks::Registry.process` dispatches to the handler with `shop: "victim.myshopify.com"`, causing the app to process attacker-supplied content as if it were an authentic event from the victim shop.

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
