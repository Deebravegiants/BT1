### Title
Webhook `shop` (and `topic`/`api_version`/`webhook_id`) attributes are not covered by the HMAC signature, allowing tenant spoofing of processed webhook data - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw request body only, while the `shop`, `topic`, `api_version`, and `webhook_id` attributes are taken from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` validates only the body's HMAC and then forwards the header-derived `shop` value to the app's webhook handler as trusted tenant identity.

### Finding Description
`Request#to_signable_string` returns `@raw_body` exclusively: [1](#0-0) 

But `Request#shop`, `#topic`, `#api_version`, and `#webhook_id` are read directly from request headers, none of which participate in `to_signable_string`: [2](#0-1) 

`Registry.process` validates the HMAC using `Utils::HmacValidator.validate(request)`, which calls `verifiable_query.to_signable_string` (the raw body) and compares it against `Context.api_secret_key`: [3](#0-2) 

After this check passes, `Registry.process` immediately forwards the header-derived, unauthenticated `request.shop` value into `WebhookMetadata`, which is delivered to the app's handler as the identity of the shop that "owns" the webhook payload: [4](#0-3) 

The identity binding that should hold is: `hmac == HMAC(secret, shop ++ topic ++ body)`, i.e., the `shop` attribute acted upon by the handler should equal the `shop` value that was actually covered by the signature. Instead, the equality that is actually enforced is only `hmac == HMAC(secret, body)`, with `shop` sourced from an entirely separate, unsigned channel (`X-Shopify-Shop-Domain` / `Shopify-Shop-Domain` header). The `client_secret` is shared across every shop that installs the app (it is not shop-specific), so any two shop installations of the same app share the same signing key.

### Impact Explanation
An unprivileged attacker who can install the target app on their own store (as any merchant can) receives legitimate webhook deliveries (body + valid HMAC) signed with the app's shared `client_secret`. The attacker can then replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `shop-domain` header with a victim shop's domain. Because the HMAC only covers the body, validation succeeds, and the app's webhook handler will process/act on the payload believing it belongs to the victim shop — a cross-tenant data/identity confusion. Depending on how host apps use `WebhookMetadata#shop` (e.g., writing to per-shop state, triggering shop-scoped side effects, or resolving credentials via `shop`), this can enable cross-tenant data corruption or actions performed against the wrong tenant.

### Likelihood Explanation
Requires the attacker to have their own installation of the target app (any Shopify merchant can install a public app), and requires the host application to trust `WebhookMetadata#shop` for tenant-scoped logic without independent verification — a very common integration pattern (mirrors the shopify_app gem's reliance on this field). No leaked secrets or privileged access are needed.

### Recommendation
Include `shop`, `topic`, `api_version`, and `webhook_id` in the signable string used for HMAC validation (or otherwise cryptographically bind the header-derived attributes to the signed payload), so that any tampering with these headers invalidates the HMAC check. Alternatively, document/enforce that consumers must not trust `WebhookMetadata#shop` unless it's cross-checked against a shop obtained through an authenticated channel.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com`, completing OAuth normally.
2. Attacker triggers a webhook event (e.g., updates a product) and captures the resulting POST request Shopify sends to the app's webhook endpoint, including the raw body and the `X-Shopify-Hmac-Sha256` header (a valid HMAC of the body computed with the app's `client_secret`).
3. Attacker resends the exact same body and HMAC header to the same webhook endpoint, but replaces `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(secret, raw_body)` — this still matches, since the body and secret are unchanged.
5. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...)`, i.e., attacker-controlled data is processed as if it originated from `victim-shop.myshopify.com`. [5](#0-4)

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
