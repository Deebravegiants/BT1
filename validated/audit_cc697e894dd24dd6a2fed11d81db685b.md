### Title
`wallet.changePassphrase()` silently strips wallet password protection when `newPassphrase` is omitted/undefined - (File: `features/wallet/module/wallet.js`)

### Summary
The external report's bug class is "a privileged setter function silently treats a missing/undefined required parameter as a meaningful falsy value (zero address), destroying a protection the caller did not intend to remove." The closest reachable analog in this wallet codebase is `Wallet#changePassphrase` in `features/wallet/module/wallet.js`, which treats a missing `newPassphrase` the same way `#setSeed` treats an intentional password removal, silently disabling password protection on the wallet seed.

### Finding Description
`changePassphrase({ currentPassphrase, newPassphrase })` [1](#0-0)  unpacks `newPassphrase` from its input with no presence/type validation, then forwards it directly into `#setSeed({ seed, passphrase: newPassphrase })`.

Inside `#setSeed`, the `passphrase` argument is treated as a boolean branch selector rather than a required credential: [2](#0-1) 

If `newPassphrase` is falsy (`undefined`, `''`, `null`) — exactly the situation the InstaRegistry report warns about, where a front-end fails to supply the value and it collapses to the "empty"/default value — the `else` branch executes: `HAS_USER_SET_PASSPHRASE_KEY` is set to `false` and (if `useAutoGeneratedPassword` is enabled) a new auto-generated passphrase is silently created and stored, effectively removing the user's chosen password protection from the seed, with the assertion at the top only checking `currentPassphrase` correctness, not `newPassphrase` presence.

The public API surfaces this function with no additional guard: `walletApiDefinition` exposes `wallet.changePassphrase` unmodified [3](#0-2) , and the higher-level `Application#changePassphrase` in `features/application/src/modules/application.ts` passes `newPassphrase` straight through without validating it is non-empty [4](#0-3) . The TypeScript type `WalletChangePassphraseParams` declares `newPassphrase: string` as required [5](#0-4) , but this is a compile-time-only guarantee; any JS caller (SDK caller, extension UI failing to bind a field, or a malformed IPC/RPC message from the extension UI process to the background) that omits the field or passes `undefined`/`''` will reach the vulnerable branch at runtime.

### Impact Explanation
Successfully triggering this path removes the user-set passphrase protecting the wallet seed (`HAS_USER_SET_PASSPHRASE_KEY` → `false`, optionally replaced by an internally generated, non-user-known passphrase). Since `#getSeed` will thereafter automatically use `#getGeneratedPassphrase()` for decryption whenever `useAutoGeneratedPassword` is enabled, the seed becomes retrievable/usable without the user's real password, which is a direct wallet-compromise / secret-disclosure risk analogous to burning the admin/owner protection in the InstaRegistry report — the "privilege" here being the requirement of a user-known passphrase to unlock/export the mnemonic.

### Likelihood Explanation
This requires either a caller bug (UI/SDK invoking `changePassphrase` with a missing `newPassphrase` field, e.g., due to an unbound form field or omitted required parameter, exactly the failure mode described in the referenced report) or a malformed/incomplete message across a process boundary (extension background/UI, or SDK/headless boundary) that already passed `currentPassphrase` verification. There is no server-side/runtime assertion forcing `newPassphrase` to be a non-empty string, so the failure is silent (no thrown error) rather than caught, increasing the chance it goes unnoticed until the account is compromised.

### Recommendation
Add an explicit runtime assertion in `changePassphrase` (and/or `#setSeed`) requiring `newPassphrase` to be a non-empty string when `#usePassword` is enabled, e.g. `assert(typeof newPassphrase === 'string' && newPassphrase.length > 0, 'newPassphrase is required')`, mirroring the existing `assertMnemonic`/`assert` patterns already used elsewhere in `wallet.js`. This prevents the "empty input silently downgrades security" failure mode while still allowing an explicit, intentional flow (if one is desired) to remove password protection via a differently-named, clearly-labeled method.

### Proof of Concept
1. Unlock a password-protected wallet with `usePassword: true` and (optionally) `useAutoGeneratedPassword: true`.
2. Call `exodus.wallet.changePassphrase({ currentPassphrase: '<correct current password>' })` (omitting `newPassphrase`, or passing `newPassphrase: undefined`/`''`), e.g. via the headless SDK or a malformed extension UI request.
3. Observe in `features/wallet/module/wallet.js` `#setSeed` that the `else` branch runs: `HAS_USER_SET_PASSPHRASE_KEY` is set to `false`, and a new `GENERATED_PASSPHRASE_KEY` may be created and stored.
4. Verify `wallet.hasPassphraseSet()` now returns `false` even though the user never intended to remove their password, and `wallet.getMnemonic()`/`unlock()` can subsequently succeed without the previously-set passphrase whenever the auto-generated passphrase path is used.
