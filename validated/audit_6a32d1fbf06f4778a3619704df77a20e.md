The pallet-ismp `execute()` path treats a single app-level rejection (an `IsmpModule::on_accept`/`on_response` returning `Err`, which the protocol documents as a graceful, per-request, retryable outcome) as a fatal error that reverts the *entire* batched extrinsic — exactly the same bug class as the ERC-777 sending-hook DoS on `batchSend()`, where one hostile/reverting recipient blocks processing of everyone else's payload.

### Title
Single rejecting `on_accept`/`on_response` callback DoSes the entire `handle_unsigned` batch, reverting delivery and fee accounting for unrelated valid messages - (File: `modules/pallets/ismp/src/impls.rs`)

### Summary
`pallet-ismp`'s unsigned, permissionless `handle_unsigned` extrinsic (`modules/pallets/ismp/src/lib.rs`) accepts a `Vec<Message>`, each of which may itself carry a batch of `PostRequest`s/`GetResponse`s verified under one membership multiproof. Per-request module callback failures are documented as benign/retryable (the request's receipt is simply deleted so it can be replayed), but `Pallet::execute()` aggregates *all* per-request outcomes from *all* messages in the call and fails the whole extrinsic if even one of them errored, and the call is `#[frame_support::transactional]`, so this reverts every state change for every other, otherwise-successful message in the same batch.

### Finding Description
`modules/ismp/core/src/handlers/request.rs::handle()` deliberately isolates each request's `on_accept` outcome as a per-item `Result` rather than short-circuiting the whole message: [1](#0-0) 
A failing `on_accept` only deletes that request's receipt so it "can be timed out"/retried — this is documented as intentional in `docs/content/protocol/ismp/requests.mdx`: [2](#0-1) 
`modules/ismp/core/src/handlers/response.rs::handle()` follows the identical per-item pattern for `on_response`.

However, `Pallet::<T>::execute()` (called from `handle_unsigned`) collapses this designed-to-be-per-item granularity into an all-or-nothing outcome for the *entire batch of messages* submitted in one extrinsic: [3](#0-2) 
The `.flatten().collect::<Result<Vec<_>, _>>()?` on line 71 turns a single `Err` event from any one request/response callback anywhere in the batch into `Error::InvalidMessage`, aborting `execute()` before `T::FeeHandler::on_executed` is ever invoked (line 78) and before any events are deposited (lines 81-84).

`handle_unsigned` is marked `#[frame_support::transactional]`: [4](#0-3) 
so the whole extrinsic's storage effects — including request/response receipts that were successfully stored for other, unrelated messages, MMR pushes, etc. — are rolled back when `execute()` returns an `Err`, exactly as the `#[transactional]` attribute intends.

Since `handle_unsigned` is unsigned (`ensure_none`) and free for anyone to submit valid proofs, and a single `RequestMessage`/`ResponseMessage` — or the outer `Vec<Message>` — can bundle many independent requests/responses destined for many different destination modules, an attacker only needs to control one destination module (`request.to`) that always returns `Err` from `on_accept` (or `on_response`). Any relayer that batches a request targeting that module together with other legitimate/valuable requests in the same `handle_unsigned` call will have the *entire* extrinsic fail, and — because it's transactional — nothing in that batch gets delivered, and `FeeHandler::on_executed` never runs, so no fees are collected for the honest requests either.

### Impact Explanation
This is a denial-of-service on message delivery, the same class explicitly in scope ("pallet-ismp handle_unsigned"). Concretely:
- An attacker-controlled malicious module can force reprocessing/retry of an unbounded number of unrelated, legitimate cross-chain requests/responses simply by ensuring their own rejecting request rides along in the same batch (which the attacker can arrange since dispatching a request to any `to` module is permissionless on the source chain).
- Relayers lose the batching efficiency the protocol is built around (per `HandlerV2.batchCall`/`generate_batched_contract_calls` design intent on the EVM side, and multiproof batching here) since any single hostile message forces full-batch retries.
- No fees are ever accrued via `FeeHandler::on_executed` for the batch when this happens, griefing relayer economics and delaying delivery of otherwise valid, possibly time-sensitive/timeout-bound messages.

This does not, by itself, achieve permanent freezing (relayers can retry with different batch composition), but it is a reliable, cost-free griefing vector on the delivery route, matching the report's "unable to deliver messages" impact class.

### Likelihood Explanation
High. Deploying a destination module/pallet handler that always errors on `on_accept`/`on_response` requires no privilege, and dispatching a request/response destined to that module is a normal, unprivileged ISMP action. Batching heuristics used by relayers are aimed at maximizing per-extrinsic throughput, which is precisely what makes this attack cheap to trigger repeatedly against live relayer batches.

### Recommendation
Do not let a single rejected `on_accept`/`on_response` event fail the whole `execute()` call. Instead of `.collect::<Result<Vec<_>, _>>()?` over the flattened per-request events, retain the individual `Err`s as normal (non-fatal) outcomes — e.g. filter/log rejected items and deposit them as an `Event::Errors`-equivalent while still crediting fees and depositing events for the requests/responses that succeeded. Only genuinely fatal, message-level failures (bad proof, unknown state machine, frozen client, etc., which are already surfaced by the first `collect::<Result<Vec<_>, _>>()?` at line 46) should abort the whole extrinsic.

### Proof of Concept
1. Deploy/register a destination module `M` whose `on_accept` (or `on_response`) implementation unconditionally returns `Err(..)`.
2. Dispatch a `PostRequest` (or `GetRequest`) with `to = M` from any source chain — this is a normal, permissionless ISMP dispatch.
3. Wait for a relayer to include this request in a `handle_unsigned` batch alongside other pending, legitimate requests/responses (or submit the batch yourself with a crafted `Vec<Message>` containing the request to `M` plus other valid requests you want to block).
4. Observe that `Pallet::execute()` returns `Error::InvalidMessage` because the flattened events collection at `modules/pallets/ismp/src/impls.rs:71` hits the `Err` from `M`'s callback; the `#[transactional]` `handle_unsigned` call then reverts all storage changes for every request/response in the batch, and no fees are charged via `FeeHandler::on_executed`.
5. Repeat with any batch composition that includes a request to `M` to reliably block delivery of everything bundled with it.
