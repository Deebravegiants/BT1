### Title
Webhook `shop` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook as authentic once `Utils::HmacValidator.validate(request)` succeeds, and then forwards `request.shop` (the tenant identity) straight to the app's handler as trusted data. However the HMAC only covers the request body — the `shop-domain` header is never part of the signed bytes — so the "verified" signature does not actually bind the shop identity that the gem hands to the app.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Webhooks::Request#shop` is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header, with no cryptographic binding to the body or to the HMAC: [2](#0-1) 

`HmacValidator.validate` computes the signature only over `to_signable_string` (the raw body) and compares it to the `hmac` field: [3](#0-2) 

`Registry.process` uses this HMAC check as the sole authenticity gate, then immediately trusts `request.shop` and passes it to the handler as the tenant identifier: [4](#0-3) 

The identity binding that should hold is:
`shop header used to attribute the webhook == shop over which the HMAC was computed`

In this gem it does not: `hmac == HMAC(raw_body, client_secret)` while `shop == header("shop-domain")`, two independent, unlinked fields. Anyone who possesses one validly-signed `(raw_body, hmac)` pair for any shop — e.g. their own app-installed test store, which they fully control and can trigger webhooks from — can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header. `HmacValidator.validate` will still return `true` (it never looks at headers), and `Registry.process` will call the app's handler with `WebhookMetadata.shop` set to the attacker-chosen victim domain, documented and consumed by apps precisely for tenant attribution: [5](#0-4) [6](#0-5) 

The gem's own documentation instructs apps to trust `data.shop` from a "verified" webhook (`Registry.process ... will verify the request did indeed come from Shopify"`), so the false sense of a validated tenant binding is baked into the library's contract, not merely a host-app mistake.

### Impact Explanation
This lets an attacker with one legitimately-signed webhook body (obtainable from any store they control, including a free development store) attribute that webhook's data/event to any other shop domain of their choosing, because the gem exposes `request.shop` as trusted, HMAC-verified data when it is in fact an unauthenticated header. Depending on how the host app keys its per-shop side effects off `WebhookMetadata.shop` (e.g. `shop/redact`, `app/uninstalled`, `customers/data_request` mandatory topics, or ordinary business webhooks), this enables cross-tenant confusion: triggering another merchant's uninstall/redaction/data flows, or injecting attacker body content that is falsely associated with a victim's account for topics whose body content is not itself shop-specific. This matches the Critical "cross-tenant access" bucket in scope, since it breaks the shop-to-signature binding that the gem is supposed to provide.

### Likelihood Explanation
Any developer who has registered even one HTTP webhook for their own shop (trivial, self-service, no privileged Shopify credentials needed) can capture a raw `(body, hmac)` pair from their own genuine deliveries and replay it against the target app's public webhook endpoint with a forged `shop-domain` header. No access token, `client_secret`, or victim credentials are required — only the ability to send an HTTP POST to the app's already-public webhook URL, which satisfies the "unprivileged internet user" bar.

### Recommendation
Bind the shop identity into the verified signable bytes, or otherwise re-derive/validate the shop out-of-band (e.g., cross-check `request.shop` against the shop associated with the session/webhook_id via a server-side lookup) before exposing it as trusted metadata. At minimum, `Utils::HmacValidator`/`Webhooks::Request` should not silently let apps treat `WebhookMetadata.shop` as authenticated when only the body has been verified; the gem should document this gap explicitly or extend `to_signable_string` to include the header value it purports to authenticate.

### Proof of Concept
1. Attacker owns/operates `attacker.myshopify.com` with the target app installed and one webhook topic registered (e.g. `orders/create`).
2. Attacker triggers that webhook normally; Shopify sends a POST with `x-shopify-hmac-sha256: H` computed as `HMAC-SHA256(raw_body, client_secret)` and `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker captures `raw_body` and `H`, then sends a new POST to the same app endpoint with identical `raw_body`/`H`, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(raw_body, client_secret)` and compares only against `H` — passes, since body is unchanged. [4](#0-3) 
5. `handler.handle` is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)`, and the app processes the (attacker-supplied) body as if it belonged to `victim.myshopify.com`.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
