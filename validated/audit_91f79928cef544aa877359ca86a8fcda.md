### Title
Webhook Shop-Domain Header Is Not Covered by HMAC Verification, Enabling Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while the tenant-identifying `shop` (and `topic`, `webhook_id`, `api_version`) are read directly from HTTP headers that are never included in the HMAC-signed payload. `Registry.process` trusts these header-derived fields to route the webhook to a handler and to populate `WebhookMetadata`, which the host app uses to attribute the event to a specific shop.

### Finding Description
The HMAC binding enforced by this gem is:

`HMAC_valid(raw_body) == true`

but the actual trust decision made by `Registry.process` binds a much larger set of fields to that verification result:

`(shop, topic, webhook_id, api_version, body)` are all trusted once `HMAC_valid(raw_body)` passes.

Concretely:
- `Request#hmac` computes the signature from the `hmac-sha256` header value [1](#0-0) .
- `Request#to_signable_string` — the string that `HmacValidator` actually verifies against — is only `@raw_body` [2](#0-1) .
- `Request#shop`, `#topic`, `#webhook_id`, `#api_version` are all pulled straight from HTTP headers with no cryptographic binding to the HMAC [3](#0-2) .
- `Registry.process` validates only the body via `Utils::HmacValidator.validate(request)`, then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` to build `WebhookMetadata` passed to the app's handler [4](#0-3) .
- `HmacValidator.validate` / `validate_signature` only ever operate on `verifiable_query.to_signable_string`, i.e., the body, never the headers [5](#0-4) .

Because the `shop-domain` header sits outside the signed material, an attacker who has ever received one genuine, correctly-signed webhook for *any* shop (e.g., by installing the app on their own shop) can capture that `raw_body` + `hmac-sha256` header pair and replay it against the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header (and, independently, the `topic`/`webhook-id` headers) with a value naming a different, victim shop. `HmacValidator.validate` will still return `true` because it only recomputes the HMAC over the untouched body, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the event belongs to the attacker-chosen shop.

This is exactly the disallowed-in-report class explicitly called out in the rules: "a field acted on but not covered by the HMAC."

### Impact Explanation
This crosses a tenant boundary: the app-level webhook handler is invoked believing the event originated from and pertains to a shop the attacker does not control (`request.shop` in `WebhookMetadata`). Depending on the host app's handler logic (e.g., updating shop-scoped records, marking a shop as uninstalled/redacted, or triggering GDPR redact flows for `shop/redact`), this can lead to cross-tenant data corruption or spoofed lifecycle events for a victim shop — a cross-tenant access impact.

### Likelihood Explanation
Requires the attacker to possess one legitimate, correctly-signed webhook body+HMAC pair, which is trivially obtainable by installing the app on any shop they control (an ordinary, unprivileged action) and capturing an inbound webhook. No `api_secret_key`, access token, or privileged account is required to perform the replay itself — only knowledge of the app's public webhook endpoint and one previously observed valid webhook.

### Recommendation
**Short term:** Include the identity-critical headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signable string used for HMAC verification, or independently verify that the shop asserted in the header matches an expected/registered shop before dispatching to the handler.

**Long term:** Document and enforce that `Registry.process` cross-checks header-derived identity fields against out-of-band state (e.g., the shop the webhook subscription was registered for) rather than trusting them solely because the body's HMAC validated.

### Proof of Concept
1. Install the app on an attacker-owned shop `attacker.myshopify.com` and capture a genuine inbound webhook request, including its raw body and the `X-Shopify-Hmac-Sha256` header.
2. Replay the exact same raw body and `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, but change `X-Shopify-Shop-Domain` to `victim.myshopify.com` (and optionally `X-Shopify-Topic`/`X-Shopify-Webhook-Id`).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` which recomputes the HMAC solely over `raw_body` and returns `true` [6](#0-5) .
4. The handler is invoked with `WebhookMetadata.new(... shop: request.shop ...)` where `request.shop` is `"victim.myshopify.com"`, even though the signed body/HMAC pair actually corresponds to the attacker's own shop [7](#0-6) .

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
