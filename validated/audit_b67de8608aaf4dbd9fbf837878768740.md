### Title
Excess native ETH sent to `EvmHost.dispatch()`/`fundRequest()` is refunded into the Host contract instead of the caller, permanently trapping user funds - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` all accept native ETH via `msg.value` and swap it for the exact fee-token amount required using `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(...)`. Any leftover ETH from that swap ("dust") is refunded by the router to `msg.sender` of the swap call — which is `EvmHost` itself, not the original transaction caller. The excess ETH therefore becomes stuck inside `EvmHost`, is never returned to the depositor, and is not tracked against any specific request/fee metadata.

### Finding Description
In `EvmHost.sol`, the three payable entry points that accept native token payment for fees are implemented identically: [1](#0-0) [2](#0-1) [3](#0-2) 

In each case, `swapETHForExactTokens{value: msg.value}(fee, path, address(this), ...)` is called. Uniswap V2's `swapETHForExactTokens` only consumes `amounts[0] <= msg.value` and refunds `msg.value - amounts[0]` to its caller — here that caller is `EvmHost`, not `_msgSender()` of the original `dispatch`/`fundRequest` call. `EvmHost` never forwards this refunded dust back out; there is no code path after the swap that checks for or returns unspent ETH to the user.

This is the exact analog of the reported `Allo::fundPool()` bug: a user overpays with `msg.value` believing the excess will either be refunded or applied toward the deposit, but the excess silently accumulates inside the receiving contract with no accounting of who sent it or how much is owed back.

The only way to move ETH out of `EvmHost` afterward is the privileged `withdraw()` function, restricted to `hostManager` (cross-chain governance): [4](#0-3) 

Regular users/apps calling `dispatch()` or `fundRequest()` have no way to reclaim their overpaid ETH — it is not tracked per-sender, so even governance could not correctly refund the rightful owner; it is simply swept as generic "host revenue."

Contrast this with the correct pattern implemented elsewhere in the codebase (`IntentGatewayV2.placeOrder`/`fillOrder` and `ExtrinsicIntents`/`IntentsBase._sendValue`), which explicitly track `msgValue -= amounts[0]` after the swap and refund the remainder to `msg.sender`: [5](#0-4) 

`EvmHost.sol` lacks this same remainder-refund logic.

### Impact Explanation
Any unprivileged caller — a message dispatcher, relayer, `HyperApp`, or any contract/app forwarding `msg.value` to `IDispatcher(host()).dispatch{value: msg.value}(...)` as shown throughout the docs (`post-requests.mdx`, `get-requests.mdx`) — will lose any ETH sent beyond what the Uniswap swap consumes for the exact fee amount. Because native-token fee payment intentionally over-provisions `msg.value` (callers are told to "send enough native tokens to cover fees," and exact swap amounts fluctuate with AMM price), overpayment is the expected/common case, not an edge case. The lost ETH is not refunded, not credited to any request, and only recoverable via privileged governance `withdraw()`, which sends it to an arbitrary beneficiary — not the original depositor. This is a concrete, permanent loss of user funds.

### Likelihood Explanation
High. Every dispatch of a POST or GET request paid for in native token, and every `fundRequest` call paid in native token, goes through this vulnerable path. Given AMM price is variable, exactly matching `msg.value` to the true swap cost is impractical for callers, so overpayment (and thus fund loss) will occur routinely in normal, honest usage — no adversarial conditions are required.

### Recommendation
After each `swapETHForExactTokens` call in `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest`, capture the `amounts` returned (or compute `msg.value - amounts[0]`) and refund the difference back to `_msgSender()`, mirroring the pattern already used in `IntentGatewayV2.sol` / `IntentsBase.sol`:
```solidity
uint256[] memory amounts = IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
    post.fee, path, address(this), block.timestamp
);
uint256 refund = msg.value - amounts[0];
if (refund > 0) {
    (bool sent, ) = _msgSender().call{value: refund}("");
    if (!sent) revert RefundFailed();
}
```

### Proof of Concept
1. `feeToken` price relative to native ETH fluctuates; a `HyperApp` estimates `nativeFee` client-side and adds a safety margin, calling:
   `IDispatcher(host()).dispatch{value: estimatedFee}(post)` where `estimatedFee > actualRequiredNative`.
2. Inside `EvmHost.dispatch`, `swapETHForExactTokens{value: estimatedFee}(post.fee, path, address(this), block.timestamp)` swaps only `amounts[0] < estimatedFee` worth of ETH for the exact `post.fee` in fee tokens.
3. The Uniswap V2 router refunds `estimatedFee - amounts[0]` to `msg.sender`, i.e., to `EvmHost`'s own address (since `EvmHost` invoked the router).
4. `EvmHost.dispatch` returns without ever forwarding this refunded dust to `_msgSender()` (the original caller); the ETH remains part of `address(EvmHost).balance`, unaccounted for and unreachable by the caller.
5. The only extraction path is `EvmHost.withdraw()`, callable solely by `hostManager` via cross-chain governance, which sends the pooled ETH to an arbitrary beneficiary unrelated to the original overpaying caller — the user's excess ETH is permanently lost to them.

     * @dev withdraws host revenue to the given address, can only be called by cross-chain governance
     * @param params, the parameters for withdrawal

    function withdraw(WithdrawParams memory params) external restrict(_hostParams.hostManager) {
        if (params.token == address(0)) {
            // this is safe because re-entrancy is mitigated before dispatching requests
            (bool sent,) = params.beneficiary.call{value: params.amount}("");
            if (!sent) revert WithdrawalFailed();
        } else {
            IERC20(params.token).safeTransfer(params.beneficiary, params.amount);
        }
        emit HostWithdrawal({beneficiary: params.beneficiary, amount: params.amount, token: params.token});
    }
