### Title
Polygon confirmation-depth ceiling of 5 blocks is insufficient to guard cross-chain intent fills against reorgs, allowing a gamed/vanished order to drain the solver's destination-chain capital - (File: sdk/packages/simplex/src/config/interpolated-curve.ts)

### Summary
Simplex's `DEFAULT_CONFIRMATION_POLICIES` caps the Polygon (`chainId 137`) confirmation requirement at only 5 blocks for orders up to $100k, on the theory that Polygon "milestone finality lands in ~5s" [2](#0-1) . This value was deliberately lowered from a previous 32-block ceiling [3](#0-2) . This is the same bug class as the referenced report: an insufficient block-confirmation threshold on a chain (Polygon) where validator-driven or ordinary chain reorgs can exceed the configured depth, letting the "randomness"/inclusion result the dependent system committed to be invalidated after the fact.

### Finding Description
The solver's cross-chain order-fill pipeline waits only for `requiredConfirmations` — sourced from `ConfirmationPolicy.getConfirmationBlocks`, which for Polygon interpolates up to a 5-block cap for a $100k order [2](#0-1)  — before treating the source-chain order as final and committing destination-chain capital via `executeOrder` [4](#0-3) .

Polygon PoS is not a chain with 5-block (~10s) practical finality against a reorg. Polygon's validator/heimdall-driven reorgs have historically exceeded far larger depths (reorgs of over 100 blocks have been observed), and even under the milestone mechanism, a colluding/majority validator set is not prevented from producing a reorg deeper than 5 blocks. The 5-block threshold assumes "milestone finality" is trustworthy and always current, but this is an assumption about liveness/behavior of Polygon's validator set — the same class of assumption the external MysteryBox report calls out for VRF `REQUEST_CONFIRMATIONS`.

Because the solver (an intent filler reachable by any unprivileged user placing a cross-chain order) commits capital on the destination chain once its own confirmation count reaches this threshold, a reorg that removes or alters the source-chain order-placement transaction after 5 blocks (but before the reorg-resistant depth) can invalidate the order the solver filled against, while the solver has already released destination-chain funds.

### Impact Explanation
If the source-chain (Polygon) transaction underlying the order is reorged out after the solver observed ≥5 confirmations but commits before Polygon's actual worst-case reorg depth, the solver pays out on the destination chain for a fill whose source-chain leg no longer exists / no longer matches. This is a direct theft-of-solver-funds vector: the solver has no on-chain safety net on cross-chain fills (unlike same-chain fills where `fillOrder` reverts if the order doesn't exist) — this is explicitly called out as the risk model the confirmation policy exists to protect against [5](#0-4) . A user or colluding validator can place a large order on Polygon, wait for the solver to release funds on the destination chain after 5 confirmations, and then have (or cause) the source chain to reorg away the order-placing transaction, leaving the solver with a loss and no recoverable claim.

### Likelihood Explanation
Exploitation requires the ability to cause or benefit from a >5-block Polygon reorg, which is realistic for validators (analogous to the VRF report's threat model) and has occurred organically on Polygon at depths far exceeding 5 blocks historically. The reduction from 32 to 5 blocks was a deliberate, recent (2026-09-08) configuration change made purely on optimistic finality-time assumptions rather than adversarial reorg-depth guarantees [3](#0-2) , and it silently applies to every solver operator who does not override `[confirmationPolicies."137"]`.

### Recommendation
Raise Polygon's default confirmation ceiling in `DEFAULT_CONFIRMATION_POLICIES["137"]` back to a value that accounts for adversarial/validator-driven reorg depth rather than average observed milestone-finality latency (e.g., back to 32 blocks or higher, consistent with the mitigation recommended in the referenced report of using a large, reorg-safe confirmation count rather than the chain's average finality time), and document that the max point must be sized against worst-case validator reorg behavior, not average block time.

### Proof of Concept
1. Operator runs Simplex with no `[confirmationPolicies."137"]` override, so the built-in default of max 5 blocks for Polygon applies [2](#0-1) .
2. A user places a ~$100k cross-chain order sourced on Polygon.
3. The solver's `waitForConfirmations` loop in `filler.ts` observes `currentConfirmations >= requiredConfirmations` (5) via `sourceQuorumClient.getTransactionConfirmations` and proceeds to `executeOrder`, releasing destination-chain funds [6](#0-5) .
4. A validator-driven or organic Polygon reorg deeper than 5 blocks removes the order-placement transaction before it reaches true finality.
5. The solver has already paid out on the destination chain against an order that no longer canonically exists on the source chain, resulting in a loss of solver funds with no on-chain recourse.

### Why this matters for cross-chain orders

On a cross-chain fill, Simplex observes an `OrderPlaced` (or `PartialFill` / `OrderFilled`) event on the source chain and then commits capital on the destination chain. Unlike same-chain fills — where the destination `fillOrder` call will revert if the source-chain order does not exist — cross-chain bids submitted through Hyperbridge are evaluated from the solver's own reading of source-chain state. A single RPC is therefore both an availability and an integrity choke point: if it lies about which orders were placed, the solver can be induced to pay out against events that never happened, and there is no on-chain safety net to catch it after the fact.
