### Title
Webhook Tenant Spoofing via Unsigned `shop-domain` Header - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by HMAC-verifying the raw request body, then trusts the unauthenticated `shop-domain` header to identify which tenant the payload belongs to. Because the HMAC secret (`Context.api_secret_key`) is the app's single `client_secret` shared across every installed shop, any shop that has installed the app can capture one of its own legitimately-signed webhook deliveries and replay the identical body/HMAC pair while substituting an arbitrary `shop-domain` header, causing the app's webhook handler to process attacker-supplied data as if it originated from a different, victim tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, however, is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header, which is never part of the signed string: [2](#0-1) 

`HmacValidator.validate` only checks the HMAC of `to_signable_string` (i.e., the body) against the shared `api_secret_key`: [3](#0-2) 

`Registry.process` gates entirely on that body-only HMAC check, and then forwards the unauthenticated `request.shop` value directly into the `WebhookMetadata` passed to the app's handler: [4](#0-3) 

The gem's own documentation states that `Registry.process` "will verify the request did indeed come from Shopify", implying the whole request — including the shop attribution — is authenticated: [5](#0-4) 

In reality, the equality the code should enforce — `hmac_signed(shop) == shop_acted_upon` — is broken: the `shop` value acted upon by the handler is never covered by the HMAC that gates admission. Since Shopify apps use one `client_secret`/`api_secret_key` for all shops that install the app, a webhook body+HMAC pair validly generated for shop A's own webhook delivery remains a valid signature no matter what `shop-domain` header accompanies it, because the signature is computed only from the body. An attacker who controls a shop that has installed the target app can therefore capture one of their own webhook deliveries and replay the same raw body/HMAC while forging the `shop-domain` header to name any other installed shop, and `Registry.process` will accept it and hand the forged shop identity to the application handler.

### Impact Explanation
This breaks the tenant boundary the gem is documented to enforce: an unprivileged attacker who has merely installed the app on their own store can inject data that is attributed, by the gem's own webhook-processing API, to an arbitrary other tenant. Any handler that uses `data.shop` from `WebhookMetadata` to look up a per-shop session/access token, trigger per-shop side effects, or gate resource access (a normal and expected use of the field per `docs/usage/webhooks.md`) will act on a victim tenant's identity using attacker-controlled body content — a cross-tenant access primitive. Depending on the topic being spoofed (e.g., `app/uninstalled`, `shop/redact`, `customers/data_request`), this can trigger destructive or data-exfiltrating actions scoped to the victim's tenant.

### Likelihood Explanation
Likelihood is high for any Shopify-app operator who can install the app on their own store (a low bar — any developer/merchant account) and capture their own outgoing webhook traffic (trivial, since it's delivered to their own endpoint). No access token, `client_secret`, or privileged account is required — only a body/HMAC pair the attacker legitimately received for their own installation, and control over the headers of a replayed HTTP request to the app's public webhook endpoint.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the HMAC-covered signable string, or otherwise cryptographically tie the claimed shop to the signature (e.g., verify against a per-shop secret or a stored session/shop record before trusting `request.shop`). At minimum, `Registry.process`/`Utils::HmacValidator.validate` should not allow a body signed under the shared app secret to be paired with an arbitrary, unauthenticated shop identity — the shop the payload is attributed to must be part of what is verified, not merely part of what is parsed from headers.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`; the app registers a webhook (e.g., `orders/create`) to receive HTTP webhooks.
2. Shopify sends the attacker a legitimately signed webhook: headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: H`, body `B`, where `H = HMAC-SHA256(api_secret_key, B)`.
3. Attacker replays the same body `B` and the same `x-shopify-hmac-sha256: H` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Registry.process` calls `Utils::HmacValidator.validate`, which recomputes HMAC over `B` only and finds it matches `H` (validation passes, since the shop header was never part of what is signed).
5. `Registry.process` invokes the app's handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: <attacker-controlled parsed body>, ...)`, causing the app to process attacker-controlled data under the victim tenant's identity.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
