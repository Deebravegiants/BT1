### Title
Stale cached operator authorization reused for subsequent user signups without re-validation - (File: `src/plans/mod.rs`)

### Summary
`MasterPlan::scan_remaining_qr_codes` and `MasterPlan::idle_scan_user_qr_code` gate whether the operator's identity is re-verified against the backend purely on a locally cached `Instant` timestamp (`operator_data.timestamp`) compared to `operator_qr_expiration_time`, rather than re-checking the operator's current authorization status with `backend::operator_status::request`. This mirrors the Goldfinch/Carapace root cause: a cached "valid" status is trusted for authorizing a security-relevant action instead of re-querying live backend state.

### Finding Description
`OperatorData` stores a `qr_code`, `location_data`, and a `timestamp` captured at the moment `verify_operator_qr_code` (which calls `backend::operator_status::request`) last returned `valid: true`. [1](#0-0) 

In `scan_remaining_qr_codes`, once an `OperatorData` exists, the code only re-invokes `verify_operator_qr_code` when the cached timestamp has expired; otherwise, it reuses the previously-validated `operator_data` directly to authorize scanning/verifying a *new* user QR code via `scan_user_qr_code` → `verify_user_qr_code`: [2](#0-1) 

The same pattern exists in the self-serve idle loop, where `idle_scan_user_qr_code` is invoked with the previously cached `operator_data` and only the remaining expiration window is used to bound the scan timeout — again without a backend re-check of operator validity: [3](#0-2) 

The actual backend authorization call only happens in `verify_operator_qr_code`, which performs a live HTTP request to `backend::operator_status::request`: [4](#0-3) [5](#0-4) 

Because the "is this operator still authorized to run signups" decision is derived solely from a local wall-clock cache (`operator_data.timestamp.elapsed() < operator_qr_expiration_time`) rather than the live backend `Status.valid` field, if the backend revokes/deactivates the operator (e.g., due to fraud, ban, or account compromise) at any point after the last successful check, the Orb continues to treat the operator as authorized and will proceed to validate and process additional user signups under that operator's identity for up to `operator_qr_expiration_time` — the exact analog to the Carapace bug where a stale, cached "pool active" status was trusted instead of the true, asynchronously-updated backend state.

### Impact Explanation
An operator whose authorization is revoked by the backend mid-session can continue to run and authorize additional user signups (and their associated biometric capture/enrollment) until the local cache naturally expires. This is a cross-signup authorization-state bleed: authorization state validated for one signup is silently extended to authorize subsequent, distinct signups without re-verification, which can result in unauthorized signups being processed under an operator identity that the backend no longer considers valid.

### Likelihood Explanation
Exploitation requires only the ordinary/unprivileged flow of running multiple signups in sequence under a single operator scan (a normal supported mode — the very purpose of `operator_qr_expiration_time`), combined with a backend-side revocation event during that window. No special hardware access, malicious peer, or off-path capability is needed; it is purely a client-side TOCTOU on an authorization decision reachable by any operator running signups in the field. Likelihood is bounded by how large `operator_qr_expiration_time` is configured; I was unable to confirm the concrete default/minimum value for this duration from the available index (the `Config::default()` block was truncated before reaching `operator_qr_expiration_time`), so the exact exposure window is uncertain.

### Recommendation
Do not rely solely on the local `timestamp` cache to skip backend re-validation for security-relevant authorization decisions. Either (a) re-validate operator status via `backend::operator_status::request` before every new user signup (not just after the cache expires), or (b) reduce `operator_qr_expiration_time` to a value tight enough that it cannot meaningfully be abused, and document that this is a deliberate trust window rather than a live authorization check.

### Proof of Concept
1. Operator scans their QR code; `verify_operator_qr_code` succeeds and `OperatorData { timestamp: Instant::now(), .. }` is cached (`src/plans/mod.rs:849-853`).
2. Operator begins running signups with `scan_remaining_qr_codes`; each subsequent signup within `operator_qr_expiration_time` takes the `if operator_data.timestamp.elapsed() < operator_qr_expiration_time` branch and skips calling `verify_operator_qr_code`/`backend::operator_status::request` again (`src/plans/mod.rs:806-819`).
3. Backend-side, the operator's authorization is revoked (e.g., flagged for fraud) immediately after step 1.
4. The Orb has no mechanism to learn of this revocation until the cached timestamp expires; it proceeds to call `scan_user_qr_code`/`verify_user_qr_code` and process additional signups under the now-revoked operator identity (`src/plans/mod.rs:1011-1090`, `src/plans/mod.rs:1580-1623`).

/// Makes a validation request.
pub async fn request(qr_code: &qr_scan::user::Data) -> Result<Status> {
    let request = super::client()?
        .get(format!(
            "{}/api/v1/distributor/{}/orb/{}/status",
            *SIGNUP_BACKEND_URL, qr_code.user_id, *ORB_ID
        ))
        .basic_auth(&*ORB_ID, Some(get_orb_token()?));
    let status: Status = match request.send().await?.error_for_status() {
        Ok(response) => response.json().await?,
        Err(err) => {
            tracing::error!("Received error response {err:?}");
            return Err(err.into());
        }
    };
    if !status.valid {
        tracing::info!(
            "Operator QR-code invalid: {qr_code:?}, reason: {:?}",
            status.reason.as_deref().unwrap_or("<empty>")
        );
        return Ok(status);
    }
    if status.location_data.is_none() {
        tracing::error!("Operator location data are missing");
        return Ok(Status {
            valid: false,
            location_data: None,
            reason: Some("Operator location data are missing".to_string()),
        });
    }
    Ok(status)
}
