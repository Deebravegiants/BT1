### Title
Webhook `shop`, `topic`, and `webhook_id` headers are trusted without HMAC coverage, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a passing HMAC check as proof that the *entire* webhook request — including the shop domain, topic, and webhook id — came from Shopify. In reality, the HMAC only signs the raw request body. The shop/topic/webhook-id values are read straight from unauthenticated HTTP headers, so they can be freely altered without invalidating the signature.

### Finding Description
`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string`: [1](#0-0) 

For a webhook `Request`, `to_signable_string` returns only the raw body: [2](#0-1) 

But `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from HTTP headers that are never included in the signable string: [3](#0-2) 

`Registry.process` validates the HMAC and then unconditionally trusts `request.topic` (to select the handler) and `request.shop` (passed into `WebhookMetadata` given to the handler): [4](#0-3) 

This breaks the identity binding the documentation promises: "This will verify the request did indeed come from Shopify and then call the specified handler for that webhook" — but the shop/topic that "came from Shopify" is never actually bound to the verified bytes. [5](#0-4) 

**Equality that should hold but doesn't:** `shop header value used to build WebhookMetadata` == `shop value covered by the HMAC-verified payload`. Instead, the code only checks `HMAC(raw_body, secret) == received_hmac`, independent of the header values acted upon.

### Impact Explanation
An attacker who is able to obtain any single legitimate Shopify-signed webhook (body + `X-Shopify-Hmac-Sha256` pair) — trivially available to any merchant/developer receiving webhooks for their own shop — can replay that exact body/HMAC pair to the target app's webhook endpoint while forging the `X-Shopify-Shop-Domain`, `X-Shopify-Topic`, and `X-Shopify-Webhook-Id` headers to arbitrary values. `HmacValidator.validate` still passes because the body is unchanged, and `Registry.process` will dispatch to the handler registered for the *attacker-chosen* topic with a `WebhookMetadata.shop` equal to the *attacker-chosen* shop domain. This is a cross-tenant impersonation: the host app's webhook handler acts on data "from" a shop domain that was never authenticated, potentially triggering shop-scoped side effects (data writes, notifications, background jobs keyed by `shop_domain`) for a tenant the attacker doesn't control.

### Likelihood Explanation
Any developer/merchant with an installed app that receives webhooks can capture one valid body+HMAC pair from their own legitimate webhook traffic (no `api_secret_key` or privileged access required), then replay it with modified headers against the same endpoint. No cryptographic material needs to be broken; the header/body decoupling is a straightforward, always-reachable code path (`Registry.process` → `HmacValidator.validate` → `Request#to_signable_string`).

### Recommendation
Bind the shop domain, topic, and webhook id into the HMAC-verified signable string (or otherwise cryptographically bind them to the signed body), or independently verify `request.shop` against the shop that the recipient session/registration expects before dispatching to a handler. At minimum, `to_signable_string` should incorporate the header values that `Registry.process` and `WebhookMetadata` rely on so a passing HMAC check certifies all fields acted upon, not just the raw body bytes.

### Proof of Concept
1. App A operates a webhook endpoint and legitimately receives a Shopify webhook for `shop-a.myshopify.com`, topic `orders/create`, with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC(secret, B)`).
2. Attacker (who is Shop A's own merchant/developer, or anyone who can observe one such delivery) resends the identical `B`/`H` pair to the same endpoint but sets:
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
   - `X-Shopify-Topic: customers/data_request` (or any registered topic)
   - `X-Shopify-Webhook-Id: <arbitrary>`
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` is constructed; `HmacValidator.validate` recomputes `HMAC(secret, B)` and it still equals `H`, so validation succeeds.
4. `Registry.process` looks up the handler for the forged topic and invokes it with `WebhookMetadata.new(topic: "customers/data_request", shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)`, causing the app to act as though a genuine, shop-specific webhook for `victim-shop.myshopify.com` was received — despite the body content having nothing to do with that shop.
