### Title
Multi-asset users are frozen out of borrow/repay/collateral operations on healthy vaults because `accrue-user-debts`/`accrue-user-collateral` panics on the first paused vault - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`v0-4-market.clar` centralizes routing to six independent per-asset vaults (`v0-vault-stx`, `v0-vault-sbtc`, `v0-vault-ststx`, `v0-vault-usdc`, `v0-vault-usdh`, `v0-vault-ststxbtc`). Whenever the market needs to evaluate a user's position (to add/remove collateral, borrow, repay, or check health), it folds over the *entire* list of the user's collateral and debt entries and force-accrues each one with `unwrap-panic`. Each vault independently exposes granular pause flags, including a dedicated `accrue` flag [1](#0-0) . If any single vault that a user happens to hold collateral or debt in has its `accrue` operation paused (or otherwise reverts), the fold's `unwrap-panic` propagates a runtime panic that reverts the *entire* market-level call - even for actions targeting a completely different, healthy asset.

### Finding Description
The market routes vault calls per-asset via long `if`/`is-eq` chains, e.g. `vault-deposit`, `vault-redeem`, `vault-system-borrow`, `vault-accrue` [2](#0-1) . But before executing a user-facing action, the market accrues *every* asset in the user's collateral/debt lists via `accrue-user-debts` and `accrue-user-collateral`, which `fold` over the lists and call `accrue-debt-asset` / `accrue-collateral-asset`:

```clarity
(define-private (accrue-debt-asset
  (debt-entry { aid: uint, scaled: uint })
  (acc { success: bool }))
  (begin
    (unwrap-panic (accrue-and-cache (get aid debt-entry)))
    acc))
``` [3](#0-2) 

`accrue-and-cache` calls `vault-accrue` for the given asset id, and `vault-accrue` itself dispatches to the underlying vault's `accrue` entrypoint [4](#0-3) . Each vault independently guards its `accrue` operation behind a `pause-states` flag that the DAO/guardian can toggle per-operation, per-vault [1](#0-0) , and when paused the vault returns `ERR-PAUSED` for that operation.

Because `accrue-debt-asset`/`accrue-collateral-asset` wrap the call in `unwrap-panic` rather than propagating the error via `try!`/`asserts!` with graceful handling, a single paused (or otherwise reverting) vault's `accrue` will cause a Clarity runtime panic that aborts the *entire* transaction - regardless of which asset the user is actually trying to interact with. This is used in collateral-add's capacity check (`accrue-user-debts (get debt position)` / `accrue-user-collateral (get collateral position)`) [5](#0-4) , and is invoked 22 times across the mainnet market contract for borrow, repay, withdraw, and liquidation flows.

### Impact Explanation
Any user who holds a multi-asset position (collateral or debt spanning more than one vault) becomes unable to deposit, withdraw, borrow, or repay against any of their *healthy* assets as soon as one unrelated vault in their portfolio has its `accrue` operation paused, disabled, or reverting for any reason (emergency pause, upgrade in progress, bug in a single vault's interest-rate math, etc.). This is a temporary freezing of funds/positions: users cannot access or manage principal or collateral on the unaffected assets until the other vault's `accrue` is unpaused, even though the affected vault itself was never touched by the user's intended action.

### Likelihood Explanation
This requires no attacker action - it is triggered purely by an operational pause on a single vault (a normal, expected DAO/guardian action for incident response) combined with any user holding a diversified, multi-asset position, which is an encouraged usage pattern of the protocol (cross-collateralization is a core feature per the egroup design). Given six vaults and the DAO's ability to pause any one of them independently for maintenance or in response to an issue, this is a realistic and easily-triggered scenario, not a contrived edge case.

### Recommendation
Do not use `unwrap-panic` in `accrue-debt-asset`/`accrue-collateral-asset`. Either:
1. Skip accrual gracefully for a vault whose `accrue` is paused (using the last cached/stored index instead of panicking), while still allowing the rest of the position's assets to be evaluated and the user's intended action (on an unrelated, healthy vault) to proceed, or
2. If a paused vault's asset absolutely must block certain operations (e.g., borrowing against unpriced collateral), scope the block to actions that specifically involve that asset rather than reverting the whole transaction for actions on unrelated vaults.

### Proof of Concept
1. User deposits collateral into `vault-usdc` and separately borrows/holds debt in `vault-stx` (a normal cross-collateralized position).
2. DAO/guardian pauses the `accrue` operation on `vault-usdc` (e.g., due to a detected issue in USDC's interest model) via the vault's pause-state setter.
3. User calls `borrow`/`repay`/`collateral-remove` on `vault-stx` only (an asset that is fully operational).
4. Market's health/capacity check invokes `accrue-user-collateral`/`accrue-user-debts` over the user's full position list, which includes the USDC entry.
5. `accrue-and-cache` → `vault-accrue` → USDC vault's `accrue` returns `ERR-PAUSED`; `unwrap-panic` triggers a runtime panic, aborting the entire transaction.
6. The user is unable to manage their STX-side debt/collateral at all until USDC's `accrue` is unpaused, despite never intending to touch USDC.
