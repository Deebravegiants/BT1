### Title
Wallet Contract permanently bricked when a mutable method's receipt fails after clearing `has_in_flight_tx`, due to full receipt-state rollback on failure - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
`WalletContract` (the eth-implicit-account wrapper contract in nearcore's Rainbow/Aurora-style wallet implementation) uses a single boolean flag, `has_in_flight_tx`, to serialize all transactions for an eth-implicit account: `rlp_execute` refuses to start a new transaction whenever the flag is `true` [1](#0-0) , and every callback (`address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`) is expected to clear it back to `false` as its very first statement [2](#0-1) [3](#0-2) [4](#0-3) . This mirrors the audited bug class: a single unrecoverable state flag whose "unlock" step is dependent on a receipt/execution succeeding, exactly like the auction's `_settleAuction()` depending on `safeTransferFrom()` not reverting.

### Finding Description
In the reported Solidity bug, an untrusted external call inside a critical state-transition (`safeTransferFrom`) can revert, and because the whole transaction (including prior state writes) is rolled back atomically, the auction's terminal state is never reached and the contract is permanently bricked.

nearcore's runtime has the analogous atomicity property at the receipt level: `apply_action_receipt` executes all actions of a receipt and, on any action failure, calls `state_update.rollback()`, which "discard[s] all state changes from the receipt" [5](#0-4) . This means if any part of a NEAR contract's mutable method body fails *after* it wrote `has_in_flight_tx = false`, that state write is rolled back along with everything else in the receipt, and the persisted account state still shows `has_in_flight_tx == true`.

`WalletContract`'s callbacks are structured exactly this way: they set `self.has_in_flight_tx = false;` as line 1 of the function, then go on to parse cross-contract results (`serde_json::from_slice`), build a new promise via `action_to_promise`, and set `self.has_in_flight_tx = true;` again before returning the new promise [6](#0-5) . If the callback's execution fails *after* clearing the flag but before/without a state-commit boundary at that point (e.g., a host-function/gas error, or any `env::panic_str`/unwrap failure triggered while building the follow-up promise), the entire receipt — including the `has_in_flight_tx = false` write — is rolled back, restoring `has_in_flight_tx = true` permanently. Since `rlp_execute` is the only entry point that starts new work, and it unconditionally rejects calls while the flag is `true` with no other method to reset it [7](#0-6) , the wallet contract for that eth-implicit account becomes permanently unusable — the direct structural analog of "the winner of a bid can brick the auction house."

The design comment inside the struct even encodes the fragile invariant this relies on: `has_in_flight_tx` must be `true` exactly while a promise is outstanding, and `false` otherwise [8](#0-7)  — a manually maintained invariant with no self-healing/reset mechanism if any single callback receipt fails without a state-committing rollback boundary between the flag write and the point of failure.

### Impact Explanation
If reachable, this permanently denies all future NEAR actions signed by the eth-implicit account's owner and forwarded by a relayer (rlp_execute always short-circuits with "transaction already in progress"), effectively freezing that account's Wallet-Contract-mediated NEAR interactions indefinitely — no funds are directly stolen, but user-controlled state and functionality become permanently unusable, analogous to the original "bricking" impact. This does not affect validators, other accounts, or chain liveness — it is scoped to the single wallet-contract account whose receipt failed in this manner.

### Likelihood Explanation
I was not able to conclusively identify (within tool limits) a concrete, attacker-triggerable failure inside the callback bodies between the `has_in_flight_tx = false` write and the subsequent `has_in_flight_tx = true` write — the visible code paths (`PromiseResult::Failed`, JSON deserialization errors, unsupported-action errors) all `return` immediately after the flag is cleared, meaning those particular error paths commit `false` successfully and are not exploitable. The unresolved uncertainty is whether any other host-function failure (e.g., an unexpected gas/deposit computation, or a panic while constructing the batched `action_to_promise`/`.then()` promise with attacker-influenced `action` gas/deposit values) can occur strictly after the flag write, since that is the necessary precondition for the rollback to reintroduce `has_in_flight_tx = true`. Confirming this requires deeper tracing of `action_to_promise`, `near_action::Action` deserialization, and the exact gas-accounting checks performed by the NEAR SDK/host functions during promise construction, which was not fully verifiable with the available context.

### Recommendation
- Avoid relying on a rollback-sensitive ordering where a critical "unlock" flag write can be undone if a later, unrelated statement in the same receipt fails. Commit the flag reset in a way that is independent of subsequent fallible operations (e.g., perform the unlock write, then immediately return/split the risky promise-construction logic into a separate, already-scheduled receipt rather than same-receipt code that runs after the write).
- Add an explicit recovery/reset path (e.g., an owner- or time-based unlock) so a single stuck receipt cannot permanently deny the account, mirroring how the original report recommends removing the single point of failure (`safeTransferFrom` → `transferFrom`) rather than depending on an operation that can revert atomically with the critical state change.

### Proof of Concept
Not able to construct a concrete, fully reachable PoC with the available tools — see Likelihood Explanation for the exact condition (a failure occurring strictly after `self.has_in_flight_tx = false;` inside `address_check_callback`, `nep_141_storage_balance_callback`, or `rlp_execute_callback`) that would need to be triggered to realize this analog. The rollback mechanism itself is confirmed via `protocol-model/spec/runtime-execution.md` (`apply_action_receipt`, step 7: "failure calls `state_update.rollback()`, discarding all state changes from the receipt") [5](#0-4) , and the vulnerable structural pattern (flag reset followed by fallible logic, then flag re-set) is confirmed directly in `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs` lines 139-192, 201-273, and 276-317.
