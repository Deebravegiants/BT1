### Title
Missing `return` after failed email-claim extraction allows OIDC session/cookie creation with an empty-email identity - ([File: core/sessions/oidcauth/oidc.go])

### Summary
In `handleTokenExchange`, when the `email` claim cannot be type-asserted from the OIDC provider's claims, the handler logs the error and writes an HTTP 500 body but fails to `return`, so execution continues exactly like the LooksRare `call`-opcode bug where an unchecked/ignored failure status lets the function proceed with a bad state (an empty ETH-return `status` there; an empty `email` here) instead of aborting.

### Finding Description
`handleTokenExchange` extracts `email` from the ID token claims: [1](#0-0) 

If the assertion fails, `ok` is `false` and `email` keeps its zero value (`""`). The code calls `c.String(http.StatusInternalServerError, ...)` but does **not** `return`. Execution falls through to role mapping and session persistence: [2](#0-1) 

and finally the session cookie is set and saved, and a success JSON response is written: [3](#0-2) 

This mirrors the report's root cause precisely: a failure signal (`call`'s `status` / here, the `ok` boolean from the claim type assertion) is produced, an error-handling branch is entered, but the code does not halt on that failure — it continues performing state-changing operations (inserting into `oidc_sessions`, setting the auth cookie) as if the operation had succeeded. Just as the LooksRare code needed `if (!status) revert(...)`, this handler needs `return` (or equivalent early exit) immediately after detecting the missing/invalid `email` claim.

Note that the earlier steps in the same function — ID token signature verification (`oi.provider.Verifier(...).Verify`) and group-claim extraction/role mapping (`ExtractIDClaimValues`, `IDClaimsToUserRole`) — do succeed and do `return` correctly on their own errors, so this is an isolated omission specific to the `email` claim check.

### Impact Explanation
A session row is written to `oidc_sessions` with `user_email = ""` and a `user_role` derived from the already-validated group claims, and the gin session cookie (`SessionIDKey`) is set and saved for the caller despite the handler having detected and reported an error. The HTTP response body ends up containing the JSON success payload with the earlier 500 status text (Gin does not re-execute `WriteHeader`, but the body writes still occur and the session/cookie side effects are unconditionally applied). This means:
- A client whose IdP token omits/misconfigures the `email` claim (or where the claim is not a string, e.g., a mis-issued or malformed claim, or a downstream proxy/IdP configuration issue) ends up authenticated with a persisted session tied to an empty-email identity and a real RBAC role.
- Downstream, `AuthorizedUserWithSession` will happily return a `User{Email: "", Role: <role>}` for that session ID, so subsequent API calls made with that session cookie are treated as an authorized user of that role — i.e., a valid, functioning authenticated session is created for an "empty user" that should have been rejected.

This is a concrete authentication-state/session-integrity bug: unprivileged input controls whether an error path fully aborts, and failing to abort results in an authenticated session/cookie being issued rather than a hard rejection. This satisfies the "concrete authentication or role bypass ... cross-user response confusion" acceptance bar.

### Likelihood Explanation
Reachability is moderate: exploitation depends on the OIDC identity provider returning an ID token whose claims lack a well-formed `email` string, which is influenced by how the client/IdP is configured or by anomalies in a compromised/misbehaving IdP response — the surrounding claim (`idClaims`/group claims) must still validate correctly via `ExtractIDClaimValues`, which is independent of the `email` field. Because this is a code-level control-flow bug (missing `return`), it will reliably trigger the described behavior any time the `email` claim is absent or non-string, which is realistic during typical OIDC provider misconfiguration or a subtly crafted upstream response.

### Recommendation
Add a `return` immediately after the failed email-claim assertion, matching the pattern used by every other error branch in the same function:
```go
email, ok := claims["email"].(string)
if !ok {
    oi.lggr.Errorf("Failed to get email from claims")
    c.String(http.StatusInternalServerError, "Failed to get email from claims")
    return
}
```
Additionally, validate that `email` is non-empty (not just present) before persisting the `oidc_sessions` row, to defensively guard against any other path that could produce an empty email.

### Proof of Concept
1. Configure/point the node's OIDC provider settings at an IdP (or a proxy in front of a legitimate IdP) that returns a valid, verifiable ID token whose claims include the configured group/role claim (satisfying `ExtractIDClaimValues`/`IDClaimsToUserRole`) but omit the `email` claim or return it as a non-string type.
2. Complete the OAuth2 authorization code flow against `/oidc-login` and hit the callback handled by `handleTokenExchange` with a valid `code` and matching `state`.
3. Observe that despite the "Failed to get email from claims" error being logged, the response still sets the session cookie (`ginSession.Save()`), and a row is inserted into `oidc_sessions` with `user_email = ''` and the mapped `user_role`.
4. Use the returned session cookie against any authenticated API endpoint; `AuthorizedUserWithSession` resolves it to a `User{Email: "", Role: <role>}`, granting API access as that role despite the handler's own error path.
