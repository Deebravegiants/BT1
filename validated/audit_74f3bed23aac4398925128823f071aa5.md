### Title
Unbounded, fully-verified ISMP message batches executed inside `validate_unsigned` allow free-for-anyone computational DoS - ([File: modules/pallets/ismp/src/lib.rs])

### Summary
Both `pallet-ismp`'s `handle_unsigned` and the `pallet-coprocessor`'s `handle_unsigned` execute the *entire* message-processing pipeline — including cryptographic membership/state-proof verification — from within `ValidateUnsigned::validate_unsigned`, on an attacker-controlled, unbounded `Vec<Message>` / `Vec<GetRequest>` batch, with no batch-size or proof-count cap. Because these are unsigned extrinsics (no fee, no signer, "free for the relayer"), any network peer can broadcast maximally-sized batches; every full node that receives the gossiped transaction re-runs this expensive verification in its transaction pool (and again on each of the `longevity: 25` block re-validations), giving an attacker a cheap N:1 amplification of expensive cryptographic work across the network — directly analogous to the Kibana issue where crafted requests to a specific, low-privilege-reachable endpoint caused disproportionate server-side work and crashed/hung the instance.

### Finding Description
`pallet_ismp::Call::handle_unsigned` takes an arbitrary-length `messages: Vec<Message>` [1](#0-0) . Its `validate_unsigned` implementation does not merely check a lightweight proof of validity — it calls `Self::execute(messages.clone())`, the *same* function used for actual dispatch, which runs `handle_incoming_message` (full membership/state-proof verification, `dedup_requests`, callback invocation) for every message in the batch [2](#0-1) [3](#0-2) .

The companion `pallet-coprocessor::handle_unsigned` follows the identical anti-pattern: `validate_unsigned` calls `Self::handle_get_requests(message.clone())`, which performs full state-machine membership verification for the source proof and a `verify_state_proof` call per `GetRequest` in `message.requests` (again unbounded) before any economic/priority gate is applied [4](#0-3) [5](#0-4) .

There is no `BoundedVec`, no `MaxRequests`, and no cheap pre-check (e.g., a size/signature check) gating the batch before the expensive verification runs — the code comment in the docs even claims this can't be exploited ("Malformed messages or those with invalid proofs are filtered out by the transaction pool validation logic preventing unnecessary processing"), but that filtering *is* the expensive full verification itself, so the "protection" runs the exact workload it's meant to prevent [6](#0-5) .

Compare this with `pallet-call-decompressor`, which explicitly documents and fixes an identical class of bug (an unbounded decompression bomb reachable from `validate_unsigned`) by moving the size bound to the single choke point before any expensive work is done [7](#0-6) . No equivalent bound exists for `pallet-ismp::handle_unsigned` or `pallet-coprocessor::handle_unsigned`.

Because `validate_unsigned` runs:
1. On every peer that receives the gossiped unsigned transaction (initial txpool admission),
2. Again on every block-import re-validation for the transaction's `longevity` window (25 blocks),

an attacker can submit a single maximally-sized batch (bounded only by `MaximumBlockLength`/extrinsic size, ~5MB per the docs) packed with many `PostRequest`/`GetRequest` entries each requiring a full Merkle/state-trie proof verification, and have every connected full node redundantly perform that expensive verification dozens of times for a single "free" transaction, with no fee deterrent since it is unsigned.

### Impact Explanation
This is a network-wide denial-of-service vector reachable by anyone (no privileged role, no locked collateral, no signed transaction fee) who can submit gossip-network transactions to a Hyperbridge/parachain node — directly matching the required reachability bar ("EvmHost/HandlerV2 dispatch... pallet-ismp handle_unsigned"). Successful exploitation degrades node responsiveness/availability for message delivery, which can stall the route (a "route unable to deliver messages") for legitimate relayers, satisfying the acceptable-impact bar in the report's validation criteria.

### Likelihood Explanation
Medium-High. No signature or fee is required to submit `handle_unsigned`; the attacker only needs syntactically valid (but not necessarily provable) requests packed into a large batch, and repeated submission at the extrinsic-size ceiling is trivial and cheap for the attacker while costly for every validating node in the network. The existing test files (e.g. `pallet_call_decompressor.rs`) already show batches of hundreds/thousands of synthetic requests being constructed and pushed through `handle_unsigned`, demonstrating this is an easy-to-reach path.

### Recommendation
- Add a cheap, unconditional cap (e.g., `MaxMessagesPerBatch`, `MaxRequestsPerCoprocessorBatch`) enforced *before* any proof verification in both `validate_unsigned` implementations (`pallet-ismp::lib.rs` and `pallet-coprocessor::lib.rs`), mirroring the fix pattern already used in `pallet-call-decompressor::decompress`.
- Consider a lightweight structural/format pre-check (e.g., proof size sanity, request count vs. configured maximum) that rejects oversized batches with `InvalidTransaction::ExhaustsResources` prior to invoking `execute`/`handle_get_requests`.
- Reduce redundant re-validation cost by shortening `longevity` or caching validation results per `provides` tag so identical/large batches aren't reverified on every block within the validity window.

### Proof of Concept
Conceptual PoC (matches existing test patterns in the repo, e.g. `modules/pallets/testsuite/src/tests/pallet_call_decompressor.rs:97-211`, which already constructs batches of 100–1000 synthetic `GetRequest`/`PostRequest` entries fed into `handle_unsigned`):
1. Craft a `RequestMessage { requests: Vec<PostRequest> }` with the maximum number of `PostRequest` entries that fit under the runtime's extrinsic-size limit (no valid proof needed to trigger expensive processing attempts — verification runs against whatever the attacker supplies, and failure only occurs after the verification work is already spent).
2. Submit as `pallet_ismp::Call::handle_unsigned { messages: vec![Message::Request(msg)] }` via an unsigned transaction to the network (as done in `parachain/simtests/src/pallet_ismp.rs:281-293` using `subxt::dynamic::tx("Ismp", "handle_unsigned", ...)`).
3. Because `validate_unsigned` calls `Self::execute(messages.clone())` synchronously, each of the N `PostRequest` entries triggers a full `handle_incoming_message` call (including membership-proof verification against the referenced state commitment) before the transaction is rejected for an invalid proof.
4. Repeat/broadcast at the mempool longevity window (25 blocks) to amplify the cost across every validating node in the network.

Note: I could not find any rate-limiting, batch-size cap, or fee-based deterrent specific to `handle_unsigned` in either `pallet-ismp` or `pallet-coprocessor` in the indexed portion of the codebase; if such a guard exists elsewhere (e.g., in node-level RPC/txpool configuration not covered by the index), it was not found and should be verified with a full repository checkout.

```text
## Transaction fees

Pallet ISMP uses unsigned transactions for executing cross-chain messages. This means all cross-chain messages received are executed for free as unsigned transactions. The upside to this is that it cannot be exploited as a spam vector, since the transaction pool will check if the submitted extrinsics are valid before they are included in the pool. This validity check ensures that the transaction can be successfully executed and contains valid proofs. Malformed messages or those with invalid proofs are filtered out by the transaction pool validation logic preventing unnecessary processing and potential network congestion.
```
