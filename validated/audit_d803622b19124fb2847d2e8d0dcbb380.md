### Title
Login Endpoint Leaks User Existence via Timing Side Channel (Bcrypt Skip on Unknown Email) - (File: core/sessions/localauth/orm.go)

### Summary
The unauthenticated `/sessions` login endpoint calls `CreateSession`, which first performs a plain SQL lookup for the user by email and immediately returns an error if no row is found — before ever invoking the deliberately-slow bcrypt password comparison. This produces two observably different response-time classes for "email exists" vs. "email does not exist," which is the same class of bug (CWE-203, Observable Discrepancy) as the reported Wildfly Elytron `ScramServer` timing issue, where an attacker can infer information not otherwise available to them purely from response timing.

### Finding Description
`SessionsController.Create` binds an unauthenticated `SessionRequest` from `POST /sessions` and forwards it directly to `AuthenticationProvider().CreateSession` [1](#0-0) .

The local-auth implementation of `CreateSession` does:
```go
func (o *orm) CreateSession(ctx context.Context, sr sessions.SessionRequest) (string, error) {
	user, err := o.FindUser(ctx, sr.Email)
	if err != nil {
		return "", err
	}
	...
	if !constantTimeEmailCompare(strings.ToLower(sr.Email), strings.ToLower(user.Email)) { ... }
	if !utils.CheckPasswordHash(sr.Password, string(user.HashedPassword)) { ... }
``` [2](#0-1) 

`FindUser`/`findUser` is a plain, fast SQL `SELECT ... WHERE lower(email) = lower($1)` [3](#0-2) . If the email does not exist, the function returns immediately with a database "no rows" error, skipping the constant-time email comparison and the bcrypt `CheckPasswordHash` call entirely. If the email *does* exist, the request proceeds to run `utils.CheckPasswordHash`, which performs a bcrypt hash computation — an operation intentionally expensive (tens of milliseconds), several orders of magnitude slower than the SQL miss path.

This means an unauthenticated caller can distinguish "email exists" from "email doesn't exist" purely by measuring response latency of `POST /sessions`, without needing to guess a correct password. The same exact pattern (SQL lookup miss short-circuits before bcrypt) also exists in the LDAP and OIDC local-login fallback paths [4](#0-3) [5](#0-4) , and in the `TestPassword` helper used for password-change confirmation [6](#0-5) .

Note: other authentication comparisons in this codebase (API token secrets, external-initiator secrets, bridge tokens, email string comparisons) correctly use `subtle.ConstantTimeCompare` with fixed-length padding (e.g. `constantTimeEmailCompare`) [7](#0-6) [8](#0-7) [9](#0-8) . The vulnerability here is specifically the control-flow short-circuit on user lookup, not a byte-comparison timing leak.

### Impact Explanation
An attacker can enumerate valid admin/API user email addresses on a Chainlink node by sending login attempts and measuring response time, without needing any credentials. This is a confidentiality-only issue (matches the CVSS vector of the referenced advisory: `C:H/I:N/A:N`) — it does not itself grant authentication bypass, but it materially aids credential-stuffing or targeted brute-force/social-engineering attacks against the node's operator UI by confirming which accounts exist.

### Likelihood Explanation
The `/sessions` endpoint is unauthenticated and internet-facing on any node exposing its operator UI. Exploitation only requires sending repeated login requests and performing statistical timing analysis, which is a well-established and low-cost attack technique (no special network position or privileges required), matching the CVSS `AC:H` (some effort needed to filter noise) `PR:N`-like reachability of the original advisory pattern.

### Recommendation
Ensure a constant amount of work is performed for both "user exists" and "user does not exist" branches in `CreateSession`, `TestPassword`, and the LDAP/OIDC local-login fallbacks: e.g., always compute (or dummy-compute) a bcrypt comparison against a fixed dummy hash when the user lookup fails, before returning the generic authentication error, so response timing does not vary with account existence.

### Proof of Concept
1. Pick a known-valid admin email `admin@example.com` and an unknown email `doesnotexist@example.com`.
2. Send repeated `POST /sessions` requests with random incorrect passwords for both emails.
3. Measure response latency: requests for the valid email will consistently take longer (bcrypt computation in `utils.CheckPasswordHash`) than requests for the nonexistent email (which fail fast at the `FindUser` SQL lookup) [10](#0-9) .
4. The measurable timing delta reveals which email addresses are registered on the node.

func (o *orm) CreateSession(ctx context.Context, sr sessions.SessionRequest) (string, error) {
	user, err := o.FindUser(ctx, sr.Email)
	if err != nil {
		return "", err
	}
	lggr := o.lggr.With("user", user.Email)
	lggr.Debugw("Found user")

	// Do email and password check first to prevent extra database look up
	// for MFA tokens leaking if an account has MFA tokens or not.
	if !constantTimeEmailCompare(strings.ToLower(sr.Email), strings.ToLower(user.Email)) {
		o.auditLogger.Audit(audit.AuthLoginFailedEmail, map[string]any{"email": sr.Email})
		return "", pkgerrors.New("Invalid email")
	}

	if !utils.CheckPasswordHash(sr.Password, string(user.HashedPassword)) {
		o.auditLogger.Audit(audit.AuthLoginFailedPassword, map[string]any{"email": sr.Email})
		return "", pkgerrors.New("Invalid password")
	}

const constantTimeEmailLength = 256

func constantTimeEmailCompare(left, right string) bool {
	length := mathutil.Max(constantTimeEmailLength, len(left), len(right))
	leftBytes := make([]byte, length)
	rightBytes := make([]byte, length)
	copy(leftBytes, left)
	copy(rightBytes, right)
	return subtle.ConstantTimeCompare(leftBytes, rightBytes) == 1
}
