### Title
Webhook `shop-domain` (and `topic`) header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while the `shop`, `topic`, `webhook_id`, and `api_version` values used by `ShopifyAPI::Webhooks::Registry.process` are all read from unauthenticated HTTP headers. The HMAC check therefore proves only that the *body bytes* were produced with the app's shared `client_secret` — it says nothing about which shop the request claims to be from. This breaks the identity binding "shop authenticated == shop the handler acts on," letting an attacker who possesses one valid `(raw_body, hmac)` pair replay it while forging the `X-Shopify-Shop-Domain` header to impersonate any other shop.

### Finding Description
`Request#hmac` and `#to_signable_string` are defined as: [1](#0-0) 

`to_signable_string` returns `@raw_body` only — no header is mixed into the signed material. Yet `shop`, `topic`, `api_version`, and `webhook_id` are all pulled straight from attacker-controllable headers: [2](#0-1) 

`HmacValidator.validate` verifies the HMAC purely against `to_signable_string` (the body): [3](#0-2) 

`Registry.process` accepts the request once that body-only HMAC passes, then dispatches to a handler keyed by the unauthenticated `topic` header and hands the unauthenticated `shop` header straight to the handler as the tenant identifier: [4](#0-3) 

Because Shopify apps use a single shared `client_secret` to sign webhooks for *every* shop that has installed the app (not a per-shop secret), any party who legitimately receives one webhook delivery for their own shop (a completely valid, unprivileged install) obtains a `(raw_body, hmac)` pair that remains valid regardless of which shop it is replayed as. Since the shop identity is carried out-of-band in a header untouched by the signature, that same request can be replayed to the app's webhook endpoint with `X-Shopify-Shop-Domain` set to a victim shop, and the app will process attacker-controlled webhook content believing it originated from the victim tenant.

The identity binding that should hold is:
`shop authenticated by HMAC == shop the handler processes as tenant`
but the actual state is:
`shop authenticated by HMAC == (nothing; only body bytes are covered)` while `shop the handler processes == unauthenticated header value`.

### Impact Explanation
This is a cross-tenant access vulnerability per the given impact list: an attacker (any shop that can install the app once, or anyone who intercepts/replays one delivery) can forge webhook events that the host application will attribute to a different, victim shop. Depending on how the host app's webhook handlers use `WebhookMetadata#shop` (e.g., to look up/update per-shop records, provision resources, or trigger financial/inventory actions), this can lead to cross-tenant data corruption or unauthorized actions performed against another merchant's account — all without possessing that merchant's access token or credentials.

### Likelihood Explanation
Moderate-to-high: obtaining one valid `(body, hmac)` pair only requires legitimate access to a single webhook delivery for any shop that has the app installed (many Shopify apps are self-serve/free to install), and replaying it to the app's public webhook endpoint with a different `Shop-Domain` header requires no special access, no TLS interception, and no knowledge of `api_secret_key`.

### Recommendation
Bind the shop (and ideally the topic/webhook id) into the signed material, or otherwise independently authenticate the shop domain — e.g., cross-check `X-Shopify-Shop-Domain` against the shop associated with the currently active/loaded session for that webhook subscription, or include the header values in the HMAC-signable string (matching what Shopify actually promises to sign, if it does) instead of trusting them unconditionally once only the body's HMAC checks out.

### Proof of Concept
1. Install the target app on shop `attacker.myshopify.com`. Shopify sends a real webhook to the app's configured endpoint with a genuine `X-Shopify-Hmac-Sha256` computed over the JSON body using the app's shared `client_secret`.
2. Capture the raw body and the `X-Shopify-Hmac-Sha256` header value from that delivery.
3. Replay the exact same body and HMAC header to the app's webhook endpoint, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` recomputes the HMAC over `to_signable_string` (the unchanged raw body) and it matches, so `Registry.process` in `lib/shopify_api/webhooks/registry.rb` accepts the request and invokes the topic's handler with `shop: "victim-shop.myshopify.com"`, even though the payload/topic/webhook_id were never authenticated as belonging to that shop.
