### Title
Webhook `shop`, `topic`, and `webhook_id` headers are not covered by the HMAC signature, allowing cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/registry.rb`, `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` is documented to "verify the request did indeed come from Shopify" before invoking the app's webhook handler. In reality, the HMAC signature only covers the raw request body — the `shop-domain`, `topic`, and `webhook-id` HTTP headers are never included in the signed payload, yet they are trusted as authenticated and handed to the app's handler unchecked. Anyone who can obtain one legitimately-signed webhook body/HMAC pair (e.g. by installing the target app on their own store) can replay that exact body+HMAC combination to the app's webhook endpoint while freely substituting the `shop-domain` header for any victim shop, achieving cross-tenant webhook injection.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, and `webhook_id` accessors are pulled straight from attacker-controlled HTTP headers with no cryptographic binding to the body: [2](#0-1) 

`HmacValidator.validate` computes the signature only from `verifiable_query.to_signable_string` (the body) and the shared `api_secret_key`: [3](#0-2) 

`Registry.process` treats a body-only HMAC match as full request authentication and then dispatches to the handler using the unauthenticated `shop`, `topic`, and `webhook_id` fields: [4](#0-3) 

This equality is what should hold but does not: `shop header authenticated == shop the body actually originated from`. Since the `api_secret_key` is a single value shared across *all* shops of the app (not per-shop), any user who can trigger a genuine webhook to their own store (installing the app on their own free dev shop is enough) legitimately obtains a `(body, hmac)` pair that passes `OpenSSL.secure_compare`. They can then POST that identical body/hmac to the app's public webhook endpoint with a forged `x-shopify-shop-domain` header naming a victim shop (and optionally a different `x-shopify-topic`/`x-shopify-webhook-id`). `Registry.process` will accept it as valid and hand `WebhookMetadata.new(shop: <victim>, topic: <attacker-chosen>, body: <attacker's own body>, ...)` to the app's handler, which the docs explicitly tell integrators to trust: [5](#0-4) [6](#0-5) 

### Impact Explanation
Applications built on this gem are told that a webhook which passes `Registry.process` "did indeed come from Shopify" for the shop named in `data.shop`. In practice an attacker can forge that shop attribution and inject arbitrary (self-controlled) webhook bodies against any other tenant's shop domain the app services, since the shop identity is never part of the authenticated payload. Depending on how the host app uses `data.shop` (e.g., to look up the session/store, update records, or dispatch background jobs keyed by shop), this enables cross-tenant data corruption/injection — writing attacker-controlled data into another merchant's store context. This matches the "cross-tenant access" high-impact category.

### Likelihood Explanation
Likelihood is high for any attacker who can install the target app on a shop they control (trivial for public apps, and even for private/dev apps distributed to any tester) — no special credentials, TLS interception, or the app's secret are required. Only network access to the app's public webhook callback URL is needed to replay the captured body/HMAC with a forged shop header.

### Recommendation
Bind the `shop`, `topic`, and `webhook_id` values into the signed payload verification, or otherwise cross-check the `shop-domain` header against a store's own record of installed shops/webhook subscriptions (e.g., via the `webhook_id` looked up server-side) before trusting it. At minimum, document loudly that `Registry.process` only authenticates the body, not the `shop`/`topic`/`webhook_id` headers, and that integrators must independently verify the shop is one their app has an active install/session for before acting on webhook data.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`.
2. Shopify sends a legitimately signed webhook: body `B`, header `x-shopify-hmac-sha256: H` (valid HMAC of `B` with the app's shared `api_secret_key`), `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker replays the exact same request to the app's webhook endpoint but changes the header to `x-shopify-shop-domain: victim.myshopify.com` (and/or changes `x-shopify-topic`).
4. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Registry.process` calls `Utils::HmacValidator.validate`, which only recomputes the HMAC over the untouched body `B` and succeeds.
5. The app's handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", topic: ..., body: B, ...)` and processes it as if Shopify sent this event for `victim.myshopify.com`.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
