### Title
Webhook `shop`, `topic`, and `webhook_id` fields are trusted without HMAC coverage, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body: `@raw_body`, which is the only data covered by the HMAC check performed in `Registry.process`. [1](#0-0) 

The `shop`, `topic`, `api_version`, and `webhook_id` values are all read directly from HTTP headers and are never included in the signed material: [2](#0-1) 

`Registry.process` validates the HMAC over `to_signable_string` (body only) and then dispatches the handler using the unauthenticated `request.topic`, passing the unauthenticated `request.shop` straight into `WebhookMetadata`, which the host application's handler treats as the authoritative tenant identifier: [3](#0-2) 

`WebhookMetadata` is a plain struct with `shop` and `topic` fields consumed as trusted routing/tenant data by the handler: [4](#0-3) 

`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (the body) and the app's `api_secret_key`, which is identical for every shop the app is installed on: [5](#0-4) 

**Broken binding (as an equality):** the code implicitly assumes
`hmac_valid(raw_body, api_secret_key) == true` implies `request.shop == the shop that generated raw_body`.
This equality does not hold, because `shop` (and `topic`, `webhook_id`) are never part of the signed payload — only `raw_body` is. Since the app's `api_secret_key` is the same across every shop that has the app installed, any HMAC computed by Shopify for a genuine webhook delivered to Shop A (where the attacker is a legitimate, unprivileged merchant/developer who installed the app on their own store) remains a *valid* signature for that exact `raw_body` regardless of which `x-shopify-shop-domain` header accompanies it.

### Impact Explanation
An attacker who has installed the target app on their own (unprivileged) store receives real webhooks with valid `hmac-sha256` values computed from the app's shared `api_secret_key`. Because the shop/topic headers are unauthenticated, the attacker can replay the exact same `body` + `hmac` pair to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` header (and/or `x-shopify-topic`) with a victim shop's domain. `HmacValidator.validate` will still pass since only the body is checked, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload originated from the victim tenant. This is a cross-tenant identity-binding failure: the host application's per-tenant business logic (e.g., updating records, triggering redact/data flows, invoking `shop/redact`-style mandatory topics) can be made to fire against a shop the attacker never had legitimate access to, using data (body) that actually belongs to the attacker's own store. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Requires only: (1) the attacker to install the vulnerable app on any store they control (a normal, unprivileged action available to anyone with a Shopify account), (2) capture one genuine webhook delivery (trivial, since webhooks are delivered in plaintext HTTP(S) to the app's registered endpoint), and (3) replay it with a forged `shop`/`topic` header to the same public endpoint. No access token, `api_secret_key`, or privileged account for the *target* shop is needed. Likelihood is high given the endpoint is intentionally public to receive Shopify's webhook POSTs.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) values in the HMAC-signed material, or otherwise cryptographically bind them to the body before trusting them for tenant routing. If Shopify's webhook payload already embeds the shop domain inside the JSON body (as it typically does for most topics), `to_signable_string`/`Registry.process` should cross-check `request.shop` (header) against the shop identifier embedded in the verified body before constructing `WebhookMetadata`, rejecting any mismatch.

### Proof of Concept
1. Attacker installs the vulnerable app on `attacker-shop.myshopify.com`.
2. Shopify delivers a legitimate webhook to the app's endpoint:
   - headers: `x-shopify-topic: orders/create`, `x-shopify-hmac-sha256: <valid_hmac_for_body>`, `x-shopify-shop-domain: attacker-shop.myshopify.com`
   - body: `{"id": 123, ...}`
3. Attacker replays the same body and hmac header to the same public endpoint, but changes only:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
4. `ShopifyAPI::Webhooks::Request.new` parses the forged headers/body. [6](#0-5) 
5. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `raw_body` against the app's shared `api_secret_key` — the same secret used for the genuine "attacker-shop" delivery. [7](#0-6) 
6. The registered handler receives `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...)` and the host application processes attacker-controlled data as if it belongs to `victim-shop.myshopify.com`, i.e., cross-tenant data injection/confusion.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

        def validate(verifiable_query)

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
