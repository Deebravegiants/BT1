## Finding

### Title
Webhook HMAC signature does not bind the `shop` (tenant) field, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, and nothing else: [1](#0-0) 

```ruby
sig { override.returns(String) }
def to_signable_string
  @raw_body
end
```

`Registry.process` accepts the request purely based on this body-only HMAC check, and then forwards the *unauthenticated* `shop` header straight to the app's handler as the tenant identifier: [2](#0-1) 

The `shop` value read by `Request#shop` comes directly from the `x-shopify-shop-domain` / `shopify-shop-domain` header and is never included in the HMAC-signed content: [3](#0-2) 

`Utils::HmacValidator.validate` only verifies that the supplied `hmac` matches `HMAC(secret, to_signable_string)` — i.e. `HMAC(client_secret, raw_body)` — and says nothing about which shop the request originated from: [4](#0-3) 

**Broken identity binding**: `shop_claimed_by_header == shop_the_HMAC_actually_authenticates_for`. The HMAC only authenticates *"this body byte-string was produced by someone possessing `client_secret`"*; it does not authenticate *"this body belongs to shop X"*. Because a single app's `client_secret` is shared across every shop that installs the app, any merchant who installs the app can trivially obtain a **valid `(body, hmac)` pair** by triggering an event on their own store (e.g. creating an order, which fires `orders/create`). That pair is signed with the exact same secret used for all other merchants' webhooks.

An attacker (an ordinary, unprivileged merchant with no special access to the target shop, no access token, and no knowledge of `client_secret`) can then:
1. Install the target Shopify app on their own store.
2. Trigger a webhook event, capturing the legitimate `raw_body` + `x-shopify-hmac-sha256` header Shopify sent them.
3. Replay that exact `(raw_body, hmac)` pair directly to the app's public webhook endpoint, but substitute the `x-shopify-shop-domain` header with the victim shop's domain.

`Utils::HmacValidator.validate` will still return `true` (the body and HMAC are genuinely valid for the shared secret), so `Registry.process` will invoke the app's handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain, while the actual payload content is the attacker's own data.

### Impact Explanation
This is a cross-tenant identity-binding bypass: the value host applications use to key per-tenant data (`data.shop` in `WebhookMetadata`, per `docs/usage/webhooks.md` and `lib/shopify_api/webhooks/registry.rb`) is attacker-controlled and unauthenticated. A downstream app that persists webhook data keyed by `shop` (e.g., updating order/customer records, triggering per-shop business logic, or looking up the shop's session to make authenticated API calls) can be tricked into associating attacker-supplied data with any other shop domain, i.e., cross-tenant data injection/corruption — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Moderate-to-high: it requires only that the attacker be a legitimate (even free-trial) installer of the target app on their own store — no leaked credentials, no `client_secret`, no access token, and no privileged account are needed. The webhook endpoint is a public HTTP(S) endpoint accepting arbitrary internet traffic, so header spoofing is trivial for anyone who can send raw HTTP requests.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) values into the signed content actually verified, or independently verify that the shop header corresponds to a shop that is legitimately expected to be delivering this specific `(topic, body)` combination (e.g., look up an installed/active session for that shop before trusting `request.shop`, and/or maintain a per-shop webhook secret/HMAC context rather than relying solely on the app-wide `client_secret`). At minimum, document that host applications must independently validate `data.shop` against a known/installed shop record before using it as a trust boundary.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`.
2. Attacker triggers `orders/create` on their own store, capturing the legitimate webhook `raw_body` and `x-shopify-hmac-sha256` header (both valid for the app's shared `client_secret`).
3. Attacker POSTs the same `raw_body` and `x-shopify-hmac-sha256` to the target app's public webhook URL, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` parses `shop` from the spoofed header; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `raw_body` against the shared secret.
5. The registered handler executes with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, even though the payload actually originates from the attacker's own shop.
