Based on my research, I found a concrete analog to the reported bug class (missing bounds validation on a timestamp parameter that can permanently disable a critical user-facing function).

### Title
Unbounded `open_time` in `Initialize2` can permanently freeze swaps in a pool - (File: program/src/processor.rs)

### Summary
`process_initialize2` accepts an attacker/pool-creator-controlled `open_time` value with no upper-bound validation. This value is stored as `amm.state_data.pool_open_time` and used to gate the pool's initial trading status. If `open_time` is set to an arbitrarily large value (e.g. close to `u64::MAX`), the pool is permanently stuck in `AmmStatus::WaitingTrade`, and all four swap instructions will perpetually reject trades, freezing the pool's economic function for any depositor/LP that trusted the pool.

### Finding Description
`InitializeInstruction2::open_time` is a raw `u64` supplied entirely by the caller of `Initialize2` with no minimum/maximum bound checks in `process_initialize2`: [1](#0-0) 

The only place `open_time` is validated at all is an equality/ordering comparison against `Clock::get()?.unix_timestamp` to decide the initial `amm.status`: [2](#0-1) 

`open_time` is persisted verbatim into `amm.state_data.pool_open_time` via `StateData::initialize`, with no range check: [3](#0-2) 

Every swap entrypoint (`SwapBaseIn/Out`, `SwapBaseIn/OutV2`) re-checks this same field against the current clock and only transitions the pool out of `WaitingTrade` once `clock.unix_timestamp >= pool_open_time`: [4](#0-3) [5](#0-4) 

If `open_time` is set to a value far in the future (or effectively unreachable, e.g. `u64::MAX`), the pool never transitions to `SwapOnly`, and every swap call permanently returns `AmmError::InvalidStatus`. The only remediation path, `process_set_params` with `AmmParams::SetOpenTime`, requires a privileged `amm_owner` signer: [6](#0-5) 

An ordinary pool creator invoking `Initialize2` (an unprivileged, permissionless instruction reachable in a single transaction with attacker-chosen `open_time` data) can trigger this state with no protocol-level defense — mirroring exactly the reported bug class: an unvalidated timestamp/duration parameter that can permanently strand the intended functionality/funds absent admin intervention.

### Impact Explanation
Swaps are the core liquidity function of the AMM pool; once frozen, coin/pc vault funds already deposited by the pool creator (and by any subsequent LPs who deposit prior to noticing the issue) cannot be traded against, and the pool is functionally dead until a privileged `amm_owner` manually calls `SetParams` with `SetOpenTime`. If the pool's designated `amm_owner` is unresponsive, unavailable, or the misconfiguration goes unnoticed, swap functionality — and by extension, price discovery/liquidity for those already-deposited funds — is frozen indefinitely, matching the "funds could be stuck forever" impact class from the report.

### Likelihood Explanation
Low-to-medium likelihood: it requires a configuration mistake (or deliberate griefing) by whoever submits the `Initialize2` transaction — since `Initialize2` is fully permissionless and takes `open_time` as raw untrusted instruction data, any pool creator (malicious or careless) can set this field to an extreme value. No signer privilege beyond a normal wallet is needed to trigger it, which is a lower barrier than the admin-misconfiguration precondition assumed in the original report.

### Recommendation
Add an explicit bound check on `open_time` in `process_initialize2`, e.g. reject values further than some reasonable maximum window (for example, days/weeks) from `Clock::get()?.unix_timestamp`, mirroring the report's recommendation of capping the analogous `_duration`/`endTime` window in `Vesting`/`DutchAuction`. This prevents a pool from ever entering a state where legitimate trading is unreachable without privileged intervention.

### Proof of Concept
1. Attacker (any wallet) derives all required PDAs/accounts and calls `Initialize2` with `open_time = u64::MAX` (or any timestamp far beyond any reasonable operational horizon).
2. `process_initialize2` accepts this value unchecked and calls `amm.initialize(..., init.open_time, ...)`, storing it in `state_data.pool_open_time`; because `init.open_time > Clock::get()?.unix_timestamp`, `amm.status` is set to `AmmStatus::WaitingTrade` [7](#0-6) .
3. Any subsequent `SwapBaseIn`/`SwapBaseOut`/`SwapBaseInV2`/`SwapBaseOutV2` call hits the `WaitingTrade` branch, compares `clock.unix_timestamp < pool_open_time` (true forever, practically), and returns `AmmError::InvalidStatus`, permanently blocking all swaps against this pool [4](#0-3) .
4. Recovery is only possible via the privileged `SetParams`/`SetOpenTime` path gated on `config_feature::amm_owner::ID`, which the pool creator (an unprivileged actor) does not control [8](#0-7) .

Note: I was unable to fully confirm within the available tool budget whether `Deposit`/`Withdraw` are also gated by the same `WaitingTrade`/status check (I could not retrieve the `AmmStatus` permission-method definitions in `state.rs` before running out of iterations), so I cannot definitively state whether LP withdrawals remain possible while swaps are frozen — this would affect the precise scope of "stuck funds" versus "frozen trading function only." I recommend verifying `AmmStatus::deposit_permission()`/`withdraw_permission()` definitions to fully bound the impact.

    pub fn process_set_params(
        program_id: &Pubkey,
        accounts: &[AccountInfo],
        setparams: SetParamsInstruction,
    ) -> ProgramResult {
        let account_info_iter = &mut accounts.iter();

        let amm_info = next_account_info(account_info_iter)?;
        let amm_owner_info = next_account_info(account_info_iter)?;

        let mut amm = AmmInfo::load_mut_checked(&amm_info, program_id)?;

        if amm_info.owner != program_id {
            return Err(AmmError::InvalidOwner.into());
        }
        if !amm_owner_info.is_signer || *amm_owner_info.key != config_feature::amm_owner::ID {
            return Err(AmmError::InvalidSignAccount.into());
        }

        let param = setparams.param;
        match AmmParams::from_u64(param as u64).unwrap() {
            AmmParams::Status => {
                match setparams.value {
                    Some(status) => {
                        if AmmStatus::valid_status(status) {
                            amm.status = status as u64;
                        } else {
                            return Err(AmmError::InvalidInput.into());
                        }
                    }
                    None => return Err(AmmError::InvalidInput.into()),
                };
            }
            AmmParams::State => {
                match setparams.value {
                    Some(state) => {
                        if AmmState::valid_state(state) {
                            amm.state = state as u64;
                        } else {
                            return Err(AmmError::InvalidInput.into());
                        }
                    }
                    None => return Err(AmmError::InvalidInput.into()),
                };
