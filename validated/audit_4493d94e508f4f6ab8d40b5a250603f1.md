### Title
Webhook `shop` identity is not covered by the HMAC, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw body alone, while the shop identity dispatched to the host application's handler is read from an unauthenticated header. Anyone who can obtain one validly-HMAC'd webhook body/signature pair (e.g., the operator of their own Shopify store, who legitimately receives valid webhooks for their own shop) can replay that exact body+HMAC while substituting an arbitrary `shop-domain` header, and `Utils::HmacValidator.validate` will still report success.

### Finding Description
The binding the library should guarantee is: `HMAC-verified bytes == data attributed to `shop`. Instead:

- `Request#to_signable_string` returns only `@raw_body` ( [1](#0-0) ).
- `Request#shop` is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header, entirely outside the signed content ( [2](#0-1) ).
- `HmacValidator.validate` verifies `verifiable_query.hmac` against `verifiable_query.to_signable_string` only — it never inspects or binds `shop` ( [3](#0-2) ).
- `Registry.process` raises only if the HMAC over the body fails, then forwards the unauthenticated `request.shop` straight to the host app's handler as the tenant identity ( [4](#0-3) ).

Contrast this with `ShopifyAPI::Auth::Oauth::AuthQuery`, where `shop` **is** part of the signed content (`to_signable_string` includes `code, host, shop, state, timestamp`) ( [5](#0-4) ) — the webhook path lacks the equivalent binding.

Before: attacker replays `(raw_body, hmac)` pair legitimately obtained for `shop=attacker-shop.myshopify.com` with header `shop-domain: attacker-shop.myshopify.com` → HMAC valid, `data.shop == attacker-shop.myshopify.com`.
After attacker's request: same `(raw_body, hmac)` replayed with header `shop-domain: victim-shop.myshopify.com` → HMAC still valid (body unchanged), but `data.shop == victim-shop.myshopify.com`, a value the HMAC never covered.

### Impact Explanation
This breaks the tenant-isolation guarantee the gem's webhook API is documented to provide: `WebhookMetadata` (`data.shop`) is presented to host applications as an authenticated attribute they can use to route/attribute the event to a merchant's data. Since the shop is unauthenticated, an attacker who controls (or has previously received) any one valid webhook body/HMAC pair for any topic can attribute that payload to any other shop domain of their choosing, enabling cross-tenant data confusion in any host app that trusts `data.shop` without independent verification, matching the "cross-tenant access" impact bucket.

### Likelihood Explanation
Likelihood is constrained: the attacker needs at least one genuine `(raw_body, hmac)` pair, which they can obtain trivially by installing the app on their own (attacker-controlled) shop and capturing any webhook Shopify sends them — no secret key or privileged access is required. From there, forging the `shop-domain` header on a replayed HTTP request is straightforward since it is a plain header value with no cryptographic binding, so the practical bar to exploit is low once one legitimate delivery has been observed.

### Recommendation
Include the shop domain (and ideally the topic/webhook-id) in the HMAC-signable content, or otherwise cryptographically bind them, e.g. have `Request#to_signable_string` incorporate `shop`/`topic` alongside `@raw_body`, and update `HmacValidator`/`Registry.process` to verify that binding before trusting `request.shop`.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com`; Shopify delivers a webhook with body `B` and header `x-shopify-hmac-sha256: H` where `H = HMAC-SHA256(api_secret_key, B)`, plus `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker captures `B` and `H` (they own this shop and can log all inbound webhook traffic to their own endpoint, or capture it via a local proxy before forwarding to the app).
3. Attacker sends a new HTTP request to the app's webhook endpoint with the same body `B`, same header `x-shopify-hmac-sha256: H`, but `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC-SHA256(api_secret_key, B)` and compares to `H` — matches, since `to_signable_string` only used `B` ( [1](#0-0) ).
5. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...)` ( [6](#0-5) ), causing any host app that trusts `data.shop` to process/store the payload against the wrong tenant.
