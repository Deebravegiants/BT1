### Title
POA batch withdrawals of the same token are matched only by `assetId`, causing `describeWithdrawal` to report the same (status, txHash) for distinct withdrawals - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`findMatchingWithdrawal` in `poa-bridge.ts` matches the POA bridge status API response purely by `nep141:<near_token_id> === assetId`, ignoring which of the possibly multiple withdrawals of that same token in the batch it belongs to. When a batch contains two withdrawals of the same token (`withdrawalParams: [a, b]` both `nep141:<same>`), `describeWithdrawal` invoked for index 0 and index 1 both query by the same `withdrawal_hash` (the shared intent tx hash) and `Array.prototype.find` returns the *first* array element matching the assetId for both calls, regardless of index.

### Finding Description
The invariant that should hold is: for withdrawal index `i` in a batch, `describeWithdrawal({..., index: i})` returns the (status, txHash) belonging to the intent's `i`-th distinct withdrawal instruction, and `completed` is returned only once that specific transfer is final.

The code path is:
- `createWithdrawalIdentifiers` (`packages/intents-sdk/src/core/withdrawal-watcher.ts:80-107`) assigns each withdrawal an `index` per bridge route, and builds a `WithdrawalIdentifier` with the *same* `tx` (the shared `intentTx`) for every withdrawal in the batch.
- `watchWithdrawal` (`withdrawal-watcher.ts:20-77`) polls `bridge.describeWithdrawal({...args.wid})` for each identifier independently.
- `PoaBridge.describeWithdrawal` (`poa-bridge.ts:313-343`) calls `getWithdrawalStatusWithRetry` keyed by `args.tx.hash` only [1](#0-0) , which — since `tx.hash` is identical for both withdrawals in the batch — returns the *same* `response.withdrawals` array to both the index-0 and index-1 calls.
- It then calls `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)` [2](#0-1) , which does `withdrawals.find((w) => nep141:${w.data.near_token_id} === assetId)` [3](#0-2) .

Because both withdrawals in the batch share the same `assetId` (`nep141:<same>`), this `.find()` call returns the **same first-matching element** of the array for *both* index 0 and index 1 lookups. The code's own comment explicitly documents this limitation: "Currently only matches by assetId. This means multiple withdrawals of the same token in a single transaction are not supported" [4](#0-3) .

Consequently, if withdrawal #0 (e.g., to address A) is `COMPLETED` while withdrawal #1 (to address B) was refunded, failed, or never executed, whichever entry happens first in the (unsorted) API response array is reported for *both* indices. `watchWithdrawal` then resolves both promises with `{ hash: transfer_tx_hash }` as `completed` [5](#0-4) . An integrator that credits a user or releases funds based on `(status, txHash)` per index will thus credit both withdrawals as completed against the same underlying transfer — a status/hash misreport enabling double credit.

None of the existing guards (`validateAddress`, `compareAddresses`, `validateWithdrawal`, `supports()` ordering, `assert` sanity checks) prevent this, because they operate at intent-construction time, not at the status-matching stage, and the intents contract's own signature/nonce checks don't constrain the POA bridge's off-chain status API matching logic.

### Impact Explanation
The misreport occurs in the withdrawal-status reporting layer that integrators are expected to rely on for crediting/refunding logic (`(status, txHash)` returned per index via `watchWithdrawal`/`waitForWithdrawalCompletion`). Two withdrawals of the same token in one batch can both resolve to `completed` with the identical `txHash`, even though only one transfer actually completed. This matches the High-severity category: "a status or hash misreport making an integrator credit or refund twice." It's repeatable on every batch that contains ≥2 withdrawals of the same NEP-141 token, and is entirely attacker/user controlled since the batch composition (`withdrawalParams[]`) is chosen by whoever calls the SDK's withdrawal API.

### Likelihood Explanation
Preconditions: the withdrawal batch must include two (or more) withdrawal legs for the same `assetId` (i.e., `nep141:<near_token_id>` identical) — trivially satisfiable by any ordinary user constructing their own withdrawal request (e.g., splitting a withdrawal to two different destination addresses of the same token). No privileged access or bridge/relayer collusion required — this is a pure client-input/matching-logic gap acknowledged in the code itself. Feasibility is high and the condition is fully reproducible with mocked HTTP responses.

### Recommendation
`findMatchingWithdrawal` must disambiguate between multiple withdrawals of the same token within a batch instead of matching only on `assetId`. As hinted in the existing code comment, options include: matching by amount (after accounting for fees) combined with sorting both the API response and the withdrawal params deterministically, or (preferably) working with the POA bridge team to expose a per-withdrawal-index or per-destination-address correlation ID in the status API so that `describeWithdrawal` can uniquely map each `WithdrawalIdentifier.index` to its corresponding API record. Until such disambiguation exists, the SDK should refuse to report `completed` for ambiguous batches (i.e., batches containing multiple withdrawals of the same token) or explicitly document/enforce this as an unsupported configuration to prevent double-crediting by integrators.

### Proof of Concept
Vitest plan (mock only the POA bridge HTTP client `getWithdrawalStatus`):
1. Build `withdrawalParams = [{assetId: "nep141:token.omft.near", amount: 100, destinationAddress: A}, {assetId: "nep141:token.omft.near", amount: 200, destinationAddress: B}]` with a shared `intentTx`.
2. Call `createWithdrawalIdentifiers({ bridges: [poaBridge], withdrawalParams, intentTx })`, yielding `wid[0].index === 0` and `wid[1].index === 1`, both with the same `tx.hash`.
3. Mock `poaBridge.httpClient.getWithdrawalStatus` to return, for that `withdrawal_hash`, `withdrawals: [{status: "COMPLETED", data: { near_token_id: "token.omft.near", transfer_tx_hash: "0xAAA" }}, {status: "REFUNDED", data: { near_token_id: "token.omft.near", transfer_tx_hash: "0xBBB" }}]` (order: completed first).
4. Call `poaBridge.describeWithdrawal({...wid[0]})` and `poaBridge.describeWithdrawal({...wid[1]})`.
5. Assert the broken equality: both calls return `{ status: "completed", txHash: "0xAAA" }`, i.e. `describeWithdrawal(wid[1])` incorrectly equals `describeWithdrawal(wid[0])`, even though withdrawal #1 was actually `REFUNDED` with `txHash "0xBBB"`. The correct expected behavior (currently violated) is `describeWithdrawal(wid[1])` should equal `{ status: "failed", reason: "REFUNDED" }`.

function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
