### Title
Emporium Min-proof path lets an unprivileged caller execute arbitrary calls from Emporium's identity with zero balance accounting - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol / contracts/CircomDataBuilder.sol)

### Summary
When `externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `erc20TokenAddresses.length == 0`, `formInputForCircom` routes to `formInputEmporiumMin`, which only proves `message == Poseidon(messageSeed)` — a value the attacker freely chooses. Combined with `EmporiumStack.signerAddress == address(0)`, `verifyWallet` skips signature verification entirely, and the `runAction` op loop and both balance-accounting loops (in `Hinkal.transact` and in `EmporiumUpgradeable.runAction`) iterate zero times because they are bounded by `circomData.erc20TokenAddresses.length`.

### Finding Description
The broken equality: "assets Emporium can move in a tx" should equal "assets accounted for in `balancesBefore`/`balancesAfter`". With `erc20TokenAddresses = []`, the RHS is forced to zero regardless of what the LHS actually is, because every accounting loop is keyed off this same empty array: [1](#0-0) [2](#0-1) [3](#0-2) 

Path:
1. `Hinkal.transact` → `hinkalHelper.performHinkalChecks` → `CircomDataBuilder.formInputForCircom` selects `formInputEmporiumMin` because `externalActionId == HINKAL_EMPORIUM_ACTION_ID && erc20TokenAddresses.length == 0`: [4](#0-3) 
2. The min circuit only constrains `message = Poseidon(messageSeed)`; `outTimeStamp`/`calldataHash` are declared public inputs but never used in any circuit constraint: [5](#0-4)  — since an unprivileged attacker generates their own proof for their own chosen calldata, this is trivially satisfiable.
3. `dimensionsCheck` and `checkOnchainCreation` only iterate arrays sized by `dimensions.tokenNumber`, which the attacker sets to 0, so both pass vacuously: [6](#0-5) [7](#0-6) 
4. `_externalTransact` builds `deltaAmountChanges` of length 0 and calls `runAction`: [8](#0-7) 
5. In `EmporiumUpgradeable.runAction`, `verifyWallet` is bypassed entirely for `signerAddress == address(0)`: [9](#0-8) 
6. The op loop then executes CASE 2 ("Stateless Interaction") for every op, since `stack.signerAddress != address(0)` is false, calling `op.endpoint.call{value: op.value}(op.callData)` directly with Emporium as `msg.sender`, restricted only from calling the `callHinkalWallet`/`doSendToRelay` selectors — any other target/selector is unrestricted: [10](#0-9) 
7. Because `circomData.erc20TokenAddresses` is empty, the pre/post balance loops in both `runAction` and `Hinkal.transact` (which enforce `balanceDif == amountChanges[i] + utxoAmount` and the slippage requirement) never execute for any token, so nothing constrains what the ops actually moved.

This confirms the root cause claimed in the question: the accounting invariant is trivially satisfied (0 == 0) while the ops loop is unconstrained, and the `EmporiumStack` signature check is fully bypassed when `signerAddress == 0`.

However, exploiting this for *theft* requires Emporium to already hold assets the attacker doesn't own (native ETH via its `receive()` function, ERC20 dust, or an external contract's approval/trust granted to Emporium's address) — the attacker's own transaction moves none of their own funds through the token array, so they cannot use this path to pull funds that are held elsewhere in Hinkal's own balance or other users' shielded UTXOs (those require nullifiers/roots and non-empty token arrays that this path never touches). I could not find, within this repo, any privileged function in `HinkalHelper` or any router contract (`LifiExternalAction`/`ExternalActionSwap`) that specifically trusts `msg.sender == Emporium address` for elevated authorization — `HinkalHelper.onlyHinkal` checks `msg.sender == hinkalAddress` (the `Hinkal.sol` contract), not Emporium, and I was unable to fully inspect `contracts/external-actions/emporium/HinkalWallet.sol` and `contracts/types/IHinkalWallet.sol` before running out of iterations to confirm or rule out such a trust relationship there.

### Impact Explanation
If Emporium ever holds a balance (native ETH sent to its `receive()`, ERC20 dust from imperfect sweeps, or a third-party approval/trust granted to the Emporium address), any unprivileged actor can drain it with zero deposit and zero signature, since the op loop is fully attacker-controlled and unaccounted-for. This matches Critical severity ("direct theft of shielded or in-flight user funds") *only if* such a pre-existing balance or external trust relationship in Emporium can be shown to exist through a code path other than "funds sent by user mistake" (explicitly out of scope). I was not able to conclusively identify a concrete such balance/trust relationship in the reachable code (e.g., `HinkalWallet.sol` was not fully reviewed), so this cannot be confirmed as a complete, reproducible theft absent that missing piece.

### Likelihood Explanation
The accounting bypass itself (min-proof path, empty token array, `signerAddress == 0` skipping signature verification, unconstrained op loop) is fully attacker-reachable with no privileged role, at the cost of one transaction and a self-generated Groth16 proof for `MainEVMCircuitMin`. Its exploitability for actual asset theft is conditional on Emporium holding value or being granted trust by another contract, which I could not confirm from the parts of the codebase reviewed.

### Recommendation
1. In `EmporiumUpgradeable.runAction`, do not allow `signerAddress == address(0)` to bypass signature verification when `stack.ops.length > 0`; require a valid signature for any state-changing op regardless of token count.
2. Do not permit the Emporium min-proof path (`formInputEmporiumMin`) to be combined with a non-empty `EmporiumStack.ops` array — enforce in `CircomDataBuilder.formInputForCircom` or `EmporiumUpgradeable.runAction` that `erc20TokenAddresses.length == 0` implies `stack.ops.length == 0` (i.e., the min path may only be used for pure message-passing/no-op executions), or alternatively require `dimensions.tokenNumber > 0` for any Emporium action carrying `ops`.
3. Ensure Emporium never accumulates a residual balance across transactions (verify `receive()` usage and full-sweep invariants), reducing the blast radius even if the above ops-gating regresses.

### Proof of Concept
Given the confirmed but incomplete trust-boundary analysis (specifically the unresolved question of whether `HinkalWallet`/`IHinkalWallet` or any router trusts Emporium's `msg.sender` identity, and whether Emporium can hold pre-existing balance through a non-mistake code path), a fully reproducible Foundry theft PoC cannot be finalized from this review alone. A Devin session with full repository/tool access should be used to inspect `contracts/external-actions/emporium/HinkalWallet.sol` and `contracts/types/IHinkalWallet.sol` for such a trust relationship, and then build the PoC:
1. Deploy Hinkal + HinkalHelper + EmporiumUpgradeable per repo constructors, register Emporium as `allowedRecipient` of itself and register `HINKAL_EMPORIUM_ACTION_ID → Emporium` in `Hinkal.externalActionMap`.
2. Fund Emporium with a token balance via a route other than "user mistake" (only valid if such a route is found in `HinkalWallet.sol`/router integration).
3. Craft `CircomData` with `erc20TokenAddresses = []`, `dimensions.tokenNumber = 0`, `externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `externalActionMetadata` = ABI-encoded `EmporiumStack{signerAddress: address(0), ops: [{endpoint: token, invokeWallet: false, value: 0, callData: transfer(attacker, balance)}]}`.
4. Generate a `MainEVMCircuitMin` proof locally for the chosen `messageSeed`/`timeStamp`/`calldataHash`.
5. Call `Hinkal.transact(...)` from an unprivileged EOA and assert: Emporium's token balance before > 0, after == 0, attacker balance increased by the same amount, while `oldBalances == newBalances == []` in `Hinkal.transact` (i.e., the equality `balanceDif == amountChanges[i] + utxoAmount` was never evaluated for the drained token).
