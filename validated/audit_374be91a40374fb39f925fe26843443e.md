### Title
Phantom price snapshot's liquidity weight is a spot token balance, letting a solver flash/self-fund inventory to dictate the published `LiquidityPool` rate used to price real orders - ([File: sdk/packages/sdk/src/protocols/intents/phantom-aggregation.ts])

### Summary
`aggregatePhantomBids` weights each solver's phantom-order quote by a plain point-in-time balance read (`getTotalSolverBalance` / `getBalance`, wallet ERC-20 + ERC-4626 `maxWithdraw`) and feeds those weights into `weightedMedian`, which is a *selection*, not a blend: whichever bidder controls over half the total weight has its exact quoted price published as the leg's `medianPrice`. That value flows unmodified into `updateLiquidityPools` → `LiquidityPool.sellRate`/`buyRate`, which `IntentGateway.quoteIntent` and `queryBuyAndSellRates` use by default to price real cross-chain intents.

### Finding Description
The weight used in the median is a raw, unlocked balance read at the current block, exactly analogous to the original report's reliance on live, easily-shiftable pool token balances to drive a financial calculation: [1](#0-0) 

`weightedMedian` explicitly documents that "a solver holding over half the leg's weight sets the published price verbatim": [2](#0-1) 

The flow doc for this path confirms this is the intended (if risky) mechanic, not a misunderstanding: [3](#0-2) 

Nothing bounds how large this weight can be relative to other participants, nothing time-locks it (it's read via `eth_call` at `"latest"`), and nothing checks it against the actual size the solver is bidding to fill — a solver only needs to (a) transiently hold (via a flash loan, an internal transfer between its own addresses, or borrowing) a balance of the leg's output token larger than every other bidder's combined balance at the moment the bid window's aggregation runs, and (b) submit a bid quoting whatever price it wants. Because `weightedMedian` treats this as a majority-weight selection rather than a depth-weighted average, one over-weighted solver's price becomes the leg's `medianPrice` outright.

That `medianPrice` is then normalized and written straight into `PoolChainLiquidity.rate`/`LiquidityPool.sellRate`/`buyRate`: [4](#0-3) [5](#0-4) 

Those pool rates are the default pricing source for real intents placed through the SDK: [6](#0-5) [7](#0-6) 

### Impact Explanation
An attacker acting as (or impersonating via a flash-loaned/borrowed balance under) a verified solver can push a manipulated `medianPrice` into `LiquidityPool.sellRate`/`buyRate` for a token pair. Since `quoteIntent` defaults to pricing real user orders directly from these indexed rates with no other sanity check besides a >5x divergence *warning* (not a rejection) across chains: [8](#0-7) 
a user constructing an order from `quoteIntent` can be quoted (and then place an order at) a price far from the real market, letting the manipulating solver later fill that order at the distorted rate for guaranteed profit at the user's expense — the same class of impact as the original report (an attacker steers a manipulable balance-derived value to control the terms of an economically significant swap).

### Likelihood Explanation
Reachable by any account that can get itself delegated/verified as a solver's `SolverAccount` and submit a phantom bid (an ordinary, permissionless bidder action already exercised by the test suite), combined with a transient balance inflation technique (flash loan, or simply funding one address heavily right before the aggregation read and moving it elsewhere afterward) — no special privilege beyond normal solver participation is required, and the read is a single unauthenticated `eth_call` at `"latest"` with no minimum holding period.

### Recommendation
Do not let a single spot balance read grant majority weight over a price selection. Options: (1) require the weight to reflect capital actually committed/locked for the bid (e.g., escrowed or time-locked at bid submission, not read independently afterward), (2) cap any single solver's weight contribution to the median (e.g., a fraction of total weight), (3) replace balance-weighted "verbatim selection" with a depth-weighted blend so no single bidder can set the exact published number, and (4) sanity-check `medianPrice`/pool rate moves against a trusted external reference or historical rate before publishing, rejecting outlier moves outright rather than only logging a warning.

### Proof of Concept
1. Attacker controls (or is) a delegated solver account `S` and knows the destination chain and output token for an upcoming phantom order leg.
2. Just before/at the block the aggregation snapshot reads balances, `S` transiently acquires (via flash loan or internal transfer) an ERC-20 balance of the leg's output token exceeding the combined balances of every other bidding solver for that leg.
3. `S` submits a phantom bid quoting an arbitrary favorable price for that leg (`fillOrder` calldata inside the ERC-7821 batch, signed per `isVerifiedSolverBid`).
4. `aggregatePhantomBids` runs (`runAggregation`), reads `S`'s inflated balance as its weight [1](#0-0) , and `weightedMedian` selects `S`'s quoted price verbatim because it holds >50% of total weight [2](#0-1) .
5. `S` returns the borrowed/transferred tokens (they were never actually used to fill anything).
6. `updateLiquidityPools` writes this distorted `medianPrice` into `LiquidityPool.sellRate`/`buyRate`.
7. A subsequent user calling `quoteIntent`/`queryBuyAndSellRates` receives a quote built from the manipulated rate, and any order placed against it can be filled by `S` (or a colluding solver) at the distorted price.

export function weightedMedian(entries: { price: bigint; weight: bigint }[]): bigint {
	const sorted = [...entries].sort((a, b) => (a.price < b.price ? -1 : a.price > b.price ? 1 : 0))
	const totalWeight = sorted.reduce((acc, e) => (e.weight > 0n ? acc + e.weight : acc), 0n)

	if (totalWeight === 0n) {
		return sorted[Math.floor(sorted.length / 2)].price
	}

	let cumulative = 0n
	for (const entry of sorted) {
		if (entry.weight <= 0n) continue
		cumulative += entry.weight
		if (cumulative * 2n >= totalWeight) return entry.price
	}
	return sorted[sorted.length - 1].price
}

function mergeChainRowsIntoPool(pool: LiquidityPool, rows: PoolChainLiquidity[], referenceBlock: bigint): void {
	for (const direction of [SELL, BUY]) {
		const directionRows = rows.filter((row) => row.direction === direction)
		if (directionRows.length === 0) continue

		// Blocks are processed in order, so the difference is non-negative in practice; a row
		// from a "future" block would simply count as fresh, which is the right reading anyway.
		const fresh = directionRows.filter((row) => referenceBlock - row.lastUpdatedBlock <= MAX_SAMPLE_AGE_BLOCKS)
		const merged = fresh.length > 0 ? fresh : directionRows

		warnOnDivergentSample(pool.id, direction, merged)

		const depth = merged.reduce((acc, row) => acc + row.depth, 0n)
		const rate = weightedRate(merged)
		const bidCount = merged.reduce((acc, row) => acc + row.bidCount, 0)

		if (direction === SELL) {
			pool.sellRate = rate
			pool.sellDepth = depth
			pool.sellBidCount = bidCount
		} else {
			pool.buyRate = rate
			pool.buyDepth = depth
			pool.buyBidCount = bidCount
		}
	}
}

### quoteIntent(params)

Quotes an intent from the latest aggregate pool buy or sell rate published by the indexer. The pool rate is depth-weighted from fresh chain samples. Pass token addresses directly—the SDK resolves their configured symbols and decimals. No `strategy` option is needed for indexed-rate quotes.

Indexed-rate quotes require an attached Hyperbridge indexer client. There is no automatic fallback to another price source.

Use `amountIn` and `amountOut` when constructing the `inputs` and `output.assets` for an IntentGateway V2 order.
