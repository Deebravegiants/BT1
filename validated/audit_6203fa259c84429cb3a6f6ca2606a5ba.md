### Title
Unbounded `unknown_headers` in GRANDPA `FinalityProof` allows a permissionless unsigned message to trigger unbounded verification work - ([File: modules/consensus/grandpa/verifier/src/lib.rs])

### Summary
`pallet_ismp::handle_unsigned` accepts unsigned `Vec<Message>` from anyone, including `ConsensusMessage`s that reach `GrandpaConsensusClient::verify_consensus`, which calls `verify_grandpa_finality_proof` / `verify_parachain_headers_with_grandpa_finality_proof`. These functions operate over `FinalityProof::unknown_headers: Vec<H>` and `parachain_headers: BTreeMap<H256, ParachainHeaderProofs>`, both fully attacker/relayer-controlled with no upper bound on element count, mirroring the crypto/x509 bug class where `VerifyOptions.Intermediates` size was unbounded and drove unbounded chain-building work.

### Finding Description
`GrandpaJustification::verify_with_voter_set` and `AncestryChain::ancestry` (`modules/consensus/grandpa/primitives/src/justification.rs:157-198`) build a `BTreeMap<H::Hash, H>` from `self.votes_ancestries` / `finality_proof.unknown_headers` and then walk parent-hash chains through it. `verify_grandpa_finality_proof` (`modules/consensus/grandpa/verifier/src/lib.rs:44-104`) does this for `finality_proof.unknown_headers`, and additionally computes `target`/`base` via `.max_by_key`/`.min_by_key` scans and an `ancestry()` walk from `from` to `target.hash()` [1](#0-0) .

`verify_parachain_headers_with_grandpa_finality_proof` (`modules/consensus/grandpa/verifier/src/lib.rs:111-165`) then iterates every entry of the attacker-supplied `parachain_headers` map, performing a full patricia-trie `read_proof_check` per entry and decoding a header per key inside it [2](#0-1) . None of these code paths cap `unknown_headers.len()` or `parachain_headers.len()`; the only checks are correctness checks (`UnknownHeadersEmpty`, ancestry validity, justification signature), not size limits.

This whole path is reachable by an unsigned, permissionless extrinsic: `pallet_ismp::Pallet::handle_unsigned` explicitly documents "permits anyone execute ISMP messages for free, provided they have valid proofs" [3](#0-2) , and `validate_unsigned` re-executes the same `Self::execute(messages.clone())` during transaction-pool validation [4](#0-3) , meaning the unbounded decode/hash/trie work can be triggered twice per submission (once at validation, once at execution) without requiring a valid justification signature check to happen first — the header vector is materialized, hashed into a BTreeMap, and scanned before the (cheaper) signature check fails.

This is directly analogous to BIT-golang-2026-32280: an unbounded attacker-supplied list of "intermediate" artifacts (there: X.509 certs; here: GRANDPA headers / parachain-header proof entries) drives unbounded verifier work with no size limit enforced before that work is performed.

### Impact Explanation
An unsigned, fee-free extrinsic accepted by any node can carry an arbitrarily large `unknown_headers` vector and/or `parachain_headers` map. Processing it forces the runtime to SCALE-decode, hash, and walk this attacker-sized structure (and perform one trie-proof verification per parachain-header entry) before rejecting an otherwise-invalid justification. Because `handle_unsigned` is unsigned and is also invoked from `validate_unsigned` during gossip/pool validation, this allows a relayer/attacker to impose disproportionate CPU/memory cost on validating and executing nodes for a route with no bounded worst case, which fits "a route unable to deliver messages" under sustained abuse (validators/collators spend block time on unbounded verification instead of legitimate message delivery).

### Likelihood Explanation
The path requires only knowledge of the public `handle_unsigned` call and the `ConsensusMessage::Polkadot`/`Relaychain`/`StandaloneChain` wire format; it needs no privileged role, no valid signature, and no prior state — an unprivileged relayer/dispatcher submitting a crafted extrinsic can reach it directly.

### Recommendation
Enforce an explicit maximum on `FinalityProof::unknown_headers.len()` and on `parachain_headers.len()` (and per-entry `para_ids.len()`) before any hashing/decoding/trie work is performed in `verify_grandpa_finality_proof` and `verify_parachain_headers_with_grandpa_finality_proof`, and size the `handle_unsigned`/consensus-message weight to scale with the actual number of headers/proof entries supplied (or reject messages exceeding a fixed bound) so the charged weight and validation cost cannot be decoupled from attacker-controlled input size.

### Proof of Concept
1. Craft an unsigned `Message::Consensus(ConsensusMessage::Relaychain(...))` (or `Polkadot`) whose `FinalityProof.unknown_headers` contains a very large number of syntactically valid but otherwise arbitrary `Header` values, and whose `parachain_headers` BTreeMap contains many entries each with a bogus (but well-formed) storage proof.
2. Submit via `Ismp::handle_unsigned` (or via the transaction pool, which invokes `validate_unsigned` and thus runs `Self::execute` once for validation and again for execution).
3. Observe that `AncestryChain::new`, `.ancestry()`, and `verify_parachain_headers_with_grandpa_finality_proof`'s per-entry `read_proof_check` all execute proportionally to the attacker-chosen vector/map sizes before the (cheap) ed25519 justification-signature check or ancestry-mismatch check ultimately rejects the message — i.e., verification cost scales with attacker input with no enforced cap, for a message that costs nothing to submit.
