### Title
Webhook `shop-domain` header is trusted for tenant identification but is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content solely from the raw request body, while the `shop`, `topic`, `webhook_id`, and `api_version` values used by `ShopifyAPI::Webhooks::Registry.process` to route and label the event to the application's handler come from unauthenticated HTTP headers. This breaks the identity binding `shop verified by HMAC == shop trusted by the handler`, letting anyone who possesses one valid `(body, hmac)` pair — trivially obtainable as any legitimate merchant using the app — replay it while swapping the `shop-domain` header to impersonate a different, victim tenant.

### Finding Description
`Utils::HmacValidator.validate` recomputes the HMAC over `verifiable_query.to_signable_string` and compares it to the `hmac` field using `OpenSSL.secure_compare`: [1](#0-0) 

For webhooks, `Request#to_signable_string` returns only `@raw_body` — the JSON body — and nothing else: [2](#0-1) 

But `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all read straight from HTTP headers, none of which are part of the signed content: [3](#0-2) 

`Registry.process` validates only the HMAC of the body and then forwards these unauthenticated header values directly into `WebhookMetadata`, which is handed to the app's `WebhookHandler#handle`: [4](#0-3) 

`WebhookMetadata.shop` is a first-class `const :shop, String` field on the struct the gem hands to every app-provided handler as the trusted tenant identifier for that event: [5](#0-4) 

The identity binding that should hold is:
`shop authenticated by HMAC == shop delivered to the handler as WebhookMetadata#shop`

Because the HMAC only signs `@raw_body`, this equality does not hold: `shop-domain` (and `topic`/`webhook_id`/`api_version`) can be changed freely by anyone forwarding the request without invalidating the signature.

### Impact Explanation
This is a cross-tenant access vulnerability, per the accepted Critical impact category. Any single valid `(raw_body, x-shopify-hmac-sha256)` pair — which the gem's own `api_secret_key` is shared across all shops that install the app, not per-tenant — can be replayed against the app's webhook endpoint with an arbitrary `shop-domain` header. `Registry.process` will pass HMAC validation (since the body is unchanged) and hand the handler a `WebhookMetadata` claiming the event belongs to a different, attacker-chosen shop. An app that uses `WebhookMetadata#shop` to look up that shop's stored session/access token, update that shop's local records, or otherwise perform tenant-scoped writes (the standard, documented usage pattern) will act on behalf of, or against, a shop the attacker does not control, achieving cross-tenant data injection/corruption without ever possessing that shop's credentials.

### Likelihood Explanation
Likelihood is high given the "unprivileged internet user" threat model: obtaining one legitimate `(body, hmac)` pair requires no special privilege beyond being any merchant who has installed the app (which itself is a normal, unprivileged action) and triggering any webhook topic (e.g. `orders/create`) for their own store, then observing the raw POST the app receives. The gem performs no other binding check (no per-shop secret, no signed header set) before trusting the `shop-domain` header, so exploitation only requires basic HTTP tooling to resend the captured request with a modified header — no TLS interception, no leaked credentials, and no access to the app's `client_secret`.

### Recommendation
Include `shop-domain`, `topic`, `webhook_id`, and `api_version` in the signed/verified content (e.g., bind them into `to_signable_string`, or independently verify that the `shop-domain` header matches a shop the app has an active session/registration for before trusting it), so that any change to these fields invalidates the HMAC. At minimum, document prominently that `WebhookMetadata#shop`/`#topic`/`#webhook_id` are unauthenticated and must not be used by consuming apps as the sole tenant-identification mechanism without additional server-side verification (e.g., cross-checking against the shop associated with the currently registered webhook subscription id).

### Proof of Concept
1. As a normal merchant, install the target app on `attacker-shop.myshopify.com` and trigger any subscribed webhook topic (e.g. create an order) to receive a legitimate webhook POST:
   ```
   POST /webhooks
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid-hmac-of-body>
   x-shopify-shop-domain: attacker-shop.myshopify.com
   x-shopify-webhook-id: <id>
   x-shopify-api-version: 2024-01
   Body: {"id":123, ...}
   ```
2. Resend the exact same body and `x-shopify-hmac-sha256` value, but replace the header:
   ```
   x-shopify-shop-domain: victim-shop.myshopify.com
   ```
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `@raw_body` per `to_signable_string`, per [2](#0-1) ; validation succeeds unchanged.
4. The app's `WebhookHandler#handle` receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` per [6](#0-5)  and performs whatever tenant-scoped action it takes for that event against `victim-shop`, even though the event actually originated from `attacker-shop`.
