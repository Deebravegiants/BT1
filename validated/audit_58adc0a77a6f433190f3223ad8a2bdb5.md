### Title
Arbitrary external call in `EmporiumUpgradeable.runAction` allows draining any undeclared token/ETH balance held by the Emporium contract - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
`EmporiumUpgradeable.runAction()` executes attacker/user-controlled calls (`op.endpoint.call{value: op.value}(op.callData)`) exactly like JOJODealer's `Funding._withdraw()` did, and its only post-call safety invariant (`balanceChange < 0 → revert`) is scoped solely to the tokens the caller chooses to list in `circomData.erc20TokenAddresses`. Any ERC20 or native ETH balance sitting on the Emporium contract that is *not* included in that self-declared array is never balance-checked, so it can be swept to an arbitrary address by any user who can produce a valid (even trivial) zk proof.

### Finding Description
`Hinkal._externalTransact()` forwards `circomData` to the registered external action (Emporium) and calls `runAction`: [1](#0-0) 

Inside `EmporiumUpgradeable.runAction`, the caller-supplied `externalActionMetadata` is decoded into an `EmporiumStack` whose `ops[].endpoint`, `ops[].callData` and `ops[].value` are fully attacker controlled when no wallet signer is used (`stack.signerAddress == address(0)`), and `verifyWallet` in that branch does nothing but mark the nonce used - no signature or op-content check is performed: [2](#0-1) 

The loop then performs the raw call: [3](#0-2) 

The only protection against value leaking out of Emporium is the post-loop balance check, but it iterates only over `circomData.erc20TokenAddresses` - an array the caller freely constructs as part of `circomData`: [4](#0-3) 

Because `getBalancesForArray`/the invariant check only look at tokens explicitly declared by the caller, any ERC20 token (or native ETH, since Emporium has a `receive()` and `address(0)` represents ETH) that the Emporium contract already holds - e.g. residual balances left by prior swaps/relay-fee flows, dust, or funds temporarily routed through Emporium as part of a multi-op stateless flow - is completely outside the equality Emporium enforces (`balancesAfter == balancesBefore (+/- declared deltas)`). An attacker simply omits that token from `erc20TokenAddresses` and adds an `EmporiumOperation` whose `endpoint`/`callData`/`value` directly transfers that balance to themselves (e.g. `endpoint = token; callData = transfer(attacker, tokenBalance)`, or for ETH `endpoint = attacker; value = ethBalance; callData = ""`). This breaks the "value moved by an external action must be counted in the balance equation" invariant: value leaves the shared contract, but is never subtracted from `newBalances`/`oldBalances` for the token that matters, so `Hinkal.transact()`'s own outer slippage check on `circomData.erc20TokenAddresses` also never sees the theft (Hinkal only diffs balances for the tokens the same attacker-chosen array names).

### Impact Explanation
This is a direct analog of the JOJO H-1 bug class: an unprivileged EOA, using nothing but a valid proof for a trivial/self-owned UTXO, can move assets out of a shared protocol contract (Emporium) using a call whose target and calldata it fully controls, and that call is validated only for the assets it chose to declare. Any residual ETH/ERC20 balance belonging to the protocol/other in-flight transactions sitting on Emporium is stealable. This constitutes direct theft of protocol/relay/other-user funds held by the contract, satisfying the Critical/High impact bar (unauthorised asset movement not backed by the balance equation).

### Likelihood Explanation
Likelihood depends on Emporium actually holding an undeclared balance at call time (e.g., dust from previous partial ops, relay-fee remainders, or ETH sent via the unconditional `receive()`), which is plausible given the multi-op, stateful/stateless mixed design; whenever such a balance exists, exploitation requires only a single `transact()` call with a normal (even minimal) valid proof and a crafted `externalActionMetadata` - no admin/relayer/owner privilege needed.

### Recommendation
Do not scope the invariant check to a caller-chosen token list. Either (a) enforce that Emporium's balance for *every* token touched by any `op.endpoint`/`op.callData` cannot decrease unless explicitly and fully accounted for in `deltaAmountChanges`, (b) whitelist/restrict `op.endpoint` to known routers/tokens and disallow direct value transfers to arbitrary externally-owned addresses, or (c) sweep/zero out Emporium's balance for all supported tokens at the end of every `runAction` call rather than only for caller-declared ones, mirroring the JOJO fix of no longer allowing arbitrary `to`/`param` combinations.

### Proof of Concept
1. Emporium accumulates a balance of token `X` (or ETH) not tied to a currently in-flight `erc20TokenAddresses` entry (e.g., leftover from a previous multi-op stateless flow, or ETH sent directly to Emporium's `receive()`).
2. Attacker deposits a trivial UTXO and calls `Hinkal.transact()` with `externalActionData.externalActionId`/`externalAddress` pointing at Emporium, and `circomData.erc20TokenAddresses` deliberately excluding `X`.
3. `externalActionMetadata` decodes to an `EmporiumStack` with `signerAddress = address(0)` and one `EmporiumOperation{ endpoint: X, invokeWallet: false, value: 0, callData: abi.encodeCall(IERC20.transfer, (attacker, balanceOfX)) }` (or, for ETH, `endpoint: attacker, value: ethBalance, callData: ""`).
4. `verifyWallet` only marks the nonce used and returns (no signature check since `signerAddress == 0`).
5. The loop executes the call, draining `X`/ETH to the attacker.
6. The post-loop check only iterates the declared `erc20TokenAddresses` (which excludes `X`), so `balanceChange < 0` is never observed for the stolen asset and the transaction succeeds.
