## Title
Unbounded BEEFY vote-array length permits gas-exhaustion DoS in `EcdsaBeefy.verifyMmrUpdateProof` - (File: evm/src/consensus/EcdsaBeefy.sol)

### Summary
`EcdsaBeefy.sol` is the on-chain BEEFY consensus verifier reachable from any unprivileged relayer via `HandlerV2.handleConsensus` → `IConsensusV2.verify` → `verifyMmrUpdateProof`. The function sizes its authority/signature-processing loops directly off `relayProof.signedCommitment.votes.length`, a value fully controlled by the calldata submitter, with no upper bound check — only a lower-bound supermajority check is applied. This mirrors the CVE-2026-3505 bug class: an attacker-controlled size field drives unbounded work before any real cryptographic authentication of most of that work occurs.

### Finding Description
In `verifyMmrUpdateProof`: [1](#0-0) 

```
uint256 sigLen = relayProof.signedCommitment.votes.length;
...
if (!checkParticipationThreshold(sigLen, authoritySet.len)) revert SuperMajorityRequired();
...
MerkleMultiProof.Leaf[] memory authorities = new MerkleMultiProof.Leaf[](sigLen);
for (uint256 i = 0; i < sigLen; i++) {
    Vote memory vote = relayProof.signedCommitment.votes[i];
    address authority = ECDSA.recover(commitmentHash, vote.signature);
    authorities[i] = MerkleMultiProof.Leaf({index: vote.authorityIndex, hash: keccak256(abi.encodePacked(authority))});

```

`checkParticipationThreshold` (`evm/src/consensus/EcdsaBeefy.sol:241-243`) only enforces `sigLen >= (2*total)/3 + 1` — a **lower** bound relative to the trusted authority set size. There is no check that `sigLen <= authoritySet.len` (or any other hard cap). Because `votes` is attacker-supplied calldata for an unsigned/permissionless dispatch path, a caller can submit an arbitrarily large `votes` array (bounded only by calldata/gas limits), each entry containing a garbage-but-well-formed ECDSA signature. `ECDSA.recover` never reverts on a syntactically valid signature — it simply returns some (wrong) address — so every entry is processed and pushed into `authorities[]`, which is then fed into `MerkleMultiProof.VerifyProof`. This causes proportionally unbounded `ecrecover` calls, memory allocation, and merkle-proof verification work per transaction, in a case where nearly all the recovered "authorities" are bogus and only enough real signatures are needed to satisfy the threshold.

The Rust-side verifier (`modules/consensus/beefy/verifier/src/lib.rs:105-176`) exhibits the exact same pattern: `signatures_length = mmr.signed_commitment.signatures.len()` is checked only via `check_participation_threshold` against a lower bound before looping over every signature to run `secp256k1_recover`.

This differs qualitatively from the hardened analogs found elsewhere in the codebase (e.g. `pallet-call-decompressor`'s explicit `MaxCallSize` gate on a claimed size before decompression, or `pharos` verifier's `MAX_VALIDATORS`/`MAX_PROOF_DEPTH` caps, or BSC's fixed 64-bit `VALIDATOR_BIT_SET_SIZE`), all of which cap work at a maximum independent of the caller's claim. BEEFY's ECDSA path has no equivalent maximum.

### Impact Explanation
An unprivileged relayer can submit a BEEFY consensus message with a bloated `votes` array to `HandlerV2.handleConsensus`, forcing the `EvmHost`/verifier to perform many multiples of the necessary `ecrecover` and merkle-leaf-construction work. This inflates gas cost for the submitter but, more importantly, can be used to grief the verification path (e.g., pushing a transaction toward the block gas limit, causing consensus updates to fail to fit in a block, or forcing legitimate relayers into unpredictable gas estimation), disrupting the ability of the route to deliver messages — a form of resource-exhaustion DoS on the message-delivery pipeline for chains anchored to BEEFY. Because BEEFY consensus updates gate all downstream request/response delivery for the affected state machine, degrading their reliability can stall an entire route.

### Likelihood Explanation
Likelihood is moderate: `handleConsensus`/`verify` are open, permissionless entry points (any caller can submit a consensus proof), and constructing a "votes" array with valid-format-but-garbage secp256k1 signatures is trivial and cheap for an attacker (recovery never reverts). The only friction is calldata size/gas cost for the attacker themselves, and it only affects chains configured to use the ECDSA-BEEFY consensus client rather than the SP1 zk-verified variant.

### Recommendation
Add an explicit upper bound on `relayProof.signedCommitment.votes.length` (and the analogous `signatures.len()` in the Rust verifier) — e.g. reject if `sigLen > authoritySet.len` (a valid commit cannot have more distinct votes than authorities) — before allocating `authorities[]` or performing any `ECDSA.recover`/`secp256k1_recover` calls, mirroring the fixed caps already used by the BSC (`VALIDATOR_BIT_SET_SIZE`) and Pharos (`MAX_VALIDATORS`, `MAX_PROOF_DEPTH`) verifiers.

### Proof of Concept
1. Craft a `BeefyConsensusProof` whose `relay.signedCommitment.votes` array contains `N` entries where `N` is far larger than `authoritySet.len` (e.g., 10,000), with just enough entries (`>= 2/3+1` of `authoritySet.len`) holding genuine signatures from real authorities and the remainder holding arbitrary 65-byte values that are valid ECDSA signature encodings (any `(r,s,v)` with `v ∈ {27,28}` and `r,s` in curve order recovers to *some* address without reverting).
2. Call `HandlerV2.handleConsensus(ismpHost, abi.encode(previousState, proof))` with this payload.
3. Observe `verifyMmrUpdateProof` iterates all `N` entries in the `for` loop performing `ECDSA.recover` and building the `authorities` array, consuming gas linear in `N` rather than in the true authority-set size, well beyond what a legitimate proof requires — demonstrating the missing upper bound.
