### Title
Webhook `shop` Header Not Covered by HMAC Enables Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw request body only, while the `shop` identity used to route and label webhook data comes from an unsigned HTTP header. Because Shopify apps use a single, shared `api_secret_key` to sign webhooks for *every* installed shop, any shop that has legitimately installed the app can capture one of its own validly-signed webhook deliveries and replay it to the app's webhook endpoint while substituting the `x-shopify-shop-domain`/`shopify-shop-domain` header for a victim shop. The gem's HMAC check still passes because it never touches that header, and `ShopifyAPI::Webhooks::Registry.process` hands the attacker-chosen shop value straight to the app's handler.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

The `shop` accessor, however, is read straight from an HTTP header that is not part of that signable string: [2](#0-1) 

`Utils::HmacValidator.validate` (shared with the OAuth callback validator) only ever verifies `to_signable_string` against the secret: [3](#0-2) 

`Webhooks::Registry.process` performs exactly this HMAC check, then immediately trusts `request.shop` (the unsigned header) to build the `WebhookMetadata` that is dispatched to the app's handler: [4](#0-3) 

This is the "field acted on but not covered by the HMAC" pattern: the binding the app relies on is `shop_header == shop_that_produced(raw_body, hmac)`. Because Shopify signs webhooks with the **app-wide** `api_secret_key` rather than a per-shop secret, that equality does not hold — `(raw_body, hmac)` pairs are valid for *any* shop using the same app, and the header is free for anyone who can reach the webhook endpoint to set.

### Impact Explanation
Any shop that installs a multi-tenant app can:
1. Trigger/observe one of its own legitimate webhooks (a valid `raw_body` + `hmac-sha256` pair signed with the shared `api_secret_key`).
2. Replay that exact `raw_body`/`hmac` pair to the app's public webhook endpoint, but with the `shopify-shop-domain` header changed to a victim shop's domain.
3. `Registry.process` validates the HMAC successfully (it never checked the header) and calls the app's handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: attacker_controlled_json, ...)`.

Because most apps key their persisted webhook data (orders, inventory changes, customer data, uninstall/app-scope changes, etc.) by `data.shop`, this allows a malicious tenant to inject or overwrite data attributed to another merchant's tenant record — i.e., **cross-tenant access/data corruption** without ever needing the victim's or the app's credentials. Depending on the handler (e.g., `app/uninstalled`, `customers/redact`, or order-sync handlers), this can also be used to falsely trigger destructive or state-changing actions against a shop the attacker does not own.

### Likelihood Explanation
This requires only that the attacker be a legitimate (even trial) installer of the target app — no special privilege, no access to `api_secret_key`, and no interaction with the victim shop is needed. Capturing one's own webhook body/HMAC is trivial (it is delivered to the attacker's own endpoint or can be intercepted via a proxy), and replaying an HTTP POST with a modified header is elementary. The vulnerability is baked into the gem's `Webhooks::Request`/`Registry.process` contract, so every app relying on this gem's built-in webhook processing inherits the flaw unless it independently re-validates `shop` against something signed.

### Recommendation
Bind `shop` (and ideally `topic`/`api-version`) into the HMAC-verified material, or otherwise cross-check the header-derived `shop` against a value that Shopify actually signs (e.g., have `to_signable_string` combine the raw body with the shop/topic headers before hashing, matching a documented Shopify-side scheme), and reject the webhook if that check fails. At minimum, document prominently that `request.shop` is unauthenticated header data and must not be trusted for tenant identification without an out-of-band verification (e.g., confirming the shop has a currently valid, stored access token/session before acting on webhook data).

### Proof of Concept
1. App installs on `attacker-shop.myshopify.com`; Shopify sends a legitimate webhook:
   - Headers: `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid-hmac-of-raw-body>`
   - Body: `{"id": 1, "note": "hello"}`
2. Attacker captures `raw_body` and `x-shopify-hmac-sha256` (both are simply their own traffic).
3. Attacker replays the same POST to the app's webhook endpoint but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only hashes `raw_body` — it succeeds unchanged, per [1](#0-0) .
5. The handler receives `WebhookMetadata(shop: "victim-shop.myshopify.com", body: {"id":1,"note":"hello"}, ...)`, per [4](#0-3) , and the app persists/acts on this data as if it genuinely came from the victim shop.
