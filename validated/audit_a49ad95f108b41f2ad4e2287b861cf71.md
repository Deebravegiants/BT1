### Title
Webhook Shop-Domain Header Not Covered by HMAC Verification, Enabling Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content solely from the raw request body, while the `shop` (tenant identity) is read directly from the unauthenticated `X-Shopify-Shop-Domain` HTTP header. `ShopifyAPI::Webhooks::Registry.process` trusts this header value and forwards it to the application's webhook handler as the authoritative shop identity, without it ever being part of the signed payload.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is derived purely from the `shopify-shop-domain` / `x-shopify-shop-domain` header, independent of the signed body: [2](#0-1) 

`HmacValidator.validate` verifies the HMAC only against `to_signable_string` (the raw body), never incorporating the shop-domain header: [3](#0-2) 

`Registry.process` treats a passing HMAC check as proof the request "did indeed come from Shopify" for the shop indicated by the header, and hands `request.shop` straight to the app's handler: [4](#0-3) 

The documented usage pattern explicitly instructs developers to treat `data.shop` — sourced from this same unauthenticated header — as the verified tenant identity and to act on it (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) after calling `Registry.process`, which the docs describe as verifying "the request did indeed come from Shopify": [5](#0-4) [6](#0-5) 

This breaks the intended identity binding: `HMAC(raw_body, client_secret) == received_hmac` is treated as proof of `shop == header("shop-domain")`, but the header is never part of the signed bytes. This is the exact analog of the reported bug class — a field acted on (the shop/tenant identity) is not covered by the cryptographic check (the HMAC) that is meant to authenticate the whole request.

### Impact Explanation
Any actor who can obtain one genuinely signed webhook body+HMAC pair for their own shop's app installation (which every "unprivileged" merchant/developer who installs the app can trivially get, since Shopify sends them valid signed webhooks) can replay that exact `(raw_body, hmac)` pair to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header value naming a different, victim shop. `HmacValidator.validate` still succeeds (it only checks the body), and `Registry.process` calls the handler with the attacker-chosen `shop` value and the attacker's own body content, which the host application is documented to trust as an authenticated event for that tenant. Depending on the handler's use of `data.shop` (e.g., looking up a merchant's session/access token, updating merchant-scoped records, triggering merchant-scoped side effects), this enables cross-tenant data confusion/injection — a High/Critical-impact identity-binding bypass matching the required impact categories (cross-tenant access).

### Likelihood Explanation
Likelihood is high for any app that follows the gem's documented pattern of trusting `data.shop`/`request.shop` from `Registry.process` as an authenticated value (as shown in the gem's own `docs/usage/webhooks.md` example). No secret, access token, or privileged access is required — only the ability to install the app on any shop (including one the attacker controls) to harvest one valid signed webhook payload, then replay it with a modified header at will.

### Recommendation
Bind the shop identity into the authenticated data rather than trusting the header independently of the signature:
- Include the shop domain (and other Shopify-supplied identity headers such as `topic`, `api-version`, `webhook-id`) in the string that is HMAC-verified, or
- Cross-check the shop domain against an independent trust anchor (e.g., verifying the shop is one that currently has this webhook registered/subscribed, and matching topic/webhook-id), or, at minimum, clearly document that `shop` is unauthenticated and must not be used for tenant attribution without additional verification.

Concretely, modify `Request#to_signable_string` (and the corresponding `HmacValidator` computation) to incorporate the shop-domain header value, so verification fails if it is altered independently of the HMAC-covered content.

### Proof of Concept
1. Install the target app on an attacker-owned/controlled shop `attacker.myshopify.com`; Shopify sends a legitimately signed webhook: `raw_body = B`, header `X-Shopify-Hmac-Sha256 = HMAC(B, client_secret)`, header `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Attacker replays this HTTP POST to the same webhook endpoint, keeping `raw_body = B` and the same HMAC header untouched, but changes `X-Shopify-Shop-Domain` to `victim.myshopify.com`.
3. Server builds `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})`; `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `HMAC(B, secret) == received_hmac` — unaffected by the header change: [7](#0-6) 
4. The handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: "victim.myshopify.com", body: request.parsed_body, ...)`, i.e., attacker-controlled body content attributed to the victim shop: [8](#0-7)

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
