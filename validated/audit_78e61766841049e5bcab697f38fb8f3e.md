### Title
Deposit into `SIP-10` Zest vaults with a rounding-to-zero share amount permanently locks the depositor's underlying with zero shares minted - (File: `mainnet/contracts/vault/v0-vault-sbtc.clar`, and the equivalent `deposit` function in `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-stx.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`)

### Summary
The `deposit` function in every Zest tokenized vault accepts `amount` and computes `inkind` via `convert-to-shares-preview`, but only guards against `amount == u0` and against `inkind < min-out`. It never asserts `inkind > u0`. If a caller supplies `min-out u0` (or any value `<= inkind`) and the share-conversion rounds down to zero — which is reachable whenever `current-assets` is non-zero while `total-supply` of `zft` is disproportionately larger (e.g. a prior direct/rounding-driven state, or a very small `amount` relative to the vault's assets/supply ratio) — the transaction still succeeds: the underlying is pulled in via `receive-underlying`, but `ft-mint?` mints `0` shares to the recipient. The depositor's principal becomes permanently unbacked/unclaimed inside the vault.

### Finding Description
`deposit` in `v0-vault-sbtc.clar` computes shares before validating them: [1](#0-0) 

The check sequence is:
1. `(asserts! (not (get deposit states)) ERR-PAUSED)`
2. `(asserts! (var-get initialized) ERR-INIT)`
3. `(asserts! (not (var-get in-flashloan)) ERR-REENTRANCY)`
4. `(asserts! (> amount u0) ERR-AMOUNT-ZERO)`
5. `(asserts! (>= inkind min-out) ERR-SLIPPAGE)`
6. `(asserts! (<= (+ current-assets amount) CAP-SUPPLY) ERR-SUPPLY-CAP-EXCEEDED)`

There is no `(asserts! (> inkind u0) ERR-OUTPUT-ZERO)`. Compare this to `redeem` in the same file, which explicitly guards the symmetric case: [2](#0-1) 

`redeem` protects the withdrawer from burning shares and receiving zero assets (`ERR-OUTPUT-ZERO`), but `deposit` has no analogous protection for the depositor against paying underlying and receiving zero shares. Because `min-out` is caller-supplied and unconstrained, a user (or a user misled by front-end defaults of `min-out = 0`) can submit a deposit whose `inkind` preview rounds to `0` and the call will not revert. `receive-underlying` still moves the caller's tokens into vault custody and `assets` is incremented, but `ft-mint?` mints `0` `zft` to the recipient.

The identity broken is the fundamental vault invariant:
```
shares_minted_to(user) / total_shares == assets_credited_from(user) / total_assets
```
Here `assets_credited_from(user) = amount > 0` while `shares_minted_to(user) = 0`, so the depositor's contribution to `current-assets`/vault backing is not reflected in any claim they hold — their `amount` becomes vault-owned backing for other shareholders' existing `zft`, i.e. their principal is transferred out of their control with nothing given in return.

### Impact Explanation
This is a permanent freezing (in the strict sense, transfer without compensation) of the depositor's principal: the `amount` becomes stuck as unclaimed backing inside the vault, inflating `assets`/backing for existing shareholders while the depositor holds `0` `zft` and has no path to reclaim the underlying (there's no owner recovery function shown, and even if there were, it would require a privileged/DAO action rather than being automatic). This directly mirrors the referenced SafEth `stake`-with-`derivativeCount = 0` bug: an operation transfers user value into contract custody while the accounting side effect (share minting) silently degenerates to zero, and the value has no owner-side hook to recover it.

### Likelihood Explanation
Reachability depends on being able to get `inkind` (the `convert-to-shares-preview` output) to round to zero for a nonzero `amount` while `min-out` is set to `0` (the natural default for a "no slippage protection" caller, or a front-end bug). This is most trivially reachable for very small `amount` values relative to the vault's `assets`-to-`supply` ratio (rounding-down division), and does not require any privileged action, flashloan, or DAO compromise — it is directly triggerable by any unprivileged caller.

### Recommendation
Add an explicit output-zero guard to `deposit`, mirroring the one already present in `redeem`:
```clarity
(asserts! (> inkind u0) ERR-OUTPUT-ZERO)
```
placed immediately after the `inkind`/`min-out` slippage check and before `receive-underlying`/`ft-mint?` are invoked, in every vault contract (`v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-stx.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, and their `local-testing` counterparts).

### Proof of Concept
1. Deploy/initialize a vault (e.g. `v0-vault-usdc.clar`) such that `current-assets` and outstanding `zft` supply already exist with a ratio that causes `convert-to-shares-preview` to round down for small inputs.
2. Caller invokes `deposit` with a small `amount` such that `(convert-to-shares-preview amount)` evaluates to `u0`, and `min-out = u0`.
3. `(asserts! (> amount u0) ERR-AMOUNT-ZERO)` passes (amount > 0).
4. `(asserts! (>= inkind min-out) ERR-SLIPPAGE)` passes because `u0 >= u0`.
5. `receive-underlying` transfers `amount` from the caller into the vault; `var-set assets` increases by `amount`.
6. `ft-mint? zft inkind recipient` mints `u0` tokens — the caller receives no `zft`.
7. The caller's `amount` is now permanently part of vault `assets` backing other holders' shares, with no `zft` balance and no mechanism to reclaim it. [3](#0-2)

(define-public (deposit (amount uint) (min-out uint) (recipient principal))
    (let (
      (states (var-get pause-states))
      (u (try! (accrue)))

      (CAP-SUPPLY (var-get cap-supply))
      (current-assets (var-get assets))
      (inkind (convert-to-shares-preview amount)))

    (asserts! (not (get deposit states)) ERR-PAUSED)
    (asserts! (var-get initialized) ERR-INIT)
    (asserts! (not (var-get in-flashloan)) ERR-REENTRANCY)
    (asserts! (> amount u0) ERR-AMOUNT-ZERO)
    (asserts! (>= inkind min-out) ERR-SLIPPAGE)
    (asserts! (<= (+ current-assets amount) CAP-SUPPLY) ERR-SUPPLY-CAP-EXCEEDED)

    (try! (receive-underlying amount account))
    (try! (ft-mint? zft inkind recipient))
    (var-set assets (+ current-assets amount))

    (print {
      action: "deposit",
      caller: contract-caller,
      data: {
        depositor: account,
        recipient: recipient,
        amount: amount,
        shares-minted: inkind,
        assets: (+ current-assets amount)
      }
    })

    (ok inkind)))
