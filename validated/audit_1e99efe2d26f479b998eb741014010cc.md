### Title
Session fixation via unsigned, deterministic session-id cookie - ([File: lib/shopify_api/utils/session_utils.rb])

### Summary
For non-embedded apps, `ShopifyAPI::Utils::SessionUtils.current_session_id` derives the lookup key for a merchant's stored session directly from a plain, client-supplied cookie value with no cryptographic binding, and that value is a deterministic, guessable string (`"offline_#{shop}"` or `"#{shop}_#{user_id}"`). This breaks the intended binding: `cookie value == session id trusted by the host app` should equal `cookie value cryptographically bound to the shop/session that issued it`, but instead the gem accepts any string the client sends as the trusted session identifier.

### Finding Description
During OAuth completion, `ShopifyAPI::Auth::Oauth.validate_auth_callback` builds a `SessionCookie` whose `value` is simply `session.id` [1](#0-0) . Session ids are deterministic and predictable, computed only from public information:
- offline: `"offline_#{shop}"` [2](#0-1) 
- online: `"#{shop}_#{user_id}"` [3](#0-2) 

`SessionUtils.cookie_session_id` then returns this cookie value verbatim, with no signature or HMAC check, to be used by the host application as the key to retrieve the corresponding `Session` object (and its `access_token`) from storage: [4](#0-3) [5](#0-4) .

The gem's own documented flow instructs the host application to pass raw browser cookies into `current_session_id` for non-embedded apps and use the returned string as the session id to retrieve the persisted session [6](#0-5) . Because the value is never checked against anything the server itself set or signed (unlike the HMAC-protected OAuth callback parameters or the signed JWT session token used for embedded apps), any unprivileged internet user can set the `shopify_app_session` cookie in their own request to a string of the form `"offline_othershop.myshopify.com"` (shop domains are public knowledge) and have the host app - following this gem's documented `current_session_id`/`cookie_session_id` API exactly as specified - retrieve and use the session (including the `access_token`) belonging to a different, unrelated merchant.

This is a genuine identity-binding failure in the gem itself: the session id returned to the browser is not bound to the browser/session that legitimately obtained it (no signing, no per-browser secret, no expiry check tied to the cookie), so `SessionUtils` treats attacker-controlled bytes as an authenticated session identifier.

### Impact Explanation
An attacker who knows or can enumerate a victim shop's domain (`{shop}.myshopify.com`, which is not secret) can set a forged `shopify_app_session` cookie value and cause a host application - if it follows this gem's documented non-embedded session-retrieval flow - to serve it the victim's persisted `Session`, including the merchant's `access_token`. This results in cross-tenant access to another merchant's Shopify Admin API session, matching the "Critical: cross-tenant access" category.

### Likelihood Explanation
Likelihood is High for non-embedded apps that follow the documented pattern: the session id format is fully deterministic and derivable from public shop domain names (or a valid online user id, which is a small integer), requiring no secret knowledge, no access token, and no privileged access - only the ability to set an HTTP `Cookie` header, which any unprivileged internet client can do.

### Recommendation
Bind the session cookie value to something the server can independently verify (e.g., sign the session id with `api_secret_key`/HMAC, or store a random, unguessable session token server-side that maps to the real session id, rather than exposing the deterministic id itself to the browser). Reject/ignore cookie-derived session ids that do not carry a valid signature.

### Proof of Concept
1. Victim shop `victim-shop.myshopify.com` installs the app; OAuth completes and the browser receives cookie `shopify_app_session=offline_victim-shop.myshopify.com` per `validate_auth_callback` [1](#0-0) .
2. Attacker, in an unrelated browser/session, sends a request to the host app with header:
   `Cookie: shopify_app_session=offline_victim-shop.myshopify.com`
3. Host app calls `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)` exactly as documented [7](#0-6) , which returns `"offline_victim-shop.myshopify.com"` unchanged [4](#0-3) .
4. Host app looks up the session by that id and uses it (per this gem's documented pattern) to make authenticated Admin API calls on behalf of the attacker, exposing `victim-shop`'s `access_token`/data to the attacker.

        def current_session_id(shopify_id_token, cookies, online)
          if Context.embedded?
            if shopify_id_token
              id_token = shopify_id_token.gsub("Bearer ", "")
              session_id_from_shopify_id_token(id_token: id_token, online: online)
            else
              # falling back to session cookie

            end

            raise Errors::CookieNotFoundError, "Session cookie not found for app" unless
              cookies && cookies[Auth::Oauth::SessionCookie::SESSION_COOKIE_NAME]

            cookie_session_id(cookies)
          end
        end

```markdown
#### Cookie
Cookie based authentication is not supported for embedded apps due to browsers dropping support for third party cookies due to security concerns. Non-embedded apps are able to use cookies for session storage/retrieval.

For *non-embedded* apps, you can pass the cookies into:
 - `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, true)` for online (user) sessions or
 - `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)` for offline (store) sessions.
```
