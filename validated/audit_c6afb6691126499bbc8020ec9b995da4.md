### Title
Webhook shop identity (tenant) is not bound to the HMAC signature, allowing cross-tenant webhook spoofing — (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, but the `shop`, `topic`, `api_version`, and `webhook_id` values that are handed to the app's handler (and used to decide *which* handler runs and *which* tenant the event belongs to) are read directly from unauthenticated HTTP headers that are never included in the signed content.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop`, `topic`, `api_version`, and `webhook_id` are all pulled straight from HTTP headers with no cryptographic binding to the HMAC at all: [2](#0-1) 

`Registry.process` verifies only the body's HMAC and then trusts these header-derived values to build the `WebhookMetadata` passed to the app's handler, and to select the handler by `topic`: [3](#0-2) 

The `HmacValidator` computes and compares the signature only over the "signable string" the object provides: [4](#0-3) 

The binding this breaks, expressed as an equality that should hold but doesn't:
`shop_identity_bound_by_HMAC` (empty — HMAC only covers the body) `≠` `shop_identity_used_for_tenant_routing` (`X-Shopify-Shop-Domain` / `shopify-shop-domain` header, fully attacker-controlled).

Because a Shopify app's `api_secret_key` (`client_secret`) is a single shared secret across **every** shop that installs the app — not a per-shop secret — any unprivileged internet user can install the target app on a shop they control, receive a legitimately-signed webhook delivery from Shopify for their own shop, and then replay that exact `body` + `hmac-sha256` pair to the app's webhook endpoint while substituting the `shop-domain` (and optionally `topic`/`webhook-id`) header to reference a victim shop. `Utils::HmacValidator.validate` still returns `true` because it only checks the body against the secret, and `Registry.process` then dispatches the handler with `WebhookMetadata#shop` set to the attacker-chosen victim shop domain. Any application logic keyed off `WebhookMetadata#shop` (e.g., "look up the merchant record for this shop and update it") is now attacker-controlled across tenants.

### Impact Explanation
This is a cross-tenant identity confusion: an attacker holding a legitimate app installation (available to any internet user via public app install) can forge webhook events that the host application will process as if they originated from an arbitrary victim shop. Any host logic that trusts `WebhookMetadata#shop` for tenant-scoped writes (uninstall handling, order/customer processing, GDPR data requests, etc.) can be triggered against a shop the attacker never installed the app on, meeting the "cross-tenant access" criterion.

### Likelihood Explanation
High — the only prerequisite is installing the target app once (or otherwise obtaining one legitimately-signed webhook body/HMAC pair for the same app, since the same `client_secret` signs webhooks for all installs of that app). No access to the target's credentials, no privileged access, and no exploitation of Shopify's own infrastructure is required — headers can be freely set by anyone POSTing to the app's public webhook endpoint.

### Recommendation
Bind the tenant/topic identity to the signed content instead of trusting unauthenticated headers:
- Include `shop`, `topic`, and `webhook_id` in the HMAC-signed payload used by `Utils::HmacValidator`, or
- At minimum, document/require host applications to cross-check the header-derived `shop` against an independently verified installation record (e.g., confirm the `shop` header corresponds to a shop for which a currently-valid access token/session is on file) rather than trusting it implicitly for routing/dispatch, and reject requests where a shop cannot be corroborated.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (any unprivileged user can do this for a public app).
2. Shopify sends a legitimately signed webhook to the app, e.g.:
   ```
   shopify-topic: orders/create
   shopify-hmac-sha256: <valid HMAC over raw body, computed with the app's shared client_secret>
   shopify-shop-domain: attacker-shop.myshopify.com
   body: {"id": 123, ...}
   ```
3. Attacker captures this request and resends it to the app's public webhook endpoint, unmodified except:
   ```
   shopify-shop-domain: victim-shop.myshopify.com
   ```
4. `Utils::HmacValidator.validate` (see `lib/shopify_api/utils/hmac_validator.rb`) still returns `true` because it only re-derives the HMAC from `raw_body`, which was not altered.
5. `ShopifyAPI::Webhooks::Registry.process` (see `lib/shopify_api/webhooks/registry.rb:188-199`) dispatches the handler with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, even though the event never occurred on that shop.
