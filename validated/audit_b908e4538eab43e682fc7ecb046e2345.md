### Title
Unchecked ERC20 return value in `IntentGatewayV2::withdraw()` and `SweepDust` handling can permanently strand escrowed funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
On the Tron deployment of `IntentGatewayV2`, escrow payouts (`withdraw()`) and dust sweeps (`SweepDust` handling in `onAccept`) transfer ERC20 tokens using a raw low-level `.call()` to the `transfer()` selector, and only check that the *call itself did not revert* (`success`). They never decode/verify the boolean return value that ERC20's `transfer()` is specified to return. This is the same bug class as the reported `RelayPolymarketSDK::transferUsdc()` issue: a token transfer that "fails silently" (returns `false` without reverting) is treated as a successful transfer, and the protocol's internal accounting is updated as if funds moved even though they did not.

### Finding Description
In `withdraw()`, escrowed tokens/fees are released to the beneficiary using: [1](#0-0) 

and in the `SweepDust` branch of `onAccept`: [2](#0-1) 

Both sites do `(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...)); if (!success) revert TransferFailed();`. The `success` flag from `.call()` only indicates that the callee did not revert — it says nothing about the ABI-decoded return value of `transfer()`. Any ERC20 implementation that returns `false` on failure instead of reverting (a well-known non-standard-compliant pattern, e.g. some legacy/fee-on-transfer/paused tokens) will cause `success == true` while no tokens are actually moved.

Because `success` is true, the code proceeds to:
- Mark the order as filled/refunded (`_filled[body.commitment] = beneficiary`) and decrement the internal escrow ledger (`_orders[body.commitment][token] -= amount`), even though the beneficiary received nothing.
- Emit `EscrowReleased`/`EscrowRefunded`/`DustSwept` events implying success.

This is in direct contrast to the rest of the same contract and the main (non-Tron) `IntentGatewayV2.sol`/`IntentsBase.sol`, which consistently use OpenZeppelin's `SafeERC20.safeTransferFrom`/`safeTransfer`, e.g.: [3](#0-2) 
`SafeERC20` correctly decodes and checks the boolean return data (or requires the call to be to a contract with code), preventing this exact class of silent failure. The `withdraw()`/`SweepDust` paths bypass that protection entirely.

### Impact Explanation
Once `withdraw()` runs to completion after a spoofed/failed transfer, the escrow accounting (`_orders[...]`) is decremented and `_filled[commitment]` is set, permanently closing out the order. There is no retry path since the commitment is already marked filled/refunded. Result: permanent loss of the user's or solver's funds — the beneficiary never receives the tokens, and the tokens remain stuck in the gateway's balance (or wherever the failed transfer left them) with no accounting entry left to claim them. This satisfies "concrete theft or permanent freezing of funds."

### Likelihood Explanation
This path is reached whenever a fill/refund/dust-sweep message is delivered to the Tron `IntentGatewayV2` via the normal ISMP delivery flow (`onAccept` → `withdraw`, reachable by any relayed `RedeemEscrow`/`RefundEscrow`/`SweepDust` request from an intent solver filling an order or a user requesting a refund — explicitly an allowed reachable actor per scope). It requires only that one of the configured escrow tokens on this chain be (or become, e.g., via upgrade/pause) a non-reverting-on-failure ERC20, or that the transfer legitimately fails for a reason that doesn't cause a revert (e.g., blacklist/pause logic returning `false`). This is a realistic condition for many production stablecoins/tokens and does not require any privileged or malicious actor.

### Recommendation
Replace the raw `.call()` + `success`-only check with OpenZeppelin's `SafeERC20.safeTransfer`, consistent with the rest of the codebase (as already done in `evm/src/apps/intentsv2/IntentsBase.sol` and the non-Tron `IntentGatewayV2.sol` for `safeTransferFrom`). If a raw low-level call must be kept, decode the returned data and require it to be either empty or ABI-decode to `true`:
```solidity
(bool success, bytes memory data) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, to, amount));
if (!success || (data.length > 0 && !abi.decode(data, (bool)))) revert TransferFailed();
```
Apply this fix to all three unchecked transfer sites in `withdraw()` (lines 703-708, 720) and the `SweepDust` handler (line 674).

### Proof of Concept
1. Configure/escrow a token whose `transfer()` implementation returns `false` on failure instead of reverting (e.g., due to an internal pause, blacklist check, or non-standard implementation) as one of `order.inputs`/`body.tokens`.
2. A solver fills the order on the destination chain; Hyperbridge relays a `RedeemEscrow` request back to the Tron `IntentGatewayV2`.
3. `onAccept` → `withdraw(body, false)` is invoked; the token's `transfer(beneficiary, amount)` call returns `false` (transfer did not happen) but does not revert, so `success == true`.
4. `withdraw()` proceeds: `_orders[commitment][token] -= amount` and `_filled[commitment] = beneficiary` are set, `EscrowReleased` is emitted — the escrowed tokens remain in the gateway contract, unclaimable by the beneficiary or the solver, resulting in permanent fund loss.
