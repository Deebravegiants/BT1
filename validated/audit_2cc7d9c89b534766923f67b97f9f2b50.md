### Title
Attacker-controlled swap routes can inject unauthorized wallet-token transfers into a caller-signed authorization tree - (File: `contracts/controller/src/strategies/swap.rs`)

### Summary
Router-backed controller strategies accept caller-supplied route bytes and forward them to the configured swap router without restricting the contracts reachable through the route. `swap_collateral` is representative: the caller authenticates and must own or control the position, after which the controller authorizes only its own exact input transfer and invokes `execute_strategy(controller, amount_in, swap)` with the supplied bytes. [1](#0-0) [2](#0-1) [3](#0-2) 

A malicious route can therefore place attacker-controlled code below the caller-signed invocation and have that code request a transfer from the caller. Soroban simulation records that unrelated token transfer as a child of the caller's `swap_collateral` authorization; if the caller signs the generated tree, the transfer executes and the protocol's input-spend, measured-output, and position-risk checks do not bound the additional wallet loss. [4](#0-3) [5](#0-4) 

### Finding Description
The strategy surface takes an opaque `swap` byte string. For example, `swap_collateral(caller, account_id, current, amount, new, swap)` passes `swap` through `process_swap_collateral`, while `swap_debt`, `multiply`, and `repay_debt_with_collateral` expose the same router-input pattern. [6](#0-5) [7](#0-6) 

`process_swap_collateral` authenticates `caller`, requires ownership or an active delegate, withdraws collateral, and invokes the common swap helper. [2](#0-1)  The helper snapshots balances, authorizes one exact `token_in.transfer(controller, router, amount_in)` as the controller, and invokes `SwapAggregatorClient::execute_strategy` with the uninterpreted route bytes. [8](#0-7) [9](#0-8) 

Those checks constrain only the controller's supplied input and measured output. They do not constrain other calls made below the route that require the original caller's authorization. [10](#0-9)  The in-repository adversarial test demonstrates a router-callable hop contract performing `token.transfer(victim, attacker, amount)`, where the victim, token, recipient, and amount are stored in the malicious contract. [11](#0-10) 

The missing invariant is a protocol-level route-domain restriction: the controller verifies token markets, amounts, output receipt, and final account health, but the route can still introduce an arbitrary execution context under the caller's signed invocation tree. [12](#0-11) [13](#0-12) 

### Impact Explanation
A user who signs the authorization tree generated for a malicious route can lose unrelated wallet tokens in addition to performing the intended collateral or debt swap. The proof records the unrelated transfer as a child of `swap_collateral`, drains the victim's unrelated wallet-token balance, and credits it to the attacker while the intended swap still produces its expected collateral output. [14](#0-13) 

This is theft of user funds rather than only a poor exchange rate: the stolen asset need not be a listed collateral or debt asset, is outside the strategy's routed `amount_in`, and is not recovered by the controller's post-swap risk checks. [10](#0-9) [15](#0-14) 

Severity is Medium because exploitation requires the victim to sign a poisoned authorization tree, but the signature prompt is generated during ordinary transaction simulation and the injected transfer is structurally represented as an additional authorization child rather than as a separate protocol operation. [16](#0-15) 

### Likelihood Explanation
The attacker needs a route source or client flow that causes a position owner to submit a crafted route through `swap_collateral`, `swap_debt`, `multiply`, or `repay_debt_with_collateral`. Each of those paths accepts caller-controlled swap bytes, and the router invocation is a normal part of the strategy rather than an unusual privileged operation. [17](#0-16) [18](#0-17) 

An honest, restrictive client that decodes the simulated authorization tree and rejects unexpected child invocations prevents the loss. The enforced-auth test shows the same malicious route fails when the caller signs only the normal tree, and succeeds only when the generated child transfer is included. [19](#0-18) 

### Recommendation
Constrain swap routes to a protocol-approved venue and pool registry before executing them under a user's authorization context, or add an execution boundary that prevents route-reachable contracts from requesting the position owner's authorization. At minimum, clients should deterministically verify that the simulated authorization tree contains only the expected token pull and reject any additional child invocation before signing. [18](#0-17) [19](#0-18) 

The controller should also reject route bytes containing venues or pool addresses outside an allowlist instead of treating `swap` as opaque data, because its measured balance deltas cannot detect a successful unrelated transfer from the caller. [10](#0-9) 

### Proof of Concept
The dedicated regression test constructs an attacker-controlled hop whose `swap` entrypoint performs `token::Client::transfer(victim, attacker, amount)` for an unrelated wallet token selected by the attacker. [11](#0-10) 

The test gives the victim supplied collateral and an unrelated wallet-token balance, embeds the malicious hop in route bytes, and calls `swap_collateral(alice, account_id, USDC, 5_000 USDC, ETH, route)`. [20](#0-19) [21](#0-20) 

Simulation records `wallet_token.transfer(alice, attacker, WALLET_BALANCE)` as a child authorization under Alice's `controller.swap_collateral` invocation. [22](#0-21) 

When Alice signs that generated tree, the malicious transfer executes: Alice's unrelated wallet balance becomes zero, the attacker receives the full balance, and Alice's intended ETH collateral output is still deposited. [23](#0-22)

/// Router double: pays a fair output and calls the hop pool the payload names.
#[contract]
pub struct UnlistedPoolRouter;

#[contractimpl]
impl UnlistedPoolRouter {
    pub fn execute_strategy(env: Env, sender: Address, total_in: i128, swap_xdr: Bytes) -> i128 {
        sender.require_auth();
        let route = RoutedSwap::from_xdr(&env, &swap_xdr).expect("route must decode");
        let router = env.current_contract_address();
        token::Client::new(&env, &route.token_in).transfer(&sender, &router, &total_in);
        let _: Val = env.invoke_contract(&route.hop_pool, &symbol_short!("swap"), vec![&env]);
        token::Client::new(&env, &route.token_out).transfer(&router, &sender, &route.min_out);
        route.min_out
    }

#[test]
fn enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer() {
    let s = Scene::new();

    // Control: a pool that touches nothing passes with the honest root-only tree.
    let benign = s.route_through_pool_stealing(0);
    s.try_swap_with_signed_tree(&benign, &[])
        .expect("the honest tree authorizes an honest route");
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);

    // Rogue pool, honest tree: the host refuses the transfer and the whole call rolls back.
    s.t.env.mock_all_auths_allowing_non_root_auth();
    let rogue = s.route_through_pool_stealing(WALLET_BALANCE);
    let usdc_before = s.t.supply_balance_raw(ALICE, "USDC");
    let refused = s
        .try_swap_with_signed_tree(&rogue, &[])
        .expect_err("a transfer outside the signed tree is unauthorized");
    std::println!("rogue transfer under the honest tree = {refused:?}");
    assert!(
        refused.is_type(ScErrorType::Auth) || refused.is_type(ScErrorType::Context),
        "expected a host auth failure, got {refused:?}"
    );
    assert!(s
        .diagnostics()
        .contains("Unauthorized function call for address"));
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);
    assert_eq!(s.wallet(&s.attacker), 0);
    assert_eq!(s.t.supply_balance_raw(ALICE, "USDC"), usdc_before);

    // Same route, with the tree that simulation returned.
    let stolen_transfer = MockAuthInvoke {
        contract: &s.wallet_token,
        fn_name: "transfer",
        args: (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        sub_invokes: &[],
    };
    s.try_swap_with_signed_tree(&rogue, core::slice::from_ref(&stolen_transfer))
        .expect("the poisoned tree authorizes the rogue transfer");
    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
}

/// Authorizes, on behalf of the current contract, one `transfer(from, to, amount)`
/// call on `token_addr` made deeper in the next contract call (for example by
/// the pool). The entry allows no further sub-invocations.
pub fn authorize_transfer_as_current(
    env: &Env,
    token_addr: &Address,
    from: &Address,
    to: &Address,
    amount: i128,
) {
    let entry = InvokerContractAuthEntry::Contract(SubContractInvocation {
        context: ContractContext {
            contract: token_addr.clone(),
            fn_name: symbol_short!("transfer"),
            args: (from.clone(), to.clone(), amount).into_val(env),
        },
        sub_invocations: Vec::new(env),
    });
    env.authorize_as_current_contract(vec![env, entry]);
}
