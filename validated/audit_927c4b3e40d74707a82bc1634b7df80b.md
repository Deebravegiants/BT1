### Title
Per-leg HF gate in `refresh_supply_risk_params` lets a third party force liquidator-favoring tuples onto an account whose true post-refresh HF < 1.05, then liquidate it — (File: contracts/controller/src/risk/params.rs)

### Summary
`apply_gated_liquidation_params` is the protocol's protection against permissionlessly restamping a borrower's stored liquidation tuple (LT / bonus / fee) to worse terms: a liquidator-favoring change is applied to an account with debt only if the account's health factor, computed with the *new* threshold, is at least 1.05 (`THRESHOLD_UPDATE_MIN_HF_RAW`). The gate is evaluated **per leg** via `clears_min_hf`, which replaces only the touched position's threshold while every other supply leg still carries its stale, pre-edit (higher) threshold. The dedicated keeper path `update_account_threshold` compensates with a final whole-book HF ≥ 1.05 assertion that reverts the batch; the supply top-up path (`merge_supply_leg`) has no such post-check. An unprivileged caller can therefore top up each collateral leg of a victim's account in separate `supply` calls, each per-leg gate passing on an inflated HF computed from the still-stale sibling legs, ending in a state the keeper path is explicitly forbidden from creating — and if the combined new thresholds push the account below HF 1, the attacker immediately liquidates it for the new bonus. [1](#0-0) 

### Finding Description
The gate lives in `apply_gated_liquidation_params` (`contracts/controller/src/risk/params.rs:68-93`): if the listing change `favors_liquidator` and the account is not debt-free, `clears_min_hf` recomputes HF with **only this position's** `liquidation_threshold` swapped into a clone of `account.supply_positions`; all other legs contribute weighted collateral at their *old* thresholds. [2](#0-1) 

`merge_supply_leg` invokes this gate on every supply merge, and third-party top-ups of an existing leg are explicitly allowed (`require_third_party_existing_supply` only blocks *new* legs). [3](#0-2) [4](#0-3) 

By contrast, `sync_account_thresholds` (the `update_account_threshold` path) applies the same gate per leg but then re-computes HF over the fully updated book and reverts with `HealthFactorTooLow` if below 1.05 — this is the "slow path" safety net that the per-call supply fast path lacks. [5](#0-4)  The design docs confirm the asymmetry is known in isolation but miss the multi-leg divergence: "In the supply path, the gate calculates the HF before the new supply adds to the collateral" and only `update_account_threshold` "reverts if the final health factor is below 1.05". [6](#0-5) 

Analogy to GHSA-c8jx-96c9-8xrp: the indexed COUNT fast path skipped the field-permission check the full scan enforced; here the per-leg restamp fast path checks HF against a stale-tuple book and never performs the final account-wide HF check that `update_account_threshold` enforces for the same mutation.

### Impact Explanation
Theft of user funds / forced premature liquidation. After governance worsens a listing's tuple (e.g., lower LT, higher bonus — a routine `EditAssetInSpoke`), an attacker holding no privileges supplies dust to each of a victim's collateral legs in separate `supply` calls. Each call's gate passes because siblings still carry old, higher thresholds inflating weighted collateral. Once all legs are restamped, the victim's HF can be < 1.05 — potentially < 1 — a state `update_account_threshold(has_risks=true)` would have reverted. The victim is now liquidatable purely because of the restamp, and the attacker liquidates them under the new (higher) bonus, extracting value the borrower never consented to and that the gate was designed to prevent until HF recovered above 1.05.

### Likelihood Explanation
Requirements: (a) a governance listing edit that `favors_liquidator` (threshold decrease, bonus increase, or fee decrease — all routine parameter tuning), (b) a victim account with ≥2 collateral legs and debt such that each single-leg hypothetical HF ≥ 1.05 but the combined-tuple HF < 1.05. The attacker needs only the dust supply amounts and must call `supply` once per leg; each call is a normal authenticated user op. The window lasts until the victim's positions are otherwise refreshed or the account's true HF drifts. Cost is near zero (supplied dust remains the victim's collateral); payoff is the liquidation bonus on the victim's collateral.

### Recommendation
Make the per-leg gate book-aware: in `clears_min_hf`, evaluate the hypothetical HF with the *listed* (new) threshold applied to all listed supply legs, or track the worst-case restamped book. Alternatively, after each `merge_supply_leg`/`merge_withdraw_leg` that applied a liquidator-favoring tuple, run the same final `health_factor >= THRESHOLD_UPDATE_MIN_HF_RAW` assertion that `sync_account_thresholds` runs, reverting the supply if the resulting book falls below the floor. Simplest conservative fix: skip liquidator-favoring tuple application on any account with debt when other legs still hold stale tuples (i.e., require all listed legs to already match the listing before applying adverse restamps on a book that can't use the final check).

### Proof of Concept
1. Victim account has supply legs in assets A and B (stamped LT 8000 each) and debt D such that HF = 1.20 with both at 8000; with both at 5300, HF = 1.20 × 5300/8000 ≈ 0.795; with only one lowered, HF ≈ 0.98 — wait, that fails the gate too. Concrete numbers: choose collateral split so each single-leg hypothetical ≥ 1.05 but combined < 1.05, e.g., A and B each contribute half the weighted collateral: HF(both old)=1.20, HF(A new)=1.20·(8000−Δ·w_A)/8000 — pick Δ and weights so each single-leg HF ≈ 1.06–1.10 while combined ≈ 0.80–0.99.
2. Governance executes `EditAssetInSpoke` lowering LT (and/or raising bonus) on A and B.
3. Attacker calls `controller.supply` with a dust amount of asset A into the victim's existing account/leg (allowed by `require_third_party_existing_supply`). `merge_supply_leg` → `refresh_supply_risk_params(FullTuple)` → `clears_min_hf` computes HF with A at 5300, B still at 8000 → ≥1.05 → tuple applied.
4. Repeat with asset B. Now both legs carry LT 5300; victim's real HF ≈ 0.80 < 1.
5. Attacker calls `liquidate` on the now-liquidatable victim, seizing collateral at the new bonus — profit directly attributable to the bypassed gate.

```rust
fn favors_liquidator(position: &AccountPosition, effective_config: &AssetConfig) -> bool {
    effective_config.liquidation_threshold.raw() < position.liquidation_threshold.raw()
        || effective_config.liquidation_bonus.raw() > position.liquidation_bonus.raw()
        || effective_config.liquidation_fees.raw() < position.liquidation_fees.raw()
}

/// Checks health factor >= 1.05 with this position's threshold replaced by `new_lt`.
fn clears_min_hf(
    env: &Env,
    cache: &mut Context,
    account: &Account,
    hub_asset: &HubAssetKey,
    position: &AccountPosition,
    new_lt: Bps,
) -> bool {
    let mut hypothetical = *position;
    hypothetical.liquidation_threshold = new_lt;
    let mut supply_positions = account.supply_positions.clone();
    supply_positions.set(hub_asset.clone(), (&hypothetical).into());
    let hf =
        calculate_account_risk_totals(env, cache, &supply_positions, &account.borrow_positions)
            .health_factor;
    hf >= Wad::from(THRESHOLD_UPDATE_MIN_HF_RAW)
}
```

**File:** docs/explanation/decisions-r23.md (L202-209)
```markdown
The refresh applies a tuple that favors the liquidator (a lower threshold, a
higher bonus or a lower fee) to an account with debt only if the health factor
with the new threshold is at least 1.05. Otherwise the stored tuple stays. A
lower bonus alone does not favor the liquidator, so the refresh applies it at
any health factor. `update_account_threshold` with `has_risks` also reverts
if the final health factor is below 1.05. Thus it cannot apply the lower bonus
to an account near liquidation, but a supply to the leg can. A position that
no path touches keeps the old bonus.
```
