Confirmed: the gem's own documentation explicitly states that `Registry.process` "will verify the request did indeed come from Shopify" (`docs/usage/webhooks.md:125`) and hands the handler a trusted `shop` field, but the HMAC only covers the raw body, not the shop-domain header.

### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , so `Utils::HmacValidator.validate` only proves the integrity of the JSON body against the app's `client_secret` [2](#0-1) . The `shop` (tenant identity) is read straight from the unauthenticated `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header [3](#0-2) , and `Registry.process` forwards that unverified header value directly into `WebhookMetadata` after only checking the body HMAC [4](#0-3) .

### Finding Description
The identity binding that should hold is: `shop attributed to the handler == shop cryptographically bound to the signed payload`. In this gem it instead holds `shop attributed to the handler == shop header value`, which is never included in the HMAC-signed string.

Because a single app's `client_secret` is shared across every shop that installs the app, an attacker who installs the app on their own (e.g. free-trial) shop receives genuine, correctly-HMAC-signed webhook deliveries for their own shop. The attacker can capture such a request, keep the body and the valid `x-shopify-hmac-sha256` value untouched, and simply rewrite the `x-shopify-shop-domain` header to a victim shop's domain before replaying it to the app's webhook endpoint. `HmacValidator.validate` will still return `true` because it only recomputes the HMAC over `@raw_body` [5](#0-4) [1](#0-0) , and `Registry.process` will happily dispatch `WebhookMetadata.new(topic: ..., shop: request.shop, ...)` to the registered handler [6](#0-5) , attributing attacker-controlled (but "verified") data to the victim shop.

The gem's own documentation instructs developers to trust the outcome of `Registry.process` as proof the request "did indeed come from Shopify" [7](#0-6)  and to key application logic off `data.shop` [8](#0-7) , so this is not a case of the host app misusing the API — it is following the documented contract exactly, and the contract's identity binding is broken inside this gem.

### Impact Explanation
This allows cross-tenant data injection/spoofing: an attacker-controlled webhook payload can be attributed to an arbitrary victim `shop`, letting the attacker feed forged "verified" webhook events (e.g. `customers/redact`, `orders/create`, `app/uninstalled`, etc., depending on what the host app registers) into a victim tenant's data pipeline. This matches the Critical "cross-tenant access" impact category, since the tenant boundary (`shop`) that the app relies on for record attribution and access control is not actually authenticated.

### Likelihood Explanation
Exploitation requires only that the attacker be able to install the target app on any shop they control (trivial — any developer/trial store) and be able to send arbitrary HTTP requests to the app's public webhook endpoint with custom headers, both of which are available to any unprivileged internet user. No access token, `client_secret`, or privileged account is needed.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the HMAC-signed string, or otherwise cryptographically bind the tenant identity to the signature (e.g. by having `Registry.process` cross-check `request.shop` against the shop associated with the specific webhook subscription/session rather than trusting the raw header). At minimum, update `VerifiableQuery#to_signable_string` for `Webhooks::Request` to incorporate the shop header, mirroring how `Oauth::AuthQuery#to_signable_string` binds `shop` into its signed string [9](#0-8) .

### Proof of Concept
1. Attacker installs the app on their own shop `attacker.myshopify.com`, receiving a legitimate webhook, e.g.:
   ```
   POST /callback/orders/create
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid HMAC over body>
   x-shopify-shop-domain: attacker.myshopify.com
   x-shopify-webhook-id: ...
   Body: {"id": 1, "note": "malicious payload"}
   ```
2. Attacker replays the exact same body and `x-shopify-hmac-sha256` value, but changes the header to:
   ```
   x-shopify-shop-domain: victim.myshopify.com
   ```
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds a request where `hmac` and `to_signable_string` are unaffected by the header change [10](#0-9) .
4. `Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which passes because it never checks the shop header [11](#0-10) , then dispatches `handler.handle(data: WebhookMetadata.new(shop: request.shop, ...))` with `shop == "victim.myshopify.com"` [12](#0-11) .
5. The victim app's handler processes attacker-controlled data as a verified event from `victim.myshopify.com`.

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
```
