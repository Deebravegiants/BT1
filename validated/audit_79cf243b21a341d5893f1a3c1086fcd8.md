### Title
Webhook `shop`, `topic`, `api_version` and `webhook_id` are trusted from unsigned HTTP headers while the HMAC only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable signature over the raw request body only, but the `shop`, `topic`, `api_version`, and `webhook_id` values that get passed downstream into the app's webhook handler are read from HTTP headers that are never included in that signature.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are pulled directly from HTTP headers (`shopify-shop-domain`, `shopify-topic`, etc.), which play no part in the signable string: [2](#0-1) 

`Registry.process` validates the HMAC via `Utils::HmacValidator.validate(request)`, which uses `to_signable_string` (the body) to compute the signature and compares it against `request.hmac` (derived from the `hmac-sha256` header): [3](#0-2) [4](#0-3) 

Once the body's HMAC checks out, `process` builds `WebhookMetadata` using `request.topic` and `request.shop` — values that were never bound by the signature — and hands them to the app's registered `WebhookHandler`: [5](#0-4) [6](#0-5) 

The equality this breaks: `shop_header_used_by_handler == shop_covered_by_hmac` should hold, but in fact `shop_covered_by_hmac` is undefined (the HMAC only proves body integrity), while `shop_header_used_by_handler` is attacker-controllable header content. Any party who can obtain one valid `(raw_body, hmac)` pair for their own installed app instance (a routine event any merchant/app-installer legitimately receives) can replay that exact body/HMAC pair to the same webhook endpoint while substituting the `shopify-shop-domain` (and/or `shopify-topic`) header to name a different shop. `HmacValidator.validate` still succeeds because it never inspects the header, and `Registry.process` will dispatch the handler believing the webhook body originates from the spoofed shop.

### Impact Explanation
This crosses the tenant boundary this gem is supposed to enforce: an app's webhook handler is meant to trust that `WebhookMetadata#shop` correctly identifies which merchant the payload/body belongs to. Because that trust is misplaced (shop is unauthenticated header data), a malicious or compromised merchant/installer can inject webhook payloads that the host application will process under another shop's identity — matching the analog rule for "a shop authenticated versus the shop stored/used as identity" and "bytes verified versus bytes/fields parsed and acted on." Depending on what the app's handler does with `shop` (e.g., updating per-shop settings, triggering shop-scoped side effects), this can lead to cross-tenant data corruption or unauthorized actions attributed to another merchant, without needing the app's `api_secret_key`.

### Likelihood Explanation
Moderate-to-high: it does not require knowledge of `Context.api_secret_key` — only possession of one legitimately-signed `(body, hmac)` pair, which any installer of the app can obtain from their own store's normal webhook traffic (e.g., by installing the app and observing an outbound webhook, or crafting one from a controlled test shop with mandatory topics like `shop/redact`). The header spoofing itself is trivial (plain HTTP header manipulation) since `Request#initialize` performs no cross-check between headers and body content.

### Recommendation
Include `shop`, `topic`, and any other header fields the app relies on for routing/tenant identity as part of the HMAC-covered signable string (or independently verify them against Shopify's known shop/topic registry per request), so the signature binds header-derived identity fields, not just the raw JSON body. At minimum, `Registry.process` should cross-validate that the `shop` value asserted in headers matches an expected/authorized shop for the given `session`/subscription before dispatching to `WebhookHandler#handle`.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` (a normal, allowed action for any merchant).
2. Attacker triggers (or waits for) a legitimate webhook delivery to their app's endpoint, capturing the raw request body `B` and the valid `X-Shopify-Hmac-Sha256: H` header (computed by Shopify using the app's real `client_secret`, which the attacker never needs to know).
3. Attacker resends an HTTP POST to the same webhook endpoint with the identical body `B` and header `H`, but changes `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com` (and/or `X-Shopify-Topic` to a different topic).
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `to_signable_string` (`= B`) and finds it matches `H` — validation passes because the shop header was never part of the signed content. [7](#0-6) 
5. `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` is built with the attacker-controlled `shop`/`topic`, and the registered handler for that topic executes believing the data is authentically from `victim-shop.myshopify.com`. [8](#0-7)

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
