## Finding

### Title
Incomplete secret-redaction blacklist causes credential leakage into Debug logs via HTTP request-body logging - (File: `core/web/router.go`)

### Summary
The Kubernetes CVE describes credentials leaking into logs at elevated log levels due to insufficient sanitization of a configuration payload. Chainlink's web API has a directly analogous pattern: `loggerFunc` in `core/web/router.go` logs the full JSON body of every incoming API request at `Debug` level, using a "sanitizer" that only redacts a narrow, hardcoded list of key names.

### Finding Description
`loggerFunc` reads the raw request body, lets the handler process it, and then logs it verbatim at `Debug` level via `readBody`/`readSanitizedJSON`: [1](#0-0) 

`readSanitizedJSON` only redacts a field if `isBlacklisted` returns true, and `readBody` falls back to logging the raw content on any parse failure: [2](#0-1) 

`isBlacklisted` is defined with an extremely narrow hardcoded list — it only matches variants of the literal substring `"password"`; it does **not** cover `"token"`, `"secret"`, `"apikey"`, `"key"`, `"authtoken"`, etc.: [3](#0-2) 

This mirrors the CVE's root cause exactly: a sanitization/redaction routine with an incomplete field-matching rule set, invoked only at a certain log verbosity (`Debug` here vs. `-v=4` in the CVE), that ends up leaking credential material verbatim into logs. Several node API request payloads legitimately carry credential-like fields that are not `"password"` — for example bridge configuration and external-initiator management flows deal with `OutgoingToken`/`OutgoingSecret` values (confirmed present in `core/bridges/bridge_type.go` and `core/web/presenters/bridges.go`, and in the `ExternalInitiator` model in `core/bridges/external_initiator.go`): [4](#0-3) 

If any authenticated API endpoint accepts (in its JSON body) a key such as `outgoingToken`, `outgoingSecret`, `apiKey`, `newPassword`-adjacent-but-differently-named secret fields, or nested objects containing `password`/`secret` fields (the sanitizer only inspects **top-level** map keys, not nested structures), that value will be written to the node's Debug logs in cleartext. I was not able to fully confirm within tool-call limits whether the exact `BridgeTypeRequest`/`ExternalInitiatorRequest` structs expose `OutgoingSecret`/`OutgoingToken` as client-writable request fields (I could only see the persisted model, not the full request DTOs), so that specific route should be verified directly in the repo, but the underlying logging/redaction defect in `router.go` is confirmed by reading the code directly.

### Impact Explanation
Any credential-bearing field that isn't literally named with a `password` substring, or that is nested inside a JSON object, will bypass redaction and be written to disk/stdout at Debug level. This can expose long-lived secrets (bridge outgoing auth tokens, external initiator secrets, API keys) to anyone with log access, which is a direct secret-disclosure vulnerability of the same class as CVE-2020-8564.

### Likelihood Explanation
Exploitation requires the operator to run the node with `Log.Level = 'debug'` (analogous to Kubernetes' `-v=4`), which is common in troubleshooting/staging environments and is exercised in the repo's own test fixtures (e.g. `testdata/scripts/node/validate/disk-based-logging.txtar`). No attacker action is needed beyond issuing a normal authenticated API request containing a non-`password`-named secret field; the leak happens automatically via the standard request-logging middleware.

### Recommendation
Expand `isBlacklisted` in `core/web/router.go` to match a broader/case-insensitive set of substrings (`secret`, `token`, `apikey`, `auth`, `credential`, etc.), and make `readSanitizedJSON` recursively redact nested objects/arrays rather than only top-level keys. Consider switching to an allowlist-based logging model for request bodies, or disabling raw body logging entirely for sensitive routes (bridge management, external initiators, sessions).

### Proof of Concept
1. Start a chainlink node with `Log.Level = 'debug'`.
2. Issue an authenticated `POST/PATCH` request to an API route whose JSON body contains a credential field not named with a `password` substring (e.g. `{"outgoingToken": "supersecret", "outgoingSecret": "supersecret2"}`), or a nested object like `{"user": {"password": "hunter2"}}`.
3. Inspect the node logs — the `Debugw` line emitted by `loggerFunc` (`core/web/router.go:556-567`) will contain the request body with `outgoingToken`/`outgoingSecret`/nested `password` values unredacted, since `isBlacklisted` (`core/web/router.go:643-658`) never matches them and `readSanitizedJSON` only inspects top-level keys.

func readBody(reader io.Reader, lggr logger.Logger) string {
	buf := new(bytes.Buffer)
	_, err := buf.ReadFrom(reader)
	if err != nil {
		lggr.Warn("unable to read from body for sanitization: ", err)
		return "*FAILED TO READ BODY*"
	}

	if buf.Len() == 0 {
		return ""
	}

	s, err := readSanitizedJSON(buf)
	if err != nil {
		lggr.Warn("unable to sanitize json for logging: ", err)
		return "*FAILED TO READ BODY*"
	}
	return s
}

func readSanitizedJSON(buf *bytes.Buffer) (string, error) {
	var dst map[string]any
	err := json.Unmarshal(buf.Bytes(), &dst)
	if err != nil {
		return "", err
	}

	cleaned := map[string]any{}
	for k, v := range dst {
		if isBlacklisted(k) {
			cleaned[k] = "*REDACTED*"
			continue
		}
		cleaned[k] = v
	}

	b, err := json.Marshal(cleaned)
	if err != nil {
		return "", err
	}
	return string(b), err
}

// NOTE: keys must be in lowercase for case insensitive match
var blacklist = map[string]struct{}{
	"password":             {},
	"newpassword":          {},
	"oldpassword":          {},
	"current_password":     {},
	"new_account_password": {},
}

func isBlacklisted(k string) bool {
	lk := strings.ToLower(k)
	if _, ok := blacklist[lk]; ok || strings.Contains(lk, "password") {
		return true
	}
	return false
}
