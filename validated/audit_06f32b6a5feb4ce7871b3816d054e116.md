### Title
Unchecked fixed-size buffer copy from attacker-controlled `bytes from` in HyperFungibleToken cross-chain calldata authorization — panics the runtime on untrusted ISMP message data - ([File: modules/pallets/hyper-fungible-token/src/module.rs])

### Summary
`Pallet::on_accept` decodes an ABI `Message { bytes from; bytes to; uint256 amount; bytes data; }` from an ISMP `PostRequest.body` relayed by any unprivileged relayer. When the optional `data` field is present and carries no signature, the code derives the substrate origin from `message.from` using an unchecked, fixed-size `copy_from_slice`/slice-index operation, with no prior length validation — the same bug class as CVE-2020-5213 (unbounded external input copied into a fixed-size buffer).

### Finding Description [1](#0-0) 

Relevant flow:
1. `on_accept` destructures an inbound `PostRequest` and ABI-decodes `Message` from its `body` — `message.from` is an arbitrary-length `bytes` field fully controlled by whoever crafts the source-chain calldata that gets relayed. [2](#0-1) 
2. When `message.data` is non-empty and `substrate_data.signature` is `None`, the code takes the unsigned path:
```rust
let from_bytes = message.from.as_ref();
if source.is_evm() {
    T::EvmToSubstrate::convert(H160::from_slice(
        &from_bytes[from_bytes.len() - 20..],
    ))
} else {
    let mut account = [0u8; 32];
    account.copy_from_slice(from_bytes);
    account.into()
};
``` [3](#0-2) 
- If `source.is_evm()` is true and `from_bytes.len() < 20`, `from_bytes.len() - 20` underflows (`usize` subtraction), producing a huge index and an out-of-bounds slice, which panics.
- If `source` is not EVM, `account.copy_from_slice(from_bytes)` panics unless `from_bytes.len()` is exactly 32 — any other length traps.

This is precisely the bug class the codebase has already fixed elsewhere in multiple spots, with code comments explicitly describing the same failure mode:
- `modules/ismp/core/src/host.rs`: "the id is copied into a `[u8; 4]`, and `copy_from_slice` traps on a length mismatch — in the runtime this is a wasm trap reachable from untrusted input ... so the length is now checked up-front." [4](#0-3) 
- `modules/utils/serde/src/lib.rs`: "It used to `copy_from_slice` straight from the input, which panics on any length mismatch — and it runs on untrusted RPC input... the panic aborted the node's `rpc` worker thread and took the process down. Wrong lengths must be serde errors." [5](#0-4) 

In `on_accept`, no such length check precedes the `from_bytes` copy/slice, unlike the parallel `to_bytes` handling a few lines above in the same function, which explicitly validates length before copying:
```rust
let to_bytes = message.to.as_ref();
if to_bytes.len() == 32 {
    beneficiary_bytes.copy_from_slice(to_bytes);
} else if to_bytes.len() == 20 {
    beneficiary_bytes[12..].copy_from_slice(to_bytes);
} else {
    Err(HftError::InvalidRecipientLength(to_bytes.len()))?;
}
``` [6](#0-5) 
This confirms the pallet's own convention is to validate length before any fixed-size copy — the `from_bytes` handling is the outlier that omits it.

### Impact Explanation
A panic inside `on_accept`, invoked from `pallet_ismp`'s request-handling path, causes a runtime (wasm) trap during dispatch of `handle_unsigned`/message execution. This is reachable by any relayer or unprivileged message dispatcher who can get a PostRequest destined for the HyperFungibleToken module delivered through the ISMP host (a standard relayed cross-chain message, not requiring any special privilege) — matching the "unprivileged message dispatcher/relayer" reachability required by scope. A panic during block-import/extrinsic execution on a Substrate-based parachain node can DoS block production/finality for the chain (a `handle_unsigned` unsigned extrinsic validated and executed by every collator), which is a Critical-class availability failure and could halt bridge message delivery entirely, matching the "route unable to deliver messages" acceptance criterion.

### Likelihood Explanation
High. Triggering it only requires:
- A registered `ContractToAsset` mapping for `(source, from)` — an already-configured legitimate bridge lane.
- An abi-encoded `Message` whose `data` is non-empty, `SubstrateCalldata.signature` is `None`, and whose `from` bytes are not exactly 20 (for EVM sources) or not exactly 32 (for non-EVM sources).

Both the ABI `Message.from` bytes and `SubstrateCalldata` are attacker-controlled payload content within a relayed message body; no special permission is needed to submit such a message via the normal cross-chain send flow feeding the destination `on_accept` handler.

### Recommendation
Mirror the `to_bytes` handling: validate `from_bytes.len()` explicitly before use, returning a decode/validation error (e.g. `HftError::InvalidFromLength`) instead of performing bounds-unchecked slicing or `copy_from_slice`, for both the EVM (`>= 20` bytes, or exactly 20) and non-EVM (exactly 32 bytes) cases.

### Proof of Concept
1. Register a legitimate `ContractToAsset` mapping for `(source, from_addr)` so `on_accept` proceeds past authentication.
2. Craft `body` as ABI-encoded `Message { from: bytes(3 bytes, e.g. 0x000000), to: <32 valid bytes>, amount: <any>, data: SubstrateCalldata { signature: None, runtime_call: <any> }.encode() }`.
3. Relay this as a `PostRequest` to the HyperFungibleToken module via `pallet_ismp::Call::handle_unsigned`.
4. Execution reaches the unsigned branch: `from_bytes.len() - 20` underflows (`3 - 20` as `usize`), producing an out-of-bounds slice access and a runtime panic/wasm trap during extrinsic execution.

Note: I was unable to independently confirm at what exact call layer the panic surfaces (whether it aborts only the extrinsic via `panic::catch_unwind` in `TryDispatch`/executive, or propagates further) due to index limitations on the full runtime dispatch stack; a Devin session with full repo access would be needed to trace `handle_unsigned`'s panic-handling boundary precisely and confirm real-world severity (single extrinsic failure vs. block-halting panic).
