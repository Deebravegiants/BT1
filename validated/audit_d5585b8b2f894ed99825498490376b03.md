### Title
Webhook `shop-domain` header trusted for tenant identity but not covered by HMAC verification - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw request body only, while the `shop`, `topic`, `api_version`, and `webhook_id` values used to route and identify the tenant are taken from HTTP headers that are never part of the signed bytes. `ShopifyAPI::Webhooks::Registry.process` accepts any request whose body+HMAC pair validates and then dispatches to handlers using the unauthenticated `shop` header value, breaking the binding: `HMAC(secret, bytes_verified) valid` should imply `shop header == shop that produced those bytes`, but the header is not part of `bytes_verified`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all read from HTTP headers, which are outside that signed string: [2](#0-1) 

`Registry.process` validates only the HMAC and then trusts `request.shop` (and `request.topic`) to build `WebhookMetadata` handed to the app's handler: [3](#0-2) 

`HmacValidator.validate` computes the signature purely over `to_signable_string` (the body) with the app's single, shop-independent `api_secret_key`: [4](#0-3) 

Because the HMAC secret is the app's `client_secret`, not a per-shop secret, and the signed content excludes the shop header, any HMAC-valid `(body, hmac)` pair remains valid for that body under **any** `shop-domain`/`topic`/`webhook-id` header value. A user who operates one shop that has the app installed will legitimately receive genuine webhook deliveries (body + valid HMAC) from Shopify to their own app endpoint infrastructure. They can then resend that same body/HMAC pair to the app's webhook endpoint while substituting a different shop's domain in the `shop-domain` header (and/or a different `topic`/`webhook-id`). `HmacValidator.validate` still returns `true` because it only re-derives the signature from the body, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the victim shop, even though the payload never actually originated from — or pertains to — that shop.

### Impact Explanation
This crosses a tenant boundary inside the gem's own trust decision: the equality the gem is supposed to guarantee, `hmac_valid(request) ⟹ request.shop is authentic`, does not hold, because `shop` is not part of the material the HMAC covers. Any app that relies on `WebhookMetadata#shop` (as the documented API encourages, since it is the only tenant identifier delivered with the callback) to look up per-shop state, sessions, or access tokens can be made to process attacker-controlled data under another merchant's identity — a cross-tenant data-processing bypass mediated entirely by this gem's webhook verification/dispatch code, without needing the `api_secret_key`, an access token, or any credential belonging to the victim.

### Likelihood Explanation
Exploitation requires only that the attacker be a legitimate (even free-tier) user of the target app on their own store, an "unprivileged internet user" relationship, and does not require possession of `api_secret_key`, TLS interception, or social engineering — merely observing/replaying their own genuinely-received webhook traffic (or scripting their own store to produce a chosen body) toward the app's public webhook endpoint with a forged header. The header-vs-body split is a structural property of `Request`/`HmacValidator`, so it is deterministic and reliably reproducible for any topic the attacker can trigger on their own shop (e.g., `orders/create`, `app/uninstalled`, etc.), and only limited by what body content is useful against the target app's handler logic.

### Recommendation
Include the shop domain (and topic/webhook id, if used for dispatch) inside the HMAC-signed material — e.g., have `Request#to_signable_string` incorporate the normalized `shop-domain` header alongside the raw body — so that a header mismatch invalidates the signature, closing the gap between "bytes verified" and "bytes acted on" in `Registry.process`/`WebhookMetadata`.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers an event (e.g. creates an order) so Shopify sends a real webhook: body `B`, header `X-Shopify-Hmac-Sha256: H` (valid for `B` under the app's `client_secret`), `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker replays the exact same `B`/`H` to the app's webhook endpoint but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and optionally alters `X-Shopify-Topic`/`X-Shopify-Webhook-Id`, which are also unsigned).
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Utils::HmacValidator.validate(request)` recomputes HMAC over `B` only and returns `true` since `H` was genuinely produced for `B`. [5](#0-4) 
4. `Registry.process` proceeds to call the registered handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...)`, causing the host app to act as though the (attacker-controlled) payload came from the victim shop.

            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
