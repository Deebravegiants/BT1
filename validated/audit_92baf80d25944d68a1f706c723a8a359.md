Based on my investigation, I've confirmed the root cause with sufficient evidence to write up the finding.

### Title
Webhook `shop-domain`/`topic` identity is trusted without HMAC coverage, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while `shop`, `topic`, `api_version`, and `webhook_id` are read directly from unauthenticated HTTP headers. `Webhooks::Registry.process` validates only the body HMAC and then hands the attacker-controllable `shop` and `topic` values straight to the registered handler, breaking the binding between "the tenant whose secret validated this request" and "the tenant the handler believes sent it."

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, `#api_version`, and `#webhook_id` are all parsed straight from headers, none of which are part of the signed string: [2](#0-1) 

`Registry.process` validates the HMAC (over body only) via `Utils::HmacValidator.validate(request)`, then dispatches using `request.shop` and `request.topic` without any further check that these header values are consistent with the request that produced the valid HMAC: [3](#0-2) 

`HmacValidator.validate_signature` compares `verifiable_query.to_signable_string` (body only) against the computed signature, and `Context.api_secret_key` is a single **app-wide** secret shared across every merchant install of the app — it is not per-shop: [4](#0-3) 

The identity binding this breaks: `shop asserted in the HTTP header == shop whose data the HMAC-signed body actually pertains to`. Because the app secret is shared across all shops using the app, any party who runs the app on a shop they control receives genuine, validly-HMAC'd webhook deliveries. They can then replay that exact raw body with the `hmac-sha256` header untouched, but substitute the `shop-domain` (and/or `topic`, `webhook_id`, `api_version`) header to reference a different merchant's shop. `Utils::HmacValidator.validate` still returns `true` (it only checks the body), and `WebhookMetadata` is built with the attacker-chosen `shop`: [5](#0-4) 

The handler then processes/persists data under the spoofed shop identity, believing it originated from that tenant.

### Impact Explanation
This is a cross-tenant identity spoofing primitive: an app installed by any merchant (an "unprivileged" actor relative to other tenants of the same app) can forge the `shop`, `topic`, `api_version`, or `webhook_id` attribution of a webhook that this gem will treat as authenticated, causing the host application's webhook handler to act on data under another shop's identity. Depending on what the host app's handler does with `WebhookMetadata#shop` (e.g., look up/update per-shop records, trigger shop-scoped side effects), this can lead to cross-tenant data corruption or disclosure — matching the "cross-tenant access" High/Critical impact category, since the trust boundary broken is exactly the shop-identity binding this gem is supposed to enforce via HMAC validation.

### Likelihood Explanation
Likelihood is Low-to-Medium: the attacker must control a legitimate installation of the target app on a shop they operate (or otherwise obtain one valid signed webhook body/HMAC pair), and the resulting impact is limited to bodies/events that make sense being replayed with different header metadata (e.g., an empty-body event like `shop/redact`, or any topic whose body content doesn't depend on shop identity). The gem itself does nothing to bind `shop`/`topic`/`webhook_id` to the signature, so the vulnerability is deterministic and always reachable through the public `Registry.process` entry point once any single valid `(body, hmac)` pair is known.

### Recommendation
Include `shop`, `topic`, `api_version`, and `webhook_id` in the signable string (or otherwise cryptographically bind them, e.g. by validating them against Shopify's actual documented webhook headers only after computing HMAC over a canonicalized combination of body + these fields), or at minimum document that consumers of `WebhookMetadata` must not trust `shop`/`topic` beyond routing purposes without an out-of-band verification (e.g., cross-checking against a known/registered shop record) before performing any tenant-scoped write.

### Proof of Concept
1. App is installed on attacker-controlled shop `attacker.myshopify.com`. Shopify sends a legitimate webhook, e.g. `shop/redact`, with headers:
   `x-shopify-topic: shop/redact`, `x-shopify-hmac-sha256: <valid HMAC of body B>`, `x-shopify-shop-domain: attacker.myshopify.com`, body `B` (e.g. `{}` or shop-independent payload).
2. Attacker captures this raw body `B` and its valid `hmac-sha256` header value.
3. Attacker resends a request to the app's webhook endpoint with the same body `B` and same `hmac-sha256` header, but with `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `body` against the app-wide `api_secret_key` [6](#0-5) .
5. The registered handler receives `WebhookMetadata.new(topic: "shop/redact", shop: "victim.myshopify.com", body: {}, ...)` and performs shop-scoped side effects (e.g., deleting/redacting data) attributed to `victim.myshopify.com`, despite the request never having been signed for that shop.
