## Title
Escrowed funds released without verifying ERC20 `transfer` return value - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
`IntentGatewayV2.withdraw()` and the `SweepDust` handler in the Tron variant of `IntentGatewayV2` release escrowed tokens using a raw low-level `.call` encoding `IERC20.transfer`, but only check that the call itself did not revert (`success`). They never decode/verify the boolean return value that the ERC20 standard defines for indicating transfer failure. Internal escrow accounting (`_orders[...]`, `_filled[...]`) is then updated as if the transfer definitively succeeded.

### Finding Description
In `withdraw()`, escrowed tokens and transaction fees are paid out via: [1](#0-0) 

and in the dust-sweep branch of `onAccept`/incoming-request handling: [2](#0-1) 

Both sites do `(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...)); if (!success) revert TransferFailed();`. This only checks that the low-level call did not revert — it never inspects the ABI-decoded boolean return data. Contrast this with the rest of the codebase, which consistently uses OpenZeppelin's `SafeERC20.safeTransfer`/`safeTransferFrom` (which does validate the return value) — including elsewhere in this very file for `predispatch` transfers: [3](#0-2) 

and the contract even imports `SafeERC20` and declares `using SafeERC20 for IERC20;`: [4](#0-3) 

For any ERC20/TRC20 implementation that signals failure by returning `false` rather than reverting (a documented, common pattern, and particularly relevant on Tron where TRC20 tokens are known to deviate from strict ERC20 semantics), `token.call(...)` succeeds (`success == true`) even though no tokens were actually moved. The code proceeds to treat the withdrawal as successful:
- `_filled[body.commitment] = beneficiary;` is set unconditionally before the loop runs. [5](#0-4) 
- `_orders[body.commitment][token] -= amount;` and fee accounting are decremented/deleted regardless of whether the recipient actually received funds. [6](#0-5) 

### Impact Explanation
Because `_filled` is marked and the escrow ledger is decremented even when the underlying token transfer silently failed, the beneficiary's funds become permanently stuck in the `IntentGatewayV2` contract: there is no remaining accounting record that would allow a retry or an alternate withdrawal path (the commitment is already marked filled/refunded). This is a concrete permanent loss/freezing of escrowed user funds reachable by the normal intent-fill/refund flow that any relayer can trigger by submitting a valid proof for a `WithdrawalRequest` or `SweepDust` request — no privileged role is required.

### Likelihood Explanation
Likelihood depends on whether a token used in an order implements the "return false on failure" pattern instead of reverting. This is realistic on Tron (the primary deployment target of this contract), where TRC20 tokens are known for non-standard, sometimes silently-failing transfer semantics, and is also possible with paused/blacklist-style ERC20 tokens (e.g., certain stablecoins can return `false` for blacklisted recipients rather than reverting). Any unprivileged relayer completing a fill/refund/dust-sweep for such a token triggers the flawed accounting.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` pattern in `withdraw()` and the `SweepDust` branch with `IERC20(token).safeTransfer(beneficiary, amount)` from the already-imported `SafeERC20` library (as used elsewhere in the same file), so that both call-level failures and ERC20 boolean-false failures cause a revert before `_filled`/`_orders` state is mutated.

### Proof of Concept
1. An order is created and tokens escrowed for a token contract `T` whose `transfer()` implementation returns `false` on failure instead of reverting (e.g., transferring to a blacklisted/paused beneficiary address, or a Tron TRC20 with this behavior).
2. A relayer submits a valid GET-response proof that resolves to `withdraw(body, isRefund)` for that commitment (via `onGetResponse` at `evm/tron/contracts/apps/IntentGatewayV2.sol:738-743`).
3. Inside `withdraw`, `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` executes; `T.transfer` runs to completion and returns `false`, but the low-level call itself does not revert, so `success == true`.
4. `_filled[body.commitment]` is already set and `_orders[body.commitment][token] -= amount` executes, marking the order fulfilled and zeroing/reducing the escrow record, even though `beneficiary` received zero tokens.
5. The tokens remain locked in the `IntentGatewayV2` contract with no code path left to reclaim them for the beneficiary, since the order's escrow accounting no longer reflects an outstanding balance.
