### Title
Webhook shop attribution is not bound to the HMAC signature, allowing cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, and `Utils::HmacValidator.validate` only checks that HMAC against that body. The `shop` (`x-shopify-shop-domain`/`shopify-shop-domain`) header that `Webhooks::Registry.process` later uses to attribute the event to a tenant is never part of the signed material, so the binding `hmac_verified_owner == webhook.shop` does not hold.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
returning only `@raw_body`. The `shop` accessor is derived independently from a header that is not part of that signable string: [2](#0-1) 

`HmacValidator.validate`/`validate_signature` compute and compare the HMAC solely against `verifiable_query.to_signable_string`: [3](#0-2) 

`Registry.process` accepts the request once the body-only HMAC check passes, then attributes the payload to whatever shop the (unsigned) header claims: [4](#0-3) 

Because the shop identity is carried in an unsigned header while only the body is bound to the signature, any exact `(raw_body, hmac)` pair that was ever validly produced for shop A can be replayed to the app's webhook endpoint with the `shop-domain` header swapped to shop B. The HMAC check still passes (it only revalidates the body against the secret), but `WebhookMetadata.shop` — and therefore whatever tenant-scoped processing the host application performs — is now attributed to shop B instead of the shop that actually authored/received that payload.

### Impact Explanation
This breaks the tenant-isolation guarantee the gem is expected to provide to host applications: a webhook handler that trusts `WebhookMetadata#shop` to determine which merchant's records to read/write can be made to act on/attribute data to a different merchant than the one that generated the signed payload, i.e. cross-tenant confusion caused entirely by data this gem exposes as "verified." This matches the Critical "cross-tenant access" impact category, since no privileged credential beyond a legitimately-received webhook from the attacker's own shop is required.

### Likelihood Explanation
An attacker who has installed the app on their own shop (an ordinary, unprivileged action) will receive real webhooks with valid `(body, hmac)` pairs for known bodies (e.g., predictable/templated events). They can capture one such pair and resend it to the app's public webhook endpoint with a forged `x-shopify-shop-domain` header pointing at a victim shop. No knowledge of `api_secret_key` is required — only observation of a webhook the attacker already legitimately received.

### Recommendation
Include the shop-identifying header (and ideally topic/webhook-id) inside the HMAC-signed material, or otherwise cryptographically bind the shop domain to the payload before `Registry.process` attributes data to it, e.g. by re-deriving/confirming the shop from a value that is itself covered by the signature rather than trusting the raw header independently.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and lets the app trigger a webhook whose body content is fully known/predictable (e.g., an app/uninstalled or empty-body webhook), capturing the resulting `x-shopify-hmac-sha256` value and raw body from their own store.
2. Attacker POSTs to the app's webhook endpoint using the identical captured `raw_body` and `hmac` header, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only re-computes HMAC over `raw_body`: [3](#0-2) 
4. The handler receives `WebhookMetadata.new(... shop: request.shop ...)` with `shop == "victim-shop.myshopify.com"`, even though the payload never originated from or was signed with victim-shop's context, causing any tenant-scoped logic in the handler to run against the wrong tenant.
