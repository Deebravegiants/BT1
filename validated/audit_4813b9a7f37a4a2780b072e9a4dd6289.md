### Title
Webhook `shop-domain`, `topic`, `webhook_id`, and `api_version` headers are trusted without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable payload from the raw body only, while the shop identity, topic, webhook id, and api version are read straight from HTTP headers that are never included in the signed data. `Registry.process` accepts any request whose body-HMAC is valid and then forwards the unauthenticated `shop` header value directly to the app's handler as the tenant identifier.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all derived purely from headers, with no cryptographic binding to the signed body: [2](#0-1) 

`Registry.process` validates only the HMAC over that signable string (the body) and then trusts `request.shop`/`request.topic` verbatim to build `WebhookMetadata`, which is handed to the app's handler as the authoritative tenant/topic identity: [3](#0-2) [4](#0-3) 

Because the `api_secret_key` used to compute the HMAC is a single per-app secret shared across every installed shop (not shop-specific), a valid `(raw_body, hmac)` pair produced for one tenant remains cryptographically valid when replayed with a different `shop-domain` header claiming a different tenant. The equality the gem should enforce — "the shop attested inside the HMAC-protected payload" == "the shop the handler is told the webhook came from" — is never checked; instead the gem checks "HMAC(body) is valid" and separately trusts "shop header says X" with no linkage between the two. This breaks the identity binding for the whole request when only the body is protected.

Any actor able to reach the app's public webhook endpoint and in possession of one genuine `(body, hmac)` pair (e.g., an app user who is a merchant on the platform and can observe their own shop's real webhook deliveries, or anyone who captures one in transit/logs) can resubmit that exact body with the HMAC intact but an altered `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) header. The `HmacValidator.validate` check still passes because it only checks the raw body against the shared secret, and `Registry.process` will invoke the handler believing the webhook belongs to the spoofed shop — a cross-tenant identity injection into the app's own webhook processing pipeline. This contrasts with `Auth::Oauth::AuthQuery`, where `shop` **is** explicitly included in `to_signable_string` and thus is protected by the HMAC: [5](#0-4) 

### Impact Explanation
This qualifies as cross-tenant access: an attacker can cause the host application to process webhook data (topic, webhook id, and merchant identity) under a spoofed `shop` value, even though the cryptographic proof only covers the body bytes. Host apps typically use `data.shop` to key session/store lookups and dispatch background jobs per documented usage: [6](#0-5) 
so an attacker-controlled `shop` value flowing into that trust boundary can misattribute or inject webhook-derived data into another tenant's processing pipeline, without requiring the `api_secret_key` for arbitrary payloads (only reuse of one already-genuine signed body).

### Likelihood Explanation
Requires the attacker to obtain at least one legitimate `(raw_body, hmac)` pair for the app (feasible for an app user replaying their own real webhook, or via captured traffic to the public endpoint) and to resend it to the webhook endpoint with modified headers — no `api_secret_key`, access token, or privileged access is needed. The webhook endpoint is by design internet-reachable.

### Recommendation
Include `shop`, `topic`, and `webhook_id` (or at minimum `shop`) in the HMAC-signed material, or otherwise cryptographically bind them to the body (e.g., verify shop against a per-shop registered webhook subscription/state before dispatch), and reject any header values not verifiable — mirroring how `AuthQuery#to_signable_string` binds `shop` inside its signed payload.

### Proof of Concept
1. Attacker owns/operates `shop-a.myshopify.com` on the target app and observes/logs a genuine Shopify webhook delivery: `raw_body = '{"id":1,...}'` with header `x-shopify-hmac-sha256: <valid-hmac-of-body>` and `x-shopify-shop-domain: shop-a.myshopify.com`.
2. Attacker POSTs the same `raw_body` and the same (still-valid) HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses `shop` as `"victim-shop.myshopify.com"` from the header (`request.rb:21-23`).
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only HMACs `@raw_body` (`request.rb:35-38`, `hmac_validator.rb:26-31`) — unrelated to which shop header is present.
5. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` (`registry.rb:198-199`) and processes/logs/stores data as if it legitimately came from `victim-shop.myshopify.com`.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
