This confirms the finding: the gem's own documentation states `ShopifyAPI::Webhooks::Registry.process` "will verify the request did indeed come from Shopify" (`docs/usage/webhooks.md:125`), and the `data.shop` field is documented as trustworthy metadata passed to the handler (`docs/usage/webhooks.md:14`). But the HMAC only covers the raw JSON body, not the `shop` (or `topic`/`webhook_id`) header, so "did indeed come from Shopify" is true only for the body bytes — the shop attribution is unauthenticated.

### Title
Webhook `shop` field is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook's authenticity by checking only `Utils::HmacValidator.validate(request)`, which computes the HMAC exclusively over the raw request body (`request.to_signable_string` → `@raw_body`). The `shop` value passed to the handler in `WebhookMetadata` comes from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, which is never included in the signed content.

### Finding Description
The equality the gem implicitly promises is: **`shop` value delivered to the handler == shop that the HMAC-verified payload originated from**. In reality:
- `HmacValidator.validate` computes `OpenSSL::HMAC.hexdigest(sha256, api_secret_key, verifiable_query.to_signable_string)` and compares it to the received HMAC. [1](#0-0) 
- For `Webhooks::Request`, `to_signable_string` returns only `@raw_body`; the `shop` accessor independently reads the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of the signed string at all. [2](#0-1) 
- `Registry.process` validates the HMAC and, on success, immediately builds `WebhookMetadata` using `request.shop` from the unauthenticated header and dispatches it to the app's handler. [3](#0-2) 

Because Shopify signs webhook payloads with the app's single `client_secret` (not a per-shop secret) and the signed content is only the raw body, any two webhooks delivered to the same app share the same signing key. An attacker who controls one shop installed on the app can capture a legitimate, validly-signed webhook body+HMAC pair for their own shop, then replay that exact `raw_body`/HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` still succeeds (it never inspects the header), and `Registry.process` calls the handler with `WebhookMetadata.new(shop: <victim-shop>, ...)`, misattributing attacker-controlled payload data to the victim tenant.

### Impact Explanation
Because the gem's own webhook documentation tells integrators that `process` "will verify the request did indeed come from Shopify" and that `data.shop` is "The shop domain of the webhook" [4](#0-3) [5](#0-4) , host applications reasonably treat `data.shop` as an authenticated tenant identifier and key their per-shop state, background jobs, or webhook-idempotency records on it (as shown in the gem's own documented handler example passing `shop_domain: data.shop` downstream [6](#0-5) ). Since `shop` is never bound to the HMAC, a malicious merchant/attacker with just one legitimate app install can inject payload content attributed to any other shop domain, corrupting per-tenant state or triggering shop-scoped side effects (e.g., mandatory redact/GDPR handlers, order/customer processing) for a tenant they do not control — a cross-tenant integrity/confidentiality violation.

### Likelihood Explanation
Exploitation only requires being (or briefly becoming) an app-installing merchant capable of receiving one legitimate webhook — no access token, `client_secret`, or privileged Shopify account is required, and the victim's shop domain is guessable/public (`*.myshopify.com`). The replay is a simple HTTP request with a substituted header.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the signed content validated against the HMAC, or independently verify the shop domain via a signed/trusted channel (e.g., cross-check against the webhook subscription owner recorded at registration time, or use a per-shop verification step) before dispatching `WebhookMetadata` to handlers.

### Proof of Concept
1. App has two merchants installed: attacker's shop `attacker.myshopify.com` and victim's shop `victim.myshopify.com`.
2. Shopify sends a legitimate webhook to the app for `attacker.myshopify.com` with body `B` and header `x-shopify-hmac-sha256: HMAC(secret, B)`.
3. Attacker captures this request and replays it to the app's webhook endpoint, keeping body `B` and the same HMAC header, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `Utils::HmacValidator.validate` recomputes `HMAC(secret, B)` — matches, since `B` is unchanged. [1](#0-0) 
5. `Registry.process` proceeds and calls the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: B, ...)`, even though `B` never originated from `victim.myshopify.com`. [3](#0-2)
