This confirms the vulnerability: `to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from HTTP headers that are never included in the HMAC computation [2](#0-1) .

### Title
Webhook tenant identity (`shop`) is not bound to the HMAC, enabling cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then trusts the `shop`, `topic`, and `webhook_id` values taken from unauthenticated HTTP headers to route and label the event. Because the HMAC secret (`api_secret_key`) is shared across every shop that has the app installed, and the signature never covers the headers, any actor who can obtain one valid `(body, hmac)` pair for the app (e.g. by installing the app on their own store and receiving a legitimate webhook) can replay that same body/HMAC to the app's webhook endpoint while substituting an arbitrary `shop-domain` header, causing the host application to process the payload as if it originated from a different, victim shop.

### Finding Description
`Registry.process` performs exactly one authentication check before dispatching to the handler:
```ruby
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
handler = @registry[request.topic]&.handler
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))
``` [3](#0-2) 

`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and compares it to the `hmac` field of the same object [4](#0-3) . For a webhook `Request`, `to_signable_string` is defined as just the raw HTTP body, and `hmac` is read from the `hmac-sha256` header:
```ruby
def hmac
  Digest.hexencode(Base64.decode64(T.cast(shopify_header("hmac-sha256"), String)))
end
...
def to_signable_string
  @raw_body
end
``` [5](#0-4) 

The `shop`, `topic`, and `webhook_id` accessors used for routing/labeling are pulled straight from headers and are never part of the signed material:
```ruby
def topic
  T.cast(shopify_header("topic"), String)
end
def shop
  T.cast(shopify_header("shop-domain"), String)
end
``` [6](#0-5) 

This breaks the identity binding: **the bytes verified by the HMAC (body) ≠ the bytes acted upon for tenant identity (`shop` header)**. The `api_secret_key` (and therefore every valid HMAC) is identical for all shops that install a given app, so a valid `(body, hmac)` pair generated for shop A remains valid when replayed with the `shop-domain` header changed to shop B. Since `process` never re-derives or cross-checks `request.shop` against anything covered by the signature, the handler receives attacker-controlled tenant identity alongside a cryptographically "verified" body.

### Impact Explanation
This is a cross-tenant identity confusion: an actor who legitimately installs the app on their own store (an "unprivileged" step requiring no special access to any other merchant) can capture a genuine webhook `(body, hmac)` pair from their own shop (or from any topic whose body content they can predict/replicate, e.g. `shop/redact` with a fixed schema) and replay it directly to the app's webhook endpoint with a forged `shop-domain` header naming a different, victim shop. Host applications built on this gem's documented `Registry.process` contract treat `WebhookMetadata#shop` as the authenticated source-of-truth shop for that event (that is the entire purpose of validating the HMAC before dispatch), so this allows injection of attacker-controlled webhook data attributed to an arbitrary tenant — meeting the "cross-tenant access" bar for Critical impact.

### Likelihood Explanation
Any party that can install the target app (a normal, unprivileged flow for public/embedded Shopify apps) can obtain a valid signed body for at least the topics with static/predictable payloads, and no additional secrets are required to replay it with a different `shop-domain` header directly to the app's public webhook endpoint. The gem provides no mechanism to bind `shop` (or `topic`/`webhook_id`) to the HMAC, so every consumer of `Registry.process` inherits this gap by default.

### Recommendation
Include the routing/identity headers (`shop-domain`, `topic`, `webhook_id`, `api-version`) in the signable string used for HMAC verification, or otherwise cryptographically bind them to the body before `HmacValidator.validate` is invoked, so that `request.shop` cannot be altered independently of a valid signature. At minimum, document that `Registry.process` callers must not treat `WebhookMetadata#shop` as authenticated unless they perform their own additional verification (e.g., confirming the shop has a known, active session before trusting the payload).

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; trigger/receive any webhook delivery with topic `T` and body `B`, capturing the genuine `X-Shopify-Hmac-Sha256` header value `H` computed as `HMAC-SHA256(api_secret_key, B)`.
2. Send a POST request directly to the app's webhook endpoint with the same raw body `B` and the same `X-Shopify-Hmac-Sha256: H` header, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `Utils::HmacValidator.validate` succeeds because it only checks `B` against `H` [7](#0-6) ; `Registry.process` then dispatches `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed(B), ...)` to the registered handler [3](#0-2) , causing the host app to process attacker-supplied data under the victim shop's identity.
