### Title
Unrestricted swap-route endpoints can execute caller-authorized token transfers outside the routed amount - (File: contracts/controller/src/strategies/swap.rs)

### Summary
XOXNO strategy functions accept opaque route bytes and invoke the configured swap router, while route hop pool addresses are supplied by the caller rather than restricted to intended DEX endpoints. A malicious endpoint can invoke an unrelated `token.transfer(caller, attacker, amount)` during the strategy; transaction simulation records that transfer in the caller’s authorization tree, and enforcing mode executes it if the caller signs the tree. This allows theft of caller wallet funds unrelated to the controller’s routed input amount. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`swap_collateral(caller, account_id, current, amount, new, swap)` forwards caller-supplied `swap` bytes to the strategy swap helper, as do `swap_debt`, `repay_debt_with_collateral`, and `multiply`. [4](#0-3) [5](#0-4) 

The controller snapshots the input and output balances, authorizes one exact input-token transfer to the configured router, invokes `execute_strategy`, and later only verifies that the controller did not overspend and received positive output. [6](#0-5) [7](#0-6) 

Those checks bound the controller’s own input and output, but they do not restrict what route-selected code asks the original caller to authorize. The strategy payload’s `assets` registry can contain arbitrary pool addresses, and each decoded swap hop consumes the caller-selected `pool`, `token_in`, `token_out`, and venue. [2](#0-1) [8](#0-7) 

The router executes each decoded hop and dispatches it to the selected venue adapter without validating the pool against a registry of intended endpoints. [9](#0-8) [10](#0-9) 

A malicious contract implementing the expected venue ABI can therefore run during the route and invoke `token.transfer(victim, attacker, amount)`. The harness demonstrates that simulation records this unauthorized-looking transfer as a child of the victim’s `swap_collateral` authorization and that signing the simulated tree makes the transfer succeed. [3](#0-2) [11](#0-10) 

### Impact Explanation
This is theft of user funds outside the nominally routed input: the malicious endpoint can move any token for which the victim signs the additional authorization-tree child, including assets never supplied to or listed by the protocol. [12](#0-11) [13](#0-12) 

The controller’s positive-output check can still pass because the malicious route can return a valid output amount after performing the unrelated wallet transfer. [7](#0-6) [14](#0-13) 

### Likelihood Explanation
An unprivileged attacker can deploy the malicious endpoint and construct the malicious route, but a victim must submit a route containing that endpoint and sign the simulation-produced authorization tree containing the extra token transfer. [15](#0-14) [13](#0-12) 

The risk is practical where users or integrations treat route bytes as opaque swap metadata rather than auditing every nested authorization. The affected controller entrypoints include `multiply`, `swap_debt`, `swap_collateral`, and `repay_debt_with_collateral` because each accepts route bytes and reaches the same router call. [16](#0-15) [4](#0-3) [5](#0-4) 

### Recommendation
Restrict route endpoints to authentic, protocol-recognized DEX pool contracts rather than accepting arbitrary `pool` addresses in the strategy payload. The router should resolve or validate pool addresses through a trusted venue/factory registry and reject routes containing unrecognized endpoint code. Clients should additionally treat any authorization-tree child other than the expected strategy input transfer as a fatal signing error, but client inspection alone should not be the only defense. [2](#0-1) [17](#0-16) 

### Proof of Concept
1. Deploy a malicious contract exposing the pool function expected by the chosen venue adapter. Configure it with `(victim, unrelated_wallet_token, attacker, amount)`. [18](#0-17) 
2. Build route bytes whose `assets` registry places the malicious contract in the hop’s `pool` position while preserving a valid input token, output token, and positive minimum output. [8](#0-7) [19](#0-18) 
3. Have the victim call `swap_collateral(caller=victim, account_id, current, amount, new, swap=malicious_route)`. [20](#0-19) 
4. During router execution, the malicious endpoint calls `token.transfer(victim, attacker, amount)` for the unrelated wallet token. [3](#0-2) 
5. Simulation records that transfer beneath the victim’s controller authorization; if the victim signs that tree, the unrelated token moves to the attacker while the strategy can still deposit a valid output. [11](#0-10)
