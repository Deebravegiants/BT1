### Title
Webhook `shop` identity header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw HTTP body, while the shop identity (`shop-domain` header) is read separately and passed downstream unverified. `HmacValidator.validate` proves only that the *body bytes* were signed with the app's secret; it says nothing about which shop the request claims to be from. `Registry.process` nonetheless treats the unverified header as the tenant identity when dispatching to the app's handler.

### Finding Description
The identity binding that should hold is: `shop value cryptographically bound by the HMAC == shop value used to attribute the webhook payload`. This binding is broken:

- `to_signable_string` signs only `@raw_body`: [1](#0-0) 
- `shop` is read from a separate, unsigned header: [2](#0-1) 
- `HmacValidator.validate` computes/compares the signature purely over `to_signable_string`, never touching `shop`: [3](#0-2) 
- `Registry.process` validates only the HMAC, then forwards `request.shop` straight into `WebhookMetadata` given to the app's handler: [4](#0-3) 
- `WebhookMetadata#shop` is documented as the trusted tenant identifier the host app is expected to key its data/storage lookups on: [5](#0-4) [6](#0-5) 

Because the app's `api_secret_key` (client secret) is the same across every shop that installs the app — it is not per-tenant — any unprivileged user can install the app on their own (e.g. free/dev) store and receive genuine, validly-HMAC-signed webhooks for their own body content. Since the HMAC never covers the `shop-domain` header, that same `(raw_body, hmac)` pair remains valid no matter what shop-domain header is attached to the replayed request. An attacker can therefore replay a webhook they legitimately received, substituting the `X-Shopify-Shop-Domain` header with a victim tenant's domain, and `HmacValidator.validate` will still return `true`.

### Impact Explanation
This is a cross-tenant identity confusion: the gem hands the host application a `shop` value it presents as authenticated (because it comes from a "validated" `Request`), but that value is not actually covered by the cryptographic check. Any host application that follows the documented pattern of using `data.shop` to key session/data lookups (as shown in the gem's own docs) can be made to process, store, or act on attacker-supplied webhook bodies under an arbitrary victim shop's identity — e.g. forging `app/uninstalled`, `shop/redact`, `orders/create`, etc. for a shop the attacker does not control. This falls under cross-tenant access.

### Likelihood Explanation
Exploitation requires no privileged credentials, no access token, and no knowledge of `api_secret_key`: the attacker only needs to be a normal user who installs the target app on any shop (even a free dev store) to obtain a legitimately-signed `(body, hmac)` pair, then replay it against the app's public webhook endpoint with a modified shop header. This is fully reachable through this gem's own `Request`/`Registry.process`/`HmacValidator` code path with no dependency on the host app misusing the API.

### Recommendation
Bind the shop identity into the verified signable content, or otherwise cryptographically tie it to the validated request, e.g.:
- Include the `shop-domain` (and/or `webhook-id`, `topic`) header value as part of `to_signable_string` so it participates in the HMAC computation, or
- Require the caller (or `Registry.process`) to cross-check `request.shop` against the specific shop for which the topic/webhook subscription (`webhook_id`) was registered before dispatching to the handler, rather than trusting the header value directly.

### Proof of Concept
1. Attacker installs the target Shopify app on their own shop `attacker.myshopify.com` (any unprivileged user can do this).
2. Shopify sends a real webhook to the app: body `B`, headers including `X-Shopify-Hmac-Sha256: HMAC(secret, B)` and `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. Attacker captures this exact `(B, hmac)` pair and replays it to the same webhook endpoint, only changing the header to `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: ...)` is constructed; `Utils::HmacValidator.validate(request)` recomputes `HMAC(secret, B)` — unchanged since only `raw_body` is signed — and returns `true`: [7](#0-6) 
5. `Registry.process` calls the app's handler with `WebhookMetadata.new(..., shop: "victim.myshopify.com", body: B, ...)`, causing the host application to attribute the attacker's payload to the victim tenant.
