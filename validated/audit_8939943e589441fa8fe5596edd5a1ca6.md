### Title
Webhook `shop` identity is taken from an unauthenticated header not covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable content solely from the raw request body (`to_signable_string` returns `@raw_body`), but exposes a separate `shop` accessor that reads the `X-Shopify-Shop-Domain` header, which is not part of the signed content at all.

### Finding Description
`Webhooks::Registry.process` performs authentication by calling `Utils::HmacValidator.validate(request)` [1](#0-0) , which computes an HMAC over `request.to_signable_string`, i.e. the raw body only [2](#0-1) . However, the tenant-identifying `shop` value that is subsequently handed to the app's registered `WebhookHandler` via `WebhookMetadata` is pulled from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header [3](#0-2) , a field that is never included in the signed payload.

This is the same class of bug as the report: an identity field (`shop`) is acted upon (used to select/route the tenant context in `WebhookMetadata`) while a *different* field (raw body bytes) is the one actually bound by the cryptographic check. The equality that should hold — "the shop cryptographically authenticated == the shop the app trusts as the event's tenant" — does not hold, because the header is fully attacker-controllable independent of the HMAC.

Any party who can obtain one genuine, HMAC-valid webhook payload/signature pair for their own store (any merchant can install the app being targeted and trigger a webhook for their own shop, or intercept a webhook delivered to their own endpoint) can replay that exact `raw_body` + valid `hmac-sha256` header to the app's webhook endpoint while substituting an arbitrary value in `X-Shopify-Shop-Domain`. `HmacValidator.validate` will pass because it only checks the body bytes, and `Registry.process` will then dispatch to `handler.handle` with `WebhookMetadata#shop` set to the attacker-chosen (victim) shop domain [4](#0-3) .

### Impact Explanation
Since `shop` is the sole tenant identifier supplied to the host application's webhook handler, and it is fully decoupled from the HMAC-verified bytes, an attacker can forge webhook events that a host application will treat as originating from an arbitrary victim shop. Any application that uses `WebhookMetadata#shop` to look up/act on per-tenant state (e.g., updating stored shop data, triggering shop-scoped side effects, or associating data to a shop record) can be tricked into writing/acting on the wrong tenant's records — a cross-tenant data integrity issue directly caused by this gem's own trust boundary (HMAC verifies bytes, but the app is only given/relies on this gem's `shop` accessor which is not part of what was verified).

### Likelihood Explanation
Exploitation only requires the attacker to have (or obtain) one valid, HMAC-signed webhook body from Shopify — trivially available to any merchant who installs the target app on their own store, since webhooks are delivered per-installation and any registered merchant can capture a legitimate payload/HMAC pair for their own shop. No access token, `client_secret`, or privileged access is required; only standard HTTP request forgery against the app's public webhook endpoint.

### Recommendation
Bind `shop` (and ideally `topic`, `api_version`, `webhook-id`) into the signed material used for verification, or otherwise cross-check the header-derived `shop` against the shop domain reflected/expected inside the verified JSON body content, rejecting requests where they disagree. At minimum, document/enforce that `Request#shop` must not be trusted as an authenticated value unless independently corroborated against verified payload content.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker-shop.myshopify.com` and captures a legitimate webhook delivery (e.g., `orders/create`), including its raw body and the `X-Shopify-Hmac-Sha256` header Shopify computed over that body.
2. Attacker replays the exact same raw body and `X-Shopify-Hmac-Sha256` header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `Webhooks::Request.new` parses headers/body without validating any relationship between the `shop` header and body content [5](#0-4) .
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `raw_body` against the (correct, replayed) HMAC [6](#0-5) .
5. The app's `handler.handle` is invoked with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, despite the payload actually originating from and describing `attacker-shop.myshopify.com`'s data.
