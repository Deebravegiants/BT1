### Title

Caller-controlled swap route can inject an unauthorized token transfer into the signed authorization tree - ([File: contracts/controller/src/strategies/swap.rs])

### Summary

`swap_collateral` and the other controller strategy entrypoints accept caller-supplied opaque route bytes and forward them to the configured router while the caller’s authorization remains active. [1](#0-0) [2](#0-1)  A malicious route can name attacker-controlled code as a hop destination; that code can request `token.transfer(caller, attacker, amount)`, which simulation records as a child of the caller’s controller authorization. [3](#0-2) [4](#0-3)  If the caller signs the simulated authorization tree, the injected child transfer succeeds and drains wallet assets unrelated to the lending position. [5](#0-4) 

### Finding Description

`process_swap_collateral` authenticates the caller, verifies account ownership or delegation, then forwards the supplied `StrategySwap` bytes into `withdraw_and_swap_from_supply`. [6](#0-5)  `swap_tokens` authorizes only the controller’s exact input transfer to the configured router, but it does not constrain which contracts the router’s decoded route subsequently invokes. [7](#0-6)  The router payload resolves a hop’s pool, input token, and output token from attacker-controlled `assets` registry indices and dispatches the selected venue adapter. [8](#0-7)  The project’s threat model confirms that the route has no pool allowlist and can put third-party code below the caller’s authorization. [9](#0-8) 

A malicious venue contract can therefore call an unrelated token’s `transfer` with `from = caller` while the caller’s controller authorization is on the call stack. [10](#0-9)  The host does not automatically reject that call merely because it was reached through untrusted route-selected code; an honest simulation records it as an additional sub-invocation under the caller’s `swap_collateral` entry. [11](#0-10)  Signing that poisoned tree authorizes the malicious token transfer as well as the intended collateral swap. [5](#0-4) 

### Impact Explanation

This is theft of user funds rather than merely loss of routed swap input. [12](#0-11)  The malicious route can target any token held by the caller and request an arbitrary transfer amount, while still returning enough expected output for the controller’s positive measured-output and final-account-risk checks. [13](#0-12) [14](#0-13)  In the regression scenario, the attacker receives the victim’s entire unrelated `WALLET_BALANCE` while the intended strategy still deposits the expected `FAIR_OUT_ETH`. [14](#0-13) 

The exposure applies to caller-supplied routes used by `multiply`, `swap_collateral`, `swap_debt`, and `repay_debt_with_collateral`, with `swap_collateral` providing a direct path because it swaps existing account collateral under the owner or delegate’s root authorization. [15](#0-14) [6](#0-5) 

### Likelihood Explanation

An unprivileged attacker can deploy the malicious hop contract and construct a structurally valid route that names it. [16](#0-15) [8](#0-7)  The route’s output and slippage measurements do not reveal or bound an unrelated caller-wallet transfer embedded deeper in the call tree. [13](#0-12) [17](#0-16)  Exploitation requires the victim to submit the malicious route and sign the authorization tree produced by simulation, but clients that trust quoted route bytes may not independently reject unexpected child invocations. [18](#0-17)  Because the injected call is presented as part of the signed controller operation, a routine wallet confirmation can authorize it. [19](#0-18) 

### Recommendation

Do not allow strategy payloads to select arbitrary executable pool addresses. [20](#0-19)  Maintain a governance-approved venue and pool registry, validate every decoded hop against that registry before execution, and reject route bytes containing unregistered executable addresses. [21](#0-20)  Until such on-chain enforcement exists, wallets and integrators must decode the full route and reject any authorization tree containing children other than the expected input transfer, but this client-side check should be treated as mitigation rather than the contract invariant. [22](#0-21) 

### Proof of Concept

1. The victim supplies USDC collateral and holds a separate unrelated token that is not a lending-market asset. [23](#0-22) 
2. The attacker deploys a route destination whose `swap` function calls `token.transfer(victim, attacker, WALLET_BALANCE)`. [10](#0-9) 
3. The malicious route supplies that contract as the hop pool while still paying the expected swap output. [24](#0-23) 
4. The victim calls `swap_collateral(caller, account_id, usdc_key, SWAP_IN_USDC, eth_key, route)`. [25](#0-24) 
5. Simulation records a child `transfer(victim, attacker, WALLET_BALANCE)` under the victim’s `swap_collateral` authorization. [11](#0-10) 
6. Without that child in the signed tree, enforcing authorization rejects the malicious transfer and rolls back the strategy. [26](#0-25) 
7. With the simulated poisoned child signed, the transaction succeeds, the attacker receives the full unrelated wallet balance, and the victim still receives the expected ETH collateral. [5](#0-4)

**File:** docs/explanation/threat-model.md (L154-165)
```markdown
That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap
user.
```

```rust
#[derive(Clone, Copy, Debug, PartialEq, Eq)]
pub(crate) enum Opcode {
    /// Swap through `venue`: `idx_a` pool, `idx_b` token in, `idx_c` token out.
    Swap(SwapVenue),
    /// Aquarius withdraw: `idx_a` pool, `idx_b` share token, `idx_c` first
    /// index of the per-constituent floor run in `amounts`.
    Burn,
    /// Aquarius deposit: `idx_a` pool, `idx_b` share token, `idx_c` index of
    /// the minimum share count in `amounts`.
    Mint,
}

impl Opcode {
    /// Decodes an opcode byte into its variant, or `None` if unrecognized.
    fn from_u8(value: u8) -> Option<Self> {
        match value {
            0 => Some(Self::Swap(SwapVenue::Soroswap)),
            1 => Some(Self::Swap(SwapVenue::Aquarius)),
            2 => Some(Self::Swap(SwapVenue::Phoenix)),
            3 => Some(Self::Swap(SwapVenue::Sushi)),
            4 => Some(Self::Swap(SwapVenue::CometDex)),
            5 => Some(Self::Burn),
            6 => Some(Self::Mint),
            _ => None,
        }
    }
```
