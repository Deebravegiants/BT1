## Analog Found

### Title
`WrappedHyperFungibleToken.send()` does not account for fee-on-transfer/deflationary underlying tokens, causing permanent shortfall in locked reserves and draining shared liquidity - (File: `sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol`)

### Summary
`WrappedHyperFungibleToken` locks an arbitrary configurable ERC20 (`_underlying`) on the source chain and unlocks the same nominal amount on the destination chain (or refunds the same nominal amount on timeout). `send()` uses `safeTransferFrom(msg.sender, address(this), params.amount)` and then dispatches a cross-chain message that always encodes the full requested `params.amount`, never the amount the contract actually received. If `_underlying` is a fee-on-transfer/deflationary token, the contract's escrowed balance is always smaller than the amount promised in the dispatched message, exactly mirroring the Tapioca mtOFT bug where `wrap()`'s fee deduction was ignored by callers who assumed the full amount was minted.

### Finding Description
In `send()`: [1](#0-0) 

the ERC20 branch does:
```solidity
IERC20(_underlying).safeTransferFrom(msg.sender, address(this), params.amount);
```
and then builds the dispatch body via `_buildDispatchPost`, which unconditionally embeds `params.amount` (the requested amount, not the actual amount received): [2](#0-1) 

Unlike `IntentGatewayV2.placeOrder()`, which explicitly measures `balanceOf` before/after `safeTransferFrom` to compute the *actual received* amount before using it downstream (precisely to defend against fee-on-transfer tokens): [3](#0-2) 

`WrappedHyperFungibleToken.send()` has no such check. When the message reaches the destination chain, `onAccept` unconditionally transfers out the full nominal `message.amount` from the destination contract's own pooled underlying balance: [4](#0-3) 

and on timeout, `onPostRequestTimeout` refunds the full nominal `message.amount` back to the sender from the source contract's pooled balance: [5](#0-4) 

Since the contract only ever received `params.amount - fee` when the underlying is fee-on-transfer, every `send()` + delivery/refund round trip pays out more than it took in, systematically depleting the pooled underlying token reserve that backs *other* users' locked balances on both chains. This is a permanent, unrecoverable accounting drift (unlike the transient case that `IntentGatewayV2` explicitly guards against for the same class of asset).

### Impact Explanation
Each transfer of a fee-on-transfer underlying token bleeds the shared liquidity pool by the fee amount. Over repeated use (or a single large transfer with a high fee-bps token), the destination-chain contract's balance of `_underlying` becomes insufficient to service other users' legitimate incoming transfers, causing `onAccept`'s `safeTransfer` to revert — a permanent Denial of Service for the wrapped-asset bridge on that chain. Because the shortfall is drawn from the shared pool rather than the sender's own funds, it also constitutes a freezing/loss of other users' bridged assets (the last users to attempt withdrawal cannot be paid). This satisfies "permanent freezing of funds" / "a route unable to deliver messages" impact criteria. This is High severity, matching the Tapioca duplicate's rating, since it can fully break a deployed wrapped-token bridge instance.

### Likelihood Explanation
Likelihood depends on the owner configuring a fee-on-transfer/deflationary/rebasing token as `_underlying` via `configure()`. Given `WrappedHyperFungibleToken` is a generic wrapper explicitly designed to support "existing ERC20 tokens" with no code-level restriction against such tokens, and the codebase itself demonstrates (via `IntentGatewayV2`'s fee-on-transfer test suite) that fee-on-transfer tokens are an anticipated, in-scope asset class for this protocol, this is a realistic deployment configuration rather than a purely theoretical one.

### Recommendation
Mirror the pattern already used in `IntentGatewayV2.placeOrder()`: measure `IERC20(_underlying).balanceOf(address(this))` before and after `safeTransferFrom` in `send()`, use the actual received delta as the amount encoded in the dispatched `Message`, and reject the send (or adjust `params.amount`) accordingly so the amount promised cross-chain never exceeds what was actually escrowed.

### Proof of Concept
1. Owner configures `WrappedHyperFungibleToken` with `_underlying` set to a token that charges a 1% transfer fee (deflationary token), on both source and destination chain deployments, each pre-seeded with liquidity from prior legitimate transfers.
2. Alice calls `send(params)` with `amount = 1000`. `safeTransferFrom` moves tokens from Alice, but due to the 1% fee the contract only receives `990` tokens.
3. `_buildDispatchPost` encodes `amount: 1000` in the dispatched `Message`, independent of the `990` actually held.
4. On delivery, the destination `onAccept` calls `IERC20(_underlying).safeTransfer(beneficiary, 1000)`, paying out `10` more tokens than were ever escrowed for this transfer, funded from the shared pool contributed by other bridge users.
5. Repeating this (or using a single high-fee-bps token) depletes the pool until a subsequent legitimate `onAccept` call reverts due to insufficient balance — a permanent DoS/freezing of other users' locked funds on the wrapped-token bridge.

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        HyperFungibleToken.Message memory message = abi.decode(request.body, (HyperFungibleToken.Message));
        address beneficiary = _toAddr(message.to);

        if (_isWeth) {
            // Try a native-ETH push first (cheap for EOAs and payable contracts);
            // if the recipient cannot accept native value (no `receive()` / `fallback()
            // payable`), re-wrap the withdrawn ETH and deliver the underlying WETH as
            // an ERC-20 transfer instead. This mirrors the deposit-side flexibility of
            // `send()` (which accepts WETH from non-payable callers via `safeTransferFrom`)
            // so the refund path doesn't permanently lock funds for the same caller class.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = beneficiary.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(beneficiary, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(beneficiary, message.amount);
        }

        if (message.data.length > 0) {
            ICallDispatcher(_dispatcher).dispatch(message.data);
        }

        emit Received({
            from: message.from,
            to: beneficiary,
            source: string(request.source),
            amount: message.amount
        });
    }

            IERC20(_underlying).safeTransfer(refundee, message.amount);
