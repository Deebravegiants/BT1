### Title
VWAPOracle's `recordSpread` treats cross-chain "same-token" swaps as symmetrically pegged, computing spread from raw input/output amount deltas with no canonical peg verification - ([File: evm/src/utils/VWAPOracle.sol])

### Summary
`VWAPOracle` (implementing `IIntentPriceOracle`) is documented as only supporting "same-token swaps," but `recordSpread` never verifies that `inputs[i].token` on the source chain and `outputs[i].token` on the destination chain are actually the same canonical asset [1](#0-0) . It simply normalizes both amounts to 18 decimals and computes a bps "spread" purely from their ratio, exactly the PegOracle anti-pattern: two token quantities are compared symmetrically against each other with no reference to a canonical USD/ETH (or any external) value [2](#0-1) .

### Finding Description
`recordSpread` is called by the `IntentGateway` (`restrict(_intentGateway)`) after every fill, passing the order's `inputs` and the solver-provided `outputs` by index [3](#0-2) . The function:
- Resolves `inputToken`/`outputToken` decimals independently per chain [4](#0-3) .
- Never checks that `inputToken` and `outputToken` are the same underlying asset (no address/registry equality assertion), despite the contract's own docstring assuming "same-token swaps only" [1](#0-0) .
- Computes `spreadBps = (output - input) / input * 10000` and folds it into a cumulative, volume-weighted running average per `(sourceChain, token)` [5](#0-4) .

This is structurally identical to PegOracle: it assumes the two sides of the comparison move in lockstep (same intrinsic value) and attributes any divergence entirely to solver behavior ("filler captured spread" / "filler provided more") rather than to a genuine asset-value change on one leg. If the source-chain representation of the token (e.g., a bridged/wrapped instance) depegs from the destination-chain instance recorded as the "same token," or if a governance-configured `TokenDecimal` entry is wrong/stale via `_processTokenDecimalsUpdates` [6](#0-5) , every subsequent fill's spread computation is skewed — permanently poisoning the cumulative average returned by `spread()` [7](#0-6) .

### Impact Explanation
`IIntentPriceOracle.spread()` is exposed as the protocol's canonical price/quality signal for the token pair on that source chain. Because the underlying computation has no canonical peg anchor and no enforcement that inputs/outputs are truly the same asset, an asset depeg (or an incorrect `TokenDecimalsUpdate`) is misrecorded as solver misbehavior (or conversely, masks genuine adverse solver pricing as normal). Any downstream consumer of this oracle (solver reputation, fee/discount logic, fill acceptance gating) built on `spread()` inherits an unsound signal, which can misprice or wrongly gate intent fills for real users' escrowed funds. I could not find, within the indexed context, the exact downstream consumer that reads `spread()` to gate an on-chain action — this is a limitation of what the available index surfaces, not evidence that no such consumer exists, since the interface is explicitly named `IIntentPriceOracle` and wired into the fill path by the gateway itself.

### Likelihood Explanation
This triggers on every fill of a "same-token" cross-chain pair the moment the two chain-local representations diverge from parity (a realistic event for bridged/wrapped tokens) or when a decimals/asset misconfiguration is pushed via governance, requiring no attacker action beyond normal usage of an already-depegged or misconfigured pair — consistent with the original report's "high severity despite prerequisites" reasoning.

### Recommendation
Enforce that `inputToken` and `outputToken` are provably the same canonical asset (e.g., via an asset registry keyed by canonical ID, not raw address) before folding their amounts into the spread calculation, and/or anchor both amounts against an independent canonical price feed (USD/ETH) rather than comparing them directly to each other.

### Proof of Concept
1. `IntentGateway` calls `recordSpread(commitment, sourceChain, inputs, outputs)` after a same-token cross-chain fill, per `restrict(_intentGateway)` [8](#0-7) .
2. Suppose the source-chain token is a bridged representation that has depegged 5% below its destination-chain counterpart's canonical value, while the solver filled honestly at the "correct" market-adjusted rate.
3. `recordSpread` normalizes both amounts to 18 decimals and computes `spreadBps` purely from `(outputAmountNormalized - inputAmountNormalized) / inputAmountNormalized` [9](#0-8) , reporting a large negative (or positive) spread that has nothing to do with solver honesty.
4. This corrupted value is folded into `_tokenSpreads[sourceChainHash][inputToken]`'s cumulative weighted average, permanently skewing `spread()` for that pair [10](#0-9) , exactly mirroring the external report's renBTC/WBTC PegOracle depeg-misattribution scenario.

    function spread(bytes memory sourceChain, address token) external view returns (int256) {
        bytes32 chainHash = keccak256(sourceChain);
        CumulativeSpreadData memory data = _tokenSpreads[chainHash][token];
        if (data.totalVolume == 0) return 0;

        return data.weightedSpreadSum / int256(data.totalVolume);
    }

    function recordSpread(
        bytes32 commitment,
        bytes memory sourceChain,
        TokenInfo[] calldata inputs,
        TokenInfo[] calldata outputs
    ) external restrict(_intentGateway) {
        // Validate inputs and outputs have the same length
        if (inputs.length != outputs.length || inputs.length == 0) {
            return;
        }

        bytes32 sourceChainHash = keccak256(sourceChain);
        uint256 tokensLen = inputs.length;
        for (uint256 i = 0; i < tokensLen; i++) {
            address inputToken = address(uint160(uint256(inputs[i].token)));
            address outputToken = address(uint160(uint256(outputs[i].token)));

            // Get decimals for input token from storage (remote chain)
            // Native tokens (address(0)) use 18 decimals
            uint8 inputDecimals = inputToken == address(0) ? 18 : _tokenDecimals[sourceChainHash][inputToken];
            if (inputDecimals == 0) continue; // Skip if decimals not configured

            // Get decimals for output token directly from contract (local chain)
            // Native tokens (address(0)) use 18 decimals
            uint8 outputDecimals = outputToken == address(0) ? 18 : IERC20Metadata(outputToken).decimals();

            // Normalize both amounts to 18 decimals for comparison
            uint256 inputAmountNormalized = _normalizeAmount(inputs[i].amount, inputDecimals);
            uint256 outputAmountNormalized = _normalizeAmount(outputs[i].amount, outputDecimals);

            // Calculate spread for this token: (output - input) / input * 10000
            // Positive spread = filler provided more tokens (good for user)
            // Negative spread = filler provided fewer tokens (filler captured spread)
            int256 spreadBps = 0;
            if (inputAmountNormalized > 0) {
                int256 amountDiff = int256(outputAmountNormalized) - int256(inputAmountNormalized);
                spreadBps = (amountDiff * int256(BPS_DENOMINATOR)) / int256(inputAmountNormalized);
            }

            // Update cumulative spread data for this token (weighted by volume)
            int256 weightedSpread = spreadBps * int256(inputAmountNormalized);
            _updateCumulativeSpread(_tokenSpreads[sourceChainHash][inputToken], weightedSpread, inputAmountNormalized);

            // Emit event for each token
            emit SpreadRecorded(commitment, outputToken, spreadBps);
        }
    }

    function _processTokenDecimalsUpdates(TokenDecimalsUpdate[] memory updates) internal {
        uint256 updatesLen = updates.length;
        for (uint256 j = 0; j < updatesLen; j++) {
            bytes32 chainHash = keccak256(updates[j].sourceChain);
            uint256 tokensLen = updates[j].tokens.length;
            for (uint256 i = 0; i < tokensLen; i++) {
                if (updates[j].tokens[i].decimals == 0) revert InvalidInput();

                _tokenDecimals[chainHash][updates[j].tokens[i].token] = updates[j].tokens[i].decimals;
                emit TokenDecimalsUpdated(
                    updates[j].sourceChain, updates[j].tokens[i].token, updates[j].tokens[i].decimals
                );
            }
        }
    }
