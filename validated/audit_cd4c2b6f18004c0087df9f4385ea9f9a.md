### Title
Shopify Webhook `shop` (and `topic`/`webhook_id`/`api_version`) Fields Are Not Covered by the HMAC, Enabling Cross-Tenant Webhook Replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values used downstream for tenant/topic dispatch are read straight from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` validates only the body's HMAC and then trusts `request.shop` as the tenant identity handed to the app's handler. Because a single app-level `client_secret` signs webhooks for every shop that has installed the app, a malicious merchant can take a genuinely-signed webhook payload delivered for their own shop and resend it to the app's public webhook endpoint with a forged `shop-domain` header pointing at a victim shop; the signature still validates because the shop field was never part of the signed bytes.

### Finding Description
In `lib/shopify_api/webhooks/request.rb`: [1](#0-0) 

`to_signable_string` returns only `@raw_body`, so the HMAC verification in `Utils::HmacValidator.validate` covers exclusively the request body: [2](#0-1) 

`shop`, `topic`, `webhook_id`, and `api_version` are pulled from HTTP headers that an attacker fully controls in the raw HTTP request and are never mixed into `to_signable_string`.

`ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then immediately trusts `request.shop` (along with `topic`/`webhook_id`/`api_version`) to build the metadata passed to the host application's handler: [3](#0-2) 

The broken identity binding, expressed as an equality that should hold but doesn't:
`shop field covered by HMAC == shop field used to attribute the webhook to a tenant`
Here, the left side is empty (nothing outside the raw body is authenticated) while the right side is `request.shop`, taken from an arbitrary, attacker-supplied header.

### Impact Explanation
Because a Shopify app's `client_secret` (and therefore its webhook HMAC key) is shared across every shop that installs the app — not per-shop — an unprivileged internet user only needs to install the target app on a shop they control to receive a genuinely, validly-signed webhook (body + HMAC) for their own store. They can then replay that exact `raw_body`/`hmac` pair to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header with a victim shop's domain. `Registry.process` will pass HMAC validation (line 190) and dispatch the handler with `WebhookMetadata#shop` set to the victim's domain, causing the host application to process/store attacker-supplied payload data under another tenant's identity — a cross-tenant confusion/injection primitive that satisfies the "cross-tenant access" impact criterion.

### Likelihood Explanation
The webhook receiver is, by design, a public unauthenticated HTTP endpoint that must accept POSTs from the internet. Obtaining a legitimately-signed body+HMAC pair requires nothing more than installing the target app on any shop (a normal, unprivileged action available to any developer/merchant), which is explicitly the kind of "unprivileged internet user" scenario in scope here. No leaked secrets, tokens, or privileged access are required — only the attacker's own valid installation of the target app.

### Recommendation
Include the authenticated identity fields in the signed content, or otherwise cryptographically bind `shop`, `topic`, and `webhook_id` to the HMAC so a replay with a substituted `shop-domain` header fails validation. At minimum, `Registry.process` (or the host app's handler contract) should not treat `request.shop` as trusted tenant identity unless it is corroborated by an independent authenticated channel (e.g., cross-checked against the recipient endpoint's own per-shop registration, or the shop is included in the signable string as Shopify's `AuthQuery`/OAuth callback already does for the `shop` parameter in `lib/shopify_api/auth/oauth/auth_query.rb`).

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`, triggering a legitimate webhook delivery with a valid `X-Shopify-Hmac-Sha256` computed over the raw JSON body using the app's shared `client_secret`.
2. Attacker captures the raw body and the `X-Shopify-Hmac-Sha256` header value from that delivery.
3. Attacker crafts a new HTTP POST to the app's public webhook endpoint, using the identical raw body and HMAC header, but replaces `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request#initialize` accepts the forged headers (only checks presence, not authenticity) at `lib/shopify_api/webhooks/request.rb` lines 45-63; `Utils::HmacValidator.validate` succeeds because it only checks `@raw_body` against the unchanged HMAC (`lib/shopify_api/utils/hmac_validator.rb` lines 26-31); `Registry.process` dispatches the handler with `shop: "victim-shop.myshopify.com"` (`lib/shopify_api/webhooks/registry.rb` line 198), even though the payload was never generated for or by that shop.
