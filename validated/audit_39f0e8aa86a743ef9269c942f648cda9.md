Confirmed: the webhook HMAC only signs `@raw_body` [1](#0-0) , while `shop` is read straight from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` header [2](#0-1) , and `Registry.process` trusts that value as the tenant identifier after only checking the HMAC [3](#0-2) .

### Title
Webhook tenant identity (`shop`) is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the `X-Shopify-Hmac-Sha256` header against the raw request body, using the app's single, install-wide `client_secret`. The `shop` value that is handed to the app's `WebhookHandler` — and that most integrations use as the tenant key to look up/update local data — comes from the `X-Shopify-Shop-Domain` header, which is never included in the HMAC-signed content. Any merchant who has installed the app on their own store (a legitimate, unprivileged holder of validly-signed webhooks) can capture one of their own genuine webhook deliveries and replay it with the `shop-domain` header changed to a victim shop, producing a request that passes HMAC validation but attributes attacker-controlled data to another tenant.

### Finding Description
`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string`, and for webhooks that method returns only the raw body: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` fields are all pulled straight out of HTTP headers that are not part of `to_signable_string` and therefore are not covered by the signature: [4](#0-3) 

`Registry.process` validates only the HMAC and then immediately trusts `request.shop` as the tenant identity forwarded to the app's handler: [5](#0-4) 

Because the `client_secret` (and thus the HMAC key) is the same for every shop that installs the app — not a per-shop secret — a signature that is valid for shop A's payload is also a syntactically valid signature for the *same bytes* delivered under a different `X-Shopify-Shop-Domain` header. Any unprivileged user who owns a store where the app is installed can:
1. Trigger a webhook so Shopify sends them a genuinely-signed payload (valid HMAC, computed with the app's real secret) for an event they fully control (e.g. `products/create`, `orders/create` with attacker-chosen content).
2. Resend that exact body and HMAC header to the app's webhook endpoint, but with `X-Shopify-Shop-Domain` swapped to a victim's `*.myshopify.com` domain.
3. `HmacValidator.validate` succeeds because it never looks at the `shop-domain` header — it only checks `raw_body` against the secret.
4. `Registry.process` calls the handler with `WebhookMetadata.new(... shop: request.shop ...)`, so the handler is invoked as if the victim shop sent this attacker-controlled payload.

This breaks the identity binding: `shop authenticated (by HMAC) != shop stored/acted upon (from an unauthenticated header)`. Any host application logic that keys persistence, sync, or side effects (e.g., updating local product/order records, billing state, GDPR redaction handling) by `WebhookMetadata#shop` is exposed to cross-tenant data write/corruption using only a webhook that was legitimately, validly signed for a *different* shop.

### Impact Explanation
This is a cross-tenant access vulnerability: an unprivileged merchant/tenant of a multi-tenant app can make the app process and store attacker-controlled data under another merchant's identity, without ever possessing that merchant's credentials. This matches the Critical bar for cross-tenant access defined in scope.

### Likelihood Explanation
Likelihood is Medium-to-High: any developer/store owner who installs the app can obtain a validly-signed webhook payload from their own store (no special access required), and forging the `shop-domain` header on the replayed HTTP request requires no cryptographic secret at all, only knowledge of the target's `myshopify.com` domain (which is public).

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the value that is authenticated, e.g., by including the `X-Shopify-Shop-Domain` header in the signable string used for HMAC comparison (mirroring how `AuthQuery#to_signable_string` includes `shop`), or by requiring callers to independently verify that `request.shop` corresponds to a shop with an active, known session/installation before trusting it in `WebhookMetadata`. At minimum, document prominently that `Request#shop` is unauthenticated and must not be used as a sole tenant key.

### Proof of Concept
```ruby
require "shopify_api"

body = '{"id": 1, "title": "attacker item"}'
secret = ShopifyAPI::Context.api_secret_key # single secret shared by ALL shops that install the app

hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), secret, body)

# Step 1: attacker triggers this exact webhook on their OWN shop, "attacker-shop.myshopify.com",
# and Shopify legitimately signs it with the app's secret.
own_headers = {
  "x-shopify-topic" => "products/create",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac),
  "x-shopify-shop-domain" => "attacker-shop.myshopify.com",
}

# Step 2: attacker resends the SAME body + SAME hmac header, only swapping shop-domain
spoofed_headers = own_headers.merge("x-shopify-shop-domain" => "victim-shop.myshopify.com")

request = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: spoofed_headers)

# HMAC validation succeeds because the signature only covers `body`, not the shop header
raise "expected valid" unless ShopifyAPI::Utils::HmacValidator.validate(request)

# Registry.process will invoke the handler believing this came from victim-shop.myshopify.com
ShopifyAPI::Webhooks::Registry.process(request)
# => handler.handle(data: WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", ...))
```
