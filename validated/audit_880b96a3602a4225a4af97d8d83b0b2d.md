I have enough evidence to establish a confirmed, reachable vulnerability. The `Sp1BeefyProof` conversion path is directly invoked from the permissionless `submit_proof`/`verify_and_apply` and `settle_uncle_proof` extrinsics in `pallet-beefy-consensus-proofs`, and the `Commitment -> SpCommitment` conversion panics on an empty `payload` array — a value fully controlled by the ABI-encoded proof bytes any unprivileged caller submits.

### Title
Panic-based Denial of Service via Malformed BEEFY Consensus Proof — ([File: evm/rust/src/conversions.rs])

### Summary
`pallet-beefy-consensus-proofs::verify_and_apply` and `settle_uncle_proof` are reachable through the permissionless extrinsics `submit_proof`/`handle_unsigned`-style flows in `modules/pallets/beefy-consensus-proofs/src/lib.rs`. Both paths ABI-decode an attacker-supplied byte string into `ismp_abi::ecdsa_beefy::BeefyConsensusProof` / `ismp_abi::sp1_beefy::SP1Beefy::SP1BeefyProof`, then convert it via `From` impls in `evm/rust/src/conversions.rs` before any cryptographic verification occurs. Several of these `From` impls call `.expect(...)` on attacker-controlled data, most notably:

```rust
impl From<Commitment> for SpCommitment {
    fn from(value: Commitment) -> Self {
        let mut iter = value.payload.into_iter();
        let first = iter.next().expect("commitment has at least one payload entry");
        ...
``` [1](#0-0) 

`Commitment.payload` is a dynamic array (`Payload[]`) decoded directly from ABI-encoded bytes with no length check. Since `abi_decode_params` (Solidity ABI decoding) allows a zero-length dynamic array, an attacker can submit a proof whose `Commitment.payload` is empty, causing `iter.next()` to return `None` and the `.expect(...)` to panic before any signature or merkle verification runs.

### Finding Description
The conversion is invoked unconditionally on decode, ahead of all cryptographic checks:

```rust
let abi_proof = <ismp_abi::ecdsa_beefy::BeefyConsensusProof as SolType>::abi_decode_params(abi_payload)
    .map_err(|_| Error::<T>::AbiDecodeFailed)?;
let scale_proof: beefy_verifier_primitives::ConsensusMessage = abi_proof.into();
``` [2](#0-1) 

The `.into()` call triggers `From<BeefyConsensusProof> for ConsensusMessage`, which in turn converts the nested `Commitment` via the panicking `From<Commitment> for SpCommitment` shown above [3](#0-2) . This is exactly the same bug class as the reported Hyperledger Fabric CVE: a malformed consensus proof from an unprivileged network participant crashes the node process before validation — except here the crash is a Rust panic that, in a Substrate/WASM runtime, aborts block execution / halts the node rather than returning a typed error, unlike the many neighboring paths in this same file which have already been hardened to return `Error::<T>::AbiDecodeFailed`/`Error::<T>::VerificationFailed` for malformed input.

Multiple other `.expect(...)` conversions in the same file (`block number out of bounds`, `validator set id out of bounds`, `authority index out of bounds`, `parachain leaf index out of bounds`, `leaf count out of bounds`, `mmr leaf index out of bounds`) share the same root cause: they convert attacker-controlled `U256`/array values with `.try_into().expect(...)` instead of returning a `Result`, all reachable from the same permissionless `submit_proof` extrinsic before cryptographic verification is performed.

### Impact Explanation
This is a route-unable-to-deliver-messages / denial-of-service condition on the BEEFY consensus update path used by Hyperbridge's Polkadot/Kusama message relay. Any unprivileged relayer can submit a single malformed (empty-payload) `BeefyConsensusProof` through `submit_proof` and panic the pallet's WASM execution, which in a Substrate runtime context aborts the extrinsic (and, depending on how the panic unwinds through `frame_support::transactional` and the executor, can be a fatal runtime trap rather than a graceful dispatch error). At minimum this denies consensus updates and blocks all downstream cross-chain message delivery relying on the BEEFY client; at worst it repeatedly interrupts block execution for validators processing the malicious extrinsic, matching the "route unable to deliver messages" acceptance criterion.

### Likelihood Explanation
High. `submit_proof` is documented and tested as a permissionless, unsigned-style extrinsic (see the test suite's `test_unknown_proof_type_rejected`/`test_empty_proof_rejected` patterns in `parachain/simtests/src/pallet_beefy_consensus_proofs.rs`, which already probe malformed-proof handling but do not cover an empty `payload` array specifically). Constructing an ABI-encoded `BeefyConsensusProof` with `payload.length == 0` requires no special privileges, no valid signatures, and no chain state — it is a pure client-side encoding exercise.

### Recommendation
Replace every `.expect(...)` in the `From` conversions in `evm/rust/src/conversions.rs` (starting with `From<Commitment> for SpCommitment`, and including the `try_into().expect(...)` conversions for block number, validator set id, authority index, leaf index/count, and para id) with fallible `TryFrom` implementations returning a typed error, and thread that error through `verify_and_apply`/`settle_uncle_proof` as `Error::<T>::AbiDecodeFailed` (mirroring how `abi_decode_params` failures are already handled at lines 824/833 of `modules/pallets/beefy-consensus-proofs/src/lib.rs`).

### Proof of Concept
1. Craft `abi_payload` bytes that ABI-encode a `BeefyConsensusProof` whose `relay.signedCommitment.commitment.payload` is a zero-length `Payload[]` array (valid ABI encoding: offset + length word `0`).
2. Prefix with `PROOF_TYPE_NAIVE` and submit via `BeefyConsensusProofs::submit_proof` (or directly call `Pallet::<T>::verify_and_apply(&proof)`).
3. `abi_decode_params` succeeds (the array itself decodes fine, just with zero elements).
4. `abi_proof.into()` invokes `From<Commitment> for SpCommitment`, `value.payload.into_iter().next()` returns `None`, and `.expect("commitment has at least one payload entry")` panics — reachable purely from unsigned/permissionless input, before any BEEFY signature or authority-set check runs.
