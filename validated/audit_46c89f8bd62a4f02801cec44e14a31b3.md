### Title
Webhook HMAC verification only covers the request body, allowing the `shop`, `topic`, `webhook_id` and `api_version` fields to be forged even after successful signature validation - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a request as authentic once `Utils::HmacValidator.validate` succeeds, and then forwards `request.shop`, `request.topic`, `request.webhook_id` and `request.api_version` to the app's handler as trusted, per-shop metadata. However, the HMAC is computed and verified only over the raw request body, `lib/shopify_api/webhooks/request.rb:35-38`, while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from unauthenticated HTTP headers, `lib/shopify_api/webhooks/request.rb:15-33`. This breaks the binding `shop_authenticated == shop_used_for_routing`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate`/`validate_signature` compute/compare the signature strictly against that signable string: [2](#0-1) 

But `Request#shop`, `#topic`, `#webhook_id`, `#api_version` all come from raw headers with no cryptographic tie to the signed body: [3](#0-2) 

`Registry.process` validates the HMAC once and then unconditionally builds handler metadata from these unverified header values: [4](#0-3) 

This is a real, exploitable asymmetry within this gem, not merely a documentation nuance: the sibling `AuthQuery` class (used for OAuth callback HMAC validation) explicitly folds `shop` into its signed string, showing the gem's own established pattern of binding `shop` into the HMAC input when tenant identity matters: [5](#0-4) 

The webhook path deviates from that pattern — `shop` (along with `topic`/`webhook_id`/`api_version`) is never included in `to_signable_string`, so the HMAC check gives no assurance about which shop, topic, or webhook the verified bytes belong to.

The gem's own documentation tells integrators that `Registry.process` "will verify the request did indeed come from Shopify" and describes `data.shop` simply as "The shop domain of the webhook" (i.e. as trustworthy metadata), reinforcing that host apps are expected to rely on it as authenticated: [6](#0-5) [7](#0-6) 

### Impact Explanation
An attacker who controls any shop that has installed the app (an ordinary, unprivileged merchant — no special credential needed) can trigger arbitrary events in their own store (e.g. create products/orders) to obtain genuine `(raw_body, hmac)` pairs signed by Shopify with the app's shared secret, where the body content is entirely attacker-chosen (their own order/product payload). The attacker then replays that exact `raw_body`/`hmac-sha256` pair to the app's public webhook endpoint while forging the `x-shopify-shop-domain` header to name a different, victim shop. `HmacValidator.validate` still passes (only the body bytes are checked), so `Registry.process` calls the app handler with `WebhookMetadata#shop == "victim-shop.myshopify.com"` while the body content actually belongs to the attacker's own shop. Any app that follows the documented pattern of keying background work, per-tenant storage, or side effects off `data.shop` (exactly as shown in the gem's own example handler) will process attacker-controlled data under the wrong tenant's identity — a cross-tenant data-confusion/injection primitive achieved purely through this gem's webhook-authenticity guarantee being weaker than documented.

### Likelihood Explanation
Requires only: (1) the attacker's own shop to have the app installed (an ordinary self-service action), (2) the ability to trigger any webhook-eligible event in their own store, and (3) sending one forged HTTP request with a swapped header to the app's public webhook endpoint. No access to the `api_secret_key`, no TLS interception, and no privileged account are needed — the attacker only ever uses signatures Shopify itself generated for their own shop. This is straightforward to execute for anyone with a normal merchant account.

### Recommendation
Bind the shop (and ideally topic/webhook_id) into the HMAC-verified content, mirroring the pattern already used in `AuthQuery#to_signable_string`. Since Shopify signs only the raw body by protocol, the gem should additionally cross-check that the shop asserted in `WebhookMetadata` corresponds to a shop the app actually has a stored session/subscription for that specific `webhook_id`/topic combination before invoking the handler, or clearly document that `data.shop` is *not* cryptographically authenticated and must be independently verified by the host application before being trusted for tenant routing.

### Proof of Concept
```ruby
# Attacker owns "attacker-shop.myshopify.com" with the app installed.
# Step 1: trigger a real event (e.g. create an order) to get a genuine
# Shopify-signed webhook delivery for their own shop:
#   raw_body = '{"id":1,"note":"malicious payload"}'
#   hmac     = Base64.encode64(OpenSSL::HMAC.digest("sha256", app_secret, raw_body))
#   (attacker captures this pair by controlling the receiving endpoint or a proxy)

# Step 2: replay the identical body+hmac, but forge the shop header:
forged_headers = {
  "x-shopify-topic"        => "orders/create",
  "x-shopify-hmac-sha256"  => hmac,                          # still valid! only signs raw_body
  "x-shopify-shop-domain"  => "victim-shop.myshopify.com",   # forged, not covered by hmac
  "x-shopify-webhook-id"   => "any-id",
  "x-shopify-api-version"  => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) succeeds (lib/shopify_api/webhooks/request.rb:35-38,
#    lib/shopify_api/utils/hmac_validator.rb:26-31)
# => handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: attacker_body, ...))
# => app processes attacker-controlled data attributed to "victim-shop.myshopify.com"
```

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
