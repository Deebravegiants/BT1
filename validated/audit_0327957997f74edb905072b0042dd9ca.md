## Title
Webhook `shop` attribution is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating an HMAC computed only over the raw request body, but then dispatches to the app's handler using the `shop` value taken from an HTTP header that is *not* covered by that HMAC. This breaks the intended binding `HMAC-authenticated body == HMAC-authenticated shop`, allowing an attacker who legitimately receives one signed webhook (as an ordinary, unprivileged merchant using the app on their own store) to relabel it as coming from a different shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

while `shop` is read straight from an unauthenticated header: [2](#0-1) 

`Registry.process` validates the HMAC against the request and, if it passes, immediately trusts `request.shop` (and `request.topic`/`request.webhook_id`) to build the metadata handed to the app's handler: [3](#0-2) 

The equality the gem is supposed to enforce is: *the shop that the HMAC secret authenticated == the shop the handler acts on*. Because `shop-domain` is never part of `to_signable_string`, `HmacValidator.validate` (which computes `HMAC(api_secret_key, raw_body)` and compares it to the `hmac-sha256`/`x-shopify-hmac-sha256` header via `OpenSSL.secure_compare`) only proves "this body byte sequence was produced with the app's secret" — it proves nothing about which shop it belongs to: [4](#0-3) 

An unprivileged attacker who runs their own store on the same app receives real, validly-signed webhooks from Shopify for their own shop (body + `X-Shopify-Hmac-Sha256` + `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`). Because the signature only covers the body, the attacker can replay the exact same body/HMAC pair to the app's webhook endpoint while substituting `X-Shopify-Shop-Domain` with a victim shop's domain. `HmacValidator.validate` still passes (body unchanged), so `Registry.process` calls the handler with `shop: "victim-shop.myshopify.com"` even though the payload actually originated from, and was signed for, the attacker's own shop.

### Impact Explanation
Any application built on this gem that keys tenant-specific logic off the `shop` value passed to `WebhookHandler#handle` (e.g., looking up/creating records, triggering GDPR redaction flows, updating per-shop state) can be made to attribute an attacker-controlled payload to an arbitrary victim shop. This is a cross-tenant confusion/access issue that crosses a tenant boundary using only an unprivileged merchant account — no access token, `client_secret`, or privileged access is required.

### Likelihood Explanation
Exploitation only requires: (1) being (or creating) an ordinary merchant/store that installs the app, so as to receive at least one legitimately signed webhook, and (2) the ability to POST an HTTP request to the app's public webhook endpoint with attacker-chosen headers — both are available to any unprivileged internet user interacting with the app normally. The check the gem is missing (binding `shop` into the signed material) is a one-line omission, making the root cause simple and the exploitation path direct.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the value that is cryptographically verified, or otherwise require the caller to independently corroborate the header-derived `shop` against a trusted source (e.g., cross-check against the API version's expected format and/or require the consuming app to validate `shop` against its own known-shop registry before trusting it) before dispatching to handlers. At minimum, document prominently that `request.shop` is unauthenticated and must not be trusted for authorization decisions, and consider raising `Errors::InvalidWebhookError` if `shop` cannot be independently confirmed.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a webhook (e.g. `orders/create`), receiving from Shopify a POST with body `B`, header `X-Shopify-Hmac-Sha256: H` (valid for `B`), and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker replays the request to the app's webhook endpoint, keeping body `B` and header `X-Shopify-Hmac-Sha256: H` unchanged, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses this into a `Request` whose `to_signable_string` is still `B`; `Utils::HmacValidator.validate` recomputes `HMAC(api_secret_key, B)` and it matches `H`, so validation succeeds.
4. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...))`, causing the app to process attacker-controlled data under the victim shop's identity.
