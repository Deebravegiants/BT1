### Title
Nil-pointer panic on unprivileged vault `publicKey.get` gateway request - ([File: core/capabilities/vault/gw_handler.go])

### Summary
`GatewayHandler.HandleGatewayMessage` dereferences `req.Params` without a nil check for the `vaulttypes.MethodPublicKeyGet` method, unlike every other vault method (`SecretsCreate`, `SecretsUpdate`, `SecretsDelete`, `SecretsList`), which are routed through `GatewayVaultRequestProcessor.processRequest`/`processXRequest`, each of which explicitly checks `if req.Params == nil` before unmarshalling [1](#0-0) . The `MethodPublicKeyGet` case skips this processor entirely and calls `handlePublicKeyGet` directly [2](#0-1) .

### Finding Description
`handlePublicKeyGet` does:
```go
r := &vaultcommon.GetPublicKeyRequest{}
if err := json.Unmarshal(*req.Params, r); err != nil {
``` [3](#0-2) 

`req.Params` is typed `*json.RawMessage` on `jsonrpc.Request[json.RawMessage]`. If a caller sends a JSON-RPC request for `vault.publicKey.get` with the `params` field entirely omitted (which is valid per JSON-RPC 2.0 — `params` is optional), `req.Params` is `nil`, and `*req.Params` dereferences a nil pointer, causing a runtime panic. This mirrors the CVE-2019-10051 bug class: an unchecked "Some/None"-style value (an `Option`/nilable field) is unconditionally unwrapped in a hot request-handling path, crashing the process.

This is reachable from an unprivileged, unauthenticated end user because `MethodPublicKeyGet` has no authorization gate — the switch statement in `HandleGatewayMessage` routes straight to `handlePublicKeyGet` with no `AuthorizeRequest` call, unlike the secrets methods that go through `requestProcessor.ProcessRequest` (which performs authorization) [4](#0-3) . The request travels through the internet-facing Gateway (`gateway.ProcessRequest`) and the Gateway↔node connector to reach this handler on the DON node [5](#0-4) , so an external client controls the JSON-RPC envelope, including whether `params` is present.

### Impact Explanation
A panic inside the connector's `readLoop` goroutine (`core/services/gateway/connector/connector.go`) that is not recovered would crash the read loop for the gateway connection, or if unrecovered further up the goroutine stack, could crash the node process — a remote, unauthenticated denial-of-service against a DON node's vault capability, analogous to the Suricata SMB crash triggered by unsafe unwrapping of an optional value from network input.

### Likelihood Explanation
High: `vault.publicKey.get` requires no signature/authorization check to reach `handlePublicKeyGet`, and omitting `params` in a JSON-RPC request is trivial and standards-compliant. Any client able to reach the Gateway's HTTP endpoint (or send a JSON-RPC message with `DonID` targeting this handler) can trigger it with a single crafted request containing no `params` field.

### Recommendation
Add an explicit `if req.Params == nil` check in `handlePublicKeyGet` (mirroring the checks already present in `processCreateSecretsRequest`, `processDeleteSecretsRequest`, etc.) and return a `UserMessageParseError`/`InvalidParamsError` response instead of dereferencing `req.Params` unconditionally. More broadly, audit `HandleGatewayMessage` for any other method routed outside `GatewayVaultRequestProcessor` to ensure symmetrical nil-params handling before authorization/unmarshalling.

### Proof of Concept
1. Send a JSON-RPC request to the Gateway (or directly craft `jsonrpc.Request[json.RawMessage]{Method: vaulttypes.MethodPublicKeyGet, Params: nil}`) with no `params` field.
2. The Gateway forwards it to the DON node handler via the connector `readLoop`.
3. `GatewayHandler.HandleGatewayMessage` matches `case vaulttypes.MethodPublicKeyGet` and calls `handlePublicKeyGet(ctx, gatewayID, req)`.
4. `json.Unmarshal(*req.Params, r)` panics with a nil pointer dereference since `req.Params` is `nil`.

**Uncertainty note:** I was unable to confirm from the indexed portion of the codebase whether the outer connector `readLoop` (or another caller of `HandleGatewayMessage`) wraps handler invocation in a `recover()`, which would determine whether this crashes only the read-loop goroutine or the whole node process. I also could not fully verify, within the index, whether the Gateway-side `core/services/gateway/handlers/vault/handler.go` performs any upstream validation that would reject a `params`-less `publicKey.get` request before forwarding to the node — the file's `HandleJSONRPCUserMessage`/`HandleLegacyUserMessage` and any related nil-params checks were not found in the available index. If precise confirmation of these points is needed, a full-repository session (not just index search) would be required.
