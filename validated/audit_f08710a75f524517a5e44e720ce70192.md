### Title
Webhook shop-domain identity spoofing due to HMAC not covering the shop header - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` claims to "verify the request did indeed come from Shopify" before invoking the app's webhook handler, but the HMAC signature verified by `Utils::HmacValidator` only covers the raw request body. The `shop` attribute exposed to the handler is read directly from the unauthenticated `shop-domain` HTTP header and is never included in the signed bytes, breaking the binding `shop authenticated == shop the handler acts on`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
while `shop` is parsed straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header, a value fully controlled by whoever sends the HTTP request: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over `to_signable_string` (i.e., the body) and compares it against the `hmac` header: [3](#0-2) 

`Registry.process` uses this validation result as the sole authentication gate, then forwards the attacker-controlled `request.shop` straight into the `WebhookMetadata` handed to the app's handler: [4](#0-3) 

Because a single `api_secret_key` is shared across every shop that has installed the same app, any unprivileged party who installs the app on their own store receives genuine Shopify webhooks (valid body + valid HMAC) for their own shop. They can then replay that exact body/HMAC pair to the app's public webhook endpoint while substituting the `shop-domain` header with a victim shop's domain. The HMAC check still passes (it only checks the body), and the app's handler — per the documented contract in `docs/usage/webhooks.md` ("`shop`, `String` - The shop domain of the webhook") — will process the webhook as if it genuinely originated from the victim shop, e.g. enqueueing `perform_later(topic:, shop_domain: data.shop, webhook:)` against the victim's tenant record.

### Impact Explanation
This crosses a tenant boundary: an attacker who is merely a legitimate installer of the app (unprivileged relative to any other merchant) can forge webhook events attributed to an arbitrary victim shop domain, since the identity binding "shop claimed in header" vs "shop bound by the signature" is never enforced by the gem despite the gem's own documentation asserting the request is "verified" to have come from Shopify. Depending on how the host app uses `data.shop` (e.g., looking up/updating the victim's local session, order, or billing records keyed by shop domain), this enables cross-tenant data injection or corruption.

### Likelihood Explanation
Requires only that the attacker be able to install the target app on a shop they control (a normal, unprivileged onboarding flow) and replay an HTTP POST with a modified header — no access token, `client_secret`, or any privileged credential is needed. This matches the reported bug class (verifying one piece of data while acting on another, unbound identity field) directly, just moved from an ERC-20 index parameter to an HTTP header.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) to the signed payload before trusting it — e.g., have `Registry.process` cross-check `request.shop` against the shop associated with the specific `webhook_id` retrieved via an authenticated API lookup, or otherwise require the host application to independently verify the shop is one it has an active session/installation for the exact `webhook_id` before acting on it, and call this out explicitly in `docs/usage/webhooks.md` since the current wording ("this will verify the request did indeed come from Shopify") overstates what is actually verified.

### Proof of Concept
1. Install the vulnerable app on attacker-controlled shop `attacker.myshopify.com`; trigger any subscribed webhook topic to receive a genuine Shopify webhook: raw body `B` with header `x-shopify-hmac-sha256: H` (valid HMAC of `B` under the app's shared `api_secret_key`) and `x-shopify-shop-domain: attacker.myshopify.com`.
2. Replay the exact same request to the app's public webhook endpoint, changing only the `x-shopify-shop-domain` header to `victim.myshopify.com` (or any arbitrary value), leaving body `B` and `hmac` header `H` untouched.
3. `ShopifyAPI::Webhooks::Request#hmac` and `#topic` read from headers unchanged; `Utils::HmacValidator.validate` recomputes HMAC over `B` only, which still matches `H`, so `Registry.process` proceeds.
4. `Registry.process` calls the app's handler with `WebhookMetadata.new(topic:, shop: "victim.myshopify.com", body:, ...)`, causing the host app to process/act on data as though it belongs to `victim.myshopify.com`.
