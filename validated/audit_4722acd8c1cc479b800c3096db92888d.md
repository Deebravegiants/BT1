### Title
Webhook shop identity is not covered by the HMAC signature, enabling cross-tenant spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, then unconditionally trusts the `shop-domain` header as the tenant identifier passed to the host application's handler. Because the header is not part of the signed material, an attacker who controls one legitimate webhook delivery (body + valid HMAC, e.g. from their own installed shop) can swap the `shop-domain` header value to any other shop and have it accepted as authentic.

### Finding Description
The equality this flow is supposed to enforce is:
`shop the payload was authenticated for == shop attributed to the handler`

`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

`ShopifyAPI::Webhooks::Request#shop` is read straight from the (attacker-controllable, header-transported) `shop-domain`/`x-shopify-shop-domain` value with no cryptographic binding to the body: [2](#0-1) 

`Utils::HmacValidator.validate` computes/compares the signature over `to_signable_string` only — i.e., over the body, never over `shop`: [3](#0-2) 

`Registry.process` runs this HMAC check and then forwards `request.shop` verbatim into `WebhookMetadata`, which is the value the host app's handler is documented to trust as the webhook's shop: [4](#0-3) 

Contrast this with the OAuth callback path, where `shop` **is** part of the signed data (`AuthQuery#to_signable_string` includes `shop`), showing the gem is capable of, and elsewhere does, bind identity fields into the HMAC: [5](#0-4) 

Because `shop` is excluded from the signed bytes, "HMAC verified" and "shop field trusted" are two different, unlinked claims — exactly the identity-binding break described in the report (a field acted upon without being covered by the authenticator).

### Impact Explanation
An attacker who operates their own shop and has installed the target app can receive genuine webhook deliveries for that shop, each with a body and a Shopify-computed HMAC signed with the app's `api_secret_key` over that body. Because the signature does not cover the `shop-domain` header, the attacker can resend that exact body/HMAC pair to the app's webhook endpoint while substituting the `shop-domain` header with a victim shop's domain. `HmacValidator.validate` still succeeds, and `Registry.process` hands the handler a `WebhookMetadata` claiming the payload came from the victim shop. The documented usage pattern for handlers explicitly trusts `data.shop` for tenant-scoped effects: [6](#0-5) 

Any host app following this documented pattern to key persistence, job scoping, or business logic by `data.shop` is exposed to cross-tenant data confusion/injection — the attacker forges which shop a given (attacker-authored) payload is attributed to.

### Likelihood Explanation
Any unprivileged user of the internet who can install the app on a shop they control (or otherwise obtain one valid webhook body/HMAC pair) can perform this attack repeatably against the app's public webhook endpoint, with no access token, secret, or privileged access required.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) header values into the HMAC-signed material, e.g., include them in `Webhooks::Request#to_signable_string` or otherwise cryptographically verify that the `shop-domain` header matches a value derivable from the authenticated body/headers before constructing `WebhookMetadata`. At minimum, document prominently that `data.shop` is unauthenticated and must not be used for tenant-scoping decisions, and prefer verifying tenant identity via a signed value in the body itself.

### Proof of Concept
1. Install the app on `attacker.myshopify.com` and subscribe to a webhook topic.
2. Capture a genuine delivery: raw body `B`, and header `x-shopify-hmac-sha256: H` (valid HMAC of `B` with the app's secret), plus `x-shopify-shop-domain: attacker.myshopify.com`.
3. Replay the same `B` and `H` to the app's webhook endpoint, but set `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `B` against `H` — this passes.
5. The handler is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", body: B, ...)`, i.e., the app now believes attacker-controlled data `B` originated from `victim.myshopify.com`, as shown by `Registry.process`: [7](#0-6)
