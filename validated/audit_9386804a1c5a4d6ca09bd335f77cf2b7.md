Based on my review of the webhook processing path, I found a valid analog to the reported bug class.

### Title
Webhook tenant identity (`shop`) is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
The reported Solidity bug is a broken binding: a value (`asyncFee`) is acted upon by one component but the follow-through step that should tie it back to the correct recipient (`keeper`) is missing, so the value ends up attributed to the wrong party (the factory instead of the caller). The equivalent binding-break in this gem is in webhook verification: the HMAC signature only binds the *body*, but the tenant identity (`shop`) used by the host application to route/act on the webhook is taken from an unauthenticated header that is never included in what the HMAC covers.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body: [1](#0-0) [2](#0-1) 

`shop` is read directly from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header and is never part of `to_signable_string`. `Registry.process` validates the HMAC only against the body via `Utils::HmacValidator.validate(request)`, and then unconditionally trusts `request.shop` (the unauthenticated header) when constructing the metadata passed to the host application's handler: [3](#0-2) 

The identity binding that should hold is: `shop` used by the handler == `shop` that produced the HMAC-signed payload. In practice, that equality is never checked — the HMAC only proves "signed with this app's `client_secret`," not "signed for this specific `shop`." Because Shopify apps use a single `client_secret` shared across every installed shop, any shop that has installed the app can obtain a validly HMAC-signed webhook body (e.g. by triggering a webhook containing attacker-influenced content on their own store), then POST that same body to the app's public webhook endpoint with the `shop-domain` header changed to a victim shop. `Utils::HmacValidator.validate` will still return `true` because it only checks the body against the shared secret, and `Registry.process` will hand the handler a `WebhookMetadata` claiming to be from the victim shop.

### Impact Explanation
This breaks the tenant boundary: an unprivileged (but legitimately app-installed) merchant can cause the host application to process a forged webhook that appears to originate from a different merchant's shop, since `shop` is never covered by the cryptographic signature. Depending on how the host application uses `WebhookMetadata#shop` (commonly to look up the tenant's session/access token and perform writes on their behalf), this can lead to cross-tenant data corruption or unauthorized actions being attributed to/performed against another tenant — matching the "cross-tenant access" impact category.

### Likelihood Explanation
Requires only: (1) attacker controls one shop that has installed the target app (unprivileged, no special credentials needed beyond a normal install), and (2) the app's webhook endpoint is reachable on the public internet (true for essentially all Shopify apps, since Shopify itself must be able to POST to it). No access token, `client_secret`, or leaked credential is required by the attacker — only the ability to receive one genuine webhook for their own shop and replay it with a modified header.

### Recommendation
Do not treat `request.shop` as trusted merely because the body's HMAC validates. Options: (a) include `shop` in the signable payload used for the HMAC comparison where feasible, or (b) require host applications/this library to cross-check `request.shop` against the shop associated with the specific webhook subscription/session that is expected to receive that topic, rather than trusting the header value outright, and document this gap clearly if it cannot be fixed at the library level (since `client_secret` is shared per-app, not per-shop, by Shopify's design).

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`.
2. Attacker triggers a webhook topic (e.g., `products/update`) whose body content they can influence, capturing the raw body `B` and the valid `X-Shopify-Hmac-Sha256` header Shopify computed over `B` with the app's shared `client_secret`.
3. Attacker POSTs to the app's public webhook endpoint with body `B`, the captured valid HMAC header, and `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` returns `true` (HMAC only checks body `B`), and `Registry.process` invokes the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, causing the host app to act as if the webhook came from the victim tenant.
