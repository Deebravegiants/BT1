### Title
Batch PoA-Bridge withdrawal status reported for the wrong destination when a transaction contains multiple withdrawals of the same asset - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal()` and `waitForWithdrawalCompletion()` resolve the on-chain settlement status of a specific withdrawal purely by matching `assetId` (via `near_token_id`), ignoring the withdrawal's `index`, `amount`, and `destinationAddress`. When a single NEAR transaction contains two or more withdrawals of the same asset (a supported, documented batch-withdrawal scenario), the SDK returns the first matching withdrawal record's status/`txHash` for every identifier that shares that assetId, even though each corresponds to a distinct destination address/amount.

### Finding Description
`findMatchingWithdrawal` in `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts` selects a withdrawal record solely by asset: [1](#0-0) 

`describeWithdrawal` uses that helper as the sole source of truth for the specific `WithdrawalIdentifier` passed in (which carries `index`, `amount`, and `destinationAddress` in `withdrawalParams`, but none of these are used in the match): [2](#0-1) 

The equivalent code path in `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts` has the identical limitation, explicitly documented in its own comment: [3](#0-2) 

The repo's own test, `"matches withdrawal by assetId, not by index"`, demonstrates the mechanism (though with distinct assets producing a coincidentally-correct result) and confirms index is discarded by design: [4](#0-3) 

The SDK's public API explicitly supports batching multiple withdrawal params — including potentially the same `assetId` with different `destinationAddress`/`amount` — into one NEAR transaction/intent: [5](#0-4) [6](#0-5) 

Because `findMatchingWithdrawal` returns the first array element whose `near_token_id` matches — with no disambiguation by `index`/`amount`/`destinationAddress` — if a batch contains two withdrawals of the same PoA-bridged token to two different destination addresses, `describeWithdrawal` called for withdrawal-identifier #0 and withdrawal-identifier #1 can both resolve to the *same* underlying withdrawal record and thus report the *same* `status`/`txHash`. This breaks the equality "status/hash reported == actual on-chain outcome for that specific withdrawal": one destination's completion (with its real `transfer_tx_hash`) gets reported for a different destination that may still be pending, failed, or settled with a different hash.

### Impact Explanation
This falls under the High-severity category: "a status or hash misreport making an integrator credit or refund twice." An integrator relying on `sdk.waitForWithdrawalCompletion` / `bridge.describeWithdrawal` / `waitForWithdrawalCompletion()` for batch PoA withdrawals of the same token could:
- Mark a withdrawal to destination B as "completed" with destination A's transaction hash, when B's funds haven't actually arrived — leading to premature crediting of a user or double-crediting after B's real completion is later (mis)detected.
- Fail to detect a genuinely failed/pending withdrawal to B because it's masked by A's "COMPLETED" record.

### Likelihood Explanation
This requires no malicious actor — it triggers under a normal, SDK-supported usage pattern: a batch withdrawal (`processWithdrawal`/`signAndSendWithdrawalIntent` with an array of `withdrawalParams`) where two or more entries share the same PoA-bridged `assetId` (e.g., the same token sent to two different destination addresses/amounts in one call, which the batch withdrawal feature explicitly allows). Both the production code comment and dedicated tests acknowledge this exact same-token-multiple-withdrawals limitation, indicating it is a known but unresolved gap rather than a rare edge case.

### Recommendation
Disambiguate withdrawal records using more than `assetId`: incorporate `amount` (and preferably `destinationAddress`, when the POA API/response exposes it) so each `WithdrawalIdentifier`'s specific withdrawal is uniquely matched, e.g. by sorting/matching candidates by `(assetId, amount)` pairs against the corresponding sorted `withdrawalParams`, as the code's own comments suggest but do not implement. Until fixed, the SDK should either reject/warn on batches containing duplicate `assetId`s routed through PoA Bridge, or surface an explicit ambiguity error from `describeWithdrawal` rather than silently returning a match.

### Proof of Concept
1. Call `sdk.processWithdrawal` (or `signAndSendWithdrawalIntent`) with `withdrawalParams` as an array containing two entries for the same PoA-bridged token (e.g., `nep141:btc.omft.near`), different `amount`/`destinationAddress` for each, in one NEAR transaction/intent.
2. After the NEAR intent settles, call `bridge.describeWithdrawal` (or `sdk.waitForWithdrawalCompletion`) for withdrawal-identifier `index: 0` and `index: 1`.
3. Because `findMatchingWithdrawal` (`packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts:418-427`) matches purely on `nep141:${near_token_id} === assetId`, both calls resolve to whichever matching withdrawal record appears first in the POA API's `withdrawals` array — observable directly from the existing test at `poa-bridge.test.ts:1054-1111`, which shows a `describeWithdrawal({ index: 0, assetId: "nep141:btc.omft.near" })` call correctly returning the BTC-matching record purely because the *other* array element has a *different* asset (`eth.omft.near`). Replacing that second record's `defuse_asset_identifier`/`near_token_id` with the same `btc.omft.near` value (as would occur in a real same-token batch withdrawal) causes `.find()` to always return the first element regardless of which `index`/`destinationAddress` was actually requested, demonstrating the misreport.

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

	withdrawals: types.WithdrawalStatusResponseOk["result"]["withdrawals"],
	criteria: WithdrawalCriteria,

	| types.WithdrawalStatusResponseOk["result"]["withdrawals"][number]
	| undefined {

		(w) => `nep141:${w.data.near_token_id}` === criteria.assetId,
	);
