### Title
Unprivileged clients can hijack/DoS Web API trigger responses by front-running `MessageID` before the legitimate request in the Gateway's WebAPI capability handler - (File: `core/services/gateway/handlers/capabilities/handler.go`)

### Summary
The Gateway's `webapicapabilities.handler` (WebAPI trigger legacy path) stores a callback for a pending user request keyed only by the client-supplied `MessageID`, with no uniqueness check before insertion. Unlike sibling handlers in the same codebase (HTTP trigger v2, Vault, ConfidentialRelay), which explicitly reject a request whose ID is already in flight, this legacy handler silently overwrites any existing entry for the same key, exactly mirroring the reported `AccountManager.createAccount` bug class: a colliding, attacker-chosen unique identifier can hijack or block processing intended for another caller.

### Finding Description
`HandleLegacyUserMessage` inserts into `h.savedCallbacks` unconditionally: [1](#0-0) 

There is no check like `if _, found := h.savedCallbacks[msg.Body.MessageID]; found { return error }` before the map write, so a second, unrelated request carrying the same `MessageID` simply replaces the first entry.

`msg.Body.MessageID` is entirely attacker-controlled (an arbitrary string bounded only by length) and validated only for length/format, not uniqueness: [2](#0-1) 

This handler is reachable directly from an unauthenticated/unprivileged HTTP client through the Gateway's public entry point, `ProcessRequest`, which routes “legacy” (DonID-bearing) JSON-RPC requests straight to `HandleLegacyUserMessage`: [3](#0-2) 

When a node later responds to a given `MessageID`, `handleWebAPITriggerMessage` looks up and deletes the entry, then delivers the response to whichever callback occupies that slot at the time — the *last* writer wins, not the original caller: [4](#0-3) 

Contrast this with the other trigger/request handlers in the same repository, which treat ID collision as an error condition rather than silently overwriting state — e.g. the HTTP trigger v2 handler: [5](#0-4) 

and the Vault gateway handler: [6](#0-5) 

The absence of the same guard in the legacy WebAPI trigger `handler` is the root cause: it is a genuine control gap, not an intentional design choice, since the pattern used elsewhere in the codebase for the identical problem is “reject on collision.”

### Impact Explanation
An unprivileged, unauthenticated actor able to reach the Gateway's public JSON-RPC endpoint can:
1. Observe or guess a victim's `MessageID` (e.g., if IDs are predictable, reused by a client library, or leaked in logs/telemetry), and
2. Submit their own signed request using that same `MessageID` before the victim's request completes.

This causes the victim's `savedCallback` entry to be overwritten. When the DON eventually responds for that `MessageID`, the response is delivered to the attacker's callback instead of the victim's, and the victim's original HTTP request will simply time out (Gateway `callback.Wait(ctx)` returns a timeout error) — a griefing/DoS condition identical in mechanism to the reported `createAccount` front-running bug, and additionally a cross-user response-confusion risk if the attacker's callback can observe response content routed to it. This matches the "griefing" and "cross-user response confusion" impact categories.

### Likelihood Explanation
Likelihood depends on how `MessageID` values are generated by legitimate clients (random/UUID vs. predictable/sequential) and on request timing (attacker must land their colliding request in the window before the legitimate response arrives). If callers use non-random or otherwise guessable IDs (or the ID is derived from a workflow/trigger event that is externally observable), exploitation is straightforward and requires no privileges, no signature forgery of the victim (the attacker signs their own message), and no financial cost beyond a normal Gateway request.

### Recommendation
Add a uniqueness check in `HandleLegacyUserMessage` before inserting into `h.savedCallbacks`, mirroring the pattern already used in `httpTriggerHandler.setupCallback` and `vault handler.newActiveRequest`: if an entry for `msg.Body.MessageID` already exists (and is not expired/processed), reject the new request with an explicit error/response instead of silently overwriting the existing callback.

### Proof of Concept
1. Legitimate client sends a signed legacy request with `MessageID = "X"` to the Gateway; `HandleLegacyUserMessage` stores `savedCallbacks["X"] = victimCallback` and forwards to DON nodes [7](#0-6) .
2. Before a DON node responds, an attacker (any unprivileged party who can sign a message with their own key) sends another legacy request also using `MessageID = "X"`. This call again reaches `HandleLegacyUserMessage`, which overwrites `savedCallbacks["X"] = attackerCallback` with no collision check.
3. When a node subsequently emits a `MethodWebAPITrigger` response tagged with `MessageID = "X"`, `handleWebAPITriggerMessage` looks up `savedCallbacks["X"]`, finds `attackerCallback`, deletes the entry, and delivers the response to the attacker [8](#0-7) .
4. The victim's original HTTP call to the Gateway times out waiting on `callback.Wait(ctx)` in `ProcessRequest`, never receiving a response [9](#0-8) .

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageID]
	delete(h.savedCallbacks, msg.Body.MessageID)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response

		codec := api.JSONRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}
