### Title
Boundary-condition inconsistency between EVM `HandlerV2` and Substrate `pallet-ismp` core in challenge-period enforcement allows messages to be delivered/timed-out one full block early on EVM hosts - (File: evm/src/core/HandlerV2.sol)

### Summary
The same "challenge period must elapse before a state commitment can be trusted" rule is implemented with two different boundary conditions across the two ISMP handler implementations in this codebase, mirroring the class of bug in the reference report (documented/expected wait period does not match the code's actual enforced wait). On EVM, `delay == challengePeriod` is treated as elapsed; on the Rust/Substrate core, the equivalent check requires `delay > challengePeriod` strictly, i.e. it needs strictly more time than the configured period to be considered elapsed.

### Finding Description
`HandlerV2.handlePostRequests`, `handleGetResponses`, `handlePostRequestTimeouts`, and `handleGetRequestTimeouts` all guard on: [1](#0-0) 
```
uint256 delay = timestamp - host.stateMachineCommitmentUpdateTime(request.proof.height);
uint256 challengePeriod = host.challengePeriod();
if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();
```
This only reverts when `challengePeriod > delay`, meaning `delay == challengePeriod` is accepted as "elapsed" — i.e. a relayer may deliver a request/response/timeout the instant `delay` reaches exactly `challengePeriod`.

The equivalent Substrate-side function `verify_delay_passed`, used by `validate_state_machine` (invoked from the ISMP core `handle`/`handle_timeouts` paths reachable by any relayer submitting a signed or unsigned message) implements the check as: [2](#0-1) 
```
pub fn verify_delay_passed<H>(host: &H, proof_height: &StateMachineHeight) -> Result<bool, Error>
...
	Ok(delay_period.as_secs() == 0 || current_timestamp.saturating_sub(update_time) > delay_period)
```
Here `delay == delay_period` returns `false` (not yet elapsed) — the code requires strictly more than the configured challenge period.

The documentation describes the challenge period uniformly as "a configurable value for how long to wait for state commitments to be challenged, before they can be used to verify incoming requests/responses" and frames it as a single protocol-wide invariant relied upon by fishermen and relayers across all connected chains: [3](#0-2) [4](#0-3) 

There is no documentation anywhere distinguishing an EVM-inclusive vs Substrate-exclusive boundary; the SDK's own off-chain waiter (`waitForChallengePeriod`/`wait_for_challenge_period`) also treats `timeElapsed > challengePeriod` as the condition to stop waiting, matching the *stricter* (Substrate) semantics, not the EVM handler's laxer one: [5](#0-4) [6](#0-5) 

Because a relayer interacts directly with the on-chain `HandlerV2` contract (not the off-chain SDK helper), the on-chain enforcement is the one that actually gates message delivery on EVM hosts, and it is looser by exactly one boundary unit (`delay == challengePeriod`) than what the fisherman-facing documentation and Substrate implementation guarantee.

### Impact Explanation
The challenge period exists specifically to give fishermen a full window to detect and veto a fraudulent `StateCommitment` before it is used to deliver messages or trigger timeouts (see the fisherman veto flow, `pallet-fishermen::veto_state_commitment`, which deletes a still-challengeable commitment). Allowing delivery at `delay == challengePeriod` instead of `delay > challengePeriod` shrinks the guaranteed observation window on EVM destinations by exactly the polling/propagation slack fishermen and off-chain watchers assume is available up to (and including) the boundary instant, since the off-chain waiter code (`wait_for_challenge_period`) is written to the strict inequality and could still be "in flight" evaluating validity when an EVM relayer is already permitted to deliver. In the worst case this allows a forged/byzantine state commitment's messages (POST requests, GET responses, or fabricated timeouts) to be accepted for processing on an EVM destination fractionally before the network-wide invariant considered safe elsewhere in the same protocol is actually satisfied, which is the same class of impact described in the source report: an on-chain enforced wait that is inconsistent with the documented/expected wait, undermining trust in the security guarantee the delay is meant to provide. This affects `handlePostRequests`, `handleGetResponses`, `handlePostRequestTimeouts`, and `handleGetRequestTimeouts` — i.e. every unprivileged relayer-driven message-delivery and timeout path on EVM hosts.

### Likelihood Explanation
Likelihood is low-to-moderate: exploiting the one-unit boundary requires a relayer to time submission to land in the exact block where `delay` first equals `challengePeriod`, and the practical window of exposure is a single block versus a fully strict `>` window — not a large gap. It is a genuine, provably reachable inconsistency (any relayer can trigger it simply by submitting at the right block), but the marginal reduction in effective challenge time is small compared to a scenario where healing/challenge windows differ by whole rounds/days as in the original report.

### Recommendation
Make the EVM `HandlerV2` boundary check consistent with the Substrate core (`verify_delay_passed`) and the documented invariant by requiring strictly more than the configured challenge period, i.e. change:
```solidity
if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();
```
to:
```solidity
if (challengePeriod != 0 && challengePeriod >= delay) revert ChallengePeriodNotElapsed();
```
in `handlePostRequests`, `handleGetResponses`, `handlePostRequestTimeouts`, and `handleGetRequestTimeouts`, and add a cross-implementation regression test asserting identical behavior at `delay == challengePeriod` for both the EVM and Substrate code paths.

### Proof of Concept
1. A consensus update sets `stateMachineCommitmentUpdateTime(height) = T0` on an EVM host with `challengePeriod = P`.
2. A relayer submits `handlePostRequests` (or any of the other three guarded handlers) at `block.timestamp = T0 + P` exactly.
3. `delay = P`; the check `challengePeriod > delay` evaluates `P > P == false`, so the call is **not** reverted and the message is dispatched.
4. On the equivalent Substrate path (`pallet-ismp::handle`/`handle_unsigned` → `validate_state_machine` → `verify_delay_passed`), the identical scenario (`current_timestamp.saturating_sub(update_time) == delay_period`) evaluates `delay_period > delay_period == false` for the `>` comparison, so `verify_delay_passed` returns `false` and the message is rejected with `ChallengePeriodNotElapsed`.
5. Same protocol-level state (delay exactly equal to configured challenge period) yields different accept/reject outcomes depending on destination chain type, confirming the inconsistency is present and directly reachable from an unprivileged relayer's message submission.
