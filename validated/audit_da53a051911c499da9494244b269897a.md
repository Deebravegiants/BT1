## Title
Webhook request `shop` (and `topic`/`webhook_id`) are trusted from unauthenticated HTTP headers while the HMAC only signs the raw body, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature exclusively over the raw request body, but `Registry.process` uses the unsigned `shop-domain` (and `topic`/`webhook-id`) headers to route and attribute the payload to a tenant. Because the webhook HMAC secret is the app's single `client_secret` (shared across every shop that installs the app, not shop-specific), an attacker who legitimately receives even one valid webhook delivery for their own shop can replay that exact `(body, hmac)` pair to the app's webhook endpoint while forging the `x-shopify-shop-domain` header to name a different, victim shop. The signature still validates because the shop value is never part of the signed content.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate_signature` computes the HMAC purely from `to_signable_string`, i.e., the raw body, using the app's `Context.api_secret_key` (or `old_api_secret_key`): [2](#0-1) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` — all pulled straight from HTTP headers with no cryptographic binding — to construct the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

`Request#shop`, `#topic`, and `#webhook_id` are simple header reads with no relation to the signed bytes: [4](#0-3) 

The equality that should hold — *shop bound by HMAC == shop acted upon by the handler* — is broken:
- **Signed side:** `hmac == HMAC(client_secret, raw_body)` — no `shop` in the signed material.
- **Acted-upon side:** `WebhookMetadata.shop == headers["x-shopify-shop-domain"]` (or `shopify-shop-domain`), fully attacker-controlled.

Since the webhook secret (`client_secret`) is identical for every merchant shop that installs the same app (it is not per-shop), any unprivileged user who operates their own store with the app installed can capture one genuine `(body, hmac)` pair from their own webhook deliveries (webhook endpoints are public HTTP endpoints exposed by the host app, and the attacker fully controls their own shop's webhook traffic/inspection). They can then re-POST that same body+hmac to the app's public webhook endpoint with the `shop-domain` header rewritten to a victim shop domain. The signature check in `HmacValidator.validate` still passes because it never inspected the shop header, and `Registry.process` will hand the (attacker-supplied) shop identity plus the (attacker's own) webhook body to the app's handler as if it originated from the victim shop.

### Impact Explanation
This crosses a tenant boundary: an app that uses `WebhookMetadata#shop` from the gem's own webhook processing pipeline to key/update per-shop data (a normal and expected usage pattern, since that field exists specifically for that purpose) can be tricked into writing or acting on another merchant's tenant record using attacker-supplied webhook content. This is a cross-tenant integrity issue rooted entirely in the gem's own `Webhooks::Request`/`Registry` design — the shop identity is never authenticated, only the byte content is.

### Likelihood Explanation
Exploitation requires no special privilege beyond being a normal merchant with the target app installed on any shop (to obtain one valid `(body, hmac)` sample from their own legitimate webhook traffic) and knowledge of the target shop's domain (public information, e.g., `victim-shop.myshopify.com`). No access token, `api_secret_key`, or credentials of the app are needed — the HMAC validation succeeds using only publicly-observable byte content the attacker already legitimately received.

### Recommendation
Include `shop`, `topic`, and `webhook_id` (or equivalently, all values consumed by the handler) inside the HMAC-signed material, or otherwise cryptographically bind them to the signature, so that `HmacValidator.validate` fails whenever these header-derived fields do not match what was actually signed by Shopify.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and receives a legitimate webhook POST with body `B` and header `x-shopify-hmac-sha256: H` (valid because `H == HMAC(client_secret, B)`).
2. Attacker replays a POST to the app's webhook endpoint with the same body `B`, the same `x-shopify-hmac-sha256: H` header, but `x-shopify-shop-domain: victim.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(client_secret, B)` — still equal to `H` — so validation succeeds [5](#0-4) .
4. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed_body, ...)` and processes attacker-controlled content attributed to the victim shop [6](#0-5) .
