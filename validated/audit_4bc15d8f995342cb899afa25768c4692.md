Confirmed: `Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop`, `topic`, `webhook_id`, and `api_version` are all read from unauthenticated HTTP headers [2](#0-1) . `Registry.process` validates only the body HMAC and then forwards the header-derived `shop` value straight into the handler's data [3](#0-2) . Since Shopify signs webhook bodies with a single app-wide `client_secret` shared across every merchant that installs the app, this signature does not bind `shop` to the body it's attached to.

### Title
Webhook `shop` identity is not covered by HMAC, allowing cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw request body. The `shop` (and `topic`/`webhook_id`) values that `Registry.process` passes to the app's webhook handler come from HTTP headers that are entirely outside the HMAC's coverage.

### Finding Description
`Utils::HmacValidator.validate` computes `HMAC-SHA256(api_secret_key, verifiable_query.to_signable_string)` and compares it against the `hmac` field [4](#0-3) . For webhooks, `to_signable_string` is defined as just `@raw_body` [1](#0-0) . The `shop` attribute read by `Registry.process` and delivered to the handler comes from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which plays no role whatsoever in the signature computation [5](#0-4) .

Because the app's `client_secret` (and hence the HMAC key) is identical for every merchant that has installed the app, any party who has legitimately installed the app on their own store (or otherwise obtains one valid `(raw_body, hmac)` pair for a given topic) can replay that exact body/HMAC pair to the app's public webhook endpoint while substituting an arbitrary `shop-domain` header. `Registry.process` verifies the HMAC (which passes, since body and secret are unchanged) and then attributes the body to the attacker-chosen shop: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))` [6](#0-5) . This breaks the intended identity binding `hmac ⟺ (shop, body)`; the gem only enforces `hmac ⟺ body`.

### Impact Explanation
An attacker who has (or can obtain, e.g. by installing the target app themselves) one valid signed webhook payload can forge webhook events attributed to a victim shop they do not control. Depending on how the host application's handler trusts `data.shop` (e.g. `shop/redact`, `customers/redact`, `app/uninstalled`, or order/product topics used to trigger data mutation or session/token cleanup for that shop), this can lead to cross-tenant data manipulation — the host application takes shop-scoped action against a shop the attacker never installed the app on, using only content the attacker controls (their own webhook body) mapped onto an arbitrary victim `shop` identity.

### Likelihood Explanation
Requires the attacker to have legitimately installed the vulnerable app somewhere (to obtain a validly-signed body/HMAC pair for a chosen topic) and knowledge/guessing of the victim's `myshopify.com` domain (commonly public/guessable). No possession of the `client_secret`, access token, or victim credentials is required — only replay of headers, which any unprivileged internet user delivering HTTP requests to the app's public webhook callback endpoint can do.

### Recommendation
Include `shop` (and ideally `topic`/`webhook_id`) in the signable string, or otherwise cryptographically bind the shop identity to the signed payload before trusting `request.shop` in `Registry.process`/`WebhookMetadata`. At minimum, document (and enforce in the gem) that consuming applications must independently verify `request.shop` against a known/installed shop record before acting on webhook data, since the current design lets the header value ride unauthenticated alongside an otherwise-valid HMAC.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and configures a webhook for a topic of interest (e.g. `app/uninstalled` or `orders/create`).
2. Shopify delivers a webhook to the app: body `B`, header `shopify-shop-domain: attacker-shop.myshopify.com`, header `shopify-hmac-sha256: H` where `H = HMAC-SHA256(client_secret, B)`.
3. Attacker captures `(B, H)` and replays an HTTP POST to the same webhook endpoint, keeping body `B` and header `shopify-hmac-sha256: H` unchanged, but sets `shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC-SHA256(client_secret, B)` — this equals `H`, so validation succeeds [7](#0-6) .
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and body `B`, even though `victim-shop` never sent this webhook and the app is not necessarily installed there [6](#0-5) .
