### Title
`cookie_session_id` trusts the raw `shopify_app_session` cookie as an authenticated session-store key, and the offline session id it is seeded with is deterministically guessable (`"offline_#{shop}"`) - ([File: lib/shopify_api/utils/session_utils.rb])

### Summary
`ShopifyAPI::Utils::SessionUtils.cookie_session_id` returns `cookies[SessionCookie::SESSION_COOKIE_NAME]` verbatim, with no MAC, signature, or comparison to any value authenticated under `Context.api_secret_key`. For non-embedded / offline installs, the value that is ever placed in that cookie (`Auth::Oauth.validate_auth_callback`, `session.id`) is not random — it is the fully deterministic string `"offline_#{shop}"`, computed in `Auth::Session.from`. Any attacker who knows a shop's domain (public information) can construct this exact cookie value and use it as the session-store lookup key against the host app, without ever touching `api_secret_key`, the real merchant's browser, or any signed artifact.

### Finding Description
The invariant this breaks: `cookie_session_id_returned == f(bytes authenticated by Context.api_secret_key)`. In reality:
`cookie_session_id_returned == cookies["shopify_app_session"]` with zero verification — [1](#0-0) 

Trace:
1. During `Auth::Oauth.validate_auth_callback`, after a real merchant completes OAuth, the server sets `SessionCookie.new(value: session.id, ...)` for non-embedded apps: [2](#0-1) 
2. `session.id` for an offline (non per-user) token is computed with no randomness at all — `id = "offline_#{shop}"`: [3](#0-2) 
3. On every subsequent request, `SessionUtils.current_session_id` falls back to the cookie for non-embedded apps (or embedded apps without a JWT) and hands the raw cookie value straight to `cookie_session_id`, which returns it unchanged as the lookup key that a host app's session storage will use to fetch the full `Session` (including `access_token`): [4](#0-3) 

No step between (1)/(2) and (3) ever re-derives or re-verifies the cookie against anything computed with `api_secret_key`. `HmacValidator.validate` and the `state == auth_query.state` check in `validate_auth_callback` only run once, during the callback itself; they never gate subsequent ordinary requests that reach `current_session_id`/`cookie_session_id`. `JwtPayload`'s `aud`/`iss` checks are irrelevant here because they only apply to the JWT branch, which is bypassed entirely once `cookie_session_id` is reached.

Because the offline session id is a pure function of the public `shop` value, an attacker never needs to observe the victim's cookie. They can compute `"offline_#{victim-shop}"` themselves and send it as a raw `Cookie` header (or equivalent, e.g. `Authorization`-adjacent header depending on host wiring) directly to any endpoint of the target app that resolves the session via `SessionUtils.current_session_id`/`cookie_session_id`, as documented for non-embedded/offline apps. If that shop has ever completed real OAuth (i.e., its session is present in the host's session storage, which is exactly the documented flow), the attacker's forged cookie resolves to that shop's stored `Session`, including its `access_token`.

### Impact Explanation
An attacker who merely knows (or enumerates) a target shop's domain can, for any non-embedded/offline-token app built on this gem, fabricate the session-store lookup key without needing to see any cookie, header, or secret belonging to the victim. This yields cross-tenant access to another merchant's session object (and, transitively, wherever the host app exposes it, the merchant's access token), which is repeatable against any shop that has installed the app — a Critical, cross-tenant authentication bypass. The blast radius is every offline, non-embedded app instance built on this gem's documented cookie-session fallback.

### Likelihood Explanation
Preconditions: the app is configured non-embedded (or embedded without JWT, which the gem itself falls back to cookies for), uses offline tokens, and the host's session storage keys sessions purely by `session.id` as documented — this is the gem's own documented pattern, not a host misconfiguration. Attacker cost is a single guess of `"offline_#{shop}"` — no brute force needed since shop domains are public/known (e.g., leaked via app listings, webhooks, or the attacker's own test-shop naming convention for enumeration). This is trivially repeatable against every shop that has installed the target app.

### Recommendation
Never use a value derivable purely from public data (`shop`) as a bearer-equivalent cookie value. Bind the cookie to an unguessable, per-installation secret (e.g. a `SecureRandom` token stored server-side alongside the session, separate from the storage lookup key), and verify that opaque token — not the storage key itself — on every request in `cookie_session_id`/`current_session_id` before treating the cookie as authoritative.

### Proof of Concept
```ruby
# test/utils/session_utils_test.rb (new test)
def test_offline_session_id_is_deterministic_and_unauthenticated
  shop = "victim-shop.myshopify.com"

  # 1. The value ever placed in the session cookie for offline installs
  #    is fully deterministic from public data - no secret involved.
  access_token_response = ShopifyAPI::Auth::Oauth::AccessTokenResponse.from_hash(
    "access_token" => "shpat_real_token",
  )
  session = ShopifyAPI::Auth::Session.from(shop: shop, access_token_response: access_token_response)
  assert_equal("offline_#{shop}", session.id)

  # 2. cookie_session_id performs no cryptographic check whatsoever -
  #    it is a bare hash lookup.
  ShopifyAPI::Utils::HmacValidator.expects(:validate).never
  JWT.expects(:decode).never

  forged_cookies = { ShopifyAPI::Auth::Oauth::SessionCookie::SESSION_COOKIE_NAME => "offline_#{shop}" }
  looked_up_id = ShopifyAPI::Utils::SessionUtils.cookie_session_id(forged_cookies)

  # 3. The attacker-guessed value is returned unchanged and equals the
  #    real session id that was set on the legitimate merchant's cookie -
  #    with zero binding to api_secret_key.
  assert_equal(session.id, looked_up_id)
end
```
This demonstrates both halves of the broken equality: (a) `session.id` for offline sessions is derivable from public data alone, and (b) `cookie_session_id` accepts and returns that value as the trusted lookup key with no `HmacValidator`, `JWT`, or nonce check anywhere in the call path.
