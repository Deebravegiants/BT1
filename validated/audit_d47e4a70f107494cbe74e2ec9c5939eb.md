### Title
Unbounded router calldata + persistent `approveUnlimited` lets an attacker convert stranded/residual input-token balance into their own swap output - ([File: contracts/external-actions/swaps/ExternalActionSwap.sol], [File: contracts/external-actions/swaps/LifiExternalAction.sol])

### Summary
`ExternalActionSwap.swap` derives `inputAmount` from `-deltaAmounts[0]` but never enforces that the router actually consumes only that amount of `inputToken`; `LifiExternalAction.callRouter` grants the router an unlimited, never-revoked allowance via `approveUnlimited` and then executes attacker-supplied `externalActionMetadata` verbatim, measuring success only by the output-token balance delta. Because the allowance persists across transactions and the amount actually pulled is dictated purely by the attacker-chosen calldata, any input-token balance already sitting in the action (dust, stranded funds from a prior failed/partial op, or funds parked by a prior Emporium operation) can be swept into the swap and its resulting output credited entirely to the attacker as their own UTXO.

### Finding Description
The invariant that should hold is:
```
tokens leaving the action to the caller in tx T == -deltaAmountChanges Hinkal sent into the action for tx T
```

In `swap()`:
```solidity
address inputToken = circomData.erc20TokenAddresses[0];
uint256 inputAmount = uint256(-deltaAmounts[0]);
...
uint256 swappedAmount = callRouter(inputToken, inputAmount, outputToken, circomData.externalActionData.externalActionMetadata);
``` [1](#0-0) 

`inputAmount` is computed but, for ERC20 inputs, is never actually used to bound what the router pulls. `LifiExternalAction.callRouter`:
```solidity
uint256 balanceBefore = getERC20OrETHBalance(outputToken);
if (inputToken == address(0)) {
    (bool success, ) = router.call{value: inputAmount}(externalActionMetadata);
    require(success, "LI.FI swap failed: native coin");
} else {
    approveUnlimited(inputToken, router);
    (bool success, ) = router.call(externalActionMetadata);
    require(success, "LI.FI swap failed: erc-20 token");
}
swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore;
``` [2](#0-1) 

For the ERC20 branch, `inputAmount` is not passed into the actual token-pull path at all - `router.call(externalActionMetadata)` executes arbitrary attacker-supplied bytes against the LI.FI router. Because `approveUnlimited` sets (and never resets to a bounded/zero value after use) an unlimited allowance for `router` over `inputToken`, and this allowance is set every time `callRouter` runs and persists between transactions, the router is free to `transferFrom` any balance of `inputToken` the action contract holds - not just the amount corresponding to the current `-deltaAmounts[0]`. If the action contract holds any residual `inputToken` (e.g., leftover from a prior Emporium operation that parked funds in the action, dust from rounding in a previous swap, or a stranded/refunded amount), the attacker can craft `externalActionMetadata` so the router pulls that residual too, producing extra `outputToken`. Since `swappedAmount` is measured purely as the output-token balance delta with no corresponding check that input consumption matched `inputAmount`, this extra output is folded into `amountToSendToHinkal` and handed to the attacker's own UTXO:
```solidity
utxoSet[0] = UTXO({ amount: amountToSendToHinkal, erc20Address: outputToken, stealthAddressStructure: circomData.stealthAddressStructure, ... });
``` [3](#0-2) 

None of Hinkal's circuit-side guarantees (`inTotal + amountChanges === outTotal`) constrain the semantics of `externalActionMetadata`'s on-chain effect; they only constrain the values Hinkal itself accounts (`deltaAmountChanges`), while the actual router consumption of the action's on-chain token balance is entirely decoupled and attacker-controlled once the unlimited allowance exists. `dimensionsCheck`, `verifyProof`, and `onlyAllowedRecipient` verify that the caller is an allowed recipient and that the declared amounts are internally consistent, but they do not verify that the router only spent `inputAmount` of `inputToken`, so the divergence is not prevented.

### Impact Explanation
An attacker who is any registered relay/allowed-recipient action caller (per the exploit's "unprivileged attacker" definition acting via their own deposit/transact) can construct `externalActionMetadata` to direct the LI.FI router to consume more of `inputToken` than `-deltaAmounts[0]` states, drawing on residual/stranded balance in the action contract and walking away with the corresponding extra `outputToken` value as their own shielded UTXO. This is direct theft of protocol/user funds parked in the action beyond what Hinkal sent for that transaction, matching the **Critical: direct theft of shielded or in-flight user funds** category, and is repeatable every time residual balance exists (e.g., after any prior partial/failed operation, or a small deliberately-triggered leftover) and the allowance is live.

### Likelihood Explanation
Preconditions: the action contract must hold some non-zero balance of `inputToken` beyond what is expected for the current transaction (achievable by seeding a small "leftover" through a normal deposit/prior operation, or exploiting rounding/fee residue), and the `router` allowance for that token must be non-zero (set automatically by every prior ERC20 swap through `approveUnlimited`, and never revoked). Attacker cost is a single crafted `externalActionMetadata` calldata blob routed through the already-integrated LI.FI diamond, well within reach of any unprivileged actor who can call `Hinkal.transact` with their own proof. This is realistically and repeatably exploitable, not merely theoretical.

### Recommendation
- Enforce that the router only consumes exactly `inputAmount` of `inputToken`: measure and require `balanceBefore(inputToken) - balanceAfter(inputToken) == inputAmount` (or transfer input via `safeTransferFrom`/exact-amount approval instead of `approveUnlimited`).
- Replace persistent unlimited approvals with per-call, exact-amount approvals that are reset to zero after the router call completes (approve exactly `inputAmount`, then set back to 0).
- Alternatively, use a pull-based pattern where the action contract itself calls `transferFrom`/holds custody and only forwards the router the exact `inputAmount`, so router-controlled calldata cannot reach beyond the intended balance.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `LifiExternalAction`, a mock LI.FI router, and a mock ERC20 `inputToken`/`outputToken`.
2. Seed a "residual" balance: send extra `inputToken` directly to the `LifiExternalAction` contract (simulating stranded/leftover funds from a prior Emporium op or failed swap), outside of any `deltaAmountChanges` accounting.
3. Perform one legitimate transaction that triggers `callRouter` for `inputToken`→ anything, so `approveUnlimited(inputToken, router)` is set and persists.
4. Craft a second transaction with a small `deltaAmounts[0]` (e.g., `-1`) but with `externalActionMetadata` calldata for the mock router that calls `transferFrom(action, router, largeResidualAmount)` and returns a proportionally larger `outputToken` amount.
5. Assert: `swappedAmount` computed in `callRouter` (and thus `amountToSendToHinkal`/`utxoSet[0].amount`) is greater than what corresponds to `-deltaAmounts[0]`, i.e., assert `utxoSet[0].amount > f(-deltaAmounts[0])` while `inputToken.balanceOf(action)` drops by more than `inputAmount`, proving the attacker captured the residual balance as their own UTXO — violating `tokens leaving action == -deltaAmountChanges Hinkal sent`.

    function callRouter(
        address inputToken,
        uint256 inputAmount,
        address outputToken,
        bytes calldata externalActionMetadata
    ) internal override returns (uint256 swappedAmount) {
        uint256 balanceBefore = getERC20OrETHBalance(outputToken);

        if (inputToken == address(0)) {
            (bool success, ) = router.call{value: inputAmount}(
                externalActionMetadata
            );
            require(success, "LI.FI swap failed: native coin");
        } else {
            approveUnlimited(inputToken, router);
            (bool success, ) = router.call(externalActionMetadata);
            require(success, "LI.FI swap failed: erc-20 token");
        }

        swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore;
    }
