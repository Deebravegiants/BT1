## Title
Webhook tenant identity (`shop-domain`, `topic`, `webhook-id`) is not covered by HMAC signature, allowing cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [1](#0-0) , while `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from unauthenticated HTTP headers [2](#0-1) . `Registry.process` validates the HMAC over that same raw body only, then dispatches the handler using the unauthenticated `request.shop`/`request.topic` values [3](#0-2) .

### Finding Description
The gem's HMAC validation guarantees `HMAC(secret, body) == received_hmac` [4](#0-3) , but does not bind that signature to the `shop-domain`, `topic`, or `webhook-id` headers, since `VerifiableQuery#to_signable_string` for webhook requests is simply `@raw_body` [1](#0-0) .

The broken identity binding is:
`shop_used_for_tenant_dispatch (WebhookMetadata.shop, from header)` ≠ `shop_covered_by_signature (none — signature only covers body bytes)`

All shops that install a given Shopify app share the same `client_secret`/`api_secret_key`, and therefore the same HMAC key used to sign every shop's webhooks. A malicious merchant who installs the app on their own store can trigger a real webhook delivery (e.g. `orders/create`) to obtain a legitimately-signed `(body, hmac)` pair. Because the signature never covers the `shop-domain`, `topic`, or `webhook-id` headers, that same `(body, hmac)` pair remains valid when replayed to the app's webhook endpoint with those headers rewritten to name a different (victim) shop, a different topic, or a different webhook id. `Registry.process` only checks `Utils::HmacValidator.validate(request)` (i.e., body integrity) before building `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` and invoking the app's handler [3](#0-2) , so the handler receives attacker-chosen `shop` and `topic` values that were never authenticated.

### Impact Explanation
This allows an unprivileged internet user (any merchant who can install the app) to inject forged, cross-tenant webhook events into any other shop's data pipeline within the same app — e.g., causing the host application to process attacker-supplied payloads (order data, customer data, `shop/redact`, etc.) as if they belong to a victim shop. This is a cross-tenant access vulnerability originating from the gem's own signing scope, matching the Critical "cross-tenant access" category.

### Likelihood Explanation
Any installed merchant of a multi-tenant app can obtain a valid `(body, hmac)` pair from their own store's real webhook traffic without any special privilege, then replay it with forged headers against the shared webhook endpoint. No access token, `client_secret`, or privileged account is required — only that the attacker also be an installed merchant of the same app, which is the normal unprivileged path for any Shopify app.

### Recommendation
Include the tenant-identifying fields (`shop-domain`, `topic`, `webhook-id`) in the HMAC-covered signable content, or otherwise cryptographically bind them to the signed body (e.g. verify them against a value independently obtained via the Admin API rather than trusting the header), so that a signature valid for one shop/topic/body combination cannot be replayed for another.

### Proof of Concept
1. App installs on attacker's own shop `attacker.myshopify.com`; attacker triggers an `orders/create` event, capturing the raw JSON body `B` and its valid `X-Shopify-Hmac-Sha256` header `H` (both are simply `body`/`HMAC(secret, body)`, per `lib/shopify_api/webhooks/request.rb` and `lib/shopify_api/utils/hmac_validator.rb`).
2. Attacker POSTs `B` with header `H` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com` (and optionally a different `X-Shopify-Topic`).
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only re-computes `HMAC(secret, B)` and matches `H` — validation succeeds [5](#0-4) .
4. The registered handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed_body, ...)`, causing the host app to process attacker data as belonging to the victim shop [6](#0-5) .
