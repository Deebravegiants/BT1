### Title
Webhook shop-domain header is trusted for tenant identity without being covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, so the HMAC that `Registry.process` verifies covers the body bytes only. The `shop` value, read from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, is never part of the signed data. `Registry.process` nonetheless passes this unauthenticated `shop` value straight into `WebhookMetadata` and on to the host app's webhook handler as the tenant identifier.

### Finding Description
- `Request#hmac` decodes the `hmac-sha256` header and `Request#to_signable_string` returns `@raw_body` only: [4](#0-3) .
- `Request#shop` simply reads the `shop-domain` header with no cryptographic binding to the HMAC: [3](#0-2) .
- `Registry.process` validates only `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `to_signable_string` (the body) and compares against the header HMAC: [5](#0-4) . It then forwards `request.shop` unchanged into the handler-facing `WebhookMetadata`: [1](#0-0) .

The binding that should hold is: `hmac == HMAC(secret, shop || body)`, i.e. the `shop` identity should be cryptographically bound to the same signature that authenticates the payload. Instead the actual binding enforced is `hmac == HMAC(secret, body)`, with `shop` taken verbatim from an unauthenticated header. Since the request body content and headers (including `shop-domain`) are both attacker-controllable transport-level values from the caller's perspective before verification, an attacker who can produce (or replay/reuse) a validly-signed body for topic X from shop A can resend it with an arbitrary `shop-domain` header value B, and the handler will process it believing it originated from shop B — a cross-tenant identity confusion.

### Impact Explanation
This breaks the tenant boundary this gem is expected to enforce for webhook consumers: any application whose webhook handler branches on `WebhookMetadata#shop` (e.g., to look up the tenant's stored session/access token, or to segregate per-merchant data) can be made to act on attacker-influenced shop attribution while still passing "HMAC valid," since the `shop` field carries no cryptographic guarantee. This matches "cross-tenant access" impact criteria, because the identity used to select/attribute a tenant is not the identity actually verified.

### Likelihood Explanation
Exploitation requires the attacker to already possess one validly HMAC-signed webhook body for some topic (e.g., by having previously received a genuine webhook for their own shop, since anyone can install/configure a Shopify webhook to their own endpoint and thus legitimately obtain a signed payload for their own tenant), and then to resend that same body to the victim application's webhook endpoint with a different `shop-domain` header. Because the header is not covered by the signature, the gem's own verification step (`HmacValidator.validate`) offers no protection against this header substitution. Likelihood depends on how the host application uses `WebhookMetadata#shop` (many use it as a lookup key for stored per-shop tokens/sessions), which is normal usage of this gem's documented API surface.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the value that is HMAC-verified, or otherwise cryptographically tie the shop-domain header to the signed payload before trusting it as tenant identity — e.g., include it in `to_signable_string`, or require the application to independently confirm that the derived shop matches a session/tenant already authenticated by other means (such as matching against the session that registered the webhook) rather than trusting the header value alone downstream.

### Proof of Concept
1. App A configures a webhook subscription and receives (or captures) a legitimate webhook POST with body `B` for shop `shop-a.myshopify.com`, with header `shopify-hmac-sha256: H`, where `H = HMAC(secret, B)`.
2. Attacker resends the same body `B` and the same header `shopify-hmac-sha256: H` to the victim's webhook endpoint, but replaces `shopify-shop-domain: shop-a.myshopify.com` with `shopify-shop-domain: shop-b.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` and finds it matches `H` — validation passes because only the body is signed: [6](#0-5) .
4. `request.shop` returns `"shop-b.myshopify.com"` from the header, and this value is passed to the handler as authenticated tenant context: [7](#0-6) .
5. The host handler processes shop A's data/event as if it belongs to shop B, despite the shop attribution never having been verified.
