### Title
Truncating division in `convert_to_balance` mints/refunds zero tokens for dust-sized cross-chain transfers - ([File: modules/pallets/hyper-fungible-token/src/impls.rs])

### Summary
`pallet-hyper-fungible-token`'s `convert_to_balance` performs integer division to rescale an incoming ERC20-denominated amount down to the local asset's decimal precision. When `erc_decimals > local_decimals` and the message amount is smaller than `10^(erc_decimals - local_decimals)`, the division truncates to zero, exactly mirroring the reported StHEU bug class ("Zero HEU Payouts Due to Rounding"): a caller who legitimately burned/escrowed real value on the source chain receives nothing on the destination.

### Finding Description
`convert_to_balance` computes:
```
dec_str = (value / 10^(erc_decimals - local_decimals)).to_string()
``` [1](#0-0) 

This is invoked in `on_accept` to convert the ABI-decoded `message.amount` (from the EVM `HyperFungibleToken`/`WrappedHyperFungibleToken` contract) into the local balance that is then minted or transferred to the beneficiary: [2](#0-1) 

It is also used identically in `on_timeout` to compute the refund amount for the original sender when a dispatched message times out: [3](#0-2) 

The EVM side already burned the sender's tokens before dispatching (`HyperFungibleTokenUpgradeable.send`: `_burn(msg.sender, params.amount)`), so the value is irrevocably destroyed on the source chain regardless of what the destination pallet computes: [4](#0-3) 

There is no minimum-amount check anywhere in `on_accept`/`on_timeout`/`convert_to_balance` — if the resulting `amount` is `0`, the code proceeds to call `mint_into`/`transfer` with `0` and still emits `TokenReceived`/`TokenRefunded` and, on `on_accept`, still executes any attached calldata. The BRIDGE token's own documentation confirms the pallet routinely scales by `10^6` between 12-decimal nexus BRIDGE and 18-decimal EVM BRIDGE, so any per-(asset, chain) precision gap of this magnitude is a first-class, expected configuration, not an edge case: [5](#0-4) 

For example, with `erc_decimals = 18` and `local_decimals = 12` (the documented BRIDGE configuration), any inbound ERC20 amount below `10^6` wei (a dust amount, e.g. `999999`) truncates to `0` local units. The same applies to the analogous EVM-side `_normalizeAmount` scaling pattern seen elsewhere in the intents subsystem, and to any asset registered with a coarser local decimal count than its EVM counterpart via `register_token`.

The scaling function `convert_to_erc20` used on the outbound `send()` path is the inverse (multiplication), so it never truncates in that direction — the asymmetry means outbound sends are always exact, but inbound receipts/refunds of dust amounts silently disappear.

### Impact Explanation
This is a direct, permanent loss of user funds reachable by any unprivileged party who dispatches a cross-chain HFT transfer:
- On the happy path (`on_accept`), a user who sends a small enough amount (relative to `erc_decimals - local_decimals`) burns real tokens on the EVM chain but the beneficiary receives zero tokens on the substrate chain — funds are permanently destroyed with no recovery path.
- On the timeout/refund path (`on_timeout`), the same truncation means a timed-out dispatch refunds `0` to the original sender instead of their escrowed/burned amount — a second independent path to permanent loss.
- Neither path reverts or blocks progress; the message is accepted, an event is emitted claiming an `amount` of the (already-truncated) value, and calldata attached to a zero-value transfer still executes, so downstream integrations relying on a non-zero credited amount could also misbehave.

This matches the "Medium" severity class of the reported analog: not a systemic drain, but a concrete, deterministic fund-loss bug triggerable by any user (or forced upon them via a relayer timing out their message), for dust-magnitude but real value, on any token pair configured with a decimal gap (the documented default for the native BRIDGE token).

### Likelihood Explanation
Likelihood is high for any token pair with `erc_decimals > local_decimals`, which is the documented, intentional configuration for the native BRIDGE token (18 EVM decimals vs. 12 nexus decimals, `10^6` scale factor) and is a supported, expected configuration for every `register_token` call (the pallet's `ErcDecimalsBelowLocal` error only guards the reverse case, i.e., it explicitly permits `erc_decimals >= local_decimals`, which is exactly the truncating direction). Any transfer amount under the scale factor — accidental (dust dispatch, fee-only messages, a UI rounding error) or the natural result of a timed-out small transfer — triggers this deterministically; no adversarial conditions beyond "small amount + configured decimal gap" are required.

### Recommendation
Reject (rather than silently truncate) conversions that would round to zero: have `convert_to_balance` return an error (e.g. `AmountBelowMinimumPrecision`) whenever `value > 0` but the scaled result is `0`, and propagate that error from both `on_accept` and `on_timeout` so the ISMP message is treated as failed rather than silently consuming the sender's already-burned/escrowed tokens for nothing. Alternatively, require `erc_decimals == local_decimals` for the mint/burn custody model or enforce a minimum transferable amount on the EVM `send()` side (`params.amount >= 10^(erc_decimals - local_decimals)`), so the truncation can never occur post-burn.

### Proof of Concept
1. Register a non-native asset via `register_token` with `native = false`, `local_decimals = 12` (e.g., matching `T::Decimals` for the BRIDGE-style native asset), and `erc_decimals = 18` for an EVM `HyperFungibleToken` deployment (this is the pallet's documented default configuration for BRIDGE, per `BridgeToken.sol`'s own comment).
2. On the EVM chain, call `send()` with `params.amount = 999999` (i.e., `< 10^6`, less than one local-unit's worth of ERC20 dust). `_burn(msg.sender, 999999)` executes, irrevocably destroying the sender's tokens, and a `Message{amount: 999999, ...}` POST request is dispatched. [4](#0-3) 
3. On delivery, `on_accept` decodes `message.amount = 999999` and calls `convert_to_balance(999999, 18, 12)` → `999999 / 10^6 = 0`. [6](#0-5) 
4. `mint_into(local_asset_id, &beneficiary, 0)` (or the native `transfer` variant) executes without error, `TokenReceived { amount: 0, ... }` is emitted, and the beneficiary receives nothing — while the source-chain sender's `999999` wei were already burned in step 2.
5. Equivalently, if the message instead times out, `on_timeout` computes the same `0` and refunds `0` to the original sender via the identical `convert_to_balance` call, permanently losing the burned amount a second way. [7](#0-6)

pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}
