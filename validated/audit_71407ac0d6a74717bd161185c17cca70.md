## Title
Passphrase cache TTL can be extended after it has already expired, resurrecting a secret that should have been irrevocably cleared - (File: `features/application/src/modules/passphrase-cache.ts`)

## Summary
`PassphraseCache.changeTtl()` extends the auto-lock TTL for the cached wallet passphrase without validating whether the cache has already crossed its own expiration boundary (`inactiveAt + ttl`). This mirrors the `name_service.move` `extend_expiration()` bug class: a renewal/extension entry point that fails to re-check the very expiry condition it is supposed to respect, allowing a stale/expired secret to be "resurrected" as valid.

## Finding Description
The passphrase cache stores `PASSPHRASE_KEY`, `ADDED_AT_KEY`, `INACTIVE_AT_KEY`, and `TTL_KEY`, and `get()` treats the passphrase as valid only while `inactiveAt + ttl > Date.now()`, clearing it otherwise: [1](#0-0) 

Physical purge of the cache is only guaranteed by an OS-level alarm scheduled in `#scheduleClear()`: [2](#0-1) 

`changeTtl()`, however, updates `TTL_KEY` to a new value and simply reschedules the clear alarm — it never checks whether the passphrase, under the *existing* `inactiveAt`/`ttl`, has already logically expired: [3](#0-2) 

Because `get()` recomputes validity using whatever `ttl` is currently stored, extending `ttl` retroactively makes an already-expired `inactiveAt + oldTtl` window appear valid again (`inactiveAt + newTtl > Date.now()`). This is exposed publicly through the application layer: [4](#0-3) 
and via the public API surface (`application.changeLockTimer`): [5](#0-4) 

The cached passphrase is used to silently re-unlock the wallet without prompting the user: [6](#0-5) 

This is structurally identical to the analog bug: `extend_expiration()` extended a resource's expiry without checking that the resource was already past its terminal window (`expiration_date + grace_period`). Here, `changeTtl()` extends the passphrase-cache's terminal window (`inactiveAt + ttl`) without checking it has already elapsed, and the OS `alarms` mechanism (the analog of the on-chain "someone else registers the domain") is not guaranteed to fire exactly at expiry — suspended/backgrounded apps and delayed OS timers create a real window where the passphrase remains in storage past its intended TTL but has not yet been wiped.

## Impact Explanation
If `changeLockTimer`/`changeTtl` is invoked during the window after the passphrase cache's `inactiveAt + ttl` has elapsed but before the `clear-passphrase` alarm has actually fired and wiped storage, the cache is resurrected as "still valid" for a new, longer TTL. A subsequent `#autoUnlock()` call will then decrypt/unlock the wallet using a passphrase that should have already been irrevocably purged, and treat this as a legitimate cache hit. This defeats the auto-lock security guarantee — the invariant that once the lock TTL elapses the plaintext passphrase must be gone and re-authentication required — and results in unauthorized wallet-unlock/secret persistence.

## Likelihood Explanation
Exploitation requires (1) a delay between logical expiry (`inactiveAt + ttl`) and the alarm's actual firing — realistic on mobile/extension platforms where background timers/alarms can be deferred while the app/extension is suspended — and (2) an in-window call to `changeLockTimer`/`changeTtl`, which is reachable through the public `applicationApi`. This is a race/timing-dependent condition rather than a straightforward one-shot exploit, but it is a genuine root-cause defect: `changeTtl()` performs no validation against the already-recorded `inactiveAt`/current `ttl` before extending, exactly analogous to the confirmed `extend_expiration()` finding.

## Recommendation
In `changeTtl()`, before applying the new TTL, re-validate the current expiry state the same way `get()` does (i.e., if `inactiveAt` is set and `inactiveAt + currentTtl <= Date.now()`, treat the cache as already expired: clear it immediately instead of rescheduling/extending). This mirrors the recommended fix for `extend_expiration()` — validate the expiry condition at the moment of extension, not only at read time.

## Proof of Concept
1. Wallet is locked; `scheduleClear()` sets `inactiveAt = T0` and schedules an OS alarm to clear the cache after `ttl` minutes. [7](#0-6) 
2. The app/extension is suspended (background/idle discard) so the OS alarm callback is delayed and does not fire exactly at `T0 + ttl`.
3. At time `T1 > T0 + ttl` (logically expired, but storage not yet wiped), the application layer calls `changeLockTimer({ ttl: newTtl })`, which forwards to `changeTtl(newTtl)`: [8](#0-7) 
4. `changeTtl()` sets `TTL_KEY = newTtl` and reschedules the clear alarm, without checking that `inactiveAt + ttl` (old ttl) had already elapsed.
5. A subsequent `get()` call computes `inactiveAt + newTtl > Date.now()` → true, returning the passphrase as "in activity period" even though it should have already been purged. [9](#0-8) 
6. `#autoUnlock()` uses this resurrected passphrase to unlock the wallet without any user re-authentication. [10](#0-9)

  async changeTtl(ttl: number) {
    const newTtl = Math.min(this.#maxTtl, ttl)

    await this.#autoLockTimerAtom.set(newTtl)

    const passphrase = await this.#storage.get(PASSPHRASE_KEY)

    if (passphrase) {
      await this.#storage.set(TTL_KEY, newTtl)

      void this.#scheduleClear()
    }
  }
