### Title
Unrestricted `superApprove` in `HyperFungibleTokenImpl` allows anyone to grant themselves unlimited spending allowance over any holder's tokens - ([File: evm/src/utils/HyperFungibleTokenImpl.sol])

### Summary
`HyperFungibleTokenImpl.superApprove(owner, spender)` is a `public` function with no access-control modifier that directly calls the internal `_approve(owner, spender, type(uint256).max)` on an arbitrary `owner` address. Since this contract is deployed and minted through `TokenFaucet`/`DeployIsmp.s.sol` as a real ERC20 used in the protocol's testnet/faucet flow, any unprivileged caller can invoke `superApprove(victim, attacker)` to grant an unlimited ERC20 allowance from any token holder to any spender, then call standard `transferFrom` to drain that holder's balance — the same missing-access-control root cause as the LaunchZone `swapXImpl` incident, where an unauthenticated function ultimately let the attacker spend tokens via an existing/forced approval.

### Finding Description
`HyperFungibleTokenImpl` is a role-gated ERC20 (`MINTER_ROLE`/`BURNER_ROLE` via `AccessControlEnumerable`) intended to restrict minting and burning to trusted gateway roles. [1](#0-0) 

However, it also exposes:
```solidity
function superApprove(address owner, address spender) public {
    _approve(owner, spender, type(uint256).max);
}
``` [2](#0-1) 

This function is `public`, carries no `onlyRole`, `onlyOwner`, or `msg.sender == owner` check, and directly calls OpenZeppelin's internal `_approve` with the caller-supplied `owner` address, rather than `msg.sender`. This mirrors the LaunchZone root cause: an externally reachable function that manipulates token allowance/authorization state for an arbitrary account without verifying the caller is that account or otherwise privileged, letting an attacker set up unauthorized withdrawal rights over someone else's balance and then complete the theft via the standard ERC20 `transferFrom` path — exactly the "approve now, sweep later" pattern LaunchZone's unverified `swapXImpl` implementation enabled.

The token is not test-only scaffolding: it is deployed and wired into the live faucet/deploy flow, reachable by any address holding or interacting with the token. [3](#0-2) [4](#0-3) 

### Impact Explanation
Any address can call `superApprove(victim, attacker)` for any `HyperFungibleTokenImpl`-based token, then call `transferFrom(victim, attacker, victim.balanceOf(victim))` on the standard ERC20 interface to drain the full balance of any holder of that token — including the faucet contract itself and any user who received minted tokens. This is a direct, unbacked-authorization / theft-of-funds vulnerability reachable from a single unprivileged transaction, matching the required impact bar (concrete theft of funds via forged authorization).

### Likelihood Explanation
Trivial and always exploitable: `superApprove` has no gating logic whatsoever, requires no proof, signature, or role, and can be called by any EOA or contract against any token holder at any time the token is deployed. The only precondition is that the target `HyperFungibleTokenImpl` token exists and has token balances worth draining (which the `TokenFaucet` and `DeployIsmp.s.sol` deployment guarantee).

### Recommendation
Remove `superApprove` from production code, or at minimum restrict it to `msg.sender == owner` (self-service approve helper) or gate it behind `onlyRole(DEFAULT_ADMIN_ROLE)`/an explicit test-only flag that is compiled out of any deployed bytecode. Given the docstring itself labels it "Helper function for tests," it should not exist in a contract that is instantiated through `DeployIsmp.s.sol` and used by `TokenFaucet` in a live environment.

### Proof of Concept
```solidity
// Attacker contract/EOA, no special role required
HyperFungibleTokenImpl token = HyperFungibleTokenImpl(TOKEN_ADDRESS);

// 1. Grant unlimited allowance from victim to attacker (no auth check bypassed)
token.superApprove(victim, address(this));

// 2. Drain victim's balance using the now-unlimited allowance
uint256 stolen = token.balanceOf(victim);
token.transferFrom(victim, address(this), stolen);
```
This requires no consensus proof, no relayer/handler interaction, and no privileged key — a single call chain analogous to the LaunchZone exploit's unauthenticated call into `swapXImpl` that ultimately spent the deployer's existing token approval.
