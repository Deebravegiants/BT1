### Title
OAuth authorization-code callback sends `client_secret` to a `shop` host that is never validated against Shopify's trusted domains, unlike every sibling grant flow - (`lib/shopify_api/auth/oauth.rb`)

### Summary
Every other grant flow in this gem (`client_credentials.rb`, `refresh_token.rb`, `token_exchange.rb#migrate_to_expiring_token`) runs the caller-influenced `shop` value through `Utils::ShopValidator.sanitize!` before building the URL that carries the app's `client_secret`. `ShopifyAPI::Auth::Oauth.validate_auth_callback` in `lib/shopify_api/auth/oauth.rb` does not: `auth_query.shop` is passed straight into `auth_base_uri(shop)` at [1](#0-0)  which builds `"https://#{shop}/admin"`, and the POST containing `client_id`/`client_secret`/`code` is sent there at [2](#0-1) .

### Finding Description
`validate_auth_callback` only checks that `auth_query.shop` was part of an HMAC-covered string (`Utils::HmacValidator.validate(auth_query)` at [3](#0-2) ) and that the CSRF `state` matches the cookie. It never checks the resulting host string against `ShopValidator::TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev` — [4](#0-3) ), unlike `client_credentials.rb` ( [5](#0-4) ), `refresh_token.rb` ( [6](#0-5) ), and `token_exchange.rb#migrate_to_expiring_token` ( [7](#0-6) ), which all call `Utils::ShopValidator.sanitize!(shop)` before constructing the same kind of `HttpClient`/`shop_session` that receives the `client_secret`.

The relevant identity binding that should hold is: `host that receives client_secret` == `a host in ShopValidator::TRUSTED_SHOPIFY_DOMAINS`. In `oauth.rb` this equality is never checked; only "host is bit-for-bit whatever byte string was HMAC-signed" is checked. Those are not the same guarantee — the gem's own `ShopValidator` module exists specifically because "HMAC-valid" and "trusted Shopify domain" are different properties (see its dedicated adversarial test cases for confusable/attacker-controlled domains at [8](#0-7) ).

### Impact Explanation
If `auth_query.shop` could ever be a non-`myshopify.com` string that still HMAC-validates (e.g., because a host application forwards other query parameters into `AuthQuery`, or a future change to the HMAC scheme/signable string weakens the coupling between `code` and `shop`), the app's `client_id`/`client_secret`/authorization `code` would be POSTed to an attacker-chosen host at `auth_base_uri(shop)`, directly exfiltrating the `client_secret` and, since `code` is exchanged there instead of at Shopify, the resulting access token as well. This is exactly the class of "field acted on but not covered/consistently checked" bug the sibling flows were hardened against by introducing `ShopValidator`, while `oauth.rb`'s authorization-code path was left out of that hardening. This maps to Critical (theft/exfiltration of the app's `client_secret` and access tokens) per the impact criteria.

### Likelihood Explanation
Today the only defense is the HMAC over `code/host/shop/state/timestamp` — since forging that requires the `client_secret`, this is not independently exploitable by an unprivileged internet user in the current code path. The likelihood is therefore low as a standalone exploit today, but it is a structural regression relative to the gem's own established pattern: three of four comparable "exchange this for an access token at `https://{shop}/admin/oauth/access_token`" call sites enforce `ShopValidator.sanitize!` and one (the historically oldest, authorization-code grant) does not. Any relaxation of HMAC coverage, any caller path that constructs `AuthQuery` from partially-trusted input, or a downstream `HmacValidator` bug reactivates this into a directly exploitable SSRF-with-credentials.

### Recommendation
Call `Utils::ShopValidator.sanitize!(auth_query.shop)` (or equivalent) inside `ShopifyAPI::Auth::Oauth.validate_auth_callback` before using the shop to build `auth_base_uri` and before constructing `null_session`, mirroring `client_credentials.rb`, `refresh_token.rb`, and `token_exchange.rb#migrate_to_expiring_token`, so the host that ultimately receives `client_secret` is always independently constrained to `ShopValidator::TRUSTED_SHOPIFY_DOMAINS` regardless of what the HMAC check does or doesn't enforce.

### Proof of Concept
Not independently reproducible today without possession of `api_secret_key` (needed to forge a valid `hmac` for an `AuthQuery` with a malicious `shop`), because `Utils::HmacValidator.validate` at [9](#0-8)  currently gates every field in `AuthQuery#to_signable_string` ( [10](#0-9) ), including `shop`. The concrete, verifiable artifact is the code-path asymmetry itself: `oauth.rb`'s `auth_base_uri`/`validate_auth_callback` ( [11](#0-10) ) has no `ShopValidator` call, while the three sibling flows do, confirmed by `grep` showing `ShopValidator`/`sanitize!` referenced only in `token_exchange.rb`, `client_credentials.rb`, `refresh_token.rb`, and `graphql/storefront.rb` — never in `oauth.rb`.

        def validate_auth_callback(cookies:, auth_query:)
          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state

          null_session = Auth::Session.new(shop: auth_query.shop)
          body = {
            client_id: Context.api_key,
            client_secret: Context.api_secret_key,
            code: auth_query.code,
            expiring: Context.expiring_offline_access_tokens ? 1 : 0, # Only applicable for offline tokens
          }

          client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
          response = begin
            client.request(
              Clients::HttpRequest.new(
                http_method: :post,
                path: "access_token",
                body: body,
                body_type: "application/json",
              ),
            )
          rescue ShopifyAPI::Errors::HttpResponseError => e
            raise Errors::RequestAccessTokenError,
              "Cannot complete OAuth process. Received a #{e.code} error while requesting access token."
          end

          session_params = T.cast(response.body, T::Hash[String, T.untyped]).to_h
          session = Session.from(shop: auth_query.shop,
            access_token_response: Oauth::AccessTokenResponse.from_hash(session_params))

          cookie = if Context.embedded?
            SessionCookie.new(
              value: "",
              expires: Time.now,
            )
          else
            SessionCookie.new(
              value: session.id,
              expires: session.expires ? session.expires : nil,
            )
          end

          { session: session, cookie: cookie }
        end

        private

        sig { params(shop: String).returns(String) }
        def auth_base_uri(shop)
          return "https://#{shop}/admin" unless defined?(DevServer) && shop.include?(".my.shop.dev")

          # For first-party apps in development only, we leverage DevServer to build the admin base URI
          admin_web = T.unsafe(Object.const_get("DevServer")) # rubocop:disable Sorbet/ConstantsFromStrings
            .new("admin-web")
          admin_host = admin_web.host!(nonstandard_host_prefix: "admin")
          shop_name = shop.split(".").first

          "https://#{admin_host}/store/#{shop_name}"
        end
