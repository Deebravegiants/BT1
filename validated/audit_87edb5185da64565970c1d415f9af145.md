### Title
Error propagation from `orb.run(self)` in `Plan::perform_overcapture` skips re-enable of eye-liveness agents and leaves FPS overrides at `INFINITY` - ([File: src/plans/biometric_capture/overcapture.rs])

### Summary
`Plan::perform_overcapture` disables `ir_net`, `ir_auto_focus`, `mirror`, `eye_tracker`, and `eye_pid_controller` and sets `ir_eye_save_fps_override`/`ir_face_save_fps_override`/`thermal_save_fps_override` to `Some(f32::INFINITY)` before calling `orb.run(self).await?`. If that call returns an `Err` (e.g., an MCU I/O fault), the `?` operator returns immediately, skipping the corresponding re-enable calls and override resets at lines 172-180. This leaves the `Orb` broker state degraded going forward.

### Finding Description
In `src/plans/biometric_capture/overcapture.rs`, `perform_overcapture` (lines 156-183) disables several agents and sets three FPS override fields to `Some(f32::INFINITY)` (lines 160-168), then calls `orb.run(self).await?` (line 170). There is no `Result`-independent cleanup (no `finally`/RAII guard/`match` with cleanup-on-error) — the re-enable block at lines 172-180 executes only on the `Ok` path. If `orb.run` returns `Err` (propagated from any agent/MCU I/O error during that run), the function returns `Err` immediately, and the disabled/overridden state persists on the shared `&mut Orb` instance.

That `Err` further propagates up through `Plan::run`'s `while !self.extension_finished(orb).await?` loop (line 146, via `?`) and out of `Plan::run` itself (line 136), and ultimately out of the calling `biometric_capture` plan chain. `Orb` is a long-lived broker structure reused across signup attempts, so whichever caller (top-level signup loop) catches this error and restarts a new signup session would inherit an `Orb` whose eye_tracker, eye_pid_controller, mirror, and ir_net remain disabled and whose FPS overrides remain "infinite" unless the top-level orchestration explicitly re-initializes/reset the whole `Orb` state on every new signup attempt. ### Impact Explanation
If confirmed that no outer reset routine restores these specific fields/agent states before the next signup attempt begins, this would degrade liveness/sharpness gating (`eye_tracker`, `eye_pid_controller`, `ir_net`-driven checks) for a subsequent signup, potentially allowing a presentation or degraded-signal capture to bypass qualification enforcement — a liveness/fraud-bypass class impact.

### Likelihood Explanation
I was unable to fully verify, within the available tool budget, whether the top-level caller of `biometric_capture`/`overcapture::Plan::run` (i.e., wherever the signup loop constructs a new `biometric_capture::Plan` and calls `run_pre`) reconstructs a fresh `Orb` per attempt, or reuses the same `Orb` and calls `enable_*`/clears these override fields in an error/retry path. `run_pre` (`src/plans/biometric_capture/mod.rs`) and the `Orb` struct's field definitions (`src/brokers/orb.rs`) were located but not read in enough depth to confirm or rule out such a reset. This is a material unknown for validity of the claim: if `run_pre` or the outer orchestration unconditionally re-enables ir_net/eye_tracker/eye_pid_controller/mirror and clears the three fps-override fields at the start of every biometric_capture attempt (as a defensive measure independent of overcapture), the described "stuck" state would be transient and fully remediated before the next user's capture begins, neutralizing the impact.

### Recommendation
Given the unresolved question of whether `run_pre` (or another reset path) already restores this state, the concrete, low-risk fix is still worthwhile: wrap the disable/enable block in `perform_overcapture` with an RAII guard (a struct with a `Drop` impl that performs the re-enable/override-reset regardless of `Ok`/`Err`), or explicitly re-enable/reset in a `match`/`if let Err` branch before propagating the error, so the invariant holds regardless of any assumptions about caller-side resets.

### Proof of Concept
Cannot be conclusively confirmed as exploitable without verifying `run_pre`'s reset behavior; the required PoC (integration test injecting a broker error mid-`perform_overcapture`, then asserting `orb.ir_eye_save_fps_override`/agent-enabled flags remain stuck across a subsequent `biometric_capture::Plan::run_pre` call) could not be fully validated against the actual `run_pre` implementation in this session, so I cannot assert with confidence that the invariant is actually violated end-to-end. This should be marked as needing further verification of `src/plans/biometric_capture/mod.rs::run_pre` and the top-level signup retry orchestration before treating it as a confirmed vulnerability.

    async fn perform_overcapture(&mut self, orb: &mut Orb) -> Result<()> {
        tracing::info!("Overcapture extension: Beginning capture");
        self.state = State::Overcapturing { start_time: Instant::now() };

        orb.main_mcu.send(mcu::main::Input::FrameRate(CAPTURE_FPS)).await?;
        orb.disable_ir_net();
        orb.disable_ir_auto_focus();
        orb.disable_mirror();
        orb.disable_eye_tracker();
        orb.disable_eye_pid_controller();
        orb.ir_eye_save_fps_override = Some(f32::INFINITY);
        orb.ir_face_save_fps_override = Some(f32::INFINITY);
        orb.thermal_save_fps_override = Some(f32::INFINITY);

        orb.run(self).await?;

        orb.main_mcu.send(mcu::main::Input::FrameRate(IR_CAMERA_FRAME_RATE)).await?;
        orb.enable_ir_net().await?;
        orb.enable_ir_auto_focus()?;
        orb.enable_mirror()?;
        orb.enable_eye_tracker()?;
        orb.enable_eye_pid_controller()?;
        orb.ir_eye_save_fps_override = None;
        orb.ir_face_save_fps_override = None;
        orb.thermal_save_fps_override = None;

        Ok(())
    }
