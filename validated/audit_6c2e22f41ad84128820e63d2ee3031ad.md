### Title
Unscoped, unswept ERC20/Permit2 approvals granted via Emporium CASE-2 stateless ops let an attacker drain Emporium's entire pooled token balance - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
`EmporiumUpgradeable.runAction` executes arbitrary attacker/user-supplied calls as `msg.sender = Emporium` (CASE 2, `op.endpoint.call(op.callData)`), including calls like `IAllowanceTransfer.approve`/`ERC20.approve` on Emporium's behalf [1](#0-0) . When such an op is issued with `circomData.erc20TokenAddresses.length == 0` (the supported "Emporium-min" metadata-only flow), no balance/slippage checks apply at all, so the resulting allowance is created with zero accounting oversight [2](#0-1) . Because Emporium is a single shared contract whose balance can transiently hold tokens belonging to unrelated users' in-flight transacts, this standing allowance is never scoped to the depositor who created it and can later be exploited by the attacker's approved spender contract to pull tokens that belong to a different user's transact.

### Finding Description
Equality claimed broken: `permit2_allowance_grantor(emporium) == token_owner_authorized_by_victim_proof` — false, because the allowance sits on Emporium's shared balance, not on a balance scoped to the proof that created it.

Code path:
- `Hinkal._externalTransact` computes `deltaAmountChanges` purely from `circomData.erc20TokenAddresses`/`amountChanges` and forwards it, together with the untouched `circomData.externalActionData.externalActionMetadata`, to `IExternalActionV2(externalAddress).runAction` [3](#0-2) .
- `EmporiumUpgradeable.runAction` decodes an `EmporiumStack` of `EmporiumOperation[]` from that metadata and, for CASE 2 ("Stateless Interaction"), performs `op.endpoint.call{value: op.value}(op.callData)` with `msg.sender == Emporium`, blocking only the `callHinkalWallet`/`doSendToRelay` selectors [4](#0-3) .
- The only accounting safety net is the per-token `balanceChange < 0` revert, but it is computed exclusively over `circomData.erc20TokenAddresses` for that call [5](#0-4) . If `circomData.erc20TokenAddresses` is empty (the `formInputEmporiumMin` path used when `externalActionId == HINKAL_EMPORIUM_ACTION_ID` and length 0), the loop never runs, so an `approve()`/Permit2 `approve()` call inside `op.callData` is completely unchecked and unaccounted for [2](#0-1) .
- `verifyWallet`'s EIP-712 signature check is only enforced when `stack.signerAddress != address(0)`; for `signerAddress == address(0)` it merely marks `emporiumMessage` as used, with no constraint tying `op.endpoint`/`op.callData` content to anything beyond the submitter's own valid proof of their own UTXOs [6](#0-5) .

Exploit flow: any user (attacker or a legitimately-behaving user following a documented "approve-then-interact" pattern) submits a transact with empty `erc20TokenAddresses` and a CASE-2 op `permit2.approve(tokenX, attackerSpenderContract, largeAmount, farExpiry)`. This creates `allowance[emporium][tokenX][attackerSpenderContract] = largeAmount` in the real Permit2 singleton with zero balance checks. Later, whenever Emporium transiently holds `tokenX` (e.g. mid another unrelated user's swap-style transact, where tokens are deposited to Emporium before `runAction`'s ops execute, per `_externalTransact` lines 247-256 [7](#0-6) ), `attackerSpenderContract` calls `permit2.transferFrom(emporium, attacker, amount, tokenX)`, since `msg.sender == attackerSpenderContract` is the approved spender in Permit2's own accounting, independent of whose transact currently has funds parked in Emporium. Existing guards (`performHinkalChecks`, `verifyProof`, the balance-diff loop in `Hinkal.transact`, `insertNullifiers`, `nonReentrant`) all validate the CALLER's own UTXO amounts/nullifiers — none of them constrain what a CASE-2 op is allowed to approve, nor sweep or revoke standing token allowances granted by Emporium.

### Impact Explanation
Direct theft of shielded/in-flight funds belonging to a different user than the one whose UTXOs the attacker's proof spends: an attacker-controlled spender contract can drain any amount of `tokenX` up to the granted allowance from Emporium's balance at any future moment that balance is non-zero, regardless of which user's transact put it there. This is repeatable per token/spender pair and does not require compromising any privileged role, matching the Critical category ("direct theft of shielded or in-flight user funds").

### Likelihood Explanation
Preconditions: (1) at least one transact routes a CASE-2 Emporium op that performs an ERC20/Permit2 `approve` to an attacker-controlled contract with `circomData.erc20TokenAddresses` empty (or otherwise not covering that token), which the current design explicitly supports via the `formInputEmporiumMin`/zero-length flow; (2) Emporium subsequently holds a non-zero balance of that token from any transact (deposits land on Emporium before ops run per `_externalTransact`). Attacker cost is limited to deploying `attackerSpenderContract` and constructing/submitting the approving transact for their own funds (no victim collusion required) or waiting for a naturally occurring "approve+interact" op pattern. Given Emporium is designed as a shared multi-tenant execution surface for arbitrary calls, this is practically feasible and repeatable across tokens/spenders.

### Recommendation
- Forbid or scope Emporium CASE-2 (and CASE-1) ops from setting durable token allowances (`approve`/`permit2.approve`/`increaseAllowance`) that are not immediately, fully consumed within the same `runAction` call; require any such allowance be reset to zero before `runAction` returns.
- Enforce that the balance-diff safety loop in `EmporiumUpgradeable.runAction` covers every token an op interacts with, not just `circomData.erc20TokenAddresses`, or reject `runAction` calls whose ops reference tokens outside that declared set.
- Disallow the empty-`erc20TokenAddresses` "metadata-only" Emporium flow from executing calls capable of approving token transfers.

### Proof of Concept
Foundry test plan:
1. Deploy real Permit2, a mock ERC20 `tokenX`, `Hinkal`, `EmporiumUpgradeable`, and an `AttackerSpender` contract exposing `pull(address owner, address to, uint160 amount, address token)` that calls `permit2.transferFrom(owner, to, amount, token)`.
2. Submit transact #1 with `circomData.erc20TokenAddresses = []`, Emporium CASE-2 op = `permit2.approve(tokenX, address(AttackerSpender), type(uint160).max, block.timestamp + 1e9)`. Assert it succeeds with no balance checks reverting, and assert `permit2.allowance(emporium, tokenX, attackerSpender)` is now non-zero.
3. Have an unrelated "victim" transact deposit `tokenX` into Emporium as part of a normal (e.g., deposit-then-swap) CASE-2 flow, and, before Emporium's internal sweep captures it, or via any window where Emporium's `tokenX` balance is transiently non-zero, call `AttackerSpender.pull(emporium, attacker, amount, tokenX)` directly (no Hinkal call needed).
4. Assert `tokenX.balanceOf(attacker)` increases by `amount` while `tokenX.balanceOf(emporium)` decreases correspondingly, proving funds not authorized by the attacker's own proof/nullifiers moved to the attacker — i.e. `amount_pulled_by_attacker == amount_belonging_to_other_user`, not to the attacker's own UTXOs.
