### Title
Min-circuit Emporium path (`erc20TokenAddresses=[]`) lets `runAction` execute arbitrary calls without any balance-conservation check, allowing theft of resident ETH/ERC20 balance on the Emporium contract - (`contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`EmporiumUpgradeable.runAction` gates its value-conservation logic (`balancesBefore`/`balancesAfter`, the `BalanceChangeShouldBePositive` revert, and `handleOut`) entirely on `circomData.erc20TokenAddresses.length`, but the operation-execution loop that performs `op.endpoint.call{value: op.value}(op.callData)` runs unconditionally regardless of that length. The protocol explicitly supports an `erc20TokenAddresses = []` "min circuit" path for `HINKAL_EMPORIUM_ACTION_ID` (`MainEVMCircuitMin` / `formInputEmporiumMin`), meaning any attacker who can produce a valid min-circuit proof for their own message can invoke arbitrary `op.endpoint.call` from the Emporium contract with zero on-chain accounting of what value leaves it.

### Finding Description
The invariant that should hold is: *for every token moved out of Emporium during `runAction`, that movement must be reflected in `balancesBefore`/`balancesAfter` (or in Hinkal's own `oldBalances`/`newBalances` loop in `Hinkal.transact`) so it is either returned to the caller as a UTXO or reverted*. This invariant is enforced only inside the `for (uint256 i = 0; i < circomData.erc20TokenAddresses.length; i++)` loops in both `EmporiumUpgradeable.runAction` ( [1](#0-0) ) and `Hinkal.transact` ( [2](#0-1) ).

However, the operations loop that performs the actual external calls is not gated by `erc20TokenAddresses.length` at all — it iterates `stack.ops` (decoded from attacker-controlled `externalActionData.externalActionMetadata`) and executes `op.endpoint.call{value: op.value}(op.callData)` unconditionally: [3](#0-2) .

The repo explicitly supports and builds proof inputs for the case `circomData.erc20TokenAddresses.length == 0` when `externalActionId == HINKAL_EMPORIUM_ACTION_ID`, routing to a trivial circuit (`MainEVMCircuitMin`, which only constrains a Poseidon hash of `messageSeed`) via `formInputEmporiumMin`: [4](#0-3)  and [5](#0-4) . This circuit imposes no meaningful semantic constraint on `stack.ops`, `endpoint`, `callData`, or `value` — it is only committed to via `calldataHash`, which the attacker (generating their own proof) fully controls.

When `erc20TokenAddresses = []`:
- `Hinkal._externalTransact`'s deltaAmountChanges loop is a no-op, so no funds are forwarded from Hinkal to Emporium ( [6](#0-5) ).
- `Hinkal.transact`'s outer balance-diff/slippage check loop is also skipped entirely ( [7](#0-6) ).
- Inside `EmporiumUpgradeable.runAction`, `balancesBefore`/`balancesAfter` are empty arrays, so the `BalanceChangeShouldBePositive` check and `handleOut` UTXO creation never execute.

`onlyAllowedRecipient` only checks `msg.sender == Hinkal` ( [8](#0-7) ), and Hinkal forwards `circomData` unconditionally to `runAction` ( [9](#0-8) ), so nothing constrains `op.endpoint`/`op.callData`/`op.value` to a token-tracked, balance-checked flow.

The net effect: the ops loop still executes `op.endpoint.call{value: op.value}(op.callData)` using Emporium's own resident ETH (Emporium has a `receive()` payable fallback, line 369) and/or ERC20 balance — with **no invariant enforcing that whatever leaves Emporium is accounted for**. Any ETH/ERC20 balance that legitimately or incidentally accumulates on the singleton Emporium contract (via `receive()`, router refunds, rounding/slippage residue from a prior tracked-token call, or an approval left standing from a prior op) is fully accessible to any attacker who can submit a min-circuit `transact` call, since `verifyWallet`'s optional signature check only applies when `stack.signerAddress != address(0)` — an attacker sets `signerAddress = address(0)` and directly calls arbitrary `op.endpoint.call` as the "Stateless Interaction" branch (lines 102-113), with no signature required at all.

### Impact Explanation
Critical: direct theft of any shielded/in-flight ETH or ERC20 balance resident on the Emporium singleton contract. This impacts every user of Emporium collectively, since the contract is shared, and the balance-conservation guard that is supposed to make every unit of value traceable to a UTXO is completely bypassed on the min-circuit path. The exploit is repeatable — an attacker can drain any balance sitting on Emporium at any time by submitting a new min-circuit call with a fresh `emporiumMessage`.

### Likelihood Explanation
Preconditions are low-cost and fully attacker-controlled: the attacker needs to (1) generate a valid proof for `MainEVMCircuitMin` (only requires knowing a `messageSeed` they choose themselves), (2) craft an `EmporiumStack` with `signerAddress = address(0)` and an arbitrary `EmporiumOperation` (attacker fully controls `endpoint`/`callData`/`value`), and (3) submit via `Hinkal.transact` with `erc20TokenAddresses = []`. No privileged role, no victim cooperation, and no reentrancy trick is required — the vulnerability is a direct, always-reachable code path whenever Emporium holds any balance.

### Recommendation
Do not allow the operations loop in `EmporiumUpgradeable.runAction` to execute when `circomData.erc20TokenAddresses.length == 0` unless the ops are provably value-neutral (e.g., disallow non-zero `op.value` and restrict `op.endpoint` to a signature-verified allowlist requiring `stack.signerAddress != address(0)`), or require the min-circuit path to still populate `erc20TokenAddresses` with every token/ETH type touched by `stack.ops` so the existing `balancesBefore`/`balancesAfter` conservation check applies uniformly regardless of circuit variant. At minimum, enforce `stack.signerAddress != address(0)` (i.e., require a valid EIP-712 signature) whenever `erc20TokenAddresses` is empty, so unauthenticated/stateless calls cannot move Emporium's resident balance.

### Proof of Concept
Hardhat fork test:
1. Deploy Hinkal + EmporiumUpgradeable, register `HINKAL_EMPORIUM_ACTION_ID`.
2. Fund Emporium with test ERC20 tokens/ETH directly (simulating residual balance from `receive()` or a prior tracked op that left dust — e.g., send 100 tokens to Emporium's address).
3. As an unprivileged attacker, construct `CircomData` with `erc20TokenAddresses = []`, `externalActionData.externalActionMetadata` encoding an `EmporiumStack` with `signerAddress = address(0)` and one `EmporiumOperation{ endpoint: token, invokeWallet: false, value: 0, callData: abi.encodeCall(token.transfer, (attacker, 100e18)) }`.
4. Generate a valid `MainEVMCircuitMin` proof for this `calldataHash`/`emporiumMessage`/`timeStamp`.
5. Call `Hinkal.transact(a,b,c,dimensions{tokenNumber:0,...}, circomData)`.
6. Assert: `token.balanceOf(attacker)` increases by 100e18 and `token.balanceOf(Emporium)` decreases by 100e18, while no UTXO/nullifier/commitment was created for this token and `Hinkal.transact`'s balance-diff loop never ran (`erc20TokenAddresses.length == 0`) — proving value left Emporium with zero on-chain accounting.
