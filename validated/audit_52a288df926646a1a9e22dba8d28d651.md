### Title
Case-insensitive Bitcoin/UTXO addresses bypass `compareAddresses` equality check used to block self-destination withdrawals - (File: packages/intents-sdk/src/lib/compareAddresses.ts)

### Summary
`validateAddress()` accepts a Bech32 Bitcoin address in an alternate valid case (e.g., all-uppercase `BC1Q...`) as the *same* address as its canonical lowercase form, per BIP-173. `compareAddresses()`, which every bridge calls to prevent a withdrawal from being sent to the token's own on-chain address, treats Bitcoin (and Litecoin/Dogecoin/BCH/Cardano) addresses with a strict `a === b` string comparison instead of normalizing case first.

### Finding Description
`OmniBridge.validateWithdrawal()`, `HotBridge.validateWithdrawal()`, and `DirectBridge.validateWithdrawal()` all call `compareAddresses(destTokenAddress, args.destinationAddress, assetInfo.blockchain)` and throw `DestinationAddressMatchesTokenAddressError` if they are equal, to stop tokens being withdrawn to their own bridge/contract address [4](#0-3) [5](#0-4) .

For Bitcoin-family chains, `compareAddresses` reaches the default branch that does `return a === b;` with zero normalization [2](#0-1) . Meanwhile `validateBtcAddress` → `validateBtcBech32Address` normalizes the human-readable prefix only for comparison but passes the raw string straight to `bech32.decode()`/`bech32m.decode()` [1](#0-0) , which per BIP-173 will happily decode an all-uppercase address to the identical witness program as its lowercase counterpart. So the SDK's own address-format validator considers `BC1QXXXXXXX...` and `bc1qxxxxxxx...` the same underlying destination, but the equality guard used to block dangerous destinations does not.

### Impact Explanation
If the token's on-chain (bridge custody) Bitcoin-family address is known/derivable and a caller supplies the same address in a different but still-valid case, `validateAddress()` accepts it as well-formed, and `compareAddresses()` fails to flag it as identical to the blocked address, letting the withdrawal proceed to what is effectively the token's own custody address. This can cause funds to be irrecoverably lost or stuck exactly in the class of "misdelivery / stuck funds" the check is designed to prevent, since the equality check that gates a Critical/High protection can be silently bypassed by a casing variant.

### Likelihood Explanation
Exploitability depends on the attacker/integrator being able to supply the destination address string directly (already the normal SDK usage pattern for `withdrawalParams.destinationAddress`) and on there being a legitimate blocked Bitcoin-family address to target (e.g., an Omni Bridge custody address for BTC). Since case variants of Bech32 addresses are rarely produced by wallets but are trivially constructed by an attacker, likelihood is moderate, gated on whether any bridge's "own address" for a UTXO chain is a Bech32 address reachable through this validation path.

### Recommendation
Normalize case (and any equivalent encodings) for Bitcoin, Litecoin, Dogecoin, Bitcoin Cash, Cardano and other UTXO-family branches in `compareAddresses()` before doing the equality check — mirroring the pattern already used for EVM (`getAddress`), Aptos/Sui/Starknet (`compareHexAddress`), TON (`compareTonAddress`) and Tron (`compareTronAddress`) — instead of falling back to raw `a === b`.

### Proof of Concept
```ts
import { compareAddresses } from "./compareAddresses";
import { validateAddress } from "./validateAddress";
import { Chains } from "./caip2";

const lower = "bc1qar0srrr7xfkvy5l643lydnw9re59gtzzwf5mdq";
const upper = lower.toUpperCase(); // BIP-173 valid representation of the same address

console.log(validateAddress(upper, Chains.Bitcoin)); // true — accepted as a valid destination
console.log(compareAddresses(lower, upper, Chains.Bitcoin)); // false — NOT flagged as the same address
```
If `lower` is the bridge's own custody address that `validateWithdrawal()` is meant to block, submitting `upper` as `destinationAddress` passes both the format check and the self-address equality check, routing funds to the blocked address.

Note: I could not fully verify whether any real bridge configuration currently uses a Bech32-formatted Bitcoin address as `assetInfo.address`/`destTokenAddress` (the "token's own address") reachable via this specific comparison path in production configs — this would need to be confirmed against the live Omni/Hot bridge asset configs to establish concrete exploitability rather than the confirmed logic bug in the comparison function itself.

function validateBtcBech32Address(address: string): boolean {
	let decoded: { prefix: string; words: number[] };
	let isBech32m = false;

	try {
		decoded = bech32.decode(address as `${string}1${string}`);
	} catch {
		try {
			decoded = bech32m.decode(address as `${string}1${string}`);
			isBech32m = true;
		} catch {
			return false;
		}
	}

	if (decoded.prefix.toLowerCase() !== "bc") return false;
