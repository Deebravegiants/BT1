### Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw request body only, while the `shop` (tenant identifier) is read from an unsigned HTTP header. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then dispatches the handler using `request.shop`, so a request whose body/HMAC pair is valid for one shop can be replayed with an attacker-modified shop-domain header to make the gem attribute the payload to a different shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

but the `shop` accessor used for tenant identification is derived purely from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of the signed data: [2](#0-1) 

`ShopifyAPI::Webhooks::Registry.process` validates only that the HMAC matches the body, then trusts `request.shop` to build the `WebhookMetadata` passed to the application's handler: [3](#0-2) 

The identity binding that should hold is: `shop header == shop that generated/authorized this signed body`. Because the HMAC only covers `@raw_body`, this equality is never checked — `HmacValidator.validate` only proves `hmac == HMAC(api_secret_key, raw_body)`, it says nothing about which shop the body came from.

**Before attack:** Shop A triggers a real event, Shopify sends a webhook to the app with body `B`, a valid `hmac = HMAC(secret, B)`, and header `shop-domain: shop-a.myshopify.com`.

**Attacker action:** An unprivileged user who controls Shop A (e.g., any merchant/tester able to trigger webhook-generating events, such as by installing the app on a shop they control) captures this legitimate webhook delivery (body + hmac), then replays the identical body and hmac to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with `shop-b.myshopify.com`.

**After attack:** `Registry.process` still validates successfully because `HmacValidator.validate` only checks `hmac` against `raw_body`, which is unchanged. `request.shop` now returns `"shop-b.myshopify.com"`, and `WebhookMetadata.new(shop: request.shop, body: request.parsed_body, ...)` is handed to the application's handler as if the payload belonged to Shop B — while the body content is actually Shop A's data.

### Impact Explanation
This breaks the tenant isolation the gem is expected to provide to consuming applications: a request that is cryptographically valid can be attributed to an arbitrary shop of the attacker's choosing simply by changing an unsigned header. Any application that uses `WebhookMetadata#shop` from this gem to scope data writes/lookups (as the documented usage pattern instructs) can be made to store or act on one merchant's data under another merchant's tenant identity — a cross-tenant access/confusion vulnerability.

### Likelihood Explanation
Likelihood is elevated because triggering a legitimately signed webhook body only requires being a merchant/user of any shop that has the app installed (a low-privilege actor from the perspective of the multi-tenant app), and replaying the captured body+HMAC with a forged shop header requires nothing beyond basic HTTP tooling — no access token, secret, or TLS interception is needed.

### Recommendation
Bind the shop identity into the value that is verified, not just the body. Options:
- Include the `shop-domain` header (and other headers such as `topic`, `webhook-id`) in `to_signable_string`, computing the signature the same way Shopify's servers do if that is verifiable, or
- Have `Registry.process`/`WebhookMetadata` cross-check `request.shop` against an out-of-band trusted value (e.g., the shop associated with the delivery endpoint or a previously stored webhook registration) before dispatching to handlers, rejecting mismatches.

### Proof of Concept
1. Shop A (attacker-controlled/unprivileged) triggers an event, causing the app to receive a webhook POST with body `B` and header `x-shopify-hmac-sha256: HMAC(secret, B)`, `x-shopify-shop-domain: shop-a.myshopify.com`.
2. Attacker replays: `POST /webhooks` with the identical body `B`, identical `x-shopify-hmac-sha256`, but header `x-shopify-shop-domain: shop-b.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `HMAC(secret, B) == hmac` — the shop header is irrelevant to this check (`lib/shopify_api/utils/hmac_validator.rb` lines 12-22, `lib/shopify_api/webhooks/request.rb` lines 35-38).
4. The handler receives `WebhookMetadata.new(shop: "shop-b.myshopify.com", body: parsed(B), ...)`, processing Shop A's data as if it belonged to Shop B.
