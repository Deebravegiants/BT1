### Title
Webhook shop-domain identity is not covered by the HMAC signature, allowing cross-tenant webhook impersonation - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, so the HMAC verification performed by `Utils::HmacValidator.validate` (invoked from `Webhooks::Registry.process`) authenticates the body content only. The `shop-domain` header — which is the value the host application actually acts on (dispatched to the handler as the webhook's tenant identity) — is never part of the signed material.

### Finding Description
`ShopifyAPI::Webhooks::Request` exposes `shop` by simply reading the `shopify-shop-domain` / `x-shopify-shop-domain` header: [1](#0-0) 

But the value it signs/verifies is only the raw body: [2](#0-1) 

`Registry.process` validates the HMAC and, if it passes, hands the (unauthenticated) `request.shop` straight to the app's webhook handler as the tenant identifier: [3](#0-2) 

`HmacValidator.validate_signature` computes the signature purely from `verifiable_query.to_signable_string` (i.e., the body) against the shared `Context.api_secret_key`: [4](#0-3) 

Since `api_secret_key` is one shared secret for the whole app (used for **every** installed shop/tenant), any shop that has legitimately installed the app receives real webhooks with a valid HMAC over the body from Shopify. Because the `shop-domain` header is excluded from the signed content, that shop's operator can capture one of their own genuine webhook deliveries (raw body + valid `x-shopify-hmac-sha256`) and resend it to the app's webhook endpoint with the `shop-domain` header swapped to any other victim shop's domain. `HmacValidator.validate` will still return `true` (it only re-computes the signature over the body), and `Registry.process` will invoke the handler with `WebhookMetadata` claiming to be the victim shop: [5](#0-4) 

The equality the code should enforce — "shop identity claimed in the header" == "shop identity cryptographically bound by the HMAC" — is broken: the header is trusted for tenant routing/lookup while the signature covers a different, narrower scope (body only).

### Impact Explanation
Downstream host applications almost universally use the webhook's `shop` value to look up per-tenant session/data (this is the documented purpose of `WebhookMetadata#shop`/`data.shop` shown in the gem's own tests and docs). An attacker who is a legitimate (even low-privilege, e.g., free-trial) installer of the app can forge webhook deliveries that the host application will process as belonging to a different merchant, since the gem asserts the HMAC is valid. This is a cross-tenant identity/data-integrity breach entirely mediated by this gem's `Webhooks::Request`/`Webhooks::Registry` validation logic — it does not require the attacker to know the victim's or the app's credentials, only to be an installed (or previously installed) tenant of the same app.

### Likelihood Explanation
Low-to-moderate: it requires the attacker to control at least one legitimate installation of the app (trivial for public apps) and to capture one real webhook delivery, which is inherent to normal operation (any topic works, since the signable string doesn't depend on topic/shop headers). No secret material or privileged access is needed beyond becoming an app user.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signed material, or otherwise cryptographically bind the header-derived `shop` to the verified payload before it's handed to `WebhookMetadata`/the handler. At minimum, `Webhooks::Request#to_signable_string` should not silently omit `shop-domain` from the value verified by `HmacValidator`.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com`; the attacker triggers any webhook topic they can influence (e.g., `products/create`), capturing the raw POST body `B` and the valid header `x-shopify-hmac-sha256: H` that Shopify computed with the app's shared `api_secret_key`.
2. Attacker resends the exact same body `B` and header `H` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and any other headers as desired).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`; since validation is computed only over `request.to_signable_string` (== `B`), it succeeds:
```ruby
# lib/shopify_api/webhooks/request.rb
def to_signable_string
  @raw_body
end
```
4. `handler.handle(data: WebhookMetadata.new(topic:, shop: request.shop, ...))` is invoked with `shop == "victim-shop.myshopify.com"`, even though the payload/HMAC never actually vouched for that shop — the host application processes the forged webhook as if it originated from the victim tenant.
