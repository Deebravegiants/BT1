### Title
POA Bridge withdrawal status/txHash misreport for batch withdrawals sharing the same `assetId` - (File: `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`, `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts`)

### Summary
`findMatchingWithdrawal()` in both the intents-sdk's `PoaBridge.describeWithdrawal()` and internal-utils' `waitForWithdrawalCompletion()` selects a withdrawal record solely by matching `assetId` (derived from `near_token_id`), never by index, destination address, or amount. When a single NEAR intent transaction contains two or more POA-bridge withdrawals of the *same* token (same `assetId`) but different destination addresses/amounts, both lookups collapse onto the *same* array entry, so the SDK reports the same status and `transfer_tx_hash` for every withdrawal that shares that `assetId`, regardless of which one actually landed on-chain.

### Finding Description
`createWithdrawalIdentifiers` (`packages/intents-sdk/src/core/withdrawal-watcher.ts:80-107`) builds one `WithdrawalIdentifier` per withdrawal param and tracks a per-route `index`, but for the POA route, `describeWithdrawal` never uses that `index` to disambiguate — it delegates entirely to `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`: [1](#0-0) 

`findMatchingWithdrawal` performs a first-match lookup keyed only on `assetId`: [2](#0-1) 

The exact same pattern exists in the internal-utils helper used for the same purpose (single-shot completion wait): [3](#0-2) 

Both functions' own doc comments acknowledge the limitation ("multiple withdrawals of the same token in a single transaction are not supported"), but the caller-facing behavior does not fail closed for this case — it silently returns whichever matching entry `Array.prototype.find` picks first, for every caller that queries with that `assetId`. This breaks the equality "status/hash reported == the on-chain outcome for *this specific* withdrawal": if withdrawal #0 (to address X) has settled COMPLETED with `transfer_tx_hash = 0xAAA`, and withdrawal #1 (to address Y, same token) is still PENDING or uses a different `transfer_tx_hash`, `describeWithdrawal`/`waitForWithdrawalCompletion` called for withdrawal #1 will still return `{status: "completed", txHash: "0xAAA"}` — the hash and completion status of a transfer that went to a different address entirely.

This is consumed by `createWithdrawalCompletionPromises`/`watchWithdrawal` (`packages/intents-sdk/src/core/withdrawal-watcher.ts:20-77`), which resolves each per-withdrawal promise based on this misreported status: [4](#0-3) 

An integrator awaiting withdrawal #1's completion promise would see it resolve with `hash: "0xAAA"` — the transaction hash of withdrawal #0's transfer to a *different destination address* — and could mark withdrawal #1 as settled/credited based on that misattributed hash.

### Impact Explanation
This satisfies the High-impact category "a status or hash misreport making an integrator credit or refund twice": an integrator relying on `describeWithdrawal`/`waitForWithdrawalCompletion` per-withdrawal result could believe a withdrawal to destination Y has completed (with a specific on-chain tx hash) when in reality that hash/status belongs to a different withdrawal to destination X. This can cause premature crediting, incorrect reconciliation, or double-crediting logic downstream, without any wrongdoing by the destination-address owner — triggered simply by batching two same-token withdrawals with different destinations in one intent, which the SDK's public batch-withdrawal API (`createWithdrawalCompletionPromises`) explicitly supports per withdrawal-params array.

### Likelihood Explanation
Likelihood is constrained to the case where a caller batches ≥2 withdrawals of the identical `assetId` via the POA bridge route within one intent transaction (e.g. two different recipients redeeming the same token). The SDK's batch API accepts arbitrary `withdrawalParams[]` without rejecting duplicate assetIds for the POA route, and the code comments confirm this is a known, unhandled case rather than a validated/rejected one — so it is reachable through normal (non-malicious) usage of the public batch-withdrawal API, not requiring any privileged or adversarial actor.

### Recommendation
- Reject (fail-fast) at `createWithdrawalIntents`/`validateWithdrawal` time (or in `createWithdrawalIdentifiers`) any batch that contains multiple POA-bridge withdrawals sharing the same `assetId`, until the POA API/SDK support disambiguating them.
- Alternatively, implement the ordering-based matching suggested in the existing code comment (sort API withdrawals and input params by amount, since relayer fees are identical for same-token entries) so `findMatchingWithdrawal` correlates the correct `index`-th same-asset withdrawal rather than the first one found.
- Add an invariant check comparing the number of same-`assetId` entries in `response.withdrawals` to the number of same-`assetId` requests in the batch, throwing `PoaWithdrawalInvariantError` (or equivalent) instead of silently returning a possibly-wrong match.

### Proof of Concept
1. Caller submits one NEAR intent with two POA-bridge withdrawal params for the same `assetId` (`nep141:usdc.omft.near`), destination `X` (index 0) and destination `Y` (index 1), via `sdk.createWithdrawalCompletionPromises`.
2. `createWithdrawalIdentifiers` produces two `WithdrawalIdentifier`s with `index: 0` and `index: 1`, both carrying the same `assetId` (`packages/intents-sdk/src/core/withdrawal-watcher.ts:80-107`).
3. On-chain, only the transfer to `X` settles; POA bridge API returns a `withdrawals` array containing one `COMPLETED` entry for `near_token_id: "usdc.omft.near"` with `transfer_tx_hash: "0xAAA"` (belonging to `X`), while `Y`'s transfer is still pending/not yet indexed.
4. Both `watchWithdrawal` calls (for index 0 and index 1) invoke `describeWithdrawal`, which both call `findMatchingWithdrawal(response.withdrawals, "nep141:usdc.omft.near")` — returning the same `COMPLETED` entry for both (`packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts:313-343,418-427`).
5. Both promises resolve to `{ hash: "0xAAA" }`, so the caller believes withdrawal #1 (to `Y`) completed with tx hash `0xAAA`, even though that hash corresponds only to the transfer sent to `X`.

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
