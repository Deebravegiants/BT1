### Title
Webhook `shop` (and `topic`/`api_version`/`webhook_id`) identity fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body. The `shop` domain (and other identity-bearing headers) that the handler subsequently trusts to identify the tenant are read from HTTP headers that are excluded from the signed material. An attacker who can obtain one genuinely-signed webhook body (e.g. from their own, self-controlled Shopify store) can replay it to the app's public webhook endpoint with an arbitrary `shop-domain` header and have it accepted as authentic for a different, victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile, `shop` (and `topic`, `api-version`, `webhook-id`) are pulled from HTTP headers that are never part of the signable string: [2](#0-1) 

`Registry.process` performs authentication by calling `Utils::HmacValidator.validate(request)`, which internally calls `request.to_signable_string` (the body only) and compares against `request.hmac`: [3](#0-2) [4](#0-3) 

After this check passes, `request.shop` (read straight from the unauthenticated header) is forwarded verbatim into `WebhookMetadata` and handed to the app's handler as the tenant identity: [5](#0-4) 

**Identity binding broken (as an equality):** the gem implicitly claims
`hmac_valid(raw_body) == true` implies `shop_header == shop_that_actually_produced(raw_body)`.
In reality `hmac_valid` only proves `raw_body` was produced/signed by Shopify for *some* shop; it says nothing about which `shop-domain` header accompanies it, because that header is not part of the signed bytes. An attacker who obtains one valid `(raw_body, hmac)` pair — trivially available to them by installing the app on their own store and letting Shopify send them a real webhook — can attach any `shop-domain` header value when replaying the request to the app's public webhook endpoint. `HmacValidator.validate` will still return `true`, and the handler will process the payload believing it originated from the attacker-chosen shop.

This is precisely the "field acted on but not covered by the HMAC" pattern named in the audit-analog rules, mirroring the root cause of the referenced report (a value used to key/derive downstream state is not the same value that was actually authenticated).

### Impact Explanation
Any app handler that uses `WebhookMetadata#shop` to select which tenant's data/session to mutate (a documented and expected usage pattern, since `shop` is the field the gem itself exposes for that purpose) can be tricked into writing, deleting, or otherwise acting on data under a victim shop's identity using attacker-controlled content signed only for the attacker's own shop. This is a cross-tenant confusion: the security boundary between merchants that the HMAC is meant to establish is broken because the tenant-identifying value bypasses the authenticated channel entirely.

### Likelihood Explanation
Any internet user can install the app for free on their own development/trial store (no privileged credentials of the target needed), capture one legitimately Shopify-signed webhook `(body, hmac)` pair for their own shop, and then POST that exact body/hmac to the app's public webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` (or `shopify-shop-domain`) header. `Registry.process` performs no header-to-body binding check, so likelihood is high and requires no secret material belonging to the victim.

### Recommendation
Include the identity-bearing headers (`shop`, `topic`, `api-version`, `webhook-id`) in the material that is authenticated, or otherwise cryptographically bind them to the body before trusting them — e.g. verify the `shop` header against an independently-authenticated source (looked-up session for that shop, rather than trusting the header verbatim), or require callers/host frameworks to separately verify the shop header is consistent with the recipient endpoint/session before invoking handlers.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` (a store the attacker fully controls) and triggers a webhook (e.g. `orders/create`), capturing the genuine `raw_body` and `x-shopify-hmac-sha256` header Shopify sends.
2. Attacker POSTs this exact `raw_body` and `hmac` header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which validates only `@raw_body` against the hmac — this succeeds because the body/hmac pair is genuinely valid (just for a different shop).
4. `WebhookMetadata.new(... shop: request.shop ...)` is constructed with `shop == "victim-shop.myshopify.com"`, taken purely from the attacker-supplied header, and passed to the app's handler as if Shopify had certified this event for the victim shop. [6](#0-5) [7](#0-6)
