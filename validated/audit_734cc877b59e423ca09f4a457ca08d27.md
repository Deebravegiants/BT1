### Title
Webhook shop-domain identity spoofing via unsigned header — HMAC does not cover the `shop` used for tenant routing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the tenant identifier (`shop`) that the gem hands to application webhook handlers is read from an HTTP header that is never included in the signed bytes. This breaks the identity binding `shop authenticated == shop acted on`, allowing anyone who can obtain one validly-signed webhook body (e.g., a merchant receiving webhooks for their own, legitimately installed shop) to relabel it with an arbitrary victim shop domain and have `ShopifyAPI::Webhooks::Registry.process` accept it as genuine, cross-tenant data.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

but `Request#shop` (and `topic`, `webhook_id`, `api_version`) are pulled straight from HTTP headers that are not part of that signed string: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` as the tenant key passed to the app's handler: [3](#0-2) 

`Utils::HmacValidator.validate` only proves that the *body* was produced with `Context.api_secret_key`; it says nothing about which shop the body belongs to: [4](#0-3) 

Because `api_secret_key` is the same for every shop that installs a given app, the HMAC over the body alone cannot distinguish "shop A's webhook body" from "shop B's webhook body" — it only proves "some shop that installed this app sent this exact body." The `shop` header is exactly the kind of "field acted on but not covered by the HMAC" that breaks the binding: `shop_verified_by_hmac (none) != shop_used_for_tenant_routing (header value)`.

The gem's own documentation instructs apps to treat `data.shop` from the handler as the trusted tenant key for routing/queuing work: [5](#0-4) 

### Impact Explanation
Any actor who can install the target app on at least one shop (i.e., an ordinary, unprivileged merchant/attacker) can capture one legitimately-signed webhook body sent to their own shop, then replay that exact body to the app's public webhook endpoint with the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header forged to a victim shop's domain. Since the HMAC check only verifies the body against the shared `api_secret_key`, `Registry.process` will accept the forged request and invoke the app's handler with `shop` set to the victim's domain and attacker-controlled body content. Any app that follows the gem's documented pattern of using `data.shop` to route/store webhook data per-tenant will process attacker-supplied content under another merchant's identity — a cross-tenant integrity/confidentiality violation (e.g., forged `app/uninstalled`, `orders/create`, `customers/data_request` events attributed to a victim shop).

### Likelihood Explanation
High. No secrets beyond a normal, unprivileged app installation are required. The only need is to install the app once (or observe one webhook delivery), which is the default state for any merchant using the app — well within reach of an "unprivileged internet user" with respect to other tenants of the same app.

### Recommendation
- Short term: Document prominently that `request.shop` / `data.shop` is **not cryptographically authenticated** by the webhook HMAC and must not be trusted as a tenant key without additional verification (e.g., cross-checking against a `webhook_id`+shop pair already registered via GraphQL, or maintaining a per-shop webhook secret).
- Long term: Extend `Request#to_signable_string` (or add a companion check in `Registry.process`) to bind the shop domain (and ideally webhook id) into what is verified — e.g., verify the shop header against a known/registered set of shops for the api key, or require per-shop HMAC secrets, so that HMAC validity implies the claimed shop is correct.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com`. Shopify sends a legitimate webhook: body `B`, headers include `X-Shopify-Hmac-Sha256: H(B, api_secret_key)` and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker captures `B` and the valid `H(B, api_secret_key)` (trivial — it's their own webhook delivery, or logged by their own server).
3. Attacker POSTs to the app's public webhook endpoint with the same body `B`, same valid HMAC header, but `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` is constructed; `Utils::HmacValidator.validate` succeeds because it only checks `B` against `api_secret_key`.
5. `Registry.process` invokes the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: B, ...)` — the app processes attacker-controlled data as if it originated from the victim shop.
