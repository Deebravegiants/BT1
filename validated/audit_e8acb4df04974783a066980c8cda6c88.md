### Title
Rounding-truncated `_noFeeSwapInput` lets a large, near-ratio HyperSwap pre-seed fall through to the unguarded `_seedDirectMint` mint, donating graduation liquidity to the attacker's pre-existing LP - ([File: packages/contracts/src/Bonding.sol])

### Summary
`Bonding.finalizeGraduation`'s hostile-pre-seed defense (`_seedRebalancing` → `_pairRebalance`) is supposed to guarantee that any HyperSwap V2 pair with a **non-negligible**, mint-pre-seeded reserve is first rebalanced toward the curve-close ratio via a direct `pair.swap`, so the final `router.addLiquidity` deposit never lands on UniswapV2's donation-prone `min()` mint formula. The fallback to the raw, ratio-naive `_seedDirectMint` is only supposed to fire when the pre-seed is "negligible" (`DIRECT_MINT_PRESEED_BPS`) or when `_pairRebalance` legitimately can't move the ratio because the swap is too small to matter. `_pairRebalance` also returns `false` — and thus also triggers the same `_seedDirectMint` fallback — whenever `_noFeeSwapInput`'s integer `sqrt` truncates the *required* swap size to zero. This truncation is a function of how close the pre-seed's ratio already is to the target ratio, not of the pre-seed's absolute size. An attacker can pre-seed the pair with a **large** reserve deliberately placed within one `sqrt`-unit of the true curve-close ratio (a ratio he can compute exactly from the `TokenGraduating` event's `tokensForLP`/`ltFromPair` fields, emitted well before `finalizeGraduation` in the two-phase-graduation window), causing `_pairRebalance` to return `false` on a reserve size that is above the `DIRECT_MINT_PRESEED_BPS` "negligible" band. `_seedRebalancing` then calls `_seedDirectMint`, which does a raw `transfer` + `pair.mint(lpLock)` against a pool with `totalSupply != 0` — exactly the `min(amount0·S/r0, amount1·S/r1)` donation scenario the whole regime-3 rebalance path exists to prevent.

### Finding Description
`finalizeGraduation` (`Bonding.sol:1000-1034`) calls `_seedUniswapV2Direct` → `_seedRebalancing` (`Bonding.sol:1279-1354`) when the pair already has LP minted (`totalSupply() != 0`). If the pre-seed reserves are above the `DIRECT_MINT_PRESEED_BPS` band on at least one side, `_seedRebalancing` attempts to rebalance via `_pairRebalance` (`Bonding.sol:1414-1429`), which computes the swap size with `_noFeeSwapInput` (`Bonding.sol:1507-1522`):

```solidity
uint256 product = Math.mulDiv(reserveIn * reserveOut, targetN, targetD);
uint256 newIn = Math.sqrt(product);
if (newIn <= reserveIn) return 0;
```

`Math.sqrt` truncates downward. If the attacker's pre-seed ratio is already within roughly `1/(2*reserveIn)` of the true target ratio, `newIn` truncates to `<= reserveIn` and the function returns `0` even though `reserveIn`/`reserveOut` are large in absolute terms — the "negligible reserve" premise stated in the `_seedRebalancing`/`_pairRebalance` natspec (`Bonding.sol:1310-1315`, `1176-1183`) does not actually hold; it only holds for the `DIRECT_MINT_PRESEED_BPS` fast-path check, not for this rounding-triggered `false`.

When `_pairRebalance` returns `false`, `_seedRebalancing` falls back to `_seedDirectMint(tokenAddress, lt, pair, tokensForLP, ltFromPair)` (`Bonding.sol:1331`, `1347`) — the same function used for the pristine empty-pair case:

```solidity
function _seedDirectMint(...) internal returns (uint256 liquidity) {
    IERC20(tokenAddress).safeTransfer(pair, tokensForLP);
    IERC20(lt).safeTransfer(pair, ltFromPair);
    liquidity = IUniswapV2Pair(pair).mint(_s().lpLock);
    ...
}
```
(`Bonding.sol:1245-1259`)

This is safe only when `IUniswapV2Pair(pair).totalSupply() == 0` (the branch documented at `Bonding.sol:1217-1226`). In the rebalance-fallback path reached here, `totalSupply() != 0` (the attacker already holds LP from a prior `pair.mint`), so `pair.mint(lpLock)` runs UniswapV2's proportional-mint formula `min(amount0·S/reserve0, amount1·S/reserve1)`. Because the deposited `(tokensForLP, ltFromPair)` amounts are large relative to the attacker's small pre-existing reserves but at a ratio only *approximately* matching them, one side's deposit-to-reserve ratio is marginally smaller than the other's, so `lpLock` is minted a `liquidity` amount capped by the smaller ratio while the pool's reserves absorb the full amount on both sides. The excess on the larger-ratio side is a straight reserve donation captured by whoever holds the pre-existing LP supply — the attacker, who minted essentially all of it moments earlier.

`LPLock.recordLock` (`LPLock.sol:70-85`) is a one-shot sentinel (`if ($.locks[token].lockedAt != 0) revert AlreadyLocked();`) with no rescue/re-lock path, so the mis-priced `liquidity` value from this single call is permanent — there is no second chance to correct the LP split for that token.

### Impact Explanation
The attacker permanently captures a disproportionate share of the graduation LP's underlying value (TOKEN and LT that should have gone entirely to `LPLock` on behalf of the protocol/creator/traders) by exploiting integer-rounding in the rebalance-decision logic to force the code down the empty-pool mint path against a non-empty, attacker-controlled pool. This is a direct theft of value seeded at graduation — the exact "LP seeded away from the curve close price" / theft-of-LP-funds impact category — and it is irreversible once `finalizeGraduation` completes because `LPLock.recordLock` cannot be re-run for that token.

### Likelihood Explanation
`triggerGraduation` and `finalizeGraduation` are both explicitly permissionless (`Bonding.sol:970-979`, `1000-1002`), and the two-phase design intentionally leaves a window (documented as "~60s" in the natspec at `Bonding.sol:994`) between the `TokenGraduating` event (which discloses the exact `tokensForLP`/`ltFromPair` needed to compute the target ratio) and the keeper's `finalizeGraduation` call. Any unprivileged address can, in that window, pre-create the HyperSwap pair, transfer TOKEN/LT at a ratio within one `sqrt`-rounding unit of the disclosed target (an off-chain-computable value), and call `pair.mint(self)` to seed real LP supply above the `DIRECT_MINT_PRESEED_BPS` threshold. This requires only standard ERC20 transfers and a direct pair `mint` call — no privileged role, no protocol bug outside this contract's own defense logic.

### Recommendation
Do not gate the `_seedDirectMint` fallback purely on `_pairRebalance` returning `false`. Independently re-check `totalSupply() == 0` (or an absolute/relative reserve-size bound consistent with `DIRECT_MINT_PRESEED_BPS`) immediately before calling `_seedDirectMint` from within `_seedRebalancing`'s rebalance-failure branches; if the pool has non-zero supply and reserves above the negligible band, route through `_routerDepositAndDispose`'s ratio-aware, `quote()`-based deposit instead of the raw proportional-mint `_seedDirectMint`, even when the swap itself rounds to zero.

### Proof of Concept
1. Attacker (unprivileged) waits for `Bonding.triggerGraduation(tokenAddress)` or the inline buy-triggered `TokenGraduating(tokenAddress, tokensForLP, ltFromPair, lpBurned, unsoldBurned)` event, learning the exact target ratio `tokensForLP : ltFromPair`.
2. Attacker calls `_ensureUniswapV2Pair`-equivalent (`factory.createPair(tokenAddress, lt)` directly, or lets `finalizeGraduation` create it — attacker just needs to seed before finalize lands), then `transfer`s TOKEN and LT to the pair at a ratio within one `sqrt`-unit of `tokensForLP/ltFromPair`, sized so both amounts exceed `DIRECT_MINT_PRESEED_BPS` of `tokensForLP`/`ltFromPair` (i.e., not "dust").
3. Attacker calls `pair.mint(attacker)` directly, minting real LP supply (`totalSupply() != 0`) to themselves.
4. Anyone calls `Bonding.finalizeGraduation(tokenAddress)`. `_seedRebalancing` computes `_noFeeSwapInput`, which truncates to `0` due to the near-exact ratio match combined with large reserves; `_pairRebalance` returns `false`; `_seedRebalancing` falls back to `_seedDirectMint`, which transfers the full `(tokensForLP, ltFromPair)` into the pair and calls `pair.mint(lpLock)` against the attacker's non-empty supply, minting `lpLock` a `min()`-capped share while the attacker's untouched pre-existing LP now represents a claim on the enlarged reserve pool.
5. Attacker removes liquidity, redeeming more TOKEN/LT value than they deposited — value effectively siphoned from the graduation's intended `LPLock` allocation, with `LPLock.recordLock` already finalized and unrecoverable.
