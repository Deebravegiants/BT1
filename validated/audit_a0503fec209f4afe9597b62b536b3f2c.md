### Title
RAY-value overflow in `scaled_to_original` permanently freezes a market before the borrow-index cap can engage - ([File: common/src/rates/scaling.rs](contracts/pool/../../../common/src/rates/scaling.rs))

### Summary
XOXNO Lending accrues interest by multiplying total borrowed shares by the borrow index in RAY (10^27) fixed point. When the product `scaled * index / RAY` exceeds `i128::MAX`, `fp_core::mul_div_half_up` raises `MathOverflow` instead of saturating. Every user-facing verb accrues first, so once a market crosses the RAY-value ceiling, `update_indexes` and therefore `supply`/`borrow`/`withdraw`/`repay`/`liquidate`/`clean_bad_debt` all revert permanently. The intended backstop `MAX_BORROW_INDEX_RAY` never engages because the value multiplication overflows at `i128::MAX / RAY ≈ 170.14` whole-token value before the index reaches its cap.

### Finding Description
The glibc CVE class is an integer overflow that corrupts execution state; the analog here is a raw `i128` overflow in index accrual that aborts all execution. `scaled_to_original` in `common/src/rates/scaling.rs:14` computes `scaled.mul(env, index)`, and `Ray::mul` calls `fp_core::mul_div_half_up`, which panics with `MathOverflow` when the result leaves `i128` (`docs/reference/formulas.md`: "Unrepresentable results raise MathOverflow"). The accrual path in `common/src/rates` (e.g. `update_borrow_index`, supplier rewards distribution via `update_supply_index`, and utilization/debt valuation `scaled * index`) is invoked at the top of every pool operation. `contracts/pool/src/cache/scale.rs` computes market totals as `half_up(total_borrowed_shares * borrow_index / RAY)`. The repo's own regression test `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321` demonstrates the cliff: on a whale market at ~98% utilization on the XLM rate curve, `update_indexes` starts reverting with `MATH_OVERFLOW` while `borrow_index < MAX_BORROW_INDEX_RAY`, and subsequent `withdraw` and `repay` calls revert identically — the market is permanently bricked with user funds inside.

### Impact Explanation
Permanent freezing of user funds and protocol insolvency for the affected market: suppliers cannot withdraw, borrowers cannot repay, liquidators cannot liquidate, and bad debt cannot be cleaned — because accrual runs first in all of those entrypoints and traps on the same overflow. There is no privileged escape path in scope; `recapitalize` also operates on accrual state.

### Likelihood Explanation
An unprivileged attacker can push a market toward the cliff by supplying a large balance and borrowing to sustained maximum utilization (the curve's steep segment compounds the borrow index), requiring no special permission — only capital and time. Caps bound by `require_cap_within_asset_domain` / `MAX_RAY_VALUE` still admit values near `i128::MAX / RAY`, so the ceiling is reachable within configured limits rather than only in theory. Severity is bounded by the capital and duration needed, so Medium/High rather than Critical.

### Recommendation
Cap accrual in value space, not only index space: clamp `borrow_index` (and the supply-side equivalent) so that `total_scaled * index / RAY` stays below `i128::MAX`, or make `scaled_to_original`/`mul_div_*` in the accrual path saturate instead of panic so the market degrades gracefully rather than bricking. Alternatively, gate borrows when `ceil(debt_value)` approaches the RAY-value ceiling, similar to the existing `require_utilization_below_max` guard.

### Proof of Concept
See `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs::a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` (lines 321-361): build a market with an 18-decimal asset on the XLM curve, lift caps, supply ~1e9 tokens, borrow ~98%, advance time yearly until `try_update_indexes_for` fails with `errors::MATH_OVERFLOW` while `borrow_index < MAX_BORROW_INDEX_RAY`; then `try_withdraw_raw` and `try_repay` both revert with `MATH_OVERFLOW`, confirming permanent freeze.
