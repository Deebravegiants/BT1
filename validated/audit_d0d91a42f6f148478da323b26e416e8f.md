### Title
`onAccept` and `onPostRequestTimeout` share the same pause switch as `send`, blocking message delivery and fund recovery for in-flight transfers - ([File: sdk/packages/core/contracts/apps/HyperFungibleToken.sol])

### Summary
`HyperFungibleToken`, `HyperFungibleTokenUpgradeable`, and `WrappedHyperFungibleToken` gate `onAccept` (message delivery/mint) and `onPostRequestTimeout` (refund of already-burned/locked funds) behind the same `whenNotPaused` modifier used for `send()`/`transfer()`. This means a single `pause()` call halts not only new outbound transfers but also the completion and refund paths for transfers that are already in flight, mirroring the reported bug class where "withdrawals" should remain open even when "deposits" are paused.

### Finding Description
`HyperFungibleToken.send()` burns the caller's tokens and dispatches an ISMP POST request to the destination chain [1](#0-0) . The two ways a burn can be reconciled are:
- `onAccept`, called by the ISMP host to mint tokens to the beneficiary on the destination chain, and
- `onPostRequestTimeout`, called by the ISMP host to re-mint (refund) the burned tokens back to the sender if the message times out.

Both are marked `whenNotPaused`: [2](#0-1) 

The same pattern exists in the upgradeable variant [3](#0-2)  and in the lock/unlock wrapper, where `onAccept` unlocks previously-escrowed underlying tokens and `onPostRequestTimeout` refunds them: [4](#0-3) 

`pause()`/`unpause()` are owner-only and apply globally to the contract, with no distinction between blocking *new* sends versus blocking *completion/refund* of transfers already committed on-chain (tokens already burned or locked) [5](#0-4) .

Because `onAccept` and `onPostRequestTimeout` are the only two ways a burned/locked balance can be resolved, once the contract is paused, any transfer already in flight (burned/locked pre-pause, or dispatched right before pause) cannot be delivered to its beneficiary via `onAccept`, nor can it be refunded via `onPostRequestTimeout`, even though the relayer/ISMP host attempts to submit the corresponding proof — both calls simply revert while `paused()` is true. This is functionally the same failure mode as the referenced report: a route that should always be able to settle/return user funds is coupled to the same pause flag as the deposit-initiating function.

### Impact Explanation
While the owner can eventually `unpause()`, in the interim window any user whose transfer is mid-flight (burned on source, not yet minted on destination, or timed out but not yet refunded) has funds that are neither on the source chain nor the destination chain and cannot self-service recovery — the ISMP host's relayer-submitted delivery/timeout proof calls simply revert. This affects unprivileged end users (senders of `send()`) who have no way to force settlement while the flag is set, and it blocks the message-delivery route (`onAccept`) entirely, matching the "route unable to deliver messages" acceptance criterion for Medium severity.

### Likelihood Explanation
Likelihood is moderate: pausing is a normal operational action (e.g., in response to an incident on one chain or one message), and doing so has an unintended side effect of also freezing in-flight funds for *all* users across *all* chains for the token, not just new sends. Any relayer attempting delivery or timeout settlement during the pause window will fail, and those messages must be redelivered only after `unpause()`, silently delaying user fund recovery.

### Recommendation
Do not gate refund/delivery-completion paths behind the same pause flag as new sends. Specifically, remove `whenNotPaused` from `onAccept` and `onPostRequestTimeout` in `HyperFungibleToken.sol`, `HyperFungibleTokenUpgradeable.sol`, and `WrappedHyperFungibleToken.sol` (or introduce a separate pause flag scoped only to `send()`/ERC20 transfers), so that in-flight funds can always be delivered or refunded regardless of the paused state of new outbound transfers.

### Proof of Concept
1. User calls `HyperFungibleToken.send(...)`, burning `amount` tokens and dispatching a POST request (commitment `C`) [1](#0-0) .
2. Before the message is delivered or times out, the owner calls `pause()` [6](#0-5) .
3. The relayer submits the delivery proof to the destination chain's ISMP host, which calls `onAccept`; the call reverts due to `whenNotPaused` [7](#0-6) . The beneficiary never receives the minted tokens.
4. Alternatively, if the message times out, the relayer submits the timeout proof and the source-chain host calls `onPostRequestTimeout`, which also reverts due to `whenNotPaused` [8](#0-7) . The sender cannot reclaim the burned tokens.
5. This confirms in-flight tokens are stranded (unmintable and unrefundable) for the duration of the pause, demonstrated in the existing test `testOnAcceptRevertsWhenPaused` which asserts `onAccept` reverts while paused [9](#0-8) .

    function onAccept(IncomingPostRequest calldata incoming) public virtual override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        Message memory message = abi.decode(request.body, (Message));
        address beneficiary = _toAddr(message.to);
        _mint(beneficiary, message.amount);

        if (message.data.length > 0) {
            ICallDispatcher(_dispatcher).dispatch(message.data);
        }

        emit Received({
            from: message.from,
            to: beneficiary,
            source: string(request.source),
            amount: message.amount
        });
    }

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        HyperFungibleToken.Message memory message = abi.decode(request.body, (HyperFungibleToken.Message));
        address beneficiary = _toAddr(message.to);

        if (_isWeth) {
            // Try a native-ETH push first (cheap for EOAs and payable contracts);
            // if the recipient cannot accept native value (no `receive()` / `fallback()
            // payable`), re-wrap the withdrawn ETH and deliver the underlying WETH as
            // an ERC-20 transfer instead. This mirrors the deposit-side flexibility of
            // `send()` (which accepts WETH from non-payable callers via `safeTransferFrom`)
            // so the refund path doesn't permanently lock funds for the same caller class.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = beneficiary.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(beneficiary, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(beneficiary, message.amount);
        }

        if (message.data.length > 0) {
            ICallDispatcher(_dispatcher).dispatch(message.data);
        }

        emit Received({
            from: message.from,
            to: beneficiary,
            source: string(request.source),
            amount: message.amount
        });
    }

    /**
     * @notice Handles timeout of a previously dispatched cross-chain transfer
     * @dev Called by the ISMP host when a sent message times out without being delivered.
     * Attempts to unwrap WETH and refund native tokens.
     * @param incoming The timed-out POST request and the relayer that submitted the timeout proof
     */
    function onPostRequestTimeout(PostRequestTimeout calldata incoming) external override onlyHost whenNotPaused {
        HyperFungibleToken.Message memory message = abi.decode(incoming.request.body, (HyperFungibleToken.Message));
        address refundee = _toAddr(message.from);

        if (_isWeth) {
            // Try a native-ETH push first; if the refundee cannot accept native value
            // (e.g. the caller used the ERC-20 deposit path in `send()` from a
            // non-payable contract), re-wrap the withdrawn ETH and deliver the
            // underlying WETH as an ERC-20 transfer so the timeout still settles and
            // funds are not permanently locked.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = refundee.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(refundee, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(refundee, message.amount);
        }

        emit Refunded({to: refundee, amount: message.amount});
    }
