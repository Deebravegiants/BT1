### Title
Unbounded ECDSA signature recovery loop in BEEFY consensus proof verification allows resource-exhaustion DoS - ([File: modules/consensus/beefy/verifier/src/lib.rs])

### Summary
`verify_mmr_update_proof` (and its Solidity counterpart in `EcdsaBeefy.sol`) checks only that the number of submitted signatures meets or exceeds the supermajority *minimum*, with no upper bound on how many signatures a submitted consensus proof may contain. Every submitted signature is then passed through an expensive `secp256k1_recover` (ECDSA public-key recovery) call in a loop, before the (cheap) merkle-membership check is done. An attacker who can submit a BEEFY consensus update — e.g. via `pallet-ismp`'s unsigned-extrinsic consensus update path, or via `EcdsaBeefy.verify` on EVM hosts — can pad the `signatures`/`votes` array with an arbitrarily large number of bogus (or reused) signatures, forcing the verifier to perform an unbounded number of costly signature-recovery operations before rejecting the proof. This is the same bug class as GHSA-2c7c-3mj9-8fqh: an attacker-controlled length/count value gates expensive cryptographic work with only a lower bound, not an upper one.

### Finding Description
`check_participation_threshold` (Rust) / `checkParticipationThreshold` (Solidity) implements:

```
len >= ((2 * total) / 3) + 1
``` [1](#0-0) 

This only enforces a *floor* on `sigLen`/`signatures_length` — the number of ECDSA signatures the caller supplies in the proof — relative to the known authority-set size. There is no ceiling tying `sigLen` to `authoritySet.len` (e.g. rejecting `sigLen > authoritySet.len`).

In the Rust verifier used by the ismp consensus-client path:
```rust
let signatures_length = mmr.signed_commitment.signatures.len();
...
if !check_participation_threshold(signatures_length as u32, authority_set.len) {
    return Err(Error::SuperMajorityRequired);
}
...
for sig in mmr.signed_commitment.signatures.iter() {
    let uncompressed = H::secp256k1_recover(&commitment_hash.0, &sig.signature)
        .map_err(|_| Error::FailedToRecoverPublicKey)?;
    ...
}
``` [2](#0-1) 

Because the threshold check only requires `signatures_length >= 2/3*total + 1` and never bounds it from above, an attacker crafting the `MmrProof` can include far more signature entries than the true authority set size (bounded only by the max extrinsic/block size, not by the authority set), each of which triggers a full `secp256k1_recover` call. The equivalent Solidity code exhibits the identical pattern:

```solidity
uint256 sigLen = relayProof.signedCommitment.votes.length;
...
if (!checkParticipationThreshold(sigLen, authoritySet.len)) revert SuperMajorityRequired();
...
for (uint256 i = 0; i < sigLen; i++) {
    Vote memory vote = relayProof.signedCommitment.votes[i];
    address authority = ECDSA.recover(commitmentHash, vote.signature);
    ...
}
``` [3](#0-2) 

Since the merkle multi-proof membership check (`MerkleMultiProof.VerifyProof` / `merkle_proof.verify`) only runs *after* all recoveries complete, the expensive work is fully paid before the ultimately-invalid proof is rejected.

### Impact Explanation
This is reachable by any unprivileged relayer submitting a BEEFY consensus update — the entry point that is the strongest "reachable" path called out in scope (consensus verification / relayed proof). On the substrate side, this proof verification runs inside the ismp consensus-client update path invoked via an unsigned extrinsic, meaning a single relayed message can force the node to perform tens of thousands of expensive secp256k1 recovery operations (each independently CPU-costly) before the proof is ultimately rejected as invalid. This can stall block execution / consensus-client processing for that node, denying timely processing of legitimate consensus updates and message delivery — a resource-consumption DoS matching CWE-400, directly analogous to the "billion hashes" PBES2 issue where an attacker-controlled iteration/count parameter is checked only against a minimum, not a maximum.

### Likelihood Explanation
Likelihood is high for the runtime path: constructing an oversized-but-otherwise-well-formed `signatures`/`votes` vector requires no privileged access or cryptographic break — an attacker only needs filler signature bytes (they need not even be valid/recoverable in a way that changes the accounting, since `check_participation_threshold` is evaluated on the raw length before the loop runs). The only constraint is the maximum extrinsic/proof size accepted by the transport layer, which is typically large enough (megabytes) to admit many thousands of bogus 65-byte signature entries.

### Recommendation
Cap `signatures_length`/`sigLen` to at most `authority_set.len` (or some fixed small multiple) before entering the recovery loop, in both `modules/consensus/beefy/verifier/src/lib.rs::verify_mmr_update_proof` and `evm/src/consensus/EcdsaBeefy.sol::verifyMmrUpdateProof`, rejecting proofs with `signatures_length > authority_set.len` (or `.len` + a small allowance for duplicate indices) prior to iterating and recovering signatures.

### Proof of Concept
1. Craft a `MmrProof` (or `RelayChainProof`) whose `signed_commitment.signatures` (`votes`) array contains, e.g., 50,000 dummy 65-byte signature entries with distinct `authorityIndex` values, satisfying `signatures_length >= 2/3*total+1` for the trusted authority set.
2. Submit this as a BEEFY consensus update via the reachable ismp consensus-client update path (or `EcdsaBeefy.verify` on EVM).
3. Observe that `verify_mmr_update_proof`/`verifyMmrUpdateProof` performs 50,000 `secp256k1_recover`/`ECDSA.recover` calls before the subsequent merkle multi-proof check rejects the (ultimately bogus) authority membership — consuming disproportionate CPU/gas relative to a legitimate proof of the true authority-set size.
