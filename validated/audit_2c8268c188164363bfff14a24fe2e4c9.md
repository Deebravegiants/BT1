### Title
Push-payment of native ETH to arbitrary beneficiary in `onAccept`/`onPostRequestTimeout` allows attacker to grief relayer's batched message delivery via unbounded gas consumption - (File: `sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol`)

### Summary
`WrappedHyperFungibleToken.onAccept` and `.onPostRequestTimeout` (and their `Upgradeable` counterparts) push native ETH directly to an attacker-controlled `beneficiary`/`refundee` address via `beneficiary.call{value: message.amount}("")`, forwarding essentially all remaining gas, during the permissionless message-delivery path (`HandlerV2.handlePostRequests` → `EvmHost.dispatchIncoming` → `IApp.onAccept`). This is the same push-payment pattern flagged in the external report: an attacker-controlled recipient can consume unbounded gas inside a payout call that is triggered as a side effect of someone else's (the relayer's) transaction.

### Finding Description
`HandlerV2.handlePostRequests` iterates over a batch of requests and calls `host.dispatchIncoming(leaf.request, _msgSender())` for each one [1](#0-0) . `EvmHost.dispatchIncoming` then performs a low-level `.call` to `IApp.onAccept` on the destination app, without any gas cap, and treats failure gracefully by deleting the receipt so it can be retried, without reverting the whole batch [2](#0-1) .

When the destination app is `WrappedHyperFungibleToken` (or its Upgradeable variant) configured for `isWeth`, `onAccept` withdraws WETH and immediately pushes native ETH to the `beneficiary` address decoded from the cross-chain message body, forwarding essentially all remaining gas in the call: [3](#0-2) 
The same pattern exists in the timeout-refund path, pushing ETH to `refundee`: [4](#0-3) 
And identically in the upgradeable variant: [5](#0-4) 

Because `beneficiary`/`refundee` is fully attacker-controlled (it is decoded from the message body sent by the attacker on the source chain, or is the attacker's own address on the source chain for a self-triggered timeout), the attacker can deploy a contract at that address whose `receive()`/`fallback()` deliberately consumes almost all of the gas forwarded by the `.call{value: ...}("")`. Since Solidity forwards ~63/64 of remaining gas to external calls, an attacker can burn the bulk of the relayer's transaction gas budget inside this single call. If the exhausted gas causes the inner call to fail purely due to running out of the forwarded gas (not an explicit revert), `sent` is `false`, but the majority of gas has already been consumed by the callee before failing back to the caller. If `handlePostRequests`/`batchCall` is used to deliver many messages in one relayer transaction, this griefing can push the whole transaction toward the block gas limit, causing legitimate, unrelated messages batched in the same transaction to run out of gas and fail to be delivered, or forcing the relayer to pay disproportionate gas for a single malicious message, discouraging relayers from delivering (or batching) messages destined for this app. This mirrors the original Fairswap/BoxExchange "force traders to mint gas token" bug class: a push-payment made mid-execution to an untrusted party with unmetered gas, letting the attacker turn the payout call into an arbitrary, expensive computation at the payer's expense.

### Impact Explanation
This does not directly let an attacker steal escrowed funds (the fallback WETH+ERC20 path exists for hard call failures), but it does:
- Grief relayers economically, since `.call{value}("")` forwards essentially all gas and the relayer bears the cost of any gas the malicious beneficiary contract burns.
- Potentially cause a "route unable to deliver messages" condition for a batched transaction: if a malicious message is bundled (by the attacker itself, since dispatch is permissionless) alongside other pending messages in the same `handlePostRequests`/`batchCall` invocation, the attacker can force that specific relayer submission to run out of gas, failing delivery of otherwise-legitimate co-batched messages, which then must be resubmitted, delaying and increasing the cost of cross-chain delivery for other users' escrowed funds tied to that submission.
- Because there is no gas cap on the pushed value transfer, this griefing vector scales with how much gas the relayer supplies, giving the attacker significant leverage over relayer economics and delivery reliability for this specific app.

### Likelihood Explanation
Reaching this path requires no privileged role: any user can call `WrappedHyperFungibleToken.send` (or the `Upgradeable` version) with `isWeth = true`, setting an arbitrary `to`/beneficiary address that is a contract with a gas-burning `receive()`, and any relayer that later delivers the resulting POST request (or the timeout, refunding to an attacker-chosen `from`) will trigger the vulnerable push. This is trivially reachable from a single dispatched request; it does not require compromising any admin, consensus, or governance role, and is exercised purely through the permissionless message-dispatch/delivery flow.

### Recommendation
Replace the push-payment ETH transfer in `onAccept`/`onPostRequestTimeout` with a pull-payment model, or at minimum cap the gas forwarded to the beneficiary (e.g., `beneficiary.call{value: amount, gas: 2300}("")` or a fixed safe stipend) and fall back to the WETH/ERC-20 credit path on any failure — including gas-exhaustion failures — exactly as recommended in the referenced report. Concretely:
- Record `amount` owed to `beneficiary`/`refundee` in a `mapping(address => uint256)` and require a separate `withdraw()` call initiated by the recipient to pull the ETH, removing the ability of an untrusted recipient to consume gas inside the relayer-triggered delivery transaction.
- Alternatively, retain the current auto-unwrap convenience but bound the gas forwarded on the native-ETH attempt so a malicious recipient cannot consume more than a small, fixed amount of the relayer's gas before falling back to the ERC-20 transfer path.

### Proof of Concept
1. Attacker deploys `Griefer.sol` with a `receive() external payable { while(true) { /* burn gas, e.g. repeated SSTORE to fresh storage slots */ } }` (loop bounded only by gas supplied, causing an out-of-gas revert internally once the forwarded gas runs low).
2. Attacker calls `WrappedHyperFungibleToken.send(SendParams{ dest: destChain, to: abi.encodePacked(address(Griefer)), amount: X, ... })` on the source chain with `isWeth = true`.
3. A relayer batches this request together with N legitimate pending POST requests into a single `HandlerV2.handlePostRequests`/`batchCall` transaction and submits it with a gas limit sized for N+1 "normal" deliveries.
4. During processing of the attacker's request, `EvmHost.dispatchIncoming` calls `WrappedHyperFungibleToken.onAccept`, which executes `beneficiary.call{value: message.amount}("")`; the `Griefer` contract consumes ~63/64 of remaining gas in its `receive()`, causing the low-level call to fail (or nearly exhaust the tx's remaining gas).
5. Because the relayer under-provisioned gas for this "unexpectedly expensive" message, subsequent legitimate requests in the same batch run out of gas and fail to be delivered (per-request receipts are rolled back per `dispatchIncoming`'s `!success` branch, so no state corruption occurs, but delivery of those legitimate messages must be retried, at extra relayer cost/delay).

Note: I could not fully verify whether Solidity's 63/64 gas-forwarding rule combined with the specific call-site gas budget in this codebase would reliably cause a full batch failure versus only failing the single malicious sub-call in every configuration (this depends on relayer-side gas estimation/padding, which is outside the scope of the on-chain code reviewed). This uncertainty affects the severity between "relayer gas griefing on a single message" (lower impact) and "griefing an entire batched delivery transaction" (higher impact); both variants stem from the same root cause of unmetered, push-style ETH transfer to an untrusted address in `onAccept`/`onPostRequestTimeout`.

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }
