### Title
Malicious order input token can permanently freeze cross-chain escrow settlement in `IntentGatewayV2` (`_withdraw`) - (File: evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
`IntentsBase._withdraw` releases every token in `WithdrawalRequest.tokens` to a beneficiary in a single loop with no isolation between transfers. Because `order.inputs` (the list of escrowed tokens) is fully attacker-controlled by whoever places the order, a malicious maker can escrow one legitimate token alongside one malicious ERC20 that always reverts on `transfer`. When a solver fills the order cross-chain and Hyperbridge later delivers the `RedeemEscrow`/`RefundEscrow` message that should release the escrow, the malicious token's revert bricks the entire `_withdraw` call, permanently blocking release of the co-escrowed legitimate token as well — exactly the "malicious token contract" bug class from Putty's `PuttyV2.exercise()`/`withdraw()`.

### Finding Description
`placeOrder` lets the order creator pick an arbitrary set of `order.inputs` tokens with no allow-list, escrowing them under `_orders[commitment][token]`: [1](#0-0) 

When a solver fills the order cross-chain (`_fillCrossChain`), the solver first pays the *output* tokens directly to the beneficiary on the destination chain, then a `RedeemEscrow` message is dispatched back to the source chain to release the *input* escrow to the solver: [2](#0-1) 

That message is handled in `onAccept`, which decodes the `WithdrawalRequest` (containing `order.inputs` as `body.tokens`) and calls `_withdraw`: [3](#0-2) 

`_withdraw` iterates over `body.tokens` and performs a plain `safeTransfer` for each token with no try/catch or per-token isolation: [4](#0-3) 

If any one of the escrowed tokens is a malicious ERC20 contract configured by the attacker (the order's own creator) to revert on `transfer` under attacker-controlled conditions, the entire `_withdraw` call reverts — every time it is retried — because the loop has no fault isolation. The same code path is reused for `RefundEscrow` (via `onAccept`) and for the GET-response-driven cancel refund path (`onGetResponse`): [5](#0-4) 

Per `EvmHost` semantics, a failed `onAccept` call is treated as an undelivered/retryable message (the receipt is deleted so the relayer can resubmit), but because the malicious token's revert condition is attacker-controlled and can be made permanent, the message can never be successfully delivered: [6](#0-5) 

The same-chain path (`IntrinsicIntents.sol`) does not call `_withdraw` for input release on fill (it computes `escrowedInputs` for the event only), so the sharpest impact is on the cross-chain settlement path, where escrow release is decoupled in time and space from the solver's own output payment — the solver has no way to abort or hedge once it has already paid the beneficiary.

### Impact Explanation
A malicious order creator can escrow a legitimate, valuable token (e.g., USDC) together with a malicious ERC20 they control as part of `order.inputs`. A solver, unaware the second token is malicious (or believing it is dust with a negligible declared amount), fills the order on the destination chain and pays the required output assets to the beneficiary — an irreversible action. The attacker then flips their malicious token to always revert on `transfer`. The `RedeemEscrow` message can never be successfully processed by `_withdraw`, so:
- The solver's rightful escrowed input tokens (including the legitimate ones) are permanently frozen in the `IntentGatewayV2` contract — the solver already paid out on the destination chain and receives nothing back.
- The same failure mode applies to `RefundEscrow`/`onGetResponse`, permanently freezing a user's own refund if any co-escrowed input token is malicious (whether self-inflicted or via multi-asset intents composed from untrusted token lists).

This is a permanent freezing-of-funds vulnerability reachable by any unprivileged user simply placing an order — matching the Medium-severity Putty analog (external requirement: attacker must control/deploy the malicious token, which is trivial and permissionless).

### Likelihood Explanation
Likelihood is Medium: placing an order with an attacker-controlled token as one of several `order.inputs` requires no special privileges — any account can call `placeOrder` with an arbitrary `TokenInfo[]`. The only "cost" to the attacker is that a solver must be willing to fill an order containing an unfamiliar/unverified token, similar to the Putty scenario where the sponsor mitigated purely at the UI level (flagging unverified tokens) rather than on-chain. Because `IntentGatewayV2`/`IntentsBase` performs no token allow-listing or per-token failure isolation in `_withdraw`, the attack is fully reproducible on-chain once a solver is lured into filling such an order.

### Recommendation
- In `_withdraw`, isolate each token transfer (e.g., wrap each `safeTransfer` in a low-level call and record failures for individual retry/claim, rather than reverting the whole loop) so a single malicious token cannot block release of the other escrowed assets.
- Consider a pull-based claim pattern per token (`claim(commitment, token)`) instead of a push loop over all tokens in one transaction.
- Alternatively/additionally, warn solvers off-chain (as Putty ultimately did) by validating/flagging unverified `order.inputs` tokens before allowing a fill, and/or cap the escrow settlement per token so one failing transfer doesn't gate the others.

### Proof of Concept
1. Attacker deploys `EvilToken`, an ERC20 whose `transfer` reverts once a flag `frozen` is set (owner-only).
2. Attacker calls `placeOrder` with `order.inputs = [ {token: USDC, amount: 10_000e6}, {token: EvilToken, amount: 1} ]` and a normal output asset request, escrowing both tokens per `placeOrder`'s input loop (`IntentGatewayV2.sol:313-328`).
3. A solver, unaware of the malicious token (or seeing it as a negligible additional input), calls `fillOrder` cross-chain (`_fillCrossChain`), paying the required output tokens directly to the beneficiary (`ExtrinsicIntents.sol:191-196`), and the gateway dispatches the `RedeemEscrow` message back to the source chain (`ExtrinsicIntents.sol:207-212`).
4. Before the message is delivered, the attacker calls `EvilToken.setFrozen(true)`.
5. When Hyperbridge relays the `RedeemEscrow` message, `onAccept` calls `_withdraw`, which attempts `IERC20(EvilToken).safeTransfer(solver, 1)` in the loop over `body.tokens` (`IntentsBase.sol:456-469`); this reverts, and the entire `_withdraw` call — including the USDC transfer — reverts.
6. Every retry of the message delivery fails identically as long as `EvilToken` stays frozen. The solver's already-paid output tokens are gone, and the escrowed USDC + EvilToken remain permanently locked in `IntentGatewayV2`.

    function _fillCrossChain(Order calldata order, FillOptions calldata options, bytes32 commitment) internal {
        uint256 outputsLen = order.output.assets.length;

        _filled[commitment] = msg.sender;

        uint256 msgValue = msg.value;
        address beneficiary = address(uint160(uint256(order.output.beneficiary)));
        TokenInfo[] memory outputFills = new TokenInfo[](outputsLen);

        for (uint256 i; i < outputsLen; i++) {
            bytes32 outputToken = order.output.assets[i].token;
            if (options.outputs[i].token != outputToken) revert InvalidInput();

            address token = address(uint160(uint256(outputToken)));
            uint256 totalRequired = order.output.assets[i].amount;
            uint256 solverAmount = options.outputs[i].amount;

            if (solverAmount < totalRequired) revert InvalidInput();

            (uint256 protocolShare, uint256 beneficiaryShare) =
                _splitSurplus(solverAmount - totalRequired, order.output.call.length > 0);

            if (token == address(0)) {
                if (msgValue < solverAmount) revert InsufficientNativeToken();
                uint256 beneficiaryTotal = totalRequired + beneficiaryShare;
                _sendValue(beneficiary, beneficiaryTotal);
                msgValue -= (beneficiaryTotal + protocolShare);
            } else {
                IERC20(token).safeTransferFrom(msg.sender, beneficiary, totalRequired + beneficiaryShare);
                if (protocolShare > 0) {
                    IERC20(token).safeTransferFrom(msg.sender, address(this), protocolShare);
                }
            }
            if (protocolShare > 0) emit DustCollected(token, protocolShare);
            outputFills[i] = TokenInfo({token: outputToken, amount: totalRequired});
        }

        _execute(order, outputsLen);

        // Native dispatch fee only if the solver sent enough to cover it; else the fee token.
        uint256 nativeFee = options.nativeDispatchFee;
        if (nativeFee > msgValue) nativeFee = 0;
        msgValue -= nativeFee;
        _post(
            order,
            _body(RequestKind.RedeemEscrow, commitment, order.inputs, bytes32(uint256(uint160(msg.sender)))),
            options.relayerFee,
            nativeFee
        );

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
