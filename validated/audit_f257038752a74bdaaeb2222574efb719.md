### Title
Webhook `shop-domain` header is trusted for tenant routing but is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` extracts `shop`, `topic`, `webhook_id`, and `api_version` from HTTP headers, but `HmacValidator` only ever validates the raw request body against the HMAC. This means the `shop` value that `Registry.process` hands to the app's webhook handler as the tenant identifier is never cryptographically bound to the signature that authenticates the request.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate` computes/compares the HMAC exclusively over `to_signable_string`: [2](#0-1) 

`Registry.process` calls `HmacValidator.validate(request)` and, once it passes, immediately trusts `request.shop` (an unauthenticated header) to build the `WebhookMetadata` passed to the app's handler, with no cross-check against anything inside the signed body: [3](#0-2) 

`request.shop` is read straight from the `x-shopify-shop-domain`/`shopify-shop-domain` header, which is never part of the signable content: [4](#0-3) 

The binding that should hold is: `hmac_signed_bytes == bytes_that_determine_tenant_identity`. Here, `hmac_signed_bytes = raw_body` while `tenant_identity = shop_header`, so the equality is broken — the shop identity used for routing/authorization is disjoint from what the signature actually authenticates.

### Impact Explanation
Because the app's `client_secret` (`api_secret_key`) is shared across every shop that installs the app, any merchant who legitimately receives a signed webhook for their own shop possesses a valid `(body, hmac)` pair. Since the `shop-domain` header is outside the signed content, that same merchant can resend the identical body+HMAC to the app's webhook endpoint while substituting a different shop's domain in the `shop-domain` header. `HmacValidator.validate` still returns `true` (body+secret match), and `Registry.process` will hand the forged `shop` value to the app's handler as if it were an authentic delivery for that other tenant. This is a cross-tenant impersonation vector purely within this gem's own verification/dispatch logic, independent of anything the host app does with the value.

### Likelihood Explanation
Any shop that has installed the app can capture at least one genuine webhook delivery for itself (webhooks are delivered routinely for normal shop events), giving them a valid `(raw_body, hmac)` pair without needing the app's secret. Replaying it with a modified `shop-domain` header requires only the ability to send an arbitrary HTTP request to the app's public webhook endpoint — no credentials, tokens, or privileged access are required.

### Recommendation
Bind the shop identity to the signed payload instead of trusting an out-of-band header: verify the `shop` header value against a shop domain recoverable from the signed body/topic context (e.g., cross-check against session/webhook-id records the app already registered for that specific shop), or extend `to_signable_string` so the HMAC is computed over the header set plus body as Shopify's canonical webhook verification recommends, so the `Request#shop` value can no longer be varied independently of the signature.

### Proof of Concept
1. Malicious merchant M installs the app; the app shares one `api_secret_key` across all installs.
2. Shopify delivers a legitimate webhook to the app for shop `m.myshopify.com` with body `B` and header `x-shopify-hmac-sha256: HMAC(secret, B)`.
3. M captures `(B, HMAC(secret, B))` (trivial — M owns that shop and can inspect/replay traffic to their own endpoint, or run a proxy in front of it).
4. M sends a new HTTP request to the app's webhook endpoint with the same body `B` and the same `x-shopify-hmac-sha256` value, but sets `x-shopify-shop-domain: victim.myshopify.com`.
5. `Registry.process` calls `HmacValidator.validate(request)`, which only checks `B` against the HMAC using the shared secret — it passes.
6. `Registry.process` builds `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed_body, ...)` and invokes the app's handler as though this is an authentic event for `victim`, even though nothing about `victim` was ever signed.
