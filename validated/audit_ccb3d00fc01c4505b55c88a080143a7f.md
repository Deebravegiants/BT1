### Title
Webhook shop attribution is not covered by HMAC verification, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` verifies the HMAC signature over the raw request body only, but the `shop` value used to attribute the webhook to a tenant is read from an HTTP header that is not included in the signed payload. This breaks the intended binding: `hmac_verifies(body) == shop_attributed_to(body)`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `Utils::HmacValidator.validate` computes/compares the HMAC strictly against that signable string [2](#0-1) . Meanwhile, `Request#shop` is derived from the `shopify-shop-domain` (or `x-shopify-shop-domain`) HTTP header, which is completely outside the HMAC-signed content [3](#0-2) .

`Registry.process` only checks `Utils::HmacValidator.validate(request)` before dispatching to the app's handler with `request.shop` as the tenant identifier [4](#0-3) . Because the header is not covered by the signature, an attacker who possesses any single valid `(raw_body, hmac)` pair signed by the app's shared `api_secret_key` (e.g., obtained from a legitimate webhook delivered to their own store, since HMAC secret is shared across all shops using the same app) can replay that exact body/HMAC pair while substituting an arbitrary `shopify-shop-domain` header value. `HmacValidator.validate` will still return `true` (it only re-hashes `@raw_body`), and the handler will receive `WebhookMetadata` attributing the (attacker-controlled or replayed) body's data to a different, victim shop of the attacker's choosing [5](#0-4) .

This is exactly the pattern of "a field acted on but not covered by the HMAC" — the `shop` identity used downstream for storage keys, job routing, or business logic (per the documented handler usage pattern `perform_later(topic: data.topic, shop_domain: data.shop, ...)` [6](#0-5) ) is never authenticated.

### Impact Explanation
This allows cross-tenant data confusion/injection: a low-privilege attacker who runs their own store using the target app (and thus legitimately receives real webhook `(body, hmac)` pairs from Shopify for their own shop) can forge a request that the app's `Registry.process` will accept as authentic and attribute to any other shop of the attacker's choosing. Depending on how the host app's webhook handler uses `data.shop` (e.g., to look up sessions, write to a per-shop record, trigger `shop/redact` or `app/uninstalled` flows), this can lead to cross-tenant data corruption or unauthorized actions performed against a victim merchant's account — meeting the "cross-tenant access" bar for Critical impact.

### Likelihood Explanation
Requires only an unprivileged internet user (any merchant who installs the target app on their own store, which is a normal/available action) to capture one legitimate webhook body+HMAC and replay it with a modified `shop-domain` header. No secrets, tokens, or privileged access are required — the app's `api_secret_key` is never exposed, but its output (valid webhook signatures) is available to any shop using the app.

### Recommendation
Bind the `shop` (and ideally `topic`, `webhook_id`, `api_version`) to the same value covered by the HMAC — either by having Shopify's webhook signature also commit to header/shop information, or (more practically) by cross-checking `request.shop` against an app-side allowlist/registration record before trusting it (e.g., only accept webhooks for shops with an active session/installation, and reject if a webhook claims a topic that is not currently registered/expected for that shop record), and by treating the header-derived `shop` as merely a routing hint rather than an authenticated identity for anything sensitive until corroborated by app-side state.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and receives a legitimate webhook: `raw_body = B`, header `X-Shopify-Hmac-Sha256: H` (valid signature of `B` under the shared `api_secret_key`), and `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Attacker sends a forged HTTP request to the app's webhook endpoint with the same `raw_body = B` and `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` is constructed; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and matches `H` — validation succeeds [7](#0-6) .
4. The app's handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and the attacker-supplied body `B`, despite the request never having been signed for or sent by `victim.myshopify.com`.
