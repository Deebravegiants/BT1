## Title
Webhook HMAC Validation Does Not Bind the `shop` (or `topic`/`webhook-id`) Header, Enabling Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `HmacValidator.validate` verifies the HMAC exclusively against that body. The `shop` attribute — which is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header and passed on unchecked to the app's webhook handler — is never included in the signed material.

### Finding Description
`Request#to_signable_string` returns `@raw_body` only, while `shop` is derived independently from a header: [1](#0-0) [2](#0-1) 

`HmacValidator.validate` computes and compares the HMAC purely over `verifiable_query.to_signable_string` (i.e. the body bytes): [3](#0-2) 

`Registry.process` only calls `Utils::HmacValidator.validate(request)` and then immediately forwards `request.shop` (the unauthenticated header value) into the handler's data object, with no additional binding check between the shop and the signed body: [4](#0-3) 

This breaks the identity binding the caller relies on: **`hmac == HMAC(secret, body)` is treated as proof that `shop == request.shopify-shop-domain header`**, but the header is never part of the HMAC input. Any client that can obtain one genuine `(body, hmac)` pair for its *own* shop (trivial — install the app on an attacker-controlled dev/trial shop and trigger any webhook topic) can replay that exact body/HMAC to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header value. `HmacValidator.validate` still succeeds because it never inspected the header, and `Registry.process` dispatches the (attacker-chosen) body to the handler tagged with the (attacker-chosen) victim shop.

### Impact Explanation
This is a cross-tenant integrity issue: an app's webhook handler typically uses `shop` to select which merchant's persisted session/data the event applies to (order records, inventory updates, GDPR-relevant customer data, etc., see `WebhookMetadata.new(topic:, shop:, body:, ...)`). Forging the shop while keeping a valid signature lets an unprivileged owner of any shop that has ever installed the app inject fabricated webhook payloads attributed to a different, victim tenant, causing the host application to process/act on data as if it originated from that victim's store — a cross-tenant access/data-integrity break satisfying the "Critical – cross-tenant access" bar.

### Likelihood Explanation
Likelihood is high for any app that installs on multiple/public shops: the attacker only needs their own (even free/dev) shop installation to legitimately trigger a webhook and capture a valid raw body + HMAC, then replay it with a modified shop header — no access to the app's `client_secret`, access tokens, or the victim's credentials is required.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) header values in the material verified against the HMAC, or otherwise cryptographically bind the header-derived `shop` to the signed body before dispatching to handlers, consistent with how `AuthQuery#to_signable_string` binds `shop`/`state`/etc. into its signable string.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` and triggers a real webhook (e.g. `orders/create`), capturing the raw POST body `B` and the legitimate `X-Shopify-Hmac-Sha256: H` header Shopify sent for that shop.
2. Attacker resends the identical body `B` and header `H` to the app's webhook endpoint but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request#hmac` reads `H`; `Utils::HmacValidator.validate` recomputes HMAC over `B` only and it matches, so `Registry.process` (`lib/shopify_api/webhooks/registry.rb:190`) proceeds and calls the handler with `shop: "victim.myshopify.com"` and the attacker-controlled body `B`.
