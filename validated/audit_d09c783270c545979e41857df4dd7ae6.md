## Finding

### Title
Webhook `shop` and `topic` values are trusted by `Webhooks::Registry.process` without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC computed over the raw request **body**. The `shop`, `topic`, `webhook_id`, and `api_version` values that are handed to the application's webhook handler are read straight from HTTP headers that are never included in the signed payload, so a caller who is in possession of *any* one authentic `(body, hmac)` pair for the app can replay it while freely rewriting the shop/topic identity headers.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

and `hmac`/`shop`/`topic`/`webhook_id`/`api_version` are all pulled from headers that are not part of that signable string: [2](#0-1) 

`Registry.process` validates only this body HMAC before dispatching to the handler with the unauthenticated `shop`/`topic`/`webhook_id` values: [3](#0-2) 

The equality this breaks is:

`HMAC-verified(body)` ⇒ `authenticated(shop, topic, webhook_id)`

but the code only proves the left side; the right side (the identity fields that `WebhookMetadata` and the handler act on) is never bound to the signature. Since `api_secret_key` is the same secret for every shop that has installed a given app, any merchant who installs the app receives at least one legitimately signed `(body, hmac)` pair addressed to their own shop. That whole request can then be replayed verbatim to the app's public webhook endpoint with the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header rewritten to name a different, victim shop. `HmacValidator.validate` will still succeed because it only recomputes the HMAC over the untouched body: [4](#0-3) 

The handler then receives `WebhookMetadata` claiming to be for the victim shop: [5](#0-4) 

Any host application that uses `request.shop`/`WebhookMetadata#shop` to select the tenant/session to act on (e.g. to look up the shop's session, update the shop's local records, or route billing/app-uninstall logic) can be made to perform that action against the wrong shop's data.

### Impact Explanation
This breaks the shop-identity binding that host applications rely on for multi-tenant isolation, letting one merchant's legitimately-signed webhook traffic be replayed to make the app treat the payload as belonging to an arbitrary other shop — a cross-tenant confusion originating entirely from this gem's webhook verification, which authenticates bytes but not the routing identity carried in headers.

### Likelihood Explanation
Any merchant that installs the app already receives real webhooks with valid HMACs signed by the app's shared `api_secret_key`; capturing one's own webhook traffic requires no special privilege, access token, or knowledge of the secret. Constructing the replay request (same body/HMAC, modified `shop`/`topic` headers) is trivial once a single sample is captured, since `Registry.process` performs no additional binding check.

### Recommendation
Bind the identity fields into the authenticated payload instead of trusting raw headers: recompute/verify `shop` against server-side registration state (e.g. compare to the shop that owns the currently active session, or cross-check against a shop allow-list retrieved via the Admin API) before dispatching to the handler, and/or document/require host apps to independently authorize `request.shop` before acting on webhook data. At minimum, `Webhooks::Registry.process` should not pass an unauthenticated `shop`/`topic` straight into `WebhookMetadata` without the caller being warned that these fields are unauthenticated relative to the HMAC.

### Proof of Concept
1. Install the target app on shop `attacker.myshopify.com`; trigger any webhook subscription (e.g. `orders/create`) to receive one legitimate webhook request with headers `x-shopify-hmac-sha256`, `x-shopify-topic: orders/create`, `x-shopify-shop-domain: attacker.myshopify.com`, and body `B`.
2. Replay the exact same body `B` and `x-shopify-hmac-sha256` value to the app's public webhook endpoint, but set `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC only over `B` and succeeds (identical to step 1's signature).
4. The registered handler is invoked with `WebhookMetadata.new(topic: "orders/create", shop: "victim.myshopify.com", body: ..., ...)`, causing the host application to act as though the payload originated from `victim.myshopify.com`.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
