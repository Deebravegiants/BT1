### Title
Webhook `shop` (tenant) field is trusted for dispatch but not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw HTTP body, while `shop`, `topic`, and `webhook_id` are read straight from unauthenticated HTTP headers and are never bound into the HMAC that `Utils::HmacValidator.validate` checks. Since the same `api_secret_key` is shared by every merchant who installs a given app, any merchant (an ordinary, unprivileged internet user who installs the app on their own store) can obtain a genuinely-signed webhook body/HMAC pair from their own store's real webhook deliveries and replay it to the app's webhook endpoint with the `shop-domain`/`x-shopify-shop-domain` header rewritten to a victim shop. `HmacValidator.validate` still returns `true` because it only checks the body, and `Registry.process` then dispatches the handler with the attacker-chosen `request.shop` as the tenant identifier.

### Finding Description
`Request#hmac` and `#to_signable_string` are defined as: [1](#0-0) 

Note that `to_signable_string` returns `@raw_body` only — `topic`, `shop`, `api_version`, and `webhook_id` (all sourced from headers via `shopify_header`) are excluded from the signed content: [2](#0-1) 

`Registry.process` validates only this body-derived HMAC before dispatching to the app-registered handler using `request.shop` as the tenant key: [3](#0-2) 

`HmacValidator.validate`/`validate_signature` compute and compare the digest solely over `verifiable_query.to_signable_string`, so for a `Webhooks::Request` this is exclusively `@raw_body`: [4](#0-3) 

The binding that should hold is: **shop authenticated by the HMAC == shop used as the tenant/session key for dispatch**. Here, the HMAC only authenticates the *body*, while `request.shop` (the tenant key handed to `WebhookMetadata`/the handler) comes from an unsigned header — so the equality is broken: `hmac-authenticated content ⊄ {shop}`, yet `shop` still drives per-tenant handling.

Because `Context.api_secret_key` is the *app's* single shared secret (not a per-shop secret), any merchant who installs the app can trigger genuine webhook deliveries to themselves signed with that same shared secret. They can then capture a valid `(raw_body, hmac)` pair and resubmit it to the app's public webhook endpoint with a forged `shop-domain` header pointing at a different, victim shop. `HmacValidator.validate` accepts it because the header isn't part of the signed content.

### Impact Explanation
This breaks the tenant isolation boundary: an app relying on this gem's webhook shop field for per-tenant lookups (e.g., resolving which shop's stored session/data a webhook applies to) can be made to process attacker-supplied body content under an arbitrary victim shop identity, once HMAC validation "succeeds." This is a cross-tenant access primitive (Critical severity per the given classification) achieved without any credential beyond the ability to install the app on one's own store — a capability any unprivileged internet user with a Shopify dev/partner account has.

### Likelihood Explanation
Moderate-to-high: no secrets need to be stolen; the attacker only needs their own installation of the target app (a normal, unprivileged action) to harvest a legitimately-signed webhook, then can freely rewrite the unauthenticated `shop-domain` header before replaying it to the app's public webhook endpoint.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the material verified against the HMAC, or otherwise cryptographically/independently verify that the `shop-domain` header corresponds to a shop that is actually installed/known to the app before dispatching webhook data — do not treat `request.shop` as trusted merely because the body-only HMAC validated.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and triggers a webhook event (e.g., updates a product), receiving a real webhook POST with a valid `X-Shopify-Hmac-Sha256` computed over the raw body using the app's shared `client_secret`.
2. Attacker captures `raw_body` and the `hmac-sha256` header value from that delivery.
3. Attacker POSTs the same `raw_body` and `hmac-sha256` header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. The app calls `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` then `ShopifyAPI::Webhooks::Registry.process(request)`.
5. `Utils::HmacValidator.validate(request)` returns `true` (per [5](#0-4) ) since only `raw_body` is checked.
6. `Registry.process` invokes the registered handler with `shop: request.shop` equal to `"victim-shop.myshopify.com"` (per [6](#0-5) ), causing the app to act on attacker-controlled data under the victim shop's identity.
