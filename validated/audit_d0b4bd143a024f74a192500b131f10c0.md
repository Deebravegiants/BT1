### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant shop spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) for an incoming webhook from the `shopify-shop-domain` HTTP header, but the HMAC signature that `Utils::HmacValidator` verifies only covers the raw request body, not this header. `Registry.process` trusts `request.shop` as the authenticated tenant identity and forwards it, unchecked, to the app's webhook handler.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header, a value never included in the signed content: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` (i.e., the body only) using `Context.api_secret_key`/`old_api_secret_key`, then compares against `verifiable_query.hmac`: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` as the tenant/session identity for the webhook, passing it into `WebhookMetadata` and on to the registered handler: [4](#0-3) 

The identity binding that should hold is:
`shop used by the app to attribute the webhook == shop covered by the verified HMAC`

Because `to_signable_string` only includes `@raw_body`, this equality is broken: the HMAC proves only "this body was signed with this app's `api_secret_key`" — it proves nothing about which shop the header claims to be from. Since `api_secret_key` (the app's `client_secret`) is shared across every shop that installs the app, any shop that has legitimately installed the app (an "unprivileged" merchant relative to other tenants of the same app) can capture one of its own valid, correctly-HMAC'd webhook deliveries and replay it to the app's webhook endpoint with the `shopify-shop-domain` header rewritten to a victim shop's domain. `Utils::HmacValidator.validate` will still return `true` because the body and secret are unchanged; `Registry.process` will then hand the handler a `WebhookMetadata` claiming to be from the victim shop.

If the host application uses `WebhookMetadata#shop` (as `Registry.process` explicitly does) to select which merchant/session record to update — e.g., processing `orders/create`, `app/uninstalled`, or GDPR topics (`shop/redact`, `customers/redact`, `customers/data_request`) keyed by shop — the attacker can inject cross-tenant data or trigger destructive/administrative actions (like `shop/redact` handling) attributed to a shop they do not control, purely from the internet, with no access token or credential beyond having their own app installation.

### Impact Explanation
This crosses the "cross-tenant access" bar: an unprivileged actor who legitimately controls one tenant (their own shop's app installation) can forge webhook attribution to another tenant by exploiting a field (`shop`) that is processed by the handler but not covered by the cryptographic integrity check that gates that processing. This matches the Critical impact category of cross-tenant access via broken identity binding.

### Likelihood Explanation
Likelihood is high for any app that installs on multiple/public shops: the attacker only needs their own valid app installation (no elevated privilege) to receive one authentic, correctly signed webhook, then can replay it with a modified `shop-domain` header to the same publicly reachable webhook endpoint. No secrets, tokens, or non-public information about the victim shop are required — only the victim's shop domain, which is not secret.

### Recommendation
Include the shop domain (and topic) inside the signed material verified by HMAC, or otherwise cryptographically/authoritatively bind the header-derived `shop` to the verified payload before it is trusted (e.g., by having `Registry.process` re-derive shop identity from Shopify's own registration/session records rather than trusting the unauthenticated header verbatim). At minimum, document to consuming apps that `WebhookMetadata#shop` is not integrity-protected by the HMAC check and must not be used as a sole tenant key without additional verification (e.g., cross-checking against an installed-shop allowlist).

### Proof of Concept
1. App is installed on `attacker.myshopify.com` and `victim.myshopify.com` (both real installs of the same app, sharing one `api_secret_key`).
2. Shopify sends a legitimate webhook to the app for `attacker.myshopify.com`, with headers `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid hmac of raw_body>`.
3. Attacker captures this raw request (they control the receiving endpoint or can sniff their own traffic) and resends it to the app's webhook endpoint, only changing the header to `X-Shopify-Shop-Domain: victim.myshopify.com`; body and HMAC header are untouched.
4. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` recomputes HMAC over `@raw_body` only and it matches, since the body/secret didn't change.
5. `Registry.process` in `lib/shopify_api/webhooks/registry.rb:188-200` proceeds and calls the handler with `WebhookMetadata.new(... shop: "victim.myshopify.com" ...)`, even though the payload actually originated from the attacker's shop.

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
