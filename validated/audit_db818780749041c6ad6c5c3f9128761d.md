### Title
User-controlled swap route can execute attacker contracts and steal caller wallet tokens - ([File: contracts/controller/src/strategies/swap.rs])

### Summary
XOXNO Lending accepts caller-controlled route bytes in collateral/debt swap entrypoints and forwards them to the configured router after authorizing the exact routed input transfer. The router executes pool addresses encoded inside the route without an allowlist. A malicious pool can therefore place additional `token.transfer` calls below the caller’s authorization tree; if the caller signs the simulated authorization tree, arbitrary wallet tokens can be transferred to an attacker while the route still returns sufficient output and passes the controller’s measured-output and solvency checks. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) 

### Finding Description
`swap_collateral` accepts a `StrategySwap` supplied by the caller and passes it through `withdraw_and_swap_from_supply`. [5](#0-4)  The controller authorizes only the exact controller-to-router input-token transfer, invokes the configured router, then validates only the router’s measured spend and positive output receipt. [6](#0-5)  Neither layer constrains which contract addresses may appear as hop pools in the route payload. [7](#0-6) 

The route format is an instruction stream whose `idx_a` field selects a pool address from the caller-provided `assets` registry. [8](#0-7) [9](#0-8)  The venue dispatcher invokes that selected pool; for example, the Soroswap adapter calls `get_reserves` and then `swap` on `hop.pool`, while the Phoenix adapter invokes `hop.pool.swap` after authorizing a router input pull. [3](#0-2) [10](#0-9) 

Because the pool is arbitrary code, it can invoke an unrelated token contract as `token.transfer(victim, attacker, amount)` while execution remains underneath the caller’s controller authorization. [11](#0-10) [12](#0-11)  Simulation records this unauthorized-looking transfer as a child invocation, and an enforcing transaction executes it if that child is included in the signed authorization tree. [4](#0-3) 

The project’s own threat model documents the behavior: an unallowlisted route can place third-party code below the caller’s authorization, create an extra child transfer from the caller, and take more than the routed amount if the caller signs the resulting tree. [13](#0-12) 

### Impact Explanation
A crafted route can transfer arbitrary victim-held tokens to an attacker-controlled recipient, not merely consume the protocol-routed input. [14](#0-13) [15](#0-14)  The malicious hop can still return enough output for the lending transaction to complete: the harness demonstrates a successful collateral swap that leaves Alice with the expected ETH deposit while her entire unrelated wallet-token balance is moved to the attacker. [15](#0-14) 

This is theft of user funds rather than only bad routing or MEV: the stolen token is separate from the swap input and its transfer is introduced by code selected through the route payload. [16](#0-15) [17](#0-16) 

### Likelihood Explanation
An unprivileged victim can reach the vulnerable path through `swap_collateral(caller, account_id, current, from_amount, new, swap)`, and equivalent route-bearing paths include `swap_debt`, `repay_debt_with_collateral`, and `multiply`. [18](#0-17) [19](#0-18)  The attacker needs only to get the victim to submit a route containing the attacker’s pool and sign the simulated authorization tree containing the extra child transfer. [20](#0-19) 

The exploit does not require compromising the router, obtaining protocol privileges, bypassing balance measurements, or producing zero output. [21](#0-20) [22](#0-21)  Its likelihood is reduced because the malicious transfer is visible in an honestly displayed authorization tree, and a wallet/client that rejects unexpected child invocations prevents it. [23](#0-22)  Nevertheless, users commonly rely on opaque route bytes and simulated auth, making malicious-route submission a realistic phishing or compromised-quote path. [24](#0-23) 

### Recommendation
Restrict route pools to governance-approved venue deployments or verified pool identities for each venue before dispatching hops. If arbitrary pools remain supported by design, the controller/router should prevent route code from expanding the caller’s authorization beyond the explicitly expected input transfer; at minimum, clients must decode `StrategyPayload`, enumerate every pool/token address, simulate the transaction, and reject any authorization child other than the expected route input transfer. [13](#0-12) 

### Proof of Concept
The repository contains a working regression test that models the exact exploitation path:

1. Alice supplies USDC and holds an unrelated wallet token. [25](#0-24) 
2. The attacker deploys a route hop containing Alice’s address, the wallet token, the attacker recipient, and the amount to steal. [26](#0-25) 
3. Alice calls `try_swap_collateral` with the route. [27](#0-26) 
4. The router double calls the attacker-selected `hop_pool.swap`. [28](#0-27) 
5. The pool executes `wallet_token.transfer(alice, attacker, amount)`. [29](#0-28) 
6. Simulation records that transfer as a child under Alice’s `swap_collateral` authorization. [17](#0-16) 
7. After execution, Alice has zero wallet-token balance, the attacker has the stolen balance, and Alice still receives the expected swapped collateral. [15](#0-14)

That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's

decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap

/// Dispatches the hop to its venue-specific swap function and returns the measured increase in
/// the router's `token_out` balance. Panics with `Error::ZeroOutput` if the output balance does
/// not strictly increase, and with `Error::InvalidAmount` if the router's `token_in` balance does
/// not decrease by exactly `amount_in`.
///
/// Venue adapters return nothing: this measured delta is the only fill the router credits.
pub(crate) fn dispatch_hop(
    env: &Env,
    router: &Address,
    hop: &SwapHop,
    amount_in: i128,
    tokens_cache: &mut Map<Address, Vec<Address>>,
) -> i128 {
    let ctx = HopContext::new(env, router, hop, amount_in);
    let before_in = ctx.input_balance();
    let before_out = ctx.output_balance();

    match hop.venue {
        SwapVenue::Soroswap => soroswap::swap(&ctx),
        SwapVenue::Aquarius => aquarius::swap(&ctx, tokens_cache),
        SwapVenue::Phoenix => phoenix::swap(&ctx),
        SwapVenue::Sushi => sushi::swap(&ctx),
        SwapVenue::CometDex => comet::swap(&ctx),
    };

    let received = ctx
        .output_balance()
        .checked_sub(before_out)
        .unwrap_or_else(|| panic_with_error!(env, Error::ZeroOutput));
    if received <= 0 {
        panic_with_error!(env, Error::ZeroOutput);
    }

    let after_in = ctx.input_balance();
    let spent = before_in
        .checked_sub(after_in)
        .unwrap_or_else(|| panic_with_error!(env, Error::InvalidAmount));
    if spent != amount_in {
        panic_with_error!(env, Error::InvalidAmount);
    }

    received
}
