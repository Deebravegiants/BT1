### Title
Stale delegate authorization survives position-NFT ownership transfer, letting the prior owner's delegate drain the account - (File: contracts/controller/src/account.rs)

### Summary
The external report's bug class is: an address binding changes while dependent state computed under the old binding is left untouched. In XOXNO Lending, account ownership is the position-NFT owner, resolved live from the NFT contract (`try_account_owner`), while delegate authorizations are stored separately in controller storage under `Delegates(account_id)` keyed by account id, not by owner. When the NFT is transferred, `account.owner` effectively changes, but the delegates map is never reconciled — delegates granted under the old owner remain authorized against the new owner's account.

### Finding Description
- `process_withdraw` in `contracts/controller/src/positions/supply.rs:140-168` authorizes via `require_owner_or_delegate(env, account_id, caller, &account.owner)`, which accepts either the current NFT owner or any entry in the account's `Delegates(account_id)` storage row (`contracts/controller/src/storage/account.rs`, referenced as `ControllerKey::BorrowPositions`/`Delegates(account_id)` in `contracts/controller/tests/storage/account.rs:329-331`).
- Delegates are added/removed through governance ops (`AddDelegate`/`RemoveDelegate` in `tests/integration/flows/production.sh:276-292`), and the integration suite only asserts the *previous owner* is denied after `NftTransfer` (`production.sh:294-300`); no path clears the delegate set on transfer.
- The NFT transfer path (`position-nft` `transfer`/`approve`, exercised as `NftTransfer` op) only changes ownership; it does not iterate or purge `Delegates(account_id)`, and `renew_account`/`storage::account_from_parts` rebuild the account from the new owner plus the unchanged stored rows (`contracts/controller/src/risk/params.rs:155-178`).

This mirrors the reported defect exactly: `self.staker` moved while `liquidity.staked` stayed stale; here `account.owner` moves while `Delegates(account_id)` stays stale.

### Impact Explanation
Theft of user funds. A stale delegate retains full owner-equivalent operational authority (`withdraw`, `borrow`, position management) over the account after ownership changes. The old owner (or a compromised/malicious delegate they previously configured) can call `withdraw` on the transferred account and route collateral to `to: Some(attacker)` via `process_withdraw`'s `recipient` parameter (`supply.rs:145-157`), draining the new owner's collateral. Any NFT sale, gift, or secondary-market transfer inherits a hidden co-signer.

### Likelihood Explanation
Low-to-Medium. Requires the account to have at least one configured delegate before the NFT transfer, and a transfer to occur (market sale, wallet migration, phishing-induced transfer). Both are ordinary user behaviors; delegate-granting is a supported feature, and nothing warns the recipient that delegate rows persist.

### Recommendation
Treat delegates as owner-scoped state: either (a) clear `Delegates(account_id)` whenever the NFT owner changes (hook the transfer path or compare-and-invalidate on a stored owner snapshot), or (b) store delegates under an `(account_id, owner_epoch)` key and bump the epoch on transfer so stale grants become unreachable. At minimum, document and emit an event so integrators can detect inherited delegates.

### Proof of Concept
1. Alice owns `account_id = N` holding supplied collateral; she executes `AddDelegate{N, Mallory}` (legitimate delegate, e.g. a keeper).
2. Alice transfers the position NFT for account `N` to Bob (`NftTransfer{token_id: N, to: Bob}`). Owner resolution (`try_account_owner`) now returns Bob; `Delegates(N)` still contains Mallory.
3. Mallory calls `withdraw{caller: Mallory, account_id: N, withdrawals: [...], to: Mallory}`. `require_owner_or_delegate` passes because Mallory is in `Delegates(N)`, and collateral is paid to Mallory — funds stolen from Bob's account with no revert.

Note: I verified that delegates are keyed by `account_id` and that no transfer-side cleanup is evident in the indexed code (the production flow asserts only prior-*owner* denial, not delegate denial). I could not fully confirm the absence of a delegate-purge inside the NFT transfer hook due to index coverage; if such a purge exists, this finding collapses — otherwise it stands.
