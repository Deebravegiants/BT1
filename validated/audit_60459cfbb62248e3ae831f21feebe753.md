### Title
Webhook `shop`, `topic`, and `webhook-id` identity fields are trusted from unauthenticated headers while the HMAC only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying fields (`shop`, `topic`, `webhook_id`, `api_version`) entirely from HTTP headers that are never included in the HMAC signature computation, yet `Registry.process` dispatches these unauthenticated values directly to the app's `WebhookHandler#handle` callback as trusted tenant context.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body: [1](#0-0) 

All the tenant/routing identity fields — `shop`, `topic`, `webhook_id`, `api_version` — are read straight from headers, none of which are folded into the signable string: [2](#0-1) 

`Utils::HmacValidator.validate` verifies only that `computed_signature = HMAC(secret, to_signable_string)` matches the received `hmac`, i.e. it verifies **body bytes only**: [3](#0-2) 

`Registry.process` then calls the HMAC check and, once it passes, builds `WebhookMetadata` directly from the *unauthenticated* header-derived `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version`, handing this to the app's handler as trusted context: [4](#0-3) 

This is a broken identity binding: `verified(raw_body) ≠ verified(shop, topic, webhook_id, api_version)`. The library's own OAuth path treats this correctly by contrast — `Auth::Oauth::AuthQuery#to_signable_string` explicitly folds `shop` (along with `code`, `host`, `state`, `timestamp`) into the signed string before computing the HMAC: [5](#0-4) 

so the webhook path's omission of `shop` (and the other routing headers) from the signable string is an inconsistency within the same gem, not an unavoidable protocol constraint.

Because only the body is authenticated, anyone who can produce (or replay/observe) one valid `(raw_body, hmac)` pair — e.g., from a request that transits a shared/logging proxy, is echoed in error tracking, or is otherwise observable in transit before reaching the app (this gem does not require or validate TLS/source at this layer) — can resubmit that exact `(raw_body, hmac)` pair to the app's webhook endpoint with a **different** `shop-domain`, `topic`, or `webhook-id` header. `HmacValidator.validate` will still return `true` because it never inspected those headers, and `Registry.process` will hand the forged `shop`/`topic` straight to the app's `handle` callback as if Shopify had attested to it for that shop.

### Impact Explanation
If the consuming application (as the library's own documentation and `WebhookMetadata` struct expect) uses `data.shop` to decide which merchant's records to create/update/delete in response to a webhook, an attacker who obtains a single valid `(body, hmac)` pair can cause that payload to be processed under an **arbitrary shop domain** of their choosing, producing cross-tenant data confusion/write without possessing that shop's access token or the app's `client_secret`. This matches the Critical "cross-tenant access" category: the boundary being crossed is the tenant (shop) boundary that the HMAC is supposed to protect, and the library itself provides no additional verification (e.g. binding `shop` into the signed bytes, or validating `shop` against an expected/registered value) to prevent it.

### Likelihood Explanation
Exploitation requires the attacker to already possess one legitimate `(raw_body, hmac)` pair for *some* shop — these are not secrets by design (Shopify webhook bodies/HMACs are visible to whoever receives the request, and can leak via logging middleware, shared proxies, request-tee'ing, or misconfigured observability tooling on the receiving app's side) — after which forging the shop/topic/webhook-id headers costs nothing since the gem never checks them against the signature. This is lower likelihood than a full HMAC-key compromise but is a real, low-cost pivot from "observe one webhook" to "impersonate any shop for that webhook's body," which the report's underlying bug class (fields acted upon but not covered by the authentication check) directly maps onto.

### Recommendation
Include the tenant/routing headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signed material, or otherwise cryptographically bind them (e.g., derive an expected value and require it match a value independently established via OAuth for that shop) before constructing `WebhookMetadata` in `Registry.process`. At minimum, document prominently that `WebhookMetadata#shop`/`#topic`/`#webhook_id` are **not** authenticated by `HmacValidator` and must not be trusted for tenant-sensitive decisions without additional verification by the host application.

### Proof of Concept
```ruby
# Attacker has observed one legitimate webhook delivery for shop-a.myshopify.com:
raw_body = '{"id":123,"note":"hi"}'
hmac     = "<valid hmac captured from the legitimate request>"

# Forge headers, keeping raw_body/hmac identical, but claim a different shop/topic:
forged_headers = {
  "x-shopify-topic"       => "orders/create",   # can also be changed freely
  "x-shopify-hmac-sha256" => hmac,               # unchanged - still validates
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # attacker-controlled
  "x-shopify-webhook-id"  => "forged-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# HmacValidator.validate(request) => true, because it only checks raw_body against hmac.
# The registered handler receives WebhookMetadata(shop: "victim-shop.myshopify.com", ...)
# even though Shopify never attested this body/hmac pair for that shop.
```

        def validate(verifiable_query)

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
