### Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
### Finding Description
`ShopifyAPI::Webhooks::Request` derives `hmac` and the value to verify (`to_signable_string`) exclusively from the raw request body: [1](#0-0) [2](#0-1) 

`shop`, `topic`, `api_version`, and `webhook_id` are all read straight from HTTP headers and are **not** part of the signed string: [3](#0-2) 

`ShopifyAPI::Webhooks::Registry.process` validates the HMAC (body-only) and then immediately trusts `request.shop` to build the dispatched `WebhookMetadata`, which is handed to the app's handler as the tenant identifier: [4](#0-3) [5](#0-4) 

The identity binding that should hold is: `shop_the_HMAC_was_computed_for == shop_attributed_to_the_processed_webhook`. Because the HMAC is computed with the app's single `client_secret` (shared across *every* shop that installs the app) over the body only, that binding never actually exists in this implementation — a valid `(body, hmac)` pair says nothing about which shop it came from. The only place tenant identity is carried is the `x-shopify-shop-domain` / `shopify-shop-domain` header, which is completely outside the signed material.

### Impact Explanation
Any unprivileged user who can install the app on their own store (a normal, non-privileged action) receives real webhook deliveries for their shop with a valid HMAC (computed with the app's shared secret, not a per-shop secret). Because the shop header is unauthenticated, that user can replay the exact same raw body + HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (or `shopify-shop-domain`) header with a victim shop's domain. `Utils::HmacValidator.validate(request)` will still succeed since it only checks the body signature, and `Registry.process` will dispatch the handler with `shop: <victim-domain>` and attacker-controlled `body`. Any host application that uses `data.shop` to look up/act on a specific merchant's tenant record (the intended and documented usage of `WebhookMetadata`) will perform that action against the wrong tenant, using data the attacker fully controls. This is cross-tenant access/data injection achieved purely by an unprivileged app installer — no leaked cred or social engineering required.

### Likelihood Explanation
The vulnerability is trivial to exploit: an attacker installs the app on their own shop, captures a real webhook delivery (e.g., `orders/create`), and replays it with a modified shop header. The HMAC validation passes because the body is unchanged. The app's handler receives the attacker's order data but with the victim shop's domain, causing the host app to record/process it under the wrong tenant. This is a concrete authentication bypass that breaks the identity binding between the signed material and the tenant the webhook is attributed to.

### Recommendation
Include the `shop-domain` header in the signed string before HMAC verification. Modify `AuthQuery.to_signable_string` (which already includes `host`) to serve as a template, and update `Webhooks::Request.to_signable_string` to include the shop domain in the signed material. This ensures that a valid HMAC proves the body *and* the shop domain came from Shopify, not just the body alone.

### Proof of Concept
1. Attacker installs the app on shop `attacker.myshopify.com`.
2. Attacker triggers an order creation and captures the webhook:
   ```
   POST /webhook
   x-shopify-shop-domain: attacker.myshopify.com
   x-shopify-hmac-sha256: <valid-hmac-for-body>
   x-shopify-topic: orders/create
   
   {"id": 123, "total": "99.99", ...}
   ```
3. Attacker replays the same request but changes the header:
   ```
   POST /webhook
   x-shopify-shop-domain: victim.myshopify.com
   x-shopify-hmac-sha256: <same-valid-hmac>
   x-shopify-topic: orders/create
   
   {"id": 123, "total": "99.99", ...}
   ```
4. `Utils::HmacValidator.validate(request)` succeeds because the body and HMAC are unchanged.
5. `Registry.process` dispatches the handler with `shop: victim.myshopify.com` and the attacker's order data.
6. The host app records the attacker's order under the victim's tenant. [6](#0-5)
