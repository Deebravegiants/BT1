### Title
Orb reports signup success for user-centric signups purely from local pipeline state, bypassing the two-step backend fraud/duplicate confirmation - (File: src/plans/mod.rs)

### Summary
The H-2 report's root cause is that a multi-step verification/liquidation process leaves an exploitable window where a party can rely on locally/partially known state instead of waiting for the full, authoritative two-step process to complete, letting it claim a benefit (inflated upnl → fund theft) before the second step finishes. The closest analog in `orb-core` is in the signup-authorization flow: for `user_centric_signup` sessions, the Orb determines the final "success" of a signup entirely from its own on-device `signup_reason` (biometric pipeline result + `detect_fraud`) and skips the two-step backend confirmation (`signup_post::request` followed by `signup_poll::request` polling) that is otherwise used to catch backend-side duplicates, in-flight matches, or backend-detected fraud.

### Finding Description
In `MasterPlan::do_signup`, after biometric capture and pipeline processing, `signup_reason` is computed purely from local state (`fraud_detected`, pipeline presence): [1](#0-0) 

The Personal Custody Package (biometric data: iris codes, normalized iris images, face embeddings) is then built and uploaded to the backend unconditionally, tagged with this locally-computed `signup_reason`: [2](#0-1) 

Immediately after, for `user_centric_signup` sessions, the "success" outcome is derived solely from the local `signup_reason`, entirely skipping the two-step backend authorization flow (`enroll_user`, which performs `signup_post::request` then repeatedly polls via `signup_poll::request` for the authoritative backend verdict, including backend-detected duplicates/fraud/in-flight matches): [3](#0-2) 

The skipped path (`enroll_user`) explicitly documents that the second, backend-driven step is what catches "Backend duplicates", "Backend legacy signup requests", "Backend inflight matches", and "Backend detected fraud" — i.e., it is the authoritative second step of a two-step signup-authorization process: [4](#0-3) 

Compounding this, the on-device fraud engine used to compute `fraud_detected`/`signup_reason` in this build has all checks removed (`N_FRAUD_CHECKS = 0`, `detect_fraud` unconditionally returns `false`): [5](#0-4) [6](#0-5) 

So for `user_centric_signup` flows, "success" reduces to "did the local biometric pipeline complete", with no analog of the backend's second-step confirmation (the equivalent of `liquidatePositionsPartyB` fully finishing) ever being consulted before the Orb reports the signup as complete and successful.

### Impact Explanation
This is a signup-authorization/identity-binding analog of the H-2 bug class: relying on state from only the first of two verification steps to grant a final outcome, instead of waiting for (or querying) the authoritative second step. Concretely, for any session flagged `user_centric_signup` by the (signed) QR user data, a successful local capture is reported to the Orb operator/App as a completed, successful signup — and the biometric package has already been uploaded — without the Orb ever confirming with the backend that this signup passed uniqueness/duplicate/backend-fraud checks. This can result in misattributed or unauthorized signup completion being surfaced locally (UI, dbus `signup_finished` signal, `SignupEnded` relay message) even where the backend would ultimately reject the enrollment, and it does so after biometric data has already left the device.

### Likelihood Explanation
`user_centric_signup` is a legitimate, backend-signed flag on the user QR data (verified via `user_data.verify(user_data_hash)`), so triggering this path does not require compromising any signature checks — any app-driven signup flagged this way by the backend takes this code path by design. No orb-local fraud checks exist in this build to make up for the missing backend confirmation step, so the "local success" reported for this flow is unconditionally trusted.

### Recommendation
For `user_centric_signup` sessions, do not report final "success" (UI completion, dbus signal, relay `SignupEnded`) based solely on the locally computed `signup_reason`. Route these signups through the same two-step backend-confirmation mechanism used by `enroll_user` (`signup_post` + `signup_poll`), or otherwise block/queue completion notifications until an explicit backend acknowledgment of uniqueness/fraud status is received, mirroring the intended fix for the H-2 report of not trusting intermediate/local state before the authoritative second step of a two-step verification process concludes.

### Proof of Concept
1. Present a user QR code whose signed `authenticated_app_data` sets `user_centric_signup: true` (a supported, backend-issued flag): [7](#0-6) 
2. Complete biometric capture; because `detect_fraud` always returns `false` in this build, `signup_reason` becomes `SignupReason::Normal` as long as the pipeline itself produced output: [8](#0-7) 
3. The PCP (iris codes, images) is uploaded to the backend regardless of what happens next: [2](#0-1) 
4. Because `user_centric_signup` is true, `do_signup` sets `success = signup_reason == SignupReason::Normal` directly, without ever calling `enroll_user`/`signup_post`/`signup_poll` — i.e., without asking the backend whether it detected this signup as a duplicate or fraudulent: [3](#0-2) 
5. The Orb reports `signup_finished(success=true)` over dbus and (in self-serve mode) sends `SignupEnded { success: true }` over the relay, even though the backend's two-step fraud/duplicate confirmation for this signup was never performed by the Orb.
