### Title
Webhook shop-domain, topic and webhook-id headers are trusted without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook delivery solely by checking the HMAC over the raw request body, then dispatches the parsed body to the app's handler tagged with `shop`, `topic`, `webhook_id`, and `api_version` values taken directly from HTTP headers that are **not** part of the signed payload.

### Finding Description
`Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

`hmac` is computed from the `shopify-hmac-sha256`/`x-shopify-hmac-sha256` header, and `shop`, `topic`, `webhook_id`, `api_version` are all read from separate, unsigned headers: [2](#0-1) 

`Registry.process` validates the HMAC of the body only, then trusts the header-derived `shop`, `topic`, `webhook_id`, and `api_version` fields when constructing the metadata passed to the app-defined handler: [3](#0-2) 

`Utils::HmacValidator.validate` confirms only that `verifiable_query.to_signable_string` (the raw body) was signed with `Context.api_secret_key`; it never binds the signature to `shop`, `topic`, or `webhook_id`: [4](#0-3) 

The identity binding that is broken is: `shop authenticated by HMAC (over body) == shop delivered to the handler (from an unsigned header)`. Since the webhook endpoint is a public route exposed by the host app, and the `api_secret_key` used to compute the HMAC is a single value shared across every merchant that has installed the app (it is not per-shop), any merchant that installs the app can legitimately trigger real events (e.g. by creating a customer, order, or updating shop settings in their own store) and receive genuine `(raw_body, hmac)` pairs signed with the app's shared secret. That merchant — an otherwise unprivileged internet user with respect to any other tenant of the app — can then replay that exact `(raw_body, hmac)` pair to the app's public webhook endpoint while forging the `shopify-shop-domain` header (and, where the body schema is compatible, the `shopify-topic` header) to name a **different, victim shop**. `Registry.process` will pass the HMAC check (the body and its real hmac are unmodified) and hand the handler a `WebhookMetadata` claiming the victim shop's identity, with attacker-controlled body content.

### Impact Explanation
This breaks the cross-tenant boundary the gem is supposed to enforce for webhook processing: the HMAC is advertised as proof that data for a given webhook "belongs" to the shop it is delivered for, but the gem never cryptographically ties the signed bytes to the `shop`/`topic` claims it also exposes and that handlers are expected to trust (`WebhookMetadata#shop`, `#topic`). A host application built on the documented `Registry.add_handler` / `Registry.process` API and following the gem's own metadata contract (which is the only contract this gem provides for webhook shop identity) will store or act on attacker-controlled data under another tenant's identity — e.g. writing fabricated order/customer/GDPR-request data into the victim shop's records, or invoking handler logic (uninstall/data-erasure/compliance topics) against a shop that never sent the event. This is a cross-tenant data-integrity/data-injection issue rooted entirely in this gem's trust model, not in host-app misuse.

### Likelihood Explanation
Reaching this requires only that the attacker be a legitimate merchant who has installed the target app (a normal, unprivileged capability — no leaked secrets, no privileged account, and no access to another tenant's credentials are needed) and that they can reach the app's public webhook receiving endpoint, which is by design internet-reachable. No man-in-the-middle or credential theft is required; the attacker uses their own genuine webhook deliveries.

### Recommendation
Bind the identity fields to the signed payload before trusting them: either include `shop`, `topic`, and `webhook_id` in the HMAC-signed material (as Shopify does not currently sign these, this would require app-level allow-listing), or — at minimum — have `Registry.process`/`WebhookMetadata` cross-check the header-derived `shop` against the set of shops that have an active, previously-established session/installation record for this app before dispatching to the handler, and document to consumers that `WebhookMetadata#shop` is unauthenticated on its own and must be revalidated against known installed shops.

### Proof of Concept
1. Malicious merchant `attacker-shop.myshopify.com` installs the target app and triggers a real event (e.g., updates a customer record) that the app is subscribed to.
2. Shopify delivers a legitimate webhook to the app's endpoint with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: customers/update`, `x-shopify-hmac-sha256: <valid HMAC over raw_body>`, and a body fully controlled by the attacker via the customer fields they set.
3. Attacker captures this exact `(raw_body, hmac)` pair.
4. Attacker replays the identical request to the same public webhook endpoint, but changes only the header `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:189-190`) calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks the (unchanged) raw body against the hmac.
6. The handler is invoked with `WebhookMetadata.new(topic: "customers/update", shop: "victim-shop.myshopify.com", body: <attacker-controlled body>, ...)`, causing the host app to process attacker-controlled data as if it originated from `victim-shop.myshopify.com`.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
