### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant impersonation of webhook events - (File: lib/shopify_api/webhooks/request.rb)

### Summary
The `TwapOracle` bug involves a calculation acting on the wrong field entirely, producing incorrect trust in a value that feeds a critical downstream mechanism (minting). The analogous defect in this gem is in `ShopifyAPI::Webhooks::Request` and `ShopifyAPI::Webhooks::Registry`: the HMAC signature that authenticates an inbound webhook only covers the raw request body [1](#0-0) , while the `shop` value that is trusted and forwarded to the app's handler is read from an unauthenticated HTTP header [2](#0-1) .

### Finding Description
`Registry.process` validates the webhook exclusively via `Utils::HmacValidator.validate(request)` [3](#0-2) , and `HmacValidator` computes/verifies the signature over `to_signable_string`, which for `Request` is simply `@raw_body` [1](#0-0) [4](#0-3) . The `shop`, `topic`, `api_version`, and `webhook_id` values are all pulled from HTTP headers that are not part of the signed content [5](#0-4) . After HMAC validation succeeds, `process` builds `WebhookMetadata` directly from `request.shop` (the unauthenticated header) and dispatches it to the app's handler [6](#0-5) .

The identity binding that should hold is: `shop_that_produced_the_signed_body == shop_trusted_by_the_handler`. Before the request, Shopify computes HMAC over `(body)` using the app's shared secret for a specific shop's event. After the gem's processing, the equality is broken because the gem swaps in a `shop-domain` header value that was never part of what was signed — an attacker who possesses one *valid, real* signed webhook (trivially obtainable by installing the target app on their own free/dev store and triggering an event) can replay that exact `body` + `hmac` pair while substituting the `shop-domain` header for any victim shop domain. `HmacValidator.validate` will still return true because it only re-computes the HMAC over `@raw_body`, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the event came from the victim shop [7](#0-6) .

### Impact Explanation
This is a cross-tenant identity spoofing vector: an unprivileged internet user (any developer able to install the target app on their own store, which requires no privileged credentials, access tokens, or `client_secret`) can forge webhook deliveries that appear to originate from an arbitrary victim shop domain, because the `shop` field the app relies on for tenant scoping is not bound to the cryptographic proof of authenticity. Depending on the host application's webhook handler, this can drive cross-tenant state changes, data corruption, or unauthorized actions attributed to a victim shop — consistent with the "Critical - cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high: the attacker only needs a free/dev Shopify store with the app installed to receive one legitimately signed webhook, then can replay it with an arbitrary `shop-domain` header value against the app's public webhook endpoint. No secret material, session, or elevated privilege is required — only the ability to intercept/replay their own webhook traffic to the app they control.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the value that is authenticated, rather than trusting an unsigned header. At minimum, `Request#to_signable_string` (or the `HmacValidator` verification step) should incorporate the `shop-domain` header alongside the raw body so that spoofing the header invalidates the signature, matching Shopify's actual webhook contract where the signature is meant to authenticate the specific delivery. Alternatively, cross-check the header's `shop` against the shop embedded in the JSON body (when present) before trusting it, and document/enforce that host apps must additionally verify the receiving endpoint's expected shop before acting on `WebhookMetadata#shop`.

### Proof of Concept
1. Attacker creates a Shopify development store, installs the target app, and configures a webhook subscription (e.g. `orders/create`) pointing at the app's public webhook endpoint.
2. Attacker triggers the event on their own store; Shopify sends a request with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid-hmac-of-body>`, and some JSON body, signed with the app's real `api_secret_key`.
3. Attacker captures this request and replays it to the same endpoint, changing only the `x-shopify-shop-domain` header to `victim-shop.myshopify.com` (leaving `raw_body` and `hmac` unchanged).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (`@raw_body` only) and succeeds because the body is untouched [3](#0-2) [1](#0-0) .
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` [6](#0-5) , causing the host app to process a forged event as if it came from the victim tenant.
