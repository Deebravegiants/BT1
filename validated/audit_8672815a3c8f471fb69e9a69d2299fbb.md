### Title
`update_token`'s reverse-lookup cleanup deletes `ContractToAsset` unconditionally, letting one asset's chain removal unmap another asset's routing entry that shares the same contract address - ([File: modules/pallets/hyper-fungible-token/src/lib.rs])

### Summary
`pallet-hyper-fungible-token` keeps a forward map `TokenContracts: (StateMachine, AssetId) -> contract bytes` and a reverse map `ContractToAsset: (StateMachine, contract bytes) -> AssetId` used by `on_accept` to route an incoming message from a peer EVM contract back to the correct local asset. In `update_token`, whenever a chain is removed (or re-pointed) from an asset's configuration, the pallet deletes `ContractToAsset::<T>::remove(chain, old_contract)` unconditionally, without checking whether that `(chain, old_contract)` entry currently still belongs to the asset being modified. This is structurally the same class of bug as the Rio `RioLRTAVSRegistry` issue: a shared keyed resource (the reverse map keyed by `(chain, contract)`) is toggled off as a side effect of managing one entity, with no verification that the resource is still exclusively "owned" by that entity.

### Finding Description
`TokenContracts` and `ContractToAsset` are declared at [1](#0-0) . Nothing in `register_token`/`update_token` enforces that a given `(chain, contract)` pair is unique across assets — governance (`CreateOrigin`) can register or update two different `AssetId`s that point to the same on-chain contract address for the same `StateMachine` (e.g. during a contract migration where an old asset's chain config is updated before the previous asset pointing at the same address is cleaned up, or where two assets are intentionally routed through a shared proxy/gateway contract on the destination chain).

In `update_token`, both the `add_chains` and `remove_chains` loops read the *current* `TokenContracts` entry for the asset being updated and then blindly delete the reverse-mapping key derived from it: [2](#0-1) [3](#0-2) 

If `ContractToAsset::(chain, old_contract)` has since been re-pointed to a *different* asset (because that other asset's `register_token`/`update_token` call inserted the same `(chain, contract)` key afterward — last-write-wins, with no ownership check before overwrite or delete), then updating/removing chains for the *first* asset silently deletes the routing entry that `on_accept` needs for the *second, still-active* asset. This mirrors the Rio bug precisely: deactivating/reconfiguring entity A collaterally deactivates a shared resource (the reverse map entry) that entity B still depends on, because the code assumes 1:1 exclusive ownership of the shared key that is never actually enforced.

### Impact Explanation
Once the reverse mapping for the surviving asset is deleted, `on_accept`'s lookup via `ContractToAsset` for that `(chain, contract)` pair fails, so legitimate inbound `Send` messages from the peer contract can no longer be routed to the correct local asset (`UnregisteredAsset`/lookup failure). Because the corresponding tokens were already burned or escrowed on the source/EVM side before dispatch, and the destination-side accounting can no longer resolve the asset to mint/release funds to the beneficiary, this results in permanent freezing of the bridged funds for that route until governance manually re-registers the mapping (and even then, historical in-flight messages referencing the deleted mapping cannot settle correctly). This satisfies the "concrete... permanent freezing of funds" bar in the validation rules.

### Likelihood Explanation
Triggering this requires two governance (`CreateOrigin`) actions that register/update chain-contract pairs sharing the same address for two different assets, followed by a normal `update_token` chain-removal/re-pointing call on one of them. It is not a malicious-admin scenario (no single privileged party intends harm) — it is a plausible, ordinary operational sequence (contract redeploys, proxy reuse, migrating an asset to a new address that a different asset previously used) that any operator running multiple bridged assets on the same destination chain could hit unintentionally, exactly as in the referenced report where deactivating one AVS's shared slashing/registry contract silently broke other active AVSs.

### Recommendation
Before deleting a `ContractToAsset` entry in `update_token` (or overwriting it in the add path), verify that the entry currently maps back to the asset being modified:
```rust
if let Some(old_contract) = TokenContracts::<T>::get(chain, update.asset_id.clone()) {
    if ContractToAsset::<T>::get(chain, &old_contract) == Some(update.asset_id.clone()) {
        ContractToAsset::<T>::remove(chain, old_contract);
    }
}
```
Additionally, consider rejecting `register_token`/`update_token` calls that would set a `(chain, contract)` pair already claimed by a different `AssetId`, so the reverse map is never silently reassigned across assets in the first place.

### Proof of Concept
1. Governance calls `register_token` for `asset_id = A` with `chains = { Evm(1): contract = 0xCCCC }`. This sets `TokenContracts(Evm(1), A) = 0xCCCC` and `ContractToAsset(Evm(1), 0xCCCC) = A` (per [4](#0-3) , mirrored in `register_token`).
2. Governance later calls `register_token`/`update_token` for a different `asset_id = B`, also configuring `Evm(1): contract = 0xCCCC` (e.g., reusing the same gateway/proxy contract). This overwrites `ContractToAsset(Evm(1), 0xCCCC) = B`, while `TokenContracts(Evm(1), A)` still equals `0xCCCC`.
3. An ordinary bridge user sends tokens for asset `B` through `send()`; the peer EVM contract at `0xCCCC` dispatches inbound `Send` messages destined for `B`, correctly resolved via `ContractToAsset(Evm(1), 0xCCCC) = B`.
4. Governance now calls `update_token` to remove `Evm(1)` from asset `A`'s configuration (unrelated maintenance on `A`). `TokenContracts::get(Evm(1), A)` still returns `0xCCCC`, so the code executes `ContractToAsset::remove(Evm(1), 0xCCCC)` — deleting the entry that actually serves asset `B`.
5. Any subsequent inbound message from `0xCCCC` on `Evm(1)` for asset `B` now fails to resolve in `on_accept`, and funds already burned/escrowed on the source side for `B` cannot be credited to the beneficiary — a de facto freeze of the bridged funds for that route.
