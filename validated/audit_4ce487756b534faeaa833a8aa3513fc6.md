Confirmed: `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `shop` is read directly from the unsigned `shop-domain` header [2](#0-1) . `Registry.process` validates the HMAC over the body only, then forwards `request.shop` straight into `WebhookMetadata` for the handler without any cross-check [3](#0-2) .

### Title
Webhook tenant identity (`shop-domain` header) is not covered by HMAC, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only. The `shop-domain` header, which the gem uses as the tenant-identifying field passed to webhook handlers, is never included in the signed material. Any party capable of producing one genuinely-signed webhook request (i.e., a merchant who has installed the app themselves) can replay that exact body/HMAC pair while substituting an arbitrary `shop-domain` header, and the gem will accept it as valid and hand it to the handler as if it came from a different shop.

### Finding Description
`Utils::HmacValidator.validate` verifies `HMAC(secret, to_signable_string)` against the `hmac` field of a `VerifiableQuery` [4](#0-3) . For webhook requests, `to_signable_string` is defined as just the raw body:

```ruby
sig { override.returns(String) }
def to_signable_string
  @raw_body
end
``` [1](#0-0) 

Meanwhile `shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, with no relationship to the signed bytes:
```ruby
sig { returns(String) }
def shop
  T.cast(shopify_header("shop-domain"), String)
end
``` [2](#0-1) 

`Registry.process` only checks the HMAC, then forwards `request.shop` into `WebhookMetadata` unmodified:
```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
``` [3](#0-2) 

This is exactly the identity-binding break named in the report's bug class: "a field acted on but not covered by the HMAC." The equality that should hold is:
`shop bound by signature == shop used for tenant attribution`
but instead the gem only guarantees:
`HMAC(secret, raw_body) == received_hmac`
with `shop` entirely unauthenticated.

An unprivileged internet user who has installed the app on their own shop (Shop A) receives genuine Shopify webhooks with a valid HMAC computed over some body `B`. Since the signature covers only `B` and not the `shop-domain` header, that same `(B, HMAC)` pair remains valid regardless of which `shop-domain` value accompanies it. The attacker can therefore submit a request directly to the app's webhook endpoint with the original valid body/HMAC but an arbitrary `shop-domain` header value (e.g., Shop B's domain), and `Registry.process` will accept it and dispatch `WebhookMetadata` claiming the event originated from Shop B.

### Impact Explanation
This crosses a tenant boundary: it lets one merchant/attacker inject webhook data that is attributed to a shop they do not control, with a validly-passing HMAC check. Depending on how a host application keys its business logic off `WebhookMetadata#shop` (e.g., updating that shop's stored records, billing, or provisioning state), this enables cross-tenant data corruption or confusion — matching the "cross-tenant access" Critical-impact category, since the forged identity field is the sole tenant key propagated by the gem's webhook API.

### Likelihood Explanation
Exploitability only requires that the attacker be able to install the app themselves (an unprivileged, publicly available action for any Shopify merchant) to obtain one legitimately HMAC-signed webhook body, then replay it directly to the app's public webhook HTTP endpoint with a modified `shop-domain` header. No access to `api_secret_key`, TLS interception, or the victim's credentials is required, since the signature never binds the shop value in the first place.

### Recommendation
Bind the tenant identity into the verified signature material, or otherwise authenticate `shop-domain` before trusting it: e.g., include the `shop-domain` (and other identifying headers like `webhook-id`/`topic`) in `to_signable_string` so they are covered by the existing HMAC, or require host applications to cross-check `request.shop` against a store of shops that have completed OAuth for this app before dispatching to handlers, rejecting any shop value not already known to be installed.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and receives a legitimate webhook `POST` from Shopify with body `{}` and header `shopify-hmac-sha256: <valid HMAC of "{}">`.
2. Attacker resends this exact `raw_body`/`hmac` pair directly to the app's webhook endpoint, replacing the `shopify-shop-domain` header with `victim-shop.myshopify.com`:
   ```ruby
   headers = {
     "shopify-topic" => "orders/create",
     "shopify-hmac-sha256" => "<same valid signature, unchanged>",
     "shopify-shop-domain" => "victim-shop.myshopify.com",
   }
   request = ShopifyAPI::Webhooks::Request.new(raw_body: "{}", headers: headers)
   ShopifyAPI::Webhooks::Registry.process(request)
   ```
3. `Utils::HmacValidator.validate` succeeds because it only checks `"{}"` against the signature [5](#0-4) ; the handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` even though the request never touched Shopify's infrastructure for that shop.
