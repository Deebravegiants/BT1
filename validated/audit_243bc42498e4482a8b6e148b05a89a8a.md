### Title
Attacker-crafted swap route executes arbitrary contract code beneath the caller's authorization tree, draining wallet funds beyond the routed amount - (File: contracts/controller/src/strategies/swap.rs)

### Summary
Analog of CVE-2021-34427 (unauthenticated parameter-driven code injection/RCE): the controller's strategy entrypoints (`multiply`, `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`) accept caller-supplied `swap: Bytes` and hand them to the configured router, which dispatches each hop to the pool/token contract addresses the payload names — with no venue allowlist. An attacker who gets a victim to sign a poisoned route runs attacker-deployed contract code inside the victim's authorized call stack, and that code can issue `token.transfer(victim, attacker, X)` on any token the victim holds. Soroban simulation records that transfer as a child of the victim's `swap_collateral`/strategy auth entry, so once the victim signs the simulated tree, the rogue transfer executes. The protocol's own threat model and harness test confirm the behavior end-to-end.

### Finding Description
`swap_tokens` in `contracts/controller/src/strategies/swap.rs` takes the user-supplied `swap` bytes, performs `authorize_transfer_as_current` for exactly `amount_in` of `token_in` to the router, and calls `router.execute_strategy(&controller, &amount_in, swap)` under the flash guard [1](#0-0) . Neither the controller nor the router restricts which contract addresses the route may name as venues: the router "calls the pool and token addresses its payload names and keeps no allowlist of them," so a route can put third-party code on the call stack below the caller's authorization [2](#0-1) . The venue dispatcher invokes the payload-selected pool and only measures the router's own balance deltas afterward [3](#0-2) . During that hop, attacker code runs while the caller's `require_auth` entry is active; any `token.transfer(caller, attacker, amount)` it issues joins the caller's recorded auth tree, and "it executes if the caller signs that tree. The loss is then the caller's wallet, not the routed amount, and neither the payload minimum nor the final risk gate bounds it" [4](#0-3) .

The harness test `rogue_hop_pool_transfer_joins_caller_auth_tree` demonstrates this concretely: an `UnlistedPoolRouter`-style route through an attacker-registered `RogueHopPool` whose `swap` calls `token.transfer(alice, attacker, WALLET_BALANCE)` on an unrelated wallet token [5](#0-4) ; simulation records the theft under Alice's `swap_collateral` entry and the wallet is drained to zero while she receives fair swap output [6](#0-5) ; in enforcing mode the signed poisoned tree executes the theft [7](#0-6) .

### Impact Explanation
Theft of user funds: the victim loses tokens from their wallet far beyond the `amount_in` the strategy was meant to spend — in the test, the victim's entire 77,770-unit balance of an unlisted token is transferred to the attacker while the swap itself settles correctly and all protocol-side checks (input spend bound, positive measured output, final account risk) pass [8](#0-7) . Because routes are produced off-chain (quote service / UI) and signed via `simulateTransaction`, the auth tree the wallet presents is generated by simulation and the extra child entry is recorded automatically; a user who does not decode and audit the signed authorization tree silently authorizes the theft [9](#0-8) .

### Likelihood Explanation
Exploitation requires the victim to sign a poisoned route — i.e., a malicious or compromised route source (quote response, phishing UI, or injected `swap` bytes for a contract caller that forwards user-supplied bytes). There is no on-chain barrier: any address may call `swap_collateral`/`swap_debt`/`repay_debt_with_collateral`/`multiply` on its own account with arbitrary `swap` bytes, and the venue addresses inside are never validated [10](#0-9) . The exploit needs no capital and no privileged role; the only mitigation is client-side route decoding, which is documented as the integrator's responsibility rather than enforced [11](#0-10) . Medium-high likelihood for users consuming routes from any source other than a fully trusted quoter; severity on impact is High/Critical since arbitrary wallet assets are at stake.

### Recommendation
Enforce a venue allowlist on-chain: governance should maintain a set of approved pool/factory addresses per venue, and the router's `dispatch_hop` should reject hops whose pool address is not registered. Additionally, the controller could constrain acceptable `swap` payloads (e.g., require routes whose terminal `token_in`/`token_out` and venue set come from a governance-approved registry). Until venue allowlisting exists, every client must implement the documented verification — decode the route, confirm all venue addresses are known DEX pools, and reject any signed auth tree whose children include anything beyond the single expected input `transfer` [12](#0-11) .

### Proof of Concept
See `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`:

1. Attacker deploys `RogueHopPool`, whose `swap()` reads a stored plan and calls `token::Client::transfer(victim, attacker, amount)` on an arbitrary wallet token [13](#0-12) .
2. A route naming that contract as its hop pool is encoded and passed to `controller.swap_collateral(alice, account_id, usdc, amount, eth, route)` [14](#0-13) .
3. `simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry` proves recording mode attaches `wallet_token.transfer(alice, attacker, WALLET_BALANCE)` as a child of Alice's `swap_collateral` auth entry, and the wallet drains to 0 while Alice receives the fair ETH output [15](#0-14) .
4. `enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer` proves that signing the simulation-produced tree makes the theft execute in enforcing mode [7](#0-6) .

#[test]
fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
}
