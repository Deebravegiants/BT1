### Title
Multisig transaction payload verification can be fully bypassed when `abort_if_multisig_payload_mismatch` is disabled, letting an executing owner run an unapproved payload - (File: `aptos-move/framework/aptos-framework/sources/multisig_account.move`)

### Summary
The external report's root cause is a validation function that only checks a caller-supplied value against on-chain state when that state is non-default; when the on-chain state is the "empty" sentinel, any supplied value is accepted. `LienToken.validateStack` only compared `stack` to `stateHash` when `stateHash != 0`. The Aptos-native analog is `multisig_account::validate_multisig_transaction`, which is meant to guarantee that the payload actually executed on-chain matches the payload that owners voted to approve, but the equality check against the on-chain stored full payload only fires under an extra, independently-gated condition (`features::abort_if_multisig_payload_mismatch_enabled()`), and the hash-based check only fires when a `payload_hash` was chosen at creation time instead of a full `payload`. When neither guard is active, `validate_multisig_transaction` behaves exactly like the vulnerable `validateStack` with `stateHash == 0`: it accepts whatever payload the executor passes in as "matching," even though it never actually checked it against the approved transaction.

### Finding Description
`validate_multisig_transaction` is invoked by the VM prologue (`aptos-move/aptos-vm/src/transaction_validation.rs::run_multisig_prologue`) with the `provided_payload`, which is derived directly from whatever `TransactionExecutableRef` the transaction *sender* put in their transaction — not from the vote records: [1](#0-0) 

Inside `validate_multisig_transaction`, there are exactly two possible equality checks against the approved transaction, and both are conditional:

```
if (transaction.payload_hash.is_some()) {
    assert!(sha3_256(payload) == *payload_hash, ...);
};

if (features::abort_if_multisig_payload_mismatch_enabled()
    && transaction.payload.is_some()
    && !payload.is_empty()
) {
    assert!(payload == *stored_payload, ...);
}
``` [2](#0-1) 

Owners can create a multisig transaction with a full `payload` on-chain (no `payload_hash`) via `create_transaction`, which sets `payload_hash: option::none()`: [3](#0-2) 

For such a transaction, `transaction.payload_hash.is_some()` is `false`, so the first check is skipped entirely. The second check — the only remaining safeguard that the payload the executor supplies actually equals the payload the owners approved — only runs when the feature flag `abort_if_multisig_payload_mismatch_enabled` is turned on. If that feature is not enabled, the condition short-circuits to `false` and the `assert!(payload == *stored_payload, ...)` never executes, regardless of what payload the executing owner supplies at execution time.

This is structurally identical to the reported bug: a state-matching invariant ("provided value must equal recorded value") is enforced only when an auxiliary condition holds (`stateHash != 0` in the Solidity report; feature flag enabled / `payload_hash` present here), and is silently skipped otherwise, at which point *any* caller-supplied value is treated as valid.

### Impact Explanation
The multisig account is a custody primitive: it holds APT/fungible-asset balances, controls resource accounts, and can hold ownership/authority over objects. `validate_multisig_transaction`'s payload check exists specifically to guarantee that the transaction executed with the multisig account's signer authority is the one that other owners actually voted to approve. If the equality check against `transaction.payload` is skipped (feature disabled and a `payload_hash`-less transaction was used), any single owner who can reach quorum/timelock conditions can substitute an arbitrary entry function call for the one that was actually approved, and it will execute with full multisig signer authority. This breaks the core custody invariant of the multisig (owner votes bind execution to a specific payload) and can be used to drain funds or reassign control of resources/objects owned by the multisig account, with no cryptographic or economic barrier beyond reaching the approval quorum for *some* transaction.

### Likelihood Explanation
Exploitation requires: (1) the multisig transaction was created via `create_transaction` (full on-chain payload, the common/no-extra-effort path) rather than `create_transaction_with_hash`, and (2) `abort_if_multisig_payload_mismatch_enabled` is not active for the account's execution context. I could not verify from the indexed code whether this feature flag is enabled by default on current mainnet — its existence as an explicitly gated flag (rather than the check being unconditional) suggests it was added later to close this exact gap, implying it may historically have been (or still could be) off in some deployments/environments. This dependency on feature-flag state is the main source of uncertainty, and should be confirmed via a live Devin session against actual on-chain feature-flag state before treating this as an active, exploitable-today issue.

### Recommendation
Make the payload-matches-approved-payload check unconditional and independent of the feature flag whenever `transaction.payload` is present, mirroring how the `payload_hash` check is unconditional whenever a hash is present:
```move
if (transaction.payload.is_some()) {
    let stored_payload = transaction.payload.borrow();
    assert!(payload == *stored_payload, error::invalid_argument(EPAYLOAD_DOES_NOT_MATCH));
};
```
Remove the `features::abort_if_multisig_payload_mismatch_enabled()` and `!payload.is_empty()` gating so this invariant always holds, closing the "empty/disabled-state accepts anything" gap analogous to the `validateStack` fix in the original report (which added an explicit revert for the previously-unchecked case rather than leaving it conditionally skippable).

### Proof of Concept
1. Owners A, B, C create a multisig account requiring 2-of-3 approvals.
2. Owner A calls `create_transaction` with a benign payload, e.g. `aptos_account::transfer(recipient_multisig, 10)`, which is stored fully on-chain (`payload_hash = none`).
3. Owner B reviews and approves the benign transfer via `approve_transaction`.
4. Assume `abort_if_multisig_payload_mismatch_enabled` is not active. Owner A (or any owner who can reach quorum, e.g. by using their own implicit approval plus B's) submits the actual execution transaction with a *different* executable, e.g. `aptos_account::transfer(attacker_address, entire_balance)`, or a call that reassigns object/resource-account ownership.
5. `run_multisig_prologue` computes `provided_payload` from this different executable and calls `validate_multisig_transaction`. Since `transaction.payload_hash.is_none()` (skips check 1) and the feature flag is disabled (skips check 2), no assertion compares `provided_payload` to the approved `transaction.payload`.
6. The VM proceeds to execute the attacker-chosen payload with the multisig account's signer authority, draining funds/reassigning ownership despite only the benign transaction having received quorum approval. [2](#0-1) [4](#0-3)

    module_storage: &impl ModuleStorage,
    txn_data: &TransactionMetadata,
    executable: TransactionExecutableRef,
    multisig_address: AccountAddress,
    features: &Features,
    log_context: &AdapterLogSchema,
    traversal_context: &mut TraversalContext,
) -> Result<(), VMStatus> {
    let unreachable_error = VMStatus::error(StatusCode::UNREACHABLE, None);
    // Note[Orderless]: Earlier the `provided_payload` was being calculated as bcs::to_bytes(MultisigTransactionPayload::EntryFunction(entry_function)).
    // So, converting the executable to this format.
    let provided_payload = match executable {
        TransactionExecutableRef::EntryFunction(entry_function) => bcs::to_bytes(
            &MultisigTransactionPayload::EntryFunction(entry_function.clone()),
        )
        .map_err(|_| unreachable_error.clone())?,
        TransactionExecutableRef::Empty => {
            if features.is_abort_if_multisig_payload_mismatch_enabled() {
                vec![]
            } else {
                bcs::to_bytes::<Vec<u8>>(&vec![]).map_err(|_| unreachable_error.clone())?
            }
        },
        TransactionExecutableRef::Script(script) => {
            if !features.is_multisig_script_enabled() {
                return Err(VMStatus::error(
                    StatusCode::FEATURE_UNDER_GATING,
                    Some("Multisig script payload is not enabled".to_string()),
                ));
            }
            bcs::to_bytes(&MultisigTransactionPayload::Script(script.clone()))
                .map_err(|_| unreachable_error.clone())?
        },
        TransactionExecutableRef::Encrypted => {
            return Err(VMStatus::error(
                StatusCode::FEATURE_UNDER_GATING,
                Some("Encrypted payload not supported for multisig transactions".to_string()),
            ));
        },
    };
