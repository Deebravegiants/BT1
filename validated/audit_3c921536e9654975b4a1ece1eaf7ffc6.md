Found the identity binding break: in `Webhooks::Request`, the HMAC signature covers only the raw request body, while the `shop` field used to identify the tenant (and the `topic`) is taken from HTTP headers that are entirely outside the HMAC-signed bytes.

### Title
Webhook tenant identity (`shop`) is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` verifies webhook authenticity by HMAC-signing only `@raw_body` [1](#0-0) , while the `shop` (tenant identity used by the host app to look up the correct session/access token) is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, which is never part of the signed material [2](#0-1) .

### Finding Description
The equality this HMAC check is supposed to guarantee is:
`hmac_valid(body) == true` implies `(topic, shop) as claimed by headers == (topic, shop) that Shopify actually sent`.

That equality does not hold. `HmacValidator.validate` only calls `to_signable_string`, which for `Webhooks::Request` returns `@raw_body` verbatim [1](#0-0)  and [3](#0-2) . The `shop` accessor used by consuming apps to route the webhook to the correct merchant/session is derived purely from `@headers["shopify-shop-domain"]` [2](#0-1) , with no cryptographic binding to the signed body at all. An unprivileged attacker who has captured (or replayed) one legitimately-signed webhook body for their own shop can send an identical HTTP request but replace the `X-Shopify-Shop-Domain` header value with a victim shop's domain; `HmacValidator.validate` still passes because it only checks the body bytes, and the gem hands the caller a `Request` object whose `.shop` now falsely claims to be the victim tenant. Any host application that trusts `.shop` (as the docs instruct ) to select which merchant's session/access token to act on will be cross-tenant confused into acting on the wrong shop's data with a validly-verified webhook.

### Impact Explanation
This breaks a tenant/session identity binding at exactly the boundary the rules call out: "a field acted on but not covered by the HMAC." A validly-signed request for shop A can be relabeled as belonging to shop B, which is a cross-tenant access primitive (Critical) once a host app uses `Request#shop` (as recommended) to select the merchant session to which the webhook payload is applied.

### Likelihood Explanation
Requires only network-level replay of a previously observed (or self-generated, for the attacker's own installed shop) webhook body with a modified header — no credentials, access token, or `client_secret` needed, and no reliance on the host app ignoring documented behavior; the gem itself never binds `shop` to the signed bytes.

### Recommendation
Include the `shop-domain` (and `topic`, `webhook-id`) header values in the signed material, or otherwise cryptographically bind them to the payload, e.g. change `to_signable_string` to fold in `shop`, `topic`, and `webhook_id` so `HmacValidator.validate` fails if any of those headers are altered independent of the body.

### Proof of Concept
1. App receives a legitimate webhook for `attacker-shop.myshopify.com` with body `B` and header `X-Shopify-Hmac-Sha256: H` where `H = HMAC(secret, B)`.
2. Attacker resends the exact same HTTP request but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`, keeping body `B` and header `H` unchanged.
3. Host app calls `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: headers)` then `ShopifyAPI::Utils::HmacValidator.validate(request)`, per [4](#0-3)  and [5](#0-4)  — validation returns `true` because only `B` is checked.
4. Host app reads `request.shop` (`"victim-shop.myshopify.com"`) and processes the webhook payload against that shop's stored session/access token — cross-tenant action performed using attacker-controlled data labeled as the victim's shop.
