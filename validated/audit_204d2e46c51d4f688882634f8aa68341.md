### Title
Cross-chain amount truncation can zero out mint/transfer in `pallet-hyper-fungible-token::on_accept` when destination decimals < source (ERC20) decimals - (File: `modules/pallets/hyper-fungible-token/src/module.rs`, `modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
`pallet-hyper-fungible-token`'s `on_accept` handler converts an incoming ERC20-denominated amount to the local asset's balance using `convert_to_balance`, which performs `value / 10^(erc_decimals - local_decimals)` whenever the remote (EVM) token has more decimals than the local asset. [1](#0-0)  If a relayed message carries a small enough `message.amount` relative to that decimals gap, the division truncates to zero, and the pallet proceeds to transfer/mint `0` to the beneficiary while still emitting a success event — this is the exact bug class from the report (division that "may result in zero" with no zero-amount guard before minting).

### Finding Description
In `on_accept`, the pallet decodes the incoming message, resolves `erc_decimals` (the sender-chain contract's precision, from `Precisions`) and `decimals` (the local asset's precision), then computes:
```rust
let amount = convert_to_balance::<...>(
    U256::from_big_endian(&message.amount.to_be_bytes::<32>()),
    erc_decimals,
    decimals,
)
``` [2](#0-1) 

`convert_to_balance` is:
```rust
pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}
``` [3](#0-2) 

When `erc_decimals > local_decimals` (e.g. a token registered with 18 decimals on the EVM side vs. 6 or 12 decimals locally — this is exactly the layout documented for `BridgeToken`, whose comment states nexus uses 12 decimals while the EVM contract fixes 18, "so the pallet scales by 10^6 in both directions") [4](#0-3) , any `message.amount` smaller than `10^(erc_decimals - local_decimals)` integer-divides to `0`. There is no check anywhere in `on_accept` (or in `convert_to_balance`) that rejects a zero-resulting conversion — the code proceeds directly to `NativeCurrency::transfer` / `Assets::mint_into` with the truncated `amount`, and then unconditionally emits `Event::TokenReceived { amount: amount.into(), .. }`. [5](#0-4) [6](#0-5) 

Because the source-chain contract (`BridgeToken`/`HyperFungibleToken`) burns or locks the *full* sent amount before dispatching the cross-chain post request, and the local `on_accept` mints/transfers `0` when the division underflows, the user's funds are destroyed on the source chain with nothing credited on the destination — a permanent loss, reachable by any unprivileged user who calls the token's send/bridge function with a small enough amount. This is not a timeout/refund path (that only triggers `on_timeout`, not `on_accept` success); a successfully delivered message that truncates to zero is treated as a completed, valid transfer.

### Impact Explanation
Medium/High severity: an unprivileged user (or an attacker deliberately targeting other users' dust-sized cross-chain transfers, or exploiting a misconfigured `Precisions` entry) can cause permanent loss of bridged funds. The source chain irrevocably burns/locks the full amount (evidenced by the BridgeToken/HyperFungibleToken escrow model) [7](#0-6) , while the destination chain mints/transfers zero, and the protocol still records the delivery as successful (`TokenReceived` event, no error), so there is no automatic remediation path (unlike a timeout, which does trigger a refund via `on_timeout`/`convert_to_balance` symmetrically). [8](#0-7) 

### Likelihood Explanation
Likelihood is real whenever a chain pair with a decimals gap is configured — which the codebase's own reference deployment (`BridgeToken`, 18 EVM decimals vs 12 nexus decimals, `Precisions` storage keyed per (AssetId, StateMachine)) [9](#0-8)  demonstrates is an expected configuration, not an edge case. Any transfer amount below `10^6` in the sender's ERC20 units (i.e. less than 0.000001 tokens in this example) triggers the truncation; users bridging fee remainders, dust, or making UX mistakes with amount entry are realistically exposed.

### Recommendation
Add an explicit check in `on_accept` (and symmetrically wherever `convert_to_balance` is used, e.g. `on_timeout`) that rejects/reverts the request when the converted `amount == 0`, e.g.:
```rust
ensure!(!amount.is_zero(), HftError::AmountTooSmall);
```
before performing any transfer/mint, so that a delivery which would result in a zero credit fails cleanly (allowing the relayer/system to surface an error and, ideally, a refund path) rather than silently consuming the source-side burn/lock with no destination-side credit.

### Proof of Concept
1. Configure `Precisions::<T>::set(asset_id, evm_chain, 18)` and let the local asset (`T::Decimals` or the `pallet-assets` asset) have `decimals = 12` (mirroring the documented `BridgeToken` 18-vs-12 split). [4](#0-3) 
2. On the EVM side, a user sends `amount = 999_999` wei (i.e. less than `10^6`) via the bridge token's send path; the contract burns/locks `999_999` and dispatches a post request with `message.amount = 999_999`.
3. On delivery, `on_accept` computes `convert_to_balance(U256::from(999_999), 18, 12)` = `999_999 / 10^6 = 0`. [3](#0-2) 
4. `Assets::mint_into(local_asset_id, &beneficiary, 0)` (or `NativeCurrency::transfer(..., 0, ...)`) succeeds trivially, and `Event::TokenReceived { amount: 0, .. }` is emitted as a normal success. [5](#0-4) [6](#0-5) 
5. The user has permanently lost `999_999` wei worth of tokens burned on the EVM side with zero credited on the destination chain, and no timeout/refund is triggered because the message was "successfully" delivered.
