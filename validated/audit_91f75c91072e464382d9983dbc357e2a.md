### Title
Fraud detection is fully disabled, allowing signups to complete without any fraud/liveness enforcement - (File: `src/plans/mod.rs`, `src/plans/fraud_check.rs`)

### Summary
The Governance.vy analog in this codebase is `MasterPlan::detect_fraud` in `src/plans/mod.rs`, whose body has been gutted so that it unconditionally returns `Ok(false)` regardless of the outcome of the biometric pipeline, and the backing `Report` fraud-check machinery in `src/plans/fraud_check.rs` has been reduced to zero checks (`N_FRAUD_CHECKS: usize = 0`). Just as the DynamoFinance `Governance.vy` bug commented out the call that would have actually applied a governance vote's effect (leaving the vote-counting logic intact but functionally dead), here the fraud-check *scaffolding* (config parsing, report struct, feedback message enum, datadog tagging) remains fully wired up and called from the signup flow, but the actual enforcement logic has been deleted/commented, so the check can never flag fraud.

### Finding Description
In `src/plans/mod.rs`, `detect_fraud` is invoked as part of the signup pipeline after biometric capture: [1](#0-0) 

The function receives the completed `biometric_pipeline::Pipeline` (which contains occlusion detection results, iris data, and `face_identifier_fraud_checks`), but instead of evaluating that data it immediately short-circuits with a comment acknowledging the checks were intentionally removed, and returns `Ok(false)` (no fraud) in every case where a pipeline exists.

This is backed by `src/plans/fraud_check.rs`, where the `Report` struct that is supposed to hold the results of individual fraud signals (contact lenses, eyeglasses, mask, occlusion, multiple faces, head pose, underage, low image quality — enumerated in `PipelineFailureFeedbackMessage`) is defined with zero fields and zero checks: [2](#0-1) [3](#0-2) 

`fraud_detected()` and `fraud_detected_with_config()` therefore always operate over empty arrays and can never return `true`: [4](#0-3) 

The `PipelineFailureFeedbackMessage` enum (`ContactLenses`, `EyeGlasses`, `Mask`, `FaceOcclusion`, `MultipleFaces`, `EyesOcclusion`, `HeadPose`, `Underaged`, `LowImageQuality`) still exists and is referenced throughout the UI/feedback code as if these checks are active, but none of them can ever actually be triggered — the enforcement path is dead code, exactly mirroring the DynamoFinance pattern where the vote-counting logic (`VoteCount`) remained intact but the actual state-changing call was commented out.

### Impact Explanation
Because `detect_fraud` always resolves to `false`, no signup can ever be rejected for fraud regardless of what the biometric pipeline detects (contact lenses, mask/occlusion, multiple faces during capture, incorrect head pose, underage user, or low image quality). This directly falls into the accepted "fraud/liveness bypass" impact category: an unprivileged user attempting to spoof or otherwise defeat liveness/anti-fraud protections during signup will always pass the fraud-check stage of `MasterPlan::run` → `do_signup` → `detect_fraud`, since the function structurally cannot report fraud. This undermines the integrity guarantee that only genuine, non-fraudulent signups are enrolled.

### Likelihood Explanation
High. This is not a conditional or edge-case code path — every signup that reaches `detect_fraud` with a completed pipeline follows this exact code path, so the bypass is deterministic and always reachable by an unprivileged user attempting a normal enrollment. No special network position, hardware access, or operator privilege is required.

### Recommendation
Restore (or reimplement, if this deletion was intentional for the FOSS build) real fraud-check evaluation logic in `detect_fraud` so that it actually inspects the `biometric_pipeline::Pipeline` output (occlusion, iris/face identifier results, etc.) instead of unconditionally returning `Ok(false)`, and populate `Report`/`N_FRAUD_CHECKS` in `src/plans/fraud_check.rs` with real check implementations rather than an empty array, so the existing feedback/reporting scaffolding is backed by functioning enforcement.

### Proof of Concept
1. Trigger a signup through `MasterPlan::run`, ensuring `biometric_pipeline` produces a `Pipeline` (e.g., simulate a capture with an obvious fraud signal such as multiple faces or heavy occlusion, which the `PipelineFailureFeedbackMessage` enum indicates should be detectable).
2. Observe that `detect_fraud` is called with `Some(pipeline)` at `src/plans/mod.rs:1399`, but per lines 1403-1405 it unconditionally returns `Ok(false)` without evaluating pipeline contents.
3. Confirm in `src/plans/fraud_check.rs:12` that `N_FRAUD_CHECKS = 0`, meaning `Report::fraud_checks()`/`fraud_detected()` structurally cannot ever return a positive fraud signal.
4. Signup proceeds to `enroll_user` regardless of the actual fraud/liveness state of the capture, confirming the bypass. [5](#0-4) [6](#0-5)
