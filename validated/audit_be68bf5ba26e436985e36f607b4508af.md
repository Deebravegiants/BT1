### Title
Outbound consensus/request delivery rewards for relayers become permanently unclaimable if the reward configuration is changed after delivery but before the claim - (File: modules/pallets/relayer/src/lib.rs)

### Summary
`pallet-ismp-relayer`'s outbound consensus and outbound request delivery reward mechanisms pay relayers for delivering hyperbridge-originated messages (BEEFY authority rotations and system requests) to destination chains. Unlike the existing `accumulate_fees`/`Fees` balance path — where a user-paid fee is escrowed at dispatch time and is independent of later config changes — these two newer claim paths determine payability by reading the *current* value of a governance-controlled reward map at claim time, keyed by `StateMachine` (`OutboundConsensusDeliveryReward`) or `module_id` (`OutboundRequestDeliveryReward`). A relayer that has already performed the qualifying delivery (an on-chain, unrecoverable, already-completed action) has no snapshot of eligibility pinned to the time of delivery. If governance lowers/zeroes the reward entry between delivery and claim, the relayer's already-earned reward for that specific delivery is permanently forfeited, mirroring the reported bug class where `_getStakerVaults` reads the *current* vault list instead of a snapshot valid at the time rewards accrued, causing already-earned rewards to become permanently unclaimable once the underlying list entry is removed.

### Finding Description
`OutboundConsensusDeliveryReward` and `OutboundRequestDeliveryReward` are plain `StorageMap`s with no per-epoch/per-request snapshot: [1](#0-0) [2](#0-1) 

Governance can change these values at will via unsigned-but-privileged extrinsics that simply overwrite the map entry: [3](#0-2) [4](#0-3) 

The comment on `set_outbound_request_delivery_reward` is explicit that "Setting `amount = 0` removes the module from the allowlist," and the design doc confirms the claim path is gated on the *live* value of this map, not a value captured at delivery time: [5](#0-4) 

> "The authoritative gate is on chain: `process_outbound_request_delivery_claim` rejects any commitment whose `request.from` is not in `OutboundRequestDeliveryReward`." — the corresponding error is `OutboundRequestNoRewardConfigured`.

The delivery itself (the `PostRequest`/`NewEpoch` event proving the relayer's work) is recorded permanently and immutably in `RequestCommitments`/`EvmHost._epochs`, but the relayer's *entitlement to be paid* is not similarly pinned — it is re-evaluated against whatever the reward map currently says at the moment `claim_outbound_consensus_delivery_reward` / `claim_outbound_request_delivery_reward` is submitted: [6](#0-5) 

This is structurally identical to the reported bug class: `Rewards::claimRewards` in the external report re-derives the *staker's list of eligible vaults* from the current, mutable `getVaults(epoch)` state instead of a value fixed at the time the reward accrued, so a vault removed between distribution and claim makes that staker's already-earned reward for that vault permanently unclaimable. Here, the relayer's already-completed, on-chain-proven delivery is the "accrued reward event," and the reward map is the mutable "list" whose current state — rather than its state at delivery time — gates the claim.

### Impact Explanation
Any relayer that delivers a mandatory BEEFY authority-set rotation or a hyperbridge-originated system message is entitled to a treasury-funded reward for that specific, already-completed, unrepeatable delivery. If governance later reduces or zeroes the relevant reward entry (a routine, legitimate reconfiguration — e.g. re-balancing incentives, disabling a module that has been fully migrated, or correcting a misconfigured reward) before the relayer submits its claim, the relayer's proof of a real, already-rendered service becomes permanently non-payable: `process_outbound_consensus_delivery_claim` / `process_outbound_request_delivery_claim` reject it with "reward off"/`OutboundRequestNoRewardConfigured`, and there is no other path to recover the amount that was owed at delivery time. This is a permanent freezing of the relayer's entitled funds (never actually escrowed, so nothing to "double pay," but the delivery event and the entitlement it should have generated are permanently lost) reachable by any of Hyperbridge's permissionless relayers as soon as governance performs a normal reward-table update — no malicious governance/collusion assumption is required, only ordinary operational timing between delivery and the (async, batch) claim task.

### Likelihood Explanation
This is not a contrived edge case: reward tables are explicitly designed to be adjustable by governance (documented use case is turning per-module/per-chain rewards on/off), and claims are submitted asynchronously by a background task on a fixed interval (`outbound_request_claim.rs`, `outbound_claim.rs`) rather than atomically with delivery. Any reward-table change landing in that window — which can be minutes to hours depending on interval and network conditions — silently forfeits every in-flight, already-earned claim for that state machine/module, with no alert other than the generic "claim failed; will retry" log which will keep retrying and failing forever since the on-chain condition never becomes true again.

### Recommendation
Snapshot reward eligibility and amount at the time the qualifying delivery event is recorded (e.g. store the reward value alongside the `RequestCommitments`/`NewEpoch` entry, or maintain a separate accrual ledger credited at delivery time similar to the `Fees` map used by `accumulate_fees`), rather than re-reading the current governance-mutable reward map at claim time. Alternatively, disallow reducing a reward value below what is required to pay out any already-delivered-but-unclaimed items, or require a time-locked/delayed reward change that only applies to deliveries made after the change takes effect.

### Proof of Concept
1. Governance sets `OutboundRequestDeliveryReward[module_id] = R` via `set_outbound_request_delivery_reward`.
2. Relayer delivers a hyperbridge-originated request from `module_id` to a destination chain; this permanently writes the delivery receipt on the destination and the commitment in `RequestCommitments` on Hyperbridge (irreversible, already-completed work).
3. Before the relayer's background claim task (`outbound_request_claim.rs`) submits `claim_outbound_request_delivery_reward`, governance calls `set_outbound_request_delivery_reward(module_id, 0)`.
4. The relayer submits the claim with a valid destination state proof of its delivery; `process_outbound_request_delivery_claim` rejects it with `OutboundRequestNoRewardConfigured` because the current map value is now `0`.
5. The relayer has no other mechanism to redeem the reward for that specific, already-completed delivery — it is permanently lost, even though `RequestCommitments[commitment]` (proof the work was done) still exists on chain forever.

			origin: OriginFor<T>,
			state_machine: StateMachine,
			amount: BalanceOf<T>,
		) -> DispatchResult {
			T::RelayerOrigin::ensure_origin(origin)?;
			OutboundConsensusDeliveryReward::<T>::insert(state_machine, amount);
			Self::deposit_event(Event::OutboundConsensusDeliveryRewardUpdated {
				state_machine,
				new_reward: amount,
			});
			Ok(())
		}
