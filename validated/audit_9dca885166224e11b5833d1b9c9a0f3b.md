### Title

RAY-scaled debt overflows before the borrow-index cap and permanently freezes a market - (`common/src/rates/simulate.rs`)

### Summary

`accrue_step` multiplies total scaled debt by the current borrow index before applying the configured index ceiling. For sufficiently large indexed balances, this product can exceed `i128::MAX` while `borrow_index` is still below `MAX_BORROW_INDEX_RAY`, causing a `MathOverflow` panic before the cap can clamp the index. [1](#0-0) [2](#0-1) 

### Finding Description

Every pool market operation loads a synchronized market cache, and `synced_market` unconditionally calls `interest::global_sync`. [3](#0-2)  `global_sync` processes every elapsed period through `accrue_chunk`, which calls `accrue_step` before any market mutation or guard runs. [4](#0-3) [5](#0-4) 

Inside `accrue_step`, `scaled_to_original(env, borrowed, borrow_index)` executes `borrowed * borrow_index` using checked fixed-point multiplication. [6](#0-5) [7](#0-6)  Only after this multiplication does `update_borrow_index` multiply the old index by the interest factor and clamp the result to `MAX_BORROW_INDEX_RAY`. [8](#0-7) [9](#0-8) 

The cap therefore bounds the index but not the indexed debt value used before the cap is reached. Because `MAX_BORROW_INDEX_RAY` is `1e36`, a scaled debt near the RAY domain overflows once the index reaches roughly `i128::MAX / borrowed`, long before the index itself reaches `1e36`. [10](#0-9)  The failed call rolls back without advancing `last_timestamp`, so every subsequent invocation reaches the same multiplication and fails again.

The strongest reachable path is:

1. Supply a large amount of a configured high-decimal asset through `controller.supply`.
2. Supply sufficient collateral and call `controller.borrow` to create a comparably large scaled debt position at sustained high utilization.
3. Wait until index growth pushes `borrowed * borrow_index` over `i128::MAX`.
4. Call permissionless `controller.update_indexes` with the victim `HubAssetKey`.
5. The pool accrual panics, and all later operations touching that market panic during their mandatory accrual phase.

### Impact Explanation

The market becomes permanently unable to process operations: suppliers cannot withdraw, borrowers cannot repay, liquidators cannot seize collateral, and debt cleanup cannot proceed because each path first synchronizes the same market. [11](#0-10)  This permanently freezes supplier claims and borrower collateral in the affected `(hub, token)` market unless the protocol upgrades or otherwise modifies the contract outside the reachable market paths.

### Likelihood Explanation

The trigger does not require privileged execution once governance has configured a market with sufficiently high caps, asset decimals, collateral capacity, and a steep borrow-rate curve. A single funded attacker can create the required supply/debt state through ordinary `supply` and `borrow` calls, then activate the cliff through permissionless `update_indexes`; alternatively, an attacker can wait for an already-large borrowed market to accrue to the unsafe index and invoke `update_indexes` first.

### Recommendation

Make the accrual ordering and value conversion overflow-safe:

- Check `borrowed > i128::MAX / borrow_index` before calling `scaled_to_original`, and handle that state deterministically instead of panicking.
- Apply the borrow-index ceiling before calculating total indexed debt, or cap the index before the value multiplication.
- Prefer saturating indexed-value calculations for utilization and interest distribution so accrual can reach `MAX_BORROW_INDEX_RAY` and remain callable.
- Add production regression coverage showing that `update_indexes`, `repay`, `withdraw`, and liquidation remain callable when `borrowed * borrow_index` would otherwise exceed `i128::MAX`.

### Proof of Concept

For a configured 18-decimal market that permits a billion-token book, use a steep configured curve such as a 175% maximum borrow rate and 75% optimal utilization. Supply `1_000_000_000` whole debt tokens, provide sufficient collateral, and borrow 98% of that liquidity. The scaled borrow balance is approximately `9.8e35`; once `borrow_index` exceeds roughly 173, `borrowed * borrow_index` exceeds `i128::MAX`.

Call `controller.update_indexes` with `hub_assets = [market_key]` after enough elapsed ledger time. It fails inside `accrue_step` at `scaled_to_original` before `update_borrow_index` can clamp to `MAX_BORROW_INDEX_RAY`. Subsequent `repay`, `withdraw`, and `liquidate` attempts for the same `HubAssetKey` fail identically because they all invoke `synced_market` first.

```rust
/// Applies `interest_factor` to `old_index` to produce the new borrow index,
/// capped at `MAX_BORROW_INDEX_RAY`.
pub fn update_borrow_index(env: &Env, old_index: Ray, interest_factor: Ray) -> Ray {
    let new_index = old_index.mul(env, interest_factor);
    if new_index.raw() > MAX_BORROW_INDEX_RAY {
        return Ray::from(MAX_BORROW_INDEX_RAY);
    }
    new_index
}
```

```rust
pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}
```
