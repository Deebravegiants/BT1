### Title
Weighted-median phantom price aggregation lets a self-funded solver set the published pool exchange rate, which real users' `quoteIntent()` orders are then priced against - ([File: sdk/packages/sdk/src/protocols/intents/phantom-aggregation.ts])

### Summary
`aggregatePhantomBids` prices each phantom-order leg with `weightedMedian`, where the weight of a solver's quote is that same solver's own on-chain balance of the leg's output token. Because the weight and the quote come from the identical unprivileged actor, a solver can inflate its own reported balance immediately before a bid window closes to obtain more than half the leg's total weight, at which point `weightedMedian` deterministically returns that solver's exact quoted price. This mirrors the DYAD liquidation flaw: the party who benefits from the outcome also controls the denominator/threshold (there, `totalDeposits`; here, per-solver "weight") that decides the outcome, with no game-theoretic floor preventing manipulation.

### Finding Description
`weightedMedian` is explicitly documented as a **selection, not a blend** — it returns one bidder's exact price verbatim once cumulative weight crosses 50%: [1](#0-0) 

The weight fed into that selection is computed per bid as the solver's own token balance (plus any Uniswap V4 position it owns) on the destination chain: [2](#0-1) 

This is confirmed by the project's own flow documentation: *"a solver holding over half the leg's weight sets the published price verbatim."* [3](#0-2) 

The resulting `medianPrice` is written straight into `PhantomOrderPriceSnapshotV2` and then folded by `updateLiquidityPools`/`mergeChainRowsIntoPool` into the pool's canonical `sellRate`/`buyRate`: [4](#0-3) 

Those aggregate rates are exactly what the SDK's default quoting strategy (`IndexedRateIntentQuoteStrategy` / `quoteIntent`) uses to price real, capital-moving orders for any caller — with "no automatic fallback to another price source": [5](#0-4) [6](#0-5) 

Because the balance read (`getBalance`) that determines weight is an unauthenticated, un-bonded on-chain balance query of the *bidder's own address*, any unprivileged solver can:
1. Temporarily move/borrow tokens into its bidding wallet to exceed 50% of the total weight for a leg during the short bid window.
2. Submit a single signed bid quoting an arbitrary price for that leg.
3. Immediately withdraw the temporary balance after the snapshot is taken.

There is no floor, no stability check, and no cost proportional to how far the quoted price deviates from a fair rate — the only cost is transiently holding tokens, which can be looped via flash-style transfers between the solver's own accounts. This is the same "no stable equilibrium / self-referential denominator" defect the source report describes: the actor who is priced also controls the input that decides how much influence its own price gets.

### Impact Explanation
A manipulated `medianPrice` propagates into `LiquidityPool.sellRate`/`buyRate`, which the SDK's default `quoteIntent()` path uses, with no other price source, to construct real cross-chain swap orders for end users. A solver that skews the published rate in its favor can:
- Quote users an inflated `amountOut`/deflated `amountIn` via `quoteIntent`, then, when the user places the resulting real order and it goes to auction, either decline to fill or force the market toward its manipulated number, effectively front-running/mispricing user orders.
- Poison `PoolChainLiquidity`/`LiquidityPool` state used by other integrators and by Simplex's own filler policies, degrading pricing integrity chain-wide until `MAX_SAMPLE_AGE_BLOCKS` rolls the stale sample off.

This is a market-pricing/oracle manipulation vulnerability reachable by a single unprivileged solver's bid submission, with concrete downstream effect on real user funds movement (mispriced swaps), which qualifies as Medium/High severity depending on deployed pool depth and how tightly `quoteIntent` consumers trust the rate without independent verification.

### Likelihood Explanation
Likelihood is Medium: the attack requires the attacking solver to be a delegated `SolverAccount` participant (already an expected, permissionless role) and to accumulate >50% of a leg's weight during a bid window. For thinly-quoted legs (few competing solvers, low overall inventory) this bar is low and repeatable every phantom-bid cycle, since balances can be recycled between the attacker's own wallets/vaults after each snapshot.

### Recommendation
Do not let a single self-reported balance snapshot at bid time both (a) come from the same address being priced and (b) fully determine the published rate via majority-weight selection. Concretely:
- Cap any single solver's contribution to a leg's total weight (e.g., ≤ some fraction such as 20–30%) so no bidder can unilaterally set the median.
- Require inventory to be held/attested over a time window (e.g., average balance over N blocks, or a bonded/staked amount) rather than an instantaneous read, to prevent flash-style balance inflation right before the snapshot.
- Prefer a genuinely blended statistic (depth-weighted mean across multiple independent samples, as already done for `weightedRate` across chains) instead of `weightedMedian`'s verbatim selection when weight concentration is high, or fall back to rejecting the leg if weight concentration exceeds a threshold.
- Cross-check the aggregated rate against an independent reference (e.g., a CEX/Uniswap TWAP) before it is used by default in `quoteIntent`, rejecting/flagging snapshots that diverge beyond a sane band (similar to the existing `warnOnDivergentSample` cross-chain check, but applied against an external reference, not just other Hyperbridge chains).

### Proof of Concept
1. Solver S controls two of its own wallets, A (bids) and B (idle inventory of output token T).
2. Immediately before a `PhantomOrderV2` bid window closes for a leg priced in T, S transfers a large balance of T from B into A (a single on-chain transfer/transaction).
3. S submits a signed `UserOperation` bid (via its delegated `SolverAccount`) quoting an arbitrary `solverAmount` for that leg — e.g., a price far off the fair market rate.
4. `aggregatePhantomBids` reads S's balance in T via `getBalance(destUrl, chain, outputToken, solver)` at that moment, giving S's quote weight exceeding 50% of the leg's total weight, per: [7](#0-6) 
5. `weightedMedian` selects S's exact quoted price as `medianPrice` because cumulative weight crosses 50% at S's entry: [1](#0-0) 
6. `updateLiquidityPools` writes this into `PoolChainLiquidity.rate`, then `mergeChainRowsIntoPool` folds it into the pool's canonical `sellRate`/`buyRate`.
7. S transfers T back out of A to B, restoring capital with no lasting cost.
8. Any subsequent caller of `IntentGateway.quoteIntent()` for that pair is now quoted using S's manipulated rate until the sample ages out (`MAX_SAMPLE_AGE_BLOCKS`) or a fresher, non-manipulated snapshot supersedes it.

Note: full exploitation economics (exact minimum capital needed to cross the 50% weight threshold on a live mainnet pool, and the precise financial upside from a specific manipulated `quoteIntent` call) were not independently modeled here and would need on-chain data (current pool depth, competing solver inventory) to quantify precisely.

export function weightedMedian(entries: { price: bigint; weight: bigint }[]): bigint {
	const sorted = [...entries].sort((a, b) => (a.price < b.price ? -1 : a.price > b.price ? 1 : 0))
	const totalWeight = sorted.reduce((acc, e) => (e.weight > 0n ? acc + e.weight : acc), 0n)

	if (totalWeight === 0n) {
		return sorted[Math.floor(sorted.length / 2)].price
	}

	let cumulative = 0n
	for (const entry of sorted) {
		if (entry.weight <= 0n) continue
		cumulative += entry.weight
		if (cumulative * 2n >= totalWeight) return entry.price
	}
	return sorted[sorted.length - 1].price
}

function mergeChainRowsIntoPool(pool: LiquidityPool, rows: PoolChainLiquidity[], referenceBlock: bigint): void {
	for (const direction of [SELL, BUY]) {
		const directionRows = rows.filter((row) => row.direction === direction)
		if (directionRows.length === 0) continue

		// Blocks are processed in order, so the difference is non-negative in practice; a row
		// from a "future" block would simply count as fresh, which is the right reading anyway.
		const fresh = directionRows.filter((row) => referenceBlock - row.lastUpdatedBlock <= MAX_SAMPLE_AGE_BLOCKS)
		const merged = fresh.length > 0 ? fresh : directionRows

		warnOnDivergentSample(pool.id, direction, merged)

		const depth = merged.reduce((acc, row) => acc + row.depth, 0n)
		const rate = weightedRate(merged)
		const bidCount = merged.reduce((acc, row) => acc + row.bidCount, 0)

		if (direction === SELL) {
			pool.sellRate = rate
			pool.sellDepth = depth
			pool.sellBidCount = bidCount
		} else {
			pool.buyRate = rate
			pool.buyDepth = depth
			pool.buyBidCount = bidCount
		}
	}
}

### quoteIntent(params)

Quotes an intent from the latest aggregate pool buy or sell rate published by the indexer. The pool rate is depth-weighted from fresh chain samples. Pass token addresses directly—the SDK resolves their configured symbols and decimals. No `strategy` option is needed for indexed-rate quotes.

Indexed-rate quotes require an attached Hyperbridge indexer client. There is no automatic fallback to another price source.

Use `amountIn` and `amountOut` when constructing the `inputs` and `output.assets` for an IntentGateway V2 order.
