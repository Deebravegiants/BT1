## Title
Webhook shop-domain header is trusted without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` validates a webhook's authenticity by HMAC-verifying only the raw request body, while the `shop` (and `topic`/`webhook-id`) values that are trusted and handed to the app's webhook handler are read straight from unauthenticated HTTP headers. The identity binding "the shop that signed this payload == the shop attributed to this event" is never actually checked.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`ShopifyAPI::Utils::HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string`, i.e. only over the body: [2](#0-1) 

Meanwhile `Request#shop` (and `#topic`, `#webhook_id`, `#api_version`) are pulled directly from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, which is not part of the signed material: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` to build the `WebhookMetadata` passed to the app's registered handler: [4](#0-3) 

Because the HMAC secret (`Context.api_secret_key`, the app's `client_secret`) is shared across **every** shop that installs the app, and the signature only binds the body — not the shop-domain header — any two (raw_body, hmac) pairs that Shopify has legitimately produced for *any* shop remain valid regardless of which `shop-domain` header value accompanies them. The binding that should hold is:

`shop_attributed_to_event (request.shop) == shop_that_actually_produced_and_signed_this_body`

but the gem only checks `hmac == HMAC(secret, raw_body)`, never binding `shop` into the signed string. An attacker who operates their own installation of the app (shop A) can capture a legitimate `(raw_body, hmac)` pair that Shopify sent to their own endpoint, then replay it to the app's webhook endpoint while substituting the `shopify-shop-domain` header value with a victim shop's domain (shop B). `HmacValidator.validate` still returns `true` because the body/HMAC pair is genuinely valid — it was simply generated by a different shop.

### Impact Explanation
The webhook handler receives `WebhookMetadata` claiming the event is for shop B while the body content actually originated from shop A. Any host application logic that uses `data.shop` to key persistence, authorization, or downstream API calls (i.e., normal expected usage per the library's documented `WebhookMetadata` shape) would associate attacker-controlled/replayed data with a different tenant's shop identity — a cross-tenant data-integrity/confusion issue. This satisfies the "cross-tenant access" Critical impact category, since the confusion is rooted entirely in this gem's own signature-verification logic (it never binds the header-derived `shop` value into the signed content), not in host misuse.

### Likelihood Explanation
Exploitation only requires the attacker to be an ordinary, unprivileged installer of the target app (to obtain one legitimate `(body, hmac)` pair from their own store) and the ability to POST directly to the app's public webhook endpoint with custom headers — no access token, `client_secret`, or privileged account is needed. This is a realistic, low-effort attack path for any internet user who can install the app once.

### Recommendation
Include the identity-binding headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signable string used for HMAC verification, or otherwise cryptographically bind the claimed shop to the signed payload, so that a valid signature for one shop's payload cannot be replayed while claiming a different shop's identity.

### Proof of Concept
1. Install the target Shopify app on an attacker-controlled shop (`attacker.myshopify.com`) and register a webhook subscription.
2. Capture a legitimate webhook delivery Shopify sends for that shop: raw body `B` and header `shopify-hmac-sha256: H` (valid because `H = HMAC(client_secret, B)`).
3. Replay a POST to the app's webhook endpoint with the same body `B` and header `shopify-hmac-sha256: H`, but set `shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because only `B` is checked against `H`: [4](#0-3) 
5. The registered handler is invoked with `WebhookMetadata.new(..., shop: "victim.myshopify.com", body: <attacker's body>)`, despite the payload never having been produced or signed on behalf of `victim.myshopify.com`.
