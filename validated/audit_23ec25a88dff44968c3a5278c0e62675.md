### Title
Webhook HMAC validation does not bind the `shop` (or `topic`) identity to the signed payload, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) that the host application uses to dispatch a webhook event straight from an HTTP header, while the HMAC signature that `Utils::HmacValidator` verifies only covers the raw request body. Because the shop attribution is never part of the signed bytes, a valid `(body, hmac)` pair legitimately produced by Shopify for one shop can be replayed with a different `shop-domain` header value and still pass HMAC validation, causing the webhook to be attributed to the wrong tenant.

### Finding Description
`Request#shop` reads directly from the `shopify-shop-domain` header with no cryptographic binding to the signature: [1](#0-0) 

The HMAC that is actually validated is computed only over the raw body, not the topic or shop headers: [2](#0-1) [3](#0-2) 

`Utils::HmacValidator.validate` verifies the signature exclusively against `to_signable_string` (the raw body): [4](#0-3) 

`Registry.process` trusts `request.shop` for downstream tenant attribution after only checking the HMAC of the body: [5](#0-4) 

The identity binding that is broken is:
`hmac_verified_bytes (raw_body) == tenant_identity_field (shop-domain header)`
This equality does not hold — the signature authenticates the body only, while the shop identity that the handler acts on is taken from an unauthenticated, unbound header. This mirrors the report's root cause exactly: a field used to route/attribute a request (there, the ActiveResource resource identifier used to build the backend URL; here, the `shop`/`topic` headers used to attribute the webhook to a tenant) is not covered by the mechanism meant to authenticate the request.

### Impact Explanation
An unprivileged internet user who legitimately operates their own shop (shop A) can receive genuine, correctly-signed webhooks from Shopify for shop A. Because the HMAC only signs the raw body, that attacker can replay the exact same `(raw_body, hmac-sha256)` pair directly to the host application's public webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header with an arbitrary value, e.g., a victim's shop domain. `Utils::HmacValidator.validate` still returns `true` because it never inspects the shop or topic headers, and `Registry.process` will hand the handler a `WebhookMetadata` with `shop: request.shop` set to the attacker-chosen value alongside the (legitimate, replayed) body. Any host application that uses `data.shop` to select a tenant record, decrypt/attribute data, or trigger tenant-scoped side effects will process shop-A's data as if it belongs to the attacker-chosen shop — a cross-tenant data/attribution confusion condition.

### Likelihood Explanation
Any merchant/developer who installs the app on their own store can capture a legitimate webhook delivery (body + valid HMAC) for their own shop and simply resend it with a modified `shop-domain` header using standard HTTP tooling — no access token, `client_secret`, or leaked credential is required, only a legitimately obtained webhook payload from the attacker's own tenant.

### Recommendation
Include the `shop` (and, ideally, `topic`, `api_version`, `webhook_id`) values in the HMAC-signed payload, or otherwise cryptographically bind them to the verified signature (e.g., verify them against a separately signed/derived structure) before `Registry.process` passes them to handlers. At minimum, document loudly that `request.shop`/`request.topic` are unauthenticated header values and must not be trusted for tenant attribution unless independently corroborated (e.g., cross-checked against the shop stored for the session that the app expects to receive webhooks from).

### Proof of Concept
1. Attacker installs the vulnerable app on their own store `attacker-shop.myshopify.com` and triggers an event that generates a webhook, capturing the raw POST body and the `x-shopify-hmac-sha256` header Shopify sent.
2. Attacker crafts a new HTTP POST to the app's public webhook endpoint using the exact same body and `x-shopify-hmac-sha256` value, but sets:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - `x-shopify-topic: <same or different topic>`
3. The app calls `ShopifyAPI::Webhooks::Registry.process(request)`: [6](#0-5) 
   `Utils::HmacValidator.validate(request)` returns `true` because it only checks the body-derived HMAC: [7](#0-6) 
4. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and the attacker's actual event body, despite the signature never having authenticated that shop association — demonstrating the broken binding between the verified bytes and the tenant identity field acted upon.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
