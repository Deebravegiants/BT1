## Analysis Summary

The CryptoPunks bug's root cause is a **missing identity binding**: the contract executes a privileged action (minting/buying) for whichever caller happens to invoke it, without verifying that the caller matches the party the "offer" was actually intended for. Searching this gem's non-generated library code for the same class of bug (an actor-supplied identity used for an action but not cryptographically bound to the credential that authorizes it) surfaces the webhook processing path.

### Title
Webhook shop identity is not bound to the HMAC signature, allowing shop-spoofing/cross-tenant confusion in `ShopifyAPI::Webhooks::Registry.process` - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, excluding the `shopify-shop-domain` header. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC over the body only, then unconditionally trusts the `shop` header value (parsed straight from the request) and forwards it to the application's webhook handler as the tenant identifier.

### Finding Description
The identity binding that should hold is: `shop reported to the handler == shop that the HMAC-signed payload actually originated from`. In practice this equality is never checked.

- `Request#to_signable_string` signs only `@raw_body`: [1](#0-0) 
- `Request#shop` is read directly and unauthenticated from the `shopify-shop-domain`/`x-shopify-shop-domain` header: [2](#0-1) 
- `Registry.process` validates HMAC over the request (i.e., over the body only) and then immediately hands `request.shop` to the app's handler as the trusted tenant identity, with no cross-check that the body's HMAC was computed for that particular shop: [3](#0-2) 

Because `Utils::HmacValidator.validate` uses `Context.api_secret_key`/`Context.old_api_secret_key` — a single secret shared by the app across **every** installed shop, not a per-shop secret — a valid HMAC only proves "this body was produced by Shopify for this app," not "this body was produced for the shop named in the `shop` header." Documented HMAC validation logic confirms the secret is global to the app: [4](#0-3) 

The webhook handler documentation explicitly instructs developers to trust `data.shop` as "The shop domain of the webhook," reinforcing that the gem's documented contract is for the header value to be authoritative: [5](#0-4) 

### Impact Explanation
This is a cross-tenant data confusion: an attacker who is a legitimate merchant on the app (and therefore receives real, validly-HMAC-signed webhook deliveries for their own shop from Shopify) can capture such a request and resend it to the app's webhook endpoint with the `shop` header rewritten to a victim shop's domain. Because the HMAC only covers the body — not the shop header — the `HmacValidator.validate` check still passes, and `Registry.process` passes the attacker-chosen `shop` value straight to the handler, which will act as if the (attacker's own) payload came from the victim tenant. Depending on how the host app uses `data.shop` (e.g., to key database writes, enqueue background jobs, or bypass per-shop authorization), this enables cross-tenant data injection/confusion.

### Likelihood Explanation
Any merchant who installs the app can generate valid, correctly-signed webhook bodies for their own shop at will (e.g., by editing a product) and replay them with a modified shop header, since sending arbitrary HTTP requests to the app's public webhook endpoint requires no special access.

### Recommendation
Verify that `request.shop` corresponds to the shop for which the request was actually authorized, e.g., by looking up an active session/installation record for that shop and confirming the shop is a "known" tenant, or by including the shop domain in the signed payload verification rather than trusting it from an unauthenticated header alone. At minimum, document prominently (and enforce in `Registry.process`) that `data.shop` must be cross-checked by the host application against a known/installed-shop list before being used for any tenant-scoped action.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker.myshopify.com` and lets Shopify deliver a real webhook (e.g. `products/update`) to the app's endpoint. The request has a valid `x-shopify-hmac-sha256` computed over the JSON body using the app's shared `api_secret_key`.
2. Attacker captures this exact request, and resends it to the same webhook endpoint, only changing `x-shopify-shop-domain` to `victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `@raw_body` (unchanged) — validation succeeds. [6](#0-5) 
4. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and the attacker-controlled body, and processes it as though it were a genuine webhook from the victim shop.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
