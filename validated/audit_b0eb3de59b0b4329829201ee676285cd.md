Based on the code reviewed, `pallet-hyper-fungible-token`'s decimal conversion helpers in `modules/pallets/hyper-fungible-token/src/impls.rs` have the same class of bug as the reported `unsoldTokens` issue: a one-directional scaling formula that silently produces zero adjustment (rather than the correct division) whenever the decimal relationship is inverted from what the author assumed.

### Title
Asymmetric decimal conversion in `convert_to_erc20`/`convert_to_balance` can mint unbacked tokens or under-credit users on cross-chain transfers - (File: `modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
`convert_to_erc20` and `convert_to_balance` only scale in one direction (multiply/divide by `10^(a.saturating_sub(b))`), exactly mirroring the `TokenSaleETH`/`TokenSaleUSDB` report's `(unsold * 10**ETH_DECIMAL) / tokenPrice` pattern that assumes decimals always work out to a fixed reference. When the decimal relationship is inverted from what the formula assumes, `saturating_sub` returns `0`, the scale factor becomes `10^0 = 1`, and no compensating division/multiplication happens — producing an amount off by a power of ten instead of the correct value.

```
pub fn convert_to_balance<B>(value: U256, erc_decimals: u8, local_decimals: u8) -> Result<B, B::Err> {
    let dec_str = (value / U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))).to_string();
    dec_str.parse::<B>()
}

pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
    U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
```

`convert_to_erc20` is called from `send()` in `modules/pallets/hyper-fungible-token/src/lib.rs` (lines 254, 287-295) to build the `Message.amount` dispatched cross-chain, after the pallet has already escrowed/burned `value` in local (`local_decimals`) precision: [2](#0-1) 

This value is trusted verbatim by the destination `HyperFungibleToken`/`WrappedHyperFungibleToken` EVM contract's `onAccept` to mint tokens (per `evm/tests/foundry/BridgeTokenTest.t.sol` `testOnAcceptFromNexusMints`, mint amount == message amount, no independent scaling on the EVM side).

`convert_to_erc20(value, erc_decimals, local_decimals)` only scales *up* correctly when `erc_decimals > local_decimals`. If instead `local_decimals > erc_decimals` (the local Substrate asset is more precise than the destination ERC20 token — e.g. a locally registered asset with 18 decimals bridging to a 6-decimal ERC20 representation), `erc_decimals.saturating_sub(local_decimals)` saturates to `0`, so the multiplier is `10^0 = 1`. The function returns `value` unscaled — i.e., the *local, high-precision* raw integer is sent as-is and interpreted by the destination contract as being denominated in the *lower* `erc_decimals`. This inflates the minted amount by `10^(local_decimals - erc_decimals)`, exactly the "wrong decimal base" failure mode described in the report (e.g. `unsoldTokens` calculated in 1e18 instead of 1e12 when the target used 12 decimals).

The reverse function, `convert_to_balance`, has the symmetric defect used in `on_accept` (`modules/pallets/hyper-fungible-token/src/module.rs` lines 74-91): when `local_decimals > erc_decimals`, `erc_decimals.saturating_sub(local_decimals)` is `0`, so the incoming ERC20 amount is divided by `1` and credited to the recipient's balance at full raw magnitude — again treating an amount as if it were already in `local_decimals` when it is really in the coarser `erc_decimals`, producing an amount inflated by the same factor.

### Impact Explanation
This is reachable by any unprivileged account calling the pallet's public `send` extrinsic — an "unauthorized app action"/"unbacked mint" class bug per the accepted analog categories. Depending on which side of the `Precisions` mapping is misconfigured relative to actual asset decimals, an attacker can:
- Trigger `send()` with a small locked/burned amount and have the destination EVM `HyperFungibleToken` mint a far larger (up to `10^n`) amount of tokens than was actually escrowed — an unbacked mint that drains the peg/backing of the bridged token.
- Or conversely under-credit incoming transfers, permanently freezing value for legitimate senders.

The severity is High because it is a decimals-direction-dependent silent value error, not a decimals-out-of-range revert; it produces silently wrong, exploitable amounts rather than failing safely, matching the "High" severity assigned to the original report.

### Likelihood Explanation
Whether this is actually triggerable in production depends on the concrete decimal configuration set via `Precisions` for each `(AssetId, StateMachine)` pair and each registered asset's `Assets::decimals()`/`T::Decimals`. I was not able to locate and fully inspect the `register_token`/`update_token` extrinsics that populate `Precisions` and `TokenContracts` within my available search budget (grep matched them but I ran out of iterations to read the exact validation logic), so I cannot confirm whether the pallet enforces `erc_decimals >= local_decimals` (which would make the vulnerable branch unreachable) or allows the inverse relationship (in which case the bug is directly exploitable by any caller of `send`). This is the one point of uncertainty that would need to be resolved by reading `register_token`/`update_token` in `modules/pallets/hyper-fungible-token/src/lib.rs` in full.

### Recommendation
Replace the one-directional `saturating_sub` scaling with a symmetric conversion that explicitly branches on which side has more decimals and scales the other direction accordingly (multiply when going to a token with more decimals, divide when going to one with fewer), mirroring the correct pattern already used elsewhere in the codebase, e.g. `_normalizeAmount` in `evm/src/utils/VWAPOracle.sol` (lines 240-248) and `adjustDecimals` in `sdk/packages/sdk/src/utils.ts` (lines 985-994), both of which explicitly handle both `from < to` and `from > to` cases rather than relying on saturating subtraction.

### Proof of Concept
Given a registered asset with `local_decimals = 18` (e.g. a standard `pallet-assets` token) bridged to an EVM `HyperFungibleToken` contract whose `Precisions` entry records `erc_decimals = 6`:
1. User calls `send(asset_id, amount = 1_000_000_000_000_000_000 /* 1.0 token, 18dp */, destination, recipient, ...)`.
2. Pallet burns/escrows `1e18` raw units from the sender (correct, 1 whole token).
3. `convert_to_erc20(1e18, erc_decimals=6, local_decimals=18)` computes `erc_decimals.saturating_sub(local_decimals) = 0`, so `erc20_amount = 1e18 * 10^0 = 1e18`.
4. The dispatched `Message.amount = 1e18` is delivered to the destination `HyperFungibleToken`, which mints `1e18` raw units — but since that contract's token is only 6 decimals, `1e18` raw units represents `1,000,000,000,000` (one trillion) whole tokens instead of `1`.
5. Net effect: burning 1 token on the source chain mints 1 trillion tokens' worth of ERC20 supply on the destination chain, an unbacked mint of `10^12`x the legitimate amount — confirmation would require verifying the actual configured decimal values via the (unread) `register_token` extrinsic.
