### Title
External caller's attached deposit is silently retained by the NEAR Wallet Contract when `rlp_execute` fails during transaction parsing - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
`WalletContract::rlp_execute` is `#[payable]`, so any unprivileged account can attach a NEAR deposit when calling it. The deposit is credited to the wallet contract's own balance as soon as the `FunctionCall` action executes (standard NEAR semantics: attached deposit is applied to the receiver's balance before the method body runs, per `docs/RuntimeSpec/Components/BindingsSpec/EconomicsAPI.md:7-15`). The contract tracks this deposit in a `CallerDeposit` struct so it can be manually refunded to the caller if the resulting cross-contract promise fails [1](#0-0) . However, this tracking value is computed and then discarded on early error returns inside `inner_rlp_execute`, meaning the deposit is never refunded and is effectively absorbed into the wallet contract's balance without being returned to the caller.

### Finding Description
Inside `inner_rlp_execute`, `CallerDeposit::new(&context)` is computed once, immediately after validating the attached deposit context [2](#0-1) . This value is only ever consumed inside the `Ok((action, transaction_kind))` branch, where it is forwarded into a promise callback (`rlp_execute_callback`, `address_check_callback`, or `nep_141_storage_balance_callback`) so that a refund transfer can later be issued if the promise fails [3](#0-2) .

But when RLP parsing fails — `Err(err @ Error::User(_))` (malformed/invalid RLP-encoded transaction data, an ordinary user error reachable by any caller) or `Err(err)` (Relayer/AccountId errors) — the function returns immediately without ever using `caller_deposit` [4](#0-3) . Back in `rlp_execute`, these errors are turned into `PromiseOrValue::Value(e.into())` — i.e., the outer `FunctionCall` receipt still *succeeds* and simply returns an error payload in the value [5](#0-4) . Because the receipt succeeds, NEAR's protocol-level deposit-refund mechanism (`refund_unspent_gas_and_deposits`, which only fires `if result.result.is_err()`) never triggers [6](#0-5) . The only thing that could return the money is the wallet contract's own manual `CallerDeposit`-based refund, and that code path was never reached.

This mirrors the Sublime `PoolFactory` bug class: a caller attaches native value alongside a call, an internal branch (selection of `_collateralToken` in Sublime; selection of the `Err(Error::User(_))`/`Err(err)` branch here) causes the code responsible for moving/tracking that value (`amount` in Sublime; `caller_deposit` here) to be silently dropped, while the surrounding transaction still completes "successfully" from the chain's perspective.

The existing test `test_caller_refunds` only verifies the refund path for a promise that fails *after* being scheduled (i.e., inside `rlp_execute_callback`'s `PromiseResult::Failed` arm) [7](#0-6)  — it does not cover the case of malformed/rejected RLP input where `inner_rlp_execute` errors out before any promise is even created.

### Impact Explanation
An external, unprivileged account can lose the NEAR deposit it attaches to a `rlp_execute` call if the RLP-encoded transaction it submits fails to parse (`Error::User`) or is otherwise rejected before a promise is scheduled. That deposit is not burned nor sent back to the caller — it remains as balance on the wallet contract's own account, i.e., it becomes an unauthorized, unrefunded transfer of value from the caller into the wallet-contract account. This is an unauthorized balance change consistent with the "assets not directly stolen but accidentally locked/misdirected due to user/branch error" impact class from the source report, mapped onto value accounting in a production NEAR contract shipped in this repo.

### Likelihood Explanation
Reachable by any unprivileged account with no special permissions: simply attach a deposit and call `rlp_execute` with an RLP-encoded Ethereum transaction that fails ABI/selector parsing (`UnknownFunctionSelector`, `InvalidAbiEncodedData`, etc., as exercised in `test_bad_data` — none of those test cases attach a deposit, which is itself a gap in test coverage) [8](#0-7) . No validator or node-privilege is required; it is purely a contract-logic defect reachable from an ordinary transaction.

### Recommendation
In `inner_rlp_execute`, before returning any `Err` (both `Error::User` and other error branches), issue a refund transfer using the already-computed `caller_deposit` if it is `Some`, mirroring the logic already present in `rlp_execute_callback`'s failure arm. Alternatively, compute `CallerDeposit` lazily only once parsing has succeeded, and refund the raw `env::attached_deposit()` directly to `predecessor_account_id` on any early-return error path when the predecessor differs from `current_account_id`.

### Proof of Concept
1. An external account (not the wallet owner) calls `rlp_execute(target, tx_bytes_b64)` on a deployed `WalletContract`, attaching some deposit (`#[payable]` permits this).
2. `tx_bytes_b64` is crafted to be syntactically valid RLP but semantically invalid so `internal::parse_rlp_tx_to_action` returns `Err(Error::User(UserError::InvalidAbiEncodedData))` (as reproduced by `test_bad_data`, minus the missing deposit in that test) [9](#0-8) .
3. `inner_rlp_execute` returns `Err(err)` at line 392-393 without referencing `caller_deposit`.
4. `rlp_execute` maps this into `PromiseOrValue::Value(e.into())`, a successful function-call outcome; no protocol-level deposit refund is generated because `result.result.is_ok()`.
5. The attached deposit remains on the wallet contract's account balance; the external caller's `view_account().balance` decreases by the full deposit and is never restored.

/// A data type to keep track of the deposit given by an external caller.
/// This allows us to refund the caller's deposit if the cross-contract call fails.
#[derive(Debug, PartialEq, Eq, Clone, serde::Serialize, serde::Deserialize)]
pub struct CallerDeposit {
    pub account_id: AccountId,
    pub yocto_near: NonZeroU128,

impl CallerDeposit {
    pub fn new(context: &ExecutionContext) -> Option<Self> {
        // Only track for external (non-self) callers
        if context.current_account_id == context.predecessor_account_id {
            return None;
        }

        NonZeroU128::new(context.attached_deposit.as_yoctonear()).map(|yocto_near| Self {
            account_id: context.predecessor_account_id.clone(),
            yocto_near,
        })
    }

// An external caller gets its deposit back if the cross-contract call fails.
#[tokio::test]
async fn test_caller_refunds() -> anyhow::Result<()> {
    let TestContext { worker, wallet_contract, wallet_sk, address_registrar, .. } =
        TestContext::new().await?;

    let caller = worker.root_account()?;
    let deposit_amount = NearToken::from_near(3);
    let create_tx = |receiver_id: &AccountId, nonce: u64| {
        let method = "register";
        let args = br#"{"account_id": "birchmd.near"}"#;
        let action = Action::FunctionCall {
            receiver_id: receiver_id.to_string(),
            method_name: method.into(),
            args: args.to_vec(),
            gas: Gas::from_tgas(10).as_gas(),
            yocto_near: 0,
        };
        utils::create_signed_transaction(
            nonce,
            receiver_id,
            Wei::new_u128(deposit_amount.as_yoctonear() / (MAX_YOCTO_NEAR as u128)),
            action,
            &wallet_sk,
        )
    };

    // External caller gets a refund when the cross-contract call fails
    let pre_tx_account_balance = caller.view_account().await?.balance;
    let receiver_id: AccountId = "fake.near".parse()?;
    let result = wallet_contract
        .rlp_execute_from(
            &caller,
            receiver_id.as_str(),
            &create_tx(&receiver_id, 0),
            deposit_amount,
        )
        .await?;
    assert!(!result.success);
    let post_tx_account_balance = caller.view_account().await?.balance;
    assert!(
        pre_tx_account_balance.as_yoctonear() - post_tx_account_balance.as_yoctonear()
            < deposit_amount.as_yoctonear()
    );
