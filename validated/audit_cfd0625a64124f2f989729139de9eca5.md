## Title
Webhook `shop-domain` (and `topic`/`webhook-id`/`api-version`) headers are trusted without being covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
The bug class in the external report is "a value that is acted upon is not the same value that was authenticated." In `ShopifyAPI::Webhooks::Request`, the HMAC signature only covers the raw request body, while the `shop` (tenant identity), `topic`, `webhook_id`, and `api_version` are taken from unauthenticated HTTP headers and passed straight into the webhook handler.

### Finding Description
`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and compares it to the `hmac` field of the same object using `Context.api_secret_key`. [1](#0-0) 

For `Webhooks::Request`, `to_signable_string` returns only the raw body — `shop`, `topic`, `webhook_id`, and `api_version` are read from separate headers and are never part of the signed string: [2](#0-1) 

`Webhooks::Registry.process` validates only this body HMAC, then constructs the tenant-scoped metadata passed to the app's handler directly from the unauthenticated `request.shop` header: [3](#0-2) 

The equality that should hold is: `shop authenticated by the app secret == shop the handler acts on`. In reality, the app's `api_secret_key` is a single, static, per-app secret shared across **every merchant** that installs the app — it is not shop-specific. Because of this, `(body, hmac)` is a valid pair for *any* shop using the app, not just the shop named in the `x-shopify-shop-domain` header. An attacker who installs the app on their own store receives genuine webhooks with a valid `(raw_body, hmac)` pair signed with the app's shared secret. They can then replay that exact `(raw_body, hmac)` pair directly to the app's public webhook endpoint while substituting a victim shop's domain in the `x-shopify-shop-domain` header (and any topic/webhook-id/api-version they like). `HmacValidator.validate` still succeeds because it only checks the body, and `Registry.process` will dispatch the forged event as if it came from the victim shop.

### Impact Explanation
This breaks the tenant/shop identity binding and results in cross-tenant impersonation: an app's webhook handler processes attacker-controlled data (order/customer/product/app-uninstalled events, etc.) under a victim shop's identity, potentially corrupting per-shop state, triggering shop-scoped side effects (e.g., billing, provisioning, deletion on uninstall handling), or leaking/mutating another merchant's data — a Critical-tier cross-tenant access issue per the given impact rubric.

### Likelihood Explanation
High. Any unprivileged internet user can install the app for free on their own development/trial store, capture one legitimate webhook `(body, hmac)` pair from their own tenant, and immediately replay it against the shared public webhook endpoint with an arbitrary spoofed `shop-domain` header — no secrets, tokens, or elevated access required.

### Recommendation
Include the shop domain (and ideally topic/webhook id/api version) in the signed payload used for verification, or otherwise cryptographically bind the claimed shop to the request before dispatching to the handler — for example, requiring callers to independently confirm `request.shop` corresponds to a shop with a known, previously-established session/install record before trusting it, and documenting this requirement prominently since `Registry.process` currently offers no such binding.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com`; trigger any webhook topic the app subscribes to and capture the raw POST body and `X-Shopify-Hmac-Sha256` header sent by Shopify to the app's webhook endpoint.
2. Replay the exact same request to the app's public webhook endpoint, keeping `raw_body` and `x-shopify-hmac-sha256` unchanged, but set `x-shopify-shop-domain: victim.myshopify.com` (and any desired `x-shopify-topic`/`x-shopify-webhook-id`).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which validates successfully because only `raw_body` is signed.
4. The handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: "victim.myshopify.com", body: request.parsed_body, ...)`, causing the app to act on attacker-supplied data attributed to the victim shop.
