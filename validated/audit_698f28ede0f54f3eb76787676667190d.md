Audit Report

## Title
Unprivileged client can overwrite an in-flight `web_api_trigger` callback by MessageID collision, orphaning the earlier request - (File: core/services/gateway/handlers/capabilities/handler.go)

## Summary
`HandleLegacyUserMessage` stores the caller's callback in `h.savedCallbacks` keyed only by the client-supplied `MessageID`, with no check for an existing entry before overwriting, confirmed at [1](#0-0) . Because `MessageID` is fully attacker-controlled — copied verbatim from the JSON-RPC request ID by `ValidatedMessageFromReq` [2](#0-1)  and only length/format checked by `Message.Validate()` [3](#0-2)  — a client can send two `web_api_trigger` requests with the same `message_id` before the first is answered, causing the second to silently overwrite the first's saved callback and permanently orphan the first request.

## Finding Description
The gateway's `ProcessRequest` decodes an incoming legacy request, validates it via `msg.Validate()` (length/format only, no uniqueness constraint), and dispatches to `h.HandleLegacyUserMessage(ctx, msg, callback)` [4](#0-3) . Inside the handler, the callback is stored unconditionally at the client-controlled key `msg.Body.MessageID`:
```go
h.mu.Lock()
h.savedCallbacks[msg.Body.MessageID] = &savedCallback{id: msg.Body.MessageID, createdAt: time.Now(), Callback: callback}
don := h.don
h.mu.Unlock()
``` [1](#0-0) 

There is no existence check (`if _, exists := h.savedCallbacks[...]; exists { ... }`) prior to this write, unlike the sibling `RequestCache.NewRequest`, which explicitly rejects duplicate keys [5](#0-4) , and unlike `confidentialrelay`'s duplicate-ID guard [6](#0-5) . When a node later responds, `handleWebAPITriggerMessage` looks up and deletes the single surviving entry by `MessageID` and answers only that callback [7](#0-6) . The only other path a callback can be removed is `pruneCallbacks`, which drops expired/excess entries without ever invoking the associated callback [8](#0-7) .

I confirmed each code fragment cited in the original report is present verbatim in this codebase at the stated locations, and traced the full call path from `gateway.ProcessRequest` through `HandleLegacyUserMessage` to `handleWebAPITriggerMessage`/`pruneCallbacks`, verifying no additional authentication, per-sender namespacing, or duplicate-key protection exists anywhere in that path. `ProcessRequest` only enforces a length cap on the raw JSON-RPC `ID` (200 chars) and format validation via `msg.Validate()` [9](#0-8)  — neither constrains `MessageID` to be unique or scopes it per authenticated caller. The `savedCallbacks` map is a single handler-wide map shared across all callers of that DON/service [10](#0-9) , so a collision (whether from the same caller sending two requests, or — depending on how signer identity does or doesn't factor into `MessageID` generation upstream — potentially different callers) silently drops the earlier request without any indication to that caller.

## Impact Explanation
This is a response-integrity/availability defect: a caller's HTTP request hangs until the gateway's own timeout mechanism (`callback.Wait(ctx)` in `ProcessRequest`) fires, returning a generic timeout error rather than the real response, while DON compute/network resources were already spent fanning out the orphaned request to all DON members [11](#0-10) . It does not enable fund theft, key exfiltration, authentication bypass, or request impersonation — the closest applicable in-scope category is "cross-user response corruption" only in the degenerate case of same-caller retries under a duplicate self-chosen ID, since nothing in the reviewed code establishes that two different unprivileged callers can even supply IDs into the same `savedCallbacks` namespace without colluding (both would need to know or coordinate the same string). Absent evidence that `MessageID` collisions are practically achievable *across distinct unprivileged parties without cooperation*, the realistic impact is that a client can only orphan its own previous request — a self-inflicted DoS with no cross-user integrity break.

## Likelihood Explanation
Triggering the self-collision is trivial for any caller (send two `web_api_trigger` requests with identical `message_id` before the first is answered), but the security-relevant scenario (attacker degrading *another* user's request) requires the attacker to know or predict the victim's `message_id`, which is not established by the report or the code inspected — `MessageID` values are chosen by the calling client itself, not derived from anything guessable by a third party. The finding is accurate as a code-quality/lack-of-duplicate-detection issue, but does not by itself demonstrate a cross-user exploit path.

## Recommendation
Add a duplicate-key guard in `HandleLegacyUserMessage`, symmetric with `RequestCache.NewRequest`, to reject a `web_api_trigger` request whose `MessageID` already has a pending entry in `h.savedCallbacks`, returning a distinct "duplicate MessageID" error to the caller instead of silently overwriting the prior entry.

## Proof of Concept
1. Send `HandleLegacyUserMessage` request with `msg.Body.MessageID = "X"`, `method = web_api_trigger`; gateway stores callback A at key `"X"` and fans out to DON members.
2. Before any node responds, send a second request with the same `MessageID = "X"`; this overwrites `h.savedCallbacks["X"]` with callback B (`core/services/gateway/handlers/capabilities/handler.go:411-414`).
3. A DON node responds for `MessageID = "X"`; `handleWebAPITriggerMessage` finds and answers only callback B (`handler.go:148-161`); callback A's `SendResponse` is never invoked and its HTTP request times out via `callback.Wait(ctx)` in `gateway.go`.

This can be reproduced as a Go unit test in `core/services/gateway/handlers/capabilities/handler_test.go` by invoking `HandleLegacyUserMessage` twice with the same `MessageID` and two distinct callbacks, then asserting only the second callback's `SendResponse` fires when `handleWebAPITriggerMessage` is invoked.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageID]
	delete(h.savedCallbacks, msg.Body.MessageID)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JSONRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil

func (h *handler) pruneCallbacks() {
	h.mu.Lock()
	defer h.mu.Unlock()

	// First, remove expired callbacks.
	maxAge := time.Duration(h.config.CallbackMaxAgeSec) * time.Second
	now := time.Now()
	var expired int
	for id, cb := range h.savedCallbacks {
		if now.Sub(cb.createdAt) > maxAge {
			delete(h.savedCallbacks, id)
			expired++
		}
	}

	// If there are still too many callbacks, sort them by creation time and remove the oldest ones.
	maxSize := h.config.MaxSavedCallbacks
	var evicted int
	if len(h.savedCallbacks) > maxSize {
		type entry struct {
			id        string
			createdAt time.Time
		}
		entries := make([]entry, 0, len(h.savedCallbacks))
		for id, cb := range h.savedCallbacks {
			entries = append(entries, entry{id, cb.createdAt})
		}
		sort.Slice(entries, func(i, j int) bool {
			return entries[i].createdAt.Before(entries[j].createdAt)
		})
		// Trim to maxSize/2 to avoid sorting the list too frequently.
		for _, e := range entries[:len(entries)-maxSize/2] {
			delete(h.savedCallbacks, e.id)
			evicted++
		}
	}

	if expired > 0 || evicted > 0 {
		h.lggr.Infow("Pruned savedCallbacks", "expired", expired, "evicted", evicted, "remaining", len(h.savedCallbacks))
	}
```
