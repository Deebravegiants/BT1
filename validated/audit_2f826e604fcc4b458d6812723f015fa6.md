### Title
Position-NFT sale frontrun: owner can drain collateral between listing and transfer because transfers have no freeze/commit state - (File: contracts/position-nft/src/contract.rs)

### Summary
The bug class is "an NFT that packages economic value can be sold while its owner retains the ability to mutate that value up to the instant the transfer executes." In `GovNFTTimelock` the drain vector was a pre-committed `commitSplit`/`finalizeSplit`. In XOXNO Lending the same class maps directly onto the position NFT: `account_id == token_id`, the controller resolves ownership lazily via `owner_of`, and a transfer moves the entire lending account with no controller-side state change or lock (`contracts/position-nft/README.md`, "Transferring the token transfers the whole position... Nothing in the controller changes on transfer"). The stock OpenZeppelin `transfer`/`transfer_from`/`approve` surface has no freeze or commit mechanism (grep over `contracts/position-nft/src` finds no freeze/escrow/lock logic). A seller who approves a marketplace (or signs a sale) can frontrun the buyer's purchase transaction with `controller::withdraw`, `repay_debt_with_collateral(close_position = true)`, or `swap_collateral` on the still-owned account, delivering an emptied NFT.

### Finding Description
The position NFT is an ordinary transferable token whose value is the underlying account's supply positions. There is no committed/frozen transfer state:

- `position-nft::transfer`/`transfer_from` are stock OpenZeppelin entrypoints; ownership is resolved live by `try_account_owner`/`owner_of` on every controller call (`contracts/position-nft/README.md`, table row "any owner check (`try_account_owner`)").
- Between approving a marketplace and the buyer's transaction executing, the seller remains `owner_of(account_id)` and passes `require_owner_or_delegate` in `contracts/controller/src/account.rs`, so all owner-gated exits remain available.
- A debt-free account exits all post-pool risk gates immediately (`require_post_pool_risk_gates` returns early when `account.debt_free()` — `contracts/controller/src/risk/validation.rs:29-32`), so `process_withdraw` in `contracts/controller/src/positions/supply.rs` can pull 100% of every supply leg. With debt, `repay_debt_with_collateral`/`swap_collateral` in `contracts/controller/src/strategies/` still let the seller extract the full collateral surplus down to HF = 1 before the transfer confirms.
- Nothing in the controller keys withdrawals to pending NFT approvals; `position-nft::approve` "grants only the power to transfer that NFT" and does not restrict owner actions (`scripts/permissionless_entrypoints.txt:113`).

This is exactly the report's scenario minus the timelock: the "pre-committed split" is unnecessary — any ordinary withdraw works — because XOXNO has no frontrun protection at all rather than a partial one.

### Impact Explanation
A buyer purchases the NFT at a price reflecting the account's collateral (visible via `get_account_positions`/indexer state at quote time). The seller frontruns the purchase in the same ledger window, withdraws the collateral to themselves, and the buyer's atomic buy settles delivering a hollow account. Result: theft of user funds — the buyer's payment is taken in exchange for an NFT whose backing was drained. Per the accepted-impact list this is theft of user funds; severity Medium, consistent with the source report's low/medium rating and with the impact being conditional on a victim buying a listed NFT.

### Likelihood Explanation
Requires an off-chain or marketplace-mediated NFT sale (no in-protocol marketplace exists), plus the buyer trusting quoted collateral state. The attack needs no privilege, no price manipulation, and no oracle interaction — only that the seller's `withdraw` lands before the buyer's `transfer_from`. Given NFT/account sales are a plausible OTC flow for leveraged positions, likelihood is moderate; hence Medium rather than High.

### Recommendation
Mirror the accepted fix from the report: add a freeze/commit state to position NFTs. Require the owner to commit a transfer freeze (disabling `withdraw`, `repay_debt_with_collateral`, `swap_collateral`, `borrow`, `multiply`, and delegate changes for that `account_id`) that, after a delay, enables the transfer; any transfer attempt on a non-frozen account — or owner actions on a frozen one — reverts. Implement the flag in controller storage keyed by `account_id` and check it in the owner/delegate auth path (`require_owner_or_delegate`) and in a `_update`/`transfer` hook on the NFT contract, taking care to exempt controller-driven `burn`/`mint` so liquidation and bad-debt cleanup are not blocked.

### Proof of Concept
Sequence, all reachable by an unprivileged seller:

1. Alice supplies 100,000 USDC via `controller::supply` (debt-free account, NFT token id `N`).
2. Alice calls `position-nft::approve(marketplace, N)` / lists the NFT; buyer Bob observes `get_account_positions(N)` showing ~$100k collateral and submits his buy.
3. Alice submits `controller::withdraw(caller=alice, account_id=N, assets=[USDC, WITHDRAW_ALL_SENTINEL])` ordered before Bob's tx. Because the account is debt-free, `require_post_pool_risk_gates` returns early (`contracts/controller/src/risk/validation.rs:30-32`) and the full balance is paid to Alice.
4. Bob's purchase executes: `position-nft::transfer_from` moves token `N` — now an account with zero supply positions — to Bob, while payment already flowed to Alice.
5. Assert: Bob owns `N` (`owner_of(N) == bob`), `get_supply_positions(N)` is empty, Alice holds the USDC and Bob's payment.

With debt present, step 3 is replaced by `repay_debt_with_collateral(close_position=true)` plus a `withdraw` of the remainder down to HF ≥ 1, achieving the same drain.

Note: I confirmed the absence of any freeze/lock in `contracts/position-nft/src` and the permissionless owner paths, but I could not fully trace `process_withdraw`'s auth line-by-line beyond `require_owner_or_delegate` in `contracts/controller/src/account.rs` within the iteration budget; the mechanism described matches the documented invariant that the NFT owner is the account owner at call time.
