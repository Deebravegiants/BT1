Confirmed root cause: the Tron variant of `IntentGatewayV2.placeOrder` never refunds unspent `msg.value`, unlike the mainline EVM `IntentGatewayV2.sol` which explicitly refunds via `_sendValue(msg.sender, msgValue)`.

### Title
Overpaid native token in `placeOrder()` is permanently locked in Tron `IntentGatewayV2` (no msg.value refund) - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron port of `IntentGatewayV2.placeOrder()` accepts native token (`msg.value`) for order inputs and, when `order.fees > 0`, swaps native for fee token, but it never returns any leftover `msgValue` to the caller. The mainline EVM implementation of the same function performs this refund explicitly, confirming the Tron path is a divergent/incomplete port.

### Finding Description
`placeOrder` computes a running `msgValue` counter, decrementing it as native inputs are consumed [1](#0-0) , and again if a fee swap is required [2](#0-1) . Unlike the canonical EVM `IntentGatewayV2.sol`, which ends `placeOrder` with an explicit `if (msgValue > 0) { _sendValue(msg.sender, msgValue); }` [3](#0-2) , the Tron file has no equivalent statement after its fee-handling block — the function simply ends at line 506 once fees are escrowed [4](#0-3) .

Because the contract has a bare `receive() external payable {}` [5](#0-4) , it accepts and silently absorbs the difference. This differs from the analogous `_splitSurplus`/`_withdraw` accounting used elsewhere for legitimate order dust, which is tracked per-commitment and released to a beneficiary [6](#0-5) ; here the leftover `msgValue` is never recorded in any commitment's escrow (`_orders[commitment][...]`), so it cannot be withdrawn through `cancelOrder`/`withdraw` either.

Reviewing `onAccept`'s `RequestKind.SweepDust` branch confirms the only sweep mechanism transfers whatever `amount` is specified in a governance-issued `SweepDust` message to an arbitrary beneficiary, without validating that amount against any tracked "dust" balance [7](#0-6) . This provides no user-facing recovery path: the excess is not the user's to reclaim, and the operator sweep is unconstrained trust rather than a designed refund. Overpayment is realistically likely because: (1) users following the fee-swap pattern intentionally overpay `msg.value` expecting a partial refund, as documented and tested for the mainline chain [8](#0-7) , and (2) the SDK's placement flow explicitly instructs sending `nativeValue` computed from a quote plus wallet slack [9](#0-8) , so any user or integrator following the documented/SDK flow against the Tron deployment will lose the difference.

### Impact Explanation
Any user calling `placeOrder` on the Tron `IntentGatewayV2` with `msg.value` exceeding the sum of native inputs plus the actual fee-swap cost permanently loses the excess native token to the contract, with no code path to reclaim it (the funds are neither escrowed against a commitment nor exposed via a user-callable withdrawal). This is a direct, unbacked loss of user funds triggered by an ordinary unprivileged transaction (`placeOrder`), matching the "permanent freezing/loss of funds" criterion.

### Likelihood Explanation
High likelihood: the documented SDK flow and fee-swap quoting mechanism (`quoteOrderFees`) intentionally instructs callers to send `nativeValue` that may exceed the exact swap cost, relying on the contract to refund the difference — behavior explicitly implemented and tested on the mainline EVM contract but absent here. Any Tron user paying the solver fee via native-to-fee-token swap, or any user who miscalculates/overestimates `msg.value` for native inputs, will trigger this loss without any special conditions.

### Recommendation
Add the same trailing refund as the mainline EVM contract: after all native token consumption (predispatch legs, direct inputs, and fee swap) is accounted for, refund the remaining `msgValue` to `msg.sender`, e.g.:
```solidity
if (msgValue > 0) {
    (bool sent,) = msg.sender.call{value: msgValue}("");
    if (!sent) revert InsufficientNativeToken();
}
```
placed at the end of `placeOrder`, mirroring `evm/src/apps/IntentGatewayV2.sol` lines 394-397.

### Proof of Concept
1. User calls `IntentGatewayV2.placeOrder{value: X}(order, graffiti)` on the Tron deployment, where `order.inputs` includes a native-token leg of amount `A < X` (or no native input at all, `A = 0`), and `order.fees > 0` triggers the Uniswap swap path.
2. In the swap branch, `IUniswapV2Router02.swapETHForExactTokens{value: msgValue}(order.fees, path, address(this), block.timestamp)` is called with the *entire* remaining `msgValue`, not just the amount needed — see `evm/tron/contracts/apps/IntentGatewayV2.sol:474-483`. Note that, unlike the mainline contract which captures returned `amounts[0]` and subtracts it from `msgValue` for a later refund (`evm/src/apps/IntentGatewayV2.sol:383-386`), the Tron version discards the returned `amounts` entirely (line 480-482).
3. Function returns after escrowing fees; no refund logic executes.
4. `address(this).balance` retains `X - A - (actual swap cost)`, which is unrecoverable by the user; `_orders[commitment]` contains no entry for this surplus, so `cancelOrder`/`withdraw` cannot release it, and only a governance-issued `SweepDust` message could move it (to an arbitrary beneficiary the operator chooses, not necessarily the user).

### Place the order and let the SDK execute it

`executeBest()` is a bidirectional async generator. Its first update contains the exact `placeOrder` calldata and the order's native-token input amounts as `value` (`0n` for this USDC order). Add the `nativeValue` from your fee quote when paying the solver fee in native token, then sign and return the signed transaction to the generator.

```typescript title="place-and-execute.ts" lineNumbers
import { IntentOrderStatus } from "@hyperbridge/sdk"

const run = gateway.executeBest(order, MY_GRAFFITI, {
  auctionTimeMs: 15_000,
  pollIntervalMs: 5_000,
})

const first = await run.next()
if (first.done || first.value.status !== IntentOrderStatus.AWAITING_PLACE_ORDER) {
  throw new Error("Expected placement transaction")
}
const { to, data, value } = first.value

// Paying the fee in native token: add nativeValue from quoteOrderFees.
// Paying with the fee-token approval: txValue is just value.
const txValue = value + nativeValue

const signedPlacementTx = await walletClient.signTransaction({
  to,
  data,
  value: txValue,
  type: "eip1559",
})
```
