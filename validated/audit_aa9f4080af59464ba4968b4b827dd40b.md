### Title
Webhook shop identity is not bound to the HMAC signature, enabling cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, while `shop`, `topic`, `api_version`, and `webhook_id` are read directly from unauthenticated HTTP headers and are never included in the HMAC-signed material. `Webhooks::Registry.process` validates the HMAC and then passes `request.shop` straight to the handler as the tenant identifier, without checking it is bound to the signature.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
while `shop`, `topic`, `api_version`, and `webhook_id` are pulled from HTTP headers that are not part of the signed payload: [2](#0-1) 

`Registry.process` validates the HMAC over that signable string (i.e. body only) and then immediately trusts `request.shop` (a header) to construct the `WebhookMetadata` handed to the app's handler: [3](#0-2) 

`Utils::HmacValidator.validate` computes the HMAC using the single, app-wide `Context.api_secret_key` — the same secret is used for every shop that has installed the app, it is not per-shop: [4](#0-3) 

The broken identity binding is the equality that should hold but doesn't:
`shop-domain header used to select the tenant == shop bound inside the HMAC-covered bytes` — the library treats the left side as trusted while only the right side (body) is authenticated, and the left side isn't authenticated at all.

Because every merchant that installs the app shares the same `api_secret_key`, a merchant on their own shop (an "unprivileged" party relative to other tenants of the same app) can legitimately trigger a webhook to their own endpoint and obtain a genuine `(raw_body, hmac)` pair signed by the app's secret. Since the signature never covers the `shop-domain` header, that same `(raw_body, hmac)` pair remains valid if replayed to the app's webhook endpoint with the `x-shopify-shop-domain` (or `shopify-shop-domain`) header rewritten to name a *different* shop. `Registry.process` will accept the HMAC (it only checks the body bytes) and dispatch the handler with `shop: request.shop` set to the attacker-chosen victim shop, even though the payload actually originated from the attacker's own store.

### Impact Explanation
This breaks the tenant boundary the whole webhook system is meant to enforce: a merchant who is only entitled to see their own shop's events can get their handler-processed data attributed to another merchant's shop. Any host application that uses `WebhookMetadata#shop` to key persistence, cache invalidation, billing, or session lookups can be made to write/act on the wrong tenant's record — classic cross-tenant access/injection made possible purely through this gem's webhook verification not binding the identity field to the signature.

### Likelihood Explanation
Any user able to install the app on a shop they control (a normal, unprivileged flow for any Shopify app) can trigger real webhooks to observe valid `(body, hmac)` pairs, then simply replay the HTTP request with a modified shop header — no access to `api_secret_key`, TLS interception, or privileged accounts required.

### Recommendation
Bind the shop (and topic) identity into the HMAC-signed material, or otherwise cryptographically tie the `x-shopify-shop-domain` header to the signed body (e.g., include it in `to_signable_string`, or independently verify the header against the shop stored for the session/webhook subscription id) before trusting `request.shop` in `Registry.process`.

### Proof of Concept
1. App is installed on attacker's own shop `attacker.myshopify.com`; attacker triggers any subscribed webhook topic (e.g. by making an order) and captures the raw POST body and the `x-shopify-hmac-sha256` header — this is a legitimately signed payload using the app's shared `api_secret_key`.
2. Attacker replays the exact same body and `hmac` header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `request.to_signable_string` (the raw body) against the hmac — this succeeds because the body/hmac pair is genuine. [5](#0-4) 
4. `handler.handle` is invoked with `shop: request.shop` equal to `"victim-shop.myshopify.com"`, even though the event content actually came from the attacker's shop — the host app processes attacker-controlled data under the victim's tenant identity.
