### Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from only the raw request body, while the `shop` value handed to webhook handlers is read from an unsigned HTTP header. An attacker who obtains any one genuine `(body, hmac)` pair from Shopify (e.g. by installing the app on their own store and receiving a real webhook) can replay that exact body and HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain`/`shopify-shop-domain` header for a victim shop. The HMAC check still passes because it never covers the shop header, so the app's webhook handler executes believing the payload belongs to the victim tenant.

### Finding Description
`Utils::HmacValidator.validate` verifies a `VerifiableQuery`'s `hmac` against `to_signable_string`. [1](#0-0) 

For webhook requests, `to_signable_string` returns only the raw body — it does not include the topic, api-version, webhook-id, or (critically) the shop domain: [2](#0-1) [3](#0-2) 

`shop` is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, which is attacker-controlled on any HTTP request the attacker sends and is never mixed into the HMAC computation: [2](#0-1) 

`Registry.process` validates the HMAC (over body only) and then dispatches the handler using this unauthenticated `request.shop` value as the tenant identity: [4](#0-3) 

This breaks the intended identity binding: `hmac == HMAC(secret, body)` is meant to prove "this payload came from Shopify for shop X," but the gem actually only proves "this body came from Shopify for *some* shop," and lets the caller supply which shop (`X`) that body is attributed to. In equality terms, the binding the gem should enforce is `shop_authenticated_by_hmac == shop_used_by_handler`, but it instead enforces only `hmac_valid_for(body)` while `shop_used_by_handler` is taken from unauthenticated header bytes.

### Impact Explanation
This is a cross-tenant identity confusion: an attacker who has captured or generated one legitimate `(raw_body, hmac)` pair (trivially available to them by installing the app on a shop they control and receiving any real webhook) can replay that pair against the same endpoint with a forged shop-domain header naming a victim shop. Any host application that keys per-tenant behavior (session/token lookup, data writes, GDPR/redact actions, order/customer processing, etc.) off `WebhookMetadata#shop` will process the request as if it originated from the victim shop, using attacker-controlled body content. Because `customers/redact`, `shop/redact`, and `customers/data_request` are mandatory topics routed through this same `process` path, this can also be leveraged to trigger destructive/compliance actions against a victim tenant. This qualifies as cross-tenant access.

### Likelihood Explanation
The prerequisite — obtaining one genuine webhook body+HMAC pair — is trivial for any developer/attacker who installs the target app on their own shop (a normal, unprivileged action, not requiring `api_secret_key`, an access token, or any privileged credential). Crafting an HTTP request with a custom `shop-domain` header to the app's public webhook endpoint requires no special access. The only constraint is that the replayed body must be accepted by the specific handler logic downstream, which is highly application-dependent but does not change the fact that the gem itself fails to bind `shop` to the HMAC.

### Recommendation
Include the shop domain (and ideally the webhook id/topic) inside the HMAC-signable content, or otherwise have `HmacValidator`/`Registry.process` cryptographically bind the header-derived `shop` value before it is trusted. At minimum, document that `WebhookMetadata#shop` is not covered by the HMAC and must not be trusted as a tenant identifier without additional verification (e.g., cross-checking against a known/stored shop for the webhook's `webhook_id`).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and receives (or triggers) a legitimate webhook delivery, capturing the exact `raw_body` and its valid `x-shopify-hmac-sha256` value (computed by Shopify with the app's real secret).
2. Attacker POSTs to the app's webhook endpoint with the same `raw_body` and same `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks the HMAC against `raw_body` — validation succeeds: [5](#0-4) 
4. The handler receives `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: <attacker-controlled data>)` and processes it as if the victim shop sent it: [6](#0-5)
