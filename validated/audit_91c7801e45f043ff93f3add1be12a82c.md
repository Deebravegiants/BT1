### Title
Per-Origin `autoApprove`/`trusted` Flags Are Not Scoped to Wallet Accounts, Causing New Accounts to Inherit Prior Consent - (File: `features/connected-origins/module/connections.js`)

### Summary
`ConnectedOrigins` stores `trusted` and `autoApprove` as attributes of an *origin* only, never scoped to a specific wallet account. When a user later creates a new wallet account, `updateConnectedAccounts` silently recomputes `connectedAccountsAtom` over *all* currently enabled wallet accounts and folds the new account into every already-trusted origin's exposed account set, without any new consent step for that specific account.

### Finding Description
`isTrusted`, `isAutoApprove`, and `setAutoApprove` key exclusively on `{ origin }`: [1](#0-0) 

There is no wallet-account dimension in this state — a decision the user made ("trust this dApp" / "auto-approve this dApp") when only `exodus_0`/`exodus_1` existed is stored as a blanket property of the origin itself.

Separately, `#getAccounts`/`updateConnectedAccounts` recompute the full account map from `enabledWalletAccountsAtom` (i.e., *every* currently enabled wallet account), and persist it into `connectedAccountsAtom` for already-trusted origins: [2](#0-1) [3](#0-2) 

This is confirmed by the test `updates connected accounts when adding a wallet account`, which shows that after a wallet account (`exodus_2`) is created post-trust, it is automatically added to `connectedAccountsAtom` for an origin that was trusted before that account existed: [4](#0-3) 

`getConnectedAccounts` then exposes this data (addresses across all wallet accounts, active one first) to the connected dApp as long as `isTrusted` is true, with no per-account gate: [5](#0-4) 

The root cause parallels the reported Uniswap `LimitOrderHook` bug: a shared piece of state (fee accrual / trust-and-auto-approve consent) is distributed/applied based on the *current* membership set (LP share / enabled wallet accounts) rather than being scoped to the point in time when each member (LP / wallet account) actually joined and the user explicitly consented for it.

### Impact Explanation
- At minimum, this is a **cross-account privilege bleed**: a dApp that a user trusted only for their original account(s) automatically gains visibility into the address of any wallet account created afterward, without a fresh per-account approval prompt.
- More severely, because `autoApprove` is also a bare per-origin boolean (see `isAutoApprove`/`setAutoApprove` above, and the `DAppAutoApproveSet`/`DAppSignTransactionRequest` analytics events referencing this flow: `libraries/analytics-validation/src/dapps/d-app-auto-approve-set.schemasafe.json`), any consumer of `connectedOrigins.isAutoApprove({ origin })` that skips a signing confirmation for that origin has no way to know from this API whether the *specific* wallet account being signed for was the one the user actually consented to auto-approve. If (as the API's shape strongly implies) auto-approve is consulted only by origin when deciding to silently approve a signing request, then a dApp auto-approved under one account could have transactions from a newly created account silently signed without the user ever confirming for that account — a direct unauthorized-signing risk.
- Note: I was unable to locate, within the indexed portion of the codebase, the exact UI/signing call site that reads `connectedOrigins.isAutoApprove` immediately before invoking the tx-signer to confirm whether it cross-checks the specific wallet account against the origin's original consent. This piece of the chain should be verified directly (the file may exist but not be covered by the current index, or may live in a private/UI-specific package not indexed here).

### Likelihood Explanation
High for the address-exposure variant: it requires only normal, expected user actions (trust a dApp, then create a new wallet account) with no attacker interaction — the "leak" is automatic and always occurs, per the passing test suite itself. The auto-approve/signing-bypass variant likelihood depends on the un-verified call site described above, so it should be treated as a hypothesis pending confirmation, not a proven exploit.

### Recommendation
- Scope `trusted`/`autoApprove` (and the resulting exposed `connectedAccountsAtom` entries) to specific wallet-account identifiers rather than to the origin alone, or require an explicit new-account consent step before extending an existing origin's trust/auto-approve state to newly created wallet accounts.
- Audit every call site of `connectedOrigins.isAutoApprove` to confirm it is never used to bypass a signing prompt for a wallet account that was not part of the account set at the time auto-approve was granted.

### Proof of Concept
1. User visits `exodus.com`, calls `connectedOrigins.add({ origin: 'exodus.com', trusted: true, connectedAssetName: 'solana' })` — origin is trusted while only `exodus_0`/`exodus_1` exist.
2. User creates a new wallet account `exodus_2`.
3. `connectedOrigins.updateConnectedAccounts()` runs (e.g., triggered by the wallet-accounts lifecycle) and adds `exodus_2`'s address into `connectedAccountsAtom` for the already-trusted `exodus.com`, per [4](#0-3) , without any new prompt.
4. `exodus.com` calls `connectedOrigins.getConnectedAccounts({ origin: 'exodus.com' })` and now receives `exodus_2`'s address as part of the connection, exposing an account the user never explicitly approved this origin for.

  getConnectedAccounts = async ({ origin }) => {
    const isTrusted = await this.isTrusted({ origin })
    if (!isTrusted) return []

    const value = await this.#getOrigin({ origin })
    const assetNames = [value.connectedAssetName, ...(value.assetNames ?? [])].filter(
      (name, index, ary) => Boolean(name) && ary.indexOf(name) === index
    )

    const activeWalletAccount = await this.#activeWalletAccountAtom.get()
    const accounts = await this.#connectedAccountsAtom.get()

    const connectedAccounts = []
    for (const name of Object.keys(accounts)) {
      if (name === activeWalletAccount) continue
      connectedAccounts.push({ name, addresses: pick(accounts[name].addresses, assetNames) })
    }

    connectedAccounts.unshift({
      name: activeWalletAccount,
      addresses: pick(accounts[activeWalletAccount].addresses, assetNames),
    })

    return connectedAccounts
  }

    const difference = xor(Object.keys(walletAccounts), Object.keys(connectedAccounts))
    if (difference.length === 0) {
      // up-to-date
      return
    }

    const connectedOrigins = await this.#connectedOriginsAtom.get()
    const assetNames = this.#getConnectedAssets(connectedOrigins)
    const updatedAccounts = await this.#getAccounts(assetNames)

    await this.#connectedAccountsAtom.set(updatedAccounts)
