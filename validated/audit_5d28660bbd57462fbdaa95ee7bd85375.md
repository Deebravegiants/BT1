### Title
Third-party supply top-up force-restamps a victim's risk parameters, blocking their borrows and withdrawals - (File: contracts/controller/src/positions/supply.rs)

### Summary
`supply(caller, account_id, spoke_id, assets)` is permissionless for topping up *existing* supply legs of any account (`require_third_party_existing_supply`, supply.rs:78-97). Every merged leg calls `refresh_supply_risk_params` with `RiskRefreshScope::FullTuple`, which unconditionally overwrites the stored `loan_to_value` with the *current* listing value (params.rs:35). Post-pool solvency for `borrow` and `withdraw` is evaluated against that restamped LTV, so a dust-sized top-up by a stranger can downgrade a victim's collateral weighting and freeze actions that were previously valid. This is the direct analog of "anyone can increase liquidity on a foreign position": the pool credits a foreign owner's position and, as a side effect, mutates that owner's stored risk parameters without their consent.

### Finding Description
- `process_supply` (supply.rs:40) loads the victim's `Account` via `account_id` and only requires that a non-owner/non-delegate caller deposit into hub assets the account already holds — `assert_with_error!(account.supply_positions.contains_key(...), NotAuthorized)` (supply.rs:89-95).
- `merge_supply_leg` (supply.rs:275-324) then calls `refresh_supply_risk_params(..., RiskRefreshScope::FullTuple)`.
- `refresh_supply_risk_params` (params.rs:25-40) always sets `position.loan_to_value = effective_config.loan_to_value`; only the liquidation tuple (threshold/bonus/fees) goes through the `favors_liquidator` + hypothetical HF ≥ 1.05 gate in `apply_gated_liquidation_params` (params.rs:68-93). The HF gate is evaluated against the *old* scaled amounts, so the liquidation tuple cannot be weaponized — but the LTV write is unguarded.
- `withdraw` must pass `enforce_post_pool_solvency` (supply.rs:158), which uses the per-position LTV-weighted collateral. The same restamp is reachable directly via permissionless `update_account_threshold(caller, false, [victim])`, but the supply path is the exact class match: an uninvited liquidity increase that silently mutates the owner's stored parameters.

The behavior is partially acknowledged in-tree: `tests/test-harness/tests/controller/security_audit.rs:507-532` (`poc_third_party_top_up_force_restamps_ltv`) demonstrates a stranger's 1-unit top-up downgrading a victim's LTV and blocking a borrow that would otherwise succeed — but it only asserts the borrow-block, not the withdrawal-block, which is the fund-freezing consequence.

### Impact Explanation
Temporary freezing of funds (Medium). If governance lowers an asset's `loan_to_value` (a routine risk action), accounts created earlier keep the stale, higher LTV stamp until touched. Any unprivileged address can force the downgrade on a victim by supplying 1 base unit of the already-held asset; afterward `borrow` and `withdraw` on that account revert on the LTV-weighted solvency check even though the victim never consented and did nothing. The victim's collateral is locked until they repay debt or governance restores parameters — a griefing/temporary-freeze, not theft, since the liquidation tuple is protected by the HF ≥ 1.05 gate.

### Likelihood Explanation
Reachable by any address holding a dust amount of a listed token; requires only that (a) the victim supplies an asset whose listing LTV was lowered after their position was stamped, and (b) the victim carries debt, so the solvency check binds. No privileged access, oracle manipulation, or victim interaction is needed.

### Recommendation
Gate the parameter restamp on the caller's authority: skip `refresh_supply_risk_params` (or apply only `RiskRefreshScope` for legs the owner opted into) when `!is_owner_or_delegate`. Alternatively, never restamp `loan_to_value` to a *lower* value on a third-party top-up — take `min(stored, current)` only on owner-initiated supplies — and/or evaluate withdraw solvency against liquidation threshold rather than the restampable LTV snapshot. Note `update_account_threshold(caller, has_risks=false, ids)` exposes the same unconditional LTV restamp permissionlessly; if the restamp-on-touch model is kept deliberately, the freeze risk should at minimum be documented as accepted alongside the existing `poc_third_party_top_up_force_restamps_ltv` test.

### Proof of Concept
Extends the existing `poc_third_party_top_up_force_restamps_ltv` (security_audit.rs:507):

```rust
#[test]
fn poc_topup_freezes_victim_withdrawal() {
    let mut t = LendingTest::new().standard_two_asset_dust_disabled();

    // Alice supplies USDC and borrows ETH at the edge of solvency.
    t.supply(ALICE, "USDC", 10_000.0);
    t.borrow(ALICE, "ETH", 3.4);                    // passes under LTV 8000
    let id = t.resolve_account_id(ALICE);

    // Confirm Alice can withdraw a slice while her stored LTV is stale.
    t.withdraw(ALICE, "USDC", 100.0);               // succeeds

    // Governance lowers USDC loan_to_value after Alice's position is stamped.
    t.edit_asset_config("USDC", |c| { c.loan_to_value = 5_000; });

    // Bob (stranger) tops up 1 unit of Alice's existing USDC supply leg.
    t.try_supply_to_account(BOB, ALICE, "USDC", 1.0)
        .expect("third-party top-up of existing leg allowed");

    // The merge restamps Alice's stored LTV to 5_000 ...
    let (ltv, _) = supply_ltv_and_lt(&t, id, "USDC");
    assert_eq!(ltv, 5_000);

    // ... and her withdrawal now reverts on LTV-weighted solvency:
    // her collateral is frozen until debt is repaid.
    let blocked = t.try_withdraw(ALICE, "USDC", 100.0);
    assert_contract_error(blocked, errors::INSUFFICIENT_COLLATERAL);
}
```

Uncertainty note: I verified the restamp path (`merge_supply_leg` → `refresh_supply_risk_params`, unconditional LTV write at params.rs:35) and the documented behavior that `withdraw`/`borrow` require LTV-weighted solvency (docs/reference/endpoints.md:55, supply.rs:158 `enforce_post_pool_solvency`), but did not open `risk/totals.rs`/`enforce_post_pool_solvency` to confirm the exact LTV read inside the solvency routine; the freeze claim rests on that documented contract plus the existing borrow-block PoC. If the solvency check uses only the liquidation threshold (not the per-position LTV), the impact degrades to borrow-blocking only, which is already documented and should be treated as an accepted ADR choice (no finding).
