### Title
Webhook shop/topic/id/api-version headers are not covered by the HMAC, allowing cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, and `Utils::HmacValidator.validate` verifies the HMAC exclusively against that body. All other request headers consumed by the library — `shop`, `topic`, `webhook_id`, and `api_version` — are read from unauthenticated HTTP headers and passed straight into `WebhookMetadata` and the app's registered handler without any cryptographic binding to the signed body.

### Finding Description
`Utils::HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the `hmac` accessor [3](#0-2) . For webhooks, `to_signable_string` is defined as simply `@raw_body` [2](#0-1) , while `shop`, `topic`, `api_version`, and `webhook_id` are all pulled from HTTP headers via `shopify_header` with no signature coverage [4](#0-3) .

`Registry.process` trusts these unauthenticated header values once the body HMAC checks out, dispatching to the app's handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` [5](#0-4) . This breaks the intended identity binding: `shop-domain(header) == shop(HMAC-verified tenant)`. In reality only `body == HMAC(body)` is proven; the `shop` (and `topic`/`webhook_id`) fields are attacker-controllable bytes distinct from the bytes actually verified.

Since a merchant/attacker who has one legitimate webhook delivery for their own shop (with a valid HMAC over a given body) can capture that raw body + HMAC pair, and replay it to the app's webhook endpoint with an arbitrary `x-shopify-shop-domain` (and `x-shopify-topic`/`x-shopify-webhook-id`) header, the app's handler will process the request as if it originated from a different, victim tenant, because HMAC validation still succeeds (it only checks the untouched body).

### Impact Explanation
This is a cross-tenant identity-binding break: the field acted upon (`shop`, used by host applications as the tenant/session key to persist orders, customer data, or trigger tenant-scoped side effects) is not covered by the HMAC that is meant to authenticate the webhook's origin. An attacker controlling one shop's legitimate webhook traffic can forge deliveries that appear to originate from another shop, leading to cross-tenant data confusion/exfiltration in applications built on this gem's documented webhook processing API.

### Likelihood Explanation
Exploitation requires the attacker to already have a legitimate webhook (any topic they can trigger on their own installed shop) delivered with a valid `hmac-sha256` value for a chosen body, plus the ability to POST to the app's public webhook endpoint with modified headers — both are unprivileged and require no `api_secret_key`, access token, or elevated access.

### Recommendation
Include the `shop-domain`, `topic`, `webhook-id`, and `api-version` headers (in addition to the raw body) in the HMAC-signed material used by `Request#to_signable_string`, or otherwise cryptographically bind the shop/topic identity to the signature computation before dispatching to registered handlers in `Registry.process`.

### Proof of Concept
1. Attacker's own shop `attacker.myshopify.com` has a webhook subscription registered against the app's endpoint for topic `orders/create`.
2. Shopify delivers a webhook with body `B` and header `x-shopify-hmac-sha256: HMAC(B, secret)` — HMAC verifiable since it is `HMAC_SHA256(secret, B)` per `compute_signature` [6](#0-5) .
3. Attacker replays the exact same body `B` and `hmac-sha256` header to the app's endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` and/or a different `x-shopify-topic`.
4. `Utils::HmacValidator.validate` succeeds because only `B` is checked [7](#0-6) .
5. `Registry.process` invokes the app's handler with `WebhookMetadata` carrying `shop: "victim-shop.myshopify.com"` [8](#0-7) , causing the application to act on data as if it came from the victim tenant.
