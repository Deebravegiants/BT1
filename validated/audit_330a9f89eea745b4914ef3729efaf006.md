### Title
Webhook `shop` field is trusted for tenant routing without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook by validating only the HMAC of the raw request body, then hands the *unauthenticated* `shop` (and `topic`) header values straight to the app's handler as the tenant identity. Because the shop-domain header is not part of the signed payload, any request bearer that can obtain one valid `(raw_body, hmac)` pair for the app's secret can replay it while swapping the `x-shopify-shop-domain` header to a different, victim shop, and the signature check will still pass.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and defines the string that gets HMAC-verified as just the raw body: [1](#0-0) 

The `shop` accessor, however, is read straight from the (attacker-controllable, in the sense described below) `shopify-shop-domain` header and is never mixed into `to_signable_string`: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC purely over `to_signable_string` (i.e., the body) and compares it against the `hmac` header: [3](#0-2) 

`Registry.process` uses exactly this check as its sole authentication gate, then immediately trusts `request.shop` to build the `WebhookMetadata` that is dispatched to the host application's handler: [4](#0-3) 

`WebhookMetadata.shop` is a plain, unauthenticated string field consumed by the handler as the tenant/shop context for whatever action it performs (e.g. looking up a `Session`, writing GDPR-redaction records, deleting shop data, crediting an order, etc.): [5](#0-4) 

**Broken equality:** the identity that is cryptographically verified is `HMAC(client_secret, raw_body)`, while the identity that is *acted upon* by the application (`shop`) comes from a header that is completely outside that signed scope:
`verified(raw_body) == authentic` is asserted, but the code then behaves as if `verified(raw_body) == authentic(shop)` — these are not the same claim.

Compare this to `Auth::Oauth::AuthQuery`, where `shop` **is** folded into `to_signable_string` and therefore is bound by the HMAC: [6](#0-5) 
This shows the gem is aware that identity fields need to be inside the signed string elsewhere, but the webhook `Request` class does not apply the same discipline to `shop` (or `topic`/`api_version`/`webhook_id`).

### Impact Explanation
Any party who can produce (or capture) one genuine `(raw_body, hmac)` pair signed with the app's `client_secret` — for example, by triggering a real webhook delivery to *their own* shop that has the same app installed — can replay that exact body/HMAC combination to the app's webhook endpoint while altering only the `x-shopify-shop-domain` header to a victim merchant's domain. `Registry.process` will accept the HMAC as valid and dispatch `WebhookMetadata` claiming the victim shop as the source. Depending on how the host application's `WebhookHandler#handle` implementation uses `data.shop` (e.g., to fetch/create a `Session`, gate GDPR redaction, credit/debit shop-level state, or trigger `app/uninstalled` cleanup), this enables cross-tenant data corruption or unauthorized actions attributed to a shop the attacker does not control — a cross-tenant boundary violation stemming directly from this gem's webhook verification code.

### Likelihood Explanation
Exploitation requires the attacker to already have a shop where the same multi-tenant app is installed (a low bar for any public/embedded app, since installation itself is unprivileged) so they can generate one legitimate signed webhook body, then replay it against the shared endpoint with a forged shop header. No access token, `client_secret`, or privileged account is needed — only a self-service app install and the ability to send an HTTP request with attacker-chosen headers, both squarely within "unprivileged internet user" capability.

### Recommendation
Bind the `shop` (and ideally `topic`, `api_version`, `webhook-id`) header values into the signed payload verified by `HmacValidator`, e.g., include them in `Webhooks::Request#to_signable_string` alongside the raw body, or otherwise cryptographically tie the shop domain to the signature so a replay with a substituted `shop` header fails validation.

### Proof of Concept
1. App `X` is installed on attacker's own shop `attacker.myshopify.com` and on victim shop `victim.myshopify.com`.
2. Attacker performs an action on `attacker.myshopify.com` that triggers a subscribed webhook (e.g. `orders/create`), capturing the genuine `raw_body` and `x-shopify-hmac-sha256` value Shopify sent to the app's webhook URL.
3. Attacker re-sends an HTTP POST to the same webhook endpoint with the identical `raw_body` and `hmac` header, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses headers/body successfully; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `raw_body` only and matches the replayed `hmac` — validation passes.
5. `handler.handle(data: WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: ..., ...))` is invoked, causing the host application to process attacker-supplied order data as though it originated from the victim shop.
