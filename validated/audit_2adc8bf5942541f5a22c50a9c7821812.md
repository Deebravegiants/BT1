Confirmed: `CallDispatcher.dispatch()` is `external` with no access control (no `onlyIntentGateway`/`onlyHost` modifier), and the same singleton `CallDispatcher` instance is shared across every order's predispatch/postdispatch execution (address stored once in `Params.dispatcher` and reused for all `placeOrder`/`fillOrder` calls). This is the same root-cause bug class as the DODO report — approvals granted to attacker-influenced swap targets during arbitrary-calldata execution are never cleared — but reachable from an unprivileged transaction and more severe because the dispatcher is a persistent, multi-tenant contract.

### Title
Shared, unauthenticated `CallDispatcher` combined with unrevoked ERC20 approvals in order calldata allows theft of any user's predispatch/postdispatch escrow assets - (File: evm/src/utils/CallDispatcher.sol, evm/src/apps/IntentGatewayV2.sol)

### Summary
`IntentGatewayV2.placeOrder`/`fillOrder` route arbitrary, user-supplied `Call[]` (encoded in `order.predispatch.call` / `order.output.call`) through a single shared `CallDispatcher` contract, identified by `_params.dispatcher` [1](#0-0) . `CallDispatcher.dispatch()` executes each call with `to.call{value: call.value}(call.data)` and has no caller restriction whatsoever [2](#0-1) . Because the dispatcher is one persistent contract reused for every order on the chain, any `approve(target, amount)` issued from within one user's calldata (e.g. approving a Uniswap router or an attacker-chosen swap target, mirroring the DODO `_swapApproveTarget.approve(..., type(uint256).max)` pattern) is never reset to `0`, and remains a live allowance on the dispatcher's balance of that ERC20 for as long as the approved spender wants it.

### Finding Description
Flows that use calldata explicitly instruct the dispatcher to approve a swap/DEX router before swapping, e.g. the documented pattern `approve(UNISWAP_V2_ROUTER, amount)` then `swapExactTokensForTokens` [3](#0-2) , and tests exercise exactly this "approve then swap on the dispatcher" sequence with `type(uint256).max` allowances (e.g. `IERC20.approve.selector, uniswapRouter, type(uint256).max`) [4](#0-3) . Neither `IntentGatewayV2` nor `CallDispatcher` ever revokes these approvals after the calls finish; only token *balances* left on the dispatcher are swept back via `_execute`/predispatch sweep logic [5](#0-4) . Approvals to the swap target are untouched.

Because `CallDispatcher` is a single shared, permanent contract for the whole gateway (not deployed per-order), and `dispatch()` is callable by anyone (no `onlyIntentGateway`/`onlyHost` guard) [6](#0-5) , an attacker can:
1. Wait for (or trigger via a benign order of their own) an approval of some token `T` to an arbitrary spender `S` to be set from the dispatcher during any order's predispatch/postdispatch calldata (approvals routinely use `type(uint256).max` per the test fixtures above).
2. Front-run/back-run the very next order that sends token `T` into the same dispatcher for predispatch execution — `IERC20(token).safeTransferFrom(msg.sender, dispatcher, amount)` in `placeOrder` [7](#0-6)  — before the gateway calls `ICallDispatcher(dispatcher).dispatch(order.predispatch.call)` and sweeps the resulting balance back with `transferCalls`.
3. Since `dispatch()` has no access control, the attacker calls it directly with `to = T, data = transferFrom(dispatcher, attacker, balance)`, draining the freshly escrowed tokens using the leftover allowance from step 1, before the legitimate sweep executes.

Even without step 3's direct-call vector, the stale max-approval alone is a standing risk: any compromised or malicious router/target address ever approved by calldata retains indefinite spending rights over whatever balance the shared dispatcher happens to be holding for a *different* user's order at any future point in time.

### Impact Explanation
This allows theft of escrowed/predispatch/postdispatch user funds routed through the `IntentGatewayV2` intents flow — a direct token-theft vulnerability that a single attacker transaction can exploit against any order using approve-then-swap calldata, satisfying "concrete theft ... of funds" for a High severity finding.

### Likelihood Explanation
Likelihood is high: approve-then-swap calldata with unbounded (`type(uint256).max`) allowances is the documented and tested pattern for predispatch/postdispatch execution [4](#0-3) , the dispatcher is a single well-known, publicly-indexed contract address [8](#0-7) , and `dispatch()` is unauthenticated, so any observer of pending mempool transactions or historical approvals can act.

### Recommendation
- Add an `onlyIntentGateway`/`onlyHost`-style access-control modifier to `CallDispatcher.dispatch()` so it cannot be invoked by arbitrary EOAs/contracts.
- After executing swap-style calls, explicitly revoke (`approve(target, 0)`) any approvals granted during the batch, or use time/session-scoped allowances instead of `type(uint256).max`.
- Alternatively, deploy a fresh, single-use `CallDispatcher` (e.g., via `CREATE2`/clones) per order so no approval or balance state can leak between unrelated orders.

### Proof of Concept
1. User A places an order with predispatch calldata: `approve(ROUTER, type(uint256).max)` then `swapExactTokensForTokens(...)` on token `USDC`, sent through the shared `dispatcher` (as in `testPostdispatchTokenSweep`) [9](#0-8) .
2. The `ROUTER` allowance from `dispatcher` for `USDC` is left at `type(uint256).max` after the swap and sweep (no revoke step exists in `IntentsBase._execute` / `IntentGatewayV2.placeOrder`).
3. User B places a new order whose predispatch step transfers `USDC` into the same `dispatcher` address (`IERC20(token).safeTransferFrom(msg.sender, dispatcher, amount)`) [10](#0-9) .
4. Before `IntentGatewayV2` calls `dispatch()` to sweep the balance back, an attacker calls `CallDispatcher.dispatch(abi.encode([Call({to: USDC, data: abi.encodeWithSelector(IERC20.transferFrom.selector, dispatcher, attacker, balance)})]))` directly (no access control blocks this) [2](#0-1) , using the still-live `ROUTER` allowance context or any other approved spender address the attacker controls, draining User B's escrowed USDC.

## Calldata

Orders support arbitrary calldata execution at two points in the lifecycle — before escrow (predispatch) and after fill (postdispatch). Both are executed through the `CallDispatcher` contract, which takes an ABI-encoded `Call[]` array:

```solidity
struct Call {
    address to;      // Target contract (must have code, reverts with NotContract otherwise)
    uint256 value;   // ETH to send with call
    bytes data;      // Calldata to execute
}
```

The `CallDispatcher` executes each call sequentially and reverts the entire batch if any call fails.

### Predispatch

The `predispatch` field in `Order` contains calldata to execute *before* escrowing inputs. The predispatch assets specified in `DispatchInfo.assets` are transferred to the `CallDispatcher`, the encoded calls are executed, and the resulting tokens are transferred back to the gateway for escrow. This enables swap-then-escrow patterns — for example, a user sends ETH which the `CallDispatcher` swaps to DAI on Uniswap, and the resulting DAI is escrowed as the order input.

### Postdispatch

The `call` field in `PaymentInfo` contains calldata to execute *after* the order is filled. This enables fill-then-act patterns — for example, output tokens received from the solver are routed through a DeFi protocol before reaching the beneficiary.

Execution timing differs by mode:

- **Same-chain**: Calldata executes only after the order is **fully filled**. Partial fills do not trigger calldata — only the final fill that completes the order executes it. This ensures all output tokens are available when the calls run.
- **Cross-chain**: Calldata executes **immediately** after the solver delivers output tokens to the beneficiary, before the settlement message is dispatched back to the source chain.

After execution, any tokens remaining in the `CallDispatcher` are swept back to the gateway and collected as dust (emitting `DustCollected` for each token). When postdispatch calldata is present, 100% of any surplus (solver overpayment) goes to the protocol rather than being split with the beneficiary — this prevents manipulation of surplus distribution through calldata side effects.
