### Title
Webhook `shop` identity used for tenant dispatch is not covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, then hands the `shop` value taken from an unauthenticated header straight to the app's handler as the tenant identifier. The equality that should hold is: `shop bound by HMAC == shop trusted by the handler`. In this gem, that equality never holds, because the HMAC covers only the body.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all read from headers that are never part of the signed payload: [2](#0-1) 

`Registry.process` validates the HMAC (over the body only) and then immediately constructs `WebhookMetadata` using `request.shop` (the unauthenticated header) and hands it to the handler: [3](#0-2) 

`HmacValidator.validate` calls `verifiable_query.to_signable_string`, which for a `Webhooks::Request` is the raw body only — the `shop` header is completely outside the signature's scope: [4](#0-3) 

Because the signature only binds the body, an attacker who is able to send arbitrary HTTP requests to the app's public webhook endpoint can take any previously observed valid `(raw_body, hmac)` pair (e.g., one delivered for their own shop/installation) and replay it with a different `x-shopify-shop-domain` / `shopify-shop-domain` header. `HmacValidator.validate` still returns `true` (it never inspects the header), so `Registry.process` dispatches the handler with `data.shop` set to the attacker-chosen tenant while `data.body` still contains the original shop's payload content.

### Impact Explanation
Any host application that uses `WebhookMetadata#shop` to select which merchant/tenant record to update (a common and encouraged pattern, since the library's own metadata object exposes `shop` for exactly that purpose) can be made to apply another shop's webhook body under an attacker-chosen shop identity. This breaks the tenant-scoping guarantee the library implicitly provides via `Registry.process`/`HmacValidator.validate` — the HMAC is presented as proof that "this webhook, including which shop it is for," is genuine, but it only proves the body is genuine for *some* shop, not the one named in the header. Depending on handler logic, this enables cross-tenant data confusion (writing/mutating tenant B's records using tenant A's webhook content), which maps to the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires the attacker to first obtain one legitimately-signed `(body, hmac)` pair — trivially available to anyone who has a shop where the app is installed (a normal, unprivileged Shopify merchant/developer), since Shopify delivers real webhooks to that shop's endpoint or the attacker can capture their own webhook traffic. No access to `api_secret_key`, access tokens, or another merchant's credentials is needed; only the ability to send an HTTP request with modified headers to the app's already-public webhook URL. This is a realistic, low-effort attack for any developer who has legitimate access to at least one shop using the app.

### Recommendation
Bind the identity fields to the signed payload rather than trusting bare headers:
- Have `Registry.process` cross-check `request.shop` against an expected/registered shop for the topic/subscription (e.g., session lookup) before invoking the handler, rather than passing the header value through unchecked.
- Alternatively/additionally, document prominently in `docs/usage/webhooks.md` that `data.shop` is NOT part of the HMAC-verified payload and MUST NOT be used as the sole tenant-scoping key without an independent, authenticated shop-to-session mapping.
- Consider incorporating `topic` and `shop` into the value that's compared/logged so integrators are forced to acknowledge they are unauthenticated inputs.

### Proof of Concept
1. Install the app on Shop A (attacker-controlled or attacker-observed) and capture one legitimate webhook delivery: raw body `B` and header `x-shopify-hmac-sha256: H` (valid signature computed by Shopify using the app's `client_secret`, unknown to the attacker but not needed since it's replayed as-is).
2. Send a new HTTP POST to the app's public webhook endpoint with:
   - Body: same `B`
   - Header `x-shopify-hmac-sha256`: same `H`
   - Header `x-shopify-shop-domain`: `shop-b.myshopify.com` (a different tenant than the one `B` actually belongs to)
   - Header `x-shopify-topic`: unchanged
3. `ShopifyAPI::Utils::HmacValidator.validate(request)` returns `true` because it only recomputes the HMAC over `B`: [1](#0-0) 
4. `Registry.process` proceeds and calls the handler with `WebhookMetadata.new(topic: ..., shop: "shop-b.myshopify.com", body: parsed(B), ...)`: [5](#0-4) 
5. If the host application's handler uses `data.shop` to look up/act on Shop B's tenant record while consuming Shop A's body content, cross-tenant data corruption occurs, with the app believing the request was validly authenticated end-to-end.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
