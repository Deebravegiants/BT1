### Title
Cross-Tenant Webhook Spoofing via Unauthenticated `shop-domain` Header - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by HMAC-verifying the raw request body, but the `shop` value it then hands to the host application's handler is read from the `x-shopify-shop-domain` header, which is never part of the signed material. This breaks the binding "shop attributed to the webhook == shop that produced the signed bytes," allowing a shop that legitimately received a signed webhook to relabel it as belonging to a different, victim shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, however, is derived independently from the `shopify-shop-domain`/`x-shopify-shop-domain` header and is not fed into the signable string at all: [2](#0-1) 

`HmacValidator.validate` only checks `hmac` against `to_signable_string` (i.e., the raw body), so it validates that the *body bytes* are authentic for the app's `client_secret`, but says nothing about which shop the header claims to be from: [3](#0-2) 

`Registry.process` runs this check and then forwards `request.shop` — the unauthenticated header value — straight into the `WebhookMetadata` passed to the app's handler: [4](#0-3) 

This is exactly the analog class called out in the rules: "a field acted on but not covered by the HMAC" — here, the `shop` identity used by the host application's business logic is a header value the HMAC never signs.

### Impact Explanation
Any merchant/shop that has installed the app is a legitimate, unprivileged sender of authentic webhooks (Shopify computes their HMAC using the app's single shared `client_secret`, identical across all shops of that app). Such an installer can capture one of their own genuine webhook deliveries — valid `raw_body` + valid `hmac` — and replay it to the app's webhook endpoint with the `x-shopify-shop-domain` header changed to a different, victim shop's domain. `HmacValidator.validate` still passes because it only checks the body bytes against the shared secret, and `Registry.process` will invoke the app's handler with `shop: <victim shop>` and the attacker-controlled/replayed body. Any host application that uses `WebhookMetadata#shop` to select the tenant's session, store, or data context (which is the intended and documented use of this field) will process forged/replayed data under the wrong tenant's identity — a cross-tenant data-integrity/confusion issue. This satisfies the "cross-tenant access" Critical impact bucket, since the identity boundary between shops (tenants) is defined entirely by this unauthenticated header.

### Likelihood Explanation
Likelihood is high for anyone who can install the app on a shop they control (a routine, unprivileged action for any Shopify store owner), since that grants them a stream of validly-signed webhook payloads they can replay against the endpoint with an arbitrary `shop-domain` header. No access token, `client_secret`, or privileged credential is required beyond normal app installation.

### Recommendation
Include the shop domain (and ideally the API version/webhook id) as part of the signed/verified material, or otherwise cryptographically bind the claimed shop to the specific webhook subscription/secret. At minimum, the gem should not expose `request.shop` for consumption by host-application authorization/tenant-selection logic without documenting that it is unauthenticated, and should provide (or require) a mechanism to correlate the `shop-domain` header against the shop that was expected to receive that specific webhook subscription (e.g., verifying against a known per-shop webhook secret/id or maintaining a mapping validated independently of the header).

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com`; Shopify sends a real webhook, e.g. `orders/create`, with body `B`, header `x-shopify-shop-domain: attacker-shop.myshopify.com`, and `x-shopify-hmac-sha256: HMAC(client_secret, B)`.
2. Attacker captures this request.
3. Attacker resends the exact same body `B` and HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(client_secret, B)` — matches, since `B` and the signature are unmodified [5](#0-4) .
5. `handler.handle` is invoked with `shop: "victim-shop.myshopify.com"` and the attacker's order body [6](#0-5) , causing the host app to process attacker-controlled data under the victim shop's tenant context.

          received_signature = verifiable_query.hmac

          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
