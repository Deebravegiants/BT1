### Title
Webhook `shop` (and `topic`/`api_version`/`webhook_id`) identity fields are trusted without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` is documented to "verify the request did indeed come from Shopify," but the HMAC verification only authenticates the raw request body. The `shop` domain (and `topic`, `webhook_id`, `api_version`) used to identify *which tenant* the webhook belongs to are read straight from HTTP headers and are never included in the signed content, so they can be forged independently of a valid HMAC.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop`, `topic`, `api_version`, and `webhook_id` are pulled from headers that are not part of what's signed: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature exclusively over `to_signable_string` (i.e. the body) and compares it to the `hmac` header: [3](#0-2) 

`Registry.process` uses this body-only HMAC check as its sole authenticity check, then unconditionally trusts `request.shop` (and the other header-derived fields) as the tenant identity passed to the handler: [4](#0-3) 

The identity binding that should hold is: `shop that produced a valid HMAC == shop attributed to the webhook by the gem`. Because the HMAC is computed only over the body, an attacker who owns/controls their own shop (an unprivileged internet user can create a free/trial store and subscribe the target app's webhooks to it) receives a genuine Shopify-signed webhook (valid HMAC, computed with the app's real `api_secret_key`, but the attacker never needs to know the secret — Shopify computed it for them). The attacker can then replay that exact body+HMAC to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) header value with a different, victim shop's domain. `Utils::HmacValidator.validate` still passes because the body is unchanged, and `Registry.process` calls the handler with `WebhookMetadata` carrying the attacker-chosen `shop`, `topic`, `webhook_id`: [5](#0-4) 

This is precisely analogous to the reported bug class: an index (`identifier`) that isn't checked against what was actually acted upon (`slashingWhitelist[index]`) — here the header-supplied `shop` is not checked against what was actually authenticated (the body's HMAC), letting the attacker rebind a validly-signed payload to an arbitrary tenant identity.

### Impact Explanation
Any host application relying on `WebhookMetadata#shop`/`#topic`/`#webhook_id` (as documented and demonstrated in `docs/usage/webhooks.md`) as an authenticated tenant identifier is exposed to cross-tenant confusion: an attacker-controlled shop's webhook payload can be attributed to a victim shop. Depending on how the host app persists/acts on this (e.g., updating per-shop caches, deduping by `webhook_id`+`shop`, triggering shop-scoped side effects), this crosses a tenant boundary using only a webhook subscription the attacker legitimately owns — classified as Critical (cross-tenant access) per the rules.

### Likelihood Explanation
Reachable by any unprivileged internet user who can install/operate a Shopify development or trial store that installs the target app (a normal, unprivileged action), receive a genuine webhook (valid HMAC over the body), and replay it with modified headers to the app's public webhook callback URL. No access to `api_secret_key`, tokens, or the app owner's credentials is required.

### Recommendation
Bind the tenant-identifying headers into the signed content, or otherwise cryptographically tie `shop`/`topic`/`webhook_id` to the verified body — e.g., include the shop domain and webhook id in `to_signable_string`, or require the host app to cross-check `request.shop` against a shop that has an active, previously-established session/registration before trusting `WebhookMetadata#shop`. At minimum, update `ShopifyAPI::Webhooks::Registry.process` to fail if the shop cannot be corroborated by data outside the unauthenticated headers, since headers alone are not covered by the HMAC.

### Proof of Concept
1. Attacker creates their own shop `attacker.myshopify.com`, installs the target app, and it registers `orders/create` webhooks pointing at the app's webhook endpoint.
2. Attacker triggers an order create event in their own shop; Shopify sends a genuine webhook: body `B`, header `x-shopify-hmac-sha256: HMAC(secret, B)`, `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker intercepts/records this request (they are the recipient's proxy, e.g., using a webhook debugging proxy they control) and resends it to the app's public endpoint, changing only `x-shopify-shop-domain` to `victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: modified_headers)` is constructed by the host per `docs/usage/webhooks.md`; `Registry.process` calls `Utils::HmacValidator.validate`, which recomputes `HMAC(secret, B)` — matches, since `B` is untouched (`lib/shopify_api/utils/hmac_validator.rb:26-31`, `lib/shopify_api/webhooks/request.rb:35-38`).
5. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and the attacker's order body, despite the payload never having originated from or been signed in connection with `victim.myshopify.com` (`lib/shopify_api/webhooks/registry.rb:196-199`).
