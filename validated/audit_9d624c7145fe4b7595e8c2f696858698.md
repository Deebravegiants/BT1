## Title
Webhook `shop-domain` header is trusted for tenant identification without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`), `topic`, `api_version`, and `webhook_id` from raw, unauthenticated HTTP headers, while the HMAC signature verified by `Utils::HmacValidator.validate` only covers the raw request body via `to_signable_string` returning `@raw_body`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `Request#shop` reads the `shop-domain` header directly, uncoupled from that signed payload [2](#0-1) . `Webhooks::Registry.process` validates the HMAC over the request and, on success, passes `request.shop` straight into the `WebhookMetadata` handed to the host application's handler as the tenant identifier [3](#0-2) . The equality the gem implicitly assumes is:

`hmac_verified_bytes (raw_body) == tenant_identity_bytes (shop-domain header)`

but this equality never holds — the header is never mixed into the signable string, so nothing cryptographically ties the `shop-domain` header to the HMAC-verified body. An unprivileged sender who possesses one single valid `(raw_body, hmac)` pair for topic `T` from `shop-A.myshopify.com` (obtainable, for example, by having their own store trigger a webhook against a shared/multi-tenant endpoint, or replaying a previously delivered webhook whose body is topic/shape-generic) can resend the exact same body/HMAC pair but substitute the `shop-domain` header with `shop-B.myshopify.com`. `HmacValidator.validate` still succeeds because it only recomputes the HMAC over `@raw_body` [4](#0-3) , and `Registry.process` will invoke the host's handler believing the event originated from `shop-B`.

### Impact Explanation
This breaks the tenant boundary that host applications rely on to route webhook data to the correct merchant record (session lookup, data storage, `shop/redact` and `customers/redact` mandatory compliance flows, etc.). Depending on how the host app keys data by `WebhookMetadata#shop`, this can lead to cross-tenant data confusion, e.g., attributing a GDPR redact request, an uninstall event, or order/customer data to the wrong shop. This aligns with the "cross-tenant access" Critical impact category, since the identity binding an app is expected to be able to rely on (verified body ⇒ verified shop) is not actually enforced by the gem.

### Likelihood Explanation
Likelihood is Low/Medium in practice: the attacker needs a valid `(body, hmac)` pair signed with the app's `api_secret_key`-derived HMAC for *some* shop (e.g., from their own installed instance of the app, or a captured/replayed delivery), and the receiving endpoint must accept attacker-controlled headers (true for any host app that exposes the webhook endpoint to raw HTTP framework input, which is the documented integration pattern for this gem — headers are taken as-is from `initialize(raw_body:, headers:)`). No access token, `client_secret`, or privileged account is required, satisfying the "unprivileged internet user" bar.

### Recommendation
Bind the tenant-identifying headers to the signed payload before trusting them: either
1. Include `shop-domain` (and ideally `topic`, `webhook_id`) inside the string that is HMAC-verified (this would require Shopify's own signing scheme change, so practically not implementable client-side), or
2. Require the host application to independently authenticate/authorize the resolved `shop` against a known, previously-established session/tenant record before acting on `WebhookMetadata#shop`, and document this requirement explicitly in `Registry.process`, since the HMAC in this gem's implementation only proves body integrity, not header authenticity.
3. At minimum, update the gem's documentation/comments on `Request#shop` and `Registry.process` to make explicit that the returned `shop` value is **not** covered by the HMAC check, so host apps do not mistakenly treat it as verified.

### Proof of Concept
1. App exposes `POST /webhooks` which reads `raw_body` and headers and constructs `ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)`, then calls `ShopifyAPI::Webhooks::Registry.process(request)`.
2. Attacker (an unprivileged merchant who has their own install of the app, or who captured one legitimate webhook delivery) obtains a valid `(raw_body, x-shopify-hmac-sha256)` pair for topic `orders/create` from `shop-attacker.myshopify.com`.
3. Attacker resends this exact body and HMAC header, but sets `x-shopify-shop-domain: shop-victim.myshopify.com`.
4. `HmacValidator.validate` recomputes the HMAC over `@raw_body` only [5](#0-4)  — it matches, so validation passes.
5. `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` using the attacker-supplied `shop-victim.myshopify.com` value [6](#0-5) , and the host application's handler processes/attributes the event to `shop-victim` instead of the shop that actually generated the signed payload.
