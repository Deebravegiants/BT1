### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` and excludes the `X-Shopify-Shop-Domain` header, so `Utils::HmacValidator.validate` never binds the claimed `shop` to the HMAC. Any actor who can obtain one valid `(raw_body, hmac)` pair signed with the app's `client_secret` (e.g. a genuine merchant who installs the app on their own store and receives real webhooks) can replay that exact body/HMAC to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header, causing the gem to accept it as an authentic webhook "from" a completely different shop.

### Finding Description
`Request#hmac` is computed from the `hmac-sha256` header and validated against `to_signable_string`, which is defined as just the raw body: [4](#0-3) 

`shop` is read from a separate, unsigned header: [5](#0-4) 

`Registry.process` verifies only the body-level HMAC, then forwards `request.shop` (attacker-controlled) unchecked into `WebhookMetadata`, which host applications are documented to treat as the authoritative tenant/shop for the event: [2](#0-1) 

Because the HMAC secret (`Context.api_secret_key`, i.e. the app's `client_secret`) is the same for every shop that installs a given app, any merchant who legitimately installs the app can capture a valid `(raw_body, hmac)` pair from a real webhook delivered to their own store (many topics — e.g. `app/uninstalled` — have a static/predictable body such as `{}`, giving a globally reusable valid signature). They can then send that exact body and HMAC to the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop, and `HmacValidator.validate` will report success because it only checks the body against the signature, never that the signature was produced for *that* shop.

This breaks the intended binding: **shop asserted in the unauthenticated header == shop the HMAC actually authenticates**. The HMAC only proves "this body was signed with the app secret", not "this body pertains to shop X".

### Impact Explanation
This is a cross-tenant integrity bypass: a low-privilege actor (any merchant who can install the public app) can forge webhook events attributed to an arbitrary victim shop. Depending on the host application's webhook handlers (which the gem's own documentation instructs to key business logic off `data.shop`), this can trigger tenant-scoped side effects for a shop the attacker does not control — e.g. spoofing `app/uninstalled` to make the host app tear down/revoke a victim's session and integration state, or spoofing GDPR/data topics — using only data forged/replayed by an unrelated, unprivileged merchant account. This matches the "cross-tenant access" high/critical impact class: the gem's webhook authentication does not actually authenticate the shop, only the body.

### Likelihood Explanation
Likelihood is high for any app that is installable by multiple untrusted third-party merchants (the standard Shopify public-app model): obtaining a legitimate `client_secret`-signed `(body, hmac)` pair only requires installing the app once on an attacker-owned store, and several standard webhook topics have static, shop-independent bodies, making the valid signature trivially reusable across shop headers.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) as part of the signed material used to identify the event, or otherwise cryptographically bind the `shop-domain` header to the specific shop's known session/access token before trusting it — e.g. cross-check `request.shop` against a shop that the host app knows has an active installation for the given `webhook_id`/API version pair, or have `HmacValidator`/`Request` require the shop to be corroborated independently rather than treated as authenticated by `Registry.process`.

### Proof of Concept
1. Attacker installs the target public app on `attacker-shop.myshopify.com`, receiving a genuine `app/uninstalled` webhook: `raw_body = "{}"`, `X-Shopify-Hmac-Sha256: <valid-hmac-for-"{}" >`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker resends an HTTP POST to the app's registered webhook path with the same `raw_body` and `X-Shopify-Hmac-Sha256` value, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes HMAC over `raw_body` [6](#0-5)  — validation succeeds despite the shop header being forged.
4. The handler executes with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: "app/uninstalled", ...)`, causing the host application to act on the victim shop's tenant data believing it came from Shopify.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
