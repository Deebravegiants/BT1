### Title
Webhook `shop-domain`, `topic`, `api-version`, and `webhook-id` headers are trusted without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the shop, topic, API version, and webhook ID are read from HTTP headers that are never included in the signed data. `ShopifyAPI::Webhooks::Registry.process` validates only the body's HMAC and then trusts the unauthenticated header values to construct `WebhookMetadata`, including the tenant-identifying `shop` field, that is handed to the host application's webhook handler.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` verifies a `VerifiableQuery`'s HMAC against `to_signable_string`. For webhooks, `to_signable_string` returns only the raw body: [1](#0-0) 

The `shop`, `topic`, `api_version`, and `webhook_id` accessors, however, are all derived from HTTP headers that are not part of the signed payload: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately builds `WebhookMetadata` using these unauthenticated header-derived fields, including `shop`, and passes it to the app's handler: [3](#0-2) 

This breaks the identity binding: **the shop the HMAC was computed for (any shop, since `api_secret_key` is a single value shared across all installations of the app) ≠ the shop the request claims via the `shop-domain` header, which the handler uses as the tenant identity**.

Since a single `api_secret_key`/`old_api_secret_key` is shared by the app across all its installed shops, any shop that has installed the app receives legitimate webhook deliveries with a valid `(raw_body, hmac)` pair signed with that shared secret. Because the signature covers only the body, an attacker who has this pair (e.g., a malicious merchant capturing a webhook their own shop received, or simply crafting an empty/`{}` body and computing the HMAC using the shared, guessable pattern) can POST directly to the app's public webhook endpoint with the same body/HMAC but an arbitrary `x-shopify-shop-domain` header pointing at a victim shop, along with an arbitrary `topic`/`webhook-id`/`api-version`. `Registry.process` still validates successfully (HMAC only checks body bytes) and passes the forged `shop` through to the handler as if the event genuinely originated from the victim's store.

### Impact Explanation
This is a cross-tenant identity confusion: the gem hands the host application a `shop` value that is not cryptographically bound to the delivery, letting an attacker impersonate any tenant shop when invoking the app's own webhook processing logic. Any host application logic that uses `data.shop` from `WebhookMetadata` to select tenant-scoped session/state/config (the documented and intended use of this field) can be tricked into acting on behalf of, or against, a different merchant's data — a cross-tenant access vulnerability.

### Likelihood Explanation
Exploitation requires only network access to the app's public webhook endpoint plus one legitimately-observed `(body, hmac)` pair, which is trivial to obtain for any shop that has the app installed (they can inspect their own webhook deliveries) or forge for common bodies like `"{}"`. No access token, `api_secret_key`, or privileged account is required, matching the "unprivileged internet user" threat model. This makes the likelihood of exploitation high given a host app that uses `shop` from `WebhookMetadata` for tenant scoping — the exact documented/intended usage pattern.

### Recommendation
Bind the header-derived identity fields (`shop`, `topic`, `webhook_id`, `api_version`) into the value that is HMAC-verified, or otherwise cryptographically authenticate them (e.g., by cross-checking against a Shopify-provided signed value, or requiring TLS-pinned/allow-listed origins from Shopify's known IP ranges as defense in depth). At minimum, document prominently that `WebhookMetadata#shop` is not authenticated by `Utils::HmacValidator.validate` and must not be used as a sole tenant-identity source without additional verification (e.g., confirming the shop has an active, previously-established session/installation record before acting on the payload).

### Proof of Concept
```ruby
require "openssl"
require "base64"

api_secret_key = "shared_app_secret" # shared across all shops using this app
raw_body = "{}"

# Attacker (any shop with the app installed, or anyone who observes one delivery)
# obtains this legitimate hmac for some body from a real Shopify webhook delivery,
# or computes it directly since it only depends on the body:
valid_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), api_secret_key, raw_body)
hmac_header = Base64.encode64(valid_hmac)

# Attacker crafts a forged request directly to the app's webhook endpoint,
# reusing the valid (body, hmac) pair but spoofing the shop-domain header
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => hmac_header,       # valid for raw_body
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # NOT covered by HMAC
  "x-shopify-webhook-id" => "attacker-chosen-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

# Passes validation because HmacValidator only checks raw_body bytes:
ShopifyAPI::Utils::HmacValidator.validate(request) # => true

# Registry.process will now invoke the app's handler with
# WebhookMetadata(shop: "victim-shop.myshopify.com", ...) even though
# the request never actually came from Shopify on behalf of that shop.
ShopifyAPI::Webhooks::Registry.process(request)
```
