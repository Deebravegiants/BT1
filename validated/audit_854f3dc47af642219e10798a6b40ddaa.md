### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) header values are trusted without being covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw body only, while the shop attribution (`shop`), `topic`, `webhook_id`, and `api_version` are read directly from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC against the body, then hands the *unsigned* `shop` value to the app's handler as trusted tenant identity. Any actor who can obtain one genuine, correctly-signed webhook delivery for their own shop (e.g., a malicious merchant who installs the app) can replay that exact `(body, hmac)` pair while substituting the `x-shopify-shop-domain` header for a victim shop, producing a request that passes HMAC validation but is attributed to the victim tenant.

### Finding Description
The equality the code is supposed to guarantee is:
`HMAC_valid(request) == true` implies `(shop, topic, body)` all originated from Shopify for that shop.

In reality:
```ruby
# lib/shopify_api/webhooks/request.rb
def to_signable_string
  @raw_body
end
``` [1](#0-0) 

only `@raw_body` is included in the signable string, so the HMAC binds solely to the body bytes.

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from headers with no binding to the HMAC at all:
```ruby
def topic
  T.cast(shopify_header("topic"), String)
end

def shop
  T.cast(shopify_header("shop-domain"), String)
end
``` [2](#0-1) 

`Registry.process` checks the HMAC and then immediately forwards the unauthenticated `shop`/`topic` values to the handler as ground truth:
```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
``` [3](#0-2) 

The `HmacValidator` itself only checks `verifiable_query.to_signable_string` against the secret, so it is oblivious to which headers accompanied that body:
```ruby
def validate_signature(verifiable_query, secret)
  received_signature = verifiable_query.hmac
  computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
  OpenSSL.secure_compare(computed_signature, T.must(received_signature))
end
``` [4](#0-3) 

Because the `x-shopify-hmac-sha256` header is computed by Shopify over the body only (as this gem itself implements), and the `api_secret_key` is shared across every shop that has installed the app, a malicious merchant tenant (call it Shop B) who installs the same app receives genuine webhooks for their own shop, each with a valid `(raw_body, hmac)` pair signed with the app's secret. Nothing in this gem stops that same `(raw_body, hmac)` pair from being POSTed again to the app's webhook endpoint with the `x-shopify-shop-domain` (and optionally `x-shopify-topic`) header rewritten to name a different, victim shop (Shop A). `HmacValidator.validate` still returns `true`, because it never inspects the header. `Registry.process` then invokes the handler with `shop: "shop-a.myshopify.com"` even though the payload actually originated from Shop B.

The library's own documentation confirms host applications are expected to trust this field as the tenant identity: `shop`, `String` - The shop domain of the webhook, and the example handler forwards `data.shop` directly into shop-scoped background work. [5](#0-4) 

This is the same class of bug as the reported `diamondCut()` issue: a value that is *acted upon* (here, the tenant/shop attribution and topic routing) is not covered by the same cryptographic commitment (HMAC) that is used to authorize the action, letting a legitimate-but-unprivileged actor (any merchant who installs the app) produce artifacts that are accepted as if they came from a different, arbitrary tenant.

### Impact Explanation
This breaks the tenant boundary the gem is responsible for enforcing before invoking the app's webhook handler: `shop` is the only signal apps have to know "which merchant does this event belong to," and it is unauthenticated. A malicious merchant can trigger handler logic (queued jobs, DB writes, notifications, syncs) that attributes attacker-supplied body content to an arbitrary victim shop of the attacker's choosing, causing cross-tenant data corruption/confusion, wrong access-token usage keyed by the forged `shop`, or duplicate/poisoned webhook_id bookkeeping for a shop the attacker doesn't control. This matches the "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high for any app that installs on multiple third-party shops (the standard SaaS deployment model): becoming "Shop B" only requires installing the app once as an ordinary, unprivileged merchant, no leaked credentials, no `api_secret_key`, and no privileged account are needed. The attacker only needs to capture one legitimate webhook delivery to their own shop and replay it with a modified header.

### Recommendation
Bind the tenant-identifying and routing fields into the HMAC-verified payload, or independently verify that the `shop` (and `topic`) header matches a shop this app actually issued/expects for that specific `webhook_id`/session, e.g. by cross-checking against stored webhook registration metadata (shop + webhook_id pairs recorded at registration time) before dispatching to the handler, rather than trusting `x-shopify-shop-domain` on its own. At minimum, document prominently that `data.shop`/`data.topic` are not authenticated by the HMAC and must be revalidated by the host app (e.g., against an allow-list of shops that have an active session/installation), and consider extending `to_signable_string` conceptually to make clear which fields carry no integrity guarantee.

### Proof of Concept
1. App is installed by attacker on `attacker-shop.myshopify.com` and by victim on `victim-shop.myshopify.com`, both under the same app (`api_secret_key`).
2. Trigger any subscribed event on `attacker-shop` (e.g., `orders/create`). Shopify delivers a webhook to the app's endpoint with body `B` and header `x-shopify-hmac-sha256: HMAC(secret, B)`.
3. Attacker captures `(B, HMAC(secret, B))` (e.g., by controlling their own receiving proxy/logging, which is normal merchant capability).
4. Attacker replays this exact POST to the app's webhook endpoint, keeping body `B` and the HMAC header unchanged, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `Utils::HmacValidator.validate(request)` returns `true` because it only checks `HMAC(secret, B)` [6](#0-5) ; `Registry.process` proceeds and calls the handler with `shop: "victim-shop.myshopify.com"` and attacker-controlled body `B` [3](#0-2) .
6. The host app's handler performs shop-scoped work (e.g., queues a job, writes to a per-shop record) believing the event and its content came from the victim shop.
