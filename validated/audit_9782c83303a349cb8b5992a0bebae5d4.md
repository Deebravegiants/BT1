This confirms the asymmetry: for OAuth callback (`AuthQuery`), the `shop` field is included in `to_signable_string` and therefore covered by the HMAC signature. But for incoming webhooks (`Webhooks::Request`), `to_signable_string` returns only `@raw_body`, meaning the `shop-domain`, `topic`, `api-version`, and `webhook-id` headers are **not** covered by the HMAC signature at all.

### Title
Webhook shop-domain header not covered by HMAC signature allows cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `ShopifyAPI::Utils::HmacValidator.validate` verifies only that string against the HMAC. The `x-shopify-shop-domain` (or `shopify-shop-domain`) header used to identify the tenant is never part of the signed material, so it can be freely forged while still passing HMAC validation, as long as the attacker can supply a body+HMAC pair that was genuinely signed by the app's shared `client_secret`.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` validates a webhook purely by checking `Utils::HmacValidator.validate(request)`: [1](#0-0) 

`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` and compares it to the received `hmac`: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` is defined as just the raw body — none of the Shopify-supplied headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) are included: [3](#0-2) 

Compare this to `Auth::Oauth::AuthQuery#to_signable_string`, where `shop` **is** explicitly part of the signed payload: [4](#0-3) 

After a successful HMAC check, `Registry.process` extracts `request.shop` directly from the unauthenticated header and hands it to the app's handler as the tenant identity, with no further verification: [1](#0-0) 

This breaks the equality that should hold: `shop claimed to the handler == shop cryptographically bound by the HMAC`. In this gem, the HMAC secret (`Context.api_secret_key`, the app's `client_secret`) is shared across every shop that installs the app — it is not shop-specific. So any tenant that has legitimately installed the app can capture one of their own genuine `(raw_body, hmac)` pairs (e.g. from a webhook Shopify sent them, or by using the app's own delivery endpoint), then replay that exact body/HMAC to the app's webhook endpoint while substituting a victim shop's domain in the `x-shopify-shop-domain` header. `Utils::HmacValidator.validate` still returns `true` (the body/HMAC pair is valid), but `Registry.process` passes the forged `shop` value into `WebhookMetadata`, which host applications use as the tenant key to store/act on the payload.

### Impact Explanation
This is a cross-tenant identity-binding bypass: a value used to select which merchant's data is created/updated/deleted is not covered by the cryptographic signature that authenticates the request. An attacker who is merely one (unprivileged relative to other tenants) installed merchant of the app can inject attacker-controlled webhook payloads that are misattributed to a different merchant's shop, achieving cross-tenant access/data corruption without ever touching the victim's credentials.

### Likelihood Explanation
Exploitation only requires the attacker to be any merchant that has the app installed (a normal, unprivileged usage flow) and to control the destination `shop-domain` header of an HTTP POST to the app's public webhook endpoint — no access to `client_secret`, tokens, or the victim's shop is needed. The only constraint is that the replayed `raw_body` must exactly match one the attacker legitimately obtained (so the payload content is limited to what the attacker's own shop produced), but the topic/shop attribution is fully forgeable, which is sufficient to corrupt cross-tenant bookkeeping (e.g., mandatory `shop/redact`, `customers/redact` compliance webhooks, order/product sync data, etc.) that keys off `request.shop`.

### Recommendation
Include the identifying headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signed material for `Webhooks::Request#to_signable_string`, or otherwise cryptographically bind the shop domain to the signed body before `Registry.process` treats it as trusted tenant identity. At minimum, document that `HmacValidator.validate` only authenticates body integrity/origin, not header-derived shop/topic values, and require host apps to cross-check `request.shop` against an independently known/authorized shop before acting on the payload.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker-shop.myshopify.com` and triggers/receives a legitimate webhook (e.g. `orders/create`), capturing the exact `raw_body` and the `x-shopify-hmac-sha256` value Shopify computed with the app's shared `client_secret`.
2. Attacker sends a POST directly to the app's webhook endpoint with the same `raw_body` and `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `raw_body` against the HMAC: [5](#0-4) 
4. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` even though the payload actually originated from the attacker's own shop: [6](#0-5) 
5. Any host-app logic that trusts `data.shop` to select which tenant's database row to write/update/delete now operates on the victim's tenant using attacker-supplied data.
