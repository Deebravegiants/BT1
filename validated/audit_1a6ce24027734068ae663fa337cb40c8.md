Audit Report

## Title
Native value sent alongside calls to `pallet-revive` precompiles (ERC20/Vesting/AssetConversion) becomes permanently stuck - (File: `substrate/frame/revive/src/exec.rs`)

## Summary
`pallet-revive`'s frame-push logic unconditionally transfers any attached native `value` to the callee account before invoking either contract code or a precompile's `call`/`call_with_info` handler [1](#0-0) . None of the three cited built-in precompiles (ERC20, Vesting, AssetConversion) read or validate `value_transferred`/`env.value()`, so a caller who attaches non-zero native value to a precompile call has that value moved into the precompile's account with no code path in the precompile logic to spend, forward, or refund it [2](#0-1) [3](#0-2) [4](#0-3) .

## Finding Description
The transfer of `frame.value_transferred` happens in `Self::transfer_from_origin(...)` prior to dispatching into either `executable.execute(...)` or `instance.call(...)`, and this code path applies identically to precompiles and real contracts [5](#0-4) . The `has_contract_info()` flag only controls whether an account is auto-minted/kept alive for "extended API" precompiles — it has no bearing on whether value transferred to the precompile is validated or rejected [6](#0-5) . Inspection of `ERC20::transfer`, `Vesting::vestedTransfer`, and `AssetConversion::swapExactTokensForTokens` confirms none of them call anything like `env.value_transferred()` or `ensure!(value.is_zero())` before proceeding with their asset-denominated logic — they operate purely on the ERC20/asset-pallet balances, entirely independent of any native currency that may have accompanied the call [2](#0-1) .

I was unable to fully confirm within this review whether `HAS_CONTRACT_INFO` is `true` or `false` for these three specific precompiles (this determines whether the destination account already exists/has an account with an owner path), since a direct grep for that constant in the three precompile files returned no matches — meaning either the trait method is implemented under a different name/pattern (e.g. via a trait default) or is defined elsewhere. This detail does not change the core root-cause finding: at the EVM/PVM `call` entry points, non-zero value is always transferred to the destination account before the precompile logic runs, and the precompile logic itself never inspects or rejects that value [7](#0-6) .

## Impact Explanation
Value sent alongside a precompile call is moved to that precompile's derived account. Whether this constitutes truly *permanent, unrecoverable* loss depends on whether that account has any owner-controlled or governance-controlled withdrawal path elsewhere in the pallet/runtime (e.g., a root-only sweep, or if the account coincides with an existing pallet sovereign account that already has spending logic elsewhere in the runtime) — this claim asserts there is no such path but does not demonstrate that no such path exists anywhere in the runtime (e.g., asset pallet sovereign account handling, governance-controlled treasury sweeps, etc.). Absent a demonstrated total absence of any recovery mechanism, the claim of "permanent, protocol-level loss of funds" is asserted but not proven with certainty in the cited code.

## Likelihood Explanation
The described trigger (attaching non-zero `value` to a precompile call) is realistic given how EVM tooling exposes a `value` field on any call, and the report is directionally correct about the code path shown: value transfer happens unconditionally in `exec.rs`, and the audited precompile handlers do not check or reject it. This matches a genuine gap in defensive coding for the precompile interfaces.

## Recommendation
Add an explicit `ensure!(env.value_transferred().is_zero(), ...)` (or equivalent revert) guard in each non-payable precompile entry point (`ERC20::transfer/approve/transferFrom/permit`, `Vesting::vestedTransfer`, `AssetConversion::swapExactTokensForTokens`, etc.), or centralize the check in the precompile dispatch path in `substrate/frame/revive/src/exec.rs`/`precompiles.rs` so that non-payable precompiles universally reject non-zero value before their business logic executes.

## Proof of Concept
Not independently reproduced with a running test in this review. To confirm the claim conclusively, a fork/integration test should: (1) deploy the runtime with the `ERC20` precompile wired in as in `cumulus/parachains/runtimes/assets/asset-hub-westend/src/lib.rs`, (2) issue an EVM `CALL` to the precompile's `transfer(to, amount)` selector with non-zero `value`, (3) assert the call succeeds (does not revert), and (4) assert the attached value remains at the precompile's account balance with no subsequent extrinsic or precompile call able to move it out. This last step — proving there is truly *no* recovery path anywhere in the runtime — is the part not verified in this review and would need to be checked before treating the impact as confirmed permanent fund loss rather than a missing-input-validation defect.
