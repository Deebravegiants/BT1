### Title
Stale cached `Account.owner` lets a previous position-NFT owner retain borrow/withdraw authority after transfer — (File: contracts/controller/src/account.rs)

### Summary
The controller records `owner` inside the `Account` struct at account creation and later authorizes value-moving entrypoints by comparing `caller` against that cached address (`require_owner_or_delegate`). Account ownership, however, is represented by the transferable position NFT (`position-nft` contract), and nothing in the controller resyncs `account.owner` on NFT transfer. Entrypoints that move funds (`borrow`, `withdraw`, `multiply`, `flash_position`, `swap_debt`, `swap_collateral`, `repay_debt_with_collateral`, `migrate_from_blend`) therefore authorize the *original* owner and its stored delegates even after the account has been sold or transferred — the same bug class as the authentik advisory, where a token flow skipped the real authorization check.

### Finding Description
`create_account` pins `owner` into `Account` at mint time via `nft_mint_call` and never updates it again [1](#0-0) . All guarded flows then check the caller against this cached field: `require_owner_or_delegate` accepts `caller == owner` (the stored field) or a delegate stored under `get_delegates(env, account_id, owner)` [2](#0-1) , and `load_or_create_account` applies that guard to `Migrate` and `Multiply` [3](#0-2) . The auth list itself documents that `borrow`, `withdraw`, `swap_debt`, `swap_collateral`, `repay_debt_with_collateral` and `migrate_from_blend` all funnel through `require_owner_or_delegate` [4](#0-3) .

Meanwhile the code itself treats NFT ownership as the live source of truth elsewhere: `require_account_owner` (used by `renew_account`, `add_delegate`, `remove_delegate`) compares `caller` to `storage::account_owner(env, account_id)`, not to `account.owner` [5](#0-4) . So the codebase has two divergent notions of ownership, and the fund-moving path uses the stale one — exactly the "access restrictions not checked on this flow" pattern of CVE-2024-38371.

### Impact Explanation
After a position NFT changes hands (sale, transfer, or theft), the *previous* owner — and any still-listed delegates keyed under that owner — can keep calling `borrow` and `withdraw` on the account, draining collateral and drawing debt to an arbitrary `to` address [6](#0-5) . Conversely, the legitimate new NFT holder is rejected by `require_owner_or_delegate` (they are neither the cached `owner` nor a delegate listed under them) and cannot even `add_delegate`/`remove_delegate` to evict the old delegates, since delegate entries are keyed by the stale owner. Theft of user funds: the seller of a leveraged account retains full spending authority over it.

### Likelihood Explanation
Reachable by a single unprivileged address: victim transfers the position NFT (a supported operation on the NFT contract), then the attacker (prior owner or a delegate the victim cannot remove) submits `borrow`/`withdraw` with `account_id` and a `to` address they control. `caller.require_auth()` passes because the caller really is the cached owner; the owner check cannot see the NFT transfer.

Caveat: this conclusion depends on (a) `position-nft` `transfer`/`approve` actually moving `owner_of` without a controller callback to rewrite `Account.owner`, and (b) `storage::account_owner` resolving the live NFT owner rather than the same cached field. I verified no `account.owner` reassignment exists anywhere under `contracts/` (the only writes are at creation), which strongly supports (a); I could not fully confirm (b) within the available iterations, though `require_account_owner` calling a separate `storage::account_owner` instead of reading `account.owner` indicates the NFT is the live source.

### Recommendation
Make the fund-moving guard consult live NFT ownership instead of the cached field: in `require_owner_or_delegate`/`is_owner_or_delegate` (contracts/controller/src/account.rs:115-140), resolve the current owner via `storage::account_owner(env, account_id)` and compare the caller to that, keying delegate lookups under the current owner too (or clearing delegate lists on transfer). `Account.owner` should be treated as historical metadata or removed from the authorization path entirely.

### Proof of Concept
1. Alice calls `supply(caller=alice, account_id=0, spoke_id=S, assets=[(USDC, 1000e7)])` → account `A` minted, `account.owner = alice`.
2. Alice calls `position-nft::transfer(alice, bob, A)` (or approves and Bob transfers). `Account.owner` still equals `alice`.
3. Alice (or a delegate she previously added) calls `borrow(caller=alice, account_id=A, borrows=[(XLM, max)], to=Some(attacker))` — `require_owner_or_delegate` passes against the stale owner, post-borrow solvency is proven against collateral Bob now owns, and funds leave to `attacker`. Bob's `withdraw`/`add_delegate` calls revert because he is neither the cached owner nor listed under it.

pub(crate) fn is_owner_or_delegate(
    env: &Env,
    account_id: u64,
    caller: &Address,
    owner: &Address,
) -> bool {
    if caller == owner {
        return true;
    }
    let active_manager =
        storage::get_position_manager(env, caller).is_some_and(|config| config.is_active);
    active_manager && storage::get_delegates(env, account_id, owner).contains(caller)
}

/// Requires the owner or a registered, active manager delegated by that owner.
pub(crate) fn require_owner_or_delegate(
    env: &Env,
    account_id: u64,
    caller: &Address,
    owner: &Address,
) {
    if is_owner_or_delegate(env, account_id, caller, owner) {
        return;
    }
    panic_with_error!(env, GenericError::NotAuthorized);
}
