### Title
Operator QR-code expiration is checked only once at signup entry, letting a near-expired operator authorization cover the entire subsequent signup flow - ([File: src/plans/mod.rs])

### Summary
`MasterPlan::scan_remaining_qr_codes` decides whether the previously-scanned operator QR-code (`OperatorData`) is still valid by comparing `operator_data.timestamp.elapsed()` against `operator_qr_expiration_time` exactly once, at the moment `do_signup` starts processing. [1](#0-0)  Once this single check passes, the same `OperatorData` (and its associated `location_data`/`qr_code`) is carried unchanged through `verify_operator_qr_code`-validated authorization for the rest of the signup: waiting for user readiness, biometric capture, the biometric pipeline, fraud detection, and enrollment/upload. [2](#0-1) [3](#0-2) 

### Finding Description
The operator QR-code expiration mechanism exists to bound how long an operator's validated identity/location (`OperatorData.timestamp`, set in `scan_initial_qr_codes` and `scan_remaining_qr_codes`) can be reused before requiring a fresh backend validation via `verify_operator_qr_code`. [4](#0-3) [5](#0-4)  The check is evaluated only at the branch-match point in `scan_remaining_qr_codes`: `operator_data.timestamp.elapsed() < operator_qr_expiration_time`. [6](#0-5)  If the elapsed time is just under the expiration threshold at that instant, the resolved `OperatorData` is bound into `ResolvedQrCodes`/`personal_custody_package::Credentials` and used for the remainder of `do_signup`, which includes a fixed 3-second wait, biometric capture (which can run up to the full capture timeout), the biometric pipeline, fraud detection, and PCP credential packaging/enrollment — all of which can take substantially longer than the remaining margin before the timestamp would have expired. [7](#0-6) [8](#0-7)  No subsequent re-check of `operator_data.timestamp.elapsed()` against `operator_qr_expiration_time` occurs after this point in the signup path. This is the same bug class as the am-AMM issue: a time-bounded authorization is validated at one instant but its effect extends, unchecked, over the entire following processing window, allowing an actor to time their action to just barely pass the boundary check and reap benefits for the whole subsequent period.

### Impact Explanation
An operator (or a self-serve flow reusing a previously-captured `OperatorData`) whose QR-code authorization is on the verge of expiring can still have that stale authorization bound to and used for a full signup/enrollment that completes well after the intended validity window, producing a misattributed signup: the enrollment credentials (`operator_qr_code`, location data) embedded in the `personal_custody_package::Credentials` reflect an operator association that the expiration policy was meant to have invalidated by the time capture/enrollment actually occurs. [8](#0-7)  This is a Medium-severity trust-boundary timing gap rather than a full authorization bypass, since the QR-code itself must have passed `verify_operator_qr_code` at some point.

### Likelihood Explanation
Exploitation only requires timing the signup so that `scan_remaining_qr_codes` is entered right before `operator_qr_expiration_time` elapses; the attacker/operator does not need to defeat any cryptographic check, only benefit from the absence of a re-check for the remainder of a multi-step, multi-second-to-multi-minute signup flow. [9](#0-8) 

### Recommendation
Re-validate `operator_data.timestamp.elapsed() < operator_qr_expiration_time` at additional checkpoints later in `do_signup` (e.g., before biometric capture completes and before enrollment/credential packaging), or bind the expiration check to the time the operator authorization is actually consumed (credential build/enrollment) rather than only to the time it is first resolved in `scan_remaining_qr_codes`. [3](#0-2) 

### Proof of Concept
1. Scan an operator QR-code so that `OperatorData.timestamp` is set (via `scan_initial_qr_codes`/`scan_remaining_qr_codes`). [10](#0-9) 
2. Wait until `operator_data.timestamp.elapsed()` is just below `operator_qr_expiration_time` (e.g., a few milliseconds before expiry), then trigger `do_signup`, which enters `scan_remaining_qr_codes` and passes the single elapsed-time check. [6](#0-5) 
3. Proceed through biometric capture, pipeline, fraud detection, and enrollment (which together can take well beyond `operator_qr_expiration_time`) without any further validity check on `operator_data.timestamp`; the signup completes and is enrolled using the operator association that should have expired mid-flow. [11](#0-10)
