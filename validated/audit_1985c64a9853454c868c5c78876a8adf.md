## Title
`TokenExchange.exchange_token` sends `client_secret` to a shop host taken from an unvalidated JWT `dest` claim - ([File: lib/shopify_api/auth/token_exchange.rb])

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` derives the destination host for the token-exchange HTTP request directly from the `dest` claim of the caller-supplied session token, without ever passing it through `Utils::ShopValidator.sanitize!`, unlike every other credential-issuing method in the same module and file.

### Finding Description
`exchange_token` decodes the caller-supplied `session_token` via `JwtPayload.new(session_token)` and takes `dest_shop = jwt_payload.shop`. [1](#0-0) 
`JwtPayload#shop` merely strips the `"https://"` prefix from the raw `dest` claim, with no check that the resulting string is a `myshopify.com`/trusted Shopify domain: [2](#0-1) 

`dest_shop` is then used, unsanitized, to build the session used for the outbound HTTP client, and the `client_secret` is placed in the request body sent to that host: [3](#0-2) 

`Clients::HttpClient#initialize` builds the request base URI directly from `session.shop`: [4](#0-3) 

This is inconsistent with the rest of the same file/module: `migrate_to_expiring_token` (same file) calls `Utils::ShopValidator.sanitize!(shop)` before building the session and sending `client_secret`: [5](#0-4) 
and `client_credentials.rb` / `refresh_token.rb` do the same: [6](#0-5) [7](#0-6) 

The security-relevant equality the fix in the sibling methods enforces is: *"the host that receives `client_secret`" == "a host in `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`"*. In `exchange_token`, that equality is never checked; the code implicitly trusts `dest_shop == host that receives client_secret` purely because the JWT signature validated. `JwtPayload` only verifies the *signature and claims* (`aud`, `exp`, `nbf`) of the token — it does not verify that `dest` is a Shopify domain, so a syntactically valid but non-Shopify `dest` value inside an otherwise-legitimately-signed token would sail straight through to `HttpClient`, which builds `https://#{dest_shop}` as the request target and posts `client_id`/`client_secret` there.

### Impact Explanation
If `dest_shop` can be influenced or is not strictly guaranteed to equal a genuine `*.myshopify.com` host, the app's `client_secret` is sent to a host that is not the intended trusted Shopify domain — SSRF carrying the app's own client_secret (an High-severity category per the rules: "SSRF with the app's credentials"). This exactly matches the requested analog class: "a host validated versus the host that receives the ... `client_secret`" — the host is used to route the client_secret without being run through the same validation (`ShopValidator.sanitize!`) applied everywhere else in the codebase for this exact purpose.

### Likelihood Explanation
Exploitability rests entirely on whether an attacker can get `JwtPayload` to accept a token whose `dest` is not a genuine Shopify domain. `JwtPayload` verifies the signature against `Context.api_secret_key` (and optionally `old_api_secret_key`), so forging an arbitrary `dest` normally requires knowledge of the app's secret — which is out of scope per the rules ("anything requiring ... leaked credentials"). Session tokens are also normally minted only by Shopify's own App Bridge/`session_token()` mechanism, which always sets `dest` to the real shop domain, so under normal operation this path is safe. The residual risk is architectural: this function is the *only* credential-minting path in the file that skips `ShopValidator.sanitize!`, breaking defense-in-depth that the maintainers clearly intended (as evidenced by every sibling method using it). I cannot demonstrate an end-to-end exploit without a way to produce a validly-signed token with an attacker-chosen `dest` (which the rules exclude, since that requires the secret), so likelihood without a secondary bug (e.g., a key-confusion or `old_api_secret_key` misconfiguration) is low.

### Recommendation
In `exchange_token`, call `Utils::ShopValidator.sanitize!(dest_shop)` (mirroring `migrate_to_expiring_token`, `client_credentials`, and `refresh_token`) before constructing `shop_session`/`Session.from`, so the host that ultimately receives `client_id`/`client_secret` is always constrained to `ShopValidator::TRUSTED_SHOPIFY_DOMAINS` regardless of how `dest` was populated.

### Proof of Concept
Not independently reproducible within the scope of this gem alone: it requires a validly HS256-signed JWT (signed with the app's own `api_secret_key`/`old_api_secret_key`) whose `dest` claim is a non-Shopify host, which requires possessing the app secret — out of scope per the rules. The finding is a code-level inconsistency/defense-in-depth gap rather than a demonstrated standalone bypass:
1. `JwtPayload.new(token)` verifies signature/claims only, never validates `dest`'s domain — [8](#0-7) 
2. `exchange_token` uses `dest_shop` unsanitized to build the request target that carries `client_secret` — [9](#0-8) 
3. Compare with the sanitized sibling call — [10](#0-9)

      sig { params(token: String).void }
      def initialize(token)
        payload_hash = begin
          decode_token(token, Context.api_secret_key)
        rescue ShopifyAPI::Errors::InvalidJwtTokenError
          raise unless Context.old_api_secret_key

          decode_token(token, T.must(Context.old_api_secret_key))
        end

        @iss = T.let(payload_hash["iss"], String)
        @dest = T.let(payload_hash["dest"], String)
        @aud = T.let(payload_hash["aud"], String)
        @sub = T.let(payload_hash["sub"], T.nilable(String))
        @exp = T.let(payload_hash["exp"], Integer)
        @nbf = T.let(payload_hash["nbf"], Integer)
        @iat = T.let(payload_hash["iat"], Integer)
        @jti = T.let(payload_hash["jti"], String)
        @sid = T.let(payload_hash["sid"], T.nilable(String))

        raise ShopifyAPI::Errors::InvalidJwtTokenError,
          "Session token had invalid API key" unless @aud == Context.api_key
      end

      sig { returns(String) }
      def shop
        @dest.gsub("https://", "")
      end
