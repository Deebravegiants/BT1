Based on my investigation, I found a genuine analog: `Router.buy()` in `packages/contracts/src/Router.sol` is missing the `pairAddr == address(0)` guard that every sibling lookup function (`sell`, `previewBuy`, `getAmountOut`, `graduate`, `addInitialLiquidity`) explicitly has.

### Title
Missing pair-existence NULL check in `Router.buy()` compared to all sibling entry points - (File: `packages/contracts/src/Router.sol`)

### Summary
`Router.buy()` resolves `pairAddr` via `factory.getPair(token, asset)` and immediately feeds it into `_computeBuy`, a token transfer, and two `IPair` calls — with no `if (pairAddr == address(0)) revert PairNotFound();` guard. Every other function in `Router.sol` that performs the identical `assetTokenFor` → `factory.getPair` lookup (`sell`, `previewBuy`, `getAmountOut`, `graduate`, `addInitialLiquidity`) has this exact guard immediately after the lookup [1](#0-0) , [2](#0-1) , [3](#0-2) , [4](#0-3) , [5](#0-4) , while `buy()` omits it entirely: [6](#0-5) .

### Finding Description
The class of bug in the external report (a lookup table that can return an unmapped/zero result being dereferenced without a NULL check) maps directly onto `Router.buy`. `assetTokenFor(token)` reads `factory.ltFor(token)`, a plain mapping that defaults to `address(0)` for any token never registered via `Factory.createPair` [7](#0-6) . `factory.getPair(token, asset)` likewise defaults to `address(0)` for any unregistered pair [8](#0-7) . In `buy()`, this potentially-zero `pairAddr` is passed straight into `_computeBuy(pairAddr, amountIn)`, which calls `IPair(pairAddr).getReserves()`, `.k()`, and `.tokenBalance()` on it [9](#0-8) , and then further into `IERC20(asset).safeTransferFrom(to, pairAddr, amountInUsed)` and `IPair(pairAddr).transferToken(...)` / `.swap(...)`.

Every other Router function that performs this same lookup treats a zero result as an explicit, named error case (`PairNotFound`) instead of relying on the downstream call reverting for some other reason. `buy()` is the sole outlier, which is inconsistent with the rest of the contract's own defensive pattern and is exactly the class of bug the analog rules describe: a lookup miss that isn't checked before the result is dereferenced.

### Impact Explanation
`Router.buy` is gated by `onlyRole(BONDING_ROLE)`, and in the deployed system only `Bonding` holds that role, and `Bonding` only calls `router.buy` for tokens it has itself launched (i.e., `tokenInfo[token].pair` is always non-zero once `info.creator != address(0)`, per `Bonding.isTrading`/`canGraduate` patterns) [10](#0-9) . I was not able to fully trace, within the remaining tool budget, whether `Bonding._executeBuy`/`buy` performs its own pre-check that guarantees `assetTokenFor(token)`/`factory.getPair` can never resolve to zero for every possible `token` argument accepted by `Bonding.buy` (e.g. whether a token that exists in `Bonding.tokenInfo` but was somehow never registered with `Factory`, or a race with a not-yet-created `Factory` pairing, is reachable). If such a path exists, an unprivileged caller could hit `_computeBuy(address(0), amountIn)`, causing `IPair(address(0)).getReserves()` to revert with no data (a NULL-pointer-style hard revert analogous to the Realtek Bluetooth Oops) rather than the clean `PairNotFound()` error, producing a denial-of-service on that call path with a confusing failure mode. Given the missing check is purely defensive and mirrors code that exists everywhere else in the same file, I cannot confirm a concrete theft or fund-freezing path from `Bonding`'s current call sites without deeper tracing of `Bonding.buy`/`_executeBuy`, which the tool budget did not allow me to complete.

### Likelihood Explanation
Low-to-uncertain reachability from a single unprivileged transaction under the current `Bonding` wiring, since `Bonding` appears to only ever call `router.buy` for tokens with an already-created `Factory` pair. The inconsistency itself (one of six near-identical lookup call sites missing the guard present in the other five) is concrete and verifiable in the source, but I could not fully confirm within this session whether any unprivileged-reachable `Bonding` code path can supply a `token` to `router.buy` for which `factory.getPair` resolves to `address(0)`.

### Recommendation
Add the same `if (pairAddr == address(0)) revert PairNotFound();` guard immediately after `address pairAddr = factory.getPair(token, asset);` in `Router.buy()` (`packages/contracts/src/Router.sol`, lines 99-102), matching the pattern already used in `sell`, `previewBuy`, `getAmountOut`, `graduate`, and `addInitialLiquidity`, so a missing/unregistered pair fails fast with an explicit error instead of an undifferentiated low-level revert inside `_computeBuy`/`IPair` calls.

### Proof of Concept
Not independently confirmed as end-to-end exploitable in this session — I could not verify, within the available tool calls, a `Bonding`-reachable code path where `Bonding.buy(...)` forwards a `token` to `Router.buy` while `Factory.getPair(token, assetTokenFor(token))` is still `address(0)`. A full PoC would need to trace `Bonding.buy`/`_executeBuy`'s pre-checks (`packages/contracts/src/Bonding.sol`) against every `token` value it accepts to determine whether such a mismatch is constructible by an unprivileged caller, which requires more of the file than I was able to read before the session ended.

```text
    function _computeBuy(
        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 amountInUsed, uint256 tokensOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        amountInUsed = amountIn;

        uint256 newReserveAsset = reserveAsset + amountInUsed;
        tokensOut = reserveToken - (k / newReserveAsset);

        uint256 realBalance = pair.tokenBalance();
        if (tokensOut > realBalance) {
            tokensOut = realBalance;
            uint256 cappedReserveToken = reserveToken - tokensOut;
            if (cappedReserveToken == 0) revert OverflowCapDegenerate();
            uint256 cappedReserveAsset = (k + cappedReserveToken - 1) / cappedReserveToken;
            amountInUsed = cappedReserveAsset - reserveAsset;
        }
    }
```
