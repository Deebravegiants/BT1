### Title
Integer overflow panic (DoS / fund-freeze) in `calc_x_power` via extreme mint-decimal AMM pools - (File: `program/src/math.rs`, `program/src/processor.rs`)

### Summary
Similar to CVE-2024-38805 (EDK2 integer overflow/wraparound leading to denial of service), the Raydium AMM program contains an unchecked-magnitude multiplication chain in the PNL-taking path (`Calculator::calc_x_power`, invoked from `Processor::calc_take_pnl`) that is reachable from the unprivileged `Deposit` and `Withdraw` instructions. Because pool coin/pc decimals — and therefore `sys_decimal_value` — are derived directly from attacker-supplied SPL mints at `Initialize2` time, an attacker who creates a pool with extreme (but valid) mint decimals can drive the normalized reserve values (`x1`/`y1`) close to `u128::MAX`. When `calc_x_power` computes `last_x * last_y * current_x`, the product of three such large `U256` values can exceed `U256::MAX`, causing `checked_mul(...).unwrap()` to panic and abort every subsequent `Deposit`/`Withdraw` on that pool.

### Finding Description
`AmmInfo::initialize` sets `sys_decimal_value` from the larger of the two mint decimals it is given: [1](#0-0) 

These decimals come straight from the SPL mints supplied by the pool creator at `Initialize2` — anyone can mint an SPL token with an arbitrary `u8` decimals value and use it to create a Raydium pool: [2](#0-1) [3](#0-2) 

`normalize_decimal_v2` scales raw vault balances by `sys_decimal_value` into `U128`: [4](#0-3) 

`calc_take_pnl` (reached from `process_deposit`, `process_withdraw`, and swap flows) feeds these normalized `x1`/`y1` values, together with previously stored `target.calc_pnl_x`/`calc_pnl_y`, into `Calculator::calc_x_power`: [5](#0-4) [6](#0-5) 

`calc_x_power` performs `last_x.checked_mul(last_y).unwrap().checked_mul(current_x).unwrap()` in `U256`. Each of `last_x`, `last_y`, `current_x`, `current_y` can individually approach `u128::MAX` when `sys_decimal_value` is large (up to `10^19`, the largest power of ten that still fits `u64` and therefore still passes `checked_pow` in `initialize`) and vault balances are large `u64` values. Multiplying three such ~10^38-magnitude values overflows `U256` (~1.16 × 10^77), so `checked_mul(...).unwrap()` panics, aborting the transaction with a runtime panic rather than a controlled error.

### Impact Explanation
Once a pool's reserves and PNL-tracking state (`target.calc_pnl_x/y`) reach the magnitude that triggers the overflow, every future call into `calc_take_pnl` — i.e., every `Deposit` and `Withdraw` — panics and reverts. Because deposits and withdrawals for that pool go through the same PNL-accounting code path, LPs lose the ability to withdraw their liquidity or coin/pc holdings from the pool, constituting a permanent freezing of LP funds for that pool, matching the "permanent freezing of user or LP funds" impact bar.

### Likelihood Explanation
Exploitation requires an attacker to (1) create SPL mints with extreme decimal values (a permissionless SPL Token operation), (2) permissionlessly create a Raydium pool for that mint pair via `Initialize2`, and (3) drive vault balances/PNL state to the magnitude needed to overflow the `U256` multiplication chain in `calc_x_power`. All of these steps are reachable from a single attacker-controlled account with no privileged signer, but require carefully chosen extreme decimals and large balances, so likelihood is moderate rather than trivial.

### Recommendation
- Bound `pc_decimals`/`coin_decimals` (and thus `sys_decimal_value`) to realistic values (e.g., ≤ 9) during `process_initialize2`, rejecting mints with excessive decimals.
- In `Calculator::calc_x_power`, replace the chained `U256` multiplication with an overflow-safe formulation (e.g., reorder operations to divide earlier, or use a wider integer type / checked arithmetic that returns a program error instead of panicking) so pool state can never become unrecoverable.
- Convert `.unwrap()` panics in `calc_take_pnl`/`calc_x_power` into explicit `AmmError` returns to avoid hard panics being the failure mode for extreme-but-reachable inputs.

### Proof of Concept
1. Create two SPL mints, one with `decimals = 19` and one with `decimals = 0` (or another extreme pairing), both permissionless operations.
2. Call `Initialize2` to create a Raydium pool for this mint pair; `sys_decimal_value` becomes `10^19` per `AmmInfo::initialize`.
3. Perform deposits/swaps to push the low-decimal-side vault balance close to `u64::MAX`.
4. `normalize_decimal_v2` scales this balance by `10^19`, producing `x1`/`y1` values approaching `u128::MAX`.
5. On the next `Deposit`/`Withdraw`, `calc_take_pnl` → `calc_x_power` multiplies three such large values together in `U256`, exceeding `U256::MAX`; `checked_mul(...).unwrap()` panics, reverting the transaction and — once the pool state has reached this magnitude — permanently blocking further deposits/withdrawals on that pool.

    pub fn calc_x_power(last_x: U256, last_y: U256, current_x: U256, current_y: U256) -> U256 {
        // must be use u256, because u128 may be overflow
        let x_power = last_x
            .checked_mul(last_y)
            .unwrap()
            .checked_mul(current_x)
            .unwrap()
            .checked_div(current_y)
            .unwrap();
        x_power
    }
