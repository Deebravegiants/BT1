### Title
Webhook shop/topic/id headers are trusted without HMAC coverage, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only [1](#0-0) , but exposes `shop`, `topic`, `webhook_id`, and `api_version` as plain, unauthenticated header reads [2](#0-1) . `Registry.process` validates only the HMAC of the body and then uses the unauthenticated `request.shop`/`request.topic` values to route and label the webhook to the handler [3](#0-2) .

### Finding Description
The intended binding is: `HMAC-verified content == identity fields the handler relies on`. Here that breaks down to: `to_signable_string (raw_body only)` != `{shop, topic, webhook_id, api_version}` used to build `WebhookMetadata`. An attacker who receives any one genuine, validly-HMAC-signed webhook body (e.g., by installing the target app on their own store and receiving a webhook for `orders/create` or similar) can replay the exact same raw body to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header with an arbitrary victim shop domain or topic. Because `Utils::HmacValidator.validate` only recomputes the HMAC over `@raw_body` [4](#0-3)  and the body is unchanged, the signature still validates, and `Registry.process` dispatches the forged `shop`/`topic` values straight into `WebhookMetadata` passed to the app's handler [5](#0-4) .

### Impact Explanation
This crosses the tenant boundary the report's bug-class describes: a field (`shop`) that is acted upon by the handler is not covered by the same authenticity check (`hmac`) applied elsewhere. An attacker-controlled shop identifier reaching the app's webhook handler as if it were verified data can cause the app to process/store data under, or trigger actions attributed to, an arbitrary victim shop — a cross-tenant confusion condition.

### Likelihood Explanation
Requires only an unprivileged attacker who can install the merchant's app on their own (attacker-owned) test store to obtain one genuinely signed webhook body, then replay it with a modified header value using any HTTP client. No secrets, tokens or elevated privileges are needed.

### Recommendation
Include `shop`, `topic`, and any other header-derived identity fields in the HMAC-signable content (or otherwise cryptographically bind them to the body), or document/require that host applications independently verify `X-Shopify-Shop-Domain` against a known/allow-listed shop before trusting `WebhookMetadata#shop`.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and receives a legitimate webhook POST with body `B` and valid `X-Shopify-Hmac-Sha256` header `H` (HMAC over `B` with the app's secret).
2. Attacker replays a POST to the app's webhook endpoint with the same body `B` and same `H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `B` against `H` [4](#0-3) .
4. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` [5](#0-4) , causing the app to act as though the webhook genuinely originated from the victim shop.
