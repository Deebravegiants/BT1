### Title
`Bonding.transferCreator` accepts a system contract address (Bonding/Zap/FeeVault/Pair) as the new creator, permanently freezing all future creator-fee payouts - (File: `packages/contracts/src/Bonding.sol`)

### Summary
`Bonding.transferCreator(address tokenAddress, address newCreator)` only rejects `address(0)` and a no-op re-assignment; it performs no check that `newCreator` is not one of alt.fun's own non-EOA contracts (`Bonding`, the `Zap`, the `FeeVault`, the token's `Pair`, or an LT). This mirrors the reported class of bug in the external report — a privileged/special contract address being usable in a generic "account" identity slot with no guard — and, once set, permanently bricks every future creator-fee claim for that token.

### Finding Description
`transferCreator` is a fully permissionless-to-the-creator entry point: [1](#0-0) 

The only validation is `newCreator != address(0)` and `newCreator != info.creator`. There is no check that `newCreator` is an EOA, nor any denylist of the protocol's own contracts.

`info.creator` (i.e., whatever `transferCreator` sets it to) is subsequently read by `Zap` on every buy/sell to route creator fees: [2](#0-1) [3](#0-2) 

The fee is transferred into `FeeVault` and credited to `creatorBalance[creator]`: [4](#0-3) 

The only way to retrieve that balance is `claim()`, which pays out to `msg.sender`: [5](#0-4) 

If `newCreator` is set to `address(bonding)`, `address(zap)`, `address(feeVault)`, or the token's own `Pair` address (all of which are contracts with no code path that calls `FeeVault.claim()` as themselves), every USDC fee accrued to that address from that point forward becomes permanently unclaimable — it is credited into `creatorBalance[newCreator]` and counted in `totalAccruedCreator`, so it can never be swept via `sweepDonations()` either (that function only sweeps balance in excess of `totalAccruedCreator + protocolBalance`).

This is the direct analog of the external report: neither `_authenticateDeleverage()` in the reported bug nor `transferCreator()` here validates that a "special" contract address (the vault / a protocol-internal contract) isn't accepted into a generic identity parameter (`Account` / `newCreator`), and in both cases the omission corrupts accounting tied to that identity.

### Impact Explanation
Any token creator can (accidentally, via a UI bug, or through a malicious frontend/bookmarklet) call `transferCreator(tokenAddress, address(feeVault))` or any other in-protocol contract address. From that point on, all creator-side trading fees for that token (`creatorFeeBps` share of every buy/sell fee, indefinitely, for the life of the token) are irretrievably locked inside `FeeVault`, since:
- `claim()` can only pay `msg.sender`, and none of `Bonding`/`Zap`/`FeeVault`/`Pair` can call it on their own behalf,
- the locked balance is counted in `totalAccruedCreator`, so `sweepDonations()` cannot recover it either.

This is a permanent freezing of creator funds (Medium-severity impact per the accepted class), with no recovery path — not even via a protocol admin, since `FeeVault` exposes no admin override to redirect a specific creator's balance.

### Likelihood Explanation
The action requires only the current token creator (an unprivileged, permissionless actor explicitly in scope) calling a single public function with no special conditions, gas cost, or timing constraints. No slippage/oracle/market state is needed. The main friction is that a rational creator would not deliberately destroy their own future fee stream, but the complete absence of any address sanity-check (not even an `isContract`/system-address guard) means it can happen from a copy-paste error, a malicious dApp/wallet integration tricking the creator into signing a bad `newCreator`, or a compromised frontend — exactly the kind of "missing validation on an identity parameter" class flagged in the source report.

### Recommendation
In `transferCreator`, reject any `newCreator` equal to a known protocol contract:
```solidity
function transferCreator(address tokenAddress, address newCreator) external {
    if (newCreator == address(0)) revert ZeroAddress();
    BondingStorage storage $ = _s();
    TokenInfo storage info = $.tokenInfo[tokenAddress];
    if (
        newCreator == address(this) ||
        newCreator == address($.router) ||
        newCreator == info.pair ||
        newCreator == info.ltAddress ||
        // also disallow known Zap/FeeVault addresses, e.g. via an owner-set denylist or isRouter-style check
        false
    ) revert InvalidInput();
    if (msg.sender != info.creator) revert NotCreator();
    if (newCreator == info.creator) revert InvalidInput();
    info.creator = newCreator;
    emit CreatorTransferred(tokenAddress, msg.sender, newCreator);
}
```
Since `Zap`/`FeeVault` addresses aren't known to `Bonding`, consider instead adding a generic `extcodesize`/`isContract` guard (as the original report suggests) or maintaining an explicit denylist of protocol-owned addresses that is checked here, and additionally allow `FeeVault` owner to reassign an unclaimable creator balance as a backstop.

### Proof of Concept
1. Creator launches a token via `Zap.createToken`, becoming `info.creator = creator`.
2. Creator calls `Bonding.transferCreator(tokenAddress, address(feeVault))` (or `address(bonding)` / the token's `pair`). No revert occurs — only `address(0)` and self-reassignment are checked.
3. Subsequent buys/sells on the token invoke `Zap._accrueFee(token, feeVault_address_as_creator, feeAmount, isBuy)`, which calls `FeeVault.accrue(token, address(feeVault), creatorShare, protocolShare, isBuy)`, crediting `creatorBalance[address(feeVault)] += creatorShare`.
4. `FeeVault.claim()` can never be called as `address(feeVault)` itself (it is a contract, not an externally-owned caller of its own function), so `creatorBalance[address(feeVault)]` is permanently stuck.
5. `sweepDonations()` cannot recover it either, since it is counted in `totalAccruedCreator` and thus excluded from the "unbacked" donation surplus. [1](#0-0) [6](#0-5)

```text
    function accrue(
        address token,
        address creator,
        uint256 creatorAmount,
        uint256 protocolAmount,
        bool isBuy
    ) external onlyDepositor {
        FeeVaultStorage storage $ = _s();
        if (creatorAmount > 0) {
            if (creator == address(0)) revert ZeroAddress();
            $.creatorBalance[creator] += creatorAmount;
            $.totalAccruedCreator += creatorAmount;
            $.lifetimeCreatorEarned[creator] += creatorAmount;
        }
        if (protocolAmount > 0) {
            $.protocolBalance += protocolAmount;
            $.lifetimeProtocolEarned += protocolAmount;
        }
        if ($.usdc.balanceOf(address(this)) < $.totalAccruedCreator + $.protocolBalance) {
            revert UnderfundedAccrual();
        }
        emit FeeAccrued(token, creator, creatorAmount, protocolAmount, isBuy);
    }
```
