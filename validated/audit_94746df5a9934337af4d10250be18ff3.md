### Title
EvmHost's state commitment veto resets `_latestStateMachineHeight` to a hardcoded `1` instead of the real prior height - ([File: evm/src/core/EvmHost.sol])

### Summary
The OpenBao report describes a deletion routine that, when reverting/cleaning up state, fails to properly restore prior state, leaving inconsistent bookkeeping behind. The Solidity `EvmHost.deleteStateMachineCommitmentInternal` has the analogous defect: when a fisherman vetoes the *latest* state commitment for a state machine, the height pointer is reset to a hardcoded `1` rather than to the actual previously-committed height, unlike the Substrate `pallet-ismp` implementation of the same operation, which explicitly tracks and restores `PreviousStateMachineHeight`.

### Finding Description
`EvmHost.deleteStateMachineCommitmentInternal` deletes the state commitment and its update time, then "resets" the latest-height pointer when the vetoed height was the latest: [1](#0-0) 

```
_latestStateMachineHeight[height.stateMachineId] = 1;
```

There is no equivalent to a "previous height" tracker in `EvmHost.sol` (no `_previousLatestStateMachineHeight` mapping exists in the contract), so the reset value is a fixed constant, not the honest prior height.

Compare this to the Substrate implementation of the same operation (`delete_state_commitment` in `pallet-ismp`), which deliberately stores and restores the actual previous height when the vetoed height is the latest one: [2](#0-1) 

The Rust side explicitly maintains `PreviousStateMachineHeight` for this purpose and documents the queue/cap interactions carefully (see the extensive design comments and dedicated regression tests): [3](#0-2) 

The EVM host, by contrast, has no such mechanism and simply discards the real prior height in favor of `1`. This is architecturally the same class of bug as the OpenBao report: a deletion/cleanup path that is supposed to safely roll back to a known-good prior state instead leaves the bookkeeping in an inconsistent, under-specified condition (analogous to "leaving unrelated storage entries around" / failing to fully restore state on retry-of-deletion).

### Impact Explanation
`_latestStateMachineHeight` is the authoritative "current height" pointer per state machine on the EVM host, consulted by consensus-client update validation (to reject/accept new state machine updates) and any downstream logic (fee/challenge-period/relayer flows) that treats "latest" as reflecting real chain progress. Resetting it to `1` after a veto of the latest legitimate commitment does not represent any actual previously-verified state — it is an arbitrary sentinel far below the real chain height. This can allow a subsequent (even much lower, stale, or attacker-influenced) height to be accepted as a fresh "latest" update where the true prior valid height should have been the floor, undermining the monotonicity guarantee that message delivery, state proofs, and challenge-period computations depend on. The precise blast radius (whether an attacker can leverage this to force acceptance of a stale/forged state commitment or otherwise bypass proof freshness checks) depends on how `_latestStateMachineHeight` is consumed by the consensus-client update path and by state-proof consumers, which I was not able to fully trace within the remaining investigation budget.

### Likelihood Explanation
Triggering the bad reset requires only that a fisherman veto the *latest* commitment for a state machine — vetoes are permissionless for any active collator and require no proof beyond collator-set membership (as documented for the Substrate side), and `deleteStateMachineCommitment` on the EVM host is called by the "handler" role that processes such vetoes/fraud-proof messages from Hyperbridge. Since honest fishermen routinely veto fraudulent commitments (including possibly the latest one), this code path is reachable through ordinary, expected protocol operation rather than an exotic attack — it does not require a malicious actor, only a legitimate veto of the newest commitment.

### Recommendation
Add a `_previousStateMachineHeight` (or similarly named) mapping to `EvmHost`, populate it alongside `_latestStateMachineHeight` in `storeStateMachineCommitment`, and use it in `deleteStateMachineCommitmentInternal` to restore the actual last-known-good height instead of the hardcoded `1`, mirroring the Substrate `PreviousStateMachineHeight` design in `modules/pallets/ismp/src/host.rs`.

### Proof of Concept
1. Consensus client submits commitments for heights `H1 < H2` on a given `stateMachineId`; `_latestStateMachineHeight` becomes `H2` via `storeStateMachineCommitment`. [4](#0-3) 
2. A fisherman/handler determines `H2`'s commitment is fraudulent and calls `deleteStateMachineCommitment(height=H2, fisherman)`.
3. Inside `deleteStateMachineCommitmentInternal`, since `_latestStateMachineHeight[id] == H2`, the pointer is set to `1` rather than `H1`. [5](#0-4) 
4. `_latestStateMachineHeight[id]` now reads `1`, discarding the legitimately-verified `H1`, leaving the host's height bookkeeping in a state inconsistent with what was actually finalized — the same "deletion path fails to fully/correctly restore state" pattern as the reported OpenBao vulnerability.

    function deleteStateMachineCommitmentInternal(StateMachineHeight memory height, address fisherman) internal {
        StateCommitment memory stateCommitment = _stateCommitments[height.stateMachineId][height.height];
        delete _stateCommitments[height.stateMachineId][height.height];
        delete _stateCommitmentsUpdateTime[height.stateMachineId][height.height];
        // technically any state commitment can be vetoed, safety check that it's the latest before resetting it.
        if (_latestStateMachineHeight[height.stateMachineId] == height.height) {
            _latestStateMachineHeight[height.stateMachineId] = 1;
        }

        // track the fisherman responsible for rewards on hyperbridge through state proofs
        _vetoes[height.stateMachineId][height.height] = fisherman;

        emit StateCommitmentVetoed({
            stateMachineId: this.stateMachineId(_hostParams.hyperbridge, height.stateMachineId),
            stateCommitment: stateCommitment,
            height: height.height,
            fisherman: fisherman
        });
    }

	fn delete_state_commitment(&self, height: StateMachineHeight) -> Result<(), Error> {
		// The height's entry in the state commitment queue is deliberately left
		// behind; locating it would mean scanning the queue, which is the per-insert
		// cost the queue exists to avoid. Usually its eviction is a no-op, but when
		// the vetoed height is the latest the reset below re-opens it for honest
		// resubmission, and the resubmitted height gets a *second* queue entry. The
		// stale entry then evicts the live commitment when it reaches the head —
		// one insertion before the live entry would have, since the resubmission
		// lands directly behind its stale twin. So a veto costs that height one
		// insertion of retention and permanently burns one queue slot. Both are
		// negligible against the configured caps; making it exact would need a
		// height -> index map on the insert path.
		BoundedStateCommitments::<T>::remove(height.id, height.height);
		BoundedStateMachineUpdateTime::<T>::remove(height.id, height.height);

		// technically any state commitment can be vetoed,
		// safety check that it's the latest before resetting it.
		if let Some(latest) = LatestStateMachineHeight::<T>::get(height.id) {
			if latest == height.height {
				// Reset back to the initial height to allow for honest updates
				let prev_height =
					PreviousStateMachineHeight::<T>::get(height.id).ok_or_else(|| {
						Error::Custom("Previous state machine height should exist".to_string())
					})?;
				LatestStateMachineHeight::<T>::insert(height.id, prev_height);
			}
		}
		Ok(())
	}

// A height below the latest can never be resubmitted — the consensus handler skips
// anything at or below `previous_latest_height` — so its stale queue entry has no
// live twin and evicting it touches nothing.
#[test]
fn vetoed_height_that_cannot_be_resubmitted_evicts_as_a_noop() {
	let mut ext = new_test_ext();
	ext.execute_with(|| {
		let host = Ismp::default();
		let id = queue_test_state_machine();
		let store = |height: u64| {
			host.store_state_machine_commitment(
				StateMachineHeight { id, height },
				queue_test_commitment(),
			)
			.unwrap();
			host.store_latest_commitment_height(StateMachineHeight { id, height }).unwrap();
		};

		pallet_ismp::Pallet::<Test>::update_commitment_caps(
			RuntimeOrigin::root(),
			BTreeMap::from([(id, 2)]),
		)
		.unwrap();

		store(10);
		store(11);

		// Veto a height below the latest: the commitment goes away immediately while
		// its queue entry stays behind as a stale index. The latest height is
		// untouched, so 10 stays permanently unsubmittable.
		host.delete_state_commitment(StateMachineHeight { id, height: 10 }).unwrap();
		assert!(host.state_machine_commitment(StateMachineHeight { id, height: 10 }).is_err());
		assert_eq!(host.latest_commitment_height(id).unwrap(), 11);
		assert_eq!(
			CommitmentQueueStates::<Test>::get(id),
			CommitmentQueueState { head: 0, tail: 2 }
		);
		assert_eq!(StateCommitmentQueue::<Test>::get(id, 0), Some(10));

		// The stale index is evicted as a no-op on the next insertion.
		store(12);
		assert_eq!(
			CommitmentQueueStates::<Test>::get(id),
			CommitmentQueueState { head: 1, tail: 3 }
		);
		assert!(StateCommitmentQueue::<Test>::get(id, 0).is_none());
		assert!(host.state_machine_commitment(StateMachineHeight { id, height: 11 }).is_ok());
		assert!(host.state_machine_commitment(StateMachineHeight { id, height: 12 }).is_ok());
	})
}
