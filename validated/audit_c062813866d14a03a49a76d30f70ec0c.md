### Title
Webhook `shop` and `topic` identity fields are not covered by the HMAC signature, enabling cross-tenant webhook replay - (`lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while `shop`, `topic`, `api_version`, and `webhook_id` are taken verbatim from unauthenticated HTTP headers. `Registry.process` validates the HMAC over the body only, then trusts those header-derived fields to build `WebhookMetadata` that is handed to the host app's handler. An attacker who has legitimately observed one valid `(raw_body, hmac)` pair (e.g. from their own shop's webhook traffic) can replay it with an arbitrary `shop-domain` header and the signature check still passes, because the header was never part of what was signed.

### Finding Description
The identity binding that should hold is:

`shop asserted in WebhookMetadata.shop == shop that produced the HMAC-covered bytes`

In practice this equality does not hold, because the HMAC only covers the body: [1](#0-0) 

and the `shop`, `topic`, `webhook_id`, `api_version` accessors are read straight from headers with no cryptographic tie to the body: [2](#0-1) 

`Registry.process` performs the HMAC check and then immediately trusts these header-derived fields to build the metadata passed to the app's handler: [3](#0-2) 

`HmacValidator.validate` computes/compares the signature purely against `verifiable_query.to_signable_string` (the raw body for webhooks), with no header material folded in: [4](#0-3) 

Because the signature check only proves "this body was produced by someone holding `api_secret_key`" and says nothing about which shop or topic that body belongs to, an attacker who possesses one valid `(raw_body, hmac)` pair — for instance, by being a merchant who has installed the app and can observe their own shop's legitimate webhook deliveries, which requires no privileged account or secret — can resend that exact body/hmac pair to the app's webhook endpoint while substituting a different `shopify-shop-domain` (and/or `shopify-topic`) header. `Utils::HmacValidator.validate` still returns `true` (the body/hmac pair is unchanged and valid), and `Registry.process` will happily hand the handler a `WebhookMetadata` claiming the payload belongs to the attacker-chosen victim shop.

### Impact Explanation
Host applications built on this gem are documented to trust `WebhookMetadata#shop` as the authenticated tenant identifier for a webhook delivery (this is the only shop-identifying signal the gem exposes for webhooks). Since that field is not bound to the HMAC, an unprivileged attacker can attribute one shop's genuine webhook payload to another (attacker-chosen) shop domain in the host app's handler, causing cross-tenant data confusion/injection in any app logic keyed off `data.shop` (e.g. writing order/customer data into the wrong tenant's records). This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is moderate-to-high for any attacker who has legitimate access to at least one shop running the app (a normal, unprivileged merchant install — no leaked secrets or elevated access needed): they can capture their own shop's real webhook `(raw_body, hmac-sha256)` pair from network traffic they legitimately receive, then replay it with a forged `shop-domain`/`topic` header at will, repeatedly, against the same public webhook endpoint.

### Recommendation
Bind the identity-carrying headers into the signature verification path instead of relying on body-only HMAC, e.g. incorporate `shop-domain`, `topic`, and `webhook-id` into `Request#to_signable_string` (or perform an independent, out-of-band cross-check that the `shop` in a delivered webhook matches a shop for which this specific `webhook_id`/subscription was actually registered) before invoking the handler in `Registry.process`. At minimum, document explicitly that `WebhookMetadata#shop`/`#topic` are unauthenticated and that host applications must independently validate them (e.g. against their own webhook subscription records) before trusting them for tenant-scoped operations.

### Proof of Concept
```ruby
# Attacker owns/operates shop "attacker-shop.myshopify.com" and receives a legitimate
# webhook for their own shop, capturing the exact bytes and header:
raw_body = '{"id":123,"note":"legit order for attacker-shop"}'
hmac     = "shopify_computed_hmac_over_raw_body_only"  # captured from real delivery

# Attacker replays the identical (raw_body, hmac) pair, but swaps the shop header
# to a victim shop domain they do not own:
forged_headers = {
  "x-shopify-topic"        => "orders/create",
  "x-shopify-hmac-sha256"  => hmac,                       # unchanged, still valid
  "x-shopify-shop-domain"  => "victim-shop.myshopify.com", # forged
  "x-shopify-webhook-id"   => "any-id",
  "x-shopify-api-version"  => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

# Passes: HMAC only ever covered raw_body, never the shop-domain header.
ShopifyAPI::Webhooks::Registry.process(request)
# => handler.handle(data: WebhookMetadata.new(topic: "orders/create",
#                                              shop: "victim-shop.myshopify.com",  # forged, trusted
#                                              body: parsed_body, ...))
```
`Utils::HmacValidator.validate(request)` returns `true` for this forged request because it only re-derives and compares the HMAC of `raw_body`; the `shop-domain` header used to populate `WebhookMetadata#shop` is never part of that computation.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

        def validate(verifiable_query)

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
