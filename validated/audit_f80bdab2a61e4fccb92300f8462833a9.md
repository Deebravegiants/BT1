## Title
Webhook `shop`, `topic`, `api_version` and `webhook_id` fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while `shop`, `topic`, `webhook_id`, and `api_version` are read from unauthenticated HTTP headers and are trusted downstream once `HmacValidator.validate` succeeds. An attacker who legitimately installs the app on any (even free/dev) Shopify store receives genuine webhook deliveries signed with the app's secret. They can replay the exact `raw_body` + `hmac` bytes to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header to name an arbitrary victim shop. The signature still validates (it only checks the body), so the app processes the payload as if it legitimately originated from the victim shop.

### Finding Description
`Webhooks::Request` mixes in `Utils::VerifiableQuery` and defines: [1](#0-0) 

Only `@raw_body` is part of `to_signable_string`; `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from headers and are never included in the signed content.

`HmacValidator.validate` verifies the HMAC purely against `to_signable_string`: [2](#0-1) 

`Registry#process` treats a passing HMAC check as proof of authenticity for the whole `Request`, then forwards the unauthenticated `request.shop` (and `request.topic`) straight to the handler: [3](#0-2) 

This breaks the identity binding `shop authenticated == shop acted on`: the HMAC only proves "this body was signed with our secret at some point," not "this body was delivered for shop X." Since the header value is never bound into the signature, `request.shop` can be swapped for any string while the signature check still passes.

### Impact Explanation
Any app that keys per-tenant logic off `WebhookMetadata#shop` (e.g., locating/creating merchant records, applying uninstall/GDPR actions, updating billing state, or dispatching to per-shop business logic) can be manipulated into applying data originally destined for the attacker's own store to an arbitrary victim shop name of the attacker's choosing. This is a cross-tenant identity-binding break reachable by any unprivileged internet user who can install the app on a store they control (no access to `api_secret_key`, no victim credentials, no TLS interception required) — they only need to capture their own legitimate webhook and resend it with a different `shop-domain` header value.

### Likelihood Explanation
High for any consumer of this gem that dispatches per-shop side effects from `WebhookMetadata.shop`/`topic`: capturing one's own genuine webhook delivery is trivial (any developer/merchant account can install a test app and observe its own webhooks), and replaying an HTTP POST with a modified header requires no special tooling.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the HMAC-signed content (or otherwise cryptographically bind them, e.g., by validating them against Shopify's registered webhook subscription for the app instead of trusting client-supplied headers), so `Utils::HmacValidator.validate` fails whenever any of these fields is altered relative to what was actually signed by Shopify.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and lets Shopify deliver a legitimate webhook (e.g., `orders/create`) to the app's endpoint; the delivery includes headers `X-Shopify-Hmac-Sha256: <hmac>`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Topic: orders/create`, and a raw JSON body.
2. Attacker captures the exact raw body bytes and the `X-Shopify-Hmac-Sha256` value from that legitimate delivery.
3. Attacker re-sends the same raw body and the same `X-Shopify-Hmac-Sha256` header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Registry#process` calls `Utils::HmacValidator.validate(request)` — this passes because it only checks the (unchanged) `raw_body` against the (unchanged) HMAC.
5. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: ..., body: <attacker's own order data>, ...)`, causing the app to attribute/act on attacker-controlled data as if it belonged to `victim-shop.myshopify.com`.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
