### Title
Unconstrained public signals in `MainEVMCircuitMin` let a single Min-path proof be replayed against arbitrary `EmporiumStack` calldata to drain parked Emporium balances - (File: circuits/MainEVMCircuitMin.circom, contracts/CircomDataBuilder.sol, contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
When `externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `erc20TokenAddresses.length == 0`, `formInputForCircom` routes to `formInputEmporiumMin`, which feeds `calldataHash` and `timeStamp` as public signals into `MainEVMCircuitMin`. That circuit never uses `calldataHash` or `outTimeStamp` in any constraint — only `messageSeed` (private) is used to compute the output `message` via Poseidon. Because these public signals never appear in any R1CS row, their Groth16 `IC_i` terms are zero, so a single valid proof verifies for *any* value of `calldataHash`/`timeStamp` supplied at call time, letting an attacker attach a completely different, self-serving `EmporiumStack` (via `externalActionData.externalActionMetadata`) to a previously-generated Min proof and drain any ERC20/ETH balance currently parked in the `EmporiumUpgradeable` contract.

### Finding Description
The claimed invariant is: **the ZK proof's public-input vector must bind the circuit's validity to the exact transaction content it is verified against** — i.e. `verifyProof(a,b,c, input, verifierId)` should only succeed for the *specific* `input` (including `calldataHash`) used to build that proof. This equality is broken.

Path:
1. `formInputForCircom` selects the Min path solely on `externalActionId == HINKAL_EMPORIUM_ACTION_ID && erc20TokenAddresses.length == 0`: `contracts/CircomDataBuilder.sol:139-148`.
2. `formInputEmporiumMin` builds `input = [emporiumMessage, timeStamp, calldataHash]`: `contracts/CircomDataBuilder.sol:150-161`.
3. `MainEVMCircuitMin` declares `outTimeStamp` and `calldataHash` as public inputs but the template body only computes `message <== Poseidon(1)([messageSeed])` — `calldataHash`/`outTimeStamp` are never referenced in any constraint (`circuits/MainEVMCircuitMin.circom:1-18`). In Groth16, a public wire that never appears in any A/B/C row has `IC_i = 0`, so its value contributes nothing to `vk_x`; changing it after the proof is generated does not break verification.
4. `HinkalHelper.performHinkalChecks` only checks that the *submitted* `circomData.calldataHash` matches `getHashedCalldata(circomData)` (a plain keccak of the calldata) — a self-consistency check with no cryptographic tie to the actual proof (`contracts/HinkalHelper.sol:208-236`, `contracts/CircomDataBuilder.sol:10-54`). Since the circuit doesn't constrain `calldataHash` either, an attacker can freely pick any `externalActionData.externalActionMetadata` (i.e., any `EmporiumStack`), recompute a matching `calldataHash`, and still pass verification using one previously generated (or reused) proof for a fixed `messageSeed`/`message`.
5. The only genuinely bound signal is `message` (an output, constrained by Poseidon), which must equal `circomData.emporiumMessage`. `EmporiumUpgradeable.verifyWallet` marks that specific message as used (`usedMessages[circomData.emporiumMessage] = true`) once (`EmporiumUpgradeable.sol:302-316`), so a literal proof can drive one Emporium `runAction` execution per generated `messageSeed` — but generating a new `messageSeed`/proof is trivial, free, and fully within an unprivileged attacker's control (they only need `Poseidon(messageSeed)` and no other secret), making the attack freely repeatable across many messages.
6. Crucially, `verifyWallet` skips the EIP-712 signature check entirely when `stack.signerAddress == address(0)`: `EmporiumUpgradeable.sol:314-316`. With `signerAddress == 0`, `runAction`'s op loop executes `op.endpoint.call{value: op.value}(op.callData)` directly from the Emporium contract's own identity (`EmporiumUpgradeable.sol:91-118`) — with zero authorization beyond the Min proof.
7. `runAction`'s accounting is driven entirely by `circomData.erc20TokenAddresses`, which is forced to length 0 to hit the Min path: `balancesBefore`/`balancesAfter` loops iterate zero times (`EmporiumUpgradeable.sol:85-87, 122-151`), so `BalanceChangeShouldBePositive` and UTXO creation never execute for whatever tokens the injected ops actually move. The op(s) can therefore call an ERC20 token held by Emporium (or Emporium's own address in a self-call chaining further ops) and transfer out Emporium's balance to the attacker with no on-chain accounting whatsoever.

Existing guards fail because: `performHinkalChecks`'s `calldataHash` equality is a plaintext consistency check, not a proof-binding constraint; `dimensionsCheck`/`checkOnchainCreation` only validate array-length consistency for the (empty) token arrays and don't touch `externalActionMetadata`; `verifyProof` succeeds because the unused public signals contribute nothing to the pairing check; and `insertNullifiers`/`rootHashExists` are irrelevant since no UTXO/nullifier is touched by an empty-array Min transaction.

### Impact Explanation
Direct theft of funds held by the `EmporiumUpgradeable` contract (e.g., in-flight balances parked there during multi-step external actions such as swaps/bridges, or residual balances left after `deltaAmountChanges` transfers in `Hinkal._externalTransact`). The attacker's crafted `EmporiumOperation` calls run with Emporium's own `msg.sender` identity and no signature or balance-accounting constraint, so any ERC20/ETH currently in Emporium's custody can be moved to an attacker-controlled address. This is **Critical**: direct theft of shielded/in-flight user funds and execution of calls (moving assets) that were never authorized by any wallet owner or by circuit constraints tied to the actual op content.

### Likelihood Explanation
- Preconditions: attacker needs (a) the ability to generate an unprivileged Groth16 proof for `MainEVMCircuitMin` (trivial — they just pick any `messageSeed`), (b) `erc20TokenAddresses.length == 0` in `circomData` to force the Min path, (c) an `EmporiumUpgradeable` contract that currently holds some parked balance (which naturally accumulates from normal Emporium usage where `Hinkal._externalTransact` pushes tokens to Emporium before/around `runAction`), and (d) `stack.signerAddress == address(0)` to skip signature verification.
- Cost: negligible — only gas plus one lightweight proof generation.
- Repeatability: bounded to one drain per distinct `emporiumMessage` (enforced by `usedMessages`), but the attacker can generate arbitrarily many new messages/proofs at will, so the attack is fully repeatable until Emporium's balance is exhausted.
- No privileged role, relay, or victim cooperation required — fully unprivileged.

### Recommendation
- In `MainEVMCircuitMin`, actually constrain `calldataHash` and `outTimeStamp` (e.g., include them in a hash/commitment constraint tied to `message`/`messageSeed`, or remove the Min-path shortcut entirely) so the proof is cryptographically bound to the exact `circomData` submitted.
- Do not allow the Min path to be used for any `externalActionId` that can invoke arbitrary external calls (`EmporiumUpgradeable.runAction`); require the full `formInputNormal` circuit (which binds `getSignedMessageHash` over the entire calldata, including `externalActionData`) whenever `externalActionId != 0`.
- In `EmporiumUpgradeable.verifyWallet`, do not skip signature verification when `signerAddress == address(0)`; require an explicit, circuit- or Hinkal-verified authorization path for "stateless" ops instead of an unconditional bypass.
- Make `runAction`'s balance/UTXO accounting independent of attacker-supplied `erc20TokenAddresses` length — e.g., derive the token set that must be balance-checked from what the ops actually touch, or forbid `erc20TokenAddresses.length == 0` combined with non-empty `ops`.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, `VerifierFacade` with the real Min verifier for `MainEVMCircuitMin`, and `EmporiumUpgradeable` registered as `HINKAL_EMPORIUM_ACTION_ID`'s external action.
2. Fund `EmporiumUpgradeable` with e.g. 1000 USDC (simulate a parked in-flight balance, e.g. by performing a legitimate normal-path Emporium op that leaves residual balance, or by directly minting/transferring for test simplicity).
3. Off-chain: pick `messageSeed`, compute `message = Poseidon(messageSeed)`, generate a valid Groth16 proof `(a,b,c)` for `MainEVMCircuitMin` with arbitrary `calldataHash`/`timeStamp` witness values.
4. Build `circomData` with `erc20TokenAddresses = []`, `amountChanges = []`, `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `externalActionData.externalActionMetadata = abi.encode(EmporiumStack({signerAddress: address(0), ops: [EmporiumOperation({endpoint: USDC, invokeWallet: false, value: 0, callData: abi.encodeCall(IERC20.transfer, (attacker, 1000e6))})], maxFee: 0, deadline: type(uint256).max, v:0, r:0, s:0}))`, `emporiumMessage = message`, `calldataHash = getHashedCalldata(circomData)` (computed to be self-consistent).
5. Call `Hinkal.transact(a, b, c, dimensions, circomData)` from an attacker EOA.
6. Assert: `verifyProof` succeeds (proof verifies despite `calldataHash` differing from what was originally in the witness), `runAction` executes the injected `transfer` call, USDC balance of Emporium goes from 1000e6 to 0, attacker's USDC balance increases by 1000e6, and no `require`/revert fires anywhere in the call path — confirming assets moved (`balanceChange`) with zero entries accounted in `balancesBefore`/`balancesAfter` (both empty arrays), proving the equality "assets Emporium can move == assets accounted" is broken.
