Webhook shop identity is unauthenticated — `Registry.process` binds `WebhookMetadata#shop` solely to the unauthenticated `shop-domain` header, with no binding to the `Registration` or any `Session` - ([File: lib/shopify_api/webhooks/registry.rb])

### Summary
`Registry.process` validates only that the HMAC of the raw request body matches a value computed from `Context.api_secret_key`; it never validates or binds the `shop-domain` header to that HMAC or to the `Registration` that was set up for the topic. As a result, the `shop` value delivered to the webhook handler in `WebhookMetadata` is fully attacker-controllable header data, decoupled from the body's actual origin.

### Finding Description
The claimed binding — `shop bound to Registration/endpoint at registration time == shop delivered in WebhookMetadata at process time` — does not exist anywhere in this code path.

- `add_registration` (`lib/shopify_api/webhooks/registry.rb:25-45`) stores a `Registration` keyed only by `topic` (`path`, `handler`, `fields`, etc.) — it has no concept of "shop" at all.
- `register` (`lib/shopify_api/webhooks/registry.rb:58-86`) uses a `Session` to talk to a specific shop's Admin API to create the subscription, but that shop identity is never persisted onto the `Registration` object or anywhere the `Registry` can later consult.
- `process` (`lib/shopify_api/webhooks/registry.rb:189-200`):
  ```ruby
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))
  ```
  Both `topic` and `shop` come from `Request` (`lib/shopify_api/webhooks/request.rb:16-23`), which reads them directly from HTTP headers (`shopify-topic`, `shopify-shop-domain`) with no authentication.
- `HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:13-31`) computes `OpenSSL::HMAC.hexdigest(sha256, secret, verifiable_query.to_signable_string)`, and `Request#to_signable_string` (`lib/shopify_api/webhooks/request.rb:36-38`) returns only `@raw_body`. Headers — including `shop-domain` and `topic` — are excluded from the signed content entirely.

Because the `api_secret_key` (a single per-app secret) signs only the body, any request bearing a body+HMAC pair that was validly signed for one shop remains HMAC-valid regardless of what `shop-domain` header accompanies it. The gem performs no secondary check that the declared shop is consistent with anything established during registration.

Existing guards do not close this gap: `HmacValidator.validate` authenticates body integrity/origin only, not header integrity; `ShopValidator.sanitize!`, `state` comparisons, and JWT `aud` checks are unrelated to this code path (they apply to OAuth/session tokens, not webhook delivery); `Context.setup?`/`private?`/`embedded?` and Sorbet runtime typing enforce types, not authenticity of header content.

### Impact Explanation
Any handler logic that trusts `WebhookMetadata#shop` as an authenticated tenant identifier (e.g., mandatory GDPR topics `shop/redact`, `customers/redact`, `customers/data_request`, or any app logic keyed by shop to fetch/update/delete tenant data) can be invoked with an attacker-chosen shop value paired with attacker-controlled body content. This is a cross-tenant data-integrity/confusion issue: one tenant's (the attacker's) event can be made to represent another tenant's identity to the application, matching the Critical "cross-tenant access" category defined in the rules.

### Likelihood Explanation
Exploitation requires the attacker to possess at least one validly HMAC-signed `(raw_body, hmac)` pair for the topic — obtainable per the stated threat model by installing the app on their own development shop and receiving their own legitimately signed webhook. No `api_secret_key`, TLS interception, or physical/local access is needed, since the HMAC never covers the `shop-domain` header — only the declared header on replay needs to change. This is repeatable against arbitrary victim shop identifiers for any topic the attacker can obtain a valid signature for.

### Recommendation
Bind the delivered shop identity to something authenticated: either (a) include the shop domain in the HMAC-signed material used to validate the request (not currently possible since Shopify's own signing scheme signs body only — this is a known limitation of the Shopify webhook HMAC scheme itself, not unique to this gem), or (b) have the application layer cross-validate `request.shop` against the shop for which the topic/handler was registered before invoking `handler.handle`, and reject/flag mismatches. At minimum, document that `WebhookMetadata#shop` is unauthenticated header data and must not be trusted as a tenant boundary without additional application-level verification.

```ruby
# test/webhooks/registry_shop_spoof_test.rb
class RegistryShopSpoofTest < Minitest::Test
  def setup
    ShopifyAPI::Context.setup(api_key: "key", api_secret_key: "secret", ...)
    ShopifyAPI::Webhooks::Registry.clear
    @handler = FakeHandler.new
    ShopifyAPI::Webhooks::Registry.add_registration(
      topic: "orders/create", delivery_method: :http, path: "/webhooks", handler: @handler,
    )
  end

  def test_shop_domain_header_is_unauthenticated
    body = '{"id":1}'
    hmac = Base64.encode64(OpenSSL::HMAC.digest("sha256", "secret", body)).strip

    req1 = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: {
      "x-shopify-topic" => "orders/create",
      "x-shopify-hmac-sha256" => hmac,
      "x-shopify-shop-domain" => "attacker-shop.myshopify.com",
      "x-shopify-api-version" => "2023-01",
      "x-shopify-webhook-id" => "1",
    })
    req2 = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: {
      "x-shopify-topic" => "orders/create",
      "x-shopify-hmac-sha256" => hmac,
      "x-shopify-shop-domain" => "victim-shop.myshopify.com",
      "x-shopify-api-version" => "2023-01",
      "x-shopify-webhook-id" => "1",
    })

    ShopifyAPI::Webhooks::Registry.process(req1) # succeeds, shop = attacker-shop
    ShopifyAPI::Webhooks::Registry.process(req2) # succeeds, shop = victim-shop, SAME hmac/body

    assert_equal "attacker-shop.myshopify.com", @handler.received[0].shop
    assert_equal "victim-shop.myshopify.com", @handler.received[1].shop
    # No error raised despite identical signature but conflicting shop claims.
  end
end
```
