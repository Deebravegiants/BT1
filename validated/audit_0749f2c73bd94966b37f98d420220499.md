### Title
Cross-Extrinsic Signature Replay via Shared Nonce Between `withdraw_fees` and `accumulate_fees` Beneficiary Redirect - ([File: modules/pallets/relayer/src/accumulate.rs, modules/pallets/relayer/src/withdrawal.rs])

### Summary
`pallet-relayer` signs two semantically distinct actions — a beneficiary redirect during fee accumulation (`accumulate_fees`) and a full fee withdrawal (`withdraw_fees`) — with message hashes that are byte-for-byte identical for the same `(nonce, state_machine, beneficiary)` tuple, while both actions consume the *same* per-`(address, chain)` `Nonce` counter. A signature a relayer produces for one action is therefore also a valid signature for the other, exactly mirroring the CoreWallet co-signer replay pattern where a nonce not scoped to the specific action/role lets a signed message be replayed under a different context.

### Finding Description
`withdrawal.rs::message` and `accumulate.rs::beneficiary_message` both hash `(nonce, state_machine, beneficiary_bytes).encode()`: [1](#0-0) [2](#0-1) 

Because `Vec<u8>` and `&[u8]` SCALE-encode identically, and both functions hash `(u64, StateMachine, bytes)` in the same order, `message(n, chain, Some(b))` and `beneficiary_message(n, chain, &b)` produce the exact same `keccak_256` digest for equal inputs.

Both consuming code paths read and increment the *same* `Nonce<T>` storage entry keyed by `(address, chain)`:
- `withdraw()` reads `Nonce::<T>::get(address.clone(), dest_chain)` and increments it after verifying `message(...)`. [3](#0-2) 
- `accumulate()`'s beneficiary-redirect branch reads `Nonce::<T>::get(&delivery_address, state_machine)` and increments the same storage entry after verifying `beneficiary_message(...)`. [4](#0-3) 

Both `withdraw_fees` and `claim/accumulate_fees` are unsigned, permissionless extrinsics whose validity is derived purely from the embedded signature and current on-chain nonce, submittable by anyone who observes the signature (e.g., in the mempool or a previous transaction) — there is no binding of the signature to the specific call it was meant for.

### Impact Explanation
A relayer who signs a beneficiary-redirect message for `accumulate_fees` (intending to redirect a specific batch's proven fee to beneficiary `B`) produces a signature that is *also* valid input for `withdraw_fees` at the same nonce, chain, and beneficiary. Any unprivileged party can capture that signature and submit it via `withdraw_fees` before the relayer's intended `accumulate_fees` call lands. Because `withdraw()` disburses the *entire* currently accumulated `Fees[chain][address]` balance (not scoped to the batch the relayer meant to authorize) via a real cross-chain ISMP POST request, this forces a premature/unintended withdrawal of the relayer's whole fee balance to `B`, and advances the shared nonce so the relayer's original, intended `accumulate_fees` call is invalidated (its nonce is now stale), causing loss of control over fee timing and potential loss/misdirection of pending fee amounts. This is an unauthorized app action / unintended fund movement reachable via a plain submitted transaction, without any privileged or malicious-insider access.

### Likelihood Explanation
Both extrinsics are unsigned and permissionless; anyone observing a relayer's broadcast signature (which must be submitted on-chain to take effect, and unsigned extrinsics are visible in the transaction pool before inclusion) can replay it in the alternate extrinsic. No special access or timing is required beyond normal chain observation, making exploitation realistic for any relayer that uses the beneficiary-redirect feature.

### Recommendation
Domain-separate the two signed payloads, e.g. by including a distinct action tag/discriminant (such as a fixed prefix like `b"WITHDRAW"` vs `b"ACCUMULATE_REDIRECT"`) in the hashed tuple, or use disjoint nonce counters per action type, so a signature produced for one extrinsic can never be replayed as valid input to the other — following the same principle used in the cited CoreWallet fix of binding the signature uniquely to its intended context.

### Proof of Concept
1. Relayer signs `beneficiary_message(nonce=N, chain=X, beneficiary=B)` intending to call `accumulate_fees` with `beneficiary_details = Some((B, sig))`.
2. Attacker (or any observer) intercepts `sig` before the relayer's `accumulate_fees` transaction is included.
3. Attacker submits `withdraw_fees(WithdrawalInputData { signature: sig, dest_chain: X, beneficiary: Some(B) })`.
4. `withdraw()` computes `message(nonce=N, X, Some(B))`, which hashes identically to the relayer's `beneficiary_message`, so the signature verifies successfully.
5. `withdraw()` dispatches a real cross-chain payout of the relayer's full `Fees[X][address]` balance to `B` and increments `Nonce[address][X]`, invalidating the relayer's original `accumulate_fees` signature and forcing an unintended withdrawal timing/amount.
