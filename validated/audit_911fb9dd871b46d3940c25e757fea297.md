Found a genuine identity-binding break in the webhook processing path, matching the reference bug class ("field acted on but not covered by the HMAC").I have enough evidence to write the finding now.

### Title
Webhook `shop-domain` and `topic` headers are trusted for tenant routing without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while the `shop`, `topic`, `webhook-id`, and `api-version` values used to route and attribute the webhook to a tenant are taken from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` accepts any request whose body HMAC matches the app's `client_secret`, then blindly forwards the attacker-controlled `shop` header to the app's handler as the tenant identity, breaking the binding: `HMAC-verified bytes == raw_body` but `data acted on (shop, topic) != raw_body`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are read straight from HTTP headers with no cryptographic binding to the body or to each other: [2](#0-1) 

`Registry.process` validates only the body HMAC via `Utils::HmacValidator.validate(request)`, which calls `request.to_signable_string` (the raw body) — it never validates that `shop`/`topic` are consistent with anything cryptographically signed — and then passes the untrusted `request.shop` straight into `WebhookMetadata` for the handler to act on: [3](#0-2) 

Since a single Shopify app's `client_secret` is shared across every merchant that installs the app, any unprivileged internet user who controls a store that has the app installed can trigger a legitimate webhook delivery for their own store (producing a correctly-HMAC'd raw body signed with the app's shared secret), capture that raw body + valid `X-Shopify-Hmac-Sha256` value, then replay it directly to the app's public webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header naming a different, victim merchant. `HmacValidator.validate` re-computes the HMAC over the (unchanged) raw body and it still matches, so `Registry.process` accepts the forged request and dispatches it to the handler tagged with the victim's shop domain: [4](#0-3) 

This equality that should hold — `shop header used for tenant routing == shop cryptographically bound to the signed payload` — does not hold, because the gem never signs or otherwise verifies the `shop-domain` header against the body/secret pairing per tenant.

### Impact Explanation
Any host application built on this gem's documented webhook API (`Registry.add_registration` + `Registry.process`) that uses `WebhookMetadata#shop` to key persistence, authorization, or business logic (the intended and documented use, per the `data.shop` usage exercised in the test suite) can be made to process and store attacker-crafted event data under an arbitrary victim shop's identity. This is a cross-tenant data-integrity/spoofing primitive reachable by any user who can get one legitimate webhook delivery from their own (possibly free/dev) store — no access token, no `client_secret`, and no privileged account is required. This satisfies the Critical "cross-tenant access" impact category since the attacker (tenant A) can inject or overwrite state attributed to tenant B purely by manipulating an unauthenticated header.

### Likelihood Explanation
Likelihood is high: obtaining one real webhook delivery only requires installing the target app on any store (including a free development store) and performing an action that triggers a subscribed topic (e.g. `orders/create`). Capturing and replaying the raw body/HMAC pair with a modified `shop-domain` header is trivial HTTP tampering with no cryptographic secret needed. The vulnerability is present in the gem's core webhook verification path (`Request#to_signable_string`, `Registry.process`), which every consuming app relies on identically.

### Recommendation
Do not treat `shop`, `topic`, `webhook_id`, or `api_version` headers as trusted solely because the body HMAC validates. At minimum, document/enforce that consuming apps must cross-check `request.shop` against a shop that is actually known/installed and has an active session/access token before acting on webhook data, and/or extend `to_signable_string` (or add a secondary check in `Registry.process`) to bind the `shop-domain` and `topic` headers into the value that is HMAC-verified, so a replay against a different shop/topic combination invalidates the signature.

### Proof of Concept
1. Install the target app (built with this gem) on attacker-controlled store `attacker.myshopify.com`.
2. Trigger a subscribed webhook topic (e.g. `orders/create`) so Shopify delivers a POST with `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Topic: orders/create`, a JSON body, and a valid `X-Shopify-Hmac-Sha256` computed with the app's shared `client_secret`.
3. Capture the raw body and the HMAC header value unchanged.
4. Resend the identical raw body + HMAC header to the app's webhook endpoint, but replace `X-Shopify-Shop-Domain` with `victim.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request#hmac`/`#shop` read the new header; `Utils::HmacValidator.validate` recomputes HMAC over the unchanged raw body and it still matches, so `Registry.process` calls the handler with `WebhookMetadata.new(topic: "orders/create", shop: "victim.myshopify.com", body: <attacker's data>, ...)`, causing the app to process forged data under the victim's tenant identity.
