### Title
Webhook `shop` (and `topic`/`api-version`/`webhook-id`) Headers Are Not Covered By The HMAC, Enabling Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` reads the identifying tenant field `shop` straight from an unauthenticated HTTP header, while `HmacValidator` only signs/verifies the raw request body. `Registry.process` trusts this unauthenticated `shop` value and hands it to the host application's webhook handler as `WebhookMetadata#shop`, breaking the equality that should hold between "the shop the HMAC actually attests to" and "the shop the library reports to the handler."

### Finding Description
`Request#to_signable_string` returns only `@raw_body`, and `Request#shop`/`#topic`/`#api_version`/`#webhook_id` are pulled from headers that are never included in that signable string: [1](#0-0) 

`HmacValidator.validate` computes the HMAC only over `verifiable_query.to_signable_string` (i.e., the raw body) and compares it against the `hmac-sha256` header: [2](#0-1) 

`Registry.process` gates only on that body HMAC, then immediately builds `WebhookMetadata` using `request.shop` — an unauthenticated header — and forwards it to the app's handler as the tenant identity: [3](#0-2) [4](#0-3) 

The broken identity binding, as an equality:
- Expected: `shop_bound_by_hmac == shop_delivered_to_handler`
- Actual: `hmac` binds only `raw_body`; `shop_delivered_to_handler = header["x-shopify-shop-domain"]`, which is fully attacker-controlled and independent of the signed bytes.

Because a public app uses a single `api_secret_key` (`Context.api_secret_key`) shared across every shop that installs it, any principal who can install the app on their *own* shop can legitimately receive a webhook with a valid `(raw_body, hmac)` pair. That exact body+HMAC pair remains valid under `HmacValidator.validate` no matter what `x-shopify-shop-domain` (or `x-shopify-topic`, `x-shopify-webhook-id`) header is attached, since none of those headers are part of the signed content.

### Impact Explanation
An attacker who has installed the app on any shop (including a free/trial one they control) can capture one legitimate webhook delivery (valid body + HMAC) and replay it to the app's webhook endpoint with the `x-shopify-shop-domain` header swapped to a victim's shop domain. `Registry.process` will validate the HMAC (it only checks the body) and dispatch the handler with `WebhookMetadata#shop` set to the victim's domain and attacker-chosen `body`/`topic`/`webhook_id`. Any host application that uses `data.shop` to route/attribute data (e.g., updating that shop's local order/customer/inventory records, as the API is explicitly designed for) will process attacker-supplied data as if it originated from the victim tenant — a cross-tenant data-integrity/confidentiality breach mediated entirely through this gem's webhook verification primitive.

### Likelihood Explanation
The prerequisite is only the ability to install the target public app on an attacker-controlled shop (the normal, unprivileged installation flow) and to capture/replay HTTP requests — no access to `api_secret_key`, access tokens, or privileged accounts is required. The replay technique is generic (any HTTP client) and the gem provides no shop-binding safeguard for callers to opt into, since `Request`/`Registry` expose no mechanism to cross-check the header `shop` against anything cryptographically tied to it.

### Recommendation
Bind the tenant-identifying fields into the verified material, or explicitly document/enforce that `shop`/`topic`/`webhook_id` headers are untrusted until the shop is otherwise validated (e.g., cross-checked against a known/installed-shop list, or a session lookup) before being handed to `WebhookHandler#handle`. At minimum, `Registry.process` should not implicitly present `request.shop` as trustworthy metadata; it should require callers to validate that the target shop expected the given `webhook_id`/topic combination.

### Proof of Concept
1. Attacker installs the target public app on `attacker.myshopify.com`, receiving a legitimate webhook request:
   - Body: `{"id":1,"note":"hello"}`
   - Header `x-shopify-hmac-sha256: <valid HMAC of body>`
   - Header `x-shopify-shop-domain: attacker.myshopify.com`
2. Attacker resends the identical body and HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` [5](#0-4)  which passes because the body/HMAC pair is untouched.
4. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: {"id":1,"note":"hello"}, ...)` [6](#0-5)  and the host app processes attacker-controlled content as authentic data for `victim-shop.myshopify.com`.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
