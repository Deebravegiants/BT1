### Title
Webhook `shop` (tenant identifier) is not covered by the HMAC signature, allowing cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` (tenant identifier) delivered to the application's webhook handler solely from the unauthenticated `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, while the HMAC signature verified by `ShopifyAPI::Utils::HmacValidator` only covers the raw request body. This breaks the intended binding `shop_verified_by_HMAC == shop_acted_on`.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` validates a webhook request by checking only that the HMAC over the raw body is correct: [1](#0-0) 

The HMAC is computed and verified against `to_signable_string`, which for `Request` returns exclusively `@raw_body`: [2](#0-1) 

However, the `shop` attribute that is exposed to the consuming application (and used to attribute the event to a tenant) is read directly from the `shop-domain` header, which is never included in the signed payload: [3](#0-2) [4](#0-3) 

After a successful HMAC check on the body, `Registry.process` forwards this unauthenticated `request.shop` value straight into `WebhookMetadata`, which is the trusted object handed to the app's `WebhookHandler#handle`: [1](#0-0) [5](#0-4) 

Because the gem's own HMAC secret (`Context.api_secret_key`) is shared across every shop that has installed the app (it is not a per-shop key), any attacker who can obtain one genuine, correctly-HMAC'd webhook delivery for **their own** installed shop (e.g. by installing the app on a shop they control and triggering a webhook, or from a `shop/redact`/`customers/redact` mandatory webhook they receive) possesses a `(raw_body, hmac)` pair that will pass `HmacValidator.validate`. Since the header `shop-domain` is outside the signed content, the attacker can replay that exact body+HMAC while substituting the `shop-domain` header for a victim shop that also uses the same app. `Registry.process` will pass this HMAC check and deliver a `WebhookMetadata` object whose `shop` field is the attacker-chosen victim domain, with body content also attacker-controlled to the extent it stays byte-identical to a valid signed payload (e.g., an attacker can trivially get Shopify to sign whatever body they choose for their own shop, since they control the events on their own store — e.g. product/order data, or even trigger `shop/redact`/`app/uninstalled`-style events on their own shop and replay them against a victim's shop identifier).

This matches the analog pattern of "a field acted on but not covered by the HMAC": the code path proves the *body* integrity, then trusts an entirely separate, unauthenticated field (`shop`) as if it had been part of the same trust boundary.

### Impact Explanation
This breaks tenant isolation for any application relying on `WebhookMetadata#shop` from this gem to route or authorize per-merchant actions (a pattern the gem itself documents/exercises, e.g. `handler.handle(data: WebhookMetadata.new(... shop: request.shop ...))`). An attacker who legitimately installed the app on one store can forge webhook deliveries that appear to originate from a different merchant's store, since the tenant-identifying field is never authenticated. Depending on how the host application uses `data.shop` (e.g., looking up and acting on a specific merchant's session/data, processing GDPR `shop/redact` or `customers/redact` requests, or triggering data mutations keyed by shop), this enables cross-tenant data manipulation — matching the High/Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires the attacker to have their own valid app installation (a normal, unprivileged capability for any merchant/developer installing a public app) and knowledge of the target's shop domain (public information, `*.myshopify.com`). No access to the app's `client_secret` or another merchant's access token is required — the only credential involved is the attacker's own legitimate webhook delivery, which is not treated as privileged. This is a design property of every consumer of this gem's `Webhooks::Request`/`Registry`, not a host-application misuse, since the gem itself defines `shop` as an unauthenticated header read.

### Recommendation
- Do not treat `Request#shop` (or any other webhook header) as a verified/trusted identifier by itself; document clearly that only the raw body is HMAC-protected.
- Where feasible, bind the shop identifier into the verified content, e.g., by including `shop-domain` in the signable string (mirroring `Auth::Oauth::AuthQuery#to_signable_string`, which does include `shop`) or by requiring callers to independently correlate `request.shop` against a known, previously-established session/shop record before trusting it.
- At minimum, surface a strong warning in `WebhookMetadata`/`WebhookHandler` documentation that `shop` is unauthenticated and must be cross-checked against the application's own shop registry before being used for any tenant-scoped action.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com` and on `victim-shop.myshopify.com`, both delivering webhooks signed with the same app `client_secret`.
2. Attacker triggers/receives a legitimate webhook for their own shop, capturing `raw_body` and the valid `X-Shopify-Hmac-Sha256` value that Shopify computed over that body.
3. Attacker replays an HTTP request to the app's webhook endpoint with the identical `raw_body` and `hmac` header, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` accepts the headers (all three required headers present) and `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes/compares HMAC over `@raw_body` — this succeeds because the body is unchanged. [6](#0-5) 
5. The handler is invoked with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, even though Shopify never issued a webhook for that shop with this content — demonstrating that the shop attribution is forgeable independent of the HMAC.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
