### Title
Orb Backend Auth Token Leaked via Debug Logging of HTTP Requests - ([File: src/backend/signup_poll.rs], [File: src/backend/signup_post.rs], [File: src/backend/presigned_url.rs], [File: src/backend/s3_region.rs])

### Summary
Multiple backend request helpers attach the Orb's backend bearer credential via `basic_auth(&*ORB_ID, Some(get_orb_token()?))` and then immediately log the entire `reqwest::Request` object with `tracing::debug!("Sending request {:#?}", request)`. Because `reqwest`'s `Debug` implementation for a `Request` prints its headers, and HTTP `Basic` auth values are base64-encoded, printable-ASCII strings, the `Authorization: Basic <base64(orb_id:token)>` header is rendered in full, plaintext-decodable form in the log output — directly analogous to the reported "API key type/allowed types logged on every auth check" and "full connection URI with credentials logged" issue.

### Finding Description
`get_orb_token()` returns the short-lived (or fallback static) bearer token used to authenticate the Orb to the backend, stored in `ORB_TOKEN` [1](#0-0) . This token is attached via `.basic_auth(&*ORB_ID, Some(get_orb_token()?))` in every backend call (signup creation, signup polling, S3 region lookup, presigned URL/package requests, operator/user status checks, config, orb OS status) [2](#0-1) [3](#0-2) [4](#0-3) .

Several of these call sites then debug-log the built `Request` (or its `{:#?}` pretty-print), which includes headers:
- `src/backend/signup_poll.rs`: `tracing::debug!("Sending request {:#?}", request);` right after attaching `basic_auth` [5](#0-4) .
- `src/backend/signup_post.rs`: the multipart-built request is logged with `tracing::debug!("Sending request {:#?} with size: {:?}", request, request_size);` [6](#0-5) .
- `src/backend/s3_region.rs`: `tracing::debug!("Sending request {:#?}", request);` [7](#0-6) .
- `src/backend/presigned_url.rs`: identical pattern repeated across `request`, `request_package`, and `request_tiered_package` [8](#0-7) [9](#0-8) [10](#0-9) .

None of these logging call sites redact the `Authorization` header before printing the request, so the Orb's backend credential (base64 of `ORB_ID:token`) ends up in whatever log sink orb-core writes to (journald / Datadog via the existing `dd_*!` macros used throughout the same files).

### Impact Explanation
If `debug` level tracing is enabled in the field (a common scenario for troubleshooting deployed Orbs, and the codebase provides no evidence of a level filter suppressing `debug` in the shipped binary at `src/bin/orb-core.rs:36`, `logger::init::<false>()`), the Orb's backend bearer token is written into logs that flow to log aggregation/observability systems. Anyone with read access to those logs (compromised log pipeline, third-party SIEM export, or an internal engineer with log-only access) could extract the token and impersonate the Orb against the signup/management backend — creating or manipulating signups, fetching presigned upload URLs, or querying operator/user status under the Orb's identity. This mirrors the reported bug class (credential/token leaked in application logs) but applied to the Orb's own backend authentication token rather than an external API key or DB URI.

### Likelihood Explanation
Likelihood is moderate: it requires `debug`-level tracing to be enabled at runtime and an attacker/insider with access to the resulting log stream. I could not confirm from the available code whether the shipped production binary configures a log-level filter that excludes `debug` (no `EnvFilter`/`RUST_LOG` gating was found for `logger::init`), so it's plausible this code path is reachable in production troubleshooting builds or via a log-level environment override.

### Recommendation
- Redact the `Authorization` header (and any other sensitive headers) before logging `Request`/`Response` objects, or replace `tracing::debug!("... {:#?}", request)` with logging of only non-sensitive fields (method, URL path, content-length).
- Audit all `tracing::debug!`/`tracing::error!` call sites in `src/backend/*` that print `request`/`response` via `{:#?}` for header leakage.
- Confirm and enforce that production builds cannot be run with `debug`-level tracing enabled for these modules, or explicitly `tracing::field::debug` with a custom `Debug` wrapper that scrubs the `Authorization` header.

### Proof of Concept
1. Enable debug-level tracing output on a deployed Orb (or a build where the log filter permits `debug`).
2. Trigger any backend call that builds a request with `.basic_auth(&*ORB_ID, Some(get_orb_token()?))` followed by a `tracing::debug!("Sending request {:#?}", request)` — e.g. `S3 region lookup` [11](#0-10)  or `signup polling` [12](#0-11) .
3. Observe the log line contains the full `Authorization: Basic <base64>` header; base64-decode to recover `ORB_ID:token`.
4. Use the recovered credential to make authenticated backend requests as the Orb.
