### Title
Pool `repay`/`recapitalize` refund the declared excess out of custody, not the measured received excess — (File: contracts/pool/src/ops/repay.rs)

### Summary
The external report's bug class is "caller sends more than required, the excess is kept." XOXNO Lending's analog is the mirror image with the same root cause — the refund amount is derived from the *declared* inbound amount, not the measured token receipt. In `pool::repay` and `pool::recapitalize`, `overpayment`/`refund = amount - applied` is computed purely from the `amount` argument the controller passes, then paid out of the pool's real token balance without debiting `cash` or checking custody. If fewer tokens actually arrived than `amount` declares (fee-on-transfer asset, or any gap between declared and received), the pool refunds tokens it never received — the excess is "refunded" out of other suppliers' funds.

### Finding Description
`ops::repay::accounting` resolves `action.amount` into `net_repay` + `overpayment` via `cache.resolve_repay`, credits only `net_repay` to cash, and `apply` then calls `cache.transfer_out(payer, overpayment)`. Neither the credit nor the refund is bound to the pool's actual token-balance delta. The pool's own test suite proves the gap: `test_unfunded_repay_overpayment_refund_also_pays_out_of_custody` calls `repay` with nothing transferred in and zero debt, and the entire declared `amount` is refunded out of real custody with the book untouched. The same shape exists in `ops::recapitalize::accounting`: `applied = amount.min(backing_shortfall)`, `refund = amount - applied`, then `transfer_out(&payer, refund)` — again with no custody check on the refund leg.

In production the pool is `#[only_owner]`-gated to the controller, so reachability comes through the controller entrypoints `repay` and `recapitalize`, both of which are unprivileged. The controller transfers `amount` in before the call; for a standard token the amounts match, but for a fee-on-transfer hub asset the pool receives `amount - fee` while the refund is still computed on the full declared `amount`. The liquidator/borrower is therefore refunded `fee` worth of tokens that came from supplier custody. The liquidation path already demonstrates awareness of this hazard — `a_fee_on_transfer_band_full_close_retires_the_debt_and_refunds_the_received_excess` pins refund = *received* − debt — but `repay` and `recapitalize` compute the refund from the declared amount inside the pool with no received-balance input.

### Impact Explanation
Theft of user funds: each over-repaying or over-recapitalizing call on a fee-on-transfer (or otherwise receipt-discounted) market extracts the fee-on-the-excess portion from pool custody that belongs to suppliers. Repeated calls scale linearly. Where the discount is large relative to the excess, the refund pays out tokens entirely unbacked by any inbound transfer, draining `cash`'s real balance while the book still shows it intact — a silent custody/book divergence that socializes onto withdrawers and revenue claims.

### Likelihood Explanation
Requires a market whose hub asset taxes or rebates transfers, or any future path where the controller's declared `amount` exceeds actual receipt. The codebase already supports and tests fee-on-transfer assets (`with_fee_on_transfer_market`), so the precondition is realistic rather than hypothetical. Any unprivileged user can trigger it via `repay` (overpay their own debt) or `recapitalize` on an affected market.

### Recommendation
Measure the refund against the actual pool token-balance delta: capture the balance before the inbound transfer and cap `overpayment`/`refund` at `received - applied` (or equivalently pass the measured received amount into `repay`/`recapitalize` instead of the declared `amount`). Alternatively debit the refund from `cash`/`require_reserves` so an unfunded refund cannot pay out of custody silently — matching the received-based refund already enforced on the liquidation path.

### Proof of Concept
1. Register a fee-on-transfer market (e.g., 10% burn, as in `with_fee_on_transfer_market`) and seed supplier liquidity so custody > 0 with zero debt.
2. Alice calls controller `repay` (or `recapitalize`) declaring `amount = X` where `X` exceeds her debt (or the backing shortfall) by `E`.
3. Pool receives `0.9X` but `resolve_repay`/`accounting` computes `overpayment = E` on the declared basis and executes `transfer_out(payer, E)` — paying `0.1·X` more than the true received excess, drawn from supplier custody.
4. Repeat; each call drains the transfer-tax fraction of the excess from the pool while `cash` remains untouched, as pinned by `contracts/pool/tests/flows.rs:3590` (`test_unfunded_repay_overpayment_refund_also_pays_out_of_custody`). [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) 

Note on uncertainty: I could not fully verify within the available iterations whether the controller re-measures the inbound balance delta before passing `amount` to `pool::repay`/`recapitalize` for fee-on-transfer assets (the strategy leg uses `refund_controller_balance_delta`, suggesting measurement exists on some paths). If the controller already clamps `amount` to the received delta on the repay/recapitalize legs, the drain vector collapses to the documented-but-unfunded refund behavior shown in the pool test, and this finding should be downgraded or rejected accordingly.

pub(crate) fn accounting(
    env: &Env,
    hub_asset: HubAssetKey,
    amount: i128,
) -> RecapitalizationOutcome {
    require_nonneg_amount(env, amount);
    let mut cache = ops::renewed_market(env, &hub_asset);

    let applied = amount.min(guards::backing_shortfall(&cache));
    let refund = amount
        .checked_sub(applied)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow));

    cache.credit_cash(applied);
    cache.commit();
```

/// The refund gap is not specific to `recapitalize`. Two pool legs refund an
/// excess derived from a declared inbound amount, not from the cash book:
/// `ops::recapitalize::apply` (the excess over the shortfall) and
/// `ops::repay::apply` (the excess over the debt). Neither refund debits `cash`
/// or passes `require_reserves`.
///
/// A repay against a market with no debt makes the entire declared amount an
/// overpayment: `current_debt_ceil` is zero, so `resolve_repay` takes the
/// full-close branch and `net_repay` is zero. The `RepayRoundsToZeroShares`
/// assert in `ops::repay::accounting` passes on its `net_repay == 0` disjunct,
/// and the whole amount is refunded out of real custody with the book untouched.
#[test]
fn test_unfunded_repay_overpayment_refund_also_pays_out_of_custody() {
    let t = TestSetup::new();
    let token = token::Client::new(&t.env, &t.asset);
    let payer = Address::generate(&t.env);

    let custody_before = token.balance(&t.pool);
    let before = t.state_snapshot();
    assert_eq!(
        before.cash, custody_before,
        "fixture guard: book and custody must start in sync"
    );
    assert_eq!(before.borrowed, 0, "fixture must carry no debt");

    // Nothing transferred in, no debt to retire: the whole amount is "excess".
    let credited = t
        .client()
        .repay(&payer, &t.ract(0, custody_before))
        .get_unchecked(0)
        .actual_amount;
    assert_eq!(credited, 0, "no debt was retired, so nothing is credited");
    assert_unfunded_refund_drained_custody(&t, &payer, custody_before, &before);
```
