Audit Report

## Title
Confidential Relay Gateway Handler Matches Node Responses to Active Requests by ID Only, Without Verifying Method — Cross-Request/Method Confusion - ([File: core/services/gateway/handlers/confidentialrelay/handler.go])

## Summary
`HandleNodeMessage` in `core/services/gateway/handlers/confidentialrelay/handler.go` resolves a node's response to a pending client request purely by the client-controlled JSON-RPC `ID`, without ever verifying that `resp.Method` matches `ar.req.Method`. Because `ID` is freed and freely reusable the instant a prior request with that ID completes, a stale/delayed response belonging to an old request can be silently merged into a newer, unrelated request of a different method and workflow/execution identity.

## Finding Description
`activeRequest`s are stored in `h.activeRequests`, keyed solely by the caller-supplied `req.ID`, validated only for non-emptiness and a 200-character bound in `HandleJSONRPCUserMessage`/`newActiveRequest` [5](#0-4) . On completion, the entry is deleted under lock in `sendResponseAndClearRequest`, freeing the ID for immediate reuse [6](#0-5) . `HandleNodeMessage` looks up the active request purely by `resp.ID` [2](#0-1)  and immediately merges the response into whatever request currently occupies that slot, feeding it to `bundler.Bundle(ar.req, ...)`, which decodes strictly by `ar.req.Method` [3](#0-2) [7](#0-6) . No comparison of `resp.Method` vs `ar.req.Method` (nor of `ar.labels`) exists anywhere in this file. The sibling `vault` handler, which shares the identical ID-keyed map and lookup structure, explicitly guards against exactly this scenario with a method-match check placed right after the lookup [8](#0-7) . The confidential relay handler is missing this equivalent check.

## Impact Explanation
A stale node response for one completed request (method/workflow A) can be attributed to a new, unrelated request (method/workflow B) that reused the same client-chosen ID after A completed and freed its slot. This corrupts the bundle passed to the enclave and misattributes per-node signed payloads across execution/workflow boundaries, a cross-user/cross-request response corruption consistent with in-scope gateway impact classes.

## Likelihood Explanation
Fully reachable by an unprivileged client: `ID` is caller-supplied, and slot reuse after completion is normal, frequent behavior. No malicious node action is required — an ordinary slow or retried node response for a freed ID is sufficient to trigger the confusion; only timing (winning the race between the old ID freeing and the late response arriving) is a precondition, which is realistic in a distributed system with node-level retries/latency.

## Recommendation
In `HandleNodeMessage` (confidentialrelay/handler.go), reject/drop responses whose `resp.Method` does not equal `ar.req.Method`, mirroring the existing check in `core/services/gateway/handlers/vault/handler.go`. Additionally, consider keying `activeRequests` by `(ID, Method)` or embedding a gateway-generated generation counter/nonce in the map key so a stale response from a prior generation of an ID can never be attributed to a newer, unrelated request.

## Proof of Concept
1. Client submits request A: `{"id": "X", "method": "wf_secretsGet", ...}` for workflow W1; gateway registers `activeRequests["X"]` with `req.Method = MethodSecretsGet`, `labels = {WorkflowID: W1}`.
2. Node N is slow to respond; A reaches quorum from other nodes and completes; `sendResponseAndClearRequest` deletes `activeRequests["X"]`.
3. A new request B reuses `id = "X"` with `method = "wf_capabilityExec"` for workflow W2; `newActiveRequest` succeeds since the slot is free; `activeRequests["X"]` now holds B's `req`/`labels`.
4. Node N's delayed response for A (`SignedSecretsResponseResult`, method `wf_secretsGet`, ID `"X"`) arrives at `HandleNodeMessage`.
5. `getActiveRequest("X")` returns B's `activeRequest`; no method check rejects the mismatch; the stale response is merged into B's `responses` and passed to `bundler.Bundle(ar.req, ...)` with `ar.req.Method == MethodCapabilityExec`, demonstrating the type/identity confusion between two unrelated, differently-typed requests sharing a reused ID.

func (h *handler) HandleJSONRPCUserMessage(ctx context.Context, req jsonrpc.Request[json.RawMessage], callback gwhandlers.Callback) error {

func (h *handler) newActiveRequest(req jsonrpc.Request[json.RawMessage], labels requestLabels, callback gwhandlers.Callback) (*activeRequest, error) {
	h.mu.Lock()
	defer h.mu.Unlock()
	if h.activeRequests[req.ID] != nil {
		h.lggr.Errorw("request id already exists", "requestID", req.ID, "executionID", labels.ExecutionID)
		return nil, errors.New("request ID already exists: " + req.ID)
	}
	ar := &activeRequest{
		Callback:  callback,
		req:       req,
		labels:    labels,
		createdAt: h.clock.Now(),
		responses: map[string]*jsonrpc.Response[json.RawMessage]{},
	}
	h.activeRequests[req.ID] = ar
	return ar, nil
}

func (h *handler) sendResponseAndClearRequest(ctx context.Context, ar *activeRequest, payload gwhandlers.UserCallbackPayload) error {
	if !ar.completed.CompareAndSwap(false, true) {
		// Another path already answered this request.
		return nil
	}

	sendErr := ar.SendResponse(payload)

	h.mu.Lock()
	delete(h.activeRequests, ar.req.ID)
	h.mu.Unlock()

	if sendErr != nil {
		h.lggr.Errorw("error sending response to user", "requestID", ar.req.ID, "executionID", ar.labels.ExecutionID, "error", sendErr)
		return sendErr
	}

	h.recordMetrics(ctx, payload.ErrorCode)
	h.lggr.Debugw("response sent to user", "requestID", ar.req.ID, "executionID", ar.labels.ExecutionID, "errorCode", payload.ErrorCode)
	return nil
}

func (b *bundler) Bundle(req jsonrpc.Request[json.RawMessage], resps map[string]jsonrpc.Response[json.RawMessage], l logger.Logger) (*BundleSummary, error) {
	summary := newBundleSummary(len(resps))

	switch req.Method {
	case relaytypes.MethodSecretsGet:
		out := make([]relaytypes.SignedSecretsResponseResult, 0, len(resps))
		for nodeAddr, r := range resps {
			if r.Error != nil || r.Result == nil {
				summary.addError(nodeAddr, r.Error)
				continue
			}
			var signed relaytypes.SignedSecretsResponseResult
			if err := json.Unmarshal(*r.Result, &signed); err != nil {
				summary.addUndecodable()
				l.Warnw("skipping undecodable secrets response from node", "nodeAddr", nodeAddr, "error", err)
				continue
			}
			out = append(out, signed)
		}
		encoded, err := json.Marshal(relaytypes.SignedSecretsResponseBundle{Responses: out})
		if err != nil {
			return nil, fmt.Errorf("failed to encode secrets response bundle: %w", err)
