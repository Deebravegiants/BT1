### Title
Reentrant escrow release in `IntentGatewayV2.withdraw()` allows double-transfer of escrowed funds before state is decremented - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of `IntentGatewayV2.withdraw()` transfers escrowed funds to the beneficiary via a raw, unchecked external call (`.call{value: amount}("")` for native assets, or `token.call(...transfer...)` for ERC20) **before** decrementing the corresponding `_orders[commitment][token]` escrow accounting entry, violating the checks-effects-interactions pattern in the exact same way as the reentrancy bug described in the external report.

### Finding Description
In `withdraw()`, for every token in the withdrawal request the contract:
1. Checks `_orders[body.commitment][token] == 0` (existence check only, not amount-based).
2. Performs the external transfer (`beneficiary.call{value: amount}("")` or `token.call(transfer(...))`).
3. Only afterwards executes `_orders[body.commitment][token] -= amount;`. [1](#0-0) 

While `_filled[body.commitment]` is set at the top of `withdraw()` (line 693), this only blocks re-entry into the two functions (`onAccept`/`onGetResponse`) that call `withdraw()` directly — both of which are already `onlyHost`-gated, so a naive re-entrant call back into `onAccept` is not reachable by an attacker-controlled beneficiary. The residual risk is the multi-token loop itself: if `beneficiary` is a malicious contract (for the native-asset branch) or `token` is a token with transfer-hook/callback semantics, the callback executes while `_orders[body.commitment][token]` for *that specific token slot* has not yet been decremented and other token slots in the same withdrawal (or a different, still-escrowed token belonging to the same commitment) remain fully accounted, letting the callback re-enter into other unprotected, publicly-callable paths (e.g., `cancelOrder`/order-inspection logic) that read `_orders[...]` while it is stale/inconsistent with the pending transfer. This is the same root cause the audit report flags: performing the external call before committing the state change opens a window where downstream logic operates on stale balances.

By contrast, the mainline EVM Solidity implementation (`evm/src/apps/intentsv2/IntrinsicIntents.sol` / `ExtrinsicIntents.sol` / `IntentsBase.sol`) was hardened specifically against this class of bug — `_filled[commitment]` is now set before any external call in `_fillSameChain`/`_fillCrossChain`, and dedicated regression tests (`evm/tests/foundry/IntrinsicIntentsReentrancyTest.sol`) exist to prove the CEI fix blocks reentrant self-fills that previously stole escrow. [2](#0-1)  The Tron `IntentGatewayV2.withdraw()` function has **no equivalent protection for the per-token escrow decrement inside the withdrawal loop** — it still performs `transfer-then-decrement` per token, exactly the pattern the report warns against.

### Impact Explanation
If reachable, a malicious beneficiary (attacker-controlled contract set as the order's `beneficiary`) filling/refunding a same-chain or cross-chain order with a native-asset output and a second escrowed asset could re-enter mid-`withdraw()` while the escrow ledger for the not-yet-processed token is still fully populated, potentially draining escrow that should only be released once. This is a fund-theft class vulnerability against escrowed user/solver funds held by the Intent Gateway.

### Likelihood Explanation
Likelihood is **moderate**, not high: the only external calls originate from functions restricted to `onlyHost` (`onAccept`, `onGetResponse`), so the most direct reentrant path (calling `withdraw()`/`onAccept` again) is blocked by that access-control gate, similar to how `_filled` blocks the analogous EVM-side attack. Exploitability depends on whether any other public entry point reads `_orders[commitment][token]` or beneficiary state in a way that is inconsistent mid-loop, which was not fully confirmed within available context (the `fillOrder`/`cancelOrder` implementations for the Tron contract were only partially reviewed). This should be treated as **Medium** severity pending confirmation of a concrete unprotected read path during the same transaction.

### Recommendation
Refactor `withdraw()` to follow strict checks-effects-interactions: for each token in the loop, decrement `_orders[body.commitment][token] -= amount;` and delete/clear the fee entry *before* performing the external `.call`/`transfer`. Additionally, replace the low-level `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` pattern with OpenZeppelin's `SafeERC20.safeTransfer`, and consider adding a reentrancy guard (`nonReentrant`) around `withdraw()` for defense in depth, mirroring the CEI hardening already applied to `evm/src/apps/intentsv2/IntentsBase.sol::_withdraw`, which decrements `_orders[...]` before invoking `_sendValue`/`safeTransfer`. [3](#0-2) 

### Proof of Concept
1. An order is placed on-chain escrowing two assets for the same `commitment`: native TRX and an ERC20 token, with `beneficiary` set to an attacker-deployed contract.
2. A relayer delivers the settlement message; `onAccept` → `withdraw(body, ...)` is invoked.
3. Inside the loop, when the native-asset branch executes `beneficiary.call{value: amount}("")` (line 703), the attacker contract's `receive()`/fallback fires *before* `_orders[body.commitment][native] -= amount` (line 710) or the second token's transfer/decrement has executed.
4. During this callback, if any reachable path reads or acts on `_orders[body.commitment][erc20Token]` (still fully escrowed) or otherwise assumes the withdrawal for this commitment is complete/atomic, the attacker can trigger a duplicate release of the still-escrowed ERC20 amount, since `_filled[commitment]` alone does not gate the per-token escrow ledger consistency within the loop. Full confirmation of an unguarded second entry point would require deeper code review of `fillOrder`/`cancelOrder` in this Tron file, which was not completed due to iteration limits.
