### Title
Duplicate WalletAccount creation within a single `createMany` batch bypasses unique-tag validation - ([File: features/wallet-accounts/src/module/wallet-accounts.ts])

### Summary
The reported MEME404 bug class is: an ordered validation step that only checks state *prior* to the current insertion (the "previous" element/snapshot) rather than re-validating against all items that have already been processed in the same operation, allowing duplicates to slip through when they are not adjacent to what was checked. The `createMany` method in `WalletAccounts` exhibits the same structural flaw: it builds a duplicate-detection index (`byUniqueFields`) once from the pre-existing on-disk state, then iterates over the *new* batch, adding entries into `walletAccounts` but never refreshing `byUniqueFields` with accounts created earlier in the same batch.

### Finding Description
In `createMany`, before processing the incoming array, a lookup table is built once: [1](#0-0) 

Then, for every item in `walletAccountsData`, an index is derived (or provided) and a new `WalletAccount` instance is constructed. The code checks whether an account with an identical `.toString()` key already exists (`exists`), and separately checks whether an account with the same `["id", "seedId", "index"]` unique tag already exists via `byUniqueFields`: [2](#0-1) 

Crucially, `byUniqueFields` (built from `getUniqueTagForWalletAccount`, which only keys on `id`, `seedId`, and `index` — not `compatibilityMode` or `source`) is computed **once, outside the loop**, from the state before the batch began. As new `WalletAccount`s are created inside the `.map()` and written into the mutable `walletAccounts` object, `byUniqueFields` is never recomputed. This is directly analogous to the MEME404 bug where `_tiers[i-1]` is checked instead of validating against the full set of already-processed tiers — here, only the pre-batch snapshot is checked instead of the full set of already-processed items in the current batch.

As a consequence, if a single `createMany([...])` call contains two (or more) items that share the same `id` + `seedId` + `index` but differ in `compatibilityMode` (so their `.toString()` values, and therefore the `exists` check, differ), both will pass the "already exists" check and both will pass the `byUniqueFields` check (since it was never updated with the first item), and both will be persisted to `walletAccountsInternalAtom`.

This matters because `compatibilityMode` also feeds into the key/address derivation path (`buildDerivationPath` / `createGetKeyIdentifier`, seen in `libraries/key-utils/src/derivation-path.js` and `libraries/key-utils/src/key-identifier.js`), so creating two account records that map to overlapping/identical `seedId`+`index` derivation coordinates under different `compatibilityMode` values can produce address/key confusion between what should be two logically distinct wallet accounts, or make one account silently shadow the assets of another in address/balance/connected-origin lookups (`features/connected-origins`, `features/address-provider`) that key off wallet-account identity.

### Impact Explanation
Two wallet accounts persisted under the same underlying `seedId`/`index` derivation coordinates (differing only by `compatibilityMode`) undermines the wallet-account isolation invariant that the rest of the SDK relies on (address caching, connected-origins account mapping, public-key store, balances). This can cause address/key collisions between accounts the user believes are distinct, and in the multi-account/connected-origins flows can bleed permissions or funds visibility across what are supposed to be isolated per-account contexts. The existing test suite explicitly guards against index reuse across sequential `createMany` calls ("should require a unique index per seed for same"), showing the developers consider this an invariant worth enforcing — but the enforcement mechanism does not cover the case where the duplicate is introduced within the *same* batch call.

### Likelihood Explanation
Any caller (including code driven indirectly by RPC/dApp-triggered account-creation flows) that invokes `walletAccounts.createMany([...])` with attacker- or bug-influenced input containing two entries sharing `id`+`seedId`+`index` but different `compatibilityMode`/`source` would trigger this. Given `createMany` is a `public: true` module method reachable from higher-level SDK flows (not merely an internal test hook), and the check is a plain in-memory snapshot bug (not requiring any malicious external actor), the likelihood of this being reachable through legitimate multi-account creation UX is moderate.

### Recommendation
Rebuild or incrementally update `byUniqueFields` (and the `exists`-by-toString check) after each account is added within the same `.map()`/loop iteration, rather than relying on a single snapshot computed before the loop starts. For example, after `walletAccounts[walletAccount.toString()] = walletAccount`, also insert the new account into `byUniqueFields` under its `getUniqueTagForWalletAccount` tag so subsequent iterations in the same batch see it.

### Proof of Concept
```ts
// within a single createMany call:
await walletAccounts.createMany([
  {
    seedId: 'seedA',
    index: 0,
    id: 'sharedId',
    source: 'seed',
    compatibilityMode: 'a',
  },
  {
    seedId: 'seedA',
    index: 0,
    id: 'sharedId',
    source: 'seed',
    compatibilityMode: 'b', // different compatibilityMode -> different toString(), same unique tag
  },
])
// Expected: second entry should be rejected as "Already have walletAccount with same .source, .id, .seedId, and .index"
// Actual (per code inspection): byUniqueFields snapshot predates both insertions, so neither the `exists`
// check (different toString keys) nor the `byUniqueFields` check (stale snapshot) catches the collision,
// and both WalletAccounts are persisted.
```
