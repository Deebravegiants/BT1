### Title
Webhook shop-domain header is not bound to the HMAC signature, allowing tenant spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC of the raw body, then hands the caller-supplied `shop` header straight to the app's handler as the trusted tenant identifier, without that header ever being part of the signed material.

### Finding Description
The gem's webhook signature verification is implemented in `Utils::HmacValidator.validate`, which calls `verifiable_query.to_signable_string` [1](#0-0) . For webhooks, `Request#to_signable_string` returns only `@raw_body` — the shop, topic, webhook id and api version headers are excluded from the signed data entirely [2](#0-1) . `Request#shop` is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no further validation [3](#0-2) .

`Registry.process` checks only `Utils::HmacValidator.validate(request)` and then immediately builds `WebhookMetadata` using `request.shop`, dispatching it to the registered handler: [4](#0-3) .

The equality that should hold but doesn't: `hmac_covers(shop_header) == true`. In reality `hmac_covers(shop_header) == false`; only `hmac_covers(raw_body) == true`. Because the app's `api_secret_key` is shared across every shop that installs the app, any unprivileged user who installs the app on their own (free/dev) store receives a legitimately HMAC-signed webhook for their own shop. They can capture that valid `(raw_body, hmac)` pair and replay it to the app's webhook endpoint with the `shop` header rewritten to a victim merchant's domain. `Utils::HmacValidator.validate` still succeeds because it only re-derives the HMAC from `raw_body`, and `Registry.process` forwards the attacker-chosen `shop` value to `WebhookMetadata.shop` unchecked [5](#0-4) .

The gem's own documentation instructs host apps to treat `data.shop` as the authoritative tenant identifier for enqueuing/storing webhook data (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, ...)`) [6](#0-5) , so this is not host-app misuse of an undocumented contract — it is exactly the documented, intended use of the gem's API, and the gem itself fails to bind that field to the authentication check.

### Impact Explanation
Any application built on this gem that uses `data.shop` from `WebhookMetadata` to route webhook payloads to per-tenant state (as the gem's own docs recommend) can be made to ingest attacker-supplied body content under a victim shop's identity, since the tenant-binding field is not part of the authenticated payload. This is a cross-tenant data confusion primitive: an attacker-controlled shop's webhook (product update, order data, GDPR/customer webhooks, etc.) can be replayed and attributed to any target `myshopify.com` domain the attacker chooses, without any credential belonging to the victim.

### Likelihood Explanation
Requires only: (1) that the attacker install the app on a shop they control — free/trivial for public/dev apps — to obtain a genuinely-signed `(body, hmac)` pair, and (2) the ability to POST to the app's public webhook endpoint with modified headers, which is inherent to how HTTP webhook delivery works. No access token, `client_secret`, or privileged access is needed.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) header values in the HMAC-signed material used by `Request#to_signable_string`, or otherwise cryptographically bind the shop domain to the payload before it is trusted (e.g., cross-check `shop` against a known/installed shop record keyed by a value that is itself HMAC-protected), rather than relying purely on body-only signature validation and passing through untrusted headers as tenant identifiers.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and captures a legitimate webhook: raw body `B` and header `x-shopify-hmac-sha256: H` (valid HMAC of `B` under the app's shared `api_secret_key`), plus `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker replays the same `B`/`H` pair to the app's webhook endpoint but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `Utils::HmacValidator.validate` recomputes the HMAC of `B` only (per `Request#to_signable_string`) and it matches `H`, so the request passes validation [7](#0-6) .
4. `Registry.process` builds `WebhookMetadata.new(..., shop: request.shop, ...)` with `request.shop == "victim.myshopify.com"` and invokes the app's handler, which — per the gem's documented usage — treats this as an authentic webhook for `victim.myshopify.com` [8](#0-7) .
