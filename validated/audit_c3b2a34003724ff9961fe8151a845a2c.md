## Title
Webhook cross-tenant impersonation via unauthenticated `shop` header — HMAC binds only the request body, not the shop domain (`lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` is documented as verifying "the request did indeed come from Shopify" before invoking the app's handler with `data.shop` set to the shop domain the webhook is "for." In reality, the HMAC only authenticates the raw request body; the `shop` value delivered to the handler is read straight from the unauthenticated `x-shopify-shop-domain` header and is never covered by the signature. Because the app-level `api_secret_key` is shared across every shop that has installed the app, a merchant who controls one installation (Shop A) can capture a genuine Shopify-signed webhook and replay it to the same endpoint with the shop header rewritten to a different tenant (Shop B), producing a request that passes HMAC validation but is misattributed to Shop B.

### Finding Description
The verified equality the gem is supposed to enforce is:

`shop value delivered to handler == shop that produced/authorizes the signed body`

What is actually enforced is only:

`HMAC-SHA256(raw_body, api_secret_key) == received HMAC`

`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate_signature` computes the signature purely over that signable string: [2](#0-1) 

`shop`, `topic`, and `webhook_id` are all pulled from headers with no cryptographic binding to the body or the HMAC: [3](#0-2) 

`Registry.process` performs only the HMAC check, then dispatches to the handler using `request.shop` taken from that unauthenticated header: [4](#0-3) 

The gem's own documentation tells integrators that `process` "will verify the request did indeed come from Shopify" and that the resulting `data.shop` is "The shop domain of the webhook" — i.e., it presents `shop` as a trusted, verified field: [5](#0-4) [6](#0-5) 

Since `api_secret_key` is the same for every shop that has the app installed, a valid `(body, hmac)` pair obtained from a legitimate webhook delivered for Shop A remains a valid `(body, hmac)` pair when replayed with the shop header changed to Shop B — the signature check has no way to detect the substitution because it never covered the shop field to begin with.

### Impact Explanation
This is a cross-tenant identity-binding failure: an attacker who merely controls their own shop's installation of a target app (no access to `api_secret_key`, no privileged account) can cause the app to process attacker-controlled/attacker-sourced webhook data under a victim shop's identity, or trigger the handler's per-shop side effects (e.g., data updates, job enqueuing keyed by `data.shop`, as shown in the documented example `perform_later(topic: data.topic, shop_domain: data.shop, ...)`) against a shop the attacker does not own. This matches the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Exploitation only requires: (1) being a merchant with the target app installed on any shop (a normal, unprivileged app install), (2) capturing one legitimate webhook delivery to that shop (trivial to observe since the attacker controls that shop and endpoint traffic), and (3) resending the identical body/HMAC to the app's webhook endpoint with a different `x-shopify-shop-domain` header. No secret material, no TLS interception, and no social engineering are needed.

### Recommendation
Bind the shop identity into the authenticated material used for webhook verification — e.g., include the shop domain (and topic/webhook id) in the signed payload used for signature comparison, or independently verify that the webhook's shop domain matches an active, previously-established session/installation before invoking the handler, and reject/flag replays using the `webhook_id` for idempotency plus a freshness/timestamp check.

### Proof of Concept
1. Install the target app on attacker-controlled Shop A; wait for Shopify to send a genuine webhook (e.g., `orders/create`) to the app's callback endpoint. Capture the raw body and the `x-shopify-hmac-sha256` / `x-shopify-shop-domain` headers.
2. Resend an HTTP request to the same app endpoint with the identical raw body and `x-shopify-hmac-sha256` value, but set `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `HmacValidator.validate` recomputes the HMAC over the unchanged body with the app's shared `api_secret_key` and it matches, so `Registry.process` proceeds: [7](#0-6) 
4. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` even though the payload originated from Shop A, and performs whatever per-shop action the app implements (data storage, job enqueue, notification, etc.) attributed to the victim shop.
