### Title
Unvalidated swap-route destinations can smuggle unauthorized wallet-token transfers into the caller’s signed authorization tree - ([File: contracts/controller/src/strategies/swap.rs](contracts/controller/src/strategies/swap.rs))

### Summary
`swap_collateral`, `swap_debt`, and `repay_debt_with_collateral` accept caller-supplied route bytes and forward them to the configured aggregator without validating the contracts that the route invokes. A malicious route can name a rogue pool contract that calls `token.transfer(victim, attacker, amount)` while still returning a valid swap result. During transaction simulation, that transfer is recorded beneath the caller’s authorization entry; if the victim signs the generated tree without inspecting every child invocation, the rogue contract receives authorization to steal unrelated wallet tokens. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
The vulnerable boundary is analogous to unchecked archive-member paths: attacker-controlled route entries are treated as trusted destinations and are executed before settlement checks. `process_swap_collateral` authorizes the account owner or delegate and passes the opaque `swap` bytes into `withdraw_and_swap_from_supply`; `swap_tokens` then authorizes only the intended controller-to-router input transfer, but does not constrain which pool contracts the router invokes. [4](#0-3) [5](#0-4) 

The router’s structural decoder bounds registries and instruction indices, but it does not require hop `pool` addresses to belong to an approved venue registry. Execution resolves `pool`, `token_in`, and `token_out` directly from the attacker-controlled `assets` registry and dispatches the selected venue adapter. [6](#0-5) [7](#0-6) 

The repository’s harness demonstrates the resulting authorization-tree injection: a route-selected contract can call `token.transfer(alice, attacker, WALLET_BALANCE)`, simulation records that transfer as a child of Alice’s `swap_collateral` authorization, and signing the returned tree makes the transfer succeed. [8](#0-7) [9](#0-8) [10](#0-9) 

### Impact Explanation
The impact is theft of user funds beyond the collateral amount intentionally routed. The malicious pool can target any token held by the victim and any recipient address because the token contract’s `transfer` call requires only victim authorization, which is smuggled into the signed invocation tree. The swap can simultaneously satisfy its minimum output, so balance-delta checks and final risk checks do not detect the unrelated wallet theft. [11](#0-10) [12](#0-11) [13](#0-12) 

The documented threat model acknowledges that a route can place third-party code below the caller’s authorization and that the resulting wallet loss is not bounded by the routed amount, payload minimum, or final risk gate. [14](#0-13) 

### Likelihood Explanation
An unprivileged attacker can deploy a malicious contract, encode a route that names it as a hop pool, and distribute that route through a quote, tutorial, shared transaction, or compromised frontend. The attack requires the victim to sign the poisoned authorization tree generated by simulation; wallets or clients that display only the root invocation, or users who do not inspect all child invocations, make this practical. The same class is reachable through `swap_debt`, `swap_collateral`, and `repay_debt_with_collateral`. [15](#0-14) [16](#0-15) [17](#0-16) 

### Recommendation
Treat route destinations as an authorization boundary rather than opaque execution data. The router should validate every venue/pool address against a governance-approved registry before executing the payload, or reject arbitrary pool addresses for public routes. In addition, clients should decode `swap_xdr`, enumerate all pool contracts and token calls, and reject any simulated authorization tree containing children other than the expected input transfer. The regression test should assert that a route-selected contract cannot add a victim-token `transfer` child beneath `swap_collateral`. [7](#0-6) [14](#0-13) [17](#0-16) 

### Proof of Concept
The included test deploys an `UnlistedPoolRouter` and a `RogueHopPool`; the pool stores `(victim, wallet_token, attacker, amount)` and calls `transfer(victim, attacker, amount)` from its `swap` method. The submitted `swap_collateral` route pays fair `ETH` output while stealing Alice’s entire unrelated wallet-token balance. [18](#0-17) [19](#0-18)

**File:** docs/explanation/threat-model.md (L154-165)
```markdown
That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap
user.
```
