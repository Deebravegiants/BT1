### Title
Webhook `shop` attribution is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook as authenticated once the HMAC over the raw body validates, then unconditionally trusts the `shop-domain` header to attribute that body to a specific tenant. Because the HMAC signable string only ever covers the raw body, the `shop` field used for tenant attribution is not bound to the signature at all, breaking the equality "HMAC-verified request == request attributed to the correct shop."

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from the unauthenticated `shop-domain`/`x-shopify-shop-domain` header: [2](#0-1) 

`Utils::HmacValidator.validate` computes and compares the HMAC exclusively against `to_signable_string`, i.e. the raw body, never the headers: [3](#0-2) 

`Registry.process` calls this validator, and on success forwards `request.shop` — the unauthenticated header — to the app's handler as the authoritative tenant identifier for the payload: [4](#0-3) 

The gem's own documentation states that `Registry.process` "will verify the request did indeed come from Shopify," and shows the recommended handler pattern using `data.shop` to route/attribute work per tenant (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), reinforcing that `shop` is meant to be treated as trusted, verified data: [5](#0-4) [6](#0-5) 

Since the app's `api_secret_key` (`client_secret`) is shared across all shops that install the app, any tenant that has legitimately installed the app (an unprivileged, non-elevated actor from the app's perspective) receives valid HMAC-signed webhook bodies for their own shop. That same body/HMAC pair remains valid regardless of which `shop-domain` header accompanies it, because the header is excluded from the signed content.

### Impact Explanation
An attacker who controls one tenant (Shop A) that has installed the app can capture a legitimately-signed webhook (raw body + `x-shopify-hmac-sha256`) originating from their own shop, then replay it against the app's webhook endpoint with the `x-shopify-shop-domain` header rewritten to a victim tenant's domain (Shop B). `Registry.process` will validate the HMAC (it still matches, since only the body is signed) and hand the handler a `WebhookMetadata` claiming `shop: "shop-b.myshopify.com"` together with attacker-chosen body content. Any host application that follows the documented pattern of keying storage, side effects, or authorization decisions off `data.shop` will process attacker-controlled data as if it were authentic data belonging to Shop B — a cross-tenant data injection/corruption impact reachable purely through this gem's `Request`/`HmacValidator`/`Registry` logic.

### Likelihood Explanation
Any merchant/tenant that installs the app can obtain valid signed webhook traffic for their own shop (this requires no elevated privilege, leaked secret, or social engineering — just installing the app once, which is the normal unprivileged use case for a Shopify merchant). Replaying the captured body with a modified header is trivial and requires no cryptographic material beyond what is naturally delivered to the attacker's own webhook endpoint.

### Recommendation
Bind the `shop-domain` (and other identity-relevant headers such as `topic`/`webhook_id`) into the HMAC-signed material, e.g. by including the shop domain header value in `to_signable_string`, so that a signature computed for one shop cannot be replayed under a different shop's identity. At minimum, document prominently that `Registry.process` does not authenticate the `shop` field and instruct implementers to independently correlate the delivered `webhook_id`/shop against known, previously-registered subscriptions before trusting attribution.

### Proof of Concept
1. App is installed on attacker-controlled Shop A; attacker captures a real webhook delivery: raw body `B`, header `x-shopify-hmac-sha256: H` (computed as `HMAC(api_secret_key, B)`), and `x-shopify-shop-domain: shop-a.myshopify.com`.
2. Attacker crafts a new inbound webhook POST to the app's webhook endpoint reusing body `B` and header `H`, but sets `x-shopify-shop-domain: shop-b.myshopify.com` (the victim tenant).
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` builds a request object; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(api_secret_key, B)` and matches `H` — validation succeeds because the shop header was never part of the signed content.
4. `Registry.process` invokes `handler.handle(data: WebhookMetadata.new(shop: "shop-b.myshopify.com", body: parsed(B), ...))`, causing the app to process/attribute attacker-supplied data as belonging to Shop B.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
