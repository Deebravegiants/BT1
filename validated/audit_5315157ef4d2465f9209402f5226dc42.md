Confirmed: `Registry.process` at [1](#0-0)  validates the HMAC and then dispatches to the handler using `request.shop` and `request.topic`, both of which come straight from HTTP headers via `shopify_header` and are never fed into the HMAC computation.

### Title
Webhook `shop-domain` header is trusted for tenant attribution but is not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, and `#hmac` is read from the `x-shopify-hmac-sha256`/`shopify-hmac-sha256` header, while `#shop` and `#topic` are read from separate, unauthenticated headers (`shopify-shop-domain`, `shopify-topic`): [2](#0-1) [3](#0-2) 

`Utils::HmacValidator.validate` computes the signature strictly from `verifiable_query.to_signable_string` (i.e., the raw body) and compares it to the `hmac` header: [4](#0-3) 

`Registry.process` treats a passing HMAC check as proof of the entire request's authenticity, then trusts `request.shop` and `request.topic` (headers, not covered by the HMAC) to route the payload to a handler and to populate `WebhookMetadata.shop`, which app code uses to key tenant-specific processing: [1](#0-0) 

This mirrors the reported bug class: a field that is *acted on* (`shop`, used for tenant attribution) is not *covered* by the integrity check (HMAC only signs the body). The equality the code implicitly assumes — `shop header == shop that generated/authenticated this body` — does not actually hold, because only `raw_body` is bound to the secret via HMAC; `shop-domain` is a bare, unauthenticated header value.

### Impact Explanation
Any party who can obtain one valid `(raw_body, hmac)` pair signed with the app's shared `api_secret_key` — for example a malicious merchant who installs the app on their own store and captures a legitimate webhook delivery for that store — can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header. `HmacValidator.validate` will still pass (it never looks at the shop header), and `Registry.process` will hand the payload to the handler tagged with the attacker-chosen `shop`, misattributing the webhook to a different (victim) tenant. Depending on how the host application's `WebhookHandler` uses `WebhookMetadata#shop` (e.g., to look up/store per-shop data, trigger per-shop side effects, or determine access), this enables cross-tenant data injection or corruption — the "cross-tenant access" impact class.

### Likelihood Explanation
Exploitability requires the attacker to obtain at least one legitimately-signed `(body, hmac)` pair, which is trivially achievable by any merchant/developer who installs the app on their own store (a normal, unprivileged capability of the multi-tenant SaaS model) and inspects the webhook delivery Shopify sends them. No access to `api_secret_key`, tokens, or TLS interception is required — only the ability to receive one's own app webhook and resend it with a modified header to the app's own public webhook endpoint.

### Recommendation
Bind `shop` (and ideally `topic`) into the signed content, or otherwise cryptographically tie the shop identity to the HMAC-covered payload, before using it for tenant dispatch — e.g., verify the `shop` returned in the (JSON) body/topic-specific schema against the header, or require host applications to independently confirm the webhook's `shop-domain` belongs to a shop with an active, matching session/installation before trusting `WebhookMetadata#shop` for tenant-scoped operations, and document this explicitly since the library currently presents `data.shop` as trustworthy once `HmacValidator.validate` succeeds.

### Proof of Concept
1. Attacker installs the target app on their own dev shop `attacker.myshopify.com` and triggers a webhook (e.g., `orders/create`).
2. Attacker captures the raw POST body and the `x-shopify-hmac-sha256` header Shopify sent — both valid, signed with the app's real `api_secret_key`.
3. Attacker POSTs the identical body and HMAC header to the app's webhook endpoint again, but changes `x-shopify-shop-domain` to `victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks the body against the HMAC — it succeeds [5](#0-4) .
5. The handler executes with `WebhookMetadata.shop == "victim.myshopify.com"` [6](#0-5) , even though the body was never actually generated for that shop.
