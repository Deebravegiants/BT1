Confirmed: `Message.from` is an ABI-encoded `bytes` field of arbitrary length [1](#0-0) , and unlike the sibling `to`/`sender` handling elsewhere in the same file which explicitly validates the length is 20 or 32 bytes before copying [2](#0-1) , the "no signature" branch of `on_accept` skips that validation entirely.

### Title
Unchecked-length slice/copy on attacker-controlled `Message.from` causes reachable panic in `hyper-fungible-token::on_accept` - (File: modules/pallets/hyper-fungible-token/src/module.rs)

### Summary
`on_accept` decodes an ABI-encoded `Message { from, to, amount, data }` from an inbound ISMP `PostRequest` body and, when the optional calldata carries no signature, derives the substrate dispatch origin from `message.from` without validating its length, unlike every other length-sensitive field in the same function.

### Finding Description
`Message.from` is a dynamic ABI `bytes` field with no length constraint enforced at decode time [1](#0-0) . In `on_accept`, when `substrate_data.signature` is `None`, the code branches on `source.is_evm()` and either slices `from_bytes[from_bytes.len() - 20..]` or does `account.copy_from_slice(from_bytes)` directly into a `[u8; 32]` buffer, with no prior length check: [3](#0-2) 

This is the exact CVE-2018-19627 bug class — a length-prefixed field consumed with a fixed-size buffer operation without verifying the boundary — and is the same pattern the codebase's own regression tests document as previously fatal elsewhere (`as_utf8_string`'s `copy_from_slice` panic on `consensus_state_id`, fixed in `modules/utils/serde/src/lib.rs`) [4](#0-3) . Two distinct panics are reachable:
- If `source.is_evm()` and `from_bytes.len() < 20`, `from_bytes.len() - 20` underflows `usize`, producing either an arithmetic-overflow panic (debug) or a slice-index-out-of-range panic (release, since the wrapped value vastly exceeds `from_bytes.len()`).
- If `source` is not EVM and `from_bytes.len() != 32`, `copy_from_slice` panics on the length mismatch.

Note that `message.data` (and thus this decode path) is only reached when `!message.data.is_empty()` [5](#0-4) , and the `SubstrateCalldata.signature` field is attacker-optional — an unsigned `substrate_data` is a legitimate, supported path (used for unsigned transfers where the beneficiary account itself is the origin) — so a message with `signature: None` and a malformed `from` (already ABI-decoded, its length is whatever the sender packed) reaches the vulnerable slice/copy unconditionally.

### Impact Explanation
A panic inside `on_accept`, which is invoked from `pallet-ismp`'s request-delivery execution path when handling a proven `PostRequest`, aborts execution of that block/extrinsic. Since `on_accept` runs as part of dispatching relayed, proof-verified requests (i.e., after `handle_unsigned`/message delivery accepts the associated commitment), a panic here can halt processing of the request batch, potentially bricking further token deliveries or, depending on runtime panic handling (`debug_assertions` vs `abort`), taking down the node process — a denial-of-service on this route unable to deliver messages/tokens. This satisfies the "route unable to deliver messages" acceptance criterion.

### Likelihood Explanation
Reaching this requires only that the source contract mapped via `ContractToAsset::<T>::get(source, &from)` be considered trusted for delivering the token message; the `Message.from` field itself, however, is fully attacker-controlled content within the ABI-encoded `body` and is not independently authenticated (it is only consulted for deriving the substrate call's dispatch origin in the unsigned path, not for accepting the request). Any relayer/attacker capable of getting a message accepted from a configured source contract (e.g., a compromised or misconfigured `HyperFungibleToken` EVM contract, or a chain where the "trusted" mapping does not itself bound `from`'s encoding) can supply an arbitrarily short or long `from` field to trigger the panic. This is a Medium-High likelihood, message-dispatch-reachable bug.

### Recommendation
Mirror the existing `to_bytes`/`sender_bytes` length validation pattern already used in the same file (lines 65–71 and 226–232) for the `from_bytes` handling in the unsigned-calldata branch: explicitly match on `from_bytes.len() == 20` / `== 32`, and return `Err(HftError::InvalidSenderLength(from_bytes.len()))` (or similar) for anything else, before doing the slice/copy.

### Proof of Concept
1. Register a token and map a source EVM contract via `ContractToAsset` as in normal operation.
2. Craft a `PostRequest.body` that ABI-decodes to `Message { from: <e.g. 3-byte value>, to: <valid>, amount: <any>, data: <SubstrateCalldata with signature: None, runtime_call: <valid encoded call>> }`.
3. Deliver this request through the standard ISMP proof-verification path so `on_accept` is invoked.
4. `from_bytes.len() - 20` underflows in the `source.is_evm()` branch (or `copy_from_slice` panics in the non-EVM branch when `from_bytes.len() != 32`), panicking inside `on_accept` and aborting message processing. [3](#0-2)
