### Title
Webhook `shop` identity is trusted from an unauthenticated header while only the raw body is HMAC-verified, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb], [File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw HTTP body, then trusts the `shop` value read from the `x-shopify-shop-domain`/`shopify-shop-domain` header — a value that is never part of the HMAC-signed bytes — to build the `WebhookMetadata` handed to the host application's per-tenant handler. Because the HMAC secret (`Context.api_secret_key`, the app's `client_secret`) is identical for every shop that installs the same app, anyone who can obtain one validly-signed `(raw_body, hmac)` pair (e.g. a merchant inspecting their own store's outgoing webhook deliveries) can resend that exact body/HMAC pair with a different `shop-domain` header and have it accepted as an authentic webhook from a different tenant.

### Finding Description
The gem's webhook authentication is implemented as:

```ruby
# lib/shopify_api/utils/hmac_validator.rb
def validate(verifiable_query)
  return false unless verifiable_query.hmac
  result = validate_signature(verifiable_query, Context.api_secret_key)
  ...
end

def validate_signature(verifiable_query, secret)
  received_signature = verifiable_query.hmac
  computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
  OpenSSL.secure_compare(computed_signature, T.must(received_signature))
end
``` [1](#0-0) 

For webhooks, `to_signable_string` returns only the raw request body:
```ruby
def to_signable_string
  @raw_body
end
``` [2](#0-1) 

`shop` is derived independently from a header, and is therefore not covered by the HMAC computation at all:
```ruby
def shop
  T.cast(shopify_header("shop-domain"), String)
end
``` [3](#0-2) 

`Registry.process` validates the HMAC (over the body only) and then unconditionally trusts `request.shop` as the tenant identity for dispatch:
```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
``` [4](#0-3) 

The identity binding that should hold is:
`hmac_verified_bytes.shop == metadata.shop_used_for_tenant_routing`

In this implementation, `hmac_verified_bytes` = `raw_body` only, while `metadata.shop` = an unauthenticated header value. These two are never bound together, so the equality does not hold. Because `Context.api_secret_key` is the single app-wide `client_secret` shared across every shop that installs the app (not a per-shop secret), a valid `(raw_body, hmac)` pair computed for shop A's data remains a valid pair regardless of which `shop-domain` header accompanies it — the signature check passes independent of the claimed tenant.

### Impact Explanation
This breaks the tenant boundary the host application relies on this gem to enforce (`WebhookMetadata#shop` is the field host apps use to route webhook payloads — e.g. order/customer data — into the correct per-shop database record). An attacker who is a legitimate merchant using the same app (and can inspect webhook deliveries/logs for their own shop, which Shopify apps and various delivery-log tooling expose) can capture one valid `(raw_body, hmac)` pair from their own store's webhook traffic and replay it to the app's webhook endpoint with an arbitrary `shop-domain` header value naming a different merchant's shop. Because the gem's HMAC verification never binds `shop` to the signed bytes, `Registry.process` will accept it as authentic and dispatch attacker-controlled body content tagged with a victim shop's identity into that victim's tenant-scoped handler — a cross-tenant data injection into another merchant's account, satisfying the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Medium-High: the only prerequisite is app installation on the attacker's own shop (a normal, low-privilege merchant action) and the ability to see one legitimate webhook body plus its `X-Shopify-Hmac-Sha256` value, which most apps/log tooling surface to store owners. No knowledge of `client_secret` or access tokens is required — this is purely a mismatch between what is signed and what is trusted for tenant identity.

### Recommendation
**Short term:** Bind `shop` (and ideally `topic`, `api_version`, `webhook_id`) into the HMAC-signable payload/verification path for webhooks, or have `Registry.process`/host applications independently verify that `request.shop` corresponds to a shop with an active, known installation before dispatching to the handler — never trust the `shop-domain` header as tenant identity on the strength of a body-only HMAC alone.

**Long term:** Document explicitly (and enforce in this library, not just leave to host apps) that `WebhookMetadata#shop` is unauthenticated header data separate from the HMAC-verified payload, and require/encourage host apps to cross-check it against their own shop/session store keyed by an authenticated identifier before trusting the metadata for any tenant-scoped operation.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and triggers a webhook (e.g., `orders/create`), capturing the raw POST body `B` and header `X-Shopify-Hmac-Sha256: H` sent by Shopify (both are visible via standard webhook delivery logs/inspection tools).
2. Attacker crafts a new HTTP request to the app's webhook endpoint reusing the exact same body `B` and header `H`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. The app calls `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {..., "x-shopify-shop-domain" => "victim.myshopify.com", "x-shopify-hmac-sha256" => H})` then `Registry.process(request)`.
4. `Utils::HmacValidator.validate(request)` recomputes HMAC over `to_signable_string` (`= B`) using the app's single `client_secret`, which matches `H` exactly as before — validation succeeds despite the spoofed shop header: [5](#0-4) 
5. `handler.handle(data: WebhookMetadata.new(..., shop: "victim.myshopify.com", body: parsed_body_of_B, ...))` is invoked — the app's handler now processes attacker's order data as if it belongs to `victim.myshopify.com`, corrupting or injecting data into the victim tenant's records.
