### Title
Webhook Topic, Shop-Domain, API-Version and Webhook-ID Headers Are Not Covered by HMAC, Enabling Cross-Tenant Webhook Spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then blindly trusts the `shop`, `topic`, `api_version`, and `webhook_id` values taken from unauthenticated HTTP headers when constructing the `WebhookMetadata` passed to the app's handler.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) . The `shop`, `topic`, `api_version`, and `webhook_id` accessors instead read directly from HTTP headers that are never included in the signable string: [2](#0-1) .

`Registry.process` validates the request using `Utils::HmacValidator.validate(request)`, which calls `to_signable_string` (i.e., only checks the body's HMAC), and then immediately dispatches to the topic handler using the unauthenticated `request.shop`, `request.topic`, `request.api_version`, and `request.webhook_id` values: [3](#0-2) . `HmacValidator.validate` computes the HMAC purely from `to_signable_string`, never touching headers: [4](#0-3) .

This breaks the identity binding: `hmac(body) == valid` is treated as equivalent to `shop-domain header == authenticated shop`, but the shop identity is never cryptographically bound to the body. Since `Context.api_secret_key` is the app's single client secret shared across every shop/tenant that installs the app (not a per-shop secret), any merchant who has installed the app can capture one of their own genuine, correctly-HMAC'd webhook deliveries (identical body content is often reproducible, e.g., `orders/create` test payload, or any body an attacker can trigger in their own store) and replay it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header rewritten to point at a different, victim shop. Because `HmacValidator.validate` only checks the body's HMAC against the shared secret — which is still valid, since the secret is the same for all shops of that app — the forged request passes verification, and `WebhookMetadata.shop` delivered to the host application's handler is the attacker-chosen victim shop rather than the shop that actually produced the payload.

### Impact Explanation
This is a cross-tenant confusion: a merchant/attacker with only the ability to receive or trigger a legitimately-signed webhook for their own shop can cause the app to process arbitrary webhook data as belonging to another tenant's shop. Depending on how the host application uses `WebhookMetadata#shop` (e.g., to look up per-shop sessions/access tokens, to update per-shop billing/state, or to key GDPR redaction actions), this can lead to cross-tenant data corruption or actions being taken against the wrong merchant's data/session — squarely matching the "cross-tenant access" impact category.

### Likelihood Explanation
Medium-High: any developer/merchant with a legitimate app installation can capture their own valid webhook HMAC and body, and headers are trivially attacker-controlled when directly invoking the exposed webhook endpoint (this gem places no constraint tying the header values to the signed payload). No access token, `client_secret`, or privileged access is required beyond what a normal installing merchant already has.

### Recommendation
Bind the tenant/topic identity into the material that is HMAC-verified, or otherwise independently authenticate the `shop-domain`/`topic` header values (e.g., cross-check `shop` against the session/shop that registered the webhook, or include the relevant headers in the signed payload) before constructing `WebhookMetadata` and dispatching to the handler.

### Proof of Concept
1. App merchant "attacker-shop" receives a legitimate webhook delivery, e.g. `orders/create`, with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(app_client_secret, B)`.
2. Attacker crafts a POST to the app's webhook endpoint with the same body `B` and same header `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and optionally a different `X-Shopify-Webhook-Id`/`X-Shopify-Topic` if desired for a different registered handler).
3. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers, and `Registry.process` calls `Utils::HmacValidator.validate(request)` which succeeds because it only hashes `@raw_body` (`B`), unaffected by the header tampering: [5](#0-4) .
4. `handler.handle` is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, causing the host application to process the payload as though it originated from `victim-shop`: [6](#0-5) .
