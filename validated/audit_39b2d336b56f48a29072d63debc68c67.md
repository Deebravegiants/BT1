### Title
Webhook Cross-Tenant Shop Spoofing via HMAC Signature Not Covering Shop Domain - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, excluding the `shop-domain` header, while `ShopifyAPI::Webhooks::Registry.process` trusts `request.shop` (derived from that unauthenticated header) as the tenant identity passed to the app's handler. An attacker who merely operates their own shop with the app installed can capture one genuine, Shopify-signed webhook and replay its exact body/HMAC while substituting the `shop-domain` header to impersonate a victim tenant, since the signature never covers that field.

### Finding Description
`HmacValidator.validate` computes the signature strictly over `verifiable_query.to_signable_string`, and for webhooks that is defined as just `@raw_body`: [1](#0-0) 

The `shop` accessor used to attribute the webhook to a tenant is read straight from the `x-shopify-shop-domain`/`shopify-shop-domain` header, which is not part of the HMAC input at all: [2](#0-1) [3](#0-2) 

`Registry.process` validates only the HMAC (which never touched the shop header) and then dispatches to the app handler using `request.shop` as the tenant identity, alongside the (attacker-controlled-origin) body: [4](#0-3) 

`WebhookMetadata.shop` is a plain `String` field with no additional binding to the signed content: [5](#0-4) 

The gem's own documentation confirms host apps are expected to key their tenant-scoped side effects (queueing jobs, updating records) directly off `data.shop`: [6](#0-5) 

The identity binding that should hold is: `shop domain verified by HMAC == shop domain the app acts on`. Because the HMAC only covers `@raw_body`, this equality never actually holds — the shop domain is fully attacker-controlled while the body's authenticity is verified against the app's secret.

### Impact Explanation
This breaks a cross-tenant boundary that host applications built on this gem rely on the gem to enforce: any user who can get one authentic webhook delivered to their own shop (i.e., anyone who installs the app — no `api_secret_key`, access token, or privileged account needed) can forge a follow-up request bearing a completely different shop domain header, reusing the same authentic body+HMAC pair. Since `Registry.process` treats the request as validated once the HMAC passes, and forwards the attacker-chosen `shop` to the app's `WebhookHandler`, the app performs the tenant-scoped effects of a webhook (e.g. `orders/create`, `app/uninstalled`, GDPR/customer data webhooks) attributed to a victim shop chosen by the attacker. This is a cross-tenant access/data-integrity issue in the app's per-tenant processing pipeline, driven entirely by this gem's failure to bind the verified shop identity to the verified bytes.

### Likelihood Explanation
High. The only prerequisite is installing the target app on any shop the attacker controls (a normal, unprivileged action any merchant can take) and observing one webhook delivery, which is a routine occurrence during normal app usage. No secrets, tokens, or elevated privileges are required, and the replay/header substitution is trivial to perform with any HTTP client.

### Recommendation
Include the shop domain (and ideally the topic/webhook-id) in the signable string used for HMAC verification, or otherwise cryptographically bind `request.shop` to the verified payload before it is exposed via `WebhookMetadata`. At minimum, document and/or enforce that `Registry.process` cross-checks `request.shop` against an expected/allow-listed shop derived from stored session data rather than trusting the raw header once the body HMAC passes.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` and registers for a webhook topic (e.g. `orders/create`).
2. Shopify delivers a genuine webhook to the app's endpoint with headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC over raw_body>`, and some `raw_body`.
3. Attacker replays the exact same `raw_body` and `x-shopify-hmac-sha256` value to the same endpoint, but changes `x-shopify-shop-domain` to `victim.myshopify.com`.
4. `HmacValidator.validate` (lib/shopify_api/utils/hmac_validator.rb:13-22) recomputes the HMAC over `raw_body` only, matches the replayed signature, and returns `true`.
5. `Registry.process` (lib/shopify_api/webhooks/registry.rb:189-199) proceeds and calls the app's handler with `WebhookMetadata.new(... shop: "victim.myshopify.com", body: <attacker's data> ...)`, causing the app to process attacker-supplied data as if it belonged to the victim tenant.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
