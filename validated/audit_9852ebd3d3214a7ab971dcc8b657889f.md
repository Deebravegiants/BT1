### Title
Webhook `shop` (and `topic`/`webhook_id`) fields are trusted for tenant attribution without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC-verifiable payload solely from the raw request body, while the `shop`, `topic`, `webhook_id`, and `api_version` values used to attribute and route the webhook are read directly from unauthenticated HTTP headers. `Registry.process` treats a passing `HmacValidator.validate(request)` check as proof the whole webhook (including its shop attribution) is trustworthy, but the signature never actually binds the shop to the body.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id` and `api_version` are parsed straight out of caller-supplied headers with no cryptographic binding to the signed body: [2](#0-1) 

`Registry.process` gates entirely on `Utils::HmacValidator.validate(request)`, then forwards `request.shop` (and `topic`, `webhook_id`) as trusted metadata to the app's handler: [3](#0-2) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string`, i.e., the raw body, and compares it against the value of the `hmac-sha256` header: [4](#0-3) 

The binding that should hold is: `shop_header == shop_bound_by(hmac)`. In reality, `hmac` binds only the body bytes, so `shop_header` can be swapped freely by anyone who can produce a request with a body+hmac pair that is valid for *some* shop, while claiming any `shop-domain` header value. This mirrors the reported bug class exactly: a field (`shop`) that is acted on (used to attribute/route webhook data to a tenant) but not covered by the HMAC.

### Impact Explanation
Any entity capable of obtaining one genuinely-signed webhook body+HMAC pair (e.g., a real merchant who has the app installed and receives their own legitimately signed webhooks) can resend that exact body and HMAC to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for an arbitrary victim shop domain. Because `HmacValidator.validate` never inspects `shop`, the request still passes as "valid," and `Registry.process` will dispatch `WebhookMetadata` with the attacker-chosen `shop` to the app's handler. If the host application uses `request.shop`/`WebhookMetadata#shop` as the tenant key (the documented purpose of that field), this results in cross-tenant data injection/confusion — data legitimately signed for shop A can be attributed to shop B. This satisfies the "cross-tenant access" criterion.

### Likelihood Explanation
Exploitation requires only: (1) the ability to send an arbitrary HTTP POST to the app's public webhook endpoint (typically internet-reachable, since Shopify itself must reach it), and (2) possession of any one valid `(raw_body, hmac)` pair, which is trivially obtainable by any merchant who installs the app (a legitimate, unprivileged action) and captures their own webhook deliveries. No `api_secret_key`, access token, or privileged account is needed beyond ordinary merchant self-service installation. This is realistically exploitable by any internet user willing to install the app on a shop they control.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the value that is HMAC-verified, or otherwise cryptographically bind the header-derived routing/attribution fields to the signed body (e.g., have `to_signable_string` incorporate a canonicalized representation of the headers alongside the body, matching whatever Shopify actually signs). At minimum, document prominently that `WebhookMetadata#shop` is *not* authenticated by the HMAC check and must not be used as a sole tenant-identification key without additional server-side session/shop verification.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and receives a legitimate webhook: body `B`, header `X-Shopify-Hmac-Sha256: H` (valid HMAC of `B` under the app's secret), header `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker resends the identical `B` and `H` to the app's webhook endpoint but changes the header to `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `request.to_signable_string` (`= B`) and matches `H` — validation passes. [3](#0-2) 
4. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, and any host logic keyed on `shop` now processes attacker-controlled data as though it originated from `victim-shop.myshopify.com`.

            result

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
