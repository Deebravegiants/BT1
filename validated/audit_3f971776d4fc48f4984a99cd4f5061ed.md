### Title
Webhook Shop-Domain Header Is Not Covered By The HMAC, Allowing Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` is documented as verifying "the request did indeed come from Shopify" and hands the handler a `shop` field described as "the shop domain of the webhook." In reality, the HMAC only signs the raw body; the `shop-domain` header used to build `WebhookMetadata.shop` is never part of the signed material. An attacker who legitimately controls one shop's installation can replay a genuine, correctly-signed webhook body while substituting an arbitrary `shop-domain` header, and the gem will report the request as valid and hand the forged shop identity to the handler.

### Finding Description
`Utils::HmacValidator.validate` verifies a `VerifiableQuery` by recomputing an HMAC over `to_signable_string` and comparing it to the `hmac` value with `OpenSSL.secure_compare`: [1](#0-0) 

For webhooks, `to_signable_string` returns only the raw HTTP body: [2](#0-1) 

But `shop`, `topic`, and `webhook_id` are all read straight from unauthenticated HTTP headers, never mixed into the signable string: [3](#0-2) 

`Registry.process` validates only the HMAC (i.e. only the body) and then dispatches to the handler using `request.shop` (a header-derived, unauthenticated value) as the tenant identity: [4](#0-3) 

The identity binding that should hold is: `hmac-verified bytes == bytes that determine the tenant (shop) the event is attributed to`. Here that equality is broken — the HMAC covers only the body, while the tenant-identifying field (`shop-domain` header) travels outside the signature. The library's own documentation reinforces the false assumption that the whole request, including the shop's identity, is verified: [5](#0-4) 
and explicitly instructs handlers to use `data.shop` for shop-scoped processing: [6](#0-5) 

### Impact Explanation
Because the handler receives `data.shop` as if it were an authenticated, Shopify-verified field, any downstream logic that looks up a shop's stored session/access token or performs shop-scoped side effects keyed on `data.shop` (exactly the pattern the docs recommend: `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) can be tricked into acting on behalf of a different tenant using attacker-controlled or replayed body content. This is a cross-tenant identity-binding failure reachable purely by an attacker with legitimate access to their own shop's webhook traffic (an "unprivileged internet user" relative to other merchants) — no access token, `client_secret`, or privileged account for the victim shop is required.

### Likelihood Explanation
Exploitation only requires capturing one legitimately-signed webhook payload (trivial for the attacker's own shop, since they can generate webhook traffic on demand by mutating their own store data) and replaying it to the app's public webhook endpoint with a substituted `X-Shopify-Shop-Domain` header. The HMAC check is unaffected because it never inspects the header, so `Registry.process` will always accept the forged request as authentic.

### Recommendation
- Do not treat `Request#shop` (or `#topic`, `#webhook_id`) as verified merely because `HmacValidator.validate` passed.
- Extend `to_signable_string` for webhooks to bind the security-relevant headers (at minimum `shop-domain`) into the signed material, or independently verify that `shop` corresponds to a shop with an active, expected registration/session before dispatching to the handler.
- Update `docs/usage/webhooks.md` to stop claiming full request verification and to warn integrators that `data.shop` must be independently corroborated (e.g., against the shop associated with the webhook subscription that was registered) before being used to select tenant-scoped credentials.

### Proof of Concept
1. Install the app on `attacker-shop.myshopify.com` and trigger a real event (e.g. `orders/create`) to receive a legitimately Shopify-signed webhook with body `raw_body` and header `X-Shopify-Hmac-Sha256: <valid hmac>`.
2. Replay the exact same `raw_body` and `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and any desired `X-Shopify-Topic`/`X-Shopify-Webhook-Id`).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only recomputes the HMAC over `raw_body` (unchanged) — see [7](#0-6) .
4. The registered handler is invoked with `WebhookMetadata.shop == "victim-shop.myshopify.com"` and the attacker-controlled `body`, even though nothing about the request actually originated from or references `victim-shop.myshopify.com`.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
