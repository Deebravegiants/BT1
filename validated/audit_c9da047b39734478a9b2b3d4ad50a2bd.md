## Title
`DirectBridge.describeWithdrawal` unconditionally reports `completed` for `ft_transfer_call`-based withdrawals, masking silent refunds - (File: `packages/intents-sdk/src/bridges/direct-bridge/direct-bridge.ts`)

### Summary
When `routeConfig.msg` is set on a Direct (NEAR) withdrawal, `createWithdrawIntentPrimitive` builds an `ft_withdraw` intent with `msg` present and `min_gas` deliberately left `undefined`, which causes `intents.near` to perform `ft_transfer_call` instead of a plain `ft_transfer`. `DirectBridge.describeWithdrawal` then unconditionally returns `{ status: "completed", txHash: args.tx.hash }` without checking whether the receiving contract's `ft_on_transfer` actually credited or refunded the tokens.

### Finding Description
The broken equality is: **"tokens credited to `destinationAddress` == `amount`" vs "SDK-reported status == completed"**. These should be equivalent, but the code never establishes this equivalence.

- `createWithdrawIntentPrimitive` (packages/intents-sdk/src/bridges/direct-bridge/direct-bridge-utils.ts:43-60) accepts an attacker/caller-supplied `msg` from `routeConfig.msg`, builds `ft_withdraw` with `msg` set and `min_gas: undefined` when `msg != null`. It only emits a `logger.warn` about "unpredictable gas consumption" — no functional safeguard. [1](#0-0) 
- `DirectBridge.createWithdrawalIntents` passes `args.withdrawalParams.routeConfig?.msg` straight through with no validation of its content or of the recipient's callback behavior. [2](#0-1) 
- `validateWithdrawal` only checks that `destinationAddress` is a valid NEAR address, that it isn't the token contract, and that the account exists — it performs zero validation of `msg` content or of eventual settlement outcome. [3](#0-2) 
- `describeWithdrawal` is a stub that always reports `completed` using the *intent transaction's* hash, regardless of whether the NEP-141 token contract's `ft_transfer_call` → `ft_on_transfer` sequence actually moved funds to `destinationAddress` or refunded them back (which is a normal, successful NEAR transaction outcome from the chain's perspective — it does not revert). [4](#0-3) 
- `watchWithdrawal` in the withdrawal-watcher trusts `describeWithdrawal`'s `status.status === "completed"` verbatim and resolves the completion promise with the tx hash, with no further on-chain balance verification. [5](#0-4) 

Root cause: `describeWithdrawal` for the Direct route was implemented as an unconditional stub (it never queries receipts/logs/balances), and it predates (or was never updated for) the `msg`/`ft_transfer_call` path that was later added to `createWithdrawIntentPrimitive`. Because a refunding `ft_on_transfer` call does not cause the underlying NEAR transaction to fail, there is no negative signal for `describeWithdrawal` to have observed even if it tried — the current implementation doesn't attempt to distinguish these cases at all.

### Impact Explanation
Any caller of `IntentsSDK.processWithdrawal` using `createNearWithdrawalRoute({ msg })` for an NEP-141 asset can end up in a state where the SDK reports `completed` with a valid `txHash` even though `ft_on_transfer` on the receiver contract refunded (or redirected) the tokens instead of crediting `destinationAddress` the full `amount`. An integrator relying on the SDK's status (e.g., to mark an internal withdrawal ledger entry as settled and release a corresponding credit, invoice, or second-leg payout) would do so on a false premise, creating a status/hash misreport that can cause double-crediting or unaccounted refunds. This matches the "status or hash misreport making an integrator credit or refund twice" High-severity category.

### Likelihood Explanation
- Preconditions: caller must use `createNearWithdrawalRoute(msg)` (a documented, supported code path) for an NEP-141 `assetId`, targeting a receiver contract whose `ft_on_transfer` refunds/redirects tokens under some msg payload.
- No privileged access is required; this is available to any ordinary SDK caller/integrator forwarding a `msg` string.
- Cost is a single normal withdrawal transaction; fully repeatable per withdrawal.
- Feasibility is high since `min_gas` is intentionally omitted and no post-hoc settlement check exists anywhere in the Direct route.

### Recommendation
`describeWithdrawal` for `DirectBridge` should not assume `completed` merely because the intent transaction is included. For `msg`-bearing NEP-141 withdrawals it should inspect the transaction's receipts/logs (e.g., the NEP-141 `ft_transfer_call` return value / refund events, or the target contract's emitted logs) to confirm the recipient actually retained the full `amount`, and report `failed`/`pending`/a distinct "refunded" status otherwise. At minimum, surface a stronger warning or require explicit opt-in acknowledgment when `msg` is used, and document that `completed` only reflects on-chain inclusion, not economic settlement, for this route.

### Proof of Concept
Vitest plan (`packages/intents-sdk/src/bridges/direct-bridge/direct-bridge.test.ts`):
1. Build withdrawal intents via `createWithdrawIntentPrimitive({ assetId: "nep141:usdt.tether-token.near", destinationAddress: "some.near", amount: 100n, storageDeposit: 0n, msg: "trigger-refund" })`.
   - Assert `intent.msg === "trigger-refund"` and `intent.min_gas === undefined` (confirms `ft_transfer_call` path with unpredictable/unchecked gas, per lines 43-60 of `direct-bridge-utils.ts`).
2. Call `DirectBridge.describeWithdrawal({ landingChain: Chains.Near, index: 0, withdrawalParams, tx: { hash: "0xabc", accountId: "user.near" } })` with no mocked receipt/log content.
   - Assert it returns `{ status: "completed", txHash: "0xabc" }` unconditionally (lines 334-338), even though no check of token movement occurred.
3. Mock a NEAR RPC transaction result where the receipt logs indicate `ft_on_transfer` returned the full `amount` (i.e., a full refund) — the equality to test is `amount credited to destinationAddress == 0` while `describeWithdrawal(...).status === "completed"`. Assert both sides diverge (SDK says completed, but 0 tokens were actually retained by `destinationAddress`), demonstrating the misreport.
