## Custody Analog Found: Silent Timelock Bypass via Unsynchronized `override_threshold` in Multisig Timelock

### Title
Reducing `num_signatures_required` after configuring a multisig timelock silently nullifies the timelock protection - (File: `aptos-move/framework/aptos-framework/sources/multisig_account.move`)

### Summary
The interest-calculator report's root cause is a value guarantee (interest owed) that is validated only at *setup time* and never re-checked against a later-changing input (elapsed time), allowing state to drift out of the invariant the fee model assumed. The Aptos-native analog is `MultisigAccountTimeLock.override_threshold` in `multisig_account.move`: it is validated to be strictly greater than `num_signatures_required` only at the moment `upsert_timelock`/`upsert_timelock_internal` is called [1](#0-0) , but `num_signatures_required` can later be lowered independently via `update_signatures_required` / `update_owner_schema`, with no re-validation that the existing `override_threshold` invariant still holds.

### Finding Description
`upsert_timelock_internal` enforces, at configuration time, that:
```
override_threshold.is_none() || *override_threshold.borrow() > multisig_account_resource.num_signatures_required
override_threshold.is_none() || *override_threshold.borrow() <= multisig_account_resource.owners.length()
``` [2](#0-1) 

The timelock-bypass check at execution time is:
```
inline fun can_execute_with_timelock(...): bool {
    if (exists<MultisigAccountTimeLock>(multisig_account)) {
        ...
        (override_threshold.is_some() && &num_approvals >= override_threshold.borrow()) || elapsed >= timelock
    } else { true }
}
``` [3](#0-2) 

`update_signatures_required` (and the owner-management variants `add_owners_and_update_signatures_required`, `swap_owners_and_update_signatures_required`) routes to `update_owner_schema`, which changes `num_signatures_required` with no reference to, or revalidation of, the `MultisigAccountTimeLock` resource: [4](#0-3) 

If `num_signatures_required` is subsequently lowered to a value at or below the previously configured `override_threshold`, the invariant "`override_threshold > num_signatures_required`" silently breaks. From that point on, in `validate_multisig_transaction`, satisfying ordinary quorum (`num_approvals >= num_signatures_required`) automatically also satisfies `num_approvals >= override_threshold`, because `override_threshold <= num_signatures_required <= num_approvals` [5](#0-4) . The `can_execute_with_timelock` override branch then evaluates `true` on every transaction, and the configured timelock delay is effectively disabled without ever calling `remove_timelock` and without emitting any event that indicates the timelock has been defeated (`TimelockUpdated`/`TimelockRemoved` are only emitted from the timelock functions themselves).

### Impact Explanation
Multisig accounts commonly custody APT, fungible assets, and code-object/module-upgrade authority. The timelock is a documented security control meant to give owners a window to detect and react to (e.g., cancel/react to) an approved-but-malicious transaction before it executes. A normal, unprivileged-relative-to-the-timelock-feature governance action (simply lowering `num_signatures_required`, which owners might do for operational convenience and with no intention of touching the timelock) can silently and permanently collapse the timelock delay to zero for all future transactions, without any explicit acknowledgment that a security control was disabled. This breaks the custody invariant that funds/authority protected by a configured delay cannot be moved before that delay elapses, enabling faster-than-intended asset transfers, ownership changes, or code upgrades out of the multisig once quorum is reached — a silent security-control downgrade rather than a merely cosmetic issue.

### Likelihood Explanation
This requires no external attacker privilege beyond what a normal multisig owner already has (approving a routine `update_signatures_required`-style transaction), and does not require malicious intent from the caller — it can happen as an operational accident. The precondition (a timelock already configured with an `override_threshold` close to `num_signatures_required`, followed by any signature-threshold reduction) is a realistic operational sequence (e.g., growing to a higher-security N-of-M, later relaxing back). Given the check is entirely absent (no cross-resource revalidation exists anywhere in `update_owner_schema`), likelihood is high whenever a deployer chooses to use both features together and later performs routine owner/threshold management.

### Recommendation
In `update_owner_schema` (the shared internal path for `update_signatures_required`, `add_owners_and_update_signatures_required`, `swap_owners_and_update_signatures_required`, and owner add/remove/swap that can change `num_signatures_required` or `owners.length()`), add a check that, if `MultisigAccountTimeLock` exists, the resulting `num_signatures_required`/`owners.length()` still satisfies `override_threshold > num_signatures_required` and `override_threshold <= owners.length()`; abort with `EINVALID_TIMELOCK_OVERRIDE_THRESHOLD` (or auto-clear/adjust the override_threshold with an emitted event) otherwise, so the timelock invariant cannot be silently invalidated by unrelated governance actions.

### Proof of Concept
1. Create a 3-of-5 multisig (`num_signatures_required = 3`, 5 owners).
2. Call `upsert_timelock(multisig_signer, 3600, option::some(4))` — passes validation since `4 > 3` and `4 <= 5` [2](#0-1) .
3. Owners later approve and execute `update_signatures_required(multisig_signer, 4)` to raise the ordinary quorum for unrelated operational reasons — succeeds; `update_owner_schema` does not check `MultisigAccountTimeLock` at all.
4. Now `num_signatures_required == 4 == override_threshold`. Any future transaction reaching 4 approvals (the now-normal quorum) also satisfies `num_approvals >= override_threshold`, so `can_execute_with_timelock` returns `true` immediately via the override branch, and `elapsed >= timelock` is never required — the 3600-second timelock is bypassed on every subsequent transaction, confirmed by the same override-vs-timelock logic exercised in `test_execute_with_override_bypasses_timelock` [6](#0-5) , except here it is triggered unintentionally, without ever explicitly calling `remove_timelock`.

    inline fun can_execute_with_timelock(multisig_account: address, sequence_number: u64, num_approvals: u64): bool {
        if (exists<MultisigAccountTimeLock>(multisig_account)) {
            let multisig_account_resource = &MultisigAccountTimeLock[multisig_account];
            let timelock = multisig_account_resource.timelock_period;
            let override_threshold = multisig_account_resource.override_threshold;

            // Get the pending transaction to check if the timelock has expired
            // Assume that the transaction has already been checked to exist and is valid
            let pending_transaction = get_transaction(multisig_account, sequence_number);

            // Use subtraction to avoid overflow (now_seconds() >= creation_time_secs is always true)
            let elapsed = now_seconds() - pending_transaction.creation_time_secs;

            // If the number of approvals meets the override threshold, or the timelock has expired, allow execution
            (override_threshold.is_some() && &num_approvals >= override_threshold.borrow()) || elapsed >= timelock
        } else {
            true
        }
    }
