### Title
Debug/staging Cargo features enabled by default risk shipping to production - (File: `Cargo.toml`)

### Summary
`Cargo.toml` declares `default = ["v2_x_x", "stage"]`, so the `stage` (staging backend) feature is compiled in by default unless a build explicitly opts out with `--no-default-features`. Separately, the `skip-user-qr-validation` feature (which enables `internal-pcp-export` + `internal-pcp-no-encryption`) is guarded only by `#[cfg(feature = ...)]`, and if enabled would deterministically fabricate valid signup credentials. [1](#0-0) 

### Finding Description
The comment at `Cargo.toml:110` states "All of these features except v2_x_x are used for internal development ONLY. They are not used for normal orbs," yet `default = ["v2_x_x", "stage"]` at line 112 makes `stage` part of the default feature set rather than something a production build script must explicitly disable-and-opt-out-of. `stage` transitively enables `livestream` and `agentwire/sandbox-network` and controls `BACKEND` resolution via `Backend::from_env_or_build_type::<{ cfg!(feature = "stage") }>()` in `src/backend/endpoints.rs:6-8`, which determines whether the orb talks to `stage.orb.worldcoin.org` or `orb.worldcoin.org` endpoints. [2](#0-1) 

More severely, `skip-user-qr-validation` in `src/backend/user_status.rs:76-110` replaces the real backend QR/session validation call with a hardcoded stub that always returns `valid: true`, fake `"test"` backend encryption keys, and a synthetic `identity_commitment: "test".to_string()`, and additionally suppresses the cryptographic `user_data.verify(user_data_hash)` check at lines 166-179 that normally binds the QR-derived user data hash to the signed app payload. [3](#0-2) [4](#0-3) 

This is analogous to the reported bug class: debug/development configuration (staging endpoints, validation bypasses) that should be excluded from production builds but is instead wired through default Cargo features and compile-time flags without a verified build-pipeline check that strips them for production artifacts.

### Impact Explanation
If a production build is ever produced without explicitly passing `--no-default-features` (e.g., a CI misconfiguration, a manual `cargo build --release` invocation, or a new build target added without mirroring the exact flag set used by existing `prod` flavour scripts), the resulting orb-core binary would either talk to the staging backend or — in the `skip-user-qr-validation` case — accept any QR code as a valid signup with attacker-controlled/fabricated identity commitment and self-custody keys, entirely bypassing user identity binding and signup authorization. This maps to concrete impact categories of unauthorized/misattributed signup and cross-signup state bleed if such a binary were deployed to a fielded orb.

### Likelihood Explanation
Likelihood depends entirely on the correctness of the out-of-repo (or partially-visible) Nix release pipeline. The `flake.nix` `build` package targets `flavours.prod` and `flavours.stage` separately at `flake.nix:294-301`, suggesting the pipeline is aware of the distinction, but I could not confirm from indexed content that the `prod` flavour build invocation actually passes `--no-default-features` plus an explicit feature allowlist rather than relying on `cargo build --release` alone (which would inherit the crate's `default` features including `stage`). Given the explicit code comment warning that these features are "internal development ONLY," the risk of an accidental default-feature production build is a legitimate configuration-hardening concern, not a purely theoretical one.

### Recommendation
Do not include `stage` (or any debug-only feature) in the crate's `default` feature set; require production builds to be built with `--no-default-features --features "v2_x_x,<explicit prod feature list>"`, and add a build-time or CI assertion (e.g., a `build.rs` check or CI gate) that fails the build if `skip-user-qr-validation`, `stage`, `ui-test-successful-signup`, `no-image-encryption`, `internal-pcp-no-encryption`, or `debug-eye-tracker` are enabled when building the `prod` release artifact. This mirrors the referenced fix pattern of programmatically excluding development configuration from production builds.

### Proof of Concept
1. Run `cargo build --release` (or `cargo build --release --bin orb-core`) without any `--no-default-features`/feature flag overrides from a checkout of this repository.
2. Because `default = ["v2_x_x", "stage"]`, the resulting binary compiles with `stage` enabled, causing `BACKEND` in `src/backend/endpoints.rs` to resolve to the staging backend channel (`"stage.orb"`) unless overridden by environment variable at runtime.
3. Separately, if a build additionally passes `--features skip-user-qr-validation` (e.g., copy-pasted from a dev script), `src/backend/user_status.rs::do_request` under `#[cfg(feature = "skip-user-qr-validation")]` unconditionally returns `Response { valid: true, ... }` with hardcoded `"test"` keys/identity commitment, and the QR/app-data hash verification block at lines 166-179 is compiled out — any QR code presented to the orb is accepted as a fully authenticated signup regardless of actual user or app data.
