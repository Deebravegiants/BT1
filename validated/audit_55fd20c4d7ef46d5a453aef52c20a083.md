### Title
Integer-underflow panic in biometric capture progress computation causes signup pipeline crash (DOS) - (File: `src/plans/biometric_capture/mod.rs`)

### Summary
The Sherlock finding describes an unchecked subtraction (`deposited_value - returnToTreasury - returnToAbond`) that reverts/DOS's the liquidation flow whenever the subtrahend can exceed the minuend due to state that grows monotonically over time (accumulated interest). The closest reachable analog in `orb-core` is the unchecked `usize` subtraction used to compute UI progress during the biometric-capture phase of a signup:

```rust
// src/plans/biometric_capture/mod.rs
let curr_objective_index = self.total_objectives - self.objectives.len() - 1;
``` [1](#0-0) 

### Finding Description
`update_ux` is invoked on every valid IR-Net frame during biometric capture (an unprivileged, user-triggered path — every person who scans a QR code and looks into the Orb reaches this code) to update the on-screen progress bar. `curr_objective_index` is computed as `self.total_objectives - self.objectives.len() - 1`, where `total_objectives` is fixed at plan construction and `self.objectives` is a `VecDeque` that is popped via `set_next_objective` as capture objectives (left/right eye, wavelengths) are completed. This mirrors the CDS-profits pattern: a value that is expected to only shrink over time (`self.objectives.len()`) is subtracted from a fixed baseline (`self.total_objectives`), with an additional flat `-1` term, and the result is used un-checked, exactly like `returnToTreasury`/`returnToAbond` being subtracted from `depositedAmountInETH` without bounds checking.

If `self.objectives.len()` is ever equal to `self.total_objectives` (i.e., the flow reaches `update_ux` before any objective has been popped, e.g., on a spurious/duplicate `handle_ir_net` callback racing with `set_next_objective`, or if `total_objectives` is undercounted relative to the actual number of enqueued objectives for a given wavelength/eye configuration), the subtraction underflows: `total_objectives - total_objectives - 1` wraps below zero. In Rust, this triggers an arithmetic-overflow panic on debug/overflow-checked builds (the same class of "revert" as the Solidity underflow), or produces a huge `usize` on release builds without overflow-checks, which then feeds into `curr_objective_index as f64 / self.total_objectives as f64` for the progress bar and further downstream UI/telemetry — the numeric analog of the huge `cdsProfits` figure in the Solidity report.

### Impact Explanation
A panic in `update_ux`, called from `handle_ir_net` inside the `OrbPlan` trait implementation driven by the Orb broker's message loop, would unwind/abort the task running the biometric-capture plan — halting the in-progress signup for that user (denial of service on the capture/signup pipeline), directly analogous to "Interruption of liquidation type 1 process" in the original report where a legitimate flow (liquidation / signup) is DOSed by an underflow that should never be reachable in the happy path but can be reached given adversarial or edge-case timing of the same inputs that are assumed monotonic.

### Likelihood Explanation
This requires the internal invariant `self.objectives.len() <= self.total_objectives - 1` to be violated at the time `update_ux` runs — this can plausibly happen due to a race between the frame-handling callback (`handle_ir_net`) and `set_next_objective`/objective bookkeeping (e.g., a stale/late frame processed before the first `pop_front` registers, or objectives being re-added for an extended/self-serve capture flow). I could not fully verify the exact temporal invariant between `total_objectives` initialization and the first `update_ux` call within the available tool budget, so likelihood should be treated as moderate/uncertain pending closer review of `Plan::new` and how `objectives`/`total_objectives` are populated for all capture configurations (including internal-data-acquisition and self-serve/extension code paths).

### Recommendation
Replace the raw subtraction with a saturating or checked computation, e.g.:
```rust
let curr_objective_index = self.total_objectives
    .saturating_sub(self.objectives.len())
    .saturating_sub(1);
```
and add a debug assertion (`debug_assert!(self.objectives.len() < self.total_objectives)`) to catch the invariant violation in testing rather than let it manifest as a runtime panic during live signups. More broadly, audit other places using bare `-` on `usize`/counters derived from consumable queues (e.g., other progress-bar computations in `biometric_pipeline/mod.rs`) for the same class of issue.

### Proof of Concept
Not independently reproduced (tool access exhausted before instrumenting `Plan::new`/`set_next_objective` call ordering); the PoC would consist of triggering `handle_ir_net` with a valid, high-scoring frame before the first `set_next_objective` pop takes effect (e.g., via a duplicated/re-ordered agent output) so that `self.objectives.len() == self.total_objectives` when `update_ux` executes, producing the underflow.
