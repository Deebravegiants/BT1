### Title
`messageSigner`/`transactionSigner` public APIs sign with any caller-supplied `walletAccount` without verifying the caller is authorized for that account - ([File: features/tx-signer/src/api/index.ts])

### Summary
The original report describes functions that are unpermissioned: they act on shared/pooled resources using an identifier controlled by the caller, without checking that the caller is entitled to use that specific resource. The closest reachable analog in `hydra` is the `transactionSigner` and `messageSigner` modules/APIs, which accept a `walletAccount` parameter (a plain string name or object) chosen entirely by the caller and use it to select the private key material to sign with — with no check that the calling context is authorized to use that particular account.

### Finding Description
`transactionSignerApi` and `messageSignerApi` are registered as public IoC APIs (`public: true`) and simply forward the caller-supplied parameters straight to the underlying signer module: [1](#0-0) [2](#0-1) 

Internally, `TransactionSigner.signTransaction` and `MessageSigner.signMessage` resolve `walletAccount` (a string is looked up directly in `walletAccountsAtom`, which contains *all* of the user's wallet accounts across all seeds) and then dispatch to the seed-based or hardware signer for that account — with no origin/caller/connection check performed at any point in this call chain: [3](#0-2) [4](#0-3) 

These same signing modules are exactly what perform the private-key operations (via `keychain.signBuffer`/`keychain.exportKey` or hardware device calls), so whoever can invoke these methods with a chosen `walletAccount` gets a valid signature for that account's key: [5](#0-4) 

These modules are reachable across trust boundaries: the SDK exposes its full API surface over RPC bridges intended to cross process/privilege boundaries (background ⇄ UI, or extension ⇄ page), e.g. `@exodus/sdk-rpc` and `@exodus/browser-extension-rpc`, which flatten and expose *all* registered API methods (including `transactionSigner.signTransaction` and `messageSigner.signMessage`) to whatever process holds the other end of the port/transport: [6](#0-5) [7](#0-6) 

Separately, the codebase does maintain a `connected-origins` feature that tracks which origins are `trusted` and which wallet accounts/assets they're allowed to see (`isTrusted`, `getConnectedAccounts`, `isAutoApprove`): [8](#0-7)  However, this authorization logic lives in a separate feature and is not invoked by, or wired into, `transactionSigner`/`messageSigner` themselves — the enforcement (if any) would have to happen in whatever glue code sits between a dApp/web3 provider request and the call into these signer APIs. I was not able to locate that glue code (e.g., the concrete Ethereum/Bitcoin/Solana provider background handler that translates a `eth_sendTransaction`/`personal_sign` request into a `transactionSigner.signTransaction`/`messageSigner.signMessage` call) within the indexed portion of the repo, so I cannot confirm with certainty whether it correctly pins `walletAccount` to the origin's authorized/connected account before calling these APIs, or whether it (or some other RPC consumer) passes through an attacker/caller-influenced `walletAccount`.

### Impact Explanation
If any RPC-reachable caller (a web3 page via the injected provider, or another process connected over `sdk-rpc`/`browser-extension-rpc`) can invoke `transactionSigner.signTransaction` or `messageSigner.signMessage` with an arbitrary `walletAccount` value that is not restricted to the account(s) the caller is authorized for (e.g., not restricted to the origin's connected account per `connectedOrigins`), it could obtain valid signatures for other wallet accounts held by the same Exodus instance (including other seeds' accounts) — directly enabling unauthorized transaction signing / fund movement or message-signing (potential impersonation), which is a wallet-compromise-class impact analogous to the referenced report's "any address can complete the action and steal the resulting funds."

### Likelihood Explanation
This is contingent on how upstream provider/background code decides what `walletAccount` value to pass into these APIs when handling requests from less-trusted callers (content scripts, dApps, or SDK consumers). Since the signer modules themselves perform no such check, likelihood is dependent entirely on whether all call sites correctly restrict `walletAccount` to the authorized account before invoking. Given the number of separate provider integrations (Ethereum, Bitcoin, Algorand, Cardano, etc., per `docs/web3-providers/*`) and multiple RPC bridges reusing the same public API surface, there is realistic risk of an integration point missing this restriction, but I could not confirm a concrete unguarded call site within available context.

### Recommendation
Enforce authorization for `walletAccount` selection at the point where signer APIs are exposed to less-privileged callers: validate that the `walletAccount` requested in `transactionSigner.signTransaction`/`messageSigner.signMessage` matches the account(s) the calling origin/connection is authorized for (via `connectedOrigins.isTrusted`/`getConnectedAccounts`) before dispatching to the underlying signer, rather than relying on callers to only ever request their own account. Ideally, this check should be centralized (e.g., wrapped into the public API layer itself, or into whatever RPC-exposed method set is given to untrusted transports) rather than depend on every provider integration independently doing it correctly.

### Proof of Concept
Not independently reproducible from the indexed code alone — a concrete PoC would require identifying the specific provider/background handler that bridges an untrusted RPC caller (dApp or UI) to `transactionSigner.signTransaction`/`messageSigner.signMessage` and confirming it forwards a caller-controlled `walletAccount` value without cross-checking against `connectedOrigins` authorization. This code path was not found within the indexed context; a Devin session with full repository access would be needed to trace the exact web3-provider handlers (e.g., Ethereum/Bitcoin provider background implementations) and confirm whether `walletAccount` is ever attacker/caller-influenced when reaching these signer APIs.

export const flattenObject = <T>(obj: T, path: string[] = []): { [name: string]: Fn } => {
  if (typeof obj === 'function') {
    return { [serializePath(path)]: obj as Fn }
  }

  if (typeof obj !== 'object' || !obj) return {}

  return Object.keys(obj).reduce((acc, key) => {
    return { ...acc, ...flattenObject(obj[key as keyof T], [...path, key]) }
  }, {})

  /**
   * Returns the connected accounts for a given origin with the active wallet account sorted first. Can be used while
   * the wallet is locked
   */
  getConnectedAccounts = async ({ origin }) => {
    const isTrusted = await this.isTrusted({ origin })
    if (!isTrusted) return []

    const value = await this.#getOrigin({ origin })
    const assetNames = [value.connectedAssetName, ...(value.assetNames ?? [])].filter(
      (name, index, ary) => Boolean(name) && ary.indexOf(name) === index
    )

    const activeWalletAccount = await this.#activeWalletAccountAtom.get()
    const accounts = await this.#connectedAccountsAtom.get()

    const connectedAccounts = []
    for (const name of Object.keys(accounts)) {
      if (name === activeWalletAccount) continue
      connectedAccounts.push({ name, addresses: pick(accounts[name].addresses, assetNames) })
    }

    connectedAccounts.unshift({
      name: activeWalletAccount,
      addresses: pick(accounts[activeWalletAccount].addresses, assetNames),
    })

    return connectedAccounts
  }
