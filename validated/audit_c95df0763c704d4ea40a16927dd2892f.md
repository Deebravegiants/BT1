## Analysis

I focused on the "double conversion" bug-class hint — a field that's checked once but a *different, uncovered* field is trusted afterward — and found a direct analog in the webhook-processing path.

### Root cause

`ShopifyAPI::Webhooks::Request#to_signable_string` returns **only the raw body** — `shop`, `topic`, `webhook_id`, and `api_version` are read straight from HTTP headers and are never included in the signed string: [1](#0-0) 

`Utils::HmacValidator.validate` only verifies that `to_signable_string` (the raw body) matches the received HMAC, computed with the app's shared `api_secret_key`: [2](#0-1) 

`Registry.process` validates the HMAC and then trusts the unauthenticated `request.shop` / `request.topic` headers to route the payload to a handler and to build `WebhookMetadata`: [3](#0-2) 

### Identity binding broken

The equality the code implicitly assumes is:

`hmac_verified(body) == shop_the_body_belongs_to`

But the HMAC only proves `body` was signed with the app's secret — it says nothing about which shop's `shop-domain` header accompanies it. Since the signing secret (`api_secret_key`) is a single **app-wide** secret shared across every installed shop (not per-tenant), any valid `(body, hmac)` pair obtained from a legitimately delivered webhook (e.g., for the attacker's own shop, which they fully control and can trigger events in) remains valid HMAC-wise if replayed with a different `shopify-shop-domain` header value. `HmacValidator.validate` will still pass because it never looks at the `shop` header, and `Registry.process` will then hand `WebhookMetadata` with an attacker-chosen `shop` to the app's handler.

### Impact

An unprivileged app-installing merchant (attacker) can:
1. Install the target app on their own shop and trigger a webhook whose body they control/observe (e.g., a product/order update with attacker-influenced JSON).
2. Capture the `raw_body` + `X-Shopify-Hmac-Sha256` pair Shopify sent to the app's webhook endpoint.
3. Replay the exact same HTTP body/HMAC to the same endpoint, but with `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`) rewritten to a victim shop's domain.
4. `HmacValidator.validate` succeeds (it only checks the body), and `Registry.process` invokes the host app's handler with `shop: victim_shop`, causing the application to process attacker-controlled webhook data as if it originated from the victim tenant — a cross-tenant data-integrity/cross-tenant access issue.

This matches the required impact bar (cross-tenant access) because the gem's own verification API (`HmacValidator.validate` + `Registry.process`) is what fails to bind `shop` to the signed bytes — it is not the host application ignoring documented behavior; the gem's `Request`/`Registry` classes are the code performing (incomplete) verification and dispatch.

### Recommendation

Bind the shop (and topic) into the material that is authenticated before dispatch — e.g., have `Registry.process` cross-check `request.shop` against a shop that is otherwise established as legitimate (such as an installed/active session for that shop), or, at minimum, document/require that host apps treat `shop`/`topic` headers as unauthenticated and always re-derive the target tenant from their own session store rather than trusting `WebhookMetadata#shop` directly, since `HmacValidator` provides no binding for it.

### Title
Webhook `shop`/`topic` headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing via replay - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw body; the `shop-domain`, `topic`, and `webhook-id` headers used downstream by `Registry.process`/`WebhookMetadata` are not part of the HMAC-verified data.

### Finding Description
`HmacValidator.validate` (lib/shopify_api/utils/hmac_validator.rb:26-31) computes/compares the HMAC solely over `Request#to_signable_string`, which returns `@raw_body` only (lib/shopify_api/webhooks/request.rb:36-38). `Registry.process` (lib/shopify_api/webhooks/registry.rb:188-200) validates that HMAC and then trusts `request.shop`/`request.topic`, sourced from HTTP headers with no cryptographic binding to the body or its signature.

### Impact Explanation
Because the signing secret is shared across all shops installing the same app, a valid `(body, hmac)` pair from any one tenant's real webhook remains valid when replayed with a different `shop-domain` header, letting an attacker cause the app to process attacker-influenced webhook payloads under a victim shop's identity — a cross-tenant impact.

### Likelihood Explanation
Requires only that the attacker install the app on their own shop (unprivileged) and be able to send arbitrary HTTP requests to the app's public webhook endpoint — no leaked secret or privileged access is needed.

### Recommendation
Include `shop`/`topic`/`webhook_id` in the signed material, or have `Registry.process` verify the `shop` header against an independently trusted source (e.g. an active session) before dispatching to handlers.

### Proof of Concept
1. Attacker installs app on `attacker.myshopify.com`, triggers a webhook, and captures `raw_body` + `X-Shopify-Hmac-Sha256` from the real Shopify request.
2. Attacker POSTs the same `raw_body`/HMAC to the app's webhook endpoint but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `HmacValidator.validate` returns `true` (body unchanged); `Registry.process` builds `WebhookMetadata` with `shop: "victim.myshopify.com"` and invokes the handler, which acts on victim tenant data using attacker-supplied payload.
