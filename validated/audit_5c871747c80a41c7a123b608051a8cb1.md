### Title
Webhook `shop-domain` Header Not Covered by HMAC Signature Enables Cross-Tenant Webhook Spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw request body only, while the `shop` (tenant) identity used downstream by webhook handlers is read from the `x-shopify-shop-domain` / `shopify-shop-domain` HTTP header, which is never included in the signed payload. Consequently, HMAC validation proves only that "someone with the secret signed this body at some point" — it proves nothing about which shop the body is attributed to. An attacker who can obtain one legitimately-signed `(body, hmac)` pair (trivially available to them for their own store, since Shopify signs webhooks with the app's shared `client_secret` for every shop that installs the app) can replay that exact body/HMAC pair to the app's public webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header value. `HmacValidator.validate` will pass because it only checks the body, and the webhook handler will process attacker-chosen data as if it came from the spoofed shop.

### Finding Description
The relevant binding equality that should hold is:

`shop asserted to the handler` == `shop that Shopify actually authenticated when it computed the HMAC`

In this gem, that equality is broken because the `shop` field is outside the HMAC-covered content: [1](#0-0) [2](#0-1) 

`hmac` is computed from the `hmac-sha256` header, and `to_signable_string` — the only value that `HmacValidator` actually verifies against the secret — is just `@raw_body`. The `shop` accessor pulls straight from the unauthenticated `shop-domain` header: [3](#0-2) 

`HmacValidator.validate` computes `HMAC(secret, to_signable_string)` and compares it to the received `hmac`, without any reference to `shop`: [4](#0-3) 

`Registry.process` trusts this validation and then forwards `request.shop` (the unauthenticated header) straight to the app's registered handler: [5](#0-4) 

Because `shop` is never part of the signed content, an attacker who controls a legitimate installation of the app on any shop (which is all that's required to obtain real, validly-signed `raw_body`/`hmac` pairs for events they trigger themselves, e.g. `orders/create`) can capture such a pair and POST it directly to the app's public webhook endpoint with the `x-shopify-shop-domain` header rewritten to a victim shop's domain. The signature check still succeeds (it only checks the body), and the handler will believe the event originated from the victim shop.

### Impact Explanation
This breaks the tenant/shop identity binding underpinning the webhook trust model, allowing a malicious actor to inject or spoof events attributed to another tenant (cross-tenant data injection/confusion) despite HMAC validation succeeding. Depending on how a host application's webhook handler uses `data.shop` (e.g., to look up records, trigger side effects, or gate per-tenant processing), this can lead to cross-tenant data corruption or unauthorized actions being attributed to/executed against a shop the attacker does not control. This matches the "cross-tenant access" criterion in the impact list.

### Likelihood Explanation
Likelihood is moderate-to-high for any app using this gem's `ShopifyAPI::Webhooks::Registry.process`/`Request` as documented: webhook endpoints are necessarily public HTTP endpoints (Shopify must be able to POST to them from the internet), and any attacker who can install the app on a shop they control (or coordinate with) can generate a valid `(body, hmac)` pair for themselves and then replay it with a forged shop header — no possession of `api_secret_key` or any privileged credential is required beyond normal, unprivileged use of the app as a merchant/installer.

### Recommendation
Include the shop domain (and ideally other identity-relevant metadata such as topic/webhook-id) as part of the HMAC-signable content, or otherwise cryptographically bind the `shop` header value to the signed body before trusting it in `Request#shop`. At minimum, document/enforce that host applications must independently verify that `request.shop` corresponds to a shop with an active, known installation before processing the payload, rather than treating a validated body-HMAC as proof of the shop identity.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a shop they legitimately control).
2. Attacker triggers a webhook-eligible event (e.g., creates an order), causing Shopify to POST to the app's webhook endpoint with headers:
   `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC over raw_body>`, and some `raw_body`.
3. Attacker captures this exact `raw_body` and `x-shopify-hmac-sha256` value (they control the endpoint/network path to their own test infrastructure, or can log it from their own server before forwarding).
4. Attacker re-sends the identical `raw_body` and `x-shopify-hmac-sha256` to the app's public webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Utils::HmacValidator.validate(request)` in `Registry.process` succeeds because it only hashes `raw_body`, which is unchanged.
6. `Registry.process` invokes the registered handler with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com", body: <attacker-controlled parsed body>, ...)`, causing the host application to process attacker-supplied data as an authentic event from `victim-shop.myshopify.com`. [5](#0-4)

          received_signature = verifiable_query.hmac
