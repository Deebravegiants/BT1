Audit Report

## Title
JWT replay guard has a check-then-act race allowing a single JWT to be reused concurrently - ([File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go])

## Summary
`WorkflowMetadataHandler.Authorize` performs the replay check (`h.jwtCache.isReplay(claims.ID)`) and the replay recording (`h.jwtCache.recordUsage(claims.ID)`) as two separate, independently-locked operations rather than one atomic check-and-set, leaving a window where two concurrent requests bearing the same JWT `jti` can both pass the replay check before either records usage. [1](#0-0)  This is in contrast to `vault.RequestReplayGuard.CheckAndRecord`, which correctly performs the check-and-insert under a single lock acquisition. [2](#0-1) 

## Finding Description
`Authorize` calls `isReplay`, which takes `cache.mu.RLock()`, checks for existence of the `jti` key, and releases the lock, then—after performing unrelated workflow ID lookup and signer authorization checks—calls `recordUsage`, which separately acquires `cache.mu.Lock()` to insert the `jti` into the map. [3](#0-2)  Because these two operations are not combined into a single critical section, two goroutines presenting the identical valid JWT can both execute `isReplay` (both observing "not present") before either executes `recordUsage`, so both are authorized. No other check in the `Authorize` path (JWT signature verification, workflow ID lookup, signer authorization) closes this window, since those checks are orthogonal to replay-state and operate on the same claims/signer for both racing requests. [4](#0-3) 

## Impact Explanation
`Authorize` gates access to workflow metadata for HTTP-trigger/gateway clients using JWTs with single-use `jti` semantics. A successful race lets an unprivileged client (or an observer who intercepted a valid JWT) have the same signed token accepted twice concurrently, defeating the anti-replay guarantee. This maps to a gateway request-impersonation/replay-protection-bypass class of issue, though the practical value is limited since it only permits reusing a token the caller already legitimately possesses within its validity window — it does not grant new privileges, only stronger reuse of ones already granted.

## Likelihood Explanation
The race requires firing two requests with an identical JWT nearly simultaneously, which is trivial for a network client to construct and does not require any special privilege beyond possessing one valid, unexpired JWT for a given workflow. The narrow instruction window between `isReplay` and `recordUsage` (spanning a map lookup and two additional in-memory checks) means the race is realistically winnable under concurrent load.

## Recommendation
Merge the check and record steps into a single atomic operation under one lock, mirroring `vault.RequestReplayGuard.CheckAndRecord`: acquire `cache.mu.Lock()` once, check for the `jti`, and if absent, insert it immediately, all before releasing the lock — replacing the separate `isReplay`/`recordUsage` calls in `Authorize` with a single `checkAndRecord`-style method called before (or atomically alongside) the rest of the authorization checks.

## Proof of Concept
1. Obtain a validly signed JWT with a given `jti` for a workflow that is authorized in `authorizedKeys`.
2. Fire two concurrent calls to `WorkflowMetadataHandler.Authorize` with the identical token/`jti`.
3. Because `isReplay` and `recordUsage` are separately locked [3](#0-2) , a Go unit test spawning two goroutines calling `Authorize` with the same token and asserting both return `nil` error (rather than one returning the "already been used" error) demonstrates the race; this can be made deterministic by inserting a short sleep/synchronization point between the `isReplay` and `recordUsage` calls in a test build to reliably interleave the goroutines.

func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
}

func (cache *jwtReplayCache) isReplay(jti string) bool {
	cache.mu.RLock()
	defer cache.mu.RUnlock()

	_, exists := cache.cache[jti]
	return exists
}

func (cache *jwtReplayCache) recordUsage(jti string) {
	cache.mu.Lock()
	defer cache.mu.Unlock()

	cache.cache[jti] = time.Now()
}

func (g *RequestReplayGuard) CheckAndRecord(digest string, expiresAtUnix int64) error {
	g.mu.Lock()
	defer g.mu.Unlock()

	g.clearExpiredLocked()

	if _, exists := g.seen[digest]; exists {
		return ErrRequestAlreadySeen
	}

	g.seen[digest] = expiresAtUnix
	return nil
}
