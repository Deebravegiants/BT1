## Title
Webhook shop/topic identity is not covered by the HMAC signature, allowing cross-tenant webhook forgery — (`File: lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the `X-Shopify-Hmac-Sha256` header against the **raw request body**. The `shop`, `topic`, `webhook-id`, and `api-version` values that the gem uses to route and label the webhook (and that host apps use to decide *which tenant's data* to act on) are read straight from HTTP headers that are **not part of the signed data**. This breaks the identity binding that a caller of this gem would reasonably expect: `hmac verifies == (body, shop, topic)` when in fact `hmac verifies == (body)` only.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`: [1](#0-0) 

`to_signable_string` returns only `@raw_body`; `shop`, `topic`, `api_version`, and `webhook_id` are all pulled from headers via `shopify_header`, entirely outside the HMAC's coverage: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately trusts `request.topic` and `request.shop` (both header-derived, unauthenticated) to select the handler and build the metadata that is handed to the app's business logic: [3](#0-2) 

`HmacValidator.validate` only compares the computed HMAC of `to_signable_string` (i.e. the raw body) against the received signature — it never binds the signature to the `shop` or `topic` header values: [4](#0-3) 

Because a single `Context.api_secret_key` is shared by the app across **all** merchants using it, any unprivileged Shopify merchant who has installed the app on their own store legitimately receives webhook deliveries with a valid `(raw_body, hmac)` pair signed with that same app secret. Since the header fields carrying `shop`, `topic`, `webhook-id`, and `api-version` are not part of the signed material, that merchant can replay the same `raw_body`/`hmac` pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain (and/or altering the topic/webhook-id/api-version headers). `Registry.process` will treat the request as authentic (`Utils::HmacValidator.validate(request)` passes because only the body is checked) and will dispatch `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` to the registered handler with the attacker-chosen `shop` value, even though the actual signer's identity was tied to the attacker's own store.

This equality that a consuming app relies on — "HMAC-authenticated sender" == "shop the code acts on" — does not hold: the gem authenticates only the byte stream of the body, while the shop identity used for routing/dispatch is unauthenticated header data.

### Impact Explanation
This crosses a tenant boundary: an app built on top of this gem that dispatches per-shop side effects from `WebhookMetadata#shop` (e.g., updating merchant records, running `shop/redact`/`customers/redact`/`customers/data_request` mandatory compliance handlers, or any handler keyed by `shop`) can be made to perform those actions attributed to, or targeting, a shop the attacker does not control — using only a webhook delivery the attacker legitimately received for their own store. This matches the "Critical – cross-tenant access" impact category, since the gem's own webhook dispatch (`lib/shopify_api/webhooks/registry.rb`, `lib/shopify_api/webhooks/request.rb`) provides no mechanism to bind the verified body to the claimed shop.

### Likelihood Explanation
Any user of the app (an ordinary, unprivileged merchant who installs the app on their own store) can obtain a valid `(raw_body, hmac)` pair without any elevated access, secrets, or social engineering — it arrives via a normal webhook delivery to their own endpoint/proxy. Replaying it with modified headers requires only the ability to send an HTTP POST to the app's public webhook endpoint, which is by definition internet-reachable and unauthenticated apart from the HMAC. No `api_secret_key`, access token, or privileged account is needed.

### Recommendation
Bind the shop (and ideally topic) identity into the authenticated material, or otherwise verify header-provided shop/topic against a trusted, already-authorized session before dispatching:
- Require `Registry.process` (or its caller) to confirm that `request.shop` corresponds to a shop for which the app already holds a valid, previously-established offline session/access token before invoking the handler.
- Consider including a canonicalized combination of body plus critical headers (`shop`, `topic`, `webhook-id`) in the value that is HMAC-verified, or document explicitly that consumers must independently authenticate the `shop`/`topic` header values before use, since the gem does not currently bind them.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`, which shares the same `Context.api_secret_key` as every other installation of the app.
2. Attacker triggers a webhook delivery to their own endpoint (e.g., updates an order), capturing the raw body `B` and the valid `X-Shopify-Hmac-Sha256: H` header Shopify computed with the app's secret.
3. Attacker crafts a new HTTP POST to the app's webhook endpoint with:
   - `X-Shopify-Hmac-Sha256: H` (unchanged, still valid for body `B`)
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (attacker-chosen)
   - `X-Shopify-Topic:` any topic the attacker wants processed
   - Body: `B` (unchanged)
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `HMAC(B, secret) == H`.
5. The registered handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: <attacker-chosen>, body: parsed(B), ...)` and performs whatever action the host app associates with that shop/topic, despite never having received an authentic signal from `victim-shop.myshopify.com`.
