### Title
Cross-tenant webhook spoofing via unauthenticated `shop-domain` header - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by HMAC-validating the raw request body, then trusts the `shop-domain` header verbatim to attribute the webhook to a tenant. Because the HMAC signable string never includes the shop identity, and the same `api_secret_key` is shared across every shop that installs the app, any two requests with an identical body produce an identical, valid HMAC regardless of which shop the `shop-domain` header claims to be from.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from the `shopify-shop-domain` (or `x-shopify-shop-domain`) header with no cryptographic binding to the body or HMAC: [2](#0-1) 

`HmacValidator.validate`/`validate_signature` compute `HMAC-SHA256(api_secret_key, signable_string)` and compare it to the received `hmac` header — again, only over the body, using the single app-wide secret: [3](#0-2) 

`Registry.process` gates the whole flow on this body-only HMAC check and then hands `request.shop` — the unauthenticated header value — straight to the app's webhook handler as the tenant identity: [4](#0-3) 

The identity binding the code implicitly assumes is:
`HMAC_valid(body, api_secret_key) == request_originated_from(shop_in_header)`

That equality does not hold: `api_secret_key` is a single app-level secret shared by every shop installing the app, and the HMAC covers none of `shop-domain`, `topic`, or `webhook-id`. Consequently:
- Before the attack: shop A legitimately installs the app and triggers events (e.g., creates a product with an attacker-chosen title/body), causing Shopify to deliver a webhook to the app with body `B` and a valid `hmac` computed from `B` and the app's secret.
- The attacker (a normal, unprivileged merchant with only their own shop A installed — no special access, no leaked credentials) captures `(B, hmac)` from their own webhook delivery.
- The attacker then replays `(B, hmac)` to the app's public webhook endpoint, substituting the `shop-domain` header with victim shop B's domain (and, if desired, `webhook-id`/`topic`, which are also unauthenticated).
- `Utils::HmacValidator.validate` still passes because `hmac` was computed correctly for body `B` — it never looked at the shop header.
- `WebhookMetadata` is constructed with `shop: "victim-shop.myshopify.com"` even though the body content was authored/controlled entirely by the attacker on shop A.

This breaks the tenant-authentication boundary: the app now believes attacker-controlled data originated from a shop the attacker does not control, enabling cross-tenant data injection (e.g., fake order/product/GDPR-type events attributed to the victim shop), which can corrupt tenant-scoped records, trigger tenant-scoped side effects (billing, fulfillment automation, customer-data writes), or be used to plant forged data that downstream host-application logic keys off `shop`.

### Impact Explanation
This is a cross-tenant access vulnerability: an attacker who only controls their own (unprivileged) shop installation of the app can make the app process attacker-crafted webhook payloads under a victim shop's identity, since the shop is never part of the HMAC and the secret is shared across all installs. This matches the Critical "cross-tenant access" bucket in the rules.

### Likelihood Explanation
Low-to-moderate likelihood: it requires the attacker to (a) install/operate the target app on their own store (something any merchant can freely do) and (b) know or discover a body value that produces meaningful data on replay against the victim shop-scoped handler logic (host-application dependent). No secret material, TLS interception, or privileged account is needed — only normal use of the app as an unprivileged shop owner and control of raw HTTP requests to the app's public webhook endpoint.

### Recommendation
Bind the shop identity into the authenticated data before trusting it:
- Include `shop-domain` (and ideally `webhook-id`/`topic`) in the HMAC signable string (Shopify-side signing would need to change) — not achievable purely client-side since Shopify controls what it signs. As a mitigation within this gem, `Registry.process` should cross-check `request.shop` against an expected/allow-listed shop (e.g., the shop of the session/installation the webhook route is scoped to) before invoking the handler, and document to consumers that `shop` in `WebhookMetadata` is unauthenticated and must be validated against the app's own shop registry before being trusted for tenant-scoped operations.

### Proof of Concept
```ruby
# Attacker installs the app on their own shop "attacker-shop.myshopify.com"
# and triggers a webhook with attacker-controlled body content, capturing:
body = '{"id": 1, "title": "malicious payload"}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, body)

# Attacker replays the exact same body+hmac, but swaps the shop-domain header
# to the victim shop, which also has the app installed:
forged_headers = {
  "x-shopify-topic" => "products/create",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac),
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # not covered by hmac
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: forged_headers)

# Passes validation because HmacValidator only checks the body:
ShopifyAPI::Webhooks::Registry.process(request)
# => handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...))
# The handler now believes this attacker-authored data came from victim-shop.
