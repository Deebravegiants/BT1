### Title
Webhook shop/topic identity headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its signable content solely from the raw HTTP body [1](#0-0) , while `shop`, `topic`, `webhook_id`, and `api_version` are all read from unauthenticated, unsigned HTTP headers [2](#0-1) . `Registry.process` validates only that the HMAC matches the body, then dispatches the handler using the header-derived `shop` and `topic` values without any binding to the signed content [3](#0-2) .

### Finding Description
The equality the gem should enforce is: `shop/topic/webhook_id authenticated == shop/topic/webhook_id acted upon`. Instead, only `raw_body` is bound by the HMAC:

```ruby
sig { override.returns(String) }
def to_signable_string
  @raw_body
end
``` [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from headers with no cryptographic tie to the HMAC:
```ruby
def topic
  T.cast(shopify_header("topic"), String)
end
def shop
  T.cast(shopify_header("shop-domain"), String)
end
``` [4](#0-3) 

`Registry.process` only checks `Utils::HmacValidator.validate(request)` (which validates the body against the secret) before trusting `request.topic` and `request.shop` to route and label the event that is handed to the app's `WebhookHandler`:
```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
``` [5](#0-4) 

Because `HmacValidator.validate` computes `OpenSSL::HMAC.hexdigest(secret, raw_body)` and compares only that [6](#0-5) , any request carrying a *body* that was legitimately signed by Shopify for one tenant will pass validation regardless of which `shop-domain`/`topic`/`webhook-id` headers accompany it. Since the app treats `data.shop` as the tenant identity for downstream processing (per the documented handler contract, `shop` is "The shop domain of the webhook" [7](#0-6) ), a merchant that legitimately receives real webhooks for their own store (a valid `(body, HMAC)` pair signed with the app's shared secret) can replay that exact body+HMAC to the app's webhook endpoint while substituting the `shopify-shop-domain` (and/or `shopify-topic`, `shopify-webhook-id`) header to name a different shop. The HMAC still validates (it only covers the body), and the handler executes under the attacker-chosen tenant identity with attacker-supplied body content.

### Impact Explanation
This breaks the tenant isolation boundary the HMAC is supposed to guarantee: an unprivileged user who is a legitimate merchant of the app (and therefore possesses at least one genuine `(body, HMAC)` pair for their own store) can inject fabricated webhook events attributed to any other shop, without ever needing the app's `client_secret`. Depending on how the host app consumes `data.shop` (e.g., updating billing state, order records, or triggering `app/uninstalled` cleanup for the named shop), this is a cross-tenant data integrity/confidentiality issue tied to the tenant identity binding. This is a High-severity finding under the cross-tenant access category.

### Likelihood Explanation
Likelihood is moderate-to-high in any multi-tenant deployment of this gem: it requires no special access beyond being a normal, currently-installed merchant of the app (to obtain one valid signed body/HMAC pair from Shopify's own webhook delivery) and only requires modifying an HTTP header value when replaying the request to the app's own public webhook endpoint.

### Recommendation
Include the identity-bearing headers (`shop`, `topic`, `webhook_id`, `api_version`) in the HMAC-signed material, or otherwise cryptographically bind them to the body (e.g., verify `shop` against a per-tenant secret/session, or require re-derivation of `topic`/`shop` from a Shopify-side lookup keyed by `webhook_id` rather than trusting the header verbatim). At minimum, `Request#to_signable_string` should incorporate the same header values that `Registry.process` relies on for routing and tenant attribution.

### Proof of Concept
1. Attacker operates a legitimate shop `attacker.myshopify.com` with the app installed; Shopify sends a real webhook (e.g., `orders/create`) with body `B` and `shopify-hmac-sha256: HMAC(secret, B)`, `shopify-shop-domain: attacker.myshopify.com`.
2. Attacker captures this request and replays it to the same app endpoint, changing only the header `shopify-shop-domain` to `victim.myshopify.com` (and/or `shopify-topic` to a different registered topic).
3. `ShopifyAPI::Webhooks::Request#hmac` still decodes the same valid HMAC from the header; `to_signable_string` returns the unchanged `raw_body` `B` [8](#0-7) .
4. `Utils::HmacValidator.validate` succeeds because it only compares HMAC against `raw_body` [6](#0-5) .
5. `Registry.process` dispatches `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: B, ...)` to the app's handler [9](#0-8) , causing the app to process attacker-supplied content as if it originated from `victim.myshopify.com`.
