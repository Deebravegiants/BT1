### Title
Enrollment signature omits distributor/signup-reason fields, enabling misattributed or fraud-flag-bypassed signups - (File: `src/plans/enroll_user.rs`)

### Summary
The Connext finding shows that a security-critical hash (the diamond-cut proposal ID) is computed over only part of the data that is actually acted upon (`_facetCuts` but not `_init`/`_calldata`), letting an attacker submit different, unauthenticated data alongside a valid-looking commitment. The orb-core signup flow contains the same class of bug: `make_signature` in `src/plans/enroll_user.rs` produces a Secure-Element-backed cryptographic signature over only a subset of the fields that are transmitted in the same signup request, while other security-relevant fields travel unsigned in the same multipart form.

### Finding Description
`make_signature` builds the signed digest from only:
- `ORB_ID`
- `user_qr_code.user_id`
- `pipeline.v2.ir_net_version`, `iris_version`
- both eyes' `iris_code`, `mask_code`, `iris_code_version` [1](#0-0) 

This signature is then submitted to the backend via `signup_post::request` as the `signature` field, but the very same request also carries `distributorId` (the operator's QR `user_id`) and `reason` (the `SignupReason`, e.g. `NORMAL`/`FRAUD`) — neither of which is included in the signed digest: [2](#0-1) 

`SignupReason` explicitly encodes whether the orb itself detected this signup as a fraud attempt, and `distributorId` attributes the signup to a specific operator/referrer: [3](#0-2) 

Because the Secure-Element signature — the one piece of data intended to give the backend a hardware-rooted, tamper-evident attestation of "this iris data, for this user, from this orb, is genuine" — does not bind the `distributorId` or `reason` fields, those two fields can be altered after signing (e.g., by any code path or intermediary between signature computation and the actual HTTP `multipart` submission, or via a malformed/duplicated request replay) without invalidating the signature. Exactly like the Diamond upgrade bug where `_init`/`_calldata` could be swapped out from under an approved hash, here the "approved" (signed) payload can be paired with a different distributor ID or a different fraud-classification tag, and the backend has no cryptographic way to detect the substitution using this signature.

### Impact Explanation
- **Misattributed signup**: `distributorId` can be changed independently of the signature, letting a signup be attributed to a different operator/referrer than the one that actually facilitated it, without breaking signature validity.
- **Fraud-flag bypass**: `reason` (`SignupReason::Fraud`) is excluded from the signed digest, so a signup that the orb classified as a fraud attempt could be resubmitted/altered with `reason = NORMAL` while keeping an otherwise valid, Secure-Element-issued signature over the iris codes — defeating the intent of the fraud-reason tag as an auditable, tamper-resistant signal.
- The impact is amplified because the signature is the one artifact explicitly rooted in the Secure Element (`secure_element::sign`), i.e., the trust anchor the backend is meant to rely on for integrity of this exact class of data. [4](#0-3) 

### Likelihood Explanation
Likelihood is moderate: exploitation requires the ability to alter form fields (`distributorId`, `reason`) after `make_signature` runs but before/during the `signup_post::request` call, or to replay/re-craft a request reusing a captured signature with different values for the unsigned fields. This does not require compromising the Secure Element itself, only interposing on the unsigned portions of the outgoing request — a materially lower bar than forging the signature.

### Recommendation
Include `distributorId` (operator QR `user_id`) and `reason` (`SignupReason`) — along with any other fields in the signup POST that the backend relies on for trust decisions — in the data hashed and signed by `make_signature`, mirroring the Connext fix of covering `_init`/`_calldata` in the proposal hash. Concretely, add:
```rust
ctx.update(operator_qr_code.user_id.as_bytes());
ctx.update(signup_reason.to_screaming_snake_case().as_bytes());
```
to the `Context` in `make_signature`, and thread these parameters through so the backend can verify the full set of security-relevant fields against the Secure-Element signature.

### Proof of Concept
1. Orb captures iris data and computes `signature = make_signature(user_qr_code, pipeline)` — covering only `ORB_ID`, `user_qr_code.user_id`, and iris/mask codes+versions. [1](#0-0) 
2. `signup_post::request` is invoked with this signature plus `operator_qr_code.user_id` (as `distributorId`) and `signup_reason` (as `reason`), neither of which fed into the signature. [2](#0-1) 
3. Any path capable of altering the outgoing form's `distributorId` or `reason` values (independent of the signed iris data) produces a request that still carries a Secure-Element-valid `signature`, yet misattributes the signup to a different operator or masks a `FRAUD`-classified signup as `NORMAL` — with no cryptographic binding to detect the change.

fn make_signature(user_qr_code: &qr_scan::user::Data, pipeline: &Pipeline) -> Result<String> {
    let mut ctx = Context::new(&SHA256);
    ctx.update(ORB_ID.as_str().as_bytes());
    ctx.update(user_qr_code.user_id.as_bytes());
    ctx.update(pipeline.v2.ir_net_version.as_bytes());
    ctx.update(pipeline.v2.iris_version.as_bytes());
    ctx.update(pipeline.v2.eye_left.iris_code.as_bytes());
    ctx.update(pipeline.v2.eye_left.mask_code.as_bytes());
    ctx.update(pipeline.v2.eye_left.iris_code_version.as_bytes());
    ctx.update(pipeline.v2.eye_right.iris_code.as_bytes());
    ctx.update(pipeline.v2.eye_right.mask_code.as_bytes());
    ctx.update(pipeline.v2.eye_right.iris_code_version.as_bytes());
    let signed = secure_element::sign(ctx.finish())?;
    Ok(BASE64.encode(&signed))
}

/// Signs this buffer with Secure Element and returns the output.
#[cfg(not(test))]
pub fn sign<T: AsRef<[u8]>>(data: T) -> Result<Vec<u8>> {
    fn inner(data: &[u8]) -> Result<Vec<u8>> {
        let encoded = BASE64.encode(data);

        tracing::info!("Running orb-sign-iris-code");
        let mut command = Command::new("/usr/bin/orb-sign-iris-code");
        command.stdin(Stdio::piped());
        command.stdout(Stdio::piped());
        command.stderr(Stdio::piped());
        let mut child = command.spawn().wrap_err("running orb-sign-iris-code")?;

        let mut stdin = child.stdin.take().unwrap();
        stdin.write_all(encoded.as_bytes())?;
        drop(stdin);

        let output = child.wait_with_output().wrap_err("waiting for orb-sign-iris-code")?;
        let success = output.status.success();
        for line in String::from_utf8_lossy(&output.stderr).lines() {
            if success {
                tracing::trace!("orb-sign-iris-code {}", line);
            } else {
                tracing::error!("orb-sign-iris-code {}", line);
            }
        }
        if !success {
            if let Some(code) = output.status.code() {
                bail!("orb-sign-iris-code exited with non-zero exit code: {code}");
            } else {
                bail!("orb-sign-iris-code terminated by signal");
            }
        }
        BASE64.decode(&output.stdout).wrap_err("decoding orb-sign-iris-code output")
    }

    inner(data.as_ref())
}
