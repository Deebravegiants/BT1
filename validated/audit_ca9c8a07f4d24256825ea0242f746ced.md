### Title
BandwidthManager governance actions (treasury `Withdraw`, `SetTiers`) reachable by any relayer, missing the relayer-authorization gate applied everywhere else - (File: evm/src/apps/BandwidthManager.sol)

### Summary
`BandwidthManager.onAccept` only restricts the caller to `onlyHost` and checks `request.source` equals hyperbridge, but — unlike every other governance-receiving app in this codebase (`HostManager`, `SimplexPaymaster`, `BridgeToken`, `IntentGatewayV2`) — it never checks `incoming.relayer` against an authorized/admin relayer address. This is the same bug class as the NetAlertX CVE: a sensitive settings/state-mutating entry point (`util.php`'s update-settings actions there; `onAccept`'s `SetTiers`/`Withdraw` here) is reachable without the authorization check the rest of the system enforces for equivalent actions.

### Finding Description
`BandwidthManager.onAccept` gates only on the message's `source` and the `onlyHost` modifier: [1](#0-0) 

Compare this to `HostManager.onAccept`, which layers a second `restrict` on `incoming.relayer` against a designated admin/relayer address in addition to the host and source checks: [2](#0-1) 

The project's own change history documents that this second check was added specifically because omitting it is a security defect: an earlier version of `HostManager.onAccept` "accepted `SetHostParam` from any relayer," and the fix was to require `onAccept` to revert with an unauthorized error "for any other relayer, zero included." [3](#0-2) 

The same relayer-gating pattern was subsequently rolled out to `SimplexPaymaster` and `BridgeToken`'s governance-receiving paths as a deliberate, repository-wide hardening measure: [4](#0-3) 

`BandwidthManager.onAccept`, however, still has only the pre-fix shape: `onlyHost` + `source` equality, and directly executes `Withdraw` (arbitrary ERC20/native transfer to an attacker-influenced-timing beneficiary) and `SetTiers` (price manipulation) without the relayer restriction: [5](#0-4) 

### Impact Explanation
`onAccept`'s `Withdraw` branch moves the full ERC20/native treasury balance held by `BandwidthManager` to whatever `beneficiary`/`amount` the request payload specifies, and `SetTiers` rewrites the tier price table that governs how much buyers pay per bandwidth purchase. Because the relayer-authorization gate that the rest of the codebase now treats as a required control for exactly this action type is absent here, any relayer able to deliver an otherwise-valid ISMP message reaches these fund- and pricing-critical branches, whereas the analogous paths elsewhere require the message to also arrive via the one designated/admin relayer. This is a concrete freezing/fund-handling risk on the module's escrowed fee-token treasury and pricing state.

### Likelihood Explanation
Reaching `onAccept` still requires a genuine ISMP delivery from `pallet-bandwidth` on Hyperbridge through `EvmHost`/`HandlerV2` (the `onlyHost` and `source` checks are intact), so this is not a fully permissionless forgery of the payload's *content*. The gap is specifically the missing relayer restriction that the project has, in every sibling contract, treated as necessary for these classes of governance actions — meaning any of the (permissionless, by ISMP design) relayer set can trigger `Withdraw`/`SetTiers` for `BandwidthManager`, not just the intended privileged relayer, unlike `HostManager`, `SimplexPaymaster`, and `BridgeToken`.

### Recommendation
Add the same relayer-authorization pattern used in `HostManager.onAccept` (a `restrict(incoming.relayer, <authorized relayer address>)` check) to `BandwidthManager.onAccept`, with an admin-settable `_relayer`/`_admin` storage slot analogous to `HostManagerParams.admin`, so `Withdraw` and `SetTiers` can only be delivered by the designated governance relayer.

### Proof of Concept
1. `pallet-bandwidth` on Hyperbridge dispatches a legitimate `Withdraw` or `SetTiers` `PostRequest` to `BandwidthManager` (module id `BWMARKET`).
2. Any relayer (not necessarily the intended/admin relayer) submits the proof to `EvmHost`/`HandlerV2`, which verifies the consensus/state proof and calls `BandwidthManager.onAccept(incoming)`.
3. `onAccept` checks only `onlyHost` and `request.source == hyperbridge()`; it never inspects `incoming.relayer`.
4. The relayer thereby controls exactly when/whether the treasury `Withdraw` or price-changing `SetTiers` action lands — a control HostManager, SimplexPaymaster, and BridgeToken all explicitly deny to arbitrary relayers per their documented fixes: [6](#0-5)

    /// @notice Inbound governance from `pallet-bandwidth`. The first
    /// body byte selects `OnAcceptActions`; the remainder is the
    /// action's ABI-encoded payload.
    /// @dev Only the configured host may invoke (`onlyHost`); the
    /// request's `source` must additionally equal hyperbridge.
    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost {
        PostRequest calldata request = incoming.request;

        if (!request.source.equals(IDispatcher(_host).hyperbridge())) revert UnauthorizedAction();

        OnAcceptActions action = OnAcceptActions(uint8(request.body[0]));
        if (action == OnAcceptActions.SetTiers) {
            Tier[] memory updates = abi.decode(request.body[1:], (Tier[]));
            for (uint256 i = 0; i < updates.length; i++) {
                tierPrice[updates[i].tier] = updates[i].price;
                emit TierSet(updates[i].tier, updates[i].price);
            }
        } else if (action == OnAcceptActions.Withdraw) {
            Withdrawal memory w = abi.decode(request.body[1:], (Withdrawal));
            if (w.token != address(0)) {
                IERC20(w.token).safeTransfer(w.beneficiary, w.amount);
            } else {
                (bool sent,) = w.beneficiary.call{value: w.amount}("");
                if (!sent) revert InsufficientNativeToken();
            }
            emit Withdrawn(w.token, w.beneficiary, w.amount);
        } else {
            revert UnauthorizedAction();
        }
    }

    function onAccept(IncomingPostRequest calldata incoming)
        external
        override
        restrict(msg.sender, _params.host)
        restrict(incoming.relayer, _params.admin)
    {
        PostRequest calldata request = incoming.request;
        // Only the Hyperbridge parachain can send requests to this module.
        if (!request.source.equals(IHost(_params.host).hyperbridge())) revert UnauthorizedAction();

        OnAcceptActions action = OnAcceptActions(uint8(request.body[0]));
        if (action == OnAcceptActions.Withdraw) {
            // This is where governance & relayers can withdraw their revenue.
            WithdrawParams memory withdrawParams = abi.decode(request.body[1:], (WithdrawParams));
            IHostManager(_params.host).withdraw(withdrawParams);
        } else if (action == OnAcceptActions.SetHostParam) {
            HostParams memory hostParams = abi.decode(request.body[1:], (HostParams));
            IHostManager(_params.host).updateHostParams(hostParams);
        } else if (action == OnAcceptActions.SetAdmin) {
            // Rotates the governance relayer.
            address newAdmin = abi.decode(request.body[1:], (address));
            if (newAdmin == address(0)) revert InvalidAdmin();
            emit AdminUpdated({previous: _params.admin, current: newAdmin});
            _params.admin = newAdmin;
        }
    }

# 2026-09-03 — Governance deliveries to `HostManager` gated on the same relayer

Closes the route around the app-level gates: `HostManager.onAccept` accepted `SetHostParam` from
any relayer, and that request can replace the host's handler, the contract every app trusts to
report the relayer address. `HostManager` now holds `_relayer`, set by the host admin through
`setRelayer`, and `onAccept` reverts with `UnauthorizedRelayer` for any other relayer, zero
included. Only governance traffic reaches this contract, so ordinary relaying is unaffected.
No file in this package changed; the entry is here because the delivery flow documented in
`Flow.md` is what it corrects.
