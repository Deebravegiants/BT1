### Title
Webhook shop/topic identity spoofing via unauthenticated HTTP headers not covered by HMAC - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the webhook `shop`, `topic`, `api_version`, and `webhook_id` values from raw HTTP headers, but the HMAC signature that `Utils::HmacValidator` verifies is computed over the request body only. Any actor who can obtain one valid `(body, hmac)` pair signed with the app's shared `api_secret_key` — trivially available to any developer/attacker who installs the app on their own store and receives a real webhook — can replay that pair to the app's public webhook endpoint while freely substituting the `shop-domain` (and `topic`/`webhook-id`) headers. The library's HMAC check passes, and the forged shop identity is handed to the app's webhook handler as authenticated.

### Finding Description
`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` returns only the raw request body: [2](#0-1) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are read straight from HTTP headers that are never included in the signed payload: [3](#0-2) 

`Registry.process` only validates the HMAC before dispatching to the topic handler using the attacker-controlled header values: [4](#0-3) 

Because `api_secret_key` is a single shared secret for the app across every shop that installs it (not a per-shop secret), an attacker who installs the app on their own shop can trigger a genuine webhook delivery, capture the resulting valid `(raw_body, X-Shopify-Hmac-Sha256)` pair, and then POST that same body/HMAC directly to the app's public webhook URL while overriding `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) to name a victim shop. `HmacValidator.validate` will accept it because it only checks the body, and `Registry.process` will invoke the handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain — i.e., the binding "shop authenticated == shop identified" is broken: the HMAC authenticates the body/secret pair but not the shop/topic claims the handler actually acts on.

### Impact Explanation
Downstream apps rely on `WebhookMetadata#shop` (and `#topic`) as an authenticated tenant identifier once `HmacValidator.validate` returns true — that is the entire purpose of webhook HMAC verification. An attacker can forge cross-tenant events (e.g., replay their own `app/uninstalled` or `shop/redact` delivery while claiming it's for a victim shop), causing the host application to perform shop-scoped side effects (deleting stored sessions/access tokens, marking a store uninstalled, processing GDPR redaction, mutating per-shop data) against a shop the attacker does not control. This is a cross-tenant access primitive rooted entirely in this library's identity binding gap.

### Likelihood Explanation
Any internet user can register the target app on a shop they control (many apps offer free installs/trials) to legitimately obtain one valid `(body, hmac)` pair for whichever topic they choose, since `api_secret_key` is shared across all installs of the app. No access token, leaked credential, or privileged access is required — only the ability to send raw HTTP POST requests to the app's public webhook endpoint, which by design must be reachable from the internet.

### Recommendation
Bind the identity-critical headers into the signed material, or otherwise cryptographically tie `shop`, `topic`, and `webhook_id` to the verified payload before trusting them (e.g., include them in `to_signable_string`, or require the caller to independently authenticate that the shop making the delivery matches an installed/authorized session for that shop before acting on webhook data).

### Proof of Concept
1. Attacker installs the target app on their own dev store (`attacker.myshopify.com`) and lets Shopify deliver a real webhook, e.g. topic `carts/update`, to the app's public endpoint. Attacker captures the exact `raw_body` and the `X-Shopify-Hmac-Sha256` header Shopify sent — this pair is valid because it's signed with the app's single shared `api_secret_key`.
2. Attacker crafts a new HTTP POST to the same app endpoint using:
   - Same `raw_body` and `X-Shopify-Hmac-Sha256` value captured above.
   - `X-Shopify-Shop-Domain: victim.myshopify.com`
   - `X-Shopify-Topic: app/uninstalled` (or any registered topic handled by the app)
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Utils::HmacValidator.validate` succeeds because it only recomputes the HMAC of `raw_body`, matching the captured signature (`lib/shopify_api/utils/hmac_validator.rb:26-31`, `lib/shopify_api/webhooks/request.rb:35-38`).
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) dispatches to the app's handler with `WebhookMetadata#shop == "victim.myshopify.com"`, causing the app to perform shop-scoped logic (e.g., revoke/delete stored session data) for a shop the attacker never controls.
