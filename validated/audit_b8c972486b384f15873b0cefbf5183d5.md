### Title
Depositor's slippage protection in `Deposit` is optional and can be bypassed via front-running, causing loss of value to the depositor - (File: program/src/processor.rs, program/src/instruction.rs)

### Summary
The `Deposit` instruction lets a liquidity provider submit an optional `other_amount_min` field to protect against unfavorable pool ratios moving between transaction submission and execution. Because this parameter is an `Option<u64>` that is silently treated as "no protection" when absent (or omitted by the client), an attacker can front-run a depositor's transaction, shift the pool ratio, and cause the depositor to receive fewer LP tokens than expected for their fixed-side contribution, with no revert to protect them — mirroring the wfCash bug where `minImpliedRate` protection could be silently skipped.

### Finding Description
`DepositInstruction` carries `other_amount_min: Option<u64>` [1](#0-0) , and its wire decoding treats missing trailing bytes as `None` rather than requiring an explicit value [2](#0-1) .

In `process_deposit`, the primary check enforces that the computed "other side" deduction does not exceed the user-declared `max_coin_amount`/`max_pc_amount` for the fixed side (`base_side`), which reverts with `ExceededSlippage` if violated [3](#0-2) . However, the LP-minting amount (`mint_lp_amount`) is calculated purely from the ratio of the "fixed" side's deposit amount to the corresponding vault's total (`total_coin_without_take_pnl` or `total_pc_without_take_pnl`) [4](#0-3) . An attacker can front-run the deposit with a swap that shifts the vault totals in a direction that keeps the "max" check passing (deduct amount for the non-fixed side decreases, easily satisfying `max_*_amount`) while simultaneously reducing the effective LP-mint ratio the depositor receives for their fixed-side contribution.

The only guard against this unfavorable ratio manipulation is the `other_amount_min` check, and it is entirely conditional on the option being populated: [5](#0-4) 
If `other_amount_min` is `None` — which is the default in the reference client CLI (`another_min_limit: false`) [6](#0-5)  — no protection is applied at all, exactly analogous to the wfCash report where `minImpliedRate` was bypassed under a specific branch.

### Impact Explanation
A depositor who does not explicitly set (or whose client/wallet omits) `other_amount_min` has zero slippage protection on the "computed" side of their deposit. An attacker who front-runs the depositor's transaction with a swap can force the depositor to receive materially fewer LP tokens for the same locked-in token amount, resulting in a direct, quantifiable loss of value to the depositor and a corresponding gain to the attacker upon reversing the swap (classic liquidity-provision sandwich). This is a loss of user funds via a reachable, single-transaction front-running attack against an unprivileged instruction (`Deposit`), matching the report's impact class.

### Likelihood Explanation
Any attacker can observe a pending `Deposit` transaction in the mempool/leader schedule and submit a preceding swap transaction (`SwapBaseIn`/`SwapBaseOut`) against the same pool with attacker-chosen accounts and amounts, then reverse it after the deposit lands. Because `other_amount_min` is optional and many client integrations default to omitting it (as shown in this repo's own CLI default `another_min_limit: false`), the vulnerable code path is easily and routinely reachable without requiring any misconfiguration beyond normal usage.

### Recommendation
Make the "other side" slippage check mandatory rather than optional in `process_deposit`, or require `other_amount_min` to always be supplied and validated regardless of client input, removing the `Option` semantics that allow the protection to be silently skipped. At minimum, reject deposits where `other_amount_min` is `None` unless the caller explicitly opts out via a clearly documented and audited flag, and update SDK/CLI defaults to always populate this parameter.

### Proof of Concept
1. Attacker observes a pending `Deposit` instruction from Victim with `base_side = 0` (fixed `max_coin_amount`), `max_pc_amount` set generously, and `other_amount_min = None` (client default).
2. Attacker submits a swap (e.g. `SwapBaseIn` swapping PC for Coin) that increases `total_coin_without_take_pnl` in the AMM vault just before Victim's deposit is processed.
3. Victim's `Deposit` executes: `deduct_pc_amount` (computed from the now-inflated coin total) decreases, comfortably passing the `deduct_pc_amount > deposit.max_pc_amount` check at `program/src/processor.rs:1206` [3](#0-2) ; since `other_amount_min` is `None`, the compensating check at lines 1224-1242 is skipped entirely [5](#0-4) .
4. `mint_lp_amount` is computed from `deduct_coin_amount / total_coin_without_take_pnl * amm.lp_amount` [4](#0-3) , which is now lower than it would have been absent the attacker's front-run swap, because `total_coin_without_take_pnl` was inflated.
5. Attacker reverses the swap after Victim's deposit lands, extracting the difference in value from Victim's contribution, with no revert ever triggered.
