### Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes/validates its HMAC over the raw request body only, while the `shop` (and `topic`) values used by host applications to route/act on the webhook are taken from unauthenticated HTTP headers that play no part in the signature. This breaks the identity binding `hmac(payload) == hmac(payload, shop)` that a webhook consumer implicitly relies on: the signature proves the body came from Shopify, but not which shop it belongs to.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#hmac` is derived purely from the `hmac-sha256` header, and `Request#shop` is read directly from the `shop-domain` header without any cryptographic binding to the body or the HMAC: [2](#0-1) 

`Utils::HmacValidator.validate` verifies `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)`, i.e. it only authenticates the raw body bytes, never the shop the caller claims the webhook is for: [3](#0-2) 

Because Shopify computes the webhook HMAC with the app's shared secret over the request body only (independent of destination shop), any entity that receives one legitimate webhook body+HMAC pair for shop A (e.g., a merchant installing the app on their own store, who can trigger webhook events for their own shop) can replay that exact `raw_body` and `hmac-sha256` header to the app's webhook endpoint while substituting an arbitrary `shop-domain` / `x-shopify-shop-domain` header value. `HmacValidator.validate` will still return `true`, because it never inspects `shop`. The host application, following this gem's documented pattern of calling `HmacValidator.validate(request)` then trusting `request.shop` to select the tenant's session/data, will process the event under the attacker-chosen shop, breaking the equality `shop_verified_by_hmac == shop_acted_on`.

### Impact Explanation
This allows an attacker who controls one legitimate webhook payload/signature pair to inject that payload as if it originated from a different, victim shop — cross-tenant data confusion/spoofing (e.g., forging `orders/create`, `app/uninstalled`, or `customers/data_request` events attributed to another tenant). This matches the Critical "cross-tenant access" impact category, since the trust boundary between tenants is defined entirely by the unauthenticated `shop-domain` header.

### Likelihood Explanation
Likelihood is high: no access token, `api_secret_key`, or privileged account is required — only a body+HMAC pair the attacker can legitimately obtain for their own shop (any app installer can trigger such webhooks), plus the ability to POST to the app's public webhook endpoint with a forged header, which is standard unauthenticated internet access.

### Recommendation
Include the shop (and topic) in the signable string / HMAC computation, or otherwise cryptographically bind `shop` to the payload before it reaches consumers, so `HmacValidator.validate` fails when the shop header has been altered relative to the shop the signature was generated for. At minimum, document and enforce that `Request#shop` must never be trusted for tenant routing unless it is independently confirmed against a value covered by the signature.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and captures one webhook delivery: raw body `B` and header `X-Shopify-Hmac-Sha256: H` (valid for the app's secret).
2. Attacker POSTs to the app's webhook endpoint with the same body `B`, same `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. Host code calls `ShopifyAPI::Utils::HmacValidator.validate(request)` per `hmac_validator.rb` lines 12-31 — this passes because it only checks `raw_body` against `H`.
4. Host code then reads `request.shop` (`webhooks/request.rb` lines 20-23), which returns `"victim-shop.myshopify.com"`, and processes the webhook payload as belonging to the victim tenant.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
