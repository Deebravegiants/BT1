## Analysis

The OpenSIPS CVE class is: a codec-processing function crashes (fatal revert) when fed adversarial/malformed input, discovered via fuzzing, and the crash is permanent/reproducible rather than a graceful reject. The closest reachable analog in alt.fun is in the two-phase-graduation LP-seeding math, specifically the hostile-mint-pre-seed rebalance path in `Bonding.sol`.

`Bonding.finalizeGraduation` (permissionless, `packages/contracts/src/Bonding.sol:1000-1034`) drains the cached `pendingGraduation` amounts and calls `_seedUniswapV2Direct` → `_seedRebalancing` when a HyperSwap V2 pair already has non-zero `totalSupply()` (i.e., an attacker pre-minted LP against it), which in turn calls `_pairRebalance` → `_noFeeSwapInput`: [1](#0-0) 

`_noFeeSwapInput` computes `Math.mulDiv(reserveIn * reserveOut, targetN, targetD)` where `reserveIn`/`reserveOut` come directly from the attacker-influenced V2 pair's `uint112` reserves (read in `_seedRebalancing`): [2](#0-1) 

The code's own natspec explicitly flags that this can overflow/revert for adversarial reserve/target combinations rather than degrade gracefully: [3](#0-2) 

This directly contradicts the documented invariant that "Phase 2 must never revert under any pre-seed shape," stated in `packages/contracts/AGENTS.md:86`: [4](#0-3) 

Because `finalizeGraduation` is atomic and the only path that can flip `Lifecycle.Graduating → Graduated`, a revert inside it leaves the token permanently stuck in `Graduating` — trading frozen (`Bonding.buy`/`sell` both revert on `Graduating`, per `TwoPhaseGraduation.t.sol:122-152`), with the curve-raised LT already pulled out of the pair via `Router.graduate` in phase 1, and the 250M `LP_RESERVE` tokens sitting in `Bonding`, with no rescue path (`pendingGraduation` is fixed at phase-1 values and there is no way to recompute or bypass the seeding math): [5](#0-4) 

### Title
Permanent DoS of `finalizeGraduation` via `Math.mulDiv` overflow in the hostile-pre-seed rebalance path freezes curve-raised LT and reserved tokens - (File: `packages/contracts/src/Bonding.sol`)

### Summary
`Bonding.finalizeGraduation` routes through `_seedRebalancing` → `_pairRebalance` → `_noFeeSwapInput` whenever the HyperSwap V2 pair already has non-zero LP supply at graduation time (the "hostile mint pre-seed" regime). `_noFeeSwapInput` computes `Math.mulDiv(reserveIn * reserveOut, targetN, targetD)` using the attacker-controllable `uint112` pair reserves as `reserveIn`/`reserveOut`. For a pre-seed combined with a graduation whose cached `tokensForLP`/`ltFromPair` ratio (`targetN`/`targetD`) is sufficiently skewed (e.g. a low-seed, supply-triggered graduation with a small `ltFromPair` denominator), the intermediate product can exceed `type(uint256).max`, causing `Math.mulDiv` to revert. Because `finalizeGraduation` is atomic and permissionless with no alternative code path or retry-with-different-parameters mechanism, this revert is permanent: the token is stuck forever in `Lifecycle.Graduating`.

### Finding Description
`_seedUniswapV2Direct` (`Bonding.sol:1201-1234`) selects the "regime 3" rebalance branch whenever `IUniswapV2Pair(pair).totalSupply() != 0`, i.e., whenever an attacker has front-run `finalizeGraduation` by creating the HyperSwap pair and calling `pair.mint()` against a self-funded seed. That branch calls `_seedRebalancing`, which reads the pair's live `uint112` reserves and feeds them as `reserveIn`/`reserveOut` into `_pairRebalance` → `_noFeeSwapInput`. `_noFeeSwapInput` multiplies these reserves together with `targetN` (either `ltFromPair` or `tokensForLP`, both fixed by phase 1) and divides by `targetD` (the other cached amount). The natspec at `Bonding.sol:1497-1506` itself documents that "constructed adversarial inputs" that violate the safe-envelope assumption will cause `Math.mulDiv` to revert rather than truncate, calling this "the correct failure mode" — but the surrounding design explicitly commits to "Phase 2 must never revert under any pre-seed shape" (`AGENTS.md:86`) and ships a dedicated brick-resistance regression test suite for exactly this scenario. Once `finalizeGraduation` reverts, `info.lifecycle` remains `Graduating` (only flipped to `Graduated` at line 1027, after the seeding call succeeds), `pendingGraduation[token]` is never cleared, and there is no other entry point to retry with different values — the cached `tokensForLP`/`ltFromPair` from phase 1 are immutable.

### Impact Explanation
A permanently bricked graduation freezes: (a) the real LT raised by the curve, already transferred out of the `Pair` into `Bonding` via `Router.graduate` during `_prepareGraduationLiquidity` (phase 1), and (b) the 250M `LP_RESERVE` tokens held by `Bonding` for LP seeding. Trading is also permanently frozen for that token since `Bonding.buy`/`sell` revert with `TokenIsGraduating` while in this state. This is a concrete, permanent freezing of curve/creator funds with no admin or user recovery path in the current contract set.

### Likelihood Explanation
The attacker must pre-create the HyperSwap V2 pair and `mint()` a self-funded seed of a specific size/ratio before calling (or letting the keeper call) `finalizeGraduation`, targeting a token whose cached `(tokensForLP, ltFromPair)` ratio makes the mulDiv product cross `type(uint256).max`. This is most feasible against tokens that graduate via the supply trigger with a minimal seed (small `ltFromPair`), which maximizes `targetN/targetD` and lowers the reserve magnitude needed to trip the overflow. It requires real capital to seed the V2 pair reserves, but no privileged role — any unprivileged address holding curve-bought tokens and LT can attempt it, satisfying the unprivileged-caller requirement.

### Recommendation
Bound the rebalance-swap computation so it cannot revert on any input: clamp `reserveIn`/`reserveOut`/`targetN`/`targetD` combinations to a safe envelope before the `mulDiv` call (e.g., pre-check the product against `type(uint256).max` and fall back to `_seedDirectMint` — the same fallback already used for the "seed too small" case — instead of letting the arithmetic revert), so the documented brick-resistance guarantee actually holds for every reachable pre-seed shape, not just economically-reasonable ones.

### Proof of Concept
1. Launch a token with the minimum seed (`Zap.createToken` with `usdcAmount = Zap.MIN_SEED_USDC`), buy it out via `Zap.buy` until the supply trigger fires (`IPair.tokenBalance() == 0`), landing `_enterGraduating` with a small `ltFromPair` and `tokensForLP` near `LP_RESERVE`.
2. Before anyone calls `Bonding.finalizeGraduation`, call the HyperSwap V2 factory's `createPair(token, lt)`, then `transfer` large token/LT amounts to the pair and call `pair.mint(attacker)` to set `totalSupply() != 0` with reserves sized so that `reserveIn * reserveOut * targetN / targetD` (as computed in `_noFeeSwapInput`, `Bonding.sol:1517`) exceeds `type(uint256).max`.
3. Call `Bonding.finalizeGraduation(token)`. The call reverts inside `Math.mulDiv`, and because the function is atomic, the token's `Lifecycle` remains `Graduating` permanently — no other call can move it forward, freezing the drained LT and the 250M reserved tokens inside `Bonding`.

```text
    function _noFeeSwapInput(
        uint256 reserveIn,
        uint256 reserveOut,
        uint256 targetN,
        uint256 targetD,
        uint256 maxSwap
    ) internal pure returns (uint256) {
        if (reserveIn == 0 || reserveOut == 0 || targetN == 0 || targetD == 0 || maxSwap == 0) {
            return 0;
        }
        uint256 product = Math.mulDiv(reserveIn * reserveOut, targetN, targetD);
        uint256 newIn = Math.sqrt(product);
        if (newIn <= reserveIn) return 0;
        uint256 s = newIn - reserveIn;
        return s > maxSwap ? maxSwap : s;
    }
```
