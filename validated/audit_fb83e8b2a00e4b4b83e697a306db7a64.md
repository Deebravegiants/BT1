Confirmed: `Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0)  while `shop` is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header, entirely outside the HMAC-covered content [2](#0-1) . `Registry.process` validates only the body's HMAC and then dispatches the handler using the unauthenticated `request.shop` value [3](#0-2) .

### Title
Webhook tenant (shop) identity is not covered by the HMAC in `ShopifyAPI::Webhooks::Request`/`Registry` - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Utils::HmacValidator.validate` authenticates a webhook purely on the raw JSON body, but the shop identity that the application uses to route/tag the handled data (`request.shop`) is taken from an HTTP header that is never included in the signed content.

### Finding Description
`Webhooks::Request#to_signable_string` is defined as `@raw_body` only [1](#0-0) , and `HmacValidator.validate_signature` computes the HMAC exclusively over `verifiable_query.to_signable_string` [4](#0-3) . Meanwhile `Registry.process` extracts `request.shop` (from the `x-shopify-shop-domain` header, see `shopify_header`) and passes it straight into `WebhookMetadata.new(... shop: request.shop ...)` for the handler to act on [3](#0-2) . Because the same `api_secret_key` is shared by every shop that installs the app, any tenant that receives a legitimately HMAC-signed webhook for its own store can capture the `(raw_body, hmac)` pair (which stays valid forever for that body) and replay it to the app's webhook endpoint with the `x-shopify-shop-domain` header rewritten to a victim shop. `Utils::HmacValidator.validate` will accept it, since the header is not part of the signed data, and the handler will process/store the body under the victim shop's identity — breaking the equality "shop authenticated by HMAC" == "shop used by the handler."

### Impact Explanation
This crosses a tenant boundary purely from data controllable by any unprivileged internet user who has installed the app on their own shop (they legitimately receive valid signed webhooks for their own shop and can freely manipulate the header on replay). Depending on the handler implementation supplied by the host app (using the documented `WebhookMetadata#shop`), this can lead to cross-tenant data being attributed to, or acted upon under, another merchant's identity.

### Likelihood Explanation
Medium-to-high: any app that has legitimately onboarded at least one shop can generate valid `(body, hmac)` pairs for arbitrary attacker-chosen body content (e.g. via that shop's own store activity) and then simply swap the shop-domain header value when replaying the request to the app's public webhook endpoint. No secret material is required.

### Recommendation
Bind the shop identity into the signed material, or otherwise cryptographically tie the `shop-domain` header to the specific installation before trusting it — e.g., verify that the shop in the webhook matches a shop with a currently valid/active session in app storage before processing, or include the shop domain in the HMAC computation if Shopify's webhook contract is extended to allow it. At minimum, document/enforce that `WebhookMetadata#shop` must be cross-checked against known installed shops before any tenant-scoped side effect is performed.

### Proof of Concept
1. App is installed on `attacker.myshopify.com`. Attacker triggers any event to receive a legitimate webhook: `raw_body = B`, headers include `x-shopify-hmac-sha256: HMAC(secret, B)` and `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker replays the exact same `raw_body` and `hmac` header to the app's public webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: headers)` parses successfully; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `B` against the shared secret [5](#0-4) .
4. `Registry.process` invokes `handler.handle(data: WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: JSON.parse(B), ...))`, causing the host application to process attacker-controlled data as if it originated from `victim.myshopify.com`.
