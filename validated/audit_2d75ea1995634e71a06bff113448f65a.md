### Title
POA Bridge `describeWithdrawal` matches withdrawals by `assetId` only, causing status/hash misreport for batched same-token withdrawals - ([File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts])

### Summary
`PoaBridge.describeWithdrawal` and the internal-utils `waitForWithdrawalCompletion` both resolve a withdrawal's on-chain status by locating an entry in the POA API's `withdrawals` array whose `near_token_id` matches the caller's `assetId`. There is no disambiguation by index, amount, or destination address. When a single NEAR transaction contains two or more withdrawals of the **same** token (e.g. a batch withdrawal to two different destination addresses/amounts of `nep141:eth.omft.near`), both `WithdrawalIdentifier`s (index 0 and index 1) resolve to the *same* matched withdrawal record via `findMatchingWithdrawal`, since matching ignores `index`/`amount`/`address` entirely.

### Finding Description
`createWithdrawalIdentifiers` (packages/intents-sdk/src/core/withdrawal-watcher.ts:80-107) assigns a per-bridge `index` to each withdrawal in a batch, intending each index to identify one specific ft_withdraw. `PoaBridge.createWithdrawalIdentifier` (poa-bridge.ts:295-311) stores this index in the `WithdrawalIdentifier`, but `describeWithdrawal` (poa-bridge.ts:313-343) never uses `args.index` to pick a specific withdrawal from the API response — it only forwards `args.withdrawalParams.assetId` to `findMatchingWithdrawal`:

```
// packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts:317-322
const withdrawal = findMatchingWithdrawal(
    response.withdrawals,
    args.withdrawalParams.assetId,
);
```

```
// packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts:418-427
function findMatchingWithdrawal(
    withdrawals: WithdrawalStatusResponse["withdrawals"],
    assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
    return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
```

`Array.prototype.find` returns the **first** matching element. If the batch contains two withdrawals of the same `assetId` (same token, different destination address/amount), calling `describeWithdrawal` for index 0 and index 1 both return the identical first match — same `status` and same `transfer_tx_hash`. The equality that should hold — "the status/txHash reported for withdrawal index N equals the on-chain outcome of the N-th ft_withdraw" — is broken: index 1's genuinely pending/failed withdrawal is reported as `completed` with index 0's `txHash`, or vice versa depending on array order (which the code comments admit is "unsorted").

The same defect exists in `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts:144-153`, whose `findMatchingWithdrawal` only matches by `assetId` from `WithdrawalCriteria`, with no index/amount disambiguation, and its own doc comment explicitly states: "This means multiple withdrawals of the same token in a single transaction are not supported."

### Impact Explanation
An integrator using `IntentsSDK.processWithdrawal`/`waitForWithdrawalCompletion` for a batch of withdrawals that includes two or more entries of the same POA-bridged token (e.g., paying two different users the same asset in one NEAR tx, or the docs' explicit RFC around batch withdrawal support) can receive a `completed` status with a `txHash` for the wrong leg of the batch. A relayer/integrator that credits or marks a withdrawal complete based on this misreport can:
- Report the wrong destination transaction hash for a given withdrawal leg (misdelivery bookkeeping / wrong tx attribution).
- Prematurely mark a still-pending or failed withdrawal as completed, or double-credit/duplicate-attribute a single destination tx hash across two logical withdrawals — matching the "status or hash misreport making an integrator credit or refund twice" impact class.

This requires no malicious actor — it is triggered by ordinary batch usage of same-token withdrawals, which the codebase's own RFC (`docs/design/rfc-batch-withdrawal-granular-control.md`) and comments acknowledge as an existing, known gap ("POA API doesn't currently support this case either").

### Likelihood Explanation
Likelihood is moderate: it requires a caller to submit a batch withdrawal containing two or more POA-bridge withdrawals of the same asset in a single NEAR transaction. The SDK's batch withdrawal API (`createWithdrawalCompletionPromises`, `processWithdrawal`) does not prevent or warn against this configuration, and the code path is exercised whenever such a batch occurs. The developers were aware enough to leave a comment describing the limitation, but did not add a guard, so any integrator/SDK consumer performing this legitimate operation triggers the misreport unintentionally.

### Recommendation
Disambiguate `findMatchingWithdrawal` by more than `assetId`:
- Track per-`assetId` occurrence counts in `createWithdrawalIdentifiers`/`WithdrawalIdentifier` (already partially present via the `index` map keyed by `bridge.route`, but not keyed by `assetId`), and have `findMatchingWithdrawal` select the Nth withdrawal matching `assetId` rather than always the first.
- Alternatively, until the POA API exposes a per-request correlation ID, explicitly reject/guard batches containing more than one withdrawal of the same POA-bridge `assetId` in `createWithdrawalIntents`/`processWithdrawal`, surfacing a clear error rather than silently misreporting completion status.
- Apply the same fix to `internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts`'s `findMatchingWithdrawal`.

### Proof of Concept
1. Build a batch withdrawal with two `ft_withdraw` intents for the same `assetId` (`nep141:eth.omft.near`) to different destination addresses/amounts, submitted in one NEAR transaction (tx hash `T`).
2. `createWithdrawalIdentifiers` assigns index 0 and index 1 for the two `PoaBridge` withdrawals (poa-bridge route), both sharing `tx.hash = T`.
3. POA API's `getWithdrawalStatus({ withdrawal_hash: T })` returns two withdrawal records, one `COMPLETED` (tx hash `H1`) and one `PENDING`, in arbitrary order (the code comments confirm the response list is "unsorted").
4. Call `bridge.describeWithdrawal(wid_index0)` and `bridge.describeWithdrawal(wid_index1)` — both invoke `findMatchingWithdrawal(response.withdrawals, "nep141:eth.omft.near")`, which returns the same first-matching record regardless of `index`.
5. Both calls resolve to `{ status: "completed", txHash: H1 }`, even though only one of the two withdrawals actually completed with `H1`; the other is still pending or uses a different destination hash. An integrator relying on `watchWithdrawal`/`waitForWithdrawalCompletion` per-index will incorrectly treat the pending withdrawal as completed and reuse `H1` as its destination tx hash.
