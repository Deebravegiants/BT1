## Title
Webhook Shop/Topic Cross-Tenant Spoofing via HMAC Coverage Gap — (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
The external report's root cause is a shared identity/isolation primitive (a mutex) being reused across two logically distinct objects (the tree and its copy), so an operation authenticated/serialized for one context leaks into the other. The equivalent identity-binding break in this gem is that `ShopifyAPI::Webhooks::Registry.process` authenticates only the webhook **body bytes** via HMAC, while the **shop identity** and **topic** used to route and process the webhook are read from unauthenticated HTTP headers that are never included in the signed payload.

### Finding Description
`ShopifyAPI::Webhooks::Request#hmac` and `#to_signable_string` define what the HMAC actually covers: [1](#0-0) 

Only `@raw_body` is signed. `shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from HTTP headers and are **not** part of `to_signable_string`.

`Registry.process` validates the HMAC and then immediately trusts the unauthenticated `request.shop` and `request.topic` to build the metadata passed to the app's handler: [2](#0-1) 

`Utils::HmacValidator.validate` only proves that `verifiable_query.to_signable_string` (the body) was signed with `Context.api_secret_key`; it says nothing about which header values accompanied that body: [3](#0-2) 

Because the same `client_secret`/`api_secret_key` is used by Shopify to sign webhooks for **every shop that has installed the app**, and the signature covers only the body, a valid `(body, hmac)` pair captured from one installation (e.g., a webhook delivered to the attacker's own store, which the attacker legitimately controls) remains **HMAC-valid** when replayed to the same app endpoint with the `shop-domain` (and `topic`/`webhook-id`) headers swapped to claim a different, victim shop. `Utils::HmacValidator.validate` returns `true` because it never inspected those headers, and `Registry.process` then dispatches the handler with `shop: request.shop` set to the attacker-chosen value.

This is the same equality violation as the report, expressed in this gem's terms:
`shop authenticated (by HMAC) == shop acted upon (WebhookMetadata#shop)` does **not** hold, because the HMAC binds only the body, not the shop field that downstream handler logic uses to select/act on tenant data.

### Impact Explanation
An app's webhook handler typically uses `WebhookMetadata#shop` to decide which merchant's data/session/state to update (e.g., look up that shop's stored session, update local records keyed by shop). By replaying a self-obtained, validly-signed webhook body with a forged `shop-domain` header, an attacker who is a legitimate (if low-privilege) merchant on the app can cause the app to process an event *as if* it came from an arbitrary victim shop — a cross-tenant confusion/spoofing condition. Depending on what the handler does with `shop` (e.g., trigger data sync, cache invalidation, uninstall/reinstall bookkeeping, GDPR flows), this can corrupt or leak another tenant's state, satisfying the "cross-tenant access" Critical impact class.

### Likelihood Explanation
The attacker needs only: (1) their own legitimate install of the app (to obtain a real, HMAC-valid `(body, hmac)` pair, e.g. from an empty-body or generically-structured webhook topic), and (2) the ability to POST to the app's public webhook endpoint with modified headers — both are unprivileged-internet-user-level actions requiring no access to `api_secret_key`, no TLS interception, and no social engineering. The only constraint is finding a webhook body that is identical or acceptable across shops (trivially true for many topics with empty or near-empty JSON bodies, as shown in the test fixtures using `raw_body: "{}"`).

### Recommendation
Include `shop`, `topic`, and any other header fields the handler relies on in the HMAC-signed payload (i.e., extend `to_signable_string` to bind these values), or otherwise cryptographically bind the shop/topic to the signature so that swapping headers invalidates the HMAC. At minimum, document and/or enforce that consumers must not trust `WebhookMetadata#shop`/`#topic` unless they are independently corroborated (e.g., cross-checked against a stored session for that shop before acting).

### Proof of Concept
1. Attacker installs the app on their own shop `attacker.myshopify.com` and receives a legitimate webhook with body `"{}"` and header `shopify-shop-domain: attacker.myshopify.com`, signed with `shopify-hmac-sha256` computed over `"{}"`.
2. Attacker resends the exact same body `"{}"` and `hmac` header to the app's webhook endpoint, but changes `shopify-shop-domain` to `victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: "{}", headers: forged_headers)` is constructed; `Utils::HmacValidator.validate(request)` returns `true` because it only recomputes HMAC over the body `"{}"`, matching the untouched `hmac` header — see [4](#0-3)  and [5](#0-4) .
4. `Registry.process` dispatches the handler with `shop: "victim.myshopify.com"` — see [6](#0-5)  — even though nothing about "victim.myshopify.com" was ever authenticated.
