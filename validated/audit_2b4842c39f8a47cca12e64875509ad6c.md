### Title
Any relayer can be gas-griefed by an attacker-controlled destination module during permissionless POST/timeout dispatch - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.dispatchIncoming(PostRequest, ...)`, `dispatchTimeOut(PostRequestTimeout, ...)`, and `dispatchTimeOut(GetRequestTimeout, ...)` invoke an attacker-influenceable destination/source address via a raw `.call()` that forwards *all* remaining gas, with no gas cap and no try/catch gas isolation. Any relayer who submits a valid proof to `HandlerV2` to deliver a message or timeout triggers this call, and pays for whatever gas the callee consumes before reverting.

### Finding Description
`EvmHost.dispatchIncoming` resolves the destination module from the `PostRequest.to` field (attacker-controlled — it is set by the request's original sender when the request is dispatched from the source chain) and forwards the call with unbounded gas: [1](#0-0) 

The two timeout-dispatch paths follow the identical unmetered `.call()` pattern against `timeout.request.from`, also attacker-controlled: [2](#0-1) [3](#0-2) 

None of these three functions caps the gas forwarded to the external callee (no `{gas: ...}` modifier, no manual gas-budget accounting before the call). This is functionally identical to the reported bug class: a permissionless external call to an address the attacker fully controls, where the callee can consume nearly all forwarded gas and then revert, griefing whoever pays for the enclosing transaction — in the original report the `AutoRange` bot; here, the relayer calling into `HandlerV2`'s request/timeout handling, which is restricted only to `_hostParams.handler` and ultimately triggered by any relayer submitting a membership proof.

An attacker can:
1. Dispatch (or cause to be dispatched) a `PostRequest` whose `to` is a malicious contract they deployed on the destination chain, implementing `onAccept` (or `IApp.onGetTimeout`/`onPostRequestTimeout`) to burn gas down to a small threshold and then `revert`.
2. Wait for a relayer to submit the corresponding proof through `HandlerV2` (`handlePostRequests`/timeout handler), which routes into `EvmHost.dispatchIncoming`/`dispatchTimeOut`.
3. The relayer's transaction pays for all gas consumed inside the malicious callback even though `success == false` causes only a local rollback (receipt deleted so it can be retried) rather than a full transaction revert — the relayer still burns gas with no compensation for that specific message, and the attack can be repeated indefinitely since the request/timeout remains retryable and the attacker's malicious module address is never removed from anything analogous to `positionConfigs`.

### Impact Explanation
Relayers are the entities funding gas for message delivery on Hyperbridge; if their gas cost per relayed message can be inflated arbitrarily by a hostile destination module while the message is simply left "retryable" and never actually completes, relayer profitability is eroded and message delivery for that route can be effectively DoS'd (the messages never get processed, matching the "route unable to deliver messages" impact class). This is a protocol-funds/availability impact analogous to the accepted Medium-severity finding in the source report.

### Likelihood Explanation
The attack is cheap and requires no privilege: any account can deploy a malicious `IApp`-compatible contract and dispatch (or induce dispatch of) messages targeting it as `to`/`from`. It can be repeated indefinitely and scaled by registering many malicious "modules"/addresses, exactly mirroring the original report's repeatability concern.

### Recommendation
- Forward a fixed, bounded gas stipend to the external module call (e.g., `.call{gas: CALLBACK_GAS_LIMIT}(...)`) in `dispatchIncoming` and both `dispatchTimeOut` overloads in `EvmHost.sol`.
- Consider explicitly checking `gasleft()` before/after the call and charging any excess consumption against the message's fee/deposit, or reverting the whole batch item deterministically instead of silently marking it retryable, so a malicious module cannot repeatedly consume relayer gas for free.
- Document/enforce a maximum gas budget per module callback as part of the relayer fee accounting so the fee compensates for worst-case gas consumption.

### Proof of Concept
1. Deploy `MaliciousApp` implementing `IApp.onAccept`/`onGetTimeout`/`onPostRequestTimeout` that loops until `gasleft()` is near zero, then reverts.
2. Dispatch a `PostRequest` (or induce a timeout) with `to`/`from` set to `MaliciousApp`.
3. Have a relayer submit the corresponding proof through `HandlerV2`, which calls `EvmHost.dispatchIncoming`/`dispatchTimeOut`.
4. Observe the relayer's transaction consumes gas up to the block/callframe limit inside the unmetered `.call()` at [4](#0-3) , `success` returns `false`, the receipt is deleted for retry, and the attack can be repeated on the same or new malicious contracts indefinitely.

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }

    function dispatchTimeOut(
        GetRequestTimeout memory timeout,
        FeeMetadata memory meta,
        bytes32 commitment
    ) external restrict(_hostParams.handler) {
        // replay protection
        delete _requestCommitments[commitment];
        (bool success,) = _bytesToAddress(timeout.request.from)
            .call(abi.encodeWithSelector(IApp.onGetTimeout.selector, timeout));

        if (!success) {
            // so that it can be retried
            _requestCommitments[commitment] = meta;
            return;
        }

        if (meta.fee != 0) {
            // refund relayer fee
            IERC20(feeToken()).safeTransfer(meta.sender, meta.fee);
        }
        emit GetRequestTimeoutHandled({commitment: commitment, dest: string(timeout.request.dest)});
    }
