### Title
Webhook shop/topic identity fields are not covered by the HMAC signature, enabling cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while the `shop`, `topic`, `webhook_id`, and `api_version` fields — all taken from unauthenticated HTTP headers — are used unverified by `Registry.process` to route and identify the tenant for the incoming webhook. Because a single app-level `client_secret` is used to sign webhooks for *every* shop that installs the app, an attacker who controls their own legitimate installation can capture a valid `(body, hmac)` pair and replay it against the app's webhook endpoint while spoofing the `X-Shopify-Shop-Domain` header to impersonate a victim shop.

### Finding Description
`Utils::HmacValidator.validate` computes the signature only over `verifiable_query.to_signable_string`: [1](#0-0) 

For webhook requests, `to_signable_string` is defined to return solely the raw body, deliberately excluding the shop/topic/webhook-id/api-version headers: [2](#0-1) 

`Registry.process` validates the HMAC and then dispatches directly using `request.shop`, `request.topic`, etc., which were never part of the signed material: [3](#0-2) 

The identity binding the protocol needs is: `HMAC(secret, body+shop+topic) == received_hmac` for the specific `(shop, topic)` pair that the app will trust. What the library actually enforces is only `HMAC(secret, body) == received_hmac`, with `shop`/`topic` accepted as unauthenticated header values. Because Shopify signs webhooks with the single `client_secret` configured for the *app* (not a per-shop secret), the same secret produces valid signatures for identical bodies regardless of which shop originated them. An attacker who has installed the app on their own store (a fully legitimate, low-privilege action) can trigger a webhook with attacker-chosen body content, capture the resulting valid `(body, hmac)` pair, then replay that exact HTTP request to the app's webhook endpoint with the `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`) header rewritten to name a victim shop. `HmacValidator.validate` still succeeds because it never looks at those headers, and `Registry.process` hands the forged `shop` straight to the app's handler as authoritative tenant identity.

### Impact Explanation
This breaks the tenant/authentication boundary the webhook mechanism is supposed to provide: the app's webhook handler receives data it will treat as originating from a specific merchant (`shop`), but that value carries no cryptographic assurance. An attacker can inject data, fire `orders/create`-style events, or trigger any handler logic (e.g., app-uninstall cleanup, billing state changes, GDPR data flows) under the identity of an arbitrary victim shop domain, without any credential belonging to that victim. This constitutes cross-tenant access/data injection into the merchant's account context solely by using an attacker-controlled install of the same app.

### Likelihood Explanation
Exploitation requires only that the attacker install the target app on a store they control (something any unprivileged internet user can do) and observe one webhook delivery — no access token, API key, or `client_secret` disclosure is needed. This is a low-effort, realistic attack path exercised entirely through headers the gem intentionally leaves outside the signed payload.

### Recommendation
Include the shop domain (and ideally topic) in the HMAC-signed material, or otherwise cryptographically bind the routed `shop`/`topic` values to the signature (e.g., derive them only from a verified source, or require the app to cross-check `request.shop` against a known-installed-shop list before trusting it). At minimum, document prominently that `request.shop`/`request.topic` are unauthenticated and must not be used as a tenant-identity boundary without additional verification.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`.
2. Attacker triggers a webhook (e.g., by modifying an order) and captures the raw POST body `B` and its `X-Shopify-Hmac-Sha256` header value `H` — valid because `H = HMAC(client_secret, B)`.
3. Attacker replays the exact same body `B` and header `H` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {..., "x-shopify-shop-domain" => "victim.myshopify.com", "x-shopify-hmac-sha256" => H})` is constructed.
5. `Utils::HmacValidator.validate(request)` succeeds because `to_signable_string` only hashes `B` (see `lib/shopify_api/webhooks/request.rb:35-38` and `lib/shopify_api/utils/hmac_validator.rb:26-31`).
6. `Registry.process(request)` invokes the app's registered handler with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)` (`lib/shopify_api/webhooks/registry.rb:188-200`), causing the app to process attacker-controlled data as if it came from the victim shop.
