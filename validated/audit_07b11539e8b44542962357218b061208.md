Based on my analysis, I found a genuine identity-binding flaw in the non-embedded session cookie mechanism.Confirmed. This is sufficient to write up the finding.

### Title
Non-embedded app session cookie value is a predictable, unsigned identifier, enabling cross-tenant session hijacking - ([File: lib/shopify_api/utils/session_utils.rb], [File: lib/shopify_api/auth/session.rb], [File: lib/shopify_api/auth/oauth.rb])

### Summary
For non-embedded apps, the gem's documented cookie-based session mechanism sets the browser's session cookie to the raw value of `Session#id`. For offline sessions, that value is computed as the deterministic, publicly-derivable string `"offline_#{shop}"` — no signature, HMAC, or any other proof of a completed OAuth flow is attached. `SessionUtils.cookie_session_id` then trusts this cookie value verbatim as "the current session id" used to look up the stored access token. Because the identifier is not cryptographically bound to an authenticated OAuth completion, any unprivileged internet user who merely knows a shop's public `myshopify.com` domain can construct this exact cookie value and impersonate that shop's offline session in the host application, achieving cross-tenant access to the merchant's stored access token/session.

### Finding Description
The intended identity binding is:
`session_cookie_value == proof that *this browser* completed OAuth for *this specific shop*`

What the gem actually implements is:
`session_cookie_value == "offline_#{shop}"` — a value that depends only on public information (the shop domain) and carries no authentication.

Walking through the code:

1. `Session.from` computes the session `id` for offline sessions as simply `"offline_#{shop}"`, with no random or secret component: [1](#0-0) 

2. After a successful OAuth callback, for non-embedded apps, `Oauth.validate_auth_callback` sets the browser session cookie's `value` directly to `session.id`: [2](#0-1) 

3. `SessionCookie` is a plain value struct with no signing/HMAC of its `value`: [3](#0-2) 

4. On every subsequent request, `SessionUtils.cookie_session_id` reads this cookie value with **no verification whatsoever** and returns it as the trusted "current session id": [4](#0-3) [5](#0-4) 

The documentation confirms this is the officially supported, intended mechanism for non-embedded apps (as opposed to the JWT-based mechanism for embedded apps, where the ID is cryptographically derived from a signed token): [6](#0-5) 

Because host applications are expected to take the string returned by `current_session_id`/`cookie_session_id` and use it as a key to fetch the stored `Session` (and its `access_token`) from their session storage — exactly as this gem's own docs instruct — this string is effectively treated as an authentication credential. Yet it is generated from, and can be regenerated by anyone from, purely public data (the shop's domain name), with zero cryptographic binding to a real, completed OAuth handshake.

### Impact Explanation
This breaks the tenant-isolation boundary between merchants. Any unprivileged internet user who knows (or guesses/enumerates) a target shop's domain — trivially discoverable, since `{shop}.myshopify.com` is public — can set/send a cookie `shopify_app_session=offline_{shop}` to the host application. If that shop has ever completed offline OAuth with the app (an extremely common state for any installed app), the host application's session-lookup layer, following this gem's documented contract, will resolve this attacker-supplied identifier to the victim shop's real stored offline access token and use it to serve subsequent Admin API requests — i.e., cross-tenant access to another merchant's authenticated session/access token without ever performing OAuth. This satisfies the Critical impact bar (cross-tenant access to a merchant's access token) defined for this assessment.

### Likelihood Explanation
Likelihood is high: no secret material, interception, or social engineering is required. The attacker only needs the target's public shop domain and the fixed, well-known cookie name (`shopify_app_session`, a public constant in this gem). Any app built following this gem's documented cookie-session pattern for non-embedded flows is affected by construction, since the vulnerable identifier-generation logic lives entirely inside this gem (`Session.from`, `Oauth.validate_auth_callback`, `SessionUtils.cookie_session_id`), not in host-application code that the gem's documentation asks apps to write differently.

### Recommendation
Do not use a deterministic, publicly-derivable string (`"offline_#{shop}"` / `"#{shop}_#{user_id}"`) as the value placed directly in an unauthenticated browser cookie. Instead:
- Generate the session cookie value as a cryptographically random, unguessable token (e.g., `SecureRandom.uuid`/`SecureRandom.hex`) that is unrelated to the shop domain, and use that random token purely as an opaque lookup key into server-side session storage, or
- Sign/HMAC the cookie value (similar to how `HmacValidator`/`JwtPayload` already authenticate other flows in this gem) so that its authenticity can be verified before it is trusted as a session identifier, and reject values that fail verification in `SessionUtils.cookie_session_id`.

### Proof of Concept
1. Note that Shop `victim-shop.myshopify.com` has previously installed and authorized the target app for offline access (a normal, common occurrence).
2. As an unrelated, unprivileged attacker (no credentials, no prior interaction with the victim), send a request to the host application with header:
   `Cookie: shopify_app_session=offline_victim-shop.myshopify.com`
3. The host application, following this gem's documented pattern, calls `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)`, which returns `"offline_victim-shop.myshopify.com"` verbatim via `cookie_session_id` — with no cryptographic check. [7](#0-6) 
4. The host application uses this attacker-controlled string to look up and load the victim shop's stored `Session` (including its real `access_token`), and proceeds to serve/authorize Admin API calls under that session — granting the attacker cross-tenant access to `victim-shop`'s data using its stolen-in-spirit (but never actually stolen — merely guessed) offline access token context.
