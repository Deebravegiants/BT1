### Title
Non-embedded (and un-authenticated-fallback) `current_session_id` trusts a deterministic, unsigned cookie value as the session identity - (`lib/shopify_api/utils/session_utils.rb`)

### Summary
`SessionUtils.current_session_id` derives the "authenticated" identity for non-embedded apps — and for embedded apps when no `shopify_id_token` is supplied — purely from the raw `shopify_app_session` cookie value, with zero cryptographic verification. That cookie's value is not a random secret: for offline sessions it is minted as the deterministic, publicly-guessable string `"offline_#{shop}"`, identical to what `SessionUtils.offline_session_id` computes from a verified JWT. An attacker who merely knows a victim's `.myshopify.com` domain can send their own request with `Cookie: shopify_app_session=offline_<victim>.myshopify.com` and no `Authorization` header, and `current_session_id` will hand back exactly the victim's real offline session id.

### Finding Description
The claimed binding is: `session_id_returned_by_current_session_id == session_id_of_the_party_that_is_cryptographically_authenticated_on_this_request`. This holds on the JWT branch (verified via `Auth::JwtPayload`), but breaks on the cookie branch.

`current_session_id` has three branches [1](#0-0) :
- Embedded + token present → identity comes from a verified JWT (`Auth::JwtPayload.new(id_token)`), signature-checked.
- Embedded + no token → falls back to `cookie_session_id(cookies)`.
- Non-embedded → **always** uses `cookie_session_id(cookies)`.

`cookie_session_id` performs no validation whatsoever — it just returns the raw cookie value [2](#0-1) .

The cookie's value is not opaque/random. It is set during `Oauth.validate_auth_callback` to `session.id` directly [3](#0-2) , and `session.id` for an offline session is deterministically `"offline_#{shop}"` [4](#0-3) , which is byte-for-byte what `SessionUtils.offline_session_id` computes from a verified token [5](#0-4) . Nothing signs or binds this cookie to the presenter; it carries no HMAC, no nonce beyond the shop name itself, and `shop` is public information (every merchant's `*.myshopify.com` handle is visible in the storefront URL).

Exploit flow: an attacker who has never installed the app, never completed OAuth, and holds no secret sends `GET /any-authenticated-route` to the target host app with header `Cookie: shopify_app_session=offline_<victim>.myshopify.com` and omits `Authorization`. If the app is non-embedded, this is the *only* code path (`current_session_id` never even asks for a token). If the app is embedded but the request lacks a session token (e.g., a legacy/back-compat surface, non-App-Bridge fetch, or any handler that calls `current_session_id(nil, cookies, false)`), the same fallback fires. `current_session_id` returns `"offline_<victim>.myshopify.com"` to the host app, which (per this gem's documented usage pattern) uses that string to load the victim's persisted `Session` from `SessionStorage` — a `Session` carrying the merchant's real `access_token` — and then serves the attacker's request as that merchant, attaching the merchant's `X-Shopify-Access-Token` to outbound Admin API calls.

Existing guards do not catch this: `HmacValidator.validate` and `ShopValidator.sanitize!` only run during the OAuth callback and REST/webhook verification paths, not on `current_session_id`; the `state` comparison in `validate_auth_callback` only protects the OAuth handshake itself, not later use of the resulting cookie as a bearer identifier; `JwtPayload`'s `aud` check never runs because no token is presented; `Context.embedded?` only decides *whether* the cookie fallback is reached, it does not validate the cookie's contents. Sorbet typing only enforces that `cookies` is a `String` hash — it does not enforce provenance or integrity.

### Impact Explanation
Any unprivileged internet attacker who knows (or brute-forces) a target merchant's `.myshopify.com` domain can cause a vulnerable host app to authenticate the attacker's request as that merchant's offline session, exposing/using the merchant's Admin API access token (`X-Shopify-Access-Token`) on the attacker's behalf. This is repeatable against any merchant whose shop domain is known and works cross-tenant with no per-victim secret required — matching Critical: theft of a merchant's Admin API access token / cross-tenant access.

### Likelihood Explanation
Preconditions: the host app must be non-embedded (the documented, supported cookie-auth mode per `docs/getting_started.md`), or an embedded app must have a code path that calls `current_session_id` without first requiring an `Authorization`/`id_token`. Attacker cost is a single crafted HTTP request with a guessable cookie value — no OAuth flow, no HMAC, no JWT, no secret required. This is highly feasible and trivially repeatable against arbitrary victims for the non-embedded, offline-session case, since the cookie value is fully deterministic from public information.

### Recommendation
Never use a bare, predictable session id as the sole bearer credential in a cookie. Bind the cookie to the authenticated OAuth transaction with an HMAC/signed token (as already done for JWT/`AuthQuery`) or store only a high-entropy random session-cookie value distinct from `session.id`, verifying it server-side before treating it as authenticated. At minimum, `SessionUtils.cookie_session_id`/`current_session_id` should require the cookie to be cryptographically verifiable, not merely present.

### Proof of Concept
```ruby
# test/utils/session_utils_test.rb (new test)
def test_cookie_session_id_accepts_forged_offline_session_id_without_any_verification
  victim_shop = "victim-shop.myshopify.com"
  forged_session_id = "offline_#{victim_shop}" # == SessionUtils.offline_session_id(victim_shop)

  ShopifyAPI::Context.stubs(:embedded?).returns(false)
  cookies = { ShopifyAPI::Auth::Oauth::SessionCookie::SESSION_COOKIE_NAME => forged_session_id }

  # Binding under test: returned id equals victim's real offline session id,
  # with no HMAC/JWT/state verification performed anywhere in this call.
  result = ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)

  assert_equal(ShopifyAPI::Utils::SessionUtils.offline_session_id(victim_shop), result)
end
```
This demonstrates that `current_session_id`/`cookie_session_id` return the attacker-supplied, deterministically-guessable value verbatim, proving the value that would be verified (the JWT-derived id) is never what gates this path — only the raw cookie is used, with no signature check anywhere in `lib/shopify_api/utils/session_utils.rb`.
