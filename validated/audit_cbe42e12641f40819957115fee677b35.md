### Title
Webhook `shop`/`topic` identity fields are not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` extracts the tenant-identifying `shop` (and `topic`) values from unauthenticated HTTP headers, but `Utils::HmacValidator` only verifies the HMAC over the raw request body. Any party that can obtain one genuinely-signed webhook body (trivially achievable by installing the target app on their own, attacker-controlled shop) can replay that body while spoofing the `shop-domain` header to name a victim merchant, and the request still passes `HmacValidator.validate`.

### Finding Description
The `VerifiableQuery` contract requires implementers to provide `to_signable_string`, which is the exact byte string signed/verified by `Utils::HmacValidator`: [1](#0-0) 

For OAuth's `AuthQuery`, the `shop` field is explicitly included in `to_signable_string`, so it is bound by the HMAC: [2](#0-1) 

For `Webhooks::Request`, however, `to_signable_string` returns only the raw body — none of the Shopify-supplied headers (`shop`, `topic`, `webhook_id`, `api_version`) are included: [3](#0-2) 

`Registry.process` validates the webhook exclusively via this HMAC check and then dispatches the handler using `request.topic` and `request.shop` taken straight from headers, without any additional binding: [4](#0-3) 

The equality that should hold is: `shop_authenticated_by_hmac == shop_used_to_key_tenant_data`. Here, `shop` used for tenant dispatch (`WebhookMetadata.shop`) is never part of the signed bytes, so the binding is broken: the HMAC only proves "this body came from Shopify for *some* shop that has this app installed," not "this body belongs to *this* shop."

### Impact Explanation
An unprivileged internet user who can install the app on any shop (including a free/test store they control, which is the normal, unauthenticated installation flow for any public app) can:
1. Trigger a real webhook event on their own shop, capturing a genuinely Shopify-signed raw body + valid `X-Shopify-Hmac-Sha256`.
2. Replay that exact raw body to the merchant's webhook endpoint, substituting `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`) with a victim merchant's domain/topic.
3. `HmacValidator.validate` still succeeds because only the body bytes are checked.
4. The host application's handler receives `WebhookMetadata` claiming the victim shop as the source, causing attacker-controlled data to be processed/stored under the victim tenant's identity — a cross-tenant data injection.

This matches the report's core bug class: a field (`shop`) that is acted upon (used as the tenant key for dispatch) is not covered by the cryptographic check that is supposed to authenticate the request.

### Likelihood Explanation
Any developer or attacker can install a public Shopify app for free on a shop they own, obtain a legitimately-signed webhook, and replay it with a forged shop-domain header against the target app's public webhook endpoint. No secrets, tokens, or privileged access to the victim's store are required — only network access to the app's webhook receiver, which is Internet-reachable by design.

### Recommendation
Include the `shop` (and ideally `topic`) values as part of the signed/verified payload for webhooks, or independently verify that the `shop` header matches an expected, already-authorized shop before trusting it (e.g., cross-check the shop-domain header against the actual HMAC-protected content of the payload, or require the host app to look up an active session/installation record for that shop and reject if the raw body's shop-scoped resource does not correlate). At minimum, document clearly that `request.shop` is unauthenticated and must not be trusted for tenant dispatch without additional verification.

### Proof of Concept
```ruby
# Attacker owns shop "attacker.myshopify.com" with the target app installed.
# Shopify sends a legitimate webhook:
raw_body = '{"id":123,"note":"legit data from attacker shop"}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), APP_SECRET, raw_body)

# Attacker replays the identical body/hmac but swaps the shop-domain header:
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac), # unchanged, still valid
  "x-shopify-shop-domain" => "victim.myshopify.com", # spoofed
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate succeeds (only raw_body is checked),
#    handler.handle receives WebhookMetadata(shop: "victim.myshopify.com", body: attacker's data)
```
