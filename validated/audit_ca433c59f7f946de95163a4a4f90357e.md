### Title
Webhook `shop-domain` is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw body only, while the `shop` (tenant identifier) is read from a separate, unauthenticated header. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then hands `request.shop` straight to the host application's webhook handler as the trusted tenant identifier, without binding it to the signature.

### Finding Description
`Webhooks::Request#to_signable_string` returns only the raw request body: [1](#0-0) 

`Webhooks::Request#shop` is derived purely from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, which is not part of the signable string at all: [2](#0-1) 

`Utils::HmacValidator.validate` computes and compares the HMAC exclusively over `verifiable_query.to_signable_string` (the body), never over `shop`: [3](#0-2) 

`Webhooks::Registry.process` validates only that HMAC, then immediately trusts `request.shop` to build `WebhookMetadata` passed to the app's handler as the authoritative tenant identifier: [4](#0-3) 

The equality the code implicitly assumes but does not enforce is:
`shop header value == shop that the HMAC-signed body actually originated from`

Because the `shop` header is excluded from the signed bytes, any two webhook deliveries with the *same body* (e.g., identical JSON payload, which is trivial to produce — for example an empty body `{}` or any payload an attacker can trigger on their own store) will produce the *same valid HMAC*, regardless of which `shop-domain` header accompanies the request. An attacker who has installed the app on their own store (an ordinary, unprivileged Shopify merchant relative to the app's trust boundary) can:
1. Trigger a webhook delivery to their app endpoint for their own shop and capture the `(raw_body, hmac)` pair that Shopify signs with the app's shared `api_secret_key`.
2. Replay that exact `raw_body` to the app's webhook endpoint, but substitute the `x-shopify-shop-domain` header with a victim shop's domain.
3. `HmacValidator.validate` passes (body + hmac are unchanged and valid), and `Registry.process` calls the handler with `WebhookMetadata#shop` set to the victim's domain.

If the host application uses `data.shop` from `WebhookMetadata` to look up the tenant's session/store record (which is the documented and expected usage pattern), the attacker can inject data attributed to, or trigger tenant-scoped side effects for, a shop they do not control — a cross-tenant confusion enabled purely by this gem's HMAC scope.

### Impact Explanation
This breaks the tenant-identity binding that webhook consumers rely on: the HMAC is meant to prove "this payload, for this shop, genuinely came from Shopify for this app," but the implementation only proves "this payload came from Shopify for this app" — the shop attribution is unauthenticated. Any downstream logic in the host app that trusts `WebhookMetadata#shop` (session lookup, data writes, entitlement checks) can be fed an attacker-chosen tenant identifier, resulting in cross-tenant access/impersonation, which matches the Critical impact bar (cross-tenant access).

### Likelihood Explanation
Likelihood is high for any app that has at least one attacker-controlled installation (a competitor, or anyone able to install a public app on their own store) and where webhook bodies can be made deterministic/predictable (many topics, e.g. `app/uninstalled`, or topics with attacker-controlled content, produce reproducible bodies). No knowledge of `api_secret_key` is required — only replay of previously observed, validly-signed traffic with a swapped header.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `webhook-id`, `api-version`) header values in the HMAC-signable string, or otherwise cryptographically bind them to the payload before comparison, so that `Utils::HmacValidator.validate` fails if the shop header does not match the shop the signature was actually generated for.

### Proof of Concept
```ruby
# Attacker owns "attacker-shop.myshopify.com" and has the app installed there.
# Step 1: attacker triggers/captures a real webhook delivery for their own shop:
raw_body = "{}"
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)
encoded_hmac = Base64.encode64(hmac)
# (This is exactly what Shopify sends the attacker's own endpoint for shop A.)

# Step 2: attacker replays the same raw_body + hmac to the target app's webhook
# endpoint, but swaps the shop-domain header to the victim shop:
forged_headers = {
  "x-shopify-topic"        => "orders/create",
  "x-shopify-hmac-sha256"  => encoded_hmac,          # unchanged, still valid
  "x-shopify-shop-domain"  => "victim-shop.myshopify.com", # forged
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# HmacValidator.validate(request) passes because to_signable_string == raw_body only.
# The handler receives WebhookMetadata with shop == "victim-shop.myshopify.com".
