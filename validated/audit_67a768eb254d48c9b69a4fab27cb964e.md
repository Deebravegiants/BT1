Based on my analysis, I've confirmed the reachable path: `AmmInfo::initialize()` in `state.rs` calls `checked_pow(...).unwrap()` on attacker-controllable mint decimals during `process_initialize2`, which is invoked by any unprivileged pool creator.### Title
Unchecked mint decimals cause unconditional panic in `AmmInfo::initialize`, permanently bricking pool creation for any coin/pc mint with `decimals > 19` - ([File: program/src/state.rs])

### Summary
`CVE-2019-6137` is a NULL pointer dereference caused by `LinkLayer_setAddress` acting on attacker/caller-influenced input without validating it first. The analogous root cause here is an unchecked, attacker-controllable value (`spl_token::Mint.decimals`, a `u8` in range 0–255) being fed directly into `checked_pow(...).unwrap()` with no upper-bound validation, causing a guaranteed Rust panic (arithmetic overflow to `None`, then `.unwrap()` on `None`) instead of a graceful `ProgramError`.

### Finding Description
`process_initialize2` (the entry point for creating a new AMM pool, reachable by any unprivileged pool creator) unpacks the coin and pc mint accounts supplied by the caller: [1](#0-0) 

Both `amm_coin_mint_info` and `amm_pc_mint_info` are fully attacker-controlled accounts — a pool creator can mint an arbitrary SPL token with any `decimals` value from `0` to `255` (nothing in the SPL Token program restricts `decimals`, and Raydium performs no range check on it before use). These raw `u8` decimals are passed straight into `AmmInfo::initialize`: [2](#0-1) 

Inside `initialize`, the larger of the two decimals is used to compute `sys_decimal_value = 10u64.checked_pow(decimals).unwrap()`: [3](#0-2) 

`10u64.checked_pow(n)` returns `None` for any `n >= 20` (since `10^20` overflows `u64::MAX ≈ 1.8×10^19`). Because the code calls `.unwrap()` on this `Option` with no prior bounds check on `coin_decimals`/`pc_decimals`, supplying either mint with `decimals >= 20` causes an immediate Rust panic. On Solana, a BPF program panic aborts the transaction with a runtime-level failure (not a controlled `ProgramError`), but critically the entire instruction — and thus pool creation — can never succeed for that (coin_mint, pc_mint) pair, because `Initialize2` is the only entry point that creates the AMM/target-orders/vault/lp-mint PDA set for a given `market_info` seed; every future attempt with the same mints hits the identical panic deterministically.

This mirrors the CVE-2019-6137 bug class precisely: a caller-supplied parameter is used to index/compute against a fixed-capacity structure without a prior sanity/range check, producing an unconditional crash instead of a validated error path.

### Impact Explanation
Any account whose fund flow depends on `Initialize2` succeeding for a chosen mint pair is denied: the AMM account, target-orders account, and LP mint were already allocated/assigned to the program via `system_instruction::allocate`/`assign` earlier in the same instruction, and the user's coin/pc tokens were already transferred into the not-yet-finalized vaults via `Invokers::token_transfer` before the panic point — but since the panic aborts the entire transaction atomically, all of these effects (account allocation, token transfers, LP mint) are rolled back by the Solana runtime, so there is no partial/inconsistent on-chain state. The primary damaging effect is a **permanent, deterministic denial-of-service for creating a pool with any mint that legitimately uses `decimals >= 20`** (e.g., certain wrapped/synthetic or non-standard SPL tokens) — this class of pool can never be created via `Initialize2`, which the docstring explicitly recommends as "due to openbook has not supported" ‑ i.e., this is the primary/only viable initialization path in this build. This is a compute-availability crash rather than fund theft/freezing of an *already-created* pool's assets, since transaction atomicity prevents any prior investment from being trapped in a broken pool state.

### Likelihood Explanation
Trivial and fully within reach of a single, unprivileged submitted transaction: any user with permission to create SPL mints (permissionless on Solana) can mint a token with `decimals = 20` (or higher) and immediately attempt `Initialize2` with it as either coin or pc mint, deterministically triggering the panic on every attempt, with attacker-chosen accounts and data and no signer privilege required beyond the normal pool-creator flow.

### Recommendation
Validate `coin_mint.decimals` and `pc_mint.decimals` are within the safe range (`<= 19` for `u64` computation, and further bounded for later `U128` normalization in `Calculator::normalize_decimal_v2`/`restore_decimal`, which also use `checked_pow(...).unwrap()` on the same decimals and can overflow for `native_decimal` values approaching 39) before calling `AmmInfo::initialize`, returning a proper `AmmError` (e.g., `InvalidInput`) instead of allowing the `.unwrap()` panic. Replace `.unwrap()` in `state.rs::initialize` (and in `Calculator::normalize_decimal`, `restore_decimal`, `normalize_decimal_v2`) with proper `ok_or(AmmError::...)?` error propagation.

### Proof of Concept
1. Attacker creates two new SPL mints via the standard SPL Token program: `mint_coin` with `decimals = 20`, and any valid `mint_pc` with `decimals <= 19`.
2. Attacker funds an ATA for `mint_coin` with a nonzero balance and calls `initialize2` (per `program/src/instruction.rs:664-729`) supplying `mint_coin` as `amm_coin_mint` and a legitimate token (e.g., a devnet USDC-like mint) as `amm_pc_mint`, along with all other required PDAs.
3. Execution reaches `Self::unpack_mint(&amm_coin_mint_info, ...)` yielding `coin_mint.decimals == 20`, then `amm.initialize(..., coin_mint.decimals, pc_mint.decimals, ...)` at `program/src/processor.rs:931-938`.
4. Inside `initialize`, since `coin_decimals (20) > pc_decimals`, the branch `10u64.checked_pow(20).unwrap()` executes; `checked_pow` returns `None`, and `.unwrap()` panics, aborting the transaction with a Solana program panic log instead of a clean `AmmError`.
5. Every subsequent attempt to initialize a pool with a mint whose `decimals >= 20` fails identically — the pool can never be created via `Initialize2`.

**Uncertainty**: I could not verify (index does not show it) whether any off-chain client-side validation restricts mint decimals before submission, or whether a differently-shaped instruction/build path bypasses this check; a Devin session with full repository access could confirm there is no such guard elsewhere in the codebase.
