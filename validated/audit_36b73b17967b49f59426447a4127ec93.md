### Title
Webhook shop identity is not bound by the HMAC signature, allowing cross-tenant shop spoofing - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC computed over the raw request body. The `shop` (and `topic`, `webhook_id`, `api_version`) values are read from HTTP headers that are completely outside the signed content, then handed to the app's handler as the trusted tenant identifier.

### Finding Description
`Registry.process` validates a webhook with: [1](#0-0) 

The validation call `Utils::HmacValidator.validate(request)` computes the signature over `verifiable_query.to_signable_string`, and for `Webhooks::Request` that method returns only the raw HTTP body: [2](#0-1) 

Meanwhile, `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from HTTP headers with no cryptographic tie to the signed body: [3](#0-2) 

After the HMAC check passes, `request.shop` (from the unbound header) is passed straight into `WebhookMetadata` and delivered to the host application's handler as the authoritative tenant: [4](#0-3) 

The security property the library implies is: **shop header == shop that produced/authorized this signed body**. In reality the check only proves: **HMAC-SHA256(api_secret_key, raw_body) == received hmac**. Nothing ties the `shop` header to that specific signed body. Because Shopify computes the webhook HMAC using the merchant-agnostic app secret (the same secret is used for every shop that installs the app), any two shops produce structurally identical, validly-signed bodies for a given topic whenever the payload content is invariant (e.g., the mandatory GDPR webhooks `shop/redact`, `customers/redact`, `customers/data_request` frequently carry small/predictable JSON, and many app-specific webhooks share identical bodies across tenants for certain event types, or an attacker who owns their own installed shop can simply capture a webhook Shopify sent them and replay it with a different `X-Shopify-Shop-Domain` header).

Since an unprivileged internet user can operate their own store to legitimately receive genuine, validly-HMAC-signed webhook deliveries from Shopify for that store, they hold a body+HMAC pair that will always pass `HmacValidator.validate`. By replaying that exact `raw_body`/`hmac-sha256` pair to the app's webhook endpoint while substituting an arbitrary victim shop domain in the `X-Shopify-Shop-Domain` header, the request still validates, and the host application's webhook handler executes attacker-supplied event data under the identity of a shop the attacker does not own.

### Impact Explanation
This breaks tenant isolation: the app processes webhook data (which can drive account state changes, data deletion via GDPR `shop/redact`/`customers/redact` handlers, uninstall cleanup, order/product state changes, etc.) attributed to a shop chosen by the attacker rather than the shop whose secret actually produced the request. This is a cross-tenant access vulnerability — the library-level authentication primitive for webhooks fails to bind the identity field to the signed content, allowing tenant confusion in any host application that trusts `WebhookMetadata#shop` (which the gem's own registry always does).

### Likelihood Explanation
Medium-High. It requires the attacker to possess at least one valid, distinct raw-body + HMAC pair, which is trivially obtainable by installing the target app on their own free/dev Shopify store and capturing any webhook delivery (mandatory compliance webhooks are sent to every installed app regardless of subscription and have small, often reusable bodies). No access to `api_secret_key`, tokens, or the merchant's credentials is needed — only the ability to send an HTTP POST to the app's public webhook endpoint with a header carrying an arbitrary target shop.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the signable content, or at minimum verify that the `shop` header corresponds to a shop with an active session/installation associated with the received event context before trusting it. Practically:
- Have `Webhooks::Request#to_signable_string` incorporate the shop domain (and topic) alongside the raw body, matching a keyed construction Shopify also verifies, or
- Require host applications to independently confirm that a stored, previously-installed session exists for `request.shop` before acting on the webhook payload, treating the header purely as a lookup key and not as an authenticated fact.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` and receives a real webhook, e.g. for `customers/data_request`, with body `raw_body` and header `X-Shopify-Hmac-Sha256: <valid_hmac_for_raw_body>`.
2. Attacker sends a POST to the app's public webhook endpoint with the same `raw_body` and `X-Shopify-Hmac-Sha256` header, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `Webhooks::Request.new` parses headers/body; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes HMAC over `raw_body` — this matches, so validation passes: [5](#0-4) 
4. `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` is built with `shop == "victim-shop.myshopify.com"` and passed to the app's handler, which processes the (attacker-controlled context/body) as an authentic event from the victim shop.
