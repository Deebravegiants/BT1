### Title
Webhook `shop-domain` header is trusted for tenant identity but is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, so `Utils::HmacValidator.validate` verifies nothing but the body bytes. The `shop` (from the `X-Shopify-Shop-Domain`/`shopify-shop-domain` header) that `Webhooks::Registry.process` later uses to identify the tenant handling the webhook is never included in the signed material, breaking the binding `hmac-verified bytes == shop identity acted on`.

### Finding Description
`Webhooks::Request` exposes `shop`, `topic`, `webhook_id`, and `api_version` as plain header reads: [1](#0-0) 

But the HMAC signable string is only the raw body: [2](#0-1) 

`Webhooks::Registry.process` validates the HMAC (over the body only) and then unconditionally trusts `request.shop` (parsed straight from the header, not from the signed payload) to build the `WebhookMetadata` handed to the app's handler: [3](#0-2) 

The `HmacValidator` itself only checks bytes vs. bytes — it has no notion of `shop` at all: [4](#0-3) 

Since every shop that installs the app shares the same app-level `api_secret_key` (there is no per-shop signing key), a `(body, hmac)` pair that is valid for one tenant's webhook is *also* a valid HMAC for the exact same body regardless of which `X-Shopify-Shop-Domain` header accompanies it. An attacker who is a legitimate (unprivileged, non-admin) user of the app on their own store can:
1. Trigger/capture a normal webhook delivery for their own shop (or any webhook that is not confidential, e.g., a `app/uninstalled` or `orders/create` test webhook — merchants can see/replay these from the Shopify admin's webhook delivery logs or via Shopify CLI `trigger`).
2. Replay the identical raw body + HMAC value to the app's webhook endpoint, but substitute the `X-Shopify-Shop-Domain` header with a victim shop's domain.
3. `HmacValidator.validate` passes (body bytes unchanged), and `Registry.process` calls the app's handler with `WebhookMetadata.new(shop: <victim-shop>, body: <attacker-controlled-but-otherwise-valid-parsed-body>, ...)`.

The handler — which the library's own documentation instructs app authors to trust as verified — will process/act on data (e.g., persist order/product/app-uninstalled state) under the wrong tenant identity, i.e., a cross-tenant confusion condition. This is a straightforward equality break: `shop authenticated (none) != shop acted upon (attacker-supplied header)`.

### Impact Explanation
This is a cross-tenant identity confusion: the gem's own webhook-processing pipeline lets an unprivileged app user forge the tenant (`shop`) attribution of an otherwise-valid webhook payload. Depending on the host application's webhook handlers (e.g., `app/uninstalled` triggering token/session deletion, or order/customer webhooks writing to a shop-keyed table), this can be used to delete/corrupt/overwrite another merchant's stored session or business data, or leak data into the wrong tenant's records — a "cross-tenant access" class impact as defined by the rules, achieved entirely through the gem's own `Webhooks::Request`/`Webhooks::Registry` code without needing `api_secret_key`, an access token, or any privileged credential.

### Likelihood Explanation
Likelihood is moderate-to-high in any host application that keys business logic strictly off `WebhookMetadata#shop` (which the docs present as the verified tenant identity) without independently re-validating that the shop actually matches an expected/known value for that specific webhook delivery. No secret material is needed by the attacker; they only need one legitimately-obtained `(body, hmac)` pair for any topic reachable to them (they are a legitimate but unprivileged consumer of the app), and the ability to POST to the app's public webhook URL with custom headers.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) values in the HMAC-verified signable string, or have `Registry.process` cross-check the header-derived `shop` against another trust anchor (e.g., re-fetch/validate against the topic-specific expected shop, or bind the webhook to a shop-specific secret/session) before constructing `WebhookMetadata`. At minimum, document loudly that `WebhookMetadata#shop` is *not* cryptographically bound to the verified payload and must not be trusted as tenant identity without additional verification.

### Proof of Concept
1. App installs webhook handler for `app/uninstalled` (or any topic) and registers it via `Webhooks::Registry`.
2. Attacker's own shop `attacker.myshopify.com` receives a legitimate webhook delivery for that topic; attacker captures the exact raw body and the `X-Shopify-Hmac-Sha256` value Shopify sent (both visible in Shopify's admin "Recent deliveries" log or replayable via Shopify CLI).
3. Attacker POSTs to the app's public webhook endpoint with the same raw body and same `X-Shopify-Hmac-Sha256` value, but sets:
   `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
4. `ShopifyAPI::Webhooks::Request.new` parses shop as `victim-shop.myshopify.com`.
5. `Utils::HmacValidator.validate(request)` returns `true` (only body bytes are checked, per `to_signable_string` returning `@raw_body`).
6. `Registry.process` invokes the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker's captured body>, ...)`, causing the app to act as if `victim-shop` sent this payload.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
