### Title
Incorrect (UTF-16 code-unit) length used for `domain` in TON Connect signature hash causes length/byte-boundary mismatch — ([File: packages/intents-sdk/src/intents/intent-hashes/ton-connect.ts])

### Summary
`computeTonConnectHash` builds a length-prefixed TLV byte string that is SHA-256 hashed and signed. For the `domain` field, the 4-byte big-endian length prefix is derived from the JavaScript string's `.length` (UTF-16 code unit count) rather than the number of UTF-8 bytes actually appended to the buffer.

### Finding Description
In `computeTonConnectHash`, the domain segment is constructed as: [1](#0-0) 
`numberToBigEndian(domain.length, 4)` is followed by `new TextEncoder().encode(domain)`. `domain.length` counts UTF-16 code units of the JS string, while the appended bytes are the UTF-8 encoding of that same string. For any `domain` containing a character whose UTF-8 encoding uses more bytes than one UTF-16 code unit (e.g. a non-ASCII/IDN-unicode character), the declared `domain_len` prefix will not equal the number of bytes actually written for `domain`. That means the length field embedded in the signed pre-image is inconsistent with the true data length — the same CWE-130 class as the reported Apache Ant issue.

This is not a hypothetical: the repository's own changelog shows this exact defect was previously discovered and patched for the ERC-191 signer: [2](#0-1) 
And the current, fixed implementations of ERC-191 and TIP-191 correctly derive the length from the already-UTF-8-encoded byte array (`data.length` where `data = new TextEncoder().encode(payload)`), not from the raw string: [3](#0-2) [4](#0-3) 
The `payloadData` field in `ton-connect.ts` follows the correct pattern (`payloadData.length` on already-encoded bytes): [5](#0-4) [6](#0-5) 
but the `domain` field was missed when this class of bug was fixed elsewhere.

`domain` is the TON Connect signing-domain binding — its role is analogous to an EIP-712 `verifying_contract`/domain separator: it is what scopes a signature to a specific origin so a signature obtained for one dApp/domain cannot be replayed against another. A length/byte mismatch corrupts the canonical framing of the signed pre-image for domains containing multi-byte UTF-8 characters, breaking the integrity of that domain-binding field in the hash that gets signed and later re-derived by `computeSignedTonConnectHash`, used by `computeIntentHash`.

### Impact Explanation
If a non-ASCII/unicode domain is ever accepted (the code does not restrict `domain` to ASCII), the SDK will construct and sign/verify a hash whose `domain_len` framing does not match the actual domain bytes present in the pre-image. This corrupts the intended domain-scoping guarantee of the signature, undermining the security property that binds a signature to one specific domain — the same class of defect that was serious enough to warrant a dedicated fix for ERC-191 (`95bee77`). Left unresolved for TON Connect, it reduces the reliability/integrity of the domain-binding field used to compute the intent hash relied upon for signature verification.

### Likelihood Explanation
Likelihood is constrained by the fact that TON Connect domains are typically plain ASCII hostnames, for which `.length` (UTF-16 units) equals UTF-8 byte length, so the mismatch does not manifest for ordinary inputs. It becomes concrete only when a domain string contains non-ASCII/multi-byte characters, similar to the "café" case that was used to prove out the analogous ERC-191 fix in this repo's own test suite.

### Recommendation
Compute `domain_len` from the UTF-8 encoded byte length, matching the pattern already used for `payloadData` and the fixed ERC-191/TIP-191 implementations:
```ts
const domainBytes = new TextEncoder().encode(domain);
...
numberToBigEndian(domainBytes.length, 4),
domainBytes,
```

### Proof of Concept
Using a domain string with a multi-byte UTF-8 character, e.g. `domain = "café.app"` (8 UTF-16 code units, but `café.app` encodes to 9 UTF-8 bytes because `é` is 2 bytes):
```ts
const domain = "café.app";
domain.length; // 8  <-- used for domain_len prefix
new TextEncoder().encode(domain).length; // 9 <-- actual bytes appended
```
The hash pre-image built by `computeTonConnectHash` declares `domain_len = 8` yet appends 9 bytes for `domain`, exactly mirroring the length-parameter inconsistency pattern already identified and fixed for `erc191.ts` in this codebase's changelog entry `95bee77`, but left unaddressed here.
