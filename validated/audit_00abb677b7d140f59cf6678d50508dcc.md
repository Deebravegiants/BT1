### Title
Webhook shop/topic identity fields not covered by HMAC allows cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then trusts unauthenticated header values (`shop`, `topic`, `webhook_id`, `api_version`) to route the request to a handler and to identify the tenant the payload belongs to. Because those identity fields are excluded from the signed content, an attacker who can obtain one valid (body, HMAC) pair can replay it against any other tenant by swapping the shop header.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors are all read from HTTP headers that are never part of the signed content: [2](#0-1) 

`Utils::HmacValidator.validate` computes `HMAC(client_secret, verifiable_query.to_signable_string)` and compares it to the received signature — for a `Webhooks::Request`, this is `HMAC(client_secret, raw_body)` only: [3](#0-2) 

`Webhooks::Registry.process` treats a passing HMAC check as full authentication of the request, then uses the unauthenticated `request.topic` to select the handler and the unauthenticated `request.shop` to build the `WebhookMetadata` that is handed to the host application's handler as the tenant identity: [4](#0-3) 

The identity-binding equality that should hold is: `shop-that-produced-the-signed-body == shop-the-handler-is-told-to-act-on`. Because `shop` (and `topic`) are never part of the HMAC input, this equality is not enforced — the gem only proves "this body byte-string was signed by someone holding `client_secret`," not "this body was signed for shop X."

### Impact Explanation
An attacker who operates or controls any legitimate Shopify store using the target app can receive a genuinely signed webhook (body `B`, signature `H = HMAC(secret, B)`) for their own store. Since `H` commits only to `B`, the attacker can resend `(B, H)` to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header changed to a different, victim tenant. `HmacValidator.validate` still passes, and `Registry.process` dispatches the handler with `WebhookMetadata#shop` set to the victim's domain. Any handler that uses `data.shop` to decide which tenant's records to create/update/delete (e.g., `orders/create`, `app/uninstalled`) will apply attacker-controlled webhook content under the victim's tenant identity — a cross-tenant access/integrity violation, which meets the Critical bar for cross-tenant access.

### Likelihood Explanation
Requires the attacker to possess (or install the app on) at least one real Shopify store to source a validly signed body/HMAC pair, and requires the target app's webhook endpoint to be reachable directly without an additional tenant-binding check (e.g., verifying `shop` against a known installed session before trusting the payload) — a check this gem does not perform or document as mandatory in `Registry.process`.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) header values into the signable content verified by `HmacValidator`, or require callers of `Registry.process` to independently verify that `request.shop` corresponds to a shop with an active installed session before invoking the handler, and document/enforce this in `lib/shopify_api/webhooks/registry.rb`.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and receives a webhook delivery with body `B` and header `X-Shopify-Hmac-Sha256: H`.
2. Attacker resends the request to the app's webhook endpoint with the same `B`/`H` but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(secret, B) == H` — this still passes.
4. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed(B), ...)`, causing the app to process attacker-controlled data under the victim tenant's identity.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
