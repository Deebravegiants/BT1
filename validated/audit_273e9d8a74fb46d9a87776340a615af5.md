### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant attribution of webhook payloads - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `ShopifyAPI::Webhooks::Registry.process` accepts the request as authentic once `Utils::HmacValidator.validate` succeeds against that body-only signature. The `shop` field that is subsequently handed to the application's `WebhookHandler` (via `WebhookMetadata#shop`) is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header and is never part of the signed bytes, so the binding "HMAC-authenticated bytes == shop attribution used by the handler" does not hold.

### Finding Description
`Request#to_signable_string` only returns `@raw_body`: [1](#0-0) 

`Request#shop` is read from an unauthenticated header, independent of the HMAC: [2](#0-1) 

`Registry.process` validates the HMAC (which only covers the body) and then dispatches to the handler using `request.shop` and `request.parsed_body` as trusted, correlated fields: [3](#0-2) 

`HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` (the body only) and compares it to the `hmac` header: [4](#0-3) 

The documented usage explicitly presents `data.shop` to app developers as reliable, verified metadata alongside `data.body`, with no caveat that `shop` is uncorrelated to the signature: [5](#0-4) 

The identity-binding equality the report's bug class targets is: `shop-that-authenticated-the-payload == shop-attributed-to-the-payload`. Here, only `raw_body` is bound by the HMAC; `shop` is a separate, unauthenticated header value that the gem merges into the same `WebhookMetadata` struct as if it had the same trust level as the HMAC-verified body. Any party who can obtain one valid `(raw_body, hmac)` pair signed with the app's secret (e.g., a legitimate webhook delivered to their own installed shop) can replay that exact body to the app's webhook endpoint while substituting a different `shopify-shop-domain` header. `HmacValidator.validate` will still pass because the signature never covered the shop domain, and `Registry.process` will call the handler with `WebhookMetadata.new(shop: <attacker-chosen shop>, body: <original body>, ...)`.

### Impact Explanation
If a host application uses `data.shop` (as the docs instruct) to route or attribute the incoming, HMAC-verified webhook body to a specific tenant/session/database record — which is exactly how the gem's own example handler in the docs uses it (`shop_domain: data.shop`) — an attacker who is a legitimate (unprivileged) user of one shop can forge webhook deliveries that are misattributed to a different shop. This breaks the shop/tenant identity binding that the HMAC is supposed to guarantee, enabling cross-tenant data injection/corruption in applications built directly against this gem's documented contract. This satisfies the "cross-tenant access" Critical/High impact category since data intended for/verified as belonging to one merchant can be attributed to another merchant's session/store.

### Likelihood Explanation
Exploitation requires no access to the app's `client_secret`, access tokens, or any privileged account: the attacker only needs (a) to be a normal merchant with the app installed on their own shop (an "unprivileged internet user" relative to other tenants), which lets them capture a genuinely valid `(raw_body, hmac)` pair for their own webhook deliveries, and (b) the ability to send an HTTP request to the app's public webhook endpoint with a modified `shopify-shop-domain` header — both of which are entirely within the gem's own request/response contract, not host misuse. No TLS interception or social engineering is needed.

### Recommendation
Bind the shop domain (and other routing-relevant headers such as `topic`/`api-version`) into the HMAC-verified surface, or, at minimum, require callers of `Registry.process`/`WebhookHandler.handle` to cross-check `data.shop` against a known, installed-shop store (e.g., an `Auth::Session` lookup) before trusting it for any tenant-scoped action, and update the documentation to make this required correlation explicit rather than presenting `data.shop` as verified metadata equivalent to `data.body`.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker-shop.myshopify.com` and receives a legitimate webhook: raw body `B`, header `x-shopify-hmac-sha256: H` (valid HMAC of `B` with the app's secret), header `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker resends the exact same body `B` and HMAC `H` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {..., "x-shopify-shop-domain" => "victim-shop.myshopify.com", "x-shopify-hmac-sha256" => H})` is constructed.
4. `Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `to_signable_string` (`B` only) and matches `H` — validation succeeds: [6](#0-5) 
5. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)`: [7](#0-6) 
6. Any host application following the gem's documented handler pattern (`perform_later(topic:, shop_domain: data.shop, webhook: data.body)`) now processes attacker-supplied webhook content as if it were verified data belonging to `victim-shop.myshopify.com`.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
