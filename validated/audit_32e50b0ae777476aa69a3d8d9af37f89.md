## Title
Direct ERC20 donation to `StreamingYieldVault` bypasses the vesting lock and lets any address instantly inflate/snipe the share price — ([File: sdk/packages/core/contracts/vaults/StreamingYieldVault.sol])

### Summary
`StreamingYieldVault.totalAssets()` derives the vault's backing directly from `IERC20(asset()).balanceOf(address(this))` minus a locally-tracked `_lockedYield()`, exactly the same anti-pattern flagged in the external report for `StargatePool`/`StargatePoolNative`: the raw ERC20 balance is trusted as the pool's accounted balance instead of an internal ledger that is only updated through the contract's own deposit/yield-recording paths.

### Finding Description
`totalAssets()` is defined as: [1](#0-0) 

`_lockedYield()` only masks the amount that was set via `_startVesting`, which is invoked exclusively from `addYield()`/`onTransferReceived()`: [2](#0-1) 

Nothing prevents any unprivileged address from calling `IERC20(asset()).transfer(vaultAddress, amount)` directly. Such a transfer raises `balanceOf(address(this))` immediately, and since `_lockedYield()` has no knowledge of it, the full donated amount is instantly reflected, unlocked, in `totalAssets()` — with none of the 22-hour vesting delay (`VEST`) that `addYield()` enforces. This is the same root cause as the reported bug: the contract conflates "raw token balance" with "internally accounted, vested balance," instead of maintaining a separate ledger that only advances through `addYield`/deposit/withdraw accounting.

### Impact Explanation
The contract's own documentation states the vesting design exists specifically so that "no single block can be sandwiched around a yield event ('yield sniping'): a same-block deposit/withdraw sees an unchanged share price and captures nothing" [3](#0-2) . A direct ERC20 transfer completely defeats this guarantee: it changes the exchange rate (`convertToAssets`/`convertToShares`, which both read `totalAssets()`) in the very same block it is sent, with no lock. This lets a depositor time a deposit immediately before a donation and a redeem immediately after (same block), capturing yield instantly instead of over the intended 22h vesting window — precisely the "yield sniping" scenario the contract was built to prevent. It also means the vault's share price no longer faithfully represents "recognized, vested yield," undermining accounting guarantees that downstream integrators (and other depositors sizing entries/exits around the vesting schedule) rely on.

### Likelihood Explanation
Triggering it requires only a plain, permissionless ERC20 `transfer` to the vault's address — no special role, no governance, and no interaction with `addYield`/`onTransferReceived` is needed. Any address holding the underlying asset can execute this in a single transaction alongside a `deposit`/`redeem`, making it trivially reachable by an ordinary user or MEV searcher.

### Recommendation
Do not derive `totalAssets()` from `IERC20(asset()).balanceOf(address(this))`. Maintain an internal ledger (e.g., `_totalPrincipalAndVestedYield`) that is only incremented by legitimate deposits and `addYield`'s vesting schedule, and decremented by withdrawals/redemptions — mirroring the report's remediation of tracking pool balance internally, distinct from the token's raw `balanceOf`, and updating it explicitly wherever principal or yield state changes.

### Proof of Concept
1. Vault is outside the vesting window (`maxDeposit`/`maxMint` open).
2. Attacker (or any address) calls `vault.deposit(x, attacker)` to acquire shares at the current price.
3. In the same block, attacker calls `asset.transfer(address(vault), y)` directly (no `approve`+`addYield`, no ERC-1363 hook needed for a plain ERC20).
4. `totalAssets()` immediately increases by `y` with `_lockedYield()` unaffected, inflating `convertToAssets`.
5. Attacker calls `vault.redeem(x, attacker, attacker)` in the same block, receiving `y`'s pro-rata share of the freshly donated funds instantly — bypassing the intended `VEST` (22h) recognition delay entirely.

    /// @notice Total assets backing shares, net of any not-yet-vested yield.

    /// @dev Linear unlock of the current tranche, keyed on `block.timestamp` so that a deposit
    ///      and withdrawal within the same block observe an identical, unchanged share price.
    function _lockedYield() internal view returns (uint256) {
        uint256 start = _vestingStart;
        uint256 elapsed = block.timestamp - start;
        if (elapsed >= VEST) return 0;
        return (_vestingAmount * (VEST - elapsed)) / VEST;
    }
    
    /// @notice Add a new yield tranche, pulled from the caller. Reverts unless the previous
    ///         tranche has fully vested, which guarantees tranches never overlap and no yield
    ///         is ever left permanently locked.
    /// @param amount The amount of `asset` to stream in over `VEST`.
    function addYield(uint256 amount) external onlyOwner {
        // Pull the funds first so `balanceOf` already reflects `amount` before it is marked
        // locked; otherwise `totalAssets` would transiently underflow when a tranche exceeds
        // the current backing (e.g. the very first `addYield` on a near-empty vault).
        IERC20(asset()).safeTransferFrom(msg.sender, address(this), amount);

        _startVesting(amount);
    }

    /// @dev Arms a new tranche after validating the no-overlap / deposit-window guards. The caller
    ///      must have already moved `amount` of `asset` into the vault (so `balanceOf` reflects it
    ///      before `_vestingAmount` is set, avoiding a transient `totalAssets` underflow).
    function _startVesting(uint256 amount) private {
        if (amount == 0) revert ZeroAmount();

        uint256 start = _vestingStart;
        if (start != 0) {
            if (block.timestamp < start + VEST) revert YieldStillVesting(start + VEST);
            // Hold off until the guaranteed deposit window has elapsed, so new capital always has
            // a chance to enter between tranches regardless of how promptly the keeper runs.
            if (block.timestamp < start + VEST + MIN_WINDOW) revert DepositWindowOpen(start + VEST + MIN_WINDOW);
        }

        _vestingAmount = amount;
        _vestingStart = block.timestamp;

        emit YieldAdded(amount, block.timestamp);
    }
