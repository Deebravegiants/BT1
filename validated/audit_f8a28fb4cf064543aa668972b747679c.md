### Title
Liquidity-weighted median lets a single dominant-weight solver set the published phantom price verbatim, which is consumed unguarded by default intent quoting - ([File: sdk/packages/sdk/src/protocols/intents/phantom-aggregation.ts])

### Summary
`weightedMedian` in the phantom-order price-aggregation pipeline is a **selection** algorithm: it returns one bidder's exact quoted price rather than a blended value. Any verified solver whose inventory weight for a leg exceeds half the leg's total counted weight has its quote returned verbatim as `medianPrice`, which is then also copied into `lowestPrice`/`highestPrice`. This is the same bug class as the Apollo Oracle report: a market/price-computation mechanism nominally averaging several independent inputs can, in fact, be dictated entirely by one participant, and that published price is consumed by other protocol logic (default intent quoting) without a deviation/sanity check on the pool side.

### Finding Description
`weightedMedian` sorts quotes by price and walks cumulative weight until it reaches half the total, returning that quote's exact price: [1](#0-0) 

The surrounding documentation makes explicit that this is intentional selection behavior, not blending, and that a majority-weight solver's quote becomes the published price exactly: [2](#0-1) 

The weight backing a quote is the solver's on-chain balance of that leg's *output token* on the *destination chain*, read live via RPC at aggregation time: [3](#0-2) 

For any output token where liquidity is thin (a newly listed pair, a low-liquidity chain, or simply a token most solvers don't hold much of), a single delegated solver can temporarily acquire a majority share of the counted weight (e.g., via a flash loan, a large transient balance, or simply being the only well-capitalized bidder for that leg) and thereby dictate the exact `medianPrice` published for the leg — to any value it wants, not merely a value bounded by honest quotes on either side, since `weightedMedian` is a pure selection over whatever price it submits. `lowestPrice` and `highestPrice` are overwritten with that same value, erasing any signal that the bid set was actually one-sided: [4](#0-3) 

This per-leg median feeds `updateLiquidityPools`, which renormalizes it into the pool's `sellRate`/`buyRate` per chain, merged across chains by a depth-weighted mean (`weightedRate`) that does not discard or clamp an individual chain's manipulated sample beyond a passive 5x divergence *warning* that still merges the value anyway: [5](#0-4) 

Those pool `sellRate`/`buyRate` values are, by default, exactly what `IntentGateway.quoteIntent` uses to price real orders for callers who don't specify another strategy: [6](#0-5) [7](#0-6) 

Unlike the FX filler's own trade-pricing path, which explicitly guards against a manipulated pool rate with a `priceGuard`/`maxDeviationBps` band before using it to size a confirmation: [8](#0-7) 
the SDK's public `quoteIntent`/`getBuyAndSellRates` path that end users and integrators call directly has no such guard — it reads the indexer's `sellRate`/`buyRate` and uses it as-is to construct order amounts: [9](#0-8) 

### Impact Explanation
A solver that can transiently dominate a thin leg's weight controls the exact published price for that leg, and by extension the pool's aggregate `sellRate`/`buyRate` for that pair/direction. Any caller of the default `quoteIntent`/`getBuyAndSellRates` path (unrestricted, unprivileged — any user constructing an intent order through the SDK) receives a price built on this potentially fully-attacker-dictated rate, with no bound relative to a reference price. An attacker can set the rate favorably, induce counterparties (other solvers filling against the quoted rate, or the SDK's own order-sizing) to trade at an off-market rate, and profit on the resulting mispricing — directly analogous to the reported Apollo Oracle exploit scenario ("Eve can then turn a profit by adjusting the rate when buying and selling assets"), except here the attacker is not bounded to the range between honest quotes; the selection semantics of `weightedMedian` let a majority-weight quote be published verbatim at any price.

### Likelihood Explanation
Requires becoming a delegated/verified solver (an EIP-7702 delegation to the chain's `SolverAccount`, which the code notes is an open, permissionless step for "anyone" submitting bids, gated only by signature/nonce checks, not by identity/reputation) and temporarily holding disproportionate weight in one leg's output token — most attainable on thin/low-liquidity pairs where legitimate competing weight is small. This is an economically motivated, self-serve attack path requiring no compromise of infrastructure, matching "Medium" difficulty in the original report.

### Recommendation
Do not let a single quote fully determine the published price regardless of weight share. Options: cap any single solver's counted weight at some fraction of total leg weight before computing the median (so no one bidder can single-handedly select the outcome); require a minimum number of independent, inventory-backed bidders per leg before a snapshot is trusted for pool-rate purposes; or apply the same kind of deviation guard the FX filler already uses (`priceGuard`/`maxDeviationBps` against an external reference) to the default `quoteIntent`/`getBuyAndSellRates` path so a moved pool rate cannot be used to size real orders beyond a bounded drift from a trusted reference.

### Proof of Concept
1. Solver S delegates its EOA to the chain's `SolverAccount` (permissionless, standard onboarding) and is therefore treated as a "verified solver" by `isVerifiedSolverBid`.
2. For a thin-liquidity leg (output token T on destination chain C), S temporarily acquires a balance of T that exceeds the combined balance of every other bidder for that leg (e.g., via a flash loan or simply being the only well-funded bidder), then submits a phantom bid quoting an arbitrary off-market price for that leg.
3. `runAggregation` weights S's quote by its (now-dominant) balance; `weightedMedian` walks cumulative weight and returns S's exact quoted price as soon as cumulative weight passes half the total — i.e. S's number verbatim, per `weightedMedian`'s selection logic (`phantom-aggregation.ts:709-724`).
4. `lowestPrice`/`highestPrice`/`medianPrice` are all set to this value (`phantom-aggregation.ts:1551-1562`); `updateLiquidityPools` renormalizes it into `sellRate`/`buyRate` for the pool (`liquidityPool.service.ts`), and any 5x-divergence check only logs a warning, never rejects the sample (`liquidityPool.service.ts:498-518`).
5. Any caller of `IntentGateway.quoteIntent` (default `indexed_rates` strategy) or `getBuyAndSellRates` receives this manipulated rate and constructs/accepts an order at the off-market price, letting S profit on the discrepancy once its transient weight advantage is released.

export function weightedMedian(entries: { price: bigint; weight: bigint }[]): bigint {
	const sorted = [...entries].sort((a, b) => (a.price < b.price ? -1 : a.price > b.price ? 1 : 0))
	const totalWeight = sorted.reduce((acc, e) => (e.weight > 0n ? acc + e.weight : acc), 0n)

	if (totalWeight === 0n) {
		return sorted[Math.floor(sorted.length / 2)].price
	}

	let cumulative = 0n
	for (const entry of sorted) {
		if (entry.weight <= 0n) continue
		cumulative += entry.weight
		if (cumulative * 2n >= totalWeight) return entry.price
	}
	return sorted[sorted.length - 1].price
}

	 * Returns the indexed pool's aggregate buy and sell rates in less-valued
	 * quote-token units per one base token.
	 *
	 * The indexer depth-weights fresh per-chain samples into the pool rates. The
	 * source and destination chains remain part of the result because they define
	 * the cross-chain route whose configured token symbols were resolved.
	 */
	async getBuyAndSellRates(params: {
		sourceChain: Chains
		destinationChain: Chains
		tokenInSymbol: ConfiguredAssetSymbol
		tokenOutSymbol: ConfiguredAssetSymbol
	}): Promise<BuyAndSellRates | undefined> {
		const pool = resolveLiquidityPool(params.tokenInSymbol, params.tokenOutSymbol)
		const response = await this.queryClient.request<BuyAndSellRatesResponse>(BUY_AND_SELL_RATES, {
			poolId: pool.poolId,
		})
		if (!response?.liquidityPools?.nodes) {
			throw new InvalidLiquidityIndexerResponseError("liquidity pool connection is missing")
		}
		const indexedPool = response.liquidityPools.nodes[0]
		if (!indexedPool) return undefined
		validateIndexedPool(indexedPool, pool)

		const sell = readIndexedRate(indexedPool.sellRate, indexedPool.lastUpdatedAt, "pool sell rate")
		const buy = readIndexedRate(indexedPool.buyRate, indexedPool.lastUpdatedAt, "pool buy rate")
		const inputIsToken0 = params.tokenInSymbol.toLowerCase() === pool.token0Symbol.toLowerCase()
		const direct = inputIsToken0 ? sell : buy
		const reverse = inputIsToken0 ? buy : sell
		if (!direct && !reverse) return undefined

		const quoteTokenSymbol = resolveQuoteTokenSymbol(
			params.tokenInSymbol,
			params.tokenOutSymbol,
			direct?.scaledRate,
			reverse?.scaledRate,
		)
		const quoteIsTokenOut = quoteTokenSymbol === params.tokenOutSymbol
		const orientedBuy = quoteIsTokenOut ? direct : reverse
		const orientedSell = quoteIsTokenOut ? reverse : direct

		return {
			baseTokenSymbol: quoteIsTokenOut ? params.tokenInSymbol : params.tokenOutSymbol,
			quoteTokenSymbol,
			sourceChain: params.sourceChain,
			destinationChain: params.destinationChain,
			buyRate: orientedBuy ? formatUnits(orientedBuy.scaledRate, INDEXER_FIXED_POINT_DECIMALS) : null,
			sellRate: orientedSell
				? formatUnits(reciprocalRate(orientedSell.scaledRate, "sell rate"), INDEXER_FIXED_POINT_DECIMALS)
				: null,
			buyRateUpdatedAt: orientedBuy?.updatedAt ?? null,
			sellRateUpdatedAt: orientedSell?.updatedAt ?? null,
		}
	}
