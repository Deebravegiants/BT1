The documentation explicitly states `ShopifyAPI::Webhooks::Registry.process` "will verify the request did indeed come from Shopify" — but the code only verifies the raw body via HMAC, and treats the `shop` (tenant identifier) as trusted from an unsigned header. This matches the "field acted on but not covered by the HMAC" analog exactly, and it's the gem's own documented behavior (not host-app misuse) that's at fault.

### Title
Webhook `shop` tenant identifier is not covered by HMAC signature, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely via `Utils::HmacValidator.validate(request)`, which computes the HMAC over `request.to_signable_string` — defined for `Webhooks::Request` as just the raw request body [1](#0-0) . The `shop` value used to identify the tenant for the webhook event is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, which is never part of the signed data [2](#0-1) . Because the app's `api_secret_key` (the HMAC secret) is shared across every shop that installs the app, an unprivileged attacker who installs the app on their own store can capture a fully valid `(raw_body, hmac)` pair for a webhook they legitimately triggered, then replay that exact body/HMAC to the app's webhook endpoint while swapping the `shop-domain` header to a victim shop. `HmacValidator.validate` still succeeds (it only checks the body), and `Registry.process` hands the attacker-chosen `shop` straight to the handler as authoritative tenant identity.

### Finding Description
- `HmacValidator.validate` only calls `verifiable_query.to_signable_string` and `verifiable_query.hmac` [3](#0-2) .
- For webhook requests, `to_signable_string` returns solely `@raw_body`, excluding `topic`, `shop`, `api_version`, and `webhook_id` from the signed material [1](#0-0) .
- `Registry.process` raises only if the HMAC is invalid, then immediately constructs `WebhookMetadata` using `request.shop` as the tenant identity passed to the host app's handler [4](#0-3) .
- The gem's own documentation states that `Registry.process` "will verify the request did indeed come from Shopify" [5](#0-4)  and instructs handlers to trust `data.shop` as "The shop domain of the webhook" [6](#0-5)  — i.e., the gem asserts an identity guarantee for `shop` that its own validation does not provide.

The broken identity binding, stated as an equality that fails to hold: `shop authenticated (bound by the HMAC over signed data)` ≠ `shop delivered to the handler (an unauthenticated header value)`.

Before the attacker's request: a legitimate webhook for shop A produces `(raw_body_A, hmac_A)` signed with the app's single, shop-independent `api_secret_key`.
After the attacker's replay: the attacker resends `(raw_body_A, hmac_A)` with `shop-domain: victim-shop.myshopify.com`. `HmacValidator.validate` still returns `true` because it never inspects the `shop` header, so `Registry.process` invokes the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, granting the attacker cross-tenant influence over the victim shop's webhook processing (e.g., triggering data writes, cache invalidation, order/product sync jobs, or queued background jobs keyed by `data.shop`) without ever compromising the victim or possessing any victim-specific secret.

### Impact Explanation
This is a cross-tenant access vulnerability (Critical): a single app secret validates the payload, but the tenant identity attached to that payload is fully attacker-controlled. Any host application that follows the gem's documented pattern (using `data.shop` from the handler as the authoritative tenant key, exactly as shown in the gem's own usage example) can be made to process attacker-supplied webhook bodies under an arbitrary victim shop's identity, since the attacker only needs their own (non-victim) shop installation to mint a valid `(body, hmac)` pair.

### Likelihood Explanation
High likelihood for any attacker able to install the target app on their own Shopify development/trial store (a normal, unprivileged action) and observe outbound webhook deliveries. No access token, `client_secret`, or victim credentials are needed — only the ability to replay an HTTP POST with a modified header value.

### Recommendation
Bind `shop`, `topic`, `webhook_id`, and `api_version` into the HMAC-signed material (or otherwise cryptographically bind them, e.g., by including them in the signable string) so that swapping the shop header invalidates the signature, matching what the documentation already promises callers.

### Proof of Concept
1. Install the vulnerable app on attacker-controlled shop `attacker.myshopify.com`; trigger any subscribed topic (e.g. `orders/create`) to receive a legitimate webhook POST with body `B` and header `x-shopify-hmac-sha256: H` (valid because `H = HMAC(api_secret_key, B)`, and `api_secret_key` is the same for all shops).
2. Replay the captured request to the app's webhook endpoint, keeping `raw_body = B` and `x-shopify-hmac-sha256 = H` unchanged, but set `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` builds `Webhooks::Request` from headers/body; `Utils::HmacValidator.validate` succeeds because the check only re-computes `HMAC(api_secret_key, B)` [7](#0-6) .
4. The handler registered for the topic is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)` [8](#0-7) , causing the host application to process attacker-supplied data as belonging to the victim's tenant.
