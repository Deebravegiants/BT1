## Title
Webhook shop identity is read from an unauthenticated header while the HMAC only covers the raw body, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` (and `topic`, `webhook_id`, `api_version`) values from HTTP headers, but its `to_signable_string` — the value that `Utils::HmacValidator` actually verifies — is only the raw request body. Any party who can obtain one valid `(body, hmac)` pair from the app's own webhook secret (e.g. by installing the app on their own store and triggering an event) can replay that pair to the app's webhook endpoint while freely substituting the `x-shopify-shop-domain` header for a different, victim shop. The signature still validates because it never covered the header, so the handler is invoked with `shop:` bound to an identity the attacker chose, breaking the equality `shop authenticated by HMAC == shop acted upon by the handler`.

### Finding Description
`AuthQuery`/webhook verification is implemented via the shared `Utils::VerifiableQuery` interface, requiring `hmac` and `to_signable_string`. For webhooks: [1](#0-0) 

`hmac` comes from the `hmac-sha256` header and `shop` comes from the `shop-domain` header, but `to_signable_string` returns only `@raw_body`: [2](#0-1) [3](#0-2) 

`HmacValidator.validate` only checks the signature against `to_signable_string` (the body), never against the headers: [4](#0-3) 

`Registry.process` then trusts `request.shop` unconditionally once the (body-only) HMAC passes, and forwards it straight to the app's handler as the tenant identity for the event: [5](#0-4) 

Because a Shopify app uses a single shared `client_secret` (`Context.api_secret_key`) across every shop that installs it, any shop that has installed the app can legitimately obtain a real `(body, hmac)` pair from Shopify (by triggering any webhook-eligible event, e.g. `orders/create`, on its own store) — this pair is valid HMAC-wise for that app secret regardless of which shop it originated from. An attacker who controls such a shop can then send that identical `(body, hmac)` pair directly to the app's webhook endpoint with the `x-shopify-shop-domain` header rewritten to any other shop that also uses the app. `HmacValidator.validate` passes (it never inspects the header), and `Registry.process` calls the handler with `WebhookMetadata.new(... shop: request.shop ...)` set to the victim shop, while the actual payload content is the attacker's own data.

This breaks the identity binding: `shop verified by HMAC` (nothing — HMAC covers no shop claim at all) vs. `shop acted upon` (attacker-controlled header), allowing cross-tenant data injection/spoofing into another merchant's webhook processing pipeline (e.g., forging fake orders, fake `app/uninstalled` events, or other tenant-scoped side effects for a shop the attacker does not own).

### Impact Explanation
This is a cross-tenant access issue: an attacker who is merely an installer of the app on their own (unprivileged) shop can cause the host application to process events under an arbitrary victim shop's identity, without ever needing that victim's credentials, access token, or `client_secret`. This matches the Critical "cross-tenant access" category, since the gem's own verification primitive (`HmacValidator`/`Webhooks::Request`) provides no binding between the authenticated bytes (body) and the tenant-identifying header consumed by the handler.

### Likelihood Explanation
Likelihood is high for any multi-tenant app: the only prerequisite is that the attacker has (or creates) their own store where the target app is installed — a normal, unprivileged action — and can send arbitrary HTTP requests to the app's public webhook endpoint (which by definition must be internet-reachable to receive Shopify webhooks).

### Recommendation
Bind the shop (and topic/webhook id) into the signed material, or otherwise verify the header-derived shop against a value that is cryptographically tied to the signed body — for example, look up the session/access token for `request.shop` and confirm it belongs to a shop that is actually entitled to send the given body, or require the host application to correlate the webhook shop against session state before trusting it. At minimum, document loudly that `WebhookMetadata#shop` is unauthenticated relative to the HMAC and must not be used as a sole tenant-selection key without additional verification (e.g., matching it against records already known for that specific webhook subscription/topic).

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`.
2. Attacker triggers a webhook-eligible event (e.g., creates an order) and captures the legitimate webhook POST Shopify sends to the app, including `raw_body` and the `x-shopify-hmac-sha256` header (valid because it's HMAC'd with the app's shared secret over `raw_body`).
3. Attacker replays this exact `raw_body` + `hmac` to the app's webhook endpoint, but changes the `x-shopify-shop-domain` header to `victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `raw_body` — it succeeds.
5. The handler is invoked with `shop: "victim.myshopify.com"` and the attacker-controlled body, causing the host app to process/store attacker-controlled data under the victim shop's identity.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
