### Title
Cross-class carry-over of `ExtrinsicWeightReclaimed` corrupts per-`DispatchClass` `BlockWeight` accounting - (File: cumulus/pallets/weight-reclaim/src/lib.rs)

### Summary
`StorageWeightReclaim::post_dispatch_details` reads the previous extrinsic's leftover reclaim (`frame_system::ExtrinsicWeightReclaimed::<T>::get()`) and re-credits it into `BlockWeight` tagged with the **currently executing** extrinsic's `info.class`, rather than the class of the extrinsic that originally produced the value. When two consecutive extrinsics in a block belong to different `DispatchClass`es, the correction meant for one class bucket is applied to the other, corrupting per-class weight bookkeeping.

### Finding Description
In `post_dispatch_details` [1](#0-0) , the mutate closure does:
```
let already_reclaimed = frame_system::ExtrinsicWeightReclaimed::<T>::get();
current_weight.accrue(already_reclaimed, info.class);
current_weight.reduce(info.total_weight(), info.class);
current_weight.accrue(accurate_weight, info.class);
```
`info` here is the `DispatchInfoOf` of the extrinsic *currently* being post-dispatched (call it B), while `already_reclaimed` is the value stored by the *previous* extrinsic's call to this same function, via `frame_system::ExtrinsicWeightReclaimed::<T>::put(accurate_unspent)` at [2](#0-1) . That stored value represents extrinsic A's own unspent/reclaimed weight, computed and staged so that a subsequent correction step can reconcile it against the generic `Ok(Weight)` refund the transaction-extension pipeline returns to the Executive for A (line 276: `Ok(accurate_unspent.saturating_sub(already_unspent_in_tx_ext_pipeline))` [3](#0-2) ). Because `ExtrinsicWeightReclaimed` stores only a bare `Weight` with no `DispatchClass` tag, the only class information available when the *next* extrinsic reconciles it is that next extrinsic's own `info.class`. If A is `Normal` and B is `Operational` (or vice versa), the credit that should land in A's class bucket is instead applied to B's class bucket.

There is no check in `post_dispatch_details`, nor evidence of a class-aware reset mechanism, that ties the stored `already_reclaimed` value to the class it was generated for.

### Impact Explanation
Per-class `BlockWeight` figures (`frame_system::BlockWeight::<T>::get().get(class)`) are used to enforce per-class block weight limits (e.g. Normal vs Operational allotments) in `frame_system::CheckWeight`. If a class's bucket is erroneously deflated by a misdirected credit, extrinsics of that class can be admitted beyond their intended weight allotment; the donor class's bucket becomes correspondingly inflated/under-reported. This is a weight-accounting integrity bug matching the "Fee/weight logic must not be bypassable by normal users" invariant, scoped to cross-class mis-accounting rather than asset theft.

### Likelihood Explanation
This does not require unusual attacker sophistication: any block containing two adjacent extrinsics of differing `DispatchClass` (which is common — e.g. inherents/`Mandatory` or `Operational` calls interleaved with ordinary `Normal` user extrinsics) triggers the mismatch. A user only needs to ensure their extrinsic executes immediately after (or is positioned near) an extrinsic of a different class — achievable probabilistically given normal block composition, though exact adjacency is ultimately controlled by the block author/collator rather than the submitter directly, which somewhat limits deterministic attacker control over the exact pairing.

### Recommendation
Store the `DispatchClass` alongside the reclaimed weight in `ExtrinsicWeightReclaimed` (e.g. change the storage item to `(Weight, DispatchClass)` or maintain a per-class map), and apply the carried-over correction using the class it was originally computed for instead of the current extrinsic's `info.class`.

### Proof of Concept
Rust unit test in `cumulus/pallets/weight-reclaim/src/tests.rs` style:
1. Execute extrinsic A with `info.class = DispatchClass::Normal`, causing a non-zero `accurate_unspent` to be written to `ExtrinsicWeightReclaimed`.
2. Execute extrinsic B immediately after with `info.class = DispatchClass::Operational`.
3. Assert `frame_system::BlockWeight::<T>::get().get(DispatchClass::Normal)` equals the expected value computed purely from A's own weight/proof-size, independent of B.
4. Assert `frame_system::BlockWeight::<T>::get().get(DispatchClass::Operational)` equals the expected value computed purely from B's own weight/proof-size.
5. Show the assertions fail with the current implementation because A's leftover credit lands in the Operational bucket instead of the Normal bucket.
