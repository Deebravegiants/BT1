### Title
Spoke cap saturation lets an attacker repeatedly grief supply and borrow transactions - ([File: contracts/controller/src/spoke_usage.rs](contracts/controller/src/spoke_usage.rs))

### Summary
Each `(spoke_id, hub_asset)` market enforces cumulative `supply_cap` and `borrow_cap`, but cap usage is released immediately by `withdraw` and `repay`. An unprivileged attacker can temporarily consume the remaining cap headroom with `supply` or `borrow`, cause a victim’s competing transaction to revert with `SpokeSupplyCapReached` or `SpokeBorrowCapReached`, and then exit the position to restore headroom.

### Finding Description
The public `supply` and `borrow` entrypoints dispatch to `positions::process_supply` and `positions::process_borrow`, while `withdraw` and `repay` provide the corresponding exits. [1](#0-0) 

Both supply and debt positions update `SpokeUsageRaw` through `apply_leg_usage`: entries call `apply_spoke_entry`, and exits call `apply_spoke_exit`. [2](#0-1) 

`apply_spoke_entry` retrieves the configured per-spoke cap and relevant supply/borrow index, then `enforce_spoke_cap` rejects whenever `existing_usage + new_scaled_amount > cap_scaled`. [3](#0-2) [4](#0-3) 

There is no minimum holding period, cooldown, deposit fee, or same-ledger exit restriction. `apply_spoke_exit` simply subtracts the scaled delta and makes missing rows or zero deltas no-ops. [5](#0-4)  The tests explicitly show that withdrawn supply restores cap headroom for subsequent deposits. [6](#0-5) 

### Impact Explanation
An attacker can repeatedly prevent other users from entering a capped spoke market:

- Saturate `supplied_scaled_ray` through `supply`, causing victims’ collateral deposits to revert.
- Saturate `borrowed_scaled_ray` through `borrow`, causing victims’ borrows to revert.
- Exit with `withdraw` or `repay`, then repeat whenever another victim attempts the operation.

This is temporary freezing of protocol functionality and can also delay a distressed borrower from adding collateral. The attacker needs enough capital to consume the cap headroom, and a borrow attack additionally needs sufficient collateral and pool liquidity; however, no protocol mechanism prevents rapid exit and repetition.

### Likelihood Explanation
The attack is reachable by any funded, unprivileged controller caller. Cap consumption and release are ordinary position accounting rather than privileged configuration. The pattern is most practical when a cap is close to current usage, because only the remaining headroom must be filled.

### Recommendation
Add an economic or temporal cost to rapid cap occupancy, for example:

- Enforce a minimum ledger/time delay between supply and withdrawal, or borrow and full repayment.
- Charge a non-refundable entry/origination fee for supply and borrow positions that consume cap headroom.
- Reserve cap headroom only after a settlement delay, rather than allowing immediate cap churn.
- Rate-limit repeated cap consumption/release per account or address.

### Proof of Concept
1. Let a spoke asset have current usage `U` and cap `C`, with `headroom = C - U`.
2. Attacker calls `supply(caller, attacker_account, spoke_id, [(hub_asset, headroom)])`.
3. `merge_supply_leg` calls `apply_leg_usage` with `UsageSide::Supply` and `LegDirection::Entry`. [7](#0-6) 
4. `enforce_spoke_cap` accepts exactly up to `cap_scaled`; the next positive victim supply computes `next_scaled > cap_scaled` and panics with `SpokeSupplyCapReached`. [8](#0-7) 
5. After the victim transaction fails, attacker calls `withdraw(caller, attacker_account, [(hub_asset, headroom)], None)`.
6. The withdrawal path decrements `supplied_scaled_ray` through `apply_spoke_exit`, restoring the headroom so the attacker can repeat. [9](#0-8) 

The borrow-side variant uses a sufficiently collateralized attacker account to call `borrow` for the remaining `borrow_cap`, then later calls `repay` to release `borrowed_scaled_ray`.

        ),

            spoke_id,
            side,
            hub_asset,

        ),

    /// Buffers a scaled decrease. Zero deltas and missing rows are no-ops;
    /// overflow or negative resulting usage fails.
    pub(crate) fn apply_exit(
        &mut self,
        side: UsageSide,
        hub_asset: &HubAssetKey,
        delta_scaled: Ray,
    ) {
        if delta_scaled == Ray::ZERO {
            return;
        }
        let Some(mut usage) = self.load_usage_row(hub_asset) else {
            return;
        };
        let next = side
            .scaled(&usage)
            .checked_sub(delta_scaled.raw())
            .unwrap_or_else(|| panic_with_error!(&self.env, GenericError::MathOverflow));

        assert_with_error!(&self.env, next >= 0, GenericError::InternalError);
        side.set_scaled(&mut usage, next);
        self.usage.set(hub_asset.clone(), usage);
    }
