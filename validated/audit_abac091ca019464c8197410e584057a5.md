Audit Report

## Title
Path traversal in workflow artifact HTTP fetcher via unvalidated URL join - (File: core/services/workflows/syncer/v2/fetcher.go)

## Summary
`newHTTPFetcher` in `core/services/workflows/syncer/v2/fetcher.go` joins a caller-supplied `req.URL` onto the configured base URL's path using `filepath.Join` without verifying the result stays within the intended base path, unlike its sibling `newFileFetcher` in the same file which performs an explicit `strings.HasPrefix` containment check. This allows a `req.URL` containing `../` segments to make the constructed request path escape the configured base path segment on the same host.

## Finding Description
`newHTTPFetcher` computes `cleanPath := strings.TrimPrefix(filepath.Clean(req.URL), "/")` and then `u.Path = filepath.Join(u.Path, cleanPath)` before issuing the HTTP GET request [1](#0-0) . `filepath.Clean` does not eliminate a leading relative `..` sequence (e.g., `Clean("../../secret-path")` stays `"../../secret-path"`), and `filepath.Join(base, "../../secret-path")` will walk upward past `base`'s trailing segments, only being bounded by the URL path root (`/`). This contrasts with `newFileFetcher` in the same file, which explicitly validates `strings.HasPrefix(fullPath, basePath+string(filepath.Separator))` before reading the file [2](#0-1)  — `newHTTPFetcher` has no equivalent check.

`req.URL` is populated from `binaryURL`/`configURL` in `Store.FetchWorkflowArtifacts`, which are supplied by the on-chain `WorkflowRegisteredEvent`'s `BinaryURL`/`ConfigURL` fields (settable by any workflow owner), and passed unmodified into `fetchFn` [3](#0-2) . The HTTP-based standalone fetcher is wired only when the operator explicitly configures `[CRE.WorkflowFetcher] URL = "http(s)://..."`, at which point `NewApplication` in `core/cmd/shell.go` constructs `creOpts.FetcherFunc` via `syncerv2.NewFetcherFunc`, which is then passed through as `opts.FetcherFunc` and used directly by `newFetcherServiceV2`, entirely bypassing the gateway-mediated broker and its `retrieveFunc`. This is a real, reachable, documented configuration path (present in `docs/CONFIG.md`, `config-full.toml` test fixtures, and `config_cre_test.go`), not a test-only artifact.

Given that `retrieveFunc` is nil in this configuration, the on-chain-controlled `binaryURL`/`configURL` values flow directly and unsanitized into `newHTTPFetcher`'s `req.URL`, and the missing containment check permits escaping the configured artifact base path to other paths on the same host.

## Impact Explanation
This maps to an in-scope confused-deputy/path-traversal issue: an unprivileged workflow owner can cause the node to make HTTP requests to unintended paths on the operator-configured artifact host, potentially retrieving artifacts/config outside the intended directory, which the node subsequently treats as workflow binary/config. The blast radius is bounded to the same host/scheme as configured (this is not full SSRF to arbitrary hosts), but it is a genuine confinement bypass matching the described root cause, and the existing containment check in the sibling `newFileFetcher` function proves the omission in `newHTTPFetcher` is an inconsistency/oversight rather than intentional design.

## Likelihood Explanation
Exploitability requires the node operator to have configured the direct HTTP fetcher (`CRE.WorkflowFetcher.URL` set to `http`/`https`), which is a real, documented, and testable configuration surface, not a hypothetical or excluded misconfiguration. Once configured, the only additional precondition is registering a workflow on-chain with a crafted `BinaryURL`/`ConfigURL`, an action available to any unprivileged actor with no special node/host access. The attack is reproducible and repeatable via a Go unit test mirroring the pattern in `fetcher_test.go`'s existing path-traversal test for `newFileFetcher` (line ~443-448), simply targeting `newHTTPFetcher` instead.

## Recommendation
Apply the same containment validation used in `newFileFetcher` to `newHTTPFetcher`: after `u.Path = filepath.Join(u.Path, cleanPath)`, verify the resulting path still has the original base path as a prefix (with a path-separator boundary) before issuing the request, rejecting it otherwise. Consider centralizing the traversal-safe join logic so both fetchers share a single vetted implementation.

## Proof of Concept
1. Configure `[CRE.WorkflowFetcher] URL = "http://artifact-host/artifacts"`.
2. As an unprivileged actor, register a workflow on-chain with `BinaryURL` set to a value that, once treated as a relative path by `newHTTPFetcher` (e.g. `"../../internal/secret.wasm"`), causes `cleanPath` to retain `..` segments.
3. When the node syncs the workflow, `Store.FetchWorkflowArtifacts` invokes `fetchFn` with this URL; `newHTTPFetcher` computes `u.Path = filepath.Join("/artifacts", "../../internal/secret.wasm")`, yielding a path outside `/artifacts` (e.g., `/internal/secret.wasm`), and issues the GET request there — unlike `newFileFetcher`, which would reject the equivalent traversal attempt with "is not within the basePath" (as demonstrated by the existing test at `core/services/workflows/syncer/v2/fetcher_test.go` lines 443-448).
4. A Go unit test extending `TestNewFetcherFunc`'s "http fetcher" subtest to assert that a `req.URL` with `../` segments is rejected (currently it is not) would confirm the fix.
