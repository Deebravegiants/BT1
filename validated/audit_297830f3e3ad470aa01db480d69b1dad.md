Audit Report

## Title
Vault gateway handler logs full JSON-RPC request (including `Auth` bearer/JWT credential) at DEBUG level prior to authorization - (File: core/services/gateway/handlers/vault/handler.go)

## Summary
`HandleJSONRPCUserMessage` calls `h.lggr.Debugw("handling vault request", "method", req.Method, "requestID", req.ID, "request", req)` immediately upon receiving any inbound request, before `h.requestProcessor.ProcessRequest` performs authorization. Because `req` is the full `jsonrpc.Request[json.RawMessage]` struct that carries the caller's `Auth` field (the JWT bearer token consumed by `jwt_based_auth.go`'s `AuthorizeRequest`), enabling DEBUG logging causes every caller's raw credential and raw params to be written to the log stream — even for requests that are subsequently rejected as unauthorized. The same unredacted pattern exists in the sibling `core/capabilities/vault/gw_handler.go` at the `Debugw("received message from gateway", "req", req)` and `Infow("Sent message to gateway", "resp", response)` call sites.

## Finding Description [1](#0-0)  confirms `req` (the whole struct) is passed directly to the logger before any authorization step (`ProcessRequest` at line 427). The `Auth` field is later checked for presence (not value) only in the error path, `"hasAuth", req.Auth != ""` [2](#0-1) , which demonstrates the codebase is aware `req.Auth` is sensitive and deliberately avoids logging it directly there — but the earlier Debug statement at line 403 has no such protection and logs the raw struct value, including `Auth`. That `Auth` field is precisely the JWT bearer credential consumed by `jwtBasedAuth.AuthorizeRequest` in `core/capabilities/vault/jwt_based_auth.go` (`v.validateToken(ctx, req.Auth)`) and used throughout `authorizer.go` (`req.Auth != ""` checks) as the authentication mechanism for the gateway. The `TestVaultHandler_InvalidParamsDoesNotLogRawParams` test's comment ("Observed at Info level so the pre-existing whole-request Debug log is excluded") corroborates that the line-403 Debug log is a known, still-present, unaddressed gap distinct from the fixed invalid-params log. The analogous unredacted logging also exists in `core/capabilities/vault/gw_handler.go` lines 182 and 231, verified directly against the file.

No redaction, masking, or `MarshalLogObject`-style custom encoder was found for the `jsonrpc.Request` type in this codebase — searches for such redaction logic returned no results, meaning the zap/structured logger serializes the struct (and its `Auth` string field) verbatim.

## Impact Explanation
If DEBUG logging is enabled on the gateway/vault-handler process, any client — including one that ultimately fails authorization — has their submitted `Auth` bearer token written to disk in cleartext at the moment their request is received, before any authorization check. This maps to the "key/secret exfiltration" and "gateway request impersonation" impact classes: anyone with read access to the resulting logs could harvest a valid bearer token and replay it to impersonate the original caller against the Vault gateway. This is a genuine logging/credential-hygiene defect in the node's own code path (not a third-party dependency, and not requiring a malicious node/peer), and is consistent in severity with the cited Kafka `SaslAuthenticateRequest` DEBUG-log precedent.

## Likelihood Explanation
The trigger (sending a JSON-RPC request to the vault gateway with an `Auth` value) requires no privilege whatsoever — it's exactly the same action any legitimate caller performs. The precondition is that DEBUG-level logging is enabled on the handler component, which is an operational/log-level setting, not a code-level privilege escalation — this mirrors the same precondition structure as the underlying Kafka advisory being analogized. Given DEBUG logging is commonly turned on for troubleshooting, likelihood is realistic, not merely theoretical.

## Recommendation
- Remove `req` (or at minimum the `Auth` and `Params` fields) from the Debug log at `handler.go:403`; log only non-sensitive fields (`method`, `requestID`).
- Apply the same redaction to `gw_handler.go:182` (`"req", req`) and `:231` (`"resp", response`).
- Extend the existing `TestVaultHandler_InvalidParamsDoesNotLogRawParams`-style regression test to assert the whole-request Debug log at line 403 never contains the raw `Auth` token or raw params, even at DEBUG level.

## Proof of Concept
1. Configure the vault gateway handler logger at DEBUG level (a supported log-level setting).
2. As any client, send a JSON-RPC request (e.g., `vault.secrets.list`) to the gateway with a crafted `Auth` value in the payload, targeting `HandleJSONRPCUserMessage`.
3. Observe the log line `"handling vault request" method=... requestID=... request=<struct with Auth field populated>"` emitted at `core/services/gateway/handlers/vault/handler.go:403`, occurring before `ProcessRequest` authorization (line 427) — i.e., even rejected/unauthorized requests have their submitted credential persisted to the log stream.
4. A Go unit test can construct a `logger.TestObserved(t, zapcore.DebugLevel)` logger, invoke `HandleJSONRPCUserMessage` with a request carrying a known `Auth` value, and assert that the observed log entries at line 403 contain that value — proving the leak (this is the natural counterpart to the existing `InvalidParamsDoesNotLogRawParams` test, which explicitly excludes this code path via `InfoLevel`).
