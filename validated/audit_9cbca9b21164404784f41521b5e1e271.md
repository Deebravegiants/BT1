### Title
Webhook `shop-domain` header is trusted for tenant attribution without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request body, then hands the caller-supplied `shop-domain` header straight to the app's handler as the tenant identifier. Because the header is never part of the signed content, the equality "shop the HMAC authenticates == shop attributed to the webhook data" does not actually hold, letting a replayed, legitimately-signed body be relabeled to any victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor is read straight from an HTTP header, entirely outside the signed material: [2](#0-1) 

`HmacValidator.validate` only ever verifies `verifiable_query.to_signable_string` (the body, in this case) against the computed HMAC — it has no knowledge of `shop`, `topic`, `webhook_id`, or `api_version`: [3](#0-2) 

`Registry.process` performs exactly that check and then immediately forwards the unauthenticated `request.shop` value to the handler as the tenant identifier, with no cross-check against any known/installed shop list or session store: [4](#0-3) 

So the binding the gem implicitly claims to enforce is:
`shop authenticated by HMAC == shop delivered to WebhookMetadata`

but in reality the HMAC only authenticates the byte-for-byte body; the `shop` field is orthogonal, unauthenticated header data. Any request whose body/HMAC pair is valid for *some* shop — for example a webhook the attacker legitimately received on their own development/test store, where the raw body content is attacker-influenceable (e.g. product/order fields the attacker fully controls on their own store) — can be replayed to the app's public webhook endpoint with the `shop-domain` (or `x-shopify-shop-domain`) header rewritten to a victim shop's domain. `HmacValidator.validate` still returns `true` because it only ever recomputes the signature over `@raw_body`, and `Registry.process` will happily invoke the topic handler with `shop: <victim-shop>`.

### Impact Explanation
This breaks the shop/tenant boundary the gem is documented to enforce for webhook processing (cross-tenant confusion): an unprivileged actor who can obtain any one validly-signed webhook body (trivially available by installing/uninstalling the app, or triggering any webhook topic, on their own store) can cause the host application's webhook handler to process that data under an arbitrary victim shop's identity. Any host app that keys persistence, cache invalidation, entitlement changes, or session/data lookups off `WebhookMetadata#shop` (exactly as this gem's docs instruct) will attribute attacker-controlled data to a shop it doesn't belong to — a cross-tenant data integrity violation reachable purely through this gem's own `Registry.process` code path, without ever needing the app's `client_secret` or an access token.

### Likelihood Explanation
Requires only network access to the app's public webhook endpoint plus one legitimately-signed webhook body (obtainable by any developer who installs the target app on their own shop, or by any user who can trigger delivery of a webhook topic whose body content is fully attacker-influenced, e.g. `orders/create` with attacker-chosen order fields). No secrets, tokens, or elevated privileges of the gem's app are needed — only the standard signature validation logic that this gem itself exposes and executes.

### Recommendation
Bind the tenant identity into the authenticated material: include `shop-domain` (and ideally `topic`/`webhook-id`) in the HMAC-signable string, or require host applications to additionally verify `request.shop` against a known/installed-shop list *before* calling into a handler, and document/enforce this in `Registry.process` rather than passing the raw header value through unchecked.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and triggers a webhook topic whose payload content they fully control (e.g. by editing an order/product with attacker-chosen field values), causing Shopify to deliver a webhook with a valid `x-shopify-hmac-sha256` for that exact `raw_body`.
2. Attacker captures the raw request (`raw_body` + `x-shopify-hmac-sha256` value) and resends it directly to the app's webhook endpoint, changing only the `x-shopify-shop-domain` (or `shopify-shop-domain`) header to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `raw_body` only — unaffected by the header change — and returns `true`.
4. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: <attacker-controlled parsed body>, ...)`, causing the host app to process attacker data as if it originated from the victim shop.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
