## Title
Webhook `shop` attribution is not bound by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`, `lib/shopify_api/utils/hmac_validator.rb`)

## Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then hands the handler a `shop` value taken from an **unsigned** header. Because the app's `api_secret_key` is shared across every shop that installs the app, any merchant who has installed the app can capture a legitimate webhook (valid body + valid HMAC for their own shop) and replay it to the app's webhook endpoint while swapping the `shop-domain`/`x-shopify-shop-domain` header to any other shop's domain. The HMAC still validates (it only covers the body), but the handler receives an attacker-chosen `shop`, breaking the binding between "the entity whose secret produced this signature" and "the tenant this data is attributed to."

## Finding Description
`Utils::HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` and the app's `api_secret_key`: [1](#0-0) 

For webhook requests, `to_signable_string` is defined to be only the raw body — the `shop`, `topic`, and `webhook-id` headers are excluded from the signed material: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` (parsed straight from the header) to build the data passed to the app's handler: [3](#0-2) 

The equality the gem implicitly assumes but never enforces is:

```
shop that produced HMAC(secret, body)  ==  shop reported in the shop-domain header
```

Since `secret` (the app's `api_secret_key`) is identical for every shop that has installed the app, any merchant that is a legitimate, unprivileged installer of the app can generate a body+HMAC pair that is valid for the app's secret (by triggering any webhook on their own store), then resend that exact `(body, hmac)` pair to the app's webhook endpoint with an arbitrary victim `shop-domain` header. `HmacValidator.validate` will accept it because it never inspects the header, and `Registry.process` will dispatch the handler with `WebhookMetadata#shop` set to the attacker-chosen victim shop.

## Impact Explanation
This breaks tenant isolation: an unprivileged app-installing merchant can cause the host application's webhook handler to process attacker-controlled data while believing it originates from a different, victim shop. Depending on what the host app's webhook handlers do with `data.shop` (e.g., look up/create records keyed by shop, trigger side effects scoped to that shop, or update per-shop billing/state), this enables cross-tenant data corruption or disclosure purely through this gem's own trust boundary — the gem is the component asserting "this webhook belongs to `shop`" via `WebhookMetadata`, and that assertion is unauthenticated. This matches the Critical "cross-tenant access" impact category.

## Likelihood Explanation
Exploitation requires only that the attacker be able to install the target app on their own shop (a normal, unprivileged capability for any Shopify merchant) and be able to send an HTTP POST to the app's public webhook endpoint with custom headers — no access token, no leaked secret, and no privileged account is needed. The attacker only needs one webhook delivery from their own store to obtain a valid `(body, hmac)` pair for the shared secret.

## Recommendation
Bind the shop identity to the signed material, or otherwise cryptographically verify it, before trusting `request.shop`:
- Include the `shop-domain` (and ideally `topic`/`webhook-id`) in the signable string used for the HMAC computation in `Webhooks::Request#to_signable_string`, matching Shopify's documented webhook verification guidance of validating the full raw payload against the header actually delivered for that shop, and additionally cross-checking that the shop domain in the header corresponds to a shop actually known/installed by the host application before dispatching the handler.
- At minimum, document and enforce in `Registry.process` that host applications must independently verify `data.shop` against their own installed-shop registry before trusting webhook content, since the gem's HMAC check does not bind the shop field.

## Proof of Concept
1. Attacker installs the target Shopify app on their own development/test store (`attacker.myshopify.com`), which is a normal, unprivileged action.
2. Attacker triggers any webhook subscription (e.g., `orders/create`) on their own store, capturing the raw POST body and the `x-shopify-hmac-sha256` header sent by Shopify — this HMAC is valid because it is computed with the app's shared `api_secret_key`.
3. Attacker resends the exact same body and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` and `x-shopify-topic` to whatever value is desired.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks the body against the secret and returns `true`: [4](#0-3) 
5. The handler is invoked with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, even though the request never involved `victim-shop`, demonstrating the cross-tenant spoof.
