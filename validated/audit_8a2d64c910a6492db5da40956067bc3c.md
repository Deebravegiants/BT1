## Title
Webhook `shop` (tenant) identity is trusted from an HTTP header that is not covered by the HMAC signature, allowing cross-tenant webhook forgery — (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its signable content from the raw body only, while the `shop` (tenant) attribute is read directly from an HTTP header that is never included in the HMAC-signed data. `Registry.process` validates the HMAC and then unconditionally forwards the header-derived `shop` value to the app's webhook handler. This breaks the intended binding `HMAC_valid(body, secret) ⟺ (body, shop) genuinely originated from that shop`, letting an attacker who owns any shop capture one of their own genuinely-signed webhooks and replay it to the app's public webhook endpoint with the `shop-domain` header rewritten to a victim shop, causing the app to attribute attacker-controlled data to the victim tenant.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Webhooks::Request#shop` is derived purely from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which plays no part in the signed content: [2](#0-1) 

`HmacValidator.validate` computes/compares the signature strictly over `verifiable_query.to_signable_string` (i.e., the raw body only): [3](#0-2) 

`Registry.process` checks only that HMAC validation passes, then trusts `request.shop` (the header) as the tenant identity handed to the app's business logic: [4](#0-3) 

This is structurally analogous to the referenced report: a user/attacker-influenced field (`shop`, like the NFT `_tier`) is consumed by downstream logic without being covered/bound by the security check (HMAC, like the tier-bounds check) that is supposed to authenticate the whole message. The equality that should hold is:

`HMAC_valid ⟺ (body AND shop) attested by Shopify for that request`

but what is actually checked is:

`HMAC_valid ⟺ body attested by Shopify` (for *some* shop), with `shop` accepted unauthenticated.

### Impact Explanation
Any unprivileged actor who can install the app on a shop they control (e.g., a free Shopify development/trial store, which requires no victim credentials, no `api_secret_key`, and no privileged account) can:
1. Trigger a legitimate webhook delivery from Shopify to the app for their own shop (Shopify signs the body with the app's `api_secret_key`, so the attacker never needs to know the secret).
2. Capture the `(raw_body, hmac-sha256 header)` pair from that genuine delivery.
3. Replay an HTTP request to the app's (necessarily internet-reachable) webhook endpoint using the captured body and HMAC header unchanged, but with the `shopify-shop-domain` header rewritten to a victim shop's domain.
4. `Registry.process` validates the HMAC successfully (it only checks the body) and passes `shop: <victim-domain>` to the app's `WebhookHandler`, causing the host application to process attacker-chosen event data (order/customer/product payload contents they fully control from their own store) as if it originated from the victim tenant.

This crosses a tenant boundary using data the app implicitly trusts as coming from a specific, HMAC-authenticated shop — matching the Impact criteria for cross-tenant access.

### Likelihood Explanation
Likelihood is High for any app that:
- Exposes a single shared webhook endpoint across all installed shops (the standard, documented pattern for this gem), and
- Uses `WebhookMetadata#shop` (populated from `request.shop`) to key any tenant-scoped action (e.g., "look up shop X's shop_id/session to act on data from this payload").

No victim credentials, TLS interception, or leaked secrets are required — only the ability to install the app on an attacker-owned shop, which is the normal, unprivileged onboarding path for any Shopify app.

### Recommendation
Include the `shop` (and ideally `topic`) value in the HMAC-signed content, or otherwise cryptographically bind them to the signature, e.g., by having `Webhooks::Request#to_signable_string` incorporate the shop-domain and topic headers (subject to how Shopify's actual webhook signing scheme allows this — if Shopify's real HMAC only ever covers the raw body per their webhook spec, this constraint should instead be documented prominently as a caveat: host apps must independently verify that the `shop` returned by `WebhookMetadata` corresponds to a known, previously-installed shop before trusting it, since it is not covered by the HMAC).

### Proof of Concept
1. Install a test app on an attacker-controlled dev shop `attacker.myshopify.com`; register a webhook for a topic the app handles.
2. Trigger the webhook (e.g., update a product) and capture the raw POST body `B` and header `x-shopify-hmac-sha256: H` sent by Shopify (H is valid HMAC-SHA256 of B under the app's real secret).
3. Send a new HTTP POST to the app's webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H` (unchanged), but `x-shopify-shop-domain: victim.myshopify.com`.
4. Observe that `ShopifyAPI::Webhooks::Registry.process` accepts this request because:
   - `Utils::HmacValidator.validate(request)` succeeds since it hashes `request.to_signable_string == B` only. [5](#0-4) 
   - The handler is invoked with `shop: "victim.myshopify.com"` sourced solely from the forged header, even though the signed body actually originated from the attacker's own shop.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
