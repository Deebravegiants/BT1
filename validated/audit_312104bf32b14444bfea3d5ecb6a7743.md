### Title
Direct token transfers to `LiquidityPool` are permanently stranded - (File: contracts/pool/src/lib.rs)

### Summary
Medium. The pool holds all market tokens but tracks available liquidity in the internal `cash` field rather than the live token balance. [1](#0-0)  A direct token transfer raises the pool's balance without minting supply shares, crediting `cash`, or creating protocol revenue, and no pool or controller entrypoint withdraws that unbooked surplus. [2](#0-1) [3](#0-2) 

### Finding Description
`LiquidityPool::transfer_out` sends only the amount supplied by an accounting operation; it does not recognize excess token balance. [4](#0-3)  `claim_revenue` burns only claimable revenue shares and debits `cash`, so it cannot withdraw a donation. [3](#0-2)  `recapitalize` applies at most `amount` and refunds only the unused portion of that new amount, leaving previously transferred tokens untouched. [5](#0-4) 

On the controller path, balance-delta refunds explicitly preserve pre-existing balances. [6](#0-5)  Likewise, `claim_revenue` forwards only the controller balance increase measured during the pool claim, not any older controller-held balance. [7](#0-6) 

### Impact Explanation
Any user who transfers a supported token directly to the pool permanently loses those tokens: the assets remain at the pool address, are unavailable to suppliers through `cash`, are unavailable to the protocol through revenue shares, and cannot be returned to the sender. This is permanent freezing of user funds, with the loss bounded to the transferred amount.

### Likelihood Explanation
The trigger is an ordinary unprivileged token `transfer`; no authorization from the pool or protocol role is required. The pool address is publicly discoverable through `Controller::get_pool_address`. [8](#0-7)  Likelihood is limited by the need for a mistaken direct transfer or callback sending assets outside a declared flow, but it is fully reachable by an unprivileged address.

### Recommendation
Add an explicit surplus-recovery path for each token held by the pool. Because one physical pool balance can back multiple `(hub_id, asset)` books, the recoverable amount must be the token balance minus the sum of `cash` for every market using that asset, not merely one market's reserves. A controller-administered rescue can then send only that surplus to a governance-controlled recipient. A separate controller-balance rescue may be needed for assets sent directly to the controller.

### Proof of Concept
Assume one listed market for `asset`:

```rust
let pool = controller.get_pool_address();
let before_balance = token.balance(&pool);
let before_cash = pool.get_reserves(&hub_asset);

// Any unprivileged holder can do this directly on the token contract.
token.transfer(&alice, &pool, &100);

assert_eq!(token.balance(&pool), before_balance + 100);
assert_eq!(pool.get_reserves(&hub_asset), before_cash);
```

The extra `100` is not supply, debt, revenue, or `cash`. `claim_revenue` cannot withdraw it because no revenue shares were minted, `withdraw` cannot withdraw it because `cash` did not increase, and `recapitalize` only refunds unused portions of a newly supplied `amount`. The donation therefore remains permanently stranded.
