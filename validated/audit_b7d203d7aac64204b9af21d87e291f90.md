## Title
Webhook HMAC does not bind the `shop-domain` header, enabling cross-tenant webhook payload replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by checking the HMAC over the raw request body, then hands the *unauthenticated* `shop-domain` header straight to the merchant's webhook handler as the trusted tenant identifier. The identity binding "HMAC-authenticated data == shop the data is attributed to" does not hold, because the shop is never part of the signed content.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

`shop` is read directly from the `x-shopify-shop-domain`/`shopify-shop-domain` header with no cryptographic tie to the body or the HMAC: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately forwards `request.shop` to the handler as an authenticated field, alongside the verified body: [3](#0-2) 

`HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` (the body only) and compares it with `secure_compare`: [4](#0-3) 

Because the HMAC is keyed only to the body bytes, the binding that actually holds is:
`hmac == HMAC(body, api_secret_key)`

but the library (and every consumer relying on `WebhookMetadata#shop`) treats it as if:
`hmac == HMAC(body, api_secret_key) AND shop == authenticated_shop`

These are not equal. Any party who can obtain one valid `(body, hmac)` pair produced with the app's secret (e.g., by registering the app on their own store — an unprivileged action — and capturing a webhook Shopify sends them) can replay that exact body and HMAC to the app's public webhook endpoint while substituting an arbitrary `shop-domain` header. `Utils::HmacValidator.validate` will still return `true` because it never inspects the header, and `Registry.process` will invoke the handler with `WebhookMetadata.new(shop: <forged-shop>, body: <attacker's real body>, ...)`.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook processing: an attacker who legitimately installs the app on a shop they control can get Shopify to sign body content (e.g., an `orders/create`, `app/uninstalled`, `customers/data_request`, or any other event body they can influence through normal store actions) and then present that authenticated body under a victim shop's identity to the host application, which keys persistence, billing, GDPR, and data-sync actions off `WebhookMetadata#shop`. This is cross-tenant data injection/confusion using data authenticated only for the attacker's own tenant — matching the Critical "cross-tenant access" category.

### Likelihood Explanation
Exploitation only requires: (1) installing the app on an attacker-owned development/trial store (no special privilege), (2) capturing one webhook delivery for that store (raw body + `X-Shopify-Hmac-Sha256`), and (3) POSTing the same body/HMAC to the app's public webhook URL with a forged `X-Shopify-Shop-Domain` header. No knowledge of `api_secret_key` or access tokens is required, since the attacker uses a genuinely-signed body rather than forging the signature.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) inside the signed/verified material, or otherwise cryptographically bind `request.shop` before it is exposed to handlers — e.g., verify it against the shop associated with the specific webhook subscription/session rather than trusting the header verbatim. At minimum, document that `WebhookMetadata#shop` is unauthenticated and must be independently verified by the host app (for example, cross-checked against a stored session for that shop) before being used for tenant-keyed lookups.

### Proof of Concept
1. Install the target app (any app using this gem) on an attacker-controlled store `attacker.myshopify.com`.
2. Trigger a webhook (e.g., `orders/create`) and capture the raw POST body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
3. Replay to the app's public webhook endpoint:
```
POST /webhooks HTTP/1.1
X-Shopify-Topic: orders/create
X-Shopify-Hmac-Sha256: H
X-Shopify-Shop-Domain: victim-shop.myshopify.com
X-Shopify-Webhook-Id: <any>
X-Shopify-Api-Version: 2024-01

B
```
4. `Utils::HmacValidator.validate` recomputes `HMAC(api_secret_key, B)`, matches `H`, and returns `true` (see `lib/shopify_api/utils/hmac_validator.rb:26-31`), since the shop header is never part of `to_signable_string`.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) invokes the registered handler with `shop: "victim-shop.myshopify.com"` and the attacker's authenticated body `B`, even though Shopify never issued this webhook for `victim-shop`.
