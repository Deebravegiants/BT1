### Title
Backend-pushed config refresh can retroactively change `operator_qr_expiration_time` mid-signup, causing unexpected QR-freshness enforcement / signup blocking - (File: `src/brokers/observer.rs`, `src/plans/mod.rs`, `src/config.rs`)

### Summary
`operator_qr_expiration_time` is a backend-controlled configuration value used purely as a security/freshness threshold to decide whether a previously-scanned operator QR-code (and its verified location data) is still valid to continue a signup, analogous to `timewindow` in the Vault contracts. This value is not pinned for the duration of a signup: it is re-read from the shared, mutable `Config` at multiple independent points during the same signup flow, while a background task silently overwrites the shared config in place at a fixed interval, regardless of whether a signup is currently in progress.

### Finding Description
The orb keeps a single shared `Arc<Mutex<Config>>` that is replaced wholesale by a background task: [1](#0-0) 
This `config_update` runs on every tick of `config_update_interval` as long as the network is unblocked, with no check on `signup_flag` or any other indicator that a signup is in progress: [2](#0-1) 

The freshness-relevant field `operator_qr_expiration_time` is downloaded from the backend and installed into the shared config unconditionally: [3](#0-2) [4](#0-3) 

Within a single top-level signup loop iteration, `operator_qr_expiration_time` is captured once at the top of `MasterPlan::run` and used to decide whether to (re)scan the operator QR-code and to gate the idle wait for the signup request: [5](#0-4) [6](#0-5) 

But later, inside `do_signup` — which runs after `idle_wait_for_signup_request` returned a set of already-scanned QR codes/operator data — the value is **re-read from the shared config a second time**, independently of the value used earlier in the same signup: [7](#0-6) 
This second value is then used by `scan_remaining_qr_codes` to decide whether the already-captured `operator_data.timestamp` is still "fresh enough": [8](#0-7) 

If the background `config_update` task swaps in a new config between the first read (in `run`/`idle_wait_for_signup_request`) and the second read (in `do_signup`), the freshness boundary applied to the *same* already-scanned `operator_data` changes retroactively, exactly mirroring the Vault bug: a value that was true/valid under the config at time T0 can become false/invalid (or vice-versa) under a different config value read at T1, even though nothing about the user's own action changed.

### Impact Explanation
- If the backend shortens `operator_qr_expiration_time` between the two reads, an operator QR-code/location verification that was valid and accepted earlier in the very same signup session is retroactively treated as expired in `scan_remaining_qr_codes`, forcing the flow back into `_ => { ... scan_operator_qr_code ... }` and discarding the already-verified operator authorization — unexpectedly disrupting an in-progress, otherwise-valid signup for an unprivileged user, exactly the "feels unfair / wastes the flow" impact described in the reference report, but here applied to signup authorization state rather than a financial deposit.
- If the backend lengthens `operator_qr_expiration_time` between the two reads, previously captured `operator_data` (whose freshness was meant to be bounded by the value in effect when it was captured) is granted an extended validity window it was never scanned/verified under, weakening the freshness guarantee that `operator_qr_expiration_time` is meant to enforce for operator identity/location binding during a signup — a cross-check inconsistency between the value used to authorize the operator QR and the value used to re-validate it later in the same flow.
- Both directions are a direct analog of the "M-08" bug class: a privileged party's config change takes effect immediately and is applied non-atomically/retroactively to an already-in-flight, unprivileged operation (here, the signup flow's operator/user QR authorization state) instead of only affecting subsequent, newly-started flows.

### Likelihood Explanation
`config_update` runs automatically and continuously (governed by `CONFIG_UPDATE_INTERVAL`) without any coordination with the signup state machine, and signups routinely span multiple seconds to tens of seconds (QR scans, biometric capture, etc.), so a config refresh landing in the middle of `run`→`do_signup` is a realistic, non-adversarial timing window; it does not require a malicious operator, only an ordinary backend-initiated configuration push while a signup happens to be active.

### Recommendation
Snapshot all timing-sensitive config values (in particular `operator_qr_expiration_time`) once at the start of a signup attempt and thread that single snapshot through the entire signup flow (`run`, `idle_wait_for_signup_request`, `do_signup`, `scan_remaining_qr_codes`, etc.) instead of re-reading the shared `Config` from the mutex mid-flow. Alternatively, gate the background `config_update` task on `signup_flag` so config swaps are deferred until no signup is in progress, or apply updated config values only to freshly-started signups rather than to state already captured in an active one.

### Proof of Concept
1. Orb starts a signup: `MasterPlan::run` reads `operator_qr_expiration_time = T1` from config and scans/verifies the operator QR code, storing `operator_data.timestamp = now`.
2. While the signup is still in progress (`idle_wait_for_signup_request` → `do_signup`), the background observer task's `config_update` fires (per `CONFIG_UPDATE_INTERVAL`), downloads a fresh backend config with `operator_qr_expiration_time = T2` (shorter than T1), and installs it via `*config.lock().await = new_config;` (`src/brokers/observer.rs` lines 194–202).
3. `do_signup` re-reads config and obtains `operator_qr_expiration_time = T2`.
4. `scan_remaining_qr_codes` evaluates `operator_data.timestamp.elapsed() < operator_qr_expiration_time` using `T2`; if `operator_data.timestamp.elapsed()` now exceeds `T2` (even though it was well within `T1` when originally scanned), the branch falls through and the already-authorized operator QR is discarded, forcing the user to restart the operator/user QR scanning step of an already in-progress signup.
