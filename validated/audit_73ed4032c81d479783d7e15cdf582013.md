This confirms the finding. The docs explicitly state at `docs/usage/webhooks.md:125` that `Registry.process` "will verify the request did indeed come from Shopify" — implying the `shop` field carried in `data.shop` is trustworthy — while the actual verification in `HmacValidator.validate` only covers `to_signable_string`, which is defined in `lib/shopify_api/webhooks/request.rb:36-38` as the raw body alone. The `shop` header is parsed independently in `shop` (`lib/shopify_api/webhooks/request.rb:20-23`) and passed straight into `WebhookMetadata` in `lib/shopify_api/webhooks/registry.rb:198-199` without any cryptographic binding to the HMAC-verified body.

### Title
Webhook `shop` field is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from only the raw body (`to_signable_string` returns `@raw_body`), while the `shop` (and `topic`, `api_version`, `webhook_id`) values are read from unauthenticated HTTP headers and forwarded to the host application's handler as trusted metadata. This breaks the intended binding `verified(body) == trusted(shop)`.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` gates handler execution on `Utils::HmacValidator.validate(request)` [1](#0-0) . That validator recomputes an HMAC over `verifiable_query.to_signable_string` and compares it to the `hmac` header using `OpenSSL.secure_compare` [2](#0-1) . For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` [3](#0-2) , while `shop` is parsed straight from the `shop-domain` header with no cryptographic tie to that HMAC [4](#0-3) . After the HMAC check passes, `shop` is forwarded verbatim into `WebhookMetadata` and handed to the app's handler [5](#0-4)  and [6](#0-5) .

Because the (body, HMAC) pair remains valid for *any* header set, an attacker who obtains one genuinely signed webhook payload (trivially achievable by installing the app on their own free Shopify development store and triggering a webhook) can replay that exact body and HMAC to the app's public webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header value naming a victim shop. `HmacValidator.validate` still returns `true` since it never inspects the header, and `Registry.process` passes the forged `shop` string straight through to the handler as if Shopify had attested to it.

The library's own documentation reinforces the false assumption that this call "will verify the request did indeed come from Shopify," implying the whole payload — including `shop` — is authenticated [7](#0-6) .

### Impact Explanation
Host applications are documented to key their tenant-scoped logic directly off `data.shop` (e.g., `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) [8](#0-7) . Because this gem supplies no guarantee that `shop` corresponds to the shop that actually produced the signed body, an attacker can attribute one shop's webhook payload to another tenant of the same app, causing the host application to write/act on data under a victim `shop` identifier it never actually received from Shopify — a cross-tenant data integrity/confusion issue for any app that trusts `WebhookMetadata#shop` as gem-verified (as the docs suggest it is).

### Likelihood Explanation
Requires only unprivileged capability: (1) create a free Shopify development store and app installation to obtain one legitimately signed `(body, hmac)` pair for any topic, and (2) send an unauthenticated POST to the app's public webhook route with the captured body/HMAC headers but a substituted `shop-domain` header. No access token, `client_secret`, or privileged account of the victim is needed.

### Recommendation
- Short term: document prominently that `shop`/`topic`/`webhook_id`/`api_version` headers are **not** covered by the HMAC and must not be trusted as authenticated without an out-of-band shop confirmation (e.g., cross-checking against a known, previously-stored session/shop, or validating the webhook came over a topic/shop combination the app actually registered).
- Long term: extend `to_signable_string` (or add a secondary check in `Registry.process`) to bind the `shop` header into the verified material, or require the host app to pass an already-known/expected shop identifier for cross-validation before dispatching to the handler.

### Proof of Concept
1. Attacker creates a free Shopify partner/dev store `attacker.myshopify.com`, installs the target app, and triggers a webhook (e.g., `orders/create`) to receive a genuine `{raw_body, x-shopify-hmac-sha256}` pair signed with the app's real secret.
2. Attacker sends `POST /callback/orders/create` directly to the app's public endpoint (bypassing Shopify) with:
   - Body: the captured raw JSON body (unchanged)
   - Header `x-shopify-hmac-sha256`: the captured, still-valid HMAC
   - Header `x-shopify-shop-domain`: `victim-shop.myshopify.com` (any value the attacker wants)
   - Header `x-shopify-topic`: unchanged
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks the body against the HMAC [9](#0-8) .
4. `WebhookMetadata.shop` is set to `"victim-shop.myshopify.com"` and forwarded to the app handler, which (per the gem's own documented usage pattern) treats it as the authenticated originating shop [10](#0-9) .
