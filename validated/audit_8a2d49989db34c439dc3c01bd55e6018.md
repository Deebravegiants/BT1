### Title
Relay-fee guard `hasPaidToRelay` can be satisfied without transferring any fee, allowing relay gas costs to go uncompensated - (File: `contracts/Hinkal.sol`)

### Summary
`_internalTransact()` in `contracts/Hinkal.sol` uses a boolean flag, `hasPaidToRelay`, to guarantee that a relay named in `circomData.relay` receives compensation whenever a relay is used. The flag is set to `true` merely by entering the withdrawal branch of the per-token loop, regardless of whether the computed `relayFee` for that token is actually non-zero. A prover can include a token slot with `amountChanges[i] == 0` that is not the designated `feeStructure.feeToken`, which satisfies the withdrawal branch, sets `hasPaidToRelay = true`, and transfers `0` to the relay, while every other token in the batch can be a pure deposit (`amountChanges[i] > 0`, which never touches the relay-fee logic at all). This is analogous to the referenced report's root cause: a protective invariant (`_nftContractToTokenIdToFirstSaleCompleted` / fee bookkeeping) is flipped to "satisfied" by an unrelated/incidental code path instead of by the actual event it is meant to represent, letting fees be skipped.

### Finding Description
```solidity
function _internalTransact(CircomData calldata circomData) private {
    bool hasPaidToRelay = false;
    for (uint64 i = 0; i < circomData.erc20TokenAddresses.length; i++) {
        int256 deltaAmountChange = _calculateDeltaAmount(circomData, i);

        if (deltaAmountChange > 0) {
            // deposit branch - relay logic never runs here
            ...
        } else {
            uint256 sumAbs = uint256(-deltaAmountChange);           // == 0 for a zero-delta slot
            uint256 relayFee = 0;
            if (circomData.relay != address(0)) {
                uint256 flatFee = circomData.feeStructure.feeToken ==
                    circomData.erc20TokenAddresses[i]
                    ? circomData.feeStructure.flatFee
                    : 0;                                            // 0 if token != feeToken

                require(sumAbs >= flatFee, "Relay Fee is over withdraw amount"); // 0 >= 0 passes

                uint256 recipientAmount = ((10000 -
                    circomData.feeStructure.variableRate) *
                    (sumAbs - flatFee)) / 10000;                      // = 0
                relayFee = sumAbs - recipientAmount;                  // = 0

                if (relayFee > 0) { transferERC20TokenOrETH(...); }   // skipped, relayFee == 0
                hasPaidToRelay = true;                                // <-- set unconditionally
            }
            if (sumAbs - relayFee > 0) { transferERC20TokenOrETH(...); } // skipped, sumAbs == 0
        }
    }
    require(
        circomData.relay == address(0) || hasPaidToRelay,
        "relay not paid"
    );
}
``` [1](#0-0) 

The equality that should hold is: *if `circomData.relay != address(0)`, the relay must receive non-zero compensation for the work of submitting/sponsoring the transaction*. Instead, the contract only checks that the withdrawal branch of the loop executed at least once (`hasPaidToRelay = true`), not that any value was actually transferred to the relay in that branch. A token slot with `amountChanges[i] == 0` (not the fee token) drives `sumAbs = 0`, `flatFee = 0`, `relayFee = 0`, satisfying the `require` at the end while transferring nothing.

Because `circomData.feeStructure` (which includes `feeToken`, `flatFee`, `variableRate`) is entirely attacker/prover-supplied data that only needs to match the `calldataHash` component built in `getHashedCalldata2` — it is never separately constrained by the circuit to guarantee a minimum fee is paid — the prover has full freedom to pick a zero-delta, non-fee-token slot purely to flip the flag. [2](#0-1) [3](#0-2) 

The balance-equation check in `transact()` does not prevent this: for a token with `amountChanges[i] == 0`, `onChainCreation[i] == false`, and no output UTXO for that token, `balanceDif == 0 == amountChanges[i] + utxoAmount` trivially holds. [4](#0-3) 

### Impact Explanation
This is a "theft ... of protocol/relay fees" scenario (High per the given severity rubric). A relay is expected to submit `transact()` on a user's behalf and be compensated in-band via `relayFee`; the `require(circomData.relay == address(0) || hasPaidToRelay, ...)` check exists specifically as the on-chain guarantee that this compensation actually occurred. By padding the token array with one zero-delta, non-fee-token slot, a user can construct a batch that is otherwise pure deposits (which never touch the fee logic at all, since `deltaAmountChange > 0` skips the whole `else` branch) while still passing the "relay was paid" gate with zero funds transferred to the relay — extracting relay-sponsored submission/gas without paying anything, despite the contract's own invariant claiming otherwise.

### Likelihood Explanation
Likelihood is moderate to high for any relay-facing flow: the attacker controls all of `circomData` (subject only to hashing/circuit constraints that do not touch fee amounts), needs no special privilege, and the exploit requires only a single extra harmless-looking token slot with a zero amount change. Any off-chain relay logic that trusts the on-chain `"relay not paid"` require statement as sufficient proof of compensation (rather than independently re-deriving expected fee amounts per token) would be silently underpaid.

### Recommendation
Track the actually-transferred relay fee total (sum of `relayFee` across all tokens) rather than a boolean "did we enter the branch" flag, and require that total to be non-zero (or match an expected minimum) whenever `circomData.relay != address(0)`. Alternatively, require `hasPaidToRelay` to only be set when `relayFee > 0` was actually transferred, and separately enforce that at least one token slot corresponds to a genuine withdrawal (`sumAbs > 0`) whenever a relay is specified, so that pure-deposit batches cannot claim to have paid a relay fee that was never economically real.

### Proof of Concept
1. Attacker/prover crafts a `transact()` call with `circomData.relay = <validRegisteredRelay>` and two token slots:
   - Slot 0: `erc20TokenAddresses[0] = TokenA` (the actual token being deposited), `amountChanges[0] = +100` (a deposit) — this hits the `deltaAmountChange > 0` branch, which never runs any relay-fee logic.
   - Slot 1: `erc20TokenAddresses[1] = TokenB` (any token ≠ `feeStructure.feeToken`), `amountChanges[1] = 0`, with matching zero-value nullifiers/outputs so the balance equation trivially holds for that slot.
2. In `_internalTransact`, slot 1 falls into the `else` branch: `sumAbs = 0`, `flatFee = 0` (TokenB ≠ feeToken), `relayFee = 0`, no transfer occurs, but `hasPaidToRelay = true` is set. [5](#0-4) 
3. Final check `require(circomData.relay == address(0) || hasPaidToRelay, "relay not paid")` passes despite zero value ever reaching the relay. [6](#0-5) 
4. The transaction succeeds: TokenA deposit completes, `circomData.relay` is recorded/associated with the tx, but the relay receives nothing.

Note: I was not able to fully trace how a relay's off-chain submission logic decides whether to broadcast a given `circomData` payload (that code is off-chain/not part of this repo), so the practical exploitability depends on relay implementations trusting this on-chain check as sufficient proof of payment; this repo-level analysis only establishes that the on-chain invariant itself is bypassable.

    function _internalTransact(CircomData calldata circomData) private {
        bool hasPaidToRelay = false;
        for (uint64 i = 0; i < circomData.erc20TokenAddresses.length; i++) {
            int256 deltaAmountChange = _calculateDeltaAmount(circomData, i);

            if (deltaAmountChange > 0) {
                require(
                    circomData.externalActionData.externalAddress == msg.sender,
                    "Deposit should come from the sender"
                );
                transferERC20TokenFromOrCheckETH(
                    circomData.erc20TokenAddresses[i],
                    circomData.externalActionData.externalAddress,
                    address(this),
                    uint256(circomData.amountChanges[i])
                );
            } else {
                uint256 sumAbs = uint256(-deltaAmountChange);
                uint256 relayFee = 0;
                if (circomData.relay != address(0)) {
                    uint256 flatFee = circomData.feeStructure.feeToken ==
                        circomData.erc20TokenAddresses[i]
                        ? circomData.feeStructure.flatFee
                        : 0;

                    require(
                        sumAbs >= flatFee,
                        "Relay Fee is over withdraw amount"
                    );

                    uint256 recipientAmount = ((10000 -
                        circomData.feeStructure.variableRate) *
                        (sumAbs - flatFee)) / 10000;

                    relayFee = sumAbs - recipientAmount;

                    if (relayFee > 0) {
                        transferERC20TokenOrETH(
                            circomData.erc20TokenAddresses[i],
                            circomData.relay,
                            relayFee
                        );
                    }
                    hasPaidToRelay = true;
                }
                if (sumAbs - relayFee > 0) {
                    transferERC20TokenOrETH(
                        circomData.erc20TokenAddresses[i],
                        circomData.externalActionData.externalAddress,
                        sumAbs - relayFee
                    );
                }
            }
        }
        require(
            circomData.relay == address(0) || hasPaidToRelay,
            "relay not paid"
        );
    }
