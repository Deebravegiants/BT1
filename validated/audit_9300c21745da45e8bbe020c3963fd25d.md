I have enough evidence to confirm the vulnerability. The `shop` field is passed to the app's handler for tenant-scoped actions (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, ...)` per the gem's own documentation), but that field is derived from an unauthenticated HTTP header and excluded from the HMAC-covered content.

### Title
Webhook `shop` field is trusted for tenant identity but excluded from HMAC verification, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` extracts the `shop` (tenant identity) from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, but `#to_signable_string` — the content actually verified by `Utils::HmacValidator` — only covers the raw request body. The shop header is never included in the HMAC-verified bytes, so any request with a valid body+HMAC pair can carry an attacker-chosen `shop` value that the app trusts as the webhook's tenant.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` validates a webhook using only `Utils::HmacValidator.validate(request)`: [1](#0-0) 

The HMAC validator computes the signature over `verifiable_query.to_signable_string`: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` returns only `@raw_body`, while `shop` is read from a separate, unauthenticated header: [3](#0-2) 

After HMAC validation succeeds, `request.shop` is forwarded verbatim into `WebhookMetadata` and handed to the app's handler as the tenant identifier: [4](#0-3) [5](#0-4) 

The gem's own documented usage pattern treats `data.shop` as an authenticated tenant key for downstream dispatch (e.g. enqueuing per-shop jobs): [6](#0-5) 

This breaks the identity binding: `HMAC(raw_body) == valid` should imply `shop == the shop that Shopify actually sent this body for`, but the equality that actually holds is only `HMAC(raw_body) == valid`, independent of `shop`. Any HTTP client (not just Shopify) can send a request with a **replayed, previously-observed valid `(raw_body, hmac)` pair** — obtainable by an unprivileged user who is a merchant that installed the app and can trigger a webhook to their own shop (or observe one via any exposed endpoint/log) — together with an arbitrary `shopify-shop-domain` header, and the gem will treat it as an authentic webhook "from" the spoofed shop, since only the body is authenticated.

### Impact Explanation
This allows cross-tenant confusion: a malicious merchant (an unprivileged installer of the app, not requiring `api_secret_key` or any leaked credential) can cause the app to process a webhook body under a different shop's identity. Depending on the app's handler logic (which the gem's docs explicitly encourage keying off `data.shop`), this can lead to data being associated with, or actions taken against, the wrong tenant — a cross-tenant access impact.

### Likelihood Explanation
Exploitation requires only the ability to send arbitrary HTTP requests to the app's public webhook endpoint plus one previously observed valid `(body, hmac)` pair (trivially obtainable by an attacker who has legitimately installed the app and can generate/replay their own webhooks, or capture one via any accessible log/proxy). No secret material or elevated privilege is needed to forge the `shop` header itself.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook-id`) header values in the HMAC-signed content that `Webhooks::Request#to_signable_string` returns (or otherwise cryptographically bind them), so that HMAC validation fails if the shop header is altered relative to what Shopify actually signed for that delivery. At minimum, document and enforce that `data.shop` must never be used as an unauthenticated tenant key without independent verification.

### Proof of Concept
1. App receives a legitimate webhook for `shop-a.myshopify.com` with body `B` and valid header `x-shopify-hmac-sha256: H` (a merchant who installed the app can trigger this, e.g., via `products/update`).
2. Attacker captures `(B, H)` (e.g., from their own webhook delivery logs, which they legitimately have access to for their own shop).
3. Attacker sends a new HTTP request to the app's webhook endpoint with the same raw body `B`, the same `x-shopify-hmac-sha256: H` header, but `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` succeeds because it only checks `H` against `B` — it never inspects the shop header: [7](#0-6) 
5. `Registry.process` calls the app's handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: B, ...)`, which the app trusts as an authentic webhook for `victim-shop`.
