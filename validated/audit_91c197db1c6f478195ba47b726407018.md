This confirms the finding: in the OAuth flow, `AuthQuery#to_signable_string` explicitly includes `shop` in the HMAC-signed string (`lib/shopify_api/auth/oauth/auth_query.rb:34-43`), correctly binding the shop identity to the signature. But in the webhook flow, `Request#to_signable_string` returns only `@raw_body` (`lib/shopify_api/webhooks/request.rb:35-38`), so the `shop` field (from the `x-shopify-shop-domain` header) is never covered by the HMAC, yet `Registry.process` passes `request.shop` straight into `WebhookMetadata` given to the app's handler (`lib/shopify_api/webhooks/registry.rb:189-199`, `lib/shopify_api/webhooks/webhook_handler.rb:6-12`).

### Title
Webhook `shop` identity is not bound to the HMAC, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw body only, while the `shop` attribute used for tenant identification is read from an unsigned header. This breaks the binding `hmac_covers(shop) == true` that the gem enforces elsewhere (e.g., in OAuth), letting an attacker who can obtain any one valid `(body, hmac)` pair for the shared app secret relabel it as coming from a different shop.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` verifies `verifiable_query.hmac` against `verifiable_query.to_signable_string` using `Context.api_secret_key`, which is the same secret for every shop installed on the app [1](#0-0) . For webhook requests, `to_signable_string` returns only `@raw_body`, and `hmac` is parsed from the `hmac-sha256` header — but `shop` is parsed from a separate, unauthenticated `shop-domain` header that plays no role whatsoever in the signature: [2](#0-1) 

`Registry.process` validates the HMAC, then immediately trusts `request.shop` to build the `WebhookMetadata` passed to the host app's handler: [3](#0-2)  `WebhookMetadata.shop` is a plain, unauthenticated `String` field [4](#0-3) .

This is inconsistent with how the gem treats the analogous `shop` field in the OAuth callback: there, `AuthQuery#to_signable_string` explicitly folds `shop` into the signed parameter set before computing the HMAC, so tampering with `shop` invalidates the signature [5](#0-4) . No equivalent binding exists for webhooks — the equality the library should be enforcing, `hmac == HMAC(secret, shop || body)`, is instead only `hmac == HMAC(secret, body)`, so `shop` is a free variable an attacker fully controls after obtaining any single valid `(body, hmac)` pair signed with the app's shared secret.

Because `api_secret_key` is one value per app (not per shop), any actor who can get a genuine webhook delivered to them for their own store (e.g., by installing the app on their own development/test shop, which any unprivileged internet user can do for any public app) obtains a `(raw_body, hmac)` pair that is valid for every shop on that app. They can then replay that exact body/HMAC to the app's webhook endpoint while substituting `x-shopify-shop-domain` with a victim merchant's domain. `Utils::HmacValidator.validate` will still pass, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload originated from the victim shop.

### Impact Explanation
This crosses a tenant boundary that the library's own `WebhookHandler` contract implicitly relies on: handlers are invoked with `data.shop` as the source of truth for which merchant's data to update, matching the Critical criterion "cross-tenant access." Any application built on this gem's webhook API that keys per-shop side effects (order sync, inventory writes, session/API-credential lookups by shop, billing state, etc.) off `data.shop` can be manipulated into applying an attacker-controlled shop's payload data to a different, unrelated merchant's tenant, without needing the victim's credentials, access token, or `client_secret` — only a genuine webhook obtained from the attacker's own store.

### Likelihood Explanation
Likelihood is high for any public/multi-tenant app using this gem: obtaining one valid webhook is trivial (install the app on any shop, including a free development store, and wait for/trigger an event), and no part of the signature depends on which shop it was issued for. The only obstacle is that Shopify's platform normally sends webhooks from Shopify's own infrastructure to the app's registered endpoint, so the "attacker" must actually be able to reach that endpoint directly (which is standard for any public HTTP webhook receiver) and craft the `x-shopify-shop-domain` header — both are unprivileged capabilities from the internet.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the HMAC-signable string for webhooks, mirroring `AuthQuery#to_signable_string`, or otherwise require that `WebhookHandler` implementations receive shop identity from a value that has been cryptographically bound to the signed payload rather than a bare header. At minimum, document that `WebhookMetadata#shop` is unauthenticated and must not be trusted for tenant selection without an out-of-band check.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com` and capture one legitimate webhook delivery: raw body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)` (`lib/shopify_api/webhooks/request.rb:12,36-38`).
2. Replay a POST to the app's webhook endpoint with the same body `B` and same `x-shopify-hmac-sha256: H`, but set `x-shopify-shop-domain: victim.myshopify.com`.
3. `Utils::HmacValidator.validate` recomputes `HMAC(api_secret_key, B)`, which still equals `H`, so validation succeeds (`lib/shopify_api/utils/hmac_validator.rb:27-31`).
4. `Registry.process` invokes the registered handler with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: JSON.parse(B), ...)` (`lib/shopify_api/webhooks/registry.rb:189-199`), causing the attacker's own webhook body to be processed as if it belonged to `victim.myshopify.com`.
