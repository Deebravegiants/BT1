### Title
Webhook shop identity spoofing — the `shop` field used to identify the tenant is not covered by the HMAC signature ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then unconditionally trusts the `shop`/`shop-domain` value extracted from an HTTP header — a value that is never included in the signed material — as the authoritative tenant identifier passed to the application's webhook handler.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`, whose `to_signable_string` is what gets HMAC-verified: [1](#0-0) 

Only `@raw_body` is fed into the signature. The `shop` accessor is derived from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is completely outside the signable string: [2](#0-1) 

`Registry.process` validates HMAC (over body only) and then, without any further check binding `shop` to that signature, forwards `request.shop` straight to the handler as the tenant identity: [3](#0-2) 

This is exactly the identity-binding break called out in the analog hint: "a field acted on but not covered by the HMAC." The equality that should hold is:

`shop used to authorize/attribute the webhook == shop covered by the verified signature`

but instead:

`shop used to authorize/attribute the webhook (header, attacker-controlled) != bytes actually verified by HMAC (raw_body only)`

Because all shops installed on a given app share the same `api_secret_key`, any party who can obtain one genuine `(raw_body, hmac)` pair for the app — e.g., by installing the app on their own (free) development/trial store and capturing a real webhook delivery — can replay that exact body+HMAC pair to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header pointing at a victim shop that also uses the same app. `Utils::HmacValidator.validate` will still succeed because it never looks at the header, and the forged `shop` is delivered to the app's `WebhookHandler#handle` as if it were authentic.

### Impact Explanation
This breaks the tenant boundary the gem's webhook API is supposed to enforce: an attacker (an unprivileged internet user who merely installed the app on a store they control) can make the host application process arbitrary webhook payloads under a different, victim shop's identity. Depending on which topic is spoofed, this enables cross-tenant data injection/corruption (e.g., orders/products data attributed to the wrong shop), or abuse of sensitive lifecycle topics such as `app/uninstalled` or GDPR webhooks against a shop the attacker does not control, causing the host app to mutate/delete another tenant's stored session or data. This is a cross-tenant access issue.

### Likelihood Explanation
Likelihood is significant but not universal: the attacker must obtain at least one genuine `(raw_body, hmac)` pair from the shared-secret app, which is achievable by any unprivileged actor who installs the (often free-to-install) app on a development store and captures one of their own legitimate webhook deliveries. No access to `api_secret_key`, tokens, or victim credentials is required — only the ability to receive a webhook for their own store and re-POST it with a modified header to the same public endpoint.

### Recommendation
Do not treat the `shop`/`shop-domain` header as trusted merely because the body-level HMAC validated. `Registry.process` (or the consuming application) should cross-check `request.shop` against the shop of a known, previously-established session/installation before dispatching to the handler, and/or the gem should document explicitly that `shop` is unauthenticated header data that must be independently verified by the host application against its own installed-shop registry before being used for any tenant-scoped action.

### Proof of Concept
1. Attacker installs the target Shopify app on their own (free) development store `attacker.myshopify.com`.
2. Attacker triggers a webhook event (e.g., updates a product) and captures the resulting POST: `raw_body` and header `x-shopify-hmac-sha256`.
3. Attacker re-sends the identical `raw_body` and `x-shopify-hmac-sha256` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com` (a real shop that has the same app installed).
4. `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb`) succeeds because it only checks the body against the shared secret.
5. `Registry.process` builds `WebhookMetadata.new(... shop: "victim.myshopify.com" ...)` and invokes the app's handler, which processes/stores the attacker's payload as if it originated from `victim.myshopify.com`.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
