### Title
Flashloan-manipulated Uniswap V4 spot tick prices FXFiller fills, and the overfill clamp meant to bound that exact risk is disabled - ([File: sdk/packages/simplex/src/strategies/fx.ts])

### Summary
`FXFiller` prices "venue-priced" pairs directly off a Uniswap V4 pool's current spot tick/`sqrtPriceX96` (no TWAP), and the only guard against a manipulated pool (`checkPriceGuard`/`maxDeviationBps`) is optional and coarse. The one control specifically documented to bound loss from "a bug / stale cache / manipulated venue price" — the per-leg overfill clamp — is explicitly disabled in code, so a manipulated quote flows straight into the payout with no ceiling.

### Finding Description
For curveless pairs whose `token0` is a USD stable, `resolveLegRates` prices the leg from the live Uniswap V4 pool instead of a static curve: [1](#0-0) 

The venue price itself is derived straight from the pool's current `slot0` (`sqrtPriceX96`/tick), refreshed on demand, with no time-weighting: [2](#0-1) 

The only defense is `checkPriceGuard`, which compares the *current* quote against a static, operator-set `referencePrice` within `maxDeviationBps` — and it is opt-in: "The two fields must be set together; omit both to leave the chain unguarded": [3](#0-2) [4](#0-3) 

Even where configured, the guard only bounds deviation from a static price, not execution cost, and does not stop an attacker from pushing the tick to the edge of the allowed band on every order. The documentation for this exact path states plainly: "`checkPriceGuard` is the only defense on this path, and it checks deviation from a static reference, not execution cost": [5](#0-4) 

Critically, the secondary safety net designed specifically for this scenario — capping payout to `(1 + maxOverfillBps) × user-requested amount` when pricing comes from an on-chain venue — is a no-op today. The code computes the ceiling, detects the breach, and only logs a warning instead of clamping: [6](#0-5) 

This is confirmed as an intentional but dangerous decision in the repo's own decision log: "the clamp at the overfill-ceiling block is still a no-op assignment... `maxOverfillBps` and the halt subsystem remain dormant config": [7](#0-6) 

The `targetOutput` derived from this unclamped, venue-sourced rate is what the filler actually pays out, funded from wallet balance and/or by withdrawing LP liquidity: [8](#0-7) 

### Impact Explanation
This mirrors the reported bug class precisely: an unprivileged actor can use a flashloan and a large swap against the configured Uniswap V4 pool to shift its spot tick, causing `getExoticTokenPrice`/`resolveLegRates` to return an inflated rate for the exotic token. The attacker then submits (or has a bid filled for) an intent order that the filler prices using this manipulated venue quote. Because:
1. The price guard is optional and, even when present, only bounds against a static reference within a configurable band (not against execution cost or price impact), and
2. The overfill clamp that exists specifically to bound "manipulated venue price" losses is disabled and only warns,

the filler will pay out the unclamped, manipulated amount — directly transferring solver-owned wallet funds and/or LP position liquidity to the attacker within the manipulated block. This is concrete theft of solver/protocol funds, reachable from a single flashloan transaction plus intent submission, with no privileged access required.

### Likelihood Explanation
High for any deployment using Uniswap V4 pool-based pricing without a configured price guard (the docs explicitly allow omitting it, "leaving the chain unguarded"). Even with a guard configured, an attacker can still move the tick up to the allowed deviation band repeatedly to extract profit, since the overfill clamp — the second line of defense — is confirmed disabled in code and only emits a warning rather than bounding payout.

### Recommendation
- Replace or supplement the spot `sqrtPriceX96`/tick read with a TWAP-based or otherwise manipulation-resistant price source for Uniswap V4 venue pricing.
- Make the price guard (`referencePrice`/`maxDeviationBps`) mandatory for any venue-priced pair rather than optional.
- Re-enable the `maxOverfillBps` clamp so venue-priced legs are hard-capped to `(1 + maxOverfillBps) × user-requested output` instead of only logging a warning, restoring the loss bound the code comments describe as its intended purpose.
- Re-arm `recordOrderOutcome`/the auto-halt path so repeated clamp triggers actually stop the filler rather than remaining dormant.

### Proof of Concept
1. Operator runs `FXFiller` with a curveless pair priced from a `[vault.uniswapV4]` position, with no `referencePrice`/`maxDeviationBps` configured (permitted per docs) — or with a guard configured but a wide/typical deviation band.
2. Attacker takes a flashloan, performs a large swap against the configured Uniswap V4 pool to move `sqrtPriceX96`/tick so that `computeDirectPoolPriceUsd` reports the exotic token as cheaper than fair value.
3. In the same block, attacker (or their bid) triggers an order fill; `resolveLegRates` → `venueUsdPrice` returns the manipulated rate; `checkPriceGuard` passes (absent, or within the allowed band).
4. `computeLegPolicyOutput` computes an inflated `policyMaxOutput`; the overfill-ceiling check at fx.ts:684-701 detects `rawPolicyMaxOutput > overfillCeiling` but only warns — `policyMaxOutput` is used unclamped as `targetOutput`.
5. The filler pays out `targetOutput` from wallet balance / LP withdrawal, over-delivering the exotic token to the attacker at the manipulated rate.
6. Attacker repays the flashloan and closes the swap, restoring the pool price, keeping the extracted token surplus.

	private checkPriceGuard(orderId: string | undefined, chain: string, venueToken1PerUsd: Decimal): boolean {
		const guard = this.priceGuard?.get(chain)
		if (!guard || guard.reference.lte(0)) return true

		const deviationBps = venueToken1PerUsd.minus(guard.reference).abs().div(guard.reference).mul(10000)
		if (deviationBps.gt(guard.maxDeviationBps)) {
			this.logger.warn(
				{
					orderId,
					chain,
					venuePrice: venueToken1PerUsd.toString(),
					referencePrice: guard.reference.toString(),
					deviationBps: deviationBps.toFixed(2),
					maxDeviationBps: guard.maxDeviationBps,
				},
				"Rejecting order: Uniswap venue quote outside price-guard band",
			)
			return false
		}
		return true
	}

		orderId: string | undefined,
		leg: ResolvedLeg,
		cappedPairNotional: Decimal,
		venueUsdPrice: (chain: string, token1Address: string) => Promise<Decimal | null>,
	): Promise<LegRates | null> {
		// Explicitly configured curves always win — the venue only prices pairs
		// with no curves at all (and never same-token pairs, where a venue quote
		// would just be the asset's own USD price, not a spread).
		const curveless = !leg.pair.bidPricePolicy && !leg.pair.askPricePolicy
		if (curveless && !isSameTokenPair(leg.pair) && USD_STABLE_SYMBOLS.has(normalizeSymbol(leg.pair.token0))) {
			const venueUsd = await venueUsdPrice(leg.token1Chain, leg.token1Address)
			if (venueUsd) {
				// Guard compares the venue's token1-per-USD quote against the static reference.
				if (!this.checkPriceGuard(orderId, leg.token1Chain, new Decimal(1).div(venueUsd))) {
					return null
				}

				// to report a round-trip margin against. The price guard above is
				// the venue-specific defense.
				const venueRate = new Decimal(1).div(venueUsd)
				return { rate: venueRate, oppositeRate: null, priceSource: "venue" }

```text
## Uniswap price guards

Pool-based pricing trusts the live pool, which leaves the solver exposed to a manipulated, stale, or thin pool returning a bad quote. To bound that risk, give a position a **`referencePrice`** and **`maxDeviationBps`**. Whenever the pool quote on that chain drifts more than `maxDeviationBps` above or below the reference, the solver refuses to fill — the order is rejected before any bid is submitted.

`referencePrice` is expressed in **exotic tokens per USD**, the same units as the bid/ask curves. The two fields must be set together; omit both to leave the chain unguarded.
```

`computeDirectPoolPriceUsd` returns the **raw pool mid** derived from `sqrtPriceX96`. The pool's
fee tier is read and stored on the hydrated position (`pos.fee`) but never applied to the price,
and there is no size or impact term — `computeLegPolicyOutput` extends the mid linearly across the
whole priced quantity. `checkPriceGuard` is the only defense on this path, and it checks deviation
from a static reference, not execution cost. A venue-priced pair that has to swap through its own
pool to source inventory pays a fee tier it never quoted against.
