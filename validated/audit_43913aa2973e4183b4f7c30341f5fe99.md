### Title
Webhook `shop` field is not covered by HMAC verification, allowing shop-domain spoofing in `ShopifyAPI::Webhooks::Request` - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook by validating an HMAC computed only over the raw request body, then hands the caller a `WebhookMetadata` struct whose `shop` field is read straight from an unauthenticated HTTP header. The gem's own documented usage pattern instructs host apps to use `data.shop` to key tenant-specific work, so the unbound `shop` field can be used to misattribute a genuine, HMAC-valid webhook payload to an arbitrary victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is instead derived from the `x-shopify-shop-domain` / `shopify-shop-domain` header, which plays no part in the signable string: [2](#0-1) 

`Registry.process` validates the HMAC and, on success, forwards `request.shop` (the unauthenticated header) directly into `WebhookMetadata` passed to the app's handler: [3](#0-2) 

`HmacValidator.validate` only checks `compute_signature(verifiable_query.to_signable_string, secret) == hmac`, i.e. it validates `hmac(body)` — it never binds the `shop` header into the signature: [4](#0-3) 

The binding that should hold but does not:
`hmac_verified_shop == shop_delivered_to_handler`

In reality: `hmac_verified_content == raw_body_only`, while `shop_delivered_to_handler == unauthenticated_header_value`. Any request whose `raw_body` + `hmac` pair is genuine (i.e., produced by Shopify for the app's own `api_secret_key`, for *some* shop event) will pass `HmacValidator.validate` regardless of what `x-shopify-shop-domain` value accompanies it. An attacker who can obtain one legitimately-delivered `(raw_body, hmac)` pair — e.g., by installing the app on a store they control and capturing a webhook Shopify sends them — can replay that exact `raw_body`/`hmac` pair to the app's public webhook endpoint while substituting a different `x-shopify-shop-domain` header value, and the gem will report the forged shop attribution as authenticated.

This is documented as the expected way for the host app to determine tenant: the docs explicitly show `data.shop` being used to key work (`shop_domain: data.shop`), so an app following the gem's own documented API is exposed: [5](#0-4) 

For contrast, the OAuth callback code path in this same gem does the correct thing: `shop` is included in the HMAC-signed string via `AuthQuery#to_signable_string`, so the two identity checks are properly bound there: [6](#0-5) 

This confirms the webhook path is the outlier — the gem elsewhere demonstrates it is capable of binding the tenant identifier into the signature, but does not do so for webhook processing.

### Impact Explanation
This is a cross-tenant identity confusion: a single authenticated app installation's captured/replayed webhook payload can be relabeled by an attacker as belonging to any other shop domain string of the attacker's choosing, and this attribution is delivered to the host app as verified/trusted (`ShopifyAPI::Errors::InvalidWebhookError` is not raised). If the host application follows the gem's documented pattern and uses `data.shop` to select which tenant's data/record to update, create, or delete, this enables cross-tenant data corruption without possessing the victim's access token or any Shopify-side credential — satisfying the "cross-tenant access" criticality bar. The severity is bounded by two factors I could not fully verify from the gem code alone: (1) whether Shopify's real webhook delivery infrastructure enforces any additional binding (e.g., TLS client identity, source IP allow-listing) that would need to be bypassed outside of this gem — this is out of scope for this analysis since it is not implemented in the gem; and (2) exactly how much of a JSON body can be reused across differently-shaped webhook topics/shops, which affects exploitability of the specific attack payload content (not the identity-confusion primitive itself, which is unconditionally present).

### Likelihood Explanation
Reaching this requires only public internet access to the app's webhook endpoint — no access token, no `api_secret_key`, and no privileged account are needed by the attacker to exploit the *binding gap* itself, only the capability to send arbitrary HTTP requests with attacker-chosen headers and a raw body/HMAC pair. The (raw_body, hmac) pair the attacker replays must itself be a legitimate one for the target app (obtainable, for the attacker's own store, by installing the target app if it's publicly installable, and observing an authentic webhook delivery), which is a normal unprivileged flow, not a privileged one. Given this, likelihood is moderate: the vulnerability is directly reachable via unprivileged internet interaction, but does require the app to be publicly installable so the attacker can harvest one genuine `(body, hmac)` sample.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the value that is HMAC-verified, or otherwise cryptographically tie the shop attribution to the signed payload before handing it to the handler in `Registry.process`. Concretely:
- Include the `shop-domain` header value in the string passed to `HmacValidator.validate` (i.e., change `Request#to_signable_string` to incorporate `shop`, mirroring what `AuthQuery#to_signable_string` already does for OAuth), or
- Recommend/require that host applications independently corroborate `data.shop` against a shop for which they hold an active, installed session before trusting it for tenant-scoped side effects, and update `docs/usage/webhooks.md` to state this caveat explicitly, since the current documented example implies it is safe to key work directly off `data.shop`.

### Proof of Concept
1. Attacker installs the target Shopify app on their own controlled store `attacker-shop.myshopify.com` and registers for a webhook topic (e.g., `orders/create`).
2. Shopify delivers a legitimate webhook to the app's endpoint with a raw body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)` — attacker captures `(B, H)` via any request logging/interception they control (their own server receives this webhook if they run the app themselves, or a MITM-less capture from their own infra logs since it is their own installation).
3. Attacker sends a forged HTTP POST directly to the app's webhook endpoint with:
   - body = `B` (unchanged)
   - header `x-shopify-hmac-sha256` = `H` (unchanged)
   - header `x-shopify-shop-domain` = `victim-shop.myshopify.com` (attacker-controlled)
   - header `x-shopify-topic` unchanged
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC-SHA256(api_secret_key, B)` and finds it equals `H` — validation passes: [3](#0-2) 
5. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, which is now treated by the app as an authenticated event for `victim-shop`, even though the actual originating (and only cryptographically-verified) shop was `attacker-shop`.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
