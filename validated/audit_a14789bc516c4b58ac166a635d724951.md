## Title
Divergent debt-to-scaled conversion formulas between `market.clar` (per-user ledger) and vault `system-repay` (aggregate ledger) break the debt identity — ([File: mainnet/contracts/market/v0-4-market.clar], [File: mainnet/contracts/vault/v0-vault-usdc.clar])

### Summary
`repay` in the market contract removes debt from the **per-user** ledger (`market-vault.debt`) using a direct index-based conversion (`amount ↔ scaled` via `borrow-index`/`INDEX-PRECISION`), while the vault's `system-repay` reduces the **aggregate** `principal-scaled` using a completely different formula: a proportional ratio of the repaid amount to total outstanding debt (`calc-principal-ratio-reduction`). Because these two paths compute "scaled units removed" via unrelated arithmetic, the sum of all per-user scaled-debt reductions tracked in `market-vault.clar` can diverge from the vault's own `principal-scaled` aggregate that backs `total-debt`/`total-assets` accounting.

### Finding Description
In `repay` (`mainnet/contracts/market/v0-4-market.clar:1316-1378`, mirrored in `local-testing/contracts/market/market.clar:1339-1401`), the per-user scaled debt to remove is computed as: [1](#0-0) 
```
borrow-index         = index at asset-id
account-scaled-debt  = user's per-account scaled debt (market-vault ledger)
max-repay-tokens      = mul-div-up(account-scaled-debt, borrow-index, INDEX-PRECISION)
safe-amount           = min(amount, max-repay-tokens)
scaled-debt-repayment = mul-div-down(safe-amount, INDEX-PRECISION, borrow-index)
repaid-scaled-debt    = min(account-scaled-debt, scaled-debt-repayment)
amount-to-repay       = mul-div-up(repaid-scaled-debt, borrow-index, INDEX-PRECISION)
```
`amount-to-repay` (a token amount) is then forwarded to the vault via `vault-system-repay`, and `repaid-scaled-debt` is removed from the *user's* ledger entry via `debt-remove-scaled` in `market-vault.clar`. [2](#0-1) 

Independently, the vault's `system-repay` reduces the *aggregate* `principal-scaled` using a proportional-ratio formula rather than the same `INDEX-PRECISION`/`borrow-index` conversion used by the market: [3](#0-2) 
```
capped-amount        = min(amount, debt)
principal-reduction  = calc-principal-ratio-reduction(capped-amount, scaled-principal, debt)
                       = mul-div-down(capped-amount, scaled-principal, debt)
capped-reduction      = min(principal-reduction, scaled-principal)
updated-scaled-principal = scaled-principal - capped-reduction
```
`calc-principal-ratio-reduction` is defined as a plain ratio, not an index-based scaled/token conversion: [4](#0-3) 

These two computations — `mul-div-down(amount, INDEX-PRECISION, borrow-index)` on the market side vs. `mul-div-down(amount, scaled-principal, debt)` on the vault side — are mathematically different unless `scaled-principal/debt == INDEX-PRECISION/borrow-index` exactly, which only holds when the vault's `debt` (accrued via `calc-cumulative-debt`, itself `mul-div-up`) and `principal-scaled` are perfectly in sync with the cached `borrow-index` the market read. Any rounding drift between the vault's live-accrued index and the market's cached index (populated earlier in the same transaction via `accrue-and-cache`), or between multiple borrowers with different scaled/borrow-index histories aggregated into `debt`, causes `principal-reduction` (vault aggregate) to differ from `repaid-scaled-debt` (per-user ledger) by rounding remainders, on every single repay call.

This directly breaks the intended identity:
```
sum(market-vault.debt[user].scaled for all users) == vault.principal-scaled
```
Each repay both sides is meant to shrink by the "same" scaled amount, but they are computed by unrelated formulas. Over repeated repay operations this drift compounds: `vault.principal-scaled` (which multiplies by `index` to determine `total-debt` used for `total-assets`, interest accrual, and share pricing in `convert-to-assets-preview`/`convert-to-shares-preview`) no longer matches the true sum of individually-tracked user obligations in `market-vault.clar`. This is the "per-user debt ledger versus the vault aggregate" identity break class explicitly called out as in-scope.

### Impact Explanation
If the vault-side aggregate `principal-scaled` drifts to be **larger** than the true sum of per-user scaled debts, the vault under-reports available assets/over-reports debt, causing incorrect `total-assets` in `convert-to-assets-preview`/`convert-to-shares-preview`, mispricing zTokens on `deposit`/`redeem` — depositors or redeemers receive incorrect shares/assets. If it drifts **smaller**, aggregate debt is understated relative to what individual borrowers still owe collectively, and `total-assets` (interest reserve) is overstated, allowing zToken holders to redeem more underlying than the vault has legitimately earned, which is a value-creation-from-nothing / insolvency-class issue since `total-assets = current-assets + max(debt - total-borrowed, 0)` where `debt` is derived from the (now-drifted) `principal-scaled`.

### Likelihood Explanation
This drift accumulates automatically on **every** `repay` call under normal operation — no attacker-crafted input, malicious timing, or special permission is required, only that borrow-index and the vault's own accrued debt/principal-scaled state differ by rounding from what the market last cached (which happens routinely given index accrual is time-based and `accrue-and-cache` is called before the market computes conversions). However, I was unable to fully verify within the available context whether `debt` used inside `system-repay` (i.e., `total-debt` computed from the vault's own `principal-scaled`/`index`) is guaranteed identical to the `borrow-index` value cached and used by `market.clar`'s `repay` in the same transaction — if the two indices are always synchronized to identical values by `accrue-and-cache`/`vault-accrue`, the ratio `scaled-principal/debt` would exactly equal `INDEX-PRECISION/borrow-index` and no drift would occur for a single, isolated borrower's repayment of their entire debt. The drift is most clearly nonzero when multiple borrowers with different individual debt histories are aggregated into a single `scaled-principal`/`debt` pair, since a per-user ratio conversion and a pool-wide ratio conversion are generically different quantities.

### Recommendation
Verify that the vault's `system-repay` computes the scaled-principal reduction using the exact same `mul-div-down(amount, INDEX-PRECISION, index)` conversion that `market.clar` uses for the per-user ledger, rather than a distinct proportional-ratio (`amount * scaled-principal / debt`) formula. If the ratio approach is intentional (e.g., to handle socialized bad debt proportionally), the market's per-user removal must use the equivalent ratio-based reduction so both ledgers move by mathematically identical amounts on every repay, and invariant tests should assert `sum(per-user scaled debt) == vault.principal-scaled` after each operation.

### Proof of Concept
Exact reproduction requires runtime state (specific `principal-scaled`, `total-borrowed`, `index`, and multiple borrower histories) to demonstrate the numeric divergence between `mul-div-down(amount, INDEX-PRECISION, borrow-index)` (market-side per-user reduction) and `mul-div-down(amount, scaled-principal, debt)` (vault-side aggregate reduction). I could not execute or simulate the Clarity contracts in this environment to produce concrete divergent numbers; a Devin session with access to the local-testing harness (`local-testing/tests/`) would be needed to script a multi-borrower repay sequence and assert `sum(per-user scaled) != vault.principal-scaled` after several `repay` calls to confirm the magnitude of drift.

(define-public (system-repay (amount uint))
  (let (
        (states (var-get pause-states))
        (u (try! (accrue)))
        (scaled-principal (var-get principal-scaled))
        (idx (var-get index))
        (debt (total-debt))
        (total-borrowed-amount (var-get total-borrowed))
        (capped-amount (if (> amount debt) debt amount))
        (principal-reduction (calc-principal-ratio-reduction capped-amount scaled-principal debt))
        (capped-reduction (if (> principal-reduction scaled-principal) scaled-principal principal-reduction))
        (updated-scaled-principal (- scaled-principal capped-reduction))
        (principal-repaid (mul-div-down capped-amount total-borrowed-amount debt))
        (interest-paid (- capped-amount principal-repaid))
        (total-borrowed-new (if (> total-borrowed-amount principal-repaid) (- total-borrowed-amount principal-repaid) u0)))

    (var-set principal-scaled updated-scaled-principal)
    (var-set total-borrowed total-borrowed-new)
