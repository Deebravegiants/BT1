### Title
Unchecked RAY value growth can permanently freeze an entire market - ([File: common/src/rates/simulate.rs](common/src/rates/simulate.rs))

### Summary
A sufficiently large, highly utilized market can make `borrowed × borrow_index` or `supplied × supply_index` exceed the `i128` domain during accrual. Because every market mutation accrues first, the resulting `MathOverflow` permanently blocks repayment, withdrawal, liquidation, and further index updates for that market.

### Finding Description
`global_sync` invokes `accrue_step` for every elapsed accrual chunk. [1](#0-0)   
`accrue_step` converts the stored scaled borrow and supply shares into original RAY values before computing utilization and interest. [2](#0-1)   
That conversion multiplies scaled shares by the market index. [3](#0-2)   
Although token-to-RAY input caps bound initial deposits to about 170.14 billion whole tokens, accrued market values are not independently bounded before these multiplications. [4](#0-3)   

The repository’s own regression test demonstrates the reachable cliff: a one-billion-token, 18-decimal market at 98% utilization causes `update_indexes` to return `MathOverflow`; afterward, even a one-unit withdrawal and a small repayment fail for the same reason. [5](#0-4)   

### Impact Explanation
Permanent freezing of user funds is possible. Suppliers cannot withdraw, borrowers cannot repay, and liquidators cannot use repayment or seizure paths that load the affected market because accrual runs before the requested operation. [5](#0-4)   
The index ceiling does not prevent the condition because the overflow occurs while computing the accrued market value, before the capped index can provide protection. [6](#0-5)   

### Likelihood Explanation
The attack requires a very large market and sustained high utilization, so it is not practical on markets with conservative caps or modest liquidity. However, the amounts are within the admitted numeric domain: cap validation permits approximately 170.14 billion whole tokens, and the demonstrated setup uses only one billion whole tokens. [7](#0-6)   
An unprivileged caller reaches the trigger through ordinary `supply`, `borrow`, and later `update_indexes`; the latter accepts caller authorization and a market list. [8](#0-7)   

### Recommendation
Bound accrued scaled-share values, not only initial token inputs and indexes. Before each accrual multiplication, compare `borrowed` and `supplied` against `i128::MAX / index`; once either product would overflow, stop growth or clamp the relevant index to the largest representable value while preserving solvent exits. Alternatively, maintain a separate checked accrued-value bound and reject new supply or borrowing before a market can cross the value ceiling.

### Proof of Concept
1. Configure an 18-decimal market with caps near the admitted domain maximum and a steep interest-rate curve.
2. Call `supply(caller, account_id=0, spoke_id, [(BIG18, 1_000_000_000 * 10^18)])`.
3. Fund a separate account with sufficient collateral and call `borrow(caller, account_id, [(BIG18, 980_000_000 * 10^18)], None)`.
4. Allow enough ledger time to pass at sustained high utilization.
5. Call `update_indexes(caller, [(hub_id, BIG18)])`.
6. The accrual path attempts `borrowed * borrow_index` or `supplied * supply_index` above the `i128` range and panics with `MathOverflow`. [2](#0-1)   
7. Subsequent `withdraw`, `repay`, `liquidate`, or `update_indexes` calls touching the same market repeat the accrual and fail before reaching their operation-specific logic. [1](#0-0)   
8. The existing production-path test reproduces this exact outcome and asserts `MathOverflow` for both index update and exit operations. [9](#0-8)

```rust
/// The cliff. A billion whole tokens is `1e36` raw ray; the value ceiling is
/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
```
