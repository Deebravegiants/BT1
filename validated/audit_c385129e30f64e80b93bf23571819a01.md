### Title
Webhook `shop-domain` and `topic` headers are trusted without being covered by the HMAC signature, enabling cross-tenant webhook shop/topic confusion - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then dispatches the handler using the `shop`, `topic`, `webhook_id`, and `api_version` values taken straight from unauthenticated HTTP headers. None of those header fields are part of the signed payload, so their binding to the verified body is never checked.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are read directly from the request headers with no cryptographic binding to the signature: [2](#0-1) 

`Utils::HmacValidator.validate` only recomputes the HMAC over `verifiable_query.to_signable_string` (i.e. the raw body) and compares it to the `hmac-sha256` header: [3](#0-2) 

`Registry.process` treats a successful body-HMAC check as sufficient authentication for the entire request, then hands `request.shop`, `request.topic`, `request.webhook_id`, and `request.parsed_body` straight to the registered handler as trusted `WebhookMetadata`: [4](#0-3) 

The binding that should hold is:
`shop_attested_by_hmac(raw_body) == shop_trusted_by_handler(header)`

But because the HMAC only covers `raw_body`, this equality is never enforced — `shop` (and `topic`) are free variables an attacker fully controls as long as they can supply *any* previously-valid `(raw_body, hmac)` pair. Since the app's webhook HMAC secret (`api_secret_key`) is shared across every shop that installs the app (it is not shop-specific), a party who legitimately receives one authentic webhook for their *own* shop — e.g., by installing the app on a shop they control, which is an ordinary unprivileged action requiring no special credentials beyond app installation — obtains a `(raw_body, valid hmac)` pair they can freely replay. They can then re-POST that exact body/HMAC to the app's webhook endpoint while substituting `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) headers for a different shop or topic. `HmacValidator.validate` still passes because the raw body is unchanged, so `Registry.process` invokes the handler believing the payload originated from — and pertains to — the spoofed shop/topic.

### Impact Explanation
Any app relying on this gem's webhook dispatch to determine which merchant a webhook body belongs to (via `WebhookMetadata#shop`) can be tricked into attributing/acting on one shop's data under another shop's identity — a cross-tenant confusion. Depending on the handler's logic (e.g. updating per-shop billing/subscription state, disabling app features, ingesting order/customer data keyed by `shop`), this can lead to cross-tenant state corruption or data leakage between merchants, which matches the "Critical - cross-tenant access" impact bucket.

### Likelihood Explanation
The attacker only needs to be an unprivileged party with (a) the ability to POST to the app's public webhook endpoint and (b) access to one legitimately-signed `(raw_body, hmac)` pair for the shared app secret — trivially obtainable by installing the target app on a shop the attacker controls and capturing the webhook Shopify sends them. No access token, `client_secret`, or privileged account is required; header spoofing on a raw HTTP POST is unrestricted.

### Recommendation
Bind `shop`, `topic`, and other Shopify-provided webhook headers into the value that is HMAC-verified (or otherwise independently validate that the `shop-domain` header corresponds to a shop for which the app has an active installation/session before trusting it), rather than trusting these headers purely because the body's HMAC validated.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (ordinary unprivileged action).
2. Shopify sends a legitimate webhook to the app's endpoint with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: orders/create`, `x-shopify-hmac-sha256: <valid-hmac-of-body>`.
3. Attacker captures this exact `raw_body` and `hmac-sha256` value.
4. Attacker re-POSTs the identical `raw_body` and `hmac-sha256` header to the same endpoint, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com` (and/or changes `x-shopify-topic`).
5. `ShopifyAPI::Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` succeeds because it only checks the (unchanged) raw body against the HMAC.
6. `ShopifyAPI::Webhooks::Registry.process` in `lib/shopify_api/webhooks/registry.rb` invokes the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: <attacker-chosen>, body: <attacker's own data>, ...)`, causing the app to process attacker-controlled data as if it belonged to the victim shop.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
