### Title
Webhook HMAC signs only the raw body, not the `shop-domain`/`topic`/`webhook-id` headers, allowing cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely by checking `Utils::HmacValidator.validate(request)`, which computes the HMAC only over `request.to_signable_string`. For `Webhooks::Request`, `to_signable_string` returns the raw body exclusively - it never includes the `shop-domain`, `topic`, or `webhook-id` headers. This breaks the identity binding: `shop == "value trusted for tenant routing"` should equal `shop == "value cryptographically bound to the signed payload"`, but here the `shop` value used to dispatch webhook data to a handler is never authenticated by the HMAC at all.

### Finding Description
- `Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
- `shop`, `topic`, and `webhook_id` are read straight from HTTP headers with no cryptographic binding to the signature: [2](#0-1) 
- `Registry.process` trusts `request.shop` to build `WebhookMetadata` after only validating the HMAC, which - per the above - never covers `shop`: [3](#0-2) 
- `HmacValidator.validate_signature` computes the digest purely from `to_signable_string` and the app's shared `api_secret_key`, with no header/tenant component mixed in: [4](#0-3) 

By contrast, the OAuth `AuthQuery` correctly binds `shop` into the signed content (`to_signable_string` includes `shop`), so OAuth callback processing does not have this flaw: [5](#0-4) 

Since the app's `api_secret_key` is shared across every shop that installs the app, any tenant that has legitimately installed the app can obtain a validly-signed `(raw_body, hmac)` pair for any webhook topic. Because the signature never binds to `shop`, that same `(raw_body, hmac)` pair remains valid when replayed with an arbitrary `shopify-shop-domain` header pointing at a different, victim tenant.

### Impact Explanation
This breaks tenant isolation (cross-tenant access): a malicious but legitimately-installed merchant can cause the app to process forged data as though it originated from a different shop. Depending on the handler, this can corrupt another tenant's records (e.g., fake `orders/create`, `products/update`) or even trigger destructive handling (e.g., an `app/uninstalled` handler that deletes local data for "that shop") for a shop the attacker does not control. This falls under the Critical "cross-tenant access" impact category since no per-tenant credential or session is required — only that the attacker's own shop has installed the app.

### Likelihood Explanation
Likelihood is high for any app relying solely on `ShopifyAPI::Webhooks::Registry.process`/`HmacValidator.validate` for webhook trust, since:
1. Any unprivileged internet user can install the app on a free/trial Shopify dev store to obtain genuine `(raw_body, hmac)` pairs.
2. No secret material beyond what Shopify already sends the attacker's own store is needed.
3. Directly crafting a POST to the app's public webhook endpoint with a spoofed `shopify-shop-domain` header requires no TLS interception or privileged access.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the value that is HMAC-verified, or otherwise require the caller (host app) to independently verify that `request.shop` corresponds to a shop with an active installation/session before trusting `WebhookMetadata.shop`. At minimum, document prominently that `HmacValidator.validate` only proves the request came from Shopify with the shared secret, not that the `shop-domain` header is authentic, and that host apps must cross-check `request.shop` against their own installed-shop registry before processing.

### Proof of Concept
1. Attacker creates a free Shopify development store and installs the target app, obtaining shop domain `attacker.myshopify.com`.
2. Attacker triggers any registered webhook topic (e.g., `orders/create`) on their own store; Shopify sends the app a request with headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC of raw body>`, and the raw JSON body.
3. Attacker captures `raw_body` and `hmac` and replays them directly to the app's public webhook endpoint, substituting `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate` succeeds because it only checks the HMAC of `raw_body`, which is unchanged. `Registry.process` calls the topic handler with `shop: "victim.myshopify.com"` from `WebhookMetadata`, so the app processes attacker-controlled data as if it came from the victim tenant.         def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
