Audit Report

## Title
HTTP Response Cache Key Omits WorkflowID, Causing Cross-Workflow Response Cache Confusion - (File: core/services/gateway/handlers/capabilities/v2/response_cache.go)

## Summary
The gateway's HTTP capability response cache (`responseCache`) is a single instance shared by the `gatewayHandler` across all node/workflow requests, and its lookup/store key is `req.Hash()`, which is computed from method, URL, headers, body, and `WorkflowOwner` but not `WorkflowID`. As a result, two distinct workflows owned by the same `WorkflowOwner` that issue an identical outbound HTTP request shape will collide on the same cache entry, contradicting the documented "Workflow Isolation" guarantee.

## Finding Description
`Fetch` and `Set` on `responseCache` use `req.Hash()` as the sole cache key against a process-wide `map[string]*cachedResponse` [6](#0-5) [7](#0-6) . This cache is instantiated once and stored as a field (`responseCache ResponseCache`) on `gatewayHandler`, which serves the entire DON/all shards, not per-workflow [8](#0-7) . The outbound HTTP action path in `makeOutgoingRequest` calls `h.responseCache.Fetch`/`h.responseCache.Set` directly with the unmarshalled `OutboundHTTPRequest` from any node message, with no additional per-workflow keying layer [9](#0-8) .

The unit tests confirm `Hash()` ignores `WorkflowID` while it does vary with `WorkflowOwner`, method, and URL [10](#0-9) . This directly contradicts the explicit documented invariant that "Cache entries are scoped by workflow ID to prevent cross-workflow data leakage" [5](#0-4) . No other code layer re-introduces `WorkflowID` into the key — `Fetch`/`Set`/`isExpiredOrNotCached` all rely purely on `req.Hash()` [11](#0-10) [2](#0-1) .

## Impact Explanation
Because the shared, global cache keys on request shape + `WorkflowOwner` only, two distinct workflows belonging to the same owner (a common scenario — one owner frequently runs multiple workflows, e.g., staging/production variants or multiple deployed workflow versions) that issue byte-identical outbound HTTP requests (same method, URL, headers, body) will read/write the same cache entry. This means one workflow's cached response — potentially containing workflow-specific secrets or context echoed in headers/body, or simply stale/incorrect data for that workflow's semantic context — can be served to a different workflow of the same owner. This is a concrete cross-workflow response corruption issue, matching the "cross-user response corruption" impact category referenced in the rules, and it directly violates a security invariant the component's own documentation claims to enforce.

## Likelihood Explanation
This is triggerable entirely through unprivileged, workflow-owner-controlled input: any workflow (no gateway/node-operator privilege required) that sets `CacheSettings.Store = true` or `CacheSettings.MaxAgeMs > 0` on an `OutboundHTTPRequest` reaches this cache path deterministically [12](#0-11) . The collision condition (same owner, same request shape, different `WorkflowID`) is realistic for any owner running multiple workflows against the same external API, and is deterministic/reproducible as shown by the existing test suite.

## Recommendation
Include `WorkflowID` as an input to `OutboundHTTPRequest.Hash()` (in `chainlink-common`'s `gateway` package) alongside `WorkflowOwner`, method, URL, headers, and body, so that the cache key matches the documented per-workflow isolation model. Add/keep a regression test asserting `Hash()` differs when only `WorkflowID` differs.

## Proof of Concept
1. Construct two `gateway.OutboundHTTPRequest` values with identical `Method`, `URL`, `MultiHeaders`, `Body`, and `WorkflowOwner`, but different `WorkflowID` (`workflow-123` vs `workflow-456`).
2. Call `req1.Hash()` and `req2.Hash()` — per `TestRequestHash` ("having different workflowID results in same Hash"), they are equal [3](#0-2) .
3. Simulate the real flow: `handler.HandleNodeMessage` for `wf-A`'s outbound request with `CacheSettings.Store=true` populates `h.responseCache` via `Set`/`Fetch` [13](#0-12) ; a subsequent `HandleNodeMessage` call for `wf-B` with an identical request shape and `MaxAgeMs > 0` retrieves `wf-A`'s cached response from the shared `gatewayHandler.responseCache` without making a fresh outbound HTTP call, confirming cross-workflow cache confusion.
