### Title
Webhook shop domain is not covered by the HMAC signature, allowing cross-tenant shop spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw body alone, while `shop` (and `topic`, `webhook_id`, `api_version`) are read directly from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` validates only that HMAC and then hands `request.shop` straight to the app's webhook handler as the authoritative tenant identifier. This breaks the identity binding: `shop authenticated by the HMAC` ≠ `shop attributed to the webhook data used by the handler`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` simply reads the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic binding to the body or HMAC: [2](#0-1) 

`Registry.process` validates the HMAC (which, as shown above, only covers the body) and then constructs `WebhookMetadata` using `request.shop` taken from the header, passing it to the app-supplied handler as the trusted tenant identity: [3](#0-2) 

`WebhookMetadata#shop` is documented and typed as the authoritative "shop domain of the webhook" that host apps are expected to trust and key their data/session lookups on: [4](#0-3) 

The gem's own documentation reinforces the false guarantee, stating that `Registry.process` "will verify the request did indeed come from Shopify," implying the whole request (including the shop header) is authenticated, when in fact only the raw body bytes are: [5](#0-4) 

Because the app's single `api_secret_key` is shared across every shop that installs the app, and the HMAC is computed purely over body bytes, any two webhook deliveries with identical bodies produce identical HMACs regardless of which shop they belong to. An unprivileged actor who legitimately installs the app on their own shop (no victim credentials, no `api_secret_key` needed) can capture a validly-signed webhook (raw body + HMAC) generated by their own shop's activity, then replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a victim shop's domain. `HmacValidator.validate` still succeeds because it only checks the (unchanged) body, and the handler receives `data.shop == victim-shop.myshopify.com` with attacker-controlled `data.body`.

### Impact Explanation
This is a cross-tenant identity binding failure: an attacker can cause the host application to process attacker-supplied webhook content while attributing it to a different, victim merchant's shop. Depending on how the host app uses `data.shop` (e.g., looking up the victim's session/access token to react to the "webhook", writing to the victim's tenant-scoped records, or triggering shop-scoped side effects), this enables cross-tenant data corruption/confusion using only a validly signed-but-misattributed webhook — satisfying the "cross-tenant access" criterion.

### Likelihood Explanation
The barrier to exploitation is low for anyone who can install the app on any shop (including a shop they control): they need no secrets, tokens, or privileged access beyond triggering an event on their own store to obtain one valid (body, HMAC) pair, and then freely choosing the `shop` header value on replay since it is never part of the signed payload. This is a straightforward, repeatable identity-spoofing primitive.

### Recommendation
Include the shop domain (and ideally topic/webhook id/api version) in the HMAC-signable string, or otherwise cryptographically bind the `shop` header to the signature verification in `HmacValidator`/`Request`, so that spoofing the shop header invalidates the signature. Alternatively, document explicitly that `data.shop` is not authenticated and host apps must cross-check it against their own shop/session records before trusting it.

### Proof of Concept
1. Install the app on attacker-owned shop `attacker.myshopify.com`; trigger an event (e.g., `orders/create`) so Shopify sends a webhook with body `B` and header `X-Shopify-Hmac-Sha256: HMAC(secret, B)`.
2. Capture `B` and the HMAC value from the legitimate delivery.
3. Replay a POST to the app's webhook endpoint with the same raw body `B` and same `X-Shopify-Hmac-Sha256` header, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `request.to_signable_string` (`= B`) against the same shared `api_secret_key`.
5. The registered handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: B, ...)`, causing the host app to act on attacker-controlled data as if it belonged to the victim shop.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
