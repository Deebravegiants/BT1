### Title
Webhook `shop`/`topic`/`webhook-id` identity fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, and `ShopifyAPI::Utils::HmacValidator.validate` verifies the HMAC exclusively against that raw-body string. [1](#0-0) [2](#0-1)  Meanwhile the fields that `Registry.process` treats as the tenant/routing identity — `shop`, `topic`, `webhook_id`, `api_version` — are all read from HTTP headers that are never included in the signed payload. [3](#0-2) [4](#0-3) 

### Finding Description
The equality actually verified by this gem is:

`HMAC(api_secret_key, raw_body) == header["x-shopify-hmac-sha256"]`

but the equality the application logic relies on for tenant identity is:

`request.shop == "the merchant this payload belongs to"`

These are not the same binding. `request.shop`, `request.topic`, and `request.webhook_id` are parsed straight from headers with no cryptographic tie to the signed body. [5](#0-4)  `Registry.process` calls `Utils::HmacValidator.validate(request)` (which only checks the body) and then, once that single check passes, unconditionally forwards `request.shop` and `request.topic` to the handler as trusted identity data: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))`. [4](#0-3) 

The app's `api_secret_key` is shared across every shop that has installed the app — it is not per-tenant. Consequently, an unprivileged attacker who legitimately installs the app on their own shop receives real, validly-signed webhooks (`raw_body` + `hmac`) for that shop. Because the signature only ever covers `raw_body`, the attacker can replay that exact `raw_body`/`hmac` pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) header with a victim shop's identifiers. `HmacValidator.validate` still succeeds, because it never inspects those headers, and `Registry.process` will invoke the handler believing the payload originated from the spoofed shop/topic. [6](#0-5) 

### Impact Explanation
Any host application whose webhook handlers key merchant-scoped operations (data writes, cache invalidation, order/inventory sync, per-shop session lookups, billing state, etc.) off `WebhookMetadata#shop`/`#topic` can be tricked into applying an attacker-controlled payload to another tenant's data — a cross-tenant access/data-corruption vector reachable by any user who can install the app on their own store, with no access token, `client_secret`, or privileged account required.

### Likelihood Explanation
Likelihood is High: the attacker only needs to install the app themselves (or use their own already-installed store) to obtain a legitimately signed `raw_body`/`hmac` pair, then send that pair with forged headers to the public webhook endpoint. No secret material or TLS interception is needed; this is squarely within an unprivileged-internet-user threat model since headers are fully attacker-controlled on the HTTP request.

### Recommendation
Bind the identity headers into the signed material, or otherwise cryptographically verify them: e.g., include `shop`, `topic`, and `webhook_id` in `to_signable_string` (if Shopify's signing scheme is extended to support this), or — more practically within the gem's control — require callers to corroborate `request.shop` against a shop that is independently known to be associated with a currently-registered webhook subscription/session before dispatching to handlers, and document prominently that `shop`/`topic` headers are unauthenticated and must not be trusted as sole tenant identifiers.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` (a normal, self-service OAuth install — no special privilege).
2. Shopify sends a real webhook to the app's endpoint for that shop, e.g. body `{"id":123,"note":"hello"}"` with header `x-shopify-hmac-sha256: <valid HMAC over that body using the app's client_secret>`.
3. Attacker captures `raw_body` and the valid `hmac` value.
4. Attacker POSTs the same `raw_body` and `hmac` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` and any desired `x-shopify-topic`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `raw_body` — it still matches, since the body is unchanged. [7](#0-6) 
6. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and processes the attacker's payload as if it belonged to the victim, even though nothing about the `shop` header was ever authenticated. [8](#0-7)

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
