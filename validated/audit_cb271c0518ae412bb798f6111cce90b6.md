### Title
Single-authorised-relayer gate on IntentGatewayV2 can permanently strand user escrow and refunds - ([File: evm/src/apps/intentsv2/ExtrinsicIntents.sol])

### Summary
`ExtrinsicIntents.onAccept` and `onGetResponse` — the only entry points that release escrowed input tokens for cross-chain `RedeemEscrow`/`RefundEscrow` deliveries and source-side cancel proofs — call `_checkRelayer(incoming.relayer)` before doing anything else [1](#0-0) [2](#0-1) . Once a single relayer address is armed via `setRelayer`, every other relayer's delivery reverts and is treated as "undelivered" rather than failed, so recovery depends entirely on that one address resubmitting [3](#0-2) . This mirrors the Sherlock M-12 pattern: a privileged/whitelisted actor (here, the sole authorised relayer) that the protocol depends on to complete a user-facing settlement, with no permissionless fallback, and a decision doc for the sibling `SimplexPaymaster` explicitly acknowledges the analogous risk as "accepted and not mitigated" for lost/withholding relayer keys [4](#0-3) .

### Finding Description
`_checkRelayer` rejects any delivery whose `msg.sender`-derived `incoming.relayer` does not match the single stored `_relayer`, once one has been set:
```
function _checkRelayer(address relayer) internal view {
    address authorised = _relayer;
    if (authorised != address(0) && relayer != authorised) revert Unauthorized();
}
``` [5](#0-4) 

Both cross-chain settlement callbacks are gated by this check before the withdrawal logic runs:
- `onAccept` (handles `RedeemEscrow` — pay the solver — and `RefundEscrow` — refund the user after a destination-side cancel) checks the relayer first, then authenticates and calls `_withdraw` [6](#0-5) .
- `onGetResponse` (handles the source-side cancel proof that unlocks escrow when the destination never filled the order) is gated identically [2](#0-1) .

The only way to change `_relayer` is `setRelayer`, callable by the host, which is itself only reachable through a governance `Execute` request delegatecalled with the host as `msg.sender` [7](#0-6) [8](#0-7) . There is no permissionless or timeout-based path for a second party to deliver `RedeemEscrow`, `RefundEscrow`, or the cancel-proof `onGetResponse` if the sole authorised relayer stops submitting (goes offline, loses its key, or withholds delivery), exactly as the sibling paymaster decision doc calls out for the same design pattern: "once armed, every recovery path sits behind the gate, so a lost or withholding relayer key strands the deposit ... for good" [4](#0-3) . The IntentGatewayV2 changelog confirms the gate covers "escrow redemptions, refunds and every governance action" and that a refused delivery merely "reverts, which the host records as undelivered, so the authorised relayer can submit the same message later" — i.e., recovery is bound to that one relayer, not to the protocol at large [9](#0-8) .

This is the direct analog of the Sherlock M-12 issue: a privileged/whitelisted party (the sole authorised relayer, chosen by governance and outside end-user control) is a hard dependency for an unprivileged counterparty (the order's user/solver) to realize funds they are otherwise entitled to (escrowed inputs, fill proceeds, refunds), and there is no liquidation/fallback/permissionless mechanism when that party fails to act.

### Impact Explanation
Any user or solver with escrowed funds pending release through a cross-chain `RedeemEscrow`, `RefundEscrow`, or source-cancel `onGetResponse` message is fully dependent on one designated relayer address. If that relayer's key is lost, compromised so it withholds delivery, or simply never resubmits (whether by malice, incompetence, or infrastructure failure), the escrowed tokens for every affected order are frozen indefinitely — a solver who legitimately delivered outputs on the destination chain never receives the corresponding input tokens on the source chain, and a user's refund after a legitimate cancellation is stuck. Governance can rotate the relayer only through another message that itself must be delivered by... the same gated relayer (since `setRelayer` arrives via `Execute`, an `onAccept` `RequestKind`), so once the relayer stops relaying, the recovery path is also blocked. This is a permanent freezing-of-funds condition reachable from ordinary unprivileged user actions (placing/filling/cancelling an order), matching the required severity bar (permanent freezing of user funds).

### Likelihood Explanation
Likelihood depends on the authorised relayer becoming unavailable or malicious — an operational/trust assumption rather than a code bug in the narrow sense, which is why the sibling `SimplexPaymaster` decision doc explicitly classifies the same design as an accepted, undocumented-for-IntentGatewayV2 risk. However, unlike `SimplexPaymaster` (which has no owner key and documents the tradeoff as deliberate), `IntentGatewayV2`/`ExtrinsicIntents` ties recovery of every user's escrow to a single relayer with no owner-level override and no permissionless alternative delivery path, so a single relayer failure (key loss, compromise, extended downtime, or intentional censorship) is sufficient to freeze funds across all pending cross-chain orders — a broader blast radius than a per-account key loss.

### Recommendation
- Provide a permissionless or multi-party fallback for delivering `RedeemEscrow`/`RefundEscrow`/cancel-proof messages once a timeout has elapsed without delivery by the authorised relayer, so no single relayer's downtime can permanently freeze escrowed funds.
- Alternatively, allow governance (or an owner-style role) to rotate `_relayer` through a path that does not itself require delivery by the very relayer being replaced (e.g., a dedicated on-chain call rather than only via a Hyperbridge-delivered `Execute` request).
- Document explicitly, if this is intended design, the same way the `SimplexPaymaster` decision log does, and evaluate whether the blast radius (all pending IntentGatewayV2 orders vs. one paymaster instance) warrants a stronger mitigation than "accepted."

### Proof of Concept
1. Governance calls `setRelayer(R)` via an `Execute` request, arming `_relayer = R` on `IntentGatewayV2` [7](#0-6) .
2. A user places a cross-chain order and a solver fills it on the destination chain; the destination gateway dispatches a `RedeemEscrow` POST back to the source chain.
3. Relayer `R` loses its signing key (or begins withholding delivery). No other relayer's delivery of the `RedeemEscrow` message is accepted: `onAccept` reverts with `Unauthorized` for any `incoming.relayer != R` [6](#0-5) [5](#0-4) .
4. The solver's escrowed input tokens (owed for the fill already delivered) remain locked in the source-chain gateway indefinitely; the same applies to any user awaiting a `RefundEscrow` or a source-side cancel `onGetResponse` for that period.
5. Because `setRelayer` is only reachable via an `Execute` request that must itself pass through `onAccept`'s `_checkRelayer(incoming.relayer)` gate [8](#0-7) , governance cannot even rotate away from the unresponsive relayer `R` without `R`'s cooperation, cementing the freeze.
