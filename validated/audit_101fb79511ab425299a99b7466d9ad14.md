## Finding: DMP messages bypass the advanced advancement-rule check (HRMP does not)

Investigating the two message compression paths in `cumulus/pallets/parachain-system/src/lib.rs`:

- **HRMP** (`enqueue_inbound_horizontal_messages`) calls **both** the basic and the advanced check before processing messages: [1](#0-0) 
- **DMP** (`enqueue_inbound_downward_messages`) calls **only** `check_enough_messages_included_basic("DMQ")` — the advanced check is never invoked for downward messages: [2](#0-1) 

The two check functions themselves: `check_enough_messages_included_basic` only asserts `full_messages.len() >= 1` when `hashed_messages` is non-empty, with no size-based reasoning at all, whereas `check_enough_messages_included_advanced` asserts that the included full-message size plus the worst-case size of the first hashed message must exceed `max_full_messages_size` (i.e., enough full messages were genuinely included to fill the collection): [3](#0-2) 

### Title
Malicious collator can censor DMP/XCM messages by including only a trivial filler full message while hashing away larger legitimate downward messages, since `enqueue_inbound_downward_messages` never enforces `check_enough_messages_included_advanced` - ([File: cumulus/pallets/parachain-system/src/lib.rs])

### Summary
For horizontal (HRMP) messages, the runtime enforces both the basic (`>=1` full message) and advanced (size-based) advancement rule before enqueueing. For downward (DMP) messages — the channel through which relay-chain-originated XCM/UMP-response/DMP messages reach a parachain's unprivileged users — the runtime only enforces the weak basic check, never the advanced one.

### Finding Description
`AbridgedInboundMessagesCollection` provides two invariant checks: `check_enough_messages_included_basic`, which merely requires at least one full (non-hashed) message when any hashed message exists, and `check_enough_messages_included_advanced`, which requires the sum of included full-message sizes plus the worst-case size of the first hashed message to exceed the collection's size budget, ensuring the collator actually included "as many full messages as fit" per the doc-comment on lines 186–191 of `parachain_inherent.rs`. `enqueue_inbound_horizontal_messages` calls the advanced check against the ingress channel's `max_message_size` before processing HRMP messages. `enqueue_inbound_downward_messages`, however, calls only the basic check and never calls the advanced check. A malicious collator submitting the `set_validation_data` inherent (built from attacker-supplied `InboundMessagesData`, since the collator — not the runtime — decides how to split full vs. hashed messages) can therefore construct a DMP collection with a single 1-byte (or otherwise minimal) full message and hash away all other larger, legitimate downward messages (e.g., DMP-delivered XCM instructing token transfers, governance-relayed remarks, or other cross-chain calls targeted at specific unprivileged accounts), and the basic check alone is satisfied. There is no on-chain size-based constraint preventing this for DMP.

### Impact Explanation
This enables selective censorship of specific parachain-bound downward XCM/DMP messages: an attacker-controlled or colluding collator can systematically hash away targeted larger DMP messages (e.g., specific users' incoming transfers or governance-triggered messages) while satisfying all consensus checks (basic advancement rule, MQC head match), delaying or effectively suppressing their delivery/execution indefinitely as long as the collator keeps only feeding a trivial filler full message per block. This matches the scoped impact of selective XCM/DMP message censorship of unprivileged users.

### Likelihood Explanation
No privileged access is required beyond being a collator producing blocks for the parachain (an operational role, not a governance/root-key role, and a common adversarial model in this codebase per the doc-comment at parachain_inherent.rs:189-191 itself: "A malicious collator can provide a collection that contains no full messages or fewer full messages than possible, leading to censorship"). The attack is trivially repeatable every block for as long as the attacker controls block production, and requires no special network conditions beyond normal DMP message flow from the relay chain.

### Recommendation
Call `check_enough_messages_included_advanced` for the DMP path in `enqueue_inbound_downward_messages`, analogous to the HRMP path, using an appropriate `AbridgedInboundMessagesSizeInfo` with `max_full_messages_size` set to the DMP portion of `messages_collection_size_limit()` and `first_hashed_msg_max_size` set to the relay chain's configured `max_downward_message_size` (available via the relay-chain state proof / host configuration).

### Proof of Concept
Rust unit test analogous to `check_enough_messages_included_advanced_works` (in `parachain_inherent.rs` tests) but exercised through `enqueue_inbound_downward_messages`:
1. Construct `AbridgedInboundDownwardMessages` with `full_messages = [1-byte message]` and `hashed_messages = [hash of a large legitimate message]`.
2. Call `Pallet::<T>::enqueue_inbound_downward_messages(expected_head, downward_messages)` with a correctly computed MQC head so structural checks pass.
3. Assert the call does NOT panic (demonstrating `check_enough_messages_included_basic` alone is insufficient) even though computing `check_enough_messages_included_advanced` with the real `max_downward_message_size` and `messages_collection_size_limit()` would fail (`full_messages_size + first_hashed_msg_max_size <= max_full_messages_size`), proving the advanced invariant is silently violated and unenforced for DMP. 		expected_dmq_mqc_head: relay_chain::Hash,
		downward_messages: AbridgedInboundDownwardMessages,
	) -> Weight {
		downward_messages.check_enough_messages_included_basic("DMQ");

		let mut dmq_head = <LastDmqMqcHead<T>>::get();

		let (messages, hashed_messages) = downward_messages.messages();
		let message_count = messages.len() as u32;
		let weight_used = T::WeightInfo::enqueue_inbound_downward_messages(message_count);
		if let Some(last_msg) = messages.last() {
			Self::deposit_event(Event::DownwardMessagesReceived { count: message_count });

			// Eagerly update the MQC head hash:
			for msg in messages {
				dmq_head.extend_downward(msg);
			}
			<LastDmqMqcHead<T>>::put(&dmq_head);
			Self::deposit_event(Event::DownwardMessagesProcessed {
				weight_used,
				dmq_head: dmq_head.head(),
			});

			let mut last_processed_msg =
				InboundMessageId { sent_at: last_msg.sent_at, reverse_idx: 0 };
			for msg in hashed_messages {
				dmq_head.extend_with_hashed_msg(msg);

				if msg.sent_at == last_processed_msg.sent_at {
					last_processed_msg.reverse_idx += 1;
				}
			}
			LastProcessedDownwardMessage::<T>::put(last_processed_msg);

			T::DmpQueue::handle_messages(downward_messages.bounded_msgs_iter());
		}

		// After hashing each message in the message queue chain submitted by the collator, we
		// should arrive to the MQC head provided by the relay chain.
		//
		// A mismatch means that at least some of the submitted messages were altered, omitted or
		// added improperly.
		assert_eq!(dmq_head.head(), expected_dmq_mqc_head, "DMQ head mismatch");

		ProcessedDownwardMessages::<T>::put(message_count);

	/// Check that the current collection contains at least 1 full message if needed.
	pub fn check_enough_messages_included_basic(&self, collection_name: &str) {
		if self.hashed_messages.is_empty() {
			return;
		}

		// Here we just check that there is at least 1 full message.
		assert!(
			self.full_messages.len() >= 1,
			"[{}] Advancement rule violation: full messages missing",
			collection_name,
		);
	}

	/// Check that the current collection contains as many full messages as possible, taking into
	/// consideration the collection constraints.
	///
	/// The `AbridgedInboundMessagesCollection` is provided to the runtime by a collator.
	/// A malicious collator can provide a collection that contains no full messages or fewer
	/// full messages than possible, leading to censorship.
	pub fn check_enough_messages_included_advanced(
		&self,
		collection_name: &str,
		size_info: AbridgedInboundMessagesSizeInfo,
	) {
		// We should check that the collection contains as many full messages as possible
		// without exceeding the max expected size.
		let AbridgedInboundMessagesSizeInfo { max_full_messages_size, first_hashed_msg_max_size } =
			size_info;

		let mut full_messages_size = 0usize;
		for msg in &self.full_messages {
			full_messages_size = full_messages_size.saturating_add(msg.data().len());
		}

		// The worst case scenario is that were the first message that had to be hashed
		// is a max size message.
		assert!(
			full_messages_size.saturating_add(first_hashed_msg_max_size) > max_full_messages_size,
			"[{}] Advancement rule violation: full messages size smaller than expected. \
			full msgs size: {}, first hashed msg max size: {}, max full msgs size: {}",
			collection_name,
			full_messages_size,
			first_hashed_msg_max_size,
			max_full_messages_size
		);
	}
