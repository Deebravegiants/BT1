### Title
Webhook tenant identity (`shop`) is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` (and `topic`, `webhook_id`, `api_version`) values from HTTP headers, but only the raw request body is included in the HMAC that `Utils::HmacValidator` verifies. `Webhooks::Registry.process` trusts `request.shop` as the tenant identifier when dispatching to the app's handler, even though that field was never cryptographically bound to the signed payload.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from unauthenticated headers with no relation to the signed bytes: [2](#0-1) 

`Registry.process` validates only the body's HMAC and then immediately trusts `request.shop` as the tenant to attribute the event to: [3](#0-2) 

The identity binding that should hold is:
`shop used to authorize/attribute the webhook == shop cryptographically bound in the HMAC-signed material`

Here it instead is:
`shop used to attribute the webhook == shop supplied in an unsigned header`

This is structurally identical to the `_calcCost()` bug class: a value (`isPositive`/`shop`) that is *used* to drive a security-relevant decision (rounding direction / tenant attribution) is not the value that was actually verified (`isBuy` / the HMAC-covered bytes). Any unprivileged party who can obtain **one** valid `(raw_body, hmac)` pair — trivially done by installing the app on their own store and letting Shopify deliver a real webhook to them — can replay that exact body and HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and `X-Shopify-Topic`/`Webhook-Id`) header for a victim shop. `HmacValidator.validate` will still pass because it only checks the body against the secret; `Registry.process` will then hand the attacker-controlled `shop` value to the host app's handler as if it were an authenticated event for the victim's tenant.

### Impact Explanation
This breaks the tenant boundary that webhook consumers rely on: a handler that uses `WebhookMetadata#shop` to look up/act on a specific merchant's data can be made to process attacker-supplied body content under a victim shop's identity, since only the body — not the tenant label — is authenticated. This falls under cross-tenant access (Critical) because the identity used to select the tenant is never verified against the cryptographic proof.

### Likelihood Explanation
Moderate-to-high: requires no special privilege — only that the attacker can create/install the app on their own store to obtain one legitimate `(body, hmac)` pair for a chosen topic (a normal, unprivileged action), and that the app's webhook endpoint is reachable from the internet (it must be, to receive real Shopify webhooks). No `api_secret_key`, access token, or TLS interception is needed, since forging the header does not require recomputing the HMAC.

### Recommendation
Bind the tenant/topic/webhook identifiers into the material that is HMAC-verified, or otherwise independently authenticate them — e.g., include `shop`, `topic`, and `webhook_id` in `to_signable_string`, or require the host application to cross-check `request.shop` against a shop that is known to have completed OAuth for this specific `webhook_id`/topic before trusting it, rather than deriving raw tenant identity solely from the `X-Shopify-Shop-Domain` header.

### Proof of Concept
1. Attacker installs the app on their own store `attacker.myshopify.com` and triggers a webhook subscription (e.g., `orders/create`), capturing the raw body `B` and the corresponding `X-Shopify-Hmac-Sha256` header `H` sent by Shopify.
2. Attacker sends `POST /webhooks` to the app with the same body `B` and header `H`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `Utils::HmacValidator.validate(request)` succeeds because it only checks `B` against `H` [4](#0-3) .
4. `Registry.process` dispatches `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed(B), ...)` to the app's handler [3](#0-2) , causing the host app to process attacker-chosen data attributed to `victim.myshopify.com`.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
