This confirms the finding: `Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from headers and are never part of the HMAC-signed string [2](#0-1) . `Registry.process` only calls `Utils::HmacValidator.validate(request)` (which recomputes the HMAC over `to_signable_string`, i.e. the body) before dispatching `request.shop` and `request.topic` straight to the app's handler [3](#0-2) .

### Title
Webhook HMAC validation does not bind the `shop-domain`/`topic` headers, allowing cross-tenant webhook replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body [1](#0-0) . The HMAC that `Utils::HmacValidator.validate` checks is therefore an equality between `HMAC(app_secret, body)` and the signature header — it says nothing about which shop or topic the body belongs to. `shop`, `topic`, `webhook_id`, and `api_version` are taken verbatim from HTTP headers that are outside the signed material [2](#0-1) .

### Finding Description
The identity binding the app relies on is: *`request.shop` (used to attribute the webhook payload to a tenant) == the shop that actually generated `request.parsed_body`*. The HMAC only proves `HMAC(secret, raw_body) == signature`; it does not prove `shop-domain header == shop that owns raw_body`, because `shop-domain`, `topic`, `webhook-id`, and `api-version` are never included in `to_signable_string`. Since Shopify computes this HMAC with the single app-level `client_secret` (identical for every shop/tenant that has the app installed), a signature that is valid for shop A's webhook body remains numerically valid when that exact same body is replayed with the `shopify-shop-domain` (and/or `shopify-topic`) header rewritten to shop B. `Registry.process` performs no additional binding check — it validates the HMAC, looks up the handler by `request.topic`, and calls the handler with `shop: request.shop` taken straight from the (unauthenticated-w.r.t. HMAC) header [3](#0-2) .

### Impact Explanation
Any party who can legitimately receive one authentic webhook delivery for their own store (e.g., a merchant who installed the app — an unprivileged, low-trust actor from the app's perspective) can capture that valid `(raw_body, hmac-sha256)` pair and re-POST it to the app's webhook endpoint with the `shop-domain` header changed to a victim shop. The HMAC check still passes because the signed string never covered the header. If the host application (following this library's documented `WebhookMetadata#shop` contract) uses that field to key persistence, entitlements, or GDPR/redact actions, the attacker achieves cross-tenant data injection or corruption — writing another merchant's data under a victim's tenant key, or triggering `customers/redact`/`shop/redact` handling for a shop that never actually sent that event. This satisfies the "cross-tenant access" criterion.

### Likelihood Explanation
Requires only: (1) the app's HMAC secret is fixed per-app, not per-shop — true for all Shopify apps by design, and (2) the attacker can observe one authentic webhook for their own shop (trivial, they run their own webhook receiver/proxy) and replay it against the app's public webhook endpoint with a modified header. No leaked credentials, no privileged account, and no `api_secret_key`/access token access are needed — only participation as a normal, installed merchant of the app, which matches the "unprivileged internet user" bar for this analysis.

### Recommendation
Include `shop`, `topic`, and ideally `webhook_id`/`api_version` in the material that is authenticated, or otherwise cross-check them against a value bound to the raw body before dispatch (e.g., verify the shop domain against an independent trusted source rather than trusting the header once HMAC-of-body passes). At minimum, document/require that `Registry.process` callers re-validate that `request.shop` matches the tenant the delivery endpoint was provisioned for, since the HMAC alone does not guarantee that binding.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and lets Shopify deliver a legitimate webhook (e.g., `orders/create`), capturing the raw POST body and the `X-Shopify-Hmac-Sha256` header value.
2. Attacker re-sends the exact same body and HMAC header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and, if desired, a different `X-Shopify-Topic`).
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` is constructed and passed to `Registry.process` [3](#0-2) .
4. `Utils::HmacValidator.validate(request)` recomputes `HMAC(secret, raw_body)` and finds it equal to the supplied signature (unchanged, since only the body is signed) [4](#0-3) [1](#0-0) .
5. The handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: "victim-shop.myshopify.com", body: <attacker's own order data>, ...)`, and the host app processes attacker-controlled content as belonging to the victim tenant.
