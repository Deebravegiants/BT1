### Title
Bounties/Orders can be permanently bricked by escrowing malicious ERC20 tokens whose transfers revert - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
The `IntentGatewayV2`/`ExtrinsicIntents`/`IntrinsicIntents` order-escrow flow lets any unprivileged user (`placeOrder`) escrow an arbitrary, attacker-chosen ERC20 as one of the order's `inputs`. Settlement (`_withdraw`, called from `onAccept` on `RedeemEscrow`/`RefundEscrow`, from `onGetResponse`, or from same-chain `fillOrder`/`cancelOrder`) iterates over **all** escrowed tokens for that commitment in a single loop and calls `safeTransfer`/`.call` for each. If any one token reverts on transfer (e.g., a blacklist-style token that always reverts transfers from the gateway address), the whole withdrawal reverts, permanently freezing every other legitimate token escrowed in the same order alongside it.

### Finding Description
`placeOrder` in `evm/src/apps/IntentGatewayV2.sol`/`evm/src/apps/intentsv2/ExtrinsicIntents.sol` accepts an `Order` whose `inputs` array names arbitrary ERC20 addresses and pulls them via `safeTransferFrom` into escrow, with no whitelist check: [1](#0-0) 

The escrowed balances are later released in `IntentsBase._withdraw`, which loops over `body.tokens` and transfers each one out, without isolating failures per token: [2](#0-1) 

This function is the single settlement path reached from:
- Cross-chain `onAccept` for both `RedeemEscrow` (solver claim) and `RefundEscrow` (user refund), authenticated only against a registered gateway instance, not against token safety: [3](#0-2) 
- `onGetResponse` for source-initiated cancellation: [4](#0-3) 
- Same-chain fill/cancel via `IntrinsicIntents`, which calls the identical `_withdraw`: [5](#0-4) 

An attacker places an order whose `inputs` include one legitimate token (e.g. USDC) and one malicious ERC20 that reverts every `transfer`/`transferFrom` where `from` is the gateway contract (the equivalent of the OpenQ report's blacklist). A solver fills the order, and settlement is attempted — `_withdraw` reverts because the malicious token cannot be transferred out, so the legitimate USDC escrowed in the same order is dragged down with it, since both are transferred in the same loop/transaction.

For cross-chain orders, `EvmHost.dispatchIncoming` catches the `onAccept` revert with a low-level `.call` and deletes the request receipt "so that it can be retried": [6](#0-5) 
but because the malicious token's revert condition is permanent (it always reverts on transfers from the gateway), every retry fails identically — the request can never be delivered, and the escrow (including the well-behaved token) is frozen indefinitely. The same applies to the `onGetResponse` cancellation path and to same-chain `withdraw`/`cancelOrder`, where the revert simply prevents settlement forever since there is no way to remove or skip the poisoned token from `body.tokens`/`_orders`.

The Tron variant contains the identical pattern: [7](#0-6) 

### Impact Explanation
This permanently freezes funds: legitimate escrowed tokens (input tokens deposited by the user, and the solver's claim to them) become unrecoverable once co-escrowed with even a single adversarial token in the same order, because the whole withdrawal transaction always reverts and there is no mechanism to partially settle or exclude the bad token. This matches the "permanent freezing of funds" acceptance criterion, reachable from a single unprivileged `placeOrder` call by anyone. It also degrades the intent-fill economics: a solver who fills such an order (transferring real value to the beneficiary) can never redeem the escrowed input from `RedeemEscrow`, causing a direct loss for the solver.

### Likelihood Explanation
Likelihood is high: `placeOrder` is fully unprivileged and permissionless, ERC20 tokens with transfer-time reverts or blacklists (deployed by the same attacker who places the order) are trivial and cheap to create, and no token whitelist or per-token isolation exists anywhere in the escrow/withdraw path (`placeOrder`, `_withdraw`, `withdraw` in the Tron variant). The attack requires no privileged role and no race condition — a single order placement with a mixed input set is sufficient to set the trap for the next solver or the user's own refund path.

### Recommendation
- Isolate per-token transfer failures in `_withdraw`/`withdraw` (Tron) using a try/catch (or low-level call with a success check that does not revert the whole function) so that one non-transferable token cannot block the release of other, well-behaved tokens in the same order.
- Alternatively/additionally, require an explicit token whitelist (as OpenQ ultimately adopted) enforced in `placeOrder`, so only vetted ERC20s can be escrowed as `order.inputs`, `predispatch.assets`, or fee tokens.
- Consider accounting for a "stuck" token separately (e.g., leaving its escrow balance in place while still releasing the other tokens and finalizing the order) so beneficiaries are not penalized for a token they didn't choose.

### Proof of Concept
1. Attacker deploys a malicious ERC20 (`MockBAD`-style) whose `_beforeTokenTransfer`/`_update` hook reverts whenever `from == <IntentGateway address>` (the attacker knows the gateway address in advance).
2. Attacker calls `placeOrder` with `order.inputs = [ {token: USDC, amount: X}, {token: MockBAD, amount: Y} ]`, approving and escrowing both tokens (see `evm/src/apps/IntentGatewayV2.sol` predispatch/escrow loop, lines 244-330).
3. A solver fills the order (`fillOrder`), delivering the required outputs to the beneficiary and triggering the `RedeemEscrow` dispatch (`ExtrinsicIntents._fillCrossChain` or `IntrinsicIntents._fillSameChain`).
4. Settlement invokes `_withdraw` with `body.tokens = [USDC, MockBAD]`. The loop reaches the `MockBAD` transfer, which reverts; the whole `_withdraw` call reverts, so the solver never receives the USDC despite having already paid out the beneficiary.
5. For the cross-chain case, `EvmHost.dispatchIncoming` deletes the request receipt to allow a retry, but every retry hits the same permanent revert — the USDC escrow (and the solver's claim to it) is frozen forever. The same order can never be cancelled/refunded successfully either, since `cancelOrder`/`onGetResponse` route through the identical `_withdraw` with the same poisoned token list.
