### Title
Webhook `shop`/`topic`/`webhook_id` identity fields are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body (`request.to_signable_string` = `@raw_body`), using a secret (`Context.api_secret_key`) that is shared across **all** shops that have installed the app. [1](#0-0)  The `shop`, `topic`, and `webhook_id` values that are handed to the application's handler as the tenant/identity context are read directly from HTTP headers and are never included in the signed bytes. [2](#0-1) 

### Finding Description
`Webhooks::Request#hmac` computes/returns the signature from the `hmac-sha256` header, and `#to_signable_string` returns only `@raw_body`. [3](#0-2)  `HmacValidator.validate` recomputes `HMAC-SHA256(api_secret_key, to_signable_string)` and compares it to the received value using `OpenSSL.secure_compare`. [4](#0-3)  Because the signable string is the body only, the `shop`, `topic`, and `webhook_id` headers are **not bound** to the signature at all.

`Registry.process` uses exactly this unauthenticated `request.shop` value as the tenant identity passed to the application's webhook handler:
```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
``` [1](#0-0) 

Since `api_secret_key` is the app's single, static client secret (not a per-shop key), a HMAC that is valid for one shop's webhook delivery is *also* valid for identical bytes claimed to originate from a different shop — the identity binding `shop_header == shop_that_signed_the_request` is never enforced by the gem. An unprivileged attacker who legitimately installs the target app on their own store (or who can otherwise trigger/observe a webhook delivery with a body they can reproduce, e.g. topics whose payload is empty or fully attacker-controlled, such as `app/uninstalled`, `shop/redact`, `customers/redact`, or `customers/data_request` with predictable/duplicate fields) can capture a genuine `(raw_body, hmac)` pair and replay it to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header (and optionally `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) to claim it belongs to a *different, victim* shop. `HmacValidator.validate` will still pass because it only checks the body bytes against the shared secret, never the shop header.

### Impact Explanation
This breaks the identity binding "shop authenticated == shop acted upon" and enables cross-tenant impact: a host application built on this gem that trusts `WebhookMetadata#shop` to select which merchant's data to mutate/delete/return (a normal and expected usage pattern, especially for the mandatory GDPR topics `shop/redact`, `customers/redact`, `customers/data_request` which this gem specifically registers and delivers) can be tricked into performing actions attributed to, or targeting, a shop that never actually sent the webhook. This matches the "cross-tenant access" Critical impact category, since the origin-shop claim used for authorization/routing is not part of the authenticated payload.

### Likelihood Explanation
Exploitability depends on the attacker being able to reproduce a body that will hash-match a legitimately-signed request while claiming a different shop header. This is realistic for webhook topics with static, minimal, or attacker-influenced payloads (e.g., `app/uninstalled` typically carries a small/predictable body, and GDPR topics carry attacker/merchant-supplied identifiers the attacker can align across their own shop and their forged request). No secret, token, or privileged access is required — only the ability to install the app on one's own shop (a normal unprivileged action) and send a crafted HTTP request to the app's public webhook endpoint.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) values into the authenticated signable string, or otherwise incorporate a per-shop secret/context into HMAC validation, so that the header-derived shop cannot be altered independently of the signed body. At minimum, `Utils::HmacValidator.validate` should be extended (or a new check added) so that `Registry.process` verifies the claimed `shop` corresponds to a shop that is actually registered/subscribed for that specific webhook delivery, rather than trusting the header verbatim.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; trigger a webhook with a body you can predict/reproduce (e.g., `app/uninstalled`).
2. Capture the raw request Shopify sends to the app's webhook endpoint, including headers `X-Shopify-Hmac-Sha256: <hmac>` and `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. Replay the same raw body and the same `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, but replace `X-Shopify-Shop-Domain` with `victim.myshopify.com`.
4. `Utils::HmacValidator.validate` recomputes HMAC over `raw_body` only and succeeds (the secret and body are unchanged), so `Registry.process` invokes the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)`, causing the host application to process an action attributed to `victim.myshopify.com` that the victim never sent.           received_signature = verifiable_query.hmac
