### Title
Webhook HMAC validation does not bind the `shop` (tenant) identity, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its signable payload from the raw body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values used by the application come from unauthenticated HTTP headers. `Utils::HmacValidator` verifies the HMAC over that body-only payload, so the tenant (`shop`) that the request claims to belong to is never bound to the signature that authenticates the request.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from attacker-controllable HTTP headers with no cryptographic binding to the body or to each other: [2](#0-1) 

`Utils::HmacValidator.validate` / `validate_signature` compute and compare the HMAC strictly against `to_signable_string`, i.e. the raw body: [3](#0-2) 

`Registry.process` trusts this validation and then forwards the header-derived, unauthenticated `request.shop` (along with `topic`/`webhook_id`) straight into the `WebhookMetadata` passed to the app's handler: [4](#0-3) 

The documented handler pattern uses `data.shop` as the tenant key to route/store the event (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`): [5](#0-4) 

The equality that should hold is: `shop_authenticated_by_HMAC == shop_used_by_app_logic`. Because the HMAC only covers `@raw_body`, `shop_authenticated_by_HMAC` is undefined/empty — the gem authenticates "this body came from someone who knows `api_secret_key`" but not "this body belongs to shop X." `shop_used_by_app_logic` is simply whatever value arrives in the `x-shopify-shop-domain` (or `shopify-shop-domain`) header, which the caller fully controls independent of the signed body.

### Impact Explanation
An attacker who controls their own Shopify shop with the app installed (an unprivileged tenant from the app's cross-tenant boundary) can trigger a legitimate webhook on their own shop (e.g. `orders/create`, `app/uninstalled`, `customers/redact`, `shop/redact`), capture the valid `(raw_body, hmac)` pair Shopify sends, and replay that exact HTTP request to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. Because the HMAC only signs the body, the signature remains valid, `Utils::HmacValidator.validate` passes, and `Registry.process` invokes the app's handler with `data.shop` set to the victim shop. This lets the attacker forge webhook events attributed to any shop domain, including mandatory compliance topics (`shop/redact`, `customers/redact`, `app/uninstalled`), potentially causing the app to delete/deactivate a victim tenant's data or otherwise corrupt cross-tenant state — a cross-tenant access/impersonation impact.

### Likelihood Explanation
Any developer/merchant who can install the app on their own store can obtain a genuine `(body, hmac)` pair for a webhook they control, then replay it with a forged shop header to any internet-reachable webhook endpoint exposed by the host app using this gem's documented `Registry.process` flow. No secret, access token, or privileged access is required.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the value that is HMAC-verified, or otherwise cryptographically tie the header-derived identity to the signed payload before trusting `request.shop` in `WebhookMetadata`. At minimum, document/require that host apps must not rely on `data.shop` from `Webhooks::Request` as an authenticated tenant identifier unless it is independently corroborated (e.g., by verifying the shop is one for which a `register`/webhook subscription actually exists), since the gem itself has no protection against shop-header spoofing on otherwise-valid webhook bodies.

### Proof of Concept
```ruby
# Attacker owns "attacker-shop.myshopify.com" with the target app installed.
# Attacker triggers a webhook (e.g. orders/create) on their own shop and
# captures Shopify's request:
raw_body = '{"id":1,"note":"legit order on attacker shop"}'
hmac     = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), APP_SECRET, raw_body)

# Attacker replays the SAME body+hmac to the app's webhook endpoint,
# but swaps the shop-domain header to the victim shop:
headers = {
  "x-shopify-topic"        => "orders/create",
  "x-shopify-hmac-sha256"  => Base64.encode64(hmac),  # still valid! (body unchanged)
  "x-shopify-shop-domain"  => "victim-shop.myshopify.com", # forged
  "x-shopify-webhook-id"   => "any-id",
  "x-shopify-api-version"  => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HMAC validation passes (Utils::HmacValidator only checks raw_body),
#    handler.handle is invoked with data.shop == "victim-shop.myshopify.com"
```

          end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
