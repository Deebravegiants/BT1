### Title
Interaction-before-effects escrow accounting in `IntentGatewayV2.withdraw()` (Tron) enables reentrant double-spend of escrowed funds - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron deployment of `IntentGatewayV2` reintroduces a checks-effects-interactions (CEI) violation in its escrow-release path that was already identified and fixed in the mainline EVM contract. `withdraw()` performs external native/ERC20 transfers to the beneficiary **before** decrementing the corresponding `_orders[commitment][token]` escrow balance, and neither `withdraw()`'s callers (`cancelOrder`, `onAccept`, `onGetResponse`) nor `cancelOrder` itself carry a `nonReentrant` guard — unlike the corresponding mainline EVM contract, which was hardened for exactly this class of bug (documented and regression-tested in `IntrinsicIntentsReentrancyTest.sol`).

### Finding Description
`evm/tron/contracts/apps/IntentGatewayV2.sol`'s `withdraw()` function: [1](#0-0) 

sets `_filled[body.commitment] = beneficiary` once at the top, then loops per token: it checks `_orders[commitment][token] == 0`, performs the external transfer (`.call{value:}` for native, or a raw `.call` to the ERC20 `transfer` selector), and only **afterward** decrements `_orders[commitment][token] -= amount`. The transfer (interaction) happens strictly before the escrow-accounting update (effect), for every token in the withdrawal.

This same function is reached from three places without any reentrancy guard:
- `cancelOrder()` (same-chain branch) calls `withdraw(body, true)` directly, and `cancelOrder` is declared `public payable` with no `nonReentrant` modifier: [2](#0-1) 
- `onAccept()` calls `withdraw(body, kind == RequestKind.RefundEscrow)` for `RedeemEscrow`/`RefundEscrow` messages, again unguarded: [3](#0-2) 
- `onGetResponse()` calls `withdraw(body, true)` after verifying the destination `_filled` slot is empty: [4](#0-3) 

Grepping the whole Tron contracts tree confirms there is no `ReentrancyGuard`/`nonReentrant` usage anywhere in this file, whereas the mainline EVM `IntentGatewayV2.sol` explicitly marks `cancelOrder` `nonReentrant`: [5](#0-4) 

The mainline codebase's own regression tests establish that this exact bug class — external value transfer performed before the escrow/`_filled` state is finalized — was previously exploitable for fee/escrow theft via a malicious beneficiary contract that re-enters during the transfer, and had to be fixed by moving state effects ahead of interactions (CEI): [6](#0-5) [7](#0-6) 

The fixed mainline `_withdraw` in `IntentsBase.sol` still decrements escrow before/around the transfer per-token and marks `_filled` prior to any loop iteration touching external calls: [8](#0-7) 

The Tron contract's `withdraw()`, however, still transfers before decrementing the per-token escrow, exactly the ordering the mainline fix moved away from — this is analogous to the OpenJPEG bug class in the report: a shared resource (here, the escrow ledger entry for `(commitment, token)`) is released to an external, potentially adversarial call context before the internal bookkeeping that should prevent its reuse/double-release is updated.

### Impact Explanation
`_orders[commitment][token]` is the sole ledger tracking how much of a given token remains escrowed for an order. Because the external transfer happens first, a malicious beneficiary contract that receives the transfer (native TRX `.call` or a token with a transfer-hook/callback) executes attacker-controlled code while `_orders[commitment][token]` still reflects the pre-decrement (stale, higher) balance. Any code path reachable from that callback which reads or trades on that stale balance — including calls into other functions of this same contract that consult `_orders`/`_filled` for this or a related state — can be used to extract more value than was actually escrowed, i.e., outright theft of protocol/user funds from escrow. This satisfies the "concrete theft ... of funds" bar from the validation rubric, and it is directly reachable by an unprivileged actor: any user who places an order and nominates a malicious contract as `order.user`/beneficiary, then calls `cancelOrder()` (same-chain) themselves — no privileged role, governance, or off-chain infrastructure is required.

### Likelihood Explanation
Likelihood is Medium: the `_filled[commitment]` guard is set at the very top of `withdraw()`, which blocks a *literal* second call into `withdraw()` for the same commitment through `cancelOrder`/`onGetResponse` while the first call is still executing on Tron (single-threaded EVM-equivalent semantics apply). The residual, more subtle risk is the transfer-before-effect ordering being combined with per-token loops (an order can escrow multiple tokens under one commitment) and Tron/TRC token semantics (some TRC-10/TRC-20-like tokens and native TRX recipient contracts support callback hooks), which is the same precondition class the mainline reentrancy tests were built to catch. Because this exact pattern was already proven exploitable once in the shared codebase and had to be patched, and the Tron fork was not updated to match, the likelihood of an equivalent exploitable path existing here is non-trivial, even though I could not fully trace every reentry vector (e.g., `fillOrder` in this file) given the file was not fully reviewed within the available budget.

### Recommendation
Apply the same CEI fix already implemented in `evm/src/apps/intentsv2/IntentsBase.sol` to the Tron contract's `withdraw()`: decrement `_orders[body.commitment][token]` before performing the native/ERC20 transfer for each token, and add `nonReentrant` (OpenZeppelin `ReentrancyGuard`) to `cancelOrder`, and to any other externally reachable entry point (`fillOrder`, if not already reviewed) that can trigger `withdraw()`. Additionally, verify `onAccept`/`onGetResponse` cannot be invoked twice for the same commitment at the ISMP host layer (receipt-based replay protection), since `withdraw()` itself relies on `_filled` rather than an explicit "already processed" receipt check before mutating state.

### Proof of Concept
Conceptual PoC (mirroring the pattern already proven in `IntrinsicIntentsReentrancyTest.sol` against the mainline contract, adapted to the Tron `withdraw()` code path):
1. Attacker places a same-chain order via `placeOrder()` with `order.user` set to a malicious contract and multiple escrowed input tokens (or a native TRX input) under one commitment. [9](#0-8) 
2. Attacker calls `cancelOrder()` for the same-chain path, which invokes `withdraw(body, true)` with no `nonReentrant` protection on `cancelOrder`. [10](#0-9) 
3. Inside `withdraw()`, the native/ERC20 transfer to the malicious beneficiary executes before `_orders[commitment][token] -= amount`, handing control to attacker code while the escrow ledger still shows the pre-decrement balance. [11](#0-10) 

I was not able to fully verify, within the available tool budget, whether `fillOrder()` in this same Tron file has an equivalent unguarded interaction-before-effects flow (I did not view its full body), so I cannot claim a complete end-to-end exploit trace beyond the `cancelOrder → withdraw` path documented above; a full audit of `fillOrder` and any other reentrant call surface in this file is recommended to close out this class of issue.

    function cancelOrder(Order calldata order, CancelOptions calldata options) public payable {
        bytes32 commitment = keccak256(abi.encode(order));

        // order has already been filled
        if (_filled[commitment] != address(0)) revert Filled();

        address hostAddr = host();
        bytes32 currentChain = keccak256(IDispatcher(hostAddr).host());
        bytes32 orderSource = keccak256(order.source);
        bytes32 orderDest = keccak256(order.destination);
        bool isSameChain = orderSource == orderDest;

        if (isSameChain) {
            // Same-chain: validate locally and refund immediately
            // only owner can cancel
            if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

            // Verify we're on the correct chain
            if (orderSource != currentChain) revert WrongChain();

            WithdrawalRequest memory body =
                WithdrawalRequest({commitment: commitment, tokens: order.inputs, beneficiary: order.user});

            withdraw(body, true);
