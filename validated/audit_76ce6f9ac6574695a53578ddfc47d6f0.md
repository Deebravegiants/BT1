EvmHost.dispatchIncoming already isolates per-item failures with a low-level `.call` and swallows failures with early `return` rather than reverting [1](#0-0) , and this design is confirmed by documentation and tests showing the rest of the batch proceeds when one delivery fails [2](#0-1) . So the EVM-side single-item isolation is already handled correctly, unlike the reported ClearingHouse bug.

However, on the Substrate side (`modules/ismp/core/src/handlers/response.rs`), the GET-response batch handler diverges from this isolation pattern used everywhere else in the codebase.

### Title
Single point of failure in GET-response batch handling aborts unrelated valid responses - (File: `modules/ismp/core/src/handlers/response.rs`)

### Summary
`response.rs::handle` processes a batch of GET responses (a single `ResponseMessage` can carry many `GetResponse` items) using `.collect::<Result<Vec<_>, _>>()?` [3](#0-2) . Any single item's failure (an `?` inside the per-item closure) short-circuits the whole batch and returns `Err` from `handle`, discarding the results of every other item in the same batch — including items that already succeeded and had their receipts stored moments earlier in the same loop.

### Finding Description
Contrast this with the equivalent POST-request handler, `request.rs::handle`, which processes each request independently and collects a plain `Vec<Result<Event, Error>>` (not `Result<Vec<_>, _>`) so that one request's `Err` does not affect the others [4](#0-3) . That per-item isolation is the intended pattern for batches in this codebase — it's also the pattern deliberately implemented in Solidity's `EvmHost.dispatchIncoming`, which explicitly returns instead of reverting on a failed delivery so "the entire batch" is not reverted [5](#0-4) .

`response.rs`, however, still uses the fail-fast `Result<Vec<_>, _>` collector. Any of the following per-item conditions inside the closure will trigger the early `?` and abort the whole batch:
- `state_machine.verify_state_proof(...)?` for that item's storage keys
- `router.module_for_id(request.from.clone())?` failing to resolve a destination module
- the re-checked duplicate-response guard, `Err(Error::DuplicateResponse {...})?`
- `host.store_response_receipt(&response, &msg.signer)?`
- `host.delete_response_receipt(&response)?` on cleanup after a failed callback

Because the outer message-execution path (`Pallet::<T>::execute` in `modules/pallets/ismp/src/impls.rs`) also treats any `handle_incoming_message` error as fatal for the whole extrinsic — depositing an `Errors` event and returning `Error::InvalidMessage` [6](#0-5)  — and `handle_unsigned` is `#[frame_support::transactional]` [7](#0-6) , a single failing GET-response item inside a `ResponseMessage` causes the entire extrinsic to revert. This nullifies delivery of every other, unrelated, independently-valid GET response bundled in the same `ResponseMessage`/batch, even though those other items would have succeeded on their own.

### Impact Explanation
This is a griefing/DoS vector against message delivery, matching the reported bug class (a single failing item in a loop causing complete failure of otherwise-independent, valid work). A relayer that batches many GET responses together (which the protocol design and fee/gas incentives encourage) risks having the whole batch fail because of one bad item — for example, an app module that was deregistered from the router between dispatch and delivery, or a request whose storage-proof verification fails for reasons unrelated to the other items in the batch. Because the whole extrinsic is transactional, the receipts and weights for the already-processed, successful items in the batch are rolled back too, and none of the responses are delivered. This can permanently deny/delay delivery of otherwise-valid cross-chain responses (a message-delivery availability issue), and forces relayers to either submit responses one-by-one (defeating the batching design) or risk their whole submission being wasted whenever a single item is problematic.

### Likelihood Explanation
Likelihood is Medium: it only requires one item among many GET responses in a single relayed batch to hit one of the listed failure conditions (deregistered module, invalid proof for one key set, or a receipt race from the same batch/reentrancy). Since relayers are incentivized to batch multiple responses for gas efficiency, and any of several independent per-item failure conditions can trigger this, the probability of at least one item degrading an entire batch over time is non-trivial, though it requires a genuine per-item failure rather than an attacker deliberately forging failures (permissionless relayers do not control module registration or proof validity for others' items).

### Recommendation
Change `response.rs::handle` to isolate per-item failures the same way `request.rs::handle` does: collect a `Vec<Result<Event, Error>>` (using a per-item lambda plus `.and_then`, mirroring the `lambda()`/`and_then` pattern in `request.rs`) instead of `.collect::<Result<Vec<_>, _>>()?`. This keeps `MessageResult::Response { events, .. }` consistent with `MessageResult::Request { events, .. }`, so a failing GET response in a batch is reported as an error for that item alone (and the enclosing `execute()` already treats any item-level error as failing the whole extrinsic, per its own comment "so we can not be spammed with failing txs" — that policy question is separate and out of scope here, but the fix at minimum stops one item's failure from silently discarding sibling items' completed receipt/weight side effects before the outer check runs).

### Proof of Concept
1. Two apps, A and B, are each registered to receive one GET response. A relayer submits a single `ResponseMessage` (batch) containing GetResponse items for both A and B.
2. Before the relayer's proof lands, the app B's module registration is removed from the router (or B's storage-proof key becomes stale/invalid for any legitimate reason unrelated to A).
3. `response.rs::handle` processes A's item first (succeeds, receipt stored, event queued), then processes B's item: `router.module_for_id(...)?` returns `Err`, which propagates through `.collect::<Result<Vec<_>, _>>()?` at line 114, returning `Err` from `handle` for the entire `ResponseMessage`.
4. `Pallet::<T>::execute` sees the `Err` from `handle_incoming_message`, deposits an `Errors` event, and returns `Error::InvalidMessage`; because `handle_unsigned` is `#[transactional]`, all state changes (including A's already-stored receipt) roll back.
5. Result: A's independently-valid GET response, which should have been delivered, is not delivered in this batch, and the relayer must resubmit A alone — demonstrating that B's unrelated failure fully blocks A's otherwise-successful delivery, unlike the equivalent request-handling path.

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }
