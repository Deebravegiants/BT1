### Title
Pre-seeding the HyperSwap V2 TOKEN/LT pair between graduation phases skews LP open price away from the curve-close price - ([File: packages/contracts/src/Bonding.sol])

### Summary
Alt.fun's graduation is split into two permissionless transactions. Phase 1 (`_enterGraduating` → `_prepareGraduationLiquidity`) freezes `tokensForLP` and `ltFromPair` from the curve's pair state at the moment the graduation trigger fires [1](#0-0) . Phase 2 (`finalizeGraduation`) later consumes those cached amounts against whatever the HyperSwap V2 TOKEN/LT pair's live state is at that time [2](#0-1) . Because pair creation and direct token/LT transfers into that pair are permissionless, an unrelated wallet can create the pair and skew its reserves before `finalizeGraduation` runs, so the amounts pinned against the *empty* phase-1 state get deposited into a *non-empty, attacker-skewed* phase-2 pool.

### Finding Description
`_enterGraduating` computes `tokensForLP`/`ltFromPair` purely from the bonding curve's pinned reserves — never re-reading exchange rate or HyperSwap state — and the code explicitly documents that this is by design: "Exchange-rate drift between phase 1 and phase 2 is accepted... What drifts is only the USD denomination of the LT side" [3](#0-2) . This reasoning assumes the *token:LT ratio* itself cannot drift between phases — but it only accounts for LT-side price drift, not for the HyperSwap V2 pair's reserve ratio being altered directly.

`finalizeGraduation` calls `_ensureUniswapV2Pair` (creates the pair if it doesn't exist) and then `_seedUniswapV2Direct(tokenAddress, lt, lpPair, p.tokensForLP, p.ltFromPair, protectedLT)` [4](#0-3) . Both `Bonding.finalizeGraduation` and `LPLock.recordLock` are externally callable by anyone with no re-validation that the target pair is still empty/unskewed at deposit time — `finalizeGraduation` is documented as "Permissionless — keeper drives the happy path; anyone can rescue a stuck token", and is explicitly "brick-proof against a front-runner pre-creating the pair and dust-seeding it between phases" [5](#0-4)  — i.e. the contract acknowledges pre-seeding as a reachable scenario and only claims resistance to being *bricked*, not to being seeded at a skewed price.

This is the structural analog of ALPINE-CVE-2016-9273: a size/shape value (`td_nstrips`, here `tokensForLP`/`ltFromPair`) is captured once against one snapshot of a structure (the TIFF strip table / the empty HyperSwap pair) and is later consumed against a different, mutated instance of that structure (a resized strip array / a pair with attacker-donated reserves) without re-deriving the value from the structure's current state — the original bug turns this into an out-of-bounds read; here it turns into an LP seeded at a ratio the attacker chose rather than the curve's true close price.

### Impact Explanation
If the fallback rebalancing path (`_seedRebalancing` / `_pairRebalance` / `_seedDirectMint`) accepts whatever ratio the pre-seeded pool enforces instead of reverting on mismatch (the "happy path" `pair.mint`-direct call can only work cleanly against an empty pair), the graduated LP opens at a price set by the attacker's donation ratio rather than the curve's last marginal price — directly violating the protocol's own "zero price gap" invariant. This misprices the pool that all post-graduation Zap trades route through, letting the attacker (or an accomplice) arbitrage the mispriced pool at the expense of the LP (locked in `LPLock`, unrecoverable in v1) and subsequent traders — a form of value extraction from LP funds that the protocol is supposed to guarantee open at the fair price.

### Likelihood Explanation
Both preconditions are permissionless and cheap: creating a HyperSwap V2 pair for a known TOKEN/LT address pair, and transferring TOKEN or LT directly into it, require no special role. The attacker only needs to watch for `TokenGraduating` (which publishes the pinned `tokensForLP`/`ltFromPair` amounts) and act before whichever address calls `finalizeGraduation`; since the keeper is documented to "drive finalize within ~60s" [6](#0-5) , the window is short but nonzero, and any delay (congestion, keeper failure) widens it, and finalize itself is permissionless so the attacker could also race to call it against their own pre-seeded pool.

### Recommendation
Before depositing the phase-1-pinned amounts in `finalizeGraduation`, re-validate that the HyperSwap V2 pair's live reserves are still empty/zero, or recompute the deposit ratio to match the pair's live state using slippage protection stricter than `amountMin = 1`, or fail closed (revert / require permissioned recovery) whenever the pair was seeded by anything other than `Bonding` itself.

### Proof of Concept
1. Trader buys on a bonding curve until `canGraduate` trips; `_enterGraduating` fires and pins `tokensForLP`/`ltFromPair`, emitting `TokenGraduating`.
2. Before any keeper calls `finalizeGraduation`, an unrelated wallet permissionlessly calls the HyperSwap V2 factory to create the TOKEN/LT pair, then directly `transfer`s a skewed ratio of TOKEN and/or LT into that pair address.
3. Any address then calls `Bonding.finalizeGraduation(tokenAddress)`. `_seedUniswapV2Direct` deposits the phase-1-pinned `tokensForLP`/`ltFromPair` against the now-nonempty, attacker-skewed pair, falling back to the rebalancing/direct-mint path (whose exact bounds-checking I was unable to fully verify from the code retrieved) rather than reverting.
4. `LPLock.recordLock` finalizes the lock on whatever liquidity resulted, and the pool subsequently trades at the attacker-influenced ratio rather than the curve-close price.

I was not able to inspect the full bodies of `_seedRebalancing`, `_pairRebalance`, and `_seedDirectMint` within the available tool budget — I confirmed their existence and role from `Bonding.sol` references and the prompt's own Rules section (which explicitly names them as the relevant fallback surface), but could not verify line-by-line whether their internal slippage checks fully close this gap. A Devin session with full file access to `packages/contracts/src/Bonding.sol` would be needed to confirm the exact fallback behavior and craft a concrete Foundry PoC with numeric price-impact.

```text
    function finalizeGraduation(
        address tokenAddress
    ) external nonReentrant {
        BondingStorage storage $ = _s();
        TokenInfo storage info = $.tokenInfo[tokenAddress];
        if (info.lifecycle != Lifecycle.Graduating) revert NotGraduating();

        address lt = info.ltAddress;
        PendingGraduation memory p = $.pendingGraduation[tokenAddress];

        // Anything in this contract beyond `p.ltFromPair` belongs to a
        // concurrent graduation on the same LT (Phase 1 transferred it
        // via `Router.graduate`) or to stray dust. Either way it is
        // off-limits to this graduation's deposit and sweep — see
        // `_routerDepositAndDispose` and `_sweepLTToOwner`.
        // Saturating subtract: a balance below `p.ltFromPair` shouldn't
        // be reachable in normal operation, but we keep finalize from
        // bricking on a Panic if any future code path or non-canonical
        // LT briefly violates the invariant.
        uint256 ltBalance = IERC20(lt).balanceOf(address(this));
        uint256 protectedLT = ltBalance > p.ltFromPair ? ltBalance - p.ltFromPair : 0;

        address lpPair = _ensureUniswapV2Pair(tokenAddress, lt);
        uint256 liquidity = _seedUniswapV2Direct(tokenAddress, lt, lpPair, p.tokensForLP, p.ltFromPair, protectedLT);
```
