### Title
Unbounded BEEFY signature array lets an attacker inflate `submit_proof` / `EcdsaBeefy.verify` execution cost far beyond its fixed benchmarked weight/gas budget - ([File: modules/consensus/beefy/verifier/src/lib.rs], [File: evm/src/consensus/EcdsaBeefy.sol])

### Summary
The TUF advisory (GHSA-2828-9vh6-9m6j / CVE-2020-6173) describes a DoS where an attacker who can post metadata can attach an unbounded number of invalid signatures, forcing every verifying client to burn CPU time on signature checks before rejecting the file. Hyperbridge's BEEFY consensus verifiers (both the Rust `pallet-ismp`/`pallet-beefy-consensus-proofs` path and the Solidity `EcdsaBeefy` path) have the analogous shape: they loop over an attacker-supplied `votes`/`signatures` array and run one recover/verify per entry, and the only length check (`checkParticipationThreshold` / `check_participation_threshold`) is a *lower* bound (supermajority), not an *upper* bound.

### Finding Description
In `EcdsaBeefy.sol::verifyMmrUpdateProof`, `sigLen` is taken directly from the attacker-controlled proof (`relayProof.signedCommitment.votes.length`), and the only length validation is `checkParticipationThreshold(sigLen, authoritySet.len)`, which only rejects *too few* signatures (`SuperMajorityRequired`), never *too many*: [1](#0-0) 

Every entry in `votes` triggers an `ECDSA.recover` call inside a loop sized by `sigLen`, and the resulting `authorities` array is fed into `MerkleMultiProof.VerifyProof` sized by the same attacker-controlled length: [2](#0-1) 

There is no check that `sigLen <= authoritySet.len`, that `authorityIndex` values are within range, or that indices are deduplicated before the expensive `ecrecover` + merkle-proof work is performed. An attacker can repeat the same (or bogus) signature many times with distinct or duplicate `authorityIndex` values to drive `sigLen` arbitrarily high (bounded only by calldata size / block gas limit), causing the transaction (or the off-chain simulation that precedes it) to cost far more gas/time than a legitimate commitment would.

The identical pattern exists in the Rust verifier used by `pallet-ismp-beefy` / `pallet-beefy-consensus-proofs`: `signatures_length` is read directly from the submitted `MmrProof`, checked only against the supermajority lower bound via `check_participation_threshold`, then iterated to perform a `secp256k1_recover` per entry: [3](#0-2) 

Crucially, `submit_proof` in `pallet-beefy-consensus-proofs` is dispatched with a **fixed, benchmarked weight** (`T::WeightInfo::submit_proof()`), which was benchmarked against a single fixed-size fixture proof rather than scaled by the number of embedded signatures: [4](#0-3) [5](#0-4) 

The only outer bound on the proof is `BoundedVec<u8, T::MaxProofSize>`, a raw byte-size cap on the whole payload — not a cap on the number of ECDSA signature entries the SCALE-decoded `signatures: Vec<SignatureWithAuthorityIndex>` field may contain (each signature is only 65 bytes plus a `u32` index, so many thousands can fit within a modest `MaxProofSize`): [6](#0-5) 

Because the *declared* weight paid by the submitter is fixed but the *actual* execution cost (number of `secp256k1_recover` calls) scales with the attacker-chosen signature count, a malicious signed submission can consume substantially more block execution time than its assigned weight budgets for — the same "delay" DoS primitive as the TUF advisory, translated to on-chain block-time/gas exhaustion instead of client-side verification delay.

### Impact Explanation
This is reachable by any account able to submit a signed extrinsic (a relayer/prover, i.e., "unprivileged message dispatcher") calling `BeefyConsensusProofs::submit_proof`, or any caller routing a consensus message through `HandlerV2`/`EcdsaBeefy.verify` on EVM. By inflating the signature count in the proof far beyond what a real BEEFY commitment would carry, the attacker can:
- On Substrate: cause `submit_proof` to run for much longer than its benchmarked weight, since weight is a fixed constant rather than a function of the decoded signature count — risking block time overruns / degraded throughput for the whole chain if repeated.
- On EVM: force `EcdsaBeefy.verify` (called via `HandlerV2`/`ConsensusRouter`) to spend gas linearly in the (unbounded) number of votes, which can cause proof submissions to become uneconomical or to revert against the block gas limit, effectively blocking honest consensus updates from being processed if the attacker can front-run/flood proof submission slots.

This matches the CWE-400 (resource-only) / "Medium — Client Denial of Service" classification of the original advisory, mapped here to a resource-consumption route in the consensus-verification path rather than a fund-loss or forged-message path.

### Likelihood Explanation
Any account can call `submit_proof` (it is a plain signed extrinsic, not permissioned) with a crafted `BoundedVec<u8, MaxProofSize>` payload whose SCALE-decoded `signatures` vector contains many entries — this requires no special access, only paying (and losing, per the pallet's fee-refund-on-success design) the base transaction fee, which is cheap relative to the block-time cost imposed. Likelihood is Medium: the attack is easy to construct, but its "damage" is throughput degradation rather than fund loss, and repeated abuse is visible/attributable on-chain (submitter pays fee on failure) which limits sustained exploitation somewhat.

### Recommendation
- Add an explicit upper bound check that `sigLen <= authoritySet.len` (and reject duplicate `authorityIndex` values) before performing any `ecrecover`/`secp256k1_recover` work, in both `EcdsaBeefy.sol::verifyMmrUpdateProof` and `beefy_verifier::verify_mmr_update_proof`.
- Make `pallet-beefy-consensus-proofs::submit_proof`'s weight scale with the decoded signature count (e.g., use a weight function of `len(signatures)` capped at `authoritySet.len`, similar to how `pallet-ismp` benchmarks per-message weights) rather than a single fixed benchmarked constant, so declared weight tracks actual cryptographic work.
- Reject proofs whose signature count is implausible relative to the known authority set size at decode time, before any recovery work begins.

### Proof of Concept
1. Obtain a valid BEEFY relay-chain proof for a given `blockNumber`/`validatorSetId` with a legitimate supermajority of signatures (e.g., 34 of 50 authorities).
2. Construct a modified `RelayChainProof`/`MmrProof` where the `votes`/`signatures` vector is expanded to include many additional entries — duplicates of a valid vote, or arbitrary garbage `(signature, authorityIndex)` pairs with indices spread across the full `authoritySet.len` range (`checkParticipationThreshold` only checks `sigLen >= threshold`, so padding above the honest count still passes).
3. Submit this proof:
   - On Substrate: `BeefyConsensusProofs::submit_proof(origin, proof)` where the SCALE-encoded `signatures` vector has, say, 10x–100x the honest count (still fitting within `MaxProofSize` bytes since each entry is small), paying the same fixed fee/weight as an honestly-sized proof.
   - On EVM: call the `ConsensusRouter`/`HandlerV2` entrypoint that dispatches to `EcdsaBeefy.verify` with the padded `RelayChainProof.signedCommitment.votes` array.
4. Observe that verification proceeds through the entire padded loop — `ECDSA.recover`/`secp256k1_recover` executed once per padded entry — consuming proportionally more gas/execution time than the fixed weight (Substrate) or than a normal-sized proof (EVM), before ultimately succeeding (if signatures still validate the merkle multi-proof) or failing late after the costly loop.

pub fn verify_mmr_update_proof<H: Keccak256 + EcdsaRecover + Send + Sync>(
	mut trusted_state: ConsensusState,
	mmr: MmrProof,
) -> Result<(ConsensusState, H256), Error> {
	let signatures_length = mmr.signed_commitment.signatures.len();
	let latest_height = mmr.signed_commitment.commitment.block_number;

	if trusted_state.latest_beefy_height >= latest_height {
		return Err(Error::StaleHeight {
			trusted_height: trusted_state.latest_beefy_height,
			current_height: latest_height,
		});
	}

	let commitment = mmr.signed_commitment.commitment.clone();

	// Pick the authority set the commitment claims to be signed under, then judge
	// participation against that set alone.
	let authority_set = if commitment.validator_set_id == trusted_state.current_authorities.id {
		&trusted_state.current_authorities
	} else if commitment.validator_set_id == trusted_state.next_authorities.id {
		&trusted_state.next_authorities
	} else {
		return Err(Error::UnknownAuthoritySet { id: commitment.validator_set_id });
	};

	if !check_participation_threshold(signatures_length as u32, authority_set.len) {
		return Err(Error::SuperMajorityRequired);
	}

	let mmr_root_data = commitment
		.payload
		.get_raw(&MMR_ROOT_PAYLOAD_ID)
		.ok_or(Error::MmrRootHashMissing)?;

	if mmr_root_data.len() != 32 {
		return Err(Error::InvalidMmrRootHashLength { len: mmr_root_data.len() });
	}
	let mmr_root = H256::from_slice(mmr_root_data);

	let commitment_hash = H::keccak256(&commitment.encode());
	let mut authority_leaves: Vec<[u8; 32]> = Vec::new();
	let mut authority_indices = Vec::new();

	for sig in mmr.signed_commitment.signatures.iter() {
		let uncompressed = H::secp256k1_recover(&commitment_hash.0, &sig.signature)
			.map_err(|_| Error::FailedToRecoverPublicKey)?;

		let hashed_uncompressed = H::keccak256(&uncompressed);

		let mut eth_address = [0u8; 20];
		eth_address.copy_from_slice(&hashed_uncompressed.as_ref()[12..]);

		let authority_address_hash = H::keccak256(&eth_address);

		authority_leaves.push(authority_address_hash.into());
		authority_indices.push(sig.index as usize);
	}
