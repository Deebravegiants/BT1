### Title
Unvalidated `shop` parameter in `Oauth.begin_auth` allows redirecting OAuth authorization requests (and the CSRF `state` nonce) to an attacker-controlled host, enabling forced OAuth completion - ([File: lib/shopify_api/auth/oauth.rb])

### Summary
`ShopifyAPI::Auth::Oauth.begin_auth` builds the authorization redirect URL directly from the caller-supplied `shop` string without validating that it is a trusted Shopify domain. Unlike `RefreshToken.refresh_access_token` and `TokenExchange.migrate_to_expiring_token`, which call `Utils::ShopValidator.sanitize!(shop)` before using `shop` to construct a request host, `begin_auth` (and `validate_auth_callback`'s downstream `auth_base_uri`) never does this check.

### Finding Description
`begin_auth` generates a CSRF-protection nonce (`state`), places it in a `SessionCookie` for the victim's browser, and then builds the authorization URL entirely from the untrusted `shop` argument: [1](#0-0) 

```
state = SecureRandom.alphanumeric(NONCE_LENGTH)
cookie = SessionCookie.new(value: state, expires: Time.now + 60)
query = { client_id: ..., scope: ..., redirect_uri: ..., state: state, ... }
auth_route = auth_base_uri(shop) + "/oauth/authorize?#{query_string}"
```

`auth_base_uri` interpolates `shop` directly into an HTTPS host with no allow-listing: [2](#0-1) 

This is inconsistent with the rest of the gem, which has a dedicated `Utils::ShopValidator.sanitize!` module specifically to reject non-Shopify hosts: [3](#0-2) [4](#0-3) 

`RefreshToken.refresh_access_token` and `TokenExchange.migrate_to_expiring_token` both call `sanitize!` before building a request host from `shop`: [5](#0-4) [6](#0-5) 

`begin_auth` has no equivalent check, even though its documented usage pattern takes `shop` straight from an unauthenticated request header: [7](#0-6) 

The equality this breaks: `host redirected to` should equal `a trusted Shopify domain`, but the gem never enforces `shop ∈ ShopValidator::TRUSTED_SHOPIFY_DOMAINS` before using it as the authorize host.

### Impact Explanation
Because `state` (the anti-CSRF nonce bound to the victim's session cookie) is embedded in the query string sent to whatever host `shop` resolves to, an attacker who controls the `shop` value can make the victim's browser leak `client_id`, `scope`, `redirect_uri`, and the CSRF `state` nonce to an attacker-controlled server (via the request itself, Referer header, or server logs). The attacker can then separately complete a legitimate Shopify installation for a shop they control, obtain a genuinely HMAC-signed callback query for that shop, and substitute in the leaked `state` value before sending the resulting callback URL to the victim (who still has the matching cookie). `validate_auth_callback` will accept it because the HMAC and state both validate: [8](#0-7) 

This forces the victim's browser/session to complete an OAuth installation flow for a shop of the attacker's choosing — a forced OAuth completion / session-fixation class issue, one of the defined High-impact categories.

### Likelihood Explanation
Requires the host application to pass an unauthenticated, user-supplied `shop` value into `begin_auth` (the exact pattern shown in the gem's own documentation), and requires the attacker to lure the victim into visiting a crafted login link — no `api_secret_key`, access token, or privileged access is needed.

### Recommendation
Validate `shop` with `Utils::ShopValidator.sanitize!` (or equivalent) inside `Oauth.begin_auth` before using it to build `auth_base_uri`, mirroring the checks already performed in `RefreshToken.refresh_access_token` and `TokenExchange.migrate_to_expiring_token`. Reject any `shop` value that is not a trusted Shopify domain before redirecting or leaking the `state` nonce.

### Proof of Concept
1. Host app exposes a login route that does `ShopifyAPI::Auth::Oauth.begin_auth(shop: params[:shop], redirect_path: "/auth/callback")` (as shown in the gem's own docs).
2. Attacker sends victim a link to that route with `shop=evil-attacker-server.com`.
3. `begin_auth` sets the `state` cookie on the victim's browser and returns `auth_route = "https://evil-attacker-server.com/admin/oauth/authorize?client_id=...&scope=...&redirect_uri=https://app.example.com/auth/callback&state=<NONCE>&grant_options[]=..."`.
4. The victim's browser is redirected to the attacker's server, which now knows `<NONCE>`, `client_id`, `scope`, and `redirect_uri`.
5. Attacker completes a real Shopify install on their own shop, obtaining a validly HMAC-signed `code`/`hmac`/`timestamp` for `shop=attacker-shop.myshopify.com`; they swap in the leaked `<NONCE>` as `state` and send the victim a link to `https://app.example.com/auth/callback?...&state=<NONCE>&shop=attacker-shop.myshopify.com&hmac=<valid>`.
6. Victim (still holding the `state` cookie) visits it; `validate_auth_callback` accepts it since HMAC and state both check out, completing an OAuth install for the attacker's shop under the victim's session context.

          return "https://#{shop}/admin" unless defined?(DevServer) && shop.include?(".my.shop.dev")

          "https://#{admin_host}/store/#{shop_name}"
        end

class ShopifyAuthController < ApplicationController
  def login
    shop = request.headers["Shop"]

    # Builds the authorization URL route to redirect the user to
    auth_response = ShopifyAPI::Auth::Oauth.begin_auth(shop: domain, redirect_path: "/auth/callback")

    # Store the authorization cookie
    cookies[auth_response[:cookie].name] = {
      expires: auth_response[:cookie].expires,
      secure: true,
      http_only: true,
      value: auth_response[:cookie].value
    }

    # Redirect the user to "auth_response[:auth_route]" to allow user to grant the app permission
    # This will lead the user to the Shopify Authorization page
    head 307
    response.set_header("Location", auth_response[:auth_route])
  end
end
