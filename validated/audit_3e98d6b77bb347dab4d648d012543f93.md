### Title
Fee-on-transfer tokens break escrow accounting in the Tron IntentGatewayV2, permanently under-collateralizing/over-crediting shared escrow - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron variant of `IntentGatewayV2.placeOrder` records escrow credit using the user-requested input amount (minus protocol fee), not the amount actually received by the contract after the ERC20 transfer. For fee-on-transfer (FOT) tokens this creates a permanent gap between the `_orders[commitment][token]` bookkeeping and the gateway's real token balance, corrupting the shared escrow pool used by all outstanding orders.

### Finding Description
In the non-predispatch escrow path of `evm/tron/contracts/apps/IntentGatewayV2.sol`: [1](#0-0) 
the contract calls `IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` and then credits escrow with `_orders[commitment][token] += reducedInputs[i].amount`, where `reducedInputs[i].amount` is derived purely from `order.inputs[i].amount` minus the protocol fee — computed *before* the transfer and never reconciled against the actual balance received: [2](#0-1) 

If the input token charges a transfer fee (deflationary/FOT token), the gateway contract actually receives `order.inputs[i].amount - transferFee`, but the escrow ledger `_orders[commitment][token]` is inflated by the un-reduced (pre-fee) amount. This happens on every `placeOrder` call using an FOT token, so the ledger total across all orders for that token progressively exceeds the contract's real token balance.

This is a direct regression compared to the parallel, actively-fixed implementation in `evm/src/apps/IntentGatewayV2.sol`, which explicitly snapshots balances before/after the transfer and mutates `order.inputs[i].amount` to the actual received amount before crediting escrow: [3](#0-2) 
The presence of dedicated `FeeOnTransferToken` fixtures and passing tests (`testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived`, `testPlaceOrder_FeeOnTransferToken_WithProtocolFee`) confirms the project is aware of and defends against this exact bug class on the mainline EVM contract: [4](#0-3) 
but the Tron fork at `evm/tron/contracts/apps/IntentGatewayV2.sol` was not updated with the same balance-reconciliation logic.

### Impact Explanation
Because `_orders[commitment][token]` is a shared per-token escrow ledger used to pay out `fillOrder` settlements and `cancelOrder` refunds for every order placed with that token, over-crediting one order's escrow entry means the contract's bookkeeping no longer matches its real balance. As additional orders using the same FOT token are placed and later filled/cancelled, the deficit compounds: earlier orders can drain real tokens that other users' orders are relying on for their own escrow refund/fill, resulting in some legitimate order redemptions failing (reverting due to insufficient balance) or, if payouts are processed in a way that lets a later actor claim first, an effective theft of other users' escrowed funds. This is a fund-freezing / fund-loss condition on the shared escrow pool, reachable by any unprivileged user who places an order with a fee-on-transfer input token.

### Likelihood Explanation
Likelihood is high whenever any deflationary/fee-on-transfer ERC20 is listed as a valid input token for the Tron IntentGatewayV2 deployment — the discrepancy is triggered unconditionally on every `placeOrder` call for such a token, with no admin or governance action required, purely as a side effect of a single user transaction.

### Recommendation
Mirror the fix already present in `evm/src/apps/IntentGatewayV2.sol`: snapshot the contract's token balance before calling `safeTransferFrom`, compute the actually-received amount as `balanceAfter - balanceBefore`, and use that reconciled amount (after subtracting protocol fee) when incrementing `_orders[commitment][token]` and when computing the commitment hash, in the non-predispatch branch of `evm/tron/contracts/apps/IntentGatewayV2.sol` (lines ~450-468). Alternatively, explicitly disallow fee-on-transfer tokens from being registered/used as order inputs on this deployment.

### Proof of Concept
1. Deploy `evm/tron/contracts/apps/IntentGatewayV2.sol` and a fee-on-transfer ERC20 (e.g., 1% fee) as in the existing `FeeOnTransferToken` test fixture used by `evm/tests/foundry/IntentGatewayV2SameChainTest.sol`.
2. User calls `placeOrder` with `inputs[0] = {token: FOT, amount: 1000e18}`, no protocol fee for simplicity.
3. `safeTransferFrom` moves 1000e18 requested, but the FOT contract only delivers 990e18 to the gateway (1% burned/fee).
4. `_orders[commitment][FOT] += reducedInputs[0].amount` credits 1000e18 (since `protocolFeeBps == 0`, `reducedInputs = order.inputs` unmodified), while `FOT.balanceOf(gateway) == 990e18`.
5. Repeat with more orders using the same FOT token; the sum of all `_orders[...][FOT]` entries exceeds `FOT.balanceOf(gateway)` by the accumulated transfer-fee shortfall.
6. When orders are filled or cancelled and the contract attempts to release the escrowed amount recorded in `_orders`, some later order's redemption will underflow/fail against actual balance, or an early claimant can drain balance intended for other users — demonstrating the fund-freezing/loss condition.

    /// @notice Escrow correctly reflects actual received amount for fee-on-transfer tokens.
    function testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived() public {
        // Deploy a 1% fee-on-transfer token
        FeeOnTransferToken fot = new FeeOnTransferToken(100); // 1% = 100 bps
        fot.mint(user, 10000 * 1e18);

        uint256 inputAmount = 1000 * 1e18;
        uint256 expectedReceived = inputAmount - (inputAmount * 100) / 10000; // 990

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(fot)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 900 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        vm.startPrank(user);
        fot.approve(address(intentGateway), inputAmount);
        intentGateway.placeOrder(order, bytes32(0));
        vm.stopPrank();

        // Gateway should hold only what it actually received
        assertEq(
            fot.balanceOf(address(intentGateway)), expectedReceived, "Gateway balance should match received amount"
        );

        // Reconstruct the order as placeOrder would have mutated it
        order.user = bytes32(uint256(uint160(user)));
        order.source = host.host();
        order.nonce = 0;
        order.inputs[0].amount = expectedReceived;
        bytes32 commitment = keccak256(abi.encode(order));

        // Escrow should match actual received, not the user-specified amount
        assertEq(
            intentGateway._orders(commitment, address(fot)),
            expectedReceived,
            "Escrow should equal actual received amount"
        );
    }
