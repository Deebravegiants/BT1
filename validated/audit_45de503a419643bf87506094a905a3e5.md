### Title
Escrow accounting in Tron `IntentGatewayV2` uses nominal transfer amount instead of actual balance increase, enabling fee-on-transfer token insolvency and fund freezing - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron fork of `IntentGatewayV2.placeOrder` escrows tokens based on the caller-specified `order.inputs[i].amount` (reduced only by the protocol fee), without verifying that this amount actually landed on the contract via `balanceOf` delta. This is the exact bug class described in the referenced report: the contract assumes `transferFrom` moves the exact amount requested, which is false for fee-on-transfer, rebasing, or otherwise non-standard ERC20 tokens.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol`, both branches of the token-escrow logic in `placeOrder` call `safeTransferFrom` and then credit `_orders[commitment][token]` using `reducedInputs[i].amount`, which is derived purely from the original `order.inputs[i].amount` minus the protocol fee — never checked against the actual contract balance increase: [1](#0-0) 

Contrast this with the primary EVM implementation in `evm/src/apps/IntentGatewayV2.sol`, which was explicitly hardened against this exact issue: it snapshots `balanceOf` before/after each `safeTransferFrom` and mutates `order.inputs[i].amount` to the *actual* received amount before computing the commitment and crediting escrow: [2](#0-1) 

The Tron contract also computes `reducedInputs`/the commitment purely from `order.inputs` (nominal, unadjusted) amounts: [3](#0-2) 

This means for any ERC20 with transfer-time deduction (fee-on-transfer, deflationary/rebasing, or a token with non-standard `transferFrom` semantics), the amount actually held by the `IntentGatewayV2` Tron contract will be strictly less than the sum it records in `_orders[commitment][token]`.

### Impact Explanation
Because `_orders[commitment][token]` is used later to authorize withdrawals (`RedeemEscrow`/`RefundEscrow` paths, filler payout, cancellation refunds), the escrow ledger becomes over-credited relative to actual contract balance. Once enough over-credited orders accumulate, later legitimate redemptions/refunds for *other, unrelated* orders will fail (revert due to insufficient token balance) or, depending on withdrawal ordering, the first withdrawer of an over-credited amount will drain balance belonging to other users' escrowed orders — a shared-pool insolvency that causes permanent freezing/loss of funds for other order owners. This is a fund-safety issue at Medium severity, matching the accepted severity of the original report.

### Likelihood Explanation
Any unprivileged user placing an order with a fee-on-transfer (or otherwise non-1:1 transferring) ERC20 as an input token can trigger the mismatch with a single `placeOrder` call — no privileged role or governance action needed. The contract explicitly supports arbitrary ERC20 `token` addresses in `order.inputs`, so this path is directly reachable by any depositor on the Tron deployment.

### Recommendation
Apply the same balance-snapshot pattern already used in `evm/src/apps/IntentGatewayV2.sol` to the Tron contract: record `balanceOf(address(this))` before each `safeTransferFrom`, compute the actual received delta afterward, and use that delta (not the nominal `order.inputs[i].amount`) both for the commitment hash computation and for crediting `_orders[commitment][token]`.

### Proof of Concept
1. Deploy the Tron `IntentGatewayV2` with a fee-on-transfer ERC20 (e.g., 1% fee) as an allowed input token, analogous to the `FeeOnTransferToken` test fixture already present in the repo's test suite: [4](#0-3) 
2. Call `placeOrder` with `order.inputs[0].amount = 1000e18` of the fee-on-transfer token; the contract only receives `990e18` due to the transfer fee.
3. Because the Tron contract does not adjust for actual received balance (unlike the fixed main EVM contract, verified in the test `testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived`), `_orders[commitment][token]` is credited with `990e18` reduced only by protocol fee off of the *nominal* 1000e18, i.e. an amount greater than what the contract actually holds.
4. Repeating this with multiple orders causes cumulative over-crediting; when solvers/users later attempt `RedeemEscrow`/`RefundEscrow` for legitimate orders, transfers revert or drain balance meant for other escrowed orders, freezing funds.

contract FeeOnTransferToken {
    string public name = "FeeOnTransferToken";
    string public symbol = "FOT";
    uint8 public decimals = 18;
    uint256 public totalSupply;
    uint256 public feeBps;

    mapping(address => uint256) public balanceOf;
    mapping(address => mapping(address => uint256)) public allowance;

    constructor(uint256 _feeBps) {
        feeBps = _feeBps;
    }

    function mint(address to, uint256 amount) external {
        balanceOf[to] += amount;
        totalSupply += amount;
    }

    function approve(address spender, uint256 amount) external returns (bool) {
        allowance[msg.sender][spender] = amount;
        return true;
    }

    function transfer(address to, uint256 amount) external returns (bool) {
        return _transfer(msg.sender, to, amount);
    }

    function transferFrom(address from, address to, uint256 amount) external returns (bool) {
        uint256 allowed = allowance[from][msg.sender];
        if (allowed != type(uint256).max) {
            allowance[from][msg.sender] = allowed - amount;
        }
        return _transfer(from, to, amount);
    }

    function _transfer(address from, address to, uint256 amount) internal returns (bool) {
        uint256 fee = (amount * feeBps) / 10_000;
        uint256 received = amount - fee;
        balanceOf[from] -= amount;
        balanceOf[to] += received;
