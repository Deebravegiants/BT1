Line 125 of `docs/usage/webhooks.md` explicitly states: "This will verify the request did indeed come from Shopify and then call the specified handler for that webhook" — meaning `ShopifyAPI::Webhooks::Registry.process` is documented as validating the sender's authenticity, and the `shop` field passed to the handler (`data.shop`) is presented as reliable, trusted webhook metadata. But the HMAC signature computed by `Utils::HmacValidator.validate` only signs `@raw_body` (`ShopifyAPI::Webhooks::Request#to_signable_string`), never the `x-shopify-shop-domain` header that becomes `WebhookMetadata#shop`.

### Title
Webhook shop-domain header is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [1](#0-0)  which `Utils::HmacValidator` uses as the sole signed payload when validating a webhook [2](#0-1) . The `shop` accessor, however, is read directly from the unauthenticated `x-shopify-shop-domain`/`shopify-shop-domain` header [3](#0-2)  and is passed straight through to the app's webhook handler as `WebhookMetadata#shop` once the HMAC check "passes" [4](#0-3) . The gem's own documentation tells developers that `Registry.process` "will verify the request did indeed come from Shopify" before invoking their handler with `data.shop` [5](#0-4) , implying the shop identity delivered to the handler is authenticated — it is not.

### Finding Description
The binding that should hold is: `bytes verified by HMAC == bytes the app trusts to identify the tenant`. Here that equality is broken: the HMAC is computed over `@raw_body` only, while the `shop` value the handler receives and typically uses as a partition/tenant key comes from a header that is completely outside the signed content.

Because the webhook secret (`api_secret_key`) is the app's single shared secret across every shop that installs the app — not a per-shop secret — any merchant who has legitimately installed the app can capture one of their own genuinely-signed webhook deliveries (raw body + valid `hmac-sha256` header) from Shopify. They can then replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with an arbitrary victim shop's domain. `Utils::HmacValidator.validate` still succeeds, because the substituted header was never part of the signed content, and `Registry.process` proceeds to invoke the handler with `WebhookMetadata.new(shop: request.shop, ...)` reporting the victim's shop.

### Impact Explanation
If a host application uses `data.shop` from the webhook to select which merchant/tenant record to create, update, or delete (a very common and gem-documented pattern, see `docs/usage/webhooks.md` example calling `perform_later(shop_domain: data.shop, ...)`), an attacker-controlled body can be injected and misattributed to a shop the attacker does not own or have any access to — a cross-tenant data integrity/confusion issue. This satisfies the "cross-tenant access" Critical impact category, since the confidentiality/integrity boundary between tenants is enforced only by this unauthenticated header.

### Likelihood Explanation
Any unprivileged actor who can install the target app on their own store (a normal, unprivileged action for any Shopify merchant) automatically receives legitimately HMAC-signed webhook payloads for their own shop and can immediately replay them against the shared webhook endpoint with a forged `shop-domain` header — no access token, `client_secret`, or privileged account is required.

### Recommendation
Include an authenticated shop identifier in the HMAC-signed payload (or bind the `shop-domain` header value into `to_signable_string`), or require host applications to cross-check `request.shop` against the shop stored for the webhook's registered access token/session before trusting it. At minimum, the gem should not present `shop` as a verified field on par with the HMAC-checked body.

### Proof of Concept
```ruby
# Attacker (real merchant on their own shop "attacker.myshopify.com") receives
# a legitimate, correctly-signed webhook from Shopify:
raw_body     = '{"id":1,"note":"hello"}'
valid_hmac   = "<hmac-sha256 header value Shopify actually sent for the body above>"

# Attacker replays the exact same body + hmac to the victim app's webhook
# endpoint, only changing the shop-domain header:
forged_headers = {
  "x-shopify-topic"       => "orders/create",
  "x-shopify-hmac-sha256" => valid_hmac,          # unchanged, still valid
  "x-shopify-shop-domain" => "victim-shop.myshopify.com" # forged
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => Utils::HmacValidator.validate(request) returns true (HMAC only covers raw_body)
# => handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: ..., ...))

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
