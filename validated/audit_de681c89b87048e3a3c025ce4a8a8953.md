## Analog Found: CEI Violation in Tron `IntentGatewayV2.withdraw()`

### Title
Checks-Effects-Interactions violation in `withdraw()` allows reentrant escrow draining before accounting update — ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Curve/Vyper incident's root cause was a mismatch between the security invariant enforced in the intended code path (the reentrancy lock) and what was actually deployed, letting an attacker re-enter mid-function while stale accounting state was still live. Hyperbridge has the exact same *class* of bug: the canonical, currently-audited EVM `IntentGatewayV2`/`IntentsBase` escrow-release path was hardened with a checks-effects-interactions (CEI) fix, but the parallel Tron port of the same contract (`evm/tron/contracts/apps/IntentGatewayV2.sol`) still contains the pre-fix ordering — external token transfer executes *before* the escrow balance is decremented, inside a loop over every token in a withdrawal.

### Finding Description
In the canonical (fixed) implementation, `IntentsBase._withdraw` decrements the escrow mapping before making the external transfer: [1](#0-0) 

By contrast, the Tron variant's `withdraw()` performs the external `.call` (native ETH transfer or raw `IERC20.transfer` low-level call) first, and only decrements `_orders[body.commitment][token]` afterward, inside the same per-token loop: [2](#0-1) 

`withdraw` is reached from `onAccept` (for `RedeemEscrow`/`RefundEscrow` settlement messages delivered via Hyperbridge) and from `onGetResponse` (for source-chain cancel refunds): [3](#0-2) [4](#0-3) 

Both entry points are `onlyHost`-gated, but the host itself (`EvmHost.dispatchIncoming`) marks the request/response receipt before invoking the app, so a strict message-replay reentrancy is not possible at the host layer: [5](#0-4) 

The exploitable surface is *within a single `withdraw()` call* that carries multiple `body.tokens` entries (e.g. native ETH plus one or more ERC-20s escrowed for the same order). For the native-ETH leg, `beneficiary.call{value: amount}("")` hands control to an attacker-controlled beneficiary contract *before* `_orders[body.commitment][address(0)] -= amount` executes. For the ERC-20 leg, the raw low-level `.call` to a malicious/hookable token (e.g. an ERC-777-style token or any token whose `transfer` invokes a callback) similarly hands control back to attacker code before that token's balance is decremented. While `_filled[body.commitment]` is set at the very top of `withdraw` (blocking a direct re-entry into `fillOrder`/`cancelOrder` for the *same* commitment), the per-token escrow ledger `_orders[commitment][token]` for tokens later in the array remains at its pre-withdrawal value during the reentrant window, and nothing prevents a reentrant call into other externally reachable, unrelated gateway functions (e.g. `placeOrder`, or reads of `_orders`) from observing or acting on that stale state while the withdrawal loop is still unwound on the stack — the same "guard is set, but book-keeping lags behind an external call" pattern that let Curve's LP-price manipulation happen between `add_liquidity` and `remove_liquidity`.

This is the exact bug class the original `IntrinsicIntentsReentrancyTest.sol` regression suite was written to close on the canonical EVM contract: [6](#0-5) 

but that fix was never carried over to the Tron deployment of the same contract, leaving a chain with a real, unprivileged, reachable reentrancy window in escrow settlement.

### Impact Explanation
`withdraw()` moves escrowed user/solver funds — native ETH and arbitrary ERC-20 inputs placed via `placeOrder`. A malicious beneficiary/token controlling the callback during the mid-loop external transfer can act while `_orders[commitment][token]` for not-yet-processed tokens in the same withdrawal is still un-decremented, and while other gateway state (unrelated commitments, dust balances) is fully mutable. This directly risks permanent loss of escrowed user/solver funds on the Tron deployment — a Critical-severity, concrete-theft outcome matching the report's bug class (state inconsistency enabling manipulation across a security boundary that was supposed to be closed).

### Likelihood Explanation
Reachable by any unprivileged party: a user can place an order (`placeOrder`) using a malicious hookable ERC-20 as an input token, or set a malicious contract as `order.user`/beneficiary for the native-ETH leg of a refund/redeem. No admin, governance, or relayer collusion is required — only a standard cross-chain settlement message delivery, which any relayer can trigger permissionlessly per the ISMP design. The likelihood is tempered only by needing a multi-token order (ETH + token, or a hookable token) to create the exploitable window, but this is trivial for an attacker to construct themselves as the order placer.

### Recommendation
Port the CEI fix from `IntentsBase._withdraw` (decrement `_orders[commitment][token]` before making the external transfer, for every token in the loop) into `evm/tron/contracts/apps/IntentGatewayV2.sol`'s `withdraw()`, and add the equivalent of `IntrinsicIntentsReentrancyTest.sol`'s regression coverage to the Tron test suite to prevent future divergence between the two implementations.

### Proof of Concept
1. Attacker calls `placeOrder` on the source chain with `order.inputs = [ {token: ETH, amount: X}, {token: maliciousHookToken, amount: Y} ]`, setting `order.user` (refund beneficiary) to an attacker-controlled contract.
2. Attacker (or anyone) later triggers a cancellation/refund path so that `withdraw(body, isRefund=true)` is invoked with `body.tokens = [ETH, maliciousHookToken]`.
3. In the loop at [7](#0-6) , the ETH leg's `beneficiary.call{value: X}("")` hands control to the attacker contract before `_orders[commitment][ETH] -= X` and before `_orders[commitment][maliciousHookToken] -= Y` execute.
4. The attacker's fallback observes `_orders(commitment, maliciousHookToken)` still equal to `Y` (unspent) and interacts with other gateway state/functions during this window, before the outer call finishes decrementing and finalizing — breaking the invariant that escrow accounting is atomic with fund movement.
