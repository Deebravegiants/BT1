### Title
Solver's Simplex `FXFiller` prices curveless pairs from live, manipulable Uniswap V4 spot price with no TWAP — analogous to the Deus Finance flash-loan oracle manipulation - ([File: sdk/packages/simplex/src/funding/uniswapV4/UniswapV4FundingPlanner.ts])

### Summary
Deus Finance was drained after an attacker used a flash loan to manipulate the spot price read from a single AMM pair (`StableV1 AMM-USDC/DEI`) and then exploited a protocol function that trusted that spot price as its oracle to borrow/drain funds. Hyperbridge's Simplex solver (`FXFiller`) contains the same bug class: for "curveless" trading pairs it prices the exotic token directly off a single Uniswap V4 pool's current `sqrtPriceX96` tick, with no TWAP and an *optional* deviation guard that many pairs can be run without.

### Finding Description
When a `TradingPair` has no `bidPriceCurve`/`askPriceCurve` configured, `FXFiller` falls back to venue pricing sourced from a live Uniswap V4 pool: [1](#0-0) 

`computeDirectPoolPriceUsd` derives the USD price purely from the pool's `token0Price`/`token1Price`, which are computed from the pool's instantaneous `sqrtPriceX96` — a single-block spot price with no time-weighting: [2](#0-1) [3](#0-2) 

This spot price flows straight into order sizing/pricing in `FXFiller.referenceRate` and `sizeOrder`, gated only by an *optional* `checkPriceGuard`: [4](#0-3) 

The guard itself is opt-in per position — the docs state explicitly that omitting `referencePrice`/`maxDeviationBps` "leaves the chain unguarded", and even when configured it only bounds deviation from a static reference, not execution/manipulation cost: [5](#0-4) [6](#0-5) 

The docs themselves acknowledge the risk in the same terms as the Deus Finance bug class: "Pool-based pricing trusts the live pool, which leaves the solver exposed to a manipulated, stale, or thin pool returning a bad quote."

### Impact Explanation
Any unprivileged user can submit a Hyperbridge intent order that gets matched against a venue-priced (curveless) `TradingPair`. An attacker can, within a single transaction bundle, swap heavily against the underlying Uniswap V4 pool to move `sqrtPriceX96`, then have their (or a colluding) intent filled by the solver at the resulting skewed spot price before arbitrageurs correct it — draining solver-held inventory/funding-venue liquidity at an off-market rate. This mirrors Deus Finance exactly: a flash-loan-movable AMM spot price is read directly as an oracle and used to size a value transfer (there: borrowing against manipulated collateral value; here: filling a bridged/intents order at a manipulated FX rate), causing direct loss of solver funds. This is explicitly flagged as in-scope: SECURITY.md states "Note: This does not exclude oracle manipulation/flash-loan attacks."

### Likelihood Explanation
- Reachable from a single, unprivileged intent order — no governance, admin, or relayer privilege required.
- The guard defense (`checkPriceGuard`) is optional per pool position; pairs configured without `referencePrice`/`maxDeviationBps` are fully unguarded.
- Even guarded pairs only reject on absolute deviation from a static reference, not on manipulation cost/liquidity depth, and provide no protection against a manipulator who stays within `maxDeviationBps` while still moving price enough to profit given typical solver spreads.
- The underlying data source (`sqrtPriceX96` via `getSlot0`) is a single-block spot read, structurally identical to the "read AMM reserves for spot price" pattern exploited in Deus Finance.

### Recommendation
- Require `referencePrice`/`maxDeviationBps` guard to be mandatory (not optional) for any venue-priced pair, or refuse pair activation without it.
- Replace or supplement spot `sqrtPriceX96` pricing with a TWAP (time-weighted average) read from the pool's oracle observations, raising the cost of manipulation to span multiple blocks.
- Bound order size against available on-pool liquidity/depth (price-impact-aware pricing) rather than treating the mid as flat across the whole notional, since `computeLegPolicyOutput` currently extends the mid linearly with no size/impact term.

### Proof of Concept
1. Attacker identifies a Simplex `FXFiller` pair configured under `[vault.uniswapV4]` without `referencePrice`/`maxDeviationBps` (per docs, this is a valid/expected configuration — "omit both to leave the chain unguarded").
2. Attacker takes a large swap in the underlying Uniswap V4 pool (optionally flash-loan funded) to move `sqrtPriceX96` sharply in the direction favorable to them.
3. In the same block/bundle, attacker (or an accomplice) submits/has filled a Hyperbridge intent order against that pair; `FXFiller.referenceRate` → `venueUsdPrice` → `UniswapV4FundingPlanner.getExoticTokenPrice` → `computeDirectPoolPriceUsd` reads the manipulated `sqrtPriceX96` and prices the fill accordingly, since `checkPriceGuard` has no reference to compare against.
4. Solver fills the order at the manipulated rate, transferring inventory at an off-market price; attacker reverses the pool swap, netting the difference as risk-free profit at the solver's expense.

```typescript
	/**
	 * Computes the USD price of the non-stable token in a pool.
	 * Returns null if neither currency is USDC/USDT on this chain.
	 */
	private computeDirectPoolPriceUsd(
		pos: HydratedV4Position,
		sdkPool: V4Pool,
		chain: string,
	): { exoticToken: string; priceUsd: Decimal } | null {
		const usdc = this.configService.getUsdcAsset(chain).toLowerCase()
		const usdt = this.configService.getUsdtAsset(chain).toLowerCase()
		const c0 = pos.currency0.toLowerCase()
		const c1 = pos.currency1.toLowerCase()

		if (c0 === usdc || c0 === usdt) {
			// currency0 is stable → exotic is currency1
			// token1Price = "token0 per token1" = USD per exotic
			return {
				exoticToken: c1,
				priceUsd: new Decimal(sdkPool.token1Price.toFixed(18)),
			}
		}

		if (c1 === usdc || c1 === usdt) {
			// currency1 is stable → exotic is currency0
			// token0Price = "token1 per token0" = USD per exotic
			return {
				exoticToken: c0,
				priceUsd: new Decimal(sdkPool.token0Price.toFixed(18)),
			}
		}

		return null
	}
```

```typescript
	private async referenceRate(
		leg: ResolvedLeg,
		venueUsdPrice: (chain: string, token1Address: string) => Promise<Decimal | null>,
	): Promise<Decimal | null> {
		const policy = leg.pair.bidPricePolicy ?? leg.pair.askPricePolicy
		if (policy) {
			const rate = policy.getPrice(new Decimal(0))
			return rate.gt(0) ? rate : null
		}
		// Venue-priced pair: token0 is USD-stable (constructor invariant), so the
		// venue's USD-per-token1 quote inverts straight into token1-per-token0.
		const venueUsd = await venueUsdPrice(leg.token1Chain, leg.token1Address)
		if (!venueUsd) return null
		const venueRate = new Decimal(1).div(venueUsd)
		// Same guard as trade pricing: this rate sizes the order's USD notional
		// for confirmation depth, and a manipulated pool understating the value
		// would shrink the reorg protection — the exact attack the guard exists
		// to stop. Refusing to size skips the order, consistent with pricing.
		if (!this.checkPriceGuard(undefined, leg.token1Chain, venueRate)) return null
		return venueRate
	}
```

```text
## Uniswap price guards

Pool-based pricing trusts the live pool, which leaves the solver exposed to a manipulated, stale, or thin pool returning a bad quote. To bound that risk, give a position a **`referencePrice`** and **`maxDeviationBps`**. Whenever the pool quote on that chain drifts more than `maxDeviationBps` above or below the reference, the solver refuses to fill — the order is rejected before any bid is submitted.

`referencePrice` is expressed in **exotic tokens per USD**, the same units as the bid/ask curves. The two fields must be set together; omit both to leave the chain unguarded.
```
