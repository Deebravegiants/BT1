### Title
Signup marked successful without backend enrollment confirmation for user-centric signups - (File: src/plans/mod.rs)

### Summary
In the `do_signup` flow, when a signup is `user_centric_signup` (app-centric), the orb never calls the backend enrollment/verification step (`enroll_user::Plan::run`, which performs `signup_post::request` + `signup_poll::request` against the backend). Instead it locally infers success purely from the *local* `signup_reason` value, without any backend confirmation that the identity commitment was actually bound and accepted server-side.

### Finding Description
For legacy (non-user-centric) signups, `do_signup` calls `self.enroll_user(...)`, which posts the biometric signature and QR data to the backend and polls for a confirmed completion status before deciding success/failure [1](#0-0) , mirroring the real backend `signup_post`/`signup_poll` round trip [2](#0-1) .

For `user_centric_signup == true`, this backend round trip is skipped entirely. Success is instead derived only from the locally-computed `signup_reason`: [3](#0-2) 

`signup_reason` is itself computed purely from local pipeline/fraud results before this branch [4](#0-3) . Crucially, by the time this branch is reached, the personal custody package (biometric data) tiers have already been uploaded to the backend unconditionally [5](#0-4) .

This is structurally analogous to the referenced DODO bug: one side of a two-sided operation (data/"collateral" upload to the backend) is performed and trusted, while the other side (server-side confirmation/"debt" verification that the enrollment was actually accepted, software version allowed, and identity properly bound) is never checked for this signup path. The local process declares "success" based on its own unverified belief instead of an authoritative backend acknowledgment, exactly like the DODO liquidation code assuming a transfer succeeded without checking its actual return status.

### Impact Explanation
If the backend would have rejected the enrollment (e.g., due to unknown/deprecated software version, signup verification failure, or a race/duplicate signup) — checks that `enroll_user::Plan::run` explicitly performs via `signup_post`/`signup_poll` [6](#0-5)  — the user-centric path has no equivalent check. The orb can report a successful signup and identity binding to the operator/UI while the backend never actually confirmed acceptance of that identity commitment. This produces a state mismatch between the orb’s belief and backend truth, which can result in a misattributed or effectively unauthorized "successful" signup being surfaced to the user, while biometric data has already been uploaded under that signup id.

### Likelihood Explanation
This path is taken for every user-centric (app-centric) signup by design (`user_centric_signup && !ignore_user_centric_signups`), so it is not a rare edge case — it is the standard flow for that signup type, making the missing verification systematically reachable rather than a corner case.

### Recommendation
For `user_centric_signup` signups, perform an equivalent backend confirmation step (or explicitly document/verify that success is guaranteed by an earlier, already-checked call) before declaring `success = signup_reason == SignupReason::Normal`. At minimum, do not treat local-only `signup_reason` as sufficient proof of backend-side identity binding; require a backend acknowledgment analogous to `signup_poll::request` before finalizing enrollment status.

### Proof of Concept
1. Trigger a signup with `user_centric_signup == true` in the QR/app data.
2. Ensure the local biometric pipeline succeeds and no local fraud check fires (`signup_reason == SignupReason::Normal`).
3. Observe that `do_signup` uploads PCP tiers to the backend and then sets `success = true` at line 645 without ever calling `enroll_user`/`signup_post`/`signup_poll`, i.e., without any backend confirmation of the enrollment, unlike the legacy branch.
