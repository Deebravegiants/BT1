### Title
Truncating ERC20→local decimal conversion in `pallet-hyper-fungible-token::on_accept`/`on_timeout` permanently destroys dust on every cross-chain transfer whose amount isn't a multiple of the decimal scale factor - ([File: modules/pallets/hyper-fungible-token/src/module.rs])

### Summary
`pallet-hyper-fungible-token` bridges EVM `HyperFungibleToken`/`WrappedHyperFungibleToken` contracts with a Substrate chain. Any user can call `send()` on the EVM side to burn (or lock) an exact ERC20 `amount` (typically 18 decimals) and dispatch a cross-chain message. On the receiving Substrate side, `on_accept` (and the refund path `on_timeout`) converts that amount down to the local asset's decimals via `convert_to_balance`, which performs plain integer division and truncates any remainder. Because the EVM side already burned/locked the *full* amount before the message was ever sent, any remainder lost to truncation on the Substrate side is permanently destroyed — nobody is credited with it, and it is not tracked anywhere (unlike `IntentGatewayV2`'s `DustCollected` mechanism used elsewhere in this codebase for the exact same class of issue).

### Finding Description
`convert_to_balance` in [1](#0-0)  divides the incoming ERC20 `U256` value by `10^(erc_decimals - local_decimals)` and parses the result — a floor division that discards any remainder below the scale factor.

This is invoked in `on_accept`, the ISMP delivery handler for incoming transfers: [2](#0-1) 

The same truncating conversion is repeated in the timeout/refund path, `on_timeout`: [3](#0-2) 

On the EVM source side, `HyperFungibleToken.send()` burns the caller's *exact* `params.amount` before dispatching the message — there is no rounding or scaling applied there: [4](#0-3) 

So, for any registered token pair where `erc_decimals > local_decimals` (which is the common case — EVM tokens are usually 18 decimals while Substrate assets, e.g. BRIDGE at 12 decimals, are lower precision, as enforced by `register_token`'s `ErcDecimalsBelowLocal` check requiring `config.decimals >= local_decimals`, see [5](#0-4) ), a user who sends an amount not evenly divisible by the scale factor `10^(erc_decimals-local_decimals)` will:
1. Have the full ERC20 amount burned/locked on the EVM chain (verified exact, e.g. `testSendBurnsTokens` in `evm/tests/foundry/HyperFungibleTokenTest.sol`).
2. Receive only `floor(amount / scale)` credited on the Substrate chain via `mint_into` (non-native asset) or `NativeCurrency::transfer`/`Assets::transfer` from the pallet's escrow account (native asset).

The truncated remainder is:
- For **non-native (mint/burn) assets**: never minted anywhere — a straightforward, permanent, unbacked loss of user value.
- For **native (escrow) assets**: left stuck in `Pallet::<T>::pallet_account()`'s escrow balance forever, since no code path releases un-transferred escrow dust back to the user or anyone else — a permanent freeze of funds.

This is structurally identical to the audited Gumball.sol bug: the full amount is taken from the user up front, but the quantity credited on the other side is computed via truncating division, silently losing the remainder with no refund mechanism.

### Impact Explanation
Every single cross-chain transfer through this pallet whose ERC20 amount is not a multiple of the registered decimal scale factor loses funds permanently — either destroyed outright (non-native assets) or made permanently unclaimable within the pallet's escrow account (native assets, including the protocol's own `BRIDGE` token, which is 18 decimals on EVM vs 12 decimals on nexus, giving a 10^6 scale factor). This is systemic: it triggers on ordinary user activity, not just adversarial input, and there is no dust accounting, sweep mechanism, or refund path anywhere in this pallet for the discarded remainder (contrast with `IntentGatewayV2`'s explicit `DustCollected` event pattern used for the same class of rounding issue elsewhere in this codebase).

### Likelihood Explanation
Extremely high. Any unprivileged user calling `send()` on an `HyperFungibleToken`/`WrappedHyperFungibleToken` deployment, or the pallet's own `send()` extrinsic in the Substrate→EVM direction is unaffected (since `convert_to_erc20` there multiplies, which is lossless — the finding is specific to EVM→Substrate direction and the `on_timeout` refund path), simply by picking an amount not aligned to the decimal scale factor (which for 18→12 decimals means any of the low 6 decimal digits being nonzero) triggers this loss with no special conditions required.

### Recommendation
Apply the same pattern already used in `IntentGatewayV2`/`IntrinsicIntents.sol` for handling rounding dust: either (a) reject/round the incoming amount to the nearest representable local value and refund/track the truncated remainder explicitly (e.g., emit a `DustCollected`-style event and accumulate it in a claimable/sweepable account), or (b) require `send()` callers to only submit amounts that are exact multiples of the decimal scale factor and revert otherwise, or (c) have the EVM-side `send()` truncate to the equivalent-local-precision amount *before* burning, and only debit the caller for the amount that will actually be credited on the destination chain — mirroring the Gumball fix's recommendation of "take only the amount necessary."

### Proof of Concept
1. Register `BRIDGE`-like token pair with `erc_decimals = 18` and `local_decimals = 12` (scale factor `10^6`), per `register_token`'s configuration in [6](#0-5) .
2. On the EVM chain, a user calls `HyperFungibleToken.send({ amount: 1_000_000_000_000_000_001 wei, ... })` (1 token + 1 wei, not a multiple of `10^6`). The contract burns exactly `1_000_000_000_000_000_001` wei, per [7](#0-6) .
3. The message is delivered and `on_accept` computes `amount = convert_to_balance(1_000_000_000_000_000_001, 18, 12)` = `1_000_000_000_000_000_001 / 10^6` = `1_000_000_000_000` (floor), discarding the trailing `1` wei-equivalent unit — per [8](#0-7)  and [1](#0-0) .
4. The beneficiary is credited `1_000_000_000_000` (local units), corresponding to exactly `1_000_000_000_000_000_000` wei worth of value — one wei's worth of pre-scale precision (which represents `10^6` erc-decimal wei once rescaled back) is permanently lost with no event, refund, or accounting anywhere in the pallet.

pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,

	dec_str.parse::<B>()

		#[pallet::call_index(1)]
		#[pallet::weight(T::WeightInfo::register_token(registration.chains.len() as u32))]
		pub fn register_token(
			origin: OriginFor<T>,
			registration: TokenRegistration<AssetId<T>>,
		) -> DispatchResult {
			T::CreateOrigin::ensure_origin(origin)?;

			let local_decimals = if registration.local_id == T::NativeAssetId::get() {
				T::Decimals::get()
			} else {
				<T::Assets as fungibles::metadata::Inspect<T::AccountId>>::decimals(
					registration.local_id.clone(),
				)
			};

			NativeAssets::<T>::insert(registration.local_id.clone(), registration.native);

			let chains: Vec<StateMachine> = registration.chains.keys().cloned().collect();
			for (chain, config) in registration.chains {
				// This pallet bridges substrate <-> EVM only; reject non-EVM peers.
				if !matches!(chain, StateMachine::Evm(_)) {
					return Err(Error::<T>::NonEvmPeerChain.into());
				}
				ensure!(
					config.decimals >= local_decimals,
					Error::<T>::ErcDecimalsBelowLocal
				);
				let token_contract = config.token_contract.0.to_vec();
				TokenContracts::<T>::insert(
					chain,
					registration.local_id.clone(),
					token_contract.clone(),
				);
				ContractToAsset::<T>::insert(
					chain,
					token_contract,
					registration.local_id.clone(),
				);
				Precisions::<T>::insert(registration.local_id.clone(), chain, config.decimals);
			}

			Self::deposit_event(Event::<T>::TokenRegistered {
				asset_id: registration.local_id,
				native: registration.native,
				chains,
			});
			Ok(())
		}
