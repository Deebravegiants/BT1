Confirmed the finding: `Registry.process` validates `Utils::HmacValidator.validate(request)`, whose `Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, uncovered by that signature [2](#0-1) . `Registry.process` then forwards that unauthenticated `request.shop` value as the tenant identifier to the app's handler [3](#0-2) , and the docs/breaking-changes guide explicitly instruct integrators to key their per-tenant logic (`shop_domain: data.shop`) off this field [4](#0-3) .

### Title
Webhook `shop` field is validated by an HMAC that only covers the body, not the shop domain, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook as authentic for a given `shop` as long as `Utils::HmacValidator.validate(request)` passes. That validator recomputes the HMAC over `request.to_signable_string`, which is defined as the raw body only [1](#0-0) . The `shop` value handed to the application's handler, however, comes from the `shopify-shop-domain` header, which is never part of the signed material [2](#0-1) [5](#0-4) . Since a single Shopify app shares one `api_secret_key` across every installing shop, any legitimately-signed webhook body an attacker can obtain for their own installed shop (e.g. from a store they control) remains validly signed even if the `shop-domain` header is swapped to a victim shop's domain, because the header is outside the HMAC's coverage.

### Finding Description
This is the same identity-binding class as the report's root cause: a field ("shop"/tenant identity) is *acted on* by the callback logic but not *covered* by the authenticity check that gates that logic — exactly analogous to `Spoke.requestCallback()` trusting `requestManager[poolId]` without checking it matches the manager that created the request.

Concretely:
- `HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the received HMAC [5](#0-4) .
- For webhooks, `to_signable_string` is `@raw_body` only [1](#0-0) .
- `shop` is read from a header that is not part of `@raw_body` [2](#0-1) .
- `Registry.process` accepts the request purely based on the body HMAC, then constructs `WebhookMetadata` using `request.shop` and dispatches it to the app's handler [3](#0-2) .

Equality that should hold but doesn't: `hmac_signed_bytes ⊇ {shop, body}` — instead `hmac_signed_bytes = {body}` only, while the trust decision downstream is keyed on `shop`.

Attack path (no `api_secret_key`, no access token, no TLS interception required):
1. Attacker installs the target app on their own Shopify development/free store (a store *they* control), a normal, permitted action.
2. Shopify's platform delivers a legitimately-signed webhook (e.g. `app/uninstalled` or any subscribed topic) to the app's public webhook endpoint, with a body `B` and a valid HMAC `H = HMAC(secret, B)` in the `x-shopify-hmac-sha256` header, and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker captures this request (it's their own network traffic to a public endpoint — no interception of anyone else's traffic needed).
4. Attacker resends the same body `B` and same HMAC `H` to the app's public webhook endpoint, but with `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `HmacValidator.validate` recomputes `HMAC(secret, B)`, matches `H`, and returns `true` — the header substitution is invisible to the check, since only `B` is signed.
6. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: B, ...))`, and the app's handler — which per the gem's own documented usage pattern keys tenant-scoped work off `data.shop` — now applies attacker-supplied webhook data as if it originated from the victim shop.

### Impact Explanation
This is a cross-tenant integrity/data-confusion vector: an attacker with no privileged credentials can cause an app built on this gem to process arbitrary webhook bodies (of topics they can generate for their own store) under a victim shop's identity, because the gem's own request-shop accessor is not bound by the same authenticity check gating the callback. Depending on the app's handler logic (documented pattern: enqueue jobs keyed by `data.shop`), this can lead to cross-tenant data being written/attributed to the wrong shop, spurious state changes for a victim tenant, or triggering shop-scoped side effects (e.g. app/uninstalled cleanup, order processing) against a shop the attacker doesn't own — meeting the "cross-tenant access" bar without requiring the app's `client_secret`, an access token, or TLS interception.

### Likelihood Explanation
Moderate-to-high: the attacker only needs their own (attacker-owned) installation of the target app to obtain a validly HMAC'd webhook body/signature pair, then a single unauthenticated POST to the app's public webhook endpoint with a substituted header — no secret material, tokens, or MITM position required. The gem provides no header-shop binding whatsoever in `to_signable_string`, so the substitution is trivial and deterministic once one legitimate webhook has been observed.

### Recommendation
Bind the tenant/shop identity into the authenticity check rather than trusting an unsigned header:
- Include `shop` (and ideally `topic`/`webhook_id`) in `Webhooks::Request#to_signable_string`'s coverage, or otherwise cross-verify the header-derived `shop` against a value embedded in (or derivable only from) the signed body/registration state before dispatching to the handler.
- At minimum, document prominently that `data.shop` is unauthenticated header data, and require app developers to independently confirm the `shop` header corresponds to a shop with an active recorded installation/session before trusting it for tenant-scoped writes.
- Consider validating that the `shop-domain` header matches an expected trusted shop domain format via `Utils::ShopValidator` and cross-checking it against stored webhook registrations/sessions rather than treating raw header content as ground truth.

### Proof of Concept
```ruby
require "openssl"
require_relative "lib/shopify_api"

ShopifyAPI::Context.setup(
  api_key: "test-key",
  api_secret_key: "shared-app-secret",
  host_name: "app.example.com",
  is_embedded: true,
)

body = '{"id":1,"note":"hello"}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), "shared-app-secret", body)
hmac_b64 = Base64.encode64(hmac)

# Step 1: attacker captures this from their OWN store's webhook delivery
legit_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => hmac_b64,
  "x-shopify-shop-domain" => "attacker-shop.myshopify.com",
  "x-shopify-webhook-id" => "abc",
  "x-shopify-api-version" => "2024-01",
}

# Step 2: attacker resends identical body+hmac, but swaps only the shop header
forged_headers = legit_headers.merge("x-shopify-shop-domain" => "victim-shop.myshopify.com")

request = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: forged_headers)

# This passes validation, because HMAC only covers `body`, not the shop header:
puts ShopifyAPI::Utils::HmacValidator.validate(request) # => true

# Registry.process would now dispatch to the handler with shop == "victim-shop.myshopify.com"
```
