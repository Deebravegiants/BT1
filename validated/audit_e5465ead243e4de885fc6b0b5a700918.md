### Title
Webhook `shop` (and `topic`/`webhook_id`) header is trusted for identity binding but is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop`, `topic`, `webhook_id`, and `api_version` values used to dispatch a webhook purely from unauthenticated HTTP headers, while the HMAC signature that `Utils::HmacValidator` verifies is computed only over the raw request body. This breaks the identity binding `hmac_signed_bytes == bytes_that_determine_identity`: the signature proves the body wasn't tampered with, but it proves nothing about which shop the request claims to be from.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`, and `HmacValidator.validate` computes/compares the HMAC exclusively over that string: [1](#0-0) [2](#0-1) 

Meanwhile, `shop`, `topic`, `webhook_id`, and `api_version` are read straight from HTTP headers (`shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`, `shopify-api-version`) with no cryptographic binding to the signed body: [3](#0-2) 

`Registry.process` validates only the HMAC of the body, then forwards `request.shop` (and `request.topic`, `request.webhook_id`) straight to the app's handler as trusted identity metadata: [4](#0-3) 

Because the `shop-domain` header sits outside the signed content, an attacker who has ever received one legitimate webhook delivery (e.g., by installing the app on their own shop, or from a topic whose body content is shop-agnostic/predictable) can replay that exact body with the identical valid HMAC while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) header for a victim shop. `Utils::HmacValidator.validate` still returns `true` because it only re-derives the signature from `@raw_body`, which is unchanged. The forged request then reaches the host application's handler carrying `shop: <victim-shop>` with a cryptographically "valid" signature, even though the identity claim was never authenticated.

This is the same bug class as the CKB report's identity-binding failure, adapted to this gem's threat model: a field acted upon (`shop`, used by the handler to resolve sessions/tokens/tenant context) is not covered by the authenticator (`hmac`) that is supposed to vouch for the whole request.

### Impact Explanation
If a host application uses `WebhookMetadata#shop` (populated from `request.shop`) to look up the shop's stored session/access token or to scope tenant data — the documented and expected usage pattern for this gem's webhook handlers — an attacker can present a validly-HMAC'd webhook body under an arbitrary victim shop domain. This enables cross-tenant impersonation of webhook delivery: the host app believes an event genuinely originated from the victim shop, potentially triggering privileged actions (data sync, order processing, uninstall/GDPR handling, etc.) attributed to the wrong tenant.

### Likelihood Explanation
Exploitability requires the attacker to obtain at least one legitimate, validly-signed webhook body (trivial: install the target app on their own store, or replay any topic where the body content doesn't intrinsically encode the shop), then replay it with a modified `shop-domain` header against the app's public webhook endpoint. No secret material is required. Likelihood depends on whether the host handler trusts `shop` from `WebhookMetadata` for tenant resolution without cross-checking against body content — which is the gem's documented pattern (`docs/usage/webhooks.md`, `WebhookMetadata`), making this a realistic misuse-inducing gap rather than a purely theoretical one.

### Recommendation
Bind the identity-bearing headers (`shop`, `topic`, `webhook_id`, `api_version`) into the signed material verified by `HmacValidator`, or otherwise cryptographically tie the header claims to the signature (e.g., include the shop domain in `to_signable_string`, matching how `Auth::Oauth::AuthQuery#to_signable_string` binds `shop` into its signable string as shown in `test/auth/oauth/auth_query_test.rb`). At minimum, document prominently that `WebhookMetadata#shop`/`#topic` are unauthenticated header values and must not be used for tenant/session resolution without independent verification.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`, triggering a webhook whose body is shop-agnostic (or captures any webhook delivery).
2. Attacker records the raw body and its valid `x-shopify-hmac-sha256` header value (computed by Shopify over that body with the app's secret).
3. Attacker replays the identical body + HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `Request.new` accepts the forged headers; `HmacValidator.validate` recomputes HMAC over `@raw_body` only and it matches — `Registry.process` proceeds and calls the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)`, even though `victim.myshopify.com` never sent this request.
