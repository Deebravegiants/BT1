Audit Report

## Title
Nil pointer dereference on missing `params` in vault public-key-get gateway message handler - ([File: core/capabilities/vault/gw_handler.go])

## Summary
`GatewayHandler.handlePublicKeyGet` on the node side unconditionally dereferences `*req.Params` in `json.Unmarshal(*req.Params, r)` without checking for `nil`, unlike every other vault gateway method which validates `req.Params == nil` in `GatewayVaultRequestProcessor`. Because `MethodPublicKeyGet` is also explicitly exempted from authorization/validation on the gateway side (`HandleJSONRPCUserMessage`), an unauthenticated client can send a `vault.publicKey.get` request with no/`null` `params` and reach the unguarded dereference, causing a panic.

## Finding Description
The gateway-side `handler.HandleJSONRPCUserMessage` special-cases `vaulttypes.MethodPublicKeyGet`: it explicitly comments "Public key requests don't require authorization" and forwards the request without calling `requestProcessor.ProcessRequest` (which is the only place that validates `req.Params != nil`) [1](#0-0) . This forwards straight to `h.handlePublicKeyGet(ctx, ar)`/DON nodes without a params-nil check, whereas all other methods (`SecretsCreate/Update/Delete/List`) go through `requestProcessor.ProcessRequest`, which does check `req.Params == nil` first [5](#0-4) .

On the node side, `GatewayHandler.HandleGatewayMessage` dispatches `MethodPublicKeyGet` directly to `handlePublicKeyGet`, bypassing `h.requestProcessor.ProcessRequest` entirely (which is used for `SecretsCreate/Update/Delete/List`) [6](#0-5) . `handlePublicKeyGet` then does `json.Unmarshal(*req.Params, r)`, dereferencing `req.Params` (a `*json.RawMessage`) with no nil guard [2](#0-1) . If `req.Params` is `nil` (e.g., the field is omitted or explicitly `null` in the incoming JSON-RPC request), this is a Go nil pointer dereference and panics.

This is a genuine inconsistency versus the sibling code paths, which explicitly guard against this exact case, e.g. `processCreateSecretsRequest` and `processDeleteSecretsRequest` both check `if req.Params == nil { return nil, InvalidVaultParamsError{...} }` before unmarshalling [7](#0-6) [8](#0-7) .

## Impact Explanation
An unauthenticated JSON-RPC request with method `vault.publicKey.get` and missing/null `params` triggers a runtime panic in the vault gateway-message handler on the node side (and potentially also in the gateway-side handler, since `handlePublicKeyGet` there presumably also touches `ar.req.Params` downstream, though this exact function body was not located in the index). If unrecovered at a higher layer (e.g. connector/gateway server goroutine `recover()`), this is a denial-of-service against the vault capability's gateway message-handling path per request. This maps to a legitimate in-scope "unauthorized action causing service disruption" style issue, though I could not find or rule out a `recover()` wrapper around `HandleGatewayMessage`/`HandleJSONRPCUserMessage` dispatch within the indexed content, so the ultimate blast radius (single request handling failure vs. full process crash) remains unconfirmed.

## Likelihood Explanation
High for reachability: `MethodPublicKeyGet` is by design unauthenticated and skips the shared params-validation pipeline that every other vault method uses, so an unprivileged/unauthenticated client can trivially construct and send such a request. This is not a hypothetical or contrived condition — it is a straightforward divergence from the validation pattern applied everywhere else in the same file.

## Recommendation
Add an explicit `if req.Params == nil` check at the top of `handlePublicKeyGet` in `core/capabilities/vault/gw_handler.go`, returning `h.errorResponse(ctx, gatewayID, req, api.InvalidParamsError, ...)` instead of unmarshalling a nil pointer, and add the equivalent guard in the gateway-side `core/services/gateway/handlers/vault/handler.go` `handlePublicKeyGet` path before constructing/forwarding the active request.

## Proof of Concept
Send a JSON-RPC request to the gateway (or directly simulate a node-side `GatewayHandler.HandleGatewayMessage` call in a unit test) with:
```json
{"jsonrpc":"2.0","id":"1","method":"vault.publicKey.get"}
```
(no `params` key, or `"params": null`). This bypasses `requestProcessor.ProcessRequest` and reaches `handlePublicKeyGet`, which executes `json.Unmarshal(*req.Params, r)` with `req.Params == nil`, panicking [9](#0-8) . A minimal Go unit test constructing a `jsonrpc.Request[json.RawMessage]{Method: vaulttypes.MethodPublicKeyGet, Params: nil}` and invoking `GatewayHandler.HandleGatewayMessage` would reproduce the panic directly.
