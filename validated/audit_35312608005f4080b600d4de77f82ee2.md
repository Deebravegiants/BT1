### Title
Cross-tenant webhook spoofing via unauthenticated `shop` header not covered by HMAC - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop` (tenant identifier) is read from an HTTP header that is never included in the signed content. `Registry.process` validates the body's HMAC and then passes this unauthenticated `shop` value straight to the webhook handler, letting an attacker attribute a validly-signed body to any shop of their choosing.

### Finding Description
`Utils::HmacValidator.validate` computes and compares the HMAC using `verifiable_query.to_signable_string` as the signed content: [1](#0-0) 

For `Webhooks::Request`, `to_signable_string` returns only the raw HTTP body: [2](#0-1) 

But `shop` is derived from the `shopify-shop-domain` / `x-shopify-shop-domain` header, which is completely outside the HMAC's signed input: [3](#0-2) 

`Registry.process` validates only the body HMAC, then forwards the unauthenticated `shop` header value directly into the data passed to the app's webhook handler: [4](#0-3) 

The equality that should hold is: **the shop credited with a webhook payload == the shop whose bytes were actually HMAC-signed by Shopify**. Because the HMAC only covers `@raw_body` and not the `shop-domain` header, this binding is broken: `request.shop` (attacker-controlled header) is not covered by `hmac` (Digest.hexencode of the `hmac-sha256` header, verified only against `@raw_body`). Since the app-wide `Context.api_secret_key` used for the HMAC is not shop-specific, any body+HMAC pair generated for one shop's genuine webhook delivery remains a validly-signed pair regardless of which `shop-domain` header accompanies it. An attacker who operates their own store using the same app can generate a legitimately-signed webhook body (e.g., by causing an `orders/create` webhook to fire in their own shop with attacker-chosen order/customer content), capture the `(raw_body, hmac-sha256 header)` pair, and replay it to the app's webhook endpoint while swapping in a victim shop's `shopify-shop-domain` header value. `HmacValidator.validate` still passes because it never inspects the shop header, and `Registry.process` hands the handler a `WebhookMetadata` claiming the data belongs to the victim shop.

### Impact Explanation
This crosses a tenant boundary: an app whose webhook handler uses `WebhookMetadata#shop` to select which merchant's records to update (a common pattern, e.g., writing order/customer data keyed by shop) can be made to attribute attacker-controlled webhook content to a different, victim tenant. This is a cross-tenant data-integrity/confusion issue reachable purely by an unprivileged user who runs their own store on the same app, satisfying the "cross-tenant access" High/Critical impact category.

### Likelihood Explanation
Likelihood is moderate-to-high for any app that (a) allows self-serve installs (so an attacker can be a legitimate merchant/tenant) and (b) keys downstream state by the `shop` field taken from `WebhookMetadata`. No secrets, tokens, or privileged access are required — only the ability to trigger a webhook in one's own shop and replay the HTTP request with a different header.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the signed content, or otherwise cryptographically bind the `shop-domain` header to the payload before trusting it. At minimum, the gem should document/verify that `shop` is not itself protected by the HMAC so consuming applications don't implicitly trust it as authenticated, or better: incorporate the header value into `to_signable_string` so `HmacValidator.validate` fails whenever the shop header is altered relative to what Shopify actually signed.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker.myshopify.com` and triggers a webhook (e.g., `orders/create`) with content of their choosing, receiving `raw_body` and the corresponding `X-Shopify-Hmac-Sha256` header from Shopify.
2. Attacker resends this exact `raw_body` and `hmac-sha256` header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the headers (all required headers present) and `Utils::HmacValidator.validate(request)` succeeds, because it only recomputes/verifies the HMAC over `@raw_body`, which is unchanged: [5](#0-4) 
4. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))` with `shop == "victim.myshopify.com"`, even though Shopify never issued this webhook for that shop: [6](#0-5) 
5. Any app logic that persists or acts on `data.shop` now processes attacker-controlled content as if it originated from the victim's store.
