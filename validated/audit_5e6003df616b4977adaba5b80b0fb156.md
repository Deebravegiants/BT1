### Title
Removing a state machine from a consensus client's whitelist permanently freezes funds for in-flight requests to that chain - (File: `modules/ismp/clients/grandpa/src/lib.rs`, `modules/ismp/clients/tendermint/src/pallet.rs`, `modules/ismp/core/src/handlers.rs`)

### Summary
`pallet-ismp-grandpa` and the Tendermint consensus pallet allow `RootOrigin`/`AdminOrigin` to remove a `StateMachine` from their `SupportedStateMachines` whitelist via `remove_state_machines` / `remove_supported_state_machine`, with no check for and no mechanism to settle outstanding requests/responses that are already in-flight to/from that state machine. Once removed, `ConsensusClient::state_machine()` unconditionally errors for that id, which is consulted by every core message handler (`validate_state_machine`, timeout handling) before any request/response/timeout for that chain can be processed. This leaves any pending request dispatched to (or awaiting timeout from) the now-unsupported chain permanently unprocessable: it can never be delivered and it can never be timed out, so the relayer fee/escrow attached to it is frozen forever.

### Finding Description
`add_state_machines`/`remove_state_machines` in the GRANDPA consensus pallet [1](#0-0)  and the analogous `remove_supported_state_machine` in the Tendermint pallet [2](#0-1)  simply delete the storage entry for a `StateMachine` with no check for outstanding commitments and no unregistration/settlement path.

The GRANDPA `ConsensusClient::state_machine` implementation looks the id up in this same whitelist and returns an error if it is absent: [3](#0-2) . Tendermint's implementation does the same [4](#0-3) .

Every core message handler that processes requests/responses/timeouts for a state machine must first resolve a `StateMachineClient` via `validate_state_machine`, which calls `consensus_client.state_machine(proof_height.id.state_id)` and propagates any error: [5](#0-4) . The timeout handler uses the same call through `validate_state_machine(host, timeout_proof.height)` before it will accept a non-membership proof and release/refund the pending request: [6](#0-5) .

Consequently, once a state machine is removed from the whitelist while there exist requests already dispatched to it (or from it, awaiting a response), those requests become permanently stuck:
- Delivery is impossible, because processing an incoming Post/Get requires the same `state_machine()` lookup via `validate_state_machine`.
- Timing out is impossible for the same reason — `handle` for `TimeoutMessage::Post`/`Get` calls `validate_state_machine(host, timeout_proof.height)` first and errors out before it ever reaches `verify_non_membership` [7](#0-6) .

The request commitment (and any escrowed relayer fee attached via `fund_message`/`FeeMetadata`) is never deleted in this failure path, so the relayer fee for that message, along with the ability to ever resolve the pending state, is frozen indefinitely — with no admin-facing recovery function to unregister/settle the stuck commitments either.

This mirrors the referenced report's root cause exactly: an unsupport/removal action for a previously-supported entity (currency pair in the bond oracle; here a `StateMachine` in a consensus client) leaves already-registered/in-flight objects (markets; here dispatched ISMP requests) referencing that entity in a permanently broken state, with the codebase providing no mechanism to gracefully unwind that dependent state.

### Impact Explanation
Any relayer fee escrowed for a pending Post/Get request or response to/from a state machine that is later removed from a consensus client's whitelist becomes permanently unrecoverable — it can neither be delivered (thus completing the transfer) nor timed out (thus refunding the sender). Since ISMP is the transport for token bridging, intents, and other value-bearing cross-chain flows in Hyperbridge, this is a permanent freezing-of-funds condition for any transaction that happens to be in-flight at the time the state machine's support is revoked — a routine maintenance action (deprecating a faulty/retired chain) that any operator would reasonably perform.

### Likelihood Explanation
`remove_state_machines`/`remove_supported_state_machine` are ordinary, expected operator actions (e.g., retiring a faulty or deprecated chain, similar to unsupporting a bad currency-pair oracle feed in the referenced report) rather than an attack requiring a malicious admin. Any unprivileged user's in-flight request that is caught mid-lifecycle when this maintenance call executes is affected — this is a realistic operational scenario, not a contrived edge case, and there is no code path anywhere in the pallets to reconcile pending commitments before/after the removal.

### Recommendation
- Before allowing `remove_state_machines`/`remove_supported_state_machine` to succeed (or as part of executing it), require that no outstanding request/response commitments exist for/targeting that state machine, or provide an explicit drain/settlement extrinsic that lets holders time out or otherwise reconcile in-flight messages for a state machine that is about to be deprecated.
- Alternatively, keep `state_machine()` resolvable (perhaps in a "deprecated, timeout-only" mode) for state machines that have been removed but still have live commitments, so that `TimeoutMessage` handling continues to work and funds can be recovered even after admin removal, while blocking new dispatches/deliveries.
- Emit an event enumerating any commitments still outstanding for a state machine being removed, so off-chain tooling can pre-emptively time these out before the removal takes effect.

### Proof of Concept
1. User dispatches a `PostRequest` (via `pallet-ismp`'s dispatcher) to `dest = StateMachine::Substrate(X)`, paying a relayer fee that is escrowed as part of the request's `FeeMetadata`/commitment.
2. Before the request is delivered or times out, the chain operator calls `pallet_ismp_grandpa::remove_state_machines(RootOrigin, vec![StateMachine::Substrate(X)])`, removing `X` from `SupportedStateMachines` [1](#0-0) .
3. A relayer attempts `handle_unsigned` with a `PostRequestMessage` destined for/originating at `X` — the underlying `validate_state_machine` call fails with `GrandpaError::UnsupportedStateMachine` because `state_machine()` no longer finds `X` in the whitelist [3](#0-2) , [8](#0-7) . Delivery permanently fails.
4. After `timeout_timestamp` elapses, a relayer submits a `TimeoutMessage::Post` with a valid non-membership proof for the same request. `handle` again calls `validate_state_machine(host, timeout_proof.height)` first [6](#0-5) , which fails for the same reason before `verify_non_membership`/refund logic is ever reached.
5. The request's commitment (and any escrowed relayer fee) remains in storage forever — neither deliverable nor timeout-able — with no extrinsic available to unregister/settle it.

pub fn validate_state_machine<H>(
	host: &H,
	proof_height: StateMachineHeight,
) -> Result<Box<dyn StateMachineClient>, Error>
where
	H: IsmpHost,
{
	// Ensure consensus client is not frozen
	let consensus_client_id = host.consensus_client_id(proof_height.id.consensus_state_id).ok_or(
		Error::ConsensusStateIdNotRecognized {
			consensus_state_id: proof_height.id.consensus_state_id,
		},
	)?;
	let consensus_client = host.consensus_client(consensus_client_id)?;
	// Ensure client is not frozen
	host.is_consensus_client_frozen(proof_height.id.consensus_state_id)?;

	// Ensure delay period has elapsed
	if !verify_delay_passed(host, &proof_height)? {
		return Err(Error::ChallengePeriodNotElapsed {
			state_machine_id: proof_height.id,
			current_time: host.timestamp(),
			update_time: host.state_machine_update_time(proof_height)?,
		});
	}

	consensus_client.state_machine(proof_height.id.state_id)
}
