### Title
Flash-loan repayment pulls `transfer_from` from a caller-chosen `receiver` that never authorizes — any contract that has approved the pool can be forced to pay the flash fee - (File: contracts/pool/src/ops/flash.rs)

### Summary
In `collect_repayment`, the pool executes `asset.transfer_from(pool, receiver, pool, total_repayment)`, spending the **pool's** allowance from `receiver`. `receiver` is an arbitrary address supplied by the unprivileged initiator through `controller.flash_loan`, and neither the controller nor the pool requires `receiver.require_auth()`. This mirrors M-02 exactly: a permissioned pull path lets a caller name any `from` that has a standing allowance to the pulling contract and spend it without that party's consent.

### Finding Description
- `contracts/controller/src/strategies/flash_loan.rs` — `process_flash_loan` only authenticates `caller` (`require_authorized_caller`), checks the hub is active, and requires `receiver` to be a WASM contract (`require_wasm_receiver`). `receiver` itself never signs and is passed through to the pool.

  ```rust
  // contracts/controller/src/strategies/flash_loan.rs:22-32
  require_authorized_caller(env, caller);
  ...
  require_wasm_receiver(env, receiver);
  ...
  pool_flash_loan_call(env, &pool_addr, hub_asset, caller, receiver, amount, data)
  ```

- `contracts/pool/src/ops/flash.rs` — `apply` sends `amount` to `receiver`, invokes `execute_flash_loan` on it, then `collect_repayment` pulls `total_repayment = amount + fee` **from `receiver`** using the pool's spender allowance:

  ```rust
  // contracts/pool/src/ops/flash.rs:173-179
  assert_with_error!(
      env,
      asset.allowance(receiver, pool) >= terms.total_repayment,
      FlashLoanError::InvalidFlashloanRepay
  );
  asset.transfer_from(pool, receiver, pool, &terms.total_repayment);
  ```

  The only guard on `from` is `allowance(receiver, pool) >= total_repayment`. The source of funds is entirely attacker-controlled and never authenticates — the same root cause as `BribeVault.depositBribeERC20`, where `DEPOSITOR_ROLE` spent `briber`'s allowance. Here the role gate is absent altogether: any unprivileged caller can invoke `flash_loan`, making it strictly worse in reachability.

### Impact Explanation
Theft of user funds: any contract that (a) exposes a `execute_flash_loan` entrypoint returning successfully (including contracts that implement the standard flash-receiver interface for their own legitimate use), and (b) holds an outstanding `approve(pool, …)` allowance on a flash-loanable asset, can be forced by any attacker to repay `amount + fee` while receiving only `amount`. The victim permanently loses `fee` (booked as protocol revenue via `book_fee`/`finalize`), scaled by `amount` up to the market's cash and the victim's allowance — repeated calls drain the full approved allowance in fee increments.

### Likelihood Explanation
- Reachability: `flash_loan` is a permissionless controller entrypoint; `caller` auth is the only signature required.
- Preconditions: a victim contract must have granted the pool a token allowance ≥ `amount + fee` and implement `execute_flash_loan`. Integrator contracts that settle with the pool via allowance (rather than the controller's `authorize_transfer_as_current` pull pattern) satisfy this. This is conditional on such a victim existing, and the extractable amount per call is limited to the fee, so likelihood is moderate but non-zero; the attack is repeatable until the allowance is exhausted.

### Recommendation
Do not pull repayment via allowance from a caller-supplied `from`. Either:
- require `receiver` itself to `transfer` the repayment inside its callback and enforce the post-callback balance check (`require_balance(balance_after_repayment)`) already present, removing `transfer_from` entirely, or
- keep `transfer_from` but require `receiver.require_auth()` (or equivalently `initiator.require_auth()` where `initiator == receiver`) so the funded party consents to the pull — the analog of the report's "first parameter of `safeTransferFrom` must be `msg.sender`" fix.

### Proof of Concept
1. Victim contract `V` implements `execute_flash_loan` (returns `()`) and at some point executed `token.approve(V, pool, X, expiry)` with `X ≥ amount + fee`.
2. Attacker calls `controller.flash_loan(hub_asset, amount, receiver = V, data)` and signs only for themselves.
3. `process_flash_loan` passes `V` to the pool with no auth from `V` (`flash_loan.rs:22-33`).
4. `ops::flash::apply` transfers `amount` to `V`, invokes `V.execute_flash_loan` (succeeds as a no-op), then `collect_repayment` executes `token.transfer_from(pool, V, pool, amount + fee)` (`flash.rs:166-179`), consuming `V`'s allowance.
5. Final state: `V` holds `amount` received but paid `amount + fee`; `fee` is credited to protocol revenue (`finalize` → `book_fee`). Attacker repeats until `allowance(V, pool)` is drained below `total_repayment`.
