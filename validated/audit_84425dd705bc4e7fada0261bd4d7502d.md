This confirms the vulnerability path: the docs explicitly tell developers that `ShopifyAPI::Webhooks::Registry.process` "will verify the request did indeed come from Shopify" (`docs/usage/webhooks.md:125`), and the `data.shop` field is documented as "The shop domain of the webhook" (`docs/usage/webhooks.md:14`) — implying it is a verified, trustworthy identifier that host apps are meant to key their per-tenant logic on (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)` in the doc's own example). But the actual HMAC computation only covers the raw body, never the shop domain header.### Title
Webhook shop identity spoofing via unauthenticated `shop-domain` header - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook's HMAC signature over the raw request **body** only, then trusts the `shop-domain` header — which is never included in that signature — as the authoritative tenant identifier passed to the app's handler. An attacker who can produce or replay one valid `(body, hmac)` pair signed with the app's shared `api_secret_key` (e.g. by installing the app on a shop they control and capturing Shopify's genuine webhook delivery) can resend that exact body with a forged `shop-domain` header naming a victim shop. The signature still validates because it never covers the shop field, so the handler processes the payload as if it legitimately originated from the victim tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request` exposes `hmac`, computed from the `hmac-sha256` header, and `to_signable_string`, which returns only `@raw_body`: [1](#0-0) [2](#0-1) 

`shop` is read independently from a separate header that is not part of the signed material at all: [3](#0-2) 

`Utils::HmacValidator.validate_signature` recomputes the HMAC solely over `to_signable_string` (the body) and compares it to the received signature — the shop field is never part of the equality check: [4](#0-3) 

`Registry.process` validates the HMAC and then immediately forwards the caller-supplied `request.shop` — unverified — to the handler as the tenant identity for the event: [5](#0-4) 

The documented contract for this API explicitly tells developers that `process` "will verify the request did indeed come from Shopify," and that `data.shop` is "the shop domain of the webhook," and shows it being used directly as the tenant key (`shop_domain: data.shop`) for later processing: [6](#0-5) [7](#0-6) 

The binding that is broken is: `shop authenticated by the gem` ≠ `shop actually bound to the signed payload`. The HMAC proves body integrity and knowledge of `api_secret_key`, but says nothing about which shop the payload is "for." Because `Registry.process` presents `request.shop` to handlers as if it were verified alongside the HMAC check, any host application that follows the documented pattern of keying per-tenant lookups (session/access-token retrieval, database writes, redaction actions) off `WebhookMetadata#shop` is relying on an identity binding this gem does not actually enforce.

### Impact Explanation
An attacker who controls any shop with the app installed receives genuine, validly-signed webhook deliveries for their own shop from Shopify. They can capture one such `(raw_body, hmac)` pair and replay it to the app's webhook endpoint with the `shop-domain`/`x-shopify-shop-domain` header rewritten to a victim shop's domain. Because the signature check is body-only, it passes, and the app's handler will process the request as an authentic event for the victim shop. Depending on how the host app is built (following this gem's own documented pattern), this can drive actions keyed by an incorrect tenant — including mandatory compliance topics like `customers/redact` or `shop/redact`, or triggering handler logic that loads the victim's stored offline session/access token to perform further API calls — resulting in cross-tenant data corruption or actions performed under the wrong merchant's identity.

### Likelihood Explanation
Any merchant/developer who can install the app on their own store (a normal, unprivileged flow) can obtain valid signed webhook bodies for arbitrary registered topics at will, simply by triggering the corresponding shop event. Forging the header requires no secret knowledge and no privileged access — only the ability to send an HTTP POST to the app's public webhook endpoint with modified headers, which this gem's `Webhooks::Request` accepts and does not cross-validate against the signed body.

### Recommendation
- Bind the shop domain (and other routing-relevant headers such as topic/api-version) into the HMAC-covered signable string, or independently verify the claimed shop against Shopify (e.g. re-fetch/validate via a shop-specific webhook secret or an authenticated lookup) before constructing `WebhookMetadata`.
- At minimum, update `docs/usage/webhooks.md` and `WebhookMetadata` documentation to clearly state that `shop` is unauthenticated header data and must not be trusted as a tenant boundary without additional verification by the host application.
- Consider validating that the resolved shop matches an expected/registered shop for the given webhook subscription id where possible.

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com` and triggers a registered webhook topic (e.g. `customers/data_request`), causing Shopify to POST a validly HMAC-signed body to the app's callback URL, e.g.:
   - Headers: `x-shopify-hmac-sha256: <valid>`, `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-topic: customers/data_request`
   - Body: `{...}` (captured by attacker, who controls their own endpoint/network).
2. Attacker resends the identical body and HMAC header to the app's webhook endpoint, but replaces the header with `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers, and `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `hmac` against `@raw_body`: [8](#0-7) 
4. The handler receives `WebhookMetadata.new(..., shop: "victim.myshopify.com", ...)` and, following this gem's documented pattern, performs tenant-scoped work (e.g. loads `victim.myshopify.com`'s offline session, executes redaction/compliance logic, writes data) under the wrong tenant, despite the payload having originated from the attacker's own shop.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
