### Title
Webhook HMAC signature does not cover the `shop-domain` header, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature only over the raw request body, while the shop identity used to route the webhook to a handler (`shop-domain` header) is read from an unsigned HTTP header. Any actor able to trigger a legitimately-signed webhook for their own shop (e.g. by installing the app on their own store/dev store and performing an action that fires a webhook) can capture that valid `(raw_body, hmac)` pair and replay it to the app's webhook endpoint with an arbitrary `x-shopify-shop-domain` header. `Utils::HmacValidator.validate` will accept it because the header is never part of the signed content, and `Webhooks::Registry.process` will hand the (attacker-chosen) `shop` value straight to the app's handler.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from request headers, none of which participate in the signature: [2](#0-1) 

`Webhooks::Registry.process` validates the request using only this HMAC (i.e. only the body) and then forwards `request.shop` (the unsigned header) directly into the metadata passed to the consuming application's handler: [3](#0-2) 

The identity binding that should hold is:
```
verified(hmac, raw_body) == true  ⇒  shop header is authentic
```
but the actual binding enforced is only:
```
verified(hmac, raw_body) == true  ⇒  raw_body is authentic
```
`shop` (and `topic`/`webhook_id`) are consumed by the handler without being covered by that proof, breaking the equality `signed_bytes == acted_on_bytes`.

### Impact Explanation
Because the shop identity is not cryptographically bound to the signature, an attacker who can obtain one valid `(raw_body, hmac)` pair — trivially achievable by installing the target app on their own (free/dev) Shopify store and triggering any webhook topic the app subscribes to — can replay that exact body+HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain`/`shopify-shop-domain` header with any other shop's domain. `Registry.process` will pass this attacker-chosen `shop` value into `WebhookMetadata`, and the host application's webhook handler will act on it as if it originated from that other tenant. Depending on how the host app uses `WebhookMetadata#shop` (e.g. looking up a session/access token for that shop, updating records keyed by shop, or triggering shop-scoped side effects), this enables cross-tenant data confusion/corruption — an attacker can inject an attacker-controlled but validly-"Shopify-signed" payload and have it attributed to an arbitrary victim shop.

### Likelihood Explanation
Likelihood is high in relative terms: no leaked secrets or privileged access are required. Any internet user can create a Shopify development store, install a target app that uses this library, and legitimately generate a webhook payload of their choosing (subject to the topic's schema) by performing corresponding actions in their own store (or in some cases via API calls against their own shop). They then simply resend the HTTP POST to the app's public webhook endpoint with a modified shop header — no cryptographic secret is needed to do this, since the header is outside the signed content.

### Recommendation
Bind the shop identity (and ideally topic/webhook-id) to the HMAC verification, e.g. by:
- Requiring the host application to compare `request.shop` against a shop it has an active session/installation for, and reject webhooks for shops that are not recognized/installed, before trusting `request.shop` for any tenant-scoped action, and/or
- Making the library itself refuse to hand off `WebhookMetadata` unless the caller supplies a known/expected shop to cross-check against `request.shop`.
- At minimum, document prominently that `request.shop` is unauthenticated and must not be trusted for tenant-scoped decisions without an independent shop allow-list/session lookup.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` and triggers a subscribed webhook topic (e.g. `orders/create`), capturing the resulting POST request: raw body `B` and header `x-shopify-hmac-sha256: H` (a valid HMAC of `B` under the app's real `api_secret_key`, computed by Shopify).
2. Attacker resends this exact request to the app's public webhook endpoint, keeping `B` and `H` unchanged, but replacing the header `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `to_signable_string` (`= B`) and compares it to `H` — this succeeds because `B` and `H` are unchanged and genuinely valid. [4](#0-3) 
4. The handler is invoked with `WebhookMetadata.new(..., shop: request.shop, ...)` where `request.shop` now returns `"victim-shop.myshopify.com"`, even though the payload actually originated from the attacker's own shop action. [5](#0-4)
