### Title
Webhook tenant identity (`shop-domain` header) is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC of the raw request body against the app's shared `client_secret` [4](#0-3) . The HMAC signable string is defined as just the raw body [1](#0-0) . The `shop` (tenant identity) is read from the `shopify-shop-domain` / `x-shopify-shop-domain` header, which is not included anywhere in the signed content [2](#0-1) . The equality the gem implicitly relies on but never checks is: `shop header used for tenant dispatch == shop that the signed body actually originated from`. Because the app's webhook HMAC secret (`client_secret`) is shared across every shop that installs the app, and the header carrying tenant identity is outside the signed payload, any store that has legitimately installed the app can capture one authentic webhook delivery (body + valid HMAC, obtained simply by using the app normally on their own store) and replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `shop-domain` header for a victim shop. `HmacValidator.validate` will still pass because it only recomputes the HMAC over the unchanged body [5](#0-4) , and `Registry.process` will hand the attacker-controlled `shop` straight to the app's handler as the authenticated tenant [6](#0-5) .

### Finding Description
`Webhooks::Request` mixes in `Utils::VerifiableQuery`, which requires `hmac` and `to_signable_string` [7](#0-6) . For webhooks, `to_signable_string` is hardcoded to the raw body only, and `shop` is parsed independently from an HTTP header that carries no cryptographic binding to that body [8](#0-7) . `Registry.process` trusts `Utils::HmacValidator.validate(request)` as its only authenticity check before forwarding `request.shop` to the handler as the tenant identifier via `WebhookMetadata` [3](#0-2) . Because the webhook secret is per-app (not per-shop) and Shopify's own webhook signing scheme signs only the body (this gem faithfully implements that), a malicious merchant who has installed the app on their own store can obtain a valid `(body, hmac)` pair from their own legitimate webhook traffic, then re-POST that pair to the app's webhook endpoint with the `shop-domain` header rewritten to a different, victim shop domain. The library has no mechanism to detect this because the shop identity is never part of what's verified.

### Impact Explanation
This breaks the tenant-isolation boundary the app relies on: an unprivileged internet user (any merchant who installed the app) can make the host application process a forged event under an arbitrary victim shop identity. Depending on how the host app's webhook handler uses `WebhookMetadata#shop` (e.g., to fetch/modify per-shop settings, trigger data sync, or scope database writes/deletes), this can lead to cross-tenant data corruption or disclosure — matching the "cross-tenant access" impact category, without requiring knowledge of `api_secret_key`, an access token, or any credential belonging to the victim.

### Likelihood Explanation
Likelihood is high for a determined but low-privileged attacker: no secret material needs to be obtained — the attacker only needs their own legitimate app installation (an ordinary, low-cost/free step for many public apps) to generate one authentic webhook body/HMAC pair, then replay it with a modified header using any HTTP client. No race condition, timing, or privileged access is required.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the signed content, or independently verify that the shop asserted in the header corresponds to the tenant that legitimately owns the signed payload (e.g., by having the host app cross-check the header shop against session/install records keyed by an out-of-band trusted identifier) before invoking the handler. At minimum, document prominently that `WebhookMetadata#shop` is not itself authenticated and must not be trusted as a tenant boundary by consuming applications without additional verification.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` (legitimate, unprivileged action).
2. Attacker triggers any webhook topic the app subscribes to (e.g., updates a product), causing Shopify to POST a legitimately HMAC-signed webhook to the app's endpoint with headers `shopify-shop-domain: attacker-shop.myshopify.com`, `shopify-hmac-sha256: <valid-hmac-of-body>`, and some JSON body.
3. Attacker captures this `(raw_body, hmac)` pair (e.g., via their own proxy/logging, since it was delivered to their own installed app instance if self-hosted, or via any means of observing their own traffic).
4. Attacker re-sends an HTTP POST to the app's webhook endpoint with the identical `raw_body` and `shopify-hmac-sha256` header, but sets `shopify-shop-domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `to_signable_string` (`@raw_body`) — unchanged, so validation passes [1](#0-0) .
6. The handler is invoked with `WebhookMetadata.new(... shop: request.shop ...)` where `request.shop` is `"victim-shop.myshopify.com"`, an identity the attacker fully controls despite having no access to that shop [9](#0-8) .
