### Title
Webhook shop-domain, topic and webhook-id are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop`, `topic`, `webhook_id`, and `api_version` from HTTP headers, but `to_signable_string` — the data actually protected by the HMAC — only covers the raw request body. `Registry.process` treats HMAC success as proof that the entire request (including the header-derived `shop`) is authentic, then hands that unauthenticated `shop` value straight to the app's webhook handler.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all pulled from HTTP headers that are never mixed into the signable string: [2](#0-1) 

`HmacValidator.validate` only checks `verifiable_query.hmac` against `verifiable_query.to_signable_string`, i.e. the body: [3](#0-2) 

`Registry.process` accepts the request as soon as this body-only HMAC check passes, then forwards the *header-derived* (unauthenticated) `shop`, `topic`, and `webhook_id` to the registered handler without any additional binding to the body content: [4](#0-3) 

This breaks the identity binding `hmac(body, secret) == received_hmac` ⇒ `shop header == authenticated tenant`. In reality the equation the code enforces is only `hmac(body, secret) == received_hmac`; the `shop` header can be swapped to any value without invalidating the signature, since it is bytes verified (the body) vs. bytes parsed for tenant identity (the header) — one of the explicitly in-scope analog classes.

### Impact Explanation
An attacker who has legitimately received one authentic webhook delivery for their own store (a completely unprivileged action — anyone can install/uninstall a public app or trigger any webhook topic on their own shop) can capture that valid `(raw_body, hmac)` pair and replay it against the app's webhook endpoint with the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`, `X-Shopify-Webhook-Id`) header changed to a victim shop. `HmacValidator.validate` still succeeds because it never looks at those headers, and `Registry.process` will dispatch the handler with `shop: <victim-shop>` and the attacker-controlled body. Any host application that uses `WebhookMetadata#shop` to scope data writes, uninstall handling, or entitlement changes per merchant will apply the attacker's payload to the victim tenant — a cross-tenant data/entitlement corruption.

### Likelihood Explanation
Requires the attacker to have received at least one real webhook (trivial: install the app on their own free dev store or trigger `app/uninstalled`), and requires the endpoint to be reachable over the internet (the normal deployment case for webhook receivers). No access token, `client_secret`, or privileged account is needed. The gem provides no header authentication at all, so exploitation is a simple curl replay with a modified header.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the HMAC-covered signable content (or otherwise cryptographically bind them to the body), and have `Registry.process` reject/re-derive `shop` from an authenticated source instead of trusting the raw header value for tenant routing.

### Proof of Concept
1. Install the target app on an attacker-owned dev store; capture a legitimate webhook POST, e.g. `orders/create`, noting the raw body `B` and the `X-Shopify-Hmac-Sha256` header `H` (valid because `HMAC(secret, B) == H`).
2. Replay the same request to the app's webhook endpoint, keeping body `B` and header `H` unchanged, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request#hmac` decodes `H`; `HmacValidator.validate` recomputes `HMAC(secret, B)` and it still matches `H`, so `Registry.process` proceeds.
4. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...))`, causing the host app to process attacker-controlled data as if it came from `victim-shop`.
