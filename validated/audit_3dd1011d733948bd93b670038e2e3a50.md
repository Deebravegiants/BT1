### Title
Tokens transferred directly to the pool or controller are permanently locked — no sweep or unbooked-balance recovery exists - (File: contracts/controller/src/payments.rs)

### Summary
The H01 class is "tokens held by the contract cannot be recovered when they fall outside the intended interface/accounting path." XOXNO Lending reproduces the stuck-funds consequence directly: the pool tracks a `cash` book per `(hub_id, asset)` rather than its real token balance, every outbound leg is bounded by that book or by a measured balance delta, and neither the pool, the controller, nor governance exposes a `sweep`/`skim`/`rescue` entrypoint. Any token — listed or unlisted — sent straight to the pool or controller address is permanently stranded.

### Finding Description
- The pool's reserve is an accounting book, not its token balance: "Tracked cash, rather than an incidental token balance, is the reserve book" (INV-ACCT-02; `docs/reference/invariants.md:104-109`, `docs/explanation/threat-model.md:129-130` — "Direct donations do not rewrite those books"). Every outbound path is book-bounded: `withdraw`/`borrow`/`claim_revenue` pass `require_reserves` against `cash`, and `claim_revenue` pays `min(cash, floor(revenue_value))` (`docs/reference/formulas.md:107-113`).
- All token-funded credits use measured deltas since a per-operation snapshot (`snapshot_balances`/`balance_delta_since` in `contracts/controller/src/payments.rs:10-37`, INV-ACCT-03), so a pre-existing surplus is invisible to `supply`, `repay`, and `recapitalize`. The two refund legs that can pay out of custody (`ops::repay::apply`, `ops::recapitalize::apply`) refund only `amount - applied` of the *declared, freshly received* amount (`contracts/pool/src/ops/recapitalize.rs:52-55`), and `refund_controller_balance_delta` explicitly "preserv[es] the pre-existing balance" (`payments.rs:39-52`).
- The pool's fourteen mutating entrypoints are `#[only_owner]` and its owner is the controller (`contracts/pool/README.md:10`); the controller's endpoint list contains no recovery function. The harness test `test_migrate_refund_ignores_preexisting_controller_balance` pins that a stray controller balance "must remain (not used as refund or swept)" — the behavior is enforced, not incidental.
- Net effect mirrors H01: an accidental direct `token.transfer` to either contract is a permanent freeze. The only escape is a Wasm `upgrade` (privileged), analogous to Endaoment needing PR #68.

### Impact Explanation
Permanent freezing of funds: any user who transfers tokens directly to the pool or controller loses them with no on-chain recovery path, matching the report's accepted impact ("funds are stuck forever").

### Likelihood Explanation
Reachable by any unprivileged address via a plain token transfer — an allowed path per the scan rules. Likelihood rests on user error (wrong-address/assistive transfers are common on Stellar), so Medium rather than High.

### Recommendation
Add an owner-gated `sweep(asset, to)` on the pool that transfers `balance - Σ cash` across markets on that asset, and/or a controller-level sweep for its own transient balances; short of that, document the freeze in the README surface table.

### Proof of Concept
1. `token.transfer(user → pool, X)` for any listed asset. `cash` is unchanged (INV-ACCT-02/03).
2. `withdraw`/`borrow`/`claim_revenue` are capped by `cash`; `recapitalize`/`repay` refunds only cover the just-measured delta. No entrypoint touches the surplus `X`.
3. Repeat for the controller address — identical outcome, confirmed by `test_migrate_refund_ignores_preexisting_controller_balance`.

Note: this is a self-inflicted-loss analog; if the audit bar excludes accidental-deposit findings (as some programs do), this may rate Low/out-of-scope despite matching H01's mechanics.
