### Title
Missing zero-address check on `_admin` in Tron `IntentGatewayV2` constructor permanently bricks `setParams` and the entire gateway - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` takes an `admin` address in its constructor and stores it in `_admin` with no zero-address validation, unlike the EVM proxy version of the same contract which explicitly reverts on `owner == address(0)`.

### Finding Description
The constructor blindly assigns the constructor argument to `_admin`: [1](#0-0) 
`_admin` is the sole gate for the one-time `setParams` call that configures the gateway's operating `Params` (host, dispatcher, fee config, etc.) and simultaneously zeroes out `_admin` after use: [2](#0-1) 

If `_admin` is ever `address(0)` (either passed as zero at construction, or because `setParams` is never called and someone later checks `msg.sender != _admin`), `setParams` can never succeed for any real caller, since no externally-owned account or contract can produce `msg.sender == address(0)`. This mirrors exactly the reported bug class in `Factory.sol`: a zero-value privileged address set unchecked in the constructor permanently locks out the only entry point that depends on it, requiring a full redeployment.

Contrast this with the parallel, already-hardened EVM implementation of the same contract, which added the check for precisely this reason: [3](#0-2) 

### Impact Explanation
Because `host()` and all order-processing logic depend on `_params` (set only via `setParams`), a gateway deployed with `admin == address(0)` (or one whose admin key is lost/misconfigured before calling `setParams`) can never be configured. `host()` would resolve to `address(0)`, and any call into the dispatcher (`IDispatcher(hostAddr).host()`) used at the top of `placeOrder` would revert against a non-contract address, making the entire cross-chain intents gateway on Tron permanently inoperable — "a route unable to deliver messages" per the acceptance criteria — and requiring a full contract redeployment with a fresh CREATE2/CREATE address. This is a Medium-severity denial-of-service/bricking issue, consistent with the severity of the original report.

### Likelihood Explanation
This requires only an operational/deployment mistake (passing `address(0)` as `admin`) with no attacker action needed to trigger the freeze — the freeze exists the moment the contract is deployed that way, and is discovered only when `setParams` is attempted. Given the EVM sibling contract already had this exact class of bug identified and fixed (adding the `owner == address(0)` check), the Tron contract's lack of the same check indicates the fix was not ported, making this a real and demonstrated regression risk in this codebase rather than a purely theoretical one.

### Recommendation
Add a zero-address check in the Tron `IntentGatewayV2` constructor, mirroring the EVM version's fix:
```solidity
constructor(address admin) EIP712("IntentGateway", "2") {
    if (admin == address(0)) revert InvalidInput();
    _admin = admin;
}
```

### Proof of Concept
1. Deploy Tron `IntentGatewayV2` with `admin = address(0)` (via `evm/tron/migrations/2_deploy_ismp.js`, if the configured admin value resolves to zero due to misconfiguration).
2. Call `setParams(params)` from any account — the check `msg.sender != _admin` (`_admin == address(0)`) always evaluates true for any real caller, so the call always reverts with `Unauthorized()`.
3. `_params` remains permanently at its zero-initialized default; `host()` returns `address(0)` forever.
4. Any subsequent `placeOrder` call reverts when it calls `IDispatcher(hostAddr).host()` against the zero address, meaning the gateway can never be used and must be redeployed. [1](#0-0) [2](#0-1)
