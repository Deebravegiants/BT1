### Title
Missing sanity check on external stSTX ratio and cached liquidity index allows mispriced collateral/debt via `resolve-ststx`/`resolve-ztoken` - (File: mainnet/contracts/market/v0-4-market.clar)

### Summary
This is an analog of the ibBTC `pricePerShare` finding: Zest's oracle pipeline in `v0-4-market.clar` reads an external "ratio" for stSTX from the `ststx-token` contract via `call-ststx-ratio`/`resolve-ststx`, and combines it multiplicatively with a cached vault liquidity index in `resolve-ztoken`, with no check that either value only increases over time (unlike the timestamp-based `oracle-timestamp-fresh` monotonicity check that IS applied to price *timestamps* but not to the *ratio/index magnitude*).

### Finding Description
`resolve-ststx` computes `mul-div-down p ratio STSTX-RATIO-DECIMALS` where `ratio` comes directly from `call-ststx-ratio` (an external staking contract), and `resolve-ztoken` computes `div-down (* p cached-lindex) INDEX-PRECISION` where `cached-lindex` is the vault's own liquidity index cached via `get-cached-indexes`/`accrue-and-cache`. [1](#0-0)  These values feed directly into `price-resolve`, which only validates `oracle-price-legal` (price > 0) and timestamp freshness/monotonicity — it does **not** validate that the ratio or liquidity index itself is monotonically non-decreasing or within a bounded delta from the last observed value. [2](#0-1) 

The resulting price is used to value both collateral and debt in `get-notional-evaluation`/`get-asset-value`, which directly gates borrow/withdraw health checks (`is-healthy`) and liquidation thresholds. [3](#0-2) [4](#0-3) 

The identity that should hold is:
`collateral_value(t) ≈ f(ratio(t), lindex(t))` should be monotonically consistent with real backing, i.e., `ratio(t+1) >= ratio(t)` and `lindex(t+1) >= lindex(t)` (both are yield-accrual style values that should never decrease absent a bug/exploit in the upstream contracts). If a bug in the external `ststx-token` ratio (or a stale/incorrect cached liquidity index reused across calls within `accrue-and-cache`) returns an artificially small `ratio`/`lindex`, `resolve-ststx`/`resolve-ztoken` will silently accept it as long as it's `> 0` and the timestamp is fresh, undervaluing stSTX-derived collateral. Conversely, an artificially inflated ratio (or a manipulation that increases it beyond legitimate accrual) would overvalue zToken collateral relative to its true backing, letting a borrower extract more debt than their real collateral supports — breaking the `collateral_notional >= debt_notional * LTV` invariant that undercollateralization checks rely on.

### Impact Explanation
If the external stSTX ratio or the cached liquidity index can be pushed to an incorrect value (whether through an upstream bug/exploit in the staking contract, or because the `index-cache` in `accrue-and-cache` reuses a value read at a specific `stacks-block-time` across multiple, differently-priced valuations without re-verifying monotonic growth), a borrower could open a health check with over-valued zToken collateral and extract more debt than the true backing supports, or a liquidator/depositor could be shortchanged (or a redeemer over-paid) when the value is under-stated. This can lead to protocol insolvency or theft of principal — a Critical/High impact per the same value-identity break described in the ibBTC report (small `pricePerShare` → larger amount paid out than deserved).

### Likelihood Explanation
Likelihood is lower than the original ibBTC finding because Zest's `oracle-timestamp-fresh` and `oracle-price-legal` add partial protection (rejecting stale/zero prices), and `call-ststx-ratio` and the liquidity index are computed from Zest's own vault state (`index`/`lindex`) rather than a fully external black box for the index portion. However, no code path in `resolve-ststx`, `resolve-ztoken`, or `price-resolve` compares the new ratio/index against the last cached/observed value to reject a decrease, so a bug in the upstream `ststx-token` ratio getter, or any edge case producing a smaller-than-expected `lindex` snapshot, would flow through undetected. This mirrors exactly the confirmed BadgerDAO issue's root cause.

### Recommendation
- Persist the last-seen `ststx` ratio and each vault's `lindex` (similar to `last-update` for timestamps), and assert the new value is `>=` the last-seen value before accepting it in `resolve-ststx` and `resolve-ztoken`.
- Reject/discard price resolutions where the ratio or liquidity index decreases, matching the mitigation recommended for the ibBTC finding (`pricePerShare` should never decrease).

### Proof of Concept
1. `price-resolve` calls `resolve-price-feed` then `resolve-callcode`, which for `CALLCODE-ZSTSTX` computes `resolve-ztoken (resolve-ststx p) stSTX`, multiplying the raw price by the externally-supplied `ratio` and the cached `lindex`. [5](#0-4) 
2. The only guards applied are `oracle-price-legal` (`p > 0`) and `oracle-timestamp-fresh` (staleness/monotonic timestamp) — neither bounds the ratio/index magnitude itself. [6](#0-5) 
3. If `call-ststx-ratio` (external contract) or the cached `lindex` returns a value smaller than the true, previously-observed value, `resolve-ztoken`/`resolve-ststx` will compute an undervalued price for zstSTX collateral; if it returns a value larger than warranted, the resulting price overvalues that collateral in `get-notional-evaluation`, letting `is-healthy` pass for positions that are not actually adequately collateralized. [7](#0-6) 

Note: I was unable to locate the exact definition of `call-ststx-ratio` and `get-cached-indexes` within the available index (only usage sites were found), so the precise external contract call and cache-key mechanics for the liquidity index could not be fully confirmed — a Devin session with full repo access would be needed to verify these exact call sites and existing (if any) staleness/monotonicity guards on `index-cache`.
