This confirms the root cause: `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop`, `topic`, `api_version`, and `webhook_id` are all read directly from HTTP headers that are never included in the HMAC-covered signable string [2](#0-1) . `HmacValidator.validate` only verifies `verifiable_query.to_signable_string` (the raw body) against the HMAC, never the headers [3](#0-2) . `Registry.process` then trusts `request.shop` unconditionally to build `WebhookMetadata`, which is handed to the app's handler as the tenant identifier [4](#0-3) .

### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) header spoofing bypasses HMAC binding, enabling cross-tenant webhook injection - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string solely from the raw request body, never binding the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers to that signature. `Registry.process` relies on `HmacValidator.validate` to authenticate the request, then unconditionally trusts `request.shop` from headers to identify which merchant/tenant the webhook belongs to. Because the shop identity is not part of what's cryptographically verified, any body+HMAC pair that is valid for the app's secret (trivially obtainable by an attacker who installs the app on their own shop and captures one of their own genuine webhook deliveries) can be replayed with an arbitrary `shop-domain` header value, causing the app to process attacker-controlled data as though it came from a different, victim shop.

### Finding Description
The binding that should hold is: `verified_bytes == acted_on_bytes`, i.e., the bytes cryptographically authenticated by the HMAC should equal the bytes the application uses to determine tenant identity (`shop`) and dispatch semantics (`topic`). Instead:

- `Request#to_signable_string` returns only `@raw_body` [1](#0-0) .
- `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are parsed straight from HTTP headers with zero cryptographic linkage to the HMAC [2](#0-1) .
- `HmacValidator.validate_signature` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the received HMAC — the body is the only thing verified [3](#0-2) .
- `Registry.process` raises only if the HMAC over the body is invalid, then immediately builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` from the unverified headers and forwards it to the app's `WebhookHandler.handle` [4](#0-3) .

Since the app secret (`api_secret_key`) is shared across all shops installing the app (it's the app's own credential, not per-shop), any shop that installs the app can trigger genuine webhooks and capture valid `(raw_body, hmac)` pairs for that shared secret. Those same bytes remain HMAC-valid no matter what `shop-domain`/`topic`/`webhook-id` headers accompany them, so an attacker can resend the identical body+HMAC with a forged `shop-domain` header claiming to be a different (victim) shop.

### Impact Explanation
This breaks the identity binding between "the request that was cryptographically verified" and "the request whose `shop` field the app uses to route data/perform tenant-scoped actions." An app's `WebhookHandler#handle` implementation (documented pattern in `docs/usage/webhooks.md`) is expected to trust `data.shop` as the authenticated origin shop and typically uses it to look up per-tenant state, apply the webhook body to the correct merchant's records, or dispatch background jobs keyed by shop [5](#0-4) . An attacker able to replay a body+HMAC pair while spoofing `shop-domain` can inject data attributed to a shop they don't control, producing cross-tenant data corruption/injection in downstream systems that rely on this gem's webhook shop attribution as authoritative — matching the report's bug-class pattern of "a field acted on but not covered by the HMAC."

### Likelihood Explanation
Moderate-to-high: no privileged credentials are required beyond installing the target app on an attacker-controlled shop (a normal, low-privilege action available to any merchant), and the webhook HTTP endpoint is internet-reachable by design. The attacker needs to capture at least one legitimate `(raw_body, hmac)` pair, which is straightforward since they fully control their own shop's webhook triggers (e.g., creating an order, updating a product) and can observe/replay the resulting POST body and `X-Shopify-Hmac-Sha256` header while modifying only the `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) headers, none of which are checked by the gem.

### Recommendation
Bind the tenant-identifying and dispatch-relevant fields into the HMAC-verified payload, or otherwise cryptographically tie the `shop-domain` header to the verified request — for example, by having `Request#to_signable_string` include the `shop`, `topic`, and `webhook_id` alongside the raw body, or by cross-checking `request.shop` against a shop this specific webhook subscription was registered against (rather than trusting the header value unconditionally) before constructing `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the target Shopify app on their own shop `attacker.myshopify.com` and receives a genuine webhook, e.g. `orders/create`, with raw body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
2. Attacker resends a POST to the app's webhook endpoint with the identical body `B` and identical `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com` (a shop the attacker does not control/own).
3. `HmacValidator.validate` succeeds because it only checks `HMAC(secret, B) == H`, which is unaffected by header values [3](#0-2) .
4. `Registry.process` builds `WebhookMetadata` with `shop: "victim.myshopify.com"` and body `B` and forwards it to the app's handler [6](#0-5) , causing the app to act on attacker-controlled data attributed to the victim tenant.
