### Title
Webhook `shop` identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw body only, while the `shop` (tenant) identity is read from an unsigned HTTP header. `ShopifyAPI::Webhooks::Registry.process` authorizes the request solely by validating that HMAC, then dispatches to the app's handler using that unsigned `shop` value. Any attacker who can obtain one valid signed webhook body (e.g., by installing the app on their own free/dev store) can replay that exact body to the app's webhook endpoint while substituting an arbitrary `shop-domain`/`x-shopify-shop-domain` header, and the request still passes HMAC validation.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read from a header that is never part of the signed content: [2](#0-1) 

`HmacValidator.validate` verifies the HMAC using `verifiable_query.to_signable_string` (the body) against the app's `api_secret_key`: [3](#0-2) 

`Registry.process` treats a passing HMAC check as full authorization, then forwards the caller-supplied `request.shop` straight to the app's webhook handler as the tenant identifier: [4](#0-3) 

Because the same `api_secret_key` is used to sign webhooks for every shop that has the app installed, and the signature covers only the body, the binding `shop_that_signed_body == shop_delivered_to_handler` is never enforced by this gem. This is exactly the "field acted on but not covered by the HMAC" pattern: `shop` is used to route/attribute the webhook to a tenant, but it is not part of `to_signable_string`, so it can be swapped without invalidating the signature.

### Impact Explanation
Any entity that can install the app on a shop they control (a free/dev store is sufficient — no privileged credentials, access tokens, or leaked secrets required) can capture a legitimately HMAC-signed webhook body from their own store and replay it against the app's public webhook endpoint with a forged `shop-domain` header naming a different, victim shop. `Registry.process` will accept it as authentic (HMAC passes) and hand the handler a `WebhookMetadata` claiming to be from the victim shop with attacker-chosen body content: [5](#0-4) 

This is a cross-tenant identity-spoofing primitive: an app that keys any internal state, redaction, deactivation, or data-processing action off `WebhookMetadata#shop` can be tricked into performing that action against another merchant's tenant record, including for mandatory compliance topics (`shop/redact`, `customers/redact`, `customers/data_request`) enumerated in the same file: [6](#0-5) 

### Likelihood Explanation
The attack requires no secrets beyond what any merchant naturally has after installing the app on their own store — a low bar that meets the "unprivileged internet user" criterion. The forged header is trivial to inject since raw headers are provided verbatim to `Request.new`: [7](#0-6) 

### Recommendation
- Short term: Document/require that host applications treat `WebhookMetadata#shop` as untrusted for any authorization or tenant-scoping decision unless independently corroborated (e.g., cross-checked against the shop associated with the webhook subscription/topic that was registered).
- Long term: Where feasible, incorporate the shop domain into an application-level integrity check (e.g., look up the expected signing/shop association per subscription, or require the host app to verify `shop` against its own installation records) rather than relying on HMAC-of-body-only as proof of tenant identity.

### Proof of Concept
1. Attacker installs the target app on their own Shopify dev store (`attacker-shop.myshopify.com`) and lets the app deliver a real webhook, e.g. `customers/redact`, capturing the raw request body `B` and the valid `X-Shopify-Hmac-Sha256` header `H = HMAC-SHA256(api_secret_key, B)`.
2. Attacker sends a new HTTP POST to the app's webhook endpoint with:
   - Body: `B` (unchanged)
   - Header `X-Shopify-Hmac-Sha256: H` (unchanged, still valid because it only covers `B`)
   - Header `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (forged)
   - Header `X-Shopify-Topic: customers/redact`
3. `HmacValidator.validate` succeeds because it only checks `H` against `B` via `to_signable_string`: [8](#0-7) 
4. `Registry.process` invokes the registered handler with `WebhookMetadata.new(topic: "customers/redact", shop: "victim-shop.myshopify.com", body: ...)`, causing the app to perform redaction/side effects attributed to `victim-shop.myshopify.com` even though the request never actually originated from Shopify on behalf of that shop.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
