### Title
Unbounded SCALE decode of attacker-supplied `runtime_call` bytes in `pallet-hyper-fungible-token::on_accept` allows a remote-decode stack-overflow DoS of the destination chain - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
`pallet-hyper-fungible-token`'s `on_accept` handler decodes an attacker-controlled, unbounded `runtime_call: Vec<u8>` blob with plain `Decode::decode` and no recursion-depth limit, unlike the codebase's own `call-decompressor` pallet which explicitly guards identical `T::RuntimeCall` decoding with `decode_all_with_depth_limit`. Any account able to call `HyperFungibleToken.send(...)` on a source EVM chain (or the Substrate-side equivalent `send` extrinsic) — i.e. any unprivileged token bridger — can embed a maliciously deep, nested `RuntimeCall` value in the message's `data` field and have it decoded on the destination chain's runtime as part of routine cross-chain message delivery.

### Finding Description
In `on_accept`, once tokens are minted/transferred, optional calldata is executed: [1](#0-0) 

The `substrate_data.runtime_call` bytes are attacker-supplied (`message.data` came directly from the source-chain `HyperFungibleToken.Message.data` field, which the caller of `send()` fully controls), and are then decoded into the runtime's full `RuntimeCall` enum with **no depth limit**: [2](#0-1) 

`RuntimeCall` in a typical Substrate runtime is a deeply recursive enum (it contains variants like `Utility::batch(Vec<RuntimeCall>)`, `Scheduler`, `Proxy`, etc.), so SCALE decoding of a nested/self-referential call graph without a recursion cap can exhaust the call stack (a classic parity-scale-codec "decode bomb"). This is exactly the bug class described in CVE-2019-7443: an unprivileged caller supplies data whose *type/shape* is attacker-chosen, which is decoded by a privileged/critical code path without validating structural bounds, and the decode itself (before any authorization or filtering) can crash the process.

The codebase is aware of and defends against this exact pattern elsewhere: `modules/pallets/call-decompressor/src/lib.rs` decodes an equivalent `T::RuntimeCall` from attacker-supplied bytes using `decode_all_with_depth_limit(MAX_EXTRINSIC_DECODE_DEPTH_LIMIT, ...)`: [3](#0-2) 

but `pallet-hyper-fungible-token::on_accept` uses plain `Decode::decode` for the identical `T::RuntimeCall` type, bypassing this protection entirely. A repo-wide search confirms `decode_all_with_depth_limit` / `MAX_EXTRINSIC_DECODE_DEPTH_LIMIT` are only used in `call-decompressor`, nowhere in `hyper-fungible-token`.

The call reaches this code path via ordinary ISMP message delivery (`pallet_ismp::Call::handle_unsigned` → `handle_incoming_message` → `IsmpModule::on_accept` for the HFT module), which is the standard relayer-driven delivery flow for any token transfer — no special privilege is required to trigger it, only a token transfer with a crafted `data` field and enough relayer-submitted proof to get it delivered.

### Impact Explanation
A successful stack-overflow during SCALE decode aborts the process handling the extrinsic. Because this path is reachable from `handle_unsigned` (an unsigned, permissionless extrinsic accepted into the mempool and processed by validators/collators), a relayer or attacker delivering a single crafted cross-chain token message can crash node instances processing that block/extrinsic, halting ISMP message delivery for the affected chain (a "route unable to deliver messages" condition) and potentially destabilizing block production/relaying for hyperbridge until operators patch. This qualifies as High severity per the report's acceptance criteria (route unable to deliver messages / DoS of message delivery reachable by an unprivileged token bridger).

### Likelihood Explanation
Likelihood is high: exploitation requires only calling `HyperFungibleToken.send()` (or the pallet's registered `send` equivalent) with a crafted `data` payload and getting a relayer to deliver the resulting message — a completely permissionless, routine action already supported by the protocol's calldata-execution feature. No governance, admin, or validator collusion is needed.

### Recommendation
Decode `substrate_data.runtime_call` (and `SubstrateCalldata` itself) using `decode_all_with_depth_limit` with the same conservative bound already established in `call-decompressor` (`MAX_EXTRINSIC_DECODE_DEPTH_LIMIT`), rather than plain `Decode::decode`, in `modules/pallets/hyper-fungible-token/src/module.rs` line 189 (and the `SubstrateCalldata::decode` call on line 121). Reject calls whose encoded depth exceeds the limit before any further processing.

### Proof of Concept
1. Attacker constructs, off-chain, a SCALE-encoded `RuntimeCall` value consisting of deeply nested `Utility::batch(vec![Utility::batch(vec![... ])])` (or any other recursive call wrapper available in the target runtime), nested to a depth sufficient to overflow the decode call stack (thousands of levels, well within `Vec<u8>`'s size limits and typical extrinsic size limits).
2. Attacker wraps this in `SubstrateCalldata { signature: None, runtime_call: <crafted bytes> }`, SCALE-encodes it, and places it in the `data` field of a `HyperFungibleToken.Message` sent via `send()` on any EVM chain configured with the token bridge, e.g. `send(SendParams{ to: <any>, amount: <any>, data: <SubstrateCalldata bytes> })`.
3. A relayer submits the resulting ISMP POST request to the destination Substrate chain via `pallet_ismp::Call::handle_unsigned`, which invokes `pallet-hyper-fungible-token::on_accept`.
4. `on_accept` reaches `T::RuntimeCall::decode(&mut &*substrate_data.runtime_call)` at `module.rs:189`, which recurses into the crafted nested call structure without a depth cap and overflows the stack, crashing the validating/collating node.
