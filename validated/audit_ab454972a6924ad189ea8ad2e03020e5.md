## Title
Unbounded in-memory bid cache in the intents-coprocessor RPC allows memory-exhaustion DoS via cheap `place_bid` mempool flooding - ([File: modules/pallets/intents-coprocessor/rpc/src/lib.rs])

### Summary
The `BidCache` used by the intents-coprocessor RPC layer to serve sub-second bid discovery (`intents_getBidsForOrder`, `intents_subscribeBids`) stores every observed `place_bid` transaction from the *mempool* in an in-process `HashMap`, with no cap on the number of order commitments or the number of filler entries per commitment. The only eviction mechanism is a periodic, time-based sweep, exactly mirroring the `zeroconf` `DNSCache` flaw: unbounded insertion, bounded-only-by-TTL cleanup that cannot keep pace with a flood.

### Finding Description
`BidCache::insert` unconditionally grows the map on every observed mempool transaction that decodes as a `place_bid` call, keyed by the attacker-chosen order `commitment` (`H256`), with a `Vec<BidEntry>` per commitment that grows per distinct filler: [1](#0-0) 

The only cleanup is `remove_expired`, run on a fixed `cleanup_interval` timer, which only removes an entry once its `first_seen` age exceeds `ttl` — it does not cap total entries, total memory, or per-commitment fan-out: [2](#0-1) 

Population happens by watching the transaction pool's *ready* notification stream — i.e. as soon as a `place_bid` extrinsic passes `validate_transaction` and becomes ready, it is decoded and inserted into the cache, well before block inclusion or execution: [3](#0-2) 

Crucially, the economic protection that gates the *on-chain* `Bids` storage — a `StorageDepositFee` reserved via `Currency::reserve` — is only enforced inside the pallet's dispatch logic (`place_bid`), not at the `validate_transaction`/mempool-admission stage: [4](#0-3) 

Because `user_op` can be up to 1 MiB (`BoundedVec<u8, ConstU32<1_048_576>>`) and the mempool-cache insertion happens purely off the "ready" transaction stream, an attacker only needs to pay the ordinary extrinsic length/weight fee — not the storage deposit — to get up to 1 MiB copied into every RPC node's `BidCache`. By submitting many transactions with distinct commitments (arbitrary `H256` values, not required to reference a real order) and/or distinct signing accounts, the attacker can grow the cache unboundedly between cleanup ticks, and can keep re-growing it faster than the TTL-based sweep can reclaim memory, exactly as in the referenced `zeroconf` `DNSCache` advisory (unbounded insert, TTL-only expiry that a flood outruns).

### Impact Explanation
This is a memory-exhaustion (OOM) vector against any full/RPC node running the intents-coprocessor bid-watcher service, which underpins Hyperbridge's intents bid-discovery/relaying infrastructure. Sustained flooding drives unbounded heap growth (each entry up to ~1 MiB of `user_op` payload, with no per-commitment or global cap), degrading or crashing the node process and breaking bid discovery for legitimate fillers/relayers — i.e., disabling the intent-fulfillment discovery route on affected nodes. This matches CWE-400/CWE-770 (uncontrolled resource consumption), the same bug class as the analog report.

### Likelihood Explanation
Likelihood is high: `place_bid` is a permissionless, signed extrinsic available to any funded account; the cache-insertion path is driven purely by mempool "ready" status, not by execution success, and the deposit that limits the equivalent *on-chain* growth is never checked at this stage. An attacker needs only enough balance to pay ordinary transaction fees (not the storage deposit) to keep injecting large payloads into the cache faster than the fixed-interval TTL sweep can remove them.

### Recommendation
Bound the `BidCache` explicitly: cap the maximum number of tracked commitments and the maximum number of filler entries per commitment (mirroring the eviction-queue pattern already used for `BoundedStateCommitments`/`StateCommitmentQueue` in pallet-ismp), reject/drop insertions once the cap is hit, and/or require a lightweight cost/rate-limit check before caching a mempool-observed bid (e.g., verify sender has sufficient reservable balance for the deposit before caching, or size-limit `user_op` far below 1 MiB for the mempool-cache path). Consider also capping total cache memory rather than relying solely on time-based expiry.

### Proof of Concept
1. Fund an account with only enough balance to pay ordinary extrinsic fees (no need to cover `StorageDepositFee`).
2. Repeatedly submit `intentsCoprocessor.placeBid(commitment, user_op)` with distinct random `commitment` values and near-1 MiB `user_op` payloads, using multiple nonces/accounts to keep transactions in the "ready" pool.
3. Each transaction reaching "ready" status is picked up by `run_bid_watcher` and inserted into `BidCache` via `bid_cache.insert(...)`, regardless of whether it will ever execute successfully on-chain.
4. Observe RPC-node memory grow unbounded between `cleanup_interval` ticks; sustained submission outpaces `remove_expired`, eventually exhausting node memory.

/// In-memory bid cache.
pub struct BidCache {
	bids: RwLock<HashMap<H256, OrderBids>>,
	ttl: Duration,
}

impl BidCache {
	pub fn new(ttl: Duration) -> Self {
		Self { bids: RwLock::new(HashMap::new()), ttl }
	}

	pub fn insert(
		&self,
		commitment: H256,
		filler: Vec<u8>,
		user_op: Vec<u8>,
	) -> Result<(), String> {
		let entry = BidEntry { filler: filler.clone(), user_op };

		let mut bids = self.bids.write().map_err(|e| format!("BidCache lock poisoned: {e}"))?;
		let order = bids
			.entry(commitment)
			.or_insert_with(|| OrderBids { first_seen: Instant::now(), entries: Vec::new() });
		if let Some(existing) = order.entries.iter_mut().find(|e| e.filler == filler) {
			*existing = entry;
		} else {
			order.entries.push(entry);
		}
		Ok(())
	}

	pub fn remove_expired(&self) -> Result<(), String> {
		let now = Instant::now();
		let mut bids = self.bids.write().map_err(|e| format!("BidCache lock poisoned: {e}"))?;
		bids.retain(|_commitment, order| now.duration_since(order.first_seen) < self.ttl);
		Ok(())
	}

pub async fn run_bid_watcher<P, Block, T, Extra>(
	pool: Arc<P>,
	bid_cache: Arc<BidCache>,
	bid_sender: broadcast::Sender<RpcBidInfo>,
	cleanup_interval: Duration,
) where
	Block: BlockT,
	P: TransactionPool<Block = Block> + 'static,
	T: pallet_intents_coprocessor::Config,
	T::RuntimeCall: frame_support::traits::IsSubType<pallet_intents_coprocessor::Call<T>>
		+ DecodeWithMemTracking,
	T::AccountId: Encode + From<[u8; 32]> + DecodeWithMemTracking,
	Extra: DecodeWithMemTracking + Send + 'static,
{
	use futures::StreamExt;

	let mut stream = pool.import_notification_stream();
	let mut timer = tokio::time::interval(cleanup_interval);

	loop {
		tokio::select! {
			Some(tx_hash) = stream.next() => {
				let tx = match pool.ready_transaction(&tx_hash) {
					Some(tx) => tx,
					None => continue,
				};

				let extrinsic_bytes = tx.data().encode();

				if let Some((commitment, filler, user_op)) = extract_bid::<T, Extra>(&extrinsic_bytes) {
					log::info!(
						target: LOG_TARGET,
						"bid in mempool for {commitment:?}",
					);
					if let Err(e) = bid_cache.insert(commitment, filler.clone(), user_op.clone()) {
						log::warn!(target: LOG_TARGET, "failed to cache bid: {e}");
						continue;
					}

					let _ = bid_sender.send(RpcBidInfo { commitment, filler, user_op });
				}
			}
			_ = timer.tick() => {
				if let Err(e) = bid_cache.remove_expired() {
					log::warn!(target: LOG_TARGET, "failed to clean bid cache: {e}");
				}
			}
		}

		pub fn place_bid(
			origin: OriginFor<T>,
			commitment: H256,
			user_op: BoundedVec<u8, ConstU32<1_048_576>>,
		) -> DispatchResult {
			let filler = ensure_signed(origin)?;

			// Validate user_op is not empty
			ensure!(!user_op.is_empty(), Error::<T>::InvalidUserOp);

			// Phantom orders have stricter rules: one bid per filler, no updates, and only
			// within the configured acceptance window after the order was registered. Every
			// chain's active order is checked, not just the most recently generated one.
			if let Some(active) = CurrentPhantomOrder::<T>::get() {
				if let Some((_, info)) = active.iter().find(|(c, _)| *c == commitment) {
					let window: BlockNumberFor<T> = Self::phantom_bid_window().into();
					ensure!(
						frame_system::Pallet::<T>::block_number() <= info.created_at_block + window,
						Error::<T>::PhantomOrderBidWindowClosed
					);
					ensure!(
						!Bids::<T>::contains_key(&commitment, &filler),
						Error::<T>::DuplicatePhantomBid
					);
				}
			}

			// If a bid already exists, unreserve the old deposit first
			if let Some(old_deposit) = Bids::<T>::get(&commitment, &filler) {
				<T as Config>::Currency::unreserve(&filler, old_deposit);
			}

			let deposit = Self::storage_deposit_fee();

			// Reserve the new deposit
			<T as Config>::Currency::reserve(&filler, deposit)
				.map_err(|_| Error::<T>::InsufficientBalance)?;

			// Store the bid in offchain storage
			let bid = Bid { filler: filler.clone(), user_op: user_op.to_vec() };
			let offchain_key = Self::offchain_bid_key(&commitment, &filler);
			offchain_index::set(&offchain_key, &bid.encode());

			// Store deposit amount in onchain storage for discoverability and accurate refunds
			Bids::<T>::insert(&commitment, &filler, deposit);

			Self::deposit_event(Event::BidPlaced { filler, commitment, deposit });

			Ok(())
		}
