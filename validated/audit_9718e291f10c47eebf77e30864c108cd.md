### Title
Webhook `shop-domain` (and `topic`/`webhook-id`) identity fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while the shop identity (`shopify-shop-domain`/`x-shopify-shop-domain` header) and other metadata (`topic`, `webhook-id`) are read directly from unauthenticated HTTP headers and passed straight through to the host application's handler.

### Finding Description
`Utils::HmacValidator.validate` computes and compares the HMAC over `verifiable_query.to_signable_string`. For webhooks, this signable string is defined as: [1](#0-0) 

i.e. only `@raw_body` is bound by the HMAC. The `shop`, `topic`, and `webhook_id` accessors read straight from HTTP headers that are never included in the signed material: [2](#0-1) 

`Registry.process` validates only the HMAC of the body and then forwards the header-derived `shop` value, unauthenticated, to the app's registered handler as the tenant identity for the event: [3](#0-2) 

The identity binding that should hold is: `shop-domain header == shop bound by HMAC`. Because the HMAC only covers `@raw_body`, this equality is never enforced by the gem — `request.shop` is "verified bytes" (headers) that are disjoint from "bytes verified" (body) by the HMAC check, matching the report's bug class of "a field acted on but not covered by the HMAC."

Since a single app's `client_secret`/`api_secret_key` is shared across every shop that has installed the app, an HMAC computed with that key over a given body is valid for a webhook that superficially claims to come from *any* shop — the HMAC does not depend on, and therefore cannot detect tampering with, the `shopify-shop-domain` header. An attacker who can capture (or otherwise obtain) one valid `(raw_body, hmac)` pair delivered to the app's webhook endpoint — for example a webhook for their own store, or one replayed/relayed via an open redirect/logging sink on the host app — can resubmit the identical body/HMAC with a modified `shopify-shop-domain` header pointing at a victim shop. `HmacValidator.validate` will still return `true` because the signature check never inspects the header, and `Registry.process` will dispatch the event to the app's handler tagged with the attacker-chosen `shop`.

### Impact Explanation
This breaks the tenant boundary that Shopify webhook processing is supposed to enforce: the `shop` value handed to the app's business logic (e.g., used to look up/mutate per-merchant data, deactivate the merchant's data, or trigger `customers/redact`/`shop/redact` compliance flows) is attacker-controllable even though the HMAC check passes. Depending on how the host app uses `WebhookMetadata#shop`, this enables cross-tenant data access or corruption (e.g., causing shop A's webhook payload to be recorded/acted upon as belonging to victim shop B), satisfying the "cross-tenant access" Critical-impact category.

### Likelihood Explanation
Exploitation requires the attacker to obtain at least one legitimately-signed `(body, hmac)` pair for the app (trivial if the attacker is a merchant using the app themselves, since they receive/can trigger their own shop's webhooks) and the ability to POST to the app's public webhook endpoint with a modified header — both of which are unprivileged-internet-user capabilities with no access token, `api_secret_key`, or TLS interception needed.

### Recommendation
Bind the shop (and ideally topic/webhook-id) into the value that is HMAC-verified, or otherwise require the caller to separately authenticate/whitelist the `shopify-shop-domain` header against known installed shops before trusting it, rather than treating an unauthenticated header as verified tenant identity in `Webhooks::Registry.process`.

### Proof of Concept
1. App has processed one legitimate webhook for `shop-a.myshopify.com`, so an attacker (as a merchant of `shop-a`) can capture the exact `raw_body` and its `x-shopify-hmac-sha256` value that Shopify sent to the app's public webhook URL.
2. Attacker replays an HTTP POST to the same webhook endpoint with the identical body and HMAC header, but sets `x-shopify-shop-domain: shop-b.myshopify.com` (a shop the attacker does not control).
3. `ShopifyAPI::Webhooks::Request.new` parses this into a request object; `Utils::HmacValidator.validate(request)` recomputes the HMAC over `@raw_body` only and it matches, since the body/HMAC pair is unmodified — validation succeeds. [4](#0-3) 
4. `Registry.process` dispatches to the handler with `shop: request.shop` == `"shop-b.myshopify.com"`, even though the payload was never signed for, or sent by, shop B — the app's handler processes/attributes the event to the wrong tenant.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
