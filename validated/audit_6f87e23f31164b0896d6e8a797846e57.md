## Analysis

Comparing `lib/shopify_api/auth/oauth.rb` (OAuth authorization-code callback) against every other flow that builds a request carrying the app's `client_secret`, there is an inconsistency in shop-domain validation.

`ShopifyAPI::Auth::Oauth.validate_auth_callback` takes the `shop` value straight from the (HMAC-covered) query parameters and uses it, unsanitized, to construct the session whose `shop` field becomes the request host that receives the `client_secret`: [1](#0-0) 

`Clients::HttpClient#initialize` builds the outbound request URL directly from `session.shop`: [2](#0-1) 

Every other credential-bearing flow in this gem funnels the shop string through `Utils::ShopValidator.sanitize!` before it is trusted as a host — e.g. `TokenExchange.exchange_token` uses `dest_shop = jwt_payload.shop` and the codebase's own `ShopValidator` module exists specifically to reject any shop value that isn't one of the `TRUSTED_SHOPIFY_DOMAINS` suffixes: [3](#0-2) [4](#0-3) 

`ShopValidator` is referenced in `token_exchange.rb`, `client_credentials.rb`, `refresh_token.rb`, and `clients/graphql/storefront.rb`, but it is never called in `oauth.rb`.

The binding being checked (HMAC validity of the query string) is not equivalent to the binding actually relied on (host-format = trusted `*.myshopify.com`/`myshopify.io`/etc.). `Utils::HmacValidator.validate` only proves that the *bytes of the query string* were signed with the app's secret — it says nothing about whether the `shop` value inside that string is a well-formed Shopify domain versus an arbitrary string (e.g. containing embedded userinfo, path tricks, or a suffix constructed to look like a trusted domain but resolve elsewhere). Because `validate_auth_callback` skips `ShopValidator.sanitize!`, a syntactically-valid but non-Shopify host value that still passes HMAC verification (which only checks byte equality, not domain shape) is used verbatim to build `https://#{shop}/admin/oauth/access_token`, and the body of that request contains `client_id` and `client_secret`.

I could not fully confirm from the available index whether `AuthQuery#to_signable_string` restricts the shape of `shop` (i.e., whether Shopify's own signed callback query enforces `*.myshopify.com` formatting server-side) or whether malformed values could ever reach this code path with a valid signature — the `auth_query.rb` file's signable-string implementation was not retrieved in enough detail to prove this end-to-end. That gap means this should be treated as a validation-inconsistency finding (missing defense-in-depth check that is applied everywhere else) rather than a fully proven exploitable SSRF/credential-exfiltration path.

### Title
Missing `ShopValidator` sanitization of OAuth callback `shop` before it is used as the token-exchange host - (File: lib/shopify_api/auth/oauth.rb)

### Summary
`Auth::Oauth.validate_auth_callback` uses the raw `auth_query.shop` value to build the session whose `shop` attribute becomes the destination host for the access-token exchange request (which carries `client_id`/`client_secret`), without ever passing it through `Utils::ShopValidator.sanitize!`, unlike every other credential-bearing flow in the gem.

### Finding Description
`validate_auth_callback` validates the callback's HMAC and state, then immediately does:
```ruby
null_session = Auth::Session.new(shop: auth_query.shop)
...
client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
``` [5](#0-4) 

`HttpClient` then builds the request base URI directly from `session.shop`: [6](#0-5) 

HMAC validation proves byte-integrity of the query string against the app secret; it does not constrain the *shape* of the `shop` value to a Shopify-controlled domain. The gem itself acknowledges this distinct concern by providing `Utils::ShopValidator`, which restricts shop hosts to `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.com`, `myshopify.io`, `spin.dev`, `shop.dev`) and is deliberately invoked in `token_exchange.rb`, `client_credentials.rb`, `refresh_token.rb`, and `clients/graphql/storefront.rb`, but is absent from `oauth.rb`. This is exactly the class of binding break described in the reference report: a check (HMAC-validity) is treated as sufficient proof of a different property (trusted-host-ness) that it does not actually establish, and the field driving where secrets are sent (`shop`) is not re-validated with the mechanism the rest of the codebase uses for that purpose.

### Impact Explanation
If a `shop` value that passes HMAC verification but is not a genuine `*.myshopify.com` host reaches this code path, the app's `client_secret` (and `client_id`) would be POSTed to a host chosen by that value — SSRF carrying the app's credential, matching the High severity bucket in scope.

### Likelihood Explanation
Likelihood is uncertain without confirming exactly what values Shopify's own signed OAuth callback permits in the `shop` query parameter, and whether `AuthQuery`'s signable-string construction lets an attacker influence `shop` independent of a legitimately-signed request. The inconsistency with every sibling flow (all of which explicitly sanitize with `ShopValidator`) is concrete and verifiable, but the exact exploit precondition for the callback path specifically was not fully traceable in the indexed code.

### Recommendation
Call `Utils::ShopValidator.sanitize!(auth_query.shop)` (mirroring `token_exchange.rb`, `client_credentials.rb`, and `refresh_token.rb`) before constructing `null_session` in `Auth::Oauth.validate_auth_callback`, so the host that receives `client_secret` is always constrained to `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`.

### Proof of Concept
Not independently reproducible from the indexed contents alone — reproducing it requires confirming the exact contents/format constraints of `AuthQuery#to_signable_string` and how `shop` is populated in a real signed callback, which was not available in the retrieved code. Recommend a Devin session with full repo/file access to trace `lib/shopify_api/auth/oauth/auth_query.rb` end-to-end and attempt to construct a callback whose `shop` value is HMAC-valid but resolves to a non-Shopify host.

        def validate_auth_callback(cookies:, auth_query:)
          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state

          null_session = Auth::Session.new(shop: auth_query.shop)
          body = {
            client_id: Context.api_key,
            client_secret: Context.api_secret_key,
            code: auth_query.code,
            expiring: Context.expiring_offline_access_tokens ? 1 : 0, # Only applicable for offline tokens
          }

          client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
          response = begin
            client.request(
              Clients::HttpRequest.new(
                http_method: :post,
                path: "access_token",
                body: body,
                body_type: "application/json",
              ),
            )
          rescue ShopifyAPI::Errors::HttpResponseError => e
            raise Errors::RequestAccessTokenError,
              "Cannot complete OAuth process. Received a #{e.code} error while requesting access token."
          end

          session_params = T.cast(response.body, T::Hash[String, T.untyped]).to_h
          session = Session.from(shop: auth_query.shop,
            access_token_response: Oauth::AccessTokenResponse.from_hash(session_params))

        [
          "shopify.com",

          "shop.dev",

      class << self
        extend T::Sig

        sig do
          params(
            shop_domain: String,
            myshopify_domain: T.nilable(String),
          ).returns(T.nilable(String))
        end
        def sanitize_shop_domain(shop_domain, myshopify_domain: nil)
          uri = uri_from_shop_domain(shop_domain, myshopify_domain)
          return nil if uri.nil? || uri.host.nil? || uri.host.empty?

          trusted_domains(myshopify_domain).each do |trusted_domain|
            host = T.cast(uri.host, String)
            uri_domain = uri.domain
            next if uri_domain.nil?

            no_shop_name_in_subdomain = host == trusted_domain
            from_trusted_domain = trusted_domain == uri_domain

            if unified_admin?(uri) && from_trusted_domain
              return myshopify_domain_from_unified_admin(uri)
            end
            return nil if no_shop_name_in_subdomain || host.empty?
            return host if from_trusted_domain
          end
          nil
        end

        sig do
          params(
            shop: String,
            myshopify_domain: T.nilable(String),
          ).returns(String)
        end
        def sanitize!(shop, myshopify_domain: nil)
          host = sanitize_shop_domain(shop, myshopify_domain: myshopify_domain)
          if host.nil? || host.empty?
            raise Errors::InvalidShopError,
              "shop must be a trusted Shopify domain (see ShopValidator::TRUSTED_SHOPIFY_DOMAINS), got: #{shop.inspect}"
          end

          host
        end
