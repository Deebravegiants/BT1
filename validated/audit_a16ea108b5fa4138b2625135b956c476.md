## Analysis

The external report's bug class is a **batch operation where per-item state (ownership) diverges from what was authorized/validated**, causing a mismatch between what was checked and what was acted on. Mapping this to this gem's trust boundary: the relevant identity binding is **"a field acted on but not covered by the HMAC."**

In `lib/shopify_api/webhooks/request.rb`, the `Request#shop` field is read directly from the `x-shopify-shop-domain` (or `shopify-shop-domain`) HTTP header: [1](#0-0) 

But `to_signable_string`, which is what `HmacValidator` actually signs/verifies, only returns the raw body: [2](#0-1) 

`HmacValidator.validate` computes the HMAC purely over `verifiable_query.to_signable_string` (the body) and compares it against the `hmac` header — the `shop` header is never part of the signed material: [3](#0-2) 

Yet `Registry.process` trusts `request.shop` (taken straight from the unsigned header) and passes it into the dispatched `WebhookMetadata`, which apps use to key data to a specific merchant/tenant: [4](#0-3) 

The identity binding broken is: **shop authenticated by the HMAC (none — HMAC only covers the body) ≠ shop attributed to the webhook event (taken from an unauthenticated header)**.

Since `api_secret_key` is shared by the app across all shops that install it (not shop-specific), any merchant who installs the app can legitimately trigger webhooks and thus obtain valid `(body, hmac)` pairs signed with the app's own secret. Because `shop-domain` is not part of the signed payload, that same attacker can replay the identical body+hmac pair to the app's webhook endpoint while swapping the `x-shopify-shop-domain` header to name a **different, victim shop**. `HmacValidator.validate` will still return `true` (the body/hmac pair is genuinely valid), and `Registry.process` will hand the attacker-supplied body off to the handler tagged as belonging to the victim shop — a cross-tenant data/event confusion entirely within this gem's webhook verification logic, requiring no access to `api_secret_key`, access tokens, or TLS interception.

### Title
Webhook `shop` domain is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw body, excluding the `shop-domain` header from the HMAC-signed content, while `Registry.process` still trusts `request.shop` (from that unsigned header) to attribute the webhook to a specific merchant.

### Finding Description
`Webhooks::Request` implements `VerifiableQuery` by exposing `hmac` (from the `hmac-sha256` header) and `to_signable_string` (the raw body only) — see [5](#0-4) . `HmacValidator.validate` signs/verifies exactly `to_signable_string`, i.e. the body, against `Context.api_secret_key` [3](#0-2) . The `shop` accessor, however, is pulled straight from the `shop-domain` header without any cryptographic binding to the signature [1](#0-0) .

`Registry.process` validates HMAC and then dispatches `request.shop` into `WebhookMetadata` handed to the app's handler [4](#0-3) . Because `api_secret_key` is a single app-wide secret shared across every shop that installs the app, a genuine `(body, hmac)` pair obtained from one shop's own legitimate webhook traffic remains "valid" under `HmacValidator` regardless of which `shop-domain` header accompanies it. An attacker who legitimately installs the app on a shop they control can harvest such valid body/HMAC pairs, then submit them to the app's webhook endpoint with an arbitrary `shop-domain` header value naming another (victim) shop's domain. The library reports this as a validated, authentic webhook for the victim shop.

### Impact Explanation
This crosses a tenant boundary within the gem's own verification primitive: the shop attribution used by downstream handlers (`WebhookMetadata#shop`) is not authenticated, only the body is. Apps built on this gem that key persistence, side effects, or session/token lookups off `data.shop` from webhook payloads can be made to process attacker-supplied (but "HMAC-valid") data under a victim shop's identity — a cross-tenant confusion classified as Critical (cross-tenant access) per the scope of this bug class.

### Likelihood Explanation
Requires only that the attacker be able to install the app on any shop (a normal, unprivileged merchant action) to harvest valid signed webhook bodies, and be able to send arbitrary HTTP requests to the app's public webhook endpoint with a spoofed header — no `api_secret_key`, access token, or privileged access needed.

### Recommendation
Include the `shop` (and ideally `topic`/`api-version`) header values as part of the material verified against the HMAC, or otherwise cryptographically bind the shop domain claimed in the request to the signed body, before `Registry.process` dispatches `WebhookMetadata` to handlers.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com`; Shopify sends a genuine webhook: body `B`, header `x-shopify-hmac-sha256: H` (computed with the app's shared `api_secret_key` over `B`), `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker resends the same `B` and `H` to the app's webhook endpoint, replacing the header with `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `to_signable_string` (`B` only) and matches `H` — validation succeeds [6](#0-5) .
4. `WebhookMetadata.new(..., shop: request.shop, ...)` is built with `shop = "victim-shop.myshopify.com"` and passed to the app's handler, which now processes attacker-controlled body content as if it belonged to `victim-shop.myshopify.com`.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
