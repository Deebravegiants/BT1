### Title
Webhook shop identity is not covered by the HMAC signature, allowing shop-domain spoofing to the handler - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` signs only the raw HTTP body for HMAC verification, but the shop identity (`shop-domain` header) that gets handed to the app's webhook handler is read directly from an unauthenticated header and is never included in the signed material.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns `@raw_body` only, and `#shop` is derived purely from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header: [1](#0-0) 

`Utils::HmacValidator.validate` computes an HMAC over `verifiable_query.to_signable_string` (i.e. the raw body) using the shared `api_secret_key`, and compares it against the `hmac` header: [2](#0-1) 

`Webhooks::Registry.process` only checks that the body's HMAC is valid, then builds `WebhookMetadata` using `request.shop` — a value that was never part of the signed bytes: [3](#0-2) 

The `api_secret_key` used to compute/verify the HMAC is a single value shared across **every shop** that has installed the app — it is not shop-specific. As a result, the equality the library implicitly claims — "the HMAC-verified bytes == the bytes that determine which shop this event is attributed to" — does not hold: the verified bytes are `raw_body` only, while the shop attribution is parsed from a header outside that signed scope. Any party who can obtain one valid `(raw_body, hmac)` pair signed with the app's secret (e.g. by installing the app on their own store and capturing one of their own legitimate webhook deliveries, or by triggering a webhook event with a body/payload they control) can replay that exact body+HMAC pair to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header value. The HMAC check still passes (it only validates the body), and the handler receives `WebhookMetadata` claiming the event originated from the attacker-chosen shop.

### Impact Explanation
This breaks the tenant-attribution boundary the gem is supposed to enforce for webhook handlers: an unprivileged user who merely holds a merchant/dev-store account (no access token, no `api_secret_key`, no privileged access) can make the app process (and potentially persist, act upon, or associate access-token/session lookups against) attacker-supplied body content while impersonating another, unrelated shop. Depending on how the host app's `WebhookHandler` uses `data.shop` (e.g., to key session/token lookups, per-tenant records, or trigger the app's own outbound API calls "as" that shop), this can lead to cross-tenant data corruption or cross-tenant action execution — matching the Critical "cross-tenant access" impact class.

### Likelihood Explanation
Likelihood is High for any application that has at least one shop installed (which is the normal operating condition for any Shopify app): the attacker only needs to control a store that installs the target app to legitimately receive one valid signed webhook body, then can replay it with a forged shop header from a standard HTTP client. No secret material, TLS interception, or social engineering is required — only the shared `api_secret_key`-signed body, which any installing shop naturally receives.

### Recommendation
Bind the shop header into the material that is HMAC-verified, or at minimum reject/flag inconsistency between the header-derived shop and any shop identifier verifiable from the payload/registered subscription for that delivery (Shopify's own webhook payloads typically include shop-scoped identifiers). At a minimum, document and enforce that `request.shop` must be cross-checked by the host application against the shop that owns the currently active session/webhook registration (e.g., match `webhook_id` back to a subscription created for a known shop) rather than trusted outright from `WebhookMetadata`, since `Utils::HmacValidator` only authenticates body integrity, not shop attribution.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and receives a legitimate webhook, e.g. `orders/create`, with headers:
   - `x-shopify-hmac-sha256: <valid HMAC of raw_body under app's api_secret_key>`
   - `x-shopify-shop-domain: attacker-shop.myshopify.com`
   - `x-shopify-topic: orders/create`
2. Attacker replays the identical `raw_body` and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but changes the header to `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` recomputes the HMAC over `raw_body` only — unaffected by the header change — so validation succeeds: [4](#0-3) 
4. `Registry.process` invokes the app's handler with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: <attacker-controlled parsed_body>, ...)`, causing the app to act on attacker data under the victim shop's identity.

          end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
