### Title
Unchecked `U256` addition in relayer fee accumulation causes chain-halting panic on overflow - (File: `modules/pallets/relayer/src/accumulate.rs`)

### Summary
`pallet-ismp-relayer`'s fee-accumulation path (`Pallet::accumulate`, backed by the unsigned extrinsic `accumulate_fees`) sums attacker-influenced fee values into `Fees` storage and a local accumulator using plain `+=` on `sp_core::U256`, with no `checked_add`/`saturating_add`. `sp_core::U256` (from the `uint` crate's `construct_uint!` macro) panics unconditionally on overflow — in debug *and* release builds — unlike native integer overflow checks. A relayer/attacker who can get a sufficiently large fee value proven via a source-chain state proof can drive this addition past `U256::MAX`, causing a runtime panic during extrinsic execution. Because `accumulate_fees` is unsigned and dispatched deterministically from a state/receipt proof, every validator that imports a block containing this call executes the same panic, which aborts block execution everywhere — a chain halt, structurally analogous to ISA-2025-005's "malicious deposit → integer overflow → chain halt" in Cosmos SDK's `x/distribution`.

### Finding Description
In `modules/pallets/relayer/src/accumulate.rs`:

- `validate_results` accumulates per-relayer-address fee totals for a batch of commitments with a raw, unchecked add:
```rust
let entry = result.entry(address).or_insert(U256::zero());
*entry += fee;
``` [1](#0-0) 

- The persisted running balance in storage is likewise updated with an unchecked add inside `try_mutate`, in three separate call sites (`accumulate`, twice, and `accumulate_fee_and_deposit_event`):
```rust
let _ = Fees::<T>::try_mutate(state_machine, delivery_address.clone(), |inner| {
    *inner += total_fee;
    Ok::<(), ()>(())
});
``` [2](#0-1) [3](#0-2) 

`fee` itself is derived directly from attacker/relayer-supplied, source-chain-proven data with essentially no upper-bound check:
```rust
s if s.is_evm() => {
    use alloy_rlp::Decodable;
    let fee = alloy_primitives::U256::decode(&mut &*encoded_metadata)
        .map_err(|_| Error::<T>::ProofValidationError)?;
    U256::from_big_endian(&fee.to_be_bytes::<32>())
},
``` [4](#0-3) 

This value is read from whatever bytes are stored at the EVM `RequestCommitments` slot for the given commitment — a field that is set at dispatch time on the EVM host and is not clamped to a sane fee size anywhere in this verification path; the pallet trusts the full 256-bit width. `sp_core::U256`'s arithmetic operators (`uint` crate) call `panic_on_overflow!` unconditionally on overflow, unlike Rust's native integer types where overflow checks are a debug-only `cfg`. A panic inside a pallet dispatchable is not caught by FRAME's executive; it propagates and aborts execution of the block for every node re-executing it.

`accumulate_fees` is dispatched with `ensure_none(origin)` (unsigned), meaning any relayer/observer that can construct a valid `WithdrawalProof` (real state + receipt proofs — no signature required for the base path) can submit it once the commitment and delivery proofs exist. Since the proofs are proofs of real (attacker-influenced) on-chain state, the same panic is reproducible deterministically by every validator that imports the block, exactly mirroring the "malicious deposit causes integer overflow that halts the chain" pattern in the Cosmos advisory.

### Impact Explanation
A panic during block execution in a Substrate/FRAME runtime is not gracefully handled at the pallet level — it aborts execution of that block. If the panic is deterministic (same state, same extrinsic bytes) then every node that attempts to import/validate the block hits it, which means the chain cannot progress past that block: a permanent halt requiring a runtime upgrade / manual intervention to recover. This satisfies the "route unable to deliver messages" / permanent-freezing-of-funds-and-liveness class of impact called out in scope (Fees remain locked, relayer withdrawal path becomes unusable, and the chain itself stalls).

### Likelihood Explanation
The attacker needs to get a single delivery address's proven fee total (within one `accumulate` batch, or across repeated `accumulate`/`accumulate_fee_and_deposit_event` calls that keep adding to the same `Fees[state_machine][address]` entry) to approach `U256::MAX`. On the EVM leg, the fee value fed into `Fees` comes from the `RequestCommitments` storage slot's fee field at the source chain, and this pallet does not itself impose a maximum fee bound before adding it into the running total — it only checks decode-ability. Whether the EVM `EvmHost`/dispatcher contract independently bounds the fee to actual transferred token amounts is the piece I could not fully confirm before running out of tool budget (I located `FeeMetadata`/fee-related code in `evm/src/core/EvmHost.sol` but did not get to read the exact `dispatch` implementation to verify how `fee` is populated and whether it's tied 1:1 to a real token transfer). If the fee field can be set independently of an actual token balance (e.g., no invariant ties it to `msg.value`/`transferFrom` amount, or a malicious/attacker-deployed fee token can report an arbitrary huge balance), reaching near-`U256::MAX` in a small number of calls is straightforward and the likelihood is high. If it is strictly tied to real token transfers, the attack would require accumulating an economically infeasible amount of real value, lowering likelihood substantially. Given this residual uncertainty, treat likelihood as **Medium** pending verification of the fee-population invariant on the EVM host contract.

### Recommendation
- Replace every unchecked `U256` `+=` in `modules/pallets/relayer/src/accumulate.rs` (`validate_results`'s `*entry += fee`, both `Fees::try_mutate` closures in `accumulate`, and `accumulate_fee_and_deposit_event`) with `checked_add` and return/propagate an error (e.g., a new `Error::<T>::FeeOverflow`) instead of panicking on failure.
- Apply the same audit to `Nonce::try_mutate`'s `*value += 1` (lower risk given `u64` width and per-call increments, but should still be `checked_add` for defense in depth) in both `accumulate.rs` and `withdrawal.rs`.
- Independently verify (and, if missing, add) an upper bound on the `fee` field at the point it is written into EVM `RequestCommitments`/dispatch, so a single request cannot carry a fee anywhere near `U256::MAX`.
- Add a regression test that constructs a `WithdrawalProof` whose proven fee, added to an already near-`U256::MAX` `Fees` balance for the same `(state_machine, address)`, exercises the overflow path and asserts a graceful `DispatchError` rather than a panic.

### Proof of Concept
1. Attacker controls (or colludes with) a relayer address `R` and dispatches/relays hyperbridge requests whose on-chain `RequestCommitments` fee field on the EVM source is set to a very large value (bounded only by whatever the EVM host's fee bookkeeping allows — needs confirmation per the Likelihood section, e.g. via a malicious ERC-20 fee token reporting inflated balances, or repeated max-fee requests).
2. `R` delivers the corresponding request to the destination chain, becoming the address recorded in `RequestReceipts[commitment]`.
3. `R` submits `accumulate_fees(withdrawal_proof)` (unsigned) with valid state proofs for the source fee and destination receipt. `validate_results` decodes the fee and does `*entry += fee;` [1](#0-0) , then `accumulate` persists it via `*inner += total_fee;` into `Fees::<T>` [2](#0-1) .
4. Repeating step 1–3 (or batching multiple large-fee commitments into one call so `entry += fee` alone overflows) drives the stored total past `U256::MAX`.
5. The next `+=` on either the local `BTreeMap<Vec<u8>, U256>` entry or the `Fees` storage item panics inside the runtime during that block's execution; every validator re-executing/importing the block hits the identical panic, halting block finalization chain-wide.
