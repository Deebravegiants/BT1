### Title
Escrow accounting in `IntentGatewayV2.placeOrder` trusts declared input amounts instead of verified balance deltas, allowing fee-on-transfer/anomalous tokens to inflate `_orders` beyond actual gateway balance - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
In the Tron `IntentGatewayV2.sol`, `placeOrder`'s non-predispatch escrow path calls `safeTransferFrom` for the user-declared `order.inputs[i].amount` and then credits the escrow ledger `_orders[commitment][token]` with `reducedInputs[i].amount` — a value derived from the *declared* amount, without ever checking how many tokens the gateway actually received. [1](#0-0) 

### Finding Description
The escrow bookkeeping is supposed to represent tokens actually held by the contract. The sibling implementation in `evm/src/apps/IntentGatewayV2.sol` explicitly guards against this by snapshotting balance before/after every transfer and using the observed delta (`order.inputs[i].amount = IERC20(token).balanceOf(address(this)) - balBefore`) both for fee-on-transfer safety and to keep the commitment/escrow consistent with what the gateway actually holds: [2](#0-1) 

The Tron variant of the same function drops this measurement. It performs the raw `safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` and unconditionally increments `_orders[commitment][token] += reducedInputs[i].amount`, where `reducedInputs[i].amount` is computed purely from the caller-supplied `order.inputs[i].amount` minus the protocol fee bps — never from an observed balance change: [3](#0-2) [4](#0-3) 

For any ERC-20 that doesn't deliver exactly the nominal `amount` to the recipient (fee-on-transfer/deflationary tokens, rebasing tokens, or any token exhibiting the "multiple entrypoints" balance-manipulation class called out in the source report), the ledger `_orders[commitment][token]` will be credited for more than the gateway's real token balance actually increased. This directly mirrors the reported bug class: code trusts a caller-supplied/nominal accounting value instead of verifying the real balance effect of a token transfer, which is exactly the flaw that let `VestingEscrow.recoverERC20()` be gamed by tokens with non-standard balance semantics.

The escrow pool (`address(this)` token balance) is shared across all orders/commitments. When `withdraw()` is later invoked via `RedeemEscrow`/`RefundEscrow`, it pays out strictly from `_orders[commitment][token]` accounting: [5](#0-4) 
Since this accounting can be inflated above the real backing balance, an order placed with such a token creates a phantom escrow balance that is redeemable by a filler/solver even though the gateway never actually received it — draining tokens legitimately escrowed by other orders in the shared pool.

### Impact Explanation
This breaks the fundamental accounting invariant that `_orders[commitment][token]` never exceeds real backing balance. A user can place an order with a fee-on-transfer or otherwise-anomalous token, inflate their own escrow ledger entry beyond what the gateway actually holds, and get it filled/settled — its (partly phantom) escrow allotment is then paid out of the shared contract balance, at the expense of other legitimate orders' escrowed tokens. This is a concrete theft/fund-freezing vector reachable via a single unprivileged `placeOrder` transaction.

### Likelihood Explanation
Reachable by any unprivileged user submitting a single `placeOrder` transaction using a token with non-1:1 transfer semantics (fee-on-transfer, rebasing, or a token that exposes "multiple entrypoints" affecting the same balance, as cited in the source report). No governance or privileged role is required to trigger the accounting drift; only a token allow-listing decision governs which tokens are usable, and typical DeFi permissionless token gateways support arbitrary ERC-20s.

### Recommendation
Mirror the fix already present in `evm/src/apps/IntentGatewayV2.sol`: measure `balanceOf(address(this))` immediately before and after each `safeTransferFrom` in the Tron `placeOrder` non-predispatch path, and derive `reducedInputs`/`_orders` credits from the observed delta rather than the caller-declared `order.inputs[i].amount`. Apply the same balance-diff discipline consistently across all token movement paths in this contract (including the predispatch branch, which currently measures `dispatcher` balance but still credits escrow with `reducedInputs[i].amount` rather than the actually swept-in amount minus fee).

### Proof of Concept
1. Governance/deployer allows a fee-on-transfer ERC-20 `FOT` as a valid input token for the Tron `IntentGatewayV2`.
2. Attacker calls `placeOrder` with `order.inputs = [{token: FOT, amount: 1000e18}]` and no predispatch call.
3. `IERC20(FOT).safeTransferFrom(attacker, address(this), 1000e18)` actually delivers, e.g., 990e18 to the gateway (1% fee burned/redirected), matching the `FeeOnTransferToken` test fixture already present in the repo's EVM test suite: [6](#0-5) 
4. Despite only 990e18 landing in the contract, `_orders[commitment][FOT] += reducedInputs[i].amount` credits the full 1000e18 (minus only protocol fee bps, not the transfer-fee loss): [7](#0-6) 
5. Order gets filled/settled cross-chain; `withdraw()` later attempts to pay out the solver/beneficiary based on the inflated `_orders` entry, drawing from the gateway's pooled `FOT` balance — which includes tokens escrowed by other, unrelated orders — resulting in those other orders' escrow being drained short.

/// @dev ERC20 with a configurable transfer fee (in basis points).
contract FeeOnTransferToken {
    string public name = "FeeOnTransferToken";
    string public symbol = "FOT";
    uint8 public decimals = 18;
    uint256 public totalSupply;
    uint256 public feeBps;

    mapping(address => uint256) public balanceOf;
    mapping(address => mapping(address => uint256)) public allowance;

    constructor(uint256 _feeBps) {
        feeBps = _feeBps;
    }

    function mint(address to, uint256 amount) external {
        balanceOf[to] += amount;
        totalSupply += amount;
    }

    function approve(address spender, uint256 amount) external returns (bool) {
        allowance[msg.sender][spender] = amount;
        return true;
    }

    function transfer(address to, uint256 amount) external returns (bool) {
        return _transfer(msg.sender, to, amount);
    }

    function transferFrom(address from, address to, uint256 amount) external returns (bool) {
        uint256 allowed = allowance[from][msg.sender];
        if (allowed != type(uint256).max) {
            allowance[from][msg.sender] = allowed - amount;
        }
        return _transfer(from, to, amount);
    }

    function _transfer(address from, address to, uint256 amount) internal returns (bool) {
        uint256 fee = (amount * feeBps) / 10_000;
        uint256 received = amount - fee;
        balanceOf[from] -= amount;
        balanceOf[to] += received;
        // fee is burned
        totalSupply -= fee;
        return true;
    }
