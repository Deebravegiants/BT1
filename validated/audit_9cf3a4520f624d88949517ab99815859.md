## Title
Reentrancy / CEI violation in `IntentGatewayV2.withdraw` — external transfer executed before escrow ledger is updated - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron deployment of `IntentGatewayV2` still contains the exact check-effects-interactions violation described in the referenced report: the internal `withdraw()` function performs the token/native transfer to the beneficiary **before** decrementing the corresponding escrow balance, instead of decrementing first as the mainline EVM contract now does.

### Finding Description
`withdraw()` in `evm/tron/contracts/apps/IntentGatewayV2.sol` is the settlement path invoked from `onAccept` (for `RedeemEscrow`/`RefundEscrow` POST requests) and `onGetResponse` (for source-chain cancellation). For each escrowed token it does a low-level external call to transfer funds to the beneficiary and only afterwards mutates the `_orders` escrow accounting: [1](#0-0) 

The native-ETH and ERC-20 branches both push value/tokens out via `.call(...)` first, and `_orders[body.commitment][token] -= amount;` runs only after that external call returns. The same pattern repeats for the transaction-fee payout, where `delete _orders[body.commitment][TRANSACTION_FEES]` happens only after the fee token's external `.call`: [2](#0-1) 

The escrowed `token` address is fully attacker-controlled — it is whatever token the order creator specifies as `order.inputs[i].token` at `placeOrder()` time, with no allow-list check: [3](#0-2) 

This means a user can place an order whose "escrowed token" is a contract they author themselves, whose `transfer()` implementation reenters the protocol during the payout call in `withdraw()`, i.e. exactly the same class of bug flagged in the report ("`withdrawToken` doesn't follow the check-effects-interactions pattern").

This is a known/previously-fixed bug class in the same codebase: the canonical EVM `IntentGatewayV2`/`IntentsBase._withdraw` was hardened to decrement escrow (and set `_filled`) **before** any external transfer, and a dedicated regression-test suite exists to prove the fix: [4](#0-3) [5](#0-4) 

The Tron contract (`evm/tron/contracts/apps/IntentGatewayV2.sol`) is a separately maintained copy that was **not** updated with this CEI fix — it still transfers before updating state, and has no `ReentrancyGuard`/`nonReentrant` modifier anywhere in the file (confirmed by grep across the file/directory).

### Impact Explanation
Escrow accounting (`_orders[commitment][token]`) is left stale during the external call window. Because the `token` is user-supplied and unvalidated, a malicious order creator can deploy a token whose `transfer()` hook re-enters the protocol while `_orders[commitment][token]` still reflects the pre-payout balance, creating a window where the escrow ledger is inconsistent with actual balances/transfers already made. This directly threatens the escrowed-funds invariant that the whole Intent Gateway relies on (theft of escrowed input tokens / double-payout on a given commitment/token), the same failure mode called out in the original report and already remediated in the sibling EVM contract.

### Likelihood Explanation
The `_filled[commitment]` flag is set at the top of `withdraw()`, which blocks a trivial re-entry into the *same* `withdraw()` call via `cancelOrder`/direct re-invocation, so exploitability is bounded by how the underlying Tron ISMP host processes deliveries (single vs. batched, and whether the receipt/commitment is consumed strictly before invoking `onAccept`). However, the code itself unconditionally violates checks-effects-interactions on a fund-transferring path with a fully attacker-controlled external contract (the escrow token), which is the precise condition auditors flag as Medium severity even before a full exploit chain through the host is demonstrated — and it is inconsistent with the hardened pattern already adopted elsewhere in this repository for the identical function.

### Recommendation
Apply the same CEI fix used in `evm/src/apps/intentsv2/IntentsBase.sol::_withdraw` to `evm/tron/contracts/apps/IntentGatewayV2.sol::withdraw`: decrement/delete the `_orders` escrow entries (and the `TRANSACTION_FEES` entry) *before* performing the native-value `.call` or token `.call(transfer)`. Additionally consider adding a `nonReentrant` guard consistent with the mainline `IntentGatewayV2` (`ReentrancyGuardTransient`) as defense in depth.

### Proof of Concept
1. Attacker deploys a malicious ERC-20-like contract `EvilToken` whose `transfer(to, amount)` implementation, when invoked by the gateway, attempts to re-enter protocol state (e.g., via any reachable external call path) before returning `true`.
2. Attacker calls `placeOrder()` with `order.inputs[0].token = EvilToken`, escrowing it in `_orders[commitment][EvilToken]`.
3. When the order settles (fill → `RedeemEscrow` on source chain, or cancel → `RefundEscrow`/GET response), `withdraw()` runs the loop in `evm/tron/contracts/apps/IntentGatewayV2.sol` lines 697-714: it calls `EvilToken.call(transfer(beneficiary, amount))` while `_orders[commitment][EvilToken]` is still un-decremented.
4. `EvilToken.transfer()` executes attacker logic during this window, before `_orders[body.commitment][token] -= amount;` runs — violating the escrow invariant the rest of the protocol assumes always holds after a payout. [6](#0-5)
