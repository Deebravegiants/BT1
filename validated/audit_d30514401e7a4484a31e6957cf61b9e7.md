## Analysis

The reported bug class — an externally-callable function that mutates authorization/nonce state without checking that the caller has any relationship to the order it operates on — has a direct analog in Hyperbridge's Intent Gateway solver-selection mechanism. [1](#0-0) 

`IntentGatewayV2.select()` is `public` with no access control, and forwards straight to `_select()`: [2](#0-1) 

`_select()` recovers *some* address from the supplied signature (it never checks that the recovered `sessionKey` equals `order.session`) and then blindly overwrites transient storage keyed only by `options.commitment` — a value that is public (emitted in `OrderPlaced`) and requires no proof of order ownership to supply:

```solidity
function _select(SelectOptions calldata options) internal returns (address) {
    bytes32 structHash = keccak256(abi.encode(SELECT_SOLVER_TYPEHASH, options.commitment, options.solver));
    bytes32 digest = _hashTypedDataV4(structHash);
    address sessionKey = ECDSA.recover(digest, options.signature);
    bytes32 commitment = options.commitment;
    bytes32 selectionHash = keccak256(abi.encode(options.solver, sessionKey));
    assembly { tstore(commitment, selectionHash) }
    return sessionKey;
}
```

`fillOrder()` later trusts whatever is in that transient slot to gate solver authorization: [3](#0-2) 

Because `select()` performs no authentication of the caller and no validation that the recovered key is the genuine session key, any address can overwrite the transient-storage selection record for any order commitment. This is functionally identical to `checkOrder()`/`_useNonce()` in the reported issue: a state-mutating function reachable by anyone, keyed only by public order data, whose side effect invalidates another party's pending authorized action.

### Title
Unauthenticated `select()` lets anyone overwrite another solver's staged authorization, blocking `fillOrder` - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentGatewayV2.select()` is a public function with no access control. It recovers an address from an attacker-supplied signature and unconditionally overwrites the transient-storage slot keyed by `options.commitment` — the same slot `fillOrder()` reads to authorize the caller when `solverSelection` is enabled. An attacker can call `select()` with any order's public commitment and a garbage-but-well-formed signature to overwrite the legitimate solver's staged selection, causing the legitimate solver's subsequent `fillOrder()` call (in the same transaction) to revert with `Unauthorized()`.

### Finding Description
When `solverSelection` is enabled, the intended flow is: a solver's `SolverAccount.validateUserOp()` calls `IntentGatewayV2.select()` to atomically stage `tstore(commitment, keccak256(abi.encode(solver, sessionKey)))`, then `fillOrder()` in the same transaction checks that `msg.sender`/`order.session` reproduce the same hash (`evm/src/apps/IntentGatewayV2.sol:464-472`).

`select()` itself, however, is unauthenticated: [1](#0-0)  and `_select()` does not verify that `ECDSA.recover` returned the *actual* `order.session` key, nor that `msg.sender` (or `options.solver`) has any relation to the order — it simply stores whatever hash results, keyed only by the caller-supplied `commitment`: [2](#0-1) .

Order commitments are public (emitted in `OrderPlaced`), so an attacker can construct a `SelectOptions` struct for any known order commitment, sign the EIP-712 `SelectSolver` struct with a throwaway key they control (a syntactically valid ECDSA signature that recovers to *some* address — it does not need to match the real session key), and call `select()` directly. As long as this call lands in the same top-level transaction as the legitimate solver's `select()`/`fillOrder()` pair — realistic under ERC-4337, since `EntryPoint.handleOps()` batches multiple UserOperations' validation phases before executing any of them, and transient storage (`tstore`/`tload`) is scoped to the whole transaction, not per-call — the attacker's later `select()` call overwrites the victim solver's staged selection hash before `fillOrder()` reads it.

### Impact Explanation
This lets any unprivileged actor grief a solver's legitimate, session-authorized fill by making `fillOrder()` revert with `Unauthorized()` within the shared bundle transaction, wasting the solver's gas/bid and denying settlement of the user's order for that attempt — a denial-of-service on the intent-fill path that the `solverSelection` feature exists specifically to protect. This maps to the "unauthorized app action" / "route unable to deliver" impact class: a party with no relationship to an order can unilaterally invalidate another party's authorized, in-flight fill.

### Likelihood Explanation
Likelihood is moderate-to-high in any deployment with `solverSelection` enabled: order commitments are public on-chain data (from `OrderPlaced`), `select()` requires no special permission or proof of relation to the order, and any valid-format ECDSA signature (trivially self-generated) satisfies `_select()`'s only check (`ECDSA.recover` not reverting). The main constraint is landing the call in the same transaction as the target `select`/`fillOrder` pair, which is a normal occurrence for bundled ERC-4337 operations submitted through a shared or malicious bundler.

### Recommendation
`_select()` should verify that the recovered `sessionKey` matches the target order's actual `order.session` (requiring the order to be passed in, or its hash bound to a value the contract can check) before writing to transient storage, and/or should only allow the write when `msg.sender` is the address about to be authorized (`options.solver`) so an unrelated third party cannot stage or clobber a selection for a commitment it does not control. At minimum, add a check that no unrelated `select()` call can silently overwrite an already-staged, still-unread selection for the same commitment within the same transaction.

### Proof of Concept
1. Attacker observes `OrderPlaced` for `order` (commitment `C`), with `solverSelection` enabled and `order.session` set to the user's session key.
2. Legitimate solver `S` gets authorized off-chain by the user (EIP-712 `SelectSolver(C, S)` signed by the real session key) and submits a UserOperation bundling `select({commitment: C, solver: S, signature: realSessionSig})` (in `validateUserOp`) followed by `fillOrder(order, ...)` (in execution).
3. Attacker submits a second UserOperation in the same bundle (e.g., via the same or a colluding bundler) that calls `select({commitment: C, solver: attackerAddr, signature: attackerSelfSignedSig})`, where `attackerSelfSignedSig` is any valid-format ECDSA signature the attacker produces with a key they control.
4. `EntryPoint.handleOps()` runs all `validateUserOp` calls first: `S`'s `select()` stores the correct hash, then the attacker's `select()` overwrites `tstore(C, ...)` with `keccak256(abi.encode(attackerAddr, recoveredGarbageKey))`.
5. In the execution phase, `S`'s `fillOrder(order, ...)` recomputes `expectedSelectionHash = keccak256(abi.encode(S, order.session))`, which no longer matches the corrupted `tload(C)`, and reverts with `Unauthorized()` — `evm/src/apps/IntentGatewayV2.sol:464-472`.
