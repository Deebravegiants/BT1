## Title
Unchecked `U128` → `u64` truncation in `swap_token_amount_base_out` lets a swapper drain the pool via `SwapBaseOut`/`SwapBaseOutV2` - (File: `program/src/math.rs`, `program/src/processor.rs`)

### Summary
`Calculator::swap_token_amount_base_out` computes the required input amount as a `U128` and the caller converts it to `u64` with the unchecked `.as_u64()` method instead of the checked `Calculator::to_u64()`. `.as_u64()` (from the `uint::construct_uint!` macro used to define `U128`/`U256`) silently returns only the low 64 bits of the value — it does not error or saturate on overflow, exactly like the unguarded `uint88(...)` downcast in the Sherlock `CollectionShutdown` report. An attacker who requests an `amount_out` close to the pool's total reserve can make the computed required input balloon past `u64::MAX`, get silently truncated to an arbitrarily small `u64`, pass all slippage/balance checks, and receive almost the entire pool reserve while paying almost nothing.

### Finding Description
`swap_token_amount_base_out` (used for the `Coin2PC` and `PC2Coin` "buy exact output" direction) is: [1](#0-0) 

For example, in the `Coin2PC` branch:
```
let denominator = total_pc_without_take_pnl.checked_sub(amount_out).unwrap();
amount_in = total_coin_without_take_pnl.checked_mul(amount_out).unwrap().checked_ceil_div(denominator).unwrap();
```
`amount_out` and `total_coin_without_take_pnl` are both derived from `u64` pool amounts, so `amount_in` is a `U128` value with no inherent bound — as `amount_out` approaches `total_pc_without_take_pnl`, `denominator` shrinks toward `1`, and `amount_in` can grow to roughly `total_coin_without_take_pnl * amount_out`, which easily exceeds `u64::MAX` (~1.8×10¹⁹) for realistic reserve sizes, while still comfortably fitting in `U128` (max ~3.4×10³⁸), so none of the `checked_mul`/`checked_ceil_div` calls panic.

The caller in `process_swap_base_out` then converts this oversized `U128` straight to `u64` via `.as_u64()` with no range check: [2](#0-1) 

`process_swap_base_out_v2` repeats the identical pattern: [3](#0-2) 

Because `U128`/`U256` are generated by `uint::construct_uint!`, `.as_u64()` simply returns the low 64 bits of the internal limb array — it truncates silently instead of erroring, unlike `Calculator::to_u64()` which uses `TryInto` and returns `AmmError::ConversionFailure` on overflow: [4](#0-3) [5](#0-4) 

The truncated `swap_in_after_add_fee` is then used for both the slippage/balance checks and the actual transfer: [6](#0-5) 
Since the check is against the truncated (small) value, `user_source.amount < swap_in_after_add_fee` and `swap.max_amount_in < swap_in_after_add_fee` both trivially pass, and the vault only receives the truncated tiny deposit while paying out the full attacker-chosen `swap.amount_out` from the vault: [7](#0-6) 

This is directly analogous to the `CollectionShutdown` bug class: a value that legitimately requires a wider type is downcast without a bounds check, producing a value far smaller than the true amount, and that undersized value is subsequently used to compute what the caller must pay.

### Impact Explanation
An attacker can call `SwapBaseIn`... actually `SwapBaseOut`/`SwapBaseOutV2` with a crafted `amount_out` just below `total_pc_without_take_pnl` (or `total_coin_without_take_pnl` for the other direction) so that the true required input overflows `u64` by design. The resulting `swap_in_after_add_fee` wraps to a small/attacker-influenced value, letting the attacker pay a negligible amount while draining nearly the entire opposite-side reserve of the pool from the AMM vault in a single transaction. This is a critical, unbounded theft of LP/user funds from `amm_coin_vault`/`amm_pc_vault`, reachable by any unprivileged swapper with `SwapBaseOut`/`SwapBaseOutV2` and attacker-chosen `amount_out`/`max_amount_in`.

### Likelihood Explanation
The attacker only needs to (1) know the current pool reserves (public on-chain data), (2) pick `amount_out` close to (but below) the opposing reserve so the denominator in `swap_token_amount_base_out` is minimal, and (3) precompute off-chain the exact truncated `u64` result to guarantee the resulting `swap_in_after_add_fee` is affordable and under `max_amount_in`. This is a deterministic, fully client-side computation requiring a single transaction with attacker-chosen instruction data and standard swap accounts — no privileged signer or special conditions are required, only sufficiently large pool reserves (large token supply / low decimal, which is common for many SPL tokens).

### Recommendation
Replace the unchecked `.as_u64()` conversions after `swap_token_amount_base_out` (and any other place converting a `U128`/`U256` swap-math result to `u64`) with the existing checked helper `Calculator::to_u64()`, which returns `AmmError::ConversionFailure` instead of silently truncating, and propagate that error to reject the swap.

### Proof of Concept
Conceptually:
1. Pool has `total_coin_without_take_pnl = C`, `total_pc_without_take_pnl = P` (both large `u64` reserve values, e.g. on the order of 10^15+, realistic for high-supply/low-decimal SPL tokens).
2. Attacker calls `SwapBaseOut` (Coin2PC direction) with `amount_out = P - 1` (just under the full pc reserve) and `max_amount_in = u64::MAX` (or the attacker's actual balance).
3. In `swap_token_amount_base_out`, `denominator = P - (P-1) = 1`, so `amount_in ≈ C * (P-1)`, which for realistic `C, P` values vastly exceeds `u64::MAX`.
4. After scaling by fee numerator/denominator, `.as_u64()` truncates this oversized `U128` to `swap_in_after_add_fee = (true_amount_in) mod 2^64`, an attacker-predictable small value (attacker can iterate `amount_out` off-chain to find a value making the truncated result minimal, e.g. near 0).
5. Checks `user_source.amount < swap_in_after_add_fee` and `swap.max_amount_in < swap_in_after_add_fee` both pass trivially.
6. `Invokers::token_transfer` moves only the tiny truncated `swap_in_after_add_fee` from the attacker into `amm_coin_vault`, while `Invokers::token_transfer_with_authority` pays out the full `swap.amount_out ≈ P - 1` from `amm_pc_vault` to the attacker — draining almost the entire pc reserve for near-zero cost. ```rust
    pub fn swap_token_amount_base_out(
        amount_out: U128,
        total_pc_without_take_pnl: U128,
        total_coin_without_take_pnl: U128,
        swap_direction: SwapDirection,
    ) -> U128 {
        let amount_in;
        match swap_direction {
            SwapDirection::Coin2PC => {
                // (x + delta_x) * (y + delta_y) = x * y
                // (coin + amount_in) * (pc - amount_out) = coin * pc
                // => amount_in = coin * pc / (pc - amount_out) - coin
                // => amount_in = (coin * pc - pc * coin + amount_out * coin) / (pc - amount_out)
                // => amount_in = (amount_out * coin) / (pc - amount_out)
                let denominator = total_pc_without_take_pnl.checked_sub(amount_out).unwrap();
                amount_in = total_coin_without_take_pnl
                    .checked_mul(amount_out)
                    .unwrap()
                    .checked_ceil_div(denominator)
                    .unwrap()
            }
            SwapDirection::PC2Coin => {
                // (x + delta_x) * (y + delta_y) = x * y
                // (pc + amount_in) * (coin - amount_out) = coin * pc
                // => amount_out = coin - coin * pc / (pc + amount_in)
                // => amount_out = (coin * pc + coin * amount_in - coin * pc) / (pc + amount_in)
                // => amount_out = coin * amount_in / (pc + amount_in)

                // => amount_in = coin * pc / (coin - amount_out) - pc
                // => amount_in = (coin * pc - pc * coin + pc * amount_out) / (coin - amount_out)
                // => amount_in = (pc * amount_out) / (coin - amount_out)
                let denominator = total_coin_without_take_pnl.checked_sub(amount_out).unwrap();
                amount_in = total_pc_without_take_pnl
                    .checked_mul(amount_out)
                    .unwrap()
                    .checked_ceil_div(denominator)
                    .unwrap()
            }
        }
        return amount_in;
    }
