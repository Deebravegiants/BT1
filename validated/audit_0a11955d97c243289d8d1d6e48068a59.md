Confirmed: the `shop` field delivered to the app's `WebhookHandler#handle` (via `WebhookMetadata#shop`) originates purely from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, and the HMAC signature only covers `@raw_body`.### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) identity headers are trusted without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop` field solely from the unauthenticated `x-shopify-shop-domain` HTTP header, while the HMAC signature validated by `HmacValidator.validate` is computed only over the raw request body via `to_signable_string`. The header used to route/attribute the webhook to a specific merchant is never part of the signed material, breaking the identity binding: `shop header value == authenticated tenant`.

### Finding Description
`Request#to_signable_string` returns `@raw_body` only [1](#0-0) , and `HmacValidator.validate_signature` computes/compares the HMAC exclusively against that signable string [2](#0-1) . Meanwhile, `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all read straight from HTTP headers, none of which are part of the signed payload [3](#0-2) .

`Registry.process` only checks `Utils::HmacValidator.validate(request)` and then forwards `request.shop`, `request.topic`, and `request.webhook_id` — all header-derived, unsigned values — directly into `WebhookMetadata` passed to the host app's handler [4](#0-3) . `WebhookMetadata#shop` is a plain `String` field with no further verification [5](#0-4) .

This is exactly the "field acted on but not covered by the HMAC" class from the report: the equality that should hold is `signed_bytes == (body || shop_header)`, but in reality only `signed_bytes == body`. A user with a legitimate Shopify store (any unprivileged internet user who installs any Shopify app and thus can trigger webhooks for their own shop) receives genuine, validly-signed `(raw_body, hmac)` pairs from Shopify for their own store. Because the `x-shopify-shop-domain` header is not part of the signed material, that attacker can replay the same `raw_body`/`hmac` pair to the host app's webhook endpoint while substituting an arbitrary victim shop domain in the header. `HmacValidator.validate` still succeeds (it only checks the body), and `Registry.process` hands the handler a `WebhookMetadata` claiming the event belongs to the victim shop.

### Impact Explanation
This breaks the shop/tenant identity binding at a Critical level: cross-tenant confusion. Any host application that relies on `WebhookMetadata#shop` (as returned by this gem, which is the documented/only way to identify the originating shop for a webhook) to select the tenant's session/data context will process a forged event as belonging to another merchant. Because attribution of the webhook body to a shop is entirely unauthenticated, an attacker can inject spoofed data (e.g., replay their own store's `orders/create` payload) under a victim shop's identity, corrupting per-tenant state or triggering tenant-scoped side effects (data writes, notifications, GDPR-mandatory webhook handling such as `shop/redact`/`customers/redact`/`customers/data_request`) attributed to the wrong merchant.

### Likelihood Explanation
High. No privileged credentials, leaked secrets, or social engineering are required. An unprivileged attacker only needs their own (or any) legitimate Shopify shop capable of triggering webhook delivery for an app they control — a normal, unauthenticated capability of any merchant/app developer — to obtain a valid `(raw_body, hmac)` pair, then replay it against the target app's public webhook endpoint with a modified `shop` header.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`/`api_version`) header values into the HMAC-signed material, or otherwise verify them independently of the header (e.g., include them in `to_signable_string`, or require the host app to cross-check the header shop domain against a known/installed shop record before trusting it). At minimum, document that `WebhookMetadata#shop` is unauthenticated and must not be used as a sole tenant-identity source without additional verification.

### Proof of Concept
1. Attacker installs the vulnerable app on their own shop `attacker.myshopify.com` and triggers a webhook (e.g., `orders/create`), capturing the genuine `raw_body` and its valid `x-shopify-hmac-sha256` value computed by Shopify with the app's `api_secret_key`.
2. Attacker replays an HTTP POST to the app's webhook endpoint with the identical `raw_body`/`hmac` header, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged header successfully [6](#0-5) .
4. `Utils::HmacValidator.validate(request)` returns `true` because it only re-hashes `@raw_body` [7](#0-6) .
5. `Registry.process` invokes the handler with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: ..., ...)` [8](#0-7) , and the host app processes attacker-controlled data as if it originated from the victim's store.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
