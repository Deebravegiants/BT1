### Title
V1 transactions with unset `compute_unit_limit` default to 0 instead of the SIMD per-instruction default, unlike Legacy/V0 - ([File: runtime-transaction/src/transaction_meta.rs])

### Summary
`VersionedTransactionConfiguration::from_v1_config` and `from_sanitized_transaction_view` derive a V1 transaction's `compute_unit_limit` via `config.compute_unit_limit.unwrap_or(0)`, while the Legacy/V0 path computes an equivalent default through `ComputeBudgetInstructionDetails::calculate_default_compute_unit_limit`, which is strictly positive and scales with instruction count. The V1 conversion path (`try_into_config`) only clamps the value to `MAX_COMPUTE_UNIT_LIMIT` and never applies a floor, so a V1 message that omits `compute_unit_limit` ends up with a final `compute_unit_limit` of `0`, whereas a semantically identical Legacy/V0 message gets a non-zero, instruction-count-scaled default.

### Finding Description
Two independent code paths compute the same logical quantity differently for V1 vs Legacy/V0 messages:

- V1: `transaction_view.rs::from_sanitized_transaction_view` (used by `RuntimeTransaction<SanitizedTransactionView>::try_new`) reads `transaction_config_view.compute_unit_limit().unwrap_or(0)` [1](#0-0) . The parallel `from_v1_config` helper does the same `.unwrap_or(0)` [2](#0-1) .
- Legacy/V0: `try_from_legacy_and_v0_instructions` builds a `ComputeBudgetInstructionDetails` from the instruction list, and when the transaction does not carry a `SetComputeUnitLimit` compute-budget instruction, `sanitize_and_convert_to_compute_budget_limits` falls back to `calculate_default_compute_unit_limit`, which sums `DEFAULT_INSTRUCTION_COMPUTE_UNIT_LIMIT` per non-compute-budget instruction (plus builtin allocation costs) [3](#0-2) [4](#0-3) .
- Finally, `VersionedTransactionConfiguration::try_into_config` handles the two variants asymmetrically: the `LegacyAndV0` branch calls `sanitize_and_convert_to_compute_budget_limits` (which applies the positive default above), while the `V1` branch simply does `transaction_configuration.compute_unit_limit.min(MAX_COMPUTE_UNIT_LIMIT)` — no minimum/default is ever applied for V1 [5](#0-4) .

An unprivileged attacker can craft a V1 message (`solana_message::v1::Message`, whose `TransactionConfig.compute_unit_limit` is an `Option<u32>`) and simply omit that field. Nothing in `ResolvedTransactionView`/`SanitizedTransactionView` sanitization rejects a V1 transaction for leaving `compute_unit_limit` unset — the field is legitimately optional per the message format, and `try_into_config` treats "unset" (0) as a valid, final value rather than triggering a default. The result is a `TransactionConfiguration.compute_unit_limit == 0` used downstream for cost estimation and CU metering, whereas the same instruction sequence sent as a Legacy or V0 message produces a positive default limit proportional to the number of instructions.

### Impact Explanation
This is a real divergence in a security-critical invariant: the same logical transaction (same instructions, same accounts) produces a materially different, and for V1 unset-limit case, a degenerate `compute_unit_limit` of `0` purely due to message version, not because the attacker requested a low limit. Since `compute_unit_limit` feeds both the cost-model estimate (used for block cost limits / cost tracking) and the actual compute meter initialization used during execution, this breaks the invariant "cost-model estimates deterministically upper-bound real work regardless of message version." A `compute_unit_limit` of `0` is accounted by the cost model as essentially free, while the validator still performs real, non-zero work (signature verification, account/ALT resolution, entering the loader) before the transaction fails on the first CU charge — i.e. real resource consumption is not reflected in the value the cost/fee subsystems rely on. This falls into the "materially underpriced execution / cost-model bypass" bounty category rather than a fund-theft bug, since the transaction itself will fail execution once compute is actually charged.

### Likelihood Explanation
Trivially reachable: any unprivileged user constructing and signing a `VersionedMessage::V1` transaction where `TransactionConfig.compute_unit_limit` is `None` triggers this path unconditionally through `RuntimeTransaction<SanitizedTransactionView>::try_new -> from_sanitized_transaction_view`, and later through `TransactionConfiguration::try_from_sanitized_message -> VersionedTransactionConfiguration::from_v1_config -> try_into_config`. No signature, lock, nonce, or sanitize-failure guard currently rejects an unset `compute_unit_limit` in a V1 message, and no code path applies a default/minimum for the V1 branch as it does for Legacy/V0.

### Recommendation
Apply an equivalent default-computation for the V1 branch of `try_into_config` (and/or `from_v1_config`/`from_sanitized_transaction_view`) when `compute_unit_limit` is unset — e.g., compute the same per-instruction default (`DEFAULT_INSTRUCTION_COMPUTE_UNIT_LIMIT` × instruction count plus builtin allocation) used by `ComputeBudgetInstructionDetails::calculate_default_compute_unit_limit`, rather than defaulting to `0`. At minimum, enforce a non-zero floor consistent with the Legacy/V0 path so cost-model and CU-metering behavior is deterministic and version-independent.

### Proof of Concept
```rust
// runtime-transaction/src/transaction_meta.rs (add to existing #[cfg(test)] mod tests)
#[test]
fn test_v1_unset_compute_unit_limit_diverges_from_legacy_default() {
    let feature_set = FeatureSet::all_enabled();

    // Legacy/V0 equivalent: N "real" instructions, no compute-budget instructions.
    let num_instructions = 3u16;
    let legacy_details = ComputeBudgetInstructionDetails {
        num_non_compute_budget_instructions: Saturating(num_instructions),
        num_non_builtin_instructions: Saturating(num_instructions),
        ..ComputeBudgetInstructionDetails::default()
    };
    let legacy_config = VersionedTransactionConfiguration::LegacyAndV0(legacy_details)
        .try_into_config(&feature_set)
        .unwrap();

    // V1 equivalent: same instruction count, but compute_unit_limit left unset (None -> 0).
    let v1_input = TransactionConfiguration {
        updated_heap_bytes: HEAP_LENGTH as u32,
        compute_unit_limit: 0, // as produced by `.unwrap_or(0)` when V1 field is None
        priority_fee_lamports: 0,
        loaded_accounts_data_size_limit: 0,
    };
    let v1_config = VersionedTransactionConfiguration::V1(v1_input)
        .try_into_config(&feature_set)
        .unwrap();

    // Legacy path yields a positive, instruction-scaled default.
    assert!(legacy_config.compute_unit_limit > 0);
    // V1 path yields exactly zero for the semantically identical transaction.
    assert_eq!(v1_config.compute_unit_limit, 0);
    // Divergence: same logical transaction, different cost-model/CU-metering outcome.
    assert_ne!(legacy_config.compute_unit_limit, v1_config.compute_unit_limit);
}
```
Expected result on current code: the assertions pass, demonstrating that a V1 transaction omitting `compute_unit_limit` receives `compute_unit_limit == 0` while an equivalent Legacy/V0 transaction receives a strictly positive default — confirming the version-dependent divergence in cost/CU accounting described above.

    fn calculate_default_compute_unit_limit(&self, feature_set: &FeatureSet) -> u32 {
        // evaluate if any builtin has migrated with feature_set
        let (num_migrated, num_not_migrated) = self
            .migrating_builtin_feature_counters
            .migrating_builtin
            .iter()
            .enumerate()
            .fold((0, 0), |(migrated, not_migrated), (index, count)| {
                if count.0 > 0 && feature_set.is_active(get_migration_feature_id(index)) {
                    (migrated + count.0, not_migrated)
                } else {
                    (migrated, not_migrated + count.0)
                }
            });

        u32::from(self.num_non_migratable_builtin_instructions.0)
            .saturating_add(u32::from(num_not_migrated))
            .saturating_mul(MAX_BUILTIN_ALLOCATION_COMPUTE_UNIT_LIMIT)
            .saturating_add(
                u32::from(self.num_non_builtin_instructions.0)
                    .saturating_add(u32::from(num_migrated))
                    .saturating_mul(DEFAULT_INSTRUCTION_COMPUTE_UNIT_LIMIT),
            )
    }
