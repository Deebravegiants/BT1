### Title
Attacker-controlled route payload executes arbitrary contract calls under the victim's authorization, enabling wallet draining - ([File: contracts/swap-aggregator/src/lib.rs])

### Summary
The swap router accepts a fully caller-supplied `swap_xdr` payload whose hop records name arbitrary `pool`/`token` contract addresses. The router invokes those addresses with `env.invoke_contract` while the sender's `require_auth` tree is still open. A malicious pool contract invoked this way can issue `token.transfer(victim, attacker, amount)` calls that attach as children of the victim's signed authorization — the on-chain analog of a crafted deeplink that installs an attacker-controlled component and gets code execution under the user's one-click confirmation.

### Finding Description
`execute_strategy(sender, total_in, swap_xdr)` is a permissionless entrypoint gated only by `sender.require_auth()` [1](#0-0) . The payload's instructions carry venue enum, `pool` address, `token_in`, and `token_out` per hop, all resolved from caller-controlled `assets` registry indices [2](#0-1) . The router keeps no allowlist of pools or tokens: `dispatch_hop` calls whatever address the payload names [3](#0-2) .

Inside the hop, the invoked pool contract runs below the caller's auth frame. The codebase's own adversarial test `RogueHopPool` shows the concretely exploitable path: the pool's `swap` function executes `token::Client::transfer(victim, attacker, amount)` on an arbitrary token the protocol never listed, and the host attaches that transfer to the caller's signed authorization tree [4](#0-3) . The same shape is reachable through the lending controller's strategy verbs (`multiply`, `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`), which forward a caller-supplied `swap` payload to the configured router [5](#0-4) . The threat model itself confirms that if the victim signs the tree, the transfer executes and the loss is the victim's whole wallet balance, unbounded by `total_min_out` or the final risk gate [6](#0-5) .

### Impact Explanation
Theft of user funds beyond the routed amount. A crafted route delivered to a victim (phishing quote, compromised frontend, malicious deeplink-style URL) causes the router to call an attacker contract that drains any token the victim holds, limited only by what the victim's signed auth tree covers. Simulation in recording mode auto-populates these child invocations into the proposed auth entries, so a wallet that presents only the top-level call for confirmation reproduces the one-click-install scenario: the victim sees `execute_strategy`, signs, and the rogue hop rides the signature.

### Likelihood Explanation
Requires the victim to sign a malicious payload — matching the report's "UI:R" precondition. Any unprivileged attacker can deploy the rogue pool contract and craft the `swap_xdr`; no privileged role, leaked key, or off-chain access is needed. The measured-delta checks (`ZeroOutput`, `InvalidAmount`, `SlippageExceeded`) only validate the router's own balances and do not restrict what the invoked pool does with the ambient authorization [7](#0-6) . Severity is tempered to High because exploitation depends on the victim signing an auth tree that contains the unexpected child invocation; a vigilant client can reject it.

### Recommendation
Constrain hops to governance-registered venue/pool addresses (allowlist keyed in router storage), or at minimum to pools whose code hash is a known DEX Wasm hash. Additionally, the controller could verify post-swap that the authorization footprint produced no child transfers outside the declared input leg, and document/enforce in the SDK that any auth tree containing children beyond the single `token_in` transfer must be refused.

### Proof of Concept
The repo contains the working exploit harness in `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`: `UnlistedPoolRouter.execute_strategy` pulls the input, invokes the payload-named `hop_pool`, and `RogueHopPool.swap` transfers the victim's unrelated `wallet_token` balance to the attacker [8](#0-7) . The test pins that in recording mode the rogue `transfer` attaches to the caller's auth entry, and in enforcing mode it succeeds when signed [9](#0-8) . To reproduce against the real router: register a malicious contract exposing a `swap`-like entrypoint, encode a `StrategyPayload` whose hop `pool` index resolves to it and whose `token_in`/`token_out` are honest listed assets, then have the victim call `controller.swap_collateral` (or `router.execute_strategy` directly) with that payload — the rogue contract's internal `token.transfer(victim, attacker, victim_balance)` executes under the victim's authorization while the router's own balance-delta checks still pass because the route's declared hop can be satisfied honestly or padded via attacker-provided liquidity.

## Authorization model

The only signature is the sender's. `execute_strategy` calls `sender.require_auth()`, and the sender's auth entry must cover the nested `token_in.transfer(sender, router, total_in)`; simulation produces that tree (`transaction.simulated = true` envelopes already carry it — `attach_simulated_transaction` copies the simulator's `auth` into the op — and `simulateTransaction` produces it for a locally built one). Do **not** `transfer` or `approve` tokens to the router beforehand: the router pulls the input itself, and tokens sent ahead of time are not credited.

Every venue call is self-authorized by the router with invoker-contract auth (`venues/auth.rs::authorize_as_current` → `env.authorize_as_current_contract`): Phoenix and Sushi (`HopContext::authorize_pool_pull`) and Aquarius (`aquarius/pool.rs::invoke_pool_swap`) register `token_in.transfer(router, pool, amount_in)` before the pool pulls; Comet registers `token_in.approve(router, pool, amount_in, expiry)`, then `swap_exact_amount_in` with a nested entry for the pool's `transfer_from`, then clears the allowance; Soroswap transfers from the router to the pool directly. None of these appear in the sender's auth tree.

A contract calling the router (the lending controller in `contracts/controller/src/strategies/swap.rs`, or your own) is the `sender`: it runs `authorize_transfer_as_current(token_in, self, router, amount_in)` (`common/src/token.rs`) immediately before `execute_strategy(self, amount_in, swap)` and measures its own balance deltas afterward (`RouterOverspend = 501`, `NoSwapOutput = 502` in `common/src/errors.rs`). Details in [composition.md](composition.md).

    pub fn execute_strategy(env: Env, sender: Address, total_in: i128, swap_xdr: Bytes) -> i128 {
        sender.require_auth();
        let route = RoutedSwap::from_xdr(&env, &swap_xdr).expect("route must decode");
        let router = env.current_contract_address();
        token::Client::new(&env, &route.token_in).transfer(&sender, &router, &total_in);
        let _: Val = env.invoke_contract(&route.hop_pool, &symbol_short!("swap"), vec![&env]);
        token::Client::new(&env, &route.token_out).transfer(&router, &sender, &route.min_out);
        route.min_out
    }
}

/// Attacker-deployed "pool". `amount == 0` is the benign control.
#[contract]
pub struct RogueHopPool;

#[contractimpl]
impl RogueHopPool {
    pub fn __constructor(env: Env, victim: Address, token: Address, to: Address, amount: i128) {
        env.storage()
            .instance()
            .set(&symbol_short!("PLAN"), &(victim, token, to, amount));
    }

    pub fn swap(env: Env) {
        let (victim, wallet_token, to, amount): (Address, Address, Address, i128) = env
            .storage()
            .instance()
            .get(&symbol_short!("PLAN"))
            .expect("plan is set by the constructor");
        if amount > 0 {
            token::Client::new(&env, &wallet_token).transfer(&victim, &to, &amount);
        }
    }
}
