### Title
Webhook shop-domain (and topic/webhook-id) identity headers are not covered by the HMAC signature, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`), `topic`, and `webhook_id` from HTTP headers that are never part of the HMAC-signed material. Only the raw body is signed. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then hands `request.shop` — an unauthenticated header — straight to the app's handler as the trusted tenant identifier.

### Finding Description
The `Request` class mixes in `Utils::VerifiableQuery` and defines the signable string as the raw body only: [1](#0-0) 

But `shop`, `topic`, and `webhook_id` — the fields used to route and attribute the webhook to a tenant — are read from separate, unsigned headers: [2](#0-1) 

`HmacValidator.validate` only checks `hmac` against `to_signable_string` (the body), never incorporating the shop/topic/webhook-id headers into the signature computation: [3](#0-2) 

`Registry.process` validates only that HMAC, then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` as authenticated identity data passed to the app-supplied handler: [4](#0-3) 

The identity binding this breaks, stated as an equality that should hold but does not:
`HMAC(secret, signable_string)` should equal `HMAC(secret, signable_string ⊕ shop ⊕ topic ⊕ webhook_id)`, but in this code `signable_string == raw_body` only. Consequently, `shop` (and `topic`/`webhook_id`) can be swapped by anyone who can produce a request with a *valid* HMAC/body pair for any tenant (e.g., a previously-observed legitimate webhook delivery, which is not confidential — bodies are often logged, proxied through third-party queues, or visible in shared infrastructure) and can still supply arbitrary `shop-domain` headers, since that header plays no role in the signature check.

Before the attacker's request: `computed_hmac(body) == received_hmac` is verified for the exact tuple Shopify sent (correct body, correct shop header).
After the attacker's request: the same `(body, hmac)` pair is replayed with a different `shop-domain` header; `computed_hmac(body) == received_hmac` still holds, and `Registry.process` still calls the handler, now attributing that body's data (`data.body`) to a different `data.shop` than Shopify actually associated it with.

### Impact Explanation
This crosses a tenant boundary: an app whose handler uses `data.shop` to key data storage, authorization, or side effects (as the gem's own documentation recommends: `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) can be made to attribute one merchant's webhook payload to a different merchant's shop identifier while the HMAC still validates. This is a cross-tenant data confusion vector reachable purely by an unprivileged party capable of delivering an HTTP request to the app's public webhook endpoint with a previously-seen valid `(body, hmac)` pair and an arbitrary `shop-domain` header — no `api_secret_key` or credentials are required by the attacker.

### Likelihood Explanation
Requires the attacker to possess at least one valid `(raw_body, hmac)` pair, which is plausible since webhook bodies/HMACs are not treated as secrets by Shopify or many app integrations (they pass through logs, third-party relay services, browser dev tools during testing, etc.), and requires only that the target app's public webhook callback endpoint is reachable, which it is by design.

### Recommendation
Bind the tenant/topic identity into the signed material, or otherwise cryptographically tie the `shop-domain`, `topic`, and `webhook-id` headers to the HMAC verification — e.g., include these header values in the string that is HMAC-verified (this would require a corresponding change on Shopify's signing side), or, at minimum, require the app to independently confirm the `shop-domain` belongs to a known, previously-installed session/tenant before trusting `data.shop` for any authorization decision, and document this gap prominently since the gem's own example code passes `data.shop` through unchecked.

### Proof of Concept
```ruby
# Attacker has observed (or replays) one legitimate webhook delivery for shop-a.myshopify.com:
raw_body = '{"id":1,"note":"hello"}'
hmac_b64 = "VALID_HMAC_FOR_ABOVE_BODY_BASE64" # captured from a real Shopify delivery

# Attacker crafts a new request with the SAME body+hmac but a DIFFERENT shop header:
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => hmac_b64,
  "x-shopify-shop-domain" => "victim-shop-b.myshopify.com", # arbitrary, attacker controlled
  "x-shopify-webhook-id" => "attacker-chosen-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# HmacValidator.validate(request) succeeds because it only checks HMAC(raw_body),
# and the handler receives WebhookMetadata with shop: "victim-shop-b.myshopify.com"
# even though the body/HMAC pair actually belonged to shop-a.
```

Note: I could not fully verify how downstream consumers (e.g., `ShopifyApp` gem or typical integrator code) use `data.shop` for authorization decisions, since that logic lives outside this gem's `lib/shopify_api/**` scope; the above analysis is confined to what this gem itself validates and passes through.
