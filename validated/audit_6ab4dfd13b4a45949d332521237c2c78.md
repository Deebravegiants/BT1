### Title
Unsynchronized concurrent map access on `authorizedKeys` in `WorkflowMetadataHandler.Authorize` causes data race / crash reachable from unprivileged gateway requests - ([File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go])

### Summary
`WorkflowMetadataHandler.Authorize` reads the `h.authorizedKeys` map without holding `h.mu`, while the background `syncMetadata` goroutine periodically replaces the same map under `h.mu.Lock()`. This is the same bug class as the hashconsing advisory: shared mutable state accessed from multiple goroutines without the synchronization the Go memory model requires, leading to undefined behavior (in Go, concurrent unsynchronized map read/write is detected at runtime and crashes the process, or can corrupt map internals under race conditions).

### Finding Description
`Authorize` is invoked per incoming JSON-RPC HTTP-trigger request (an unprivileged, internet-facing gateway request path) and reads the shared field directly: [1](#0-0) 

Note the absence of `h.mu.RLock()`/`RUnlock()` around the read of `h.authorizedKeys[workflowID]` at line 92, unlike every other accessor on this struct (`WorkflowShards`, `GetWorkflowID`, `GetWorkflowReference`), which all correctly take `h.mu.RLock()`: [2](#0-1) [3](#0-2) 

Meanwhile, a background ticker goroutine started in `Start` invokes `syncMetadata` on a fixed period (`MetadataAggregationIntervalMs`), which replaces the entire `authorizedKeys` map under `h.mu.Lock()`: [4](#0-3) [5](#0-4) 

Because `Authorize`'s map read at line 92 is unguarded, any concurrent execution of `syncMetadata`'s write (`h.authorizedKeys = authorizedKeys` at line 178, plus the associated internal map mutation while building the new map) while a client's `Authorize` call is reading the old map reference constitutes a classic unsynchronized concurrent map access. Go's runtime race detector treats this as a data race, and in production (without `-race`) concurrent map access of this kind reliably triggers `fatal error: concurrent map read and map write`, which is unrecoverable and crashes the whole process — this is the direct Go-runtime analog of the CWE-662/CWE-787 "shared data structure accessed without proper synchronization → undefined behavior/memory corruption" pattern described in the hashconsing advisory.

### Impact Explanation
An unprivileged actor can trigger this race merely by sending ordinary HTTP-trigger workflow requests to the gateway at the moment `syncMetadata`'s periodic sync (which is entirely internal/automatic, not attacker-controlled) is running. Because the metadata sync runs on every configured `MetadataAggregationIntervalMs` tick for the lifetime of the gateway process, any client (no special authorization needed — this races before authorization even succeeds) can eventually hit the race window and crash the gateway node process (`fatal error: concurrent map read and map write` is fatal and not recoverable by `recover()`), producing a denial of service. This is a High-severity availability impact on the internet-facing gateway.

### Likelihood Explanation
Likelihood is high given sufficient request volume: `syncMetadata` runs on a fixed timer for the entire process lifetime, and `Authorize` is called on every single unauthenticated inbound gateway request for this handler type (JWT verification happens first, but the vulnerable map read occurs before the request is otherwise authorized/rejected). A moderate rate of requests from any external client is enough to statistically hit the race window repeatedly over time.

### Recommendation
Add `h.mu.RLock()` / `defer h.mu.RUnlock()` around the read of `h.authorizedKeys` in `Authorize` (mirroring the pattern already used in `WorkflowShards`, `GetWorkflowID`, and `GetWorkflowReference`), and take a local reference to the inner `map[gateway.AuthorizedKey]struct{}` under that lock before releasing it and checking `keys[key]`.

### Proof of Concept
1. Start a `WorkflowMetadataHandler` with a short `MetadataAggregationIntervalMs` and at least one shard whose aggregator periodically reports metadata (so `syncMetadata` actually replaces `h.authorizedKeys`).
2. Concurrently, from a separate goroutine simulating unprivileged client traffic, repeatedly call `h.Authorize(workflowID, token, req)` with any `workflowID`/token in a tight loop.
3. Run with `go test -race` (or in production under load): the concurrent unguarded read of `h.authorizedKeys` in `Authorize` against the locked write in `syncMetadata` is flagged by the race detector, and under real concurrent load can produce `fatal error: concurrent map read and map write`, crashing the process.

func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}

func (h *WorkflowMetadataHandler) GetWorkflowID(workflowOwner, workflowName, workflowTag string) (string, bool) {
	h.mu.RLock()
	defer h.mu.RUnlock()
	workflowRef := workflowReference{
		workflowOwner: workflowOwner,
		workflowName:  workflowName,
		workflowTag:   workflowTag,
	}
	workflowID, exists := h.workflowRefToID[workflowRef]
	if !exists {
		return "", false
	}
	return workflowID, true
}
