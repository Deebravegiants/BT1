### Title
Post-graduation trades that swap directly on the HyperSwap TOKEN/LT pair permanently bypass the 0.75% Alt Fun protocol/creator fee - ([File: packages/contracts/src/Zap.sol])

### Summary
Every trade Alt Fun intends to monetize is charged its 0.75% fee inside `Zap._executeBuy`/`_executeSell`, which is the only code path that calls `_accrueFee` → `FeeVault.accrue`. Once a token graduates, however, the actual settlement venue is a standard, permissionless HyperSwap V2 pair (`Bonding.graduatedPair(tokenAddress)`), which has no knowledge of `Zap`, `FeeVault`, or the Alt Fun fee at all. Any unprivileged trader or LT holder can call `IUniswapV2Pair(pair).swap(...)` (or transfer LT/Token to the pair and mint) directly, completely bypassing `Zap` and permanently avoiding the protocol/creator fee on that trade — exactly the "avoid the fee-collecting entry point" bug class from the referenced report, where programs bypassed `RoundImplementation.setReadyForPayout` to dodge protocol fees.

### Finding Description
`Zap.buy`/`Zap.sell` charge the fee before routing the trade: pre-graduation via `_buyOnCurve`/`_sellOnCurve` (which call the access-controlled `Bonding.buy`/`Bonding.sell`, gated `onlyRouter`), and post-graduation via `_swapOnUniswapV2`, which calls the graduated pair's `swap()` directly: [1](#0-0) 

The fee is only ever accrued inside `_accrueFee`, invoked from `_executeBuy`/`_executeSell` in `Zap`: [2](#0-1) 

Crucially, the HyperSwap pair that `Zap` calls (`bonding_.graduatedPair(tokenIn)`) is a vanilla, permissionless Uniswap V2 fork pool created by `Bonding.finalizeGraduation`'s `addLiquidity`/`pair.mint` calls. It exposes a public `swap(amount0Out, amount1Out, to, data)` function with no access control tying it to `Zap`. The codebase itself documents this gap explicitly in the comment inside `Zap._buyInternal`: [3](#0-2) 

This is the direct analog of the report's bug class: the protocol collects its fee only at one designated entry point (`RoundImplementation.setReadyForPayout` / `Zap.buy`/`sell`), while the underlying value-transfer mechanism (custom payout contract / HyperSwap pair) is reachable independently and unconditionally by anyone, with no fee logic baked in at that layer.

### Impact Explanation
Post-graduation, any trader (or a wallet/bot the trader controls) can compute the correct `amount0Out`/`amount1Out` from the pair's own `getAmountOut` (same math `Zap` itself uses), transfer LT or Token to the pair, and call `swap()` directly — paying only HyperSwap's 0.3% LP fee and skipping the Alt Fun 0.75% fee (0.5% protocol / 0.25% creator) entirely. Because post-graduation is a permanent lifecycle state (`Lifecycle.Graduated`, no reverting back), this is not a transient griefing window but a durable, repeatable fee-avoidance path for the entire remaining lifetime of every graduated token — a systemic, unbounded loss of protocol and creator fee revenue (`FeeVault.protocolBalance` / `creatorBalance` under-accrue relative to actual trading volume on the graduated pair). This directly matches "programs can avoid protocol fee" impact from the source report, generalized to "every post-graduation trader can avoid protocol/creator fee."

### Likelihood Explanation
High likelihood: no privilege, approval, or special role is required — any EOA or contract holding LT or the launched Token can interact with the public HyperSwap pair. The pair address is discoverable via `Bonding.graduatedPair(tokenAddress)` (a public view) or simply by observing the `TokenGraduated` event, and the swap math (`getAmountOut`) needed to correctly size the trade is a standard, public V2 pair function. Sophisticated traders/MEV bots/arbitrageurs are economically incentivized to trade directly on the pair rather than pay the extra 0.75% through `Zap`, so this will be exploited routinely and at scale, not as an edge case.

### Recommendation
Mirror the referenced report's recommendation of enforcing fee collection at a layer the bypass path cannot avoid: since a raw Uniswap V2 pair cannot itself charge a protocol-specific fee, either (a) deploy a custom pair/hook that skims the Alt Fun fee on every `swap()` at the pair level (so direct pair interaction is impossible without paying it), or (b) explicitly document/accept that post-graduation fee capture is best-effort/advisory (front-end only) rather than an enforced on-chain guarantee, and adjust protocol revenue projections and creator-fee promises accordingly rather than presenting the 0.75% as charged "on every buy/sell... post-grad" as stated in `docs/contracts-scope.md`.

### Proof of Concept
1. Launch and graduate a token via the normal flow (`Zap.createToken` → buys via `Zap.buy` → `Bonding.triggerGraduation`/inline threshold cross → `Bonding.finalizeGraduation`), producing a HyperSwap pair at `Bonding.graduatedPair(tokenAddress)`.
2. As an arbitrary EOA holding the paired LT (obtained via `IBounceLeveragedToken.mint`, unrelated to Zap), read `pair.getReserves()` and `pair.getAmountOut(amountIn, lt)` to compute the correct `tokensOut`.
3. `IERC20(lt).transfer(pair, amountIn)` then `IUniswapV2Pair(pair).swap(tokensOut, 0, msg.sender, "")` (or the reverse for selling Token for LT).
4. Observe: the trade fully executes, tokens are delivered, and `FeeVault.creatorBalance`/`protocolBalance` never change — no `FeeAccrued` event is emitted for this trade, confirming the fee was completely bypassed, versus the equivalent trade run through `zap.buy`/`zap.sell` which always emits `FeeAccrued` per `Zap._accrueFee`.     function _swapOnUniswapV2(
        address tokenIn,
        address tokenOut,
        uint256 amountIn
    ) internal returns (uint256 amountOut) {
        Bonding bonding_ = _s().bonding;
        // `graduatedPair` is keyed by the launched token only; check `tokenIn`
        // first (sell direction) then fall back to `tokenOut` (buy direction).
        address pair = bonding_.graduatedPair(tokenIn);
        if (pair == address(0)) pair = bonding_.graduatedPair(tokenOut);

        bool inIsToken0 = IUniswapV2Pair(pair).token0() == tokenIn;
        // Quote from the pair so the output tracks its live fee instead of a
        // hardcoded rate, keeping `amountOut` consistent with the K-check.
        amountOut = IUniswapV2Pair(pair).getAmountOut(amountIn, tokenIn);

        IERC20(tokenIn).safeTransfer(pair, amountIn);

        (uint256 amount0Out, uint256 amount1Out) = inIsToken0 ? (uint256(0), amountOut) : (amountOut, uint256(0));
        IUniswapV2Pair(pair).swap(amount0Out, amount1Out, address(this), new bytes(0));
    }
