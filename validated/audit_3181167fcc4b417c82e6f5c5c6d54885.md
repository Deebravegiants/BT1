## Analysis

I focused on the webhook‑processing path in this gem, since it contains an explicit identity binding — the HMAC signature — that is supposed to authenticate the origin of an inbound Shopify event, similar to the way the strategies in the reference report fail to bind an expected output value to an actual on‑chain swap result.

### The binding that should hold but doesn't

`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body: [1](#0-0) 

but the `shop` (and `topic`, `webhook_id`, `api_version`) values are pulled straight from unauthenticated HTTP headers: [2](#0-1) 

`ShopifyAPI::Webhooks::Registry.process` validates only that the body's HMAC matches the app's `api_secret_key`, then immediately trusts `request.shop` as the tenant identifier passed to the app's handler: [3](#0-2) 

So the equality that is verified is:
`HMAC(api_secret_key, raw_body) == received_hmac`

but the equality that actually matters for tenant isolation —
`shop_header == shop_that_the_signed_body_was_generated_for`

— is never checked. The `shop` field is "a field acted on but not covered by the HMAC," exactly one of the explicitly in‑scope analog classes.

### Why this is exploitable, not theoretical

The webhook HMAC secret (`api_secret_key`) is shared across every shop that installs the app — it is not shop‑specific. An unprivileged attacker who installs the target app on their own store (a normal, unprivileged action) will receive legitimately Shopify‑signed webhook deliveries (body + valid `x-shopify-hmac-sha256`). Because the signature never binds to the `shop-domain` header, the attacker can replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` will still return `true` (the body/secret pair really is valid), and `Registry.process` will hand the attacker's data to the handler tagged as belonging to the victim shop, since `WebhookMetadata.shop` comes straight from the unverified header. [3](#0-2) 

This lets an attacker forge webhook events "from" any shop that has ever installed the app, achieving cross‑tenant data injection under the guise of a validated (HMAC‑passed) webhook — an authentication bypass on the tenant identity of the request.

## Output

### Title
Webhook `shop` (and `topic`/`webhook_id`) identity is not covered by the HMAC signature, enabling cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw body, while `shop`, `topic`, `webhook_id`, and `api_version` are read from unauthenticated HTTP headers and are passed unchecked to the webhook handler by `ShopifyAPI::Webhooks::Registry.process`.

### Finding Description
Shopify webhook authenticity in this gem is established solely by `Utils::HmacValidator.validate`, which recomputes `HMAC-SHA256(api_secret_key, raw_body)` and compares it to the `x-shopify-hmac-sha256` header (`lib/shopify_api/utils/hmac_validator.rb`). The `shop` accessor used to identify which merchant/tenant a webhook belongs to is derived independently from the `x-shopify-shop-domain` header (`lib/shopify_api/webhooks/request.rb:21-23`) and is never included in the signed string (`lib/shopify_api/webhooks/request.rb:36-38`). `Registry.process` checks the HMAC and then unconditionally trusts `request.shop` as the tenant key forwarded to the app's handler (`lib/shopify_api/webhooks/registry.rb:188-200`). Because `api_secret_key` is shared by every installation of the app, any signed body captured from one shop (including a shop controlled by the attacker) can be replayed against the same endpoint with a different `shop-domain` header and will still pass HMAC validation.

### Impact Explanation
This breaks tenant isolation (cross-tenant access): a body that was legitimately signed for the attacker's own shop can be presented as originating from any other shop that uses the app, letting the attacker inject arbitrary "shop-scoped" data (order/product/customer events, etc.) into a victim tenant's processing pipeline while passing the library's own authenticity check.

### Likelihood Explanation
An attacker only needs to install the target app on a shop they control — no privileged credentials, leaked secrets, or social engineering are required — then capture one legitimate webhook delivery and replay it with a modified `shop-domain` header. This requires no interaction with Shopify's servers beyond normal, unprivileged app installation.

### Recommendation
Bind the shop identity into the verified signable content. Options:
- Include `shop-domain`, `topic`, and `webhook_id` in the signable string used for `HmacValidator.validate`, if Shopify's webhook signing were extended to cover them, or
- At minimum, document/require that consumers additionally verify `request.shop` against a shop the app knows it has installed for that specific webhook subscription (e.g., correlate against a per-shop webhook registration/secret) rather than trusting the header value as an authenticated identity.
- Consider treating `shop`, `topic`, and `webhook_id` as untrusted metadata in the gem's own documentation so consuming apps are not misled into treating them as verified.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`.
2. Shopify sends a legitimate webhook to the app's endpoint: body `B`, headers include `x-shopify-hmac-sha256: HMAC(secret, B)` and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker resends the identical body `B` and HMAC header to the same endpoint, replacing only `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate` recomputes `HMAC(secret, B)` — unaffected by header changes — and returns `true`.
5. `ShopifyAPI::Webhooks::Registry.process` builds `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: B, ...)` and invokes the app's handler as if the event genuinely came from `victim-shop.myshopify.com`.
