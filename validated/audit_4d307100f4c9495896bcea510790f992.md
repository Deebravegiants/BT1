Confirmed: the webhook `shop` (and `topic`, `webhook_id`, `api_version`) identity fields are sourced purely from HTTP headers and are never part of the HMAC-signed payload.

### Title
Webhook `shop-domain` header trusted without HMAC coverage, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC over `@raw_body` only, while the `shop` identity value handed to the app's `WebhookHandler` is read from the `X-Shopify-Shop-Domain` header, a field that is never included in the signed material.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely via `Utils::HmacValidator.validate(request)` [1](#0-0) , which in turn calls `request.to_signable_string` and compares an HMAC over that string against the `hmac-sha256` header using the app's `api_secret_key` [2](#0-1) .

For `ShopifyAPI::Webhooks::Request`, `to_signable_string` returns only the raw request body: [3](#0-2) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers with no cryptographic binding to the signed body: [4](#0-3) 

After the HMAC check passes, `Registry.process` builds `WebhookMetadata` directly from these unauthenticated header values and dispatches it to the app's handler: [1](#0-0) 

The equality this breaks: **shop authenticated by the HMAC signature ≠ shop delivered to the handler.** The HMAC only proves "this body was signed by Shopify with our secret"; it proves nothing about which shop, topic, or webhook id that signature was intended for. Because Shopify webhook bodies are frequently identical or highly predictable across shops (e.g., mandatory topics `shop/redact` with fixed/minimal payloads, or any topic sharing the same body shape across tenants installed on the same app), a body legitimately signed for tenant A's webhook delivery can be replayed to the app's webhook endpoint with the `shop-domain` (and `topic`/`webhook-id`) headers changed to point at tenant B. `HmacValidator.validate` will still succeed because it only checks the body/secret pair, never the header values, so the handler executes tenant-B-labeled logic using tenant-A-signed bytes.

### Impact Explanation
This is a High severity scope/identity-binding bypass: an unprivileged actor who can trigger or capture one genuine webhook delivery for any shop on the same app (including their own shop, which they fully control and can freely trigger events on) can relabel it to any other tenant's `shop`, `topic`, or `webhook_id` and have the app process it as authentic, because the gem's `Utils::HmacValidator.validate` and `Registry.process` never verify that the signed bytes correspond to the claimed header identity. Downstream app logic (data deletion via `customers/redact`/`shop/redact`, app-uninstalled cleanup, order/customer processing keyed by `shop`) is invoked with attacker-controlled tenant attribution, which is a cross-tenant integrity/confidentiality break within the scope of this gem's own verification code.

### Likelihood Explanation
Likelihood is moderate-to-high for topics with fixed or predictable bodies (mandatory GDPR topics and any topic whose payload the app does not itself vary per shop, e.g., minimal or templated payloads), since the attacker only needs one valid signed delivery to their own shop's endpoint and full control over which headers accompany their replayed HTTP request. No access token, `client_secret`, or privileged account is required — only the ability to install the target app on a shop the attacker controls and observe/capture a webhook delivery.

### Recommendation
Bind the `shop`, `topic`, and `webhook_id` header values into the HMAC-signed material (or otherwise cryptographically tie them to the signed body) before trusting them in `Registry.process`/`WebhookMetadata`, so `Utils::HmacValidator.validate` fails whenever any identity header is altered relative to what Shopify actually signed for that specific delivery.

### Proof of Concept
1. App is installed on attacker-controlled shop `attacker.myshopify.com` and on victim shop `victim.myshopify.com`.
2. Attacker triggers a `shop/redact` (or any topic with a body identical/predictable across shops) webhook delivery to their own endpoint; captures the raw body `B` and its valid `X-Shopify-Hmac-Sha256` header `H` (computed by Shopify over `B` with the shared app secret).
3. Attacker replays an HTTP POST to the app's webhook endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` (unchanged, still valid since body is unchanged), but `X-Shopify-Shop-Domain: victim.myshopify.com` and/or a different `X-Shopify-Webhook-Id`.
4. `ShopifyAPI::Webhooks::Request.new` accepts the headers, `Utils::HmacValidator.validate` succeeds because it only checks `B` against `H` [5](#0-4) , and `Registry.process` invokes the handler with `shop: "victim.myshopify.com"` [6](#0-5) , causing the app to execute victim-attributed webhook logic from attacker-forged headers.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

          end

          received_signature = verifiable_query.hmac

          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
