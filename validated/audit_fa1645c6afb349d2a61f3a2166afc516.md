### Title
Rounding-down decimal conversion in `pallet-hyper-fungible-token` permanently loses dust on every ERC20→local balance conversion - ([File: modules/pallets/hyper-fungible-token/src/impls.rs])

### Summary
The `hyper-fungible-token` pallet converts between the ERC20-side decimal precision (`erc_decimals`, tracked per `(AssetId, StateMachine)` in the `Precisions` storage map) and the local pallet/asset decimal precision (`local_decimals`) whenever tokens cross between an EVM `HyperFungibleToken`/`BridgeToken` contract and this pallet. The conversion helper `convert_to_balance` truncates via integer division rather than rounding, mirroring the exact rounding-down defect described in the referenced SolverVaults report.

### Finding Description
`convert_to_balance` divides the incoming ERC20 `U256` amount by `10^(erc_decimals - local_decimals)` whenever the EVM side carries more decimal precision than the local asset: [1](#0-0) 

This is the reverse of `convert_to_erc20`, which multiplies (lossless) when going from the pallet's local balance out to the EVM side: [2](#0-1) 

`erc_decimals` is per-asset, per-destination-chain configuration stored in `Precisions`, so it is not guaranteed to be a value that evenly matches `local_decimals` — unlike the fixed 18-vs-12 (a clean power of ten) case hard-coded for `BridgeToken`: [3](#0-2) [4](#0-3) 

`convert_to_balance` is referenced from `module.rs` (the pallet's ISMP receive-side handler, per grep match count) to translate the amount encoded in an incoming `Message` (ERC20-decimal `U256`) into the local `Balance` type before crediting/unlocking the recipient's local balance. Because the EVM side burns/escrows the *exact* ERC20-precision amount before dispatch, and the pallet then floors the converted amount when crediting locally, any fractional remainder below `10^(erc_decimals - local_decimals)` is silently dropped — burned on the source side but never credited on the destination side.

This is precisely the same rounding-down defect flagged in the external SolverVaults report: a lossy decimal-scaling division on token movement between two token representations with differing decimals, applied without any remainder handling or a "trim before burn" pre-check.

### Impact Explanation
Every incoming HFT transfer from an EVM chain where the registered `erc_decimals` for that asset exceeds the pallet's local asset decimals loses the truncated remainder permanently: it is burned/escrowed on the source chain but never minted/unlocked on nexus. This breaks the 1:1 backing invariant the token model depends on (documented for `BridgeToken` as "the supply of this token is always backed by the pallet's escrow account") and constitutes a permanent, protocol-level loss of user funds on the affected asset registrations, not merely a UX inconvenience. Because `Precisions` is configurable per asset/chain via governance-style registration rather than fixed at deployment, this is reachable for any asset registered with a non-power-of-ten-aligned decimals delta, not only the fixed BRIDGE/nexus pair.

### Likelihood Explanation
Triggered on the ordinary token-receive path for any registered asset whose `erc_decimals` is not a clean multiple aligning with `local_decimals` (i.e. `erc_decimals - local_decimals` is such that the amount isn't already a multiple of `10^(erc_decimals-local_decimals)`), which happens on essentially every real-world transfer amount for such an asset pair. No privileged action or attacker cooperation is required — a normal user's cross-chain send triggers the loss deterministically.

### Recommendation
- Reject (or round the source-side burn amount down to) the granularity supported by the destination's decimals *before* burning/escrowing on the sending side, so the exact amount burned is representable losslessly after conversion, analogous to the report's "trim the original deposit amount" recommendation.
- Alternatively, track/accumulate the truncated remainder per asset and either refuse transfers that would create dust loss, or credit the remainder via a dust-sweep mechanism so value is never simply destroyed.
- Add an invariant/test asserting that `convert_to_erc20(convert_to_balance(x, e, l), e, l) == x` for the full range of configured `Precisions` entries, and add explicit coverage for `erc_decimals > local_decimals` amounts that are not multiples of the scaling factor.

### Proof of Concept
1. Register an asset in `Precisions` with, e.g., `erc_decimals = 18` on the EVM peer and `local_decimals = 6` on nexus (scale factor `10^12`), a legitimate configuration since `Precisions` is a generic per-(asset, chain) map: [3](#0-2) 
2. On the EVM chain, a user sends `1_000_000_000_000_000_001` wei (18 decimals) of the token to nexus; the contract burns/escrows this exact amount and dispatches a `Message` with `amount = 1_000_000_000_000_000_001`.
3. On delivery, the pallet's receive handler calls `convert_to_balance(1_000_000_000_000_000_001, 18, 6)`, which computes `1_000_000_000_000_000_001 / 10^12 = 1_000_000` (integer division truncates the trailing `000000000001`): [5](#0-4) 
4. The recipient is credited `1_000_000` local units (equivalent to `1_000_000_000_000_000_000` wei), permanently losing the `1` wei remainder that was burned on the EVM chain and is unrecoverable, since no dust-tracking or trimming exists in `send`/`convert_to_erc20`/`convert_to_balance`.

```rust
/// Converts an ERC20 U256 amount to a local balance type
///
/// Divides by 10^(erc_decimals - local_decimals) to scale down from ERC20 precision.
/// The target type must implement `FromStr`.
pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}
```

```rust
///
/// Multiplies by 10^(erc_decimals - local_decimals) to scale up to ERC20 precision
```
