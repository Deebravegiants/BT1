### Title
`findMatchingWithdrawal` matches by `assetId` only, causing status/txHash misattribution for duplicate-token batch withdrawals - (File: `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`)

### Summary
`PoaBridge.describeWithdrawal` resolves each `WithdrawalIdentifier`'s status by calling `findMatchingWithdrawal`, which matches purely on `nep141:<near_token_id> === assetId` and ignores `index`, `destinationAddress`, and `amount`. When a batch contains two or more withdrawals of the same PoA asset (e.g. two `nep141:cardano.omft.near` withdrawals to different destination addresses in one intent), both `WithdrawalIdentifier`s poll the same underlying withdrawal-hash query and both resolve to the *same* array entry (`Array.prototype.find` always returns the first match), so one destination's `completed`/`txHash` gets reported for the other's withdrawal.

### Finding Description
The broken equality is: `describeWithdrawal({wid_A}).txHash` should correspond to the withdrawal whose `destinationAddress`/`amount` matches `wid_A.withdrawalParams`, not to `wid_B`'s withdrawal, when `wid_A.withdrawalParams.assetId === wid_B.withdrawalParams.assetId`.

Code path:
- `IntentsSDK.waitForWithdrawalCompletion` / `createWithdrawalCompletionPromises` accepts an array of `WithdrawalParams` with no uniqueness constraint on `assetId` [1](#0-0) .
- `createWithdrawalIdentifiers` assigns a per-bridge `index` counter but does not disambiguate withdrawals by destination/amount [2](#0-1) .
- `watchWithdrawal` polls `bridge.describeWithdrawal(wid)` independently per `WithdrawalIdentifier` [3](#0-2) .
- `PoaBridge.describeWithdrawal` fetches `getWithdrawalStatus({ withdrawal_hash: args.tx.hash })` (same NEAR tx hash for all withdrawals in the batch) and then calls `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)` [4](#0-3) .
- `findMatchingWithdrawal`'s own comment admits: "multiple withdrawals of the same token in a single transaction are not supported," yet nothing in `supports()`, `validateWithdrawal`, or `createWithdrawalIdentifiers` rejects such batches [5](#0-4) .

Root cause: matching is by `assetId` alone via `Array.prototype.find`, which always returns the first entry in the unsorted `response.withdrawals` list satisfying the predicate. If two withdrawals share the same `near_token_id`, both `WithdrawalIdentifier`s (index 0 and index 1) converge on the *same* matched entry — whichever happens to be first in the API's unsorted response — regardless of which one truly belongs to which destination address/amount. Neither `validateAddress`, `compareAddresses`, nor `supports()` guards against duplicate-asset batches; they operate on a single withdrawal's parameters and don't compare against sibling withdrawals in the batch.

Attacker/exploit flow: an ordinary integrator/user submits `withdrawalParams` as `[{assetId: "nep141:cardano.omft.near", destinationAddress: A, amount: X}, {assetId: "nep141:cardano.omft.near", destinationAddress: B, amount: Y}]` via `processWithdrawal`/`waitForWithdrawalCompletion`. Once the POA bridge processes both withdrawals for the batch's NEAR tx hash, both `describeWithdrawal` calls return the same matched withdrawal (e.g., the one destined for A also gets reported for B, or vice versa), including the same `transfer_tx_hash`. An integrator using the SDK's polling result to credit/settle would then wrongly believe both destinations' withdrawals are `completed` with a shared tx hash, even though only one payout occurred (or the two are conflated), enabling incorrect crediting/refund decisions for one of the two destinations.

### Impact Explanation
The SDK-reported `WithdrawalStatus.txHash` and `status` for one `WithdrawalIdentifier` in a batch can reflect the wrong physical withdrawal's completion state/hash. An integrator relying on `waitForWithdrawalCompletion`/`createWithdrawalCompletionPromises` per-index results to mark payouts as settled could credit or release funds for a withdrawal that has not actually completed to that destination, or double-count a single payout across two destinations — a status/hash misreport matching the "High" impact category (integrator credits or refunds twice).

### Likelihood Explanation
Preconditions: an integrator/user must submit a batch withdrawal containing two or more `WithdrawalParams` with identical PoA-bridge `assetId` (e.g. `nep141:cardano.omft.near`) but different destination addresses/amounts — this is a normal API usage that nothing in `supports()`/`validateWithdrawal`/`createWithdrawalIdentifiers` rejects. This requires no special privileges beyond calling the SDK's public batch-withdrawal methods with attacker/integrator-controlled `withdrawalParams`, so it is fully attacker-reachable and repeatable per batch.

### Recommendation
Reject or disambiguate duplicate-`assetId` withdrawals within a single batch for the POA bridge: either throw an explicit `UnsupportedBatchError` when `createWithdrawalIdentifiers`/`supports()` detects more than one withdrawal with the same POA `assetId` in a batch, or extend `findMatchingWithdrawal` to also match on `destinationAddress`/`amount` (and consume matched entries so they aren't reused across identifiers) once the POA API supports disambiguating fields, as the existing code comment anticipates.

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
