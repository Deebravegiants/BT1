### Title
Webhook HMAC Does Not Bind the `shop-domain` Header, Enabling Cross-Tenant Webhook Spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, excluding the `shopify-shop-domain`, `shopify-topic`, and `shopify-webhook-id` headers from the HMAC-verified payload. `ShopifyAPI::Webhooks::Registry.process` trusts `request.shop` and `request.topic` — which come straight from unauthenticated headers — to route and label the webhook to a handler, without any additional binding to the HMAC. This breaks the identity binding: `shop_used_for_processing == shop_covered_by_hmac` does not hold, since the header value is never included in the signed string.

### Finding Description
`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` and compares it to the value taken from the `hmac-sha256` header: [1](#0-0) 

For webhook requests, `to_signable_string` is defined to return only `@raw_body`: [2](#0-1) 

Meanwhile, `shop`, `topic`, and `webhook_id` are all read straight from HTTP headers with no cryptographic binding to the HMAC signature: [3](#0-2) 

`Registry.process` validates only that the HMAC of the body matches, then immediately dispatches the (unauthenticated) `request.shop` and `request.topic` values to the handler: [4](#0-3) 

Because the signable string is `raw_body` alone, any request with a body/HMAC pair that is valid for the app's `client_secret` remains valid regardless of what `shop-domain`, `topic`, or `webhook-id` headers are attached to it. An unprivileged internet user who can obtain one genuinely-signed webhook body (e.g., by installing the app on a shop they control, or by triggering any webhook topic that Shopify will legitimately sign for that shop) can replay that exact body to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header value. `HmacValidator.validate` still returns `true`, since it only checks the body, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the attacker-chosen shop as the source.

### Impact Explanation
This is a scope/identity-binding bypass leading to cross-tenant data injection: an app's webhook handler (e.g., `orders/create`, `app/uninstalled`, `customers/data_request`) will process attacker-controlled data while believing it originates from a different, victim tenant. Depending on what the handler does with `data.shop` (e.g., write to that shop's records, trigger de-provisioning, fulfill mandatory GDPR webhook processing), this can corrupt cross-tenant state or trigger actions against a shop the attacker does not control, without ever needing the `client_secret`.

### Likelihood Explanation
Likelihood is moderate to high for any attacker who can install the target app on their own store (common for public apps) or otherwise obtain one legitimately-HMAC'd webhook payload. No secret material or privileged access is required beyond that — only header manipulation on the replay request, which is trivial for any unprivileged internet user capable of sending arbitrary HTTP requests to the app's webhook endpoint.

### Recommendation
Include the `shop-domain`, `topic`, and `webhook-id` header values in the HMAC-signable string (or otherwise cryptographically bind them, e.g., by having `to_signable_string` concatenate headers + body) so a signature stays valid only for the exact shop/topic/id it was issued for. At minimum, `Registry.process` should not trust `request.shop` for tenant-sensitive dispatch unless it participated in the HMAC computation.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and triggers a webhook (e.g., `orders/create`) with an arbitrary JSON body of their choosing. Shopify signs it with the app's real `client_secret`:
```
POST /webhooks
shopify-topic: orders/create
shopify-hmac-sha256: <valid HMAC of raw_body>
shopify-shop-domain: attacker-shop.myshopify.com
{"id": 1, "malicious": "payload"}
```
2. Attacker captures this exact `raw_body` and `hmac-sha256` value.
3. Attacker replays the identical body+HMAC to the same endpoint, but swaps the shop header:
```
POST /webhooks
shopify-topic: orders/create
shopify-hmac-sha256: <same HMAC as step 1>
shopify-shop-domain: victim-shop.myshopify.com
{"id": 1, "malicious": "payload"}
```
4. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` recomputes the HMAC over `raw_body` only (per `Request#to_signable_string` in `lib/shopify_api/webhooks/request.rb:35-38`) and it matches, so `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) invokes the handler with `shop: "victim-shop.myshopify.com"` and the attacker-chosen body, even though Shopify never sent this webhook for `victim-shop`.
