## Title
Webhook `shop` domain is trusted for tenant attribution but is not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then hands the handler a `shop` value taken directly from the unauthenticated `x-shopify-shop-domain`/`shopify-shop-domain` header. Because the tenant identity (`shop`) is never part of the signed material, the binding `shop that produced a valid HMAC == shop attributed to the delivered event` does not hold.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and defines: [1](#0-0) 
`hmac` is computed from the `hmac-sha256` header and `to_signable_string` returns only `@raw_body`: [2](#0-1) 
`shop` is read directly from the `shop-domain` header and is not part of `to_signable_string`: [3](#0-2) 

`Utils::HmacValidator.validate` verifies the signature only against `verifiable_query.to_signable_string` (i.e. the raw body), using the app's shared `api_secret_key`: [4](#0-3) 

`Registry.process` checks the HMAC and then dispatches the handler using `request.shop`, which was never bound into the signature: [5](#0-4) 

Since the `api_secret_key` is a single, app-wide secret shared across every shop that has installed the app (not a per-shop secret), any merchant who installs the app receives real, validly-HMAC-signed webhook deliveries for their own shop. That merchant can capture a `(raw_body, hmac)` pair from their own legitimate webhook and replay it to the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop's domain. `HmacValidator.validate` still succeeds (it never looked at the header), and `Registry.process` will construct `WebhookMetadata` with the attacker-chosen `shop`, causing the host application's handler to process/act on data as if it came from the victim tenant — breaking the equality `authenticated shop == shop the handler acts on`.

### Impact Explanation
This is a cross-tenant identity-attribution flaw: an unprivileged merchant (who legitimately installed the app on their own store, so no additional credential or privileged access is required) can forge webhook events attributed to any other shop simply by changing an HTTP header, since the shop identity is excluded from the HMAC-covered content. Any host application logic that uses `WebhookMetadata#shop` from this gem to select per-tenant session/data will act on the wrong tenant, meeting the "cross-tenant access" Critical impact criterion.

### Likelihood Explanation
Likelihood is high for any consumer of this gem's webhook handling: the exploit requires only (1) installing the target app on an attacker-controlled shop (a normal, unprivileged action for any Shopify merchant/app tester) to obtain a validly signed body/HMAC pair, and (2) replaying that request with a modified `shop-domain` header to the app's public webhook endpoint. No access token, `client_secret`, or privileged account is needed.

### Recommendation
Bind the shop identity into the verified material, or otherwise establish out-of-band trust for `request.shop` before it is used for tenant attribution:
- Extend `Utils::VerifiableQuery`/`Webhooks::Request#to_signable_string` (or the `HmacValidator`) to require the caller to supply the previously known/installed shop domain for the target tenant and reject the webhook if it doesn't match, or
- Document/require that consuming applications independently verify `request.shop` against their own store of installed/authorized shops before trusting `WebhookMetadata#shop`, and make this an explicit, enforced step in `Registry.process` rather than leaving it silently absent.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`, and receives a legitimate webhook delivery, e.g. body `{"id":1}` with a valid `x-shopify-hmac-sha256` header computed with the app's `api_secret_key`.
2. Attacker replays the exact same body and HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `OpenSSL::HMAC.hexdigest(sha256, api_secret_key, raw_body)` — this still matches, since `raw_body` and `hmac` are unchanged: [6](#0-5) 
4. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` and the host application processes the (attacker-supplied) body under the victim's tenant context.
