Audit Report

## Title
Fee-on-transfer / deflationary ERC20 tokens break XCM holding-register accounting in `ERC20Transactor` - (File: `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`)

## Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `deposit_asset_with_surplus` credit or report the full nominal XCM `amount` as soon as the ERC20 `transfer` call returns `true`, without ever reading `balanceOf` on the checking account/beneficiary before and after the call to confirm that `amount` tokens actually moved. <cite repo="Tylerpinwa/polkadot-sdk--011" path="cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs" start="191-203" end="203" /> <cite repo="Tylerpinwa/polkadot-sdk--011" path="cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs" start="276-280" end="280" /> Since `ERC20Matcher` matches any local `AccountKey20` location without an allow-list, any account can deploy an arbitrary fee-on-transfer contract via `pallet-revive` and reference it as an XCM asset, so this path is reachable by an unprivileged user. <cite repo="Tylerpinwa/polkadot-sdk--011" path="cumulus/parachains/runtimes/assets/common/src/lib.rs" start="157-160" end="160" />

## Finding Description
In `withdraw_asset_with_surplus`, the contract's `transfer(checking_address, amount)` is invoked and, on `Ok(true)`, the code unconditionally constructs `Erc20Credit(amount)` and inserts it into `AssetsInHolding` without verifying that the checking account's balance actually increased by `amount`. [1](#0-0) 

Symmetrically, `deposit_asset_with_surplus` calls `transfer(beneficiary, amount)` from the checking account and, on `Ok(true)`, treats the operation as fully successful (`Ok(surplus)`) without confirming the beneficiary actually received `amount`. [2](#0-1) 

Both functions only guard against `did_revert()` and non-`true`/undecodable return values — they never compare pre/post `balanceOf`, so a contract that deducts a fee/burns a portion of the transferred amount while still returning `true` (a fee-on-transfer or deflationary token) will cause the runtime's internal accounting (`AssetsInHolding`, and later requested deposit amounts) to diverge from the checking account's real on-chain balance. This is consistent with the code as read; the existing guards (`did_revert`, `abi_decode_returns_validate`) address malformed/failed transfers but not partial transfers with a truthful `true` return.

The claim that any unprivileged user can register an arbitrary ERC20 as an XCM asset is also supported: `ERC20Matcher` in `assets-common` matches any `Location` of the form `(0, [AccountKey20 { .. }])` with no contract vetting or allow-list. <cite repo="Tylerpinwa/polkadot-sdk--011" path="cumulus/parachains/runtimes/assets/common/src/lib.rs" start="132-160" end="160" />

## Impact Explanation
Because the holding register is credited/debited using the nominal `amount` rather than the observed balance delta, repeated withdraw/deposit cycles using a fee-on-transfer token will cause the shared checking account's real balance to fall behind the amount the runtime believes it holds. This can starve later legitimate deposit attempts for the same token (causing `ERC20 contract reverted`/insufficient-balance failures), which is an availability/accounting-drift issue scoped to the specific ERC20 contract's checking-account bookkeeping rather than a direct fund-theft primitive against unrelated assets, matching the report's own "Medium" self-assessment.

## Likelihood Explanation
Likelihood is realistic: deploying a custom ERC20 via `pallet-revive` and referencing it by address in an `AccountKey20` XCM asset ID is a normal, permissionless user flow already exercised by existing tests such as `smart_contract_not_erc20_will_error` and `smart_contract_does_not_return_bool_fails` in the asset-hub-westend test suite, which use custom Solidity fixtures analogous to a fee-on-transfer token. No privileged registration step is required since `ERC20Matcher`/`IsLocalAccountKey20` accepts any local `AccountKey20` location.

## Recommendation
Read `balanceOf(checking_address)` (withdraw path) and `balanceOf(beneficiary)` (deposit path) before and after the `IERC20::transferCall`, and credit/report only the actually-observed delta instead of the requested nominal `amount`. Alternatively, explicitly document that fee-on-transfer/rebasing ERC20 tokens are unsupported and add a defensive check that fails the whole XCM instruction (`FailedToTransactAsset`) if the observed delta does not equal the requested `amount`, extending the existing `did_revert`/`abi_decode_returns_validate` guard pattern in `withdraw_asset_with_surplus` (`erc20_transactor.rs:185-208`) and `deposit_asset_with_surplus` (`erc20_transactor.rs:270-298`).

## Proof of Concept
1. Deploy via `pallet-revive` a Solidity ERC20 contract whose `transfer(to, value)` moves `value - fee` to `to` (burning or redirecting `fee`) while still returning `true`.
2. Reference this contract's address as an `AccountKey20` XCM `AssetId`, following the same pattern as `smart_contract_not_erc20_will_error`/`smart_contract_does_not_return_bool_fails` in `cumulus/parachains/runtimes/assets/asset-hub-westend/tests/tests.rs`.
3. Execute an XCM program with `WithdrawAsset`/`DepositAsset` moving `amount` of this token through `ERC20Transactor`.
4. Observe that `withdraw_asset_with_surplus` credits `AssetsInHolding` with the full nominal `amount` (`erc20_transactor.rs:195-203`) even though the checking account's real `balanceOf` only increased by `amount - fee`; repeating this cycle drains the checking account's real balance faster than the runtime's internal accounting expects, eventually causing `deposit_asset_with_surplus` calls against the same checking account to fail with `ERC20 contract reverted`/insufficient-balance errors.
