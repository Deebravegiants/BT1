### Title
Webhook shop-domain and topic are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its signable content from only the raw HTTP body, while the `shop`, `topic`, and `webhook_id` values used by the application (via `ShopifyAPI::Webhooks::Registry.process`) come from unauthenticated HTTP headers that are excluded from the HMAC computation. An attacker who can obtain one validly-signed webhook body/HMAC pair (e.g., by installing the target app on their own store and receiving a genuine webhook) can replay that body with a forged `shop-domain` header pointing at a victim shop, and the signature check will still pass.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, and `#webhook_id` are all read straight from HTTP headers with no cryptographic binding to the body: [2](#0-1) 

`HmacValidator.validate` only verifies `verifiable_query.to_signable_string` (i.e., the raw body) against the HMAC header — it never incorporates `shop`, `topic`, or `webhook_id` into the signed material: [3](#0-2) 

`Registry.process` validates the HMAC and then unconditionally trusts the unsigned `request.shop` header to build the `WebhookMetadata` passed to the app's handler: [4](#0-3) 

The identity binding that should hold is:
`HMAC(api_secret_key, raw_body || shop || topic) == received_hmac`

but the actual implementation only enforces:
`HMAC(api_secret_key, raw_body) == received_hmac`

Since `api_secret_key` is the same for every shop that installs a given app, any merchant who installs the app (a normal, unprivileged action — no special credentials required) can trigger genuine webhooks for their own store and thus obtain a body+HMAC pair signed with the app's shared secret. That pair remains valid regardless of which `shop-domain` header accompanies it, because the header is never part of the signed content. The attacker can therefore forge a webhook delivery that appears (per `WebhookMetadata#shop`) to originate from a different, victim shop while carrying body content controlled by the attacker's own store.

### Impact Explanation
This crosses a tenant boundary: the app's webhook handler receives `data.shop` claiming to be the victim shop, but the payload was never generated by or signed on behalf of that shop. If the host application (as documented/intended usage of this gem) uses `WebhookMetadata#shop` to select which merchant's session/record to update with the body content (a normal, encouraged usage pattern shown in the webhooks docs), an attacker can inject or attribute fabricated webhook data to an arbitrary target shop without ever possessing that shop's credentials — a cross-tenant data-integrity/spoofing impact.

### Likelihood Explanation
Exploitation only requires installing the target app on any store (including a store the attacker controls) to receive one legitimately HMAC-signed webhook, then replaying it against the endpoint with a modified `shop-domain` header. No access token, `api_secret_key`, or privileged account is needed beyond ordinary app installation, which is the normal unprivileged path any merchant/attacker can take.

### Recommendation
Bind the identity fields used for authorization decisions into the HMAC-verified content, or otherwise cryptographically tie the `shop-domain`/`topic` headers to the signed payload (e.g., include them in the signable string, or cross-check them against a value obtained through an authenticated channel such as a previously stored session for that shop) before trusting `WebhookMetadata#shop` in `Registry.process`.

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com`; trigger a real webhook (e.g., `orders/create`) and capture the raw request: body `B`, and header `x-shopify-hmac-sha256` = `HMAC(api_secret_key, B)`.
2. Replay a POST to the app's webhook endpoint with the same body `B` and the same HMAC header, but set `x-shopify-shop-domain: victim.myshopify.com`.
3. `HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:13-22`) succeeds because it only checks `B` against the HMAC.
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:189-200`) invokes the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed(B), ...)`, causing the host app to act on attacker-supplied data as if it came from `victim.myshopify.com`.
