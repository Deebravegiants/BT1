I have enough evidence to confirm the analog vulnerability in `WrappedHyperFungibleToken.send()` (and its upgradeable twin). This is a direct match to the reported `StandardBridge._initiateBridgeERC20` bug class: the contract trusts `_amount`/`params.amount` after `safeTransferFrom` without verifying actual tokens received, unlike `IntentGatewayV2.sol` which was already hardened with balance-before/after checks for this exact reason.

### Title
Unverified `safeTransferFrom` amount in `WrappedHyperFungibleToken.send()` allows accounting desync and destination-side insolvency with non-standard ERC20 tokens - (File: sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol)

### Summary
`WrappedHyperFungibleToken.send()` pulls `params.amount` of the underlying ERC20 via `safeTransferFrom` but never verifies that this exact amount was actually received by the contract. It unconditionally encodes `params.amount` into the cross-chain `Message` and dispatches it, regardless of the real amount locked.

### Finding Description
In `send()`, the ERC20-lock branch performs:
```solidity
IERC20(_underlying).safeTransferFrom(msg.sender, address(this), params.amount);
``` [1](#0-0) 

with no balance-before/after check. The subsequent `_buildDispatchPost` encodes `params.amount` (not the actual received delta) into the `Message.amount` field that is dispatched cross-chain: [2](#0-1) 

If `_underlying` is a fee-on-transfer, rebasing, or otherwise non-standard ERC20 (which is entirely possible since `_underlying` is set once via owner `configure()` and any token can later be swapped for a compromised/deflationary implementation, or the owner may simply misconfigure it), the amount actually locked in the contract will be less than `params.amount`. The destination `HyperFungibleToken` mints exactly `message.amount` to the beneficiary — an amount the source-side lock did not actually back.

This is the identical root cause as the reported `StandardBridge._initiateBridgeERC20` issue: no `balanceOf` diffing around `safeTransferFrom` to guarantee the declared amount was truly deposited before propagating it downstream. Notably, the same codebase already fixed this exact pattern elsewhere — `IntentGatewayV2.sol` explicitly diffs `balanceOf` before/after `safeTransferFrom` and uses the real delta:
```solidity
uint256 balBefore = IERC20(token).balanceOf(address(this));
IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
order.inputs[i].amount = IERC20(token).balanceOf(address(this)) - balBefore;
``` [3](#0-2)  — `WrappedHyperFungibleToken` and its upgradeable counterpart lack this same safeguard.

### Impact Explanation
Each `send()` call with such a token would under-collateralize the wrapper by the fee/skim amount while promising the full `params.amount` to be minted/unlocked on the destination chain. Repeated over many transfers, this creates a growing shortfall between the wrapper's actual locked balance and the sum of tokens the destination side believes it can redeem — a classic unbacked-mint / insolvency condition that eventually causes `onAccept`'s `safeTransfer(beneficiary, message.amount)` on some destination call to revert or leave later beneficiaries unable to redeem, i.e., permanent freezing of funds for other users of the same pool.

### Likelihood Explanation
The `_underlying` token is chosen by the contract owner at `configure()` time and is externally controlled — the contract makes no assumption/enforcement of standard 1:1 ERC20 semantics. Any deployment wrapping a fee-on-transfer, deflationary, or otherwise non-conforming token (or a token that later becomes such via a proxy upgrade) triggers this immediately and deterministically on every `send()`, requiring no special privilege from the caller — a normal token bridger transaction is sufficient to reach this path.

### Recommendation
Mirror the fix already applied in `IntentGatewayV2.sol`: measure `balanceOf(address(this))` before and after `safeTransferFrom`, use the actual received delta as the amount encoded into the dispatched `Message` (or revert if it doesn't match `params.amount`), for both `WrappedHyperFungibleToken.send()` and `WrappedHyperFungibleTokenUpgradeable.send()`.

### Proof of Concept
1. Owner configures `WrappedHyperFungibleToken` with `_underlying` set to a fee-on-transfer ERC20 (charges e.g. 1% fee on transfer).
2. User calls `send({ amount: 100, ... })`. `safeTransferFrom` moves only 99 tokens into the contract (1 taken as fee), but `params.amount = 100` is dispatched unmodified in the `Message`. [4](#0-3) 
3. On the destination chain, `HyperFungibleToken.onAccept` mints 100 tokens to the beneficiary based on `message.amount`. [5](#0-4) 
4. When that beneficiary bridges back 100 tokens to redeem the lock, `WrappedHyperFungibleToken.onAccept` attempts `safeTransfer(beneficiary, 100)` but the contract only ever held 99 for that transfer, plus whatever surplus exists from other users' locked balances — the shortfall compounds across transfers and eventually a transfer reverts, permanently freezing funds for users caught by the insolvency.

            dest: params.dest,
            to: dest,

            timeout: params.timeout,
            fee: params.relayerFee,

    function onAccept(IncomingPostRequest calldata incoming) public virtual override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        Message memory message = abi.decode(request.body, (Message));
        address beneficiary = _toAddr(message.to);
        _mint(beneficiary, message.amount);

        if (message.data.length > 0) {
            ICallDispatcher(_dispatcher).dispatch(message.data);
        }

        emit Received({
            from: message.from,
            to: beneficiary,
            source: string(request.source),
            amount: message.amount
        });
    }
