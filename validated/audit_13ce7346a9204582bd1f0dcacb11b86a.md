This confirms the root cause. Both `process_swap_base_out` and `process_swap_base_out_v2` call `Calculator::swap_token_amount_base_out` (line 2172/2551) with attacker-controlled `swap.amount_out` **before** the `if swap.amount_out >= total_pc_without_take_pnl` / `total_coin_without_take_pnl` bounds check (line 2214/2237, 2593/2616). Inside that function, when `amount_out` equals the pool's `total_pc_without_take_pnl` (or `total_coin_without_take_pnl`) exactly, the denominator of `checked_ceil_div` becomes zero, and `.unwrap()` on the resulting `None` panics.

### Title
Divide-by-zero panic in `swap_token_amount_base_out` reachable via attacker-controlled `amount_out` in SwapBaseOut / SwapBaseOutV2 - (File: program/src/math.rs, program/src/processor.rs)

### Summary
`Calculator::swap_token_amount_base_out` computes `denominator = total_pc_without_take_pnl.checked_sub(amount_out).unwrap()` (or the coin-side equivalent) and then divides by it with `checked_ceil_div(denominator).unwrap()`. This function is invoked by `Processor::process_swap_base_out` and `Processor::process_swap_base_out_v2` with the caller-supplied `swap.amount_out` *before* the program validates that `amount_out < total_{pc,coin}_without_take_pnl`. A caller who sets `amount_out` exactly equal to the pool's available balance drives the denominator to zero, causing `checked_ceil_div` to return `None` and the subsequent `.unwrap()` to panic, aborting the transaction with a Solana program panic.

### Finding Description
In [1](#0-0)  `swap_token_amount_base_out` computes, for `SwapDirection::Coin2PC`:
```
let denominator = total_pc_without_take_pnl.checked_sub(amount_out).unwrap();
amount_in = total_coin_without_take_pnl.checked_mul(amount_out).unwrap().checked_ceil_div(denominator).unwrap()
```
and symmetrically for `PC2Coin` using `total_coin_without_take_pnl`. `checked_sub` succeeds (returns `0`) when `amount_out == total_pc_without_take_pnl` (this is not an overflow, so `.unwrap()` on the subtraction does not panic), but the following `checked_ceil_div(0)` internally calls `checked_div`/`checked_rem` by zero, which returns `None`, causing the outer `.unwrap()` to panic.

The processors call this function with the fully attacker-controlled `swap.amount_out` value before performing the bound check that would reject `amount_out >= total_pc_without_take_pnl`:
- `process_swap_base_out`: computation at [2](#0-1) , and the bound check only happens afterward at [3](#0-2) .
- `process_swap_base_out_v2`: same pattern at [4](#0-3)  and [5](#0-4) .

This is the direct analog of CVE-2014-9763's divide-by-zero crash: attacker-supplied input data drives a denominator computed from subtraction to exactly zero before any validation rejects it, and the program uses an unchecked division (`.unwrap()` on `checked_ceil_div`) instead of returning a graceful error.

### Impact Explanation
Any unprivileged user can submit a single `SwapBaseOut` or `SwapBaseOutV2` transaction with attacker-chosen `amount_out` equal to the current pool balance of the output token (an easily observable, publicly-readable on-chain value: `amm_pc_vault.amount`/`amm_coin_vault.amount` minus `need_take_pnl_*`). This triggers a program panic instead of a controlled error, aborting the current transaction. While Solana transactions fail atomically (no funds are lost in that single tx), this is a denial-of-service/crash-class bug matching the reported CVE's bug class (uncontrolled divide-by-zero from crafted input causing an application crash) directly reachable from the four swap instructions listed in scope.

### Likelihood Explanation
High likelihood of triggering: any user can query the pool's vault balances and PnL state via standard RPC reads (all public on-chain accounts), compute the exact `total_pc_without_take_pnl`/`total_coin_without_take_pnl`, and submit a swap transaction with `amount_out` set to that exact value. No special privileges, timing races, or non-default builds are required — a single crafted transaction with attacker-chosen instruction data is sufficient.

### Recommendation
In `Calculator::swap_token_amount_base_out` (`program/src/math.rs`), replace the `.unwrap()` calls on `checked_sub` and `checked_ceil_div` with proper error propagation (e.g., return `Result`/`Option` and bubble up `AmmError`) instead of panicking, and/or move the `amount_out >= total_pc_without_take_pnl` / `total_coin_without_take_pnl` bound checks in `process_swap_base_out` and `process_swap_base_out_v2` to occur *before* calling `swap_token_amount_base_out`, so a zero or negative denominator condition is rejected with a normal program error rather than a panic.

### Proof of Concept
1. Read the pool's `AmmInfo` account and vaults to compute `total_pc_without_take_pnl = amm_pc_vault.amount - amm.state_data.need_take_pnl_pc` (Coin2PC direction target).
2. Submit a `SwapBaseOut` (tag `11`) instruction (or `SwapBaseOutV2`) with `user_token_source` mint = coin mint, `user_token_destination` mint = pc mint, and `amount_out` set exactly equal to `total_pc_without_take_pnl`, with `max_amount_in` set high enough to pass later slippage checks (irrelevant since panic occurs first).
3. The call reaches `Calculator::swap_token_amount_base_out(swap.amount_out.into(), total_pc_without_take_pnl.into(), total_coin_without_take_pnl.into(), SwapDirection::Coin2PC)` at [2](#0-1) , computing `denominator = total_pc_without_take_pnl.checked_sub(amount_out).unwrap() == 0`, then `checked_ceil_div(0).unwrap()` panics as shown in [6](#0-5) .
4. The transaction aborts with a runtime panic instead of returning the intended `AmmError::InsufficientFunds`.

    pub fn swap_token_amount_base_out(
        amount_out: U128,
        total_pc_without_take_pnl: U128,
        total_coin_without_take_pnl: U128,
        swap_direction: SwapDirection,
    ) -> U128 {
        let amount_in;
        match swap_direction {
            SwapDirection::Coin2PC => {
                // (x + delta_x) * (y + delta_y) = x * y
                // (coin + amount_in) * (pc - amount_out) = coin * pc
                // => amount_in = coin * pc / (pc - amount_out) - coin
                // => amount_in = (coin * pc - pc * coin + amount_out * coin) / (pc - amount_out)
                // => amount_in = (amount_out * coin) / (pc - amount_out)
                let denominator = total_pc_without_take_pnl.checked_sub(amount_out).unwrap();
                amount_in = total_coin_without_take_pnl
                    .checked_mul(amount_out)
                    .unwrap()
                    .checked_ceil_div(denominator)
                    .unwrap()
            }
            SwapDirection::PC2Coin => {
                // (x + delta_x) * (y + delta_y) = x * y
                // (pc + amount_in) * (coin - amount_out) = coin * pc
                // => amount_out = coin - coin * pc / (pc + amount_in)
                // => amount_out = (coin * pc + coin * amount_in - coin * pc) / (pc + amount_in)
                // => amount_out = coin * amount_in / (pc + amount_in)

                // => amount_in = coin * pc / (coin - amount_out) - pc
                // => amount_in = (coin * pc - pc * coin + pc * amount_out) / (coin - amount_out)
                // => amount_in = (pc * amount_out) / (coin - amount_out)
                let denominator = total_coin_without_take_pnl.checked_sub(amount_out).unwrap();
                amount_in = total_pc_without_take_pnl
                    .checked_mul(amount_out)
                    .unwrap()
                    .checked_ceil_div(denominator)
                    .unwrap()
            }
        }
        return amount_in;
    }
