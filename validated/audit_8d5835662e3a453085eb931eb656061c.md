### Title
Backend enrollment/signature verification is unconditionally skipped for `user_centric_signup` sessions, allowing signup success to be reported without server-side uniqueness/attestation confirmation - (File: `src/plans/mod.rs`)

### Summary
The external report describes a class of bug where a protocol omits an explicit, verifiable acceptance/tolerance gate that is supposed to protect the operation's outcome (here: a user-supplied minimum), so the operation blindly proceeds and reports success under unfavorable/unverified conditions. The closest reachable analog in orb-core is `MasterPlan::do_signup` in `src/plans/mod.rs`, where the decision to treat a signup as successful is short-circuited based on the `user_centric_signup` flag, bypassing the call to `enroll_user::Plan::run` (the only code path that computes the secure-element signature and submits/polls the backend `signup_post`/`signup_poll` enrollment endpoints).

`user_centric_signup` originates from `backend::user_status::UserData::user_centric_signup`, which is set from `authenticated_app_data.user_centric_signup` returned by the `/status` session endpoint: [2](#0-1) [3](#0-2) 

When this flag is `true` (and the orb config does not explicitly override it via `ignore_user_centric_signups`, which defaults to `false`): [4](#0-3) 

the orb **never calls `enroll_user`**, meaning:
- The cryptographic secure-element signature over the iris/mask codes (`make_signature`, which binds the orb identity and iris data together and is meant as proof that a genuine orb performed the biometric verification) is never computed or sent to the backend. [5](#0-4) 
- The `signup_post::request` / `signup_poll::request` calls — the only calls that submit the enrollment for backend-side validation (e.g. duplicate/uniqueness checks, deprecation/blocking checks, and the actual completion status) — are skipped entirely. [6](#0-5) 
- Instead, `success` is derived purely from the *local* `signup_reason`, which is computed from the local biometric pipeline result and the (in this FOSS build) empty fraud-check engine: [7](#0-6) 

This is directly analogous to the reported DeFi bug class: a critical acceptance/verification gate (there: user-specified minimum output; here: backend-side enrollment/uniqueness verification and secure-element attestation) is not enforced, and the "unrestricted" path silently accepts the outcome instead of requiring proof from the authoritative party (the backend / global uniqueness service).

### Impact Explanation
The World ID enrollment flow's core anti-Sybil guarantee depends on the backend performing global iris/identity uniqueness checks and validating the secure-element attestation signature during `signup_post`/`signup_poll`. By skipping `enroll_user` whenever `user_centric_signup` is true, the orb can locally report a signup as `Success` (and mark the debug report/enrollment status accordingly) without the backend ever confirming or refuting uniqueness, and without any cryptographic attestation binding this specific orb hardware to the produced iris codes. This can result in misattributed/unverified signups being reported as successful, and removes a fraud/duplicate-enrollment enforcement boundary that the rest of the codebase depends on the backend for (since local fraud checks are already stripped, per `N_FRAUD_CHECKS = 0` in `src/plans/fraud_check.rs`).

### Likelihood Explanation
`user_centric_signup` is a boolean returned by the backend per-session and is not directly forgeable by an anonymous, unprivileged actor scanning a QR code in the field; however, the flag is part of the app-driven ("user-centric") signup flow, which is on by default (`ignore_user_centric_signups: false`) and requires no explicit operator action to enable. Any session for which the backend sets `user_centric_signup = true` — the normal app-driven flow — automatically takes this shortcut, so the exposure is broad by default rather than requiring a rare condition, though it does require whatever party controls session creation to set the flag (typically the World App backend/session, not a random passerby).

### Recommendation
Do not bypass the backend enrollment/verification path for `user_centric_signup` sessions. At minimum, still compute and submit the secure-element signature and invoke the backend enrollment/verification endpoint (or an equivalent lightweight verification call) so that uniqueness/attestation checks are always enforced server-side before a signup is marked `Success`, mirroring the recommendation from the source report to always require an explicit, server/verified minimum acceptance criterion rather than trusting a locally-derived result.

### Proof of Concept
Not independently exploitable purely client-side by an unprivileged QR-scanning bystander without control over the backend's `user_centric_signup` flag; the control-flow bypass itself is deterministic and directly observable in code: whenever `user_centric_signup == true` and `ignore_user_centric_signups == false` (the default), `do_signup` takes the branch at `src/plans/mod.rs:639-645` and returns `success = (signup_reason == SignupReason::Normal)` without ever calling `self.enroll_user(...)`, which is the only code path performing secure-element signing (`src/plans/enroll_user.rs:290-304`) and backend `signup_post`/`signup_poll` requests (`src/plans/enroll_user.rs:72-102`).

fn make_signature(user_qr_code: &qr_scan::user::Data, pipeline: &Pipeline) -> Result<String> {
    let mut ctx = Context::new(&SHA256);
    ctx.update(ORB_ID.as_str().as_bytes());
    ctx.update(user_qr_code.user_id.as_bytes());
    ctx.update(pipeline.v2.ir_net_version.as_bytes());
    ctx.update(pipeline.v2.iris_version.as_bytes());
    ctx.update(pipeline.v2.eye_left.iris_code.as_bytes());
    ctx.update(pipeline.v2.eye_left.mask_code.as_bytes());
    ctx.update(pipeline.v2.eye_left.iris_code_version.as_bytes());
    ctx.update(pipeline.v2.eye_right.iris_code.as_bytes());
    ctx.update(pipeline.v2.eye_right.mask_code.as_bytes());
    ctx.update(pipeline.v2.eye_right.iris_code_version.as_bytes());
    let signed = secure_element::sign(ctx.finish())?;
    Ok(BASE64.encode(&signed))
}
