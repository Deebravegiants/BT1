### Title
Stranded/leftover ERC-20 balance in `LifiExternalAction` can be swept into a fully-backed shielded UTXO by any unprivileged caller with zero nullifier spend - (File: `contracts/external-actions/swaps/LifiExternalAction.sol`)

### Summary
`LifiExternalAction.callRouter` grants `router` an unlimited, persistent ERC-20 allowance and then forwards fully attacker-chosen `externalActionMetadata` to `router.call(...)` without ever constraining how much of `inputToken` the router actually pulls. `ExternalActionSwap.swap` computes `swappedAmount` purely from the output-token balance delta of `LifiExternalAction`, never checking that it corresponds to the caller's own `-deltaAmounts[0]`. Any residual `inputToken` balance left in `LifiExternalAction` (whether from a caller who deliberately under-pulls, or any other residue) is already pre-approved to `router` and can be pulled by a completely unrelated, subsequent `transact()` call that declares `amountChanges = 0` / no nullifiers for that token, letting it mint itself a real, on-chain-backed shielded UTXO funded entirely by someone else's stranded value.

### Finding Description
Equality that must hold and is broken across two transactions targeting the same `LifiExternalAction` instance:
`tokens actually leaving LifiExternalAction to router in a given call` **should equal** `-deltaAmountChanges[0]` that `Hinkal._externalTransact` sent to `LifiExternalAction` for *that same* call. Nothing enforces this.

Path:
- `Hinkal._externalTransact` (`contracts/Hinkal.sol:234-261`) transfers `uint256(-deltaAmountChanges[i])` of `inputToken` to `LifiExternalAction` based purely on the caller's own proven `amountChanges`, then calls `runAction` → `ExternalActionSwap.swap` (`contracts/external-actions/swaps/ExternalActionSwap.sol:40-102`).
- `swap` computes `inputAmount = uint256(-deltaAmounts[0])` (line 45) but this value is **never used to authorize or bound** the router call — it is only passed as a plain function argument to `callRouter`. [1](#0-0) 
- `LifiExternalAction.callRouter` calls `approveUnlimited(inputToken, router)` (persistent `type(uint256).max` allowance, only reset if it drops below half-max) and then executes `router.call(externalActionMetadata)` — fully attacker-supplied calldata, with no check that the router pulled `inputAmount` (or any specific amount) of `inputToken`. [2](#0-1) 
- `swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore` (line 35) is derived solely from the *output*-token balance delta; it is disconnected from `inputAmount` and from how much `inputToken` actually left the contract.
- Back in `Hinkal.transact`, the only cross-checks are per-token balance equalities on **Hinkal's own** balance (`contracts/Hinkal.sol:97-147`): `balanceDif == (onChainCreation[i] ? 0 : amountChanges[i]) + utxoAmount`. For the output token, callers set `onChainCreation[i] = true`, which `HinkalHelper.checkOnchainCreation` requires to pair with `amountChanges[i] == 0` and zero nullifiers for that index — this is the legitimate mechanism for creating an on-chain UTXO whose amount is only known after the swap executes. The circuit (`MainEVMCircuit.circom`) never sees or constrains this token row at all in that case. [3](#0-2) 

Exploit flow:
1. Any unprivileged EOA calls `transact()` targeting `LifiExternalAction` with a genuine input deposit (their own nullifiers burned) for `inputToken`, but crafts `externalActionMetadata` so the LI.FI router pulls **less** than `inputAmount`. The remainder stays in `LifiExternalAction`, which already holds an unlimited allowance to `router`. All existing Hinkal/circuit equalities still hold for this transaction because they only check *this caller's own* balance deltas and UTXO amounts, not what fraction of the transferred input was actually consumed by the router.
2. A second, unrelated unprivileged EOA calls `transact()` targeting the same `LifiExternalAction`, setting `amountChanges[inputTokenIndex] = 0` (no nullifiers spent for `inputToken`, so `deltaAmountChanges[inputTokenIndex] = 0` and `Hinkal` transfers nothing new to `LifiExternalAction`), and for `outputToken` sets `onChainCreation = true`, `amountChanges = 0`. Their own `externalActionMetadata` instructs the router to pull the residual stranded `inputToken` balance (using the pre-existing unlimited allowance) and swap it for real `outputToken`.
3. `swappedAmount` reflects this real, non-zero value; it is transferred to `Hinkal` and wrapped into `utxoSet[0]`, which — because `onChainCreation=true` — is inserted directly as a valid on-chain commitment with no circuit constraint tying its amount to any nullifier spend by the second caller.
4. All `Hinkal.transact` equalities (`balanceDif == amountChanges[i] + utxoAmount`, slippage) are satisfied trivially because they are self-referential to the second caller's own transaction, not to the true origin of the funds.

Existing guards fail because: `performHinkalChecks`/`checkOnchainCreation`/`dimensionsCheck` only validate structural consistency and that `onChainCreation` pairs with zero `amountChanges`/nullifiers — they do not (and cannot, since it's a Solidity-side check) verify that the swapped value used to back an `onChainCreation` UTXO originated from that same transaction's own deposited input. `insertNullifiers`/`rootHashExists`/`verifyProof` never come into play for the stolen portion since no nullifier is spent for it.

### Impact Explanation
Critical — theft of another depositor's already-nullified/burned shielded value and minting of a legitimately-inserted shielded UTXO with no corresponding nullifier spend or backing by the thief. This directly matches "theft of shielded or in-flight user funds" / "minting shielded value without backing." It is repeatable against any residual balance left in the shared `LifiExternalAction` singleton and is not limited to a single incident — any future stranded balance (deliberate or accidental) is sweepable by any subsequent caller.

### Likelihood Explanation
The attacker needs no privileged role: only the ability to deposit their own funds, generate their own valid proof, and craft `externalActionMetadata` — all explicitly permitted to unprivileged users. The "stranding" step is entirely under the attacker's control (they choose the LI.FI calldata pulling less than `inputAmount`), and the "sweep" step only requires observing `LifiExternalAction`'s public ERC-20 balance and crafting a second proof with `amountChanges=0`/no nullifiers for the input token and `onChainCreation=true` for the output token — both explicitly allowed combinations per `checkOnchainCreation`. Cost is just two ordinary `transact()` calls; the technique is fully repeatable and does not depend on any router pricing defect (the router executes a real swap of real balance at real cost, only the *authorization* to spend it is misappropriated by the second, unrelated call).

### Recommendation
In `LifiExternalAction.callRouter`/`ExternalActionSwap.swap`, enforce that the router pulls exactly `inputAmount` of `inputToken` from `LifiExternalAction` (e.g., snapshot `inputToken` balance before/after the router call and `require` the decrease equals `inputAmount`), and avoid persistent unlimited allowances across calls (approve exactly `inputAmount` per call, or reset allowance to zero after each `callRouter` invocation) so no residual pre-approved balance can ever be swept by a later, unrelated caller.

### Proof of Concept
Foundry fork test plan:
1. Deploy `Hinkal`, `HinkalHelper`, `LifiExternalAction` pointed at a mock `router` contract that implements a `partialPull(address token, uint256 pull, uint256 give, address outToken)` selector: transfers `pull` of `token` from `msg.sender` (LifiExternalAction) to itself via `transferFrom`, then sends `give` of `outToken` back to `msg.sender`.
2. EOA #1 deposits `inputAmount = 1000` `inputToken` into the shielded pool, generates a valid proof, and calls `Hinkal.transact` with `externalActionId` = LifiExternalAction, `amountChanges[0] = -1000`, `externalActionMetadata` calling `partialPull(inputToken, 400, X, outputToken)` (only pulls 400, strands 600 `inputToken` in `LifiExternalAction`, already infinite-approved to `router`).
   - Assert `IERC20(inputToken).balanceOf(address(lifiExternalAction)) == 600` after tx1.
3. EOA #2 (different address, no relationship to EOA #1, zero prior shielded balance for `inputToken`) generates its own proof with `amountChanges[inputTokenIndex] = 0`, no nullifiers for `inputToken`, `onChainCreation[outputTokenIndex] = true`, `amountChanges[outputTokenIndex] = 0`, and `externalActionMetadata` calling `partialPull(inputToken, 600, Y, outputToken)` to sweep the stranded 600.
   - Assert `Hinkal.transact` for EOA #2 succeeds (no revert on slippage/balance/proof checks).
   - Assert the new on-chain commitment inserted for EOA #2 encodes `amount == Y` (backed by the stolen 600 `inputToken`), while EOA #2 spent zero nullifiers and contributed zero `inputToken`.
   - Assert `IERC20(inputToken).balanceOf(address(lifiExternalAction)) == 0` after tx2, and that EOA #2 can later withdraw/spend this UTXO as a normal shielded balance, proving theft of EOA #1's stranded 600 `inputToken` equivalent value.

```text
    function callRouter(
        address inputToken,
        uint256 inputAmount,
        address outputToken,
        bytes calldata externalActionMetadata
    ) internal override returns (uint256 swappedAmount) {
        uint256 balanceBefore = getERC20OrETHBalance(outputToken);

        if (inputToken == address(0)) {
            (bool success, ) = router.call{value: inputAmount}(
                externalActionMetadata
            );
            require(success, "LI.FI swap failed: native coin");
        } else {
            approveUnlimited(inputToken, router);
            (bool success, ) = router.call(externalActionMetadata);
            require(success, "LI.FI swap failed: erc-20 token");
        }

        swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore;
    }
```
