## Finding

### Title
OAuth `begin_auth` fails to validate the `shop` domain before building the authorize redirect, enabling open-redirect–driven session fixation / forced OAuth completion - (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
`ShopifyAPI::Auth::Oauth.begin_auth` builds the Shopify authorization redirect URL directly from the caller-supplied `shop` string, with no validation that it is a trusted `*.myshopify.com` (or other trusted Shopify) domain. This breaks the equality that should hold before the OAuth handshake starts: `shop used to build the authorize redirect == a shop validated against ShopifyAPI::Utils::ShopValidator`. That validation already exists in the gem and is applied in sibling OAuth-adjacent flows, but is missing here.

### Finding Description
`begin_auth` sets a `state` nonce, stores it in a `SessionCookie`, and then redirects the browser to `auth_base_uri(shop) + "/oauth/authorize?..."`: [1](#0-0) 

`auth_base_uri` builds the host straight from the raw `shop` argument with no format check: [2](#0-1) 

By contrast, the gem added `ShopifyAPI::Utils::ShopValidator` specifically to enforce this binding (`sanitize!` raises `Errors::InvalidShopError` unless the shop resolves to a `TRUSTED_SHOPIFY_DOMAINS` domain), and this validator is applied in `ClientCredentials.client_credentials` and `RefreshToken.refresh_access_token` before those flows send the app's `client_secret` to the resulting host: [3](#0-2) [4](#0-3) [5](#0-4) 

`begin_auth` and `validate_auth_callback` are the two places that never apply this same sanitation to the `shop` value used to construct the authorize redirect / OAuth session: [6](#0-5) 

The documented usage pattern confirms hosts are expected to pass through a raw `shop` value (e.g. from a request header) directly into `begin_auth` with no sanitization step shown or required: [7](#0-6) 

This is the same bug class as the Hats Protocol report: a value that is supposed to be constrained/validated (there, `newThreshold` bounded by `target`; here, `shop` bounded to `TRUSTED_SHOPIFY_DOMAINS`) is instead used unchecked in a security-critical call, even though the correct guarded value/pattern already exists elsewhere in the same codebase.

### Impact Explanation
Because `shop` is not validated as a genuine Shopify domain, an unprivileged attacker who can get a victim merchant/admin to hit the app's login route with an attacker-chosen `shop` (e.g., `shop=evil.com`) causes:
1. The app to set a `state` nonce cookie on the victim's browser.
2. The victim's browser to be redirected (open redirect) to `https://evil.com/admin/oauth/authorize?client_id=...&scope=...&redirect_uri=...&state=<nonce>`, leaking the app's `client_id`, `redirect_uri`, and the exact `state` nonce to the attacker's server as plain GET parameters.
3. The attacker, now knowing the victim's exact `state` value, initiates their own legitimate Shopify OAuth authorize request using their own shop but sets `state=<the stolen nonce>`.
4. Shopify legitimately signs and returns this callback (with the attacker's real `shop`/`code`, but the victim's `state`) to the app's redirect_uri; because Shopify itself computed the HMAC over these exact returned parameters, `Utils::HmacValidator.validate` in `validate_auth_callback` succeeds, and `state == auth_query.state` also succeeds since it matches the victim's cookie.
5. The app completes OAuth and binds a session using `auth_query.shop` (the attacker's shop) while operating under the victim's browser/cookie context — a forced OAuth completion / session fixation scenario, as explicitly enumerated as a High-impact class.

No possession of the app's `api_secret_key` or the merchant's access token is required by the attacker; only the ability to send the victim a crafted install link and to complete a normal OAuth install for their own shop.

### Likelihood Explanation
Reaching `begin_auth` only requires the standard, always-reachable app install/login entry point with attacker-controlled `shop` — exactly the pattern shown in the gem's own docs example. No secret material, privileged account, or host-app misuse of the documented API is required; the gem's own `begin_auth`/`auth_base_uri` code path is what constructs the unsafe redirect.

### Recommendation
Apply `ShopifyAPI::Utils::ShopValidator.sanitize!(shop)` (consistent with `ClientCredentials` and `RefreshToken`) inside `Oauth.begin_auth` before calling `auth_base_uri(shop)`, and likewise sanitize `auth_query.shop` in `Oauth.validate_auth_callback` before it is used to build the OAuth session/host, rejecting any `shop` that does not resolve to a domain in `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`.

### Proof of Concept
1. Attacker sends victim a link to the app's login route with `shop=evil.com`.
2. App calls `ShopifyAPI::Auth::Oauth.begin_auth(shop: "evil.com", redirect_path: "/auth/callback")`; per `lib/shopify_api/auth/oauth.rb:117-128`, `auth_base_uri("evil.com")` returns `"https://evil.com/admin"` with no domain check.
3. Victim's browser is set with the `state` cookie and redirected to `https://evil.com/admin/oauth/authorize?client_id=...&scope=...&redirect_uri=...&state=<nonce>` (attacker-controlled server logs the `state`).
4. Attacker performs a genuine OAuth authorize request to real Shopify for their own store, supplying `state=<stolen nonce>` as the `state` parameter.
5. Shopify redirects to the app's real callback URL with a validly-HMAC-signed query (`shop=attacker-shop.myshopify.com`, `code=...`, `state=<stolen nonce>`).
6. Attacker causes the victim's browser (still holding the fixed `state` cookie) to load this callback URL. `ShopifyAPI::Auth::Oauth.validate_auth_callback` (`lib/shopify_api/auth/oauth.rb:60-73`) passes HMAC validation and state-match validation, completing OAuth bound to the attacker's shop under the victim's session context.

      TRUSTED_SHOPIFY_DOMAINS = T.let(
        [
          "shopify.com",
          "myshopify.io",
          "myshopify.com",
          "spin.dev",
          "shop.dev",
        ].freeze,
        T::Array[String],
      )

      class << self
        extend T::Sig

        sig do
          params(
            shop_domain: String,
            myshopify_domain: T.nilable(String),
          ).returns(T.nilable(String))
        end
        def sanitize_shop_domain(shop_domain, myshopify_domain: nil)
          uri = uri_from_shop_domain(shop_domain, myshopify_domain)
          return nil if uri.nil? || uri.host.nil? || uri.host.empty?

          trusted_domains(myshopify_domain).each do |trusted_domain|
            host = T.cast(uri.host, String)
            uri_domain = uri.domain
            next if uri_domain.nil?

            no_shop_name_in_subdomain = host == trusted_domain
            from_trusted_domain = trusted_domain == uri_domain

            if unified_admin?(uri) && from_trusted_domain
              return myshopify_domain_from_unified_admin(uri)
            end
            return nil if no_shop_name_in_subdomain || host.empty?
            return host if from_trusted_domain
          end
          nil
        end

        sig do
          params(
            shop: String,
            myshopify_domain: T.nilable(String),
          ).returns(String)
        end
        def sanitize!(shop, myshopify_domain: nil)
          host = sanitize_shop_domain(shop, myshopify_domain: myshopify_domain)
          if host.nil? || host.empty?
            raise Errors::InvalidShopError,
              "shop must be a trusted Shopify domain (see ShopValidator::TRUSTED_SHOPIFY_DOMAINS), got: #{shop.inspect}"
          end

          host
        end

    auth_response = ShopifyAPI::Auth::Oauth.begin_auth(shop: domain, redirect_path: "/auth/callback")

    # Store the authorization cookie

    head 307
