## Title
Webhook `Request#shop` (and other Shopify headers) are not covered by the HMAC signature, allowing cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` verifies webhook authenticity using `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `to_signable_string`. That method returns only the raw request body [1](#0-0)  . The `shop` value exposed by the same class, however, is read directly from the `X-Shopify-Shop-Domain` header and is never included in the signed payload [2](#0-1)  . `Registry.process` validates the HMAC and then hands `request.shop` straight to the webhook handler as the tenant identity, with no additional cross-check [3](#0-2)  .

### Finding Description
The binding the library is supposed to guarantee is:
`hmac_valid(raw_body, secret) == true` `⇒` `shop header is authentic for that raw_body`

In reality the HMAC only binds the raw body bytes to the secret; it says nothing about which shop the request is "from". The equality that actually holds is:
`hmac(raw_body) is valid` AND `shop header is attacker-controlled / unauthenticated`

Any party that can obtain one legitimately-signed webhook (e.g., an attacker who installs the app on their own store and receives a real webhook with a valid HMAC over that body) can replay that exact `raw_body`/`hmac` pair to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. `HmacValidator.validate` will still succeed, because it never looks at the shop header [4](#0-3)  , and `Registry.process` will invoke the registered handler with `WebhookMetadata` claiming the victim's shop [5](#0-4)  .

This is the same class of bug as the referenced report: a privileged/trust-bearing action (`restakeToken` bypassing the owner check because a boolean flag it doesn't control decides the guard) is performed using an assumption ("the caller controls only what the signature covers") that the code does not actually enforce ("only the raw body is covered, not the shop identity attached to it").

### Impact Explanation
This breaks the tenant boundary the HMAC is supposed to enforce: a webhook payload can be attributed to any shop domain the attacker chooses while still passing signature verification. Depending on how the host application's webhook handlers use `shop` (e.g., mandatory `shop/redact`, `customers/redact`, `app/uninstalled`, or any topic that triggers data deletion/state changes keyed by shop), this enables cross-tenant data corruption or forged lifecycle events against a shop the attacker does not control, satisfying the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Exploitation only requires the attacker to install the app on a store they control (an ordinary, unprivileged action) to obtain one valid `raw_body`/HMAC pair, then send a forged HTTP request to the app's already-public webhook endpoint with a different `Shop-Domain` header. No access token, `client_secret`, or victim credential is required, making this practically exploitable by any unprivileged internet user who knows/guesses the webhook endpoint URL (typically documented/predictable, e.g. `/webhooks`).

### Recommendation
Include `shop` (and ideally `topic`, `webhook_id`, `api_version`) in the signable payload used for a secondary/internal integrity check, or have `Registry.process`/host apps independently verify that the shop domain in the header matches an actual installed/known shop before trusting it — never treat `request.shop` as authenticated purely because the raw-body HMAC validated.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a real, self-owned store) and triggers a webhook topic the app registers (e.g., `orders/create`), capturing the raw POST body and the legitimate `X-Shopify-Hmac-Sha256` header Shopify sent.
2. Attacker replays that exact body and HMAC header to the app's public webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `to_signable_string` (`@raw_body` only) — it matches, since the body is unchanged [6](#0-5) [7](#0-6)  .
4. The registered handler is invoked with `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body:, ...)` [5](#0-4)  , even though the payload actually originated from the attacker's own shop.
