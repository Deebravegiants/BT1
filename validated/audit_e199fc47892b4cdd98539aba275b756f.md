### Title
`Webhooks::Registry.process` trusts an unauthenticated `shop-domain` header as tenant identity because the webhook HMAC signs only the body, never the shop - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`Webhooks::Registry.process` accepts a webhook once `Utils::HmacValidator.validate(request)` succeeds, then builds `WebhookMetadata` using `request.shop`, which is read verbatim from the `X-Shopify-Shop-Domain` header. Because `Request#to_signable_string` returns only the raw body and the HMAC never covers any header, the shop-domain header is completely detached from the cryptographic proof, so any request carrying a previously-valid `(body, hmac)` pair passes validation regardless of what shop-domain header is attached to it.

### Finding Description
The invariant that should hold is:

`shop authenticated by HMAC(secret, signable_string) == shop delivered to the host app as WebhookMetadata#shop`

Tracing the code:

- `Request#to_signable_string` returns `@raw_body` only [1](#0-0) 
- `Request#shop` is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic tie to the signature [2](#0-1) 
- `HmacValidator.validate_signature` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it only against the received HMAC — the shop, topic, and webhook-id headers never enter the signable string or the comparison [3](#0-2) 
- `Registry.process` gates only on this body-only HMAC check, then hands `request.shop` straight into `WebhookMetadata`, which the host app uses to select the tenant record to mutate [4](#0-3) 
- `WebhookMetadata#shop` is declared as a plain `String` const with no validation (`ShopValidator.sanitize!` is never invoked here) [5](#0-4) 

Because the app's `api_secret_key` (`Context.api_secret_key`) is a single secret shared across every shop that installs the app, an attacker can install the target app on their own development shop, receive a legitimately Shopify-signed webhook `(body, hmac)` pair for their own shop, and then submit that exact `(body, hmac)` pair directly to the host app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header (e.g., a victim merchant's domain). `HmacValidator.validate` still returns `true` because it only re-derives the HMAC from the body — it never checks that the shop header corresponds to the shop that actually produced that body/signature. `Registry.process` then calls the host app's `handler.handle` with `WebhookMetadata#shop` equal to the attacker-chosen victim domain, even though nothing about that domain was ever verified.

None of the listed guards close this gap: `HmacValidator.validate` is exactly the vulnerable check; `ShopValidator.sanitize!` is not called anywhere in the webhook path; there is no `state` comparison or JWT (`aud`/`iss`/`sub`) involved in webhook delivery at all; `HttpRequest#verify`, `Context.setup?/private?/embedded?` govern OAuth/session-token flows, not webhook processing.

### Impact Explanation
Any host application that follows the documented pattern of trusting `WebhookMetadata#shop` as the authenticated tenant identifier (the gem's own docs present this field as the "shop" the webhook is "for") will perform reads or writes scoped to whatever shop domain the attacker places in the header, as long as the attacker can produce one valid `(body, hmac)` pair from any shop, including their own. This is a full cross-tenant break: the attacker never needs the victim's data, session, or access token — they only need their own legitimately delivered webhook for the app and a way to POST the replayed body/HMAC with a substituted shop header to the app's public webhook endpoint. This is repeatable against arbitrary victim shop domains (which are often guessable/enumerable `*.myshopify.com` handles) for every topic the app has registered a handler for.

### Likelihood Explanation
Preconditions are minimal and entirely within the attacker's control: they install the target app (any app built on this gem) on their own store, trigger an action that generates a webhook of a topic they want to attack, capture the resulting `(body, hmac)` at their own receiving endpoint, and replay it to the same public webhook URL with a forged `shop-domain` header. No secret, access token, or victim interaction is required. The cost is a single webhook capture plus one replayed HTTP request; it is fully repeatable and scriptable.

### Recommendation
Bind the shop identity to the verified payload instead of trusting a bare header:
- Include the `shop-domain` (and ideally `topic`, `webhook-id`) in the signable string used for HMAC computation, or otherwise cryptographically tie the header set to the signature, so a replayed body/HMAC cannot be paired with a different shop header.
- At minimum, run `ShopValidator.sanitize!` on `request.shop` before constructing `WebhookMetadata`, and require host apps to cross-check the delivered shop against a shop known to have this webhook subscription (e.g., verified via the `webhook_id` looked up server-side), rather than trusting the header value as-is.

### Proof of Concept
```ruby
# test/webhooks/shop_header_forgery_test.rb
require "test_helper"

class ShopHeaderForgeryTest < Test::Unit::TestCase
  def setup
    ShopifyAPI::Context.setup(
      api_key: "key",
      api_secret_key: "sekrit",
      api_version: "2023-01",
      host_name: "app.example.com",
      scope: "read_products",
      is_private: false,
      is_embedded: true,
    )
  end

  def test_shop_header_is_unbound_from_hmac_and_can_be_forged
    body = '{"id":123}'
    computed = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), "sekrit", body)
    hmac_b64 = Base64.strict_encode64(computed)

    attacker_headers = {
      "x-shopify-topic" => "orders/create",
      "x-shopify-hmac-sha256" => hmac_b64,
      "x-shopify-shop-domain" => "attacker-shop.myshopify.com",
      "x-shopify-api-version" => "2023-01",
      "x-shopify-webhook-id" => "1",
    }
    attacker_request = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: attacker_headers)
    assert ShopifyAPI::Utils::HmacValidator.validate(attacker_request)
    assert_equal "attacker-shop.myshopify.com", attacker_request.shop

    # Replay identical body/hmac, only the shop header changes.
    forged_headers = attacker_headers.merge("x-shopify-shop-domain" => "victim-shop.myshopify.com")
    forged_request = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: forged_headers)

    # Signature still validates: shop was never part of the signed data.
    assert ShopifyAPI::Utils::HmacValidator.validate(forged_request)
    # But the "verified" shop is now the victim's, not the shop that actually produced the signature.
    assert_equal "victim-shop.myshopify.com", forged_request.shop

    received_shop = nil
    handler = Class.new do
      extend T::Sig
      include ShopifyAPI::Webhooks::WebhookHandler
      define_method(:handle) { |data:| received_shop = data.shop }
    end.new

    ShopifyAPI::Webhooks::Registry.add_registration(
      topic: "orders/create", delivery_method: :http, path: "/webhooks", handler: handler,
    )
    ShopifyAPI::Webhooks::Registry.process(forged_request)

    # Host app's handler receives an attacker-chosen shop despite a "validated" webhook.
    assert_equal "victim-shop.myshopify.com", received_shop
  end
end
```
This demonstrates the equality `shop authenticated by HMAC == shop delivered as WebhookMetadata#shop` is false: the HMAC validates purely on body content, and the shop header — the value the host app treats as verified tenant identity — can be swapped to any string, including a victim shop's domain, without invalidating the signature.
