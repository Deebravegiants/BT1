### Title
Webhook HMAC only covers the request body, not the `shop-domain` header, allowing cross-tenant webhook replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, and `Utils::HmacValidator.validate` verifies the HMAC solely against that body. The `shop` (from the `X-Shopify-Shop-Domain` header) used by `Webhooks::Registry.process` to route the webhook to the host application's handler is never bound to the HMAC. This lets a party who legitimately owns one shop (and thus receives genuinely-signed webhooks for it) replay the exact same body+HMAC pair while swapping only the shop-domain header, causing the host app to apply another tenant's webhook to a different shop.

### Finding Description
The HMAC validation in this gem authenticates the *body* of a webhook request but not the header fields that are used to determine which tenant (shop) the payload belongs to: [1](#0-0) 

`to_signable_string` returns `@raw_body` exclusively — `shop`, `topic`, `api_version`, and `webhook_id` are all pulled from unauthenticated headers: [2](#0-1) 

`HmacValidator.validate` / `validate_signature` only ever hash `verifiable_query.to_signable_string`, i.e., just the body for webhook requests: [3](#0-2) 

`Registry.process` checks the HMAC and then immediately builds `WebhookMetadata` (routed to the handler) using the unauthenticated `request.shop`: [4](#0-3) 

The identity binding broken is an equality that should hold but does not:
`shop_that_produced_the_valid_HMAC(body) == shop_passed_to_handler_as_tenant_identity`

Since the shop header is not part of the signed material, both sides can diverge: the HMAC only proves "this body was signed with the app's secret at some point for some shop," not "this body belongs to shop X." An attacker who is a legitimate merchant of the app receives a real webhook (real body + real HMAC) for their own store. Because the HMAC over that captured body/signature pair remains valid regardless of what shop-domain header accompanies it, the attacker can resend the identical body and HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header with a victim shop's domain. `Registry.process` will pass HMAC validation (it only checks the body) and hand the handler a `WebhookMetadata` claiming `shop: <victim>`, `body: <attacker's own data>`.

### Impact Explanation
If the host application uses `WebhookMetadata#shop` to select which merchant's session/records the webhook payload should be applied to (the intended and documented use of this field), this allows cross-tenant data injection/corruption — an attacker can write their own webhook content into another merchant's tenant context. This matches the Critical "cross-tenant access" impact category, since the gem's own header-parsing/validation logic is the root cause, not a host misuse of an undocumented API — the library documents `shop` on `WebhookMetadata` as a trustworthy source of tenant identity once HMAC validation succeeds.

### Likelihood Explanation
Requires: (1) attacker has (or briefly controls) at least one legitimate installed shop of the target app so a real webhook is delivered to them, and (2) attacker can control/replay raw HTTP headers to the app's public webhook endpoint (trivial for any internet-facing endpoint, no secret needed). No access to `api_secret_key`, tokens, or TLS interception is required — only observation of one's own legitimately-received webhook traffic.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the HMAC-signed material, or otherwise cryptographically bind the shop identity to the payload before exposing it via `WebhookMetadata`. At minimum, `Webhooks::Request#to_signable_string` should incorporate the `shop-domain` header (matching how Shopify's own webhook signing actually covers the full delivered payload/headers used for routing), and `Registry.process` should reject/flag any mismatch between the shop encoded in the body (if present) and the header-derived shop.

### Proof of Concept
1. App installs on `attacker-shop.myshopify.com`; app receives a legitimate webhook: body `B`, header `X-Shopify-Hmac-Sha256: H` (valid, computed over `B` with the app's shared secret), header `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker captures this request and resends it to the same webhook endpoint, keeping body `B` and header `X-Shopify-Hmac-Sha256: H` unchanged, but replacing `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com`.
3. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only (`to_signable_string` at lib/shopify_api/webhooks/request.rb:36-38) — validation succeeds because the body and secret are unchanged.
4. `Registry.process` invokes `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))` with `shop == "victim-shop.myshopify.com"` (lib/shopify_api/webhooks/registry.rb:198-199), even though the payload actually originated from and was signed for `attacker-shop`.
5. Any host application logic that uses `data.shop` to select the victim's session/tenant context will apply attacker-controlled data under the victim's identity.
