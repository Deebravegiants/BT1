### Title
Webhook `shop-domain` Header Not Covered by HMAC Signature Enables Cross-Tenant Webhook Forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes and validates the HMAC over the raw request body only, while the `shop-domain` header — the tenant identifier passed to the app's webhook handler — is never included in the signed payload. This breaks the binding `authenticated_bytes == bytes_acted_on`: the bytes cryptographically verified (`raw_body`) are not the bytes used to determine which shop/tenant the webhook data belongs to (`shop-domain` header).

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `Utils::HmacValidator.validate` computes/verifies the HMAC exclusively against that signable string [2](#0-1) . The `shop` accessor, however, is read directly from the unauthenticated `shop-domain` header, with no cryptographic linkage to the signed body [3](#0-2) .

`Registry.process` validates only `Utils::HmacValidator.validate(request)` and then forwards `request.shop` straight into `WebhookMetadata` for the handler, with no additional check tying the shop header to the body's origin [4](#0-3) .

Because the HMAC secret (`api_secret_key`) is a single shared secret for the app across every installed shop (not shop-specific), any unprivileged user who installs the target app on their own store legitimately receives real webhook deliveries with a valid `x-shopify-hmac-sha256` signature over a given `raw_body`. That attacker can then replay the exact same `raw_body`/`hmac` pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` will still pass — it only checks the body — yet `Registry.process` will hand the handler `shop: <victim-domain>` together with the attacker-controlled body content, producing a cross-tenant identity confusion in the app's data layer.

This mirrors the report's Root Cause B pattern: the check that is supposed to bind the acted-upon field (shop identity) to a verified quantity actually verifies a different, decoupled quantity (only the body), leaving the tenant-binding path effectively unauthenticated.

### Impact Explanation
This qualifies as Critical under "cross-tenant access": an attacker with no privileges beyond installing the app on any store (an action Shopify allows for any developer/merchant) can forge webhook payloads attributed to any victim shop domain, causing the host application to process attacker-chosen event data (e.g., fake `orders/create`, `app/uninstalled`, `customers/data_request`, GDPR topics, or any registered topic) as though it originated from a shop the attacker does not control. Depending on how the host app consumes `data.shop`/`data.body`, this can lead to data corruption, incorrect tenant records, spoofed uninstall/GDPR events, or triggering of privileged per-shop workflows for a victim's store — all without ever possessing the victim's access token or the app's `client_secret`.

### Likelihood Explanation
Likelihood is high for any app that relies on this gem's documented webhook flow as-is. The only prerequisite is that the attacker can install the target app on a store they control (ordinary, unprivileged action) to obtain one validly-signed `raw_body`/`hmac` pair, and can send an HTTP request to the app's public webhook endpoint with a modified `shop-domain` header — no secret material, TLS interception, or elevated access required. The gem's own documented usage pattern (`docs/usage/webhooks.md`) instructs developers to trust `data.shop` from `Registry.process` output directly [5](#0-4) , so a normal integration built per the documented interface is exposed.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) as part of the signed material verified against the HMAC, or independently re-derive/validate the shop identity from a source cryptographically tied to the payload (e.g., cross-check against the shop that registered the specific `webhook_id`/subscription, rather than trusting the header verbatim). At minimum, `to_signable_string` should not treat `shop-domain` as out-of-band from what `HmacValidator` protects when that field is subsequently used as a tenant key.

### Proof of Concept
1. Install the target app on attacker-controlled store `attacker.myshopify.com`; trigger any webhook topic the app subscribes to (e.g., `orders/create`) to capture a real HTTP POST with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
2. Replay this request to the app's webhook endpoint, keeping body `B` and header `x-shopify-hmac-sha256: H` unchanged, but set `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` builds a request whose `hmac` matches `H`; `Utils::HmacValidator.validate` succeeds because it only checks `B` against `H` [6](#0-5) .
4. `Registry.process` calls the registered handler with `shop: "victim.myshopify.com"` and the attacker's chosen body content [4](#0-3) , causing the host app to process forged data as belonging to the victim tenant.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
