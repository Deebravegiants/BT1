### Title
Webhook `shop`, `topic`, and `webhook_id` fields are trusted by handlers without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw body only, while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from HTTP headers and passed unauthenticated into the handler via `WebhookMetadata`. This breaks the intended identity binding of `HMAC-validated bytes == bytes acted upon by the handler`.

### Finding Description
`Registry.process` validates only that the raw request body is properly signed: [1](#0-0) 

The HMAC check calls `Utils::HmacValidator.validate(request)`, which in turn signs `request.to_signable_string`, defined as just `@raw_body`: [2](#0-1) 

Meanwhile `topic`, `shop`, `api_version`, and `webhook_id` are pulled straight from attacker-controllable HTTP headers with no cryptographic binding to the signed body: [3](#0-2) 

These unauthenticated values are then handed directly to the application's webhook handler as trusted metadata: [1](#0-0) 

The documented handler contract explicitly tells integrators to trust `data.shop` and `data.topic` for tenant/topic routing (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), with no guidance to independently re-verify shop or topic against the signed payload.

Equality that should hold but doesn't: `bytes verified by HMAC == bytes acted upon by handler`. In reality: `bytes verified by HMAC (raw_body) != bytes acted upon (raw_body + shop-domain header + topic header + webhook-id header)`.

### Impact Explanation
If an application relies on the gem's `WebhookMetadata#shop` (as documented) to determine which tenant's data a webhook body applies to, an attacker who can produce or capture one validly-HMAC-signed webhook body (e.g., by installing the app on their own store and receiving a real webhook with a guessable/replayable body, such as an empty-JSON-body event) can resubmit that exact raw body with the same valid HMAC while substituting the `shop-domain` and/or `topic` headers. Because these headers are never covered by the signature, `Registry.process` will still validate successfully and dispatch the forged `shop`/`topic` into the handler, potentially causing cross-tenant data application (Critical impact category: cross-tenant access) if the host application does not perform its own additional shop verification.

### Likelihood Explanation
Exploitation requires the attacker to obtain at least one legitimately HMAC-signed raw body from Shopify (achievable by installing the target app on an attacker-controlled shop, a normal unprivileged action for any third-party/public app), and requires the victim application to trust `data.shop`/`data.topic` from `WebhookMetadata` without independent verification — which is exactly what the gem's own documentation instructs consumers to do. Likelihood is dependent on the host app's handler logic, but the gem provides no protection or warning against this header/body mismatch, and its own webhook docs encourage the vulnerable pattern.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the HMAC-signable string (or otherwise cryptographically bind them to the verified payload), or explicitly document that the host application must independently validate that `data.shop` matches an install the app expects before trusting webhook headers. At minimum, warn in `docs/usage/webhooks.md` that `shop`/`topic` headers are unauthenticated and must not be used for tenant-authorization decisions without additional checks.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and registers a webhook whose payload body is predictable/empty (e.g., `app/uninstalled` often has body `{}`).
2. Shopify sends a legitimate webhook POST with header `X-Shopify-Hmac-Sha256` computed over body `{}` using the app's real `api_secret_key`.
3. Attacker captures this raw body + valid HMAC header.
4. Attacker crafts and sends their own POST request to the app's webhook endpoint, reusing the exact same raw body `{}` and valid `X-Shopify-Hmac-Sha256`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` and `X-Shopify-Topic: orders/create`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks the raw body against the HMAC — validation succeeds.
6. The handler configured for `orders/create` is invoked with `WebhookMetadata(topic: "orders/create", shop: "victim-shop.myshopify.com", body: {})`, as shown in [1](#0-0)  — a forged shop/topic combination accepted as authentic by the gem.
