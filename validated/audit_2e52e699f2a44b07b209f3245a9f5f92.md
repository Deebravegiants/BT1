### Title
Webhook shop-domain identity spoofing via HMAC scope gap enables cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/utils/hmac_validator.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, then hands the caller-supplied `shop-domain` header straight to the app's webhook handler as the authenticated tenant identity. Because the HMAC signature only covers `@raw_body` and never the `shop-domain`, `topic`, `api-version`, or `webhook-id` headers, the tenant-identity field consumed by the handler is not the field verified by the cryptographic check. This breaks the intended binding: `hmac_verified_bytes == identity_bytes_trusted_by_handler`.

### Finding Description
`ShopifyAPI::Webhooks::Request#hmac` reads the `hmac-sha256` header and `#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string` (i.e., the raw body) and compares it to the `hmac` header: [2](#0-1) 

`Registry.process` validates the HMAC and then passes `request.shop` (sourced purely from the unauthenticated `shop-domain`/`x-shopify-shop-domain` header) into `WebhookMetadata`, which is what the app-provided handler uses to determine which tenant the event belongs to: [3](#0-2) [4](#0-3) 

The equality the library is supposed to guarantee is: *the shop identity delivered to the handler == the shop identity that was cryptographically bound by Shopify at signing time*. In reality the guarantee only covers: *raw body bytes delivered == raw body bytes signed*. The `shop-domain` header sits entirely outside that guarantee, so any two values are decoupled — an attacker who possesses one valid `(raw_body, hmac)` pair (e.g. captured from a webhook Shopify legitimately sent for a shop the attacker controls/owns, since app developers routinely have a dev/test store) can replay that exact body+hmac to the app's public webhook endpoint while substituting the `shop-domain` header for any victim shop domain. `HmacValidator.validate` still returns `true` (the body is unchanged and correctly signed), and `Registry.process` will invoke the app's handler with `shop: <victim-shop>` and attacker-chosen `body` content that was never actually generated for, or authorized by, the victim shop.

### Impact Explanation
Applications built on this gem are expected to trust `WebhookMetadata#shop` (equivalently `Request#shop`) as the authenticated tenant identifier once `Registry.process` succeeds — that is the entire purpose of running HMAC validation before dispatch. Because the header is unauthenticated, an attacker can make the app believe a webhook event (with attacker-chosen JSON body, since the attacker fully controls the body of webhooks fired for their own store) originated from an arbitrary victim shop. Typical downstream effects in real integrations include: triggering `app/uninstalled` cleanup logic against a victim's stored session/tokens, spoofing GDPR compliance webhooks (`shop/redact`, `customers/redact`, `customers/data_request`) causing unauthorized data deletion for a victim tenant, or corrupting per-tenant business state keyed by the trusted `shop` value (e.g., fulfillment/order-processing webhooks). This is a cross-tenant identity-binding break reachable by any unprivileged internet user who can (a) register/own a Shopify store to legitimately receive one signed webhook and (b) send an HTTP request directly to the app's public webhook endpoint — no `api_secret_key`, access token, or privileged account of the *victim* is required.

### Likelihood Explanation
Likelihood is high for any app that exposes its webhook endpoint on the public internet (a documented requirement for Shopify webhooks) and uses `Registry.process`/`WebhookMetadata#shop` as the tenant key, which is the intended and only supported usage pattern of this API. The attacker only needs an account with Shopify (to receive one legitimately-signed webhook for their own store) and the ability to send an arbitrary HTTP POST with custom headers to the target app's known callback URL — both trivially available to an unprivileged internet user.

### Recommendation
Bind the tenant identity into the HMAC-covered material, or independently verify the `shop-domain` header against a value already associated (server-side, via prior OAuth) with the *specific* webhook subscription/HMAC secret used, rather than trusting an unauthenticated header. Concretely:
- Modify `VerifiableQuery`/`Request#to_signable_string` so the signable string includes the `shop`, `topic`, and other headers used downstream, matching them against Shopify's actual signing behavior if headers are in fact reproducible from data Shopify signs (if Shopify's HMAC truly signs only the body, the library must not expose `request.shop` as a "verified" identity without an explicit warning/opt-in re-verification step).
- At minimum, update documentation/`WebhookMetadata` to make clear that `shop` is unauthenticated and must be cross-checked by the app (e.g., against the shop stored for the corresponding `webhook_id` from a prior `GET /admin/webhooks/{id}.json` lookup) before being used for tenant-scoped actions.
- Consider requiring HTTPS-pinned, per-shop webhook secrets or shop allow-listing at the transport layer as a defense-in-depth measure.

### Proof of Concept
1. Attacker creates their own Shopify development store, `attacker-shop.myshopify.com`, and installs the target app so a legitimate webhook (e.g. `app/uninstalled`) is delivered to the app's public webhook endpoint. Attacker captures the full raw HTTP request, including `raw_body` and the `X-Shopify-Hmac-Sha256` header — this `(raw_body, hmac)` pair is valid because it was genuinely computed by Shopify using the app's `api_secret_key`.
2. Attacker replays this exact request to the same endpoint, keeping `raw_body` and `X-Shopify-Hmac-Sha256` identical, but changes `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com`.
3. Server-side, `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` is constructed, and `Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which validates successfully because it only recomputes the HMAC over `raw_body` — unchanged from step 1: [5](#0-4)  and [6](#0-5) .
4. `Registry.process` then dispatches to the app's registered handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: <attacker-controlled JSON originally generated for attacker's own shop>, ...)`: [3](#0-2) .
5. The app's handler executes tenant-scoped logic (e.g., uninstall cleanup, GDPR data deletion, order/fulfillment updates) believing the event is authentically about `victim-shop.myshopify.com`, even though nothing about that shop identity was ever cryptographically verified.

          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
