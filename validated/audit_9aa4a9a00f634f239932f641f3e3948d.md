### Title
Unbounded scrypt `n`/`r`/`p` parameters from untrusted metadata enable DoS via CPU/memory exhaustion - (File: libraries/secure-container/src/metadata.js)

### Summary
`metadata.decode()` only logs a `console.warn` when the input blob exceeds `METADATA_LEN_BYTES` and unconditionally proceeds to `struct.decode()`, and neither `metadata.js` nor `crypto.js` validates the decoded scrypt cost parameters (`n`, `r`, `p`) before they are used. An attacker who supplies a crafted `.seco` file can set extreme values for these fields, which are passed straight into `scrypt()` during `decryptBlobKey`/`boxDecrypt`, causing multi-hour computation or excessive memory allocation on the victim's device.

### Finding Description
`metadata.decode()` decodes the `scrypt.n`, `scrypt.r`, `scrypt.p` fields as raw `UInt32BE` values with no range checking: [1](#0-0) 

These attacker-controlled values flow unmodified into `decryptBlobKey`, which calls `boxDecrypt`: [2](#0-1) 

`boxDecrypt` merges the attacker-provided `scryptParams` object *over* the defaults (`{ ...createScryptParams(), ...scryptParams }`), so any attacker-supplied `n`/`r`/`p` fully override the safe defaults, and these are passed directly to the `scrypt()` primitive without any upper-bound or memory-cost check: [3](#0-2) [4](#0-3) 

The reachable call path is `secoFile.read`/`seco-rw` `read()` → `secure-container.decrypt` → `metadata.decode(oversizedBlob)` → `decryptBlobKey` → `boxDecrypt` → `scrypt(passphrase, salt, { N: n, r, p })`: [5](#0-4) [6](#0-5) 

The checksum check performed in `decrypt()` before metadata decode does not prevent this attack: it merely confirms that the metadata bytes match what the attacker wrote into the file, since the attacker fully controls both the metadata content and the accompanying checksum in a self-crafted `.seco` file: [7](#0-6) 

No code path in `metadata.js` or `crypto.js` enforces bounds on `n`, `r`, or `p`, or checks the total scrypt memory cost (`N * r * 128` bytes) before invoking `scrypt`.

### Impact Explanation
An attacker who can get a victim to import/read a crafted `.seco` container (e.g., via `seco-rw`/`seco-keyval`/`seco-file` import flows) can force the victim's device to perform scrypt key-stretching with attacker-chosen `n`/`r`/`p`, causing severe CPU-bound and/or memory-bound denial of service — potentially hanging the wallet-decryption operation for a very long time or exhausting device memory. This blocks legitimate decryption/use of the wallet data being imported, matching a resource-exhaustion / DoS impact class rather than key or fund compromise.

### Likelihood Explanation
Exploitation only requires the attacker to produce a `.seco`-formatted file (which is a documented, simple binary format) and have it passed into `read()`/`decrypt()` — e.g., via an import feature that accepts an untrusted file. No privileged wallet state or secret material is needed; the attacker only needs to control the imported file's bytes, which is explicitly one of the intended entry points for this library (import/restore flows). This makes the issue readily and repeatably triggerable.

### Recommendation
In `metadata.js` `decode()`, reject (throw) rather than warn when `metadataBlob.byteLength !== METADATA_LEN_BYTES`. Additionally, add explicit validation of `scrypt.n`, `scrypt.r`, `scrypt.p` after decode (and in `boxDecrypt`/`stretchPassphrase`) enforcing sane upper bounds (e.g., `n <= 2**20`, `r <= 16`, `p <= 4`, and total derived memory cost `128 * n * r` under a fixed ceiling such as a few hundred MB), failing closed with a thrown error before any call to `scrypt()`.

### Proof of Concept
Unit test to add to `libraries/secure-container/src/__tests__/metadata.test.js`:
```js
test('decryptBlobKey should reject oversized scrypt params', async (t) => {
  const md = metadata.create()
  await metadata.encryptBlobKey(md, 'pw', randomBytes(32))
  // attacker tampers with decoded metadata object before decrypt
  md.scrypt.n = 2 ** 30 // absurd N
  md.scrypt.r = 255
  md.scrypt.p = 255
  await t.rejects(
    () => metadata.decryptBlobKey(md, 'pw'),
    /scrypt parameters exceed allowed bounds/,
    'should fail closed instead of running scrypt with attacker-controlled params'
  )
})
```
Expected (currently failing) assertion: `decryptBlobKey`/`boxDecrypt` must throw before invoking the underlying `scrypt()` call when `n`, `r`, or `p` exceed defined safe bounds, instead of proceeding to run scrypt with attacker-supplied extreme cost parameters.

export async function decrypt(encryptedData, passphrase) {
  const fileObj = conFile.decode(encryptedData)

  const checksum = await conFile.computeChecksum(fileObj.metadata, fileObj.blob)
  if (!fileObj.checksum.equals(checksum))
    throw new Error('seco checksum does not match; data may be corrupted')

  const metadata = conMetadata.decode(fileObj.metadata)
  const blobKey = await conMetadata.decryptBlobKey(metadata, passphrase)
  const header = conHeader.decode(fileObj.header)
  const data = await conBlob.decrypt(fileObj.blob, metadata, blobKey)

  return { data, blobKey, metadata, header }
}
