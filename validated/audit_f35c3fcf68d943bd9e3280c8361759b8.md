## Finding: Hardware‑wallet `getAddress()` does not enforce the same passphrase-session ("hidden wallet") isolation that signing operations enforce

### Title
Trezor `getAddress()` returns an address from whichever passphrase session (standard/hidden wallet) happens to be active, bypassing the wallet-context check that `signTransaction`/`signMessage` perform - ([File: features/hardware-wallets/src/module/hardware-wallets.ts])

### Summary
Trezor devices in this codebase implement two isolated "sessions" per physical device: the **standard wallet** and a **passphrase-protected hidden wallet**, tracked by `walletId` [1](#0-0) . This is architecturally the same "no‑mix vs. mix" segregation pattern from the external report: two logically separate fund contexts on one shared transport/session that the software must select correctly before each sensitive operation.

### Finding Description
The signing path (`HardwareWallets#signTransaction` / `#signMessage`) routes through `#signGeneric`, which calls `device.ensureDeviceReady({ baseAssetName, walletAccount })` before invoking `sign()` [2](#0-1) . `ensureDeviceReady` in the Trezor device implementation actively probes and, if needed, switches the passphrase mode (standard vs. hidden) until the device's current `walletId` matches the `walletAccount.id` that the caller intends to operate on, throwing `WrongWalletSelectedError` if it never matches [3](#0-2) . This is the correct “select the right session” behavior — analogous to Lombard correctly picking `noMixClientSession` vs `clientSession`.

However, `HardwareWallets#getAddress()` does not go through this check at all. It calls `#getSelectedDevice()` (which only picks a manufacturer-matching *device*, not a *wallet context*) and then directly asks the device to derive/display an address for an `accountIndex`/`addressIndex`, with no `walletAccount` parameter and no call to `ensureDeviceReady` [4](#0-3) . The underlying `TrezorDevice#getAddress` simply asks the currently-initialized session for an address at the given derivation path, with no verification of which `walletId`/passphrase context is currently active [5](#0-4) .

The same gap exists in `scan`, `sync`, and `create`, which also call `#getSelectedDevice()` without any `ensureDeviceReady`/`walletId` check [6](#0-5) .

### Impact Explanation
If the physical Trezor is currently unlocked into one wallet context (e.g., the hidden/passphrase wallet from a previous operation) and the application subsequently calls `getAddress()` intending to display/verify an address belonging to the *other* context (the standard wallet, or a different hidden wallet), the function will silently return an address derived from the wrong session — there is no `walletAccount` input to cross-check against, unlike `signTransaction`/`signMessage`. This can cause the wallet to show or register an address that does not actually belong to the wallet account the user believes they are viewing/funding, which is the same class of impact as the original report: an isolation boundary meant to keep two fund contexts strictly separate is not enforced uniformly across all operations that touch that context, only across some of them (signing) and not others (address derivation/account discovery).

### Likelihood Explanation
This requires a user (or the app) to have previously switched the Trezor into a non-default passphrase context (e.g., during a prior signing operation, sync, or manual passphrase entry) and then invoke `getAddress`/`scan`/`sync` without the app explicitly resetting/validating the context first. Because `HardwareWallets` maintains a single active `#signingRequest` and device session across calls, and nothing resets the passphrase mode between unrelated calls, this is plausible in normal multi-account/hidden-wallet usage flows, not just a contrived edge case.

### Recommendation
Extend `getAddress`, `scan`, `sync`, and `create` to accept/verify the intended `walletAccount` (or its `walletId`) and call the same `ensureDeviceReady` check used by `signTransaction`/`signMessage` before deriving or displaying an address, so that every operation that reads or discloses key material from the device is bound to the correct passphrase/wallet session, consistent with how signing already enforces it.

### Proof of Concept
Conceptual sequence (cannot be dynamically executed via static code index, but demonstrated by code paths above):
1. App calls `signTransaction` for `walletAccount` "Hidden Wallet A" → `ensureDeviceReady` switches device into hidden-wallet session A [7](#0-6) .
2. App later calls `getAddress({ assetName, accountIndex, addressIndex })` intending to show an address for the *standard* wallet (or a different hidden wallet) — no `walletAccount`/`walletId` is passed and no session check occurs [4](#0-3) .
3. The device is still in hidden-wallet session A, so `TrezorDevice#getAddress` returns an address derived under session A's passphrase, not the standard/other-wallet context the caller expected [5](#0-4) .

Note: I could not find a UI-level caller in the indexed portion of the repo that reveals whether this address is ever used for fund-receiving confirmation without further checks; confirming full end-to-end exploitability (e.g., whether displayed addresses are cross-checked elsewhere) would require deeper review than the current index provides.

  ensureDeviceReady = async ({ walletAccount }: EnsureDeviceReadyParams): Promise<void> => {
    const walletId = String(walletAccount.id ?? '')

    // Legacy accounts may have id === <deviceId> (no walletId persisted).
    // In that case, treat as standard and avoid triggering a passphrase prompt.
    if (!/^[\da-f]{32}$/iu.test(walletId)) {
      if (this.#events.getPassphraseMode() !== 'standard') {
        await this.setPassphraseMode('standard')
      }

      return
    }

    // Attempt 1: check current session first (avoids resets/prompts when already correct).
    const walletIdCurrent = await this.getWalletId()
    if (walletIdCurrent === walletId) return

    // Attempt 2: reset to standard wallet context (no passphrase prompt) and re-check.
    await this.setPassphraseMode('standard')
    const walletIdStandard = await this.getWalletId()
    if (walletIdStandard === walletId) return

    // Attempt 3: reset to hidden wallet context and prompt for passphrase on-device, then re-check.
    await this.setPassphraseMode('hidden')
    const walletIdHidden = await this.getWalletId()
    if (walletIdHidden === walletId) return

    throw new WrongWalletSelectedError()
  }

  /**
   * Fetch the XPUBs and public keys from the hardware wallet device and return it as a result.
   * note: this will only sync the currently opened asset on Ledger.
   * @param {SyncParams} params
   * @param {number} params.accountIndex - the account index to sync
   * @returns {string} the unique identifier for the synchronized keys
   */
  sync = async ({ accountIndex: index, isMultisig }: SyncParams = {}): Promise<SyncedKeysId> => {
    const keysToSync: KeyToSyncData[] = []

    // Retrieve the public keys from the device to our wallet
    const { device } = await this.#getSelectedDevice()
    const source = device.descriptor.manufacturer
    const accountIndex = index ?? this.#walletAccounts.getNextIndex({ source })
    // Compute the walletId fingerprint in the currently selected session context.
    // The caller is responsible for putting the device in the desired context
    // (standard/hidden) prior to calling sync (e.g. via setPassphraseMode()).
    // Fallback to randomly generated id, since Ledger doesn't support this..
    const walletId = (await device.getWalletId?.()) ?? randomBytes(32).toString('hex')

    const useableAssetNames = new Set(await device.listUseableAssetNames())
    for (const assetName of useableAssetNames) {
      const asset = this.#assetsModule.getAsset(assetName)
      if (!asset) {
        this.#logger.warn(`asset with ${assetName} was not found`)
        continue
      }

      const baseAsset = asset.baseAsset
      const supportedPurposes = baseAsset.api.getSupportedPurposes?.({
        compatibilityMode: source,
        isMultisig,
      }) ?? [44]
      for (const purpose of supportedPurposes) {
        const {
          keyIdentifier,
          xpub,
          publicKey,
        }: Partial<GetXPUBResult> & Partial<GetPublicKeyResult> =
          (await this.#getXPUB({ device, baseAsset, purpose, accountIndex })) ||
          (await this.#getPublicKey({ device, baseAsset, purpose, accountIndex }))

        keysToSync.push([keyIdentifier, { xpub, publicKey }] as KeyToSyncData)
      }
    }

    // Generate a random id and map it to the public keys
    // this prevents a bunch of serialization issues.
    const id = randomBytes(16).toString('hex')
    this.#syncedKeysMap.set(id, {
      accountIndex,
      model: device.descriptor.model,
      assetNames: useableAssetNames,
      keysToSync,
      walletId,
    })

    return id
  }

  /**
   *
   * @param {CreateParams} params
   * @param {string} params.syncedKeysId - the unique id for synced keys

  create = async ({ syncedKeysId, isMultisig }: CreateParams): Promise<WalletAccount> => {
    assert(
      this.#syncedKeysMap.has(syncedKeysId),
      `no synchronized keys found for id ${syncedKeysId}`
    )

    const { device } = await this.#getSelectedDevice()
    const source = device.descriptor.manufacturer
    const label = source === WalletAccount.LEDGER_SRC ? 'Ledger' : 'Trezor'
    const { accountIndex, model, walletId } = this.#syncedKeysMap.get(syncedKeysId)!

    // Create a new wallet account
    const walletAccount = new WalletAccount({
      label: `${label}${accountIndex === 0 ? '' : '_' + accountIndex}`,
      icon: source,
      source,
      model,
      index: accountIndex,
      id: walletId,
      isMultisig: !!isMultisig,
    })
    const walletAccountName = walletAccount.toString()
    await this.#walletAccounts.create(walletAccount)
    await this.#walletAccounts.setActive(walletAccountName)

    await this.addPublicKeysToWalletAccount({ walletAccount, syncedKeysId })

    return walletAccount
  }
