## Analog Vulnerability Found

### Title
Any connected dApp can untrust, disconnect, or hijack another origin's wallet connection - ([File: features/connected-origins/module/connections.js])

### Summary
The `ConnectedOrigins` module exposes `untrust`, `disconnect`, and `connect` methods that take an arbitrary `origin` string as a caller-supplied parameter and mutate that origin's trust/connection state, with no verification that the caller (the RPC-connected dApp) actually *is* that origin. This mirrors the reported `Bet::cancel` bug class: an action meant to be restricted to the party that owns the state (there, the bet's maker/taker; here, the specific connected website) can instead be performed by any other unprivileged caller by simply naming a different target.

### Finding Description
`ConnectedOrigins.untrust`, `.disconnect`, and `.connect` operate purely on the `origin` value passed into the call, looking it up and mutating stored state without any binding to the actual sender identity of the RPC/API call: [1](#0-0) 

These methods are exposed directly on the public API surface used by consuming SDKs/dApp bridges: [2](#0-1) 

Unlike `getConnectedAccounts`, which at least gates the read path behind `isTrusted({origin})`, the mutating methods (`untrust`, `disconnect`, `connect`) perform no check that the `origin` argument matches the actual origin of the calling context. As in the `Bet::cancel` report — where the code only blocked the `maker` from cancelling an `ACTIVE` bet but let *any other* address cancel — here the code only checks whether the target `origin` *exists* in storage, not whether the caller *is* that origin. Any connected/embedded dApp that can reach this API (e.g., through the RPC bridge in `libraries/browser-extension-rpc` or `libraries/sdk-rpc`) can pass another site's origin string as the parameter and:
- Call `untrust({ origin: 'victim.com' })` to silently revoke another site's authorized connection.
- Call `disconnect({ id, origin: 'victim.com' })` to tear down another site's active session.
- Call `connect({ id, origin: 'victim.com' })` to inject a bogus "active connection" entry for another site.

### Impact Explanation
This breaks origin isolation for the connected-dApp trust model: a malicious/unprivileged website with any RPC access to the wallet's `connectedOrigins` API could grief or disrupt another legitimate dApp's session state without the user's consent — analogous to how the taker in the bet contract could unilaterally undo a state transition (`ACTIVE` → `CANCELLED`) that should have required the counterparty's or a privileged party's action. While this doesn't directly leak keys or funds, it undermines the integrity of the per-origin authorization/session boundary that the whole `connected-origins` feature is designed to enforce, enabling unauthorized revocation/disruption of other origins' wallet connections.

### Likelihood Explanation
Likelihood depends on whether the RPC/API layer that exposes `connectedOriginsApi` to external callers (dApps) enforces origin-binding *before* invoking these module methods, or passes through the caller-supplied `origin` untouched. Based on the reviewed code, the module itself (the security-relevant business logic) performs no such check, and the API definition passes the module methods through unmodified. If the outer RPC transport does not independently bind/validate the `origin` parameter against the sender's actual origin, this is directly reachable by any connected dApp.

### Recommendation
Bind the `origin` used by `untrust`, `disconnect`, and `connect` to the verified sender origin at the RPC/API boundary rather than trusting a caller-supplied parameter, or add an explicit check inside `ConnectedOrigins` that the acting origin matches the target origin before mutating trust/connection state.

### Proof of Concept
```js
// Malicious dApp connected as "attacker.com" calls the exposed connectedOrigins API
// with a different origin as the target, without any ownership check:
await exodus.connectedOrigins.untrust({ origin: 'victim-dapp.com' })
// victim-dapp.com's previously trusted connection is now revoked,
// even though the call originated from attacker.com.

await exodus.connectedOrigins.disconnect({ id: 'victims-connection-id', origin: 'victim-dapp.com' })
// victim-dapp.com's active connection session is torn down by an unrelated caller.
``` [1](#0-0) [2](#0-1)

  untrust = async ({ origin }) => {
    const isTrusted = await this.isTrusted({ origin })

    if (!isTrusted) return

    const data = await this.#getData()
    const newData = data.filter((connection) => connection.origin !== origin)

    await this.#setData(newData)
  }

  isTrusted = async ({ origin }) => {
    const value = await this.#getOrigin({ origin })

    if (!value) {
      return false
    }

    // backward compatibility
    return value.trusted === undefined || value.trusted
  }

  isAutoApprove = async ({ origin }) => {
    const value = await this.#getOrigin({ origin })
    return value?.autoApprove || false
  }

  setAutoApprove = async ({ origin, value }) => {
    return this.#setAttributes({ origin, attributes: { autoApprove: value } })
  }

  setFavorite = async ({ origin, value, assetNames = [] }) => {
    return this.#setAttributes({ origin, attributes: { favorite: value, assetNames } })
  }

  connect = async ({ id, origin }) => {
    const value = await this.#getOrigin({ origin })

    if (!value) return

    const activeConnections = value.activeConnections || []
    const newConnection = { id, createdAt: Date.now() }
    const newConnections = uniqBy([...activeConnections, newConnection], 'id')

    await this.#setAttributes({ origin, attributes: { activeConnections: newConnections } })
  }

  disconnect = async ({ id, origin }) => {
    const value = await this.#getOrigin({ origin })

    if (!value) return

    const activeConnections = value.activeConnections || []
    const newConnections = activeConnections.filter((connection) => connection.id !== id)

    await this.#setAttributes({ origin, attributes: { activeConnections: newConnections } })
  }
