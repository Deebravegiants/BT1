### Title
Auto-Lock `maxTtl` Bound Bypassed via Repeated Inactivity Resets in `PassphraseCache` - ([File: features/application/src/modules/passphrase-cache.ts])

### Summary
`PassphraseCache` caches the wallet decryption passphrase in storage so the wallet can auto-unlock, and is meant to be bounded by a hard `maxTtl` ceiling regardless of activity. However, once the cache transitions into the "inactive" state, the code stops enforcing `maxTtl` against the original `addedAt` timestamp and instead re-evaluates expiry purely from the most recently reset `inactiveAt` timestamp. Because `inactiveAt` (and the underlying clear-passphrase alarm) is refreshed every time `scheduleClear()`/`changeTtl()` run, a caller that keeps the app transitioning into/out of the background within the `ttl` window can keep pushing out the passphrase expiry indefinitely, defeating the `maxTtl` security bound. This is the direct analog of the reported bug class: a security-relevant accrual/expiry (interest accrual on pending debt / here, the mandatory countdown to invalidate cached secret) can be indefinitely deferred by structuring the timing of otherwise-normal interactions, instead of being an unconditional, monotonic bound from the original event.

### Finding Description
`PassphraseCache.get()` implements two different expiry checks: [1](#0-0) 

- If `inactiveAt` has never been set, the passphrase is valid only while `addedAt + this.#maxTtl > Date.now()` — i.e., bounded by the absolute maximum lifetime `maxTtl` computed from when the passphrase was first cached.
- Once `inactiveAt` is set (which happens any time `scheduleClear()` runs, e.g. when the app is backgrounded), the check switches entirely to `inactiveAt + ttl > Date.now()`. `addedAt`/`maxTtl` is never consulted again for this cached secret.

`scheduleClear()` and `changeTtl()` both reset `inactiveAt` to `Date.now()` and re-arm the OS-level `clear-passphrase` alarm from scratch every time they are invoked: [2](#0-1) 

Because the private `#scheduleClear` reschedules the alarm using `ttl` (the per-session inactivity TTL, not `maxTtl`), and because `scheduleClear()`/`changeTtl()` can be invoked repeatedly (e.g. every time the app backgrounds/foregrounds, or the user adjusts their auto-lock timer setting), the `inactiveAt` timestamp is continually pushed forward. From that point on, `get()` only checks `inactiveAt + ttl > Date.now()`, so as long as the interval between successive backgrounding events stays under `ttl`, the cached passphrase never expires — the intended hard ceiling `maxTtl` set in configuration (`(config.maxTtl || 60) * ms('1m')`) is silently bypassed for the remainder of the app's runtime. [3](#0-2) 

This mirrors the reported bug's root cause: a value that should accrue/expire against its original absolute basis (debt should accrue interest from origination even while "pending"; here, the passphrase should expire against `addedAt + maxTtl` regardless of activity) is instead reset each time an intermediate, gas/perf-motivated bookkeeping event occurs (moving debt into `DefaultPool` without accruing interest; resetting `inactiveAt` on every backgrounding event without re-checking `maxTtl`), letting the actor indefinitely defer the intended security consequence by controlling the timing/frequency of ordinary interactions.

### Impact Explanation
The wallet's decryption passphrase is one of the most sensitive secrets in the system — it is stored (even if in platform-provided secure storage) specifically to allow bounded-duration auto-unlock. The `maxTtl` configuration value exists precisely to guarantee that this cached secret cannot persist forever regardless of how often the user interacts with the device. This bypass allows the cached passphrase to remain valid far beyond the configured absolute maximum, directly weakening a control designed to limit the exposure window of the wallet's decryption secret (e.g., in a lost/stolen/compromised device scenario after the intended `maxTtl` should have forced re-authentication). This is a direct security-boundary violation touching an auth/secret-caching control rather than merely a cosmetic issue.

### Likelihood Explanation
Triggering this does not require any special privilege or attacker capability beyond normal usage patterns: any user (or any code path, such as app backgrounding/foregrounding cycles, that are part of routine mobile OS behavior) that causes `scheduleClear()` to fire more often than the `ttl` interval will continuously extend the cache well past `maxTtl`. This is highly likely to occur in ordinary use (e.g., users frequently switching apps on mobile), so the "wait long enough" precondition from the original report analog is trivially satisfiable without deliberate exploitation, though the security-relevant consequence (secret outliving its absolute security bound) still requires a scenario where the device/session is later accessed by someone other than the current authenticated user during the improperly-extended window.

### Recommendation
Enforce `maxTtl` as an absolute, monotonic ceiling independent of `inactiveAt` resets: retain and check `addedAt + maxTtl` on every `get()` call in addition to the inactivity-based `inactiveAt + ttl` check, and never allow `scheduleClear()`/`changeTtl()` to extend validity beyond `addedAt + maxTtl`. Concretely, `get()` should compute `Math.min(inactiveAt + ttl, addedAt + maxTtl)` as the effective expiry rather than switching exclusively to the inactivity-based check once `inactiveAt` exists.

### Proof of Concept
1. Cache a passphrase: `passphraseCache.set(passphrase)` → sets `addedAt = now`, `ttl = autoLockTimerAtom value`.
2. Immediately call `scheduleClear()` (simulating app backgrounding) → sets `inactiveAt = now`.
3. Repeat step 2 at an interval smaller than `ttl` (e.g., every `ttl - 1ms`) for a duration far exceeding `maxTtl` (e.g., loop for `10 * maxTtl`).
4. At any point, call `passphraseCache.get()`. Because `inactiveAt` was always refreshed within the last `ttl` window, `get()` returns the cached passphrase every time — `addedAt + maxTtl` is never re-checked once `inactiveAt` is set — demonstrating that the `maxTtl` absolute bound from [4](#0-3)  is bypassed indefinitely.

  async get() {
    const [passphrase, addedAt, inactiveAt, ttl] = (await this.#storage.batchGet([
      PASSPHRASE_KEY,
      ADDED_AT_KEY,
      INACTIVE_AT_KEY,
      TTL_KEY,
    ])) as [string, number, number, number]

    if (passphrase) {
      if (inactiveAt) {
        if (inactiveAt + ttl > Date.now()) {
          this.#logger.log('fetched cached passphrase, in activity period')
          return passphrase
        }
      } else if (addedAt + this.#maxTtl > Date.now()) {
        this.#logger.log('fetched cached passphrase')
        return passphrase
      }

      this.#logger.log('fetched expired passphrase, clearing and preventing unlock')
      void this.clear()
    }

    this.#logger.log('passphrase not in cache')
  }

  async changeTtl(ttl: number) {
    const newTtl = Math.min(this.#maxTtl, ttl)

    await this.#autoLockTimerAtom.set(newTtl)

    const passphrase = await this.#storage.get(PASSPHRASE_KEY)

    if (passphrase) {
      await this.#storage.set(TTL_KEY, newTtl)

      void this.#scheduleClear()
    }
  }

  async scheduleClear() {
    const passphrase = await this.#storage.get(PASSPHRASE_KEY)

    if (passphrase) {
      await this.#storage.set(INACTIVE_AT_KEY, Date.now())

      void this.#scheduleClear()
    }
  }
