## Analysis

The Nebula Revelation incident is a reentrancy attack on a staking contract — an unrelated smart-contract bug class. Per the scoping rules, I looked for the closest unprivileged-actor analog in the gateway's authentication/authorization path (JWT-based external-request authentication), since reentrancy's essential characteristic is a **check-then-act race**: a security check is performed, an external/async operation proceeds, and only afterward is protective state updated — creating a window where the check can be bypassed by concurrent execution.

That exact pattern exists in the HTTP Trigger JWT replay-protection logic.

### Title
JWT replay-protection check-then-act race allows duplicate/unauthorized workflow trigger execution - ([File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go])

### Summary
`WorkflowMetadataHandler.Authorize` checks whether a JWT's `jti` has already been used via `isReplay`, and only records the `jti` as used via `recordUsage` *after* performing authorization/key lookups. These are two separate, non-atomic lock acquisitions on `jwtReplayCache`, so two concurrent requests carrying the identical signed JWT can both pass the `isReplay` check before either calls `recordUsage`, defeating the intended single-use guarantee.

### Finding Description
`Authorize` is the JWT-based authentication path for unprivileged clients invoking HTTP Trigger capability requests through the gateway: [1](#0-0) 

The flow is:
1. `h.jwtCache.isReplay(claims.ID)` — read the cache (`RLock`), return false if not present.
2. Signer/authorized-key checks proceed (no cache interaction).
3. `h.jwtCache.recordUsage(claims.ID)` — write the cache (`Lock`), marking the `jti` used.

`jwtReplayCache` uses a `sync.RWMutex` but the check (`isReplay`) and the write (`recordUsage`) are two independent critical sections, not a single atomic "check-and-set" operation: [2](#0-1) 

If a client (or an attacker who has captured a valid signed JWT header once) sends the same JWT-signed trigger request twice concurrently, both goroutines can execute `isReplay` before either executes `recordUsage`, since nothing serializes the two operations against the same `jti`. Both requests will then pass authorization and proceed to `checkRateLimit` and workflow dispatch in `HandleUserTriggerRequest`: [3](#0-2) 

This is structurally the same class of bug as the reported reentrancy: a state-changing guard (`recordUsage`) is deferred until after externally-observable/async work (signer verification, key lookup) has completed, leaving a window in which the same credential can be "reused" before the protective state update lands — precisely how reentrancy exploits allow a second call to execute before balance/state is finalized.

### Impact Explanation
A single valid signed JWT (one `jti`), which is meant to be single-use per the code's own comment ("Please generate a new one with new id (jti)"), can be replayed to trigger the same workflow execution multiple times within the race window. Since HTTP Trigger requests initiate workflow executions (and workflows may move funds, invoke external actions, etc., depending on the capability), this is a duplicate/unauthorized job-run vector reachable by any unprivileged external caller who can send two near-simultaneous copies of a captured request (e.g., via network retry, proxy duplication, or intentional replay). Severity is bounded by the fact that the attacker still needs a validly signed JWT for the target workflow — this is not a full authentication bypass — but it does defeat the intended anti-replay/anti-duplicate-execution guarantee.

### Likelihood Explanation
Likelihood is **moderate**: exploitation requires winning a narrow race window (two requests processed on different goroutines before the mutex-protected write occurs), which is plausible under real network conditions (retries, deliberate duplicate submission, or an attacker capturing and replaying a request within milliseconds). It does not require any elevated privilege — only capture/possession of one valid signed request.

### Recommendation
Make the replay check-and-mark atomic: acquire a single write lock and perform the "already used?" check and "mark used" write under the same critical section (i.e., a true CAS/check-and-set on the `jti` key), before proceeding with any further authorization logic, e.g.:
```go
if !h.jwtCache.checkAndRecord(claims.ID) {
    return nil, errors.New("JWT token has already been used...")
}
```
where `checkAndRecord` performs the read+write under one `mu.Lock()`.

### Proof of Concept
1. Obtain (or have) a validly signed JWT-authenticated HTTP Trigger request destined for a registered workflow, with `jti = X`.
2. Send the identical request twice concurrently (e.g., two goroutines/sockets hitting the gateway near-simultaneously).
3. Both requests may call `isReplay(X)` (both see "not replayed") before either calls `recordUsage(X)`, because these are independent lock acquisitions rather than one atomic operation, per `Authorize` at core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go:80-108.
4. Both requests pass authorization and are forwarded via `HandleUserTriggerRequest` (core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go:95-120), resulting in duplicate workflow execution from a single supposedly single-use signed request.

**Note on confidence:** I was unable to fully trace the downstream effects of a duplicate `HandleUserTriggerRequest` call (e.g., whether idempotency elsewhere in the DON/workflow execution layer would additionally block a duplicate execution) due to the limited number of remaining tool iterations. The race in `Authorize`/`jwtReplayCache` itself is confirmed by direct code reading, but whether it is fully exploitable end-to-end (versus mitigated by request-ID or workflow-execution-ID idempotency elsewhere) is not verified.

```go
func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
}
```
