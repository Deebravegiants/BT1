## Title
Unhandled revert in `IBounceLeveragedToken.exchangeRate()` permanently freezes both buy and sell on a curve token — ([File: packages/contracts/src/Bonding.sol])

### Summary
The original finding concerns an unguarded call to `latestRoundData()` that can revert and permanently DoS all price reads because the price feed address is fixed at configuration time with no setter. Alt.fun has a directly analogous pattern: each launched token is bound at `Bonding.launch()` to a single, immutable `TokenInfo.ltAddress` (a third-party BounceTech LT), and every buy and sell path makes an unguarded external call to that LT's `exchangeRate()` — with no `try/catch`, no fallback, and no per-token way to repoint the LT.

### Finding Description
`Bonding.canGraduate` reads `IBounceLeveragedToken(info.ltAddress).exchangeRate()` directly whenever the supply leg hasn't fired yet: [1](#0-0) 

`Bonding.previewLtUntilGraduation`, used by every curve buy in `Zap._executeBuy` to pre-size the mint, makes the same unguarded call: [2](#0-1) 

Critically, `Zap._sellInternal` calls `bonding_.canGraduate(tokenAddress)` unconditionally as the very first side-effecting step of every sell, before the tokens are even pulled or `redeem()` is reached: [3](#0-2) 

And `Zap._executeBuy` calls `Bonding.previewLtUntilGraduation` on every non-graduated buy: [4](#0-3) 

The LT bound to a token is set once at `launch()` and stored in `TokenInfo.ltAddress`; there is no admin or permissionless function anywhere in `Bonding.sol` to change it for an already-launched token — the docs explicitly confirm this is a one-time binding (`Bonding.launch` only *gates* which LT can be used for *new* launches; already-launched tokens are permanently wired to their original LT): [5](#0-4) 

If the bound LT's `exchangeRate()` reverts for any reason (BounceTech emergency pause, an internal invariant break, a compromised/malfunctioning oracle feed inside the LT, or any other operational fault on the BounceTech side), both `canGraduate` and `previewLtUntilGraduation` revert, which cascades into:
- Every `Zap.buy` on that curve token reverting (via `previewLtUntilGraduation`).
- Every `Zap.sell` on that curve token reverting (via the unconditional `canGraduate` check at the top of `_sellInternal`, which runs *before* `redeem()` is ever reached).

This differs from — and is strictly worse than — the protocol's own documented and accepted tradeoff that "BounceTech LTs are mint-pausable... every buy through Zap... DoSes for that token while sells keep working (sells go through redeem, not mint)": [6](#0-5) 

That accepted tradeoff assumes sells always remain available as an exit path. An `exchangeRate()` revert breaks that assumption because it is read unconditionally on the sell path too, before `redeem()` — so both sides of the market freeze simultaneously with no accepted fallback.

### Impact Explanation
Trading tokens/LT already raised on the curve become permanently locked with no way to buy or sell, and — because the LT binding is immutable per token — no admin remedy exists short of a full `Bonding` UUPS upgrade to special-case the affected token. This matches the "permanent freezing of trader/creator funds" bar: curve-holders cannot exit, LT already raised in the pair cannot be redeemed via `Zap`, and the token can never reach the graduation checks that gate `finalizeGraduation` either (since `canGraduate` itself reverts instead of returning `false`).

### Likelihood Explanation
`exchangeRate()` is a call into an external, upgradeable/administered third-party contract (BounceTech LT) outside alt.fun's control. The protocol's own comments already acknowledge that BounceTech can pause `mint` and can de-register/retire LTs, demonstrating that adverse third-party states are a recognized and realistic operational risk for this dependency. A revert-capable failure mode of `exchangeRate()` (pause, migration, internal bug, or admin action) is a plausible extension of the same trust class already called out in the codebase, and it is triggered purely by ordinary trader transactions (`Zap.buy`/`Zap.sell`) with no privileged action required to reach the vulnerable code path.

### Recommendation
Wrap the `exchangeRate()` (and other LT view) calls in `Bonding.canGraduate` and `Bonding.previewLtUntilGraduation` in `try/catch`, treating a revert as "not graduatable right now" rather than propagating the revert into the caller. At minimum, decouple the sell path so `_sellInternal`'s graduation check failing does not block the underlying `redeem()`-based exit — e.g., fall back to a normal sell if `canGraduate` reverts, rather than letting the revert kill the entire sell transaction.

### Proof of Concept
1. Token `T` is launched against LT `L` via `Bonding.launch`, becoming permanently bound (`TokenInfo.ltAddress = L`), with no setter available afterward.
2. `L.exchangeRate()` starts reverting (e.g., BounceTech pauses/faults the contract, or any bug in `L` causes the view to revert).
3. Any trader calls `Zap.buy(T, ...)` → `_executeBuy` → `Bonding.previewLtUntilGraduation(T)` → `IBounceLeveragedToken(L).exchangeRate()` reverts → the whole buy reverts.
4. Any trader calls `Zap.sell(T, ...)` → `_sellInternal` → `Bonding.canGraduate(T)` → `IBounceLeveragedToken(L).exchangeRate()` reverts → the whole sell reverts, even though `redeem()` on `L` is never reached and might otherwise still work.
5. Token `T` is now permanently untradeable in both directions; its curve funds and LT reserve are stuck with no remediation path since the LT binding cannot be changed for an already-launched token.
