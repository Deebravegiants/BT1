## Finding

### Title
Unchecked ERC20 return value in `withdraw()` allows permanent loss of escrowed intent funds - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron deployment of `IntentGatewayV2` releases escrowed intent tokens using a raw low-level `.call()` to the ERC20 `transfer` function and only checks that the call did not revert (`success`), never decoding/validating the returned boolean. Any ERC20 that returns `false` instead of reverting on a failed transfer will be silently treated as a successful payout, while the contract's internal accounting is unconditionally decremented and the order is marked filled — permanently trapping the escrowed tokens with no remaining path to recovery.

### Finding Description
`withdraw()` is invoked from `onAccept()` when a `RedeemEscrow`/`RefundEscrow` message is relayed cross-chain (an unprivileged, relayer-reachable path proving order fill/timeout): [1](#0-0) 

Inside `withdraw()`, escrowed ERC20 tokens are paid out via a raw call, checking only `success` and never inspecting/decoding the ABI-encoded boolean return value that ERC20 `transfer()` is expected to return: [2](#0-1) 

`_filled[body.commitment]` is set unconditionally at the top of the function, and `_orders[body.commitment][token] -= amount;` is executed immediately after the `success`-only check, regardless of whether the token actually moved value to `beneficiary`. The same unchecked pattern is repeated for protocol/tx fee payout, and again in the `SweepDust` handler in `onAccept()`: [3](#0-2) [4](#0-3) 

This is precisely the bug class from the external report: an ERC20 implementation that signals failure by returning `false` (rather than reverting) — a documented, real-world ERC20 behavior — passes the `success` check because the low-level call itself does not revert; only the ABI-encoded return data (which is never decoded here) communicates the failure. By contrast, the main EVM `IntentGatewayV2.sol` and `IntentsBase.sol` correctly use OpenZeppelin's `SafeERC20.safeTransfer`/`safeTransferFrom`, which decode and enforce the boolean return value: [5](#0-4) 

The Tron variant diverges from this safe pattern and reintroduces the exact unchecked-return-value flaw.

### Impact Explanation
Once `withdraw()` runs against a token whose `transfer()` returns `false` on failure (insufficient balance in the gateway due to a prior accounting drift, a paused/blacklist-style token, or any conforming-but-non-reverting ERC20), the beneficiary receives nothing, yet:
- the escrow amount is decremented (`_orders[...] -= amount`), and
- the order is marked filled (`_filled[body.commitment] = beneficiary`),

permanently foreclosing any retry or refund path. The tokens remain locked in the `IntentGatewayV2` contract with no recoverable accounting trail pointing back to the rightful beneficiary — a direct instance of permanent freezing of user/solver funds reachable through the normal escrow redemption flow.

### Likelihood Explanation
Triggering this requires only that the escrowed input token be one of the many real-world ERC20 tokens that return `false` on failure instead of reverting (a widely known and still-used pattern), combined with a transfer that legitimately fails (e.g., transient insufficient balance from rounding/dust sweeps elsewhere in the same file, or a token that can be paused/blacklisted). No privileged role is needed — the withdrawal path is driven by ordinary relayed ISMP messages as part of standard intent settlement.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `withdraw()` and the `SweepDust` branch of `onAccept()` with OpenZeppelin's `SafeERC20.safeTransfer`, mirroring the pattern already used correctly in `evm/src/apps/intentsv2/IntentsBase.sol` and `evm/src/apps/IntentGatewayV2.sol`. This ensures both call-level success and the ERC20 boolean return value (when present) are validated before escrow accounting is mutated and the order is marked filled.

### Proof of Concept
1. An order escrows token `T` (an ERC20 that returns `false`, not revert, on failed `transfer`) via the standard intent flow.
2. A relayer submits a `RedeemEscrow` request; `onAccept()` calls `withdraw()`.
3. `T.transfer(beneficiary, amount)` returns `false` (e.g., due to the gateway's balance of `T` being insufficient at that moment because of concurrent dust-sweep accounting elsewhere in the contract, or `T` being paused for `beneficiary`).
4. The low-level `.call()` does not revert (`success == true`), so the `if (!success) revert TransferFailed();` guard is bypassed.
5. `_orders[body.commitment][token] -= amount;` executes and `_filled[body.commitment] = beneficiary;` is already set — the order is now considered settled, but `beneficiary` received zero tokens, which are now permanently stranded in the contract.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
