No validation anywhere blocks batches with duplicate `assetId` for the same PoA token — confirmed by the absence of any dedup/uniqueness check in `sdk.ts`, `withdrawal-watcher.ts`, or `poa-bridge.ts`. This confirms the vulnerability.

### Title
Two same-asset PoA withdrawals in one batch collapse to a single status/txHash via `findMatchingWithdrawal` - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal` matches a withdrawal in the POA bridge API response solely by `nep141:<near_token_id>` equality via `findMatchingWithdrawal`, using `Array.prototype.find`, which returns only the first matching entry. When a batch intent contains two (or more) withdrawals of the same PoA token (e.g. `nep141:tron-d28a265909efecdcee7c5028585214ea0b96f015.omft.near`) to different destinations, both `WithdrawalIdentifier`s resolve to the identical first-matched API entry, so both `describeWithdrawal` calls report the same status/`txHash` regardless of which destination it actually belongs to.

### Finding Description
The broken equality: `WithdrawalIdentifier[i].status/txHash` should equal the API entry whose destination/amount corresponds to `withdrawalParams[i]`, but the code guarantees only `nep141:${w.data.near_token_id} === assetId` [1](#0-0) .

`describeWithdrawal` calls `getWithdrawalStatusWithRetry` (keyed only by `args.tx.hash`, the shared intent transaction hash — identical for every withdrawal in the batch), then calls `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)` [2](#0-1) . Since `withdrawal_status` is queried by `withdrawal_hash` (the shared NEAR intent tx hash) rather than per-withdrawal index, the response array contains all withdrawals from that intent tx. `findMatchingWithdrawal` uses `Array.find`, so when two withdrawals share the same `assetId`, both `WithdrawalIdentifier`s (index 0 and index 1) are matched to the *same* first array element — the code comment itself admits: "multiple withdrawals of the same token in a single transaction are not supported" [3](#0-2) .

Nothing upstream prevents this batch composition. `createWithdrawalIdentifiers` and `waitForWithdrawalCompletion`/`processWithdrawal` accept arbitrary arrays of `WithdrawalParams` without deduplication or same-token checks [4](#0-3) [5](#0-4) . `PoaBridge.supports` and `validateWithdrawal` validate each withdrawal independently and never reject a batch containing two entries with the same `assetId` [6](#0-5) .

Exploit flow: an integrator (or an attacker controlling batch composition, since they can freely choose `withdrawalParams`) submits a batch with two withdrawals of `nep141:tron-...omft.near` to two different TRON addresses (or same address, different amounts). Once the intent settles, `waitForWithdrawalCompletion` calls `describeWithdrawal` for each identifier. If the POA indexer processes them at different times (one COMPLETED with `transfer_tx_hash` A, one still PENDING), `findMatchingWithdrawal` returns the same COMPLETED entry (first found) for *both* identifiers, reporting `{status: "completed", txHash: A}` for the withdrawal that actually went to destination B (or hasn't happened yet). The integrator observing per-identifier completion incorrectly believes destination B's funds have arrived when they have not, based on destination A's txHash.

### Impact Explanation
This is a status/hash misreport: an integrator relying on `waitForWithdrawalCompletion`/`describeWithdrawal` per-`WithdrawalIdentifier` results to credit downstream ledgers or trigger customer notifications would attribute one destination's completion (and tx hash) to the other withdrawal. This matches the "High - a status or hash misreport making an integrator credit or refund twice" category, since an integrator could credit both legs of the batch based on a single actual completed transfer, or fail to notice a stuck withdrawal because it was reported as completed via the sibling's hash.

### Likelihood Explanation
Preconditions: batch withdrawal containing ≥2 entries with the identical `assetId` for a POA-bridged token (no SDK-side restriction prevents this — an ordinary user/integrator can trivially construct such a batch). Attacker cost is minimal (a normal withdrawal batch with a repeated token); it is fully repeatable for every batch with duplicate same-token withdrawals, and worsens whenever the two withdrawals settle out of order or have different completion times, which is common for two independent destination-chain transfers.

### Recommendation
Reject batches containing multiple withdrawals with the same `assetId` for the PoA bridge (fail fast in `supports`/`validateWithdrawal`/`createWithdrawalIdentifiers`) until the POA API and `findMatchingWithdrawal` support disambiguating by amount/destination/order as the existing code comment proposes (sorting both sides by amount), or extend `getWithdrawalStatus` matching to use destination address/amount/memo in addition to `assetId`.

### Proof of Concept
Vitest plan (mock only HTTP, i.e. `poaBridge.httpClient.getWithdrawalStatus`):
1. Construct two `WithdrawalParams` for `nep141:tron-d28a265909efecdcee7c5028585214ea0b96f015.omft.near` with different `destinationAddress` (`addrA`, `addrB`) and amounts.
2. Build two `WithdrawalIdentifier`s via `PoaBridge.createWithdrawalIdentifier` with `index: 0` and `index: 1`, sharing the same `tx.hash`.
3. Mock `poaBridge.httpClient.getWithdrawalStatus` to return `{ withdrawals: [ { status: "COMPLETED", data: { near_token_id: "tron-...omft.near", transfer_tx_hash: "0xhashA" } }, { status: "PENDING", data: { near_token_id: "tron-...omft.near" } } ] }`.
4. Call `describeWithdrawal` for both identifiers.
5. Assert equality break: both calls return `{ status: "completed", txHash: "0xhashA" }` even though identifier index 1 (destined for `addrB`) should report `pending` — i.e. `result[0] === result[1]` when they should differ, demonstrating the misattribution described in the code comment at [3](#0-2) .

				txHash: withdrawal.data.transfer_tx_hash,

function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}
