### Title
Stale delegate authorization is resurrected when position NFT returns to prior owner - ([File: contracts/controller/src/storage/account.rs](contracts/controller/src/storage/account.rs))

### Summary
Controller delegate grants are keyed only by `account_id` and stamped with the granting owner's address. Transferring the position NFT disables the old owner's grants, but does not delete them. If the NFT later returns to that owner, `get_delegates` treats the stale grant as valid again because `granted_by` once more equals the current owner. A formerly delegated position manager can then borrow or withdraw without the returning owner reauthorizing it. [1](#0-0) 

### Finding Description
`DelegateGrant` persists under `ControllerKey::Delegates(account_id)` independently of NFT ownership. `get_delegates` returns the stored list whenever its recorded `granted_by` equals the address currently returned by `owner_of`. [1](#0-0) 

NFT transfer itself does not delete this controller-side grant. During the interval in which another address owns the NFT, `granted_by != owner`, so the grant is inactive. When the NFT is transferred back, ownership equality is restored and every delegate in the stale list becomes authorized again. The authorization check accepts any stored delegate that is also an active position manager. [2](#0-1) 

The grant is only removed if a later owner explicitly calls `remove_delegate`; otherwise the stale entry remains in storage across the ownership round trip. [3](#0-2) 

### Impact Explanation
An active manager that was delegated by a former owner can regain full account-control capability after that former owner reacquires the position NFT. The revived manager can call owner/delegate entrypoints such as `withdraw` or `borrow`, specifying itself as recipient through the `to` argument. The account must remain solvent, but all withdrawable collateral and all newly available borrowing capacity can be extracted to the manager, leaving the returning owner with impaired collateral and debt. This is theft of user funds caused by stale lifetime-scoped authorization surviving the ownership transfer.

### Likelihood Explanation
The attacker must first receive a delegate grant from an owner while registered as an active position manager, the NFT must subsequently move to another owner, and it must later return to the original owner while the stale grant still exists. Position NFT transfers are ordinary unprivileged operations, and the grant survives them silently. No protocol administrator, oracle manipulation, leaked key, or contract upgrade is required. The attack depends on a plausible ownership round trip rather than a timing race.

### Recommendation
Invalidate all controller delegates atomically whenever a position NFT changes owner. Since the NFT contract is controller-aware only for mint/burn, a practical mitigation is to include an ownership generation or transfer nonce in `DelegateGrant`: store a monotonically increasing transfer count beside the grant, update it through a controller/NFT synchronization path, and require the grant's generation to match the account's current generation. Alternatively, replace `granted_by` equality with a grant record whose validity is explicitly cleared through a controller hook invoked on NFT transfer. At minimum, delete `Delegates(account_id)` during every successful transfer rather than relying on later owner cleanup.

### Proof of Concept
1. Alice owns `account_id = N` and calls `add_delegate(Alice, N, Manager)` while `Manager` is active. The stored grant is `{ granted_by: Alice, delegates: [Manager] }`.
2. Alice transfers NFT `N` to Bob. Controller ownership resolution now returns Bob, so `get_delegates(N, Bob)` filters out Alice's stale grant, but the grant remains stored.
3. Bob later transfers NFT `N` back to Alice without first calling `remove_delegate`.
4. Controller ownership resolution again returns Alice. `get_delegates(N, Alice)` now returns `[Manager]` because the stored `granted_by` equals Alice.
5. `Manager` calls `withdraw(Manager, N, withdrawals, Some(Manager))` or `borrow(Manager, N, borrows, Some(Manager))`. `require_owner_or_delegate` passes because the stale grant is treated as Alice's current grant, allowing Manager to receive the withdrawn collateral or borrowed assets.

```rust
/// Returns grants stamped by `owner`, or an empty list. Ownership changes
/// invalidate a previous owner's grants without deleting them.
pub(crate) fn get_delegates(env: &Env, account_id: u64, owner: &Address) -> Vec<Address> {
    get_user::<DelegateGrant>(env, &ControllerKey::Delegates(account_id))
        .filter(|grant| grant.granted_by == *owner)
        .map(|grant| grant.delegates)
        .unwrap_or_else(|| Vec::new(env))
}
```

```rust
/// Removes a live delegate and reports whether it changed the list.
/// Deletes stale grants but returns false, preventing those grants from
/// reactivating if the NFT returns to their original owner.
pub(crate) fn remove_delegate(
    env: &Env,
    account_id: u64,
    owner: &Address,
    delegate: &Address,
) -> bool {
    let key = ControllerKey::Delegates(account_id);
    let Some(grant) = get_user::<DelegateGrant>(env, &key) else {
        return false;
    };
    if grant.granted_by != *owner {
        env.storage().persistent().remove(&key);
        return false;
    }
    let mut delegates = grant.delegates;
    let Some(index) = delegates.first_index_of(delegate) else {
        return false;
    };
    delegates.remove(index);
    set_delegates(env, account_id, owner, &delegates);
```

```rust
pub(crate) fn is_owner_or_delegate(
    env: &Env,
    account_id: u64,
    caller: &Address,
    owner: &Address,
) -> bool {
    if caller == owner {
        return true;
    }
    let active_manager =
        storage::get_position_manager(env, caller).is_some_and(|config| config.is_active);
    active_manager && storage::get_delegates(env, account_id, owner).contains(caller)
}
```
