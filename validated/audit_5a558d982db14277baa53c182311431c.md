### Title
Webhook `shop` identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw request body, then dispatches the handler using a `shop` value read from an unauthenticated HTTP header. Because the header is not part of the signed material, any two values `(shop_header, body+hmac)` can be freely recombined as long as the body+hmac pair is valid for the shared app secret — allowing an attacker who can obtain one legitimate `(body, hmac)` pair to relabel it as belonging to a different, arbitrary tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and defines the material that is actually protected by the HMAC: [1](#0-0) 

`to_signable_string` returns only `@raw_body`. The `shop` accessor, in contrast, is read directly and unconditionally from the `x-shopify-shop-domain` (or `shopify-shop-domain`) header with no cryptographic tie to the signature: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC purely from `to_signable_string` (i.e., the body) and compares it against the received `hmac-sha256` header: [3](#0-2) 

`Registry.process` treats this body-only check as authenticating the whole request, then forwards the unauthenticated `shop` header straight to the application handler as the tenant identity: [4](#0-3) 

This breaks the identity binding: `shop authenticated (header, unverified)` ≠ `shop whose data is bound into the HMAC (none — only the body is signed)`. Since the `api_secret_key` is shared across all shops installed on the same app, any valid `(body, hmac)` pair obtained from any one tenant of the app remains a valid HMAC no matter which `shop-domain` header it is paired with. An attacker who can obtain (e.g. by installing the app on their own store, or observing/replaying a webhook delivered to their own store) one legitimate `(raw_body, hmac-sha256)` pair can resend it to the app's webhook endpoint with the `x-shopify-shop-domain` header changed to a victim shop. `Utils::HmacValidator.validate` still returns `true` because it only checks the body, and `Registry.process` will invoke `handler.handle` with `WebhookMetadata#shop` set to the attacker-chosen victim domain while `body` contains data belonging to the attacker's own shop.

### Impact Explanation
This is a cross-tenant identity confusion: application code that trusts `WebhookMetadata#shop` (as the library's own webhook API contract implies it should, since it is the field exposed for tenant attribution) will process data under the wrong merchant's identity. Depending on the handler's logic (e.g., writing order/customer/fulfillment data keyed by `shop`, or using `shop` to select which merchant record to update), this enables injection of attacker-controlled payloads into another tenant's data scope — a cross-tenant access impact.

### Likelihood Explanation
Any unprivileged internet user who is (or can become) a merchant/installer of the target app can capture a legitimate `(body, hmac)` pair from their own store's own webhook delivery (webhook payload and HMAC header are visible to the receiving endpoint owner in typical self-hosted app deployments, or can be captured by simply subscribing an attacker-controlled shop and observing the outbound HTTP call). No access to `api_secret_key`, access tokens, or leaked credentials is required — only the ability to receive one webhook and resend it with a modified header, which is directly reachable through this gem's public `Webhooks::Registry.process`/`Webhooks::Request` API.

### Recommendation
Bind the tenant/topic identity into the signed material, or otherwise cryptographically verify the `shop-domain` (and `topic`/`webhook-id`) headers rather than trusting them verbatim. At minimum, `Request#to_signable_string` should incorporate the `shop-domain` header (mirroring how `Auth::Oauth::AuthQuery#to_signable_string` includes `shop` in its signable string), or `Registry.process` should cross-check the header-derived shop against an independently trusted source (e.g., an installed-shop registry) before dispatching to the handler.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`. Trigger any webhook topic that the app subscribes to (e.g., `orders/create`), and capture the raw POST body and the `x-shopify-hmac-sha256` header sent by Shopify — this HMAC is valid because it is computed only over the body using the app's shared `api_secret_key`.
2. Replay this exact `(raw_body, hmac-sha256)` pair to the app's webhook endpoint, but replace the `x-shopify-shop-domain` header with `victim.myshopify.com`.
3. `Utils::HmacValidator.validate` (called from `Registry.process`) validates successfully because it only checks `raw_body` against the secret: [5](#0-4) 
4. `Registry.process` invokes the registered handler with `WebhookMetadata#shop == "victim.myshopify.com"` and `body` containing attacker-controlled data from step 1: [4](#0-3) 
5. Any application logic keyed on `data.shop` now processes attacker-supplied `body` content under the victim tenant's identity.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
