### Title
Unbounded `RuntimeCall::decode` in HFT `on_accept` allows stack-exhaustion DoS via untrusted cross-chain calldata - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
The `pallet-hyper-fungible-token` (HFT) `IsmpModule::on_accept` handler SCALE-decodes an attacker-supplied `RuntimeCall` from the untrusted cross-chain message body using a plain, depth-unbounded `Decode::decode`, rather than the depth-limited decoder (`decode_all_with_depth_limit`) that the codebase already uses elsewhere for exactly this reason (`pallet-call-decompressor`). A deeply nested call (e.g. thousands of nested `Sudo`/`Utility::batch`-style wrappers) recurses the native call stack during decode and crashes the executing node, which is deterministic across all validators processing the same relayed message/block.

### Finding Description
`on_accept` decodes optional calldata attached to a cross-chain token transfer: [1](#0-0) 

then decodes the embedded runtime call directly from that untrusted byte blob with no recursion bound: [2](#0-1) 

`substrate_data.runtime_call` originates from the ISMP `PostRequest` body (`message.data`), which is fully attacker-controlled: any unprivileged party can call/deploy the counterpart EVM/host contract to submit a cross-chain transfer whose `data` field carries an arbitrary byte sequence, which a relayer then delivers via ISMP dispatch, reaching this `on_accept` handler with no elevated privileges required.

The codebase already demonstrates this exact bug class and its exploitability in `pallet-call-decompressor`: a comment and dedicated test show that undepth-limited `T::RuntimeCall::decode` on an attacker-nested call causes stack exhaustion, which is why that pallet was hardened to use `decode_all_with_depth_limit(MAX_EXTRINSIC_DECODE_DEPTH_LIMIT, ...)`: [3](#0-2) [4](#0-3) [5](#0-4) 

The HFT `module.rs` decode at line 189 was never migrated to this depth-limited pattern, leaving the same unbounded-recursion deserialization hazard reachable through the token-bridge message path instead of the decompressor extrinsic path.

### Impact Explanation
A single crafted cross-chain transfer with a deeply nested SCALE-encoded `RuntimeCall` in its calldata, once relayed and dispatched through `on_accept`, triggers native stack exhaustion during decode. Because block execution is deterministic, every validating/collating node that processes the block containing this message hits the same crash, halting block production/finality for the chain — a "route unable to deliver messages" / chain-halt condition reachable by any unprivileged token bridger or relayer, with no signature or governance privilege required. This matches the severity class of the reference CVE (untrusted deserialization reachable without authentication, causing uncontrolled execution/crash).

### Likelihood Explanation
High. The only prerequisites are: (1) a destination-chain asset mapping already configured for some source contract (`ContractToAsset`), which is a normal, expected bridge configuration, and (2) the ability to submit a cross-chain transfer with non-empty `data` — something the protocol explicitly supports as a feature ("Execute optional calldata"). No signature bypass or privileged role is needed to reach the vulnerable decode call.

### Recommendation
Replace the plain `T::RuntimeCall::decode(&mut &*substrate_data.runtime_call)` at `modules/pallets/hyper-fungible-token/src/module.rs:189` with a depth-limited decode (e.g. `T::RuntimeCall::decode_all_with_depth_limit(MAX_DEPTH, &mut &*substrate_data.runtime_call)`), mirroring the pattern already established in `pallet-call-decompressor`, and reject calls whose encoding exceeds the configured depth/size bound before any recursive decode work begins.

### Proof of Concept
1. Construct a `RuntimeCall` value nested ~1000 levels deep (e.g. repeated `Sudo::sudo { call: Box::new(previous) }` or an equivalent always-available wrapper call), as already demonstrated by the repo's own `decompress_stack_exhaustion_poc` test pattern: [6](#0-5) 
2. SCALE-encode this nested call and place the bytes into `SubstrateCalldata.runtime_call` (with `signature: None` and a valid `from` field) as the `data` field of an HFT cross-chain `Message`.
3. Submit this message as a normal cross-chain token transfer to the HFT contract on any source chain mapped in `ContractToAsset`, and have it relayed through ISMP so it reaches `on_accept`.
4. `T::RuntimeCall::decode` at line 189 recurses once per nesting level with no bound, exhausting the native stack and aborting the node process during message execution — reproducing the same class of crash the `decompress_stack_exhaustion_poc` test guards against in the sibling pallet.
