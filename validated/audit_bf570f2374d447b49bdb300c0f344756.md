Audit Report

## Title
`ERC20Transactor` credits/debits the requested `amount` rather than the actual ERC20-transferred amount, creating a shared-checking-account shortfall/DoS risk for non-standard ERC20 tokens - (File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs)

## Summary
`withdraw_asset_with_surplus` and `deposit_asset_with_surplus` call `IERC20::transfer` and, upon a `true` boolean return, unconditionally treat the full requested `amount` as having moved, crediting/debiting that nominal amount into XCM holding (`Erc20Credit(amount)`) and out of a shared `TransfersCheckingAccount`, without checking the checking account's/beneficiary's actual balance delta. [1](#0-0) [2](#0-1)  If a contract's `transfer` moves less than `value` while still returning `true` (rebasing/fee-on-transfer/share-based tokens), the checking account's real balance can fall short of what holdings assume, and a later `deposit_asset_with_surplus` for a different user's transfer of the same token could revert with `XcmError::FailedToTransactAsset`.

## Finding Description
The root cause and mechanics as described are accurately reflected in the code: `Erc20Credit`'s own doc comment states that "the actual balance constraints are enforced by the ERC20 smart contract itself rather than the runtime," [3](#0-2)  and both `withdraw_asset_with_surplus` [4](#0-3)  and `deposit_asset_with_surplus` [5](#0-4)  trust the boolean return value and the nominal `amount` rather than observing actual balance changes.

However, this pattern is standard/accepted behavior for ERC20 integrations generally (relying on `transfer`'s return value per the ERC20 standard), and the actual severity hinges entirely on whether the deployed/whitelisted ERC20 contracts used in production asset-hub configurations can exhibit this non-compliant "returns true but transfers less" behavior. This depends on the `Matcher: MatchesFungibles<H160, u128>` type actually wired into the runtime's `xcm_config.rs`, which determines which contract addresses are recognized as valid XCM assets. I was unable to fully retrieve/verify the concrete `Matcher` and `TransfersCheckingAccount` wiring in `asset-hub-westend`'s `xcm_config.rs` in this session — my tool calls to inspect that file's relevant matcher/account definitions did not return the necessary source lines despite grep confirming their presence (5 matches for `TransfersCheckingAccount`/`ERC20Transactor`/`ERC20Matcher`). This is a genuine gap in verification: I cannot confirm from the available index whether the matcher is a permissionless "any H160 contract that implements the interface" matcher or a curated/permissioned allow-list of vetted tokens.

This uncertainty matters because:
- If any user can permissionlessly register an arbitrary `pallet-revive` contract as an XCM-routable ERC20 asset (as the report's cited test `smart_contract_does_not_return_bool_fails` suggests is at least testable), then the DoS path is plausible and reachable by an unprivileged attacker deploying a malicious contract.
- If asset registration/matching is restricted to a curated, reviewed set of tokens (which is the typical design intent for asset-hub — assets must generally be registered via governance or a permissioned process before being XCM-routable), then this finding reduces to "the transactor doesn't defensively re-verify balances for tokens it already trusts," which is a code-quality/defense-in-depth concern rather than an exploitable vulnerability by an unprivileged attacker.

## Impact Explanation
If reachable, the impact is a denial-of-service on XCM transfers of an affected ERC20 asset: a shortfall in the shared `TransfersCheckingAccount`'s real balance causes subsequent unrelated users' `deposit_asset_with_surplus` calls for the same asset to fail with `FailedToTransactAsset`, trapping their assets in that XCM leg. This is a real accounting-assumption bug in the transactor code as written, independent of whether it's currently reachable in the deployed asset-hub configuration.

## Likelihood Explanation
Likelihood is not fully verifiable from the index available to me. The report assumes the ERC20 asset matcher used with `ERC20Transactor` is permissionless (any deployed `pallet-revive` contract can be matched via its `Location`/H160 address), which would make this trivially triggerable by an unprivileged attacker deploying a custom rebasing contract. I could not confirm this assumption against the actual `Matcher` type used in `asset-hub-westend`'s `xcm_config.rs` due to tool limitations in this session. If asset registration for ERC20 tokens is gated (e.g., requires governance/root to register a token before it becomes matchable/spendable via XCM), the practical likelihood of an unprivileged attacker exploiting this drops significantly, since only already-vetted tokens would be reachable.

## Recommendation
Regardless of matcher permissioning, defensively verify the checking account's/beneficiary's actual `balanceOf` delta (or the pre/post balance of the checking account) rather than trusting the nominal `amount` and boolean return value, so that non-standard token behavior cannot desynchronize XCM holding accounting from the checking account's real balance. Consider per-asset escrow (or balance-difference-based crediting) instead of a single shared pooled account with trust-based accounting.

## Proof of Concept
The claim's PoC is only conceptual and was not executed; the report itself acknowledges it "cannot be executed in this ask-only environment, and no on-chain reproduction was run." A concrete test to prove this in a Devin session would need to: (1) confirm the actual `Matcher`/`TransfersCheckingAccount` configuration in `asset-hub-westend`'s `xcm_config.rs` to establish whether arbitrary contracts are matchable, (2) if so, deploy a `pallet-revive` contract whose `transfer` moves `value - 1` while returning `true`, and (3) drive two sequential XCM withdraw/deposit cycles through `ERC20Transactor` to demonstrate the checking account's real balance falls below what a subsequent unrelated deposit requires, causing `FailedToTransactAsset`.

	fn withdraw_asset_with_surplus(
		what: &Asset,
		who: &Location,
		_context: Option<&XcmContext>,
	) -> Result<(AssetsInHolding, Weight), XcmError> {
		tracing::trace!(
			target: "xcm::transactor::erc20::withdraw",
			?what, ?who,
		);
		let (asset_id, amount) = Matcher::matches_fungibles(what)?;
		let who = AccountIdConverter::convert_location(who)
			.ok_or(MatchError::AccountIdConversionFailed)?;
		// We need to map the 32 byte checking account to a 20 byte account.
		let checking_account_eth = T::AddressMapper::to_address(&TransfersCheckingAccount::get());
		let checking_address = Address::from(Into::<[u8; 20]>::into(checking_account_eth));
		let weight_limit = WeightLimit::get();
		// To withdraw, we actually transfer to the checking account.
		// We do this using the solidity ERC20 interface.
		let data =
			IERC20::transferCall { to: checking_address, value: EU256::from(amount) }.abi_encode();
		let ContractResult { result, weight_consumed, storage_deposit, .. } =
			pallet_revive::Pallet::<T>::bare_call(
				OriginFor::<T>::signed(who.clone()),
				asset_id,
				U256::zero(),
				TransactionLimits::WeightAndDeposit {
					weight_limit,
					deposit_limit: StorageDepositLimit::get(),
				},
				data,
				&ExecConfig::new_substrate_tx(),
			);
		// We need to return this surplus for the executor to allow refunding it.
		let surplus = weight_limit.saturating_sub(weight_consumed);
		tracing::trace!(target: "xcm::transactor::erc20::withdraw", ?weight_consumed, ?surplus, ?storage_deposit);
		if let Ok(return_value) = result {
			tracing::trace!(target: "xcm::transactor::erc20::withdraw", ?return_value, "Return value by withdraw_asset");
			if return_value.did_revert() {
				tracing::debug!(target: "xcm::transactor::erc20::withdraw", "ERC20 contract reverted");
				Err(XcmError::FailedToTransactAsset("ERC20 contract reverted"))
			} else {
				let is_success = IERC20::transferCall::abi_decode_returns_validate(&return_value.data).map_err(|error| {
					tracing::debug!(target: "xcm::transactor::erc20::withdraw", ?error, "ERC20 contract result couldn't decode");
					XcmError::FailedToTransactAsset("ERC20 contract result couldn't decode")
				})?;
				if is_success {
					tracing::trace!(target: "xcm::transactor::erc20::withdraw", "ERC20 contract was successful");
					Ok((
						AssetsInHolding::new_from_fungible_credit(
							what.id.clone(),
							Box::new(Erc20Credit(amount)),
						),
						surplus,
					))
				} else {
					tracing::debug!(target: "xcm::transactor::erc20::withdraw", "contract transfer failed");
					Err(XcmError::FailedToTransactAsset("ERC20 contract transfer failed"))
				}
			}
		} else {
			tracing::debug!(target: "xcm::transactor::erc20::withdraw", ?result, "Error");
			// This error could've been duplicate smart contract, out of gas, etc.
			// If the issue is gas, there's nothing the user can change in the XCM
			// that will make this work since there's a hardcoded gas limit.
			Err(XcmError::FailedToTransactAsset("ERC20 contract execution errored"))
		}
	}

	fn deposit_asset_with_surplus(
		what: AssetsInHolding,
		who: &Location,
		_context: Option<&XcmContext>,
	) -> Result<Weight, (AssetsInHolding, XcmError)> {
		tracing::trace!(
			target: "xcm::transactor::erc20::deposit",
			?what, ?who,
		);
		defensive_assert!(what.len() == 1, "Trying to deposit more than one asset!");
		// Check we handle this asset.
		let maybe = what
			.fungible_assets_iter()
			.next()
			.and_then(|asset| Matcher::matches_fungibles(&asset).ok());
		let (asset_contract_id, amount) = match maybe {
			Some(inner) => inner,
			None => return Err((what, MatchError::AssetNotHandled.into())),
		};
		let who = match AccountIdConverter::convert_location(who) {
			Some(inner) => inner,
			None => return Err((what, MatchError::AccountIdConversionFailed.into())),
		};
		// We need to map the 32 byte beneficiary account to a 20 byte account.
		let eth_address = T::AddressMapper::to_address(&who);
		let address = Address::from(Into::<[u8; 20]>::into(eth_address));
		// To deposit, we actually transfer from the checking account to the beneficiary.
		// We do this using the solidity ERC20 interface.
		let data = IERC20::transferCall { to: address, value: EU256::from(amount) }.abi_encode();
		let weight_limit = WeightLimit::get();
		let ContractResult { result, weight_consumed, storage_deposit, .. } =
			pallet_revive::Pallet::<T>::bare_call(
				OriginFor::<T>::signed(TransfersCheckingAccount::get()),
				asset_contract_id,
				U256::zero(),
				TransactionLimits::WeightAndDeposit {
					weight_limit,
					deposit_limit: StorageDepositLimit::get(),
				},
				data,
				&ExecConfig::new_substrate_tx(),
			);
		// We need to return this surplus for the executor to allow refunding it.
		let surplus = weight_limit.saturating_sub(weight_consumed);
		tracing::trace!(target: "xcm::transactor::erc20::deposit", ?weight_consumed, ?surplus, ?storage_deposit);
		if let Ok(return_value) = result {
			tracing::trace!(target: "xcm::transactor::erc20::deposit", ?return_value, "Return value");
			if return_value.did_revert() {
				tracing::debug!(target: "xcm::transactor::erc20::deposit", "Contract reverted");
				Err((what, XcmError::FailedToTransactAsset("ERC20 contract reverted")))
			} else {
				match IERC20::transferCall::abi_decode_returns_validate(&return_value.data) {
					Ok(true) => {
						tracing::trace!(target: "xcm::transactor::erc20::deposit", "ERC20 contract was successful");
						Ok(surplus)
					},
					Ok(false) => {
						tracing::debug!(target: "xcm::transactor::erc20::deposit", "contract transfer failed");
						Err((
							what,
							XcmError::FailedToTransactAsset("ERC20 contract transfer failed"),
						))
					},
					Err(error) => {
						tracing::debug!(target: "xcm::transactor::erc20::deposit", ?error, "ERC20 contract result couldn't decode");
						Err((
							what,
							XcmError::FailedToTransactAsset(
								"ERC20 contract result couldn't decode",
							),
						))
					},
				}
			}
		} else {
			tracing::debug!(target: "xcm::transactor::erc20::deposit", ?result, "Error");
			// This error could've been duplicate smart contract, out of gas, etc.
			// If the issue is gas, there's nothing the user can change in the XCM
			// that will make this work since there's a hardcoded gas limit.
			Err((what, XcmError::FailedToTransactAsset("ERC20 contract execution errored")))
		}
	}
