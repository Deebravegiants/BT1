## Analysis Result

### Title
Webhook Shop-Domain Header Not Covered by HMAC Enables Cross-Tenant Webhook Spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` extracts the tenant identifier (`shop`) from an HTTP header that is never included in the HMAC-signed payload, while `ShopifyAPI::Webhooks::Registry.process` treats HMAC success as proof the entire request — including the shop attribution — is authentic and safe to hand to the app's handler.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, a value that is completely outside the signed content: [2](#0-1) 

`Registry.process` gates everything on `Utils::HmacValidator.validate(request)`, which in turn calls `to_signable_string` (body only) and never touches `shop`, `topic`, or any header: [3](#0-2) [4](#0-3) 

Once the body-only HMAC passes, `request.shop` is forwarded verbatim into `WebhookMetadata` and delivered to the app's handler as the trusted tenant identifier: [5](#0-4) 

The library's own documentation reinforces that host apps are expected to trust `data.shop` as verified: "This will verify the request did indeed come from Shopify and then call the specified handler," and the sample handler uses `data.shop` directly as `shop_domain` for downstream processing (docs/usage/webhooks.md — informational reference, not the vulnerable code itself).

**The broken identity binding, stated as an equality that the gem fails to enforce:**
`shop reported in WebhookMetadata == shop that the HMAC-signing secret actually attests to`

In reality the gem only proves: `bytes verified (raw_body) == bytes signed`, with no binding between the signature and the `shop-domain` header used for tenant attribution.

Because the HMAC key (the app's `client_secret`) is shared across every shop that installs the app, any merchant who installs the app can trigger a legitimate webhook to their own endpoint, capture the valid `(raw_body, hmac)` pair, and replay it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to a different, victim shop that also uses the same app. `HmacValidator.validate` still returns `true` (it only checks the body against the shared secret), so `Registry.process` proceeds and calls the handler with `WebhookMetadata.shop` set to the attacker-chosen victim shop domain, together with attacker-controlled body content.

### Impact Explanation
This is a cross-tenant confusion vector: an attacker-controlled webhook body can be attributed to any other shop that shares the same app installation, without needing that shop's access token, session, or credentials. Applications that use `data.shop` (as documented) to select which shop's stored access token/session to act on, or to write data scoped to that shop, will process attacker-supplied content under a victim tenant's identity — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Exploitation requires only that the attacker be an unprivileged internet user who can install the same public app on their own shop (to legitimately obtain one valid signed body/HMAC pair) and can send an arbitrary HTTP POST to the app's public webhook endpoint with a modified header — no secrets, tokens, or privileged access are required. The library provides no additional check to prevent this; `Registry.process` performs no verification correlating `shop` to the signed content.

### Recommendation
Bind the shop identity to the signed content, e.g., include the `shop-domain` (and ideally `topic`, `webhook-id`) in the HMAC computation, or require the caller to supply an expected shop and compare it against a value that has independent verification. At minimum, document prominently that `data.shop` is unauthenticated and must not be trusted for authorization decisions without an out-of-band check (e.g., verifying the shop has an active installation/session before using webhook data to act on that tenant's behalf).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook (e.g., `orders/create`) they control the body of.
2. Attacker captures the raw POST: headers `X-Shopify-Topic`, `X-Shopify-Hmac-Sha256`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, and `raw_body`.
3. Attacker resends the identical `raw_body` and `X-Shopify-Hmac-Sha256` to the same app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds successfully (all required headers present).
5. `ShopifyAPI::Webhooks::Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `raw_body` only using the app's shared `client_secret` — it matches, since the body/HMAC pair is unchanged.
6. `handler.handle(data: WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body: request.parsed_body, ...))` is invoked, causing the host app to process attacker-controlled data as if it originated from `victim-shop.myshopify.com`.
