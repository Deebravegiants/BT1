### Title
Simplex FXFiller prices Uniswap V4 venue fills off an unprotected, single-block spot price - ([File: sdk/packages/simplex/src/funding/uniswapV4/UniswapV4FundingPlanner.ts])

### Summary
The Vader finding shows an LP/IL-compensation formula that trusts an instantaneous, atomically-manipulable pool price, letting an attacker flashloan-skew reserves and extract value before the price reverts. Hyperbridge's Simplex solver has the same shape of bug: for curveless ("venue-priced") pairs, `UniswapV4FundingPlanner.getExoticTokenPrice` / `computeDirectPoolPriceUsd` reads the *current* `sqrtPriceX96` from Uniswap V4's `slot0` via `StateView.getSlot0` and uses it directly as the fill/funding price for real intent orders, with no TWAP and no built-in deviation check.

### Finding Description
`computeDirectPoolPriceUsd` computes `priceUsd` straight from `sdkPool.token0Price`/`token1Price`, which are derived from the pool's live `sqrtPriceX96` read in `UniswapV4LiquidityState.refresh()`: [1](#0-0) [2](#0-1) 

That price feeds directly into `getExoticTokenPrice`, which the FX strategy consults for any pair without static bid/ask curves: [3](#0-2) 

The documented flow confirms this price is used both to size the fill and to compute the solver's on-chain LP withdrawal, with only an *optional* deviation guard as protection, and explicitly notes the fee tier / execution impact is never applied: [4](#0-3) 

The only defense, `checkPriceGuard`, compares the venue quote against a **static reference price** the operator must manually configure per chain; if `referencePrice`/`maxDeviationBps` are omitted (which the docs explicitly allow — "omit both to leave the chain unguarded"), there is no protection at all: [5](#0-4) [6](#0-5) 

Same-chain intent orders — reachable by any unprivileged user submitting an order/intent — are filled **immediately, without waiting for confirmations**, meaning a single transaction (or a bundled/flashloan-composed set of transactions) can move the Uniswap V4 pool's spot price and have the fill priced off the manipulated state before it reverts: [7](#0-6) 

This directly mirrors the Vader/Warp Finance root cause: pricing a position (there, LP value for IL compensation; here, exotic-token fair value for a solver fill/withdrawal) off a single, unweighted, instantaneous pool price with no manipulation resistance (no TWAP, no per-tx impact bound, guard optional).

### Impact Explanation
When the price guard is unconfigured (the documented default/allowed state), or when the manipulation stays inside the configured `maxDeviationBps` band, an attacker can:
1. Skew the configured Uniswap V4 pool's spot price in one direction via a large swap.
2. Submit (or have controlled) an intent order that the FXFiller prices off that skewed spot price via `getExoticTokenPrice`.
3. Force the solver to withdraw liquidity (`planWithdrawalForToken`) and deliver output tokens priced at the manipulated rate, extracting value from the solver's Uniswap V4 LP position — a direct loss of solver/vault funds, analogous to draining the reserve via manipulated IL compensation in the Vader report.
4. Reverse the price-moving swap afterward (or let it be reversed by other traders) to restore normal book state, completing an atomic-style extraction.

This is a concrete theft-of-funds vector against the solver's own liquidity, reachable by any user who can submit a same-chain order and interact with the referenced Uniswap V4 pool — satisfying the "concrete theft ... of funds" bar.

### Likelihood Explanation
Likelihood is Medium-to-High: it requires (a) an LP/venue-priced pair with no `referencePrice`/`maxDeviationBps` configured (explicitly a supported, documented configuration), or a manipulation kept under the configured `maxDeviationBps`, and (b) sufficient capital/flashloan access to move the referenced pool's price meaningfully within one block relative to its depth. Given the guard is opt-in per chain and the price itself has no TWAP or execution-impact term, an operator following the documented minimal config (`[vault.uniswapV4] positions = [...]` without a guard) is exposed by default.

### Recommendation
- Make the price guard (`referencePrice`/`maxDeviationBps`) mandatory whenever a pair is configured as venue-priced (curveless), rather than optional.
- Replace or supplement the instantaneous `slot0` spot price with a TWAP (Uniswap V4 truncated oracle / observation-based average) for `computeDirectPoolPriceUsd`.
- Apply the pool's fee tier and a size/impact term to the quoted price (`computeLegPolicyOutput` currently extends the mid price linearly with no impact modeling), rather than treating the mid price as flat across the whole notional.
- Consider bounding fill size relative to the pool's actual on-chain liquidity depth, and/or requiring multiple price observations across blocks before honoring a venue-priced fill for larger orders.

### Proof of Concept
Conceptual, using the reachable code path:
1. Configure Simplex with `[vault.uniswapV4]` and a `[[pairs]]` entry with no `bidPriceCurve`/`askPriceCurve` and no `referencePrice`/`maxDeviationBps` on the position (a documented, supported configuration per `docs/content/developers/evm/simplex/pricing.mdx` lines 44/64-66/72).
2. Attacker executes a large swap against the exotic/USDC(T) Uniswap V4 pool referenced by the solver's position, moving `slot0.sqrtPriceX96` sharply.
3. Attacker (or a colluding party) immediately submits a same-chain intent order matching the venue-priced pair; per `docs/content/developers/evm/simplex/markets.mdx` (lines 8-10) it fills without waiting for confirmations.
4. `FXFiller.referenceRate`/leg-rate resolution calls `getExoticTokenPrice` → `computeDirectPoolPriceUsd`, which reads the just-manipulated `sqrtPriceX96` (`UniswapV4LiquidityState.refresh`, lines 199-217) and returns a skewed USD price with no guard rejecting it (`fx.ts` lines 422-448, guard is a no-op with `guard === undefined`).
5. The solver's `UniswapV4FundingPlanner.planWithdrawalForToken` withdraws LP liquidity and delivers tokens priced at the manipulated rate, transferring value to the attacker's counterparty position at the solver's expense.

Note: I could not fully trace the exact leg-rate resolution function (`resolveLegRates`) used at trade-execution time (as opposed to `referenceRate`, used for confirmation sizing) within the available tool budget; the described flow document (`venue-pricing-uniswap-v4-funded-pairs.md`) confirms the same `checkPriceGuard`/venue-price path is shared, but this should be independently verified in a full session before treating exploitability as fully proven end-to-end.

	async getExoticTokenPrice(chain: string, exoticToken: string): Promise<Decimal | null> {
		const state = this.stateByChain.get(chain)
		if (!state || !state.isHydrated()) return null

		try {
			await state.refresh()
		} catch (err) {
			this.logger.error({ err, chain }, "Failed to refresh state for price query")
			return null
		}

		const tokenLower = exoticToken.toLowerCase()
		let bestPrice: Decimal | null = null
		let bestLiquidity = 0n

		for (const pos of state.allPositions()) {
			if (pos.currency0.toLowerCase() !== tokenLower && pos.currency1.toLowerCase() !== tokenLower) continue
			const sdkPool = state.getSdkPool(pos.tokenId)
			if (!sdkPool) continue

			const result = this.computeDirectPoolPriceUsd(pos, sdkPool, chain)
			if (result && result.exoticToken.toLowerCase() === tokenLower) {
				const poolLiquidity = state.getPoolLiquidity(pos.tokenId)
				if (poolLiquidity > bestLiquidity) {
					bestPrice = result.priceUsd
					bestLiquidity = poolLiquidity
				}
			}
		}

		if (bestPrice) {
			this.logger.debug({ chain, token: tokenLower, priceUsd: bestPrice.toString() }, "Exotic token price computed")
		}
		return bestPrice
	}

	private computeDirectPoolPriceUsd(
		pos: HydratedV4Position,
		sdkPool: V4Pool,
		chain: string,
	): { exoticToken: string; priceUsd: Decimal } | null {
		const usdc = this.configService.getUsdcAsset(chain).toLowerCase()
		const usdt = this.configService.getUsdtAsset(chain).toLowerCase()
		const c0 = pos.currency0.toLowerCase()
		const c1 = pos.currency1.toLowerCase()

		if (c0 === usdc || c0 === usdt) {
			// currency0 is stable → exotic is currency1
			// token1Price = "token0 per token1" = USD per exotic
			return {
				exoticToken: c1,
				priceUsd: new Decimal(sdkPool.token1Price.toFixed(18)),
			}
		}

		if (c1 === usdc || c1 === usdt) {
			// currency1 is stable → exotic is currency0
			// token0Price = "token1 per token0" = USD per exotic
			return {
				exoticToken: c0,
				priceUsd: new Decimal(sdkPool.token0Price.toFixed(18)),
			}
		}

		return null
	}

`computeDirectPoolPriceUsd` returns the **raw pool mid** derived from `sqrtPriceX96`. The pool's
fee tier is read and stored on the hydrated position (`pos.fee`) but never applied to the price,
and there is no size or impact term — `computeLegPolicyOutput` extends the mid linearly across the
whole priced quantity. `checkPriceGuard` is the only defense on this path, and it checks deviation
from a static reference, not execution cost. A venue-priced pair that has to swap through its own
pool to source inventory pays a fee tier it never quoted against.

	/**
	 * Validates a live venue quote against the static reference price for the chain.
	 * Returns true (pass) when no guard is configured, or no reference exists for the
	 * chain. Returns false when the quote (token1 per USD) deviates from the reference
	 * by more than `maxDeviationBps`, in which case the order must not be filled.
	 */
	private checkPriceGuard(orderId: string | undefined, chain: string, venueToken1PerUsd: Decimal): boolean {
		const guard = this.priceGuard?.get(chain)
		if (!guard || guard.reference.lte(0)) return true

		const deviationBps = venueToken1PerUsd.minus(guard.reference).abs().div(guard.reference).mul(10000)
		if (deviationBps.gt(guard.maxDeviationBps)) {
			this.logger.warn(
				{
					orderId,
					chain,
					venuePrice: venueToken1PerUsd.toString(),
					referencePrice: guard.reference.toString(),
					deviationBps: deviationBps.toFixed(2),
					maxDeviationBps: guard.maxDeviationBps,
				},
				"Rejecting order: Uniswap venue quote outside price-guard band",
			)
			return false
		}
		return true
	}

**File:** docs/content/developers/evm/simplex/pricing.mdx (L68-72)
```text
## Uniswap price guards

Pool-based pricing trusts the live pool, which leaves the solver exposed to a manipulated, stale, or thin pool returning a bad quote. To bound that risk, give a position a **`referencePrice`** and **`maxDeviationBps`**. Whenever the pool quote on that chain drifts more than `maxDeviationBps` above or below the reference, the solver refuses to fill — the order is rejected before any bid is submitted.

`referencePrice` is expressed in **exotic tokens per USD**, the same units as the bid/ask curves. The two fields must be set together; omit both to leave the chain unguarded.
```

Simplex is a single pair engine. Every market it serves — cross-asset swaps like USDC/cNGN and same-asset cross-chain transfers like USDC→USDC — is a **`[[pairs]]`** entry in your TOML config, priced by its own bid/ask curves. Pairs reference assets by symbol from the built-in [asset registry](#the-asset-registry), and an LP can declare any number of them. Both **same-chain** and **cross-chain** orders are supported.

Same-chain orders (`source == destination`) are filled immediately without waiting for additional confirmations. Cross-chain orders wait per the configured [confirmation policy](/developers/evm/simplex/confirmations#confirmation-policy) before bidding.
