## Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) from an HTTP header that is completely outside the scope of the HMAC signature it validates. `Webhooks::Registry.process` trusts this header value as the authoritative shop for the webhook handler, even though the cryptographic proof (`HmacValidator.validate`) only attests to the integrity of the raw body — not the shop header. This breaks the equality that should hold: `shop authenticated by HMAC == shop delivered to the handler`.

### Finding Description
`Webhooks::Request` implements `Utils::VerifiableQuery`: [1](#0-0) 

Specifically:
- `hmac` is read from the `hmac-sha256` header.
- `to_signable_string` returns only `@raw_body`.
- `shop` is read independently from the `shop-domain` header, and is never included in `to_signable_string`. [2](#0-1) 

`HmacValidator.validate` computes `HMAC(secret, to_signable_string)` and compares it against the received `hmac`: [3](#0-2) 

Since `to_signable_string` for a webhook request is just `@raw_body`, the signature check only proves "this body was authored by someone who knows `api_secret_key`". It proves nothing about the `shop-domain`, `topic`, `api-version`, or `webhook-id` headers.

`Webhooks::Registry.process` nevertheless forwards `request.shop` straight to the handler as the trusted tenant identifier, without any additional binding check between the verified body and the claimed shop: [4](#0-3) 

Consequently, any attacker who can obtain one genuinely-signed webhook body+HMAC pair for **any** shop (e.g., from their own shop's app install, from a shared/generic webhook payload, or from a leaked/logged delivery) can resend the exact same `raw_body`/`hmac-sha256` pair to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header. `HmacValidator.validate` will still pass (it never looks at the header), and `Registry.process` will invoke the handler claiming the payload belongs to the attacker-chosen shop.

### Impact Explanation
This is a cross-tenant identity-binding break: the value used to route/attribute webhook data to a merchant (`shop`) is not bound to the cryptographic proof that a host application relies on to trust the request. A host app using this gem as documented (validate via `Webhooks::Registry.process`, then trust `data.shop`) can be made to process attacker-supplied `shop` values with a signature that was never computed over that shop, i.e., a form of cross-tenant access/spoofing satisfying the "Critical – cross-tenant access" bar.

### Likelihood Explanation
Requires an unprivileged internet user (no `access_token`, no `client_secret`, no privileged account) to: (1) obtain a single valid `raw_body` + `hmac-sha256` pair — for instance by installing the app to their own shop and receiving one legitimate webhook — and (2) POST it to the app's public webhook endpoint with a rewritten `shopify-shop-domain` header. No timing/race condition or secret knowledge is needed; only the currently-unauthenticated header needs to be attacker-controlled, which it always is on an inbound webhook HTTP request.

### Recommendation
Include the shop (and ideally topic/webhook-id/api-version) in the signable content the HMAC is verified against, or otherwise cryptographically bind the shop claim to the verified body (e.g., require callers to independently confirm `request.shop` corresponds to a shop with an active, previously-established session/installation before trusting it). At minimum, document prominently that `request.shop` is unauthenticated and must not be used as a sole tenant-routing key.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and receives one legitimate webhook delivery, capturing `raw_body` and the `x-shopify-hmac-sha256` value.
2. Attacker sends a request to the app's webhook endpoint with the same `raw_body` and `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only hashes `@raw_body` — validation succeeds. [5](#0-4) 
4. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` even though the HMAC was never computed with knowledge of, or binding to, that shop, letting the attacker impersonate a webhook for a shop they do not control.
