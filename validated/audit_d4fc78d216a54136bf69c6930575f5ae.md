### Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while the tenant-identifying `shop` value used downstream by the handler is read from an HTTP header that is never included in the HMAC-signed material. `ShopifyAPI::Utils::HmacValidator.validate` therefore only proves that *some* request with this exact body was signed by the app's secret — it proves nothing about which shop that body belongs to. This is the same class of bug as the C4 finding: a value that is *acted upon* (here, the tenant/shop the webhook payload is attributed to) is not bound by the authentication primitive (here, HMAC) that is supposed to guarantee authenticity.

### Finding Description
`ShopifyAPI::Webhooks::Request` exposes: [1](#0-0) [2](#0-1) 

`shop` (line 21-23) is parsed straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, but `to_signable_string` (line 36-38) — the value that is actually HMAC-verified — only returns `@raw_body`. Verification is performed here: [3](#0-2) 

and consumed in the registry's `process` method: [4](#0-3) 

The equality that should hold is:
`shop bound by HMAC == shop the handler attributes the payload to`

In this code path that equality never holds, because the left side is empty — HMAC only guarantees `body bound by HMAC == raw_body received`. Any request with a body that produces a correct HMAC for the shared `api_secret_key` will pass `Utils::HmacValidator.validate`, regardless of the `shop-domain` header sent alongside it.

### Impact Explanation
An attacker who legitimately installs the target app on their own (unprivileged) development/trial store can trigger a real webhook for their own shop (e.g. `orders/create`) and capture the resulting `raw_body` + valid `x-shopify-hmac-sha256` value — both are computed with the **same shared `api_secret_key`** used for every shop that installs the app, not a per-shop secret. The attacker can then POST that exact `body`/`hmac` pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and `x-shopify-webhook-id`/`x-shopify-topic`) headers with a victim shop's domain. `HmacValidator.validate` still succeeds (it only checks the body), and `Registry.process` invokes the app's handler with `WebhookMetadata.new(... shop: request.shop ...)` pointing at the victim shop. Any app logic keyed by `shop` (e.g., updating victim-shop records, triggering victim-shop side effects, writing into the victim tenant's data store) is now attacker-controlled — a cross-tenant access/injection primitive achievable by an unprivileged internet user with no access to the app's `client_secret`, access tokens, or the victim's credentials.

### Likelihood Explanation
Likelihood is high for apps that (a) allow public/self-serve installation (typical Shopify app model) and (b) key any business logic off `WebhookMetadata#shop` without independently re-validating that shop against the session/install record for that webhook id. No secret material needs to be recovered — only a legitimately obtained webhook body/HMAC pair from the attacker's own shop, which is trivial to obtain by installing the app once.

### Recommendation
Include the tenant-identifying header value(s) (at minimum `shop-domain`, ideally also `topic` and `webhook-id`) in the signed material verified by `HmacValidator`, or independently verify that `request.shop` matches a shop the app has an active, previously-registered subscription/session for before dispatching to the handler. Shopify's own webhook HMAC is computed over the raw body by design, so the safer fix is for `Registry.process` (or `Request`) to cross-check `shop` against known/authorized installations (e.g., via the `webhook_id` looked up per-shop) rather than trusting the header value implicitly once body HMAC succeeds.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com`.
2. Attacker triggers a real event (e.g., creates an order) causing Shopify to send a legitimate webhook to the app, with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
3. Attacker captures `B` and `H` from their own network traffic (their own webhook, no interception of others' traffic needed).
4. Attacker crafts a new HTTP POST to the app's webhook endpoint with the same body `B` and the same `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes HMAC over `raw_body` (`B`) — validation succeeds.
6. The registered handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed_body_of_B, ...)`, causing the app to process attacker-supplied data as though it originated from `victim-shop`.
