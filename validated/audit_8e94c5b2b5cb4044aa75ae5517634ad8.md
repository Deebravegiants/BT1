### Title
Webhook `shop` (and `topic`) identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop` (and `topic`) strictly from HTTP headers, while the HMAC signature validated by `Utils::HmacValidator` only covers the raw request body via `to_signable_string`. This breaks the intended binding `hmac_signed_bytes == authenticated_shop_identity`: the shop that receives an authenticated webhook is not the same field that is cryptographically protected.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are all pulled from HTTP headers, which are not part of the signed material: [2](#0-1) 

`Registry.process` validates the HMAC using `Utils::HmacValidator.validate(request)`, which internally calls `verifiable_query.to_signable_string` (the body) against the `hmac` header — it never mixes in `shop`, `topic`, or `webhook_id`: [3](#0-2) [4](#0-3) 

After the HMAC check passes, `request.shop` (unauthenticated header value) is forwarded verbatim into `WebhookMetadata`, which is the exact object handed to the application's `WebhookHandler#handle`: [5](#0-4) 

The equality the gem implicitly promises to the host application is: *"if `Utils::HmacValidator.validate(request)` returns true, then `request.shop` is the shop Shopify authenticated this delivery for."* In reality the check only proves *"the body bytes were signed by our secret"* — it says nothing about which shop-domain header accompanied those bytes. Any party capable of delivering an HTTP request with a previously-valid `(raw_body, hmac)` pair (e.g., a merchant who owns their own instance of the app and can replay/relay a webhook they legitimately received for their own shop) can swap the `x-shopify-shop-domain` header to name a different, victim shop while keeping the body and HMAC bytes unchanged. `HmacValidator.validate` still returns `true` because it never looked at the shop header, and the handler will process the payload as if it came from the victim shop.

### Impact Explanation
This is a cross-tenant identity confusion: an unprivileged webhook sender (any merchant/attacker who can obtain one valid signed body+hmac pair for their own shop, since the app's secret is never exposed to them and outbound webhooks always carry a valid signature for the sender's own events) can cause the receiving application to attribute webhook data to an arbitrary victim `shop` domain of their choosing. If the host app's handler trusts `WebhookMetadata#shop` to select which merchant record/session/tenant to update (a documented, intended usage of this exact field), this enables cross-tenant data corruption or disclosure — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Exploitation requires only the ability to send/replay one HTTP POST with the header changed; no access to the app's `client_secret`, access tokens, or any privileged credential is needed. Any user who can trigger a legitimate webhook delivery to themselves (e.g., installing the app on their own store, or triggering a mandatory GDPR webhook) obtains a valid `(body, hmac)` pair. Because the header is not covered by the signature, likelihood is moderate-to-high, gated only on the host application's webhook endpoint being reachable and the attacker being able to relay a request with a modified header value to it.

### Recommendation
Bind the shop identity to the signature verification: include `shop`, `topic`, and `webhook_id` header values in the string that is HMAC-verified (or otherwise cryptographically bind them, e.g. by verifying `shop` against the current app installation/session rather than trusting the header directly), so a body signed for one shop cannot be replayed for another. At minimum, document explicitly that `WebhookMetadata#shop` is untrusted header data and instruct implementers not to use it as a tenant key without independent verification (e.g., cross-checking against the session/shop that installed the webhook).

### Proof of Concept
1. App A (attacker-controlled) installs the Shopify app and receives a legitimate webhook delivery with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid-hmac-of-body>`, and some `raw_body`.
2. Attacker (running their own server/proxy in front of, or replaying to, the same app instance) resends the exact same `raw_body` and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC solely from `raw_body` [6](#0-5)  — validation succeeds because the body is unchanged.
4. `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` is built with `shop == "victim-shop.myshopify.com"` [7](#0-6)  and passed to the app's handler, which processes attacker-supplied data under the victim's tenant identity.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
