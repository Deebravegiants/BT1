### Title
Emporium `EmporiumStack{signerAddress: address(0)}` authorization bypass drains all ETH/ERC20 custodied in `EmporiumUpgradeable` - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
When `CircomData.externalActionData.externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `circomData.erc20TokenAddresses.length == 0`, `CircomDataBuilder.formInputForCircom` routes to `formInputEmporiumMin`, whose only circuit (`MainEVMCircuitMin`) constrains `message === Poseidon(1)([messageSeed])` and never checks `rootHashHinkal`, `inNullifiers`, or `spendingPublicKey`. Any unprivileged attacker can trivially generate a valid proof for this circuit (they pick `messageSeed` themselves), and combine it with an `EmporiumStack{signerAddress: address(0), ...}` so that `EmporiumUpgradeable.verifyWallet` skips ECDSA signature verification entirely, letting the attacker execute arbitrary `ops` (arbitrary `endpoint.call{value: op.value}(callData)`) directly from `EmporiumUpgradeable`'s own balance.

### Finding Description
The broken equality: the protocol implicitly assumes `AUTHORITY: signer of ops executed against Emporium's custody == account that produced the Groth16 proof (or a wallet contract that signed the EIP-712 EmporiumSignature)`. In the `signerAddress == address(0)` branch this equality collapses to nothing — there is no signer at all.

Code path:
1. `CircomDataBuilder.formInputForCircom` selects `formInputEmporiumMin` whenever `externalActionId == HINKAL_EMPORIUM_ACTION_ID && erc20TokenAddresses.length == 0`: [1](#0-0) 
2. The circuit used for this branch, `MainEVMCircuitMin`, only constrains `message <== Poseidon(1)([messageSeed])` — a value the prover fully controls by choosing `messageSeed` — and never touches `rootHashHinkal`, `inNullifiers`, or `spendingPublicKey`: [2](#0-1) 
3. `HinkalHelper.dimensionsCheck`/`checkOnchainCreation`/calldata-hash integrity all pass trivially with empty arrays and attacker-controlled fields, since the attacker builds `circomData` themselves and can compute `getHashedCalldata` to match: [3](#0-2) 
4. `Hinkal.transact`, with `erc20TokenAddresses.length == 0`, skips the balance/slippage-diff loop entirely (loop bound is 0), so no UTXO accounting constrains this action: [4](#0-3) 
5. `Hinkal._externalTransact` builds an empty `deltaAmountChanges` array (length 0) and forwards to `EmporiumUpgradeable.runAction`: [5](#0-4) 
6. `EmporiumUpgradeable.runAction` decodes `EmporiumStack` from attacker-supplied `externalActionMetadata` and calls `verifyWallet`: [6](#0-5) 
7. `verifyWallet` marks the message used and returns immediately when `stack.signerAddress == address(0)`, skipping the EIP-712 signature check entirely: [7](#0-6) 
8. Because `signerAddress == address(0)`, every op falls into "CASE 2: Stateless Interaction", executing `op.endpoint.call{value: op.value}(op.callData)` directly from `EmporiumUpgradeable`'s own held balance, with `endpoint`, `value`, and `callData` fully attacker-chosen: [8](#0-7) 

No existing guard catches this: `dimensionsCheck` only validates array-length consistency (trivially satisfiable with `tokenNumber=0`), `usedMessages` only prevents replay of the same forged message (not the underlying authorization), and there is no requirement anywhere that `signerAddress != address(0)` when `erc20TokenAddresses.length == 0`. The Min-circuit branch was seemingly intended only for cases where a real wallet-contract signature (EIP-712, `signerAddress != 0`) authorizes the ops; the `signerAddress == address(0)` shortcut removes that authorization entirely while still being reachable through this same unauthenticated code path.

### Impact Explanation
Any ETH or ERC20 balance that transiently sits in `EmporiumUpgradeable` (e.g., leftover dust from prior legitimate actions where `handleOut` intentionally leaves `balanceChange <= 0` un-transferred, refunds, or funds deposited by a legitimate user's own prior operation before their follow-up op executes) can be swept out by any unprivileged attacker to an address/contract of their choosing. This is direct theft of protocol/user custodied funds with no proof-of-ownership requirement — matching the Critical category ("direct theft of shielded or in-flight user funds ... proof or nullifier verification bypass"). The attack is fully repeatable for any balance that accumulates in the contract over time.

### Likelihood Explanation
Preconditions are minimal and attacker-controlled: the attacker needs (a) a verifier registered for `buildVerifierId(dimensions, HINKAL_EMPORIUM_ACTION_ID)` corresponding to `MainEVMCircuitMin` (required for the "Min" flow to function at all, so it must exist for the feature to be usable), and (b) any non-zero balance currently held by `EmporiumUpgradeable`. No signature, no shielded UTXO, no Merkle root, and no relay whitelisting are required when `circomData.relay == address(0)`. Generating the Groth16 proof costs nothing beyond picking an arbitrary `messageSeed` locally with snarkjs — this is by design trivial in the Min circuit. The attack is repeatable every time funds land in the contract.

### Recommendation
Reject the "no-signer" bypass path for arbitrary external calls: require `stack.signerAddress != address(0)` (and always require the EIP-712 signature check) whenever the action can move funds out of `EmporiumUpgradeable`'s own custody via `op.endpoint.call{value: op.value}(...)`. Alternatively, disallow `formInputEmporiumMin`/`signerAddress == address(0)` combinations where `op.value > 0` or where `callData` performs a token transfer of contract-held funds, and bind the op set (`_hashEmporiumOps`) cryptographically to a real prover-controlled secret (e.g., require nullifier/root-based ownership proof) rather than an unconstrained `Poseidon(messageSeed)` output.

### Proof of Concept
Foundry fork test outline:
1. Deploy/point to `Hinkal`, `EmporiumUpgradeable`, register a verifier for `MainEVMCircuitMin` at `buildVerifierId({tokenNumber:0, nullifierAmount:0, outputAmount:0}, HINKAL_EMPORIUM_ACTION_ID)`.
2. Fund `EmporiumUpgradeable` with ETH/ERC20 via a legitimate prior `transact` action (e.g., normal Emporium deposit flow), leaving a known balance `B` in the contract.
3. Off-chain (snarkjs), generate `messageSeed`, compute `message = Poseidon(1)([messageSeed])`; build `circomData` with `externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `erc20TokenAddresses = []`, `amountChanges = []`, `emporiumMessage = message`, `externalActionData.externalActionMetadata = abi.encode(EmporiumStack({signerAddress: address(0), ops: [EmporiumOperation({endpoint: attackerContract, invokeWallet: false, value: B, callData: drainCalldata})], maxFee:0, deadline:0, v:0, r:0, s:0}))`, and set `calldataHash = getHashedCalldata(circomData)`.
4. Generate a Groth16 proof `(a,b,c)` for `MainEVMCircuitMin` with public inputs `[message, timeStamp, calldataHash]`.
5. Call `Hinkal.transact(a,b,c,dimensions,circomData)` from an attacker EOA with no prior deposits/UTXOs of their own.
6. Assert: `verifyWallet` never reverts with `InvalidSignature` (no signature was checked); attacker's balance increases by exactly `B`; `EmporiumUpgradeable`'s balance goes to 0; assert equality broken: `signer-of-ops == prover` is never enforced (no `ecrecover` call occurs on this path, confirmed via trace).
