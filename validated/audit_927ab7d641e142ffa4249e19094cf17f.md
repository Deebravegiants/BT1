This confirms the root cause. The `Utils::VerifiableQuery` interface (`lib/shopify_api/utils/verifiable_query.rb`) requires only `hmac` and `to_signable_string`, and `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) . The `shop`, `topic`, `webhook_id`, and `api_version` values are all read straight from HTTP headers via `shopify_header` [2](#0-1)  and are never included in the HMAC-signed material. `Registry.process` validates only the body's HMAC, then dispatches using the unauthenticated `request.topic` header and forwards the unauthenticated `request.shop` header straight to the handler [3](#0-2) .

### Title
Webhook `shop`/`topic` headers are not covered by HMAC verification, allowing cross-tenant event/topic spoofing via signature replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` binds the HMAC only to `@raw_body`, while `shop`, `topic`, `webhook_id`, and `api_version` are read from unauthenticated HTTP headers and never enter the signed material.

### Finding Description
`Utils::HmacValidator.validate` computes `OpenSSL::HMAC.hexdigest(secret, verifiable_query.to_signable_string)` and compares it to the header-supplied `hmac` value [4](#0-3) . For webhooks, `to_signable_string` returns only the raw body bytes [1](#0-0) . The identity binding the gem implicitly promises is: `HMAC-authenticated bytes == bytes acted upon (body + shop + topic)`. In reality it is only `HMAC-authenticated bytes == body`; `shop`, `topic`, `webhook_id`, and `api_version` are unauthenticated header reads [2](#0-1) .

`Registry.process` trusts these unauthenticated fields directly: it looks up the handler by `request.topic` and passes `request.shop` into `WebhookMetadata` for the handler, with no verification that the topic/shop actually correspond to the signed body [3](#0-2) .

Because any app installer legitimately receives real, validly-signed webhook deliveries for their own (attacker-owned) shop — an ordinary, unprivileged action requiring no leaked secret — an attacker can capture a genuine `raw_body` + `x-shopify-hmac-sha256` pair from their own store's webhook traffic, then replay that exact body/HMAC pair directly to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` and/or `x-shopify-topic` headers. Since these headers are not part of the signed content, `HmacValidator.validate` still returns `true`, and `Registry.process` will dispatch to whatever handler is registered for the spoofed topic, passing the spoofed shop identity to the handler.

### Impact Explanation
This breaks tenant isolation (cross-tenant access): a host application's webhook handler that keys off `WebhookMetadata#shop` (e.g., to look up which shop's session/data to update, or to route GDPR compliance actions like `customers/redact`/`shop/redact`) can be made to attribute an attacker-supplied signed payload to a different, victim shop, or to redirect a signed payload of one topic into the handler registered for another topic. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Requires only that the attacker install the target app on a shop they control (a normal, unprivileged action available to anyone) and then send a direct HTTP request to the app's public webhook endpoint with modified headers — no secret, token, or privileged access is needed. Likelihood is High for any app whose webhook endpoint is reachable from the internet, which is the standard deployment model documented for this gem [5](#0-4) .

### Recommendation
Extend `Utils::VerifiableQuery`/`HmacValidator` (or `Webhooks::Request#to_signable_string`) so the HMAC binds to the header fields the library exposes as trusted (`shop`, `topic`, `webhook_id`, `api_version`) in addition to the raw body, or otherwise document/enforce that consumers must not treat these header-derived accessors as authenticated unless they are cross-checked against out-of-band knowledge (e.g., verifying `shop` against the session that requested webhook registration). At minimum, `Registry.process` should not implicitly imply these fields are verified.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (free, unprivileged).
2. Attacker triggers an `orders/create` event on their own store and captures the app's inbound webhook request: raw body `B` and header `x-shopify-hmac-sha256: H` (valid because Shopify computed it with the app's real secret over `B`).
3. Attacker sends a new HTTP POST directly to the app's public webhook endpoint with the same body `B` and same `x-shopify-hmac-sha256: H`, but with `x-shopify-shop-domain: victim-shop.myshopify.com` (and optionally a different `x-shopify-topic`).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `B` against `H` and passes [6](#0-5) .
5. The registered handler is invoked with `WebhookMetadata#shop == "victim-shop.myshopify.com"` even though the payload never originated from that shop [7](#0-6) .

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

class WebhookController < ApplicationController

    )
    render json: {success: true}.to_json
  end
end
