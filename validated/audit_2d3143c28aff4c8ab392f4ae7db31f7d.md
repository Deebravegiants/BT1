### Title
Bad-debt supply-index floor leaves wiped positions a phantom claim that drains fresh deposits - ([File: contracts/pool/src/interest.rs])

### Summary
`apply_bad_debt_to_supply_index` socializes bad debt by shrinking `supply_index`, but clamps the result upward at `SUPPLY_INDEX_FLOOR_RAW` (`RAY/1000`) instead of letting it reach zero. When the bad debt equals or exceeds total supplied value (full wipeout), surviving supply shares keep a strictly positive floor-valued claim even though the backing was fully written off. The pool's own tests demonstrate that after a wipeout a fresh deposit lets the wiped survivor withdraw real tokens equal to the fresh deposit, leaving the new depositor unbacked. The bug class — a write (index write-down) that corrupts state beyond the intended scope, analogous to an out-of-bounds write corrupting adjacent memory — maps onto the share/index accounting boundary here.

### Finding Description
In `contracts/pool/src/interest.rs:73-89`, `apply_bad_debt_to_supply_index` computes `remaining = total_supplied_value - min(bad_debt, total_supplied_value)`, derives `reduction_factor = remaining / total_supplied_value`, and sets `supply_index = max(supply_index * reduction_factor, SUPPLY_INDEX_FLOOR_RAW)`. On a full wipeout `remaining = 0`, so the mathematical index is 0, but it is clamped up to `RAY/1000`. Every unburned supply share thereby retains a claim of `floor(shares * RAY/1000 / 10^(27-d))` asset units against a market whose cash was fully consumed.

The cleanup is reachable permissionlessly: `process_clean_bad_debt` (`contracts/controller/src/positions/liquidation/mod.rs:196-200`) requires only `caller.require_auth()` and the `DustCapped` gate (`mod.rs:241-243`, `is_socializable_bad_debt` requires insolvency plus collateral at/below the dust threshold), and liquidation itself calls `check_bad_debt_after_liquidation` (`mod.rs:135`). Both paths funnel into `bad_debt::execute_bad_debt_cleanup` → the pool write-down.

Withdrawal uses `resolve_withdrawal` + `require_reserves` (`contracts/pool/src/cache/scale.rs:97`, `cache/cash.rs`); `require_reserves` only checks `cash >= gross`, so it passes as soon as any new supplier deposits.

### Impact Explanation
Theft of user funds / protocol insolvency. After a full bad-debt wipeout, the first fresh supplier's deposit can be fully extracted by a wiped-out legacy supplier (the clamp leaves the survivor a `> 0` stranded claim). The pool's own unit tests assert exactly this: `test_raw_cache_floor_clamp_strands_claim_without_supply_guard` and `test_raw_cache_seizure_residual_would_drain_fresh_cash_without_supply_guard` in `contracts/pool/tests/interest.rs:372-494` show `gross == fresh_cash` paid out to the wiped position and the fresh depositor's claim no longer covered by cash. Each wiped market permanently mis-prices legacy shares, so the pool books are insolvent (`total_owed > cash`) until the phantom claims are burned.

### Likelihood Explanation
Requires a market wipeout: residual debt with collateral at/below dust so `clean_bad_debt` socializes it, and bad debt ≥ total supplied value so the index would hit zero and the floor clamp binds. This is reachable when a market's debt is mostly bad debt or supply is thin, and any unprivileged caller can trigger `clean_bad_debt` (or `force_socialize_bad_debt` for larger residuals). Post-wipeout, a legacy supplier simply calls `withdraw` after any new deposit lands — no privileged role, no timing race. The caveat is that the floor clamp is a documented design choice ("Floors the resulting index at `SUPPLY_INDEX_FLOOR_RAW` to avoid a zero index"), which may reduce severity classification if considered an accepted trade-off; the fund-loss mechanics, however, are concrete and test-verified.

### Recommendation
On a wipeout (`capped == total_supplied_value`), burn or zero all outstanding supply shares and set the index explicitly rather than clamping to a positive floor — e.g., write `supplied = 0` / zero per-position shares during `execute_bad_debt_cleanup`, or have the controller delete dust collateral/debt positions atomically. Alternatively, gate withdrawals so positions whose shares predate a floor-clamped write-down cannot unscale against the clamped index (track a "wiped" epoch/generation per market). Add a production-flow regression test proving `clean_bad_debt` → `supply` → `withdraw` cannot transfer fresh cash to a wiped account.

### Proof of Concept
Reachable path: attacker or anyone observes an insolvent account with dust-level collateral → calls `clean_bad_debt(account_id)` (permissionless, `mod.rs:196`) → pool executes `apply_bad_debt_to_supply_index` which clamps `supply_index` to `SUPPLY_INDEX_FLOOR_RAW` (`interest.rs:88`) → victim calls `supply` crediting cash → wiped legacy supplier calls `withdraw` and `resolve_withdrawal`/`require_reserves` pays out the fresh deposit. Mechanism demonstrated by `contracts/pool/tests/interest.rs:372-494`.
