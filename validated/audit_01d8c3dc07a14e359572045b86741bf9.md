### Title
Webhook shop identity spoofable because HMAC binds only the request body, not the `shop-domain` header - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body, so `Utils::HmacValidator.validate` proves nothing about the `x-shopify-shop-domain` (or `shopify-shop-domain`) header. `Registry.process` trusts `request.shop` (parsed straight from that header) when it invokes the handler, without ever verifying that the shop header is tied to the HMAC-verified body.

### Finding Description
The identity binding that should hold is:
`shop delivered in WebhookMetadata == shop that produced/authorized the signed body`

`Request#hmac` and `Request#to_signable_string` are defined as: [1](#0-0) 

Only `@raw_body` is fed into the HMAC check, while `shop`, `topic`, `api_version`, and `webhook_id` are all read from unauthenticated headers: [2](#0-1) 

`Registry.process` validates the HMAC over the body only, then immediately builds `WebhookMetadata` using the unverified `request.shop` value and dispatches it to the app's handler: [3](#0-2) 

`HmacValidator.validate` computes the HMAC purely from `verifiable_query.to_signable_string` (the body) and compares it against the `hmac` header — it has no knowledge of, and does not cover, the shop header: [4](#0-3) 

Because the app's `client_secret` (the HMAC key) is shared across all shops that install the app, any tenant of a multi-tenant app can legitimately trigger a webhook for their own shop (e.g. by editing a resource), capture the resulting valid `(raw_body, hmac)` pair, and then replay it to the app's webhook endpoint with the `x-shopify-shop-domain` header changed to a victim shop's domain. `Registry.process` will pass HMAC validation (since the body/hmac pair is genuinely valid for the shared secret) and will hand the handler a `WebhookMetadata` claiming the payload belongs to the victim shop. Any host application that follows this gem's documented contract — using `data.shop` from the webhook handler to key session lookups, look up the merchant's access token, or persist per-tenant data — will process the attacker's payload as if it originated from the victim's shop, achieving cross-tenant data confusion using only an unprivileged, self-owned Shopify store installation.

### Impact Explanation
This breaks the shop/tenant identity guarantee the gem is expected to provide from `Registry.process`/`WebhookMetadata`: a value that host apps use to select the tenant record, access token, or session is not bound by the cryptographic check that is supposed to authenticate the whole request. This enables cross-tenant confusion/injection driven entirely by an attacker who is merely an app installer on their own store — no stolen credentials or TLS interception required.

### Likelihood Explanation
Medium-to-High: any developer/merchant who installs the target app on a store they control can generate arbitrary numbers of legitimately-signed webhook bodies (by triggering typical shop events), intercept them, and replay them against the webhook endpoint with a forged `shop-domain` header. No secret material needs to be recovered; the attacker only needs one authentic `(body, hmac)` pair from their own installation.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the signable content that is HMAC-verified, or otherwise cryptographically bind `request.shop` to the verified body before constructing `WebhookMetadata` in `Registry.process`. At minimum, document and enforce that `request.shop` must be cross-checked against a known, previously stored session/shop record before being trusted as an identity value, rather than being handed to handlers as if it were verified.

### Proof of Concept
1. Install the target multi-tenant app on an attacker-controlled development store `attacker-shop.myshopify.com`.
2. Trigger any subscribed webhook topic (e.g. `products/update`) on that store; capture the raw POST body and its `X-Shopify-Hmac-Sha256` header — this is a fully valid pair for the app's `client_secret`.
3. Replay the exact same body and HMAC header to the app's webhook endpoint, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` — which only checks `@raw_body` against the HMAC header — and it passes.
5. `WebhookMetadata` is built with `shop: "victim-shop.myshopify.com"` and dispatched to the app's handler, which will treat the attacker's payload as authentic data belonging to the victim tenant.
