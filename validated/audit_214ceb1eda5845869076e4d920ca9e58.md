### Title
Unprivileged bandwidth purchasers can evict another app's already-paid subscriptions from the FIFO cap, permanently destroying paid-for bandwidth and blocking that app's message route - (File: modules/pallets/bandwidth/src/lib.rs)

### Summary
`pallet-bandwidth` grants any caller of `BandwidthManager.purchase()` the ability to credit bandwidth to an **arbitrary** `(app_chain, app)` pair via the `chain`/`app` parameters it does not validate against the caller's identity. Each `(app_chain, app)` bucket keeps a FIFO list capped at 1024 `Subscription` entries; once full, the *next* purchase silently evicts the oldest entry, regardless of how much was paid for it or whether it has been consumed. Because purchasing is cheap and permissionless, and eviction is unconditional on cap overflow, any unprivileged actor can pay for a stream of minimal-tier subscriptions targeting a victim app to push the FIFO queue past 1024 entries, permanently evicting the victim's legitimately-paid, unconsumed bandwidth allowance and simultaneously starving the victim app's outbound-message route once its allowance is drained.

### Finding Description
`BandwidthManager.purchase()` on any EVM source chain lets `msg.sender` specify `app` (recipient) and `chain` (credit target) freely and pays only the tier price out of their own pocket: [1](#0-0) 

The docs confirm this is by design for "sponsorship" — anyone can credit any `(app_chain, app)`: [2](#0-1) 

On Hyperbridge, `pallet-bandwidth::on_accept` appends every accepted purchase as a new `Subscription` to the `(app_chain, app)` FIFO list via `push_subscription`, which is capped at `MAX_SUBSCRIPTIONS` (1024) and **unconditionally evicts the oldest entry** — silently destroying whatever bytes/time remained on it — whenever the cap is reached: [3](#0-2) 

This mirrors the report's bug class: a per-call check (`purchase()` succeeds, tier is valid, price is paid) never verifies the *aggregate* state of the downstream system (the FIFO subscription list) before committing new state, so repeated calls can push the total past a hard external cap, and the excess is silently and irreversibly destroyed — just as repeated `protocolDeposit` calls in the Lido case pushed the aggregate stake past Lido's hard `MAX_STETH_WITHDRAWAL_AMOUNT`, permanently trapping funds with no recovery path. Here, the "trapped" funds are the fee tokens the victim already paid for a subscription that gets evicted before being consumed — there is no refund, and the pallet's own documentation acknowledges the eviction path exists but assumes it's "only" a self-inflicted, pathological accident (`SubscriptionEvicted` is emitted "so the lost bytes are auditable on-chain" — i.e., the loss is expected, not prevented): [4](#0-3) 

Because `app`/`chain` are attacker-controlled and unauthenticated against the caller, this is not limited to self-griefing: any third party can target a victim `(app_chain, app)` pair they don't own.

### Impact Explanation
An unprivileged bandwidth purchaser can:
1. Repeatedly call `purchase()` (cheapest configured tier, 1 month) targeting a victim's `(app_chain, app)` pair until the victim's FIFO list reaches 1024 entries and beyond.
2. Each purchase past the cap evicts the oldest live entry — including the victim's own genuine, unconsumed, previously-paid subscription(s) — with the lost bytes gone forever (no refund path exists anywhere in the pallet or `BandwidthManager`).
3. Once the victim's real allowance is evicted, `BandwidthGate::try_consume` starts rejecting the victim app's outbound ISMP dispatches with `NoAllowance`/`Insufficient`, halting that app's route until it re-purchases — a "route unable to deliver messages" condition — while the fee tokens it already spent on the evicted subscription are permanently lost (frozen with no recovery), a direct funds-loss impact.

This is a permanent, irreversible loss of paid protocol revenue/allowance for the victim app, achievable by any unprivileged bandwidth purchaser without any special privilege, and it also produces a denial-of-service on the victim's message route — both outcomes are explicitly in-scope impacts.

### Likelihood Explanation
The attack requires no privileged role, no collusion, and no race condition — only sequential transactions from any account, each independently valid per the pallet's own rules (`purchase()` never validates that the caller "owns" `app`/`chain`, by explicit design for sponsorship). The only cost is 1024 × cheapest tier price (e.g., ~$50 per purchase at `TierOne`), which is a bounded, attacker-known cost to permanently destroy a competitor's/victim's paid allocation and disrupt its bridging route — a realistic griefing economics for high-value targets (e.g., a rival token gateway whose bandwidth purchase cost or business disruption exceeds the attack cost). The eviction logic itself is deterministic and always triggers once the cap is hit, so the outcome is guaranteed, not probabilistic.

### Recommendation
- Restrict `purchase()`/`on_accept` credit targeting so a caller can only credit `(app_chain, app)` pairs it is authorized for (e.g., require the dispatching contract's own address as `app`, or an explicit allow-list/registration step), removing the ability for arbitrary third parties to write into another app's subscription queue.
- If cross-app sponsorship must be retained, replace unconditional oldest-eviction with a policy that never destroys value for consumers other than the purchaser (e.g., reject the purchase with an error instead of silently evicting when the list is full, or merge same-tier "consumable-soon" subscriptions instead of a strict cap-based eviction), and/or refund/credit the evicted subscription's remaining value back to whoever paid for it.
- Consider raising `MAX_SUBSCRIPTIONS` well beyond realistic usage or moving to an aggregate-byte-balance model (single counter with expiry buckets) instead of a bounded FIFO list, closing the "hard external cap can be forced by third-party spam" class of issue entirely.

### Proof of Concept
1. Governance configures `TierOne` at price `P` and registers a `BandwidthManager` on chain `S`.
2. Victim app `A` legitimately purchases a large tier (e.g., `TierFour`) on `S`, crediting `(app_chain = A_chain, app = A)`, receiving a `Subscription` with a long `expires_at` and large `remaining_bytes`. This becomes entry #1 (or later, but unexpired) in `Allowance::<T>::get(A_chain, A)`.
3. Attacker, from any account, calls `BandwidthManager.purchase(app = A, tier = TierOne, months = 1, chain = A_chain)` 1024 times (using their own funds), each producing a `BandwidthPurchaseMsg` accepted by `pallet-bandwidth::on_accept`, each calling `push_subscription` and appending to the same `(A_chain, A)` list: [5](#0-4) 
4. Once the list length reaches `MAX_SUBSCRIPTIONS` (1024), each subsequent attacker purchase evicts the oldest entry (`list.remove(0)`), which — depending on ordering — eventually reaches and evicts victim `A`'s genuine `TierFour` subscription, emitting `SubscriptionEvicted` with its full `lost_bytes`, permanently destroying the value `A` paid for.
5. `A`'s subsequent outbound ISMP dispatches on chain `A_chain` are rejected by `BandwidthGate::try_consume` once its real allowance is gone, even though `A` paid for `TierFour` and never got to use it — funds permanently lost, route blocked until `A` re-purchases.

```text
    function purchase(bytes calldata app, uint256 tier, uint256 months, bytes calldata chain)
        external
        returns (bytes32 commitment)
    {
        if (app.length == 0 || app.length > MAX_APP_LENGTH || chain.length == 0 || months == 0) {
            revert InvalidPurchase();
        }
        uint256 price18d = tierPrice[tier];
        if (price18d == 0) revert UnknownTier();

        uint256 total18d = price18d * months;
        address feeToken = IDispatcher(_host).feeToken();
        uint8 dec = IERC20Metadata(feeToken).decimals();
        uint256 scale = 10 ** (18 - dec);
        if (total18d % scale != 0) revert PriceNotRepresentable();
        uint256 amount = total18d / scale;

        IERC20(feeToken).safeTransferFrom(msg.sender, address(this), amount);

        BandwidthPurchaseMsg memory body = BandwidthPurchaseMsg({
            app: app,
            tier: tier,
            months: months,
            chain: chain
        });

        commitment = IDispatcher(_host).dispatch(
            DispatchPost({
                dest: IDispatcher(_host).hyperbridge(),
                to: PALLET_BANDWIDTH_MODULE_ID,
                body: abi.encode(body),
                timeout: 0,
                fee: 0,
                payer: address(this)
            })
        );
```

```text
## Sponsorship

The purchase message carries its own `chain` (the _credit chain_) which is **independent of the source chain** that sent the message. This means a buyer on Ethereum can credit an app on Base by dispatching a purchase whose payload sets `chain = "EVM-8453"`.

The pallet keys allowance storage by `(app_chain, app)` taken from the message body, not by `request.source`. The event `BandwidthCredited` carries both — `app_chain` (where the credit lands) and `paid_from` (where the payment came from) — so the cross-chain payer is auditable.

This is what makes the system multi-tenant friendly: a treasury on a single chain can sponsor bandwidth for an app deployed across many chains, without having to deploy `BandwidthManager` on each chain the app lives on.
```

```rust
		/// Append a fresh subscription with a fixed expiry. If the list
		/// is already at `MaxSubscriptions`, evict the oldest entry and
		/// emit [`Event::SubscriptionEvicted`] so the lost bytes are
		/// auditable. Returns the new subscription's `expires_at`.
		fn push_subscription(
			app_chain: &StateMachine,
			app: &AppKey,
			tier: TierIndex,
			bytes: BandwidthBytes,
			duration_secs: u64,
		) -> u64 {
			let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();
			let expires_at = now.saturating_add(duration_secs);
			let new_sub =
				Subscription { tier, remaining_bytes: bytes, expires_at, purchased_at: now };

			let evicted = Allowance::<T>::mutate(app_chain, app, |list| {
				let evicted = if list.len() == MAX_SUBSCRIPTIONS as usize {
					Some(list.remove(0))
				} else {
					None
				};
				// Capacity is now guaranteed; try_push can't fail.
				let _ = list.try_push(new_sub);
				evicted
			});

			if let Some(old) = evicted {
				Self::deposit_event(Event::SubscriptionEvicted {
					app_chain: *app_chain,
					app: app.clone(),
					tier: old.tier,
					lost_bytes: old.remaining_bytes,
				});
			}

			expires_at
		}
```
