### Title
Webhook shop-domain header is not covered by HMAC, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC of the raw body, then hands the handler a `WebhookMetadata` whose `shop` field is copied verbatim from the `x-shopify-shop-domain` HTTP header — a value that is never part of the signed payload.

### Finding Description
`Utils::HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the `hmac` accessor with `OpenSSL.secure_compare` [4](#0-3) . For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` [1](#0-0) , and `hmac` is derived purely from the `hmac-sha256` header [5](#0-4) . None of `topic`, `shop`, `webhook_id`, or `api_version` — all read directly from attacker-controllable headers via `shopify_header` [3](#0-2) [6](#0-5)  — participate in the signed bytes.

`Registry.process` then does: `raise ... unless Utils::HmacValidator.validate(request)` followed immediately by `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))` [2](#0-1) . The identity binding broken here is: `shop asserted to handler == shop bound by HMAC` is treated as true, but in reality `shop bound by HMAC == ∅` (the header is outside the MAC scope) while `shop asserted to handler == attacker-controlled header value`.

Since `Context.api_secret_key` is a single per-app secret shared across every shop that installs the app (not a per-shop secret) [7](#0-6) , any party who can obtain one valid `(raw_body, hmac)` pair for the app — trivially achievable by installing the app on their own shop and capturing a genuine webhook delivery — can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary victim shop domain in `x-shopify-shop-domain`. `HmacValidator.validate` still passes because it only checks the body against the shared secret, and `Registry.process` forwards the attacker-chosen `shop` value to the host application's handler as if it were authenticated.

### Impact Explanation
This breaks the tenant boundary that host applications rely on: `WebhookMetadata#shop` is the only tenant identifier delivered to webhook handlers, and it is trusted as authenticated once `HmacValidator.validate` returns true. Any host app that uses `data.shop` to look up a session/access token, write per-merchant records, or trigger merchant-scoped side effects (e.g. GDPR `customers/redact`, `shop/redact` mandatory webhooks, order/product sync) can be made to act on/against the wrong tenant's data using another (attacker-controlled) shop's payload, i.e. cross-tenant access/confusion — meeting the Critical bar for cross-tenant access.

### Likelihood Explanation
Moderate-to-high: the attacker needs only (a) a free/dev install of the target app on a shop they control to obtain one legitimately-signed `(body, hmac)` pair, and (b) the ability to POST to the app's public webhook endpoint with a forged `x-shopify-shop-domain` header — both are unprivileged-internet-user capabilities requiring no access token, no `api_secret_key`, and no interaction with the victim shop.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the authenticated bytes, e.g. include `x-shopify-shop-domain` and `x-shopify-topic` in the value passed to `HmacValidator` (matching Shopify's documented webhook verification, where the signature is over the raw body but delivery-time authenticity of the shop should additionally be cross-checked against the app's own installed-shop/session store before dispatch), or require `Registry.process` callers to verify `request.shop` corresponds to a shop with an active session/installation before invoking `handler.handle`. At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated header data and must not be trusted as a tenant key without an independent lookup.

### Proof of Concept
```ruby
# Attacker installs the app on their own shop "attacker.myshopify.com" and
# receives a legitimate webhook delivery, e.g. for topic "customers/redact":
#   raw_body = '{"customer":{"id":123}}'
#   valid_hmac = <the real x-shopify-hmac-sha256 header Shopify sent>
#
# Attacker replays the exact same body+hmac to the target app's webhook
# endpoint, but swaps the shop-domain header to the victim shop:
headers = {
  "x-shopify-topic"       => "customers/redact",
  "x-shopify-hmac-sha256" => valid_hmac,                # unchanged, still valid for raw_body
  "x-shopify-shop-domain" => "victim-shop.myshopify.com" # forged, not covered by hmac
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => Utils::HmacValidator.validate(request) returns true (body/hmac match the shared secret)
# => handler.handle(data: WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", ...))
# The host app's handler now processes attacker-supplied data attributed to the victim shop.
```
