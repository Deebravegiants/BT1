### Title
`deposit` mints `u0` shares for a dust deposit while still crediting `amount` to `assets`, permanently losing the depositor's contribution - (File: `mainnet/contracts/vault/v0-vault-ststx.clar`)

### Summary
`deposit` computes `inkind` via `convert-to-shares-preview` and only guards against `amount == u0`, never against `inkind == u0`, unlike `redeem` which explicitly checks `(asserts! (> inkind u0) ERR-OUTPUT-ZERO)`. Once the vault's share price (`total-assets-preview / total-supply-preview`) exceeds `1`, any depositor supplying the smallest unit of `amount` (e.g. `u1`) gets `inkind = u0` from `mul-div-down amount ts ta`, yet `receive-underlying` still pulls the full `amount` in real tokens and `(var-set assets (+ current-assets amount))` permanently records it as backing with no shares issued to redeem it.

### Finding Description
The intended ERC-4626-style invariant is:
```
sum(zft balances) * (total-assets / total-supply) == total-assets
```
i.e. every unit of `assets` must be represented by a claimable amount of `zft`. `deposit` breaks this: [1](#0-0) 

```
(define-private (convert-to-shares-preview (amount uint))
  (let ((ta (total-assets-preview))
        (ts (total-supply-preview)))
    (if (is-eq ts u0)
        amount
        (if (is-eq ta u0)
            u0
            (mul-div-down amount ts ta)))))
```

When `ts > 0` and `ta > ts` (share price > 1, which happens after any interest accrual since `total-assets-preview` grows via `debt-preview` interest while `total-supply-preview` only grows by the smaller treasury-fee share `calc-treasury-lp-preview`), a deposit of `amount = u1` yields `mul-div-down(1, ts, ta) = 0` because `ts < ta`.

`deposit` only validates the raw `amount`, not the derived shares: [2](#0-1) 

```
(define-public (deposit (amount uint) (min-out uint) (recipient principal))
    ...
      (inkind (convert-to-shares-preview amount)))

    ...
    (asserts! (> amount u0) ERR-AMOUNT-ZERO)
    (asserts! (>= inkind min-out) ERR-SLIPPAGE)
    ...

    (try! (receive-underlying amount account))
    (try! (ft-mint? zft inkind recipient))
    (var-set assets (+ current-assets amount))
    ...
    (ok inkind)))
```

With default `min-out = u0`, `(>= u0 u0)` passes, so the slippage check does not stop the zero-mint. `ft-mint? zft u0 recipient` succeeds (Clarity's `ft-mint?` does not reject amount `u0`), `receive-underlying` transfers the real `amount` of underlying stSTX from the depositor into the contract, and `assets` is incremented by that `amount`. Contrast this with `redeem`, which has the matching guard the depositor-side lacks: [3](#0-2) 

```
  (asserts! (>= current-assets inkind) ERR-INSUFFICIENT-ASSETS)
  (asserts! (not (get redeem states)) ERR-PAUSED)
  (asserts! (> amount u0) ERR-AMOUNT-ZERO)
  (asserts! (> inkind u0) ERR-OUTPUT-ZERO)
```

The asymmetry (guard present in `redeem`, missing in `deposit`) confirms this is an omission rather than intended design.

### Impact Explanation
Per triggering call, the depositor irrecoverably loses exactly `amount` (the smallest transferable unit, e.g. `u1` underlying) since no shares are minted to redeem it back; those tokens become permanently trapped in the vault's `assets` balance, silently diluting share price in favor of all existing `zft` holders. The action is fully repeatable — any account can call `deposit` with `amount = u1` as many times as it wants once share price > 1, each time losing `u1` with no way to reclaim it. While the per-call loss is tiny, it is a genuine, deterministic, permanent loss of principal for the caller (not an intended fee), and no existing check prevents it (min-out defaults to `u0` and passes trivially). This matches the "permanent freezing/loss of funds" category, though only the caller's own dust amount is at risk per call, not third-party funds, since the caller supplies their own `amount`.

### Likelihood Explanation
The precondition — share price (`total-assets-preview`/`total-supply-preview`) exceeding `1` — occurs naturally and quickly after any interest accrues in the vault (via `accrue`/`next-index`), which is routine, expected protocol operation, not an attacker-manufactured condition. Once that holds, triggering the bug costs only `u1` of underlying and one transaction; it requires no privileges, oracle interaction, or flashloan, and is trivially repeatable.

### Recommendation
Add the same zero-output guard used in `redeem` to `deposit`:
```
(asserts! (> inkind u0) ERR-OUTPUT-ZERO)
```
placed alongside the other precondition checks in `deposit`, before `receive-underlying`/`ft-mint?`/`var-set assets` are executed, so a dust deposit reverts instead of silently consuming the depositor's funds.

### Proof of Concept
Clarinet/vitest simnet plan:
1. Deploy and `initialize` the `v0-vault-ststx` vault (mints `MINIMUM-LIQUIDITY` shares to `NULL-ADDRESS`, so `total-supply-preview > 0`).
2. Perform a normal deposit from account A of a large amount (e.g. `u1_000_000_000`) to establish `ts > 0`, `ta > 0`, price = 1.
3. Simulate interest accrual: e.g. call `system-borrow` from an authorized contract and advance `stacks-block-time`, then call `accrue`, so `total-assets-preview` grows relative to `total-supply-preview` (price per share > 1). Confirm via `get-total-assets` and `get-total-supply` that `ta > ts`.
4. From account B (attacker/depositor), call `deposit(u1, u0, B)`.
5. Assert:
   - `(ft-get-balance zft B)` == `u0` (no shares minted).
   - `(get-assets)` increased by exactly `u1` compared to pre-call value.
   - The underlying stSTX balance of B decreased by `u1` and the vault contract's real token balance increased by `u1` (confirm via `ubalance`/`get-balance` on the `ststx-token` contract).
6. This demonstrates `sum(zft balances) * price != total-assets` by exactly `u1`, and that B's `u1` deposit is permanently unattributed/unredeemable (no `redeem` call can recover it since B holds `u0` shares).
