### Title
Webhook `shop` (and `topic`, `webhook_id`, `api_version`) identity fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw request body only, while the shop identity (`shop`), event `topic`, `webhook_id`, and `api_version` are all read directly from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` verifies only that the HMAC of the raw body is valid, then unconditionally trusts `request.shop`/`request.topic` to dispatch the event to the host app's handler. Anyone who can produce (or replay) one valid `(body, hmac)` pair can attach that pair to arbitrary `shop-domain`, `topic`, `webhook-id`, and `api-version` header values, and the library will accept it as an authentic event for that spoofed shop/topic.

### Finding Description
`Request#to_signable_string` returns only the raw body: [1](#0-0) 

But `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from headers with no cryptographic binding to that body: [2](#0-1) 

`Registry.process` validates the HMAC of the body, then dispatches using the unauthenticated `request.shop`/`request.topic` values: [3](#0-2) 

`HmacValidator.validate` performs `OpenSSL.secure_compare` between the received signature and the signature computed over `verifiable_query.to_signable_string` — i.e., the body only: [4](#0-3) 

The identity binding that should hold is:
`shop attributed to the event by process()` == `shop the HMAC signature actually authenticates`

Because the signature only authenticates the byte-string of the body, and the shop/topic/webhook_id/api_version headers are excluded from that signable string, the equality does not hold. Any party who legitimately receives one valid webhook delivery (e.g., a merchant who installs the app on their own store and receives a real, correctly-signed webhook for their own shop) can capture that `(raw_body, hmac)` pair and resend it to the app's public webhook endpoint with a different `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header. `HmacValidator.validate` still returns `true` because it only checks the body bytes, and `Registry.process` will hand the attacker-chosen `shop` value straight to the host app's handler alongside the replayed body.

### Impact Explanation
This breaks the tenant boundary the HMAC check is meant to enforce: the library asserts "this event, attributed to this shop, is authentic," but it can only prove "this body is authentic," not which shop it belongs to. A host app that trusts `WebhookMetadata#shop` (as the library's own webhook contract instructs it to) can be made to record, act on, or overwrite tenant-scoped data (e.g., orders, customers, app-installation state) under a shop identity chosen by the attacker rather than the one Shopify actually delivered the event for — i.e., cross-tenant access/injection, satisfying the High-impact bar for a scope/expiry-style identity-check bypass in this gem.

### Likelihood Explanation
The prerequisite is only possession of one genuinely-signed webhook for any shop (trivially available to any merchant who installs an app using this gem and receives its own webhooks) and the ability to POST to the app's public webhook callback URL, which by design is an unauthenticated internet-facing endpoint. No `api_secret_key`, access token, or privileged account is required — only replay/tamper of headers that are outside the signed payload.

### Recommendation
Include the shop domain (and ideally topic/webhook id/api version) in the value that is HMAC-verified, or otherwise cryptographically/contextually bind the header-derived `shop` to the specific signature before dispatching to handlers — e.g., verify `request.shop` against the shop associated with the session used to register the webhook subscription, rather than trusting the header value once the body-only HMAC passes.

### Proof of Concept
1. Register a webhook handler for topic `orders/create` in the host app using this gem.
2. Attacker installs the same public app on their own store `attacker.myshopify.com` and receives one legitimate webhook delivery with body `B` and header `X-Shopify-Hmac-Sha256: H` (a valid signature of `B`), `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. Attacker replays a POST to the app's webhook endpoint with the same body `B` and signature `H`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `B` against `H`: [3](#0-2) 
5. The host app's handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and processes the attacker's body as though it originated from the victim shop, demonstrating cross-tenant identity spoofing without any secret material.
