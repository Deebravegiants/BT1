Audit Report

## Title
Cross-user response hijacking via attacker-controlled MessageID collision in Gateway WebAPI trigger handler - (File: core/services/gateway/handlers/capabilities/handler.go)

## Summary
The Gateway's legacy WebAPI trigger flow keys pending user callbacks solely by a client-supplied `MessageID` with no binding to the requester's identity or DON-level authorization. An attacker who can obtain any signing key (no special privilege required) can submit a `web_api_trigger` request reusing the same `MessageID` as another in-flight legitimate request, silently overwriting that victim's saved callback in `h.savedCallbacks`, so that the subsequent DON node response intended for the victim is delivered to the attacker instead.

## Finding Description
`ProcessRequest` in `core/services/gateway/gateway.go` decodes the untrusted JSON-RPC request and, for legacy requests (those with `msg.Body.DonID != ""`), only validates the message's signature via `msg.Validate()` before dispatching to `HandleLegacyUserMessage` [1](#0-0) . `msg.Validate()` in `core/services/gateway/api/message.go` only confirms the signature matches the sender's own key and derives `Sender` from it — it performs no check that `MessageID` is unique or bound to a particular sender [2](#0-1) . Any party holding an ECDSA keypair can self-sign a message with an arbitrary, attacker-chosen `MessageID`, since nothing at the Gateway layer restricts who may submit such a request; the code explicitly flags the absence of allowlist/rate-limiting enforcement at this point (`// TODO: apply allowlist and rate-limiting here`) [3](#0-2) .

`HandleLegacyUserMessage` then unconditionally stores the caller's callback keyed only by `MessageID`, overwriting any existing entry without a duplicate/ownership check: `h.savedCallbacks[msg.Body.MessageID] = &savedCallback{...}` [4](#0-3) . When a DON node later responds to a `web_api_trigger` message, `handleWebAPITriggerMessage` looks the callback up strictly by `MessageID` and delivers it to whichever callback is currently present, with no verification that the response corresponds to the same sender who registered it: `savedCb, found := h.savedCallbacks[msg.Body.MessageID]` followed by `savedCb.SendResponse(...)` [5](#0-4) . The collision window is bounded by `CallbackMaxAgeSec`, defaulting to 120 seconds [6](#0-5) .

Downstream sender-allowlist enforcement (`allowedSenders` checked in `processTrigger`) exists only at the DON's `triggerConnectorHandler.HandleGatewayMessage`, which determines whether a workflow actually fires, but it does not affect or protect the Gateway's `savedCallbacks` map — the map overwrite and response misdelivery happen entirely at the Gateway layer, before/independent of that downstream check [7](#0-6) . Consequently the attacker's own message (even if ultimately rejected as an unauthorized sender by the workflow's `allowedSenders` list) still succeeds in overwriting the victim's callback entry at the Gateway, and the victim's authorized trigger response can then be delivered to the attacker's callback instead.

This is corroborated by the fact that the newer v2 HTTP trigger handler (`core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go`) explicitly guards against exactly this class of bug by rejecting duplicate/in-flight request IDs (`require.Contains(t, err.Error(), "in-flight request")` in its test suite) [8](#0-7) , confirming that the legacy handler's lack of such a check is a real, unaddressed gap rather than an intentional design choice.

## Impact Explanation
An unprivileged actor with only a self-generated signing key can cause cross-user response misdelivery at the Gateway: the victim's workflow-trigger response payload can be delivered to the attacker's HTTP connection instead of the victim's, and the victim's request will hang until `RequestTimeoutError` fires in `callback.Wait(ctx)` [9](#0-8) . This matches the in-scope "cross-user response corruption" / "gateway request impersonation" impact category, since it is caused entirely by Gateway-layer code (not a malicious node/peer) and is triggerable by any external caller who can reach the Gateway's legacy user-facing endpoint.

## Likelihood Explanation
Exploitability requires the attacker to predict or guess the exact `MessageID` string used by a legitimate in-flight request and to submit their own signed message with that ID within the up-to-120-second window before the DON responds. Since `MessageID` is fully client-supplied with no server-side randomness or entropy requirement, this is straightforward against callers using low-entropy, predictable, or observable IDs (e.g., sequential/fixed IDs used by some integration), but harder against callers using high-entropy random IDs (e.g., UUIDs). The exact ease of exploitation therefore depends on real-world ID generation conventions of Gateway clients, which was not verifiable purely from the indexed code.

## Recommendation
Bind `savedCallbacks` entries to both `MessageID` and the authenticated sender (derived from `msg.Validate()`'s signature check), rejecting a new registration if an entry for that `MessageID` already exists and belongs to a different sender — mirroring the "in-flight request" duplicate-ID rejection already implemented in the v2 `httpTriggerHandler`. Additionally, implement the still-outstanding TODO for allowlist and rate-limiting enforcement in `HandleLegacyUserMessage`.

## Proof of Concept
1. Victim submits a valid, self-signed `web_api_trigger` request to the legacy Gateway endpoint with `MessageID = "shared-id"`; `HandleLegacyUserMessage` stores the victim's callback in `h.savedCallbacks["shared-id"]` and dispatches to DON members.
2. Before the DON responds, attacker (any party with a keypair) submits their own self-signed `web_api_trigger` request, also with `MessageID = "shared-id"`, to the same DON handler; `h.savedCallbacks["shared-id"]` is overwritten with the attacker's callback (no uniqueness check exists in `HandleLegacyUserMessage`).
3. When the DON node responds with `MessageID = "shared-id"` for the victim's original (authorized) trigger, `handleWebAPITriggerMessage` looks up `h.savedCallbacks["shared-id"]`, finds the attacker's callback, and delivers the victim's response to the attacker.
4. The victim's original HTTP request receives no response and times out via `RequestTimeoutError`.
5. A Go unit test analogous to `TestHandlerReceiveHTTPMessageFromClient` in `handler_test.go` can be constructed: call `HandleLegacyUserMessage` twice with different callbacks but the same `MessageID`, then invoke `HandleNodeMessage` once to confirm the second (attacker) callback receives the response while the first (victim) callback never resolves.

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageID) == 0 || len(m.Body.MessageID) > MessageIDMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageID, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonID) == 0 || len(m.Body.DonID) > MessageDonIDMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonID, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil
}

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageID]
	delete(h.savedCallbacks, msg.Body.MessageID)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JSONRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}
