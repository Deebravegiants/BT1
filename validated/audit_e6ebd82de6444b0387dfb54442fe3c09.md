I have enough context to confirm the finding on webhook shop-domain header spoofing.### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then trusts the unauthenticated `shop-domain` header as the tenant identity handed to the host application's handler. Because the HMAC signature never covers the `shop`, `topic`, `webhook-id`, or `api-version` headers, an attacker who can obtain any one validly-signed webhook body/HMAC pair (e.g. from a webhook Shopify legitimately delivers for a shop the attacker controls, such as a free development store) can replay that exact body+HMAC to the app's webhook endpoint while substituting an arbitrary victim `shop-domain` header, causing the application to process the payload under the wrong tenant identity.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body: [1](#0-0) 

```
sig { override.returns(String) }
def to_signable_string
  @raw_body
end
```

`Utils::HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string` and compares it to the `hmac-sha256` header value: [2](#0-1) 

`Registry.process` gates on this HMAC check, then immediately trusts `request.shop` (parsed from the `shopify-shop-domain` / `x-shopify-shop-domain` header) to build the `WebhookMetadata` handed to the application's `WebhookHandler#handle`: [3](#0-2) [4](#0-3) 

The identity binding that should hold is: `shop authenticated by the HMAC == shop delivered to the handler`. In reality, the HMAC binds only the request body's bytes; the `shop` field used downstream (`WebhookMetadata.shop`, consumed by host apps to select per-tenant records/credentials) is attacker-controlled and unauthenticated. Any client that can present a body/HMAC pair that passes `OpenSSL.secure_compare` (trivially satisfiable for a shop the attacker legitimately controls, since Shopify will sign real webhook bodies with the app's secret for that shop) can pair it with a forged `shop-domain` header for a different shop, and `Registry.process` will accept it.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook processing: an attacker with no access to the victim's data or credentials can get the host application to process webhook data (topic/body they control) tagged as belonging to a victim shop. Depending on how the host app uses `WebhookMetadata.shop` (commonly used as the tenant/session lookup key, e.g. to pick the shop's stored access token or update per-shop records), this can lead to cross-tenant data injection/corruption, and in apps that key credential or state lookups off the webhook's reported shop, it can escalate to cross-tenant access. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Medium-High: the attacker needs a genuinely-signed webhook body/HMAC pair, but this is trivially obtainable — install (or already have) the app on any shop the attacker controls (including a free Shopify developer/trial store), trigger any subscribed webhook event, and capture the exact `raw_body` + `x-shopify-hmac-sha256` value Shopify sends. No secret key, no victim credentials, and no privileged access are required; only the ability to send an arbitrary HTTP request to the app's public webhook endpoint with a forged `shop-domain` header.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) headers into the value that is authenticated, or otherwise cryptographically tie the accepted shop to the registered/expected shop for that endpoint before dispatching to `WebhookHandler#handle`. At minimum, document prominently that `WebhookMetadata.shop` is unauthenticated header data and must not be trusted as a tenant identity without independent verification (e.g. cross-checking against the shop's known registered webhook endpoint or session store) — but the safer fix is to include the `shop-domain` header value as part of the signable string validated by `Utils::HmacValidator`, matching Shopify's own recommendation to treat the shop domain in outbound requests as sensitive/trustable only via the signed payload where possible.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com` and subscribe to any webhook topic (e.g. `orders/create`).
2. Trigger the event; Shopify delivers a webhook to the app's endpoint with a body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
3. Capture `B` and `H` (attacker fully controls this shop, so this is trivial — e.g. via a local proxy or a temporary echo endpoint substituted during setup).
4. Replay the request to the target app's real webhook endpoint with the same body `B` and header `x-shopify-hmac-sha256: H`, but set `x-shopify-shop-domain: victim.myshopify.com`.
5. `Utils::HmacValidator.validate` succeeds because it only checks `B` against `H`; `Registry.process` dispatches `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed(B), ...)` to the app's handler, which now processes attacker-controlled data under the victim shop's identity.
