### Title
Silent-failure ERC20 transfers in `IntentGatewayV2.withdraw()` and `SweepDust` permanently freeze escrowed funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` releases escrowed order tokens and dust using a raw low-level `.call()` to `IERC20.transfer`, checking only that the external call itself did not revert (`success`) but never checking (or decoding) the boolean return value. For "no-revert-on-transfer" style ERC20 tokens — tokens that return `false` on a failed transfer instead of reverting — this makes the contract believe the payout succeeded when it did not, while it simultaneously updates internal accounting to mark the order as filled/paid and decrements escrow balances. The result is that the beneficiary never receives their tokens, and the escrow bookkeeping makes recovery impossible, permanently freezing the funds inside the contract.

### Finding Description
In `withdraw()`, which is invoked from `onAccept()` for `RequestKind.RedeemEscrow` / `RequestKind.RefundEscrow` after ISMP proof verification (i.e., reachable by any relayer delivering a validly proven cross-chain message), token payout is performed like this: [1](#0-0) 

```solidity
function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
    address beneficiary = address(uint160(uint256(body.beneficiary)));
    _filled[body.commitment] = beneficiary;
    ...
    if (token == address(0)) {
        (bool sent,) = beneficiary.call{value: amount}("");
        if (!sent) revert InsufficientNativeToken();
    } else {
        (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
        if (!success) revert TransferFailed();
    }

    _orders[body.commitment][token] -= amount;
    ...
}
```

`success` here only reflects whether the low-level call reverted, not whether the ERC20 `transfer()` actually succeeded. A "no-revert-on-transfer" token (e.g. tokens like ZRX that return `false` instead of reverting on failure) will make this call return `success = true` with encoded `false` returndata, which is never decoded or checked. Because the order is already marked `_filled[body.commitment] = beneficiary` before the loop and `_orders[body.commitment][token]` is decremented regardless of actual transfer outcome, the contract's state now reflects that the beneficiary was paid, permanently blocking any retry or recovery of the escrowed tokens.

The identical unchecked-return pattern also exists in the `SweepDust` handler: [2](#0-1) 

and for the fee-token payout at the end of `withdraw()`: [3](#0-2) 

The contract already imports and uses `SafeERC20`/`safeTransferFrom` elsewhere in the same file for escrowing inputs during `placeOrder` (e.g. `IERC20(token).safeTransferFrom(...)` at line 405/459/484), confirming that `SafeERC20.safeTransfer` was the intended pattern but was not used for these payout paths. The sibling non-Tron implementation, `IntentsBase._withdraw`, correctly uses `IERC20(token).safeTransfer(beneficiary, amount)`: [4](#0-3) 

confirming this Tron-specific code path is the divergent, vulnerable one.

### Impact Explanation
Any order or dust-sweep involving a "no-revert-on-transfer" ERC20 token that returns `false` on failure (due to insufficient balance in the contract, blacklisting of the beneficiary, or any other soft-failure condition supported by that token) will cause the `IntentGatewayV2` (Tron) contract to mark the order as filled/refunded and decrement its internal escrow accounting without the beneficiary actually receiving any tokens. This permanently strands the escrowed tokens in the contract with no accounting path to recover them — a direct loss/permanent freezing of user/solver funds reachable purely by an unprivileged relayer delivering a proven `RedeemEscrow`/`RefundEscrow`/`SweepDust` message.

### Likelihood Explanation
This requires one of the escrowed input tokens (configured by governance/order creators, not restricted to a hardened allowlist in this code) to be a non-reverting-on-failure ERC20, or for a `transfer` call to a beneficiary to otherwise return `false` without reverting (which is a known, documented ERC20 quirk affecting real deployed tokens such as ZRX). Given IntentGatewayV2 is designed to be a generic multi-token intents/bridging escrow, the likelihood of at least one supported token exhibiting this behavior is realistic, and the trigger path (relayed proof for withdrawal) is fully permissionless from the caller's perspective once a valid proof exists.

### Recommendation
Use `SafeERC20.safeTransfer` (already imported via `using SafeERC20 for IERC20;`) instead of raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` in `withdraw()` (both the token loop and the fee-token payout) and in the `SweepDust` handler in `evm/tron/contracts/apps/IntentGatewayV2.sol`. This ensures both call failures and false-return failures cause a proper revert, preventing the escrow accounting from being finalized when a payout did not actually occur.

### Proof of Concept
1. Governance/order flow configures or a user creates an order whose input/output token is a no-revert-on-transfer ERC20 (returns `false` on failed transfer instead of reverting), and tokens are escrowed via `placeOrder`.
2. A relayer delivers a proven ISMP `RedeemEscrow` (or `RefundEscrow`) request targeting this order, invoking `onAccept` → `withdraw`.
3. The beneficiary address is such that the token's `transfer()` call returns `false` (e.g., beneficiary is blacklisted by the token, or contract balance edge case specific to that token's internal logic).
4. `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` returns `(success = true, data = abi.encode(false))`; the code only checks `success`, so it proceeds.
5. `_filled[body.commitment] = beneficiary` was already set and `_orders[body.commitment][token] -= amount` executes, permanently marking the order as paid despite the beneficiary receiving zero tokens — the escrowed amount is now unrecoverable.
