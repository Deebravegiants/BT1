### Title
Rounding of `calc_take_pnl` silently resets the PnL baseline (`target_orders.calc_pnl_x/y`) even when the accrued reward is zeroed out — permanent loss of protocol PnL - (`program/src/processor.rs`)

### Summary
`Processor::calc_take_pnl` computes the accrued PnL (`delta_x`, `delta_y`) that must be reserved via `need_take_pnl_pc/coin`, and every caller (`process_deposit`, `process_withdraw`, `process_withdrawpnl`, and their v2 variants) unconditionally re-bases `target_orders.calc_pnl_x` / `target_orders.calc_pnl_y` to the *current* normalized reserves (`x1`, `y1`) minus whatever `delta_x`/`delta_y` was returned. When the true PnL is small enough that decimal restoration rounds `pc_pnl_amount` or `coin_pnl_amount` to `0`, `calc_take_pnl` deliberately zeroes both `delta_x` and `delta_y` — but the caller still re-bases the target-orders baseline to the new price/reserves. The tiny-but-real PnL accrued since the last baseline is discarded forever instead of being carried forward.

### Finding Description
`calc_take_pnl` in `program/src/processor.rs` computes the raw (1e18-ish normalized) difference `diff_x`/`diff_y` between the pool's last recorded invariant (`target.calc_pnl_x`/`calc_pnl_y`) and the current invariant, then restores those diffs to native decimals and checks if the result is nonzero: [1](#0-0) 

If `pc_pnl_amount != 0 && coin_pnl_amount != 0`, the reserved PnL (`need_take_pnl_pc/coin`) is updated and `delta_x`/`delta_y` (the raw, un-rounded normalized diffs) are returned. Otherwise, the `else` branch forces `delta_x = 0; delta_y = 0;`: [2](#0-1) 

The bug is in every caller of this function. In `process_deposit`, the new baseline is computed as `x1 + deduct_pc_amount(normalized) - delta_x` regardless of whether the rounding branch was hit: [3](#0-2) 

The same unconditional re-basing pattern occurs in `process_withdrawpnl`: [4](#0-3) 

Since `delta_x`/`delta_y` are `0` whenever the rounded PnL amount is `0` (even though the true, un-rounded `diff_x`/`diff_y` computed at line 213-214 may be nonzero), the baseline `calc_pnl_x`/`calc_pnl_y` gets snapped to the *current* invariant state (`x1`, `y1`, plus deposit/withdraw deltas) without ever crediting `need_take_pnl_pc`/`need_take_pnl_coin` with the discarded remainder. Any user who calls `deposit`/`withdraw`/`swap`-adjacent instructions frequently enough to keep each individual PnL delta below the rounding threshold can cause the protocol to permanently lose the accumulated trading-fee PnL that should have accrued to `need_take_pnl_pc`/`need_take_pnl_coin` (and ultimately to the `pnl_owner`).

This mirrors the reported Derby `Vault.storePriceAndRewards` bug class exactly: a price/exchange-rate difference is rounded to zero due to low-decimal tokens (e.g., 6-decimal USDC-like `pc` or `coin` mints) and low decimals, but the "last price" baseline (`lastPrices[_protocolId]` there, `target_orders.calc_pnl_x/y` here) is updated anyway, causing the reward for that period to be permanently lost rather than carried forward to the next check.

### Impact Explanation
Each time PnL rounds to zero, the true (unrecorded) PnL — while small per-call — is permanently forfeited because the baseline moves forward. Since `calc_take_pnl` runs on essentially every state-mutating instruction (deposit, withdraw, withdrawpnl, and the base-in/base-out swap paths route through the same reserve calculations feeding this baseline), an attacker or normal high-frequency LP activity can repeatedly "reset" the baseline before enough PnL accrues to clear the rounding threshold, resulting in the protocol's/pnl_owner's PnL entitlement (funds ultimately withdrawn via `process_withdrawpnl`) being silently and irrecoverably reduced over time. This is an unbacked accounting drift and constitutes an insolvent pool PnL accounting issue.

### Likelihood Explanation
Likelihood is best characterized as low/medium in practice — it requires either naturally low-decimal `pc`/`coin` mints combined with frequent small deposit/withdraw activity, or an attacker deliberately submitting many small deposit/withdraw transactions to keep the per-call PnL delta below the native-decimal rounding threshold. Unlike the swap path (which uses `checked_ceil_div` for fees), `calc_take_pnl`'s reward computation uses plain `checked_div` (floor), so any attacker can trivially construct amounts that floor to zero. Reachability requires only ordinary unprivileged `deposit`/`withdraw` calls with attacker-chosen amounts, no special permissions.

### Recommendation
Do not update `target_orders.calc_pnl_x`/`calc_pnl_y` to the post-rounding baseline when `calc_take_pnl` returns `delta_x == 0 && delta_y == 0` due to rounding. Instead, either (a) keep the previous `calc_pnl_x`/`calc_pnl_y` unchanged so the un-rounded difference accumulates across calls until it clears the rounding threshold, or (b) accumulate the truncated remainder in a separate dust accumulator that is added back into the next `calc_take_pnl` computation, so no PnL is silently lost.

### Proof of Concept
1. Initialize a pool where the accrued invariant growth per LP action is small enough that, after `Calculator::restore_decimal` into native `pc_decimals`/`coin_decimals`, `pc_pnl_amount` or `coin_pnl_amount` computed at [5](#0-4)  equals `0` (e.g., low-decimal mints, or PnL numerator/denominator fee fraction shrinking a genuine nonzero `diff_x`/`diff_y` below one native unit).
2. Call `deposit` (or `withdraw`) repeatedly with amounts chosen so each call's incremental invariant growth stays under this rounding threshold.
3. Observe that `calc_take_pnl`'s `else` branch fires each time (`delta_x = delta_y = 0`) at [6](#0-5) , yet `process_deposit` still re-bases `target_orders.calc_pnl_x`/`calc_pnl_y` to the new `x1`/`y1` (plus deposit deltas) at [3](#0-2) .
4. Confirm `amm.state_data.need_take_pnl_pc`/`need_take_pnl_coin` never increase despite genuine trading-fee-driven invariant growth, and that this growth is not recoverable in any subsequent call because the baseline has already moved past it — resulting in the `pnl_owner`'s eventual `withdrawpnl` amount permanently understating the true accrued PnL.
