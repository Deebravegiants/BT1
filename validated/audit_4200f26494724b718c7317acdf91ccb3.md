I found a concrete binding break: `exchange_token` in `TokenExchange` sends the app's `client_secret` to a host built directly from the JWT's `dest` claim, without applying the same shop-domain sanitization used everywhere else in the OAuth flows.

### Title
Token Exchange sends `client_secret` to an unsanitized shop host derived from JWT `dest` claim - (File: `lib/shopify_api/auth/token_exchange.rb`)

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` builds the outbound request host from `jwt_payload.shop` (the JWT `dest` claim) and passes it straight into `Session.new(shop: dest_shop)`, which `Clients::HttpClient` uses to construct the request URL that carries the app's `client_id`/`client_secret` in the body. Every other credential-bearing flow in this gem (`ClientCredentials.client_credentials`, `TokenExchange.migrate_to_expiring_token`) runs the shop value through `Utils::ShopValidator.sanitize!` before using it to build the request host, but `exchange_token` does not.

### Finding Description
In `exchange_token`: [1](#0-0) 
the shop used to build the outbound host (`dest_shop`) comes only from `JwtPayload#shop`, which is simply `@dest.gsub("https://", "")`: [2](#0-1) 
`JwtPayload` verifies the JWT signature and the `aud` claim against `Context.api_key`, but it performs no validation that `dest`/`iss` is actually a `*.myshopify.com` (or allowed dev/spin) domain: [3](#0-2) 

Compare this to the two sibling credential-granting flows in the same module and in `ClientCredentials`, which explicitly sanitize the shop before it is used to build the request host: [4](#0-3) [5](#0-4) 

The equality that should hold is: *the host that is authenticated as belonging to a legitimate Shopify shop* == *the host that receives the request body containing `client_id`/`client_secret`*. Because `exchange_token` skips `ShopValidator.sanitize!`, an app that is embedded and whose front end forwards an attacker-supplied or attacker-influenced session token (e.g., a token signed by the app's own `api_secret_key` for a value under the app's control, or a `dest` claim that is not confined to the shop's canonical domain) determines the destination host, while the sibling functions verify the shop format before ever building the URL.

Unlike the oracle report's `price()`/`lotPrice()` mismatch — where a function silently returning a permissive fallback (`0, FIX_MAX`) instead of a well-bounded value caused an unintended amount to be actioned — here the unintended consequence is that a permissive, unvalidated field (`dest`) is trusted to select the network destination for a secret-bearing request, instead of the validated field used everywhere else in the same module.

### Impact Explanation
If `dest_shop` can be influenced to be a non-`myshopify.com` host, `Clients::HttpClient` (base_path `/admin/oauth`) will issue a POST containing `client_id` and `client_secret` to that host — SSRF carrying the app's credentials, matching the "High" impact class (SSRF with the app's credentials / credential leakage). This requires the app to accept a session token whose `dest` is not independently confirmed to be the expected merchant's canonical domain before calling `exchange_token`.

### Likelihood Explanation
Likelihood is moderate to low: `JwtPayload` does correctly verify the signature and `aud`, so an attacker without the app's `api_secret_key` cannot forge an arbitrary `dest`. The realistic exploitation path depends on how the host application obtains and forwards the session token to `exchange_token` (i.e., whether it enforces shop-domain shape before trusting the token's `dest`). I could not fully verify from this index whether Shopify's own session-token issuance guarantees `dest` is always `*.myshopify.com`-shaped, or whether the gem is relied upon as the last line of defense — the inconsistency with `ShopValidator.sanitize!` usage elsewhere in the same file is the strongest concrete signal.

### Recommendation
Apply `Utils::ShopValidator.sanitize!(dest_shop)` to the value extracted from `jwt_payload.shop` in `exchange_token` before constructing `Session.new(shop: dest_shop)`, mirroring the sanitization already performed in `migrate_to_expiring_token` and `ClientCredentials.client_credentials`.

### Proof of Concept
1. Construct or obtain a session token whose `dest` claim is not a canonical `*.myshopify.com` host but is otherwise validly signed for the app's `aud`.
2. Call `ShopifyAPI::Auth::TokenExchange.exchange_token(session_token: token, requested_token_type: ...)`.
3. Observe that `Clients::HttpClient` is instantiated with `session: Session.new(shop: dest_shop)` and issues the `/admin/oauth/access_token` POST (containing `client_id`/`client_secret`) to a host derived directly from the unsanitized `dest_shop`, unlike `migrate_to_expiring_token`/`client_credentials`, which reject malformed shop values via `ShopValidator.sanitize!` before reaching this point.
