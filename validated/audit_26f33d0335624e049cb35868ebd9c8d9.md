### Title
Unfreed shared-memory allocation on error path in `ExternalConsumeWorker::check_batch` leaks the external-scheduler allocator - (File: core/src/banking_stage/consume_worker.rs)

### Summary
`check_batch` allocates a shared-memory response region up front via `allocate_check_response_region`, then performs further fallible work (`check_resolve_pubkeys`) using the `?` operator before that region is ever written into a message and sent back to the scheduler. If the fallible call returns `Err`, the function returns early and the previously-allocated `responses_ptr`/`response_region` allocation is never freed and never transmitted, permanently leaking that slot in the shared `rts_alloc::Allocator` arena.

### Finding Description
In `check_batch`, the sequence is:
1. Allocate a response region sized for the batch: `allocate_check_response_region(&self.allocator, ...)` at [1](#0-0) .
2. Populate initial responses and possibly perform fee-payer / pubkey / status checks.
3. If `LOAD_ADDRESS_LOOKUP_TABLES` is set, call `self.check_resolve_pubkeys(...)?` which can return an `Err(ExternalConsumeWorkerError)` and cause an early `return` from `check_batch`: [2](#0-1) .
4. Only after that point is the `responses` region wrapped into a `WorkerToPackMessage` and sent to the scheduler, at which point ownership (and eventual `free`) transfers to the scheduler side (`handle_worker_response` explicitly frees `rep.responses` via `self.allocator.free(...)`, see [3](#0-2) ).

If `check_resolve_pubkeys` errors out (e.g. `ExternalConsumeWorkerError::SenderDisconnected` from an internal `try_write`, per the pattern used elsewhere such as `send_execution_response` at [4](#0-3) ), `check_batch` bails out before constructing/sending the `WorkerToPackMessage`. The `responses_ptr` allocation made at line 497-501 is dropped as a raw `NonNull<CheckResponse>`/`TransactionResponseRegion` value — these types carry no `Drop` impl that calls `allocator.free`, unlike the explicit `unsafe { allocator.free(...) }` calls used everywhere else the code intentionally releases these allocations (e.g. `CheckResponsesPtr::free` at [5](#0-4) , or the `return_not_included_with_reason` comment explicitly acknowledging skipped frees are only acceptable on unrecoverable-error paths at [6](#0-5) ). No such acknowledgment or free is present in `check_batch`'s early-return path.

This is structurally analogous to the SEDA bug: a resource is allocated unconditionally at the top of a hot-path function, and a subsequent fallible branch can exit the function before the resource is either transmitted (transferring ownership) or freed, so each occurrence permanently consumes shared-allocator capacity.

### Impact Explanation
The external scheduler's per-worker `Allocator` is a fixed-size, bump/free-list shared-memory arena (`allocator_size` set at session logon, e.g. 64 MiB in test setups: [7](#0-6) ). Each leaked `check_batch` response allocation permanently reduces the usable arena. Because `check_batch` executes on every batch of transactions routed through the external-scheduler bindings path, repeated triggering of the error branch degrades the allocator over time, eventually causing allocation failures (`ExternalConsumeWorkerError::AllocationFailure`) for legitimate transaction batches, which would stall consumption of transactions and could contribute to a liveness/perf degradation of the validator's banking stage — not unlike the SEDA node's eventual crash from unbounded native-heap growth. This is a validator-internal resource-exhaustion bug rather than a fund-loss or consensus-divergence bug.

### Likelihood Explanation
Triggering the leak requires the external-scheduler consume-worker path to be active and for `check_resolve_pubkeys` to return an error after the response region has already been allocated (e.g., the scheduler-side channel becoming disconnected/full during ALT resolution). This is an internal/operational condition rather than something an unprivileged network user can directly force per-transaction, and I could not fully confirm the exact conditions under which `check_resolve_pubkeys` returns `Err` (its body was not retrieved), so the frequency of the failure branch is uncertain. The external-scheduler bindings machinery (`agave_scheduler_bindings`, `rts_alloc`) also overlaps with `scheduler-bindings`, which is called out as out of scope in SECURITY.md for external processes; however, `check_batch` itself lives in `core/src/banking_stage/consume_worker.rs`, in-tree validator code, so the analog is only partially certain to be in-scope.

### Recommendation
Ensure the response-region allocation in `check_batch` is either always sent (transferring ownership) or explicitly freed on every early-return path — e.g., wrap the allocation in an RAII guard that frees it via `allocator.free` unless explicitly "disarmed" once the message is queued, mirroring the explicit `.free(&self.allocator)` calls used elsewhere in this module and in `responses_region.rs`.

### Proof of Concept
Not independently reproducible without exercising the external-scheduler bridge and forcing `check_resolve_pubkeys` to return an `Err` after the allocation at [8](#0-7) ; I was unable to retrieve the full body of `check_resolve_pubkeys` in this session to confirm all of its error conditions, so this should be validated against the actual source before treating it as confirmed exploitable.
