## Finding

The webhook signature verification in `ShopifyAPI::Webhooks::Request` only covers the raw HTTP body, not the Shopify identity headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) that the registry later treats as trusted. This lets a party who can obtain one valid `(body, hmac)` pair for an app relabel it as belonging to a different shop. [1](#0-0) 

`Registry.process` verifies only `request.to_signable_string` (`@raw_body`) against the HMAC header, then unconditionally trusts `request.shop` and `request.topic` — both parsed straight from unauthenticated headers — to route and label the payload: [2](#0-1) 

### Title
Webhook `shop`/`topic` identity headers are not covered by the HMAC, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Utils::HmacValidator.validate` binds only the raw request body to the HMAC signature via `Request#to_signable_string`, which returns `@raw_body` and nothing else. The `shop`, `topic`, `webhook_id`, and `api_version` values consumed by `Registry.process` and forwarded into `WebhookMetadata` (and therefore into the host app's per-tenant handler) come from HTTP headers (`shopify-shop-domain`, `shopify-topic`, etc.) that are entirely outside the signed content.

### Finding Description
The identity binding the library is supposed to enforce is: `hmac_valid(raw_body) == true` implies `shop-domain header is authentic for this body`. In reality the code only proves `hmac_valid(raw_body) == true`; the `shop-domain`/`topic` headers are unauthenticated and can be set to any value independent of the signed body, because `client_secret`/`api_secret_key` is shared across every shop that installs a given app (it is not shop-specific). Any party who legitimately installs the app on a shop they control (a trivial, unprivileged action — e.g., a free Shopify development store) will receive real webhooks correctly signed with that same shared `api_secret_key`. They can capture one such `(raw_body, x-shopify-hmac-sha256)` pair and replay it to the app's webhook endpoint with an arbitrary `shopify-shop-domain` header. `HmacValidator.validate` re-verifies successfully (it never looks at the header), `Registry.process` accepts it, and the app's handler receives a `WebhookMetadata` claiming the event happened on the victim shop, when the body actually originated from the attacker's own shop.

### Impact Explanation
This breaks the tenant boundary the gem is expected to preserve for webhook consumers: an attacker who is merely a low-privilege merchant with the app installed on their own store can inject webhook payloads that the host application attributes to any other shop that installed the app. Depending on how the host application keys off `WebhookMetadata#shop` (most `shopify_app`/customer integrations use it to select the tenant's session/DB record before processing the body), this enables cross-tenant data corruption or triggering privileged per-shop side effects (e.g., `shop/redact`, `app/uninstalled`, order-processing automation) against a victim tenant without ever compromising that tenant's credentials.

### Likelihood Explanation
Reachable by any unprivileged internet user who can install the target app on a shop they control (a normal, permitted action for any Shopify app) and can send arbitrary HTTP requests to the app's public webhook endpoint — no access token, `client_secret`, TLS interception, or social engineering is required. The gem's own API (`Webhooks::Request.new` / `Registry.process`) does not require or provide any additional header authentication, so the gap is in-scope library behavior rather than host-app misuse.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signable content used for HMAC verification (or otherwise cryptographically bind them to the payload), rather than deriving `Request#to_signable_string` from `@raw_body` alone. At minimum, document and enforce that `request.shop`/`request.topic` must only be trusted after being cross-checked against an out-of-band record (e.g., confirming the shop actually has an active session/registration) before being used to select a tenant context.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (free/dev store), a normal unprivileged action.
2. Shopify sends the attacker's store a legitimately signed webhook, e.g. `orders/create`, with body `B` and header `X-Shopify-Hmac-Sha256: H = HMAC-SHA256(secret, B)`.
3. Attacker captures `B` and `H`, then sends a POST to the app's webhook endpoint with:
   - Body: `B` (unchanged)
   - Header `x-shopify-hmac-sha256: H` (unchanged, still valid since `to_signable_string` only covers `B`)
   - Header `x-shopify-shop-domain: victim-shop.myshopify.com` (forged)
   - Header `x-shopify-topic: <same or different topic>` (forged, if desired)
4. `ShopifyAPI::Utils::HmacValidator.validate(request)` recomputes `HMAC-SHA256(secret, B)`, matches `H`, and returns `true`.
5. `Registry.process` proceeds and invokes the topic handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)`, so the host application processes attacker-controlled data under the victim shop's identity.
