### Title
Webhook `topic` header is unauthenticated yet used to select the handler in `Registry.process` - ([File: lib/shopify_api/webhooks/registry.rb])

### Summary
`Registry.process` validates only the raw request body's HMAC and then uses the attacker-controlled `topic` (and `shop`) headers—neither of which are covered by that HMAC—to select and invoke a webhook handler. Because the signable string is the body alone, any body an attacker can get Shopify to sign for one topic can be replayed with a different `x-shopify-topic`/`shopify-topic` header to trigger an entirely different, unrelated handler (e.g. `customers/data_request`) with attacker-chosen body content.

### Finding Description
The broken binding: `Utils::HmacValidator.validate(request)` proves `HMAC(api_secret_key, request.to_signable_string) == received_hmac`, where `to_signable_string` returns `@raw_body` only [1](#0-0) . It does **not** prove `request.topic == <topic Shopify actually sent this body for>`. Yet `Registry.process` uses that same unauthenticated `request.topic` both to look up the handler and to build the metadata passed to it:

```
handler = @registry[request.topic]&.handler
...
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))
``` [2](#0-1) 

`Request#topic` and `Request#shop` are parsed directly from HTTP headers with no cross-check against the body or against each other [3](#0-2) . `HmacValidator.validate_signature` only compares `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)` — the topic and shop headers never enter the signature computation [4](#0-3) .

`api_secret_key` is the app's single shared client secret, not shop-specific, so any webhook body Shopify signs for the attacker's own (attacker-installed) shop is signed with the same secret used for every other merchant's webhooks. An attacker can therefore: install the target app on their own store, trigger any topic (e.g. `app/uninstalled`) to receive a validly HMAC'd body at their own endpoint, then POST that exact `raw_body` to the host app's real webhook-processing endpoint with the `x-shopify-topic` header changed to a topic they want to trigger (e.g. `customers/data_request`) and, if desired, the `x-shopify-shop-domain` header changed to a different value. `HmacValidator.validate` still returns `true` (body+secret unchanged), so `Registry.process` looks up `@registry['customers/data_request']` and invokes that handler with the attacker's chosen body parsed as if it were a legitimate `customers/data_request` payload, and with an attacker-controlled `shop` value in the metadata.

No code in this repo cross-validates `request.topic`/`request.shop` against the body or binds them into the signable string; `ShopValidator.sanitize!` is not invoked anywhere in this path, and there is no session/tenant check in `Registry.process`. This confirms the divergence is real and unmitigated.

### Impact Explanation
Any handler registered via `Registry.add_registration` can be invoked with attacker-fabricated `topic`/`shop`/`body` combinations, provided the attacker can obtain one validly signed body for *any* topic (trivial: install the app on their own store and receive any real webhook). This is a genuine authentication-bypass: an unauthenticated value (header-derived topic/shop) is trusted as if it were authenticated by the HMAC. Concretely this lets an attacker force execution of sensitive compliance handlers (`customers/data_request`, `customers/redact`, `shop/redact`) or any other registered handler with fabricated JSON content and a spoofed `shop` value, potentially causing the host app to act on/against a shop it never actually received that event for. This is repeatable against any app using this library, for any handler the developer registers, and matches the Critical "authentication bypass (forged webhook ... accepted)" category.

### Likelihood Explanation
Preconditions are low-cost and fully attacker-controlled: register/own a development shop, install the target app (standard, unprivileged flow), and receive at least one legitimately signed webhook for any topic to that shop's endpoint. No secrets, tokens, or elevated access are required. The host app only needs to use `Registry.process`/`Request` as documented [5](#0-4) , which is the intended usage pattern. This makes the attack highly feasible and repeatable at will.

### Recommendation
Bind the topic (and ideally shop) into the authenticated context instead of trusting bare headers for handler dispatch:
- Include the `x-shopify-topic` (and/or `x-shopify-shop-domain`) header value in the signable string used for HMAC verification, or
- After verifying the body, cross-check that the resource type/schema embedded in the parsed body is consistent with the declared topic before handler lookup, and/or
- Verify `request.shop` against the session/shop the app expects for that webhook endpoint before dispatch.
At minimum, document and enforce that `topic`/`shop` headers must not be trusted independent of a stronger binding.

### Proof of Concept
```ruby
# test/webhooks/registry_test.rb (new test)
def test_topic_header_swap_invokes_wrong_handler
  body = "{}"
  hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, body)
  valid_hmac_header = Base64.encode64(hmac)

  uninstall_handler = TestHelpers::FakeWebhookHandler.new(lambda { |data| flunk("should not be called") })
  data_request_handler = mock
  data_request_handler.expects(:handle).with do |args|
    args[:data].topic == "customers/data_request" && args[:data].body == {}
  end

  ShopifyAPI::Webhooks::Registry.clear
  ShopifyAPI::Webhooks::Registry.add_registration(
    topic: "app/uninstalled", path: "path", delivery_method: :http, handler: uninstall_handler,
  )
  ShopifyAPI::Webhooks::Registry.add_registration(
    topic: "customers/data_request", path: "path", delivery_method: :http, handler: data_request_handler,
  )

  # Attacker's own validly-signed body for app/uninstalled, replayed with topic header swapped
  spoofed_headers = {
    "x-shopify-topic" => "customers/data_request", # attacker-changed
    "x-shopify-hmac-sha256" => valid_hmac_header,   # still valid because HMAC only covers body
    "x-shopify-shop-domain" => "shop.myshopify.com",
  }

  ShopifyAPI::Webhooks::Registry.process(
    ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: spoofed_headers),
  )
  # data_request_handler.handle is invoked despite the body never actually being sent by
  # Shopify as a customers/data_request webhook.
end
```
This demonstrates `HmacValidator.validate` returning `true` while `request.topic` (attacker-controlled) selects and invokes a handler unrelated to what Shopify actually signed.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

```markdown
To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
