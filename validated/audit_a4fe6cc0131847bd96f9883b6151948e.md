### Title
`PoaBridge::describeWithdrawal()` misreports status/txHash for batched same-asset withdrawals due to assetId-only matching - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal()` relies on `findMatchingWithdrawal()`, which matches a withdrawal record from the POA bridge API purely by `assetId` (via `nep141:${w.data.near_token_id}`), ignoring the `index` field that is supposed to disambiguate multiple withdrawals within the same NEAR transaction.

### Finding Description
`createWithdrawalIdentifiers()` in `packages/intents-sdk/src/core/withdrawal-watcher.ts` assigns each withdrawal in a batch an `index` per bridge route [1](#0-0) , and `WithdrawalIdentifier` explicitly documents `index` as the "per-bridge withdrawal sequence number" [2](#0-1) .

However `PoaBridge.describeWithdrawal()` never uses `args.index`; it calls `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`, which does `withdrawals.find((w) => \`nep141:${w.data.near_token_id}\` === assetId)` — i.e., it returns the *first* API record whose asset matches, regardless of which of the (possibly several) same-asset withdrawals in the transaction it actually corresponds to [3](#0-2) [4](#0-3) .

The code comment itself acknowledges the limitation: "Currently only matches by assetId. This means multiple withdrawals of the same token in a single transaction are not supported" [5](#0-4) .

This breaks the equality that `describeWithdrawal(wid)` must report the on-chain outcome of the specific withdrawal identified by `wid.index`. If a user (or an integrator building a batch) creates two or more withdrawals of the same asset (e.g., two BTC withdrawals to different destination addresses, or split amounts) inside a single NEAR intents transaction, `PoaBridge.createWithdrawalIntents()` is invoked once per withdrawal param and produces one intent primitive per call (each with its own `amount`/`destinationAddress`) [6](#0-5) . `watchWithdrawal()` then polls `describeWithdrawal` for each identifier separately [7](#0-6) , but because `findMatchingWithdrawal` ignores `index`, both identifiers (index 0 and index 1) resolve to the same underlying API record — reporting the same `status`/`transfer_tx_hash` for both, even though they represent two distinct on-chain transfers to two different destinations/amounts.

### Impact Explanation
This is a status/hash misreport: `watchWithdrawal` for withdrawal #2 would report "completed" with the tx hash that actually belongs to withdrawal #1 (or vice versa), before or without waiting for withdrawal #2 to actually settle. An integrator relying on the SDK's per-withdrawal completion status to credit/refund a specific leg of a batch could mark the second withdrawal as completed using the first withdrawal's transaction hash — a "status or hash misreport" that can cause an integrator to credit or settle a withdrawal that has not actually completed (or attribute the wrong destination's tx hash), a High-severity outcome per the report's impact taxonomy ("a status or hash misreport making an integrator credit or refund twice").

### Likelihood Explanation
Likelihood is constrained by whether the SDK/consuming applications actually construct batches containing two-plus withdrawals of the *same* asset in one NEAR transaction. The SDK's public API (`estimateWithdrawalFee`, `createWithdrawalIntents`) does support arrays of `WithdrawalParams`, and `createWithdrawalIdentifiers` explicitly assigns sequential indexes per bridge route to handle exactly this multi-withdrawal-per-tx case, showing this is an intended, reachable feature path, not a hypothetical one. The bug requires no malicious actor — any legitimate batch withdrawal request with two same-asset legs (e.g., splitting a BTC withdrawal to two different recipients) triggers it deterministically once the POA bridge API returns multiple matching records or even a single record shared incorrectly across two lookups.

### Recommendation
Update `findMatchingWithdrawal` (and `describeWithdrawal`) to disambiguate using more than `assetId` — e.g., match by `assetId` + `destinationAddress` + `amount`, or track the count of records already consumed per assetId and select the Nth unclaimed match corresponding to `args.index`, consistent with the ordering guarantee promised elsewhere in the code (see the ordering note for token amounts in the docstring). At minimum, until the POA API supports index-based lookup, the SDK should refuse duplicate same-asset withdrawals within a single batch (throw explicitly) rather than silently misreport status for one of them.

### Proof of Concept
1. Build a NEAR intents transaction with two POA-bridge withdrawal intents for the same `assetId` (e.g., `nep141:btc.omft.near`) but different `destinationAddress`/`amount`, submitted via a single `createWithdrawalIntents({ withdrawalParams: [w1, w2] })`-style batch (both routed to `PoaBridge`).
2. `createWithdrawalIdentifiers` assigns `index: 0` to `w1` and `index: 1` to `w2` [8](#0-7) .
3. Call `watchWithdrawal` for both identifiers. Both calls route to `PoaBridge.describeWithdrawal`, which calls `getWithdrawalStatusWithRetry` (keyed only by `tx.hash`, same for both) then `findMatchingWithdrawal(response.withdrawals, assetId)` — same `assetId` for both, so both calls return the identical array `.find()` result [3](#0-2) .
4. Once the POA API returns the first (or only currently indexed) matching withdrawal as `COMPLETED` with `transfer_tx_hash = X`, both `describeWithdrawal({index:0,...})` and `describeWithdrawal({index:1,...})` return `{ status: "completed", txHash: X }` — even though withdrawal #2's actual on-chain transfer may still be pending or have a different hash entirely.

export async function watchWithdrawal(args: {
	bridge: Bridge;
	wid: WithdrawalIdentifier;
	signal?: AbortSignal;
	logger?: ILogger;
}): Promise<TxInfo | TxNoInfo> {
	const stats = getWithdrawalStatsForChain({
		chain: args.wid.landingChain,
		bridgeRoute: args.bridge.route,
	});
	let consecutiveErrors = 0;

	try {
		return await poll(
			async () => {
				try {
					const status = await args.bridge.describeWithdrawal({
						...args.wid,
						logger: args.logger,
					});

					consecutiveErrors = 0;

					if (status.status === "completed") {
						return status.txHash != null
							? { hash: status.txHash }
							: { hash: null };
					}

					if (status.status === "failed") {
						throw new WithdrawalFailedError(status.reason);
					}

					return POLL_PENDING;
				} catch (err: unknown) {
					if (err instanceof WithdrawalFailedError) {
						throw err;
					}

					consecutiveErrors++;
					if (consecutiveErrors >= MAX_CONSECUTIVE_ERRORS) {
						throw new WithdrawalWatchError(err);
					}

					args.logger?.warn(
						`Transient error (${consecutiveErrors}/${MAX_CONSECUTIVE_ERRORS}): ${err}`,
					);
					return POLL_PENDING;
				}
			},
			{ stats, signal: args.signal },
		);
	} catch (err: unknown) {
		if (err instanceof PollTimeoutError) {
			throw new WithdrawalWatchError(err);
		}
		throw err;
	}
}

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};

type WithdrawalStatusResponse = Awaited<
	ReturnType<typeof poaBridge.httpClient.getWithdrawalStatus>
>;

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
