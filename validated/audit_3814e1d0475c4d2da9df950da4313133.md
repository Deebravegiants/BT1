### Title
Unfunded repay/recapitalize "overpayment refund" pays attacker-declared amounts out of pool custody - (File: contracts/pool/src/ops/repay.rs)

### Summary
The NanaZip bug class — trusting a header-declared size larger than the data actually delivered — maps directly onto the pool's repay and recapitalize legs. Both compute an "excess" purely from the **declared** `amount` argument and pay it back to the caller via `transfer_out`, without ever measuring how many tokens were actually transferred in. A comment assumes "the controller transfers the repay amount into the pool before this call", but the pool itself performs no balance-delta check, and the pool test suite demonstrates that a freshly generated, unprivileged address can call `repay` directly with zero tokens sent and receive the entire declared amount out of real custody.

### Finding Description
`ops::repay::apply` resolves the repay into `overpayment` via `cache.resolve_repay(amount, position)` — which is `resolve_repay` in `common/src/rates/scaling.rs` returning `amount - current_debt_ceil` when `amount` covers the (ceiling-rounded) debt — and then unconditionally sends `outcome.overpayment` to `payer` with `cache.transfer_out`. `credit_cash` only books `net_repay`; the refund leg is never reconciled against a measured inbound transfer.

The same shape exists in `ops::recapitalize::accounting`: `applied = min(amount, backing_shortfall)`, `refund = amount - applied`, then `apply` does `cache.transfer_out(&payer, outcome.refund)`. When a market has no shortfall, `applied == 0` and the entire declared `amount` is refunded from custody.

The in-repo test `test_unfunded_repay_overpayment_refund_also_pays_out_of_custody` in `contracts/pool/tests/flows.rs` demonstrates this end to end: a brand-new `payer` calls `pool.repay` with `amount = custody_before` on a market with no debt, gets `actual_amount == 0` credited, and the pool's token balance drops by the full declared amount while the book is untouched.

### Impact Explanation
Theft of user funds. An attacker picks a market with zero (or small) outstanding debt/shortfall, calls `repay` (or `recapitalize`) on the pool directly with `amount` equal to the pool's token balance, transfers nothing in, and the "overpayment refund" wires the full declared sum out of supplier custody. This can be repeated per market/asset to drain every pool.

### Likelihood Explanation
High if reachable: the call requires no capital (nothing is transferred in), no special role is evidenced in the demonstrated call path, and the pool-level entrypoint is directly invoked in the repo's own test. The main uncertainty is whether the deployed pool enforces a controller-only caller check outside `apply`; the repo's test invokes the pool client with an arbitrary generated `Address` and succeeds, indicating no such gate exists in this code.

### Recommendation
- Gate `repay`, `recapitalize` (and any other leg that refunds a declared excess) to the controller contract, or
- measure the inbound transfer (`balance_after - balance_before`) and cap `overpayment`/`refund` at `received - applied`, never at `declared - applied`.
- Add `require_reserves`/custody conservation checks before any `transfer_out` of a refund.

### Proof of Concept
```rust
// Mirrors contracts/pool/tests/flows.rs::test_unfunded_repay_overpayment_refund_also_pays_out_of_custody
let token = token::Client::new(&env, &asset);
let attacker = Address::generate(&env);           // no funds, no role
let custody = token.balance(&pool);               // e.g. market with no debt

// No transfer-in. Declared amount = entire custody.
let mutations = pool_client.repay(&attacker, &ract(0, custody));
assert_eq!(mutations.get_unchecked(0).actual_amount, 0); // no debt retired
assert_eq!(token.balance(&attacker), custody);           // refund drained custody
assert_eq!(token.balance(&pool), 0);
```

Relevant code: `contracts/pool/src/ops/repay.rs` `apply`/`accounting` (lines 25–67), `contracts/pool/src/ops/recapitalize.rs` `apply`/`accounting` (lines 26–67), `common/src/rates/scaling.rs` `resolve_repay` (lines 171–191), test `contracts/pool/tests/flows.rs` (lines 3578–3611).

Note: if deployment wraps the pool behind a caller-auth check not visible in `apply`, the direct-drain path may be unreachable; in that case the same defect still exists latent for any future caller that does not pre-fund exactly the applied amount.
