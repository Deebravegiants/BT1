### Title
Permissionless `CallDispatcher.dispatch()` lets anyone drain funds it momentarily or residually holds - ([File: evm/src/utils/CallDispatcher.sol])

### Summary
`CallDispatcher.dispatch()` is a fully unauthenticated, `external` entry point with no caller restriction whatsoever. It is meant to be invoked only as one step inside a larger, trusted orchestration (`HyperFungibleToken.onAccept`, `WrappedHyperFungibleToken.onAccept`, `IntentsBase._execute`), but nothing enforces that: any account can call `CallDispatcher.dispatch(bytes)` directly with an attacker-chosen `Call[]` and have the dispatcher execute arbitrary calls to arbitrary targets, forwarding any ETH balance the dispatcher currently holds and using the dispatcher's own address as `msg.sender`. This is the same root cause as the reported analog: a contract designed to be triggered only through a specific privileged internal flow exposes a public entry point that anyone can invoke directly with attacker-controlled parameters, letting them execute the "callback" logic out of its intended context and steal whatever value is sitting there.

### Finding Description
`CallDispatcher` is a shared singleton deployed once per chain and reused by every `HyperFungibleToken`/`WrappedHyperFungibleToken` transfer with calldata and every `IntentGatewayV2`/`ExtrinsicIntents` order with pre/post-dispatch calldata: [1](#0-0) 

- `dispatch()` has no `onlyHost`, no `onlyGateway`, no ownership or role check of any kind - it is `external` with zero restriction.
- It has a `receive()` that accepts native ETH unconditionally.
- Inside `dispatch()`, each `Call` is executed with `to.call{value: call.value}(call.data)`, so any ETH balance sitting on the `CallDispatcher` at the moment of the call can be forwarded to an attacker-chosen address, and any ERC-20/target contract can be invoked with the `CallDispatcher` itself as `msg.sender`.

The documented usage pattern confirms the dispatcher is expected to hold funds transiently as part of a trusted, multi-step flow: [2](#0-1) 

`_execute` transfers/leaves solver output assets on the dispatcher, invokes `dispatch(order.output.call)` (attacker/solver-influenced calldata), and only afterward sweeps back whatever balance remains for the tokens enumerated in `order.output.assets`. Likewise `HyperFungibleToken.onAccept` and `WrappedHyperFungibleToken.onAccept` mint/unlock tokens to a beneficiary and then call `ICallDispatcher(_dispatcher).dispatch(message.data)`: [3](#0-2) 

Because `dispatch()` itself is unauthenticated, none of these callers' checks (`onlyHost`, source verification, relayer checks) actually protect the dispatcher's balance - they only gate who can *legitimately orchestrate* a call through it. Any account can bypass that orchestration entirely and call `CallDispatcher.dispatch()` directly to spend:
- any native ETH balance currently on the contract (from its unconditional `receive()`),
- any token balance currently on the contract that has not yet been swept back (dust from a prior fill/mint whose sweep only covers the tokens explicitly enumerated in that order's `outputs`, per `_execute`'s loop over `order.output.assets`), or
- more generally, any value the contract is holding at the instant of the call, since the dispatcher is a single shared address used concurrently by unrelated HFT transfers and intent fills across the whole chain.

This mirrors the reported bug class precisely: the intended caller (the flashloan pool / here, the HFT or IntentGateway contract) is not the only path to the sensitive logic; an unprivileged actor can invoke the "callback" (here, `dispatch`) directly with arbitrary parameters and act on whatever state/funds are present, exactly as the Aave flash-loan receiver could be triggered directly by anyone to drain the margin account.

### Impact Explanation
Any native ETH or token balance sitting on the shared `CallDispatcher` — whether transient dust from a prior fill/mint that wasn't fully swept, or ETH sent via `receive()` — can be swept to an attacker by a single unprivileged transaction to `dispatch()`. Since the `CallDispatcher` is a shared, chain-wide singleton reused by every `HyperFungibleToken`, `WrappedHyperFungibleToken`, and `IntentGatewayV2`/`ExtrinsicIntents` instance on that chain, this is not scoped to one app or one order — it is a chain-wide unauthenticated withdrawal primitive over whatever balance the dispatcher happens to hold at any time. This qualifies as concrete theft of funds reachable from a single, permissionless transaction.

### Likelihood Explanation
High: `dispatch()` requires no authorization to call, and the CallDispatcher legitimately and routinely holds ETH/token balances between the point tokens are delivered to it and the point they are swept back out, as explicitly acknowledged in the codebase's own security notes ("the dispatcher contract holds tokens temporarily during execution"). Any watching bot can call `dispatch()` the instant it detects a non-zero balance on the dispatcher address.

### Recommendation
Restrict `CallDispatcher.dispatch()` to a caller allow-list (e.g., only the registered `HyperFungibleToken`/`WrappedHyperFungibleToken`/`IntentGatewayV2` instances that are configured to use it), or make the dispatcher single-use/ephemeral per call (e.g., deploy a fresh minimal-proxy dispatcher per operation via `CREATE2`/`CREATE` so no shared, persistently-addressable balance ever exists), or add a reentrancy/ownership guard so that only the contract that funded a given `dispatch()` invocation in the same transaction can trigger it, and ensure sweep logic accounts for all tokens that could have been touched by attacker/solver-controlled calldata, not just the ones enumerated in `order.output.assets`.

### Proof of Concept
1. Observe (via mempool/state) that the shared `CallDispatcher` at a known address currently holds a non-zero ETH or ERC-20 balance — e.g., dust left over after `IntentsBase._execute` swept only the tokens listed in `order.output.assets`, or native ETH sent to it via its unconditional `receive()` during a prior `Call.value` step.
2. Encode `Call[] calls = [Call({ to: <token or self>, value: <balance>, data: <transfer-to-attacker calldata or empty for native> })]`.
3. Call `CallDispatcher.dispatch(abi.encode(calls))` directly from an unrelated EOA/contract — no `onlyHost`, no gateway check, no ownership check blocks this.
4. The dispatcher executes the call with its own balance/identity as `msg.sender`, transferring the funds to the attacker, exactly as any of the legitimate app contracts would have, but without going through any of their access checks.

    /**
     *  @dev reverts if the target is not a contract or if any of the calls reverts.
     */
    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }

    function _execute(Order calldata order, uint256 outputsLen) internal {
        if (order.output.call.length == 0) return;

        address dispatcher = _params.dispatcher;
        ICallDispatcher(dispatcher).dispatch(order.output.call);

        Call[] memory sweepCalls = new Call[](outputsLen);
        uint256 sweepCount = 0;

        for (uint256 i; i < outputsLen;) {
            address token = address(uint160(uint256(order.output.assets[i].token)));

            if (token == address(0)) {
                uint256 balance = dispatcher.balance;
                if (balance > 0) {
                    sweepCalls[sweepCount] = Call({to: address(this), value: balance, data: ""});
                    sweepCount++;
                    emit DustCollected(token, balance);
                }
            } else {
                uint256 balance = IERC20(token).balanceOf(dispatcher);
                if (balance > 0) {
                    sweepCalls[sweepCount] = Call({
                        to: token,
                        value: 0,
                        data: abi.encodeWithSelector(IERC20.transfer.selector, address(this), balance)
                    });
                    sweepCount++;
                    emit DustCollected(token, balance);
                }
            }

            unchecked {
                ++i;
            }
        }

        if (sweepCount > 0) {
            Call[] memory finalCalls = new Call[](sweepCount);

                    ++i;
                }
            }

        }
    }
