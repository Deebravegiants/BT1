### Title
Webhook HMAC does not bind the `shop-domain` header, allowing shop-identity spoofing on webhook processing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC over the raw request body. The `shop`, `topic`, `webhook_id`, and `api_version` values that are handed to the app's handler as the tenant identity for the event are read from HTTP headers that are **not** part of the signed material, so any attacker who possesses one valid `(raw_body, hmac)` pair can replay it while swapping in an arbitrary `shop-domain` header value.

### Finding Description
`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and compares it to the caller-supplied `hmac`: [1](#0-0) 

For a webhook `Request`, `to_signable_string` returns only `@raw_body` — none of the Shopify headers are included in the signable string: [2](#0-1) 

But `shop`, `topic`, `webhook_id`, and `api_version` — the values used to identify *which tenant* the event belongs to — are all pulled straight from headers, independent of the HMAC: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately forwards the header-derived `request.shop` (together with the body) to the app's handler as trusted tenant metadata: [4](#0-3) 

The intended binding is `hmac(secret, body || shop || topic) == received_hmac`, but what is actually enforced is `hmac(secret, body) == received_hmac` while `shop` is taken verbatim from an unauthenticated header. Since `hmac-sha256`, `topic`, and `shop-domain` are all attacker-controlled HTTP headers on a POST to the app's own public webhook endpoint, an attacker who possesses **any** one legitimately-signed `(raw_body, hmac)` pair (e.g., from a webhook delivered to their own development store, using the app's own `client_secret`) can replay that exact body+hmac to the target app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` still succeeds because it only checks the body's integrity against the shared secret, not the shop the body actually originated from.

### Impact Explanation
`WebhookMetadata.shop` is the field host applications rely on to scope handling of the event to the correct merchant/tenant (e.g., writing data, triggering shop-specific business logic, cache invalidation, billing operations). Because `shop` is not bound by the HMAC, an attacker who has any valid signed webhook payload (from their own shop, since app secrets are shared across all installs of a given app) can cause the app to process that payload under an arbitrary victim shop's identity — a cross-tenant confusion inside the app's webhook processing pipeline that this gem is trusted to authenticate.

### Likelihood Explanation
Exploitation requires only: (1) the app be installed on any shop the attacker controls (trivial, since any Shopify Partner can create a development store) so they can capture one real, validly-signed webhook body+hmac pair, and (2) sending a forged POST directly to the app's own public webhook endpoint. No access to the app's `client_secret`, access tokens, or privileged accounts is needed — the HMAC used is derived only from data the attacker already legitimately possesses via their own installed session.

### Recommendation
Include the identity-binding headers (`shop-domain`, `topic`, and ideally `webhook_id`) in the signable string used for HMAC verification, or otherwise cryptographically bind them to the payload before trusting `request.shop`/`request.topic` in `Registry.process`.

### Proof of Concept
1. Install the target app on an attacker-controlled development store; capture a legitimate webhook delivery, including its raw body and `x-shopify-hmac-sha256` header (both are valid because they share the app's `client_secret` with all shops).
2. Replay that same raw body and `hmac-sha256` value to the target app's webhook endpoint, but set `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `HmacValidator.validate` succeeds because it only checks the body against the shared secret (`lib/shopify_api/utils/hmac_validator.rb:26-31`), and `Registry.process` invokes the app's handler with `shop: "victim-shop.myshopify.com"` (`lib/shopify_api/webhooks/registry.rb:198-199`), causing the app to process attacker-supplied data under the victim's tenant identity.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
