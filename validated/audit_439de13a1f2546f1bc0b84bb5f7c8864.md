Found it. `TokenExchange.exchange_token` is the only OAuth entry point in this gem that builds the outbound HTTP host from a value that is **not** passed through `ShopValidator.sanitize!`, unlike every sibling method (`ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, `TokenExchange.migrate_to_expiring_token`), which all call `Utils::ShopValidator.sanitize!(shop)` before constructing the `Session` used to build the request host.

### Title
SSRF via unsanitized JWT `dest` claim used as request host in `TokenExchange.exchange_token` - (File: `lib/shopify_api/auth/token_exchange.rb`)

### Summary
`TokenExchange.exchange_token` derives the outbound request host (which carries the app's `client_secret`) directly from the `dest` claim of an attacker-decodable JWT segment, without ever running it through `Utils::ShopValidator.sanitize!`, unlike every other credential-exchange method in the same file/module.

### Finding Description
`exchange_token` decodes the session token with `ShopifyAPI::Auth::JwtPayload.new(session_token)` and takes `dest_shop = jwt_payload.shop` [1](#0-0) . `JwtPayload#shop` merely strips `"https://"` from the raw `dest` claim string with no domain allow-listing [2](#0-1) . That unvalidated `dest_shop` is used to build `shop_session = ShopifyAPI::Auth::Session.new(shop: dest_shop)` [3](#0-2) , which is then passed into `Clients::HttpClient.new(session: shop_session, base_path: "/admin/oauth")`. `HttpClient#initialize` builds the actual request host straight from `session.shop`: `@base_uri = "https://#{api_host || session.shop}"` [4](#0-3) . The subsequent POST to `#{base_uri}/admin/oauth/access_token` carries `client_secret` in the body [5](#0-4) .

The binding that should hold is: **host validated == host that receives the `client_secret`**, restricted to `ShopValidator::TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`) [6](#0-5) . This binding is enforced everywhere else that builds a `shop_session` for an OAuth token request: `ClientCredentials.client_credentials` calls `Utils::ShopValidator.sanitize!(shop)` [7](#0-6) , `RefreshToken.refresh_access_token` does the same [8](#0-7) , and even `TokenExchange.migrate_to_expiring_token` in the very same file does the same [9](#0-8) . `exchange_token` is the outlier that skips this check.

Crucially, unlike the OAuth-callback HMAC (`AuthQuery`) or the JWT signature itself, `dest` is **not cryptographically bound to a Shopify-issued value the way callers assume**: `JwtPayload` only requires that the token be signed by the app's own `api_secret_key` and that `aud == Context.api_key` [10](#0-9) . It performs no validation that `dest`/`iss` is a real `*.myshopify.com` (or other trusted) domain. Any party capable of getting the host application to call `exchange_token` with a token whose `dest` claim is an arbitrary string will cause this gem to send the app's `client_secret` to that arbitrary host.

### Impact Explanation
This breaks the "host validated versus host that receives the `client_secret`" binding called out in the rules. If the `dest` claim can be influenced (e.g., a session token obtained from a source other than App Bridge's guaranteed-safe token, or a malicious/compromised token relay), the gem will POST the app's `client_id`/`client_secret`/`subject_token` to an attacker-controlled origin — SSRF carrying the app's credentials, and effectively leaking `client_secret` to a third party, satisfying the "High: SSRF with the app's credentials" impact class.

### Likelihood Explanation
Every other method building a `shop_session` from user/host-application input in this module enforces `ShopValidator.sanitize!`; `exchange_token` conspicuously does not, showing this was an oversight rather than an intentional design choice (the `dest` claim is treated as implicitly trustworthy, but the code makes no cryptographic guarantee that `dest` is a genuine Shopify domain beyond signature-and-audience checks).

### Recommendation
Sanitize `dest_shop` with `Utils::ShopValidator.sanitize!(dest_shop)` before constructing `shop_session` in `TokenExchange.exchange_token`, mirroring `migrate_to_expiring_token`, `client_credentials`, and `refresh_access_token`.

### Proof of Concept
1. Obtain/produce a valid session token whose `dest` claim is `https://attacker.example.com` but which still satisfies `JwtPayload`'s checks (valid signature under the app's `api_secret_key`/`old_api_secret_key`, `aud == Context.api_key`, not expired).
2. Call `ShopifyAPI::Auth::TokenExchange.exchange_token(session_token: token, requested_token_type: ...)`.
3. Observe `Clients::HttpClient` builds `@base_uri = "https://attacker.example.com"` and POSTs a body containing `client_id` and `client_secret` to `https://attacker.example.com/admin/oauth/access_token`, exfiltrating the app's `client_secret` to the attacker's host. [11](#0-10)
