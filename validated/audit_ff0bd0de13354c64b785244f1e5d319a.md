### Title
Escrow-Withdrawal State Finalized After External Token Transfer in Tron `IntentGatewayV2.withdraw` - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
`IntentGatewayV2.withdraw` on the Tron deployment releases escrowed order tokens to a beneficiary via a low-level `token.call(...)` **before** decrementing the corresponding `_orders[commitment][token]` accounting entry, unlike the hardened, CEI-compliant `_withdraw` in the shared EVM `IntentsBase.sol`. This reproduces the exact bug class from the referenced report: an authoritative accounting variable is updated only *after* an external call that can run attacker-supplied code, leaving a window where stale (not-yet-decremented) escrow state can be observed/acted upon.

### Finding Description
`IntentsBase._withdraw` (the audited/fixed EVM path) follows checks-effects-interactions: it computes `escrowed`, writes `_orders[commitment][token] = escrowed - amount` **first**, then performs the transfer via `_sendValue`/`safeTransfer`. [1](#0-0) 

The Tron contract's `withdraw` does the opposite: it checks `_orders[body.commitment][token] == 0`, performs the external token/native transfer via a raw `.call`, and only afterwards executes `_orders[body.commitment][token] -= amount`: [2](#0-1) 

Because `order.inputs`/`body.tokens` token addresses are attacker-chosen when the order is placed (an order's escrowed input token can be any contract implementing an ERC20-like `transfer` selector), the beneficiary/token contract executing during the `.call` runs with `_orders[commitment][token]` still at its pre-decrement value. This is structurally identical to the FERC1155 bug: `totalSupply` (state used to gate later privileged logic) was updated only after `_mint`'s external callback, letting attacker-controlled code observe/exploit stale accounting mid-call. Here the stale value is the escrow ledger entry that gates whether further redemption/refund against the same commitment is considered valid.

`withdraw` is only reachable from `onAccept`/`onGetResponse`, both `onlyHost`-gated, so a directly re-entrant call from the malicious token back into `withdraw()` itself is blocked at the access-control layer — this is the one aspect I could not fully verify end-to-end: whether the `EvmHost`/`HandlerV2` message-processing loop marks a request's delivery receipt strictly before invoking the app's `onAccept`, or whether multiple relayed messages targeting the same commitment can be processed within a single host transaction (which would let the reentrant call ride back in through a second, distinct `onAccept` invocation for a different-but-related request before the first `_orders` write completes). I was unable to confirm this ordering in `HandlerV2.sol`/`EvmHost.sol` within the available searches, so the full attack chain is not proven, only the CEI-violation root cause.

### Impact Explanation
If any reentrant path back into `onAccept`/`onGetResponse` exists during the host's request-processing (e.g., receipt marking after dispatch, or batched delivery of multiple queued messages in one transaction), an attacker who places an order using a malicious "token" contract as escrow input could cause the same escrowed amount to be paid out multiple times before `_orders` is decremented — a direct theft of escrowed funds from the Tron `IntentGatewayV2` contract. Even absent full reentrancy, this ordering is a latent, exploitable primitive that the equivalent audited EVM contract has already been hardened against (see `_withdraw`'s CEI ordering), and should be treated as Medium risk consistent with the original finding's judged severity.

### Likelihood Explanation
Reaching this code path requires only a standard cross-chain order placement with an attacker-controlled input token, plus a solver filling the order and a relayer delivering the resulting `RedeemEscrow`/`RefundEscrow` message — all steps available to an unprivileged actor. The only unresolved variable is whether the host's dispatch mechanism permits nested/batched `onAccept` calls for related messages before receipts are committed; if so, likelihood is high given attacker control over the token contract's callback code.

### Recommendation
Align `evm/tron/contracts/apps/IntentGatewayV2.withdraw` with the CEI pattern already used in `IntentsBase._withdraw`: decrement `_orders[body.commitment][token]` (and the transaction-fee entry) **before** performing the native/ERC20 transfer, and adopt `SafeERC20.safeTransfer` instead of raw low-level `.call` with a manually checked boolean, matching the fixed EVM implementation.

### Proof of Concept
Conceptual PoC (blocked from full construction by uncertainty in host dispatch ordering, per above):
1. Attacker deploys `EvilToken`, an ERC20-like contract whose `transfer(address,uint256)` function, when called, attempts to trigger a second, concurrently-relayed message delivery for the same order commitment (e.g., by exploiting any host-side batch/multi-message processing window).
2. Attacker places a same-chain-input/cross-chain-output order with `order.inputs[0].token = address(EvilToken)`.
3. A solver fills the order on the destination chain; a relayer delivers the resulting `RedeemEscrow` request back to the Tron `IntentGatewayV2` via the host.
4. Inside `withdraw`, `token.call(transfer(...))` invokes `EvilToken.transfer`, which — if the host permits nested delivery — triggers a second `onAccept`/`onGetResponse` call reading the still-undecremented `_orders[commitment][EvilToken]`, releasing the escrow a second time.
5. `_orders[commitment][EvilToken] -= amount` finally executes for both calls, but the second payout has already been sent, resulting in double payment of escrowed funds. [2](#0-1) [3](#0-2)

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }
