### Title
`deposit` in `v0-vault-ststx.clar` lacks a zero-shares-minted guard, permanently donating principal to the unredeemable `NULL-ADDRESS` minimum-liquidity position - ([File: mainnet/contracts/vault/v0-vault-ststx.clar])

### Summary
`initialize` permanently locks `MINIMUM-LIQUIDITY` (`u1000`) `zft` shares to `NULL-ADDRESS`, a burn address with no controlling key [1](#0-0) [2](#0-1) . Once every other depositor redeems out and `var-get assets` reaches exactly `u0` while `(total-supply)` still equals `u1000` from `NULL-ADDRESS`, `deposit` will happily mint `u0` shares for any subsequent deposit and still pull in and record the underlying, because unlike `redeem`, `deposit` has no `(> inkind u0)` assertion.

### Finding Description
The broken identity: `convert-to-assets-preview(total-supply)` should always equal the sum of all underlying ever deposited and not yet withdrawn, i.e. `total-assets-preview() == Σ deposits − Σ redemptions`, and every unit of `assets` should be backed by a redeemable `zft` claim held by *some* principal capable of calling `redeem`.

Code path:
- `convert-to-shares-preview` returns `u0` shares whenever `ts != u0` and `ta == u0` [3](#0-2) .
- `deposit` computes `inkind` via this function, then only checks `(asserts! (>= inkind min-out) ERR-SLIPPAGE)` and `(asserts! (> amount u0) ERR-AMOUNT-ZERO)` - there is no `(> inkind u0)` check [4](#0-3) .
- Contrast with `redeem`, which explicitly guards against a zero output: `(asserts! (> inkind u0) ERR-OUTPUT-ZERO)` [5](#0-4) .

Exploit flow:
1. All real depositors redeem their `zft`, which is allowed as long as `inkind > 0` at each step; the final redemption can drive `(var-get assets)` to exactly `u0` while total-borrowed stays `u0` (no outstanding interest), so `total-assets-preview()` also becomes `u0`. `NULL-ADDRESS`'s `u1000` balance is untouched since it never calls `redeem`.
2. Attacker (or any unaware depositor) calls `(deposit X u0 attacker)`. `ta = 0`, `ts = 1000` ⇒ `inkind = 0`. All of `deposit`'s guards pass (`amount > 0`, `inkind (u0) >= min-out (u0)`, cap check). `receive-underlying` pulls in `X` real underlying, `ft-mint? zft u0 attacker` mints nothing, and `(var-set assets (+ current-assets amount))` sets `assets = X`.
3. Post-state: `total-supply = 1000` (all held by `NULL-ADDRESS`), `assets = X`, attacker's `zft` balance is `u0`. `convert-to-assets-preview(1000)` now equals `X` - the entire deposited value is attributed to `NULL-ADDRESS`'s locked shares.
4. Because `NULL-ADDRESS` was constructed via `principal-construct?` with no known private key [1](#0-0) , no principal can ever call `redeem` on its behalf to retrieve `X`. Note also that this per-share value (`X/1000`) is preserved under future proportional deposits, so the frozen amount does not get "fixed" by later activity - it is permanently locked.

Existing guards (`min-out`, `> amount u0`, supply cap, pause states) do not catch this because they check `amount` and `inkind` against `min-out`, not against `u0` itself; `min-out = u0` trivially satisfies `inkind >= min-out` even when `inkind = 0`.

### Impact Explanation
Each occurrence of this state (`ta = 0`, `ts != 0`) permanently freezes 100% of the next deposit's principal `X`, attributing its value entirely to the unredeemable `NULL-ADDRESS` shares. This is repeatable any time the vault's real liquidity is fully drained to zero (zero utilization, no outstanding interest) - not an isolated one-time event. The party bearing the loss is whoever deposits into that zero-`ta`/nonzero-`ts` window (an unaware ordinary user, or an attacker if used as a griefing tool against a victim's pending deposit). This matches the Critical category: permanent freezing of funds (the principal is not merely redistributed - it becomes attributed to a principal that structurally cannot ever call `redeem`).

### Likelihood Explanation
Preconditions require the vault's real depositors to fully exit while there is no outstanding debt/interest (i.e., utilization at or near zero and no accrued interest keeping `total-assets-preview` above zero) - a normal, unprivileged, reachable state with no special capital cost beyond the deposit amount itself. Any unprivileged principal can trigger it by simply calling `deposit` with `min-out = u0` at that state; no oracle, DAO, or privileged access is needed, and it is fully repeatable each time the vault re-empties to zero real assets.

### Recommendation
Add an explicit zero-shares guard in `deposit`, mirroring the `redeem` guard, e.g. `(asserts! (> inkind u0) ERR-OUTPUT-ZERO)` immediately after computing `inkind`, so that a deposit which would mint zero shares reverts instead of silently absorbing the underlying into the unredeemable `NULL-ADDRESS` position.

### Proof of Concept
Clarinet/vitest simnet plan:
1. Call `initialize` - locks `u1000` `zft` to `NULL-ADDRESS`, `assets = 0` (or whatever floor deposit was made at init).
2. Have a second depositor deposit `Y` underlying, receive `S` shares.
3. Ensure no borrow occurs (`total-borrowed = 0`), so `total-assets-preview() == var-get assets` exactly.
4. Second depositor calls `redeem(S, 0, depositor)`. Assert `(get-assets)` returns `u0` afterward and `(get-total-supply)` is still `u1000` (only `NULL-ADDRESS`'s balance).
5. Attacker calls `deposit(X, u0, attacker)` with `X > 0`. Assert the call succeeds (`ok`), `(get-balance attacker)` (`ft-get-balance zft attacker`) equals `u0`, and `(get-assets)` equals `X`.
6. Assert `(convert-to-assets u1000)` equals `X` - i.e., all of `X` is now attributed to `NULL-ADDRESS`'s locked shares.
7. Assert no test principal (including simulated `NULL-ADDRESS` `tx-sender`) can successfully call `redeem` to retrieve `X`, since `NULL-ADDRESS` has no controllable key in the test harness - demonstrating the funds are permanently frozen.

  (let ((ta (total-assets-preview))
