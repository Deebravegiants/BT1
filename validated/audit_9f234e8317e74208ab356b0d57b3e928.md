The `shop` field consumed by webhook handlers is sourced from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, while the HMAC signature (matching the real Shopify webhook design) covers only the raw request body via `to_signable_string` returning `@raw_body` [1](#0-0) . `Registry.process` validates only that HMAC, then immediately trusts `request.shop` to build `WebhookMetadata` passed to the app's handler [2](#0-1) . Since the HMAC secret (`api_secret_key`) is shared across every shop that installs the app, any merchant who installs the app can capture a genuine, validly-signed webhook delivered to their own shop and replay it to the app's webhook endpoint with the `shop-domain` header swapped to a victim shop's domain — the signature still validates because it never covered the shop identity, and the handler will process cross-tenant data as if it came from the victim shop.

### Title
Webhook shop identity not bound to HMAC signature allows cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body, and `HmacValidator.validate` verifies the HMAC solely over that body [3](#0-2) . The `shop` (and `topic`, `webhook_id`, `api_version`) values consumed by `Registry.process` come from HTTP headers that are never part of the signed material [4](#0-3) . Because `api_secret_key` is the same shared secret for all shops using a given app, a webhook body/HMAC pair legitimately issued for one shop remains valid when replayed with a different shop's identifier in the header.

### Finding Description
`Registry.process(request)` performs a single authenticity check: `Utils::HmacValidator.validate(request)` [2](#0-1) . That validator recomputes an HMAC over `verifiable_query.to_signable_string` and compares it to the `hmac` value [3](#0-2) . For `Webhooks::Request`, `to_signable_string` is defined as just `@raw_body` [5](#0-4) , and `shop` is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic binding to the signature [6](#0-5) .

This breaks the identity equality that should hold: `shop-authenticated-by-HMAC == shop-passed-to-handler`. In reality, `shop-authenticated-by-HMAC` is undefined — the HMAC proves only "some install of this app produced this body," not "this specific shop produced this body." `Registry.process` nonetheless builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` straight from the header and hands it to the app-defined handler [7](#0-6) , which per the library's own documented contract is expected to trust `data.shop` to key its side effects (e.g., `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) [8](#0-7) .

### Impact Explanation
This is a cross-tenant identity confusion: a malicious merchant who has installed the app on their own shop can obtain a validly HMAC-signed webhook body for their own tenant (many topics, notably the mandatory `shop/redact`, `customers/redact`, `customers/data_request` topics or any topic whose payload doesn't itself encode the shop, produce predictable/reusable bodies), then replay that body+HMAC pair to the app's webhook endpoint while substituting the victim's shop domain in the `shopify-shop-domain` header. `Registry.process` accepts it, and the handler executes shop-scoped logic (data deletion, redaction, state changes, enqueued background jobs) attributed to the victim shop. Depending on the handler's semantics this can trigger unauthorized cross-tenant actions — e.g. spoofed `customers/redact` / `shop/redact` processing against a shop the attacker doesn't control, or corrupting another tenant's derived state — which matches the Critical "cross-tenant access" impact class.

### Likelihood Explanation
Reachable by any unprivileged internet user who can install the target app on a shop they control (a normal, unprivileged action for any Shopify merchant) and send crafted HTTP requests to the app's public webhook endpoint. No access token, `client_secret`, or privileged credential is required — only knowledge of one genuine `(body, hmac)` pair generated by Shopify for the attacker's own shop, which the attacker legitimately receives as part of normal app installation/usage.

### Recommendation
Bind the shop identity into the material that is cryptographically verified, or otherwise cross-check the header-derived `shop` against a value that is itself authenticated (e.g., verify the webhook's `shop` header corresponds to a shop with a currently registered/active session/webhook subscription known to the app, rather than trusting the header unconditionally). At minimum, document prominently that `WebhookMetadata#shop` is not covered by the HMAC and must not be used by host applications as a trusted tenant key without an independent authorization check (e.g., confirming the shop has an existing installation record) before performing shop-scoped side effects.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker.myshopify.com` and receives a genuine webhook, e.g. for `customers/data_request` with a body the attacker fully controls or that is otherwise predictable, along with headers:
   ```
   x-shopify-topic: customers/data_request
   x-shopify-hmac-sha256: <valid HMAC of raw_body computed with the shared api_secret_key>
   x-shopify-shop-domain: attacker.myshopify.com
   ```
2. Attacker resends the exact same `raw_body` and `x-shopify-hmac-sha256` value to the app's public webhook endpoint, but changes the header to:
   ```
   x-shopify-shop-domain: victim-shop.myshopify.com
   ```
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `raw_body` [5](#0-4)  — validation succeeds since the body/HMAC pair wasn't tampered with.
4. `WebhookMetadata.new(shop: request.shop, ...)` now reports `shop: "victim-shop.myshopify.com"` [7](#0-6) , and the app's handler performs shop-scoped processing believing it originated from the victim shop.
