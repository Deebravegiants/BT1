### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing shop-identity spoofing on otherwise-authentic webhook requests - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [1](#0-0) , while `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from unauthenticated HTTP headers [2](#0-1) . `Registry.process` validates only this body-only HMAC and then immediately trusts `request.shop` as the tenant identity passed to the app's handler [3](#0-2) . This breaks the identity binding `HMAC-authenticated bytes == bytes acted upon`: the signature authenticates the body, but the `shop` value used to attribute the payload to a tenant is never part of the signed material.

### Finding Description
`HmacValidator.validate` recomputes the HMAC over `verifiable_query.to_signable_string` and compares it to the `hmac` header using `OpenSSL.secure_compare` [4](#0-3) . For `Webhooks::Request`, `to_signable_string` is exactly `@raw_body` [5](#0-4) . The `shop` accessor is pulled straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header with no cryptographic linkage to the HMAC or to the body [6](#0-5) .

`Registry.process` calls `Utils::HmacValidator.validate(request)` and, once that passes, builds `WebhookMetadata` using `request.shop` as the tenant identifier that is handed to the app-supplied handler [7](#0-6) . The library's own documentation instructs apps to treat `data.shop` as the authoritative shop identity for routing/attribution (`shop_domain: data.shop`) [8](#0-7) , so this is the intended, documented usage pattern, not host-application misuse.

**Equality that should hold but doesn't:** `shop identity bound by the HMAC == shop identity acted upon by the handler`. In fact: `HMAC covers only raw_body` while `handler acts on shop-domain header`, an entirely independent, attacker-controllable field.

**Exploitability by an unprivileged internet user:** The webhook HTTP endpoint is a public URL by design (Shopify posts to it over plain HTTPS, and any actor can also POST to it directly). An attacker can:
1. Install the target app on their own (attacker-owned) Shopify development store — an unprivileged, self-service action — and receive a genuine Shopify-signed webhook for a chosen topic/body.
2. Capture that exact `(raw_body, hmac)` pair, since the attacker controls the delivery endpoint for their own shop.
3. Replay the identical body and HMAC directly to the app's public webhook endpoint, but with the `x-shopify-shop-domain` header changed to an arbitrary victim shop domain.
4. `HmacValidator.validate` still succeeds (it never looked at the header), and `Registry.process` calls the handler with `shop:` set to the attacker-chosen victim domain.

### Impact Explanation
This is a cross-tenant identity-confusion primitive: an attacker can make forged webhook data appear to originate from any shop domain of their choosing, while the actual payload only needs to be a genuine webhook the attacker legitimately obtained for their own store. Because the shop identity drives which merchant's data/session the host app updates (exactly as documented), this can be leveraged to write attacker-controlled state into another tenant's records, or to trigger app logic (e.g., data resync, notifications, state changes) attributed to a victim shop the attacker never installed the app on. This satisfies the "cross-tenant access" criterion, since the identity boundary between tenants (shop domains) is not authenticated by the gem despite it being presented as an authenticated field to consumers.

### Likelihood Explanation
Medium-high: no secrets are required beyond installing the target app on an attacker-owned/free development store (a normal, self-service action any internet user can perform), and no valid credentials for the victim shop are needed. The main constraint is that the attacker's forged webhook always carries the exact same `body` (and thus `topic`/data) that Shopify originally signed for the attacker's own shop — they cannot fabricate arbitrary victim-shop data, only relabel their own legitimate webhook payload as belonging to a victim shop. Real-world impact therefore depends on what host apps do with `data.shop` alone (e.g., look up a session/access token for that shop and apply the received body's data), which is exactly the pattern the library's docs recommend.

### Recommendation
Bind the shop identity into the authenticated material, e.g., include `shop-domain` (and ideally `topic`/`webhook-id`) in `to_signable_string`, or independently verify the `shop` header against Shopify's canonical domain format via `Utils::ShopValidator` and cross-check it against the shop that Shopify's webhook infrastructure is known to have delivered for a given app/topic (e.g., validate against previously stored session/shop records before trusting `data.shop`). At minimum, the library should document explicitly that `shop`, `topic`, `webhook_id`, and `api_version` headers are *not* covered by the HMAC and must not be trusted for tenant attribution without additional verification.

### Proof of Concept
```ruby
# 1. Attacker installs the target app on their own store "attacker-shop.myshopify.com"
#    and receives a genuine Shopify webhook, e.g. body = '{"id":123}'.
# Captured legitimate headers (HMAC computed by Shopify using the real api_secret_key):
raw_body = '{"id":123}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), REAL_API_SECRET, raw_body) # attacker doesn't know the key but Shopify computed this and delivered it

headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac),
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # <-- attacker rewrites this
  "x-shopify-webhook-id" => "any-id",
  "x-shopify-api-version" => "2024-01",
}

# 2. Attacker POSTs raw_body + headers directly to the app's public webhook endpoint.
request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)

# 3. HMAC validation succeeds because it only checks raw_body:
ShopifyAPI::Utils::HmacValidator.validate(request) # => true

# 4. Registry.process invokes the handler believing this data is from "victim-shop.myshopify.com":
ShopifyAPI::Webhooks::Registry.process(request)
# handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: {"id"=>123}, ...))
```

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
