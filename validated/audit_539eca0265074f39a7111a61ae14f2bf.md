### Title
BEEFY consensus proofs count raw vote/signature entries toward the supermajority threshold without deduplicating authority indices, letting a single relayer forge quorum with fewer distinct authorities - ([File: evm/src/consensus/EcdsaBeefy.sol], [File: modules/consensus/beefy/verifier/src/lib.rs])

### Summary
Both the Solidity (`EcdsaBeefy.verifyMmrUpdateProof`) and Rust (`verify_mmr_update_proof`) BEEFY consensus verifiers compute the supermajority threshold from the raw length of the submitted votes/signatures array, then build a `MerkleMultiProof` leaf set directly from those same entries (`authorityIndex`/`sig.index`) without ever checking that the indices are unique. This mirrors the class of bug in the external report: a component that is supposed to represent "N distinct authorized participants" instead accepts a count that can be inflated by duplicate entries, letting the real quorum check be silently bypassed.

### Finding Description
`EcdsaBeefy.verifyMmrUpdateProof` takes `sigLen = relayProof.signedCommitment.votes.length` and checks `checkParticipationThreshold(sigLen, authoritySet.len)` — i.e., `sigLen >= (2*len)/3 + 1` — purely on the size of the attacker-supplied `votes` array: [1](#0-0) 

It then loops over `votes` again, recovering an address for every vote and inserting `MerkleMultiProof.Leaf({index: vote.authorityIndex, hash: keccak256(...)})` for each, and validates them in a single multi-proof call. Nowhere is `vote.authorityIndex` checked for uniqueness. The equivalent Rust verifier used by the Substrate-side ismp-beefy client has the identical pattern: [2](#0-1) 

Contrast this with the Pharos consensus verifier in the same codebase, which explicitly treats duplicate participants as a distinct threat and rejects them before computing stake/threshold: [3](#0-2) 

The BEEFY path has no analogous `deduped.len() != participants.len()` guard. Because the participation count (`sigLen`/`signatures_length`) and the merkle-multiproof leaf set are both derived straight from the submitted array, a relayer who possesses valid signatures from fewer than `2/3+1` authorities can pad the `votes`/`signatures` array with repeated `(authorityIndex, signature)` entries for the same authority (the signature is valid and reused, or the same `authorityIndex` is referenced multiple times) to inflate `sigLen` past the threshold. This is the same bug class the external report describes: the mechanism used to *count* legitimate participants diverges from the mechanism that *proves* they participated, and the count can be manipulated by an attacker who controls the ordering/composition of the input array, without needing to obtain the real number of distinct legitimate signers.

### Impact Explanation
If the merkle multi-proof library used (`@polytope-labs/solidity-merkle-trees` `MerkleMultiProof.VerifyProof` / `rs_merkle::MerkleProof::verify`) does not itself reject duplicate leaf indices — a documented weakness class in several merkle-multiproof implementations — an attacker holding signatures from fewer than the true `2/3+1` BEEFY authority supermajority could forge an accepted consensus update. This would let a relayer commit an unsound/forged parachain state commitment into `EcdsaBeefy`/the Rust `ismp-beefy` client, which is the root-of-trust consensus proof feeding new cross-chain messages, resulting in forged message delivery or an invalid state root being trusted by Hyperbridge — a critical unsound-state-commitment condition.

### Likelihood Explanation
BEEFY consensus proofs are submitted by permissionless relayers via a single transaction/extrinsic (`verify`/`verify_consensus`), matching the required "reachable from a single relayed proof" bar. No special privilege is needed to submit a consensus update; only possession of a subset of valid authority signatures (which are public once broadcast in relay-chain justifications) is required to attempt padding the vote array with duplicated authority entries.

### Recommendation
In both `EcdsaBeefy.verifyMmrUpdateProof` and `verify_mmr_update_proof` (beefy verifier), explicitly reject duplicate `authorityIndex`/`sig.index` values before computing `sigLen`/`signatures_length` and before building the leaf set for the merkle multi-proof, mirroring the `verify_validator_membership` dedup check already present in the Pharos verifier. Additionally, confirm (or add a defensive check ensuring) that the underlying `MerkleMultiProof`/`rs_merkle` verification routines reject proofs containing duplicate leaf indices.

### Proof of Concept
1. Attacker observes a BEEFY commitment for block `B` signed by only `k < 2/3*len+1` authorities out of the authority set.
2. Attacker constructs `RelayChainProof.signedCommitment.votes` (or the Rust `signatures` vec) containing the `k` genuine `(authorityIndex, signature)` pairs, then duplicates one or more of these entries until `votes.length >= (2*len)/3 + 1`.
3. `checkParticipationThreshold(sigLen, authoritySet.len)` passes because it only checks array length.
4. The `MerkleMultiProof.Leaf[]` built from `votes` includes the duplicated `authorityIndex` more than once; if `MerkleMultiProof.VerifyProof` (or `rs_merkle`'s multiproof `verify`) does not reject duplicate indices, the proof validates against `authoritySet.root`.
5. `verify()` returns a new `BeefyConsensusState` with `latestHeight` advanced and parachain state commitments trusted, despite fewer than a true supermajority of authorities having actually signed.
