Confirmed: `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, and the `shop` value comes from an unauthenticated header, not from the signed payload.### Title
Webhook HMAC signature does not cover the `shop` identity, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw body only, while the `shop` value used by `ShopifyAPI::Webhooks::Registry.process` to attribute the webhook to a tenant is read from an unauthenticated HTTP header that is never included in the signed bytes. This breaks the required identity binding `verified_bytes == bytes_that_determine_tenant`, letting any merchant who has legitimately installed the app on their own shop replay a valid `(raw_body, hmac)` pair while spoofing the `shop` header to impersonate a different shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, however, is parsed directly from the `x-shopify-shop-domain`/`shopify-shop-domain` header and is never part of the signed content: [2](#0-1) 

`Registry.process` validates the HMAC against `request` (i.e. against `raw_body` only) and then, on success, dispatches to the app's handler using `request.shop` taken from the same unauthenticated header: [3](#0-2) 

`HmacValidator.validate` confirms this: it only ever calls `verifiable_query.to_signable_string`, which for a webhook request is `@raw_body`, and never incorporates the shop domain header into the signature check: [4](#0-3) 

Because the webhook signing secret (`Context.api_secret_key`, i.e. the app's `client_secret`) is the **same for every shop that has installed the app**, and the HMAC binds only the body — not the shop — any shop that has installed the app can obtain a valid `(raw_body, hmac)` pair for its own legitimate webhooks and then replay that exact pair to the app's webhook endpoint with an arbitrary `x-shopify-shop-domain` header. `Registry.process` will pass HMAC validation (since it only checks `raw_body`) and hand the handler a `WebhookMetadata` claiming the body belongs to a completely different, victim shop: [3](#0-2) 

The equality that should hold is: `shop_the_HMAC_authenticates == shop_the_handler_receives`. In reality it is: `hmac_valid(raw_body)` (true for any shop that installed the app) is independent of `shop` (attacker-chosen header), so the gem hands the host application a `shop` value that looks "verified" (because `Utils::HmacValidator.validate` succeeded) but was never cryptographically bound to that shop at all.

### Impact Explanation
Any host application that follows the documented pattern (`ShopifyAPI::Webhooks::Registry.process` → handler keyed by `data.shop`) is exposed to cross-tenant data injection: an attacker with a normal, unprivileged installation of the app on their own shop can forge webhook payloads (topic, body content) that the app will process and persist/act on as if they came from an arbitrary target shop, without ever holding that target shop's access token or credentials. This is a cross-tenant access/data-integrity break, matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation only requires the attacker to be a merchant who installed the public app on their own store (a routine, unprivileged action for any app listed for install), then capture one of their own legitimate webhook deliveries (body + `X-Shopify-Hmac-Sha256`) and resend it to the same webhook endpoint with a modified `X-Shopify-Shop-Domain` header. No secrets, tokens, or elevated access are needed, and the gem's own `Registry.process`/`HmacValidator` accept the forged request as valid.

### Recommendation
Include the shop domain (and other identity-bearing headers such as topic/webhook-id, if the app depends on them) in the value verified by the HMAC check, or require the host application to independently corroborate `shop` against a value derived from an authenticated source (e.g., cross-check against the shop stored for the known webhook subscription/session) before trusting `WebhookMetadata#shop`. At minimum, the gem should document loudly that `request.shop` is unauthenticated and must not be used as a tenant-selection key without additional verification.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a shop they legitimately control) and triggers a real webhook (e.g., `orders/create`).
2. Shopify delivers `POST /webhook` with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC over raw_body>`, and the JSON body.
3. Attacker captures `raw_body` and `x-shopify-hmac-sha256` exactly as received.
4. Attacker replays the identical request to the app's webhook endpoint, changing only `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `raw_body` only — this still matches, since the body is unmodified — and the request passes validation.
6. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: <attacker-controlled>, ...)`, causing the host application to process/store attacker-controlled data under the victim shop's identity.

          received_signature = verifiable_query.hmac
