### Title
Fixed-amount SPL transfers without balance-delta verification break accounting for fee-on-transfer/Token-2022 mints - (File: program/src/processor.rs, program/src/invokers.rs)

### Summary
Every value-moving instruction in the AMM (`Deposit`, `Withdraw`, `SwapBaseIn`, `SwapBaseOut`, `WithdrawPnl`) calls `Invokers::token_transfer` / `Invokers::token_transfer_with_authority` with a fixed amount computed purely from off-chain-supplied instruction data and cached vault balances, without re-reading vault/token-account balances after the CPI to confirm the amount actually received. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`Invokers::token_transfer` and `Invokers::token_transfer_with_authority` are thin wrappers around `spl_token::instruction::transfer` invoked via `invoke_signed`, with no post-transfer balance check. [4](#0-3) 
In `deposit`, `deduct_coin_amount`/`deduct_pc_amount` are computed from the pool invariant and then transferred verbatim into `amm_coin_vault_info`/`amm_pc_vault_info`, and `mint_lp_amount` LP tokens are minted based on that same nominal amount rather than what the vault actually received. [5](#0-4) 
In `swap_base_in`/`swap_base_out`, `swap.amount_in`/`swap_in_after_add_fee` is transferred from the user into the vault, and `swap_amount_out`/`swap.amount_out` is paid out of the opposite vault, both computed from the invariant math against the *pre-transfer* `total_coin_without_take_pnl`/`total_pc_without_take_pnl`, not the post-transfer vault balance. [6](#0-5) [7](#0-6) 
If the coin or pc mint bound to the pool is a deflationary/fee-on-transfer token (or a Token-2022 mint with the `TransferFeeConfig` extension enabled or later enabled by a mint authority upgrade), the vault will receive strictly less than the nominal amount used in all subsequent accounting: LP minting in `deposit`, `calc_pnl_x`/`calc_pnl_y` updates, and `total_coin_without_take_pnl`/`total_pc_without_take_pnl` bookkeeping used in `withdraw` and future swaps. [8](#0-7) 
This causes the pool's internal invariant/pnl bookkeeping to diverge from real vault balances, exactly the root cause described in the analogous BvbProtocol report (nominal amount used instead of `balanceAfter - balanceBefore`).

### Impact Explanation
If reachable, the impact is insolvent pool accounting: LPs are minted against phantom deposited liquidity, `calc_take_pnl`/withdraw calculations assume more tokens are present than actually exist in vaults, and later swaps/withdraws can fail with `InsufficientFunds`/`TakePnlError`, or in the worst case allow one side of the pool to be drained relative to actual backing, harming other LPs/swappers. This would qualify as Medium/High under "insolvent pool accounting" if the underlying token program allows fee-on-transfer/deflationary behavior for pool-bound mints.

### Likelihood Explanation
I could not verify — due to running out of tool budget — whether this program's `unpack_token_account`/`unpack_mint` and `spl_token_program_id` validation restrict pools strictly to the legacy `spl_token` program (which has no transfer-fee mechanism and therefore makes this bug class unreachable), or whether Token-2022 mints with the `TransferFeeConfig` extension are permitted for `coin_mint`/`pc_mint` at `Initialize2`/pool-listing time. Classic Raydium AMM V4 historically only supports the legacy SPL Token program for its vaults, which would make this analog **not reachable** and therefore not a valid finding for this program. Given this unresolved but security-relevant precondition, I cannot confirm this as a valid, reachable vulnerability without further verification of the mint/token-program validation logic in `program/src/processor.rs`.

### Recommendation
If Token-2022 or any transfer-fee-capable mint is (or could be) accepted as `coin_mint`/`pc_mint`, either (a) explicitly reject mints with the `TransferFeeConfig` (or any fee-bearing) extension during `Initialize2` and refuse to process deposits/swaps/withdraws for such mints, or (b) compute all deduct/mint/payout amounts from `balance_after - balance_before` measured immediately around each `Invokers::token_transfer`/`token_transfer_with_authority` call, rather than trusting the nominal instruction-derived amount, for `deposit`, `withdraw`, `swap_base_in`, and `swap_base_out` in `program/src/processor.rs`.

### Proof of Concept
Given that reachability (token-program/mint restriction) could not be confirmed, no concrete on-chain PoC transaction sequence can be provided with confidence. If Token-2022 fee-bearing mints are confirmed permitted as pool coin/pc mints, the PoC would be: (1) create a pool with a Token-2022 mint having `TransferFeeConfig` set to e.g. 10%, (2) call `Deposit` with `max_coin_amount = X`; the vault receives `0.9*X` but `mint_lp_amount` is computed from `X`, immediately over-minting LP relative to real backing, provable by comparing `amm_coin_vault_info` balance post-CPI to `deduct_coin_amount` used in the LP-mint calculation at [9](#0-8) .
