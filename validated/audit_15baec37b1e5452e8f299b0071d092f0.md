### Title
Webhook `X-Shopify-Shop-Domain` header is not covered by HMAC verification, allowing cross-tenant shop spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body. The `shop` value that is then handed to the app's handler is read from the `X-Shopify-Shop-Domain` / `shopify-shop-domain` header, which is never included in the signed data. An attacker who owns any real value of a valid `(raw_body, hmac)` pair (e.g. from their own installed shop's genuine webhook delivery) can replay that exact body/HMAC to the app's webhook endpoint while substituting an arbitrary shop domain in the header, and the check will still pass.

### Finding Description
`Utils::HmacValidator.validate` computes the signature only from `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` is defined as just the raw request body — headers, including the shop domain, are excluded from the signed content: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` (parsed straight from the unauthenticated header) to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

The identity binding that should hold is: `shop-domain header == shop that produced/authorizes this HMAC-signed body`. Because the header is outside the signed bytes, that equality is never enforced — only `hmac == HMAC(secret, body)` is checked, independent of which shop domain is claimed in the header. Any actor capable of obtaining one legitimate `(body, hmac)` pair (trivially achievable by installing the app on their own store and triggering any webhook topic they can control the payload for) can resend that same body/HMAC combination with a forged `shop-domain` header pointing at a different, victim tenant.

### Impact Explanation
If the host application uses `WebhookMetadata#shop` (as documented/intended by this gem) to select which tenant's session/config/database row to act on, this break in the header↔signature binding lets an attacker's own attacker-controlled webhook body be attributed to and processed under a different shop's identity — a cross-tenant data integrity/confusion issue. This matches the "Critical - cross-tenant access" impact category, since data intended for one merchant can be forged so the app processes/stores it under another merchant's identity, all without needing `api_secret_key`, an access token, or any credential beyond the ability to install the app on one's own store (an unprivileged-internet-user capability).

### Likelihood Explanation
Likelihood is limited by the fact that this mirrors Shopify's real, documented webhook HMAC scheme (only the body is signed) — this is not a divergence from Shopify's protocol, but the gem does nothing to compensate for it by binding the shop header into the verified data or by cross-checking `request.shop` against a shop known from a prior authenticated session/registration. Any developer relying on `WebhookMetadata#shop` as an authenticated identifier (as its name and the docs imply) is exposed. Exploitation requires only an app installation on an attacker-owned store to legitimately mint one valid `(body, hmac)` pair, then a direct HTTP replay to the app's public webhook endpoint with a modified shop header — no secrets, tokens, or elevated access needed.

### Recommendation
Do not treat `request.shop` (or any other header value) as authenticated merely because `HmacValidator.validate` succeeded. Either:
- Bind the shop domain into the value that is verified (e.g., require callers to reconcile `request.shop` against a shop already associated with a stored/active session before trusting it), or
- Clearly document that `WebhookMetadata#shop` is unauthenticated header data and instruct consuming apps to independently verify shop identity (e.g., against known registered shops) before using it for tenant-scoped operations.

### Proof of Concept
1. Attacker installs the target app on their own development store `attacker.myshopify.com` and enables a webhook topic whose payload content they control (e.g., `orders/create`, setting order fields to attacker-chosen values).
2. Shopify delivers the webhook to the app's endpoint with headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC over raw body>`, and the raw JSON body.
3. Attacker captures this raw body and its accompanying `hmac` value (both attacker-observable since the request lands wherever the app's webhook URL points, which the attacker controls/observes for their own install).
4. Attacker sends a new HTTP request directly to the app's webhook endpoint, reusing the identical raw body and `hmac` header, but replacing `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
5. `Utils::HmacValidator.validate` recomputes the HMAC over the (unchanged) body and it matches, so `Registry.process` proceeds and calls the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker-controlled body>, ...)`, causing the app to process attacker-controlled data as if it originated from `victim-shop.myshopify.com`.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
