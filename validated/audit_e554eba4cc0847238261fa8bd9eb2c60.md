## Title
Webhook shop identity spoofing due to `shop-domain` header not being covered by HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) for a webhook exclusively from the unauthenticated `X-Shopify-Shop-Domain` header, while the HMAC signature that `ShopifyAPI::Webhooks::Registry.process` validates only covers the raw request body. This breaks the equality that should hold: `shop_bound_by_hmac == shop_used_by_handler`. An attacker who legitimately owns any Shopify shop and receives a genuinely-signed webhook for their own store can replay the exact `(raw_body, hmac)` pair to the app's shared webhook endpoint while substituting the `shop-domain` header for a victim shop, and the request will still pass HMAC validation.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from HTTP headers, none of which are part of the signed content: [2](#0-1) 

`ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then dispatches the handler using `request.shop` directly, with no cross-check that the shop is the one the webhook was actually generated for: [3](#0-2) 

`ShopifyAPI::Utils::HmacValidator.validate` computes the HMAC purely over `verifiable_query.to_signable_string` (i.e., the raw body for webhooks) using the app-wide `api_secret_key`, and compares it to the header-provided digest: [4](#0-3) 

Because the `shop` value is not part of the signed bytes, `hmac_valid_for(body)` is true regardless of the `shop-domain` header value. This is exactly the "field acted on but not covered by the HMAC" identity-binding break: the equality `hmac_verified_bytes == bytes_the_handler_trusts_for_shop` does not hold — the HMAC binds only the body, while `WebhookMetadata.shop` (and therefore all downstream per-tenant logic in the host app) is built from an independent, unauthenticated header.

### Impact Explanation
Any internet user who can install the target app on their own (freely obtainable) Shopify development store is a valid, non-privileged webhook source. Such a user can:
1. Capture a genuine `(raw_body, X-Shopify-Hmac-Sha256)` pair that Shopify delivers to the app's webhook endpoint for their own shop (they control the endpoint/log, so no MITM or Shopify credentials are needed).
2. Replay that exact body/HMAC pair to the same shared webhook endpoint, but with the `X-Shopify-Shop-Domain` header rewritten to a victim shop's domain (and optionally a different `topic`/`webhook_id`, also unauthenticated).
3. `HmacValidator.validate` still succeeds because only the (unchanged) body is checked, and `Registry.process` calls the handler with `shop: <victim-domain>` and attacker-controlled body content.

Since apps built on this gem are expected to key persisted data, access tokens, and business logic off `WebhookMetadata#shop`, this allows a malicious tenant to inject attacker-controlled webhook payloads that are processed under an arbitrary victim shop's identity — a cross-tenant confusion/injection primitive reachable purely through this gem's own webhook-processing code path.

### Likelihood Explanation
Requires only owning/installing on any shop (trivially obtainable by any internet user via a free Shopify dev store) and knowledge of the app's webhook endpoint URL, which is typically public/predictable. No access token, `client_secret`, or privileged account for the victim shop is needed. The replay is a straightforward HTTP request forgery once one legitimate webhook has been observed.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the HMAC-signed content, or otherwise cryptographically tie the header-derived shop to the signature — e.g., include the `shop-domain`, `topic`, and `webhook-id` header values in `to_signable_string` in addition to the raw body, matching them against values embedded/verified in the payload, so that any mismatch between the claimed shop and the shop the signature was generated for is rejected by `HmacValidator.validate`.

### Proof of Concept
1. Attacker installs the target app on shop `attacker.myshopify.com` and triggers a webhook event (e.g., `orders/create`) that the app has registered for, capturing the exact raw POST body `B` and the resulting `X-Shopify-Hmac-Sha256: H` header that Shopify sends to the app's webhook endpoint.
2. Attacker crafts a new request to the same endpoint with:
   - Body: `B` (unchanged)
   - Header `X-Shopify-Hmac-Sha256: H` (unchanged)
   - Header `X-Shopify-Shop-Domain: victim.myshopify.com` (changed)
   - Header `X-Shopify-Topic`: unchanged or altered to any registered topic
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only hashes `@raw_body` (`B`) with the app's `api_secret_key`, matching `H`. [5](#0-4) 
4. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: JSON.parse(B), ...)`, causing the host app to process attacker-controlled data under the victim shop's identity.
