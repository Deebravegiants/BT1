### Title
Webhook `shop-domain` header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `#shop` is read from a separate, unauthenticated header (`shopify-shop-domain` / `x-shopify-shop-domain`). `Utils::HmacValidator.validate` (used by `Webhooks::Registry.process`) only verifies that the HMAC matches the raw body; it never verifies that the `shop` header is bound to that HMAC.

### Finding Description
Shopify's HMAC scheme for webhooks signs the raw body, so `Request#to_signable_string` correctly returns `@raw_body`. However, the shop tenant identity that the app relies on to route/attribute the webhook (`request.shop`, sourced from the `shopify-shop-domain` header) is never included in the signed material. `Registry#process` treats a successful `HmacValidator.validate(request)` call as full authentication of the request, then immediately trusts `request.shop` when building `WebhookMetadata` for the app's handler:
```ruby
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
  body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
``` [4](#0-3) 

Because the body-HMAC is valid for *any* value of the `shop-domain` header (the header isn't part of the signed payload), an attacker who can obtain one genuine, HMAC-signed webhook body (e.g., from their own shop where they have installed the app, or from a captured/publicly-known-format webhook payload for a topic with a body shared across merchants) can replay that same body with the HMAC unchanged while substituting an arbitrary `shopify-shop-domain` header value pointing at a *different* merchant's shop. `HmacValidator.validate` will still return `true` because it never inspects the header, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the webhook belongs to the attacker-chosen shop.

The binding that should hold is:
`hmac_signed_bytes == bytes_containing_shop` (i.e., the identity used by the app, `request.shop`, should be provably tied to the same signed bytes verified by `HmacValidator`).

Instead the binding is:
`hmac_signed_bytes == @raw_body` (body only) while `shop` is taken from an independent, unverified header — breaking the equality and allowing the shop-identity field to be forged independently of the signature check.

### Impact Explanation
Any host application built on this gem that uses `WebhookMetadata#shop` (as returned by `Webhooks::Registry.process`) to determine which merchant/tenant a webhook event applies to — e.g., to look up that shop's session/access token, update that shop's records, or make an API call "on behalf of" that shop — can be tricked into acting on data intended for shop A while attributing/crediting it to attacker-chosen shop B, and vice versa. This is a cross-tenant confusion / authentication-bypass class issue: the HMAC check that is supposed to authenticate "this webhook truly originates from Shopify for this shop" no longer authenticates the shop component at all, letting an unprivileged party who can produce (or replay) any valid signed body assert an arbitrary tenant identity for it.

### Likelihood Explanation
Exploitability depends on the attacker being able to produce a raw body whose HMAC they know, e.g., by installing the app on their own store (getting a legitimately-signed webhook for their own shop) and then re-delivering that exact body under a forged `shop-domain` header to the app's webhook endpoint directly (bypassing Shopify's delivery infra, since the gem's `Registry.process` is exposed to raw HTTP input the host app forwards). This requires no possession of `api_secret_key`, no access token, and no privileged account — only the ability to install the app once (a normal, unprivileged merchant action) and then send a crafted HTTP request to the app's own public webhook endpoint. No TLS interception or social engineering is required.

### Recommendation
Include the shop identity (and other headers the app relies on, such as `topic`, `api-version`, `webhook-id`) in the HMAC-signed material, or independently verify that the shop header corresponds to the same request whose body-HMAC was validated (e.g., by having `to_signable_string` incorporate the shop-domain header in a fixed canonical format, or by requiring the host app to separately authenticate the `shop` against a known/allow-listed installed-shop list before trusting it). At minimum, document loudly that `request.shop` is *not* authenticated by `HmacValidator.validate` and must not be trusted as a tenant identity without additional verification.

### Proof of Concept
```ruby
# Attacker installs the app on their own shop "attacker.myshopify.com" and
# receives (or replays) a legitimately HMAC-signed webhook with body "{}"

hmac = OpenSSL::HMAC.digest(
  OpenSSL::Digest.new("sha256"),
  ShopifyAPI::Context.api_secret_key, # not needed by the attacker in practice;
                                       # this HMAC/body pair is captured from a real
                                       # webhook delivery for attacker's own shop
  "{}",
)

forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac),   # unchanged, still valid for body "{}"
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged: not covered by the HMAC
  "x-shopify-webhook-id" => "forged-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: "{}", headers: forged_headers)

# HmacValidator.validate(request) => true, because it only checks the raw body "{}"
ShopifyAPI::Webhooks::Registry.process(request)
# => handler receives WebhookMetadata(shop: "victim-shop.myshopify.com", ...)
#    even though the HMAC never authenticated that shop value.
```
