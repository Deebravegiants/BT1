### Title
Stale `Account.owner` field used for authorization instead of live NFT owner lets the previous owner (and their delegates) retain spending authority after a position NFT transfer - (File: contracts/controller/src/account.rs)

### Summary
The OpenClaw advisory is an allowlist check that trusts a mutable identifier (display name) where an immutable ID was documented. The analog in XOXNO Lending is the account-authorization path: `require_owner_or_delegate` / `is_owner_or_delegate` authorize `caller` against `account.owner` read from the stored `Account` struct (`load_or_create_account` passes `&account.owner` at `contracts/controller/src/account.rs:102` and `:106`), while the canonical ownership record is the position NFT (`require_account_owner` deliberately re-reads the live NFT owner via `storage::account_owner` at `account.rs:143-147` rather than trusting the struct field). If `Account.owner` is only written at account creation and is not restamped on NFT transfer, the stored value acts like the mutable display name: authorization follows the stale field, not the canonical owner.

### Finding Description
`is_owner_or_delegate(env, account_id, caller, owner)` returns true when `caller == owner` or when `caller` is an active manager present in `storage::get_delegates(env, account_id, owner)` (`account.rs:115-127`). Every spend authority path (`borrow`, `withdraw`, `multiply`, `flash_position`, `swap_debt`, `swap_collateral`, `repay_debt_with_collateral`, `migrate_from_blend`) reaches this check through `load_or_create_account` with `owner` taken from `get_account`, i.e., the persisted `Account` struct. By contrast, owner-only flows (`add_delegate`, `remove_delegate`, `renew_account`) go through `require_account_owner`, which ignores `account.owner` and queries `storage::account_owner` — the NFT `owner_of` — and the test `transfer_revokes_prior_owner_and_delegates` confirms `storage::account_owner` tracks live NFT ownership while delegate lists are keyed by the owner address used at grant time. The divergence between "stored struct field" and "live NFT owner" is only safe if `get_account`/`account.owner` is restamped from the NFT on every load or on every transfer; nothing in the reachable code shown performs that restamp, and `require_account_owner`'s explicit re-read strongly suggests `account.owner` is not the canonical source.

### Impact Explanation
If `account.owner` is stale after a `position-nft::transfer`/`transfer_from`, two failures follow: (1) the previous owner and any delegate they granted remain authorized under `is_owner_or_delegate` keyed to the old owner, so they can call `withdraw`/`borrow` on an account they no longer own — theft of the buyer's collateral and unbacked debt; (2) the new owner fails the equality check and is not on the old owner's delegate list, so their own account is unusable for owner-gated verbs — freezing of funds. Either is a Critical/High impact reachable by any unprivileged address that buys or receives a position NFT.

### Likelihood Explanation
NFT transfers are a supported, unprivileged operation (`position-nft::transfer`, `transfer_from`), and the codebase treats NFT ownership as the canonical account ownership ("An NFT transfer moves the account"). The bug triggers on the first owner-gated call after any transfer, so likelihood is high whenever positions change hands. Confidence is bounded: I could not inspect `storage::get_account`/`account_owner` in `contracts/controller/src/storage/account.rs` or the `Account` type in `common/src/types/controller.rs` to confirm whether `account.owner` is a persisted stale field or is always hydrated from `owner_of`; if it is always hydrated live, this finding is void.

### Recommendation
Make all authorization reads single-source: either populate `Account.owner` exclusively from `storage::account_owner` (NFT `owner_of`) inside `get_account`, or change `require_owner_or_delegate`/`is_owner_or_delegate` to resolve the owner via `storage::account_owner` exactly as `require_account_owner` does, and key delegate lists by the live owner. Add a regression test that transfers the NFT and asserts the previous owner and their delegates fail `borrow`/`withdraw` while the new owner passes.

### Proof of Concept
1. Alice opens an account via `supply` (NFT minted to Alice) with collateral and headroom to borrow.
2. Alice calls `add_delegate(caller=alice, account_id, delegate=manager)` for an active position manager.
3. Alice calls `position-nft::transfer(from=alice, to=bob, token_id=account_id)`.
4. With the stale-field bug, `storage::account_owner` returns Bob but `account.owner` still equals Alice.
5. Alice (or `manager`) calls `withdraw(caller=alice_or_manager, account_id, withdrawals=[...], to=Some(attacker_addr))`; `require_owner_or_delegate` compares against stale `account.owner == alice` and passes, draining collateral the NFT buyer owns. Bob's own `withdraw` reverts with `NotAuthorized`.
