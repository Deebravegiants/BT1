### Title
Panic-inducing unchecked-length `copy_from_slice` in `HyperFungibleToken::on_accept` — attacker-controlled `message.from` crashes `on_accept` for non-EVM sources - (File: modules/pallets/hyper-fungible-token/src/module.rs)

### Summary
`Pallet::on_accept` (the `IsmpModule` handler invoked whenever a `PostRequest` is delivered to the hyper-fungible-token pallet) decodes an ABI-encoded `Message` from an untrusted, relayer-delivered request body and, for the "no signature" calldata-dispatch path with a non-EVM `source`, copies the attacker-controlled `message.from` bytes into a fixed 32-byte array using `copy_from_slice` without first validating the length. `copy_from_slice` panics on any length mismatch. This mirrors the reported bug class exactly: an untrusted, variable-length wire field copied into a fixed-size destination via an unchecked, panicking/overflowing copy primitive, reachable before authorization/consistency checks reject the malformed input.

### Finding Description
`on_accept` decodes the message body with `Message::abi_decode(&body)` [1](#0-0) . The `to` field is correctly length-checked before being copied into a fixed buffer: [2](#0-1) 

However, later in the same function, when calldata is present and no signature was supplied, the destination-side account for a non-EVM source is derived from `message.from` with **no length check at all**: [3](#0-2) 

`message.from` is a field of the Solidity ABI-encoded `Message` struct that is fully controlled by whoever calls the source-chain bridge contract to initiate the transfer — it is not validated to be 32 bytes anywhere before this point (unlike `to_bytes`, which is validated at lines 65-71). If `source.is_evm()` is false (i.e., the request's source state machine is not an EVM chain — reachable whenever the pallet is configured to accept token transfers from a non-EVM source, e.g. a Substrate/Cosmos-family chain), execution reaches `account.copy_from_slice(from_bytes)` with `from_bytes.len() != 32`, which panics.

This is directly analogous to the Sandboxie `wcscpy(dst, boxname)` bug: a fixed-size destination buffer is filled from an attacker-supplied, length-unchecked source field, and the copy executes before any authorization/consistency check would otherwise reject the malformed packet. Here, the "authorization" analog (asset/contract mapping lookup via `ContractToAsset`) has already passed by the time the vulnerable copy executes, and the only thing standing between the attacker and the panic is the unenforced assumption that ABI-encoded `bytes` fields are always exactly 32 bytes.

### Impact Explanation
`on_accept` is invoked from ISMP's request-delivery path when processing `Message::Request` messages inside `pallet_ismp::Pallet::execute`, which is reachable via the permissionless, fee-less `handle_unsigned` extrinsic (validated in `ValidateUnsigned::validate_unsigned` and dispatched via `Call::handle_unsigned`) [4](#0-3) . A Rust panic surfacing during WASM runtime execution of a block (or during unsigned-transaction validation in the transaction pool) is not a recoverable `Result::Err` — it is a WASM trap that aborts the current runtime call. Triggered during block execution this can force nodes to reject/re-fail the block; triggered during `validate_unsigned` on every full node's mempool it can be used to repeatedly abort transaction-pool validation for whichever node processes the malicious pending extrinsic. This matches the report's "route unable to deliver messages" / crash-of-service outcome: a single relayer-submitted message can disrupt the hyper-fungible-token bridge module (and the shared ISMP dispatch pipeline it runs inside) for any node that attempts to apply it, effectively freezing token delivery for that route until an admin intervenes.

### Likelihood Explanation
The precondition is that the destination pallet is configured to accept `PostRequest`s from at least one non-EVM `source` state machine (the pallet's `ContractToAsset` mapping is generic over `StateMachine`, not restricted to EVM). Given such a mapping exists, any party able to get an ISMP `PostRequest` proven and delivered from that source (a normal token-bridge user flow, or a relayer replaying/crafting a request whose commitment matches a source-chain event) can set the ABI-encoded `Message.from` field to any length other than 32 bytes and omit `substrate_data.signature`, driving execution into the vulnerable branch. No special privilege beyond "submit an ISMP message with a valid proof from a configured source" is required — matching the "unprivileged relayer/message dispatcher" reachability required by scope.

### Recommendation
Validate `from_bytes.len()` before copying, mirroring the existing `to_bytes` handling:
```rust
let from_bytes = message.from.as_ref();
if source.is_evm() {
    ...
} else {
    if from_bytes.len() != 32 {
        Err(HftError::InvalidSenderLength(from_bytes.len()))?;
    }
    let mut account = [0u8; 32];
    account.copy_from_slice(from_bytes);
    account.into()
}
```
Alternatively use `TryFrom<&[u8]>`/`try_into()` and map failures to a proper `HftError` variant, consistent with the pattern already used elsewhere in this same function (e.g. lines 134-137, 145-148) and in `modules/utils/serde/src/lib.rs` (`as_utf8_string::deserialize`), which was itself hardened against this exact panic-on-length-mismatch class for `consensus_state_id`.

### Proof of Concept
1. Configure the `hyper-fungible-token` pallet's `ContractToAsset` mapping for a non-EVM `source` state machine (e.g. a Substrate-based `StateMachine` variant) and a given source contract/address.
2. From that source chain, initiate a token transfer whose bridge-contract call ABI-encodes a `Message` where:
   - `to` is a valid 32-byte (or 20-byte) recipient,
   - `data` is non-empty and decodes to a `SubstrateCalldata` with `signature: None`,
   - `from` is set to a byte string of any length other than 32 (e.g., 0, 1, or 33 bytes) — trivially achievable since ABI `bytes` fields carry no length constraint.
3. Have the resulting ISMP `PostRequest` relayed and delivered to the destination chain via `Ismp::handle_unsigned` with a valid membership proof.
4. During `Pallet::execute` → `on_accept`, execution reaches `account.copy_from_slice(from_bytes)` with `from_bytes.len() != 32`, panicking and aborting execution of the extrinsic/block on every node that processes it.
