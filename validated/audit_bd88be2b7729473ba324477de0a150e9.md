### Title
Cumulative rounding drift in PnL accounting can make `need_take_pnl_pc`/`need_take_pnl_coin` exceed vault balances, permanently reverting `calc_total_without_take_pnl_no_orderbook` and bricking swap/deposit/withdraw/withdrawpnl - (File: program/src/processor.rs, program/src/math.rs)

### Summary
The reported bug class is a subtraction that can underflow due to an accumulator drifting past the value it is subtracted from, permanently reverting a core price/accounting function. In this codebase the analogous accumulator is `AmmInfo.state_data.need_take_pnl_pc` / `need_take_pnl_coin`, which is subtracted from live vault balances in `Calculator::calc_total_without_take_pnl_no_orderbook` [1](#0-0) . This function is called at the start of every swap, deposit, withdraw, and withdrawpnl instruction [2](#0-1) [3](#0-2) [4](#0-3) . If `need_take_pnl_pc`/`need_take_pnl_coin` ever exceeds the actual vault balances, this subtraction fails via `.ok_or(AmmError::CheckedSubOverflow)` and **every** subsequent instruction on the pool (including `withdrawpnl`, the only path that could otherwise reset the accumulator) reverts, permanently freezing the pool.

### Finding Description
`calc_take_pnl` computes a PnL "profit" portion whenever the pool's constant-product `k` grows, and cumulatively adds it into `amm.state_data.need_take_pnl_pc` / `need_take_pnl_coin` via `checked_add` [5](#0-4) . These accumulators are only ever incremented in `calc_take_pnl` (called from deposit, withdraw, and withdrawpnl) and are only reset to zero inside `process_withdrawpnl`, itself gated by `calc_total_without_take_pnl_no_orderbook` succeeding first [6](#0-5) , [7](#0-6) .

The pnl-delta computation relies on chained fixed-point conversions (`normalize_decimal_v2`, `restore_decimal`, integer square roots, and truncating integer division) across mismatched coin/pc decimals and `sys_decimal_value` scaling [8](#0-7) . Every one of these steps truncates towards zero rather than being conservatively rounded down for the accumulator side, so successive deposit/withdraw calls compound a small but systematic rounding bias into `need_take_pnl_pc`/`need_take_pnl_coin`. Because vault balances (`amm_pc_vault.amount`, `amm_coin_vault.amount`) are the actual, non-inflatable source of truth, while `need_take_pnl_*` is a purely internal counter driven by repeated approximate math, there is no invariant in the code that mathematically guarantees `need_take_pnl_pc <= amm_pc_vault.amount` and `need_take_pnl_coin <= amm_coin_vault.amount` at all times — it is only checked reactively in `process_withdrawpnl` (`if amm.state_data.need_take_pnl_coin <= amm_coin_vault.amount && ...`) and only after `calc_total_without_take_pnl_no_orderbook` has already succeeded [9](#0-8) .

Once accumulated drift pushes `need_take_pnl_pc` or `need_take_pnl_coin` past the corresponding vault balance, `calc_total_without_take_pnl_no_orderbook`'s `checked_sub(...).ok_or(AmmError::CheckedSubOverflow)` fails unconditionally [10](#0-9) . Since this call is the very first accounting step in `swap_base_in`, `swap_base_out`, `deposit`, `withdraw`, and `withdrawpnl`, the entire pool becomes permanently unusable — mirroring the reported pattern where an unrecoverable subtraction underflow bricks all price/trade paths, with the added severity here that `withdrawpnl` (the only recovery mechanism) is itself gated behind the same failing call, so there is no in-protocol way to reset the counters.

### Impact Explanation
This is a full, permanent denial of service on a live pool: all four swap instructions, `Deposit`, `Withdraw`, and `WithdrawPnl` all begin by calling `calc_total_without_take_pnl_no_orderbook`, so a single triggering event freezes all trading and all liquidity withdrawal for every LP and swapper in the pool, with funds locked in the vaults with no callable instruction path to recover them (matching "permanent freezing of user or LP funds").

### Likelihood Explanation
Likelihood depends on how much rounding drift accrues per deposit/withdraw over the pool's lifetime relative to the safety margin between `need_take_pnl_*` and vault balances (which itself shrinks whenever `withdrawpnl` is not called often, since the counters keep growing). This requires many normal deposit/withdraw cycles over time rather than a single crafted transaction, and I could not fully trace bounds proving the drift is unidirectional/large enough to trigger under realistic parameters within the scope of this review, so likelihood should be treated as uncertain pending deeper numerical analysis of `normalize_decimal_v2`/`restore_decimal` rounding behavior — flagged here as the closest structural analog to the reported bug rather than a fully proven exploit.

### Recommendation
- Add an explicit invariant check in `calc_take_pnl` before growing `need_take_pnl_pc`/`need_take_pnl_coin`, clamping to the actual pc/coin surplus available (vault balance) rather than trusting the derived approximation.
- Ensure `restore_decimal`/`normalize_decimal_v2` round in the direction that is always conservative for accumulator growth (round down profit taken, not up), so the accumulators never overtake the real backing balances.
- Add a dedicated, permissioned recovery instruction that can reset/clamp `need_take_pnl_pc`/`need_take_pnl_coin` to vault balances without going through the normal `calc_total_without_take_pnl_no_orderbook` gate, so the pool cannot be permanently bricked.

### Proof of Concept
Not concretely constructed — a full PoC would require simulating many deposit/withdraw cycles with adversarially chosen decimals/amounts to accumulate rounding drift in `need_take_pnl_pc`/`need_take_pnl_coin` past `amm_pc_vault.amount`/`amm_coin_vault.amount`, then showing the subsequent revert of `calc_total_without_take_pnl_no_orderbook` on all instructions including `withdrawpnl`. This was not verified experimentally within this review; see the "Likelihood Explanation" caveat.

```rust
    pub fn calc_total_without_take_pnl_no_orderbook<'a>(
        pc_amount: u64,
        coin_amount: u64,
        amm: &'a AmmInfo,
    ) -> Result<(u64, u64), AmmError> {
        let total_pc_without_take_pnl = pc_amount
            .checked_sub(amm.state_data.need_take_pnl_pc)
            .ok_or(AmmError::CheckedSubOverflow)?;
        let total_coin_without_take_pnl = coin_amount
            .checked_sub(amm.state_data.need_take_pnl_coin)
            .ok_or(AmmError::CheckedSubOverflow)?;
        Ok((total_pc_without_take_pnl, total_coin_without_take_pnl))
    }
```
