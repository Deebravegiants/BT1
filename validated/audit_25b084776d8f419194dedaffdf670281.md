### Title
Webhook shop attribution is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook by validating an HMAC that covers only the raw request body, while the `shop` (tenant identity) that the handler acts on is read from an unauthenticated HTTP header. This breaks the binding: `shop_the_handler_trusts == shop_covered_by_the_HMAC`, since the HMAC never actually covers the shop field.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`ShopifyAPI::Webhooks::Registry.process` validates the HMAC against this signable string, and — if valid — hands the `shop` value (read straight from the `x-shopify-shop-domain`/`shopify-shop-domain` header, with no cryptographic binding) to the merchant's webhook handler via `WebhookMetadata`: [2](#0-1) 

`Request#shop` simply reads the header value with no validation against the signed body: [3](#0-2) 

`WebhookMetadata.shop` is the only tenant-identifying field passed to the handler, and handlers are expected to use it to route/act on data for a specific merchant: [4](#0-3) 

The identity equality this code implicitly assumes is: *"the shop this request claims to be from" == "the shop whose credentials/secret produced this HMAC."* Because the HMAC is computed over `@raw_body` only, that equality never holds — the same signature is valid for the same body regardless of which `shop-domain` header value accompanies it.

### Impact Explanation
An attacker who controls (or has installed the app on) their own Shopify store, Shop A, receives genuine Shopify-signed webhooks for Shop A (valid HMAC over the body, computed with the app's real secret by Shopify's servers). Because the header carrying the shop domain is excluded from the signed bytes, the attacker can capture such a webhook and replay it to the app's webhook endpoint with the `x-shopify-shop-domain` header rewritten to Shop B (the victim). `Utils::HmacValidator.validate` still succeeds (it only checks the body bytes), so `Registry.process` will invoke the handler with `WebhookMetadata.shop == "shop-b.myshopify.com"` even though the body/HMAC never originated for Shop B. Any handler logic that uses `data.shop` to select which merchant's data/session to operate on (a documented, expected usage pattern per `docs/usage/webhooks.md` and `WebhookMetadata`) will process attacker-controlled body content under a victim tenant's identity — a cross-tenant data-integrity/confusion issue.

### Likelihood Explanation
Exploitation requires the attacker to be an unprivileged internet user who can install the app on their own store (a routine, credential-free action for any public Shopify app) and can freely target the app's public webhook endpoint with arbitrary headers/body combinations; no access token, `api_secret_key`, or privileged account is needed, since only reuse of a body+HMAC pair the attacker legitimately received for their own shop is required. The gem's own `Request`/`Registry` code path performs no cross-check between the authenticated bytes and the claimed shop, making this reachable in every consumer of this library's webhook processing.

### Recommendation
Bind the shop identity into the material that is HMAC-verified, or otherwise cryptographically tie the `shop-domain` header to the request body — for example, by including the shop domain in the signable string, or by requiring/verifying the shop against a value obtained from a source that is itself authenticated (e.g., a per-shop webhook secret or the value returned from a prior authenticated session lookup) rather than trusting the raw header value once body-only HMAC validation succeeds.

### Proof of Concept
```ruby
# Attacker owns Shop A and has installed the app; Shopify sends a genuine,
# correctly HMAC-signed webhook for Shop A:
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, '{"malicious":"payload"}')

headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac),
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # attacker rewrites this header
  "x-shopify-webhook-id" => "attacker-controlled-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: '{"malicious":"payload"}', headers: headers)

# Validation succeeds because the HMAC only ever covered the raw body:
ShopifyAPI::Utils::HmacValidator.validate(request) # => true

# The handler is invoked believing this data is authoritatively from victim-shop:
ShopifyAPI::Webhooks::Registry.process(request)
# handler.handle(data: WebhookMetadata(shop: "victim-shop.myshopify.com", body: {"malicious"=>"payload"}, ...))
```

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,

        end
