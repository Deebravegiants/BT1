### Title
Webhook HMAC only signs the request body, not the `shop-domain` header, allowing shop-identity spoofing in `ShopifyAPI::Webhooks::Registry.process` - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, so `Utils::HmacValidator.validate` never binds the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header to the signature. Any party who can obtain one valid `(body, hmac)` pair for the app (e.g. by installing the app on their own store and receiving a genuine webhook) can resend that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary victim shop domain in the `shop-domain` header. `Registry.process` accepts the request as authentic and forwards the attacker-chosen `shop` value to the app's handler.

### Finding Description
The binding that should hold is: `shop value trusted by the handler == shop value cryptographically bound by the HMAC`. In this gem that equality is broken.

- `Request#to_signable_string` signs only `@raw_body`: [1](#0-0) 
- `Request#shop` is read straight from an attacker-controllable header, entirely outside the signed material: [2](#0-1) 
- `HmacValidator.validate_signature` recomputes the HMAC purely from `to_signable_string` (the body) and compares it to the supplied `hmac`, never touching `shop`, `topic`, or `webhook_id`: [3](#0-2) 
- `Registry.process` treats a passing HMAC check as proof of authenticity for the *entire* request and then dispatches `request.shop` (the unbound header) directly to the app's handler: [4](#0-3) 

Because every shop installed on the same app shares the identical `Context.api_secret_key`, any legitimate merchant/user of the app can capture one authentic `(body, hmac)` pair delivered to their own store, then POST that same pair straight to the app's public webhook endpoint with the `shop-domain` header rewritten to a victim shop. `HmacValidator.validate` still returns `true` because it only checks the body, and `Registry.process` will invoke the handler believing the event originated from the victim shop.

### Impact Explanation
This breaks the tenant-isolation boundary the HMAC check is supposed to enforce: an attacker who legitimately installed the app on shop A can make the host application process a webhook "as if" it came from shop B, without ever possessing shop B's credentials. Depending on what the app's webhook handlers do (e.g., look up/mutate data keyed by `shop`, trigger notifications, sync inventory, disable features), this enables cross-tenant data confusion/access driven entirely by an unprivileged internet user who merely installed the app once.

### Likelihood Explanation
Likelihood is meaningful but not trivial: the attacker must (1) install the target app on a shop they control (normal, unprivileged action for any public app), (2) capture one real webhook delivery (trivial — just observe their own endpoint traffic), and (3) resend it directly to the app's webhook URL with a modified `shop-domain` header, bypassing Shopify's delivery infra. All three steps require nothing more than standard HTTP tooling and no special credentials, secrets, or social engineering.

### Recommendation
Include the `shop-domain` (and ideally `topic`/`webhook-id`) header values in the signed/verified material, or otherwise independently confirm that `request.shop` corresponds to a shop session actually associated with the client that owns the currently configured `api_secret_key`/webhook subscription before dispatching to handlers. At minimum, document that `HmacValidator.validate` only authenticates the body and that consumers must not trust `request.shop` for tenant-sensitive logic without additional verification (e.g., checking against a known/registered shop list).

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`, receiving genuine webhook deliveries signed with the app's `api_secret_key`.
2. Attacker captures one such delivery: raw body `B` and header `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC-SHA256(secret, B)` per `Request#to_signable_string`/`HmacValidator.compute_signature`).
3. Attacker sends a new HTTP POST directly to the app's webhook endpoint with:
   - Body: `B` (unchanged)
   - Header `X-Shopify-Hmac-Sha256: H` (unchanged)
   - Header `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (rewritten)
   - Header `X-Shopify-Topic`: same or different registered topic.
4. `Webhooks::Request.new` parses headers/body normally; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC from `B` only and matches `H` — validation passes.
5. `Registry.process` invokes the registered handler with `shop: "victim-shop.myshopify.com"`, `body: parsed_body_of_B`, even though this data never came from Shopify on behalf of that shop. [4](#0-3) [5](#0-4) [6](#0-5)

module ShopifyAPI
  module Webhooks
    class Request
      extend T::Sig
      include Utils::VerifiableQuery

      sig { override.returns(String) }
      def hmac

      end

      sig { returns(String) }
      def topic

      end

      sig { returns(String) }
      def shop

      end

      sig { returns(String) }
      def api_version
        T.cast(shopify_header("api-version"), String)
      end

      sig { returns(String) }
      def webhook_id
        T.cast(shopify_header("webhook-id"), String)
      end

      sig { override.returns(String) }
      def to_signable_string
        @raw_body
      end

      sig { returns(T::Hash[String, T.untyped]) }
      def parsed_body
        JSON.parse(@raw_body)
      end

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

      private

      sig { params(name: String).returns(T.untyped) }
      def shopify_header(name)
        @headers["shopify-#{name}"] || @headers["x-shopify-#{name}"]
      end
    end
  end
end

# typed: strict

module ShopifyAPI
  module Utils
    module HmacValidator
      extend T::Sig

      class << self
        extend T::Sig

        sig { params(verifiable_query: VerifiableQuery).returns(T::Boolean) }
        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end

        sig { params(signable_string: String, secret: String).returns(String) }
        def compute_signature(signable_string, secret)
          OpenSSL::HMAC.hexdigest(
            OpenSSL::Digest.new("sha256"),
            secret,
            signable_string,
          )
        end
      end
    end
  end
end
