### Title
Webhook HMAC only covers the request body, not the `shop`, `topic`, or `webhook-id` headers, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, and `Utils::HmacValidator` verifies the HMAC exclusively over that body. The `shop`, `topic`, `api_version`, and `webhook_id` values are read straight from unauthenticated HTTP headers and passed downstream unchecked once the body HMAC passes. Any actor able to produce one validly-signed webhook body for the app (e.g., a merchant who installs the app on their own store and thus receives genuine, correctly-signed webhooks, since the HMAC secret is the app's single `client_secret` shared across every shop using the app) can replay that same body with a **different `shop-domain`, `topic`, or `webhook-id` header**. The library still reports `Utils::HmacValidator.validate` as `true` and dispatches the handler with the attacker-chosen `shop`/`topic`, breaking the binding between "the tenant whose secret-authenticated bytes we verified" and "the tenant the handler is told this event belongs to."

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 

which returns only `@raw_body`. `HmacValidator.validate` computes and compares HMAC over exactly that signable string: [2](#0-1) 

Meanwhile, `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are parsed directly from HTTP headers with no cryptographic binding to the body or to each other: [3](#0-2) 

`Registry.process` validates only the HMAC of the body, then unconditionally trusts these header-derived fields to route the event and build the `WebhookMetadata` object handed to the app's handler: [4](#0-3) 

The equality the library implicitly (and incorrectly) treats as verified is:
`hmac_valid(body, api_secret_key) == true` ⟺ `(shop, topic, webhook_id)` are authentic for that body.

In reality the correct binding should be `hmac_valid(body ‖ shop ‖ topic ‖ webhook_id, api_secret_key) == true`. Because `shop`/`topic`/`webhook_id` sit outside the signed payload, and because the same `api_secret_key` is used to validate webhooks for every shop that has installed the app (it is the app's secret, not a per-shop secret), an attacker who is a legitimate merchant on Shop A can:
1. Install the app on their own Shop A and receive a real, validly-HMAC'd webhook (body `B`, HMAC `H`, for topic `T1`).
2. Replay `B`/`H` to the app's webhook endpoint but with headers rewritten to `shop-domain: shop-b.myshopify.com` and/or `topic: <different mandatory/privileged topic>`.
3. `Utils::HmacValidator.validate` still returns `true` (it only checks `B` against `H`), so `Registry.process` dispatches the app's handler with `WebhookMetadata(topic: <attacker-chosen>, shop: "shop-b.myshopify.com", body: B, ...)`.

Any app handler that trusts `data.shop` from `WebhookMetadata` to select which tenant's stored session/access token to act on, or trusts `data.topic` to decide the operation to perform, can now be tricked into performing tenant-B-scoped actions driven by attacker-controlled body content that was never actually sent by Shopify for shop B — a cross-tenant confusion entirely within this gem's own verification boundary, not a host-app misuse of a documented API.

### Impact Explanation
This crosses the tenant boundary this gem exists to enforce: it lets one merchant's genuinely-signed webhook be relabeled as belonging to a different shop or topic while still passing `HmacValidator.validate`. Because the same `api_secret_key` authenticates webhooks for all shops on the app, this is not merely "the host app trusted an unauthenticated header" in the abstract — the gem's own `Registry.process` API returns success/dispatches the handler for a payload whose claimed `shop`/`topic`/`webhook_id` were never actually verified, meeting the "cross-tenant access" Critical bar defined in scope.

### Likelihood Explanation
Any user can become a legitimate merchant of a shop that installs the target app and thereby obtain at least one genuinely-signed webhook body/HMAC pair for that app's shared secret. Replaying it with modified headers to the same public webhook endpoint requires no secret knowledge — only that the header-checking logic in `Request`/`Registry` never re-validates `shop`/`topic`/`webhook_id` against the signed body.

### Recommendation
Extend `Request#to_signable_string` (or add a separate integrity check in `Registry.process`) to bind `shop`, `topic`, and `webhook_id` into the value verified against the HMAC, or otherwise require the caller to independently confirm that the `shop` header matches an expected/registered shop for the session context before dispatching the handler. At minimum, document prominently that `request.shop`/`request.topic` are not covered by the HMAC and must not be trusted for tenant routing without additional verification.

### Proof of Concept
```ruby
# Attacker owns shop-a.myshopify.com and has the app installed there,
# so Shopify sends them a real, validly-signed webhook:
real_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => real_hmac_b64,   # computed by Shopify over `raw_body`
  "x-shopify-shop-domain" => "shop-a.myshopify.com",
  "x-shopify-webhook-id" => "real-id",
}

# Attacker replays the *same* raw_body/hmac but forges shop + topic:
forged_headers = {
  "x-shopify-topic" => "app/uninstalled",          # different, possibly privileged topic
  "x-shopify-hmac-sha256" => real_hmac_b64,         # unchanged: HMAC is only over raw_body
  "x-shopify-shop-domain" => "shop-b.myshopify.com", # victim shop, never actually sent this
  "x-shopify-webhook-id" => "real-id",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: real_raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => Utils::HmacValidator.validate(request) is true (body/HMAC match),
#    handler.handle is invoked with WebhookMetadata(shop: "shop-b.myshopify.com", topic: "app/uninstalled", ...)
```
