This confirms the root cause: `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from unauthenticated HTTP headers [2](#0-1) . `Registry.process` validates the HMAC only against the body, then dispatches to the handler using the unverified `request.shop`/`request.topic` values [3](#0-2) , and this `shop` is delivered straight to the app's `WebhookHandler.handle` as the tenant identifier [4](#0-3) , which documentation explicitly tells developers to trust for tenant-scoped actions such as `shop_domain: data.shop` [5](#0-4) .

### Title
Webhook shop/topic identity not bound by HMAC, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` signs only the raw request body with HMAC-SHA256, but the `shop-domain`, `topic`, `webhook-id`, and `api-version` values used by `Registry.process` to route and attribute the webhook to a tenant are taken from unauthenticated HTTP headers that are never included in the signable content.

### Finding Description
The equality that should hold is: `hmac_verifies(raw_body) == identity_of(shop, topic)`. In reality: `to_signable_string` returns only `@raw_body` [6](#0-5) , and `HmacValidator.validate` computes the signature purely from `to_signable_string` [7](#0-6) . The `shop` accessor is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header without any cryptographic binding to the signed body [8](#0-7) .

`Registry.process` only checks `Utils::HmacValidator.validate(request)` (i.e., body integrity) before using `request.shop` and `request.topic` — both unauthenticated fields — to select the handler and populate `WebhookMetadata` passed to the app [9](#0-8) .

Since the api_secret_key (used to compute the HMAC) is shared across *all* shops installing the same app, any shop that has legitimately installed the app receives real, validly-signed `(body, hmac)` pairs from Shopify. An attacker controlling one such installed/malicious shop can capture one of their own legitimate webhook deliveries (body + valid hmac) and replay that exact body/hmac pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. Because `shop` is not part of the signed content, `HmacValidator.validate` still returns true, and the forged request is processed as if it originated from the victim shop.

### Impact Explanation
This breaks the binding between "the shop whose secret produced this valid signature" and "the shop the application attributes/acts on for this webhook", enabling cross-tenant impersonation of webhook events for any shop installed on the same app — matching the Critical "cross-tenant access" impact category. Any host application that follows the documented pattern of trusting `data.shop` for tenant-scoped side effects (queueing jobs, updating tenant records, deletion/redaction flows, etc., as the gem's own webhooks doc recommends) can be tricked into performing those actions against an arbitrary other tenant.

### Likelihood Explanation
Medium-High: it requires the attacker to control (or compromise) at least one shop that has installed the target app — an unprivileged party relative to other tenants of the same multi-tenant app — and to capture one legitimate webhook delivery from their own shop (trivially done by inspecting their own app's inbound requests/logs, which they fully control). No access to `api_secret_key`, access tokens, or other shops' credentials is required.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the value verified by HMAC, e.g., by including the `x-shopify-shop-domain` header (and other routing headers) in `to_signable_string`, or by independently verifying that `request.shop` matches a shop associated with a previously-established, verifiable relationship (such as a stored session/access-token record) before dispatching to the handler.

### Proof of Concept
1. Attacker installs the target app on shop `attacker-shop.myshopify.com` and receives a real webhook: raw body `B` with a valid `x-shopify-hmac-sha256` header `H` (computed over `B` with the app's shared `api_secret_key`) and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker POSTs to the app's webhook endpoint with the same body `B` and same `hmac-sha256` header `H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and, if desired, a different `x-shopify-topic`/`x-shopify-webhook-id` not present in signed content).
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `to_signable_string` (= `B`) and succeeds since `B` and `H` are unchanged [10](#0-9) .
4. The app's `WebhookHandler.handle` is invoked with `WebhookMetadata` where `shop == "victim-shop.myshopify.com"`, even though the event actually never originated from Shopify for that shop [11](#0-10) .
