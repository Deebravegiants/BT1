### Title
Webhook `shop-domain` header is trusted to identify the tenant but is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable payload as the raw HTTP body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values used by `Registry.process` to route and attribute the webhook are all pulled from unauthenticated HTTP headers. Since `Context.api_secret_key` is a single app-wide secret shared across every shop that installs the app (not a per-shop secret), the HMAC only proves "this body was produced with this app's secret" — it proves nothing about which shop the body belongs to.

### Finding Description
`Request#to_signable_string` returns `@raw_body` only: [1](#0-0) 

Meanwhile `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are read directly from HTTP headers (`shopify-shop-domain`, `shopify-topic`, etc.) with no cryptographic binding to the body or the HMAC: [2](#0-1) 

`Registry.process` validates only the HMAC of the raw body, then immediately trusts `request.shop` and `request.topic` (both header-derived, unauthenticated) to build the `WebhookMetadata` handed to the app's handler: [3](#0-2) 

The HMAC check itself uses `Context.api_secret_key`, which is the app's single `client_secret` — the same value for every shop that has installed the app: [4](#0-3) 

This is exactly the "field acted on but not covered by the HMAC" identity-binding break described in the prompt rules, and it is structurally the same defect class as the analog report: two independently-trusted pieces of state (`hmac`-validated body vs. header-derived `shop`) are never checked for consistency, so the invariant "this body belongs to this shop" is never actually enforced by the library.

**Equality that should hold but doesn't:** `hmac == HMAC(secret, body ‖ shop)` is required for correctness, but the library only checks `hmac == HMAC(secret, body)`, independent of `shop`.

### Impact Explanation
Because the app secret is shared across all tenants, an attacker who legitimately installs the target app on their own store (a normal, unprivileged action any merchant can do) can capture one real, validly-signed webhook body+HMAC pair for their own shop (e.g. via `orders/create` on a test order). They can then replay that exact `raw_body`/`X-Shopify-Hmac-Sha256` pair to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. `HmacValidator.validate` still succeeds (it only checks the body), and `Registry.process` dispatches the forged payload to the app's handler tagged as coming from the victim shop. This lets one tenant inject attacker-controlled webhook data into another tenant's data flow inside the host app — a cross-tenant identity/data confusion enabled entirely by this gem's `Webhooks::Request`/`Registry` implementation, not by host-app misuse.

### Likelihood Explanation
Requires only: (1) the ability to install the target app on an attacker-controlled shop (available to any Shopify merchant/developer, no special privilege), and (2) the ability to send an arbitrary HTTP POST with custom headers to the app's public webhook endpoint (the standard, documented way webhooks are delivered — no TLS interception, no leaked credentials, no access token needed). Both preconditions are trivially satisfiable by an "unprivileged internet user" as defined by the scope rules.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the signed material, or otherwise cryptographically tie the header-derived tenant identity to the verified body — e.g., include the shop domain in `to_signable_string`, or (better, matching Shopify's actual webhook model) verify the signature and independently confirm that the resulting shop maps to a session/install actually holding that domain before trusting `request.shop`. At minimum, document and enforce that `Registry.process` must correlate `request.shop` against a known, previously-established session/shop record rather than treating the header value as ground truth.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com`, which uses the same `client_secret` (`Context.api_secret_key`) as every other installation.
2. Attacker triggers a real webhook (e.g., `orders/create`) and captures `raw_body` and the `X-Shopify-Hmac-Sha256` header Shopify sent them — this HMAC is valid because `HmacValidator.validate_signature` only signs `raw_body`: [5](#0-4)  and [1](#0-0) .
3. Attacker POSTs the same `raw_body` and `X-Shopify-Hmac-Sha256` to the app's webhook endpoint but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and any `X-Shopify-Topic`/`Webhook-Id` they like).
4. `Registry.process` calls `Utils::HmacValidator.validate(request)` — passes, since only the body is checked: [6](#0-5) .
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and the attacker-controlled body, believing it originated from the victim tenant: [7](#0-6) .
