### Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates only the raw webhook body via HMAC, while the `shop` attribute used to attribute the webhook to a tenant is read directly from an unauthenticated HTTP header. This breaks the identity binding `shop authenticated by HMAC == shop attributed to the processed data`.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`, and `hmac` is derived from the `hmac-sha256`/`x-shopify-hmac-sha256` header: [1](#0-0) [2](#0-1) 

`request.shop`, however, is read straight from the `shop-domain`/`x-shopify-shop-domain` header, which is never included in the signable string: [3](#0-2) 

`Registry.process` validates the HMAC over the body only, then forwards `request.shop` (the unauthenticated header value) directly to the app's handler via `WebhookMetadata`: [4](#0-3) 

The `HmacValidator.validate` call only checks `verifiable_query.to_signable_string` (the body) against the HMAC secret — it never checks that the `shop` field is consistent with, or covered by, that signature: [5](#0-4) 

Because the webhook endpoint is a public HTTP endpoint (that's the entire reason HMAC verification exists instead of relying on network-level trust), any actor who can obtain one legitimately-signed `(raw_body, hmac)` pair — for example a merchant installing the same app on their own store, who receives real webhooks for their own shop with a valid HMAC over the body — can replay that exact body and HMAC to the app's public webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header. `HmacValidator.validate` will still succeed, since it only checks the body, and `Registry.process` will hand the (attacker-chosen) `shop` value to the app's webhook handler as if it were authenticated.

This is precisely the "field acted on but not covered by the HMAC" identity-binding break: the equality `shop verified by signature == shop passed to the handler as the tenant key` does not hold. The HMAC proves the byte-for-byte body is unmodified and was produced with knowledge of `api_secret_key`; it proves nothing about which shop the header claims the payload belongs to.

### Impact Explanation
An attacker who is a legitimate (but unprivileged relative to other tenants) user of a multi-tenant app can cause the host application to process attacker-supplied webhook data under another merchant's (`shop`) identity — e.g., trigger `orders/create`/`customers_data_request`-style handlers keyed off `data.shop` for a victim shop, poisoning per-tenant caches, records, or triggering side effects (order sync, GDPR data actions, inventory updates) attributed to a shop the attacker does not control. This is a cross-tenant data-integrity/impersonation issue reachable by any internet user who can send an HTTP request with a previously captured valid `(body, hmac)` pair to the app's webhook URL.

### Likelihood Explanation
Exploitation requires the attacker to have obtained at least one valid `(raw_body, hmac)` pair signed with the app's `api_secret_key` — trivially satisfied by any merchant who installs the app on their own store and inspects an incoming webhook, since webhooks are delivered as plaintext HTTP POSTs to the app's public endpoint. No access to `api_secret_key`, access tokens, or the victim's credentials is required; only replay of a captured signed body with a modified `shop-domain` header.

### Recommendation
Include the `shop` (and ideally `topic`) values in the signable payload actually verified by the HMAC (or, at minimum, require the app to independently verify `request.shop` against a known/installed shop before trusting it), so that the shop attribute cannot be altered independently of the HMAC-protected body. `Registry.process` should reject if the `shop` header cannot be cryptographically bound to the payload.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and receives a legitimate webhook, e.g. topic `orders/create`, with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
2. Attacker sends a POST to the app's public webhook endpoint with the exact same body `B` and header `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (`= B`) and succeeds because `B` and `H` are unchanged: [6](#0-5) 
4. The handler is invoked with `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body: B, ...)`, so the app processes attacker's payload `B` under the victim shop's identity: [7](#0-6)

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
