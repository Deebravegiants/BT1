## Title
Webhook HMAC only covers the raw body, not the `shop-domain`/`topic` headers used for tenant attribution and dispatch - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` implements the `Utils::VerifiableQuery` interface so that `Registry.process` can verify a webhook's authenticity. However, the HMAC is computed only over the raw request body, while the `shop`, `topic`, `webhook_id` and `api_version` values that the registry uses to route and attribute the webhook are read straight from unauthenticated HTTP headers.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

but `Request#shop` and `Request#topic` are pulled from the `x-shopify-shop-domain` / `x-shopify-topic` headers with no cryptographic tie to the body: [2](#0-1) 

`Registry.process` validates the HMAC (body-only) and then unconditionally trusts `request.shop` and `request.topic` to select the handler and construct `WebhookMetadata`: [3](#0-2) 

The identity binding that should hold is: `shop/topic authenticated by HMAC == shop/topic acted upon by the handler`. Because the HMAC only signs `@raw_body`, that equality does not hold — the `shop` and `topic` fields are "acted on but not covered by the HMAC," exactly the analog class called out for this bug family. Anyone who obtains one valid `(raw_body, hmac)` pair for a legitimate webhook delivery (e.g., a webhook sent by Shopify that traverses logs, a debugging proxy, browser devtools when testing, or any place the delivery is visible before reaching the app) can resend that same body+hmac to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` and/or `x-shopify-topic` header. `HmacValidator.validate` will still return `true` because it only recomputes the signature over `to_signable_string` (the body), so `Registry.process` will dispatch the (attacker-relabeled) event as if it came from a different shop or represents a different topic.

### Impact Explanation
This crosses a tenant boundary without requiring the app's `client_secret`, `api_secret_key`, or any privileged credential — the attacker only needs one previously-observed valid webhook body/HMAC pair. By re-labeling the `shop-domain` header, an attacker can make the host application process a webhook as belonging to a shop it did not originate from (cross-tenant confusion), or re-label the `topic` header to make the app treat body content as a different event type than what was actually signed (e.g. causing the mandatory `customers/data_request`/`shop/redact` handling logic, or any app-specific per-topic business logic, to run against the wrong tenant or wrong semantics). This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires possession of one legitimately-signed `(body, hmac)` pair, which is not secret information under this gem's threat model — webhook deliveries are plaintext-observable at many points outside the attacker's own tenant boundary (proxies, logs, non-TLS-terminated infra, replay from an app's own inbound request logs). No secret key or token is needed to forge the headers; only the previously-seen body/hmac combination is replayed with edited headers. Likelihood is moderate to low depending on operational exposure, but the check itself is trivially bypassed once such a pair is obtained.

### Recommendation
Include the tenant- and routing-relevant fields (`shop-domain`, `topic`, and ideally `webhook_id`) in the signed material, or otherwise cryptographically bind them to the payload before trusting them for dispatch. If Shopify's own webhook HMAC spec only signs the body, the gem should not treat the headers-derived `shop`/`topic` as trusted identity beyond "this body is authentic"; the host app should be required (and the library documentation/API updated) to independently corroborate `shop`/`topic` against the parsed body content or a nonce/timestamp+dedup mechanism keyed off `webhook_id`, and `Registry.process` should not use header-only fields as the sole tenant/topic attribution for dispatch.

### Proof of Concept
1. Capture (or otherwise obtain) one legitimate webhook delivery for `shop-a.myshopify.com`, topic `orders/create`: raw body `B` and its valid `x-shopify-hmac-sha256` value `H` (computed by Shopify over `B` with the app's secret).
2. Replay a request to the app's webhook endpoint with the same body `B` and the same header `x-shopify-hmac-sha256: H`, but set `x-shopify-shop-domain: victim-shop.myshopify.com` (a different, unrelated tenant) and/or `x-shopify-topic: customers/redact`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` is constructed successfully (required-header check only looks at header presence, not consistency with the body).
4. `Utils::HmacValidator.validate(request)` returns `true` because it only recomputes the signature over `request.to_signable_string` (`B`), independent of the forged `shop`/`topic` headers: [4](#0-3) 
5. `Registry.process(request)` dispatches the handler registered for the forged topic and builds `WebhookMetadata` with the forged `shop`, so the host application processes the event as originating from `victim-shop.myshopify.com` / as a `customers/redact` event, even though neither was part of what Shopify actually signed.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
