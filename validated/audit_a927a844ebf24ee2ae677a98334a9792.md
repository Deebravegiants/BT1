This confirms the vulnerability. The docs explicitly document `data.shop` as "The shop domain of the webhook" — a value applications are expected to trust and act on (as shown in the `docs/usage/webhooks.md` example: `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), yet this field is never part of the HMAC-signed material.

### Title
Webhook shop-domain header is not covered by HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` validates webhook authenticity via `Utils::HmacValidator.validate`, which HMACs only the raw request body [1](#0-0) . The `shop` accessor, which the gem's own documentation instructs applications to trust as "the shop domain of the webhook" and use for shop-scoped side effects, is read directly from an unauthenticated HTTP header and is never bound to the signature [2](#0-1) .

### Finding Description
`Registry.process` only checks `Utils::HmacValidator.validate(request)` before dispatching to the app's handler with `request.shop` as the trusted tenant identifier [3](#0-2) . `HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string`, and for `Request` that is `@raw_body` only [4](#0-3) [1](#0-0) . The `hmac`, `topic`, `shop`, `api_version`, and `webhook_id` fields are all read straight from headers via `shopify_header`, none of which are covered by the signature computation [5](#0-4) .

The equality that should hold is: `shop asserted by X-Shopify-Shop-Domain header == shop cryptographically bound to the HMAC-signed bytes`. In this implementation that equality is never checked — the HMAC only proves the body bytes were signed with the app's shared `api_secret_key` (which is identical across every shop that installs the app), not which shop the body belongs to.

Because Shopify apps use one `api_secret_key` for all installs, an attacker who installs the app on their own store receives genuinely Shopify-signed webhook deliveries (valid HMAC over a body containing their own store's data). The attacker can capture such a delivery and replay it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header rewritten to a victim shop's domain. `HmacValidator.validate` still passes because it never inspects the shop header, and `Registry.process` forwards `WebhookMetadata.new(... shop: request.shop ...)` to the handler as if the (attacker-controlled) body genuinely belonged to the victim shop [6](#0-5) .

### Impact Explanation
Applications are documented to key per-shop logic (data storage, job dispatch, session/store lookup) off `data.shop` [7](#0-6) . Since the gem provides no binding between the shop identity and the authenticated payload, any app that follows this documented pattern is exposed to cross-tenant data confusion/injection: an attacker-controlled webhook body can be attributed to an arbitrary victim shop domain, corrupting per-tenant records, triggering shop-scoped business logic, or polluting a victim's audit/webhook processing pipeline under a spoofed identity. This crosses the tenant boundary the gem is supposed to enforce via HMAC verification.

### Likelihood Explanation
Any internet user can register as an app's own installed test/dev shop (installation is typically self-service for apps not doing OAuth `funder==issuer` type restrictions) and thereby obtain genuinely-signed webhook deliveries with a valid HMAC. Rewriting an unauthenticated header before replay requires no secret material — only the freedom to send an arbitrary HTTP request to the app's public webhook endpoint, which is the same capability the legitimate Shopify webhook delivery normally uses. This is a design gap in the gem's own verification method, not a host-app misuse, since `Registry.process`/`HmacValidator.validate` never advertises or requires shop-binding.

### Recommendation
Extend the HMAC-covered signable string (or add a secondary integrity check) to bind the shop-domain header to the signature, or require callers to independently correlate `request.shop` against a known/installed shop record with an active webhook subscription id before trusting it. At minimum, document prominently that `request.shop`/`data.shop` is NOT cryptographically authenticated and must be independently verified by the host application before use in tenant-scoped logic.

# => HmacValidator.validate(request) returns true (only raw_body is checked)
# => handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: ..., ...))
