### Title
Excess native ETH sent to `EvmHost.dispatch()`/`fundRequest()` for fee-token swaps is never refunded to the original caller - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` accept `msg.value` and forward the entire amount to `IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(...)` to buy the exact `fee`/`amount` of fee token needed. The router (or the project's own `UniV3UniswapV2Wrapper`/`UniV4UniswapV2Wrapper`) refunds any unspent ETH — but that refund is sent to `msg.sender` **as seen by the router**, which is `EvmHost` itself, not the original transaction sender (`_msgSender()`) who called `dispatch`/`fundRequest`. `EvmHost` never captures or forwards this refund back to the user.

`swapETHForExactTokens` is an "exact-out" swap: the caller supplies an `amountInMaximum` (here, the entire `msg.value`) and the router refunds whatever ETH wasn't needed to fill the exact output. Both custom router-wrapper implementations in this repo confirm the refund pattern by explicitly sending ETH back to `msg.sender` at the end of the swap: [4](#0-3) [5](#0-4) 

The problem: these `call{value: msg.value}(...)` invocations are made directly by `EvmHost`, so from the router/wrapper's perspective `msg.sender` is `EvmHost`, not the end user who called `IDispatcher(host).dispatch{value: msg.value}(...)`. The refunded ETH lands in `EvmHost`'s own balance. `EvmHost.dispatch()` and `fundRequest()` do not check the router's return value, do not compute `msg.value - amountSpent`, and never forward any leftover ETH back to `_msgSender()`. There is no `receive()`/sweep logic visible in `EvmHost.sol` to later distribute this trapped ETH to the affected users — it is simply retained by the contract with no accounting of who is owed what.

This is directly analogous to the reported `PythAggregator.updatePrice` bug: a payable function that computes an exact required payment, forwards the user's full `msg.value` to a third party, and never returns the difference to the caller.

Note: I could not find any admin-only sweep/withdraw function for accumulated native ETH in `EvmHost.sol` within the available index; I was unable to confirm with full certainty whether such a mechanism exists elsewhere in the contract due to index size limits, but no such function appeared among the dispatch/fee-handling code reviewed. Documentation for downstream callers (e.g. `IDispatcher`/`IHost` API docs) does not mention any excess-ETH refund from `EvmHost.dispatch`.

### Impact Explanation
Any account — end user, app contract (`IntentGatewayV2`, `HyperFungibleTokenUpgradeable`/`WrappedHyperFungibleToken`, `HyperbridgeLzEndpoint`, or any `HyperApp`) — that calls `dispatch()`/`fundRequest()` with `msg.value` greater than what's strictly needed to cover the exact-out swap will permanently lose the difference: it is stuck in `EvmHost` with no recovery path for the specific payer. Since `dispatch` is the core function used by virtually every cross-chain message (posts, gets, LayerZero adapter messages, wrapped-token transfers, intents), this is broadly reachable by ordinary unprivileged users through a single transaction that simply overestimates gas/fee headroom (a very common and encouraged pattern per the project's own documentation, which recommends "generous" ETH buffers, e.g. sending 5x the expected fee "since the swap only needed a tiny fraction"). This results in a direct, permanent loss of user funds and unbounded accumulation of unaccounted ETH inside `EvmHost`.

### Likelihood Explanation
High likelihood: this is not an edge case but the expected normal usage pattern. The project's own test suite and documentation explicitly demonstrate/encourage sending excess ETH for the fee swap (e.g. `testPlaceOrder_FeeSwap_RefundsExcessNativeToken` in `IntentGatewayV2Test.sol` sends 5 ETH expecting a refund of the unused portion at the app level), and callers of `dispatch()` directly (bypassing an app-level refund wrapper) would lose that excess with no recourse. Any relayer, app developer, or SDK user calling `EvmHost.dispatch`/`fundRequest` directly with `msg.value` — rather than going through an app that separately tracks and refunds unspent value itself — will trigger the loss on virtually every call, since exact price quoting for AMM swaps is inherently approximate.

### Recommendation
In `EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()`, track the ETH balance before and after the `swapETHForExactTokens` call (or capture the returned `amounts[0]` actually spent) and refund the difference (`msg.value - amountSpent`) to `_msgSender()` via a low-level call, reverting on failure — mirroring the pattern already implemented in `UniV3UniswapV2Wrapper.swapETHForExactTokens` and `UniV4UniswapV2Wrapper.swapETHForExactTokens`.

### Proof of Concept
1. A user calls `EvmHost.dispatch{value: 1 ether}(post)` where the actual required fee (in fee token) only costs `0.01 ether` worth of ETH via the configured Uniswap V2 pool.
2. `EvmHost.dispatch` invokes `IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: 1 ether}(post.fee, path, address(this), block.timestamp)`.
3. The router spends `0.01 ether` and refunds `0.99 ether` — but the refund destination is `msg.sender` of the router call, i.e., `address(EvmHost)`.
4. `EvmHost.dispatch` returns normally with the commitment; the user's transaction succeeds but `0.99 ether` remains stuck in `EvmHost`'s balance, permanently inaccessible to the user who sent it, with no event or accounting tying the surplus back to them.
