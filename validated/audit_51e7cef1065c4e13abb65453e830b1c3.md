### Title
Emporium wallet-delegated fee token is not bound by the EIP-712 signature, allowing arbitrary-token fee extraction beyond the signer's intended value - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`EmporiumUpgradeable.verifyWallet` authorizes a wallet-delegated Emporium execution by recovering `stack.signerAddress` from an EIP-712 signature over `EMPORIUM_SIGNATURE_TYPEHASH` [1](#0-0) . That signed struct commits only to `emporiumMessage`, the hash of `ops`, `maxFee` and `deadline` [2](#0-1) . The fee is enforced only as a bare numeric ceiling, `circomData.feeStructure.flatFee > stack.maxFee`, with no binding of `feeStructure.feeToken` (which ERC20 the fee is actually denominated in) [3](#0-2) . `feeStructure` (including `feeToken`) is part of `CircomData`, which is authenticated by the *shielded-pool user's* EdDSA signature via `calldataHash`/`signedMessageHash` [4](#0-3) , but that user is not necessarily the wallet owner whose funds are being spent. The wallet owner (`stack.signerAddress`) only cryptographically authorizes `maxFee` as an abstract number with no token/unit binding, exactly analogous to the referenced report's pattern of a numeric configuration value whose real-world impact depends on an unconstrained companion parameter (here, `feeToken`) that is never checked for consistency.

### Finding Description
When `runAction` executes wallet-invoked operations (`op.invokeWallet && stack.signerAddress != address(0)`), the relay fee is ultimately pulled directly from the delegated wallet via `sendToRelayFromWallet` → `IHinkalWallet(signerAddress).doSendToRelay(relay, relayFee, feeToken)` [5](#0-4) . The `feeToken` and `flatFee` values used come from `circomData.feeStructure`, which is not part of the wallet owner's signed payload at all [6](#0-5) . The only guard, `flatFee > maxFee` reverting with `FeeExceedsSignedMax`, checks a plain integer against `maxFee`, never verifying that `feeToken` matches whatever asset/denomination the wallet owner had in mind when they signed `maxFee` [3](#0-2) . Whoever assembles `circomData` (the relay/prover submitting `Hinkal.transact`) fully controls `feeStructure.feeToken`, so the same numeric `maxFee` the wallet owner signed can be re-interpreted against any ERC20 the assembler chooses, extracting value orders of magnitude beyond what the wallet owner intended, exactly as the referenced bug allowed an admin-set numeric value (`plotsAvailablePerSize`) to break an invariant (`MAX_SUPPLY`) that depended on an unconstrained companion value.

### Impact Explanation
This breaks the equality "value pulled from signer's wallet ≤ what the signer explicitly authorized." Because token denomination is unconstrained, the actual value extracted from the delegated wallet can vastly exceed the signer's intent (e.g., signing `maxFee = 5` expecting 5 USDC but having 5 WBTC extracted instead). This is unauthorized asset movement from a wallet — funds are moved via `doSendToRelay` without the wallet owner's authorization of the specific asset, meeting the High-severity bar ("executing calls or moving assets a wallet owner or prover never authorised").

### Likelihood Explanation
Any relay/prover that constructs `circomData` for an Emporium wallet-delegated action can trivially set `feeStructure.feeToken` to any ERC20 the wallet holds, as long as the numeric `flatFee` stays under the previously signed `maxFee`. No special privilege is needed beyond being the party submitting the `transact` call (an unprivileged EOA acting as relay), and the wallet owner has no on-chain way to detect or prevent the mismatch before signing, since the EIP-712 struct never surfaces `feeToken`.

### Recommendation
Include `feeStructure.feeToken` (and ideally the full `feeStructure`, or at minimum the specific token address) inside `EMPORIUM_SIGNATURE_TYPEHASH` so the wallet owner explicitly authorizes both the fee amount and the token/denomination before any value can be pulled via `doSendToRelay`.

### Proof of Concept
1. Wallet owner `W` signs an `EmporiumStack` authorizing some ops with `maxFee = 5` (intending "5 USDC"), producing `(v, r, s)` over the typed struct that includes only `emporiumMessage`, ops hash, `maxFee`, `deadline`.
2. A relay (unprivileged EOA) builds `CircomData` with `feeStructure = { feeToken: WBTC, flatFee: 5, variableRate: 0 }` and submits it via `Hinkal.transact`, referencing `stack.signerAddress = W`.
3. `verifyWallet` succeeds because the signature only covers `maxFee = 5`, which still equals `flatFee = 5` — the check `flatFee > maxFee` passes trivially [3](#0-2) .
4. `payRelayFees` → `sendToRelayFromWallet` → `IHinkalWallet(W).doSendToRelay(relay, 5, WBTC)` executes, pulling 5 WBTC from `W`'s wallet to the relay — vastly more value than the `W` believed they authorized [5](#0-4) .

Note: I could not directly inspect `IHinkalWallet.doSendToRelay`'s implementation (only its interface signature was located via `sendToRelayFromWallet`), so I cannot fully confirm whether any additional guard exists at the wallet-implementation layer restricting which tokens `doSendToRelay` accepts. This should be verified before treating the finding as fully confirmed; if `IHinkalWallet` implementations enforce their own token allow-list, this reduces the practical severity.

```text
    function payRelayFees(
        CircomData calldata circomData,
        address signerAddress,
        int256[] calldata deltaAmountChanges
    ) internal {
        FeeStructure calldata feeStructure = circomData.feeStructure;

        bool foundToken = false;

        for (uint256 i = 0; i < circomData.erc20TokenAddresses.length; i++) {
            // tokens deposited into Emporium are not charged
            if (deltaAmountChanges[i] >= 0) {
                continue;
            }

            address erc20TokenAddress = circomData.erc20TokenAddresses[i];
            bool isFeeToken = erc20TokenAddress == feeStructure.feeToken;

            if (isFeeToken) {
                foundToken = true;
            }

            uint256 relayFee = 0;
            uint256 flatFee = isFeeToken ? feeStructure.flatFee : 0;

            if (signerAddress == address(0)) {
                uint256 sumAbs = uint256(-deltaAmountChanges[i]);

                EmporiumStorageVars storage $ = _getEmporiumStorage();
                relayFee = $._hinkalHelper.calculateRelayFee(
                    sumAbs,
                    flatFee,
                    feeStructure.variableRate
                );
            } else {
                relayFee = flatFee;
            }

            payRelay(
                circomData.relay,
                signerAddress,
                relayFee,
                erc20TokenAddress
            );
        }

        if (!foundToken && feeStructure.flatFee != 0) {
            require(
                signerAddress != address(0),
                "Gas Token in Emporium is not found"
            );

            payRelay(
                circomData.relay,
                signerAddress,
                feeStructure.flatFee,
                feeStructure.feeToken
            );
        }
```
