### Title
`Webhooks::Request#shop`/`#topic` are trusted unauthenticated headers while HMAC covers only `@raw_body` - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`Webhooks::Request#to_signable_string` returns only `@raw_body`, so `Utils::HmacValidator.validate` verifies nothing about the `shopify-shop-domain`/`x-shopify-shop-domain` and `shopify-topic`/`x-shopify-topic` headers. `Registry.process` nonetheless uses those same unauthenticated headers to select the handler and to populate `WebhookMetadata.shop`/`topic` that is handed to app code as trusted, tenant-identifying data.

### Finding Description
The intended binding is: `bytes signed by compute_signature(to_signable_string, secret) == bytes that determine which tenant/topic the handler acts on`. In this codebase that equality does not hold:

- `to_signable_string` returns `@raw_body` only: [1](#0-0) 
- `shop`, `topic`, `api_version`, and `webhook_id` are all read from `@headers` via `shopify_header`, independent of the signed body: [2](#0-1) 
- `HmacValidator.validate_signature` computes the signature strictly from `to_signable_string` (i.e. the body) and compares it to `verifiable_query.hmac`; it never touches the header values: [3](#0-2) 
- `Registry.process` validates the HMAC once, then immediately trusts `request.topic` (to look up the handler) and `request.shop` (passed into `WebhookMetadata`) as if they were covered by that same validated signature: [4](#0-3) 

Because the app-level `api_secret_key` used for `compute_signature` is identical for every shop installed on a given app (it is the app's client secret, not a per-shop secret), any merchant who installs the app on their own development shop can receive a genuinely Shopify-signed `(raw_body, hmac)` pair for a webhook topic they registered. Since headers are not part of the signable string, that attacker can resend the identical body and HMAC directly to the app's public webhook endpoint while substituting `x-shopify-shop-domain` with a victim shop's domain and `x-shopify-topic` with any topic the app has a handler for. `HmacValidator.validate` still succeeds (body and secret are unchanged), `Registry.process` selects the handler based on the forged topic, and the handler receives `WebhookMetadata` carrying the forged `shop` value as if it were authenticated. No code in this path (`Request#initialize`, `shopify_header`, `HmacValidator.validate`, `Registry.process`) cross-checks header values against the signature or against any Shopify-verified shop identity.

### Impact Explanation
An attacker who is a legitimate, unprivileged merchant of the same app can cause the app to process a webhook labeled with an arbitrary victim shop domain and arbitrary topic, while carrying a cryptographically valid HMAC. If the app's webhook handler uses `WebhookMetadata.shop`/`topic` to look up sessions, write data, or trigger mutations scoped "for that shop" (the documented usage pattern), this is a cross-tenant integrity issue: one shop's signed traffic can be relabelled to appear as another shop's event. This is repeatable per request and is not limited to a single victim — any shop domain string can be substituted.

### Likelihood Explanation
Preconditions: the attacker must install the target app on their own (even free/dev) shop and register at least one webhook topic to obtain one genuine `(raw_body, hmac)` pair — both permitted under the stated attacker model. No secret, token, or credential theft is required; only the header-substitution step needs a direct HTTP request to the app's public webhook endpoint. Feasibility is high and cost is low; the attack is trivially repeatable.

### Recommendation
Bind the tenant/topic-identifying headers into the signed material, or otherwise validate `shop`/`topic` independently of header trust: e.g. include `topic`, `shop-domain`, `api-version`, and `webhook-id` in `to_signable_string` (matching what is actually verified), or have the host application cross-check `request.shop` against the session/shop the app expects for that endpoint before invoking `handler.handle`, rather than trusting the header verbatim.

### Proof of Concept
```ruby
# test/webhooks/request_relabel_test.rb
require_relative "../test_helper"

class WebhookRelabelTest < Minitest::Test
  def setup
    ShopifyAPI::Context.setup(api_key: "key", api_secret_key: "secret", ...)
  end

  def test_hmac_is_identical_across_different_shop_and_topic_headers
    raw_body = '{"id":1}'
    hmac = Base64.encode64(
      OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), "secret", raw_body)
    )

    legit_headers = {
      "x-shopify-topic" => "products/update",
      "x-shopify-hmac-sha256" => hmac,
      "x-shopify-shop-domain" => "attacker-dev-shop.myshopify.com",
    }
    forged_headers = {
      "x-shopify-topic" => "customers/data_request", # different topic
      "x-shopify-hmac-sha256" => hmac,                # same body/signature
      "x-shopify-shop-domain" => "victim-shop.myshopify.com", # different shop
    }

    legit_request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: legit_headers)
    forged_request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

    # Same signature bytes for two different (shop, topic) pairs:
    assert_equal(legit_request.hmac, forged_request.hmac)

    # Both pass validation despite different shop/topic:
    assert(ShopifyAPI::Utils::HmacValidator.validate(legit_request))
    assert(ShopifyAPI::Utils::HmacValidator.validate(forged_request))
    refute_equal(legit_request.shop, forged_request.shop)
    refute_equal(legit_request.topic, forged_request.topic)
  end
end
```
