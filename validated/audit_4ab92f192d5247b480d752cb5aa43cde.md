### Title
Webhook shop domain, topic, and webhook id are trusted unauthenticated because the HMAC only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then hands the caller-supplied `shop-domain`, `topic`, and `webhook-id` headers to the app's handler as if they were verified. These fields are never part of the signed material, so they can be freely swapped by anyone who can produce a byte-for-byte-identical body signed with the app's (single, shared-across-all-installs) `api_secret_key`.

### Finding Description
`Registry.process` performs exactly one check before dispatching to the app-registered handler: [1](#0-0) 

The HMAC validation itself only signs the raw body, never the shop, topic, or webhook id headers: [2](#0-1) 

Meanwhile, `shop`, `topic`, and `webhook_id` are read directly from attacker-controllable HTTP headers with no cryptographic binding to the body or to the HMAC signature: [3](#0-2) 

And `HmacValidator.validate` computes/compares the signature purely from `verifiable_query.to_signable_string` (the raw body) and the shared secret — the shop identity plays no role in the proof: [4](#0-3) 

`Registry.process` then forwards the unauthenticated `request.shop` value straight to the app handler as trustworthy tenant data: [5](#0-4) 

This breaks the identity binding `authenticated_secret_owner == shop_claimed_in_header`. Because a single Shopify app's `api_secret_key` is shared across every merchant that installs the app, a valid HMAC only proves "this body was signed by someone who knows this app's secret" (i.e., Shopify itself, for any of the app's installs) — it does **not** prove which shop the payload belongs to. Any legitimate webhook delivery to Shop A (attacker's own store, or a store the attacker can trigger events on) produces a body+HMAC pair that remains valid if the attacker swaps the `x-shopify-shop-domain` (or `shopify-shop-domain`) header to Shop B, as long as the body content stays byte-identical (e.g. generic/templated payloads, or replaying a captured request while relabeling the shop). The gem will validate the HMAC successfully and hand the handler `shop: "shop-b.myshopify.com"` with data that actually originated from shop A.

### Impact Explanation
Host applications built on this gem are documented to receive `WebhookMetadata#shop` as the verified tenant identifier for looking up the merchant's session/access token and processing the payload under that merchant's context. Because the shop header is not covered by the HMAC, an attacker who controls (or can trigger events in) one shop can cause the webhook processor to attribute that shop's payload to a different shop of the attacker's choosing, corrupting cross-tenant state, or triggering the correct handler under a false shop identity that host apps use as an authorization/session key. This crosses the tenant boundary the gem is supposed to guarantee via `HmacValidator`, matching a High-severity scope-check/tenant-binding bypass.

### Likelihood Explanation
Likelihood is bounded by the requirement that the attacker control or be able to trigger a webhook-eligible event with a body they can predict/replay (e.g., generic membership/app-uninstalled events, or events with attacker-controlled content sent from a shop they own), and knowledge that the shop header is not covered by the signature is trivial to derive from this code path. No access token, no `api_secret_key`, and no privileged account are needed — only the ability to deliver an HTTP request that reaches the app's public webhook endpoint (an unprivileged internet actor, since the shop header itself is fully attacker-controlled and independently swappable post-signing).

### Recommendation
Bind the shop domain (and ideally topic/webhook id) into the signed material, or otherwise cryptographically tie them to the verified body — e.g., include the shop domain in the HMAC computation, or require the caller to independently verify that `request.shop` corresponds to a shop known to have an active install with the secret used, before trusting it as a session/tenant key. At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must not be used as sole tenant-authorization input.

### Proof of Concept
1. App is installed on `shop-a.myshopify.com` and `shop-b.myshopify.com`, both sharing the same `api_secret_key` (standard Shopify app behavior).
2. Shopify delivers a webhook for `shop-a` with body `{}` and headers:
   - `x-shopify-hmac-sha256: <valid HMAC over "{}">`
   - `x-shopify-shop-domain: shop-a.myshopify.com`
3. Attacker (who owns `shop-a` and thus can observe/trigger this delivery, or who can reproduce an identical generic body) resends the exact same body+HMAC to the app's webhook endpoint but rewrites the header to `x-shopify-shop-domain: shop-b.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks the body against the secret — this succeeds (see `lib/shopify_api/utils/hmac_validator.rb:27-31` and `lib/shopify_api/webhooks/request.rb:35-38`).
5. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "shop-b.myshopify.com", body: {}, ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), even though the payload actually originated from `shop-a`.
6. Any host-app logic that uses `data.shop` to select a session/access token/tenant context now operates on the wrong tenant, despite the HMAC "passing."

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
