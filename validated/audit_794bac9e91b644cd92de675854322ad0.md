### Title
Convoluted merge of backend-confirmed and locally-determined signup finalization paths in `do_signup` - (File: `src/plans/mod.rs`)

### Summary
`do_signup` combines two fundamentally different signup-finalization behaviors — a backend-confirmed enrollment flow and a purely local, orb-determined success flow — inside a single branch keyed off a backend-supplied `user_centric_signup` flag. [1](#0-0)  This mirrors the "exercise" bug class in the external report: merging two distinct use-cases (real exercise vs. flash loan) into one function based on an argument value, increasing complexity and making the authorization logic harder to reason about and more error-prone.

### Finding Description
In `do_signup`, after biometric capture and pipeline processing, the orb computes a local `signup_reason` (`Normal`, `Fraud`, or `Failure`) from the pipeline result and `detect_fraud`. [2](#0-1)  Notably, `detect_fraud` in this build always returns `Ok(false)` because "FOSS: WE HAVE DELETED ALL FRAUD CHECKS", so `signup_reason` can essentially only ever be `Normal` or `Failure`. [3](#0-2) [4](#0-3) 

The function then branches on `user_centric_signup` (sourced from the backend-validated user QR data, `qr_codes.user_data.user_centric_signup`) and the config flag `ignore_user_centric_signups`:
- If `user_centric_signup` is true (and not overridden), enrollment success is decided **entirely locally** — `success = signup_reason == SignupReason::Normal` — with no additional backend round-trip to confirm the signup server-side.
- Otherwise, the code calls `enroll_user`, which performs a full backend `signup_post` + polling `signup_poll` confirmation cycle before declaring success. [1](#0-0) [5](#0-4) 

Merging these two authorization models into one conditional inside `do_signup` is exactly the pattern flagged in the external report: a single function serving two semantically different purposes (backend-attested enrollment vs. orb-local attestation) based on a data-driven flag, which increases the risk that one path is under-scrutinized relative to the other, and makes it harder for reviewers/testers to reason about which enrollment guarantee actually applies for a given signup.

### Impact Explanation
If `user_centric_signup` can be set to `true` (legitimately by backend logic for a certain signup type, or through any weakness in how that flag is derived/transmitted), the orb will locally mark a signup as `Success` without ever confirming with the backend that the enrollment was accepted, duplicate-checked, or free of backend-side fraud signals — the very checks that `enroll_user`'s `signup_post`/`signup_poll` cycle exists to perform. [6](#0-5)  Combined with `detect_fraud` being a stub that never reports fraud in this build, the only gate left before declaring a "successful" signup in the `user_centric_signup` branch is `pipeline.is_some()`. This creates a path where signup success/authorization is attested purely by the orb software's local state rather than by mutual backend confirmation, which is a weaker trust boundary than the standard flow and could lead to misattributed or unconfirmed signups being reported as successful.

### Likelihood Explanation
Reaching this branch requires the backend to set `user_centric_signup = true` for a given user's QR-derived data and `ignore_user_centric_signups` to be false in orb config — both are legitimate, backend/orb-operator-controlled configuration surfaces rather than something a signing-up user can directly forge from the QR code content itself (the boolean travels signed/encoded through `orb_qr_link::UserData`, validated via `user_data.verify(user_data_hash)`). [7](#0-6)  This limits direct unprivileged exploitation, but the underlying design flaw — a single function silently switching between backend-confirmed and orb-local success determination — remains a convoluted-implementation risk exactly as described in the source report, and any future change to how/when `user_centric_signup` is derived (or a bug in `verify`) would directly translate into an authorization bypass with no additional code changes needed in `do_signup`.

### Recommendation
Split the "backend-confirmed enrollment" and "locally-determined enrollment" logic into two clearly separate, independently testable functions rather than one conditional inside `do_signup`. Ensure the local-success path still requires some backend confirmation or is documented/audited as a distinct trust model, and add explicit logging/metrics distinguishing which path determined success for every signup, to reduce the risk of unconfirmed signups being silently treated the same as backend-confirmed ones.

### Proof of Concept
Not directly reproducible from unprivileged input alone: exploitation depends on the backend setting `user_data.user_centric_signup = true` for the scanned user QR code (a value carried inside the signed `orb_qr_link::UserData` payload) while `ignore_user_centric_signups` remains `false` in orb config. Given that constraint, a signup for which `pipeline` succeeds and `detect_fraud` (a stub always returning `false` in this build) reports no fraud will be marked `Status::Success` locally in `do_signup` without ever invoking `enroll_user`'s backend `signup_post`/`signup_poll` confirmation cycle.
