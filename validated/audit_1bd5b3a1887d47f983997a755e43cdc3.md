### Title
Webhook shop domain (and topic) not covered by HMAC signature, enabling cross-tenant webhook spoofing - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook as verified once `Utils::HmacValidator.validate` passes, but the HMAC only signs the raw request body, not the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers. An attacker who can obtain any single valid `(body, HMAC)` pair for the app (e.g., by installing the app on their own store and receiving a real webhook) can replay that exact body/HMAC to the app's webhook endpoint while swapping the `shop-domain` header to a victim shop, producing a request that passes signature validation yet is attributed to an arbitrary tenant.

### Finding Description
`Registry.process` verifies authenticity solely via HMAC and then unconditionally forwards `request.shop` and `request.topic` to the handler: [1](#0-0) 

The HMAC is computed by `HmacValidator.validate`/`validate_signature`, which signs `verifiable_query.to_signable_string`: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` is defined to be only the raw HTTP body, while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from unauthenticated headers: [3](#0-2) 

So the equality the code implicitly assumes is:
`shop verified-by-HMAC == shop used for tenant dispatch`

but what is actually true is:
`bytes verified-by-HMAC (raw_body only) β‰  shop header parsed and trusted for tenant dispatch`

This is exactly the "field acted on but not covered by the HMAC" class: the signature proves the *body* came from someone possessing the app's `client_secret` (Shopify), but it proves nothing about which shop header accompanied that body, because the header is never part of the signed content.

The gem's own documentation confirms `shop` is treated as the verified tenant identifier once `process` succeeds, instructing callers to route background jobs by it: `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`, and states processing "will verify the request did indeed come from Shopify" β€” implying the whole request, including the shop, is authenticated: [4](#0-3) 

### Impact Explanation
Since a single `api_secret_key`/`client_secret` is shared by an app across all of its installed shops, any unprivileged user who installs the public app on their own store can legitimately trigger and capture a real `(raw_body, HMAC)` pair (e.g. for `orders/create`). Because the HMAC never binds the `shop-domain` header, that same body+HMAC pair remains valid when replayed with a forged `shop-domain` header pointing at a victim shop. Downstream host applications that follow the gem's documented pattern of trusting `data.shop` as the tenant key will process attacker-controlled webhook payloads under the victim's tenant identity β€” a cross-tenant data injection / confusion issue meeting the "cross-tenant access" bar.

### Likelihood Explanation
Any actor capable of installing the target app on a store they control (which is generally open to any merchant/developer for public apps) can obtain a valid signed body without needing the `client_secret`, `api_secret_key`, or any privileged credential, and then replay it against the shared webhook endpoint with a different `shop-domain` header. No TLS interception, leaked secrets, or social engineering is required β€” only standard app installation and a normal HTTP client.

### Recommendation
Include the identifying headers (`shop-domain`, `topic`, `webhook_id`, `api_version`) in the HMAC-signed content, or otherwise cryptographically bind them (e.g., verify `shop-domain` against the shop associated with the webhook subscription/topic via a separate authenticated lookup) instead of trusting them as bare, unauthenticated headers in `ShopifyAPI::Webhooks::Request`.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and registers for `orders/create`.
2. Shopify sends a legitimately signed webhook: body `B`, header `X-Shopify-Hmac-Sha256: H` (valid for `B` under the shared `api_secret_key`), `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker POSTs the same `B` and `H` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:13-22`) validates successfully because it only checks `B` against `H`.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) dispatches to the handler with `shop: "victim-shop.myshopify.com"`, and any host app following the documented pattern (`data.shop`) processes/enqueues attacker-controlled data as if it originated from the victim shop.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
