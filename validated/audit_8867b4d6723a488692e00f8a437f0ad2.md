Found a valid analog in the webhook processing code — the `shop` field trusted for tenant routing is not covered by the HMAC signature.

### Title
Webhook `shop` identity is not covered by HMAC verification, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies webhook authenticity solely via `Utils::HmacValidator.validate`, which computes the HMAC over `Request#to_signable_string` — the raw request body only. The `shop` identity that is subsequently handed to the app's webhook handler as the authoritative tenant identifier is read directly from the `x-shopify-shop-domain` HTTP header, which is never included in the signed bytes.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
while `#shop` is read from an unauthenticated header: [2](#0-1) 

`Registry.process` only checks the HMAC before dispatching to the handler, and forwards `request.shop` verbatim as the tenant identity: [3](#0-2) 

`HmacValidator.validate`/`validate_signature` compute and compare the HMAC strictly over `verifiable_query.to_signable_string` (i.e., the body), never the `shop` header: [4](#0-3) 

Because the same `api_secret_key` is used to sign webhooks for *every* shop that installs a given app (it is an app-level secret, not a per-shop secret), any merchant who legitimately installs the app receives genuinely-signed `(body, hmac)` pairs for their own shop. Since the header carrying the shop identity is excluded from the signed payload, that same valid `(body, hmac)` pair remains valid when replayed with the `x-shopify-shop-domain` header rewritten to name a different, victim shop. `Registry.process` will accept it (HMAC still matches) and dispatch to the app's handler with `data.shop` set to the attacker-chosen victim domain.

This breaks the intended identity binding: `shop_authenticated_by_hmac == shop_used_for_tenant_routing`. In reality, only `hmac_verifies(body)` is true; `shop` is fully attacker-controlled and independent of what was actually signed.

The gem's own documentation explicitly instructs host applications to trust `data.shop` from `WebhookMetadata` as "The shop domain of the webhook" for routing/persisting merchant-specific data: [5](#0-4) 

so this is a documented, intended-use trust relationship, not a case of the host app misusing the API.

### Impact Explanation
An ordinary installed merchant (unprivileged relative to other tenants) can capture a validly-signed webhook payload sent to their own endpoint and replay it against the app's shared webhook controller with the `shop-domain` header changed to a victim shop. The app will process attacker-controlled body content (e.g., a forged `orders/create`, `app/uninstalled`, or other topic payload) under the *victim's* tenant identity. Depending on how the host application acts on `data.shop` (which the gem explicitly documents it should), this can lead to cross-tenant data injection, corruption of another merchant's records, or triggering of shop-scoped business logic (fulfillment, refunds, deactivation flows) attributed to a shop the attacker doesn't control — a cross-tenant boundary violation.

### Likelihood Explanation
Any developer/merchant able to install the target app (a normal, unprivileged action available to any Shopify user) can obtain a real signed `(body, hmac)` pair by simply triggering a webhook for their own store, then replay it with a modified header — no access to `api_secret_key`, tokens, or TLS interception is required. This is a low-effort, no-privilege attack chain against the intended, documented usage of the gem's webhook API.

### Recommendation
- Short term: Include the shop domain (and other identity-relevant headers such as `topic`/`webhook_id`) in the HMAC-signed material used for verification, or independently verify that `x-shopify-webhook-id` belongs to the claimed shop before dispatching to the handler.
- Long term: Do not treat any header value as authenticated unless it is cryptographically bound to the signature that was verified; document clearly that `shop` is currently unauthenticated so host apps can add their own cross-checks (e.g., correlating `webhook_id` via the Admin API for the claimed shop) until the signature scope is fixed.

### Proof of Concept
1. App merchant M installs the target Shopify app and registers a webhook (e.g., `orders/create`) via `ShopifyAPI::Webhooks::Registry.register_all`.
2. M triggers an order creation in their own store, causing Shopify to POST a body `B` with header `x-shopify-hmac-sha256: H` (HMAC computed by Shopify over `B` using the app's `api_secret_key`) and `x-shopify-shop-domain: m-shop.myshopify.com` to the app's webhook endpoint.
3. M intercepts/records `(B, H)` from their own traffic (trivial, since it is delivered to an endpoint they control/observe).
4. M resends the same `(B, H)` to the app's webhook endpoint, but replaces the header with `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request#hmac` and `#shop` parse the (unchanged) HMAC and the (attacker-modified) shop header respectively; `HmacValidator.validate` succeeds because it only checks `B` against `H`.
6. `Registry.process` calls the app's handler with `WebhookMetadata`'s `shop` set to `victim-shop.myshopify.com` and `body` equal to M's forged/controlled payload `B`, even though `victim-shop` never sent this webhook.
