### Title
Unrevoked ERC20 approvals set via arbitrary `op.endpoint.call` in `EmporiumUpgradeable.runAction` CASE 2 allow later draining of Emporium-held token balances - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
In `EmporiumUpgradeable.runAction`, CASE 2 (`op.invokeWallet == false`) executes `op.endpoint.call{value: op.value}(op.callData)` directly from Emporium's own address, with the only restriction being a selector block on `callHinkalWallet`/`doSendToRelay`. If `op.callData` targets an ERC20 `approve(spender, amount)`, Emporium becomes the approving owner, and nothing in `runAction` ever inspects or resets that allowance. Because Emporium is a shared, reused singleton contract across all users' `EmporiumStack` operations, a dangling infinite approval left by one call persists into future calls, letting the attacker-controlled `spender` pull any token balance Emporium later holds via a plain `transferFrom`, entirely outside of any Hinkal `transact` call.

### Finding Description
The broken equality is: `IERC20(token).allowance(emporium, spender)` must return to `0` (or be otherwise inert) once `runAction` for the op that set it has completed, since no future operation is meant to rely on a stale allowance. Tracing the code: [1](#0-0) 

confirms CASE 2 performs an unrestricted low-level call from Emporium's own address to `op.endpoint` with `op.callData`, checking only two forbidden selectors. There is no allowlist of target contracts/selectors, no post-call `approve(spender, 0)` reset, and no allowance check anywhere in the function.

The balance-diff loop that follows only compares `getBalancesForArray(circomData.erc20TokenAddresses)` before/after: [2](#0-1) 

`approve()` never changes `balanceOf`, so it is invisible to this loop regardless of whether `token` is in `circomData.erc20TokenAddresses`. `verifyWallet` (called earlier) only validates the EIP-712 signature when `stack.signerAddress != address(0)`; for `signerAddress == address(0)` it returns immediately after marking the message used: [3](#0-2) 

so nothing constrains the *content* of `op.callData` for stateless ops beyond the two forbidden selectors — a self-crafted `approve()` call passes unchecked. `Transferer.sol` confirms no allowance-reset helper is invoked from `runAction`; `unsafeApproveERC20Token`/`approveToken` exist but are never called in this path, and `getERC20Allowance` (the exact function named in the audit question) is defined but never used to validate post-conditions.

Attacker exploit flow: craft (or, as a legitimate user, submit) an `EmporiumStack` with `signerAddress = address(0)` and an op whose `endpoint = token` and `callData = approve(spender, type(uint256).max)`, where `spender` is a contract the attacker controls. After `runAction` returns, `token.allowance(emporium, spender)` is nonzero and there is no mechanism in `EmporiumUpgradeable` that will ever reset it. Whenever Emporium subsequently holds any balance of `token` — which is possible in later, unrelated `EmporiumStack` operations whose `op.endpoint.call` deposits or routes `token` to Emporium without `token` being included in *that* call's `circomData.erc20TokenAddresses` (the array is used purely for the sweep-diff calculation and does not gate what `op.callData` is allowed to touch) — the attacker calls `spender.transferFrom-triggering logic` (a plain, non-Hinkal call) to drain it directly.

### Impact Explanation
This allows an unprivileged attacker to drain ERC20 balances that transiently or persistently sit on the shared `EmporiumUpgradeable` contract, which acts as the execution vault for every user's external-action operations. Since Emporium is reused across all users, funds belonging to other users' in-flight operations (or leftover token balances not covered by a given call's `erc20TokenAddresses`) can be pulled by the attacker's pre-deployed `spender` at any later time with a single `transferFrom`, requiring no further proof, signature, or privileged role. This matches the Critical category: direct theft of pooled/in-flight funds.

### Likelihood Explanation
Preconditions: the attacker needs Emporium to actually hold a balance of `token` at some point after the approval is set, which depends on other operations' `op.callData` (fully attacker/user controlled) causing `token` to land on Emporium without being swept by the declaring call's `erc20TokenAddresses` array. This is plausible given `erc20TokenAddresses` is not proof-cross-checked against every token an arbitrary `op.endpoint.call` could touch, but I was not able to fully verify within the available context whether the circom circuit or `performHinkalChecks`/`dimensionsCheck` places any additional binding constraint forcing `erc20TokenAddresses` to enumerate every token touched by `op.callData.` The root-cause bug itself — an unbounded, never-reset `approve()` reachable from unauthenticated CASE 2 ops — is confirmed directly in the Solidity code with no additional assumptions.

### Recommendation
In `EmporiumUpgradeable.runAction` CASE 2, either (a) disallow ERC20 `approve`/`increaseAllowance`/`permit`-style selectors entirely from being called via ops.endpoint.call unless routed through a dedicated, revocation-guaranteed helper, or (b) after every op execution, explicitly reset (`approve(spender, 0)`) any allowance the op may have granted for tokens in `circomData.erc20TokenAddresses` and require that any token an op interacts with be declared in `erc20TokenAddresses` so it is covered by the sweep, or (c) require all ERC20 approvals set within an op to be scoped to `type(uint256).max` == false patterns that are immediately consumed (e.g., approve-then-transferFrom in the same op) and add an explicit `require(getERC20Allowance(token, address(this), spender) == 0)` check at the end of `runAction` for every token/spender pair touched during the call.

### Proof of Concept
Foundry test plan:
1. Deploy `EmporiumUpgradeable`, register it in `Hinkal` as an allowed external action, deploy a test ERC20 `token`, and deploy an attacker `SpenderMock` contract with a `drain(address emporium, address attacker, uint256 amount)` function calling `token.transferFrom`.
2. Build a `CircomData`/`EmporiumStack` with `signerAddress = address(0)`, one `EmporiumOperation{endpoint: token, invokeWallet: false, callData: abi.encodeCall(IERC20.approve, (spenderMock, type(uint256).max))}`, and `token` deliberately excluded from `circomData.erc20TokenAddresses`.
3. Assert before: `token.allowance(emporium, spenderMock) == 0`.
4. Call `Hinkal.transact(...)` (with a valid proof for the attacker's own UTXOs) to trigger `EmporiumUpgradeable.runAction`.
5. Assert after: `token.allowance(emporium, spenderMock) != 0` (nonzero/max) — equality broken.
6. Fund `emporium` with `token` via a second, unrelated legitimate action that does not declare `token` in its `erc20TokenAddresses` (simulating a real-world side effect), then call `spenderMock.drain(emporium, attacker, amount)` directly (no Hinkal call) and assert `token.balanceOf(attacker) == amount`, proving the dangling approval was exploited outside of any Hinkal `transact` flow.
