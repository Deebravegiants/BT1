### Title
Webhook `shop` identity is taken from an HTTP header not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `#shop`, `#topic`, `#api_version`, and `#webhook_id` are all read from HTTP headers [2](#0-1) . `Registry.process` validates only that the body's HMAC matches (`Utils::HmacValidator.validate(request)`), then forwards `request.shop` (the header value) to the app's handler as the tenant identifier, with no binding between the signed body and the header-derived shop [1](#0-0) .

### Finding Description
The gem's `HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` and compares it to `verifiable_query.hmac` [3](#0-2) . For webhooks, `to_signable_string` is defined as `@raw_body` only [4](#0-3) , and the `hmac` value comes from the `X-Shopify-Hmac-Sha256` header [5](#0-4) . Neither `shop` (`X-Shopify-Shop-Domain`) nor `topic`, `api_version`, or `webhook_id` are included in the signed bytes [6](#0-5) .

This is the same class of bug as the reported issue: a value that is *acted on* downstream (the array length / here, the tenant identity) is not part of what's *actually verified* (the HMAC / the `allTokens` mapping). Here, the identity binding broken is: `shop authenticated (bytes verified by HMAC) != shop used as tenant key (header value trusted by Registry.process)`.

Concretely, if an attacker controls a legitimate Shopify store (trivial to obtain a free/dev store) and triggers a real webhook delivery to their own app endpoint, they receive a body + a genuinely valid HMAC signed with the app's `client_secret` by Shopify for that specific body. Because the header `X-Shopify-Shop-Domain` is not part of the signed bytes, the attacker can replay that exact body+HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. `Utils::HmacValidator.validate` still succeeds (it only checks the body), and `Registry.process` will hand the handler a `WebhookMetadata` claiming `shop: <victim-domain>` [7](#0-6) .

### Impact Explanation
If the host application's webhook handler uses `WebhookMetadata#shop` as the tenant/session key to look up the victim's stored access token, update per-shop records, or perform actions scoped to "the shop that sent this webhook" (the exact pattern the library's own `WebhookMetadata` struct is designed to support [8](#0-7) ), an attacker who owns Shop A can inject attacker-controlled webhook payloads (e.g., fabricated order/customer data, or trigger mandatory-topic side effects) that are processed and stored under Shop B's identity — a cross-tenant data-confusion/injection primitive. This satisfies the "cross-tenant access" criterion under Critical impact, since the attacker never needs Shop B's credentials, only a legitimate account of their own.

### Likelihood Explanation
Requires only: (1) the attacker registers/owns a normal Shopify store that installs the target app (no elevated privileges needed), (2) the ability to trigger at least one real webhook delivery to the app (trivial — e.g., create/update a resource that the app subscribes to), and (3) the ability to replay an HTTP POST with a modified header to the app's public webhook endpoint. No knowledge of `client_secret`, no TLS interception, and no social engineering are required — only standard internet access to the app's public webhook URL. This is a realistic, unprivileged-internet-user attack path.

### Recommendation
Bind the shop (and ideally topic/webhook_id) to the signed payload rather than trusting the raw header value independent of the HMAC. At minimum, applications should be warned/documented that `shop` in `WebhookMetadata` is derived from an unauthenticated header and must not be trusted as an unforgeable tenant identifier unless cross-validated against the shop the app's stored session/webhook subscription actually expects. Ideally, `Request#to_signable_string` (or `Registry.process`) should incorporate the header set (or at least `shop-domain` and `topic`) into the value verified against the HMAC, or the registry should independently confirm that the reporting shop has an active, matching webhook subscription before dispatching.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`.
2. Attacker triggers a webhook (e.g., updates a product) causing Shopify to POST a signed webhook to the app's endpoint with headers `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`, and some `raw_body`.
3. Attacker intercepts/captures this raw body and HMAC (it's delivered to their own endpoint, so no interception of Shopify's channel is needed).
4. Attacker resends an HTTP POST to the app's webhook endpoint with the identical `raw_body` and `X-Shopify-Hmac-Sha256` header, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
5. `Utils::HmacValidator.validate(request)` returns `true` because it only checks `raw_body` against the HMAC [9](#0-8) .
6. `Registry.process` dispatches to the app's handler with `WebhookMetadata.shop == "victim.myshopify.com"` even though the payload actually originated from the attacker's own store [7](#0-6) .
