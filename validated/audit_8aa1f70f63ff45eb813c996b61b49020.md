I have enough evidence to confirm the vulnerability. The `Registry.process` method validates the HMAC over the raw body only, but passes the unauthenticated `shop-domain` header value to the handler as the trusted tenant identifier.

### Title
Webhook `shop` field trusted by handlers is not covered by HMAC verification, allowing tenant spoofing - (File: lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies webhook authenticity using `Utils::HmacValidator.validate(request)`, which only signs/verifies `request.to_signable_string` (the raw body bytes). The `shop` field, taken from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, is never included in the HMAC computation, yet it is passed directly into `WebhookMetadata` and handed to the app's `WebhookHandler#handle` as the trusted tenant identifier.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) . The HMAC validator computes and compares a signature over that signable string only: [2](#0-1) . `Registry.process` gates further processing purely on this HMAC check, then forwards `request.shop` unauthenticated into `WebhookMetadata`, which is delivered to the app's handler: [3](#0-2) . The `shop` header itself is read straight from attacker-controlled HTTP headers with no cryptographic binding: [4](#0-3) .

This breaks the identity binding: `shop-header-verified-by-HMAC == shop-value-delivered-to-handler` does not hold — the gem verifies "bytes parsed" (the body) but not "bytes acted on" (the `shop` header used by the app to key sessions/data per tenant), directly matching the reported bug class of "a field acted on but not covered by the HMAC."

### Impact Explanation
Any unprivileged internet user who can obtain one valid `(raw_body, hmac)` pair from Shopify — e.g., by owning a development store and receiving one legitimate webhook for any topic — can replay that exact body+HMAC to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header naming a victim shop. `HmacValidator.validate` will still pass because it never inspects the shop header, and the handler receives `WebhookMetadata#shop` set to the attacker-chosen value. Apps that use `data.shop` to look up sessions, write per-tenant data, or trigger tenant-scoped side effects (a documented and expected usage pattern per `docs/usage/webhooks.md`) will act on forged cross-tenant data, enabling cross-tenant data corruption/injection under the identity of a victim merchant.

### Likelihood Explanation
Exploitation only requires network access to the app's public webhook endpoint and a single previously-observed legitimate `(body, hmac)` pair, which is trivial to obtain from any shop (including one the attacker controls, e.g., using their own dev store's `orders/create` topic and reusing generic-body webhooks like `shop/redact` where the body may be shop-independent, or any topic whose body content the attacker doesn't need to control since only the header is forged). No secret key, access token, or privileged account is required — this satisfies the "unprivileged internet user" threat model.

### Recommendation
Include the `shop` (and ideally `topic`, `api_version`, `webhook_id`) header values in the HMAC signable string, or otherwise cryptographically bind the shop domain to the verified payload before it is trusted by `WebhookMetadata`/handlers. At minimum, document/enforce that `data.shop` in `WebhookHandler#handle` must not be trusted without additional server-side confirmation (e.g., cross-checking against a shop the app has an active session for) since the current gem-level guarantee does not cover it.

### Proof of Concept
1. Attacker registers/owns a shop `attacker.myshopify.com` and receives one legitimate webhook delivery (`raw_body`, `x-shopify-hmac-sha256`) from Shopify for a topic the target app also subscribes to.
2. Attacker POSTs to the victim app's webhook endpoint with the same `raw_body` and `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `raw_body` — validation succeeds despite the shop header mismatch: [5](#0-4) .
4. The handler is invoked with `WebhookMetadata.new(... shop: request.shop ...)` set to `"victim-shop.myshopify.com"`, an unauthenticated attacker-controlled value: [6](#0-5) .
