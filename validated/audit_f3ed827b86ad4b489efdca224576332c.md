### Title
Missing L2 sequencer uptime check in SimplexPaymaster oracle pricing allows stale/manipulated gas-fee charges during L2 sequencer downtime - (File: evm/src/utils/SimplexPaymaster.sol)

### Summary
`SimplexPaymaster._getOraclePrice` prices ERC-20 gas payments against Chainlink `nativeOracle` and per-token oracles using only a `block.timestamp - updatedAt > maxOracleAge` staleness check, without verifying the L2 sequencer uptime feed. On Arbitrum/Optimism/Base (all in the paymaster's target chain set per its own doc comments), sequencer downtime can leave a Chainlink round's `updatedAt` looking "fresh" while the L2 execution environment (and the price it should reflect) is stale or in a distorted recovery state, letting UserOps be charged (or refunded) using an unreliable native/token price.

### Finding Description
`_getOraclePrice` at [1](#0-0)  only checks `answer <= 0` and the `updatedAt` staleness bound; it never queries a sequencer-uptime oracle (e.g. Chainlink's `L2SequencerUptimeFeed`) nor enforces a grace period after a sequencer restart. This price feeds directly into `_tokenPrice`, which is used both to size the ERC-20 pull for a sponsored UserOp and to compute `estimateTokenCost`: [2](#0-1) . The contract's own header documents multi-L2 deployment intent (`Native asset / USD oracle (BNB/USD on BSC, ETH/USD on Ethereum, etc.)`) at [3](#0-2) , and Chainlink feeds on Arbitrum/Optimism/Base are known to require sequencer-uptime gating because the L2 execution context (and thus contract logic relying on "current" pricing) can diverge from what the raw `updatedAt` timestamp implies during and immediately after an outage.

### Impact Explanation
An unprivileged UserOp sender can submit sponsored ERC-20-gas UserOps to the paymaster during/just-after an L2 sequencer outage on Arbitrum/Optimism/Base and be charged token amounts computed from an oracle price that Chainlink's own guidance says must not be trusted without a sequencer check, exposing the protocol treasury to financial loss (undercharging sponsored gas relative to true native cost) or users to overcharging, both of which are concrete fund-loss vectors reachable from an ordinary, unprivileged UserOp submission — matching the reported bug class of using a Chainlink price without an L2 sequencer check to compute gas/keeper-style fees.

### Likelihood Explanation
This triggers passively any time the relevant L2's sequencer experiences downtime or restarts within `maxOracleAge` of a stale round, requiring no special privilege — any user submitting a paymaster-sponsored UserOp during that window is affected, and L2 sequencer outages, while infrequent, are a recurring, externally-triggered event outside the protocol's control.

### Recommendation
Add a Chainlink `L2SequencerUptimeFeed` check (with the standard grace period, e.g. Chainlink's recommended pattern) inside `_getOraclePrice`, reverting when the sequencer is down or has been up for less than the grace period, mirroring the mitigation recommended in the source report.

    /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
