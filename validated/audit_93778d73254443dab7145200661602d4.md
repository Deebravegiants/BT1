### Title
Webhook shop/topic/version identity fields are unauthenticated — HMAC signs only the raw body - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
The gem's webhook HMAC verification (`ShopifyAPI::Utils::HmacValidator.validate`) authenticates only the raw request body of a webhook. The `shop`, `topic`, `api_version`, and `webhook_id` values, which are taken from unauthenticated HTTP headers, are passed straight into `WebhookMetadata` and handed to the app's registered `WebhookHandler` as if they were verified alongside the body.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are all read from HTTP headers, none of which are part of the signable string: [2](#0-1) 

`Registry.process` validates the HMAC over the body via `Utils::HmacValidator.validate(request)`, and — once that single check passes — trusts every header-derived field to build `WebhookMetadata` and dispatch it to the app's handler: [3](#0-2) [4](#0-3) 

The identity binding that should hold is: `shop header used to attribute the webhook == shop covered by the HMAC`. In this implementation that equality is false — `HmacValidator` only proves `HMAC(secret, raw_body)` is valid; it proves nothing about which shop, topic, or webhook produced that body. The gem's own `Utils::HmacValidator.validate_signature` computes the digest solely from `verifiable_query.to_signable_string`, which for webhooks resolves to the raw body: [5](#0-4) 

Any party that has ever received one genuine, correctly-signed webhook body from Shopify for the app's `client_secret` (e.g., an unprivileged user who installs the app on their own free/dev store and thus gets real, validly-signed webhook deliveries) can replay that exact body to the app's webhook endpoint while substituting the `shopify-shop-domain` (and/or `shopify-topic`, `shopify-webhook-id`) header for a different, victim shop's domain. `HmacValidator.validate` still returns `true` (the body/HMAC pair is untouched), so `Registry.process` proceeds and calls the handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain.

### Impact Explanation
This breaks the tenant-isolation guarantee that "a webhook whose HMAC verifies represents an authentic Shopify event for the shop named in it." A host application that (reasonably, given the gem's API) trusts `WebhookMetadata#shop` as verified — e.g., to look up the target shop's session/access token, write data, or trigger shop-scoped side effects — can be made to attribute attacker-controlled body content to an arbitrary victim shop chosen by the attacker. This is a cross-tenant integrity/confusion issue reachable purely by anyone able to obtain one legitimately signed webhook from the app (installing the app is generally open to any Shopify user), with no need for the app's `client_secret`, an access token, or any privileged account.

### Likelihood Explanation
Low-to-moderate: it requires the attacker to have their own valid installation of the target app (to obtain a genuinely signed body+HMAC pair) and to know/guess a victim shop's `myshopify.com` domain (which is not secret and is often discoverable). No cryptographic secret needs to be recovered — only the header, which is entirely unauthenticated, needs to be swapped.

### Recommendation
Bind the identity-bearing headers into the HMAC-covered signable string (or otherwise cryptographically bind `shop`/`topic`/`webhook_id` to the verified payload), or, failing that, explicitly document that `WebhookMetadata#shop`/`topic`/`webhook_id` are unauthenticated header values and require host applications to independently confirm the shop domain against their own installed-shop/session store before acting on webhook data. At minimum, `Registry.process` should not present these fields to `WebhookHandler#handle` in a way that implies they carry the same integrity guarantee as the HMAC-verified body.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` and registers a webhook (e.g. `orders/create`), receiving a genuine POST from Shopify:
   - Headers: `x-shopify-hmac-sha256: <valid HMAC over body>`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: orders/create`.
   - Body: arbitrary JSON the attacker controls to some extent by placing test orders.
2. Attacker replays the identical body and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the headers; `HmacValidator.validate(request)` recomputes `HMAC(secret, raw_body)` — unchanged, so it still matches — and returns `true`.
4. `Registry.process` proceeds, builds `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: "orders/create", body: attacker_body, ...)` and calls the app's handler, which processes attacker-supplied data under the victim shop's identity.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
