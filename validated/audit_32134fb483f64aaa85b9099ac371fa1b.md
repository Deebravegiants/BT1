### Title
Webhook tenant identity (`shop`) is not covered by the HMAC signature, allowing cross-tenant shop spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw request body, then hands the caller a `shop` value that is taken from an unauthenticated HTTP header. Because the app's webhook HMAC secret (`Context.api_secret_key`) is a single shared secret used for *every* shop that has installed the app, a valid HMAC only proves "this body was HMAC-signed by Shopify for some shop of this app" — it does not bind the request to the specific shop claimed in the `X-Shopify-Shop-Domain` header.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements the `Utils::VerifiableQuery` interface used by `HmacValidator`: [1](#0-0) 

Its `to_signable_string` returns only `@raw_body` — the `shop` (from the `shopify-shop-domain` / `x-shopify-shop-domain` header) is read separately via `shopify_header` and is **not part of the signed material at all**.

`Registry.process` validates the request and then forwards the header-derived `shop` directly to the app's webhook handler as the tenant identity, with no independent verification against the HMAC-protected body or against any list of known/installed shops: [2](#0-1) 

`HmacValidator.validate` computes `OpenSSL::HMAC.hexdigest(... Context.api_secret_key ..., raw_body)` and compares it to the received signature: [3](#0-2) 

`Context.api_secret_key` is a single, app-wide secret (the app's `client_secret`), not a per-shop secret — it is the same value used for every shop that installs the app. Consequently, the equality that should hold —

`shop authenticated by HMAC == shop trusted/used as tenant key by the handler`

— is broken: the HMAC binds only the *body bytes* to "this app", while the `shop` used to key the handler's tenant lookup (session storage, `perform_later(shop_domain: data.shop, ...)` in the documented example) comes from a header outside that signature.

Because the secret is shared across all shops, any merchant who has genuinely installed the app on their own store can capture a real, validly-signed webhook delivery (body + HMAC) that Shopify sent for *their own* shop, then replay that exact body/HMAC pair directly to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. `HmacValidator.validate` still succeeds (it never looks at the header), and `Registry.process` calls the handler with `shop: "victim-shop.myshopify.com"` even though the signed body content actually originates from the attacker's own store.

This is the exact bug class from the referenced report — a field ("shop"/tenant identity) that is acted upon by the caller but is not covered by the cryptographic verification (`trimBalance`/`VaultProxy.withdraw` acting on unqueued state vs. the analog here of a handler acting on an unauthenticated header) — mapped onto this gem's webhook identity binding.

### Impact Explanation
If the host application uses `data.shop` from `WebhookMetadata` to select a tenant/session (a documented, encouraged usage pattern shown in `docs/usage/webhooks.md`, e.g. `shop_domain: data.shop`), a spoofed `shop` value causes the webhook payload (attacker-originated, actually about the attacker's own shop) to be attributed/written into a different shop's tenant record. This is a cross-tenant data-integrity/confusion issue: data intended for shop A can be forced into being processed as if it belongs to shop B. Depending on what the handler does with `data.shop` (e.g., look up an access token/session keyed by that shop, trigger side effects scoped "for that shop"), this can escalate to cross-tenant action or information disclosure.

### Likelihood Explanation
Requires only that the attacker be a genuine (even free/trial) merchant who has installed the target app — no leaked credentials, no privileged access, and no dependency on `api_secret_key`/access tokens being compromised. The attacker never needs to know the secret; they only need to capture one legitimate webhook delivery addressed to themselves and resend it with a different header, which is straightforward with standard HTTP tooling.

### Recommendation
Bind the `shop` (and other routing-relevant headers, e.g. `topic`, `api_version`, `webhook_id`) into the HMAC-signed material, or otherwise authenticate the header-derived `shop` against the body/HMAC before it is handed to the handler. At minimum, `to_signable_string` in `lib/shopify_api/webhooks/request.rb` should include the shop domain, so that a body signed for shop A cannot be replayed and attributed to shop B.

### Proof of Concept
1. App installs on attacker's own store `attacker.myshopify.com`; app registers a webhook (e.g., `orders/create`).
2. Shopify delivers a webhook to the app: body `B`, header `X-Shopify-Hmac-Sha256: H` (computed with the shared `api_secret_key`), header `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. Attacker captures `B` and `H` (e.g., via their own logging/proxy since it's their own request) and issues a new POST directly to the app's public webhook endpoint with the same `B`/`H` but header `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `B` against `H` using the shared secret — validation passes.
5. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed(B), ...)`, i.e., attacker-originated data is now attributed to the victim shop.
