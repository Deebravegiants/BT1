### Title
Webhook `shop-domain` header is trusted for tenant identification without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`), event `topic`, `api_version`, and `webhook_id` entirely from unauthenticated HTTP headers, while the HMAC that `Utils::HmacValidator.validate` checks is computed only over the raw request body via `to_signable_string` returning `@raw_body`. This breaks the intended binding "shop that owns this webhook == shop the HMAC was signed for."

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely with: [1](#0-0) 

```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
``` [1](#0-0) 

`HmacValidator.validate` computes the signature exclusively from `verifiable_query.to_signable_string`: [2](#0-1) 

And for `Webhooks::Request`, `to_signable_string` returns only `@raw_body`; `shop`, `topic`, `api_version`, and `webhook_id` are read straight from headers with no cryptographic binding to that signature: [3](#0-2) 

Compare this to the OAuth callback path, `ShopifyAPI::Auth::Oauth::AuthQuery`, where `shop` **is** included inside `to_signable_string` and therefore is covered by the HMAC: [4](#0-3) 

This asymmetry is exactly the "field acted on but not covered by the HMAC" class from the report: the identity binding the protocol needs — `HMAC(secret, body) valid ⇒ (shop, topic) in headers are authentic` — does not hold. Only `HMAC(secret, body) valid ⇒ body is authentic` holds.

**Exploit path (no privileged credentials needed):** An unprivileged attacker who installs the app on their own store (a normal merchant with a store, not requiring the app's `client_secret` or any leaked credential) will legitimately receive real webhook deliveries from Shopify, each with a valid `shopify-hmac-sha256` computed over the body with the app's real secret. The attacker captures one such delivery (raw body + valid HMAC), then replays it to the app's webhook endpoint while rewriting only the `shopify-shop-domain` header (and optionally `shopify-topic`) to name a **different, victim** shop. `HmacValidator.validate` still succeeds because it never inspects the headers — it only recomputes the HMAC of `@raw_body`, which is unchanged. `Registry.process` then invokes the app's handler with `WebhookMetadata` claiming the payload originated from the victim shop.

### Impact Explanation
Any app built on this gem that uses `WebhookMetadata#shop` (via `request.shop`) to key per-tenant storage, GDPR/data-request routing, or trust decisions will process attacker-controlled data under a different tenant's identity — a cross-tenant data-integrity/confusion vulnerability. This satisfies the "Critical: cross-tenant access" impact bar: an attacker who is only a merchant on their own store forges the tenant binding of data delivered to the host application for another store, without needing the app's `client_secret`, an access token, or any privileged access.

### Likelihood Explanation
Likelihood is high for any real deployment: capturing your own valid webhook delivery requires nothing more than installing the app (a normal, unprivileged action available to any internet user with a Shopify store), and replaying an HTTP POST with modified headers is trivial. The gem provides no additional binding (e.g., re-deriving shop from a signed claim, or validating that the header's shop matches a shop the raw body's HMAC was actually generated for) to prevent this.

### Recommendation
Include `shop`, `topic`, `api_version`, and `webhook_id` in the signable material used for webhook HMAC validation (mirroring what Shopify webhook signing actually is scoped to, if it can be extended), or otherwise cryptographically bind the header-derived tenant identity to the payload before trusting `request.shop`/`request.topic` in `Registry.process`. At minimum, document and/or enforce that host applications must independently corroborate `request.shop` (e.g., against a known/registered shop for the given webhook subscription) rather than trusting the header value merely because the body's HMAC validated.

### Proof of Concept
1. Register the app on attacker-controlled shop `attacker.myshopify.com` and enable a webhook topic (e.g., `orders/create`).
2. Capture a real webhook delivery from Shopify for that topic — headers include a valid `shopify-hmac-sha256` (signed with the app's real `api_secret_key`) and `shopify-shop-domain: attacker.myshopify.com`, plus the JSON body.
3. Replay the exact same body/HMAC to the app's webhook endpoint, but change the header:
   ```
   shopify-shop-domain: victim.myshopify.com
   ```
4. The app calls `ShopifyAPI::Webhooks::Registry.process(request)`:
   - `Utils::HmacValidator.validate(request)` returns `true` because it only recomputes/compares the HMAC over `@raw_body`, per `to_signable_string` returning `@raw_body` in `lib/shopify_api/webhooks/request.rb`.
   - `handler.handle(data: WebhookMetadata.new(..., shop: request.shop, ...))` is invoked with `shop == "victim.myshopify.com"` even though the payload actually originated from the attacker's own store.
5. Any host-application logic keyed on `WebhookMetadata#shop` (e.g., "store this order data under `victim.myshopify.com`'s tenant record") now attributes attacker-controlled data to the victim tenant — demonstrating the cross-tenant confusion enabled purely by the unauthenticated header.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
