Webhook tenant identity (`shop`) is passed to handlers unauthenticated because it is not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, then hands the handler a `shop` value read from an HTTP header that was never part of the signed bytes. This breaks the intended binding `hmac == HMAC(secret, body ‖ shop)`; in this gem the binding actually enforced is only `hmac == HMAC(secret, body)`, while `shop` is trusted independently for tenant scoping.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `shop` is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cross-check against the HMAC [2](#0-1) . `Utils::HmacValidator.validate` computes the signature purely from `to_signable_string`, i.e. the body [3](#0-2) . `Registry.process` accepts any request whose body-only HMAC checks out, then constructs `WebhookMetadata` using the header-derived, unauthenticated `request.shop` as the tenant identifier passed to the host application's handler [4](#0-3) .

Because the shop header is not part of the signed content, a request with a given `(raw_body, hmac)` pair that is valid for shop A remains HMAC-valid if the `shop-domain` header is swapped to shop B — the validator has no way to detect the substitution. This is directly analogous to the reported bug class: "a field acted on but not covered by the HMAC."

### Impact Explanation
An attacker who can obtain one genuinely-signed webhook payload (e.g., by installing the app on their own shop and receiving legitimate webhooks addressed to them) can replay that exact body/HMAC pair while relabeling the `shop-domain` header to a victim shop. If the host application relies on `WebhookMetadata#shop` to route data to per-tenant storage (a documented, expected usage pattern of this gem), the attacker's data gets written/attributed to another tenant, or the attacker successfully injects a "confirmed-authentic" webhook under an arbitrary shop's identity — a cross-tenant integrity/isolation violation.

### Likelihood Explanation
Exploitation requires only sending an HTTP request; no access token, `client_secret`, or privileged account is needed. Any developer/attacker able to install the app on a shop they control can obtain a validly-signed webhook body and then freely re-target it to a different shop identifier client-side, since only the body is authenticated.

### Recommendation
Bind the shop identity into the authenticated bytes, e.g. include the `shop-domain` header (and ideally `topic`/`api-version`/`webhook-id`) in `to_signable_string`, or independently verify the header-derived shop against a value the app already trusts for that installation before dispatching to handlers.

### Proof of Concept
1. Install the app on `attacker.myshopify.com`; receive a legitimate webhook with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC(secret, B)`.
2. Replay a request to the app's webhook endpoint with the same body `B` and `H`, but set `x-shopify-shop-domain: victim.myshopify.com`.
3. `Utils::HmacValidator.validate` succeeds because it only hashes `B` [3](#0-2) .
4. `Registry.process` calls the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed(B), ...)` [5](#0-4) , causing the application to treat attacker-controlled data as authentic for the victim tenant.
