### Title
Unauthenticated origin selection via decoded `message.from` allows arbitrary `RuntimeCall` dispatch on behalf of any account — (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
The `on_accept` handler of the `hyper-fungible-token` pallet deserializes an attacker-controlled `SubstrateCalldata` blob embedded in a cross-chain ISMP `PostRequest` body, and, when no signature is supplied, derives the dispatch origin directly from the unauthenticated `message.from` bytes before dispatching an arbitrary decoded `RuntimeCall`.

### Finding Description
`on_accept` first ABI-decodes the incoming `Message` (`from`, `to`, `amount`, `data`) from the ISMP request body [1](#0-0) . When `message.data` is non-empty, it SCALE-decodes it into `SubstrateCalldata { signature: Option<Vec<u8>>, runtime_call: Vec<u8> }` [2](#0-1) [3](#0-2) .

If `substrate_data.signature` is `None`, the code takes the *unverified* `message.from` field — which is just raw bytes chosen by whoever called the source-chain sending contract/module — and converts it directly into the dispatch origin with no cryptographic check that the caller actually controls that identity: [4](#0-3) 

The decoded `runtime_call` is then dispatched as `RawOrigin::Signed(origin)`: [5](#0-4) 

Unlike the signed branch — which cryptographically verifies an Ed25519/Sr25519/Ecdsa signature over `(nonce, runtime_call)` against the `beneficiary` account before allowing dispatch [6](#0-5)  — the unsigned branch performs **no proof of authorization at all**: it trusts the `from` bytes embedded in the deserialized cross-chain message as an implicit identity assertion. Only `ContractToAsset::<T>::get(source, &from)` is checked, which authenticates the *source contract/module address*, not the individual sender identity carried inside the message body [7](#0-6) .

This is the same bug class as the CVE report: an externally-reachable endpoint deserializes an untrusted payload (there, `app_auth`; here, the ISMP-delivered `Message`/`SubstrateCalldata`) and uses fields from that deserialized structure to perform a privileged action without independently authenticating the actor. Whether this is exploitable to impersonate a *third party* account depends on how the source-chain sending contract/pallet populates `Message.from` (i.e., whether it is hard-bound to `msg.sender`/the extrinsic signer, or can be freely chosen by the caller) — that source-side binding could not be fully verified from the pieces of the sending contracts inspected in this session.

### Impact Explanation
If the source-chain sender is able to set `message.from` to an arbitrary 32-byte (or 20-byte, EVM path) value independent of their own signing key, a completely unprivileged relayer of a cross-chain HFT transfer can cause the destination pallet to dispatch **any runtime call permitted by `BaseCallFilter`** under an origin of the attacker's choosing — including accounts they do not control — enabling theft of funds or unauthorized privileged actions (e.g., asset transfers, governance-adjacent calls) signed as someone else, with no signature check at all.

### Likelihood Explanation
The `on_accept` entrypoint is reached by any relayer delivering a valid ISMP proof for a message from a registered source contract; the source-side "no calldata signature" path is a documented, first-class feature of the API (`SubstrateCalldata.signature: Option<...>`), meaning triggering the unsigned branch requires no special privilege beyond initiating an ordinary cross-chain HFT transfer with calldata attached.

### Recommendation
Require the unsigned branch to bind the dispatch origin exclusively to the already-verified `beneficiary` account (derived from `message.to`, which is independently validated and minted-to) rather than the unauthenticated `message.from` field, or remove the no-signature origin-selection branch entirely and always require the existing Ed25519/Sr25519/Ecdsa proof-of-control check before dispatching any `RuntimeCall`.

### Proof of Concept
1. Attacker calls the source-chain HFT sending function/contract, setting the cross-chain `Message.from` field to the raw account bytes of a victim account on the destination substrate chain (assuming the source-side encoder does not hard-bind `from` to the caller's own key).
2. Attacker embeds `SubstrateCalldata { signature: None, runtime_call: <encoded privileged call> }` in `message.data`.
3. Relayer delivers the ISMP `PostRequest`; `on_accept` executes lines [8](#0-7) , dispatching `runtime_call` as `RawOrigin::Signed(victim_account)` with no signature verification, since the `signature` field is `None`.
