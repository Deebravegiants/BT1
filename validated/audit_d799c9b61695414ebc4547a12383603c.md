### Title
Webhook `shop` (and `topic`/`api-version`) identity used by handlers is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then hands the handler a `WebhookMetadata` object built from `request.shop`, `request.topic`, and `request.api_version` — none of which are part of the signed payload.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop`, `topic`, `api_version`, and `webhook_id` are all read from unauthenticated HTTP headers [2](#0-1) . `Registry.process` validates the HMAC (`Utils::HmacValidator.validate(request)`, which calls `to_signable_string`, i.e. body-only) and then immediately passes `request.shop`, `request.topic`, `request.api_version`, and `request.webhook_id` straight into the handler via `WebhookMetadata.new` [3](#0-2) .

The bug-class binding this breaks is: **shop acted upon (`request.shop`, used by the handler as the tenant identity) ≠ shop covered by the HMAC (only `raw_body` is signed)**. Because the signature never binds the `x-shopify-shop-domain` (or `x-shopify-topic`) header to the body, any actor who obtains one legitimately-signed `(raw_body, hmac)` pair for a webhook — which is not a secret, since it travels in a plain HTTP request and is not encrypted by anything this gem controls beyond TLS-in-transit — can replay that same body/HMAC pair to the app's webhook endpoint with a *different* `x-shopify-shop-domain` header. `Registry.process` will accept it (the HMAC check only validates the body, which is unchanged) and dispatch it to the handler tagged with the attacker-chosen shop, causing cross-tenant data confusion in any application that uses `WebhookMetadata#shop` to attribute the payload to a tenant (the intended and documented use of that field).

### Impact Explanation
This falls under **cross-tenant access**: an application built on `ShopifyAPI::Webhooks::Registry` that stores/attributes incoming webhook data by `data.shop` can be made to associate Shop A's payload with Shop B's tenant record, because the identity claim used for tenant routing is not part of the cryptographically verified data.

### Likelihood Explanation
Exploitation requires an attacker to have captured a valid `(raw_body, hmac)` pair for at least one legitimate webhook delivery (e.g., via a misconfigured proxy/log, a shared multi-tenant endpoint, or another integration point that echoes webhook payloads) — the gem itself does not leak this. Given that constraint, forging the request to the same endpoint with a different `shop` header requires no cryptographic secret and no privileged access, and the receiving code (as designed by this gem) has no way to detect the substitution.

### Recommendation
Document/require that host applications never trust `request.shop`/`WebhookMetadata#shop` (or `topic`) as an integrity-protected tenant identifier without an independent side-channel (e.g., correlating against a known shop→webhook registration), or extend `to_signable_string`/webhook processing to bind the shop domain and topic into the value that is HMAC-verified before it is handed to handlers.

### Proof of Concept
1. Attacker legitimately observes (or otherwise obtains) one valid webhook delivery for `shop-a.myshopify.com`: raw body `B` and header `x-shopify-hmac-sha256: H` (a valid HMAC of `B` under the app's `client_secret`).
2. Attacker sends a new HTTP request to the app's webhook endpoint with the *same* body `B` and header `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: shop-b.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers into `shop = "shop-b.myshopify.com"` [4](#0-3) .
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `to_signable_string` = `B` only, and it matches `H` — validation succeeds [5](#0-4) .
5. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "shop-b.myshopify.com", body: parsed_body_of_B, ...)` [6](#0-5) , causing Shop A's payload to be processed as if it belonged to Shop B.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
