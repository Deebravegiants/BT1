### Title
Predictable, Unsigned Session Cookie Enables Session Fixation / Cross-Tenant Session Hijacking - ([File: lib/shopify_api/utils/session_utils.rb])

### Summary
For non-embedded apps (and embedded apps falling back to cookie auth), the gem derives the "current session id" directly and solely from the raw value of the `shopify_app_session` cookie, with no cryptographic binding to any authenticated request. Because the gem itself sets this cookie's value to the fully predictable string `"offline_#{shop}"` (or `"#{shop}_#{user_id}"` for online sessions), any unprivileged internet user who knows (or guesses) a target's public `*.myshopify.com` domain can set that exact cookie value in their own browser and be treated by the host application as if they were the authenticated session for that shop.

### Finding Description
`ShopifyAPI::Utils::SessionUtils.cookie_session_id` reads the session id straight from client-supplied cookie bytes with zero verification: [1](#0-0) 

`current_session_id` falls back to this cookie-derived id for non-embedded apps (and even for embedded apps without a bearer/id_token): [2](#0-1) 

The offline session id format itself is fully deterministic and public-computable: [3](#0-2) 

And the gem's own `Oauth.validate_auth_callback` sets the browser cookie value to exactly this deterministic id after a real OAuth completion: [4](#0-3) 

The `SessionCookie` object carries no HMAC/signature of its own — it is a plain struct with `name`, `value`, `expires`: [5](#0-4) 

The test suite confirms the deterministic mapping the library itself produces and expects host apps to trust as a session identifier: [6](#0-5) 

**Broken identity binding (equality that should hold but doesn't):**
`session_id_supplied_in_client_cookie == session_id_authenticated_for(shop)` is treated as true by `SessionUtils.current_session_id`/`cookie_session_id` purely because the *string format* matches, without the request ever proving possession of any credential (access token, JWT, or OAuth state) tying it to that shop. The cookie is never checked against an HMAC, signature, or any secret-derived value — it's raw, attacker-controllable, unauthenticated bytes accepted as an authoritative session key.

### Impact Explanation
Since `"offline_#{shop}"` is derived only from the shop's public `myshopify.com` domain (which is either publicly known, guessable, or trivially discoverable), an attacker can compute the exact session id string for any target merchant that has installed the app. If the attacker sets their browser's `shopify_app_session` cookie to that computed value and calls into a host application built on this gem (using `current_session_id`/`cookie_session_id` to resolve "the session" and then retrieving the corresponding stored `Session` — including its access token — from `SessionRepository`), the attacker is treated as though they are that shop's authenticated session. This results in cross-tenant access to another merchant's stored access token and Admin API capabilities — a Critical-severity outcome (cross-tenant access / access-token exposure via impersonation) achieved without ever needing `api_secret_key`, a leaked token, or local access.

### Likelihood Explanation
Likelihood is high in any non-embedded deployment (or any embedded deployment that falls back to cookie auth per the documented API) because: (1) the session id format is fixed and documented/tested by the gem itself, (2) shop domains are public/discoverable, and (3) no additional secret material is required to construct a valid-looking session id — only knowledge of the target's shop domain.

### Recommendation
Do not use a predictable, attacker-guessable string as the sole session lookup key trusted from an unauthenticated cookie. Either (a) sign/HMAC the session cookie value (e.g., MAC over the session id with `api_secret_key`) and verify it in `cookie_session_id` before returning it as trusted, or (b) treat the raw cookie value as an opaque, unguessable random token (unrelated to `shop`/`user_id`) generated at OAuth completion, and store the mapping server-side, rather than deriving the session store key directly from client-supplied bytes.

### Proof of Concept
1. Victim shop `victim-shop.myshopify.com` installs the app and completes OAuth; the gem's `Oauth.validate_auth_callback` returns a cookie with `value: "offline_victim-shop.myshopify.com"` [7](#0-6) , which the host app stores/sets per the documented flow.
2. Attacker, with no credentials, sets their own browser cookie `shopify_app_session=offline_victim-shop.myshopify.com` (the shop name is public knowledge).
3. Attacker visits any host-app route/page that calls `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, attacker_cookies, false)`.
4. `cookie_session_id` returns `"offline_victim-shop.myshopify.com"` verbatim [8](#0-7) , which the host app uses to load the victim's stored `Session` (including access token) and perform Admin API calls on the attacker's behalf as the victim shop.

          if Context.embedded?
            if shopify_id_token
              id_token = shopify_id_token.gsub("Bearer ", "")
              session_id_from_shopify_id_token(id_token: id_token, online: online)

            end

            raise Errors::CookieNotFoundError, "Session cookie not found for app" unless
              cookies && cookies[Auth::Oauth::SessionCookie::SESSION_COOKIE_NAME]

            cookie_session_id(cookies)
          end
        end
