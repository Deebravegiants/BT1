### Title
Webhook `shop` (and `topic`/`api_version`/`webhook_id`) identity fields are trusted without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb](file))

### Summary
`ShopifyAPI::Webhooks::Request` computes/validates the webhook HMAC over the raw request body only, while the `shop`, `topic`, `api_version`, and `webhook_id` values that are handed to the app's webhook handler are read directly from HTTP headers that are never included in the HMAC-signed material. Any actor who can obtain one validly-signed `(raw_body, hmac)` pair (e.g. a merchant receiving real webhooks for their own store) can relay that same body/HMAC pair to the app's webhook endpoint with an arbitrary `x-shopify-shop-domain` header, and `ShopifyAPI::Webhooks::Registry.process` will accept it and hand the attacker-chosen `shop` value to the app's handler as if it were authenticated.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

and `hmac` is likewise derived purely from a header, decoupled from any other field: [2](#0-1) 

The `shop`, `topic`, `api_version`, and `webhook_id` accessors are all read from unauthenticated HTTP headers with no cryptographic binding to the HMAC: [3](#0-2) 

`Registry.process` validates only the HMAC over the body, then immediately trusts `request.shop`, `request.topic`, etc. to build the `WebhookMetadata` passed to the app's handler: [4](#0-3) 

`WebhookMetadata.shop` is documented and used by consuming applications as the authoritative tenant identifier for the webhook (e.g. to route the update to the correct shop's records): [5](#0-4) [6](#0-5) 

The identity binding that should hold is:

`shop header value == shop bound inside the HMAC-signed payload`

but in this implementation:

`shop header value` is **independent** of `HMAC(raw_body, api_secret_key)` — the equality never actually gets checked, because the `shop` field is not part of `to_signable_string`.

### Impact Explanation
Because `Utils::HmacValidator.validate` only proves that `raw_body` was signed with the app's secret at some point — it proves nothing about which shop, topic, or webhook that body/signature pair was originally intended for — an attacker who can obtain any one valid `(raw_body, hmac)` pair (trivially available to any merchant who installs the app on their own store and receives a real webhook) can resend that exact body/HMAC to the app's public webhook endpoint while substituting a different `x-shopify-shop-domain` (and/or `x-shopify-topic`) header. `Registry.process` will pass HMAC validation and deliver `WebhookMetadata` with the attacker-chosen `shop` to the handler. Applications that use `data.shop` to select the tenant/session/database record to update (exactly as shown in this gem's own documentation example, `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) will process and persist attacker-controlled data under a victim shop's identity — a cross-tenant data injection into another merchant's account, without needing the app's `api_secret_key` or any credential belonging to the victim.

### Likelihood Explanation
Any user who can become a merchant/install target of the app (a normal, unprivileged flow) can generate a legitimately-signed webhook body for their own shop and then modify only the non-signed headers before delivering it to the app's public webhook receiver endpoint. No secret material or privileged access is required beyond running one's own store instance, which is achievable by any internet user for apps distributed publicly.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) values into the HMAC-signed material, or otherwise cryptographically tie the header-supplied shop domain to the authenticated payload before it is trusted as the webhook's origin — e.g., by including these headers in `to_signable_string`, or by cross-checking the header-derived shop against an independent trusted source (such as the registered webhook subscription/session for that shop) before invoking the handler.

### Proof of Concept
```ruby
# Attacker installs the app on their own shop "attacker.myshopify.com" and
# receives a legitimate webhook delivery with a valid HMAC over the body:
raw_body = '{"id": 123, "note": "hello"}'
valid_hmac = Base64.encode64(
  OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), app_api_secret_key, raw_body)
) # captured from the real Shopify delivery to attacker's own shop

# Attacker now POSTs the same raw_body + hmac to the app's webhook endpoint,
# but swaps the shop-domain header to the victim shop:
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => valid_hmac,
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # not covered by HMAC
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HMAC validation passes (it only checks raw_body), and the app's handler
#    receives WebhookMetadata(shop: "victim-shop.myshopify.com", ...),
#    processing attacker-controlled data under the victim's tenant.
```
