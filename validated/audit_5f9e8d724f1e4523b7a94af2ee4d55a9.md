### Title
Webhook `shop`/`topic` identity is read from unauthenticated headers while only the raw body is HMAC-verified - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its signable content as `to_signable_string => @raw_body` only [1](#0-0) . The `shop`, `topic`, `api_version`, and `webhook_id` values that the app relies on to route and attribute the webhook are pulled directly from HTTP headers that are never covered by the HMAC digest [4](#0-3) . `Utils::HmacValidator.validate` only recomputes and compares the digest over `to_signable_string` (the body) [5](#0-4) , so the equality the library actually enforces is `HMAC(secret, body) == received_hmac`, not `HMAC(secret, body ‖ shop ‖ topic) == received_hmac`. `Registry.process` then trusts `request.shop` and `request.topic` as the identity/routing key for dispatch without any additional binding to the verified body [3](#0-2) .

### Finding Description
Because the client secret (`api_secret_key`) is shared by the app across **all** installing shops (it is not shop-specific), any two webhooks legitimately sent by Shopify to the same app - regardless of which shop they originated from - are signed with the exact same key. The signature only binds the body bytes; it says nothing about which shop or which topic the body was produced for.

An unprivileged internet user can install the target app on a shop they control (e.g., a free development store) and receive a genuinely Shopify-signed webhook for that shop (capturing `raw_body` + `X-Shopify-Hmac-Sha256`). Because many webhook bodies are shop-agnostic or attacker-influenced (e.g., `{}` for `app/uninstalled`, or a payload whose relevant fields are attacker-controlled resource content on their own store), the attacker can then resend that identical, still-validly-signed body to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` and/or `X-Shopify-Topic` headers to name a different, victim shop. `HmacValidator.validate` still returns `true` because it never inspected the headers, and `Registry.process` will hand the handler a `WebhookMetadata`-equivalent payload asserting `shop: <victim>` even though the verified bytes came from the attacker's own shop.

This breaks the identity equality that the host application expects to hold after HMAC verification: `shop_verified_by_hmac == shop_used_for_tenant_dispatch`. In reality, `shop_used_for_tenant_dispatch` is attacker-controlled while `shop_verified_by_hmac` is undefined (the signature covers no shop at all).

### Impact Explanation
If the host application uses `request.shop` (or the equivalent field in the resulting `WebhookMetadata`) as the tenant key to load a session/access token or to attribute the event without any secondary shop confirmation, an attacker can trigger the app's webhook handler logic under the identity of an arbitrary victim shop using only a legitimately-signed payload from their own shop. Depending on the handler, this is a cross-tenant confusion primitive: the app processes attacker-supplied verified bytes as if they belong to a different merchant's store, satisfying the "cross-tenant access" criterion for a Critical-impact finding.

### Likelihood Explanation
Likelihood is constrained by the fact that the attacker needs a real Shopify webhook signed for *some* shop they control, which is trivial to obtain (install the app on a free/dev store and trigger any webhook topic), and the ability to POST to the app's webhook endpoint with custom headers, which is standard unauthenticated HTTP access. No access token, `client_secret`, or privileged account is required — only ordinary merchant/developer-level interaction with the target app.

### Recommendation
Bind the identity fields into the verified signature domain rather than trusting raw headers post-hoc:
- Require host applications (and update this gem's `Request`/`Registry`) to cross-check `shop` against the actual session/shop the app expects for that endpoint/tenant before dispatch, or
- Extend `to_signable_string` (or add a secondary check) so that `shop`, `topic`, and `webhook_id` are confirmed against Shopify's registered webhook subscription metadata (e.g., via the `webhook_id` looked up through the Admin API) instead of being accepted verbatim from headers, and
- Document prominently that `request.shop`/`request.topic` are **not** covered by the HMAC and must not be used as a sole tenant-identity or authorization boundary.

### Proof of Concept
1. Install the target app (which uses this gem) on an attacker-controlled development store `attacker.myshopify.com`.
2. Trigger any subscribed webhook topic (e.g., `app/uninstalled`) and capture the raw POST body and its `X-Shopify-Hmac-Sha256` header — this is a validly Shopify-signed payload for the app's `api_secret_key`.
3. Replay the identical body and HMAC header to the app's webhook endpoint, but change `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com` (and optionally `X-Shopify-Topic`).
4. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds a request whose `hmac` still matches `to_signable_string` (the unchanged body) [6](#0-5) .
5. `Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks the body [7](#0-6) , and then invokes the handler with `shop: request.shop` equal to `"victim-shop.myshopify.com"` [8](#0-7) , even though the verified bytes never originated from that shop.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
