This confirms the analog: the docs explicitly state `Registry.process` "will verify the request did indeed come from Shopify" via HMAC, then dispatches `data.shop` (from the `shopify-shop-domain` header) to the app's handler as the trusted tenant identifier — but the HMAC in `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb`) only signs `to_signable_string`, which for `Webhooks::Request` is just `@raw_body` [1](#0-0) . The `shop` accessor is pulled straight from an unauthenticated HTTP header [2](#0-1) , and `Registry.process` forwards that header-derived value into `WebhookMetadata` after only checking the body HMAC [3](#0-2) .

### Title
Webhook tenant identity (`shop`) is taken from an unauthenticated header not covered by the HMAC, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb, lib/shopify_api/utils/hmac_validator.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body [4](#0-3) . The `shop` field that identifies which merchant/tenant the webhook belongs to is read from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, which is never included in the HMAC computation [2](#0-1) [1](#0-0) . Because Shopify signs webhooks using the app's single shared `client_secret` (the same secret is used for every shop that installs the app), an unprivileged attacker can install the target app on their own free/dev store, capture a genuinely-signed `(raw_body, hmac)` pair for their own shop, then replay that exact body+HMAC to the app's webhook endpoint while substituting the `shopify-shop-domain` header with a victim shop's domain. The HMAC still validates (it only covers the body), but the handler receives `WebhookMetadata` claiming to be from the victim shop.

### Finding Description
The identity binding that should hold is:
`shop authenticated by HMAC == shop delivered to the app's webhook handler`

In this gem that equality is broken. `HmacValidator.validate` computes/compares a signature only over `verifiable_query.to_signable_string` [5](#0-4) . For `Webhooks::Request`, `to_signable_string` returns just `@raw_body` [1](#0-0) ; none of `topic`, `shop`, `webhook_id`, or `api_version` (all read from headers) are part of the signed material [6](#0-5) . `Registry.process` then trusts `request.topic` and `request.shop` unconditionally, after only checking the HMAC, to build the `WebhookMetadata` passed to the app-provided handler [3](#0-2) . The gem's own documentation instructs developers to treat the check as full request authentication ("This will verify the request did indeed come from Shopify") and to trust `data.shop` as the webhook's shop domain, feeding it directly into tenant-scoped work such as job enqueueing (`perform_later(topic: data.topic, shop_domain: data.shop, ...)`).

Because the HMAC secret (`api_secret_key`/`client_secret`) is shared across all shops that install a given app — not shop-specific — any unprivileged user who installs the app on a shop they control can obtain a validly-signed `(body, hmac)` pair from Shopify for a real topic (e.g. `orders/create`), and then forge a request to the app's own webhook endpoint using arbitrary `shopify-topic` / `shopify-shop-domain` / `shopify-webhook-id` header values, since none of those are checked against the signed body.

### Impact Explanation
This crosses a tenant boundary using only content the attacker legitimately received via their own (attacker-owned) shop installation — no `api_secret_key`, access token, or privileged account is required. By spoofing the `shop` field, the attacker can cause the host application's webhook handler to run tenant-scoped business logic (e.g., updating orders/customers, disabling/enabling features, writing audit logs, dequeuing jobs) attributed to a victim shop rather than their own. Depending on how the host app uses `data.shop` (e.g., looking up the victim's stored access token/session by shop domain to perform authenticated write operations on the app's behalf), this can escalate into cross-tenant data corruption or actions performed against a victim's store using the app's stored credentials for that shop — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
High. Creating a Shopify development/trial store and installing an app that uses this gem is trivial and available to any unprivileged internet user. Capturing one's own legitimately signed webhook `(body, hmac)` pair requires no special access, and replaying it with a different `shopify-shop-domain` header to the publicly reachable webhook endpoint is straightforward with any HTTP client.

### Recommendation
- Include the tenant-identifying fields (`shop`, `topic`, `webhook_id`, `api_version`) in the HMAC-signed material, or otherwise cryptographically bind them to the body (e.g., require them to be embedded in and derived from the JSON payload rather than headers).
- At minimum, document and/or enforce that host applications must independently verify that `data.shop` corresponds to a shop that actually has this webhook/topic registered and is expected to receive it, rather than treating `HmacValidator.validate` as authenticating the header-derived `shop` value.
- Consider validating the `shop` header against an app-provided list of currently-installed shops before dispatching to the handler.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` and triggers a webhook (e.g. `orders/create`) to their registered callback URL, capturing the raw POST body and the `x-shopify-hmac-sha256` header value sent by Shopify (both legitimately signed with the app's shared `client_secret`).
2. Attacker sends a new HTTP POST to the app's public webhook endpoint with:
   - Body: the exact captured raw body bytes (unchanged, so HMAC still validates).
   - Header `x-shopify-hmac-sha256`: the exact captured HMAC value (unchanged).
   - Header `x-shopify-shop-domain`: `victim-shop.myshopify.com` (forged).
   - Header `x-shopify-topic`: unchanged or attacker-chosen registered topic.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `Digest.hexencode(...)` against `@raw_body` [7](#0-6) .
4. The registered handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...)` [8](#0-7) , causing the host app to process attacker-controlled webhook content as if it originated from the victim's shop.
