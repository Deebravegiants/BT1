### Title
Webhook `shop` (and other headers) are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC over the raw body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values used to route and process the webhook come from unauthenticated HTTP headers. This breaks the intended binding "shop verified by HMAC == shop the payload is processed for," letting an attacker who controls any single valid `(body, hmac)` pair replay it with an arbitrary `shop` header to make the registered handler process the payload as if it came from a different, victim shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate` only checks that signature against the secret: [2](#0-1) 

But `Registry.process` uses `request.shop` (and `request.topic`, `webhook_id`, `api_version`), read straight from headers, to build the `WebhookMetadata` passed into the app's handler: [3](#0-2) [4](#0-3) 

Since none of `shop`, `topic`, `webhook_id`, or `api_version` are part of `to_signable_string`, the HMAC check proves only that "some previously‑HMAC'd body was sent by someone who once received a signature for that exact body" — it proves nothing about which shop, topic, or webhook the body belongs to. The library's own documentation states process "will verify the request did indeed come from Shopify," which overstates what is actually verified (only the body bytes, not the header-derived identity fields consumed by the handler): [5](#0-4) 

This is the exact bug class named in scope: "a field acted on but not covered by the HMAC." The identity equality that should hold — `shop-that-produced-the-HMAC == shop-passed-to-handler` — does not hold, because the shop is never part of the signed material.

### Impact Explanation
An attacker who has legitimately received (or otherwise obtained) even one valid `(raw_body, hmac)` pair for a given webhook topic (e.g. from installing the app on their own store, a trivially attainable unprivileged position) can replay a POST to the app's webhook endpoint with the same body/HMAC but an arbitrary `x-shopify-shop-domain` header naming a different, victim shop. Because `Registry.process` never re-derives or cross-checks `shop` against anything cryptographically bound to the payload, the handler executes with `data.shop` set to the attacker-chosen victim shop while carrying attacker-controlled `body` content that is valid for at least one (any) shop's HMAC. Any app logic keyed off `data.shop` (e.g., looking up the victim's stored session/access token to act on their behalf, writing to victim-shop-scoped data) is attacker-triggerable, which is a cross-tenant access issue.

### Likelihood Explanation
Exploitability requires only network access to the app's public webhook route plus one legitimately obtained `(body, hmac)` pair (trivial for anyone able to install the app on any shop, or observe any real webhook delivery for any tenant). No secret material, TLS interception, or privileged account is needed to forge the `shop` header value — normal HTTP clients can set arbitrary headers. This is directly exploitable by an unprivileged internet user once one valid webhook body/signature has been observed.

### Recommendation
Include the identity-relevant fields (`shop`, `topic`, at minimum) in the signed material verified by `HmacValidator`, or otherwise cryptographically bind the header values to the HMAC (e.g., by verifying that the `shop` header matches a shop the app has an active registration for that specific webhook id, and/or requiring Shopify's newer body constructs that embed shop/topic). At minimum, document that `Request#shop`/`#topic` are not authenticated by the HMAC and must not be trusted for authorization decisions without additional verification (e.g. cross-referencing against `Registry`'s known registrations or session store).

### Proof of Concept
1. Attacker installs the app on their own shop `attacker.myshopify.com` (or otherwise observes) and captures a legitimate webhook POST for topic `orders/create` with raw body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(client_secret, B)`.
2. Attacker sends a new POST to the app's webhook endpoint with:
   - Body: `B` (unchanged)
   - Header `x-shopify-hmac-sha256: H` (unchanged, still valid because it only signs `B`)
   - Header `x-shopify-shop-domain: victim-shop.myshopify.com` (changed)
   - Header `x-shopify-topic: orders/create` (unchanged/as needed)
3. `Utils::HmacValidator.validate` succeeds because `to_signable_string` only covers `B`, per [1](#0-0) .
4. `Registry.process` invokes the app's handler with `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)`, per [6](#0-5) , causing the app to process attacker-supplied data under the victim shop's identity.
