This confirms `ShopValidator` is never invoked in `Registry.process` or `Request#initialize` on the webhook path — only `Utils::HmacValidator.validate(request)` gates the request before `handler.handle` is invoked.

### Title
Shop, topic, webhook-id, and api-version headers are not covered by webhook HMAC, allowing header spoofing of a replayed body - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC signature Shopify computes never covers `shop`, `topic`, `webhook_id`, or `api_version`. `Registry.process` calls `Utils::HmacValidator.validate(request)` (body-only check) and, if it passes, immediately builds `WebhookMetadata` from the raw, unauthenticated headers and hands it to the host app's handler.

### Finding Description
The broken binding: the code implicitly assumes `HMAC_valid(body) == authenticated(shop, topic, webhook_id, api_version)`, but in fact `HMAC_valid(body)` only proves `body` was signed with `Context.api_secret_key`; it says nothing about the header values.

Trace:
- `Webhooks::Request#initialize` (`lib/shopify_api/webhooks/request.rb:46-63`) normalizes headers and stores `@headers`/`@raw_body`, but only checks that the three required headers are *present*, not that they are covered by any signature.
- `#shop`, `#topic`, `#webhook_id`, `#api_version` (lines 15-33) all read straight from `@headers` via `shopify_header`, with no cryptographic binding.
- `#to_signable_string` (lines 35-38) returns `@raw_body` only [1](#0-0) .
- `Utils::HmacValidator.validate`/`validate_signature` (`lib/shopify_api/utils/hmac_validator.rb:26-31`) computes `HMAC(secret, verifiable_query.to_signable_string)` and compares to the `hmac` header — i.e., it only ever signs/verifies the body [2](#0-1) .
- `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) does exactly: validate HMAC of body → look up handler by `request.topic` (unauthenticated) → build `WebhookMetadata.new(topic: request.topic, shop: request.shop, ..., webhook_id: request.webhook_id)` from unauthenticated headers → call `handler.handle(data: ...)` [3](#0-2) . No `ShopValidator.sanitize!` or any other check on `request.shop` occurs anywhere on this path.

Attacker exploit flow: since the app's webhook endpoint is a public HTTP endpoint, the attacker can POST to it directly with arbitrary headers (Shopify does not authenticate the connection by IP or mTLS in this library). The attacker installs the same target app on their own development shop (a capability explicitly granted to them) and receives one legitimately Shopify-signed webhook delivery — a `(raw_body, x-shopify-hmac-sha256)` pair signed with the app's shared `api_secret_key`. Because that key is shared across all shops that install the app, this signature is valid regardless of which shop it's attributed to. The attacker then replays the exact same `raw_body`+HMAC to the app's endpoint, but substitutes `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) with a victim shop's domain or a different topic/id of their choosing. `HmacValidator.validate` still passes because it never inspects those headers. `Registry.process` then dispatches the handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain, `topic` set to the attacker-chosen topic, causing the host app to write/act on the replayed body as if it belonged to a different tenant.

No existing guard prevents this: `HmacValidator.validate` only proves body integrity/origin, not header integrity; there is no `ShopValidator.sanitize!` call in `Registry.process`; nothing tracks `webhook_id` for replay/idempotency detection; Sorbet's `sig` type checks only enforce that headers are `String`, not that they match the signed payload.

### Impact Explanation
Any header consumed downstream by the host app's handler (`shop`, `topic`, `webhook_id`, `api_version`) is fully attacker-controlled once a single valid `(body, hmac)` pair for the shared app secret has been obtained legitimately (e.g., via the attacker's own installed dev-shop webhook). This enables cross-tenant data corruption/confusion: the app can be made to process a replayed, structurally-valid payload as belonging to an arbitrary victim shop or an arbitrary topic, which is a authentication-bypass-class issue (a forged/misattributed request accepted as authentic for a different tenant). It is repeatable indefinitely against any victim shop domain the attacker chooses to type into the header, using the same captured signature.

### Likelihood Explanation
Preconditions are modest and within the described attacker's granted capabilities: the attacker only needs (1) the app's webhook endpoint to be reachable directly (true for any public HTTP webhook endpoint), and (2) one legitimately obtained `(body, hmac)` pair, obtainable by installing the app on their own free development shop and triggering any webhook topic. No secret material, session, or access token is required. Cost is a single HTTP capture plus a crafted replay request — trivially feasible and fully repeatable.

### Recommendation
Bind the headers that the handler relies on into the signed material, or independently verify them before trusting them: e.g., include `shop`, `topic`, and `webhook_id` in `to_signable_string` (this would require Shopify's delivery side to sign them too, which it currently does not for standard webhooks — so this must instead be mitigated app-side), or require host apps to cross-check `WebhookMetadata#shop` against a known/installed shop list (`ShopValidator.sanitize!` plus a session lookup) and treat `webhook_id` as an idempotency key stored server-side to reject duplicates/replays before invoking `handler.handle`.

### Proof of Concept
```ruby
# test/webhooks/registry_shop_spoof_test.rb
require "test_helper"

class RegistryShopSpoofTest < Test::Unit::TestCase
  def setup
    ShopifyAPI::Context.setup(api_key: "key", api_secret_key: "secret", ...)
    @handler = Class.new do
      include ShopifyAPI::Webhooks::WebhookHandler
      attr_reader :seen_shops
      def initialize; @seen_shops = []; end
      def handle(data:); @seen_shops << data.shop; end
    end.new
    ShopifyAPI::Webhooks::Registry.add_registration(
      topic: "orders/create", delivery_method: :http, path: "/webhooks", handler: @handler,
    )
  end

  def test_same_signature_two_shops
    body = '{"id":1}'
    hmac = Base64.encode64(OpenSSL::HMAC.digest("sha256", "secret", body)).strip

    headers_a = { "x-shopify-topic" => "orders/create", "x-shopify-hmac-sha256" => hmac,
                  "x-shopify-shop-domain" => "attacker-shop.myshopify.com",
                  "x-shopify-webhook-id" => "id-1", "x-shopify-api-version" => "2024-01" }
    headers_b = headers_a.merge("x-shopify-shop-domain" => "victim-shop.myshopify.com")

    ShopifyAPI::Webhooks::Registry.process(ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: headers_a))
    ShopifyAPI::Webhooks::Registry.process(ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: headers_b))

    # Same HMAC accepted for two different shop identities -> broken binding.
    assert_equal ["attacker-shop.myshopify.com", "victim-shop.myshopify.com"], @handler.seen_shops
  end
end
```
Both requests share identical `raw_body`/HMAC, yet `HmacValidator.validate` accepts both and the handler receives two different, attacker-selected shop values for the one signature — demonstrating the binding `HMAC_valid(body) == authenticated(shop)` does not hold.
