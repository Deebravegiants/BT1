### Title
Webhook `shop` domain is trusted for tenant routing without being covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes the webhook HMAC over the raw body only, but the shop identity attached to every processed webhook is read from an unsigned HTTP header. Since the app's `api_secret_key` is shared across every merchant that has installed the app, any unprivileged user who controls their own installation can capture a validly-signed webhook body and replay it against the same endpoint with a different `shop-domain` header, causing the library to hand the handler a victim shop identity for attacker-controlled data.

### Finding Description
`Request#to_signable_string` returns only the raw body, not any header: [1](#0-0) 

`Request#shop` is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header, which is not part of that signable string: [2](#0-1) 

`Registry.process` validates the HMAC against the body only, and then immediately forwards `request.shop` — the unauthenticated header — to the app's handler as the authoritative tenant identity: [3](#0-2) 

The gem's own documentation instructs app authors to treat `data.shop` as "The shop domain of the webhook" with no caveat that it is unauthenticated: [4](#0-3) 

The broken identity binding is:
`HMAC-valid(raw_body) == true` ⇏ `shop-domain header == shop that generated raw_body`

Because the same `api_secret_key`/`client_secret` is used to sign webhooks for every shop that has the app installed (not per-shop), a genuine signature obtained from one tenant (the attacker's own store) remains valid when replayed with a forged `shop-domain` header naming a different, victim tenant.

### Impact Explanation
This breaks the shop-authenticated vs. shop-acted-upon binding described in scope: the value used to route/attribute webhook data (`request.shop`, exposed to handlers as `data.shop`) is never covered by the cryptographic check that gates processing (`Utils::HmacValidator.validate`). Any app that uses `data.shop` to select which tenant's records to create/update/delete (the pattern shown in the gem's own documentation) can be made to attribute attacker-supplied webhook payloads to an arbitrary victim shop, i.e., cross-tenant data injection/corruption through a legitimate signature the attacker obtained for their own tenant.

### Likelihood Explanation
High for any unprivileged attacker: they only need to install the target app on their own free/dev shop (a normal, privilege-free step for any public app), capture one legitimate webhook delivery (body + HMAC), and replay it to the app's known webhook endpoint with the `shop-domain` header changed to the victim's domain. No access to the app's `client_secret`, to the victim's credentials, or to Shopify infrastructure is required.

### Recommendation
Do not treat `request.shop` (or `data.shop`) as authenticated identity on its own. Either:
- Cross-check the header-derived shop against a shop actually known/installed by the app (e.g., verify a session/install record exists for that shop) before acting, or
- Extend `to_signable_string` / a documented verification step to also require and check the shop domain against server-side state, and update `docs/usage/webhooks.md` to explicitly warn that `shop-domain` is not covered by the HMAC and must be independently validated by the host app.

### Proof of Concept
1. Attacker installs the target Shopify app on their own shop `attacker.myshopify.com` (app secret `S` is shared across all shops for this app).
2. Shopify sends attacker a real webhook: body `B`, header `x-shopify-hmac-sha256: HMAC(S, B)`, header `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker POSTs the same `B` and same `hmac` header to the app's webhook endpoint but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(S, B)` — this passes because `B` and the HMAC are untouched (see `Request#to_signable_string`, `lib/shopify_api/webhooks/request.rb:35-38`).
5. `Registry.process` builds `WebhookMetadata.new(topic:, shop: request.shop, body:, ...)` using the forged header (`lib/shopify_api/webhooks/registry.rb:198`), so the app's handler processes `B` as if it originated from `victim.myshopify.com`.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
