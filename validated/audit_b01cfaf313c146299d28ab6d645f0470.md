This confirms the identity-binding gap: `Webhooks::Request#hmac` is computed only over the `to_signable_string` (the raw body), while `shop` is read directly from the `shopify-shop-domain` HTTP header, which is **not covered by the HMAC signature**. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` only proves that the raw body was signed with `Context.api_secret_key`; it says nothing about which shop-domain header accompanied that body. `Registry#process` then trusts `request.shop` and hands it straight to the host application's handler as `WebhookMetadata#shop` without any additional binding check. ### Title
Webhook HMAC does not bind the `shop-domain` header, allowing cross-tenant webhook spoofing (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC signature validated by `Utils::HmacValidator.validate` proves nothing about the `shopify-shop-domain` (or `x-shopify-shop-domain`) header. An attacker who can capture (or otherwise obtain) any single valid `(raw_body, hmac)` pair sent to the app's public webhook endpoint can resend it with an arbitrary `shop-domain` header value, and the gem will treat the forged shop as authentic.

### Finding Description
`Request#hmac` reads the signature from the `hmac-sha256` header, and `to_signable_string` returns just `@raw_body`:
```ruby
sig { override.returns(String) }
def to_signable_string
  @raw_body
end
```
`shop` is derived independently from a header that is never mixed into the signed string:
```ruby
sig { returns(String) }
def shop
  T.cast(shopify_header("shop-domain"), String)
end
```
`Registry.process` validates only the HMAC/body binding, then forwards `request.shop` unchecked to the registered handler:
```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))
end
```
The identity binding that should hold is: `shop-domain header == shop that produced the signed body`. Because the header is excluded from the signable string, this equality is never enforced — `Utils::HmacValidator.validate_signature` only confirms `HMAC(api_secret_key, raw_body) == received_signature`, independent of which shop-domain header is attached to the request.

Since all shops installed under one app share the same `api_secret_key`, any legitimately observed `(body, hmac)` pair (e.g., captured from network logs, a shared proxy, a debugging tool, or a merchant-controlled webhook consumer) remains valid when replayed with a different `shop-domain` header. The gem will pass through `request.shop` = attacker-chosen value as authentic to the host application's webhook handler, which typically uses `shop` as the tenant key to write/update records — resulting in cross-tenant data being attributed to, or acted upon under, the wrong shop.

### Impact Explanation
This breaks the tenant-identity boundary that host applications rely on `WebhookMetadata#shop` to enforce (e.g., which merchant's record to update in `customers/redact`, `shop/redact`, order webhooks, etc.). This matches the Critical class of "cross-tenant access" because a value the app is meant to trust as an authenticated tenant identifier is not actually bound to the cryptographic proof of authenticity.

### Likelihood Explanation
Exploitation requires the attacker to obtain one valid `(raw_body, hmac)` pair sent to the app's webhook receiver for any shop under the app (e.g. via a compromised intermediary, logging, or a shop the attacker controls that receives webhooks under the same app). Given that many apps log inbound webhook payloads/headers for debugging, or forward them through third-party observability tools, capturing one such pair is plausible, after which replay against a different `shop-domain` is trivial and requires no `api_secret_key` knowledge.

### Recommendation
Include the `shop-domain` (and ideally `topic`/`webhook-id`) in the signed material that `to_signable_string` returns, or otherwise independently verify that the shop the app expects to receive a webhook from matches the header claim, e.g. by cross-checking against a known-installed shop list before dispatching to the handler. At minimum:
```diff
 def to_signable_string
-  @raw_body
+  "#{shop}\n#{@raw_body}"
 end
```
Note this diverges from Shopify's actual HMAC scheme (which only signs the body); a more faithful fix is for the host application/gem to independently validate the shop-domain header against the app's known installed-shop set rather than assuming HMAC success implies binding to that header.

### Proof of Concept
1. Attacker obtains any legitimate webhook delivery for the app (body `B` and its valid `X-Shopify-Hmac-Sha256` header `H`), for shop `victim-innocent.myshopify.com` — e.g., by having their own shop `attacker.myshopify.com` installed under the same app and inspecting outbound webhook traffic, or by intercepting logs/proxies that see the app's inbound requests.
2. Attacker resends the exact same body `B` and hmac header `H`, but sets `shopify-shop-domain: other-shop.myshopify.com` (any shop domain string, since it is never HMAC-bound).
3. `Utils::HmacValidator.validate(request)` in `hmac_validator.rb` still returns `true`, because `to_signable_string` only ever returns `B`.
4. `Registry.process` invokes the registered handler with `WebhookMetadata.new(shop: "other-shop.myshopify.com", ...)`, and the host app processes/attributes the webhook data under the spoofed shop, achieving cross-tenant confusion.
