## Analog found

### Title
Fee evasion in `ExternalActionSwap` swaps via a fabricated, attacker-controlled "output token" address - (File: contracts/external-actions/swaps/ExternalActionSwap.sol)

### Summary
`ExternalActionSwap.swap()` computes the amount that owes relay/protocol fees purely from a balance diff (`getERC20OrETHBalance`) on `circomData.erc20TokenAddresses[1]`, an address that is **entirely chosen by the caller** and never checked to be a legitimate, tradable token. Since the caller also fully controls the raw calldata forwarded to the trusted `router` (`LifiExternalAction.callRouter`), a user can substitute a self-deployed contract as the "output token", make it report an arbitrary `balanceOf`, and simultaneously direct the real swap proceeds elsewhere (or receive them and still under-report the observed amount). Fees (`hinkalFee`, `relayFee`) are derived only from the spoofed `swappedAmount`, so the real value extracted by the swap escapes fee collection almost entirely — the direct analog of the reported 0x "refunded ETH" fee bypass, but generalized to any token pair because there is no validation of `erc20TokenAddresses[1]` at all.

### Finding Description
In `swap()`: [1](#0-0) 

`callRouter` (LI.FI variant) computes the swapped amount purely as a balance diff on `outputToken`, using raw, attacker-controlled `externalActionMetadata` as the call to a fixed, trusted `router`: [2](#0-1) 

`getERC20OrETHBalance` simply calls `balanceOf` on whatever address is supplied — nothing constrains it to be a real, honest ERC20: [3](#0-2) 

`erc20TokenAddresses` (which include `outputToken`) are fully caller-supplied circuit public inputs; the circuit only checks internal self-consistency (`inTotal + amountChanges[i] === outTotal`) and pairwise distinctness — it never validates that the address is a genuine token contract: [4](#0-3) 

Because the caller (an unprivileged EOA submitting their own `transact()` proof) controls both `erc20TokenAddresses[1]` and `externalActionData.externalActionMetadata`, they can:
1. Deploy a malicious contract `M` with a spoofable `balanceOf(address)`.
2. Set `erc20TokenAddresses[1] = M` (the declared "output token" of the swap).
3. Craft `externalActionMetadata` so the trusted `router` performs the real swap but routes real proceeds to a destination outside the fee-accounting path (or simply lets `M.balanceOf` under-report the true balance increase).
4. `swappedAmount = getERC20OrETHBalance(M).after - .before` returns an arbitrary attacker-chosen (tiny) number, since `M` is fully attacker-controlled.
5. `hinkalFee`/`relayFee`, and the value later shielded via the resulting UTXO, are all computed from this fabricated `swappedAmount`, not from the actual value the router moved.

This breaks the intended equality that "protocol/relay fee = f(real swap output value)" — here fee = f(fabricated `balanceOf` value of a token the attacker invented), while the real value produced by the trusted router call is moved by an external action but never counted in Hinkal's balance/fee equation.

### Impact Explanation
High: this is theft of protocol/relay fees (a strict superset of the referenced report, which was limited to ETH-vs-ERC20 misclassification). Here, no misclassification trick with two return values is even required — the attacker directly names the "output token" and its balance oracle, so any swap's fee can be reduced to near zero and, depending on where the calldata routes the real proceeds, the shielded note created can be for a self-invented worthless token while the real swapped assets go straight to the attacker.

### Likelihood Explanation
Medium-High. No privileged role, relayer collusion, or upgrade key is required — `transact()` is callable by any user with a valid proof, and both `erc20TokenAddresses` and `externalActionData.externalActionMetadata` are attacker-supplied inputs to that call. The only extra step versus a normal swap is deploying one small helper contract and crafting router calldata, both trivial for a technical attacker.

### Recommendation
Do not trust caller-supplied token addresses as balance oracles for fee computation. Either (a) restrict swap `inputToken`/`outputToken` to a protocol-maintained allowlist of vetted tokens, or (b) require that the router calldata's recipient/swap-destination be provably `address(this)` (e.g., by decoding/validating the LI.FI call parameters on-chain), so that the balance diff used for fee calculation cannot be decoupled from the token actually received.

### Proof of Concept
1. Deploy contract `M` implementing `balanceOf(address)` that returns `0` on the first call and an attacker-chosen small value `x` on the second call (mirroring the original 0x PoC pattern).
2. Generate a Hinkal swap proof with `erc20TokenAddresses = [realInputToken, M]`, `slippageValues[1] = 1` (nonzero), and `externalActionData.externalActionMetadata` crafted to call the trusted `router` such that the real swap output is sent to a destination of the attacker's choosing (or simply accept that `M`'s fake balance under-reports the true output held by the contract).
3. Call `Hinkal.transact()` with this proof; `ExternalActionSwap.swap()`/`LifiExternalAction.callRouter()` compute `swappedAmount = x` regardless of the real value moved by `router`.
4. `hinkalFee`/`relayFee`, computed from `x`, are negligible; the attacker keeps (or diverts) the real swap proceeds while paying near-zero protocol/relay fee.

        CircomData calldata circomData,

            inputAmount -= circomData.feeStructure.flatFee;
        }

        address outputToken = circomData.erc20TokenAddresses[1];

        require(
            circomData.slippageValues[1] != 0,
            "swap output slippage floor not set"
        );

        require(
            block.timestamp <= circomData.timeStamp + SWAP_DEADLINE_WINDOW,
            "swap expired"
        );

        uint256 swappedAmount = callRouter(
            inputToken,
            inputAmount,
            outputToken,
            circomData.externalActionData.externalActionMetadata
        );

        uint256 relayFee = circomData.feeStructure.flatFee;

        uint256 hinkalFee = hinkalHelper.calculateRelayFee(
            swappedAmount,
            0,
            circomData.feeStructure.variableRate
        );

        if (circomData.feeStructure.feeToken == outputToken) {
            sendToRelay(circomData.relay, relayFee + hinkalFee, outputToken);
        } else {
            sendToRelay(
                circomData.relay,
                relayFee,
                circomData.feeStructure.feeToken
            );
            sendToRelay(circomData.relay, hinkalFee, outputToken);
        }

        uint256 totalFee = hinkalFee +
            (outputToken == circomData.feeStructure.feeToken ? relayFee : 0);
        uint256 amountToSendToHinkal = swappedAmount - totalFee;

        transferERC20TokenOrETH(outputToken, msg.sender, amountToSendToHinkal);

    function callRouter(
        address inputToken,
        uint256 inputAmount,
        address outputToken,
        bytes calldata externalActionMetadata
    ) internal override returns (uint256 swappedAmount) {
        uint256 balanceBefore = getERC20OrETHBalance(outputToken);

        if (inputToken == address(0)) {
            (bool success, ) = router.call{value: inputAmount}(
                externalActionMetadata
            );
            require(success, "LI.FI swap failed: native coin");
        } else {
            approveUnlimited(inputToken, router);
            (bool success, ) = router.call(externalActionMetadata);
            require(success, "LI.FI swap failed: erc-20 token");
        }

        swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore;
    }

    function getERC20OrETHBalance(
        address _erc20TokenAddress
    ) internal view returns (uint256) {
        if (_erc20TokenAddress == address(0)) {
            return address(this).balance;
        } else {
            IERC20 outToken = IERC20(_erc20TokenAddress);
            return outToken.balanceOf(address(this));
        }
    }
