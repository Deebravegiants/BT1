## Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop` from the `x-shopify-shop-domain` HTTP header, but the HMAC signature that authenticates the webhook is computed only over the raw request body. Any attacker who can obtain one genuinely-signed webhook body/HMAC pair (e.g. from their own Shopify store on which the app is installed) can replay that exact body and HMAC to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` (or `shopify-shop-domain`) header value. `ShopifyAPI::Webhooks::Registry.process` accepts the request as valid and hands the attacker-chosen `shop` straight to the app's handler, breaking the binding between "the shop the HMAC actually authenticates" and "the shop the request claims to be from."

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read verbatim from a header that is not part of the signed content: [2](#0-1) 

`Utils::HmacValidator.validate` only verifies `verifiable_query.to_signable_string` against the secret — it never binds `shop` (or `topic`, or `webhook_id`) into that signature: [3](#0-2) 

`Webhooks::Registry.process` validates the HMAC and then forwards `request.shop` (the unauthenticated header value) directly to the app's handler as the tenant identifier: [4](#0-3) 

This is the identity-binding break described by the bug class: a field (`shop`) that is acted upon (used as the tenant key passed to `WebhookMetadata`) is not covered by the HMAC that is meant to authenticate the whole request. The equality that should hold — "shop cryptographically bound in the signed payload" == "shop delivered to the handler" — does not hold; only the raw body bytes are authenticated, not the header claiming which shop they belong to.

### Impact Explanation
Because a single `api_secret_key` is shared across all shops using a given app, any unprivileged user who installs the app on their own (potentially free/dev) shop receives genuinely-signed webhook deliveries with a valid HMAC computed over the body. That user can capture the raw body + `X-Shopify-Hmac-SHA256` value and replay it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to target a different, victim shop. `Registry.process` will treat this as an authentic webhook for the victim shop and invoke the app's handler with `shop: <victim-shop>`, `body: <attacker-controlled genuine JSON>`. Depending on how the host application uses `WebhookMetadata#shop` (e.g. to select which shop's local records to create/update/delete), this enables cross-tenant data injection or corruption — a Critical-severity cross-tenant access issue, achieved without ever possessing the target's credentials or the app's `client_secret`.

### Likelihood Explanation
No special privileges are required beyond being able to install the target app on any Shopify store (including a free/development store) to receive at least one legitimately-signed webhook, and the ability to send an HTTP request to the app's public webhook endpoint with a forged header. This is a realistic, low-effort attack path for any internet user targeting a public or freely-installable Shopify app.

### Recommendation
Bind the shop (and other identity-relevant fields such as `topic`/`webhook_id`) into the authenticated material, e.g. by having `Webhooks::Request#to_signable_string` include the shop domain header alongside the body, or by independently verifying the shop against a value obtained via a trusted, per-tenant channel (such as the caller's own stored session for that shop) before trusting `request.shop`. At minimum, document clearly that `request.shop` is not cryptographically authenticated by the webhook HMAC and must not be trusted as a tenant key without additional verification.

### Proof of Concept
1. Attacker creates/owns Shopify store `attacker.myshopify.com` and installs the target app (public webhook endpoint, uses `ShopifyAPI::Webhooks::Registry.process`).
2. Shopify delivers a real webhook to the app for topic `orders/create` with body `B` and header `X-Shopify-Hmac-SHA256: H`, where `H = HMAC-SHA256(secret, B)` — valid per `HmacValidator.validate`.
3. Attacker captures `B` and `H` (e.g., via their own logging/proxy since it is their own store's traffic).
4. Attacker sends a new POST to the app's webhook endpoint with:
   - Body: `B` (unchanged)
   - Header `X-Shopify-Hmac-SHA256: H` (unchanged, still valid because `to_signable_string` only covers `B`)
   - Header `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (changed)
5. `Registry.process` calls `Utils::HmacValidator.validate(request)` — passes, since only the body is checked.
6. `handler.handle(data: WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: parsed_body, ...))` is invoked, and the host application processes attacker-controlled `body` data under the identity of `victim-shop.myshopify.com`.
