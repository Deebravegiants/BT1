### Title
Webhook `shop` identity is trusted from an unauthenticated header, not bound to the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` (and `topic`, `api_version`, `webhook_id`) used to route and process a webhook from raw, unauthenticated HTTP headers, while the HMAC signature verified by `ShopifyAPI::Utils::HmacValidator` only covers the raw request body. This breaks the identity binding between "the request whose authenticity Shopify's shared secret verifies" and "the shop the app processes/dispatches the webhook for," letting anyone who can generate a validly-signed webhook body (e.g. by installing the app on their own shop) relabel it as coming from any other shop.

### Finding Description
`Webhooks::Request#shop` reads directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header: [1](#0-0) 

but the HMAC that is validated only signs `@raw_body`: [2](#0-1) 

`HmacValidator.validate` computes the signature purely from `to_signable_string` (the raw body) and the app's shared `api_secret_key`; it never incorporates `shop`, `topic`, `webhook_id`, or `api_version`: [3](#0-2) 

`Registry.process` treats a passing HMAC check as authorization to dispatch the (attacker-controllable) `shop` value straight to the app's handler: [4](#0-3) 

The identity binding the library implicitly claims to provide is:
```
shop authenticated by HMAC == shop dispatched to handler
```
In reality the HMAC only proves "signed with this app's `api_secret_key`" — it says nothing about which shop the payload is "for." Because a single `api_secret_key` is shared across every shop that installs the app, any unprivileged actor who installs the app on their own store (a routine, self-service action) obtains a stream of genuinely-signed `(raw_body, hmac)` pairs. They can replay any such pair to the app's webhook endpoint while swapping the `X-Shopify-Shop-Domain` header to a victim shop's domain. `HmacValidator.validate` still returns `true` (it never looked at the header), and `Registry.process` calls the handler with `shop: "<victim>.myshopify.com"` and attacker-chosen body content.

### Impact Explanation
If the host app's webhook handler uses `WebhookMetadata#shop` to select which shop's stored access token/session to use, or to scope data mutations (a common and Shopify-documented pattern — see `docs/usage/webhooks.md`), an attacker can cause the app to perform shop-scoped actions (e.g., process an `orders/create`/`app/uninstalled`/other topic body) against a shop they do not own. This is a cross-tenant integrity failure: data belonging to shop B gets processed/mutated as a result of a request the attacker fully controls the content of, merely by spoofing an HTTP header, with no cryptographic binding preventing it. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high for any attacker capable of installing the target app on a store they control (a normal, self-service, unprivileged action for any public/embedded Shopify app) and capable of sending arbitrary HTTP requests to the app's public webhook endpoint (which by design must be internet-reachable). No leaked secrets, TLS interception, or privileged account is required — only spoofing a plain HTTP header.

### Recommendation
Bind the `shop` (and other routing-relevant fields such as `topic`) into the value that is HMAC-verified, or otherwise cryptographically tie the header-derived identity to the verified payload. Concretely:
- Include `shop`, `topic`, `api_version`, and `webhook_id` in the signable string used by `Webhooks::Request#to_signable_string` (this would require coordinating with Shopify's webhook signing scheme), or
- At minimum, document prominently and enforce in `Registry.process` that `request.shop` must be cross-checked by the host application against a shop for which the app already holds a legitimately-obtained session/access token before any shop-scoped action is taken, rather than presenting `shop` as if it were part of the authenticated payload.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (self-service, no privileges needed).
2. Shopify sends a legitimate webhook to the app, e.g. body `{"id":1,...}` with header `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>` and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`. The attacker captures `raw_body` and the valid `hmac`.
3. Attacker POSTs the exact same `raw_body` and `hmac` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds a request whose `hmac` still matches `raw_body` (unchanged) via `HmacValidator.validate`, per:
```ruby
# lib/shopify_api/utils/hmac_validator.rb
computed_signature = compute_signature(verifiable_query.to_signable_string, secret) # only raw_body
OpenSSL.secure_compare(computed_signature, received_signature) # passes
```
5. `ShopifyAPI::Webhooks::Registry.process` passes validation and calls the registered handler with `shop: "victim-shop.myshopify.com"`, even though Shopify never sent a webhook for that shop for this content:
```ruby
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))
``` [4](#0-3) [5](#0-4)
