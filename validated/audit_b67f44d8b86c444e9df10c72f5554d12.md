## Analysis

I traced the bug-class hint ("a field acted on but not covered by the HMAC") through this gem's webhook-verification code path (`lib/shopify_api/webhooks/**` and `lib/shopify_api/utils/hmac_validator.rb`), which sits squarely in the in-scope library surface. [1](#0-0) [2](#0-1) [3](#0-2) 

`Webhooks::Request#to_signable_string` returns only `@raw_body`, and `HmacValidator.validate_signature` computes/compares the HMAC exclusively over that signable string. The `shop` (and `topic`, `webhook_id`, `api_version`) values are read straight from HTTP headers (`shopify-shop-domain`/`x-shopify-shop-domain`) and are never included in the signed payload. `Registry.process` then hands `request.shop` unchecked to the app's handler via `WebhookMetadata`.

The equality this breaks: `shop_bound_by_hmac == shop_delivered_to_handler` does **not** hold — the HMAC only proves *"the body was produced by someone who knows this app's `api_secret_key`"*, not *"this body belongs to the shop named in this header."* Critically, `api_secret_key` is a single value shared by the app across **every** merchant that installs it — it is not a per-tenant secret. That means any unprivileged internet user can install the target app on their own free/dev store, legitimately trigger a webhook (e.g. `orders/create`, `app/uninstalled`), capture a genuinely valid `(raw_body, hmac)` pair signed with the shared app secret, and then POST that exact body + hmac to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with the victim shop's domain. `HmacValidator.validate` still passes (it never looked at the shop header), and `Registry.process` invokes the handler with `shop:` equal to the attacker-chosen victim domain — causing the host application to process attacker-controlled webhook data as if it originated from, and belongs to, the victim tenant.

### Title
Webhook `shop` (and `topic`/`webhook_id`) header is not bound to the HMAC, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw request body, while `shop`, `topic`, `webhook_id`, and `api_version` are taken from unauthenticated HTTP headers. `Utils::HmacValidator` verifies the HMAC solely against the body, so passing verification proves only that *some* installer of the app produced that body — not that it belongs to the shop claimed in the header.

### Finding Description
`HmacValidator.validate_signature` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the received HMAC using `OpenSSL.secure_compare`. For webhook requests, `to_signable_string` returns just `@raw_body`. `shop`, `topic`, and `webhook_id` come from separate, unsigned headers (`shopify_header`). `Registry.process` trusts `request.shop` (and `request.topic`) directly when constructing the `WebhookMetadata` object handed to the app's handler: [3](#0-2) 

Because the `api_secret_key` used to compute the HMAC is a single shared per-app secret (not per-shop), any entity able to install the app on a shop they control can generate a body/HMAC pair that is cryptographically valid for the app but not tied to any particular shop. Replaying that pair with a different `shop-domain` header value passes verification unchanged.

### Impact Explanation
This breaks the tenant-isolation guarantee webhook signature verification is meant to provide: an attacker-controlled webhook payload can be attributed to an arbitrary victim shop merely by controlling the `X-Shopify-Shop-Domain` header, since that header is outside the cryptographic boundary. Depending on how the host app's webhook handler uses `shop` (e.g., looking up the merchant's stored session/access token to act on their behalf, or updating records keyed by shop), this can result in cross-tenant data corruption or actions being taken against/on behalf of a victim shop using attacker-supplied data — a cross-tenant impact.

### Likelihood Explanation
Medium-to-High: no privileged credentials, access tokens, or the app's `client_secret` are required. The attacker only needs to install the target app on a free/dev store they control (a standard, unprivileged action for any public Shopify app) to obtain a validly-signed body/HMAC pair, then send a forged HTTP request with a substituted shop header directly to the app's public webhook endpoint.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the signed material, or otherwise cryptographically tie the header values to the verified request — for example by including the `shop-domain`/`topic` headers in the string that is HMAC'd, or by requiring the receiving application to cross-check `request.shop` against an independently verified installed-shop record before trusting it. At minimum, document prominently that `request.shop`/`request.topic` are **not** covered by the HMAC and must not be trusted as tenant identifiers without additional verification.

### Proof of Concept
1. Attacker signs up for a free Shopify development store (`attacker-shop.myshopify.com`) and installs the target app (uses the app's single shared `api_secret_key`).
2. Attacker triggers a webhook event (e.g. `orders/create`) on their own store, capturing the raw POST body and its valid `X-Shopify-Hmac-Sha256` header — both are legitimate because the app's secret is shared across all installs.
3. Attacker sends a new POST to the victim app's webhook endpoint using the exact captured `raw_body` + `hmac` header, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and desired `X-Shopify-Topic`).
4. `Utils::HmacValidator.validate` succeeds because it only checks the body against the secret [4](#0-3) ; `Registry.process` [5](#0-4)  invokes the app's handler believing the event and body genuinely belong to `victim-shop.myshopify.com`.

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
