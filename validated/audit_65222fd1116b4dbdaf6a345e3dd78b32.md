### Title
A malicious swap route can hide an unrelated token transfer in the user’s authorization tree - ([File: contracts/controller/src/strategies/swap.rs](contracts/controller/src/strategies/swap.rs))

### Summary
`swap_collateral` lets an account owner supply opaque route bytes, which the controller forwards to the configured router after authorizing only the controller’s own input transfer. Because Soroban authorization is tree-based, code reached through an unallowlisted route can add a victim-signed nested `token.transfer(victim, attacker, amount)` beneath the root `swap_collateral` authorization. The controller’s balance checks measure only the strategy input and output; they do not detect unrelated wallet-token transfers authorized through a poisoned route. [1](#0-0) [2](#0-1) 

### Finding Description
`process_swap_collateral` authenticates `caller`, requires ownership or delegation over `account_id`, and passes the caller-supplied `swap` payload to `withdraw_and_swap_from_supply`. [1](#0-0)  That path invokes `swap_tokens`, which snapshots only the controller’s balances of `token_in` and `token_out`, registers one exact controller-to-router transfer authorization, invokes `router.execute_strategy`, and then checks controller input/output deltas. [2](#0-1) 

The exact authorization registered by the controller covers `token_in.transfer(controller, router, amount_in)` and contains no sub-invocations. [3](#0-2)  It does not constrain what the user’s outer `swap_collateral` authorization may contain. If simulation of a malicious route records a child invocation such as `unrelated_token.transfer(victim, attacker, amount)`, and the victim signs that poisoned tree, the host treats it as authorized even though the controller never requested it.

The same authorization-tree exposure applies to the other controller strategy entrypoints that accept route bytes and call the same settlement helper: `multiply`, `swap_debt`, and `repay_debt_with_collateral`. [4](#0-3) 

### Impact Explanation
A victim who signs the simulated authorization tree can lose unrelated tokens held in their wallet, not merely the collateral submitted to the strategy. The malicious child transfer can name any token contract and attacker recipient, while the visible controller call remains a valid `swap_collateral` invocation. Because the transfer is outside the controller’s `token_in`/`token_out` measurements, neither `RouterOverspend` nor `NoSwapOutput` bounds or detects the stolen amount. [5](#0-4) 

This is theft of user funds reachable by an unprivileged attacker that can deploy or select a malicious route component and induce the victim to sign the resulting transaction.

### Likelihood Explanation
The attack requires victim interaction: the victim must submit or sign an authorization tree containing the malicious child invocation. An honest simulation records that child, so a wallet or client that decodes and rejects unexpected children prevents execution. However, opaque route bytes and an unexpected nested authorization are difficult for an ordinary signing flow to understand, and the route can still satisfy the strategy’s own positive-output and final-account-risk checks. [6](#0-5) [7](#0-6) 

### Recommendation
Do not rely on balance deltas as an authorization boundary for caller-supplied routes. Suitable mitigations include:

- constrain routes to governance- or controller-approved venue/pool addresses;
- require the signed `swap` payload to commit to the complete set of contracts that may be invoked;
- make the controller/router reject any route component capable of requesting authorization from the original `caller`;
- require clients to simulate and enforce an exact authorization-tree policy: for controller swaps, reject any child beneath the user’s root authorization that was not explicitly expected.

Until route contracts are constrained, clients should treat any extra child in the signed invocation tree as malicious, even if the swap output appears fair.

### Proof of Concept
1. Victim owns an account containing USDC collateral and also holds an unrelated wallet token.
2. Attacker creates a route whose venue or pool contract, when invoked during `swap_collateral`, calls `unrelated_token.transfer(victim, attacker, victim_balance)`.
3. Victim invokes:
   `controller.swap_collateral(victim, account_id, usdc_key, amount, eth_key, malicious_swap_bytes)`. `swap_collateral` authenticates the victim, verifies ownership/delegation, withdraws the collateral, and forwards `malicious_swap_bytes` to the router. [1](#0-0) 
4. During router execution, the malicious route component requests the unrelated token transfer. Simulation records it as a child under the victim’s `swap_collateral` authorization.
5. The victim signs the poisoned tree. The malicious token transfer executes, while the controller still observes a valid input spend and positive output and completes final risk checks. [2](#0-1) 
6. Result: the unrelated wallet tokens are transferred to the attacker, independently of the collateral amount routed through the strategy.

/// Authorizes, on behalf of the current contract, one `transfer(from, to, amount)`
/// call on `token_addr` made deeper in the next contract call (for example by
/// the pool). The entry allows no further sub-invocations.
pub fn authorize_transfer_as_current(
    env: &Env,
    token_addr: &Address,
    from: &Address,
    to: &Address,
    amount: i128,
) {
    let entry = InvokerContractAuthEntry::Contract(SubContractInvocation {
        context: ContractContext {
            contract: token_addr.clone(),
            fn_name: symbol_short!("transfer"),
            args: (from.clone(), to.clone(), amount).into_val(env),
        },
        sub_invocations: Vec::new(env),
    });
    env.authorize_as_current_contract(vec![env, entry]);
}
