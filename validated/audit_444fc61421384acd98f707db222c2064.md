### Title
Webhook shop-domain identity spoofing via HMAC that only signs the request body, not the `shop`/`topic` headers - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` and `ShopifyAPI::Webhooks::Registry.process` authenticate an incoming webhook solely by validating the HMAC over the raw request body, then hand the caller's *unauthenticated* `shop-domain` header straight to the app's handler as the tenant identifier. This breaks the binding "shop verified by HMAC == shop delivered to the handler," analogous to the `mergeDeep`-style prototype-pollution bug class where a value used to make a security decision is not the value that was actually verified.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` (and `topic`, `webhook_id`, `api_version`) are pulled straight from HTTP headers that are never part of the signed material: [2](#0-1) 

`Registry.process` verifies only the HMAC (which covers the body) and then constructs `WebhookMetadata` using `request.shop` taken directly from the header, with no cross-check that the header value corresponds to the shop that actually produced the signed body: [3](#0-2) 

Contrast this with the OAuth callback flow, where `AuthQuery#to_signable_string` explicitly includes `shop` in the signed parameters, so the shop value is cryptographically bound to the signature: [4](#0-3) 

No equivalent binding exists for webhooks. The gem's own documentation instructs host apps to trust `data.shop` directly after calling `Registry.process`, treating it as an authenticated tenant identifier: [5](#0-4) [6](#0-5) 

Because the HMAC never covers the `shop-domain` header, any body+HMAC pair that is valid for shop A (e.g. obtained by installing the app on an attacker-controlled development store and capturing a real webhook delivery) remains a byte-for-byte valid HMAC when replayed with the `shop-domain` header rewritten to shop B. `HmacValidator.validate` will report success because it only recomputes/compares the HMAC of the body: [7](#0-6) 

The equality this breaks is: **shop cryptographically authenticated by the app's `client_secret` HMAC == shop identifier consumed by the app's webhook handler for tenant/session lookup**. The gem lets these two diverge.

### Impact Explanation
Per the documented usage pattern, apps key their per-tenant data/session lookups off `data.shop` from `WebhookMetadata` without any additional verification, since the gem's own contract is "`Registry.process` ... will verify the request did indeed come from Shopify." An attacker who is a legitimate (even free/dev-store) merchant of the target app can capture a real, validly-signed webhook body from their own store's install and replay it to the app's webhook endpoint with the `shop-domain` header changed to any victim shop the attacker chooses. If the app trusts `data.shop` to select which tenant's records/session to mutate (as the docs recommend), this yields cross-tenant data confusion/corruption — writing or triggering side effects against a shop the attacker does not control, using a payload the attacker fully controls (since the body originates from their own store). This matches the "cross-tenant access" impact bucket.

### Likelihood Explanation
Exploitation requires only: (1) installing the target app on an attacker-owned or throw-away development store to obtain one real, validly-HMAC-signed webhook delivery, and (2) resending that request to the same public webhook endpoint with a forged `shop-domain`/`X-Shopify-Shop-Domain` header. Both steps are achievable by an unprivileged internet user/merchant with no access to the app's `client_secret`, access tokens, or TLS interception — it is a pure header/body decoupling bug in the verification logic itself.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) values into the signed material that `HmacValidator` checks, or otherwise cryptographically tie the header-derived shop to the verified payload (e.g., include the shop domain in the canonical string that is HMAC'd, or cross-validate the header shop against a shop value embedded in the JSON body when available). At minimum, update `docs/usage/webhooks.md` to explicitly warn that `data.shop` is not covered by the HMAC and must not be treated as authenticated on its own; recommend that host apps independently verify the shop against a known/registered shop set before using it as a tenant key.

### Proof of Concept
1. Install the target app on an attacker-owned development store `attacker.myshopify.com`, triggering Shopify to send a real webhook (e.g. `orders/create`) to the app's registered endpoint. Capture the raw body `B` and the `X-Shopify-Hmac-Sha256` header value `H` (valid because `H = HMAC-SHA256(client_secret, B)`).
2. Replay the captured request to the same endpoint, keeping `raw_body = B` and `X-Shopify-Hmac-Sha256 = H` unchanged, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` builds `hmac` from `H` and `shop` from the forged header: [8](#0-7) 
4. `ShopifyAPI::Webhooks::Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `B` only and matches `H`, so validation succeeds despite the forged shop: [9](#0-8) 
5. The registered handler is invoked with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com", body: attacker_controlled_body ...)`, causing the host app to act on victim-shop's tenant context using attacker-controlled webhook content.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
