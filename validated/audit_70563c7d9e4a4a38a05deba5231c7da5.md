The documentation explicitly states that `ShopifyAPI::Webhooks::Registry.process` "will verify the request did indeed come from Shopify" (`docs/usage/webhooks.md` line 125) and hands the app a `shop` field it presents as verified data (`docs/usage/webhooks.md` lines 12-16). This is exactly the trust boundary the gem promises and breaks internally.

### Title
Webhook shop-domain identity spoofing via HMAC that only covers the request body - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, excluding the `shop-domain`, `topic`, `api-version`, and `webhook-id` headers from the HMAC-covered bytes. `ShopifyAPI::Webhooks::Registry.process` validates that HMAC and then trusts `request.shop` (parsed directly from the unauthenticated `shopify-shop-domain` header) as the tenant identity passed to the app's handler.

### Finding Description
`Webhooks::Request` implements `Utils::VerifiableQuery` with: [1](#0-0) [2](#0-1) 

`to_signable_string` returns only `@raw_body`, so `HmacValidator.validate` (which HMAC-signs `to_signable_string` with the app's shared `api_secret_key`) never covers `shop`, `topic`, `webhook_id`, or `api_version`: [3](#0-2) 

`Registry.process` checks only that HMAC, then forwards `request.shop` (i.e., the raw `shopify-shop-domain` header) unchanged to the handler as the identified tenant: [4](#0-3) 

The equality the gem is supposed to guarantee is: `shop asserted in the authenticated bytes == shop delivered to the handler`. Instead, the gem guarantees only `HMAC(api_secret_key, raw_body) == received_hmac`, while `shop` is read from a header that sits entirely outside that signature.

Because `api_secret_key` is the app's single client secret shared across every merchant that installs the app (not a per-shop secret), any merchant who installs the app receives legitimately-signed `(raw_body, hmac)` pairs for webhook events they themselves can trigger (e.g. `orders/create` in their own store). An attacker who controls a shop that has installed the app can:
1. Trigger a real webhook event in their own shop to obtain a body + HMAC that is validly signed with the app's `api_secret_key`.
2. Replay that exact `(raw_body, hmac)` pair to the app's webhook endpoint while substituting the `shopify-shop-domain` header (and, if desired, `webhook_id`/`topic`, though the same body must decode to a topic the app has a handler for) with a victim shop's domain.
3. `HmacValidator.validate` passes because it only checks the body bytes, and `Registry.process` calls the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: attacker-controlled data, ...)`.

The app author, following the documented contract that `process` "will verify the request did indeed come from Shopify" and that `data.shop` is "The shop domain of the webhook", has no library-provided way to know `shop` was not actually authenticated.

### Impact Explanation
This breaks the tenant identity binding at the core of webhook processing: an attacker with no privileged credentials (only the ability to install the app on a shop they control, and to trigger ordinary events in that shop) can inject attacker-controlled webhook payloads that the app processes as if they originated from a different (victim) shop. This is a cross-tenant access vector — the app's downstream logic (e.g., updating order data, triggering fulfillment actions, or store-scoped business logic keyed on `data.shop`) can be poisoned with attacker data attributed to another tenant.

### Likelihood Explanation
The attacker only needs to be an ordinary merchant who installs the target app (a normal, unprivileged flow), capture one legitimate webhook body+HMAC pair from their own shop, and replay it with a modified `shop-domain` header to the app's public webhook endpoint. No access token, `client_secret`, or victim credentials are required.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the HMAC-signed bytes (or otherwise cryptographically bind them to the payload) so that `HmacValidator.validate` fails if any of these identity fields are altered independently of the signed body — mirroring the fix pattern of binding all security-relevant fields into a single signable string, as already done for `Auth::Oauth::AuthQuery#to_signable_string`.

### Proof of Concept
1. App installs on attacker's shop `attacker.myshopify.com`; attacker triggers `orders/create`, and Shopify sends the app a real webhook: body `B`, headers include `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: HMAC(api_secret_key, B)`.
2. Attacker replays to the app's webhook endpoint the same body `B` and same HMAC header, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process(ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: replayed_headers))` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(api_secret_key, B)` (matches, since only `B` is signed) and returns `true`. [5](#0-4) 
4. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", body: B's parsed content, ...)`, processing attacker-controlled data under the victim's tenant identity.
