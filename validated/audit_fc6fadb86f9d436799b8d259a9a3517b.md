### Title
`computeTonConnectHash` encodes `domain_len` as UTF-16 code-unit count instead of UTF-8 byte length, diverging from the relayer's hash for non-ASCII domains - (File: `packages/intents-sdk/src/intents/intent-hashes/ton-connect.ts`)

### Summary
`computeTonConnectHash` builds the TON Connect sign-data message as `0xffff || "ton-connect/sign-data/" || wc || addr || domain_len || domain || ts || "txt" || payload_len || payload`, but computes `domain_len` from JavaScript's string `.length` property rather than the byte length of the UTF-8 encoded domain. For any `domain` containing non-ASCII characters (e.g. `пример.рф`), this produces a different length field — and therefore a different SHA-256 hash — than the byte-accurate reference implementation (`multi.rs`) that intents.near/relayer use to compute `intent_hash`.

### Finding Description
The claimed equality is:
`computeIntentHash(mp) == relayer intent_hash(mp)` for all valid `ton_connect` MultiPayloads.

In `computeTonConnectHash` [1](#0-0)  the payload text length is computed correctly from the encoded bytes (`payloadData = new TextEncoder().encode(payloadSchema.text)`, then `payloadData.length`), but the domain length is computed as:

```
numberToBigEndian(domain.length, 4),
new TextEncoder().encode(domain),
```

`domain.length` is the number of UTF-16 code units in the JS string, not the number of UTF-8 bytes that `TextEncoder().encode(domain)` actually produces and appends to the message. For an ASCII-only domain the two values coincide, but for a domain containing multi-byte UTF-8 characters (e.g. Cyrillic `пример.рф`, where each Cyrillic letter is 1 UTF-16 code unit but 2 UTF-8 bytes), `domain.length` undercounts the true byte length. This means the 4-byte big-endian length field embedded in the hash preimage differs from what a byte-accurate implementation (matching the on-chain/relayer Rust `multi.rs` logic, which uses byte length per the TON Connect off-chain signing spec) would produce.

Since SHA-256 is preimage-sensitive, any divergence in the byte sequence — including this length-field mismatch — yields a completely different hash. The locally computed `computeIntentHash` result for a payload with a non-ASCII domain will not match the `intent_hash` returned by `get_status`/the relayer for the same signed payload.

Existing guards do not catch this: there is no validation step that cross-checks the SDK-computed hash against a relayer-returned hash before use, and the only existing regression test for `ton-connect.ts` covers raw vs. user-friendly address equivalence, not domain encoding [2](#0-1) . The general `computeIntentHash` test suite exercises a non-ASCII `café` case only for `erc191`, not for `ton_connect` domains [3](#0-2) , so this divergence is untested.

### Impact Explanation
`computeIntentHash`/`computeTonConnectHash` feeds into `IntentsSDK.signAndSendIntent` (via `IntentExecuter`) and is the mechanism an integrator would use to independently derive the `intent_hash` for reconciliation against tickets returned by `sendSignedIntents` [4](#0-3) . If an integrator locally recomputes the hash for a `ton_connect` payload with a non-ASCII domain and compares it to the `intent_hash` used by `getIntentStatus`/the relayer, the values will not match. A settled withdrawal would then appear unmatched/missing under the integrator's locally computed key, potentially causing the integrator to treat it as not-yet-settled and re-issue/re-send the withdrawal — a status misreport leading to a double payout, matching the "High" impact category (status/hash misreport causing an integrator to credit/refund twice).

### Likelihood Explanation
Preconditions: the attacker (an ordinary TON wallet user) only needs to sign with any dApp/domain string containing non-ASCII characters (a fully realistic scenario for non-English TON dApps or IDN domains, e.g. `пример.рф`) and go through the normal `ton_connect` signing flow. No privileged access, malicious relayer, or misuse of an escape hatch is required — this is triggered by ordinary use with a legitimate domain string that just happens to be non-ASCII. It is deterministic and repeatable on every call with such a domain, not merely theoretical: the divergence is confirmed directly by inspecting the source, since `domain.length` (UTF-16 units) is provably not equal to `TextEncoder().encode(domain).length` (UTF-8 bytes) whenever the domain contains non-ASCII characters.

### Recommendation
Compute `domain_len` from the UTF-8 encoded byte length instead of the JS string `.length`:
```ts
const domainBytes = new TextEncoder().encode(domain);
...
numberToBigEndian(domainBytes.length, 4),
domainBytes,
```
Reuse the same `TextEncoder`-encoded buffer for both the length prefix and the body, exactly as is already done correctly for `payloadData`. Add a regression test with a non-ASCII domain (e.g. `пример.рф` or `café.com`) verifying the hash against a reference/relayer-derived value.

### Proof of Concept
```ts
// packages/intents-sdk/src/intents/intent-hashes/ton-connect.non-ascii.test.ts
import { describe, expect, it } from "vitest";
import type { MultiPayload } from "@defuse-protocol/contract-types";
import { computeTonConnectHash } from "./ton-connect";

describe("computeTonConnectHash non-ASCII domain", () => {
	it("uses UTF-8 byte length, not UTF-16 code-unit count, for domain_len", () => {
		const basePayload = {
			standard: "ton_connect",
			address:
				"0:fa63f5195b0f8682d3f3413e2b40decfae7778b3691748a2d55dae5b243a3054",
			domain: "пример.рф", // 9 UTF-16 code units, but 16 UTF-8 bytes
			timestamp: 1762354640,
			payload: { type: "text", text: "hello world" },
			public_key: "ed25519:F8PB56zdMYNDL7Mq43DV4cV17uRqQkpn6ZygNdqavXCr",
			signature: "ed25519:not-checked-by-hash-fn",
		} satisfies Extract<MultiPayload, { standard: "ton_connect" }>;

		const hash = computeTonConnectHash(basePayload);

		// Reference: byte-accurate implementation (matching Rust multi.rs / TON Connect spec)
		const domainBytes = new TextEncoder().encode(basePayload.domain);
		expect(domainBytes.length).not.toEqual(basePayload.domain.length); // 16 !== 9, proving the divergence exists

		// The SDK's hash embeds domain.length (9) as domain_len, not domainBytes.length (16).
		// Therefore it does not equal the hash computed with the correct byte length,
		// which is what the relayer/on-chain multi.rs implementation would produce.
		// (Full equality assertion requires a fixture with a relayer-derived intent_hash
		// for the same signed payload, per the "Fast validation" instructions.)
	});
});

		multiPayloads: MultiPayload[];
		quoteHashes?: string[];

		const tickets = await this.intentRelayer.publishIntents(

				quoteHashes: args.quoteHashes ?? [],
			},
			{ logger: args.logger },

	public async signAndSendIntent(
		args: SignAndSendArgs,
	): Promise<IntentPublishResult> {
		const intentSigner = args.signer ?? this.intentSigner;
		assert(intentSigner != null, "Intent signer is not provided");

		const intentExecuter = new IntentExecuter({
			envConfig: this.envConfig,
			logger: args.logger,
			intentSigner,
			intentRelayer: this.intentRelayer,
			intentPayloadFactory: args.payload,
			onBeforePublishIntent: args.onBeforePublishIntent,
		});

		const { ticket } = await this.withSaltRetry(args, async (salt) =>
			intentExecuter.signAndSendIntent({
				intents: args.intents,
				salt,
				relayParams: args.relayParams,
				signedIntents: args.signedIntents,
			}),
		);

		return { intentHash: ticket };
	}
