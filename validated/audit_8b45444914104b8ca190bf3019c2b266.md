### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant impersonation - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body, while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from unauthenticated HTTP headers. [3](#0-2)  `Registry.process` validates the request solely via `Utils::HmacValidator.validate(request)`, which recomputes and time-safe-compares the HMAC over `to_signable_string` (i.e., the body only) and then forwards `request.shop` (the raw header value) to the app's handler as the authoritative tenant identifier. [4](#0-3) [5](#0-4) 

### Finding Description
The identity binding broken is: `shop` field trusted by the app for tenant context == `shop` field cryptographically authenticated by the HMAC. In this gem, that equality does not hold — `to_signable_string` in `Request` only includes `@raw_body` [6](#0-5) , so the HMAC proves only that the *body bytes* originated from a holder of `api_secret_key`; it proves nothing about which shop, topic, or webhook id the sender claims via headers. `Registry.process` then constructs `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` straight from those unauthenticated headers and hands it to the app's registered handler as the trusted tenant/topic context. [7](#0-6)  An attacker who controls any shop (e.g., their own free/dev store) can trigger a real webhook to obtain a genuinely valid `(body, HMAC)` pair signed with the app's real `api_secret_key`, then POST that same body/HMAC pair directly to the app's public webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header value. Because the header is never part of the signed material, the forged request passes `HmacValidator.validate` unchanged, and the handler receives attacker-chosen `shop` (and `topic`/`webhook_id`) values as if Shopify had authenticated them for that shop.

### Impact Explanation
Apps built on this gem are documented to trust the webhook's `shop` value for tenant routing and typically use it as a session-store/tenant key when persisting or acting on webhook data. [2](#0-1)  Since `shop` is unauthenticated, an attacker can make the app associate attacker-controlled webhook `body` content with a victim shop's tenant context, i.e., cross-tenant data injection/confusion — this meets the Critical "cross-tenant access" bar, achieved purely by an unprivileged internet user with network access to the app's public webhook endpoint and control of any Shopify shop of their own.

### Likelihood Explanation
Likelihood is moderate-to-high: no `api_secret_key` leak or privileged account is needed. The attacker only needs a legitimate webhook from any store they control (trivially obtainable) and the ability to POST to the target app's public webhook URL with modified headers, which is standard unauthenticated HTTP access.

### Recommendation
Bind the `shop`, `topic`, `webhook_id`, and `api_version` values into the HMAC-covered signable string (or otherwise cryptographically authenticate them, e.g., by validating `shop` against a Shopify-signed component), so `HmacValidator.validate` fails if any of these headers are altered after signing.

### Proof of Concept
1. Attacker's own store `attacker.myshopify.com` has a webhook registered to the target app's endpoint; attacker triggers an event (e.g., updates a product) to receive a genuine POST with body `B` and header `x-shopify-hmac-sha256: H` (valid for secret key `S`).
2. Attacker replays: `POST /webhooks` with body `B`, header `x-shopify-hmac-sha256: H` (unchanged), but `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Registry.process` calls `HmacValidator.validate(request)`, which only hashes `@raw_body` (`B`) and compares to `H` — validation passes. [8](#0-7) 
4. `WebhookMetadata` is built with `shop: "victim-shop.myshopify.com"` and the attacker's chosen body, and the app's handler processes/stores it under the victim shop's tenant context. [7](#0-6)

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
