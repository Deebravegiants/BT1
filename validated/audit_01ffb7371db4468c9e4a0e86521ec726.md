### Title
Unrestricted `CallDispatcher.dispatch()` combined with persistent ERC-20 allowances enables theft of tokens transiting the shared dispatcher across unrelated orders/transfers - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
The reported ERC777 bug class is: an unprivileged actor pre-configures a piece of *shared, persistent, external state* (an ERC1820 interface registration) via a permissionless call, which later hijacks or blocks funds that pass through a shared execution context belonging to a *different* user's transaction. Hyperbridge has a structurally identical primitive: `CallDispatcher` is a single, chain-wide singleton contract used by `IntentGatewayV2` (predispatch/postdispatch calldata execution) and by every `HyperFungibleToken`/`WrappedHyperFungibleToken` deployment (calldata execution on mint/unlock) to route arbitrary tokens through arbitrary `Call[]`. Its `dispatch()` entrypoint has **no caller restriction whatsoever** — anyone can invoke it directly, not just the gateway contracts that are supposed to be its only legitimate callers.

### Finding Description
`CallDispatcher.dispatch()` is fully public and unauthenticated: [1](#0-0) 

Any address — not just `IntentGatewayV2` or a `HyperFungibleToken` instance — can call `dispatch()` with an arbitrary `Call[]` targeting any contract, including ERC-20 tokens that the dispatcher will later hold. This lets an attacker pre-set persistent state on the dispatcher, e.g. `IERC20(TOKEN).approve(attacker, type(uint256).max)`, at zero cost and at any time, since `approve()` does not require the caller to hold a balance.

The dispatcher is a shared, chain-wide singleton referenced by address in `Params.dispatcher` and used across many unrelated flows:
- `IntentGatewayV2.placeOrder` predispatch: assets are transferred to `dispatcher`, `dispatch()` is invoked with attacker-order-controlled calldata, and only the tokens listed in `order.inputs` are swept back: [2](#0-1) 
- `IntentsBase._execute` postdispatch: `dispatch()` is invoked with the order's output calldata, and the sweep loop **only iterates over `order.output.assets`** (`outputsLen`), not the dispatcher's full token surface: [3](#0-2) 
- `HyperFungibleToken.onAccept` and `WrappedHyperFungibleToken.onAccept` route `message.data` through the very same `ICallDispatcher(_dispatcher).dispatch(...)` call on every incoming cross-chain mint/unlock: [4](#0-3) 

Because ERC-20 allowances are permanent on-chain state, any allowance the attacker grants themselves via a direct, unauthenticated `dispatch()` call persists indefinitely and is not scoped to any particular order or user. If the dispatcher ends up holding *any* balance of that token — whether from dust left over after an intermediate swap step whose resulting token isn't among the accounted `order.output.assets`/`order.inputs`, or from any other application (HFT, WrappedHFT, future IntentGatewayV2 orders) that also routes that token through the same shared dispatcher — the attacker can immediately drain it with `transferFrom(dispatcher, attacker, amount)` using the pre-existing allowance, without needing to participate in or control the victim's transaction at all.

The project's own documentation acknowledges the dispatcher accumulates residual token balances and calls out unlimited-allowance risk, but frames it only as a self-risk for the order's own calldata author, not as a cross-user attack surface enabled by the completely unrestricted `dispatch()` entrypoint: [5](#0-4) 

### Impact Explanation
This allows an unprivileged attacker to pre-position a standing, unlimited ERC-20 allowance on a shared, protocol-critical contract (`CallDispatcher`) at zero cost, then later drain any tokens of that type that transiently or residually sit on the dispatcher as a result of *any other user's* order fill, order placement, or HyperFungibleToken cross-chain delivery that happens to route or leave dust of that same token through the shared dispatcher. This is a concrete theft-of-funds vector reachable from a single, permissionless transaction, matching the report's DoS/theft bug class of "an unprivileged party can manipulate a piece of shared external state that a victim's transaction unknowingly relies on."

### Likelihood Explanation
Likelihood is Medium: calling `dispatch()` directly to set an approval costs only gas and requires no special conditions, and the dispatcher is deliberately designed to be a shared, chain-wide singleton used by multiple independent applications and many different token types. The actual drain is opportunistic — it depends on the dispatcher later holding a non-zero balance of the pre-approved token, which can arise from unaccounted intermediate-swap dust (tokens not listed in `order.output.assets`/`order.inputs`, and thus never swept) or from any other flow (HFT/WrappedHFT calldata execution) that transiently moves that token through the same dispatcher.

### Recommendation
Restrict `CallDispatcher.dispatch()` so it can only be called by the trusted application contracts that are meant to use it (e.g., an allow-list of `IntentGatewayV2` / `HyperFungibleToken` / `WrappedHyperFungibleToken` addresses configured at deployment, or make the dispatcher single-purpose per calling contract instead of a shared singleton). Additionally, harden the dust-sweep logic in `IntentsBase._execute` and the predispatch transfer logic in `IntentGatewayV2.placeOrder` to sweep the dispatcher's *full* balance of any token touched during execution (not just the tokens explicitly listed in `order.output.assets`/`order.inputs`), and consider having the dispatcher revoke any allowances it granted immediately after each `dispatch()` call completes.

### Proof of Concept
1. Attacker calls `CallDispatcher.dispatch(abi.encode([Call({to: TOKEN_X, value: 0, data: abi.encodeWithSelector(IERC20.approve.selector, attacker, type(uint256).max)})]))` directly — no access control blocks this call: [6](#0-5) 
2. This grants `attacker` a standing max allowance over `CallDispatcher`'s balance of `TOKEN_X`, independent of any specific order.
3. Any later, unrelated user places or fills an order (or triggers an HFT calldata-execution transfer) whose `predispatch`/`output.call` routes `TOKEN_X` through the same dispatcher and leaves an un-swept residual balance (e.g., an intermediate-hop token from a multi-step swap that isn't among the accounted `order.output.assets`): [7](#0-6) 
4. Attacker calls `TOKEN_X.transferFrom(dispatcher, attacker, balance)` using the pre-existing allowance from step 1, draining tokens that belonged to the protocol/other users, with no interaction with or permission from the victim's transaction required.

        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }

### Security

The `CallDispatcher` executes calls in its own context (not via `delegatecall`), so the HFT contract's storage is never at risk. If any call in the array reverts, the entire `onAccept` handler reverts — including the token mint/unlock. The request can then be retried by any relayer until the timeout expires. If no successful execution occurs before the timeout, the request times out and the sender is eligible for a refund on the source chain. Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution.

Existing `CallDispatcher` deployments are listed on the [contract addresses](/developers/evm/contract-addresses/mainnet) page.
