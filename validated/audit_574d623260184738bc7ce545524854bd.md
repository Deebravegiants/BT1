### Title
Unchecked ERC20 `transfer` return value in `IntentGatewayV2.withdraw()`/`SweepDust` on Tron can silently fail while escrow accounting is finalized, permanently losing user/beneficiary funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` deliberately avoids `SafeERC20.safeTransfer` for outbound token payouts and instead performs a raw low-level call to the `transfer` selector, checking only that the call itself did not revert — not that the token's returned boolean actually indicates success. This is the exact same bug class as `FootiumPrizeDistributor.claimERC20Prize()`: escrow/accounting state is updated (or the order is marked filled/refunded) regardless of whether the token transfer logically succeeded.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol`, the contract imports and applies `SafeERC20` (`using SafeERC20 for IERC20;`) and correctly uses `safeTransferFrom` for pulling funds in (e.g. `placeOrder`), but for paying tokens *out* to beneficiaries it uses a manual low-level call pattern instead of `safeTransfer`: [1](#0-0) 

```solidity
if (token == address(0)) {
    (bool sent,) = beneficiary.call{value: amount}("");
    if (!sent) revert InsufficientNativeToken();
} else {
    (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
    if (!success) revert TransferFailed();
}

_orders[body.commitment][token] -= amount;
```

`success` here only reflects whether the low-level call reverted — it does **not** decode or check the ABI-encoded `bool` return value that a spec-compliant `transfer()` returns. Any ERC20/TRC20 token that signals failure by returning `false` (rather than reverting) will make `token.call(...)` return `success == true` even though zero tokens moved. Despite this, the escrow balance `_orders[body.commitment][token]` is decremented and (in `withdraw()`) the order is marked filled via `_filled[body.commitment] = beneficiary;`, and an `EscrowReleased`/`EscrowRefunded` event is emitted — so the protocol believes the beneficiary was paid.

The same unchecked pattern recurs across the file for every outbound token payout path:
- `withdraw()` escrow releases (lines ~702-708)
- Transaction-fee payout in `withdraw()` (line ~720)
- `SweepDust` handling in `onAccept()` (line ~674)
- Internal sweep-back calldata built via `Call` structs in `placeOrder`/fill flows (lines ~279, ~433) that construct `abi.encodeWithSelector(IERC20.transfer.selector, ...)` calldata for the `ICallDispatcher` to execute, whose results are only checked for `balance` deltas afterward. [2](#0-1) [3](#0-2) 

By contrast, the equivalent shared library used by the mainnet gateway, `IntentsBase.sol`, correctly uses `safeTransfer` for the identical operation: [4](#0-3) 

confirming that the Tron file's raw `.call` + `success`-only check is a regression/divergence from the safe pattern used elsewhere, and not an intentional Tron-specific workaround (OpenZeppelin's `SafeERC20._callOptionalReturn` already handles no-return-value tokens correctly, so there was no need to bypass it).

### Impact Explanation
`withdraw()` is reachable from `onAccept()` for `RedeemEscrow`/`RefundEscrow` request kinds after `authenticate(incoming.request)` succeeds — i.e., via a relayed, authenticated cross-chain message completing a user's cross-chain intent order: [5](#0-4) 

If the escrowed token is a non-standard ERC20/TRC20 that returns `false` on failed transfers (e.g., due to a paused state, denylist, or insufficient balance drained by a reentrant/race condition) rather than reverting, the beneficiary receives no tokens, yet:
1. The escrow accounting (`_orders[commitment][token]`) is decremented as if paid.
2. The order is marked `_filled[commitment] = beneficiary`, permanently preventing any retry or alternative recovery of the escrowed funds.
3. `EscrowReleased`/`EscrowRefunded` events falsely report success.

This results in a permanent, unrecoverable loss of user/solver funds already escrowed in the contract — the funds remain stuck in the contract (or effectively burned from the user's perspective) with no path to reclaim them since the order is marked as finalized.

### Likelihood Explanation
Likelihood depends on the escrowed/output token behaving as a non-reverting-on-failure ERC20 (returns `false` instead of reverting), which is a known real-world pattern (e.g., some legacy or denylist-capable tokens, and notably relevant given this file explicitly targets Tron, where TRC20 token implementations vary and non-compliant behavior is common). Since the same manual `.call` pattern is used across every disbursement path in the contract, a single non-compliant listed token or an edge condition (e.g., token pausing/blacklisting the recipient) is sufficient to trigger fund loss on any withdrawal/sweep for that token.

### Recommendation
Replace all outbound `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `evm/tron/contracts/apps/IntentGatewayV2.sol` with `IERC20(token).safeTransfer(...)` (the contract already has `using SafeERC20 for IERC20;` and uses it for inbound transfers), so that both call failure and a `false` return value cause a revert, keeping escrow state and token movement atomic and consistent — mirroring the pattern already used in `IntentsBase.sol`.

### Proof of Concept
1. Deploy `IntentGatewayV2` (Tron variant) with a mock ERC20 token whose `transfer()` returns `false` when the recipient is blacklisted/paused (instead of reverting), simulating a real non-compliant TRC20 token.
2. Place and fill a cross-chain order so tokens become escrowed for a beneficiary in `_orders[commitment][token]`.
3. Blacklist/pause the beneficiary address on the mock token so `transfer()` returns `false`.
4. Trigger `onAccept()` with a `RedeemEscrow` request for that commitment (simulating the authenticated relayed message).
5. Observe: `withdraw()` calls `token.call(...)`, which returns `success == true` (no revert) even though the token internally returned `false` and moved no funds; `_orders[commitment][token] -= amount` executes, `_filled[commitment]` is set, and `EscrowReleased` is emitted — yet the beneficiary's token balance is unchanged, and the escrowed funds are now unrecoverable.
