### Title
Webhook `shop-domain` header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `ShopifyAPI::Utils::HmacValidator.validate` verifies the HMAC exclusively against that raw body. The `shop` field, however, is read straight from the unauthenticated `shopify-shop-domain` / `x-shopify-shop-domain` header and is passed on as the tenant identity to the app's webhook handler. Since the shop identity is never part of the signed content, an attacker can take a validly-signed webhook body (which they can legitimately obtain by triggering a webhook to their own shop, since the app's `api_secret_key` — and therefore the HMAC — is shared across every shop that installs the app) and resubmit it with the `shop-domain` header set to a victim shop, producing a request that passes HMAC validation but is attributed to the wrong tenant.

### Finding Description
The identity binding that should hold is:
`hmac_verified_content == tenant_identity_used_by_handler`

In `Request#to_signable_string`, only `@raw_body` is included:
```ruby
sig { override.returns(String) }
def to_signable_string
  @raw_body
end
``` [2](#0-1) 

`Request#shop` reads the shop identity from a header that is not part of `to_signable_string`:
```ruby
sig { returns(String) }
def shop
  T.cast(shopify_header("shop-domain"), String)
end
``` [4](#0-3) 

`Registry.process` validates the HMAC over the body only, then unconditionally trusts `request.shop` and forwards it to the app-supplied handler as the tenant for this event:
```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
``` [3](#0-2) 

Because Shopify signs webhooks with an app-wide secret (`api_secret_key`) shared by every installation of the app, and because that secret only signs the body, a `(raw_body, hmac)` pair valid for one shop is equally valid for a different shop's `shop-domain` header. This mirrors the report's bug class of "checking/authorizing against the wrong or uncovered field" — here the HMAC covers the body, but the value actually used to determine *which tenant this event belongs to* is a completely separate, unauthenticated header.

### Impact Explanation
This breaks the tenant/shop identity boundary that host applications rely on `WebhookMetadata#shop` to enforce (e.g., looking up the correct shop's session, writing data scoped to that shop, or reacting to `shop/redact` / `customers/redact` compliance topics). An attacker who is a legitimate (unprivileged) user of the app on their own shop can capture one of their own valid webhook deliveries and replay it against the app's endpoint with a forged `shop-domain` header, causing the host app to process attacker-controlled data as if it originated from the victim shop — a cross-tenant data injection/spoofing primitive that matches the "High: cross-tenant access" criteria.

### Likelihood Explanation
Any merchant/developer who installs the app on their own store can trigger a webhook delivery to capture a legitimately signed `(body, hmac)` pair, since the HMAC secret is shared across all shops for a given app. Replaying that pair with a modified `shop-domain` header requires no special access — it's a straightforward unauthenticated HTTP replay against the app's public webhook endpoint. No access to the app's `api_secret_key` or any credentials is needed.

### Recommendation
Bind the shop identity into the signed content that is verified, or verify it out-of-band against a trusted source before use:
- Include `shop-domain` (and ideally `topic`/`webhook-id`) in the signable string used for HMAC validation instead of only the raw body, or
- After HMAC validation, cross-check `request.shop` against the shop of an existing, previously-stored session/webhook registration before invoking the handler, rejecting shops that are not known/expected for this delivery.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com`.
2. Trigger any registered webhook topic (e.g., `products/update`) and capture the raw HTTP request, including the body and the `x-shopify-hmac-sha256` header — this HMAC is valid because it's computed with the app's shared `api_secret_key` over the body only.
3. Resend the exact same body and HMAC header to the app's webhook endpoint, but change `x-shopify-shop-domain` to `victim.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` succeeds because it only checks the body against the HMAC (`request.rb` lines 35-38), and `Registry.process` forwards `shop: "victim.myshopify.com"` to the app's handler (`registry.rb` lines 188-199), causing the host application to process the payload as an event from the victim shop.
