### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant shop spoofing during webhook processing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC of the raw request body, but the `shop` value that is handed to the application's webhook handler is read from an unauthenticated HTTP header. The identity binding `shop-domain header == shop covered by HMAC` does not hold, so the `shop` field acted on by the handler is not the field verified by the signature.

### Finding Description
`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` and compares it to the received signature: [1](#0-0) 

For webhooks, `to_signable_string` is defined as just the raw body — none of the HTTP headers are part of the signed payload: [2](#0-1) 

The `shop` accessor, however, is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header, with no cryptographic tie to the HMAC or the body: [3](#0-2) 

`Registry.process` validates only the HMAC (i.e., body integrity) and then forwards `request.shop` — the unauthenticated header — directly into the `WebhookMetadata` passed to the app's handler: [4](#0-3) 

The documented handler contract explicitly instructs the app to trust `data.shop` as the tenant identifier for follow-up actions (e.g., looking up per-shop records, enqueuing per-shop jobs): [5](#0-4) 

Because `shop` is excluded from the signed string, the equality the app implicitly relies on — `shop used to route/attribute the webhook == shop verified by HMAC` — is broken. Any entity able to produce a body + HMAC pair that validates against the app's `api_secret_key` (e.g., an unprivileged internet user who is themselves a legitimate merchant on the platform and thus knows a valid `(body, hmac)` pair for their own shop's webhook traffic, since the same shared `client_secret`/HMAC algorithm is used for all shops of an app) can replay that same `body`/`hmac` pair while substituting an arbitrary `shop-domain` header value naming a victim shop. `Registry.process` will accept it as authentic and dispatch it to the handler labeled with the attacker-chosen shop, since nothing in the verification path binds the header to the signed bytes.

### Impact Explanation
This falls under "cross-tenant access" (Critical) in the rules: an attacker can cause the app to process attacker-controlled body content under an arbitrary victim shop's identity, since the app's handler contract (as documented by this gem) trusts `data.shop` for attributing/persisting webhook data per tenant. Depending on how the host app uses `data.shop` (e.g., updating that shop's cached data, triggering per-shop side effects, resource lookups keyed by shop), this can lead to cross-tenant data corruption or confusion — data belonging to shop A being written into or associated with shop B's tenant context, without ever needing shop B's credentials.

### Likelihood Explanation
Likelihood is moderate-to-high for apps that follow the gem's documented pattern literally (using `data.shop` from `WebhookMetadata` as the trust anchor for the tenant). Any user who can register an app on their own store (a normal, unprivileged action — creating a Shopify dev/partner store is free) automatically obtains a legitimate `(body, hmac)` pair usable against the target app's webhook endpoint, since webhook signing is per-app (via `client_secret`), not per-shop. No secrets belonging to the victim shop or the app owner are required.

### Recommendation
Bind the shop identity to the signed payload before trusting it:
- Include `shop-domain` (and ideally `topic`, `webhook-id`, `api-version`) in the HMAC-signed string, or
- Cross-check `request.shop` against the shop associated with the specific `webhook_id`/subscription that was registered via the GraphQL Admin API (`Registry` already tracks registrations per shop when calling `register`/`unregister`), rejecting the webhook if the header-provided shop does not match the shop on record for that `webhook_id`.
- At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must not be used as a tenant-authorization boundary without additional verification.

### Proof of Concept
1. Attacker installs the target app on their own Shopify store `attacker-shop.myshopify.com` and subscribes it to a webhook topic the app handles (e.g. `orders/create`).
2. Shopify sends a legitimate webhook to the app's endpoint for `attacker-shop.myshopify.com`; the attacker captures the exact `raw_body` and the corresponding `x-shopify-hmac-sha256` value (both are visible to them since it is their own store/traffic and TLS terminates at their own infrastructure/proxy or via a controlled webhook relay).
3. Attacker crafts a new POST to the app's webhook endpoint using the exact same `raw_body` and `x-shopify-hmac-sha256` value, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses this and `Utils::HmacValidator.validate` succeeds because it only checks `raw_body` against the HMAC — the `shop-domain` header is irrelevant to the check: [4](#0-3) 
5. The app's handler receives `WebhookMetadata` with `shop == "victim-shop.myshopify.com"` and `body` fully controlled by the attacker (from their own shop's webhook), and performs whatever per-shop action the app implements (e.g., persisting order data, updating cached shop state) attributed to the victim shop.

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
