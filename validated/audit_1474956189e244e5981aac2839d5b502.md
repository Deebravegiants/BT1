### Title
Webhook `shop` (and `topic`/`webhook_id`) identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, and `Utils::HmacValidator.validate` HMACs that string against `Context.api_secret_key` (the app's single shared client secret, identical for every installed shop). The `shop` value handed to the app's `WebhookHandler` via `WebhookMetadata` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, which is never part of the signed material.

### Finding Description
The relevant flow:
- `Request#to_signable_string` returns `@raw_body` only [1](#0-0) 
- `Request#shop` is derived purely from the header, unauthenticated by the signature [2](#0-1) 
- `HmacValidator.validate`/`validate_signature` compute the HMAC only over `verifiable_query.to_signable_string` (i.e., the raw body) using the app's single `api_secret_key` [3](#0-2) 
- `Registry.process` validates the HMAC and then immediately trusts `request.shop` as the tenant identity passed to the handler [4](#0-3) 
- `WebhookMetadata.shop` is the exact value the host application uses to attribute the webhook to a merchant [5](#0-4) 

Because the app's `api_secret_key`/client secret is the same for all shops that install the app (it is not per-shop), any attacker who installs the app on their own shop can capture a legitimately signed `(raw_body, hmac)` pair from a real webhook delivery to their shop. The equality the gem should enforce is: `shop-header-in-signed-payload == shop-header-used-for-tenant-attribution`. Instead the gem enforces only `HMAC(raw_body, api_secret_key) == received_hmac`, which is satisfied independently of the `shop` header's value. The attacker can then replay that exact `(raw_body, hmac)` pair to the target app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. `Utils::HmacValidator.validate` still returns `true` (the body and secret are unchanged), so `Registry.process` calls the registered `WebhookHandler#handle` with `WebhookMetadata.shop` set to the victim's domain, even though the body content actually originated from the attacker's own shop.

### Impact Explanation
This breaks the tenant/shop identity binding that host applications rely on to attribute webhook data to the correct merchant. Depending on how the app uses `WebhookMetadata.shop` (e.g., to look up the merchant's session/access token and write attacker-controlled data — orders, customer records, fulfillment status, `shop/redact` or `customers/redact` compliance events — into the victim shop's stored state), this enables cross-tenant data injection/confusion using only the identity binding defect in this gem's webhook verification path. This matches the High-severity class of "scope or expiry check bypass" style identity-binding failures called out in scope, since the verified bytes (body) are decoupled from the identity claim (`shop`) acted upon.

### Likelihood Explanation
Exploitation requires only an unprivileged attacker to run their own Shopify store, install the target app themselves (a normal, unprivileged action), capture one genuine webhook delivery (raw body + `X-Shopify-Hmac-Sha256` header) to their own shop, then POST that same body/hmac to the app's webhook endpoint with a forged `X-Shopify-Shop-Domain` header pointing at any other shop the app serves. No secrets, tokens, or privileged access to the victim are needed.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) header values into the signed payload verification, or otherwise cryptographically bind the header set to the body before trusting `request.shop`. Concretely, change `Request#to_signable_string` to include the shop domain (and other identity-bearing headers) canonically, and update `HmacValidator` documentation/usage so host apps cannot be misled into trusting `WebhookMetadata.shop` without independently checking it against a known/registered shop for the session that installed the webhook — e.g., cross-check `request.shop` against the shop associated with the webhook subscription/registration before invoking the handler.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker.myshopify.com` and triggers a webhook (e.g., `orders/create`) with an attacker-controlled payload.
2. Shopify delivers the webhook to the app's endpoint with headers `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`, and the JSON body.
3. Attacker captures the raw body and the `X-Shopify-Hmac-Sha256` value.
4. Attacker crafts a new HTTP request to the same app endpoint, re-using the identical raw body and `X-Shopify-Hmac-Sha256` value, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
5. The app calls `ShopifyAPI::Webhooks::Registry.process(request)`; `Utils::HmacValidator.validate` recomputes HMAC over the (unchanged) raw body with the app's single `api_secret_key` and returns `true`. [6](#0-5) 
6. The registered `WebhookHandler#handle` is invoked with `WebhookMetadata.shop == "victim.myshopify.com"`, causing the app to process attacker-supplied data as if it belonged to the victim shop.
