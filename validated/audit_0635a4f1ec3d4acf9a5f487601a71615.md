Audit Report

## Title
ERC20Transactor credits/moves a fixed requested amount instead of the actual ERC20 balance delta, breaking XCM asset accounting for non-standard ERC20 tokens - (File: `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`)

## Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `ERC20Transactor::deposit_asset_with_surplus` move ERC20 tokens via `IERC20::transferCall` through `pallet_revive::Pallet::bare_call`, but only inspect the call's revert status and boolean return value rather than verifying the actual balance delta on the `TransfersCheckingAccount` or beneficiary. This mirrors the classic fee-on-transfer/non-standard-token accounting flaw: the `AssetsInHolding` credit is set to the requested `amount` unconditionally on a successful-looking call, regardless of how many tokens actually moved.

## Finding Description
In `withdraw_asset_with_surplus`, a `transfer(checking_account, amount)` call is issued and, if it doesn't revert and decodes to `true`, the function unconditionally credits `AssetsInHolding::new_from_fungible_credit` with `Erc20Credit(amount)` [1](#0-0) . Symmetrically, `deposit_asset_with_surplus` issues `transfer(beneficiary, amount)` from the checking account and treats a `true` return as full success without checking the beneficiary's balance increase [2](#0-1) . Neither function calls `balanceOf` before/after to confirm the actual amount moved.

The asset id used to select the target contract is unrestricted: `ERC20Matcher` matches any `Location` of the form `(0, [AccountKey20 { key, .. }])` via `IsLocalAccountKey20`/`AccountKey20ToH160`, with no registry or allow-list requirement, unlike `ForeignAssetsConvertedConcreteId` which requires explicit registration [3](#0-2) . This transactor is wired directly into Asset Hub Westend's `AssetTransactors` tuple consumed by the XCM executor [4](#0-3) .

## Impact Explanation
The `TransfersCheckingAccount` is a single shared account (`ERC20TransfersCheckingAccount`, a `PalletId`-derived account) used for all withdraw/deposit operations against a given ERC20 contract [5](#0-4) . If a non-standard (fee-on-transfer/rebasing) contract is referenced, the XCM holding register credited by `withdraw_asset_with_surplus` will not match the real token balance actually received by the checking account. A subsequent `deposit_asset_with_surplus` attempting to move the full accounted amount out of the checking account can then revert (insufficient real balance), causing the XCM instruction to fail and the assets to be trapped (`AssetsTrapped`). This is a concrete accounting/state divergence bug reachable in-code, matching the reported class of vulnerability.

## Likelihood Explanation
The path requires no privileged role: `ERC20Matcher` accepts any `AccountKey20` location without registration, and a signed account can invoke `pallet_xcm::execute` to run a local XCM program (e.g., `WithdrawAsset`/`DepositAsset`) referencing an attacker-deployed `pallet-revive` contract. The only precondition is that the attacker deploys/uses a non-standard ERC20 contract, which is fully within an unprivileged user's control.

## Recommendation
Query `balanceOf` for the relevant account before and after the `transfer()` call in both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus`, and use the observed delta — not the requested `amount` — to construct the `AssetsInHolding` credit and to determine success/failure. Alternatively, restrict `ERC20Matcher` to an explicitly vetted/allow-listed set of ERC20 contracts guaranteed to implement standard, non-fee-on-transfer semantics.

## Proof of Concept
1. Deploy a `pallet-revive` contract implementing `IERC20` whose `transfer()` deducts a fee (e.g., 5%) but still returns `true`.
2. Submit an XCM program via `pallet_xcm::execute` with `WithdrawAsset` for `Asset { id: Location(0, [AccountKey20 { key: <contract address> }]), fun: Fungible(100) }` from the signed origin's own account.
3. `withdraw_asset_with_surplus` calls `transfer(checking_account, 100)`; the contract moves only 95 tokens to the checking account but returns `true`; the function still returns `AssetsInHolding` credited with `Erc20Credit(100)`.
4. A subsequent `DepositAsset` instruction attempting to move the full "100" out of the checking account causes `deposit_asset_with_surplus` to call `transfer(beneficiary, 100)` from an account holding only 95 real tokens, causing a revert, XCM instruction failure, and asset trapping (`AssetsTrapped`) — demonstrating the accounting/reality mismatch.

/// `Contains<Location>` implementation that matches locations with no parents,
/// a `PalletInstance` and an `AccountKey20` junction.
pub struct IsLocalAccountKey20;
impl Contains<Location> for IsLocalAccountKey20 {
	fn contains(location: &Location) -> bool {
		matches!(location.unpack(), (0, [AccountKey20 { .. }]))
	}
}

/// Fallible converter from a location to a `H160` that matches any location ending with
/// an `AccountKey20` junction.
pub struct AccountKey20ToH160;
impl MaybeEquivalence<Location, H160> for AccountKey20ToH160 {
	fn convert(location: &Location) -> Option<H160> {
		match location.unpack() {
			(0, [AccountKey20 { key, .. }]) => Some((*key).into()),
			_ => None,
		}
	}

	fn convert_back(key: &H160) -> Option<Location> {
		Some(Location::new(0, [AccountKey20 { key: (*key).into(), network: None }]))
	}
}

/// [`xcm_executor::traits::MatchesFungibles`] implementation that matches
/// ERC20 tokens.
pub type ERC20Matcher =
	MatchedConvertedConcreteId<H160, u128, IsLocalAccountKey20, AccountKey20ToH160, TryConvertInto>;
