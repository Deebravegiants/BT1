## Title
Solver-controlled `amount_in` in exact-out quotes is not bounded against fair market value - ([File: packages/internal-utils/src/solverRelay/getQuote.ts])

## Summary
`matchesRequest` (lines 119-138) only verifies the fixed side of an exact-out request (`amount_out === exact_amount_out`) and the asset identifiers; it never checks whether the free side (`amount_in`) is close to fair value. `getFeeQuote` in `estimate-fee.ts` uses `exact_amount_out` as its primary path and returns `quote` directly with no post-hoc sanity check on `quote.amount_in`, unlike its own `exact_in` fallback branch which does bound `amount_out` to `<=1.5x` of `feeAmount`.

## Finding Description
The broken equality: `feeEstimation.quote.amount_in` (debited from the user via the `token_diff` intent) must be bounded by the real market cost of `feeAmount` units of `feeAssetId`. In practice nothing enforces this bound on the primary exact-out path.

- `getFeeQuote` (`packages/intents-sdk/src/lib/estimate-fee.ts:62-80`) calls `solverRelay.getQuote` with `exact_amount_out: feeAmount.toString()`. If this succeeds, the raw `quote` is returned immediately with no ratio/price check — contrast with the fallback branch (lines 139-160) which computes `actualRatio = amount_out * SCALE / feeAmount` and throws if `actualRatio > 1500n` (i.e., >1.5x), plus a floor check. That fallback protection **does not exist** for the primary exact-out branch.
- Inside `solverRelay/getQuote.ts`, `handleQuoteResult` filters quotes via `matchesRequest` (lines 119-138): for exact-out requests it only checks `BigInt(quote.amount_out) === BigInt(quoteParams.exact_amount_out)` and the two `defuse_asset_identifier_*` fields. `quote.amount_in` is completely unchecked.
- `sortQuotes` (lines 96-113) picks the minimum `amount_in` only *among competing quotes returned in the same relay response*. If only one solver responds (or the relay returns a single quote), there's no competitor to filter an inflated `amount_in`.
- The returned quote flows into `OmniBridge.createWithdrawalIntents` (`packages/intents-sdk/src/bridges/omni-bridge/omni-bridge.ts:304-315`), which builds a `token_diff` intent debiting `-${quote.amount_in}` of `tokenAssetId` and crediting `quote.amount_out` of `feeAssetId` — directly using the attacker-controlled `amount_in` with no further validation. `validateWithdrawal` (lines 332-534) checks `feeEstimation.amount > 0n` and underlying-fee-specific `>0` assertions, but never bounds `amount_in`/`feeEstimation.amount` against a market price ceiling.

Exploit flow: a malicious/permissionless solver responds to the exact-out quote request (`tokenAssetId -> feeAssetId`, `exact_amount_out = feeAmount`) with a quote where `amount_out === feeAmount` (satisfying `matchesRequest`) but `amount_in` set arbitrarily high (e.g., 1000x fair value). If it's the only quote returned (or relay picks it as best due to no competing quotes), `getFeeQuote` returns it unmodified, and the SDK signs a `token_diff` intent debiting that inflated `amount_in` from the user.

## Impact Explanation
The user's signed `token_diff` intent debits an attacker (solver)-controlled, essentially unbounded amount of `tokenAssetId` in exchange for a small fixed `feeAmount` of `feeAssetId`, directly draining user funds to the solver. This matches "Critical - a fee error draining a material share of the amount" (or higher, since it's not merely a fee but the entire withdrawal fee-funding leg being fully solver-controlled with no cap). This affects any bridge route that calls `getFeeQuote` for fee funding (Omni Bridge, Aurora Engine Bridge, Direct Bridge, Hot Bridge — confirmed via grep of `getFeeQuote` usage across bridge files), and is repeatable on every withdrawal that needs fee-asset conversion.

## Likelihood Explanation
Preconditions: the attacker only needs to be a permissionless solver capable of responding to relay quote requests (explicitly in-scope per the rules: "a permissionless solver answering a quote"). No special routing/token state is required beyond a withdrawal needing `getFeeQuote` (fee asset != token asset), which is common (e.g., paying NEAR-denominated relayer fees for non-NEAR withdrawal tokens). Attacker cost is minimal — just answering the relay's RFQ with an out-of-market `amount_in`; the existing guards (`matchesRequest`, `sortQuotes`, `assert` checks in `validateWithdrawal`) do not catch this because none of them compare `amount_in` to any price reference on the exact-out path. Feasibility is high whenever there's no competing quote (e.g., low-liquidity fee routes, thin markets, or if the solver relay for a given asset pair has few competing market makers), and is fully repeatable per withdrawal call.

## Recommendation
Add a price-sanity check on the exact-out branch of `getFeeQuote` (mirroring the existing fallback's ratio check), e.g., look up the market prices for `tokenAssetId`/`feeAssetId` and reject the quote if `amount_in` exceeds fair value by more than a configurable multiplier (as already implemented for `amount_out` in the exact-in fallback). Alternatively, enforce a bound inside `matchesRequest`/`handleQuoteResult` in `solverRelay/getQuote.ts` requiring the unfixed side to be within an acceptable multiple of an independently-sourced reference price before accepting a single-solver quote.

function matchesRequest(
	quote: Quote,
	quoteParams: GetQuoteParams["quoteParams"],
): boolean {
	if (
		quote.defuse_asset_identifier_in !==
			quoteParams.defuse_asset_identifier_in ||
		quote.defuse_asset_identifier_out !==
			quoteParams.defuse_asset_identifier_out
	) {
		return false;
	}

	// Only the side fixed by the request is verified; the other side is what the
	// solver competes on (max amount_out for exact_in, min amount_in for
	// exact_out). Compare as BigInt so formatting differences don't matter.
	if (quoteParams.exact_amount_in != null) {
		return BigInt(quote.amount_in) === BigInt(quoteParams.exact_amount_in);
	}
	return BigInt(quote.amount_out) === BigInt(quoteParams.exact_amount_out);
