### Title
`validateZcashAddress()` accepts checksum-invalid t1/t3 transparent addresses, allowing signed PoA `WITHDRAW_TO` withdrawals to unbroadcastable Zcash addresses - ([File: packages/intents-sdk/src/lib/validateAddress.ts])

### Summary
`validateZcashAddress()` validates Zcash transparent addresses (`t1`/`t3`) with a bare regex on length and Base58 charset only, never decoding the payload or verifying the SHA256d checksum that real Zcash Base58Check addresses carry. Every sibling implementation in the same file (Bitcoin, Litecoin, Tron, Dash) decodes the Base58 payload and checks the 4-byte checksum, but Zcash transparent addresses do not. A string that matches `/^t[13][a-km-zA-HJ-NP-Z1-9]{33}$/` but has a corrupted or entirely fabricated checksum passes `validateAddress()`/`validateWithdrawal()`, gets embedded into a signed `ft_withdraw` intent's `WITHDRAW_TO:<addr>` memo, and is submitted to `intents.near`, debiting the user's balance for an address that a real Zcash node/relayer cannot accept.

### Finding Description
The broken equality is: **"address accepted by `validateZcashAddress()`" == "address that is a valid, checksum-correct Zcash Base58Check transparent address that the PoA bridge relayer can actually broadcast to."**

`validateZcashAddress()` at [1](#0-0)  only regex-tests the string:
```
if (address.startsWith("t1") || address.startsWith("t3")) {
    return /^t[13][a-km-zA-HJ-NP-Z1-9]{33}$/.test(address);
}
```
It never calls `base58.decode()` and never verifies a checksum, unlike every comparable function in the file: `validateBtcBase58Address` [2](#0-1) , `validateTronBase58Address` [3](#0-2) , `validateDashAddress` [4](#0-3) , and `validateLitecoinBase58Address` [5](#0-4) , all of which decode the payload and compare the trailing 4 bytes against `sha256(sha256(payload))`.

Reachable path: a caller invokes `PoaBridge.validateWithdrawal()` with `destinationAddress` set to a Zcash transparent address whose checksum bytes are wrong but whose length/charset satisfy the regex. `validateAddress(args.destinationAddress, Chains.Zcash)` returns `true` at [6](#0-5) , so `validateWithdrawal` proceeds. `createWithdrawalIntents` then builds the `ft_withdraw` intent whose memo is `WITHDRAW_TO:<address>` via `createWithdrawIntentPrimitive`/`createWithdrawMemo` [7](#0-6) . This intent is signed and submitted through `intents.near`, which debits the user's balance — `intents.near`'s own signature/nonce checks have no notion of "is this a real Zcash address," so they do not catch the defect. Only later, when the PoA relayer attempts to actually pay out on the Zcash network, will the malformed checksum be discovered — by which point the debit inside `intents.near` has already happened.

No other guard closes this gap: `compareAddresses` only compares two strings for equality/self-transfer, not checksum validity; `FeeExceedsAmountError`/`getUnderlyingFee` deal with fee arithmetic, not address correctness; `matchesRequest` and the contract's signature/nonce checks operate on the intent structure, not on whether the embedded destination string is a real, checksummed address.

### Impact Explanation
The user's own funds are debited from `intents.near` and committed into a signed `ft_withdraw` intent referencing a destination string that cannot be delivered on the actual Zcash network. Because the withdrawal has already been signed and the balance already moved inside the intents contract, recovery depends entirely on manual intervention by the PoA bridge/relayer operators — this matches the **High** category ("a withdrawal stuck until manual intervention"). It is repeatable on every call with a fresh checksum-corrupted t1/t3 string, and it uniquely affects Zcash transparent addresses since every sibling Base58Check validator in the same module performs the checksum check that this one omits.

### Likelihood Explanation
No special privileges are required — any SDK caller (a NEAR Intents user, or an integrator forwarding a counterparty-supplied `destinationAddress`) can pass an arbitrary 35-character string starting with `t1`/`t3` composed of valid Base58 characters. Generating such a string (e.g., by corrupting one character of a real Zcash address, or fabricating one from scratch) is trivial and costs nothing. The only precondition is that the withdrawal route targets a Zcash asset through `PoaBridge`.

### Recommendation
Decode the Base58 payload for `t1`/`t3` addresses and verify the SHA256d checksum and version bytes, mirroring `validateBtcBase58Address`/`validateDashAddress`/`validateTronBase58Address`:
```
const decoded = base58.decode(address); // expect 26 bytes: 2-byte prefix + 20-byte hash + 4-byte checksum
// check decoded[0..2] against {0x1c,0xb8} (t1) or {0x1c,0xbd} (t3)
// check decoded[22..26] against sha256(sha256(decoded[0..22])).slice(0,4)
```

### Proof of Concept
```ts
import { describe, it, expect } from "vitest";
import { base58 } from "@scure/base";
import { sha256 } from "@noble/hashes/sha2";
import { validateAddress } from "../src/lib/validateAddress";
import { Chains } from "../src/lib/caip2";

function buildValidT1Address(): string {
  const version = new Uint8Array([0x1c, 0xb8]); // t1 prefix
  const hash160 = new Uint8Array(20).fill(1);
  const payload = new Uint8Array([...version, ...hash160]);
  const checksum = sha256(sha256(payload)).subarray(0, 4);
  return base58.encode(new Uint8Array([...payload, ...checksum]));
}

describe("validateZcashAddress checksum gap", () => {
  it("accepts a t1 address with a corrupted checksum (equality broken)", () => {
    const valid = buildValidT1Address();
    expect(validateAddress(valid, Chains.Zcash)).toBe(true); // legit address: both sides agree

    // Corrupt one character while keeping regex-valid length/charset.
    const corrupted = valid.slice(0, -1) + (valid.at(-1) === "1" ? "2" : "1");

    // Real Zcash Base58Check decoding would reject `corrupted` (bad checksum).
    const decoded = base58.decode(corrupted);
    const payload = decoded.subarray(0, decoded.length - 4);
    const checksum = decoded.subarray(decoded.length - 4);
    const expected = sha256(sha256(payload)).subarray(0, 4);
    const realZcashWouldAccept = checksum.every((b, i) => b === expected[i]);
    expect(realZcashWouldAccept).toBe(false);

    // But the SDK's validator still says it's valid — the equality is broken.
    expect(validateAddress(corrupted, Chains.Zcash)).toBe(true);
  });
});
```
This demonstrates that `validateAddress(corrupted, Chains.Zcash) === true` while the same string is not a valid checksummed Zcash address, i.e. the address that would pass `PoaBridge.validateWithdrawal()` and get signed into a `WITHDRAW_TO` memo is not guaranteed to be broadcastable on the real Zcash network.

```typescript
function validateBtcBase58Address(address: string): boolean {
	const decoded: Uint8Array = base58.decode(address);

	// version (1) + hash160 (20) + checksum (4) = 25 bytes
	if (decoded.length !== 25) return false;

	const version = decoded[0];
	// 0x00 = P2PKH mainnet, 0x05 = P2SH mainnet
	if (version !== 0x00 && version !== 0x05) return false;

	const payload = decoded.subarray(0, 21);
	const checksum = decoded.subarray(21, 25);
	const expectedChecksum = sha256(sha256(payload)).subarray(0, 4);

	for (let i = 0; i < 4; i++) {
		if (checksum[i] !== expectedChecksum[i]) return false;
	}
	return true;
```

```typescript
function validateTronBase58Address(address: string): boolean {
	try {
		const decoded = base58.decode(address);

		if (decoded.length !== 25) return false;

		// The first 21 bytes are the address data, the last 4 bytes are the checksum.
		const data = decoded.slice(0, 21);
		const checksum = decoded.slice(21);

		const expectedChecksum = sha256(sha256(data)).slice(0, 4);
		for (let i = 0; i < 4; i++) {
			if (checksum[i] !== expectedChecksum[i]) return false;
		}

		return data[0] === 0x41;
	} catch {
		return false;
	}
}
```
