## Title
Webhook `shop-domain` and `topic` headers are trusted without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` verifies webhook authenticity via `Utils::HmacValidator.validate`, but the signable string used for that HMAC check is the raw request body only. The `shop` (from the `X-Shopify-Shop-Domain` header) and `topic` fields — which the host application uses to identify *which tenant* and *which event* the webhook belongs to — are read directly from unauthenticated HTTP headers and are never included in the HMAC-covered payload.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop` and `topic` are pulled straight from headers with no cryptographic binding to the body or to each other: [2](#0-1) 

`Utils::HmacValidator.validate` computes the expected signature purely from `verifiable_query.to_signable_string` (the body) and compares it to the `hmac-sha256` header: [3](#0-2) 

Because the app's `client_secret` (the HMAC key) is shared across *every* shop that installs the app, any shop that legitimately installs the app can obtain a validly-signed webhook body (e.g. by triggering any webhook topic on their own store). That attacker-controlled body/HMAC pair remains valid regardless of which `X-Shopify-Shop-Domain` or `X-Shopify-Topic` header is sent alongside it, since those headers are excluded from `to_signable_string`. An attacker can therefore replay a legitimately-signed webhook body while substituting an arbitrary target shop domain in the header. Any host application that trusts `Request#shop` (or `#topic`) to route/attribute the event to a tenant — the documented purpose of this accessor — will process the payload as if it originated from a different merchant than the one who actually signed it.

This breaks the intended identity binding:
`shop-domain header used to attribute event == shop that produced the HMAC-signed body`
which does not hold, since the shop identity is never part of the signed bytes.

### Impact Explanation
This is a cross-tenant confusion vulnerability: an unprivileged attacker who can install the app on their own (attacker-controlled) shop can forge webhook events that appear to originate from any other shop domain, because the `shop`/`topic` headers used for tenant/event attribution are not bound to the HMAC. Depending on how the host app uses `Webhooks::Request#shop` (e.g., updating per-shop data, processing `app/uninstalled`, `customers/redact`, or other mandatory compliance webhooks), this can lead to cross-tenant data manipulation or spoofed compliance events for shops the attacker does not control. Per the impact rubric, this qualifies as cross-tenant access (Critical).

### Likelihood Explanation
Any developer/attacker can install the target app on a shop they control (free/dev store), which is enough to receive one legitimately-signed webhook body/HMAC pair. Replaying that body with a forged `Shop-Domain` header requires only crafting an HTTP request to the app's own webhook endpoint — no access to `client_secret`, tokens, or privileged accounts is needed. Likelihood is high wherever the host app trusts `Request#shop`/`#topic` for tenant routing, which is their documented purpose.

### Recommendation
Include `shop` and `topic` (and ideally `webhook_id`) in the HMAC-signable string, or otherwise cryptographically bind them to the raw body before exposing `Request#shop`/`#topic` to consumers, so that the verified signature also attests to the tenant and event type — not just the body bytes.

### Proof of Concept
1. Install the target app on an attacker-owned development shop (`attacker.myshopify.com`), and trigger any webhook subscription (e.g., `orders/create`) to receive a request with a valid `X-Shopify-Hmac-SHA256` computed over the JSON body using the app's shared `client_secret`.
2. Capture the raw body and the valid HMAC header value.
3. Replay this exact body + HMAC to the app's webhook endpoint, but replace `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com` (and optionally change `X-Shopify-Topic`).
4. `ShopifyAPI::Utils::HmacValidator.validate` succeeds because it only checks the body bytes via `Request#to_signable_string` [1](#0-0) ; the host application then reads `Request#shop` [4](#0-3)  and processes the event as though it came from `victim-shop.myshopify.com`.
