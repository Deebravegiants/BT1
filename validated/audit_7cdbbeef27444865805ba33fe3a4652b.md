### Title
`PoaBridge.describeWithdrawal` matches withdrawals by `assetId` only, misreporting `txHash`/status across batched same-asset withdrawals with different `destinationAddress` - ([File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts])

### Summary
`findMatchingWithdrawal` in `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts` selects a withdrawal from the POA bridge's unsorted status response solely by matching `nep141:${w.data.near_token_id} === assetId`, ignoring `destinationAddress` and the batch `index`. When a single `processWithdrawal`-style call batches two withdrawals of the same `assetId` to two different `destinationAddress`es, `Array.prototype.find` deterministically returns the same (first-matching) entry for both `describeWithdrawal(index=0)` and `describeWithdrawal(index=1)` calls, so both indices report the identical `status`/`transfer_tx_hash`, which is only actually correct for one of them.

### Finding Description
The claimed equality is: `WithdrawalStatus(index_i) == outcome(withdrawal_i)` for each `i` in a batch. The code in `describeWithdrawal` (poa-bridge.ts:313-343) computes:

```
const withdrawal = findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId);
```

and `findMatchingWithdrawal` (poa-bridge.ts:418-427) does:

```
return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
```

This ignores `args.destinationAddress` and `args.index` entirely (the `index` field of `WithdrawalIdentifier` is present on `args` but never consulted). If two withdrawals in the same batch share `assetId` but differ in `destinationAddress`, both `describeWithdrawal` calls (for index 0 and index 1) run against the exact same `response.withdrawals` array (since they use the same `withdrawal_hash`/`args.tx.hash`), and `Array.find` returns the *same* entry both times (the first match) — the second call's real matching withdrawal is never selected, so its actual `transfer_tx_hash` is never surfaced for that index; instead the first entry's status/hash is reported for both.

The code itself acknowledges this exact limitation in the comment directly above the function (poa-bridge.ts:409-416): "NOTE: Currently only matches by assetId. This means multiple withdrawals of the same token in a single transaction are not supported." This is a known, documented gap rather than a hidden bug, but it is still a real reachable defect: nothing in `supports()`, `validateWithdrawal()`, `createWithdrawalIdentifier()`, or the withdrawal-watcher blocks a caller from constructing a batch with two same-`assetId`/different-`destinationAddress` withdrawals — those functions validate each withdrawal independently and don't reject same-asset batches.

### Impact Explanation
For a batch of two POA-bridge withdrawals of the same token to two different destination addresses, an integrator relying on `describeWithdrawal`/`waitForWithdrawalCompletion` to determine per-withdrawal completion can observe: (a) both indices reporting "completed" with the *same* `transfer_tx_hash`, even though only one leg actually completed with that hash, or (b) the txHash belonging to the wrong destination's transfer being attributed to the other index. This is a status/hash misreport that could cause an integrator to treat a not-yet-completed withdrawal as completed (double credit) or attribute the wrong destination's completion to the wrong logical withdrawal — matching the "High: a status or hash misreport making an integrator credit or refund twice" category.

### Likelihood Explanation
Preconditions: an unprivileged NEAR Intents user must batch ≥2 withdrawals in a single call using the same POA-bridge-supported `assetId` but different `destinationAddress`es. There's no validation preventing this construction; it depends only on caller input, is fully attacker/user-controlled, and reproducible on every such batch. However, this requires the POA bridge indexer to genuinely return multiple withdrawal entries for the same `withdrawal_hash`/tx and the batch to actually contain duplicate-asset withdrawals — a real but narrower usage pattern than typical single-asset-per-tx withdrawals.

### Recommendation
Extend `findMatchingWithdrawal` to disambiguate among same-`assetId` candidates using additional fields the POA API returns (e.g., `data.address`/destination, and amount), and correlate remaining ambiguous entries by relative order (sort both the API withdrawals and requested withdrawal params by amount, as the existing code comment already suggests) instead of relying purely on `Array.find` returning the first match for every index.

### Proof of Concept
Vitest plan (mocking only `poaBridge.httpClient.getWithdrawalStatus`):
1. Mock `getWithdrawalStatus` to return `{ withdrawals: [ {status:"COMPLETED", data:{near_token_id:"token.near", address:"addrA", transfer_tx_hash:"hashA"}}, {status:"COMPLETED", data:{near_token_id:"token.near", address:"addrB", transfer_tx_hash:"hashB"}} ] }`.
2. Call `bridge.describeWithdrawal({..., index:0, withdrawalParams:{assetId:"nep141:token.near", destinationAddress:"addrA", ...}, tx})` and `describeWithdrawal({..., index:1, withdrawalParams:{assetId:"nep141:token.near", destinationAddress:"addrB", ...}, tx})`.
3. Assert both calls return `{status:"completed", txHash:"hashA"}` (i.e., index 1's expected `txHash` of `"hashB"` is never returned) — demonstrating `TXHASH_REPORTED[1] !== outcome(withdrawal_1).transfer_tx_hash`, breaking the per-index equality.
