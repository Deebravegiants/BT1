### Title
Unbounded HTTP Response Body Read in `DirectHTTPAction`/`DirectConfidentialHTTPAction` HTTP Capabilities Bypasses Response-Size Limits - ([File: core/capabilities/fakes/http_action.go])

### Summary
The `DirectHTTPAction` and `DirectConfidentialHTTPAction` capabilities (registered under `HTTPActionID = "http-actions@0.1.0"`) execute outbound HTTP requests on behalf of workflow-supplied URLs and read the entire response body with `io.ReadAll(resp.Body)`, with no byte cap, no `Content-Length` pre-check, and no `http.MaxBytesReader`. This is the same bug class as the reported mcp-searxng issue (CWE-400, unbounded response read), but here it is not even guarded by a `Content-Length` check that could be bypassed — it is fully unbounded by design.

### Finding Description
`DirectHTTPAction.SendRequest` in `core/capabilities/fakes/http_action.go` builds an `http.Client` via `newHTTPClient` (only a request `Timeout` and `CheckRedirect: disableRedirects` are set — no transport-level byte limiting) and sends the workflow-supplied request: [1](#0-0) 

The response body is read fully into memory: [2](#0-1) 

`newHTTPClient` never sets a transport `MaxResponseHeaderBytes`/body cap: [3](#0-2) 

The confidential variant `DirectConfidentialHTTPAction.SendRequest` has the identical pattern: [4](#0-3) 

Contrast this with the gateway's own outbound HTTP client, `core/services/gateway/network/httpclient.go`, which correctly wraps the body reader in `http.MaxBytesReader` bounded by `MaxResponseBytes`/`defaultMaxResponseBytes`: [5](#0-4) 

and the workflow syncer's `newHTTPFetcher`, which at least conditionally applies `http.MaxBytesReader` when `req.MaxResponseBytes > 0` (though unbounded when the workflow-controlled field is left at 0): [6](#0-5) 

`DirectHTTPAction`/`DirectConfidentialHTTPAction` have no equivalent size-limiting mechanism at all — there is no `MaxResponseBytes` field consulted anywhere in `SendRequest`.

### Impact Explanation
An unprivileged workflow author (any user who can register a workflow capable of invoking the `http-actions@0.1.0` capability) can point the `URL` field of a `customhttp.Request` at an attacker-controlled or attacker-influenced endpoint that streams an arbitrarily large response body. Because `io.ReadAll` has no cap, the node process will allocate memory proportional to the entire response, and for `DirectConfidentialHTTPAction`, the body is additionally passed through AES-GCM encryption, adding CPU cost proportional to body size: [7](#0-6) 
Repeated or concurrent invocations from one or more workflows can exhaust node memory/CPU, causing a Denial of Service against the capability host process — the same "Uncontrolled Resource Consumption" impact category as the reported advisory (CWE-400, `AV:N/AC:L/PR:N/UI:N`, `A:H`).

### Likelihood Explanation
The capability is invoked directly by workflow logic — no operator-only gate or role check stands between an unprivileged workflow author and the HTTP send path once the capability is registered. The only bound on the request is the client's `Timeout`, which limits duration but not bytes transferred within that window; a fast/local attacker-controlled server can still stream many megabytes before the timeout fires. This makes exploitation straightforward for any workflow author able to specify an arbitrary/attacker-controlled URL.

### Recommendation
Wrap `resp.Body` in `http.MaxBytesReader(nil, resp.Body, maxBytes)` (mirroring the gateway's `httpclient.go` pattern) before calling `io.ReadAll` in both `DirectHTTPAction.SendRequest` and `DirectConfidentialHTTPAction.SendRequest`, using a configurable/default max response size, and return a clear "response too large" error (analogous to the gateway's `ErrHTTPRead`) instead of allowing unbounded reads.

### Proof of Concept
1. Register a workflow capable of invoking capability `http-actions@0.1.0` (`DirectHTTPAction`) with an attacker-controlled or attacker-influenced target.
2. Set `customhttp.Request.Url` to an endpoint that returns a very large (e.g., multi-GB) `200 OK` response body, optionally without a `Content-Length` header (HTTP/1.0 style, chunked, or streamed).
3. Invoke `SendRequest`; because `io.ReadAll(resp.Body)` in `core/capabilities/fakes/http_action.go` line 141 has no byte cap, the node reads and buffers the entire body in memory.
4. Repeat concurrently from multiple workflow executions to amplify memory/CPU pressure and induce a DoS on the node process running the capability.

func newHTTPClient(input *customhttp.Request, timeout time.Duration) (*http.Client, error) {
	client := &http.Client{
		Timeout:       timeout,
		CheckRedirect: disableRedirects,
	}

	mtls := input.GetMtls()
	if mtls == nil {
		return client, nil
	}

	cert, err := tls.X509KeyPair(mtls.GetCertificate(), mtls.GetPrivateKey())
	if err != nil {
		return nil, fmt.Errorf("failed to parse mtls auth into key pair: %w", err)
	}

	client.Transport = &http.Transport{
		TLSClientConfig: &tls.Config{
			Certificates: []tls.Certificate{cert},
			MinVersion:   tls.VersionTLS12,
		},
	}

	return client, nil
}
