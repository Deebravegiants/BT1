### Title
Reachable underflow revert in `Bonding.canGraduate` / `_prepareGraduationLiquidity` from K-invariant rounding slack permanently freezes a curve - (File: packages/contracts/src/Bonding.sol)

### Summary
CVE-2018-20217 is a reachable-assertion DoS: an unprivileged actor can construct ticket state (old-encryption krbtgt + S4U2Self) that trips an internal assertion in the KDC, crashing it. The alt.fun analog is a reachable **integer-underflow revert** (Solidity's Panic(0x11), functionally an unhandled assertion) in the graduation-trigger math that any unprivileged trader can induce through ordinary buy/sell sequencing, permanently DoS-ing a curve's trading and graduation path.

### Finding Description
`Bonding.canGraduate` and `Bonding._prepareGraduationLiquidity` both derive the "real LT raised" by subtracting the launch-time virtual LT reserve from the pair's *stored* `assetReserve`: [1](#0-0) 

and [2](#0-1) 

The virtual reserve is recovered as `Pair.k() / Token.TOTAL_SUPPLY()`, exploiting the fact that `_pool.k` is fixed once at `Pair.mint` and never updated by `Pair.swap`: [3](#0-2) 

`Pair.swap`, however, does **not** enforce that the product of reserves stays at-or-above `k` — it only guards a *floor* with a `+1` slack: [4](#0-3) 

`(newTokenReserve + 1) * (newAssetReserve + 1) < k` reverting means the *actual* product `newTokenReserve * newAssetReserve` is allowed to land strictly below `k` by an amount bounded only by the reserves themselves (the classic UniswapV2 `+1` rounding slack, here applied without any protocol fee to offset it — the rules explicitly call out "no curve fee"). Because there is no fee cushioning the rounding loss, a sequence of buys and sells that round systematically in the trader's favor can push the pair's stored `assetReserve` to a value *strictly below* the immutable `virtualLtReserve` baked into `k / TOTAL_SUPPLY` at launch — even though `assetReserve` started exactly equal to that value at `Pair.mint`.

Once that happens, `assetReserve - _launchTimeVirtualLtReserve(...)` underflows and reverts with Panic(0x11) in:
- `canGraduate` (a `view`, but called inline at the end of every buy per `_executeBuy`, and directly by `triggerGraduation`),
- `_prepareGraduationLiquidity` (called by `_enterGraduating`, itself invoked at the end of every threshold-crossing buy).

Because `canGraduate`/`_enterGraduating` sit on the hot path of every buy (`Bonding.buy` → `_executeBuy` → `canGraduate`), a curve that lands in this rounding-underwater state becomes permanently un-tradeable: every subsequent `Zap.buy`/`Bonding.buy` reverts, `triggerGraduation` reverts, and the curve can never graduate. This is the direct on-chain equivalent of the CVE's reachable assertion crash — no privileged action needed, just a specific sequence of otherwise-legal transactions producing a state the code's arithmetic doesn't defend against.

This is distinct from, and not covered by, the existing donation-resistance regression (`test_donation_realBalanceExceedsReserveToken` / `test_donation_previewLtUntilGraduation_returnsThresholdLeg`), which only guards the **token-side** balance-vs-reserve underflow in `previewLtUntilGraduation`: [5](#0-4) 

There is no analogous regression test asserting `assetReserve >= _launchTimeVirtualLtReserve(...)` as an invariant across arbitrary buy/sell sequences, and the K-invariant check in `Pair.swap` provides no such guarantee — it only bounds the reserve *product*, not either reserve individually against the launch-time value.

### Impact Explanation
If this state is reached, every trader with tokens or LT already committed to that curve is permanently frozen: they cannot buy, sell, or trigger graduation, since all three paths route through `canGraduate` / `_prepareGraduationLiquidity` and both revert. Funds already inside the `Pair` (real tokens and real LT raised) become permanently stuck with no owner-privileged escape hatch (per the codebase's own "brick resistance" philosophy, there is no admin rescue for a bricked curve pre-graduation). This is a concrete, permanent freezing of trader and creator funds, satisfying the "Validate" bar.

### Likelihood Explanation
Reachability depends on whether the rounding slack permitted by `Pair.swap`'s `+1` floor check is large enough, and whether `Router._computeBuy`/`_computeSell` round systematically against the pool over repeated trades, to shift `assetReserve` below the immutable `virtualLtReserve` baked into `k`. This requires either: (a) many small round-trips accumulating sub-wei rounding losses, or (b) one large trade near the K-floor boundary. The exact `Router._computeBuy`/`_computeSell` formulas were not available in this review to fully quantify the accumulation rate, so likelihood is assessed as plausible but unconfirmed without executing the arithmetic — this is the one gap in an otherwise fully-grounded root-cause analysis and should be closed with a fuzz/invariant test before treating the finding as fully proven.

### Recommendation
- Add an explicit invariant in `Router`/`Pair` (or a defensive check in `canGraduate`/`_prepareGraduationLiquidity`) that `assetReserve >= _launchTimeVirtualLtReserve(token, pair)` always holds, and treat a would-be violation as a saturating clamp (`realLtRaised = assetReserve > virtual ? assetReserve - virtual : 0`) rather than a raw subtraction — mirroring the saturating-subtract pattern already used defensively in `finalizeGraduation` (`ltBalance > p.ltFromPair ? ... : 0`).
- Add a fuzz/invariant test that performs long buy/sell round-trip sequences and asserts `IPair(pair).getReserves().assetReserve >= Pair.k()/TOTAL_SUPPLY` never breaks, to determine and close the actual rounding-slack magnitude in `Router._computeBuy`/`_computeSell`.

### Proof of Concept
Conceptual (formulas in `Router._computeBuy`/`_computeSell` were not available for exact numeric derivation in this review):
1. Launch a token normally; `Pair.mint` sets `_pool.k = TOTAL_SUPPLY * virtualLtReserve_init`, `assetReserve = virtualLtReserve_init`.
2. An unprivileged trader repeatedly buys then sells back (or executes a sequence of buys/sells) sized to exploit the `Pair.swap` K-floor's `+1` rounding slack, each round-trip landing the stored `(tokenReserve+1)*(assetReserve+1)` just above `k` rather than exactly at it — i.e., leaking a few wei of `assetReserve` below the true `virtualLtReserve_init` per round-trip, with no protocol fee to counteract the drift (per `AGENTS.md`: "bonding-curve AMM math ... with no curve fee").
3. After enough round-trips, `assetReserve < k/TOTAL_SUPPLY`.
4. The next `Zap.buy`/`Bonding.buy` call reaches `_executeBuy → canGraduate(token)`, which executes `assetReserve - _launchTimeVirtualLtReserve(token, pair)` and reverts with Panic(0x11).
5. Every further trade attempt and `triggerGraduation` call on this token now reverts identically — the curve is permanently frozen, exactly analogous to the KDC crashing on a crafted S4U2Self request.
