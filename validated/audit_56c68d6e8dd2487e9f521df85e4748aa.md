### Title
Stale positive `storageDepositCache` entry causes `ft_withdraw` intents to omit required storage deposit after on-chain `storage_unregister` - (File: packages/intents-sdk/src/bridges/direct-bridge/direct-bridge.ts)

### Summary
`DirectBridge.getCachedStorageDepositValue` only writes to its LRUCache when `result[1] >= result[0]` (i.e., "storage is sufficient"), and keys the cache purely by `${contractId}${accountId}` with a 1-hour TTL and no invalidation. If the `destinationAddress` account's on-chain NEP-141 storage becomes insufficient after the cache entry is written (e.g., via `storage_unregister`), `estimateWithdrawalFee` keeps returning the stale "sufficient" result for up to an hour, so `createWithdrawIntentPrimitive` emits an `ft_withdraw` intent with no `storage_deposit`, even though the receiver is no longer registered on-chain.

### Finding Description
The claimed equality is: `feeEstimation.underlyingFees[NearWithdrawal].storageDepositFee` (and thus `intent.storage_deposit` produced by `createWithdrawIntentPrimitive`) should equal the real on-chain shortfall `max(0, minStorageBalance_onchain - userStorageBalance_onchain)` at the time the intent is submitted.

Code path:
- `estimateWithdrawalFee` calls `getCachedStorageDepositValue(tokenAccountId, destinationAddress)` [1](#0-0) 
- `getCachedStorageDepositValue` keys the LRUCache by `${contractId}${accountId}` and only stores `[minStorageBalance, userStorageBalance]` when `result[1] >= result[0]` (i.e., only "sufficient" states are cached, for a 1-hour TTL), and returns the cached tuple on any subsequent call within TTL without re-checking on-chain state [2](#0-1) 
- When `minStorageBalance <= userStorageBalance`, `estimateWithdrawalFee` returns `amount: 0n, quote: null, storageDepositFee: 0n` [3](#0-2) 
- `createWithdrawalIntents` passes `getUnderlyingFee(feeEstimation, ..., "storageDepositFee")` straight into `createWithdrawIntentPrimitive` as `storageDeposit` [4](#0-3) 
- `createWithdrawIntentPrimitive` only sets `storage_deposit` on the `ft_withdraw` intent when `storageDeposit > 0n`, so a `0n` value omits the field entirely [5](#0-4) 

Exploit flow with attacker-controlled `destinationAddress` (any NEAR account they hold keys for, or even an account they merely designate as recipient and control via re-registration/unregistration timing):
1. Attacker's `destinationAddress` account has sufficient NEP-141 storage balance registered on `tokenAccountId`. Attacker triggers `estimateWithdrawalFee` (directly, or implicitly through any SDK flow that calls it) — the cache stores `[minStorageBalance, userStorageBalance]` because `userStorageBalance >= minStorageBalance`.
2. Attacker calls `storage_unregister` on the token contract for that account (a legitimate, permissionless action any NEAR account holder can perform on their own registered storage), reclaiming the deposited NEAR and dropping their on-chain storage balance below `minStorageBalance`.
3. Within the cache TTL (1 hour), attacker triggers a second `estimateWithdrawalFee` for the same `tokenAccountId`+`destinationAddress` pair. The cache hit at line 278-281 returns the stale tuple, so the function still reports `amount: 0n, quote: null, storageDepositFee: 0n` even though `minStorageBalance > userStorageBalance` now holds on-chain.
4. `createWithdrawalIntents` builds an `ft_withdraw` intent with no `storage_deposit` field.
5. When submitted, the token contract's `ft_transfer`/`ft_transfer_call` will fail because the receiver is not storage-registered, leaving the withdrawal intent stuck/failed and requiring manual re-estimation and resubmission, while the withdrawn amount remains locked in the withdrawal pipeline.

No existing guard prevents this: `withdrawalParamsInvariant` only checks the route type, `validateWithdrawal`/`validateAddress`/`compareAddresses` only validate address format and existence (not storage balance), and there is no re-check of on-chain storage state immediately before intent construction — the cache is trusted for its full TTL regardless of intervening on-chain state changes.

### Impact Explanation
The `ft_withdraw` intent is submitted without the `storage_deposit` field that the token contract requires for a newly-unregistered receiver, causing the on-chain withdrawal to fail after the intent has already been signed and processed by the solver/relayer pipeline. This matches the "withdrawal stuck until manual intervention" High-severity category: the user's own funds become locked in transit and require manual re-estimation and resubmission to recover. This is repeatable per cache TTL window and per `tokenAccountId`+`destinationAddress` pair.

### Likelihood Explanation
Preconditions are entirely within an ordinary user's control: they need an account with existing sufficient storage balance on the target NEP-141 contract, must call the estimate once to populate the cache, then call `storage_unregister` (a standard permissionless NEP-141 action) on their own account, then re-request the estimate within the 1-hour cache TTL. No privileged access, relayer collusion, or contract bug is required — only the SDK's own caching logic. This is straightforward and cheap to trigger, and is self-inflicted (the attacker's own funds get stuck), but the finding is valid as a functional/caching defect that produces the specified High-impact outcome.

### Recommendation
Do not cache "sufficient storage" results indefinitely without invalidation, or shorten/remove the TTL for this specific check, or re-validate the on-chain storage balance immediately before constructing the withdrawal intent (bypassing the cache) at the point `createWithdrawalIntents` is called, so the `storage_deposit` amount reflects current on-chain state rather than a potentially stale cached value.

### Proof of Concept
```ts
// vitest test plan (mock only the HTTP/RPC-backed helpers getNearNep141MinStorageBalance / getNearNep141StorageBalance)
import { describe, it, expect, vi } from "vitest";
import { DirectBridge } from "./direct-bridge";
import * as internalUtils from "@defuse-protocol/internal-utils";

it("returns stale zero fee after on-chain storage_unregister within cache TTL", async () => {
  const minStorage = 1250000000000000000000n; // e.g. 1.25e21 yoctoNEAR
  vi.spyOn(internalUtils, "getNearNep141MinStorageBalance").mockResolvedValue(minStorage);

  const storageBalanceSpy = vi
    .spyOn(internalUtils, "getNearNep141StorageBalance")
    .mockResolvedValueOnce(minStorage) // call 1: sufficient -> cached
    .mockResolvedValueOnce(0n);        // call 2: on-chain now insufficient after storage_unregister

  const bridge = new DirectBridge({ envConfig: {} as any, nearProvider: {} as any });

  const args = {
    withdrawalParams: {
      assetId: "nep141:usdt.tether-token.near",
      destinationAddress: "attacker.near",
      routeConfig: undefined,
    },
  };

  const first = await bridge.estimateWithdrawalFee(args as any);
  expect(first.amount).toBe(0n); // sufficient -> correct

  // simulate attacker calling storage_unregister on-chain here (not re-queried due to cache)
  const second = await bridge.estimateWithdrawalFee(args as any);

  // Broken equality: SDK still reports amount 0n / quote null,
  // but real on-chain shortfall is minStorage - 0n = minStorage > 0
  expect(second.amount).toBe(0n);
  expect(second.quote).toBeNull();
  expect(storageBalanceSpy).toHaveBeenCalledTimes(1); // second call served from stale cache, no re-check

  const intent = await bridge.createWithdrawalIntents({
    withdrawalParams: { ...args.withdrawalParams, amount: 100n } as any,
    feeEstimation: second,
  });
  // ft_withdraw intent has no storage_deposit despite real shortfall == minStorage
  expect((intent[intent.length - 1] as any).storage_deposit).toBeUndefined();
});
```

	private async getCachedStorageDepositValue(
		contractId: string,
		accountId: string,
	): Promise<[MinStorageBalance, StorageDepositBalance]> {
		const key = `${contractId}${accountId}`;
		const cached = this.storageDepositCache.get(key);
		if (cached !== undefined) {
			return cached;
		}

		const result = await Promise.all([
			getNearNep141MinStorageBalance({
				contractId: contractId,
				nearProvider: this.nearProvider,
			}),
			getNearNep141StorageBalance({
				contractId: contractId,
				accountId: accountId,
				nearProvider: this.nearProvider,
			}),
		]);

		if (result[1] >= result[0]) {
			this.storageDepositCache.set(key, result);
		}

		return result;
	}
