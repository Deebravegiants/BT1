### Title
Insufficient Validation of Locked Amount in `WrappedHyperFungibleToken.send()` Allows Fee-on-Transfer/Deflationary Underlying Tokens to Drain Escrowed Reserves - (File: `sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol`)

### Summary
`WrappedHyperFungibleToken.send()` (and its identical twin `WrappedHyperFungibleTokenUpgradeable.send()`) locks the underlying ERC20 token via `safeTransferFrom` but never checks how much was actually received by the contract. The full `params.amount` requested by the caller is embedded in the cross-chain `Message` and used to mint/unlock the same amount on the destination chain, creating a mismatch between what is actually escrowed and what is promised to be released.

### Finding Description
In `send()`, the contract does:
```solidity
IERC20(_underlying).safeTransferFrom(msg.sender, address(this), params.amount);
``` [1](#0-0) 

It never measures the actual balance delta before/after the transfer. The unvalidated `params.amount` is then encoded verbatim into the dispatched `Message.amount` via `_buildDispatchPost`: [2](#0-1) 

On the remote `HyperFungibleToken`, `onAccept` mints exactly `message.amount` tokens to the beneficiary, trusting the source-side amount unconditionally: [3](#0-2) 

If the underlying token has any fee-on-transfer, deflationary, or rebasing behavior, the wrapper contract will lock strictly less than `params.amount` while the destination chain mints/unlocks the full nominal amount. This is the exact bug class from the reported `OFTTransportAdapter._transferViaOFT` issue: the amount actually taken/held at the origin is not validated against the amount credited elsewhere — only the "intended" amount is trusted.

Notably, the codebase is aware of this exact risk elsewhere: `IntentGatewayV2.placeOrder` explicitly measures `balanceOf` before and after `safeTransferFrom` and uses the *actual received* amount for both escrow accounting and the commitment hash: [4](#0-3) 
and this defensive pattern is directly validated by tests for fee-on-transfer tokens: [5](#0-4) 

`WrappedHyperFungibleToken.send()` lacks this same balance-delta check, meaning the mitigation applied in one part of the codebase was not applied to the token-bridging app.

### Impact Explanation
Any unprivileged user can call `send()` using a fee-on-transfer/deflationary ERC20 as the wrapped underlying (or if such a token is later configured as `_underlying` by the owner). Each `send()` call locks less than `params.amount` but the destination chain mints/unlocks the full `params.amount`. Over repeated round-trips, unlocks on the wrapper chain (`onAccept`, which does `IERC20(_underlying).safeTransfer(beneficiary, message.amount)`) will progressively drain the wrapper's actual token reserve below what is needed to honor all outstanding unlocks — an unbacked-mint/fund-drain condition affecting all users of that token pair, not just the attacker. This is a direct loss/freezing of funds for the wrapper's liquidity and other bridge users.

### Likelihood Explanation
The trigger requires only a single `send()` transaction with a fee-on-transfer or deflationary token configured as `_underlying`, reachable by any unprivileged sender — no privileged role, governance, or off-chain component is needed. Likelihood is governed by whether an owner ever configures such a token as the underlying, which is plausible given `WrappedHyperFungibleToken` is a generic, permissionless-to-deploy wrapper meant to support "existing ERC20 tokens" broadly.

### Recommendation
Mirror the `IntentGatewayV2` pattern: measure `IERC20(_underlying).balanceOf(address(this))` before and after `safeTransferFrom` in `send()`, and use the actual received delta (not `params.amount`) both for the amount encoded in the dispatched `Message` and for the `Sent` event. Apply the same fix to `WrappedHyperFungibleTokenUpgradeable.send()`.

### Proof of Concept
1. Owner configures `WrappedHyperFungibleToken` with `underlying` set to a token that charges a 1% fee-on-transfer (analogous to `FeeOnTransferToken` used in `evm/tests/foundry/IntentGatewayV2SameChainTest.sol`).
2. User calls `send({amount: 1000e18, dest: remoteChain, to: user, ...})`. `safeTransferFrom` moves 1000e18 nominally but the wrapper only receives 990e18 due to the transfer fee.
3. `_buildDispatchPost` encodes `Message.amount = 1000e18` (the pre-fee value) and dispatches it.
4. On the destination `HyperFungibleToken`, `onAccept` mints `1000e18` tokens to the recipient — 10e18 more than was actually escrowed on the source chain.
5. If the recipient bridges the full `1000e18` back, `WrappedHyperFungibleToken.onAccept` unlocks `1000e18` of the underlying, but the wrapper only ever held `990e18` from that operation — repeating this drains reserves backing other users' locked balances.

    function _buildDispatchPost(HyperFungibleToken.SendParams calldata params) internal view returns (DispatchPost memory) {
        bytes memory dest = _supportedChains[params.dest];
        if (dest.length == 0) revert UnsupportedChain();

        bytes memory body = abi.encode(HyperFungibleToken.Message({
            from: abi.encodePacked(msg.sender),
            to: params.to,
            amount: params.amount,
            data: params.data
        }));

        return DispatchPost({
            dest: params.dest,
            to: dest,
            body: body,
            timeout: params.timeout,
            fee: params.relayerFee,
            payer: msg.sender
        });
    }

    function onAccept(IncomingPostRequest calldata incoming) public virtual override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        Message memory message = abi.decode(request.body, (Message));
        address beneficiary = _toAddr(message.to);
        _mint(beneficiary, message.amount);

        if (message.data.length > 0) {
            ICallDispatcher(_dispatcher).dispatch(message.data);
        }

        emit Received({
            from: message.from,
            to: beneficiary,
            source: string(request.source),
            amount: message.amount
        });
    }
