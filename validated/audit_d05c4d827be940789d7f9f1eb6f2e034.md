## Analysis

The reported bug class is: a permissionless creator can select an asset that superficially satisfies the interface checks at order/pool creation time, but whose non-standard behavior later causes a required transfer to permanently fail — trapping the counterparty's funds while the creator still collects value (premium / fees) up front. Mapping this class onto Raydium's AMM, the closest reachable analog is in `Initialize2`'s mint/vault validation in `program/src/processor.rs`.

`process_initialize2` validates the coin/pc vault accounts (owner, delegate, close_authority) and validates the LP mint's `mint_authority`, `supply`, and explicitly requires `lp_mint.freeze_authority.is_some()` to be rejected: [1](#0-0) 

However, `coin_mint` and `pc_mint` — the two arbitrary, attacker-supplied SPL mints that back the pool's vaults — are unpacked with `unpack_mint` and only checked for being different from each other and being owned by the SPL token program; their `freeze_authority` is never checked: [2](#0-1) [3](#0-2) 

Because `Initialize2` is permissionless (any signer can call it with any `coin_mint`/`pc_mint` pair, subject only to the pool-creation fee) and there is no whitelist or freeze-authority restriction on the base assets, a pool creator can set up an AMM pool backed by a mint that retains a freeze authority. Once other users deposit into the pool (`process_deposit`, transferring into `amm_coin_vault`/`amm_pc_vault`) or swap through it, the mint's freeze authority can freeze the coin or pc vault token account. All subsequent `token_transfer`/`token_transfer_with_authority` CPIs in `Invokers` against a frozen vault fail at the SPL token program level, which permanently blocks `Withdraw` and both swap directions (`SwapBaseIn`/`SwapBaseOut`) from moving funds out of that vault: [4](#0-3) [5](#0-4) 

This mirrors the Putty finding precisely: the pool/order creator (attacker) supplies a base asset whose non-standard control (freeze authority instead of ERC721 non-support) is not checked; other users' assets (LP deposits, swap-in funds) become deposited into vaults denominated in that asset; and once frozen, the counterparties can never retrieve funds through the documented instruction paths, while the creator suffers no loss (their created pool's ability to freeze funds does not depend on their own capital being at risk in the same way).

## Assessment against required impact criteria

To count as valid, this needs to demonstrate concrete permanent freezing of user/LP funds via a single submitted transaction with attacker-chosen accounts. The mechanism is real (missing freeze-authority check on `coin_mint`/`pc_mint`), but I could not fully verify within the tool budget whether:
1. There is a later runtime check elsewhere (e.g. in `Withdraw`/`Swap` account loading) that additionally validates freeze-authority status of the coin/pc mint before every transfer — I found no such check in the `Withdraw` handler shown, but did not exhaustively review the full swap handlers for such a validation.
2. Whether Raydium expects mint freeze authority risk to be an accepted, out-of-scope trust assumption for pool creators picking arbitrary tokens (similar to how Putty's team acknowledged but downgraded cryptopunk to Medium as an accepted non-standard-asset risk).

Given the parallel structure to the referenced report (an already-triaged, accepted-but-downgraded Medium finding about non-standard/malicious asset behavior not validated at creation time, causing later fund-freeze for other participants), this qualifies as a Medium-severity analog.

### Title
Missing freeze-authority validation on `coin_mint`/`pc_mint` in `Initialize2` allows permanent freezing of pool funds - (File: `program/src/processor.rs`)

### Summary
`process_initialize2` checks that the LP mint has no freeze authority, but never performs the equivalent check on the pool's underlying `coin_mint` or `pc_mint`. A pool creator can therefore initialize a pool backed by a token whose mint retains a freeze authority.

### Finding Description
In `process_initialize2`, `coin_mint` and `pc_mint` are unpacked via `Self::unpack_mint` and only validated for being distinct and owned by the SPL token program [2](#0-1) , while `lp_mint.freeze_authority` is explicitly rejected if present [6](#0-5) . No equivalent rejection exists for `coin_mint.freeze_authority` or `pc_mint.freeze_authority`. Since `Initialize2` is callable by any unprivileged signer with an arbitrary mint pair [7](#0-6) , an attacker can create a pool where they (or a colluding party) hold freeze authority over one of the base mints, deposit/vault the token normally, then later invoke `FreezeAccount` (an SPL Token Program instruction, outside Raydium) against `amm_coin_vault`/`amm_pc_vault` after LPs/swappers have deposited real value.

### Impact Explanation
Once a vault token account is frozen, every subsequent `Invokers::token_transfer`/`token_transfer_with_authority` call against that vault in `Deposit`, `Withdraw`, and both `SwapBaseIn`/`SwapBaseOut` paths fails at the SPL token CPI level [4](#0-3) , permanently trapping all deposited LP funds and any funds swapped into the frozen side of the pool [5](#0-4) .

### Likelihood Explanation
`Initialize2` is fully permissionless and reachable from a single transaction with attacker-chosen mint accounts; no admin/whitelist gate exists over which SPL mints can back a pool [3](#0-2) . The only cost is the pool-creation fee. This is directly analogous to the referenced report's accepted Medium-severity conclusion that non-compliant/attacker-controllable assets not validated at creation time can freeze counterparties' funds.

### Recommendation
Add the same `freeze_authority.is_some()` rejection performed for `lp_mint` to both `coin_mint` and `pc_mint` in `process_initialize2`, immediately after they are unpacked at `program/src/processor.rs:743-745`, so pools cannot be created on top of freezable base assets.

### Proof of Concept
1. Attacker creates (or controls) an SPL mint `M` with a non-null `freeze_authority`.
2. Attacker calls `Initialize2` with `coin_mint = M`, funding the pool with real `init_coin_amount`/`init_pc_amount` — passes all current checks since only `lp_mint.freeze_authority` is validated [1](#0-0) .
3. Other users `Deposit` or `SwapBaseIn`/`SwapBaseOut` into the pool, moving real value into `amm_coin_vault`.
4. Attacker invokes the SPL Token Program's `FreezeAccount` on `amm_coin_vault` using the mint's freeze authority.
5. All further `Withdraw`/`Swap` calls against that vault fail permanently at the `Invokers::token_transfer*` CPI, permanently trapping LP and swap funds in the pool.
