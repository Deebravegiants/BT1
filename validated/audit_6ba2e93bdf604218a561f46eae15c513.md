Audit Report

## Title
Unprotected spot-price AMM swap in `SwapFirstAssetTrader::refund_weight` enables sandwich extraction on XCM fee refunds - (File: `cumulus/primitives/utility/src/lib.rs`)

## Summary
`SwapFirstAssetTrader::refund_weight` swaps the unused portion of an XCM execution fee back to the original payment asset via `SwapCredit::swap_exact_tokens_for_tokens(..., None)`, passing no `amount_out_min`. Because the pallet skips the minimum-output check entirely when this parameter is `None`, the swap executes at whatever spot price the pool currently offers, with no floor, making the refund sandwichable by anyone who can move the relevant pool's reserves before the refund executes.

## Finding Description
`refund_weight` extracts the unused fee credit and swaps it from `Target` back into the asset the user originally paid with, unconditionally passing `None` for `amount_out_min` [4](#0-3) . The pallet's swap implementation only enforces a minimum output when `amount_out_min` is `Some`; with `None` the `ensure!` conditions are trivially satisfied (`map_or(true, ...)`), so the swap accepts the `amount_out` computed from current pool reserves via the constant-product formula regardless of how unfavorable it is [2](#0-1) . This is asymmetric with `buy_weight`, which uses `swap_tokens_for_exact_tokens` to buy an exact `fee` amount out, an operation that is naturally bounded on the input side [3](#0-2) . `SwapFirstAssetTrader` is configured in production `Trader` tuples for Asset Hub Rococo, Asset Hub Westend, and Penpal, so this refund path is live whenever XCM fees are paid in a non-native, pool-tradeable asset.

## Impact Explanation
Anyone who can create or influence a shallow `(Target, X)` pool and observe/predict an XCM message paying fees in `X` can skew reserves immediately before the refund executes, causing the refund to settle at a manipulated spot price with zero downside protection, then reverse the trade to capture the price-impact spread. The maximum extractable value is bounded by the refund size (the unused portion of the purchased weight-fee), which is typically small relative to deep, arbitraged pools (e.g., DOT/USDT) but fully attacker-controlled for newly created, shallow pools of arbitrary assets.

## Likelihood Explanation
The attack is unprivileged: pool creation, asset selection, and surrounding-block trades are all standard, permissionless AMM operations available to any user, and the refund path triggers on essentially every XCM message that overpays weight fees in a swappable non-native asset — a common, non-adversarial occurrence. Profitability scales with attacker-controlled pool depth (via `MintMinLiquidity` floor), making it a real, repeatable MEV/griefing vector, though the absolute value at risk per refund is generally small.

## Recommendation
Supply a real `amount_out_min` in `refund_weight`, derived from a quoted price (e.g., via `QuotePrice`/`quote_price_exact_tokens_for_tokens`) at the time of `buy_weight`, adjusted by a bounded slippage tolerance, mirroring the protection implicitly present in `buy_weight`'s exact-output swap. Alternatively, avoid the live-pool swap for refunds below a threshold, or refund exclusively in the `Target` asset to eliminate the sandwichable code path.

## Proof of Concept
1. Attacker permissionlessly creates a `pallet-asset-conversion` pool for `(Target, X)` with minimal liquidity (bounded only by `MintMinLiquidity`).
2. Attacker sends or predicts an XCM message paying execution fees in `X`, which triggers `SwapFirstAssetTrader::buy_weight` and subsequently `refund_weight` for the unused weight.
3. In the surrounding block(s), attacker trades against the `(Target, X)` pool to skew the spot price unfavorably for the pending refund; `swap_exact_tokens_for_tokens(..., None)` executes with no minimum-output check regardless of the unfavorable rate, as confirmed at `substrate/frame/asset-conversion/src/lib.rs` lines 1086-1097.
4. Attacker reverses the trade after the refund settles, capturing the price-impact spread as profit.
