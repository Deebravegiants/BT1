Confirmed: `ShopValidator` is used in `token_exchange.rb`, `client_credentials.rb`, `refresh_token.rb`, and `graphql/storefront.rb`, but **not** in `lib/shopify_api/auth/oauth.rb`'s `validate_auth_callback`. This is the key asymmetry.

### Title
Authorization-code OAuth callback sends `client_secret` to an unvalidated `shop` host derived from query parameters - ([File: lib/shopify_api/auth/oauth.rb])

### Summary
`ShopifyAPI::Auth::Oauth.validate_auth_callback` builds the access-token request host directly from `auth_query.shop` without ever passing it through `ShopifyAPI::Utils::ShopValidator.sanitize!`, unlike every other place in the gem that turns an externally supplied shop string into a request host (`TokenExchange#migrate_to_expiring_token`, `client_credentials.rb`, `refresh_token.rb`, `graphql/storefront.rb`).

### Finding Description
`validate_auth_callback` only checks that `auth_query.hmac` matches a signature computed over `{code, host, shop, state, timestamp}` via `Utils::HmacValidator.validate` [1](#0-0) . It never validates that the `shop` value is actually a `*.myshopify.com` (or other trusted) domain the way `ShopValidator` does elsewhere:

```ruby
null_session = Auth::Session.new(shop: auth_query.shop)
body = {
  client_id: Context.api_key,
  client_secret: Context.api_secret_key,
  code: auth_query.code,
  ...
}
client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
``` [2](#0-1) 

`HttpClient#initialize` then builds the request URI directly from `session.shop`: `@base_uri = "https://#{api_host || session.shop}"` [3](#0-2) , so the app's `client_secret` and authorization `code` are POSTed to whatever host is in `auth_query.shop`.

Compare this to `TokenExchange.migrate_to_expiring_token`, which explicitly calls `Utils::ShopValidator.sanitize!(shop)` before building the session/host [4](#0-3) , and to `TokenExchange.exchange_token`, which (per the CHANGELOG) was specifically hardened to derive the target host from a cryptographically verified source (the session token's `dest` claim) rather than an unauthenticated string [5](#0-4) .

The identity binding that should hold is: *"the host that receives the app's `client_secret`" == "a value that has been validated as belonging to the trusted `*.myshopify.com`/`ShopValidator` domain set."* In `validate_auth_callback`, the host that receives the `client_secret` is instead bound only to *"whatever string arrived in the `shop` query parameter and matched the HMAC over that same string"* — HMAC integrity is not the same guarantee as domain-trust validation. `AuthQuery#to_signable_string` signs `shop` together with the other fields [6](#0-5) , so as long as `Context.api_secret_key` (or `old_api_secret_key`) is used to compute a matching digest, any string can be signed as `shop`. Because this is a callback endpoint hosted by the app (not Shopify), and the HMAC secret is the same secret Shopify uses when redirecting genuine callbacks, the correctness of this design depends entirely on Shopify never emitting an HMAC over an untrusted `shop` string — the library itself provides no independent check.

### Impact Explanation
If any path exists where an app-controlled or replayed `hmac`/`shop` pair for a non-`myshopify.com` host can reach this method (e.g., an app that generates its own signed query for internal testing/staging tooling reusing this validator, or any deviation from Shopify's exact behavior), the app's `client_secret` and the merchant's OAuth authorization `code` are sent to an attacker-influenced host — i.e., SSRF carrying the app's credentials, and potential authorization-code/credential exfiltration. This is exactly the class of bug the ed25519 report describes structurally: a value (`shop`) is treated as canonical/trusted because one check (HMAC match) passed, while a second necessary check (domain-membership/canonical-form validation, provided elsewhere in the codebase by `ShopValidator`) is silently skipped for this code path only.

### Likelihood Explanation
Likelihood is moderate-to-low under normal operation, because in the standard flow Shopify itself signs the `hmac` over the real shop parameter, and only Shopify holds `api_secret_key`. However, the gem's own defense-in-depth pattern (`ShopValidator` used in three/four other credential-sending call sites) demonstrates the maintainers recognize HMAC alone is insufficient to trust a host value for credential-bearing requests — `validate_auth_callback` is the one call site that was missed. This mirrors the ed25519 report's root cause: an unconditional operation (trusting `shop` after HMAC match) without the additional canonical/membership guard applied everywhere else in the codebase.

### Recommendation
In `ShopifyAPI::Auth::Oauth.validate_auth_callback`, after successfully validating the HMAC, pass `auth_query.shop` through `Utils::ShopValidator.sanitize!` (as already done in `TokenExchange.migrate_to_expiring_token`) before constructing `null_session` and issuing the `access_token` request, so the host that receives `client_secret` is always bound to a validated Shopify domain rather than merely to a string that matched an HMAC.

### Proof of Concept
Not directly demonstrable without control of `api_secret_key` (out of scope per the exclusion rules) or a downstream integration that reuses `HmacValidator`/`AuthQuery` with attacker-influenced input; the finding is a defense-in-depth/consistency gap rather than a directly exploitable unprivileged path in the current call graph, given no additional caller was found that feeds unauthenticated `shop` values into `AuthQuery` while bypassing HMAC secrecy.
