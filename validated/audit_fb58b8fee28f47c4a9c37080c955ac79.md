### Title
Webhook `shop` identity is trusted without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` extracts the `shop` domain from an HTTP header, but `ShopifyAPI::Utils::HmacValidator` only verifies the HMAC over the raw request body. The shop identity that the handler receives and acts on is never part of the signed material, so it can be substituted freely while keeping a valid signature.

### Finding Description
The binding that should hold is: `hmac == HMAC(secret, bytes_that_include_shop)`. Instead, the actual binding implemented is `hmac == HMAC(secret, raw_body)` while `shop` comes from an independent, unauthenticated header: [1](#0-0) 

`to_signable_string` returns only `@raw_body`, never mixing in the topic, webhook id, or shop-domain header: [2](#0-1) 

`HmacValidator.validate` (and thus `Registry.process`) only checks that the body's HMAC matches the app's `api_secret_key`; it never checks that the `shop` header is consistent with anything else: [3](#0-2) 

`Registry.process` then hands the header-derived, unauthenticated `shop` straight to the app's handler as trusted tenant identity: [4](#0-3) 

Because a single app has one `api_secret_key` shared across every shop that installs it, any tenant that has legitimately installed the app (an "unprivileged" merchant relative to any other tenant) will receive genuinely Shopify-signed webhooks (`raw_body` + valid `hmac`) for their own shop. That same `raw_body`/`hmac` pair remains valid under `HmacValidator.validate` regardless of what `x-shopify-shop-domain` header accompanies it, because the header is not part of the signed bytes. An attacker who controls their own installed shop can therefore capture one such genuine webhook and replay the identical body+HMAC to the app's webhook endpoint while swapping the `x-shopify-shop-domain` (or `shopify-shop-domain`) header to name a different, victim shop. The library will report this as a validly-verified webhook and pass `WebhookMetadata` with the victim's shop name and the attacker's forged/replayed body to the handler.

The library's own documentation reinforces the false assumption that verification covers the whole request, stating that `Registry.process` "will verify the request did indeed come from Shopify," without qualifying that only the body — not the shop attribution — is authenticated: [5](#0-4) 

### Impact Explanation
This breaks the tenant boundary the library is supposed to establish for webhook processing: an app author reasonably relies on `data.shop` (from `WebhookMetadata`) as an authenticated tenant identifier, since it comes from a call that "verifies the request came from Shopify." A malicious actor who is merely a legitimate merchant of their own store (not privileged with respect to any other merchant) can make the app believe a webhook (topic, body, webhook_id) belongs to an arbitrary other shop using the app. Depending on how the host app keys its data/session lookups off `data.shop`, this can cause cross-tenant data confusion, corruption of another merchant's records, or forged mandatory compliance webhooks (e.g., spoofing `customers/redact`/`shop/redact` attributed to a victim shop). This matches the "cross-tenant access" criterion for High/Critical impact.

### Likelihood Explanation
Exploitation only requires the attacker to install the target app on a shop they control (a normal, unprivileged action), capture one genuine webhook delivery, and replay it with a modified `shop-domain` header value to the app's public webhook endpoint. No access token, `client_secret`, or privileged account for the victim shop is required. This is straightforward to carry out against any app using this gem's `Registry.process`/`Request` as documented.

### Recommendation
Bind the tenant identity to the signed payload before trusting it: either include the shop-domain (and preferably the webhook id/topic) inside the HMAC signable string, or have the gem require the caller to supply the expected shop for the session/store being acted upon and assert equality against the header value before invoking the handler, and update `docs/usage/webhooks.md` to clarify that only the payload authenticity — not sender shop attribution — is currently verified.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, receiving genuine Shopify-signed webhooks for that shop.
2. Attacker captures a `POST` webhook delivery: raw body `B` and header `x-shopify-hmac-sha256: H` (valid HMAC of `B` under the app's shared `api_secret_key`), plus `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker replays a request to the same webhook endpoint with the identical body `B` and header `H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses headers normally; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and finds it matches `H` — validation succeeds.
5. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, i.e., the app processes attacker-controlled data as though it originated from the victim shop.
