## Analog Found: Oracle price staleness exploitable in `SimplexPaymaster`'s gas-sponsorship pricing

### Title
MEV/front-running of Chainlink oracle updates lets a UserOp sender pay stale, favorable token prices for gas sponsorship, draining the paymaster's native deposit - (File: `evm/src/utils/SimplexPaymaster.sol`)

### Summary
`SimplexPaymaster` charges ERC-20 tokens for ERC-4337 gas sponsorship using a price computed directly from two live Chainlink feeds at validation time, with no delay, TWAP, or deviation check beyond a maximum staleness window. This mirrors the reported bug class: a rate used to settle value between a user and the protocol is derived from a price oracle whose update transactions are visible in the mempool, so an actor can time their own transaction around the oracle update to capture the rate discontinuity at the protocol's expense.

### Finding Description
`_tokenPrice` computes the amount of ERC-20 token owed per unit of native gas directly from `AggregatorV3Interface.latestRoundData()` for both the native asset and the fee token: [1](#0-0) 

`_getOraclePrice` only guards against a stale or non-positive Chainlink answer, but does not otherwise smooth, delay, or rate-limit how the price is consumed the instant a new round lands: [2](#0-1) 

This price is read at `_fetchDetails`, called during every `_validatePaymasterUserOp`, i.e. on every UserOp that uses this paymaster: [3](#0-2) 

Because the paymaster is described as "fully onchain, permissionless" and callable by any account holding a registered fee token, an attacker (or a colluding relayer/bundler) monitoring the mempool for the Chainlink update transaction can submit a UserOp that lands in the same block just before the update, locking in the stale (pre-update) `tokenPrice`. If the native asset's USD price is about to rise (or the fee token's price is about to fall), `tokenPrice` computed pre-update requires fewer fee-token units than the post-update fair value, so the attacker pays less than the true cost of the native gas the paymaster's EntryPoint deposit funds: [4](#0-3) 

This is exactly the bug class in the reported issue: a protocol quotes a fixed rate off an oracle, the rate jumps discretely on an update transaction, and anyone watching the mempool can transact to capture the delta rather than the protocol.

### Impact Explanation
Every sponsored UserOp submitted with a stale, favorable price directly under-charges the fee-token amount relative to the native gas the paymaster's EntryPoint deposit actually spends, transferring value from the paymaster's treasury/deposit to the UserOp submitter. Because this can be repeated on every relevant Chainlink round, and there is no cap on how many UserOps can be submitted around a given price update (only the per-op permit amount is bounded), this is a recurring value leak out of protocol-controlled funds (the paymaster's native EntryPoint deposit and/or treasury markup), matching the "theft of protocol assets" impact class.

### Likelihood Explanation
Chainlink price update transactions are ordinary transactions visible in the public mempool before inclusion, so timing a UserOp submission around them is a standard MEV technique requiring no special privilege — any address able to construct a valid paymaster UserOp (with a permit/Permit2 signature over a registered fee token) can attempt it. The contract's own documentation acknowledges the oracle risk ("bounding exposure to the residual allowance even against a malicious oracle") but this only bounds a single op's permit size; it does not prevent the underlying stale-price arbitrage from being executed repeatedly.

### Recommendation
- Introduce a minimum delay or a TWAP/median-of-recent-rounds price instead of the latest raw round for `_tokenPrice`, so a single discrete update cannot be raced.
- Consider bounding the maximum price deviation allowed between consecutive `_tokenPrice` reads within a short block window, rejecting or re-pricing sponsorship requests that fall right after a large jump.
- Alternatively, require a minimum confirmation delay after a Chainlink round update before the paymaster will use the new price for the first N blocks, closing the front-running window used to exploit the discontinuity.

### Proof of Concept
1. Attacker monitors the mempool and detects a pending Chainlink `transmit`/answer-update transaction for `nativeOracle` that will raise the native asset's USD price (making `tokenPrice` cheaper pre-update per `_tokenPrice`'s formula: `(nativeUsd * 10**tokenDecimals * (10000+markupBps)) / (tokenUsd*10000)`).
2. Attacker crafts a UserOp with `paymasterAndData` in mode `0x00`/`0x02` referencing the registered fee token and submits it with higher priority fee/gas so it lands in the same block just before the Chainlink update.
3. `_validatePaymasterUserOp` → `_fetchDetails` → `_tokenPrice` reads the stale, cheaper price via `_getOraclePrice`, computing a `prefundAmount`/`erc20Cost` lower than what the post-update fair price would require.
4. The paymaster's EntryPoint deposit pays the actual (post-update, higher-value) native gas cost while the attacker is charged the stale (lower-value) token amount, repeatable across successive rounds, draining value from the paymaster's deposit/treasury over time.

```text
        PackedUserOperation calldata userOp,
        bytes32 /* userOpHash */
    )
        internal
        view
        override
        returns (uint256 validationData, IERC20 token, uint256 tokenPrice)
    {
        bytes calldata data = userOp.paymasterData();
        if (data.length < 21) revert InvalidPaymasterData(data.length);

        uint8 mode = uint8(data[0]);
        if (mode != 0x00 && mode != 0x02) revert InvalidMode(mode);

        address tokenAddr = address(bytes20(data[1:21]));

        TokenConfig memory cfg = tokenConfigs[tokenAddr];
        if (address(cfg.tokenOracle) == address(0)) revert TokenNotRegistered(tokenAddr);
        if (!cfg.active) revert TokenNotActive(tokenAddr);

        tokenPrice = _tokenPrice(cfg);
        token = IERC20(tokenAddr);
```

```text
    function _tokenPrice(TokenConfig memory cfg) internal view returns (uint256) {
        uint256 nativeUsd = _getOraclePrice(nativeOracle, nativeOracleDecimals);
        uint256 tokenUsd = _getOraclePrice(cfg.tokenOracle, cfg.tokenOracleDecimals);

        return (nativeUsd * (10 ** cfg.tokenDecimals) * (10_000 + markupBps)) / (tokenUsd * 10_000);
    }
```

```text
    /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
```
