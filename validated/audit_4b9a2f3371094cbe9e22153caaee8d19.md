### Title
`WrappedHyperFungibleToken` locks/unlocks a fixed `amount` without balance-delta accounting, causing fund loss or unlock failure for rebasing/fee-on-transfer underlying tokens - ([File: sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol])

### Summary
`WrappedHyperFungibleToken.send()` calls `safeTransferFrom(msg.sender, address(this), params.amount)` and then commits the caller-supplied `params.amount` — not the actual balance change — into the cross-chain `Message` that is dispatched to mint/unlock tokens on the destination chain. The contract never reconciles its actual underlying-token balance against the sum of amounts it has promised to release via `onAccept`/`onPostRequestTimeout`, which unconditionally transfer the encoded `message.amount` of underlying tokens. [1](#0-0) 

### Finding Description
The wrapper's custody model assumes 1 underlying token locked == 1 unit of cross-chain claim, backed by exactly matching balances:

- `send()` locks tokens with `safeTransferFrom(msg.sender, address(this), params.amount)` and immediately encodes `params.amount` (the requested amount, not the amount actually received) into the `Message.amount` field that becomes the cross-chain commitment. [2](#0-1) [3](#0-2) 

- `onAccept()` (unlock path) and `onPostRequestTimeout()` (refund path) both perform `IERC20(_underlying).safeTransfer(beneficiary/refundee, message.amount)` — a fixed amount taken from an ISMP message body, with no check that the contract's actual token balance can cover it. [4](#0-3) [5](#0-4) 

Unlike `HyperFungibleTokenImpl`'s explicit role-gated `mint`/`burn` on a self-issued ERC20 (which is unaffected because the token isn't external), `WrappedHyperFungibleToken` wraps an arbitrary externally supplied ERC20 configured once via `configure()` and never revisited. If that underlying token is:
- A **positive-rebase token** (e.g., an aToken-style yield-bearing asset) — the contract's actual balance grows over time beyond the sum of amounts it promised to unlock. That excess is never tracked or exposed by any accounting variable, and there is no function to sweep or distribute it — it is permanently stuck in the contract.
- A **negative-rebase or fee-on-transfer token** — the actual balance held by the contract can fall below the sum of amounts it has already committed to release via dispatched (and possibly already relayed/finalized) `Message`s. Because `onAccept` performs a fixed-amount `safeTransfer` with no balance check, once the shortfall is reached, legitimate unlock calls for already-dispatched, proven ISMP messages will revert on insufficient balance, permanently blocking delivery of that route/message.

This is the same root-cause pattern as the referenced Blueberry `WERC20` finding: fixed accounting of amounts (`amount`/`params.amount`) instead of tracking real balance deltas at both lock and unlock time, applied here across the cross-chain trust boundary rather than a local vault.

### Impact Explanation
- For yield-bearing/rebasing underlying tokens, the excess balance accrued to the contract is permanently locked — user funds that should belong pro rata to depositors are unrecoverable (Medium impact: permanent freezing of "excess" funds).
- For deflationary/fee-on-transfer or negative-rebasing tokens, this can degrade to insolvency: the contract can end up owing more underlying tokens across all in-flight and completed cross-chain transfers than it actually holds, causing `onAccept` to revert for legitimately delivered/relayed messages — i.e., a route that becomes unable to deliver already-dispatched messages, freezing user funds that are stuck mid-transfer (unlock side reverts forever since the message body's fixed `amount` can't be re-encoded).
- Reachable by any ordinary unprivileged user calling `send()` on a `WrappedHyperFungibleToken` instance configured (by the owner) with such a token as `_underlying` — no privileged action needed to trigger the loss once the token type is in use.

### Likelihood Explanation
Likelihood depends on the owner configuring the wrapper with a rebasing or fee-on-transfer ERC20 via `configure()`. This is plausible: the contract is a generic "wrap any ERC20" bridge and the docs describe wrapping "existing ERC20 tokens" without restricting token type or warning against non-standard tokens. Given the growing prevalence of yield-bearing/rebasing assets bridged cross-chain, this is a realistic deployment scenario, though it requires that specific token choice (not a universal vulnerability for all deployments).

### Recommendation
- In `send()`, measure the actual balance delta (`balanceBefore`/`balanceAfter` around `safeTransferFrom`) and use that measured amount in the dispatched `Message`, rather than trusting `params.amount`.
- Track total escrowed/locked amount per underlying token, and only allow the excess actual balance (rebase yield) to be swept via an explicit, accounted mechanism (e.g., pro-rata distribution or admin-directed handling), rather than left inaccessible.
- Alternatively, explicitly document and enforce (e.g., via a token allow-list or standard-compliance check) that only strictly non-rebasing, non-fee-on-transfer ERC20 tokens may be configured as `_underlying`.

### Proof of Concept
1. Owner deploys `WrappedHyperFungibleToken` and calls `configure()` with `_underlying` set to a positive-rebasing token (balance of holders increases over time without transfers). [6](#0-5) 
2. User A calls `send()` with `amount = 100`; contract's balance becomes 100, and `Message.amount = 100` is dispatched. [3](#0-2) 
3. Time passes; the rebasing token increases the contract's balance to 110 (10 tokens of yield accrue) with no corresponding change tracked anywhere in the contract.
4. User A bridges back; destination chain HFT burns 100 wrapped tokens and dispatches a message back to release exactly 100 from escrow via `onAccept`, which transfers exactly `message.amount = 100`. [4](#0-3) 
5. The 10 extra tokens remain permanently stuck in the `WrappedHyperFungibleToken` contract with no function able to recover or distribute them.

        bytes memory dest = _supportedChains[params.dest];

            data: params.data

            dest: params.dest,
            to: dest,
            body: body,
            timeout: params.timeout,
            fee: params.relayerFee,

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        HyperFungibleToken.Message memory message = abi.decode(request.body, (HyperFungibleToken.Message));
        address beneficiary = _toAddr(message.to);

        if (_isWeth) {
            // Try a native-ETH push first (cheap for EOAs and payable contracts);
            // if the recipient cannot accept native value (no `receive()` / `fallback()
            // payable`), re-wrap the withdrawn ETH and deliver the underlying WETH as
            // an ERC-20 transfer instead. This mirrors the deposit-side flexibility of
            // `send()` (which accepts WETH from non-payable callers via `safeTransferFrom`)
            // so the refund path doesn't permanently lock funds for the same caller class.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = beneficiary.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(beneficiary, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(beneficiary, message.amount);

    function onPostRequestTimeout(PostRequestTimeout calldata incoming) external override onlyHost whenNotPaused {
        HyperFungibleToken.Message memory message = abi.decode(incoming.request.body, (HyperFungibleToken.Message));
        address refundee = _toAddr(message.from);

        if (_isWeth) {
            // Try a native-ETH push first; if the refundee cannot accept native value
            // (e.g. the caller used the ERC-20 deposit path in `send()` from a
            // non-payable contract), re-wrap the withdrawn ETH and deliver the
            // underlying WETH as an ERC-20 transfer so the timeout still settles and
            // funds are not permanently locked.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = refundee.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(refundee, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(refundee, message.amount);
        }

        emit Refunded({to: refundee, amount: message.amount});
    }
