## Title
Unchecked ERC20 return value in escrow withdrawal permanently locks/burns solver funds - (`evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` (`evm/tron/contracts/apps/IntentGatewayV2.sol`) imports and declares `using SafeERC20 for IERC20;` [1](#0-0)  but does **not** use `safeTransfer` for outbound escrow payouts. Instead, `withdraw()` and the `SweepDust` handler make raw low-level `.call()`s encoding `IERC20.transfer.selector` and only check that the call did not revert (`success`), never decoding/validating the returned boolean payload.

### Finding Description
In `withdraw()`, escrowed tokens are released to the beneficiary via:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
``` [2](#0-1) 

and identically for fee redemption:
```solidity
(bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
if (!success) revert TransferFailed();
``` [3](#0-2) 

and in the `SweepDust` handler:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, req.beneficiary, amount));
if (!success) revert TransferFailed();
``` [4](#0-3) 

`success` from a low-level `.call` only reflects whether the callee reverted — it says nothing about the ABI-encoded return value. Any ERC20/TRC20 token that returns `false` on failure instead of reverting (a documented non-standard-but-common behavior, and exactly the bug class this report targets) will cause `success == true` even though no tokens were actually moved. The code proceeds to decrement escrow accounting unconditionally right after:
```solidity
_orders[body.commitment][token] -= amount;
``` [5](#0-4) 

This is the exact analog of the reported `StakedToken.sol` bug — raw `transfer`/`transferFrom` calls whose boolean return is unchecked — but here it manifests in the Intent Gateway's cross-chain settlement path reachable by any solver, since `withdraw()` is invoked from `onAccept()` when a `RedeemEscrow`/`RefundEscrow` message is delivered from Hyperbridge: `if (kind == RequestKind.RedeemEscrow || kind == RequestKind.RefundEscrow) { ... return withdraw(body, kind == RequestKind.RefundEscrow); }` [6](#0-5) .

Notably, the sibling EVM contract `evm/src/apps/IntentGatewayV2.sol` and `evm/src/apps/intentsv2/IntentsBase.sol` correctly use `IERC20(token).safeTransfer(beneficiary, amount)` for the same operation [7](#0-6) , confirming the Tron variant regressed to the unsafe raw-call pattern despite importing `SafeERC20`.

### Impact Explanation
If the escrowed input token (or the protocol fee token) is a non-standard TRC20/ERC20 that returns `false` instead of reverting on failure (e.g. due to a paused state, blacklist, insufficient contract balance edge case, or any other soft-failure implementation), the solver/beneficiary silently receives nothing while the contract's internal escrow accounting (`_orders[commitment][token]`) is permanently decremented as if payment succeeded. The underlying tokens remain trapped in the `IntentGatewayV2` contract with the accounting now showing zero owed, so there is no remaining code path to recover them — a permanent freezing/loss of user (solver) funds. This is a Medium/High severity accounting-integrity bug reachable by any relayer delivering a legitimate cross-chain settlement message.

### Likelihood Explanation
Reachability requires only that the escrowed token or fee token be a non-standard token that returns `false` rather than reverting — a real-world pattern for several deployed tokens (and notably common on Tron/TRC20 ecosystems, which is exactly what this contract variant targets). No malicious admin or privileged actor is needed; a normal solver fill → `RedeemEscrow` delivery flow triggers `withdraw()` unconditionally for whatever token was configured as input/fee token.

### Recommendation
Replace the raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `withdraw()` and the `SweepDust` handler with `IERC20(token).safeTransfer(beneficiary, amount)`, using the already-imported `SafeERC20` library (already declared via `using SafeERC20 for IERC20;` at the top of the contract) so failures decode and validate the boolean return value and revert on both call failure and `false` return, consistent with the rest of the codebase (`evm/src/apps/intentsv2/IntentsBase.sol`).

### Proof of Concept
1. Deploy a TRC20/ERC20 mock token whose `transfer` returns `false` when, e.g., `to` is blacklisted or balance insufficient, without reverting.
2. Configure this token as an order's input token; a user places an order and it gets filled cross-chain, triggering a `RedeemEscrow` message back to the source (Tron) chain.
3. `onAccept()` routes to `withdraw()`, which calls `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))`; the mock token returns `(true, abi.encode(false))` — the call succeeds (`success == true`) but transfers nothing.
4. `_orders[body.commitment][token] -= amount` executes, permanently zeroing the escrow record even though the beneficiary received no tokens; the tokens remain locked in the contract with no method to reclaim them.
