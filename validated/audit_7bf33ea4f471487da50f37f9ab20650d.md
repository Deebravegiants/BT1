Audit Report

## Title
Bridge delivery fee factor can be inflated by unrelated (non-bridge) traffic to the sibling BridgeHub, since congestion is measured at the shared XCMP-channel level, not at the bridge-lane level - (File: bridges/modules/xcm-bridge-hub-router/src/lib.rs)

## Summary
`Pallet::on_message_sent_to_bridge` and `Pallet::on_initialize` gate fee-factor increase/decrease exclusively on `T::LocalXcmChannelManager::is_congested(&T::SiblingBridgeHubLocation::get())`. [1](#0-0) [2](#0-1)  In the deployed asset-hub runtimes, this manager is `InAndOutXcmpChannelStatusProvider`, which reports congestion based on the generic HRMP/XCMP channel state (channel suspension or `queued_pages > 4`) for the entire sibling BridgeHub parachain destination, not on bridge-specific traffic. [3](#0-2)  Because `OutboundXcmpStatus`/queued pages are shared across all XCM traffic to that parachain, any unrelated XCM message queuing to the BridgeHub can inflate `queued_pages` and flip `is_congested` to true, causing the router to raise fees for/freeze recovery of legitimate bridge users regardless of actual bridge-lane load.

## Finding Description
The code exactly matches the claim: `on_message_sent_to_bridge` increases `delivery_fee_factor` whenever `is_channel_with_bridge_hub_congested || is_bridge_congested`, and `on_initialize` refuses to decrease the factor under the same congestion check. [4](#0-3)  `InAndOutXcmpChannelStatusProvider::is_congested` resolves congestion purely from `Parachain(para_id)` — the whole sibling parachain — checking inbound suspension and delegating to `OutXcmpChannelStatusProvider::is_congested`, which checks `outbound_channel_state` and the `MAX_QUEUED_PAGES_BEFORE_DEACTIVATION` threshold of 4 pages. [5](#0-4)  This status is confirmed to be wired into the real asset-hub-rococo and asset-hub-westend runtime configs as `LocalXcmChannelManager` (one usage match each in `cumulus/parachains/runtimes/assets/asset-hub-rococo/src/lib.rs` and `asset-hub-westend/src/lib.rs`), corroborating that this is not a mock-only path. The existing guard (`is_congested` check) is insufficient because it cannot distinguish bridge-exported messages from any other XCM message queued to the same destination parachain over the shared HRMP channel — there is no bridge-lane-specific accounting anywhere in this code path.

## Impact Explanation
The impact described is real but is an economic griefing vector rather than a fund-loss/insolvency bug: an attacker who queues enough unrelated XCM traffic to the sibling BridgeHub parachain can cause `delivery_fee_factor` to increase for genuine bridge users and prevent its natural decay, raising the fees legitimate users pay per `ExporterFor::exporter_for`. This is a real design coupling issue between generic XCMP channel congestion and bridge-specific fee accounting, as documented by the codebase's own `prdoc/stable2412/pr_6781.prdoc`, which exists in-repo and discusses moving the bridge-hub-side congestion mechanism away from generic XCMP-queue monitoring for similar reasons (though the exact quoted prose from the summary could not be located verbatim, the prdoc file is present, corroborating the historical concern).

## Likelihood Explanation
Exploitability is bounded by practical constraints not fully resolved in this review: triggering `queued_pages > 4` or channel suspension requires sustained throughput of enqueued messages to the BridgeHub parachain exceeding the per-block drain rate, gated by relay-chain HRMP channel capacity, XCM execution weight/fee costs, and possibly `SendXcmOrigin`/barrier filters on `pallet_xcm::send` in the specific runtime — none of which were retrievable in this pass. This makes the attack plausible in principle but its cost/feasibility versus the griefing benefit is unquantified and was explicitly noted as unverified by the report itself ("not directly measurable from the indexed code").

## Recommendation
Decouple the bridge fee-factor congestion signal from generic per-destination-parachain XCMP queue state, either by having BridgeHub explicitly report bridge-lane-specific congestion via `report_bridge_status` (already supported), or by tracking bridge-attributable queued bytes/pages separately from the parachain-wide `OutboundXcmpStatus`.

## Proof of Concept
Unit test extension of `bridges/modules/xcm-bridge-hub-router/src/lib.rs` mock tests: (1) set up an uncongested bridge at `MIN_FEE_FACTOR`; (2) toggle the mock `LocalXcmChannelManager` to congested without any bridge message being sent (simulating unrelated XCMP traffic pushing `queued_pages > 4`); (3) send a single small bridge message via `send_xcm` and assert `DeliveryFeeFactorIncreased` fires; (4) call `on_initialize` repeatedly while congestion persists and assert the fee factor never decreases. A companion `xcm-emulator` fork test on asset-hub-rococo/westend would need to enqueue several unrelated `pallet_xcm::send` messages to the sibling BridgeHub parachain to push `queued_pages > 4`, then confirm `pallet_xcm_bridge_hub_router::Bridge::get().delivery_fee_factor` rises for a subsequently sent bridged message — this fork-level validation (required to confirm real-world throughput feasibility) was not performed in this review.

	for InAndOutXcmpChannelStatusProvider<Runtime>
{
	fn is_congested(with: &Location) -> bool {
		// handle congestion only for a sibling parachain locations.
		let sibling_para_id: ParaId = match with.unpack() {
			(_, [Parachain(para_id)]) => (*para_id).into(),
			_ => return false,
		};

		// if the inbound channel with recipient is suspended, it means that we are unable to
		// receive congestion reports from the `with` location. So we assume the pipeline is
		// congested too.
		if pallet::Pallet::<Runtime>::is_inbound_channel_suspended(sibling_para_id) {
			return true;
		}

		// if the outbound channel with recipient is suspended, it means that one of further
		// queues (e.g. bridge queue between two bridge hubs) is overloaded, so we shall
		// take larger fee for our outbound messages
		OutXcmpChannelStatusProvider::<Runtime>::is_congested(with)
	}
}

/// Adapter implementation for `bp_xcm_bridge::ChannelStatusProvider` and/or
/// `bp_xcm_bridge_hub_router::XcmChannelStatusProvider` which checks only `OutboundXcmpStatus`
/// for defined `Location` if is suspended.
pub struct OutXcmpChannelStatusProvider<Runtime>(core::marker::PhantomData<Runtime>);
impl<Runtime: crate::Config> OutXcmpChannelStatusProvider<Runtime> {
	fn is_congested(with: &Location) -> bool {
		// handle congestion only for a sibling parachain locations.
		let sibling_para_id: ParaId = match with.unpack() {
			(_, [Parachain(para_id)]) => (*para_id).into(),
			_ => return false,
		};

		// let's find the channel's state with the sibling parachain,
		let Some((outbound_state, queued_pages)) =
			pallet::Pallet::<Runtime>::outbound_channel_state(sibling_para_id)
		else {
			return false;
		};
		// suspended channel => it is congested
		if outbound_state == OutboundState::Suspended {
			return true;
		}

		// It takes some time for target parachain to suspend inbound channel with the target BH and
		// during that we will keep accepting new message delivery transactions. Let's also reject
		// new deliveries if there are too many "pages" (concatenated XCM messages) in the target BH
		// -> target parachain queue.

		// If the outbound channel has at least `N` pages enqueued, let's assume it is congested.
		// Normally, the chain with a few opened HRMP channels, will "send" pages at every block.
		// Having `N` pages means that for last `N` blocks we either have not sent any messages,
		// or have sent signals.

		const MAX_QUEUED_PAGES_BEFORE_DEACTIVATION: u16 = 4;
		if queued_pages > MAX_QUEUED_PAGES_BEFORE_DEACTIVATION {
			return true;
		}

		false
	}
}
