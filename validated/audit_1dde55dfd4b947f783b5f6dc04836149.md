## Title
Webhook `shop` (and `topic`/`webhook_id`) headers are not bound to the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request body. The `shop-domain`, `topic`, `webhook-id`, and `api-version` HTTP headers are never included in the signed material, yet they are trusted verbatim and forwarded to the app's registered handler as the tenant/shop identity for the payload. Because the same `api_secret_key` is shared by every shop that installs the app, any unprivileged user who can get one legitimately signed webhook delivered to their own (self-installed) shop can replay that body/HMAC pair while substituting an arbitrary `shop-domain` header, causing the host application to process attacker-controlled data under a spoofed (victim) shop identity.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes and compares the HMAC exclusively over that signable string: [2](#0-1) 

`Registry.process` treats a passing HMAC check as sufficient authentication for the whole request, then immediately reads the unauthenticated `shop`, `topic`, `webhook_id`, and `api_version` headers straight off the request object and hands them to the handler as trusted metadata: [3](#0-2) 

`Request#shop`/`#topic`/`#webhook_id`/`#api_version` are plain header reads with no cryptographic binding to the signed body: [4](#0-3) 

The identity binding that should hold is:
`hmac_valid(body) == true` should imply `shop_header == shop_that_Shopify_actually_associated_with_this_body`.

In this implementation, `hmac_valid(body)` only proves the body bytes were signed at some point with the app's shared `api_secret_key` — it says nothing about which shop header accompanies it. Since `api_secret_key` is identical across every shop that installs the app, a party who legitimately controls one shop installation can obtain a validly signed `(body, hmac)` pair (e.g. by triggering `orders/create` on their own store with attacker-chosen order fields) and then resend that exact body+HMAC to the app's webhook endpoint with a different `shop-domain` header value. `Registry.process` will accept it, because `HmacValidator.validate` never inspects the `shop` header at all.

### Impact Explanation
This breaks the tenant boundary the webhook handler relies on. Host applications commonly use the `shop` value delivered in `WebhookMetadata` to select which merchant's stored session/access token to act on, or to attribute/persist the payload to a specific tenant's records. An attacker who owns any shop where the app is installed can:
1. Trigger a real Shopify event on their own store with attacker-controlled body content (many webhook topics contain fields largely under the merchant's control, e.g., order notes, customer metadata, product data).
2. Capture the resulting legitimately-signed webhook request.
3. Replay it to the app's webhook endpoint with the `shop-domain` header changed to a victim shop's domain.

Because the signature check never touches the `shop` header, the forged request passes validation and the host application processes attacker-supplied data as if it originated from the victim tenant — a cross-tenant data-integrity/spoofing issue reachable by any unprivileged user who can install the app on a shop they control.

### Likelihood Explanation
Likelihood is realistic: installing a Shopify app on a free/dev store is trivial for any internet user, obtaining a legitimately-signed webhook for a chosen topic requires no special privilege, and replaying an HTTP POST with a modified header is straightforward. No possession of `api_secret_key`, access tokens, or any privileged account is required — the attacker only needs to be one of the app's many (self-serviced) installations, which is the normal, expected way any merchant interacts with the app.

### Recommendation
Bind the shop (and ideally the topic/webhook id) to the signature verification, not just the raw body. Concretely:
- Include the `shop-domain` (and `topic`) header in the signable string used by `HmacValidator`, mirroring how `Auth::Oauth::AuthQuery#to_signable_string` binds `shop` into its own signed payload.
- Alternatively/additionally, require callers of `Registry.process` to pass the expected shop (derived from an authenticated source, e.g. the session lookup key already used to store that shop's data) and assert `request.shop == expected_shop` before dispatching to the handler.
- Document clearly that `WebhookMetadata#shop` is currently unauthenticated and must not be used as a sole tenant-selection key without additional verification.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`.
2. Trigger `orders/create` (or any topic reachable to a merchant) with attacker-chosen body content.
3. Capture the resulting webhook delivery, e.g.:
```
POST /webhooks
x-shopify-topic: orders/create
x-shopify-hmac-sha256: <valid HMAC over body>
x-shopify-shop-domain: attacker.myshopify.com
{ ...attacker-controlled JSON body... }
```
4. Resend the identical body and `x-shopify-hmac-sha256` value, but change the header:
```
x-shopify-shop-domain: victim.myshopify.com
```
5. `ShopifyAPI::Webhooks::Registry.process` (via `lib/shopify_api/webhooks/registry.rb#process`) calls `Utils::HmacValidator.validate(request)`, which only checks the body against the HMAC and returns `true` regardless of the `shop-domain` header value — confirmed by `HmacValidator#validate_signature` at `lib/shopify_api/utils/hmac_validator.rb:26-31` never referencing `verifiable_query.shop`. The handler then receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and attacker-controlled body content, exactly as if Shopify itself had delivered that webhook for the victim's store.
