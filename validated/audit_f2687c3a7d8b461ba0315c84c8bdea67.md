### Title
Accidental native-token payment during ERC20-mode `send()` is silently trapped with no refund or recovery path - (File: `sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol`)

### Summary
`WrappedHyperFungibleToken.send()` (and the identical `WrappedHyperFungibleTokenUpgradeable.send()`) is marked `payable` to support the WETH-wrapping mode, but when the wrapper is configured for ERC20 mode (`_isWeth == false`), the function neither rejects nor forwards/refunds any `msg.value` sent along with the call. Any user who mistakenly attaches ETH to an ERC20-mode `send()` call permanently loses that ETH.

### Finding Description
`send()` branches on `_isWeth`: [1](#0-0) 

When `_isWeth` is `false`, the `else` branch performs `IERC20(_underlying).safeTransferFrom(...)` and completely ignores `msgValue` — it is never checked against zero, never refunded, and never used to pay the dispatch fee (fees in this branch are paid via `dispatchWithFeeToken(request)` pulling the ERC20 fee token, not native value). Because the function signature is `external payable`, any accidentally attached `msg.value` is accepted into the contract's balance via the `receive()` fallback: [2](#0-1) 

There is no owner-only sweep/rescue function anywhere in the contract to recover stray native balance, and the only other codepath that spends the contract's native balance is the WETH-unwrap refund logic in `onAccept`/`onPostRequestTimeout`, which is gated by `_isWeth` and therefore never executes for an ERC20-mode wrapper. The identical pattern exists in `WrappedHyperFungibleTokenUpgradeable.sol`: [3](#0-2) 

This mirrors the reported analog exactly: a `payable` deposit-style function intended for dual token/native handling silently swallows unexpected native value in the ERC20 branch instead of requiring `msg.value == 0` or refunding the excess.

### Impact Explanation
Any external caller who mistakenly (e.g., via wallet UI defaults, script bugs, or copy-pasted WETH-mode integration code) attaches native ETH/BNB value while calling `send()` on an ERC20-mode `WrappedHyperFungibleToken` deployment permanently loses those funds — they become stuck in the contract with no owner or user-facing function to recover them. This is a permanent freezing-of-funds condition for the mistaken sender.

### Likelihood Explanation
Likelihood is moderate: integrators who deploy or interact with both WETH-mode and ERC20-mode wrappers (which share the same `SendParams`/`send()` ABI and same SDK documentation showing `send{value: nativeFee}(params)` for fee payment) can easily send a nonzero `msg.value` to an ERC20-mode instance by mistake, especially since the fee-quoting docs describe both a native-fee path and a fee-token path for the same function signature.

### Recommendation
In the ERC20 branch (`_isWeth == false`) of `send()`, require `msg.value == 0` and revert otherwise (e.g., `if (msg.value != 0) revert UnexpectedNativeValue();`), consistent with the OpenQ recommendation of rejecting native token when it is not the expected payment mode. Apply the same fix to both `WrappedHyperFungibleToken.sol` and `WrappedHyperFungibleTokenUpgradeable.sol`. Alternatively, add an owner-only rescue function to sweep stray native balance that is not accounted for by pending WETH-mode operations.

### Proof of Concept
1. Owner deploys `WrappedHyperFungibleToken` and calls `configure()` with `isWeth = false` (a plain ERC20 wrapper, e.g. for USDC).
2. A user calls `send{value: 1 ether}(params)` intending to pay a native dispatch fee (as shown in the SDK/docs examples for the WETH-mode flow), not realizing this instance is ERC20-mode.
3. Inside `send()`, since `_isWeth` is `false`, execution goes straight to the `else` branch: `IERC20(_underlying).safeTransferFrom(...)`; `msgValue` (1 ether) is never read, never refunded, and the fee is instead pulled again from the caller via `dispatchWithFeeToken`.
4. The 1 ether sent with the call is retained by the contract via `receive()`, with no function in the contract capable of returning it to the user or letting the owner recover it — the funds are permanently frozen.

        uint256 msgValue = msg.value;
        if (_isWeth && msgValue >= params.amount) {
            msgValue = msgValue - params.amount;
            IWETH(_underlying).deposit{value: params.amount}();
        } else {
            IERC20(_underlying).safeTransferFrom(msg.sender, address(this), params.amount);
