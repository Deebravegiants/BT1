### Title
Webhook shop-domain header is not covered by HMAC verification, allowing cross-tenant webhook shop-spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` exposes a `shop` accessor sourced from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, and `ShopifyAPI::Webhooks::Registry.process` passes that value straight through to the app's webhook handler as the tenant identifier, while the HMAC signature that Shopify computes and this gem verifies covers only the raw request body — never the shop-domain header. This breaks the intended binding `HMAC-verified bytes == bytes the app trusts as tenant-identifying`, since the shop header can be swapped without invalidating the signature.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read from a header that is completely independent of that signable string: [2](#0-1) 

`HmacValidator.validate` / `validate_signature` compute and compare the HMAC exclusively against `verifiable_query.to_signable_string` (i.e. the raw body), never against the shop header: [3](#0-2) 

`Registry.process` validates the HMAC and then forwards `request.shop` unchanged to the registered handler as the authoritative tenant identifier: [4](#0-3) 

Because the shop-domain header is never included in the signed payload, an attacker who possesses one valid `(body, hmac)` pair (e.g., from a webhook fired by their own, attacker-controlled shop installation of the app — a normal, unprivileged event they can trigger themselves) can resend the exact same body and HMAC to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` value for a different (victim) shop. `HmacValidator.validate` will report the signature as valid, because it only checks the raw body, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload originated from the victim shop.

This is precisely the class of bug called out by the report: an identity/tenant-binding field (`shop`) is acted upon by downstream code but is not covered by the same authenticity mechanism (HMAC) that is used to establish trust in the request.

### Impact Explanation
Any application built on this gem that uses `WebhookMetadata#shop` (as returned from `Registry.process`) to decide which merchant/tenant record to create, update, or delete is vulnerable to cross-tenant data injection: an attacker-controlled shop can forge webhook events that are processed under another shop's identity, since the shop attribution is trusted without being part of the authenticated payload. This matches the "cross-tenant access" critical-impact category, since it lets one tenant inject event data attributed to another tenant, bypassing the gem's HMAC-based authenticity guarantee for the shop identity.

### Likelihood Explanation
The attacker only needs: (1) their own legitimate app installation on any shop (unprivileged, self-serve — installing an app that supports Shopify webhooks is something any merchant can do), (2) network access to POST to the app's public webhook endpoint, and (3) knowledge that the shop header is not signed (this is discoverable from Shopify's own documented HMAC scheme, which only signs the body). No access to `api_secret_key`, tokens, or victim credentials is required. The gem's own header-parsing/verification code independently makes no attempt to bind the shop header to the signature, so the flaw is intrinsic to this library and does not depend on the host app misusing the API.

### Recommendation
Include the shop-domain (and ideally topic/api-version) header values in the signable material used by `HmacValidator`, or otherwise cryptographically bind them to the verified payload, so that any tampering with `x-shopify-shop-domain` invalidates the HMAC. At minimum, document prominently that `request.shop` is unauthenticated and that host applications must independently verify the shop against a known, previously-authorized installation (e.g. cross-check against a stored session/access token for that shop) before trusting it for tenant-scoped operations.

### Proof of Concept
1. App has webhooks configured; attacker installs the app on their own shop `attacker.myshopify.com` and triggers a webhook (e.g. `orders/create`), receiving a POST with body `B` and header `x-shopify-hmac-sha256: H` (valid because `H = HMAC(api_secret_key, B)`), plus `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker resends the exact same body `B` and the same `x-shopify-hmac-sha256: H` to the app's public webhook endpoint, but replaces the header with `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses this into a request object; `Utils::HmacValidator.validate` recomputes `HMAC(api_secret_key, B)` and compares it to `H` — this succeeds because the shop header was never part of the signed content (`lib/shopify_api/webhooks/request.rb:35-38`, `lib/shopify_api/utils/hmac_validator.rb:12-31`).
4. `Registry.process` calls the registered handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed(B), ...)` (`lib/shopify_api/webhooks/registry.rb:188-200`), even though the event body actually originated from the attacker's own shop — demonstrating that the shop attribution can be forged despite HMAC verification succeeding.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
