Audit Report

## Title
Cross-workflow HTTP response mix-up due to under-scoped cache key in `responseCache` - ([File: core/services/gateway/handlers/capabilities/v2/response_cache.go])

## Summary
The gateway's outbound-HTTP-action `responseCache` keys cached responses solely by `req.Hash()`, a hash that is proven (by the codebase's own test suite) to be identical across different `WorkflowID`s while still varying by `WorkflowOwner`. This directly contradicts the documented "Workflow Isolation" guarantee in the component's README, and results in a workflow owner's concurrent or sequential workflows sharing cached HTTP responses across distinct workflow executions whenever they issue identical outbound requests.

## Finding Description
`responseCache.Fetch` and `responseCache.Set` use `req.Hash()` as the sole cache key [1](#0-0) , and the lookup path `isExpiredOrNotCached`/cache map access is likewise keyed only on `req.Hash()` [2](#0-1) . The struct's own comment states the hash covers "method, URL, headers, body, workflowOwner" [3](#0-2)  — `WorkflowID` is conspicuously absent.

This is confirmed by the test `TestRequestHash`, which explicitly asserts `"Hash should be the same regardless of WorkflowID"` while a companion test confirms the hash *does* vary with `WorkflowOwner` [4](#0-3) . This directly contradicts the module's documented invariant that "Cache entries are scoped by workflow ID to prevent cross-workflow data leakage" and that the "Cache Key" is "Generated from workflow ID and request hash" [5](#0-4) .

The untrusted, workflow-node-supplied `OutboundHTTPRequest` (which includes `WorkflowID`, decoded directly from node message JSON) is passed unmodified into `Fetch`/`Set` in `makeOutgoingRequest` [6](#0-5) . No code re-derives or incorporates the `WorkflowID` into the cache key before calling `Fetch`/`Set`, so two different workflow executions belonging to the same `WorkflowOwner` that issue byte-identical HTTP Actions (same method/URL/headers/body) collide on the exact same cache entry, and one workflow's execution can be served the other's previously-cached response.

## Impact Explanation
This is a legitimate cross-execution/cross-workflow data confusion bug: state that the codebase documents and intends to be workflow-scoped is actually only owner-scoped. An owner running multiple workflows against the same external endpoint with identical request shape can have one workflow's HTTP Action result served to a different, unrelated workflow execution when `CacheSettings.MaxAgeMs`/`Store` are used — a supported, normal feature per the README, not an edge case. This falls into the "cross-user response corruption" class of impact explicitly allowed in scope, since it breaks the confidentiality/integrity boundary between separate workflow executions that the code's own documentation claims to enforce.

## Likelihood Explanation
No privileged access, malicious node, or elevated role is required. Any workflow owner who operates two or more workflows that call the same external API/webhook with the same method/URL/headers/body — a common and realistic pattern — will trigger the collision automatically whenever caching is enabled (`CacheSettings.Store`/`MaxAgeMs`), which is standard, documented functionality. The behavior is deterministic and repeatable, as directly demonstrated by the existing unit test `TestRequestHash`.

## Recommendation
Incorporate `WorkflowID` (and consider `ExecutionID` for stricter per-execution isolation) into `OutboundHTTPRequest.Hash()`, or otherwise scope the `responseCache` map by `WorkflowID` in addition to the request hash, so the implementation matches the documented "Workflow Isolation" guarantee.

## Proof of Concept
The existing test `TestRequestHash` in `response_cache_test.go` already demonstrates the root cause directly: `req1.WorkflowID = "workflow-123"` and `req2.WorkflowID = "workflow-456"` (same owner, same request otherwise) produce identical hashes [7](#0-6) . To demonstrate end-to-end impact, extend `http_handler_test.go`'s existing `TestHandleNodeMessage`-style setup to: (1) send an `OutboundHTTPRequest` for Workflow A with `CacheSettings.Store=true`, `MaxAgeMs>0`, get a mocked response body `"A"`; (2) send a second `OutboundHTTPRequest` for Workflow B (different `WorkflowID`, same `WorkflowOwner`, identical method/URL/headers/body) within the TTL; (3) assert the mock HTTP client's `Send` is only invoked once and Workflow B receives body `"A"` from `responseCache.Fetch`, proving the cross-workflow cache hit.
