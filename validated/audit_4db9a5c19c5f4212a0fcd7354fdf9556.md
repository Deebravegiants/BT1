I found a concrete analog of the CVE's root-cause pattern (independently valid boundary checks whose combination is never checked to reference the *same* logical segment) in the Pharos state-machine's `verify_state_proof`.

### Title
GetRequest/withdrawal-proof storage key confusion — non-existence lookup indexed only by slot hash, not by (contract address, slot) — allows cross-contract proof substitution in Pharos state proofs - (File: modules/ismp/state-machines/pharos/src/lib.rs)

### Summary
`verify_state_proof` in `modules/ismp/state-machines/pharos/src/lib.rs` (lines 238-336) resolves a query key into a `(contract_addr, slot_hash)` pair, but then looks up the corresponding proof/value maps — `pharos_proof.non_existence_proofs`, `pharos_proof.storage_proof`, and `pharos_proof.storage_values` — solely by `slot_key`/`slot_hash`, never combined with `contract_addr`. This is structurally the same "checked independently, not bound together" flaw as the CVE: the CVE validates `start` and `end` addresses individually but never confirms they fall in the same memory segment; here the code validates "does the contract exist" and "does the slot exist" independently, using maps that are keyed only by the slot component, so a proof entry produced for one contract's slot can be looked up and accepted for a different, requested contract's identical slot number.

### Finding Description [1](#0-0) 
For a 52-byte key, `contract_addr` is parsed from the first 20 bytes and `slot_hash` from the last 32. The subsequent lookups:
```
pharos_proof.non_existence_proofs.get(slot_key.as_slice())
pharos_proof.storage_proof.get(slot_key.as_slice())
pharos_proof.storage_values.get(&slot_hash)
```
are all keyed by `slot_key`/`slot_hash` alone. `contract_address` is only reintroduced afterward, when constructing the leaf key via `spv::build_storage_key(&contract_address, &slot_key)` for the actual Merkle/SPV verification call.

If a GET request batches keys for two different contracts that happen to use the same raw slot number (a routine occurrence — e.g., slot `0` for balances mappings, or any attacker-chosen slot on their own deployed contract), the map lookup for the second contract's slot silently resolves to whatever entry the relayer placed under that slot number in the proof structure (maps overwrite/collide on identical keys since `BTreeMap`/`HashMap` insertion is keyed by slot only). Since `contract_to_keys`/`contract_addr` correctness is enforced later only via the SPV walk itself (`spv::build_storage_key`), the outcome depends entirely on whether the relayer-supplied `proof_nodes` happen to validate against the trusted `state_root` for the *substituted* key — but there is no independent check tying "the proof node retrieved" to "the contract address it was retrieved for" before it is fed into the SPV walk. This mirrors the CVE's flaw: the address (contract) and the offset (slot) are each syntactically well-formed and individually plausible, but the code never enforces that the retrieved proof entry actually belongs to the requested (contract, slot) pair as a bound unit before using it.

Compare this to the sibling EVM implementation `modules/ismp/state-machines/evm/src/lib.rs`, which explicitly groups keys `contract_to_keys` by contract address and defends against contract/key mismatch with `IncompleteStorageProof`/`UnrequestedContractProof` checks that require the storage-proof structure's keys to exactly correspond to the *set of requested contracts* — Pharos lacks this equivalent binding at the map-lookup layer for slot-level entries.

### Impact Explanation
GET responses (`GetResponse.values`) feed directly into application callbacks (`onGetResponse`) across Hyperbridge's cross-chain messaging, and the same `verify_state_proof` code path backs relayer fee accumulation (`pallet_ismp_relayer::accumulate_fees` → `verify_withdrawal_proof` → `state_machine.verify_state_proof`) for Pharos-sourced fee/receipt data [2](#0-1) . A forged/substituted storage entry accepted under the wrong contract could cause: incorrect state delivered to a dependent application (forged message delivery / unsound state commitment), or a forged non-existence/existence result used in relayer fee crediting, enabling unbacked fee accrual. This satisfies "forged message delivery" / "unsound state commitment" criteria.

### Likelihood Explanation
Exploitability is uncertain without confirming whether the off-chain prover (`modules/consensus/pharos/prover`) can be induced by a relayer to submit a `PharosStateProof` whose maps are keyed only by slot and contain colliding slot numbers across different contracts within a single GET batch, and whether the SPV walk (`spv::verify_proof`, which independently binds `contract_address` into `build_storage_key`) would still catch the mismatch in practice. Given `spv::verify_proof` reconstructs the full storage key including the address before walking the trie, a substituted proof node would very likely fail hash verification against the trusted root unless the two contracts/slots coincidentally shared proof paths — this significantly limits practical exploitability and I could not fully verify a working exploit without deeper access to the Pharos SPV format and prover code.

### Recommendation
Key `non_existence_proofs`, `storage_proof`, and `storage_values` maps by `(contract_address, slot_hash)` tuples (or the full 52-byte key) instead of `slot_hash` alone, mirroring the `contract_to_keys` grouping already used in the EVM state machine's `verify_state_proof`, so that a proof entry cannot be resolved for a contract it was not produced for regardless of any downstream SPV check.

### Proof of Concept
Not independently verified — constructing the byte-level `PharosStateProof` and prover-side response would require exercising `modules/consensus/pharos/prover` in a live/test environment (not accessible via static code search) to confirm whether `spv::verify_proof`'s address-bound key reconstruction fully neutralizes the map-lookup ambiguity in practice.

	pub fn verify_withdrawal_proof(
		state_machine: &dyn ismp::consensus::StateMachineClient,
		proof: &Proof,
		keys: Vec<Vec<u8>>,
	) -> Result<BTreeMap<Vec<u8>, Option<Vec<u8>>>, DispatchError> {
		let host = <T as Config>::IsmpHost::default();
		let state = host
			.state_machine_commitment(proof.height)
			.map_err(|_| Error::<T>::ProofValidationError)?;
		// Select the trie root explicitly instead of letting the relayer-supplied proof choose
		// it. Fee accumulation reads ISMP request/receipt metadata, which lives in the global
		// state trie on EVM chains and in the ISMP child trie (overlay root) on substrate
		// chains.
		let root = if proof.height.id.state_id.is_evm() {
			state.state_root
		} else {
			state.overlay_root.ok_or(Error::<T>::ProofValidationError)?
		};
		let result = state_machine
			.verify_state_proof(&host, keys, root, proof)
			.map_err(|_| Error::<T>::ProofValidationError)?;

		Ok(result)
	}
