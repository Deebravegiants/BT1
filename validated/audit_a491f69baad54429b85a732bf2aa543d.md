### Title
Webhook `shop-domain` header is trusted for tenant routing but is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and is validated via `HmacValidator.validate(request)` before being dispatched to app handlers [1](#0-0) . The signature check computes an HMAC purely over the raw request body:

```ruby
sig { override.returns(String) }
def to_signable_string
  @raw_body
end
``` [2](#0-1) 

However, the tenant-identifying field used downstream, `shop`, is read straight from an HTTP header rather than from the signed payload:

```ruby
sig { returns(String) }
def shop
  T.cast(shopify_header("shop-domain"), String)
end
``` [3](#0-2) 

`HmacValidator.validate_signature` recomputes the HMAC only from `verifiable_query.to_signable_string` (the raw body) and compares it to the `hmac` header value using `OpenSSL.secure_compare` [4](#0-3) . The `shop-domain`, `topic`, `api-version`, and `webhook-id` headers play no role in that computation at all.

After validation passes, `Registry.process` builds `WebhookMetadata` directly from `request.shop`, `request.topic`, etc., and calls the app's `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))` [5](#0-4) . Apps are expected to use `data.shop` to determine which merchant/tenant the webhook body applies to (e.g., to look up the correct session/store record), as documented by the `WebhookMetadata` struct [6](#0-5) .

This mirrors the `RentPayload` replay bug class: the report's `RentPayload` was signed but omitted a binding field (`orderHash`), so a signature that was valid for one payload could be replayed against a different order carrying the same signed fields. Here the equality that should hold is:

`bytes covered by HMAC` == `bytes the app trusts to identify the tenant (shop)`

but instead:

`to_signable_string` (raw body only) != `shop` (from an unauthenticated header)

Because Shopify signs webhooks using HMAC over the body only (this is Shopify's real webhook signing scheme, not a bug introduced by this library), the `shop-domain`, `topic`, and other headers are never bound to the signature. Any party that can influence request headers reaching the app's webhook endpoint before this gem validates it (e.g., a component that forwards/proxies webhook headers, a load balancer or CDN that lets header values be attacker-influenced, or any code path that re-uses a previously-captured valid `(body, hmac)` pair with substituted headers) can cause `Request#shop` to report an arbitrary shop domain while the HMAC check still passes, since the check never inspects the header.

### Impact Explanation
If an app implementer (or any component upstream of `Webhooks::Registry.process`) relies on `WebhookMetadata#shop` for tenant identification without independent verification, an attacker who can replay a captured valid `(raw_body, hmac)` webhook while substituting the `shop-domain` header can make the gem attribute another merchant's data/events to a different shop context — i.e., cross-tenant misattribution enabled by this library's validation function, since `HmacValidator.validate` returns `true` regardless of what `shop-domain` says. This matches the "cross-tenant access" impact category, because the identity binding the app is meant to rely on (`shop`) is exactly the field this library fails to authenticate.

### Likelihood Explanation
Exploitability depends on an attacker being able to replay or forge the `shop-domain` header on an otherwise-valid signed webhook body (e.g., via a proxy, shared infrastructure, or webhook forwarding setup) — it does not require the app's `client_secret` or an access token, since the HMAC is computed by Shopify and the header is not part of what's checked. This is a real gap in the library's own validation logic (`HmacValidator`/`Webhooks::Request`), independent of how any specific host app chooses to use `WebhookMetadata`.

### Recommendation
Extend `Webhooks::Request#to_signable_string` (or add a secondary check in `Registry.process`) so that the `shop-domain` (and ideally `topic`, `webhook-id`) headers are cryptographically bound to the signature, or otherwise require the caller to cross-check the shop domain against a known/registered shop before trusting `WebhookMetadata#shop`. At minimum, document clearly that `WebhookMetadata#shop` is unauthenticated and must not be used as a sole tenant-identity source.

### Proof of Concept
1. Capture a legitimately Shopify-signed webhook request: raw body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`, along with header `X-Shopify-Shop-Domain: shop-a.myshopify.com`.
2. Resend the exact same body `B` and the same `H` header to the app's webhook endpoint, but change the `X-Shopify-Shop-Domain` header to `shop-b.myshopify.com`.
3. In `Registry.process`, `Utils::HmacValidator.validate(request)` succeeds because it only recomputes the HMAC over `request.to_signable_string` (`= B`) [2](#0-1) [4](#0-3) .
4. `WebhookMetadata.shop` is set to `"shop-b.myshopify.com"` even though the payload was never signed for shop B [5](#0-4) , causing the app's handler to process shop A's webhook body under shop B's tenant context.
