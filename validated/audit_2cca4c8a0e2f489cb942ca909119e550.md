Audit Report

## Title
User enumeration via distinct login error messages disclosed to unauthenticated clients - (File: core/sessions/localauth/orm.go)

## Summary
The unauthenticated `/sessions` login endpoint returns provider errors verbatim to the client, and `orm.CreateSession` in the local auth backend returns different error content depending on whether an email exists in the `users` table versus whether the password is wrong for a known email, enabling account enumeration by an unauthenticated caller.

## Finding Description
`SessionsController.Create` forwards `err` from `AuthenticationProvider().CreateSession` directly into the 401 JSON API error body: [1](#0-0) . This endpoint is mounted unauthenticated at `POST /sessions` (only rate-limited, not blocked) [2](#0-1) .

In `orm.CreateSession`, the code first looks up the user by email via `FindUser`, and if that lookup fails, returns the raw error immediately: [3](#0-2) . Since `findUser` executes `SELECT * FROM users WHERE lower(email) = lower($1)` via `GetContext`, a non-existent email produces a distinct SQL "no rows" style error (not literally "Invalid email" as the original claim states — that message is unreachable in normal flow because the query already filters by matching email, so `constantTimeEmailCompare` will pass whenever `FindUser` succeeds) [4](#0-3) . When the email does exist but the password is wrong, a distinct `"Invalid password"` error is returned: [5](#0-4) .

The net effect is the same as claimed even though the specific message differs from what was described: an unauthenticated client can distinguish "email not found" (raw DB/no-rows error) from "email found, password wrong" (`"Invalid password"`), because `SessionsController.Create` propagates the raw `err.Error()` string into the response body without normalization [1](#0-0) . No middleware, redaction, or generic-error wrapper intervenes before this value reaches the client.

## Impact Explanation
This is an information-disclosure issue (CWE-209): an unauthenticated attacker can enumerate which email addresses are registered as node/API users by observing distinguishable error text returned from `/sessions`. This does not grant authentication bypass or fund/key access directly, but it discloses account existence that operators would expect to remain private and materially aids follow-on credential-stuffing or phishing against a known-valid account set.

## Likelihood Explanation
The endpoint is intentionally public to allow login and is rate-limited but not blocked [2](#0-1) , so an attacker can enumerate over time with only a single POST per guess and no special privilege. The distinguishing signal is deterministic and always present given the current code path, so likelihood is high for any node exposing this API endpoint.

## Recommendation
Normalize the error path in `orm.CreateSession` so that both "email not found" (including the raw error returned by `FindUser`) and "wrong password" cases return one generic error (e.g., "invalid credentials"), while continuing to record the distinguishing detail only in the audit log (`AuthLoginFailedEmail` / `AuthLoginFailedPassword` calls already do this). Additionally, `SessionsController.Create` should map any 401 from `CreateSession` to a fixed generic message rather than forwarding `err.Error()` verbatim, to prevent future regressions from surfacing internal error text.

## Proof of Concept
1. `POST /sessions` with `{"email":"realuser@example.com","password":"wrongpassword"}` (where `realuser@example.com` is a known valid user) → response body contains `"Invalid password"`.
2. `POST /sessions` with `{"email":"nonexistent@example.com","password":"wrongpassword"}` → response body contains a different error string derived from the raw `FindUser`/SQL "no rows" error (not the literal string "Invalid email" as originally claimed, since that branch is unreachable given the query already filters on matching email).
3. Comparing the two distinct response bodies allows an unauthenticated client to determine whether `email` is registered. This can be verified with a Go integration test against `SessionsController.Create` similar to the existing table-driven test cases in `core/web/sessions_controller_test.go` (lines 39-41), asserting on the exact error string returned for "incorrect pwd" vs "incorrect email" cases rather than just the boolean success/failure.
