### Title
Signup success is determined by an easily-manipulable, locally-computed fraud/pipeline result instead of the authoritative backend enrollment check - (File: src/plans/mod.rs)

### Summary
`do_signup` in `Plan::do_signup` decides whether a signup is a "success" using two different code paths depending on the `user_centric_signup` flag. When that flag is set (and `ignore_user_centric_signups` is not enabled), the orb skips the authoritative backend round-trip (`enroll_user`, which posts the signup and polls the backend for a verified result) and instead derives `success` purely from a locally-computed `signup_reason` value. [1](#0-0)  That `signup_reason` is itself derived from `detect_fraud`, which in this build unconditionally returns `false` because all fraud checks have been stripped (`N_FRAUD_CHECKS = 0`). [2](#0-1) [3](#0-2)  This is structurally the same bug class as the reported Frax issue: a security-critical decision (there, collateral valuation; here, enrollment success) is made from a value that can be trivially forced into the "favorable" state by whoever controls the input (there, a flash-loan-manipulated Curve spot price; here, the always-passing local fraud/pipeline outcome), instead of consulting the tamper-resistant authority (there, an oracle/`get_virtual_price`; here, the backend's `signup_post`/`signup_poll` verification).

### Finding Description
In `do_signup`, once the biometric pipeline finishes, `signup_reason` is computed as `Failure` (pipeline missing), `Fraud` (fraud detected), or `Normal` otherwise:
```rust
let fraud_detected = !self.skip_fraud_checks()
    && self.detect_fraud(orb, debug_report, pipeline.as_ref()).await?;
let signup_reason = if pipeline.is_none() {
    SignupReason::Failure
} else if fraud_detected {
    SignupReason::Fraud
} else {
    SignupReason::Normal
};
``` [4](#0-3) 

`detect_fraud` is a no-op in this build:
```rust
async fn detect_fraud(...) -> Result<bool> {
    orb.set_phase("Fraud detection").await;
    let Some(_pipeline) = pipeline else {
        return Ok(false);
    };
    // FOSS: WE HAVE DELETED ALL FRAUD CHECKS
    Ok(false)
}
``` [2](#0-1) 

`fraud_check.rs` confirms this is by design in the FOSS build (`N_FRAUD_CHECKS: usize = 0`, empty checks arrays). [5](#0-4) [6](#0-5) 

Later, `do_signup` branches on `user_centric_signup`:
```rust
let success = if user_centric_signup && !orb.config.lock().await.ignore_user_centric_signups
{
    debug_report.enrollment_status(match signup_reason {
        SignupReason::Normal => enroll_user::Status::Success,
        _ => enroll_user::Status::Error,
    });
    signup_reason == SignupReason::Normal
} else {
    Box::pin(self.enroll_user(orb, debug_report, &capture, pipeline.as_ref(), signup_reason))
        .await
        .is_success()
};
``` [1](#0-0) 

The `else` branch is the authoritative path: `enroll_user::Plan::run` uploads the iris-code signature and capture data to the backend (`signup_post::request`) and then polls `signup_poll::request` up to 30 times until the backend reports `Status::Completed` with `success: true` — this is where backend-side duplicate detection and fraud confirmation actually happen. [7](#0-6) 

When `user_centric_signup` is true, none of that backend confirmation occurs. `success` is set purely from the on-device `signup_reason`, which — given `detect_fraud` always returns `false` — will be `SignupReason::Normal` for essentially every completed capture (only agent/timeout failures produce anything else). This mirrors the reported vulnerability class exactly: a decision that should rely on an external, manipulation-resistant source of truth instead relies on an internal, real-time, effectively-always-favorable computed value.

### Impact Explanation
Any signup flow that sets `user_centric_signup=true` will be marked `Status::Success` / `SignupReason::Normal` locally without ever confirming with the backend that: (a) the person hasn't already signed up under a different identity, (b) the backend's own fraud/duplicate detection didn't flag the attempt, or (c) the enrollment was actually accepted server-side. This allows misattributed or unauthorized signups to be locally recorded as successful and enables cross-signup state bleed, since the backend-side de-duplication/fraud gate that `enroll_user` normally enforces is bypassed entirely for this code path.

### Likelihood Explanation
The likelihood is high for any deployment using the `user_centric_signup` code path: `detect_fraud` unconditionally returns `false` in this build, so the "manipulable" value that gates the decision is not just theoretically weak — it is a constant. No flash-loan-style precision timing is even required; the branch degenerates to "always succeed locally when pipeline completes," which is a stronger and more trivially triggerable analog of the underlying bug class described in the report (using a spot/instant, attacker-influenceable value for a critical decision instead of an authoritative check).

### Recommendation
- Short term: Do not allow `user_centric_signup` to bypass the backend confirmation (`enroll_user`/`signup_post`/`signup_poll`) entirely. At minimum, still perform the backend round-trip and only use the locally-computed `signup_reason` as a hint, not as the sole basis for `Status::Success`.
- Long term: Ensure any security-critical "success" determination is always corroborated by the backend's authoritative fraud/duplicate-detection system, and treat locally computed fraud/pipeline results as advisory only, consistent with the recommendation to avoid relying on manipulable local state for high-value security decisions.

### Proof of Concept
1. Present a QR code/app flow where the backend returns `authenticated_app_data.user_centric_signup = true` (a supported, legitimate app flow) and ensure `orb.config.ignore_user_centric_signups` is `false` (default-permitted configuration). [8](#0-7) 
2. Complete a biometric capture and pipeline run normally (no need to defeat liveness/fraud detection since `detect_fraud` always returns `false` in this build). [2](#0-1) 
3. Observe that `do_signup` takes the `user_centric_signup` branch, setting `success = (signup_reason == SignupReason::Normal)` without ever calling `enroll_user`/contacting the backend for confirmation. [1](#0-0) 
4. The signup is reported as successful (`debug_report.signup_successful()`) purely from local state, with no server-side duplicate/fraud verification ever performed for this attempt. [9](#0-8)
