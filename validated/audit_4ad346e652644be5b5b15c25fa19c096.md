### Title
Unvetted swap routes can attach hidden caller-funded token transfers to strategy calls - (File: contracts/controller/src/strategies/swap.rs)

### Summary
The controller accepts an opaque `StrategySwap` route and executes it through the configured router while the account owner’s `require_auth()` invocation is still active. Because the controller validates only the router’s effect on its own input/output balances and does not constrain route-internal calls, a malicious route venue can add an unrelated token transfer from the caller to the transaction’s authorization tree. If the caller signs the simulated tree without noticing that extra child invocation, the venue can drain unrelated wallet tokens in the same transaction.

### Finding Description
`swap_collateral` is reachable by an account owner or delegate and accepts attacker-controlled `swap` bytes along with the collateral market and amount. [1](#0-0)  The entrypoint authenticates `caller` and verifies account ownership or delegation before withdrawing collateral. [2](#0-1) 

`StrategySwap` is only an opaque `Bytes` payload for the router; the controller does not decode or whitelist the venues encoded in it. [3](#0-2)  `swap_tokens` forwards that payload to the configured router, authorizing only the controller’s exact input transfer, then checks only the controller’s input spend and output receipt. [4](#0-3)  The contract authorization helper creates one exact `transfer` entry on behalf of the controller, but it does not prevent route code from requesting a separate transfer from the user as a child of the user-authorized controller call. [5](#0-4) 

After the router returns, the checks are confined to `token_in` overspend and a positive `token_out` balance delta. [6](#0-5)  They do not account for unrelated token movements out of the caller’s wallet during router execution.

The same route boundary is reachable through `multiply`, `swap_debt`, and `repay_debt_with_collateral`, but `swap_collateral` is the clearest path because it directly converts a victim’s existing collateral through caller-supplied route bytes. [7](#0-6) [8](#0-7) 

### Impact Explanation
A malicious venue embedded in the route can execute `token::transfer(victim, attacker, amount)` for a token unrelated to the lending position while the victim’s authorization is active. The controller still receives a positive swap output and can pass its final account checks, so the swap succeeds while the victim’s unrelated wallet balance is stolen. This is theft of user funds.

### Likelihood Explanation
The attacker must cause the victim to submit a strategy call containing the malicious route and sign an authorization tree containing the extra token transfer. Wallets or clients that display only the top-level controller call and expected route, rather than forcing review of every child invocation, make this comparable to the embedded-frame issue: attacker-controlled content triggers an action beyond the action the user intended to authorize.

### Recommendation
Do not rely on opaque route bytes and post-call balance checks as the authorization boundary. At minimum:

- Use a typed route representation in the controller interface and reject routes containing unrecognized or unapproved venue addresses.
- Require the router to expose a bounded venue allowlist or route manifest that can be checked before invocation.
- Ensure wallets and clients display every child authorization requested under the controller call and reject unexpected `transfer` calls whose `from` is the user.
- Prefer a settlement design where the router cannot request any authorization beyond the explicitly granted input transfer.

### Proof of Concept
1. Victim owns a lending account with USDC collateral and also holds an unrelated `VICTIM_TOKEN`.
2. Attacker deploys a route-compatible venue contract whose execution calls:

   `VICTIM_TOKEN.transfer(victim, attacker, victim_balance)`

   while still arranging for the configured router to return a positive amount of the requested output token to the controller.
3. Attacker supplies route bytes naming that venue.
4. Victim invokes:

   `swap_collateral(victim, account_id, current=usdc_hub_asset, amount, new=eth_hub_asset, swap=malicious_route)`

5. `swap_collateral` authenticates the victim and withdraws the victim’s USDC into controller custody. [9](#0-8) 
6. `swap_tokens` invokes `router.execute_strategy(controller, amount_in, malicious_route)`. During route execution, the malicious venue requests `VICTIM_TOKEN.transfer(victim, attacker, victim_balance)`, which appears as an additional child beneath the victim’s `swap_collateral` authorization.
7. If the victim signs the simulated tree, the unrelated token transfer succeeds. The router then returns enough `token_out` for `verify_router_output` to pass, and the account can remain solvent. [10](#0-9)

/// Authorizes, on behalf of the current contract, one `transfer(from, to, amount)`
/// call on `token_addr` made deeper in the next contract call (for example by
/// the pool). The entry allows no further sub-invocations.
pub fn authorize_transfer_as_current(
    env: &Env,
    token_addr: &Address,
    from: &Address,
    to: &Address,
    amount: i128,
) {
    let entry = InvokerContractAuthEntry::Contract(SubContractInvocation {
        context: ContractContext {
            contract: token_addr.clone(),
            fn_name: symbol_short!("transfer"),
            args: (from.clone(), to.clone(), amount).into_val(env),
        },
        sub_invocations: Vec::new(env),
    });
    env.authorize_as_current_contract(vec![env, entry]);
