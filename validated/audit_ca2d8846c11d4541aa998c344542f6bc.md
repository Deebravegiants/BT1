## Title
Webhook shop/topic identity not covered by HMAC allows cross-tenant webhook spoofing - (`lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signable string from the raw body only, while the `shop-domain`, `topic`, `api-version`, and `webhook-id` values used for dispatch and delivered to the app's handler come from unauthenticated HTTP headers. Because the app's `api_secret_key` is shared across every shop that installs the app, any user in possession of one *validly signed* webhook body (e.g., from their own store) can replay that body with a forged `shop-domain`/`topic` header to the app's public webhook endpoint, and `Registry.process` will accept it as an authentic webhook for a different tenant.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

All tenant-identifying fields are pulled straight from headers, none of which participate in the signature: [2](#0-1) 

`Registry.process` validates only the HMAC over the body, then immediately trusts `request.topic` and `request.shop` to route and construct the delivered metadata: [3](#0-2) 

The identity binding this design implicitly assumes is: `hmac(raw_body, api_secret_key) valid ⇒ (shop, topic) headers are authentic for that raw_body`. That equality does not hold — `shop` and `topic` are never part of the signed material, so `verified(raw_body) != verified(shop, topic)`. Since `api_secret_key` is the same secret for every merchant that installs a given app (it's an app-level secret, not a per-shop secret), a legitimate webhook captured from Shop A's own store carries a body+HMAC pair that remains valid when replayed with a `shopify-shop-domain` header claiming to be Shop B, or a `shopify-topic` header claiming to be a different topic than the one Shopify actually sent.

### Impact Explanation
Any application built on this gem that uses `WebhookMetadata#shop` (delivered from `request.shop`) to scope data writes, cache keys, or session lookups per tenant can be made to process attacker-supplied JSON as if it originated from a different, victim shop — a cross-tenant data-integrity/confusion issue. It can also be used to invoke a handler registered for a different `topic` than what Shopify actually signed for that body, since `topic` is likewise unauthenticated.

### Likelihood Explanation
The attacker only needs to be an ordinary merchant who has the target app installed on their own store (an "unprivileged" outsider relative to any other tenant). They receive legitimately signed webhook deliveries for their own shop, extract the body/HMAC pair, and POST it directly to the app's public webhook endpoint with forged `shopify-shop-domain`/`shopify-topic` headers. No access token, `api_secret_key`, or privileged access is required — only network access to the app's publicly reachable webhook URL, which is inherent to the webhook feature.

### Recommendation
Bind the tenant-identifying headers into the signed material (or otherwise authenticate them), and reject requests where `request.shop` cannot be corroborated against an expected/registered shop, rather than trusting header values that sit outside the HMAC's coverage.

### Proof of Concept
1. Merchant A installs the app; the app registers a webhook for `orders/create`.
2. Shopify sends a webhook to the app: body `B`, headers `x-shopify-hmac-sha256: HMAC(B, secret)`, `x-shopify-shop-domain: shop-a.myshopify.com`, `x-shopify-topic: orders/create`.
3. Merchant A (attacker) captures this exact `(B, HMAC(B, secret))` pair.
4. Attacker POSTs the same body `B` and same HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: shop-b.myshopify.com` (a victim shop that also installed the app).
5. `HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` succeeds because it only checks `raw_body` against `secret`, which hasn't changed.
6. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) builds `WebhookMetadata` with `shop: "shop-b.myshopify.com"` and dispatches the handler, causing the app to process attacker-controlled content as authentic data for Shop B.
