### Title
Stale commitment-queue index causes premature eviction of a live state commitment after a veto/resubmission cycle - (File: `modules/pallets/ismp/src/host.rs`)

### Summary
`IsmpHost::delete_state_commitment` in `modules/pallets/ismp/src/host.rs:194-222` intentionally leaves a stale index in the bounded commitment queue when a state-machine height's commitment is vetoed. When the vetoed height is the *latest* height, the reset of `LatestStateMachineHeight` re-opens that same height for honest resubmission, which is then inserted with a *second, live* queue entry. The code's own comment documents that the leftover stale entry from the veto later reaches the queue head first and evicts the newly resubmitted, live commitment one insertion earlier than it should be evicted — a classic "reference outlives the object it pointed to, and is later reused against a different live object" bug class, analogous to a use-after-free where a stale handle is dereferenced/acted upon after the underlying resource has been replaced. [1](#0-0) 

### Finding Description
`store_state_machine_commitment` inserts new commitments into a bounded, capacity-limited queue (`BoundedStateCommitments`, tracked via `StateCommitmentQueue`/`CommitmentQueueStates`) that evicts the oldest entry by queue index once the cap is reached. [2](#0-1) 

`delete_state_commitment` removes the `BoundedStateCommitments` and `BoundedStateMachineUpdateTime` entries for a vetoed height, and if that height was the current latest, resets `LatestStateMachineHeight` back to the previous height — but it deliberately does **not** locate and remove the height's stale entry from the queue index, because doing so would require a per-insert `height -> index` map: [1](#0-0) 

The pallet's own test suite pins the consequence: vetoing a non-latest height is a harmless no-op eviction later, but vetoing the *latest* height and then resubmitting it creates two queue entries pointing at the same height — the stale (veto-era) entry and the live (resubmission) entry. When the queue's rolling eviction reaches the stale entry first, it deletes the **live** commitment for that height, one insertion earlier than the cap should allow: [3](#0-2) 

This is functionally a stale-reference-reuse bug: the queue index recorded at veto time is a "freed" reference to state that no longer describes the resubmitted commitment, yet it is later "dereferenced" (used to drive an eviction) as if it still corresponded to the original, now-replaced object, destroying the live one instead.

### Impact Explanation
A state-machine commitment that relayers and applications depend on for proof verification (`EvmHost.stateMachineCommitment` / `HandlerV2.handlePostRequests`, `handleGetResponses`, timeout handlers) can be deleted prematurely and unexpectedly relative to the configured retention cap. [4](#0-3) 
Any pending POST request, GET response, or timeout message whose merkle proof is anchored to that specific height becomes undeliverable once the commitment is gone (`StateCommitmentNotFound`), since the queue's normal cap-based retention was bypassed one slot early and the height cannot be recovered without resubmitting a fresh consensus update for a higher height. This matches the "route unable to deliver messages" / "unsound state commitment" impact classes, since retention guarantees the protocol relies on for message delivery windows are silently violated.

### Likelihood Explanation
Triggering this requires (a) a valid veto of a state-machine commitment (the fraud/veto path reachable via the fishermen mechanism, `modules/pallets/fishermen/src/lib.rs`) landing on the *latest* height, and (b) an honest resubmission of that same height afterward, and (c) enough subsequent commitments to advance the queue head to the stale entry. This is a narrow, specific sequence rather than something exploitable in a single transaction, and the code comment and paired tests indicate the maintainers are aware of and have accepted this as a low-cost, bounded "wart" (burns one queue slot, retains one fewer commitment than the cap) rather than an unbounded or silently-invisible failure.

### Recommendation
Track a `height -> queue index` mapping (or invalidate/overwrite the stale index) at veto time so that a resubmitted height's live entry cannot be shadowed by its own stale predecessor, or explicitly skip eviction when the entry at the queue head no longer matches the live commitment for that height (compare the stored value before removing).

	fn delete_state_commitment(&self, height: StateMachineHeight) -> Result<(), Error> {
		// The height's entry in the state commitment queue is deliberately left
		// behind; locating it would mean scanning the queue, which is the per-insert
		// cost the queue exists to avoid. Usually its eviction is a no-op, but when
		// the vetoed height is the latest the reset below re-opens it for honest
		// resubmission, and the resubmitted height gets a *second* queue entry. The
		// stale entry then evicts the live commitment when it reaches the head —
		// one insertion before the live entry would have, since the resubmission
		// lands directly behind its stale twin. So a veto costs that height one
		// insertion of retention and permanently burns one queue slot. Both are
		// negligible against the configured caps; making it exact would need a
		// height -> index map on the insert path.
		BoundedStateCommitments::<T>::remove(height.id, height.height);
		BoundedStateMachineUpdateTime::<T>::remove(height.id, height.height);

		// technically any state commitment can be vetoed,
		// safety check that it's the latest before resetting it.
		if let Some(latest) = LatestStateMachineHeight::<T>::get(height.id) {
			if latest == height.height {
				// Reset back to the initial height to allow for honest updates
				let prev_height =
					PreviousStateMachineHeight::<T>::get(height.id).ok_or_else(|| {
						Error::Custom("Previous state machine height should exist".to_string())
					})?;
				LatestStateMachineHeight::<T>::insert(height.id, prev_height);
			}
		}
		Ok(())
	}

// Vetoing the *latest* height resets the latest pointer, which re-opens that height
// for honest resubmission. The resubmission gets a second queue entry, and the stale
// twin ahead of it evicts the live commitment one insertion early. This pins that
// wart: it costs the height one insertion of retention and burns one queue slot,
// which is negligible against the configured caps but is not a no-op.
#[test]
fn vetoed_latest_height_that_is_resubmitted_evicts_one_insertion_early() {
	let mut ext = new_test_ext();
	ext.execute_with(|| {
		let host = Ismp::default();
		let id = queue_test_state_machine();
		let store = |height: u64| {
			host.store_state_machine_commitment(
				StateMachineHeight { id, height },
				queue_test_commitment(),
			)
			.unwrap();
			host.store_latest_commitment_height(StateMachineHeight { id, height }).unwrap();
		};

		pallet_ismp::Pallet::<Test>::update_commitment_caps(
			RuntimeOrigin::root(),
			BTreeMap::from([(id, 2)]),
		)
		.unwrap();

		store(10);
		store(11);

		// Vetoing the latest height rolls the latest pointer back to 10, so the
		// consensus handler would accept 11 again: it is not below the latest and
		// its commitment is now absent.
		host.delete_state_commitment(StateMachineHeight { id, height: 11 }).unwrap();
		assert_eq!(host.latest_commitment_height(id).unwrap(), 10);

		store(11);
		assert!(host.state_machine_commitment(StateMachineHeight { id, height: 11 }).is_ok());
		// Two queue entries now point at height 11: the stale one and the live one.
		assert_eq!(StateCommitmentQueue::<Test>::get(id, 1), Some(11));
		assert_eq!(StateCommitmentQueue::<Test>::get(id, 2), Some(11));

		// Evicting the stale entry at index 1 deletes the live commitment for 11,
		// one insertion before the entry at index 2 would have.
		store(12);
		assert!(host.state_machine_commitment(StateMachineHeight { id, height: 11 }).is_err());
		assert!(host.state_machine_commitment(StateMachineHeight { id, height: 12 }).is_ok());
		// The queue still counts index 2 as live, so the burnt slot leaves this
		// chain retaining one fewer commitment than its cap of 2.
		assert_eq!(
			CommitmentQueueStates::<Test>::get(id),
			CommitmentQueueState { head: 2, tail: 4 }
		);
		assert_eq!(StateCommitmentQueue::<Test>::get(id, 2), Some(11));
	})
}
