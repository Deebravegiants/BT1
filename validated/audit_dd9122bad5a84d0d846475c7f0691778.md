### Title
Emporium "Min" proving path lets an unprivileged caller execute unsigned, unaccounted-for external calls from the Emporium contract's identity - (File: `contracts/CircomDataBuilder.sol`, `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`, `contracts/Hinkal.sol`)

### Summary
When `externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `erc20TokenAddresses.length == 0`, `formInputForCircom` routes to `formInputEmporiumMin`, which only proves `message == Poseidon(messageSeed)` plus opaque `timeStamp`/`calldataHash` passthroughs [1](#0-0) . This lets an attacker submit an `EmporiumStack` with `signerAddress == address(0)`, which skips all EIP-712 signature verification of the operations in `verifyWallet` [2](#0-1)  and runs `op.endpoint.call{value: op.value}(op.callData)` directly with `msg.sender == Emporium` [3](#0-2) , while both the balance-accounting loops in `EmporiumUpgradeable.runAction` and `Hinkal.transact` iterate over the (attacker-chosen) empty `erc20TokenAddresses` array, so any value movement performed by the call is never measured or constrained.

### Finding Description
The invariant that should hold is:

`value actually moved by ops executed as Emporium == Σ balanceChange measured over circomData.erc20TokenAddresses (both in EmporiumUpgradeable.runAction and in Hinkal.transact)`.

The attacker breaks this by choosing `erc20TokenAddresses.length == 0`, which is exactly the condition `formInputForCircom` uses to select the minimal proving path:

```solidity
if (circomData.externalActionData.externalActionId == HINKAL_EMPORIUM_ACTION_ID &&
    circomData.erc20TokenAddresses.length == 0) {
    return formInputEmporiumMin(circomData);
}
``` [4](#0-3) 

`formInputEmporiumMin` only emits three public signals: `emporiumMessage`, `timeStamp`, `calldataHash` [5](#0-4) . It proves nothing about `stack.ops`, `stack.signerAddress`, `amountChanges`, nullifiers or roots — none of the normal-path constraints (`getSignedMessageHash`, `formBasicInput`) are exercised [6](#0-5) .

Reaching `Hinkal.transact` with this configuration flows into `_externalTransact`, which only checks that the registered `externalAddress` for `HINKAL_EMPORIUM_ACTION_ID` matches — it places no constraint on the contents of `externalActionMetadata` (the `EmporiumStack`) [7](#0-6) . That metadata is decoded inside `EmporiumUpgradeable.runAction`:

```solidity
EmporiumStack memory stack = abi.decode(circomData.externalActionData.externalActionMetadata, (EmporiumStack));
``` [8](#0-7) 

`verifyWallet` skips signature validation entirely when `stack.signerAddress == address(0)`:
```solidity
if (stack.signerAddress == address(0)) { return; }
``` [9](#0-8) 

The loop over `stack.ops` then executes the "stateless" branch, calling `op.endpoint.call{value: op.value}(op.callData)` with `msg.sender == Emporium contract` [3](#0-2) . If any ERC20 token has previously granted a standing approval to the Emporium contract as spender (e.g., left over from a legitimate prior Emporium flow where a victim's tokens were approved to Emporium and not fully consumed), the attacker can encode `op.callData = token.transferFrom(victim, attacker, remainingAllowance)`. Because `msg.sender` of that call is the Emporium contract (the approved spender), the transfer succeeds and funds move from the victim directly to the attacker.

Crucially, the accounting loops that are supposed to catch any unauthorized balance movement are both driven by `circomData.erc20TokenAddresses`, which the attacker deliberately set to length 0 to unlock the Min path:
```solidity
for (uint256 i = 0; i < circomData.erc20TokenAddresses.length; i++) { ... }
```
in `EmporiumUpgradeable.runAction` [10](#0-9) , and the analogous loop in `Hinkal.transact`:
```solidity
for (uint64 i; i < circomData.erc20TokenAddresses.length; i++) { ... balanceDif ... utxoAmount ... }
``` [11](#0-10) 

With `erc20TokenAddresses.length == 0`, both loops iterate zero times: no `balanceDif`, no `utxoAmount`, no slippage check, no UTXO creation, no nullifier obligation tied to the stolen value. The transfer that actually happened via `op.callData` is completely invisible to every invariant that `Hinkal.transact` and `EmporiumUpgradeable.runAction` otherwise enforce.

### Impact Explanation
An unprivileged attacker can direct the Emporium contract (acting with its own `msg.sender` identity) to call arbitrary external contracts and consume any standing ERC20 approvals held by Emporium as spender, or otherwise move value through `op.endpoint.call{value: op.value}(...)`, with zero on-chain accounting. This is a direct theft path: value leaves a victim's balance (or Emporium's own held balance) into an attacker-chosen address, with no UTXO, nullifier, or balance check ever recording it. This matches the Critical category: "direct theft of shielded or in-flight user funds" and additionally "executing calls or moving assets ... never authorised" since `verifyWallet` performs no signature check at all in the `signerAddress == 0` branch. It is repeatable for every standing approval or every value the attacker can otherwise induce Emporium to move, limited only by `usedMessages[emporiumMessage]` (trivially avoided by picking a fresh, self-chosen `emporiumMessage`/`messageSeed` per attack).

### Likelihood Explanation
Preconditions: (1) `HINKAL_EMPORIUM_ACTION_ID` must already be registered against the `EmporiumUpgradeable` address (a normal, expected deployment state, not a privileged action performed by the attacker), and (2) there must exist a standing ERC20 approval (or other exploitable value Emporium can move) where Emporium is the approved spender or otherwise controls transferable value — a state that can arise from ordinary prior Emporium flows. The attacker needs no special role: they self-generate `messageSeed`/`message`, self-craft the `EmporiumStack` bytes, and self-supply an empty `erc20TokenAddresses` array — all fields explicitly listed as attacker-controlled in the rules. Cost is a single transaction; feasibility is high because the Min-path circuit's public inputs are all self-chosen or opaque passthroughs with no cross-field constraint tying `calldataHash` to any operation's authenticity or amount, and `verifyWallet` explicitly disables its only authentication check when `signerAddress == 0`.

### Recommendation
- Do not allow the "stateless" `op.endpoint.call` branch (or any external call at all) when `stack.signerAddress == address(0)` unless the operation set is itself constrained by the circuit (e.g., include a hash of `stack.ops` as a required public input verified in-circuit, not just an opaque `calldataHash`).
- Require `verifyWallet` to always validate an authenticated signer/signature for any op execution, removing the unconditional early return for `signerAddress == address(0)`, or restrict the zero-signer path to a fixed, non-arbitrary, protocol-defined operation (no attacker-supplied `callData`/`endpoint`).
- Ensure the Min proving path cannot be paired with externally callable, attacker-defined `ops`: either force `erc20TokenAddresses.length > 0` (and thus the full accounting loop) whenever `stack.ops` is non-empty, or add explicit circuit constraints binding `calldataHash` to a value that is cryptographically tied to signer authorization of every op.
- Add a Solidity-level invariant check independent of `erc20TokenAddresses.length` that reverts if `stack.ops` performs any external call while no token/balance accounting is configured for the transaction.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, `EmporiumUpgradeable`, register `HINKAL_EMPORIUM_ACTION_ID -> Emporium`.
2. Set up a victim ERC20 token; have the victim `approve(Emporium, X)` (simulating a standing approval left over from legitimate Emporium usage).
3. As an unprivileged attacker EOA, build `CircomData` with:
   - `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`
   - `erc20TokenAddresses = []`
   - `externalActionData.externalActionMetadata = abi.encode(EmporiumStack({signerAddress: address(0), ops: [EmporiumOperation({endpoint: token, invokeWallet: false, value: 0, callData: abi.encodeCall(IERC20.transferFrom, (victim, attacker, X))})], ...}))`
   - self-chosen `emporiumMessage`, matching Min-path circuit proof (`message == Poseidon(messageSeed)`).
4. Call `Hinkal.transact(a, b, c, dimensions, circomData)` from attacker.
5. Assert:
   - `token.balanceOf(attacker)` increases by `X` and `token.balanceOf(victim)` decreases by `X` (LHS of the broken equality: real value moved).
   - No revert occurs from `Hinkal.transact`'s balance-diff/slippage checks (RHS: `balanceDif == 0` since loop never runs) — confirming the equality "assets moved == assets accounted" is violated.
   - No nullifier is inserted and no UTXO commitment is created corresponding to the `X` tokens.
