### Title
FXFiller and UniswapV4FundingPlanner price venue-priced pairs off the manipulable Uniswap V4 pool spot price (`slot0`/`sqrtPriceX96`), with the flash-loan guard optional and non-execution-aware - (File: sdk/packages/simplex/src/strategies/fx.ts, sdk/packages/simplex/src/funding/uniswapV4/UniswapV4FundingPlanner.ts)

### Summary
The Simplex solver's FX strategy prices "curveless" cross-asset pairs using the live Uniswap V4 pool mid-price (`sqrtPriceX96`/tick from `slot0`) as the sole oracle, exactly analogous to the audited `UNI_V3Validator` flaw of trusting `slot0` as a spot price for valuation. The only defense (`checkPriceGuard`) is optional, static, and non-execution-aware, so an unprivileged order placer can flash-loan-manipulate the referenced pool and have the solver fill (or size) an order against the manipulated price.

### Finding Description
`UniswapV4FundingPlanner.getExoticTokenPrice` → `computeDirectPoolPriceUsd` derives a token's USD price directly from `sdkPool.token0Price`/`token1Price`, which is built from the pool's live `sqrtPriceX96` read via `StateView.getSlot0` [1](#0-0) . This is the same primitive the external report flags — an instantaneous AMM spot price, manipulable within a single block via a large swap (e.g., funded by a flash loan) — with no TWAP, no size/impact term, and the pool's own fee tier "read and stored... but never applied to the price" [2](#0-1) .

That price feeds `FXFiller.resolveLegRates` and `referenceRate`, which price and size venue-priced pairs (curve-less pairs whose `token0` is a USD stable) directly off `venueUsdPrice` [3](#0-2) [4](#0-3) . The only mitigation is `checkPriceGuard`, and the project's own tests confirm it is optional: "sizes unguarded when no reference is configured (guard is optional)" [5](#0-4) , and documentation states the guard "checks deviation from a static reference, not execution cost" [6](#0-5) . Even when configured, `referencePrice`/`maxDeviationBps` is a static, operator-set band and does not account for the pool's own liquidity depth or resistance to manipulation — a thin/manipulated pool moved to just inside the configured band still passes [7](#0-6) .

The venue price is also used to fund fills by withdrawing liquidity from the solver's own Uniswap V4 LP positions [8](#0-7) , meaning a manipulated `slot0` at the moment of pricing directly determines both (a) how much output the solver commits to deliver, and (b) how the solver's own LP inventory is valued/withdrawn against that same manipulated price — structurally identical to the reported `LiquidityAmounts.getAmountsForLiquidity` mis-valuation vector, just applied to pricing an intent fill instead of loan collateral.

### Impact Explanation
An intent placer (fully unprivileged — anyone who can submit an order the solver evaluates) can manipulate the referenced Uniswap V4 pool's spot price via a flash-loan-funded swap immediately before/around order evaluation, causing:
- The solver (FXFiller) to compute a favorable-to-attacker `rate` for a venue-priced pair leg, over-delivering the output token relative to fair value, directly draining solver funds on fill (`resolveLegRates`/`computeLegPolicyOutput`).
- Mis-sized USD notional for confirmation-depth/reorg-protection decisions via `referenceRate`, which the code's own comment flags as "the exact attack the guard exists to stop" when unguarded [9](#0-8) .
- Since the guard is optional and, when present, is a static-reference check rather than a manipulation-resistance check, deployments without a configured `referencePrice`/`maxDeviationBps` (or with a wide band, or a thin pool) remain exposed.

This is a concrete theft-of-solver-funds vector reachable from a single submitted intent/order, consistent with the "intents escrow and bids" reachable-surface criteria.

### Likelihood Explanation
Medium: exploitation requires (1) a curve-less, venue-priced pair configured (an opt-in feature, not default), and (2) either no price guard configured or a guard band wide/loose enough (or a pool with insufficient liquidity depth) to tolerate the manipulation needed to move the solver's quoted rate profitably net of flash-loan and swap costs. Given the guard is explicitly optional and non-execution-aware per the project's own docs and tests, operators who enable venue pricing without a tight, liquidity-aware guard are directly exposed, and the attack requires only a single transaction/flash loan plus an intent submission — no privileged access.

### Recommendation
- Do not rely on instantaneous `slot0`/`sqrtPriceX96` as a sole price source for venue pricing; use a TWAP over a sufficiently long window, or cross-check against an independent oracle (e.g., Chainlink), before deriving `venueUsdPrice`.
- Make the price guard mandatory (not optional) for any curve-less/venue-priced pair, and extend it beyond a static-reference deviation check to also account for pool liquidity depth/expected price impact of a bounded attacker-sized swap, rejecting quotes from pools too thin to resist manipulation within the configured deviation band.
- Apply the pool's fee tier to the derived price and add a size/impact term so a single-block manipulated tick cannot be linearly extended across the whole priced quantity (`computeLegPolicyOutput`).
- Document this risk explicitly for operators enabling `[vault.uniswapV4]` pool-based pricing, per the recommendation in the source report to document the risk when a manipulable spot-price valuator is used.

### Proof of Concept
1. Operator configures a curve-less pair, e.g. `USDC/CNGN`, with `[vault.uniswapV4]` positions and no `referencePrice`/`maxDeviationBps` (guard "unguarded", as covered by the project's own test) [5](#0-4) .
2. Attacker takes a flash loan and executes a large swap against the configured Uniswap V4 pool (`token0`=USDC/token1=CNGN) to push `slot0.sqrtPriceX96` far from fair value in the direction that makes CNGN look cheap in USD terms.
3. Attacker (or a colluding relayer) immediately submits/bids on an intent order swapping USDC→CNGN sized to this pair; `FXFiller.calculateProfitability` → `resolveLegRates` → `getVenueUsdPrice` → `UniswapV4FundingPlanner.getExoticTokenPrice`/`computeDirectPoolPriceUsd` reads the manipulated `slot0` [10](#0-9) [11](#0-10) .
4. The solver computes an output amount favorable to the attacker and fills the order, funding it in part by withdrawing from its own manipulated-price-valued LP position.
5. Attacker reverses the swap, repays the flash loan, and keeps the surplus value extracted from the solver — the same "manipulate spot price → get overvalued/undervalued position accepted → restore price → profit" pattern described in the source report, applied to intent-fill pricing rather than loan collateral valuation.

	async getExoticTokenPrice(chain: string, exoticToken: string): Promise<Decimal | null> {
		const state = this.stateByChain.get(chain)
		if (!state || !state.isHydrated()) return null

		try {
			await state.refresh()
		} catch (err) {
			this.logger.error({ err, chain }, "Failed to refresh state for price query")
			return null
		}

		const tokenLower = exoticToken.toLowerCase()
		let bestPrice: Decimal | null = null
		let bestLiquidity = 0n

		for (const pos of state.allPositions()) {
			if (pos.currency0.toLowerCase() !== tokenLower && pos.currency1.toLowerCase() !== tokenLower) continue
			const sdkPool = state.getSdkPool(pos.tokenId)
			if (!sdkPool) continue

			const result = this.computeDirectPoolPriceUsd(pos, sdkPool, chain)
			if (result && result.exoticToken.toLowerCase() === tokenLower) {
				const poolLiquidity = state.getPoolLiquidity(pos.tokenId)
				if (poolLiquidity > bestLiquidity) {
					bestPrice = result.priceUsd
					bestLiquidity = poolLiquidity
				}
			}
		}

		if (bestPrice) {
			this.logger.debug({ chain, token: tokenLower, priceUsd: bestPrice.toString() }, "Exotic token price computed")
		}
		return bestPrice
	}

	private async getVenueUsdPrice(chain: string, token1Address: string): Promise<Decimal | null> {
		if (this.fundingVenues.length === 0) return null

		// Prefer V4, fall back to others
		const v4 = this.fundingVenues.filter((v) => v.name === "UniswapV4")
		const venues = v4.length > 0 ? v4 : this.fundingVenues

		for (const venue of venues) {
			const usdPrice = await venue.getExoticTokenPrice(chain, token1Address)
			if (usdPrice?.isPositive()) return usdPrice
		}
		return null
	}

	private async referenceRate(
		leg: ResolvedLeg,
		venueUsdPrice: (chain: string, token1Address: string) => Promise<Decimal | null>,
	): Promise<Decimal | null> {
		const policy = leg.pair.bidPricePolicy ?? leg.pair.askPricePolicy
		if (policy) {
			const rate = policy.getPrice(new Decimal(0))
			return rate.gt(0) ? rate : null
		}
		// Venue-priced pair: token0 is USD-stable (constructor invariant), so the
		// venue's USD-per-token1 quote inverts straight into token1-per-token0.
		const venueUsd = await venueUsdPrice(leg.token1Chain, leg.token1Address)
		if (!venueUsd) return null
		const venueRate = new Decimal(1).div(venueUsd)
		// Same guard as trade pricing: this rate sizes the order's USD notional
		// for confirmation depth, and a manipulated pool understating the value
		// would shrink the reorg protection — the exact attack the guard exists
		// to stop. Refusing to size skips the order, consistent with pricing.
		if (!this.checkPriceGuard(undefined, leg.token1Chain, venueRate)) return null
		return venueRate
	}

	private async resolveLegRates(
		orderId: string | undefined,
		leg: ResolvedLeg,
		cappedPairNotional: Decimal,
		venueUsdPrice: (chain: string, token1Address: string) => Promise<Decimal | null>,
	): Promise<LegRates | null> {
		// Explicitly configured curves always win — the venue only prices pairs
		// with no curves at all (and never same-token pairs, where a venue quote
		// would just be the asset's own USD price, not a spread).
		const curveless = !leg.pair.bidPricePolicy && !leg.pair.askPricePolicy
		if (curveless && !isSameTokenPair(leg.pair) && USD_STABLE_SYMBOLS.has(normalizeSymbol(leg.pair.token0))) {
			const venueUsd = await venueUsdPrice(leg.token1Chain, leg.token1Address)
			if (venueUsd) {
				// Guard compares the venue's token1-per-USD quote against the static reference.
				if (!this.checkPriceGuard(orderId, leg.token1Chain, new Decimal(1).div(venueUsd))) {
					return null
				}
				// A pool mid is ONE price, not a book: there is no opposite side
				// to report a round-trip margin against. The price guard above is
				// the venue-specific defense.
				const venueRate = new Decimal(1).div(venueUsd)
				return { rate: venueRate, oppositeRate: null, priceSource: "venue" }
			}
		}

## Uniswap price guards

Pool-based pricing trusts the live pool, which leaves the solver exposed to a manipulated, stale, or thin pool returning a bad quote. To bound that risk, give a position a **`referencePrice`** and **`maxDeviationBps`**. Whenever the pool quote on that chain drifts more than `maxDeviationBps` above or below the reference, the solver refuses to fill — the order is rejected before any bid is submitted.

`referencePrice` is expressed in **exotic tokens per USD**, the same units as the bid/ask curves. The two fields must be set together; omit both to leave the chain unguarded.

```toml lineNumbers
[vault.uniswapV4]
# referencePrice is the expected cNGN per USD;
# reject if the quote is more than 2% off.
# The two go together — one without the other is rejected.
[[vault.uniswapV4.positions]]
chain           = "EVM-8453"
tokenId         = "2087350"
referencePrice  = "1575"
maxDeviationBps = 200
```
