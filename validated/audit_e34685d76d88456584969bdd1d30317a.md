### Title
Webhook `shop`, `topic`, and `webhook_id` fields are trusted from unauthenticated headers while HMAC only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC computed over the raw HTTP body against the app's shared `api_secret_key`. The `shop-domain`, `topic`, `webhook-id`, and `api-version` values — which are taken from HTTP headers and then handed to the app's webhook handler as the tenant/topic identity — are never included in the signed material, so they are not bound to the signature at all.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors instead read directly from caller-supplied headers with no cryptographic binding: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string` (i.e., the raw body) using the app-wide `Context.api_secret_key`, which is the same secret for every shop that has installed the app: [3](#0-2) 

`Registry.process` uses this same HMAC check as its only authentication gate, then dispatches to the app's handler using the unverified header-derived `shop`, `topic`, and `webhook_id`: [4](#0-3) [5](#0-4) 

Because the shared secret is identical for all shops of the app, and the signature is computed only over the body, `HMAC(secret, body)` is a valid signature for *any* combination of shop/topic/webhook_id headers accompanying that same body. This breaks the identity binding that a webhook consumer must rely on:

`(shop header, topic header claimed to the handler) == (shop, topic that actually generated and owns this signed body)`

An unprivileged internet user who is a legitimate merchant of the app (any user can install a public Shopify app on their own store) can trigger a real webhook delivery to capture a valid `(raw_body, hmac)` pair signed with the app's secret for their own shop. They can then replay that exact body and HMAC to the app's webhook endpoint while forging the `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) header to name a victim shop. `Utils::HmacValidator.validate` will still pass, because it never looks at these headers, and `Registry.process` will invoke the handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain.

### Impact Explanation
If the host application's webhook handler trusts `WebhookMetadata#shop` to look up per-tenant session/access-token data or to key any per-merchant state (a documented and expected usage pattern for `ShopifyAPI::Webhooks::Registry.process`), an attacker can cause the handler to act on/associate captured data with an arbitrary victim shop, i.e. cross-tenant confusion driven entirely by a request that this gem itself certified as "verified" via HMAC. This matches the Critical "cross-tenant access" impact category since the trust boundary broken is inside this gem's own webhook authentication primitive, not a host-application bug — the gem's `process` method is the one asserting authenticity of the `shop` field it hands to the caller.

### Likelihood Explanation
Exploitation requires only: (1) the attacker being able to install the target app on a shop they control (any Shopify app installable via a normal OAuth flow satisfies "unprivileged internet user"), (2) capturing one webhook delivery's raw body + HMAC header for their own shop (trivial, since it's delivered to their own configured endpoint or can be intercepted at their own infrastructure), and (3) replaying it against the shared webhook endpoint with a forged shop-domain header. No access token, `client_secret`, or privileged credential is needed. Likelihood is Medium-High for any app relying on `data.shop` from `Registry.process` without an independent registration/verification step.

### Recommendation
Include the `shop-domain`, `topic`, and (optionally) `webhook-id` header values in the signable string used for webhook HMAC validation, or otherwise cryptographically bind them (e.g., per-shop signing key, or cross-checking `shop` against a previously-registered webhook subscription id/shop pairing) before handing the data to `WebhookHandler#handle`. At minimum, document explicitly that `WebhookMetadata#shop`/`topic` are unauthenticated and must not be trusted for tenant identification without an additional server-side check.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and registers a webhook (e.g. `orders/create`).
2. Shopify delivers a webhook to the app's endpoint with body `B` and header `x-shopify-hmac-sha256: HMAC(secret, B)`, `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker captures `B` and the HMAC value (their own delivery, no interception required).
4. Attacker POSTs the same `B` and same `x-shopify-hmac-sha256` value to the app's webhook endpoint again, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` computes `Utils::HmacValidator.validate(request)` using only `raw_body`; it succeeds because the body and secret are unchanged.
6. The app's handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: ..., body: B, ...)` — a spoofed shop identity that this gem asserted as "verified" via `process`.

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
