### Title
Webhook `shop` (tenant) identity is not covered by the HMAC signature, enabling cross-tenant spoofing via replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC signature verified by `Utils::HmacValidator.validate` proves nothing about the `shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`, or `shopify-api-version` headers. `Registry.process` passes `request.shop` (an unauthenticated header) straight into the `WebhookMetadata` object that the host app's handler uses to attribute the webhook to a tenant.

### Finding Description
`Utils::HmacValidator.validate` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it against the `hmac` accessor of the object implementing `Utils::VerifiableQuery`. For webhooks, `to_signable_string` is defined as:

```ruby
def to_signable_string
  @raw_body
end
``` [4](#0-3) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are pulled directly from HTTP headers with no cryptographic tie to the body or to each other:

```ruby
def shop
  T.cast(shopify_header("shop-domain"), String)
end
``` [5](#0-4) 

`Registry.process` validates only the HMAC-over-body, then forwards the unauthenticated `shop` header as the tenant identity to the app's handler:

```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
``` [2](#0-1) 

The identity binding that should hold is: `HMAC-verified bytes == bytes the handler trusts as belonging to shop X`. Here the equality is broken: the HMAC only certifies the body bytes; the `shop` (and `topic`/`webhook_id`) that the handler treats as authoritative are unauthenticated header values that can differ from whatever shop actually produced/authorized that body. Because the app's `api_secret_key` (`client_secret`) is shared across *all* shops that have installed the app, any tenant that legitimately receives a genuine webhook (with a valid HMAC over a body it can influence, e.g. via a customer-supplied order note or product field) can capture that valid `(body, hmac)` pair and replay it to the app's public webhook endpoint with the `shopify-shop-domain` header changed to a victim shop. `HmacValidator.validate` will still return `true`, because the signature was never bound to the shop domain, topic, or webhook id.

### Impact Explanation
This crosses the tenant boundary documented in the rules ("a field acted on but not covered by the HMAC"): the handler receives `data.shop` as trustworthy per the gem's own documentation (`docs/usage/webhooks.md:12-17`), and downstream apps use it directly to select the tenant record to update (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)` in the gem's own documented example, `docs/usage/webhooks.md:26`). An attacker who controls one installed shop can forge webhook deliveries attributed to a different shop, causing cross-tenant data injection/corruption in any host application that trusts `data.shop` for record attribution — this is a cross-tenant access impact.

### Likelihood Explanation
Exploitation requires only: (1) the attacker's own shop has the app installed and receives a genuine webhook whose body content the attacker can influence (common for topics like `orders/create`, `products/update` where fields like `note`, `title`, etc. are attacker-controlled), and (2) network access to POST to the app's public webhook endpoint, which by design must be internet-reachable to receive Shopify's callbacks. No access token, `client_secret`, or privileged access is needed — only the HMAC and body captured from a legitimate webhook to their own shop.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the HMAC-signed material (or otherwise cryptographically bind them to the request, e.g. verify them against Shopify's IP ranges and pin `shop` through a webhook-subscription lookup keyed by `webhook_id` rather than trusting the header directly). At minimum, document prominently that `data.shop` from `WebhookMetadata` is not authenticated by the HMAC and must not be used alone to select the tenant record without additional verification (e.g. cross-checking against a locally stored mapping of `webhook_id -> shop` established at subscription time).

### Proof of Concept
1. App installs on `attacker-shop.myshopify.com` and registers an `orders/create` webhook handler that does `Order.find_by(shop: data.shop).update(notes: data.body["note"])`.
2. Attacker places a real order on their own shop with `note` containing a malicious payload; Shopify delivers a webhook to the app with a valid `x-shopify-hmac-sha256` computed over the real body and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker intercepts/replays this exact `(raw_body, hmac)` pair to the same webhook endpoint but with the header changed to `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:12-22`) succeeds because it only checks `raw_body` against the HMAC; `Registry.process` calls the handler with `shop: "victim-shop.myshopify.com"` and the attacker-controlled body, causing the host app to write attacker-controlled data against the victim tenant.
