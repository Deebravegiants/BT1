### Title
Webhook shop-domain identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Registry.process` is documented to "verify the request did indeed come from Shopify" before invoking the app's webhook handler, but the HMAC check only authenticates the request body — it never authenticates the `shop` value that the handler receives and trusts as the tenant identity.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `HmacValidator.validate` computes/compares the HMAC solely over that signable string [2](#0-1) . The `shop` accessor, however, is read straight from the `shop-domain` header without any cryptographic binding to the signed body [3](#0-2) .

`Registry.process` validates only the HMAC and then forwards `request.shop` unchanged into `WebhookMetadata`, which the app's handler treats as the authoritative tenant/shop identity: [4](#0-3) 

Because the HMAC secret is the app's single `Context.api_secret_key`, shared across every shop that has installed the app (not a per-shop secret), any unprivileged user can install the app on their own store, trigger an event to receive a validly-signed webhook body+HMAC pair for content they control, and then replay that exact `(raw_body, hmac)` pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (or `shopify-shop-domain`) header with a victim shop's domain. `HmacValidator.validate` will still pass because it never inspects the header, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the (attacker-controlled) body originated from the victim shop.

The equality that should hold is:
`shop authenticated by HMAC == shop trusted by the handler as WebhookMetadata#shop`
but in this implementation:
`shop covered by HMAC == ∅` (only the body is signed) while `shop trusted by the handler == request header value`.

The gem's own documentation reinforces the false sense of security by asserting the call "will verify the request did indeed come from Shopify," without qualifying that the shop identity itself is unverified: [5](#0-4) 

### Impact Explanation
This enables cross-tenant confusion/spoofing: an attacker who legitimately installs the target app on their own store can forge webhook deliveries that the host application will process as if they came from an arbitrary other shop domain, with attacker-controlled body content. Any downstream logic that keys off `data.shop` (e.g., looking up the corresponding merchant session, updating per-shop records, billing, or fulfillment automation) can be manipulated to act on/against a different tenant, which falls under the "cross-tenant access" Critical-impact category.

### Likelihood Explanation
Likelihood is meaningful but not trivial: exploitation requires (1) the ability to install the target app on the attacker's own shop to obtain at least one legitimately signed `(body, hmac)` pair, and (2) an app handler whose logic is influenced by the `shop` field of `WebhookMetadata` rather than independently verified via a stored session lookup keyed by other data. Because installing a public Shopify app is available to any unprivileged internet user, and the gem's documentation actively encourages trusting `data.shop`, this is realistically reachable.

### Recommendation
`ShopifyAPI::Webhooks::Request#to_signable_string`/`HmacValidator` should bind the `shop` domain (and ideally `topic`) into the value that is HMAC-verified, or `Registry.process` should require the caller to supply/verify the expected shop out-of-band (e.g., against the shop associated with the resolved webhook topic/session) before trusting `request.shop`. At minimum, the documentation should be corrected to state that only the body is authenticated by HMAC, and that the `shop` header must be independently validated by the host application against a known/installed shop before use.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`.
2. Attacker triggers a webhook event (e.g., `products/update`) with a crafted body/payload of their choosing.
3. Attacker's app endpoint (or a network capture) records the legitimate `(raw_body, x-shopify-hmac-sha256)` pair Shopify sent, valid under the shared app `client_secret`.
4. Attacker POSTs the exact same `raw_body` and `x-shopify-hmac-sha256` header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `HmacValidator.validate` succeeds (only body is checked) [6](#0-5) , and `Registry.process` invokes the handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: <attacker-controlled>)` [4](#0-3) , causing the host app to act on attacker-controlled data attributed to the victim shop.
