### Title
Webhook HMAC only covers the request body, allowing `shop`/`topic`/`webhook_id` header spoofing for cross-tenant webhook injection - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `ShopifyAPI::Webhooks::Registry.process` trusts `request.shop`, `request.topic`, and `request.webhook_id` — all derived from unauthenticated HTTP headers — after validating only that the body's HMAC is correct. Since Shopify's HMAC for a given webhook body is identical regardless of which shop or topic it's delivered for, any holder of one valid (body, HMAC) pair (trivially obtainable by installing the app on their own store) can replay it with forged shop/topic headers to impersonate another tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`: [1](#0-0) 

`to_signable_string` returns `@raw_body` exclusively — it does not include `shop`, `topic`, `webhook_id`, or `api_version`, all of which are read straight from client-controlled headers: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC purely over `to_signable_string`, i.e. the body: [3](#0-2) 

`Registry.process` treats a passing HMAC check as proof the entire request, including `shop`, is legitimate, then forwards `request.shop` and `request.topic` unchanged to the app's handler: [4](#0-3) 

The identity binding that should hold is:
`shop authenticated by HMAC == shop delivered to the handler`

But the actual binding is:
`bytes verified by HMAC (raw_body only) != shop/topic/webhook_id parsed from headers`

Because the HMAC key (`api_secret_key`) is shared across all shops using the app, and many webhook topics have constant or attacker-influenceable bodies (e.g. `app/uninstalled`, `shop/redact`, or any webhook the attacker's own store receives), an attacker who installs the target app on their own store can legitimately receive a webhook with a valid `(raw_body, hmac)` pair, then resend that exact body and HMAC to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` (and optionally `x-shopify-topic`) header for a victim shop. The docs describe `Registry.process` as verifying "the request did indeed come from Shopify," which is misleading: only body integrity is verified, not the sender's claimed identity.

### Impact Explanation
This breaks the tenant isolation the library implies it provides. An attacker can trigger handlers for a victim shop they don't control — e.g. spoofing `app/uninstalled` or `shop/redact` to make the host app delete the victim shop's stored session, access token, or customer data, or spoofing any other business-logic webhook keyed by `data.shop`. This is a cross-tenant attack achievable without ever knowing `api_secret_key`, matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Any external user can trivially install the target app on their own shop (most apps are installable by any merchant) and capture a legitimate webhook body/HMAC pair for a topic whose body is constant or shop-independent. No secrets, tokens, or privileged access are required — only the ability to install the app and send an HTTP request with forged headers to the app's public webhook route.

### Recommendation
Include the identity-bearing fields (`shop`, `topic`, `webhook_id`, `api_version`) in the signable string used for HMAC verification, or otherwise cryptographically bind the header values to the signed payload, so that `Registry.process` can guarantee the claimed `shop`/`topic` match what Shopify actually signed. At minimum, update the documentation to make clear that `data.shop` is not authenticated and must be independently verified by the host application against the shop's known installation state.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com`.
2. Shopify delivers a webhook (e.g. `app/uninstalled`) to the app's webhook endpoint with body `"{}"` and a valid `x-shopify-hmac-sha256` computed by Shopify using the app's `api_secret_key`.
3. Attacker records this `(raw_body="{}", hmac=H)` pair.
4. Attacker sends a new HTTP request to the same webhook endpoint with:
   - `x-shopify-hmac-sha256: H`
   - `x-shopify-topic: app/uninstalled`
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - body `"{}"`
5. `Utils::HmacValidator.validate` succeeds because it only checks `raw_body` against `H`.
6. `Registry.process` invokes the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: "app/uninstalled", ...)`, causing the app to perform uninstall cleanup (e.g., delete stored access token/session) for a shop the attacker never installed the app on nor has any relationship with.
