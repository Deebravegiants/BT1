## Title
ERC-721 tokens escrowed via `IntentGatewayV2.placeOrder` can be permanently locked because `safeTransferFrom` accepts ERC-721 transfers but the refund/fill/delivery paths use `safeTransfer` (`ERC20.transfer`), which ERC-721 does not implement - (File: `evm/src/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2.placeOrder` collects order inputs with `IERC20(token).safeTransferFrom(msg.sender, address(this), amount)` without any check that `token` is actually a fungible ERC-20. Because `ERC721.transferFrom(address,address,uint256)` has the exact same function selector as `ERC20.transferFrom(address,address,uint256)`, an ERC-721 contract satisfies this call (with `amount` interpreted as a `tokenId`) and the NFT is pulled into the gateway's escrow successfully. The gateway later moves escrowed tokens back out — on fill, refund/cancel, or dust sweep — using `IERC20.safeTransfer(...)`, which calls the ERC-20-only `transfer(address,uint256)` selector. ERC-721 does not implement `transfer`, so this call always reverts, permanently locking the NFT in the contract with no path to recovery for the user.

### Finding Description

There is no validation (e.g. `decimals()`/ERC165 check) that `order.inputs[i].token` is a genuine ERC-20 contract before calling `safeTransferFrom`. Since `transferFrom(address,address,uint256)` is a shared selector between ERC-20 and ERC-721, an attacker or a naive user can supply an ERC-721 contract address as the input `token` and its own token id as `amount`; `safeTransferFrom` succeeds (the NFT's `transferFrom` runs and moves the NFT into the gateway), and the escrow accounting (`_orders[commitment][token] = amount`) treats it as a normal fungible balance: [2](#0-1) 

The same unguarded pattern with the same selector-collision risk is repeated for `predispatch` assets: [3](#0-2) 

Once escrowed, every exit path for that "amount" (order cancellation/refund, fill settlement, dust sweep) is implemented with `SafeERC20.safeTransfer`, which dispatches the ERC-20-only `transfer(address,uint256)` selector — a function ERC-721 tokens do not expose. Grepping the intents module confirms `safeTransfer(...)` is the exclusive outbound-payment primitive used across the intents codebase (`IntentsBase.sol`, `ExtrinsicIntents.sol`, `IntrinsicIntents.sol`) alongside the `safeTransferFrom` inbound calls in `IntentGatewayV2.sol`. Any outbound leg touching the locked "token" (refund on `cancelOrder`, payout on `fillOrder`, or `SweepDust`) reverts unconditionally, so the ERC-721 can never leave the contract. There is no owner/governance sweep function found in this contract to rescue an arbitrary non-fungible asset, so recovery would require a contract upgrade — an even weaker guarantee than Linea's own "upgrade only" caveat, since `IntentGatewayV2` is deployed at deterministic CREATE2 addresses across many chains and any upgrade must be coordinated per-chain.

This is a direct structural analog of the reported Linea `TokenBridge` bug: an inbound function whose selector is inadvertently ERC-721-compatible (`safeTransferFrom`/`transferFrom`) admits the asset, while the outbound function (`safeTransfer`/`transfer`) is ERC-20-only and reverts, permanently freezing the asset.

### Impact Explanation
Any unprivileged user who calls `placeOrder` with an ERC-721 contract as an input token (deliberately or by mistake, e.g., copy-pasting an address) has their NFT irreversibly locked in the `IntentGatewayV2` proxy: it can never be filled (fill payout uses `safeTransfer`), never cancelled/refunded (refund uses `safeTransfer`), and cannot be swept by governance without a contract upgrade. This is a permanent freezing of user funds (the NFT), matching the "permanent freezing of funds" acceptance criterion.

### Likelihood Explanation
Reachable by any user via a single, ordinary `placeOrder` transaction — no privileged role, no cross-chain proof, no relayer collusion required. The selector collision between `ERC20.transferFrom` and `ERC721.transferFrom` is a well-known Solidity gotcha (identical to the root cause acknowledged by the Linea team), and nothing in `IntentGatewayV2` checks token type before escrowing. Likelihood is Medium-to-High: it requires a user (attacker griefing themselves, or a UI bug/attacker tricking a victim into submitting an NFT address) to submit an ERC-721 as an order input, but the contract provides zero defense against it.

### Recommendation
Before accepting a `token` into escrow in `placeOrder` (and the `predispatch` asset loop), verify it is a genuine ERC-20: e.g., require a successful staticcall to `decimals()` (reverting otherwise, mirroring Linea's proposed fix) and/or explicitly reject contracts that implement `IERC721`/`ERC165.supportsInterface(0x80ac58cd)`. Additionally, add an owner/governance-gated emergency sweep for arbitrary tokens/NFTs stuck in escrow so a future mis-escrowed asset (of any kind) is recoverable without a full contract upgrade.

### Proof of Concept
1. Deploy or use any standard ERC-721 contract; mint token id `T` to `attacker`.
2. `attacker` approves `IntentGatewayV2` for token id `T` (`approve(gateway, T)`).
3. `attacker` calls `placeOrder(order, graffiti)` with `order.inputs[0].token = <erc721Address>` and `order.inputs[0].amount = T`.
4. `IERC20(erc721).safeTransferFrom(attacker, address(this), T)` succeeds because `ERC721.transferFrom(address,address,uint256)` matches the called selector, and `T` (the tokenId) is now escrowed as `_orders[commitment][erc721Address] = T`.
5. `attacker` (or anyone) calls `cancelOrder`/awaits `fillOrder` to trigger payout; the refund/fill code path calls `IERC20(erc721).safeTransfer(beneficiary, T)`, which reverts because `ERC721` has no `transfer(address,uint256)` function — permanently freezing the NFT with id `T` inside `IntentGatewayV2`.
