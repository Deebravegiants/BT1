### Title
Unvalidated `shop` parameter in `Oauth.begin_auth` enables SSRF-like redirection of OAuth flow to attacker-controlled host - (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
`ShopifyAPI::Auth::ClientCredentials.client_credentials` and `ShopifyAPI::Auth::RefreshToken.refresh_access_token` both validate the caller-supplied `shop` string with `Utils::ShopValidator.sanitize!` before using it to construct the HTTP client that sends `client_id`/`client_secret` to derive an access token [1](#0-0) [2](#0-1) . `Oauth.begin_auth`, by contrast, takes the same kind of `shop:` string but never sanitizes it, feeding it straight into `auth_base_uri(shop)`, which builds `"https://#{shop}/admin"` [3](#0-2) , and then issues (or instructs the host app to issue) the OAuth `/oauth/authorize` redirect to that host, together with the app's `client_id` and `redirect_uri` [4](#0-3) .

### Finding Description
The intended invariant, established by the sibling flows, is: `shop` (== identity of the merchant tenant) must equal a value validated against `Utils::ShopValidator::TRUSTED_SHOPIFY_DOMAINS` before it is used to construct any outbound request URI [5](#0-4) . `begin_auth` breaks this equality: the `shop` used to build `auth_route` is the caller-supplied value verbatim, unchecked against the trusted-domain allowlist that every other grant flow (`client_credentials`, `refresh_token`, `token_exchange`) enforces. `Utils::ShopValidator` is never referenced in `oauth.rb` at all.

Because `begin_auth` is the entry point a host application typically calls with a `shop` value taken from an unauthenticated query parameter on the app's own login route (before any HMAC or session exists), an unprivileged internet user can supply a hostile `shop` string (e.g. `attacker.example.com` or a domain string engineered to pass naive host-application checks) and cause the gem to construct `auth_route = "https://attacker.example.com/admin/oauth/authorize?client_id=...&redirect_uri=...&state=..."`. The gem itself performs no allowlist check, unlike its own `ShopValidator` utility that exists specifically to prevent this class of issue elsewhere in the same codebase.

### Impact Explanation
This does not leak `client_secret` (that only travels in `validate_auth_callback`'s POST body, which is host-bound by `auth_base_uri(auth_query.shop)` using the HMAC-validated `shop` from the callback, not `begin_auth`'s value). However, it does leak the app's `client_id` and the CSRF `state` nonce to an attacker-controlled host, and it can be used to force an OAuth completion against an attacker's fake authorize page, which can lead to session fixation / forced OAuth completion — matching the High-severity category "session fixation or forced OAuth completion". It also constitutes a scope/host-binding check that the gem itself omits relative to its own established pattern in `client_credentials.rb`/`refresh_token.rb`.

### Likelihood Explanation
Likelihood depends entirely on whether the host application passes its own unauthenticated request parameter as `shop:` to `begin_auth` without first calling `ShopValidator` itself — which is exactly the behavior the gem encourages by providing (and using internally in three other flows) a `sanitize!` helper that `begin_auth` conspicuously does not call. Since this is an inconsistency in the gem's own internal enforcement (not merely "the host app ignoring documented API" — the documented and internally-used pattern is inconsistent within the gem), this is in scope.

### Recommendation
Call `Utils::ShopValidator.sanitize!(shop)` (or `sanitize_shop_domain`) at the top of `Oauth.begin_auth`, before constructing `auth_base_uri`, mirroring `ClientCredentials.client_credentials` and `RefreshToken.refresh_access_token`, and use the sanitized value throughout (including as the `shop` stored in `AuthQuery`/cookie for the later callback comparison).

### Proof of Concept
1. Host app calls `ShopifyAPI::Auth::Oauth.begin_auth(shop: params[:shop], redirect_path: "/auth/callback")` where `params[:shop]` is taken from an unauthenticated query string (a common integration pattern, since the gem provides no built-in extraction/validation step for this parameter, unlike the other grant flows).
2. Attacker sends the victim a link with `shop=attacker.example.com` (or any non-myshopify host).
3. `auth_base_uri("attacker.example.com")` returns `"https://attacker.example.com/admin"` [6](#0-5) , and `begin_auth` returns `auth_route = "https://attacker.example.com/admin/oauth/authorize?client_id=<APP_CLIENT_ID>&scope=...&redirect_uri=<APP_HOST>/auth/callback&state=<NONCE>"`.
4. The victim's browser is redirected there, exposing `client_id`, `scope`, `redirect_uri`, and `state` to the attacker's server, which the attacker can use to craft a forged callback / forced OAuth completion against the real app.
