### Title
Webhook shop-domain header is trusted for tenant routing but is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating an HMAC computed only over the raw request body, then hands the caller's declared `shop` header straight to the app's handler as the tenant identifier — without that header ever being covered by the signature that was just verified.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `HmacValidator.validate` computes/compares the HMAC solely against that signable string [2](#0-1) . The `shop` value, however, is read from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header [3](#0-2) , which is never included in `to_signable_string`.

`Registry.process` validates the HMAC and, if it passes, immediately forwards `request.shop` (the unauthenticated header value) to the registered handler as the tenant identity for the event: [4](#0-3) .

This breaks the identity binding: `hmac_valid(raw_body) == true` is treated as proof that `(shop, topic, body)` as a whole originated from Shopify for that shop, when in fact only `hmac_valid(raw_body)` is proven. `shop_header_used_by_app != shop_bound_by_signature`.

### Impact Explanation
Any party who has legitimately received one authentic webhook delivery for their own shop (i.e., an ordinary merchant/tenant of the host app — no `client_secret`, access token, or privileged access needed) possesses a `(raw_body, hmac)` pair that will always validate successfully regardless of which `shop-domain` header accompanies it. By replaying that same body+signature to the app's webhook endpoint with the `x-shopify-shop-domain` header changed to a different shop, the request passes `Utils::HmacValidator.validate` and is dispatched to the handler tagged with the attacker-chosen shop. If the host application uses `WebhookMetadata#shop` (as documented/intended) to look up the tenant's session/data and apply the webhook body, this allows cross-tenant data injection/corruption — a different merchant's records can be mutated using data the attacker controls (their own webhook body) but attributed to a shop they do not own. This meets the Critical "cross-tenant access" bar.

### Likelihood Explanation
Likelihood is moderate-to-high in any hosting app that follows this gem's own documented pattern of trusting `WebhookMetadata#shop`/`#topic` once `Registry.process` doesn't raise. The prerequisite (having a legitimately-signed webhook for one's own shop) is trivially satisfiable by any user who installs the target app, since webhook triggering is entirely within their control (e.g., updating their own product/order fires the webhook with their own valid body+HMAC), after which they can replay it with a spoofed shop header.

### Recommendation
Bind the shop (and ideally topic) identity into the value that is HMAC-verified, or otherwise cryptographically tie the header to the signed payload before it is trusted as a tenant identifier. Concretely:
- Include `shop`/`topic` in `to_signable_string`, or
- Require callers to independently verify that `request.shop` corresponds to an installed/known shop before processing, and document/enforce this in `Registry.process` rather than leaving `WebhookMetadata#shop` implicitly trusted, or
- Have `Registry.process` reject requests where the resolved shop cannot be independently confirmed as the origin of `raw_body` (e.g., pair with a per-shop secret if the app uses per-shop offline tokens with unique secrets, if supported).

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and triggers any subscribed webhook topic (e.g., `orders/create`), capturing the raw POST body and the `X-Shopify-Hmac-Sha256` header sent by Shopify — both fully legitimate and requiring no secrets.
2. Attacker resends this exact `(raw_body, hmac)` pair to the same app endpoint but sets `X-Shopify-Shop-Domain: victim.myshopify.com` (and any other headers as needed, e.g. topic left the same or adjusted, since only `hmac-sha256`, `topic`, and `shop-domain` are required per `Webhooks::Request#initialize` [5](#0-4) ).
3. `Utils::HmacValidator.validate` recomputes the HMAC over `raw_body` only, matches the attacker-supplied HMAC, and returns `true` [6](#0-5) .
4. `Registry.process` proceeds and calls `handler.handle(data: WebhookMetadata.new(..., shop: "victim.myshopify.com", body: <attacker's body>, ...))` [4](#0-3) , causing the host app to process attacker-controlled webhook data under the victim shop's identity.
