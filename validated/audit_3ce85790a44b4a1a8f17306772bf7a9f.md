### Title
On-Chain AMM Quote Used for Fee-Asset Swap Without User-Supplied Slippage Bound Enables Front-Running/Sandwich Overpayment - (File: `substrate/frame/transaction-payment/asset-conversion-tx-payment/src/payment.rs`)

### Summary
`SwapAssetAdapter::withdraw_fee` computes how much of a non-native `asset_id` a user must pay for a transaction fee by calling `S::quote_price_tokens_for_exact_tokens` against the live AMM pool reserves, then immediately executes `S::swap_tokens_for_exact_tokens` using that quoted amount as the exact input. [1](#0-0)  Unlike the direct `swap_exact_tokens_for_tokens`/`swap_tokens_for_exact_tokens` extrinsics in `pallet-asset-conversion`, which take an explicit `amount_out_min`/`amount_in_max` chosen by the caller, [2](#0-1)  there is no equivalent bound the fee payer can set here — the "acceptable price" is derived entirely from the same manipulable on-chain state used for the swap itself.

### Finding Description
`quote_price_tokens_for_exact_tokens` explicitly documents that "the price may have changed by the time the transaction is executed" and that callers should use a min/max parameter to control slippage. [3](#0-2)  In `withdraw_fee`, this quote is taken and used directly as the swap amount with no such protection:

```rust
let asset_fee =
    S::quote_price_tokens_for_exact_tokens(asset_id.clone(), A::get(), fee, true)
        .filter(|asset_fee| !asset_fee.is_zero())
        .ok_or(InvalidTransaction::Payment)?;
...
let (fee_credit, change) = match S::swap_tokens_for_exact_tokens(
    vec![asset_id, A::get()],
    asset_fee_credit,
    fee,
) { ... };
``` [4](#0-3) 

Because both the quote and the swap read the same pool reserves at extrinsic-execution time, an attacker can submit a swap transaction ordered immediately before the victim's fee-paying transaction in the same block (a classic sandwich front-run), pushing the AMM price of `asset_id` against native `A::get()` up right before the quote is taken. The victim's `withdraw_fee` then computes an inflated `asset_fee`, withdraws that inflated amount from the victim, and swaps it — after which the attacker can reverse their initial swap to extract the AMM fee/price spread as profit. The `ChargeAssetTxPayment` extension gives the victim no parameter to cap the acceptable `asset_id` cost, unlike the pallet's own swap extrinsics.

### Impact Explanation
Any user paying transaction fees via a non-native asset through `pallet-asset-conversion-tx-payment` can be forced to overpay in `asset_id` for the same fixed native fee, with the attacker profiting from the manipulated spread. This is a direct value-transfer/loss issue for the fee payer, not merely theoretical, because the withdrawal and swap amounts are entirely a function of pool state that any unprivileged party can move within the same block.

### Likelihood Explanation
Exploitation requires only the ability to submit ordinary swap transactions against the same pool and achieve favorable ordering relative to the victim's transaction (via mempool front-running or block-author/MEV influence) — no privileged role or trusted component is required. This mirrors the exact vulnerability class in the referenced report: an on-chain, same-transaction price quote used to bound a swap is inherently exposed to sandwich manipulation.

### Recommendation
Allow the transaction sender to supply an explicit maximum acceptable `asset_id` cost (analogous to `amount_in_max`) for `ChargeAssetTxPayment`, and reject the transaction if `quote_price_tokens_for_exact_tokens`/the resulting swap would exceed it, rather than relying solely on the freshly-computed on-chain quote as the swap bound.

### Proof of Concept
1. Attacker observes a pending transaction from Victim using `ChargeAssetTxPayment` with `asset_id = X` to pay fee `F` (in native asset `A`).
2. Attacker submits (and gets ordered first, e.g., via higher tip/MEV) a large swap of `A` into `X` in the same pool, spiking the `X`/`A` price.
3. Victim's `withdraw_fee` executes: `quote_price_tokens_for_exact_tokens(X, A, F, true)` returns an inflated `asset_fee` reflecting the manipulated reserves, per `substrate/frame/transaction-payment/asset-conversion-tx-payment/src/payment.rs` lines 142-146.
4. Victim's `asset_fee` of `X` is withdrawn and swapped for exactly `F` of `A`, per lines 148-164.
5. Attacker submits a back-run swap reversing step 2, extracting the price-impact profit; Victim has paid more `X` than they would have absent manipulation, with no recourse since no max-cost parameter exists. [5](#0-4)

				fee,
				Precision::Exact,
				Preservation::Preserve,
				Fortitude::Polite,
			)
			.map_err(|_| InvalidTransaction::Payment)?;

			return Ok((fee_credit, fee));
		}

		let asset_fee =
			S::quote_price_tokens_for_exact_tokens(asset_id.clone(), A::get(), fee, true)
				.filter(|asset_fee| !asset_fee.is_zero())
				.ok_or(InvalidTransaction::Payment)?;

		// Withdraw the `asset_id` credit for the swap.
		let asset_fee_credit = F::withdraw(

			asset_fee,

			Preservation::Preserve,
			Fortitude::Polite,
		)

		let (fee_credit, change) = match S::swap_tokens_for_exact_tokens(

		ensure!(change.peek().is_zero(), InvalidTransaction::Payment);

		Ok((fee_credit, asset_fee))
	}
