### Title
Webhook shop-domain header is not covered by HMAC verification, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC that `Utils::HmacValidator.validate` checks in `Registry.process` binds solely to the request body. The `shop` (`x-shopify-shop-domain`), `topic`, and `webhook_id` values are read straight from unauthenticated HTTP headers and handed to the app's `WebhookHandler` as trusted tenant identity, breaking the equality "shop authenticated == shop acted upon."

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
and the `shop`, `topic`, and `webhook_id` accessors simply read from headers with no binding to the HMAC: [2](#0-1) 

`HmacValidator.validate` computes and compares the HMAC only over `to_signable_string` (i.e., the raw body): [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` (all header-derived, unauthenticated values) to build the `WebhookMetadata` passed to the app's handler: [4](#0-3) 

The `shop` field on `WebhookMetadata` is explicitly documented as the authoritative "shop domain of the webhook" for the handler to key its logic/data storage on: [5](#0-4) [6](#0-5) 

Because the `shop-domain` header is not part of the signed material, any two requests with the same body will validate under the same HMAC regardless of which shop header is attached. An attacker who is a legitimate merchant on a shop they control (an "unprivileged internet user" relative to other tenants) will receive genuine webhook deliveries — valid body + valid HMAC — from Shopify to their own installed endpoint. They can then replay that exact body/HMAC pair to the app's shared webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) header with another (victim) shop's domain. `Utils::HmacValidator.validate` still returns `true` because it only checks the body, and `Registry.process` forwards the attacker-chosen `shop` value straight to the host application's handler as if it were verified Shopify-authenticated tenant data.

### Impact Explanation
This breaks the identity binding "shop verified by HMAC == shop acted upon by the handler," letting a merchant attacker inject data attributed to, or trigger processing on behalf of, another merchant's tenant (`shop`) inside the host application, since the library asserts the request "did indeed come from Shopify" for that shop after HMAC validation (see `docs/usage/webhooks.md` line 125) while in fact only the body's origin (not the shop attribution) is verified. This is a cross-tenant data/processing confusion issue matching the Critical "cross-tenant access" impact category, because host applications built per this gem's documented contract will use `data.shop` as the trusted tenant key (as shown in the gem's own usage example: `perform_later(topic: data.topic, shop_domain: data.shop, ...)`).

### Likelihood Explanation
Likelihood is limited by the fact that: (1) the attacker needs at least one genuine webhook delivery (obtainable by installing the app on their own store — a normal, unprivileged action), (2) they must be able to intercept/replay the raw HTTP request to the app's public webhook endpoint with a modified `shop-domain` header (feasible for any client since it's just an HTTP header, not signed), and (3) the impact depends on the host app trusting `data.shop`/`data.topic` as the gem's documentation instructs it to. Given the gem explicitly instructs developers to trust these fields once `Registry.process` succeeds, and the attack requires no secret credentials, this is a realistic, low-effort attack path once the attacker is a legitimate app user.

### Recommendation
Bind the `shop`, `topic`, and `webhook_id` values into the signed material used for HMAC verification (or otherwise cryptographically/authoritatively confirm the shop identity against a source not controlled by the requester, e.g., cross-check against the shop that installed/registered that specific `webhook_id`) before exposing them to `WebhookHandler#handle`. At minimum, document/require that host apps independently verify `data.shop` belongs to a store that actually has this webhook/topic registered, or extend `to_signable_string` to include the shop/topic/webhook_id headers so tampering invalidates the HMAC.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and registers for a webhook topic (e.g. `orders/create`).
2. Shopify delivers a legitimate webhook: body `B`, headers include `x-shopify-hmac-sha256: H(B)` (valid), `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-topic: orders/create`, `x-shopify-webhook-id: W`.
3. Attacker captures this raw request (body `B` and the valid HMAC header), then replays it to the app's shared webhook endpoint but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com` (and optionally to a different registered topic/webhook_id), keeping body `B` and the original HMAC unchanged.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes HMAC over `request.to_signable_string` (`B`) — this still matches, so validation passes.
5. `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` using the attacker-supplied `victim-shop.myshopify.com`, and invokes the host app's handler, which (per the gem's documented contract) treats this as an authenticated webhook belonging to `victim-shop.myshopify.com`.
