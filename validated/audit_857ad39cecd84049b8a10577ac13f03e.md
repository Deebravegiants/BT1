### Title
`IntentGatewayV2::placeOrder` sets Uniswap V2 swap `deadline` to `block.timestamp`, nullifying deadline protection on the fee swap - (File: `evm/src/apps/IntentGatewayV2.sol`)

### Summary
When a user places an order with `order.fees > 0` and pays the fee in native token, `placeOrder` swaps ETH for the exact fee-token amount via `IUniswapV2Router02.swapETHForExactTokens`, passing `block.timestamp` as the `deadline` argument instead of a caller-supplied or forward-looking deadline. [1](#0-0) 

### Finding Description
`deadline` in Uniswap V2 router calls is meant to bound how long a signed/submitted transaction may sit unconfirmed before its swap becomes invalid, protecting the sender against having the transaction included at an arbitrarily later block with a materially different price. Because `block.timestamp` evaluates to the timestamp of whichever block the transaction is *eventually* mined in, `deadline == block.timestamp` at execution time is always satisfied — it provides no actual protection. This is the same root-cause class as the referenced report (`LiquidityManager::_decreaseLiquidity`): a hardcoded `block.timestamp` deadline instead of a bounded, forward-looking one.

Here the call is:
```solidity
uint256[] memory amounts = IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msgValue}(
    order.fees, path, address(this), block.timestamp
);
```
`amountInMaximum` is effectively the entire remaining `msgValue` sent by the user (the router will consume up to all of it to obtain the exact `order.fees` output), so an adversary (e.g., a relayer/searcher/validator with mempool visibility) can hold the `placeOrder` transaction and have it included after adverse price movement (or directly sandwich it), forcing the swap to execute near the worst acceptable price and consuming far more of the user's ETH than intended, without deadline expiry ever blocking it. [2](#0-1) [3](#0-2) 

### Impact Explanation
This is directly reachable by any unprivileged user calling `placeOrder` with a native-token input and a nonzero `order.fees` — the standard order-placement entry point of the Intent Gateway. Loss manifests as excess ETH spent for the swap that reduces the refund (`msgValue -= amounts[0]`) sent back to the user, i.e., concrete value extraction/loss of user funds via MEV/sandwiching that a correct deadline would otherwise bound. Because the swap's `amountInMaximum` is essentially the user's full deposited value, the worst case is bounded only by however unfavorable the pool price can be moved before/at inclusion. [4](#0-3) 

### Likelihood Explanation
Any transaction touching a public Uniswap V2 pool is visible in the mempool; a searcher/validator can trivially sandwich or delay it since the `deadline` check never actually constrains inclusion time. No special privilege or governance action is required — only that a user places an order with `order.fees > 0` paid in native token.

### Recommendation
Replace `block.timestamp` with a caller-specified `deadline` parameter (validated to be `>= block.timestamp` at submission and reasonably bounded), or at minimum `block.timestamp + <fixed window>`, so the swap can actually expire if not promptly included:
```diff
- order.fees, path, address(this), block.timestamp
+ order.fees, path, address(this), block.timestamp + MAX_SWAP_WINDOW
```
Combine this with tightening `amountInMaximum` (currently the full `msgValue`) against an oracle/quote-derived bound so a stale or manipulated price cannot silently consume excess user funds even within the window.

### Proof of Concept
1. User calls `placeOrder` with a native-token input, `order.fees > 0`, and `msg.value` covering both the input and an expected fee-swap cost.
2. `placeOrder` reaches the fee block and calls `swapETHForExactTokens{value: msgValue}(order.fees, path, address(this), block.timestamp)`.
3. A searcher observing the pending transaction front-runs the pool (or a validator delays inclusion) to move the ETH/`feeToken` price unfavorably.
4. The swap still executes and succeeds (since `deadline` trivially matches whatever block it lands in and `amountInMaximum` is essentially unbounded), consuming significantly more ETH than the pre-attack price implied.
5. `msgValue -= amounts[0]` is smaller, so the refund transferred back to the user at the end of `placeOrder` is correspondingly reduced — the user has lost the difference to the attacker/pool, with no deadline mechanism having protected them. [5](#0-4)
