### Title
Webhook shop/topic identity is not bound by the HMAC signature, enabling cross-tenant webhook forgery via replay - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw body only, while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from unauthenticated HTTP headers and passed straight into the handler as trusted tenant-identifying data. This is the same class of bug as the reported front-running issue: a value that downstream code treats as an identity binding (`shop`) is never covered by the cryptographic commitment (the HMAC) that is supposed to authenticate the request.

### Finding Description
`Utils::HmacValidator.validate` verifies a `VerifiableQuery` by comparing `verifiable_query.hmac` against a signature computed over `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` returns only `@raw_body`: [2](#0-1) 

But `shop`, `topic`, `webhook_id`, and `api_version` are all pulled from headers that are entirely outside that signable string: [3](#0-2) 

`Registry.process` validates only the body's HMAC and then forwards the unauthenticated `request.shop`/`request.topic` values straight to the app's handler as the tenant identity for the event: [4](#0-3) 

Because the HMAC never binds `shop` (or `topic`/`webhook_id`), any request whose `raw_body` + `hmac` pair is valid for the app's secret can be replayed with an arbitrary `x-shopify-shop-domain` header, and `HmacValidator.validate` will still pass — exactly like the reported bug where `commit()`/`register()` failed to bind the commitment to a specific owner, letting a front-runner repurpose someone else's commitment for their own address. Here, an unprivileged attacker who has ever obtained one legitimate `(raw_body, hmac)` pair for the app — trivially available to any user who installs the app on their own store and triggers a webhook-worthy event — can resend that exact body/HMAC pair to the app's public webhook endpoint with the `shop-domain` header changed to a victim shop. The handler receives `WebhookMetadata` claiming the event belongs to the victim shop, even though the HMAC only ever authenticated the attacker's own body.

### Impact Explanation
This breaks the tenant identity binding `shop-header == shop actually authenticated by the HMAC`. An app that keys any state, side effects, or access-token lookups off `WebhookMetadata#shop` (the documented and only way this gem exposes the webhook's shop) can be made to process attacker-supplied data under another merchant's identity — a cross-tenant access/data-injection primitive, which the rules classify as Critical impact.

### Likelihood Explanation
Likelihood is realistic: any unprivileged user can install the target app on their own free/dev Shopify store (no special privilege beyond normal signup), trigger a webhook topic that is registered by the app (e.g., `orders/create` with attacker-controlled content), capture the resulting `(raw_body, x-shopify-hmac-sha256)` from their own endpoint logs, then POST it to the same publicly reachable webhook URL while swapping only the `x-shopify-shop-domain` header. No secret, token, or privileged access to the victim's data is required — only network access to the app's own webhook endpoint.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the value that is HMAC-verified, or at minimum require callers to cross-check `request.shop` against a known-installed session/shop list before trusting it, and document this requirement clearly in `Registry.process`/`WebhookMetadata`. Where feasible, prefer deriving the shop identity from data that Shopify itself signs (or from a per-shop webhook secret) rather than an unauthenticated header.

### Proof of Concept
1. Install the target app on attacker-controlled store `attacker.myshopify.com`; trigger a subscribed webhook topic (e.g. `orders/create`).
2. Capture the delivered request: `raw_body` and header `x-shopify-hmac-sha256` (valid for the app's secret, per `HmacValidator.validate`).
3. Replay the exact same `raw_body` and `hmac` header to the app's public webhook endpoint, but set `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb:190`) validates the HMAC over `raw_body` only — it passes — then calls the handler with `shop: "victim-shop.myshopify.com"` (`lib/shopify_api/webhooks/registry.rb:198`), even though the HMAC never authenticated that shop value.
