### Title
Webhook `shop` field is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw request body, then hands the handler an unauthenticated `shop` value taken directly from the `X-Shopify-Shop-Domain` header. Because the shop identity is not part of the signed material, an attacker who possesses one valid `(raw_body, hmac)` pair for their own shop can replay it with a forged `shop-domain` header to make the app process the webhook as if it belonged to a different, victim shop.

### Finding Description
The gem's own documentation states that `Registry.process` "will verify the request did indeed come from Shopify" before invoking the handler [1](#0-0) . In practice, verification is implemented as: [2](#0-1) 

`Utils::HmacValidator.validate` computes and compares the HMAC using `verifiable_query.to_signable_string`, and for `Webhooks::Request` that method returns only the raw HTTP body — never the headers: [3](#0-2) 

Yet the `shop` accessor used to build `WebhookMetadata` (and handed to the app's handler) is read straight from the `x-shopify-shop-domain` / `shopify-shop-domain` header with no cross-check against the signed body, the topic, or any known/registered shop list: [4](#0-3) [5](#0-4) 

The equality this breaks is: `shop used by handler.handle == shop the HMAC-signed payload was actually generated for`. Because the HMAC secret (`api_secret_key`) is shared by every shop that has installed the app, and only `raw_body` is signed, an attacker who has legitimate access to their own shop's webhook feed (which any developer/tester can obtain simply by installing the app on a shop they control) can capture a `(body, hmac)` pair that Shopify computed correctly for their own tenant, then POST that exact body/hmac to the app's webhook endpoint while substituting an arbitrary victim `shop-domain` header. `HmacValidator.validate` still succeeds because it only checks the body bytes, and `Registry.process` calls the handler with `shop: request.shop` set to the attacker-chosen victim domain — resulting in the app applying data/state changes intended for the attacker's shop to a different tenant.

### Impact Explanation
This crosses the tenant boundary the webhook system is meant to enforce: host applications rely on `WebhookMetadata#shop` (documented as "The shop domain of the webhook") to route data updates, cache invalidation, order/inventory sync, etc., per-merchant. An attacker can forge which merchant a webhook event is attributed to, causing cross-tenant data injection/corruption without needing the `api_secret_key`, an access token, or any privileged credential — only a legitimate (even free) installation of the app on a shop they control. This matches the Critical criterion "cross-tenant access."

### Likelihood Explanation
Likelihood is high for any app with public/self-serve installation: the attacker needs no secret material, only a working webhook subscription on their own shop (trivial to obtain) and the ability to send an HTTP POST to the app's public webhook endpoint with a spoofable header. The vulnerability is fully within this gem's code path (`Request#shop`, `Registry.process`, `HmacValidator.validate`/`Request#to_signable_string`), not a host-app misuse of a documented contract — the gem itself both computes the "verified" claim and supplies the unverified `shop` field to the handler.

### Recommendation
Bind the shop identity to the signature verification, e.g.:
- Require the `shop` value to be included in `to_signable_string` (or otherwise cryptographically bound), or
- Cross-check `request.shop` against the shop(s) a session/registration is known for before invoking the handler, or
- Document explicitly (and enforce in `Registry.process`) that `shop` must be validated by the host app against its own shop/session store before being trusted, since the current API and docs imply the value is already verified.

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com`; trigger a real webhook (e.g., `orders/create`) so Shopify sends a legitimately HMAC-signed request:
   ```
   POST /webhook
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid HMAC over body>
   x-shopify-shop-domain: attacker.myshopify.com
   Body: {"id": 1, ...}
   ```
2. Capture the raw body and the valid `x-shopify-hmac-sha256` value.
3. Replay the identical body and HMAC header to the app's webhook endpoint, but change the header:
   ```
   x-shopify-shop-domain: victim.myshopify.com
   ```
4. `ShopifyAPI::Webhooks::Request#hmac` still matches, since `to_signable_string` (lib/shopify_api/webhooks/request.rb:36-38) returns only `@raw_body`, unaffected by the header change; `Utils::HmacValidator.validate` (lib/shopify_api/webhooks/registry.rb:190) passes.
5. `Registry.process` invokes `handler.handle(data: WebhookMetadata.new(..., shop: "victim.myshopify.com", ...))` (lib/shopify_api/webhooks/registry.rb:198-199), causing the host app to process attacker-supplied data as if it originated from `victim.myshopify.com`.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
