### Title
Webhook HMAC Does Not Cover the `shop-domain` Header, Allowing Cross-Tenant Shop Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw body only, while the shop identity (`shop-domain` header) used downstream for tenant attribution is never included in the signed bytes. `Registry.process` validates the HMAC and then trusts the unauthenticated `shop` value to build `WebhookMetadata`, breaking the binding "bytes verified == bytes acted on."

### Finding Description
`HmacValidator.validate` accepts any object implementing `Utils::VerifiableQuery`, which requires only `hmac` and `to_signable_string`. For webhooks, `to_signable_string` returns `@raw_body` exclusively: [1](#0-0) 

The `shop` accessor, however, is read straight from the `shop-domain` header, independent of the signed payload: [2](#0-1) 

`Registry.process` validates the HMAC against the request, then dispatches to the handler using `request.shop`, which was never part of the signature check: [3](#0-2) 

The HMAC secret (`Context.api_secret_key`) is the app's single `client_secret` shared across every shop that installs the app — it is not per-shop. That means the equality the code implicitly relies on is:

`hmac_valid(raw_body, api_secret_key) == true` implies `shop-domain header is authentic`

but the actual guarantee provided by `HmacValidator.validate` is only:

`hmac_valid(raw_body, api_secret_key) == true` implies `raw_body is authentic`

The `shop` header is disjoint from what's verified, so any party who can obtain one genuine webhook delivery for their own shop (trivial — they just need any shop that installs the multi-tenant app, e.g., a development store) can replay that exact raw body to the app's webhook endpoint while substituting `x-shopify-shop-domain` (or `shopify-shop-domain`) with a victim shop domain. The HMAC computed over the untouched body still validates successfully because the secret and body are unchanged, and the forged shop value flows unchecked into `WebhookMetadata` and the app's handler logic.

### Impact Explanation
This is a cross-tenant integrity/confusion issue: an attacker-controlled `shop` value reaches app-side handlers (e.g., mandatory topics like `customers/redact`, `customers/data_request`, `shop/redact`, or any app-registered handler that keys business logic, session lookups, or storage writes by `data.shop`). This can be leveraged to trigger tenant-scoped actions (data deletion, redaction routines, order/customer processing) attributed to a shop the attacker does not control or have access to — a cross-tenant access primitive that satisfies the Critical impact bar (cross-tenant access) defined for this analysis.

### Likelihood Explanation
Likelihood is meaningful but bounded: the attacker must (a) control or observe at least one legitimate webhook delivery raw body from Shopify to any shop (achievable with a free development store installing the same multi-tenant app), and (b) know/guess the victim's `myshopify.com` domain (often publicly discoverable). No access token, `client_secret`, or privileged account is required — only the ability to send an HTTP request to the app's public webhook endpoint with a forged header, which is entirely within this gem's own trust boundary (`Registry.process` / `HmacValidator.validate`).

### Recommendation
Bind the shop identity into the signed material actually verified, or otherwise cryptographically tie the `shop-domain` header to the HMAC:
- Prefer verifying against Shopify's per-request signature semantics that already include the header value it protects, or
- If continuing to rely on `hmac-sha256` over raw body only, additionally validate that the resolved `shop` corresponds to a shop with an active, previously-established webhook subscription/session known to the app (e.g., cross-check against stored offline session for that shop) before trusting `request.shop` for any tenant-scoped action, rather than trusting the header verbatim once the body-only HMAC passes.

### Proof of Concept
1. Attacker installs the target (multi-tenant) app on `attacker-shop.myshopify.com` and registers a webhook handler, e.g. for `customers/data_request`.
2. Shopify delivers a webhook to the app with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid-hmac-of-body>`, and some JSON body.
3. Attacker replays the identical raw body and HMAC header to the app's webhook endpoint, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `OpenSSL.secure_compare(computed_signature, received_signature)` against `@raw_body` — this still passes because the body and secret are unchanged: [4](#0-3) 
5. `handler.handle` is invoked with `WebhookMetadata.new(..., shop: request.shop, ...)` where `shop` is `"victim-shop.myshopify.com"`, an attacker-forged value never covered by the signature, causing the app to execute shop-scoped logic against a tenant the attacker does not control.
