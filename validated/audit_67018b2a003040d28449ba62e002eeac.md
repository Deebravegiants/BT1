## Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing shop-identity spoofing on inbound webhooks - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes and verifies the HMAC over the raw request body only, while the `shop` value that is later trusted and forwarded to the app's webhook handler is read straight from the unauthenticated `X-Shopify-Shop-Domain` header. This breaks the identity binding **shop asserted in the request == shop actually authenticated by the HMAC**, letting anyone who can produce one valid `(body, hmac)` pair for the shared app secret relabel that payload as belonging to a different shop.

### Finding Description
`Request#to_signable_string` only returns `@raw_body`: [1](#0-0) 

`Request#shop` is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of the signed material at all: [2](#0-1) 

`Registry.process` validates only the HMAC of the body (via `Utils::HmacValidator.validate`), then immediately forwards `request.shop` (the unauthenticated header value) into `WebhookMetadata`, which is handed to the app's handler as the trusted tenant identifier: [3](#0-2) 

`HmacValidator.validate` confirms only that `verifiable_query.to_signable_string` (the raw body) was signed with `Context.api_secret_key`/`old_api_secret_key` — it never touches `shop`: [4](#0-3) 

Because `api_secret_key` is a single, app-wide secret shared across every installed shop (not a per-tenant key), any merchant who has installed the app can legitimately receive a real `(body, hmac)` pair from Shopify for their own shop. That merchant can then replay the identical `body` + `hmac` pair to the app's webhook endpoint while substituting a different value in `X-Shopify-Shop-Domain`. The HMAC check still passes (it never inspects the header), so the app processes attacker-controlled webhook data under the identity of a victim shop it does not control — a cross-tenant identity binding break, directly analogous to the reported class ("shop authenticated versus the shop stored as a session key").

### Impact Explanation
If a webhook handler uses `data.shop` (from `WebhookMetadata`) to look up or mutate per-tenant state (e.g., resolve a stored session/access token for that shop, update the victim shop's local records, or trigger shop-scoped side effects), an attacker-controlled shop can forge webhook events "from" an arbitrary victim shop domain and inject or corrupt that victim's data — a cross-tenant access/integrity violation. This matches the Critical "cross-tenant access" impact bucket in scope, since the only binding that should prevent this (the HMAC) does not actually cover the shop field being trusted.

### Likelihood Explanation
Any unprivileged party who can install the app on at least one shop (a normal, unprivileged action for a public/embedded Shopify app) automatically receives legitimately-signed webhook bodies for their own shop from Shopify. No secret, token, or special access is required beyond normal app installation — replaying the captured body/hmac pair with a modified header is a trivial HTTP replay.

### Recommendation
Bind the shop identity into the verified material instead of trusting an unauthenticated header:
- Include the `shop-domain` header (and ideally `topic`/`webhook-id`) in the signable string used for HMAC computation, or
- Cross-check the shop asserted by the header against the shop embedded in the parsed webhook body (Shopify webhook payloads typically include the shop's numeric/domain identifier), rejecting the request if they don't match.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com`, triggering a legitimate Shopify webhook delivery with body `B` and header `X-Shopify-Hmac-Sha256: H` (computed by Shopify with the app's shared `api_secret_key`).
2. Attacker captures `(B, H)` from their own webhook endpoint traffic.
3. Attacker replays a request to the app's webhook endpoint with the same body `B`, same `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` succeeds because it only checks `B` against `H` [5](#0-4) .
5. `Registry.process` builds `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` [6](#0-5)  and the app's handler processes the attacker's data as if it originated from the victim shop.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
