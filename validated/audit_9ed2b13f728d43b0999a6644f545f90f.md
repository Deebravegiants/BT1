Confirmed root cause. The `Webhooks::Request` HMAC signable string is only the raw body; the `shop-domain` header is never covered by that signature, yet `Registry.process` passes `request.shop` straight through to the handler as the authoritative tenant identifier.### Title
Webhook `shop` tenant identifier is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, so `Utils::HmacValidator.validate` in `Registry.process` proves nothing about the `x-shopify-shop-domain` (or `shopify-shop-domain`) header. That header is nonetheless taken as the trusted tenant identifier and handed directly to every app's `WebhookHandler#handle` via `WebhookMetadata#shop`. This is the same bug class as the `safeTransferMany()` report: a function whose name/contract implies a full integrity check (`validate`/HMAC-authenticated webhook) but which actually leaves a security-relevant field — here the shop binding — outside the guarantee, letting a caller supply that field unauthenticated.

### Finding Description
- `Request#to_signable_string` (`lib/shopify_api/webhooks/request.rb:35-38`) returns `@raw_body` exclusively:
  ```ruby
  def to_signable_string
    @raw_body
  end
  ``` [1](#0-0) 
- `shop` is read straight from an HTTP header with no cryptographic binding at all:
  ```ruby
  def shop
    T.cast(shopify_header("shop-domain"), String)
  end
  ``` [2](#0-1) 
- `Registry.process` validates the HMAC over the body only, then immediately forwards `request.shop` — the unverified header — to the app's handler as the authoritative shop:
  ```ruby
  def process(request)
    raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
    handler = @registry[request.topic]&.handler
    ...
    handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))
  end
  ``` [3](#0-2) 
- `HmacValidator.validate` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it to the `hmac` header via `OpenSSL.secure_compare` — again, only over the signable string (the body), never the shop header:
  ```ruby
  def validate_signature(verifiable_query, secret)
    received_signature = verifiable_query.hmac
    computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
    OpenSSL.secure_compare(computed_signature, T.must(received_signature))
  end
  ``` [4](#0-3) 
- `WebhookMetadata` (the struct every app handler consumes) trusts `shop` as ground truth, with no further validation performed anywhere in the gem:
  ```ruby
  class WebhookMetadata < T::Struct
    const :topic, String
    const :shop, String
    const :body, T::Hash[String, T.untyped]
    ...
  end
  ``` [5](#0-4) 

The equality this design breaks: the shop the app *acts on* (`request.shop` fed into `WebhookMetadata`) is not guaranteed to equal the shop that actually produced the *signed* body. The HMAC only proves "this body was signed with our client secret at some point by Shopify," not "this body+shop pairing is authentic." Because a single app's client secret is shared across all merchant installs of that app, any unprivileged user who legitimately installs the app on a shop they control (a free/dev store, no special privilege required) will receive real, validly-signed webhook deliveries for their own shop. They can then replay that exact signed body to the app's webhook endpoint while substituting a different `x-shopify-shop-domain` header value (e.g., a victim shop that also has the app installed). The HMAC still validates (it only checks the body), and the app's handler executes with `data.shop` pointing at the victim tenant while `data.body` contains attacker-controlled content — a cross-tenant data-integrity/confidentiality violation entirely within this gem's `Webhooks::Registry`/`Request` code path, requiring no access token, no `api_secret_key`, and no privileged account.

### Impact Explanation
This crosses the Critical bar of "cross-tenant access": an attacker with only the unprivileged ability to install the app on their own store can cause the app's webhook processing logic to attribute forged/replayed data to a different, unrelated shop. Since most Shopify apps key persistence and business logic off the `shop` field from `WebhookMetadata` (e.g., updating orders/products/customers, or triggering redaction/GDPR flows keyed by shop), this allows cross-tenant data corruption or triggering of privileged per-tenant operations (e.g., forging a `customers/redact` or `app/uninstalled` event against a shop the attacker doesn't own) without ever needing that victim's credentials.

### Likelihood Explanation
Moderately likely to be reachable: any app using this gem's `Webhooks::Registry`/`Request` as documented is affected, since the vulnerable code path is the gem's own webhook verification primitive, not something the host app can opt out of short of re-implementing header-aware HMAC checking itself. The main precondition is that the attacker can install/operate at least one shop with the target app installed (trivial via a free Shopify dev/partner store) in order to harvest one legitimately signed body+HMAC pair, then replay it with a modified shop header to the app's public webhook endpoint.

### Recommendation
Bind the shop identity into the material that is HMAC-verified, or otherwise cryptographically/authoritatively re-derive it instead of trusting an unauthenticated header:
- Include `shop-domain` (and ideally `topic`, `webhook-id`, `api-version`) in `Request#to_signable_string`, matching whatever canonicalization Shopify actually signs for webhooks, so `HmacValidator.validate` fails if the shop header is altered post-signing; or
- If Shopify's webhook HMAC scheme genuinely only ever covers the raw body (matching the official platform behavior), document this prominently and require host apps to cross-check `request.shop` against a shop known to have installed the app (e.g., an existing offline session) before trusting `WebhookMetadata#shop`, rather than silently handing it to `WebhookHandler#handle` as if it were verified.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker-shop.myshopify.com`; trigger any webhook topic the app subscribes to (e.g., `products/update`) and capture the delivered request: raw body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
2. Replay the exact same request to the app's webhook endpoint, keeping `body = B` and `x-shopify-hmac-sha256 = H` unchanged, but set `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. In `Registry.process`, `Utils::HmacValidator.validate(request)` succeeds because it only recomputes the HMAC over `@raw_body` (`Request#to_signable_string`), which is unchanged. [6](#0-5) 
4. `handler.handle(data: WebhookMetadata.new(..., shop: request.shop, body: request.parsed_body, ...))` is invoked with `shop == "victim-shop.myshopify.com"` and `body == B`, even though `B` never originated from `victim-shop`. [7](#0-6)
