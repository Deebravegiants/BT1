### Title
Webhook shop-domain and topic headers are trusted without being covered by the HMAC signature, enabling cross-tenant webhook confusion - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC of the raw request body via `Utils::HmacValidator.validate(request)` [1](#0-0) . The `Request#to_signable_string` used for that signature check is just `@raw_body` [2](#0-1) , so only the payload bytes are bound by the HMAC. The `shop`, `topic`, `api_version`, and `webhook_id` values, however, are read straight from HTTP headers (`shopify-shop-domain`, `shopify-topic`, etc.) with no cryptographic binding to the signed body [3](#0-2) . `Registry.process` then dispatches the handler using these unauthenticated header values, including `request.shop`, directly as `WebhookMetadata` [4](#0-3) .

### Finding Description
The binding that should hold is: **bytes verified (body signed by HMAC with the app's `client_secret`) == bytes the handler acts on for tenant identity (`shop` header)**. In this gem that equality does not hold — the HMAC only covers `@raw_body` [5](#0-4) , while `shop`, `topic`, `webhook_id`, and `api_version` are parsed from headers that sit entirely outside the signed byte range [3](#0-2) .

An unprivileged internet user who is themselves a legitimate (or trial) merchant installing the same app can, from their own shop, trigger any webhook topic and observe a genuine `raw_body` + valid `x-shopify-hmac-sha256` pair signed with the app's real `client_secret` (this is normal, expected traffic the attacker legitimately receives for their own shop — no secret leakage or privileged access is required). Because the endpoint is a public HTTP endpoint and the HMAC only signs the body, the attacker can replay that exact `raw_body`/HMAC pair to the same webhook endpoint while substituting the `x-shopify-shop-domain` header (and/or `x-shopify-topic`) for a victim shop's domain. `HmacValidator.validate` still succeeds because it only checks the body bytes against the same secret [6](#0-5) , and `Registry.process` passes the attacker-chosen `shop` value straight into the handler as if it were an authenticated Shopify claim [7](#0-6) .

This breaks the tenant-authentication equality the app relies on: `shop` claimed in `WebhookMetadata` is supposed to equal the shop that Shopify's signed webhook infrastructure actually originated the event for, but the gem never checks that. A host application that trusts `data.shop` from `WebhookMetadata` (as the gem's own docs and generated handler interface imply it should) will attribute the replayed payload's content to the wrong tenant.

### Impact Explanation
This crosses a tenant boundary using only the payload/HMAC pair the attacker legitimately obtains for their own shop — no `api_secret_key`, access token, or privileged access is required, only observing traffic for the attacker's own shop and re-POSTing it with a different `shop` header value. Depending on how the host app uses `data.shop` (e.g., to look up which merchant's records to update, delete, or reveal), this can cause cross-tenant data corruption or disclosure — i.e., cross-tenant access, which matches the Critical impact category defined in scope.

### Likelihood Explanation
Likelihood is moderate-to-high for apps that expose a webhook endpoint reachable by any client with valid credentials to at least one shop (trivial to obtain via installing on a development/trial store) and that trust `WebhookMetadata#shop`/`#topic` without independent verification (e.g., re-fetching the resource via the Admin API scoped to a stored, trusted session). The gem provides no header-body binding and no built-in warning about this, so any host app following the documented `Registry.process` usage inherits the exposure.

### Recommendation
- Include the `shop-domain`, `topic`, `api_version`, and `webhook_id` header values in the signable string used for HMAC verification (or otherwise cryptographically bind them to the payload), so any tampering with these headers invalidates the signature.
- Alternatively, document explicitly that `WebhookMetadata#shop`/`#topic` are unauthenticated header values and require host applications to independently verify shop ownership (e.g., cross-check against a known/installed shop list) before acting on webhook data.
- Consider validating that `request.shop` matches an expected/allow-listed shop domain associated with the specific webhook subscription id before dispatching to handlers.

### Proof of Concept
1. Install the target app (or use a trial/dev store) as an unprivileged attacker; trigger any webhook (e.g., `orders/create`) to capture a real request with:
   - `raw_body` = legitimate JSON payload
   - `x-shopify-hmac-sha256` = valid HMAC over that body computed with the app's `client_secret`
   - `x-shopify-shop-domain` = `attacker-shop.myshopify.com`
2. Replay the exact same `raw_body` and `x-shopify-hmac-sha256` value to the app's public webhook endpoint, but set `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
3. In the gem: `ShopifyAPI::Webhooks::Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `@raw_body` against the HMAC [8](#0-7) .
4. The handler receives `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` with `shop == "victim-shop.myshopify.com"`, even though the payload actually originated from the attacker's own shop event [9](#0-8) .
5. Any host-app logic keyed on `data.shop` (e.g., "update this shop's local cache with this order data") now operates on the victim tenant using attacker-controlled webhook content.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
