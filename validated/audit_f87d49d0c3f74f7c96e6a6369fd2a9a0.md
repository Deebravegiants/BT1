**Analysis:**

`validator_consensus_info::new` at [1](#0-0)  is a plain, unguarded constructor, but it is only invoked internally by `validator_consensus_infos_from_validator_set`, a `friend`-only function that populates `ValidatorConsensusInfo` from the already-computed `ValidatorInfo.voting_power` field of the live `ValidatorSet` resource: [2](#0-1) . There is no entrypoint that lets an unprivileged caller supply an arbitrary `voting_power` value that gets written into the on-chain `ValidatorSet.active_validators`/`pending_inactive` collections.

The `voting_power` used to populate `ValidatorInfo` (and hence `ValidatorConsensusInfo`) is always derived directly from real coin balances via `get_voting_power`/`generate_validator_info`, which sums `coin::value` over the validator's `active`, `pending_active`, and `pending_inactive` sub-stores: [3](#0-2) . This value is not attacker-suppliable; it reflects the actual custodied balance.

`voting_power_increase_limit` (checked in `update_voting_power_increase`) bounds only the *rate* at which new stake can join per epoch relative to `total_voting_power`, aborting with `EVOTING_POWER_INCREASE_EXCEEDS_LIMIT` if exceeded: [4](#0-3) . It is not, and was never intended to be, an invariant that individual validator `voting_power` values are capped by this limit — `total_voting_power` itself is always recomputed as the sum of real per-validator balances in `refresh_validator_set_in_place`/`next_validator_consensus_infos_v2`, so there is no "legitimately capped total_voting_power" that a forged `ValidatorConsensusInfo` could exceed: [5](#0-4) .

Even hypothetically, `ValidatorConsensusInfo`/`ValidatorSetLivenessFallback` are consensus/BFT bookkeeping and event-emission constructs — they do not gate coin ownership, minting, burning, freezing, or transfer authority for any custody-grade asset. There is no unprivileged transaction, package, view, authenticator, or proof-input path that can inject a forged `ValidatorConsensusInfo` into the framework's authoritative `ValidatorSet`, and no custody boundary (owner, capability, balance) is crossed by this constructor.

    fun update_voting_power_increase(increase_amount: u64) acquires ValidatorSet {
        let validator_set = borrow_global_mut<ValidatorSet>(@aptos_framework);
        let voting_power_increase_limit =
            (
                staking_config::get_voting_power_increase_limit(&staking_config::get()) as u128
            );
        validator_set.total_joining_power +=(increase_amount as u128);

        // Only validator voting power increase if the current validator set's voting power > 0.

            assert!(
                validator_set.total_joining_power
                    <= validator_set.total_voting_power * voting_power_increase_limit
                        / 100,
                error::invalid_argument(EVOTING_POWER_INCREASE_EXCEEDS_LIMIT)
            );
        }
    }
