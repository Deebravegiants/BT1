### Title
Webhook `shop` (and `topic`/`webhook-id`) identity fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then trusts the unauthenticated `X-Shopify-Shop-Domain` header as the tenant identity passed to the app's handler. Because all webhooks for a given app share the same `api_secret_key` regardless of which merchant installed the app, any merchant who has installed the app can capture a genuinely-signed webhook delivered to their own store and replay it with the `shop` (and `topic`/`webhook-id`) header rewritten to point at a different, victim shop. The HMAC still validates (it only signs the body bytes), so the gem accepts the forged tenant binding and hands it to the host app as authentic data for the victim shop.

### Finding Description
`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` and compares it with `OpenSSL.secure_compare`: [1](#0-0) 

For webhooks, `to_signable_string` is defined to be just the raw HTTP body — none of the identifying headers (`shop`, `topic`, `webhook-id`, `api-version`) are part of the signed material: [2](#0-1) 

`Registry.process` validates only this body-bound HMAC and then constructs `WebhookMetadata` using `request.shop`, which is read straight from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` header: [3](#0-2) [4](#0-3) 

The identity binding that should hold is: `shop-header used by handler == shop that produced the signed body`. Because `shop` is not part of `to_signable_string`, the gem only proves `HMAC(secret, body)` is valid — it proves nothing about which installed shop sent that body. Since `secret` (`Context.api_secret_key`) is the app's single client secret shared across every merchant installation, any merchant is capable of producing a request that passes `HmacValidator.validate` for a body they legitimately received, then relabeling it with an arbitrary target shop domain.

This differs from the OAuth callback path, where `AuthQuery#to_signable_string` explicitly includes `shop` in the signed parameters, correctly binding shop identity to the HMAC: [5](#0-4) 
The webhook path has no equivalent binding for `shop`.

### Impact Explanation
An unprivileged internet user who is able to install the target app on their own Shopify store (a normal, free/self-serve action for public apps) receives real, correctly-signed webhooks addressed to their own shop. They can capture the raw body + valid `X-Shopify-Hmac-SHA256` value from any webhook topic they can trigger (e.g. `app/uninstalled`, `orders/create` with attacker-controlled content in their own store), then POST that exact body/HMAC pair to the victim application's webhook endpoint with the `X-Shopify-Shop-Domain` header changed to a target shop. `Registry.process` will accept it as authentic and dispatch it to the app's webhook handler tagged with the victim's shop, letting the attacker inject or spoof data attributed to a different tenant. Depending on what the host application's webhook handlers do with that data (update order/customer state, mark app as uninstalled and purge/disable the victim's data, etc.), this is a cross-tenant identity/data-integrity break.

### Likelihood Explanation
Likelihood is Medium-High: exploitation only requires becoming a merchant installer of the target app (a normal unprivileged action for any public app) and basic HTTP tooling to replay a captured request with one header changed — no access token, `client_secret`, or privileged account is required.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the material that is authenticated for webhook requests, or otherwise cryptographically/contractually bind the `X-Shopify-Shop-Domain` header to the specific shop before trusting it — e.g., cross-check `request.shop` against a shop that is known to have valid app installation/session state before invoking the handler, rather than relying solely on the body-only HMAC to imply the header's authenticity. At minimum, document prominently that `Registry.process`'s `shop` value is not authenticated by the HMAC and that host applications must independently verify the shop is a legitimate, currently-installed tenant before trusting webhook payload attribution.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com`.
2. Shopify delivers a legitimate webhook, e.g. `orders/create`, to the app with body `B` and header `X-Shopify-Hmac-SHA256: H`, where `H = Base64(HMAC-SHA256(api_secret_key, B))`.
3. Attacker captures `B` and `H` (they own the receiving server or can intercept their own inbound traffic).
4. Attacker crafts a new POST to the app's webhook endpoint:
   - Body: `B` (unchanged — HMAC only covers this)
   - Header `x-shopify-hmac-sha256`: `H` (unchanged, still valid since body unchanged)
   - Header `x-shopify-shop-domain`: `victim-shop.myshopify.com` (changed)
   - Header `x-shopify-topic`: unchanged or attacker's choice (also unsigned)
5. `ShopifyAPI::Webhooks::Request.new` parses these headers; `HmacValidator.validate` succeeds because `to_signable_string` only returns `@raw_body`. [6](#0-5) 
6. `Registry.process` invokes the registered handler with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)`, so the host application processes attacker-controlled data as if it originated from the victim shop. [7](#0-6)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,

        end
