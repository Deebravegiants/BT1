Based on my investigation, I found a concrete analog to the TradeCallee bug class in the `CallDispatcher` contract, which is the "confused deputy" primitive used throughout Hyperbridge's intent/token-bridge apps to execute predispatch/postdispatch calldata with escrowed funds.

### Title
`CallDispatcher.dispatch` has no caller restriction, letting anyone drive the shared dispatcher to spend residual token approvals or balances it holds - (File: evm/src/utils/CallDispatcher.sol)

### Summary
`CallDispatcher.dispatch(bytes memory encoded)` is a fully public, unauthenticated entrypoint that executes an attacker-supplied `Call[]` array `to.call{value}(data)` **in the CallDispatcher's own context**. It is a single, shared, redeployed-once contract (`_params.dispatcher`) referenced by `IntentGatewayV2`/`IntentsBase` for predispatch (swap-then-escrow) and postdispatch (fill-then-act) calldata, and by `HyperFungibleToken`/`WrappedHyperFungibleToken` for calldata execution on token delivery. Just like the TradeCallee finding — where funds were pulled and orders executed without verifying the caller was authorized to trigger that specific spend — `CallDispatcher.dispatch` moves/approves value on behalf of whoever holds a residual claim on the contract, without verifying the caller is the gateway or the order owner.

### Finding Description
`dispatch` has no `onlyGateway`/`onlyOwner` modifier: [1](#0-0) 

Any address can call it directly at any time with any `Call[]`. Documented usage explicitly acknowledges the contract "holds tokens temporarily during execution" and recommends predispatch/postdispatch calldata use **exact amounts rather than unlimited allowances**, precisely because of this residual-approval risk: [2](#0-1) 

The documented predispatch pattern is "a user sends ETH which the `CallDispatcher` swaps to DAI on Uniswap" — meaning the order's calldata routes an `approve` + swap through the dispatcher: [3](#0-2) 

`IntentGatewayV2._fillSameChain`/`placeOrder` transfer input assets to `dispatcher`, then invoke `ICallDispatcher(dispatcher).dispatch(order.predispatch.call)`, relying entirely on the encoded calldata to fully consume and sweep back everything: [4](#0-3) 

Because any resulting ERC20 `approve` a swap leaves on `CallDispatcher` (e.g. a router granted allowance for the input amount but only partially consumed due to price movement) is **not** reset after the sweep — only token *balances* are swept, not allowances — the residual allowance is a standing, permanent grant sitting on the shared `CallDispatcher` address. Since `dispatch` is callable by anyone, an attacker can later submit their own `Call[]` instructing `CallDispatcher` to call the approved router/spender with the attacker as the recipient, draining the leftover approved amount, or instructing `CallDispatcher` to `transfer`/`approve` away any token/ETH balance it happens to hold at call time (including ETH received via its permissive `receive()`).

### Impact Explanation
This breaks the core Gamma/TradeCallee-style invariant: funds or approvals belonging to (or routed through) a shared, unprivileged contract must never be spendable by an arbitrary, unauthenticated third party. Any residual allowance or dust balance left on `CallDispatcher` by a legitimate order's predispatch/postdispatch execution is concrete, unbacked, stealable value for whoever calls `dispatch()` first — a direct theft-of-funds primitive reachable from a single unprivileged transaction, matching the report's "Medium/High" bar for concrete theft of funds.

### Likelihood Explanation
`dispatch()` is public with no gating, so calling it costs nothing beyond gas. Its exploitability depends on a residual condition (leftover allowance/dust) actually existing on the shared `CallDispatcher`, which the protocol's own documentation flags as a real, expected risk of the calldata patterns it recommends (Uniswap swaps via predispatch, arbitrary postdispatch DeFi routing). Any order whose swap/router calldata doesn't consume 100% of an approved amount — routine with slippage-bounded swaps — creates the exploitable window, and the shared, singleton nature of `CallDispatcher` means the attacker doesn't need to interact with the victim order at all.

### Recommendation
Restrict `CallDispatcher.dispatch` to be callable only by its intended caller(s) (e.g., an `onlyGateway`/allowlist of authorized dispatcher-callers set at construction, or make it a per-order/ephemeral contract rather than a shared singleton). Additionally, have the gateway explicitly revoke any approvals it caused `CallDispatcher` to grant within the same transaction (reset allowance to zero after the calldata executes), rather than relying solely on documentation telling integrators to use exact amounts.

### Proof of Concept
1. A user places an order whose `predispatch.call` swaps input ETH to DAI via a router, granting the router a token approval from `CallDispatcher` for `amountIn`, but the router (e.g. `swapExactTokensForTokens`) only pulls the exact amount needed for the trade, leaving a nonzero residual allowance to the router address recorded against `CallDispatcher`.
2. After the transaction settles, an attacker calls `CallDispatcher.dispatch(abi.encode([Call({to: router, value: 0, data: <call router function that pulls from CallDispatcher's allowance and sends output to attacker>})]))` directly.
3. Because `dispatch` performs no caller check, `CallDispatcher` executes the call in its own context; the router (already approved) pulls the residual amount from `CallDispatcher` and delivers the swap output to the attacker-controlled address, stealing value never returned to the original user or protocol.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }

### Security

The `CallDispatcher` executes calls in its own context (not via `delegatecall`), so the HFT contract's storage is never at risk. If any call in the array reverts, the entire `onAccept` handler reverts — including the token mint/unlock. The request can then be retried by any relayer until the timeout expires. If no successful execution occurs before the timeout, the request times out and the sender is eligible for a refund on the source chain. Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution.

### Predispatch

The `predispatch` field in `Order` contains calldata to execute *before* escrowing inputs. The predispatch assets specified in `DispatchInfo.assets` are transferred to the `CallDispatcher`, the encoded calls are executed, and the resulting tokens are transferred back to the gateway for escrow. This enables swap-then-escrow patterns — for example, a user sends ETH which the `CallDispatcher` swaps to DAI on Uniswap, and the resulting DAI is escrowed as the order input.
