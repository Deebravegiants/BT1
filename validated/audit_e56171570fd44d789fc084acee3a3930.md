### Title
Withdrawal of intent escrow permanently reverts and locks funds if the beneficiary is blacklisted by the escrow token (e.g. USDC) - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentsBase._withdraw()`, which backs both `RedeemEscrow` (successful fill payout to solver) and `RefundEscrow` (cancellation refund to user), transfers escrowed ERC-20 tokens with a bare `IERC20(token).safeTransfer(beneficiary, amount)` with no failure isolation. [1](#0-0)  This is functionally the same pattern flagged in the referenced Sherlock report against `Stream.cancel()`: any beneficiary that is blacklisted by the underlying token (canonically USDC/Circle) makes the transfer revert unconditionally, and there is no try/catch to isolate that failure.

### Finding Description
`_withdraw()` is invoked from `onAccept()` in `IntentGatewayV2`/`ExtrinsicIntents` for both `RedeemEscrow` and `RefundEscrow` requests arriving via Hyperbridge, and from `onGetResponse()` for the cross-chain "cancel from source" path. [2](#0-1)  Inside `_withdraw`, for every non-native input token the function does:
```
IERC20(token).safeTransfer(beneficiary, amount);
```
with no try/catch, so if `beneficiary` is blacklisted by that token contract (e.g. USDC's `blacklist` mechanism), the `transfer` call reverts, propagating up and reverting the whole `onAccept`/`onGetResponse` call. [3](#0-2) 

Crucially, this is dispatched from `EvmHost.dispatchIncoming(PostRequest, address)`, which catches call failure only to allow message *retry*, not to make progress: on `!success` it deletes the replay-protection receipt "so it can be retried" and returns silently. [4](#0-3)  Because the revert is deterministic (the beneficiary is always blacklisted for that token), every retry attempt by any relayer will revert identically forever — the message can never be delivered.

This matches the bug class from the external report precisely: an unprivileged/permissionless actor (any user placing an intent order, or a solver filling it) can trigger a cross-chain escrow-withdrawal delivery whose destination beneficiary later becomes blacklisted (or is blacklisted at fill/cancel time), permanently freezing the corresponding escrow on the source chain. Unlike `Stream.sol`'s no-token-specific rescue limitation, here the frozen value is the full escrowed input token amount that a user/solver already deposited into `IntentGatewayV2`/`ExtrinsicIntents`.

### Impact Explanation
- **Cancellation deadlock**: If a user cancels an order (`RefundEscrow`) and their own account is (or becomes) blacklisted by the escrowed token, the refund message will never successfully deliver — their escrowed funds are permanently stuck in the gateway contract, with no rescue path shown in this base contract.
- **Fill/redemption deadlock**: The same failure mode blocks `RedeemEscrow` if the solver's beneficiary address is blacklisted, freezing the user's escrowed input tokens that were supposed to pay the solver.
- Because `EvmHost.dispatchIncoming` deletes the receipt and silently returns rather than reverting the batch, this failure is contained to a single message but is deterministically undeliverable forever — a genuine "route unable to deliver messages" / permanent freezing-of-funds condition, not merely resource exhaustion.
- No sweep/dust mechanism exists for escrowed input tokens themselves (only for protocol dust/fees, per `SweepDust`), so the funds have no alternate exit.

### Likelihood Explanation
Requires only that the escrow token (a realistic scenario for USDC-denominated intents, which is the primary stablecoin used across these bridges) implement address blacklisting and that the beneficiary address (user or solver) be blacklisted, which is entirely outside the protocol's control and can happen at any time between order placement and settlement. No malicious/privileged actor is needed on the Hyperbridge side; this is triggerable by ordinary intent flow (place → fill/cancel → cross-chain settlement) using a standard blacklist-capable token.

### Recommendation
Wrap the per-token transfer in `_withdraw` (and the analogous fee-token transfer) in a try/catch (or use a pull-based claim pattern) so that a reverting transfer to one beneficiary does not permanently block delivery of the underlying message:
```solidity
try IERC20(token).transfer(beneficiary, amount) {
} catch {
    // credit an internal "claimable" balance for beneficiary to withdraw later,
    // or escrow the failed portion for governance-assisted recovery
}
```
This mirrors the Sherlock recommendation for `Stream.cancel()` and ensures the cross-chain message still finalizes (order marked filled/cancelled) even when a leg of the transfer cannot complete due to token-level blacklisting.

### Proof of Concept
1. User places a cross-chain intent order escrowing `USDC` as input, with `order.user` set to address `U`.
2. Circle blacklists `U` (or `U` is a smart-contract wallet address that becomes non-transferable for any reason enforced at the token level).
3. User calls `cancelOrder()` on the destination or source chain, dispatching a `RefundEscrow` message back to the source `IntentGatewayV2`/`ExtrinsicIntents` instance.
4. On delivery, `EvmHost.dispatchIncoming` calls `onAccept` → `_withdraw(body, isRefund=true, finalize=true)` → `IERC20(usdc).safeTransfer(U, amount)` reverts because `U` is blacklisted. [5](#0-4) 
5. `dispatchIncoming` catches the failed call, deletes the receipt, and returns — the message is "retryable" but every subsequent relayer attempt reverts identically. [6](#0-5) 
6. The escrowed USDC remains locked in the gateway contract indefinitely; no other function path releases it to `U`.

Note: I could not verify whether a later version of `IntentGatewayV2` (e.g. the Tron variant at `evm/tron/contracts/apps/IntentGatewayV2.sol`) has an alternate mitigation, since that contract uses raw low-level `.call` with `TransferFailed()` revert rather than `safeTransfer`, exhibiting the identical unmitigated behavior. [7](#0-6)

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }
