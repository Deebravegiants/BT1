## Title
Webhook shop-domain identity spoofing via HMAC that only covers the request body, not the `shop` header - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives its `shop` (tenant identity) from the unauthenticated `X-Shopify-Shop-Domain`/`shopify-shop-domain` HTTP header, while its HMAC signature (`to_signable_string`) covers only the raw body. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC over the body and then unconditionally trusts `request.shop` to build the `WebhookMetadata` handed to the host application's webhook handler. This breaks the identity binding `shop_authenticated == shop_signed`: the HMAC never certifies which shop the payload belongs to, only that the body was produced with the app's shared `api_secret_key`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) [2](#0-1) 

Meanwhile `shop` is read straight from an HTTP header that is not part of the signed content: [2](#0-1) 

`Registry.process` validates the HMAC and then passes `request.shop` straight through to the handler without re-deriving or cross-checking it against anything cryptographically bound to that shop: [3](#0-2) 

`HmacValidator.validate` only ever checks `verifiable_query.to_signable_string` (the body for webhooks) against the app's `api_secret_key`/`old_api_secret_key` — it never incorporates the shop header: [4](#0-3) 

Because `api_secret_key` is the app's single client secret shared across *every* shop that installs the app (not a per-shop secret), any merchant who installs the app can legitimately receive a webhook with a valid `body` + `hmac-sha256` pair for their own shop. They can then replay that exact `(body, hmac)` pair to the app's public webhook endpoint while substituting the `shopify-shop-domain` header with an arbitrary victim shop's domain. `HmacValidator.validate` still succeeds because it never looks at the header, and `Registry.process` forwards the attacker-chosen `shop` value into `WebhookMetadata#shop` used by the handler.

The gem's own documentation instructs host apps to key their persistence/business logic directly off `data.shop` from `WebhookMetadata`: [5](#0-4) 

So the binding the caller relies on — "the shop this webhook body is about" == "the shop named in `data.shop`" — is not actually enforced by the gem; it silently trusts an unauthenticated header while advertising the field as verified webhook metadata (`ShopifyAPI::Webhooks::Registry.process` "will verify the request did indeed come from Shopify" per the docs): [6](#0-5) 

### Impact Explanation
This allows a low-privilege attacker (any merchant capable of installing the target app on their own store, which is an unprivileged, self-service action) to make the host application attribute attacker-controlled webhook body content to a victim shop of the attacker's choosing. Since apps commonly use `data.shop` to select which tenant's records/session to update (as shown in the gem's own example `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), this is a cross-tenant data-integrity/confidentiality issue: attacker-chosen payloads get processed under a victim shop's identity, potentially corrupting victim shop data, triggering victim-scoped side effects, or being used to probe/manipulate multi-tenant state despite the "HMAC verified" appearance.

### Likelihood Explanation
Likelihood is high for any app built on this gem that trusts `WebhookMetadata#shop` as previously "verified" (which the docs strongly imply). The only prerequisite is the ability to receive one genuine webhook delivery for an attacker-owned shop (trivial — install the target app) and the ability to POST directly to the app's public webhook endpoint with modified headers (also trivial, since that endpoint must be internet-reachable to receive Shopify's real webhooks).

### Recommendation
Include the shop domain (and/or other webhook-identifying headers like topic, api-version, webhook-id) in the HMAC-signed content, or otherwise cryptographically bind them, instead of relying on `hmac-sha256` covering only the raw body. At minimum, `ShopifyAPI::Webhooks::Registry.process` should require the caller to supply/verify the expected shop (e.g., cross-referencing an existing session for that shop) rather than trusting `request.shop` as an already-authenticated identity.

### Proof of Concept
1. Attacker installs the target Shopify app on their own shop (`attacker.myshopify.com`), a legitimate unprivileged action.
2. Shopify sends a real webhook to the app's endpoint, e.g. `products/update`, with body `B` and header `X-Shopify-Hmac-Sha256: H` where `H = HMAC-SHA256(api_secret_key, B)` and `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. Attacker captures `(B, H)` (e.g., via their own reverse proxy/logging in front of their webhook receiver).
4. Attacker crafts a new HTTP POST to the same public webhook endpoint with body `B` unchanged, header `X-Shopify-Hmac-Sha256: H` unchanged, but `X-Shopify-Shop-Domain: victim.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request.new` parses the forged headers/body; `Utils::HmacValidator.validate` succeeds because it only checks `B` against `H`, per [7](#0-6) .
6. `Registry.process` invokes the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: B, ...)`, per [8](#0-7) , and the host app processes attacker-controlled data as if it belonged to the victim shop.
