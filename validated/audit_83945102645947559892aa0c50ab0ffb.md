### Title
Webhook HMAC covers only the raw body, not the `shop-domain`/`topic` headers, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw request body only, while `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from unauthenticated HTTP headers. `Webhooks::Registry.process` validates the HMAC and then immediately trusts `request.shop`/`request.topic` to route and label the payload, without any check binding those header values to the signature.

### Finding Description
The HMAC validation flow is: [1](#0-0) 

`to_signable_string` returns only `@raw_body`; none of `shop`, `topic`, `webhook_id`, `api_version` participate in the signature computation: [2](#0-1) 

`Registry.process` validates that HMAC and then trusts the header-derived `request.shop` and `request.topic` to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

The webhook signing secret (`Context.api_secret_key`) is the app's single client secret, shared across every shop that has the app installed — it is not per-shop. This means any merchant who installs the app can receive a webhook that is *genuinely and validly HMAC-signed* for their own shop. Because the HMAC only covers `raw_body`, that merchant can replay the identical body to the app's webhook endpoint while forging the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header to name a different, victim shop. `HmacValidator.validate` (which only checks the body signature) will still pass: [4](#0-3) 

The identity binding broken is: `hmac_signing_shop (the shop whose body was actually signed by Shopify)` should equal `request.shop (the header value the library hands to the app's webhook handler)`, but the library never enforces this equality — `shop` is accepted purely from an attacker-controllable header.

### Impact Explanation
This is a cross-tenant confusion vulnerability: an app that relies on `WebhookMetadata#shop` (as provided by this gem's own `Registry.process`) to determine which merchant's data to update, store, delete (e.g. GDPR `customers/redact`, `shop/redact`, `orders/*`, `customers/data_request`) can be tricked by one of its own merchants into processing forged/attacker-chosen data under a different shop's identity. This can lead to cross-tenant data corruption, unauthorized state changes, or injection of attacker-controlled data into another merchant's account context — a Critical-tier cross-tenant access scenario per the impact taxonomy.

### Likelihood Explanation
Any user who can install the app on their own store (or a free/dev store) automatically receives correctly-HMAC-signed webhooks from Shopify. No access to `api_secret_key`, access tokens, or any privileged account is required — only a normal app installation and the ability to send an HTTP POST to the app's public webhook endpoint with modified headers. This is directly reachable through the gem's documented `Webhooks::Request`/`Webhooks::Registry.process` API path.

### Recommendation
Bind the header-derived `shop`, `topic`, and `webhook_id` values into the HMAC-verified surface, or independently authenticate `shop` (e.g., cross-check it against the session/shop associated with the app's expected webhook, or include these fields in the signable string if Shopify's webhook signing were extended to cover headers). At minimum, document prominently that `request.shop`/`request.topic` are NOT covered by the HMAC and must not be trusted as tenant identifiers without additional verification (such as confirming the shop has an active installation session before trusting webhook-attributed data).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`.
2. Shopify sends a legitimate webhook, e.g. `orders/create`, to the app's endpoint with body `B` and header `X-Shopify-Hmac-Sha256: HMAC(secret, B)` and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker captures `B` and its valid HMAC, then replays a POST to the same endpoint but with `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (same `B`, same HMAC).
4. `HmacValidator.validate(request)` in `Registry.process` succeeds because it only checks `B` against the HMAC.
5. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))` with `shop == "victim-shop.myshopify.com"`, causing attacker-controlled body content to be processed as if it originated from `victim-shop`.
