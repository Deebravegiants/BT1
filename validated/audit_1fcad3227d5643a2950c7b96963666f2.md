### Title
Consensus relayers are rewarded from the treasury for state-machine updates that are still inside their challenge period and can later be vetoed - ([File: modules/pallets/consensus-incentives/src/impls.rs])

### Summary
`pallet-consensus-incentives::on_executed` pays a `$BRIDGE` treasury reward to the relayer that submitted a `ConsensusMessage`, computed from `latest_commitment_height` immediately after `update_client` stores the new state-machine commitment - in the very same extrinsic, before the state machine's `challenge_period` has elapsed and before a fisherman has had any chance to veto it. This mirrors the reported bug class exactly: an economically-significant value (a stake cache / here, a reward payout) is derived from a state that the protocol itself treats as provisionally unconfirmed elsewhere (challenge-period gated message delivery, fisherman veto), but the reward-accounting code path does not wait for or re-check that confirmation.

### Finding Description
`update_client` in `modules/ismp/core/src/handlers/consensus.rs` verifies a consensus proof and, for every intermediate state that advances the height, immediately calls: [1](#0-0) 
storing the new `StateCommitment`, the update time, and the `latest_commitment_height` - all before any challenge period has elapsed.

Directly afterwards, in the same transaction, `pallet_ismp::Pallet::<T>::execute` invokes the configured `FeeHandler::on_executed` with the events produced by that call: [2](#0-1) 

When `pallet-consensus-incentives` is wired in as (or as part of) that `FeeHandler`, its `on_executed` recovers the relayer's signature and calls `process_message` → `calculate_reward`, which reads `host.latest_commitment_height(state_machine_id)` (the value just stored, unconfirmed) and pays out `(latest_height - baseline) * cost_per_block` from the treasury, immediately: [3](#0-2) [4](#0-3) 

Nowhere in this reward path is `challenge_period`/`verify_delay_passed` consulted - contrast this with the ordinary message-delivery path, which explicitly gates on the elapsed challenge period before it will act on a state commitment: [5](#0-4) 

Hyperbridge's own documentation confirms the challenge-period/fisherman design is exactly the "unconfirmed state" window analogous to the P-Chain confirmation gap in the report: state commitments are optimistically accepted, and fishermen may veto them for the duration of `challenge_period` before relayers/applications are meant to treat them as final: [6](#0-5) 

If a fisherman later vetoes the commitment (`veto_state_commitment` in `pallet-fishermen`, which deletes the commitment and rolls `latest_commitment_height` back): [7](#0-6) 
the relayer has already collected the treasury reward and minted reputation for a "state advance" that is subsequently proven fraudulent/invalid and removed. There is no clawback mechanism anywhere in `consensus-incentives` or `fishermen` - the reward transfer and reputation mint are irreversible.

This is structurally identical to the reported bug: (1) an internal cache/value (`nodeStakeCache` there, `latest_commitment_height`/reward here) is updated immediately upon submission of a not-yet-finalized change; (2) a downstream reward-computation path consumes that value without checking the "pending/unconfirmed" flag that the protocol maintains elsewhere (`isValidatorPendingWeightUpdate` there, `challenge_period`/veto window here); (3) the protocol *does* correctly gate on that flag in a sibling code path (`forceUpdateNodes` there, `validate_state_machine`/`verify_delay_passed` for request/response/timeout handling here), proving the omission in the reward path is an inconsistency rather than intentional design.

### Impact Explanation
A malicious or compromised consensus relayer (for any client using `pallet-consensus-incentives`, e.g. BSC, sync-committee, Arbitrum/optimistic rollup clients, Pharos) can submit a consensus update that advances `latest_commitment_height` by many blocks, collect the corresponding treasury reward (and reputation-asset mint, which also feeds collator selection) in the same transaction, and have the state commitment vetoed shortly after by a fisherman once the fraud is detected. The treasury payout and reputation mint are not reverted. This is a direct, unbacked drain of protocol treasury funds tied to state that Hyperbridge's own security model (challenge period + fishermen) says must not yet be trusted - a repeatable strategy for extracting real value from a permissionless, single-transaction action (submitting a `ConsensusMessage`).

### Likelihood Explanation
Submitting `ConsensusMessage`s is explicitly permissionless (any relayer can call `handle_unsigned`/`execute`); no staking or whitelisting is required. The reward payout is unconditional on message success and occurs synchronously with the state write, so an attacker does not need to race anyone - they simply need to get one fraudulent/borderline update through consensus-proof verification before a fisherman reacts, which the documented optimistic model with a nonzero `challenge_period` explicitly allows for by design. This is Medium-High likelihood for any deployment where `pallet-consensus-incentives` is paired with a state machine that has a configured `challenge_period` > 0 and fishermen enabled (i.e., any optimistic client such as BSC/Arbitrum/OP-stack/sync-committee rather than fully-final BEEFY).

### Recommendation
Do not pay the consensus-incentives reward (or mint reputation) synchronously inside `update_client`/`on_executed`. Instead:
- Defer reward issuance until `challenge_period` has elapsed for the relevant `StateMachineHeight` (mirroring `verify_delay_passed`/`validate_state_machine`), e.g. by recording a pending reward keyed by height and relayer, and releasing it only after confirming the commitment still exists and was not vetoed.
- Alternatively, add a clawback: if `pallet-fishermen::veto_state_commitment` fires for a height whose reward has already been paid, slash/reclaim that reward from the relayer (with reputation-asset burn as well).
- At minimum, gate `calculate_reward`'s height reads by only counting heights whose challenge period has already elapsed at the time of payout, so `latest_commitment_height` used for reward math is never behind an active challenge window.

	fn process_message(
		state_machine_height: StateMachineHeight,
		state_machine_id: StateMachineId,
		relayer_account: T::AccountId,
	) -> Result<(), Error<T>> {
		if let Some(block_cost) = StateMachinesCostPerBlock::<T>::get(state_machine_id) {
			let reward = Self::calculate_reward(&state_machine_id, block_cost)?;

			if reward.is_zero() {
				return Ok(());
			}

			T::Currency::transfer(
				&T::TreasuryAccount::get().into_account_truncating(),
				&relayer_account,
				reward,
				Preservation::Expendable,
			)
			.map_err(|_| Error::<T>::RewardTransferFailed)?;

			Self::deposit_event(Event::<T>::RelayerRewarded {
				relayer: relayer_account.clone(),
				amount: reward,
				state_machine_height,
			});

			T::ReputationAsset::mint_into(&relayer_account, reward.saturated_into())
				.map_err(|_| Error::<T>::ReputationMintFailed)?;

			LastRewardedHeight::<T>::mutate(state_machine_id, |watermark| {
				*watermark = Some(watermark.unwrap_or_default().max(state_machine_height.height));
			});
		}
		Ok(())
	}

/// Implementation of the FeeHandler trait for the RelayerIncentives pallet
impl<T: Config> FeeHandler for Pallet<T>
where
	<T as frame_system::Config>::AccountId: From<[u8; 32]>,
{
	fn on_executed(
		messages: Vec<MessageWithWeight>,
		events: Vec<IsmpEvent>,
	) -> DispatchResultWithPostInfo {
		let maybe_relayer_account = messages.get(0).and_then(|first_message| {
			if let Message::Consensus(consensus_msg) = &first_message.message {
				let data = sp_io::hashing::keccak_256(&consensus_msg.consensus_proof);
				Signature::decode(&mut &consensus_msg.signer[..])
					.ok()
					.and_then(|sig| sig.verify_and_get_sr25519_pubkey(&data, None).ok())
					.map(|pub_key| pub_key.into())
			} else {
				None::<[u8; 32]>
			}
		});

		if let Some(relayer_account) = maybe_relayer_account {
			// When a batch contains multiple `StateMachineUpdated` events for the
			// same `state_machine_id` (sequential consensus updates for the same
			// chain), `calculate_reward` reads the same persisted
			// `(latest_commitment_height, previous_commitment_height)` pair on
			// every iteration and pays the same block-span reward N times.
			// Collapse the per-state-machine event stream to the single highest
			// `latest_height` so each state machine receives one reward per
			// batch, sized by the actual span of its commitment advance.
			let mut highest_per_state_machine: BTreeMap<StateMachineId, u64> = BTreeMap::new();
			for event in events {
				if let IsmpEvent::StateMachineUpdated(update) = event {
					highest_per_state_machine
						.entry(update.state_machine_id)
						.and_modify(|h| {
							if update.latest_height > *h {
								*h = update.latest_height;
							}
						})
						.or_insert(update.latest_height);
				}
			}

			for (state_machine_id, latest_height) in highest_per_state_machine {
				let state_machine_height =
					StateMachineHeight { id: state_machine_id.clone(), height: latest_height };

				let _ = Self::process_message(
					state_machine_height,
					state_machine_id,
					relayer_account.clone().into(),
				);
			}
		}

	let update_time = host.state_machine_update_time(*proof_height)?;

```text
The `freeze_client` method is used to prove the existence of a consensus fault to an onchain consensus client. This message will be sent by offchain parties, colloquially known as _fishermen_ when they detect the existence of two conflicting views of the network backed by consensus proofs. This may arise from double signing or eclipse attacks. The consensus client after successfully verifying the validity of the conflicting views of the network will go into a frozen state. In this state it can no longer process new consensus messages as well as new requests & responses. Frozen consensus clients cannot be unfrozen and a new consensus client must be initialized through the `create_client` method instead.

## Events

The consensus handlers should emit events when a consensus proof is successfully processed or a consensus client is frozen due to consensus fault proofs. This action enables relayers responsible for transmitting requests and responses to either start relaying new eligible requests or stop their relaying tasks.

### `StateMachineUpdated`

```rust showLineNumbers
/// Emitted when a state machine is successfully updated to a new height
struct StateMachineUpdated {
    /// State machine height
    state_machine_id: StateMachineId,
    /// State machine latest height
    latest_height: u64,
}
```

A `StateMachineUpdated` event is emitted to notify network participants (both relayers and fishermen) of some newly available `StateCommitment`s for a given state machine. Relayers will wait for the configured `challenge_period` before attempting to transmit new requests & responses. While fishermen will check if these pending `StateCommitment`s describe valid states on the counterparty network. If the `challenge_period` elapses without any fraud proofs being presented, we can safely conclude that the provided `StateCommitment`s are indeed canonical.
