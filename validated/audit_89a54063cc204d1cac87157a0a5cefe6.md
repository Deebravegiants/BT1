### Title
Delegator-Deposited Vote Rewards Become Permanently Locked When a Vote Account Has No Active Delegated Stake - (File: programs/vote/src/vote_state/mod.rs, runtime/src/bank/partitioned_epoch_rewards/calculation.rs)

### Summary
`DepositDelegatorRewards` (SIMD-0123) lets any signer transfer lamports into a vote account and increments `pending_delegator_rewards` on that account, intending those lamports to be distributed to delegators as "block reward" during epoch-boundary processing. Distribution of that pool is entirely gated on the vote account having non-zero `total_active_stake` at the reward epoch. If a vote account has zero delegated/active stake, the deposited lamports are never distributed, and the `withdraw` instruction explicitly forbids withdrawing lamports below `rent_exempt_minimum + pending_delegator_rewards`, and forbids closing the account at all while `pending_delegator_rewards > 0`. This mirrors the reported bug class: a permissionless deposit into an escrow-like balance intended for future per-epoch distribution, with no recovery path when the qualifying "activity" (active stake) never materializes.

### Finding Description
`deposit_delegator_rewards` performs an unprivileged system transfer into the vote account and unconditionally increases `pending_delegator_rewards`: [1](#0-0) 

Distribution of this pool happens in `calculate_block_reward`, which is only non-zero when the vote account currently has non-zero `total_active_stake` for the rewarded epoch: [2](#0-1) 

If `total_active_stake == 0` (e.g., no stake is delegated to this vote account, or all delegated stake has been deactivated/cooled down before the epoch boundary), `calculate_block_reward` always returns `0`, and `pending_delegator_rewards` is never reduced anywhere else in the reward-commission or distribution paths (`distribute_reward_commissions`, `store_stake_accounts_in_partition`) — those paths only touch `commission_lamports`/`stake_reward`, not `pending_delegator_rewards` itself.

Meanwhile, `withdraw()` treats `pending_delegator_rewards` as an un-withdrawable reserve: [3](#0-2) 

- If `remaining_balance == 0` (attempting to close/empty the account) and `pending_delegator_rewards > 0`, the withdrawal is rejected with `InstructionError::InsufficientFunds`.
- Otherwise, the withdrawable amount is capped at `lamports - rent_exempt_minimum - pending_delegator_rewards`.

There is no instruction to decrement or reclaim `pending_delegator_rewards` directly, nor any recovery mechanism for the depositor (or the vote account's authorized withdrawer) to redeem the reserved balance if no active stake ever exists to receive it. This is confirmed by the vote-program test suite itself, which documents that the account "can't be closed when `pending_delegator_rewards > 0`": [4](#0-3) 

This is the direct analog of the reported bug class: funds are deposited for future distribution keyed to "activity" (here, active delegated stake, analogous to lending/borrowing activity in the report), and if that activity never occurs during the relevant epoch(s), the deposited lamports become permanently locked with the accounting field (`pending_delegator_rewards`) itself acting as the mechanism blocking withdrawal.

### Impact Explanation
Any account that deposits via `DepositDelegatorRewards` into a vote account that subsequently has (or already has) zero active stake will have those lamports locked in the vote account indefinitely: they cannot be distributed (block reward is always `0` for zero-stake accounts) and cannot be withdrawn (blocked by the `pending_delegator_rewards` check in `withdraw`). This is a genuine, concrete loss of value for the depositor/validator with no code path to recover the funds — matching the "Add a recovery mechanism" mitigation called out in the source report. Depositors have no way to know in advance whether stake will remain active for the vote account through the reward epoch, so this can occur under normal, non-adversarial conditions (e.g., a validator deposits ahead of expected delegation growth, or delegators withdraw/deactivate stake before the epoch boundary).

### Likelihood Explanation
`DepositDelegatorRewards` is a normal, unprivileged, permissionless instruction — any signer can call it and increase `pending_delegator_rewards` on any (v4) vote account. Vote accounts naturally can have zero currently-active delegated stake (new vote accounts, vote accounts whose delegators have withdrawn/deactivated, or accounts intentionally created without stake). No special conditions or malicious crafting are needed; this is a straightforward "no activity in the relevant epoch" scenario, directly analogous to the zero-activity-epoch precondition in the source report.

### Recommendation
Add a mechanism to reclaim or redistribute `pending_delegator_rewards` when a vote account has zero active/effective stake at an epoch boundary — for example, allow the authorized withdrawer to reclaim the deposited amount (or route it back to depositors, or roll it forward and allow the withdraw path to treat it as reclaimable) when `total_active_stake` for that vote account is confirmed to be zero for the relevant reward epoch, instead of leaving `pending_delegator_rewards` as a permanent, unconditional withdrawal floor.

### Proof of Concept
Not executable from static analysis alone; the flaw is demonstrated structurally:
1. Caller invokes `DepositDelegatorRewards` on vote account `V` with zero currently-delegated stake, incrementing `pending_delegator_rewards` by amount `X` — [1](#0-0) .
2. At the next epoch boundary(s), `calculate_block_reward` computes `0` for every stake delegated to `V` because `total_active_stake == 0` — [5](#0-4) , so `X` is never distributed and `pending_delegator_rewards` stays at `X` indefinitely.
3. The authorized withdrawer attempts `Withdraw` for any amount that would bring balance below `rent_exempt_minimum + X`, or attempts to fully close the account; both are rejected — [6](#0-5) , confirmed by the existing test `test_withdraw_pending_delegator_rewards` — [4](#0-3) .

Note: I was unable to find any code path elsewhere in the reward pipeline that decrements or otherwise reclaims `pending_delegator_rewards` outside of block-reward distribution to active stake, based on the available index; if such a path exists in code not captured by the index, it would need to be checked in a full repository clone (e.g., via a Devin session) to confirm there is truly no recovery mechanism.
