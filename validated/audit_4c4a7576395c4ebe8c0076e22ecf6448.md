### Title
Webhook `shop-domain` (and topic/api-version/webhook-id) headers are trusted for tenant identification without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then hands the *shop* identity — taken from an unauthenticated header — to the app's handler as the tenant context. This breaks the intended binding `HMAC-authenticated bytes == identity used for tenant dispatch`.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which computes `HMAC(api_secret_key, request.to_signable_string)` and compares it to the `hmac` header: [2](#0-1) [3](#0-2) 

Because only the body is signed, the `shop`, `topic`, `api-version`, and `webhook-id` values — parsed straight from HTTP headers — are never authenticated: [4](#0-3) 

Yet `Registry.process` forwards `request.shop` directly into `WebhookMetadata`, which is the only tenant-identifying field the consuming app's `WebhookHandler#handle` receives: [5](#0-4) [6](#0-5) 

Since the `api_secret_key` is shared across every shop that has installed the app, any merchant that installs the app can obtain a genuinely-signed `(raw_body, hmac)` pair for their own shop's webhook. Because `shop-domain` is not part of the signed payload, that same `(raw_body, hmac)` pair remains valid if replayed to the app's webhook endpoint with the `shop-domain` header rewritten to a *different, victim* shop. `HmacValidator.validate` will still pass (it only re-derives the HMAC from `raw_body`), but `WebhookMetadata#shop` will now report the victim shop, and the value equality the system relies on — "the shop whose webhook signature was verified" == "the shop the handler is told to act on" — no longer holds.

### Impact Explanation
Applications commonly key data/session lookups off `WebhookMetadata#shop` (e.g., to determine which merchant record/order data a webhook update applies to). An attacker who is a legitimate, unprivileged installer of the app can forge the shop identity attached to an otherwise-genuine, HMAC-valid webhook, causing the handler to act as if the payload belonged to an arbitrary victim shop — cross-tenant data confusion/access without any credential belonging to the victim.

### Likelihood Explanation
The prerequisite is only that the attacker run/install the target app on their own store (unprivileged, no special access needed) to obtain one valid `(body, hmac)` pair, then send a raw POST with a modified `shop-domain` header to the app's webhook callback endpoint. No secrets, tokens, or victim-side actions are required, making this straightforward for anyone with basic HTTP tooling.

### Recommendation
Bind the shop (and ideally topic/webhook-id) into the value that is verified, not just parsed. Either include the `shop-domain` header in the signable string that `HmacValidator` checks, or — since Shopify signs only the body by design — have `Registry.process`/the host app cross-check `request.shop` against the shop context already established for the session/webhook subscription (e.g., verify the reported shop matches a shop that currently has this webhook topic registered) before dispatching to `handler.handle`. At minimum, document that `WebhookMetadata#shop` is unauthenticated and must not be trusted for tenant selection without additional verification.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`, triggering a legitimate webhook, e.g. `orders/create`, with body `B` and header `shopify-hmac-sha256: H` where `H = HMAC_SHA256(api_secret_key, B)`.
2. Attacker captures `(B, H)` from their own webhook delivery (they own this shop, so this is normal/legitimate access to their own data).
3. Attacker crafts a new HTTP POST to the app's webhook endpoint with body `B`, header `shopify-hmac-sha256: H` (unchanged), but `shopify-shop-domain: victim-shop.myshopify.com`, `shopify-topic` unchanged.
4. `Webhooks::Request.new` parses this into a request object; `Utils::HmacValidator.validate` recomputes HMAC over `B` only and it matches `H` — validation succeeds.
5. `Registry.process` builds `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body: parsed_body, ...)` and invokes the app's `handle`, which processes attacker-controlled data under the victim shop's tenant context. [2](#0-1)

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

        end
