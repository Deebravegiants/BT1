Webhook shop-domain (tenant identity) is not covered by the HMAC signature, allowing cross-tenant event spoofing - ([File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by verifying an HMAC over the raw request body, then blindly trusts the `shop-domain` header (and `topic`/`api_version`/`webhook_id`) to attribute the event to a tenant, even though none of these header fields are included in the HMAC-signed data.

### Finding Description
`ShopifyAPI::Webhooks::Request` extracts the tenant identity from an unauthenticated header: [1](#0-0) 

Its `to_signable_string`, which is what actually gets HMAC-verified, returns only the raw body — not the shop, topic, api_version, or webhook_id headers: [2](#0-1) 

`HmacValidator.validate` computes the signature exclusively over `verifiable_query.to_signable_string` (i.e., the raw body) and compares it to the received `hmac` header: [3](#0-2) 

`Registry.process` then uses the *unauthenticated* `request.shop` to construct `WebhookMetadata` and hands it to the host app's handler as the authoritative tenant identity: [4](#0-3) [5](#0-4) 

This breaks the identity binding: `hmac_valid == true` should imply `shop == shop_that_actually_generated_this_body`, but the gem only proves `hmac_valid == true` implies `body == body_originally_signed`. The `shop` field is disjoint from what is cryptographically bound.

**Exploit path (no `client_secret`/access-token required):** An unprivileged attacker who is themself a legitimate merchant with an app installed (or who otherwise obtains one genuine, validly-HMAC-signed webhook delivery addressed to their own shop) can capture that request (raw body + valid `hmac-sha256` header) and replay it to the app's webhook endpoint while altering only the `x-shopify-shop-domain` header to name an arbitrary victim shop. Because `to_signable_string` never includes the shop header, the HMAC check in `HmacValidator.validate` still passes. `Registry.process` will then invoke the host app's `WebhookHandler#handle` with `WebhookMetadata#shop` set to the attacker-chosen victim shop, while `body`/`topic` are the attacker's own legitimate captured payload.

### Impact Explanation
Any host application that uses `WebhookMetadata#shop` to select which tenant's data to update (a common pattern — e.g., processing an `orders/create` or `app/uninstalled` webhook and mutating/deleting records keyed by `shop`) can be tricked into applying an attacker-controlled event under a different merchant's identity. This is a cross-tenant boundary break: an attacker with no relationship to the victim shop can inject fabricated webhook events attributed to that shop purely by relabeling a header, without possessing the app's `client_secret` or any victim credential.

### Likelihood Explanation
Requires only network access to the app's public webhook endpoint and possession of one genuine signed webhook body (trivially available to any merchant who installs the app themselves, since Shopify signs bodies with the app's single shared `client_secret` across all shops using that app). No secret, token, or privileged access is required to perform the header substitution.

### Recommendation
Bind the tenant/topic identity into the HMAC-verified material, or independently authenticate `shop`, `topic`, `api_version`, and `webhook_id` against a source of truth (e.g., cross-check `shop` against an active, previously-established session for that shop before dispatching to the handler) rather than trusting header values that sit outside the signed payload. At minimum, document that `WebhookMetadata#shop` is not a verified value and must not be used as a sole tenant-selection key by host applications, or change `to_signable_string`/verification to canonically include these header values in the signed data if Shopify's out-of-band HMAC scheme allows it.

### Proof of Concept
```ruby
# Attacker owns "attacker-shop.myshopify.com" and installs the app there,
# so they legitimately receive a validly-signed webhook for it:
captured_body = '{"id": 1, "note": "legit order"}'
captured_hmac_header = "<value from a real, validly-signed webhook they received>"

# Replay to the app's webhook endpoint, changing only the shop header:
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => captured_hmac_header,   # unchanged, still valid
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # attacker-controlled
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: captured_body, headers: forged_headers)

# HmacValidator.validate(request) returns true, because it only checks captured_body's HMAC,
# never the shop-domain header.
ShopifyAPI::Webhooks::Registry.process(request)
# -> host app's handler.handle is invoked with WebhookMetadata(shop: "victim-shop.myshopify.com", ...)
```
