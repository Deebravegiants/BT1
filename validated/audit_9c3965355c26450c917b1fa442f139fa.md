### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant spoofing of webhook shop attribution - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, while `shop` is read from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header. `Registry.process` validates the HMAC against the body only, then trusts the unauthenticated `shop` header when constructing `WebhookMetadata` and dispatching to the app's handler.

### Finding Description
The gem's webhook verification binds authenticity to `HMAC(secret, raw_body) == received_hmac`, as implemented in `Utils::HmacValidator.validate` and `Request#to_signable_string` (`@raw_body` only) at [1](#0-0) . The `shop` accessor, however, is derived purely from the `shop-domain` header, which is never part of the signable string: [2](#0-1) .

`Registry.process` performs `Utils::HmacValidator.validate(request)` and, on success, forwards `request.shop` unchanged into `WebhookMetadata`, which is handed to the app-defined handler: [3](#0-2) .

The intended identity binding is: `shop that the HMAC authenticates == shop the handler acts on`. Because the header is outside the signed content, this equality does not hold — the HMAC only proves "this body was signed by our `api_secret_key`", not "this body pertains to shop X". An attacker who operates their own Shopify store can receive a legitimate webhook (valid HMAC, real body) for their own shop, then replay that exact body with a forged `shop-domain` header set to a victim shop's domain. `HmacValidator.validate` recomputes the HMAC solely over `raw_body` and will still pass, since the body was unmodified, and `Registry.process` will dispatch `WebhookMetadata` claiming the victim shop's domain to the app's handler.

### Impact Explanation
Apps built on this gem are documented to key their downstream persistence/business logic directly off `data.shop` (see `docs/usage/webhooks.md`, "shop_domain: data.shop"). If an app trusts `data.shop` to select which tenant's database rows to write, requeue jobs against, or attribute webhook effects to (which the gem's own documentation instructs), a malicious merchant can inject fabricated events attributed to another merchant's shop domain by replaying their own genuinely-signed webhook payloads with a substituted `shop-domain` header. This breaks the cross-tenant boundary the HMAC is supposed to enforce and can lead to state corruption or unauthorized actions being attributed to a shop the attacker does not control — matching the "cross-tenant access" class of impact.

### Likelihood Explanation
Exploitation requires only an ordinary, unprivileged Shopify merchant account capable of installing the app and receiving legitimate webhooks for their own store (no `api_secret_key`, access token, or privileged access needed). The attacker fully controls the HTTP headers of the forged replay request; only the raw body — which they already possess unmodified from a real webhook — needs to stay intact for the HMAC check to pass.

### Recommendation
Include the `shop` (and ideally `topic`) values in the signable content used for HMAC verification, or independently validate that the `shop-domain` header corresponds to a shop with an active registration/session known to the app before dispatching to the handler. At minimum, document prominently that `data.shop` is not cryptographically bound by the HMAC check and must be cross-checked by the consuming application against a known/authorized shop list before being trusted for tenant-scoping decisions.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker.myshopify.com` and triggers a real webhook event (e.g., `orders/create`), receiving a valid request with headers `x-shopify-hmac-sha256: <valid>` and `x-shopify-shop-domain: attacker.myshopify.com`, and some `raw_body`.
2. Attacker replays the identical `raw_body` and `hmac-sha256` header to the app's webhook endpoint but changes `x-shopify-shop-domain` to `victim.myshopify.com`.
3. Server constructs `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` and calls `ShopifyAPI::Webhooks::Registry.process(request)`.
4. `Utils::HmacValidator.validate(request)` recomputes HMAC over `raw_body` only (per `to_signable_string`) — it matches, since the body is untouched — so validation succeeds despite the header being attacker-controlled.
5. `Registry.process` builds `WebhookMetadata.new(topic:, shop: "victim.myshopify.com", body:, api_version:, webhook_id:)` and invokes the app's handler, which (per the gem's documented usage pattern) acts on behalf of `victim.myshopify.com` using attacker-supplied data.
