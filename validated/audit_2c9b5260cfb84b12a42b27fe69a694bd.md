Audit Report

## Title
GraphQL `UpdateUserPassword` mutation bypasses password complexity validation enforced elsewhere - (File: core/web/resolver/mutation.go)

## Summary
`Resolver.UpdateUserPassword` in `core/web/resolver/mutation.go` never calls `utils.VerifyPasswordComplexity` before invoking `AuthenticationProvider().SetPassword`, unlike the REST-facing `UserController.UpdatePassword` in `core/web/user_controller.go`, which explicitly validates the new password's complexity before persisting it. This inconsistency lets any authenticated GraphQL user set an arbitrarily weak new password for their own account, bypassing the length/whitespace/email-exclusion policy enforced everywhere else.

## Finding Description
Password complexity is treated as a system-wide invariant: `sessions.ValidateAndHashPassword` (user creation) and `UserController.UpdatePassword` (REST password change, `core/web/user_controller.go` L226-230) both call `utils.VerifyPasswordComplexity` before the new password is hashed and stored. The underlying data-layer function `orm.SetPassword` (`core/sessions/localauth/orm.go` L298-306) performs no complexity check of its own — it hashes and stores whatever password string it is given, delegating validation entirely to callers.

`Resolver.UpdateUserPassword` (`core/web/resolver/mutation.go` L934-970) is confirmed by direct code inspection to be such a caller that omits the check: it calls `authenticateUser(ctx)` (only requires a valid session, `core/web/resolver/auth.go` L11-17, no role restriction), verifies the old password hash, clears other sessions, and calls `SetPassword(ctx, &dbUser, args.Input.NewPassword)` directly — with no `utils.VerifyPasswordComplexity` call anywhere in the function. This is a genuine divergence between the two code paths that reach the same underlying setter.

## Impact Explanation
Any authenticated user, regardless of role (`View`/`Run`/`Edit`/`Admin`, since `authenticateUser` imposes no role restriction), can set their own account password to a trivially weak value (e.g., a single character) via the GraphQL `updatePassword` mutation, while the equivalent REST endpoint correctly rejects such a request. This weakens the node's authentication posture for that account and is inconsistent with the security assumption, documented and enforced elsewhere in the codebase, that all Chainlink node user passwords satisfy `utils.PasswordComplexityRequirements`. This maps to an in-scope "node API authentication" weakening impact, though the affected account is limited to the requester's own credentials (no cross-user or privilege-escalation effect is demonstrated).

## Likelihood Explanation
High likelihood for the narrow scenario described: the only precondition is possessing valid session credentials and knowledge of the current password (trivial for a legitimate account holder acting on their own account). The path is reachable through the standard, documented GraphQL mutation surface with no additional exploitation complexity.

## Recommendation
Add `utils.VerifyPasswordComplexity(args.Input.NewPassword, dbUser.Email)` in `Resolver.UpdateUserPassword` before calling `SetPassword`, mirroring `UserController.UpdatePassword`, and return a structured `UpdatePasswordPayload` input error on failure instead of proceeding. For defense in depth, consider moving the complexity check into `orm.SetPassword` itself so all callers are protected uniformly.

## Proof of Concept
1. Authenticate as any user via the GraphQL session cookie flow.
2. Send the `updatePassword` mutation with `oldPassword` set to the correct current password and `newPassword` set to `"a"`.
3. Observe `Resolver.UpdateUserPassword` (`core/web/resolver/mutation.go` L934-970) succeeds and calls `SetPassword`, storing the weak password hash, whereas issuing the same weak password via `PATCH /v2/user/password` (`UserController.UpdatePassword`, `core/web/user_controller.go` L201-233) is correctly rejected with a 422 complexity error. func (r *Resolver) UpdateUserPassword(ctx context.Context, args struct {
	Input UpdatePasswordInput
}) (*UpdatePasswordPayloadResolver, error) {
	if err := authenticateUser(ctx); err != nil {
		return nil, err
	}

	session, ok := webauth.GetGQLAuthenticatedSession(ctx)
	if !ok {
		return nil, errors.New("couldn't retrieve user session")
	}

	dbUser, err := r.App.AuthenticationProvider().FindUser(ctx, session.User.Email)
	if err != nil {
		return nil, err
	}

	if !utils.CheckPasswordHash(args.Input.OldPassword, string(dbUser.HashedPassword)) {
		r.App.GetAuditLogger().Audit(audit.PasswordResetAttemptFailedMismatch, map[string]any{"user": dbUser.Email})

		return NewUpdatePasswordPayload(nil, map[string]string{
			"oldPassword": "old password does not match",
		}), nil
	}

	if err = r.App.AuthenticationProvider().ClearNonCurrentSessions(ctx, session.SessionID); err != nil {
		return nil, clearSessionsError{}
	}

	err = r.App.AuthenticationProvider().SetPassword(ctx, &dbUser, args.Input.NewPassword)
	if err != nil {
		return nil, failedPasswordUpdateError{}
	}

	r.App.GetAuditLogger().Audit(audit.PasswordResetSuccess, map[string]any{"user": dbUser.Email})
	return NewUpdatePasswordPayload(session.User, nil), nil
}

func VerifyPasswordComplexity(password string, disallowedStrings ...string) (merr error) {
	errMsg := ErrMsgHeader
	var stringErrs []string

	if LeadingWhitespace.MatchString(password) || TrailingWhitespace.MatchString(password) {
		stringErrs = append(stringErrs, ErrWhitespace.Error())
	}

	if len(password) < MinRequiredLen {
		stringErrs = append(stringErrs, fmt.Sprintf("password is less than %d characters long", MinRequiredLen))
	}

	for _, s := range disallowedStrings {
		if strings.Contains(strings.ToLower(password), strings.ToLower(s)) {
			stringErrs = append(stringErrs, fmt.Sprintf("password may not contain: %q", s))
		}
	}

	if len(stringErrs) > 0 {
		for _, stringErr := range stringErrs {
			errMsg = fmt.Sprintf("%s	%s\n", errMsg, stringErr)
		}
		merr = errors.New(errMsg)
	}

	return
}
