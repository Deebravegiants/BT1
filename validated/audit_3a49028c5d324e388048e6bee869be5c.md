## Analysis

I traced the class from CVE-2021-43312 (bad pointer arithmetic causing an out-of-bounds/inaccessible-memory access) onto alt.fun's real arithmetic surface: `Bonding.canGraduate`'s USD-trigger subtraction.

`canGraduate` computes:
```
realLtRaised = assetReserve - _launchTimeVirtualLtReserve(token_, pair)
``` [1](#0-0) 

where `_launchTimeVirtualLtReserve` recovers the launch-time virtual LT reserve as `Pair.k() / Token.TOTAL_SUPPLY()` [2](#0-1) , a constant fixed at launch (`k = totalSupply * virtualLtReserve` at `Pair.mint`) [3](#0-2) .

`assetReserve` is the stored `_pool.assetReserve`, which starts exactly equal to `virtualLtReserve` at launch (`addInitialLiquidity(token, totalSupply, curveSupply, virtualLtReserve)` mints with `assetReserve = virtualLtReserve`) [4](#0-3) . Buys increase `assetReserve`; sells decrease it via `Pair.swap`, which is gated only by the K-invariant `(newTokenReserve+1)*(newAssetReserve+1) >= k`, not by any floor tied to `virtualLtReserve` [5](#0-4) . Because `tokenReserve` can grow past `totalSupply` when tokens are sold back onto the curve (tokens sold in > tokens originally on curve), the K-invariant allows `assetReserve` to drop *below* `virtualLtReserve` while still satisfying K — this is not defensively checked anywhere in `Router._computeSell` or `Pair.swap`.

Once `assetReserve < virtualLtReserve`, every subsequent call to `canGraduate` performs an unchecked `uint256` subtraction that underflows and reverts with a Solidity 0.8 Panic (0x11). `canGraduate` is invoked unconditionally at the end of **every buy** inside `_executeBuy` [6](#0-5) , and directly by the permissionless `triggerGraduation` [7](#0-6) . This means once the state is reached, **every future buy on that curve reverts**, permanently freezing the token in `Lifecycle.Curve` with no way to ever graduate or trade forward (sells continue to work since `Bonding.sell` does not call `canGraduate`, but the curve's forward price discovery and its buy-side liquidity are permanently bricked, and the token can never reach the LP/graduation stage that would otherwise unlock trading on HyperSwap).

I was not able to fully confirm within the available budget whether some other invariant elsewhere in the codebase (e.g., a floor on `tokenReserve` sell-in size or an implicit cap preventing `tokenReserve` from exceeding `totalSupply` enough to drive `assetReserve` below `virtualLtReserve`) rules this out in practice — `Router._computeSell` and `Pair.swap` show no such floor, and `GraduationInvariants.t.sol`/`Router.t.sol` cover the *buy*-side overflow cap extensively but I did not find an explicit invariant test asserting `assetReserve >= virtualLtReserve` is preserved across sells (unlike the token-side invariant `tokenBalance() < tokenReserve()` which *is* explicitly tested). This asymmetry — buy side is defensively capped, sell side has no analogous floor — is the crux of the finding, but confirming the exact numeric feasibility (how large a sell relative to typical launch parameters is required) would need a live fuzz/PoC run, which I could not execute here.

### Title
Unchecked subtraction in `canGraduate`'s USD trigger permanently bricks curve buys once large sells drain `assetReserve` below the launch-time virtual LT reserve - (File: `packages/contracts/src/Bonding.sol`)

### Summary
`Bonding.canGraduate` computes `assetReserve - _launchTimeVirtualLtReserve(...)` without a floor check. `assetReserve` is not floor-protected against falling below the launch-time virtual reserve on the sell side (only the token-side virtual reserve is defensively capped on buys). Once a sell (or sequence of sells) drives `assetReserve` below `virtualLtReserve`, the subtraction underflows and reverts with a Panic on every future call, and since `canGraduate` is invoked unconditionally at the end of every `Bonding.buy` and by the permissionless `triggerGraduation`, all future buys on that token permanently revert.

### Finding Description
- `Pair.mint` fixes `k = tokenReserve_init * assetReserve_init = totalSupply * virtualLtReserve` once at launch and never updates it [3](#0-2) .
- `Bonding._launchTimeVirtualLtReserve` recovers `virtualLtReserve` on the fly as `Pair.k() / Token.TOTAL_SUPPLY()` [2](#0-1) .
- `canGraduate`'s USD leg computes `realLtRaised = assetReserve - _launchTimeVirtualLtReserve(...)` with plain unchecked-by-design Solidity 0.8 arithmetic (relying on the assumption `assetReserve >= virtualLtReserve` always) [1](#0-0) .
- `Pair.swap`'s only guard is the K-invariant `(newTokenReserve+1)*(newAssetReserve+1) >= k`; it places no floor on `assetReserve` relative to `virtualLtReserve` [5](#0-4) . A large sell increases `tokenReserve` (tokens flow back into the pair) which relaxes the K constraint enough to allow `assetReserve` to fall below `virtualLtReserve` while K is still satisfied.
- The virtual-reserve invariant that the test suite explicitly checks and relies on is only the token-side one, `tokenBalance() < tokenReserve()` [8](#0-7)  — there is no analogous, tested guarantee that `assetReserve >= virtualLtReserve` after sells.
- `_executeBuy` calls `canGraduate(tokenAddress)` unconditionally after every buy [6](#0-5) , and `triggerGraduation` (permissionless) also calls it directly [7](#0-6) . Once the underflow condition is reached, both paths revert with a Panic every time, for every caller, permanently.

This maps directly onto the CVE-2021-43312 bug class: an arithmetic/pointer computation that is assumed always valid but is not actually bounded, producing access to an "inaccessible" (here, underflowed/reverting) state that corrupts/breaks the program's normal control flow — except here the "corruption" manifests as a permanent on-chain DoS instead of a heap crash.

### Impact Explanation
This is a permanent freezing-of-funds / protocol-availability bug reachable by any unprivileged trader: after the underflow condition is triggered, the affected token's bonding curve can never accept another buy through `Zap.buy`/`Bonding.buy`, and `triggerGraduation` also permanently reverts, so the token can never graduate to the HyperSwap LP either. Buyers are locked out of that token's curve indefinitely; the token is stuck in `Lifecycle.Curve` forever with no recovery path (no owner escape hatch exists for this state). This satisfies the "permanent freezing of trader ... funds" acceptance bar in the rules.

### Likelihood Explanation
Reachable purely through `Zap.sell`/`Bonding.sell`, calls any unprivileged holder can make — no privileged role, no upgrade, no off-chain dependency. It requires accumulating enough sell volume on a given curve to push `tokenReserve` far enough above `totalSupply` that `assetReserve` is driven below `virtualLtReserve` while K still holds; whether this is trivially cheap or requires substantial capital depends on the specific launch parameters (`VIRTUAL_LIQUIDITY_USD`, curve depth) and was not numerically confirmed in this pass — flagged above as an open item requiring a fuzz/PoC to pin down exact feasibility bounds.

### Recommendation
Add an explicit floor check before the subtraction in `canGraduate` (and anywhere else `assetReserve - virtualLtReserve` is computed, e.g. `_prepareGraduationLiquidity`), e.g. `if (assetReserve <= virtualLtReserve) return false;` for the USD leg, so the function degrades gracefully instead of panicking. Additionally, consider whether `Pair.swap`/`Router._computeSell` should enforce a floor keeping `assetReserve >= virtualLtReserve` (symmetric with the existing token-side virtual-reserve invariant) to prevent the underlying state from ever reaching this condition in the first place, and add a fuzz/invariant test analogous to `test_inv_virtualReserveAlwaysExceedsRealBalance` but for the asset side across sell sequences.

### Proof of Concept
1. Launch a token via `Zap.createToken` with a modest seed; buy a substantial amount of tokens on the curve via `Zap.buy` to accumulate a large token balance while `assetReserve` sits only slightly above `virtualLtReserve` (i.e., trade the curve down toward its starting virtual asset reserve).
2. Sell a large fraction of the acquired tokens back via `Zap.sell`/`Bonding.sell`. Each sell increases `tokenReserve` and decreases `assetReserve` per `Pair.swap`'s K-invariant check only (`Pair.sol:65-79`), which does not floor `assetReserve` at `virtualLtReserve`.
3. Continue selling until `assetReserve < virtualLtReserve` (recoverable off-chain by reading `Pair.getReserves()` and `Pair.k() / Token.TOTAL_SUPPLY()`).
4. Attempt any subsequent `Zap.buy` on the same token, or call `Bonding.triggerGraduation(token)`. Both revert with a Solidity Panic (arithmetic underflow, `0x11`) inside `canGraduate`'s `assetReserve - _launchTimeVirtualLtReserve(...)` subtraction, permanently — the token's curve is bricked for buys from that point forward.

(Exact sell-volume threshold to trigger the underflow was not numerically derived here and should be confirmed with a Foundry fuzz test mirroring `test_inv_virtualReserveAlwaysExceedsRealBalance` but on the sell side before treating this as fully validated.)
