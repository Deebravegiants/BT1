### Title
Missing underflow guard on `assetReserve - virtualLtReserve` bricks `canGraduate`, permanently freezing a token's curve — ([File: packages/contracts/src/Bonding.sol])

### Summary
CVE-2023-2898 is a missing-null-check DoS: `f2fs_write_end_io` dereferences a pointer without validating it can be null, crashing the kernel for an unprivileged local user. Alt.fun's `Bonding.sol` has the same defensive-check gap in Solidity form: two `assetReserve - virtualLtReserve` subtractions are done as plain, unchecked subtraction while a functionally-identical subtraction elsewhere in the same file was explicitly hardened with a saturating pattern because the author already recognized the underflow risk.

### Finding Description
`Bonding.canGraduate` computes the real LT raised by the curve as: [1](#0-0) 

```
address pair = info.pair;
if (IPair(pair).tokenBalance() == 0) return true;
(, uint256 assetReserve) = IPair(pair).getReserves();
uint256 realLtRaised = assetReserve - _launchTimeVirtualLtReserve(token_, pair);
```

`_prepareGraduationLiquidity` (phase-1 graduation) repeats the identical pattern: [2](#0-1) 

Both subtract the immutable launch-time virtual LT reserve — recovered as `Pair.k() / Token.TOTAL_SUPPLY()` — from the live stored `assetReserve`, in plain Solidity `-`, which reverts with an unhandled Panic(0x11) on underflow.

Contrast this with `finalizeGraduation`, where the same author explicitly guards an equivalent subtraction: [3](#0-2) 

```
// Saturating subtract: a balance below `p.ltFromPair` shouldn't
// be reachable in normal operation, but we keep finalize from
// bricking on a Panic if any future code path or non-canonical
// LT briefly violates the invariant.
uint256 ltBalance = IERC20(lt).balanceOf(address(this));
uint256 protectedLT = ltBalance > p.ltFromPair ? ltBalance - p.ltFromPair : 0;
```

This shows the team is aware that reserve/balance drift below an expected floor is a real (if rare) risk that must not be allowed to Panic — yet `canGraduate` and `_prepareGraduationLiquidity` were left unguarded. `assetReserve` is stored pair state mutated only by `Pair.swap` (buy/sell flow through `Router._computeBuy`/`_computeSell` into `Pair.swap`, which enforces its K-invariant with a `+1` slack per the scan rules). Any rounding drift in that K-slack across a sell that drives `assetReserve` back toward its virtual floor can leave the stored `assetReserve` one wei (or more) below the immutable `virtualLtReserve` baseline that `_launchTimeVirtualLtReserve` recovers — a value that is fixed forever at launch and never adjusted for rounding.

Once `assetReserve < virtualLtReserve` for a given token, `canGraduate(token)` unconditionally reverts with an arithmetic Panic. Because `canGraduate` is invoked unconditionally on every trade:
- at the end of every buy via `_executeBuy` (`Bonding.sol:929`),
- at the top of every sell (`Bonding.sol:598`),
- and inside the permissionless `triggerGraduation` (`Bonding.sol:977`),

the underflow makes **buy, sell, and triggerGraduation on that token all revert permanently**. There is no admin recovery path, no retry, and no way to reach `_enterGraduating`/`finalizeGraduation` to unlock the curve-held LT or curve-held tokens. This is a full, permanent freeze of the token's curve, reachable purely through normal unprivileged buy/sell traffic that a trader or the token's own creator can trigger.

### Impact Explanation
A DoS'd curve permanently locks all curve-raised LT and all remaining curve-side tokens inside `Bonding`/`Pair` for that token — funds belonging to every trader and the creator become unreachable (no sell, no graduation, no withdrawal path exists in the current contract set). This satisfies "permanent freezing of trader, creator or LP funds."

### Likelihood Explanation
Reaching the exact one-wei (or larger) drift requires a sequence of buys/sells that lands `assetReserve` at or fractionally below the immutable virtual floor via the `Pair.swap` K-slack rounding — plausible given the codebase's own acknowledgment (the `finalizeGraduation` saturating-subtract comment) that such drift is a real, if narrow, condition. It requires no privilege, only ordinary `Zap.buy`/`Zap.sell` calls from any wallet, making it reachable by a single unprivileged trader repeatedly trading near the curve's low end.

### Recommendation
Apply the same saturating-subtraction pattern already used in `finalizeGraduation` to both `canGraduate` (`Bonding.sol:692`) and `_prepareGraduationLiquidity` (`Bonding.sol:1084`): compute `realLtRaised = assetReserve > virtualLtReserve ? assetReserve - virtualLtReserve : 0` (and analogously for `ltFromPair`), so a floor-adjacent reserve reading degrades gracefully instead of Panicking and permanently bricking the token's curve.

### Proof of Concept
1. A token launches normally via `Zap.createToken`, seeding the curve with `virtualLtReserve` baked into `Pair.k()`.
2. Multiple unprivileged traders buy and sell through `Zap.buy`/`Zap.sell` → `Bonding.buy`/`sell` → `Router._computeBuy`/`_computeSell` → `Pair.swap`, repeatedly exercising the `+1` K-slack rounding on both legs, driving the *stored* `assetReserve` down toward (and, due to rounding, marginally below) the immutable `virtualLtReserve` recovered by `_launchTimeVirtualLtReserve`.
3. The next call to any of `Bonding.buy`, `Bonding.sell`, or `Bonding.triggerGraduation` for that token executes `canGraduate(token)`, which underflows at `assetReserve - _launchTimeVirtualLtReserve(...)` and reverts with an unhandled Panic(0x11).
4. Every subsequent buy/sell/triggerGraduation call on that token now reverts identically — the curve is permanently frozen with all raised LT and remaining tokens stranded in `Bonding`, with no recovery function available.
