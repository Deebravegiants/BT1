### Title
Attacker-controlled swap route executes arbitrary pool code under the caller’s authorization - (`contracts/swap-aggregator/src/execute/mod.rs`)

### Summary
A swap payload can name an arbitrary contract as a route `pool`; the aggregator resolves that address directly from caller-controlled `assets` and invokes the selected venue method on it. [1](#0-0) [2](#0-1) 

### Finding Description
`StrategySwap` is opaque caller-supplied `Bytes` forwarded by controller strategies to `execute_strategy`. [3](#0-2) [4](#0-3) 

The aggregator decodes a program and treats each `Swap` instruction’s `idx_a` registry entry as the executable pool address, without validating that address against trusted deployments. [5](#0-4) [1](#0-0) 

Venue adapters then call attacker-selected methods on that address; for example, Phoenix invokes `pool.swap`, Aquarius invokes `pool.swap` after reading pool metadata, and Soroswap invokes `pool.get_reserves` and `pool.swap`. [6](#0-5) [7](#0-6) [8](#0-7) 

Because `execute_strategy` begins with `sender.require_auth()`, malicious pool code runs inside the transaction authorized for that sender and can place additional token transfers beneath the sender’s authorization tree. [9](#0-8) 

### Impact Explanation
An attacker can encode a route that reaches a contract controlled by the attacker and have that contract invoke `token.transfer(victim, attacker, amount)` during the swap. [1](#0-0) 

If the victim signs the simulated authorization tree containing that child transfer, the malicious route steals arbitrary wallet tokens while still returning enough `token_out` to satisfy the router and controller settlement checks. [10](#0-9) [11](#0-10) 

The same arbitrary-code primitive is reachable through the controller’s user-supplied `swap` argument in routes such as `swap_collateral`, which forwards the payload through `withdraw_and_swap_from_supply`. [12](#0-11) 

### Likelihood Explanation
No privileged role is needed to create the payload: any caller can encode an `assets` registry containing a malicious contract and reference it from a swap instruction. [13](#0-12) [1](#0-0) 

The controller validates only that the swap payload is nonempty and later checks measured input/output balances; it does not inspect or allowlist route destinations. [14](#0-13) [11](#0-10) 

Successful exploitation requires the victim to sign a simulation-generated authorization tree containing the malicious child transfer, so likelihood depends on the wallet/interface failing to reject unexpected child authorizations rather than on any privileged access. [15](#0-14) 

### Recommendation
Constrain swap execution so route-specified addresses cannot introduce arbitrary code under the sender’s authorization. [1](#0-0) 

Recommended controls:

- Maintain a governance-controlled pool allowlist keyed by `(venue, pool, token_in, token_out)` and reject any payload outside it.
- Alternatively, verify route pools against venue factory/registry contracts before dispatch.
- Require the router authorization and signed auth tree to contain only the intended input transfer, and make clients reject any additional child invocation.
- Document that an unexpected child transfer in a simulated route is invalid and must never be signed.

### Proof of Concept
1. Deploy `RoguePool` implementing `swap(...)`; inside it, call `token::Client::transfer(victim, attacker, victim_balance)` for an unrelated token held by the victim. [6](#0-5) 
2. Build a `StrategySwap` whose `assets` registry contains `RoguePool` as `idx_a`, a listed `token_in` as `idx_b`, and a listed `token_out` as `idx_c`. [16](#0-15) 
3. Have the victim call `controller.swap_collateral(caller=victim, account_id, current, amount, new, route)`, which forwards `route` to `execute_strategy`. [17](#0-16) [18](#0-17) 
4. `execute_strategy` decodes the route and dispatches the instruction to `RoguePool`; the rogue contract requests a victim token transfer as a child of the victim’s authorization. [19](#0-18) [20](#0-19) 
5. If the victim signs the expanded tree and `RoguePool` returns enough `token_out`, the router’s positive-output and exact-spend checks pass while the unrelated token transfer has already stolen wallet funds. [10](#0-9) [21](#0-20)
