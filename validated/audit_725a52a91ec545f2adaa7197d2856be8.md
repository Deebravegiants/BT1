### Title
`DirectBridge.describeWithdrawal` always reports `completed` without verifying the underlying `native_withdraw`/`ft_withdraw` receipt actually succeeded - ([File: packages/intents-sdk/src/bridges/direct-bridge/direct-bridge.ts])

### Finding Description
The claimed equality is: `WithdrawalStatus.status === 'completed'` should mean "the withdrawal's underlying on-chain effect (token delivered to `destinationAddress` on NEAR) has actually settled." Instead, `describeWithdrawal` unconditionally returns `{ status: "completed", txHash: args.tx.hash }` using only the NEAR intent-execution tx hash that was captured earlier by `createWithdrawalIdentifier`, with zero on-chain verification. [1](#0-0) 

`args.tx` is the same `NearTxInfo` passed from `createWithdrawalIdentifiers` in `withdrawal-watcher.ts`, i.e. the hash of the outer `intents.near` transaction that published the signed intents (`args.intentTx`), not a per-receipt confirmation of the nested `ft_withdraw`/`native_withdraw` cross-contract call: [2](#0-1) 

`watchWithdrawal` polls `bridge.describeWithdrawal` and, upon `status === "completed"`, immediately reports success with the returned `txHash` — it performs no independent check of receipt outcomes: [3](#0-2) 

On NEAR, `ft_withdraw`/`native_withdraw` on `intents.near` triggers an async cross-contract call to the token/receiver contract followed by a resolver callback (the standard NEP-141 refund-on-failure pattern). If that inner transfer receipt fails (e.g., receiver lacks storage registration, or panics), the resolver callback catches the failure and refunds the balance back inside `intents.near` — but the **outer** transaction (`args.tx.hash`) still finalizes as `SuccessValue`, because the outer contract method does not propagate the inner failure. Since `DirectBridge.describeWithdrawal` never inspects `FunctionCallResult`/receipt outcomes of the nested withdraw call (unlike, e.g., `poa-bridge.ts` or `hot-bridge.ts`, which query external status APIs), it cannot distinguish "outer tx succeeded, inner transfer also succeeded" from "outer tx succeeded, inner transfer failed and was refunded." Both cases report `completed` with the same `txHash`.

### Impact Explanation
An integrator relying on `describeWithdrawal`/`watchWithdrawal` to gate off-chain actions (e.g., releasing fiat, crediting a ledger, marking a support ticket resolved) will treat the withdrawal as delivered as soon as the outer `intents.near` tx finalizes, even when the actual token transfer to `destinationAddress` failed and was refunded internally. There is no failure path surfaced by this bridge (`status: "failed"` is never returned), so the integrator has no signal to reconcile or retry — matching the High-severity category "a status or hash misreport making an integrator credit or refund twice." This is repeatable for every `DirectBridge` (NEAR-landing) withdrawal where the destination account has a storage/registration issue or rejects the transfer.

### Likelihood Explanation
Preconditions are cheap and fully attacker/user-controlled: an ordinary user can withdraw NEP-141 tokens to a NEAR account that lacks storage registration for that token (or a receiver contract that panics on `ft_on_transfer`). `validateWithdrawal` only checks that explicit (named) accounts exist via `getCachedAccountExistenceCheck`; it does not guarantee the account is registered with the specific token contract's storage, nor does it protect against a receiver contract logic that rejects the transfer: [4](#0-3) 
No RPC/receipt-outcome check exists anywhere in `direct-bridge.ts` to close this gap, so the divergence is reachable on every call without special privileges.

### Recommendation
Have `describeWithdrawal` query the NEAR RPC for the full execution outcome (`receipts_outcome`) of the withdraw-related receipt(s), or otherwise inspect the resolver callback's `SuccessValue`/refund event, and return `status: "failed"` (or keep `pending`) if the underlying `ft_transfer`/`native_withdraw` did not actually complete, instead of trusting outer-transaction finality alone.

### Proof of Concept
1. Mock `nearProvider` such that `txStatus`/`tx` for `args.tx.hash` returns a `FinalExecutionOutcome` where the outer call's `SuccessValue` is present, but a nested receipt for `ft_transfer` has `status: { Failure: ... }` and a subsequent `ft_resolve_transfer` receipt refunds the amount.
2. Construct a `WithdrawalIdentifier` via `DirectBridge.createWithdrawalIdentifier` using that `tx`.
3. Call `directBridge.describeWithdrawal(wid)`.
4. Assert: the equality `status === 'completed'` currently holds regardless of the nested `Failure`, i.e. `result.status === "completed"` and `result.txHash === args.tx.hash`, even though the true on-chain state is "refunded / not delivered" — demonstrating the broken equality since no code path inspects the nested receipt outcome to flip `status` to `"failed"`.

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}
