This confirms the vulnerability. The Emporium `runAction` op-execution loop (`stack.ops.length`) is entirely decoupled from the `circomData.erc20TokenAddresses.length`-bound reconciliation loop, and nothing in `dimensionsCheck`, `_externalTransact`, or `verifyWallet` prevents a zero-length token array combined with non-empty `stack.ops` performing arbitrary external calls.

### Title
Min-circuit Emporium path allows unaudited arbitrary external calls draining Emporium's resident token balances with zero UTXO/nullifier backing - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
When `circomData.erc20TokenAddresses.length == 0` and `externalActionId == HINKAL_EMPORIUM_ACTION_ID`, `CircomDataBuilder.formInputForCircom` routes to `formInputEmporiumMin`, which is verified by the minimal `MainEVMCircuitMin` circuit that only constrains `emporiumMessage`, `timeStamp`, and `calldataHash` — no root, nullifier, or amount accounting exists. `EmporiumUpgradeable.runAction`'s operation-execution loop iterates `stack.ops.length` independently of `circomData.erc20TokenAddresses.length`, so any attacker can submit a `transact()` with an empty token array (satisfying `dimensionsCheck`) but a non-empty `EmporiumStack.ops` containing arbitrary `endpoint.call(callData)` calls, draining any ERC20 balance resident in the Emporium contract with zero balance/UTXO reconciliation.

### Finding Description
The broken equality: tokens leaving the `Emporium` contract via `op.endpoint.call{value: op.value}(op.callData)` == entries reconciled against `deltaAmountChanges`/UTXO output. Both sides should match for every token moved; here the reconciliation side is structurally empty by construction whenever `circomData.erc20TokenAddresses.length == 0`, while the op-execution side is unconstrained.

Path:
1. `dimensionsCheck` in `contracts/HinkalHelper.sol` (lines 64-171) only requires internal consistency between `dimensions.tokenNumber` and all the various `circomData` array lengths — it never forbids `tokenNumber == 0` for an external action, and `checkOnchainCreation`/`performHinkalChecks` similarly impose no minimum. [1](#0-0) 
2. `CircomDataBuilder.formInputForCircom` routes to `formInputEmporiumMin` whenever `externalActionId == HINKAL_EMPORIUM_ACTION_ID && erc20TokenAddresses.length == 0`, producing only 3 public signals (`emporiumMessage`, `timeStamp`, `calldataHash`). [2](#0-1) 
3. `MainEVMCircuitMin` only computes `message <== Poseidon(1)([messageSeed])` — it never constrains a Merkle root, a nullifier, or any spend of a UTXO. [3](#0-2) 
4. `VerifierFacade.buildVerifierId` derives the verifier solely from `(tokenNumber, nullifierAmount, outputAmount, externalActionId)`, so `dimensions = {0,0,0}` plus the Emporium action id resolves to `VerifierEVMMin0v4`, which the attacker can trivially satisfy (they only need to know their own `messageSeed`). [4](#0-3) 
5. `Hinkal.transact`'s reconciliation loop (`balanceDif`, slippage check, UTXO amount equality) is bounded by `circomData.erc20TokenAddresses.length`, i.e. it never runs when that array is empty. [5](#0-4) 
6. `EmporiumUpgradeable.runAction`'s operation loop iterates `stack.ops.length` — decoded from attacker-controlled `circomData.externalActionData.externalActionMetadata` — independently of `circomData.erc20TokenAddresses.length`, executing `op.endpoint.call{value: op.value}(op.callData)` for `invokeWallet == false`. `balancesBefore`/`balancesAfter`/`handleOut` are all bound to the (empty) `erc20TokenAddresses` array, so any token moved by `ops` that isn't in that array is never checked, never reverted, and never turned into a tracked UTXO. [6](#0-5) 
7. `verifyWallet` returns immediately without any signature check when `stack.signerAddress == address(0)`, only marking `emporiumMessage` used. [7](#0-6) 

Attacker's exact call: `Hinkal.transact(a,b,c, dimensions={tokenNumber:0,nullifierAmount:0,outputAmount:0}, circomData)` where `circomData.erc20TokenAddresses = []`, `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `externalActionData.externalActionMetadata` encodes `EmporiumStack{signerAddress: address(0), ops: [{endpoint: T, invokeWallet: false, value: 0, callData: abi.encodeCall(IERC20.transfer, (attacker, T.balanceOf(Emporium)))}]}`, and a proof from the trivially-satisfiable `MainEVMCircuitMin`. If token `T` has any resident balance in the `EmporiumUpgradeable` contract (e.g., dust/residue left over from a prior legitimate multi-token swap operation whose output token wasn't included in that transaction's `erc20TokenAddresses`), the attacker's op drains it in full, with no balance check, no slippage check, no UTXO creation, and no signature required.

Existing guards fail because: `dimensionsCheck` never enforces a minimum token count for external actions; `rootHashExists` only checks that *some* historical root exists on-chain (trivially true) since the Min circuit never binds a root to a spend; `insertNullifiers`/`insertCommitments` operate on the (also empty) `inputNullifiers`/`outCommitments` arrays so nothing is spent or created; and the balance reconciliation in both `Hinkal.transact` and `EmporiumUpgradeable.runAction` is indexed by the same zero-length array, making the check vacuously pass regardless of what `stack.ops` actually did.

### Impact Explanation
An unprivileged attacker can steal any ERC20 (or ETH via `op.value`) balance resident in the `EmporiumUpgradeable` contract that is not part of the attacker's declared `erc20TokenAddresses` for that transaction — i.e., value belonging to other users/the protocol sitting in Emporium (dust, unswept swap outputs, relay-fee remainders). This is repeatable for every token balance the Emporium contract accumulates and matches "theft of protocol/relay fees" or, if the resident balance represents another user's pending shielded value, "theft of shielded or in-flight user funds" (Critical/High depending on the nature of the resident balance).

### Likelihood Explanation
Preconditions: the `EmporiumUpgradeable` contract must hold a nonzero balance of some ERC20 (this can arise naturally from any legitimate multi-token swap whose output token isn't declared in `erc20TokenAddresses`, or relay-fee remainders, or simply from a benign user forgetting to list a token). Attacker cost is a single `transact()` call plus a locally-generated, trivially satisfiable Min-circuit proof — no signature, no whitelisted role, no victim key needed. This is fully within reach of any EOA and repeatable any time such a resident balance exists.

### Recommendation
Enforce a minimum `tokenNumber >= 1` (or otherwise forbid the Min-circuit/empty-array path) whenever `externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `stack.ops.length > 0`; alternatively, make `EmporiumUpgradeable.runAction`'s balance snapshot/reconciliation cover every token actually touched by `stack.ops` (e.g., derive the token list from `op.callData`/`op.endpoint` or require it be a superset declared in `circomData.erc20TokenAddresses`), so that any token balance change is always checked against `deltaAmountChanges`/UTXO output, regardless of the token-array length used to select the circuit/verifier.
