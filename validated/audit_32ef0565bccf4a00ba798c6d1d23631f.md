### Title
Unconstrained swap-route venue lets attacker-selected contract steal caller wallet tokens through a poisoned authorization tree - ([File: contracts/controller/src/strategies/swap.rs](contracts/controller/src/strategies/swap.rs))

### Summary

`swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, and `multiply` accept caller-controlled route bytes and forward them to the configured router while the caller has authorized the root controller invocation [1](#0-0) . The controller constrains only the router's measured input spend and positive output receipt, not which external pool contracts the route causes to run [2](#0-1) . A malicious route can therefore invoke attacker-deployed code beneath the caller's authorization, and that code can request a token transfer from the caller that appears as a signed child invocation of the original controller call [3](#0-2) .

### Finding Description

The controller's public strategy entrypoints take opaque `swap: Bytes` supplied by the caller [4](#0-3) . `process_swap_collateral` authenticates the caller, resolves their account, withdraws collateral, and sends the caller-supplied route into the shared swap path [5](#0-4) .

`swap_tokens` authorizes exactly one controller input-token transfer to the configured router and invokes `execute_strategy` with the attacker-selected route bytes [6](#0-5) . Its subsequent checks enforce only that the router cannot overspend `amount_in` and must return a positive amount of the declared output token [7](#0-6) .

The route interpreter treats an `assets` registry entry as a hop's `pool` address and dispatches execution to that address [8](#0-7) . Payload validation range-checks the pool registry index but does not require the referenced contract to belong to an approved venue registry [9](#0-8) .

Because the router runs below the caller's root authorization, arbitrary code in the route can request `token.transfer(caller, attacker, amount)` as a child invocation [10](#0-9) . If the caller signs the authorization tree produced by simulation without detecting that extra child, the host accepts the unauthorized-by-intent wallet transfer while the lending operation still completes successfully [11](#0-10) .

### Impact Explanation

An attacker can steal arbitrary wallet tokens held by a strategy caller, not merely the `amount_in` allocated to the lending operation [12](#0-11) . The malicious venue can simultaneously return enough declared output for `verify_router_output` and final account risk checks to pass, so the protocol-level settlement checks do not bound the stolen amount [13](#0-12) . This is theft of user funds and is reachable through `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, or `multiply` [14](#0-13) .

### Likelihood Explanation

The attacker needs a victim to submit an attacker-controlled route and sign the complete authorization tree returned by simulation [15](#0-14) . The route is opaque bytes, while wallet interfaces commonly present signatures at the transaction level rather than semantically proving that every nested contract invocation is expected [4](#0-3) . Because the same malicious venue can produce a fair output and hide an unrelated token transfer in the child tree, the operation appears economically normal while stealing any signed-for wallet token [16](#0-15) .

### Recommendation

Constrain route execution to governance-approved venue contracts rather than allowing arbitrary `assets` entries to be invoked as pools [9](#0-8) . The router should reject any route whose pool address is not on a venue-compatible allowlist, and the controller should additionally refuse opaque routes whose execution can introduce caller-child authorizations beyond the expected token transfers [17](#0-16) . Client-side transaction builders should also decode the simulated authorization tree and reject any child invocation other than the expected strategy token movement [18](#0-17) .

### Proof of Concept

1. Deploy a rogue contract exposing the venue swap entrypoint expected by the router [19](#0-18) .
2. Configure it with the victim address, an unrelated token held by the victim, the attacker recipient, and the full wallet balance to steal [20](#0-19) .
3. Construct a route whose hop `pool` resolves to the rogue contract while still naming normal `token_in` and `token_out` assets and a fair minimum output [21](#0-20) .
4. Have the victim call `swap_collateral(caller, account_id, current, amount, new, swap)` with that route [4](#0-3) .
5. During simulation, the rogue contract calls `token.transfer(victim, attacker, victim_balance)`; the host records that transfer as a child of the victim's `swap_collateral` authorization [10](#0-9) .
6. Submit the poisoned authorization tree; the swap completes, the victim's unrelated wallet token balance becomes zero, and the attacker receives the balance [11](#0-10) .
