### Title
Unauthenticated `RuntimeCall` dispatch via forged `message.from` in HyperFungibleToken cross-chain calldata - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
The `on_accept` handler of `pallet-hyper-fungible-token` executes an arbitrary, attacker-supplied `RuntimeCall` under a `RawOrigin::Signed` origin derived from the incoming message's `from` field, but only *requires* a cryptographic signature check when the sender chooses to supply one. When `substrate_data.signature` is `None`, the origin is derived purely from `message.from`, a field that is fully attacker-controlled on the EVM source contract, with **no proof of key ownership** enforced.

### Finding Description
`on_accept` in [1](#0-0)  decodes optional `SubstrateCalldata` from the incoming cross-chain `Message.data` and dispatches a decoded `T::RuntimeCall`. The origin used for dispatch is resolved as follows:

- If a `signature` is present, it is cryptographically verified against the `beneficiary` account (`message.to`) — this path is safe.
- If no `signature` is present, the origin is derived directly from `message.from` with **zero verification**: [2](#0-1) 

The call is then dispatched as `RawOrigin::Signed(origin)`: [3](#0-2) 

Crucially, `message.from` in the ABI-encoded `Message` struct is set by the caller of the EVM `send()` function on the source chain as `abi.encodePacked(msg.sender)`: [4](#0-3) , which is `msg.sender` of the *EVM call*. Because this is a self-set field encoded by the caller's own EVM transaction, `msg.sender` there is simply whichever address the caller chooses to use as the transaction sender — there is no cross-chain proof binding that EVM address to actual control over the corresponding **Substrate** account that `EvmToSubstrate::convert` derives. Any address on the EVM side maps deterministically to a Substrate account via zero-padding [5](#0-4) , so an attacker can trivially originate a transfer from any EVM address (including counterfactual/precompile-style addresses that have Substrate-side balances, permissions, approvals, staked collateral, or asset admin rights bound to their derived account) and have `on_accept` execute **any runtime call filtered only by `BaseCallFilter`** as that derived account — without ever proving ownership of a private key for it.

This is functionally identical in structure to the Ghostscript CVE's flaw: a privileged internal operation (`.setuserparams2` bypassing `-dSAFER`; here, dispatching a `RuntimeCall` as an arbitrary account) is gated by a check that can be omitted or is insufficiently authenticated by the caller (the optional/absent `signature` branch), letting the unprivileged submitter (anyone able to call `send()` on the EVM side and relay the message) act with the privileges of an arbitrary account.

The only mitigating control is `BaseCallFilter::contains(&runtime_call)`, which filters dispatchables blocked network-wide (e.g., during maintenance/SafeMode) but does **not** prevent impersonation of a specific account for calls the filter otherwise permits (transfers, asset operations, governance-approved actions tied to that account, proxy/multisig approvals, etc.).

### Impact Explanation
An attacker can dispatch arbitrary permitted `RuntimeCall`s as any account whose derived Substrate address (from a chosen 20-byte EVM address) they select, without holding that account's private key. Depending on what the runtime allows through `BaseCallFilter`, this can result in unauthorized transfers of funds, cancellation/consumption of the victim account's nonce-dependent actions, or interaction with pallets keyed on `ensure_signed` origin (theft or unauthorized app action), satisfying the "unauthorized app action" / "concrete theft" impact bar.

### Likelihood Explanation
High: the only requirement is that a source-chain `HyperFungibleToken` deployment be configured and relayed (an ordinary token transfer), and the calldata field is fully attacker-supplied with no signature required in the fallback path. Any unprivileged party who can call `send()` and get the message relayed can trigger this.

### Recommendation
Require a valid signature (or otherwise verifiable proof of key ownership, e.g. only allow the unsigned path when `origin == beneficiary` derived directly and disallow arbitrary `message.from`-derived origins for calldata execution) whenever `message.data` carries a `RuntimeCall`. At minimum, the unsigned fallback should never be permitted to dispatch privileged/state-mutating calls — either remove the no-signature branch entirely for calldata execution, or restrict it to a fixed, non-spoofable origin (e.g., a pallet-controlled sub-account keyed by `(source, message.from)`, not one that collides with organically-created Substrate accounts).

### Proof of Concept
1. Attacker identifies a victim account `V` (32-byte Substrate `AccountId`) whose corresponding 20-byte EVM representation is `E = last20bytes(V)`.
2. Attacker calls `HyperFungibleToken.send()` on the EVM source chain from an EOA/contract they fully control, but the `Message.from` field is set to `abi.encodePacked(E)` because that's simply `msg.sender` of that call, so the attacker uses `E` (or any EVM address they can transact from, e.g. via `CREATE2` self-deployed contract) as `msg.sender`, and sets `params.data` to an ABI-encoded `SubstrateCalldata { signature: None, runtime_call: <malicious call encoded, e.g. Balances::transfer(attacker, V's_balance)> }`.
3. Relayer delivers the message; `on_accept` decodes `message.from = E`, converts it via `EvmToSubstrate::convert` to Substrate account `V`, and dispatches `runtime_call` with `RawOrigin::Signed(V)` — executing the malicious call as if `V` itself authorized it, despite `V`'s private key never being involved.
