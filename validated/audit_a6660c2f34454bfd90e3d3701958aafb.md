### Title
Webhook `shop-domain` header (and `topic`/`webhook-id`) are trusted as tenant identity without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating an HMAC that covers only the raw request body, then unconditionally trusts the `shop-domain` (and `topic`/`webhook-id`) HTTP headers to route/attribute the payload to a specific merchant. Because the HMAC signature never binds these headers, an attacker who receives legitimate, validly-signed webhooks for their own (attacker-controlled) shop can resend the exact same signed body while substituting a victim's `shop-domain` header, producing a request that still passes HMAC validation but is attributed to the wrong tenant.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes the HMAC purely from `verifiable_query.to_signable_string`: [1](#0-0) 

For webhook requests, `Webhooks::Request#to_signable_string` returns only `@raw_body`: [2](#0-1) 

All other identifying data — `topic`, `shop`, `api_version`, `webhook_id` — is read straight out of unauthenticated HTTP headers with no cryptographic binding to the signed body: [3](#0-2) 

`Registry.process` validates the HMAC (over the body only) and then immediately uses the header-derived `request.shop` and `request.topic` to dispatch the payload to the app's registered handler as the tenant/session identity for that data: [4](#0-3) 

The equality this breaks: `shop authenticated == shop used as the tenant key`. The HMAC only proves "this body was produced with the app's `client_secret`" — it says nothing about which shop the body belongs to. `shop` (and `topic`/`webhook_id`) are "fields acted on but not covered by the HMAC," matching the specified bug class exactly.

### Impact Explanation
This is a cross-tenant data-attribution flaw: an attacker who legitimately installs the app on their own shop (Shop A) receives real webhooks with valid HMACs for Shop A's data. By replaying the identical `raw_body`+`hmac-sha256` header pair to the app's webhook endpoint while changing only the `x-shopify-shop-domain` header to Shop B, the forged request still passes `Utils::HmacValidator.validate` (since only the body is signed) but is delivered to the handler tagged as belonging to Shop B. Any host application that uses `WebhookMetadata#shop` to look up a session, update per-tenant state, or gate business logic (e.g., order/customer records, subscription state, app-uninstall handling) will process attacker-supplied data under another merchant's identity — a cross-tenant integrity violation.

### Likelihood Explanation
Exploitability requires only that the attacker install the app on their own store (a normal, unprivileged act) and capture one legitimate webhook delivery, which is trivial since any webhook subscriber sees the exact bytes and headers Shopify sends. No access token, `client_secret`, or privileged access is needed — the attacker only replays their own already-signed traffic with a substituted header value. This is fully reachable through the gem's own public webhook-processing entry point (`Registry.process`), not dependent on the host app misusing the API.

### Recommendation
Bind the `shop`, `topic`, and `webhook_id` values into the signable string used for HMAC verification (or otherwise cryptographically tie the header values to the signed payload), so that changing any of these header fields invalidates the HMAC. At minimum, document that `WebhookMetadata#shop` is not authenticated and must not be used as a tenant key without independent verification (e.g., cross-checking against a shop known to have that webhook subscription/session).

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; trigger a webhook (e.g., `orders/create`) and capture the raw HTTP request, including `x-shopify-hmac-sha256` and the raw body.
2. Resend the identical body and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but set `x-shopify-shop-domain` to `victim.myshopify.com`.
3. `Utils::HmacValidator.validate` (over `@raw_body` only, per `lib/shopify_api/webhooks/request.rb:35-43` and `lib/shopify_api/utils/hmac_validator.rb:12-31`) succeeds because the body/HMAC pair is unmodified.
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) dispatches the handler with `shop: "victim.myshopify.com"`, causing the host app to process attacker-controlled data as if it originated from the victim's store.
