### Title
Webhook `shop` and `topic` fields are not covered by the HMAC signature, allowing tenant/topic spoofing on otherwise-valid webhook deliveries - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while the `shop`, `topic`, `api_version`, and `webhook_id` fields — all read directly from unauthenticated HTTP headers — are trusted and forwarded to the handler untouched. This breaks the identity binding `hmac(signed_bytes) == hmac(bytes_acted_on)`, since the bytes verified (body only) are not the same as the bytes the app acts on (body + shop + topic).

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` validates a webhook purely via `Utils::HmacValidator.validate(request)`, which compares the received HMAC against a signature computed over `request.to_signable_string`: [1](#0-0) 

`to_signable_string` for `Webhooks::Request` is defined as just `@raw_body`: [2](#0-1) 

But `shop`, `topic`, `api_version`, and `webhook_id` are all pulled straight from HTTP headers with no cryptographic binding to the HMAC: [3](#0-2) 

Once the HMAC check passes (because the body matches), the registry hands these unauthenticated fields directly to the app's handler as the tenant identity for the event: [4](#0-3) 

This is the same class of bug flagged in the Allora report — a value that is used as an authoritative signal downstream (there: fee revenue used for weight/activation; here: `shop`/`topic` used for tenant/topic attribution) is not the value actually covered by the integrity check (there: `msg.Amount` passed instead of the real revenue delta; here: header fields not included in the signed payload). Notably, this codebase's own OAuth `AuthQuery` class demonstrates the correct pattern by including `shop` explicitly inside `to_signable_string`: [5](#0-4) 

showing that `Webhooks::Request` deviates from the gem's own established binding convention for that same `shop` field.

Because Shopify computes the HMAC over `(secret, raw_body)` only (per Shopify's webhook spec, which this gem faithfully mirrors), any request whose body was legitimately HMAC-signed by Shopify's servers for the app's `client_secret` — regardless of which shop/topic it was originally destined for — will pass `HmacValidator.validate` even if the `x-shopify-shop-domain` or `x-shopify-topic` headers are altered afterward, since those headers are never fed into the signature computation on the sending or receiving side.

### Impact Explanation
An app operator that runs one shared endpoint for multiple installed shops (the standard multi-tenant Shopify app model this gem is built for) relies on `request.shop` from `Registry.process` to route the webhook payload to the correct tenant's data store, session lookup, or business logic. Since `shop` is not bound to the HMAC, an unprivileged actor who can capture or replay a legitimately-signed webhook body (e.g., from their own installed dev shop, or via a MITM/logging exposure of a webhook delivery not otherwise protected) can resubmit that exact body with a forged `x-shopify-shop-domain` header naming a different, victim shop. The HMAC check still succeeds (it only checks the body), and the handler receives `WebhookMetadata` attributing attacker-controlled body content to the victim shop — a cross-tenant data-integrity/confusion violation in a multi-tenant app built on this gem's documented API.

### Likelihood Explanation
Exploitation requires the attacker to already possess one genuinely-signed webhook body (obtainable from their own tenant/shop, which is an "unprivileged internet user" position relative to other tenants of the same app) and the ability to POST to the app's registered webhook endpoint with modified headers — no `api_secret_key`, access token, or privileged credentials are needed. The bug is a direct, reachable design flaw in `to_signable_string`, not a theoretical concern, and requires no host-application misuse beyond following this gem's documented `Registry.process` usage exactly as shown in the gem's own docs.

### Recommendation
Include the `shop`, `topic`, and other trusted-attribution headers inside the HMAC-signed payload used for verification (i.e., extend `to_signable_string` to canonically incorporate `shop`/`topic`, mirroring `AuthQuery#to_signable_string`), or otherwise cryptographically bind these header values before they are surfaced to the handler via `WebhookMetadata`.

### Proof of Concept
1. App has one endpoint handling webhooks for many installed shops, per `docs/usage/webhooks.md`'s documented `Registry.process` pattern.
2. Attacker installs the app on their own shop A and captures a legitimate webhook delivery (raw body `B`, valid `hmac-sha256` header `H`, `shop-domain: A.myshopify.com`).
3. Attacker resends the identical body `B` and header `H` to the same endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `HmacValidator.validate` recomputes HMAC over `B` only [2](#0-1)  — it matches `H`, so validation passes.
5. `Registry.process` invokes the handler with `shop: request.shop` = `"victim.myshopify.com"` and the attacker-controlled body `B`, causing the app to process/store attacker data under the victim tenant's identity. [4](#0-3)
