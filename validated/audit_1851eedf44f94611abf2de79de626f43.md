### Title
Underage-Signup Safeguard Never Enforced — `self_serve_ask_op_qr_for_possibly_underaged` Config Is Dead / Unwired - ([File: src/config.rs])

### Summary
`Config` defines `self_serve_ask_op_qr_for_possibly_underaged` (and its companion timeout) as the control that is supposed to force an operator-assisted QR/age-verification step whenever the biometric pipeline flags a possibly-underage person during a self-serve signup. This mirrors the `Fintroller.isRedeemHTokenAllowed` pattern in the external report: a backend-controlled permission/gating flag is declared, deserialized, and documented as an enforcement switch, but — unlike `ignore_user_centric_signups`, `pcp_v3`, `user_qr_validation_use_full_operator_qr`, and `block_signup_when_no_internet`, which are all read out of `Config` and consumed at a decision point — this flag and its timeout are never read anywhere in the signup/plan execution path.

### Finding Description
`Config::self_serve_ask_op_qr_for_possibly_underaged` and `self_serve_ask_op_qr_for_possibly_underaged_timeout` are declared with clear intent in the doc comments: "Ask the operator for a QR code when a possibly underaged person is detected" / "How long to wait for the operator to scan the QR code when a possibly underaged person is detected." [1](#0-0) 

The field is populated from the backend response and given a default value, exactly like every other enforced flag in the same struct (e.g. `ignore_user_centric_signups`, `pcp_v3`, `block_signup_when_no_internet`): [2](#0-1) [3](#0-2) 

The backend response schema also carries the field, confirming it is meant to be operator-controlled server-side, exactly like `Fintroller`'s `isRedeemHTokenAllowed` being controlled by the protocol admin: [4](#0-3) 

Contrast this with flags that actually gate behavior in `do_signup`/`biometric_capture`, all of which are destructured out of `Config` and checked with an `if`: [5](#0-4) [6](#0-5) 
`proceed_with_biometric_capture` similarly reads `self_serve`, `self_serve_app_skip_capture_trigger`, and `self_serve_app_capture_trigger_timeout` out of `Config` and acts on them: [7](#0-6) 

A grep across the whole crate shows `self_serve_ask_op_qr_for_possibly_underaged` only appears in `src/config.rs` and `src/backend/config.rs` — it is never read by `MasterPlan`, `do_signup`, `biometric_capture`, `detect_face`, or any self-serve/orb-relay flow. There is a related message type, `self_serve::orb::v1::AgeVerificationRequiredFromOperator`, but this too only appears in the message-encoding boilerplate in `orb-relay-client/src/lib.rs`; it is never constructed or sent from `src/plans/mod.rs` or anywhere else in the signup flow. The wire message exists, the config flag that should trigger sending it exists, but the code path that would call `orb_relay.send(self_serve::orb::v1::AgeVerificationRequiredFromOperator{})` after a possibly-underage detection is absent. [8](#0-7) 

This is the same bug class as the reported `HToken.redeem()` issue: a protection flag defined for exactly one purpose (gate a sensitive operation — redemption there, unsupervised biometric enrollment of a possibly-underage person here) is present in the data model but is a "leftover" that the enforcement code forgot to check, so the gate has no effect regardless of its configured value.

### Impact Explanation
If this flag is truly unwired (as the crate-wide search indicates), then in self-serve mode a possibly-underage person detected by the person/age classifier is never redirected to an operator-assisted age-verification/QR flow, no matter how the backend configures `self_serve_ask_op_qr_for_possibly_underaged`. This can result in unsupervised biometric capture and enrollment of a minor — a compliance and safety control silently bypassed, analogous to a financial protocol silently allowing a disallowed redemption. It is an unprivileged-user reachable path since it's the ordinary self-serve signup flow that any signee (including a minor) would trigger.

### Likelihood Explanation
Likelihood is uncertain from the indexed portion of the codebase. The index does not show the code that performs the "possibly underage" detection and decision itself (e.g., a person-classifier / face-identifier consumer that would be the natural place to check this flag) — only its declaration in `Config`/`backend::config::Config` and the unused message enum variant. It's possible that logic lives in a file/module not captured by the index (index size limits), in which case the flag might be consumed elsewhere not surfaced by search. I was not able to find any call site consuming `self_serve_ask_op_qr_for_possibly_underaged` anywhere in the repository via grep, which strongly suggests it is dead configuration, but I cannot rule out with full certainty that consuming code exists outside indexed content.

### Recommendation
Audit the self-serve signup pipeline (person/age classification stage) to confirm whether `self_serve_ask_op_qr_for_possibly_underaged` and `self_serve_ask_op_qr_for_possibly_underaged_timeout` are read and enforced. If they are not, wire this flag into the flow so that when a possibly-underage person is detected during self-serve capture, the orb (a) sends `self_serve::orb::v1::AgeVerificationRequiredFromOperator` over `orb_relay`, (b) blocks biometric capture/enrollment until the operator provides a QR code or the configured timeout expires, and (c) fails the signup (or forces the app-initiated non-self-serve path) if the operator does not respond in time — mirroring how `self_serve_app_skip_capture_trigger`/`proceed_with_biometric_capture` already gate capture start.

### Proof of Concept
Given a Devin session with repository access, the concrete PoC would be:
1. Configure the backend orb-config response with `SelfServeAskOpQrForPossiblyUnderaged: true` and a short timeout.
2. Run a self-serve signup (`self_serve: true`) using CLI test hooks (`--user-qr-code`, `ui-test-successful-signup` feature) with a biometric input directory / mocked classifier output that would be flagged as "possibly underage".
3. Observe that `do_signup`/`biometric_capture` proceeds directly to capture and enrollment without ever sending `AgeVerificationRequiredFromOperator` or pausing for operator QR scan — because no code path reads `self_serve_ask_op_qr_for_possibly_underaged`.

I could not execute this PoC without tool/filesystem access beyond static search; a background Devin session with full repo and test-harness access would be needed to confirm end-to-end absence of enforcement and to implement the fix.
