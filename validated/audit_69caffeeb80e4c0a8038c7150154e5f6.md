### Title
Webhook `shop-domain`, `topic`, and `webhook-id` headers are trusted for tenant/event identity but are not covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop`, `topic`, `webhook_id`, and `api_version` entirely from HTTP headers, while `to_signable_string` — the value that `Utils::HmacValidator` actually authenticates — returns only the raw request body. `Registry.process` accepts any request whose body HMAC validates and then hands the unauthenticated `shop`/`topic`/`webhook_id` values straight to the host app's `WebhookHandler` as trusted tenant/event identifiers.

### Finding Description
`Utils::HmacValidator.validate` computes `OpenSSL::HMAC.hexdigest(sha256, secret, verifiable_query.to_signable_string)` and compares it to the supplied `hmac` [1](#0-0) .

For webhooks, `Request#to_signable_string` returns only `@raw_body` [2](#0-1) ,
while `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers with no cryptographic binding to the signature: [3](#0-2) .

`Registry.process` only checks the body HMAC and then forwards the unauthenticated header-derived `shop`/`topic`/`webhook_id` fields to the app's handler as `WebhookMetadata`: [4](#0-3) .
`WebhookMetadata.shop` is a plain `String` constant with no independent verification against the signed payload: [5](#0-4) .

**Identity binding broken:** the gem implicitly claims `hmac-verified(raw_body) == authenticated(shop, topic, webhook_id)`, but in reality only `hmac-verified(raw_body)` holds; `shop`, `topic`, and `webhook_id` are unauthenticated header bytes accepted verbatim.

### Impact Explanation
An attacker who can obtain **any** single legitimately-signed webhook body+HMAC pair for the app (e.g., by installing the app on their own store and triggering an event, which produces a valid `(raw_body, hmac)` for a topic they control) can replay that exact body/HMAC to the app's webhook endpoint while substituting the `shopify-shop-domain` header (and/or `shopify-topic`, `shopify-webhook-id` headers) to point at a victim shop. `Registry.process` will treat this as a valid, authenticated webhook for the spoofed shop/topic, because the signature check never touches the headers. Since apps are expected to use `WebhookMetadata#shop` to select the tenant record to act on, this enables cross-tenant confusion: data or side effects intended for the attacker's own shop get attributed to and applied against a different merchant's tenant record (e.g., app/uninstalled-style state changes, order/customer data processing, or redact-topic handling being fired for the wrong shop). This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Requires only unprivileged network access to the app's public webhook endpoint plus the ability to obtain one legitimately signed payload of the desired shape (trivially available by installing the app on an attacker-controlled development/free store and capturing the resulting webhook). No access to `api_secret_key`, access tokens, or the merchant's credentials is required — only header manipulation on an unauthenticated HTTP POST. This makes the likelihood reasonably high for any app whose HTTP layer allows raw header injection (e.g., a naive Rack/Sinatra endpoint that passes through client-supplied headers rather than fixed values from the platform's proxy).

### Recommendation
Include `shop`, `topic`, and `webhook_id` (or at minimum `shop` and `topic`) in the HMAC-signed payload used by `to_signable_string`, or independently verify these header values against an authenticated channel (e.g., cross-check `shop` against a value obtained via a signed/mTLS-verified delivery channel, or require the host application to validate `shop` against its own known installed-shop list before trusting it). At minimum, document prominently that `WebhookMetadata#shop`/`#topic`/`#webhook_id` are **not** cryptographically bound to the HMAC and must not be treated as a verified tenant identifier without additional application-level cross-checks.

### Proof of Concept
1. Attacker installs the target app on an attacker-controlled shop `attacker.myshopify.com` and triggers a webhook (e.g., `orders/create`), capturing the raw POST body `B` and the valid `x-shopify-hmac-sha256` header `H` (computed by Shopify over `B` using the app's `client_secret`, unknown to the attacker but included verbatim in Shopify's legitimate delivery).
2. Attacker replays the identical body `B` and header `H` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com` (and optionally alters `x-shopify-topic` / `x-shopify-webhook-id`).
3. `ShopifyAPI::Webhooks::Request.new` parses these headers uncritically [6](#0-5) .
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only hashes `@raw_body` (`B`) — still matches `H` — and passes [7](#0-6) .
5. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", topic: ..., body: B, ...)` and performs its business logic against the victim shop's tenant record, even though the payload actually originated from the attacker's own shop event.

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
