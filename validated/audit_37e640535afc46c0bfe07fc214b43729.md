### Title
Webhook HMAC validation covers only the request body, allowing cross-tenant/topic impersonation via header forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook request as authenticated once its HMAC validates, but the HMAC signature is computed over the raw request body only. The `shop-domain`, `topic`, `webhook-id` and `api-version` values that the handler acts on are read straight from HTTP headers and are never included in the signed bytes, so they can be freely forged by anyone able to send a POST to the app's webhook endpoint while reusing a body/HMAC pair the attacker legitimately obtained.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `topic`, `shop`, `api_version`, and `webhook_id` are read verbatim from attacker-controllable HTTP headers (`x-shopify-topic`, `x-shopify-shop-domain`, `x-shopify-api-version`, `x-shopify-webhook-id`), with no cryptographic binding to the body: [2](#0-1) 

`Utils::HmacValidator.validate_signature` computes the HMAC solely from `verifiable_query.to_signable_string`, i.e. the raw body: [3](#0-2) 

`Registry.process` uses this body-only validation as its sole authentication check, then dispatches the handler using the unauthenticated `topic` and `shop` values pulled from headers: [4](#0-3) 

The identity binding that should hold is:
`hmac_valid(body) == true` **should imply** `(shop, topic, webhook_id)` in the request are the same `(shop, topic, webhook_id)` Shopify used when generating that HMAC.

In this implementation that equality does not hold: `hmac_valid(body)` only proves the body bytes were signed with the app's `api_secret_key` at some point (by Shopify, for *some* shop/topic combination) — it says nothing about which shop or topic the caller is now claiming. Because the app's `api_secret_key` is shared across every shop that has installed the app (it is not a per-shop secret), any merchant/attacker who has legitimately received one real webhook for their own shop (any topic, any payload) can capture that `(raw_body, hmac)` pair and resend it to the app's public webhook endpoint with forged `x-shopify-shop-domain` and `x-shopify-topic` headers pointing at a different tenant or at a sensitive topic (e.g. `customers/redact`, `shop/redact`). `HmacValidator.validate` will still pass because the signed string is identical, and `Registry.process` will invoke the handler believing the request is an authentic, Shopify-issued webhook for the forged shop/topic.

### Impact Explanation
This breaks tenant isolation for any multi-tenant Shopify app built on this gem: an attacker who is simply a legitimate but malicious installer of the app for their own shop can forge webhook headers to make the app believe a webhook (with attacker-chosen `shop` and `topic` values) originated from another merchant's shop or represents a different (potentially privileged/compliance) event. Depending on how the host app's `WebhookHandler` implementations trust `WebhookMetadata#shop`/`#topic` (which is the documented, expected usage pattern), this enables cross-tenant data access/mutation or triggering of mandatory compliance handlers (`customers/redact`, `shop/redact`) against a victim shop — satisfying the "cross-tenant access" Critical impact bucket. No possession of `api_secret_key`, access tokens, or any other credential is required beyond being one of the app's own (potentially malicious) merchants, or anyone who otherwise obtains one valid `(body, hmac)` pair.

### Likelihood Explanation
Likelihood is high for any app that installs on multiple shops: obtaining a single valid `(raw_body, hmac)` pair only requires triggering (or waiting for) one ordinary Shopify webhook delivery to the attacker's own shop — a routine, self-serve action. Forging the `x-shopify-shop-domain`/`x-shopify-topic` headers on a replayed HTTP POST requires no special access. The vulnerability is entirely in this gem's `Request`/`HmacValidator`/`Registry` code path, which is documented and expected to be the primary authentication mechanism for inbound webhooks.

### Recommendation
Include `topic`, `shop-domain`, and `webhook-id` (in addition to the body) in the value that is HMAC-verified, or otherwise cryptographically bind them (e.g., verify them against Shopify's API using the webhook_id, or require the caller to independently confirm the `shop` value against a known, previously-authenticated session/shop before trusting `WebhookMetadata`). At minimum, document prominently that `shop`/`topic`/`webhook_id` are unauthenticated and must not be trusted for authorization decisions without additional verification.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com` and `victim-shop.myshopify.com` (same `api_secret_key` shared for both, as is standard for Shopify apps).
2. Attacker (owner of `attacker-shop`) receives (or triggers) any real webhook delivery to their app endpoint, capturing the raw POST body `B` and the `X-Shopify-Hmac-Sha256` header value `H` (valid because `H = HMAC-SHA256(api_secret_key, B)`).
3. Attacker POSTs the identical body `B` and header `X-Shopify-Hmac-Sha256: H` to the same webhook endpoint, but sets:
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
   - `X-Shopify-Topic: customers/redact` (or any topic registered by the app)
4. `ShopifyAPI::Utils::HmacValidator.validate` recomputes the HMAC over `B` only, matches `H`, and returns `true`. [5](#0-4) 
5. `Registry.process` accepts the request as authentic and calls the registered handler with `shop: "victim-shop.myshopify.com"`, `topic: "customers/redact"`, and the attacker-controlled body `B`, even though Shopify never issued a webhook with that shop/topic combination. [4](#0-3)
