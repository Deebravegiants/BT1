### Title
Webhook `shop-domain` and `topic` headers are trusted for tenant routing but are not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw JSON body only, while the shop, topic, webhook-id and api-version values used by `ShopifyAPI::Webhooks::Registry.process` to route and attribute the webhook are read from HTTP headers that are never included in that signed content. Any party who can obtain one valid `(body, hmac)` pair signed with the app's shared `api_secret_key` — including any merchant who has installed the app on their own store and can trigger an ordinary webhook — can replay that exact body/HMAC pair to the app's public webhook endpoint with arbitrary `x-shopify-shop-domain` and `x-shopify-topic` headers, and it will still pass `HmacValidator.validate`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all pulled from headers that are completely outside that signed string: [2](#0-1) 

`Registry.process` validates the HMAC against the body only, then trusts the header-derived `request.shop` / `request.topic` to dispatch the payload to the registered handler: [3](#0-2) 

`HmacValidator.validate` / `validate_signature` only ever hashes `verifiable_query.to_signable_string`, i.e. the raw body, against the app's `api_secret_key` (the app-wide secret, shared across every shop that installs the app, not shop-specific): [4](#0-3) 

This breaks the identity binding the report's bug class describes: the check that is actually performed (`HMAC(secret, raw_body)` matches) is not the same as the identity the application relies on (`request.shop` / `request.topic`, taken from unauthenticated headers). Formally, the code assumes:

`valid_hmac(body, hmac) ⇒ (shop, topic) are authentic`

but the code only proves `valid_hmac(body, hmac)`; it never binds `shop`/`topic` into the signed content, so the equality the code needs — `signed(shop, topic, body) == received(shop, topic, body)` — never holds. Any shop that installed the app shares the same `api_secret_key`, so any such (unprivileged, in the sense of not needing the app's owner credentials) merchant can capture a legitimate `(body, hmac)` pair from their own store's webhook traffic and replay it with a forged `shop-domain`/`topic` header to the shared webhook endpoint. The receiving app's handler will process the payload as if it originated from the spoofed shop/topic.

### Impact Explanation
This is a cross-tenant confusion vulnerability: a party with access to only their own store's legitimate webhook traffic can make the app process/attribute a webhook event as belonging to a different shop, or under a different topic than what was actually delivered by Shopify. Depending on the handler logic, this can lead to data being written to, or actions taken against, the wrong tenant's records — matching the "cross-tenant access" high/critical impact category, since the shop identity used downstream is not actually authenticated by the HMAC despite the code assuming it is.

### Likelihood Explanation
Likelihood is high for any actor who already has legitimate access to one shop using the target app (a very low bar — any merchant who installs a public app) because the `api_secret_key` used for HMAC verification is shared across all installations of the app, and the vulnerable fields (`shop-domain`, `topic`, `webhook-id`, `api-version`) are freely attacker-controlled HTTP headers that require no forgery of the secret itself.

### Recommendation
Include the header-derived identity fields (`shop`, `topic`, `webhook_id`, `api_version`) in the signed content used for HMAC verification, or otherwise cryptographically bind them to the body (e.g., verify them against Shopify's known/expected values for the specific delivery, or require an additional authenticated channel to confirm shop/topic), so that the HMAC check actually authenticates the fields the registry uses to route and attribute the webhook.

### Proof of Concept
1. Install the target app on an attacker-controlled/owned shop `attacker.myshopify.com` and trigger any registered webhook topic (e.g. `orders/create`) to capture a legitimate `raw_body` and its `x-shopify-hmac-sha256` value (both signed with the app's shared `api_secret_key`).
2. POST that exact `raw_body` to the app's public webhook endpoint, keeping the captured `x-shopify-hmac-sha256` header unchanged, but set:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - `x-shopify-topic: <any topic the app has a handler for>`
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks the (unmodified) `raw_body` against the shared secret — see [5](#0-4) .
4. The handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` using the attacker-forged header values — see [6](#0-5) , causing the app to process the replayed payload as though it came from `victim-shop.myshopify.com` under the spoofed topic.

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
