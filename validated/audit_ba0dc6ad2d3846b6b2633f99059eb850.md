### Title
Reentrancy in Tron `IntentGatewayV2.withdraw()` — external token/ETH transfer before escrow balance decrement - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron deployment of `IntentGatewayV2` (`evm/tron/contracts/apps/IntentGatewayV2.sol`) settles cross-chain intent escrow via `withdraw()`, called from `onAccept()` when a `RedeemEscrow`/`RefundEscrow` message is delivered by the ISMP host. `withdraw()` performs the beneficiary's ETH/ERC-20 transfer **before** decrementing the corresponding `_orders[commitment][token]` escrow balance, and transfers accumulated transaction fees before deleting the fee entry — the exact "check-then-external-call-then-effect" ordering flagged in the referenced Olympus `WstethLiquidityVault._withdraw()` report. This is the same bug class the main EVM `IntentsBase._withdraw()` (`evm/src/apps/intentsv2/IntentsBase.sol`) has already fixed by decrementing state before the external call — but the Tron contract still has the vulnerable ordering, and unlike the main EVM `IntentGatewayV2` (which guards `fillOrder`/`cancelOrder` with `ReentrancyGuardTransient`), the Tron contract has **no reentrancy guard anywhere**.

### Finding Description
`onAccept` dispatches to `withdraw()`: [1](#0-0) 

`withdraw()` sets `_filled[commitment] = beneficiary`, then for each escrowed token performs the external call (native ETH `.call{value:}` or `token.call(transfer)`) and only afterwards decrements `_orders[body.commitment][token]`: [2](#0-1) 

The transaction-fee payout follows the same unsafe order — external `feeToken.call(transfer)` happens before `delete _orders[body.commitment][TRANSACTION_FEES]`: [3](#0-2) 

`beneficiary` is attacker-influenced: for a `RedeemEscrow` it is the solver who filled the order (`msg.sender` on the destination chain, stamped into the withdrawal request); for `RefundEscrow` it is the order's original `user`. Either actor can be a contract that executes arbitrary code on receiving the ETH transfer or via a callback-capable ERC-20/fee-token transfer hook.

Contrast with the (already patched) main EVM path, `IntentsBase._withdraw()`, which decrements the escrow **before** the external transfer (correct CEI order): [4](#0-3) 

The project's own regression test suite documents that this exact reentrancy class was fixed for the main same-chain fill path (`_fillSameChain`) by moving the `_filled[commitment]` write and, implicitly, all effects before the external calls — but this fix and the accompanying analysis were never applied to `withdraw()` in the Tron contract: [5](#0-4) 

The Tron `IntentGatewayV2` contract has no `ReentrancyGuard`/`ReentrancyGuardTransient` inheritance at all (confirmed absent from imports and inheritance list), so nothing else in the call stack blocks a reentrant call: [6](#0-5) 

### Impact Explanation
A malicious beneficiary (solver or order owner) that is a smart contract can re-enter during the ETH `.call` or a hookable-token `transfer` before `_orders[commitment][token] -= amount` executes. Because `withdraw()` is only reachable from `onAccept`/`onGetResponse` (both `onlyHost`), the most direct exploitation vector is a fee/output token with a transfer hook (ERC-777-style or a custom callback token) that calls back into any externally reachable, non-reentrancy-guarded gateway function while the stale (not-yet-decremented) escrow balance is still readable/usable, or — more critically — if any batched/looped delivery path in the handler allows a second `onAccept`/`onGetResponse` for the same commitment to be processed within the same external call before the first `withdraw()` finishes. In either case the result is double-spend of escrowed input tokens/fees for the same order commitment, i.e. theft of escrowed funds/permanent shortfall for the protocol or other users. This qualifies as concrete theft/freezing of funds via unsound settlement accounting on the intent escrow path.

### Likelihood Explanation
Medium-to-High: reaching `withdraw()` requires a relayed ISMP message to be delivered by the host (`onlyHost`), i.e., a single relayed proof from an attacker acting as (or colluding with) the filling solver / order owner, both of which are unprivileged, attacker-controllable roles by design of the Intent Gateway. The precondition of a hookable token being one of the escrowed input/fee assets, or a reentrant delivery path in the handler, is required to trigger the callback — this narrows likelihood somewhat, but the missing CEI ordering combined with total absence of reentrancy protection makes this a real, non-speculative code defect distinct from (and less defended than) the main EVM contract, which already applies the correct effects-before-interactions ordering.

### Recommendation
Mirror the fix already applied in `IntentsBase._withdraw()`: decrement `_orders[body.commitment][token]` (and `delete _orders[body.commitment][TRANSACTION_FEES]`) **before** performing the external ETH/ERC-20 transfer in the Tron `withdraw()` function. Additionally, add a reentrancy guard (e.g., `ReentrancyGuardTransient`) to the Tron `IntentGatewayV2` contract's externally reachable entry points, consistent with the main EVM `IntentGatewayV2`, to defend against any transitive reentrancy paths through hookable tokens or handler batching.

### Proof of Concept
1. Attacker crafts an order whose escrowed input token (or `feeToken`) is a token contract they control that implements a transfer hook (e.g., `_beforeTokenTransfer`/`tokensReceived`-style callback) which calls back into the gateway or another contract before returning.
2. Attacker's contract is set as `beneficiary` of a `RedeemEscrow`/`RefundEscrow` withdrawal request (as either the filling solver or order owner).
3. A relayer delivers the corresponding ISMP message; the host calls `onAccept` → `withdraw()`.
4. During `token.call(transfer(...))` (or the ETH `.call`), the malicious token's hook re-enters before `_orders[commitment][token] -= amount` executes, exploiting the stale escrow value read in a nested call/path to have it counted or transferred twice, or to manipulate other escrow entries under the still-unset `_filled`/undecremented balance state.
5. Result: escrowed funds are drained beyond the legitimate entitled amount, matching the exact "external call before balance update" root cause identified in the reference report.

        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();

                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;

                ++i;
            }
        }
