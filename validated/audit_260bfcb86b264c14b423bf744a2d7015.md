### Title
Checks-Effects-Interactions violation in `withdraw()` — escrow balance decremented after external token transfer - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
`IntentGatewayV2.withdraw()` in the Tron deployment of the Intent Gateway performs the outbound token transfer to the beneficiary via a raw external `.call` **before** decrementing the corresponding `_orders[commitment][token]` escrow balance, and before deleting the escrowed transaction-fee bucket. This is exactly the CEI-violation pattern described in the external report (external call before the state that backs it is finalized), and it is reachable from a fully unprivileged, single-transaction entry point: `cancelOrder()` on a same-chain order. [1](#0-0) 

### Finding Description
`withdraw()` is called directly from the public, unprivileged `cancelOrder()` function for same-chain orders: [2](#0-1) 

Inside `withdraw()`, for each token in the withdrawal request, the contract makes a raw external call/transfer (native ETH via `.call{value: amount}("")`, or ERC20 via a raw `token.call(...)` — notably **not** `SafeERC20.safeTransfer`) and only afterwards decrements the escrow accounting:

```solidity
function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
    address beneficiary = address(uint160(uint256(body.beneficiary)));
    _filled[body.commitment] = beneficiary;

    for (...) {
        ...
        if (token == address(0)) {
            (bool sent,) = beneficiary.call{value: amount}("");
            if (!sent) revert InsufficientNativeToken();
        } else {
            (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
            if (!success) revert TransferFailed();
        }

        _orders[body.commitment][token] -= amount;   // <-- state updated AFTER the external call
        ...
    }

    // redeem tx fees
    uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
    if (fees > 0) {
        (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
        ...
        delete _orders[body.commitment][TRANSACTION_FEES];  // <-- also after the external call
    }
    ...
}
``` [3](#0-2) 

The `order.inputs` array used as `body.tokens` for a same-chain cancel is fully attacker-controlled at `placeOrder()` time — there is no token allowlist — and native ETH transfer or an attacker-supplied token contract can execute arbitrary code during the `.call`, gaining control of execution while `_orders[commitment][token]` still reflects the pre-decrement (stale) value.

The sibling, already-hardened contracts in this codebase (`evm/src/apps/intentsv2/IntentsBase.sol::_withdraw`, used by `IntrinsicIntents.sol`/`ExtrinsicIntents.sol`) apply the opposite, correct ordering — decrementing `_orders[...]` **before** the transfer — specifically because a documented CEI violation in the analogous same-chain fill path was previously exploitable for fee theft and multi-output escrow theft, as recorded in the regression test suite: [4](#0-3) [5](#0-4) 

The Tron `IntentGatewayV2.withdraw()` never received the equivalent CEI fix, leaving the transfer-before-decrement ordering intact.

### Impact Explanation
An external call executes while the escrow ledger (`_orders[commitment][token]`) and the transaction-fee bucket (`_orders[commitment][TRANSACTION_FEES]`) are still in their pre-withdrawal state. `_filled[commitment]` is set at the very top of `withdraw()`, which blocks the most direct re-entry (a second `cancelOrder`/`withdraw` call on the *same* commitment), but the per-token decrement ordering remains an unsafe pattern: any state-changing function reachable during the callback window that reads or mutates `_orders[commitment][...]` for that commitment before it is decremented is exposed to a stale-balance read, and the fee-token transfer at the end of the function is likewise made before the fee bucket is cleared. This is a direct deviation from the CEI pattern the project deliberately adopted elsewhere after finding it exploitable for escrow/fee theft, so this is at minimum a reentrancy hazard of the same class flagged in the external report, in the shipped Tron intent-gateway contract.

### Likelihood Explanation
Reachability is high: `cancelOrder()` is public and unprivileged, requires no special role, and the order owner (the caller) fully controls `order.inputs` (token addresses and beneficiary) supplied at `placeOrder()` time with no allowlist. The transfer path uses a low-level `.call` to the token contract rather than `SafeERC20.safeTransfer`, giving an attacker-supplied token full control of execution during the transfer, at exactly the point where `_orders[commitment][token]` has not yet been decremented.

### Recommendation
Apply the same CEI fix already present in `IntentsBase.sol::_withdraw`: decrement `_orders[body.commitment][token]` (and delete the `TRANSACTION_FEES` bucket) **before** performing the external transfer/call in `evm/tron/contracts/apps/IntentGatewayV2.sol::withdraw()`. Additionally, replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns with `SafeERC20.safeTransfer`, consistent with the rest of the codebase, to avoid silently accepting non-standard/malicious token return behavior.

### Proof of Concept
1. Attacker calls `placeOrder()` on the Tron `IntentGatewayV2` with a same-chain order whose `inputs` include a malicious ERC20 token (or native ETH) and `beneficiary`/`user` set to an attacker-controlled contract.
2. Attacker calls `cancelOrder()` for that order; since it is same-chain and unfilled, `withdraw(body, true)` is invoked internally.
3. Inside `withdraw()`, `_filled[commitment]` is set, then the loop reaches the attacker's token/ETH transfer and executes the external `.call`.
4. The attacker's contract/token gains control before `_orders[commitment][token] -= amount` executes, i.e., before escrow state is finalized — demonstrating the CEI violation is live and exploitable code, matching the reported bug class (external call preceding the state update that should have already occurred).
