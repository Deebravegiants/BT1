### Title
Signup-extension QR codes bypass backend user eligibility verification (`verify_user_qr_code`) - ([File: src/plans/mod.rs])

### Summary
`handle_user_qr_code` in `src/plans/mod.rs` calls the backend-eligibility check `verify_user_qr_code` for a normal signup, but takes an entirely separate branch — skipping that call — whenever either the operator or the user QR code is flagged as a "signup extension". This is the same bug class as the `RubiconMarket` finding: a security-relevant check (`buyEnabled`) is enforced on one code path (`buy`) but omitted on an alternate code path (`_buys` when `matchingEnabled` is false). Here, the backend verification check (`verify_user_qr_code`) is enforced on the normal signup path but omitted on the signup-extension path.

### Finding Description
In `handle_user_qr_code`, once a valid user QR code is parsed, the function branches on whether either QR code declares itself a "signup extension": [1](#0-0) 

If both operator and user QR codes are signup-extension-flagged and carry a `SignupExtensionConfig`, the function returns immediately with a synthetic, empty `backend::user_status::UserData::default()` instead of the backend-verified data: [2](#0-1) 

By contrast, the normal (non-extension) path is the only place that calls the backend verification routine: [3](#0-2) 

Whatever eligibility/fraud/duplicate-signup logic lives inside `verify_user_qr_code` (referenced at [4](#0-3) ) is therefore never executed for signup-extension flows — mirroring exactly how `buyEnabled` was checked only inside `_buys` and silently skipped when `matchingEnabled` was false, allowing the "disable" mechanism to be bypassed via an alternate call path. I was not able to retrieve the full body of `verify_user_qr_code` or the definition of `signup_extension()` within the available index, so the precise checks being skipped (e.g. duplicate-signup detection, ban/block-list checks, orb_relay app-id binding) could not be directly confirmed from source — this is a limitation of what is indexed/reachable, not a claim about the check's absence being intentional.

### Impact Explanation
If `verify_user_qr_code` is the gate that determines whether a given user QR code is allowed to proceed to a real signup (e.g., confirming the user isn't already enrolled, isn't blocked, or is otherwise eligible per backend state), then any QR code pair that is flagged with a valid `signup_extension_config` skips that gate entirely and proceeds straight into `do_signup` with a default/empty `UserData`. This is a cross-signup state bleed / unauthorized-signup class of impact: a user could enter the signup extension flow to avoid whatever eligibility enforcement occurs in the main flow, since the branch check happens purely on QR-code-declared fields (`signup_extension()`, `signup_extension_config`) rather than on backend-verified user state.

### Likelihood Explanation
The signup-extension flag and its `SignupExtensionConfig` are both derived from user-provided QR code content, as seen in [5](#0-4) , meaning the trigger for skipping `verify_user_qr_code` is fully controllable by whoever generates the QR code presented at the orb. This makes the bypass path reachable without any elevated privilege, so long as the "signup extension" feature paths (data acquisition / extension modes) are compiled into the running build, similar to how `matchingEnabled` being false was an ordinary, easily reachable admin toggle in the original finding.

### Recommendation
Move the backend verification/eligibility logic that `verify_user_qr_code` performs so that it runs unconditionally before branching on `signup_extension()`, or explicitly re-invoke the necessary checks inside the extension branch before returning `UserData::default()`. This ensures the eligibility gate cannot be bypassed merely by using an alternate (signup-extension) code path, mirroring the fix recommended for `RubiconMarket` (move the `require(buyEnabled)` check up to the shared entry point `buy` instead of leaving it only in `_buys`).

### Proof of Concept
1. Craft an operator QR code and a user QR code that both set `signup_extension = true` and include a valid `signup_extension_config` (e.g. `SignupMode::Basic` or another supported mode).
2. Present both QR codes to the orb during idle scanning; `handle_user_qr_code` is invoked as shown in [6](#0-5) .
3. Because both QR codes are extension-flagged with valid configs, execution enters the branch at [7](#0-6)  and returns immediately with `UserData::default()`, never calling `verify_user_qr_code` ( [3](#0-2) ).
4. The flow proceeds into `do_signup`/`biometric_capture` ( [8](#0-7) ) without whatever backend-side eligibility check `verify_user_qr_code` would have otherwise performed.
