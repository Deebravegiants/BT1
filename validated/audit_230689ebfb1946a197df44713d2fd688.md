### Title
`client_secret` sent to attacker-influenced host due to missing `ShopValidator` check on `AuthQuery#shop` in `validate_auth_callback` - (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
`ShopifyAPI::Auth::Oauth.validate_auth_callback` (`lib/shopify_api/auth/oauth.rb:60-113`) builds a `null_session` and an `HttpClient` directly from `auth_query.shop`, and sends the app's `client_id`/`client_secret` in the POST body to `https://#{shop}/admin/oauth/access_token` (via `Clients::HttpClient#initialize`, `lib/shopify_api/clients/http_client.rb:16-19`). Unlike every other credential-exchange entry point in the gem — `ClientCredentials.client_credentials` (`lib/shopify_api/auth/client_credentials.rb:25`), `RefreshToken.refresh_access_token` (`lib/shopify_api/auth/refresh_token.rb:24`), and `TokenExchange.migrate_to_expiring_token` (`lib/shopify_api/auth/token_exchange.rb:103`) — `validate_auth_callback` never calls `Utils::ShopValidator.sanitize!`/`sanitize_shop_domain` on the shop value before using it as the request host.

### Finding Description
The identity binding that should hold is: *the host that receives the `client_secret` == a host validated to be a genuine Shopify domain (`ShopValidator::TRUSTED_SHOPIFY_DOMAINS`)*.

In `validate_auth_callback`:
```ruby
raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
...
null_session = Auth::Session.new(shop: auth_query.shop)
body = {
  client_id: Context.api_key,
  client_secret: Context.api_secret_key,
  code: auth_query.code,
  expiring: Context.expiring_offline_access_tokens ? 1 : 0,
}
client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
response = client.request(...)
``` [1](#0-0) 

`Clients::HttpClient` derives its request host directly from `session.shop`: [2](#0-1) 

The only integrity check performed on `auth_query.shop` is the HMAC (`AuthQuery#to_signable_string` includes `shop`), which only proves the query parameters were signed with `Context.api_secret_key` — it does not prove `shop` is a `*.myshopify.com`/trusted Shopify domain, because `AuthQuery` is constructed directly from raw request parameters by the host application before being handed to this method, and the gem never restricts the domain shape: [3](#0-2) 

By contrast, `Utils::ShopValidator.sanitize!` exists precisely to enforce this binding (restricting the host to `shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`, or a configured `myshopify_domain`) and is used by every sibling OAuth/token method: [4](#0-3) [5](#0-4) [6](#0-5) 

`validate_auth_callback` is the one place that both (a) receives the shop as `String` from the calling application without any gem-level domain restriction, and (b) sends the `client_secret` to a host built from that value.

### Impact Explanation
If a host application forwards the callback request's `shop` parameter into `AuthQuery` without independently validating it as a trusted Shopify domain (the gem provides `ShopValidator` for exactly this purpose but does not enforce its use here, and the documented example in `docs/usage/oauth.md` constructs `AuthQuery` straight from `request.parameters` without any `ShopValidator` call), a value that passes HMAC validation but resolves to a host other than a genuine merchant shop would cause the gem to POST `client_id` and `client_secret` to that host — an SSRF that exfiltrates the app's `client_secret` carrying the app's own credentials, matching the High-impact "SSRF with the app's credentials" / "credential leakage" class in scope.

### Likelihood Explanation
Likelihood depends on whether the calling application passes an HMAC-validated but domain-unrestricted `shop` value straight through, which is the pattern shown in the gem's own `docs/usage/oauth.md` example. Because `ShopValidator.sanitize!` is applied everywhere else the gem talks to a shop-derived host except this one function, the omission is a genuine, gem-side inconsistency in the identity binding rather than a hypothetical host misuse.

### Recommendation
In `ShopifyAPI::Auth::Oauth.validate_auth_callback`, validate `auth_query.shop` with `Utils::ShopValidator.sanitize!` (as done in `client_credentials.rb`, `refresh_token.rb`, and `token_exchange.rb`) before constructing `null_session`/`Session.from`, e.g.:
```ruby
validated_shop = Utils::ShopValidator.sanitize!(auth_query.shop)
null_session = Auth::Session.new(shop: validated_shop)
...
session = Session.from(shop: validated_shop, access_token_response: ...)
```

### Proof of Concept
1. App exposes a callback route that builds `ShopifyAPI::Auth::Oauth::AuthQuery.new(request.parameters...)` directly from query params, matching the documented pattern in `docs/usage/oauth.md`.
2. Attacker triggers this callback route with a `shop` value that is not restricted to a genuine Shopify domain but for which they can still supply parameters that pass `Utils::HmacValidator.validate` in the application's own trust flow (e.g., a misconfigured or lenient upstream, or a shop value accepted by the host app before delegating to this gem without the host app itself checking `ShopValidator`).
3. `ShopifyAPI::Auth::Oauth.validate_auth_callback` proceeds to call `Clients::HttpClient.new(session: Auth::Session.new(shop: attacker_supplied_host), base_path: "/admin/oauth")`, which sends a POST containing `client_id` and `client_secret` to `https://#{attacker_supplied_host}/admin/oauth/access_token`.         def validate_auth_callback(cookies:, auth_query:)
          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state

          null_session = Auth::Session.new(shop: auth_query.shop)
          body = {
            client_id: Context.api_key,
            client_secret: Context.api_secret_key,
            code: auth_query.code,
            expiring: Context.expiring_offline_access_tokens ? 1 : 0, # Only applicable for offline tokens
          }

          client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
          response = begin
            client.request(
              Clients::HttpRequest.new(
                http_method: :post,
                path: "access_token",
                body: body,
                body_type: "application/json",
              ),
            )
          rescue ShopifyAPI::Errors::HttpResponseError => e
            raise Errors::RequestAccessTokenError,
              "Cannot complete OAuth process. Received a #{e.code} error while requesting access token."
          end
