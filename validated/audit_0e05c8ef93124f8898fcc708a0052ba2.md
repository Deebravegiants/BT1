### Title
Webhook `shop-domain` (and `topic`/`webhook-id`) header is not covered by the HMAC, breaking the payload↔tenant binding - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating an HMAC that is computed over the raw request body only, but it then trusts the `shop-domain` HTTP header — which is completely outside the HMAC — as the tenant identity handed to the app's webhook handler.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate` computes/verifies the HMAC exclusively against that signable string: [2](#0-1) 

`Registry.process` checks only that HMAC, then immediately builds tenant-identifying metadata straight from the unauthenticated `shop`, `topic`, `webhook_id`, and `api_version` headers and dispatches it to the registered handler: [3](#0-2) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors all read straight from headers with no cryptographic tie to the body that was actually HMAC-signed: [4](#0-3) 

The identity equality the library implicitly claims to guarantee is:
`HMAC_valid(body) == (body genuinely originated from the shop named in the shop-domain header)`

but the actual guarantee it provides is only:
`HMAC_valid(body) == (body was signed with this app's secret at some point, by any shop that installed the app)`

Because the shop/topic/webhook-id headers are never mixed into the signed material, any body+HMAC pair legitimately obtained by one tenant (e.g., by installing the app on the attacker's own store and observing/recording an inbound webhook, which is not secret data protected from the app owner) can be re-POSTed to the same endpoint with a different `x-shopify-shop-domain` header. `Registry.process` will validate the HMAC successfully (it never inspected the header) and hand the handler a `WebhookMetadata` claiming the payload came from a shop it did not come from.

### Impact Explanation
In a multi-tenant host application that keys per-shop state off `WebhookMetadata#shop` (the documented and expected usage pattern), this allows an attacker who controls one legitimate installation of the app to inject data or trigger side effects (order/customer/product events, mandatory GDPR webhooks, etc.) that the host app will attribute to a different, victim shop — a cross-tenant data/authenticity boundary violation. This fits the "cross-tenant access" class of impact.

### Likelihood Explanation
Exploitation requires the attacker to be (or install as) a tenant of the multi-tenant app so they can capture a validly-HMAC'd webhook body/signature pair for their own shop — no access to the app's `api_secret_key` is needed, no privileged account beyond a normal shop install, and no TLS interception is required. The header spoofing itself is trivial (attacker fully controls the headers of their own outbound HTTP request to the app's public webhook endpoint).

### Recommendation
Include the `shop-domain` (and ideally `topic`/`webhook-id`) values in the signed material that is compared against the HMAC, or otherwise cryptographically bind them (e.g., require the host application to independently confirm the shop is one it has an active session/installation for that specific topic/webhook-id combination) before trusting `request.shop` for tenant-scoped processing.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and registers webhook.
2. Shopify sends a legitimate webhook POST to the app: body `B`, headers include `x-shopify-hmac-sha256: H(secret, B)` and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker captures this POST (they own the receiving endpoint) and re-sends it to the same app endpoint, changing only `x-shopify-shop-domain` to `victim-shop.myshopify.com`, keeping body `B` and the same HMAC header value.
4. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `HmacValidator.validate` succeeds because it only checks `HMAC(secret, B)`, which is unchanged.
5. `Registry.process` invokes the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: B, ...)`, causing the host application to process attacker-controlled data under the victim shop's identity.
