### Title
Front-running `rlp_execute()` on the Wallet Contract causes automatic ban of an honest relayer's access key — (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The NEP-518 Wallet Contract's `rlp_execute()` entry point is fully permissionless: any NEAR account (`predecessor_account_id`) may submit any previously-observed, publicly visible `tx_bytes_b64` payload on behalf of an ETH-implicit account. Because the RLP payload (including nonce and signature) is public once broadcast, an attacker can copy a pending, legitimately-signed transaction and front-run the honest relayer's submission of the same payload. When the honest relayer's transaction later lands with a stale nonce, the contract treats it as a "faulty relayer" and irrevocably deletes the relayer's access key via `create_ban_relayer_promise`, even though the relayer did nothing wrong.

### Finding Description
`rlp_execute` accepts `target` and `tx_bytes_b64` from any predecessor and does not gate execution to a specific caller — the security model relies purely on validating the embedded ECDSA signature and expected nonce inside the payload: [1](#0-0) 

Because `tx_bytes_b64` bytes are attacker-readable calldata of a transaction sitting in the network before inclusion, anyone can extract them and resubmit the identical payload as their own, unrelated NEAR transaction — no private key or special key is required, since the signature check inside `parse_rlp_tx_to_action`/`validate_tx_relayer_data` only checks that the *embedded* Ethereum signature matches the wallet owner, not who the NEAR caller (predecessor) is: [2](#0-1) 

If the attacker's copy lands first, the contract's internal `nonce` advances. When the honest relayer's original transaction is later included on-chain with the now-stale nonce, `inner_rlp_execute`/`validate_tx_relayer_data` returns `Error::Relayer(RelayerError::InvalidNonce)`. If that relayer used a dedicated `FunctionCall` access key added directly to the wallet account (`signer_account_id == current_account_id`, the pattern the Wallet Contract's own documentation and tests recommend for gasless relayers), the contract automatically deletes that access key: [3](#0-2) [4](#0-3) 

The code's own reasoning for banning assumes any nonce mismatch implies a *malicious/faulty relayer*: [5](#0-4) 

This assumption is false: a nonce mismatch can be caused entirely by an unrelated third party who simply relayed the same publicly-visible signed bytes first. This is the exact bug class from the report — anyone can "front-run" a batched/queued operation intended for a specific account by resubmitting identical, publicly-observable authorization data, forcing the legitimate call to fail — except here the on-chain consequence is worse than wasted gas: it triggers an automatic, irreversible `DeleteKey` action against the victim relayer's access key.

### Impact Explanation
An attacker can repeatedly and cheaply grief any ETH-implicit account's registered relayer:
- Every time the wallet owner (or their relayer) prepares to submit a transaction via a dedicated relayer access key, the attacker races it with the same public payload.
- Regardless of who "wins" the race for execution (the intended action still executes correctly either way, since the payload is valid), the *relayer's* access key gets deleted whenever its now-stale copy of the same nonce lands afterward.
- This disables the “gasless relayer” UX pattern that NEP-518 / the Wallet Contract is specifically designed to provide, forcing the wallet owner to re-register (via another signed `AddKey` action, itself another `rlp_execute` call, again racable) a new relayer key each time — a denial-of-service against the wallet's relayer infrastructure, achievable by any unprivileged account with no special access, matching the "prevent all users from claiming/using their intended flow" impact class.

### Likelihood Explanation
The attack requires no special privileges, no access key, and no funds beyond gas for a normal `FunctionCall` action; it only requires observing a broadcast (but not yet included) `rlp_execute` transaction's calldata and resubmitting it faster. This is standard, well-understood blockchain front-running and is readily automatable by any node/validator or mempool-watching bot. The condition that triggers the ban (`signer_account_id == current_account_id`) is exactly the pattern documented and tested as the intended relayer-onboarding flow (`register_relayer`, `test_register_relayer`), so it is expected to be common in production use.

### Recommendation
Do not treat a nonce mismatch alone as proof of a faulty/malicious relayer. Before deleting the relayer's access key, distinguish "this exact payload/nonce was already consumed by a *different, successfully executed* action" from actual relayer misbehavior (e.g., wrong target/sender/chain id, insufficient gas). At minimum, avoid banning on `InvalidNonce` errors caused by a nonce that was already fulfilled with an identical action outcome, or require additional confirmation (e.g., only ban after repeated distinguishable protocol violations, not a single stale-nonce replay) before revoking the relayer key.

### Proof of Concept
1. Wallet owner registers a relayer access key on their ETH-implicit account via `register_relayer`, so future `rlp_execute` calls can be signed with `signer_account_id == current_account_id`, as in [6](#0-5) .
2. The relayer prepares and broadcasts a NEAR transaction calling `rlp_execute(target, tx_bytes_b64)` with the user's next valid nonce.
3. Attacker observes this pending transaction, extracts `tx_bytes_b64`, and immediately submits their own NEAR transaction (from an arbitrary unrelated account) calling `rlp_execute` with the same `target`/`tx_bytes_b64`, with higher priority/gas price, landing first.
4. The contract nonce advances; the intended action executes correctly, but that is irrelevant — the wallet's own nonce is now ahead of what the relayer's inflight tx expects.
5. The relayer's original transaction lands afterward with the stale nonce; `validate_tx_relayer_data` returns `RelayerError::InvalidNonce`, and because `signer_account_id == current_account_id`, `rlp_execute` triggers `create_ban_relayer_promise`, deleting the relayer's access key (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:121-124`, `:503-512`) — confirmed by the existing test pattern in `test_register_relayer`, which asserts the key is revoked whenever a stale/repeated nonce is submitted ( [7](#0-6) ), regardless of whether the stale nonce originated from the relayer itself or from an unrelated front-runner.

    #[payable]
    pub fn rlp_execute(
        &mut self,
        target: AccountId,
        tx_bytes_b64: String,
    ) -> PromiseOrValue<ExecuteResponse> {
        // To ensure user actions are executed in the desired order,
        // having multiple transactions in flight at the same time is
        // not allowed.
        if self.has_in_flight_tx {
            return PromiseOrValue::Value(ExecuteResponse {
                success: false,
                success_value: None,
                error: Some(
                    "Error: transaction already in progress, please try again later.".into(),
                ),
            });
        }
        let current_account_id = env::current_account_id();
        let predecessor_account_id = env::predecessor_account_id();
        let result = inner_rlp_execute(
            current_account_id.clone(),
            predecessor_account_id,
            target,
            tx_bytes_b64,
            &mut self.nonce,
        );

        match result {
            Ok(promise) => {
                self.has_in_flight_tx = true;
                PromiseOrValue::Promise(promise)
            }
            Err(Error::Relayer(_)) if env::signer_account_id() == current_account_id => {
                let promise = create_ban_relayer_promise(current_account_id);
                self.has_in_flight_tx = true;
                PromiseOrValue::Promise(promise)
            }
            Err(e) => PromiseOrValue::Value(e.into()),
        }
    }

/// Validates the transaction is following the Wallet Contract protocol.
/// This includes checks for:
/// - from address matches current account address
/// - to address is present and matches the target address (or hash of target account ID)
/// - nonce matches expected nonce
/// If this validation fails then the relayer that sent it is faulty and should be banned.
fn validate_tx_relayer_data<'a>(
    tx: &NormalizedEthTransaction,
    target: &'a AccountId,
    context: &ExecutionContext,
    expected_nonce: u64,
) -> Result<TargetKind<'a>, Error> {
    if tx.address.raw() != context.current_address {
        return Err(Error::Relayer(RelayerError::InvalidSender));
    }

    if tx.chain_id != Some(CHAIN_ID) {
        return Err(Error::Relayer(RelayerError::InvalidChainId));
    }

    let to = tx.to.ok_or(Error::User(UserError::EvmDeployDisallowed))?.raw();

    let target_kind = parse_target(target, context.current_address);

    // valid targets satisfy `to == target` or `to == hash(target)`
    let is_valid_target = match target_kind {
        TargetKind::CurrentAccount if to == context.current_address => {
            target == &context.current_account_id
        }
        TargetKind::EthImplicit(address) if to == address => {
            target.as_str()
                == format!("0x{}{}", hex::encode(address), context.current_account_suffix())
        }
        _ => to == account_id_to_address(target),
    };

    if !is_valid_target {
        return Err(Error::Relayer(RelayerError::InvalidTarget));
    }

    let nonce = if tx.nonce <= U64_MAX {
        tx.nonce.low_u64()
    } else {
        return Err(Error::Relayer(RelayerError::InvalidNonce));
    };
    if nonce != expected_nonce {
        return Err(Error::Relayer(RelayerError::InvalidNonce));
    }

    /// Add a new `FunctionCall` access key to the Wallet Contract.
    /// The idea is that this allows the relayer to submit transactions signed by
    /// the Wallet Contract directly.
    pub async fn register_relayer(
        &mut self,
        worker: &Worker<Sandbox>,
    ) -> anyhow::Result<PublicKey> {
        let relayer_account = worker.dev_create_account().await?;
        let relayer_key = SecretKey::from_random(KeyType::ED25519);
        let relayer_pk = relayer_key.public_key();

        let action = Action::AddKey {
            public_key_kind: 0,
            public_key: relayer_pk.key_data().to_vec(),
            nonce: 0,
            is_full_access: false,
            is_limited_allowance: false,
            allowance: 0,
            receiver_id: self.inner.id().to_string(),
            method_names: vec![RLP_EXECUTE.into()],
        };
        let nonce = self.get_nonce().await?;
        let signed_transaction =
            utils::create_signed_transaction(nonce, self.inner.id(), Wei::zero(), action, &self.sk);

        // Call the Wallet Contract from the relayer account to add the key
        let result: ExecuteResponse = relayer_account
            .call(self.inner.id(), RLP_EXECUTE)
            .args_json(serde_json::json!({
                "target": self.inner.id(),
                "tx_bytes_b64": codec::encode_b64(&codec::rlp_encode(&signed_transaction))
            }))
            .max_gas()
            .transact()
            .await?
            .into_result()?
            .json()?;

        assert!(result.success, "Adding Relayer's key failed: {:?}", result.error);

        // Tell near-workspaces to use this new key instead when
        // signing transactions from the Wallet Contract
        self.inner.as_account_mut().set_secret_key(relayer_key);

        Ok(relayer_pk)
    }

// A relayer can use its own Near account to send a transaction containing data
// signed by the user which adds a FunctionCall access key to the Wallet
// Contract account. This allows the relayer to send transactions on the user's
// behalf while the user covers the gas costs.
#[tokio::test]
async fn test_register_relayer() -> anyhow::Result<()> {
    let TestContext { worker, mut wallet_contract, wallet_sk, .. } = TestContext::new().await?;

    let relayer_pk = wallet_contract.register_relayer(&worker).await?;
    let key = wallet_contract.inner.as_account().view_access_key(&relayer_pk).await?;
    match &key.permission {
        AccessKeyPermission::FunctionCall(access) => {
            assert_eq!(access.allowance, None);
            assert_eq!(access.receiver_id.as_str(), wallet_contract.inner.id().as_str());
            assert_eq!(&access.method_names, &[RLP_EXECUTE]);
        }
        _ => panic!("Unexpected full access key"),
    }

    // Should be able to submit transactions using the new key
    utils::deploy_and_call_hello(&worker, &wallet_contract, &wallet_sk, 1).await?;

    // If the relayer is dishonest then its key is revoked.
    // In this case the relayer will try to repeat a nonce value.
    let result = utils::deploy_and_call_hello(&worker, &wallet_contract, &wallet_sk, 1).await;
    let error_message = format!("{:?}", result.unwrap_err());
    assert!(error_message.contains("faulty relayer"));

    assert_revoked_key(&wallet_contract.inner, &relayer_pk).await;

    Ok(())
}
