### Title
Webhook `shop` field is trusted for tenant identification but excluded from the HMAC signature, enabling cross-tenant webhook confusion - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` used by webhook processing from the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header, but the HMAC signature that `ShopifyAPI::Webhooks::Registry.process` validates only covers the raw request body, never the shop header. Any party who can obtain a validly-signed webhook body under the app's shared `api_secret_key` (i.e., any merchant who has installed the app, since Shopify signs every tenant's webhooks with the same per-app secret) can replay that exact body while substituting an arbitrary shop domain in the header, and the library will report it as authenticated and pass the attacker-chosen `shop` value straight to the handler.

### Finding Description
`Utils::VerifiableQuery#to_signable_string` for `Webhooks::Request` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes and compares the HMAC strictly over that signable string: [2](#0-1) 

`Registry.process` uses this validation as the sole authentication gate before dispatching to the handler, and then forwards `request.shop` — read straight from the unauthenticated header — as the tenant identity in `WebhookMetadata`: [3](#0-2) 

`request.shop` itself is a pure header read with no cross-check against the HMAC or against the body: [4](#0-3) 

The identity binding that should hold is: `shop authenticated by HMAC == shop delivered to the handler`. Here, the HMAC authenticates only the body bytes, while the shop passed to the handler comes from an entirely separate, unauthenticated header — the two are never bound to each other. Because Shopify signs webhooks for *every* installation of an app using the same app-level `api_secret_key` (not a per-shop secret), a signature that is valid for shop A's payload is equally "valid" (per this library's check) when replayed with shop B's domain in the header, since the header plays no part in the signature. The documentation explicitly instructs apps to key their downstream processing off `data.shop`, trusting it as the authenticated tenant: [5](#0-4) 

### Impact Explanation
This is a cross-tenant confused-deputy vector fully rooted in this gem's own verification logic: `Registry.process` tells the host application "this webhook is authenticated for `request.shop`" when in fact only the body bytes were authenticated, not the shop association. A merchant who has installed the app (an unprivileged, non-credentialed party from the perspective of other tenants) can capture one of their own genuine webhook deliveries (raw body + valid HMAC) and replay it against the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop. Any host app that follows this gem's documented pattern of trusting `data.shop` to select the tenant record/session to update will process attacker-supplied data (or attacker-triggered actions) under a victim shop's identity — a cross-tenant access impact.

### Likelihood Explanation
Likelihood is high: exploitation requires no secrets beyond a legitimate app installation the attacker already controls (their own shop), which is the normal, unprivileged position of any merchant using the app. No `api_secret_key`, access token, or the app's `client_secret` need be obtained; the attacker only needs to capture and replay one of their own valid webhook deliveries with an edited header, which is trivial since the header is not part of the signed content.

### Recommendation
Bind the shop identity into the authenticated material used for webhook verification, e.g., include the `shop-domain` (and ideally `topic`/`webhook-id`) in the HMAC-signed string (matching how Shopify signs/validates on its own side), or otherwise cryptographically bind the header value to the payload before trusting `request.shop` as the tenant identifier in `WebhookMetadata`. At minimum, document prominently that `data.shop` is not covered by the HMAC and must be independently cross-checked (e.g., against a shop already known to have registered that specific `webhook_id`/topic) before being used for any tenant-scoped operation.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com` and `victim-shop.myshopify.com`, both webhooks signed with the same app `api_secret_key` (this is how Shopify signs webhooks — per-app secret, not per-shop).
2. Attacker triggers or receives a genuine webhook for their own shop, capturing:
   - `raw_body` (e.g., `{"id":123,...}`)
   - `X-Shopify-Hmac-Sha256: <valid HMAC of raw_body>`
   - `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`
3. Attacker POSTs the identical `raw_body` and identical `X-Shopify-Hmac-Sha256` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses headers/body as usual; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `raw_body` only — this still matches, since the body/HMAC pair is unchanged.
5. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(topic:, shop: request.shop, ...))` with `shop == "victim-shop.myshopify.com"`, even though this payload was never actually sent by/for that shop.
6. Any host application that uses `data.shop` to select which merchant's records to update (per the documented usage pattern) now performs cross-tenant writes/reads based on attacker-controlled, unauthenticated data.

          received_signature = verifiable_query.hmac
