Audit Report

## Title
View-role users can read External Initiator `AccessKey` and `OutgoingToken` via `GET /v2/external_initiators`, enabling job-run request forgery - (File: core/web/router.go)

## Summary
The `/v2/external_initiators` list endpoint is registered with only the blanket `authv2` authentication group and no role-gating middleware, unlike the `POST`/`DELETE` routes on the same controller which require `auth.RequiresEditRole`. The handler's `Index` method returns each external initiator's plaintext `AccessKey` and `OutgoingToken` to any authenticated user, including those with the lowest-privilege `view` role.

## Finding Description
In `core/web/router.go`, the external initiators routes are defined as:
```go
authv2.GET("/external_initiators", paginatedRequest(eia.Index))
authv2.POST("/external_initiators", auth.RequiresEditRole(eia.Create))
authv2.DELETE("/external_initiators/:Name", auth.RequiresEditRole(eia.Destroy))
```
`GET` has no `auth.RequiresEditRole` (or any other role) wrapper, while `POST`/`DELETE` do [1](#0-0) . The only check applied to `GET` is the generic `authv2` group authentication (`AuthenticateByToken`/`AuthenticateBySession`), which establishes identity but not role-based authorization [2](#0-1) .

`ExternalInitiatorsController.Index` fetches all external initiators and serializes them via `presenters.NewExternalInitiatorResource`, with no field filtering by caller role [3](#0-2) . The presenter includes both `AccessKey` and `OutgoingToken` in the JSON response [4](#0-3) .

This is corroborated by the repository's own RBAC route-permission test table, which explicitly documents `GET /v2/external_initiators` as `viewOnlyAllowed: true`, in contrast to `POST`/`DELETE` on the same resource being `false` for view and edit-minimal roles [5](#0-4) .

`AccessKey` is one half of the credential pair used in `AuthenticateExternalInitiator`, and successful authentication with that credential pair is automatically granted the internal `run` role, which is authorized to trigger job runs [6](#0-5) . `OutgoingToken` is a distinct, separately stored plaintext secret used by the node for outbound calls to the initiator, and is not otherwise protected by hashing/salting the way the inbound `Secret` is.

## Impact Explanation
Disclosure of `OutgoingToken` allows a low-privilege `view`-role account holder to obtain a bearer-style secret that the external system might use to validate that outbound calls truly originated from the node, enabling potential impersonation of the node's outbound authentication to the external initiator. Disclosure of `AccessKey` provides reconnaissance value toward the credential pair gating the `AuthenticateExternalInitiator` path (though the corresponding `Secret` is hashed and not retrievable via this endpoint, so full inbound impersonation is not directly achievable from this leak alone). This maps to an in-scope credential/secret exfiltration and node API role-boundary weakness.

## Likelihood Explanation
Exploitation requires an authenticated account with at least the `view` role — a supported, documented multi-role feature of Chainlink's user management, not a pre-auth vulnerability. Given such an account, the exploit is trivially and repeatably reproducible: a single unauthenticated-role-elevation-free `GET` request. The node's own test suite (`auth_test.go`) confirms this behavior is present and, notably, appears to be an intentional design decision (`viewOnlyAllowed: true`) rather than an accidental omission, though the security posture is still questionable and arguably a genuine broken-access-control weakness for the `OutgoingToken` disclosure.

## Recommendation
Elevate `GET /v2/external_initiators` to require at least `auth.RequiresEditRole` (matching `Create`/`Destroy`), or alternatively strip `AccessKey` and `OutgoingToken` from the list/index presenter entirely, only exposing them once at creation time via `ExternalInitiatorAuthentication`, consistent with how the inbound `Secret` is already handled (never retrievable after creation).

## Proof of Concept
1. Create a Chainlink node user with role `view` (e.g., `POST /v2/users` as admin, or via LDAP/OIDC group mapping).
2. Log in as that `view`-role user (session or API token).
3. Issue `GET /v2/external_initiators`.
4. Observe the JSON response includes `accessKey` and `outgoingToken` for every configured external initiator, per `presenters.ExternalInitiatorResource` [7](#0-6) .
5. Confirm via `core/web/auth/auth_test.go` line 224 that this is validated in the RBAC test suite as `viewOnlyAllowed: true` for this route [8](#0-7) .

```go
func (eic *ExternalInitiatorsController) Index(c *gin.Context, size, page, offset int) {
	ctx := c.Request.Context()
	externalInitiators, count, err := eic.App.BridgeORM().ExternalInitiators(ctx, offset, size)
	resources := make([]presenters.ExternalInitiatorResource, 0, len(externalInitiators))
	for _, initiator := range externalInitiators {
		resources = append(resources, presenters.NewExternalInitiatorResource(initiator))
	}

	paginatedResponse(c, "externalInitiators", size, page, resources, count, err)
}
```

```go
func AuthenticateExternalInitiator(c *gin.Context, store Authenticator) error {
	ctx := c.Request.Context()
	eia := &auth.Token{
		AccessKey: c.GetHeader(static.ExternalInitiatorAccessKeyHeader),
		Secret:    c.GetHeader(static.ExternalInitiatorSecretHeader),
	}

	ei, err := store.FindExternalInitiator(ctx, eia)
	if err != nil {
		if errors.Is(err, sql.ErrNoRows) {
			return auth.ErrorAuthFailed
		}

		return errors.Wrap(err, "finding external initiator")
	}

	ok, err := bridges.AuthenticateExternalInitiator(eia, ei)
	if err != nil {
		return err
	}
	if !ok {
		return auth.ErrorAuthFailed
	}

	// External initiator endpoints (wrapped with AuthenticateExternalInitiator) inherently assume the role
	// of 'run' (required to trigger job runs)
	c.Set(SessionExternalInitiatorKey, ei)
	c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})
```
