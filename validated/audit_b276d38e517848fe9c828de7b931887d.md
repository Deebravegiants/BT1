### Title
HOT Bridge API fallback reports withdrawal as "completed" without checking `verified_withdraw` flag - (File: packages/intents-sdk/src/bridges/hot-bridge/hot-bridge.ts)

### Summary
`HotBridge.fetchWithdrawalHashFromApi` parses the HOT API response with `HotApiWithdrawalSchema`, which includes a `verified_withdraw: boolean` field, but the function never reads or checks that field before returning the hash. `describeWithdrawal` then reports `status: "completed"` with that unverified hash as soon as any non-empty `hash` is present for the matching nonce.

### Finding Description
The schema explicitly models `verified_withdraw` as part of each withdrawal record: [1](#0-0) 

But `fetchWithdrawalHashFromApi` only matches by `nonce` and checks `withdrawal?.hash` truthiness/hex-validity — it never inspects `withdrawal.verified_withdraw`: [2](#0-1) 

This function is used as the fallback path in `describeWithdrawal`, both for EVM/Stellar/TON chains (when the bridge indexer fails) and for other non-EVM chains (when the contract view call returns null/pending): [3](#0-2) [4](#0-3) 

In both branches, as soon as `apiHash != null`, the SDK returns `{ status: "completed", txHash: ... }`. If HOT's API returns a record where `hash` is populated (e.g. a submitted-but-not-yet-confirmed or provisional destination tx hash) while `verified_withdraw` is `false`, the SDK will still report the withdrawal as `"completed"`. This breaks the equality that the reported status must match the actual on-chain outcome — the API-reported hash is treated as proof of completion without confirming the withdrawal was verified.

The test suite's own mock fixtures always set `verified_withdraw: true` in cases that are asserted to yield `"completed"`, and no test exercises the case where a hash is present but `verified_withdraw: false`, which is consistent with the field being parsed but effectively unused for the completion decision: [5](#0-4) 

### Impact Explanation
`describeWithdrawal`'s output feeds `watchWithdrawal`, which resolves the polling promise the instant `status === "completed"`: [6](#0-5) 

An integrator relying on `sdk.waitForWithdrawalCompletion` / `watchWithdrawal` to decide when funds have landed on the destination chain could be told a withdrawal is `"completed"` with a `txHash` while the underlying transfer is not actually verified/finalized on-chain (`verified_withdraw: false`). This is a status misreport that does not match the true on-chain outcome, which can cause an integrator to credit the user, close out an order, or release matching funds based on a withdrawal that never verifiably completed — a "status or hash misreport making an integrator credit or refund twice" class issue.

### Likelihood Explanation
This path only triggers in a fallback flow (bridge indexer down/failed, or contract view returning null on non-EVM/non-Stellar/non-TON chains), so it is not on the primary happy path, but it is a genuine reachable API fallback that is exercised in production whenever the primary indexer is unavailable. The likelihood depends on how often HOT's API actually returns `hash` non-null with `verified_withdraw: false` in practice, which cannot be confirmed from this repo alone (external API behavior).

### Recommendation
In `fetchWithdrawalHashFromApi`, require `withdrawal.verified_withdraw === true` in addition to a valid non-empty hex hash before returning the hash to the caller; otherwise return `null` (keep status "pending") so `describeWithdrawal` does not prematurely report `"completed"`.

### Proof of Concept
1. Bridge indexer request fails (or throws) for an EVM/Stellar/TON withdrawal, or the HOT contract view returns `null`/pending status for another chain.
2. HOT API `/api/v1/evm/bridge_withdrawal_hash` returns a withdrawal record matching the nonce with `hash: "0xDEADBEEF"` and `verified_withdraw: false` (i.e., not yet confirmed/verified on-chain).
3. `fetchWithdrawalHashFromApi` returns `"DEADBEEF"` because it only checks `hash` truthiness/hex format, ignoring `verified_withdraw`.
4. `describeWithdrawal` returns `{ status: "completed", txHash: "0xDEADBEEF" }`.
5. `watchWithdrawal`/`waitForWithdrawalCompletion` resolves immediately, reporting the withdrawal as done to the caller, even though `verified_withdraw` indicates the transfer is not actually confirmed on-chain.

	private async fetchWithdrawalHashFromApi(
		nearTxHash: string,
		nonce: bigint,
		logger?: ILogger,
	): Promise<string | null> {
		try {
			const response = await withTimeout(
				() =>
					this.hotSdk.api.requestApi(
						`/api/v1/evm/bridge_withdrawal_hash?near_trx=${nearTxHash}`,
						{ method: "GET" },
					),
				{ timeout: HotBridge.API_FALLBACK_TIMEOUT_MS },
			);
			const data: unknown = await response.json();

			const parseResult = v.safeParse(HotApiWithdrawalResponseSchema, data);
			if (!parseResult.success) {
				logger?.debug("HOT API response parse failed", {
					issues: parseResult.issues,
				});
				return null;
			}

			const withdrawal = parseResult.output.withdrawals.find(
				(w) => w.nonce === nonce.toString(),
			);

			if (withdrawal?.hash) {
				const hash = withdrawal.hash.replace(/^0x/, "");
				if (isHex(hash)) {
					logger?.info("HOT withdrawal hash found via API fallback", {
						nearTxHash,
						nonce: nonce.toString(),
					});
					return hash;
				}
			}
			return null;
		} catch (error) {
			logger?.debug("HOT API fallback failed", { error, nearTxHash });
			return null;
		}
	}
