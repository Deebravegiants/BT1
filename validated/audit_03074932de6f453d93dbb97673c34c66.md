Found a genuine binding break in the webhook validation flow.### Title
Webhook shop identity spoofing via unauthenticated `shop-domain` header — cross-tenant confusion in `ShopifyAPI::Webhooks::Registry.process` (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC that `ShopifyAPI::Utils::HmacValidator.validate` checks in `ShopifyAPI::Webhooks::Registry.process` covers exclusively `@raw_body`. The `shop` value that the app trusts to identify the tenant (`request.shop`, sourced from the `X-Shopify-Shop-Domain`/`shopify-shop-domain` header) is never part of the signed bytes, breaking the equality "shop authenticated == shop the data is attributed to."

### Finding Description
`ShopifyAPI::Webhooks::Request` reads `shop` straight from an HTTP header: [1](#0-0) 

but the same class's `to_signable_string`, which is what `HmacValidator` verifies against the HMAC header, only returns the raw JSON body: [2](#0-1) 

`Registry.process` performs exactly one check — HMAC over the body — before handing `request.shop` (the unauthenticated header) straight to the app's handler as the tenant identity: [3](#0-2) 

Because the app's `client_secret` (used to compute the HMAC) is shared across every shop that has installed the app, a byte-identical `(body, hmac)` pair is valid for *any* shop. The only thing that ties a webhook delivery to a particular merchant is the `shop-domain` header, and that header is excluded from the signed content. This is precisely the "shop authenticated vs. shop stored/acted upon" binding break: `hmac_valid(body) == true` but `shop_header != shop_that_produced(body)` is never checked.

### Impact Explanation
An unprivileged internet user who is a legitimate (even free-trial) installer of the target app on their own store can:
1. Trigger any webhook topic on their own shop (e.g. `orders/create`) to obtain a genuine `(raw_body, hmac)` pair signed with the app's real `client_secret` — no secret leakage or privileged access required, since Shopify sends this to any installed merchant.
2. Replay that exact body/HMAC pair to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain.
3. `HmacValidator.validate` still passes (it only checks the body), and `Registry.process` forwards `WebhookMetadata` with `shop:` set to the attacker-chosen victim domain to the app's handler.

Depending on how the host app keys its per-tenant storage/business logic off `WebhookMetadata#shop` (documented as the tenant identifier), this allows a merchant to inject events, forge state transitions, or corrupt data attributed to another merchant's tenant — i.e., cross-tenant access/data confusion, which the rules classify as Critical impact. This does not require the app's `client_secret`, an access token, or any privileged account; it only requires being a normal installed user of the app (which any Shopify user can become for free) — this is an unprivileged-internet-user analog with a real credential/tenant boundary broken.

### Likelihood Explanation
Likelihood is moderate-to-high for apps that key any business logic (state changes, mandatory GDPR redaction routing, order/customer record association, billing, etc.) directly off `WebhookMetadata#shop` without independently confirming that shop is one that legitimately owns an install/session — which is the documented, intended use of the field. The gem provides no warning or secondary binding check, so this is a systemic design gap rather than a host-app misuse.

### Recommendation
Extend `AuthQuery`/`VerifiableQuery` semantics used for OAuth to webhooks as well: include the `shop-domain`, `topic`, `webhook-id`, and `api-version` headers in the signed material, or otherwise cryptographically bind the header-derived `shop` to the signed payload (e.g., HMAC over `"#{shop}\n#{topic}\n#{raw_body}"`, matching how Shopify signs newer webhook formats if it exposes richer signature coverage), and reject requests where the header-derived shop cannot be corroborated against the signature. At minimum, document prominently that `WebhookMetadata#shop` is *not* authenticated and must not be trusted for tenant selection without an independent check (e.g., cross-referencing an existing stored session for that shop).

### Proof of Concept
```ruby
# 1. Attacker is a legitimately installed merchant on "attacker-shop.myshopify.com".
#    They trigger a webhook on their own shop (e.g. update a product) and capture
#    the raw POST Shopify sends to the app's webhook endpoint:
raw_body = '{"id":123,"note":"hello"}'
hmac     = request.headers["X-Shopify-Hmac-Sha256"]   # genuine, computed with the app's real client_secret

# 2. Attacker replays the identical body/hmac to the same endpoint, but swaps only
#    the shop-domain header to the victim's shop:
headers = {
  "x-shopify-topic"       => "products/update",
  "x-shopify-hmac-sha256" => hmac,                      # unchanged, still valid
  "x-shopify-shop-domain" => "victim-shop.myshopify.com" # attacker-controlled, unsigned
}

req = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(req)
# => HmacValidator.validate(req) succeeds (only checks raw_body)
# => handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...))
```
`Registry.process`'s single gate is shown here — no verification ties `request.shop` to the signed bytes: [3](#0-2) 
and `to_signable_string` confirms the header is out of scope of what's signed: [4](#0-3)
