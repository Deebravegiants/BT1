### Title
Permissionless pre-graduation pair pre-seeding can force the locked HyperSwap LP to open materially off the curve-close price (M-02 residual) - ([File: packages/contracts/src/Bonding.sol])

### Summary
`Bonding.finalizeGraduation` seeds the HyperSwap V2 TOKEN/LT pair through `_seedUniswapV2Direct` → `_seedRebalancing` → `_pairRebalance`, which is designed to defend against an attacker who front-runs graduation by minting a hostile-ratio LP into the pair (`factory.createPair` + `transfer` + `pair.mint`). The rebalance swap that restores the curve-close ratio is deliberately capped at 99% of the available per-side inventory via `_swapBudget` to guarantee `finalizeGraduation` can never revert (brick-resistance). For a sufficiently extreme pre-seed ratio, the swap required to fully correct the pool exceeds this budget, so the pool is only partially corrected and the resulting LP — permanently locked in `LPLock` with no withdraw path — opens materially away from the true curve-close price.

### Finding Description
`_seedRebalancing` computes the swap needed to bring a hostile-mint-pre-seeded pair back to the cached curve-close ratio (`tokensForLP`/`ltFromPair`), then calls `_pairRebalance`, which computes the swap input via `_noFeeSwapInput` and executes it directly against the pair: [1](#0-0) 

That swap input is capped by `_swapBudget`, which reserves only 99% of the caller's own inventory so the subsequent `addLiquidity` deposit always has a non-zero amount to place on both sides: [2](#0-1) 

`AGENTS.md` documents that this budget cap can bind for extreme pre-seed ratios, in which case the deposit lands at a materially wrong price: [3](#0-2) 

This is exercised directly by the test suite's own "M-02" reproducer, an LT-rich mint pre-seed (`reserveLt = ltFromPair * 200`, `reserveToken = tokensForLP / 100`) whose optimal rebalance swap exceeds the 99% budget: [4](#0-3) 

The test confirms `finalizeGraduation` does not revert, but the pool price ends up more than 20% off the curve-close price: [5](#0-4) 

The only remedy documented for the attacker's own economics is that their resulting LP claim, valued at fair price, must not exceed their deposit (`P&L ≤ 0`) — i.e., the attacker personally doesn't profit: [6](#0-5) 

However, the "attacker doesn't profit" property says nothing about the health of the locked LP itself. `LPLock` has no rescue/withdraw path in v1 (documented repeatedly in `AGENTS.md`), so once the mispriced LP is minted, it is permanently frozen at the wrong price. This is analogous to the Footium report's core mechanic: a party pre-manipulates on-chain state (here, the pair reserves) immediately ahead of the counterparty-relied-upon settlement transaction (`finalizeGraduation`), leaving everyone who transacts against that settled state economically worse off than the price they were promised (the curve's last traded price) — the difference being that here it is every post-graduation buyer/seller trading against the newly-opened HyperSwap pool who inherits the mispricing, since the very first post-grad swap arbitrages the gap and extracts value out of the (protocol-owned, permanently-locked) LP.

### Impact Explanation
Any unprivileged address can permissionlessly call `IUniswapV2Factory.createPair(token, lt)` and `pair.mint(attacker)` at any point between phase 1 (`_enterGraduating`) and phase 2 (`finalizeGraduation`, itself permissionless) to set up an extreme pre-seed ratio. Once `finalizeGraduation` runs, the budget-capped rebalance cannot fully correct the ratio, so the LP permanently locked in `LPLock` opens materially off the curve-close price. Because `LPLock` cannot be unwound, this mispricing is baked into the pool forever; the first arbitrage trade against the mispriced pool extracts value from the LP (which represents the pooled contribution of every curve-stage buyer and the 250M reserved LP tokens), i.e., a permanent value transfer out of protocol/community funds to whichever party captures the arbitrage. This is a concrete, permanent loss to LP value distinct from — and not mitigated by — the "attacker cost-negative" property, which only bounds the *attacker's own* LP claim, not the damage to the correctly-priced portion of the pool.

### Likelihood Explanation
The precondition (creating and pre-seeding the HyperSwap pair with an extreme skewed ratio before `finalizeGraduation`) requires only standard ERC20 transfers and calls to a permissionless factory/pair — no privileged role, no governance, no off-chain dependency. Any token about to graduate is a target, and the window between `_enterGraduating` (phase 1) and `finalizeGraduation` (phase 2) is exactly the attack surface `AGENTS.md` itself calls "the actual exploit." The mitigations reduce but, per the codebase's own M-02 test, do not eliminate the mispricing for sufficiently lopsided pre-seed ratios, which cost an attacker only the deposited pre-seed amount (bounded, and cheaply affordable relative to the value at stake in a popular graduating token).

### Recommendation
Either (a) remove the hard 1%-reserved swap-budget shortfall by allowing `_pairRebalance` to consume up to 100% of available inventory when the alternative is a large residual price gap (falling back to direct-mint only when the swap output would legitimately round to zero, not merely when it exceeds the 99% heuristic), or (b) route any residual price gap's arbitrage value back to the protocol/LP instead of leaving it for a general searcher — e.g., by executing an internal top-up swap using a small owner-controlled buffer, or by disproportionately slashing the pre-seeder's minted LP share (beyond simple non-profitability) to also compensate for the opened price gap. At minimum, the acceptable mispricing bound for the M-02 regime should be tightened and explicitly tested against a maximum bps deviation rather than only against attacker P&L, since LP holders (not just the attacker) bear the cost of a mispriced, permanently-locked pool.

### Proof of Concept
Using the existing test harness pattern from `test_hostilePreSeed_budgetCappedSwap_isNotProfitable`:
1. Launch a token and drive it to `Lifecycle.Graduating` via `_enterGraduating` (a normal curve buy crossing the graduation threshold).
2. Before `finalizeGraduation` is called, an unprivileged address calls `factory.createPair(token, lt)`, transfers `reserveToken = tokensForLP / 100` TOKEN and `reserveLt = ltFromPair * 200` LT to the pair, then calls `pair.mint(attacker)`.
3. Anyone calls `bonding.finalizeGraduation(token)`. It does not revert (brick-resistant), but `_seedRebalancing`'s budget-capped swap cannot fully correct the ratio; the pool's post-graduation price ends up >20% (up to ~2x, per `AGENTS.md`) away from the curve-close price, and this LP is locked forever in `LPLock`.
4. Any third party can then arbitrage the mispriced pool for a profit funded by the value that should have belonged to the locked LP, permanently reducing the LP's fair value versus the honest curve-close price it should have opened at. [7](#0-6)

    /// @dev Cap the rebalance swap at 99% of the available side's budget,
    ///      so the subsequent `addLiquidity` always has a non-zero amount
    ///      of BOTH sides to deposit. Without this, an extreme hostile
    ///      pre-seed (massively imbalanced reserves) drives the
    ///      unconstrained `_noFeeSwapInput` past our per-side budget,
    ///      `_pairRebalance` clamps to the full budget, and the swap
    ///      consumes 100% of one side. `_routerDepositAndDispose` then
    ///      skips `addLiquidity` (`remToken == 0` or `remLT == 0`),
    ///      `finalizeGraduation` returns `liquidity = 0`, and
    ///      `LPLock.recordLock(...)` records a zero-sized lock — the
    ///      attacker's pre-existing LP becomes 100% of the pool. Reserving
    ///      1% guarantees the deposit leg always lands AND mints non-zero
    ///      LP at the post-swap ratio. The 1% comes off the swap, not the
    ///      deposit — for any realistic pre-seed `s_unconstrained` is
    ///      orders of magnitude below `maxSwap`, so the cap doesn't bind
    ///      and behaviour is unchanged. It only kicks in for catastrophic
    ///      pre-seeds beyond our budget capacity, where the alternative
    ///      is bricking.
    function _swapBudget(
        uint256 budget
    ) internal pure returns (uint256) {
        return (budget * 99) / 100;
    }

    function _pairRebalance(
        RebalanceParams memory p
    ) internal returns (bool) {
        uint256 s = _noFeeSwapInput(p.reserveIn, p.reserveOut, p.targetN, p.targetD, p.maxSwap);
        if (s == 0) return false;

        // Quote from the pair so the output tracks its live fee; a value
        // derived from a stale fee rate would trip the pair's K-check.
        uint256 expectedOut = IUniswapV2Pair(p.pair).getAmountOut(s, p.tokenIn);
        if (expectedOut == 0) return false;

        IERC20(p.tokenIn).safeTransfer(p.pair, s);
        (uint256 amount0Out, uint256 amount1Out) = p.tokenInIs0 ? (uint256(0), expectedOut) : (expectedOut, uint256(0));
        IUniswapV2Pair(p.pair).swap(amount0Out, amount1Out, address(this), new bytes(0));
        return true;
    }

#### Regime 3 — mint pre-seed (the actual exploit)

Attacker called `pair.mint(attacker)` against a self-funded dust seed. Reserves are non-zero at a hostile ratio. We:

1. **Compute the swap input** that would drive the pool ratio back to the curve-close ratio under the no-fee constant-product model: `s = sqrt(reserveIn · reserveOut · targetN / targetD) − reserveIn`, capped at our per-side budget. Implementation in `_noFeeSwapInput`. Closed-form via OZ `Math.sqrt + Math.mulDiv`; no binary search, no convergence loop.
2. **Execute the swap directly on the pair** via `pair.swap(amount0Out, amount1Out, address(this), "")`. We read the output from the pair's own fee-aware `getAmountOut` quote and pass it as the output. **Bypasses the router** — HyperSwap's V2 router has no canonical `swapExactTokensForTokens` (see "HyperSwap Router non-standard ABI" above). Same direct-to-pair pattern Zap uses for post-grad user swaps. Implementation in `_pairRebalance`.
3. **Deposit the remaining inventory** via `router.addLiquidity(rest, 1, 1, lpLock, ...)`. The router's `quote()`-based optimal split deposits only the matched-ratio subset; neither side becomes a `min()` donation. Off-ratio remainder stays in `Bonding`. The router's `addLiquidity` IS canonical V2 on HyperSwap (verified selector `0xe8e33700`), so this leg is safe to keep on the router and gets the `quote()` math for free.
4. **Dispose the off-ratio remainder.** TOKEN side burned (`Bonding` is the Token owner). LT side auto-swept to the protocol owner by `finalizeGraduation`'s post-sweep — emits `LTRescued(lt, owner, amount)` for observability. See "Per-graduation LT isolation" below.

Why the **asymmetric router usage** (pair for swap, router for addLiquidity): the swap is unsafe to send through the router because HyperSwap's swap ABI is non-standard; the deposit IS safe because HyperSwap's `addLiquidity` ABI is canonical AND the `quote()`-based optimal-split logic is the part that defuses the LP-capture attack. We get the best of both — no HyperSwap-specific footgun on the swap, no reimplementation burden on the deposit.

Why the fourth step matters: **mass conservation prevents fixing both the price and the deposit.** If the pool starts off-target and our inventory is on-target, we cannot end with both at-target reserves AND a fully-deposited inventory — something has to absorb the imbalance. Step 4 is where it goes.

**Dust pre-seeds skip steps 1–4 for a direct mint.** When the swap-output side of the pre-seed is small enough that the rebalance swap rounds to zero (`s == 0` or `getAmountOut(s) == 0`), no swap can move the ratio. The reserves are then negligible against `(tokensForLP, ltFromPair)`, so `_pairRebalance` returns `false` and `_seedRebalancing` falls back to `_seedDirectMint` — the same `transfer + pair.mint` as Regime 1 — opening at the cached ratio and depositing both sides in full (nothing burned or swept). The attacker's dust LP captures `max(reserveToken/tokensForLP, reserveLT/ltFromPair)` of the pool, which vanishes. This is strictly preferable to depositing at the dust ratio via the router, which would open the pool off curve-close.
```

    /// @notice M-02 reproducer. An LT-rich mint pre-seed so lopsided that the
    ///         TOKEN-side rebalance swap exhausts its full budget (~99% of
    ///         `tokensForLP`) without reaching the cached ratio, so the pool
    ///         deposits materially off curve-close. Finalize must still succeed
    ///         (no brick), the over-funded LT side must be confiscated to the
    ///         owner, and the pre-seeder must end net-negative.
    function test_hostilePreSeed_budgetCappedSwap_isNotProfitable() public {
        (address tokenAddr,) = _launchToken();
        _enterGraduating(tokenAddr);

        (uint256 tokensForLP, uint256 ltFromPair,,) = bonding.pendingGraduation(tokenAddr);

        // Extreme LT-rich shape: TOKEN side at 1% of target, LT side at 200x.
        // The optimal TOKEN-in swap to reach the cached ratio is ~1.4x
        // `tokensForLP`, so the 99%-of-`tokensForLP` budget cap binds and the
        // pool stays ~2x off curve-close after the swap.
        uint256 reserveToken = tokensForLP / 100;
        uint256 reserveLt = ltFromPair * 200;

        // M-02 precondition: the optimal swap exceeds the budget (this is the
        // budget-capped regime, distinct from the swap-rounds-to-zero fallback
        // covered by the dust tests above).
        assertGt(
            _noFeeSwapInputUncapped(reserveToken, reserveLt, tokensForLP, ltFromPair),
            (tokensForLP * 99) / 100,
            "setup: optimal rebalance swap must exceed the per-side budget (M-02 regime)"
        );

        deal(tokenAddr, griefer, reserveToken);
        address hyperPair = _grieferMintPreSeed(tokenAddr, reserveToken, reserveLt);
        uint256 grieferLp = MockHyperswapPair(hyperPair).balanceOf(griefer);
        uint256 ownerLtBefore = lt.balanceOf(bonding.owner());

        bonding.finalizeGraduation(tokenAddr);
        assertTrue(bonding.isGraduated(tokenAddr), "finalize must succeed despite an unrecoverable pre-seed");

        // The accepted residual: no bounded swap can correct a 200x LT-rich
        // pre-seed, so the pool opens materially off curve-close.
        assertGt(
            _poolPriceLtPerToken(hyperPair, tokenAddr),
            (((ltFromPair * 1e18) / tokensForLP) * 12) / 10,
            "M-02 regime: pool opens materially off curve-close"
        );
```
