### Title
Unbounded arbitrary `call` in `EmporiumUpgradeable.runAction` CASE 2 lets an attacker plant persistent ERC20 approvals for tokens outside `circomData.erc20TokenAddresses` - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
`EmporiumUpgradeable.runAction` allows `stack.signerAddress = address(0)`, which causes `verifyWallet` to skip signature verification entirely (only checking `usedMessages`), letting any unprivileged caller with a valid Hinkal proof fully control `stack.ops[]`. In CASE 2 ("Stateless Interaction"), `op.endpoint.call(op.callData)` is executed with only two forbidden selectors (`callHinkalWallet`, `doSendToRelay`), meaning an attacker can direct Emporium to call `approve()` on any ERC20 token to any attacker-controlled spender, for a token entirely absent from `circomData.erc20TokenAddresses`.

### Finding Description
The broken equality: `balanceOf(Emporium, tokenX)` before tx1 should equal `balanceOf(Emporium, tokenX)` after any later tx2 that involves no Hinkal accounting entry for `tokenX`, since Hinkal's `balanceDif` accounting in `Hinkal.sol:transact` (lines 78-146) and Emporium's own `balancesBefore/balancesAfter` snapshot (`EmporiumUpgradeable.sol:85-87, 122-124`) iterate exclusively over `circomData.erc20TokenAddresses`. Any token not included in that attacker-chosen array is invisible to both invariants.

Code path: `Hinkal.transact` → `_externalTransact` → `EmporiumUpgradeable.runAction` (`onlyAllowedRecipient`, called by Emporium's registered relay/wallet as `msg.sender=Emporium`'s allowed caller) [1](#0-0) . Inside `runAction`, `stack` is decoded straight from `circomData.externalActionData.externalActionMetadata` with no cross-check against `circomData.erc20TokenAddresses` [2](#0-1) . `verifyWallet` returns immediately without any signature check when `stack.signerAddress == address(0)`, only marking `emporiumMessage` used [3](#0-2) . CASE 2 then executes `op.endpoint.call{value: op.value}(op.callData)` with only wallet-selector checks, no restriction on which token/contract is targeted or what state it mutates [4](#0-3) . Because the post-call balance/UTXO accounting loop only walks `circomData.erc20TokenAddresses` (lines 132-151), any `approve(spender, amount)` call against a token not included in that array produces no balance delta to check and is never swept via `handleOut`. The resulting approval persists indefinitely in that token's own storage, independent of the Hinkal transaction lifecycle, because Emporium is a single shared contract across all users rather than a per-user proxy.

This means the attacker can, in one transaction, cause Emporium to grant an approval for an arbitrary token/spender pair with zero cost beyond gas, and this approval is not reflected anywhere in Hinkal's `balanceDif`/UTXO invariant since the token was deliberately excluded from `erc20TokenAddresses`.

### Impact Explanation
If any balance of the un-listed token X later accumulates in Emporium — from dust/rounding leftovers of another user's swap routed through Emporium, an intermediate token in a multi-hop DEX call, or any other legitimate flow that doesn't force `erc20TokenAddresses` to include every token ever touched — the attacker can, with a completely separate, no-proof-required call (`tokenX.transferFrom(Emporium, attacker, ...)`), drain it using the previously planted approval. Because Emporium is a shared, cross-user contract (not scoped per wallet), this is theft of protocol/relay-adjacent funds belonging to other users or the protocol, matching the "High - executing calls or moving assets ... never authorised" category, and it's repeatable indefinitely for any token that ever touches Emporium's balance outside the declared `erc20TokenAddresses` set for a given call.

### Likelihood Explanation
Preconditions are attacker-controlled and cheap: the attacker only needs one valid Hinkal proof for their own UTXOs (`stack.signerAddress = address(0)` is a legitimate supported code path, not a bypass of proof validity) and to choose `circomData.erc20TokenAddresses` to exclude the target token. The harder precondition — for the exploit to yield real stolen value rather than just planting a dormant approval — is that Emporium must later hold a nonzero balance of the un-listed token from some other source. I could not verify from the available code (limited by index coverage of the swap/DEX external-action integrations, e.g. `ExternalActionSwap.sol`, LI.FI routing paths) whether such dust/leftover balances routinely and reliably accumulate in Emporium in practice, or whether other invariants elsewhere (not fully explored) prevent Emporium from ever holding non-swept token balances. The root-cause bug (unrestricted arbitrary `call` from Emporium's own context with no relationship to the declared token list) is confirmed in the code, but full exploitability depends on this unverified precondition.

### Recommendation
Constrain CASE 2 stateless calls so they cannot invoke state-changing functions (especially `approve`/`increaseAllowance`/`setApprovalForAll`) on tokens outside `circomData.erc20TokenAddresses`, or require Emporium to explicitly revoke any approvals granted during `runAction` before returning, or track/whitelist per-call which contracts/selectors `op.endpoint.call` is allowed to target so approvals cannot be silently left dangling on unrelated tokens.

### Proof of Concept
Foundry fork test plan:
1. Deploy Emporium, register it as an external action in `Hinkal`, generate a valid attacker proof for a self-owned UTXO with `circomData.externalActionData.externalActionId` pointing to Emporium.
2. Set `circomData.erc20TokenAddresses` to a list that excludes token X (an arbitrary ERC20 deployed by the attacker or an existing token).
3. Encode `externalActionMetadata` as an `EmporiumStack` with `signerAddress = address(0)` and one op: `{endpoint: tokenX, invokeWallet: false, value: 0, callData: abi.encodeCall(IERC20.approve, (attackerSpender, type(uint256).max))}`.
4. Call `Hinkal.transact(...)`; assert it succeeds and `tokenX.allowance(Emporium, attackerSpender) == type(uint256).max`.
5. Separately fund Emporium with token X (e.g., simulate a legitimate transaction/dust leftover by directly transferring X to Emporium, representing an out-of-scope but plausible source) and assert `tokenX.balanceOf(Emporium) > 0`.
6. From attacker EOA, call `tokenX.transferFrom(Emporium, attacker, tokenX.balanceOf(Emporium))` with no Hinkal interaction; assert it succeeds and drains Emporium's balance to 0.
7. Assert nowhere in `Hinkal.sol`'s `balanceDif`/UTXO checks (lines 97-146) was token X ever referenced, confirming the drain is entirely untracked by the protocol's accounting invariant.
