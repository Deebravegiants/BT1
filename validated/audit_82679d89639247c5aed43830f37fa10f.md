### Title
Integer-division truncation in `CostModel::get_instructions_data_cost` lets an attacker embed instruction data in a block at zero marginal cost - ([File: cost-model/src/cost_model.rs])

### Summary
`CostModel::get_instructions_data_cost` computes the "data bytes" cost of a transaction with a plain integer division (`instruction_data_len() / INSTRUCTION_DATA_BYTES_COST`) with no rounding-up/ceiling and no remainder handling. This is the same "Pattern 1: Division Rounding to Zero" primitive described in the report (`a += input / x; b += input`): for any `input < x`, `a` accrues nothing while the underlying resource (`b`, i.e., bytes actually included in the block) is fully consumed. Here, `x = INSTRUCTION_DATA_BYTES_COST`, and any instruction whose total instruction data is smaller than that constant contributes `0` to the transaction's cost-model total, even though the bytes are fully written into the block/entries and are charged for by no other cost-model component. [1](#0-0) 

### Finding Description
`get_instructions_data_cost` is:

```rust
fn get_instructions_data_cost(transaction: &impl TransactionMeta) -> u16 {
    transaction.instruction_data_len() / (INSTRUCTION_DATA_BYTES_COST as u16)
}
``` [1](#0-0) 

This value (`data_bytes_cost`) is folded directly into `TransactionCost::sum()`, which is the quantity checked against the block cost limit and per-account cost limit in `CostTracker::would_fit`: [2](#0-1) [3](#0-2) 

The test at `runtime/src/transaction_execution.rs` explicitly confirms this truncating (floor) division is used when reconstructing the expected total cost of a committed transaction: `tx.message.instructions[0].data.len() as u64 / INSTRUCTION_DATA_BYTES_COST`. [4](#0-3) 

Unlike every other rounding-sensitive computation found in the cost/fee code paths - which were deliberately hardened to round up (ceiling) so as to never under-charge:
- `ComputeBudgetLimits::get_prioritization_fee` explicitly adds `MICRO_LAMPORTS_PER_LAMPORT - 1` before dividing, with a test comment "should round up (<1.0) lamport fee to 1 lamport" [5](#0-4) 
- `CostModel::calculate_pages_for_bytes` adds `ACCOUNT_DATA_COST_PAGE_SIZE - 1` before dividing, so partial pages still get charged [6](#0-5) 

`get_instructions_data_cost` performs plain floor division with no compensating `+1`/`div_ceil`. Any transaction whose combined instruction data length is less than `INSTRUCTION_DATA_BYTES_COST` bytes (currently defined in `cost-model/src/block_cost_limits.rs`) is charged **zero** data-bytes cost in the cost model, even though those bytes are fully present in the transaction, occupy block/entry space, and must be processed and stored. This directly mirrors the report's Pattern 1: `user / x == 0` while `b` (block space consumed) is still fully increased by `input`.

An unprivileged user fully controls `instruction_data_len()` (sum of instruction data across the transaction) and can therefore consistently keep it just under the `INSTRUCTION_DATA_BYTES_COST` threshold per transaction, or split payload across many instructions/transactions, to have their data-carrying transactions treated by the cost model as if they carried no data bytes at all.

### Impact Explanation
This is a materially underpriced-execution / cost-accounting bug that is explicitly in-scope ("cost model" is one of the accepted categories). It does not create free lamports/tokens directly (unlike the Sai report's exact scenario), but it produces the exact same class of defect: an attacker-controlled quantity (`input`) that is fully consumed by the system (block space/bytes) while the corresponding accounted resource (`data_bytes_cost`) is truncated to zero. The practical effect is that the on-chain cost model (used for `WouldExceedMaxBlockCostLimit`/`WouldExceedMaxAccountCostLimit` checks in `CostTracker::would_fit`) under-counts real resource consumption for data-heavy-but-below-threshold transactions, allowing more instruction-data bytes to be packed into a block/account cost budget than the model intends to permit, without being detected as such.

### Likelihood Explanation
Trivial and fully attacker-controlled: any unprivileged user constructing a transaction can choose instruction data lengths below `INSTRUCTION_DATA_BYTES_COST` (a fixed public constant) to guarantee `data_bytes_cost == 0`. No special account state, timing, or privileged role is required, unlike the reward-splitting rounding elsewhere in the codebase (`commission_split`/`commission_split_preserve_lamports` in `runtime/src/inflation_rewards/mod.rs`) which is not attacker-triggerable and is explicitly value-preserving/self-corrective by design (excluded per the report's own "unprivileged user" scope requirement).

### Recommendation
Change `get_instructions_data_cost` to round up (ceiling), matching the pattern already used elsewhere in the same file (`calculate_pages_for_bytes`) and in `ComputeBudgetLimits::get_prioritization_fee`:

```rust
fn get_instructions_data_cost(transaction: &impl TransactionMeta) -> u16 {
    transaction
        .instruction_data_len()
        .div_ceil(INSTRUCTION_DATA_BYTES_COST as u16)
}
```

This mirrors the report's Pattern 1 mitigation (`require(div(wad, chi()) > 0)` / ensure any nonzero input contributes a nonzero accounted amount), ensuring no instruction data bytes are ever excluded from the cost model due to floor-division truncation. Any such change is consensus-affecting (changes `TransactionCost::sum()` values used for block-cost-limit checks) and would need a feature gate and thorough compatibility testing.

### Proof of Concept
1. Construct a transaction whose combined instruction data across all instructions is `INSTRUCTION_DATA_BYTES_COST - 1` bytes (e.g., pad a custom/no-op program's instruction data to just under the threshold).
2. Call `CostModel::calculate_cost` (or `estimate_cost`/`calculate_cost_for_executed_transaction`) on it, as done in `cost-model/src/cost_model.rs` tests (`test_cost_model_token_transaction` already demonstrates `data_bytes_cost == 0` for small instruction data) [7](#0-6) .
3. Observe `TransactionCost.data_bytes_cost == 0` and that this value feeds unmodified into `TransactionCost::sum()` [2](#0-1)  which is what `CostTracker::would_fit` checks against block/account cost limits [3](#0-2) .
4. Repeat across many transactions/instructions, each staying just under the threshold, to accumulate many bytes of "free" (un-costed) instruction data within a slot's cost-tracked budget.
