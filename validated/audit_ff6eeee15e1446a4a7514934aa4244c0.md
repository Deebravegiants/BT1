### Title
Webhook `shop-domain` and `topic` headers are trusted without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives its `shop`, `topic`, `webhook_id`, and `api_version` fields entirely from HTTP headers, while the HMAC signature it verifies against covers only the raw request body [1](#0-0) . `ShopifyAPI::Utils::HmacValidator.validate` computes and compares the signature purely from `to_signable_string`, i.e. the raw body [2](#0-1) . Since the `shop` and `topic` values that `Registry.process` relies on for routing and tenant identification are never part of the signed bytes, they can be freely modified by anyone who can replay a validly-signed webhook body.

### Finding Description
The identity-binding equality that should hold is:

`bytes verified by HMAC == bytes that determine the tenant (shop) the webhook is attributed to`

In this gem that equality is broken:

- `Request#hmac` reads `shopify-hmac-sha256` header [3](#0-2) .
- `Request#shop` and `Request#topic` are read from separate, unauthenticated headers `shop-domain` and `topic` [4](#0-3) .
- `Request#to_signable_string` — the only data actually covered by the HMAC — returns just `@raw_body`, excluding `shop`, `topic`, `webhook_id`, and `api_version` [1](#0-0) .
- `Registry.process` validates the HMAC and then immediately trusts `request.shop` and `request.topic` to route the payload to a handler and build `WebhookMetadata`, without any additional cross-check tying `shop` to the signed content [5](#0-4) .

Because the HMAC is computed only over the raw body, any attacker who can obtain one genuinely-signed webhook body/signature pair (e.g., by installing the same public app on a store they control, which is always possible for any embedded/public Shopify app since installation itself is unprivileged) can replay that exact body+HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with any victim shop domain, and/or the `X-Shopify-Topic` header with a different topic. The HMAC check in `HmacValidator.validate` still succeeds because it only re-derives the signature from the untouched body, so `Registry.process` will dispatch the forged shop/topic combination to the registered handler as if Shopify had sent it for that shop [5](#0-4) .

### Impact Explanation
This breaks the tenant-identity binding for the app's entire webhook pipeline: `handler.handle` receives a `WebhookMetadata` whose `shop` field is fully attacker-controlled while its `body` is a legitimately-signed but attacker-chosen payload from a shop the attacker owns [6](#0-5) . A host application that keys any per-tenant state (order records, customer data, subscription state, uninstall/redact actions such as `shop/redact`) off `data.shop` can be made to apply the attacker's own webhook data against an arbitrary victim shop record — a cross-tenant data corruption/injection primitive, satisfying the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Any unprivileged internet user can install a target public/embedded Shopify app on a free development store they control, causing the app to legitimately receive an HMAC-signed webhook. They can capture that raw body and signature via a normal HTTP proxy, then replay the POST to the app's webhook endpoint with a forged `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header. No access to the app's `client_secret`, access tokens, or any privileged account is required — only the ability to install the app once, which is the normal, unprivileged Shopify app-install flow.

### Recommendation
Include the header-derived identity fields (`shop`, `topic`, and ideally `webhook_id`/`api_version`) in the HMAC-signed material `to_signable_string` returns, or otherwise cryptographically bind them (e.g., verify `shop` against a value embedded in the payload, or require the caller to separately confirm the shop is one for which the app holds an active session/access token) before dispatching to `handler.handle`. At minimum, `Registry.process` should reject requests where the `shop` header cannot be corroborated by data actually covered by the signature.

### Proof of Concept
1. Attacker installs the target public app on `attacker-shop.myshopify.com`, a store they control.
2. Shopify sends a legitimately HMAC-signed webhook, e.g. `orders/create`, to the app's webhook endpoint:
   ```
   X-Shopify-Topic: orders/create
   X-Shopify-Hmac-Sha256: <valid HMAC over body>
   X-Shopify-Shop-Domain: attacker-shop.myshopify.com
   Body: {"id": 1, "note": "malicious payload"}
   ```
3. Attacker replays the exact same body and `X-Shopify-Hmac-Sha256` value, but changes the header:
   ```
   X-Shopify-Shop-Domain: victim-shop.myshopify.com
   ```
4. `ShopifyAPI::Webhooks::Request.new` parses this into a request whose `hmac` matches (body unchanged) but whose `shop` is now `victim-shop.myshopify.com` [7](#0-6) .
5. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because `to_signable_string` never included `shop` [8](#0-7) .
6. The handler receives `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: {...}, ...)`, causing the host app to process attacker-supplied data as if it belonged to the victim shop [9](#0-8) .
