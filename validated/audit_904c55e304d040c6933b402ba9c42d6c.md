### Title
Missing shop-domain validation in `Oauth.validate_auth_callback` allows the app's `client_secret` to be sent to an attacker-controlled host - (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
`ShopifyAPI::Auth::Oauth.validate_auth_callback` builds the OAuth token-exchange request host directly from `auth_query.shop` and never runs it through `Utils::ShopValidator.sanitize!`, unlike every other credential-bearing flow in this gem (`ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, `Clients::Graphql::Storefront`). The bound checked (HMAC over the query string) and the value that actually receives the app's `client_secret` (the raw, unsanitized `shop`) are not the same thing that was validated as "a legitimate Shopify domain."

### Finding Description
`validate_auth_callback` only checks:
1. `Utils::HmacValidator.validate(auth_query)` — proves the query bytes (`code`, `host`, `shop`, `state`, `timestamp`) were signed with `Context.api_secret_key`. [1](#0-0) 

It then immediately does:
```ruby
null_session = Auth::Session.new(shop: auth_query.shop)
body = { client_id: ..., client_secret: Context.api_secret_key, code: auth_query.code, ... }
client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
client.request(... path: "access_token" ...)
``` [2](#0-1) 

The host that receives the POST (carrying `client_secret`) is derived purely from `auth_query.shop`, with **no call to `Utils::ShopValidator.sanitize!`** to confirm it is a `*.myshopify.com`/`spin.dev`/etc. domain. Compare this to the two sibling credential flows in the same gem, both of which sanitize the shop before using it to build the request host: [3](#0-2) [4](#0-3) 

The identity binding that should hold is: *"the host validated as trustworthy" = "the host that receives `client_secret`"*. `validate_auth_callback` breaks this equality — it validates only that the byte string was HMAC-signed, not that the `shop` value inside it is a real Shopify domain (`Utils::ShopValidator.sanitize!` is the codebase's own mechanism for that check, defined in `lib/shopify_api/utils/shop_validator.rb`). [5](#0-4) 

### Impact Explanation
In the intended flow the callback query (including `shop`) is generated and HMAC-signed by Shopify itself, so the byte-level HMAC check normally implies `shop` is a real store domain. However, this reliance is implicit and undocumented in the gem's own code path, and it diverges from the gem's own established pattern (`ShopValidator.sanitize!`) used everywhere else `client_secret` is transmitted. Any host application that reuses `AuthQuery` values from another source, replays/relaxes the flow (e.g., custom middleware constructing `AuthQuery` from other trusted-but-not-domain-checked inputs), or any future change loosening `HmacValidator` would result in the app's `client_secret` being POSTed to a host built from unvalidated `shop` input — a credential-exfiltration/SSRF primitive identical in class to the Cantina report (a value used as a security boundary — the target host for credentials — was never bound to a proper domain-format check, only to an unrelated verification of byte equality).

### Likelihood Explanation
Low likelihood under the current single call path, since `HmacValidator.validate` covers `shop` and requires knowledge of `api_secret_key` to forge, which an unprivileged internet user does not have (excluded per the rules against requiring `api_secret_key`). This keeps the issue below the bar of a directly exploitable, credential-less bug in the current code path, but it remains a structural inconsistency and a latent risk that is one refactor/consumer-code-path away from becoming exploitable, since the gem itself never enforces the domain-format invariant at this specific site the way it does in `ClientCredentials` and `RefreshToken`.

### Recommendation
Add `validated_shop = Utils::ShopValidator.sanitize!(auth_query.shop)` in `Oauth.validate_auth_callback` before constructing `null_session`, and use `validated_shop` for both the session host and the returned `Session.from(shop: ...)` call, mirroring `ClientCredentials.client_credentials` and `RefreshToken.refresh_access_token`. This makes the "trusted domain" check an explicit, defense-in-depth invariant at every site that transmits `client_secret`, rather than relying implicitly on HMAC coverage alone.

### Proof of Concept
Not applicable as a directly exploitable unprivileged-attacker PoC today — exploitation would require either (a) an ability to supply an HMAC-valid `AuthQuery` with an attacker-chosen `shop` (requires `api_secret_key`, out of scope), or (b) a host application/future code path that constructs `AuthQuery` from a `shop` value not itself validated as a Shopify domain before calling `validate_auth_callback`. No PoC satisfying the "no credential" and "unprivileged internet user" constraints was found for this specific gap.

        def validate_auth_callback(cookies:, auth_query:)
          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state
