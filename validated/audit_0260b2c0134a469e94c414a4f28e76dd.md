### Title
Personal Custody Package (biometric credential) is uploaded to S3 before the backend's own duplicate/fraud verdict is known, with no compensating deletion/revocation path - ([File: src/plans/mod.rs])

### Summary
The reported GasTankPaymaster bug is a classic "benefit before settlement" ordering flaw: gas is spent executing the user's operation, but the corresponding debit (`repaySponsoredTransaction`) is only applied *after* the fact, and nothing prevents the user from withdrawing funds (`gasTankWithdraw`) in the window before that debit lands — letting the user permanently escape the consequence that should be tied to the action already taken. The same class of bug (irreversible transfer of a valuable artifact before the authoritative check that should gate it has concluded, with no compensating rollback) is reachable in `orb-core`'s signup flow: the Personal Custody Package (PCP) — which contains the user's iris codes, iris/face embeddings, and encrypted private keys — is built and uploaded to S3 before the backend's own signup verification (duplicate detection, backend-side fraud detection) completes, and the codebase has no revoke/delete step to retract that upload if the backend later rejects the signup.

### Finding Description
In `MasterPlan::do_signup` (`src/plans/mod.rs`), the sequence of operations is:

1. Biometric capture and pipeline run.
2. `detect_fraud()` runs — but note that in this FOSS build all fraud checks are stripped: [1](#0-0) 
3. `signup_reason` is derived from the (empty) local fraud result.
4. `build_pcp()` constructs the Personal Custody Package (biometric codes, embeddings, encrypted keys) tagged with that `signup_reason`: [2](#0-1) 
5. The PCP tiers (0/1/2 — containing iris codes, iris/face embeddings, and encrypted backend private keys) are uploaded to S3/the data uploader **before** the authoritative backend verdict is obtained: [3](#0-2) 
6. Only *after* this biometric material has already been persisted does the code call `enroll_user`, which performs the real backend check via `signup_post`/`signup_poll` — the same call that can return `Fail` for reasons explicitly including "Backend duplicates", "Backend legacy signup requests", "Backend inflight matches", and "Backend detected fraud": [4](#0-3) 

The `PersonalCustodyPackages` built in `personal_custody_package.rs` contain the sensitive biometric payload (iris codes/shares, mask codes, face embeddings, encrypted private keys) that this upload step ships out: [5](#0-4) [6](#0-5) 

After `enroll_user` completes (whether success or failure), `after_signup` only uploads a debug report and finalizes UI state — there is no call anywhere in this path that deletes, invalidates, or requests deletion of the already-uploaded PCP tiers when the backend subsequently reports the signup as a duplicate or as fraud: [7](#0-6) [8](#0-7) 

This is structurally identical to the GasTankPaymaster flaw: an irreversible, valuable transfer (uploading raw biometric secrets/keys) is committed to persistent storage *before* the authoritative check (`repaySponsoredTransaction` / backend `signup_poll` verdict) that is supposed to gate whether the transaction is legitimate, and no mechanism exists to "claw back" the transferred asset once the authoritative check comes back negative.

### Impact Explanation
If the backend later determines the signup is a duplicate, an in-flight match for another identity, or backend-side fraud, the user's iris codes, face embeddings, and encrypted private keys have already left the orb and been persisted to S3 under that signup ID. Because there is no deletion/rollback of the uploaded PCP tiers tied to the negative verdict, biometric data belonging to a signup that the system itself considers illegitimate (duplicate/fraudulent) remains disclosed and stored, i.e. cross-signup state bleed / biometric data disclosure that should have been avoided since the record was never supposed to be considered a valid, standalone identity.

### Likelihood Explanation
This occurs for every signup that reaches the pipeline stage and is subsequently rejected by the backend as duplicate/fraud/in-flight-match during `signup_poll` — a normal, expected failure path (explicitly documented in the code's own comments), not a rare race condition. It requires no special privilege beyond going through the ordinary signup flow as an unprivileged user/attempted-duplicate enroller.

### Recommendation
Gate the PCP tier uploads on the backend's authoritative signup verdict (i.e., move the `upload_pcp_tier_0`/tier1/tier2 sends to occur only after `enroll_user`/`signup_poll` reports `Status::Success`), or, if uploading earlier is required for latency reasons, add an explicit compensating deletion request against the storage backend for the corresponding `signup_id`/`user_id` whenever `signup_poll` returns a non-success/duplicate/fraud verdict, mirroring the "pause withdrawals until settlement" pattern recommended for the original GasTankPaymaster finding (track an in-flight/unsettled state per signup and only release/retain the uploaded package once the backend confirms it as legitimate).

### Proof of Concept
1. Attacker completes a normal biometric capture/pipeline pass with the FOSS build (where local `detect_fraud` always returns `false`, but this holds even with fraud checks enabled since it's the *backend's* duplicate/fraud check that lags): [9](#0-8) 
2. `build_pcp` and the subsequent tier0/tier1/tier2 uploads execute unconditionally, persisting iris codes/embeddings/keys to S3: [3](#0-2) 
3. `enroll_user` then calls the backend, which detects the attempt as a duplicate or fraudulent signup and returns `success: false` at `signup_poll`: [4](#0-3) 
4. `do_signup` returns with `result.success = false`, and `after_signup` runs only debug-report upload / UI cleanup — the previously uploaded PCP tiers are never deleted: [7](#0-6) 

Consequence: biometric secrets from a signup that the backend itself flags as duplicate/fraudulent remain stored, with no code path shown that retracts them.

        let SignupResult { capture_start, debug_report, .. } = signup_result;

            sleep(Duration::from_secs(5)).await;
            return Ok(());

        let Some(debug_report) = debug_report else { return Ok(()) };

        tracing::info!("After-signup phase");
        dd_timing!("main.time.signup.full_signup", capture_start);

        let signup_status = debug_report.signup_status.clone();

        let enrollment_status = debug_report.enrollment_status.clone();
        let failure_feedback = debug_report.failure_feedback_after_capture_proto();
        Box::pin(self.upload_debug_report(orb, debug_report)).await?;

        if let Some(signup_status) = signup_status {
            Self::ui_complete_signup(orb, &signup_status, enrollment_status);
        }

        if orb.config.lock().await.self_serve {
            if let Some(relay) = orb.orb_relay.as_mut() {
                relay
                    .send(self_serve::orb::v1::SignupEnded {
                        success: signup_result.success,
                        failure_feedback,
                    })
                    .await
                    .inspect_err(|e| tracing::error!("Relay: Failed to SignupEnded: {e}"))?;
