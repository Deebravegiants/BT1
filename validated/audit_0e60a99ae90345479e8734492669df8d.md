## Analysis

The equality claimed to be broken: `public_key` embedded in the sep53 `MultiPayload` (derived from `stellarAddressToBytes(userInfo.userAddress)`) must equal the raw ed25519 key bytes of the Stellar `G...` account that produced `signature`.

`stellarAddressToBytes` decodes the base32 string, splits off the last byte-pair as a CRC16-XModem checksum, verifies that checksum, and returns `payload.slice(1)` — but it **never inspects the version byte** (`payload[0]`), the byte that distinguishes an account ID (`0x30`, `G...`) from a seed (`0x18`, `S...`), a pre-auth tx hash, a signed payload, or a muxed account. [1](#0-0) 

However, this scope's premise — "an attacker supplies a userAddress string" — does not correspond to a real cross-user attack surface. `userInfo.userAddress`/`userChainType` is not an untrusted counterparty field like `assetId`, `destinationAddress`, `memo`, `routeConfig`, etc. It is the **caller's own wallet address**, passed by the same party that is constructing and submitting their own `prepareSwapSignedData`/`publishIntent` call for their own signed intent: [2](#0-1) [3](#0-2) 

If a user deliberately feeds their own seed string (or any malformed but checksum-valid string) as `userAddress`, they only harm themselves: the resulting `public_key` in their own `MultiPayload` would not correspond to a key that could ever have produced a valid `signature` over the actual intent message via the sep53/ed25519 verification performed by intents.near. The intents contract's own signature verification (`ed25519` verify of `signature` against `public_key` and the exact payload) would simply reject the intent — since the "wrong" derived bytes are not the attacker's real signing key, the signature check fails and the intent is never accepted. There is no second party whose funds, identity, or signer_id could be hijacked this way: this is a self-inflicted malformed input, not an attack on another user or on protocol invariants enforced by this SDK.

The rules explicitly exclude findings that only affect the caller supplying their own malformed data to their own request, and require the impact be something signed/debited/routed/misreported **that the caller did not ask for**, affecting another party. Here, the caller controls both the `userAddress` and the `signature`/`quoteHashes` sent in their own `publishIntent` call — there is no cross-user equality (`SIGNED(x) != BUILT(y)` for two different, mutually-untrusting parties) that this missing version-byte check breaks in a way that lets one unprivileged actor bind another party's funds, signer_id, or nonce to an unintended value.
