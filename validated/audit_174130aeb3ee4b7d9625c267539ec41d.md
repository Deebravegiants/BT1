### Title
`describeWithdrawal()` reports `completed` for non-EVM/Stellar/TON chains from bare contract status with zero txHash verification - (File: `packages/intents-sdk/src/bridges/hot-bridge/hot-bridge.ts`)

### Summary
In `HotBridge.describeWithdrawal()`, for withdrawals landing on chains outside `{EVM, Stellar, TON}`, the code short-circuits to `{status: 'completed', txHash: null}` as soon as `hotSdk.getGaslessWithdrawStatus(nonce)` returns `HotWithdrawStatus.Completed`, without ever calling the bridge indexer or the HOT API fallback that other branches use. This means the reported "completed" status is backed by no destination-chain evidence whatsoever, unlike the EVM/Stellar/TON path which requires an actual bridge-indexer- or API-sourced hash before declaring completion.

### Finding Description
The broken equality: reported `status === 'completed'` should imply "funds landed on the destination chain, proven by a `txHash`," but for the non-EVM/non-Stellar/non-TON branch this equality is violated — `completed` is asserted purely from a boolean-like contract view call result, with `txHash: null`.

Code path (`packages/intents-sdk/src/bridges/hot-bridge/hot-bridge.ts`, `describeWithdrawal`, lines 375-503):
1. `status` is fetched via `this.hotSdk.getGaslessWithdrawStatus(nonce.toString())` (line 389), a NEAR contract view call.
2. `isEvm`, Stellar, and `isTon` chains (lines 400-464) go through `fetchWithdrawalHashBridgeIndexer`, with API fallback (`fetchWithdrawalHashFromApi`) on indexer failure — completion is only reported when an actual destination `txHash` string is obtained.
3. For any other `landingChain` (the `else` branch, lines 465-500):
   - If `status === HotWithdrawStatus.Completed` (line 468), the function **immediately** returns `{status: 'completed', txHash: null}` (line 469) — no call to `fetchWithdrawalHashFromApi` or any indexer occurs in this case.
   - Only when `status` is a *different* string (raw hex bytes, lines 471-486) or not `Completed` at all (falls through to `fetchWithdrawalHashFromApi`, lines 489-499) does the code attempt to resolve or fetch a `txHash`.

So the one case where the contract explicitly signals `"COMPLETED"` is the one case that skips all verification and is trusted blindly, while ambiguous/pending states get an API fallback attempt. `HotWithdrawStatus` (`hot-bridge-constants.ts`) is defined as just two string constants (`"COMPLETED"`, `"CANCELED"`) with no further contract-side guarantee documented in this repo about when `Completed` is set relative to destination-chain finality.

None of the existing guards (`validateAddress`, `compareAddresses`, `validateWithdrawal`, `supports()` ordering, `FeeExceedsAmountError`, `getUnderlyingFee`, `assert` checks) touch `describeWithdrawal`'s completion-status logic at all — they operate at withdrawal-creation/fee-estimation time, not at status-polling time. There is no mechanism preventing an integrator from treating this bare, unverified `completed` result as truth via `watchWithdrawal`/`waitForWithdrawalCompletion`.

### Impact Explanation
Any integrator polling `describeWithdrawal` (directly or via `watchWithdrawal`) for a HOT-bridge withdrawal to a supported non-EVM/non-Stellar/non-TON chain will treat the withdrawal as `completed` — and typically release credit, mark an off-chain ledger entry, or unblock a downstream operation — the instant the contract's view status flips to `"COMPLETED"`, with `txHash: null` and no independent confirmation that funds actually landed. If that contract status can be set before (or independent of) actual bridge-side settlement, integrators are exposed to premature crediting with no on-chain proof to later verify or dispute. This matches the "status or hash misreport making an integrator credit... twice/prematurely" High-severity category, since it is a real code-path divergence between the safeguarded branch (EVM/Stellar/TON) and the unsafeguarded branch (all other chains), reachable simply by withdrawing to any bridge-supported chain in that category.

### Likelihood Explanation
Preconditions: HOT bridge must support at least one chain outside `{EVM, Stellar, TON}` (the code's own comment "Fallback for other non EVM networks" implies such chains exist/are expected), and a withdrawal must be routed there. No special attacker privilege is needed beyond being an ordinary user (or a counterparty whose destination chain an integrator forwards) initiating a normal HOT-bridge withdrawal to such a chain. Whether the contract genuinely sets `Completed` early relative to true destination finality is an external/contract-side behavior not verifiable purely from this repo's code, but the SDK-side gap — zero cross-check performed specifically for the `Completed` case — is definitively present and inconsistent with the verification standard applied to EVM/Stellar/TON. This is repeatable on every withdrawal to an affected chain, at zero extra attacker cost.

### Recommendation
For the non-EVM/non-Stellar/non-TON branch, do not return `completed` on `HotWithdrawStatus.Completed` alone. Instead, treat `Completed` the same as the ambiguous/pending cases: attempt to resolve a concrete `txHash` via `fetchWithdrawalHashFromApi` (or a bridge indexer if available for that chain) before reporting `completed`; if no hash can be resolved, return `{status: 'pending'}` rather than `{status: 'completed', txHash: null}`.

```ts
// vitest, mocking only the HOT SDK contract-view call (hotSdk.getGaslessWithdrawStatus)
// and the HOT API fetch (hotSdk.api.requestApi) — no other internals touched.

it("reports completed with null txHash for non-EVM/Stellar/TON chain based on bare contract status", async () => {
  const hotSdk = {
    near: { parseWithdrawalNonces: vi.fn().mockResolvedValue([123n]) },
    getGaslessWithdrawStatus: vi.fn().mockResolvedValue(HotWithdrawStatus.Completed),
    api: { requestApi: vi.fn() }, // should NOT be called
  };
  const bridge = new HotBridge({ envConfig, hotSdk, solverRelayApiKey: undefined });

  const result = await bridge.describeWithdrawal({
    landingChain: Chains.SomeOtherChain, // e.g. a chain kind that is neither eip155:*, Stellar, nor TON
    index: 0,
    withdrawalParams: {/* ... */},
    tx: { hash: "near-tx-hash", accountId: "acc.near" },
  });

  // Assert the broken equality: 'completed' reported with NO destination-side evidence
  expect(result).toEqual({ status: "completed", txHash: null });
  // Assert no cross-check was ever attempted for this "Completed" case
  expect(hotSdk.api.requestApi).not.toHaveBeenCalled();
});
```
This demonstrates that, unlike the EVM/Stellar/TON path (which requires `fetchWithdrawalHashBridgeIndexer`/API to yield a real hash before declaring completion), the non-EVM/Stellar/TON branch reports `completed` purely from `getGaslessWithdrawStatus === HotWithdrawStatus.Completed`, with `txHash: null` and zero calls to any hash-resolution mechanism.
