### Title
Withdrawal status/hash misattribution across identical-token batch withdrawals - (File: `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`)

### Summary
`PoaBridge.describeWithdrawal` matches a withdrawal's on-chain completion status/tx-hash purely by `assetId`, ignoring the `index`/destination/amount that uniquely identify each leg of a batch withdrawal, so two withdrawals of the same token in one batch collapse onto the same reported status.

### Finding Description
`describeWithdrawal` fetches all withdrawals for a NEAR transaction hash and calls `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`, which resolves to `withdrawals.find((w) => nep141:${w.data.near_token_id} === assetId)` [1](#0-0) [2](#0-1) . The code comment acknowledges the gap explicitly: "multiple withdrawals of the same token in a single transaction are not supported" [3](#0-2) . Because `.find()` always returns the first array element matching that `assetId`, every `WithdrawalIdentifier` sharing that `assetId` (i.e. every index in a batch withdrawing the same token to different destinations) resolves to the same underlying `withdrawal` record — the same `status` and the same `transfer_tx_hash`. This is consumed by `watchWithdrawal`/`waitForWithdrawalCompletion`, which reports `{status: "completed", txHash}` per index independently [4](#0-3) , and by `sdk.waitForWithdrawalCompletion` which resolves per-index promises for batch withdrawals [5](#0-4) . The equality broken: "the withdrawal identified by index N landed with tx hash H" is not actually validated — the same H (and completed/failed/pending status) gets attributed to a different, unrelated withdrawal leg with a different destination address and possibly different amount and outcome.

### Impact Explanation
An integrator that batches two withdrawals of the same POA-bridged token (e.g., to two different destination addresses in one call to `sdk.processWithdrawal`/`sdk.waitForWithdrawalCompletion`) can be told both legs "completed" with the same `txHash`, or have one leg's failure/pending status suppressed by the other leg's completed record. This matches the "status or hash misreport making an integrator credit or refund twice" High-impact category — an integrator relying on this API's per-index completion result could credit/settle both withdrawals based on one on-chain transfer, or fail to detect that the other leg genuinely failed.

### Likelihood Explanation
This does not require any adversarial actor — a normal, benign batch withdrawal request from the SDK's own supported API surface (`withdrawalParams: WithdrawalParams[]`) with two entries sharing an `assetId` is sufficient to trigger it. The bug is already self-documented in code as a known unsupported case, but the SDK provides no runtime guard (assertion/throw) preventing or flagging such batches; `supports()`/`validateWithdrawal()` perform no duplicate-assetId check across batch entries.

### Recommendation
- Reject (throw) batch withdrawals in `IntentsSDK`/`PoaBridge` when two or more entries share the same `assetId`, until POA API-side disambiguation is available, or
- Disambiguate `findMatchingWithdrawal` by additionally matching `data.address` (destination) and `data.amount`, consuming matched entries so subsequent lookups for the same `assetId` don't reuse an already-claimed record.

### Proof of Concept
1. Call `sdk.waitForWithdrawalCompletion({ withdrawalParams: [ {assetId: "nep141:zec.omft.near", destinationAddress: A, amount: 100}, {assetId: "nep141:zec.omft.near", destinationAddress: B, amount: 200} ], intentTx })`.
2. POA bridge indexer returns two withdrawal records for the same NEAR tx hash, one COMPLETED to `A` and one still PENDING/FAILED to `B`.
3. `findMatchingWithdrawal` is called twice (once per index) with the identical `assetId`, both times returning `Array.find`'s single first match (the COMPLETED record for `A`).
4. Both index-0 and index-1 promises resolve `{status: "completed", txHash: <A's hash>}`, even though the withdrawal to `B` never completed — see `describeWithdrawal` at [6](#0-5) .

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}

function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
