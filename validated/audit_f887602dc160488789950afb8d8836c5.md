### No vulnerability found for this question.

**Reasoning:**

The equality claimed to be broken would be: `HmacValidator.validate(query) == true` while `query.hmac` was computed by an attacker who does not possess `Context.api_secret_key` *or* `Context.old_api_secret_key`.

Tracing `ShopifyAPI::Utils::HmacValidator.validate`: [1](#0-0) 

The guard `return false unless verifiable_query.hmac` only rejects a `nil`/missing `hmac` field (e.g. an omitted query param or missing webhook header); it does not need to check digest length because the actual authentication decision is made later by `OpenSSL.secure_compare(computed_signature, received_signature)` in `validate_signature`, which will simply return `false` if the received value doesn't match the HMAC-SHA256 hex digest computed over `to_signable_string` — a length mismatch just fails the comparison, it does not create a bypass. [2](#0-1) 

The fallback to `Context.old_api_secret_key` is a deliberate, documented secret-rotation mechanism (`Context.setup` accepts `old_api_secret_key:`), letting requests signed with a previous secret validate during rotation: [3](#0-2) [4](#0-3) 

Exercising that branch requires producing `OpenSSL::HMAC.hexdigest(sha256, old_api_secret_key, signable_string)` that matches — i.e., the attacker must already know `Context.old_api_secret_key`. The question's own attacker model explicitly excludes this: "They never hold `api_secret_key`, `old_api_secret_key`, an access token or any leaked credential." Test `test_valid_signature_signed_with_old_api_secret_key` confirms the fallback only succeeds when the caller supplies the correct old secret value, not an attacker-chosen or absent one: [5](#0-4) 

Since forging a signature valid under `old_api_secret_key` requires possession of that secret, and the rules explicitly reject "any path requiring app secrets," the premise of the question (an unprivileged attacker producing such a signature) is unreachable under the stated attacker model. The `to_signable_string` / signature-coverage argument and the UTF-8 vs ASCII-8BIT encoding scenario don't change this: HMAC operates on the underlying bytes regardless of Ruby string encoding tag, so re-tagging an identical byte sequence as `ASCII-8BIT` does not change `OpenSSL::HMAC.hexdigest`'s output, and this was not shown to allow an attacker without the secret to forge a valid signature.

No code path lets an unprivileged attacker (without `api_secret_key` or `old_api_secret_key`) cause `HmacValidator.validate` to return `true` for `ShopifyAPI::Auth::Oauth.validate_auth_callback` or `ShopifyAPI::Webhooks::Registry.process`. [6](#0-5) [7](#0-6)
