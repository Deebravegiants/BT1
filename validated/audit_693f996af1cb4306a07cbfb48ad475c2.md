### Title
Unused/refunded native ETH from LI.FI swap calls becomes permanently trapped in `LifiExternalAction` / `ExternalActionSwap` with no recovery path - ([File: contracts/external-actions/swaps/LifiExternalAction.sol])

### Summary
`LifiExternalAction.callRouter` forwards `inputAmount` of native ETH to the LI.FI router and measures the swap result solely by the balance delta of `outputToken`. If the router returns unused/leftover ETH to this contract (a documented LI.FI/router behavior when a swap consumes less native value than sent, or when intermediate bridging legs revert/short-circuit), that returned ETH increases the contract's ETH balance but is never included in `swappedAmount`, never forwarded to the relay/user, and — because the contract only exposes `receive() external payable {}` with no withdraw function — can never be extracted afterward.

### Finding Description
`ExternalActionSwap`/`LifiExternalAction` accept native ETH as `inputToken` and pass the full `inputAmount` as `msg.value` to the router: [1](#0-0) 

`swappedAmount` is computed strictly as the delta of `outputToken`'s balance before/after the router call: [2](#0-1) 

Back in `ExternalActionSwap.swap`, only `outputToken` (scaled by `amountToSendToHinkal`) is transferred back to the caller (Hinkal contract); any leftover/refunded ETH balance is never referenced again: [3](#0-2) 

The contract only declares a bare `receive()` with no corresponding rescue/withdraw entrypoint: [4](#0-3) 

This breaks the intended balance equality that Hinkal enforces at the top level in `Hinkal.transact`, which only checks the balance delta for each `erc20TokenAddresses[i]` explicitly listed in `circomData` — any ETH balance increase on the external-action contract that is not one of the tracked tokens (e.g. ETH returned as "change" when the tracked pair is ERC20→ERC20, or ETH sent in as `inputToken` but partially refunded) is invisible to this accounting and is never moved back into the shielded pool or to the relay/fee recipients: [5](#0-4) 

Because value can enter the `ExternalActionSwap`/`LifiExternalAction` contract (via `receive()`) but the contract has no function that can move ETH back out except through the strict `outputToken` accounting path in `swap()`, any residual ETH is permanently stranded.

### Impact Explanation
Any ETH left over from a router refund is permanently unrecoverable — there is no owner/admin rescue function and no user-triggerable withdraw path in `ExternalActionSwap` or `LifiExternalAction`. This is a permanent freezing of user/protocol funds routed through the swap external action, since the input ETH originated from a user's shielded balance that was moved out of the Hinkal pool for the swap.

### Likelihood Explanation
Likelihood is low-to-moderate: it requires (a) using ETH as the swap `inputToken` through the LI.FI external action, and (b) the underlying LI.FI/router call path returning unused native value to the caller (e.g., partial fills, intermediate leg failures with refund, or `inputAmount` overestimation relative to what the aggregated route actually consumes). This does not require any privileged role or user mistake — it is a normal, externally-triggerable interaction with the router via the standard `runAction` flow.

### Recommendation
Either remove the generic `receive()` fallback from `ExternalActionSwap` (and rely on explicit ETH accounting only when `inputToken == address(0)`), or add explicit handling in `callRouter`/`swap` to sweep any residual native ETH balance back to `msg.sender` (the Hinkal contract) alongside `outputToken`, so leftover value is folded into the balance-delta accounting Hinkal performs, or explicitly refund/relay it. At minimum, add an owner-gated (or Hinkal-gated) rescue function that can move stray ETH out of the external-action contract into the correct UTXO/relay flow rather than leaving it permanently stuck.

### Proof of Concept
1. User initiates a Hinkal `transact` with `externalActionId` pointing to `LifiExternalAction`, `erc20TokenAddresses = [address(0), USDC]` (ETH → USDC swap), with `inputAmount` computed from the shielded balance.
2. `Hinkal._externalTransact` forwards `inputAmount` ETH to `LifiExternalAction` via `transferERC20TokenOrETH`. [6](#0-5) 
3. `LifiExternalAction.callRouter` forwards the full ETH balance to `router.call{value: inputAmount}(externalActionMetadata)`.
4. The LI.FI route (e.g., a multi-hop/bridge route encoded off-chain) consumes less than `inputAmount` and the router refunds the difference to `msg.sender` (i.e., `LifiExternalAction`), which is silently accepted by `receive()`.
5. `swappedAmount` is computed only from the `USDC` balance delta, so the refunded ETH is excluded from all downstream accounting; `swap()` only forwards `USDC` back to Hinkal.
6. The refunded ETH remains on `LifiExternalAction` indefinitely — there is no function in `ExternalActionSwap`, `LifiExternalAction`, `ExternalActionBaseV2`, or `OwnerHinkal` (as far as reachable in the in-scope contracts) that can transfer arbitrary ETH out of the contract.

Note: I was not able to fully verify the contents of `OwnerHinkal.sol` in this pass (its code wasn't returned by search), so I cannot rule out with certainty that it contains a generic owner-only ETH rescue function that would mitigate this to a lower-severity/admin-recoverable issue rather than a permanent freeze. If Devin has time to open `contracts/OwnerHinkal.sol` directly, that should be checked to confirm severity.

    function callRouter(
        address inputToken,
        uint256 inputAmount,
        address outputToken,
        bytes calldata externalActionMetadata
    ) internal override returns (uint256 swappedAmount) {
        uint256 balanceBefore = getERC20OrETHBalance(outputToken);

        if (inputToken == address(0)) {
            (bool success, ) = router.call{value: inputAmount}(
                externalActionMetadata
            );
            require(success, "LI.FI swap failed: native coin");
        } else {
            approveUnlimited(inputToken, router);
            (bool success, ) = router.call(externalActionMetadata);
            require(success, "LI.FI swap failed: erc-20 token");
        }

        swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore;
    }
