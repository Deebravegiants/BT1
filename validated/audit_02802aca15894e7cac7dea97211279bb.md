## Finding: `SignerCapabilityOfferProofChallengeV2` omits `chain_id`, unlike its sibling `RotationCapabilityOfferProofChallengeV2` — cross-chain replay of full signer-capability grants

### Title
Missing chain-id domain separator in `offer_signer_capability`'s signed challenge enables cross-network replay of full account-control grants - (File: `aptos-move/framework/aptos-framework/sources/account/account.move`)

### Summary
Aptos' `account.move` already recognizes that a signed authorization message must be bound to the network via `chain_id` to prevent replay — this is explicitly done for `RotationCapabilityOfferProofChallengeV2` and `MultisigAccountCreationMessage`. However, the structurally identical `SignerCapabilityOfferProofChallengeV2`, used to authorize `offer_signer_capability` (which grants the recipient full `signer` authority over the offering account), does not include `chain_id`. This is the same class of bug as the external report: a signed authorization digest lacking a domain separator that ties it to a specific network.

### Finding Description
`account.move` defines two "V2" offer-challenge structs used to gate delegation of powerful capabilities: [1](#0-0) 

The comment on `RotationCapabilityOfferProofChallengeV2` is explicit about the design intent — chain_id was added specifically to prevent replay across networks:
```
/// This V2 struct adds the `chain_id` and `source_address` to the challenge message, which prevents replaying the challenge message.
struct RotationCapabilityOfferProofChallengeV2 has drop {
    chain_id: u8,
    sequence_number: u64,
    source_address: address,
    recipient_address: address,
}
```
That fix is applied and used correctly in `offer_rotation_capability`: [2](#0-1) 

But `SignerCapabilityOfferProofChallengeV2`, the sibling struct used to gate `offer_signer_capability`, carries only `sequence_number`, `source_address`, `recipient_address` — no `chain_id`: [3](#0-2) 

It is built and verified this way in `offer_signer_capability`: [4](#0-3) 

The signature over this struct is produced via `ed25519::sign_struct`/`multi_ed25519::sign_struct`, which wraps the payload in `SignedMessage<T>` carrying `type_info::type_of<T>()` before BCS-serializing and signing: [5](#0-4) 

`type_info::type_of<T>()` binds the message to the fully qualified Move type (`0x1::account::SignerCapabilityOfferProofChallengeV2`), which prevents cross-*struct* confusion, but this qualified type is byte-for-byte identical on every network running the same Aptos Framework (mainnet, testnet, devnet, or any Aptos-based fork/L2 at address `0x1`). It provides **no chain-specific domain separation** — exactly the gap flagged in the external report ("chain ID ... absent" from the signed digest).

`verify_signed_message` only checks that the signature is valid for the account's current public key/auth key; it has no independent chain-binding check either: [6](#0-5) 

The `sequence_number` field included in the challenge only protects against *intra-chain* replay (each chain tracks its own sequence number independently and starts fresh); it does nothing to scope a signature to one network.

### Impact Explanation
`offer_signer_capability` is a custody-critical function: successfully verifying the challenge lets the `recipient_address` call `account::create_signer_with_capability` and obtain a `signer` for the offering account — i.e., complete, unrestricted authority to transfer/withdraw APT, fungible assets, and any object/resource controlled by that account, exactly the kind of "unauthorized takeover of ... resource-account control ... tied to live assets" the custody gate targets.

Because Aptos account addresses are deterministically derived from the public key (`auth_key = sha3_256(pk || scheme)`), the same address naturally exists with the same authentication key across every Aptos-Framework-compatible network (mainnet/testnet/devnet, or any fork/appchain deployed from this codebase) whenever a user reuses a keypair — a very common practice. An attacker who obtains a `SignerCapabilityOfferProofChallengeV2` signature intended for use on one network (e.g. solicited via a phishing dApp on testnet, or captured from a legitimate low-stakes offer on a devnet/appchain) can replay the identical signature bytes against `offer_signer_capability` on another network where the victim's account (same address, same auth key, not yet key-rotated) holds real value, since nothing in the signed payload differs between networks. This directly matches the custody pivot: "Multisig-owned assets, resource accounts... must not leak... transfer authority to unprivileged callers."

### Likelihood Explanation
Exploitation requires only (a) the victim to have signed a `SignerCapabilityOfferProofChallengeV2` message on any Aptos-compatible network (which can be solicited via a malicious front-end presenting it as a low-risk action, since it looks identical to a benign devnet/testnet offer) and (b) the victim's account to exist with the same auth key on another network with real assets — a realistic scenario given Aptos's deterministic address derivation and common key reuse across mainnet/testnet by the same wallet. This is a design gap intentionally already fixed for the parallel rotation-capability struct, indicating the fix pattern is well understood but was not applied consistently.

### Recommendation
Add `chain_id: u8` to `SignerCapabilityOfferProofChallengeV2` (mirroring `RotationCapabilityOfferProofChallengeV2`) and update `offer_signer_capability` to populate it with `chain_id::get()`, with an appropriate framework upgrade/versioning path (e.g., a `V3` struct) since this is a binary-compatible but semantically breaking change to the signed message format.

### Proof of Concept
1. On Network A (e.g., a testnet/devnet running the same Aptos Framework), attacker tricks victim (or victim independently, in a low-value test context) into signing `SignerCapabilityOfferProofChallengeV2 { sequence_number, source_address = victim_addr, recipient_address = attacker_addr }` and submitting/leaking `signer_capability_sig_bytes`.
2. Victim's account with the same public key (hence identical address/auth key, per `account.move` derivation) also exists on Network B (mainnet or another compatible chain) and holds real APT/fungible-asset balances, with the same current sequence number state relevant to the offer having not changed (sequence numbers reset per-chain, so an unused nonce is trivially available on B).
3. Attacker submits the identical `signer_capability_sig_bytes`, `account_scheme`, `account_public_key_bytes`, `recipient_address` to `offer_signer_capability` on Network B.
4. `verify_signed_message` succeeds because the reconstructed `SignerCapabilityOfferProofChallengeV2` (lacking chain_id) is bit-identical to the one signed on Network A, and the auth key matches.
5. Attacker's address is now the signer-capability recipient for the victim's account on Network B; calling `create_signer_with_capability`-gated flows lets the attacker act with full custody authority over the victim's mainnet assets. [4](#0-3)

    public entry fun offer_signer_capability(
        account: &signer,
        signer_capability_sig_bytes: vector<u8>,
        account_scheme: u8,
        account_public_key_bytes: vector<u8>,
        recipient_address: address
    ) acquires Account {
        let source_address = signer::address_of(account);
        ensure_resource_exists(source_address);
        assert!(exists_at(recipient_address), error::not_found(EACCOUNT_DOES_NOT_EXIST));

        // Proof that this account intends to delegate its signer capability to another account.
        let proof_challenge = SignerCapabilityOfferProofChallengeV2 {
            sequence_number: get_sequence_number(source_address),
            source_address,
            recipient_address,
        };
        verify_signed_message(
            source_address, account_scheme, account_public_key_bytes, signer_capability_sig_bytes, proof_challenge);

        // Update the existing signer capability offer or put in a new signer capability offer for the recipient.
        let account_resource = &mut Account[source_address];
        account_resource.signer_capability_offer.for.swap_or_fill(recipient_address);
    }

    public fun verify_signed_message<T: drop>(
        account: address,
        account_scheme: u8,
        account_public_key: vector<u8>,
        signed_message_bytes: vector<u8>,
        message: T,
    ) acquires Account {
        let auth_key = get_authentication_key(account);
        // Verify that the `SignerCapabilityOfferProofChallengeV2` has the right information and is signed by the account owner's key
        if (account_scheme == ED25519_SCHEME) {
            let pubkey = ed25519::new_unvalidated_public_key_from_bytes(account_public_key);
            let expected_auth_key = ed25519::unvalidated_public_key_to_authentication_key(&pubkey);
            assert!(
                auth_key == expected_auth_key,
                error::invalid_argument(EWRONG_CURRENT_PUBLIC_KEY),
            );

            let signer_capability_sig = ed25519::new_signature_from_bytes(signed_message_bytes);
            assert!(
                ed25519::signature_verify_strict_t(&signer_capability_sig, &pubkey, message),
                error::invalid_argument(EINVALID_PROOF_OF_KNOWLEDGE),
            );
        } else if (account_scheme == MULTI_ED25519_SCHEME) {
            let pubkey = multi_ed25519::new_unvalidated_public_key_from_bytes(account_public_key);
            let expected_auth_key = multi_ed25519::unvalidated_public_key_to_authentication_key(&pubkey);
            assert!(
                auth_key == expected_auth_key,
                error::invalid_argument(EWRONG_CURRENT_PUBLIC_KEY),
            );

            let signer_capability_sig = multi_ed25519::new_signature_from_bytes(signed_message_bytes);
            assert!(
                multi_ed25519::signature_verify_strict_t(&signer_capability_sig, &pubkey, message),
                error::invalid_argument(EINVALID_PROOF_OF_KNOWLEDGE),
            );
        } else {
            abort error::invalid_argument(EINVALID_SCHEME)
        };
    }
