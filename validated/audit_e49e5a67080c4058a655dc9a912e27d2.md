## Analysis: Uncontrolled Resource Consumption Analog in Chainlink Gateway

The CVE (CVE-2022-1699) is a generic "unauthenticated request causes uncontrolled resource consumption / DDoS" bug class. I found a reachable analog in the Chainlink Gateway's legacy user-message path.

### Title
Unauthenticated Gateway User Requests Fan Out to All DON Nodes Without Allowlist or Rate-Limiting - (File: `core/services/gateway/handlers/capabilities/handler.go`)

### Summary
The Gateway's `UserServerConfig` HTTP endpoint accepts requests with no authentication requirement (only a byte-size cap), and every accepted `web_api_trigger` message is unconditionally broadcast to every member node of the DON, with a TODO explicitly acknowledging the missing allowlist/rate-limit check.

### Finding Description
`gateway.ProcessRequest` decodes any incoming HTTP body and, for legacy requests, calls `h.HandleLegacyUserMessage` [1](#0-0)  without any caller-identity check — the `UserServerConfig` (e.g. `core/scripts/gateway/sample_config.toml`) has no auth/session/API-key gate, only `MaxRequestBytes`.

Inside `HandleLegacyUserMessage`, the code performs payload parsing, a staleness check, and a method check, but the comment `// TODO: apply allowlist and rate-limiting here` sits directly above the fan-out logic [2](#0-1) . After that point, the handler stores a callback keyed by attacker-controlled `msg.Body.MessageID` and then sends the request to **every** DON member: [3](#0-2) 

The `savedCallbacks` map has size/age based mitigation via `pruneCallbacks` (bounded by `MaxSavedCallbacks`, default 20000) [4](#0-3) [5](#0-4) , so pure map-memory growth is capped. However, there is **no rate limiting on the ingress (unauthenticated) side of this path** — `nodeRateLimiter` in this handler only throttles messages coming *from* nodes (`handleWebAPIOutgoingMessage`), not user-submitted trigger requests [6](#0-5) . Each accepted user request causes one send-to-node call per DON member, so a single unauthenticated client can multiply a small request volume into N times the outbound message/network load on the DON.

### Impact Explanation
An unauthenticated actor can repeatedly submit trivially-crafted `web_api_trigger` JSON-RPC bodies to the Gateway's public user-facing port. Each request is amplified into one message per DON member (`don.SendToNode`), and processed by every one of those Chainlink nodes. Since there is no per-sender or global limiter on this legacy ingress path, this allows resource-consumption amplification against both the Gateway and the DON nodes, degrading availability for legitimate workflow triggers — matching the "Uncontrolled Resource Consumption" DDoS bug class of the reference CVE.

### Likelihood Explanation
Likelihood is moderate-to-high: the endpoint is internet-facing by design (it's the "UserServerConfig" — the intended ingress for external triggers), requires no credentials, and the missing-rate-limit gap is explicitly flagged by a TODO comment in the shipped code, indicating it is a known, not-yet-addressed gap rather than a hardened path.

### Recommendation
Implement the allowlist/rate-limiting called out by the TODO in `HandleLegacyUserMessage` before the fan-out to DON members — e.g., reuse the same per-sender/global `ratelimit.RateLimiter` pattern already used elsewhere in the gateway (see `nodeRateLimiter`, `incomingRateLimiter` in `core/capabilities/webapi/outgoing_connector_handler.go`) on the ingress side, and reject/allowlist-check senders prior to broadcasting to all DON members.

### Proof of Concept
1. Stand up a Gateway with `UserServerConfig` exposed per `core/scripts/gateway/sample_config.toml` (no auth configured).
2. Send repeated POST requests to the user endpoint with a legacy-format `web_api_trigger` message body (valid `Timestamp`, arbitrary unique `MessageID`s) — no credentials required.
3. Observe that each request results in `don.SendToNode` calls to all configured DON members [7](#0-6) , with no rate limit rejecting the flood, consuming Gateway and DON node resources proportionally to (request rate × number of DON members).

---
Note: this is a code-pattern analog based on static analysis of the noted TODO and missing rate limiter on this ingress path; it has not been dynamically verified against a running deployment.

func (h *handler) pruneCallbacks() {
	h.mu.Lock()
	defer h.mu.Unlock()

	// First, remove expired callbacks.
	maxAge := time.Duration(h.config.CallbackMaxAgeSec) * time.Second
	now := time.Now()
	var expired int
	for id, cb := range h.savedCallbacks {
		if now.Sub(cb.createdAt) > maxAge {
			delete(h.savedCallbacks, id)
			expired++
		}
	}

	// If there are still too many callbacks, sort them by creation time and remove the oldest ones.
	maxSize := h.config.MaxSavedCallbacks
	var evicted int
	if len(h.savedCallbacks) > maxSize {
		type entry struct {
			id        string
			createdAt time.Time
		}
		entries := make([]entry, 0, len(h.savedCallbacks))
		for id, cb := range h.savedCallbacks {
			entries = append(entries, entry{id, cb.createdAt})
		}
		sort.Slice(entries, func(i, j int) bool {
			return entries[i].createdAt.Before(entries[j].createdAt)
		})
		// Trim to maxSize/2 to avoid sorting the list too frequently.
		for _, e := range entries[:len(entries)-maxSize/2] {
			delete(h.savedCallbacks, e.id)
			evicted++
		}
	}

	if expired > 0 || evicted > 0 {
		h.lggr.Infow("Pruned savedCallbacks", "expired", expired, "evicted", evicted, "remaining", len(h.savedCallbacks))
	}
}
