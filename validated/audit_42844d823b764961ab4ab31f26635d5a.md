Based on my investigation, `_authenticate` confirms `_instance(request.source) == request.from` — it verifies the message came from *the registered gateway on the chain the message claims to be from*, but it never checks that `request.source` is the specific chain that the `body.commitment`'s order was actually placed against (`order.destination` / `order.source`). Since `_orders[commitment][token]` is a flat global mapping keyed only by `commitment` and `token` (no chain binding), any registered peer IntentGateway instance on **any** other connected chain can forge a `RedeemEscrow`/`RefundEscrow` message referencing an arbitrary `commitment` that has escrow on this chain, and `_withdraw` will pay out. This mirrors the Open WebUI class of bug precisely: access control is checked on the "container" (the trusted peer/gateway per the source chain) but not on whether the specific object (the order commitment) actually belongs to that container.

### Title
Cross-chain escrow redemption/refund does not bind the withdrawal to the order's registered counterpart chain, enabling any connected peer gateway to drain another order's escrow - (File: evm/src/apps/intentsv2/ExtrinsicIntents.sol)

### Summary
`onAccept` authenticates `RedeemEscrow`/`RefundEscrow` messages only by checking that the message's `source` chain has a registered `IntentGateway` instance matching `request.from` [1](#0-0) . It never verifies that the specific `order.commitment` embedded in the `WithdrawalRequest` body was actually placed with that chain as its `destination` (for `RedeemEscrow`) or `source` (for `RefundEscrow`). `_withdraw` then pays out purely based on `_orders[commitment][token]` being non-zero [2](#0-1) .

### Finding Description
`IntentGatewayV2`/`ExtrinsicIntents` maintains a registry of trusted peer gateway deployments per state machine (`_instance`/`_addDeployment`), and `onAccept` dispatches `RedeemEscrow`/`RefundEscrow` requests to `_withdraw` after calling `_authenticate`: [3](#0-2) 

`_authenticate` only checks that the message purportedly originates from the registered gateway module for whatever `request.source` chain the message claims: [1](#0-0) 

Once authenticated, `_withdraw` looks up escrow purely by `body.commitment` and `token`, with no cross-check against the order's `source`/`destination` fields recorded when the order was originally placed and escrowed: [2](#0-1) 

Because `_orders` is a flat `mapping(bytes32 => mapping(address => uint256))` with no per-counterpart-chain namespacing, and Hyperbridge is a hub connecting many chains, any state machine that has a legitimately registered `IntentGateway` instance can dispatch a `PostRequest` (source = that chain, from = its registered gateway address) carrying an arbitrary `commitment` value copied/observed from an order actually destined for a *different* chain. `_authenticate` passes because the message truly is from that chain's registered gateway — the check only validates the messenger's identity, not that the messenger is the counterpart this specific order was bound to. `_withdraw` then finds `_orders[commitment][token] != 0` (escrow exists because the real order is still pending) and releases the tokens to whatever `beneficiary` the forging message specifies.

This is the direct analog of GHSA-26gm-93rw-cchf: Open WebUI validated write access to the *knowledge base* (the container) but not that the *file id* actually belonged to that knowledge base, letting an attacker delete arbitrary files by supplying a valid file id under their own, unrelated knowledge base. Here, the contract validates the identity of the *messaging peer chain* (the container/context) but not that the *order commitment* actually belongs to a cross-chain relationship with that peer, letting any connected chain's gateway drain escrow for orders that were never destined for/sourced from it.

### Impact Explanation
A compromised, malicious, or simply misconfigured `IntentGateway` deployment on any one connected chain (which need not be the order's actual counterpart) can dispatch forged `RedeemEscrow`/`RefundEscrow` messages that pass `_authenticate` and drain another chain-pair's escrowed user funds to an attacker-controlled `beneficiary`. This is concrete theft of escrowed user funds across the intents system — the exact fund-loss class the "no-impact" exclusion rules require (arbitrary-file-deletion analog → arbitrary escrow-drain).

### Likelihood Explanation
Exploitability requires control of, or the ability to relay through, a legitimately registered `IntentGateway` instance on some chain other than the victim order's counterpart — realistic for any of Hyperbridge's many supported state machines given the protocol's multi-chain design, and does not require any admin/governance/relayer key compromise on the victim chain itself; only a normal cross-chain `PostRequest` dispatch from an already-registered peer gateway is needed.

### Recommendation
Bind the withdrawal authorization to the specific order rather than only to the messaging chain: store (or derive) each order's expected counterpart chain at placement time (e.g., `order.source`/`order.destination`, which are already part of the commitment preimage) and, inside `onAccept`'s `RedeemEscrow`/`RefundEscrow` branch, additionally require that `request.source` equals the counterpart chain recorded for `body.commitment` before calling `_withdraw`. Equivalently, namespace `_orders` (or a companion mapping) by counterpart chain id so that escrow can only be released by the specific chain the order was actually sent to/from.

### Proof of Concept
1. `ChainX` and `ChainY` both have legitimately registered `IntentGatewayV2` instances known to `ChainZ`'s gateway (`_instances[ChainX] = gatewayX`, `_instances[ChainY] = gatewayY`).
2. User places a cross-chain order on `ChainZ` with `destination = ChainX`; escrow is recorded at `_orders[commitment][token] = amount`.
3. An attacker who controls (or can relay through) `gatewayY` on `ChainY` crafts and dispatches a `PostRequest` with `source = ChainY`, `from = gatewayY`, body = `RedeemEscrow` kind encoding `WithdrawalRequest{commitment: commitment, tokens: order.inputs, beneficiary: attacker}` — reusing the same `commitment` value observed from the real order (commitments are public via `OrderPlaced`/on-chain events).
4. This message is delivered to `ChainZ`'s gateway via Hyperbridge; `onAccept` calls `_authenticate`, which succeeds because `_instance(ChainY) == gatewayY` really is true.
5. `_withdraw` finds `_orders[commitment][token] != 0` (the legitimate escrow) and transfers the tokens to `attacker`, even though `ChainY` was never the order's registered destination. [3](#0-2) [1](#0-0) [2](#0-1)

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
