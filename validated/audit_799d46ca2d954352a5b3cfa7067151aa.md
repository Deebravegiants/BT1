### Title
Hostile HyperSwap V2 pre-seed can force `Bonding._seedRebalancing` into an unguarded `_seedDirectMint` fallback, donating the graduation LP deposit to the attacker's pre-minted LP position - ([File: packages/contracts/src/Bonding.sol])

### Summary
`Bonding.finalizeGraduation` → `_seedUniswapV2Direct` → `_seedRebalancing` defends against a hostile "mint pre-seed" of the HyperSwap V2 TOKEN/LT pair by rebalancing the pool toward the curve-close ratio via `_pairRebalance` before depositing through the router. The only place the code explicitly re-routes to the raw `_seedDirectMint(...)` primitive against a *non-empty* pool (`totalSupply() != 0`, i.e. attacker already holds pre-minted LP) is gated by the "both sides below `DIRECT_MINT_PRESEED_BPS`" dust check at [1](#0-0) . However, `_pairRebalance` can independently return `false` — and trigger the exact same unguarded `_seedDirectMint` fallback — whenever its fee-charging quote rounds to zero, which is a function of the *ratio* being swapped, not of the absolute reserve size [2](#0-1) . That second path is reached without re-verifying the "reserves are negligible" precondition the dust-gate exists to enforce, at [3](#0-2) .

### Finding Description
`_seedDirectMint` unconditionally transfers `(tokensForLP, ltFromPair)` into the pair and calls `IUniswapV2Pair(pair).mint(lpLock)` [4](#0-3) . This primitive is only safe to call against an *empty* pool (`totalSupply() == 0`), because Uniswap V2's `mint()` computes `liquidity = min(amount0*S/r0, amount1*S/r1)` once `S = totalSupply() > 0`; any side whose contributed amount exceeds the ratio implied by the smaller side is silently donated into pool reserves and captured pro-rata by *all* existing LP holders, including a pre-existing attacker position. This exact concern is what `_seedRebalancing` is built to prevent for the "mint pre-seed" regime, per its own natspec at [5](#0-4) .

The dust-gate at lines 1297–1302 legitimizes calling `_seedDirectMint` against a non-empty pool only when *both* `reserveToken` and `reserveLT` are within `DIRECT_MINT_PRESEED_BPS` (1 bp) of their LP targets — i.e. the pre-seed is provably negligible [6](#0-5) . If that gate is not hit (at least one side is not dust), control instead flows to `_pairRebalance` [3](#0-2) . `_pairRebalance` returns `false` — again falling back to `_seedDirectMint` on a non-empty pool — whenever `_noFeeSwapInput` computes `s == 0`, or the pair's fee-charging `getAmountOut(s, tokenIn)` rounds to zero [7](#0-6) . Both conditions are governed by the *relative ratio* between `(reserveIn, reserveOut)` and the target `(targetN, targetD)`, not by an absolute-size floor: an attacker can pre-seed the pair with reserves large enough to clear the dust-gate at lines 1297–1302, yet shaped so the required rebalance swap size rounds to zero under `_noFeeSwapInput`/`getAmountOut`. In that engineered case, the code takes the same "overpower the pre-seed" `_seedDirectMint` path that was only proven safe for negligible reserves, but now against reserves the dust-gate itself classified as non-negligible.

This mirrors the WASI `open_at`/`path_open` bug class precisely: a state-mutating operation (`TRUNCATE`, here `pair.mint()` against a live, attacker-controlled LP supply) is reachable through a control-flow branch (`OpenFlags::TRUNCATE`-only, here `_pairRebalance` returning `false` via rounding) that was never folded into the permission/precondition check (`open_mode |= OpenMode::WRITE`, here the `DIRECT_MINT_PRESEED_BPS` dust-size gate) guarding that operation on the primary path.

### Impact Explanation
A successful exploit lets an attacker who pre-creates and pre-mints LP against the HyperSwap V2 TOKEN/LT pair before `finalizeGraduation` is called capture part of the protocol's own graduation deposit (`tokensForLP`/`ltFromPair`, funded from curve-raised LT and the token's LP reserve) as unlocked LP under their own address, rather than having it fully credited as `liquidity` locked via `LPLock.recordLock` [8](#0-7) . The attacker can then withdraw the donated value by burning their own (unlocked) LP tokens, directly stealing funds that should have backed the graduated pool/LP-lock — an LP seeded away from the curve-close price and a real transfer of value out of the protocol's graduation deposit, at the expense of the token's creator, traders and future LPs.

### Likelihood Explanation
`finalizeGraduation` is explicitly permissionless ("keeper drives the happy path; anyone can rescue a stuck token") [9](#0-8) , and the HyperSwap V2 pair for a given TOKEN/LT is not created until phase 2 unless an attacker front-runs it — `_ensureUniswapV2Pair` will happily reuse a pair that already exists [10](#0-9) . An attacker can acquire the launched TOKEN (via `Zap.buy`) and LT (directly from BounceTech), pre-create the V2 pair, and pre-mint LP with a ratio/size engineered to survive the dust-gate but defeat `_pairRebalance`'s rounding. This requires careful sizing but no privileged access and no race against the honest flow beyond ordinary front-running of pair creation — a realistic Medium/High-likelihood griefing-for-profit scenario.

### Recommendation
Re-validate the "reserves are negligible relative to the LP-bound target" invariant immediately before any call to `_seedDirectMint` against a non-empty pool, rather than relying solely on `_pairRebalance`'s boolean return. Concretely, when `_pairRebalance` returns `false`, re-check `reserveToken`/`reserveLT` against the `DIRECT_MINT_PRESEED_BPS` band (the same check already performed at lines 1297–1302) before falling back to `_seedDirectMint`; if the reserves are *not* negligible, force a swap via a minimum-output floor (or a smaller/adjusted swap size) rather than silently permitting a raw `mint()` donation.

### Proof of Concept
1. Attacker buys some `TOKEN` via `Zap.buy` on the curve and separately mints/holds some `LT` directly from BounceTech.
2. Attacker calls the HyperSwap V2 factory to create the `TOKEN`/`LT` pair (or lets `Bonding._ensureUniswapV2Pair` create it, then races to be first to mint) before the token graduates.
3. Attacker transfers `TOKEN` and `LT` into the pair in a ratio/size crafted so that: (a) neither side is within `DIRECT_MINT_PRESEED_BPS` of the eventual `(tokensForLP, ltFromPair)` targets (bypassing the dust-gate at Bonding.sol:1297-1302), and (b) `_noFeeSwapInput`'s computed swap `s`, or the pair's fee-adjusted `getAmountOut(s, tokenIn)`, rounds to zero for the resulting `(reserveIn, reserveOut, targetN, targetD)`.
4. Attacker calls `pair.mint(attackerAddress)` to mint themselves LP against this pre-seed.
5. Token graduates (via curve buys crossing the threshold or `triggerGraduation`); anyone calls `Bonding.finalizeGraduation(tokenAddress)`.
6. Inside `_seedRebalancing`, the dust-gate fails to trip (step 3a), `_pairRebalance` returns `false` (step 3b), and `_seedDirectMint` is invoked against the non-empty, attacker-seeded pool.
7. `pair.mint(lpLock)`'s `min()` formula donates the off-ratio excess into pool reserves, which is shared pro-rata with the attacker's pre-existing LP shares from step 4; attacker withdraws their LP to redeem a slice of the protocol's graduation deposit.

Note: exact numeric parameters that satisfy both conditions in step 3 depend on `getAmountOut`'s fee constant on the live HyperSwap deployment, which was not available in the indexed contract set; a background engineering session with access to the deployed HyperSwap V2 pair fee logic would be needed to derive concrete reserve values and confirm the PoC end-to-end in a fork test.

        address tokenAddress,

        address pair,

        uint256 ltFromPair
    ) internal returns (uint256 liquidity) {

        uint256 leftoverToken = IERC20(tokenAddress).balanceOf(address(this));

            Token(tokenAddress).burn(address(this), leftoverToken);
        }

    function _pairRebalance(
        RebalanceParams memory p
    ) internal returns (bool) {
        uint256 s = _noFeeSwapInput(p.reserveIn, p.reserveOut, p.targetN, p.targetD, p.maxSwap);
        if (s == 0) return false;

        // Quote from the pair so the output tracks its live fee; a value
        // derived from a stale fee rate would trip the pair's K-check.
        uint256 expectedOut = IUniswapV2Pair(p.pair).getAmountOut(s, p.tokenIn);
        if (expectedOut == 0) return false;

        IERC20(p.tokenIn).safeTransfer(p.pair, s);
        (uint256 amount0Out, uint256 amount1Out) = p.tokenInIs0 ? (uint256(0), expectedOut) : (expectedOut, uint256(0));
        IUniswapV2Pair(p.pair).swap(amount0Out, amount1Out, address(this), new bytes(0));
        return true;
    }
