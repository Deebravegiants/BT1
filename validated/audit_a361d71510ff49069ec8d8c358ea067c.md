### Title
Leftover swap input tokens permanently stranded in `ExternalActionSwap`/`LifiExternalAction` with no recovery path - (File: `contracts/external-actions/swaps/ExternalActionSwap.sol`, `contracts/external-actions/swaps/LifiExternalAction.sol`)

### Summary
This is the closest structural analog to the Tapioca `Balancer` conversion-rate bug: an amount is pulled out of the shielded pool, handed to an external router via an unlimited allowance, and only the *output*-side balance delta is measured and reconciled back into the UTXO accounting. Any portion of the *input* token that the router does not consume is left sitting in the external-action contract with a dangling `approveUnlimited` allowance, permanently outside any UTXO — mirroring the Stargate case where non-multiple-of-conversion-rate amounts accumulated inside `Balancer`.

### Finding Description
`Hinkal._externalTransact` transfers the full negative `deltaAmountChanges[i]` (the entire debited input amount) to the external action address before invoking `runAction` [1](#0-0) . `ExternalActionSwap.swap` then forwards that whole `inputAmount` to `callRouter`, which for `LifiExternalAction` calls `approveUnlimited(inputToken, router)` and blindly executes `router.call(externalActionMetadata)` [2](#0-1) .

The only value that flows back into Hinkal's accounting is `swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore`, i.e. the *output* token balance change [3](#0-2) . Nothing measures or refunds `inputToken` balance held by `ExternalActionSwap` after the router call. `swap()` builds exactly one output UTXO from `amountToSendToHinkal` and never inspects or returns unspent `inputToken` [4](#0-3) .

Back in `Hinkal.transact`, the post-action balance check only compares Hinkal's own balances before/after (`oldBalances`/`newBalances`) and validates them against `slippageValues[i]` and the returned `utxoSet` [5](#0-4) . This equation is satisfied as long as Hinkal itself sent out the input amount and received at least `slippageValues[1]` of output — it never checks that the router fully consumed what was sent to `ExternalActionSwap`. Any input-token dust left inside `ExternalActionSwap`/`LifiExternalAction` therefore silently escapes the balance equation entirely: it is not represented by any UTXO/commitment, yet it is real ERC20 value that left the shielded pool.

Neither `ExternalActionSwap.sol`/`LifiExternalAction.sol` nor `OwnerHinkal.sol` (its only inherited admin base) expose any sweep/rescue/withdraw function for arbitrary ERC20 balances — a search for `withdraw|sweep|rescue|recover` across the whole in-scope contract set found no such function. Compounding this, `approveUnlimited` leaves a `type(uint256).max` allowance to the router for `inputToken` (analogous to the "dangling allowance to StargateRouter" in the referenced report) [6](#0-5) .

### Impact Explanation
Whenever a LI.FI (or any future `ExternalActionSwap` subclass) route does not consume 100% of the approved/transferred input amount — due to router-side rounding, partial fills, fee deduction taken from the input side, or any calldata that swaps a smaller amount than what was sent — the leftover input tokens become permanently stuck in the external-action contract with no code path to return them to the user's shielded balance or to any recipient. This is a permanent loss of value that was debited from the user's shielded UTXO set (the balance equation shows the tokens left Hinkal, but no corresponding UTXO/commitment for the shortfall exists anywhere), i.e. permanent freezing/loss of user funds.

### Likelihood Explanation
The `externalActionMetadata` is covered by `calldataHash` (via `circomData.externalActionData`, part of `getHashedCalldata1`) [7](#0-6) , so this is not a scenario where an unprivileged relay can maliciously substitute the swap calldata to siphon extra input without invalidating the proof. This lowers likelihood of an *actively exploited* theft path and makes the analog closer to an accidental/latent value-leak condition (exactly like the original Stargate finding, which was also framed as an unintentional accumulation from legitimate rebalance calls rather than an attacker-crafted exploit). Realistic triggers are legitimate LI.FI/router behavior (slippage-based partial spend, fee-on-transfer input tokens, dust rounding) rather than attacker-controlled calldata, so likelihood is moderate rather than high, but the lack of any accounting or recovery mechanism means every such occurrence is a permanent, unrecoverable loss.

### Recommendation
- In `ExternalActionSwap.callRouter`/`LifiExternalAction.callRouter`, measure the input token balance of the external-action contract before and after the router call, and require the delta equals `inputAmount` (or refund the leftover input token back into a new UTXO/back to `msg.sender` (Hinkal) instead of leaving it stranded).
- Replace `approveUnlimited` with an approval scoped to `inputAmount` for the duration of the call, then reset the allowance to zero afterward, to avoid indefinite dangling allowances.
- If partial fills must be supported, explicitly account for the unspent input token as an additional output UTXO in `utxoSet` so it re-enters the shielded balance equation instead of disappearing.

### Proof of Concept
1. User creates a valid shielded swap transaction: `erc20TokenAddresses = [inputToken, outputToken]`, `amountChanges[0] = -100`, routed through `LifiExternalAction` with LI.FI calldata that (due to normal router-side rounding/partial-fill behavior) only spends `99` of the approved `100` `inputToken`.
2. `Hinkal._externalTransact` sends `100 inputToken` to `LifiExternalAction` [8](#0-7) .
3. `LifiExternalAction.callRouter` approves unlimited `inputToken` to `router`, calls `router.call(externalActionMetadata)`, which only consumes `99 inputToken`, producing some `outputToken` [3](#0-2) .
4. `swap()` only creates a UTXO for the received `outputToken` amount; the `1 inputToken` remaining in `LifiExternalAction`'s balance is never touched again [4](#0-3) .
5. `Hinkal.transact`'s balance/slippage checks pass because Hinkal's own token accounting is self-consistent (it sent `100`, got the resulting output UTXO) [9](#0-8) ; the `1 inputToken` (plus a max `approve` to `router`) is permanently stuck in `LifiExternalAction` with no function anywhere in scope to retrieve it.

    function callRouter(
        address inputToken,
        uint256 inputAmount,
        address outputToken,
        bytes calldata externalActionMetadata
    ) internal override returns (uint256 swappedAmount) {
        uint256 balanceBefore = getERC20OrETHBalance(outputToken);

        if (inputToken == address(0)) {
            (bool success, ) = router.call{value: inputAmount}(
                externalActionMetadata
            );
            require(success, "LI.FI swap failed: native coin");
        } else {
            approveUnlimited(inputToken, router);
            (bool success, ) = router.call(externalActionMetadata);
            require(success, "LI.FI swap failed: erc-20 token");
        }

        swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore;
    }
