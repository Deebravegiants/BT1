### Title
Debt-accrual overflow in `calculate_supplier_rewards` permanently freezes a market before the borrow-index cap can engage - (File: common/src/rates/index.rs)

### Summary
`calculate_supplier_rewards` computes `borrowed.mul(env, new_borrow_index)` via `mul_div_half_up`, which widens to `I256` for the product but raises `MathOverflow` when the *result* exceeds `i128::MAX`. The borrow index is capped at `MAX_BORROW_INDEX_RAY = 10^36` (1e9 × RAY), but the total-debt valuation overflows far earlier — at `borrowed * index > i128::MAX`, i.e. an index of roughly 170× RAY for a billion-token-scaled debt book. Since every state-mutating pool/controller verb accrues indexes first, a market that crosses this threshold panics on `update_indexes`, `supply`, `borrow`, `withdraw`, `repay`, `liquidate`, `clean_bad_debt` and every strategy path — permanently.

### Finding Description
In `common/src/rates/index.rs`, `calculate_supplier_rewards` values the debt book twice per accrual step:

```rust
let old_total_debt = borrowed.mul(env, old_borrow_index);
let new_total_debt = borrowed.mul(env, new_borrow_index);
```

`Ray::mul` → `fp_core::mul_div_half_up` panics with `GenericError::MathOverflow` when the quotient does not fit `i128` (`common/src/math/fp_core.rs`). The same overflow occurs earlier in `accrue_step` at `scaled_to_original(env, borrowed, borrow_index)` (`common/src/rates/simulate.rs:60`), which runs inside `simulate_update_indexes_body` on every cache sync (`contracts/pool/src/interest.rs` `global_sync`).

`update_borrow_index` caps the index at `MAX_BORROW_INDEX_RAY` (`common/src/rates/index.rs:13-19`), but the cap check happens on the *index*, not the *debt value*. For a debt book whose scaled shares `borrowed > i128::MAX / MAX_BORROW_INDEX_RAY` (≈ 170 raw units of debt in RAY terms, e.g. ~170 million whole tokens at 18 decimals — below the admitted `supply_cap`/`borrow_cap` maximum of ~170 billion whole tokens per `max_cap_for_decimals`), the borrow index reaches `i128::MAX / borrowed` strictly before `10^36`. From that block on, every accrual panics.

The repo's own harness test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-361`) demonstrates exactly this: after index growth at 98% utilization, `update_indexes`, `withdraw` and `repay` all revert with `MATH_OVERFLOW`, and "the index cap did not engage before the value overflow."

### Impact Explanation
Permanent freezing of all funds in the affected market book. Suppliers cannot withdraw, borrowers cannot repay (repayment accrues first), liquidations cannot execute, and bad debt cannot be cleaned — because all of these paths run `global_sync`/index accrual before touching balances. Unlike a fail-closed parameter guard, there is no privileged recovery verb that bypasses accrual; the market is bricked and every deposited token is locked. On hub/spoke markets sharing one physical pool balance, a frozen book also blocks accounting for that (hub, token) pair indefinitely.

### Likelihood Explanation
A single unprivileged address can reach this with only `supply` + `borrow` and elapsed time:

- The admitted cap ceiling is ~170.14 billion whole tokens (`i128::MAX / 10^(27-d)`), while overflow needs a scaled debt book of only ~1/1000th of that at index cap — and far less at realistic index growth, since `borrowed * index` hits `i128::MAX` at index ≈ `i128::MAX / borrowed`.
- An attacker can deliberately construct the state: supply a large amount to a hub market, borrow at high utilization to pin the borrow rate on the steep part of the curve (up to `MAX_BORROW_RATE_RAY` = 200% APR), then simply let time pass. Interest compounds the index automatically; the attacker loses only time value, and no further action is needed once the product crosses `i128::MAX`.
- The attacker can keep the market near the cliff cheaply: debt grows via accrual without new capital, and utilization near max is self-sustaining once other suppliers' funds are locked in.
- The threshold is reachable well before the documented `10^9 × RAY` index ceiling — the harness test reaches it within tens of simulated years at sustained high utilization, and any `borrow`/`repay`/`update_indexes` call by anyone triggers the panic, so an attacker can also *choose the moment* to cross it and freeze counterparties' funds.

### Recommendation
Make accrual saturating rather than panicking on value overflow:

- In `accrue_step`/`global_sync`, detect when `borrowed * new_borrow_index` would exceed `i128::MAX` and clamp `new_borrow_index` to `min(computed, i128::MAX / borrowed)` (or to `MAX_BORROW_INDEX_RAY` semantics: stop accruing interest at the cliff instead of reverting), mirroring the existing index-cap behavior.
- Alternatively use a saturating variant of `scaled_to_original` for the *debt valuation inside accrual* (keeping the panicking path for per-position valuation), so the market keeps operating and `update_borrow_index`'s cap remains the effective stop.
- At minimum, add a guard in `update_indexes` that, on overflow, freezes the indexes at their last values rather than reverting, so `repay`/`withdraw`/`liquidate`/`clean_bad_debt` remain callable.

### Proof of Concept
Mirrored by the existing harness test (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-361`):

```rust
// Attacker: supply 1e9 * 10^18 units of an 18-decimal asset, borrow 98%.
let principal = BILLION * 10i128.pow(18);
t.supply_raw(BOB, "BIG18", principal);
t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
t.borrow_raw(ALICE, "BIG18", principal / 100 * 98);

// Advance time; each year update_indexes accrues.
loop {
    t.advance_time(YEAR_SECS);
    if let Err(e) = t.try_update_indexes_for(&["BIG18"]) { break e; } // -> MATH_OVERFLOW
}
// borrow_index < MAX_BORROW_INDEX_RAY, yet:
t.try_withdraw_raw(BOB, "BIG18", 1) // MATH_OVERFLOW
t.try_repay(ALICE, "BIG18", 1.0)    // MATH_OVERFLOW
```

Root cause chain: `update_indexes` → `global_sync` (`contracts/pool/src/interest.rs`) → `accrue_step` (`common/src/rates/simulate.rs:51-94`) → `scaled_to_original` / `calculate_supplier_rewards` (`common/src/rates/index.rs:73-89`) → `Ray::mul` → `mul_div_half_up` → `MathOverflow` panic (`common/src/math/fp_core.rs`), while `update_borrow_index`'s `MAX_BORROW_INDEX_RAY` clamp (`common/src/rates/index.rs:13-19`) never engages because the value overflow occurs at a much lower index.
