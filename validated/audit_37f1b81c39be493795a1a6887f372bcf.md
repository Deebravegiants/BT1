## Title
Malicious solver can permanently freeze escrowed native-token order funds by reverting on payout in `IntentsBase._withdraw` / `IntentGatewayV2.withdraw` - (File: `evm/src/apps/intentsv2/IntentsBase.sol`, `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The intent-gateway cross-chain settlement path pushes native-token payouts directly to an attacker-controlled address (`msg.sender` of the fill call) using a low-level `call{value:...}` that reverts the whole settlement on failure. This mirrors the tbtc `liquidationInitiator`/`purchaseSignerBondsAtAuction` bug class: an unprivileged actor (the solver) can pick their own payout address, make it revert on ETH receipt, and permanently block delivery of the settlement message — freezing the user's escrowed input tokens with no recovery path.

### Finding Description
In `_fillCrossChain` (`evm/src/apps/intentsv2/ExtrinsicIntents.sol:164-220`), the destination-chain gateway marks the order filled and dispatches a `RedeemEscrow` request back to the source chain using the filler's own address as the beneficiary: [1](#0-0) [2](#0-1) 

On the source chain, `onAccept` decodes this and calls `_withdraw`, which for native-token (`address(0)`) inputs sends funds via `_sendValue`, a low-level call that **reverts** on failure: [3](#0-2) [4](#0-3) 

The Tron variant has the identical pattern in `withdraw`: [5](#0-4) 

Because the beneficiary is `msg.sender` of the fill (attacker-controlled), the attacker deploys a contract with a reverting `receive()`/`fallback()`, calls `fillOrder`/`_fillCrossChain` from it, and guarantees the subsequent `onAccept` call on the source chain will always revert.

`EvmHost.dispatchIncoming` for POST requests swallows this failure to allow retries, but retries execute the exact same call with the exact same (unchangeable) beneficiary, so the failure is deterministic and permanent: [6](#0-5) 

Two facts make this unrecoverable rather than merely retry-able:
1. `_fillCrossChain` sets `_filled[commitment] = msg.sender` on the **destination** chain unconditionally, before the source-chain settlement even happens (`evm/src/apps/intentsv2/ExtrinsicIntents.sol:167`). This is exactly the same escrow-independent state flag that source-chain cancellation logic checks.
2. Source-chain cancellation (`_cancelFromSource`) dispatches a GET request to check the destination’s `_filled` slot and refunds only if it is empty; since it is already non-empty (set in fact 1), `onGetResponse` reverts with `Filled()`, so the user can never claim a refund either: [7](#0-6) [8](#0-7) 

Additionally, `_post` dispatches the `RedeemEscrow` message with `timeout: 0` (no timeout), so there is no timeout-triggered fallback recovery path either: [9](#0-8) 

The net effect: user's escrowed native-token `order.inputs` remain locked in the source-chain gateway contract forever — they cannot be released to the solver (call always reverts) and cannot be refunded to the user (order already marked filled on the destination).

### Impact Explanation
This is a permanent freezing-of-funds vulnerability reachable by any unprivileged actor who can call `fillOrder`/`_fillCrossChain`. An attacker with zero economic stake (they never intend to actually receive the payout) can grief any cross-chain order whose input asset is the native token, permanently locking the user's escrowed funds in the `ExtrinsicIntents`/`IntentGatewayV2` contract with no path to recovery — matching "permanent freezing of funds" in the validation criteria.

### Likelihood Explanation
High likelihood: no privileged role is required, the attacker only needs to deploy a simple reverting-receiver contract and call the public `fillOrder` function as that contract, choosing an order with a native-token input. The griefing cost is limited to whatever output tokens are required to be delivered by the fill (which the attacker fully controls, and typically the amount can be made deliberately small on low-value orders) — offset by causing indefinite loss of the victim's escrowed native token principal.

### Recommendation
Do not let payout delivery success gate protocol state transitions for un-refundable escrow. Options, similar to the tbtc fix (`transfer` → `send`) but stronger given the unbounded blocking:
- Use a pull-payment pattern: on failed native-token push, credit the beneficiary's address with a withdrawable balance instead of reverting the whole settlement (`_withdraw`/`withdraw` should not revert the entire flow just because one beneficiary can't receive ETH).
- Alternatively, wrap failed native sends into WETH (as already done in `WrappedHyperFungibleToken.onAccept`/`onPostRequestTimeout`) so delivery always succeeds and funds are never dependent on the untrusted beneficiary’s receive behavior: [10](#0-9) 
- Ensure `_filled` is only durably set on the destination chain after the corresponding source-chain settlement has actually completed, or provide an alternate unlock path independent of the beneficiary's cooperation.

### Proof of Concept
1. Attacker deploys `MaliciousSolver`, a contract with `receive() external payable { revert(); }`.
2. A user places a cross-chain order via `ExtrinsicIntents.placeOrder` with a native-token (`address(0)`) input on the source chain.
3. `MaliciousSolver` calls `fillOrder`/`_fillCrossChain` on the destination chain, supplying the correct output amount to the beneficiary, setting itself (`msg.sender`) as the redemption target; `_filled[commitment]` is set on the destination chain and a `RedeemEscrow` message with `beneficiary = address(MaliciousSolver)` is dispatched to the source chain.
4. When the relayed message reaches the source chain, `onAccept` → `_withdraw` attempts `_sendValue(address(MaliciousSolver), amount)`, which reverts because of the malicious `receive()`. `EvmHost.dispatchIncoming` catches the failure and allows retries, but every retry reverts identically.
5. The user attempts `cancelOrder` on the source chain; `_cancelFromSource` dispatches a GET check, and `onGetResponse` reverts with `Filled()` because `_filled[commitment]` was already set in step 3 — the user's escrowed native input is permanently stuck.
