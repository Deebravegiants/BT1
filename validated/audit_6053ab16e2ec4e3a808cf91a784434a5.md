### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` exposes a `shop` accessor that reads the unauthenticated `X-Shopify-Shop-Domain` HTTP header, but the HMAC signature validated via `Utils::HmacValidator` only covers the raw request body. Because the app's webhook signing secret (`client_secret`) is identical for every shop that installs the app, any shop that installs the app can capture one of its own legitimately-signed webhook deliveries and replay the same `(body, hmac)` pair while substituting a different `shop-domain` header, producing a request that still passes signature validation but is attributed to an arbitrary victim shop.

### Finding Description
`HmacValidator.validate` computes the signature exclusively over `verifiable_query.to_signable_string` and compares it to the received HMAC: [1](#0-0) 

For webhook requests, `to_signable_string` returns only the raw body — it never incorporates the shop identity: [2](#0-1) 

Meanwhile, `Request#shop`, which callers are expected to trust as the tenant identifier for the webhook, is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header with no cryptographic binding to the signed body: [3](#0-2) 

The only headers validated for presence (not authenticity) are `topic`, `hmac-sha256`, and `shop-domain`: [4](#0-3) 

Because Shopify signs app webhooks with the single app-level `client_secret` (the same secret used for every shop that has installed the app, as also used in `Auth::Oauth` and `TokenExchange`), the HMAC is not shop-specific: [5](#0-4) 

This breaks the intended identity binding `hmac-signed-body == authenticated-shop`. An attacker who legitimately installs the target app on their own shop receives valid `(body, hmac)` pairs from Shopify for their own webhooks. They can then send an HTTP request directly to the app's webhook endpoint using that captured `raw_body`/`hmac-sha256` header pair, but with the `shop-domain` header rewritten to a victim shop's domain. `HmacValidator.validate` still returns `true` (it never inspects the header), yet `Request#shop` now reports the victim's shop to the host application's webhook handler.

### Impact Explanation
Any application built on this gem that uses `Request#shop` to select which shop's session/access token to act on, or to key per-tenant state when processing "verified" webhooks, can be made to process attacker-supplied payloads under another merchant's identity — a cross-tenant boundary crossing achieved purely through this gem's exposed, "verified" webhook object. This matches the Critical "cross-tenant access" impact category since the gem's own `HmacValidator`/`Request` abstractions present the header-derived `shop` as trustworthy once `validate` succeeds, with no documented caveat that `shop` is unauthenticated.

### Likelihood Explanation
Any account holder can install the app on a shop they control (no special privilege needed), capture one authentic webhook delivery, and replay it with a modified `shop-domain` header to the app's public webhook endpoint. No secrets, tokens, or elevated access are required — only the ability to install the target app once, which is the normal, unprivileged flow for any Shopify merchant.

### Recommendation
Bind the shop identity into the HMAC-covered signable content, or otherwise cryptographically verify `shop-domain` against the signed payload (e.g., require the body's own shop-scoped identifiers to match the header, or reject/flag when the header-derived shop cannot be independently confirmed) before exposing `Request#shop` as a trusted value to consumers of this gem.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker.myshopify.com`.
2. Attacker triggers/receives a real webhook from Shopify: captures `raw_body` and the `X-Shopify-Hmac-Sha256` header (valid because it is signed by the app-level `client_secret`, not shop-specific).
3. Attacker sends a POST to the victim app's webhook endpoint with the identical `raw_body` and `X-Shopify-Hmac-Sha256` header, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate(request)` returns `true` because `to_signable_string` only checks `raw_body`.
5. `request.shop` returns `"victim-shop.myshopify.com"`, and any handler that trusts this value processes the attacker's payload as if it came from the victim shop.

          received_signature = verifiable_query.hmac
