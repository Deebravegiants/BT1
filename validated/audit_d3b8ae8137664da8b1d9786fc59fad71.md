### Title
Reachable panic via `.expect()` on empty precommits in GRANDPA justification verification causes consensus-client DoS - (File: modules/consensus/grandpa/primitives/src/justification.rs)

### Summary
`GrandpaJustification::verify_with_voter_set` computes `base_hash` by taking the `min_by_key` over `self.commit.precommits` and then unconditionally calls `.expect("can only fail if precommits is empty; commit has been validated above; valid commits must include precommits; qed.")` [1](#0-0) . This assumption — that `finality_grandpa::validate_commit` rejects empty-precommit commits before this code runs — is asserted via a code comment, not verified by an explicit, typed check in this crate. If that invariant does not hold for some crafted `Commit` (e.g., an empty `precommits: Vec` that the external `finality_grandpa` crate's `validate_commit` treats as vacuously "valid" for a particular `voters`/threshold configuration, or any future behavior change in that dependency), `.expect()` triggers a Rust panic, i.e., an unconditional process abort analogous to the OpenExr/OpenJPH `abort()` on the malformed QCD marker.

### Finding Description
The GRANDPA consensus client accepts a SCALE-decoded `ConsensusMessage`/justification supplied by an unsigned extrinsic (`handle_unsigned`) or relayed proof, and eventually calls into `GrandpaJustification::verify`/`verify_with_voter_set` to validate the commit against the trusted authority set [2](#0-1) . The `commit.precommits` field is fully attacker-controlled input decoded from the wire (it is part of `Commit<H>` inside the justification bytes), so a submitter can construct a justification whose `precommits` vector is empty. The code relies entirely on the *external* `finality_grandpa::validate_commit` call to guarantee non-emptiness before reaching the `.expect()` at line 102, rather than an internal check in this crate. This is the same anti-pattern as the CVE: a safety invariant that crosses a library boundary (OpenJPH's internal `assert()` vs. OpenEXR's own error-handling wrapper; here, `finality_grandpa`'s internal validation vs. `justification.rs`'s own error-handling), where the calling code trusts the invariant absolutely and panics instead of returning a typed `Result::Err` if it is ever violated.

### Impact Explanation
`verify_with_voter_set` is reached from `ismp-grandpa`'s `verify_grandpa_finality_proof`/consensus client wrapper on the fully permissionless message-delivery path: any relayer can submit a GRANDPA consensus update via `pallet_ismp::Call::handle_unsigned`, which is dispatched through `ValidateUnsigned::validate_unsigned` → `Pallet::execute` → `handle_incoming_message` → the GRANDPA `ConsensusClient::verify_consensus` → this `verify()`/`verify_with_voter_set()` call, all with no prior signature/authorization gate other than proof validity itself [3](#0-2) [4](#0-3) . A panic inside transaction-pool validation (`validate_unsigned`) or block execution on this path is a process abort of the collator/validator node executing it — i.e., a denial-of-service on the state-machine's ability to deliver any messages via the GRANDPA-secured route, matching the "route unable to deliver messages" acceptance criterion. Because `validate_unsigned` runs during off-chain transaction-pool gossip validation, a single crafted transaction can be used to repeatedly crash any node that receives and validates it before it reaches a block.

### Likelihood Explanation
Likelihood hinges entirely on whether `finality_grandpa::validate_commit` (an external dependency, not part of this repo) can return `Ok(result) if result.is_valid()` for a commit whose `precommits` is empty. This repository's own regression-test history shows a pattern of exactly this class of bug being found and fixed elsewhere (e.g., the BEEFY MMR `leaf_indices[0]` panic, the RLP node-codec `data[0]` panic, the sync-committee `multi_proof` panic — see comments in `modules/consensus/beefy/verifier/src/lib.rs:229-236` and `modules/trees/ethereum/src/tests.rs:74-85`), indicating the team actively hunts for and hardens against exactly this "unchecked invariant → indexing/`.expect()` panic on attacker data" pattern, but this particular `.expect()` in `justification.rs` line 102 was not found in the search results to have an accompanying explicit internal length/emptiness check or regression test proving `finality_grandpa::validate_commit` can never let an empty-precommit commit through. Since I could not verify the internal behavior of `finality_grandpa::validate_commit` from within this codebase, I cannot definitively confirm whether the invariant genuinely always holds; I flag this as a real code-smell/defensive-programming gap that mirrors the reported CVE's root cause (trusting an external library's un-enforced internal invariant instead of an explicit typed check), but cannot fully prove reachability of the panic without auditing the `finality_grandpa` crate's source, which is outside this repo's index.

### Recommendation
Replace the `.expect(...)` at `modules/consensus/grandpa/primitives/src/justification.rs:102` with an explicit, local guard: check `self.commit.precommits.is_empty()` (or equivalently handle `min_by_key` returning `None`) before computing `base_hash`, and return a typed `anyhow::Error`/`Err` instead of panicking — regardless of what `finality_grandpa::validate_commit` is currently believed to guarantee. This removes the cross-crate trust assumption entirely, consistent with how other similarly-shaped issues (BEEFY MMR leaf index, RLP HP-prefix, sync-committee multi-proof) were fixed elsewhere in this same codebase.

Conceptual PoC (cannot be fully executed without the `finality_grandpa` crate's internals, which are external to this repo):
1. Craft a GRANDPA `ConsensusMessage`/justification whose `commit.precommits` is an empty `Vec` while `commit.target_hash`/`target_number` are set to any value and `votes_ancestries` is empty.
2. Submit it via `pallet_ismp::Call::handle_unsigned` (or the tesseract relayer's GRANDPA consensus-update path) to a node running the GRANDPA `ConsensusClient`.
3. If `finality_grandpa::validate_commit` returns `Ok(result)` with `result.is_valid()` true for this degenerate empty-precommit commit under the configured `voters`/threshold (e.g., a zero-threshold or trivially-satisfied edge case), execution reaches `justification.rs:95-107`, `.map(|precommit| ...)` yields `None` from `min_by_key` over an empty iterator, and `.expect(...)` panics, aborting the process validating/executing that transaction.
