# CVE-2021-4066 Analog Analysis — Raydium AMM

## Title
Unchecked Integer Underflow in `calc_take_pnl` PnL Reconciliation Causes Program Panic / Permanent Denial-of-Service — (File: `program/src/processor.rs`)

## Summary
The CVE describes an integer underflow in graphics processing that leads to memory corruption. The analogous bug class here is an **unguarded arithmetic subtraction (`checked_sub(...).unwrap()`) that can underflow and panic**, reachable from every unprivileged swap, deposit, and withdrawal instruction via the shared `Processor::calc_take_pnl` helper.

## Finding Description
`calc_take_pnl` reconciles pool reserves against the "unrealized PnL" baseline stored in `TargetOrders.calc_pnl_x` / `calc_pnl_y`. It first performs a solvency guard **in native token-decimal units**: [1](#0-0) 

then, if the guard passes, it computes a new "post-pnl" point `(x2, y2)` and subtracts it from `x1, y1` — but `x1`/`y1` were normalized to the pool's fixed `sys_decimal_value` scale by the *caller* before being passed in (`Calculator::normalize_decimal_v2`), a completely different unit basis than the native amounts used in the guard above: [2](#0-1) 

Because `normalize_decimal_v2`/`restore_decimal` truncate (integer floor division) on every conversion, and because real pools routinely have `pc_decimals != coin_decimals` (e.g. USDC=6 vs SOL=9), the native-unit guard and the normalized-unit subtraction are not guaranteed to agree on ordering. When `pool_pc*pool_coin >= calc_pc*calc_coin` holds in native units but the corresponding normalized `x2` (derived from `calc_x_power`/`integer_sqrt`) exceeds `x1` due to rounding drift, `x1.checked_sub(x2).unwrap()` (and the analogous `y1.checked_sub(y2)`) underflows and **panics**, aborting the transaction with a runtime panic rather than a handled `AmmError`.

`calc_take_pnl` is invoked unconditionally from every reachable state-mutating path an ordinary user can trigger:
- `process_deposit` [3](#0-2) 
- `process_withdraw` (non-`WithdrawOnly` status) [4](#0-3) 
- `process_withdrawpnl` [5](#0-4) 

The same unguarded-subtraction pattern re-appears when the delta is later applied back to `TargetOrders`: [6](#0-5) [7](#0-6) 

Since `TargetOrders.calc_pnl_x/calc_pnl_y` are pool-global, persistent state, an attacker does not need any privileged role — a sequence of ordinary `Deposit`/`Withdraw`/`Swap` calls that shifts the pool reserve ratio (skewed single-sided swaps followed by deposits/withdrawals at different decimal ratios) can push the pool into the region where the native-vs-normalized rounding mismatch flips sign and the subtraction underflows.

## Impact Explanation
Once the pool state is driven into the panic-triggering region, **every subsequent call** to `Deposit`, `Withdraw`, or `WithdrawPnl` (all of which unconditionally invoke `calc_take_pnl`) will panic and revert. Because the panicking arithmetic is on core reserve-accounting state that cannot be reset by any unprivileged instruction, this constitutes a **permanent freezing of LP and user funds** in the affected pool — LPs cannot withdraw liquidity and PnL cannot be collected, matching the "permanent freezing of user or LP funds" impact bar in the validation rubric.

## Likelihood Explanation
The trigger conditions require accumulating specific rounding drift through the two-stage decimal-normalization round trip (`normalize_decimal_v2` / `restore_decimal`) that only affects pools with `pc_decimals != coin_decimals` (the common case for real pools, e.g., stablecoin/SOL pairs). No signer privilege beyond a normal user-owned token account is required — only crafted amounts on `Deposit`/`Swap`/`Withdraw` instructions, which are exactly the four in-scope instruction types. This is a Medium-to-High likelihood issue: it requires deliberate numerical crafting but no privileged access, no off-chain component, and no non-default build.

## Recommendation
- Replace the native-unit guard at `processor.rs:190-192` with a comparison performed in the **same normalized unit basis** used by `calc_x_power`/`x1`/`y1`, eliminating the decimal-basis mismatch.
- Replace `checked_sub(...).unwrap()` at lines 213-214, 1531-1532, and 1819-1838 with `checked_sub(...).ok_or(AmmError::CheckedSubOverflow)?` (as is already done correctly in `Calculator::calc_total_without_take_pnl_no_orderbook`), so that an ordering violation returns a graceful program error instead of panicking and does not desynchronize `TargetOrders` state.
- Add an explicit `if x2 > x1 { return Err(AmmError::CalcPnlError) }` sanity check prior to the subtraction, independent of the pre-existing native-unit guard.

## Proof of Concept
A fully deterministic on-chain reproduction requires iterating decimal-normalization arithmetic to find a concrete `(pc_decimals, coin_decimals, reserve, calc_pnl_x/y)` tuple where the native-unit guard at `processor.rs:190-192` passes while `integer_sqrt`-derived `x2` (line 206) exceeds the normalized `x1` fed in by the caller. Conceptually:
1. Create a pool with `pc_decimals = 6`, `coin_decimals = 9` (a realistic USDC/SOL-style pair).
2. Perform a sequence of single-sided `Swap` calls to drive the reserve ratio to an extreme skew, then a `Deposit` with a `base_side` chosen to maximize floor-rounding loss in `normalize_decimal_v2`, updating `TargetOrders.calc_pnl_x/calc_pnl_y` to a value whose *restored* native form sits just below the true native reserve product while its *normalized* form sits just above the current normalized `x1/y1` product.
3. Submit a subsequent `Withdraw` or `WithdrawPnl` instruction; `calc_take_pnl`'s guard (native units) passes, but `x1.checked_sub(x2)` underflows, panicking the transaction and, because `TargetOrders` was already left in the skewed state during step 2, causing the panic to recur on every future call, freezing the pool.
