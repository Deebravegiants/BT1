## Title
Webhook `shop` identity is not bound by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, then dispatches the handler using a `shop` value taken from an HTTP header that is never covered by that HMAC. This breaks the intended binding `hmac_verified_bytes == acted_on_identity`: the signature only proves "this body byte stream was produced with the app's secret," while the tenant the webhook is attributed to (`shop`) is attacker-controllable header data.

### Finding Description
`HmacValidator.validate` computes and compares the HMAC exclusively over `to_signable_string`, which for `Webhooks::Request` is just `@raw_body`: [1](#0-0) 

The `shop` accessor, however, is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header, which is completely outside the signed content: [2](#0-1) 

`Registry.process` treats a passing HMAC check as sufficient authentication for the whole request, then forwards the unverified `request.shop` value straight into the handler's `WebhookMetadata`: [3](#0-2) 

Because a single app's `api_secret_key` is shared across every shop that has installed the app, any merchant/attacker who has installed the app on their own store can capture one of their own genuine, HMAC-valid webhook deliveries (many mandatory/GDPR webhooks have static/predictable bodies such as `{}`), then replay the identical body and HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop's domain. `HmacValidator.validate` still succeeds because it never inspects the header, and the handler receives `WebhookMetadata` claiming to originate from the victim shop.

This is the direct analog of the `UnionToken` finding: the check (`isWhitelisted`/HMAC) is performed on one identity (`msg.sender`/raw body bytes) while the security-relevant action is performed against a different, uncontrolled identity (`from`/`shop` header).

### Impact Explanation
Any host application that keys off `WebhookMetadata#shop` to select which tenant's data to modify (delete customer data, mark app as uninstalled, disable billing, rotate credentials, etc. — all standard patterns recommended by Shopify's own mandatory webhook docs) can be tricked into performing that action against an arbitrary victim shop chosen by the attacker. This is a cross-tenant integrity/access issue: an attacker with no relationship to the victim shop can cause shop-scoped side effects to be attributed to it, purely from the library's failure to bind the authenticated bytes to the acted-upon shop identity.

### Likelihood Explanation
Requires only that the attacker be able to install the target app on a shop they control (or otherwise obtain one genuine, HMAC-valid webhook payload for the app) and can send arbitrary HTTP requests with custom headers to the app's public webhook endpoint — both are unprivileged-internet-user actions with no need for the `api_secret_key`, an access token, or any victim credential.

### Recommendation
Bind the verified bytes to the identity that is acted upon: either include the shop domain (and ideally topic/webhook id) inside the HMAC-signed payload/signable string, or require the calling application to independently verify that `request.shop` corresponds to a shop with an active installation/session before trusting it, and document this requirement prominently. At minimum, `Registry.process`/`HmacValidator` should not treat a body-only HMAC pass as authenticating the `shop` header value used for dispatch.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and receives a legitimate mandatory webhook (e.g., `customers/data_request`) with a raw body such as `{}"` and a valid `x-shopify-hmac-sha256` value computed with the app's shared `api_secret_key`.
2. Attacker resends the exact same raw body and HMAC header to the app's webhook endpoint but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate(request)` returns `true` because it only checks `Digest.hexencode(...)` against `@raw_body` [4](#0-3) .
4. `Registry.process` invokes the registered handler with `WebhookMetadata.new(... shop: request.shop ...)` set to `"victim-shop.myshopify.com"` [5](#0-4) , causing the host app to act as though the victim shop sent this webhook.
