### Title
Silent-failure ERC20 `transfer` in the predispatch escrow-sweep credits the full requested amount even when the token never moved, allowing uncollateralized/inflated order escrow - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron `IntentGatewayV2.placeOrder` predispatch path sweeps tokens from the `CallDispatcher` back to the gateway using a raw, unchecked-by-return-value `IERC20.transfer` call, and credits the order's escrow (`_orders[commitment][token]`) with the *expected* (`reducedInputs[i].amount`), not the amount actually received. If the input token is a non-standard-compliant ERC20 that returns `false` on transfer failure instead of reverting (a documented behavior of a number of real Tron TRC20 tokens), the `CallDispatcher.dispatch` call will still report success (the low-level `.call` itself does not revert), the escrow will nonetheless be fully credited, and no tokens will have actually entered the gateway.

### Finding Description
In `placeOrder`'s predispatch branch, escrow accounting is done purely based on the pre-computed `requiredAmount`/`reducedInputs[i].amount`, not on any post-transfer balance check of the gateway itself: [1](#0-0) 

The actual token movement is executed via `ICallDispatcher(dispatcher).dispatch(abi.encode(transferCalls))`, which internally performs a raw, low-level `.call()` and only checks the boolean `success` returned by the EVM call — it never inspects/validates the ABI-encoded boolean return value of the ERC20 `transfer` function itself: [2](#0-1) 

Because the `transfer` call is built with `abi.encodeWithSelector(IERC20.transfer.selector, address(this), balance)` rather than routed through `SafeERC20.safeTransfer`, a non-standard-compliant ERC20 that returns `false` instead of reverting on failure (e.g., due to allowance/blacklist/insufficient-balance edge cases in some TRC20 implementations) will make the `.call()` succeed (`success == true`) while transferring zero tokens. `CallDispatcher` does not revert in this case, so `placeOrder` proceeds to compute the order commitment and has *already* incremented `_orders[commitment][token] += reducedInputs[i].amount` before the sweep call even executes.

This directly mirrors the bug class in the referenced report: code paths (`request`/`repay` there, `placeOrder`/escrow-crediting here) that trust a non-reverting `transferFrom`/`transfer` return value to represent a successful token movement, allowing a caller to make the protocol believe funds were deposited when they were not.

Contrast this with the equivalent mainline EVM contract (`evm/src/apps/IntentGatewayV2.sol`), which recomputes `received = IERC20(token).balanceOf(address(this)) - balancesBefore[i]` after the sweep and clamps `order.inputs[i].amount` to the actual balance delta observed on the gateway before crediting escrow — i.e., it is balance-based and immune to a silently-failing transfer: [3](#0-2) 

The Tron variant lacks this balance-based reconciliation for the predispatch path, relying solely on the unchecked `CallDispatcher` sweep result.

### Impact Explanation
An order creator can place a cross-chain or same-chain intent order using a non-standard-compliant TRC20 token as an input asset routed through the predispatch/call-dispatcher path. If the token's `transfer` returns `false` under some condition triggerable by the order creator (e.g., insufficient balance at sweep time, a blacklist flag, or any other non-reverting failure mode), the gateway will:
1. Never actually receive the input tokens (or receive less than expected).
2. Still record a full escrow credit (`_orders[commitment][token]`) for the order.
3. Allow a solver to fill the order and later redeem the escrow via the `RedeemEscrow` cross-chain flow, paying out real tokens that were never backed by an actual deposit.

This results in uncollateralized escrow entries backed by nonexistent tokens, ultimately allowing theft/drain of the gateway's real token reserves (funds deposited by other, honest users) once a solver redeems against the fraudulent escrow. This satisfies "concrete theft ... of funds" from a single submitted transaction (`placeOrder`).

### Likelihood Explanation
Requires: (a) the intent order to specify a non-standard ERC20/TRC20 input token that can return `false` instead of reverting on failed transfer, and (b) use of the predispatch/call-dispatcher escrow path (`order.predispatch.call.length > 0 && order.predispatch.assets.length > 0`), which is a normal, unprivileged, user-selectable code path in `placeOrder`. No special privileges are needed — any unprivileged order creator controls the token choice and predispatch parameters. Likelihood depends on availability of a suitably non-compliant token on Tron, which is plausible given Tron's TRC20 ecosystem includes tokens with non-standard failure semantics.

### Recommendation
Route the sweep transfer in the predispatch branch through `SafeERC20.safeTransfer`/`safeTransferFrom` (as is already done elsewhere in this same file and consistently in the mainline EVM contract), and additionally reconcile escrow credit against the gateway's actual balance delta before/after the sweep (mirroring `evm/src/apps/IntentGatewayV2.sol`'s `received = balanceOf(address(this)) - balancesBefore[i]` pattern), rather than crediting escrow with the pre-computed `reducedInputs[i].amount` unconditionally.

### Proof of Concept
1. Deploy a malicious/non-standard TRC20 token whose `transfer` function returns `false` (without reverting) when, e.g., `balanceOf(from) < amount` or a caller-controlled flag is set, instead of reverting.
2. As an unprivileged user, call `placeOrder` with:
   - `order.inputs[0].token` = the non-compliant token, `amount = X`.
   - `order.predispatch.assets` and `order.predispatch.call` populated such that the predispatch call ultimately leaves the `CallDispatcher` holding less than `X` of the token (e.g., have the predispatch call itself drain the dispatcher's balance of that token to another address the attacker controls, or configure the token to make `transfer` from dispatcher fail non-revertingly).
3. `placeOrder` executes: `balance = IERC20(token).balanceOf(dispatcher)` check may pass at snapshot time, but the sweep `transfer` call returns `false` without reverting; `CallDispatcher.dispatch` sees `success == true` and does not revert.
4. `_orders[commitment][token] += reducedInputs[i].amount` has already recorded the full amount despite the gateway's real token balance not increasing by that amount.
5. A colluding/attacker-controlled solver fills the order and redeems the escrow cross-chain via `RedeemEscrow`, withdrawing real tokens from the gateway's pool that were deposited by other legitimate users, realizing a direct profit funded by draining the shared pool.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
