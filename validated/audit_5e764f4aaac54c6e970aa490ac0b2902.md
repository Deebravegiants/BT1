### Title
Webhook `shop` and `topic` identity fields are not covered by HMAC verification, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC of the raw request body, but the `shop` (and `topic`) values that the gem hands to the host application as the trusted tenant identity are read from unauthenticated HTTP headers that are never included in the signed payload.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and the HMAC is computed exclusively over that string via `HmacValidator.compute_signature(verifiable_query.to_signable_string, secret)` [2](#0-1) . However, `Request#shop`, `#topic`, `#api_version`, and `#webhook_id` are all parsed straight out of HTTP headers (`shopify-shop-domain`, `shopify-topic`, etc.) that carry no cryptographic binding to the HMAC at all [3](#0-2) .

`Registry.process` validates the HMAC and then immediately forwards the unauthenticated `request.shop` value into `WebhookMetadata`, which is passed to the app's handler as the tenant identifier: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))` [4](#0-3) .

The identity binding that should hold is: `shop authenticated by HMAC == shop delivered to handler`. In this gem it does not — the HMAC only proves "this body was signed with the app's secret," not "this body originated from shop X." Since `api_secret_key` is shared across all shops that install the same app, any merchant who installs the app (an ordinary, unprivileged action) can obtain genuinely Shopify-signed webhook deliveries for their own store, then replay that exact signed body to the app's webhook endpoint with a forged `shopify-shop-domain` (and/or `shopify-topic`) header pointing at a victim shop. `HmacValidator.validate` will pass, because it only recomputes over `@raw_body` [5](#0-4) , and `Registry.process` will hand the handler a `WebhookMetadata` claiming the body belongs to the victim shop.

The gem's own documentation instructs integrators to trust `data.shop` as the tenant key for follow-up processing, e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)` [6](#0-5) , and the struct itself documents `shop` as trusted webhook metadata [7](#0-6) .

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce: an attacker who has any (even a free, trial) install of the host app on their own shop can forge webhook deliveries that the host application will process as belonging to a different, victim tenant, since the only cryptographic guarantee (HMAC over the body) says nothing about which shop the data came from. Depending on how the host app uses `data.shop`/`data.topic` (record lookups, queue routing, cache keys, authorization decisions), this enables cross-tenant data corruption or disclosure — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Exploitation only requires installing the app on an attacker-controlled shop (a normal, unprivileged action available to anyone), capturing one legitimately-signed webhook body/HMAC pair, and replaying it against the app's public webhook endpoint with modified `shop-domain`/`topic` headers. No access to `api_secret_key`, tokens, or victim credentials is required.

### Recommendation
Bind the shop identity to the authenticated payload rather than trusting an unauthenticated header. At minimum, extend `to_signable_string` (or add a separate check in `Registry.process`) to incorporate the `shop-domain` and `topic` headers into the HMAC-covered material, matching how Shopify's own webhook signing scheme is documented, or cross-validate `request.shop` against an authenticated session/shop record already known to the app for that specific webhook subscription (e.g., via the `webhook_id` looked up server-side) before dispatching to the handler.

### Proof of Concept
1. Install the target app on attacker-owned shop `attacker.myshopify.com`; trigger a webhook (e.g. `orders/create`) and capture the raw POST body `B` and its genuine `shopify-hmac-sha256` header value `H` (valid since `H = HMAC-SHA256(secret, B)`).
2. Replay the request to the same app's webhook endpoint, keeping body `B` and header `shopify-hmac-sha256: H` unchanged, but set `shopify-shop-domain: victim.myshopify.com` and, if desired, a different `shopify-topic`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC only over `@raw_body` [8](#0-7)  — validation succeeds because `B`/`H` are unchanged.
4. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", body: <attacker's body>, ...)` [9](#0-8)  and, following the documented pattern, dispatches attacker-controlled work under the victim's tenant identity.
