### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while `shop`, `topic`, `webhook_id`, and `api_version` are all read from unauthenticated HTTP headers. `Registry.process` validates only that the body's HMAC matches, then passes the attacker-controllable `shop` header straight to the handler.

### Finding Description
`Registry.process` validates the webhook by calling `Utils::HmacValidator.validate(request)`, which checks `request.hmac` against a signature computed over `request.to_signable_string`: [1](#0-0) [1](#0-0) 

`to_signable_string` is defined to be just the raw body: [2](#0-1) 

But `shop`, `topic`, `webhook_id`, and `api_version` are all pulled from HTTP headers that are never included in the signed bytes: [3](#0-2) 

`HmacValidator.validate_signature` compares `verifiable_query.hmac` against a signature computed solely from `to_signable_string`: [4](#0-3) 

Finally, `Registry.process` forwards the unauthenticated `request.shop` value directly into the `WebhookMetadata` passed to the app's handler: [5](#0-4) 

The identity binding that is broken is: `hmac_valid_for(raw_body)` should imply `shop_header == shop_that_originated_this_body`, but the gem never enforces that equality — `to_signable_string` covers only `raw_body`, not `shop`, `topic`, or `webhook_id`. Any bytes (`raw_body`, `hmac`) pair that is valid for one shop's webhook remains valid when replayed with an arbitrary `x-shopify-shop-domain` header, because that header plays no role in the signature computation.

### Impact Explanation
An unprivileged internet user who can trigger any webhook delivery to their own shop (e.g., by installing a public/dev version of the target app, which produces a legitimately-signed `raw_body`/`hmac` pair) can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `shop-domain` header. Because `Registry.process` only verifies the HMAC of the body and then trusts `request.shop` as the tenant identity for the handler, the host application's webhook handler will process attacker-supplied data under the identity of a victim shop of the attacker's choosing. This is a cross-tenant identity confusion in the gem's own signature-verification/dispatch logic, which is the exact class of "field acted on but not covered by the HMAC" break called out for this exercise.

### Likelihood Explanation
Likelihood is moderate-to-high in practice: the webhook endpoint is public by design (Shopify calls it unauthenticated), so any internet user who can obtain one legitimately-signed body (which is easy for public apps supporting free installs, since installing gives them a real webhook body/HMAC for their own shop) can immediately attempt the replay with a forged `shop-domain` header, with no dependency on `api_secret_key`, tokens, or any other credential.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) as part of the signed/verified material for webhook requests, or explicitly bind the verified body to the specific shop it was issued for (e.g., require the handler-visible `shop`/`topic`/`webhook_id` to be derived only from data that is itself covered by `to_signable_string`, or maintain a separate signature check that covers these header values before trusting them in `WebhookMetadata`).

### Proof of Concept
1. Attacker installs the target Shopify app on their own controlled shop `attacker.myshopify.com` and triggers a webhook subscription (e.g., `orders/create`), receiving a legitimately Shopify-signed POST with body `B` and header `x-shopify-hmac-sha256: H` (valid for `B`), plus `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker replays the exact same body `B` and `hmac` header `H` to the same webhook endpoint of a shared/multi-tenant app instance, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because `to_signable_string` only checks body `B` against `H` — `shop` is never part of the signed bytes: [6](#0-5) 
4. The handler is invoked with `WebhookMetadata` whose `shop` field is `victim.myshopify.com`, causing the host application to process attacker-controlled data as if it originated from the victim tenant. [5](#0-4)
