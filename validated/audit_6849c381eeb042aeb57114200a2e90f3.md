### Title
Attacker-controlled `swap` route injects arbitrary token transfers into the caller's signed auth tree, draining wallet funds beyond the routed amount - (File: contracts/controller/src/strategies/swap.rs)

### Summary
The SQLi class (a user-controlled parameter reaching a privileged execution sink unsanitized) maps onto XOXNO Lending's strategy verbs: `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, and `multiply` accept attacker-influenced `swap: Bytes` route payloads and forward them verbatim to the configured swap aggregator without decoding or constraining the pool/token addresses the payload names. The router invokes whatever pool contract the payload names; code running in that frame can issue `token.transfer(victim, attacker, amount)` calls that Soroban simulation records as children of the caller's `require_auth` entry. A caller who signs the simulated auth tree thereby authorizes transfers of arbitrary wallet tokens unrelated to the swap.

### Finding Description
`swap_tokens` in `contracts/controller/src/strategies/swap.rs` (lines 13-55) forwards the opaque `swap: &StrategySwap` bytes to `router.execute_strategy(&controller, &amount_in, swap)` without inspecting which addresses the route invokes. The controller bounds only its own grant: one exact `authorize_transfer_as_current` of `amount_in` plus measured output checks (`RouterOverspend`, `NoSwapOutput`). That bound covers the controller's input only — it does not constrain what the route-named pools do while on the call stack beneath the caller's root `require_auth` on `swap_collateral`/`swap_debt`/`repay_debt_with_collateral`/`multiply` (`interfaces/controller/src/lib.rs`, lines 88-117).

Because Soroban records every `require_auth` that executes during simulation as a sub-invocation of the signer's auth entry, a payload-named contract calling `token::Client::transfer(victim, attacker, amount)` is recorded under the caller's `swap_collateral` root. The host then executes it if the caller signs that tree. The proof exists in the repo's own harness: `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` registers an `UnlistedPoolRouter` that calls the payload-named `hop_pool`, and a `RogueHopPool` whose `swap()` executes `token.transfer(alice → attacker, WALLET_BALANCE)` (lines 39-72). `simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry` shows the recorded auth tree contains the stolen transfer as a child of `swap_collateral`, and `enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer` shows the signed tree executes the drain (lines 194-269). The threat model documents the same exposure for the real router, which "keeps no allowlist" of the pools/tokens its payload names (`docs/explanation/threat-model.md`, lines 154-165).

The injection vector is the `key`/`swap` parameter: arbitrary contract addresses embedded in caller-supplied bytes are dispatched as code, and their privilege demands (arbitrary `transfer` auths) are folded into the signer's authorization tree — directly analogous to the `key` parameter reaching command execution in CVE-2025-45809.

### Impact Explanation
Theft of user funds. A malicious route can transfer any token the caller holds in any amount, recorded as a legitimate child of the authorization the caller signs for an ordinary swap. The loss is the caller's whole wallet exposure at signing time, not bounded by `amount_in`, the router `min_out`, or the controller's post-swap risk gates — none of which inspect the auth children. The attack surface is every strategy verb that accepts `swap`/`convert_swap` bytes.

### Likelihood Explanation
Medium. Exploitation requires the caller to sign a route whose auth tree contains the rogue transfer — typically delivered via a poisoned off-chain quote or a compromised/malicious router payload — and an honest simulation does disclose the extra child to a decoding client. However, wallets do not render nested auth children to users, and the repository's own guidance acknowledges clients must explicitly decode and reject such trees; nothing on-chain prevents it. The reachability path (`swap` bytes on `swap_collateral` etc.) is explicitly in-scope and an unprivileged address supplies the payload.

### Recommendation
Constrain the injection at the contract layer instead of relying on client-side auth-tree hygiene:
- Have the controller decode the route (or require the router to) and verify every pool/token address it will invoke against the protocol's known-venue registry, or enforce that the strategy call produces no auth children beyond the single authorized input transfer by refusing routes that cause additional `require_auth` under the caller.
- Alternatively, run the router leg under a dedicated sub-account/auth scope so pool-invoked `require_auth` calls can never join the user's signature tree.
- At minimum, document the hard requirement that integrators simulate, decode the auth tree, and reject any child other than the expected input transfer before signing.

### Proof of Concept
Existing test: `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`.

1. Alice has a funded lending account and holds `WALLET_BALANCE` of an unrelated token.
2. Attacker crafts a `RoutedSwap` whose `hop_pool` is `RogueHopPool`, configured with `(victim=alice, wallet_token, to=attacker, amount=WALLET_BALANCE)` (lines 111-125).
3. Alice invokes `swap_collateral(alice, account_id, USDC, SWAP_IN, ETH, route)` under recording-mode simulation; the router calls `hop_pool.swap()`, which executes `token.transfer(alice → attacker, WALLET_BALANCE)` (lines 62-71).
4. Simulation records the theft as a sub-invocation of Alice's `swap_collateral` auth entry (asserted at lines 206-222); Alice's wallet balance goes to 0 and the attacker's to `WALLET_BALANCE` (lines 224-226).
5. In enforcing mode, signing the simulation-produced tree authorizes and executes the drain (lines 258-268); only a caller who independently detects the extra child is safe (lines 239-256).
