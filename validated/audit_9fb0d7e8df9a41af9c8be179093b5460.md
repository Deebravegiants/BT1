## Title
Webhook `shop` domain trusted from unauthenticated header while HMAC only signs the request body — ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop` value from the `x-shopify-shop-domain` / `shopify-shop-domain` HTTP header, but the HMAC signature that `ShopifyAPI::Webhooks::Registry.process` validates only ever covers the raw request body. The `shop` (and `topic`, `webhook_id`, `api_version`) fields are never part of the signed bytes, so they are not bound by the HMAC check at all.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` reads the tenant identity straight from a header that is not part of that signed string: [2](#0-1) 

`Registry.process` validates the HMAC over the request, then immediately hands `request.shop` to the app's webhook handler as trusted tenant identity, with no additional check tying the shop header to the signed payload: [3](#0-2) 

The identity binding that should hold is:
`shop asserted to the handler (request.shop, from header)` == `shop cryptographically authenticated by HMAC (bytes covered by to_signable_string)`

Before the attack: for a legitimately delivered webhook, `hmac = HMAC(secret, raw_body)` and `shop-domain header = <shop that triggered the event>` happen to correspond because Shopify's servers set both correctly for that specific shop's event.

After the attacker's request: an attacker who controls a shop that has the app installed can trigger a webhook event with a body of their choosing (e.g. `app/uninstalled`, or any webhook with attacker-controlled content such as `orders/create` with attacker-chosen order fields) and capture the resulting `(raw_body, hmac)` pair — both values are visible to the attacker because they are delivered to the attacker's own registered callback URL. Since `HMAC(secret, raw_body)` depends only on the body and the app's shared `client_secret` (not on the shop), the attacker can then replay the exact same `raw_body` and `hmac` header to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` will pass because it only re-derives the HMAC from `raw_body`: [4](#0-3) 

`Registry.process` then dispatches to the handler with `shop: request.shop` set to the victim's domain, even though nothing about that value was ever authenticated: [5](#0-4) 

This is precisely the "bytes verified versus bytes parsed" analog to the H‑9 report's pattern: a field that is acted upon (`shop`, used as the tenant key by the handler) is not covered by the integrity check (`HMAC` over `raw_body` only), letting the attacker desynchronize the two.

### Impact Explanation
Any host application that uses `data.shop` from the webhook handler as the tenant key (exactly as the gem's own documentation recommends: `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) can be tricked into attributing attacker-controlled webhook content to an arbitrary victim shop. Depending on the topic replayed (e.g. `app/uninstalled`, `shop/redact`, `customers/data_request`, or business-logic-relevant topics like `orders/create`/`app_subscriptions/update`), this enables cross-tenant data injection/confusion in the merchant's own backend under a victim shop's identity — a cross-tenant boundary violation stemming entirely from this gem's failure to bind the header-derived `shop` to the HMAC-verified bytes.

### Likelihood Explanation
The attacker only needs their own (or any) shop with the target app installed to obtain one legitimately-signed `(raw_body, hmac)` pair — no access to `client_secret`, no privileged account, and no interception of the victim's traffic is required. They then send a normal unauthenticated HTTP POST to the app's public webhook endpoint with a forged `shop-domain` header. This requires no special network position.

### Recommendation
Include the shop domain (and ideally topic, webhook id, api version) in the value that is HMAC-verified, or otherwise cryptographically bind the header-derived `shop` to the signed payload before it is handed to `WebhookMetadata`/the handler in `Registry.process`. At minimum, document that `shop-domain` is unauthenticated and callers must independently corroborate it against a known installed-shop record before trusting it as a tenant key.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; trigger a webhook (e.g. `app/uninstalled`) to capture a valid `(raw_body="{}", x-shopify-hmac-sha256=<hmac>)` pair delivered to the attacker's endpoint.
2. Send a POST to the victim app's webhook endpoint with the same `raw_body` and `x-shopify-hmac-sha256` header, but set `x-shopify-shop-domain: victim.myshopify.com` and `x-shopify-topic: app/uninstalled`.
3. `ShopifyAPI::Webhooks::Registry.process` computes `HmacValidator.validate(request)` using only `raw_body`, which matches, so it proceeds: [6](#0-5) 
4. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"`, believing the (attacker-crafted) event genuinely originated from the victim shop.

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

        end
