### Title
Emporium `runAction` skips ALL balance/backing checks when `erc20TokenAddresses.length==0`, letting an attacker drain Emporium's ETH via `op.endpoint.call{value: op.value}(op.callData)` - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
When the "Min" circuit path is used (`erc20TokenAddresses.length==0`, verified by `MainEVMCircuitMin` whose only real signal is `Poseidon(1)([messageSeed])`), `runAction` still unconditionally executes `stack.ops`, including `op.endpoint.call{value: op.value}(op.callData)`, but every balance-backing loop in both `EmporiumUpgradeable.runAction` and `Hinkal.transact` is keyed on `circomData.erc20TokenAddresses.length`, so with length 0 none of them execute. An unprivileged EOA can therefore craft `stack.signerAddress=address(0)` (skipping the ECDSA check in `verifyWallet`) and an op that sends Emporium's own ETH balance to an attacker-controlled endpoint, with no on-chain requirement that this outflow be matched by any deposit, `amountChanges`, or UTXO accounting.

### Finding Description
The broken equality: `ETH leaving Emporium via op.value` should equal `-deltaAmountChanges[i]` / `amountChanges[i]` for `erc20TokenAddresses[i]==address(0)`, enforced by the `balanceChange`/`BalanceChangeShouldBePositive` check in `EmporiumUpgradeable.runAction` (lines 132-151) and by the slippage/balance-diff `require` in `Hinkal.transact` (lines 97-146). Both are `for (uint i = 0; i < circomData.erc20TokenAddresses.length; i++)` loops [1](#0-0) [2](#0-1) . When `erc20TokenAddresses.length == 0` (the "Min" path selected by `formInputForCircom`) [3](#0-2) , these loops never execute at all, but the ops-execution loop that performs the actual ETH transfer is *not* gated by `erc20TokenAddresses.length` — it iterates `stack.ops` directly [4](#0-3) .

`verifyWallet` only checks a signature when `stack.signerAddress != address(0)`; if it is `address(0)` it returns immediately after marking `usedMessages[emporiumMessage]=true` [5](#0-4) . With `signerAddress==0`, the ops loop takes the "Stateless Interaction" branch and calls `op.endpoint.call{value: op.value}(op.callData)` directly from the Emporium contract's own balance [6](#0-5) .

Note however that `runAction` is protected by `onlyAllowedRecipient`, which requires `msg.sender` (i.e., `Hinkal`, the caller of `IExternalActionV2.runAction`) to be a registered allowed recipient [7](#0-6) . Since `Hinkal._externalTransact` is the only caller in the intended flow, and `Hinkal` would need to be whitelisted as an allowed recipient, this modifier does not block the attacker's path as long as `Hinkal` itself is on that allow-list (which is the expected production configuration; only `owner` can add/remove allowed recipients, but `Hinkal` is intended to be one).

The `calldataHash` binds `circomData.externalActionData` (hence the raw bytes of `externalActionMetadata`, i.e. `stack.ops`) via `getHashedCalldata1`, and this is checked with a plain Solidity `require` in `performHinkalChecks`, independent of the circuit [8](#0-7) . This prevents an attacker from swapping ops *after* proof generation, but does **not** prevent the attacker from initially choosing malicious `op.value`/`op.endpoint`/`op.callData` themselves, since they fully control `circomData` and can compute a matching proof and hash for whatever ops they choose.

Exploit flow:
1. Attacker observes/creates a state where Emporium holds ETH (e.g. leftover dust from relay fee flows, or ETH sent to Emporium accidentally/by design in an earlier transaction).
2. Attacker crafts `CircomData` with `erc20TokenAddresses=[]`, `amountChanges=[]`, `dimensions.tokenNumber=0`, `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `externalActionData.externalAddress = Emporium`, and `externalActionMetadata = abi.encode(EmporiumStack{signerAddress:address(0), ops:[{endpoint: attackerContract, invokeWallet:false, value: address(Emporium).balance, callData: "" }]})`.
3. Attacker generates a trivial valid proof for `MainEVMCircuitMin` (only needs a `messageSeed` witness), and calls `Hinkal.transact` directly with matching `calldataHash`.
4. `performHinkalChecks` passes (`dimensionsCheck` trivially passes with tokenNumber 0; `getHashedCalldata` matches since attacker computed it correctly), `verifyProof` passes, `rootHashExists` — note this still requires a valid on-chain Hinkal root, but with `erc20TokenAddresses.length==0` no nullifiers/commitments are required so this doesn't gate anything meaningfully tied to funds.
5. `_externalTransact` computes `deltaAmountChanges = []` (empty, since based on `erc20TokenAddresses.length`), calls `EmporiumUpgradeable.runAction`.
6. `runAction`: `verifyWallet` short-circuits (no signature check); ops loop executes `op.endpoint.call{value: Emporium.balance}(op.callData)`, draining Emporium's ETH to the attacker's contract; all subsequent balance-check loops are skipped (length 0); function returns an empty `utxoSet`.
7. Back in `Hinkal.transact`, the `erc20TokenAddresses.length==0` loop (lines 96-147) is also skipped, so no revert.

### Impact Explanation
This allows theft of any ETH balance sitting in the Emporium contract by an unprivileged attacker, with zero proof coverage or on-chain accounting constraining the outflow. This is theft of protocol/relay funds parked at the Emporium address — classified High under the given severity rubric ("theft or permanent freezing of protocol/relay fees ... executing calls or moving assets ... never authorised"), and could reach Critical if the drained ETH is user-owned in-flight funds (e.g., a prior Emporium op's leftover deposit not yet swept out). The attack is repeatable every time Emporium accumulates ETH balance (dust from relay fees, partial op execution leftovers, or accidental transfers), and costs the attacker only gas plus proof generation for a trivial circuit.

### Likelihood Explanation
Preconditions: (1) Emporium holds a nonzero ETH balance at the time of attack — this can happen from relay-fee routing dust, prior ops leaving residual ETH un-swept (because `handleOut`'s sweep logic is itself gated on `erc20TokenAddresses.length>0`), or a direct ETH transfer to the Emporium address; (2) `Hinkal` is a registered `onlyAllowedRecipient` for `EmporiumUpgradeable` (expected in production since Hinkal is the entrypoint that calls `runAction`). The attacker needs no privileged role, no compromised relay, and only needs to generate a proof for a circuit with a single trivial constraint (`message <== Poseidon(1)([messageSeed])`), which they can freely do as they control the private witness. The attack is fully repeatable as long as Emporium's ETH balance is nonzero.

### Recommendation
Do not gate the balance-backing / `BalanceChangeShouldBePositive` verification loops in `EmporiumUpgradeable.runAction` (and the corresponding loop in `Hinkal.transact`) solely on `circomData.erc20TokenAddresses.length`. Instead, always verify that the sum of ETH/token value moved by `stack.ops` (tracked via `address(this).balance` before/after, for ETH specifically) is fully accounted for even when `erc20TokenAddresses.length==0`, e.g. by checking `address(Emporium).balance` (and/or all relevant token balances) before and after the ops loop regardless of the token-array length, and reverting if any balance decreases without matching authorized backing. Alternatively, forbid `op.value > 0` entirely on the Min circuit path, since that path is documented as depending only on `messageSeed`/`calldataHash`/`timeStamp` and was never meant to authorize value transfers.

### Proof of Concept
Hardhat fork test:
1. Deploy Hinkal + EmporiumUpgradeable, register `HINKAL_EMPORIUM_ACTION_ID`, register `Hinkal` as `EmporiumUpgradeable`'s allowed recipient, register `VerifierEVMMin0v4`.
2. Fund `EmporiumUpgradeable` with 1 ETH directly (`hre.network.provider.send("hardhat_setBalance", ...)` or a prior legitimate op that leaves dust).
3. Deploy a simple `AttackerSink` contract with a `receive()` function.
4. Off-chain: compute `emporiumMessage`, `timeStamp`, build `EmporiumStack{signerAddress: address(0), ops: [{endpoint: AttackerSink, invokeWallet:false, value: 1 ether, callData: "0x"}]}`, ABI-encode into `externalActionMetadata`.
5. Compute `calldataHash = getHashedCalldata(circomData)` matching the constructed `circomData` (empty `erc20TokenAddresses`/`amountChanges`/etc., `dimensions.tokenNumber=0`).
6. Generate a valid `MainEVMCircuitMin` proof locally with an arbitrary `messageSeed` witness satisfying `message <== Poseidon(1)([messageSeed])`, matching the 3 public inputs `[emporiumMessage /*outTimeStamp per struct order*/, timeStamp, calldataHash]` as built by `formInputEmporiumMin`.
7. Call `Hinkal.transact(a,b,c,dimensions,circomData)` from an unprivileged EOA.
8. Assert: `address(EmporiumUpgradeable).balance` decreases by exactly 1 ether and `address(AttackerSink).balance` increases by 1 ether, while `circomData.amountChanges` is empty (`[]`) and no `require` in either `Hinkal.transact` or `EmporiumUpgradeable.runAction` reverted — proving the ETH outflow is entirely uncorrelated with, and unconstrained by, any `amountChanges`/`deltaAmountChanges`/proof-covered value.
