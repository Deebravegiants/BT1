Based on my review of the webhook verification code, I found a genuine identity-binding gap that matches the requested bug class.

### Title
Webhook `shop`/`topic` attribution is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable signature from the raw request body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values that the handler later trusts as the event's tenant identity are read from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then unconditionally forwards these header-derived values to the app's handler as if they were verified, breaking the binding between "bytes verified" and "bytes acted on."

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from attacker-controllable HTTP headers, none of which are part of the signed content: [2](#0-1) 

`Registry.process` verifies the HMAC against the body, but then trusts `request.shop` and `request.topic` (unverified headers) to route and label the event: [3](#0-2) 

The `HmacValidator` only compares the computed signature of `to_signable_string` (the body) against the `hmac` header — it never binds `shop-domain` or `topic` into the signed material: [4](#0-3) 

The equality that should hold is: `shop attributed to the processed event == shop that the HMAC-signed bytes originated from`. Because the HMAC only covers the body, this equality is never enforced — the `shop` (and `topic`/`webhook_id`) fields are "fields acted on but not covered by the HMAC."

An unprivileged internet user who operates their own Shopify store can install the target app, causing Shopify to send legitimate webhook POSTs to the app's public webhook endpoint containing a valid `(body, hmac)` pair signed with the app's `client_secret` for their own shop. Because headers are not signed, the attacker can capture such a request and replay it directly against the app's webhook endpoint with the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header rewritten to name a **different, victim** shop. `Registry.process` will still find the HMAC valid (it only checks the body) and will hand `WebhookMetadata.new(shop: <victim-shop>, topic: ..., body: <attacker's own body>, ...)` to the app's handler.

### Impact Explanation
If the host application follows the gem's documented usage — which explicitly states that `Registry.process` "will verify the request did indeed come from Shopify" — and uses `WebhookMetadata#shop` as the authenticated tenant key (e.g., to look up/update per-shop records, decrement inventory, mark orders paid, trigger fulfillment, etc.), an attacker can inject events falsely attributed to any shop of their choosing. This is a cross-tenant confused-deputy vulnerability: data or side effects intended for the attacker's own store get attributed to (and can corrupt state for) a victim merchant, without needing the victim's credentials, access token, or `client_secret`.

### Likelihood Explanation
Exploitation only requires an attacker to install the app on their own store (unprivileged, self-service) to obtain one legitimately signed `(body, hmac)` pair, then send a direct HTTP POST to the app's public webhook URL with a modified `shop-domain`/`topic` header. No secret material, victim credentials, or privileged access is needed, making this readily reachable by any internet user targeting an app built per the gem's own documentation.

### Recommendation
Bind the `shop`, `topic`, and `webhook_id` header values into the HMAC-signable representation (or otherwise cross-check them against a value obtained from a source that Shopify signs, such as re-verifying the webhook via the Admin API using the claimed shop's session before dispatching to the handler). At minimum, `ShopifyAPI::Webhooks::Request#to_signable_string` should include the shop domain and topic so that `HmacValidator.validate` fails if these headers are altered independently of the body.

### Proof of Concept
1. Install the target app on an attacker-controlled development/trial store (`attacker-shop.myshopify.com`) and subscribe to a webhook topic (e.g., `orders/paid`).
2. Capture a legitimate webhook Shopify sends to the app's endpoint: raw body `B`, header `x-shopify-hmac-sha256: H` (valid HMAC of `B` with the app's `client_secret`), `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Replay the exact same body `B` and HMAC header `H` to the app's webhook endpoint, but change `x-shopify-shop-domain` to `victim-shop.myshopify.com` (and/or a different `x-shopify-topic`).
4. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` succeeds (it only checks body `B` against `H`), and `Registry.process` in `lib/shopify_api/webhooks/registry.rb` dispatches `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: ..., body: parsed(B), ...)` to the app's handler, causing the app to process attacker-supplied data under the victim shop's identity.
