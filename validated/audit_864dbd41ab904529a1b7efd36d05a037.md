### Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while `ShopifyAPI::Webhooks::Registry.process` validates the request's HMAC and then unconditionally trusts the un-signed `shop-domain` header when dispatching to the app's handler. Because Shopify's webhook HMAC is computed over the request body with the app's single, shop-independent `client_secret`, any request whose body+HMAC pair is valid for *any* shop installed on the app will also pass validation for a forged `shop-domain` header value, letting an attacker attribute arbitrary webhook payloads to a victim shop.

### Finding Description
The equality that should hold is:

`shop bound by the verified HMAC == shop the handler acts on`

`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` is only `@raw_body`: [2](#0-1) 

The `shop` accessor instead reads directly from the `shop-domain` HTTP header, which is not part of the signed content at all: [3](#0-2) 

`Registry.process` validates the HMAC and then, immediately afterward, builds the metadata handed to the app's handler using this unauthenticated `request.shop`: [4](#0-3) 

Because Shopify computes webhook HMACs using the app's single `client_secret` (the same secret is used for every shop that installs the app — see `Context.api_secret_key`/`old_api_secret_key` used identically for all shops in `HmacValidator.validate`), any `(raw_body, hmac)` pair that is valid for one installed shop is valid for the exact same body regardless of which shop the request claims to be from. An unprivileged attacker who installs the target app on their own shop (a normal, unprivileged action for any public Shopify app) will receive genuine Shopify-signed webhook deliveries for their own shop. They can then replay that exact `(raw_body, hmac)` pair directly to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header value naming a victim shop. `HmacValidator.validate` will report success (the body/HMAC pair is untouched and correctly signed), and `Registry.process` will forward `WebhookMetadata.new(... shop: request.shop ...)` with the attacker-chosen shop to the app's handler — breaking the binding between "bytes cryptographically verified" and "tenant the data is attributed to."

This mirrors the report's bug class: a field ("shop") that the receiving logic acts on (tenant attribution/dispatch) is not covered by the cryptographic check (HMAC over `raw_body` only), so verifying the bytes gives no guarantee about the field's authenticity.

### Impact Explanation
This allows cross-tenant data injection: an app that uses `WebhookMetadata#shop` to decide which merchant record to update/delete (e.g., `customers/redact`, `shop/redact`, order/product sync) can be tricked into applying attacker-controlled webhook content to a victim shop's data, since the gem presents `request.shop` as if it were verified once `HmacValidator.validate` succeeds. This satisfies the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Exploitation only requires the attacker to be an unprivileged installer of the target public app on their own store — a normal, unprivileged action — and the ability to send an HTTP POST to the app's public webhook endpoint with a captured body/HMAC and a forged header. No access to the app's `client_secret`, access tokens, or any victim credentials is required.

### Recommendation
Bind the shop (and other dispatch-critical fields such as topic/api_version/webhook_id) into the HMAC-covered content, or otherwise independently authenticate the shop associated with a webhook delivery (e.g., cross-check against a shop that is known to have this webhook subscribed, rather than trusting the header once the body HMAC validates). At minimum, document clearly that `request.shop` is unauthenticated and must not be used as a trust boundary by consuming applications, or change `HmacValidator`/`Registry.process` to fail closed if the header-derived shop cannot be corroborated.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (normal, unprivileged install flow).
2. Shopify delivers a legitimate webhook to the app's endpoint with a real body `B` and header `X-Shopify-Hmac-Sha256: HMAC(B, client_secret)`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker captures `B` and the HMAC value.
4. Attacker crafts and sends their own POST to the app's webhook endpoint with the same body `B`, the same (still-valid) HMAC header, but `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `HMAC(B, client_secret)`: [5](#0-4) 
6. The app's handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and processes attacker-controlled body content as though it belongs to the victim shop.
