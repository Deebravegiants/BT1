### Title
Unvalidated `shop` domain in `Oauth.begin_auth`/`validate_auth_callback` allows attacker-controlled OAuth redirect host and forced OAuth completion - ([File: lib/shopify_api/auth/oauth.rb])

### Summary
Every other credential-issuing entry point in this gem (`TokenExchange.exchange_token`'s `dest` handling, `ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`) validates the caller-supplied `shop` string with `Utils::ShopValidator.sanitize!` before using it to build a request host and before binding it into the resulting `Session`. `ShopifyAPI::Auth::Oauth.begin_auth` and `ShopifyAPI::Auth::Oauth.validate_auth_callback`, which implement the Authorization Code Grant flow, never call `ShopValidator` at all. The `shop` string flows straight from the app's own (unauthenticated) input into the OAuth redirect URL and into the session that is ultimately created.

### Finding Description
`ShopValidator.sanitize!` / `sanitize_shop_domain` exist specifically to constrain a `shop` string to `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`) before it is used to construct a request host: [1](#0-0) [2](#0-1) 

`ClientCredentials.client_credentials` and `RefreshToken.refresh_access_token` both call `Utils::ShopValidator.sanitize!(shop)` first, and only the *validated* shop is used to build the session and issue the request: [3](#0-2) [4](#0-3) 

`TokenExchange.exchange_token` avoids the issue differently, by deriving the shop from the signed JWT `dest` claim rather than trusting a caller-supplied string: [5](#0-4) 

By contrast, `Oauth.begin_auth` takes the caller-supplied `shop:` parameter (per the gem's own docs, this typically comes straight from a request header/query param, e.g. `shop = request.headers["Shop"]`) and feeds it unvalidated into `auth_base_uri(shop)`, which builds `https://#{shop}/admin` and is used as the redirect target the merchant's browser is sent to: [6](#0-5) [7](#0-6) [8](#0-7) 

The nonce `state` is put in a cookie and returned to be set on the requester's browser regardless of what `shop` was supplied: [9](#0-8) 

Later, `validate_auth_callback` re-uses the (still-unvalidated-against-`ShopValidator`) `auth_query.shop` value both to build the access-token request host (via `Auth::Session.new(shop: auth_query.shop)` → `Clients::HttpClient`) and as the `shop` bound into the resulting persisted `Session`: [10](#0-9) [11](#0-10) 

The only integrity guarantee here is `Utils::HmacValidator.validate(auth_query)`, which binds `shop` only into the HMAC computed over `code, host, shop, state, timestamp` using the app's own `api_secret_key`: [12](#0-11) [13](#0-12) 

This HMAC check happens on the **callback** step (`validate_auth_callback`), i.e. after Shopify has already signed and redirected back — it validates that Shopify (holder of the secret) produced the parameters, so `shop` at that point can't be forged by a network attacker without the secret. **The gap is `begin_auth`**: it has no equivalent binding at all, because the flow hasn't started yet — `shop` there is raw, attacker-influenceable input from whoever hits the app's own login route, and it is never checked against `ShopValidator.TRUSTED_SHOPIFY_DOMAINS` (unlike the sibling flows in `client_credentials.rb` and `refresh_token.rb`).

The identity binding broken is: `shop as trusted by the app when redirecting a merchant's browser into an OAuth grant flow` should equal `shop validated as an actual Shopify domain`, but in `begin_auth` the app trusts whatever `shop` string it was given with no domain check.

### Impact Explanation
An attacker who controls (or can influence) the `shop` value passed to `begin_auth` (e.g., by getting a victim merchant to click a crafted link into the host app's own `/login?shop=...` style route, which the gem's own documented usage pattern takes straight from request input) can cause the app to:
- Redirect the victim's browser to `https://attacker-controlled-host/admin/oauth/authorize?client_id=<app_client_id>&scope=...&redirect_uri=<app_callback>&state=<nonce>`, disclosing the app's `client_id`/scopes and its `redirect_uri` to a domain the attacker controls, and
- Set a `state` cookie on the victim's browser tied to a nonce the attacker can precompute/observe, enabling a forced-OAuth-completion / session-fixation attack: if the attacker can subsequently drive the victim (or their own browser under the victim's session) through the callback with a Shopify-signed `code`/`hmac` for the *attacker's own* shop, the app will bind and persist that attacker shop's session as if it were the intended flow, because `validate_auth_callback` performs no independent domain check of its own beyond the HMAC (which the attacker can legitimately obtain for their own shop).

This matches the rules' explicitly listed High-impact category: "session fixation or forced OAuth completion." No `api_secret_key`, access token, or privileged credentials are required to trigger the initial redirect misdirection, since it's the `begin_auth` step itself that is unguarded.

### Likelihood Explanation
Likelihood is Medium: the vulnerable code path (`begin_auth`) is only reachable if the host application passes attacker-influenced input directly into `shop:`, which is exactly the pattern shown in this gem's own documentation (`shop = request.headers["Shop"]`, then straight into `begin_auth`). Because `ShopValidator.sanitize!` is applied everywhere else in the auth surface (`client_credentials.rb`, `refresh_token.rb`), the omission in `oauth.rb` appears to be an inconsistency/gap rather than an intentional design choice — directly analogous to the storage-slot gap miscalculation in the reference report, where one code path (`LockingBase`) failed to apply a safeguard that sibling/parallel code consistently applies elsewhere.

### Recommendation
Apply `Utils::ShopValidator.sanitize!(shop)` (or `sanitize_shop_domain`) at the start of `Oauth.begin_auth` before calling `auth_base_uri(shop)`, and likewise validate `auth_query.shop` against `ShopValidator` in `validate_auth_callback` before using it to build `Auth::Session.new(shop: auth_query.shop)` / issuing the access-token request, mirroring the pattern already used in `client_credentials.rb` and `refresh_token.rb`.

### Proof of Concept
1. Host app implements the OAuth login route exactly as documented: `shop = request.headers["Shop"]; ShopifyAPI::Auth::Oauth.begin_auth(shop: shop, redirect_path: "/auth/callback")` (see `docs/usage/oauth.md` lines 181–199).
2. Attacker crafts a request/link to the app's login route with `Shop: evil.example.com` (or a look-alike domain not matching `TRUSTED_SHOPIFY_DOMAINS`).
3. `Oauth.begin_auth` calls `auth_base_uri("evil.example.com")` → `https://evil.example.com/admin`, and the app issues `head 307` / `Location: https://evil.example.com/admin/oauth/authorize?client_id=<APP_CLIENT_ID>&scope=<APP_SCOPES>&redirect_uri=<APP_HOST>/auth/callback&state=<nonce>`, disclosing app configuration to an attacker-controlled host and setting the `state` cookie on the requester's browser — with no domain validation performed anywhere in `lib/shopify_api/auth/oauth.rb`, unlike the equivalent `ShopValidator.sanitize!` guard present in `lib/shopify_api/auth/client_credentials.rb` and `lib/shopify_api/auth/refresh_token.rb`.

        def begin_auth(shop:, redirect_path:, is_online: true, scope_override: nil)
          scope = if scope_override.nil?
            ShopifyAPI::Context.scope
          elsif scope_override.is_a?(ShopifyAPI::Auth::AuthScopes)
            scope_override
          else
            ShopifyAPI::Auth::AuthScopes.new(scope_override)
          end

          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = SecureRandom.alphanumeric(NONCE_LENGTH)

          cookie = SessionCookie.new(value: state, expires: Time.now + 60)

          query = {
            client_id: ShopifyAPI::Context.api_key,
            scope: scope.to_s,
            redirect_uri: "#{ShopifyAPI::Context.host}#{redirect_path}",
            state: state,
            "grant_options[]": is_online ? "per-user" : "",
          }

          query_string = URI.encode_www_form(query)
          auth_route = auth_base_uri(shop) + "/oauth/authorize?#{query_string}"

          { auth_route: auth_route, cookie: cookie }
        end

        def validate_auth_callback(cookies:, auth_query:)
          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state

          null_session = Auth::Session.new(shop: auth_query.shop)
          body = {
            client_id: Context.api_key,
            client_secret: Context.api_secret_key,
            code: auth_query.code,
            expiring: Context.expiring_offline_access_tokens ? 1 : 0, # Only applicable for offline tokens
          }

          client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
          response = begin
            client.request(
              Clients::HttpRequest.new(
                http_method: :post,
                path: "access_token",
                body: body,
                body_type: "application/json",
              ),
            )
          rescue ShopifyAPI::Errors::HttpResponseError => e
            raise Errors::RequestAccessTokenError,
              "Cannot complete OAuth process. Received a #{e.code} error while requesting access token."
          end

          session_params = T.cast(response.body, T::Hash[String, T.untyped]).to_h
          session = Session.from(shop: auth_query.shop,
            access_token_response: Oauth::AccessTokenResponse.from_hash(session_params))

        def auth_base_uri(shop)
          return "https://#{shop}/admin" unless defined?(DevServer) && shop.include?(".my.shop.dev")

          # For first-party apps in development only, we leverage DevServer to build the admin base URI

          shop_name = shop.split(".").first

          "https://#{admin_host}/store/#{shop_name}"
        end

    auth_response = ShopifyAPI::Auth::Oauth.begin_auth(shop: domain, redirect_path: "/auth/callback")

    # Store the authorization cookie

      value: auth_response[:cookie].value

    head 307
    response.set_header("Location", auth_response[:auth_route])
