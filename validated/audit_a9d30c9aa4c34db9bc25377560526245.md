Confirmed: this is a genuine, reachable analog to the audit report on the Tron variant of the IntentGateway.

### Title
Non-standard ERC20/TRC20 `transfer` return value not decoded in `withdraw()` and `SweepDust` handling permanently locks escrowed funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron `IntentGatewayV2` contract escrows input tokens via `SafeERC20.safeTransferFrom` when orders are placed, but releases them via raw low-level `.call()` to the token's `transfer` selector without decoding the returned boolean, unlike the rest of the codebase (and the EVM `IntentGatewayV2`/`ExtrinsicIntents`/`HyperFungibleToken` contracts) which consistently use `SafeERC20.safeTransfer`/`safeTransferFrom`.

and for fee-token payouts: [2](#0-1) 
The same unsafe pattern is used in `SweepDust` handling inside `onAccept`: [3](#0-2) 

In every case, the code checks only that the low-level `call` itself did not revert (`success`), but never decodes/validates the returned `bool` value from `transfer()`. Per EIP-20 and Sherlock's referenced report class, some ERC20/TRC20 tokens (and non-standard, deflationary, blacklist-capable, or pausable tokens common on Tron) return `false` on failure instead of reverting. Contrast this with the intended pattern used for entering escrow, `IERC20(token).safeTransferFrom(...)` used in `placeOrder`, which reverts on any non-true return via OpenZeppelin's `SafeERC20`: [4](#0-3) 

Because `withdraw()` unconditionally proceeds — decrementing `_orders[body.commitment][token]`, setting `_filled[body.commitment] = beneficiary`, and (on the final leg) emitting `EscrowReleased`/`EscrowRefunded` — as soon as the raw call does not revert, a token that silently returns `false` will cause the gateway to mark the order as settled and destroy its accounting state while the beneficiary never actually receives the tokens.

### Impact Explanation
This is reachable by any relayer delivering a legitimate cross-chain `RedeemEscrow`/`RefundEscrow` POST message (`onAccept`, gated only by `onlyHost`/message authentication, not by privileged roles) or a `cancelOrder` GET response (`onGetResponse`), i.e. through the normal, unprivileged intent-fill/cancel flow — no malicious admin or governance action is required. If the escrowed token (or the configured fee token) is one that returns `false` instead of reverting on transfer failure (e.g. paused, blacklisted recipient, or a non-standard TRC20), the gateway will:
1. Decrement/zero the escrow accounting (`_orders[...] -= amount`), and
2. Mark the order `_filled`/emit `EscrowReleased`/`EscrowRefunded`,

while the beneficiary receives nothing. Because `_filled` and `_orders` are now updated, the escrowed funds become permanently unrecoverable — there is no other code path to re-attempt the transfer or refund since the withdrawal request is already considered fulfilled. This is a concrete freezing-of-funds vulnerability satisfying the "permanent freezing of funds" acceptance criterion.

### Likelihood Explanation
Likelihood is Medium: it requires the escrowed/fee token to be one whose `transfer` returns `false` on failure rather than reverting, combined with a transient failure condition (e.g., a blacklisted or paused beneficiary, or insufficient balance edge case on a non-reverting token implementation) at the exact time settlement is processed. This is plausible given Tron's TRC20 ecosystem includes several such non-standard tokens, and the protocol's own governance-driven token registration (`create_asset_mapping`) does not appear to restrict tokens to strict EIP-20 semantics.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `withdraw()` and the `SweepDust` branch of `onAccept()` with `SafeERC20.safeTransfer()`, consistent with the rest of the contract (which already imports and uses `SafeERC20` for `safeTransferFrom`). This ensures any non-true return value or revert is treated as a genuine failure, reverting the whole settlement transaction (allowing retry) instead of silently marking the order as settled.

### Proof of Concept
1. Governance registers a TRC20 token via `create_asset_mapping`/`NewDeployment` whose `transfer()` implementation returns `false` (rather than reverting) when the recipient is blacklisted or contract-paused, as is common for several Tron TRC20 tokens.
2. A user places a cross-chain order escrowing this token via `placeOrder` (uses `safeTransferFrom`, succeeds normally).
3. A solver fills the order on the destination chain; the source chain gateway receives the relayed `RedeemEscrow` message and calls `onAccept` → `withdraw()`.
4. At settlement time the beneficiary address happens to be blacklisted/paused on the token contract, so `token.call(transfer(...))` returns `(true, abi.encode(false))` — the call succeeds but the encoded return value is `false`.
5. `withdraw()` only checks `success` (true), so it proceeds to decrement `_orders[commitment][token]` and set `_filled[commitment] = beneficiary`, emitting `EscrowReleased`.
6. The beneficiary's tokens were never transferred, and the escrow has already been marked spent — the funds are permanently lost with no remaining recovery path.
