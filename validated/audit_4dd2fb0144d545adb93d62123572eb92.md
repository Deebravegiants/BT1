### Title
Webhook `shop` domain is not covered by the HMAC signature, allowing cross-tenant webhook impersonation - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` treats the `x-shopify-shop-domain` header as trusted tenant identity, but the HMAC signature computed by `Utils::HmacValidator` only ever covers the raw request body. Any actor who can obtain one valid `(body, hmac)` pair signed with the app's shared `client_secret` can replay that pair while substituting an arbitrary `shop` header, and `Registry.process` will accept it and dispatch it to the app's handler as if it came from that other shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes/compares the signature exclusively over `to_signable_string`: [2](#0-1) 

`Request#shop` is read directly from the `x-shopify-shop-domain`/`shopify-shop-domain` header with no cryptographic binding to the signature at all: [3](#0-2) 

`Registry.process` verifies the HMAC and then hands the *unverified* `request.shop` straight to the registered handler as the tenant identifier: [4](#0-3) 

The equality that should hold is: `shop that produced/authorized this signed payload == shop delivered to the handler`. Because `shop` is excluded from the signed content, this equality is not enforced by the gem — only `body` is bound to the secret, while `shop` is parsed independently and passed through unauthenticated. Since a Shopify app has one `client_secret` shared across every shop installation (not a per-shop secret), anyone who can install the app on any store (including their own) can obtain a validly-signed `(body, hmac)` pair and then resend it with a different `shop` header value. `HmacValidator.validate` will still return `true` because it never inspects `shop`.

### Impact Explanation
This breaks the tenant boundary the host application relies on `WebhookMetadata#shop` to establish: an attacker-controlled shop can produce webhook deliveries that the app processes as belonging to a victim shop it does not control, injecting attacker-influenced data (order/customer payloads, `app/uninstalled`, mandatory GDPR topics, etc.) into the victim tenant's processing path while passing the gem's own HMAC check. This is a cross-tenant access primitive gated only by the gem's HMAC verification, which the caller reasonably expects to authenticate the whole webhook including its origin.

### Likelihood Explanation
Requires only that the attacker install the target app on any shop (their own) and capture one real webhook delivery, or otherwise obtain a single valid `(raw_body, hmac)` pair for the app's shared secret — no access to `client_secret`, access tokens, or victim credentials is needed. The `shop` header can then be freely rewritten before delivery to the app's webhook endpoint.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the signable content used by `Request#to_signable_string`, or have `Registry.process`/`HmacValidator` independently bind the verified body to the specific `shop` header before constructing `WebhookMetadata`, so a payload signed for one shop cannot be replayed as another.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` and triggers a webhook (e.g. `orders/create`), capturing the raw POST body and its `x-shopify-hmac-sha256` value sent by Shopify — this HMAC is valid because it's computed from the shared `client_secret` over the body only, per `HmacValidator.validate`/`Request#to_signable_string` ( [1](#0-0) ).
2. Attacker resends the exact same body and `hmac` header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)` which passes (body unchanged), then builds `WebhookMetadata.new(shop: request.shop, ...)` using the spoofed `victim.myshopify.com` value ( [4](#0-3) ), and the handler processes it as an event from the victim shop.
