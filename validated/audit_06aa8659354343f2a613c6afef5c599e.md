### Title
`messageSigner.signMessage` accepts a caller-supplied `WalletAccount` object without validating its `seedId` against the authorized wallet, allowing cross-seed signing via `SeedBasedMessageSigner.#getSigner` / `keychain.signBuffer` - ([File: features/message-signer/src/module/message-signer.ts])

### Summary
`MessageSigner.#normalizeWalletAccount` only performs a trust-establishing lookup (via `walletAccountsAtom`) when the `walletAccount` param is a string key; when a raw `WalletAccount`-shaped object is passed, it is returned as-is and forwarded unchecked to `SeedBasedMessageSigner.signMessage`, which derives the signing key using `walletAccount.seedId` directly. This means the `seedId` field of the caller-supplied object is trusted implicitly, with no check that it matches an account registered under `walletAccountsAtom` or belongs to the caller's authorized wallet/session.

### Finding Description
The relevant code path is: [1](#0-0) 
which shows `#normalizeWalletAccount` short-circuiting object inputs without validation, versus the string branch that resolves against the trusted `walletAccountsAtom`.

`signMessage` then dispatches straight through: [2](#0-1) 

`SeedBasedMessageSigner.signMessage` -> `#getSigner` uses `walletAccount.seedId` verbatim to build the signer that calls `keychain.signBuffer({ seedId, keyId, ... })`: [3](#0-2) 

`keychain.signBuffer` itself performs no cross-check that the given `seedId` corresponds to any particular caller/session/account — it just looks up the seed's key material and signs: [4](#0-3) 

The SDK-level `exodus.messageSigner.signMessage` API is a thin passthrough with no additional origin/account scoping: [5](#0-4) 

The `messageSigner` module is registered as `public: true`, and its `README.md`/test fixtures show that both string and full `WalletAccount` object forms are accepted as valid inputs to `signMessage`: [6](#0-5) [7](#0-6) 

**However**, I could not find, in the code I was able to inspect, an actual dapp-facing RPC/provider handler (e.g. `personal_sign` / `eth_signTypedData` handler, wallet-connect or a browser-extension "dapp" bridge) that forwards an attacker/dapp-supplied `WalletAccount` object directly into `exodus.messageSigner.signMessage`. The dapp-facing layers I found (`connected-origins`, Solana/Ethereum provider docs) deal with origin trust/connection state and account addresses, not raw `WalletAccount` objects with `seedId`. It's plausible dapp-facing signing flows resolve to the string-key form (a stable wallet-account identifier tied to the connected/active account) rather than exposing a raw object with a `seedId` field to untrusted callers — but I was unable to conclusively locate that resolution code within the indexed content, so I cannot confirm whether an ordinary dapp/origin request can actually reach `signMessage` with a caller-constructed object containing an arbitrary `seedId`.

### Impact Explanation
If a caller (dapp/origin, or any code with reach to the `messageSigner` module) *can* supply a raw `WalletAccount` object rather than a string account key, the missing validation in `#normalizeWalletAccount` allows binding the signing operation to an arbitrary `seedId`/`index`/`isSoftware` combination not tied to the resolved account state (`walletAccountsAtom`). This would let a signature be produced against a different seed's key material than intended, which is a wrong-account/cross-wallet signing issue matching the "unauthorized signing"/"wrong-account access" bounty category — but only if that object is attacker-reachable and the attacker can supply/guess a valid `seedId` present in the local keychain (e.g. from a multi-seed wallet).

### Likelihood Explanation
This requires: (1) multiple seeds imported in the same keychain instance, (2) an attacker-reachable call path to `messageSigner.signMessage` that accepts a raw object (not resolved through `walletAccountsAtom`), and (3) the attacker knowing/guessing another seed's `seedId`. I could not verify precondition (2) — i.e., that any dapp-facing RPC surface actually exposes the raw `WalletAccount`-object form of the parameter to untrusted origins rather than only a string handle bound to the connected account. Without confirming that reachability, this is a code-level weak-validation observation rather than a demonstrated end-to-end exploit from an unprivileged dapp.

### Recommendation
Regardless of current reachability, `#normalizeWalletAccount` should validate object-form `walletAccount` inputs the same way as string inputs: resolve/cross-check against `walletAccountsAtom` (e.g., by `walletAccount.toString()` key) and reject if the resulting instance's `seedId`/fields don't match, rather than trusting caller-supplied objects verbatim. This closes the gap even if no current dapp-facing caller exploits it.

### Proof of Concept
Integration test (extends `features/message-signer/src/module/__tests__/index.test.ts` pattern):
1. Create a `walletAccountsAtom` with a legitimate account `exodus_0` bound to `seedId: 'seedA'`.
2. Construct two seeds (`seedA`, `seedB`) in one `Keychain` instance.
3. Call `messageSigner.signMessage({ walletAccount: { isSoftware: true, seedId: 'seedB', index: 0, source: 'seed' }, baseAssetName: 'ethereum', message })` — an object not registered in `walletAccountsAtom`.
4. Assert whether the signature/public key returned corresponds to `seedB`'s key material (bypassing whatever account was actually authorized/displayed to the user), i.e. `#normalizeWalletAccount` did not enforce that the object matches a known/authorized account.
5. Expected secure behavior: the call should be rejected or resolved strictly against `walletAccountsAtom`, not against caller-supplied `seedId` values.

Note: this PoC demonstrates the weak-validation code path only; it does not by itself establish that an untrusted dapp/origin can invoke `signMessage` with such an object, which I was unable to confirm from the indexed code.

  async signBuffer({ seedId, keyId, data, signatureType, enc, tweak, extraEntropy, ...rest }) {
    const noTweak = tweak === undefined
    const noEnc = enc === undefined
    const noOpts = noEnc && noTweak && extraEntropy === undefined
    const invalidOptions = Object.keys(rest).filter((key) => key !== 'ecOptions') // ignore legacy option `ecOptions`

    assert(invalidOptions.length === 0, `unsupported options supplied to signBuffer()`)
    assert(data instanceof Uint8Array, `expected "data" to be a Uint8Array, got: ${typeof data}`)
    assert(
      (['ecdsa', 'schnorr', 'schnorrZ'].includes(signatureType) && keyId.keyType === 'secp256k1') ||
        (signatureType === 'ed25519' && ['nacl', 'cardanoByron'].includes(keyId.keyType)),
      `"keyId.keyType" ${keyId.keyType} does not support "signatureType" ${signatureType}`
    )

    if (signatureType === 'ed25519') {
      assert(noOpts, 'unsupported options supplied for ed25519 signature')

      if (keyId.keyType === 'cardanoByron') {
        return this.cardanoEd25519.signBuffer({ seedId, keyId, data })
      }

      return this.ed25519.signBuffer({ seedId, keyId, data })
    }

    if (signatureType === 'schnorrZ') {
      assert(noOpts, 'unsupported options supplied for schnorrZ signature')
      return this.secp256k1.signSchnorrZ({ seedId, keyId, data })
    }

    // only accept 32 byte buffers for ecdsa
    assert(data.length === 32, `expected "data" to have 32 bytes, got: ${data.length}`)

    if (signatureType === 'schnorr') {
      assert(noEnc, 'unsupported options supplied for schnorr signature')
      return this.secp256k1.signSchnorr({ seedId, keyId, data, tweak, extraEntropy })
    }

    // signatureType === 'ecdsa'
    assert(noTweak, 'unsupported options supplied for ecdsa signature')
    return this.secp256k1.signBuffer({ seedId, keyId, data, enc, extraEntropy })
  }
