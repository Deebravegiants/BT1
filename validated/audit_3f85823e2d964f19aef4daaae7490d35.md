### Title
Webhook shop identity spoofing via HMAC/header binding mismatch - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC that `Registry.process` validates covers the JSON body alone. The `shop` field delivered to the app's handler is read straight from the unauthenticated `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header and is never included in the signed material.

### Finding Description
`Utils::HmacValidator.validate` computes and compares the signature only against `verifiable_query.to_signable_string`. For webhooks, `Request#to_signable_string` returns `@raw_body` exclusively: [1](#0-0) 
while `Request#shop` is derived purely from the header: [2](#0-1) 
`Registry.process` validates the HMAC and then hands `request.shop` straight into `WebhookMetadata` passed to the app's handler, with no cross-check that the header's shop domain is the shop the webhook subscription/HMAC actually corresponds to: [3](#0-2) 
This breaks the intended binding: `HMAC-verified-bytes == shop-attributed-to-webhook`. In reality, integrity is proven only for the body; the shop identity is an attacker-controlled header value that rides along unauthenticated. Because HMAC secrets are per-app (not per-shop), any body+HMAC pair that is valid for one shop under a given app remains a valid signature for that same body regardless of which shop-domain header accompanies it — the gem provides no mechanism to bind them together.
The gem's own docs promise the opposite: `Registry.process` "will verify the request did indeed come from Shopify" (`docs/usage/webhooks.md:125`), and document `data.shop` as trustworthy tenant identity (`docs/usage/webhooks.md:14`), which is what a host app relying on this gem's documented API would reasonably assume.

### Impact Explanation
If a host application uses `data.shop` from the handler to select a tenant record, apply per-shop authorization, or attribute writes/side effects (exactly as the gem's own documented example does — `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`, `docs/usage/webhooks.md:26`), an attacker who can obtain any one valid `(raw_body, hmac)` pair for the app (e.g., from their own installed shop, which requires no special privilege) can replay that request to the app's public webhook endpoint with the `x-shopify-shop-domain` header swapped to a victim shop. `Registry.process` will accept it as authentic and dispatch the payload under the victim shop's identity — a cross-tenant data/action confusion.

### Likelihood Explanation
Exploitation only requires: (1) installing the target app on any shop the attacker controls (any unprivileged merchant can do this to get an app that publishes webhook endpoints), (2) capturing one legitimate webhook body/HMAC pair sent to their own endpoint, and (3) POSTing it to the app's public webhook route with a forged shop-domain header. No access token, `client_secret`, or privileged account is needed — the gem never checks the header against anything.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the signable material used for HMAC verification for webhooks, or otherwise require `Registry.process`/the handler contract to cross-verify the header-derived shop against a value bound to the signed body (e.g., have callers pass the expected shop and compare it explicitly, or extend `to_signable_string` for webhook requests to incorporate the shop header before hashing).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (self-service, unprivileged).
2. Attacker triggers any subscribed webhook event (e.g., updates a product) and captures the raw POST to their own webhook endpoint, including `x-shopify-hmac-sha256` and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker replays the identical `raw_body` and `hmac` header to the app's public webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` succeeds (it only checks `raw_body` against the HMAC, per `lib/shopify_api/utils/hmac_validator.rb:26-31` and `lib/shopify_api/webhooks/request.rb:35-38`).
5. `Registry.process` builds `WebhookMetadata.new(... shop: request.shop ...)` with `shop == "victim-shop.myshopify.com"` and invokes the handler, which trusts this value per the gem's documented contract.
