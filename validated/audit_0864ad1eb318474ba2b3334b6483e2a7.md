### Title
Webhook shop identity is not covered by the HMAC, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw request body, then dispatches the handler using the `shop` value taken from the `X-Shopify-Shop-Domain` HTTP header — a value that is never included in the signed bytes. This breaks the intended binding `authenticated_bytes == acted_on_identity`: the HMAC proves the *body* came from Shopify using the app's `client_secret`, but it proves nothing about which shop the event is attributed to, since `shop` is read from an unsigned header.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) . The `shop` accessor, however, is derived independently from the `shop-domain` header, which is not part of the signed string: [2](#0-1) .

`Registry.process` validates the HMAC against `request` (i.e., against the body only) and, once that check passes, hands the handler `request.shop` — the unauthenticated header value — as the tenant identity for the event: [3](#0-2) . `Utils::HmacValidator.validate` confirms only that the computed HMAC of `to_signable_string` (the body) matches the received signature — it never inspects `shop`: [4](#0-3) .

Because the app's webhook `client_secret` is shared across every shop that has installed the app, an unprivileged attacker who controls their own shop installation can:
1. Install the app on their own store and receive/capture a real, validly-signed webhook (e.g. `orders/create`) — a legitimate byte-for-byte body with a correct `X-Shopify-Hmac-Sha256` header.
2. Replay that exact HTTP request to the app's webhook endpoint, but with the `X-Shopify-Shop-Domain` header rewritten to a victim shop's domain.
3. Since the HMAC only covers the body (unchanged), `HmacValidator.validate` still succeeds, and `Registry.process` calls the handler with `shop: <victim shop>`.

The equality the gem is supposed to enforce is: `shop attributed to event == shop that produced the authenticated bytes`. In fact the gem only proves `body received == body signed by app secret`; the `shop` value is orthogonal and attacker-controlled.

### Impact Explanation
This is a cross-tenant integrity break: a host application built on top of this gem, following its documented API (`Registry.process`), will process attacker-forged events *as if they came from a victim shop*, without any way to detect the forgery via the gem's own validation. Depending on the handler logic (common patterns: creating/deleting records keyed by `shop`, triggering GDPR/`shop/redact` or `app/uninstalled` cleanup, updating billing/entitlement state, etc.), this enables injecting or corrupting another tenant's data purely from an unprivileged, self-service app installation — no access token or leaked credential required, only what any developer installing the app in a test store already has.

### Likelihood Explanation
High. The attacker only needs to be a legitimate installer of the target app on their own store (a normal, unprivileged capability) to obtain one authentic signed webhook body/HMAC pair, and standard HTTP tooling to replay it with a modified header. No secret material, token, or elevated access is required.

### Recommendation
Include `shop` (and ideally `topic`, `api_version`, `webhook_id`) in the signed material used for verification, or independently verify that the header-derived `shop` matches an expectation the app controls (e.g., cross-check against the shop associated with the webhook subscription/registration, not trust the header blindly). At minimum, document that `request.shop` is unauthenticated and must not be used as a trust boundary by consuming applications — though since `Registry.process` itself performs the dispatch using this value, the fix belongs in the gem.

### Proof of Concept
```
# Attacker installs the app on attacker-shop.myshopify.com and captures a real webhook POST, e.g.:
POST /webhooks HTTP/1.1
X-Shopify-Topic: orders/create
X-Shopify-Hmac-Sha256: <valid-signature-for-body>
X-Shopify-Shop-Domain: attacker-shop.myshopify.com
X-Shopify-Webhook-Id: ...
X-Shopify-Api-Version: 2024-01
Content-Type: application/json

{"id":123, ...}

# Attacker replays the identical body/HMAC, only changing the shop header:
POST /webhooks HTTP/1.1
X-Shopify-Topic: orders/create
X-Shopify-Hmac-Sha256: <same-valid-signature, body unchanged>
X-Shopify-Shop-Domain: victim-shop.myshopify.com
X-Shopify-Webhook-Id: ...
X-Shopify-Api-Version: 2024-01
Content-Type: application/json

{"id":123, ...}

# ShopifyAPI::Webhooks::Registry.process(request) -> HmacValidator.validate(request) succeeds
# (only checks body), handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...))
# is invoked — the app now processes an attacker-controlled event attributed to the victim shop.
```

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
