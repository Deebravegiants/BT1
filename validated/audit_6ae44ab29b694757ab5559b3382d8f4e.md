### Title
Accrual overflows `i128` before the borrow-index cap and permanently freezes a market - (File: `common/src/rates/scaling.rs`) [1](#0-0) 

### Summary
Each accrual converts aggregate scaled debt and supply back to RAY values before calculating rates and applying the borrow-index cap. [2](#0-1)  The conversion calls `Ray::mul`, which delegates to `mul_div_half_up`. [1](#0-0) [3](#0-2)  `mul_div_half_up` panics with `MathOverflow` when the quotient cannot fit in `i128`. [4](#0-3) [5](#0-4) 

### Finding Description
An unprivileged caller can create an account supplying a very large amount of a high-decimal asset, create another account with sufficient collateral, borrow most of that liquidity, and repeatedly call `Controller::update_indexes(caller, [hub_asset])` as ledger time advances. [6](#0-5)  The pool’s `update_indexes` handler calls `ops::market::accrue`, which loads each market and invokes `interest::global_sync`. [7](#0-6) [8](#0-7) 

`global_sync` calls `accrue_step`, whose first operation is `scaled_to_original(borrowed, borrow_index)`. [9](#0-8) [10](#0-9)  Once `borrowed * borrow_index / RAY` exceeds `i128::MAX`, this conversion panics before `update_borrow_index` can apply its global index ceiling. [11](#0-10)  Because the failed accrual never commits `last_timestamp`, every later accrual retries the same overflowing interval. [12](#0-11) 

Every normal market leg uses `load_leg`, and `load_leg` always calls `synced_market`, which performs the same accrual before the operation-specific accounting. [13](#0-12) [14](#0-13)  Withdrawals, repayments, and borrows therefore all revert before reaching their business logic. [15](#0-14) [16](#0-15) [17](#0-16) 

### Impact Explanation
The result is permanent freezing of all supplier cash in the affected hub market and permanent inability to repay, liquidate, withdraw, update parameters, or accrue that market. [18](#0-17)  The market does not become temporarily fail-closed: the overflowing multiplication is evaluated before any state commit, so the stored timestamp and indexes remain on the same unreachable accrual boundary forever. [19](#0-18) 

This is not merely an unusually large index: the aggregate value ceiling is hit while `borrow_index` remains below `MAX_BORROW_INDEX_RAY`, so the existing cap cannot rescue the market. [11](#0-10)  The checked conversion correctly detects overflow, but converting a recoverable economic bound into a pre-commit panic creates the permanent freeze. [5](#0-4) 

### Likelihood Explanation
The attack requires an asset market whose scaled debt approaches `i128::MAX / borrow_index`, which implies an extremely large listed token supply or position and sustained high utilization. [2](#0-1)  No privileged role is required to create the positions or invoke `update_indexes`; the feasibility constraint is acquiring or minting enough ordinary market assets and collateral. [6](#0-5) 

The protocol itself documents the relevant domain as a valid market state: token upscaling and caps can admit approximately `i128::MAX`-scale RAY values, while the borrow-index ceiling is much higher than the index at which aggregate debt-value multiplication overflows. [20](#0-19)  A dedicated regression test demonstrates the freeze using a one-billion-whole-token, 18-decimal market and then confirms that both withdrawal and repayment return `MathOverflow`. [21](#0-20) [22](#0-21) 

### Recommendation
Cap index growth according to the market’s actual scaled totals, not only the global `MAX_BORROW_INDEX_RAY`. [11](#0-10)  Before applying an accrual step, compute the largest safe index such that both `borrowed * borrow_index / RAY` and `supplied * supply_index / RAY` fit `i128`, clamp to that value, and commit timestamp progress so later operations do not retry an impossible interval. [2](#0-1) 

Also reject supply or borrow mints that would create scaled totals with no safe headroom for subsequent index accrual. [23](#0-22)  The failure mode should leave the market at a saturated but representable index instead of making every mutator panic during mandatory accrual. [18](#0-17) 

### Proof of Concept
A single funded unprivileged caller can execute this sequence on one spoke:

```text
hub_asset = HubAssetKey { hub_id, asset: BIG18 }

// Account A: create the oversized liquidity market.
account_a = Controller::supply(
    caller,
    account_id = 0,
    spoke_id,
    [(hub_asset, 1_000_000_000 * 10^18)]
)

// Account B: provide enough $1 collateral to borrow at high utilization.
account_b = Controller::supply(
    caller,
    account_id = 0,
    spoke_id,
    [(collateral_asset, 3_000_000_000 * 10^7)]
)

Controller::borrow(
    caller,
    account_b,
    [(hub_asset, 980_000_000 * 10^18)],
    Some(caller)
)

// As ledger time advances, repeatedly accrue the market.
Controller::update_indexes(caller, [hub_asset])
```

The initial `1e27` BIG18 base units become `1e36` RAY-scaled supply shares because the 18-decimal asset is upscaled by `10^9`; the 98% borrow becomes approximately `0.98e36` debt shares. [24](#0-23) [25](#0-24)  When `borrow_index` is high enough that `borrowed * borrow_index / RAY > i128::MAX`, the next `update_indexes` call panics inside `scaled_to_original` before the borrow-index cap is applied. [2](#0-1) [11](#0-10) 

The existing regression test uses these market sizes, observes `MathOverflow` from `update_indexes`, and then confirms that even a one-unit withdrawal and a repayment both fail with the same error because they must accrue first. [26](#0-25) [27](#0-26)

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
