This confirms the mechanism, and this is actually the intended, reachable path: `sdk.createWithdrawalIntents` (`packages/intents-sdk/src/sdk.ts:334-372`) takes `args.feeEstimation` directly from the caller, calls `bridge.validateWithdrawal` with it, and then — using that *same* object — calls `bridge.createWithdrawalIntents`, which builds the final intent via `deriveOmniWithdrawIntentParams`.

### Title
Stale caller-supplied `feeEstimation.underlyingFees[OmniBridge].utxoMaxGasFee/utxoProtocolFee` bypasses UTXO min-amount check and is baked into the final `ft_withdraw` intent - (File: packages/intents-sdk/src/bridges/omni-bridge/omni-bridge.ts)

### Summary
`OmniBridge.validateWithdrawal`'s UTXO branch fetches a fresh `fee` (with `min_amount`) from `omniBridgeAPI.getFee` but validates `minAmount` against `utxoMaxGasFee`/`utxoProtocolFee` taken from the caller-supplied `args.feeEstimation`, not from the just-fetched `fee.gas_fee`/`fee.protocol_fee`. Because `createWithdrawalIntents` (both at the SDK level and inside `OmniBridge`) reuses the exact same `feeEstimation` object to build the final `ft_withdraw` amount and `msg.MaxGasFee` via `deriveOmniWithdrawIntentParams`, an attacker-supplied stale/low fee estimate can pass the min-amount check and be signed into the final intent unchanged.

### Finding Description
Equality that should hold: the `utxoMaxGasFee`/`utxoProtocolFee` used to validate `minAmount` (omni-bridge.ts:489-511) should equal the `utxoMaxGasFee`/`utxoProtocolFee` derived from the live `fee` response just fetched at omni-bridge.ts:460-472 (`fee.gas_fee`, `fee.protocol_fee`) for this exact destination/amount — not stale values baked into `args.feeEstimation` from an earlier call.

Trace:
- `OmniBridge.validateWithdrawal` (omni-bridge.ts:457-519) calls `this.omniBridgeAPI.getFee(...)` fresh, obtains `fee.min_amount`, `fee.gas_fee`, `fee.protocol_fee`, but only uses `fee.min_amount` for the comparison; `utxoMaxGasFee`/`utxoProtocolFee` are pulled via `getUnderlyingFee(args.feeEstimation, RouteEnum.OmniBridge, "utxoMaxGasFee"/"utxoProtocolFee")` (lines 489-498) — i.e., from the caller's input, not `fee.gas_fee`/`fee.protocol_fee`.
- `actualAmountWithFee = args.amount + utxoMaxGasFee + utxoProtocolFee` (lines 510-511) is checked against `minAmount = BigInt(fee.min_amount)`.
- The public entry point `IntentsSDK.createWithdrawalIntents` (sdk.ts:334-372) accepts `args.feeEstimation: FeeEstimation` directly from the caller (an ordinary SDK consumer/integrator forwarding data), calls `bridge.validateWithdrawal(...)` with it, and then immediately calls `bridge.createWithdrawalIntents(...)` with that same unmodified `feeEstimation`.
- `OmniBridge.createWithdrawalIntents` (omni-bridge.ts:283-330) forwards `args.feeEstimation` into `deriveOmniWithdrawIntentParams` (omni-withdraw-params.ts:92-116), which re-derives `utxoMaxGasFee`/`utxoProtocolFee` from that same `feeEstimation` to compute the final `amount` and `msg = {"MaxGasFee": ...}` written into the signed `ft_withdraw` intent.
- No code path re-fetches `getFee` or cross-checks `fee.gas_fee`/`fee.protocol_fee` against `feeEstimation`'s values before building the final intent. `assert(utxoMaxGasFee > 0n)` and `assert(utxoProtocolFee > 0n)` only guard against zero/undefined, not staleness/understatement.

Exploit flow: an integrator/caller obtains (or fabricates) a `FeeEstimation` object with `underlyingFees[OmniBridge].utxoMaxGasFee`/`utxoProtocolFee` set lower than the connector's true current requirement, and calls `sdk.createWithdrawalIntents` directly with `withdrawalParams` and that `feeEstimation` (skipping/independent of any prior `estimateWithdrawalFee` call — nothing enforces that `feeEstimation` passed to `createWithdrawalIntents` originated from a just-completed `estimateWithdrawalFee`). Because `minAmount` comes from the live `getFee` call but the fee added to `args.amount` comes from the stale, attacker-controlled `feeEstimation`, the min-amount check can pass with understated fees, and `deriveOmniWithdrawIntentParams` then signs an intent whose UTXO amount and `MaxGasFee` reflect that understated, stale fee rather than the freshly fetched connector fee.

### Impact Explanation
The final signed `ft_withdraw` intent's `amount` and `msg.MaxGasFee` (built via `createWithdrawIntentsPrimitive`/`deriveOmniWithdrawIntentParams`) can carry a fee lower than what the UTXO connector currently requires, even though `validateWithdrawal` just fetched the correct, current fee via `getFee`. This risks the withdrawal being stuck or failing at the connector (insufficient gas fee for the BTC/UTXO relayer to process it), matching "a withdrawal stuck until manual intervention" (High) rather than direct fund drain, since `deriveOmniWithdrawIntentParams`'s own `assert(utxoMaxGasFee > 0n)` guards remain satisfied and the amount is still added to the intent (no negative-amount drain). This is repeatable per call — any caller invoking `createWithdrawalIntents` directly with a stale `feeEstimation` triggers it every time.

### Likelihood Explanation
This requires the caller (an ordinary SDK consumer/integrator) to pass a `feeEstimation` to `createWithdrawalIntents` that is different from the one returned by a `estimateWithdrawalFee` call executed just prior for the same destination/amount — e.g., caching an old estimate and reusing it, or an integrator building its own `FeeEstimation`. The SDK's public API does allow `feeEstimation` to be supplied independently of `estimateWithdrawalFee` (sdk.ts:334-338 takes it as a plain argument), so this is reachable without any documented escape hatch. However, the "normal" recommended flow (calling `estimateWithdrawalFee` immediately before `createWithdrawalIntents`) is unaffected in practice since both calls compute fees within the same short window, making significant divergence timing-dependent (UTXO connector fee/`min_amount` volatility) rather than trivially exploitable by an attacker without control over their own fee-estimation inputs.

### Recommendation
In `OmniBridge.validateWithdrawal`, derive `utxoMaxGasFee`/`utxoProtocolFee` for the `actualAmountWithFee` comparison from the freshly-fetched `fee.gas_fee`/`fee.protocol_fee` (the same live response used for `minAmount`), and either (a) assert that `args.feeEstimation`'s `utxoMaxGasFee`/`utxoProtocolFee` equal these live values before proceeding to `createWithdrawalIntents`, or (b) have `createWithdrawalIntents`/`deriveOmniWithdrawIntentParams` re-fetch/re-validate fees rather than trusting a caller-supplied `feeEstimation` object across calls.
