### Title
Withdrawal status/hash misattribution for same-asset withdrawals — ([File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts])

### Summary
`PoaBridge.describeWithdrawal()` looks up the on-chain withdrawal result using `findMatchingWithdrawal`, which matches purely by `assetId` and ignores the withdrawal's `index`. When a single NEAR intent transaction contains more than one POA-bridge withdrawal of the *same* token (e.g. two BTC withdrawals to two different destination addresses in one batched intent), the SDK can report the destination tx hash of one withdrawal as the result of the other.

### Finding Description
`createWithdrawalIdentifiers` in [2](#0-1)  assigns a per-bridge, per-route `index` (0, 1, 2, …) to every withdrawal contained in a single intent transaction, so two POA-bridge withdrawals of `nep141:btc.omft.near` in one tx become index 0 and index 1, sharing the same `tx.hash`.

`PoaBridge.describeWithdrawal()` fetches the list of withdrawals for that tx hash and then resolves the *specific* withdrawal with: [3](#0-2) 

```
const withdrawal = findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId);
```

`findMatchingWithdrawal` only compares `assetId`: [4](#0-3) 

The code comment explicitly acknowledges the limitation ("multiple withdrawals of the same token in a single transaction are not supported"), but the function is still called unconditionally for every `WithdrawalIdentifier`, including when `index > 0`. Because the POA API's withdrawal list is "unsorted" (per the same comment), the first array element with a matching `assetId` is returned for *every* index that shares that asset — i.e. index 0's caller and index 1's caller can both receive the *same* `withdrawal.data.transfer_tx_hash`, which in reality only corresponds to one of the two actual on-chain transfers.

This breaks the equality that the reported destination-chain status/hash for a given `WithdrawalIdentifier` corresponds to the actual on-chain outcome of *that* specific withdrawal.

### Impact Explanation
This matches the "status or hash misreport" class explicitly called out as High impact: an integrator using `describeWithdrawal`/`waitForWithdrawalCompletion` (used by `sdk.processWithdrawal`/`waitForWithdrawalCompletion`, see [5](#0-4) ) for two same-asset POA withdrawals in one intent could:
- Mark the wrong withdrawal as "completed" with a tx hash that actually belongs to the sibling withdrawal, causing the integrator to release/credit funds for a withdrawal that has not actually landed yet, or
- Report the destination hash of a withdrawal to a different destination address than the one actually associated with that hash, potentially leading an integrator to credit/refund based on incorrect completion data (double credit risk) when both withdrawals eventually resolve and the mapping is inconsistent across polls (list ordering is described as "unsorted").

### Likelihood Explanation
This requires no malicious actor — it triggers whenever a normal user or integrator batches two or more POA-bridge withdrawals of the same NEP-141 asset (even to different destination addresses/amounts) into a single signed intent, which the SDK's public API (`createWithdrawalIntents`, `IntentPayloadBuilder.addIntents`) explicitly allows.

### Recommendation
Extend the POA bridge withdrawal-status API response matching to disambiguate by more than `assetId` — e.g., match on `(assetId, destinationAddress, amount)` combined, or maintain a stable ordering contract with the POA API and match by position, or track per-request correlation IDs if the API exposes one. At minimum, detect when multiple withdrawal params share the same `assetId` within one tx and throw/flag an explicit "not supported" error rather than silently returning an ambiguous result.

### Proof of Concept
1. Build an intent with two `ft_withdraw` primitives for `nep141:btc.omft.near`, to two different destination BTC addresses, in the same signed payload (via `IntentPayloadBuilder.addIntents`).
2. Broadcast the intent; both withdrawals settle in the same NEAR tx.
3. Call `sdk.processWithdrawal`/`bridge.describeWithdrawal` for index 0 and index 1: both calls hit `PoaBridge.describeWithdrawal`, and both resolve via `findMatchingWithdrawal(response.withdrawals, "nep141:btc.omft.near")`, which returns the same (first-matching) entry from the unsorted `withdrawals` array — regardless of which index/destination it was actually generated for.

type WithdrawalStatusResponse = Awaited<
	ReturnType<typeof poaBridge.httpClient.getWithdrawalStatus>
>;

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}
