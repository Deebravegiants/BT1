### Title
`EvmHost.dispatch()` forwards entire `msg.value` to Uniswap swap without refunding unused native token, permanently locking excess native sent by callers - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)` and `EvmHost.dispatch(DispatchGet)` accept native token payment and forward the caller's *entire* `msg.value` to `swapETHForExactTokens`, but the requested output amount is only `post.fee`/`get.fee`. Any unspent ETH returned by the swap is refunded to the swap caller — which is `EvmHost` itself, not the original dispatcher — and no code path afterward returns the excess to the original caller, resulting in native tokens becoming permanently stuck in the `EvmHost` contract.

### Finding Description
`EvmHost.dispatch(DispatchPost memory post)` performs: [1](#0-0) 

and `EvmHost.dispatch(DispatchGet memory get)` performs the identical pattern: [2](#0-1) 

In both functions, `swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)` is called with the caller's full `msg.value`, even though only `post.fee` (or `get.fee`) worth of fee-token output is required. Any dust/excess ETH the underlying router refunds during an *exact-output* swap (e.g., as seen in the project's own Uniswap wrapper implementations which explicitly refund unspent ETH back to `msg.sender` of the swap call — `UniV3UniswapV2Wrapper.sol` and `UniV4UniswapV2Wrapper.sol`) is refunded to `EvmHost` (the address that invoked the router), not to the original dispatcher/caller who supplied the native token: [3](#0-2) [4](#0-3) 

After the swap call, `dispatch()` proceeds directly to constructing/emitting the request with no logic to compute unspent ETH and return it to `_msgSender()`: [5](#0-4) 

This is the exact bug class from the reference report — a `payable` function that sends `msg.value` on to a downstream fee-paying call without refunding the difference to the caller, leaving native currency stuck in the intermediate contract.

Notably, the codebase demonstrates that the project is aware of this exact pitfall and correctly handles it elsewhere: `IntentGatewayV2`/`ExtrinsicIntents.sol` explicitly tracks `msgValue`, computes leftovers after any Uniswap swap, and refunds unspent native to `msg.sender` at the end of `placeOrder`/`fillOrder`: [6](#0-5) [7](#0-6) 

However, `EvmHost.dispatch(DispatchPost)` and `EvmHost.dispatch(DispatchGet)` — the core, most widely used entry points for any application dispatching cross-chain POST/GET requests with native payment — lack this refund logic entirely.

### Impact Explanation
Any unprivileged caller (an `IHyperApp`, or an EOA calling through a wrapper like `WrappedHyperFungibleToken.send()`) dispatching a POST or GET request with native token payment and sending more `msg.value` than strictly required for the exact-output swap will have the excess permanently locked inside `EvmHost`, with no withdrawal mechanism visible to return it to the original payer. Because fee estimation off-chain via Uniswap's `getAmountsIn`/`quote()` is explicitly warned to be imprecise (subject to sandwich attacks and price movement) per the project's own documentation, users are effectively encouraged to overpay as a safety margin — directly maximizing exposure to this fund-loss bug. Every native-token dispatch across the protocol (`IDispatcher.dispatch()`, `fundRequest()`, and any `HyperApp`/token-bridge integration using native payment) is affected, representing a systemic path to permanent freezing of user/keeper funds.

### Likelihood Explanation
Likelihood is high: this occurs on every native-token dispatch where the actual `msg.value` supplied exceeds the exact fee required by the swap — a routine occurrence given documented guidance to estimate fees off-chain (subject to slippage/sandwiching) and given that `dispatch()`/`fundRequest()` are the primary entry points recommended in the docs for native-token payments (`docs/content/developers/evm/messaging/post-requests.mdx`, `get-requests.mdx`). No malicious actor or special conditions are required — normal use with any overestimate of the fee triggers permanent loss.

### Recommendation
Mirror the pattern already used correctly in `IntentGatewayV2`'s `ExtrinsicIntents`/`IntrinsicIntents`: track the amount actually spent by the swap (e.g., via `swapETHForExactTokens`'s returned `amounts[0]`, or by snapshotting `address(this).balance` before/after the swap), and refund any leftover native token to `_msgSender()` at the end of `dispatch(DispatchPost)` and `dispatch(DispatchGet)` (and similarly in `fundRequest()` if it follows the same pattern), following checks-effects-interactions.

### Proof of Concept
1. Caller invokes `EvmHost.dispatch{value: 1 ether}(post)` where `post.fee` only requires `0.1 ether` worth of native token to obtain via `swapETHForExactTokens`.
2. `dispatch()` forwards the full `1 ether` as `value` to `swapETHForExactTokens(post.fee, path, address(this), block.timestamp)`.
3. The Uniswap router/wrapper spends only what's needed and refunds the unspent ~`0.9 ether` back to `msg.sender` of the swap call — which is `EvmHost`, not the original caller.
4. `dispatch()` continues execution and returns, with the ~`0.9 ether` now held as `EvmHost`'s balance and no code path to return it to the original caller.
5. This can be repeated by any caller sending excess `msg.value` on `dispatch()`, accumulating stuck native token in `EvmHost` indefinitely, with no observed `withdraw`/`receive` sweep mechanism benefiting the affected users. [1](#0-0)
