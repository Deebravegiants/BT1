### Title
Webhook `shop-domain` header is not covered by HMAC verification, breaking the tenant-binding invariant `hmac(shop-domain) == verified(shop-domain)` - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so `ShopifyAPI::Utils::HmacValidator.validate` only proves that the *body bytes* were signed by Shopify with `api_secret_key`. The `shop` value, taken from the `X-Shopify-Shop-Domain` header via `shopify_header("shop-domain")`, is never included in the signed material, so it is not bound to the HMAC at all.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes an HMAC over `request.to_signable_string` (the raw JSON body) and compares it to the `hmac-sha256` header value. [3](#0-2) 
`request.shop`, however, is read straight from the `shop-domain` header without any cryptographic binding to that HMAC: [1](#0-0) 
This breaks the identity-binding equality that should hold: `hmac_covers(shop) == true`. In this gem, `hmac_covers(shop) == false` — the bytes that are HMAC-verified (the body) are not the bytes that are trusted as the tenant identifier (the `shop-domain` header). The value returned by `WebhookMetadata` (and passed to the app's registered handler) as `shop` therefore comes from an attacker-controllable, unauthenticated header rather than from any value inside the HMAC-covered payload. [4](#0-3) 

### Impact Explanation
Any host application that trusts `WebhookMetadata#shop` (as returned by `Registry.process`) to select which merchant's data/session/token to act on is vulnerable to cross-tenant confusion: an attacker who can produce any valid Shopify webhook (e.g., from their own installed/free test shop) can replay that webhook's body+HMAC while substituting an arbitrary `X-Shopify-Shop-Domain` header value, since that header is not part of the signed content. Because Shopify's genuine HMAC only certifies the body, this gem hands the host application a `shop` value with no cryptographic guarantee, enabling cross-tenant webhook processing (Critical impact class: cross-tenant access) if the host uses `data.shop` to load per-shop sessions/tokens as intended by the documented usage pattern. [5](#0-4) 

### Likelihood Explanation
Likelihood is moderate-to-high: it requires the attacker to control at least one legitimate webhook delivery (trivial — install a free/dev app on their own store to receive genuine signed webhooks), then replay the exact same raw body/HMAC pair while forging the `shop-domain` header, which this gem never validates against the signed payload. No secrets are required.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `api-version`, `webhook-id`) header values in the HMAC-signed material verification path, or otherwise cryptographically bind them — e.g., by having `to_signable_string` incorporate the shop domain, or by validating that the recomputed HMAC is unique to a `(body, shop)` pair rather than `body` alone.

### Proof of Concept
1. Attacker installs a test/dev app on their own `attacker.myshopify.com` store and receives a genuine Shopify webhook: raw body `B`, header `X-Shopify-Hmac-Sha256: H` (valid HMAC of `B` under the real `api_secret_key`), and `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Attacker sends a forged HTTP request to the victim app's webhook endpoint with the same body `B` and same `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers and computes `hmac` from the `hmac-sha256` header and `shop` from the `shop-domain` header. [6](#0-5) 
4. `Utils::HmacValidator.validate(request)` recomputes the HMAC over `to_signable_string` (`B` only) — it matches `H`, since `shop-domain` was never part of the signed data. [2](#0-1) 
5. `Registry.process` passes validation and invokes the app's handler with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", ...)`, even though the request never involved the victim shop. [7](#0-6)

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
