### Title
Webhook shop-domain/topic spoofing via HMAC that only covers the body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then forwards `shop`, `topic`, `webhook_id`, and `api_version` — all read from unauthenticated HTTP headers — to the host application's handler as if they were verified, trusted identifiers.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` calls `verifiable_query.to_signable_string` to compute the expected signature. For webhooks, `Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
None of `shop`, `topic`, `webhook_id`, or `api_version` — all read directly from HTTP headers (`shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`, `shopify-api-version`) — are included in the signed content: [2](#0-1) 

`Registry.process` validates only the HMAC (over the body) and then constructs `WebhookMetadata` directly from these unauthenticated header values, passing them to the app's handler as trusted, verified context: [3](#0-2) [4](#0-3) 

The identity binding that is broken: `hmac == HMAC(secret, signed_content)` should equal `hmac == HMAC(secret, signed_content_that_includes_shop_and_topic)`. Because `shop` and `topic` are excluded from `signed_content`, any request with a *previously observed, genuinely-signed body+hmac pair* (e.g. from the attacker's own store, which any unprivileged internet user can obtain by installing an app or subscribing a webhook on a store they control) can be replayed to a target app's webhook endpoint with the `shop-domain` header rewritten to name an arbitrary victim shop, and `topic` rewritten to any topic supported by a body-compatible payload. `Utils::HmacValidator.validate` still returns `true` because it only checks the body, and `Registry.process` dispatches the forged `shop`/`topic` to the handler unchanged.

### Impact Explanation
Host applications built on this gem are documented to trust `WebhookMetadata#shop` as the authenticated tenant identity for the event (e.g. to look up sessions/access tokens per shop, update per-shop records, or trigger uninstall/GDPR flows) since it comes from a "verified" webhook. Because the gem lets an attacker forge this field while still passing HMAC validation, an attacker can make the host application process attacker-controlled webhook bodies under an arbitrary victim shop's identity — a cross-tenant confused-deputy condition (e.g. forging `app/uninstalled` or order/customer events attributed to a shop the attacker does not own).

### Likelihood Explanation
Exploitation requires only: (1) the attacker's own genuinely-signed webhook body+HMAC pair, obtainable by any unprivileged user who installs any Shopify app or configures a webhook subscription on a store they control (no `api_secret_key` or privileged access needed), and (2) the ability to POST an HTTP request with attacker-chosen headers to the target app's public webhook endpoint, which by design is internet-reachable. No credentials of the target app or victim shop are required.

### Recommendation
Include the identity-bearing headers (`shop`, `topic`, `webhook_id`, `api_version`) in the HMAC-signed content used by `Webhooks::Request#to_signable_string`, or otherwise bind them cryptographically to the payload before trusting them in `Registry.process`/`WebhookMetadata`. At minimum, document that host applications must independently verify `data.shop` against their own known/installed-shop list rather than treating it as authenticated by the gem's HMAC check.

### Proof of Concept
1. Attacker installs a test app / configures a webhook on their own store `attacker-shop.myshopify.com`; Shopify sends a legitimately HMAC-signed webhook, e.g.:
```
POST /webhooks
x-shopify-topic: orders/create
x-shopify-hmac-sha256: <valid HMAC over BODY>
x-shopify-shop-domain: attacker-shop.myshopify.com
Body: BODY
```
2. Attacker captures `BODY` and the valid `x-shopify-hmac-sha256` value.
3. Attacker replays the exact same request to the same (or a different) app's webhook endpoint but changes only the header:
```
x-shopify-shop-domain: victim-shop.myshopify.com
```
4. `Utils::HmacValidator.validate(request)` still returns `true` because `to_signable_string` only returns `BODY`, unaffected by the header change.
5. `Registry.process` invokes the app's handler with `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: <attacker's BODY>, ...)`, causing the host app to treat attacker-controlled data as an authenticated event from `victim-shop.myshopify.com`.
