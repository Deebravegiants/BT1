### Title
POA Bridge withdrawal status is matched by `assetId` only, causing wrong destination tx hash to be reported when a batch withdrawal contains multiple withdrawals of the same token - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
The SDK's `IntentsSDK.processWithdrawal` / `waitForWithdrawalCompletion` / `createWithdrawalCompletionPromises` support batching multiple withdrawals into a single NEAR intent, including multiple withdrawals of the same asset to different destination addresses. For POA-bridge-routed withdrawals, the completion status for each withdrawal in the batch is looked up via `findMatchingWithdrawal`, which matches purely by `assetId` (`nep141:${near_token_id}`), not by index, amount, or destination address.

### Finding Description
`PoaBridge.describeWithdrawal` calls `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`: [1](#0-0) 

and `findMatchingWithdrawal` itself only compares `assetId`: [2](#0-1) 

The function's own docstring acknowledges the root cause: "Currently only matches by assetId. This means multiple withdrawals of the same token in a single transaction are not supported." The identical, unguarded matching logic exists a second time in `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts`: [3](#0-2) 

Meanwhile, the SDK's public batching APIs explicitly support multiple withdrawal entries per intent, keyed by index rather than de-duplicated by asset, and iterate per-`index` calling `describeWithdrawal` independently for each withdrawal in the batch: [4](#0-3) 

There is no validation anywhere in `IntentsSDK.createWithdrawalIntents` / `processWithdrawal` that rejects a batch containing two POA-bridge withdrawals of the same `assetId` (e.g., two withdrawals of `nep141:usdt.tether-token.near` to two different destination addresses). Because `findMatchingWithdrawal` ignores index/amount/address and returns the *first* array element whose `near_token_id` matches, when the POA API returns two completed withdrawal records for the same token (belonging to withdrawal #1 and withdrawal #2 of the batch, potentially with different `transfer_tx_hash` and `address`), both `describeWithdrawal({index:0,...})` and `describeWithdrawal({index:1,...})` calls will resolve to the *same* matched record — reporting the same `txHash` (and implicitly the same completion status) for both withdrawals regardless of which one it actually corresponds to.

### Impact Explanation
This breaks the equality "status/hash reported == actual on-chain outcome for that specific withdrawal." An integrator using `waitForWithdrawalCompletion`/`createWithdrawalCompletionPromises`/`processWithdrawal` on a batch containing two same-asset withdrawals with different destination addresses could:
- Report `withdrawal[1]`'s destination tx hash for `withdrawal[0]` (and vice-versa), i.e. attribute the wrong on-chain settlement to the wrong request.
- Mark a withdrawal as "completed" using another withdrawal's hash while the actual withdrawal to the intended address is still pending or failed, causing an integrator to credit/release funds or mark a leg "done" prematurely based on a hash that doesn't correspond to that request.

This matches the "a status or hash misreport making an integrator credit or refund twice" category under High impact, since a service relying on this SDK to confirm delivery to a specific address per withdrawal record could act on incorrect confirmation.

### Likelihood Explanation
Likelihood is limited by: (1) needing a batch withdrawal with two entries of the identical `assetId` value routed through the POA bridge, (2) both withdrawals completing around the same polling window so the API returns both records simultaneously. This is a plausible, entirely unprivileged legitimate use case (e.g., splitting one token to two recipients in one intent) rather than requiring any malicious actor — this is explicitly acknowledged as a known limitation in the code comments, indicating it is a real, reachable gap rather than a purely theoretical one.

### Recommendation
- Disambiguate `findMatchingWithdrawal` beyond `assetId`: match on `(assetId, amount, destinationAddress)` tuple, or use ordering/index-stable identifiers if the POA API can supply them, per the sorting-by-amount approach suggested in the existing code comment.
- Until the API supports better matching, add an explicit guard in `IntentsSDK.createWithdrawalIntents`/`validateWithdrawal` that rejects (or requires disambiguating metadata for) batches containing more than one POA-bridge withdrawal with the same `assetId`, to fail closed rather than silently misreport.

### Proof of Concept
1. Caller builds a batch withdrawal via `sdk.processWithdrawal({ withdrawalParams: [ {assetId: "nep141:btc.omft.near", amount: 100000n, destinationAddress: "addrA"}, {assetId: "nep141:btc.omft.near", amount: 200000n, destinationAddress: "addrB"} ] })`, both routed through POA bridge.
2. Both withdrawals complete on-chain, and POA API's `getWithdrawalStatus` returns two `COMPLETED` records for `near_token_id: "btc.omft.near"`, one with `transfer_tx_hash: "tx-for-addrA"` and one with `transfer_tx_hash: "tx-for-addrB"`.
3. `waitForWithdrawalCompletion` internally calls `describeWithdrawal` once per index; `findMatchingWithdrawal(response.withdrawals, "nep141:btc.omft.near")` (poa-bridge.ts lines 418-427) returns the *same first matching record* for both index 0 and index 1 calls, so both entries are reported with the same `txHash`, mismatching the actual per-request outcome as demonstrated by the unit test `matches withdrawal by assetId, not by index` at [5](#0-4)  (which only verifies matching across *different* assets, not the same-asset collision case that remains unhandled).

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

	withdrawals: types.WithdrawalStatusResponseOk["result"]["withdrawals"],

	public createWithdrawalCompletionPromises(
		params: CreateWithdrawalCompletionPromisesParams,
	): Array<Promise<TxInfo | TxNoInfo>> {
		const { withdrawalParams, intentTx, signal, logger } = params;

		const widsPromise = createWithdrawalIdentifiers({
			bridges: this.bridges,
			withdrawalParams,
			intentTx,
		});

		// Track the last promise per HOT bridge landing chain for sequential waiting.
		// HOT bridge processes withdrawals sequentially per chain with ~30s gaps,
		// so polling in parallel would cause later withdrawals to timeout.
		const hotChainLastPromise = new Map<Chain, Promise<TxInfo | TxNoInfo>>();

		return withdrawalParams.map(async (_, index) => {
			const wids = await widsPromise;
			const entry = wids[index];
			assert(entry != null, `Missing wid for index ${index}`);

			// Only apply sequential waiting for HOT bridge
			if (entry.bridge.route === RouteEnum.HotBridge) {
				const landingChain = entry.wid.landingChain;
				const previousPromise = hotChainLastPromise.get(landingChain);

				const sequentialPromise = (async () => {
					if (previousPromise) {
						// Wait for previous withdrawal to same chain to complete.
						// Use allSettled to continue even if previous fails.
						await Promise.allSettled([previousPromise]);
					}
					return watchWithdrawal({
						bridge: entry.bridge,
						wid: entry.wid,
						signal,
						logger,
					});
				})();

				hotChainLastPromise.set(landingChain, sequentialPromise);
				return sequentialPromise;
			}

			// Non-HOT bridges: parallel polling (existing behavior)
			return watchWithdrawal({
				bridge: entry.bridge,
				wid: entry.wid,
				signal,
				logger,
			});
		});
