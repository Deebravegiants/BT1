### Title
Missing Chainlink `minAnswer`/`maxAnswer` deviation check lets a clamped price feed mis-price gas costs in `SimplexPaymaster` - (File: `evm/src/utils/SimplexPaymaster.sol`)

### Summary
`SimplexPaymaster._getOraclePrice` only validates that a Chainlink answer is positive and not stale; it never checks the reported answer against the feed's configured `minAnswer`/`maxAnswer` boundaries. This is exactly the bug class from the referenced report: during a de-peg or crash, Chainlink continues to report the clamped min/max value instead of the true market price, and any contract that trusts that value without a sanity/deviation check will use an incorrect price.

### Finding Description
`_getOraclePrice` is the sole gate on every Chainlink read used for pricing in this contract: [1](#0-0) 

It reverts only on `answer <= 0` or staleness (`block.timestamp - updatedAt > maxOracleAge`). There is no check that `answer` differs from the aggregator's registered `minAnswer`/`maxAnswer`, and no cross-check against a second price source or TWAP, unlike the recommendation in the referenced report.

This function feeds `_tokenPrice`, which is called from `_fetchDetails` — the function `PaymasterERC20` invokes during `_validatePaymasterUserOp` for **every** ERC-4337 `UserOperation` that uses this paymaster: [2](#0-1) [3](#0-2) 

`_validatePaymasterUserOp`/`_fetchDetails` is reachable by any unprivileged bandwidth purchaser: anyone can submit a `PackedUserOperation` naming any registered token, and the paymaster computes `tokenPrice = (nativeUsd * 10^tokenDecimals * (10000+markup)) / (tokenUsd * 10000)` straight from the two raw oracle reads, with no bound on how far `nativeUsd`/`tokenUsd` are allowed to be pinned at a stale floor/ceiling.

The same unchecked price also drives `swapAndDeposit`'s `amountOutMin` computation via `_getOraclePrice`: [4](#0-3) 

### Impact Explanation
If a registered stablecoin (or the chain's native asset) collapses in price and its Chainlink feed clamps to `minAnswer` (a floor well above the real market price), `_getOraclePrice` will happily return that stale floor as long as it's within the heartbeat window. In `_tokenPrice`:
- An inflated `tokenUsd` (stablecoin pinned above its real depegged value) lowers the token amount charged per unit of gas, so `UserOperation` senders systematically underpay the paymaster in real USD terms, draining the paymaster's EntryPoint deposit / treasury value over time.
- Conversely, if `nativeOracle` clamps to a floor/ceiling during a native-asset crash, users are overcharged relative to the true gas cost.

Either direction is a direct mispricing of value transferred through an unprivileged, permissionless path (any UserOp sender), matching the report's "incorrect price passes" impact — financial loss to the protocol/treasury or overcharging of unprivileged users, without any code change or governance action required to trigger it (only a real-world oracle clamp event).

### Likelihood Explanation
This requires the underlying asset to actually breach its Chainlink `minAnswer`/`maxAnswer` bound (a known, previously-observed real-world event, e.g. LUNA/UST). It does not require an attacker to control the oracle, only to submit ordinary `UserOperation`s (or wait for others to) while the feed is clamped — a plausible, market-driven trigger rather than a contrived scenario, consistent with the Medium severity of the original finding.

### Recommendation
In `_getOraclePrice`, fetch and cache each aggregator's `minAnswer`/`maxAnswer` (via `AggregatorV2V3Interface`/`aggregator()` on the proxy) and revert if the returned `answer` is at or outside those bounds, or add a secondary/TWAP price check and revert on excessive deviation, mirroring the recommendation in the referenced report.

### Proof of Concept
1. Governance registers a stablecoin `USDX` with a Chainlink feed whose configured `minAnswer` is `0.90e8`.
2. `USDX` depegs to `$0.10` in the real market; the aggregator keeps reporting `0.90e8` (clamped) with a fresh `updatedAt`.
3. Any user submits a `UserOperation` with `paymasterData` mode `0x00`/`0x02` naming `USDX`. `_fetchDetails` calls `_tokenPrice` → `_getOraclePrice(cfg.tokenOracle, ...)`, which returns `0.90e8` — passing the staleness/positivity checks with no bound check.
4. `tokenPrice` is computed using the inflated `$0.90` instead of the real `$0.10`, so the paymaster charges roughly 9x too few `USDX` tokens for the sponsored gas, silently draining the paymaster's EntryPoint deposit relative to the real value it collects.

    /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
