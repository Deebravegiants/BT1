### Title
Cross-Chain Decimal-Scaling Truncation in `pallet-hyper-fungible-token` Can Zero Out Received/Refunded Token Amounts - ([File: modules/pallets/hyper-fungible-token/src/impls.rs])

### Summary
`pallet-hyper-fungible-token` converts ERC20-denominated amounts to the local (Substrate) balance type via `convert_to_balance`, which unconditionally divides by `10^(erc_decimals - local_decimals)` with no floor/zero check. Because `register_token`/`update_token` only enforce `erc_decimals >= local_decimals`, any bridged token pair with a nonzero decimal gap allows a caller-controlled dust amount sent from the EVM side to be silently truncated to zero on `on_accept` (mint/transfer credit) and on `on_timeout` (refund), while the corresponding ERC20 tokens have already been irrecoverably burned/locked on the EVM contract. This mirrors the reported ZNSCurvePricer class of bug: a division that truncates to zero because of an admin-set-but-user-triggerable decimal/precision mismatch, with no guard against a zero-value result.

### Finding Description
`convert_to_balance` performs the down-scaling division with no zero check: [1](#0-0) 

`register_token`/`update_token` validate only that `erc_decimals >= local_decimals` (`ErcDecimalsBelowLocal`), which is the direction needed for `convert_to_erc20` (scale-up, lossless) but does nothing to bound how small an EVM-side amount can be before `convert_to_balance` (scale-down) rounds it to zero: [2](#0-1) 

The vulnerable division is invoked in two unprivileged, message-driven paths:
1. `on_accept` — an inbound `Send` from the peer EVM contract mints/transfers `convert_to_balance(message.amount, erc_decimals, decimals)` to the beneficiary with no check that `amount > 0`: [3](#0-2) 
2. `on_timeout` — the refund path applies the identical conversion and mint/transfer, again with no zero guard: [4](#0-3) 

Concretely: if a token is registered with, say, `erc_decimals = 18` and `local_decimals = 6` (a valid, non-malicious configuration satisfying `ErcDecimalsBelowLocal`), any EVM-side amount below `10^12` wei (i.e. any amount ≤ 0.000000999999 of a whole token) truncates to `0` local balance units on delivery. The EVM contract has already burned/locked the sender's tokens before dispatch; the destination-chain leg silently mints/transfers `0`, permanently losing the bridged value with no revert, in contrast to `BandwidthManager.sol`, which explicitly reverts with `PriceNotRepresentable()` rather than silently under-charging in the analogous decimal-scaling scenario: [5](#0-4) 

### Impact Explanation
Any unprivileged user who dispatches a `Send`/teleport from the EVM-side `HyperFungibleToken`/`BridgeToken` contract with a sufficiently small amount relative to the registered decimal gap has their tokens burned/escrowed on the source chain while the pallet mints/credits/refunds zero on the destination (or on timeout-refund) side. This is a permanent, protocol-level loss of user funds triggered by a single ordinary token-bridge transaction — no governance or admin action is required beyond the normal (and expected) act of registering a token pair with differing decimals, which the codebase's own validation (`ErcDecimalsBelowLocal`) shows is an anticipated configuration, not a misconfiguration.

### Likelihood Explanation
Likelihood is high for any token pair with a decimal gap (e.g., 18-decimal EVM token bridged against a 6- or 10-decimal Substrate asset, which is common) — a user only needs to send a dust amount, whether by mistake, by a wallet/dApp rounding bug, or by an attacker deliberately griefing the sender/beneficiary or accumulating this behavior programmatically. The `BandwidthManager.sol`/`BandwidthPurchase` bandwidth-purchase flow in the same repository already demonstrates the project's awareness of, and standard fix for, this exact class of bug (explicit revert on non-representable amounts), underscoring that its absence here is an oversight rather than a deliberate design choice.

### Recommendation
In `convert_to_balance`, reject (return an error) rather than silently truncate when the division would yield zero for a nonzero input, e.g. mirror `BandwidthManager`'s pattern: require `value % 10^(erc_decimals-local_decimals) == 0` or explicitly check `result == 0 && value != 0` and error out (`InvalidAmountConversion`) in both `on_accept` and `on_timeout`. Alternatively/additionally, enforce a protocol-level minimum transferable amount on the EVM-side `send()` given the registered `Precisions` gap so dust amounts are rejected before tokens are burned/escrowed.

### Proof of Concept
1. Governance registers a token via `register_token` with `local_decimals = 6` and an EVM chain config of `decimals = 18` (passes the `ErcDecimalsBelowLocal` check since `18 >= 6`). [2](#0-1) 
2. A user calls `send()`/the EVM `HyperFungibleToken` contract's send path with `amount = 999_999_999_999` wei (i.e., `< 10^12`, the scale factor `10^(18-6)`), which burns/locks that amount on the EVM contract and dispatches a `Message` carrying it.
3. On delivery, `on_accept` computes `convert_to_balance(999_999_999_999, 18, 6)` = `999_999_999_999 / 10^12` = `0` (integer division), and mints/transfers `0` to the beneficiary with no revert: [6](#0-5) [7](#0-6) 
4. Result: the sender's EVM-side tokens are gone, the beneficiary receives nothing, and the pallet emits `TokenReceived { amount: 0, ... }` as if the transfer succeeded normally — an unrecoverable loss of funds. The identical issue reproduces via `on_timeout`'s refund path if the corresponding original dispatch amount likewise falls below the scale factor.

/// Converts an ERC20 U256 amount to a local balance type
///
/// Divides by 10^(erc_decimals - local_decimals) to scale down from ERC20 precision.
/// The target type must implement `FromStr`.
pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}
