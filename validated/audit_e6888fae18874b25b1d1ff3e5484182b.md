### Title
Webhook `shop-domain` identity is trusted without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then hands the caller-supplied `shop-domain` header straight through to the app's handler as the authenticated tenant identifier. The HMAC never covers that header, so the "verified" bytes and the "trusted" tenant field are not the same data.

### Finding Description
`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and compares it to the `hmac` field [1](#0-0) . For webhooks, `to_signable_string` returns only `@raw_body`, and `hmac` is read from the `x-shopify-hmac-sha256`/`shopify-hmac-sha256` header [2](#0-1) . The `shop` accessor, however, is read from the `x-shopify-shop-domain`/`shopify-shop-domain` header, which is never included in the signed material [3](#0-2) .

`Registry.process` validates only the HMAC and then trusts `request.shop` as the tenant identity that gets forwarded to the app's webhook handler in `WebhookMetadata`: [4](#0-3) [5](#0-4) 

The identity binding the gem implicitly claims to provide is: `shop header == HMAC-authenticated field`. In reality the equality that holds is only `raw_body == HMAC-authenticated field`; the `shop` header is disjoint from what is verified. Because a single app's `client_secret` (the webhook signing secret) is shared across every shop that installs the app, an attacker who controls one shop that has the app installed can receive a legitimately-signed webhook (valid HMAC over some body they chose to trigger, e.g. by editing a product in their own store) and then replay that exact body + HMAC to the app's webhook endpoint with the `x-shopify-shop-domain` header rewritten to a victim shop's domain. `HmacValidator.validate` will still pass, because it only checks the body bytes, and `Registry.process` will invoke the app's handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain.

This is structurally the same class of bug as the referenced btcd fix: a boundary check (there, an index bound; here, an identity/authentication boundary) is performed against the wrong data — the code verifies one thing (raw body bytes) but acts on/trusts another (the `shop` header) without tying the two together.

### Impact Explanation
Any app built on this gem whose webhook handler branches on `data.shop` (e.g., to look up per-shop state, apply the payload to the addressed tenant's records, or make trust decisions) is exposed to cross-tenant data injection: an attacker with a real (even free/trial) install of the app can forge webhook events that the app will process as if they originated from a different, arbitrary merchant shop. This matches the "cross-tenant access" Critical impact category, since the attacker crosses a tenant identity boundary using only their own legitimate app installation — no access token, leaked credential, or privileged account is required.

### Likelihood Explanation
Likelihood is high for any app that has at least one active (even free-tier) install: the attacker needs no special access — they can trigger arbitrary webhook bodies for their own shop, capture the resulting HMAC-signed payload, and replay it with a modified `shop-domain` header directly to the app's public webhook endpoint. This requires no secrets beyond what any merchant installer already legitimately possesses.

### Recommendation
Bind the shop identity into the material that is cryptographically verified, or otherwise cross-check it: either include the `shop-domain` header in the HMAC-signed payload passed to `HmacValidator`/`to_signable_string`, or require callers to resolve/validate `request.shop` against a known/expected shop (e.g., a shop associated with a stored, verified session or webhook subscription id) before trusting it in `WebhookMetadata`. At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must not be used as a trust boundary by consuming applications.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a legitimate install, e.g. free plan).
2. Attacker triggers an event that causes Shopify to send a webhook to the app, e.g. `products/update`, with body `B`. Shopify computes `HMAC = HMAC-SHA256(client_secret, B)` and sends headers `x-shopify-hmac-sha256: HMAC`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: products/update`.
3. Attacker intercepts/replays this exact request to the app's webhook endpoint but changes only the `x-shopify-shop-domain` header to `victim-shop.myshopify.com`, keeping body `B` and `HMAC` unchanged.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `raw_body` (`B`) only [1](#0-0)  — validation succeeds because the body wasn't modified.
5. The handler is invoked with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)` [6](#0-5) , causing the app to process attacker-controlled data as if it belongs to the victim shop.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

        end
