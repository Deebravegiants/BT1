### Title
Escrow/dust/fee payouts use unchecked low-level `.call` for ERC20 transfers, silently accepting failed transfers as success - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` pays out escrowed tokens, protocol fees, and swept dust using a raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` and only checks the low-level `success` flag of the call, never validating the ERC20 `transfer` return value (the ABI-decoded boolean).

### Finding Description
In `withdraw()` and in the `SweepDust` branch of `onAccept()`, token payouts are performed like this: [1](#0-0) 

```
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
```

`success` here only reflects whether the external call reverted, not whether the token actually transferred the funds. Non-standard ERC20 tokens that return `false` on failure instead of reverting (a well-known deviation covered by the exact bug class in the external report) will make this call return `success = true` with return data encoding `false`. Because the code never decodes/validates that returned boolean, it proceeds as if the transfer succeeded:

- `_orders[body.commitment][token] -= amount;` is decremented and `_orders[body.commitment][TRANSACTION_FEES]` is deleted, permanently erasing the escrow accounting for those funds [2](#0-1) 
- `EscrowReleased`/`EscrowRefunded`/`DustSwept` events are emitted, and `_filled[body.commitment] = beneficiary` is recorded, signalling to relayers/indexers/users that the beneficiary was paid [3](#0-2) 

This same unchecked pattern is used for the `SweepDust` admin/relayer callback and for `TRANSACTION_FEES` payout to the beneficiary, so the same class of failure hits fee distribution as well as intent-fill/refund payouts [4](#0-3) .

This is precisely the bug class in the external report (unchecked ERC20 transfer return value leading to false assumption of success), except here it is not merely "unchecked `SafeERC20`" — it's a manually constructed low-level `.call` that explicitly discards the ABI-decoded success boolean, which is a stronger and more directly reachable version of the same defect.

By contrast, the sibling EVM contract (`evm/src/apps/IntentGatewayV2.sol`/`IntentsBase.sol`) and the fungible-token apps (`HyperFungibleToken.sol`, `WrappedHyperFungibleToken.sol`) consistently use OpenZeppelin's `SafeERC20.safeTransfer`/`safeTransferFrom`, which reverts on a `false` return, so this defect appears specific to the Tron deployment target.

### Impact Explanation
Any order beneficiary/solver receiving a payout in a token that returns `false` on failed transfer (rather than reverting) — e.g., due to being paused, blocklisted, or otherwise failing internal checks for that specific transfer at withdraw time — will have their escrow entry zeroed out and the order marked filled/refunded/dust-swept without ever receiving the tokens. The escrowed funds remain custodied in the `IntentGatewayV2` contract with no accounting entry pointing to them, and the beneficiary has no path to re-claim (the commitment is deleted / `_filled` already set), resulting in a permanent freeze/loss of user funds. Because fee payouts (`TRANSACTION_FEES`) go through the identical unguarded pattern, relayer/solver reward accounting can also be silently corrupted.

### Likelihood Explanation
This is reachable by any solver or user completing a normal intent lifecycle (`RedeemEscrow`/`RefundEscrow` requests delivered via ISMP, or the `SweepDust`/GET-response timeout path) — no privileged or malicious actor is required. The trigger condition depends on the specific ERC20 token configured for an order returning `false` instead of reverting; while common "clean" tokens (USDC, WETH, DAI) revert on failure and would not trigger this, a subset of tokens in the wild follow the return-false convention, and this contract accepts arbitrary caller-specified `token` addresses in orders, so an attacker (or even an ordinary user who unknowingly picks such a token, or one whose transfer starts failing due to token-side pausing/blacklisting) can hit this path.

### Recommendation
Replace the raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` pattern in `withdraw()` and the `SweepDust` branch of `onAccept()` with OpenZeppelin's `SafeERC20.safeTransfer`, consistent with the non-Tron `IntentGatewayV2`/`IntentsBase` implementations, e.g.:

```solidity
IERC20(token).safeTransfer(beneficiary, amount);
```

This reverts the whole withdrawal (and any state mutation to `_orders`) if the token transfer does not actually succeed, keeping accounting and token custody consistent.

### Proof of Concept
1. An order escrows a non-standard ERC20 token `T` (one that returns `false` instead of reverting on failed transfers) as `order.inputs[i].token`.
2. Hyperbridge delivers a `RedeemEscrow` request for that commitment; `onAccept` calls `withdraw(body, false)`.
3. Suppose token `T`'s `transfer` call would fail for the beneficiary at that moment (e.g., temporarily blacklisted, paused, or insufficient allowance-independent internal check) and per its non-standard implementation returns `false` rather than reverting.
4. `token.call(...)` returns `(success=true, data=abi.encode(false))`. The code only checks `success`, so `if (!success) revert TransferFailed();` does not trigger.
5. `_orders[body.commitment][token] -= amount;` executes, zeroing the escrow entry; `_filled[body.commitment] = beneficiary;` is set; `EscrowReleased` is emitted.
6. The beneficiary never received the tokens (`T.balanceOf(beneficiary)` unchanged), but the contract's internal bookkeeping shows the order fully settled and the funds remain stuck in the `IntentGatewayV2` contract with no remaining path to recover them for that beneficiary.

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
    }
