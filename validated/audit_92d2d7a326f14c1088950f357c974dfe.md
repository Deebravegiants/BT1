### Title
Excess native ETH sent to `EvmHost.dispatch`/`fundRequest` is not refunded to the caller - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest` all accept `msg.value` and, when non-zero, forward the *entire* `msg.value` into `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(fee, path, address(this), block.timestamp)`. Any ETH left over after the exact-output swap is refunded by the Uniswap router to `msg.sender` of that call — which is `EvmHost` itself, not the original transaction sender. `EvmHost` never captures the swap's return value or forwards the leftover ETH back to `_msgSender()`, so any overpayment is permanently retained inside the `EvmHost` contract instead of being returned to the user.

and identically in `dispatch(DispatchGet)`: [2](#0-1) 

and in `fundRequest`: [3](#0-2) 

In each case, `swapETHForExactTokens` is an *exact-output* swap: it consumes at most `msg.value` ETH to buy exactly `post.fee`/`get.fee`/`amount` fee tokens, and any unused ETH is refunded by the standard UniswapV2Router02 implementation to whoever called it — here, `EvmHost`. None of the three functions capture the `amounts` array returned by the swap, nor do they call `_sendValue`/`.call{value: ...}` to return the unspent ETH to `_msgSender()`. This is unlike the codebase's own `IntentGatewayV2`/`ExtrinsicIntents` contracts, which correctly track `msgValue -= amounts[0]` and explicitly refund any remainder to the caller, e.g.: [4](#0-3) 

This shows the intended pattern exists elsewhere in the repo but is missing in `EvmHost`.

The documentation for the dispatcher confirms the intended semantics ("Native token (msg.value): Automatically swapped to fee token via Uniswap") without describing any overpayment protection or refund: [5](#0-4) 

Any unprivileged caller (an application contract, or an EOA calling `fundRequest` directly) that sends `msg.value` greater than what the Uniswap swap needs to acquire `post.fee`/`get.fee`/`amount` fee tokens loses the difference permanently to `EvmHost`'s balance.

### Impact Explanation
This is a direct, permanent loss of user/application funds: any excess native token sent to `dispatch()` or `fundRequest()` on `EvmHost` is retained by the contract and never returned to the sender. Since the exact fee-token cost of an ETH→feeToken swap is subject to market price fluctuation and can only be estimated off-chain, users/integrators sending a safety margin of ETH (a very common practice, as demonstrated by the project's own test intent in `IntentGatewayV2Test.testPlaceOrder_FeeSwap_RefundsExcessNativeToken`, which expects refunds elsewhere in the codebase) will systematically lose the unspent portion when interacting with `EvmHost` directly. This affects every POST/GET dispatch and every `fundRequest` call paid in native token, making it a broadly reachable fund-loss bug for any message dispatcher, relayer-funding user, or app contract using native-token payment.

### Likelihood Explanation
High likelihood: this triggers on virtually every call where `msg.value` is not computed to the exact wei needed for the swap, which is the normal case since slippage/price movement makes precise sizing infeasible from off-chain estimation. No malicious actor is required — this occurs for any legitimate, unprivileged user dispatching a message or funding a request with native token.

### Recommendation
Capture the `amounts` array returned from `swapETHForExactTokens` in all three functions (`dispatch(DispatchPost)`, `dispatch(DispatchGet)`, `fundRequest`) and refund any unspent ETH (`msg.value - amounts[0]`) back to `_msgSender()`, mirroring the pattern already implemented in `IntentGatewayV2`/`ExtrinsicIntents` (`_sendValue(msg.sender, msgValue)`).

### Proof of Concept
1. Configure `EvmHost` with a Uniswap V2 router and fee token as in the deployed setup.
2. Caller invokes `dispatch(DispatchPost)` (or `dispatch(DispatchGet)`/`fundRequest`) with `post.fee = X` fee-token units and sends `msg.value` deliberately larger than the ETH amount required to purchase `X` fee tokens (e.g., 2x the estimated cost, to cover slippage).
3. Internally, `swapETHForExactTokens{value: msg.value}(X, path, address(this), block.timestamp)` executes; the router spends only `amounts[0] < msg.value` ETH and refunds `msg.value - amounts[0]` to `EvmHost` (the caller of the router).
4. `EvmHost` never forwards this refund to the original caller — the function returns without any ETH transfer back to `_msgSender()`.
5. Assert: `address(EvmHost).balance` increases by `msg.value - amounts[0]`, while the caller's balance decreases by the full `msg.value`, not just the actual swap cost — confirming the excess is permanently lost by the caller.
