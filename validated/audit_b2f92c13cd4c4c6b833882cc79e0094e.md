### Title
Uncapped scaled-debt valuation overflows before borrow-index cap and permanently freezes a market - ([File: `common/src/rates/simulate.rs`])

### Summary
A sufficiently large market can make `borrowed * borrow_index` exceed `i128` before `borrow_index` reaches `MAX_BORROW_INDEX_RAY`. Every accrual step evaluates that product before applying the index cap, so the next `Controller::update_indexes` call panics. Because all state-changing pool operations synchronize interest before mutating the market, the panic prevents repayment, withdrawal, liquidation, bad-debt cleanup, and further accrual.

### Finding Description
`accrue_step` first converts stored scaled debt and scaled supply to RAY-denominated values by calling `scaled_to_original` on both `borrowed` and `supplied`. [1](#0-0)  `scaled_to_original` is implemented as `scaled.mul(env, index)`, which returns `MathOverflow` when the resulting RAY value cannot fit in `i128`. [2](#0-1) 

The intended safety ceiling is applied only later by `update_borrow_index`, which computes a new index and clamps it to `MAX_BORROW_INDEX_RAY`. [3](#0-2)  The reward calculation then separately multiplies the unchanged scaled debt by both the old and new indexes, creating additional `i128` overflow points. [4](#0-3) 

`MAX_BORROW_INDEX_RAY` bounds the index itself but does not constrain `borrowed * index` to the representable RAY-value domain. [5](#0-4)  Consequently, a market with enough scaled debt can reach the value ceiling while its index remains below the configured cap. Once the state reaches that boundary, `global_sync` invokes the overflowing step on every subsequent accrual. [6](#0-5) 

The pool's public mutators are controller-owned, but ordinary users reach them through unprivileged controller entrypoints such as `supply`, `borrow`, `withdraw`, `repay`, `liquidate`, and `clean_bad_debt`. [7](#0-6)  The pool's `update_indexes` entrypoint calls `ops::market::accrue`, which loads each market and invokes `global_sync`. [8](#0-7) [9](#0-8) 

### Impact Explanation
This is a permanent freezing-of-funds condition for the affected hub-asset market. Once `borrowed * borrow_index` or `supplied * supply_index` exceeds `i128::MAX`, interest synchronization panics before any operation can safely reduce debt, withdraw supply, liquidate collateral, or change the rate model. The regression scenario demonstrates that attempted withdrawals and repayments continue to fail with `MATH_OVERFLOW` after accrual fails. [10](#0-9) 

Unlike an overflow corrected by the index ceiling, this failure occurs before the ceiling can protect the market. `update_borrow_index` may cap the next index, but the surrounding accrual arithmetic still has to evaluate the already-overlarge scaled value, and `calculate_supplier_rewards` evaluates both old and new debt values.

### Likelihood Explanation
An unprivileged participant can reach the accrual path through normal supply, borrow, and index-update flows. The practical precondition is an exceptionally large market balance multiplied by a sufficiently high accrued index; the test uses a one-billion-whole-token, eighteen-decimal market with sustained high utilization to cross the `i128` RAY-value ceiling. [11](#0-10) 

The bug therefore requires substantial liquidity and favorable accrual conditions rather than a single small transaction. However, it is a deterministic arithmetic boundary in production code, not dependent on privileged access, oracle manipulation, leaked keys, or third-party contract behavior. Once reached, ordinary unprivileged calls can trigger the freeze and no normal user path can recover the market.

### Recommendation
Bound accrual by representable total value, not merely by the index. Before compounding, calculate safe index ceilings from `i128::MAX / borrowed` and `i128::MAX / supplied`, then clamp the effective borrow and supply growth so every product used by `accrue_step`, `calculate_supplier_rewards`, `update_supply_index`, and `supply_index_reward_shortfall` remains representable. Alternatively, introduce explicit saturating total-value calculations for utilization and rewards while ensuring the stored indexes cannot permit later unscale or accrual operations to panic.

The fix should also cover the simultaneous `supplied * supply_index` calculation, because the same boundary can freeze a market through supplier value even when debt remains representable.

### Proof of Concept
The repository contains a directed reproduction in `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs`:

```rust
let principal = BILLION * 10i128.pow(18);
t.supply_raw(BOB, "BIG18", principal);
let debt = principal / 100 * 98;
t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
t.borrow_raw(ALICE, "BIG18", debt);

loop {
    t.advance_time(YEAR_SECS);
    if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
        break e;
    }
}
```

The test observes `MATH_OVERFLOW` while `borrow_index < MAX_BORROW_INDEX_RAY`, proving that the value multiplication overflows before the configured index cap is reached. It then confirms that `withdraw` and `repay` fail with the same error because both paths accrue interest first. [12](#0-11)

/// The cliff. A billion whole tokens is `1e36` raw ray; the value ceiling is
/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
