Found it: `store_consensus_state_id()` in `modules/pallets/ismp/src/host.rs` is documented in the `IsmpHost` trait as "Should return an error if the consensus_state_id already exists," but the implementation performs an unconditional `insert` with no existence check whatsoever.

### Title
Missing existence check in `store_consensus_state_id()` allows silent overwrite of an existing consensus client binding - (File: modules/pallets/ismp/src/host.rs)

### Summary
The `IsmpHost` trait documents `store_consensus_state_id` with an explicit contract: "Should return an error if the consensus_state_id already exists" [1](#0-0) . The `pallet-ismp` implementation ignores this contract and unconditionally overwrites the `ConsensusStateClient` map: `ConsensusStateClient::<T>::insert(consensus_state_id, client_id); Ok(())` [2](#0-1) . This is the same class of bug as the reported IBCClient issue: a "must not overwrite existing commitment/binding" invariant is documented but not enforced in code.

### Finding Description
`create_client()` calls `store_consensus_state_id(message.consensus_state_id, message.consensus_client_id)` as part of onboarding a new consensus client [3](#0-2) . The error enum even defines a dedicated variant, `DuplicateConsensusStateId`, apparently intended for exactly this check [4](#0-3) , but neither `create_client` nor `store_consensus_state_id` ever returns/uses it. As implemented, a second `create_client` call (or any `AdminOrigin`-gated re-creation flow) referencing an already-used `consensus_state_id` silently rebinds that id to a different `consensus_client_id`, without reverting and without any signal that state is "out of sync," exactly the scenario the external report highlights for `consensusStateCommitmentKey`.

### Impact Explanation
`ConsensusStateClient` is the mapping that `consensus_client_id()` uses to resolve which `ConsensusClient` implementation (BEEFY, GRANDPA, Tendermint, BSC, etc.) governs a given `consensus_state_id`'s trust root, and every `update_client()` call looks this up before calling `verify_consensus` [5](#0-4) . If a `consensus_state_id` can be silently rebound to a different client implementation or a different, attacker-influenced initial state (via `create_client`'s `state_machine_commitments` and `consensus_state` parameters), all subsequent proof verification and state-machine commitments for that id are computed against the wrong trust anchor. That is a forged/unsound consensus-state root vector, matching the "unsound state commitment" impact category.

### Likelihood Explanation
`create_client` is restricted (called through `AdminOrigin`/root in the observed call sites, e.g. `create_consensus_client`), so this is not directly reachable by an arbitrary unprivileged relayer under normal governance discipline — this narrows the severity versus the external report's original EVM public-relayer path. However, it remains a genuine mismatch between the documented safety invariant and the actual implementation, and any governance/admin flow (or a future permissionless extension of `create_client`) that assumes the documented "errors on duplicate" behavior will be silently unprotected.

### Recommendation
Enforce the documented contract in `store_consensus_state_id`: check `ConsensusStateClient::<T>::contains_key(consensus_state_id)` and return `Error::DuplicateConsensusStateId { consensus_state_id }` if already set, mirroring the existing (unused) error variant, before inserting.

### Proof of Concept
1. Call `create_consensus_client` (or the equivalent `create_client` message) with `consensus_state_id = X`, `consensus_client_id = BEEFY_ID`.
2. Call it again with the same `consensus_state_id = X` but `consensus_client_id = GRANDPA_ID` (or any other registered client) and an attacker-chosen initial `consensus_state`/`state_machine_commitments`.
3. `store_consensus_state_id` overwrites `ConsensusStateClient[X]` without error [2](#0-1) ; subsequent `update_client` calls against `X` now resolve to the new client implementation and trust the newly-seeded state, with no on-chain signal that a rebinding occurred.

Note: I was not able to fully confirm the exact set of runtime call sites that can trigger `create_client`/`create_consensus_client` outside of `AdminOrigin`-gated paths across the whole codebase within the scope of this investigation; the severity assessment above assumes the standard `AdminOrigin` gating observed in `modules/pallets/beefy-consensus-proofs/src/lib.rs`. If any pallet exposes an unprivileged or under-privileged path to `create_client`, the impact would be materially higher.
