## Title
Webhook shop-domain identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) from the unauthenticated `X-Shopify-Shop-Domain` HTTP header, while the HMAC signature it validates covers only the raw request body. This breaks the binding "shop the HMAC authenticates == shop the app acts on," allowing any shop that can produce a genuinely-signed webhook (e.g. by triggering an event in its own, legitimately-installed store) to relabel that webhook as belonging to a different merchant simply by changing the header, since the header plays no role in the signature check.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw JSON body: [1](#0-0) 

The `shop` accessor, however, is read straight from the `shopify-shop-domain` (or `x-shopify-shop-domain`) header, which is never included in the signed content: [2](#0-1) 

`Utils::HmacValidator.validate` verifies the HMAC solely against `to_signable_string` (i.e. the body): [3](#0-2) 

`Webhooks::Registry.process` validates that HMAC and, once it passes, immediately hands `request.shop` (from the unauthenticated header) to the app's handler as the tenant identity for the operation: [4](#0-3) 

The equality that should hold is: `shop authenticated by HMAC == shop the handler acts on for tenant-scoped data`. Because the HMAC only proves "this body was signed with the app's `api_secret_key`" and says nothing about which shop it was signed for, the two sides diverge: any party capable of obtaining one genuinely-signed webhook body/HMAC pair (trivially available to any shop that has installed the app, since all shops of a given app share the same `api_secret_key`) can replay that exact body+HMAC to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header naming a different, victim shop. The HMAC still validates because it never covered the header.

### Impact Explanation
This is a cross-tenant integrity issue: an app that (as documented in `WebhookMetadata`) uses `request.shop` to select which merchant's session/access token/data to update will process attacker-supplied data under a victim shop's identity, or attribute a webhook event to the wrong tenant, purely because the shop field is unauthenticated. This matches the "cross-tenant access" impact bucket, since a malicious-but-legitimately-installed shop (an unprivileged tenant relative to other merchants) can forge webhook attribution across tenant boundaries using only its own valid app-secret-signed payloads.

### Likelihood Explanation
Any store that installs the app can trigger real webhook deliveries for its own store (e.g. by placing an order, updating a product) and thus obtain a body+HMAC pair signed with the app's shared `api_secret_key`. Replaying that request to the app's public webhook endpoint with a different `X-Shopify-Shop-Domain` header requires no secret knowledge beyond what the attacker's own shop already legitimately possesses, and no interaction with Shopify's own webhook delivery infrastructure is required to change the header — the header is just an HTTP field on the request the app process receives.

### Recommendation
Include the shop domain (and topic/webhook-id, ideally) in the HMAC-covered signable content, or otherwise cryptographically bind the shop identity to the payload, e.g., by validating the header value against the shop-to-secret/session mapping resolved independently of headers, or by requiring the app to compare `request.shop` against the shop of the session/token used to originally register that specific webhook subscription. At minimum, document clearly that `request.shop` is not authenticated by the HMAC and must not be trusted as a tenant boundary on its own.

### Proof of Concept
1. Attacker legitimately installs the app on `attacker-shop.myshopify.com`.
2. Attacker triggers a real event (e.g., creates an order) causing Shopify to send a genuine webhook: body `B`, header `X-Shopify-Hmac-Sha256: HMAC(secret, B)`, header `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker resends this exact request to the app's webhook endpoint but changes only `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com`.
4. `HmacValidator.validate` recomputes `HMAC(secret, B)` — unchanged, since body `B` is untouched — and the check passes. [5](#0-4) 
5. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: B, ...))`, and the app's business logic processes body `B` under the identity of `victim-shop.myshopify.com`.
