### Title
Unallowlisted route venues can execute arbitrary token transfers under the caller's authorization tree - (File: contracts/controller/src/strategies/swap.rs)

### Summary
Controller strategy entrypoints pass caller-supplied swap routes to the configured router while the caller's `require_auth` remains active for the transaction. Because route pool/token addresses are not allowlisted, a malicious venue contract can invoke `token.transfer(caller, attacker, amount)` from inside the route. Soroban records that transfer as a child of the caller's authorization; if the caller signs the simulated authorization tree, the transfer executes even though it is unrelated to the intended swap.

### Finding Description
`swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, and `multiply` all route through `swap_tokens`. `swap_tokens` authorizes only the controller's exact input transfer to the router, then calls `router.execute_strategy` with attacker-controlled route bytes in `contracts/controller/src/strategies/swap.rs:33-38`.

The router interprets route registry entries as arbitrary `Address` values and invokes whichever pool contract the payload names. There is no venue/pool allowlist or authorization-scope confinement. A malicious contract implementing the expected venue interface can therefore run arbitrary code below the router call and issue a token transfer from the strategy caller.

The repository's adversarial test demonstrates the primitive: a rogue hop pool calls `token::Client::transfer(victim, attacker, amount)`; transaction simulation attaches that call under the victim's `swap_collateral` authorization entry, and signing that tree makes the theft execute in enforcing mode.

### Impact Explanation
An unprivileged attacker can construct a malicious route and cause a victim contract/user flow to sign a simulated authorization tree containing an unexpected child transfer. The attacker can steal unrelated wallet tokens not supplied to the lending protocol, bounded by the victim's balances and the malicious transfer encoded in the signed tree. The protocol-level swap can still satisfy measured output and final solvency checks, so the controller's positive-output accounting does not detect the unrelated transfer.

### Likelihood Explanation
Likelihood depends on convincing a victim to sign a route whose simulated authorization tree contains the extra transfer. No protocol privilege, leaked key, oracle manipulation, or prior approval is required, but the victim's wallet/client must sign the poisoned authorization tree. This makes the attack a meaningful authorization-confusion/phishing path rather than an unconditional theft.

### Recommendation
Constrain route execution to governance- or router-allowlisted venue contracts, or redesign strategy execution so untrusted route code cannot run inside the caller's authorization subtree. At minimum, enforce a hard invariant that expected strategy transactions contain only the known controller/root authorization and exact token pulls required by the route, and make protocol-provided route construction/signing reject any additional child authorization.

### Proof of Concept
1. Deploy a malicious contract exposing a venue-compatible `swap`/pool interface.
2. Its handler calls:
   ```rust
   token::Client::new(&env, &wallet_token)
       .transfer(&victim, &attacker, &wallet_balance);
   ```
3. Construct a `swap_collateral` route that names this contract as a hop pool while still producing enough output to satisfy the strategy's balance-delta checks.
4. Simulate the victim's `swap_collateral` transaction. Soroban records the malicious wallet-token transfer as a child under the victim's controller authorization.
5. If the victim signs the returned authorization tree, the rogue transfer executes atomically with an otherwise valid collateral swap.
