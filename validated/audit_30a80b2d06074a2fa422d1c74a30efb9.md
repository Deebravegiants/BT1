### Title
Webhook `shop` tenant identifier is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, excluding all HTTP headers. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC over that body-only string and, upon success, trusts `request.shop` (derived from the unauthenticated `shopify-shop-domain` header) as the tenant identity forwarded to the host application's webhook handler.

### Finding Description
The HMAC binding invariant should be: `hmac == HMAC(secret, bytes_that_include_everything_the_app_will_act_on)`. Here the equality that actually holds is `hmac == HMAC(secret, raw_body)`, while the app acts on `shop` from `request.shop`, a value taken from `shopify-shop-domain`/`x-shopify-shop-domain` header (`lib/shopify_api/webhooks/request.rb:20-23`) that is never included in `to_signable_string` (`lib/shopify_api/webhooks/request.rb:35-38`). `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) checks `Utils::HmacValidator.validate(request)`, which recomputes the HMAC only over `to_signable_string`/raw body (`lib/shopify_api/utils/hmac_validator.rb:26-31`), then immediately builds `WebhookMetadata` with `shop: request.shop` and dispatches it to the app's `handler.handle`, without any secondary check that the header-derived shop matches a shop bound into the signed payload.

An unprivileged attacker who has captured (or replayed) one legitimately-HMAC'd webhook body/signature pair for topic `T` from shop `A` can resend that exact body+signature combination to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header value for shop `B`. The HMAC still validates (it never covered the header), and the host application's handler will process shop `A`'s data under shop `B`'s tenant identity.

### Impact Explanation
This crosses a tenant boundary: cross-tenant data leakage/confusion is possible because the gem hands the host app a `shop` value that is presented as authenticated (having passed `HmacValidator.validate`) but is not actually bound to the signed bytes. Any app logic that keys database writes/lookups, GDPR redaction actions, or session lookups by `WebhookMetadata#shop` can be made to act on the wrong tenant. This matches the "Cross-tenant access" Critical impact category.

### Likelihood Explanation
Exploitation requires only network access to the app's public webhook endpoint and one previously-observed valid `(raw_body, hmac)` pair for any topic/shop (webhook payloads/signatures are not treated as secret by Shopify's docs, and mandatory topics like `customers/redact`, `shop/redact` are especially sensitive). No credentials, TLS interception, or privileged account are needed — only header manipulation on an HTTP request, squarely inside the "unprivileged internet user" threat model.

### Recommendation
Include the shop domain (and ideally the topic and webhook id) in the signable/verified bytes, or otherwise independently verify that `request.shop` corresponds to the tenant the HMAC was actually issued for — e.g., require the app to look up the shop's known secret/session per-shop rather than trusting the header, or bind the header value into `to_signable_string` before computing/validating the HMAC.

### Proof of Concept
1. Capture a legitimate webhook delivery to the app: raw body `B`, header `shopify-hmac-sha256: H`, header `shopify-shop-domain: shop-a.myshopify.com`.
2. Resend an HTTP request with the identical raw body `B` and identical `shopify-hmac-sha256: H`, but with `shopify-shop-domain: shop-b.myshopify.com`.
3. `ShopifyAPI::Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb:26-31` recomputes the HMAC solely from `raw_body` (via `Request#to_signable_string`, `lib/shopify_api/webhooks/request.rb:36-38`) and returns `true`.
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:190,198-199`) proceeds and invokes `handler.handle(data: WebhookMetadata.new(..., shop: "shop-b.myshopify.com", ...))`, so the app processes shop A's webhook payload as if it belonged to shop B. [1](#0-0) [2](#0-1) [3](#0-2)
