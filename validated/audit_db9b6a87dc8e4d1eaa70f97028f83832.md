### Title
Webhook shop-identity spoofing via unauthenticated `shop-domain` header not covered by HMAC - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by verifying an HMAC over the raw request body, then trusts the `shop` value taken from the `X-Shopify-Shop-Domain` HTTP header — a value that is never included in the signed bytes — as the tenant identity for dispatch. This breaks the intended binding `hmac_signed_bytes == identity_bytes_used_for_dispatch`, letting a merchant who has legitimately installed the app on their own store forge the tenant identity of any webhook delivery and cause the host application to process it as if it came from a different, victim shop.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read from a separate, unsigned header: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string` (i.e. the raw body) and compares it to the `hmac` header: [3](#0-2) 

`Registry.process` gates on that HMAC check alone, then forwards `request.shop` (the unauthenticated header value) straight into `WebhookMetadata`, which the host application's handler uses as the tenant/session key: [4](#0-3) 

Because the app's `api_secret_key` is shared across *every* shop that has installed the app, any merchant who installs the app on their own store receives legitimately-signed webhook deliveries (valid HMAC over the body, computed with that same shared secret). Since the HMAC never binds `shop-domain`, an attacker can take one of their own store's genuine deliveries — valid body + valid HMAC header — and simply replace the `X-Shopify-Shop-Domain` header with a victim shop's domain before POSTing it to the app's public webhook endpoint. The gem's `Registry.process` will accept it as authentic and dispatch it under the victim's identity, because the equality it actually should enforce — `shop_bound_by_hmac == shop_used_for_dispatch` — never holds; the left side is undefined and the right side is attacker-controlled.

### Impact Explanation
This is a cross-tenant identity confusion: an unprivileged attacker (any merchant capable of installing the app on a store they control — no `api_secret_key`, access token, or victim credentials required) can make the host application execute webhook-driven logic (session teardown on `app/uninstalled`, order/customer data workflows, billing state changes, cache/state updates, etc.) attributed to a shop they do not own. Per the code-423n4 report's bug class ("a field acted on but not covered by the HMAC"), the `shop` field is exactly such a field here — it drives tenant-scoped side effects in the host app but carries none of the cryptographic assurance the HMAC is supposed to provide. This satisfies the Critical "cross-tenant access" bar.

### Likelihood Explanation
High. No secrets, tokens, or victim interaction are needed — only a legitimate app installation on an attacker-owned store (the normal, unprivileged path any merchant can take) plus the ability to replay an HTTP POST with one modified header to the app's public webhook endpoint.

### Recommendation
Bind the shop identity into the authenticated bytes before trusting it: include `shop-domain` (and ideally `topic`/`webhook-id`) in the HMAC-covered signable string (mirroring how Shopify's own webhook payloads embed shop-scoped identifiers), or independently verify `request.shop` against the shop associated with the specific HMAC secret used to validate the request (e.g., per-shop secret or a signed claim), instead of trusting an unauthenticated header for tenant dispatch.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (ordinary, unprivileged merchant action).
2. Shopify sends the attacker a legitimate webhook, e.g. `orders/create`, to the app's registered endpoint with:
   - `X-Shopify-Hmac-Sha256: <valid HMAC over raw body, computed with the app's shared api_secret_key>`
   - `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`
   - raw JSON body `B`
3. Attacker copies this exact request, leaving the body `B` and `X-Shopify-Hmac-Sha256` untouched, and changes only:
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
4. Attacker POSTs the modified request directly to the app's public webhook endpoint, which internally calls `ShopifyAPI::Webhooks::Registry.process(request)`.
5. `HmacValidator.validate` recomputes HMAC over `to_signable_string` (== `B`, unchanged) and it matches → validation passes: [5](#0-4) 
6. `Registry.process` dispatches `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body: ..., ...)` to the handler, which the host app uses to look up/act on `victim-shop`'s session/state — despite the request never having been authenticated for that shop.
