### Title
Missing Chainlink L2 sequencer-uptime check in `SimplexPaymaster` oracle pricing enables stale/incorrect gas pricing on Arbitrum - (File: evm/src/utils/SimplexPaymaster.sol)

### Summary
`SimplexPaymaster` prices ERC-20 gas payments using Chainlink `AggregatorV3Interface.latestRoundData()` feeds and only checks `answer > 0` and staleness against `maxOracleAge` [1](#0-0) . Chainlink price feed contracts are registered per-chain, including Arbitrum Mainnet (`EVM-42161`) [2](#0-1) , so this contract is deployable/usable on Arbitrum. On Arbitrum (and other L2s using Chainlink's off-chain-report price feeds), Chainlink recommends checking the `L2 Sequencer Uptime Feed` in addition to the price feed's `updatedAt`, because when the Arbitrum sequencer is down, L1-submitted transactions can still update round data with a delay, but during/immediately-after an outage the feed can return a technically "fresh" `updatedAt` timestamp that does not reflect current market price, since price updates during downtime are deferred and then batch-applied once the sequencer resumes. `SimplexPaymaster` has no analogous sequencer-uptime check.

### Finding Description
`_getOraclePrice` is the sole gatekeeper for price freshness used throughout the pricing path — `_tokenPrice` (called from `_fetchDetails`, `getTokenPrice`, `estimateTokenCost`) and `swapAndDeposit` [3](#0-2) [4](#0-3) . It validates only:
1. `answer > 0`
2. `block.timestamp - updatedAt <= maxOracleAge`

There is no check of an Arbitrum `L2 Sequencer Uptime Feed` (e.g. `0xFdB631F5EE196F0ed6FAa767959853A9F217697D` on Arbitrum One) to detect sequencer downtime, nor a grace period after the sequencer resumes before trusting fresh price data — exactly the pattern flagged in the referenced Sherlock report against `OTLM.sol`.

This gap is directly reachable by any unprivileged bundler/UserOp submitter: `_validatePaymasterUserOp` and `_fetchDetails` are invoked during ERC-4337 validation for every sponsored `UserOperation`, and both ultimately call `_getOraclePrice` via `_tokenPrice` [5](#0-4) [6](#0-5) . `swapAndDeposit` is treasury-only, but the pricing bug still corrupts every unprivileged UserOp's gas cost computation, since `_fetchDetails`/`_tokenPrice` are on that path.

### Impact Explanation
During an Arbitrum sequencer outage, the on-chain Chainlink round data can appear within `maxOracleAge` (since L1 fallback updates can post a timestamp that is not truly synchronized with the paused L2 clock/market), letting `_getOraclePrice` accept a stale/incorrect price as valid. Any unprivileged UserOp sender interacting with this paymaster during that window is charged (or undercharged) ERC-20 tokens against a stale native/USD or token/USD price:
- If the token is undervalued relative to native, users are overcharged, draining more of their approved/permitted tokens than fair.
- If the token is overvalued, the paymaster undercharges, allowing users to obtain gas sponsorship for less than actual cost, draining the paymaster's native EntryPoint deposit disproportionately to the ERC-20 collected — a fund-drain/insolvency vector for the paymaster's deposit.

This is a Medium-severity issue: it requires the specific precondition of an L2 sequencer outage window, but when triggered it produces concrete economic loss (either to unprivileged users or to the paymaster's treasury-owned float) without any privileged action.

### Likelihood Explanation
Likelihood is Medium: Arbitrum sequencer outages are infrequent but have occurred historically; the vulnerable window is bounded to the outage duration plus any lag before Chainlink's L1-fallback mechanism catches up, and any of the many ordinary UserOp submitters on Arbitrum during that window would trigger mispriced gas charges without needing any special privilege.

### Recommendation
Add a Chainlink `L2 Sequencer Uptime Feed` check to `_getOraclePrice` (or a new preliminary check in `_tokenPrice`/`_validatePaymasterUserOp`) that:
1. Reads `latestRoundData()` from the sequencer uptime feed.
2. Reverts if `answer == 0` (sequencer down).
3. Enforces a grace period (e.g. Chainlink's recommended ~1 hour) after `startedAt` of the last "up" transition before trusting price data again.

Since the paymaster is chain-agnostic (same contract deployed to Ethereum, BSC, Base, etc., per `nativeOracle`/`tokenOracle` configuration), make this check conditional/configurable per-deployment (e.g. an optional `sequencerUptimeFeed` parameter in `Params`, only enforced when non-zero) so L1/non-L2 deployments are unaffected.

### Proof of Concept
1. Deploy `SimplexPaymaster` on Arbitrum with a registered token/USD Chainlink feed and native/USD feed, `maxOracleAge` set to Chainlink's normal heartbeat (e.g. 24h for many pairs).
2. Simulate an Arbitrum sequencer outage (e.g. via a forked test manipulating `block.timestamp` while the feed's `updatedAt` reflects an L1-fallback update that lags true price movement, staying within `maxOracleAge`).
3. Submit a UserOp through the paymaster using mode `0x00`/`0x02`; `_fetchDetails` → `_tokenPrice` → `_getOraclePrice` accepts the price since `answer > 0` and `updatedAt` is within `maxOracleAge`, despite the price being stale relative to actual market conditions during the outage.
4. Observe the computed `tokenPrice` diverges from the fair market rate, resulting in over/under-charging the UserOp sender relative to actual gas cost — demonstrated by `testStaleOracleReverts`/`testNonPositiveOraclePriceReverts` in the test suite [7](#0-6)  showing these are the *only* freshness checks exercised — no sequencer-uptime scenario is tested.

    /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
