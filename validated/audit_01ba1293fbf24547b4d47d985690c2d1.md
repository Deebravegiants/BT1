### Title
`_select()` Accepts Malformed/Zero-Recovered Session Signatures Because `ECDSA.recover` Output Is Never Checked Against `address(0)` - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`_select()` recovers a `sessionKey` from an EIP-712 signature via `ECDSA.recover(digest, options.signature)` and immediately commits `keccak256(abi.encode(options.solver, sessionKey))` to transient storage without ever validating that the recovered address is non-zero or otherwise sane [1](#0-0) . This mirrors the Beebots `verify()` root cause: a signature-recovery result is trusted and stored/compared with no `!= address(0)` guard.

### Finding Description
The OpenZeppelin `ECDSA.recover` used in modern releases does revert on a canonical malformed signature (bad `s`/`v` or zero-address recovery via `tryRecover`'s error path), which differs from raw `ecrecover`'s silent zero-return behavior that the original Beebots bug relied on. This library version dependency could not be fully confirmed from the indexed code (the OpenZeppelin `ECDSA.sol` source itself is not present in the indexed contents), so it is not possible to prove from this repo alone whether the exact `ECDSA` version in use here always reverts on invalid signatures rather than ever returning `address(0)`.

Even setting aside the OZ recover behavior, the structural issue is analogous: `_select()` never checks `sessionKey != address(0)` before using it to derive the `selectionHash` stored in transient storage at slot `commitment`. At fill time, `fillOrder` (not shown in the excerpt retrieved) re-derives `keccak256(abi.encode(msg.sender, order.session))` and compares against this stored value — if `order.session` were ever `address(0)` (e.g., an order created with an unset/default session key) and an attacker could supply any signature that happens to recover to `address(0)` (or if OZ's recover ever permits that in this dependency graph), the selection check would pass without a legitimate session-key signature, similar to how Beebots' `tradeValid()` was fooled by a zero maker/signer.

### Impact Explanation
If the zero-address bypass were reachable, an attacker could forge solver selection for any order whose `session` field is `address(0)` or uninitialized, letting an unauthorized solver claim the fill and its associated escrowed input tokens — a direct theft-of-funds path through the intents escrow.

### Likelihood Explanation
Low-to-uncertain: this requires either (a) a code path elsewhere that permits `order.session == address(0)` to be a valid/expected state, or (b) an OpenZeppelin `ECDSA` version/edge case that still returns `address(0)` instead of reverting on invalid signature data. Neither could be confirmed from the indexed codebase (the OZ library source and the full `fillOrder`/order-construction validation for `session` were not found in the index).

### Recommendation
Add an explicit `require(sessionKey != address(0), "invalid session key")` (or equivalent revert) in `_select()` immediately after `ECDSA.recover`, and separately ensure order construction rejects `session == address(0)`, so that no order can ever be selectable via a degenerate/zero recovered signer, independent of the underlying ECDSA library's exact failure semantics.

### Proof of Concept
Not constructible with confidence from the indexed code: proving exploitability requires (1) confirming the exact `ECDSA.recover` implementation pinned in this repo's dependencies actually can return `address(0)` for some malformed input rather than reverting, and (2) confirming a code path that creates or accepts an `Order` with `session == address(0)`. Both of these details are outside what the current index exposes. [1](#0-0) 

**Note on limitations:** Due to index size limits, the full `IntentGatewayV2`/`fillOrder` implementation, the `Order.session` validation logic at order-placement time, and the vendored OpenZeppelin `ECDSA.sol` source were not available in the index. A Devin session with full repository access would be needed to confirm whether `session == address(0)` is reachable and whether the pinned `ECDSA.recover` can return `address(0)` on any input, before this can be escalated from a plausible analog to a confirmed vulnerability.

```text
    function _select(SelectOptions calldata options) internal returns (address) {
        bytes32 structHash = keccak256(abi.encode(SELECT_SOLVER_TYPEHASH, options.commitment, options.solver));
        bytes32 digest = _hashTypedDataV4(structHash);
        address sessionKey = ECDSA.recover(digest, options.signature);

        bytes32 commitment = options.commitment;
        bytes32 selectionHash = keccak256(abi.encode(options.solver, sessionKey));
        assembly {
            tstore(commitment, selectionHash)
        }

        return sessionKey;
    }
```
