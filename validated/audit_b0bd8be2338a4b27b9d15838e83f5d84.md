### Title
Webhook `shop` (tenant) identity is not covered by the HMAC signature, allowing a valid webhook body to be replayed under a forged tenant identity - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`, `lib/shopify_api/utils/hmac_validator.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body. The `shop` (tenant identity), `topic`, `api_version` and `webhook_id` values are read from unauthenticated HTTP headers and handed to the application's handler as if they had been verified alongside the payload. Because these fields are not part of the signed content, an attacker who can obtain one genuinely-signed webhook (e.g., by triggering an event on a store/shop they control) can replay the exact `raw_body`/HMAC pair while substituting the `shop-domain` header to claim the event originated from a different, victim tenant.

### Finding Description
The signature binding used by the gem is: [1](#0-0) 

`hmac` is computed over `@raw_body` only (`to_signable_string` returns `@raw_body`): [2](#0-1) 

`shop`, `topic`, `api_version`, and `webhook_id` are all pulled straight from HTTP headers with no cryptographic binding to the signed body: [3](#0-2) 

`HmacValidator.validate` only verifies the `hmac` claim against `to_signable_string` (i.e., the body): [4](#0-3) 

`Registry.process` calls this single check and then immediately trusts `request.shop`, `request.topic`, etc., forwarding them to the consuming application's handler as authenticated metadata: [5](#0-4) 

The equality that should hold is: **shop claimed in the header == shop cryptographically bound to the delivered payload**. In this implementation that equality is never enforced — the HMAC only proves "this body was produced by someone possessing the shared secret," not "this body belongs to shop X." Any header value can be substituted after the fact without invalidating the signature, because the signature never covered the header in the first place.

### Impact Explanation
If the app built on top of this gem uses `WebhookMetadata#shop` (as populated by `Registry.process`) to decide which merchant/tenant record an incoming event applies to — which is the documented and expected usage pattern of this field — an attacker can inject a validly-signed payload (originating from their own store) while asserting it belongs to an arbitrary victim shop domain. This is a cross-tenant data/state injection: order, customer, or app-data events can be attributed to a shop the attacker does not control, corrupting or manipulating another merchant's data/state within the host application. This satisfies the Critical "cross-tenant access" impact category, since the tenant boundary (`shop`) is the exact identity binding broken.

### Likelihood Explanation
Exploitation requires no privileged credentials, no `api_secret_key`, no access token, and no interception: an attacker only needs their own (free) Shopify development store with the target app installed to legitimately trigger a webhook and capture a valid `raw_body` + `hmac` pair, then replay it to the same public endpoint with a modified `shop-domain` header. This is fully achievable by an unprivileged internet user and does not depend on any misuse of the gem's documented API by the host app — the host app is following the documented contract (`Registry.process` → `WebhookMetadata#shop`) exactly as intended.

### Recommendation
Include the tenant-identifying fields (`shop`, `topic`, `webhook_id`) in the signed content, or otherwise cryptographically bind them to the payload (e.g., re-derive/confirm shop identity via an authenticated side-channel, or require the app to independently verify shop ownership of the referenced resource before trusting `data.shop`). At minimum, the library should not present `shop`/`topic`/`webhook_id` as validated data once `HmacValidator.validate` succeeds, since only the body is actually authenticated.

### Proof of Concept
1. Attacker creates their own Shopify development store, `attacker-shop.myshopify.com`, and installs the target app.
2. Attacker triggers a normal event (e.g., `orders/create`) on their own store; Shopify delivers a webhook to the app's endpoint with a valid `X-Shopify-Hmac-Sha256` computed over the JSON body using the shared `api_secret_key`.
3. Attacker captures the raw request: `{raw_body, hmac_header}`.
4. Attacker replays this exact `raw_body` and `hmac_header` to the same webhook endpoint, but changes `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com` (and optionally `X-Shopify-Webhook-Id`/`X-Shopify-Topic`).
5. `ShopifyAPI::Webhooks::Request.new` parses these headers unchanged; `Utils::HmacValidator.validate(request)` recomputes the HMAC over `raw_body` only, which still matches, so validation succeeds (`lib/shopify_api/utils/hmac_validator.rb:12-31`).
6. `Registry.process` invokes `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))` with `shop == "victim-shop.myshopify.com"`, even though the payload actually originated from and describes `attacker-shop.myshopify.com`'s data (`lib/shopify_api/webhooks/registry.rb:188-200`).
