### Title
Webhook `shop-domain`/`topic` headers are trusted without HMAC coverage, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw body, then trusts the `shop-domain` and `topic` HTTP headers — which are never covered by that HMAC — as the tenant identity handed to the app's handler.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0)  The `shop` and `topic` accessors instead read directly from unauthenticated headers: [2](#0-1)  `Registry.process` validates the HMAC using `Utils::HmacValidator.validate(request)`, which only checks `request.hmac` against a signature computed over `to_signable_string` (i.e. the body) using `Context.api_secret_key` — a single secret shared by the app across *all* installed shops, not per-tenant: [3](#0-2) [4](#0-3)  After the HMAC check passes, `request.topic` and `request.shop` (both header-derived, unsigned) are forwarded verbatim into `WebhookMetadata` and given to the app's handler as the authoritative tenant/topic identity: [5](#0-4) 

The identity binding that should hold is: `hmac-verified bytes == bytes the handler treats as authenticated for a given shop`. In reality the HMAC only proves "signed with this app's shared secret" over the body; it says nothing about which shop or topic the request is for, because those fields live in headers excluded from `to_signable_string`.

Because the app's `client_secret`/HMAC key is identical for every merchant that installs the app, any unprivileged user who installs the app on their own (attacker-controlled) development store legitimately receives real webhooks from Shopify with a valid `hmac-sha256` value for a body they can freely trigger/observe (e.g., updating a product on their own store to control the JSON body). That attacker can then replay the same raw body and valid HMAC to the app's webhook endpoint while substituting the `shopify-shop-domain` (and/or `shopify-topic`) header with a victim shop's domain. `HmacValidator.validate` still succeeds because it never inspected those headers, and `Registry.process` dispatches the forged event to the handler labeled as coming from the victim shop.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook processing: an attacker who controls no more than their own shop installation can inject a webhook event that the host application will attribute to an arbitrary other shop (`shop-domain` header is fully attacker-controlled once HMAC only covers the body). Any app logic keyed on `data.shop` (job routing, per-tenant DB writes, tenant-scoped side effects — exactly the pattern shown in the gem's own docs, `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) can be poisoned with attacker-chosen data attributed to a different tenant, i.e. cross-tenant access/data corruption, without needing the victim's access token, session, or the app's `client_secret`.

### Likelihood Explanation
Requires only: (1) the ability to install the target app on any shop (any developer/merchant can do this — no privileged credentials, no access token, no leaked secret needed), and (2) the ability to send an arbitrary HTTP POST to the app's public webhook endpoint with custom headers, which is inherent to how webhook endpoints work. No cryptographic secret needs to be broken; the attacker reuses a legitimately-issued, valid HMAC for a body they already control from their own shop's webhook traffic.

### Recommendation
Bind the tenant/topic identity into the value that is HMAC-verified, not just the raw body. Options:
1. Include `shop-domain` and `topic` (and `webhook-id`) in `to_signable_string` so the signature covers the full logical message, matching how `Auth::Oauth::AuthQuery#to_signable_string` already includes `shop` in its signed parameters (`lib/shopify_api/auth/oauth/auth_query.rb`).
2. At minimum, document/require callers to cross-check `WebhookMetadata#shop` against the set of shops for which the app currently holds a valid session before acting on the payload, and warn explicitly that headers are unauthenticated.
3. Consider deriving/validating shop identity from data embedded in the signed body where Shopify includes it, rather than solely from headers.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and registers for topic `products/update`.
2. Attacker triggers a product update on their own store; Shopify sends a legitimate webhook POST with body `B` and header `shopify-hmac-sha256: H` (valid HMAC of `B` under the app's shared `api_secret_key`), plus `shopify-shop-domain: attacker.myshopify.com`.
3. Attacker resends the identical `B`/`H` to the app's public webhook endpoint, but rewrites the header to `shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...shop-domain: "victim.myshopify.com", hmac-sha256: H...})` is constructed; `Registry.process` calls `HmacValidator.validate`, which recomputes HMAC over `B` only and matches `H`, so validation succeeds.
5. The handler receives `WebhookMetadata(topic: "products/update", shop: "victim.myshopify.com", body: parsed(B), ...)` and performs tenant-scoped work believing the event genuinely originated from `victim.myshopify.com`.
