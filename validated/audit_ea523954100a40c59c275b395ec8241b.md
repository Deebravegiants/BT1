### Title
Unbounded nested loop over registered workflows × attacker-controlled topics list enables gateway-triggered DoS / trigger starvation - (File: core/capabilities/webapi/trigger/trigger.go)

### Summary
The `web_api_trigger` capability handler on the node side iterates every registered workflow trigger against every entry of an attacker-supplied `Topics` array with no bound on either dimension, mirroring the BetaFinance `enterMarkets`/`accrue` pattern where an unprivileged actor inflates loop iterations that another party (here, the node/gateway path) must pay compute cost for.

### Finding Description
`processTrigger` in [1](#0-0)  takes `payload.Topics` directly from the inbound gateway message body and iterates it in a nested loop against every trigger registered in `h.registeredWorkflows`: [2](#0-1) 

The only validation performed on `topics` is a non-empty check (`len(topics) == 0`) — there is no upper bound on the number of topics a caller can submit, and no bound on the number of trigger registrations (`h.registeredWorkflows`) that get collected under `h.mu.Lock()` and then scanned in the nested loop: [3](#0-2) 

This function is reached from `HandleGatewayMessage`, which decodes an untrusted `TriggerRequestPayload` body forwarded from the internet-facing Gateway (sender is an arbitrary externally-supplied `body.Sender` address) and calls `processTrigger` for every `MethodWebAPITrigger` request: [4](#0-3) 

Similar to the reported Omni Protocol issue — where a borrower could inflate `enterMarkets` and force the liquidator to pay unbounded gas in the `accrue` loop — here an unprivileged HTTP caller of the Gateway's web API trigger endpoint controls one dimension of the loop (`Topics` array length) while the number of registered workflow triggers (potentially large in a busy DON) provides the other dimension. Nothing in the reviewed authorization path (`ValidatedMessageFromReq`, `HandleLegacyUserMessage` in `core/services/gateway/handlers/capabilities/handler.go`) caps the size of `Topics` before it reaches this per-request O(triggers × topics) scan on the node.

### Impact Explanation
A single malicious/careless request with a very large `Topics` array multiplies the per-message CPU cost by the number of currently-registered `web_api_trigger` workflows on that node. Since this handler runs synchronously inside `HandleGatewayMessage` (invoked from the connector's `readLoop`, per [5](#0-4) ), a computationally expensive call can degrade processing of the connector's message loop, delaying or starving trigger delivery/registration handling for other, unrelated workflows on the same node — a cross-workflow (cross-tenant) availability impact analogous to the bad-debt/blocked-liquidation outcome in the referenced report, though here the effect is CPU/goroutine contention rather than on-chain fund loss.

### Likelihood Explanation
Reachability requires only that the attacker's `body.Sender` address is present in at least one victim workflow's `allowedSenders` list (or that many empty-match iterations still execute the inner loop body before the `allowedSenders` check) — actually, the `allowedTopics` check happens first per registered trigger and is independent of sender identity, so the O(triggers × topics) cost is paid by any caller before the sender/authorization checks (`trigger.allowedSenders[sender.String()]`) are even evaluated, per [6](#0-5) . This means any external caller able to reach the Gateway's `web_api_trigger` method (no per-workflow authorization needed to trigger the scan itself) can supply an oversized `Topics` array. Likelihood is Medium: it depends on how many workflows are registered on a given node/DON and whether the Gateway or transport layer imposes a message-size ceiling that indirectly bounds `Topics` length (not confirmed in the reviewed code paths).

### Recommendation
- Enforce a maximum number of entries in `payload.Topics` (and reject/​truncate oversized requests) before entering the matching loop in `processTrigger`.
- Consider indexing `registeredWorkflows` by topic (e.g., `map[topic][]*webapiTrigger`) instead of scanning the full trigger set per request, to make lookup cost proportional to matches rather than total registrations × topics.
- Apply the sender/rate-limit check ahead of, or independent from, the expensive topic-membership scan so that costs cannot be inflated for triggers the caller isn't authorized against.

### Proof of Concept
Conceptual (not verified end-to-end due to index limits on gateway transport-layer size checks):
1. Register N `web_api_trigger` workflows on a node, each with a modest `AllowedTopics` set, via `RegisterTrigger` (`core/capabilities/webapi/trigger/trigger.go:212-269`).
2. As an external, unauthenticated-to-any-specific-workflow caller, send a `MethodWebAPITrigger` message through the Gateway with `payload.Topics` containing a very large number of distinct topic strings (e.g., tens of thousands).
3. The Gateway forwards the message to the node; `HandleGatewayMessage` → `processTrigger` executes the nested loop over all N triggers × all supplied topics, consuming CPU proportional to `N × len(Topics)` regardless of whether the caller is authorized for any of them, before any authorization or rate-limit check short-circuits the cost.
4. Repeated such requests can degrade node responsiveness to legitimate trigger events for other workflows sharing the connector's message loop.

Note: I was unable to confirm from the indexed code whether the Gateway's HTTP/WS transport layer (`core/services/gateway/network/httpserver.go`, `wsserver.go`) enforces a request body size limit that would cap the practical size of `Topics` before it reaches this handler; this would materially affect the actual severity and should be verified in a full checkout of those files.

func (h *triggerConnectorHandler) HandleGatewayMessage(ctx context.Context, gatewayID string, req *jsonrpc.Request[json.RawMessage]) error {
	msg, err := hc.ValidatedMessageFromReq(req)
	if err != nil {
		h.lggr.Errorw("error validating message from request", "err", err, "request", req)
		return nil
	}
	body := &msg.Body
	sender := ethCommon.HexToAddress(body.Sender)
	var payload webapicap.TriggerRequestPayload
	err = json.Unmarshal(body.Payload, &payload)
	if err != nil {
		h.lggr.Errorw("error decoding payload", "err", err)
		err = h.sendResponse(ctx, gatewayID, body, ghcapabilities.TriggerResponsePayload{Status: "ERROR", ErrorMessage: fmt.Errorf("error %s decoding payload", err.Error()).Error()})
		if err != nil {
			h.lggr.Errorw("error sending response", "err", err)
		}
		return nil
	}

	switch body.Method {
	case ghcapabilities.MethodWebAPITrigger:
		resp := h.processTrigger(ctx, gatewayID, body, sender, payload)
		var response ghcapabilities.TriggerResponsePayload
		if resp == nil {
			response = ghcapabilities.TriggerResponsePayload{Status: "ACCEPTED"}
		} else {
			response = ghcapabilities.TriggerResponsePayload{Status: "ERROR", ErrorMessage: resp.Error()}
			h.lggr.Errorw("Error processing trigger", "gatewayID", gatewayID, "body", body, "response", resp)
		}
		err = h.sendResponse(ctx, gatewayID, body, response)
		if err != nil {
			h.lggr.Errorw("Error sending response", "body", body, "response", response, "err", err)
		}
		return nil
