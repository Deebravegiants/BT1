### Title
Same-asset multi-withdrawal status misreport due to assetId-only matching - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts, packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts)

### Summary
`findMatchingWithdrawal` in both the POA bridge status-tracking code paths matches a withdrawal record returned by the POA API using only the asset identifier (`nep141:${near_token_id}`), ignoring the withdrawal's index, amount, or destination address. When a single NEAR intents transaction contains more than one withdrawal leg of the *same* asset (e.g., two `ft_withdraw` intents for `nep141:btc.omft.near` to two different destinations), every leg resolves to the *same first-matching* record, so the SDK reports identical `completed`/`txHash` status for withdrawals that are, on-chain, distinct and may not have equally completed.

The `WithdrawalIdentifier.index` field (set by `createWithdrawalIdentifier`, `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts` `createWithdrawalIdentifier`) is carried through the whole flow (`withdrawal-watcher.ts`, `sdk.waitForWithdrawalCompletion`) specifically to disambiguate multiple withdrawals within the same NEAR transaction, as shown by the test `"maintains indexes specific to bridge route"` in `packages/intents-sdk/src/sdk.waitForWithdrawalCompletion.test.ts:99-124`. However, the POA status lookup discards this index and matches purely on the token id, which the code comment itself acknowledges: "multiple withdrawals of the same token in a single transaction are not supported."

The equality that should hold is: *status/txHash reported for withdrawal at index N == on-chain outcome of the specific withdrawal issued at index N*. Because matching ignores index/amount/destination, when two same-asset legs exist in one transaction, both indices resolve to the *first* array element returned by the API, so index 1's reported status/txHash is actually index 0's outcome (or vice versa, depending on array order, which the code comments even note is "unsorted").

### Impact Explanation
An integrator or caller that issues a batch withdrawal containing two legs of the same asset (a legitimate, unprivileged usage pattern — e.g., paying two different users the same token in one intents transaction) will receive a `completed` status with a `txHash` for the *wrong* leg once the first leg's withdrawal is processed by the POA relayer. This is a status misreport: it can cause an integrator built on top of the SDK to believe withdrawal B has completed (and release funds, mark an invoice paid, or stop retrying) when only withdrawal A has actually landed on the destination chain, and withdrawal B may still be pending or fail. This matches the "status or hash misreport making an integrator credit or refund twice" impact class.

### Likelihood Explanation
This does not require any malicious relayer/bridge behavior or price manipulation — it is triggered purely by normal usage: any caller (not necessarily privileged) constructing a multi-withdrawal intent with two same-asset legs, which the SDK's `IntentsSDK`/`withdrawal-watcher.ts` explicitly supports (multiple `withdrawalParams` per tx, with `index` tracked exactly for this reason). The bug is acknowledged in the code's own comments as a known gap, but it remains live and reachable in the current status-polling code paths (`PoaBridge.describeWithdrawal` and `waitForWithdrawalCompletion`), so likelihood is more than theoretical for any integrator batching same-asset withdrawals.

### Recommendation
Disambiguate `findMatchingWithdrawal` beyond `assetId`: use `amount` and/or `address`/`destinationAddress` (and, if the POA API preserves order, positional matching after sorting both sides by amount, as the code comment itself suggests) to bind each `WithdrawalIdentifier.index` to the correct API record. Until the POA API supports precise correlation, the SDK should either reject/flag batches with duplicate-asset legs in `createWithdrawalIntents`/`withdrawal-watcher.ts`, or surface an explicit "ambiguous status" error rather than silently returning the first same-asset match as `completed` for every duplicate leg.

### Proof of Concept
1. Caller builds a NEAR intents transaction with two `ft_withdraw` legs for `nep141:btc.omft.near`: leg 0 → address A (amount 100000), leg 1 → address B (amount 50000).
2. `createWithdrawalIdentifier` produces `{index: 0, ...}` and `{index: 1, ...}` for the two legs (see `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`).
3. The POA relayer completes leg 0 (to A) first; leg 1 (to B) is still pending.
4. POA API's `getWithdrawalStatus` returns a `withdrawals` array containing only leg 0's `COMPLETED` record (matching `nep141:btc.omft.near`), since both legs share the same `near_token_id`.
5. `describeWithdrawal` is called for both index 0 and index 1; `findMatchingWithdrawal` finds the *same* record for both, since it only checks `nep141:${near_token_id} === assetId`, per `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts:409-427`.
6. Both `describeWithdrawal({index:0,...})` and `describeWithdrawal({index:1,...})` return `{status: "completed", txHash: "<leg-0-tx-hash>"}`, even though leg 1 (to address B) has not actually completed — reproducing the exact scenario shown by the existing unit test `"matches withdrawal by assetId, not by index"` (`packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.test.ts:1054-1111`), generalized to the case where the two same-asset withdrawals are *not* both completed yet.

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
