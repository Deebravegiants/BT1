### Title
Webhook shop identity is not bound by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives its HMAC-signable material from the raw request body only, while the shop identity (`x-shopify-shop-domain` header) used to attribute the webhook to a tenant is read separately from an unauthenticated header. `Utils::HmacValidator` verifies only the body against the secret; it never checks that the `shop` value handed to the webhook handler is the one the signature was actually computed for. This breaks the identity binding `shop_bound_by_hmac == shop_attributed_to_webhook_data`.

### Finding Description
`Webhooks::Request#to_signable_string` returns `@raw_body` exclusively: [1](#0-0) 
while `shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from HTTP headers with no cryptographic tie to the body or to the HMAC: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (i.e. the raw body) and secure-compares it to the `hmac` header: [3](#0-2) 

`Webhooks::Registry.process` only calls this body-only HMAC check before trusting `request.shop` and forwarding it to the app's handler as tenant identity: [4](#0-3) 

Because the shop header is never covered by the signature, `hmac(raw_body)` remains valid for any `shop-domain` header value an attacker chooses to send alongside that exact `raw_body`. The equality the library implicitly assumes — "if the HMAC validates, the shop header is trustworthy" — does not actually hold, since the two are computed independently.

### Impact Explanation
An unprivileged actor who owns any shop with the target app installed (a normal, unprivileged action — installing a free/dev app requires no special access) receives legitimate webhook deliveries for that shop, each with a valid `(raw_body, hmac)` pair. Because the header carrying tenant identity is outside the signed material, the attacker can replay that exact `(raw_body, hmac)` pair directly to the app's public webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` value (e.g. a victim's shop). `HmacValidator.validate` still returns `true`, and `Registry.process` dispatches the payload to the app's handler tagged with the attacker-chosen shop. Any app logic that uses `WebhookMetadata#shop` to select the tenant's stored session/access token or to apply the payload to per-tenant records is now operating on forged tenant attribution — a cross-tenant data confusion, matching the Critical impact category ("cross-tenant access").

### Likelihood Explanation
The attack requires no leaked secrets, tokens, or privileged access — only the ability to install the target app on any shop (which the attacker fully controls) to harvest a valid signed body, and the ability to POST directly to the app's already-public webhook URL, which is a normal internet-reachable endpoint. This is entirely within the reach of an unprivileged internet user.

### Recommendation
Bind the identity fields to the signature verification: require that the shop (and ideally topic/webhook_id) used by `Registry.process`/`WebhookMetadata` be re-derived only from data that was part of the HMAC-signed payload, or additionally verify the `shop` header against a list of shops/sessions the app has legitimately registered before trusting it, rather than accepting any header value once the body-only HMAC passes.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and lets Shopify deliver a real webhook, capturing `raw_body` and the `x-shopify-hmac-sha256` header (valid for that body under the app's secret).
2. Attacker sends a POST to the app's webhook endpoint with the same `raw_body` and `hmac` header, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `raw_body` against the secret.
4. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ...)` and processes it as though it originated from the victim shop.
