### Title
Duplicate `address(0)` entries in `erc20TokenAddresses` let a depositor mint 2x shielded ETH for 1x real `msg.value` - ([File: contracts/Hinkal.sol])

### Summary
`Hinkal.transact` computes `balanceDif` per index `i` in `circomData.erc20TokenAddresses`, adding `msg.value` fully in every iteration where `erc20TokenAddresses[i] == address(0)`. Because `HinkalHelper.dimensionsCheck`/`checkOnchainCreation` never reject duplicate token addresses, an attacker can submit `erc20TokenAddresses = [address(0), address(0)]` with `amountChanges = [X, X]` and `msg.value = X`, causing both per-index balance checks to pass independently and two X-value shielded outputs to be created for a single X-wei deposit.

### Finding Description
Broken equality: real value received (`msg.value = X`) should equal the total shielded value minted (`sum(amountChanges)` over the duplicate ETH legs). Instead, the per-index accounting lets `sum(balanceDif) == 2*msg.value` while the actual contract ETH balance increases by only `msg.value`.

Trace:
1. `Hinkal.transact` (contracts/Hinkal.sol:78-90) snapshots `oldBalances`/`newBalances` via `getBalancesForArray`, which for `address(0)` just reads `address(this).balance`. If both array slots are `address(0)`, both reads return the identical contract balance, before and after `_internalTransact`.
2. Inside `_internalTransact` (contracts/Hinkal.sol:172-230), the loop calls `transferERC20TokenFromOrCheckETH` for each index with positive `deltaAmountChange`. In `Transferer.sol:111-128`, when `_contractAddress == address(0)` and `_to == address(this)`, the function **only asserts** `require(msg.value == _value)`—it performs no transfer and does not consume/track `msg.value`. It is checked independently and identically for i=0 and i=1, both against the same unspent `msg.value = X`, so both pass.
3. Back in `transact`'s outer loop (contracts/Hinkal.sol:97-146), for each duplicate `address(0)` index `i`: `balanceDif = newBalances[i] + msg.value - oldBalances[i]`. Since the real ETH balance didn't change (no transfer happened for `_to == address(this)`), `newBalances[i] == oldBalances[i]`, so `balanceDif == msg.value == X` for **both** i=0 and i=1.
4. The final require, `balanceDif == amountChanges[i] + utxoAmount`, is checked per-index: `X == amountChanges[0] (=X) + 0` and `X == amountChanges[1] (=X) + 0` — both individually pass. `utxoAmount` is 0 in both iterations because `utxoSet` is only populated by `_externalTransact` and stays empty for `_internalTransact` (externalActionId == 0).
5. No code path (`dimensionsCheck`, `checkOnchainCreation`, `getHashedCalldata`) rejects duplicate entries in `circomData.erc20TokenAddresses`; these only check array-length equality across dimensions, not uniqueness of token addresses.
6. The zk-circuit's balance equation (`inTotal + amountChanges === outTotal`) is applied per index slot as well (public inputs are consumed in `formBasicInput`, one entry per array index), so a self-crafted proof with `inTotal[0]=inTotal[1]=0`, `amountChanges[0]=amountChanges[1]=X` and two output commitments of value `X` each is a circuit-valid, unconstrained-by-duplication proof from the attacker's own perspective (attacker fully controls proof generation for their own UTXOs).

Net effect: attacker sends `X` wei of real ETH, but the contract accepts and inserts two off-chain output commitments (via `insertCommitments`, contracts/Hinkal.sol:161-166) each worth `X`, i.e. `2X` of shielded ETH backing for `X` wei actually held.

### Impact Explanation
This mints shielded value without backing — for every `X` wei sent, the attacker can create `2X` worth of spendable shielded UTXOs. The excess `X` can later be withdrawn by the same attacker (or transferred to others) by spending the nullifiers/UTXOs, directly draining the contract's actual ETH reserves that back other users' legitimate shielded balances. This matches the Critical category: "minting shielded value without backing." The exploit is fully repeatable per transaction and scales linearly with the number of duplicate `address(0)` entries an attacker includes (n duplicates → n*X minted for X wei paid).

### Likelihood Explanation
- No privileged role required; the attacker only needs to be able to call `Hinkal.transact` with `originalSender == msg.sender` and `relay == address(0)` (self-relayed deposit path) — fully within an unprivileged EOA's capability.
- Attacker must locally generate a valid Groth16 proof for a circuit instance with `tokenNumber = 2` (or more), both token slots equal to `address(0)`, zero input nullifiers, and outputs summing per-slot to `amountChanges[i]`. This is possible because there's nothing in `dimensionsCheck`/`checkOnchainCreation` preventing duplicate token addresses, and the attacker fully controls all `CircomData`/`Dimensions` fields for their own transaction.
- Cost is simply generating the proof and paying `X` wei plus gas; the vulnerability is deterministic and repeatable, not probabilistic.

### Recommendation
Enforce uniqueness of `erc20TokenAddresses` entries in `HinkalHelper.dimensionsCheck` (or a dedicated check called from `performHinkalChecks`), rejecting any `circomData` where the same token address (including `address(0)`) appears more than once. Additionally, harden the `balanceDif` accounting in `Hinkal.transact` to add `msg.value` only once overall (e.g., track a `msg.value` consumed a single time across the whole loop rather than once per matching index), so that even absent the duplicate-address check, per-leg accounting cannot double-count the same native value.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, verifier mocks/stubs sufficient to make `verifyProof` return true for a crafted proof (or use a real circuit build with `tokenNumber = 2`).
2. Construct `CircomData` with:
   - `erc20TokenAddresses = [address(0), address(0)]`
   - `amountChanges = [X, X]` (both positive, `onChainCreation = [false, false]`)
   - `inputNullifiers = [[0],[0]]` (fresh deposit, no spend)
   - `outCommitments`/`encryptedOutputs` sized per `dimensionsCheck` to represent two output UTXOs of value `X` each for token `address(0)`.
   - `externalActionData.externalActionId = 0`, `externalActionData.externalAddress = attacker`.
   - `relay = address(0)`, `originalSender = attacker`.
3. Call `hinkal.transact{value: X}(a, b, c, dimensions, circomData)`.
4. Assert:
   - Both `require(balanceDif == amountChanges[i] + utxoAmount)` checks in `Hinkal.transact` pass (transaction does not revert).
   - `address(hinkal).balance` increased by exactly `X` (not `2X`).
   - Two output commitments of value `X` (for token `address(0)`) were inserted via `insertCommitments`.
   - Equality check: `sum(balanceDif over the two address(0) legs) == 2*X` while `address(hinkal).balance - balanceBefore == X`, demonstrating the divergence between minted shielded value (`2X`) and real value received (`X`).
