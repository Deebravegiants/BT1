Based on the gem's own code, there is a genuine identity-binding inconsistency between how `shop` is handled in OAuth callbacks versus webhook requests.

### Title
Webhook `shop` (tenant) identifier is not covered by the HMAC signature, unlike OAuth callback `shop` - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` exposes a `shop` accessor read straight from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, but the HMAC verification performed by `Utils::HmacValidator` (via `to_signable_string`) only ever covers the raw request body. The `shop` value is therefore never bound to the signature, even though `Webhooks::Registry.process` uses it downstream as the tenant identifier passed to the handler.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read from an unauthenticated header: [2](#0-1) 

`HmacValidator.validate` verifies exactly `to_signable_string` against the received HMAC, i.e. only the body: [3](#0-2) 

`Registry.process` accepts the request once the HMAC (body-only) check passes, then forwards the unauthenticated `request.shop` straight to the app-supplied handler as the tenant identity for the webhook: [4](#0-3) 

This is in sharp contrast to how the gem itself handles OAuth callback verification: `Oauth::AuthQuery#to_signable_string` explicitly includes `shop` in the signed parameter set, so the OAuth `shop` claim *is* bound to the signature: [5](#0-4) 

The equality that should hold — `shop` used by the handler == `shop` cryptographically bound to the authenticated payload — is broken for webhooks. Since all shops using a given app share the same `api_secret_key`, any unprivileged internet user who can install the app on their own store (a normal, self-service action) can capture a legitimately-signed `(body, hmac)` pair for their own shop, then replay that exact body/HMAC combination against the app's webhook endpoint while substituting an arbitrary value in `x-shopify-shop-domain`. `HmacValidator.validate` still succeeds because it never inspects the header, and `Registry.process` calls the handler with `WebhookMetadata.new(shop: request.shop, ...)` where `shop` is the attacker-controlled, unverified value.

### Impact Explanation
Any application that keys per-tenant state (order data, inventory events, session/token lookups, webhook idempotency, etc.) off `WebhookMetadata#shop` as returned by this gem's own `Registry.process` API can be made to apply data belonging to the attacker's shop to a victim shop's record, i.e. cross-tenant data injection/corruption through the documented webhook-processing entry point of this gem. This matches the "Critical - cross-tenant access" impact category since the tenant boundary enforced elsewhere in the gem (OAuth) is not enforced here.

### Likelihood Explanation
Likelihood is realistic but not trivial: the attacker must (1) be able to install the target app on a shop they control (self-service for public apps) to obtain a validly HMAC-signed webhook body, and (2) be able to deliver a forged HTTP request with a substituted `shop-domain` header to the victim app's webhook endpoint (feasible since the endpoint is a public HTTP callback and the gem does not restrict source IPs). No possession of `api_secret_key`, access tokens, or other credentials belonging to the victim is required.

### Recommendation
Bind `shop` (and ideally `topic`) into the value verified by `HmacValidator`, mirroring what `Oauth::AuthQuery` already does, e.g. have `Webhooks::Request#to_signable_string` incorporate the shop/topic headers before hashing, or have `Registry.process` cross-check `request.shop` against the destination host previously established for the tenant (if known) before invoking the handler. At minimum, document prominently that `WebhookMetadata#shop` is not cryptographically authenticated and must not be trusted as a tenant key without additional verification.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`, obtaining a legitimate webhook delivery with body `B` and header `x-shopify-hmac-sha256: H` (valid because `H = HMAC(app_secret, B)`).
2. Attacker sends `POST /webhook` to the victim app's endpoint with the same body `B`, the same `x-shopify-hmac-sha256: H`, but `x-shopify-shop-domain: victim.myshopify.com`.
3. `Webhooks::Request.new` parses headers, `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(app_secret, B)` and matches `H` — validation passes because `to_signable_string` never included the shop header [1](#0-0) .
4. The handler is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", body: <attacker's data>, ...)` [6](#0-5) , causing the attacker-controlled payload to be processed under the victim's tenant identity.
