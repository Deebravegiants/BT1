### Title
Webhook HMAC signature does not cover the `shop`, `topic`, `webhook-id`, or `api-version` headers, allowing cross-tenant webhook forgery via header substitution - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, and `ShopifyAPI::Utils::HmacValidator.validate` verifies the HMAC solely against that raw body using the app's shared `api_secret_key`. The `shop`, `topic`, `webhook_id`, and `api_version` values are all read straight from HTTP headers (`shopify-shop-domain`, `shopify-topic`, etc.) and are never included in the signed content, yet `Registry.process` forwards them unchecked into `WebhookMetadata` for the handler to act on.

### Finding Description
The equality the code relies on is: `HMAC-valid(raw_body)` ⇒ `shop header is trustworthy`. These are not equivalent. `HmacValidator.validate_signature` computes `HMAC(raw_body, api_secret_key)` [3](#0-2)  and compares it to the `hmac-sha256` header. `Request#to_signable_string` returns only `@raw_body` [4](#0-3) , while `shop`, `topic`, `webhook_id`, and `api_version` are pulled directly from headers with no participation in the signature [5](#0-4) .

Because the app's `api_secret_key` is shared across all merchants/tenants using the app (it is not per-shop), any party who can obtain one genuinely-signed `(raw_body, hmac)` pair — for example a merchant capturing a legitimate webhook delivery sent to their own installation, or any observer of a delivered webhook — can replay that exact body and HMAC to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` and/or `x-shopify-topic` headers with arbitrary values. `Registry.process` only re-validates the HMAC against the body [2](#0-1) ; it performs no check that the signed body was actually issued for the claimed `shop` or `topic`. The forged `shop`/`topic` values are then passed straight into `WebhookMetadata` [1](#0-0)  and handed to the host application's handler as authoritative.

### Impact Explanation
This breaks the tenant-identity binding: "shop the HMAC authenticates" vs. "shop the handler acts on" are treated as equal but are not, since the header is fully attacker-controlled and unauthenticated. A malicious or compromised merchant (an unprivileged party relative to other tenants) can cause the host application to process webhook data while attributing it to a different, victim shop domain, or to a different topic than the one actually signed — cross-tenant data confusion in the webhook processing pipeline of any app built on this gem's documented `Registry.process`/`WebhookHandler` API.

### Likelihood Explanation
Exploitation requires only network access to the app's public webhook endpoint and possession of any single legitimately-signed webhook body (trivially available to a merchant who installs the app on their own store and inspects their own webhook traffic, or via any point capable of observing webhook deliveries). No access to `api_secret_key`, access tokens, or other privileged material is needed, making this readily reachable by an unprivileged internet user who controls the crafted headers.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the signed content evaluated by `to_signable_string`, or otherwise cryptographically bind these header values to the signature before trusting them in `WebhookMetadata`. At minimum, the caller-supplied `shop` should be cross-checked against an independent, trusted source (e.g., a known/registered shop for that HMAC) before being used as the tenant identifier passed to `handler.handle`.

### Proof of Concept
1. App installs on `attacker-shop.myshopify.com` and registers an HTTP webhook handler for topic `orders/create`.
2. Shopify delivers a legitimately-signed webhook to the app's endpoint:
   ```
   POST /webhooks
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid HMAC of raw body computed with the app's api_secret_key>
   x-shopify-shop-domain: attacker-shop.myshopify.com
   { ...order body... }
   ```
3. The attacker captures this exact `(raw_body, hmac)` pair and replays it to the same endpoint, changing only the header:
   ```
   x-shopify-shop-domain: victim-shop.myshopify.com
   ```
4. `HmacValidator.validate` recomputes `HMAC(raw_body, api_secret_key)` and it still matches the unmodified `hmac-sha256` header, since the header value was never part of the signed content [6](#0-5) .
5. `Registry.process` accepts the request and invokes the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` [2](#0-1) , causing the host application to process attacker-controlled order data attributed to a shop the attacker does not own.
