### Title
Stale device-passcode-fallback auth trigger persists after switching to biometry-only, allowing silent authentication downgrade - ([File: features/auth-mobile/module/auth.js])

### Summary
`Auth#setBioAuth`'s `on` branch only ever writes the keystore secrets for the currently requested mode (`useDeviceAuth` true/false) and never deletes the keys belonging to the *other* mode. As a result, calling `enableBioAuth({fallbackToDevicePin:true})` followed later by `enableBioAuth({fallbackToDevicePin:false})` leaves `AUTH_KEYSTORE_DEVICE_AUTH_KEY`/`AUTH_KEYSTORE_DEVICE_AUTH_TRIGGER_KEY` in the keystore alongside the new `AUTH_KEYSTORE_BIO_AUTH_KEY`/`AUTH_KEYSTORE_BIO_AUTH_TRIGGER_KEY`. Because `getBioAuthTrigger` checks the device-auth trigger key first, `BioAuth#authenticate` (iOS) will silently succeed via device-passcode fallback even though the user's latest explicit action requested biometry-only authentication.

### Finding Description
`#setBioAuth(on, { useDeviceAuth })` in `features/auth-mobile/module/auth.js` has two branches:
- `!on`: deletes all four keys (`AUTH_KEYSTORE_DEVICE_AUTH_KEY`, `AUTH_KEYSTORE_DEVICE_AUTH_TRIGGER_KEY`, `AUTH_KEYSTORE_BIO_AUTH_KEY`, `AUTH_KEYSTORE_BIO_AUTH_TRIGGER_KEY`).
- `on` with `useDeviceAuth` true: only sets `AUTH_KEYSTORE_DEVICE_AUTH_KEY`/`AUTH_KEYSTORE_DEVICE_AUTH_TRIGGER_KEY` (with `ACCESS_CONTROL_USER_PRESENCE`, which permits device-passcode fallback).
- `on` with `useDeviceAuth` false: only sets `AUTH_KEYSTORE_BIO_AUTH_KEY`/`AUTH_KEYSTORE_BIO_AUTH_TRIGGER_KEY` (with `ACCESS_CONTROL_BIOMETRY_CURRENT_SET`, biometry-only). [1](#0-0) 

Neither `on` branch clears the keys from the opposite mode. `enableBioAuth` calls `#setBioAuth(true, { useDeviceAuth: fallbackToDevicePin })` directly, so calling it twice with different `fallbackToDevicePin` values accumulates secrets from both modes instead of replacing them: [2](#0-1) 

`getBioAuthTrigger` then checks the device-auth trigger key before the bio-auth trigger key and returns whichever is present first: [3](#0-2) 

`BioAuth#authenticate` (iOS) relies on this ordering to trigger the OS keychain prompt and treats any truthy resolved value as a successful authentication: [4](#0-3) 

Since the leftover `AUTH_KEYSTORE_DEVICE_AUTH_TRIGGER_KEY` was stored with `ACCESS_CONTROL_USER_PRESENCE` (device passcode fallback allowed), the OS-level keychain prompt for that stale key will accept the device passcode alone, satisfying `authenticate()` even though the user's last explicit configuration action (`enableBioAuth({fallbackToDevicePin:false})`) intended to require biometry only. The existing unit tests for `enableBioAuth` (`features/auth-mobile/module/__tests__/auth.test.js`) only test each mode in isolation and never exercise a mode switch, so this accumulation is untested.

### Impact Explanation
This is an authentication-strength downgrade / stale-credential-persistence bug: once a user has ever enabled `fallbackToDevicePin: true`, no subsequent `enableBioAuth({fallbackToDevicePin:false})` (attempting to tighten security to biometry-only) actually removes the weaker device-passcode-fallback trigger. Anyone who can supply the device passcode (a materially weaker secret than the user's biometric) can unlock/authenticate into the wallet's protected auth flow, defeating the user's explicit intent to require biometry only. This matches an auth-bypass / privilege-persistence class impact scoped to the local auth gating logic used before sensitive operations gated by `BioAuth#authenticate`.

### Likelihood Explanation
Fully reproducible and deterministic — no attacker input beyond normal use of the app's own settings flow is required. Precondition is simply that the user (or app logic) calls `enableBioAuth({fallbackToDevicePin:true})` at least once, and later calls `enableBioAuth({fallbackToDevicePin:false})` without an intervening `disableBioAuth()`/`removePin()` call (both of which do fully clear all four keys). This is a plausible real-world sequence, e.g. a user who initially opts into "biometrics or device passcode" and later revisits settings to select "biometrics only."

### Recommendation
In `#setBioAuth`'s `on` branch, delete the keys for the mode not being enabled before/while setting the new mode's keys — i.e., when `useDeviceAuth` is true, delete `AUTH_KEYSTORE_BIO_AUTH_KEY`/`AUTH_KEYSTORE_BIO_AUTH_TRIGGER_KEY`, and when `useDeviceAuth` is false, delete `AUTH_KEYSTORE_DEVICE_AUTH_KEY`/`AUTH_KEYSTORE_DEVICE_AUTH_TRIGGER_KEY`, so only the currently selected mode's secrets exist in the keystore at any time.

### Proof of Concept
Add to `features/auth-mobile/module/__tests__/auth.test.js`:
```js
test('switching from fallbackToDevicePin true to false removes device-auth secrets', async () => {
  biometry.get.mockResolvedValue('Touch ID')
  await auth.load()

  await auth.enableBioAuth({ fallbackToDevicePin: true })
  await auth.enableBioAuth({ fallbackToDevicePin: false })

  // Expect stale device-auth trigger/key to be gone
  expect(await keystore.getSecret(key(AUTH_KEYSTORE_DEVICE_AUTH_KEY))).toBeUndefined()
  expect(await keystore.getSecret(key(AUTH_KEYSTORE_DEVICE_AUTH_TRIGGER_KEY))).toBeUndefined()

  // getBioAuthTrigger should now only be satisfiable via biometry
  const trigger = await auth.getBioAuthTrigger()
  expect(keystore.getSecret).toHaveBeenCalledWith(key(AUTH_KEYSTORE_BIO_AUTH_TRIGGER_KEY))
  expect(trigger).toBe(true) // only via bio-auth key, not device-auth fallback
})
```
Expected current (buggy) behavior: the assertions on `AUTH_KEYSTORE_DEVICE_AUTH_KEY`/`AUTH_KEYSTORE_DEVICE_AUTH_TRIGGER_KEY` being `undefined` fail, demonstrating both secrets coexist and `getBioAuthTrigger` would resolve via the stale device-passcode-fallback trigger first.

  #setBioAuth = async (on, { useDeviceAuth } = {}) => {
    if (!on) {
      await this.#keystore.deleteSecret(this.#key(AUTH_KEYSTORE_DEVICE_AUTH_KEY))
      await this.#keystore.deleteSecret(this.#key(AUTH_KEYSTORE_DEVICE_AUTH_TRIGGER_KEY))
      await this.#keystore.deleteSecret(this.#key(AUTH_KEYSTORE_BIO_AUTH_KEY))
      await this.#keystore.deleteSecret(this.#key(AUTH_KEYSTORE_BIO_AUTH_TRIGGER_KEY))
      return
    }

    const keyOpts = {
      accessible: ACCESSIBLE_WHEN_UNLOCKED_THIS_DEVICE_ONLY,
    }

    if (useDeviceAuth) {
      // Android and iOS handle `ACCESS_CONTROL_USER_PRESENCE` differently when device auth
      // is not enabled. This check ensures consistent behavior across platforms.
      const canAuth = await this.canUseDeviceAuth()
      if (!canAuth) {
        throw new DeviceAuthenticationUnavailableError()
      }

      await this.#keystore.setSecret(this.#key(AUTH_KEYSTORE_DEVICE_AUTH_KEY), on, keyOpts)
      await this.#keystore.setSecret(this.#key(AUTH_KEYSTORE_DEVICE_AUTH_TRIGGER_KEY), on, {
        ...keyOpts,
        accessControl: ACCESS_CONTROL_USER_PRESENCE, // This flag allows iOS to fallback to device pin.
      })
    } else {
      await this.#keystore.setSecret(this.#key(AUTH_KEYSTORE_BIO_AUTH_KEY), on, keyOpts)
      await this.#keystore.setSecret(this.#key(AUTH_KEYSTORE_BIO_AUTH_TRIGGER_KEY), on, {
        ...keyOpts,
        accessControl: ACCESS_CONTROL_BIOMETRY_CURRENT_SET,
      })
    }
  }
