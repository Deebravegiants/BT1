### Title
Unchecked low-level ERC20 `transfer` return value in Tron `IntentGatewayV2.withdraw` lets escrow accounting finalize without tokens actually moving - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron port of `IntentGatewayV2` releases escrowed order inputs, transaction fees, and swept dust using raw low-level `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` calls and only checks that the *call itself* did not revert (`success`), never decoding and verifying the boolean return value of the ERC20 `transfer()` function. This is the same root-cause pattern as the referenced M-16 finding: the withdrawal path reports/finalizes success (decrements escrow, marks the order filled, emits `EscrowReleased`/`EscrowRefunded`) even when the token has not actually been transferred to the beneficiary.

### Finding Description
In `withdraw()` [1](#0-0) , each escrowed token release does:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
_orders[body.commitment][token] -= amount;
```
and fees:
```solidity
(bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
if (!success) revert TransferFailed();
```
The same pattern is used for `SweepDust` handling [2](#0-1) .

`success` here is only `true` when the external call did not revert — it says nothing about the ABI-encoded boolean the ERC20 `transfer` function returns. Per ERC20, a compliant token may legitimately return `false` on failure (insufficient balance/paused/blacklist) instead of reverting. In that case `success == true` (the call executed fine and returned `abi.encode(false)`), so `TransferFailed()` is never triggered, yet the beneficiary received zero tokens. Despite this, the contract decrements `_orders[body.commitment][token]`, marks `_filled[body.commitment] = beneficiary`, and emits `EscrowReleased`/`EscrowRefunded` as if the transfer succeeded.

This directly mirrors the `AssetManager::withdraw` bug class: a function that is supposed to move funds returns/finalizes as successful without checking that the actual transfer occurred, when partial/failed sub-transfers are possible. The canonical (non-Tron) implementation in `IntentsBase.sol` avoids this by using OpenZeppelin's `SafeERC20.safeTransfer`, which decodes and enforces the boolean return value [3](#0-2) , but the Tron variant does not use `SafeERC20` for these release paths [4](#0-3) .

### Impact Explanation
- **Permanent loss/freezing of escrowed funds**: Once `withdraw()` runs, `_filled[body.commitment]` is set and `_orders[body.commitment][token]` is decremented, marking the order as settled. If the underlying token silently returned `false`, the beneficiary (solver on a fill, or user on a refund/cancel) never receives their tokens, but the order can never be re-claimed because it is already recorded as filled/refunded and the escrow balance is already reduced. This is a direct, unrecoverable loss of user/solver funds.
- Applies to the primary escrow release path reachable from a relayed `RedeemEscrow`/`RefundEscrow` cross-chain message (`onAccept` → `withdraw`) and from `onGetResponse` (cancellation) — both single relayed-message-triggered, unprivileged-reachable paths [5](#0-4) [6](#0-5) .
- Also affects `SweepDust`, where governance-swept protocol dust could similarly "succeed" without the treasury actually receiving funds, though this path is privileged.

### Likelihood Explanation
Likelihood depends on whether any token used with the Tron IntentGatewayV2 deployment can return `false` rather than revert on transfer failure. This is a known, non-hypothetical behavior class among ERC20/TRC20 tokens (some older or non-standard tokens return `false` instead of reverting on failed transfers, e.g. due to blacklists, pauses, or insufficient balance edge cases introduced by fee-on-transfer/rebasing behavior). Given the intent gateway is designed to be permissionless as to which tokens users escrow as order inputs, exposure to such tokens is plausible and not solver/admin-gated.

### Recommendation
Replace the raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` + `success`-only check with OpenZeppelin's `SafeERC20.safeTransfer`/`safeTransferFrom` (as already used elsewhere in this same contract for `predispatch` transfers [7](#0-6)  and in `IntentsBase.sol`), so that a token returning `false` causes a revert rather than a silently "successful" no-op transfer. Apply this consistently to `withdraw()` and the `SweepDust` handler.

### Proof of Concept
1. Deploy `IntentGatewayV2` (Tron variant) with an ERC20/TRC20 token whose `transfer()` returns `false` (rather than reverting) when, e.g., the recipient is blacklisted or some internal check fails, while still allowing the call itself to complete without reverting.
2. A user places an order escrowing this token as an input [8](#0-7) .
3. A solver fills the order cross-chain; the settlement `RedeemEscrow` message is delivered via `onAccept` → `withdraw(body, false)` [9](#0-8) .
4. Inside `withdraw`, `token.call(...)` returns `success = true` (call executed) but the ABI-decoded boolean payload is `false` — no tokens are transferred to the solver.
5. `_orders[body.commitment][token] -= amount` still executes, `_filled[body.commitment] = beneficiary` is set, and `EscrowReleased` is emitted — the order is now permanently marked filled/settled with the escrow debited, while the solver's balance never changed. The tokens are stuck in the contract with no code path to reclaim them for that commitment.

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
    }
