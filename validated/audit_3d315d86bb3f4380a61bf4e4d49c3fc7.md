### Title
Webhook shop-domain header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC of the raw request body, but then hands the caller-supplied `shop`, `topic`, `api_version`, and `webhook_id` header values — none of which are covered by that HMAC — directly to the app's webhook handler as trusted identity data.

### Finding Description
`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string`, and for a webhook `Request` that method returns only the raw body: [1](#0-0) 

Meanwhile `Request#shop`, `#topic`, `#api_version`, and `#webhook_id` are all read straight from HTTP headers, which are never included in the signed content: [2](#0-1) 

`Registry.process` verifies only the HMAC and then trusts `request.shop` as the tenant identity when constructing the data passed to the app's handler: [3](#0-2) 

The broken binding, stated as an equality that the code fails to enforce:

`shop_header_used_by_handler == shop_bound_by_hmac`

is false — the HMAC only proves `raw_body` was signed with the app's `api_secret_key`; it proves nothing about which shop's header accompanies that body. Every shop that has the app installed shares the same `api_secret_key`, so any merchant who installs the app on their own store (an unprivileged internet user with no special access to the target) can trigger a legitimate webhook delivery to themselves, capture the resulting `(raw_body, x-shopify-hmac-sha256)` pair — which is valid and will pass `HmacValidator.validate` unchanged — and replay it to the app's webhook endpoint with a forged `x-shopify-shop-domain` header naming a different (victim) shop. `Registry.process` will accept it as authentic and invoke the handler with `WebhookMetadata#shop` set to the spoofed victim shop, while the body content is attacker-controlled (from the attacker's own store).

### Impact Explanation
This breaks the tenant boundary the HMAC is supposed to enforce: an app that scopes any state update, cache invalidation, notification, or webhook-triggered business logic by `WebhookMetadata#shop` (the documented/intended way to consume this field, per `docs/usage/webhooks.md`) can be made to apply attacker-controlled data to another merchant's tenant record. This is cross-tenant access/write achieved without any credential belonging to the victim, matching the Critical "cross-tenant access" impact bucket in scope.

### Likelihood Explanation
The attacker only needs to install the target app on their own shop (a normal, unprivileged action any merchant can take), receive one real webhook, and replay the captured request with a modified `shop-domain` header to the same public endpoint. No secrets, tokens, or victim-controlled material are required — only the app's publicly known webhook endpoint.

### Recommendation
Bind the shop (and ideally topic/api_version/webhook_id) header values into the HMAC-signed content, or explicitly document and enforce that `WebhookMetadata#shop` must be cross-checked by the host application against a shop that is independently known to have a valid, HMAC-legitimate installation before being trusted for any tenant-scoped action. At minimum, `to_signable_string` for webhook `Request` should incorporate the shop-domain header so `HmacValidator.validate` fails whenever that header is altered relative to the value Shopify actually signed the delivery for.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`.
2. Attacker triggers a webhook event (e.g., `orders/create`) on their own shop; Shopify delivers a POST with a valid `X-Shopify-Hmac-Sha256` computed over the raw body using the app's shared `api_secret_key`, plus `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker replays the exact same raw body and HMAC header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks the (unmodified) raw body against the secret (`lib/shopify_api/webhooks/request.rb:35-38`, `lib/shopify_api/utils/hmac_validator.rb:26-31`).
5. The handler is invoked with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: <attacker-controlled parsed body>, ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), causing the host app to process attacker data as if it belonged to `victim-shop`.
