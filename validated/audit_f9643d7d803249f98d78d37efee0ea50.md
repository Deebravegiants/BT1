## Analysis

The reported bug class — computing a "swap/transfer amount" from `balanceOf(contract)` (the contract's **total** balance) instead of the delta actually produced by the intended operation — has a direct analog in Hyperbridge's `IntentGatewayV2` predispatch-sweep logic, most clearly in the Tron variant.

### Title
Escrow funding relies on `CallDispatcher`'s total token balance instead of the delta produced by `order.predispatch.call`, allowing residual/pre-existing balances to satisfy a caller's funding requirement - (`evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`placeOrder`'s predispatch path funds an order's escrow by checking `IERC20(token).balanceOf(dispatcher)` against `requiredAmount` and sweeping the *entire* balance back to the gateway, rather than measuring the amount actually produced by that specific call's `predispatch.call`. Any token balance already sitting on the shared `CallDispatcher` — from an earlier order's un-swept byproduct tokens, a stuck/failed sweep, or tokens simply sent to the dispatcher — is silently absorbed into whichever `placeOrder` call happens to run next, exactly the "use of total contract balance instead of the delta that should be used" pattern flagged in the USSD report.

### Finding Description
In `placeOrder` (Tron variant), for the predispatch branch: [1](#0-0) 

```solidity
for (uint256 i; i < inputsLen;) {
    ...
    balance = IERC20(token).balanceOf(dispatcher);
    if (balance < requiredAmount) revert InvalidInput();
    transferCalls[i] = Call({..., data: abi.encodeWithSelector(IERC20.transfer.selector, address(this), balance)});
    ...
    uint256 dust = balance - requiredAmount;
    if (dust > 0) emit DustCollected(token, dust);
    _orders[commitment][token] += reducedInputs[i].amount;
    ...
}
```

`balance` is the dispatcher's *absolute* balance at the time of the check, not a before/after delta isolating what `ICallDispatcher(dispatcher).dispatch(order.predispatch.call)` (line 414) actually produced for *this* order. The loop only sweeps tokens that appear in `order.inputs` — any other token type the predispatch call produces as a byproduct (e.g. swap dust, multi-hop leftovers) stays parked on the dispatcher indefinitely, because nothing tracks "pre-existing balance" vs "balance this order is entitled to."

The nominally-fixed EVM mainline version (`evm/src/apps/IntentGatewayV2.sol`) added a gateway-side before/after snapshot for the *receiving* side: [2](#0-1) 

but it still performs the identical absolute-balance read and check on the *source* side (the dispatcher): [3](#0-2) 

```solidity
uint256 balance = IERC20(token).balanceOf(dispatcher);
if (balance < requiredAmount) revert InvalidInput();
```

So the same root defect — no delta isolation of the dispatcher's balance attributable to *this* transaction's `predispatch.call` — exists in both files; the Tron file additionally lacks the gateway-side delta protection entirely, making it the more direct analog of the reported issue.

### Impact Explanation
Because the `requiredAmount` check only demands that the dispatcher's *total* balance be sufficient, a caller can satisfy an order's funding requirement using tokens that were never generated by their own `predispatch.call` — for example, byproduct tokens left behind by an earlier, unrelated order's swap (since only tokens present in `order.inputs` get swept, any other output token type is stranded on the dispatcher). A subsequent caller whose `order.inputs` happens to include that stranded token type can pass the `balance >= requiredAmount` check while supplying a smaller or cheaper `predispatch.assets`/`predispatch.call`, effectively funding their escrow with value that belonged to a prior, unrelated transaction. This is fund misdirection through the shared `CallDispatcher`: value that should have been returned/refunded to its rightful depositor (or remained available for future sweep) is instead consumed to fund a different user's order commitment, which can result in permanent loss/freezing of the original depositor's funds and unearned escrow funding for the attacker.

### Likelihood Explanation
The dispatcher (`_params.dispatcher`) is a single shared, permissionless contract that any user can target with an arbitrary `predispatch.call` and `predispatch.assets` in a single `placeOrder` transaction — this is fully reachable by any unprivileged caller submitting an ordinary transaction, no special role or governance action required. The only prerequisite is that a residual balance of a token later included in an attacker-crafted `order.inputs` exists (or is created) on the dispatcher — achievable by choosing a predispatch call whose swap path naturally leaves byproducts, or by observing/waiting for such residue from other traffic.

### Recommendation
Snapshot the dispatcher's per-token balance *before* executing `order.predispatch.call`, and use `balanceOf(dispatcher) - balanceBefore` (the delta actually produced by this specific call) as `balance`/`requiredAmount` comparison and as the swept amount, mirroring the delta-based approach already used on the gateway-receiving side in `evm/src/apps/IntentGatewayV2.sol`. Any leftover token types not part of `order.inputs` should be swept back to their original depositor (or explicitly tracked as protocol dust with an owner-only sweep), never silently absorbed by an unrelated subsequent order.

### Proof of Concept
1. User A calls `placeOrder` with a `predispatch.call` that swaps token X for token Y through a DEX, but `order.inputs` only lists token X's output — token Y byproducts remain un-swept on `dispatcher`.
2. Attacker observes (or engineers) this residual token-Y balance sitting on the shared `dispatcher`.
3. Attacker calls `placeOrder` with `order.inputs` including token Y with `amount = requiredAmount` set to (or below) the residual balance, and a `predispatch.call` that produces little or no actual token Y (a cheap/no-op call).
4. `balance = IERC20(tokenY).balanceOf(dispatcher)` includes User A's stranded residue, passes `balance >= requiredAmount`, and the full balance is swept to the gateway and credited toward the attacker's escrow (`_orders[commitment][tokenY] += reducedInputs[i].amount`), while the attacker never supplied the equivalent value themselves.
