Confirmed: `ShopValidator.sanitize!` is used in `token_exchange.rb`, `client_credentials.rb`, and `refresh_token.rb`, but it is **not** used anywhere in `lib/shopify_api/auth/oauth.rb`. This confirms `begin_auth` and `validate_auth_callback` never sanitize the `shop` value before using it to construct the host that receives the app's `client_secret`.

### Title
OAuth flow sends `client_secret` to an unvalidated `shop` host, enabling SSRF/credential exfiltration - (File: lib/shopify_api/auth/oauth.rb)

### Summary
`ShopifyAPI::Auth::Oauth.begin_auth` and `ShopifyAPI::Auth::Oauth.validate_auth_callback` both derive the destination host for OAuth requests directly from the caller-supplied `shop` string, without ever passing it through `ShopifyAPI::Utils::ShopValidator.sanitize!`. As a result, the app's `client_secret` can be sent to a host that is not a genuine Shopify domain.

### Finding Description
The report's bug class is "action taken on a field that is not properly bound/validated to the expected identity" — here, the identity that should be bound is "the host that receives the app's `client_secret`" versus "a verified Shopify shop domain."

In `begin_auth`, the `shop` parameter is used unsanitized to build the authorization URL: [1](#0-0) 
`auth_base_uri(shop)` builds `"https://#{shop}/admin"` directly from the caller-supplied string with no domain validation.

In `validate_auth_callback`, the flow is worse because the `shop` value there comes from `auth_query.shop`, which is only checked via HMAC (proving it was signed with `api_secret_key`, i.e., that the *query parameters are internally consistent*), not that `shop` is a `*.myshopify.com` (or other trusted Shopify) domain: [2](#0-1) 
The `null_session` is built from `auth_query.shop` and used to instantiate `Clients::HttpClient` with `base_path: "/admin/oauth"`. That client's `auth_base_uri`-equivalent path resolution ultimately issues a POST to `https://#{shop}/admin/oauth/access_token` carrying `client_id` and `client_secret` in the body — sent to whatever host `shop` resolves to.

By contrast, other OAuth-adjacent flows in the same gem do enforce this binding: `token_exchange.rb`, `client_credentials.rb`, and `refresh_token.rb` all call `ShopValidator.sanitize!` before using the shop value, and `ShopValidator` itself is designed exactly for this purpose — restricting shop values to `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`): [3](#0-2) [4](#0-3) 

`oauth.rb` is the one auth entry point in the library that omits this call entirely — confirmed by the absence of `ShopValidator` in that file, unlike the three sibling files.

### Impact Explanation
If the host application passes an attacker-influenced `shop` value into `begin_auth` (e.g., taken from an unauthenticated install-initiation request query string, which is common in Shopify app installation flows) or if `auth_query.shop` is otherwise attacker-influenced upstream, the gem will send the app's `client_id`/`client_secret` to an arbitrary attacker-controlled host during the `access_token` exchange POST. This is SSRF carrying the app's credentials to a non-Shopify host — meeting the "High: SSRF with the app's credentials" impact bar defined in scope. It can also lead to leakage of the app's `client_secret` if the attacker-controlled endpoint logs or reflects the POST body.

### Likelihood Explanation
Likelihood depends on the host application forwarding an unvalidated `shop` string into `begin_auth`/`validate_auth_callback`, which is a realistic integration pattern since many Shopify app install flows read `shop` straight from the initial unauthenticated request query parameters, exactly as documented in `docs/usage/oauth.md`. The gem provides no defense-in-depth here, unlike its sibling OAuth flows, so any host app that doesn't add its own separate validation is exposed.

### Recommendation
Call `ShopValidator.sanitize!(shop)` (or `sanitize_shop_domain`) at the start of `begin_auth` and on `auth_query.shop` at the start of `validate_auth_callback` in `lib/shopify_api/auth/oauth.rb`, mirroring the pattern already used in `token_exchange.rb`, `client_credentials.rb`, and `refresh_token.rb`, before the value is used to build `auth_base_uri` or to construct the `HttpClient`/`null_session` that sends the `client_secret`.

### Proof of Concept
1. Host app calls `ShopifyAPI::Auth::Oauth.begin_auth(shop: params[:shop], redirect_path: ...)` where `params[:shop]` is taken unauthenticated from the install URL (a common pattern shown in the gem's own docs).
2. Attacker sets `shop=attacker-controlled-host.example.com` (or a value that resolves via DNS to an attacker server).
3. `auth_base_uri(shop)` builds `"https://attacker-controlled-host.example.com/admin"`, and the resulting authorize URL is returned to the browser/redirected to.
4. If the attacker's server can also complete a callback with a valid-looking `code`/`state` and a self-signed HMAC is bypassed (or an SSRF-only PoC is used against `begin_auth` alone, which is sufficient to demonstrate the missing validation), the subsequent `validate_auth_callback` again uses the same unsanitized `shop` to POST `client_id`+`client_secret` to `https://attacker-controlled-host.example.com/admin/oauth/access_token`, exfiltrating the app's `client_secret` to the attacker's server.           end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state

          null_session = Auth::Session.new(shop: auth_query.shop)
          body = {
            client_id: Context.api_key,
            client_secret: Context.api_secret_key,
            code: auth_query.code,
            expiring: Context.expiring_offline_access_tokens ? 1 : 0, # Only applicable for offline tokens
          }

          client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
          response = begin
            client.request(
              Clients::HttpRequest.new(
                http_method: :post,
                path: "access_token",
                body: body,
                body_type: "application/json",
              ),
            )
          rescue ShopifyAPI::Errors::HttpResponseError => e
            raise Errors::RequestAccessTokenError,
              "Cannot complete OAuth process. Received a #{e.code} error while requesting access token."
          end
