### Title
Pause is not synchronized across `HyperFungibleToken`/`WrappedHyperFungibleToken` peers, letting activity continue on unpaused chains after an incident - (File: `sdk/packages/core/contracts/apps/HyperFungibleToken.sol`, `sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol`)

### Summary
`HyperFungibleToken` (burn/mint, deployed on every remote chain) and `WrappedHyperFungibleToken` (lock/unlock, deployed on the home chain) are peer contracts for the same fungible asset, but each maintains its own independent, owner-controlled `Pausable` state with no mechanism to propagate a pause across the topology, mirroring the reported L1/L2 Eco pause-incompatibility bug class.

### Finding Description
`HyperFungibleToken.pause()`/`unpause()` only flips that single contract's local `Pausable` flag via `onlyOwner`, gating `send()`, `onAccept()`, and `onPostRequestTimeout()` on that one deployment. [1](#0-0) 
The same independent pattern is duplicated in `WrappedHyperFungibleToken`, which locks/unlocks the underlying escrowed asset on the home chain. [2](#0-1) 
Both `send()` and `onAccept()` are only gated by that local `whenNotPaused` modifier, and `send()` is callable by any token holder (no privileged role) to burn/lock their own balance and dispatch a cross-chain transfer. [3](#0-2) 
There is no ISMP governance instruction, no `Nexus`/host-relayed message, and no shared config that broadcasts a pause from one deployment to its registered peers on other chains — the docs explicitly describe pause as a per-contract, owner-only switch with no cross-chain propagation. [4](#0-3) 
This is the same root cause pattern as the reported issue: the home/lock side (analogous to L1 ECO) and the remote/burn-mint side (analogous to L2 ECO) can be paused independently and out of sync, so pausing the compromised deployment does nothing to stop `send()`/`onAccept()` continuing to execute on every other peer deployment of the same asset.

### Impact Explanation
If an operator pauses one deployment in response to an incident (e.g. a compromise of the home-chain escrow backing `WrappedHyperFungibleToken`, or a bug discovered in one remote `HyperFungibleToken` deployment), every other peer deployment for the same asset on other chains remains fully operational: unprivileged holders can keep calling `send()` to burn/lock and `onAccept` continues minting/unlocking on delivery of any message already dispatched (or dispatched via any peer that has not yet been paused). Since each `HyperFungibleToken`/`WrappedHyperFungibleToken` pair represents one fungible asset across many chains, this breaks the intended invariant that the asset's supply is safely haltable during an incident, enabling continued token movement/supply manipulation on chains where the token may be used as collateral elsewhere, exactly the price-manipulation/other-issue impact described in the source report.

### Likelihood Explanation
No attacker privilege is required to keep triggering `send()`/`onAccept` on an unpaused peer chain — it is the default, unprivileged path used by every legitimate transfer. The only requirement is that an incident occurs on one deployment while its peers remain unpaused, which is the expected operational reality given pause is enforced per-contract by a per-chain owner with no synchronization tooling.

### Recommendation
Add a cross-chain pause-propagation mechanism (e.g. dispatch a pause/unpause ISMP message to all registered peers when `pause()`/`unpause()` is called, or gate `send()`/`onAccept()` on a globally-replicated frozen flag similar to `EvmHost.setFrozenState`) so pausing any one deployment of an asset reliably halts `send()` and `onAccept()` on all of its registered peers until explicitly resumed.

### Proof of Concept
1. Deploy `WrappedHyperFungibleToken` on chain A (home) and `HyperFungibleToken` on chains B and C (remote), registered as peers via `addChain`.
2. An incident occurs affecting chain A's escrow; the owner calls `WrappedHyperFungibleToken.pause()` on chain A. [5](#0-4) 
3. `send()`/`onAccept` on the chain B and C `HyperFungibleToken` deployments are unaffected — any holder can still call `send()` to burn on chain B/C and dispatch a transfer, and any in-flight/new message can still be delivered via `onAccept` on chain B/C, because those deployments track a wholly separate `Pausable` state. [6](#0-5) 
4. This confirms the pause on the home/escrow deployment does not stop token movement on the peer burn/mint deployments, matching the reported L1/L2 pause-incompatibility bug class.

## Pausability

Both contracts inherit from OpenZeppelin's `Pausable`. The owner can pause and unpause all operations:

```solidity lineNumbers
IHyperFungibleToken(tokenAddress).pause();
IHyperFungibleToken(tokenAddress).unpause();
```

When paused, `HyperFungibleToken` blocks all ERC20 transfers (`transfer` and `transferFrom`) in addition to cross-chain `send()` and `onAccept()`. This is a full stop on all token movement — use it for emergency situations or during migrations.
