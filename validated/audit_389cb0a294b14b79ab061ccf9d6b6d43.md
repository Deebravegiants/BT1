### Title
Unbounded swap routes can piggyback unauthorized wallet transfers on a signed strategy call - (File: contracts/controller/src/strategies/swap.rs)

### Summary

`swap_collateral` and the other router-backed strategy entrypoints accept caller-supplied route bytes and invoke the configured router inside the caller’s authorization tree. A malicious route can name an attacker-controlled venue that performs an unrelated `token.transfer(victim, attacker, amount)`. Soroban simulation records that transfer as a child of the victim’s controller authorization; if the victim signs the simulated tree, the wallet transfer executes even though the protocol’s own input/output accounting remains correct. The in-repo adversarial test demonstrates complete theft of an unrelated wallet token through `swap_collateral`. [1](#0-0) 

### Finding Description

The controller accepts opaque `swap` bytes, snapshots only the swap input and output tokens held by the controller, authorizes the expected `token_in.transfer(controller, router, amount_in)`, and then calls `router.execute_strategy(controller, amount_in, swap)`. [2](#0-1) 

After execution it checks only that the controller did not gain input tokens, did not spend more than `amount_in`, and received positive `token_out`. [3](#0-2) 

These checks do not bound what other authorization-sensitive calls a routed venue adds beneath the victim’s top-level authorization. The harness registers a route containing a malicious pool whose `swap` function calls `token.transfer(victim, attacker, WALLET_BALANCE)` for an unrelated token. [4](#0-3) 

Simulation records the rogue transfer as a sub-invocation of the victim’s `swap_collateral` authorization. [1](#0-0) 

The host correctly rejects the transfer when the victim signs only the honest root authorization, but executes it when the victim signs the poisoned simulated tree. [5](#0-4) 

### Impact Explanation

A successful route can steal tokens from the victim’s wallet that were never deposited into or listed by the protocol. The demonstrated path drains `WALLET_BALANCE` units of a separate asset to the attacker while still depositing the expected fair swap output into the victim’s lending account. [6](#0-5) 

This is theft of user funds and is not limited to the strategy’s input amount, because the measured router-output and final-account checks only observe the controller’s balances. [3](#0-2) 

### Likelihood Explanation

Exploitation requires the victim to authorize a malicious route, normally after a malicious interface or quote presents the simulated authorization tree for signing. That makes the attack contingent on deception or insufficient client-side authorization review rather than unilateral theft from an inactive wallet.

The probability is nevertheless material because the route is opaque bytes, the protocol accepts it as a strategy argument, and the poisoned child authorization can be generated by ordinary simulation. [1](#0-0) 

### Recommendation

Do not allow opaque strategy routes to name arbitrary executable venue contracts without a protocol-controlled allowlist. Bind each route hop to a governance-approved pool or venue deployment, reject unknown pool addresses before execution, and make clients reject any signed authorization tree containing calls beyond the expected strategy and token-input transfer.

If arbitrary pools are required, introduce a router authorization boundary or route-manifest validation that prevents venue code from inheriting the end user’s authorization context; balance checks alone are insufficient.

### Proof of Concept

1. Victim owns a normal account with supplied USDC collateral and holds an unrelated `wallet_token`.
2. Attacker deploys a contract exposing the expected pool `swap()` ABI. Inside `swap()`, it calls `wallet_token.transfer(victim, attacker, wallet_balance)`.
3. Attacker constructs a route whose hop pool is that malicious contract while presenting a fair USDC-to-ETH swap result.
4. Victim calls:

   `controller.swap_collateral(victim, account_id, usdc_hub_asset, 50_000_000_000, eth_hub_asset, malicious_route)`

5. During simulation, the rogue wallet-token transfer is recorded as a child of the victim’s `swap_collateral` authorization. [1](#0-0) 
6. If the victim signs that simulated tree, `swap_collateral` succeeds, the victim receives the expected collateral output, and the attacker receives the unrelated wallet token. [6](#0-5)

#[test]
fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
