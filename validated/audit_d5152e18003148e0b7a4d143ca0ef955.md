This confirms the vulnerability path: `Registry.process` (`lib/shopify_api/webhooks/registry.rb:189-199`) only validates `Utils::HmacValidator.validate(request)` against `request.to_signable_string` (the raw body), then unconditionally trusts `request.shop`, `request.topic`, and `request.webhook_id` — all parsed straight from HTTP headers — to build the `WebhookMetadata` struct passed to the app's handler.

### Title
Webhook shop/topic/webhook-id headers are trusted without HMAC coverage, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content solely from the raw request body [1](#0-0) , while `shop`, `topic`, `api_version`, and `webhook_id` are read directly from HTTP headers with no cryptographic binding to the signature [2](#0-1) . `Registry.process` validates only the body HMAC and then blindly attributes the request to whatever `shop` header was supplied when constructing `WebhookMetadata` for the handler [3](#0-2) .

### Finding Description
The identity binding that should hold is: `hmac_verified(shop_header) == shop_header_used_by_handler`. In this gem that equality never holds, because the HMAC only covers `@raw_body` [4](#0-3)  — the `shop-domain`, `topic`, and `webhook-id` headers are excluded from `to_signable_string` entirely [5](#0-4) .

Shopify signs webhooks using the app's `client_secret` (`Context.api_secret_key`), and this same secret is used for **every shop that installs the app**, not a per-shop key [6](#0-5) . Consequently, a malicious merchant who installs the victim's app on their own store can legitimately trigger a webhook delivery and capture a valid `(raw_body, hmac)` pair signed with the app's shared secret. Because the header fields are never part of the signed content, that attacker can replay the exact same body and HMAC directly to the app's public webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header naming a different, victim shop. `HmacValidator.validate` will still pass, since it only re-computes the HMAC over `raw_body` [7](#0-6) , and `Registry.process` will hand the forged `shop` straight into the app's `WebhookHandler#handle` via `WebhookMetadata` [8](#0-7) .

### Impact Explanation
This crosses a tenant boundary: an attacker who only controls their own shop's app installation can forge webhook events that the host application will process as if they originated from any other shop (e.g., injecting fabricated `orders/create`, `app/uninstalled`, or GDPR `customers/redact` payloads attributed to a victim's `shop` domain). Depending on how the host app keys its data/session lookups off `WebhookMetadata#shop`, this enables cross-tenant data corruption or spoofed lifecycle events for shops the attacker does not own.

### Likelihood Explanation
Exploitation only requires installing the target app on an attacker-controlled shop (a normal, unprivileged action) to obtain one valid `(body, hmac)` pair, and the ability to send an arbitrary HTTP POST to the app's public webhook endpoint (no interception, no secret, no privileged account needed). This is well within reach of any internet user who can install a public app.

### Recommendation
Bind the header-derived identity fields into the signed content, or otherwise cryptographically verify that `shop`, `topic`, and `webhook_id` are consistent with the signed body — e.g., include them in `to_signable_string`, or require the host application to cross-check `request.shop` against a shop known to have installed the app via a separately verified channel before trusting `WebhookMetadata#shop`. At minimum, document that `shop`/`topic`/`webhook_id` headers are unauthenticated and must not be trusted for authorization decisions.

### Proof of Concept
1. Attacker installs the vulnerable app on `attacker.myshopify.com` and lets Shopify deliver a legitimate webhook (e.g., `orders/create`) to the app's endpoint, capturing the raw body `B` and the valid `X-Shopify-Hmac-Sha256` header `H` (computed with the app's shared `client_secret`).
2. Attacker sends a direct POST to the same webhook endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` (unchanged, still valid since it only covers `B`), but `X-Shopify-Shop-Domain: victim-shop.myshopify.com` and any desired `X-Shopify-Topic`/`X-Shopify-Webhook-Id`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `raw_body` against `H` [9](#0-8) .
4. The handler receives `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` with `shop == "victim-shop.myshopify.com"` [10](#0-9) , even though the payload actually originated from the attacker's own shop.
