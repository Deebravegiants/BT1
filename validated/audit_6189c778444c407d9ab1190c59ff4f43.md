### Title
Native-token overpayment to `EvmHost.dispatch()`/`fundRequest()` is permanently trapped in the contract instead of being refunded to the caller - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` accept native token payment and swap it for the exact `feeToken` amount required via Uniswap V2's `swapETHForExactTokens`. The router refunds any unspent ETH to its immediate caller — `EvmHost` itself — but `EvmHost` never forwards that refund back to the original `msg.sender`/app that funded the call. Any native token sent above what the swap actually consumes is silently absorbed by `EvmHost` and lost to the caller, exactly like the referenced Allo `_createPool` issue where a surplus of sent value is not returned to the sender.

### Finding Description
In `EvmHost.sol`, the POST/GET dispatch functions and `fundRequest` do the same pattern: [1](#0-0) [2](#0-1) [3](#0-2) 

In each case, `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(exactAmountNeeded, path, address(this), ...)` is invoked. Uniswap V2's canonical implementation only spends `amounts[0] <= msg.value` and refunds `msg.value - amounts[0]` back to `msg.sender` of that call — i.e., back to `EvmHost`, not to the original transaction sender or calling contract. `EvmHost` has no logic afterward to compute this delta and forward it to `_msgSender()`/`post.payer`/`get.payer`; the refunded ETH simply becomes part of the Host's own balance.

This is exactly the bug class in the reference report: the caller must send the *exact* required native amount (impossible to know precisely on-chain due to AMM price movement between quoting and execution), and any conservative overpayment (a common and expected pattern, since callers typically add slippage buffer) is permanently lost. Contrast this with `IntentGatewayV2.placeOrder()`, which explicitly tracks `msgValue -= amounts[0]` and refunds the remainder to `msg.sender`: [4](#0-3) 

This shows the codebase is aware refunding leftover native value is required, yet `EvmHost.sol`'s own `dispatch`/`fundRequest` paths — which are directly callable by any unprivileged EOA or app contract dispatching a POST/GET request or funding a pending request — omit this refund entirely.

### Impact Explanation
Any unprivileged caller (message dispatcher, app contract, or relayer funding a request) who sends native token value to `EvmHost.dispatch()` or `EvmHost.fundRequest()` in excess of the amount actually consumed by the Uniswap swap permanently loses that surplus — it becomes stranded in the `EvmHost` contract with no code path to return it to the sender. Since callers cannot predict the exact AMM execution price at call time (it depends on pool state at the moment of the swap) and typically must pad `msg.value` to avoid reverts from price movement/slippage, this loss is essentially unavoidable for any caller using native-token payment and directly impacts end users/integrators funds (concrete loss of funds), matching the Medium severity of the original report.

### Likelihood Explanation
High likelihood: this is the default, documented way to pay for dispatch/fundRequest with native tokens (per the function NatSpec: "Payment for the request can be made with either the native token or the feeToken... If native tokens are supplied, it will perform a swap"), so every caller using the native-token path is exposed. No malicious actor or privileged role is needed — the loss occurs on ordinary usage the moment a caller sends slightly more ETH than the swap consumes, which is the normal/expected practice.

### Recommendation
After the `swapETHForExactTokens` call in `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()`, capture the `amounts[0]` actually spent (the first return value) and refund `msg.value - amounts[0]` back to `_msgSender()` (or the designated payer), mirroring the pattern already used in `IntentGatewayV2.placeOrder()`:
```solidity
uint256[] memory amounts = IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
    post.fee, path, address(this), block.timestamp
);
if (msg.value > amounts[0]) {
    (bool sent, ) = _msgSender().call{value: msg.value - amounts[0]}("");
    require(sent, "refund failed");
}
```

### Proof of Concept
1. Configure `EvmHost` with a Uniswap V2 router and `feeToken`.
2. A user/app calls `EvmHost.dispatch(DispatchPost)` (or `DispatchGet`, or `fundRequest`) with `msg.value` intentionally padded above the current spot-price cost of `post.fee` feeToken units (as any prudent caller would do to avoid reverts from slippage/price movement between quote time and execution time).
3. Internally, `swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), ...)` only spends `amounts[0] < msg.value`; the Uniswap router refunds `msg.value - amounts[0]` to `address(this)` (`EvmHost`).
4. `EvmHost` does not forward this refund to the caller — the excess ETH remains in `EvmHost`'s balance permanently, with no observable event or accounting entry crediting it back to the caller.
5. Result: the caller's overpaid ETH is irrecoverably lost, confirmed by comparing caller balance before/after against `amounts[0]` actually needed (as demonstrated for the analogous, correctly-handled case in `IntentGatewayV2Test.testPlaceOrder_FeeSwap_RefundsExcessNativeToken`, which explicitly asserts a refund occurs there but no equivalent refund/test exists for `EvmHost.dispatch`/`fundRequest`).
