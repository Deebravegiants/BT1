### Title
Whale-scale market accrual permanently freezes the market via `MathOverflow` in `scaled_to_original` — all repay/withdraw/liquidate paths revert - (File: common/src/rates/scaling.rs)

### Summary
CVE-2020-2898 is a complete-DOS class bug (unauthenticatedly reachable hang/crash of the service). The analog on XOXNO Lending is a permanent, irrecoverable freeze of an entire pool market: once a market's scaled `borrowed` (or `supplied`) RAY value times the growing index exceeds `i128`, `interest::global_sync` panics inside `scaled_to_original` on **every** verb — `supply`, `borrow`, `withdraw`, `repay`, `seize_positions`, `net_settle`, `claim_revenue`, `recapitalize`, and `update_indexes` itself — because every pool mutation accrues first (`Cache::load → interest::global_sync → mutate`, contracts/pool/README.md). A single unprivileged address can set the condition up entirely through `controller::supply` + `controller::borrow`: supply a whale-sized position on a high-decimals market and borrow near max utilization on a steep curve so index growth drives the debt value past the representable bound.

### Finding Description
- `scaled_to_original` is `scaled.mul(env, index)` and panics on `i128` overflow (common/src/rates/scaling.rs:14-16).
- Accrual computes `utilization` from `scaled_to_original(borrowed, borrow_index)` and `scaled_to_original(supplied, supply_index)` each chunk (common/src/rates/simulate.rs:160-168; mirrored in `accrue_step`), so once `scaled × index > i128::MAX` the next accrual panics with `GenericError::MathOverflow`.
- `interest::global_sync` runs unconditionally at the head of every market mutation (contracts/pool/src/interest.rs:20-33), so the panic bricks the market.
- The index ceiling does **not** protect against this: `MAX_BORROW_INDEX_RAY = 1e36` only caps the index itself, while the overflowing term is `scaled_amount × index`, which is unbounded in the scaled amount. The protocol's own test confirms the order of failure: `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` shows `update_indexes`, `withdraw`, and `repay` all reverting with `MATH_OVERFLOW` while `borrow_index < MAX_BORROW_INDEX_RAY` (tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:316-360). The invariants doc acknowledges "Debt-value overflow can still revert accrual before that ceiling is reached" (docs/reference/invariants.md, INV-IDX-01), i.e. the bound is documented but the freeze outcome is not mitigated.

### Impact Explanation
Permanent freezing of funds (accepted impact). After the cliff, suppliers cannot withdraw, borrowers cannot repay, liquidators cannot liquidate (liquidation also accrues first), `clean_bad_debt`/`seize_positions` cannot socialize the loss, and `recapitalize` — the documented recovery path for under-backed markets — reverts too, since it is a market mutation. Every token held as cash in that market's book is frozen forever; the bad debt cannot even be written down. The companion view `get_bulk_indexes`/`simulate_update_indexes` also panics, breaking integrators.

### Likelihood Explanation
Medium, consistent with the source CVE's 4.9. No privileged access is needed — `supply`/`borrow`/`update_indexes` are reachable by any account — but the trigger requires (a) a listed market with high token decimals and a curve allowing sustained high utilization (the test uses an 18-decimal asset at 98% utilization on the XLM curve), and (b) multi-year accrual at high utilization before the ceiling `i128` debt value is crossed (~170× index growth in the harness). An attacker can front the capital, or the condition can arise organically; either way there is no recovery transaction once crossed. Governance cannot fix it via `update_params` either, since that path also accrues first (contracts/pool/src/lib.rs:115-117).

### Recommendation
- In `accrue_step`/`scaled_to_original`, saturate or clamp `borrowed`/`supplied` RAY values (or the resulting debt value) rather than letting `Ray::mul` panic, mirroring how `update_borrow_index` caps at `MAX_BORROW_INDEX_RAY`.
- Alternatively cap per-market scaled positions at listing/accrual time so `scaled × MAX_*_INDEX_RAY` always fits `i128` — `require_cap_within_asset_domain` already bounds caps; enforce the same bound on live scaled totals.
- At minimum, give `recapitalize` and the bad-debt seizure path an accrual-free escape so the market can be wound down after the cliff.

### Proof of Concept
The harness test is the PoC (tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:316-360):

```rust
// 18-decimal market on the XLM curve, caps lifted, max_utilization disabled
let principal = BILLION * 10i128.pow(18);
t.supply_raw(BOB, "BIG18", principal);          // unprivileged supply
let debt = principal / 100 * 98;
t.borrow_raw(ALICE, "BIG18", debt);             // unprivileged borrow @98% util

// advance years; eventually:
assert_contract_error(t.try_update_indexes_for(&["BIG18"]), errors::MATH_OVERFLOW);
assert!(last.borrow_index < MAX_BORROW_INDEX_RAY); // index cap never engaged
// permanent freeze:
assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
```

Root cause chain: `controller::update_indexes`/any verb → `pool::update_indexes` → `interest::global_sync` → `accrue_step` → `scaled_to_original(borrowed, borrow_index)` → `Ray::mul` → `panic_with_error!(MathOverflow)` (common/src/rates/scaling.rs:14-16, common/src/rates/compound.rs:41).

Caveat: this overflow cliff is partially documented (INV-IDX-01, the harness test's comment about the formulas.md bound), which may make it a known accepted limitation; it is reported here because the outcome — permanent, unrecoverable freezing of all funds in the market — matches the accepted impact list and is reachable by unprivileged entrypoints.
