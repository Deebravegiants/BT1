### Title
Webhook HMAC only covers the raw body — `shop-domain`, `topic`, and `webhook-id` headers are unauthenticated, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its signable content from the raw body only, and `Registry.process` accepts any request whose HMAC matches that raw body — regardless of which `shop-domain`/`topic`/`webhook-id` headers are attached to it. This breaks the identity binding `hmac_computed(secret, raw_body) == hmac_received` **into** the effectively-used binding `hmac_computed(secret, raw_body) == hmac_received AND (shop, topic, webhook_id are trusted verbatim)`, when in fact `shop`, `topic`, and `webhook_id` are never part of the signed material.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are all read directly from unauthenticated headers with no cryptographic binding to the body or to each other: [2](#0-1) 

`HmacValidator.validate` only checks `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)`, i.e. HMAC(secret, raw_body): [3](#0-2) 

`Registry.process` only asserts this body-only HMAC before dispatching to the app's handler with the attacker-controlled `shop` value baked into `WebhookMetadata`: [4](#0-3) [5](#0-4) 

The gem's own documentation instructs host apps to trust `data.shop` as "the shop domain of the webhook" and use it to key business logic (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`): [6](#0-5) 

Because the HMAC only proves "this body was produced/blessed by the app's `client_secret` owner for *some* delivery," and never proves *which* shop, topic, or webhook id it belongs to, any actor who can obtain one genuinely-signed `(body, hmac)` pair — for example, by operating (or trialing) their own store that has this same app installed and receiving that app's real webhooks — can replay that exact `(raw_body, hmac)` pair to the app's public webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header (a victim tenant) and/or a different registered `x-shopify-topic`/`webhook-id`. The HMAC check in `HmacValidator.validate` still passes because it is blind to headers, and `Registry.process` forwards the forged `shop` value straight into the handler as ground truth.

This is the equality-breaking analog called out in the rules: a field (`shop`, `topic`, `webhook_id`) is acted upon by the host application but is not covered by the HMAC that is supposed to authenticate the request.

### Impact Explanation
This crosses a tenant boundary: an attacker without any app-secret or elevated privileges can cause the app to process attacker-chosen (but real, HMAC-valid) webhook payloads under an arbitrary victim shop's identity, or re-attribute one topic's data as another registered topic. Any app logic that keys per-tenant state, triggers per-tenant side effects (e.g., updating billing, inventory, order records, or issuing an action against the "originating" shop) based on `WebhookMetadata#shop`/`#topic` is directly exposed to cross-tenant data injection/impersonation — this satisfies the "cross-tenant access" Critical impact category.

### Likelihood Explanation
The attacker needs only one legitimately-signed `(raw_body, hmac)` pair from a webhook delivered to a store they control (trivially obtainable — any developer/merchant with a test store using the same app receives real webhooks with valid HMACs), and the app's public webhook endpoint URL (typically documented/predictable, e.g. `/callback/orders/create`). No access token, `api_secret_key`, or privileged account is required. The only constraint is that the replayed body content is whatever was in the attacker's own legitimate webhook (they cannot forge arbitrary body content), which still allows meaningful cross-tenant confusion (e.g., replaying their own `orders/create` body but claiming it belongs to a victim `shop-domain`).

### Recommendation
Bind `shop`, `topic`, and `webhook_id` into the material that `HmacValidator` verifies (or require the host application to independently re-verify that the `shop-domain` header corresponds to a session/shop it actually has webhooks registered for), instead of trusting these headers as unauthenticated metadata alongside a body-only HMAC.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and registers/receives a real webhook, e.g. `orders/create`, capturing the raw POST body `B` and the valid header `x-shopify-hmac-sha256: H` (computed by Shopify as `HMAC-SHA256(client_secret, B)`).
2. Attacker sends a new POST request directly to the app's public webhook endpoint with:
   - body: `B` (unchanged)
   - `x-shopify-hmac-sha256: H` (unchanged, still valid because HMAC only covers `B`)
   - `x-shopify-shop-domain: victim-shop.myshopify.com` (forged)
   - `x-shopify-topic: orders/create` (unchanged or swapped to another registered topic)
3. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` and matches `H` — validation passes: [7](#0-6) 
4. The handler executes with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, i.e., the app now processes attacker-supplied order data as if it belonged to the victim shop.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
