Confirmed: `WrappedHyperFungibleToken` has no admin sweep/recovery function for any surplus balance — unlike `IntentGatewayV2`, which already implements `DustCollected`/`DustSwept` governance recovery for exactly this class of stray-balance issue.

### Title
Rebasing/interest-bearing underlying tokens permanently lock accrued balance in `WrappedHyperFungibleToken` - (File: sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol)

### Summary
`WrappedHyperFungibleToken` custodies an arbitrary ERC20 `_underlying` by locking exact amounts via `safeTransferFrom` on `send()` and releasing exact amounts via `safeTransfer` on `onAccept`/`onPostRequestTimeout`. It never tracks a running internal accounting variable analogous to Allo's `poolAmount` — instead it moves and unlocks *exactly* the `message.amount` recorded in each cross-chain message. If `_underlying` is a rebasing token (e.g., an aToken) or the contract otherwise receives non-message-driven inflows (interest accrual, airdrops), that surplus balance is never referenced by any code path and has no owner-callable recovery function.

### Finding Description
`send()` locks tokens 1:1 with the message amount: [1](#0-0) . On the receiving side, `onAccept` unlocks exactly `message.amount` to the beneficiary: [2](#0-1) , and `onPostRequestTimeout` refunds exactly `message.amount` back to the sender: [3](#0-2) .

None of these paths read or credit `IERC20(_underlying).balanceOf(address(this))`; they only move the amount encoded in the cross-chain `Message`. The owner-only admin surface is limited to `configure`, `addChain`, `removeChain`, `pause`, `unpause` — no sweep/rescue/recover function exists: [4](#0-3) . Documentation confirms the wrapper is intended for arbitrary "existing ERC20 tokens" including rebasing-adjacent categories (WETH is the only special-cased type, via the `isWeth` flag), with no rebasing-token exclusion or blacklist mechanism: [5](#0-4) .

This mirrors the reported Allo `Allo#fundPool()`/`BaseStrategy#increasePoolAmount()` pattern exactly: static per-message/per-pool accounting against a token whose `balanceOf()` can independently grow (rebase, airdrop, or accrued yield), leaving the delta permanently stuck with zero mechanism to reach it.

By contrast, `IntentGatewayV2`/`IntentsBase` in the same repo already anticipated and mitigated this exact bug class for its escrow — it tracks per-order balances in `_orders[commitment][token]`, emits `DustCollected` for any surplus beyond what's owed, and exposes governance-gated `DustSwept`/sweep functionality: [6](#0-5) . `WrappedHyperFungibleToken` has no equivalent recovery path.

### Impact Explanation
Any deployment of `WrappedHyperFungibleToken` wrapping a rebasing token (aTokens, stETH-style tokens, or any yield-accruing wrapper) will accumulate unreachable balance over time as the token's `balanceOf(address(this))` grows independently of the locked/unlocked message amounts. This is a permanent freezing of funds — the surplus can never be withdrawn by anyone, including governance, since no sweep function exists. Given the wrapper is a generic, permissionlessly deployable primitive (deployment guides explicitly invite wrapping "existing ERC20 tokens" with no restriction on rebasing behavior), this is a realistic deployment configuration, not a contrived edge case.

### Likelihood Explanation
Likelihood is moderate: it requires an operator to configure `_underlying` as a rebasing or yield-bearing token, which the documentation neither prohibits nor warns against (only WETH gets special handling via `isWeth`). Once deployed with such an underlying, the loss accrues automatically and passively with every rebase/interest event — no attacker action is needed, and every legitimate `send()`/receive cycle also continues to work normally, so the stuck balance would likely go unnoticed until it becomes material.

### Recommendation
Adopt one of the mitigations from the referenced report, adapted to this contract:
- Document/enforce that `_underlying` must be a standard, non-rebasing ERC20 (similar to the explicit restriction already applied to `StreamingYieldVault`'s asset), and validate this at `configure()` time where feasible.
- Add an owner/governance-gated `sweepSurplus(address token, address to)` function that transfers `balanceOf(address(this)) - <sum of amounts implied by in-flight/locked messages>` (or, more simply, any balance above what any legitimate unlock could need) to a treasury, mirroring `IntentGatewayV2`'s `DustCollected`/`DustSwept` pattern.
- Alternatively, switch to a dynamic accounting model that reads `balanceOf` deltas around lock/unlock operations, similar to how fee-on-transfer handling already exists in `IntentGatewayV2SameChainTest`'s `FeeOnTransferToken` tests, so actual received/held amounts are always the source of truth.

### Proof of Concept
1. Deploy `WrappedHyperFungibleToken` and `configure()` it with `_underlying` set to an interest-bearing rebasing token (e.g., a mock aToken whose `balanceOf` increases over time for all holders proportionally).
2. A user calls `send()` locking `1000` tokens; the contract's `balanceOf` becomes `1000`.
3. Time passes and the rebasing token's rebase mechanism increases the contract's `balanceOf` to, say, `1050` (50 tokens of accrued interest), without any corresponding `Message`.
4. The user's cross-chain transfer completes normally (or times out and is refunded) via `onAccept`/`onPostRequestTimeout`, unlocking exactly `1000` back out.
5. The contract is left holding the `50` accrued tokens with `balanceOf(address(this)) == 50` and no code path, view function, or owner-callable method able to reference or withdraw this balance — it is permanently frozen. [7](#0-6)

    function send(HyperFungibleToken.SendParams calldata params) external payable whenNotPaused {
        uint256 msgValue = msg.value;
        if (_isWeth && msgValue >= params.amount) {
            msgValue = msgValue - params.amount;
            IWETH(_underlying).deposit{value: params.amount}();
        } else {
            IERC20(_underlying).safeTransferFrom(msg.sender, address(this), params.amount);
        }

        DispatchPost memory request = _buildDispatchPost(params);
        bytes32 commitment;
        if (msgValue > 0) {
            commitment = IDispatcher(_host).dispatch{value: msgValue}(request);
        } else {
            commitment = dispatchWithFeeToken(request);
        }

        emit Sent({
            from: msg.sender,
            to: params.to,
            dest: string(params.dest),
            amount: params.amount,
            commitment: commitment
        });
    }

    /**
     * @notice Handles incoming cross-chain token transfer messages
     * @dev Called by the ISMP host when a POST request is received. Verifies the source
     * address matches the configured contract for that chain, then transfers the underlying
     * ERC20 to the recipient. If calldata is present, executes it via the CallDispatcher.
     * @param incoming The incoming POST request containing the token transfer message
     */
    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        HyperFungibleToken.Message memory message = abi.decode(request.body, (HyperFungibleToken.Message));
        address beneficiary = _toAddr(message.to);

        if (_isWeth) {
            // Try a native-ETH push first (cheap for EOAs and payable contracts);
            // if the recipient cannot accept native value (no `receive()` / `fallback()
            // payable`), re-wrap the withdrawn ETH and deliver the underlying WETH as
            // an ERC-20 transfer instead. This mirrors the deposit-side flexibility of
            // `send()` (which accepts WETH from non-payable callers via `safeTransferFrom`)
            // so the refund path doesn't permanently lock funds for the same caller class.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = beneficiary.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(beneficiary, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(beneficiary, message.amount);
        }

        if (message.data.length > 0) {
            ICallDispatcher(_dispatcher).dispatch(message.data);
        }

        emit Received({
            from: message.from,
            to: beneficiary,
            source: string(request.source),
            amount: message.amount
        });
    }

# WrappedHyperFungibleToken

Deploy this on the token's **home chain** where the canonical ERC20 supply lives. The wrapper custodies the underlying token without minting any new supply — it locks tokens when users bridge out and unlocks them when users bridge back. No pre-funding is required.

For WETH wrappers (`isWeth = true`), users can send native ETH/BNB directly via `msg.value` and the contract wraps it automatically. On receive, the contract unwraps WETH and sends native tokens to the recipient. On timeout, the contract unwraps and refunds native tokens.
