### Title
Unrestricted, reentrancy-unguarded `CallDispatcher.dispatch()` exposes transiently-held funds and lingering ERC20 approvals to any caller - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher.dispatch()` has no access control and no reentrancy guard, yet a single deployed instance is shared as the "untrusted call dispatcher" for every Hyperbridge EVM app on a chain — `IntentGatewayV2`/`IntrinsicIntents`/`ExtrinsicIntents`, `HyperFungibleToken`, `WrappedHyperFungibleToken`, and `BridgeToken` all route arbitrary post/pre-dispatch calldata through the same `CallDispatcher` address (confirmed identical address reused across apps in `docs/content/developers/evm/contract-addresses/testnet.mdx`). This is structurally the same bug class as `safeFunctionCall`: an unrestricted function executes arbitrary attacker-supplied calls with the dispatcher itself as `msg.sender`/`address(this)`, so any privilege or balance the dispatcher transiently holds (or any approval granted to/by it) can be seized by anyone who calls `dispatch()` — including via reentrancy from calldata the caller themselves supplies.

### Finding Description
`CallDispatcher.dispatch(bytes memory encoded)` decodes an attacker-supplied `Call[]` and executes each `to.call{value: call.value}(call.data)` with no `msg.sender` check and no reentrancy guard: [1](#0-0) 

This dispatcher is invoked from multiple independent, user/solver-controlled entry points, all sharing the same instance:
- `IntentsBase._execute` dispatches `order.output.call` (attacker/order-creator supplied) after output beneficiary has already received funds, then sweeps the dispatcher's residual balance back: [2](#0-1) 
- The Tron `IntentGatewayV2` predispatch flow transfers input assets into the dispatcher and then dispatches attacker-supplied `order.predispatch.call` before pulling the swapped balance back based on a `balanceOf` snapshot: [3](#0-2) 
- `HyperFungibleToken.onAccept` forwards attacker(sender)-supplied `message.data` to the same dispatcher after minting tokens to the beneficiary (which the docs recommend setting to the dispatcher address itself so it holds spendable balance): [4](#0-3) 
- The docs explicitly acknowledge the dispatcher temporarily holds value and warn against unlimited allowances, showing the team is aware the dispatcher's held balance/approvals are attacker-reachable: [5](#0-4) 

Because `dispatch()` is callable by anyone and is not reentrancy-guarded, the `Call[].to` supplied by an order creator/solver/sender can point to an attacker-controlled contract whose fallback reenters `CallDispatcher.dispatch()` mid-execution. At that point the dispatcher's balance is fully spendable by the reentrant caller — exactly the risk flagged in the original report ("since the caller to the approved target is `address(this)`, any special privilege granted to this consumer contract can be accessed by anyone using this function"). Here the "consumer contract" is the shared `CallDispatcher`, and "anyone" includes the very calldata the flow is executing.

### Impact Explanation
If a relayer/bundler batches multiple independent deliveries (e.g. several ISMP `onAccept`/`fillOrder` calls) into one transaction — a normal operational pattern for gas efficiency — funds belonging to one flow can be transiently sitting in the shared `CallDispatcher` while a different, attacker-controlled flow's calldata executes within the same call stack. Because `dispatch()` performs no ownership/session accounting of whose funds it currently holds, an attacker's malicious `Call.to` target can reenter `dispatch()` and redirect that balance to itself — a concrete theft of funds belonging to an unrelated order/message. Even absent batching, any integrator who (against the documented warning) leaves a non-exact ERC20 allowance granted to/through the dispatcher creates a standing exploitable surface reachable by any subsequent `dispatch()` caller, mirroring the ERC-20-approval theft path called out in the source report.

### Likelihood Explanation
The `dispatch()` function requires no privilege whatsoever to call, and the `Call[].to`/`data` fields dispatched by `IntentGatewayV2`, `IntrinsicIntents`/`ExtrinsicIntents`, and `HyperFungibleToken`/`WrappedHyperFungibleToken` are all populated from unprivileged, user-submitted order/message fields (`order.output.call`, `order.predispatch.call`, `message.data`). Any single order placer or token sender can supply a malicious `to` target, making the reentrant-drain path reachable from a single submitted order or dispatched message without needing any admin/governance compromise.

### Recommendation
- Add a reentrancy guard to `CallDispatcher.dispatch()`.
- Scope dispatcher balances per-call (e.g. deploy a fresh minimal-proxy dispatcher per order/message, or require the calling app to pass and enforce an expected pre/post balance invariant that reverts on shortfall even under reentrancy).
- Restrict `dispatch()` to be callable only by the whitelisted set of app contracts (`onlyApprovedCaller`), removing the fully-public entry point.
- Enforce in documentation and, where feasible, in code that any approvals set up inside `Call[]` are revoked or set to exact amounts within the same dispatch, never left standing.

### Proof of Concept
Conceptual PoC (illustrating the reentrant-drain window; exact exploitation depends on relayer batching behavior, which could not be independently confirmed in the indexed code):
1. Attacker submits an intent order whose `order.output.beneficiary` and `order.predispatch`/`output.call` target the shared `CallDispatcher` address, with `Call[0].to` = an attacker-controlled contract.
2. When `IntentsBase._execute` (or the Tron `IntentGatewayV2` predispatch path) calls `ICallDispatcher(dispatcher).dispatch(order.output.call)`, the attacker's contract's fallback is invoked as part of `to.call{value}(data)`.
3. From that fallback, the attacker calls `CallDispatcher.dispatch()` again directly, passing a new `Call[]` that transfers out whatever ERC20/native balance the shared dispatcher currently holds (its own order's assets, or — if this call lands inside a batched relayer transaction alongside another flow's delivery — a different order's/message's transiently-held funds).
4. Because `dispatch()` has no caller check and no reentrancy guard, step 3 succeeds unconditionally, and the outer flow's post-dispatch balance check (`balanceOf(dispatcher)`) then either reverts (griefing) or, if timed against a concurrent unrelated flow's funds, results in an actual, unauthorized transfer of those funds to the attacker.

### Security

The `CallDispatcher` executes calls in its own context (not via `delegatecall`), so the HFT contract's storage is never at risk. If any call in the array reverts, the entire `onAccept` handler reverts — including the token mint/unlock. The request can then be retried by any relayer until the timeout expires. If no successful execution occurs before the timeout, the request times out and the sender is eligible for a refund on the source chain. Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution.

Existing `CallDispatcher` deployments are listed on the [contract addresses](/developers/evm/contract-addresses/mainnet) page.
