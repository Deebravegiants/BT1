### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) attribution is not covered by the HMAC, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` accepts a webhook only if `Utils::HmacValidator.validate(request)` succeeds, but the HMAC is computed exclusively over the raw request body. The `shop`, `topic`, `webhook_id`, and `api_version` values that are later trusted and forwarded to the app's business logic come from unauthenticated HTTP headers that are never part of the signed material.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate_signature` computes/compares the HMAC solely against `verifiable_query.to_signable_string` (i.e. the body) and the app's shared `api_secret_key`: [2](#0-1) 

`Registry.process` gates purely on this body-only HMAC check, then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` — all sourced from headers — to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

`Request#shop`, `#topic`, `#webhook_id`, `#api_version` are read straight from `@headers` with no cryptographic binding to the HMAC: [4](#0-3) 

Because the same `api_secret_key` is shared across every shop that installs the app, the identity binding that should hold is: `shop authenticated by HMAC == shop delivered to the handler`. In reality the equality is broken — the HMAC only proves "this body+secret pair is genuine for some shop that installed this app," not "this body came from the shop named in the `shop-domain` header." An attacker who installs the app on their own shop receives genuinely-signed webhook deliveries (valid body + valid HMAC, since the secret is app-wide, not per-tenant). They can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` (and `topic`/`webhook-id`) header pointing at a victim shop. `HmacValidator.validate` still returns `true` because it never inspects the headers, so `Registry.process` dispatches the attacker-controlled body to the handler labeled as belonging to the victim shop.

This is the direct analog of the reported bug class: a value that is acted upon (`shop`, used by the host app to resolve tenant/session context) is not covered by the integrity check (`HMAC` over body only), breaking the binding `verified-bytes == acted-upon-identity`.

### Impact Explanation
This enables cross-tenant confusion: any app built on this gem that uses `WebhookMetadata#shop` to select tenant state, sessions, or perform per-shop side effects can be made to process attacker-supplied (self-generated) webhook bodies under a victim shop's identity, since the only cryptographic guarantee (HMAC) never binds to `shop`. This matches the Critical "cross-tenant access" impact category, as the trust boundary between one merchant's data/webhooks and another's is not enforced by the gem's own verification logic.

### Likelihood Explanation
Exploitation requires only that the attacker install the app on any shop they control (a normal, unprivileged step for any Shopify app), capture one genuinely-signed webhook delivery, and replay it with modified headers to the app's public webhook endpoint. No access token, `client_secret`, or victim credentials are needed — only observation of the attacker's own legitimately received webhook traffic.

### Recommendation
Bind the header-derived identity fields into the signed material used for verification, or independently prove that the header `shop` actually installed the app for this specific delivery (e.g., cross-check against the app's own installation/session records rather than trusting the header). At minimum, `Registry.process` should treat `request.shop`/`request.topic`/`request.webhook_id` as unauthenticated inputs and document that host applications must not rely on them for tenant attribution without additional verification.

### Proof of Concept
1. Attacker installs the target Shopify app on their own controlled store `attacker.myshopify.com`.
2. Shopify delivers a webhook to the app: body `B`, header `x-shopify-hmac-sha256: HMAC(secret, B)`, `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker captures `(B, HMAC(secret, B))` and re-sends a new HTTP request to the same webhook endpoint with the same body `B` and same HMAC header, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `Utils::HmacValidator.validate` recomputes `HMAC(secret, B)` (from `to_signable_string` = `@raw_body`) and it matches — validation passes because `shop` is never included in the signed string (`lib/shopify_api/webhooks/request.rb:35-38`, `lib/shopify_api/utils/hmac_validator.rb:26-31`).
5. `Registry.process` calls the app's handler with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed(B), ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), causing the host app to act on attacker-controlled data under the victim shop's identity.
