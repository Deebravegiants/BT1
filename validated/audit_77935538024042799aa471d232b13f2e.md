### Title
Deposit accounting assumes full transfer amount reaches the vault, enabling LP-share dilution/insolvency with fee-on-transfer or other non-standard SPL tokens - (File: program/src/processor.rs)

### Summary
`process_deposit`'s LP-mint and internal PnL accounting are computed from the nominal `deduct_coin_amount`/`deduct_pc_amount` values before the transfer executes, and the program never verifies that the AMM vault's balance actually increased by that amount after the `spl_token::instruction::transfer` CPI.

### Finding Description
In `process_deposit`, `deduct_coin_amount`/`deduct_pc_amount` and `mint_lp_amount` are derived purely from the deposit parameters and the vault balances read at the start of the instruction [4](#0-3) . The program then issues `Invokers::token_transfer` for the coin and pc legs using these computed amounts, and mints LP tokens (`Invokers::token_mint_to`) for `mint_lp_amount`, and updates `target_orders.calc_pnl_x`/`calc_pnl_y` and `amm.lp_amount` using the same pre-computed values [5](#0-4) . `Invokers::token_transfer` (`program/src/invokers.rs:148-168`) simply issues an `spl_token::instruction::transfer` for the specified amount and does not check the resulting destination balance [6](#0-5) . If either the coin or pc mint is a non-standard SPL token that deducts a fee/tax on transfer (or otherwise delivers less than the transferred amount, e.g. via a rebasing or fee-charging mint extension), the vault receives strictly less than `deduct_coin_amount`/`deduct_pc_amount`, yet the program still mints `mint_lp_amount` LP tokens and records the full nominal amounts in `calc_pnl_x`/`calc_pnl_y`. The same unchecked-transfer-then-fixed-accounting pattern also appears in the swap handlers (`process_swap_base_in`, `process_swap_base_out`, and their `_v2` variants), where `swap.amount_in`/`swap_in_after_add_fee` is transferred into the vault and `swap_amount_out`/`swap.amount_out` is transferred out based on pre-transfer vault balances, without re-checking actual balances after the inbound transfer [7](#0-6) .

### Impact Explanation
For deposits, this causes unbacked LP token minting: a depositor (or a colluding attacker depositing a fee-on-transfer token that the pool was configured with) receives LP shares priced as if the vault gained the full nominal amount, while the vault only gained `amount * (1 - fee)`. This directly dilutes/undercollateralizes the existing LP pool relative to its issued LP supply, letting the depositor later withdraw more value (in the unaffected asset) than they contributed, at the expense of other liquidity providers — an insolvent pool accounting condition explicitly in scope. For swaps, the same unchecked-transfer assumption means the swapper can end up paying less into the vault than accounted, degrading pool solvency (though this self-corrects to some degree since vault balances for subsequent instructions are freshly read).

### Likelihood Explanation
Reachable by any unprivileged user submitting a single `Deposit` (or `Swap`) transaction against a pool whose `coin_vault_mint`/`pc_vault_mint` happens to be, or is later migrated/mapped to, a fee-charging or otherwise transfer-amount-altering SPL token/mint extension; no special privileges, signer keys, or off-chain component are required. Likelihood depends entirely on whether such a pool is created/permitted with a non-standard mint, which the program does not explicitly forbid.

### Recommendation
After each `Invokers::token_transfer` call feeding the AMM vaults in `process_deposit` (and analogous swap handlers), reload the vault token account and use the actual balance delta (post-transfer minus pre-transfer) — rather than the pre-computed nominal amount — for LP-mint sizing and PnL bookkeeping (`calc_pnl_x`/`calc_pnl_y`, `amm.lp_amount`). Alternatively, explicitly document and enforce (e.g., via an allowlist check at `Initialize2`) that only standard, fee-free SPL Token mints are supported for `coin_vault_mint`/`pc_vault_mint`.

### Proof of Concept
1. Attacker (or pool creator) initializes/uses a pool where `coin_vault_mint` is a fee-on-transfer SPL token that deducts, e.g., 5% on every transfer.
2. Attacker calls `Deposit` with `base_side = 0` and `max_coin_amount = 1_000_000`. `deduct_coin_amount = 1_000_000`, and `deduct_pc_amount`/`mint_lp_amount` are computed from that nominal figure at `program/src/processor.rs:1197-1250`.
3. `Invokers::token_transfer` sends the coin CPI for `1_000_000`, but due to the 5% fee only `950_000` actually lands in `amm_coin_vault` [8](#0-7) .
4. The program still mints `mint_lp_amount` LP tokens (computed for the full `1_000_000`) and records `calc_pnl_x`/`calc_pnl_y` as if `1_000_000` coin were deposited [3](#0-2) , leaving the vault under-collateralized relative to the newly issued LP supply.
5. Attacker withdraws proportional LP shares later, extracting more pc/coin value than they actually contributed, diluting the remaining LPs.
