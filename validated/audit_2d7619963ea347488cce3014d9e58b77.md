### Title
Webhook HMAC signature does not cover the `shop`/`topic`/`webhook-id` headers, allowing shop-domain spoofing on otherwise-valid webhook deliveries - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while `shop`, `topic`, and `webhook_id` are read straight from HTTP headers that are never included in the HMAC-signed payload. `Registry.process` verifies the HMAC and then unconditionally trusts `request.shop` to identify the tenant the webhook belongs to, breaking the intended binding `hmac_signed_bytes == identity_bytes_acted_on`.

### Finding Description
`Utils::HmacValidator.validate` computes the expected signature purely from `verifiable_query.to_signable_string` and compares it to the `hmac` field [1](#0-0) . For webhooks, `to_signable_string` is defined as just `@raw_body`, and `hmac` is pulled from the `X-Shopify-Hmac-Sha256` header [2](#0-1) [3](#0-2) . Meanwhile `shop`, `topic`, and `webhook_id` are all sourced from separate HTTP headers (`X-Shopify-Shop-Domain`, `X-Shopify-Topic`, `X-Shopify-Webhook-Id`) that are not part of the signed string at all [4](#0-3) .

`Registry.process` validates only the body HMAC, then dispatches to the registered handler using the unverified `request.shop`, `request.topic`, and `request.webhook_id` values: [5](#0-4) 

This is exactly the "field acted on but not covered by the HMAC" analog: the equality the system should enforce is `shop_used_by_handler == shop_that_shopify_actually_signed_for`, but in practice the code only enforces `raw_body_used_by_handler == body_that_was_signed`, and `shop` can be swapped independently.

### Impact Explanation
Any actor who can obtain one legitimately-signed webhook delivery (e.g., from their own store where they install the app, since Shopify signs webhooks per-shop with the app's shared secret computed only over the body) can replay that exact body/HMAC pair while substituting an arbitrary value in the `X-Shopify-Shop-Domain` header. `HmacValidator.validate` will still pass because it never looks at the shop header, and `WebhookMetadata` will be built with the attacker-chosen `shop`. If the host application's webhook handler uses `data.shop` to look up the tenant, apply mutations, or issue actions scoped "per shop" (a well-documented and expected usage pattern per `docs/usage/webhooks.md`), the attacker can cause tenant-scoped webhook processing to run against a victim shop's data using a payload the attacker fully controls, i.e. cross-tenant data manipulation/injection without needing that victim's credentials or the app's `client_secret`.

### Likelihood Explanation
Likelihood is high for any app that installs webhook handlers via this gem's documented `ShopifyAPI::Webhooks::Registry` mechanism, since the vulnerable code path is the gem's canonical, always-invoked webhook verification routine (`process`), not an edge case. Any attacker able to install the app on their own shop (a normal, unprivileged action) can generate valid signed webhook bodies at will and then forge the shop header when replaying the request to the app's public webhook endpoint.

### Recommendation
Include the identity-bearing headers (`shop`, `topic`, `webhook_id`, `api_version`) in the signed material used for HMAC verification, or otherwise cryptographically bind them to the verified body (e.g., derive the signable string from a canonical concatenation of headers + body rather than raw body only). At minimum, `Registry.process` should independently validate that `request.shop` corresponds to a shop with an active session/registration before dispatching to handlers.

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com`; trigger any webhook topic the app subscribes to, capturing the raw body `B` and the valid `X-Shopify-Hmac-Sha256` header `H` that Shopify computed over `B` using the shared `client_secret`.
2. Replay a POST to the app's webhook endpoint with the same body `B` and header `H`, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC only over `B` and matches `H` successfully [6](#0-5) .
4. `handler.handle` is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed_body(B), ...)` [7](#0-6) , causing the host application's handler to process attacker-supplied data under the victim shop's identity.
