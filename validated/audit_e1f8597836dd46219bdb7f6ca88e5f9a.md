### Title
`deposit` on Zest lending vaults can mint zero shares while still crediting the deposited assets, permanently destroying the depositor's principal - ([File: mainnet/contracts/vault/v0-vault-usdc.clar])

### Summary
The report's root cause is a missing/insufficient guard against a proportional value-conversion rounding to zero while the corresponding state-changing side effect (crediting real value) still proceeds unconditionally. In the Zest vault contracts (`v0-vault-usdc.clar`, and structurally identical `v0-vault-stx.clar` / `v0-vault-sbtc.clar`), `deposit` computes the number of vault shares (`zft`) to mint via `convert-to-shares-preview`, which performs `mul-div-down`. Unlike `redeem`, which explicitly checks `(asserts! (> inkind u0) ERR-OUTPUT-ZERO)`, `deposit` has no equivalent floor check on the minted share amount before proceeding.

### Finding Description
`deposit` is defined as: [1](#0-0) 

It computes `inkind` via: [2](#0-1) 

`convert-to-shares-preview` uses `mul-div-down`, which truncates toward zero: [3](#0-2) 

When `total-supply-preview` (`ts`) is greater than `total-assets-preview` (`ta`) by a sufficient factor (e.g., after significant interest/treasury-lp accrual inflates `ts` relative to `ta`, or simply due to a low-value deposit relative to the prevailing share price), `mul-div-down(amount, ts, ta)` can round down to `0` for a nonzero `amount`. `deposit`'s only guards are:

```
(asserts! (> amount u0) ERR-AMOUNT-ZERO)
(asserts! (>= inkind min-out) ERR-SLIPPAGE)
```

There is no `(asserts! (> inkind u0) ...)`. If the caller supplies `min-out u0` (the default/naive value when no slippage protection is desired, or simply because share price is far above 1:1 and the caller under-estimates it), the deposit proceeds with `inkind = u0`:
- `receive-underlying` pulls the full `amount` of real underlying tokens from the depositor into the vault.
- `(ft-mint? zft inkind recipient)` mints `u0` shares to the recipient — the depositor receives no claim on the vault.
- `(var-set assets (+ current-assets amount))` still increases the vault's recorded backing by the full `amount`.

This breaks the core share-to-backing identity `shares_minted / total_supply == assets_deposited / total_assets` at the transaction boundary: assets increase by `amount` with zero shares issued, meaning the deposited principal is absorbed into the vault and silently redistributed pro-rata to all existing shareholders, while the depositor who paid for it receives nothing and has no claim to reclaim it. This exactly parallels the GNS report's core defect: value is transferred into the system (GNS collateral / vault assets) but the corresponding "reward"/share accounting update rounds to zero, permanently orphaning the value from the party that provided it.

### Impact Explanation
Any depositor who submits a deposit whose `amount` is small relative to the current share price (`ta`/`ts` ratio) — which naturally grows over time as interest and treasury-lp minting occur — will have their principal permanently and irrecoverably absorbed by the vault with zero shares minted. This is a permanent loss of principal for the depositor, categorized as High/Critical-adjacent "theft/permanent freezing of principal," since the redeem path enforces `ERR-OUTPUT-ZERO` but the deposit path (the mirror operation) does not enforce the analogous `inkind > 0` check.

### Likelihood Explanation
Likelihood grows directly with vault age/share-price appreciation: as `total-supply-preview` diverges from `total-assets-preview` (via interest accrual and treasury-lp minting increasing `ts` relative to `ta`), the minimum non-zero deposit amount increases proportionally. Any integrator, bot, or user submitting a small deposit with `min-out` set to `u0` (a common default when slippage protection isn't tightly configured) is exposed. No privileged action is required to trigger this — it is directly reachable by any unprivileged caller of `deposit`.

### Recommendation
Add an explicit zero-share guard to `deposit`, mirroring `redeem`'s `ERR-OUTPUT-ZERO` check:
```
(asserts! (> inkind u0) ERR-OUTPUT-ZERO)
```
before minting, so that a deposit which would result in zero shares reverts rather than silently forfeiting the depositor's underlying assets to the pool.

### Proof of Concept
1. Vault operates over time; interest accrues and `total-supply-preview` (via `calc-treasury-lp-preview`) grows relative to `total-assets-preview`, pushing the effective share price (`ta`/`ts`) below 1 unit of underlying per unit of share equivalent for small amounts, i.e., `ts/ta` becomes large.
2. A user calls `deposit` with a small `amount` (e.g., `amount = 1`) and `min-out = u0`.
3. `convert-to-shares-preview(1)` computes `mul-div-down(1, ts, ta)`, which truncates to `0` given `ts/ta >> 1`.
4. `(asserts! (>= inkind min-out) ERR-SLIPPAGE)` passes trivially since `0 >= 0`.
5. `receive-underlying` transfers `1` unit of the underlying token from the user into the vault; `ft-mint? zft 0 recipient` mints nothing; `assets` is incremented by `1`.
6. The user has permanently lost their deposited unit with no corresponding share claim, and it is redistributed pro-rata to existing `zft` holders. [1](#0-0) [4](#0-3)
