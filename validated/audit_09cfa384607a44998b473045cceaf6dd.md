### Title
Webhook `shop-domain` (and `topic`/`webhook-id`/`api-version`) header is not covered by the HMAC signature, allowing cross-tenant attribution of a validly-signed webhook payload - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while the `shop`, `topic`, `webhook_id`, and `api_version` fields used downstream to process the webhook are read from unauthenticated HTTP headers. `Utils::HmacValidator.validate` only verifies the body bytes against the HMAC, never the headers, so any request carrying a previously-observed valid `(body, hmac)` pair will pass validation regardless of which shop's identity is attached to it via the header.

### Finding Description
`Webhooks::Request#hmac` and `#to_signable_string` are defined as: [1](#0-0) 
`to_signable_string` returns `@raw_body` exclusively — it does not include `shop`, `topic`, or `webhook_id`, all of which are parsed straight from HTTP headers in the same class: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC purely from `verifiable_query.to_signable_string` (i.e., only the body) and compares it with `verifiable_query.hmac`: [3](#0-2) 

`Webhooks::Registry.process` then uses the header-derived, HMAC-unauthenticated `request.shop` (along with `topic`/`webhook_id`/`api_version`) to build the `WebhookMetadata` object handed to the app's handler, after only checking the body signature: [4](#0-3) 

Because Shopify signs app webhooks with the app's single shared `client_secret` across **every** shop that has the app installed, the `(raw_body, hmac)` pair produced for one legitimately-installed shop is valid HMAC material for the app as a whole — it is not shop-scoped. This breaks the intended identity binding: `shop_that_produced_the_HMAC == shop_attributed_to_the_webhook`. An attacker who is an ordinary, unprivileged merchant with the app installed (no special privilege, no access to `api_secret_key`) can capture a genuine webhook delivery for their own shop and resend the same `raw_body`/`hmac-sha256` header pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`/`Webhook-Id`) header value with a victim shop's domain. `HmacValidator.validate` still succeeds (it only checks the body against the secret), and `Registry.process` will dispatch the handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain.

### Impact Explanation
This is a cross-tenant identity-binding bypass: it lets an unprivileged tenant of a multi-tenant Shopify app cause the app's own webhook handler to process attacker-supplied (but validly-signed) payload data under an arbitrary victim shop's identity. Depending on how the host app persists webhook data keyed by `shop` (e.g., orders/inventory/customer sync, GDPR triggers, billing state), this can corrupt or exfiltrate cross-tenant data, or trigger tenant-scoped side effects (e.g., app-uninstall/GDPR handlers, billing webhooks) against a shop that never sent that event. This satisfies the "cross-tenant access" Critical impact category, since the binding `shop-authenticated == shop-acted-on` is broken purely via HTTP header manipulation, without any credential theft.

### Likelihood Explanation
Any merchant who installs a multi-tenant app built on this gem can trivially capture one legitimate webhook delivery to their own endpoint (which they operate) and replay it with a modified `shop-domain` header. No `api_secret_key`, access token, or TLS interception is required — only ordinary use of the app as an installed merchant plus the ability to send an HTTP request to the app's public webhook endpoint with edited headers.

### Recommendation
Bind the shop/topic/webhook identity into the signed material, or independently authenticate the shop header against the session/tenant the webhook claims to originate from before dispatching to the handler. At minimum, `Webhooks::Request#to_signable_string` (or the validation call site in `Registry.process`) should incorporate `shop`, `topic`, and `webhook_id` into the value verified against the HMAC (mirroring how Shopify's `hmac-sha256` is scoped) rather than trusting the header value verbatim once the body-only HMAC passes.

### Proof of Concept
1. App `Foo` is installed on `shop-a.myshopify.com` and `shop-b.myshopify.com` (both using the same app `client_secret`).
2. Attacker controls `shop-a.myshopify.com` and, via their own webhook receiver/proxy, captures one delivered webhook: raw body `B` and header `X-Shopify-Hmac-Sha256: H` (valid HMAC of `B` under the shared secret), together with the original `X-Shopify-Topic` and `X-Shopify-Webhook-Id`.
3. Attacker POSTs the same body `B` and header `X-Shopify-Hmac-Sha256: H` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: shop-b.myshopify.com`.
4. `Webhooks::Request#hmac` reads `H` from the header; `to_signable_string` returns `B`; `HmacValidator.validate` recomputes HMAC(`B`, secret) and it matches `H` — validation passes. [5](#0-4) 
5. `Registry.process` dispatches the handler with `WebhookMetadata(shop: "shop-b.myshopify.com", topic: ..., body: parsed(B), ...)`, causing the app to act on `shop-b`'s tenant data/state using attacker-supplied body content, despite `shop-b` never having sent this webhook.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
