### Title
Webhook `shop` domain is trusted without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely by checking `Utils::HmacValidator.validate(request)`, but the HMAC signable string is only the raw HTTP body — the `shop-domain`, `topic`, `webhook-id`, and `api-version` headers are never part of the signed material. The library nonetheless hands the unauthenticated `request.shop` value straight to the handler as trusted tenant identity, and the documentation explicitly claims this call "will verify the request did indeed come from Shopify," which is not true for the shop attribution.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from unauthenticated headers: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC over `to_signable_string` (i.e., the body only) using the app's single, shop-independent `api_secret_key`: [3](#0-2) 

`Registry.process` treats a passing HMAC check as proof the whole request — including the shop — is authentic, then forwards `request.shop` unchanged into `WebhookMetadata` given to the app's handler: [4](#0-3) 

Because the secret key (`Context.api_secret_key`) is shared by the app across every merchant/tenant that installs it (not per-shop), any user who has installed the app on their own store can generate arbitrary body content with a valid HMAC (e.g. by triggering `orders/create` on their own shop and controlling order fields), capture the `(raw_body, hmac)` pair from that legitimate delivery, then replay it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to a victim shop's domain. `HmacValidator.validate` still succeeds because the shop header was never part of the signed bytes, so `Registry.process` invokes the handler with `WebhookMetadata#shop` set to the victim's domain, using the request bytes (body) verified but not the shop identity claim that the application logic actually keys on.

This breaks the identity binding: `shop verified-by-HMAC` ⚌ `shop asserted-and-consumed-by-handler`. The gem's own documentation reinforces the false assumption by stating `Registry.process` "will verify the request did indeed come from Shopify": [5](#0-4) 

### Impact Explanation
Applications built on this gem (per the documented pattern) use `data.shop` from `WebhookMetadata` to select which tenant's session/data to act on, as shown in the gem's own example (`perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`): [6](#0-5) 
An attacker who is a legitimate (if low-privilege) installer of the app can forge webhook deliveries that appear to originate from any other merchant's shop domain while carrying attacker-chosen body content, leading to cross-tenant data injection/manipulation in any app that trusts `data.shop` as gem-verified (as the docs instruct). This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Medium-to-High: exploitation requires only that the attacker install the target app on their own Shopify store (a normal, unprivileged action) and trigger any webhook topic to obtain a validly-HMAC'd `(body, hmac)` pair, then replay it with a rewritten `shop-domain` header to the app's public webhook endpoint. No access to `api_secret_key`, tokens, or victim credentials is required.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the HMAC-covered signable string, or independently verify that `request.shop` corresponds to a shop the app actually has an active session/install for before trusting it in `Registry.process`/`WebhookMetadata`. At minimum, update `HmacValidator`/`Request` so `to_signable_string` binds the header-derived identity fields it exposes, and correct the documentation to stop asserting that HMAC validation proves the shop attribution.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and legitimately receives an `orders/create` webhook with attacker-controlled body content and a valid `X-Shopify-Hmac-Sha256` signature (computed by Shopify using the app's shared `api_secret_key`).
2. Attacker replays this exact `(raw_body, hmac)` pair to the app's webhook endpoint but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body normally; `Utils::HmacValidator.validate(request)` succeeds because it only hashes `@raw_body`, which is unchanged: [7](#0-6) 
4. The app's handler receives `WebhookMetadata` with `shop == "victim-shop.myshopify.com"` and attacker-chosen `body`, and — per the gem's documented usage pattern — performs tenant-scoped work keyed on that spoofed shop.
