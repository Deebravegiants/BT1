### Title
LimitSecretReferences admission check omits Projected-volume Secret sources, allowing pods to read Secrets not declared by their ServiceAccount - ([File: plugin/pkg/admission/serviceaccount/admission.go])

### Summary
`Plugin.limitSecretReferences` only inspects `volume.VolumeSource.Secret` when scanning `pod.Spec.Volumes` for Secret references, but never inspects `volume.VolumeSource.Projected.Sources[].Secret`. An attacker with only "create pods" RBAC can mount an arbitrary Secret via a `Projected` volume's `SecretProjection` and it will pass the `LimitSecretReferences=true` check even though the pod's ServiceAccount never declared that Secret.

### Finding Description
`limitSecretReferences` builds the allow-list `mountableSecrets` from `serviceAccount.Secrets`, then walks `pod.Spec.Volumes` checking only the plain Secret volume source: [1](#0-0) 
It also enumerates `Env`/`EnvFrom` secret refs for InitContainers and Containers, and `ImagePullSecrets`: [2](#0-1) 

However, a Secret can also be mounted into a pod via a `Projected` volume source containing a `SecretProjection` (`api.VolumeProjection.Secret`), which is a completely separate field from `VolumeSource.Secret`. The loop's guard `if source.Secret == nil { continue }` skips over `source.Projected` entirely - there is no traversal of `volume.VolumeSource.Projected.Sources` looking for `Secret` projections anywhere in `limitSecretReferences` or `limitEphemeralContainerSecretReferences`.

Because Kubernetes' Pod validation permits a `Projected` volume source with a `Secret` projection referencing any Secret name in the same namespace (RBAC on Secrets is not checked at admission/validation time - Secret access is normally gated only by the ServiceAccount-secret linkage that `LimitSecretReferences` is meant to enforce), an attacker who can only create Pods (and cannot read Secrets directly) can still cause the kubelet to mount an arbitrary Secret's data into the pod's filesystem, then read it from inside the container - fully bypassing the intended `LimitSecretReferences` allow-list.

The `EphemeralContainers` path (`limitEphemeralContainerSecretReferences`) has the analogous but narrower gap: it only checks `Env`/`EnvFrom` of ephemeral containers and has no volume/projected-volume enumeration at all (ephemeral containers don't carry their own volumes, so that omission is less relevant there, but it further shows the enumeration is not exhaustive/systematic).

### Impact Explanation
This is a Secret-disclosure / SA-declared-secret-allowlist bypass: any principal with only Pod-create permission in a namespace can read any Secret in that namespace regardless of the ServiceAccount's declared `.secrets` list, when the cluster relies on `LimitSecretReferences=true` (or the per-SA `EnforceMountableSecretsAnnotation`) as a security boundary. This matches the "admission/validation bypass leading to unauthorized secret read" class in Kubernetes' bug-bounty impact taxonomy.

### Likelihood Explanation
- Precondition: cluster operator has enabled `LimitSecretReferences=true` (this is a compile-time-off-by-default flag: `NewServiceAccount()` sets `LimitSecretReferences: false` per [3](#0-2) ; note the code comment "TODO: enable this once we've swept secret usage..." indicating this exact class of gap is the reason it remains disabled upstream).
- Attacker only needs `create` on `pods` in a namespace - a very common, minimally privileged RBAC grant.
- Exploit is a single Pod spec with a `Projected` volume referencing the target Secret; no race conditions, no additional access needed. Fully repeatable.

### Recommendation
Extend `limitSecretReferences` (and, for completeness, `limitEphemeralContainerSecretReferences` where ephemeral containers can carry volume-like references) to also walk `volume.VolumeSource.Projected.Sources` and validate every `projSource.Secret.Name` against `mountableSecrets`, mirroring the enumeration already used for mirror-pod ServiceAccountToken projection detection at [4](#0-3) . Better yet, replace the hand-rolled per-field checks with a single call to `podutil.VisitPodSecretNames` (already used elsewhere in this file for the mirror-pod check) so that any future new Secret-reference field is automatically covered by this admission check instead of requiring a hand enumeration to be kept in sync.

### Proof of Concept
Table-driven unit test in `plugin/pkg/admission/serviceaccount/admission_test.go`:
1. Create a ServiceAccount `sa` with `Secrets: []{Name: "allowed-secret"}` and no other secrets referenced.
2. Enable `Plugin.LimitSecretReferences = true`.
3. Construct a Pod with `Spec.ServiceAccountName: "sa"` and a `Volumes` entry:
   ```go
   Volumes: []api.Volume{{
       Name: "proj",
       VolumeSource: api.VolumeSource{
           Projected: &api.ProjectedVolumeSource{
               Sources: []api.VolumeProjection{{
                   Secret: &api.SecretProjection{LocalObjectReference: api.LocalObjectReference{Name: "not-declared-secret"}},
               }},
           },
       },
   }},
   ```
4. Call `plugin.Validate(ctx, admission.NewAttributesRecord(pod, ...Create...), objectInterfaces)`.
5. Expected (correct) behavior: `Validate` returns a `Forbidden` error indicating `"not-declared-secret"` is not allowed.
   Actual (current) behavior: `Validate` returns `nil` (admitted), confirming the bypass - the projected Secret reference is never checked by `limitSecretReferences`.
