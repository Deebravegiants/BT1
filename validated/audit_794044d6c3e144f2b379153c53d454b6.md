### Title
Newly-set multisig timelock can be silently bypassed for already-pending transactions because the timelock clock starts at proposal `creation_time_secs`, not at timelock activation - (File: aptos-move/framework/aptos-framework/sources/multisig_account.move)

### Summary
`multisig_account.move` implements an opt-in timelock (`MultisigAccountTimeLock`) that is supposed to delay execution of a queued multisig transaction until `timelock_period` seconds have elapsed, unless a configured `override_threshold` of approvals is reached. The elapsed-time check is computed from the transaction's `creation_time_secs`, which is set once when the transaction is proposed via `create_transaction`/`create_transaction_with_hash`, not from the moment the timelock policy is activated with `upsert_timelock`. This is exactly analogous to the seed bug class: a security-relevant state change (owners "overwriting" the allowance/permission surface) can be raced/pre-staged by an unprivileged-relative-to-quorum actor before the protective control is put in place, defeating the intent of the control. Here, a minority-but-quorum-capable owner can pre-stage a malicious transaction long before a timelock is added, so that once other owners believe they've protected the account with a timelock, that old transaction is already "aged" past the timelock window and executes immediately.

### Finding Description
The timelock gate is implemented in `can_execute_with_timelock`: [1](#0-0) 

It reads `pending_transaction.creation_time_secs` (set at proposal time) and compares `now_seconds() - creation_time_secs >= timelock`. The comment on `upsert_timelock` explicitly documents this design choice and its consequence: [2](#0-1) 

Concretely:
1. A multisig has `num_signatures_required = N` and no timelock configured.
2. A subset of owners that can reach `N` approvals (but not full unanimity, and possibly including a compromised or malicious signer) creates a malicious transaction (e.g., draining APT/FA via a resource-account/coin transfer, or reassigning multisig owners/threshold) and gets it to `N` approvals. Under normal (no-timelock) conditions this transaction is immediately executable — so this pending, fully-approved, dangerous transaction just sits at the head of the execution queue (since execution requires strict sequence ordering, `sequence_number == last_resolved_sequence_number + 1`).
3. Other owners, suspecting risk, react by calling `upsert_timelock` to add a delay + override threshold, expecting all pending and future transactions to now require waiting.
4. Because `elapsed = now_seconds() - pending_transaction.creation_time_secs` is computed from the original proposal time, and that proposal may already be older than `timelock_period` (or close to it), the malicious transaction can become — or already be — immediately executable the moment the timelock is turned on, completely bypassing the intended delay window that the defenders just tried to impose.

This breaks the core custody invariant that the timelock is supposed to protect: "any transaction subject to a newly-imposed timelock must wait the full configured delay from the point protection was requested," so that other owners have a real reaction/veto window. Instead, the code silently grandfathers in elapsed time accrued before the protection existed.

### Impact Explanation
The multisig timelock is a custody control guarding execution of arbitrary multisig-authorized transactions, which can include APT transfers, fungible-asset mint/burn/freeze via `TransferRef`/`MintRef`/`BurnRef` held by the multisig, resource-account signer capabilities, or code-object upgrade authority. If the timelock can be bypassed for already-queued transactions, a malicious or compromised co-owner who can already reach the base signature threshold can force through a value-draining or ownership-hijacking transaction essentially instantly, at the exact moment other owners believe they have bought themselves reaction time by enabling the timelock — the worst possible moment for the delay to fail. This is a full defeat of the security guarantee the feature exists to provide, directly enabling theft/reassignment of any asset the multisig controls. Impact is High: it doesn't grant a totally unprivileged attacker instant custody takeover (the attacker must already be able to reach normal quorum), but it silently nullifies a security control precisely in the adversarial scenario (racing to react to a compromise) where it matters most.

### Likelihood Explanation
Likelihood is moderate-to-high in realistic incident-response scenarios: enabling a timelock is a natural reaction once owners suspect a rogue co-signer or key compromise, and the exact use case for a timelock is to buy time to react to already-proposed suspicious transactions. The vulnerable window is not a rare edge case — it exists for every transaction created before `upsert_timelock` is (first) called or reconfigured, and the code's own comment acknowledges the residual window is "bounded by the previous timelock period," meaning for any proposal older than the newly configured `timelock_period`, the bypass is immediate on activation.

### Recommendation
Track `timelock_activated_at` (or equivalent) per-transaction or per-config-epoch, and compute `elapsed` relative to `max(creation_time_secs, timelock_last_updated_secs)` rather than raw `creation_time_secs`. Alternatively, when `upsert_timelock` is invoked (or the period is shortened/override lowered), force all currently pending, unexecuted transactions to require the full `timelock_period` measured from the `upsert_timelock` call itself, closing the pre-staging window entirely.

### Proof of Concept
1. Multisig `M` created with owners `{A, B, C}`, `num_signatures_required = 2`, no timelock.
2. `A` calls `create_transaction(A, M, malicious_payload)` (auto-approves) — `creation_time_secs = t0`.
3. `B` (compromised or colluding with `A`) calls `approve_transaction(B, M, seq=1)`. Transaction now has 2/3 approvals, meets quorum, and with no timelock would already be executable.
4. `C` (defender) notices suspicious activity and calls `upsert_timelock(multisig_signer, timelock_period=3600, override_threshold=Some(3))`, believing this now blocks execution for at least one hour.
5. If `now_seconds() - t0 >= 3600` already (or becomes so shortly after), `can_execute_with_timelock` returns `true` immediately via the `elapsed >= timelock` branch — see `can_execute_with_timelock`: [3](#0-2) 
6. `A` or `B` immediately executes the malicious transaction via `validate_multisig_transaction`/`can_be_executed`, despite `C` having just enabled the timelock specifically to prevent that.

Note: I could not fully verify the exact `MultisigTransaction`/`creation_time_secs` field initialization code (`create_transaction`/`create_transaction_with_hash`) or the `MIN_TIMELOCK_PERIOD`/`MAX_TIMELOCK_PERIOD` constants within the available tool budget — these appear in the file but were not retrieved before the iteration limit was reached. The behavior above is directly supported by the `can_execute_with_timelock` function body and by the explicit doc-comment on `upsert_timelock`/`upsert_timelock_internal` acknowledging this exact residual-window risk, both cited above.

    inline fun can_execute_with_timelock(multisig_account: address, sequence_number: u64, num_approvals: u64): bool {
        if (exists<MultisigAccountTimeLock>(multisig_account)) {
            let multisig_account_resource = &MultisigAccountTimeLock[multisig_account];
            let timelock = multisig_account_resource.timelock_period;
            let override_threshold = multisig_account_resource.override_threshold;

            // Get the pending transaction to check if the timelock has expired
            // Assume that the transaction has already been checked to exist and is valid
            let pending_transaction = get_transaction(multisig_account, sequence_number);

            // Use subtraction to avoid overflow (now_seconds() >= creation_time_secs is always true)
            let elapsed = now_seconds() - pending_transaction.creation_time_secs;

            // If the number of approvals meets the override threshold, or the timelock has expired, allow execution
            (override_threshold.is_some() && &num_approvals >= override_threshold.borrow()) || elapsed >= timelock
        } else {
            true
        }
    }
