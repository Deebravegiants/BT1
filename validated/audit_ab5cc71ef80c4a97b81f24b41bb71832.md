### Title
Webhook shop-domain spoofing via cross-tenant HMAC replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#shop` reads the shop identity straight from the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header, but `HmacValidator` only verifies the HMAC over the raw request body (`to_signable_string`). The `shop` field is never bound into the signed payload, so it can be altered without invalidating the signature.

### Finding Description
`Registry.process` treats a request as authentic solely based on `Utils::HmacValidator.validate(request)` succeeding [5](#0-4) . `HmacValidator#validate_signature` computes the HMAC exclusively over `verifiable_query.to_signable_string` [6](#0-5) , and for webhook requests `to_signable_string` is just the raw body bytes [2](#0-1) . The `shop` accessor, however, is derived independently from a header that is not part of the signed bytes at all [7](#0-6) .

Critically, `Context.api_secret_key` is a single, app-wide client secret shared by every shop that installs the app — it is not per-tenant [4](#0-3) . This means: `HMAC(body_A, secret) == HMAC(body_A, secret)` holds regardless of which shop the body originated from. The equality that should hold — "the shop attributed to a webhook equals the shop that actually produced the signed bytes" — is broken, because the signature proves only "this body was signed with the app's secret by *some* installed shop," not "this body came from shop X."

An attacker who installs the target app on their own (attacker-controlled) shop receives genuine webhooks with a valid HMAC signed by the shared `api_secret_key`. They can capture one such `(body, hmac)` pair and POST it to the app's webhook endpoint while substituting `X-Shopify-Shop-Domain` with a victim shop's domain. `HmacValidator.validate` still returns `true` because it never inspects the shop header, and `Registry.process` forwards `WebhookMetadata.new(..., shop: request.shop, ...)` — now containing the victim's shop — to the host application's handler [3](#0-2) . Any handler that trusts `data.shop` to look up or mutate tenant-scoped records (a normal and expected usage pattern for this gem) will act on attacker-supplied data under the identity of a shop the attacker does not control.

### Impact Explanation
This breaks the tenant isolation the HMAC check is meant to provide: a merchant who legitimately installs the app can forge webhook events that the host application will attribute to any other merchant's shop, using only their own genuine app installation and no possession of the victim's credentials. Depending on what the host app does with `WebhookMetadata#shop` and `#body` (e.g., creating/deleting resources, updating billing state, disabling features, writing audit or config data keyed by shop), this is a cross-tenant data integrity/confidentiality violation delivered entirely through this gem's own webhook verification API.

### Likelihood Explanation
Exploitation requires only installing the app once as any shop (a normal, low-privilege action available to any Shopify merchant/attacker) and replaying a captured legitimate body+HMAC pair with a modified shop header to the app's public webhook endpoint. No access to another shop's token, the app's `client_secret`, or any privileged action is required.

### Recommendation
Bind the shop identity into the verified material: either include the shop-domain (and topic) header value in the HMAC-signed string used by `to_signable_string`, or independently verify that `request.shop` is one for which the app holds a legitimate, previously-established session/access token before dispatching to a handler. At minimum, document/require that consuming apps must not trust `WebhookMetadata#shop` without separately confirming shop membership, since the value is presently unauthenticated.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker.myshopify.com`, completing OAuth normally so a webhook subscription fires for their own shop.
2. Shopify delivers a webhook to the app's registered endpoint with headers including `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid hmac of raw body B signed with the app's shared api_secret_key>`, and body `B`.
3. Attacker captures body `B` and the valid `hmac` value.
4. Attacker sends a new POST to the same webhook endpoint with the same body `B` and the same `hmac` header, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` builds successfully (all required headers present) [8](#0-7) .
6. `Utils::HmacValidator.validate(request)` returns `true` because it only recomputes HMAC over `B`, which is unchanged [6](#0-5) .
7. `Registry.process` invokes the app's handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed(B), ...)` [3](#0-2) , causing the host app to act on `victim.myshopify.com`'s tenant data using attacker-chosen body content.
