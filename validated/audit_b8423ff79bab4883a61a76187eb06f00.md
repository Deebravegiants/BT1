### Title
Webhook shop/topic attribution not bound to HMAC signature enables cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by verifying the HMAC over the raw request body, then trusts the unauthenticated `shop-domain`, `topic`, and `webhook-id` headers to attribute and dispatch the event to the app's handler. Because the HMAC signable string is only the raw body — never the shop or topic — the identity binding "HMAC-verified sender" ≠ "shop the app attributes the event to" is broken.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`, and `hmac` is decoded from the `hmac-sha256` header: [1](#0-0) 

`Registry.process` validates that HMAC and then immediately builds `WebhookMetadata` from the unauthenticated headers (`request.shop`, `request.topic`, `request.webhook_id`) and hands it to the app's handler: [2](#0-1) 

`shop` and `topic` are read directly from headers with no cryptographic binding to the signed body: [3](#0-2) 

`Utils::HmacValidator.validate` computes the signature only over `verifiable_query.to_signable_string`, i.e. the raw body, using the app's single, app-wide `Context.api_secret_key`: [4](#0-3) 

By contrast, the OAuth `AuthQuery` (used in `validate_auth_callback`) does include `shop` inside `to_signable_string`, so shop is cryptographically bound there: [5](#0-4) 

For webhooks there is no equivalent binding. `client_secret`/`api_secret_key` is a single per-app secret shared across every shop that installs the app (not a per-shop secret) — the gem itself uses `Context.api_secret_key`/`old_api_secret_key` uniformly regardless of shop, as seen in `HmacValidator.validate`. Consequently, an attacker who can install the (public) app on their own shop can legitimately trigger webhooks (e.g. via a topic they control, such as `app/uninstalled`, or an empty-body/GDPR-style webhook), capture a genuinely-signed `(raw_body, hmac)` pair, and then replay that exact body+HMAC to the app's webhook endpoint while substituting the `shop-domain` and `topic` headers of their choice. `Registry.process` re-verifies the same HMAC (which only covers the untouched body) successfully, and dispatches to the handler with attacker-chosen `shop`/`topic` in `WebhookMetadata`, per the documented handler contract: [6](#0-5) 

This lets an unprivileged internet user (any developer who can install the public app on a shop they control) forge webhook events attributed to a victim shop, because the gem's `shop`/`topic` fields acted upon by the handler are not covered by the HMAC that is supposed to authenticate the message.

### Impact Explanation
This is a cross-tenant identity confusion: the handler processes data believing it originates from and pertains to a specific shop/topic, but that attribution is unauthenticated. Depending on what the host app's `WebhookHandler#handle` does with `data.shop`/`data.topic` (e.g., invalidate a session, trigger data deletion/redaction flows, mark a shop as uninstalled, queue background jobs keyed by `shop_domain` as shown in the gem's own doc example `perform_later(topic: data.topic, shop_domain: data.shop, ...)`), this enables cross-tenant impact such as spoofed uninstall/redact events or corrupted per-shop state for a victim shop the attacker never has credentials for.

### Likelihood Explanation
Requires the attacker to be able to install the target's public app on a shop they control (a normal, low-privilege action for any Shopify merchant/developer using a public app) and to capture one legitimate signed webhook body for a topic with body content that is either shop-agnostic or ignorable by the handler. It also depends on the host application acting on `data.shop`/`data.topic` for privileged/state-changing operations, which the gem's own documented usage example (`perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) explicitly encourages.

### Recommendation
Bind `shop` (and ideally `topic`) into the value that is HMAC-verified, or otherwise cryptographically tie the webhook subscription/registration id to the expected shop so that `Registry.process` can reject a body whose signature is valid but whose header-derived shop/topic don't match what was registered for that webhook id/subscription.

### Proof of Concept
1. Attacker installs the target's public Shopify app on `attacker-shop.myshopify.com`, registering for a topic with a static/predictable body (e.g., an empty-body webhook).
2. Shopify (or the attacker directly, since they know the flow) delivers a webhook to the app's endpoint with body `"{}"` and a valid `x-shopify-hmac-sha256` computed with the app's single `client_secret`.
3. Attacker replays that exact `raw_body`/`hmac-sha256` pair to the same endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` and `x-shopify-topic: app/uninstalled` (or any topic registered by the app).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only re-computes the HMAC over `raw_body` — it succeeds. [2](#0-1) 
5. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: "app/uninstalled", ...)`, causing the app to act as if the victim shop triggered that event.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
