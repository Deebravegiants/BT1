## Finding: Unvalidated signature length before fixed-buffer copy in BEEFY vote conversion

### Title
Unchecked-length `copy_from_slice` into a fixed 65-byte buffer when converting attacker-supplied BEEFY vote signatures - (`evm/rust/src/conversions.rs`)

### Summary
The `oFono` CVE is a class of bug where a variable-length, attacker-controlled buffer is copied into a fixed-size destination without first validating its length. The closest reachable analog in this repo is the conversion `From<Vote> for SignatureWithAuthorityIndex`, which copies an ABI-decoded `bytes` signature field into a fixed `[u8; 65]` array with no length check.

### Finding Description
`Vote` is a Solidity-ABI-shaped type (`ecdsa_beefy::Beefy::Vote`) whose `signature` field is an arbitrary-length `bytes`. When converting it to the Rust/Substrate-native `SignatureWithAuthorityIndex` used by the BEEFY verifier, the code does: [1](#0-0) 

```rust
impl From<Vote> for SignatureWithAuthorityIndex {
    fn from(value: Vote) -> Self {
        let sig_bytes = value.signature.to_vec();
        let mut signature: TSignature = [0u8; 65];
        signature.copy_from_slice(&sig_bytes);
        ...
```

`sig_bytes.len()` is never checked against 65 before `copy_from_slice`. This is the same root cause pattern as CVE-2024-7539: data whose length is controlled by an external party (a relayer/prover assembling a `BeefyConsensusProof`/`RelayChainProof`/`SignedCommitment.votes`) is copied into a fixed-size destination without a prior length validation. In Rust, `copy_from_slice` does not corrupt memory on a mismatch — it panics — but the missing bounds check is otherwise structurally identical to the original bug class.

This conversion sits in the `beefy` module gated by `#[cfg(feature = "substrate")]` and is used when building `ConsensusMessage`/`MmrProof` values from Solidity-ABI-encoded BEEFY proof structs for the SP1 BEEFY consensus pipeline (`sp1_beefy`, `beefy_verifier_primitives`). [2](#0-1) 

### Impact Explanation
Because `copy_from_slice` panics on length mismatch instead of overflowing, this cannot be leveraged for code execution as in the original oFono CVE. Its concrete impact is a panic in whatever process performs this conversion when handed a malformed `Vote.signature` (any length other than 65 bytes) as part of an untrusted BEEFY consensus proof — i.e., a crash of the BEEFY consensus-update/prover pipeline for that message, which can prevent that route's consensus updates (and therefore its message deliveries) from being processed until the process is restarted. This falls short of memory-corruption RCE but can match the allowed "route unable to deliver messages" impact category if this conversion executes on an untrusted-proof ingestion path outside of a sandboxed/panic-caught context.

### Likelihood Explanation
Likelihood is uncertain: I was not able to fully trace, within the available tool budget, the exact call site that invokes `From<Vote> for SignatureWithAuthorityIndex` with a `Vote` value taken directly from untrusted, attacker/relayer-controlled input (as opposed to internally-constructed, already-validated test or SDK data). The type is used by `beefy_verifier_primitives::ConsensusMessage`/`MmrProof` construction, which appears in prover/host code that processes external consensus proofs, but confirming that the `signature` bytes reach this conversion without a prior 65-byte length check elsewhere in the call chain would require deeper tracing than I could complete.

### Recommendation
Add an explicit length check (`sig_bytes.len() == 65`) before `copy_from_slice`, returning a `TryFrom`/`Result` error instead of an infallible `From` conversion, mirroring the pattern already used elsewhere in the codebase (e.g., `to_bytes_32`, `ModuleId::from_bytes`, `WithdrawParamsAbi::try_from`) which explicitly validate lengths before fixed-array copies. [3](#0-2) 

### Proof of Concept
Not independently confirmed end-to-end due to inability to trace the full untrusted-input call path in the time available. A minimal unit-level repro: construct a `Vote { authorityIndex, signature: Bytes::from(vec![0u8; 64]) }` (or any length ≠ 65) and call `SignatureWithAuthorityIndex::from(vote)` — this panics inside `copy_from_slice` at `evm/rust/src/conversions.rs:360`.

**Caveat:** Given the difficulty confirming the exact untrusted-input reachability of this conversion within the iteration budget, I'd recommend treating this as a lower-confidence analog. If you want a definitive verdict, a Devin session with full repo/tool access could trace every caller of `SignatureWithAuthorityIndex::from`/`Vote` construction to confirm whether attacker-controlled `signature` bytes reach this code without prior validation.
