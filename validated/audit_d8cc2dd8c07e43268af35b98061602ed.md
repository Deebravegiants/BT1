### Title
Missing zero-address validation on `IntentGatewayV2` admin (Tron variant) permanently bricks the gateway - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron-targeted `IntentGatewayV2` contract's constructor accepts an `admin` address with no zero-address check, unlike the primary EVM `IntentGatewayV2` implementation which explicitly reverts on `address(0)` (`InvalidInput`). If the deployer mistakenly (or via a misconfigured deployment script) supplies `address(0)` as `admin`, the one-time `setParams` gate can never be exercised, permanently bricking the gateway before it ever accepts an order.

### Finding Description
The Tron variant's constructor stores the admin without validation: [1](#0-0) 

The only function that can populate `_params` (host, dispatcher, fee configuration, etc.) is `setParams`, gated solely by `_admin`, and it self-destructs the gate after a single use: [2](#0-1) 

If `_admin` is `address(0)`, `msg.sender != _admin` is always true for every real caller (no account can send from `address(0)`), so `setParams` can never succeed. `host()` returns `_params.host`, which stays `address(0)` forever: [3](#0-2) 

There is no alternate admin-setting or recovery path in this contract — `_admin` and `_params` have no other writers. By contrast, the primary `evm/src/apps/IntentGatewayV2.sol` was hardened against exactly this class of bug: [4](#0-3) 

This confirms the project's own precedent (and the referenced external report's fix pattern) that a zero-admin/zero-owner constructor parameter must be rejected, but the Tron fork of the same contract was not updated to match.

### Impact Explanation
A zero `_admin` permanently prevents `setParams` from ever succeeding, so `_params.host`, `_params.dispatcher`, and fee/oracle configuration are permanently unset. `placeOrder` and all order-fulfillment/escrow logic depend on `host()` and `_params.dispatcher` resolving to real contracts; with them stuck at `address(0)`, any native or ERC-20 assets sent into `placeOrder` before this is noticed would either revert or, in flows that transfer to `_params.dispatcher` (`address(0)`), be irrecoverably lost/burned, and the deployment itself becomes permanently unusable — a route unable to deliver messages/orders at all. This matches the "permanent freezing of funds" / "route unable to deliver messages" impact class.

### Likelihood Explanation
This requires a deployment-time mistake (deploy script/config error) that supplies `address(0)` as the constructor's `admin` argument — a plausible operational error given there is no redeploy-time safeguard, especially since the sibling EVM contract already treats this as a real enough risk to explicitly guard against it. It is not a malicious-admin/governance scenario; it is a straightforward missing-input-validation bug reachable by whoever runs the deployment.

### Recommendation
Add the same guard used in `evm/src/apps/IntentGatewayV2.sol` to the Tron variant's constructor:
```solidity
constructor(address admin) EIP712("IntentGateway", "2") {
    if (admin == address(0)) revert InvalidInput();
    _admin = admin;
}
```
Optionally also add a recovery path (e.g., a re-arm mechanism gated by another privileged actor) in case `setParams` is never called for other operational reasons.

### Proof of Concept
1. Deploy `evm/tron/contracts/apps/IntentGatewayV2.sol` with constructor argument `admin = address(0)`.
2. Observe `_admin == address(0)`.
3. Any attempt to call `setParams(...)` from any real account fails `msg.sender != _admin` check (since `msg.sender` can never equal `address(0)`), reverting with `Unauthorized`.
4. `_params.host` remains `address(0)` forever; `host()` returns `address(0)`.
5. The gateway is permanently non-functional — no order can be correctly routed/dispatched, and this state is irreversible since nothing else can write `_params` or `_admin`.
