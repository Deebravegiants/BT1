## Analysis

This is a valid analog. The external report concerns missing validation of the token used when creating a pool, allowing a malicious token to trap value belonging to other users. In Raydium AMM, the analogous unprivileged entry point is `Processor::process_initialize2` (`Initialize2` instruction), which is reachable by anyone since account creation for a pool requires no privileged signer beyond the pool creator's own wallet.

### Root cause

`process_initialize2` in `program/src/processor.rs` unpacks and validates `amm_coin_mint_info` / `amm_pc_mint_info` only for:
- being owned by the SPL Token program (`Self::unpack_mint`) [1](#0-0) 
- `coin_mint != pc_mint` [2](#0-1) 
- decimals are copied into `AmmInfo` state [3](#0-2) 

For the freshly-created `lp_mint`, the code explicitly checks that it has zero `supply`, that `mint_authority` is the pool `$authority`, and that `freeze_authority` is `None` [4](#0-3) . The coin/pc vault token accounts are checked for `delegate.is_some()` and `close_authority.is_some()` [5](#0-4) .

However, there is **no check on the `freeze_authority` field of the attacker-supplied `coin_mint`/`pc_mint` themselves**. Since the coin/pc vaults are plain SPL Token accounts owned by the pool `$authority` PDA (not the mint's freeze authority), the token creator's mint-level `freeze_authority` still applies to those vault accounts. Any pool creator can supply a mint they control with `freeze_authority` set to their own key, deposit the required non-zero initial liquidity to pass the `amount == 0` checks [6](#0-5) , and later, once other users have deposited via `Deposit`/`Withdraw`/swap instructions, call `spl_token::instruction::freeze_account` (a normal SPL Token CPI) against `amm_coin_vault` or `amm_pc_vault`.

### Impact

Freezing either vault account permanently blocks `Deposit`, `Withdraw`, and all four swap instructions from transferring out of that vault, since the underlying SPL Token program will reject any transfer from a frozen account. This traps **every LP's** share of the paired token in the vault — not just the malicious creator's — i.e. permanent freezing of user/LP funds, which satisfies the validation bar (concrete permanent freezing of user funds) even though it does not lead to theft.

### Recommendation

In `process_initialize2`, after unpacking `coin_mint` and `pc_mint`, reject pools whose `coin_mint.freeze_authority` or `pc_mint.freeze_authority` is `COption::Some(_)`, mirroring the existing `lp_mint.freeze_authority.is_some()` check.

### Title
Pool creation accepts coin/pc mints with an attacker-controlled freeze authority, allowing permanent freezing of LP funds - (File: `program/src/processor.rs`)

### Summary
`process_initialize2` validates the newly-created `lp_mint`'s `freeze_authority` but never validates the `freeze_authority` of the user-supplied `coin_mint`/`pc_mint`, letting anyone create a pool backed by a token they can freeze at will.

### Finding Description
`Initialize2` is a fully permissionless instruction — any signer can supply arbitrary `amm_coin_mint_info`/`amm_pc_mint_info` accounts as long as they are owned by the SPL Token program [1](#0-0)  and pass the non-equality check [2](#0-1) . The coin/pc vault accounts created for the pool are regular SPL Token accounts owned by the pool `$authority` PDA [7](#0-6) , but the SPL Token program still enforces the *mint's* `freeze_authority`, independent of the account owner. The code checks the vault's `delegate` and `close_authority` fields but omits any check of `coin_mint.freeze_authority` / `pc_mint.freeze_authority` [8](#0-7) , unlike the analogous check performed for `lp_mint` [4](#0-3) .

### Impact Explanation
An attacker mints a token with `freeze_authority` set to themselves, creates a Raydium pool pairing it with a legitimate token via `Initialize2`, and waits for other LPs to deposit through `Deposit`. At any point the attacker calls the standard SPL Token `FreezeAccount` instruction against `amm_coin_vault` or `amm_pc_vault`. Once frozen, `Withdraw` and all swap instructions fail because the SPL Token program rejects transfers from a frozen account, permanently locking every depositor's share of both tokens in the pool (the vault holds funds pooled from all LPs, not just the attacker).

### Likelihood Explanation
Likelihood is high: no privileged signer or non-default build/config is required, only a single `Initialize2` transaction with attacker-chosen mint accounts and a subsequent standard `FreezeAccount` CPI, both fully reachable by an ordinary unprivileged user.

### Recommendation
Add explicit checks in `process_initialize2` rejecting `coin_mint.freeze_authority.is_some()` and `pc_mint.freeze_authority.is_some()`, consistent with the existing `lp_mint.freeze_authority` check.

### Proof of Concept
1. Attacker creates SPL mint `M` with `freeze_authority = attacker`.
2. Attacker calls `initialize2` pairing `M` as `coin_mint` with a legitimate `pc_mint` (e.g. USDC), depositing minimal non-zero `init_coin_amount`/`init_pc_amount` to pass the vault-amount checks.
3. Victims call `Deposit`, adding USDC/`M` liquidity to the pool vaults.
4. Attacker submits an SPL Token `FreezeAccount` instruction targeting `amm_coin_vault` (or `amm_pc_vault`), signed by themselves as the mint's freeze authority.
5. All subsequent `Withdraw`/swap instructions referencing that vault fail permanently, locking all LPs' deposited funds.
