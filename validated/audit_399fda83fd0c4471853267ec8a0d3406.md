### Title
Non-Embedded Session Cookie Value Trusted as Session ID Without Cryptographic Binding, Enabling Cross-Tenant Session Hijacking - ([File: lib/shopify_api/utils/session_utils.rb])

### Summary
`ShopifyAPI::Utils::SessionUtils.current_session_id` returns the raw, unsigned value of the `shopify_app_session` cookie as the session identifier for non-embedded apps (and as a fallback for embedded apps), with no HMAC or signature verification binding that value to the session it was originally issued for. Combined with the fully deterministic offline session ID format (`"offline_#{shop}"`), this breaks the identity binding: `shop authenticated by the request` **should equal** `shop whose session/access-token is retrieved`, but here `session id retrieved == raw bytes supplied in a client-controlled cookie`, with no verification that those bytes were ever issued by the app for that browser.

### Finding Description
`ShopifyAPI::Auth::Oauth.validate_auth_callback` issues a `SessionCookie` whose `value` is simply the plain session `id` (`Session#id`, itself `SecureRandom.uuid` for online sessions, but a fully predictable `"offline_#{shop}"` for offline sessions): [1](#0-0) [2](#0-1) 

This cookie is a plain, unsigned struct with no MAC over its value: [3](#0-2) 

When the app later needs to resolve "who is making this request", `SessionUtils.current_session_id` — for non-embedded apps, and as the fallback branch for embedded apps without a JWT — takes the cookie value **directly** and returns it as the session id, with no signature check that the value was actually issued by the app for this browser: [4](#0-3) [5](#0-4) 

Contrast this with the embedded/JWT path, where the session id is derived from a cryptographically verified claim (`dest`/`sub` inside a JWT signed with `Context.api_secret_key`): [6](#0-5) [7](#0-6) 

The cookie-based path has no equivalent binding: the returned id is exactly whatever bytes are present in the client-supplied cookie header. Because offline session ids are computed purely from the public shop domain (`offline_#{shop}`), any browser client can set `shopify_app_session=offline_victim-shop.myshopify.com` (shop domains are public/known, e.g. discoverable via the storefront) without ever completing OAuth for that shop. The gem's own documentation instructs host apps to call `current_session_id` and use the returned id directly to look up the persisted `Session`/access token (`MyApp::SessionRepository.retrieve(id)` pattern shown in `docs/usage/oauth.md`), so an app following the documented pattern will load and use the victim shop's stored access token for the attacker's request.

This is the same class of bug as the external report: an identity-binding step (`_currentDefaultAdmin` transfer) that is supposed to enforce "only the party that legitimately holds this role/identifier can use it" is skipped, so two unrelated parties end up sharing the same privileged identity. Here, "the party the cookie was issued to" and "the party presenting the cookie" are never bound cryptographically — the equality `session_id_returned == session_id_the_app_actually_issued_to_this_client` is not enforced.

### Impact Explanation
An unprivileged internet user (any visitor to the vulnerable app's non-embedded/legacy pages, or any user hitting the embedded app's cookie-fallback path without a JWT) can set an arbitrary, guessable `shopify_app_session` cookie value and have the app resolve and use another merchant's persisted offline session, including its access token, for their requests. This is cross-tenant access to another merchant's Shopify Admin API session/access token — a Critical-severity outcome per the stated impact criteria (theft/use of another merchant's access token, cross-tenant access), achieved purely by breaking the cookie↔session identity binding, with no credentials, TLS interception, or privileged access required.

### Likelihood Explanation
Likelihood is high for offline sessions because the id is fully deterministic from a public value (the shop's `myshopify.com` domain), requiring no guessing beyond knowing/enumerating shop domains. For online sessions the id includes a `SecureRandom.uuid`-style component and is not practically guessable, so the exploitable case is specifically the offline-session / non-embedded-app path, which the gem still documents and supports as first-class usage (`docs/usage/oauth.md`).

### Recommendation
Do not derive or trust a session identifier from raw, unsigned cookie bytes. Either (a) sign/MAC the cookie value with `Context.api_secret_key` and verify that MAC before returning the id from `cookie_session_id`, or (b) store an opaque, unpredictable, per-issuance token in the cookie unrelated to the `offline_#{shop}` naming scheme, and always re-validate that the resolved session's `shop`/ownership matches an independently authenticated signal (e.g., a JWT `dest` claim, or a server-side lookup keyed by an unguessable random cookie value rather than the shop-derived id).

### Proof of Concept
1. Deploy a non-embedded app using this gem exactly as documented (`docs/usage/oauth.md`): complete OAuth once, storing sessions server-side and using `SessionUtils.current_session_id` to look up sessions on each request.
2. Victim merchant `victim-shop.myshopify.com` installs the app (offline session created, id = `offline_victim-shop.myshopify.com`).
3. Attacker, in their own browser, sets a cookie:
   `shopify_app_session=offline_victim-shop.myshopify.com`
4. Attacker sends a request to the app. `SessionUtils.current_session_id(nil, {"shopify_app_session" => "offline_victim-shop.myshopify.com"}, false)` returns `"offline_victim-shop.myshopify.com"` unchanged, per: [8](#0-7) 
5. The host app's session repository loads the victim's persisted `Session` (containing the victim's access token) using this id and makes Admin API calls with it on the attacker's behalf — cross-tenant access to the victim's store data/access token.

      class SessionCookie < T::Struct
        extend T::Sig

        SESSION_COOKIE_NAME = "shopify_app_session"

        const :name, String, default: SESSION_COOKIE_NAME
        const :value, String
        const :expires, T.nilable(Time)

        alias_method :eql?, :==
        sig { params(other: T.nilable(SessionCookie)).returns(T::Boolean) }
        def ==(other)
          return false unless other

          name == other.name &&
            value == other.value &&
            expires == other.expires
        end
      end
