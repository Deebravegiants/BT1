### Title
Cache key collision in `getCachedStorageDepositValue` due to unseparated string concatenation - (File: `packages/intents-sdk/src/bridges/direct-bridge/direct-bridge.ts`)

### Summary
`DirectBridge.getCachedStorageDepositValue` builds its LRU cache key as `` `${contractId}${accountId}` `` with no delimiter, so two distinct `(contractId, accountId)` pairs whose strings concatenate to the same value collide on the same cache entry. Because the cache only ever stores tuples where `userStorageBalance >= minStorageBalance` (line 295-297), a colliding lookup for a pair that actually needs storage deposit will incorrectly reuse the "sufficient" tuple from the other pair and report `storageDepositFee = 0n`.

### Finding Description
The broken equality: `feeEstimation.underlyingFees[NearWithdrawal].storageDepositFee` must equal `minStorageBalance(tokenAccountId, destinationAddress) - userStorageBalance(tokenAccountId, destinationAddress)` for the exact `(tokenAccountId, destinationAddress)` pair being withdrawn to.

In `estimateWithdrawalFee` (`direct-bridge.ts:225-241`), the fee is derived entirely from `getCachedStorageDepositValue(tokenAccountId, destinationAddress)`: [1](#0-0) 

The cache key construction and store logic: [2](#0-1) 

`key = \`${contractId}${accountId}\`` has no separator between `contractId` and `accountId`. Since both `contractId` (derived from the attacker-supplied `assetId` via `utils.parseDefuseAssetId`) and `accountId` (the attacker-supplied `destinationAddress`) are valid NEAR account-id strings, an attacker can pick `contractId='a', accountId='bc'` for one call and `contractId='ab', accountId='c'` for another — both producing the identical key `'abc'`.

Exploit flow:
1. Attacker calls `estimateWithdrawalFee` for `(tokenAccountId='a', destinationAddress='bc')` where `'bc'` genuinely has sufficient storage balance on token `'a'`. The real RPC calls run, `result[1] >= result[0]` is true, so the tuple `[min, bal]` is cached under key `'abc'` (line 295-297).
2. Attacker (or the same code path reused for a different actual withdrawal) calls `estimateWithdrawalFee` for `(tokenAccountId='ab', destinationAddress='c')`, a completely different token/account pair that has *not* registered storage. The lookup `this.storageDepositCache.get('abc')` hits the entry from step 1 and returns it without any RPC call.
3. Because the reused tuple satisfies `minStorageBalance <= userStorageBalance` (it was only cached because it did), `estimateWithdrawalFee` short-circuits to `storageDepositFee = 0n` and `amount = 0n` for the second pair, even though the real minimum-storage/storage-balance state for `('ab','c')` requires a nonzero deposit.
4. `createWithdrawalIntents` then calls `getUnderlyingFee(args.feeEstimation, RouteEnum.NearWithdrawal, "storageDepositFee")` (`direct-bridge.ts:137-141`) and sets `storageDeposit: 0` on the withdraw intent, even though the destination account is not storage-registered on the token contract.

No existing guard prevents this: `validateWithdrawal` only checks address format/account existence, not storage balance; `supports()` ordering and `assert` checks don't touch the cache; and the cache key itself, not the arithmetic, is the flaw.

### Impact Explanation
The withdrawal intent's `storage_deposit` field is signed and submitted as `0` for a destination that actually requires a nonzero NEP-141 storage deposit. Depending on the token contract's `ft_transfer`/`ft_transfer_call` behavior, this can cause the transfer to revert (funds stuck, requiring manual intervention/re-estimation) or force whichever party covers the underlying `near_withdraw` call to eat the true storage cost while the fee reported/charged to the user was zero. This matches "a withdrawal stuck until manual intervention" / "a fee error" categories. The bug is fully repeatable: any attacker who can name/construct colliding `(contractId, accountId)` string pairs (which, given account naming freedom, is feasible) can trigger it on demand, and if a single `DirectBridge` instance is shared across users/requests (as is typical for backend integrators), one user's cached entry can poison another's fee estimate.

### Likelihood Explanation
The attacker fully controls both inputs (`assetId` → `contractId`, and `destinationAddress` → `accountId`) via the public `estimateWithdrawalFee` API, at zero cost beyond crafting the colliding strings and having one of the two pairs genuinely storage-registered. The only precondition is finding/creating two valid NEAR account-id strings whose naive concatenation coincides — realistic given NEAR account-id character rules allow this by construction (e.g., `contractId='ab', accountId='c'` vs `contractId='a', accountId='bc'`). No RPC, relayer, or contract-side flaw is required — the defect is purely in the SDK's cache-key derivation.

### Recommendation
Use an unambiguous composite cache key, e.g. `` `${contractId}:${accountId}` `` with a reserved separator not permitted inside either NEAR account id, or key the `LRUCache` by a tuple/array, or use `JSON.stringify([contractId, accountId])`.

// vitest, mocking only the NEAR RPC provider used by

it("cache key collision returns stale storage deposit state", async () => {
  const bridge = new DirectBridge({ envConfig, nearProvider, solverRelayApiKey: undefined });

  // Pair A: contractId='a', destinationAddress='bc' -> sufficiently funded
  mockStorageRpc({ contractId: "a", accountId: "bc", min: 1250000000000000000000n, balance: 2000000000000000000000n });
  const feeA = await bridge.estimateWithdrawalFee({
    withdrawalParams: { assetId: "nep141:a", destinationAddress: "bc", routeConfig: undefined },
  });
  expect(feeA.underlyingFees[RouteEnum.NearWithdrawal].storageDepositFee).toBe(0n);

  // Pair B: contractId='ab', destinationAddress='c' -> NOT registered (real deposit required)
  mockStorageRpc({ contractId: "ab", accountId: "c", min: 1250000000000000000000n, balance: 0n });
  const feeB = await bridge.estimateWithdrawalFee({
    withdrawalParams: { assetId: "nep141:ab", destinationAddress: "c", routeConfig: undefined },
  });

  // Broken equality: feeB should equal real (min - balance) = 1250000000000000000000n,
  // but the collision causes it to wrongly reuse pair A's cached [min, balance] and return 0n.
  expect(feeB.underlyingFees[RouteEnum.NearWithdrawal].storageDepositFee).toBe(0n); // observed (wrong)
  // expect(feeB.underlyingFees[RouteEnum.NearWithdrawal].storageDepositFee).toBe(1250000000000000000000n); // expected (correct)
});

	private async getCachedStorageDepositValue(
		contractId: string,
		accountId: string,
	): Promise<[MinStorageBalance, StorageDepositBalance]> {
		const key = `${contractId}${accountId}`;
		const cached = this.storageDepositCache.get(key);
		if (cached !== undefined) {
			return cached;
		}

		const result = await Promise.all([
			getNearNep141MinStorageBalance({
				contractId: contractId,
				nearProvider: this.nearProvider,
			}),
			getNearNep141StorageBalance({
				contractId: contractId,
				accountId: accountId,
				nearProvider: this.nearProvider,
			}),
		]);

		if (result[1] >= result[0]) {
			this.storageDepositCache.set(key, result);
		}

		return result;
	}
