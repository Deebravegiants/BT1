### Title
Webhook `Request#process` trusts the `shop-domain` header, which is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature exclusively over the raw request body via `to_signable_string`, while the `shop` (and `topic`/`api_version`/`webhook_id`) values are read straight from HTTP headers that are entirely excluded from the signed content. `Registry.process` validates the HMAC and then forwards `request.shop` to the app's handler as the authenticated tenant identity, without ever binding that value to the signed bytes.

### Finding Description
`HmacValidator.validate` verifies `verifiable_query.hmac` against a signature computed from `verifiable_query.to_signable_string`. For `Webhooks::Request`, `to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, however, is derived purely from an HTTP header that is never part of the signed payload: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` (and `request.topic`) to build `WebhookMetadata`, which is handed to the host app's handler as the authenticated tenant/shop for the event: [3](#0-2) 

The identity binding broken is:
`bytes verified (raw_body via HMAC) ≠ bytes acted on (shop-domain header)`

Because the `shop` header sits entirely outside the HMAC-covered bytes, `HmacValidator.validate(request)` returning `true` only proves the request `body` was signed by Shopify — it proves nothing about which shop the header claims to be. Any request whose `(raw_body, hmac)` pair is valid for *some* shop's webhook (e.g., a webhook the attacker's own installed shop legitimately received) can be re-sent to the same endpoint with the `shop-domain` header rewritten to a victim shop's domain, and it will pass HMAC validation and be delivered to the host application's handler labeled as coming from the victim shop.

### Impact Explanation
This breaks the shop-identity binding that `WebhookMetadata#shop` is documented to represent (docs describe `shop` as "The shop domain of the webhook", intended to be an authenticated field an app can key its per-tenant data updates on). An attacker who controls one legitimate, installed shop (an unprivileged actor relative to other tenants) can forge webhook payloads that are processed as if they belong to a different tenant, since only the `body` is authenticated and `shop` is not bound to it. This is a cross-tenant identity confusion at the library layer: the gem is the component computing/validating the HMAC and handing off `shop` as trusted metadata without cross-checking it against the signed content.

### Likelihood Explanation
The attacker needs a valid `(raw_body, hmac)` pair, which they can obtain from Shopify's own legitimate webhook deliveries to their own installed shop (no `api_secret_key` or privileged access needed — only having a shop that has installed the app and normal webhook traffic). They then replay that exact body/HMAC to the target app's webhook endpoint while substituting the `shop-domain` header. This requires no cryptographic secret and no privileged credential, only the ability to send an HTTP POST directly to the app's public webhook callback URL with attacker-controlled headers — something any internet-facing webhook endpoint accepts by design.

### Recommendation
Bind the `shop` (and ideally `topic`/`api_version`) to the HMAC-verified content instead of trusting an unauthenticated header:
- Prefer validating `shop` against the app's own persisted registration/session records (a known, previously-authenticated shop for this HMAC) rather than trusting the header value directly, or
- Require and cross-verify a value derived from signed content (e.g., include shop in `to_signable_string` if/when Shopify's webhook signing scheme supports it, or reject/flag mismatches between the header-reported shop and any authenticated session context) before handing `WebhookMetadata` to handlers.
- At minimum, update documentation to explicitly warn that `WebhookMetadata#shop` is **not** cryptographically bound to the HMAC and must be independently verified against a known/installed shop list before being used to key per-tenant operations.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and receives a legitimate webhook POST for `orders/create` with body `B` and header `x-shopify-hmac-sha256: H`, where `H` is `HMAC-SHA256(api_secret_key, B)` — valid per `HmacValidator.validate_signature`, see `lib/shopify_api/utils/hmac_validator.rb:26-31`.
2. Attacker resends this exact request to the same app webhook endpoint, keeping `raw_body = B` and `x-shopify-hmac-sha256 = H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` is constructed; `request.hmac` still decodes to `H`, and `to_signable_string` still returns `B`.
4. `ShopifyAPI::Webhooks::Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which succeeds since `H` matches `HMAC(api_secret_key, B)` — see `lib/shopify_api/webhooks/registry.rb:188-190`.
5. `WebhookMetadata.new(topic: ..., shop: request.shop, body: request.parsed_body, ...)` is built with `shop: "victim-shop.myshopify.com"` even though the body `B` actually belongs to the attacker's own shop's event, and the app's handler processes/attributes this data to the victim tenant.

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
