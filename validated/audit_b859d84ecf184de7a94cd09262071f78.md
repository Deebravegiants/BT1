### Title
Webhook `shop` (and `topic`) identity is trusted from an unauthenticated header while only the raw body is covered by the HMAC, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) and the `topic` purely from HTTP headers, but the HMAC signature that `ShopifyAPI::Utils::HmacValidator` verifies is computed **only over the raw request body** [1](#0-0) [2](#0-1) . Because the `shopify-shop-domain` header is never part of the signed payload, any request that carries a *genuine* body/HMAC pair (obtainable by an attacker who legitimately installs the app on their own store and triggers a real webhook) will pass `HmacValidator.validate` regardless of which shop domain is placed in the header. `Registry.process` trusts this unauthenticated header value as the shop identity that is handed to the application's handler [3](#0-2) .

### Finding Description
The binding that should hold is:
`HMAC-verified-shop == shop-used-by-handler`

but the gem instead implements:
`HMAC-verified-bytes == raw_body` (only)
`shop-used-by-handler == headers["shopify-shop-domain"]` (unsigned, unverified)

`Request#shop` simply reads the header value with no cryptographic binding to the signed body [4](#0-3) . `Request#to_signable_string` — the only input to the HMAC check — returns `@raw_body` alone [1](#0-0) . `HmacValidator.validate_signature` recomputes the HMAC over that same signable string and compares it to the `hmac-sha256` header [2](#0-1) . Since Shopify's `client_secret` (and therefore `api_secret_key`) is shared across all shops that installed the same app (it is not shop-specific), a body+HMAC pair that is genuinely delivered for one shop remains a **valid signature** even when the `shop` header is swapped for a different shop domain.

`Registry.process` then raises only if the HMAC check fails; once it passes, it forwards `request.shop` unchecked into the handler's `WebhookMetadata` [3](#0-2) . Any application built on top of this gem that uses `WebhookMetadata#shop` to select the tenant/session context (the documented and expected usage per the gem's own webhook docs) will process attacker-supplied data under an attacker-chosen shop identity, even though the cryptographic guarantee it relies on (`HmacValidator.validate`) only proves the *body* came from Shopify — not that it belongs to the claimed shop.

### Impact Explanation
This breaks the tenant boundary the HMAC check is meant to enforce: an attacker who legitimately controls one shop (trivial — anyone can create a Shopify dev/partner store and install a public app) can capture a genuine, validly-signed webhook body for their own shop and resubmit it directly to the app's public webhook endpoint with the `shopify-shop-domain` header rewritten to a victim shop. The gem will accept it as authentic (`HmacValidator.validate` returns `true`) and hand the attacker-controlled body to the app's handler under the victim's shop identity — i.e., cross-tenant data injection/confusion using data the gem itself asserts is "verified." This matches the Critical impact category of cross-tenant access.

### Likelihood Explanation
The only prerequisite is the ability to install the app on an attacker-owned store (unprivileged, self-service) and network access to POST directly to the app's public webhook URL (which must already be internet-reachable to receive Shopify's webhooks). No access token, `api_secret_key`, or privileged credential is required — the attacker reuses a signature that was legitimately generated for their own data.

### Recommendation
Include the `shop` domain (and ideally `topic`, `webhook_id`, `api_version`) in the signed/verified material, or independently verify that the shop domain in the header corresponds to a shop for which the app holds a session/registration, before trusting `request.shop` in `Registry.process` and `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers any webhook (e.g., `orders/create`) whose body content they control (e.g., order note/line item title containing malicious payload).
2. Shopify delivers a legitimate request to the app's public webhook endpoint with:
   - `x-shopify-hmac-sha256`: valid HMAC over `raw_body`, computed with the shared `api_secret_key`
   - `x-shopify-shop-domain: attacker-shop.myshopify.com`
   - `raw_body`: attacker-controlled JSON
3. Attacker crafts a new HTTP POST to the same public webhook endpoint, reusing the identical `raw_body` and `x-shopify-hmac-sha256` value, but replacing the header with `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` accepts the request (headers present) [5](#0-4) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `raw_body` against the HMAC [6](#0-5) .
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and the attacker-controlled body, even though the victim shop never sent this webhook.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
