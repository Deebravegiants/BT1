### Title
Webhook `shop` domain is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `Utils::HmacValidator.validate` verifies the HMAC against that body alone. The `shop` (and `topic`) values used to attribute the webhook to a tenant are read straight from unauthenticated HTTP headers and are never included in the signed payload. Any party that can obtain one genuinely-signed webhook body/HMAC pair for the app's shared `client_secret` (e.g. a merchant who has installed the app on their own store) can replay that exact body+HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a different, victim shop. `HmacValidator.validate` will report success because it only checks the (unchanged) body, and `Registry.process` will dispatch the handler with the attacker-chosen `shop`, causing the app to attribute/process the webhook data as if it came from the victim tenant.

### Finding Description
The identity binding that should hold is:
`shop value cryptographically bound in the HMAC-signed payload == shop value the handler acts on`

In this gem that binding does not exist:

- `Request#to_signable_string` is defined as just the raw body: [1](#0-0) 
- `Request#shop` is pulled from the `shopify-shop-domain` / `x-shopify-shop-domain` header, entirely outside the signed content: [2](#0-1) 
- `HmacValidator.validate` computes the signature only from `to_signable_string` (the body) and compares it to the received `hmac` header: [3](#0-2) 
- `Registry.process` trusts the header-derived `shop` once the body-only HMAC check passes, and hands it straight to the handler: [4](#0-3) 

Because the `client_secret` (and therefore the HMAC key) is identical for every shop that installs the same app, any shop that has installed the app can generate its own genuinely-signed webhook (e.g. by creating/editing a resource that triggers a subscribed topic) and capture the resulting `(raw_body, hmac)` pair. That pair remains valid for *any* value of the `shop`/`topic` headers, since those headers are not part of the signed string. Replaying the same body+HMAC with the `X-Shopify-Shop-Domain` header changed to a different, victim shop passes `Utils::HmacValidator.validate` unchanged, and `Registry.process` will invoke the registered handler with `WebhookMetadata#shop` set to the victim's domain instead of the actual originating shop.

### Impact Explanation
This breaks the tenant boundary the webhook mechanism is supposed to enforce: a handler that keys its side effects (data writes, cache invalidation, billing, notifications, etc.) off `WebhookMetadata#shop` can be made to apply another merchant's webhook body under a victim shop's identity, or vice-versa attribute a victim's own webhook data as belonging to the attacker's shop. This is a cross-tenant access issue attributable to a gem-level design flaw (missing binding between the signed payload and the header-derived tenant identifier), matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is Medium: the attacker needs their own working install of the target app (a legitimate, if unprivileged, tenant) to obtain a validly signed body/HMAC pair, and needs to trigger the desired webhook topic/body content on their own shop, then replay it to the app's public webhook endpoint with a forged shop header. No access to the app's `client_secret` or another tenant's credentials is required — only the ability to install the app as any customer and control the header of the HTTP request sent to the app's public webhook receiver.

### Recommendation
Bind the tenant identity into the verified data before trusting it:
- Include `shop-domain` (and ideally `topic`, `webhook-id`, `api-version`) in the signed string checked by `HmacValidator`, or
- Independently verify that `request.shop` corresponds to a shop that is expected to receive this specific webhook (e.g. cross-check against a known/installed-shop list and the `webhook_id` returned by Shopify's API for that shop) before dispatching to the handler in `Registry.process`.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and triggers a webhook (e.g. `orders/create`), capturing the raw POST body and the `X-Shopify-Hmac-Sha256` header Shopify sends — this HMAC is valid because it's computed with the app's shared `client_secret`.
2. Attacker replays the exact same body and HMAC header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Utils::HmacValidator.validate` succeeds because `to_signable_string` only depends on the (unchanged) body.
4. `ShopifyAPI::Webhooks::Registry.process` calls the registered handler with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)`, causing the app to process the attacker's webhook body as though it belongs to the victim's tenant.

        def validate(verifiable_query)

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
