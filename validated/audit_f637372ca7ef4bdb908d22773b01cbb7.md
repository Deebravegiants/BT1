### Title
`shop-domain` and `topic` headers are trusted by `Registry.process` without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`HmacValidator.validate` only proves that `@raw_body` (via `to_signable_string`) was signed with the secret; the `x-shopify-topic` and `x-shopify-shop-domain` headers are never part of the signed data. `Registry.process` still uses `request.topic` to select the handler and `request.shop` to build `WebhookMetadata` before any authorization on those values exists, so an attacker who possesses one validly-signed `(raw_body, hmac)` pair can replay it with arbitrary `topic`/`shop` headers and have it accepted as authentic for a different tenant/topic. The base64-padding-leniency angle from the prompt is not itself exploitable (it cannot help forge a signature without the secret); the real, provable break is the missing signature coverage of `topic`/`shop`.

### Finding Description
The claimed binding is: `signed(@raw_body) == true` should imply `authenticated(request.topic, request.shop, request.parsed_body)`. Tracing the code shows this equality does not hold.

- `to_signable_string` returns only `@raw_body`: [1](#0-0) 
- `HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and compares it with the decoded `hmac` header: [2](#0-1) 
- `Registry.process` first validates the HMAC, then immediately dispatches on `request.topic` (looked up in `@registry`) and forwards `request.shop` into `WebhookMetadata` handed to the handler — neither value was part of the signed string: [3](#0-2) 
- `topic` and `shop` are read straight from attacker-suppliable headers with no cryptographic tie to the body: [4](#0-3) 

Root cause: the invariant "every value acted on downstream is inside the string handed to `HmacValidator`" is violated — `topic` and `shop` are acted on downstream (registry dispatch, handler metadata) but are outside `to_signable_string`.

Attack flow: the attacker sets up their own development shop, registers their own webhook endpoint, and receives one genuine `(raw_body, x-shopify-hmac-sha256)` pair from Shopify (explicitly permitted under the rules). They then POST that exact `raw_body` and `hmac` header to the target app's single shared webhook endpoint, substituting any `x-shopify-shop-domain` and `x-shopify-topic` header values they choose. `HmacValidator.validate` still succeeds because it only checks `@raw_body` against the secret; `Registry.process` then dispatches to whatever handler is registered for the forged `topic` and stamps the handler's `WebhookMetadata` with the forged `shop`. There is no code path in `Request`, `Registry`, or `HmacValidator` that binds `topic`/`shop` to the signature, and Sorbet typing does not add any semantic check — `T.cast` merely satisfies the type checker, not authenticity.

The base64-decode-leniency detail in the prompt (`Base64.decode64` silently ignoring invalid characters/padding) does not by itself defeat `OpenSSL.secure_compare` — an attacker without `api_secret_key`/`old_api_secret_key` cannot produce a `computed_signature` match regardless of how the header is padded, so that specific mechanism is not an exploitable primitive on its own. The actual demonstrable break is the missing coverage of `topic`/`shop` in `to_signable_string`, confirmed by the "Fast validation" test description itself (same signed body/hmac, two different `x-shopify-shop-domain` values, handler receives both without any error).

### Impact Explanation
Any app handler consuming `data.shop` or dispatching solely by `data.topic` (as shown by the gem's own `WebhookMetadata`/`Registry.process` contract) can be handed data falsely attributed to another shop or another webhook topic, while still passing HMAC verification. This is a cross-tenant confusion / authentication-bypass class issue: the app's trust boundary ("this shop/topic combination was verified by Shopify") is broken because the gem never verifies that binding, only the raw body's integrity. Repeatability is high — the attacker needs exactly one genuine webhook delivery to their own shop and can then replay it indefinitely with arbitrary shop/topic header values against the same app endpoint.

### Likelihood Explanation
Preconditions: the attacker must operate a real (even free development) Shopify shop, install the target app, and receive at least one legitimately signed webhook — all explicitly allowed under the stated threat model. No secret, access token, or privileged access is required. The webhook endpoint URL is typically shared across all shops/tenants of an app (it's the app's registered callback path), so no per-shop secret barrier exists to stop the replay. Cost to the attacker is minimal (one webhook capture, then scripted replays).

### Recommendation
Include `topic` and `shop` (and ideally `webhook_id`/`api_version`) in the signable string, or otherwise cryptographically bind them to the verified payload, so `HmacValidator.validate` fails whenever these header values are altered relative to what Shopify actually signed. At minimum, `Registry.process` should not trust `request.shop`/`request.topic` for cross-tenant decisions without an independent verification (e.g., confirming the shop is an installed/known session before acting on the payload).

### Proof of Concept
Minitest sketch (mirrors `test/webhooks/registry_test.rb` fixtures already present in the repo):
```ruby
def test_shop_header_not_covered_by_signature
  topic = "orders/create"
  body = "{}"
  hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, body)
  hmac_header = Base64.encode64(hmac)

  received_shops = []
  handler = TestHelpers::FakeWebhookHandler.new(lambda { |data| received_shops << data.shop })
  ShopifyAPI::Webhooks::Registry.add_registration(topic: topic, path: "path", delivery_method: :http, handler: handler)

  ["shop-a.myshopify.com", "shop-b.myshopify.com"].each do |shop|
    headers = {
      "x-shopify-topic" => topic,
      "x-shopify-hmac-sha256" => hmac_header,
      "x-shopify-shop-domain" => shop,
    }
    ShopifyAPI::Webhooks::Registry.process(ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: headers))
  end

  # Same signed body/hmac accepted for two different, unverified shop identities
  assert_equal(["shop-a.myshopify.com", "shop-b.myshopify.com"], received_shops)
end
```
Both requests pass `HmacValidator.validate` (identical `raw_body`/`hmac`), yet `data.shop` differs per request, proving `topic`/`shop` are outside signature coverage while still being acted on by `Registry.process`.
