### Title
Manipulable instantaneous utilization lets an attacker permanently erase accrued interest/fees via `accrue` - (File: mainnet/contracts/vault/v0-vault-usdc.clar and equivalent v0-vault-*.clar vaults)

### Summary
`accrue()` computes the interest rate to apply retroactively over the *entire elapsed time* since `last-update` using the **current, spot** utilization at the moment of the call, rather than a time-weighted historical utilization. Because utilization can be manipulated within a single transaction (e.g. via a large flash-funded deposit or repay), an attacker can force the rate applied over a long stale period to be near zero, permanently wiping out interest that should have accrued to lenders and fee-reserve shares that should have been minted to the treasury — the same "single manipulable spot value applied over a stale-but-long accounting window" bug class as `OCL_ZVE.sol::fetchBasis`/`forwardYield`, where a manipulated Uniswap V2 spot reading was baked into `basis` and persisted across the next distribution window.

### Finding Description
`accrue()` is public and permissionless, and is invoked internally by `deposit`, `redeem`, `system-borrow`, `system-repay`, `set-fee-reserve`, `set-points-util`, `set-points-rate`, and `set-pause-states`: [1](#0-0) 

The rate used inside `next-index` is derived from `interest-rate()`, which is a function of the **current** `utilization()`: [2](#0-1) 

`next-index` then applies that single spot rate over the **entire** `time-delta` since `last-update` (which can be arbitrarily long — hours, days, or however long since the last call to any of the functions above):
```
(rate (interest-rate))
(time-delta (- stacks-block-time (var-get last-update)))
(multiplier (if (is-eq time-delta u0) INDEX-PRECISION (calc-multiplier-delta rate time-delta true)))
(calc-index-next idx multiplier)
``` [3](#0-2) 

The fee-reserve treasury share mint (`treasury-lp`) is computed from that same debt delta: [4](#0-3) 

Once `accrue()` runs, `index`/`lindex` are updated and `last-update` is advanced to `stacks-block-time` — this permanently commits the (possibly manipulated) delta; there is no mechanism to "catch up" missed interest for the elapsed period afterward. [5](#0-4) 

This is structurally identical to the reported bug: in `OCL_ZVE.sol`, `fetchBasis()` reads a manipulable, spot AMM-derived value and that value is committed into `basis`, which then governs distribution for the entire next 30-day window; here, `interest-rate()` reads a manipulable, spot utilization value and that value is committed into the index growth for the entire elapsed window since `last-update`, which can be an arbitrary, long stale period.

### Impact Explanation
An attacker who holds an outstanding borrow position (or intends to borrow) can flash/large-fund a deposit to spike `available-assets`, driving `utilization()` toward zero and thus `interest-rate()` toward zero, then call (or trigger via `deposit`) `accrue()` to lock in a near-zero index multiplier for the entire elapsed period. This permanently erases interest that should have accrued to depositors (unclaimed yield) and the corresponding `fee-reserve` share that should have been minted to the DAO treasury (unclaimed protocol fee revenue) — both fall under the "theft of unclaimed yield" high-severity bucket, since interest for that time window is gone forever once `last-update` advances. In the reverse direction, an attacker with a large deposit position could spike utilization instantaneously right before `accrue()` to inflate the rate applied over a long stale window, over-crediting the index (and thus over-minting withdrawable value to their own shares) at the expense of the vault's real assets, which risks insolvency for other depositors.

### Likelihood Explanation
`accrue()` requires no privileged role and is triggered by ordinary user-facing functions (`deposit`, `redeem`, borrow/repay) that any account can call, so no admin/DAO compromise is needed. The manipulation only requires capital sized relative to the vault's `available-assets`/`total-debt`, deployable via a flash loan purely as capital (permitted per scope rules) or a sufficiently large self-funded deposit. The attack becomes more attractive the longer `last-update` has been stale (e.g., low-traffic vaults, or windows between keeper/automation calls), mirroring the original report's dependence on the keeper being delayed.

### Recommendation
Do not let a single spot reading of `utilization()` govern interest accrual over an arbitrarily long stale window. Options: (1) accrue interest incrementally/checkpointed more frequently so that any single block's utilization only affects a bounded time window; (2) use a time-weighted-average utilization (TWAU) over the elapsed period instead of the instantaneous value at the `accrue()` call block; (3) bound the maximum utilization swing usable per accrual call, or require `accrue()` to be called at fixed cadence by a trusted keeper with a fallback that reverts (rather than silently using the manipulated spot rate) if the elapsed window exceeds a safe threshold.

### Proof of Concept
1. Attacker observes a vault (e.g. `v0-vault-usdc.clar`) where `last-update` has not been refreshed for a long period (e.g. no `deposit`/`redeem`/`borrow`/`repay` calls in that window). [6](#0-5) 
2. Attacker takes a flash loan of the underlying asset and calls `deposit` with a very large `amount`, which internally calls `accrue()` **before** updating `assets`, but the deposit's own capital is already available to the pool at the time other users interact, OR the attacker performs the deposit in the same block and then immediately calls `accrue()`-triggering function again — either way `available-assets` (and thus `utilization()`) is depressed at the moment `interest-rate()` is evaluated. [7](#0-6) 
3. `next-index` computes a near-zero `rate` and applies it across the full stale `time-delta`, permanently advancing `last-update` and `index` with minimal growth; `treasury-lp` fee mint is also minimized. [8](#0-7) 
4. Attacker withdraws (`redeem`) their deposit in the same or next block, repaying the flash loan, having permanently suppressed interest/fee accrual for the vault over that entire elapsed window — a benefit to any concurrent borrower (including the attacker, if they hold debt) and a loss to lenders/treasury.

Note: I was unable to fully verify the exact bodies of `interpolate-rate`, `calc-utilization`, `calc-multiplier-delta`, and `get-available-assets` due to running out of tool iterations before the final read — their signatures and call sites were confirmed, but full line-by-line arithmetic was not re-verified in this pass.
