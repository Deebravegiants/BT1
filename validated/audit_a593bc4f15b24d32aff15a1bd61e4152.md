### Title
Webhook `shop-domain` header not covered by HMAC allows cross-tenant shop spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw request body, then trusts the unauthenticated `shop-domain` header to identify which tenant the event belongs to. Because the identity-binding field (`shop`) is not included in the signed payload, an attacker who legitimately receives one genuine, validly-signed webhook (e.g., by installing the public app on their own store) can replay that exact body+HMAC to the app's webhook endpoint while substituting an arbitrary `shop-domain` header, causing the handler to process the event as if it originated from a different shop.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read straight from the `shop-domain` header, independent of the signed content: [2](#0-1) 

`Registry.process` verifies only the HMAC (over the body) and then hands `request.shop` (the unauthenticated header) directly to the handler as the tenant identity: [3](#0-2) 

`HmacValidator.validate` computes the signature purely from `to_signable_string` (the body) using the app's single, shared `api_secret_key` across all shops that install the app: [4](#0-3) 

The identity binding broken is: `shop-domain header == shop bound inside the HMAC-signed content`. In this gem that equality is never enforced — the header is not part of `to_signable_string`, so the HMAC only proves "this body was produced by an app installed with this `api_secret_key`" and says nothing about which of the app's shops it came from. Because `api_secret_key` is shared across every merchant that installs the app, any merchant (an unprivileged internet user who simply installs the public app on their own store) receives genuine webhooks with a valid HMAC for that body. They can then send that captured body and HMAC to the app's webhook endpoint again, this time with a forged `shop-domain` header pointing at a different (victim) shop. `Registry.process` will pass HMAC validation (the body/HMAC pair is genuine) and dispatch to the handler with `shop: <attacker-chosen value>`, per the documented `data.shop` contract: [5](#0-4) 

This lets an attacker inject events attributed to a shop they do not control into the host app's per-tenant processing logic (e.g., triggering the app to write, or act on, data associated with a shop id it did not actually receive from).

### Impact Explanation
This breaks the tenant/shop identity binding that the webhook subsystem is supposed to guarantee — the entire purpose of `shop` in `WebhookMetadata` is to scope the incoming event to the correct tenant. An attacker can present events as if they belong to an arbitrary target shop, resulting in cross-tenant data confusion in any host application that keys its per-shop processing off `data.shop` without separately corroborating it (which is exactly how this gem documents and demonstrates using it). This meets the Critical bar for cross-tenant access.

### Likelihood Explanation
High. The only prerequisite is that the attacker has legitimately installed the same public app on any shop they control (a completely unprivileged action) so they can capture one genuine `(raw_body, hmac)` pair; no access token, `client_secret`, or credential theft is required. They then replay that pair with a forged `shop-domain` header to the app's public webhook endpoint.

### Recommendation
Bind the shop identity into the signed material, or otherwise cryptographically tie the `shop-domain` header to the payload before trusting it: either include the `shop-domain` header in `to_signable_string` for webhook requests, or require host applications to re-validate `request.shop` against an installed/known session before processing — and document this requirement explicitly in `docs/usage/webhooks.md`, since currently the documented handler contract implies `data.shop` can be trusted as-is.

### Proof of Concept
1. Install the target app (any public app using this gem) on attacker-controlled shop `attacker.myshopify.com`.
2. Trigger a webhook event (e.g., `orders/create`) on the attacker's own shop; capture the raw body and the `X-Shopify-Hmac-Sha256` header Shopify sends — this HMAC is valid because it's computed with the app's shared `api_secret_key` over the body only, per `HmacValidator.validate`.
3. POST that same raw body and HMAC header to the app's registered webhook endpoint, but replace `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com`.
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:189-200`) validates the HMAC successfully (body unchanged) and invokes the handler with `shop: "victim-shop.myshopify.com"`, causing the host app to process/attribute the event to the victim shop.

```ruby
        sig { params(request: Request).void }
        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
```

```ruby
          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
```
