Confirmed: the webhook `hmac` is computed and validated only against the raw request body (`to_signable_string` returns `@raw_body`), while `topic`, `shop`, `api_version`, and `webhook_id` are all pulled straight from unauthenticated HTTP headers via `shopify_header` and passed downstream unverified.

### Title
Webhook `shop` (and `topic`/`webhook_id`) header is trusted for tenant routing without being covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC over the raw body only, but the shop domain that is later used as the tenant identity for the webhook handler is read from an HTTP header that is never included in that signature. This breaks the intended binding `hmac == HMAC(secret, body ‖ shop)`; in reality the gem only enforces `hmac == HMAC(secret, body)`, so `shop` is a free variable an attacker (an app installer on their own shop) can set to any value while still presenting a cryptographically valid signature.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are all read from headers that are never part of the signed material: [2](#0-1) [3](#0-2) 

`Utils::HmacValidator.validate` only checks `verifiable_query.to_signable_string` (the body) against the secret-derived HMAC — it has no knowledge of `shop`: [4](#0-3) 

`Registry.process` accepts any request that passes this body-only HMAC check and then forwards the unauthenticated `request.shop` directly into the handler's tenant-identifying metadata: [5](#0-4) 

Since Shopify's `client_secret` (used to key the HMAC) is per-app and shared across every shop that has the app installed, any merchant who installs the app on their own store legitimately receives HTTP webhook deliveries carrying a valid `hmac` for arbitrary bodies they control (e.g., by triggering events on their own store). That attacker can then replay the exact same `body` + `hmac` to the app's webhook endpoint while swapping the `x-shopify-shop-domain` header to a victim shop. `HmacValidator.validate` still passes (it never looked at the shop header), and `Registry.process` hands the handler a `WebhookMetadata` claiming the payload came from the victim's shop.

### Impact Explanation
This breaks the binding "shop authenticated versus the shop acted upon" — the identity used for tenant routing (`request.shop`) is not the identity actually verified by the HMAC (only the body is verified). Any host application that uses `WebhookMetadata#shop` to select which tenant's data to update, look up, or process (a documented and expected use per `lib/shopify_api/webhooks/webhook_metadata.rb` and the registry API) can be made to apply attacker-controlled webhook content under a victim shop's identity — i.e., cross-tenant data confusion/injection, which is Critical impact.

### Likelihood Explanation
Exploitation only requires an attacker to be an ordinary merchant who installs the target app (no special privilege, no leaked secret, no TLS interception) and can freely craft their own webhook payloads/headers to the public webhook endpoint. The only "hard" requirement — a valid HMAC for a chosen body — is trivially satisfied because the attacker triggers genuine Shopify webhook deliveries on their own store, which the app's secret validly signs; only the header (never signed) needs to be altered afterward.

### Recommendation
Include the shop domain (and ideally topic/webhook_id) in the HMAC-covered material, or independently verify the `shop` header against a known, previously-authenticated tenant (e.g., cross-check against a stored session for that shop, or validate the shop suffix/format and reconcile it against the app's own installation records) before trusting it in `WebhookMetadata`. At minimum, document to consuming apps that the `shop` header of `ShopifyAPI::Webhooks::Request` is not authenticated by the HMAC and must not be trusted as a tenant boundary on its own.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`.
2. Trigger a webhook event (e.g., `orders/create`) on that shop; capture the resulting HTTP POST, including its genuine `x-shopify-hmac-sha256` header and raw body — both are valid because they were produced and signed by Shopify using the app's real `client_secret`.
3. Replay this exact POST to the app's webhook endpoint, but replace the `x-shopify-shop-domain` header with `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (`@raw_body`, unchanged) and compares it to the unchanged `hmac` header — validation succeeds.
5. `handler.handle(data: WebhookMetadata.new(..., shop: request.shop, ...))` is invoked with `shop == "victim-shop.myshopify.com"`, even though the body/content actually originated from the attacker's shop, demonstrating cross-tenant identity confusion carried entirely by unauthenticated header data.

          received_signature = verifiable_query.hmac
