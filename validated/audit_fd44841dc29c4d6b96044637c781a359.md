### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/registry.rb], [File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely via `Utils::HmacValidator.validate(request)`, whose signable content is `Request#to_signable_string`, which returns **only** the raw request body [1](#0-0)  and [2](#0-1) . The `shop` value that is handed to the handler and used to attribute the webhook to a tenant comes from the `shopify-shop-domain` HTTP header, a field that is completely excluded from the HMAC computation [3](#0-2) . `Registry.process` validates the HMAC and then immediately trusts `request.shop` when constructing `WebhookMetadata` for the handler [4](#0-3) .

### Finding Description
The identity binding that should hold is:
`hmac_signed_bytes == bytes_that_determine_the_tenant("shop")`

In this gem it does not: `hmac_signed_bytes == raw_body` while `shop == headers["shopify-shop-domain"]` (or the legacy `x-shopify-shop-domain`), which is a value read from `@headers` and never mixed into `to_signable_string` [5](#0-4) .

The HMAC secret (`Context.api_secret_key`, the app's `client_secret`) is shared by Shopify across **every shop** that has installed the app — it is not shop-specific. Consequently, `OpenSSL.secure_compare(computed_signature, received_signature)` in `HmacValidator.validate_signature` only proves "this body was signed by someone in possession of this app's secret" (i.e., Shopify, for any of the app's installs) — it proves nothing about which shop the body belongs to [6](#0-5) .

An attacker who legitimately installed the app on their own shop (unprivileged relative to other tenants of the same app) receives genuine webhook deliveries with a valid `x-shopify-hmac-sha256` for their own shop's body. Because the header carrying the tenant identity (`shop-domain`) is not part of the signed content, the attacker can resend that same body/HMAC pair to the app's webhook endpoint while substituting the `shop-domain` header with a victim shop's domain. `Registry.process` will still consider the HMAC valid (it only checks the body) and will invoke the handler with `shop: <victim-shop>` [7](#0-6) , even though the signature never attested to that shop.

This is exactly the "field acted on but not covered by the HMAC" pattern from the report: `stable_pool::repay_stable_from_liquidation` trusted an unauthenticated `minter` parameter while performing a privileged transfer; here `Registry.process`/`WebhookMetadata` trusts an unauthenticated `shop` header while performing tenant-scoped side effects (job enqueuing, DB writes keyed by shop, etc., per the gem's documented handler contract) [8](#0-7) .

### Impact Explanation
This crosses the tenant boundary that the gem's `process` API is documented to enforce ("This will verify the request did indeed come from Shopify…") [9](#0-8) . Any host application that follows the documented contract and trusts `data.shop` from `WebhookMetadata` as an authenticated tenant identifier (as the gem's own example handler does — `perform_later(topic: data.topic, shop_domain: data.shop, ...)` [10](#0-9) ) is exposed to cross-tenant data injection: an attacker with any single valid install of the app can make the app believe arbitrary shop-scoped events occurred for a different (victim) shop, potentially triggering shop-scoped business logic (e.g., `orders/create`, `app/uninstalled`, GDPR topics) attributed to a shop they do not control. This is a cross-tenant access vector (Impact: Critical per the rubric's "cross-tenant access" category), rooted entirely in this gem's `Webhooks::Request`/`Registry` code.

### Likelihood Explanation
Likelihood is moderate-to-high for any app that has at least one real install (an "unprivileged internet user" relative to other tenants only needs to install the target app once, which is normal, low-friction Shopify app installation — not a privileged action). No secrets need to be recovered; the attacker only needs one authentic webhook delivery for their own shop and the ability to POST arbitrary headers to the app's public webhook endpoint.

### Recommendation
Bind the shop identity into the verified signature material, or otherwise cryptographically tie the `shop-domain` header to the signed payload before trusting it:
- Do not treat `request.shop` (from `shopify-shop-domain`/`x-shopify-shop-domain`) as authenticated by `HmacValidator.validate`; document/require that host apps additionally validate the shop against a shop for which they have an active session/registration (see `webhook_id`/topic uniqueness), or
- Extend `to_signable_string`/HMAC scheme to include the shop domain (would require a corresponding change on Shopify's signing side), or, more practically for this gem,
- Cross-check the incoming `shop` header against known registered shops (e.g., verify the app actually has a stored session/subscription for that shop and topic) before dispatching to the handler in `Registry.process`.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`.
2. Attacker triggers (or waits for) a real webhook delivery, capturing `raw_body` (e.g., `{}` or any real order payload) and its valid `x-shopify-hmac-sha256` header — both computed by Shopify using the app's shared `client_secret`.
3. Attacker POSTs to the app's registered webhook endpoint with:
   - `raw_body`: unchanged from step 2
   - `x-shopify-hmac-sha256`: unchanged from step 2 (still valid, since it only signs the body)
   - `x-shopify-shop-domain`: `victim-shop.myshopify.com` (attacker-chosen)
   - `x-shopify-topic`, `x-shopify-webhook-id`: attacker-chosen/reused values
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `to_signable_string` (`raw_body`) against the secret [11](#0-10) .
5. The handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: "victim-shop.myshopify.com", body: ..., ...)` [12](#0-11) , causing the host application to process an event as if it genuinely originated from the victim shop, despite the signature never attesting to that shop.

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
