### Title
Webhook shop-domain identity is trusted without HMAC coverage, enabling cross-tenant webhook spoofing via replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw request body, then hands the caller-supplied `shop-domain` header straight through to the app's handler as the trusted tenant identity — without that header ever being part of the signed data. This is the same class of bug as the oracle report: a field that is *acted on* (the shop identity used by the consuming logic) is not covered by the integrity check (`hmac`) that is supposed to guarantee authenticity.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`, and its `to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are all read from HTTP headers that are completely outside the signed bytes: [2](#0-1) 

`HmacValidator.validate` only checks `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)` — i.e., against the raw body only: [3](#0-2) 

`Registry.process` then treats the request as fully authenticated and forwards the unauthenticated `request.shop` header value as the tenant identity to the app's handler: [4](#0-3) 

The documented handler contract explicitly tells app authors that `data.shop` is "The shop domain of the webhook," implying it is a trustworthy, Shopify-asserted tenant identifier once `Registry.process` succeeds: [5](#0-4) 

**Binding that should hold but doesn't:** `hmac == HMAC(secret, body || shop || topic)` is what an app author is led to believe `Registry.process` guarantees; in reality the gem only guarantees `hmac == HMAC(secret, body)`, with `shop` left as an arbitrary, attacker-controllable header value on any request whose body/HMAC pair the attacker can obtain (e.g. from a legitimately-installed instance of the app on their own shop, or from any body they can otherwise get validly signed — note bodies for topics like `app/uninstalled`, `shop/redact`, etc. carry no shop identifier of their own).

### Impact Explanation
Any endpoint implementing the documented pattern (`ShopifyAPI::Webhooks::Registry.process(Request.new(raw_body:, headers:))`) receives `data.shop` as the tenant key. If a host app uses `data.shop` to look up which merchant's session/access token to act on (a very common integration pattern for webhook-triggered background jobs, exactly as shown in the gem's own doc example `perform_later(topic: data.topic, shop_domain: data.shop, ...)`), an attacker who can obtain one validly-signed body+HMAC pair for the correct secret (trivially available since they can install their own free/dev store instance of any public app and receive genuine webhooks) can resend that same body/HMAC with a spoofed `x-shopify-shop-domain` header naming a victim shop. `Registry.process` will accept it as authentic and the handler will process attacker-controlled webhook content under the victim's tenant identity — a cross-tenant access primitive. Depending on the topic and how the host app wires the data (e.g. triggering `app/uninstalled` cleanup, refunds, or fulfillment logic keyed by shop), this can corrupt or exfiltrate another merchant's data or trigger authenticated actions against the wrong tenant.

### Likelihood Explanation
High reachability: the vulnerable code path (`Registry.process` → `HmacValidator.validate` → handler dispatch with unauthenticated `shop`) is the gem's only documented and supported mechanism for processing webhooks, so every app built per the docs is affected the same way. The only prerequisite is obtaining one valid `(body, hmac)` pair signed with the target app's real `client_secret`, which any developer can trivially get by installing the app themselves (no privileged credentials, TLS interception, or social engineering needed) and replaying it toward the app's public webhook endpoint with a different shop header.

### Recommendation
- **Short term:** Document (and where feasible enforce) that `shop-domain`/`x-shopify-shop-domain` must never be trusted for tenant-identity decisions unless corroborated by an existing, independently-established session/registration record for that exact shop; reject webhooks whose `shop` does not match a shop with an active, previously-registered webhook subscription tracked by the app.
- **Long term:** Extend `VerifiableQuery`/`HmacValidator` for webhooks so the signable string binds the header fields that matter for tenant identity (e.g., include `shop`, `topic`, `webhook_id` alongside the raw body when computing/verifying the signature, matching how Shopify's own webhook replay-protection guidance recommends deduplicating on `webhook_id` *and* validating shop context out-of-band), so that `hmac` validation cannot be satisfied by body/HMAC reuse under a different shop header.

### Proof of Concept
1. Attacker installs the target public app on their own store `attacker-shop.myshopify.com` (no special privileges required — any Partner/dev account can do this).
2. Attacker triggers a real webhook for a topic whose body carries no shop-specific data of interest for the app's business logic (e.g. `app/uninstalled`, or a generic topic with minimal body), capturing the exact `raw_body` and the corresponding `x-shopify-hmac-sha256` value Shopify sent them — a value that is a valid HMAC under the real app `client_secret`, since it's computed against `raw_body` only.
3. Attacker POSTs that same `raw_body` and `x-shopify-hmac-sha256` to the app's public webhook endpoint again, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` instead of their own shop.
4. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `Registry.process` calls `HmacValidator.validate(request)`, which recomputes the HMAC over `raw_body` only and matches — validation passes.
5. `Registry.process` invokes the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`; the host app, following the gem's documented pattern, acts as though this is a genuine webhook for `victim-shop`, even though `victim-shop` never sent it and its own secret/session was never involved.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
