### Title
Webhook shop-domain (and topic/webhook-id) header spoofing — HMAC only covers raw body, not the identifying headers - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so `Utils::HmacValidator.validate` authenticates nothing but the JSON body bytes. The `shop` (and `topic`, `webhook_id`, `api_version`) values that `Registry.process` extracts and hands to the app's `WebhookHandler` come straight from HTTP headers (`X-Shopify-Shop-Domain`, etc.) that are never included in the signed material, so they carry no cryptographic binding to the shop that actually generated the event.

### Finding Description
`Request#to_signable_string` at [1](#0-0)  is defined as just `@raw_body`. `Registry.process` verifies the request with `Utils::HmacValidator.validate(request)` [2](#0-1) , and `HmacValidator.validate_signature` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to `verifiable_query.hmac` [3](#0-2) . Because `to_signable_string` is only the raw body, the signature is entirely independent of the `shop`, `topic`, `webhook_id`, and `api_version` accessors, which are read straight from headers [4](#0-3) .

`Registry.process` then trusts `request.shop` to build `WebhookMetadata` and dispatches it to the app's handler unchanged [2](#0-1) . `WebhookMetadata.shop` is the field host apps are documented to use as the tenant identifier for the event [5](#0-4) , and the gem's own docs instruct apps to key their processing off `data.shop` (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`).

The binding this breaks, stated as an equality that should hold but doesn't:
`shop_used_for_tenant_routing == shop_that_actually_produced_the_signed_body`

Since the app's client/webhook secret (`Context.api_secret_key`) is shared across every shop that has the app installed, any unprivileged internet user can install the (public) app on their own development/test store, receive a genuinely-signed webhook for that store, and replay the identical raw body + HMAC value while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header to name a *different* shop. `HmacValidator.validate` still succeeds because it only checks the untouched body bytes, and `Registry.process` forwards the attacker-chosen `shop` value to the handler as if it were authentic.

### Impact Explanation
This is a cross-tenant identity confusion: an attacker-controlled payload (fully attacker-authored content, since it originates from a webhook the attacker triggered on their own store) can be attributed to an arbitrary other shop domain when it reaches the host application's webhook handler. Any app that uses `data.shop` from `WebhookMetadata` to select which merchant's records/session/access token to act on (exactly as the gem's own documentation recommends) can be made to write, delete, or otherwise process attacker-supplied data under a victim tenant's identity — a cross-tenant access/data-integrity break, without needing the target's credentials, access token, or `api_secret_key`.

### Likelihood Explanation
Any actor able to install the target app on a shop they control (a normal, unprivileged action for any public Shopify app) can obtain a validly-HMAC'd webhook body signed with the shared app secret, then trivially replay it over HTTP with a modified `shop-domain` (or other) header to any webhook endpoint the host app exposes — no elevated access or reversing of secrets required.

### Recommendation
Include the identifying headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signed material returned by `Request#to_signable_string` (or otherwise cryptographically bind them, e.g. by validating `shop` against a separately-authenticated source such as the shop tied to the stored session/access token before dispatching), instead of authenticating only `@raw_body`.

### Proof of Concept
1. Attacker installs the vulnerable multi-tenant app on their own store `attacker.myshopify.com` (a normal, permitted action for any public app).
2. Shopify sends a legitimate webhook to the app's endpoint: body `B`, headers including `X-Shopify-Hmac-Sha256: H` (valid HMAC of `B` using the shared app secret) and `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. Attacker captures this request and resends it to the same endpoint, keeping body `B` and header `X-Shopify-Hmac-Sha256: H` unchanged, but rewrites `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `Registry.process` calls `HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string == B` and matches `H` — validation passes [6](#0-5) .
5. `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` using the spoofed `shop` header value and dispatches it to `handler.handle` [7](#0-6)  — the host app now processes attacker-controlled body `B` as though it were an authentic event for `victim.myshopify.com`.
