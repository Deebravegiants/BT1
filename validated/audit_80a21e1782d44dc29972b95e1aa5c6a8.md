### Title
Webhook shop-domain spoofing via HMAC that binds only the request body, not the `shopify-shop-domain` header - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook by recomputing an HMAC over the **raw request body only** and comparing it to the `x-shopify-hmac-sha256`/`shopify-hmac-sha256` header, but it reads the **shop identity** (`data.shop`) from a completely separate, unsigned header (`x-shopify-shop-domain`/`shopify-shop-domain`). Because the HMAC digest is computed exclusively from the JSON body bytes, the shop-domain claim that the host application uses to route/attribute the webhook is never bound to the signature that authenticates the request.

### Finding Description
The webhook signature verification flow, as exercised in `test/webhooks/registry_test.rb:271-330` and `test/webhooks/request_test.rb:31-89`, shows: [1](#0-0) [2](#0-1) 

The HMAC is computed as `OpenSSL::HMAC.digest(sha256, api_secret_key, raw_body)` — the signable material is only the request body string, e.g. `"{}"`. The `shopify-shop-domain` header is parsed into `request.shop` independently and is never included in the signable string used to derive/verify the HMAC. `ShopifyAPI::Webhooks::Registry.process` accepts the request once `raw_body` HMAC validation passes and then hands `data.shop` (sourced purely from the unauthenticated header) to the registered handler as the shop the webhook is "for."

This breaks the intended identity binding: **shop claimed in the request == shop actually authenticated by the signature**. Since the signature only proves "this body was HMAC-signed by an app secret holder for *some* webhook," and not "this body was signed *for shop X*," any request whose body happens to match a body Shopify has already signed for a *different* shop (or a shop the attacker legitimately owns) can have its shop-domain header rewritten and still pass verification. Many webhook payloads are trivially reproducible or predictable per-topic (e.g., `app/uninstalled` payloads, low-entropy JSON bodies, or bodies an attacker can observe from webhooks fired to their own store), making body-only signing insufficient to prevent shop-domain spoofing.

Contrast this with `AuthQuery`'s HMAC design, where **every** field that identity-sensitive logic relies on (`shop`, `host`, `code`, `state`, `timestamp`) is explicitly included in the signable string: [3](#0-2) 
The webhook path does not apply the same principle to the shop-domain header.

### Impact Explanation
An app that uses `ShopifyAPI::Webhooks::Registry.process`/`Request` to dispatch webhook handling by `shop` (the normal, documented usage pattern) can be tricked into applying a webhook payload to the wrong merchant's data/session. Because the shop attribution is not covered by the cryptographic proof, this is a cross-tenant identity-confusion vector: an attacker who controls or can observe any Shopify shop (including their own store, which is sufficient to receive legitimately signed webhooks with attacker-chosen/predictable content in some topics) can relay that valid signature+body pair while substituting the shop-domain header of a victim shop, causing the receiving app to process/act on data as if it originated from the victim tenant.

### Likelihood Explanation
Exploitation requires (a) obtaining at least one legitimately-signed webhook whose body content is attacker-controlled, predictable, or reproducible for the target topic, and (b) the ability to replay/re-send an HTTP request to the app's webhook endpoint with a modified shop-domain header (which any internet-reachable webhook endpoint accepts, since delivery is just an HTTP POST). No leaked credentials, `api_secret_key`, or access tokens are required — only ordinary access to one's own Shopify store to receive real webhooks, satisfying the "unprivileged internet user" bar. Likelihood is moderate: it depends on payload predictability/replayability per topic, but the underlying binding gap (shop domain not in the HMAC-signed material) is unconditional.

### Recommendation
Bind the shop-domain claim to the signature the same way `AuthQuery` binds `shop`/`host`/`state`: either (1) include the shop domain (and ideally webhook id / topic) in the HMAC-signable material before verification, or (2) require host applications to cross-check `request.shop` against an independently known/authorized shop for the session before trusting it, and document this requirement prominently. At minimum, `Webhooks::Request`/`Registry` should not expose `shop` as a trusted identity value derived purely from an unsigned header.

### Proof of Concept
1. Attacker installs the target app on their own Shopify store `attacker.myshopify.com` and triggers a webhook whose JSON body is fully attacker-controlled or predictable (e.g., an empty/normalized payload like `{}` as used in tests) for a topic also relevant to the victim.
2. Attacker's server receives the legitimately-Shopify-signed webhook: headers `shopify-hmac-sha256: <valid-HMAC-of-body>`, `shopify-shop-domain: attacker.myshopify.com`, and raw body `{}`.
3. Attacker resends this exact POST to the app's public webhook endpoint but rewrites `shopify-shop-domain: victim.myshopify.com`, leaving body and HMAC header untouched.
4. `ShopifyAPI::Webhooks::Registry.process` recomputes the HMAC over the (unchanged) raw body and it matches — as shown by `OpenSSL::HMAC.digest(secret, "{}")` in `test/webhooks/registry_test.rb:284-298` — so verification passes, and the handler receives `data.shop == "victim.myshopify.com"` even though Shopify never issued a webhook for the victim shop with this body.
