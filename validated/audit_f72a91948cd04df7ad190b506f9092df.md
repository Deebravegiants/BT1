### Title
`EmporiumUpgradeable.runAction` only sweeps/verifies tokens the attacker chooses to list in `circomData.erc20TokenAddresses`, letting a CASE 2 op drain any other token balance held by Emporium - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`runAction` computes `balancesBefore`/`balancesAfter` and the `BalanceChangeShouldBePositive()` guard exclusively over `circomData.erc20TokenAddresses`, an array fully controlled by whoever crafts the transaction's `CircomData`. Because the CASE 2 "stateless" branch permits an arbitrary `op.endpoint.call(op.callData)` with no restriction on target or calldata (only wallet-selector calls are blocked), an attacker can craft an op that calls `transfer(attacker, amount)` on any ERC20 token held by the Emporium contract while simply omitting that token address from `erc20TokenAddresses`, bypassing all balance accounting for it.

### Finding Description
The equality the contract is meant to enforce is: for every token whose balance the Emporium contract moves during `runAction`, `balancesAfter[i] - balancesBefore[i] + (deltaAmountChanges[i] < 0 ? -deltaAmountChanges[i] : 0) >= 0` must hold, and the resulting `handleOut` UTXO must capture the exact leftover. [1](#0-0) 

That equality is only ever evaluated for indices `i` inside `circomData.erc20TokenAddresses`. Since this array, `stack.ops`, and `deltaAmountChanges` are all attacker-supplied fields of `CircomData` (attacker crafts their own proof/UTXOs and metadata per the threat model), an attacker can:

1. Set `circomData.erc20TokenAddresses = []`.
2. Encode an `EmporiumStack` with a single op where `invokeWallet = false` and `stack.signerAddress == address(0)` (forcing CASE 2), `op.endpoint = vaultShareERC20`, `op.callData = abi.encodeWithSelector(IERC20.transfer.selector, attacker, amount)`. [2](#0-1) 

The only restriction on CASE 2 is a selector check to block `callHinkalWallet`/`doSendToRelay`; there is no restriction on which ERC20 contract can be targeted or that the target must appear in `erc20TokenAddresses`. [3](#0-2) 

Since the loop over `circomData.erc20TokenAddresses` is empty, `balancesBefore`/`balancesAfter` never observe `vaultShareERC20`, `BalanceChangeShouldBePositive()` cannot trigger, and no `deltaAmountChanges` entry is required or checked for it — the token simply leaves the Emporium contract to the attacker with zero on-chain accounting tying that movement to the shielded-value ledger. `runAction` itself acknowledges (in a code comment) that Emporium balances can legitimately carry over between transactions ("the only case when balanceChange can be < 0, when there were some funds on emporium before the call"), confirming that leftover token balances (e.g. vault shares deposited in one op, to be redeemed in a later op) are an expected state, not a hypothetical. [4](#0-3) 

`onlyAllowedRecipient` restricts `msg.sender` of `runAction` to the Hinkal contract itself, not to the attacker directly, but this does not block the attack: the attacker reaches `runAction` through Hinkal's normal external-action dispatch by submitting their own valid ZK proof for their own (possibly zero-value) UTXOs, while fully controlling `CircomData.erc20TokenAddresses`, `externalActionData.externalActionMetadata` (the `EmporiumStack`), and `deltaAmountChanges`, per the stated threat model. No check in `performHinkalChecks`, `verifyProof`, or the circuit constrains the *contents* of `erc20TokenAddresses` against the tokens actually touched by `stack.ops` — the circuit only balances `inTotal + amountChanges === outTotal` for the tokens the prover chose to declare, so a token deliberately excluded from the declared set is invisible to both the on-chain balance diff and the circuit's conservation constraint.

### Impact Explanation
Any ERC20 (or ETH) balance sitting in the Emporium contract — including vault-share/LP tokens deposited by a victim in a prior stateless op awaiting a follow-up redemption — can be transferred out to an attacker-chosen address with zero balance accounting or UTXO creation tying the movement to the shielded ledger. This is direct theft of another user's ERC20-shaped position with no proof/nullifier consumed for it, matching the Critical category ("direct theft of shielded or in-flight user funds"). The attack is repeatable against any token left in Emporium, for as many times as such leftover balances exist.

### Likelihood Explanation
Preconditions: Emporium must hold a nonzero balance of the target token from some prior operation (deposit/vault-share receipt that has not yet been fully swept in the same transaction — a state the code's own comments indicate is expected/normal). The attacker only needs to submit one ordinary transaction with their own valid proof and freely crafted `CircomData`/`EmporiumStack`; no special role, no compromise of other keys, and no interaction with the victim is required. Attacker cost is a single gas-paying transaction; feasibility is high since all crafted fields (`erc20TokenAddresses`, `stack.ops`, `deltaAmountChanges`) are entirely attacker-controlled per the stated model.

### Recommendation
Do not let the balance-diff safety net be scoped by an attacker-chosen array. Either (a) require `circomData.erc20TokenAddresses` to include every token address touched by any `op.endpoint`/decoded transfer target in `stack.ops` (validated on-chain, e.g. by decoding/whitelisting call targets or by tracking all tokens Emporium ever holds and looping the balance check over that full set), or (b) restrict CASE 2 `op.endpoint.call` targets to a pre-approved allowlist of protocol integrations rather than arbitrary addresses/calldata, and additionally re-check balances for any token that changed during the call regardless of whether it was declared, reverting if an undeclared token's balance decreased.

### Proof of Concept
Foundry test plan:
1. Deploy `EmporiumUpgradeable`, a mock `HinkalHelper`, and a mock `vaultShareERC20` (ERC20).
2. Simulate a victim's prior op that leaves `amount` of `vaultShareERC20` held by the Emporium contract (e.g., mint tokens directly to Emporium to represent an incomplete/pending multi-step vault flow).
3. As the attacker, build a `CircomData` with `erc20TokenAddresses = []`, `deltaAmountChanges = []`, and `externalActionData.externalActionMetadata` encoding an `EmporiumStack` with one op: `invokeWallet=false`, `endpoint=address(vaultShareERC20)`, `callData=abi.encodeWithSelector(IERC20.transfer.selector, attacker, amount)`, `stack.signerAddress=address(0)`.
4. Call `runAction` (as the allowed-recipient `Hinkal` mock) with this `CircomData`.
5. Assert: before call, `vaultShareERC20.balanceOf(emporium) == amount` and `vaultShareERC20.balanceOf(attacker) == 0`; after call, `vaultShareERC20.balanceOf(attacker) == amount` and `vaultShareERC20.balanceOf(emporium) == 0`, while `deltaAmountChanges` was empty and no `BalanceChangeShouldBePositive()` revert occurred and no UTXO for `vaultShareERC20` was minted — demonstrating `0 == amountActuallyMoved` (the required conservation equality) is false.
