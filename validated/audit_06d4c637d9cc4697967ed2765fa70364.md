### Title
`_prepareGraduationLiquidity`'s rounding-to-zero `tokensForLP` permanently bricks `finalizeGraduation`, freezing curve-raised LT and the LP-reserve tokens - ([File: packages/contracts/src/Bonding.sol])

### Summary
`Bonding._prepareGraduationLiquidity` computes `tokensForLP = (ltFromPair * tokenReserve) / assetReserve` with plain integer division and no floor/minimum check. When the real LT actually raised by the curve (`ltFromPair`) is small relative to the pair's asset reserve (`virtualLtReserve + ltFromPair`), this division truncates to `0`. Because `tokensForLP` is cached verbatim in `pendingGraduation` and consumed deterministically by phase 2, every subsequent call to `finalizeGraduation` for that token replays the same zero and reverts forever, permanently freezing the token in `Lifecycle.Graduating` with its curve-raised LT and reserved tokens unrecoverable.

### Finding Description
`Bonding._prepareGraduationLiquidity` (`packages/contracts/src/Bonding.sol:1073-1096`) computes:

```
ltFromPair = assetReserve - _launchTimeVirtualLtReserve(tokenAddress, pairAddr);
...
tokensForLP = assetReserve == 0 ? 0 : (ltFromPair * tokenReserve) / assetReserve;
``` [1](#0-0) 

This is called from `_enterGraduating` (phase 1, fired inline by the threshold-crossing buy or via the permissionless `triggerGraduation`), which caches the result unmodified in `pendingGraduation[token]`: [2](#0-1) 

Phase 2 (`finalizeGraduation`) reads that cached, frozen value and passes it straight into `_seedUniswapV2Direct` → (empty-pool fast path) `_seedDirectMint`: [3](#0-2) [4](#0-3) 

If `tokensForLP == 0`, `_seedDirectMint` transfers `0` of the token side into the (empty) HyperSwap V2 pair and calls `pair.mint(lpLock)`. Standard V2 `mint` computes `liquidity = sqrt(amount0*amount1) - MINIMUM_LIQUIDITY` on the first mint; with `amount0 == 0` this is `0` (or reverts on underflow), which V2's own `require(liquidity > 0, ...)` rejects — i.e. `pair.mint` reverts. Even in the non-empty-pool rebalance branch, the same `tokensForLP == 0` numerator collapses `_routerDepositAndDispose`'s deposit and yields `liquidity == 0`, which is then passed to `LPLock.recordLock`: [5](#0-4) 
which explicitly reverts with `ZeroAmount()` when `amount == 0`.

Either way, `finalizeGraduation` reverts every single time it is called for that token, because `pendingGraduation[token]` is fixed (deterministic, re-derivable byte-for-byte) and there is no way to recompute or override it — the lifecycle can only move `Curve → Graduating → Graduated`, never back, and `LPLock` and `Bonding` expose no admin rescue for a stuck `Graduating` token. This is the exact "malformed-input causes permanent-degraded-state" bug class from the report: a validly-reachable, unprivileged-triggerable input shape (a graduation where `ltFromPair` is small relative to the pool's virtual+real asset reserve) is never rejected at the point that matters, and once it lands the contract is stuck in a degraded state forever, not just for one transaction.

`ltFromPair` becomes small relative to `assetReserve` whenever the external LT's `exchangeRate()` has appreciated enough that the USD graduation trigger `(storedAssetReserve - virtualLtReserve) × exchangeRate ≥ $9K` fires with very little real LT actually parked in the curve (LT is a leveraged, rebasing-priced asset by design, so large rate swings are the expected steady state, not an edge case) — this is read live and used unprivileged by any trader's buy that lands while the token is "ripe," per the documented dual-trigger design: [6](#0-5) 

### Impact Explanation
Once bricked, the token's `ltFromPair` (already drained out of the curve `Pair` into `Bonding` via `Router.graduate` during phase 1) and its LP-reserve tokens (`lpBurned`/`tokensForLP` share of the 250M reserve, and `unsoldBurned`, already burned in phase 1) are permanently unreachable: the LP is never seeded, `LPLock.recordLock` never succeeds, and the token can never reach `Lifecycle.Graduated`, so post-graduation HyperSwap trading never opens either. All curve LT raised from every buyer of that token is permanently frozen inside `Bonding` with no code path to recover or refund it — this is a permanent freezing of trader/creator funds (Critical-leaning High, matching the "degraded state, funds effectively stuck" character of the source advisory).

### Likelihood Explanation
The trigger condition (real LT raised small relative to the pool's total LT reserve at the moment of graduation) is a natural consequence of the protocol's own virtual-reserve design combined with a volatile, rebasing-priced LT reserve asset — it does not require compromising or modifying BounceTech's LT, only ordinary price appreciation of the LT the creator chose to pair against, which is exactly the kind of asset alt.fun explicitly supports. Any unprivileged trader's ordinary buy that lands while the token is "ripe" on the USD trigger can be the one that locks in the fatal rounding, and `Bonding.triggerGraduation` is itself a permissionless, argument-free entry point that fires phase 1 for any already-ripe token — no special crafting of calldata or malicious contracts is needed, only a normal LT rate move plus a normal buy/trigger call.

### Recommendation
In `_prepareGraduationLiquidity`, floor-check `tokensForLP` (and ideally `ltFromPair`) before caching them in `pendingGraduation`, and either (a) round up / apply a minimum LP-seed amount so `tokensForLP` can never truncate to `0` while `ltFromPair > 0`, or (b) explicitly revert `_enterGraduating` with a dedicated error (rather than letting the un-recoverable state be committed) so the threshold-crossing buy itself fails safely and the token remains tradable on the curve until conditions allow a non-degenerate graduation. Add an invariant test asserting `tokensForLP > 0` whenever `ltFromPair > 0` across a wide range of `assetReserve`/`tokenReserve` ratios, including LT exchange rates orders of magnitude away from 1.

### Proof of Concept
1. Launch a token paired with an LT (`Bonding.launch`), leaving the standard virtual reserve (`virtualLtReserve`) seeded at launch.
2. Perform ordinary curve buys via `Zap.buy` to raise some LT into the pair, keeping `ltFromPair` modest.
3. Have the LT's `exchangeRate()` appreciate substantially (a normal leveraged-token event — no privileged action needed) so that `(assetReserve - virtualLtReserve) × exchangeRate ≥ $9K` while `ltFromPair` (raw LT units) stays numerically small relative to `assetReserve` (dominated by `virtualLtReserve`).
4. Call `Bonding.triggerGraduation(token)` (permissionless) or let the next ordinary buy trip `canGraduate` inside `_executeBuy` — phase 1 fires, `_prepareGraduationLiquidity` computes and caches `tokensForLP = (ltFromPair * tokenReserve) / assetReserve == 0` due to truncation, `Router.graduate` has already drained `ltFromPair` LT out of the pair into `Bonding`.
5. Call `Bonding.finalizeGraduation(token)` — it reverts (either inside HyperSwap V2 `pair.mint`'s `INSUFFICIENT_LIQUIDITY_MINTED`/underflow, or inside `LPLock.recordLock`'s `ZeroAmount()`).
6. Any subsequent call to `finalizeGraduation(token)` replays byte-identical cached values and reverts identically — the token is permanently stuck in `Lifecycle.Graduating`, and the drained LT plus reserved tokens are unrecoverable.

    function finalizeGraduation(
        address tokenAddress
    ) external nonReentrant {
        BondingStorage storage $ = _s();
        TokenInfo storage info = $.tokenInfo[tokenAddress];
        if (info.lifecycle != Lifecycle.Graduating) revert NotGraduating();

        address lt = info.ltAddress;
        PendingGraduation memory p = $.pendingGraduation[tokenAddress];

        // Anything in this contract beyond `p.ltFromPair` belongs to a
        // concurrent graduation on the same LT (Phase 1 transferred it
        // via `Router.graduate`) or to stray dust. Either way it is
        // off-limits to this graduation's deposit and sweep — see
        // `_routerDepositAndDispose` and `_sweepLTToOwner`.
        // Saturating subtract: a balance below `p.ltFromPair` shouldn't
        // be reachable in normal operation, but we keep finalize from
        // bricking on a Panic if any future code path or non-canonical
        // LT briefly violates the invariant.
        uint256 ltBalance = IERC20(lt).balanceOf(address(this));
        uint256 protectedLT = ltBalance > p.ltFromPair ? ltBalance - p.ltFromPair : 0;

        address lpPair = _ensureUniswapV2Pair(tokenAddress, lt);
        uint256 liquidity = _seedUniswapV2Direct(tokenAddress, lt, lpPair, p.tokensForLP, p.ltFromPair, protectedLT);

        _sweepLTToOwner(lt, protectedLT);

        info.lifecycle = Lifecycle.Graduated;
        $.graduatedPair[tokenAddress] = lpPair;
        delete $.pendingGraduation[tokenAddress];

        LPLock($.lpLock).recordLock(tokenAddress, lpPair, liquidity);

        emit TokenGraduated(tokenAddress, lpPair, liquidity, p.tokensForLP, p.lpBurned, p.unsoldBurned);
    }

    function recordLock(
        address token,
        address lpPair,
        uint256 amount
    ) external {
        LPLockStorage storage $ = _s();
        if (!$.isLocker[msg.sender]) revert NotAuthorized();
        if (lpPair == address(0)) revert ZeroAddress();
        if (amount == 0) revert ZeroAmount();
        // `lockedAt` is the one-shot sentinel: it is always set to a non-zero
        // timestamp on the first lock, so the guard holds for any `amount`.
        if ($.locks[token].lockedAt != 0) revert AlreadyLocked();
        if (IERC20(lpPair).balanceOf(address(this)) < amount) revert InsufficientLPBalance();
        $.locks[token] = LockInfo({lpPair: lpPair, amount: amount, lockedAt: block.timestamp});
        emit LPLocked(token, lpPair, amount);
    }

- **Dual trigger.** Phase 1 fires on whichever hits first: `(storedAssetReserve - virtualLtReserve) × exchangeRate ≥ $9K` (USD, for LT pumps) or `IPair.tokenBalance() == 0` (supply, for flat/bear markets). The USD trigger reads STORED reserves so direct LT donations to the pair don't count toward the threshold; the launch-time `virtualLtReserve` is recovered on-the-fly as `Pair.k() / Token.TOTAL_SUPPLY()` (K is set once at mint and never modified by `Pair.swap`). The supply trigger reads live `tokenBalance()`, which is donation-resistant in the opposite direction: token donations only INCREASE the balance and can never satisfy `== 0`, and any donated tokens are unconditionally burned by `_prepareGraduationLiquidity`.
