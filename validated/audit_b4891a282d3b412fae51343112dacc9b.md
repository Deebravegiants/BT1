## Title
Missing minimum-LP-out slippage check in `process_deposit` allows depositors to be sandwiched into minting far fewer LP tokens than expected - (`program/src/processor.rs`)

### Summary
`Deposit` only protects the *ratio* between the two input tokens (`other_amount_min`) but has no check that the LP tokens actually minted (`mint_lp_amount`) meet a user-specified minimum. Because `mint_lp_amount` is derived from the pool's live reserves (`amm.lp_amount`, `total_coin_without_take_pnl`/`total_pc_without_take_pnl`) at execution time, an attacker who alters those reserves between the time the victim signs the deposit and the time it lands on-chain (e.g. via a preceding swap in the same block/bundle) can cause the victim to mint substantially fewer LP tokens for the same locked-in token amounts — the exact class of bug described in the referenced report ("withdrawal/deposit lacks slippage control on the output share amount").

### Finding Description
`DepositInstruction` only carries `max_coin_amount`, `max_pc_amount`, `base_side`, and an optional `other_amount_min`: [1](#0-0) 

`other_amount_min` only bounds the *counter-side* token amount deduced from the chosen base side (`deduct_pc_amount`/`deduct_coin_amount`); it never bounds `mint_lp_amount`, which is the actual value the user receives: [2](#0-1) [3](#0-2) 

`mint_lp_amount` is computed from `total_coin_without_take_pnl`/`total_pc_without_take_pnl` and `amm.lp_amount`, all of which reflect the *current* pool state at execution time, not the state the user observed when constructing/signing the transaction: [4](#0-3) 

Contrast this with `Withdraw`, where the actual output token amounts (`coin_amount`, `pc_amount`) *are* protected by `min_coin_amount`/`min_pc_amount`: [5](#0-4) [6](#0-5) 

So the deposit path is inconsistent with the withdraw path: withdraw checks the real output, deposit does not. If any transaction changes the pool's coin/pc reserves or `lp_amount` between quote time and execution time (a normal swap, or an attacker-crafted swap placed immediately before the victim's deposit within the same block/validator batch), the ratio `deduct_coin_amount / total_coin_without_take_pnl` used to mint LP shifts, and the victim receives a different (potentially much smaller) `mint_lp_amount` for the exact same `max_coin_amount`/`max_pc_amount` they authorized — with no on-chain enforcement of a minimum acceptable LP output.

### Impact Explanation
This directly transfers value from depositors to whoever manipulated the pool state immediately beforehand: the victim locks in fixed token amounts but has no guarantee on the LP shares (i.e., pool ownership / future redeemable value) they receive in return. An attacker can inflate one side of the reserves right before the victim's deposit executes, causing the victim's deposit to mint a diluted amount of LP, then reverse the position afterward, extracting value from the victim — a classic sandwich attack enabled specifically by the absence of output-side slippage protection in `Deposit`. This is a concrete loss of user funds, matching the accepted impact criteria (theft of LP/user funds via unprotected valuation at deposit time).

### Likelihood Explanation
Any transaction that alters `amm.lp_amount`, `amm_coin_vault.amount`, or `amm_pc_vault.amount` between the victim's deposit being quoted/signed and it landing on-chain is sufficient to trigger the underpricing — this includes ordinary swaps or an attacker's own crafted swap placed adjacent to the victim's deposit transaction. No privileged access is required; any unprivileged actor able to submit a transaction that changes the pool reserves before the victim's deposit executes can trigger this.

### Recommendation
Add an explicit `min_lp_amount` (or equivalent) field to `DepositInstruction`/`WithdrawInstruction`-style deposit handling, and enforce `mint_lp_amount >= min_lp_amount` in `process_deposit` (mirroring the `min_coin_amount`/`min_pc_amount` check already present in `process_withdraw`), returning `AmmError::ExceededSlippage` when violated.

### Proof of Concept
1. Attacker observes a pending `Deposit` instruction (base_side = 0, `max_coin_amount = C`, `max_pc_amount = P`, `other_amount_min = None` or a loose bound) targeting pool `AmmInfo` with current `total_coin_without_take_pnl = TC`, `total_pc_without_take_pnl = TP`, `amm.lp_amount = L`.
2. Immediately before the victim's deposit is processed (same block/bundle), attacker submits a swap that substantially increases `total_coin_without_take_pnl` to `TC' >> TC` (e.g., a large coin-for-pc swap), without necessarily breaching the loose `other_amount_min` bound the victim set.
3. Victim's `Deposit` executes: `deduct_coin_amount = C` (unchanged), `mint_lp_amount = invariant_coin.exchange_token_to_pool(L, Floor)` computed against the now-inflated `TC'`, yielding a much smaller `mint_lp_amount` than the victim expected when quoting against `TC` — see the mint calculation at: [4](#0-3) 
4. There is no on-chain check rejecting this reduced `mint_lp_amount`; the deposit succeeds and the victim's LP tokens are diluted relative to the value they contributed.
5. Attacker reverses their swap afterward, recovering their capital while having captured the pricing distortion at the victim's expense.
