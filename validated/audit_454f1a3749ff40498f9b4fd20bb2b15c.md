Confirmed: no rescue/withdraw function exists in `ExternalActionBaseV2` or `ExternalActionSwap` to recover stray token balances, so any fee amount stuck there is permanently unrecoverable.

### Title
Self-relay swap silently burns relay/protocol fee, permanently freezing user value with no UTXO backing - (File: contracts/external-actions/swaps/ExternalActionSwap.sol)

### Summary
When a user self-relays a `transact()` call routed to the swap external action (i.e. sets `circomData.relay == address(0)`, which is an explicitly valid, unprivileged configuration), `ExternalActionSwap.swap()` still computes and subtracts a relay/protocol fee from the swap output, but the fee amount is never actually transferred anywhere because `sendToRelay` is a no-op when `relay == address(0)`. The deducted fee amount is left stranded in the `ExternalActionSwap` contract with no corresponding UTXO minted for it and no admin rescue mechanism, permanently freezing that value.

### Finding Description
`HinkalHelper.performHinkalChecks` explicitly allows and requires the self-relay case: `circomData.originalSender == sender && circomData.relay == address(0)` [1](#0-0) . In the internal-transfer path, `Hinkal._internalTransact` correctly special-cases this: the fee-calculation block is only entered `if (circomData.relay != address(0))`, so a self-relaying user pays no fee and the entire withdrawn amount is returned to them [2](#0-1) .

`ExternalActionSwap.swap()` does not implement this same guard. It unconditionally computes `relayFee` (the flat fee) and `hinkalFee` (the variable-rate fee on `swappedAmount`) regardless of whether `circomData.relay` is zero: [3](#0-2) 

`sendToRelay` (used to actually transfer the fee) is defined to silently no-op when `relay == address(0)`: [4](#0-3) 

But `amountToSendToHinkal = swappedAmount - totalFee` is computed and sent to the user irrespective of whether the fee transfer actually occurred. So when `relay == address(0)`, `totalFee` (both `relayFee` and `hinkalFee`) is deducted from the user's proceeds but is never transferred to the relay, never returned to the user, and never represented by any UTXO — it simply remains as unaccounted ERC20/ETH balance sitting in the `ExternalActionSwap` contract.

This breaks the balance equation the Hinkal core relies on: in `Hinkal.transact()`, `balanceDif` (the actual on-chain balance change for the token) is checked against `circomData.amountChanges[i] + utxoAmount` [5](#0-4) ; because `handleOut`/UTXO issuance in the swap path only mints a UTXO for `amountToSendToHinkal` (already fee-reduced), that equation checks out formally, but the underlying value that funded `totalFee` has left the shielded system's accounted balance without being paid to any party — it is neither returned to the depositor's shielded balance, nor delivered to a relay, nor claimable by anyone. There is no `withdraw`/`rescue`/`sweep` function anywhere in `ExternalActionBaseV2` or `ExternalActionSwap` to recover it.

### Impact Explanation
This is a permanent freezing of protocol/relay fee value (and effectively of a slice of the depositing user's funds), reachable by any ordinary, unprivileged user who self-relays a swap transaction (a fully legitimate, explicitly supported mode per `performHinkalChecks`). Each affected swap permanently locks `relayFee + hinkalFee` worth of tokens in the `ExternalActionSwap` contract, unrecoverable by anyone, including the protocol itself, matching the "permanent freezing of protocol/relay fees" High-impact category.

### Likelihood Explanation
High likelihood: self-relaying (submitting your own `transact()` without going through a whitelisted relay) is a normal, documented, and explicitly checked-for usage pattern (`relay == address(0)` combined with `originalSender == sender`). Any user doing a swap via self-relay hits this path automatically whenever `feeStructure.flatFee > 0` or `feeStructure.variableRate > 0`, with no special crafting required.

### Recommendation
Mirror the guard already used in `Hinkal._internalTransact`: skip fee computation/deduction entirely when `circomData.relay == address(0)`, i.e. set `relayFee = 0` and `hinkalFee = 0` (or otherwise route the full `swappedAmount` back into the UTXO) whenever there is no relay to pay, so self-relaying users are not charged a fee that is then unrecoverable.

### Proof of Concept
1. User builds a valid proof/`CircomData` for `transact()` calling the swap external action, with `circomData.originalSender == msg.sender` and `circomData.relay == address(0)` (a self-relay transaction), and `feeStructure.flatFee > 0` and/or `feeStructure.variableRate > 0`.
2. `performHinkalChecks` accepts this as valid self-relay configuration [1](#0-0) .
3. `Hinkal._externalTransact` routes to `ExternalActionSwap.runAction` → `swap()`.
4. Inside `swap()`, `relayFee` and `hinkalFee` are computed from `flatFee`/`variableRate` and `swappedAmount` [6](#0-5) .
5. `sendToRelay(address(0), ...)` is called and does nothing (no-op) because `relay == address(0)` [4](#0-3) .
6. `amountToSendToHinkal = swappedAmount - totalFee` is transferred to `msg.sender` (the Hinkal core contract) and a UTXO for only that reduced amount is minted [7](#0-6) .
7. `totalFee` worth of `outputToken`/`feeToken` remains stuck in the `ExternalActionSwap` contract's balance permanently, with no function anywhere to withdraw or reclaim it.
