### Title
`WrappedHyperFungibleToken.send()` does not account for fee-on-transfer underlying tokens, causing unbacked cross-chain mint/unlock and eventual insolvency - (File: `sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol`)

### Summary
`WrappedHyperFungibleToken.send()` locks the underlying ERC20 via `safeTransferFrom(msg.sender, address(this), params.amount)` and then dispatches a cross-chain message that always encodes the caller-supplied `params.amount` as `message.amount`, regardless of how much the contract actually received. If `_underlying` is a fee-on-transfer (or otherwise non-standard, deflationary) token, the contract locks strictly less than `params.amount` while instructing the peer contract on the destination chain to mint or unlock the full `params.amount`.

### Finding Description
In `send()`: [1](#0-0) 

the ERC20 branch calls `IERC20(_underlying).safeTransferFrom(msg.sender, address(this), params.amount)` and never checks the actual balance delta. The message body is then built directly from the unmodified `params.amount`: [2](#0-1) 

and re-emitted with the same untouched value: [3](#0-2) 

Contrast this with `IntentGatewayV2.placeOrder`, which explicitly guards against this class of bug by snapshotting the balance before/after the transfer and using the actual delta for escrow/commitment accounting: [4](#0-3) 

`WrappedHyperFungibleToken` has no equivalent balance-before/balance-after check. When the message reaches the destination chain, `onAccept()` on the peer (either another `WrappedHyperFungibleToken` unlocking its own underlying, or a `HyperFungibleToken` minting fresh supply) trusts `message.amount` as authoritative and transfers/mints exactly that amount: [5](#0-4) [6](#0-5) 

Because the source-chain contract only actually escrowed `amount - fee`, every `send()` call using a fee-on-transfer underlying token creates a permanent shortfall between what is locked on the source chain and what is released/minted on the destination chain.

### Impact Explanation
This is a direct unbacked-mint / reserve-drain bug reachable by any unprivileged user who calls `send()` with a fee-on-transfer underlying token:
- If the destination peer is a `HyperFungibleToken` (burn/mint model), destination supply is inflated beyond what is actually escrowed on the source chain — an unbacked mint.
- If the destination peer is another `WrappedHyperFungibleToken` (lock/unlock model), each `send()` progressively drains the destination's locked reserve faster than it is replenished, eventually causing `onAccept()`/`safeTransfer()` calls to revert for later users due to insufficient balance — a permanent freezing of funds for those users while earlier senders effectively extracted value the protocol never actually held.

This matches the High severity bar (unbacked mint / permanent freezing of funds) and is reachable from a single user-submitted `send()` transaction — no privileged role required.

### Likelihood Explanation
Likelihood depends on whether a deployment configures `_underlying` to a fee-on-transfer token (or any token with a non-1:1 transfer semantics, e.g. tokens with transfer taxes, rebasing deflation, or blacklist-based partial burns). Since `WrappedHyperFungibleToken` is explicitly designed as a generic "wrapper for existing ERC20 tokens" (per its own NatSpec) and is meant to be configurable for arbitrary tokens across chains, this is a realistic configuration that the contract itself does not guard against, and the bug triggers on every single `send()` call once such a token is wrapped — no special conditions or race needed.

### Recommendation
Mirror the pattern already used in `IntentGatewayV2.placeOrder`: snapshot `IERC20(_underlying).balanceOf(address(this))` before and after the `safeTransferFrom` call, compute the actual received amount, and use that amount (not the caller-supplied `params.amount`) both for the dispatched `message.amount` and for the emitted `Sent` event. Apply the same balance-delta check to the WETH-deposit branch if `IWETH.deposit` can ever behave non-1:1.

### Proof of Concept
1. Owner configures `WrappedHyperFungibleToken` with `_underlying` set to a fee-on-transfer token that charges, e.g., 1% on every transfer, and registers a peer `HyperFungibleToken` on chain B.
2. User calls `send({ amount: 1000e18, dest: chainB, to: user, ... })`.
3. `safeTransferFrom` moves only 990e18 into the wrapper contract (1% fee retained by the token), but `message.amount` in the dispatched `DispatchPost` is still `1000e18`.
4. On chain B, `HyperFungibleToken.onAccept()` mints `1000e18` to the recipient — 10e18 more than was ever actually escrowed on chain A.
5. Repeating this drains/inflates the cross-chain accounting indefinitely; if the destination side is a lock/unlock `WrappedHyperFungibleToken` instead of mint/burn, its reserve is depleted below what later `onAccept()` calls require, causing those transfers to revert and permanently stranding legitimate users' funds.

    function onAccept(IncomingPostRequest calldata incoming) public virtual override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        Message memory message = abi.decode(request.body, (Message));
        address beneficiary = _toAddr(message.to);
        _mint(beneficiary, message.amount);

        if (message.data.length > 0) {
            ICallDispatcher(_dispatcher).dispatch(message.data);
        }

        emit Received({
            from: message.from,
            to: beneficiary,
            source: string(request.source),
            amount: message.amount
        });
    }
