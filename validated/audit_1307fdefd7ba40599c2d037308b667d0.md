### Title
Potential panic-based DoS in BSC consensus verifier via unchecked BLS public key length conversion - (File: modules/consensus/bsc/verifier/src/lib.rs)

### Summary
`verify_bsc_header` in [1](#0-0)  and [2](#0-1)  converts each validator's `bls_public_key` bytes into a fixed-size `BlsPublicKey` using `.try_into().expect("Infallible")`. This code path is reached from the unsigned, permissionless `handle_unsigned` extrinsic [3](#0-2)  via the `ismp-bsc` client's `verify_consensus`, which decodes a relayer-submitted `BscClientUpdate` and calls `verify_bsc_header` on the attested/epoch header's `extra_data` [4](#0-3) .

### Finding Description
The header `extra_data` (containing the `validators` list with each validator's `bls_public_key`) is parsed from a raw block header supplied inside the untrusted consensus proof (`update.attested_header` or `update.epoch_header_ancestry[0]`), via `parse_extra::<H, C>`. If `parse_extra`/the validator RLP decoding does not itself enforce that `bls_public_key` is exactly 48 bytes (the size of `BlsPublicKey`), then `.try_into().expect("Infallible")` is a mislabeled invariant: it is not actually infallible for adversarial input, and would panic the runtime when a relayer submits a BSC epoch header whose extra_data encodes a validator entry with the wrong-length key. This is structurally analogous to CVE-2017-7994 — a crafted/malformed input field driving a hard crash in a parsing/extraction routine that assumes well-formed data.

I was unable to confirm, within the given tool budget, whether `modules/consensus/bsc/verifier/src/primitives.rs` (where `parse_extra` and the `Validator` struct live) already validates the `bls_public_key` length during RLP decoding. If it does, this `.expect` is unreachable and this is not a valid finding.

### Impact Explanation
If reachable, an unprivileged relayer could submit a single crafted BSC consensus update through `pallet-ismp::handle_unsigned` and panic the runtime handling `handle_unsigned`, which — depending on how panics propagate through Substrate's transaction execution — could halt block production or repeatedly abort message processing, a "route unable to deliver messages" outcome for the BSC consensus client. This would be Medium/High severity if confirmed.

### Likelihood Explanation
Likelihood cannot be confirmed without inspecting `primitives.rs`'s decoding logic for `extra_data`/`Validator`. Given the codebase shows extensive prior hardening against exactly this bug class (unchecked `.unwrap()`/`.expect()`/index panics on relayer-supplied proof data — see the BEEFY MMR leaf index fix [5](#0-4) , the GRANDPA `RelayHeaderNotInUnknownHeaders` fix [6](#0-5) , the sync-committee multi-proof length check [7](#0-6) , and the Pharos SPV proof-depth/nibble-index fixes [8](#0-7) ), it's plausible the BSC RLP decoder already validates fixed-length fields the same way, in which case this `.expect("Infallible")` would be truly unreachable.

### Recommendation
Verify whether `parse_extra`/the BSC `Validator` RLP decoder in `modules/consensus/bsc/verifier/src/primitives.rs` enforces `bls_public_key.len() == 48` at decode time. If it does not, replace the `.try_into().expect("Infallible")` calls at [9](#0-8)  and [10](#0-9)  with a typed error (e.g., `Error::InvalidBlsPublicKeyLength`) so a malformed epoch header is rejected instead of panicking.

### Proof of Concept
Could not be constructed/confirmed without access to `primitives.rs`'s RLP decoding rules for the `Validator` type and `extra_data` layout — this is needed to determine whether a wrong-length `bls_public_key` can even survive decoding to reach the `.expect("Infallible")` call.

			.map_err(|_| Error::DecodeConsensusState)?;

			Err(Error::ExpiredUpdate {
				current: consensus_state.finalized_height,
				update: bsc_client_update.source_header.number.low_u64(),
			})?
		}

		let epoch_length = Pallet::<T>::epoch_length().ok_or(Error::EpochLengthNotSet)?;
		if let Some(next_validators) = consensus_state.next_validators.clone() {
			let attested_number = bsc_client_update.attested_header.number.low_u64();
			let attested_epoch = compute_epoch(attested_number, epoch_length);
			let rotation_epoch = compute_epoch(next_validators.rotation_block, epoch_length);
			// Promote the pending validator set only when the submitted update is in the
			// specific epoch where that set is scheduled to activate, and the attested
			// header has reached the recorded `rotation_block`. The previous rule —
			// "any update whose `attested.number % epoch_length` is past the rotation
			// midpoint" — promoted the pending set in any later epoch, so an attacker
			// holding the keys of a stale `next_validators` (e.g. retired or compromised
			// validators) could submit an update many epochs later, get their set
			// promoted to `current_validators`, and then have their forged
			// `source_header`'s `state_root` accepted as a BSC state commitment. Binding
			// rotation to the recorded `rotation_block`'s epoch prevents that reuse.
			if attested_epoch == rotation_epoch && attested_number >= next_validators.rotation_block {
				// During authority set rotation, the source header must be from the same epoch as
				// the attested header.
				let source_header_epoch =
					compute_epoch(bsc_client_update.source_header.number.low_u64(), epoch_length);
				if source_header_epoch != attested_epoch {
					Err(Error::SourceHeaderEpochMismatch {
						attested_epoch,
						source_epoch: source_header_epoch,
					})?
				}
				consensus_state.current_validators = next_validators.validators;
				consensus_state.next_validators = None;
				consensus_state.current_epoch = attested_epoch;
			}
		}

		let VerificationResult { hash, finalized_header, next_validators } =
