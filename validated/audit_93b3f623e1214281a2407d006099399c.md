### Title
Webhook `shop` identity not bound by HMAC, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then unconditionally trusts the `shop` value taken from the (unauthenticated) `x-shopify-shop-domain` header when dispatching to the app's webhook handler.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`ShopifyAPI::Utils::HmacValidator.validate` computes/verifies the HMAC exclusively over that signable string: [2](#0-1) 

Meanwhile, `Request#shop` is read straight from the `x-shopify-shop-domain`/`shopify-shop-domain` header with no cryptographic binding to the body or the HMAC: [3](#0-2) 

`Registry.process` checks only the body HMAC and then forwards `request.shop` (plus the parsed body) to the registered handler without any further check that the shop matches the tenant the body/signature was actually generated for: [4](#0-3) 

The binding the gem should be enforcing is: `hmac_valid(raw_body) == shop_header_authenticity`. In reality the code only proves `hmac_valid(raw_body)`; `shop` is an independent, attacker-controlled header value that is never covered by the signature. Because a single app's Client Secret (`api_secret_key`) is shared across every merchant install of that app, any merchant who has installed the app (an "unprivileged" party with respect to other tenants of the same app) legitimately receives real webhooks whose HMAC is computed with that same shared secret. Such a merchant can capture one of their own validly-signed webhook deliveries (a fixed `raw_body` with a correct HMAC) and replay it to the app's webhook endpoint while substituting an arbitrary value for `x-shopify-shop-domain`. `HmacValidator.validate` still passes (it never looked at the shop header), and `Registry.process` calls the handler with `WebhookMetadata#shop` set to the forged shop domain, and the handler's business logic will attribute the payload to a shop that never sent it — i.e., a cross-tenant identity break.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to guarantee to host applications that rely on `request.shop`/`WebhookMetadata#shop` as an authenticated identifier once `HmacValidator.validate` succeeds. An attacker who is a legitimate merchant of the app (no special privilege, no access to `api_secret_key`) can cause the app to process arbitrary previously-observed webhook bodies under another shop's identity, leading to cross-tenant data corruption/confusion inside any host app that keys off `request.shop`/`WebhookMetadata#shop` returned by this gem after `Registry.process` succeeds. This matches the "cross-tenant access" Critical impact category, since the binding broken is exactly "a field acted on but not covered by the HMAC."

### Likelihood Explanation
Likelihood is bounded by the need for the attacker to (a) be a legitimate merchant of the target app so they possess at least one validly HMAC-signed webhook body, and (b) be able to POST directly to the app's webhook endpoint with custom headers (trivial, since webhook endpoints are just HTTP endpoints exposed by the host app, not gated by IP allow-listing in this gem). No secrets, tokens, or privileged access are required beyond normal merchant use of the app.

### Recommendation
Bind the shop identity into the authenticated material: either include the `shop` domain (and ideally topic/webhook-id) in the HMAC signable string in `Request#to_signable_string`, or have `Registry.process` cross-check `request.shop` against a value independently derived from Shopify's out-of-band webhook metadata (e.g., verify against the shop tied to the specific webhook subscription/`webhook_id`) rather than trusting the raw header once only the body HMAC has been checked.

### Proof of Concept
1. App merchant "Shop A" installs the app and receives a legitimate webhook delivery: body `B`, header `x-shopify-hmac-sha256: <valid HMAC of B with the app's shared client secret>`, header `x-shopify-shop-domain: shop-a.myshopify.com`.
2. Attacker (Shop A's own operator, or anyone who intercepts this delivery) resends the exact same body `B` and HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: shop-b.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `raw_body` against the HMAC [5](#0-4) .
4. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "shop-b.myshopify.com", body: parsed_body, ...)` [6](#0-5) , causing Shop A's webhook content to be processed under Shop B's tenant identity.
