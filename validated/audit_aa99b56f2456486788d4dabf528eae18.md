### Title
Attacker-supplied route injects arbitrary authorized calls under the victim's signed `swap_collateral`/`swap_debt` session, stealing wallet funds beyond the routed amount - ([File: contracts/controller/src/strategies/swap.rs](contracts/controller/src/strategies/swap.rs))

### Summary
CVE-2021-23214 lets a man-in-the-middle inject arbitrary SQL into a session the client believes is authenticated and certificate-verified. The analog in XOXNO Lending: a swap route submitted to `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, or direct router `execute_strategy` names arbitrary pool/token addresses, and code at those addresses executes *inside the caller's authenticated invocation tree*. Any `token.transfer(caller, attacker, x)` it issues is recorded as a child of the caller's signed auth entry and executes if the caller signs the simulated tree — the same shape as commands injected into an authenticated channel the victim trusts.

### Finding Description
Router settlement is measured but the route's venue addresses are not allowlisted. `dispatch_hop` in `contracts/swap-aggregator/src/venues/mod.rs:23-58` invokes whatever pool contract the payload names and only checks the router's own measured input/output deltas. The controller grants exactly one input-transfer invocation and validates only measured spend and positive output (`docs/reference/invariants.md` INV-STRAT-01/02) — none of this bounds what else runs under the caller's authorization.

The threat model itself records the gap at `docs/explanation/threat-model.md:154-165`: "The router calls the pool and token addresses its payload names and keeps no allowlist of them, so a route can put third-party code on the call stack below the caller's authorization. A token transfer that such code makes from the caller is recorded... as a child of the caller's authorization entry, and it executes if the caller signs that tree. The loss is then the caller's wallet, not the routed amount."

The harness proves it end-to-end in `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs:195-227`: a `RogueHopPool` named by the route calls `wallet_token.transfer(alice, attacker, WALLET_BALANCE)` mid-swap; simulation records it as a child of Alice's `swap_collateral` entry, and on execution her unrelated wallet token is fully drained while her position still receives the "fair" swap output.

### Impact Explanation
Theft of user funds. The victim's loss is not limited to the routed `amount_in` or any slippage bound — every token the victim holds whose `transfer` succeeds under her auth entry can be taken, exactly like injected SQL running with the victim's authenticated privileges. Neither the payload `min_out`, the controller's measured-output check, nor the final health-factor gate bounds the loss, since the stolen transfer never touches position accounting.

### Likelihood Explanation
Reachable by a single unprivileged attacker who gets a victim to sign a poisoned route — e.g., via a malicious quote/route source, phishing UI, or a route pasted from an untrusted party. The on-chain path itself (`swap_collateral` → router → attacker pool → nested `transfer`) requires no privilege and no protocol flaw in accounting; it relies on the victim signing the recorded auth tree, which an honest simulation dutifully produces as a normal-looking child entry. This is the same precondition as the CVE (a connection the victim believes is protected) and is the realistic exploitation path.

### Recommendation
The protocol cannot fix this on-chain without breaking permissionless routing; mitigation belongs where the threat model places it — clients must decode the route and reject any authorization tree containing children other than the single expected input transfer. At minimum, document prominently that `swap_*`/`execute_strategy` signers must verify the recorded auth tree contains exactly one `token_in.transfer` child, and consider a router-side venue allowlist or a simulation-time assertion that no other sub-invocation consumed the caller's auth.

### Proof of Concept
`tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` constructs the full attack: `UnlistedPoolRouter` (line 39) pulls `total_in` under `sender.require_auth()`, invokes the route-named `hop_pool.swap`, and pays out `min_out`. `RogueHopPool` (lines 62-71) calls `token::Client::transfer(&victim, &to, &amount)` on a wallet token the protocol never listed. The test at line 195 shows the recorded auth tree attaches the stealing transfer beneath Alice's `swap_collateral` entry and, once signed, `assert_eq!(s.wallet(&s.alice), 0)` while `s.wallet(&s.attacker) == WALLET_BALANCE` — arbitrary command execution inside the victim's authenticated session, the direct analog of CVE-2021-23214's injected SQL.
