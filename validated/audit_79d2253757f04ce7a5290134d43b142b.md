### Title
Webhook `shop` (and `topic`) identity fields are trusted for handler dispatch without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw request body, then dispatches the handler using `shop` and `topic` values extracted from unauthenticated HTTP headers. This mirrors the reported bug class: a value that drives subsequent business logic (`vault_total_balance` in the report; here, `shop`/`topic`) is not covered by the same integrity check that gates the operation (`total_shares` reduction in the report; here, the HMAC).

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`, whose contract is `hmac` and `to_signable_string`. For webhooks, `to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all read directly from HTTP headers, which are never part of the signed material: [2](#0-1) 

`Registry.process` validates the HMAC once, and only over the body, then immediately trusts `request.shop` and `request.topic` — values it never verified — to select the handler and build the `WebhookMetadata` passed into application code: [3](#0-2) 

The equality the gem implicitly claims to hold is:
`hmac_signed_bytes == bytes_that_determine_which_shop/topic_the_handler_processes`

But in reality:
`hmac_signed_bytes == raw_body_only`, while `shop`/`topic` (headers) are outside that boundary — exactly the same class of break as the report's `vault.total_shares` (adjusted, authenticated) vs. `vault_total_balance` (stale, unadjusted) mismatch: an operation is gated by one piece of state while a materially relevant piece of identity/state is left unchecked.

Compare this to `ShopifyAPI::Auth::Oauth::AuthQuery`, where the analogous `shop` field *is* included in `to_signable_string` and thus covered by the HMAC: [4](#0-3) 

This confirms the webhook path is inconsistent with the gem's own established pattern for binding identity fields to the HMAC.

### Impact Explanation
Because `shop` is not bound to the HMAC, a request whose body was legitimately signed by Shopify for shop A could, if headers are attacker-controlled or mismatched by a misconfigured proxy/load balancer in front of the app, be delivered to the handler labeled as originating from shop B. Handlers typically use `WebhookMetadata#shop` to select which tenant's data to mutate (e.g., updating that shop's stored settings, orders, or inventory records) purely based on this unauthenticated field. This creates a cross-tenant data integrity risk: the authenticated payload's provenance (HMAC) is decoupled from the tenant identity actually acted upon by host application code.

### Likelihood Explanation
Exploitability requires control over headers reaching the app while the HMAC/body pairing is either replayed, reused, or forgeable for a specific target body — this depends heavily on deployment/infrastructure (e.g., a reverse proxy that does not re-verify header/body pairing, or an app that logs/replays webhook headers separately from body). Within the gem's own contract, however, the root cause is unambiguous: `to_signable_string` intentionally excludes `shop`/`topic`/`webhook_id`, so the gem itself provides no protection binding those values to the signature. This is a design gap rather than a purely theoretical one, but it does require an external mechanism (proxy misrouting, replay tooling, or a permissive host setup) to fully realize cross-tenant impact, which is consistent with the report's own framing of the bug as "no corresponding adjustment" rather than a full authentication bypass.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signable string used for HMAC verification (or otherwise cryptographically bind them to the body), so that `Utils::HmacValidator.validate` fails if any of these identity-bearing headers is altered independently of the body — mirroring how `AuthQuery#to_signable_string` binds `shop` into its signed payload.

### Proof of Concept
1. Capture a legitimate Shopify webhook: raw body `B` with valid `x-shopify-hmac-sha256` computed over `B`, and headers `x-shopify-shop-domain: shop-a.myshopify.com`, `x-shopify-topic: orders/create`.
2. Replay the exact same `raw_body` and HMAC header (both untouched, so `Utils::HmacValidator.validate` still returns `true`), but rewrite `x-shopify-shop-domain` to `shop-b.myshopify.com` (e.g., via a proxy or any component sitting between Shopify's TLS termination and the app that does not itself re-verify header authenticity).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` — passes, since only `@raw_body` is checked: [5](#0-4) 
4. The handler receives `WebhookMetadata.new(topic: request.topic, shop: "shop-b.myshopify.com", body: ...)` and processes/mutates data attributed to shop B using data legitimately signed only for shop A. [6](#0-5)

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
