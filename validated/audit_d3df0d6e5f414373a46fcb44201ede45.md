### Title
Webhook `shop-domain` (and `topic`/`webhook-id`) headers are not covered by HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so `Utils::HmacValidator.validate` authenticates the *body bytes* using the app's `client_secret`. However, the `shop` identity attribute exposed to the webhook handler (`request.shop`, sourced from the `X-Shopify-Shop-Domain` header) is never included in the signed content. `Registry.process` treats a valid body-HMAC as sufficient proof of authenticity and then hands the caller-supplied, unauthenticated `shop` header straight to the app's handler as `WebhookMetadata#shop` — the attribute apps are documented to use as the tenant key. This breaks the equality `shop verified-by-HMAC == shop used-for-tenant-lookup`.

### Finding Description
`ShopifyAPI::Webhooks::Request` exposes `shop`, `topic`, and `webhook_id` purely from HTTP headers: [1](#0-0) 

The HMAC signature that `Utils::HmacValidator.validate` checks is computed only over `to_signable_string`, which is `@raw_body` — the shop/topic/webhook-id headers are not part of the signed input: [2](#0-1) 

`Registry.process` uses this body-only HMAC check as the sole authenticity gate, then forwards the unauthenticated `request.shop` header value straight into `WebhookMetadata` given to the app's handler: [3](#0-2) [4](#0-3) 

The gem's own documentation instructs apps to trust `data.shop` as the tenant/shop identifier for downstream processing (e.g. enqueuing background jobs keyed by shop domain), and describes `Registry.process` as verifying "the request did indeed come from Shopify": [5](#0-4) [6](#0-5) 

Because `client_secret` is shared across all shops that install a given app, any shop that has legitimately installed the app receives genuinely-HMAC-signed webhook deliveries. An attacker who controls one such installed shop (an unprivileged, ordinary merchant — no special privilege, no leaked credentials) can capture one of their own legitimate webhook deliveries (raw body + `X-Shopify-Hmac-Sha256` header) and replay that exact byte-for-byte body/HMAC pair to the app's webhook endpoint while swapping only the `X-Shopify-Shop-Domain` header to a victim shop's domain. Since the shop header is not part of the signed content, `Utils::HmacValidator.validate` still returns `true`, and `Registry.process` calls the handler with `WebhookMetadata#shop` set to the attacker-chosen victim shop domain instead of the shop that actually owns that payload/access token.

### Impact Explanation
This is a cross-tenant identity confusion: the gem authenticates *that a byte sequence was produced by someone possessing the app's `client_secret`* but not *which shop it pertains to*. Any app that follows the documented pattern of trusting `data.shop` to route/store/attribute webhook data (as shown in the gem's own webhooks doc) is exposed to a malicious merchant injecting payloads attributed to another tenant — e.g., poisoning another shop's cached order/product/customer data, or triggering shop-scoped side effects (job re-processing, notifications, state changes) under a victim's identity. This matches the Critical "cross-tenant access" impact category since one tenant's request is processed as if it belonged to another tenant.

### Likelihood Explanation
Likelihood is moderate-to-high in any app that is publicly installable (the standard Shopify app distribution model): an attacker only needs to install the app on any shop they control, trigger one webhook (e.g., update a product), capture the raw POST body and its `X-Shopify-Hmac-Sha256` header, and resend it with a forged `X-Shopify-Shop-Domain` header. No access to `client_secret`, access tokens, or the target shop's credentials is required.

### Recommendation
Bind the shop identity to the signed content, or otherwise cryptographically/logically tie the verified HMAC to the claimed shop:
- Reject/flag webhooks where `request.shop` does not correspond to a shop for which the app currently holds an active session/access token (cross-check against the app's own installed-shop records) before invoking the handler.
- Where feasible, additionally verify that `request.shop` matches a shop the app expects to receive this particular `webhook_id`/topic combination for, rather than trusting the header value implicitly.
- Update `docs/usage/webhooks.md` to explicitly warn that `data.shop` is not covered by the HMAC and must be independently validated by the app before being used as a tenant key.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com` and register a webhook (e.g. `products/update`).
2. Trigger the webhook (e.g. update a product) and capture the raw POST body `B` and header `X-Shopify-Hmac-Sha256: H` sent by Shopify to the app's webhook endpoint — `H` is `HMAC-SHA256(client_secret, B)`, valid because the app's `client_secret` is shared across all its installations.
3. Resend an HTTP POST to the same webhook endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` unchanged, but `X-Shopify-Shop-Domain: victim.myshopify.com` (and any topic/webhook-id headers desired).
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: ...)` is constructed; `Utils::HmacValidator.validate(request)` recomputes `HMAC-SHA256(client_secret, B)` which still equals `H`, so validation passes.
5. `Registry.process` invokes the app's handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed(B), ...)`, causing the app to process attacker-controlled data as if it originated from the victim shop.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
```
