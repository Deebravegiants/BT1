### Title
Excess native-token payment on `EvmHost.dispatch`/`fundRequest` is permanently absorbed into the host contract instead of being refunded to the caller - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest` all accept `msg.value` and forward it to `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(fee, ...)`. This is a `swapETHForExactTokens` call, which by design only consumes `amounts[0]` (the exact ETH needed to buy `fee` units of the fee token) and refunds any leftover ETH — but it refunds it to `msg.sender` of the *swap call*, which is `EvmHost` itself, not the original caller (`_msgSender()`) who supplied the `msg.value`. The `receive()` function's comment even documents this: "receive function for UniswapV2Router02, collects all dust native tokens." Any excess above the exact fee-token cost is therefore stranded in `EvmHost`'s native balance rather than returned to the app/user who paid it, exactly analogous to the `ASDRouter._sendASD` bug where excess `msg.value` was not refunded.

### Finding Description
In `EvmHost.dispatch(DispatchPost)`: [1](#0-0) 

and identically in `dispatch(DispatchGet)`: [2](#0-1) 

and in `fundRequest`: [3](#0-2) 

All three functions are `payable`, accept `msg.value`, and pass the *entire* `msg.value` into `swapETHForExactTokens{value: msg.value}(fee/amount, ...)`. Standard `UniswapV2Router02.swapETHForExactTokens` computes `amounts[0]` (exact ETH needed) and refunds `msg.value - amounts[0]` to its own `msg.sender`, which in this call chain is the `EvmHost` contract, not the original transaction initiator. This means any over-payment of native gas token by an app or user is silently absorbed by `EvmHost` and never returned to the payer. This is confirmed by the `receive()` function's own doc comment: [4](#0-3) 

Every one of the calling apps in the codebase (`IntentGatewayV2.sol`, `ExtrinsicIntents.sol`, `IntrinsicIntents.sol`, `HyperbridgeLzEndpoint.sol`, `HyperFungibleToken.sol`, etc.) is written to forward `msg.value` directly to `IDispatcher(host).dispatch{value: msg.value}(request)` without first quoting the exact needed amount and only sending precisely that — e.g.: [5](#0-4) [6](#0-5) 

None of these callers, nor `EvmHost` itself, refund the dust back to the caller. Unlike `IntentGatewayV2.placeOrder`, which explicitly tracks `msgValue` and refunds any unspent amount via `_sendValue(msg.sender, msgValue)` at the end of the flow — [7](#0-6)  — `EvmHost.dispatch`/`fundRequest` have no such refund path at all. The only way to move native ETH back out of `EvmHost` is the privileged `withdraw()` function restricted to `hostManager` governance: [8](#0-7) 

This function requires a cross-chain governance decision (via `HostManager.onAccept`) to name a specific beneficiary and amount; it provides no mechanism to automatically or permissionlessly refund the specific over-paying caller. Practically, any unprivileged user calling any of the many apps built on `dispatch{value: msg.value}` (intents, token bridging, LZ compatibility layer, etc.) who supplies `msg.value` even slightly above the exact ETH needed for the Uniswap swap into `fee` units of the fee token loses that excess permanently to the `EvmHost` contract's balance.

### Impact Explanation
Any unprivileged user or app dispatching an ISMP request through `EvmHost.dispatch(DispatchPost|DispatchGet)` or funding a request via `fundRequest`, paying with native gas token, will have any overpayment beyond the exact Uniswap-computed cost of the requested `fee` permanently stuck in the `EvmHost` contract with no user-triggerable recovery path — only cross-chain governance can move it, and even then not necessarily back to the original payer. Given that on-chain gas-fee/price quoting for a Uniswap swap is inherently imprecise (slippage, MEV, price movement between quote and execution), and none of the dependent apps precisely compute the exact swap input before calling `dispatch`, this is a systemic native-token loss vector reachable by ordinary users on every call path that pays dispatch/relayer fees in native token. This matches the impact class of the referenced report: permanent freezing/loss of user funds in a core, widely-reachable dispatch path.

### Likelihood Explanation
High. This occurs on the ordinary, unprivileged happy path of dispatching any ISMP request/response funding using native token payment — no attacker action, adversarial timing, or special conditions are required. Simply calling `dispatch{value: msg.value}(...)` with a `msg.value` that doesn't exactly equal the amount the router consumes (which is the normal case since apps forward user-supplied `msg.value` or client-side quotes with any buffer, and swap execution price can differ from quote-time estimate) triggers the loss. This is corroborated by the SDK docs' own guidance that clients should query the fee off-chain and send exactly that value, but nothing in the contract enforces or fails safely on excess input.

### Recommendation
In `EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest`, capture the router's return value (`amounts[0]`, the ETH actually spent) and refund any remainder (`msg.value - amounts[0]`) back to `_msgSender()` rather than leaving it in the contract's balance. Alternatively, quote the exact input amount required before calling `swapETHForExactTokens` and require `msg.value == amounts[0]`, reverting otherwise so users cannot overpay in the first place.

### Proof of Concept
1. Deploy `EvmHost` with a configured `uniswapV2` router and `feeToken`.
2. Call `dispatch(DispatchPost)` (via any app, e.g. `HyperbridgeLzEndpoint.send`) with `msg.value` set well above the actual ETH cost of acquiring `post.fee` units of `feeToken` (e.g., 1 ETH sent for a request whose fee costs 0.001 ETH worth of feeToken).
3. Observe: `swapETHForExactTokens{value: msg.value}(post.fee, ...)` only spends the exact ETH needed and refunds the rest to `address(this)` (the `EvmHost` contract) via its `receive()` function.
4. Check `address(EvmHost).balance` after the call — it now holds the un-refunded dust (≈0.999 ETH in the example), which cannot be recovered by the original caller and is only movable through a full cross-chain governance `withdraw()` call.
