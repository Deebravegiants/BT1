Webhook shop identity is not bound to the HMAC signature, enabling cross-tenant data misattribution - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop`, `topic`, `webhook_id`, and `api_version` entirely from unauthenticated HTTP headers, while `Utils::HmacValidator` only verifies the *raw request body*. Any actor who can obtain one legitimately HMAC-signed webhook body (e.g., by being a merchant who installs the app on their own shop and thus legitimately receives signed webhooks) can replay that same body/HMAC pair to the app's public webhook endpoint with a different `X-Shopify-Shop-Domain` header. `HmacValidator.validate` will still pass because the header is not part of `to_signable_string`, and `Registry.process` will hand the (attacker-chosen) `shop` straight to the app's handler as authenticated fact.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, `#api_version`, and `#webhook_id` are read straight from HTTP headers with no cryptographic binding to the signed content: [2](#0-1) 

`HmacValidator.validate` computes the HMAC purely over `verifiable_query.to_signable_string` (i.e., the body) and compares it against the `hmac` field, never touching `shop`: [3](#0-2) 

`Registry.process` treats a passing HMAC check as sufficient proof of authenticity for the whole request, then forwards `request.shop` (from the unauthenticated header) directly into `WebhookMetadata` given to the app's handler: [4](#0-3) 

The equality this breaks: the gem implicitly asserts `shop_bound_by_HMAC == shop_used_by_handler`, but in reality `shop_bound_by_HMAC = ∅` (nothing) while `shop_used_by_handler = header_value`, which is attacker-controlled. Because the signature only covers the body, a valid `(body, hmac)` pair generated for shop A remains valid when the `shop-domain` header is swapped to shop B — the check answers "authentic" for a request whose tenant claim was never verified.

### Impact Explanation
This is a cross-tenant identity-confusion vulnerability. Apps built on this gem are documented and expected to trust `WebhookMetadata#shop` (surfaced from `request.shop`) as the authenticated tenant for the payload (see `docs/usage/webhooks.md`, `WebhookMetadata`/`WebhookHandler` usage), since the gem itself performs the HMAC "authenticity" check before dispatch. An attacker who legitimately installs the app on their own store (a normal, unprivileged self-service action requiring no `api_secret_key`, access token, or credential leakage) can capture a genuinely signed webhook body/HMAC pair sent to their own endpoint, then re-POST that exact body+HMAC to the app's public webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header for a victim shop. `Registry.process` will accept it as valid and dispatch it to the handler under the victim's shop identity, letting the attacker inject or corrupt data (orders, inventory, customer records, GDPR/mandatory-topic actions, uninstall events, etc.) attributed to a shop they do not own — i.e., cross-tenant access/write without any credential belonging to the victim.

### Likelihood Explanation
Likelihood is meaningful because: (1) the webhook endpoint is a public, unauthenticated HTTP endpoint by design; (2) obtaining one valid signed body/HMAC pair requires nothing more than installing/using the app on any shop, which is an unprivileged, self-service action available to any internet user; (3) the vulnerable code path (`HmacValidator.validate` + `Request#shop` read from header) is exercised on every webhook delivery, so no special conditions are needed beyond capturing one legitimate delivery.

### Recommendation
Bind the tenant/shop claim to the HMAC-verified content instead of trusting a bare header:
- Extend `to_signable_string` (or add a secondary check) so that `shop`, `topic`, and `webhook_id` are covered by, or cross-checked against, an authenticated value (e.g., verify `shop` against the shop embedded in the JSON body when available, or require callers to additionally confirm the shop against their own session/install record before trusting `WebhookMetadata#shop`).
- At minimum, document prominently that `request.shop`/`WebhookMetadata#shop` is NOT authenticated by the HMAC check and must be independently validated by the host app against its own installed-shop registry before being used for any tenant-scoped operation.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`, triggering Shopify to send a legitimately signed webhook (e.g., `orders/create`) to the app's public webhook endpoint, with body `B` and header `X-Shopify-Hmac-Sha256: H` where `H = HMAC-SHA256(client_secret, B)`.
2. Attacker captures `(B, H)` from their own delivery (they can simply observe it via their own reverse proxy/logging since it was sent to an endpoint they control or can inspect).
3. Attacker re-sends a POST to the same public webhook endpoint with:
   - Body: `B` (unchanged)
   - Header `X-Shopify-Hmac-Sha256: H` (unchanged)
   - Header `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (changed)
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `request.to_signable_string` (== `B`, unchanged) and matches `H` — validation succeeds: [5](#0-4) 
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and the attacker's payload data `B`, processing it as authentic data for the victim tenant.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
