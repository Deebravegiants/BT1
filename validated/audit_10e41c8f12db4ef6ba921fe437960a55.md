### Title
Webhook `shop` domain header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely via `Utils::HmacValidator.validate(request)`, which computes the HMAC exclusively over the raw request body. The `shop` (and `topic`, `webhook_id`, `api_version`) values come from HTTP headers that are never part of the signed payload, so the gem authenticates the *body* but not the *tenant* it hands to the application's webhook handler.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from an `x-shopify-shop-domain`/`shopify-shop-domain` header with no cryptographic binding to the HMAC: [2](#0-1) 

`HmacValidator.validate` only ever recomputes the signature over `verifiable_query.to_signable_string`, i.e. the body: [3](#0-2) 

`Registry.process` accepts the request once the body HMAC checks out, then forwards the unauthenticated `request.shop` header directly to the application handler as the tenant identifier: [4](#0-3) 

The gem's own documentation instructs consumers to key their per-tenant business logic off exactly this unauthenticated field (`shop_domain: data.shop`), which is the expected/intended usage pattern, not a case of the host app ignoring the documented API.

The identity binding that should hold is:
`HMAC-signed bytes == bytes that determine which shop the payload is attributed to`

but in this gem it is actually:
`HMAC-signed bytes (raw body only) != bytes used to select the shop (unsigned header)`

Because the same `api_secret_key` is shared by the app across every shop that installs it, any merchant who has legitimately installed the app can capture one authentic, correctly-HMAC'd webhook delivery for their own shop and replay it with the `x-shopify-shop-domain` (or `shopify-shop-domain`) header rewritten to name a different shop. As long as the body content is attacker-known/reusable (many webhook topics carry generic or predictable JSON, and an attacker fully controls the body of their own shop's webhooks, including triggering deliveries with content they choose), the HMAC will still validate under the shared secret, while `data.shop` now names an arbitrary victim shop.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to help enforce: a party with only unprivileged access to their own installed shop can make the application process/attribute webhook data as if it came from a different merchant (cross-tenant access), for example enqueuing background jobs, updating per-shop records, or triggering shop-scoped side effects keyed by `data.shop` for a shop they do not operate and hold no access token for.

### Likelihood Explanation
Likelihood is moderate-to-high in any app that follows the gem's documented pattern of trusting `data.shop`/`data.topic` for tenant routing (as literally shown in `docs/usage/webhooks.md`), since no additional secret or privileged access is required beyond the attacker's own legitimate app installation, which any unprivileged internet user can obtain by installing the app on their own store.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the signable string used for HMAC computation (or otherwise cryptographically bind them, e.g. verify `shop` against the value returned in the original OAuth/session flow), instead of signing the body alone, so a forged/replayed header set cannot be paired with a legitimately-signed body from a different context.

### Proof of Concept
1. Attacker installs the app on their own store `attacker.myshopify.com`, becoming a legitimate low-privilege webhook sender for that shop.
2. Attacker triggers (or crafts, depending on topic content) a webhook delivery whose JSON body content they know or control, and captures the resulting `x-shopify-hmac-sha256` header — this HMAC is valid because it's computed over the raw body using the shared `api_secret_key`.
3. Attacker replays the exact same raw body and HMAC header to the app's webhook endpoint, but substitutes `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) calls `Utils::HmacValidator.validate(request)`, which succeeds because the body/HMAC pair is untouched; it then dispatches `WebhookMetadata.new(..., shop: request.shop, ...)` with `shop == "victim-shop.myshopify.com"` to the app's handler, exactly per the documented usage pattern in `docs/usage/webhooks.md:14,26`.
