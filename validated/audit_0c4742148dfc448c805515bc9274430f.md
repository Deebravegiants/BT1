Based on my investigation, I've found a valid analog to the reported bug class in this gem's webhook processing code.

### Title
Webhook shop domain not covered by HMAC signature allows shop spoofing / cross-tenant confusion - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies a webhook's authenticity by HMAC-validating only the raw request body, but the `shop` (and `topic`/`webhook_id`/`api_version`) values that are handed to the app's handler are read directly from unauthenticated HTTP headers, never included in the signed bytes.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`#shop` (and other metadata fields) are derived purely from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, with no cryptographic binding to the signed body: [2](#0-1) 

`Registry.process` validates the HMAC over `to_signable_string` (the raw body) and, if it passes, unconditionally trusts `request.shop` (and other header-derived fields) when constructing `WebhookMetadata` passed to the app's handler: [3](#0-2) 

`HmacValidator.validate` computes the signature only over `verifiable_query.to_signable_string`, i.e. only over the raw body for webhook requests: [4](#0-3) 

This is precisely the reported bug class: a field (`shop`) that is acted on by the application (used as the tenant identifier for session/access-token lookups) is not covered by the HMAC that is presented as proof of authenticity. The equality that should hold — `shop authenticated by HMAC == shop stored/used as tenant key` — is broken: HMAC only proves "this raw body was sent by an app with this client_secret for *some* webhook," not "for *this* shop." Because the same `client_secret` is shared across all shops installed on an app, any merchant who has installed the app (an unprivileged party relative to other merchants of the same app) can capture one of their own genuine, validly-HMAC'd webhook deliveries and replay the identical raw body while substituting a different value in the `x-shopify-shop-domain` header. The `HmacValidator.validate` call still succeeds (it only checks the raw body against the secret), and `Registry.process` passes the attacker-chosen `shop` value straight to the handler as trusted `WebhookMetadata#shop`.

The gem's own documentation explicitly instructs handler authors to trust `data.shop` for tenant-scoped operations (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, ...)`), so this is not a case of the host app ignoring the gem's documented API — the documented API itself has no protection against shop spoofing.

### Impact Explanation
This qualifies as Critical - cross-tenant access. An app built per the gem's documented pattern will process webhook payloads keyed to whatever `shop` value the request presents, since that field carries no authenticity guarantee. A merchant with legitimate access to the app can trigger cross-tenant data confusion by relabeling their own legitimately-signed webhook payloads as belonging to a different shop, potentially causing writes, cache updates, or job dispatch to be associated with the wrong tenant.

### Likelihood Explanation
Likelihood is high for any app that follows the gem's documented webhook handling pattern: any existing merchant/installer of the target app already possesses a source of validly-signed raw bodies (their own legitimate webhook deliveries) and can freely control the HTTP headers of the replayed request since headers are not part of the signed content.

### Recommendation
Bind the shop (and ideally topic/webhook_id/api_version) into the HMAC-covered signable content, or otherwise cryptographically verify that the `shop` header value corresponds to the account which the client_secret metadata was actually delivered for (e.g., by validating against the shop associated with a known, previously-established session before trusting `data.shop`). At minimum, document prominently that `data.shop` from `WebhookMetadata` is unauthenticated and must be independently verified before being used to select tenant-scoped credentials.

### Proof of Concept
1. Register a legitimate webhook handler and let it receive one authentic Shopify webhook for `shop-a.myshopify.com`, capturing `raw_body` and the `x-shopify-hmac-sha256` header (both valid, signed with the app's `client_secret`).
2. Replay an HTTP request to the app's webhook endpoint with the identical `raw_body` and `x-shopify-hmac-sha256` value, but set `x-shopify-shop-domain: shop-b.myshopify.com`.
3. `ShopifyAPI::Utils::HmacValidator.validate(request)` returns `true` because it only checks `raw_body` against the secret (`lib/shopify_api/utils/hmac_validator.rb` L26-31); `Registry.process` then invokes the handler with `WebhookMetadata#shop == "shop-b.myshopify.com"` (`lib/shopify_api/webhooks/registry.rb` L188-200), even though the payload actually originated for `shop-a.myshopify.com`.
