### Title
Hyperbridge-originated system messages (host-executive, intents-coprocessor, token-governor, relayer withdrawal) dispatch with zero relayer fee, leaving them permanently undeliverable by the permissionless relayer network - (File: `modules/pallets/host-executive/src/lib.rs`, `modules/pallets/intents-coprocessor/src/lib.rs`)

### Summary
Several `pallet-ismp`-based pallets that originate cross-chain POST requests from Hyperbridge itself dispatch those requests with `FeeMetadata { payer: [0u8; 32].into(), fee: Default::default() }` — a zero fee and a null payer. Because `pallet-ismp`'s relayer-reward pipeline only pays relayers for delivering requests that carry a non-zero fee escrowed from a real payer, these system messages provide no economic incentive for Hyperbridge's permissionless relayer network to deliver them, mirroring the reported "settlement does not pay relayer fee" bug class where a dispatch call is made without funding the delivery incentive.

### Finding Description
`IsmpDispatcher::dispatch_request` in `modules/pallets/ismp/src/dispatcher.rs` only transfers a relayer fee into `RELAYER_FEE_ACCOUNT` when `fee.fee != Zero::zero()`: [1](#0-0) 

Multiple system pallets call this dispatcher with a hard-coded zero fee and a zero/null payer account, e.g. `host-executive`'s `update_host_params`: [2](#0-1) 

and `intents-coprocessor`'s internal `dispatch` helper used for gateway cross-chain governance messages: [3](#0-2) 

The project's own internal design doc confirms this is a systemic pattern spanning host-executive, intents-coprocessor, the relayer pallet's withdrawal path, and token-governor, and explicitly states relayers have "no economic reason to pick them up," with delivery today depending purely on altruism: [4](#0-3) 

This is the same root cause as the reported analog: a dispatch call to the cross-chain messaging layer is made without funding the relayer incentive required for delivery, so the permissionless relayer network has no reason to forward the message to its destination.

### Impact Explanation
Messages dispatched via these code paths include destination `HostParams` updates (manager rotation, fee-token/consensus configuration), Intent Gateway parameter/governance updates, and gateway deployment notifications. If no relayer voluntarily delivers them (which is the expected steady state for a decentralized relayer market driven by `minimum_profit_percentage`), these governance/config messages never reach their destination — i.e., the route is unable to deliver messages for these critical system flows. This can permanently stall protocol-critical operations such as manager rotation or Intent Gateway parameter updates on destination chains, since applications cannot retry with a funded fee (the dispatch already succeeded on the source side and there's no re-dispatch path shown for a stuck message).

### Likelihood Explanation
This isn't a hypothetical attacker-triggered bug — it fires on every single call to `update_host_params`, the intents-coprocessor gateway dispatch helper, and (per the design doc) the relayer pallet's withdrawal and token-governor paths, under normal governance operation. The relayer's own selection logic explicitly gates delivery on profitability (`minimum_profit_percentage` in basis points) as documented in `docs/content/developers/explore/relayers.mdx`, so zero-fee messages are naturally deprioritized/skipped by the reference relayer implementation, making non-delivery the default behavior rather than an edge case.

### Recommendation
Fund these system dispatches with a genuine relayer incentive rather than a zero fee, or — per the project's own proposed fix in `docs/outbound-request-incentivization.md` — implement the decoupled `OutboundRequestDeliveryReward`/claim mechanism (keyed by `source_module_id`) in `pallet-relayer` so relayers can claim a governance-set reward against a destination delivery proof for these hyperbridge-originated messages, ensuring they are reliably delivered without depending on altruistic relaying.

### Proof of Concept
1. Governance calls `host-executive::update_host_params` (or `intents-coprocessor::update_params` / `add_deployment`) to update state that must propagate cross-chain.
2. The pallet calls `IsmpDispatcher::dispatch_request` with `FeeMetadata { payer: [0u8;32].into(), fee: Zero::zero() }` as shown at `modules/pallets/host-executive/src/lib.rs:225-231` and `modules/pallets/intents-coprocessor/src/lib.rs:1233-1239`.
3. `pallet-ismp`'s `dispatch_request` skips the `T::Currency::transfer` fee-escrow step because `fee.fee == Zero::zero()` (`modules/pallets/ismp/src/dispatcher.rs:98-106`), so no funds are placed in `RELAYER_FEE_ACCOUNT` for this commitment.
4. The Tesseract relayer's outbound-delivery selection logic queries the user-posted fee on the source and skips messages that fail the configured `minimum_profit_percentage` threshold; a zero fee never clears this bar.
5. The dispatched request commitment sits undelivered indefinitely — the destination host params/Intent Gateway parameters never update unless an altruistic relayer manually delivers it.

```markdown
## The problem

A regular cross-chain message that flows *through* hyperbridge has a fee attached at origin (the source chain transfers `fee.payer → RELAYER_FEE_ACCOUNT` and records `RequestPayments[commitment]` in pallet-hyperbridge's child trie). When a relayer delivers and the destination receipt lands back on hyperbridge, the existing `accumulate_fees` flow credits that fee to the relayer. That whole pipeline assumes a *user* paid at origin.

But hyperbridge itself originates requests too: host parameter propagation, host-executive updates, intents-coprocessor responses, token-governor messages, the relayer pallet's withdrawal request. Today these all dispatch with `FeeMetadata { payer: [0u8; 32].into(), fee: Default::default() }` (see `modules/pallets/host-executive/src/lib.rs:228`, `modules/pallets/intents-coprocessor/src/lib.rs:486`, `modules/pallets/relayer/src/lib.rs:638`, and `modules/pallets/token-governor/src/impls.rs`). Zero fee, zero payer. So relayers have no economic reason to pick them up, and the only thing that keeps them flowing today is altruism.

## The shape of the solution

The issue creator's preferred shape ([comment 4428807013](https://github.com/polytope-labs/hyperbridge/issues/532#issuecomment-4428807013)): use `pallet-relayer` to pay BRIDGE to whoever proves they delivered a hyperbridge-originated request. The messaging task in the tesseract relayer submits the claim.

Not every pallet on hyperbridge that dispatches a request is in scope. `pallet_ismp::child_trie::RequestCommitments` ends up holding commitments for every successful dispatch via `IsmpDispatcher`, which includes both the system messages we want to incentivize (host-executive, intents-coprocessor, token-governor, the relayer pallet's withdrawal path, future modules like bandwidth) and any other pallet that ends up dispatching from hyperbridge. The reward storage is therefore keyed by `source_module_id` and only modules with a non-zero reward are eligible. The `module_id` is the `from` field on the `PostRequest`, which each pallet sets to its unique module identifier. A module with zero reward is treated as not on the allowlist and rejected before any state proof verification runs.

This is structurally identical to the existing `claim_outbound_consensus_delivery_reward` (see `modules/pallets/relayer/src/outbound_consensus.rs`) on the consensus side. The request claim lives in its own `modules/pallets/relayer/src/outbound_request.rs` module that mirrors it: swap "consensus rotation delivered" for "request delivered," key the reward storage by `module_id`, and have the relayer ship the full `PostRequest` in the claim so the pallet can hash it on chain.

No changes to pallet-hyperbridge or to any of the system-message dispatch sites. The reward is decoupled from the dispatch path and paid out at claim time against a destination state proof.
```
