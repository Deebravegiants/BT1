### Title
Division rounding in `convert_to_balance` silently mints/refunds zero after tokens are already burned on the EVM side, permanently destroying bridged value - (File: `modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
`pallet-hyper-fungible-token`'s `on_accept` and `on_timeout` handlers convert an incoming ERC20 `uint256` amount into the local substrate `Balance` via `convert_to_balance`, which performs `value / 10^(erc_decimals - local_decimals)` and never checks whether the result truncates to zero. Because the corresponding EVM-side `send()` already unconditionally burned the full token amount before dispatch, any transfer whose scaled-down value rounds to zero results in tokens burned on the source chain with nothing minted (or refunded) on the destination — a silent, unrecoverable loss of funds, structurally identical to the reported `Pool.sol` division-rounding bug class.

### Finding Description
`convert_to_balance` in `modules/pallets/hyper-fungible-token/src/impls.rs`: [1](#0-0) 

divides the raw `U256` ERC20 amount by `10^(erc_decimals - local_decimals)` and stringifies/parses the quotient into the target `Balance` type. If the quotient is `0`, `dec_str` is `"0"`, which parses successfully as zero — the function returns `Ok(0)` rather than an error, so no validation catches the truncation.

This conversion is used in both cross-chain delivery paths:
- `on_accept` (normal delivery, mints/transfers to the beneficiary): [2](#0-1) 
- `on_timeout` (refund path, releases escrow/mints back to the original sender): [3](#0-2) 

Crucially, on the EVM side, `HyperFungibleToken.send()` burns the full `params.amount` from the caller *before* dispatching the cross-chain message, with no minimum-amount check: [4](#0-3) 

Token registration only enforces `erc_decimals >= local_decimals` (`ErcDecimalsBelowLocal`), it does not bound how large the decimal gap can be: [5](#0-4) 

So for any registered asset where `erc_decimals - local_decimals` is non-trivial (e.g. a token with 18 EVM decimals bridged to a local asset with 2, 4, or 6 decimals — well within what governance can configure), any bridged amount smaller than `10^(erc_decimals - local_decimals)` (in ERC20 base units) is burned on EVM but converts to `0` on the substrate side. `on_accept` proceeds to "mint" 0 and emits `TokenReceived { amount: 0, .. }` without any error, and the timeout/refund path likewise can refund `0` after the message already failed, leaving the original burn permanently unrecoverable in both cases.

### Impact Explanation
This is a direct, permanent loss/freezing of user funds reachable by any unprivileged user simply calling `send()` on a `HyperFungibleToken`/`WrappedHyperFungibleToken` EVM contract with an amount below the rounding threshold for that asset's registered decimal gap, or any relayer delivering a request whose dust-sized amount underflows to zero on `on_timeout`. Depending on the decimal configuration chosen by governance for a given asset (up to full range permitted by `ErcDecimalsBelowLocal`), the "dust" threshold can represent economically meaningful amounts, not just wei-level dust, making this exploitable as a systematic value-destruction vector (repeated small sends silently burn tokens with no compensating mint) — matching the "permanent freezing of funds" acceptance criterion.

### Likelihood Explanation
Likelihood is moderate-to-high: it requires no privileged access, only a normal `send()` call with a sufficiently small amount relative to the registered per-chain decimal precision, which is entirely within the control of the calling user or can be triggered incidentally by any UI/SDK that doesn't clamp minimum transfer sizes. The larger the configured decimal gap (e.g., a local asset with very few decimals bridging an 18-decimal EVM token), the larger the "zero-value" band and the easier it is to trigger, whether accidentally or as a griefing/value-destruction tool.

### Recommendation
In `convert_to_balance`, reject (return an error) when the computed local balance is zero but the input `value` was non-zero, and surface this as a distinct error variant in `HftError` (e.g. `AmountTooSmallForPrecision`) so `on_accept`/`on_timeout` fail loudly instead of silently minting/refunding zero. Additionally, consider enforcing on `send()` (EVM side) and/or `register_token`/`update_token` (substrate side) a minimum transferable amount derived from the configured decimal gap, or bound the maximum allowed `erc_decimals - local_decimals` spread, so dust amounts are rejected before the source-side burn/escrow occurs rather than after.

### Proof of Concept
1. Governance registers an asset via `register_token` with `local_decimals = 2` and an EVM chain config `decimals = 18` (permitted since `18 >= 2` satisfies `ErcDecimalsBelowLocal`), via: [6](#0-5) 
2. A user calls `HyperFungibleToken.send()` on the EVM chain with `amount = 10**15` wei (0.001 tokens) — well below `10^(18-2) = 10^16`, the rounding threshold. The contract burns this amount unconditionally: [7](#0-6) 
3. The message is relayed and delivered to `on_accept` on the substrate side. `convert_to_balance(10**15, 18, 2)` computes `10**15 / 10**16 = 0`, returning `Ok(0)`: [1](#0-0) 
4. `on_accept` mints/transfers `0` to the beneficiary and emits `TokenReceived { amount: 0, .. }` without reverting: [8](#0-7) 
5. Result: 0.001 tokens were burned on the EVM chain and nothing was credited on Hyperbridge — a permanent, unrecoverable loss of the bridged value.

pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}
