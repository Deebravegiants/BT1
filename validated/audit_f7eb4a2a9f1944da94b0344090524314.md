## Title
`fundRequest` swaps native ETH for fee tokens using `block.timestamp` as the Uniswap deadline, nullifying deadline protection - (`evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.fundRequest` lets any unprivileged caller top up the relayer fee for a pending request by sending native ETH, which is swapped into `feeToken()` via `IUniswapV2Router02.swapETHForExactTokens`. The deadline argument passed to the router is `block.timestamp` — the transaction's own execution time — rather than a caller-supplied, pre-committed deadline.

### Finding Description [1](#0-0) 

```solidity
function fundRequest(bytes32 commitment, uint256 amount) external payable notFrozen {
    if (msg.value > 0) {
        address[] memory path = new address[](2);
        address uniswapV2 = _hostParams.uniswapV2;
        path[0] = IUniswapV2Router02(uniswapV2).WETH();
        path[1] = feeToken();
        IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
            amount, path, address(this), block.timestamp
        );
    }
    ...
}
```

Uniswap's `deadline` check is `require(block.timestamp <= deadline)`. Since `deadline` here is set to `block.timestamp` at execution time, the check is tautologically true no matter when the transaction is actually mined — it provides zero real protection, exactly the anti-pattern flagged in the referenced report (using a low-level/near-equivalent mechanism that can be executed at an arbitrary, later point in time with stale price expectations). A transaction sitting in the mempool (delayed by network congestion, low gas price, or deliberately withheld/reordered by a block builder/validator) can be included and executed far later than when the user submitted it, at whatever the pool price is at that later time, with no reversion for staleness.

This is directly reachable by any unprivileged user calling `fundRequest` with `msg.value > 0` — no special role or governance action is required, satisfying the "unprivileged message dispatcher" reachability bar.

### Impact Explanation
Because the swap is `swapETHForExactTokens` (exact output of `amount` fee tokens, `msg.value` as max input), a user whose transaction is delayed will unknowingly execute the swap at whatever market price prevails when it is eventually mined, using up to their entire supplied `msg.value` of ETH — potentially reverting (if the required input now exceeds `msg.value`) or consuming substantially more ETH than intended for the same fixed fee-token amount. In either case, funds are spent unfavorably or the request-funding accounting is disrupted, since the caller has no way to bound the price impact of a delayed execution. This aligns with a Medium-severity "swap executed unfavorably due to missing deadline enforcement" class finding.

### Likelihood Explanation
Likelihood is realistic: any relayer or user funding a pending request via native ETH triggers this path, and transaction delay/reordering (congestion, MEV, private mempool holding) is common on public EVM chains. No attacker privilege is needed — an attacker (or even ordinary network conditions) can simply cause the transaction to be included later than expected.

### Recommendation
Accept a caller-supplied `deadline` parameter (or a bounded max delay, e.g. `block.timestamp + maxDelay`) in `fundRequest` and forward that value to `swapETHForExactTokens` instead of `block.timestamp`, so the Uniswap deadline check meaningfully rejects execution after the intended window, consistent with how `UniV3UniswapV2Wrapper` and `UniV4UniswapV2Wrapper` correctly thread through caller-provided deadlines ( [2](#0-1) ).

### Proof of Concept
1. Alice calls `fundRequest(commitment, amount)` with `msg.value = X` ETH intending to fund `amount` fee tokens at the current market rate.
2. The transaction is submitted with low gas or otherwise delayed/held (e.g., by a validator/MEV searcher) for an extended period.
3. When later included, `block.timestamp` at execution equals the deadline passed to the router, so the deadline check always succeeds regardless of elapsed time.
4. If ETH price relative to the fee token has moved unfavorably in that period, the swap either consumes far more of Alice's `msg.value` than expected, or reverts after the delay, wasting gas and leaving the request underfunded — all despite Alice believing a deadline safeguard was in place.
