### Title
Missing freeze-authority validation on `coin_mint`/`pc_mint` in `Initialize2` permanently freezes pool and LP funds - (File: `program/src/processor.rs`)

### Summary
`process_initialize2` explicitly rejects an `lp_mint` that has a freeze authority, but performs no equivalent check on the `coin_mint` or `pc_mint` supplied by the (unprivileged) pool creator. Because the AMM's coin/pc vaults are just token accounts of those externally-supplied mints, any freeze authority retained on `coin_mint`/`pc_mint` can later freeze the vault accounts, permanently DoS-ing swaps, deposits and withdrawals for the whole pool.

### Finding Description
This is the same bug class as the external report: `safeName()` assumes every ERC20 behaves in a "standard-compliant" way and blindly decodes external data, causing an unhandled failure mode when a non-conforming token is used. Here, `process_initialize2` makes the analogous unvalidated assumption that any SPL mint used as `coin_mint`/`pc_mint` behaves like a "safe" token (no freeze authority), yet never checks for it — even though the code demonstrably knows this check matters, since it performs it for `lp_mint`: [1](#0-0) 

The mints are unpacked directly from attacker-supplied accounts with no freeze-authority validation: [2](#0-1) 

The vaults created for those mints are then only checked for delegate/close-authority, never freeze status: [3](#0-2) 

Any unprivileged caller of `Initialize2` fully controls which mint accounts are passed in as `coin_mint`/`pc_mint`. If either mint retains an active `freeze_authority` (attacker-controlled), the attacker can later call the standard SPL Token `FreezeAccount` instruction against `amm_coin_vault`/`amm_pc_vault` at any point after pool creation.

### Impact Explanation
Once a vault token account is frozen by the mint's freeze authority, the SPL Token program rejects any `Transfer`/`Burn`/`MintTo` operation touching it. All AMM instructions that move funds through `Invokers::token_transfer`, `token_transfer_with_authority`, or `token_burn` against that vault (`Deposit`, `Withdraw`, `SwapBaseIn`, `SwapBaseOut`) will subsequently fail: [4](#0-3) [5](#0-4) 

This permanently locks all coin/pc tokens, and by extension all LP holders' claims on them, inside the pool with no recovery path (only `withdrawpnl`, which is privileged/config-gated, remains reachable, and even that requires unfrozen vaults). This is a permanent freezing of user and LP funds, matching the accepted impact classes.

### Likelihood Explanation
High reachability: pool creation via `Initialize2` is fully permissionless, and the attacker chooses both mints in the same transaction. The only extra step needed is invoking the standard SPL Token `FreezeAccount` instruction (with the mint's freeze authority, which the attacker controls since they created/chose the mint) against the AMM's vault at any later point — no privileged Raydium signer is required.

### Recommendation
Mirror the existing `lp_mint` check for both `coin_mint` and `pc_mint` in `process_initialize2`: reject initialization if either mint's `freeze_authority` is `COption::Some(_)`, i.e. add the same guard used at: [6](#0-5) 
right after unpacking `coin_mint`/`pc_mint` at: [2](#0-1) 

### Proof of Concept
1. Attacker creates SPL mint `M` with a freeze authority they control (or with mint/freeze authority combined at first, then keeps freeze authority live).
2. Attacker calls `Initialize2` (`process_initialize2`) as `user_wallet_info`, supplying `M` as `amm_coin_mint_info` (or `amm_pc_mint_info`). The function unpacks the mint at [2](#0-1)  and never checks `freeze_authority`, so initialization succeeds and vault `amm_coin_vault_info` is created as an ATA of `M`.
3. At any later time, the attacker issues a standard SPL Token `FreezeAccount` instruction against `amm_coin_vault_info` using the freeze authority of `M`.
4. Any subsequent `Deposit`, `Withdraw`, `SwapBaseIn`, or `SwapBaseOut` instruction that calls `Invokers::token_transfer`/`token_transfer_with_authority`/`token_burn` on the frozen vault (e.g. [7](#0-6) ) now fails at the SPL Token program level, permanently locking all coin/pc/LP funds already deposited in the pool.
