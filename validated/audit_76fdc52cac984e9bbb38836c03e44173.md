Audit Report

## Title
Vault gateway replay-guard permanently blocks legitimate request retries after a downstream failure - ([File: core/capabilities/vault/request_replay_guard.go])

## Summary
`RequestReplayGuard.CheckAndRecord` is invoked inside `authorizer.AuthorizeRequest` (`core/capabilities/vault/authorizer.go:109`) as soon as JWT/allowlist authorization succeeds — before the request is actually dispatched to and processed by the Vault DON. If any step after authorization fails (fan-out to DON nodes fails, `writeMethodsEnabled` gate is disabled, quorum can't be reached), the client's callback returns an error but the digest recorded in the replay guard is never cleared, so any retry of the identical operation is rejected with `ErrRequestAlreadySeen` until the entry naturally expires, even though the operation never completed.

## Finding Description
The authorization flow computes and records the request digest for replay protection at `core/capabilities/vault/authorizer.go:99-119`: `AuthorizeRequest` calls the underlying auth mechanism (JWT or allowlist) to get an `AuthResult`, then immediately calls `a.replayGuard.CheckAndRecord(authResult.Digest(), authResult.ExpiresAt())` — consuming the digest slot at this point. [2](#0-1) 

This authorization step happens inside `GatewayVaultRequestProcessor.ProcessRequest` (via `authorizeAndStamp`), which is called from `handler.HandleJSONRPCUserMessage` at `core/services/gateway/handlers/vault/handler.go:427` — strictly before `h.newActiveRequest` and before dispatch to `handleSecretsCreate`/`handleSecretsUpdate`/`handleSecretsDelete`/`fanOutToVaultNodes`. [3](#0-2) 

Those downstream handlers can independently fail for reasons unrelated to authorization validity: the `writeMethodsEnabled.AllowErr` gate can reject the request (`core/services/gateway/handlers/vault/handler.go:616-623`), or `fanOutToVaultNodes` can fail if all DON members are unreachable (`core/services/gateway/handlers/vault/handler.go:736-748`). In both cases `sendResponse` is called with an error, but nothing here touches the replay guard.

`RequestReplayGuard.CheckAndRecord` and `ClearExpired`/`clearExpiredLocked` are the only functions that mutate the `seen` map — entries are removed only by time-based expiry, never by an explicit rollback on downstream failure. [4](#0-3) 

Grepping the codebase confirms `CheckAndRecord` is called from exactly one call site (`authorizer.go`), and there is no corresponding "un-record" or "release" function called anywhere on failure paths in `handler.go`, `gateway_vault_request_processor.go`, or elsewhere. The existing system test explicitly documents and tolerates this exact behavior as an expected side effect under load, treating the `ErrRequestAlreadySeen` message as evidence the original request must have succeeded — which is only true if the failure mode is a client-side timeout, not a genuine gateway/DON-side failure. [5](#0-4) 

## Impact Explanation
This is a legitimate-client denial-of-service / stuck-retry bug: any properly-authorized `vault.secrets.create/update/delete` request that fails for a transient, gateway-side reason after authorization (DON connectivity blip, `writeMethodsEnabled` gate flip, quorum unreachable) becomes un-retryable with the identical content until the replay-guard entry naturally expires (bounded by `jwtValidationLeeway` + JWT `exp`, or the allowlist-auth equivalent). Since the digest is a deterministic function of request content and (for JWT auth) is asserted externally in the token, the client cannot simply resubmit the same logical operation sooner. This maps to an availability/reliability impact on the Vault capability rather than a confidentiality/authorization-bypass issue — no unauthorized action, key/secret exfiltration, or role bypass occurs.

## Likelihood Explanation
The trigger conditions (fan-out failure to all DON members, or `writeMethodsEnabled` toggling off mid-flight) are operational conditions reachable without any privilege escalation, from ordinary network flakiness or admin-side config toggles, and require only a normal, already-authorized client request. No malicious peer, node compromise, or operator access is needed to reach the buggy code path itself — an ordinary authorized workflow client hitting a transient gateway/DON hiccup is sufficient.

## Recommendation
Move the replay-guard consumption (`CheckAndRecord`) to occur only after a request has reached a terminal, DON-verified success outcome, rather than at authorization time — or add an explicit "release/unrecord" call on the replay guard for any gateway/infrastructure-side failure path (fan-out failure, write-methods-disabled gate, quorum unreachable) in `handler.go`, while preserving replay protection for genuine user errors (invalid params, unauthorized).

## Proof of Concept
1. Client obtains a valid Auth0 JWT (or allowlist-based auth) with `request_digest` = D for a specific `vault.secrets.create` payload.
2. Client sends the request; `authorizer.AuthorizeRequest` (`core/capabilities/vault/authorizer.go:109`) succeeds and records digest D in `RequestReplayGuard.seen`.
3. `handler.handleSecretsCreate` → `fanOutToVaultNodes` fails because all DON members are unreachable (`core/services/gateway/handlers/vault/handler.go:746-748`), returning a `FatalError` to the client; the create never completes.
4. Client retries with the identical payload/digest D (fresh JWT if using JWT auth).
5. `authorizer.AuthorizeRequest` → `CheckAndRecord(D, ...)` returns `ErrRequestAlreadySeen` (`core/capabilities/vault/request_replay_guard.go:41-43`), and the retry is rejected despite the original operation never succeeding, until the entry expires.

A Go unit test can construct a `handler` with a `don.SendToNode` mock that always errors, submit a create request through `HandleJSONRPCUserMessage`, confirm the `FatalError` response, then resubmit the identical request/digest and assert `ErrRequestAlreadySeen` is returned instead of another attempt to fan out to nodes.

func (g *RequestReplayGuard) CheckAndRecord(digest string, expiresAtUnix int64) error {
	g.mu.Lock()
	defer g.mu.Unlock()

	g.clearExpiredLocked()

	if _, exists := g.seen[digest]; exists {
		return ErrRequestAlreadySeen
	}

	g.seen[digest] = expiresAtUnix
	return nil
}

// ClearExpired removes all entries whose expiry timestamp is in the past.
// Call this to eagerly reclaim memory even when CheckAndRecord is not invoked.
func (g *RequestReplayGuard) ClearExpired() {
	g.mu.Lock()
	defer g.mu.Unlock()
	g.clearExpiredLocked()
}

func (g *RequestReplayGuard) clearExpiredLocked() {
	now := g.nowFunc().UTC().Unix()
	for digest, expiry := range g.seen {
		if now > expiry {
			delete(g.seen, digest)
		}
	}
}
