### Title
`send_transaction_with_context` panics on unknown/garbage `recent_blockhash`, halting the BanksServer channel - (File: banks-server/src/banks_server.rs)

### Summary
`Banks::send_transaction_with_context` calls `root_bank().get_blockhash_last_valid_block_height(blockhash).unwrap()` on a caller-supplied `VersionedTransaction` before any sanitization or blockhash validation occurs. Any transaction whose `recent_blockhash` field is not a hash the bank recognizes causes `get_blockhash_last_valid_block_height` to return `None`, and the `.unwrap()` panics the executing task.

### Finding Description
`send_transaction_with_context` (banks-server/src/banks_server.rs:222-244) extracts `blockhash` directly from the unvalidated `transaction.message.recent_blockhash()` and immediately does:
```
let last_valid_block_height = self
    .bank_forks
    .read()
    .unwrap()
    .root_bank()
    .get_blockhash_last_valid_block_height(blockhash)
    .unwrap();
``` [1](#0-0) 

Unlike `process_transaction_with_commitment_and_context`, which first runs `SanitizedTransaction::try_create` and `sanitized_transaction.verify()` before touching `get_blockhash_last_valid_block_height` and gracefully returns `Some(Err(err))` on failure [2](#0-1) , `send_transaction_with_context` performs no sanitization at all — it does not check signatures, does not verify the message, and does not validate that the blockhash is known. `get_blockhash_last_valid_block_height` returns an `Option<u64>` and yields `None` whenever the supplied hash isn't present in the bank's recent blockhash queue (e.g., a garbage/expired hash), so any attacker-controlled `VersionedTransaction` with an arbitrary `recent_blockhash` reaches the `.unwrap()` and panics the async task handling that tarpc call.

This entrypoint is exposed over the network via `start_tcp_server`, which spawns a `BanksServer` per accepted TCP channel and executes `chan.execute(server.serve())` [3](#0-2) . A panic inside the task driving that channel will abort processing for that connection/channel; because channels are limited to one per IP but the service otherwise accepts any TCP client that can reach the BanksServer listen address, an unprivileged remote caller can trigger this without any special privileges beyond network reachability to the endpoint.

### Impact Explanation
This is a denial-of-service against the `Banks` tarpc service: an attacker sends one `VersionedTransaction` with a non-existent `recent_blockhash` to `send_transaction_with_context`, and the async task servicing that channel panics rather than returning an error. This halts transaction submission processing on that channel/connection instead of rejecting the malformed transaction deterministically, matching the "liveness/denial of service" bounty category for the BanksServer test-transport pathway.

### Likelihood Explanation
Trivial and fully reproducible: the attacker only needs network access to the exposed tarpc/BanksServer TCP endpoint (`start_tcp_server`) and can construct a `VersionedTransaction` with any `recent_blockhash` not present in `root_bank`'s blockhash queue (e.g., `Hash::default()` or a random hash). No signature validity, staking, or leader/gossip control is required — this matches the "attacker is unprivileged" threat model in scope.

### Recommendation
Validate/sanitize the transaction (or at minimum check the blockhash) before calling `get_blockhash_last_valid_block_height`, and replace the `.unwrap()` with a graceful error path, mirroring the pattern already used in `process_transaction_with_commitment_and_context`. For example:
```rust
let last_valid_block_height = match self
    .bank_forks
    .read()
    .unwrap()
    .root_bank()
    .get_blockhash_last_valid_block_height(blockhash)
{
    Some(h) => h,
    None => return, // or propagate an error via the API surface
};
```
Ideally also sanitize/verify the transaction before forwarding it to `transaction_sender`, consistent with the other `process_transaction_*` handlers.

pub async fn start_tcp_server(
    listen_addr: SocketAddr,
    tpu_addr: SocketAddr,
    bank_forks: Arc<RwLock<BankForks>>,
    block_commitment_cache: Arc<RwLock<BlockCommitmentCache>>,
    exit: Arc<AtomicBool>,
) -> io::Result<()> {
    // Note: These settings are copied straight from the tarpc example.
    let server = tcp::listen(listen_addr, Bincode::default)
        .await?
        // Ignore accept errors.
        .filter_map(|r| future::ready(r.ok()))
        .map(server::BaseChannel::with_defaults)
        // Limit channels to 1 per IP.
        .max_channels_per_key(1, |t| {
            t.as_ref()
                .peer_addr()
                .map(|x| x.ip())
                .unwrap_or_else(|_| Ipv4Addr::UNSPECIFIED.into())
        })
        // serve is generated by the service attribute. It takes as input any type implementing
        // the generated Banks trait.
        .map(move |chan| {
            let (sender, receiver) = unbounded();

            let client = create_client(None, tpu_addr, exit.clone());

            SendTransactionService::new(
                bank_forks.clone(),
                receiver,
                client,
                Config {
                    retry_rate_ms: 5_000,
                    ..Config::default()
                },
                exit.clone(),
            );

            let server = BanksServer::new(
                bank_forks.clone(),
                block_commitment_cache.clone(),
                sender,
                Duration::from_millis(200),
            );
            chan.execute(server.serve())
        })
        // Max 10 channels.
        .buffer_unordered(10)
        .for_each(|_| async {});
