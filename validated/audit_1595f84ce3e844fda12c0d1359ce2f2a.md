### Title
Stale operator authorization reused for delayed signups instead of re-validating at time of use - (File: `src/plans/mod.rs`)

### Summary
The GMX report describes a "time-of-check vs. time-of-use" flaw: an order's validity is checked against a price at submission time (T), but keeper delay causes execution at time T+N using a different, potentially stale/incorrect value, without re-validating against the authoritative source at execution time. The analogous pattern in orb-core is `scan_remaining_qr_codes` and `idle_scan_user_qr_code` in `src/plans/mod.rs`, which cache the result of the backend operator-authorization check (`verify_operator_qr_code`) and reuse that cached `valid=true` verdict for as long as `operator_qr_expiration_time` has not elapsed, rather than re-checking operator authorization at the moment the signup is actually authorized/executed.

### Finding Description
`verify_operator_qr_code` performs a backend call at time T to determine whether an operator QR code is currently valid, and returns location data associated with that check: [1](#0-0) 

The result of that single check (`OperatorData`, stamped with `timestamp: Instant::now()`) is then cached and reused across subsequent signup attempts as long as the elapsed time is below `operator_qr_expiration_time`, in both `scan_remaining_qr_codes`: [2](#0-1) 

and `idle_scan_user_qr_code`, which computes the *remaining* expiration window and continues to trust the same cached operator authorization for further user QR scans: [3](#0-2) 

Just as GMX's `Oracle._setPricesFromPriceFeeds` uses "the current value, rather than the value at the time the order was submitted" for delayed order execution, here the orb uses the operator-validity verdict from the *initial* scan for every subsequent signup performed within the expiration window, rather than re-confirming operator authorization (revocation, ban, fraud flag, etc.) with the backend at the time each individual signup is actually executed. The `user_status::request` call that follows only validates the *user* QR code and forwards the cached `operator_data` (including its stale location/validity context) without re-verifying the operator status itself: [4](#0-3) 

### Impact Explanation
If an operator's authorization is revoked or altered on the backend (e.g., due to fraud detection, suspension, or a compromised operator credential) after the initial QR scan but before the expiration window elapses, the orb will continue to process one or more additional signups attributing them to that operator using the stale authorization/location data, without re-checking with `backend::operator_status::request`. This can result in signups being processed under an operator identity that should no longer be trusted at the time of execution — a misattributed/unauthorized-signup condition analogous to GMX orders executing against stale price data during a de-peg window.

### Likelihood Explanation
This requires a legitimate multi-signup session where the expiration window (`operator_qr_expiration_time`) is non-trivial and an operator's backend status changes mid-window — a plausible but narrow operational scenario. I could not fully verify the exact default duration configured for `operator_qr_expiration_time` (only found its declaration/usage sites in `src/config.rs` and `src/plans/mod.rs`, not the concrete default constant value), so the real-world exposure window size is unconfirmed.

### Recommendation
Re-validate operator authorization against the backend (`backend::operator_status::request`) at signup-execution time rather than relying solely on a cached verdict bounded only by a time-based expiration, particularly for self-serve flows where multiple signups can occur in the same session (`idle_scan_user_qr_code`, `scan_remaining_qr_codes`). At minimum, shorten `operator_qr_expiration_time` or force re-verification before finalizing each individual signup (`do_signup`).

### Proof of Concept
Not directly demonstrable without backend access to toggle an operator's authorization status mid-session; the vulnerable code path is the reuse condition `operator_data.timestamp.elapsed() < operator_qr_expiration_time` in `scan_remaining_qr_codes` (`src/plans/mod.rs:797,807`), which allows bypassing a fresh `verify_operator_qr_code` call for subsequent signups within that window.
