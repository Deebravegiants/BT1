### Title
`require_external_recipient` only blocks the pool and controller, so `borrow`/`withdraw` to other protocol contracts strands the tokens permanently - (File: contracts/controller/src/positions/mod.rs)

### Summary
The analog of the external report's "insufficient input validation locks funds forever" class in XOXNO Lending is the recipient whitelist in `require_external_recipient`. `borrow` and `withdraw` accept an arbitrary `to: Option<Address>` and only reject two protocol addresses — the pool and the controller itself. Tokens sent to any other protocol contract whose custody cannot move them (position NFT, governance, price aggregator) are debited from the position/pool but land in a contract with no recovery or forwarding entrypoint, so they are stuck forever.

### Finding Description
`process_borrow` resolves `to.unwrap_or(caller)` and passes it through `require_external_recipient`, which asserts only that `recipient != controller && recipient != pool`. [1](#0-0) [2](#0-1)  The same helper gates `withdraw`. This check was added for the GH-17 issue, whose test file documents the stranding mechanism: "the pool debits cash without its balance moving, and the controller holds funds no balance-delta measurement can ever claim". [3](#0-2) 

The identical mechanism applies to the other protocol contracts: the pool's `transfer_out` sends real tokens to `receiver`, and neither the position NFT, governance, nor price aggregator exposes any token-sweep/rescue interface (architecture docs confirm the DeFindex adapter "has no recovery path for arbitrary stranded assets" and no contract other than the pool/controller moves custody). [4](#0-3) [5](#0-4) 

### Impact Explanation
Permanent freezing of funds: a `borrow(caller, account_id, legs, Some(position_nft_or_governance))` mints debt on the account, debits pool `cash`, and delivers tokens to a contract that can never release them. The borrower still owes the debt while the principal is unrecoverable — a total loss of the borrowed amount with no admin rescue path.

### Likelihood Explanation
Low-to-medium. It requires the account owner/delegate to pass a wrong-but-plausible address (e.g., copying a protocol contract address into `to`), which is a self-inflicted misconfiguration — the same "user can misconfigure inputs" likelihood profile as the external report. No privileged action is needed; any holder of a collateralized account reaches it.

### Recommendation
Extend `require_external_recipient` (or the call sites in `positions/debt.rs` and `positions/supply.rs`) to also reject the position NFT, governance, price aggregator, swap aggregator and any other known protocol contract addresses, mirroring how the flash-position receiver check rejects the controller (`#412`). Alternatively, bound `to` to non-contract addresses or to caller by default.

### Proof of Concept
```rust
// Setup: Alice owns a collateralized account (supplied USDC, ETH market has cash).
let alice = t.get_or_create_user(ALICE);
let id = t.account_id(ALICE);
let nft = t.position_nft_address(); // or governance / price-aggregator address
let leg = vec![&t.env, (hub_asset(t.resolve_asset("ETH")), 10_000_000)];

// Passes require_external_recipient: nft != controller && nft != pool.
t.ctrl_client().borrow(&alice, &id, &leg, &Some(nft));

// Debt is minted on Alice's account; ETH sits in the NFT contract.
// The NFT contract has no token-transfer-out entrypoint -> tokens stuck forever.
```
The existing test `borrow_to_the_pool_is_rejected_before_cash_moves` shows the exact stranding shape that motivated the guard; the guard simply does not extend to the remaining protocol contracts. [6](#0-5)

pub(crate) fn require_external_recipient(env: &Env, cache: &mut Context, recipient: &Address) {
    let pool = cache.cached_pool_address();
    assert_with_error!(
        env,
        *recipient != env.current_contract_address() && *recipient != pool,
        FlashLoanError::InvalidFlashloanReceiver
    );
}
