### Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, excluding the `shop-domain`, `topic`, and `webhook-id` headers from the HMAC-protected surface. `Webhooks::Registry.process` nonetheless trusts these unauthenticated headers to construct the `WebhookMetadata` handed to the app's handler, breaking the intended binding: HMAC(secret, body) == valid should imply shop-domain == the shop the payload actually originated from, but the shop value is never part of what's authenticated.

### Finding Description
`Webhooks::Request#hmac` and `#to_signable_string` are defined as: [1](#0-0) 

Only `@raw_body` is fed into HMAC verification. Meanwhile, `shop`, `topic`, `api_version`, and `webhook_id` are all read straight from HTTP headers with no cryptographic tie to the signed payload: [2](#0-1) 

`Registry.process` validates only the HMAC of the body, then forwards the unauthenticated `request.shop` value directly to the handler: [3](#0-2) 

`HmacValidator.validate` computes the digest strictly over `verifiable_query.to_signable_string`: [4](#0-3) 

The binding that should hold is: `shop header == shop that legitimately produced this exact signed body`. Because the `shop-domain` header sits outside `to_signable_string`, that equality is never checked. An unprivileged internet user who has installed the app on their own (freely creatable) Shopify shop will legitimately receive real webhook deliveries whose HMAC is computed with the app's real `api_secret_key` over the body. Since the header set is not part of the signed material, the attacker can replay that exact body/HMAC pair to the app's public webhook endpoint while substituting the `shopify-shop-domain` header for a victim shop's domain. `Registry.process` will still validate the HMAC successfully (it only checks the body) and will hand the handler a `WebhookMetadata` claiming the payload is `shop: <victim>` while it's actually attacker-controlled content.

### Impact Explanation
Any handler that uses `WebhookMetadata#shop` to key per-tenant storage, look up/create sessions, or attribute data to a merchant will process attacker-supplied content under the identity of a shop the attacker does not control — a cross-tenant identity confusion rooted entirely in this gem's `Webhooks::Request`/`Registry` implementation.

### Likelihood Explanation
Exploitation only requires: (1) installing the target app on any shop, which is a normal, unprivileged, and free operation for an internet user, to obtain one genuinely-HMAC'd webhook body/signature pair, and (2) POSTing that same body/HMAC to the app's public webhook endpoint with a forged `shop-domain` header. No access to `api_secret_key`, access tokens, or the merchant's credentials is required.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the HMAC-protected signable string, or otherwise cryptographically bind the shop identity to the payload before trusting `request.shop` in `Registry.process`, e.g. verify the shop against a shop known to be associated with the specific webhook subscription/session rather than trusting the header at face value.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and triggers a webhook (e.g. `orders/create`) so Shopify delivers a POST with body `B` and header `shopify-hmac-sha256: HMAC(secret, B)`.
2. Attacker captures `B` and the valid HMAC.
3. Attacker POSTs to the app's public webhook endpoint with the same body `B`, the same valid HMAC header, but `shopify-shop-domain: victim.myshopify.com`.
4. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `B` against the HMAC (`lib/shopify_api/webhooks/request.rb:35-38`, `lib/shopify_api/utils/hmac_validator.rb:26-31`).
5. The handler receives `WebhookMetadata.new(..., shop: "victim.myshopify.com", body: <attacker-controlled JSON>, ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), causing the app to process attacker data under the victim shop's identity.
