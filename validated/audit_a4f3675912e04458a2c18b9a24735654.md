### Title
Webhook `shop` domain is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, then unconditionally trusts the `shop-domain` header as the tenant identity passed to the app's handler. Because the HMAC signature never binds the `shop` value, an attacker who possesses one valid `(body, hmac)` pair can replay it with an arbitrary `shop-domain` header and have it accepted as an authentic webhook for any shop.

### Finding Description
`Webhooks::Request` implements `Utils::VerifiableQuery`, and `to_signable_string` returns only the raw body: [1](#0-0) 

The `shop` accessor is read directly from the unauthenticated `shopify-shop-domain` / `x-shopify-shop-domain` header: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (i.e., the raw body) and compares it to the `hmac` header: [3](#0-2) 

`Registry.process` checks only this body HMAC, then builds `WebhookMetadata` using the unauthenticated `request.shop` and hands it to the app's registered handler as though it were verified: [4](#0-3) 

The identity binding that should hold is: `shop-domain header == shop bound by HMAC(secret, signed_content)`. In this implementation, `signed_content` = raw body only, so `shop` is **not** part of what is authenticated — breaking that equality. The gem's own documentation confirms `data.shop` is meant to be trusted directly by host applications for tenant-scoped work (e.g. enqueuing jobs keyed by shop), reinforcing that this is the gem's intended trust contract, not a case of the host ignoring documented API: [5](#0-4) 

### Impact Explanation
This is a cross-tenant identity confusion: the gem hands the downstream app handler a `shop` value that was never authenticated by the HMAC, while asserting (via `InvalidWebhookError` only firing on body mismatch) that the whole request "did indeed come from Shopify." An attacker who can obtain any single legitimate `(raw_body, hmac)` pair — trivially achievable by installing the app on their own shop and capturing one of their own genuine webhook deliveries — can resend that exact body/HMAC pair to the app's webhook endpoint while substituting a victim shop's domain in the `shop-domain` header. The signature still validates (it never covered `shop`), and the handler will process/attribute that body as belonging to the victim shop. Depending on the handler logic (e.g., `customers/redact`, `shop/redact`, `orders/create` webhooks driving per-shop state), this enables cross-tenant data injection/confusion in the host application, satisfying the Critical "cross-tenant access" impact category via a boundary the gem itself is responsible for (webhook authenticity/tenant binding).

### Likelihood Explanation
Likelihood is realistic: an attacker needs no privileged credentials, no access token, and no `api_secret_key`. They only need to be a Shopify Partner/developer able to install their own app instance and capture one webhook body+HMAC pair for a topic they intend to spoof (bodies for many topics like `shop/redact` or `app/uninstalled` are fixed or attacker-influenced in structure), then replay it against any target app's public webhook endpoint with a forged `shop-domain` header.

### Recommendation
Bind the `shop` domain into the signed material used to authenticate the webhook, or independently verify `request.shop` against Shopify's HMAC-covered payload data (e.g., derive/cross-check shop identity from a value that is actually inside the signed body, or require the host app to look up an existing registered webhook/session for that shop and reject if inconsistent). At minimum, document explicitly that `data.shop` in `WebhookMetadata` is not authenticated and must not be trusted for tenant attribution without additional verification, and consider validating it against a known/trusted shop list before dispatching to the handler in `Registry.process`.

### Proof of Concept
```ruby
# Attacker owns "attacker-shop.myshopify.com" and has installed the target app there.
# Shopify sends a genuine webhook to the attacker's own endpoint:
#   body = '{"id":123,"note":"hi"}'
#   headers include:
#     x-shopify-hmac-sha256: <valid HMAC of body computed with the app's real secret>
#     x-shopify-shop-domain: attacker-shop.myshopify.com

body = '{"id":123,"note":"hi"}'
valid_hmac_base64 = "<captured from genuine delivery>"

# Attacker replays the exact same body+hmac to the app's public webhook URL,
# only changing the shop-domain header to a victim shop:
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => valid_hmac_base64, # unchanged - still matches body
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged, not covered by HMAC
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => Utils::HmacValidator.validate(request) returns true (body HMAC still matches)
# => handler.handle(data: WebhookMetadata(shop: "victim-shop.myshopify.com", body: ..., ...))
# The host app now processes/attributes this data as belonging to victim-shop.myshopify.com.
