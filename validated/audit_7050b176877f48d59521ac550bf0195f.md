### Title
Fee-on-Transfer Tokens Cause Escrow Over-Crediting in Tron `IntentGatewayV2.placeOrder` - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2.placeOrder` credits the intent's escrow accounting (`_orders[commitment][token]`) with the user-specified/requested input amount (reduced only by the protocol fee), instead of the amount actually received by the contract via `safeTransferFrom`/sweep. For fee-on-transfer (deflationary) ERC20 tokens, the contract receives strictly less than the escrowed accounting believes it holds, producing a permanent shortfall between real token balance and the sum of all outstanding escrow claims.

### Finding Description
In the non-predispatch branch of `placeOrder`, tokens are pulled with `safeTransferFrom` and the escrow is incremented using the *nominal* `reducedInputs[i].amount` (derived from `order.inputs[i].amount`), with no balance-before/balance-after check: [1](#0-0) 

Compare this to the mainline EVM `IntentGatewayV2.sol`, which was hardened specifically for this bug class: it records `balBefore`, performs the transfer, then sets `order.inputs[i].amount = IERC20(token).balanceOf(address(this)) - balBefore` before computing the commitment and crediting escrow: [2](#0-1) 

The Tron predispatch branch has the same defect: it computes `dust` from `balance - requiredAmount` (the dispatcher-side balance vs. the nominal requirement) but then credits escrow with the pre-computed `reducedInputs[i].amount`, not the amount the gateway itself actually received after the final sweep `transfer` call (which can itself be taxed again by a fee-on-transfer token): [3](#0-2) 

The dedicated foundry test suite (`FeeOnTransferToken`) exists and passes only against the patched mainline contract, confirming this is a known, previously-fixed bug class that was not ported to the Tron contract: [4](#0-3) 

### Impact Explanation
Because escrow bookkeeping (`_orders[commitment][token]`) is inflated relative to the token balance actually custodied by the Tron `IntentGatewayV2` contract, the aggregate escrow liabilities across all open orders can exceed the real ERC20 balance held by the contract. When solvers fill orders and users/solvers withdraw via `_withdraw`-style logic (shared `IntentsBase._withdraw`, which does `IERC20(token).safeTransfer(beneficiary, amount)` based on the escrow accounting), the first several withdrawals succeed by draining real balance, but the shortfall means later legitimate order fillers/beneficiaries cannot be paid in full — their transfers revert or the contract becomes insolvent for that token, permanently freezing funds tied to unrelated, honestly-collateralized orders. This is a cross-user fund-freezing/insolvency bug reachable by any user submitting a single `placeOrder` transaction with a deflationary/fee-on-transfer input token.

### Likelihood Explanation
Likelihood is high: any unprivileged user can trigger this by simply placing an order using a fee-on-transfer or rebasing ERC20 token as input — no special permissions, timing, or race conditions are required. Given fee-on-transfer tokens are common in the wild, and the gateway does not reject or specially handle them, this is trivially reachable via the `placeOrder` entry point.

### Recommendation
Mirror the fix already applied in the mainline `evm/src/apps/IntentGatewayV2.sol`: measure `balanceOf(address(this))` immediately before and after each `safeTransferFrom`/sweep, use the delta as the actual received amount when computing `reducedInputs`, the commitment, and the escrow credit in `evm/tron/contracts/apps/IntentGatewayV2.sol`'s `placeOrder` (both the predispatch and non-predispatch branches), instead of trusting the caller-specified `order.inputs[i].amount`.

### Proof of Concept
1. Deploy a 1%-fee deflationary ERC20 token (e.g. the `FeeOnTransferToken` test contract) and mint balance to a user on the Tron deployment.
2. User approves `IntentGatewayV2` (Tron) for `inputAmount = 1000e18` and calls `placeOrder` with `order.inputs[0] = {token: FOT, amount: 1000e18}` (no predispatch).
3. `safeTransferFrom` moves only `990e18` into the gateway (1% fee burned/retained by token), but `_orders[commitment][FOT] += reducedInputs[0].amount` credits based on `1000e18` (minus only the protocol fee), i.e. escrow believes it holds ~1000e18 (or `1000e18 * (1-protocolFeeBps)`), not the actual `990e18` received.
4. Repeat with multiple orders/users. Aggregate escrow claims for `FOT` across all commitments will exceed `IERC20(FOT).balanceOf(gateway)`.
5. When solvers attempt to withdraw escrowed `FOT` for earlier orders, later withdrawals fail (insufficient balance) or the contract lacks funds to honor all outstanding escrow, demonstrating the freezing/insolvency impact — directly analogous to the escrow test in `evm/tests/foundry/IntentGatewayV2SameChainTest.sol:2440-2494`, but unmitigated on the Tron contract.

    /// @notice Escrow correctly reflects actual received amount for fee-on-transfer tokens.
    function testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived() public {
        // Deploy a 1% fee-on-transfer token
        FeeOnTransferToken fot = new FeeOnTransferToken(100); // 1% = 100 bps
        fot.mint(user, 10000 * 1e18);

        uint256 inputAmount = 1000 * 1e18;
        uint256 expectedReceived = inputAmount - (inputAmount * 100) / 10000; // 990

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(fot)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 900 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        vm.startPrank(user);
        fot.approve(address(intentGateway), inputAmount);
        intentGateway.placeOrder(order, bytes32(0));
        vm.stopPrank();

        // Gateway should hold only what it actually received
        assertEq(
            fot.balanceOf(address(intentGateway)), expectedReceived, "Gateway balance should match received amount"
        );

        // Reconstruct the order as placeOrder would have mutated it
        order.user = bytes32(uint256(uint160(user)));
        order.source = host.host();
        order.nonce = 0;
        order.inputs[0].amount = expectedReceived;
        bytes32 commitment = keccak256(abi.encode(order));

        // Escrow should match actual received, not the user-specified amount
        assertEq(
            intentGateway._orders(commitment, address(fot)),
            expectedReceived,
            "Escrow should equal actual received amount"
        );
    }
