### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable payload from the raw request body only, while the `shop` (and `topic`/`webhook_id`/`api_version`) values are read directly from unauthenticated HTTP headers. `Utils::HmacValidator` verifies only that the body matches the given HMAC, never binding the claimed shop to that signature. The registry then dispatches to the app's webhook handler using this unauthenticated `shop` value.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is derived purely from the `shopify-shop-domain` / `x-shopify-shop-domain` header, with no cryptographic tie to the HMAC: [2](#0-1) 

`Utils::HmacValidator.validate` only recomputes and compares the HMAC over `to_signable_string` (i.e., the body) against the `hmac` value; it never inspects or binds `shop`: [3](#0-2) 

`Webhooks::Registry.process` accepts any request that passes this HMAC check and dispatches to the app-registered handler using `request.shop` taken straight from the header: [4](#0-3) 

**Binding that should hold:** `shop_bound_by_hmac == shop_acted_upon`.
**What actually holds:** `hmac` only proves `body_bytes_signed == body_bytes_received`; `shop_acted_upon` is an independent, unauthenticated header value. So the equality the code implicitly relies on (that a valid HMAC implies the claimed shop is authentic) does not hold.

**Attack sequence:**
1. Attacker owns/controls a legitimate Shopify store, Shop A, which is a genuine merchant/tenant of the target app.
2. Shopify delivers a real webhook to the target app for Shop A: `raw_body = B`, header `shopify-shop-domain: shop-a.myshopify.com`, and a valid `shopify-hmac-sha256` computed over `B` with the app's `api_secret_key`. The attacker captures this `(B, hmac)` pair (e.g., by proxying their own store's webhook traffic, which they legitimately receive/can trigger since it's their own shop).
3. Attacker replays a POST to the app's webhook endpoint with the **same** `raw_body = B` and **same** `hmac`, but changes `shopify-shop-domain` to `shop-victim.myshopify.com` (a different tenant of the same app).
4. `HmacValidator.validate` succeeds because it only checks `B` against `hmac` — the shop header is irrelevant to that check.
5. `Registry.process` builds `WebhookMetadata.new(shop: "shop-victim.myshopify.com", body: parsed(B), topic: ..., ...)` and invokes the app's handler as if this event legitimately originated from the victim shop.

Before the attack: `shop_bound_by_hmac` is undefined/non-existent (HMAC never encodes shop); the app's trust model implicitly assumes the header is Shopify-authenticated. After the attack: the app processes attacker-controlled webhook content (body content the attacker fully controls, since it's their own store's data/topic) under the identity of a victim shop, breaking the tenant isolation boundary the app relies on webhook handlers to enforce (e.g., app/uninstalled, customers/redact, shop/update, billing-related topics keyed off `shop`).

### Impact Explanation
This is a cross-tenant boundary break: the app's own gem-provided verification (`Webhooks::Registry.process` + `HmacValidator`) gives host applications a false guarantee that a validated webhook's `shop`/topic/body triple is authentic for that shop. Because `shop` (and topic/webhook_id/api_version) are excluded from the signed payload, any actor who can obtain one valid `(body, hmac)` pair for any shop (trivially, their own) can relabel it for an arbitrary victim shop of the same app. Depending on how the host app's webhook handlers act on `data.shop` (e.g., un-installing the victim's app registration, redacting/deleting victim customer data, mutating billing/subscription state, or triggering re-registration flows), this can lead to cross-tenant data corruption or unauthorized actions against a shop the attacker does not control — meeting the "cross-tenant access" Critical impact bar.

### Likelihood Explanation
High. Any user who is a legitimate merchant of the target app (i.e., anyone who installs the app on any Shopify store) can obtain a valid `(raw_body, hmac)` pair from their own genuine webhook deliveries — no access to the app's `api_secret_key`, access tokens, or victim credentials is required. Only network access to the app's public webhook endpoint and the ability to modify one HTTP header is needed.

### Recommendation
Include the identity-relevant headers (`shop`, `topic`, `api_version`, `webhook_id`) in the HMAC-signable payload, or otherwise cryptographically bind them (e.g., derive/verify shop identity from a value that Shopify itself signs, not a bare header echoed by the transport). At minimum, `Utils::HmacValidator`/`Webhooks::Request` should not allow the `shop` used for dispatch to be independent of what the HMAC actually authenticates. Until fixed, document to gem consumers that `data.shop` in webhook handlers must not be trusted as Shopify-authenticated on its own.

### Proof of Concept
```ruby
require "shopify_api"
require "openssl"
require "base64"

ShopifyAPI::Context.setup(
  api_key: "key", api_secret_key: "shhh", host: "app.example.com",
  scope: [], is_embedded: false, is_private: false, api_version: "2024-01",
)

body = '{"id":123,"note":"legit payload from attacker-owned store"}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, body)

# Step 1: Attacker's own shop legitimately received this (body, hmac) pair from Shopify.

# Step 2: Attacker replays it, swapping only the shop-domain header to the victim's shop.
forged_headers = {
  "x-shopify-topic" => "customers/redact",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac), # unchanged, still valid for `body`
  "x-shopify-shop-domain" => "shop-victim.myshopify.com", # spoofed
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: forged_headers)

# HMAC validation passes because it only checks `body` vs `hmac`, ignoring shop-domain.
ShopifyAPI::Webhooks::Registry.process(request)
# => handler invoked with WebhookMetadata(shop: "shop-victim.myshopify.com", topic: "customers/redact", body: parsed(body))
```
Note: full verification of every webhook handler consequence in a real host application was not possible from this gem's code alone (handler behavior is app-defined), but the root cause — the HMAC not covering `shop`/`topic`/`webhook_id` — is proven directly at [5](#0-4)  and [3](#0-2) .
