### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable signature over the raw request body only, while the `shop-domain` header (and `topic`, `webhook-id`, `api-version` headers) are read directly from unauthenticated HTTP headers and passed straight through to the webhook handler. Because Shopify signs webhooks with a single `client_secret` shared across every shop that has the app installed, any merchant who has installed the app (an "unprivileged" actor from the perspective of other tenants) can capture a legitimate, validly-signed webhook delivered to their own shop and replay it to the app's webhook endpoint with the `x-shopify-shop-domain` header rewritten to a victim shop's domain. The HMAC check still passes because it never covers that header, so the request is processed as if it genuinely originated from the victim shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no binding to anything cryptographically verified: [2](#0-1) 

`Utils::HmacValidator.validate` only recomputes and compares the signature of `to_signable_string` (the body): [3](#0-2) 

`Registry.process` accepts any request whose body/HMAC pair validates, and then forwards the unauthenticated `request.shop` value straight into the metadata handed to the app's handler, which host applications use to identify the tenant the event belongs to: [4](#0-3) 

The identity binding that should hold is: `shop authenticated by HMAC == shop the handler acts on`. Because the `shop-domain` header is excluded from the signed bytes, this equality does not hold — the bytes verified (raw body) are not the bytes/headers actually used to route/attribute the event (headers, particularly `shop`). This is directly analogous to the reported bug class: a field that is acted upon (the shop identity used for tenant routing) is not covered by the authentication mechanism (HMAC) that is supposed to bind it.

Since Shopify apps use one `client_secret`/signing key across all shop installations, any shop that installs the app can obtain a validly-signed webhook body+HMAC (Shopify sends it to them for their own store's events) and reuse it against the same endpoint while spoofing a different shop's domain in the header — a classic cross-tenant confusion enabled purely by this gem's verification logic, without needing the victim's or the app's secret.

### Impact Explanation
This breaks the shop-authentication boundary that `HmacValidator`/`Webhooks::Registry` are meant to enforce: an attacker who is merely a legitimate installer of the app on their own store can make the app process events attributed to an arbitrary other shop. Any handler logic that uses `WebhookMetadata#shop` to look up sessions, persist data, or trigger actions for "that shop" would act on attacker-supplied data under a spoofed tenant identity — a cross-tenant access impact.

### Likelihood Explanation
Any merchant who installs the app can generate a genuine, validly HMAC-signed webhook (Shopify sends them for their own shop's events) and needs only to replay it to the app's public webhook endpoint with a modified `shop-domain` header — no access to `api_secret_key`, tokens, or victim credentials is required. This requires only normal, low-privilege use of the app (installing it on one's own store), matching the "unprivileged internet user" threat model in scope.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `webhook-id`) header values in the signable bytes verified by `HmacValidator`, or otherwise cryptographically bind them to the signed body (e.g., re-deriving/confirming the shop from a value that Shopify itself signs, or requiring the caller to supply/validate the shop out-of-band per registered webhook subscription) so the header used for tenant routing cannot be altered independently of the verified signature.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com`. Attacker triggers a real Shopify event (e.g., updates a product) so Shopify delivers a webhook to the app's endpoint with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC of raw body>`, and body `B`.
2. Attacker captures this raw body `B` and its valid HMAC (they control the receiving server / can intercept their own traffic).
3. Attacker resends a request to the same webhook endpoint with the identical body `B` and HMAC header, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks the HMAC of `B` — this still passes because the shop header was never part of the signed bytes: [5](#0-4) 
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and `body` from the attacker's own store's event, causing the host application to process attacker-controlled data as if it belonged to `victim-shop.myshopify.com`.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
