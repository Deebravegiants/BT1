### Title
Router/proxy forwarding lets any external chain forge a "hyperbridge-originated" request and drain the outbound-request relayer-reward treasury - (File: `parachain/runtimes/nexus/src/ismp.rs`)

### Summary
`ProxyModule::on_accept` on the Nexus/Gargantua hub re-dispatches any incoming request whose `dest` is not the local chain by calling `Ismp::dispatch_request` directly, preserving the attacker-supplied `from` field unmodified. The reward-claim logic (`process_outbound_request_delivery_claim`) authenticates "hyperbridge-originated" requests solely by `request.source == host_state_machine()` plus `request.from` being on the reward allowlist — both of which are satisfied by this forwarded, attacker-controlled request, letting anyone forge a payout-eligible system message and drain the treasury.

### Finding Description
Nexus/Gargantua is configured as an ISMP router (`host.is_router()` true), so the core handler explicitly skips the destination check for it: [1](#0-0) 
This means any external, unprivileged chain can dispatch a `PostRequest` with an arbitrary `dest` (not Nexus) and have Nexus accept it as an incoming message, routed to a single global `ProxyModule`: [2](#0-1) 

Inside `ProxyModule::on_accept`, when `request.dest != HostStateMachine::get()`, the request is simply re-dispatched via the same `IsmpDispatcher` used by hyperbridge's own system pallets: [3](#0-2) 
`pallet_ismp`'s dispatcher stamps `source = host_state_machine()` and assigns a fresh nonce, but `from`, `to`, `dest`, and `body` come straight from the attacker-controlled inbound request — nothing re-validates that `from` actually corresponds to a genuine local system-pallet caller (host-executive, intents-coprocessor, token-governor, relayer). This is the same low-level dispatcher genuine system pallets use to originate their (currently zero-fee) messages, as documented in the incentivization design doc: [4](#0-3) 

The reward-claim pipeline treats any request satisfying two checks as legitimately "hyperbridge-originated": `request.source == host.host_state_machine()` and a non-zero reward configured for `request.from`: [5](#0-4) 
Neither check distinguishes a request dispatched by a real system pallet from one that merely passed through the router-forward branch of `ProxyModule::on_accept`. Since `from` is attacker-chosen on the original (unprivileged) source chain, an attacker can set it to match any allowlisted system `module_id` (e.g. whichever module governance has configured a non-zero `OutboundRequestDeliveryReward` for, analogous to the documented `b"ismp-ast"` example): [6](#0-5) 

This is structurally the same bug class as the OpenClaw advisory: a "spawn"/forward operation (`ProxyModule`'s cross-chain re-dispatch) does not enforce that the resulting child context (the re-dispatched request treated as hyperbridge-system-originated for reward purposes) inherits the trust level of its true origin (an unprivileged, "sandboxed" external chain), letting an untrusted caller escalate into the privileged, reward-eligible class.

### Impact Explanation
An attacker can repeatedly forge fake "system-originated" requests, deliver them to a destination they control, and claim `OutboundRequestDeliveryReward` payouts from the treasury (`hb/trsry` PalletId account) via `claim_outbound_request_delivery_reward`, without ever having triggered a genuine host-executive/intents-coprocessor/token-governor/relayer-withdrawal action. This is a direct, repeatable theft of protocol treasury funds (concrete theft of funds), reachable from a single unprivileged cross-chain dispatch plus a self-submitted relayer proof.

### Likelihood Explanation
High reachability: dispatching an ISMP `PostRequest` from any connected chain is a permissionless, standard primitive available to any dapp/contract; the attacker fully controls `from`, `dest`, and `to`. The only prerequisite is that governance has configured a non-zero `OutboundRequestDeliveryReward` for at least one `module_id` (which is the entire purpose of the feature, per `docs/outbound-request-incentivization.md`), and that the attacker can act as (or collude with) the delivering relayer to control the `RequestReceipts[commitment]` proof used for `signature`/`delivered_by` attribution — trivial since the attacker controls the destination-side delivery when the destination `to` target is their own contract/module.

### Recommendation
Do not treat router-forwarded/proxied requests as reward-eligible "hyperbridge-originated" messages. Either:
- Tag requests dispatched via the `ProxyModule` forward branch (`Ismp::dispatch_request` call in `on_accept` when `request.dest != HostStateMachine::get()`) with a reserved/unspoofable marker distinct from genuine local dispatcher calls, and have `process_outbound_request_delivery_claim` reject anything carrying that marker; or
- Restrict the reward allowlist keys (`OutboundRequestDeliveryReward`) to module ids that can only originate from privileged, non-forwardable internal pallet calls (e.g. require an additional internal-only provenance field set exclusively by `pallet_ismp::dispatcher` call sites invoked directly by system pallets, not reachable from `ProxyModule`'s forwarding path).

### Proof of Concept
1. Attacker deploys a contract/pallet on any chain connected to Nexus.
2. It dispatches an ISMP `PostRequest` with `dest = <some other connected chain>`, `from = <bytes matching an allowlisted system module_id, e.g. host-executive's module id>`, `to = <attacker's own contract/module on the destination>`, arbitrary `body`.
3. Nexus accepts the incoming message (bypassing the destination check because `host.is_router()` is true — [1](#0-0) ), routes it to `ProxyModule::on_accept`, which detects `request.dest != HostStateMachine::get()` and forwards it via `Ismp::dispatch_request` — [3](#0-2) , producing a new commitment recorded in `RequestCommitments` with `source = Nexus` and the spoofed `from`.
4. Attacker (as their own relayer) delivers the request to the destination, ensuring `RequestReceipts[commitment]` records their own address/signature.
5. Attacker submits `claim_outbound_request_delivery_reward` with the forwarded `request`; `process_outbound_request_delivery_claim` passes the source check, allowlist check (spoofed `from`), and state-proof/signature checks — [7](#0-6)  — and pays out the configured reward from the treasury to the attacker.

Note: I was unable to verify (due to running out of tool iterations) the exact production `module_id` values that currently have non-zero `OutboundRequestDeliveryReward` configured on mainnet, nor whether any additional off-chain/on-chain filter beyond what's shown here further restricts this path; this should be confirmed against the live `OutboundRequestDeliveryReward` storage before treating this as exploitable in the current deployed configuration.

**File:** docs/outbound-request-incentivization.md (L9-11)
```markdown
A regular cross-chain message that flows *through* hyperbridge has a fee attached at origin (the source chain transfers `fee.payer → RELAYER_FEE_ACCOUNT` and records `RequestPayments[commitment]` in pallet-hyperbridge's child trie). When a relayer delivers and the destination receipt lands back on hyperbridge, the existing `accumulate_fees` flow credits that fee to the relayer. That whole pipeline assumes a *user* paid at origin.

But hyperbridge itself originates requests too: host parameter propagation, host-executive updates, intents-coprocessor responses, token-governor messages, the relayer pallet's withdrawal request. Today these all dispatch with `FeeMetadata { payer: [0u8; 32].into(), fee: Default::default() }` (see `modules/pallets/host-executive/src/lib.rs:228`, `modules/pallets/intents-coprocessor/src/lib.rs:486`, `modules/pallets/relayer/src/lib.rs:638`, and `modules/pallets/token-governor/src/impls.rs`). Zero fee, zero payer. So relayers have no economic reason to pick them up, and the only thing that keeps them flowing today is altruism.
```

```markdown

Not every pallet on hyperbridge that dispatches a request is in scope. `pallet_ismp::child_trie::RequestCommitments` ends up holding commitments for every successful dispatch via `IsmpDispatcher`, which includes both the system messages we want to incentivize (host-executive, intents-coprocessor, token-governor, the relayer pallet's withdrawal path, future modules like bandwidth) and any other pallet that ends up dispatching from hyperbridge. The reward storage is therefore keyed by `source_module_id` and only modules with a non-zero reward are eligible. The `module_id` is the `from` field on the `PostRequest`, which each pallet sets to its unique module identifier. A module with zero reward is treated as not on the allowlist and rejected before any state proof verification runs.
```
