### Title
Webhook `shop-domain` header trusted for tenant routing while HMAC only covers the request body - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` exposes `shop` (from the `shopify-shop-domain`/`x-shopify-shop-domain` header) as the tenant identity handed to app webhook handlers, but the HMAC signature validated by `Registry.process` only covers the raw request body, not the shop header. This breaks the intended identity binding: `hmac == HMAC(secret, body)` should also imply `shop == the shop that produced body`, but nothing in the gem enforces that equality.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from an HTTP header with no cryptographic tie to the body or its HMAC: [2](#0-1) 

`Registry.process` validates the HMAC over exactly that signable string, then immediately forwards the untethered `request.shop` value into the handler's data as the tenant identifier: [3](#0-2) 

Because the app's webhook secret (`Context.api_secret_key`) is shared across every shop that installs the app (it is not per-shop), any merchant who installs the app can obtain a genuinely-signed webhook: a valid `(raw_body, hmac)` pair produced by Shopify using the app's real secret. Since `hmac` is a function of `body` alone, that same `(raw_body, hmac)` pair remains valid no matter what `shop-domain` header value is sent alongside it. An attacker-merchant can therefore replay their own legitimately-signed webhook body while substituting an arbitrary victim shop domain in the header, and `HmacValidator.validate` at `lib/shopify_api/utils/hmac_validator.rb:12-22` will still return `true` because it never inspects `shop`.

This is analogous to the report's root cause: a value (the ADL factor / here, `shop`) is trusted for a security-relevant decision downstream of a check (`withdrawUsdTokenFromMarket` / here, tenant routing in the handler) without accounting for what the earlier verification step (`getAdjustedProfitForMarketId` / here, HMAC validation) actually covers.

### Impact Explanation
This crosses the "shop authenticated versus shop bound to the verified bytes" boundary called out in scope. A handler that uses `WebhookMetadata#shop` to select which tenant's records to create/update/delete (the documented, expected usage pattern for webhook handlers built on this gem) can be made to attribute attacker-controlled, HMAC-verified payload content to a victim shop, i.e., cross-tenant data injection/confusion — the app cannot distinguish "genuine data for shop X" from "attacker's own data falsely labeled as shop X," despite the HMAC check having passed. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Requires only that the attacker be a legitimate, unprivileged merchant able to install the target app on their own store (a routine, low-privilege action) and capture one webhook delivery to their own endpoint/log — no leaked credentials, no access to `api_secret_key`, and no TLS interception are needed, since the attacker legitimately receives the signed payload for their own shop.

### Recommendation
Bind `shop` (and other routing-relevant headers such as `topic`/`webhook_id`) into the signed material, or otherwise cross-check the header-supplied `shop` against a value derived from data the app already trusts for that specific webhook delivery (e.g., validate that the `shop-domain` header matches a shop for which the app has an active, previously-established session/installation, and reject/flag mismatches) before passing it to `WebhookHandler#handle`.

### Proof of Concept
1. App developer's app is installed by attacker-controlled shop `attacker.myshopify.com`.
2. Shopify sends a genuine webhook to the app: body `B`, header `shopify-hmac-sha256: HMAC(secret, B)`, header `shopify-shop-domain: attacker.myshopify.com`.
3. Attacker replays the identical `B` and `hmac` to the app's webhook endpoint, but sets `shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses this into `shop = "victim.myshopify.com"`, `to_signable_string = B` [4](#0-3) .
5. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` and compares to the supplied hmac — it matches, so validation succeeds [5](#0-4) .
6. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: <attacker-controlled B's JSON>, ...)` [6](#0-5) , causing the app to process attacker-supplied data under the victim shop's identity.
