### Title
Missing domain-allowlist validation on JWT `dest` claim before it is used as the OAuth token-exchange request host — (File: lib/shopify_api/auth/token_exchange.rb)

### Summary
`TokenExchange.exchange_token` takes the `dest` claim straight out of `JwtPayload` (`dest_shop = jwt_payload.shop`) and uses it, unsanitized, both as the `Session#shop` used to build the HTTP request host (`Clients::HttpClient` sets `@base_uri = "https://#{session.shop}"`) and as the value later stored as the session's `shop` attribute — all while the request body carries `client_secret` in plaintext. Every other place in the library that turns caller/token-derived shop strings into a request host (`ClientCredentials.client_credentials`, `TokenExchange.migrate_to_expiring_token`) calls `Utils::ShopValidator.sanitize!` first, which enforces that the host is one of `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`) or an explicitly configured `myshopify_domain`. `exchange_token` skips this check entirely.

### Finding Description
The equality this breaks is: *host that receives `client_secret`* == *a Shopify-domain string validated against `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`*. `JwtPayload#shop` only strips `"https://"` from the raw `dest` claim string (`@dest.gsub("https://", "")`) — it does not check the value is even a well-formed hostname, let alone that it resolves under a trusted Shopify TLD/suffix. That string is fed directly to `Auth::Session.new(shop: dest_shop)` and then to `Clients::HttpClient.new(session: shop_session, ...)`, whose constructor builds `@base_uri = "https://#{api_host || session.shop}"` with no further validation. The `client_id` and `client_secret` are then POSTed to that URI.

While `JwtPayload` does verify the token's HMAC signature against `Context.api_secret_key` and checks `aud == Context.api_key`, it never validates that `dest` is a legitimate Shopify-controlled host. If a token is ever accepted whose `dest` claim doesn't correspond to a real Shopify shop domain (e.g., a token signed by/for a differently configured/misconfigured issuer, a replayed/crafted token in an environment where key material is shared, or any future relaxation of validation), `exchange_token` will happily send `client_id`/`client_secret` to whatever host string is in `dest`. This is precisely the same identity-binding class the Shopify maintainers themselves flagged as needing a fix in `ShopValidator` (per the changelog entry for PR #1443, which added the validator and changed token-exchange behavior to read the shop "from the session token's `dest` claim" instead of caller input) — but the fix was only wired into `migrate_to_expiring_token` and `client_credentials`, not into `exchange_token`, which is the primary/most-used token-exchange path. ### Impact Explanation
This maps to the report's bug class ("field acted on but not covered by/validated against the trust boundary") applied to SSRF with the app's credentials: the request host used to deliver `client_id`/`client_secret` is not validated against the same allowlist that other, parallel code paths in this exact file/module enforce. If reachable with an untrusted `dest`, this is a High-severity SSRF carrying the app's `client_secret` to an attacker-influenced host.

### Likelihood Explanation
Likelihood is limited by the fact that `dest` is inside an HMAC-signed JWT keyed by `Context.api_secret_key`, so under correct configuration only Shopify (or someone possessing the app's secret) can set `dest`. I could not verify within this gem's code whether Shopify's token issuance can ever produce a `dest` outside `ShopValidator::TRUSTED_SHOPIFY_DOMAINS` (e.g., non-canonical dev/spin domains), nor could I find any test exercising `exchange_token` with a malicious/non-trusted `dest` to confirm exploitability end-to-end. This is an inconsistency/defense-in-depth gap versus the sibling methods rather than a proven, directly triggerable exploit from an unauthenticated internet user, given the current information available.

### Recommendation
Route `dest_shop` through `Utils::ShopValidator.sanitize!` in `TokenExchange.exchange_token` before constructing `shop_session`/`HttpClient`, mirroring `migrate_to_expiring_token` and `client_credentials`, so the request host is always confirmed to be a trusted Shopify domain before the app's `client_secret` is sent to it.

### Proof of Concept
Not able to construct a concrete forged-token PoC from this gem's code alone, because `dest` is protected by HMAC verification in `JwtPayload#initialize` using `Context.api_secret_key`. The finding is a structural/defense-in-depth gap (missing `ShopValidator.sanitize!` call on the `exchange_token` path that exists on sibling paths) rather than a demonstrated exploit; verifying real-world reachability would require confirming under what conditions Shopify (or a compatible issuer) can be made to sign a token with a non-trusted `dest`, which is outside this repository's scope.
