### Title
Orb-Core Fraud/Liveness Enforcement Is a No-Op, Making Signup Legitimacy Fully Dependent on an Unverified, Unmonitored Backend - (File: `src/plans/mod.rs`, `src/plans/fraud_check.rs`)

### Summary
The `detect_fraud` step in the signup pipeline, which is supposed to be the on-device fraud/liveness enforcement checkpoint, is hard-coded to always return `false` ("no fraud"), with an explicit comment that all fraud checks have been deleted. Combined with `FraudChecks::run` always returning an empty `Report {}`, the orb itself never independently determines whether a signup is fraudulent — that determination is delegated entirely to the off-chain/off-device backend (`signup_poll` / `signup_post` responses), which the orb blindly trusts without any local corroboration or audit trail. This is the same class of risk flagged in the external report: a critical trust decision (fund movement / balance update in the report; signup fraud/legitimacy determination here) is made entirely by an opaque backend with no on-device verification or monitoring.

### Finding Description
`MasterPlan::detect_fraud` in [1](#0-0)  is invoked from the signup flow to decide `fraud_detected`, but its body only checks whether the pipeline succeeded and otherwise unconditionally returns `Ok(false)`:
```
// FOSS: WE HAVE DELETED ALL FRAUD CHECKS
Ok(false)
```
This value feeds directly into `signup_reason` selection in [2](#0-1) , meaning the orb can never classify a signup as `SignupReason::Fraud` on its own.

The underlying `FraudChecks` engine in `src/plans/fraud_check.rs` mirrors this: `N_FRAUD_CHECKS` is `0`, `BackendConfig` and `Report` are empty structs, and `FraudChecks::run` always returns `Report {}` [3](#0-2) [4](#0-3) . `Report::fraud_detected` and `fraud_detected_with_config` operate over a zero-length array of checks, so they are permanently vacuously `false` [5](#0-4) .

The comment on `SignupReason::Fraud` explicitly separates the orb's own detection from backend detection: "Signup was detected as a fraud attempt at the orb (not to be confused with the backend fraud checks)" [6](#0-5) . Because the orb-side path is disabled, the *only* fraud signal is what the backend chooses to report in the polling response — a case explicitly acknowledged in the enrollment plan's handling of `success: false` polls, which lists "Backend detected fraud" as one of several opaque failure causes the orb cannot distinguish or verify locally [7](#0-6) .

This is a direct analog of the reported issue: just as the Ithaca system relies on an off-chain Java backend to track settlement/fund movement without on-chain enforcement, orb-core relies entirely on the signup backend to determine fraud/legitimacy of a biometric signup, with the on-device enforcement layer stripped out and no attestation of *why* the backend accepted or rejected a signup.

### Impact Explanation
Fraud and liveness enforcement is one of the core unprivileged-user trust boundaries for the Orb's signup process. With on-device fraud checks permanently disabled, a compromised, misconfigured, or malicious backend response can cause the orb to treat any signup as legitimate (`SignupReason::Normal`), or the true rejection reason (fraud vs. duplicate vs. internal error) is entirely opaque to the device and to any local audit/log — matching the report's concern about "fund movement" (here, signup/credential issuance) being controllable by a backend admin "without proper monitoring in place." This centralizes the fraud-prevention guarantee entirely off-device with no attestation of correctness in the client, undermining the client-facing claim that the orb performs local fraud detection.

### Likelihood Explanation
This is not a theoretical or test-only gap — `detect_fraud` is called unconditionally in the normal signup path (`do_signup`) whenever fraud checks are not explicitly skipped, and the empty `Report`/`FraudChecks` are the actual, shipped implementation (not behind a test-only feature flag). Every real signup that reaches the pipeline stage exercises this no-op path.

### Recommendation
- Disclose in user/operator-facing documentation that fraud/liveness determination is currently performed solely by the backend, with no independent on-device enforcement, and describe the backend's fraud-detection process and its logging/attestation guarantees.
- Where on-device fraud checks are intentionally stripped for the FOSS build, ensure the production (non-FOSS) build restores a functioning local `FraudChecks` implementation, and require the backend to return a verifiable/attestable rejection reason for `signup_poll` failures, rather than an opaque `success: false`.
- Add explicit local auditing/telemetry that flags when a signup relies entirely on unverified backend fraud judgment, so this centralization is monitorable and disclosed rather than silent.

### Proof of Concept
1. Trigger a signup with a valid biometric capture (`pipeline.is_some()`).
2. Observe `detect_fraud` in [8](#0-7)  returns `Ok(false)` unconditionally, regardless of capture content.
3. Confirm `FraudChecks::run` in [9](#0-8)  always returns an empty `Report{}`, and `Report::fraud_detected()` evaluates over `N_FRAUD_CHECKS = 0` entries, i.e., always `false` [10](#0-9) .
4. `signup_reason` is therefore always `SignupReason::Normal` or `SignupReason::Failure`, never orb-determined `Fraud` [11](#0-10) .
5. The only remaining fraud signal is the backend's `signup_poll::Response { success: false, ... }`, which the orb cannot distinguish from other failure causes and must simply trust [7](#0-6) .

impl Report {
    const DATADOG_TAGS: [&'static str; N_FRAUD_CHECKS] = [];

    fn fraud_checks(&self) -> [Option<bool>; N_FRAUD_CHECKS] {
        []
    }

    /// If fraud data are missing, we assume fraud is detected.
    fn fraud_checks_strict(&self) -> [bool; N_FRAUD_CHECKS] {
        self.fraud_checks().map(|v| v.unwrap_or(true))
    }

    fn enabled_checks_from_config(_config: &BackendConfig) -> [bool; N_FRAUD_CHECKS] {
        []
    }

    fn feedback_messages() -> [Option<PipelineFailureFeedbackMessage>; N_FRAUD_CHECKS] {
        []
    }

    /// Get the || result of all fraud checks, but under the Orb configuration.
    /// The end result might be different from the || of all fraud booleans as
    /// we might decide to not block a signup even if it's fraudulent.
    #[must_use]
    pub fn fraud_detected_with_config(
        &self,
        config: &BackendConfig,
    ) -> (bool, Vec<PipelineFailureFeedbackMessage>) {
        let enabled_checks = Self::enabled_checks_from_config(config);
        let fraud_results = self.fraud_checks_strict();
        let feedback_msgs = Self::feedback_messages();

        let feedback: Vec<PipelineFailureFeedbackMessage> = enabled_checks
            .iter()
            .zip(fraud_results.iter())
            .zip(feedback_msgs.iter())
            .filter_map(
                |((&enabled, &result), feedback_msg)| {
                    if enabled && result { feedback_msg.clone() } else { None }
                },
            )
            .collect();

        (!feedback.is_empty(), feedback)
    }

    /// If any fraud check fails or is missing data, fraud is reported.
    #[must_use]
    pub fn fraud_detected(&self) -> bool {
        self.fraud_checks_strict().iter().any(|&v| v)
    }
