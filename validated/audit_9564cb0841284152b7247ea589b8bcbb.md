## Title
`HyperApp.dispatchWithFeeToken` allows arbitrary third parties to drain any approved `payer`'s fee-token allowance — ([File: sdk/packages/core/contracts/apps/HyperApp.sol])

### Summary
`HyperApp.dispatchWithFeeToken` (used by every ISMP-dispatching application built on the Hyperbridge SDK) pulls fee tokens from a `payer` address taken directly from the caller-supplied `DispatchPost`/`DispatchGet` struct, with no check that `payer == msg.sender` or that `msg.sender` is otherwise authorized to spend on `payer`'s behalf. This is the exact bug class from the referenced report: any account that has approved a `HyperApp`-derived contract to spend its fee tokens can have that allowance consumed by an unrelated, uninvited caller.

### Finding Description
`dispatchWithFeeToken` is the officially documented helper for fee-token-based dispatch: [1](#0-0) [2](#0-1) 

Both variants perform:
```solidity
if (request.payer != address(this)) IERC20(feeToken).safeTransferFrom(request.payer, address(this), request.fee);
```
with no verification that `msg.sender` is `request.payer` or has been delegated by `payer`. The `payer` field is a plain struct member, populated by whatever the calling application chooses to put there — it is not tied to `msg.sender` by the framework.

Hyperbridge's own developer documentation instructs app authors to expose `payer` as a directly caller-supplied function parameter: [3](#0-2) 

This is structurally identical to `PerpDepository.rebalance`'s `account` parameter: a user grants an ERC-20 approval to a contract expecting only *they* (or the contract itself) will trigger a pull, but the actual pull is gated on a struct field an unrelated caller controls. Any dApp built on `HyperApp` that follows the documented pattern (passing a caller-supplied `payer` into `dispatchWithFeeToken`) inherits this vulnerability directly from the shared base contract, and once a user approves the fee token to that app (a normal, expected action for regular dApp use), anyone can front-run/replay a call that dispatches a message with `payer` set to that victim's address, draining their fee-token allowance to fund dispatch fees for messages the caller wants sent — with no consent or benefit to the victim.

Note that the actual shipped Hyperbridge apps in this repo (`HyperFungibleToken`, `WrappedHyperFungibleToken`, `IntentGatewayV2`'s cancel-from-source path, `BandwidthManager`) all correctly hard-code `payer: msg.sender` (or `address(this)` after already pulling funds themselves): [4](#0-3) [5](#0-4) 

However, the vulnerability is in the reusable `HyperApp` base contract and its documented usage pattern, not in any one shipped app — any third-party or future Hyperbridge app that follows the documented `payer` parameter pattern (as explicitly shown in the docs) is directly exposed.

### Impact Explanation
Any account that approves fee tokens to a `HyperApp`-derived contract (standard practice for repeat dispatchers, e.g. to avoid re-approving each call) can have that allowance drained by an arbitrary, unrelated caller who dispatches messages with `payer` set to the victim's address. This constitutes unauthorized transfer of the victim's tokens (theft of approved funds) with no compensating benefit to the victim, matching a High-severity "any account" fund-draining bug class. It is Medium/High rather than a full drain since it's bounded by the current allowance and per-dispatch fee amount, but it can be triggered repeatedly.

### Likelihood Explanation
Likelihood is amplified by the fact that Hyperbridge's own documentation instructs developers to implement the vulnerable pattern (`payer` as a caller-supplied parameter, forwarded verbatim to `dispatchWithFeeToken`), so any app following the docs is affected by default. Exploitation requires only that a target has left an active fee-token approval to the vulnerable app — a common condition for regular users of message-dispatching dApps.

### Recommendation
In `HyperApp.dispatchWithFeeToken`, require `request.payer == msg.sender` (or `address(this)`) before pulling funds, or explicitly check `IERC20(feeToken).allowance(payer, msg.sender)`/an authorization mapping if delegated payment is intended. Update the developer documentation examples to stop demonstrating a caller-supplied `payer` parameter being forwarded directly into `dispatchWithFeeToken`.

### Proof of Concept
1. Victim `V` approves fee tokens to app contract `A` (a `HyperApp` following the documented pattern, e.g. `readRemoteState(dest, keys, payer)` where `payer` is caller-supplied).
2. Attacker calls `A.readRemoteState(dest, keys, V)`.
3. Inside, `A` builds a `DispatchGet` with `payer: V` and calls `dispatchWithFeeToken`.
4. `dispatchWithFeeToken` executes `IERC20(feeToken).safeTransferFrom(V, address(this), fee)` since `V != address(this)`, pulling `V`'s tokens with no signature or authorization from `V`, funding a dispatch the attacker initiated for their own purposes.

    function dispatchWithFeeToken(DispatchPost memory request) internal returns (bytes32) {
        address hostAddr = host();
        address feeToken = IDispatcher(hostAddr).feeToken();
        if (request.payer != address(this)) IERC20(feeToken).safeTransferFrom(request.payer, address(this), request.fee);
        IERC20(feeToken).forceApprove(hostAddr, request.fee);
        return IDispatcher(hostAddr).dispatch(request);
    }
