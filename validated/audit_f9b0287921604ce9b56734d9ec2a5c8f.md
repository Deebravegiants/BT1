## Title
Fee-on-transfer / deflationary tokens over-credit escrow in `IntentGatewayV2.placeOrder`, causing under-collateralized escrow and stuck funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron deployment of `IntentGatewayV2.placeOrder` credits escrow with the user-declared (fee-adjusted only for protocol fee) input amount rather than the amount actually received by the contract. Any ERC20 token that charges a fee on transfer, rebases, or otherwise delivers less than the nominal `amount` will cause the on-chain escrow ledger `_orders[commitment][token]` to exceed the contract's real token balance for that token.

### Finding Description
In the non-predispatch branch of `placeOrder`, tokens are pulled via `safeTransferFrom` and the escrow mapping is incremented by `reducedInputs[i].amount` (the requested amount minus protocol fee) with no verification that this amount was actually received: [1](#0-0) 

This is functionally identical to the reported `Cooler.request()` pattern, where `collateral.transferFrom(msg.sender, address(this), collateralFor(...))` is trusted to deliver the full nominal amount, and a later function (`defaulted`) that relies on the recorded/expected amount reverts or drains real balance improperly because the actual token balance is short.

The predispatch branch is partially guarded — it checks `IERC20(token).balanceOf(dispatcher)` before sweeping — but the final "sweep back to gateway" transfer (`transferCalls[i]` using `IERC20.transfer` from dispatcher to the gateway) is not verified with a before/after balance check on the gateway itself, so a second fee-on-transfer deduction on that hop is also silently ignored: [2](#0-1) 

This is a genuine regression relative to the canonical EVM `IntentGatewayV2.sol`, which was hardened specifically against this class of bug: it snapshots balances before/after each transfer and mutates `order.inputs[i].amount` to the actually-received value before computing the commitment and crediting escrow: [3](#0-2) [4](#0-3) 

The presence of dedicated fee-on-transfer regression tests for the main EVM gateway confirms this was a known, intentionally-fixed issue there, but the fix was not carried over to the Tron contract: [5](#0-4) 

### Impact Explanation
Once escrow is over-credited, `_withdraw` will decrement `_orders[commitment][token]` and attempt `IERC20(token).safeTransfer(beneficiary, amount)` for the recorded (inflated) amount: [6](#0-5) 

For any given token, the sum of all escrowed balances recorded by the ledger can exceed the contract's real balance. This has two consequences reachable by ordinary users/solvers with a single transaction:
1. **Legitimate solvers/users lose funds**: after a solver fills a cross-chain order and delivers real output tokens on the destination chain, the corresponding `RedeemEscrow` settlement on the source chain can revert (insufficient real balance) or, if it succeeds by draining tokens meant for other orders, leaves other legitimate order withdrawals under-collateralized and permanently unable to complete — a direct loss/freezing of funds for other users of the same token.
2. Because Tron is a first-class deployment target of the same `IntentGatewayV2` protocol (mirrored ABI/logic), this constitutes unauthorized/incorrect accounting reachable from a single unprivileged `placeOrder` call.

### Likelihood Explanation
Any user can call `placeOrder` with an arbitrary ERC20 `token` address of their choosing — there is no allow-list or balance verification. Fee-on-transfer, deflationary/rebasing, and similar tokens are common on Tron/EVM-compatible chains, so triggering the mismatch requires no special privileges and can be done by any single order placer with an unmodified transfer-fee token.

### Recommendation
Apply the same fix used in the canonical `evm/src/apps/IntentGatewayV2.sol`: measure the gateway's actual token balance before and after each `transferFrom`/sweep, and credit escrow (and the commitment hash) with the actually-received amount instead of the nominal requested amount, for both the direct-transfer branch and the predispatch/dispatcher-sweep branch.

### Proof of Concept
1. Deploy a fee-on-transfer ERC20 (e.g., 1% fee) on Tron and mint balance to `user`.
2. `user` approves `IntentGatewayV2` and calls `placeOrder` with `inputs[0].amount = 1000e18` for that token (no predispatch).
3. `safeTransferFrom` delivers only `990e18` to the gateway, but `_orders[commitment][token]` is credited with `reducedInputs[0].amount` derived from `1000e18` (minus protocol fee only), i.e. an amount greater than what the contract actually holds.
4. When the order is later settled/withdrawn (`_withdraw`), the ledger claims more tokens than the contract's real `balanceOf`, causing either a revert for competing withdrawals on the same token or a shortfall that leaves other users' escrow entries unbacked — exactly the "loss of funds" scenario described in the referenced Cooler report.

    /// @notice Escrow correctly reflects actual received amount for fee-on-transfer tokens.
    function testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived() public {
        // Deploy a 1% fee-on-transfer token
        FeeOnTransferToken fot = new FeeOnTransferToken(100); // 1% = 100 bps
        fot.mint(user, 10000 * 1e18);

        uint256 inputAmount = 1000 * 1e18;
        uint256 expectedReceived = inputAmount - (inputAmount * 100) / 10000; // 990

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(fot)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 900 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        vm.startPrank(user);
        fot.approve(address(intentGateway), inputAmount);
        intentGateway.placeOrder(order, bytes32(0));
        vm.stopPrank();

        // Gateway should hold only what it actually received
        assertEq(
            fot.balanceOf(address(intentGateway)), expectedReceived, "Gateway balance should match received amount"
        );

        // Reconstruct the order as placeOrder would have mutated it
        order.user = bytes32(uint256(uint160(user)));
        order.source = host.host();
        order.nonce = 0;
        order.inputs[0].amount = expectedReceived;
        bytes32 commitment = keccak256(abi.encode(order));

        // Escrow should match actual received, not the user-specified amount
        assertEq(
            intentGateway._orders(commitment, address(fot)),
            expectedReceived,
            "Escrow should equal actual received amount"
        );
    }

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {

            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
