### Title
Webhook shop identity is not bound to the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature only over the raw request body, while the `shop` value that is later trusted and forwarded to the app's webhook handler is taken from an attacker-controllable HTTP header that plays no part in that signature. This breaks the implicit binding `shop_verified_by_hmac == shop_delivered_to_handler`, letting anyone who possesses one valid `(body, hmac)` pair (e.g. from their own shop's legitimate webhook) relabel it as belonging to a different, victim shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

and `#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cross-check against the signed content: [2](#0-1) 

`HmacValidator.validate` verifies the signature purely against `to_signable_string` (i.e. the body) and the app's `api_secret_key`: [3](#0-2) 

`Registry.process` performs this HMAC check and then immediately constructs `WebhookMetadata` using `request.shop`, implicitly presenting it as verified/trusted alongside the HMAC-checked body: [4](#0-3) 

Because `shop` is excluded from the signable string, `hmac` only proves "this body was HMAC-signed with our secret" — not "this body belongs to shop X". Anyone in possession of one valid `(raw_body, hmac)` pair for their own store can resend it with the `shop-domain` header swapped to any other shop, and `HmacValidator.validate` will still return `true`, because the header is never part of the signed input.

### Impact Explanation
This is a cross-tenant identity confusion: the `shop` field that host applications rely on (per the gem's documented `WebhookMetadata#shop` usage in webhook handlers) to determine which merchant/tenant the event applies to is not actually bound to the cryptographic proof that authenticates the event. An attacker who legitimately installs the app on their own store (or otherwise obtains one valid webhook body/HMAC pair for their own shop) can forge webhook deliveries that are processed as if they originated from an arbitrary victim shop, since `Registry.process` treats `request.shop` as authenticated once `Utils::HmacValidator.validate(request)` passes.

### Likelihood Explanation
Requires only network access to the app's webhook endpoint and possession of one legitimately-signed `(body, hmac)` pair (trivially obtainable by installing the app on an attacker-controlled shop, which is a normal, unprivileged action). No access token, `api_secret_key`, or other privileged credential is required.

### Recommendation
Include the shop domain (and other identity-relevant metadata) in the HMAC-covered signable content, or independently verify that `request.shop` matches an authenticated context (e.g., a shop-scoped session/access token already on file) before dispatching to the handler, rather than trusting the `shop-domain` header as authenticated purely because the body's HMAC validated.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and receives a legitimate webhook: raw body `B`, header `x-shopify-hmac-sha256: H`, `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker replays the exact same `B` and `H` to the app's webhook endpoint but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` is built; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and succeeds (per `lib/shopify_api/webhooks/request.rb` L35-38 and `lib/shopify_api/utils/hmac_validator.rb` L26-31).
4. `Registry.process` calls the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)` (`lib/shopify_api/webhooks/registry.rb` L198-199), even though Shopify never sent this event for `victim-shop`.
5. Any host-app logic keyed on `data.shop` (session lookup, per-tenant processing, etc.) now executes attacker-controlled body content under the victim shop's identity.
