### Title
Cache key collision in `DirectBridge.getCachedStorageDepositValue` due to unseparated string concatenation - (File: `packages/intents-sdk/src/bridges/direct-bridge/direct-bridge.ts`)

### Summary
`DirectBridge.getCachedStorageDepositValue` builds its LRU cache key by naively concatenating `contractId` and `accountId` with no delimiter: `` `${contractId}${accountId}` ``. Two distinct `(contractId, accountId)` pairs can produce the identical cache key string, letting a cached "storage already sufficient" result computed for one token/account pair be served for an unrelated token/account pair, which breaks the equality between the storage-deposit fee actually required for the current withdrawal and the fee value used to build the on-chain `ft_withdraw` intent.

### Finding Description
`getCachedStorageDepositValue` is called from `estimateWithdrawalFee` with `tokenAccountId` (the NEP-141 token contract being withdrawn) and `args.withdrawalParams.destinationAddress` (the caller-controlled destination account): [1](#0-0) 

The cache key is built without a delimiter: [2](#0-1) 

Every other cache in this codebase that composes a multi-part key uses an explicit separator to avoid ambiguity, e.g. `` `${omniChainKind}:${contractId}` `` in `OmniBridge.getCachedDestinationTokenAddress` and `` `${tx.hash}:${tx.accountId}` `` in `HotBridge.getNoncesCacheKey`: [3](#0-2) [4](#0-3) 

Because `contractId` (a NEP-141 token id, e.g. `"foo.near"`) and `accountId` (fully attacker-controlled via `destinationAddress`) are just concatenated, an attacker who wants to withdraw token `foo.nearbar.near` to destination `""`-like short strings, or more generally, any attacker who controls `destinationAddress` can choose a value such that `contractId + accountId` collides with an already-cached key from a prior, unrelated `(contractId', accountId')` pair (e.g. `contractId = "foo.near"`, `accountId = "bar.near"` collides with `contractId' = "foo.nearbar.near"`, `accountId' = ""` or any other split that yields the identical concatenated string). Since account names on NEAR only need to satisfy the generic NEAR account-id charset/length rules, many such splits are constructible for realistic token ids.

Only "storage sufficient" (fee-free) results are cached — `if (result[1] >= result[0]) this.storageDepositCache.set(key, result);` — so a colliding cache hit specifically forges the answer "no storage deposit is needed" onto a withdrawal that actually requires one.

### Impact Explanation
If `estimateWithdrawalFee` returns a false "storage deposit not needed" result due to the collision, `createWithdrawalIntents` propagates a `storageDepositFee` of `0`, which flows into `createWithdrawIntentPrimitive` as `storage_deposit: undefined` for the resulting `ft_withdraw` intent: [5](#0-4) 

An `ft_withdraw`/`ft_transfer` targeting an account that lacks the token's storage registration and receives no storage deposit will fail on-chain, leaving the withdrawal stuck and requiring manual intervention/recovery — matching the "High: a withdrawal stuck until manual intervention" impact bucket.

### Likelihood Explanation
The attacker only needs control over `destinationAddress` (which is already user-supplied in every call to `estimateWithdrawalFee`/`signAndSendWithdrawalIntent`) and knowledge of the supported token contract ids, which are public. No privileged access, relayer cooperation, or malicious third party is required — the collision is purely a client-observable input-crafting exercise against an in-process cache that is shared across all callers/users of a single `DirectBridge` instance (e.g. inside a long-running relayer/integrator service).

### Recommendation
Use an unambiguous, delimited cache key, consistent with the rest of the codebase, e.g.:
```ts
const key = `${contractId}:${accountId}`;
```
or better, use a compound/tuple cache keyed structure (e.g. nested Maps or a key encoding length-prefixed segments) so that no two distinct `(contractId, accountId)` pairs can ever produce the same cache key.

### Proof of Concept
1. Caller A requests a withdrawal fee estimate for token `foo.near` to account `bar.near`, where `bar.near` already has sufficient NEP-141 storage on `foo.near`. This populates the cache: key `"foo.nearbar.near"` → `[min, sufficientBalance]` (fee-free result cached).
2. Caller B (attacker) requests a fee estimate for a *different* token contract, e.g. `foo.nearbar.near` (a distinct, valid NEP-141 contract id), with destination account `""`... or more concretely any pair `(contractId2, accountId2)` such that `contractId2 + accountId2 === "foo.nearbar.near"` — e.g. `contractId2 = "foo.nearba"`, `accountId2 = "r.near"`.
3. `getCachedStorageDepositValue("foo.nearba", "r.near")` computes key `"foo.nearbar.near"`, hits the cache populated in step 1, and returns the cached `[min, sufficientBalance]` even though `r.near` has never registered storage on `foo.nearba`.
4. `estimateWithdrawalFee` reports `storageDepositFee: 0n`, and the subsequently built `ft_withdraw` intent omits `storage_deposit`, causing the on-chain transfer to `r.near` to fail for lack of storage registration — the withdrawal becomes stuck.

		contractId: string,
		accountId: string,
	): Promise<[MinStorageBalance, StorageDepositBalance]> {
		const key = `${contractId}${accountId}`;
