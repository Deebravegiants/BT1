### Title
Webhook shop/topic identity headers are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes the signable string used for HMAC verification from the raw body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values that the registry acts on are read from unauthenticated HTTP headers. Any party who can obtain one validly-signed webhook body/HMAC pair (e.g. by operating their own free/dev Shopify store that legitimately receives webhooks from the target app) can replay that exact body with the same valid HMAC while substituting arbitrary values for `shop-domain`, `topic`, and `webhook_id` headers, and the gem will accept it as authentic.

### Finding Description
`Utils::HmacValidator.validate` verifies a request by comparing the HMAC header against a signature computed over `to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` is defined as just the raw request body: [2](#0-1) 

But `shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from HTTP headers with no cryptographic binding to the signature: [3](#0-2) 

`Registry.process` validates only the HMAC (i.e., only the body) and then unconditionally trusts these unauthenticated header-derived fields to look up the handler and build the metadata object passed to app code: [4](#0-3) 

This breaks the intended identity binding: `shop-header == shop the payload actually originated from` (and similarly for `topic`). Since the HMAC is computed with `Context.api_secret_key` over the body only, an attacker who legitimately owns any store that installs the target app receives real, correctly-signed webhooks from Shopify. Capturing one `(raw_body, hmac)` pair and re-POSTing it to the app's webhook endpoint with a forged `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header produces a request that still passes `HmacValidator.validate` (body/HMAC untouched), but is processed by `Registry.process` under an attacker-chosen shop identity and/or attacker-chosen topic.

### Impact Explanation
This is a cross-tenant identity confusion: the app's webhook handler executes business logic (e.g., updating order/customer state, triggering GDPR redaction flows for `MANDATORY_TOPICS`, invalidating sessions, writing to per-shop storage) believing the data belongs to `request.shop`/`request.topic`, when in fact only the body was authenticated and the shop/topic labels are attacker-controlled. This can lead to data being attributed to or acted upon for the wrong merchant (cross-tenant access), or a benign topic's body being replayed and reprocessed under a different topic name that the handler treats specially, without needing the app's `client_secret` or an access token — only a legitimately signed webhook the attacker themselves received.

### Likelihood Explanation
Likelihood is moderate: it requires the attacker to have access to at least one legitimately signed webhook body/HMAC (achievable by installing the app on any store they control, including a free development store, and capturing the webhook Shopify sends them), then replaying it with modified headers to the app's public webhook endpoint. No secret material or privileged account beyond an ordinary/dev shop install is needed.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the signable string (or otherwise cryptographically bind them, e.g. by having `HmacValidator`/`Request` incorporate these header values into the signature check), so header spoofing invalidates the HMAC. At minimum, `Registry.process` should not trust `request.shop`/`request.topic` for tenant-sensitive logic unless they are covered by the same signature that authenticates the body.

### Proof of Concept
1. Attacker installs the app on their own Shopify store `attacker-shop.myshopify.com` and lets it send a legitimate webhook, e.g. topic `orders/create`, capturing the raw JSON body `B` and the valid `X-Shopify-Hmac-Sha256` header `H` (computed by Shopify over `B` with the app's real `api_secret_key`).
2. Attacker replays `POST /webhooks` to the victim app with the same body `B` and header `H`, but sets:
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
   - `X-Shopify-Topic: shop/redact` (or any registered mandatory/high-impact topic)
3. `ShopifyAPI::Utils::HmacValidator.validate(request)` succeeds because it only recomputes the HMAC over `@raw_body`, which is unchanged: [5](#0-4) 
4. `Registry.process` looks up the handler for the attacker-chosen `topic` and invokes it with `shop: request.shop` set to `victim-shop.myshopify.com`, even though the payload never originated from that shop: [6](#0-5)
