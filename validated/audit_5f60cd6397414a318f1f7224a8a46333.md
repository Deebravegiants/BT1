Audit Report

## Title
Gateway HTTP Action response cache key omits `WorkflowID`, allowing session-bearing cached responses (e.g. `Set-Cookie`) to be served across different workflow executions - (File: core/services/gateway/handlers/capabilities/v2/response_cache.go)

## Summary
The `responseCache` used by the gateway's HTTP Action handler keys cached `OutboundHTTPResponse` entries solely by `req.Hash()`, and the repository's own test suite proves that `Hash()` is invariant to `WorkflowID` while depending on `WorkflowOwner`, method, URL, headers, and body. This contradicts the documented "Workflow Isolation" guarantee in the feature's README and allows two distinct workflow executions under the same owner to collide on a single cache entry, including any `Set-Cookie`/session data returned by the external endpoint.

## Finding Description
`makeOutgoingRequest` in [1](#0-0)  reads a per-node-decoded `OutboundHTTPRequest` and, when `CacheSettings.MaxAgeMs > 0` or `CacheSettings.Store` is set, routes the response through `responseCache.Fetch`/`Set`. Both operations use `req.Hash()` as the sole cache key [2](#0-1) [3](#0-2) [4](#0-3) .

The test suite in this repo directly demonstrates that `Hash()` does not incorporate `WorkflowID`: two requests differing only in `WorkflowID` produce the same hash [5](#0-4) , while `WorkflowOwner` does affect the hash [6](#0-5) . The comment on the `responseCache` struct itself documents the key composition as "method, URL, headers, body, workflowOwner" [7](#0-6) , which is inconsistent with the README's claim that "Cache entries are scoped by workflow ID to prevent cross-workflow data leakage."

Cached `OutboundHTTPResponse` objects carry through arbitrary response headers, including `Set-Cookie`, unmodified from the external endpoint [8](#0-7) , and this is explicitly exercised in tests using session/CSRF cookies [9](#0-8) . There is no header-stripping or redaction logic anywhere in the cache write path.

Because `Hash()` is invariant to `WorkflowID`, two different workflow executions belonging to the same `WorkflowOwner` that issue an identical outbound request (same method/URL/headers/body) with caching enabled will read/write the same cache entry, and the second workflow will receive the first workflow's cached response — including session cookies — via `sendResponseToNode` [10](#0-9) .

## Impact Explanation
This is a legitimate cross-workflow response confusion (CWE-524-class issue): a workflow author's cached HTTP response, potentially containing session cookies, CSRF tokens, or other per-call sensitive data returned by an external API, can be served to a different workflow execution owned by the same address. This maps to the in-scope "cross-user response corruption" impact category — although note the collision is scoped to the same `WorkflowOwner` (not an arbitrary unrelated third party), since `WorkflowOwner` does participate in the hash. The severity depends on whether distinct workflows under one owner are meant to be mutually isolated from each other's cached data, which the README explicitly promises and the code fails to deliver.

## Likelihood Explanation
No privilege escalation is required beyond normal workflow-authoring capability: any workflow owner running two workflows (or two executions with distinct `WorkflowID`s) that call the same external endpoint with identical method/URL/headers/body and enable `CacheSettings.Store`/`MaxAgeMs` will trigger this behavior automatically, through documented HTTP Action + caching functionality — no malicious node, host access, or operator privilege is needed. This is realistic for common patterns like polling APIs that set per-session cookies.

## Recommendation
Include `WorkflowID` in the `Hash()` computation used as the `responseCache` key so cache entries are correctly isolated per the documented guarantee, and/or strip session-identifying response headers (`Set-Cookie`, `Authorization`, and similar) before storing responses in the shared cache.

## Proof of Concept
1. Workflow A (owner `0xabc`, `WorkflowID: "wf-1"`) issues an `OutboundHTTPRequest` to `https://api.example.com/data` with `CacheSettings{Store:true, MaxAgeMs:600000}`; external endpoint responds `200` with `Set-Cookie: sessionid=A-secret`.
2. `responseCache.Set` stores this response keyed by `req.Hash()`, which does not vary with `WorkflowID` (proven in `response_cache_test.go` L139-149).
3. Workflow B (same owner `0xabc`, `WorkflowID: "wf-2"`) issues an identical request (same method/URL/headers/body) with caching enabled before TTL expiry.
4. `responseCache.Fetch` returns the cached entry from step 1; Workflow B's node receives `Set-Cookie: sessionid=A-secret` via `sendResponseToNode`, despite belonging to a distinct workflow.
5. A Go unit test extending `response_cache_test.go` can directly assert: build two `OutboundHTTPRequest`s with same `WorkflowOwner` but different `WorkflowID`, call `Set` with request A and a response containing a `Set-Cookie` header, then call `Fetch`/`isExpiredOrNotCached` with request B and confirm the cached response (including the cookie) is returned.

```go
func (h *gatewayHandler) makeOutgoingRequest(ctx context.Context, resp *jsonrpc.Response[json.RawMessage], nodeAddr string) error {
	requestID := resp.ID
	h.lggr.Debugw("handling outgoing message", "requestID", requestID, "nodeAddr", nodeAddr)
	var req gateway_common.OutboundHTTPRequest
	err := json.Unmarshal(*resp.Result, &req)
	if err != nil {
		return fmt.Errorf("failed to unmarshal HTTP request from node %s: %w", nodeAddr, err)
	}
	timeout := time.Duration(req.TimeoutMs) * time.Millisecond
	httpReq := network.HTTPRequest{
		Method:           req.Method,
		URL:              req.URL,
		Headers:          req.Headers, //nolint:staticcheck // forward deprecated Headers for backward compatibility; request uses MultiHeaders when set
		MultiHeaders:     req.MultiHeaders,
		Body:             req.Body,
		MaxResponseBytes: req.MaxResponseBytes,
		Timeout:          timeout,
	}

	sendResponseTimeout := time.Duration(defaultSendResponseTimeoutMs) * time.Millisecond

	// send response to node async
	h.wg.Go(func() {
		// not cancelled when parent is cancelled to ensure the goroutine can finish
		baseCtx := context.WithoutCancel(ctx)
		httpCtx, httpCancel := context.WithTimeout(baseCtx, timeout)
		defer httpCancel()
		l := logger.With(h.lggr, "requestID", requestID, "method", req.Method, "timeout", req.TimeoutMs)
		var outboundResp gateway_common.OutboundHTTPResponse
		callback := h.createHTTPRequestCallback(httpCtx, requestID, httpReq, req)
		if req.CacheSettings.MaxAgeMs > 0 {
			h.metrics.IncrementCacheReadCount(ctx, h.lggr)
			outboundResp = h.responseCache.Fetch(httpCtx, req, callback, req.CacheSettings.Store)
		} else {
			outboundResp = callback()
			if req.CacheSettings.Store {
				h.responseCache.Set(req, outboundResp)
			}
		}
```

```go
// isExpiredOrNotCached returns true if the cached response is expired or not cached.
// IMPORTANT: this method does not lock the cache map. MUST be called with cacheMu write-locked.
func (rc *responseCache) isExpiredOrNotCached(req gateway.OutboundHTTPRequest) bool {
	cachedResp, exists := rc.cache[req.Hash()]
	if !exists || time.Now().After(cachedResp.storedAt.Add(rc.ttl)) {
		return true
	}
	return false
}
```

```go
func (rc *responseCache) Fetch(ctx context.Context, req gateway.OutboundHTTPRequest, fetchFn func() gateway.OutboundHTTPResponse, storeOnFetch bool) gateway.OutboundHTTPResponse {
	cacheKey := req.Hash()
	cacheMaxAge := time.Duration(req.CacheSettings.MaxAgeMs) * time.Millisecond

	// Fast path: check cache without singleflight overhead.
	rc.cacheMu.RLock()
	cachedResp, exists := rc.cache[cacheKey]
	rc.cacheMu.RUnlock()
	if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
		rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
		return cachedResp.response
	}
```

```go
func (rc *responseCache) Set(req gateway.OutboundHTTPRequest, response gateway.OutboundHTTPResponse) {
	rc.cacheMu.Lock()
	defer rc.cacheMu.Unlock()
	if isCacheableStatusCode(response.StatusCode) && rc.isExpiredOrNotCached(req) {
		rc.cache[req.Hash()] = &cachedResponse{
			response: response,
			storedAt: time.Now(),
		}
	}
}
```
