### Title
IntentGatewayV2 (Tron) escrows the nominal input amount instead of the actual balance received, breaking accounting for fee-on-transfer tokens - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of `IntentGatewayV2.placeOrder` credits escrow (`_orders[commitment][token]`) with the user-specified `order.inputs[i].amount` (minus protocol fee), but performs the actual token pull via `safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` without ever measuring what the contract actually received. For any ERC20/TRC20 fee-on-transfer token, the contract will receive strictly less than the escrowed bookkeeping amount.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol`, `placeOrder`:
1. Computes `reducedInputs[i].amount` from `order.inputs[i].amount` (user-supplied) minus protocol fee (lines 359-385).
2. Transfers tokens with `IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` (line 459) — a raw ERC20 transfer that can silently deduct a fee.
3. Immediately credits escrow with `_orders[commitment][token] += reducedInputs[i].amount` (line 463) — the *nominal*, not the actually-received, amount.

The same pattern exists in the predispatch/call-dispatcher path (lines 387-449), where `_orders[commitment][token] += reducedInputs[i].amount` (line 441) is likewise based on nominal input rather than measured balances (though this branch at least checks `balance < requiredAmount` before sweeping, the escrowed value stored is still the pre-fee `reducedInputs[i].amount`, not the swept `balance`).

This is the same root cause described in the external report: internal bookkeeping (`_orders` mapping) diverges from the actual token balance held by the contract when the underlying asset takes a transfer fee.

Compare with the patched primary contract `evm/src/apps/IntentGatewayV2.sol` (lines 312-329), which explicitly snapshots `balBefore`/`balAfter` around `safeTransferFrom` and overwrites `order.inputs[i].amount` with the actually-received delta before any fee/commitment/escrow math is performed — confirming this is a known bug class in this codebase that was fixed in one contract variant but not the Tron fork. [1](#0-0) [2](#0-1) 

### Impact Explanation
Once escrow accounting exceeds the real token balance, the contract becomes insolvent for that token: later withdrawals (`withdraw`/`_withdraw`, which `safeTransfer`s the escrowed amount to the solver or refunds the user) will attempt to pay out more than the contract actually holds. Depending on order of settlement, either the solver who fills the order or the user requesting a refund/cancellation will have their transfer revert (insufficient balance) or, if multiple orders share the same token, an early claimant can drain funds that back a later order, permanently freezing/breaking fulfillment for other orders on the same token. This is a direct, concrete freezing-of-funds condition reachable by any unprivileged user submitting a single `placeOrder` transaction with a fee-on-transfer TRC20 token. [3](#0-2) 

### Likelihood Explanation
Likelihood depends on a fee-on-transfer token being used as an order input on the Tron deployment. TRC20 tokens with transfer fees exist in the Tron ecosystem, and nothing in `placeOrder` validates or rejects such tokens — any user can submit an order with an arbitrary ERC20-compatible token address, making this fully attacker/user-triggerable without special privilege.

### Recommendation
Apply the same fix already present in `evm/src/apps/IntentGatewayV2.sol`: snapshot the contract's token balance immediately before and after each `safeTransferFrom` call, and use the measured delta (not the nominal `order.inputs[i].amount`) as the basis for `reducedInputs`, the commitment hash, and the `_orders` escrow credit, in both the direct-transfer and predispatch/call-dispatcher code paths.

### Proof of Concept
1. Deploy a TRC20 token that deducts a 1% fee on every `transfer`/`transferFrom` (e.g. the `FeeOnTransferToken` test helper already present in `evm/tests/foundry/IntentGatewayV2SameChainTest.sol` lines 2690-2730).
2. User calls `placeOrder` on the Tron `IntentGatewayV2` with `order.inputs[0] = {token: FOT, amount: 1000e18}` and `protocolFeeBps = 0`.
3. `safeTransferFrom` moves 1000e18 nominal but the contract only receives 990e18 (1% fee retained by the token).
4. `_orders[commitment][FOT]` is nonetheless credited with `1000e18` (line 463), not `990e18`.
5. A solver fills the order and calls `withdraw`, which attempts `IERC20(FOT).transfer(beneficiary, 1000e18)` (line 706) — this either reverts (insufficient contract balance) or, if other orders in the same token exist, siphons their escrowed balance, leaving those orders permanently unfulfillable.
