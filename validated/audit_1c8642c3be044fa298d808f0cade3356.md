This confirms the vulnerability. The docs explicitly document `ShopifyAPI::Webhooks::Registry.process` as "verify the request did indeed come from Shopify" — but the HMAC only covers the raw body, not the `shop-domain` header that is passed straight through to the app's handler as the authoritative tenant identifier.

### Title
Webhook `shop` field is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes the signable string used for HMAC validation solely from the raw HTTP body [1](#0-0) , while the `shop` attribute — which downstream handlers treat as the authenticated tenant identifier — is read directly from the unauthenticated `shopify-shop-domain` HTTP header [2](#0-1) . `Registry.process` validates the HMAC and, if it matches, unconditionally forwards `request.shop` to the app's webhook handler as trusted tenant data [3](#0-2) .

### Finding Description
The identity binding that should hold is: `hmac_signed_bytes == bytes_that_determine_the_tenant`. Here it does not: the HMAC in `HmacValidator.validate_signature` is computed over `verifiable_query.to_signable_string`, which for `Request` returns only `@raw_body` [4](#0-3) [1](#0-0) . The `shop` value is taken from the `shopify-shop-domain` (or `x-shopify-shop-domain`) header, which is not part of that signed string [2](#0-1) .

The HMAC secret (`Context.api_secret_key`) is a single value shared across all shops that install the app — it is not shop-specific [5](#0-4) . Therefore any unprivileged user who installs the target app on their own (attacker-controlled) shop receives genuine webhook deliveries whose bodies are validly signed with that shared secret. Because the signature never covers the `shop-domain` header, the attacker can capture one such legitimate webhook POST and replay it to the app's webhook endpoint with the `x-shopify-shop-domain` header rewritten to an arbitrary victim shop domain. `HmacValidator.validate` will still return `true` (the body and signature are unchanged), and `Registry.process` will hand the handler a `WebhookMetadata` whose `shop` field is the attacker-chosen victim domain [6](#0-5) .

The library's own documentation states that `Registry.process` "will verify the request did indeed come from Shopify" [7](#0-6)  and that host apps are expected to key their own webhook processing (job enqueuing, persistence, etc.) off `data.shop` [8](#0-7) , so this gem's own contract establishes `shop` as an authenticated field, which it is not.

### Impact Explanation
This breaks the tenant identity binding at the core of webhook processing: an attacker can forge webhook events "from" any other merchant's shop while only needing the ability to install the app on a shop they control. Depending on how the host app consumes `data.shop` (e.g., looking up the shop's stored access token/session, updating shop-scoped records, or triggering shop-scoped side effects), this enables cross-tenant data confusion/corruption — for example injecting attacker-controlled webhook bodies (order data, product data, uninstall/app-scope events, etc.) attributed to a victim shop that never sent them. This matches the Critical impact category of cross-tenant access via a credential/tenant boundary that is nominally protected by HMAC but is not actually bound to the tenant field being trusted.

### Likelihood Explanation
Likelihood is high for any app that lets attackers self-register (most public/embedded Shopify apps do, since anyone can install a listed app on their own development or trial store). No access token, `client_secret`, or privileged account is required — only the ability to become a legitimate installer of the target app on a shop the attacker controls, then replaying an HTTP POST with a modified header to the app's own public webhook endpoint.

### Recommendation
Bind the `shop` (and ideally `topic`/`api_version`/`webhook_id`) values into the HMAC-signed payload, or otherwise cryptographically tie the header-derived `shop` to the signed body (e.g., require the body to embed/echo the shop domain, or validate the header-derived shop against Shopify's real webhook payload conventions where the resource itself is scoped, and cross-check it against a known/expected shop for that endpoint). At minimum, `to_signable_string` in `lib/shopify_api/webhooks/request.rb` should incorporate the `shop`, `topic`, and `webhook_id` headers so that any tampering with those headers invalidates the HMAC.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker.myshopify.com` (a shop they control) and registers a webhook, e.g. `orders/create`.
2. Shopify delivers a legitimate webhook POST to the app's endpoint:
   ```
   POST /callback/orders/create
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid HMAC of body, computed with the app's shared api_secret_key>
   x-shopify-shop-domain: attacker.myshopify.com
   Body: {"id": 1, ...attacker-controlled order payload...}
   ```
3. Attacker captures this request and replays it to the same endpoint, changing only the header:
   ```
   x-shopify-shop-domain: victim.myshopify.com
   ```
   (body and `x-shopify-hmac-sha256` left untouched).
4. `ShopifyAPI::Webhooks::Request.new` parses the tampered request; `Utils::HmacValidator.validate` recomputes the HMAC over `@raw_body` only, which still matches, so `Registry.process` proceeds [3](#0-2) .
5. The app's `WebhookHandler#handle` receives `data.shop == "victim.myshopify.com"` with the attacker-controlled body, and performs shop-scoped work (e.g., writes to the database keyed by `victim.myshopify.com`) — cross-tenant impact achieved despite the "verified" HMAC.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
