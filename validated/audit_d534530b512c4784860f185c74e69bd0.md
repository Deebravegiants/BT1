### Title
Webhook HMAC signs only the request body, not the shop-domain/topic headers, allowing cross-tenant shop-attribution spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, and `ShopifyAPI::Utils::HmacValidator.validate` verifies the HMAC solely over that signable string. [1](#0-0) [2](#0-1)  The `shop` and `topic` values, however, are read directly from the `x-shopify-shop-domain` / `x-shopify-topic` HTTP headers and are never included in the signed material. [3](#0-2)  `Registry.process` accepts the request once `HmacValidator.validate(request)` passes and then dispatches `request.shop` (an unauthenticated header) straight into `WebhookMetadata` for the handler to consume as the tenant identity. [4](#0-3) 

### Finding Description
The intended binding is: **`shop` attributed to a processed webhook == `shop` that produced the HMAC-signed content**. This gem breaks that equality:

- The HMAC is computed only over `raw_body` (`OpenSSL::HMAC.hexdigest(..., secret, signable_string)` where `signable_string == @raw_body`). [5](#0-4) [1](#0-0) 
- `shop`, `topic`, `api_version`, and `webhook_id` are pulled straight from caller-supplied headers with no cryptographic tie to the signed body. [6](#0-5) 
- `Registry.process` only re-checks the HMAC validity, not any correspondence between the header-supplied `shop`/`topic` and the body content, before handing `request.shop` to the handler as the authoritative tenant identifier: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))`. [4](#0-3) 

Concretely: an unprivileged attacker who has installed the app on their own store receives genuine Shopify webhooks with a valid HMAC computed only over the JSON body. Because the signature never covers the shop-domain header, the attacker can replay that exact `raw_body`/`hmac` pair while substituting the `x-shopify-shop-domain` header with a victim shop's domain (or any other topic in the `x-shopify-topic` header). `HmacValidator.validate` still returns `true` since it only recomputes the HMAC over `raw_body`, and the gem forwards `shop: <attacker-chosen victim domain>` to the host application's webhook handler as if it were an authentic message from that shop.

### Impact Explanation
This is a cross-tenant identity-confusion vector inside the gem's own request-authentication code: the value the gem asserts as "verified webhook origin shop" is not actually bound to the cryptographic signature. Any host application that uses `WebhookMetadata#shop` (as documented/intended) to key persistence, trigger tenant-scoped side effects, or select which merchant's session/access token to act on can be made to attribute attacker-controlled body content to an arbitrary victim shop domain — a cross-tenant boundary violation reachable without any secret, token, or privileged access, using only the app's own already-issued webhook to the attacker's own store.

### Likelihood Explanation
Likelihood is Medium-High: exploitation requires only (1) installing the target app on any store the attacker controls (a normal, unprivileged interaction) to obtain a legitimately-signed `raw_body`/`hmac` pair, and (2) sending a forged HTTP request to the app's webhook endpoint with that same body/hmac but an arbitrary `shop-domain` header. No access to `api_secret_key`, access tokens, or the shop's real credentials is needed — only network access to the app's public webhook endpoint, which is unauthenticated by design (the HMAC is meant to be the sole authentication mechanism).

### Recommendation
Include `shop`, `topic`, and any other header fields the handler relies on for identity/routing inside the HMAC-signed material (or independently verify that the header-derived `shop`/`topic` match values embedded in the signed body/payload) before constructing `WebhookMetadata`. At minimum, document/enforce that `Registry.process` cross-checks header-derived identity fields against Shopify's known shop registry for the delivered `hmac`, rather than trusting unauthenticated headers verbatim.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and triggers a real webhook (e.g. `orders/create`), capturing the genuine request: `raw_body = B`, header `x-shopify-hmac-sha256 = H` (valid signature over `B` with the app's `client_secret`), and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker crafts a new HTTP POST to the app's webhook endpoint with the same body `B` and same `hmac` header `H`, but replaces `x-shopify-shop-domain` with `victim-shop.myshopify.com` (and optionally a different `x-shopify-topic`).
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...shop-domain: "victim-shop.myshopify.com", hmac-sha256: H...})` is constructed; `Utils::HmacValidator.validate(request)` recomputes the HMAC over `B` only and returns `true` (per `lib/shopify_api/webhooks/request.rb:35-38` and `lib/shopify_api/utils/hmac_validator.rb:12-22`).
4. `ShopifyAPI::Webhooks::Registry.process(request)` accepts the forged request and calls the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)` (per `lib/shopify_api/webhooks/registry.rb:188-200`), causing the host application to process attacker-controlled data under the victim shop's identity.
