### Title
Non-embedded session lookup trusts an unsigned, deterministic session ID cookie as a tenant identity binding - (File: `lib/shopify_api/utils/session_utils.rb`)

### Summary
For non-embedded apps, `ShopifyAPI::Utils::SessionUtils.current_session_id` derives the "authenticated" session identifier purely from the raw value of the `shopify_app_session` cookie, with no cryptographic binding (no HMAC/signature) tying that value to a completed OAuth flow for the shop it names.

### Finding Description
`SessionUtils.current_session_id` (non-embedded path) requires only that a cookie named `Auth::Oauth::SessionCookie::SESSION_COOKIE_NAME` be present, and returns its raw value unmodified as the session ID: [1](#0-0) [2](#0-1) 

This cookie value is produced during `Oauth.validate_auth_callback` as `session.id`, which for offline sessions is simply `"offline_#{shop}"` — a value fully derivable from public information (the shop's own domain), with no random or HMAC component: [3](#0-2) [4](#0-3) 

`SessionCookie` itself is a plain value struct with no signature/MAC field: [5](#0-4) 

The gem's own documented usage pattern instructs host applications to feed raw request cookies into `current_session_id` and use the returned string directly as the lookup key into their session store to retrieve the merchant's access token: [6](#0-5) 

The binding that should hold is: `session_id used for token lookup == session_id produced through a verified OAuth completion for that specific shop`. Because the ID is a deterministic, unsigned function of the shop domain (and, for online sessions, the numeric Shopify user ID, also learnable via the JWT's `sub` claim or observable IDs), that equality does not require possessing any secret — an attacker who merely knows or guesses a target shop's domain can compute the exact same string and present it as a cookie value on a direct HTTP request to the host app (HTTP clients, unlike browsers, can set arbitrary `Cookie` headers on cross-origin requests). If the host application follows this library's documented pattern, `current_session_id` returns the attacker-chosen ID indistinguishably from a legitimately-issued one, and the application's session store will resolve it to the real access token belonging to that shop.

### Impact Explanation
This breaks the tenant boundary in a multi-tenant Shopify app: cross-tenant access to another merchant's stored access token/session becomes possible without any credential, purely by supplying a computable string as a cookie value. This matches the "Critical – cross-tenant access" impact category, since the value that is supposed to function as proof of authentication (`session.id`) carries no unforgeability guarantee.

### Likelihood Explanation
Likelihood is constrained by real-world deployment factors this analysis cannot fully verify from the gem alone: the cookie is marked `http_only`/`secure` in the documented examples (mitigating browser-based theft via JS, but not mitigating direct-HTTP-client forgery), and exploitation additionally depends on the host application's session store performing a naive lookup keyed purely by this ID (a pattern the gem's own docs explicitly recommend). Given that shop domains are public (`*.myshopify.com`) and offline session IDs require no other secret, likelihood is Medium-to-High for any app implementing session storage exactly as documented.

### Recommendation
Do not derive the session-store lookup key solely from unauthenticated, deterministic values. Bind the session identifier to a value only obtainable via a Shopify-issued credential — e.g., generate a cryptographically random session ID at OAuth-completion time (unlinkable to the shop string) and/or HMAC/sign the cookie value with the app's secret so that `current_session_id`/`cookie_session_id` can verify integrity before trusting it, rejecting any cookie whose signature doesn't match.

### Proof of Concept
1. Host app implements the documented non-embedded flow exactly as shown in `docs/getting_started.md`, storing sessions keyed by `SessionUtils.current_session_id`.
2. Victim shop `victim-shop.myshopify.com` completes OAuth; the app stores a session under `session.id == "offline_victim-shop.myshopify.com"` per `Session.from`/`validate_auth_callback` logic.
3. Attacker (unauthenticated, no cookie ever issued to them) sends a direct HTTP request to any authenticated route of the host app with header:
   `Cookie: shopify_app_session=offline_victim-shop.myshopify.com`
4. `SessionUtils.current_session_id(nil, cookies, false)` → `cookie_session_id(cookies)` returns `"offline_victim-shop.myshopify.com"` unchanged (no signature check performed).
5. Host app's session store (implemented per this gem's documented pattern) looks up and returns victim's session/access token, and the attacker's request is now treated as an authenticated call on behalf of `victim-shop`.

```ruby
        end
```

```ruby
      class SessionCookie < T::Struct
        extend T::Sig

        SESSION_COOKIE_NAME = "shopify_app_session"

        const :name, String, default: SESSION_COOKIE_NAME
        const :value, String
        const :expires, T.nilable(Time)

        alias_method :eql?, :==
        sig { params(other: T.nilable(SessionCookie)).returns(T::Boolean) }
        def ==(other)
          return false unless other

          name == other.name &&
            value == other.value &&
            expires == other.expires
        end
      end
```

```markdown
#### Cookie
Cookie based authentication is not supported for embedded apps due to browsers dropping support for third party cookies due to security concerns. Non-embedded apps are able to use cookies for session storage/retrieval.

For *non-embedded* apps, you can pass the cookies into:
 - `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, true)` for online (user) sessions or
 - `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)` for offline (store) sessions.
```
