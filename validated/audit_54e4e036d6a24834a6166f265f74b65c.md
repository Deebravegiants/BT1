### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing shop-identity spoofing on an otherwise validly-signed webhook - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) it hands to the app's webhook handler from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, but `Utils::HmacValidator` only verifies the raw request **body**. The header that identifies *which shop* the webhook belongs to is never part of the signed bytes, so it can be freely rewritten without invalidating the HMAC check.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Registry.process` validates the request solely against that signable string: [2](#0-1) 

`HmacValidator.validate` computes the HMAC purely from `to_signable_string` (the body) and compares it to the `hmac-sha256` header — it never touches `shop`, `topic`, or any other header: [3](#0-2) 

Meanwhile, `shop` is read straight from the unauthenticated header: [4](#0-3) 

and that value is forwarded verbatim to the app's handler as the tenant identity in `WebhookMetadata`: [5](#0-4) [6](#0-5) 

This is exactly the bug class described in the external report ("bytes verified versus bytes parsed" — an identity field that is *acted upon* is not covered by the cryptographic check). The equality that should hold is:

`shop used to authorize/attribute the webhook == shop covered by the verified HMAC bytes`

but in this gem it is actually:

`shop used to attribute the webhook (Request#shop, header value) != bytes covered by HmacValidator (raw_body only)`

**Exploit path (unprivileged internet user, no leaked secret needed):** An attacker who has installed the target app on their own store (a normal, unprivileged merchant relationship with the app — not a privileged account on the victim's shop) can trigger a genuine Shopify webhook for their own store. This produces a *validly signed* `(raw_body, hmac)` pair, since the HMAC key is the app's own `client_secret` and Shopify signs it correctly for that request. The attacker then replays this exact `raw_body`/`hmac-sha256` pair to the app's webhook endpoint while substituting the `shop-domain` header with the victim shop's domain. `HmacValidator.validate` still passes because it never inspects the header, only the body bytes. `Registry.process` proceeds and calls the handler with `WebhookMetadata#shop` set to the victim's domain, even though the signed payload never actually originated from, nor was signed in relation to, that shop.

### Impact Explanation
Any app built on this gem that uses `WebhookMetadata#shop` to decide which merchant's data/session/access token to act on (a documented, expected usage pattern of this API) can be made to process attacker-supplied webhook content under a victim shop's identity. This is a cross-tenant identity-binding break: content whose integrity is attacker-influenced (the attacker fully controls the body of the webhook fired for their own installation) is attributed to an unrelated tenant purely because of an unauthenticated header. This satisfies the "cross-tenant access" criterion for High/Critical impact, since the app's per-shop authorization decisions can be forced to key off a spoofed identity.

### Likelihood Explanation
Requires only a free/normal installation of the target app on an attacker-controlled shop (no leaked credentials, no TLS interception, no social engineering) plus the ability to send an arbitrary HTTP request with the captured body/HMAC pair and a modified header — well within the "unprivileged internet user" threat model defined for this scan.

### Recommendation
Include the shop-identifying header (and ideally `topic`/`webhook_id`) inside the bytes covered by the HMAC, or independently bind/verify `shop-domain` against a value that Shopify signs (or against a known/pre-registered shop for that installation) before trusting it in `WebhookMetadata`. At minimum, document and enforce that consumers must not treat the unauthenticated `shop-domain` header as a trust boundary on its own.

### Proof of Concept
1. Install the target Shopify app on attacker-owned shop `attacker-shop.myshopify.com`.
2. Trigger any subscribed webhook topic (e.g., `orders/create`) on that shop; capture the raw POST body and the `X-Shopify-Hmac-Sha256` header — this is a validly-signed pair produced by Shopify using the app's real `client_secret`.
3. Replay the exact same body and `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate` (called from `Registry.process`) succeeds because it only checks `raw_body` against the HMAC — the header substitution is invisible to it. [7](#0-6) 
5. The app's `WebhookHandler#handle` receives `WebhookMetadata` with `shop == "victim-shop.myshopify.com"`, causing the app to act on attacker-controlled data attributed to the victim tenant.
