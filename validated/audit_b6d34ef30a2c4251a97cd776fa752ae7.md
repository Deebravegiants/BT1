### Title
`RelayPayload` state-resend bypasses source-identity check - (File: `orb-relay-client/src/client.rs`)

### Summary
Orb-Relay client authenticates a whole relay session (via `Auth::Token`/`Auth::ZKP` and `src_id`/`dst_id`) but then, inside the per-message dispatch loop, performs an unauthenticated, message-type-driven action: if the incoming payload matches `self_serve::app::v1::RequestState`, the client immediately re-sends its cached `self.last_message` — without checking whether the message's `src.id` actually equals the expected counterpart (`self.config.dst_id`). This mirrors the tx.origin analog in the report: an action (resending previously sent state) is authorized based on message *shape*, not on a verified binding to the party that is supposed to be allowed to trigger it.

### Finding Description
The relay stream handler distinguishes two kinds of incoming payloads: it either resends the cached last message when the payload is a `RequestState`, or checks `src.id != self.config.dst_id` and drops/handles the message accordingly for every other payload type: [1](#0-0) 

```
message = response_stream.next() => {
    match message {
        Some(Ok(RelayConnectResponse {
            msg: Some(relay_connect_response::Msg::Payload(RelayPayload {
                src: Some(src), dst, seq, payload: Some(payload),
            })),
        })) => {
            if self_serve::app::v1::RequestState::matches(&payload).is_some() {
                sender_tx.send(self.last_message.clone()).await...
            } else if src.id != self.config.dst_id {
                tracing::error!("Skipping received message from unexpected source: ...");
            } else {
                self.handle_message(...).await?;
            }
        }
```

The `src.id != self.config.dst_id` identity check — the only place in the loop that verifies the sender is the expected counterpart entity — is skipped entirely for the `RequestState` branch. `src` is destructured but never consulted for that branch. Any relay-routed peer able to deliver a payload matching the `RequestState` shape (this only requires framing an `Any` whose `type_url`/fields decode into `self_serve::app::v1::RequestState`, as validated purely by `PayloadMatcher::matches`) causes the client to re-emit `self.last_message` on the wire, regardless of which entity actually sent it.

`self.last_message` holds whatever was last sent by this client (Orb→App or App→Orb), set unconditionally on every outgoing send: [2](#0-1) 

This state channel is used to drive the self-serve signup flow (`StartCapture`, `AnnounceOrbId`, `CaptureStarted/Ended`, `SignupEnded`, etc.), i.e. exactly the kind of signup/identity-binding state the "Reject … no-impact analogs" rule cares about, since it is what synchronizes which app/session is currently paired with which Orb for a signup.

### Impact Explanation
Because the resend path bypasses the `src.id` equality check, an entity other than the expected paired counterpart can, by sending a `RequestState`-shaped message, force the client to re-transmit its most recent state message. Depending on relay routing/broadcast semantics, this can cause state belonging to one signup session to be replayed toward, or in response to, a party that was never validated as the legitimate `dst_id` for that session — a cross-signup state bleed / misattribution risk analogous to the tx.origin trust bypass in the report (an action gets executed based on an unverified identity assumption instead of the one true authorization check that exists elsewhere in the same function).

### Likelihood Explanation
The relay server sits between Orb and App and mediates message delivery; the client-side code explicitly anticipates and must defend against messages "from unexpected source" (hence the existing `src.id != self.config.dst_id` check for all other payload types), which signals that the client does not otherwise fully trust relay-delivered `src` fields to be pre-filtered on delivery. The `RequestState` branch, however, omits this defense, so the likelihood is directly tied to whether the relay/session-routing layer independently guarantees message provenance for every payload delivered to a given stream — something not established purely from this client's code, and the same file's explicit source check for other payload types suggests it is not assumed.

### Recommendation
Move the `src.id != self.config.dst_id` check before the `RequestState::matches` branch so it applies uniformly to all incoming payloads, i.e. only resend `last_message` when the request also comes from the verified `dst_id` counterpart. This restores a single, consistent authorization point for all relay-driven state actions rather than one that a specific message type can bypass.

### Proof of Concept
1. Establish (or gain access to) a relay-routed source entity whose `id` differs from the client's configured `dst_id`.
2. Send a `RelayPayload` whose `payload` is an `Any` decodable as `self_serve::app::v1::RequestState` (either wrapped in `self_serve::app::v1::W` or as the bare message type), with any `src.id`.
3. Observe that the client's stream handler at `orb-relay-client/src/client.rs:436-440` matches on `RequestState` first and calls `sender_tx.send(self.last_message.clone())`, resending the cached last outgoing message — without ever reaching the `src.id != self.config.dst_id` check that governs every other message type in the same match arm.
