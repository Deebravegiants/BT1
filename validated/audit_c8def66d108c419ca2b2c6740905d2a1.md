The code confirms the claim exactly as described. The suffix check has no dot-boundary enforcement, so `evil-ethereum.org` would satisfy `strings.HasSuffix("evil-ethereum.org", "ethereum.org")`. This does require operator misconfiguration (a wildcard `CORSAllowedOrigins` entry), but the rules state misconfiguration-only issues should be rejected — however here, wildcard CORS is a documented/supported feature (confirmed by the test file), not truly a misconfiguration outside the norm; it's a logic bug in how the supported feature is implemented. This is analogous to accepted CORS-wildcard-bypass bug classes and does not require any operator/admin/host access to *exploit* — only requires an operator to opt into wildcard usage, which is a normal, intended feature usage, not privilege escalation. The exploit itself is purely from an unprivileged network client (attacker's malicious webpage), matching the required impact category (gateway request impersonation / allowlist bypass).

Audit Report

## Title
Overly Permissive CORS Wildcard-Origin Matching via Improper Domain-Suffix Check - ([File: core/services/gateway/network/httpserver.go])

## Summary
The `isAllowedOrigin` function's wildcard host matching in `core/services/gateway/network/httpserver.go` uses `strings.HasSuffix(originHost, allowedHost)` after stripping the `*.` prefix, without requiring a `.` boundary before the matched suffix. This allows a malicious domain that merely ends with the allowed suffix (e.g. `evil-ethereum.org` against allowed `*.ethereum.org`) to be treated as a valid subdomain, bypassing the CORS allowlist.

## Finding Description
In `isAllowedOrigin`, when an allowed entry has the `*.` wildcard prefix, the code strips the prefix and performs a raw suffix check: [1](#0-0) . This check does not verify that the character preceding the matched suffix in `originHost` is a `.`, so any string ending with the literal characters of `allowedHost` — not just true subdomains — passes. For example, `evil-ethereum.org` satisfies `strings.HasSuffix("evil-ethereum.org", "ethereum.org")`. This bypassed result is then used directly in `handleRequest` to reflect the attacker's origin into the `Access-Control-Allow-Origin` response header: [2](#0-1) . There is no other validation step (no allowlist normalization, no dot-boundary check, no exact-match fallback for the wildcard branch) that would catch this before the header is set.

## Impact Explanation
When a gateway operator configures a wildcard `CORSAllowedOrigins` entry — a supported and documented configuration pattern, as confirmed by the dedicated test `TestHTTPServer_HandleRequest_CORSEnabled_FromAllowedOriginWildcards`: [3](#0-2)  — an attacker who registers a lookalike domain sharing the literal suffix (no dot boundary needed) can have their origin reflected back in `Access-Control-Allow-Origin`. This enables cross-origin browsers on the attacker's page to read JSON-RPC responses from the gateway's user-facing endpoint that were intended to be restricted to the legitimate wildcard-matched domains, constituting a gateway request/response allowlist bypass.

## Likelihood Explanation
Exploitation requires only that the operator use a wildcard entry in `CORSAllowedOrigins` (an intended, supported feature of this code, not an unusual misconfiguration) and that an attacker register or control a domain string sharing the suffix (e.g., a cheap, commonly available hyphenated lookalike domain). No additional privilege beyond controlling a malicious webpage and getting a victim's browser to load it is required, matching the standard CORS-bypass threat model.

## Recommendation
Enforce a `.` boundary in the wildcard suffix comparison:
```go
if strings.HasPrefix(allowedHost, "*.") {
    allowedHost = allowedHost[2:]
    if originHost == allowedHost || strings.HasSuffix(originHost, "."+allowedHost) {
        return true
    }
}
```

## Proof of Concept
1. Start the gateway HTTP server with `CORSEnabled = true` and `CORSAllowedOrigins = ["https://*.ethereum.org"]`.
2. Send a POST request to the server with header `Origin: https://evil-ethereum.org`.
3. Observe the response includes `Access-Control-Allow-Origin: https://evil-ethereum.org`, because `isAllowedOrigin` returns `true` via the flawed suffix check in `core/services/gateway/network/httpserver.go` lines 185-190.
4. This can be verified by extending the existing test `TestHTTPServer_HandleRequest_CORSEnabled_FromAllowedOriginWildcards` in `core/services/gateway/network/httpserver_test.go` with an origin like `https://evil-ethereum.org` against allowed origin `https://*.ethereum.org`, and asserting that the response incorrectly includes the CORS header for the non-subdomain origin.
