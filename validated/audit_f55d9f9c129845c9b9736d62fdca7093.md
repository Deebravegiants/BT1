### Title
Webhook `shop` (and `topic`) identity is taken from unauthenticated HTTP headers that are not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop` attribute from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, but the HMAC signature that `Registry.process` validates only covers the raw request body, not the headers. This breaks the identity binding `shop-header == HMAC-authenticated-shop`, allowing a valid HMAC (computed by Shopify with the app's shared `client_secret` for a webhook the attacker legitimately receives on their own store) to be replayed with a different, victim `shop-domain` header value, causing the webhook handler to process attacker-supplied data under the wrong tenant's identity.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) . The `shop`, `topic`, `api_version`, and `webhook_id` accessors are all read directly from HTTP headers with no cryptographic binding to the HMAC: [2](#0-1) .

`Registry.process` validates only that `Utils::HmacValidator.validate(request)` succeeds (i.e., that the body's HMAC matches), and then immediately trusts `request.shop` and `request.topic` to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) . `Utils::HmacValidator.validate` computes the HMAC purely over `to_signable_string` (the body) and compares it to the `hmac` header - it never incorporates `shop`, `topic`, or any other header into the signed material: [4](#0-3) .

Since the app's `client_secret` is shared across every shop that installs the app, any shop that installs the app is a valid "unprivileged internet user" with respect to every other tenant of the same app. Such a user can capture a genuine webhook (body + valid HMAC) delivered to their own shop, then resend that exact body/HMAC pair to the app's webhook endpoint while substituting the `shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` will still report the HMAC as valid because it never looks at the shop header, while `Registry.process` will hand the (attacker-controlled) body to the app's handler labeled with the victim shop's identity. This is the "field acted on but not covered by the HMAC" analog: the code authenticates `raw_body` bytes but acts on `shop` bytes that were never signed.

### Impact Explanation
This enables cross-tenant confusion: a webhook payload can be attributed to a shop other than the one it actually originated from, without needing the app's `client_secret`, an access token, or any credential belonging to the victim shop. Any downstream logic in the host application that uses `WebhookMetadata#shop` to select which tenant's data to update (a common integration pattern explicitly supported by this gem, since `shop` is the primary field surfaced to handlers) can be tricked into applying attacker-controlled webhook data to a victim tenant's records - i.e., cross-tenant access/injection through the app's own webhook processing pipeline supplied by this gem.

### Likelihood Explanation
Exploitation requires only that the attacker be able to install the target app on their own shop (a normal, unprivileged action available to any merchant/developer) to obtain a genuinely-signed body/HMAC pair, and then be able to POST to the target's public webhook endpoint with a modified `shop-domain` header - both of which are standard capabilities of an "unprivileged internet user" as scoped by this analysis. No leaked secrets, TLS interception, or privileged accounts are needed.

### Recommendation
Bind the `shop` (and ideally `topic`/`api_version`) to the signature verification, e.g. by including the relevant Shopify headers in the HMAC-signed material (matching upstream Shopify guidance where feasible), or at minimum have `Registry.process`/`HmacValidator.validate` reject any change to the identity headers via a MAC over `"#{shop}\n#{topic}\n#{raw_body}"` instead of `raw_body` alone, so an attacker cannot reuse one shop's valid HMAC under another shop's header value.

### Proof of Concept
1. Attacker installs the vulnerable app on their own shop (`attacker.myshopify.com`), obtaining a legitimate webhook delivery with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC(client_secret, B)`.
2. Attacker crafts an HTTP POST to the app's webhook endpoint reusing body `B` and header `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses this into a `Request` object whose `shop` returns `"victim.myshopify.com"` [5](#0-4)  while `to_signable_string` still returns `B`.
4. `Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(client_secret, B) == H` and passes, because `shop` is never part of the signed content [6](#0-5) .
5. The registered handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and body `B`, even though the webhook truly originated from the attacker's own shop.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
