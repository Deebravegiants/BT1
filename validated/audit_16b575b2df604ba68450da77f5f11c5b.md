### Title
Webhook HMAC only authenticates the request body, not the `shop-domain`/`topic`/`webhook-id` headers used for tenant identification - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying fields (`shop`, `topic`, `webhook_id`, `api_version`) from raw HTTP headers, but its `to_signable_string` — the value that `HmacValidator` actually authenticates — is only the raw request body. `Registry.process` trusts the header-derived `shop` value and hands it straight to the app's webhook handler as the tenant identifier, without that value ever being covered by the HMAC signature.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0)  while `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from HTTP headers with no cryptographic binding: [2](#0-1) 

`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (i.e. the body) and compares it against the `hmac` header: [3](#0-2) 

`Registry.process` only checks this body HMAC, then immediately trusts `request.shop` (an unauthenticated header) as the tenant identity passed into the app's handler: [4](#0-3) 

This breaks the intended identity binding:
`HMAC-authenticated bytes (raw_body) == bytes used to identify the tenant (shop-domain header)`

In reality the HMAC only proves the body was produced with the app's secret; it says nothing about which shop the headers claim to be from. Any request whose `raw_body` + `hmac-sha256` pair is valid (e.g. a webhook the attacker legitimately received for their *own* shop, or any endpoint that echoes/forwards such a payload) can have its `shopify-shop-domain`, `shopify-topic`, and `shopify-webhook-id` headers freely rewritten by anyone who can reach the app's webhook endpoint — the signature check will still pass, because those headers were never part of the signed payload.

### Impact Explanation
This is a cross-tenant access/confusion vector: an app's webhook handler processes `WebhookMetadata.new(shop: request.shop, ...)` believing `shop` is authenticated by the same HMAC that Shopify used to sign the payload, when it is not. An attacker who can obtain one valid `(raw_body, hmac)` pair (trivially available to them for their own shop's webhooks, since they are a legitimate merchant who can receive real webhooks from Shopify) can replay it to the app's endpoint while substituting an arbitrary victim `shopify-shop-domain` and topic. Any host application that keys per-tenant side effects (e.g., data updates, cache invalidation, entitlement changes) off `WebhookMetadata#shop` will attribute attacker-controlled webhook data to a victim tenant, causing cross-tenant data corruption/exposure. This falls under "cross-tenant access."

### Likelihood Explanation
No `api_secret_key`, access token, or privileged access is required — only a body+HMAC pair the attacker can legitimately obtain for their own shop (any topic works, since HMAC is body-only and independent of topic/shop). The webhook endpoint is by definition internet-reachable (Shopify must be able to POST to it), so any unprivileged internet user with a valid app account/shop can mount this.

### Recommendation
Bind the header-derived identity fields into the signed payload the library verifies, e.g. include `shop`, `topic`, and `webhook_id` (not just the raw body) in `to_signable_string`, or otherwise cryptographically bind the shop domain used for dispatch to the value Shopify actually delivered for that specific webhook subscription (for example, cross-checking `request.shop` against the shop associated with the session/subscription that was registered, rather than trusting the header outright).

### Proof of Concept
1. Attacker owns/operates a real Shopify store `attacker-shop.myshopify.com` and registers the app's webhook endpoint to receive any topic (e.g. `orders/create`).
2. Shopify delivers a legitimate webhook to the app: body `B`, header `x-shopify-hmac-sha256: H` (valid HMAC of `B` under the app's secret), `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker replays the exact same `B`/`H` pair to the app's webhook endpoint but rewrites the header to `x-shopify-shop-domain: victim-shop.myshopify.com` (and optionally a different `x-shopify-topic`/`x-shopify-webhook-id`).
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` builds successfully; `Utils::HmacValidator.validate(request)` passes because it only checks `HMAC(B)` against `H`, per `to_signable_string` returning `@raw_body`: [1](#0-0) 
5. `Registry.process` invokes the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)`, causing the app to act as though the (attacker-supplied) body originated from the victim tenant: [4](#0-3)
