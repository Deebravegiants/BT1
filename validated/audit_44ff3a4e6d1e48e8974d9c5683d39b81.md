### Title
`set_epoch_length` lets governance change the BSC light client's epoch boundary while a validator set is in flight, permanently stalling (or unsoundly rotating) BSC consensus updates - (File: `modules/ismp/clients/bsc/src/pallet.rs`)

### Summary
This is the direct analog of the Symbiotic report: just as `EpochManager::setEpochDuration()` can be updated independently of the vaults/slashers that already assume a fixed epoch duration, `Pallet::<T>::set_epoch_length()` in the `ismp-bsc` light-client pallet lets `AdminOrigin` change `EpochLength` at any time, completely independent of the live `ConsensusState` (`finalized_height`, `current_epoch`, `next_validators.rotation_block`) that was computed and persisted under the *old* epoch length.

### Finding Description
The BSC consensus client's epoch length is a mutable, admin-settable storage value: [1](#0-0) 

`set_epoch_length` simply overwrites `EpochLength::<T>` (optionally resetting the consensus state) with no validation against the currently stored `ConsensusState` for the BSC client. Meanwhile, `verify_consensus` reads `epoch_length` fresh on every call and uses it to: (1) decide whether a staged `next_validators.rotation_block` should be promoted via `compute_epoch`, and (2) enforce `ensure_finalized_epoch_consistent`, both of which assume the `rotation_block`/`current_epoch`/`finalized_height` values already stored in `ConsensusState` were computed under the *same* epoch length: [2](#0-1) 

`rotation_block` itself is computed and persisted at verification time as `epoch_header.number + current_validators.len()/2` using the epoch length in effect *when that update was verified*: [3](#0-2) 

If governance changes `EpochLength` after a `NextValidators { rotation_block, .. }` has already been staged in the persisted `ConsensusState` (without resetting the consensus state), the next call to `verify_consensus` recomputes `attested_epoch`/`rotation_epoch` with the new `epoch_length`: [4](#0-3) 

Because `rotation_block` is a raw block number (not itself epoch-length-aware), and `compute_epoch` is a pure `number / epoch_length` division, changing `epoch_length` shifts every epoch boundary. This breaks the invariant the promotion/rotation logic depends on (`attested_epoch == rotation_epoch`), and likewise perturbs `ensure_finalized_epoch_consistent`'s "finalized height never runs ahead of the held validator set" check, which is keyed on `compute_epoch(finalized_height, epoch_length)` vs. `current_epoch`.

### Impact Explanation
Two outcomes are possible depending on the direction of the change:
1. **Permanent stall (freezing/DoS of message delivery)**: If the new `epoch_length` makes `attested_epoch` never equal `rotation_epoch` for any future header (or makes `ensure_finalized_epoch_consistent` reject every subsequent update as "would strand the client"), no further BSC consensus updates can ever be accepted. Since BSC state commitments (used for all `EvmHost` state proofs sourced from BSC) are gated behind this consensus client, the route from BSC to Hyperbridge becomes permanently unable to deliver messages, timeouts, or relay any state-proof-backed request — a route unable to deliver messages, which is an explicitly accepted High/Critical outcome.
2. **Unsound rotation**: Conversely, a change in `epoch_length` can cause `compute_epoch` to alias a *stale* `rotation_block` into matching a *different* `attested_epoch` than originally intended, promoting `next_validators` prematurely or on the wrong header. This is precisely the class of bug the surrounding code comment explicitly warns about (promoting a stale/retired validator set that could then get a forged `source_header`'s `state_root` accepted as a BSC state commitment) — i.e., forged message delivery / unsound state commitment.

Either outcome matches the reachable, high-severity categories in scope (route unable to deliver messages, or forged/unsound state commitment via consensus verification).

### Likelihood Explanation
This requires `AdminOrigin` (typically governance/root, reachable via a privileged/cross-chain-governance extrinsic) to call `set_epoch_length`, which is a deliberate governance action rather than something an ordinary user triggers directly. It is acknowledged as non-trivial to trigger accidentally, but the report explicitly notes the analogous Symbiotic issue was "acknowledged by the team but won't be fixed," reflecting that a legitimate operational need (BSC epoch length has in fact changed on-chain via hard forks such as Lorentz/Maxwell) creates a realistic scenario for this call to be exercised without full awareness that it can strand or corrupt in-flight rotation state. The absence of any validation against the existing `ConsensusState`'s staged rotation is a straightforward code-review-detectable root cause with concrete blast radius.

### Recommendation
`set_epoch_length` should not allow changing `EpochLength` in-place while an active `ConsensusState` has non-`None` `next_validators` staged, unless the consensus state is atomically reset/migrated in the same call. At minimum:
- Require the caller to also supply a reset `ConsensusState` (already supported optionally) whenever `epoch_length` changes, making the reset mandatory rather than optional.
- Recompute/rebase `next_validators.rotation_block`, `current_epoch`, and `finalized_height` bookkeeping consistently with the new `epoch_length` instead of leaving raw block numbers whose meaning silently shifts.
- Add an explicit check in `verify_consensus`/`ensure_finalized_epoch_consistent` that detects an epoch-length change since the last stored update and refuses to apply the old `rotation_block` under the new length until state has been re-synced.

### Proof of Concept
1. BSC client operates normally with `epoch_length = 1000`; at some epoch boundary, `verify_consensus` stages `next_validators.rotation_block = N + validators.len()/2` (per `modules/consensus/bsc/verifier/src/lib.rs` lines 176-183).
2. Before that staged rotation is enacted, `AdminOrigin` calls `set_epoch_length` with a new `epoch_length` (e.g., 2000), without resetting `consensus_state` (per `modules/ismp/clients/bsc/src/pallet.rs` lines 79-94, `consensus_state`/`consensus_state_id` are `Option`s and can be `None`).
3. The next relayed BSC consensus proof is checked in `verify_consensus`: `attested_epoch = compute_epoch(attested_number, 2000)` and `rotation_epoch = compute_epoch(next_validators.rotation_block, 2000)` are now computed against boundaries that no longer correspond to where the validator set was staged (per `modules/ismp/clients/bsc/src/lib.rs` lines 95-124).
4. Depending on the arithmetic, either: (a) no future `attested_epoch` ever equals `rotation_epoch` again, and/or `ensure_finalized_epoch_consistent` permanently rejects updates as "would strand the client," halting all further BSC consensus/state updates on Hyperbridge; or (b) the promotion condition fires on an unintended header, silently promoting a validator set out of its intended rotation boundary.

	#[pallet::storage]
	#[pallet::getter(fn epoch_length)]
	pub type EpochLength<T: Config> = StorageValue<_, u64, OptionQuery>;

	#[derive(
		Clone,
		codec::Encode,
		codec::Decode,
		DecodeWithMemTracking,
		scale_info::TypeInfo,
		PartialEq,
		Eq,
		Debug,
	)]
	pub struct UpdateParams {
		pub epoch_length: u64,
		pub consensus_state: Option<Vec<u8>>,
		pub consensus_state_id: Option<ConsensusStateId>,
	}

	#[pallet::call]
	impl<T: Config> Pallet<T> {
		/// Sets the new BSC epoch length and resets the consensus state
		#[pallet::call_index(0)]
		#[pallet::weight(<T as frame_system::Config>::DbWeight::get().reads_writes(1, 3))]
		pub fn set_epoch_length(origin: OriginFor<T>, params: UpdateParams) -> DispatchResult {
			<T as Config>::AdminOrigin::ensure_origin(origin)?;
			let host = <T as Config>::IsmpHost::default();
			EpochLength::<T>::put(params.epoch_length);
			if let Some((consensus_state_id, consensus_state)) = params
				.consensus_state_id
				.and_then(|id| params.consensus_state.map(|state| (id, state)))
			{
				host.store_consensus_state(consensus_state_id, consensus_state)
					.map_err(|_| Error::<T>::ErrorStoringConsensusState)?;
			}

			Self::deposit_event(Event::<T>::NewEpochLength { epoch_length: params.epoch_length });

			Ok(())
		}
