## Title
Session identifier trusted from raw, unsigned cookie value enables cross-tenant session hijacking - ([File: lib/shopify_api/utils/session_utils.rb])

### Summary
`ShopifyAPI::Utils::SessionUtils` derives the "current session id" for non-embedded apps (and as a fallback for embedded apps) directly from the raw `Cookie` header value with no cryptographic binding to a prior HMAC-verified OAuth callback. Because the session id format is fully deterministic and derivable from public data (the shop domain), an unprivileged caller can present a forged cookie value equal to another merchant's session id and have the host application resolve and use that merchant's stored `Session` (including its access token).

### Finding Description
`SessionUtils.current_session_id` and `cookie_session_id` return whatever value is present in the `SESSION_COOKIE_NAME` cookie, verbatim, with no signature check: [1](#0-0) [2](#0-1) 

This value is expected to equal `session.id`, which the gem itself computes deterministically from the shop domain alone for offline sessions, and from shop + user id for online sessions: [3](#0-2) 

When the OAuth callback completes, the non-embedded cookie is set to this predictable `session.id` value directly, with no HMAC or signature protecting it: [4](#0-3) 

The identity binding that should hold is:
`session_id_returned_by_cookie_session_id == session_id_derived_from_an_HMAC-verified_OAuth_callback_for_the_requesting_party`

In reality, `cookie_session_id` enforces no such binding — it is `session_id_returned_by_cookie_session_id == bytes_the_client_chose_to_send`. Since `offline_session_id(shop)` is simply `"offline_#{shop}"` and shop domains are public (`*.myshopify.com`, discoverable from the storefront), any caller can compute the exact session id string for a target merchant and submit it as their own cookie value. `current_session_id` and `cookie_session_id` will happily return it as "the" authenticated session id, which the host application then uses to look up a `Session` (containing the merchant's access token) from its session storage. This is a session id "derived from unauthenticated bytes" — the exact bug class called out for this scan.

### Impact Explanation
An unprivileged internet user who knows or guesses a target merchant's shop domain can obtain that merchant's session id for free (it is a pure string transformation of public information, not a secret), inject it as the value of their own request's session cookie, and cause the host application's session lookup (built on top of `ShopifyAPI::Utils::SessionUtils.current_session_id` / `cookie_session_id`, exactly as documented in `docs/getting_started.md`) to return the victim merchant's `Session`, including its Admin API access token. Subsequent API calls made by the attacker's request would then execute with the victim merchant's credentials — cross-tenant access and access-token theft, matching the "Critical: cross-tenant access / theft of a merchant access token" impact bucket.

### Likelihood Explanation
No secret, prior compromise, XSS, or CSRF is required — the attacker only needs to control the `Cookie` header of their own outgoing HTTP request, which is trivial. The only "gate" is guessing/knowing the victim's shop domain, which is normally public for a live e-commerce store. The construction of the id (`"offline_#{shop}"` or `"#{shop}_#{user_id}"`) is intentionally documented and stable, so no brute-forcing of a secret is required — only knowledge of the shop's domain and, for online sessions, an associated Shopify user id (often small sequential integers).

### Recommendation
Do not trust a bare client-supplied cookie value as an authoritative session identifier. Either:
- Sign/HMAC the cookie value (or store an opaque, cryptographically random session id in the cookie instead of the deterministic `shop`/`shop_user_id` string) and verify the signature in `cookie_session_id` before use, or
- Require that non-embedded/cookie-derived session ids be validated against a server-side, HMAC-verified record established during `validate_auth_callback`, rejecting cookie values that do not match a session actually created via `validate_auth_callback`.

### Proof of Concept
1. Attacker looks up the victim's public storefront domain, e.g. `victim-shop.myshopify.com`.
2. Attacker computes the offline session id exactly as the gem does: `"offline_victim-shop.myshopify.com"` (per `SessionUtils.offline_session_id`).
3. Attacker sends a request to the host application's protected endpoint with `Cookie: shopify_per_user_token=offline_victim-shop.myshopify.com` (cookie name from `SessionCookie::SESSION_COOKIE_NAME`).
4. The host app calls `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)`, which returns `"offline_victim-shop.myshopify.com"` unchanged (`lib/shopify_api/utils/session_utils.rb:19-37,68-71`).
5. Host app's session storage returns the victim's stored `Session` object (containing the victim's real access token) for that id, and the attacker's request is served using the victim's credentials.
