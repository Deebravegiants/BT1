## Finding

### Title
`CallDispatcher.dispatch()` has no access control, letting anyone drain any native ETH or ERC-20 tokens the shared dispatcher holds - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher` is a shared, chain-wide utility contract reused by `IntentGatewayV2`, `HyperFungibleToken`, and `WrappedHyperFungibleToken` to execute arbitrary predispatch/postdispatch calls on behalf of users. It exposes an unrestricted `receive()` and an unrestricted `dispatch()` function that lets the caller specify arbitrary `to`/`value`/`data` for any number of external calls. This is the same root-cause pattern as the NestedFactory finding: an unrestricted `receive()` combined with a function that lets anyone consume the contract's balance for their own benefit.

### Finding Description
`CallDispatcher` accepts ETH unconditionally: [1](#0-0) 

and `dispatch()` is a public, unauthenticated entry point that executes attacker-supplied `Call[]` with attacker-chosen `to` and `value`, drawing from the dispatcher's own balance: [2](#0-1) 

There is no check restricting `msg.sender` of `dispatch()` to a specific gateway (e.g. `IntentGatewayV2`), and no restriction on `receive()`'s sender either. In normal operation, native tokens and ERC-20s transiently sit in the `CallDispatcher` while `IntentGatewayV2.placeOrder`/`fillOrder` (and `HyperFungibleToken`/`WrappedHyperFungibleToken` calldata execution) stage funds there before running a predispatch/postdispatch `Call[]`: [3](#0-2) 

Because `dispatch()` has no gateway-only guard, any ETH or approved/transferred ERC-20 balance the dispatcher is holding at any point — whether from an accidental direct transfer, unconsumed dust left over from a partially-executed predispatch call, or the brief holding window between the gateway funding the dispatcher and the dispatcher's own `dispatch()` call completing — can be swept by an unrelated third party who simply calls `CallDispatcher.dispatch()` directly with a `Call` that sends the balance to an address they control (any address with non-zero `extcodesize`, trivially satisfied by deploying a one-line receiver contract).

This mirrors the reported NestedFactory bug exactly: an unrestricted `receive()` plus a downstream function that lets any caller redirect the contract's balance without verifying provenance of the funds.

### Impact Explanation
Since `CallDispatcher` is documented and deployed as a shared, reusable utility across multiple apps on a chain (`IntentGatewayV2`, `HyperFungibleToken`, `WrappedHyperFungibleToken` all reference "existing `CallDispatcher` deployments"), any native-token dust left behind by one app's flow (e.g., a predispatch swap that doesn't consume 100% of forwarded value, or a user/tool mistakenly sending ETH to the dispatcher address) is not scoped to that app or that order — it becomes a shared, permissionless honeypot. Any external actor can drain it at will, resulting in direct theft of funds that rightfully belonged to a user or to the protocol (as `DustCollected` accounting in `IntentGatewayV2` assumes such dust is later attributable/sweepable by the gateway, not by arbitrary third parties).

### Likelihood Explanation
High. No special conditions are required beyond the dispatcher holding any non-zero native (or approved/transferred token) balance at any point in time — a state that is a normal, expected byproduct of `IntentGatewayV2`'s predispatch/postdispatch flows (see the "dust" and balance-sweep logic in `placeOrder`/`fillOrder` at [4](#0-3) ) and of `WrappedHyperFungibleToken`/`HyperFungibleToken` calldata execution via the same dispatcher. Any user monitoring the dispatcher's balance can call `dispatch()` at any time with no privilege check.

### Recommendation
Restrict `CallDispatcher.dispatch()` to only be callable by authorized/registered gateway contracts (e.g., an allowlist of gateway addresses set at deployment or via governance), and/or restrict `receive()` similarly to only accept ETH from those same authorized senders — analogous to the recommended `require(msg.sender == address(weth), ...)` pattern in the original report. Additionally, `CallDispatcher` should not retain any balance across transactions; each `dispatch()` invocation should verify/enforce zero leftover balance for the assets it was funded with, or immediately sweep any residual balance back to the calling gateway/caller rather than leaving it available to be claimed by unrelated third parties.

### Proof of Concept
1. Any transaction (accidental transfer, or an `IntentGatewayV2` predispatch call that doesn't fully consume its native-value leg) leaves ETH sitting in the shared `CallDispatcher` contract at address `D`.
2. An attacker deploys a trivial contract `A` with a `receive()` function.
3. The attacker calls `CallDispatcher(D).dispatch(abi.encode([Call({to: A, value: D.balance, data: ""})]))` directly — no `msg.sender` restriction blocks this call.
4. The dispatcher forwards its entire native balance to `A`, which the attacker fully controls, completing the theft of any funds — whether they belonged to the protocol (dust) or another user (accidentally sent or transiently escrowed).

```text
    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
```
