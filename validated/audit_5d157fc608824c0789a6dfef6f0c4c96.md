### Title
Webhook `shop-domain` header is trusted for tenant identification without being covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by HMAC-verifying the raw request body, then reads the tenant identity (`shop`) from an HTTP header that is never included in the signed material. This breaks the binding `bytes_verified == bytes_used_for_tenant_identity`, allowing any holder of one validly-signed webhook payload to relabel it as belonging to an arbitrary shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `hmac` accessor reads the `hmac-sha256` header, and the `shop` accessor independently reads the `shop-domain` header: [2](#0-1) 

`Registry.process` validates the request using only this body-based HMAC, then immediately forwards `request.shop` (the unauthenticated header value) to the app's handler as the tenant identity for the event: [3](#0-2) 

`Utils::HmacValidator.validate` recomputes the HMAC over `verifiable_query.to_signable_string` (i.e. the raw body only) and compares it to the `hmac` header using `OpenSSL.secure_compare`: [4](#0-3) 

Because `shop-domain` is never part of the signed string, the equality the code implicitly relies on — "the shop whose secret produced this HMAC" == "the shop named in the `shop-domain` header" — does not hold. Any party capable of obtaining one validly HMAC-signed webhook body for a given topic (e.g. from their own shop, which any merchant/app-installer legitimately receives) can replay that exact body with the `x-shopify-shop-domain` (or `shopify-shop-domain`) header changed to a victim shop's domain. `Utils::HmacValidator.validate` will still return `true`, because it never inspects the header, and the app's webhook handler will process/attribute the event to the victim shop.

This is the direct structural analog of the reported bug class ("a field acted on but not covered by the HMAC" — Firedancer's `parent_off` field is used to compute shred lineage but is not covered by the shred's validation, here the `shop-domain` field is used to compute tenant identity but is not covered by the webhook's HMAC).

### Impact Explanation
Apps built on this gem typically use `WebhookMetadata#shop` to look up the merchant record, update per-shop state, or trigger shop-scoped side effects (e.g., marking a shop as uninstalled on `app/uninstalled`, updating subscription/billing state, or writing order/customer data under a shop key) based solely on this field, since the gem provides no separate authenticated shop check. Because the `shop-domain` header is attacker-controllable independent of the signature, an attacker can cause an app to process a valid Shopify-signed payload under an arbitrary, victim shop's identity — a cross-tenant identity confusion. Depending on the handler logic this can range from data corruption/spoofed events for another tenant up to state changes (e.g., forcing marks of install/uninstall, scope, or subscription events) being applied to a shop the attacker does not control.

### Likelihood Explanation
Exploitation requires the attacker to have at least one genuine HMAC-signed webhook body for the topic being targeted, which is trivial to obtain: any developer/attacker who installs the target app on their own (even free/dev) store will receive real, validly signed webhooks for standard topics (e.g. `app/uninstalled`, `orders/create` if scopes allow, etc.). They can then replay that exact body to the app's webhook endpoint with a forged `shop-domain` header pointing at any victim shop. No access token, `api_secret_key`, or privileged access is required — only a normal, unprivileged relationship with the target app (installing it on an attacker-controlled store).

### Recommendation
Include the shop identity in the HMAC-protected material, or otherwise cryptographically bind the `shop-domain` header to the signed body before trusting it as the event's tenant. At minimum, `Utils::HmacValidator`/`Webhooks::Request` should not expose `shop` as authenticated data derived independently of the signature; instead, the shop should be derived from Shopify's per-shop webhook signing behavior in a way that lets `Registry.process` verify that the HMAC was computed with the secret associated with the claimed `shop-domain`, not merely with the app's single global `api_secret_key`.

### Proof of Concept
1. Install the target app on attacker-owned dev store `attacker.myshopify.com`; capture any webhook Shopify delivers, e.g. `orders/create`, noting `raw_body`, `x-shopify-hmac-sha256`, and `x-shopify-topic`.
2. Replay the exact same `raw_body` and `x-shopify-hmac-sha256` to the app's webhook endpoint, but set `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Utils::HmacValidator.validate(request)` returns `true` because it only checks the raw body against the HMAC computed with the app's `api_secret_key` — see [5](#0-4)  and [1](#0-0) .
4. `Registry.process` invokes the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` — see [3](#0-2)  — causing the app to process attacker-supplied data as if it belonged to `victim-shop.myshopify.com`.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

        end
