## Analysis

The bug class in the report is: a downstream operation applies a limit/constraint (`AlchemistV2._checkMintingLimit`) that the calling contract (`Vault.register_deposit`) never accounts for, so an otherwise-valid, already-computed operation reverts unconditionally and the surrounding transaction (funding a project) is lost with no self-serve retry path.

The closest reachable analog in Hyperbridge is in the ISMP message-execution path, where a per-message fee transfer with an unrelated balance constraint (`ExistenceRequirement::KeepAlive`) can revert an entire batch of otherwise valid, already proof-verified messages because `handle_unsigned` is wrapped in `#[frame_support::transactional]`.

### Title
Unrelated fee-transfer failure in `WeightFeeHandler::on_executed` reverts an entire batch of validly-proven ISMP messages - (File: `modules/pallets/ismp/src/fee_handler.rs`)

### Summary
`pallet_ismp::Pallet::execute` processes a batch of ISMP messages, then calls `T::FeeHandler::on_executed(...)` to charge/incentivize the batch [1](#0-0) . When the configured fee handler is `WeightFeeHandler`, `on_executed` attempts a `Currency::transfer` from each message originator to the treasury using `ExistenceRequirement::KeepAlive`, and propagates any transfer failure with `?` [2](#0-1) . Because `handle_unsigned` is annotated `#[frame_support::transactional]`, any error from `execute()` — including this unrelated fee-transfer failure — rolls back the entire extrinsic, discarding every already-verified state update, consensus update, and request/response delivery in that batch [3](#0-2) .

### Finding Description
`execute()` maps proof-checked messages to results, computes their weights, and only after all of that succeeds calls the fee handler: [4](#0-3) 

`WeightFeeHandler::on_executed` never checks whether the originator can pay the fee without dropping below the existential deposit before attempting the transfer; it simply calls `C::transfer(..., ExistenceRequirement::KeepAlive)` and bubbles the error up with `?`: [2](#0-1) 

This mirrors the reported pattern exactly: the amount/eligibility check that determines whether the downstream call will succeed (an account's spendable balance above ED, analogous to `AlchemistV2`'s dynamic minting limit) is evaluated by a completely separate subsystem, and the calling code (`execute`/`handle_unsigned`) never accounts for it before committing to the batch. Since `handle_unsigned` is `#[frame_support::transactional]`, a single message's fee-payer having insufficient balance causes `Error::<T>::ErrorChargingFee` and reverts **every** message in that unsigned call — including unrelated, fully-verified consensus updates, POST/GET requests, and responses that had nothing to do with the failing account.

### Impact Explanation
Because `handle_unsigned` is the permissionless entry point any relayer uses to deliver consensus updates and cross-chain requests/responses to Hyperbridge [5](#0-4) , this failure mode blocks message delivery for the whole batch rather than just the offending message. A relayer that batches multiple unrelated requests (which is exactly the incentive design, since one proof can cover many requests) risks having legitimate, proof-verified deliveries — including consensus/state-machine updates needed to unblock other pending messages — permanently fail every time the batch is resubmitted, until the fee-payer's balance is topped up. This satisfies the "route unable to deliver messages" acceptance criterion: valid requests can be stuck non-deliverable through no fault of their own sender.

### Likelihood Explanation
Whether this is actually triggerable in production depends on which `FeeHandler` a given runtime configures. The default/mocked `MessagingRelayerIncentives::on_executed` used in the testsuite silently logs a warning on mint failure and always returns `Ok(...)`, so it is *not* affected [6](#0-5) . However, `WeightFeeHandler` is the documented, intended weight-based fee model for `pallet-ismp` deployments (shown as the canonical example config in the pallet's own docs) [7](#0-6) , and it is composable via the `#[impl_for_tuples(5)]` `FeeHandler` blanket impl, which also short-circuits on the first error with `?` [8](#0-7) . I was not able to confirm from the indexed code whether any currently-deployed Hyperbridge runtime (nexus/gargantua) actually wires `WeightFeeHandler` into production with `POLICY = true`; the runtime `ismp.rs` files reference `FeeHandler` but their concrete type parameter wasn't visible in this pass. This should be verified directly before treating likelihood as confirmed.

### Recommendation
- In `WeightFeeHandler::on_executed`, do not let a single originator's insufficient balance abort the whole batch: use `ExistenceRequirement::AllowDeath`, or catch the transfer error per-message (log/skip, matching the `MessagingRelayerIncentives` pattern) instead of propagating it with `?`.
- Alternatively, pre-check `C::free_balance(originator) >= fee + ED` before attempting the transfer, and skip/degrade gracefully (e.g., treat as fee-exempt or emit an event) rather than failing the extrinsic.
- More generally, avoid embedding `#[frame_support::transactional]` around fee-charging logic that has failure modes independent of message/proof validity, or split fee charging so it cannot roll back already-verified message state.

### Proof of Concept
1. Deploy a runtime with `pallet_ismp::Config::FeeHandler = WeightFeeHandler<AccountId, Balances, WeightToFee, TreasuryPalletId, true>` (the documented configuration).
2. Have an account `A` sign and relay a batch via `handle_unsigned` containing (a) a valid consensus/state update message and (b) a request message it signed, where `A`'s free balance is just above the existential deposit but less than `fee + ED`.
3. `execute()` processes both messages successfully (proofs are valid), then calls `WeightFeeHandler::on_executed`, which attempts `Currency::transfer(A, treasury, fee, KeepAlive)`.
4. The transfer fails (would reduce `A` below ED), `on_executed` returns `Err`, `execute()` maps this to `Error::<T>::ErrorChargingFee`, and because `handle_unsigned` is transactional, the entire extrinsic reverts — including the valid consensus/state update that had nothing to do with account `A`.
5. Resubmitting the same batch fails identically until `A`'s balance changes, permanently blocking delivery of the batched messages exactly as `Vault.register_deposit` was permanently blocked by `AlchemistV2`'s minting limit in the original report.

	pub fn execute(messages: Vec<Message>) -> Result<Vec<events::Event>, Error<T>> {
		let host = Pallet::<T>::default();

		let message_results = messages
			.iter()
			.map(|msg| handle_incoming_message(&host, msg.clone()))
			.collect::<Result<Vec<_>, _>>()
			.map_err(|err| {
				log::debug!(target: "ismp", "Handling Error {:#?}", err);
				Pallet::<T>::deposit_event(Event::<T>::Errors { errors: vec![err.into()] });
				Error::<T>::InvalidMessage
			})?;

		let messages_with_weights = message_results
			.iter()
			.zip(messages)
			.map(|(result, message)| MessageWithWeight { message, weight: result.weight() })
			.collect::<Vec<_>>();

		let events = message_results
			.into_iter()
			// check that requests will be successfully dispatched
			// so we can not be spammed with failing txs
			.map(|result| match result {
				MessageResult::Request { events, .. } |
				MessageResult::Response { events, .. } |
				MessageResult::Timeout { events, .. } => events,
				MessageResult::ConsensusMessage(events) => events.into_iter().map(Ok).collect(),
				MessageResult::FrozenClient(_) => vec![],
			})
			.flatten()
			.collect::<Result<Vec<_>, _>>()
			.map_err(|err| {
				log::debug!(target: "ismp", "Handling Error {:#?}", err);
				Pallet::<T>::deposit_event(Event::<T>::Errors { errors: vec![err.into()] });
				Error::<T>::InvalidMessage
			})?;

		T::FeeHandler::on_executed(messages_with_weights, events.clone())
			.map_err(|_| Error::<T>::ErrorChargingFee)?;

	fn on_executed(
		messages: Vec<MessageWithWeight>,
		_events: Vec<IsmpEvent>,
	) -> DispatchResultWithPostInfo {
		let rate = MintPerByte::<T>::get();
		if !rate.is_zero() {
			for mw in &messages {
				let bytes = Self::message_bytes(&mw.message);
				let bytes_balance: BalanceOf<T> = (bytes as u128).saturated_into();
				let amount = rate.saturating_mul(bytes_balance);
				if amount.is_zero() {
					continue;
				}
				if let Some(relayer) = Self::relayer_for(&mw.message) {
					match T::ReputationAsset::mint_into(&relayer, amount) {
						Ok(_) =>
							Self::deposit_event(Event::ReputationMinted { relayer, bytes, amount }),
						Err(err) => log::warn!(
							target: "messaging-incentives",
							"reputation mint failed for {bytes}b: {err:?}",
						),
					}
				}
			}
		}
		Ok(PostDispatchInfo { actual_weight: None, pays_fee: Pays::No })
	}
