### Title

Unpriceable dust collateral can block liquidation and bad-debt cleanup - ([File: contracts/controller/src/positions/liquidation/plan.rs])

### Summary

A borrower can add an economically negligible collateral position whose oracle is an Aquarius LP source, then drain that LP pool below its configured `min_pool_value_wad`. Because liquidation and bad-debt cleanup require a valid price for every collateral leg, the dust leg makes those operations revert even when the remaining positions establish insolvency. This creates an unprivileged temporary, and potentially persistent, freeze of the protocol’s liquidation and cleanup paths for that account.

### Finding Description

`supply` accepts additional collateral through measured token transfers and market/flag checks; it does not require the collateral’s oracle to remain readable at entry time. [1](#0-0) 

Later, `liquidate` calls `calculate_account_risk_totals` over the full `supply_positions` map before checking `health_factor < 1` or constructing a seizure plan. [2](#0-1) 

For an `AquariusLp` or `AquariusStableLp` source, the price read calculates the pool’s total WAD value and returns `InsufficientAquariusLiquidity` when it is below the configured floor. [3](#0-2) 

The repository’s regression test demonstrates the resulting behavior: adding a dust collateral leg with a stale or otherwise unusable feed causes both `liquidate` and `clean_bad_debt` to revert, and the same liquidation succeeds after the price becomes usable again. [4](#0-3) 

### Impact Explanation

While the LP oracle remains below its liquidity floor, no liquidator can complete the account valuation required by `liquidate`, so collateral cannot be seized even if the account is deeply undercollateralized. The same all-position valuation blocks `clean_bad_debt`, including the owner-forced cleanup path, because cleanup still requires readable prices for required positions. [5](#0-4) 

The attacker can keep borrowed assets outstanding while interest accrues, delaying lender recovery and allowing debt to grow beyond the value obtainable from collateral. If the attacker controls enough LP shares and does not restore liquidity, the account can remain uncleanable until governance changes the oracle configuration or another recovery mechanism is introduced.

### Likelihood Explanation

The attack requires no privileged controller, pool, governance, or oracle role. The attacker opens their own account, supplies an ordinary collateral position and a minimum admissible amount of a listed Aquarius LP collateral, borrows against the ordinary collateral, and then withdraws sufficient liquidity that they control from the referenced Aquarius pool to push its total value below `min_pool_value_wad`.

The main precondition is control of enough LP liquidity to cross the configured floor, or another way to make the LP source unavailable. Once established, every liquidation or cleanup attempt reverts, while restoring liquidity makes the account actionable again.

### Recommendation

Do not make liquidation and cleanup dependent on pricing economically negligible collateral legs.

A practical fix is to derive an upper bound for an unpriceable leg from its raw amount, decimals, and configured maximum sanity price. If that upper bound is below a protocol dust threshold, exclude or zero-value the leg for liquidation while still removing or socializing its shares during cleanup. For bad-debt cleanup, use the configured upper-bound collateral value conservatively: proceed only when debt still exceeds that upper bound.

Additionally, monitor LP collateral whose pool value is close to `min_pool_value_wad`, and consider requiring a valid strict price when adding a new collateral position so borrowers cannot plant dormant fragile legs during an outage.

### Proof of Concept

Assume spoke `s` lists ordinary collateral `C`, debt asset `D`, and Aquarius LP collateral `L`.

1. Attacker calls:

   ```text
   supply(
       caller = attacker,
       account_id = 0,
       spoke_id = s,
       assets = [(C, normal_amount), (L, minimum_admissible_amount)]
   )
   ```

   This creates an account holding both collateral legs; supply only measures token receipt and does not establish that `L`’s price remains usable.

2. Attacker calls:

   ```text
   borrow(
       caller = attacker,
       account_id = account,
       borrows = [(D, borrow_amount)],
       to = None
   )
   ```

   The borrow is sized near the account’s permitted limit or is followed by interest accrual or a collateral-price decline until `HF < 1`.

3. Attacker withdraws liquidity they control from the Aquarius pool referenced by `L`’s oracle until `pool_value_wad < min_pool_value_wad`.

4. Any liquidator calls:

   ```text
   liquidate(
       liquidator = liquidator,
       account_id = account,
       debt_payments = [(D, repayment_amount)],
       seize_mode = Transfer
   )
   ```

   `calculate_account_risk_totals` attempts to price `L`; `AquariusLp::read` returns `InsufficientAquariusLiquidity`, so liquidation reverts before seizure.

5. A caller invokes:

   ```text
   clean_bad_debt(
       caller = caller,
       account_id = account
   )
   ```

   Cleanup also requires the account’s collateral valuation and reverts on the same unusable dust-priced leg.

6. The attacker restores liquidity to make the LP price valid again. The same liquidation call then succeeds, demonstrating that the blocker is the negligible `L` leg rather than the debt or collateral accounting.
