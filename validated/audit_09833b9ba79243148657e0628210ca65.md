Audit Report

## Title
`run_call` reentrancy heuristic misclassifies value-transferring stipend calls as `AllowReentry` instead of `AllowNext`, defeating explicit reentrancy protection - ([File: substrate/frame/revive/src/vm/evm/instructions/contract.rs])

## Summary
In `run_call`, the match on `(value.is_zero(), gas_limit == CALL_STIPEND)` places the `(false, _) => AllowReentry` arm before the `(_, true) => AllowNext` arm, so any call with `value != 0` is classified `AllowReentry` regardless of whether it also carries the 2300-gas stipend. This means the intended `AllowNext` protection—documented as the explicit compensating guard for the fact that revive's gas scale doesn't guarantee stipend-gas exhaustion the way Ethereum's does—never applies to value-transferring calls, which is exactly the case (`.transfer`/`.send`, or `call{value: v, gas: 2300}`) it was designed to protect.

## Finding Description
The code in `run_call` is confirmed exactly as described:

```rust
let (add_stipend, reentracy) =
    match (value.is_zero(), gas_limit.try_into().is_ok_and(|limit: u64| limit == CALL_STIPEND))
    {
        (false, _) => (true, ReentrancyProtection::AllowReentry),
        (_, true) => (true, ReentrancyProtection::AllowNext),
        (_, _) => (false, ReentrancyProtection::AllowReentry),
    };
``` [1](#0-0) 

Because Rust matches arms top-down and `(false, _)` is listed first, every call with `value > 0` (`value.is_zero() == false`) is captured by that arm before the `(_, true)` arm can be reached — the `AllowNext` arm is therefore only reachable when `value.is_zero()` is `true`, i.e., precisely when the value-transfer protection is least needed. This is the reverse of the intent stated in the `AllowNext` doc comment in `exec.rs`, which says it exists for "calls that transfer value but restrict gas so that the callee only has a stipend gas amount," since "due to gas scale differences that guarantee does not automatically hold in revive and we enforce it explicitly here." [2](#0-1) 

`ReentrancyProtection::AllowReentry` is explicitly documented as "Don't activate reentrancy protection" — the weakest setting, contrasted with `Strict` and `AllowNext`. [3](#0-2) 

This is called from `call<E: Ext>` for the EVM `CALL` opcode, which is the opcode used for `.transfer`/`.send` (value-transfer, gas-limited to 2300 by solc) as well as arbitrary low-level `call{value: v, gas: 2300}(...)`. [4](#0-3) 

## Impact Explanation
This is a genuine logic defect that inverts the intended security control for a documented, purpose-built reentrancy protection. As shown in the code, `AllowReentry` disables the reentrancy check entirely for the target callee, whereas `AllowNext` was specifically added to compensate for the fact that Ethereum's 2300-gas physical stipend exhaustion guarantee does not automatically translate to revive's gas/weight scale. Any value-transferring call using the stipend heuristic (real `.transfer()`/`.send()`, or a `call{value: v, gas: 2300}(...)`) receives no reentrancy protection instead of the intended `AllowNext` guard, undermining the checks-effects-interactions safety net that Solidity developers rely on when using `.transfer`/`.send`. If a malicious receiving contract's `receive()`/fallback attempts a reentrant call back into the caller during such a value transfer, the reentrancy-denial check that should trigger (per `PrecompileExt::call`'s `allows_reentry` gating) will not activate, and the only remaining barrier is however much weight the stipend actually buys at revive's gas scale — not a guaranteed protection.

## Likelihood Explanation
The precondition set is realistic and requires no privileged access: any contract that legitimately performs `.transfer(amount)`/`.send(amount)` (an extremely common Solidity idiom for paying out value) to an attacker-controlled address, or any caller issuing a low-level `call{value: v, gas: 2300}(...)`, triggers this code path. This is reachable through ordinary signed extrinsics invoking revive-EVM contracts — no governance, admin, or root access needed.

## Recommendation
Restructure the match so the gas-stipend heuristic is evaluated independently of `value.is_zero()`, e.g., check `gas_limit == CALL_STIPEND` first and assign `AllowNext` regardless of `value`, then handle the remaining `value != 0` / `value == 0` cases separately for `add_stipend`/`AllowReentry` decisions. This ensures any call carrying the 2300-gas stipend is classified `AllowNext` per the documented intent, whether or not it also transfers value.

## Proof of Concept
1. Add a Solidity fixture with a victim contract that calls `target.call{value: v, gas: 2300}(data)` (or `.transfer(v)`) to an attacker contract.
2. The attacker's `receive()`/fallback attempts a reentrant call back into a state-mutating function on the victim (e.g., a withdrawal or counter update).
3. Instrument/trace `run_call` to confirm the `ReentrancyProtection` variant selected for the `value > 0`, `gas_limit == 2300` case is `AllowReentry` (as the code shows) rather than `AllowNext`.
4. Assert that the reentrant call is not blocked by `ReentranceDenied` and that caller state is mutated during the outer call, in contrast to the behavior if `AllowNext` were correctly applied (in which case `self.top_frame_mut().allows_reentry = false` would be set after the frame push, blocking the callee's nested calls back into the caller per the check in `exec.rs`'s call handling).

pub fn call<E: Ext>(interpreter: &mut Interpreter<E>) -> ControlFlow<Halt> {
	let [gas_limit, to, value] = interpreter.stack.popn()?;
	let to = to.into_address();
	let has_transfer = !value.is_zero();
	if interpreter.ext.is_read_only() && has_transfer {
		return ControlFlow::Break(Error::<E::T>::StateChangeDenied.into());
	}
	let (input, return_memory_range) = get_memory_in_and_out_ranges(interpreter)?;
	let scheme = CallScheme::Call;

	run_call(
		interpreter,
		to,
		gas_limit,
		interpreter.memory.slice(input).to_vec(),
		scheme,
		value,
		return_memory_range,
	)
}
