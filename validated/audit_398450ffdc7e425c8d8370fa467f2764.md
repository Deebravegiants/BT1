### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing shop-identity spoofing in `process` - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, never the `shop-domain`/`topic`/`webhook-id`/`api-version` headers, so `Utils::HmacValidator.validate` only proves that *some* HMAC-signed body was produced with the app's shared `api_secret_key` — it proves nothing about which shop the body belongs to. `Registry.process` nonetheless treats `request.shop` (an unauthenticated header value) as trusted tenant identity and hands it straight to the host app's handler.

### Finding Description
The HMAC binding breaks the equality: `shop authenticated == shop attributed to the webhook payload`.

- `to_signable_string` signs only `@raw_body`: [1](#0-0) 

- `shop` is read straight from an HTTP header, with no cryptographic tie to the signed bytes: [2](#0-1) 

- `HmacValidator.validate`/`validate_signature` only checks `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)` — i.e., against the body only: [3](#0-2) 

- `Registry.process` validates the HMAC and then forwards the unauthenticated `request.shop` header value directly into `WebhookMetadata`, which the host app's handler is documented to trust as the originating shop: [4](#0-3) 

- The gem's own documentation instructs handlers to key persistence/business logic off `data.shop` without any caveat that it is unauthenticated: [5](#0-4) 

Because `api_secret_key` is shared across every shop that has the app installed (not per-tenant), any attacker who can install the app on their own store (an ordinary, unprivileged action — public apps can be installed by anyone) can:
1. Trigger a real webhook from Shopify for their own shop (e.g., `orders/create`) and capture the genuine HTTP request Shopify sends, including a *valid* `x-shopify-hmac-sha256` for that raw body.
2. Replay that exact request to the app's webhook endpoint, but with the `x-shopify-shop-domain` header rewritten to the victim's shop domain.
3. `HmacValidator.validate` still returns `true`, because the signature only ever covered the raw body, which is unchanged.
4. `Registry.process` calls the handler with `WebhookMetadata#shop` set to the victim's domain, even though the payload actually originated from the attacker's own store.

This is exactly the bug class flagged by the report: "operations executed on a field that is not covered by the integrity check," here manifesting as a shop-authenticated-vs-shop-attributed mismatch rather than a stake-accounting mismatch.

### Impact Explanation
If the host application does what the gem's own documentation recommends — key a background job, database write, or notification off `data.shop` — an attacker can inject forged webhook events attributed to any other merchant using this app, corrupting or exfiltrating cross-tenant state (e.g., causing order/product data belonging to the attacker's shop to be written into or trigger side effects for a victim shop's records). This meets the "Critical – cross-tenant access" bar because the boundary crossed is the tenant (shop) boundary, and the only prerequisite is the ability to install the app on a shop the attacker controls — no leaked credentials, no `api_secret_key`, no privileged account.

### Likelihood Explanation
High. Installing a Shopify app on one's own store is unprivileged and requires no special access. Capturing your own shop's outbound webhook requests (they arrive at whatever endpoint you configure) is trivial, and replaying an HTTP request with one header changed requires no cryptographic knowledge, since the header is deliberately excluded from the signed payload.

### Recommendation
Bind the shop identity into the integrity check, not just the body:
- Include the `shop-domain` (and ideally `topic`/`webhook-id`) header in the bytes that are HMAC-verified, or
- Independently verify that `request.shop` corresponds to a shop with an active, previously-established session/installation for this app before invoking the handler, and
- Update `docs/usage/webhooks.md` to explicitly document that `data.shop` alone is not proof of origin unless cross-checked against a known installation.

### Proof of Concept
```ruby
# 1. Attacker owns "attacker-shop.myshopify.com" with the app installed.
# 2. Attacker triggers "orders/create" on their own store; Shopify sends:
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(
    OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), api_secret_key, raw_body)
  ),
  "x-shopify-shop-domain" => "attacker-shop.myshopify.com",
}
# raw_body and hmac are valid and unmodified.

# 3. Attacker replays the identical request but swaps the shop header:
forged_headers = headers.merge("x-shopify-shop-domain" => "victim-shop.myshopify.com")

ShopifyAPI::Webhooks::Registry.process(
  ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
)
# HmacValidator.validate returns true (only raw_body is checked),
# and the handler is invoked with data.shop == "victim-shop.myshopify.com".

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
