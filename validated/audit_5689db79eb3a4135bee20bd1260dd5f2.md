### Title
Webhook `shop-domain` (and `topic`/`webhook-id`) header is trusted without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature only over the raw request body, but `Registry.process` uses the unauthenticated `shop-domain` header to attribute the webhook to a tenant. This breaks the intended binding "HMAC-verified payload == payload for the shop the handler believes it is processing," analogous to the report's core defect: a value acted upon by downstream logic that is not covered by the same integrity check used to authorize it.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, and `#webhook_id` are read directly from HTTP headers, which are never included in the signable string and therefore are not part of the HMAC computation: [2](#0-1) 

`Registry.process` validates the HMAC over the body only, then immediately trusts `request.shop` and `request.topic` (both header-derived, unauthenticated) to dispatch to a handler and build `WebhookMetadata`: [3](#0-2) 

Because `HmacValidator.validate` only calls `to_signable_string` (the body) against the `hmac` header, the check proves the body is authentic Shopify content signed with `api_secret_key`, but it proves nothing about which shop the headers claim it originated from: [4](#0-3) 

**Attack sequence:**
1. Attacker installs the app on their own shop (or captures/replays a legitimately delivered webhook they control, e.g., from a shop where they have installed the app).
2. Attacker (or Shopify, on the attacker's shop) delivers a webhook with a valid `X-Shopify-Hmac-Sha256` for a body the attacker fully controls (e.g., `orders/create` with attacker-chosen JSON).
3. Attacker replays this exact `(raw_body, hmac)` pair to the app's webhook endpoint, but substitutes `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and optionally a different `topic`/`webhook-id`).
4. `HmacValidator.validate` still succeeds because it only checks the body bytes against the HMAC — the shop header was never part of the signed data.
5. `Registry.process` calls the handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: attacker_body, ...)`, so the host application's handler logic (e.g., updating local order/customer/product state keyed by `shop`) operates on data purportedly from `victim-shop` while an attacker fully controls the body content.

This equality is broken: `hmac_verified_body == body_intended_for(shop)`. The gem verifies the byte integrity of the body but never binds it to the shop asserted in the (unauthenticated) header, so any shop identifier accompanying a validly-HMAC'd body can be substituted.

### Impact Explanation
This is a cross-tenant integrity issue: an attacker with access to any one legitimate webhook (from their own shop install) can forge webhook deliveries that the host application attributes to an arbitrary victim shop, with attacker-controlled body content. Depending on how the host app's webhook handlers use `WebhookMetadata#shop` (commonly to select the tenant record to update), this enables cross-tenant data corruption/confusion driven entirely by unprivileged internet-reachable input — matching the "cross-tenant access" class of impact.

### Likelihood Explanation
Medium-High. The attacker only needs one authentic `(raw_body, hmac)` pair, obtainable trivially by installing the app on an attacker-controlled dev/test shop and triggering any webhook event, since `api_secret_key` is shared across all shops using the app (it's not shop-specific). No access to the victim's credentials, session, or access token is required.

### Recommendation
Include the shop domain (and ideally topic/webhook id/api-version) in the HMAC-signed material, or otherwise cryptographically bind the header-derived identifiers to the body before trusting them. Concretely, update `Request#to_signable_string` (or add a separate verification step in `Registry.process`) to incorporate `shop-domain`, e.g. by validating that the shop matches an expected/looked-up value independent of the untrusted header, or by requiring the host app to cross-check `shop` against a known installed-shop list before acting on `WebhookMetadata`.

### Proof of Concept
```ruby
# Attacker has genuinely installed the app on their own shop "attacker.myshopify.com"
# and receives a real webhook delivery for it:
raw_body = '{"id": 1, "malicious": "payload"}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)

# Attacker replays the exact (raw_body, hmac) pair, changing only the shop-domain header:
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac),
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # attacker-controlled value, not covered by HMAC
  "x-shopify-webhook-id" => "forged-id",
  "x-shopify-api-version" => "2024-01",
}

forged_request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

# This succeeds: HMAC validation only checks raw_body, not shop-domain
ShopifyAPI::Webhooks::Registry.process(forged_request)
# => handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: {"id"=>1, "malicious"=>"payload"}, ...))
``` [3](#0-2)  confirms `request.shop` is passed unchecked into the handler once `Utils::HmacValidator.validate(request)` passes, and that validator only signs `@raw_body` per [1](#0-0) .
