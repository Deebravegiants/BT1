Based on the code I traced, this is a real, exploitable divergence, but the attacker who can trigger it is only the caller of `processWithdrawal`/`signAndSendWithdrawalIntent` themselves (i.e., they can only shortchange or overpay against *their own* withdrawal) — the FeeExceedsAmountError guard exists only in one of two paths that reach `createWithdrawalIntents`.

### Title
`feeInclusive: true` withdrawals with `amount == feeEstimation.amount` bypass the `FeeExceedsAmountError` guard when a `feeEstimation` is supplied directly, letting PoaBridge mis-price the withdraw intent - (File: `packages/intents-sdk/src/sdk.ts`, `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`)

### Summary
`IntentsSDK.createWithdrawalIntents` computes `actualAmount = amount - feeEstimation.amount` for `feeInclusive` withdrawals with no lower-bound check, unlike `_estimateWithdrawalFee`, which guards with `FeeExceedsAmountError` when `amount <= fee.amount`. When `processWithdrawal`/`signAndSendWithdrawalIntent` is called with an explicit `feeEstimation` (bypassing `_estimateWithdrawalFee` entirely), and `amount == feeEstimation.amount`, `actualAmount` becomes `0n`, and `PoaBridge.createWithdrawalIntents` then re-adds `relayerFee` to build the `ft_withdraw` intent amount as `0 + relayerFee = relayerFee`, which is nonzero and equal to the "fee" that was supposed to make the net delivered amount zero.

### Finding Description
The invariant that should hold is: `ft_withdraw intent amount == withdrawalParams.amount` (with the bridge subtracting fee on redemption) and the amount arriving at the destination is `amount - fee`, i.e. **zero** in this edge case, not `feeEstimation.amount`.

Trace:
1. `IntentsSDK.processWithdrawal` (`packages/intents-sdk/src/sdk.ts:793-857`) has Step 1: if `args.feeEstimation != null`, it uses it directly and skips `estimateWithdrawalFee`/`_estimateWithdrawalFee` altogether [1](#0-0) . This means the `FeeExceedsAmountError` guard in `_estimateWithdrawalFee` (`sdk.ts:421-425`) is never evaluated for this call.
2. Step 2 calls `signAndSendWithdrawalIntent` → `createWithdrawalIntents` (`sdk.ts:334-372`), which computes `actualAmount = feeInclusive ? amount - feeEstimation.amount : amount` with **no** check that `amount > feeEstimation.amount` [2](#0-1) .
3. With `amount == feeEstimation.amount`, `actualAmount` becomes `0n` and is passed both to `bridge.validateWithdrawal` and into `bridge.createWithdrawalIntents` as `withdrawalParams.amount`.
4. `PoaBridge.createWithdrawalIntents` (`poa-bridge.ts:142-162`) computes the `ft_withdraw` intent amount as `withdrawalParams.amount + relayerFee` — i.e. `0 + relayerFee = relayerFee = feeEstimation.amount` [3](#0-2) .
5. `bridge.validateWithdrawal` for PoA checks `amount < minWithdrawalAmount` (skippable) but has no check that amount is zero/nonzero relative to fee [4](#0-3) , so nothing stops the zero-net-amount withdrawal from being signed.

Net effect: the signed `ft_withdraw` intent debits `relayerFee` (== `feeEstimation.amount`, the user-facing display fee) from the user's intents balance, sent to the PoA bridge for a withdrawal whose net-of-fee amount is `relayerFee - relayerFee = 0` (i.e., the bridge takes the whole debited amount as its fee and the destination receives nothing). This matches the scenario described in the question: the user is debited `feeEstimation.amount` in the withdrawn token but receives `0` at the destination — an overcharge/loss of the full displayed fee amount, with the bridge retaining the fee.

The normal path (`estimateWithdrawalFee` → `_estimateWithdrawalFee`) *does* correctly guard this exact condition (`amount <= fee.amount` throws `FeeExceedsAmountError`) before the intent is ever built, but this guard is bypassed whenever a caller supplies `args.feeEstimation` directly to `processWithdrawal` or `signAndSendWithdrawalIntent`, since `createWithdrawalIntents` (the function that actually builds the signed intent) does not repeat the check.

### Impact Explanation
The user who supplies (or is given, e.g. by an integrator relaying a cached/stale quote) a `feeEstimation` with `amount == withdrawalParams.amount` under `feeInclusive: true` will have a `ft_withdraw` intent signed and published that debits the full fee amount from their own balance while delivering zero value to the destination. This is a fee-calculation error that can drain a material share (up to 100%) of the intended withdrawal amount for that call, matching the Critical fee-calculation-error category. The affected party is the caller themselves (self-inflicted, since only their own signer produces the signed intent) — there's no cross-user grief vector shown here, since `createWithdrawalIntents`/`signAndSendWithdrawalIntent` sign with the caller's own `intentSigner`, and the `feeEstimation` object is only used by the SDK for the caller's own request, not injected by a third party into another user's flow.

### Likelihood Explanation
Requires: `feeInclusive: true`, PoA-bridge-routed asset (e.g. `nep141:bera.omft.near`), and a caller who bypasses `estimateWithdrawalFee` by supplying `args.feeEstimation` directly with `amount == feeEstimation.amount` (a stale/attacker-constructed quote where relayer fee has since risen to equal the requested amount, or simply a caller-supplied malformed fee object). Since only `_estimateWithdrawalFee` guards this, and `createWithdrawalIntents`/`processWithdrawal`'s "supply your own feeEstimation" path is a documented, supported SDK usage (not a misuse of an internal-only escape hatch), this is reachable by an ordinary unprivileged caller using public API surface with attacker-controlled `feeEstimation`.

### Recommendation
Move the `FeeExceedsAmountError` (or equivalent `actualAmount > 0n` / `actualAmount >= minimum` check) into `createWithdrawalIntents` in `packages/intents-sdk/src/sdk.ts`, so it is enforced on every call path that builds the intent (both when fee is freshly estimated and when a `feeEstimation` object is supplied directly), not only in `_estimateWithdrawalFee`.

### Proof of Concept
```ts
// vitest, mocking only the PoA bridge HTTP client
const feeEstimation: FeeEstimation = {
  amount: 1000n,
  quote: null,
  underlyingFees: { [RouteEnum.PoaBridge]: { relayerFee: 1000n } },
};

const withdrawalParams: WithdrawalParams = {
  assetId: "nep141:bera.omft.near",
  amount: 1000n, // == feeEstimation.amount
  feeInclusive: true,
  destinationAddress: "<valid bera address>",
  routeConfig: { route: RouteEnum.PoaBridge },
};

const intents = await sdk.createWithdrawalIntents({
  withdrawalParams,
  feeEstimation,
});

const ftWithdraw = intents.find((i) => i.intent === "ft_withdraw");
const debited = BigInt(ftWithdraw.amount);

// Broken equality:
// Expected: debited == withdrawalParams.amount (1000n), destination receives amount - fee == 0n
// Actual:   debited == relayerFee == 1000n as well, but this is NOT amount - fee (which is 0n) reconstructed correctly —
// the destination-facing amount that should be delivered is 0, yet the same 1000n fee is taken from the user with
// nothing left to withdraw, i.e., the withdrawal is fully consumed by fee with no FeeExceedsAmountError thrown.
expect(() => sdk.createWithdrawalIntents({ withdrawalParams, feeEstimation })).not.toThrow();
// whereas the "safe" path throws:
await expect(
  sdk.estimateWithdrawalFee({ withdrawalParams }) // internally re-derives fee, hits amount <= fee.amount guard
).rejects.toThrow(FeeExceedsAmountError);
```
