### Title
Webhook shop-domain identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` validates the authenticity of an incoming webhook by HMAC-signing only the raw request body, while the `shop` (tenant identity) is read from a separate, unsigned header. `ShopifyAPI::Webhooks::Registry.process` then treats that unauthenticated `shop` value as trusted and hands it directly to the app's webhook handler. Because the webhook HMAC secret (`api_secret_key`) is the single shared secret for the whole app (identical for every merchant/tenant that installs it), any unprivileged user who installs the app on their own store can capture a valid `(body, hmac)` pair from their own webhook deliveries and replay it with a forged shop-domain header claiming to be a different tenant.

### Finding Description
`Request#hmac` decodes the `hmac-sha256` header, and `Request#to_signable_string` returns only `@raw_body`: [1](#0-0) [2](#0-1) 

`shop` is read independently from the `shop-domain` header, which is never included in the signed bytes: [3](#0-2) 

`HmacValidator.validate` computes the signature over `to_signable_string` (the body only) and compares it against the `hmac` header — it never sees or checks `shop`: [4](#0-3) 

`Registry.process` uses this validator and, once it passes, forwards `request.shop` verbatim into `WebhookMetadata` for the handler, without any additional check that the shop actually matches the sender of that body: [5](#0-4) 

The binding that is broken: `shop == the tenant that produced/authorized this signed payload` is assumed by `Registry.process`, but the HMAC only proves `raw_body == the bytes signed with api_secret_key`; it says nothing about which shop sent it. Since `api_secret_key` is one shared value across every merchant that installs the app, a `(raw_body, hmac)` pair valid for shop A's webhook is equally valid (same signature) when replayed with shop B's domain in the header, because the signature doesn't depend on the shop at all.

### Impact Explanation
This breaks the tenant boundary the webhook mechanism is meant to enforce. Any actor who can install the app on a store they control (no privileged access, no leaked secret, no social engineering — simply installing a public/listed app) can capture their own valid webhook `(body, hmac)` samples and replay them against the app's webhook endpoint with an arbitrary `shop-domain` header. `Registry.process` will accept the request as valid (HMAC checks out) and dispatch to the host application's handler with attacker-chosen `data.shop`. If the host application uses `data.shop` to look up the affected merchant's session/record (the documented and expected usage pattern, per `WebhookMetadata`), this yields cross-tenant data injection/corruption — e.g., an attacker can make the app believe a webhook body (order, product, GDPR, app-uninstalled, etc.) came from a victim shop, potentially corrupting or leaking that victim's data. This matches the "cross-tenant access" Critical-impact category from a purely unauthenticated party.

### Likelihood Explanation
Likelihood is high for anyone motivated: creating a store and installing a target Shopify app requires no special privilege, and once installed, the attacker's own store will receive real webhooks signed with the shared `api_secret_key`, giving them arbitrary numbers of valid `(body, hmac)` samples they can replay with a spoofed `shop-domain` header.

### Recommendation
Do not treat `request.shop` as authenticated tenant identity based on HMAC validation alone. Either (a) bind `shop` into the signable payload used for verification (not possible unilaterally since Shopify itself signs only the body), or (b) require host applications/`Registry.process` to cross-check `request.shop` against an independently verified list of shops that have legitimately installed the app (e.g., only accept webhooks for shops with an active, previously stored session/access token), and document clearly that `HmacValidator.validate` provides no guarantee about the `shop` header's authenticity.

### Proof of Concept
1. Install the target app on an attacker-controlled development store (`attacker-shop.myshopify.com`); this is available to anyone with a free Shopify partner/dev account.
2. Trigger any subscribed webhook topic (e.g., `orders/create`) on the attacker's store and capture the raw request, including the `X-Shopify-Hmac-Sha256` header and body.
3. Replay the exact same body and `X-Shopify-Hmac-Sha256` header to the app's webhook endpoint, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` succeeds because it only checks the body against the shared secret [6](#0-5) , and `Registry.process` dispatches the handler with `shop: "victim-shop.myshopify.com"` [7](#0-6) , even though the payload actually originated from the attacker's own store.
