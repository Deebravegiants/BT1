### Title
Pausing `HyperFungibleToken` (and its variants) blocks delivery of already-in-flight cross-chain messages, causing route delivery failure and stuck refunds - (File: `sdk/packages/core/contracts/apps/HyperFungibleToken.sol`)

### Summary
`HyperFungibleToken::onAccept` and `HyperFungibleToken::onPostRequestTimeout` are both gated with `whenNotPaused`, exactly the pattern flagged in the external report for `Karma::_slash`/`StakeManager::redeemRewards`: a `Pausable` guard sits on a callback that the ISMP host invokes on behalf of an already-committed cross-chain message, so pausing the app makes that message's delivery/timeout resolution impossible, regardless of who tries to submit it.

### Finding Description
`HyperFungibleToken::send` burns the caller's tokens and dispatches a POST request via the host [1](#0-0) . Once dispatched, only two outcomes exist for that message: it is delivered to the destination via `onAccept`, or it times out and is refunded via `onPostRequestTimeout`. Both of these host-invoked callbacks carry the `whenNotPaused` modifier: [2](#0-1) [3](#0-2) 

The same pattern is repeated in the upgradeable and wrapped variants: `HyperFungibleTokenUpgradeable::onAccept`/`onPostRequestTimeout` [4](#0-3)  and `WrappedHyperFungibleToken::onAccept` [5](#0-4) , as well as `BridgeToken`, which inherits the same `whenNotPaused` gate through `super.onAccept`/`super.onPostRequestTimeout` [6](#0-5) .

This mirrors the reported bug class exactly: a `Pausable` guard on a function that is supposed to resolve an already-in-flight, externally-triggered obligation (there, redeeming/slashing virtual rewards; here, delivering a POST or refunding a timed-out one) means that a relayer submitting a fully valid proof for a committed message cannot get it processed while the app is paused — the call reverts due to an orthogonal, module-level pause state rather than any fault in the message or proof itself.

### Impact Explanation
While the token contract is paused, any relayer attempting to deliver an incoming transfer via `onAccept`, or to resolve a timed-out transfer's refund via `onPostRequestTimeout`, will have their transaction revert. This is a route unable to deliver messages: the ISMP host has a valid, verified request/timeout ready for processing, but the destination application unconditionally rejects it purely due to its own pause flag. Funds already burned on the source chain via `send()` cannot be refunded through `onPostRequestTimeout` while paused, and legitimate inbound transfers cannot be credited through `onAccept` while paused, effectively freezing user funds in transit for the duration of the pause.

### Likelihood Explanation
`pause()`/`unpause()` are owner-only [7](#0-6) , so the pause itself requires privileged action — but the resulting failure is not a "malicious admin" scenario: pausing is a normal, expected operational control (e.g., for incident response), and nothing in the design prevents legitimate in-flight messages from becoming permanently stuck as a side effect of an otherwise legitimate pause, since the pause makes zero distinction between new user-initiated calls (`send`, `transfer`) and host-driven resolution of already-committed messages (`onAccept`, `onPostRequestTimeout`). Any relayer submitting a proof during a pause window will trigger this.

### Recommendation
Do not gate `onAccept` and `onPostRequestTimeout` with `whenNotPaused`. `pause()` should only block new user-initiated operations (`send`, `transfer`, `transferFrom`), not the resolution of already-dispatched/committed ISMP messages. This matches the fix pattern recommended in the source report: critical settlement paths for already-committed obligations should not be blockable by an unrelated pause switch.

### Proof of Concept
1. User calls `HyperFungibleToken::send`, burning tokens and dispatching a POST request to a destination chain [1](#0-0) .
2. Owner calls `pause()` on the token contract (e.g., during a routine security review) [8](#0-7) .
3. The destination-side message either times out, or a relayer attempts delivery via the host, which calls `onAccept`/`onPostRequestTimeout` on the token — both revert due to `whenNotPaused` [9](#0-8) .
4. The user's already-burned tokens cannot be refunded and the message cannot be delivered until the contract is unpaused, demonstrating the route-delivery failure. This exact revert behavior is already exercised by the repo's own tests `testOnAcceptRevertsWhenPaused` and the analogous timeout test in `evm/tests/foundry/HyperFungibleTokenTest.sol` [10](#0-9) .

    function onAccept(IncomingPostRequest calldata incoming) public virtual override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        Message memory message = abi.decode(request.body, (Message));
        address beneficiary = _toAddr(message.to);
        _mint(beneficiary, message.amount);

        if (message.data.length > 0) {
            ICallDispatcher(_dispatcher).dispatch(message.data);
        }

        emit Received({
            from: message.from,
            to: beneficiary,
            source: string(request.source),
            amount: message.amount
        });
    }

    /**
     * @notice Handles timeout of a previously dispatched cross-chain transfer
     * @dev Called by the ISMP host when a sent message times out without being delivered.
     * Re-mints the burned tokens back to the original sender as a refund.
     * @param incoming The timed-out POST request and the relayer that submitted the timeout proof

    function onPostRequestTimeout(PostRequestTimeout memory incoming) public virtual override onlyHost whenNotPaused {
