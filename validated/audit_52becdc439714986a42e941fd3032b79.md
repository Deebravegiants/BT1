## Finding

### Title
`handlePostRequests` reverts the entire batch of relayed messages when a single request times out mid-flight, delaying delivery of otherwise-valid messages - (File: `evm/src/core/HandlerV2.sol`)

### Summary
`HandlerV2.handlePostRequests` checks every request's timeout inside the same loop that builds the Merkle proof leaves, and reverts the whole call with `MessageTimedOut` if even one request in the batch has timed out by the time the transaction is mined. Because relayers permissionlessly batch multiple POST requests into a single `handlePostRequests` (or `batchCall`) transaction to save gas, a single request racing past its timeout between submission and inclusion causes the entire batch — including all still-valid, non-timed-out requests — to fail delivery, exactly the same "single item's state changes mid-flight → entire multi-item operation reverts" bug class described in the Notional report.

### Finding Description
`handlePostRequests` iterates over `request.requests` and unconditionally reverts if any single leaf has timed out: [1](#0-0) 

```
for (uint256 i = 0; i < requestsLen; ++i) {
    PostRequestLeaf memory leaf = request.requests[i];
    // check destination
    if (!leaf.request.dest.equals(host.host())) revert InvalidMessageDestination();
    // check time-out
    if (timestamp >= leaf.request.timeout()) revert MessageTimedOut();
    leaves[i] = MerkleMountainRange.Leaf(leaf.index, leaf.request.hash());
}
```

This is a hard `require`-style revert on `block.timestamp` state that can legitimately change between the moment a relayer assembles/submits the transaction and the moment it lands on-chain (mempool delay, gas-price competition, reorgs, or simply a batch that straddles a request's `timeout` boundary). Because the same loop is also the one that builds the `leaves` array consumed by the Merkle proof verification a few lines later, there is no way to "skip" the timed-out entry and still deliver the rest of the batch with the same proof — one bad apple reverts everything.

The same pattern recurs in the sibling batch handlers, compounding the exposure:
- `handlePostRequestTimeouts` reverts the whole batch with `MessageNotTimedOut` if any timeout entry hasn't actually timed out yet: [2](#0-1) 
- `handleGetRequestTimeouts` has the identical check: [3](#0-2) 

`handleConsensus`, `handlePostRequests`, `handleGetResponses`, and the timeout handlers can additionally be chained together via `batchCall`, which is documented as fully atomic — "any failure reverts the entire batch" — making an accidental timeout revert propagate even further and undo an otherwise-successful consensus update or unrelated message delivery bundled in the same transaction: [4](#0-3)  All of these entry points are explicitly permissionless, reachable by any relayer: [5](#0-4) 

### Impact Explanation
When a relayer batches several requests for gas efficiency (the documented purpose of batching in `IHandlerV2`), a race between one request's timeout and block inclusion nullifies delivery of all co-batched requests, not just the expired one. The relayer must then re-derive a fresh Merkle proof excluding the expired leaf and resubmit, during which time other requests in the batch move closer to their own timeouts — creating a self-reinforcing delay under network congestion or high message volume, analogous to the rebalance-delay dynamic in the source report. Repeated failures under sustained load can cause legitimate cross-chain messages to time out before ever being delivered, which is a "route unable to deliver messages" condition.

### Likelihood Explanation
This requires no malicious actor — any relayer batching real-world traffic under normal network latency/congestion can trigger it, since request timeouts are typically short-lived windows and transaction inclusion time is not fully controllable. The larger the batch (which relayers are incentivized to use for gas savings), the higher the probability that at least one leaf's timeout elapses before inclusion.

### Recommendation
Filter out (or skip) leaves whose timeout has already elapsed before verification instead of reverting the whole batch, and dispatch only the remaining valid leaves — mirroring the source report's recommendation of "skip the affected item, process the rest." Concretely, precompute/validate timeouts and build the Merkle leaf set only from currently-valid requests, or split verification per-leaf so a stale leaf's exclusion doesn't invalidate the batch's proof for the rest. Similarly adjust `handlePostRequestTimeouts`/`handleGetRequestTimeouts` to skip not-yet-timed-out entries rather than reverting the entire timeout batch.

### Proof of Concept
1. A relayer collects `N` POST requests destined for this host and constructs a `PostRequestMessage` with a single Merkle multiproof covering all `N` leaves, calling `handlePostRequests`.
2. Between proof construction/submission and block inclusion, request `k` (out of `N`) crosses its `timeout()` value relative to `block.timestamp` (e.g., due to gas-price competition delaying inclusion, or a deliberately tight timeout).
3. At inclusion, the loop at `evm/src/core/HandlerV2.sol:190-197` reaches leaf `k` and executes `if (timestamp >= leaf.request.timeout()) revert MessageTimedOut();`, reverting the entire transaction.
4. None of the other `N-1` valid, non-timed-out requests are dispatched via `host.dispatchIncoming`, even though their proofs were valid and they were within their timeout window. The relayer must regenerate the proof (excluding leaf `k`) and resubmit, repeating the race for the remaining requests. [6](#0-5)

     * @dev Process a batch of encoded handler calls in a single transaction.
     * Uses delegatecall to self so msg.sender is preserved and storage writes
     * happen in this contract's context. Atomic, any failure reverts the entire batch.
     * @param calls - array of ABI-encoded handler function calls

    function batchCall(bytes[] memory calls) external {
        uint256 len = calls.length;
        for (uint256 i = 0; i < len; ++i) {
            (bool success, bytes memory returnData) = address(this).delegatecall(calls[i]);
            if (!success) revert BatchCallFailed(i, returnData);
        }
    }

    function handlePostRequests(IHost host, PostRequestMessage calldata request) external notFrozen(host) {
        uint256 timestamp = block.timestamp;
        uint256 delay = timestamp - host.stateMachineCommitmentUpdateTime(request.proof.height);
        uint256 challengePeriod = host.challengePeriod();
        if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();

        uint256 requestsLen = request.requests.length;
        MerkleMountainRange.Leaf[] memory leaves = new MerkleMountainRange.Leaf[](requestsLen);

        for (uint256 i = 0; i < requestsLen; ++i) {
            PostRequestLeaf memory leaf = request.requests[i];
            // check destination
            if (!leaf.request.dest.equals(host.host())) revert InvalidMessageDestination();
            // check time-out
            if (timestamp >= leaf.request.timeout()) revert MessageTimedOut();
            leaves[i] = MerkleMountainRange.Leaf(leaf.index, leaf.request.hash());
        }

        bytes32 root = host.stateMachineCommitment(request.proof.height).overlayRoot;
        if (root == bytes32(0)) revert StateCommitmentNotFound();
        bool valid = MerkleMountainRange.VerifyProof(root, request.proof.multiproof, leaves, request.proof.leafCount);
        if (!valid) revert InvalidProof();

        for (uint256 i = 0; i < requestsLen; ++i) {
            PostRequestLeaf memory leaf = request.requests[i];
            // duplicate request?
            if (host.requestReceipts(leaf.request.hash()) != address(0)) revert DuplicateMessage();
            host.dispatchIncoming(leaf.request, _msgSender());
        }
