### Title
Webhook `shop`, `topic`, and `webhook_id` fields are trusted without HMAC coverage, enabling cross-tenant webhook confusion - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook's authenticity solely by HMAC-verifying the raw request body, but the `shop`, `topic`, `webhook_id`, and `api_version` values used to build `WebhookMetadata` (and dispatch it to the app's handler) are read straight from unauthenticated HTTP headers that the HMAC never covers.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all pulled from HTTP headers via `shopify_header`, completely outside the signed payload: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately builds `WebhookMetadata` using those unauthenticated header values, handing them to the app's handler as the trusted tenant/topic identifiers: [3](#0-2) 

`HmacValidator.validate` only checks `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)`, i.e. only the body bytes are bound to the signature: [4](#0-3) 

The equality that should hold is: `shop header used for tenant dispatch == shop bound inside the HMAC-signed payload`. In this gem it instead holds: `shop header used for tenant dispatch == shop header, unauthenticated`. Because the app's `client_secret`/HMAC secret is shared across every shop that installs the app, any merchant (including an unprivileged attacker who simply installs the target app on their own free/dev store) can legitimately trigger a webhook for their own shop, capture the validly-signed raw body + HMAC, and then resend it directly to the app's public webhook endpoint with the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header swapped to a victim shop. The HMAC still validates (body unchanged), `Registry.process` accepts it, and the handler receives `WebhookMetadata` claiming to be from the victim shop/topic even though only the attacker's own body content is authenticated.

### Impact Explanation
Any application built on this gem that uses `WebhookMetadata#shop` (or `#topic`) to look up per-tenant records, apply per-tenant business logic, or route data by shop, can be tricked into applying attacker-controlled webhook body content under a victim shop's identity — a cross-tenant access/confusion condition, since the shop identity that reaches application logic is never bound to the cryptographically verified bytes.

### Likelihood Explanation
High. No privileged credentials are required beyond installing the target app on a shop the attacker legitimately controls (any developer/free store), which is the normal, unprivileged path for using a Shopify app. Triggering any webhook event (e.g. `orders/create`) on their own store yields a validly-HMAC-signed body; only the request headers need to be altered, and the gem provides no mechanism to bind headers to the signature.

### Recommendation
Bind `shop`, `topic`, and `webhook_id` into the signed payload verification — e.g., include them in `to_signable_string`, or independently validate that the `shop` header/domain matches an app-known, previously-authenticated tenant record (rather than trusting the header in isolation) before constructing `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com`.
2. Attacker triggers a webhook event (e.g., creates an order) causing Shopify to POST a validly HMAC-signed webhook to the app's endpoint, with headers `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Topic: orders/create`, and a correctly computed `X-Shopify-Hmac-Sha256` over the raw body.
3. Attacker captures this raw HTTP request (they are the recipient's network operator/can replay via their own tooling since it's their own webhook), then re-sends the identical body and HMAC header to the app's public webhook endpoint, but changes `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses headers, `HmacValidator.validate` succeeds because the body/HMAC pair is untouched (`lib/shopify_api/webhooks/request.rb` lines 35-43, `lib/shopify_api/utils/hmac_validator.rb` lines 12-31).
5. `Registry.process` dispatches `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: <attacker's order payload>, ...)` to the app's handler (`lib/shopify_api/webhooks/registry.rb` lines 188-200), causing the app to process attacker-controlled data as if it belonged to the victim tenant.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
