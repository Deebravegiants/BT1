### Title
`DirectBridge.describeWithdrawal` always reports `status: 'completed'` without checking the NEAR transaction's receipt outcomes, violating STATUS TRUTH - (`File: packages/intents-sdk/src/bridges/direct-bridge/direct-bridge.ts`)

### Summary
`DirectBridge.describeWithdrawal` unconditionally returns `{ status: "completed", txHash: args.tx.hash }` for every call, regardless of whether the underlying `ft_withdraw`/`native_withdraw` intent actually succeeded on-chain. Every other bridge implementation (e.g. `PoaBridge.describeWithdrawal`) queries an authoritative status source and can return `"pending"` or `"failed"`; `DirectBridge` performs no such check at all.

### Finding Description
The claimed equality is: `describeWithdrawal(wid).status == on-chain outcome of the withdrawal identified by wid.tx.hash`. In `DirectBridge`: [1](#0-0) 

`describeWithdrawal` takes no RPC action, inspects no receipt, and returns `completed` immediately. Contrast with `PoaBridge.describeWithdrawal`, which retrieves the withdrawal's real status from the bridge API and returns `pending`/`completed`/`failed` accordingly: [2](#0-1) 

The `ft_withdraw`/`native_withdraw` intents are executed by the intents contract as cross-contract calls (with a bounded `min_gas` per `createWithdrawIntentPrimitive` in `direct-bridge-utils.ts`), meaning the outer NEAR transaction can return `SuccessValue` at the top level while a downstream receipt (e.g., `ft_transfer`/`ft_transfer_call` to the token contract, or the storage-deposit sub-call) fails due to insufficient storage, receiver panic, or gas exhaustion under `MIN_GAS_AMOUNT`. `DirectBridge.describeWithdrawal` never distinguishes this case from a fully successful withdrawal.

This status feeds directly into `watchWithdrawal` in `core/withdrawal-watcher.ts`, which treats any `status === "completed"` as resolved success and resolves the promise with the tx hash: [3](#0-2) 

and ultimately surfaces through `sdk.waitForWithdrawalCompletion`, which an integrator uses to decide when to credit the withdrawal as final, as shown in the existing test mocking `describeWithdrawal` to `completed`: [4](#0-3) 

None of the existing guards (`validateAddress`, `compareAddresses`, `supports()`, `FeeExceedsAmountError`, `getUnderlyingFee`, contract-side signature/nonce checks) address this — they all operate before submission and have no bearing on post-submission receipt inspection. The attacker doesn't even need malicious intent: an ordinary user withdrawing to an address without sufficient NEP-141 storage deposit, or a `ft_transfer_call` receiver that panics, naturally triggers this divergence on their own withdrawal.

### Impact Explanation
An integrator polling via `waitForWithdrawalCompletion`/`watchWithdrawal` will treat the withdrawal as final and credit it in their own ledger (e.g., mark an off-chain balance as debited/settled, release a corresponding cross-chain leg, or stop retry logic) even though the tokens never left the intents contract's balance. If the user or integrator later retries the withdrawal manually (since funds are still in the intents balance), a double-credit / double-accounting scenario is created downstream. This matches the "status or hash misreport making an integrator credit or refund twice" High/Critical impact category — funds delivered nowhere while the system of record says otherwise.

### Likelihood Explanation
No special privileges are required. Preconditions are entirely ordinary: a `nep141` withdrawal via the `NearWithdrawal` route (`DirectBridge`) to a destination account lacking sufficient token storage balance, or with a `msg`-carrying `ft_transfer_call` receiver that panics or runs out of gas (explicitly called out as gas-unpredictable in `direct-bridge-utils.ts` comments), is enough to produce a failed sub-receipt under a successful top-level transaction. This is highly feasible and repeatable — it will occur on essentially every `DirectBridge` withdrawal whose token-transfer receipt fails, at zero attacker cost.

### Recommendation
Implement `describeWithdrawal` in `DirectBridge` to actually fetch the transaction/receipt outcomes for `args.tx.hash` via the NEAR RPC (`this.nearProvider`), inspect all receipt `FunctionCallAction` outcomes relevant to the withdrawal intent (the `ft_withdraw`/`native_withdraw` call and any nested `ft_transfer`/`ft_transfer_call`/storage-deposit receipts), and return `"failed"` if any relevant receipt failed, `"pending"` if not yet finalized, and only `"completed"` if all relevant receipts succeeded — mirroring the pattern used by `PoaBridge.describeWithdrawal`.

### Proof of Concept
```ts
// direct-bridge.describeWithdrawal.test.ts
import { describe, it, expect, vi } from "vitest";
import { DirectBridge } from "./direct-bridge";

describe("DirectBridge.describeWithdrawal STATUS_TRUTH", () => {
  it("must not report 'completed' when the ft_withdraw receipt failed on-chain", async () => {
    // Mock NEAR provider: tx succeeds at top level, but a nested receipt
    // (ft_transfer_call to the token contract) fails.
    const mockNearProvider = {
      txStatus: vi.fn().mockResolvedValue({
        status: { SuccessValue: "" }, // top-level tx "succeeds"
        transaction_outcome: { outcome: { status: { SuccessValue: "" } } },
        receipts_outcome: [
          {
            outcome: {
              status: { Failure: { ActionError: { kind: "FunctionCallError" } } },
            },
          },
        ],
      }),
    };

    const bridge = new DirectBridge({
      envConfig: {} as any,
      nearProvider: mockNearProvider as any,
    });

    const wid = {
      landingChain: "near",
      index: 0,
      withdrawalParams: {
        assetId: "nep141:wrap.near",
        amount: 5n,
        destinationAddress: "no-storage.near",
        feeInclusive: true,
      },
      tx: { accountId: "foo.near", hash: "failing-tx-hash" },
    } as any;

    const result = await bridge.describeWithdrawal(wid);

    // Actual on-chain outcome (mocked): failed
    const actualOnChainOutcome = "failed";

    // Bug: SDK reports 'completed' regardless
    expect(result.status).toBe("completed"); // demonstrates current (buggy) behavior
    expect(result.status).not.toBe(actualOnChainOutcome); // STATUS_TRUTH violated
  });
});
```
This test only mocks the NEAR RPC (`nearProvider.txStatus`), calls the public `describeWithdrawal` method, and proves `result.status === "completed"` while the mocked actual outcome is `"failed"`, confirming `(status, txHash)` reported does not equal the on-chain outcome.

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}
