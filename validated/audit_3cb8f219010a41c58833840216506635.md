### Title
Webhook `shop` (and `topic`/`webhook_id`) fields are trusted for routing without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook by validating only the raw request body against the `hmac-sha256` header, then unconditionally trusts the `shop-domain` header to route the payload to a handler as the tenant identity. Because the shop header is never part of the signed material, the identity used for routing/authorization (`shop` header) is not the same identity that was cryptographically verified (the HMAC over the body).

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body: [1](#0-0) 

The `shop`, `topic`, and `webhook_id` accessors are read directly from unauthenticated HTTP headers, entirely independent of the signed payload: [2](#0-1) 

`Registry.process` validates the HMAC (which only proves the body's integrity/authenticity) and then immediately constructs `WebhookMetadata` using `request.shop`, `request.topic`, and `request.webhook_id` — none of which were part of the signed data — and hands it to the app-registered handler: [3](#0-2) [4](#0-3) 

The identity binding that should hold is: `shop authenticated by HMAC == shop acted on by the handler`. Here, the HMAC only authenticates `raw_body`, while `data.shop` used by the handler comes from an unsigned header. The check (`Utils::HmacValidator.validate(request)`) answers "is this body genuinely signed by our shared secret" but the code then treats that as if it also answered "is this body genuinely *from this specific shop*" — which it does not, since the shared HMAC secret (`api_secret_key`) is common to all shops that have installed the app, not per-shop.

### Impact Explanation
Any merchant who has installed the app on their own store receives genuinely Shopify-signed webhooks (valid body + `hmac-sha256`) for their own store. Because the signature never binds the `shopify-shop-domain` header, that same attacker can replay the identical body/HMAC pair to the app's webhook endpoint while substituting an arbitrary victim `shop-domain` header. `HmacValidator.validate` still returns `true` (it only checks the body), and `Registry.process` will invoke the app's handler with `shop: <victim-shop>` for content that actually originated from the attacker's own store. Any app logic that trusts `WebhookMetadata#shop` to scope tenant data (e.g., "update customer/order data for this shop") can be tricked into writing or acting on a different, unrelated shop's identity — a cross-tenant identity confusion.

### Likelihood Explanation
Likelihood is Medium: exploitation requires the attacker to be a legitimate (even free) installer of the target app in order to obtain one valid body/HMAC pair, and to be able to POST directly to the app's public webhook endpoint with custom headers (webhook endpoints are typically public HTTP endpoints with no additional caller-authentication beyond the HMAC check this gem provides).

### Recommendation
Bind the shop identity into the verified material, or otherwise attest it. Preferably, drop the `shop-domain` header from the trust boundary entirely and instead require callers of the app to fetch the shop identity from a store keyed by `webhook_id`/`X-Shopify-Api-Version`/registered subscription, or (if header trust is unavoidable) include the shop domain in the value being HMAC-verified, e.g., verify `hmac(shop + "\n" + raw_body)` against a per-shop expectation, or cross-check the header shop against the shop associated with the session/webhook registration before invoking the handler.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com`, triggering Shopify to send a legitimate webhook: body `B`, header `X-Shopify-Hmac-Sha256: H` (valid HMAC of `B` under the app's `api_secret_key`), `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Attacker captures `B` and `H`.
3. Attacker crafts a new POST to the app's webhook endpoint with the same body `B`, same header `H`, but `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses headers, `Registry.process` calls `Utils::HmacValidator.validate(request)`, which validates `H` against `HMAC(secret, B)` — passes, since `B` and `H` are unchanged.
5. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(shop: "victim.myshopify.com", ...))`, causing the app to process attacker-controlled webhook content under the victim shop's identity. [4](#0-3) [5](#0-4)

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
