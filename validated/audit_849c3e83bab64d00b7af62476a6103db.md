### Title
Webhook shop-domain header is not covered by HMAC, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` value from the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) HTTP header, but the HMAC signature that `Registry.process` verifies only covers the raw request body, not this header. An attacker who owns a legitimate Shopify store (an unprivileged, non-victim tenant) can capture a real, validly-signed webhook body sent to their own endpoint and replay it to the app's webhook endpoint while substituting the `shop-domain` header for a victim shop's domain. The HMAC check still passes because the header is never part of the signed payload, so the forged shop identity is delivered to the app's handler as if it were authentic.

### Finding Description
The webhook signature verification binds only the byte content of the body: [1](#0-0) 

Meanwhile, `shop` is read from an HTTP header that is entirely outside that signed scope: [2](#0-1) 

`Registry.process` validates the HMAC using `Utils::HmacValidator.validate(request)`, which calls `to_signable_string` (the raw body) — it never incorporates `request.shop`: [3](#0-2) [4](#0-3) 

After the HMAC passes, `request.shop` (unauthenticated) is forwarded directly to the handler via `WebhookMetadata`, which the gem's own documentation instructs developers to treat as the tenant/shop identity for storing or routing webhook data: [5](#0-4) 

This breaks the identity binding: `shop authenticated by HMAC` should equal `shop attributed to the webhook payload`, but here the HMAC only authenticates the body bytes while the shop identity is taken from an out-of-band, unsigned header.

### Impact Explanation
An attacker who controls any real Shopify store can receive genuine webhooks from Shopify for their own store (fully valid HMAC over the body), then replay that exact body/HMAC pair to the target app's webhook endpoint with a forged `shop-domain` header pointing at a victim shop. Because the header is not part of the signed content, `Registry.process` accepts it as valid and hands the attacker-controlled `shop` value to the app's handler as the identified tenant. Per the documented usage pattern, apps use `data.shop` to key persistence/queueing of webhook data (e.g., `shop_domain: data.shop`), so this allows an unprivileged actor to inject or misattribute webhook data under another tenant's identity — a cross-tenant data integrity/confusion issue.

### Likelihood Explanation
Exploitation requires only that the attacker operate their own legitimate, unprivileged Shopify store — a widely available capability (any developer can create a Shopify dev/trial store) — and does not require the app's `client_secret`, an access token, or any privileged account belonging to the victim. The replay is a simple HTTP request with a substituted header.

### Recommendation
Include `shop` (and ideally `topic`) as part of the HMAC-signed content that `Utils::HmacValidator` verifies, or otherwise cryptographically bind the header value to the signed payload, rather than trusting the header value independently of the body HMAC.

### Proof of Concept
1. Attacker installs the target app on their own Shopify store `attacker.myshopify.com` and triggers a webhook (e.g. `orders/create`) they control, obtaining `raw_body` and the valid `X-Shopify-Hmac-Sha256` value that Shopify computed for that body using the app's shared secret.
2. Attacker sends a POST to the app's webhook endpoint reusing that identical `raw_body` and `X-Shopify-Hmac-Sha256`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `Registry.process` builds `ShopifyAPI::Webhooks::Request`, calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC only over `raw_body` and finds it matches — validation succeeds.
4. `Registry.process` invokes the handler with `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body: attacker_data, ...)`, so the app processes attacker-supplied data as belonging to `victim-shop.myshopify.com`.
