## Analysis

The reported bug class ("a field acted on but not covered by the HMAC") maps directly onto the webhook-processing path in this gem. [1](#0-0) 

`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` — the HMAC signature that Shopify sends is verified exclusively against the raw JSON body. The `topic`, `shop`, `api_version`, and `webhook_id` values are all read straight from HTTP headers and are never included in the signed content: [2](#0-1) 

`ShopifyAPI::Webhooks::Registry.process` validates the HMAC of the request, then hands the header-derived, unauthenticated `topic`/`shop`/`webhook_id`/`api_version` straight to the app's handler: [3](#0-2) 

and `HmacValidator.validate` confirms only that `verifiable_query.hmac` matches `compute_signature(verifiable_query.to_signable_string, secret)` — i.e. it authenticates the body bytes, not the header metadata: [4](#0-3) 

### Title
Webhook `shop`/`topic`/`webhook_id` headers are not covered by HMAC verification, enabling cross-tenant/topic webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook request as authentic once `Utils::HmacValidator.validate(request)` succeeds. That validator only proves the raw request body was HMAC-signed with the app's `api_secret_key`; the shop-identifying and topic-identifying HTTP headers (`x-shopify-shop-domain`/`shopify-shop-domain`, `x-shopify-topic`/`shopify-topic`, `webhook-id`, `api-version`) are excluded from `to_signable_string` and thus never authenticated.

### Finding Description
`Request#to_signable_string` (`lib/shopify_api/webhooks/request.rb:36-38`) returns `@raw_body` alone. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) checks `Utils::HmacValidator.validate(request)` — which recomputes the HMAC over `to_signable_string`, i.e. the body only — and, if it matches, forwards `request.topic`, `request.shop`, `request.parsed_body`, `request.api_version`, and `request.webhook_id` to the registered handler as `WebhookMetadata`, all read directly from unauthenticated headers (`request.rb:15-23`).

Because any Shopify merchant can install a target app on a store they themselves control, they can legitimately receive genuine, correctly-signed webhook deliveries (valid body + valid HMAC) for their own shop. Nothing in this gem prevents that captured, still-validly-signed body from being replayed to the same webhook endpoint with the `shop-domain` header rewritten to a different (victim) shop domain, and/or the `topic`/`webhook-id` headers rewritten to a different topic. `HmacValidator.validate` still succeeds because it only checks the untouched body bytes; the gem then reports the attacker-chosen `shop` and `topic` values as authentic in `WebhookMetadata`, breaking the identity binding: "shop cryptographically authenticated" (none) vs. "shop the handler is told to act on" (attacker-controlled header).

### Impact Explanation
Applications built on this gem rely on `WebhookMetadata#shop`/`#topic` to route webhook data to the correct tenant/handler, since the library's own HMAC check is the only authenticity guarantee it provides for webhook headers. An attacker who controls their own installation can forge the shop/topic association of an otherwise-legitimate signed payload, causing the host application to process (store, act upon) attacker-supplied webhook data attributed to a different merchant/shop — a cross-tenant data confusion, and/or invoke the wrong topic handler with attacker-chosen (but validly signed) body content.

### Likelihood Explanation
Exploitation requires only that the attacker install the target app on a shop they control (an unprivileged action available to any Shopify user) and be able to send arbitrary HTTP requests with custom headers to the app's public webhook endpoint — no access token, `client_secret`, or victim credentials are needed. The only real-world friction is that the attacker doesn't control the JSON body content (it must be a body Shopify actually signed for their own shop), which somewhat limits, but does not eliminate, impact since body reuse/replay across shop-domain claims and topic claims is still possible.

### Recommendation
Include the `shop-domain`, `topic`, and `webhook-id`/`api-version` header values in the HMAC-signed content that `Request#to_signable_string` returns (or otherwise cryptographically bind them, e.g. by having the host verify `shop` returned from `WebhookMetadata` against the session/store that owns the registered webhook subscription) before trusting them for routing or persistence decisions.

### Proof of Concept
1. Attacker creates their own development/test shop and installs the target app, causing Shopify to deliver a genuine webhook, e.g. `orders/create`, to the app's endpoint with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: orders/create`, and a valid `x-shopify-hmac-sha256` computed over the raw body.
2. Attacker replays the exact same raw body and HMAC header to the app's webhook endpoint, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com` (and/or changes `x-shopify-topic`/`webhook-id`).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over the (unchanged) raw body and succeeds, since headers are not part of the signed content.
4. The registered handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` (attacker-controlled) despite the payload never having been signed for that shop.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
