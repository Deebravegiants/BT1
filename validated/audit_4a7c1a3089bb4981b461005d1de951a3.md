### Title
Webhook `shop` domain is trusted by handlers without being covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook request's authenticity solely via `Utils::HmacValidator.validate(request)`, and that HMAC is computed only over the raw request body. The `shop` value that the library extracts and hands to the app's handler as the tenant identifier comes from an HTTP header that is never included in the signed material, breaking the intended binding "shop authenticated == shop the data is attributed to."

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, however, is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is completely outside the signed payload: [2](#0-1) 

`Registry.process` validates only the HMAC of the request (i.e., the body) and then immediately forwards the header-derived `shop` value to the app's handler as the trusted tenant identifier: [3](#0-2) 

`Utils::HmacValidator.validate` calls `verifiable_query.to_signable_string`, confirming that for a `Request` object this signable string is exactly the raw body and nothing about the shop/topic headers: [4](#0-3) 

The documented handler contract explicitly instructs apps to treat `data.shop` as the trustworthy shop identifier returned by the library, with no caveat that it is unauthenticated: [5](#0-4) 

The binding that breaks is: `shop authenticated by HMAC` (nothing, since HMAC only covers the body) **!=** `shop key used by the handler` (the unauthenticated `shopify-shop-domain` header). An attacker who controls any shop that can trigger genuine, HMAC-valid Shopify webhook deliveries to the app (e.g., their own installed/dev store) obtains a body + valid HMAC pair. Because the header carrying `shop` is not part of the signed content, that same valid `(body, hmac)` pair remains valid if the `shopify-shop-domain` header is swapped for an arbitrary victim shop domain when the request is replayed to the app's public webhook endpoint. `Registry.process` will pass HMAC validation and call the handler with `shop: <victim-shop>` and the attacker's body content.

### Impact Explanation
This lets an unprivileged internet user cause a webhook event to be processed by the app as if it originated from a different (victim) shop than the one that actually produced the HMAC-valid payload. Since `WebhookMetadata.shop` is the field apps are documented to use to look up per-tenant sessions/state and to act on incoming data, this is a cross-tenant identity-binding break: data or events attributed to shop A (attacker) can be delivered under the identity of shop B (victim), corrupting per-tenant processing/state keyed by `shop`. This matches the "cross-tenant access" impact category via a genuine identity-binding failure between the HMAC-covered bytes and the field used to key the tenant.

### Likelihood Explanation
Requires only: (1) the attacker be able to obtain at least one genuine Shopify-signed webhook (trivial — install the target app on their own store or trigger any subscribed event), and (2) the ability to send an arbitrary HTTP request with custom headers to the app's public webhook endpoint (any internet user, since these endpoints are unauthenticated by design and must accept unauthenticated Shopify calls). No access token, `client_secret`, or privileged account is needed — the library's own header parsing and HMAC scope are what fail to bind `shop` to the signature.

### Recommendation
Do not treat the `shopify-shop-domain` header as authenticated. Either:
- Extend the HMAC-covered signable string to include the shop/topic headers (would require Shopify-side changes and is not solely fixable in this gem), or
- Have `Registry.process`/`WebhookMetadata` clearly flag `shop` as unauthenticated and require/encourage callers to cross-check it against an app-known list of currently-installed shops (e.g., verify a session exists for that shop) before trusting it for tenant-scoped operations, and update `docs/usage/webhooks.md` to state this caveat explicitly instead of presenting `data.shop` as trustworthy on its own.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, triggering a legitimate `orders/create` webhook. Shopify sends:
   - Body: `{"id":1,...}` (attacker-controlled content since it's their own store)
   - Headers: `x-shopify-hmac-sha256: <valid HMAC of body>`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: orders/create`
2. Attacker captures this exact `(body, hmac)` pair.
3. Attacker replays the identical body and `x-shopify-hmac-sha256` value directly to the app's public webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses headers/body as usual; `Utils::HmacValidator.validate(request)` recomputes HMAC over `@raw_body` only — it matches, since the body is unchanged. [6](#0-5) 
5. The handler receives `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: <attacker body>, ...)` and processes it as if it were a genuine event for `victim-shop.myshopify.com`.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
