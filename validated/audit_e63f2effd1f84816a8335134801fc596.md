### Title
Webhook `shop` attribution read from unauthenticated header while HMAC signature only covers the raw body - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` exposes a `shop` accessor that reads the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, but the HMAC signature validated via `Utils::HmacValidator.validate` (through `to_signable_string`) covers only the raw request body, never the headers. This breaks the identity binding: `shop` (used to attribute the webhook to a tenant) ≠ `bytes covered by the verified HMAC`.

### Finding Description
`Webhooks::Request#to_signable_string` returns `@raw_body` only: [1](#0-0) 

`Webhooks::Request#shop` reads the value straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, with no cross-check against the HMAC-protected content: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` and compares it to the `hmac` field: [3](#0-2) 

Since `Webhooks::Request` implements `Utils::VerifiableQuery` (`hmac` + `to_signable_string`) and `to_signable_string` is defined as the raw body alone, a caller doing the documented validate-then-trust pattern (`HmacValidator.validate(request)` then reading `request.shop` to look up/authorize the tenant) is trusting a header value that is not bound by the signature it just checked. The equality that should hold is:

`shop used for tenant identification == shop bound inside the HMAC-signed bytes`

but the actual behavior is:

`shop used for tenant identification == header value, unrelated to HMAC-signed bytes (raw body only)`

An unprivileged internet user who can obtain any one genuinely-signed webhook delivery for any shop (e.g., their own trial/dev store, which is legitimate and requires no special access) can capture the raw body + valid `hmac-sha256` value, then resend that exact body/HMAC pair to the app's webhook endpoint with an arbitrary `shopify-shop-domain` header value. `HmacValidator.validate` will still return `true` (the body is unchanged, so the signature matches), yet `request.shop` will return the attacker-controlled shop domain rather than the shop that actually produced the payload.

### Impact Explanation
Any host application that follows the natural pattern of "validate HMAC, then trust `request.shop` for tenant routing/authorization" is exposed to cross-tenant misattribution: a payload legitimately signed for tenant A can be replayed and accepted as belonging to tenant B (attacker-chosen), because the gem's own `VerifiableQuery` contract for webhooks never binds the shop identity into the signed bytes. This matches the "Critical - cross-tenant access" impact category, since it allows an attacker to make the app process/store data (or trigger tenant-scoped side effects) under an identity of their choosing while passing the gem's own signature check.

### Likelihood Explanation
The attack requires only a single legitimately-delivered webhook (obtainable from the attacker's own store, which any unprivileged developer/merchant can create) and standard HTTP tooling to resend the request with a modified header — no access to `api_secret_key`, access tokens, or the target app's `client_secret` is needed. The header-vs-signed-bytes mismatch lives directly in the gem's `Webhooks::Request`/`HmacValidator` contract, so any app that relies on this class's documented API is affected without any additional misconfiguration.

### Recommendation
Bind the shop (and topic/webhook-id) into the data that is actually verified, e.g., include the `shop-domain` (and other identity-bearing headers) in `to_signable_string`, or have `HmacValidator`/`Webhooks::Request` cross-verify that the header-derived shop matches a shop value embedded in the signed payload before exposing it via `shop`. At minimum, document prominently that `request.shop` is unauthenticated and must not be used for tenant lookup without additional binding.

### Proof of Concept
1. Attacker creates/owns a legitimate trial store and installs the target app, receiving one real webhook delivery with body `B` and header `X-Shopify-Hmac-Sha256: H` (a valid signature over `B` per `Digest::hexencode(Base64.decode64(H))`).
2. Attacker resends `POST /webhooks` to the target app with the identical raw body `B`, identical `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. App code executes:
   ```ruby
   request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
   raise "invalid" unless ShopifyAPI::Utils::HmacValidator.validate(request)  # passes: body unchanged
   handle_webhook(shop: request.shop, ...)  # returns "victim-shop.myshopify.com"
   ```
4. `HmacValidator.validate` returns `true` [3](#0-2)  because only the body is checked, while `request.shop` [2](#0-1)  returns the attacker-supplied header value — the app processes the webhook under the wrong tenant identity despite a "valid" signature.
