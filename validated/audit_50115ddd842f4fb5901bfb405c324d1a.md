## Finding

### Title
Webhook shop/topic identity spoofing via unauthenticated headers outside HMAC coverage - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while `shop`, `topic`, `api_version`, and `webhook_id` are read straight from unauthenticated HTTP headers and then handed to the application's webhook handler as trusted identity data. This breaks the equality `shop bytes verified by HMAC == shop bytes acted on by the handler`.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Registry.process` validates the HMAC over that same `VerifiableQuery` (i.e. the raw body only) and then constructs `WebhookMetadata` from `request.shop`, `request.topic`, and `request.webhook_id`, none of which participated in the signature: [2](#0-1) 

Those fields are all sourced from raw HTTP headers with no cryptographic binding to the body: [3](#0-2) 

The `HmacValidator.validate` call only checks `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)`, i.e. it only proves the body was signed by the app's shared secret — it says nothing about which shop or topic that body was signed for: [4](#0-3) 

Because a single app-wide `client_secret` (the same secret for every merchant installation) is used to compute the webhook HMAC, any party who has legitimately received one authentic `(raw_body, hmac)` pair from Shopify for their own shop (e.g., by installing the public app on their own free/dev store — no elevated privilege required) can replay that exact body and HMAC to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain`, `X-Shopify-Topic`, and `X-Shopify-Webhook-Id` headers. `HmacValidator.validate` will still pass because it never inspects those headers, and `Registry.process` will forward the attacker-chosen `shop` value straight into `WebhookMetadata` as if it were authenticated: [5](#0-4) 

This is the "field acted on but not covered by the HMAC" identity-binding break: the gem's own webhook-processing API leads host applications to believe `data.shop` is authenticated (it's guarded by "the HMAC validated"), when in fact it is fully attacker-controlled header data.

### Impact Explanation
Any handler that keys tenant-scoped operations off `WebhookMetadata#shop` (the pattern the library itself documents/tests, e.g. `assert_equal(@shop, data.shop)` in the registry tests) can be made to attribute a genuinely-signed payload to an arbitrary victim shop domain. Depending on the app's handler logic this enables cross-tenant data injection or processing of compliance/lifecycle webhooks (e.g. `app/uninstalled`, `shop/redact`) against a shop the attacker does not control, purely by manipulating unauthenticated headers on a replayed request. This matches the Critical/High bar of cross-tenant access via a credential/identity-binding break, without needing the app's `client_secret`, an access token, or TLS interception.

### Likelihood Explanation
Obtaining one authentic `(raw_body, hmac)` pair requires nothing more than installing the target app on any store the attacker controls (public apps can typically be installed on a free/dev store by anyone) and capturing a webhook Shopify sends to that attacker-owned endpoint. Replaying it with modified headers to the app's public webhook URL requires only basic HTTP tooling. Likelihood is therefore realistic for any app exposing this library's default webhook processing without adding its own out-of-band shop validation.

### Recommendation
Bind the identity fields into the signed content, or otherwise cryptographically/contractually tie them to the verified body:
1. Include `shop`, `topic`, and `webhook_id` in `to_signable_string` (or a canonicalized combination of headers + body) so `HmacValidator` covers them.
2. Alternatively, require host applications to cross-check `request.shop` against a known/installed-shop registry before trusting `WebhookMetadata#shop`, and document this prominently since the current API implies HMAC success authenticates the whole `WebhookMetadata`, not just the body bytes.

### Proof of Concept
1. Install the target Shopify app on an attacker-controlled development store; the app registers webhooks (e.g., `orders/create`) that Shopify delivers to the app's public webhook endpoint with headers `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Topic: orders/create`, `X-Shopify-Hmac-Sha256: <valid hmac over raw_body>`.
2. Capture the exact `raw_body` and `X-Shopify-Hmac-Sha256` value from this real delivery.
3. Replay an HTTP POST to the same app webhook endpoint using the identical `raw_body` and `X-Shopify-Hmac-Sha256`, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb#L13-L22` returns `true` because it only checks the body bytes; `Registry.process` (`lib/shopify_api/webhooks/registry.rb#L188-L200`) invokes the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, causing the host app to act on attacker-supplied data under the victim shop's identity.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

        end
