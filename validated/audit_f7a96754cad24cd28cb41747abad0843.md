### Title
EvmHost native-fee dispatch permanently traps user's excess ETH after `swapETHForExactTokens` — ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` accept native ETH and swap it for `feeToken` via `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(...)`, but never handle or forward the ETH refund that the Uniswap V2 router issues for unspent input. Because the router refunds any leftover ETH to its immediate caller (`msg.sender` from the router's perspective, i.e. `EvmHost` itself), and `EvmHost` neither tracks nor returns that refund to the original transaction sender, any user who supplies more ETH than the exact amount consumed by the swap has that excess permanently trapped inside the Host contract.

### Finding Description
In `EvmHost.dispatch(DispatchPost)`: [1](#0-0) 

the same unguarded pattern repeats in `dispatch(DispatchGet)`: [2](#0-1) 

and in `fundRequest`: [3](#0-2) 

`swapETHForExactTokens(amountOut, path, to, deadline)` is a "swap for exact output" call: the router only spends as much ETH as the current pool price requires to deliver exactly `post.fee`/`get.fee`/`amount` of `feeToken`, and refunds the unspent balance of `msg.value` to whoever called it. Because `EvmHost` calls the router directly (not via `delegatecall`), the router's refund lands on `address(EvmHost)`, not on the original caller (`_msgSender()`). `EvmHost` performs no bookkeeping of this refund and has no mechanism that returns it to the depositor — the ETH simply becomes part of the Host's own balance, indistinguishable from protocol funds, and only the privileged `hostManager`/admin `withdraw` path can move ETH out (and that path is documented for "bridge revenue" withdrawal, not user refunds).

This is a genuine oversight rather than a deliberate design choice: the sibling application contract `IntentGatewayV2.sol` performs the identical swap pattern but explicitly tracks and refunds the leftover value to `msg.sender`: [4](#0-3) 

`EvmHost` lacks this `msgValue -= amounts[0]; ... _sendValue(msg.sender, msgValue);` step entirely.

Because the exact ETH amount required by a `getAmountsIn`/spot-price swap depends on the pool's reserves at execution time (which can move between the moment a caller queries `quote()` off-chain/at simulation and the moment their transaction is mined — due to normal trading, MEV, or intentional front-running of the pool), it is practically impossible for any caller to supply the exact `msg.value` the swap will consume. Overpayment is therefore the expected, common case, not an edge case — every native-fee dispatcher/relayer/bandwidth purchaser interacting with `dispatch()`/`fundRequest()` is at risk of losing the difference.

### Impact Explanation
This is a direct, permanent freezing-of-funds bug reachable by any unprivileged caller who dispatches a POST/GET request or funds a request using native ETH (the exact class of "message dispatcher" / "bandwidth purchaser" actor named in scope). Excess ETH sent to cover Uniswap V2 slippage is irrecoverably absorbed into the Host contract's balance with no path back to the sender, and is comingled with protocol fee-token/native revenue that only governance can withdraw.

### Likelihood Explanation
High likelihood: this triggers on ordinary usage, not an attack requiring special conditions. Any relayer, app, or SDK integration paying dispatch fees in native token (as documented and exercised in `EvmHost.dispatch`) will almost always send `msg.value` slightly above the amount the router ultimately consumes, because the swap price is determined at execution time while the payer's value is fixed beforehand.

### Recommendation
After calling `swapETHForExactTokens`, capture the `amounts[0]` actually spent (as `IntentGatewayV2` does) and refund `msg.value - amounts[0]` back to `_msgSender()` in `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()`.

### Proof of Concept
1. Attacker/user calls `EvmHost.dispatch{value: X}(post)` where `post.fee = F` and `X` is intentionally (or simply realistically) larger than the ETH required to buy `F` fee tokens at the current pool price (e.g., `X = 2×` the quoted amount, as is typical to cover slippage).
2. `IUniswapV2Router02.swapETHForExactTokens{value: X}(F, path, address(this), deadline)` spends `amountIn < X` ETH and refunds `X - amountIn` to `address(this)` (`EvmHost`).
3. `EvmHost.dispatch` returns normally; the request is dispatched correctly, but `X - amountIn` ETH now sits in the Host contract with no code path returning it to the caller.
4. Repeating this over many dispatches by many callers accumulates a growing, permanently stuck ETH balance inside `EvmHost`.
