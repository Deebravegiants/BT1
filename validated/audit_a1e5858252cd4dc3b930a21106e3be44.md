### Title
Webhook shop-domain header is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook request by checking the HMAC-SHA256 signature over the raw request body only. The `shop` (and `topic`/`webhook_id`/`api_version`) values are read directly from HTTP headers that are never included in the signed data, so they carry no cryptographic binding to the signature that "proves" the request came from Shopify for that shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, which is the data hashed/compared in `HmacValidator`: [1](#0-0) [2](#0-1) 

`HmacValidator.validate` computes the HMAC over `to_signable_string` (the body) and compares it with the `hmac` header value using `OpenSSL.secure_compare`: [3](#0-2) 

`Registry.process` then trusts `request.shop`, taken straight from the unauthenticated `x-shopify-shop-domain`/`shopify-shop-domain` header, to build the `WebhookMetadata` passed to the app's handler: [4](#0-3) 

This breaks the identity binding `shop authenticated == shop used to attribute/act on the webhook data`. Because the signature covers only the body bytes, any raw body + HMAC pair that was legitimately generated for one shop remains valid when replayed with a different `shop-domain` header value. An unprivileged internet user who controls (or can trigger webhooks for) their own Shopify store can capture a genuine, correctly-signed webhook payload sent to the app, then resend that exact body/HMAC pair to the same webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop. `HmacValidator.validate` still returns `true` (the body/HMAC pair is untouched), so `Registry.process` calls the configured handler with `data.shop` set to the victim's domain and `data.body` containing content the attacker fully controls.

The gem's own documentation reinforces that this is the intended, trusted use of the field: `Registry.process` is described as verifying "the request did indeed come from Shopify," and `data.shop` is documented as "The shop domain of the webhook" for the handler to act on — i.e., the host app is expected to trust `data.shop` as an authenticated tenant identifier, per the gem's documented contract (docs/usage/webhooks.md:14,125). The gem provides no additional binding (e.g., hashing the shop domain into the signed payload, or validating that the shop header matches a value embedded in the body) to prevent this substitution.

### Impact Explanation
This enables cross-tenant confusion: an attacker without any access token, `client_secret`, or privileged relationship to the victim shop can cause the app to process attacker-controlled webhook content as if it originated from the victim shop, and to attribute it to the victim's identity in `WebhookMetadata#shop`. Any host application that uses `data.shop` to select which shop's stored session/state to update (the exact pattern the docs' example demonstrates: `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) can be tricked into writing attacker-supplied data under a victim tenant's identity — a cross-tenant access/data-integrity violation matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires only that the attacker: (1) operate their own Shopify store that has installed the target app (readily achievable via public app install or a free/dev store), (2) capture one legitimate signed webhook body sent to the app's endpoint (network vantage point, logging system, or shared/misconfigured endpoint), and (3) resend that body with a forged `shop-domain` header — all without any secret material. No cryptography needs to be broken; the vulnerability is a missing binding, not a weak one.

### Recommendation
Include the shop domain (and ideally `topic`/`webhook_id`) in the HMAC-signed material verified by `HmacValidator`, or otherwise cryptographically bind `request.shop` to the verified payload before it is handed to `WebhookMetadata`/handlers — for example, by cross-checking the header-derived shop against a shop identifier embedded in the JSON body, or documenting/enforcing that host apps must not trust `data.shop` without an independent binding. At minimum, update `Request#to_signable_string` (lib/shopify_api/webhooks/request.rb:35-38) so the signed payload the gem verifies also covers the shop-domain header value.

### Proof of Concept
1. Attacker installs the vulnerable app on their own dev store `attacker.myshopify.com` and triggers a webhook (e.g., `products/update`) with attacker-controlled body content.
2. Attacker's endpoint (or a MITM/log capture point) records the raw POST body and the `X-Shopify-Hmac-Sha256` header Shopify sent — this HMAC is valid because it was genuinely computed by Shopify using the real `api_secret_key` over that body.
3. Attacker resends the exact same raw body and `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over the (unchanged) raw body and passes: `lib/shopify_api/utils/hmac_validator.rb:26-31`.
5. The handler is invoked with `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body: <attacker body>, ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), even though the payload never originated from, nor was authenticated for, `victim-shop.myshopify.com`.
