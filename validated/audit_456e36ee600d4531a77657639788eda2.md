### Title
Permissionless `TransferToGasKey` action lets any account grief a victim's gas key and block `DeleteKey`/`DeleteAccount` - (File: `runtime/runtime/src/access_keys.rs`)

### Summary
NEAR's gas-key feature exposes `TransferToGasKeyAction`, which funds an arbitrary account's gas key. Unlike other account-mutating actions, this action carries no check that the caller (predecessor) is the account owner: [1](#0-0)  operates purely on `account_id` (the receipt receiver) and `action.public_key`, crediting the deposit to `gas_key_info.balance` without any ownership check. It is validated only for the `GasKeys` protocol feature, with no actor/owner restriction: [2](#0-1) . It is also explicitly promise-batchable to any receiver from a contract via `promise_batch_action_transfer_to_gas_key`, which forwards the action to whatever `receiver_id` the promise targets: [3](#0-2) .

This mirrors the reported Uniswap bug class: an unprivileged actor can permissionlessly inflate state belonging to someone else's resource (a gas key, analogous to the NFT position), and that inflated state later causes a required "close"/"cleanup" operation on the resource to fail.

### Finding Description
Both `DeleteKey` (targeting a gas key) and `DeleteAccount` (which sums all gas-key balances on the account) reject the operation if gas-key balance exceeds `GasKeyInfo::MAX_BALANCE_TO_BURN` (1 NEAR):

- `delete_gas_key` rejects with `GasKeyBalanceTooHigh` when `gas_key_info.balance > GasKeyInfo::MAX_BALANCE_TO_BURN`: [4](#0-3) .
- `action_delete_account` computes `gas_key_balance_to_burn` from *all* gas keys on the account and rejects the whole account deletion the same way: [5](#0-4) .

Because `action_transfer_to_gas_key` has no restriction tying the funding transaction's predecessor to the target account, any account (or any contract dispatching a promise) can push a victim's gas-key balance above the 1-NEAR threshold at will, at negligible cost (the deposit itself is refunded/burned, not stolen — the attack is a griefing/DoS, not a theft). Tests in the repo directly demonstrate this failure mode: `test_delete_gas_key_balance_too_high` and `test_delete_account_gas_key_balance_too_high` both show `GasKeyBalanceTooHigh` blocking deletion once the funded balance crosses the threshold: [6](#0-5) [7](#0-6) .

This is the same root-cause pattern as the reported bug: the "closing" operation (`DeleteKey`/`DeleteAccount`) checks a live value (current gas-key balance) that any unprivileged third party can unilaterally increase, and the closing operation has a hard upper bound rather than decreasing/reconciling to the attacker-inflated amount — so once inflated past the limit, the close action deterministically reverts.

### Impact Explanation
An attacker can repeatedly (and cheaply, since `TransferToGasKeyAction.deposit` funds are not lost — they sit in the gas key balance or get burned only on successful deletion) fund a victim's gas key(s) to keep the balance above 1 NEAR, blocking:
- Deletion of that specific gas key (`DeleteKey` fails with `GasKeyBalanceTooHigh`).
- Deletion of the entire account (`DeleteAccount` fails the same way, since it sums all gas-key balances).

This is a denial-of-service / griefing vector against a legitimate account-cleanup operation, not a fund-theft bug (the "burn" is capped at 1 NEAR and is the victim's own funds sitting in the gas key, refundable via `WithdrawFromGasKey`). The victim can mitigate by calling `WithdrawFromGasKey` to reduce the balance before retrying deletion, but an attacker capable of front-running (re-funding right before the victim's delete transaction/receipt is applied) can indefinitely stall the account/key deletion, forcing repeated remediation transactions and preventing the account from ever being cleanly removed while contested.

### Likelihood Explanation
High for anyone motivated to grief a specific account: `TransferToGasKeyAction` requires only that the target account has an existing gas key (`GasKeyDoesNotExist` otherwise) and a `GasKeys`-enabled protocol version; no special permission, ownership, or non-trivial cost is required beyond the deposit itself, which is not lost outright (refundable by the victim). The action is reachable both directly via a transaction and via a contract-issued promise to an arbitrary receiver.

### Recommendation
Restrict `TransferToGasKeyAction` so it can only be applied when the receipt's predecessor is the account itself (self-funding), or alternatively, have `DeleteKey`/`DeleteAccount` cap/refund the excess gas-key balance back to the account owner instead of hard-failing when the balance exceeds `MAX_BALANCE_TO_BURN`, so a griefed balance cannot permanently block cleanup. This mirrors the recommended Uniswap fix of reconciling against the live/actual state at closing time rather than failing outright on values a third party can unilaterally inflate.

### Proof of Concept
1. Victim account `victim.near` has a gas key `PK_gas` (`AddKey` with `gas_key_full_access`).
2. Attacker sends a transaction/promise with action `TransferToGasKey { public_key: PK_gas, deposit: 2 NEAR }` targeting `victim.near` — this succeeds per `action_transfer_to_gas_key`, which performs no ownership check: [1](#0-0) .
3. `victim.near` submits `DeleteKey { public_key: PK_gas }`. `delete_gas_key` checks `gas_key_info.balance (2 NEAR) > GasKeyInfo::MAX_BALANCE_TO_BURN (1 NEAR)` and returns `ActionErrorKind::GasKeyBalanceTooHigh`, aborting the deletion: [4](#0-3) .
4. Alternatively, `victim.near` submits `DeleteAccount`. `action_delete_account` sums all gas-key balances (`compute_gas_key_balance_sum`), finds it exceeds `MAX_BALANCE_TO_BURN`, and rejects with the same error, leaving the account undeleted: [5](#0-4) .
5. The attacker can repeat step 2 (re-fund) whenever the victim attempts to reduce the balance via `WithdrawFromGasKey`, sustaining the DoS.

pub(crate) fn action_transfer_to_gas_key(
    state_update: &mut TrieUpdate,
    result: &mut ActionResult,
    account_id: &AccountId,
    action: &TransferToGasKeyAction,
) -> Result<(), RuntimeError> {
    let Some(mut access_key) = get_access_key(state_update, account_id, &action.public_key)? else {
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };
    let Some(gas_key_info) = access_key.gas_key_info_mut() else {
        // Key exists but is not a gas key
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };

    gas_key_info.balance = gas_key_info.balance.checked_add(action.deposit).ok_or_else(|| {
        RuntimeError::StorageError(StorageError::StorageInconsistentState(
            "gas key balance integer overflow".to_string(),
        ))
    })?;
    set_access_key(state_update, account_id.clone(), action.public_key.clone(), &access_key);
    Ok(())
}

    fn test_delete_account_gas_key_balance_too_high() {
        let (account_id, public_key, access_key) = test_account_keys();
        let public_keys: Vec<PublicKey> = (0..3)
            .map(|i| PublicKey::from_seed(KeyType::ED25519, &format!("gas_key_{i}")))
            .collect();
        let mut state_update = setup_account(&account_id, &public_key, &access_key);
        let mut account = get_account(&state_update, &account_id).unwrap().unwrap();
        for public_key in &public_keys {
            add_gas_key_to_account(&mut state_update, &mut account, &account_id, public_key);
        }

        // Fund gas keys so total exceeds 1 NEAR
        let deposit_amounts = [
            Balance::from_millinear(400),
            Balance::from_millinear(400),
            Balance::from_millinear(201),
        ];
        for (pk, amount) in public_keys.iter().zip(deposit_amounts.iter()) {
            transfer_to_gas_key(&mut state_update, &account_id, pk, *amount);
        }
        state_update.commit(StateChangeCause::InitialState);

        let action_result = test_delete_account(
            &account_id,
            AccountContract::from_local_code_hash(CryptoHash::default()),
            100,
            PROTOCOL_VERSION,
            &mut state_update,
        );
        let expected_total =
            deposit_amounts.iter().fold(Balance::ZERO, |acc, x| acc.checked_add(*x).unwrap());
        assert_eq!(
            action_result.result,
            Err(ActionErrorKind::GasKeyBalanceTooHigh {
                account_id: account_id.clone(),
                public_key: None,
                balance: expected_total,
            }
            .into())
        );
        assert_eq!(action_result.tokens_burnt, Balance::ZERO);
    }
