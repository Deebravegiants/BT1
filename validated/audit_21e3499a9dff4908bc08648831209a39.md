Confirmed: the webhook HMAC in `Utils::HmacValidator.validate` signs only `Webhooks::Request#to_signable_string`, which returns `@raw_body` alone [1](#0-0) . None of the Shopify headers — including `shop-domain`, `topic`, `webhook-id`, `api-version` — are part of the signed content [2](#0-1) . `Registry.process` validates only this body HMAC, then forwards `request.shop` unchecked to the app's handler [3](#0-2) .

Since a single app has one `client_secret` (`Context.api_secret_key`) shared across all installing shops, any shop that installs the app can generate a legitimately-HMAC'd webhook body (e.g. by triggering `orders/create` on their own store) and then replay that raw body to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a victim shop — the gem has no way to detect this because the header isn't covered by the signature.

### Title
Webhook shop-domain header not covered by HMAC allows cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, excluding all `X-Shopify-*` headers. `Utils::HmacValidator.validate` therefore only proves that the body bytes were produced by an app holding the correct `client_secret` — it proves nothing about which shop (`shop-domain` header) the payload belongs to. Because a single app shares one `client_secret` across every merchant that installs it, any unprivileged merchant/attacker who installs the app can capture a validly-signed webhook body from their own shop and replay it to the app's webhook handler with the `X-Shopify-Shop-Domain` header changed to a victim's shop domain.

### Finding Description
The identity binding that should hold is: `hmac(raw_body) valid` ⇒ `shop header == shop that produced raw_body`. In this gem that equality does not hold, because:
- `hmac` is computed with `Digest.hexencode(Base64.decode64(shopify_header("hmac-sha256")))` [4](#0-3) .
- The signed content is `to_signable_string` = `@raw_body` only [1](#0-0) .
- `shop`, `topic`, `webhook_id`, and `api_version` are read straight from unauthenticated headers [2](#0-1) .
- `HmacValidator.validate` recomputes the HMAC purely from `to_signable_string` and the app's `api_secret_key`, comparing it against the received `hmac` header value [5](#0-4) .
- `Registry.process` trusts this result and passes `request.shop` (an unverified header) straight into `WebhookMetadata` handed to the app's handler [3](#0-2) .

Because `api_secret_key` is the same for every shop that installs a given app, an attacker's own (legitimately installed) shop can produce a fully valid `(raw_body, hmac)` pair. The attacker then re-POSTs that exact body/HMAC pair to the app's webhook endpoint with a forged `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header pointing at a victim shop. `HmacValidator.validate` still returns `true` because it never looks at the header, and `Registry.process` dispatches the handler believing the payload originated from the victim shop.

### Impact Explanation
This breaks the tenant-identity boundary the gem is supposed to provide app authors: `WebhookMetadata#shop` is the primary signal apps use to know which merchant a webhook event belongs to (used to look up that shop's session/access token, update that shop's records, etc.). An attacker able to forge this field can inject events attributed to a shop they do not own, resulting in cross-tenant data confusion/corruption within the app built on this gem — e.g., a victim shop's synced data being overwritten with attacker-controlled content, or app-side per-shop state being manipulated using another tenant's identity, without any credential belonging to the victim.

### Likelihood Explanation
Reachable by any unprivileged attacker who can install the target app on a shop they control (a normal, unprivileged flow) and who can send arbitrary HTTP requests to the app's public webhook receiver endpoint. No access token, `client_secret`, or victim credential is required — only reuse of a body/HMAC pair the attacker legitimately obtained for their own shop.

### Recommendation
Bind the `shop-domain` (and ideally `topic`/`webhook-id`) header into the material that is verified, e.g. require the caller to additionally confirm `request.shop` is a shop with an active, known installation/session in the app's own store *before* trusting it, or incorporate the header value into the signed payload comparison used at the transport layer (this requires coordinating with Shopify's webhook signing scheme). At minimum, document clearly that `Webhooks::Request#shop` is unauthenticated and must be cross-checked by the host application against a known/registered shop list before being used for any tenant-scoped action.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (a normal, unprivileged install).
2. Attacker triggers a webhook event (e.g. `orders/create`) on their own shop; Shopify sends a POST with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(client_secret, B)` and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker replays the identical body `B` and header `X-Shopify-Hmac-Sha256: H` to the app's webhook endpoint but changes `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...shop-domain: "victim-shop.myshopify.com", hmac-sha256: H...})` is constructed; `Utils::HmacValidator.validate(request)` returns `true` because it only hashes `B`.
5. `Registry.process` dispatches the handler with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the app to act on `B`'s content as if it belongs to `victim-shop.myshopify.com`.
