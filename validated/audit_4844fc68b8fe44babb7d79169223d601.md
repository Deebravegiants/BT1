## Finding

### Title
Object ownership cycle via unrestricted `to` in `object::transfer_raw` permanently bricks the object and defeats `root_owner()`/`owns()` traversal bounds - ([File: aptos-move/framework/aptos-framework/sources/object.move])

### Summary
`object::transfer_raw` only validates that the calling signer currently (transitively) owns the object being moved; it never validates the destination address `to`. This lets a legitimate owner set `to` to an object that is itself (directly or transitively) owned by the object being transferred, creating a 2-object ownership cycle. Once created, the cycle permanently blocks any future transfer of either object (via the bounded nesting check in `verify_ungated_and_descendant`), and causes `root_owner()` — which has no nesting bound at all — to loop until the transaction runs out of gas whenever invoked on either object or any of their descendants.

### Finding Description
`transfer_raw` calls `verify_ungated_and_descendant(owner_address, object)` to confirm `owner_address` transitively owns `object`, then unconditionally sets `object`'s owner to `to`: [1](#0-0) 

Nothing checks that `to` is not itself owned (directly or indirectly) by `object`. So:
1. Alice owns Object `A` (`A.owner = Alice`).
2. Anyone creates Object `B` with `owner_address = A` (any address can be passed to `object::create_object`), so `B.owner = A`.
3. Alice — who legitimately owns `A` — calls `transfer(alice, A, to = address_of(B))`. `verify_ungated_and_descendant(alice, A)` succeeds trivially since `A.owner == alice` already. `transfer_raw_inner` then sets `A.owner = B`.

Now `A.owner = B` and `B.owner = A`: a closed 2-cycle with no EOA at the root.

This breaks two custody invariants:
- `verify_ungated_and_descendant` (used by every ungated `transfer`/`transfer_raw`) walks the owner chain bounded by `MAXIMUM_OBJECT_NESTING` and aborts with `EMAXIMUM_NESTING` if the bound is exceeded: [2](#0-1) 
Once `A`/`B` cycle, any attempt to transfer `A` or `B` (or verify their ownership chain against any address) walks the 2-cycle forever until it hits the bound and reverts — it can never resolve to an actual owner. This means `A` and `B`, and any resource held under their signer-derived addresses (e.g. `ExtendRef`-derived resources, nested `FungibleStore`/token objects, `ManagingRefs` for code objects), can never again be ungated-transferred out. This is a **permanent, non-recoverable lock** of any value custodied by those addresses.
- `root_owner()` has **no nesting bound whatsoever**, unlike `owns()` and `verify_ungated_and_descendant()`: [3](#0-2) 
Calling `root_owner()` on `A`, `B`, or any object nested under them loops indefinitely (until out-of-gas) since `is_object(obj_owner)` will always be true for the alternating `A`/`B` addresses.

`root_owner()` is directly used in the code-object custody path: `code::publish_package` calls it to record the "deploy owner" gate for lazy self-initialization, and `init::assert_may_self_initialize` re-derives it to authorize minting a signer for a code object: [4](#0-3) [5](#0-4) 
If a code object is ever nested under (or becomes part of) such a cycle, both `publish_package` (republishing/upgrading that code object) and `internal_maybe_initialize`'s self-init guard become permanently unusable (guaranteed out-of-gas), which — combined with the transfer lock above — freezes both ownership *and* upgrade/init authority for any code object caught in or beneath the cycle.

### Impact Explanation
This meets the custody bar: "Permanent lock or non-recoverable loss of object-held, multisig-held, or resource-account-held value." Any asset custodied by an object that becomes part of (or a descendant of) such a 2-cycle — token objects, fungible stores held under the object's signer, code-object upgrade/freeze authority — can never be transferred or recovered again, because the only transfer path (`transfer`/`transfer_raw`/`transfer_to_object`) is gated by `verify_ungated_and_descendant`, which will deterministically abort once the cycle exists. No owner, admin, or governance action within the `object` module can undo it, since there is no cycle-repair function.

### Likelihood Explanation
The root cause requires no privilege beyond normal, unprivileged object usage: `object::create_object(owner_address)` accepts an arbitrary address argument from any caller, and `transfer`/`transfer_raw` never validate `to`. Any account that legitimately owns one object can trivially construct a second object owned by the first, then transfer the first into the second, at the cost of two ordinary transactions. This requires no oracle, no governance, no leaked keys — it is directly reachable by an unprivileged user, including against their own or a victim's shared/child objects if the attacker is (even transiently) the current owner of `A` (e.g., during a marketplace escrow window, or against an object they legitimately own but plan to sell).

### Recommendation
- Add a `to`-side ownership-cycle check in `transfer_raw`/`transfer_raw_inner` (or in `verify_ungated_and_descendant`) that rejects transfers where `to` is already transitively owned by `object`, mirroring the bounded walk already used for the `owner` side.
- Add the same `MAXIMUM_OBJECT_NESTING` bound to `root_owner()` that `owns()` and `verify_ungated_and_descendant()` already enforce, and have it abort (rather than loop unbounded) on a detected cycle, so at minimum the failure mode is a bounded, diagnosable abort instead of an unrestricted out-of-gas any time the function is invoked.

### Proof of Concept
```move
// 1. Alice creates object A, owned by herself.
let a_ref = object::create_object(@alice);
let a = object::address_from_constructor_ref(&a_ref);

// 2. Anyone creates object B, owned by A (create_object takes a raw address, no ownership check).
let b_ref = object::create_object(a);
let b = object::address_from_constructor_ref(&b_ref);

// 3. Alice, the legitimate current owner of A, transfers A to B.
object::transfer(&alice_signer, object::object_from_constructor_ref<ObjectCore>(&a_ref), b);
// Now: A.owner == B, B.owner == A.

// 4. Any subsequent transfer of A or B now aborts (EMAXIMUM_NESTING) forever:
object::transfer(&alice_signer, object::object_from_constructor_ref<ObjectCore>(&a_ref), @alice); // aborts

// 5. root_owner() on either object infinite-loops until out-of-gas:
object::root_owner(object::address_to_object<ObjectCore>(a)); // never returns, OOG
```

### Note on unverified scope
I was unable to fully confirm within this session whether `fungible_asset::withdraw`/deposit authorization for non-primary `FungibleStore`s calls the chain-walking `object::owns()`/`root_owner()` (which would extend this bug to directly bricking arbitrary fungible-asset balances) or only the direct `object::owner()`/`is_owner()` check (which reads `ObjectCore.owner` without walking the chain and would not itself infinite-loop, though the store would still become unrecoverable once its owning object is caught in the cycle, since it can never be transferred out). The code-object custody impact (via `code::publish_package`/`init::assert_may_self_initialize`) and the general transfer-lock impact via `verify_ungated_and_descendant`, however, are directly proven by the cited code.

    fun verify_ungated_and_descendant(owner: address, destination: address) {
        let current_address = destination;
        assert!(
            exists<ObjectCore>(current_address),
            error::not_found(EOBJECT_DOES_NOT_EXIST),
        );

        let object = borrow_global<ObjectCore>(current_address);
        assert!(
            object.allow_ungated_transfer,
            error::permission_denied(ENO_UNGATED_TRANSFERS),
        );

        let current_address = object.owner;
        let count = 0;
        while (owner != current_address) {
            count += 1;
            assert!(count < MAXIMUM_OBJECT_NESTING, error::out_of_range(EMAXIMUM_NESTING));
            // At this point, the first object exists and so the more likely case is that the
            // object's owner is not an object. So we return a more sensible error.
            assert!(
                exists<ObjectCore>(current_address),
                error::permission_denied(ENOT_OBJECT_OWNER),
            );
            let object = borrow_global<ObjectCore>(current_address);
            assert!(
                object.allow_ungated_transfer,
                error::permission_denied(ENO_UNGATED_TRANSFERS),
            );
            current_address = object.owner;
        };
    }
