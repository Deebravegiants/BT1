### Title
Webhook tenant-identifying headers (`shop-domain`, `topic`, `webhook-id`) are not bound by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while `shop-domain`, `topic`, and `webhook-id` are read from unauthenticated headers and passed straight into the application's webhook handler. Because Shopify signs webhooks with the app's single, shared `client_secret` (not a per-shop secret), any installer of the app can obtain a validly-signed `(body, hmac)` pair for content of their own choosing and replay it with a different `shop-domain` header, causing the host application to attribute attacker-controlled webhook data to another merchant's tenant.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop`, `topic`, and `webhook_id` are pulled directly from headers with no cryptographic binding to the signature: [2](#0-1) 

`HmacValidator.validate` only ever checks the signable string (the body) against the received `hmac`: [3](#0-2) 

`Webhooks::Registry.process` validates that HMAC and then immediately trusts the unauthenticated `request.topic`, `request.shop`, and `request.webhook_id` values to dispatch the payload to the handler, using `shop` as the tenant identifier: [4](#0-3) 

The identity binding that should hold is:
`HMAC(client_secret, signed_bytes)` valid ⇒ `(shop, topic, webhook_id, body)` as delivered by Shopify for *that* installation.

What actually holds is:
`HMAC(client_secret, body)` valid ⇒ only `body` is authentic; `shop`, `topic`, and `webhook_id` are arbitrary attacker-supplied bytes that were never part of `signed_bytes`.

Because the HMAC secret (`Context.api_secret_key`, the app's `client_secret`) is shared across every shop that installs the app, an attacker who is themselves a legitimate (if unprivileged) installer of the app can:
1. Trigger a webhook delivery to their own shop with a body of their choosing (e.g., by creating an order, editing a product, etc., whatever maps to the webhook topic they want to abuse).
2. Capture the legitimately-signed `(raw_body, X-Shopify-Hmac-Sha256)` pair Shopify sends them.
3. Replay that exact body/HMAC pair to the app's webhook endpoint, substituting the `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header with a victim shop's domain.
4. `Utils::HmacValidator.validate` accepts the request because it only checks the body, and `Registry.process` forwards `shop: request.shop` (the attacker-chosen victim domain) to the handler as if Shopify had confirmed this data belongs to that shop.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook processing: the `shop` value acted upon by the handler is not the `shop` value verified by the cryptographic signature. Depending on how the host app uses `WebhookMetadata#shop` (e.g., as a lookup key to update per-tenant records, trigger per-tenant business logic, or attribute events), this permits cross-tenant data injection/corruption — one merchant can inject attacker-controlled webhook payloads that the app will process as authentic events belonging to a different merchant. This matches the Critical "cross-tenant access" impact category, since the boundary broken is the per-shop authentication scope of the shared webhook secret.

### Likelihood Explanation
Likelihood is bounded by the fact that the attacker must be able to install the app on at least one shop (a normal, unprivileged action for any Shopify merchant/developer using a public or custom app) and knows/controls the victim shop's domain string (public information, since myshopify.com subdomains are guessable/enumerable). No leaked secret, access token, or privileged account is required — only normal use of the app as an installer plus direct HTTP requests to the app's public webhook endpoint with forged headers, both of which are available to any unprivileged internet user.

### Recommendation
Include the identifying headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signed material, or otherwise cryptographically bind them to the request (e.g., derive/verify `shop` independently against the app's own installation records rather than trusting the header), before `Webhooks::Registry.process` uses `request.shop`/`request.topic` to route or attribute the payload. At minimum, document and enforce that `WebhookMetadata#shop`/`#topic`/`#webhook_id` must be cross-checked by the host application against the tenant that installed the app for the given `X-Shopify-Api-Key`/session, since they carry no integrity guarantee from `HmacValidator.validate`.

### Proof of Concept
```ruby
# Attacker owns shop "attacker.myshopify.com" and has the app installed there.
# Step 1: attacker triggers a real webhook to their own shop and captures the raw body + valid HMAC
raw_body = '{"id": 1, "note": "attacker-controlled content"}'
valid_hmac = Base64.encode64(
  OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)
)

# Step 2: attacker replays the same (body, hmac) pair, but swaps the shop-domain header
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => valid_hmac,
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # not covered by the HMAC
  "x-shopify-webhook-id" => "forged-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

# Passes validation because only raw_body is checked:
ShopifyAPI::Utils::HmacValidator.validate(request) # => true

# Registry.process dispatches attacker-controlled data as if it belongs to victim-shop:
ShopifyAPI::Webhooks::Registry.process(request)
# handler.handle(data: WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: ...))
```
