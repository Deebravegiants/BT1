## Title
Webhook `shop` (tenant) identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-covered content from the raw body only, while the `shop` (tenant identity) used by `Registry.process` to dispatch a webhook to a handler is read from an HTTP header that is completely outside the HMAC's coverage. This breaks the identity binding `shop_verified == shop_acted_upon`, the exact bug class described in the report (a field acted on but not covered by the HMAC).

### Finding Description
`Webhooks::Request#to_signable_string` returns only the raw request body: [1](#0-0) 

The `shop` accessor, however, is parsed straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, with no cryptographic tie to the signed body: [2](#0-1) [3](#0-2) 

`Registry.process` validates the HMAC against the body only, then passes the header-derived, unverified `shop` straight to the handler as the tenant identity: [4](#0-3) 

And `HmacValidator.validate` / `validate_signature` confirm the check only ever operates on `verifiable_query.to_signable_string`, i.e., the body — never the headers: [5](#0-4) 

So the equality that should hold is:
`HMAC-verified-bytes == bytes the app treats as the shop identity used to select per-tenant state/handlers`

but in fact:
`HMAC-verified-bytes = raw_body` while `shop-identity-used-by-handler = header("shopify-shop-domain")`, which is disjoint from the verified bytes.

### Impact Explanation
Any unprivileged actor who can obtain one legitimately-signed webhook delivery for a shop they control (trivial — install the app on their own dev/test store and let Shopify deliver a real webhook) can replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a victim shop. Because the header is not part of the signed content, `Utils::HmacValidator.validate` still succeeds, and `Registry.process` dispatches the forged request to the handler tagged with the victim's shop: [6](#0-5) 

Downstream handlers that key off `WebhookMetadata#shop` (e.g., an `app/uninstalled` handler that deletes stored sessions/tokens, or a handler that looks up the victim's session/access token to act on the forged body) will act on behalf of the victim shop, using attacker-supplied data. This is a genuine cross-tenant identity break reachable without any secret, TLS interception, or privileged account.

### Likelihood Explanation
Requires only: (1) being a legitimate merchant/user of the target app on at least one store, to capture one valid signed webhook body/HMAC pair, and (2) the ability to send an arbitrary HTTP request to the app's public webhook receiving endpoint with modified headers. Both are attacker-controlled, unprivileged actions — no credentials of the victim, no `api_secret_key`, and no network interception are needed.

### Recommendation
Bind the shop (and topic/webhook-id) into the value that is HMAC-verified, or otherwise cryptographically tie the header-derived `shop` to the signed body before it is trusted as tenant identity (e.g., verify `shop` against a shop that the app already has an active session/installation for, or include shop/topic in the signed payload as Shopify's newer webhook formats support). At minimum, document prominently that `request.shop` is unauthenticated and must be cross-checked by the host app against known/installed shops before being used to select tenant state.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook (e.g., `orders/create`) with a body they control.
2. Attacker captures the delivered `X-Shopify-Hmac-Sha256` value and raw body — this HMAC is valid for that body under the app's `api_secret_key`.
3. Attacker POSTs the same body and HMAC header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` and `X-Shopify-Topic: app/uninstalled` (or any topic/body reused as-is).
4. `ShopifyAPI::Webhooks::Request.new` accepts the headers, `Utils::HmacValidator.validate` succeeds (it only checks `raw_body` against the HMAC), and `Registry.process` invokes the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, causing the handler to act on the victim shop using attacker-supplied body data.
