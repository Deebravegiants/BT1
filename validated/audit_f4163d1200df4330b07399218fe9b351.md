### Title
Webhook tenant identity (`shop`, `topic`, `webhook_id`) is not covered by the HMAC signature - (`File: lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop`, `topic`, `webhook_id`, and `api_version` from raw, unauthenticated HTTP headers, while `to_signable_string` — the value that `Utils::HmacValidator` actually verifies — is only the raw request body. `Registry.process` validates the HMAC over the body and then unconditionally trusts the header-derived `shop` value to build the `WebhookMetadata` object passed to the host app's handler. The identity binding the gem is implicitly claiming ("this webhook, verified by HMAC, belongs to shop X") is false: the HMAC proves the body is authentic, not that it belongs to the shop named in the header.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from headers, none of which are part of the signed content: [2](#0-1) 

`Registry.process` validates only the HMAC of the request (i.e., the body) and then immediately builds `WebhookMetadata` using the unauthenticated `request.shop`, `request.topic`, and `request.webhook_id`, handing it to the app's registered handler as if the shop attribution were verified: [3](#0-2) 

`Utils::HmacValidator.validate` computes/compares the signature purely against `verifiable_query.to_signable_string`: [4](#0-3) 

The broken identity equality is:
`shop attribute trusted by Registry.process/WebhookMetadata` == `shop attribute covered by the HMAC that Registry.process just verified`

These are not the same value — the second set is empty. The HMAC guarantees body integrity/authenticity (i.e., that whoever holds `api_secret_key` produced this exact JSON payload) but says nothing about which shop, topic, or webhook subscription the header claims to represent. Because the same `api_secret_key` is shared across all shops that have the app installed, any two deliveries with byte-identical bodies (which is common for events with sparse/templated bodies, and trivially engineered by an attacker who fully controls their own shop's data feeding a webhook body) produce identical HMACs regardless of which shop they were generated for. This directly mirrors the reported bug class: an untyped/loosely-validated field (there, Sawyer's dynamic accessor on the `id`; here, the header-derived `shop`) is trusted for a security-relevant operation without being bound to the value the cryptographic check actually protects.

### Impact Explanation
If exploitable end-to-end, this allows a `shop`/`topic`/`webhook_id` header value to be substituted on an otherwise-validly-HMAC'd webhook body, causing the host application's handler to act on data attributed to the wrong tenant (cross-tenant data confusion) — e.g., writing/deleting/redacting records for shop B while believing the event came from shop B, when in fact only the body content (and its HMAC) originated from a delivery for shop A. This falls under the "cross-tenant access" Critical impact category defined in the rules, since the gem's own `Registry.process`/`WebhookMetadata` construction is the exact place binding shop identity to body without cryptographic backing.

### Likelihood Explanation
Likelihood is constrained by how an attacker actually obtains a legitimate `(body, hmac)` pair and delivers a header-modified copy to the app's public webhook endpoint. The gem does not require a specific transport, and if the host application exposes the webhook receiver as a normal public HTTP endpoint (which is the documented integration pattern — see `docs/usage/webhooks.md`/`Registry.process` usage), an attacker with a legitimate, unprivileged app installation (their own shop) can generate outbound webhook deliveries with attacker-influenced body content and then submit a modified copy of that captured request (same body/HMAC, different `shop-domain`/`topic`/`webhook-id` headers) directly to the app's endpoint over the open internet, with no need for TLS interception, secrets, or privileged access — only for the header fields to differ from the ones the body was actually generated for. I was not able to fully verify, purely from static analysis of this repo, whether typical deployments expose enough opportunity for an attacker to capture their own valid `(body, hmac)` pair without any interception step (e.g., via app-provided webhook logs/replay tooling) — that depends on host-application behavior which is outside this library's code. The root cause inside the gem, however, is unambiguous: no part of the shop/topic/webhook identity is bound to the signature it validates.

### Recommendation
Include `shop-domain`, `topic`, and `webhook-id` (and any other header claimed as authoritative) in the HMAC-signed material, or otherwise cryptographically bind them to the request (e.g., verify `shop` against the session/tenant context the app already trusts, not solely against the unauthenticated header) before constructing `WebhookMetadata` in `Registry.process`. At minimum, document prominently that `Webhooks::Request#shop`/`#topic`/`#webhook_id` are NOT covered by `Utils::HmacValidator.validate` and must not be used as the sole tenant-identification mechanism by host applications.

### Proof of Concept
1. Attacker installs the target app on their own shop (`attacker-shop.myshopify.com`), a fully unprivileged, legitimate app-install action.
2. Attacker triggers/observes a webhook delivery whose JSON body they control or can predict (many topics have sparse/templated bodies, e.g., minimal metafield or compliance-topic payloads), capturing the resulting `raw_body` and the corresponding `X-Shopify-Hmac-Sha256` value delivered to the app's endpoint (via any means available to them for their own shop, without needing to attack Shopify's transport).
3. Attacker crafts a new HTTP POST to the same public webhook endpoint using the identical `raw_body` (thus identical `X-Shopify-Hmac-Sha256`, since HMAC is computed only over the body with a shared secret) but sets `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) to a different shop's domain.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because the signature check only covers `@raw_body`:
```ruby
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))
```
5. The handler receives `WebhookMetadata` attributing the (attacker-influenced) body to the spoofed `shop`, and the host application processes/acts on it as an authenticated event for that shop.

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
