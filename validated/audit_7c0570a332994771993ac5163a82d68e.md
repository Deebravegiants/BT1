### Title
Webhook shop identity not bound to HMAC signature allows cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC computed by `Utils::HmacValidator.validate` authenticates the JSON body alone. The `shop` (and `topic`, `webhook_id`, `api_version`) values are read straight from HTTP headers that are never included in the signed content, yet `Registry.process` trusts `request.shop` as the tenant identity handed to the app's handler.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
and `shop` is pulled from the `x-shopify-shop-domain`/`shopify-shop-domain` header without any cryptographic tie to the body: [2](#0-1) 

`Registry.process` validates only the HMAC over the body, then immediately forwards the header-derived, unauthenticated `shop` value to the app-supplied handler: [3](#0-2) 

Because Shopify signs the webhook body with the app's `client_secret`, and that same `client_secret` is used for every shop that installs the app, any merchant who installs the app (an unprivileged action available to any internet user who can create a store) receives a legitimate `(raw_body, hmac)` pair. Since the header carrying the shop identity is outside the signed content, that attacker can capture one legitimate webhook delivery for their own shop and replay it to the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop. `HmacValidator.validate` still succeeds (the body and hmac are unchanged and self-consistent), and `Registry.process` passes the attacker-chosen `shop` string straight into `WebhookMetadata`, which the host application will treat as the authenticated tenant for that webhook event.

The identity binding that should hold is:
`shop authenticated by HMAC == shop attributed to the webhook event`
but the actual code enforces:
`shop attributed to the webhook event == unauthenticated header value`,
breaking the equality and letting one tenant forge events (e.g. `orders/create`, `customers/data_request`, `app/uninstalled`) attributed to a different tenant.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook processing: any app relying on `WebhookMetadata#shop` (as documented and demonstrated in `docs/usage/webhooks.md`) to select which shop's data to mutate, delete, or redact can be made to act on behalf of an attacker-chosen shop, resulting in cross-tenant access/data corruption purely through the gem's own webhook verification API.

### Likelihood Explanation
Any user can install a Shopify app for free/trial to obtain one valid `(raw_body, hmac)` pair, and no secret, access token, or privileged access is required to replay it against the webhook endpoint with a different `shop-domain` header — the exploit path is fully reachable through the gem's documented, public `Registry.process` / `Request.new` API.

### Recommendation
Bind the shop (and topic/webhook id) into the signed context, e.g., by requiring the caller to pass the expected shop/session and comparing it against `request.shop`, or by validating that `request.shop` corresponds to a shop with an active session/installation before dispatching to the handler, rather than trusting the header value implicitly once the body-only HMAC passes.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`, completing OAuth normally.
2. Shopify delivers a legitimate webhook (e.g., `orders/create`) to the app: raw body `B`, header `X-Shopify-Hmac-Sha256: H` (valid HMAC of `B` with the app's `client_secret`), header `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. Attacker resends the exact same body `B` and `H` to the app's webhook endpoint but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` returns `true` because it only checks `HMAC(B, secret) == H`, which is unchanged.
5. `Registry.process` calls the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)`, causing the host app to process an order/customer event as if it originated from the victim shop.
