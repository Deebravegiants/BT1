### Title
Unrestricted route-hop call targets let attacker code join the caller's authorization tree and drain wallet tokens - (File: contracts/swap-aggregator/src/venues/mod.rs)

### Summary
CVE-2021-30720 is a logic flaw where missing restrictions let a malicious site reach restricted destinations. The analog in XOXNO Lending is the swap aggregator's lack of any allowlist or validation on the external contract addresses a route names: every hop pool and token is taken verbatim from the attacker-controlled `swap_xdr` payload and invoked inside the caller's authorization context. A route can therefore place arbitrary attacker code on the call stack below the user's `require_auth`, where it issues token transfers out of the victim's wallet.

### Finding Description
`Program::decode` validates only the structural shape of the packed instruction stream (indices into the `assets` registry, mode bytes, distinct endpoints); it never checks whether the referenced `pool` or `token` addresses belong to a known venue. `dispatch_hop` then measures router balances around `ctx.hop.pool`'s swap and calls it unconditionally.

From `contracts/swap-aggregator/src/venues/mod.rs`:
```rust
match hop.venue {
    SwapVenue::Soroswap => soroswap::swap(&ctx),
    SwapVenue::Aquarius => aquarius::swap(&ctx, tokens_cache),
    SwapVenue::Phoenix => phoenix::swap(&ctx),
    SwapVenue::Sushi => sushi::swap(&ctx),
    SwapVenue::CometDex => comet::swap(&ctx),
};
```
Each adapter ends in `env.invoke_contract(&ctx.hop.pool, ...)` against an attacker-chosen address (e.g., `contracts/swap-aggregator/src/venues/phoenix.rs:23-25`). The venue enum is chosen by the payload's opcode byte, not by verifying the pool address — any contract can be reached under any venue label.

Because `execute_strategy` runs under `sender.require_auth()` (root entry), `require_auth` calls made by the rogue "pool" (e.g., `token.transfer(victim, attacker, X)` on an unrelated token) are recorded as children of the caller's root authorization entry by `simulateTransaction`, and they execute when the caller signs that tree. The controller strategies (`swap_collateral`, `swap_debt`, `multiply`, `repay_debt_with_collateral`) run under the same pattern: the account owner's root `require_auth` on the controller entrypoint absorbs the rogue child invocation.

The codebase itself proves this in `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`: a `RogueHopPool` named by the route performs `token.transfer(alice → attacker, WALLET_BALANCE)` during `swap_collateral`; simulation records it as a child of Alice's `swap_collateral` entry (line 222) and, once signed, the theft executes (lines 265-268). The threat model acknowledges the exposure: "The router calls the pool and token addresses its payload names and keeps no allowlist of them ... it executes if the caller signs that tree. The loss is then the caller's wallet, not the routed amount" (`docs/explanation/threat-model.md:154-161`).

### Impact Explanation
Theft of user funds: the attacker's contract can transfer the victim's entire balance of any token — including tokens unrelated to the swap and never deposited into the protocol. The loss is unbounded by `total_min_out`, residual allowances, or the controller's post-swap health-factor check, all of which pass normally since the rogue pool returns a fair output. Direct `execute_strategy` callers face identical exposure.

### Likelihood Explanation
Medium. Exploitation requires the victim to sign a transaction whose authorization tree contains the rogue child transfer — realistically served by a malicious/compromised quote or frontend that presents the poisoned simulated tree, exactly the web-facing trust boundary the CVE addresses. No privileged access, leaked key, or contract bug beyond the missing restriction is needed; a single unprivileged attacker deploys the rogue pool and crafts the route. The defense rests entirely on off-chain clients decoding and rejecting unexpected auth children, which the threat model itself prescribes as an external mitigation rather than a contract guarantee.

### Recommendation
Restrict the set of callable venues/pools on-chain: maintain an owner-managed pool/token allowlist (extending the existing whitelist storage in `contracts/swap-aggregator/src/storage.rs` beyond fee tokens), or bind each venue opcode to a known factory/registry so `dispatch_hop` can verify `hop.pool` before `invoke_contract`. Alternatively, scope the sender's authorization so venue calls cannot attach children to the caller's root entry. Until enforced, the documented client-side check (reject any auth tree with children beyond the single expected input transfer) is the only barrier and should be treated as mandatory.

### Proof of Concept
1. Attacker deploys `RogueHopPool` whose `swap()` calls `token::transfer(victim, attacker, balance)` on a token the victim holds.
2. Attacker builds `swap_xdr` naming that contract as a hop `pool` (any venue opcode) for a `USDC→ETH` route with a fair `min_out`, and serves it to the victim via a malicious quote.
3. Victim calls `controller.swap_collateral(caller, account_id, usdc_key, amount_in, eth_key, route)` (or router `execute_strategy` directly); simulation returns an auth tree containing `wallet_token.transfer(victim → attacker, balance)` as a child of the caller's root entry.
4. Victim signs the simulated tree; the rogue pool executes the transfer and the wallet balance is drained while the swap settles normally — reproduced in `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs:229-268`.
