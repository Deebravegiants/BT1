## Analysis

The reported bug class is "funds/fields acted upon that are not covered by the integrity check that gates the action" — i.e., a value trusted and acted on without being bound to the verified signature. In `shopify-api-ruby`, the analogous binding is: **the shop identity used by a webhook handler must equal the shop identity that was cryptographically verified by the HMAC.**

### Finding Description

`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content solely from the raw body: [1](#0-0) 

but exposes `shop` (and `topic`, `webhook_id`, `api_version`) purely from unauthenticated HTTP headers: [2](#0-1) 

`Utils::HmacValidator.validate` verifies only `to_signable_string` (the raw body) against `Context.api_secret_key`: [3](#0-2) 

`Registry.process` calls this validator, and — if it passes — trusts `request.shop` as the authenticated tenant identity, passing it straight into the handler via `WebhookMetadata`: [4](#0-3) 

The binding that should hold is: `verified(hmac_secret, raw_body) ⇒ shop == header["shop-domain"]`. In fact the HMAC only proves "this body was signed with the app's `api_secret_key`" — it says nothing about which shop the header claims to be. Since `api_secret_key` is a single **per-app** secret shared across every shop that installs the app (not a per-shop secret), any merchant who installs the app receives their own stream of genuinely-signed webhook deliveries. That merchant can capture a `(raw_body, hmac)` pair from their own legitimate webhook, then replay it to the app's public webhook endpoint with the `X-Shopify-Shop-Domain` header changed to a victim shop's domain. `HmacValidator.validate` still returns `true` (it never looks at the shop header), and `Registry.process` calls the handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain instead of the shop that actually produced the signature.

### Impact Explanation

Any app built on this gem whose webhook handlers use `WebhookMetadata#shop` to look up a session/token, write data, or gate a per-tenant action (the documented, intended usage pattern shown in `docs/usage/webhooks.md`) can be made to act on behalf of, or attribute data to, a shop the attacker does not control — a cross-tenant identity confusion caused purely by this gem's `Request`/`Registry` design not binding the header-derived `shop` to the HMAC-verified content.

### Likelihood Explanation

Requires only: (1) installing the app on any store (no elevated privilege, no leaked secret, no `api_secret_key` needed), (2) capturing one legitimate webhook delivery to that store, and (3) POSTing it back to the app's public webhook endpoint with a modified shop header. All of this is achievable by an unprivileged internet user/merchant.

### Recommendation

Bind the shop (and topic/webhook_id) into the verified signable content, e.g. include the `shop-domain` header value in `to_signable_string`, or independently verify that the shop claimed in the header matches a shop-specific expectation before trusting `WebhookMetadata#shop` in `Registry.process`.

### Proof of Concept

1. Attacker installs the target app on `attacker.myshopify.com` and receives a genuine webhook: body `B`, header `X-Shopify-Hmac-Sha256: H` (computed by Shopify using the app's single `api_secret_key`), `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Attacker replays the exact same request to the app's webhook endpoint, only changing the header to `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `request.to_signable_string` (`= B`, unchanged) and finds it matches `H` — validation passes.
4. The registered handler is invoked with `WebhookMetadata.new(topic:, shop: "victim.myshopify.com", body: parsed(B), ...)`, causing the app to process/act as though the (unrelated) webhook body came from `victim.myshopify.com`. [4](#0-3) [5](#0-4) [3](#0-2)

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
