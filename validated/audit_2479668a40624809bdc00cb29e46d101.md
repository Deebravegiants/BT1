### Title
Predictable, Secret-less Offline Session ID Used as the Trusted Session Cookie Enables Cross-Tenant Session Hijacking - (File: `lib/shopify_api/auth/session.rb`, `lib/shopify_api/auth/oauth.rb`, `lib/shopify_api/utils/session_utils.rb`)

### Summary
For non-embedded apps, `ShopifyAPI::Auth::Oauth.validate_auth_callback` sets the app's session-identifying cookie value directly to `session.id`. For offline sessions, `Session.from` computes that id as `"offline_#{shop}"` — a value derived entirely from the public, attacker-knowable shop domain, containing no secret entropy. `ShopifyAPI::Utils::SessionUtils.current_session_id` / `cookie_session_id` then treats this raw, unauthenticated cookie value as the authoritative key used by the host app to look up the stored `Session` (and its real `access_token`). Any unprivileged internet user who knows or guesses a target merchant's `.myshopify.com` domain can set this exact cookie value themselves and be resolved to that merchant's session.

### Finding Description
The binding that should hold is:
`session_id used to resolve a stored Session` == `a value only obtainable by completing OAuth for that specific shop (i.e., authenticated)`

This binding is broken because the id is a deterministic function of public data: [1](#0-0) 

```
def from(shop:, access_token_response:)
  is_online = access_token_response.online_token?
  if is_online
    ...
    id = "#{shop}_#{associated_user.id}"
  else
    id = "offline_#{shop}"
  end
```

`shop` here is the merchant's `myshopify.com` domain, which is public/guessable. For offline sessions (the default, most common token type for background/API work), the resulting `id` has zero secret entropy.

`Oauth.validate_auth_callback` then places this predictable id directly, in plaintext, as the value of the session cookie for non-embedded apps: [2](#0-1) 

Finally, `SessionUtils.current_session_id` trusts whatever value arrives in that cookie as the identity key, with no additional signature, MAC, or freshness check: [3](#0-2) [4](#0-3) 

The cookie is opaque only in appearance — the value equals a well-known, publicly computable string. This is exactly the "session id derived from unauthenticated bytes" bug class: the identity presented by the browser is never actually proven to have come from a completed OAuth flow for that tenant; it's just a formula anyone can compute (`"offline_" + shop`).

Contrast this with the embedded-app path, which correctly relies on a cryptographically-signed JWT (`Auth::JwtPayload`) bound to `Context.api_secret_key` — the non-embedded, cookie-based path has no equivalent binding.

### Impact Explanation
This enables cross-tenant session access: an attacker with no credentials can present `Cookie: shopify_app_session=offline_targetshop.myshopify.com` to the host application. Because the gem's own `SessionUtils.current_session_id`/`cookie_session_id` treat that raw string as sufficient proof of identity, the host app (following the gem's documented `SessionRepository.store_session` / lookup pattern in `docs/usage/oauth.md`) will resolve and use the real, previously-stored `Session` for that shop — including its live `access_token` — for the attacker's unauthenticated request. This is a cross-tenant access / session-fixation class issue meeting the Critical bar (cross-tenant access to another merchant's authenticated session and, transitively, its access token) without the attacker ever completing OAuth or possessing any secret.

### Likelihood Explanation
Likelihood is high for offline sessions: the only prerequisite is knowledge of the target's `myshopify.com` domain, which is routinely public (visible in storefront URLs, app installation flows, admin URLs, etc.) and requires no interaction with the victim, no TLS interception, and no leaked credential. Online sessions are less trivially guessable since they additionally require the numeric Shopify user id, but that is also often enumerable/discoverable in many app contexts.

### Recommendation
Do not use a deterministic, secret-free string as the value stored in the session cookie for non-embedded apps. Instead, generate an unguessable, high-entropy, per-session identifier for the cookie value (e.g., `SecureRandom.uuid`, which `Session#initialize` already generates by default when no `id:` is passed) and keep the `"offline_#{shop}"`/`"#{shop}_#{user_id}"` string purely as an internal storage key, not exposed as the value trusted from an unauthenticated cookie. Alternatively, sign/MAC the cookie value (e.g., HMAC with `Context.api_secret_key`) so `SessionUtils.cookie_session_id` can verify authenticity before trusting it.

### Proof of Concept
1. Merchant M installs a non-embedded app for `m-shop.myshopify.com` and completes OAuth; per `Session.from`, the host stores an offline `Session` with `id == "offline_m-shop.myshopify.com"`, and the browser receives `Set-Cookie: shopify_app_session=offline_m-shop.myshopify.com`.
2. Attacker A, who has never installed the app and holds no credentials, sends any authenticated-looking request to the host app with header `Cookie: shopify_app_session=offline_m-shop.myshopify.com` (a value trivially computed from the merchant's public shop domain).
3. The host app calls `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)`, which (per `lib/shopify_api/utils/session_utils.rb` lines 31-36) returns `cookie_session_id(cookies)` — i.e., the raw, attacker-supplied string — with no verification.
4. The host app's session storage lookup (per the gem's documented pattern) returns merchant M's real, previously stored `Session`, including its live `access_token`, letting attacker A act as merchant M.
