### Title
Atomic multi-token withdrawal in `IntentGatewayV2` permanently freezes an order's entire escrow if a single asset transfer reverts - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`IntentsBase._withdraw` releases every token in a `WithdrawalRequest` to one beneficiary inside a single loop. If the transfer for any one asset in that list reverts (a native-ETH send to a beneficiary without a payable fallback, or an ERC-20 with a compliance/blacklist hook such as USDC), the whole `_withdraw` call reverts. Since `EvmHost.dispatchIncoming` swallows a reverting `onAccept` and simply deletes the request receipt so delivery "can be retried," and the beneficiary/asset set never changes between retries, the delivery will fail identically forever — permanently freezing every other (otherwise redeemable) token escrowed for that same order, not just the one causing the revert. This mirrors the reported `FeeDistributor` bug class: one uncooperative recipient blocks withdrawal for everyone/everything in the same batch, with no migration or per-asset skip path.

### Finding Description
`IntentGatewayV2`/`ExtrinsicIntents` escrows one or more `TokenInfo` entries (native ETH and/or ERC-20s) per order. Redemption (`RedeemEscrow`) and refund (`RefundEscrow`) are both cross-chain messages delivered through Hyperbridge and processed by `onAccept`, which calls `_withdraw`: [1](#0-0) 

The function iterates `body.tokens` and, for each entry, transfers to a single `beneficiary` — native ETH via `_sendValue` (a raw `.call{value:}` whose failure reverts `InsufficientNativeToken`) or ERC-20 via `safeTransfer`: [2](#0-1) 

If any single element in that loop reverts — the beneficiary contract has no payable fallback / consumes excessive gas on receive, or one ERC-20 in the multi-asset order reverts the transfer (e.g. a blacklist-style token) — the entire `_withdraw` transaction reverts, and none of the tokens for that order (including otherwise-fine assets) are released.

Because delivery goes through the ISMP host, a reverting `onAccept` does not permanently fail the batch — `EvmHost.dispatchIncoming` catches the low-level call failure, deletes the request receipt "so that it can be retried," and returns without reverting the outer transaction: [3](#0-2) 

This "retryable" design assumes retries can eventually succeed. But `WithdrawalRequest.beneficiary` and `tokens` are fixed at dispatch time (set by `_fillCrossChain`'s `beneficiary`/`order.user`, and `order.inputs`), so every retry replays the exact same failing transfer — the message can never be delivered successfully, and the escrow is stuck with no on-chain path to bypass, split, or migrate the withdrawal.

### Impact Explanation
This is a permanent freeze of escrowed user funds: as soon as one asset transfer to the fixed beneficiary in a `WithdrawalRequest` reverts, none of the assets for that order — potentially multiple distinct ERC-20s plus native ETH totaling significant value — can ever be released, since the failure mode is deterministic and Hyperbridge's retry semantics cannot change the beneficiary or skip the offending asset. There is no `IntentGatewayV2` function that lets governance or the user re-route or force-withdraw the remaining good assets independently of the failing one. This matches "permanent freezing of funds" in the validation criteria.

### Likelihood Explanation
The trigger conditions are realistic and require no special privilege: a beneficiary that is a smart-contract wallet without a payable `receive`/`fallback` (common for some multisigs/vaults), out-of-gas on a beneficiary's fallback under the fixed gas stipend of `.call`, or an ERC-20 among the order's input/output tokens that can revert transfers to a specific address (e.g. compliance/blacklist tokens like USDC). Any user placing or filling an order with such a beneficiary or token combination — even unintentionally — locks that order's entire escrow. No admin or governance action is required to trigger it.

### Recommendation
Avoid all-or-nothing multi-asset release to a single, unchangeable beneficiary in one atomic call:
- Make asset transfers in `_withdraw` best-effort per token (catch/skip failures individually, e.g. using a low-level call with a bounded gas stipend and continuing the loop) so one failing asset cannot block release of the others.
- Persist any un-transferable amounts in a per-token, per-beneficiary "owed" balance that can be pulled later or redirected to a different address, rather than relying solely on ISMP's identical-input retry.
- Consider capping/forwarding gas on native transfers and falling back to a WETH-wrap-and-transfer pattern (as many escrow/vault contracts do) so a non-payable beneficiary cannot block ETH release.

### Proof of Concept
1. User places a cross-chain order with `order.inputs` containing two escrowed assets: `USDC` and native ETH.
2. Filler fills the order; `_fillCrossChain` dispatches `RedeemEscrow` with `beneficiary = filler` and `tokens = order.inputs` (both USDC and ETH) — see [4](#0-3) .
3. Suppose `filler`/beneficiary is a contract without a payable fallback (or the USDC beneficiary address is later blacklisted). On delivery, `onAccept` → `_withdraw` iterates the token list; the native ETH `_sendValue(beneficiary, amount)` reverts (`InsufficientNativeToken`), see [5](#0-4) .
4. The whole `_withdraw` call reverts, so `onAccept` reverts; `EvmHost.dispatchIncoming` catches this, deletes the receipt, and returns without reverting the batch ( [6](#0-5) ), leaving the message "retryable."
5. Any subsequent redelivery of the identical `RedeemEscrow` message hits the exact same revert (beneficiary and token list are unchanged), so it never succeeds — both the USDC and the ETH remain escrowed in `IntentGatewayV2` indefinitely, with no function to release them via any other path.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }
