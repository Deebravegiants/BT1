## Title
Unbounded input-token array in Intent Gateway orders enables gas-limit DoS that permanently freezes escrowed funds - (File: evm/src/apps/IntentGatewayV2.sol, evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
`placeOrder()` only checks that `order.inputs.length != 0` but imposes no upper bound on the number of distinct input tokens a user can escrow in a single order. `_withdraw()`, which releases the escrow, loops over the entire `tokens` array and performs one external transfer per element. This is the same bug class as Sherlock M-13 (Teller `CollateralManager#_withdraw()`): an unbounded, user-controlled array iterated with per-item external calls in the fund-release path.

### Finding Description
`placeOrder()` validates only `order.inputs.length == 0` before escrowing every input token in a loop [1](#0-0) , and credits escrow for each token with no cap on `inputsLen` [2](#0-1) .

`fillOrder()` only requires that `order.inputs.length == options.outputs.length` — it never bounds the absolute size [3](#0-2) . For cross-chain orders, "fills are all-or-nothing" (per the docs), so the full `tokens` list must be redeemed in one settlement message.

Escrow release happens in `_withdraw()`, which iterates the entire `body.tokens` array and performs an external ERC-20 `safeTransfer` (or native `_sendValue`) per token: [4](#0-3) . This is invoked from the cross-chain settlement path `onAccept()` → `_withdraw()` [5](#0-4) , and from same-chain cancellation `_cancelSameChain()`, which similarly builds a `remainingTokens` array of the same unbounded size and calls `_withdraw()` [6](#0-5) . The Tron variant (`IntentGatewayV2.sol`) has an identical unbounded loop in its `withdraw()` [7](#0-6) .

Just as in the Teller report — where an attacker inflated `_collateralInfo` so `CollateralManager#_withdraw()`'s per-asset loop exceeded the block gas limit and made `withdraw()`/`liquidateCollateral()` permanently revert — a user (or colluding solver) can construct an `Order` with an arbitrarily large `inputs` array (many distinct cheap ERC-20 tokens), escrow it via `placeOrder()`, and then trigger settlement (`onAccept` → `_withdraw`) whose loop size is proportional to `inputs.length`. If sized large enough, the release transaction exceeds the block gas limit and can never complete, on any resubmission.

### Impact Explanation
This is a fund-freezing (loss-of-funds) issue, not merely an availability issue: the number of tokens is fixed at `placeOrder` time and baked into the order commitment (`keccak256(abi.encode(order))`), so the size of the `_withdraw()` loop for that specific order can never shrink. Once an order's `inputs.length` is large enough to exceed the destination chain's block gas limit, `_withdraw()` for that commitment will revert on every call, forever — the escrowed tokens (and the accompanying protocol/relayer/transaction fees) become permanently unrecoverable, matching the "permanent freezing of funds" bar for a valid finding. Both settlement (redeem to solver) and refund/cancellation paths share the same `_withdraw()` function, so cancellation cannot serve as a fallback recovery mechanism either.

### Likelihood Explanation
The attack requires only a single `placeOrder()` call by any unprivileged user, using ordinary (or newly-deployed minimal) ERC-20 tokens as inputs — no privileged role, governance, or off-chain trust assumption is needed. Because there is no cap on `order.inputs.length` anywhere in `placeOrder`, `fillOrder`, or `_withdraw`, constructing an oversized array is straightforward and only requires deploying/using enough distinct token addresses and paying the associated gas/approval cost at placement time (which is cheaper than the release-time revert cost, mirroring the sherlock report's cost asymmetry). This affects a single order at a time (not the whole protocol), consistent with the "Medium" severity determination on the original Teller report.

### Recommendation
Enforce an explicit upper bound on `order.inputs.length` (and `order.output.assets.length`) in `placeOrder()`/`fillOrder()`, sized so that the worst-case `_withdraw()` loop cannot approach the destination chain's block gas limit. Alternatively, decouple withdrawal from a single atomic loop (e.g., allow per-token/partial withdrawal calls, similar to how Teller separated "withdraw" from "repay" logic) so that no single transaction is forced to iterate an unbounded, user-chosen array.

### Proof of Concept
1. Attacker calls `placeOrder()` with `order.inputs` containing N (e.g., 2,000+) distinct, cheaply-deployed ERC-20 tokens, each with a nonzero amount; only `inputs.length != 0` is checked [8](#0-7) . Escrow is credited per-token with no size limit [9](#0-8) .
2. For a cross-chain order, a solver (potentially the attacker itself, or anyone willing to match N output tokens) calls `fillOrder()`, which only checks `order.inputs.length == options.outputs.length` [3](#0-2) , and dispatches a `RedeemEscrow` cross-chain message carrying all N tokens.
3. On the source chain, `onAccept()` decodes the `WithdrawalRequest` and calls `_withdraw(body, ..., true)` [5](#0-4) , which loops over all N tokens performing an external transfer per iteration [10](#0-9) .
4. With N large enough, this transaction's gas cost exceeds the block gas limit and reverts unconditionally on every future attempt (the commitment/order data is fixed), permanently locking the escrowed input tokens and accrued fees for that order.
