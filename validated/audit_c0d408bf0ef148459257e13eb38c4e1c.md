### Title
Forged cross-chain messages can drain IntentGatewayV2 escrow on Tron via `instance()`'s unsafe `address(this)` fallback in `authenticate()` - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The LORIS CVE describes a backend endpoint that fails to correctly re-verify access permissions that the frontend assumed were already enforced, letting an unprivileged actor reach protected data by supplying a guessable identifier. The Tron variant of `IntentGatewayV2` has the analogous "authorization check that silently degrades" flaw: its `authenticate()` function is supposed to restrict `RedeemEscrow`/`RefundEscrow` message processing to messages originating from a *known, registered* peer `IntentGatewayV2` instance, but the helper it relies on (`instance()`) silently falls back to `address(this)` for any source chain that has no registered deployment, turning the check into a self-matching tautology that an attacker can satisfy from an unregistered/attacker-controlled source chain.

### Finding Description
`instance()` is defined as: [1](#0-0) 

```solidity
function instance(bytes calldata stateMachineId) public view returns (address) {
    address gateway = _instances[keccak256(stateMachineId)];
    return gateway == address(0) ? address(this) : gateway;
}

function authenticate(PostRequest calldata request) internal view {
    if (request.from.length != 20) revert InvalidInput();
    address module = address(bytes20(request.from));
    // IntentGateway only accepts incoming assets from itself or known instances
    if (instance(request.source) != module) revert Unauthorized();
}
```

`onAccept()` gates escrow release exclusively on `authenticate()` for `RedeemEscrow`/`RefundEscrow`: [2](#0-1) 

When `request.source` is a state machine for which no `_instances[keccak256(source)]` deployment has ever been registered by governance (`NewDeployment`), `instance(source)` returns `address(this)` instead of reverting. `authenticate()` then only checks whether `request.from == address(this)`. Since `from` is attacker-controlled content of the ISMP message (the sending module's address on the *source* chain, not something the destination host verifies against a registry), an attacker who deploys a contract at the exact address of the destination `IntentGatewayV2` (trivial via `CREATE2`/vanity deployment on any chain not already registered as a peer instance) can dispatch a legitimate, cryptographically-valid ISMP `PostRequest` from that chain with `from = address(destinationGateway)` and a forged `WithdrawalRequest` body (`RedeemEscrow`/`RefundEscrow`) naming an arbitrary existing order `commitment` and an arbitrary `beneficiary`.

Compare this to the current/hardened EVM implementation, whose `_instance()` explicitly reverts (`UnknownInstance`) rather than falling back to `address(this)`: [3](#0-2) 
This confirms the fallback in the Tron contract is a regression/divergence from the fixed pattern used elsewhere in the codebase, exactly mirroring the LORIS pattern of one code path enforcing access control correctly while a sibling path (the "backend" here being the Tron deployment) does not.

### Impact Explanation
Because `withdraw()` releases the full escrowed `TokenInfo[]` for the named `commitment` to `beneficiary` and marks `_filled[commitment]`, and does not re-derive/verify the commitment against the actual order or the actual filler, any attacker capable of relaying a valid consensus/state proof from an unregistered source chain can steal escrowed input tokens belonging to a legitimate user's order (theft/permanent freezing/unbacked release of escrowed funds) — this is concrete theft of funds via a forged, authenticated-looking message delivery, satisfying the "unauthorized app action" / "concrete theft of funds" bar.

### Likelihood Explanation
Reachable from a single relayed ISMP message dispatched by an unprivileged relayer/attacker from any chain with a consensus client registered on the destination host but which the specific `IntentGatewayV2` instance has never registered as a peer deployment (a very likely state for any newly-added or long-tail chain, or simply any chain omitted from `NewDeployment` governance calls). The only "difficulty" is deploying a contract at a colliding address via `CREATE2`, which is a standard, well-understood technique and requires no privileged access.

### Recommendation
Change `instance()` (or `authenticate()`) so that an unregistered `stateMachineId` reverts (e.g., `UnknownInstance`) instead of defaulting to `address(this)`, matching the hardened `_instance()` behavior already used in `evm/src/apps/intentsv2/IntentsBase.sol`. If the `address(this)` fallback is intentionally needed for same-chain self-addressed flows, gate it strictly to `request.source == host state machine` rather than any unmapped chain.

### Proof of Concept
1. Governance never calls `NewDeployment` to register a peer `IntentGatewayV2` for state machine `X` on the destination `IntentGatewayV2` (Tron).
2. Attacker deploys a contract via `CREATE2` on chain `X` (any chain with a working, registered ISMP consensus client on the destination host) at the exact address of the destination `IntentGatewayV2` contract.
3. From that contract, attacker dispatches a `PostRequest` to the destination chain: `source = X`, `from = address(destinationGateway)`, `to = destinationGateway`, `body = RedeemEscrow || abi.encode(WithdrawalRequest{commitment: <victim's known order commitment>, tokens: <victim's escrowed tokens>, beneficiary: attacker})`.
4. A relayer delivers the message with a valid state/consensus proof from chain `X` (this proof is legitimate — it's the attacker's own chain's state).
5. `onAccept()` → `authenticate()` → `instance(X)` returns `address(this)` (no registration exists) → equals `module` (`address(this)`, forged `from`) → passes.
6. `withdraw()` transfers the victim's escrowed tokens to the attacker's `beneficiary` and marks the order filled, before the legitimate solver/user can claim or cancel it. [4](#0-3)

                if (!success) revert TransferFailed();
