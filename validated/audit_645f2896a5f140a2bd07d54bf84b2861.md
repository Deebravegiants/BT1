### Title
Webhook `shop` (and `topic`/`webhook-id`/`api-version`) identity fields are not covered by the HMAC signature, enabling cross-tenant webhook replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, but the `shop` (tenant) identity that the handler ultimately trusts is read from an HTTP header that is excluded from the signed payload. This breaks the intended binding: `hmac == HMAC(raw_body)` should imply `shop-that-produced-body == shop-attributed-to-request`, but the header can be modified independently of the signed body.

### Finding Description
`Utils::HmacValidator.validate` computes and compares the signature only against `to_signable_string`, and for webhooks that method returns just the raw body: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` values used downstream are parsed straight from HTTP headers and are never included in the signed string: [2](#0-1) 

`Registry.process` validates only the HMAC-over-body, then immediately trusts `request.shop` (and `request.topic`) to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

Because the `shop-domain` header sits outside the HMAC's coverage, any request bearing a *previously observed, validly-signed* `(raw_body, hmac)` pair (e.g., from one tenant's webhook delivery) can be replayed with an attacker-substituted `shopify-shop-domain` header for a different tenant of the same app. `HmacValidator.validate` still returns `true` because it never inspects the header, and the app's handler receives `WebhookMetadata` claiming the forged shop while operating on the original tenant's body — a cross-tenant identity confusion.

### Impact Explanation
This satisfies the "cross-tenant access" impact bucket: an unprivileged party who has obtained (or can trigger) one legitimately HMAC-signed webhook delivery for the app (e.g., by installing the app on their own store and capturing their own webhook traffic) can relabel it to a victim shop and have the multi-tenant app process/attribute that payload under the victim's tenant identity, since the gem's own `Registry.process`/`HmacValidator` provide no mechanism to bind `shop` to the signed bytes.

### Likelihood Explanation
Requires the attacker to capture at least one validly-signed webhook (achievable by installing the app themselves, a normal unprivileged action) and to be able to deliver a crafted HTTP request with the forged header to the app's webhook endpoint — no `api_secret_key`, access token, or privileged account is needed, consistent with the "unprivileged internet user" threat model.

### Recommendation
Include `shop` (and ideally `topic`) in the value that is HMAC-verified, or otherwise cryptographically bind the shop identity to the authenticated body (e.g., verify the header value against a shop the app independently expects for that raw body/subscription) before trusting `request.shop` in `Registry.process`.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com`; capture a legitimate webhook POST — raw body `B` and header `X-Shopify-Hmac-Sha256: H` where `H = HMAC_SHA256(api_secret_key, B)`.
2. Replay the exact same body `B` and header `H`, but replace `X-Shopify-Shop-Domain` with `victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request#hmac` and `#to_signable_string` are unaffected by the header change, so `Utils::HmacValidator.validate(request)` at `lib/shopify_api/webhooks/registry.rb:190` still returns `true`.
4. `Registry.process` invokes `handler.handle` with `WebhookMetadata.new(... shop: "victim.myshopify.com" ...)`, causing the app to process attacker-supplied body content under the victim tenant's identity. [4](#0-3) [5](#0-4)

module ShopifyAPI
  module Webhooks
    class Request
      extend T::Sig
      include Utils::VerifiableQuery

      sig { override.returns(String) }
      def hmac
        Digest.hexencode(Base64.decode64(T.cast(shopify_header("hmac-sha256"), String)))
      end

      sig { returns(String) }
      def topic
        T.cast(shopify_header("topic"), String)
      end

      sig { returns(String) }
      def shop
        T.cast(shopify_header("shop-domain"), String)
      end

      sig { returns(String) }
      def api_version
        T.cast(shopify_header("api-version"), String)
      end

      sig { returns(String) }
      def webhook_id
        T.cast(shopify_header("webhook-id"), String)
      end

      sig { override.returns(String) }
      def to_signable_string
        @raw_body
      end

      sig { returns(T::Hash[String, T.untyped]) }
      def parsed_body
        JSON.parse(@raw_body)
      end

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end
