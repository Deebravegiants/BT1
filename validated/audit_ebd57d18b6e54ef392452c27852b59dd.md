### Title
Intent Gateway `_paused` flag is stored but never enforced, allowing order placement and fills to continue after pause - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentsBase` declares a `_paused` storage boolean (intended as an emergency-pause switch for the IntentGateway) but neither `IntentsBase.sol`, `ExtrinsicIntents.sol`, nor `IntrinsicIntents.sol` ever read it or gate any external entry point with it. There is no `whenNotPaused` modifier defined or applied anywhere in the intents module, so solvers can continue to fill orders (`_fillSameChain`, `_fillCrossChain`) and escrow can continue to be released/refunded (`_withdraw`, `onAccept`) regardless of the pause state — the exact analog of the reported "bid after pause" bug class, applied to intents fills/escrow instead of an auction bid.

### Finding Description
`IntentsBase.sol` defines: [1](#0-0) 
as an "appended last" storage slot, implying a pause mechanism was intended to be layered on top of the gateway's core order lifecycle.

However, none of the externally reachable order-lifecycle functions check this flag:
- `_fillSameChain` in `IntrinsicIntents.sol` (solver-callable same-chain fill), which transfers output tokens to the beneficiary and releases escrow via `_withdraw`, has no pause check: [2](#0-1) 
- `_fillCrossChain` in `ExtrinsicIntents.sol` (solver-callable cross-chain fill), which marks the order filled and dispatches escrow release, also has no pause check: [3](#0-2) 
- `onAccept`, which processes `RedeemEscrow`/`RefundEscrow` messages and releases escrow via `_withdraw`, only checks `_checkRelayer`, never `_paused`: [4](#0-3) 
- `_withdraw`, the common escrow-release/refund routine, similarly performs no pause check: [5](#0-4) 

A search across the repository confirms `_paused` is referenced only in test files and documentation/decision notes, never in an `if (_paused) revert ...` guard or a `whenNotPaused` modifier applied to any function in the intents module — unlike the sibling token-bridge contracts (`HyperFungibleToken.sol`, `WrappedHyperFungibleToken.sol`, `HyperbridgeLzEndpoint.sol`), which correctly gate `send`/`onAccept` with `whenNotPaused`: [6](#0-5) 

This is precisely the bug class from the external report: a pause primitive exists but the state-changing entry points that should respect it (here, order fills and escrow settlement, analogous to `createBid`) do not check it.

### Impact Explanation
If governance/operator pauses the IntentGateway (presumably in response to a discovered vulnerability, price-oracle manipulation, a compromised solver, or another active incident), solvers can still call `fillOrder`/`fillOrderPartial` paths, complete fills against user escrow, and receive escrowed input tokens via `_withdraw`, and incoming cross-chain `RedeemEscrow`/`RefundEscrow` messages will still be processed. This defeats the entire purpose of the pause mechanism, allowing continued draining/settlement of user escrow during an incident the pause was meant to halt — a direct path to loss of user funds under adversarial conditions the pause was designed to prevent.

### Likelihood Explanation
High likelihood if the pause mechanism is ever engaged: any solver (an unprivileged, permissionless actor) can simply keep calling the fill functions as normal; nothing in the code differentiates paused from unpaused state. The bug requires no special conditions beyond the protocol operator invoking pause during an incident, at which point the vulnerability is trivially exploitable by any solver already interacting with the system.

### Recommendation
Add a `whenNotPaused` modifier (checking `_paused`) to all state-changing, non-emergency entry points in the intents module: `placeOrder`, `fillOrder`/`_fillSameChain`, `_fillCrossChain`, and the `onAccept`/`onGetResponse` escrow-release paths (`_withdraw`), consistent with how `HyperFungibleToken.sol` and `WrappedHyperFungibleToken.sol` gate `send` and `onAccept`. Ensure cancellation/refund paths remain available (or are deliberately excluded) so users can still exit while paused, but fills/new orders must be blocked. Also confirm a `pause()`/`unpause()` setter for `_paused` actually exists and is wired to governance (not found in the reviewed files, which is itself worth flagging).

### Proof of Concept
1. Governance calls the gateway's pause function, setting `_paused = true` (assuming such a setter exists elsewhere in `IntentGatewayV2.sol`, which was not directly inspected in this pass).
2. A solver calls `fillOrder`/`fillOrderPartial`, which internally invokes `_fillSameChain` — no check on `_paused` exists, so the call succeeds: [2](#0-1) 
3. Escrowed tokens are released to the solver via `_withdraw`, bypassing the intended halt: [5](#0-4) 
4. Equivalently, an in-flight cross-chain `RedeemEscrow` message delivered to `onAccept` after pause still executes and releases escrow: [4](#0-3) 

Note: I was unable to inspect `IntentGatewayV2.sol` (the concrete external-facing contract that composes `IntentsBase`/`ExtrinsicIntents`/`IntrinsicIntents` and presumably exposes `placeOrder`/`fillOrder`/`pause`) within this session due to the final-iteration constraint, so I could not directly confirm whether a `pause()` setter exists or whether it's wired anywhere. This should be verified in a follow-up pass, but the absence of any `_paused` check or `whenNotPaused` modifier across all three reviewed source files strongly supports the finding.
