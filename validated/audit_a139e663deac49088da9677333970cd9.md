### Title
POA Bridge `describeWithdrawal` misreports withdrawal status/txHash when batching multiple withdrawals of the same asset - (File: `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`)

### Summary
The SDK supports batching multiple withdrawals in a single NEAR transaction via `createWithdrawalIdentifiers`, which assigns a per-bridge-route sequence `index` to each withdrawal [1](#0-0) . For PoA-bridge withdrawals, however, `describeWithdrawal` never uses this `index` to disambiguate between multiple withdrawals of the same asset — it matches purely by `assetId` via `findMatchingWithdrawal`, which returns the *first* array element whose `near_token_id` matches, regardless of which index is being queried [2](#0-1) [3](#0-2) .

### Finding Description
When a caller batches two or more withdrawals of the same token (e.g., two separate BTC withdrawals to different destination addresses in one NEAR transaction), `createWithdrawalIdentifiers` assigns them indices 0 and 1 within the `poa_bridge` route [4](#0-3) . Each identifier is later passed independently to `PoaBridge.describeWithdrawal` through `watchWithdrawal` [5](#0-4) .

Inside `describeWithdrawal`, the `index` field of the `WithdrawalIdentifier` is accepted as an argument but is **never used** to select which returned withdrawal record corresponds to which request; matching is done solely by `assetId`:
```
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
``` [3](#0-2) 

Because `.find()` always returns the first matching element in the (unsorted) API response array, calling `describeWithdrawal` for index 0 and index 1 of the same asset both resolve to the **same** underlying withdrawal record — same `status` and same `transfer_tx_hash` [6](#0-5) . This breaks the equality "status/hash reported == the on-chain outcome for *this specific* withdrawal instance": the second (and any subsequent) withdrawal of the same asset in a batch is reported as completed with a transaction hash that actually belongs to a *different* withdrawal (different destination address / amount).

This is a known, explicitly documented limitation in the code comments ("Currently only matches by assetId... multiple withdrawals of the same token in a single transaction are not supported") [7](#0-6) , but it is not enforced — the SDK does not reject or warn when such a batch is submitted; `createWithdrawalIdentifiers`/`supports()` place no guard against duplicate-asset batches for the PoA route.

### Impact Explanation
`watchWithdrawal`/`waitForWithdrawalCompletion` surfaces the misreported `{status: "completed", txHash}` to the caller/integrator as ground truth for a specific withdrawal instance [8](#0-7) . An integrator that credits or reconciles a withdrawal based on this reported `txHash` for withdrawal #2 will actually be looking at withdrawal #1's transaction hash. This matches the "Critical/High" category of "a status or hash misreport making an integrator credit or refund twice": the integrator may believe two independent withdrawals landed on-chain under one recorded hash, and mis-track/re-credit/refund funds, or fail to notice that withdrawal #2 never actually completed on-chain when it should have used a distinct transaction.

### Likelihood Explanation
Any caller of the intents-sdk that batches ≥2 withdrawals of the same asset in a single NEAR transaction (a supported and documented flow via `createWithdrawalIntents`/`waitForWithdrawalCompletion` accepting arrays of `WithdrawalParams`) will trigger this unconditionally — no malicious actor or special conditions are required beyond ordinary usage of the batching feature with a common token (e.g., two BTC withdrawals to different users). This makes the likelihood high whenever batch withdrawals of the same asset are used, though it does require that pattern of usage rather than being triggered on every single withdrawal.

### Recommendation
- Extend the POA-bridge withdrawal status API/response (or the SDK's client-side matching) to disambiguate withdrawals of the same asset by additional criteria (e.g., destination address + amount, or a sequence/order field returned by the API), rather than relying on `assetId` alone.
- Until API support exists, have `supports()`/`createWithdrawalIdentifiers` detect and reject (or explicitly warn/error on) batches containing multiple withdrawals of the same asset routed through PoA bridge, instead of silently returning a misleading "completed" status.
- Add regression tests that submit two same-asset withdrawals with different destination addresses in one batch and assert distinct, correctly-attributed statuses for each index.

### Proof of Concept
1. Build withdrawal params for two POA-bridge withdrawals of `nep141:btc.omft.near` to two different addresses (Alice, Bob) in one NEAR transaction.
2. `createWithdrawalIdentifiers` assigns `index: 0` (Alice) and `index: 1` (Bob), both route `poa_bridge` [4](#0-3) .
3. The PoA bridge API returns a single `COMPLETED` withdrawal entry for `btc.omft.near` (Alice's), with `transfer_tx_hash: "alice-tx-hash"`.
4. Calling `bridge.describeWithdrawal({..., index: 0, withdrawalParams: aliceParams})` and `bridge.describeWithdrawal({..., index: 1, withdrawalParams: bobParams})` both invoke `findMatchingWithdrawal(withdrawals, "nep141:btc.omft.near")`, which ignores `index` and returns the same record for both calls — both resolve to `{status: "completed", txHash: "alice-tx-hash"}`, even though Bob's withdrawal has not necessarily completed or uses a different transaction. This is demonstrated by the existing unit test explicitly documenting "matches withdrawal by assetId, not by index" for a *different*-asset scenario [9](#0-8) ; the same-asset case is the unguarded gap that produces the misreport described above.

	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
