Confirmed: the webhook HMAC only ever signs `@raw_body` — the `shop`, `topic`, `webhook-id`, and `api-version` values are read straight from unauthenticated HTTP headers and passed downstream to the handler untouched.### Title
Webhook `shop` (and `topic`) identity is trusted from an unauthenticated HTTP header while the HMAC only covers the raw body, breaking the shop-authenticated-vs-shop-acted-on binding - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, then hands the handler a `WebhookMetadata` struct whose `shop`, `topic`, `webhook_id`, and `api_version` fields are read straight from HTTP headers that are never included in the signed material.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are parsed directly from headers with no relation to the signed payload: [2](#0-1) 

`HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` (i.e., the raw body only) and compares it against the `hmac-sha256` header: [3](#0-2) 

`Registry.process` only checks this body-only HMAC before dispatching to the handler with the header-derived, unauthenticated `shop` value: [4](#0-3) 

`WebhookMetadata.shop` is a plain `String` field with no cryptographic binding to the body it travels with: [5](#0-4) 

The identity binding broken is: `HMAC-authenticated bytes (raw_body)` ≠ `shop identity acted upon (header value)`. Any unprivileged internet user who is themselves a merchant with the app installed (shop A) receives legitimate webhook deliveries with a valid `(raw_body, hmac-sha256)` pair for their own shop. Because the `shop-domain`, `topic`, and `webhook-id` headers are outside the signed content, that same valid `(raw_body, hmac)` pair can be replayed to the app's webhook endpoint with an attacker-modified `x-shopify-shop-domain` header naming a victim shop B. `Utils::HmacValidator.validate` still passes (it only checks the body/secret pair), and `Registry.process` forwards `WebhookMetadata.new(shop: "shop-B.myshopify.com", body: <shop A's data>, ...)` to the host application's handler as if the data legitimately originated from shop B.

### Impact Explanation
This crosses a tenant boundary: an attacker who controls one authenticated shop (their own installed instance of the app) can inject arbitrary attacker-chosen webhook bodies that the library asserts, with a passing signature check, belong to a different shop. Any host application that keys persistence, redaction, or business logic off `WebhookMetadata#shop` (which is exactly the documented purpose of that field, and includes the `MANDATORY_TOPICS` like `shop/redact` and `customers/redact`) will process forged data under the wrong tenant, corrupting cross-tenant state or triggering redaction/compliance actions against a shop that never sent the webhook. This matches the "cross-tenant access" High/Critical impact class since it lets a low-privileged actor cross an identity boundary that the HMAC is supposed to enforce.

### Likelihood Explanation
Any developer using an app on Shopify can register the app on their own store, capture a real webhook delivery (raw body + valid `hmac-sha256`), and replay the exact same body/HMAC pair to the app's public webhook endpoint with a rewritten `x-shopify-shop-domain` header. No secret material, privileged account, or the app's `client_secret`/access token is required — only the ability to receive one's own legitimate webhook and re-POST it with a different header value, which is squarely available to an unprivileged internet user/merchant.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) header values into the HMAC-verified material — for instance, verify webhooks only against the tuple of headers plus body, or require host applications to separately assert that `request.shop` matches the origin the app expects for that delivery route/session before trusting `WebhookMetadata#shop`. At minimum, document prominently that `shop`, `topic`, and `webhook_id` in `WebhookMetadata` are NOT covered by the returned HMAC validation and must not be trusted for tenant-scoping without independent verification (e.g., cross-checking against a known/expected shop for that webhook subscription).

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a real webhook (e.g., `orders/create`), capturing the raw POST body and the `x-shopify-hmac-sha256` header Shopify sent.
2. Attacker crafts a new POST to the app's webhook endpoint using the identical raw body and `hmac-sha256` value, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses this into a request object; `Utils::HmacValidator.validate` succeeds because it only signs/checks `@raw_body`. [6](#0-5) 
4. `Registry.process` invokes the host's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker's data>, ...)`, and any application logic keyed on `data.shop` treats attacker-controlled content as authentic data for the victim shop.
