### Title
Webhook tenant identity (`shop` header) is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` verifies webhook authenticity by HMAC-ing only the raw request body [1](#0-0) , while the `shop` value used to identify which merchant/tenant the webhook belongs to comes from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header [2](#0-1) , which is never included in the signed bytes. `Registry.process` treats the request as fully authenticated once `Utils::HmacValidator.validate(request)` passes and immediately forwards the caller-supplied `shop` header value to the app's handler [3](#0-2) .

### Finding Description
The identity binding that should hold is: `shop value cryptographically bound in the HMAC == shop value the handler trusts as the request's tenant`. In this gem, that equality does not hold — the HMAC only proves "this body was signed with our `api_secret_key`" (`HmacValidator.compute_signature` over `to_signable_string`, which for webhooks is just `@raw_body`) [4](#0-3) . It does not prove which shop that body came from. Since the `api_secret_key` is shared across *all* merchants who have installed the app (it is not per-shop), any valid `(raw_body, hmac)` pair generated by Shopify for one merchant remains cryptographically valid no matter which `X-Shopify-Shop-Domain` header value accompanies it. The gem's own documentation and `WebhookMetadata` struct instruct app developers to trust `data.shop` as the authoritative tenant identifier for processing the (also trusted) `data.body` [5](#0-4) [6](#0-5) , without any warning that `shop` is unauthenticated relative to the signature.

### Impact Explanation
An attacker who is a legitimate merchant of the app (an "unprivileged" party relative to other tenants) can replay their own genuinely Shopify-signed webhook body/HMAC pair to the app's webhook endpoint while substituting a different `X-Shopify-Shop-Domain` header value. Because the signature check only covers the body, `Registry.process` will accept the request as valid and hand the handler a `WebhookMetadata` claiming the (validated) body belongs to a different shop. If the app's handler uses `data.shop` to select the tenant record/session/access-token context in which to apply `data.body` (as the gem's docs recommend), this results in cross-tenant data injection/impersonation.

### Likelihood Explanation
Exploitation requires the attacker to already be an app merchant capable of receiving at least one legitimate webhook (trivial — they can trigger topics like `orders/create` on their own store) and the ability to send an arbitrary HTTP POST with custom headers to the app's public webhook endpoint (also trivial, since these endpoints are unauthenticated by design and only rely on the HMAC check). No secrets, tokens, or privileged access are required.

### Recommendation
Bind the shop identity into the verified material: either require the app to independently verify `shop` (e.g. against a known installed-shop list before trusting `data.shop`), or better, have `Registry.process` cross-check the `shop`/`topic` header values against the value(s) embedded in the signed body/topic registration where possible, and clearly document that `WebhookMetadata#shop` is not itself covered by the HMAC and must not be used as the sole tenant boundary without additional verification (e.g. comparing to the shop associated with the session used to register the webhook).

### Proof of Concept
1. App merchant `shop-a.myshopify.com` triggers `orders/create`; Shopify sends a real webhook to the app's endpoint with body `B` and header `X-Shopify-Hmac-Sha256: HMAC(secret, B)`.
2. Attacker captures `(B, HMAC(secret,B))` from their own webhook delivery.
3. Attacker (or a co-conspirator) replays the exact same `B` and `HMAC` to the same endpoint, but sets `X-Shopify-Shop-Domain: shop-victim.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` returns `true` because it only checks `B` against the HMAC [7](#0-6) .
5. `Registry.process` calls the handler with `WebhookMetadata.new(shop: "shop-victim.myshopify.com", body: parsed(B), ...)` [8](#0-7) , and the app applies attacker-supplied order/product data to the victim shop's tenant context.

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
```
