### Title
Unvalidated reserve subtraction in `_prepareGraduationLiquidity` underflows and permanently bricks graduation - ([File: packages/contracts/src/Bonding.sol])

### Summary
`Bonding._prepareGraduationLiquidity` (called from `_enterGraduating`, which both the inline post-buy trigger and the permissionless `triggerGraduation` invoke) computes `ltFromPair = assetReserve - _launchTimeVirtualLtReserve(tokenAddress, pairAddr)` with a plain, non-saturating `uint256` subtraction. [1](#0-0) 
Unlike the analogous subtraction in `finalizeGraduation`, which was deliberately hardened with a saturating subtract specifically to avoid a Panic-underflow bricking finalize, the same class of unvalidated arithmetic remains in the phase-1 helper. [2](#0-1) 

### Finding Description
The invariant the comment relies on — `assetReserve ≥ virtualLtReserve` — is asserted only in prose, not enforced on-chain. `Pair.swap`'s K-invariant check is intentionally loose: it allows the post-swap product to fall slightly below `k` via a `+1` slack on both reserves (`(newTokenReserve+1)*(newAssetReserve+1) < _pool.k`). [3](#0-2) 
Combined with `Router._computeSell`'s floor-rounded `assetOut = reserveAsset - (k / newReserveToken)`, every `sell()` a trader executes can extract fractional-wei more asset reserve than the strict curve math would allow, because both the router's floor division and the pair's `+1` slack round in the seller's favor. [4](#0-3) 
Any unprivileged trader can call `Bonding.sell` (routed through `Router.sell`/`_computeSell`) repeatedly with the smallest tradable amounts, each call permissibly extracting this rounding slack, monotonically walking the pair's `assetReserve` down. Because `_launchTimeVirtualLtReserve` is a fixed, derived constant (`Pair.k() / Token.TOTAL_SUPPLY()`) that never decreases, enough repeated small sells can, over time, push `assetReserve` at or below `virtualLtReserve`. The very next call into `_prepareGraduationLiquidity` — whether from the inline post-buy trigger or the fully permissionless `triggerGraduation(tokenAddress)` — then executes `assetReserve - virtualLtReserve` and reverts with an arithmetic-underflow Panic, since Solidity 0.8's checked arithmetic reverts rather than wrapping. This is the same bug class as the ngtcp2 CVE: a downstream computation trusts an unvalidated invariant instead of re-deriving/clamping it, and an attacker-reachable rounding channel lets that invariant be violated, corrupting a security-critical arithmetic operation.

### Impact Explanation
Once `_prepareGraduationLiquidity` becomes unreachable for a given token, both graduation triggers (`_enterGraduating`'s inline call from `_executeBuy` and the permissionless `triggerGraduation`) permanently revert for that token — there is no other code path that transitions `Lifecycle.Curve → Graduating`. This permanently freezes: all curve-raised LT sitting in the `Pair`, the up to 250M reserved launch tokens, and blocks the token from ever reaching HyperSwap V2, denying creators, traders and LPs any exit via graduation. This matches the "permanent freezing of trader, creator or LP funds" impact bar in the validation rules.

### Likelihood Explanation
The attack requires only ordinary, permissionless calls to `sell()` at minimum tradable sizes — no privileged role, no special timing, and no interaction with `LPLock`/`FeeVault`. The rounding channel (`+1` K slack plus floor-rounded `_computeSell`) is a structural property of the AMM math documented as a known hotspot in this codebase, not a hypothetical. The number of iterations needed depends on the wei-level slack per call and the size of `virtualLtReserve`, which could be significant for realistic reserve sizes — this is the main source of uncertainty, since I could not execute the exact numeric magnitude of drift per `sell()` call against production reserve sizes to bound the number of transactions required.

### Recommendation
Apply the same saturating-subtraction defense already used in `finalizeGraduation` to `_prepareGraduationLiquidity`:
```solidity
uint256 virtualLt = _launchTimeVirtualLtReserve(tokenAddress, pairAddr);
ltFromPair = assetReserve > virtualLt ? assetReserve - virtualLt : 0;
```
This mirrors the existing pattern and comment rationale at `Bonding.sol:1015-1020` and removes the reachable Panic path without changing normal-path economics.

### Proof of Concept
1. Launch a token normally via `Bonding.launch`; a `Pair` is created with `virtualLtReserve = k / TOTAL_SUPPLY` fixed at mint time. [5](#0-4) 
2. An unprivileged trader repeatedly calls `Bonding.sell` (→ `Router.sell` → `_computeSell` → `Pair.swap`) with minimum-sized token amounts. Each call is a legitimate trade, but the floor-rounded `_computeSell` output plus `Pair.swap`'s `+1` K-invariant slack lets the trader extract a small amount of extra `assetReserve` beyond what strict curve math allows. [6](#0-5) 
3. Repeated over enough transactions, `assetReserve` drifts down to/below `virtualLtReserve = k / TOTAL_SUPPLY`.
4. Any subsequent call that reaches `_enterGraduating` (either a normal buy crossing the USD/supply threshold, or a direct call to the permissionless `Bonding.triggerGraduation(tokenAddress)`) executes `_prepareGraduationLiquidity`, which reverts with an arithmetic-underflow Panic at `ltFromPair = assetReserve - _launchTimeVirtualLtReserve(...)`. [7](#0-6) 
5. The token is permanently stuck in `Lifecycle.Curve`, unable to graduate; all LT and reserved tokens held by the `Pair`/`Bonding` are frozen.

    function _prepareGraduationLiquidity(
        address tokenAddress
    ) internal returns (uint256 tokensForLP, uint256 ltFromPair, uint256 lpBurned, uint256 unsoldBurned) {
        address pairAddr = _s().tokenInfo[tokenAddress].pair;
        (uint256 tokenReserve, uint256 assetReserve) = IPair(pairAddr).getReserves();

        unsoldBurned = IPair(pairAddr).tokenBalance();
        if (unsoldBurned > 0) {
            Token(tokenAddress).burn(pairAddr, unsoldBurned);
        }

        ltFromPair = assetReserve - _launchTimeVirtualLtReserve(tokenAddress, pairAddr);
        if (ltFromPair > 0) {
            _s().router.graduate(tokenAddress, ltFromPair);
        }

        tokensForLP = assetReserve == 0 ? 0 : (ltFromPair * tokenReserve) / assetReserve;
        if (tokensForLP > LP_RESERVE) tokensForLP = LP_RESERVE;

        lpBurned = LP_RESERVE - tokensForLP;
        if (lpBurned > 0) {
            Token(tokenAddress).burn(address(this), lpBurned);
        }
    }

    function _computeSell(
        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 assetOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        uint256 newReserveToken = reserveToken + amountIn;
        assetOut = reserveAsset - (k / newReserveToken);
