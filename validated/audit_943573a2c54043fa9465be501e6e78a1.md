### Title
Webhook `shop` and `topic` fields are not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely via `Utils::HmacValidator.validate(request)`, and `Request#to_signable_string` returns only `@raw_body` [1](#0-0) . The `shop`, `topic`, `webhook_id`, and `api_version` values are all read from HTTP headers that are never part of the signed payload [2](#0-1) . `Registry.process` then forwards `request.shop` and `request.topic` unchecked into `WebhookMetadata` given to the app-supplied handler [3](#0-2) .

### Finding Description
The identity binding that should hold is: `hmac_signed_bytes == bytes_the_handler_trusts_as_the_shop_identity`. Here, `hmac_signed_bytes` is only `@raw_body` [4](#0-3) , while `bytes_the_handler_trusts_as_the_shop_identity` is `shopify_header("shop-domain")` [5](#0-4) , an independent, unauthenticated header. `HmacValidator.validate` only checks `verifiable_query.to_signable_string` (the body) against the HMAC secret [6](#0-5) ; it never incorporates the shop-domain, topic, webhook-id, or api-version headers into the signature check.

This is directly analogous to the reported bug class: a field that is *acted upon* (here, the `shop` field used for tenant identification and dispatch) is not covered by the authentication check (here, HMAC), even though a sibling field (`raw_body`) is.

Because Shopify computes the webhook HMAC purely over the raw JSON body using the app's shared `client_secret`, any two webhook deliveries with byte-identical bodies (e.g. an empty-body test webhook, or two orders with identical field content across two different shops installed on the same app) produce the identical HMAC signature `HMAC(secret, body)`, independent of which shop or topic the body was delivered for. Since the library never binds the header values into the signature, an attacker who receives a legitimate webhook for their own shop (they can install the app on their own store) can capture body+HMAC and replay it to the app's webhook endpoint with a forged `X-Shopify-Shop-Domain` header pointing at a victim shop and/or a forged `X-Shopify-Topic` header — the same valid HMAC will still pass `Utils::HmacValidator.validate` because it only checks the body.

### Impact Explanation
This breaks the tenant boundary the gem is documented to provide: `docs/usage/webhooks.md` explicitly tells developers that `data.shop` is "The shop domain of the webhook" and shows it being used directly for tenant-scoped work such as `perform_later(topic: data.topic, shop_domain: data.shop, ...)`. An app that trusts `data.shop`/`data.topic` as authenticated (as the library documentation encourages) can be made to process attacker-controlled data under another merchant's identity — i.e., cross-tenant data injection/confusion, satisfying the "Critical - cross-tenant access" impact bar.

### Likelihood Explanation
Exploitation requires only the ability to receive any webhook with a valid HMAC (trivially available to any developer with a store, since installing on their own dev shop and receiving normal webhook traffic is enough) and the ability to send crafted HTTP requests with attacker-controlled headers to the target app's public webhook endpoint. No access token, `client_secret`, or privileged credential of the victim is required — only a body whose bytes coincide with (or that the attacker can produce, e.g., empty-body or template webhooks) a validly-signed request.

### Recommendation
Bind the header values that are acted upon into the signed material, or otherwise cryptographically tie `shop`/`topic`/`webhook_id` to the HMAC-checked payload before they are trusted (e.g., verify the shop domain against the session/store the app already trusts for that webhook subscription rather than trusting the header verbatim), and update `Utils::HmacValidator` / `Webhooks::Request#to_signable_string` so signature verification covers the full set of security-relevant fields, not just the raw body.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and registers for topic `orders/create`; Shopify delivers a webhook with body `B` and header `X-Shopify-Hmac-Sha256: HMAC(secret, B)` — this is legitimately obtained since the attacker owns the shop receiving it.
2. Attacker replays this exact `body=B` and `hmac` to the app's public webhook endpoint but substitutes `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(secret, B)` against the header, succeeds because `B` and the HMAC are byte-identical to what Shopify actually sent [7](#0-6) .
4. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and the attacker-supplied body, and performs tenant-scoped work (e.g., enqueuing a job "for" `victim-shop.myshopify.com`) as shown in the documented handler pattern [8](#0-7) .
