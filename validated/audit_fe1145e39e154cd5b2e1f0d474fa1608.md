### Title
Missing shop-domain allow-list validation in `TokenExchange.exchange_token` sends `client_secret` to an unvalidated host - (File: `lib/shopify_api/auth/token_exchange.rb`)

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` derives the destination host for the token-exchange request directly from the session token's `dest` claim, without ever passing it through `Utils::ShopValidator.sanitize!`. Every sibling credential-issuing method in this gem (`ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, and even `TokenExchange.migrate_to_expiring_token` in the same file) validates the `shop` string against the trusted-domain allow-list before using it to build the request host that receives `client_id`/`client_secret`. `exchange_token` skips this step, breaking the identity binding "host validated == host that receives the `client_secret`" that every other flow in the module enforces.

### Finding Description
`exchange_token` extracts the shop straight from the JWT payload and uses it unsanitized to build the outgoing request: [1](#0-0) [2](#0-1) 

`JwtPayload#shop` performs no domain validation either — it just strips the `https://` prefix from the raw `dest` claim: [3](#0-2) 

That unvalidated string is passed straight into `Session.new(shop: dest_shop)`, and `Clients::HttpClient` builds the outbound request host directly from `session.shop` when no `Context.api_host` override is configured: [4](#0-3) 

The request body containing `client_id` and `client_secret` is then POSTed to that host: [5](#0-4) 

Contrast this with `migrate_to_expiring_token` in the very same file, and with `client_credentials`/`refresh_access_token`, all of which call `Utils::ShopValidator.sanitize!(shop)` — which restricts the destination host to `ShopValidator::TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`) — before constructing the session used for the credentialed request: [6](#0-5) [7](#0-6) [8](#0-7) 

### Impact Explanation
If an attacker can influence the `dest` claim value of a session token that still passes `JWT.decode` verification (e.g., via a dev/spin-tunnel flow, a proxy that forwards a token issued for a domain outside the intended production allow-list, or any deployment where the shared secret's trust boundary is broader than intended), the gem will POST the app's `client_id` and `client_secret` to that attacker-influenced host — an SSRF that exfiltrates the app's OAuth client credentials, matching the report's "High - SSRF with the app's credentials" / credential-leakage category.

### Likelihood Explanation
Exploitability is constrained: `JwtPayload.new` validates the token's HMAC signature against `Context.api_secret_key` (or `old_api_secret_key`) via `JWT.decode(token, api_secret_key, true, algorithm: "HS256")`, so an attacker with no knowledge of the app's secret cannot forge an arbitrary `dest` value from scratch. The practical exposure is therefore limited to environments where a validly-signed token can carry a `dest` outside the intended host set (e.g., multi-environment or dev-tunnel deployments), which is a narrower path than a pure unauthenticated bypass — but it is still a code-level inconsistency: three sibling entry points in the same module enforce the allow-list and this one does not, so any expansion of who can obtain a validly-signed token (dev flows, spin.dev tenants, token reuse across environments) silently loses this protection.

### Recommendation
Call `Utils::ShopValidator.sanitize!` (or `sanitize_shop_domain`) on `jwt_payload.shop` in `TokenExchange.exchange_token` before constructing `shop_session`, mirroring `migrate_to_expiring_token`, `client_credentials`, and `refresh_access_token`, so the host that receives `client_secret` is always constrained to `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`.

### Proof of Concept
1. Obtain a session token whose `dest` claim is signed correctly (valid `aud`/`iss`/signature) but whose host value falls outside the production allow-list — e.g., because it was issued for a spin/dev tunnel or a re-purposed environment that shares the app's `api_secret_key`.
2. Call `ShopifyAPI::Auth::TokenExchange.exchange_token(session_token: token, requested_token_type: ...)`.
3. Observe that `Clients::HttpClient` sends a POST containing `client_id`/`client_secret` to `https://<dest_shop>/admin/oauth/access_token` with no allow-list check, whereas the equivalent call through `RefreshToken.refresh_access_token` or `ClientCredentials.client_credentials` with the same untrusted `shop` string would raise `Errors::InvalidShopError` from `ShopValidator.sanitize!` and never send the credential.

**Uncertainty note:** I could not verify from the in-scope code alone whether any deployment path allows an unprivileged, uncredentialed attacker to obtain a validly-signed session token with an attacker-chosen `dest` outside `TRUSTED_SHOPIFY_DOMAINS` — that depends on how the host application issues/relays session tokens, which is outside `lib/shopify_api/**`. This finding is reported as a concrete host-validation inconsistency matching the requested SSRF/credential-leakage identity-binding pattern, with the caveat above on end-to-end exploitability.
