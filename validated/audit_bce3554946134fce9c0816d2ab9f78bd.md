### Title
Webhook `shop-domain` header is trusted without being covered by the HMAC, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw request body, then hands the caller-supplied `shop-domain` header straight to the app's handler as the authoritative tenant identifier, without that header ever being part of the signed material.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `hmac` is read from the `hmac-sha256` header [2](#0-1) . `Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` (i.e. the body only) and compares it with `secure_compare` [3](#0-2) . The `shop` accessor is read separately from the `shop-domain` header and is never included in the signed bytes [4](#0-3) .

`Registry.process` performs exactly this check-then-trust pattern: it raises only if the HMAC over the body fails, then immediately builds `WebhookMetadata` using `request.shop` as the tenant identifier for the handler: [5](#0-4) 

The broken identity binding is: `shop header value == tenant the payload is attributed to`, while the actual authenticated equality the HMAC proves is only `body bytes == signed-by-client_secret bytes`. The `shop-domain` header sits entirely outside that proof.

Because Shopify signs webhook bodies with the single app-wide `client_secret` shared across every merchant that installs the app, a party who receives one genuine, correctly-signed webhook for their own shop (e.g. a merchant who installed the multi-tenant app) possesses a valid `(raw_body, hmac)` pair. That party can replay this exact body and HMAC directly to the app's webhook endpoint while substituting an arbitrary victim `shop-domain` header. `HmacValidator.validate` will pass (it never looks at the header), and `Registry.process` will dispatch to the handler with `data.shop` set to the attacker-chosen victim shop, `data.body` set to the attacker's own (valid, replayable) payload.

### Impact Explanation
This crosses a tenant boundary: the gem asserts to the calling application, via `WebhookMetadata#shop`, that a given payload originates from a specific merchant, but that assertion is not backed by any cryptographic proof. Any application logic that keys writes, credits, notifications, order/inventory mutations, or session lookups off `data.shop` post-verification can be tricked into acting on behalf of, or against, a shop the attacker does not control — a cross-tenant access primitive that meets the Critical bar for cross-tenant impact.

### Likelihood Explanation
Exploitation requires the attacker to already have received (or captured) one legitimately signed webhook body+HMAC for a shop they control — which any merchant who installs a multi-tenant app trivially has — and the ability to POST directly to the app's public webhook endpoint with modified headers, which is standard for webhook receivers and requires no additional secrets, tokens, or privileged access.

### Recommendation
Bind the `shop-domain` (and ideally `topic`/`api-version`) header into the signed material actually verified, or independently corroborate the header against a value the app already trusts for that installation (e.g., cross-check against a known/authorized shop list or an out-of-band webhook subscription ID) before dispatching to handlers, rather than trusting `request.shop` purely on the strength of a body-only HMAC.

### Proof of Concept
1. Attacker installs the multi-tenant Shopify app on their own shop `attacker.myshopify.com` and triggers a webhook (e.g. `orders/create`), capturing the raw JSON body `B` and the `X-Shopify-Hmac-Sha256` header value `H` that Shopify computed with the app's shared `client_secret`.
2. Attacker sends a POST directly to the app's webhook endpoint with:
   - Body: `B` (unchanged)
   - `x-shopify-hmac-sha256: H` (unchanged)
   - `x-shopify-shop-domain: victim.myshopify.com` (forged)
   - `x-shopify-topic: orders/create`
3. `ShopifyAPI::Webhooks::Request.new` accepts the headers [6](#0-5) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `B` against `H` [7](#0-6) .
4. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed(B), ...)` [8](#0-7)  — the app now processes attacker-controlled data as if it belonged to `victim.myshopify.com`.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
