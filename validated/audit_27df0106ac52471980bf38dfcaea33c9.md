### Title
Unsafe low-level ERC20 `transfer` calls in Tron `IntentGatewayV2.withdraw`/`onAccept` do not validate the boolean return value - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of `IntentGatewayV2` reintroduces the exact unsafe-ERC20-interaction pattern the referenced report warns about. Instead of using `SafeERC20.safeTransfer`, `withdraw()` and the `SweepDust` branch of `onAccept()` manually build the `transfer` calldata and call the token with a raw `.call(...)`, checking only that the low-level call did not revert (`success`) — never decoding/verifying the ERC20 boolean return value.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol`, the escrow redemption path does:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
``` [1](#0-0) 

The same pattern is used for fee redemption: [2](#0-1) 

and for the protocol's dust-sweep path reachable via `onAccept`: [3](#0-2) 

`success` only reflects whether the external call reverted, not whether the ERC20 `transfer` actually succeeded. Tokens that return `false` instead of reverting on failure (a well-known non-compliant ERC20/TRC20 pattern — e.g. insufficient contract balance edge cases, paused/blacklisted transfers, or tokens with non-standard return semantics common on Tron) will make the low-level call return `success = true` while the token balance is never moved. This is precisely the pattern flagged in the external report — using raw `IERC20` calls instead of `SafeERC20.safeTransfer`, which decodes and enforces the boolean return value.

Notably, the primary EVM `IntentGatewayV2.sol` and `IntentsBase.sol` already use `SafeERC20`'s `safeTransfer`/`safeTransferFrom` throughout [4](#0-3) , confirming the fix was applied elsewhere but the Tron fork of the contract regressed to the unsafe raw-call pattern.

`withdraw()` is invoked from `onAccept`, which is called by the ISMP host when a relayer delivers a verified `RedeemEscrow`/`RefundEscrow` cross-chain message: [5](#0-4) . This makes it reachable from a single relayed message with no privileged caller involved beyond message authentication.

### Impact Explanation
If the escrowed token silently returns `false` on a failed transfer:
- `withdraw()` still decrements `_orders[body.commitment][token] -= amount` and emits `EscrowReleased`/`EscrowRefunded` as if the beneficiary was paid, even though no tokens moved [6](#0-5) .
- The escrow accounting is now permanently inconsistent with actual token custody: the beneficiary never receives funds, yet the protocol considers the order filled/refunded and there is no retry path, resulting in a permanent freezing/loss of the escrowed user funds for the affected order.
- The same silent-failure risk applies to protocol dust sweeps and fee redemption, corrupting protocol fee accounting as well.

### Likelihood Explanation
This requires an ERC20/TRC20 token in the input/output/fee-token set that returns `false` rather than reverting on failure — a documented and common non-standard token behavior, and especially prevalent among TRC20 tokens on Tron where the contract is deployed. Given `IntentGatewayV2` is a generic multi-token intents/escrow gateway (any listed token can be used as input/output/fee token), the likelihood of encountering such a token is non-trivial, and the trigger condition (a transient balance issue, blacklist, or pause on the token side) is realistic in production without any attacker action required.

### Recommendation
Replace the manual `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `withdraw()` and the `SweepDust` handling in `onAccept()` with `SafeERC20.safeTransfer(IERC20(token), beneficiary, amount)`, consistent with the rest of the codebase (`IntentsBase.sol`, `HyperFungibleToken.sol`), so that non-compliant tokens returning `false` cause a revert instead of silently corrupting escrow state.

### Proof of Concept
1. Deploy (or use) an ERC20/TRC20 token that returns `false` on `transfer` failure instead of reverting (a standard pattern for some legacy/non-compliant tokens).
2. Place an order on the source chain using this token as input, escrowing funds in `IntentGatewayV2`.
3. A solver fills the order on the destination chain; the source-chain gateway relays a `RedeemEscrow` message.
4. When the relayer delivers the message, `onAccept` → `withdraw()` executes the raw `token.call(...)`. If the token's `transfer` returns `false` (e.g., because the beneficiary is blacklisted or another internal condition prevents movement), `success` is still `true` because the call itself didn't revert.
5. `_orders[commitment][token]` is decremented and `EscrowReleased` is emitted, but the beneficiary's balance never increased — the escrowed tokens are now stuck in the contract with no accounting path to recover them.
