### Title
Webhook `shop-domain` (tenant identity) header is not covered by the HMAC signature, allowing cross-tenant webhook impersonation - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by verifying the HMAC over the raw request body, then trusts the `shop-domain` (and `topic`, `webhook-id`, `api-version`) HTTP headers verbatim to build the `WebhookMetadata` passed to the app's handler. Because those headers are never included in the signed payload, any request whose body+HMAC pair is valid for *some* shop can be replayed with a different `shop-domain` header and will still pass validation, letting an attacker who can obtain one valid (body, HMAC) pair (e.g. from their own store's webhook deliveries) impersonate another tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

and `shop`, `topic`, `webhook_id`, `api_version` are all pulled straight from HTTP headers, untouched by the signature: [2](#0-1) 

`ShopifyAPI::Utils::HmacValidator.validate` computes/compares the HMAC exclusively over `verifiable_query.to_signable_string`, i.e. the body — never the headers: [3](#0-2) 

`Registry.process` performs no additional binding check between the validated body and the `shop`/`topic`/`webhook_id` headers before invoking the app's handler with them: [4](#0-3) 

The identity binding that should hold is:
`hmac_verified(body) == shop_claimed_in_header`

but the code only checks `hmac_verified(body) == true`, leaving `shop` (and topic/webhook_id) as an attacker-controlled, unauthenticated value that is handed to the host application as if it were verified tenant identity.

### Impact Explanation
Any unprivileged internet user who can obtain one legitimate (body, `hmac-sha256`) pair — trivially available since they can install the target app on their own store and observe the webhooks Shopify delivers to their own endpoint, or capture/replay any webhook whose body they can view — can resend that exact body/HMAC to the app's webhook endpoint while substituting the `shopify-shop-domain` header for a victim shop. `Registry.process` will accept it as authentic (`HmacValidator.validate` only checks the body) and call the app's handler with `WebhookMetadata.shop` set to the victim's domain and attacker-chosen body content. Any host application that uses `data.shop` to look up per-tenant state, apply the payload, or drive further Admin API calls on behalf of "the shop that sent this webhook" will now be operating on the wrong tenant with attacker-supplied data — a cross-tenant integrity/confidentiality violation.

### Likelihood Explanation
Getting one legitimate signed payload is straightforward for any developer/merchant who can install the app on a store they control (a normal, unprivileged action), and HTTP header manipulation on a replayed request requires no credentials. No access token, `api_secret_key`, or privileged account is needed.

### Recommendation
Bind the identity fields to the signature, not just the body. Practical options:
- Verify that the HMAC covers (or is otherwise cryptographically bound to) `shop`, `topic`, and `webhook_id`, not only the body.
- Require the host application (or the gem itself) to cross-check the `shop-domain` header against the shop a given `webhook_id`/subscription was registered for before invoking the handler.
- At minimum, document prominently that `WebhookMetadata.shop` is unauthenticated header data and must be independently validated by the consuming application (e.g., against its own stored session/shop registry) before being trusted for tenant-scoped operations.

### Proof of Concept
1. Install the target app on attacker-controlled store `attacker-shop.myshopify.com`; trigger a webhook (e.g. `orders/create`) so Shopify POSTs a body `B` with header `x-shopify-hmac-sha256: H` (valid HMAC of `B` under the app's `api_secret_key`) and `x-shopify-shop-domain: attacker-shop.myshopify.com` to the app's webhook endpoint.
2. Capture `B` and `H` from that request (attacker fully controls their own endpoint/network, so this is observable).
3. Replay a new POST to the same webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H` unchanged, but `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` builds a `ShopifyAPI::Webhooks::Request`, calls `Utils::HmacValidator.validate`, which recomputes HMAC over `B` only and matches `H` — validation passes.
5. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, so the app processes attacker-controlled data as if it originated from the victim's shop.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
