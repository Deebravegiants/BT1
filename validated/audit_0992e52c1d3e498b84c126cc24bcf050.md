## Analysis: Signature Replay Analog in `pallet-nfts` Pre-Signed Minting

I found a genuine structural analog to the RabbitHole `mintReceipt` signature-replay pattern in `pallet-nfts`'s pre-signed mint/attribute mechanism. Unlike the base FRAME extrinsic pipeline — which is *not* vulnerable to this class because `CheckGenesis`/`CheckNonce`/`CheckSpecVersion` bind every signed transaction to a specific chain and account nonce ( [1](#0-0) , [2](#0-1) ) — the `pallet-nfts` pre-signed voucher scheme is a bespoke, application-level signature similar to RabbitHole's `claimSignerAddress`-based scheme.

### Title
Cross-chain/cross-instance replay of `pallet-nfts` pre-signed mint/attribute vouchers due to missing domain separation - (File: `substrate/frame/nfts/src/types.rs`, `substrate/frame/nfts/src/lib.rs`)

### Summary
`pallet-nfts` allows a collection `Issuer`/`Admin` to authorize a mint or attribute-set operation off-chain by signing a `PreSignedMint`/`PreSignedAttributes` struct. The signed payload is the raw SCALE encoding of the struct and contains no chain/genesis-hash or pallet-instance discriminator, only `collection`, `item`, `attributes`, `metadata`, `only_account`, `deadline`, `mint_price` [3](#0-2) . The dispatchables `mint_pre_signed` and `set_attributes_pre_signed` verify only that the signature matches the encoded struct via `Self::validate_signature`, with no additional domain-separation data [4](#0-3) .

### Finding Description
`do_mint_pre_signed` checks: attribute count limit, `only_account`, `deadline >= now`, and that `signer` holds the `Issuer` role on `collection` [5](#0-4) . It does not bind the signed message to:
- a specific chain (no genesis hash / chain-id analog to `CheckGenesis`),
- a specific pallet instance (the pallet is generic over `I` and can be instantiated multiple times in one runtime),
- a specific nonce (only in-band replay protection is the `AlreadyExists` check when `item` is minted once, confirmed by the test at [6](#0-5) ).

This is exactly the pattern flagged in the RabbitHole report: an authority (`Issuer`) issues an off-chain signature authorizing a specific action, and the signature itself carries no information tying it to one chain/deployment/pallet instance.

### Impact Explanation
If the same `Issuer` account manages collections with the same `collection`/`item` numbering across two independent deployments that both run `pallet-nfts` (e.g. sibling parachains, testnet/mainnet pairs, or a runtime instantiating `pallet_nfts` twice via `Config<I>`), a `PreSignedMint`/`PreSignedAttributes` voucher signed for use on one deployment can be replayed verbatim on the other, minting/setting attributes the issuer did not authorize there — an unintended state change performed by an unprivileged holder of the voucher, mirroring the "unintended minting" impact in the RabbitHole report.

### Likelihood Explanation
Exploitation requires that the same account holds the `Issuer`/`Admin` role over a `collection` with colliding `collection`/`item` identifiers on two live deployments of `pallet-nfts` — a scenario dependent on external/deployment coincidence rather than attacker-forced conditions. This mirrors the C4 judge's final "Medium" (not High) severity rationale for the original finding: replay is only exploitable under specific overlapping setup conditions, not from any arbitrary attacker-controlled path.

### Recommendation
Include a domain separator in the signed payload — e.g. the genesis hash (or a configurable `T::Hash` chain identifier) and the pallet instance discriminator — before hashing/signing `PreSignedMint`/`PreSignedAttributes`, analogous to how `frame_system::CheckGenesis` binds ordinary extrinsics to one chain.

### Proof of Concept
Using the existing test harness pattern at [7](#0-6) : sign a `PreSignedMint{collection:0, item:0, ...}` with the Issuer key on "Chain A" and submit it via `mint_pre_signed`. Because the signed bytes are just `Encode::encode(&mint_data)` with no chain-binding, submitting the identical `(mint_data, signature, signer)` tuple to a second runtime instance (or a second `pallet_nfts::Config<I>` instance in the same runtime) that also has `collection:0`/`item:0` free and the same account holding `Issuer` on that collection will pass `validate_signature` and mint again, since nothing in the signed data or verification path distinguishes the two contexts.

---

Note: this is presented as an investigative finding rather than a confirmed exploit against any specific production Polkadot/Kusama deployment — it requires coincidental collection/item numbering and Issuer-role setup across two independent `pallet-nfts` deployments to be actionable, which is the same caveat the original C4 judge applied to downgrade the RabbitHole finding from High to Medium.

```rust
	pub(crate) fn do_mint_pre_signed(
		mint_to: T::AccountId,
		mint_data: PreSignedMintOf<T, I>,
		signer: T::AccountId,
	) -> DispatchResult {
		let PreSignedMint {
			collection,
			item,
			attributes,
			metadata,
			deadline,
			only_account,
			mint_price,
		} = mint_data;
		let metadata = Self::construct_metadata(metadata)?;

		ensure!(
			attributes.len() <= T::MaxAttributesPerCall::get() as usize,
			Error::<T, I>::MaxAttributesLimitReached
		);
		if let Some(account) = only_account {
			ensure!(account == mint_to, Error::<T, I>::WrongOrigin);
		}

		let now = T::BlockNumberProvider::current_block_number();
		ensure!(deadline >= now, Error::<T, I>::DeadlineExpired);

		ensure!(
			Self::has_role(&collection, &signer, CollectionRole::Issuer),
			Error::<T, I>::NoPermission
		);
```

```rust
fn pre_signed_mints_should_work() {

		let mint_data = PreSignedMint {

			item: 0,

			deadline: 10000000,
			mint_price: Some(10),
		};
		let message = Encode::encode(&mint_data);
```
