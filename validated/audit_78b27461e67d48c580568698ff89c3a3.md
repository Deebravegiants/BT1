Based on my investigation, I found a genuine analog to the Penumbra summonerd issue in nearcore's chunk-application job scheduler.

### Title
Chunk-application worker panics are silently converted into recoverable errors instead of crashing the node, risking use of corrupted shared state - (File: chain/chain/src/pending_shard_jobs.rs)

### Summary
`PendingShardJobs::run`, which drives parallel chunk application (`apply_chunks`) for every block, wraps each shard's apply task in `std::panic::catch_unwind(std::panic::AssertUnwindSafe(task))` and, on panic, converts the panic into an ordinary `Err(Error::Other(message))` result rather than letting the panic propagate and crash the process. [1](#0-0) 

### Finding Description
The Penumbra report's underlying bug class is: unexpected worker-thread crashes were being silently swallowed and turned into "handled" outcomes instead of being bubbled up and crashing the process, hiding real bugs. Nearcore's `PendingShardJobs::run` does exactly this for the block/chunk apply pipeline: any panic that occurs while applying a chunk (invoked via `schedule_apply_chunks` in `chain.rs`, used for both normal and optimistic block processing, and also for spice's per-shard executor) is caught with `AssertUnwindSafe` and converted to a normal `Result::Err`, then delivered through the same `on_done` callback as a successful result. [2](#0-1) [3](#0-2) 

`AssertUnwindSafe` is an explicit escape hatch that disables Rust's unwind-safety checks; it does not make the wrapped closure's shared state actually safe to reuse after a panic. `apply_chunk` tasks mutate shared, `parking_lot`-guarded structures (e.g., trie/shard caches, prefetching staging areas as seen in `core/store/src/trie/prefetching_trie_storage.rs`), and `parking_lot::Mutex` (unlike `std::sync::Mutex`) does **not** poison on panic, so a lock held during a panicking apply task will simply be released with whatever partial mutation happened, and the node will continue as if nothing went wrong. Instead of stopping (which is what the caller would want when an "unexpected" invariant violation happens deep in the runtime, e.g. a state/gas accounting or trie-mutation bug), the shard job is silently recorded as `Err`, tracing an error log line, and processing continues. [4](#0-3) [5](#0-4) 

### Impact Explanation
Because `apply_chunk` execution is on the direct path from a submitted transaction/receipt to state transition, a panic triggered there by a crafted or edge-case transaction (e.g. an unexpected arithmetic/invariant panic in gas/balance/trie accounting) would, on other implementations, either crash the node (safe, loud failure) or be caught safely without touching shared unpoisoned state. Here, the panic is caught but with `AssertUnwindSafe` around a task that can mutate globally shared caches guarded by non-poisoning locks, so the node keeps running with potentially inconsistent internal cache state while only surfacing a soft per-shard error. This can manifest as incorrect subsequent state computations (if cached trie/prefetch data is left partially updated) or as masked-but-recoverable node behavior for what should be a hard-stop condition, which is precisely the "silently handle what should crash" bug class the source report addresses.

### Likelihood Explanation
This requires a code path in chunk application (trie ops, runtime execution, gas/balance accounting) to actually panic on some malformed-but-syntactically-valid input, which is an "unexpected bug" scenario rather than a normal error path — the same characterization the source Penumbra commit uses ("these crashes are unexpected and indicative of some actual issue"). I was not able to trace, within the available iterations, the exact shared mutable state touched by the real `apply_chunk` implementation deep inside `near-vm`/`near-store`/`runtime` crates to confirm that a specific corrupting sequence exists today; the finding is grounded in the panic-catching design itself (`AssertUnwindSafe` + non-poisoning `parking_lot::Mutex` + continuing execution) rather than a demonstrated triggering transaction. This should be treated as moderate/uncertain likelihood pending deeper tracing of what state guards are actually held during `task()` execution.

### Recommendation
Reconsider whether `PendingShardJobs::run` should convert a shard-apply-task panic into a recoverable error at all. If the intent is defense-in-depth against DoS, at minimum: (1) audit whether any locks/caches mutated during `task()` execution can be left in an inconsistent state on panic, given `parking_lot::Mutex` does not poison, and add explicit poisoning/consistency guards around those structures; or (2) mirror the Penumbra fix and propagate the panic to crash the node/process for chunk-apply failures, since a panic in this deterministic, consensus-critical path indicates a real bug that should not be silently absorbed and continued past.

### Proof of Concept
Not independently reproduced — the analysis is based on the documented panic-handling logic in `PendingShardJobs::run` and its `AssertUnwindSafe` catch, combined with `parking_lot::Mutex`'s non-poisoning semantics used by shared trie/prefetch caches touched during chunk application; no reachable panic-triggering transaction was verified within the scope of this review.
