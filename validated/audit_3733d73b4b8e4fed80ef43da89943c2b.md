### Title
Webhook `shop` and `topic` fields are dispatched to handlers without HMAC coverage, allowing cross-tenant data injection via header manipulation - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then trusts the `shop`, `topic`, and `webhook_id` values taken from unauthenticated HTTP headers to route and label the payload to the app's handler.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop`, `topic`, and `webhook_id` are read directly from HTTP headers that are never part of the signed content [2](#0-1) . `Registry.process` validates only this body-only HMAC via `Utils::HmacValidator.validate(request)` and then immediately uses `request.topic` to select a handler and `request.shop` to populate `WebhookMetadata` passed to the app's handler [3](#0-2) .

This breaks the intended identity binding: `hmac == HMAC(body)` is checked, but the code proceeds to trust `shop == header["x-shopify-shop-domain"]` and `topic == header["x-shopify-topic"]` as if they were authenticated too — i.e., the binding `authenticated(shop) == shop_acted_on` does not hold. Concretely, if an attacker (an unprivileged internet user who is themselves able to install the app on their own shop, or who has captured/observed one legitimate webhook delivery to their own shop for a given body/topic) resends the same `raw_body` and its valid `hmac-sha256` header, but substitutes a different `x-shopify-shop-domain` or `x-shopify-topic` header, `HmacValidator.validate` still returns true (because it only recomputes HMAC over the untouched body), and the forged `shop`/`topic` values flow straight to the host application's webhook handler via `WebhookMetadata`.

### Impact Explanation
Per the documented `data` contract, the host application is told that `data.shop` and `data.topic` are reliable identifiers of "The shop domain of the webhook" and "The topic of the webhook" [4](#0-3) . Any downstream consumer that keys per-tenant processing, storage, or authorization off `data.shop` (exactly as shown in the gem's own example, which forwards `shop_domain: data.shop` into a job queue) inherits an unauthenticated tenant identifier. This is a genuine cross-tenant boundary break: the value the gem hands the host app as "the shop this webhook is for" is not the value that was actually cryptographically verified.

### Likelihood Explanation
Reaching this path requires no access to `client_secret`, no privileged account, and no leaked credentials — only the ability to author raw HTTP requests to the app's public webhook endpoint (an unprivileged internet capability) plus one legitimately observed body+hmac pair (obtainable by installing the app on an attacker-owned shop and receiving one real webhook, or by capturing/replaying any webhook delivery whose body is attacker-known/predictable, such as an empty or fixed-content topic).

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signable content (or otherwise independently bind and verify them, e.g., by requiring the host app to check `data.shop` against its known installed-shops table before trusting it), rather than exposing raw, unauthenticated header values as if they were verified alongside the HMAC.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and registers for `orders/create`. Shopify delivers a webhook with body `B`, headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: orders/create`, and a valid `x-shopify-hmac-sha256: H = HMAC(secret, B)`.
2. Attacker resends the identical body `B` and identical `x-shopify-hmac-sha256: H` to the app's webhook endpoint, but changes the header `x-shopify-shop-domain` to `victim-shop.myshopify.com` (or changes `x-shopify-topic` to a more sensitive topic such as `customers/data_request`).
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` — this still equals `H` because `to_signable_string` only ever returns the body [1](#0-0) , so validation passes.
4. `Registry.process` looks up the handler by the attacker-controlled `request.topic` and invokes it with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` [3](#0-2)  — the host app's handler now processes data it believes came from `victim-shop.myshopify.com` (or under a different topic than Shopify actually sent), even though only the body was ever authenticated.

```ruby
        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
```
