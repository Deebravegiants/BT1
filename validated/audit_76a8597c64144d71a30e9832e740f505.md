## Finding

### Title
Webhook `shop-domain` header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, but the `shop` (and `topic`, `webhook_id`, `api_version`) values that are handed to the app's handler as the trusted tenant identifier come from unauthenticated HTTP headers that are excluded from the signed payload.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is never part of the signable string: [2](#0-1) 

`Registry.process` validates only `Utils::HmacValidator.validate(request)` (i.e., body vs. HMAC) and then forwards the unauthenticated `request.shop` straight into `WebhookMetadata` that is passed to the app's handler: [3](#0-2) 

`HmacValidator.validate` in turn only compares `verifiable_query.hmac` against a signature computed from `verifiable_query.to_signable_string` (the body): [4](#0-3) 

This breaks the identity binding `shop_verified_by_hmac == shop_delivered_to_handler`. The gem's own documentation instructs host apps to treat `data.shop` as the trustworthy shop identifier once `Registry.process` "verif[ies] the request did indeed come from Shopify," and shows it being used directly to key background work (`shop_domain: data.shop`): [5](#0-4) [6](#0-5) 

Because the `api_secret_key` used to sign webhooks is shared across every shop that has installed a given app (it is per-app, not per-shop), any merchant who installs the app receives genuine webhooks with a body+HMAC pair that is valid under that shared secret. Since the HMAC never covers the `shop-domain` header, that same attacker (an "unprivileged" merchant relative to other tenants of the same app) can replay the identical `raw_body`/`hmac` pair to the app's webhook endpoint while substituting any other shop's domain in the `x-shopify-shop-domain` header. `HmacValidator.validate` will still return `true` (it only checks the body), and `Registry.process` will dispatch the payload to the handler labeled with the attacker-chosen `shop`, producing cross-tenant data confusion in any host application that follows the documented pattern of trusting `data.shop`.

### Impact Explanation
This matches the "Critical - cross-tenant access" category: an attacker who is a legitimate installer of the app (not requiring `api_secret_key`, an access token, or any credential belonging to the victim) can cause the app to process/attribute webhook data under a victim shop's identity, corrupting per-tenant state, triggering unauthorized actions keyed off the spoofed shop, or polluting per-shop caches/queues that key off `data.shop`.

### Likelihood Explanation
Likelihood is realistic but not trivial: the attacker must (a) install the target app themselves (or otherwise obtain one legitimate `raw_body`+`hmac` pair signed with the app's shared secret) and (b) know or guess a target `shop-domain` to spoof, both of which are within reach of an ordinary internet user who can sign up for the app. No secret material or elevated privileges are required — only the fact that HMAC validation is scoped to the body while the identity field flows from an unauthenticated header.

### Recommendation
Bind the shop (and ideally topic/webhook_id) into the value that is HMAC-verified, e.g. by including the `shopify-shop-domain` header value in `to_signable_string`, or by requiring host apps/the gem itself to independently verify that `request.shop` matches a shop with an active, previously-established session/webhook registration before dispatching to the handler.

### Proof of Concept
1. App "target-app" is installed by attacker's own shop `attacker.myshopify.com` and by victim shop `victim.myshopify.com`; both webhooks are signed with the same app-wide `api_secret_key`.
2. Attacker receives a genuine webhook delivery to their own shop: body `{"id":123}"`, header `x-shopify-hmac-sha256: <valid HMAC of body>`, `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker POSTs the identical body and HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate` succeeds because it only checks the body against the HMAC: [7](#0-6) 
5. `Registry.process` builds `WebhookMetadata` with `shop: request.shop` = `"victim.myshopify.com"` (attacker-controlled header) and calls the app's handler, which — per the gem's documented usage — trusts `data.shop` as the tenant identifier.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
