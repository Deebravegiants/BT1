## Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` (tenant) identity from the `X-Shopify-Shop-Domain` HTTP header, but the HMAC signature that `Registry.process` validates is computed only over the raw request body. The shop domain that the gem hands to the host application's webhook handler is therefore never authenticated, breaking the binding: `hmac-verified-bytes == identity-bytes acted upon`.

### Finding Description
`Request#hmac` reads the `hmac-sha256` header, and `Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read from a separate, unsigned header: [2](#0-1) 

`Registry.process` validates only the HMAC over the raw body, then immediately trusts `request.shop` to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

`Utils::HmacValidator.validate` confirms the signable string is compared byte-for-byte against the computed HMAC, but the signable string never includes the shop domain: [4](#0-3) 

Because the shop-domain header sits outside the HMAC-covered bytes, an attacker who possesses one legitimately-signed webhook (raw body + `hmac-sha256` for a topic on their own, attacker-controlled shop) can resend that exact body/HMAC pair to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a victim shop's domain. `Utils::HmacValidator.validate` still succeeds (it only checks the body), and `Registry.process` dispatches the handler with `shop: <victim-domain>`, `body: <attacker-controlled-content>`. This is exactly the "verified bytes vs. acted-upon bytes" binding break called out for the HMAC bug class: the identity field (`shop`) that downstream code treats as authenticated is disjoint from the field actually protected by the signature.

### Impact Explanation
This crosses a tenant boundary that this gem is specifically responsible for enforcing, since `Registry.process`'s entire purpose is to hand the host application verified, shop-attributed webhook data. An attacker can cause the app to process attacker-controlled webhook content (e.g. `orders/create`, `customers/data_request`, `shop/redact`) as if it originated from a shop they do not control, leading to cross-tenant data confusion/injection — data belonging to the attacker's own shop being written into, or triggering deletion/side-effects against, another merchant's tenant space within the host application. This matches the Critical "cross-tenant access" impact category, since the compromised binding is `shop` identity vs. signed bytes, with no credential or privileged access required beyond running an app install on one's own store (available to any unprivileged internet user) and the ability to POST to the app's public webhook endpoint.

### Likelihood Explanation
Likelihood is moderate-to-high in relative terms for this bug class: the attacker needs (1) to install the app on any store they control (a normal, unprivileged action) to obtain one validly-signed webhook body/HMAC pair for a topic of interest, and (2) the ability to resend that request to the app's public webhook endpoint with a modified `shop-domain` header — both being externally reachable, no leaked secret or privileged Shopify credential required. This satisfies the "unprivileged internet user" threat model in scope.

### Recommendation
Bind the shop domain (and other identity-bearing headers such as `topic`/`api-version`) into the HMAC-signable content, or otherwise require the host application to independently correlate `request.shop` against a shop it has a legitimate, established relationship/session with before trusting the webhook payload. At minimum, `Request#to_signable_string` should incorporate the `shop-domain` header (or the caller must be required to pre-validate that the shop is one they have on record) so that `Utils::HmacValidator.validate` cannot pass when the shop-domain header has been tampered with independently of the body.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (any unprivileged internet user can do this) and triggers a webhook (e.g., `customers/data_request`), capturing the raw POST body and the `X-Shopify-Hmac-Sha256` header Shopify sent.
2. Attacker resends the exact same raw body and `X-Shopify-Hmac-Sha256` header to the app's public webhook endpoint, but changes `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` in `Registry.process` (`lib/shopify_api/webhooks/registry.rb:190`) succeeds because it only checks `@raw_body` against the HMAC — the shop-domain header is not part of the signed content (`lib/shopify_api/webhooks/request.rb:36-38`).
4. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: <attacker body>, ...))`, causing the host application to process attacker-controlled data under the victim's tenant identity.
