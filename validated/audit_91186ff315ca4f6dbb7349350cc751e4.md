### Title
Permissionless HyperSwap V2 pool pre-seeding lets an unrelated wallet MitM the graduation LP open price, seeding the TOKEN/LT pair up to ~50 bps away from curve-close — ([File: packages/contracts/src/Bonding.sol])

### Summary
Between phase 1 (`_enterGraduating`) and phase 2 (`finalizeGraduation`) of graduation, an unprivileged wallet can permissionlessly create the HyperSwap V2 `TOKEN/LT` pair and `mint` LP against a self-chosen hostile reserve ratio, the same way a rogue router advertisement redirects traffic before the legitimate host configures its route. `finalizeGraduation`'s rebalance-and-deposit defense (`_seedRebalancing` / `_pairRebalance` / `_routerDepositAndDispose`) is documented by the protocol's own AGENTS.md as opening the LP within "~50 bps" of curve-close for this attack shape, rather than at the zero-gap price the honest path guarantees, and the dedicated regression suite that verified the wrong-opening-price / attacker-no-profit claims (`test/HostilePreSeed.t.sol`) has been removed.

### Finding Description
Graduation is split into two transactions to fit HyperEVM's small-block gas ceiling [1](#0-0) . `_enterGraduating` fires inline at the end of the threshold-crossing buy, caches `(tokensForLP, ltFromPair)` at the last curve price, and freezes trading, while `finalizeGraduation` is a separate, **permissionless** transaction anyone can call [2](#0-1) .

Between these two transactions, `factory.createPair(token, lt)` is permissionless and, once created, anyone can `transfer` tokens/LT to the pair and call `pair.mint(to)` to seed LP at any ratio they choose — this is the "front-run" exploit the protocol's own AGENTS.md documents in detail [3](#0-2) .

`finalizeGraduation` calls `_seedUniswapV2Direct` → `_seedRebalancing`, which handles a non-empty, mint-seeded pair by computing a rebalancing swap via `_noFeeSwapInput` — an explicitly **no-fee** constant-product model — and then executing the real swap on the fee-charging pair via `pair.swap` [4](#0-3) . The mismatch between the no-fee target computation and the fee-charging execution is acknowledged directly in the code: "the actual swap is fee-charging (the pair's live fee), so the post-swap ratio drifts from the target by the fee; the balanced-subset deposit absorbs the residual without donating" [5](#0-4) . The remaining inventory is then deposited through the HyperSwap router's `addLiquidity` with `min0=1, min1=1`, whose `quote()`-based optimal-split logic introduces additional integer-rounding drift [6](#0-5) .

The protocol's own security documentation quantifies the resulting deviation: "Larger mint pre-seeds (where the rebalance swap fires) open within ~50 bps — the structural ceiling is the V2 fee landing between rebalance and deposit (~30 bps) plus integer rounding in the router's `quote()`-based split (~10 bps)" [7](#0-6) . This is a direct violation of the protocol's own "Zero price gap" invariant, which is only claimed to hold "within 1 bps" and is only enforced by `test/GraduationInvariants.t.sol` for the honest (no-pre-seed) path [8](#0-7) .

Critically, the dedicated end-to-end suite that used to assert the "wrong-opening-price" bound and the "attacker P&L ≤ 0" property (`test/HostilePreSeed.t.sol`) has been deleted and is no longer run: "the wrong-opening-price / LP-capture scenarios, attacker-no-profit, leftover recovery, and concurrent-graduation isolation properties are no longer enforced by automated tests" [9](#0-8) . Only the brick-resistance regression (`test_brick_resistance_frontRun_dust_seed` in `test/TwoPhaseGraduation.t.sol`) is currently exercised, and that test only asserts that finalize doesn't revert and that LP is nonzero — it does not assert the open price is within any bound [10](#0-9) .

### Impact Explanation
Any unrelated wallet — no `BONDING_ROLE`, no creator or owner privilege — can, between `_enterGraduating` and `finalizeGraduation`, seed the graduation LP so it opens up to ~50 bps away from the true curve-close price, and per the protocol's own "LP capture" analysis, "the wasted-side excess goes to the attacker's LP claim" [11](#0-10) . This is a concrete "LP seeded away from the curve close price" outcome, and because `LPLock.recordLock` is a one-shot call that `finalizeGraduation` cannot skip or retry [12](#0-11) , the mispriced/attacker-captured LP position is locked permanently with no remediation path once `finalizeGraduation` completes. Every trader who buys/sells post-graduation through `Zap`/HyperSwap trades against this off-price pool until arbitrage closes the gap, transferring value from honest holders to the pre-seeding attacker in the interim.

### Likelihood Explanation
`finalizeGraduation` is explicitly permissionless and expected to be called by anyone (a keeper Worker in the happy path, "anyone can call to rescue a stuck token" otherwise) [13](#0-12) . The window between `_enterGraduating` (which is observable via the `TokenGraduating` event) and `finalizeGraduation` is exactly the race window the attacker needs, and `factory.createPair` + `transfer` + `pair.mint` are all unprivileged calls documented as the exact exploit primitives in AGENTS.md itself. The unit-level guardrails (`DIRECT_MINT_PRESEED_BPS` direct-mint fallback, 1% swap-budget reservation) prevent bricking and bound the *worst-case* deviation, but they don't eliminate the acknowledged ~50 bps drift, and the test suite that once verified the bound end-to-end no longer runs.

### Recommendation
Either (a) collapse the two-phase graduation window so pre-seeding cannot occur between phases (e.g., create the pair and reserve/lock it in phase 1), or (b) re-instate an end-to-end regression suite (restore/rebuild the equivalent of `test/HostilePreSeed.t.sol`) that asserts a strict bound on the LP open-price deviation and on attacker LP capture for every pre-seed shape, gating CI on it. Additionally, consider making `_noFeeSwapInput`'s target account for the pair's actual fee rate so the rebalance swap lands closer to the true target ratio before the router deposit, shrinking the ~30 bps fee-driven component of the drift.

### Proof of Concept
1. Token `T` trades on `Bonding`'s curve against LT `L`; a buy crosses the USD/supply threshold, `_executeBuy` calls `_enterGraduating`, emitting `TokenGraduating` and caching `(tokensForLP, ltFromPair)` — lifecycle flips to `Graduating`, trading frozen [14](#0-13) .
2. Attacker (any EOA, no roles) calls `IUniswapV2Factory(uniswapV2Factory).createPair(T, L)`, then `transfer`s a small amount of `T` and `L` to the pair at a ratio far from `tokensForLP/ltFromPair`, then calls `pair.mint(attacker)` — minting LP to itself at the hostile ratio, exactly as described in AGENTS.md's "The exploit" section [15](#0-14) .
3. Anyone calls `Bonding.finalizeGraduation(T)`. Since `totalSupply() != 0`, `_seedUniswapV2Direct` routes to `_seedRebalancing`, which rebalances via the no-fee-modeled `_pairRebalance` and deposits via `_routerDepositAndDispose`'s `addLiquidity(..., 1, 1, lpLock, ...)` [16](#0-15) .
4. Per the protocol's own quantified analysis, the resulting pool opens up to ~50 bps off the curve-close price, and the attacker's pre-existing LP position (from step 2) captures a pro-rata share of the "wasted-side" deposit — locked permanently via `LPLock.recordLock` with no automated regression test currently verifying the bound [17](#0-16) .

### The exploit

A vanilla UniswapV2 pair is deployable by anyone: `factory.createPair(token, lt)` is permissionless, and after creation anyone can call `pair.mint(to)` against pre-transferred tokens. So between phase 1 (`_enterGraduating` flips lifecycle to `Graduating` and caches `tokensForLP / ltFromPair`) and phase 2 (`finalizeGraduation` mints LP via `pair.mint(lpLock)`), an attacker can:

1. Front-run by calling `factory.createPair(token, lt)` themselves
2. `transfer(pair, smallToken)` and `transfer(pair, smallLT)` at any ratio they choose
3. Call `pair.mint(attacker)` — they now own LP at a hostile reserve ratio

When our `pair.mint(lpLock)` runs in phase 2 against this non-empty pair, V2's mint formula picks up the existing reserves:

```
liquidity = min(amount0 · totalSupply / reserve0, amount1 · totalSupply / reserve1)
```

The `min(...)` arm whose denominator is bigger relative to its numerator wins, and the OTHER arm's "excess" deposit is donated pro-rata to existing LP holders — i.e. to the attacker. Two harms:

- **Wrong opening price.** Post-mint reserves are `(R_attacker + T_a, R_attacker + T_b)`, so the LP opens at `(R_a + T_a) / (R_b + T_b)`, NOT at the curve close `T_a / T_b`. A `$15` LT pre-seed at 50% off curve close opens the pool ~454 bps off.
- **LP capture.** The wasted-side excess goes to the attacker's LP claim. A `1 wei + 1 LT` pre-seed (~`$1` attack budget) captures ~34 bps of LP.

### Pool-open precision

Honest graduations open at 0 bps gap (Regime 1, exact direct mint). Dust mint pre-seeds also open at ~0 bps — they take the `_seedDirectMint` fallback, which deposits at the cached ratio with only a vanishing skew from the dust reserves. Larger mint pre-seeds (where the rebalance swap fires) open within ~50 bps — the structural ceiling is the V2 fee landing between rebalance and deposit (~30 bps) plus integer rounding in the router's `quote()`-based split (~10 bps). 50 bps is well inside "exploit denied" — arbitrage closes the gap within blocks and the attacker still loses pre-seed value.

### Per-graduation LT isolation

`finalizeGraduation` snapshots `protectedLT = balanceOf(this) - p.ltFromPair` at the top: any LT in `Bonding` beyond this graduation's earmark is either another concurrent graduation's escrow (Phase 1 already moved it in via `Router.graduate`) or stray dust. Both must stay out of THIS graduation's LP and post-sweep.

That snapshot is plumbed through `_seedUniswapV2Direct` → `_seedRebalancing` → `_routerDepositAndDispose`, where the deposit allowance is capped at `balanceOf(this) - protectedLT`. Then a single `_sweepLTToOwner(lt, protectedLT)` at the end of `finalizeGraduation` sends only THIS graduation's rebalance residue to the protocol owner, leaving any concurrent-graduation escrow / stray dust untouched. Honest empty-pair graduations have no residue at the post-sweep so it's a no-op there.

Two scenarios this guards against:

- **Concurrent graduations on the same LT.** Two tokens A and B share an LT and both reach `Lifecycle.Graduating` before either finalizes (the keeper takes ~60s and popular LTs see overlap). Without `protectedLT`, A's finalize would treat the full balance as its own and either sweep B's escrow to the owner (bricking B's later finalize) or — for hostile-pre-seed graduations — deposit it into A's locked LP. With it, A only ever sees `ltFromPair_A` and B is preserved.
- **Cross-token LT residue.** Old residue or a misdirected transfer sitting in `Bonding` would otherwise be visible to `_routerDepositAndDispose`'s `balanceOf(this)` read and could be silently consumed into a future graduation's locked LP. With `protectedLT`, contamination stays in `Bonding` and the deposit only sees this graduation's earmark.

The auto-sweep emits `LTRescued(lt, owner, amount)` for indexer observability. The dedicated regression tests for these edge cases were removed alongside `HostilePreSeed.t.sol`; future changes to `finalizeGraduation` / `_routerDepositAndDispose` / `_sweepLTToOwner` should add targeted coverage if the behaviour is non-obvious from the unit-level tests in `TwoPhaseGraduation.t.sol`.

### Tests you MUST re-run if you change any of this

- `test/NoFeeSwapInput.t.sol` — 9 deterministic + 2 fuzz tests on the load-bearing math (degenerate inputs, monotonicity, cap-at-budget, closed-form correctness, overflow safety, the round-down-to-zero input shape that motivated the precheck).
- `test/TwoPhaseGraduation.t.sol` — brick-resistance + phase-1-fits-in-small-block tests, plus the hostile-pre-seed open-at-cached-ratio tests (`test_hostilePreSeed_*`) covering both the dust direct-mint fallback and the meaningful-reserve swap path, must still pass.
- `test/GraduationInvariants.t.sol` — zero-gap, supply conservation, parabola cap. Honest-path properties unchanged by the defense.

The dedicated end-to-end hostile-pre-seed integration suite (`test/HostilePreSeed.t.sol`) was removed for runtime reasons after deployment — the wrong-opening-price / LP-capture scenarios, attacker-no-profit, leftover recovery, and concurrent-graduation isolation properties are no longer enforced by automated tests. If you change any of the graduation / rebalance / deposit code paths, consider re-deriving these properties manually and / or adding targeted regressions for whatever you touch.

    function _pairRebalance(
        RebalanceParams memory p
    ) internal returns (bool) {
        uint256 s = _noFeeSwapInput(p.reserveIn, p.reserveOut, p.targetN, p.targetD, p.maxSwap);
        if (s == 0) return false;

        // Quote from the pair so the output tracks its live fee; a value
        // derived from a stale fee rate would trip the pair's K-check.
        uint256 expectedOut = IUniswapV2Pair(p.pair).getAmountOut(s, p.tokenIn);
        if (expectedOut == 0) return false;

        IERC20(p.tokenIn).safeTransfer(p.pair, s);
        (uint256 amount0Out, uint256 amount1Out) = p.tokenInIs0 ? (uint256(0), expectedOut) : (expectedOut, uint256(0));
        IUniswapV2Pair(p.pair).swap(amount0Out, amount1Out, address(this), new bytes(0));
        return true;
    }
