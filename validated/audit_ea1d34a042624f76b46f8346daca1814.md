### Title
Webhook shop-domain identity spoofing via HMAC that only covers the request body - ([File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then trusts the unauthenticated `x-shopify-shop-domain` header as the tenant identity passed to the host application's handler. Because the app's `api_secret_key` is shared across every shop that installs the app, and the HMAC signature never covers the shop-domain header, an attacker who can obtain one genuine `(body, hmac)` pair (e.g., by installing the app on their own store and triggering any webhook) can replay that exact body/HMAC pair to the app's public webhook endpoint while substituting an arbitrary victim shop domain in the header. The signature still validates, and the forged shop identity is delivered to the handler as authentic.

### Finding Description
`Utils::HmacValidator.validate` computes and compares the signature only against `verifiable_query.to_signable_string`, and for webhook requests that method returns just the raw body: [1](#0-0) 

The `shop`, `topic`, and `webhook_id` fields are all parsed straight from HTTP headers and are never part of the signed material: [2](#0-1) 

`HmacValidator.validate_signature` performs a byte-for-byte compare of the computed HMAC (over the body only) against the received HMAC, with no binding to the shop claimed in the headers: [3](#0-2) 

`Registry.process` uses the result of this body-only HMAC check as sufficient authorization to trust `request.shop` (the header value) as the tenant identity forwarded to the application's webhook handler: [4](#0-3) 

Because `api_secret_key` is the same secret for every shop the app is installed on (it's the app's client secret, not a per-shop secret), any merchant who has installed the app can generate a *valid* `(raw_body, hmac)` pair by having Shopify send them a real webhook. That pair is valid for any shop-domain header, since the shop header is not part of the signed content. The binding that should hold — "the shop claimed by `request.shop`" equals "the shop whose data the HMAC actually attests to" — does not exist anywhere in this code path.

### Impact Explanation
This breaks a tenant identity boundary: the library hands the host application a `WebhookMetadata` object whose `shop` field is claimed to have been "verified" (the HMAC check gates delivery to the handler) but is in fact attacker-controlled and decoupled from the actual signed payload. A malicious/attacker-controlled merchant tenant can inject a passing-HMAC request that impersonates a *different* shop, causing the host app to process attacker-supplied data (order data, `app/uninstalled`, `shop/redact`, GDPR events, inventory changes, etc.) under another tenant's identity. Depending on how the host app keys its per-shop persistence off `WebhookMetadata#shop` (as the docs instruct: register/process webhooks "for a shop" using the `shop` field), this enables cross-tenant data corruption or triggering of privileged per-shop side effects (e.g., forcing an uninstall/token-revocation flow, forging compliance webhooks) against a shop the attacker does not control. This matches the Critical "cross-tenant access" category since the identity binding between the authenticated bytes (body) and the trusted tenant key (shop header) is absent.

### Likelihood Explanation
Exploitation requires only: (1) the attacker be a legitimate merchant/tenant of the app (an "unprivileged internet user" relative to other tenants — no special access needed to the app's `client_secret` or another shop's credentials), and (2) knowledge of the victim's `*.myshopify.com` domain, which is public. The attacker only needs to capture one genuine webhook delivery from their own store (trivial, since installing the app and triggering any event yields one) and replay it to the app's public webhook endpoint with a forged `x-shopify-shop-domain` header. No secrets, tokens, or privileged access are required, making this readily reachable by any user who can install the app on a store they control.

### Recommendation
Do not treat `request.shop` as authenticated purely because the body HMAC validated. At minimum:
- Cross-check `request.shop` against the shop associated with the session/webhook registration expected to receive that specific `topic`/payload before invoking the handler, or
- Bind the shop domain into the signed material used for comparison (not possible since Shopify's own HMAC spec only signs the body — so instead) require that the host application separately confirms the shop is one for which the app currently holds an active session/installation before trusting webhook content tied to that shop, and treat `WebhookMetadata#shop` as an unauthenticated hint rather than a verified value in the library's documentation, explicitly warning integrators that shop-domain spoofing is possible if they don't independently validate installation/session state for the claimed shop.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com`.
2. Attacker triggers a real webhook (e.g. `orders/create`) with attacker-controlled body content; Shopify delivers it with a valid `x-shopify-hmac-sha256` computed over that raw body using the app's shared `api_secret_key`.
3. Attacker captures the exact `raw_body` and `x-shopify-hmac-sha256` value.
4. Attacker POSTs the same `raw_body` and `x-shopify-hmac-sha256` to the app's public webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` and `x-shopify-topic: orders/create`.
5. `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:12-31`) returns `true` because the signature check only covers `raw_body`, which is unmodified.
6. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) invokes the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker's data>, ...)`, and the host app processes attacker-controlled content as though it originated from the victim shop.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
