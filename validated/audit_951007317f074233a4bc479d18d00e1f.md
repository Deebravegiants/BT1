### Title
Webhook `shop` (and `topic`/`webhook-id`) identity fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by verifying an HMAC over the raw request body, then trusts the `shop-domain` (and `topic`/`webhook-id`) HTTP headers — which are never included in the signed material — to decide which merchant/tenant the webhook belongs to.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, and `webhook_id` accessors instead read directly from unauthenticated HTTP headers: [2](#0-1) 

`Registry.process` verifies only that body-derived HMAC, then forwards the unauthenticated `request.shop`, `request.topic`, and `request.webhook_id` straight into `WebhookMetadata`, which is handed to the application's webhook handler as trusted tenant-identifying data: [3](#0-2) 

This reproduces the report's bug class exactly: a field that is *acted on* (the `shop` value used to identify which tenant's data the webhook concerns) is not *covered by the HMAC* that is supposed to authenticate the request. The equality that should hold — "the shop the HMAC authenticates == the shop the handler acts on" — is broken; the HMAC only authenticates "this body byte-string was produced with our shared `api_secret_key`," it says nothing about which shop the request claims to be for.

Because the same app `client_secret`/`api_secret_key` is shared across every shop that installs the app, any shop that receives (or can trigger) a legitimately-signed webhook body for itself possesses a valid `(body, hmac)` pair. That pair remains valid under `HmacValidator.validate` no matter what `x-shopify-shop-domain`, `x-shopify-topic`, or `x-shopify-webhook-id` header values accompany it, since those headers play no part in `to_signable_string`.

### Impact Explanation
An attacker who controls one legitimate tenant (shop) of a multi-tenant app can capture a validly-HMAC'd webhook body delivered to their own shop, then replay it to the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop. `Registry.process` will accept the HMAC (it only checks the body) and dispatch `WebhookMetadata` claiming to be from the victim shop/topic. If the host application uses `WebhookMetadata#shop` to select the tenant record/session/access token to operate on (the normal and documented usage pattern), this results in cross-tenant data confusion — the classic impact category of "cross-tenant access" listed as Critical impact.

### Likelihood Explanation
Exploitation requires only: (1) being an "unprivileged" outsider relative to the victim tenant while being a legitimate/attacker-controlled shop for some tenant of the same app (a very low bar — one can install almost any public app), and (2) sending an HTTP request to the app's public webhook endpoint with attacker-chosen headers, which is trivial since headers are never authenticated. No access token, `client_secret`, or credential theft is required — exactly matching the report's "unprivileged internet user breaking an identity binding" class.

### Recommendation
Bind the shop (and topic/webhook id) identity to the HMAC-verified content, e.g., by having Shopify-delivered payload bodies or an authenticated channel carry the shop identity, or by requiring the host application (and documenting this requirement loudly) to cross-check `request.shop` against the shop for which the corresponding webhook registration/session was created, and rejecting webhooks whose claimed shop does not match a registration made via `Registry.register`/`register_all` for that topic. At minimum, update `docs/usage/webhooks.md` to explicitly warn that `shop`, `topic`, and `webhook_id` are unauthenticated headers and must be independently verified against known installed shops before being used to select tenant data.

### Proof of Concept
1. App has two installs: Shop A (attacker-controlled) and Shop B (victim), sharing one `api_secret_key`.
2. Shopify (or the attacker, via any action that triggers a webhook on Shop A) delivers a legitimate webhook to the app for Shop A:
   ```
   POST /webhook
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid HMAC of body computed with shared api_secret_key>
   x-shopify-shop-domain: shop-a.myshopify.com
   body: {"id": 123, ...}
   ```
3. Attacker captures this `(body, hmac)` pair and resends it, only changing the header:
   ```
   x-shopify-shop-domain: shop-b.myshopify.com
   ```
4. `ShopifyAPI::Utils::HmacValidator.validate(request)` returns `true` because it only hashes `@raw_body` (`lib/shopify_api/utils/hmac_validator.rb:26-31`, `lib/shopify_api/webhooks/request.rb:36-38`).
5. `Registry.process` calls the registered handler with `WebhookMetadata.new(... shop: "shop-b.myshopify.com" ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), even though the payload never originated from or was authenticated for Shop B.
