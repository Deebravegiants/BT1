The bug-class from the external report — a sensitive function skipping a zero-value check that the docstring/design implicitly assumes never happens — reproduces in `evm/tron/contracts/apps/IntentGatewayV2.sol`'s `placeOrder`/`withdraw` pair, reachable by any ordinary intent-order placer.

### Title
Missing zero-amount validation in Tron `IntentGatewayV2.placeOrder`'s predispatch path permanently freezes escrowed order funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`placeOrder`'s predispatch branch never rejects a zero `amount` for `order.inputs`/`order.predispatch.assets`, unlike the non-predispatch branch and unlike the mainline EVM `IntentGatewayV2.sol`. A zero-amount input token leaves its `_orders[commitment][token]` escrow slot at `0`, and the shared `withdraw()` function treats a `0` escrow balance as "unknown order" and reverts the entire withdrawal loop, permanently locking every other (legitimately non-zero) token escrowed under the same commitment.

### Finding Description
In the predispatch branch of `placeOrder` (no protocol fee case is irrelevant; this affects both), the amount checks that exist in the non-predispatch `else` branch are missing: [1](#0-0) 

Compare with the `else` branch a few lines below, which does check: [2](#0-1) 

The mainline (non-Tron) `IntentGatewayV2.sol` explicitly guards against this with `if (amount == 0) revert InvalidInput();` in the equivalent predispatch loop and again in `order.inputs`: [3](#0-2) 

Because the Tron variant's predispatch loop skips this check, a caller can place an order whose predispatch `TokenInfo.amount == 0` for one leg. Escrow bookkeeping then stores `0` for that token: [4](#0-3) 

Later, whether the order is redeemed (`RedeemEscrow`), refunded (`RefundEscrow`), or cancelled via the GET-response path, all roads lead to the shared `withdraw()` function, which iterates every token in `body.tokens` and reverts the *entire* call the moment it finds a zero escrow balance: [5](#0-4) 

`_orders[body.commitment][token] == 0` is meant to detect "this order/token was never escrowed" (protecting against forged withdrawal requests), but it cannot distinguish that case from "this token really was escrowed with amount zero." Since `withdraw` is atomic (a single `for` loop with no per-token try/catch), one zero-amount leg reverts the whole transfer — including all other, non-zero tokens escrowed for that same commitment (and any transaction fees held under `TRANSACTION_FEES`). This is true both for solver-driven redemption and for the user's own cancellation/refund path, so the user has no recovery route once the order is placed.

### Impact Explanation
This is a permanent freezing of user funds: any order placed through the predispatch path with a zero-amount input leg becomes unfulfillable and unrefundable. The solver's fill attempt reverts, the source-chain refund via `cancelOrder`/`withdraw` reverts, and the destination-chain GET-response cancellation path reverts as well, since all three converge on the same `withdraw()` function and the same all-or-nothing loop. All tokens escrowed under that commitment — not just the zero-amount one — are stuck in the contract indefinitely.

### Likelihood Explanation
High. `placeOrder` and its predispatch mechanism are unprivileged, user-facing entry points intended for ordinary intent placers (the "token bridger"/"intent solver" surface explicitly in scope). No special permissions or governance action are required — a single crafted transaction with `order.predispatch.assets[i].amount == 0` (or, via the predispatch flow, `order.inputs[i].amount` ending up `0`) is sufficient to trigger the freeze, whether by mistake or intentionally against another user's funds if predispatch calldata is attacker-influenced.

### Recommendation
Add the same zero-amount guard already present in the mainline `evm/src/apps/IntentGatewayV2.sol` to the Tron variant's predispatch loop, e.g. `if (amount == 0) revert InvalidInput();` for `order.predispatch.assets[i].amount`, and `if (order.inputs[i].amount == 0) revert InvalidInput();` before computing `requiredAmount`/escrow amounts in the predispatch transfer-back loop. Additionally, consider hardening `withdraw()` itself so a single zero-balance/unknown token cannot revert redemption of the other, correctly-escrowed tokens in the same order (e.g., track presence with a separate existence flag rather than overloading `== 0`).

### Proof of Concept
1. Attacker/user calls `placeOrder` with `order.predispatch.call` and `order.predispatch.assets` non-empty, and `order.inputs` containing two tokens: token A with a normal amount, token B with `amount == 0`.
2. The predispatch loop (`evm/tron/contracts/apps/IntentGatewayV2.sol:393-446`) transfers/dispatches without checking token B's zero amount; `_orders[commitment][tokenB] += 0`, leaving it at `0`, while `_orders[commitment][tokenA]` is correctly credited.
3. A solver fills the order (or the user calls `cancelOrder` after expiry, or the destination dispatches `RefundEscrow`/`RedeemEscrow`) — all paths call `withdraw(body, ...)`.
4. Inside `withdraw`'s loop (`evm/tron/contracts/apps/IntentGatewayV2.sol:691-714`), when `token == tokenB`, `_orders[body.commitment][tokenB] == 0` is true, so it `revert UnknownOrder()`, aborting the whole transaction before token A's (and any fee's) transfer executes.
5. Token A's escrowed balance, and any escrowed transaction fees, remain locked in the contract with no successful code path to release them, since every caller of `withdraw` hits the same revert.
