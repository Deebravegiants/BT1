Based on my research, I found a strong analog. The Pluck CVE's root cause is that attacker-supplied content is trusted and later acted upon without validating its origin against the actually-authenticated actor. The closest reachable analog in this codebase is in the `pallet-hyper-fungible-token` calldata-execution path, where the *inner* `from` field of an ABI-encoded cross-chain `Message` — fully attacker-controlled — is used as the dispatch origin for an arbitrary runtime call whenever no cryptographic signature is supplied, without ever checking it against the party that actually triggered the transfer.

### Title
Unauthenticated Runtime-Call Origin Spoofing via Unsigned HyperFungibleToken Calldata - (File: modules/pallets/hyper-fungible-token/src/module.rs)

### Summary
`pallet_hyper_fungible_token::on_accept` authenticates the *outer* `PostRequest.from` (the peer contract address) via `ContractToAsset`, but the *inner* `Message.from` field — which is used to select the account that a bundled `runtime_call` is dispatched as — comes straight from the ABI-decoded request body and is never checked against any authenticated identity when `substrate_data.signature` is `None`.

### Finding Description
`on_accept` decodes the incoming ERC20 `Message` from the request body: [1](#0-0)  then, for the optional calldata-execution feature, decodes `SubstrateCalldata` from `message.data` and branches on whether a signature is present: [2](#0-1) 

When a signature *is* present, the origin is properly derived by verifying an Ed25519/Sr25519/ECDSA signature over `(nonce, runtime_call)` against the beneficiary account: [3](#0-2) 

But when no signature is supplied, the origin is instead derived directly from `message.from` — an attacker-controlled byte string that is part of the same ABI-encoded `Message` payload the caller freely constructs when invoking `send()`/calldata-bearing transfers on the source chain — and used unmodified as the `Signed` origin for dispatch: [4](#0-3) 

The only gate applied to the dispatched call is the runtime's `BaseCallFilter`, which restricts *which* calls are reachable at all (e.g. blocking calls during maintenance mode) but performs no authorization check tying the call to the actual sender: [5](#0-4) 

This is structurally the same bug class as CVE-2023-25828: a user-controlled value (there, file content; here, the `Message.from` byte string embedded in the cross-chain payload) is accepted without validating that it actually originates from what it claims to represent, and is then used to perform a privileged action (there, code execution when the file is later served as if it were a plain image; here, dispatching a runtime call as if it were properly signed by `from`).

### Impact Explanation
Any account able to call the source-chain `HyperFungibleToken`/token-bridge `send()` function with calldata (an ordinary, unprivileged token bridger — no special permission required) can set `message.from` to an arbitrary victim account/EVM address and attach a `data.runtime_call` of their choosing (e.g. `Balances::transfer_all`, `Assets::transfer`, or any other call reachable through `BaseCallFilter`). Because the unsigned branch trusts `message.from` verbatim as the dispatch origin, the call executes as `RawOrigin::Signed(victim)`, allowing unauthorized app actions — draining balances or performing any privileged call the victim account is authorized to make — without the victim's consent or a valid signature. This satisfies the "unauthorized app action" impact criterion.

### Likelihood Explanation
High. The attack requires only a normal cross-chain transfer with calldata dispatched from any EVM-supported chain — a capability explicitly exposed to ordinary users/token bridgers via the documented "Calldata Execution" feature [6](#0-5) . No consensus forgery, admin privilege, or race condition is needed — only crafting the `Message.data` payload with `signature: None` and an attacker-chosen `from`/`runtime_call`.

### Recommendation
Reject the unsigned branch entirely, or require that `message.from` be cryptographically bound (e.g., always require a signature verifying `from` controls the private key, removing the no-signature fallback), or derive the dispatch origin solely from an authenticated identity (e.g., mapping the true EVM `msg.sender` captured at message-construction time) rather than from an attacker-suppliable field inside the message body.

### Proof of Concept
1. Attacker calls the source-chain bridge's transfer function with a `data` payload encoding `SubstrateCalldata { runtime_call: <Balances::transfer_all(attacker, false)>, signature: None }` and `Message.from = victim_bytes`.
2. Message is relayed and delivered; `on_accept` decodes it, sees `signature.is_none()`, and sets `origin = victim` derived purely from `message.from`. [7](#0-6) 
3. `runtime_call.dispatch(RawOrigin::Signed(victim))` executes `Balances::transfer_all` from the victim's account to the attacker. [8](#0-7) 

**Caveat on confidence:** I was unable to inspect, in this session, the exact EVM-side `send()`/`HyperFungibleToken.sol` encoding logic that produces the `Message.from` field, to conclusively confirm whether the source contract ever independently pins `Message.from` to `msg.sender` before ABI-encoding it (which would partially mitigate this if enforced identically on every calling path). The pallet-side test fixtures I retrieved construct `Message.from` as an arbitrary literal independent of any sender check [9](#0-8) , which is consistent with it being attacker-suppliable, but a full audit of the EVM contract's `send()` implementation would be needed to close this gap definitively.
