### Title
Webhook `shop` (and other identity headers) are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook request as authenticated for a given shop once `Utils::HmacValidator.validate` succeeds, but the HMAC signature only covers the raw request body. The `shop`, `topic`, `webhook_id`, and `api_version` values are read straight from HTTP headers and are never included in the signed bytes, so the binding `HMAC_valid == true` does **not** imply `header.shop == shop that Shopify actually signed for`. Any merchant who has legitimately installed the app on their own store can capture one of their own genuine webhook deliveries (valid body + HMAC) and replay it to the app's webhook endpoint while swapping the `X-Shopify-Shop-Domain` header for a victim shop's domain. The signature check still passes because it only hashes `@raw_body`, letting the attacker's own webhook body be attributed to a different tenant.

### Finding Description
`Webhooks::Request` extracts identity fields purely from headers: [1](#0-0) 

But its `to_signable_string` — the value that actually gets HMAC-verified — only returns the raw body, deliberately excluding `shop`, `topic`, `webhook_id`, and `api_version`: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature purely over `to_signable_string` and secure-compares it to the `hmac` header: [3](#0-2) 

`Webhooks::Registry.process` uses this validation result as if it authenticates the entire request, including `request.shop`, and hands that unauthenticated header straight to the host application's handler as the tenant identity for the event: [4](#0-3) 

This is precisely the “field acted on but not covered by the HMAC” pattern: the equality that should hold — `hmac_verified(body) ⇒ shop_header == originating_shop` — is broken, because `shop_header` is never part of the signed input.

### Impact Explanation
Any unprivileged party who has installed the app on a store they control (a completely ordinary, unprivileged onboarding action — no credentials, tokens, or `api_secret_key` needed) can:
1. Trigger or capture a legitimate webhook delivery to their own shop (valid `raw_body` + valid `hmac` header, signed by Shopify with the app's real secret for a topic they control, e.g. `orders/create`).
2. Replay the exact same body and HMAC header to the app's webhook endpoint, but substitute `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) with a victim merchant's domain.
3. `HmacValidator.validate` still succeeds because the header is not part of the signed bytes, and `Registry.process` calls the handler with `shop: <attacker-chosen victim domain>`.

If the host application uses `WebhookMetadata#shop` to select which tenant's data to update/store/act on (the documented and expected usage), the attacker can inject their own data into another merchant's tenant context — a cross-tenant integrity/confidentiality violation reachable by any unprivileged internet user with just their own app installation, satisfying the "cross-tenant access" Critical impact bucket.

### Likelihood Explanation
Likelihood is high: exploitation only requires installing the target app on an attacker-owned development/trial store (which is free and unprivileged), capturing one webhook delivery, and replaying it with a modified header via any HTTP client. No secret material, access tokens, or social engineering is required — only the gem's own `Registry.process`/`Request`/`HmacValidator` code path, which is exactly what host apps are documented to call.

### Recommendation
Bind the identity headers into the signed material, or otherwise cryptographically tie `shop`/`topic`/`webhook_id` to the verified payload before trusting them — e.g., include them in `to_signable_string`, or cross-check `request.shop` against an out-of-band trusted source (such as a previously stored session for that shop combined with a nonce/webhook id uniqueness check) before dispatching to handlers. At minimum, document prominently that `shop` in `WebhookMetadata` is not covered by the HMAC and must not be trusted for tenant selection without additional verification.

### Proof of Concept
1. Install the target Shopify app on attacker-controlled store `attacker.myshopify.com`.
2. Receive a real webhook, e.g. `orders/create`, with headers:
   ```
   X-Shopify-Topic: orders/create
   X-Shopify-Hmac-Sha256: <valid-signature-of-raw-body>
   X-Shopify-Shop-Domain: attacker.myshopify.com
   ```
3. Resend the identical raw body and `X-Shopify-Hmac-Sha256` value to the same endpoint, but set:
   ```
   X-Shopify-Shop-Domain: victim.myshopify.com
   ```
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` which returns `true` (per `lib/shopify_api/webhooks/request.rb` L35-38 and `lib/shopify_api/utils/hmac_validator.rb` L26-31, since only the body is checked), then dispatches `handler.handle(data: WebhookMetadata.new(..., shop: "victim.myshopify.com", ...))` (`lib/shopify_api/webhooks/registry.rb` L188-200), causing the host app to process attacker-supplied data under the victim's tenant identity.
