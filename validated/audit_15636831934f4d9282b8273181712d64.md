### Title
Missing domain/session binding in enrollment signature allows replay of a valid signature across different signup sessions - (File: `src/plans/enroll_user.rs`)

### Summary
The `make_signature` function in `src/plans/enroll_user.rs` computes a SHA-256 digest over `ORB_ID`, the user QR code's `user_id`, and pipeline/iris code fields, then signs it via the Secure Element. This digest never includes the `signup_id`, a timestamp, or any nonce, so the resulting signature is not bound to a specific signup attempt. A signature computed for one signup session is therefore valid input for any other request carrying the same `(orbId, userId, codes)` tuple, mirroring the reported "missing domain separator" issue where a signed artifact lacks the context (chain ID / session ID) needed to scope it to one specific transaction.

### Finding Description
`make_signature` builds its digest from a fixed set of fields: [1](#0-0) 

Note that `self.signup_id` — the unique identifier generated for each enrollment attempt and used as the URL path parameter in the signup POST — is never included in the signed material: [2](#0-1) 

The signature and the `signup_id` are then submitted independently: `signup_id` goes into the URL path, while `signature` goes into a form field, and the backend receives them as two separately-controlled values with no cryptographic link between them: [3](#0-2) 

Because the digest is deterministic over `(ORB_ID, userId, ir_net_version, iris_version, iris_code, mask_code, iris_code_version)` only, any two signup attempts that reuse the same orb, same user QR code, and same pipeline output (a realistic occurrence — e.g. a retried enrollment, a re-presented QR code, or backend-side retry/duplicate handling) will produce an identical signature. This signature can then be paired with a *different* `signup_id` in the POST body/path without failing verification, since nothing in the signed payload ties it to one specific signup transaction — the same root cause described in the report: a signed artifact that omits the context needed to scope it to exactly one intended operation.

### Impact Explanation
If the backend relies on this signature as proof that the Secure Element attested a specific enrollment event, the missing session binding allows the same signed proof to be replayed and associated with a different `signup_id`. This enables cross-signup state bleed: a captured or retried `(signature, codes, userId, orbId)` tuple can be resubmitted against a new signup attempt, potentially letting the backend accept a signup as validly attested when it was not freshly attested for that specific attempt. This weakens the enrollment integrity guarantee the Secure Element signature is meant to provide.

### Likelihood Explanation
The `RETRIES_COUNT` retry loop in `Plan::run` already produces this exact scenario organically — up to 3 signup POST attempts reuse the identical precomputed `signature` value: [4](#0-3) 
Beyond built-in retries, any actor able to observe/replay the outgoing multipart form (e.g. via debugging, logging, or a compromised transport) can reuse the signature with an alternate `signup_id`, since nothing in the signed digest constrains it to one attempt. No privileged access to the Secure Element or signing key is required — only knowledge of a previously-issued signature value and the ability to submit a new signup request.

### Recommendation
Include `signup_id` (and ideally a monotonic counter/timestamp) inside the digest computed in `make_signature`, so each signature is cryptographically bound to exactly one signup attempt: [5](#0-4) 
This mirrors the reported fix pattern of embedding a scoping/domain value (there: chain ID; here: signup/session ID) directly in the signed material so it cannot be replayed outside its intended context.

### Proof of Concept
1. Perform enrollment `Plan::run` for `signup_id = A` with a given `user_qr_code` and `pipeline` output; `make_signature` computes `sig = Sign(SHA256(orbId || userId || codes...))`.
2. The signup POST to `.../api/v2/signups/A` fails or is retried (or an attacker captures the multipart body from a log/proxy).
3. Re-issue a POST to `.../api/v2/signups/B` (a different `signup_id`) reusing the same `signature`, `userId`, and `codes` fields — the signature verifies successfully because it was never bound to `A` in the first place, since the digest inputs (`ORB_ID`, `user_id`, pipeline/iris fields) are identical to signup `A`.
4. The backend accepts a signed attestation for enrollment `B` that was never freshly generated for that attempt, demonstrating the replay/cross-session binding weakness.

fn make_signature(user_qr_code: &qr_scan::user::Data, pipeline: &Pipeline) -> Result<String> {
    let mut ctx = Context::new(&SHA256);
    ctx.update(ORB_ID.as_str().as_bytes());
    ctx.update(user_qr_code.user_id.as_bytes());
    ctx.update(pipeline.v2.ir_net_version.as_bytes());
    ctx.update(pipeline.v2.iris_version.as_bytes());
    ctx.update(pipeline.v2.eye_left.iris_code.as_bytes());
    ctx.update(pipeline.v2.eye_left.mask_code.as_bytes());
    ctx.update(pipeline.v2.eye_left.iris_code_version.as_bytes());
    ctx.update(pipeline.v2.eye_right.iris_code.as_bytes());
    ctx.update(pipeline.v2.eye_right.mask_code.as_bytes());
    ctx.update(pipeline.v2.eye_right.iris_code_version.as_bytes());
    let signed = secure_element::sign(ctx.finish())?;
    Ok(BASE64.encode(&signed))
}
