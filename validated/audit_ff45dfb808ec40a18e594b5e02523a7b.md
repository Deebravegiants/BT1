### Title
Livestream downstream frame buffer is not cleared on new TCP connection, causing prior signup's biometric camera frames to be streamed to a new viewer - ([File: src/agents/livestream/mod.rs])

### Summary
`Agent::run` in `src/agents/livestream/mod.rs` maintains a single, long-lived `Gpu` texture/state object that is only cleared on `Input::Clear` or agent startup, never on `Event::Connected`. Because `port.poll_next_unpin` is polled before `upstream.poll_next_unpin` on every iteration of the `poll_fn` [1](#0-0) , any `Input::IrEyeFrame`/`IrFaceFrame`/etc. already queued for the previous signup will be drained into `gpu` *before* a queued `Event::Connected` for a new client is processed, and there is no reset of that GPU state at connection time [2](#0-1) .

### Finding Description
The event loop alternates between draining `Input` frames from `port` (rendered into persistent `gpu` textures/app state) and `Event`s from `upstream` (connection lifecycle) [1](#0-0) . On `Event::Connected`, the code only creates a new `Downstream` and starts pushing subsequent `gpu.render` output to it - it does **not** call `gpu.clear_textures()`/`gpu.app.clear()` [3](#0-2) . Clearing only happens explicitly via `Input::Clear`, which is sent from `Session::start_signup` at the very beginning of a new signup, gated behind `#[cfg(feature = "livestream")]` [4](#0-3) .

This creates a race: if a burst of `Input::IrEyeFrame`/`IrFaceFrame`/`RgbFrame` frames for signup A is already enqueued on `port` when a new TCP client B connects (`Event::Connected` arrives concurrently on `upstream`), the deterministic check order in the `poll_fn` (`port` checked first, `upstream` second) means those frames get rendered into the shared `gpu` texture state first [5](#0-4) . Once `Event::Connected` is subsequently processed and `downstream = Some(...)` is set, the *next* render call (triggered by any later `Input` or `Event::UiEvents`) will push the **already-updated GPU texture state containing A's frames** to B's freshly created `Downstream` [6](#0-5) . There is no per-connection reset tying GPU state to the currently connected client's identity - the `Input::Clear` sent at `start_signup` protects against stale data from a *finished* signup only if it is processed before B connects, but it does nothing to prevent A's in-flight, already-queued frames captured during the same window from bleeding into the new connection.

### Impact Explanation
This is a biometric data disclosure across signup sessions: raw IR/RGB eye/face camera frames captured for signup A can be streamed over the network (TCP port 9201) to a distinct connecting client B who has not been authenticated/scanned as that user. This directly violates the session-isolation invariant (capture state must be fully reset between users) and matches the "biometric data disclosure" / cross-signup state bleed impact category.

### Likelihood Explanation
The livestream feature is gated by the `livestream` Cargo feature, which is included transitively via the `stage` feature, itself in the crate's `default` feature set (`default = ["v2_x_x", "stage"]`) [7](#0-6) , so it may be compiled into standard/staging builds rather than being a fully isolated debug-only binary. However, the TCP listener binds `0.0.0.0:9201` [8](#0-7) , meaning any attacker able to reach that port on the orb's network can exploit the race by connecting at the moment frames are queued. Exploitability depends on precise timing (attacker must connect while a burst of frames for another signup is in-flight in the `port` queue and before the next `Input::Clear`), which is plausible given `INPUT_CAPACITY: 0` back-pressure semantics of the port but requires network access and timing control that is feasible for a networked attacker, not merely theoretical.

### Recommendation
Clear `gpu` textures/app state (`gpu.clear_textures(); gpu.app.clear();`) immediately upon handling `Event::Connected`, before setting `downstream = Some(...)`, so a newly connected client never receives frames rendered from data queued prior to its connection. Additionally, consider draining/discarding any already-buffered `Input` frames in `port` at connection time (or tagging frames with the signup/session id and dropping frames not belonging to the currently active session) rather than relying solely on `Input::Clear` sent at `start_signup`, since that message does not account for frames enqueued but not yet processed concurrently with a new connection.

### Proof of Concept
Integration test plan (using the existing `Agent`/`port::Inner`/`Upstream`/`Downstream` test scaffolding, or a targeted refactor exposing `gpu` state for inspection):
1. Start the `Agent` thread with a mock `port` and a mock `Upstream` that allows manual `Event` injection and manual `Input` queuing.
2. Enqueue several `Input::IrEyeFrame(frame_A)` for "signup A" into the `port` input queue without letting the loop drain them yet (simulate backlog).
3. Immediately emit `Event::Connected(addr_B)` on the mock `upstream`, simulating attacker B's connection arriving while A's frames are still queued.
4. Let the event loop run: assert that `port.poll_next_unpin` is checked before `upstream.poll_next_unpin` per iteration order in the code, confirming A's frames are rendered into `gpu` before `Event::Connected` is handled.
5. After `Downstream` for B is created, trigger any subsequent render (e.g., an empty `Input::Phase` update) and capture what is pushed to B's `Downstream` buffer via a mock/fake `Downstream::push`.
6. Assert that the pushed buffer contains rendered content derived from `frame_A` (e.g., by checking `gpu.app`/texture state fingerprint), demonstrating that biometric frames captured for signup A reached B's downstream connection despite no explicit authorization or scan association between A and B.
