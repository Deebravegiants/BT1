## Title
Stale `yield_timeout_length_in_blocks` parameter changes break the PromiseYield timeout queue's expiry-ordering invariant, delaying promise resolution - (File: `runtime/runtime/src/lib.rs`)

### Summary
The `PromiseYieldTimeout` queue is a FIFO trie-backed queue that the runtime explicitly assumes is ordered by `expires_at` (push order == expiry order). Each entry's `expires_at` is computed at creation time as `apply_state.block_height + config.wasm_config.limit_config.yield_timeout_length_in_blocks`. Because `yield_timeout_length_in_blocks` is a `RuntimeConfig`/`LimitConfig` parameter that can change across protocol versions, a decrease in this parameter can produce a later-pushed entry with a smaller `expires_at` than an earlier-pushed entry still sitting in front of it in the queue — exactly the class of bug described in the report (a mutable duration parameter invalidating a FIFO-by-expiry queue assumption).

### Finding Description
When a contract calls `promise_yield_create`, the runtime enqueues a timeout entry via `enqueue_promise_yield_timeout`, computing the expiry as: [1](#0-0) 

This value is appended to the back of the persistent `PromiseYieldTimeout` FIFO queue keyed by monotonically increasing `next_available_index`: [2](#0-1) 

The consumer, `resolve_promise_yield_timeouts`, explicitly relies on the invariant "Queue entries are ordered by expires_at" and stops draining the queue as soon as it hits the *first* (oldest-pushed) entry whose `expires_at` is still in the future: [3](#0-2) 

The invariant "entries are ordered by expires_at" only holds if `yield_timeout_length_in_blocks` is constant. If a protocol upgrade reduces this parameter, an entry `A` created at height `h1` under the old (larger) value has `expires_at = h1 + T_old`, while an entry `B` created later at height `h2 > h1` under the new (smaller) value can have `expires_at = h2 + T_new < h1 + T_old`. Since `B` is pushed after `A`, it sits behind `A` in the FIFO queue. The loop in `resolve_promise_yield_timeouts` will not reach `B` until `A` (and everything else ahead of it) has been popped, even though `B` has already logically expired.

### Impact Explanation
The effect mirrors the referenced report's DoS: a promise created via `promise_yield_create` that should time out (resolve with `PromiseResult::Failed`/`data: None`) after `yield_timeout_length_in_blocks` can instead remain unresolved for up to as long as it takes for all older, longer-timeout entries queued ahead of it to be drained. This delays finalization of the corresponding transaction/receipt chain and can hold the parked `PromiseYield` receipt (and its already-prepaid gas/deposit) in state longer than the protocol-documented bound, which contracts and callers rely on for liveness guarantees (`runtime/near-vm-runner/src/logic/logic.rs` doc: "the created promise will instead be executed... after a certain protocol-defined number of blocks"). This is a liveness/availability degradation of the yield-resume mechanism reachable purely by an unprivileged contract call plus a routine protocol-parameter change, not by any privileged or validator-only action at the exploitation layer.

### Likelihood Explanation
Likelihood is low-to-moderate: it requires two things to occur together — (1) the network votes in a protocol upgrade that reduces `yield_timeout_length_in_blocks`, and (2) at that moment there exist queued `PromiseYield` timeouts created under the previous (larger) value that have not yet expired, with new-value entries queued behind them. Parameter changes across protocol versions do occur in nearcore's history (this and other `LimitConfig`/`RuntimeConfig` fields are versioned per protocol version in `core/parameters/res/runtime_configs/parameters.yaml` and change over time), so the precondition is plausible during a future upgrade, though it has not necessarily happened yet for this specific parameter. Unlike the original Cosmos report, the effect is bounded and self-healing (once the blocking older entries drain, the queue proceeds normally), not a full DoS of the mechanism.

### Recommendation
Change `resolve_promise_yield_timeouts` to not assume strict `expires_at` monotonicity across the queue: instead of breaking at the first not-yet-expired entry, either (a) recompute/store a per-entry deadline that is invariant to later config changes (e.g., freeze the timeout length used per entry, which is already done — the problem is the *queue draining* logic, not the stored value), or (b) scan past not-yet-expired entries (bounded by the compute/proof-size budget already enforced) rather than stopping at the first miss, mirroring the report's suggested fix of using `continue` instead of `break`. Any change must preserve determinism and be gated behind a protocol feature/version to avoid a consensus-breaking behavior change.

### Proof of Concept
1. At protocol version `N`, `yield_timeout_length_in_blocks = T_old` (large). A contract calls `promise_yield_create` at block height `h1`, producing timeout entry `A` with `expires_at = h1 + T_old`, pushed to the back of the `PromiseYieldTimeout` queue (`function_call.rs:162-169`, `core/store/src/utils/mod.rs:181-198`).
2. A protocol upgrade to version `N+1` reduces `yield_timeout_length_in_blocks` to `T_new` such that `T_new < T_old`.
3. Another contract call at block height `h2` (with `h1 < h2`, `A` not yet expired) creates entry `B` with `expires_at = h2 + T_new`, chosen such that `h2 + T_new < h1 + T_old`. `B` is pushed behind `A` in the FIFO queue.
4. Once `apply_state.block_height` passes `B`'s `expires_at` but is still below `A`'s `expires_at`, `resolve_promise_yield_timeouts` reads `A` (front of queue, `promise_yield_indices.first_index`), sees `A.expires_at > block_height`, and `break`s (`runtime/runtime/src/lib.rs:3041-3044`) — `B`'s already-expired timeout is never processed until `A` is dequeued, delaying `B`'s promise resolution beyond the documented `yield_timeout_length_in_blocks` bound.

// Enqueues given timeout to the PromiseYield timeout queue
pub fn enqueue_promise_yield_timeout(
    state_update: &mut TrieUpdate,
    promise_yield_indices: &mut PromiseYieldIndices,
    account_id: AccountId,
    data_id: CryptoHash,
    expires_at: BlockHeight,
) {
    set(
        state_update,
        TrieKey::PromiseYieldTimeout { index: promise_yield_indices.next_available_index },
        &PromiseYieldTimeout { account_id, data_id, expires_at },
    );
    promise_yield_indices.next_available_index = promise_yield_indices
        .next_available_index
        .checked_add(1)
        .expect("Next available index for PromiseYield timeout queue exceeded the integer limit");
}
