### Title
Webhook `shop-domain`, `topic`, and `webhook-id` headers are trusted by handlers without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from only the raw request body, while the `shop`, `topic`, `api_version`, and `webhook_id` values consumed by `Registry.process` and delivered to app handlers are read directly from HTTP headers that are never included in that signable string. An attacker who possesses one valid `(raw_body, hmac)` pair for a webhook (e.g., a webhook Shopify delivered for their own store) can replay that exact body/HMAC to the host application's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a different (victim) shop. The HMAC check still passes because it only verifies the body bytes, so the app's handler executes believing the event belongs to the victim shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, `#api_version`, and `#webhook_id` are all read straight from attacker-controlled headers, with no cryptographic binding to the signed body: [2](#0-1) 

`Registry.process` validates only the HMAC over the body via `Utils::HmacValidator.validate(request)`, then immediately trusts `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` when constructing `WebhookMetadata` for the handler: [3](#0-2) 

`HmacValidator.validate_signature` only proves that `to_signable_string` (the raw body) was signed with the secret — it says nothing about which shop, topic, or webhook id the caller is claiming: [4](#0-3) 

This is the exact class of bug in the report: a value the application acts on (`shop`, used as the tenant identity for handler logic) is not covered by the integrity check (`hmac`, which binds only the body). The equality that should hold — "the shop verified by the HMAC == the shop the handler believes it received data for" — does not hold, because the HMAC verifies zero shop information at all.

### Impact Explanation
This breaks the tenant-identity binding relied on by every host application built on this gem's webhook mechanism (`WebhookHandler#handle(data:)` receives `WebhookMetadata.shop` as the trusted tenant key). An attacker who owns/operates any shop with an app installed (a fully unprivileged, non-Shopify-employee actor) can capture one legitimate signed webhook payload from Shopify and replay it against the app's webhook endpoint with a forged `shop-domain` header pointing at an arbitrary victim shop, and the app will process/store/act on that data as if it originated from the victim tenant. Depending on the handler's logic (e.g., updating per-shop state, triggering fulfillment, redact/GDPR handlers, billing, etc.), this can lead to cross-tenant data corruption or disclosure — classified as Critical (cross-tenant access) under the given severity rubric.

### Likelihood Explanation
Low-to-moderate likelihood in practice, but concretely exploitable: the attacker needs one authentic `(body, hmac)` pair, which is trivially obtainable by installing the target app on their own store (any developer/merchant account) and capturing the webhook Shopify sends them. No access token, `client_secret`, or privileged access is required — only a normal, unprivileged merchant/developer account and network access to the app's public webhook endpoint.

### Recommendation
Bind the trusted routing metadata (`shop`, `topic`, `webhook_id`, `api_version`) into the HMAC-verified signable content, or otherwise cryptographically tie the header values to the signed body (e.g., verify the shop domain against a known/allow-listed set of installed shops before trusting `WebhookMetadata.shop`, or require Shopify's webhook delivery to sign the headers themselves). At minimum, document clearly that the HMAC only proves body integrity and that consumers must independently authenticate the `shop` value against their own installation records before trusting it as a tenant key.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; trigger any webhook topic the app subscribes to (e.g., `orders/create`).
2. Capture the raw POST body and the `X-Shopify-Hmac-Sha256` header Shopify sent for that delivery — this `(body, hmac)` pair is valid because it was legitimately signed by Shopify for the attacker's own shop.
3. Replay the exact same body and HMAC header to the app's webhook endpoint, but override `X-Shopify-Shop-Domain` to `victim.myshopify.com` (and optionally alter `X-Shopify-Webhook-Id`, which is also unauthenticated).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` [5](#0-4)  which succeeds because the body/HMAC pair is genuinely valid.
5. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", ...)` [6](#0-5)  and processes the attacker's data as if it belongs to the victim tenant.
