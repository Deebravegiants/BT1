### Title
Webhook `shop`, `topic`, `webhook_id`, and `api_version` Fields Are Not Covered by HMAC Verification, Enabling Cross-Tenant Webhook Forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC of the raw request body, but the `shop`, `topic`, `webhook_id`, and `api_version` values that are trusted and handed to the app's handler come from HTTP headers that are never included in the signed payload. An attacker who possesses one validly-signed webhook body (e.g., from their own shop's legitimate webhook delivery) can replay it with a modified `shop-domain`/`topic` header and have it pass HMAC validation while being attributed to an arbitrary shop or topic.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes the signature purely from `to_signable_string` (the raw body) and compares it to the `hmac` header: [2](#0-1) 

`Registry.process` only checks this body-derived HMAC, then immediately trusts the `shop`, `topic`, `webhook_id`, and `api_version` values parsed straight from unauthenticated headers, and forwards them to the app's registered handler: [3](#0-2) 

Those values are extracted from headers with no cryptographic binding to the HMAC at all: [4](#0-3) 

The identity binding broken is: `HMAC(raw_body) == received_hmac` is treated as proof that `(shop, topic, webhook_id, api_version)` are also authentic, when in fact only `raw_body` is covered by the signature. Any attacker in possession of one legitimately-signed webhook body/HMAC pair (trivially obtainable by installing the app on their own shop and receiving a real webhook) can resubmit that exact body+HMAC to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header value and/or `shopify-topic` header value. `HmacValidator.validate` will still return `true` because it never inspects those headers, and `Registry.process` will dispatch to the handler with `WebhookMetadata.shop` and `WebhookMetadata.topic` set to attacker-chosen values, even though the body content did not actually originate for that shop/topic.

### Impact Explanation
This breaks the cross-tenant isolation the gem is supposed to guarantee for webhook consumers: a host application that keys business logic (e.g., which merchant's data to update, which session/access token to use, or which mandatory-topic action like GDPR redact to perform) off `WebhookMetadata.shop`/`topic` can be made to act on the wrong tenant's data using an attacker-controlled shop identifier, despite HMAC verification "passing." This is a cross-tenant access vector introduced by the gem's own trust model rather than by host misuse of documented behavior, since the gem documents/exposes `shop`/`topic` as verified fields of a webhook whose authenticity is established by `HmacValidator.validate`.

### Likelihood Explanation
Exploitation requires only that the attacker be able to receive at least one legitimately-signed webhook body (trivial for anyone who can install the target app on a shop they control, or capture one delivery) and then replay it to the app's webhook endpoint with modified headers. No access token, `api_secret_key`, or privileged credential is needed — only the ability to send HTTP requests to the app's public webhook receiver, which is by design internet-reachable.

### Recommendation
Include the security-relevant headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signable string used for HMAC computation, or otherwise cryptographically bind them to the body's signature, so that `HmacValidator.validate` can only succeed if the entire tuple of `(body, shop, topic, webhook_id, api_version)` matches what Shopify actually signed. At minimum, document clearly that only the raw body is authenticated and that `shop`/`topic`/`webhook_id`/`api_version` must not be trusted for authorization decisions without additional verification (e.g., cross-checking `shop` against a known/installed shop list before processing).

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; capture one legitimate webhook POST, e.g. body `{}` with headers `x-shopify-hmac-sha256: <valid HMAC of "{}">`, `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-topic: orders/create`.
2. Replay the same raw body and the same (still-valid, since body unchanged) `x-shopify-hmac-sha256` value to the app's webhook endpoint, but set `x-shopify-shop-domain: victim.myshopify.com` (and/or a different `x-shopify-topic`).
3. `ShopifyAPI::Webhooks::Request.new` accepts the headers, and `Utils::HmacValidator.validate(request)` returns `true` because it only recomputes the HMAC over `raw_body`, as shown in: [5](#0-4) 
4. `Registry.process` dispatches to the registered handler with `WebhookMetadata.shop == "victim.myshopify.com"` even though Shopify never signed a webhook claiming to be for `victim.myshopify.com`, giving the attacker control over the shop identity attributed to a cryptographically "verified" webhook.
