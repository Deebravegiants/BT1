### Title
Relayer fee `withdraw`/`accumulate` signatures omit a Hyperbridge-instance identifier, enabling cross-deployment signature replay - (File: modules/pallets/relayer/src/withdrawal.rs)

### Summary
`pallet-relayer`'s `withdraw` and `accumulate` extrinsics authenticate a relayer's beneficiary/withdrawal instructions with a raw signature over `(nonce, dest_chain, beneficiary)`. This payload contains no data identifying *which* Hyperbridge deployment (source chain / genesis / pallet instance) is verifying it — only the ISMP `dest_chain` the payout targets. Because relayers run the identical keys and identical pallet code across multiple independent Hyperbridge instances (e.g. testnet vs. mainnet, or separate parachains each running `pallet-relayer`), a signature captured from one deployment can be replayed verbatim on another deployment whenever `(nonce, dest_chain)` coincide, exactly mirroring the Futureswap `instantWithdraw` finding where the signed struct lacked any Futureswap-specific data.

### Finding Description
`message()` (withdrawal path) and `beneficiary_message()` (accumulate path) construct the signed digest as: [1](#0-0) [2](#0-1) 

Both digests bind only to the per-relayer `nonce` (stored keyed by `(address, dest_chain)` in this pallet's own storage), the destination state machine the payout is routed to, and the beneficiary bytes. Verification in `withdraw()` and `accumulate()` recovers the signer and checks it against the on-chain relayer address, but never checks anything that identifies the local Hyperbridge instance itself (no genesis hash, no `host_state_machine()`/source-chain identifier, no pallet/runtime instance tag): [3](#0-2) [4](#0-3) 

The existing regression test in the testsuite only proves that a signature signed for a *different `dest_chain`* value is rejected (because `dest_chain` is part of the hash) — it does not, and cannot, protect against replay across two different Hyperbridge deployments that happen to route to the *same* `dest_chain` with the *same* relayer nonce, since nothing in the signed bytes distinguishes the deployments: [5](#0-4) 

This is structurally identical to the reported Futureswap bug: the signed struct is "generic enough" (chain-scoped state variables only) to be valid across multiple independent verifying systems that share the same signature scheme, rather than being scoped to "this specific instance."

### Impact Explanation
A relayer that operates the same signing key across two or more Hyperbridge deployments (a common operational pattern — the same infrastructure/keys serving mainnet and a sibling deployment, or two chains that both embed `pallet-relayer`) can have a `beneficiary_details` signature or a `withdraw` signature — visible on-chain once submitted via the unsigned `accumulate`/`withdraw` extrinsics — captured and replayed on a second deployment where the relayer's nonce for that `dest_chain` happens to match. The replay:
- Advances that relayer's nonce out of sync with their own bookkeeping (denial-of-service on future legitimate withdrawals/redirects until they notice and re-sign), and
- Silently redirects/withdraws the relayer's fee balance on the second deployment to a beneficiary address that was chosen for a different chain's context (potential fund misdirection to an address the relayer didn't intend for that deployment).

This lands squarely in the explicitly in-scope category "relayer fee and reward accounting," and constitutes a griefing / fund-misdirection vector consistent with a Medium severity finding.

### Likelihood Explanation
Requires that a relayer reuse the same private key across multiple Hyperbridge deployments and that the deployments' independent nonce counters for that relayer/`dest_chain` pair coincide (nonces start at 0 and increment per successful call, so collisions are especially likely early in a relayer's lifetime on each deployment, or can be engineered by an attacker submitting decoy withdrawals to advance/align counters). No privileged access is needed — `accumulate` and `withdraw` are reachable by any relayer/unsigned-origin caller, and the signature bytes are public once broadcast on the source deployment.

### Recommendation
Include a Hyperbridge-instance-specific value in the signed payload of both `message()` and `beneficiary_message()` — e.g. `host.host_state_machine()` (the local chain's own StateMachine identifier) and/or the genesis hash — so a signature is cryptographically bound to the specific Hyperbridge deployment it was created for, mirroring the fix applied for the analogous Futureswap issue (binding the signature to the verifying `Registry` contract address).

### Proof of Concept
1. Relayer `R` operates on Hyperbridge deployment `A` and deployment `B` using the same EVM key.
2. On deployment `A`, `R` submits `accumulate` with `beneficiary_details = (beneficiary_X, sig)` where `sig = sign(beneficiary_message(nonce=0, dest_chain=EVM-1, beneficiary_X))`, redirecting `A`'s fee accrual to `beneficiary_X`.
3. An observer extracts `sig` from `A`'s on-chain transaction.
4. On deployment `B`, `R`'s nonce for `dest_chain=EVM-1` is also `0` (fresh relayer on `B`). The observer submits `accumulate` on `B` reusing `sig` with the same `beneficiary_details`.
5. `beneficiary_message(0, EVM-1, beneficiary_X)` matches exactly on `B`; `signature.verify` succeeds because nothing in the digest differs between deployments `A` and `B`.
6. `B`'s fee balance for `R` is redirected to `beneficiary_X` and `R`'s nonce on `B` is incremented — without `R` ever having authorized this action on deployment `B`.

/// Signed payload for [`WithdrawalInputData`]. Includes the per-relayer nonce so a captured
/// signature cannot be replayed.
pub fn message(nonce: u64, dest_chain: StateMachine, beneficiary: Option<Vec<u8>>) -> [u8; 32] {
	if let Some(beneficiary) = beneficiary {
		return sp_io::hashing::keccak_256(&(nonce, dest_chain, beneficiary).encode());
	}
	sp_io::hashing::keccak_256(&(nonce, dest_chain).encode())

/// Signed payload authorising a beneficiary redirect on a specific source chain.
/// Including the relayer nonce alongside the state machine keeps the signature usable for
/// exactly one accumulate call on that chain, mirroring how `withdraw_fees` binds its signed

	nonce: u64,
	state_machine: StateMachine,
	beneficiary: &[u8],

	sp_io::hashing::keccak_256(&(nonce, state_machine, beneficiary).encode())
