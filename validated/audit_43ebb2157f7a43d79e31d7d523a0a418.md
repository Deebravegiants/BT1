## Analysis

The report's bug class is a **broken identity binding due to incomplete coverage of the integrity check** — a value is trusted and acted upon (the "shop") without being cryptographically bound to the signature that supposedly authenticates the request. The strongest analog in this gem is in the webhook HMAC verification path.

`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body: [1](#0-0) 

but `shop` (and `topic`) are read directly from unauthenticated HTTP headers, entirely outside the signed content: [2](#0-1) 

`Utils::HmacValidator.validate` only checks that `HMAC(api_secret_key, raw_body)` matches the `hmac` header — it never binds `shop` or `topic` into the signed message: [3](#0-2) 

`Registry.process` accepts the request once that body-only HMAC validates, then dispatches the handler using the unauthenticated `request.shop` and `request.topic` as the tenant identity for the event: [4](#0-3) 

### Title
Cross-tenant webhook spoofing via shop-domain header not covered by HMAC - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
The gem's webhook signature verification computes the HMAC exclusively over the raw request body (`to_signable_string == @raw_body`), while the "shop" identity (and topic) used to attribute the webhook event to a tenant is taken from HTTP headers that are never included in the signed content. Since the API's `client_secret` is a single global value shared by an app across every installed shop (not per-tenant), any legitimate merchant who installs the app on their own store can capture one valid `(raw_body, hmac)` pair from a real webhook Shopify sends them, and then replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header. `HmacValidator.validate` will still pass (the body and secret are unchanged), and `Registry.process` will hand the attacker-authored payload to the app's handler tagged with the victim's `shop` value.

### Finding Description
This breaks the equality that should hold: `shop authenticated by HMAC == shop attributed to the event`. In reality, the signature proves only "this body byte string was produced under the app's `client_secret`" — it says nothing about which shop the header claims it is for. `WebhookMetadata` is built directly from `request.shop`/`request.topic`, both unauthenticated: [5](#0-4) 
Because the `client_secret` is shared across all shops that install the app (it is not shop-specific), an attacker does not need the secret at all — they only need to be a legitimate installer of the app on a store they control to obtain one valid signed body, then can relabel it as belonging to any victim shop.

### Impact Explanation
This is a cross-tenant integrity violation (Critical): an unprivileged internet user who is simply a normal merchant installing the target app can forge webhook events that the host application will process as coming from an arbitrary victim shop domain (which need not even be a real, installed shop). Depending on how the host application's webhook handlers act on `WebhookMetadata#shop` (e.g., `app/uninstalled`, `shop/redact`, order/customer data ingestion keyed by shop), this can be used to corrupt or inject data attributed to another tenant, or trigger tenant-lifecycle actions (like uninstall/redact processing) for a shop the attacker does not control.

### Likelihood Explanation
High. No secrets, tokens, or privileged access are required — only the ability to install the app on any shop (trivial for anyone, including on a free Shopify dev/partner store) to obtain one legitimately signed webhook body/HMAC pair, and the ability to send an HTTP request to the app's public webhook endpoint with a forged `X-Shopify-Shop-Domain` header.

### Recommendation
Bind the shop (and topic) into the signed content check, or otherwise cryptographically tie the webhook's claimed shop to a value that cannot be replayed cross-tenant — e.g., verify `request.shop` against the shop's known session/access-token before trusting `WebhookMetadata#shop`, or require the host application to cross-check the header-derived shop against its own store of installed shops rather than trusting it purely because the body-only HMAC validated.

### Proof of Concept
1. Attacker installs the target Shopify app on their own (attacker-controlled) shop `attacker.myshopify.com` and lets Shopify deliver a real webhook, e.g. for a topic whose body is minimal/predictable (or attacker-controlled, such as a webhook triggered by attacker's own store data).
2. Attacker captures the raw request body and the `X-Shopify-Hmac-Sha256` header from that legitimate delivery.
3. Attacker sends a new POST request to the app's webhook endpoint with the identical captured body and HMAC header, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` in `lib/shopify_api/webhooks/registry.rb` returns `true` because it only validates `HMAC(api_secret_key, raw_body)`, which is unchanged.
5. `Registry.process` invokes the registered handler with `WebhookMetadata.new(topic: request.topic, shop: "victim-shop.myshopify.com", body: request.parsed_body, ...)`, causing the app to act on attacker-controlled data as if it belonged to the victim shop.

          received_signature = verifiable_query.hmac
