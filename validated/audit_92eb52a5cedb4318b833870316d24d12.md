Based on my investigation, I've confirmed the core vulnerability: `ShopifyAPI::Webhooks::Request#to_signable_string` (used by `HmacValidator.validate`) only covers the raw request body, while `Request#shop`, `#topic`, and `#webhook_id` are read directly from unauthenticated HTTP headers and passed unchecked into the handler via `Registry.process`.

### Title
Webhook shop-domain/topic identity spoofing via HMAC that only covers the body, not headers - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` exposes `shop`, `topic`, and `webhook_id` from HTTP headers (`x-shopify-shop-domain`, `x-shopify-topic`, `x-shopify-webhook-id`), but its `to_signable_string` — the value HMAC-verified by `Utils::HmacValidator.validate` — returns only `@raw_body`. `Registry.process` verifies the HMAC and then trusts `request.shop`/`request.topic` to build `WebhookMetadata` passed to the app's handler, without those fields ever being covered by the signature.

### Finding Description
The identity binding that should hold is: `shop header used to attribute a webhook == shop the HMAC signature actually authenticates`. In this gem that equality does not hold.

- `Request#to_signable_string` returns `@raw_body` only: [1](#0-0) 
- `Request#shop`, `#topic`, `#webhook_id` are parsed straight from headers with no cross-check against the signed content: [2](#0-1) 
- `HmacValidator.validate` computes/compares the signature over exactly `to_signable_string`: [3](#0-2) 
- `Registry.process` validates only that HMAC, then immediately forwards `request.shop` and `request.topic` — unauthenticated header values — to the handler: [4](#0-3) 

Because the `api_secret_key` used for HMAC is the app's single client secret shared across every shop that installs the app (not a per-shop secret), any unprivileged user who can install the app on their own shop can obtain a legitimately-signed `(raw_body, hmac)` pair from a real webhook delivery. They can then replay that exact body+HMAC directly to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` header (and/or `x-shopify-topic`) with a different, victim shop's domain. `HmacValidator.validate` still succeeds because it only checks the body, and `Registry.process` hands the handler a `WebhookMetadata` claiming the data belongs to the victim shop.

### Impact Explanation
This breaks the shop-identity binding the gem is supposed to guarantee for webhook authenticity, enabling cross-tenant data confusion/injection: an attacker-controlled payload (from their own shop) can be attributed to an arbitrary victim shop domain in the app's webhook handler. Depending on how the host app uses `WebhookMetadata#shop` (e.g., looking up/mutating per-shop records, honoring GDPR `customers/redact`/`shop/redact` mandatory topics, or feeding into per-tenant business logic), this can lead to cross-tenant data corruption or unauthorized actions being recorded against a shop the attacker doesn't control.

### Likelihood Explanation
Requires only an unprivileged Shopify Partner account able to install the app on an attacker-owned development/trial shop and to send arbitrary HTTP requests to the app's public webhook endpoint — no access token, secret, or privileged relationship with the victim shop is needed.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the HMAC-signable content (or otherwise cryptographically bind them to the verified body), or at minimum require the host application to independently authenticate/authorize the shop before trusting `WebhookMetadata#shop` for any per-tenant action, and document this gap prominently since `Request#to_signable_string` currently silently ignores all headers.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a webhook (e.g. `orders/create`) so Shopify sends a legitimately HMAC-signed request with body `raw_body` and header `x-shopify-hmac-sha256: H`.
2. Attacker captures `(raw_body, H)`.
3. Attacker POSTs directly to the app's webhook endpoint with the same `raw_body` and `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` and any desired `x-shopify-topic`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `request.to_signable_string` (== `raw_body`) using the app's single `api_secret_key`; it matches `H`, so validation passes: [5](#0-4) 
5. The handler receives `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` with `shop == "victim-shop.myshopify.com"`, despite the payload originating from the attacker's own shop.
