Based on my investigation, I've confirmed the vulnerability: the `shop` field passed to webhook handlers is not covered by the HMAC signature, and the HMAC secret is not shop-specific.

### Title
Webhook `shop` domain field is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by verifying that the HMAC of the raw request body matches a signature computed with the app's `api_secret_key`. However, the `shop` identity that is handed to the app's `WebhookHandler` (and that apps use to scope tenant data) is read from an HTTP header that is **not** part of the signed content, so any request with a valid body/HMAC pair can carry an attacker-chosen shop value.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`. Its `to_signable_string` returns only `@raw_body`, and its `hmac` reader decodes the `hmac-sha256` header: [1](#0-0) 

`shop` is read independently from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is never included in `to_signable_string`: [2](#0-1) 

`Registry.process` validates the request purely via `Utils::HmacValidator.validate(request)`, i.e. it recomputes `HMAC-SHA256(api_secret_key, raw_body)` and compares it to the header value — the `shop` header plays no role in this check — then forwards `request.shop` straight into `WebhookMetadata` given to the app's handler: [3](#0-2) [4](#0-3) 

Crucially, `api_secret_key` is the app's single `client_secret` — it is identical for every shop that installs the app, not a per-shop value. This means a valid `(raw_body, hmac)` pair generated for **any** shop that has the app installed (including one controlled entirely by the attacker) will also validate for a forged request that declares a *different* `shop` header.

The identity binding that should hold is:
`shop asserted to the handler (request.shop)` == `shop that actually produced the HMAC-signed body`

This binding is broken: the HMAC only proves "some installed shop sent this exact body," not "this specific shop sent this body." The app's `WebhookHandler` is documented to trust `data.shop` as the tenant identifier for the event, per the gem's own documentation: [5](#0-4) 

### Impact Explanation
This enables cross-tenant data confusion/injection: an attacker who installs the app on their own store (an ordinary, unprivileged action available to anyone) can trigger any webhook topic on their own shop, capture the genuine `(raw_body, x-shopify-hmac-sha256)` pair Shopify sends to the app's callback URL, and then replay that exact body/HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `Registry.process` will accept it as authentic (the HMAC check only covers the body) and hand the forged `shop` value to the app's handler as if the event genuinely originated from the victim shop. Any app logic that uses `data.shop` to look up/update per-tenant records (exactly as shown in this gem's own documentation example, `perform_later(topic: data.topic, shop_domain: data.shop, ...)`) will operate on the wrong tenant using attacker-supplied (though structurally valid, e.g. `orders/create`) body content — a cross-tenant access/data-integrity issue.

### Likelihood Explanation
High. Becoming an "attacker shop" requires nothing more than installing the app once (a normal unprivileged flow), after which capturing a legitimate `(body, hmac)` pair is trivial (it's simply the payload Shopify sends to the app's own webhook URL). Forging the `shop` header on a replayed POST requires no secret knowledge at all, since HTTP headers are attacker-controlled on any raw request the app's server accepts.

### Recommendation
Include the shop domain (and ideally topic/api-version) in the HMAC-signed content, or otherwise cryptographically bind the `shop` value to the verified payload before trusting it, e.g. by having `Request#to_signable_string` incorporate `shop`/`topic` alongside `raw_body`, or by validating in `Registry.process` that the shop asserted in the request actually owns the webhook subscription referenced (e.g., cross-check against `webhook_id`/registered subscriptions per shop) rather than trusting the header verbatim.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (normal, unprivileged install).
2. Attacker triggers a webhook subscribed by the app (e.g., `orders/create`) on their own shop; Shopify POSTs to the app's webhook endpoint with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC of raw_body with app's client_secret>`, and some `raw_body`.
3. Attacker captures this exact `raw_body` and `x-shopify-hmac-sha256` value.
4. Attacker sends a new POST directly to the app's webhook endpoint with the same `raw_body` and `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request.new` parses this into a request object; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only hashes `@raw_body` — it passes.
6. The app's `WebhookHandler#handle` is invoked with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: <attacker's body>, ...)`, causing the app to act on `victim-shop.myshopify.com`'s tenant data using attacker-supplied content.
