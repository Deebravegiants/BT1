### Title
Relayer's tx.origin is inherited by attacker-controlled destination code during `dispatchIncoming`, risking relayer fund loss to tx.origin-checking contracts - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatchIncoming` executes a low-level `.call()` to `request.to`, a destination address that is fully controlled by the source-chain application dispatching the cross-chain message, in the same transaction the relayer submits to `HandlerV2`. Because the relayer is the transaction originator, `tx.origin` throughout this entire call chain is the relayer's EOA. Any contract targeted by a malicious `PostRequest` can therefore make further external calls that surface `tx.origin` as the relayer's address, exactly matching the reported vulnerability class.

### Finding Description
The delivery path is: a relayer calls `HandlerV2.handlePostRequests` (or similar), which after proof verification calls `host.dispatchIncoming(request, _msgSender())`, where `_msgSender()` is `msg.sender` of the relayer's own transaction. [1](#0-0) 

`EvmHost.dispatchIncoming` then performs an unrestricted low-level call into an arbitrary destination decoded from the request body (`request.to`), invoking `IApp.onAccept`: [2](#0-1) 

The only gating on `destination` is an `extcodesize` check (must be a contract) — there is no restriction on what that contract's code does once called. Because `request.to`/`request.body`/the contract's own logic is entirely determined by whatever application dispatched the request on the *source* chain (permissionless dispatch), an attacker can pre-deploy a malicious contract at an address they control and dispatch a `PostRequest` targeting it. When any relayer (chosen adversarially or opportunistically) delivers that message, the malicious contract's `onAccept` executes inside the relayer's own transaction, with `tx.origin` equal to the relayer's EOA. From there the malicious contract can call into any third-party protocol that authorizes actions via `tx.origin` (e.g., session-key patterns, third-party deposit/withdraw flows) instead of `msg.sender`, and drain funds belonging to that `tx.origin`-checked account — which happens to be the relayer's address.

This is the direct on-chain analog of the audited "Relayer could lose funds" finding: the reachable, unprivileged surface is the message body/destination crafted by any source-chain application, delivered by any permissionless relayer, with `tx.origin` propagated unchanged through `EvmHost.dispatchIncoming`'s low-level `.call()`.

### Impact Explanation
Relayer operators run automated, funded EOAs (as documented, "relayers EOA should be single-purpose"), but nothing in the protocol enforces or technically requires isolation — the vulnerability is a protocol-level design property, not merely an operational recommendation. Any relayer that reuses an EOA holding balances/approvals in a `tx.origin`-checking external contract can have those funds withdrawn without consent, purely by delivering a maliciously crafted but otherwise valid cross-chain message. This is a Medium-severity fund-loss risk for relayer operators, consistent with the original report's Medium rating (Connext: "to be documented", Spearbit: "Acknowledged").

### Likelihood Explanation
Likelihood is limited by real-world prevalence of `tx.origin`-based authorization patterns in third-party protocols the relayer might interact with elsewhere. However, the attack requires no privileged access: any account can dispatch a `PostRequest` targeting an attacker-controlled contract, and any relayer executing normal, expected duties (delivering all valid messages for fee revenue) will trigger it. No proof forgery or consensus compromise is needed.

### Recommendation
- Document explicitly (as Connext did) that relayer signing keys must be single-purpose, freshly-generated, isolated EOAs never used to interact with, hold funds in, or receive approvals from any other protocol.
- Consider architectural mitigations such as having `EvmHost.dispatchIncoming` route the destination call through an intermediate minimal-privilege forwarding contract so that `tx.origin` is never the relayer's actual signing key (e.g., wrap the call so `tx.origin` becomes a purpose-built forwarder), removing reliance purely on operational hygiene.

### Proof of Concept
1. Attacker deploys `MaliciousApp` on chain B implementing `onAccept(IncomingPostRequest calldata)` that calls `SomeLendingProtocol.withdrawOnBehalfOfOrigin()` — a hypothetical (but realistic) pattern where a foreign protocol authorizes withdrawals based on `tx.origin` rather than `msg.sender`, and where the relayer's EOA happens to hold a position.
2. Attacker dispatches a `PostRequest` on chain A with `to = address(MaliciousApp)` and any dummy body; no fee is required for the message to be deliverable by an altruistic/opportunistic relayer, or attacker can attach a fee to guarantee pickup.
3. A relayer submits proofs via `HandlerV2`, which calls `EvmHost.dispatchIncoming(request, relayer)` on chain B. [3](#0-2) 
4. `MaliciousApp.onAccept` executes with `tx.origin == relayer`, and its internal call into `SomeLendingProtocol` succeeds because that protocol trusts `tx.origin`, draining the relayer's funds there.

    /**
     * @dev Dispatch an incoming POST request to destination module
     * @param request - post request
     */
    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }
