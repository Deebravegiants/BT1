### Title
Unsigned `feeStructure.feeToken` and `relay` in Emporium wallet-op flow allow draining arbitrary ERC20 tokens held by a `HinkalWallet` - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
When a user routes an Emporium transaction through their `HinkalWallet` (a persistent smart-contract wallet holding the user's on-chain assets), the EIP-712 message the user signs only commits to `emporiumMessage`, the hash of `ops`, `maxFee`, and `deadline`. It does **not** commit to `feeStructure.feeToken` or `circomData.relay`. Because of this, the caller submitting the transaction (a relay/prover) can pick an arbitrary ERC20 token as the "fee token" and route up to `maxFee` of that token — a token completely unrelated to the transaction being executed — straight out of the user's wallet to any whitelisted relay address, without the wallet owner ever authorizing that specific asset movement.

### Finding Description
`EmporiumUpgradeable.verifyWallet` recovers the signer over: [1](#0-0) 

This hash covers `circomData.emporiumMessage`, `_hashEmporiumOps(stack.ops)`, `stack.maxFee`, and `stack.deadline` only. The only fee-related check enforced against the signature is a numeric ceiling: [2](#0-1) 

`feeStructure.feeToken` and `circomData.relay` are never part of the EIP-712 payload, so the signer never authorizes *which token* or *which relay* the fee is paid in/to.

After running the (signed) `ops`, `payRelayFees` is invoked: [3](#0-2) 

For the "Emporium-min" path (`externalActionId == HINKAL_EMPORIUM_ACTION_ID && erc20TokenAddresses.length == 0`, i.e. a pure wallet-op call with no shielded value moved), the `deltaAmountChanges`/`erc20TokenAddresses` loops are empty, so `foundToken` stays `false` and the flat-fee branch fires unconditionally whenever `feeStructure.flatFee != 0`: [4](#0-3) 

Since `signerAddress != address(0)`, this routes to `sendToRelayFromWallet`, which calls the wallet directly: [5](#0-4) 

And `HinkalWallet.doSendToRelay` unconditionally transfers `erc20TokenAddress`/`actualAmount` out of the wallet to `relay`, gated only by `onlyEmporium`: [6](#0-5) 

Neither `feeStructure` nor `relay` is bound by the wallet-owner's signature, and for this zero-token path they are also not bound by the ZK proof: `formInputEmporiumMin` only feeds `emporiumMessage`, `timeStamp`, and `calldataHash` into the circuit's public input: [7](#0-6) 

`calldataHash` is only checked for internal consistency between the submitted calldata and its hash in `HinkalHelper.performHinkalChecks` — it is not a proof that the wallet owner approved `feeStructure`/`relay`, since the caller controls the full `circomData` payload (including `feeStructure` and `relay`) that gets hashed: [8](#0-7) 

As a result, any whitelisted relay (which just needs `tx.origin == relay` and to be in the relay list per `relayerIsValid`) submitting a legitimately-signed `EmporiumStack` can independently choose `feeStructure.feeToken` to be **any ERC20 token the `HinkalWallet` happens to hold**, and drain up to `stack.maxFee` of that unrelated token to itself, entirely outside of what the user signed for. [9](#0-8) 

### Impact Explanation
This is an unauthorized wallet operation: value is moved out of the user's `HinkalWallet` (a call the relay/prover was never authorized by the signer to make on that specific token/relay pair) — matching the "High" impact category of "executing calls or moving assets a wallet owner or prover never authorised." A malicious or compromised whitelisted relay can repeatedly siphon any ERC20 balance sitting in a user's `HinkalWallet` (e.g., leftover swap outputs, airdropped tokens, dust from prior emporium ops) as "fees," up to `maxFee` per signed message, with the wallet owner having only authorized a fee bound in an unspecified token, not the actual token drained.

### Likelihood Explanation
Requires a malicious or compromised whitelisted relay (an unprivileged-EOA analog once whitelisted, and relay whitelisting is intended to be permissionless/rotatable per the RelayStore design) to submit an otherwise-valid, user-signed Emporium message with `feeStructure.flatFee > 0`, `feeStructure.feeToken` set to a token the wallet holds, and `deadline`/`maxFee` still satisfied. Since these fields are entirely relay-controlled and the user's signature never pins them, exploitation only needs the relay to observe a `HinkalWallet` address holding some ERC20 balance and craft the transaction — no wallet-owner or admin key needed.

### Recommendation
Include `feeStructure.feeToken`, `feeStructure.flatFee` (or the whole `feeStructure`), and `circomData.relay` in the EIP-712 `EMPORIUM_SIGNATURE_TYPEHASH` payload so the wallet owner explicitly authorizes which token and which relay the fee is paid to, mirroring how `ops` are bound today. Alternatively, restrict `feeStructure.feeToken` to be one of `circomData.erc20TokenAddresses` even in the zero-token Emporium-min path, and/or require `relay`/`feeToken` to be part of the ZK public input for all Emporium action variants, not just the token-bearing path.

### Proof of Concept
1. User signs an `EmporiumStack` (`ops`, `maxFee = X`, `deadline`) for a benign wallet operation with `erc20TokenAddresses.length == 0` (Emporium-min path).
2. A whitelisted relay submits `Hinkal.transact` with the valid signature, but sets `circomData.feeStructure = {feeToken: TOKEN_HELD_BY_WALLET, flatFee: X, variableRate: 0}` and `circomData.relay = <itself>`.
3. `verifyWallet` passes (signature only covers ops/maxFee/deadline/message; `flatFee (X) <= maxFee (X)` passes).
4. `payRelayFees` takes the `!foundToken && feeStructure.flatFee != 0` branch (no token loop entries exist) and calls `sendToRelayFromWallet` → `HinkalWallet.doSendToRelay(relay, X, TOKEN_HELD_BY_WALLET)`, transferring `X` of `TOKEN_HELD_BY_WALLET` from the wallet to the relay — a token/amount pair the user never signed off on.

```text
    function payRelayFees(
        CircomData calldata circomData,
        address signerAddress,
        int256[] calldata deltaAmountChanges
    ) internal {
        FeeStructure calldata feeStructure = circomData.feeStructure;

        bool foundToken = false;

        for (uint256 i = 0; i < circomData.erc20TokenAddresses.length; i++) {
            // tokens deposited into Emporium are not charged
            if (deltaAmountChanges[i] >= 0) {
                continue;
            }

            address erc20TokenAddress = circomData.erc20TokenAddresses[i];
            bool isFeeToken = erc20TokenAddress == feeStructure.feeToken;

            if (isFeeToken) {
                foundToken = true;
            }

            uint256 relayFee = 0;
            uint256 flatFee = isFeeToken ? feeStructure.flatFee : 0;

            if (signerAddress == address(0)) {
                uint256 sumAbs = uint256(-deltaAmountChanges[i]);

                EmporiumStorageVars storage $ = _getEmporiumStorage();
                relayFee = $._hinkalHelper.calculateRelayFee(
                    sumAbs,
                    flatFee,
                    feeStructure.variableRate
                );
            } else {
                relayFee = flatFee;
            }

            payRelay(
                circomData.relay,
                signerAddress,
                relayFee,
                erc20TokenAddress
            );
        }

        if (!foundToken && feeStructure.flatFee != 0) {
            require(
                signerAddress != address(0),
                "Gas Token in Emporium is not found"
            );

            payRelay(
                circomData.relay,
                signerAddress,
                feeStructure.flatFee,
                feeStructure.feeToken
            );
        }
```
