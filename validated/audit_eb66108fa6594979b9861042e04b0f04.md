### Title
Webhook Shop Identity Spoofing via HMAC Scope Mismatch - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature only over the raw request body, while the shop identity (`shop`) that the registry hands to application webhook handlers is taken from an unauthenticated HTTP header. Because the app's webhook secret (`api_secret_key`) is shared across every shop that installs the app, any shop owner can legitimately receive a genuinely signed webhook for their own store and then replay that exact body/HMAC pair against the app's webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop. The signature still validates, and the handler is invoked believing the data belongs to the victim tenant.

### Finding Description
`Utils::HmacValidator.validate` computes the expected signature from `verifiable_query.to_signable_string` and compares it with the request's `hmac`: [1](#0-0) 

For webhooks, `to_signable_string` returns only the raw JSON body — it does not include the topic, shop domain, webhook id, or api version headers: [2](#0-1) 

`shop` is read straight from the `x-shopify-shop-domain` (or legacy `shopify-shop-domain`) header, a value that is never included in the signed payload: [3](#0-2) 

`Registry.process` only checks `Utils::HmacValidator.validate(request)` (i.e., body integrity) and then dispatches to the handler using `request.shop` as the tenant identifier, with no additional binding between the verified body and the claimed shop: [4](#0-3) 

The equality the library implicitly claims is:
`HMAC-verified(body) == authenticated(shop, topic, webhook_id)`

but what is actually true is:
`HMAC-verified(body only) ≠ authenticated(shop header)`

Since the same `api_secret_key` is used to sign webhooks for every shop that installs a given app (it is the app's secret, not a per-shop secret), a valid `(body, hmac)` pair obtained from one authentic delivery (e.g., to the attacker's own store) remains cryptographically valid for that body regardless of which shop-domain header accompanies it. An attacker who installs the target app on their own Shopify store (an ordinary, unprivileged action available to any merchant/developer) will receive real, correctly-signed webhook deliveries. They can capture one such delivery and resend it to the app's webhook endpoint with the `x-shopify-shop-domain` header changed to another (victim) shop the attacker does not control. `HmacValidator.validate` still succeeds because it only checks the body, and `Registry.process` invokes the app's handler with `WebhookMetadata` claiming the victim's shop.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook processing: the shop identity handed to the application layer is not actually authenticated by the HMAC, only the body is. Any application logic that trusts `WebhookMetadata#shop` to scope data writes/reads (e.g., "process this order for shop X", "mark subscription active for shop X") can be tricked into acting on/for a victim tenant using attacker-supplied body content that was only ever signed for the attacker's own shop. This is a cross-tenant access primitive delivered purely by an unprivileged internet user/merchant with no access to the app's `client_secret`.

### Likelihood Explanation
Exploitation only requires: (1) installing the target app on an attacker-controlled Shopify development/trial store (routine, unprivileged), (2) capturing one genuine webhook delivery for a topic whose body doesn't strictly require shop-specific values to be dangerous (many topics carry attacker-influenced or attacker-chosen data, e.g., `carts/update`, `app/uninstalled`, product/order test data the attacker fully controls in their own store), and (3) replaying it with a different `shop-domain` header value. No cryptographic secret needs to be recovered.

### Recommendation
Include the shop domain (and ideally topic/webhook id) inside the HMAC-covered signable string, or otherwise cryptographically bind the claimed `shop` header to the verified payload before it is handed to `WebhookMetadata`/handlers. At minimum, document and enforce that `request.shop` must be cross-checked against an out-of-band trusted source (e.g., session/shop registered for that webhook subscription) rather than trusted solely because `HmacValidator.validate` returned true.

### Proof of Concept
1. Install the target Shopify app on an attacker-owned development store (`attacker-shop.myshopify.com`).
2. Trigger a webhook whose body the attacker can influence/control, e.g. `carts/update`, and capture the real delivery:
   - Headers: `x-shopify-hmac-sha256: <valid_hmac_for_body>`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: carts/update`
   - Body: attacker-chosen JSON.
3. Resend the identical body and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but replace the header:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
4. `Utils::HmacValidator.validate` recomputes the HMAC over the (unchanged) body only and succeeds: [5](#0-4) 
5. `Registry.process` calls the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, so the app processes attacker-controlled data as if it originated from the victim shop: [6](#0-5)
