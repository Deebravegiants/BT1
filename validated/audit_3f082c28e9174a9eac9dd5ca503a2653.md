### Title
`Pool::recapitalize` refunds "excess" tokens without verifying any deposit occurred, letting anyone drain pool custody while the cash book still reports solvency - ([File: contracts/pool/src/ops/recapitalize.rs])

### Summary
`recapitalize` credits `min(amount, backing_shortfall)` to the market's `cash` book and unconditionally transfers `amount - applied` tokens back to `payer`. It never verifies that `amount` tokens were actually transferred into the pool beforehand — it assumes the controller did so in a prior call. When the market has no backing shortfall (`applied == 0`), the entire declared `amount` is refunded to an arbitrary `payer` address. An unprivileged caller can invoke `recapitalize` directly on the pool with `amount` equal to the pool's full token balance and receive every token of custody, while the `cash` ledger is unchanged and continues to overstate reserves.

### Finding Description
The bug class in the report is a state-changing entrypoint that skips a precondition check ("is the loan funded?"), producing an irreversible inconsistent state. The analog in XOXNO Lending is `contracts/pool/src/ops/recapitalize.rs`:

- `accounting` computes `applied = amount.min(guards::backing_shortfall(&cache))` and `refund = amount - applied`, credits only `applied` to `cash`, and commits (lines 52–58).
- `apply` then calls `outcome.cache.transfer_out(&payer, outcome.refund)` unconditionally (line 34).
- The doc comment states the trust assumption: "The controller transfers `amount` into the pool before this call" — but no balance-delta measurement or any other check enforces it.

On a healthy market, `backing_shortfall == 0`, so `applied == 0`, `cash` is unchanged, and `refund == amount` is transferred to `payer`. The in-repo test `test_unfunded_recapitalize_leaves_the_cash_book_overstating_custody` (`contracts/pool/tests/flows.rs:3408`) proves the attack: a direct `recapitalize` call with `payer = attacker` and `amount = pool balance` drains custody to zero while `state_snapshot().cash` still shows the deposited funds (lines 3430–3439).

### Impact Explanation
Two compounding impacts, both reachable in one permissionless call:

1. **Theft of user funds.** The attacker receives the pool's entire token balance as the "refund" of a deposit that never happened.
2. **Frozen funds / broken solvency accounting for anyone remaining.** The `cash` book still reports the drained funds as present. `Cache::require_reserves` reads the book, not the balance, so withdrawals pass the pool's liquidity guard and then revert inside the SAC transfer (`BalanceError = 10`), as the test asserts at lines 3441–3477. Suppliers' exits fail indefinitely — permanent freezing of their funds — and the market reports itself solvent while unable to pay.

### Likelihood Explanation
High for a motivated attacker. The call requires no collateral, no position, no privilege, and no capital — the pool pays out its own balance. The only precondition is a market whose `backing_shortfall` is less than the desired refund, which trivially includes `0` (any healthy market). The attacker's only cost is the transaction invocation.

### Recommendation
Enforce the funding precondition before paying the refund, mirroring the fix recommended in the report:

- Measure the pool's token balance delta across the recapitalize call (snapshot the SAC balance at entry, require `balance_after - balance_before >= applied` before `transfer_out`), or
- Restrict `recapitalize` to the controller entrypoint (`Controller::recapitalize`) where the inbound transfer is executed atomically in the same call, and reject direct pool invocations, and
- Cap `refund` by the actual increase in the pool's token balance rather than by `amount - applied` alone.

### Proof of Concept
Modeled on the existing test `test_unfunded_recapitalize_leaves_the_cash_book_overstating_custody` in `contracts/pool/tests/flows.rs:3408-3483`:

```rust
// Setup: pool holds `deposit` tokens backing a live supplier.
let deposit = 10_000_000_000i128;
token_admin.mint(&t.pool, &deposit);
t.client().supply(&t.sup(0, deposit));

// Attacker calls recapitalize directly on the pool. No tokens are sent.
// Healthy market => backing_shortfall == 0 => applied == 0,
// refund == amount => the whole balance is transferred to `attacker`.
let attacker = Address::generate(&t.env);
let custody = token.balance(&t.pool);
t.client().recapitalize(&hub(&t.asset), &attacker, &custody);

assert_eq!(token.balance(&t.pool), 0);          // custody drained
assert_eq!(token.balance(&attacker), custody);  // attacker holds it all
assert_eq!(t.state_snapshot().cash, deposit);   // book still claims solvency

// The legitimate supplier's withdraw now passes require_reserves (book says
// cash is there) and reverts inside the SAC transfer with BalanceError = 10.
let outcome = t.client().try_withdraw(&receiver, &false, &t.wdr(supplied, i128::MAX, 0));
assert!(outcome.is_err()); // Error 10, not InsufficientLiquidity/PoolInsolvent
```

Entrypoint: `Pool::recapitalize(hub_asset, payer, amount)` — a direct call to the pool contract, reachable by any address; equivalently the class maps to `Controller::recapitalize` whenever the refund leg can be settled without a matching inbound transfer.
